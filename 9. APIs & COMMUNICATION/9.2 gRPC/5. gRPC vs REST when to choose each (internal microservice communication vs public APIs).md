# gRPC vs REST: When to Choose Each — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why the Choice Matters

**Q1. Why is the gRPC vs REST decision consequential enough to design around, rather than defaulting to one for everything?**
A: The choice of communication protocol is not cosmetic — it embeds assumptions about clients, schema contracts, operational tooling, and performance characteristics that are expensive to change after the fact. Migrating a public API from REST to gRPC means breaking every client that integrated with it; migrating an internal service mesh from REST to gRPC requires updating code generation pipelines, deployment tooling, and observability across every service. The decision deserves deliberate reasoning rather than convention.

Three dimensions drive the choice:

- **Who calls the API**: A public API must be callable from browsers, mobile apps, third-party developers with arbitrary HTTP clients, and curl. A gRPC API requires a generated client stub — most browsers cannot call gRPC directly without a translation layer. Internal microservices are controlled environments: you choose the client, you generate the stub, you own both sides.
- **Contract rigidity vs. flexibility**: gRPC requires a `.proto` schema defining every field, type, and RPC before any code is written. REST allows incremental, schema-optional evolution — you can add a JSON field without regenerating anything. For internal services with known, stable interfaces this rigidity is a feature; for exploratory public APIs it is friction.
- **Performance envelope**: gRPC over HTTP/2 with protobuf binary serialization uses dramatically less bandwidth and CPU than REST over HTTP/1.1 with JSON. For a microservice that processes 50,000 requests per second, this difference is measurable in infrastructure cost. For a public API handling 100 requests per second, it is irrelevant.

The answer is almost never "gRPC everywhere" or "REST everywhere" — it is "gRPC for internal service-to-service communication where both sides are controlled, REST for public APIs and browser-facing endpoints." Understanding exactly why and the exceptions to that rule is what the interview probes.

**Q2. What are the fundamental architectural differences between gRPC and REST?**
A: They differ across five dimensions:

**Transport and protocol:**
- REST: HTTP/1.1 (overwhelmingly) or HTTP/2. One request per TCP connection in HTTP/1.1 (with pipelining limitations); connection pooling required for concurrency.
- gRPC: HTTP/2 exclusively. Multiple RPCs multiplex over a single TCP connection — no head-of-line blocking, no connection pool overhead, native bidirectional streaming.

**Serialization:**
- REST: JSON (dominant), occasionally XML or MessagePack. Text-based; self-describing (field names in every payload); human-readable without tooling.
- gRPC: Protocol Buffers (default). Binary; schema-required for decoding; not human-readable without tooling (`grpc_cli`, `grpcurl`, or reflection).

**Interface definition:**
- REST: No mandatory IDL. OpenAPI/Swagger is the convention, not a requirement. The API can be defined informally, evolved without schema updates, and consumed by any HTTP client.
- gRPC: `.proto` file is mandatory. Every message, field, and RPC must be defined before code generation. Schema is the source of truth; client and server stubs are generated from it.

**Communication patterns:**
- REST: Request/response only. Webhooks, SSE, or WebSockets required for streaming and push patterns — each a different protocol with different operational concerns.
- gRPC: Four native patterns (unary, server streaming, client streaming, bidirectional streaming) over the same HTTP/2 connection with the same API design model.

**Browser and ecosystem support:**
- REST: First-class browser support via `fetch`, `XMLHttpRequest`, curl, and every HTTP library ever written. Zero setup.
- gRPC: Not directly callable from browsers (HTTP/2 framing is inaccessible to browser JavaScript). Requires gRPC-Web proxy (Envoy) for browser clients. Command-line tooling (`grpcurl`) less ubiquitous than `curl`.

## Section 2: REST — Strengths and Ideal Contexts

**Q3. What are REST's genuine strengths, and what does it do better than gRPC structurally?**
A: REST's strengths are not merely "it's simpler" — each maps to a structural property:

**Universal client compatibility:**
Every platform, language, and runtime that can make an HTTP request can consume a REST API. A mobile app, a browser, a bash script, a Python notebook, a third-party integration partner — all use the same `curl` or `fetch` semantics with no generated stubs. This zero-friction client story is REST's most durable advantage and the primary reason public APIs default to it.

**Human readability and debuggability without tooling:**
A REST response is inspectable with `curl` and readable in a terminal. JSON error messages are readable without schema files. This lowers the debugging barrier significantly — an engineer can investigate a production issue without setting up `grpcurl`, knowing the proto definition, or having reflection enabled on the server.

```bash
# REST: works immediately, everywhere
curl -H "Authorization: Bearer $TOKEN" \
     https://api.example.com/payments/pay_001 | jq .

# gRPC: requires grpcurl, proto file or server reflection, correct call format
grpcurl -H "Authorization: Bearer $TOKEN" \
        -d '{"payment_id": "pay_001"}' \
        api.example.com:443 \
        com.example.payments.v1.PaymentService/GetPayment
```

**Caching infrastructure integration:**
HTTP GET semantics enable response caching at every layer — browser cache, CDN edge (Cloudflare, CloudFront), reverse proxy (Nginx, Varnish). A `GET /exchange-rates/USD-INR` response with `Cache-Control: public, max-age=300` is served from CDN edge for 5 minutes with zero origin hits. gRPC has no caching semantics — all RPCs go to the origin.

**Ecosystem maturity:**
REST's ecosystem is 25 years deep: API gateways, rate limiters, WAFs, authentication middleware, monitoring dashboards, documentation generators, mock servers, contract testing frameworks — all built REST-first. gRPC equivalents exist but are younger, less battle-tested, and require more configuration.

**Schema-optional evolution:**
Adding a field to a REST JSON response requires no client update — tolerant JSON parsers ignore unknown fields. Adding a field to a proto schema requires regenerating stubs and redeploy, even if the client doesn't use the field. For exploratory APIs where the schema is evolving quickly, REST's schemaless flexibility is an asset.

**Q4. What are REST's weaknesses that gRPC addresses?**
A: REST's weaknesses are not about being "old" — they are structural limitations of its design:

**HTTP/1.1 head-of-line blocking:**
In HTTP/1.1, one connection serves one request at a time (without pipelining). Concurrent requests require multiple connections — browsers open 6 connections per host; microservices maintain connection pools. Connection pool management adds latency, memory overhead, and operational complexity. gRPC's HTTP/2 multiplexing eliminates this: 100 concurrent RPCs share one TCP connection.

**JSON verbosity at high throughput:**
JSON field names repeat in every message. A service processing 100,000 requests/second of `{"payment_id":"...","amount":500,"currency":"INR","status":"PENDING"}` transmits field names in every single payload. At scale this is hundreds of megabytes of bandwidth per second for metadata that both sides already know from the schema. Protobuf's field number encoding transmits the same information in 20–30% of the bytes.

**No native streaming:**
REST has no first-class streaming primitive. Long-polling, SSE, and WebSockets each solve different streaming use cases but are operationally separate from the REST API — different connection management, different authentication flows, different load balancer configuration. gRPC streaming is native to the protocol: the same auth headers, the same load balancer, the same monitoring.

**No schema enforcement at the protocol level:**
A REST API that adds a required field has no mechanism to enforce that clients send it until runtime — the server rejects requests, clients update code, a deployment cycle passes. Proto schemas catch this at compile time: the generated stub will not compile if a required field is missing. For internal services where both sides are owned, compile-time safety is strongly preferable to runtime discovery.

**No type-safe generated clients:**
REST clients are either hand-written or generated from OpenAPI specs — a two-step process (write the spec, generate the client) that diverges if the spec is not kept in sync with the implementation. gRPC clients are generated directly from the `.proto` that the server implements — the client and server are guaranteed to agree on field types and RPC signatures at the code-generation step.

## Section 3: gRPC — Strengths and Ideal Contexts

**Q5. What are gRPC's genuine strengths, and what does it do better than REST structurally?**
A: gRPC's advantages are most pronounced in controlled, high-throughput, polyglot internal service environments:

**HTTP/2 multiplexing and connection efficiency:**
All RPCs from one service to another share a single TCP connection. No connection pool management, no connection establishment latency for concurrent requests, no TCP slow-start penalty per request. For a service making 1,000 concurrent downstream calls, this eliminates 999 TCP connection establishments and the associated kernel overhead.

```
REST (HTTP/1.1):
  Service A → [TCP conn 1] → Payment Service  (request 1)
  Service A → [TCP conn 2] → Payment Service  (request 2)
  Service A → [TCP conn 3] → Payment Service  (request 3)
  ... (connection pool of N connections)

gRPC (HTTP/2):
  Service A → [TCP conn 1] → Payment Service  (request 1, stream 1)
                                               (request 2, stream 3)
                                               (request 3, stream 5)
  All multiplexed; single connection
```

**Strongly typed, generated clients in any language:**
One `.proto` file generates correct, type-safe client stubs in Go, Java, Python, Node.js, Ruby, C++, and more. All stubs are guaranteed to agree with the server — a field type change in the proto is caught at compile time across every language simultaneously. In a polyglot microservices system (Go payment service, Java fraud service, Node.js notification service), this cross-language type safety is irreplaceable.

**Native streaming:**
Server streaming, client streaming, and bidirectional streaming are first-class RPC patterns with the same operational model as unary calls. A `StreamPaymentEvents` RPC delivers real-time payment updates to subscribers over the same authenticated, load-balanced, monitored connection as `CreatePayment`. No separate WebSocket infrastructure, no SSE endpoint, no long-polling logic.

**Deadlines and cancellation propagated through the call chain:**
gRPC deadlines are distributed — a client sets a deadline, and that deadline context propagates through every service in the call chain. When the deadline expires, every service in the chain cancels its in-progress work. REST has no equivalent: timeouts are per-hop connection timeouts, not end-to-end call chain deadlines. A 3-second deadline in gRPC means the entire chain of calls (A → B → C → D) has 3 seconds total; a 3-second timeout in REST means each hop has 3 seconds independently, allowing a chain of 5 hops to take 15 seconds.

**Interceptors — cross-cutting concerns as middleware:**
gRPC interceptors (the equivalent of HTTP middleware) apply to all RPCs uniformly — authentication, distributed tracing, logging, rate limiting, retry logic, and circuit breaking are configured once and applied everywhere:

```go
// One interceptor applies to every RPC in the service
server := grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        authInterceptor,        // validates JWT/mTLS
        tracingInterceptor,     // OpenTelemetry span injection
        loggingInterceptor,     // structured request/response logging
        rateLimitInterceptor,   // per-client rate limiting
        recoveryInterceptor,    // panic recovery → INTERNAL status
    ),
)
```

The equivalent in REST requires middleware to be applied consistently across every router, every endpoint, every framework — a more fragile proposition.

**Q6. What are gRPC's weaknesses that constrain where it can be used?**
A: gRPC's weaknesses are not incidental — they reflect structural trade-offs in its design:

**No direct browser support:**
HTTP/2's binary framing layer is inaccessible to browser JavaScript. The `fetch` API and `XMLHttpRequest` operate at the HTTP request/response level, not the HTTP/2 frame level. gRPC-Web exists as a workaround — a JavaScript client that sends gRPC-encoded payloads over HTTP/1.1 or HTTP/2, with an Envoy proxy translating to native gRPC on the backend — but it requires infrastructure (the Envoy sidecar) and loses native gRPC streaming in older browsers.

```
Browser                  Envoy Proxy              gRPC Service
  ──────                 ───────────              ────────────
  fetch() ──HTTP/1.1──→  gRPC-Web translation  ──gRPC/HTTP2──→  handler
  (gRPC-Web encoded)     (Envoy)                (native gRPC)
```

This is not a minor operational detail — it means gRPC cannot be the public-facing protocol for any API that browser clients consume without a dedicated translation proxy.

**Tooling and debugging friction:**
Binary protobuf payloads require schema files to decode. `curl` cannot be used for ad-hoc testing. Server reflection must be explicitly enabled for `grpcurl` to work without providing the proto file. Log aggregation systems that capture raw HTTP payloads cannot display gRPC message contents without a protobuf decoder. Every layer of the operational stack requires additional configuration that REST gets for free.

**Limited HTTP ecosystem integration:**
API gateways (AWS API Gateway, Kong, Apigee), WAFs, CDNs, and most third-party HTTP middleware are built for REST. gRPC support is available but often second-class — fewer features, less documentation, more configuration. Rate limiting, request transformation, and analytics features that work out-of-the-box for REST APIs require custom configuration or plugins for gRPC.

**Schema rigidity during rapid iteration:**
During early-stage development when the API shape is still evolving, maintaining a `.proto` file, running `protoc`, and regenerating stubs on every schema change is friction. REST's ability to add a JSON field with no schema update enables faster iteration. The rigidity that protects production schemas is a hindrance in the exploratory phase.

**Load balancer compatibility:**
REST load balancing at L7 (HTTP) is universal — every load balancer understands HTTP/1.1 requests. gRPC's HTTP/2 multiplexing breaks naive L4 (TCP) load balancing: all requests from a client share one TCP connection, which always routes to the same backend instance — no load distribution. Correct gRPC load balancing requires L7 HTTP/2-aware load balancers (Envoy, AWS ALB with HTTP/2 target, Nginx 1.13.10+, or client-side load balancing). This is solvable but adds operational complexity that REST over HTTP/1.1 does not have.

## Section 4: The Decision Framework

**Q7. What is the decision framework for choosing gRPC vs REST for a given service interface?**
A: The framework has four sequential questions. Stop at the first question that produces a clear answer:

**Question 1: Who are the callers?**
```
External / public callers (third-party developers, browsers, mobile apps, partners)?
  → REST. Non-negotiable. gRPC-Web is not a reasonable requirement for external callers.

Internal callers only (services you own and deploy)?
  → Continue to Question 2.
```

**Question 2: Is streaming a first-class requirement?**
```
Bidirectional streaming, server push, or client upload streams?
  → gRPC. REST cannot model these natively; WebSocket/SSE is a different protocol.

Request/response only?
  → Continue to Question 3.
```

**Question 3: What are the throughput and latency requirements?**
```
High throughput (>1,000 req/s per instance) or strict latency SLAs (<10ms p99)?
  → gRPC. The bandwidth and CPU savings from protobuf + HTTP/2 are measurable.
  → The connection multiplexing matters at high concurrency.

Moderate throughput and latency requirements?
  → Continue to Question 4.
```

**Question 4: What is the team's operational maturity with each?**
```
Team has strong gRPC experience, proto toolchain in CI, grpcurl in runbooks?
  → gRPC is operationally acceptable; use it for internal services.

Team is REST-native; gRPC is new territory?
  → REST for now. Operational complexity of gRPC (tooling, load balancing, debugging)
    outweighs benefits at low scale. Revisit when throughput demands it.
```

**The default recommendation from this framework:**
- Public APIs: REST.
- Internal high-throughput or streaming services: gRPC.
- Internal moderate-throughput services with a REST-native team: REST until scale demands otherwise.
- Mixed: REST public facade, gRPC internal mesh (the most common production architecture).

**Q8. How do companies typically combine REST and gRPC in a single architecture?**
A: The dominant pattern in mature microservices architectures is a hybrid: REST at the edge, gRPC internally.

```
                    ┌─────────────────────────────────┐
External clients    │         API Gateway / BFF        │  REST / HTTP
(browser, mobile,   │   (NestJS, Express, Kong)        │  JSON
 third-party)       └──────────────┬──────────────────┘
                                   │ translates REST → gRPC
                    ┌──────────────▼──────────────────┐
                    │       Internal gRPC Mesh          │
                    │                                   │
                    │  PaymentService ←──gRPC──→ FraudService   │
                    │       ↕ gRPC           ↕ gRPC             │
                    │  AccountService ←──gRPC──→ NotificationSvc│
                    └─────────────────────────────────┘
```

**The BFF (Backend for Frontend) / API Gateway pattern:**
A dedicated service (or API gateway layer) receives REST requests from external clients, validates and authenticates them, and translates them into gRPC calls to internal services. The internal services communicate with each other via gRPC. The external contract is REST; the internal contract is gRPC.

```typescript
// NestJS BFF: REST endpoint that calls a gRPC service internally
@Controller('payments')
export class PaymentController {
  constructor(
    @Inject('PAYMENT_SERVICE')
    private readonly paymentClient: ClientGrpc,
  ) {}

  @Post()
  async createPayment(@Body() dto: CreatePaymentDto): Promise<PaymentResponse> {
    // External: REST POST /payments with JSON body
    // Internal: gRPC CreatePayment RPC to PaymentService
    const paymentService = this.paymentClient
      .getService<PaymentServiceClient>('PaymentService');

    const grpcRequest: CreatePaymentRequest = {
      userId:         dto.user_id,
      amount:         { amountMinor: dto.amount_paise, currency: dto.currency },
      idempotencyKey: dto.idempotency_key,
    };

    const response = await firstValueFrom(
      paymentService.createPayment(grpcRequest)
    );

    // Translate gRPC response → REST JSON response
    return {
      payment_id: response.payment.paymentId,
      status:     PaymentStatus[response.payment.status].toLowerCase(),
      amount:     response.payment.amount.amountMinor / 100,
      currency:   response.payment.amount.currency,
    };
  }
}
```

**Why this hybrid is the right default:**
- External clients get the universal REST interface they expect — any HTTP client, no stub generation, human-readable JSON.
- Internal services get gRPC's performance, streaming, type safety, and deadline propagation.
- The translation layer (BFF) is the only place where REST↔gRPC conversion logic lives — not scattered across every internal service.
- The internal proto schema is an implementation detail; external clients never see it.

## Section 5: Operational Considerations

**Q9. How does observability differ between gRPC and REST, and what does each require in production?**
A: Both protocols need the same observability pillars (metrics, tracing, logging), but the tooling and configuration differ enough to matter operationally.

**Metrics:**

REST metrics are captured by HTTP middleware almost universally — request count, latency histograms, status code distributions. Every APM tool (Datadog, New Relic, Prometheus) has out-of-the-box HTTP instrumentation.

gRPC metrics require explicit instrumentation or a framework that provides it. The key metrics differ in naming:
```
REST:             gRPC equivalent:
  http_request_duration_seconds   →  grpc_server_handling_seconds
  http_requests_total             →  grpc_server_handled_total
  http_response_size_bytes        →  grpc_server_msg_sent_bytes
  status_code (200/404/500)       →  grpc_code (OK/NOT_FOUND/INTERNAL)
```

gRPC's status codes are more semantically rich than HTTP codes (14 distinct codes vs. HTTP's 5xx/4xx grouping), but monitoring dashboards built for HTTP status codes don't map cleanly. A `RESOURCE_EXHAUSTED` gRPC error is a rate limit; a `FAILED_PRECONDITION` is a business logic error — both look like "non-OK" in naive monitoring. Dashboards must be gRPC-aware.

**Distributed tracing:**

Both REST and gRPC propagate trace context through headers — REST uses `traceparent` (W3C Trace Context standard) or `X-B3-*` (Zipkin B3 format); gRPC uses metadata (the equivalent of HTTP headers in gRPC). The propagation is functionally equivalent; the difference is implementation:

```javascript
// REST: trace context in HTTP headers (automatic in most frameworks)
fetch(url, { headers: { 'traceparent': '00-traceId-spanId-01' } });

// gRPC: trace context in metadata (requires explicit interceptor)
const metadata = new grpc.Metadata();
metadata.set('traceparent', '00-traceId-spanId-01');
client.createPayment(request, metadata, callback);
```

OpenTelemetry auto-instrumentation handles both, but gRPC requires the gRPC-specific auto-instrumentation plugin, which is less mature than the HTTP plugin in most languages.

**Logging:**

REST request/response logging is trivial — body is JSON text, readable in log aggregators directly. gRPC request/response logging requires decoding binary protobuf, either by logging structured objects (after deserialization) or by configuring a protobuf-aware log decoder. Never log raw binary proto bytes — they are unreadable and waste storage.

```go
// gRPC logging interceptor: log the deserialized struct, not raw bytes
func loggingInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo,
                        handler grpc.UnaryHandler) (interface{}, error) {
    start := time.Now()
    resp, err := handler(ctx, req)

    log.Info("gRPC call",
        zap.String("method",   info.FullMethod),
        zap.Duration("duration", time.Since(start)),
        zap.String("request",  protojson.Format(req.(proto.Message))),   // ← JSON encode proto for logging
        zap.String("status",   status.Code(err).String()),
    )
    return resp, err
}
```

**Q10. How does authentication and authorization differ between gRPC and REST?**
A: The mechanisms are analogous but the implementation details differ:

**JWT / Bearer token:**

REST: `Authorization: Bearer <token>` in HTTP headers — universal, supported by every API gateway and middleware.

gRPC: same token in gRPC metadata — functionally identical, but the header name is `authorization` (lowercase by convention in gRPC metadata):
```go
// gRPC client: attach JWT to metadata
md := metadata.Pairs("authorization", "Bearer "+token)
ctx := metadata.NewOutgoingContext(context.Background(), md)
resp, err := client.CreatePayment(ctx, request)

// gRPC server: extract JWT from metadata
func authInterceptor(ctx context.Context, req interface{}, ...) {
    md, ok := metadata.FromIncomingContext(ctx)
    tokens := md.Get("authorization")  // ["Bearer eyJ..."]
    // validate token...
}
```

**mTLS (Mutual TLS):**
gRPC's HTTP/2 transport runs over TLS by default. Mutual TLS — where the client also presents a certificate — is the standard zero-trust authentication mechanism for service-to-service gRPC calls in a service mesh (Istio, Linkerd). The service mesh sidecar handles certificate rotation and mTLS enforcement transparently; the application code does not need to manage certificates.

REST services can also use mTLS, but it is less commonly configured end-to-end without a service mesh. In practice, REST internal services more often rely on network-level security (VPC, security groups) with per-request JWT tokens, while gRPC internal services in a service mesh use mTLS for transport security and JWT for application-level authorization.

**API keys:**
REST API keys in `X-API-Key` headers are the standard for third-party developer authentication — supported by every API gateway. gRPC API keys go in metadata — supported but not as well-documented in gateway configuration guides. For public-facing APIs with API key auth, REST is the path of least resistance.

**Q11. How does load balancing differ between gRPC and REST, and what are the failure modes?**
A: This is one of gRPC's most significant operational differences from REST.

**REST over HTTP/1.1:**
Each request is an independent TCP connection (or a connection from the pool, but each connection carries one request at a time). L4 (TCP) load balancers distribute connections; L7 (HTTP) load balancers distribute requests. Both work correctly because one connection = one request (approximately).

```
REST with L4 load balancer:
  Client → [TCP conn] → LB → [TCP conn] → Backend 1  (request)
  Client → [TCP conn] → LB → [TCP conn] → Backend 2  (next request)
  Connections distributed → requests distributed ✅
```

**gRPC over HTTP/2 with L4 load balancer — the failure mode:**
HTTP/2 multiplexes all RPCs over one TCP connection. An L4 load balancer routes connections, not requests. Once the single gRPC connection is routed to Backend 1, all 1,000 concurrent RPCs go to Backend 1 — regardless of Backend 2, 3, and 4 sitting idle.

```
gRPC with L4 load balancer:
  Client → [1 TCP conn] → LB → [1 TCP conn] → Backend 1  (ALL 1000 requests)
                                              → Backend 2  (0 requests) ← idle
                                              → Backend 3  (0 requests) ← idle
  TCP connection pinned to Backend 1 → no load distribution ❌
```

**Correct gRPC load balancing options:**

**Option 1 — L7 (HTTP/2-aware) load balancer:**
The load balancer terminates the HTTP/2 connection and makes a new downstream connection per RPC (or per backend, with its own connection pool). AWS ALB with HTTP/2 target groups, Nginx 1.13.10+ with `grpc_pass`, and Envoy all handle this correctly.

```
gRPC with L7 load balancer:
  Client → [1 HTTP/2 conn] → LB → Backend 1  (RPC 1, 4, 7, ...)
                                 → Backend 2  (RPC 2, 5, 8, ...)
                                 → Backend 3  (RPC 3, 6, 9, ...)
  LB distributes individual RPCs ✅
```

**Option 2 — Client-side load balancing:**
The gRPC client maintains connections to all backend instances and distributes RPCs across them using a load balancing policy (round-robin, weighted round-robin, least-loaded). The client must discover all instances via a resolver (DNS, service registry, Kubernetes endpoints):

```go
// Go gRPC client with round-robin client-side load balancing
conn, err := grpc.Dial(
    "dns:///payment-service.prod.svc.cluster.local:50051",
    grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`),
    grpc.WithTransportCredentials(credentials.NewClientTLSFromCert(nil, "")),
)
```

Client-side load balancing eliminates the load balancer as a bottleneck but requires the client to know all backend addresses — works naturally in Kubernetes where DNS returns all pod IPs for a headless service.

**Option 3 — Service mesh (Istio, Linkerd):**
The sidecar proxy (Envoy) handles gRPC load balancing transparently. The application connects to `localhost:50051` (the sidecar); the sidecar load-balances across backend instances using L7 gRPC-aware routing. This is the most operationally clean solution in Kubernetes environments.

## Section 6: Specific Use Cases

**Q12. For each of the following services, choose gRPC or REST and justify:**
**(a) Public payment API for third-party merchants, (b) Internal fraud scoring service, (c) Real-time payment event stream, (d) Admin dashboard API, (e) Inter-datacenter replication service.**

**A:**

**(a) Public payment API for third-party merchants → REST**

Merchants integrate from arbitrary stacks — PHP, Ruby, Python, Java, JavaScript, and legacy systems that predate gRPC. Requiring stub generation from a `.proto` file creates an integration barrier. The API must be callable with `curl` for debugging, testable in Postman, and documentable in a Swagger UI that non-engineers can read. Idempotency keys go in HTTP headers (`Idempotency-Key`), rate limits in `X-RateLimit-*` headers, authentication in `Authorization: Bearer`. Every third-party integration library (Stripe's approach being the canonical reference) is REST. The throughput from third-party merchants is moderate and can be served by REST with connection pooling.

**(b) Internal fraud scoring service → gRPC**

The fraud service is called by the payment service on every transaction — high throughput (50,000 calls/second at scale), strict latency SLA (<5ms p99, because it is on the critical path of payment processing). The callers are controlled internal services with generated stubs. The schema (`FraudScoreRequest`, `FraudScoreResponse`) is stable and benefits from compile-time type safety. The bandwidth savings from protobuf are meaningful at this call rate. Deadline propagation from the payment service's deadline through the fraud call is critical — a hung fraud check must not block the payment beyond the client's timeout.

```protobuf
service FraudService {
  rpc ScorePayment (FraudScoreRequest) returns (FraudScoreResponse);
}
message FraudScoreRequest {
  string payment_id   = 1;
  string user_id      = 2;
  Money  amount       = 3;
  string ip_address   = 4;
  string device_id    = 5;
}
message FraudScoreResponse {
  int32       risk_score_bps = 1;  // 0–10000 (basis points of risk)
  FraudAction recommended_action = 2;
  repeated string triggered_rules = 3;
}
```

**(c) Real-time payment event stream → gRPC (server streaming)**

A dashboard or analytics service subscribing to payment events as they happen — not polling, not batch export, but live streaming. REST has no clean model for this: SSE works but is HTTP/1.1 and lacks bidirectional framing; WebSockets are a different protocol with different operational concerns. gRPC server streaming is the native solution:

```protobuf
service PaymentEventService {
  rpc StreamEvents (StreamEventsRequest) returns (stream PaymentEvent);
}
```

The client opens one long-lived streaming RPC; the server pushes events as they occur. Reconnection on disconnect is handled by the gRPC client library with configurable backoff. This is cleaner than maintaining a WebSocket connection with a separate authentication and keepalive mechanism.

**(d) Admin dashboard API → REST**

Admin dashboards are typically low-throughput, human-operated interfaces. The callers are browsers (often with the same frontend developers who are already comfortable with REST and JSON). The schemas are complex and evolving — admins need different data shapes for different views, which REST's flexible query parameter model (with sparse fieldsets, `?fields=payment_id,status,amount`) handles more naturally than maintaining separate RPCs per view. Debuggability is paramount — a support engineer investigating a production issue from the admin UI should be able to inspect network requests in browser DevTools without proto decoder plugins. REST's human-readable JSON is directly observable in the browser.

**(e) Inter-datacenter replication service → gRPC (bidirectional streaming)**

Replicating state between datacenters requires sustained high-throughput, bidirectional acknowledgment flows, and efficient binary encoding. A replication protocol sends millions of small records per hour — JSON overhead is significant at this volume. Bidirectional streaming allows the receiving datacenter to send acknowledgments as records are applied, allowing the sender to manage backpressure and retry unacknowledged records without a separate request/response cycle. Deadline and cancellation propagation matters: if the receiving datacenter goes offline, the sender needs to cancel in-flight replication streams quickly, not wait for TCP timeout. gRPC's deadline mechanism handles this correctly; REST has no equivalent.

**Q13. How does versioning strategy differ between gRPC and REST APIs?**
A: Both need versioning, but the mechanisms and constraints differ:

**REST versioning:**

URL versioning is the dominant convention — `/v1/payments`, `/v2/payments`. This makes the version explicit in every request, allows parallel deployment of multiple versions, and is immediately visible in logs and monitoring. Header versioning (`Accept: application/vnd.example.v2+json`) is cleaner architecturally but harder to inspect and route.

REST JSON's tolerant-reader model (unknown fields ignored, missing optional fields get nulls) means minor, additive changes often require no version bump — a new field can be added without breaking old clients. Breaking changes (removing fields, changing types) require a new version endpoint.

```
/v1/payments/{id}   → maintained for 12 months after v2 launch
/v2/payments/{id}   → current version
/v3/payments/{id}   → new beta version
```

**gRPC versioning:**

Package versioning in the proto package name — `package com.example.payments.v1;` — is the idiomatic approach. The package becomes part of the RPC's full method name:

```
/com.example.payments.v1.PaymentService/CreatePayment   ← v1
/com.example.payments.v2.PaymentService/CreatePayment   ← v2
```

Both v1 and v2 can run as separate services (separate deployments) or as separate service implementations within the same binary. Old clients generate stubs from the v1 proto and call the v1 package; new clients use v2.

The proto schema's own evolution rules (field number permanence, `reserved` for removed fields) handle minor, backward-compatible changes without a package version bump. A new `optional` field in the proto is transparent to old clients — they get the zero default; new clients get the value. Breaking changes (removed fields, changed types, changed RPC signatures) require a `v2` package.

**The key difference:**
REST versioning is relatively easy to operate but requires maintaining multiple URL prefixes and routing rules. gRPC versioning is structurally cleaner (the package name is the version) but requires clients to regenerate stubs when upgrading — a heavier migration step for internal consumers. For external consumers: REST's URL versioning is more accessible; for internal consumers: gRPC's package versioning combined with proto schema evolution handles most changes without requiring a version bump.

**Q14. "Your team is building a new payment microservice in NestJS. It will be called by three other internal services and also expose an API for merchant webhooks. How do you structure the communication?"**
A:

```
Architecture decision:

  External: Merchant webhooks
    → REST (POST /webhooks/payment-status)
    → JSON payload, HMAC signature in X-Webhook-Signature header
    → Merchants implement REST webhook handlers; gRPC is not appropriate

  Internal: Three services calling PaymentService
    → gRPC
    → All three are internal Node.js/Go/Java services we control
    → High call frequency (FraudService on every transaction)
    → Compile-time type safety across polyglot services

  package com.example.payments.v1;
  service PaymentService {
    rpc CreatePayment   (CreatePaymentRequest)  returns (CreatePaymentResponse);
    rpc GetPayment      (GetPaymentRequest)     returns (GetPaymentResponse);

NestJS gRPC server setup:
  @Module({

  @Controller('webhooks')

```

**Q15. "A senior engineer proposes using gRPC for your public payment API, arguing that it's faster and more efficient. How do you respond?"**
A: Acknowledge the performance argument is correct, then explain why performance is not the deciding factor here:

**Where the engineer is right:**
gRPC with protobuf is genuinely faster and more efficient than REST with JSON — lower latency per call, lower bandwidth, lower CPU utilization for serialization. These are real advantages.

**Where the argument breaks down for a public API:**

*Client ecosystem*: Third-party merchants and partners use arbitrary tech stacks. Requiring stub generation from a `.proto` file raises the integration barrier significantly. A PHP developer integrating a payment SDK expects to call a REST endpoint with `curl`. A gRPC integration requires proto compilation toolchain setup, generated stub management, and understanding of gRPC concepts that many developers outside large tech companies have not encountered. This friction directly impacts adoption and support burden.

*Browser clients*: If any part of the payment flow involves a browser (payment form, status check, redirect handling), gRPC cannot be called directly. gRPC-Web with an Envoy proxy adds infrastructure complexity for a public API that should "just work" from a browser's `fetch()`.

*Operational tooling for merchants*: Merchants debugging integration issues use Postman, curl, and browser DevTools. REST responses are directly inspectable. Proto binary is not.

*The performance argument at the scale of a public API*: A public payment API handling 1,000 requests/second does not have the same performance pressure as an internal fraud scoring service handling 50,000 calls/second. The serialization savings from protobuf at 1,000 req/s are measured in hundreds of megabytes per day — infrastructure costs that are completely dominated by other factors (database, payment processor round-trips, logging).

**The counterproposal:**
```
Public API:  REST (JSON, standard HTTP, developer-friendly)
Internal:    gRPC (for performance-sensitive service-to-service calls)

BFF layer:   NestJS API Gateway translates REST → gRPC internally.
             External callers get REST; internal services get gRPC.
             Best of both — no compromise on either interface.
```

The engineer's instinct to optimize is correct — apply it to the internal services where the performance difference is measurable and where the client ecosystem is controlled. The public API's developer experience and integration simplicity are features worth more than the serialization efficiency gain.

**Q16. "Your internal gRPC services are experiencing uneven load — some instances are at 90% CPU while others are idle. Diagnose and fix."**
A: Uneven load in gRPC is the load balancing failure mode described in Q11. The diagnosis:

```
Step 1: Verify it is a load balancing problem, not a data skew problem
  → Check if the high-CPU instances are handling more requests or
    more expensive requests (large payloads, heavy computation).
  → If request count is also uneven: load balancing problem.
  → If request count is even but CPU is not: data/workload skew (different problem).

Step 2: Identify the load balancer type
  kubectl describe service payment-service
  → type: ClusterIP with kube-proxy?  → L4 (TCP) load balancing → root cause confirmed
  → type: with Istio sidecar?         → should be L7; check Istio configuration

Step 3: Check connection distribution
  grpcurl -plaintext payment-service:50051 list
  # If only one backend responds to multiple calls → connection pinned to one instance

  # Check which pods are receiving connections:
  kubectl exec -it payment-service-pod-1 -- netstat -an | grep ESTABLISHED | wc -l
  # One pod with many connections, others with few → L4 pinning confirmed
```

**Fixes (in order of operational simplicity):**

**Fix 1 — Enable client-side load balancing (if callers are gRPC clients you control):**
```go
// In the calling service: use DNS resolver + round-robin
conn, err := grpc.Dial(
  "dns:///payment-service.prod.svc.cluster.local:50051",
  grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`),
)
// DNS for a Kubernetes headless service returns all pod IPs
// round_robin distributes RPCs across all returned addresses
```
Requires the Kubernetes service to be headless (`clusterIP: None`) so DNS returns individual pod IPs rather than the virtual service IP.

**Fix 2 — Deploy Istio or Linkerd service mesh:**
```yaml
# Istio DestinationRule: configure gRPC load balancing
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: payment-service
spec:
  host: payment-service
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN
    connectionPool:
      http:
        h2UpgradePolicy: UPGRADE  # force HTTP/2 for gRPC
```
The Envoy sidecar handles per-RPC load balancing transparently — application code is unchanged.

**Fix 3 — Switch to an L7 load balancer:**
If using AWS: change the load balancer target group protocol to HTTP/2. If using Nginx: configure `grpc_pass` with upstream load balancing. This requires the load balancer to terminate and re-establish HTTP/2 connections per-RPC — adds latency but distributes load correctly without service mesh complexity.

**What not to do:**
- Do not disable HTTP/2 and fall back to HTTP/1.1 — you lose all gRPC streaming capabilities and the performance benefits that justified using gRPC.
- Do not add artificial connection timeouts to force reconnection — this causes a thundering herd when all connections reconnect simultaneously.

## Quick Reference

| Dimension | REST | gRPC |
|---|---|---|
| Transport | HTTP/1.1 (typical) or HTTP/2 | HTTP/2 (required) |
| Serialization | JSON (text, self-describing) | Protobuf (binary, schema-required) |
| Schema | Optional (OpenAPI is convention) | Required (`.proto` file) |
| Browser support | Native | Requires gRPC-Web + Envoy proxy |
| Streaming | No native support (SSE/WebSocket separate) | Native (4 patterns) |
| Generated clients | Optional (OpenAPI codegen) | Required (`protoc`) |
| Load balancing | L4 or L7; both work | L7 or client-side required |
| Caching | CDN/proxy caching for GET | No caching semantics |
| Deadlines | Per-hop timeouts only | End-to-end propagated deadline |
| Debugging | `curl`, browser DevTools, Postman | `grpcurl`, reflection, proto decoder |
| Ecosystem maturity | 25 years; universal tooling | ~8 years; growing but thinner |
| Bandwidth (typical) | 100% (baseline) | 20–30% of REST (protobuf) |
| Latency (p99 vs REST) | Baseline | 30–70% lower at high load |

| Use case | Choose |
|---|---|
| Public API (third-party developers) | REST |
| Browser-facing API | REST |
| Internal service-to-service, high throughput | gRPC |
| Internal service-to-service, low-moderate throughput | Either (REST if team is REST-native) |
| Real-time streaming / event feeds | gRPC (server streaming) |
| Bulk upload / ingestion | gRPC (client streaming) |
| Bidirectional real-time (chat, collaboration) | gRPC (bidi streaming) |
| Mobile SDK API | REST (gRPC supported but REST is simpler) |
| Admin / internal dashboard API | REST |
| Inter-datacenter replication | gRPC |
| Webhook receiver | REST |

## The Core Mental Model

```
The fundamental split:
  Who controls the caller?

  You don't control the caller (public API, partners, browsers):
    → REST. No exceptions.
    → JSON is the lingua franca of HTTP integrations.
    → Requiring proto toolchain is an integration tax on every external developer.

  You control the caller (internal services you deploy):
    → gRPC if performance or streaming matters.
    → REST if team is REST-native and throughput is moderate.
    → The generated stub is not a burden — it is a compile-time contract.

The hybrid architecture (what most mature systems use):
  Public edge:     REST (API Gateway / BFF)
  Internal mesh:   gRPC
  Translation:     BFF translates REST → gRPC; external clients never see proto.

The five gRPC production gotchas:
  1. L4 load balancers don't distribute gRPC load → use L7 or client-side LB
  2. Debugging requires grpcurl + reflection or proto files → add to runbooks
  3. Proto binary in logs is unreadable → log JSON-encoded protos (protojson)
  4. Deadlines must be propagated, not reset → always pass remaining deadline
  5. Browser clients cannot use gRPC directly → add gRPC-Web proxy or use REST

The five REST production gotchas:
  1. No end-to-end deadline propagation → per-hop timeouts can compound
  2. No native streaming → WebSocket/SSE is a different operational surface
  3. JSON verbosity at high throughput → measurable cost at >10k req/s
  4. No compile-time contract → schema drift discovered at runtime
  5. HTTP/1.1 connection pools add overhead at high concurrency

When to revisit the REST → gRPC migration decision:
  Internal service exceeds 5,000 req/s sustained
  JSON serialization appears in CPU profiling as a top contributor
  Streaming requirement emerges (real-time events, bulk ingestion)
  Type safety issues (null field bugs, wrong types) are causing incidents
  Team has stabilized and has capacity to absorb gRPC operational learning
```

**Tip for the interview:** gRPC vs REST questions at 5 YOE almost always escalate to one of three places: (1) the load balancing failure mode — knowing that HTTP/2 multiplexing breaks L4 load balancing, and being able to name the three fixes (L7 LB, client-side LB with round-robin, service mesh) signals you have operated gRPC in production rather than just read about it; (2) the hybrid architecture — the answer that impresses is not "gRPC is better so use it everywhere" or "REST is simpler so use it everywhere" but "REST at the public edge, gRPC internally, BFF translates between them" — with the ability to sketch the NestJS implementation of that translation; (3) the browser constraint — knowing that gRPC cannot be called from browsers without gRPC-Web and an Envoy proxy, and that this alone disqualifies gRPC for any API with browser clients, is the practical knowledge that separates architects who have shipped public APIs from those who have only built internal tooling. The fintech-specific callout: your JusPay and Razorpay payment gateway integrations are REST — you are consuming their public REST APIs. The internal services you build (fraud scoring, NACH processing, deduplication, Account Aggregator) are the gRPC candidates. The boundary is exactly where your control ends.
