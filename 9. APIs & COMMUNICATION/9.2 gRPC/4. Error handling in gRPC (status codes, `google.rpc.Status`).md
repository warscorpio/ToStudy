# Error Handling in gRPC (Status Codes, `google.rpc.Status`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. How does gRPC communicate errors, and how does this differ from REST?**
A: In REST, errors are communicated primarily through the HTTP status code (404, 500, etc.) in the response line, with an error body in the response payload. In gRPC, errors are communicated through **trailing metadata** — HTTP/2 trailers sent after the response body (or instead of it, for error-only responses). Two mandatory trailers carry the error:
- `grpc-status`: an integer representing the gRPC status code (0 = OK, 1–16 for error codes).
- `grpc-message`: a URL-percent-encoded human-readable string describing the error.

For unary RPCs, a successful response sends the response proto message followed by trailers with `grpc-status: 0`. An error response sends no response proto; only the trailers with a non-zero status code. For streaming RPCs, trailers are sent when the stream ends — either normally or with an error.

The key conceptual difference from REST: gRPC status codes are **domain-specific** (designed for distributed RPC semantics — cancellation, deadline expiry, resource exhaustion) rather than HTTP-generic (designed for web document semantics). The gRPC status code and message alone form a minimal error model; the richer `google.rpc.Status` model extends this with structured detail.

**Q2. What is `google.rpc.Status` and why was it introduced?**
A: The basic `grpc-status` + `grpc-message` model is insufficient for production use — a status code of `INVALID_ARGUMENT` tells you the request was bad but not which field, what the value was, or what the constraint was. `google.rpc.Status` is a proto message that provides a **richer error model**:

```proto
// google/rpc/status.proto
message Status {
  int32 code = 1;           // google.rpc.Code enum value
  string message = 2;       // human-readable, not for programmatic use
  repeated google.protobuf.Any details = 3;  // structured error details
}
```

It is transmitted as a serialized proto binary in an additional trailer: `grpc-status-details-bin` (base64-encoded binary proto). The `details` field is the key innovation: it carries a list of typed proto messages (serialized as `google.protobuf.Any`) that provide machine-readable structured information about the error — which field was invalid, when to retry, which quota was exceeded, where to find documentation. This enables clients to programmatically handle errors rather than parsing human-readable strings.

`google.rpc.Status` is the foundation of Google's **AIP (API Improvement Proposals)** error model and is used by all Google Cloud APIs, making it the de facto standard for gRPC error handling in production systems.

**Q3. How is `google.rpc.Status` transmitted on the wire?**
A: When a server returns a `google.rpc.Status` error, it populates three trailers:
- `grpc-status`: the integer status code (e.g., `3` for `INVALID_ARGUMENT`).
- `grpc-message`: the URL-encoded human-readable message from `Status.message`.
- `grpc-status-details-bin`: the base64-encoded serialized binary of the full `Status` proto, including the `details` repeated field.

The gRPC framework in most languages handles encoding and decoding of `grpc-status` and `grpc-message` automatically. The `grpc-status-details-bin` trailer must typically be handled by the application or a helper library: in Go, the `google.golang.org/grpc/status` package provides `status.New()` and `st.WithDetails()` to construct statuses with details; in Java, `StatusRuntimeException` wraps the status; in Python, `grpc_status` provides helpers. Libraries like `grpc-gateway` handle transcoding `google.rpc.Status` to JSON for HTTP/REST clients.

**Q4. What is the difference between the gRPC status code and the `google.rpc.Status` code field?**
A: They must be equal — the `Status.code` field should always match the `grpc-status` trailer integer. The `grpc-status` trailer is the authoritative code used by the gRPC transport; the `Status.code` is the same code repeated within the structured proto for convenience when processing the full `Status` object. In practice: (1) the status code is extracted from the `grpc-status` trailer by the gRPC framework and available as a typed enum in client code; (2) the `Status` proto (from `grpc-status-details-bin`) provides additional context including the `details` list. Clients should use the framework-provided status code (from the `grpc-status` trailer) as the primary signal for programmatic error handling, and use the `details` from `Status` for additional context.

## Section 2: gRPC Status Codes

**Q5. What are all seventeen gRPC status codes and when does each apply?**
A: The `google.rpc.Code` enum defines seventeen codes:

| Code | Value | Meaning | Retryable? |
|--- |--- |--- |--- |
| `OK` | 0 | Success | N/A |
| `CANCELLED` | 1 | The client cancelled the request | No (client-initiated) |
| `UNKNOWN` | 2 | Unknown error; catch-all for unclassified server errors | Sometimes |
| `INVALID_ARGUMENT` | 3 | Client sent a malformed or invalid argument | No (fix the request) |
| `DEADLINE_EXCEEDED` | 4 | Request deadline expired before completion | If idempotent |
| `NOT_FOUND` | 5 | Requested resource does not exist | No |
| `ALREADY_EXISTS` | 6 | Resource the client tried to create already exists | No |
| `PERMISSION_DENIED` | 7 | Caller is authenticated but lacks permission | No |
| `RESOURCE_EXHAUSTED` | 8 | Quota or rate limit exceeded | Yes (with backoff) |
| `FAILED_PRECONDITION` | 9 | System not in a state required for the operation | No (fix state first) |
| `ABORTED` | 10 | Operation aborted due to concurrency conflict | Yes (retry transaction) |
| `OUT_OF_RANGE` | 11 | Operation attempted past valid range | No |
| `UNIMPLEMENTED` | 12 | Operation not implemented or not supported | No |
| `INTERNAL` | 13 | Internal server error; invariant broken | No |
| `UNAVAILABLE` | 14 | Server temporarily unavailable | Yes (with backoff) |
| `DATA_LOSS` | 15 | Unrecoverable data loss or corruption | No |
| `UNAUTHENTICATED` | 16 | No valid authentication credentials | No (authenticate first) |

**Q6. What is the precise distinction between `INVALID_ARGUMENT`, `FAILED_PRECONDITION`, and `OUT_OF_RANGE`?**
A: These three codes are frequently confused because all three represent "the request can't be processed" but for different reasons:

- **`INVALID_ARGUMENT`**: the argument value itself is malformed or logically invalid, regardless of system state. Requesting page size `-1`, a negative price, or a malformed email address. The error would occur even on an otherwise healthy, idle system. This is a **client bug** — the client sent data it should never send.
- **`FAILED_PRECONDITION`**: the system state doesn't allow this operation right now, but the operation's arguments are valid. Deleting a non-empty directory, reading from an empty queue, attempting to resume a paused task that has been deleted. The system state must change before the operation is retried. The argument is valid; the system precondition isn't met.
- **`OUT_OF_RANGE`**: the argument is outside the valid range for the current iteration or context. Seeking to file offset 100 when the file is only 50 bytes. A subset of `INVALID_ARGUMENT` specifically for range/boundary violations; use `OUT_OF_RANGE` when there's an obvious valid upper bound the client should have respected.

Decision heuristic: if the same request would succeed on a completely empty or reset system, use `INVALID_ARGUMENT`. If the request would succeed after some system state changes (not due to client action), use `FAILED_PRECONDITION`. If the request specifies a value past a clearly defined bound, use `OUT_OF_RANGE`.

**Q7. What is the distinction between `PERMISSION_DENIED` and `UNAUTHENTICATED`?**
A: A precise and security-relevant distinction:
- **`UNAUTHENTICATED`** (16): the caller has not provided valid authentication credentials — there is no recognized identity. The request did not include a token, the token is expired, or the token signature is invalid. The caller is effectively anonymous. Equivalent to HTTP 401.
- **`PERMISSION_DENIED`** (7): the caller is authenticated (their identity is known) but they lack authorization to perform the requested operation. A regular user trying to access an admin endpoint. Equivalent to HTTP 403.

The security implication: use `NOT_FOUND` (404 equivalent) instead of `PERMISSION_DENIED` when you want to avoid confirming that a resource exists to an unauthorized caller. Returning `PERMISSION_DENIED` reveals the resource exists; `NOT_FOUND` hides its existence. For highly sensitive resources, `NOT_FOUND` prevents enumeration attacks.

**Q8. When should `ABORTED` be used vs. `FAILED_PRECONDITION`, and what retry behavior does each imply?**
A: Both indicate the operation failed due to system state, but with different retry semantics:
- **`FAILED_PRECONDITION`**: the system is not in the state the operation requires, and the client should **not retry the same operation** without first changing the system state (or waiting for it to change). The client needs to take a corrective action before retrying.
- **`ABORTED`**: the operation was aborted due to a concurrency conflict — optimistic locking failure, transaction abort, sequencer check failure — and the client **can and should retry the entire operation** from the beginning. The conflict is transient; the retry may succeed.

`ABORTED` is the correct code for: optimistic locking failures (`compare-and-swap` that failed because another writer updated the resource), transaction aborts in distributed transactions, message queue operations where a message was claimed by another consumer. The client should retry the full operation (re-read the current state, recompute the update, re-submit) not just the failing call.

**Q9. How do gRPC status codes map to HTTP status codes for REST/gRPC transcoding?**
A: When using `grpc-gateway` or Google's HTTP transcoding to expose gRPC services via REST:

| gRPC Code | HTTP Code |
|--- |--- |
| `OK` | 200 |
| `CANCELLED` | 499 (client closed request) |
| `UNKNOWN` | 500 |
| `INVALID_ARGUMENT` | 400 |
| `DEADLINE_EXCEEDED` | 504 |
| `NOT_FOUND` | 404 |
| `ALREADY_EXISTS` | 409 |
| `PERMISSION_DENIED` | 403 |
| `RESOURCE_EXHAUSTED` | 429 |
| `FAILED_PRECONDITION` | 400 |
| `ABORTED` | 409 |
| `OUT_OF_RANGE` | 400 |
| `UNIMPLEMENTED` | 501 |
| `INTERNAL` | 500 |
| `UNAVAILABLE` | 503 |
| `DATA_LOSS` | 500 |
| `UNAUTHENTICATED` | 401 |

The mapping is not perfectly bidirectional — HTTP 400 maps to three different gRPC codes (`INVALID_ARGUMENT`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`). When transcoding HTTP errors back to gRPC, an HTTP 400 becomes `INVALID_ARGUMENT` by default. For gRPC clients the distinction matters; for REST clients receiving transcoded responses, the HTTP status code is the primary signal.

## Section 3: Error Detail Types

**Q10. What is `google.protobuf.Any` and how does it enable typed error details?**
A: `google.protobuf.Any` is a proto wrapper that can hold any proto message in a type-erased form, alongside a `type_url` string that identifies the message type:

```proto
message Any {
  string type_url = 1;  // e.g., "type.googleapis.com/google.rpc.ErrorInfo"
  bytes  value    = 2;  // serialized proto of the embedded message
}
```

In `google.rpc.Status.details`, each element is an `Any` containing a typed error detail proto. The client inspects the `type_url` to know which proto type to deserialize the `value` into. This design enables the `Status` message to carry an open-ended set of error types without requiring changes to the `Status` proto itself — new error detail types can be defined independently and embedded via `Any`.

Framework helpers handle the encoding/decoding: in Go, `st.WithDetails(detail1, detail2)` encodes proto messages as `Any`; `st.Details()` decodes them back to the concrete proto types. In Java, `StatusProto.toStatusRuntimeException(status)` handles encoding; unpacking uses `status.getDetailsList()` with `detail.is(BadRequest.class)` / `detail.unpack(BadRequest.class)`.

**Q11. What are the standard error detail types in `google.rpc` and when does each apply?**
A:

**`google.rpc.ErrorInfo`** — identifies the error domain and reason as a stable machine-readable string. Use for all errors where the client needs to programmatically identify the specific error:
```proto
message ErrorInfo {
  string reason   = 1;  // e.g., "USER_NOT_FOUND", "QUOTA_EXCEEDED"
  string domain   = 2;  // e.g., "myservice.example.com"
  map<string, string> metadata = 3;  // additional key-value context
}
```

**`google.rpc.RetryInfo`** — specifies when the client should retry:
```proto
message RetryInfo {
  google.protobuf.Duration retry_delay = 1;
}
```
Include with `UNAVAILABLE` and `RESOURCE_EXHAUSTED` — tells the client exactly how long to wait before retrying rather than requiring it to implement its own backoff.

**`google.rpc.BadRequest`** — lists field-level validation failures for `INVALID_ARGUMENT`:
```proto
message BadRequest {
  repeated FieldViolation field_violations = 1;
  message FieldViolation {
    string field       = 1;  // e.g., "user.email"
    string description = 2;  // e.g., "Invalid email format"
  }
}
```

**`google.rpc.QuotaFailure`** — describes which quota was exceeded for `RESOURCE_EXHAUSTED`:
```proto
message QuotaFailure {
  repeated Violation violations = 1;
  message Violation {
    string subject     = 1;  // e.g., "quota/api-requests-per-day"
    string description = 2;  // e.g., "Limit: 1000, Available: 0"
  }
}
```

**`google.rpc.PreconditionFailure`** — describes which precondition failed for `FAILED_PRECONDITION`:
```proto
message PreconditionFailure {
  repeated Violation violations = 1;
  message Violation {
    string type        = 1;  // e.g., "DIRECTORY_NOT_EMPTY"
    string subject     = 2;  // e.g., "/home/user/data"
    string description = 3;
  }
}
```

**`google.rpc.RequestInfo`** — provides the request ID for correlation with server-side logs:
```proto
message RequestInfo {
  string request_id       = 1;  // unique ID for this request
  string serving_data     = 2;  // opaque server context for support
}
```

**`google.rpc.ResourceInfo`** — identifies which resource was not found or affected:
```proto
message ResourceInfo {
  string resource_type = 1;  // e.g., "users"
  string resource_name = 2;  // e.g., "users/123"
  string owner         = 3;
  string description   = 4;
}
```

**`google.rpc.DebugInfo`** — server-side debug information (stack traces, internal detail). **Never return in production to external clients** — for internal services or debug builds only:
```proto
message DebugInfo {
  repeated string stack_entries = 1;
  string detail                 = 2;
}
```

**`google.rpc.Help`** — links to documentation:
```proto
message Help {
  repeated Link links = 1;
  message Link {
    string description = 1;
    string url         = 2;
  }
}
```

**`google.rpc.LocalizedMessage`** — user-facing localized message (the `Status.message` field is not localizable):
```proto
message LocalizedMessage {
  string locale  = 1;  // BCP-47 locale, e.g., "en-US", "fr-FR"
  string message = 2;  // localized message for display to end user
}
```

**Q12. How should `ErrorInfo` be used, and why is it the most important detail type?**
A: `ErrorInfo` is the most important detail because it provides a **stable, machine-readable error identity** — a reason code the client can `switch` on programmatically, without parsing fragile human-readable messages. The `reason` field is a SCREAMING_SNAKE_CASE string that identifies the specific error condition; the `domain` field namespaces it to prevent collisions across services:

```go
// Server side:
st, _ := status.New(codes.NotFound, "user not found").
    WithDetails(&errdetails.ErrorInfo{
        Reason: "USER_NOT_FOUND",
        Domain: "users.myservice.com",
        Metadata: map[string]string{
            "user_id": req.UserId,
        },
    })
return nil, st.Err()

// Client side:
if st, ok := status.FromError(err); ok {
    for _, detail := range st.Details() {
        if ei, ok := detail.(*errdetails.ErrorInfo); ok {
            switch ei.Reason {
            case "USER_NOT_FOUND":
                // handle specifically
            case "USER_SUSPENDED":
                // handle differently
            }
        }
    }
}
```

Without `ErrorInfo`, clients are forced to parse `Status.message` strings like "user not found" — which break if the message is reformatted, localized, or extended. `ErrorInfo.reason` is a contract between client and server that should be treated as stable API surface and documented alongside method signatures.

## Section 4: Client-Side Error Handling

**Q13. How do you extract a gRPC status code and details in Go, Java, and Python?**
A: Language-specific patterns for status extraction:

**Go**:
```go
import (
    "google.golang.org/grpc/status"
    "google.golang.org/grpc/codes"
    errdetails "google.golang.org/genproto/googleapis/rpc/errdetails"
)

resp, err := client.GetUser(ctx, req)
if err != nil {
    st, ok := status.FromError(err)
    if !ok {
        // Not a gRPC error — network error, local failure
    }
    switch st.Code() {
    case codes.NotFound:
        // handle not found
    case codes.InvalidArgument:
        for _, detail := range st.Details() {
            if br, ok := detail.(*errdetails.BadRequest); ok {
                for _, v := range br.GetFieldViolations() {
                    log.Printf("Field %s: %s", v.GetField(), v.GetDescription())
                }
            }
        }
    }
}
```

**Java**:
```java
try {
    User user = stub.getUser(request);
} catch (StatusRuntimeException e) {
    Status status = e.getStatus();
    switch (status.getCode()) {
        case NOT_FOUND:
            // handle
            break;
        case INVALID_ARGUMENT:
            Metadata trailers = e.getTrailers();
            com.google.rpc.Status statusProto =
                StatusProto.fromStatusAndTrailers(e.getStatus(), trailers);
            for (Any detail : statusProto.getDetailsList()) {
                if (detail.is(BadRequest.class)) {
                    BadRequest br = detail.unpack(BadRequest.class);
                    // process field violations
                }
            }
            break;
    }
}
```

**Python**:
```python
from grpc_status import rpc_status
from google.rpc import error_details_pb2

try:
    response = stub.GetUser(request)
except grpc.RpcError as e:
    status = rpc_status.from_call(e)
    if e.code() == grpc.StatusCode.INVALID_ARGUMENT:
        for detail in status.details:
            if detail.Is(error_details_pb2.BadRequest.DESCRIPTOR):
                br = error_details_pb2.BadRequest()
                detail.Unpack(br)
                for violation in br.field_violations:
                    print(f"{violation.field}: {violation.description}")
```

**Q14. Which gRPC status codes are safe to retry, and what retry strategy should be applied to each?**
A: The retryability of each code depends on the error semantics and whether the operation is idempotent:

**Unconditionally retryable** (safe to retry immediately with backoff):
- `UNAVAILABLE`: the server is temporarily unavailable — a transient infrastructure issue. Retry with exponential backoff. Most common transient error in gRPC; the `RetryInfo` detail specifies the recommended delay.
- `RESOURCE_EXHAUSTED`: rate limited or quota exceeded. Retry with exponential backoff + jitter; use the `RetryInfo.retry_delay` if present. For quota exhaustion (not rate limiting), retrying may not help until the quota resets.

**Conditionally retryable** (safe to retry only for idempotent operations):
- `DEADLINE_EXCEEDED`: the operation timed out. If the RPC is idempotent (safe to execute multiple times), retry with a fresh deadline. If not idempotent, do not retry — the operation may have completed on the server but the response was lost.
- `UNKNOWN`: may be a transient error or a permanent bug. Retry a small number of times for idempotent operations.

**Retry the full operation** (not just the failing RPC call):
- `ABORTED`: concurrency conflict — re-read the resource, recompute the operation, and retry the full sequence from the beginning. Not just retrying the gRPC call.

**Never retry**:
- `INVALID_ARGUMENT`, `OUT_OF_RANGE`: fix the request.
- `NOT_FOUND`, `ALREADY_EXISTS`: the resource state is the issue; retrying produces the same result.
- `PERMISSION_DENIED`, `UNAUTHENTICATED`: authorization/authentication must be resolved first.
- `FAILED_PRECONDITION`: fix the system precondition first.
- `UNIMPLEMENTED`: the server doesn't support this operation.
- `INTERNAL`, `DATA_LOSS`: server-side bug or data corruption; retrying will not help and may make things worse.
- `CANCELLED`: the client cancelled the request; don't retry unless the client initiates a new request.

**Q15. What is gRPC's built-in retry policy and how does it differ from application-level retries?**
A: gRPC provides **built-in service config retries** — retry logic configured at the channel/stub level that is applied transparently by the gRPC framework before the application sees the error:

```json
{
  "methodConfig": [{
    "name": [{"service": "myservice.UserService", "method": "GetUser"}],
    "retryPolicy": {
      "maxAttempts": 4,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE", "RESOURCE_EXHAUSTED"]
    }
  }]
}
```

This policy is applied per-method, is transparent to the application (the application only sees the final outcome after all retries), and is defined per-service in the service config (distributed via service discovery or hardcoded in channel options).

**Difference from application-level retries**: (1) gRPC framework retries happen at the transport level — they can retry before the request even leaves the connection pool (hedged requests); (2) framework retries apply to the exact byte-for-byte same request — they're only safe for idempotent operations; (3) application-level retries give you full control (re-read state, recompute, handle `ABORTED` by retrying the full sequence); (4) both can coexist — framework retries for transient `UNAVAILABLE` errors, application retries for `ABORTED` transactions.

## Section 5: Server-Side Error Construction

**Q16. How should a server construct a rich `google.rpc.Status` error for a validation failure?**
A: For an `INVALID_ARGUMENT` error with field-level violations, the server should:

```go
func (s *UserService) CreateUser(ctx context.Context, req *pb.CreateUserRequest) (*pb.User, error) {
    var fieldViolations []*errdetails.BadRequest_FieldViolation

    if req.Email == "" || !isValidEmail(req.Email) {
        fieldViolations = append(fieldViolations, &errdetails.BadRequest_FieldViolation{
            Field:       "email",
            Description: "Must be a valid email address",
        })
    }
    if len(req.Password) < 8 {
        fieldViolations = append(fieldViolations, &errdetails.BadRequest_FieldViolation{
            Field:       "password",
            Description: "Must be at least 8 characters",
        })
    }

    if len(fieldViolations) > 0 {
        st, err := status.New(codes.InvalidArgument, "Request validation failed").
            WithDetails(
                &errdetails.ErrorInfo{
                    Reason: "VALIDATION_FAILED",
                    Domain: "users.myservice.com",
                },
                &errdetails.BadRequest{
                    FieldViolations: fieldViolations,
                },
                &errdetails.RequestInfo{
                    RequestId: extractRequestID(ctx),
                },
            )
        if err != nil {
            return nil, status.Error(codes.Internal, "failed to construct error")
        }
        return nil, st.Err()
    }

    // ... create user
}
```

Key practices: (1) collect **all** violations before returning (not just the first) — clients need to know about all invalid fields to display a complete error form; (2) include `RequestInfo` with the request ID for correlation; (3) use `ErrorInfo` with a stable `reason` code alongside `BadRequest` for programmatic handling; (4) keep `Status.message` human-readable but not machine-parsed.

**Q17. How should a server return a rate-limiting error with retry guidance?**
A:
```go
func applyRateLimit(ctx context.Context) error {
    retryAfter := time.Second * 5  // computed from token bucket state

    st, _ := status.New(codes.ResourceExhausted, "API rate limit exceeded").
        WithDetails(
            &errdetails.ErrorInfo{
                Reason: "RATE_LIMIT_EXCEEDED",
                Domain: "api.myservice.com",
                Metadata: map[string]string{
                    "limit":     "100",
                    "window":    "60s",
                    "remaining": "0",
                },
            },
            &errdetails.RetryInfo{
                RetryDelay: durationpb.New(retryAfter),
            },
            &errdetails.QuotaFailure{
                Violations: []*errdetails.QuotaFailure_Violation{{
                    Subject:     "api-requests-per-minute/user:123",
                    Description: "Limit: 100 requests/minute, Available: 0",
                }},
            },
        )
    return st.Err()
}
```

The client reads `RetryInfo.retry_delay` to know exactly when to retry, rather than implementing its own guess-based backoff. This is significantly better UX — the client backs off for the precise window rather than using a fixed or exponential delay that may not align with the server's rate limit window.

**Q18. What should a server do when it catches an unexpected internal error, and what must it never do?**
A: For unexpected internal errors (panics, unhandled exceptions, database errors), the server must:

**Do**:
```go
// In a recovery interceptor:
defer func() {
    if r := recover(); r != nil {
        requestID := extractRequestID(ctx)
        log.Errorf("panic recovered: %v\n%s", r, debug.Stack())
        st, _ := status.New(codes.Internal, "Internal server error").
            WithDetails(&errdetails.RequestInfo{
                RequestId: requestID,
            })
        // Return the status error; the interceptor sets it as the response
    }
}()
```

Log the full error including stack trace internally. Return `INTERNAL` with a `RequestInfo` detail containing the request ID so operators can correlate the client's error report with server logs.

**Never do**:
- Return the internal error message, stack trace, or database error text in the `Status.message` or any detail. `"pq: duplicate key value violates unique constraint users_email_key"` reveals database type, schema, and constraint names — a security vulnerability.
- Return `DebugInfo` with stack traces to external clients — `DebugInfo` is for internal services and debug environments only.
- Return `UNKNOWN` for known error conditions — `UNKNOWN` signals the error was truly unexpected and unclassified; known error paths should return the appropriate specific code.
- Return HTTP 200 with an error body — gRPC errors must be communicated via status codes, not the response payload.

## Section 6: Interceptors & Middleware

**Q19. How do server-side interceptors standardize error handling across a gRPC service?**
A: A unary server interceptor wraps every handler, enabling cross-cutting error handling:

```go
func ErrorHandlingInterceptor(ctx context.Context, req interface{},
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {

    resp, err := handler(ctx, req)
    if err != nil {
        // If already a gRPC status error, enrich it
        if st, ok := status.FromError(err); ok {
            // Add request ID if not already present
            enriched, newErr := st.WithDetails(&errdetails.RequestInfo{
                RequestId: extractRequestID(ctx),
            })
            if newErr == nil {
                return nil, enriched.Err()
            }
        }
        // If a domain error (not yet a gRPC status), map it
        if errors.Is(err, ErrUserNotFound) {
            return nil, status.Error(codes.NotFound, "user not found")
        }
        // Unknown error — log and return INTERNAL
        log.Errorf("unhandled error in %s: %v", info.FullMethod, err)
        return nil, status.Error(codes.Internal, "internal server error")
    }
    return resp, nil
}
```

Interceptors are the correct place for: (1) **panic recovery** — catching panics and converting them to `INTERNAL` status; (2) **domain error mapping** — translating application-layer errors (not-found errors, validation errors) to gRPC status codes without requiring each handler to know gRPC semantics; (3) **request ID injection** — attaching a request ID to every error response; (4) **error logging** — centralized logging of all errors with full context; (5) **metrics** — incrementing error counters by status code.

**Q20. How do client-side interceptors implement transparent retry logic?**
A:
```go
func RetryInterceptor(maxRetries int) grpc.UnaryClientInterceptor {
    return func(ctx context.Context, method string, req, reply interface{},
        cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {

        var lastErr error
        for attempt := 0; attempt <= maxRetries; attempt++ {
            if attempt > 0 {
                backoff := computeBackoff(attempt) // exponential with jitter
                if st, ok := status.FromError(lastErr); ok {
                    for _, detail := range st.Details() {
                        if ri, ok := detail.(*errdetails.RetryInfo); ok {
                            // Use server-specified delay if available
                            backoff = ri.RetryDelay.AsDuration()
                        }
                    }
                }
                time.Sleep(backoff)
            }

            lastErr = invoker(ctx, method, req, reply, cc, opts...)
            if lastErr == nil {
                return nil
            }

            if st, ok := status.FromError(lastErr); ok {
                if !isRetryable(st.Code()) {
                    return lastErr  // non-retryable, fail fast
                }
            }
        }
        return lastErr
    }
}

func isRetryable(code codes.Code) bool {
    return code == codes.Unavailable || code == codes.ResourceExhausted
}
```

The interceptor uses `RetryInfo` from the status details if available (honoring the server's explicit retry delay guidance) and falls back to computed exponential backoff. It short-circuits for non-retryable status codes — no point retrying `NOT_FOUND` or `INVALID_ARGUMENT`.

## Section 7: Streaming Error Handling

**Q21. How do errors work differently in server streaming vs. unary RPCs?**
A: In a **unary RPC**, there is one request and one response; the error (if any) replaces the response and is returned atomically. In a **server streaming RPC**, the server sends a stream of response messages followed by a final status. An error can occur:
- **Before any messages**: the server returns an error immediately; the client's `Recv()` call returns the error on the first call.
- **Mid-stream**: the server encounters an error after sending some messages. It terminates the stream with a non-OK status. The client receives the already-sent messages successfully via `Recv()`, then receives the error on the next `Recv()` call.
- **On stream close**: the server finishes successfully with `SendAndClose()` or returns `nil` after the last `Send()`. The client receives `io.EOF` from `Recv()` — this is not an error.

Client handling for server streaming:
```go
stream, err := client.ListUsers(ctx, req)
if err != nil {
    // Error establishing the stream
    st := status.Convert(err)
    // handle
}
for {
    user, err := stream.Recv()
    if err == io.EOF {
        break  // stream completed successfully
    }
    if err != nil {
        st := status.Convert(err)
        // Error mid-stream — some users may already have been processed
        // Handle based on st.Code() — CANCELLED, DEADLINE_EXCEEDED, etc.
        break
    }
    processUser(user)
}
```

**Q22. How does error handling work in bidirectional streaming RPCs?**
A: Bidirectional streaming is the most complex case. Both client and server can send and receive concurrently. Errors can originate from either side:

- **Client cancels**: if the client calls `CloseSend()` followed by context cancellation, the server's `Recv()` returns a `CANCELLED` error. The server should detect this and stop processing.
- **Server errors**: the server returns a non-nil error from its handler function. The client's next `Recv()` call returns this error. Messages already sent by the server before the error are still available to the client.
- **Deadline exceeded**: if the context deadline fires, both `Send()` and `Recv()` on both sides return `DEADLINE_EXCEEDED`.
- **Network errors**: connection drops or protocol errors return `UNAVAILABLE` or `INTERNAL`.

Best practices for bidirectional streaming error handling: (1) always check `ctx.Done()` in processing loops alongside `Recv()` errors; (2) distinguish `io.EOF` (normal stream end) from error codes (abnormal termination); (3) implement graceful shutdown — when the server encounters an error, finish processing in-flight messages before returning the error; (4) use `context.WithCancel` on the client side so the client can cancel the stream and propagate cancellation to the server.

## Section 8: Failure Modes & Anti-patterns

**Q23. What is the "`UNKNOWN` for everything" anti-pattern and why is it harmful?**
A: Using `UNKNOWN` (or `INTERNAL`) as the default error code for all errors — essentially `throw new Exception("something went wrong")` in gRPC form:

```go
// Anti-pattern: every error becomes UNKNOWN
if err != nil {
    return nil, status.Error(codes.Unknown, err.Error())
}
```

Harmful because: (1) **clients can't programmatically handle errors** — they have no way to distinguish "user not found" (NOT_FOUND, safe to show to user) from "database connection failed" (UNAVAILABLE, retry) from "invalid email" (INVALID_ARGUMENT, show validation error). All are `UNKNOWN`; the client must either show a generic error for all cases or parse the message string. (2) **Retry logic fails** — clients that retry `UNAVAILABLE` don't retry `UNKNOWN`, so transient errors that should be retried are not. (3) **Monitoring is useless** — error rate dashboards show all errors as `UNKNOWN`, making it impossible to distinguish new bugs from known transient failures. (4) **Reveals internal details** — `status.Error(codes.Unknown, err.Error())` passes the raw error message, which may include database errors, file paths, or internal service names.

Fix: maintain a mapping from domain errors to gRPC status codes in an interceptor. Use `UNKNOWN` only for truly unclassified errors that the server developer couldn't anticipate.

**Q24. What is "error message as API contract" anti-pattern?**
A: Encoding business logic in the `Status.message` string and relying on clients to parse it:

```go
// Server (anti-pattern):
return nil, status.Error(codes.NotFound, fmt.Sprintf("user %s not found in region %s", userID, region))

// Client (anti-pattern):
if strings.Contains(err.Error(), "not found in region") {
    region := parseRegion(err.Error())  // fragile string parsing
}
```

The `Status.message` field is **human-readable only** — it is not a stable API contract. It may be reformatted, localized, or changed in a refactoring. Clients that parse it will break silently when the server's message format changes.

Correct pattern: put machine-readable information in `ErrorInfo.reason`, `ErrorInfo.metadata`, `ResourceInfo`, or `BadRequest.FieldViolation`. The message is for human display (logs, developer tools); the details are for programmatic use.

**Q25. What is the "sensitive data in error details" anti-pattern?**
A: Including sensitive information in error responses that could be exploited or that violates privacy requirements:

```go
// Anti-pattern: leaks sensitive info
st, _ := status.New(codes.NotFound, "user not found").
    WithDetails(&errdetails.ErrorInfo{
        Reason: "USER_NOT_FOUND",
        Metadata: map[string]string{
            "internal_user_id": "uuid-a3f8bc",  // internal identifier
            "hashed_password":  "bcrypt:...",   // never expose
            "query":            "SELECT * FROM users WHERE email='alice@...'",  // SQL!
            "admin_notes":      "Account flagged for fraud review",  // confidential
        },
    })
```

Any information in a gRPC error detail is visible to the calling client, potentially logged by every intermediary proxy, and may appear in client-side error logging, bug reports, and third-party monitoring tools. Rules: (1) never include credentials, tokens, passwords, or PII in error details; (2) never include raw SQL queries or database error messages; (3) never include internal resource identifiers that expose system architecture; (4) `DebugInfo` with stack traces must never be returned to external clients — only in internal service-to-service calls with appropriate trust boundaries; (5) treat error details as part of the public API surface — they are as visible as response fields.

**Q26. What is the "losing error context across service boundaries" anti-pattern?**
A: In a microservices architecture where Service A calls Service B, Service A receives a rich `google.rpc.Status` from Service B (with `ErrorInfo`, `BadRequest` details, etc.) and then replaces it entirely with a new, less informative error when returning to its caller:

```go
// Anti-pattern: loses all context
resp, err := serviceB.GetUser(ctx, req)
if err != nil {
    return nil, status.Error(codes.Internal, "backend error")
    // All of Service B's ErrorInfo, RequestInfo, etc. is lost
}
```

Consequences: the ultimate caller (and the caller's operator) has no way to trace the error to Service B, no structured error details to act on, and no request IDs for correlation. Debugging requires adding tracing after the fact.

Better patterns: (1) **passthrough** — if the error from Service B should be returned as-is to the caller, propagate the exact status: `return nil, err`; (2) **wrapping** — translate Service B's error to a new status but include the original request ID in `RequestInfo.serving_data` and add a `DebugInfo` detail (for internal service calls only) with the upstream error; (3) **aggregation** — if multiple upstream errors need to be combined, the `details` field can include multiple `ErrorInfo` messages, one per upstream failure; (4) use distributed tracing (OpenTelemetry) so errors can be correlated across service boundaries via trace IDs even when error context is translated.

## Section 9: Trade-offs & Decision-Making

**Q27. When should you use a single `FAILED_PRECONDITION` vs. defining multiple specific `ErrorInfo` reasons?**
A: The status code (`FAILED_PRECONDITION`) tells the client the category of failure — the system state doesn't allow the operation. The `ErrorInfo.reason` tells the client specifically which precondition failed. Both are needed:

- **Status code alone** (`FAILED_PRECONDITION` without details): acceptable for simple services where there's only one possible precondition failure per method, and clients always take the same action (display a generic "precondition not met" message).
- **`ErrorInfo.reason` with specific reasons**: required when the client needs to take different actions for different preconditions. "Payment method not set up" vs. "Account suspended" vs. "KYC verification required" are all `FAILED_PRECONDITION` but require entirely different client-side flows.

Design rule: define a `reason` string for every distinct error condition the client must handle differently. If all `FAILED_PRECONDITION` errors lead to the same client action, a single reason is sufficient. If different failures lead to different flows (show a payment setup UI, show an account suspension message, redirect to a KYC flow), each needs its own `reason`.

**Q28. How do you design error handling for gRPC APIs exposed via gRPC-Gateway (HTTP transcoding)?**
A: `grpc-gateway` automatically transcodes `google.rpc.Status` to JSON for REST clients, using the `grpc-status-details-bin` trailer:

```json
// HTTP response for INVALID_ARGUMENT with BadRequest details:
{
  "code": 3,
  "message": "Request validation failed",
  "details": [
    {
      "@type": "type.googleapis.com/google.rpc.BadRequest",
      "fieldViolations": [
        {"field": "email", "description": "Must be a valid email address"}
      ]
    },
    {
      "@type": "type.googleapis.com/google.rpc.ErrorInfo",
      "reason": "VALIDATION_FAILED",
      "domain": "users.myservice.com"
    }
  ]
}
```

Design considerations: (1) the HTTP status code is automatically derived from the gRPC code (see the mapping in Q9) — ensure gRPC codes are chosen correctly because they determine the HTTP code REST clients see; (2) `@type` URLs must match the proto package paths for `grpc-gateway` to serialize correctly; (3) test error responses via the REST gateway with real clients — the JSON shape differs from gRPC binary and some tools have quirks in `Any` serialization; (4) `DebugInfo` must be suppressed for external REST clients the same as for gRPC clients — the gateway transparently forwards all details including debug stacks if not filtered.

**Q29. How should you handle error translation at an API gateway that aggregates multiple gRPC backend services?**
A: An API gateway receiving gRPC errors from multiple backends must decide: pass through the backend error, translate it, or aggregate it. The right choice depends on the trust boundary:

- **Internal service calls** (gateway and backends are owned by the same team): pass through the full `google.rpc.Status` including details. The gateway acts as a transparent proxy; the calling service should see the full error context.
- **External-facing gateway** (backends are internal; the gateway is customer-facing): translate errors. The backend error may reference internal systems, use internal error codes, or contain `DebugInfo` that must not reach customers. The gateway should: extract the `ErrorInfo.reason` and `Status.code`, construct a new `Status` appropriate for external clients (no DebugInfo, no internal resource names), and preserve the `RequestInfo.request_id` for support correlation.
- **Status code normalization**: different backends may use different gRPC codes for conceptually similar errors. The gateway can normalize (e.g., always return `UNAVAILABLE` for backend timeout regardless of whether the backend returned `DEADLINE_EXCEEDED` or `UNAVAILABLE`).
- **Aggregate errors**: when the gateway fans out to multiple backends and some fail, return the most appropriate single status code (the "worst" failure) and include per-backend `ErrorInfo` details in the `details` list.

## Section 10: Scenario / System Design Style Questions

**Q30. "Design the error handling for a gRPC CreateOrder RPC that must validate input, check inventory, and process payment."**
A: Three distinct failure domains, each with specific error types:

**Input validation failures** (all collected, not fail-fast):
```go
// Return INVALID_ARGUMENT with BadRequest
&errdetails.BadRequest{FieldViolations: []*errdetails.BadRequest_FieldViolation{
    {Field: "items[0].quantity", Description: "Must be positive"},
    {Field: "shipping_address.zip_code", Description: "Invalid format"},
}}
```

**Inventory check failures**:
```go
// Return FAILED_PRECONDITION with PreconditionFailure
&errdetails.PreconditionFailure{Violations: []*errdetails.PreconditionFailure_Violation{
    {Type: "OUT_OF_STOCK", Subject: "products/SKU-123",
     Description: "Requested: 5, Available: 2"},
}}
// ErrorInfo.reason = "INSUFFICIENT_INVENTORY"
```

**Payment failures**:
```go
// Return FAILED_PRECONDITION with ErrorInfo for declined card
// OR INVALID_ARGUMENT if card details are malformed
&errdetails.ErrorInfo{
    Reason: "PAYMENT_DECLINED",
    Domain: "payments.myservice.com",
    Metadata: map[string]string{
        "decline_code": "insufficient_funds",
        // Never include: card number, CVV, full error from payment gateway
    },
}
```

**Transient failures** (DB unavailable, payment service down):
```go
// Return UNAVAILABLE with RetryInfo
&errdetails.RetryInfo{RetryDelay: durationpb.New(2 * time.Second)}
```

**Always include** `RequestInfo` with a request ID in every error response. Run validation before calling inventory or payment — don't call external services if the request is structurally invalid.

**Q31. "A client receives `UNKNOWN` errors intermittently from a gRPC service. How do you diagnose and fix it?"**
A: `UNKNOWN` is the "we didn't classify this error" code — the root cause could be anything. Systematic diagnosis:

**Step 1 — Get the request ID**: the `UNKNOWN` error should have a `RequestInfo` detail. If not, the server's error handling is missing request ID injection — fix that first (it makes all future debugging tractable).

**Step 2 — Correlate server logs**: search for the request ID in server logs. `UNKNOWN` errors from the gRPC framework are almost always unhandled panics or uncaught exceptions that the framework catches and returns as `UNKNOWN`. Look for panic stack traces or exception logs near the timestamp.

**Step 3 — Check the error source**: in Go, `status.Error(codes.Unknown, err.Error())` is the most common source — a developer passed a raw error to `status.Error` without classifying it. Search the codebase for `codes.Unknown` and `codes.unknown` to find all deliberate `UNKNOWN` returns.

**Step 4 — Check framework-generated `UNKNOWN`**: gRPC frameworks return `UNKNOWN` when: a handler panics (without a panic recovery interceptor), a serialization error occurs (proto marshal/unmarshal failure), or an unimplemented streaming handler is called. Add a recovery interceptor if missing.

**Step 5 — Fix**: replace all `codes.Unknown` returns with the appropriate specific code. Add a panic recovery interceptor that returns `codes.Internal`. Add request ID injection to all error responses. Treat `codes.Unknown` in production metrics as an alert — it should never appear in a well-maintained service.

**Q32. "How would you implement a gRPC interceptor that translates all domain errors to gRPC status codes in one place?"**
A: A domain error translation interceptor using sentinel errors and error unwrapping:

```go
// Domain error types
type NotFoundError struct {
    ResourceType string
    ResourceID   string
}
type ValidationError struct {
    Violations []FieldViolation
}
type ConflictError struct {
    Reason string
}

func ErrorTranslationInterceptor(ctx context.Context, req interface{},
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {

    resp, err := handler(ctx, req)
    if err == nil {
        return resp, nil
    }

    // Already a gRPC status error — ensure request ID is attached
    if st, ok := status.FromError(err); ok {
        enriched, enrichErr := st.WithDetails(&errdetails.RequestInfo{
            RequestId: requestIDFromContext(ctx),
        })
        if enrichErr == nil {
            return nil, enriched.Err()
        }
        return nil, err
    }

    requestID := requestIDFromContext(ctx)

    // Translate domain errors to gRPC status
    var notFound *NotFoundError
    var validation *ValidationError
    var conflict *ConflictError

    switch {
    case errors.As(err, &notFound):
        st, _ := status.New(codes.NotFound, "resource not found").
            WithDetails(
                &errdetails.ErrorInfo{Reason: "NOT_FOUND", Domain: "myservice.com"},
                &errdetails.ResourceInfo{
                    ResourceType: notFound.ResourceType,
                    ResourceName: notFound.ResourceID,
                },
                &errdetails.RequestInfo{RequestId: requestID},
            )
        return nil, st.Err()

    case errors.As(err, &validation):
        violations := make([]*errdetails.BadRequest_FieldViolation, len(validation.Violations))
        for i, v := range validation.Violations {
            violations[i] = &errdetails.BadRequest_FieldViolation{
                Field: v.Field, Description: v.Description,
            }
        }
        st, _ := status.New(codes.InvalidArgument, "validation failed").
            WithDetails(
                &errdetails.BadRequest{FieldViolations: violations},
                &errdetails.RequestInfo{RequestId: requestID},
            )
        return nil, st.Err()

    default:
        // Unknown error — log internally, return generic INTERNAL
        log.Errorf("[%s] unhandled error in %s: %v", requestID, info.FullMethod, err)
        st, _ := status.New(codes.Internal, "internal server error").
            WithDetails(&errdetails.RequestInfo{RequestId: requestID})
        return nil, st.Err()
    }
}
```

This pattern centralizes all gRPC status code decisions in one place — handlers deal only in domain errors, and the interceptor handles the translation. Adding a new error type requires only adding a new `case` in the interceptor, not modifying every handler.

## Key Concepts Cheat Sheet

| Term | One-line definition |
|--- |--- |
| `grpc-status` trailer | HTTP/2 trailer carrying the integer gRPC status code; 0 = OK |
| `grpc-message` trailer | URL-encoded human-readable error description trailer |

| `ErrorInfo` | Machine-readable `reason` + `domain` + `metadata`; most important detail type |
| `BadRequest` | Field-level violations for validation errors; all violations in one response |
| `RetryInfo` | Server-specified `retry_delay`; client should honor this over computed backoff |
| `RequestInfo` | Request ID for correlating client error reports with server logs |
| `DebugInfo` | Stack trace and debug detail; only for internal services, never external clients |
| `INVALID_ARGUMENT` | Client argument is wrong regardless of system state; never retry |
| `FAILED_PRECONDITION` | Valid argument, wrong system state; fix state before retrying |
| `ABORTED` | Concurrency conflict; retry the full operation sequence from scratch |
| `UNAVAILABLE` | Transient server unavailability; retry with backoff |
| `UNAUTHENTICATED` | No valid credentials; refresh auth before retrying |
| `PERMISSION_DENIED` | Authenticated but not authorized; different from `UNAUTHENTICATED` |
| Service config retry | Framework-level retry configured per method; transparent to application |
| Panic recovery interceptor | Server interceptor catching panics and returning `INTERNAL` |
| Error translation interceptor | Maps domain errors to gRPC codes centrally; handlers use only domain types |
| Passthrough error | Propagating upstream `google.rpc.Status` unchanged across service boundaries |
