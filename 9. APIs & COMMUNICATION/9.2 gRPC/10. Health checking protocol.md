# Health Checking Protocol — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is health checking and why does every production service need it?**
A: Health checking is the mechanism by which infrastructure — load balancers, orchestrators, service meshes, and monitoring systems — determines whether a service instance is capable of handling requests. It is the foundation of automated failure recovery: without health checks, a crashed or degraded pod continues receiving traffic until a human notices and intervenes. With health checks, infrastructure detects the problem within seconds and routes traffic away from the unhealthy instance automatically.

Every production service needs health checks because:

**Load balancer routing** — ALBs, NLBs, Nginx, and HAProxy only route to instances that pass health checks. An instance that fails its health check is removed from the rotation without manual intervention.

**Kubernetes pod lifecycle** — Kubernetes uses health checks (liveness, readiness, startup probes) to decide when to restart a pod, when to send it traffic, and when a new pod has finished initializing. Without them, Kubernetes sends traffic to pods that are still bootstrapping or are deadlocked, and never restarts pods that are alive but stuck.

**Rolling deployments** — a deployment only proceeds to the next batch of pods after the new pods pass their readiness check. Without readiness checks, traffic is sent to pods that haven't finished warming up connection pools, loading caches, or completing database migrations.

**Service mesh circuit breaking** — Istio and Linkerd use health check signals to automatically eject unhealthy endpoints from load balancing pools, implementing circuit breaking at the infrastructure layer rather than the application layer.

**Q2. What are the three types of health checks and what does each measure?**
A: The three types address different failure modes:

**Liveness check** — "is this process still alive and not deadlocked?" A liveness failure means the process should be killed and restarted. It detects: infinite loops that lock up all goroutines/threads, deadlocks, memory exhaustion causing the process to become unresponsive. A liveness check should be minimal — it must succeed as long as the process is running and not completely hung. It must NOT check whether downstream dependencies are healthy; a database outage should not cause the service to restart in a loop.

**Readiness check** — "is this instance ready to receive traffic?" A readiness failure means traffic should be routed away from this instance, but the instance should not be restarted. It detects: the instance is still initializing (loading caches, running migrations, warming connection pools), the instance is temporarily overloaded and needs backpressure, or a critical dependency is currently unavailable and the instance cannot process requests correctly. When a readiness check fails, the load balancer removes the instance from rotation; when it passes again, the instance is returned to rotation.

**Startup check** — "has this process finished its initialization phase?" A startup failure means the instance hasn't started yet and should not receive traffic, but should be given more time before being considered failed. Without startup probes, a slow-starting container (one that takes 60 seconds to load a large ML model or run database migrations) would repeatedly fail its liveness check during startup and be killed before it can finish initializing.

```
Process lifecycle:
  Starting    → Startup probe  (pass: move to Running phase)
  Running     → Liveness probe (fail: restart the container)
  Running     → Readiness probe (fail: remove from LB pool; pass: add to LB pool)
```

**Q3. What is the difference between a shallow health check and a deep health check?**
A: The distinction matters for liveness vs readiness:

**Shallow (liveness) check** — verifies only that the process is alive and its event loop / thread pool is responsive. Does not check external dependencies. Returns a fixed response from a handler that the event loop executes:

```
GET /health/live → 200 OK {"status": "ok"}
```

If this returns 200, the event loop is running, memory is not exhausted, and the process is not deadlocked. This is sufficient for liveness — if these are true, restarting won't help; if they're false, restarting may help.

**Deep (readiness) check** — verifies that the service can actually process requests end-to-end. Checks the health of critical dependencies: database connectivity (execute a `SELECT 1`), Redis connectivity (PING), message queue consumer lag (is the consumer keeping up?), external API availability (can we reach the PSP?):

```
GET /health/ready → 200 OK or 503 Service Unavailable
{
  "status": "degraded",
  "checks": {
    "database": "ok",
    "redis": "ok",
    "kafka": "degraded",
    "psp": "ok"
  }
}
```

If `kafka` is degraded, the readiness check fails → the load balancer routes traffic away. The instance does not restart (liveness is still passing). When Kafka recovers, the readiness check passes again → traffic resumes.

The critical antipattern: using a deep check for liveness. If a database outage causes liveness to fail, all instances restart simultaneously in a loop — a "thundering herd" that further stresses the recovering database and makes the outage worse. Liveness must be shallow; readiness can be deep.

## Section 2: HTTP Health Check Design

**Q4. What should health check endpoints return?**
A: Health check endpoints should return structured JSON with enough detail for both automated infrastructure and human operators:

```
GET /health
```

```json
{
  "status": "healthy",
  "version": "1.4.2",
  "commit":  "a3f9b12",
  "uptime":  "3h42m15s",
  "checks": {
    "database": {
      "status":      "healthy",
      "latencyMs":   2,
      "lastChecked": "2024-07-23T14:03:00Z"
    },
    "redis": {
      "status":      "healthy",
      "latencyMs":   0,
      "lastChecked": "2024-07-23T14:03:00Z"
    },
    "kafka": {
      "status":      "degraded",
      "message":     "consumer lag on 'payments' topic: 15,000 records",
      "lastChecked": "2024-07-23T14:03:00Z"
    }
  }
}
```

HTTP status codes map to overall health:
- `200 OK` — service is healthy and ready to serve traffic.
- `503 Service Unavailable` — service is unhealthy; infrastructure should route traffic away.
- `500 Internal Server Error` — the health check itself failed unexpectedly; treat as unhealthy.

**Why `503` and not `200` with `{"status": "unhealthy"}`:** Load balancers and Kubernetes probes read the HTTP status code, not the body. A `200` response with an "unhealthy" body will fool most infrastructure into keeping the instance in rotation. The HTTP status code is the machine signal; the body is the human-readable explanation.

**Q5. How do you implement a health check endpoint in NestJS?**
A:

```typescript
// health.module.ts
import { Module } from '@nestjs/common';
import { TerminusModule } from '@nestjs/terminus';
import { HttpModule } from '@nestjs/axios';
import { HealthController } from './health.controller';
import { DatabaseHealthIndicator } from './indicators/database.health';
import { RedisHealthIndicator } from './indicators/redis.health';
import { KafkaHealthIndicator } from './indicators/kafka.health';

@Module({
  imports: [TerminusModule, HttpModule],
  controllers: [HealthController],
  providers: [DatabaseHealthIndicator, RedisHealthIndicator, KafkaHealthIndicator],
})
export class HealthModule {}
```

```typescript
// health.controller.ts
import { Controller, Get } from '@nestjs/common';
import {
  HealthCheck, HealthCheckService, HealthCheckResult,
  TypeOrmHealthIndicator, MicroserviceHealthIndicator,
} from '@nestjs/terminus';
import { DatabaseHealthIndicator } from './indicators/database.health';
import { RedisHealthIndicator } from './indicators/redis.health';

@Controller('health')
export class HealthController {
  constructor(
    private health: HealthCheckService,
    private db: DatabaseHealthIndicator,
    private redis: RedisHealthIndicator,
  ) {}

  // Liveness: is the process alive?
  @Get('live')
  @HealthCheck()
  liveness(): Promise<HealthCheckResult> {
    // Minimal check — just executes a handler in the event loop
    return this.health.check([]);   // empty checks = "event loop is running"
  }

  // Readiness: can the service handle traffic?
  @Get('ready')
  @HealthCheck()
  readiness(): Promise<HealthCheckResult> {
    return this.health.check([
      () => this.db.isHealthy('database'),
      () => this.redis.isHealthy('redis'),
    ]);
  }

  // Full: detailed status for monitoring dashboards
  @Get()
  @HealthCheck()
  full(): Promise<HealthCheckResult> {
    return this.health.check([
      () => this.db.isHealthy('database'),
      () => this.redis.isHealthy('redis'),
      // kafka, external APIs, etc.
    ]);
  }
}
```

```typescript
// indicators/database.health.ts
import { Injectable } from '@nestjs/common';
import {
  HealthIndicator, HealthIndicatorResult, HealthCheckError
} from '@nestjs/terminus';
import { InjectDataSource } from '@nestjs/typeorm';
import { DataSource } from 'typeorm';

@Injectable()
export class DatabaseHealthIndicator extends HealthIndicator {
  constructor(
    @InjectDataSource() private readonly dataSource: DataSource
  ) {
    super();
  }

  async isHealthy(key: string): Promise<HealthIndicatorResult> {
    const start = Date.now();
    try {
      await this.dataSource.query('SELECT 1');
      const latencyMs = Date.now() - start;

      return this.getStatus(key, true, { latencyMs });

    } catch (err) {
      throw new HealthCheckError(
        'Database check failed',
        this.getStatus(key, false, { error: err.message })
      );
    }
  }
}
```

**Terminus** is the standard NestJS health check library. It handles: aggregating multiple check results, setting the correct HTTP status code (`200` vs `503`), and formatting the response body consistently. The `HealthCheckError` exception is caught by Terminus and converted to a `503` response automatically.

**Q6. What are the performance concerns with health check endpoints and how do you address them?**
A: Health checks run frequently — Kubernetes defaults to probing every 10 seconds per pod. At 100 pods, that is 10 probes per second hitting the health endpoint. At 1,000 pods, it is 100 probes per second. Each probe that executes a `SELECT 1` against the database adds load to the database.

**Caching health check results:**

```typescript
@Injectable()
export class CachedDatabaseHealthIndicator extends HealthIndicator {
  private lastResult: HealthIndicatorResult | null = null;
  private lastChecked: number = 0;
  private readonly cacheTtlMs = 5_000;  // cache for 5 seconds

  async isHealthy(key: string): Promise<HealthIndicatorResult> {
    const now = Date.now();
    if (this.lastResult && now - this.lastChecked < this.cacheTtlMs) {
      return this.lastResult;  // return cached result
    }

    // Execute the actual check
    try {
      const start = Date.now();
      await this.dataSource.query('SELECT 1');
      const latencyMs = Date.now() - start;

      this.lastResult = this.getStatus(key, true, { latencyMs });
      this.lastChecked = now;
      return this.lastResult;

    } catch (err) {
      this.lastResult = null;  // don't cache failures (check again immediately)
      throw new HealthCheckError('DB check failed',
        this.getStatus(key, false, { error: err.message }));
    }
  }
}
```

Caching for 5 seconds means at 100 pods × 1 probe/10s = 10 probes/second, the database sees at most `100 / (5000ms / 10000ms interval) = ~2` actual `SELECT 1` queries per second rather than 10. Cache successes but not failures — a failing dependency should be re-checked on every probe to detect recovery quickly.

**Dedicated connection pool for health checks:**
If the main connection pool is exhausted (a symptom of overload), the health check should not compete for connections. Use a separate, small pool exclusively for health check queries:

```typescript
// Health check uses its own connection, not the application pool
const healthCheckConnection = await createConnection({
  ...mainDbConfig,
  name: 'health-check',
  extra: { max: 1, min: 1 }   // single dedicated connection
});
```

## Section 3: Kubernetes Probes

**Q7. How do you configure Kubernetes liveness, readiness, and startup probes?**
A: Kubernetes probes are configured in the pod spec's container definition:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  template:
    spec:
      containers:
        - name: payment-service
          image: payment-service:1.4.2
          ports:
            - containerPort: 3000

          startupProbe:
            httpGet:
              path: /health/live
              port: 3000
            # Allow up to 60s × 10 attempts = 600s for startup
            failureThreshold: 60
            periodSeconds: 10
            # Don't start liveness/readiness until startup passes
            initialDelaySeconds: 0

          livenessProbe:
            httpGet:
              path: /health/live
              port: 3000
            initialDelaySeconds: 0     # startup probe guards early phase
            periodSeconds: 10          # probe every 10 seconds
            timeoutSeconds: 5          # fail if no response within 5s
            failureThreshold: 3        # restart after 3 consecutive failures
            successThreshold: 1        # 1 success to recover

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 3000
              httpHeaders:
                - name: Accept
                  value: application/json
            initialDelaySeconds: 0
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3        # remove from LB after 3 failures
            successThreshold: 2        # require 2 consecutive successes to re-add
                                       # (prevents flapping)
```

**Key configuration decisions:**

`failureThreshold` for liveness — how many consecutive failures before the container is restarted. A threshold of 3 with `periodSeconds: 10` means 30 seconds of unresponsiveness before a restart. Set this high enough to tolerate transient GC pauses or brief spikes without unnecessary restarts, but low enough that a truly deadlocked container is restarted in a reasonable time.

`successThreshold` for readiness — must be ≥ 1. Setting it to 2 prevents flapping: a pod that alternates between healthy and unhealthy on every probe is not repeatedly added to and removed from the load balancer rotation. Two consecutive successes are required before traffic is restored.

`timeoutSeconds` — must be less than `periodSeconds`. If the health check takes longer than `timeoutSeconds`, it's counted as a failure. Set to 5 seconds; if your health check consistently takes close to 5 seconds, that's a performance problem in the health check itself.

**Q8. What is the startup probe and when do you need it?**
A: Before startup probes were added (Kubernetes 1.18), teams had to choose between:
- Large `initialDelaySeconds` on the liveness probe (e.g., 120 seconds) — wastes time for fast-starting containers; masks liveness failures during early startup.
- Small `initialDelaySeconds` — kills slow-starting containers (database migration, model loading) before they finish initializing.

The startup probe solves this cleanly: it runs instead of the liveness and readiness probes until it passes. Once it passes, the liveness and readiness probes take over. This gives slow-starting containers all the time they need without delaying failure detection for fast-starting containers.

```yaml
startupProbe:
  httpGet:
    path: /health/live
    port: 3000
  failureThreshold: 30     # 30 attempts × 10 seconds = 5 minutes maximum startup time
  periodSeconds: 10
```

Use startup probes for: services that run database migrations on startup, services that load large models or caches into memory, services that warm connection pools before accepting traffic.

**Q9. What happens during a rolling deployment with readiness probes?**
A: Readiness probes are what make zero-downtime rolling deployments possible:

```
Initial state: 3 pods running v1, all passing readiness → serving traffic

Rolling update to v2 begins:
  Pod v1-1 is terminated (gets SIGTERM; completes in-flight requests)
  Pod v2-1 starts; startup probe runs
  ↓
  Pod v2-1 startup probe passes
  ↓
  Pod v2-1 readiness probe begins
  Pod v2-1 readiness FAILS (still warming up; DB connections not yet established)
  Traffic continues to v1-2 and v1-3 only
  ↓
  Pod v2-1 readiness PASSES (fully initialized)
  Traffic routes to v1-2, v1-3, v2-1
  ↓
  Pod v1-2 terminates; Pod v2-2 starts; same cycle
  ↓
  ...until all pods are v2
```

Without readiness probes: Kubernetes terminates v1-1 and immediately starts routing traffic to v2-1 — which may not have established its database connections yet. Users get connection errors during the few seconds it takes v2-1 to initialize.

**`maxUnavailable` and `maxSurge`** in the deployment strategy control the rollout pace:
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0    # never reduce below the desired number of pods
    maxSurge: 1          # allow 1 extra pod during rollout
```

`maxUnavailable: 0` + `maxSurge: 1` is the safest configuration: always maintain the full capacity; bring up a new pod before taking down an old one. Requires extra resources during rollout.

## Section 4: gRPC Health Checking Protocol

**Q10. What is the gRPC Health Checking Protocol and how does it differ from HTTP health checks?**
A: The gRPC Health Checking Protocol (defined in `grpc/health/v1`) is a standardized way to expose health status over gRPC. Infrastructure that communicates with gRPC services (Kubernetes, Envoy, Istio) uses this protocol instead of HTTP checks.

The protocol defines a single service and two methods:

```protobuf
syntax = "proto3";
package grpc.health.v1;

service Health {
  // Unary check — returns current health status
  rpc Check(HealthCheckRequest) returns (HealthCheckResponse);

  // Server-streaming watch — streams status updates as they change
  rpc Watch(HealthCheckRequest) returns (stream HealthCheckResponse);
}

message HealthCheckRequest {
  string service = 1;   // empty string = overall server health
                        // "payments.ChargesService" = specific service health
}

message HealthCheckResponse {
  enum ServingStatus {
    UNKNOWN        = 0;
    SERVING        = 1;    // healthy; accept traffic
    NOT_SERVING    = 2;    // unhealthy; do not send traffic
    SERVICE_UNKNOWN = 3;   // requested service is not registered
  }
  ServingStatus status = 1;
}
```

The `service` field enables per-service health within a single gRPC server — a server may host multiple services (ChargesService, RefundsService) and report them as independently healthy or unhealthy.

**Q11. How do you implement the gRPC health checking protocol in Go?**
A:

```go
import (
  "google.golang.org/grpc"
  "google.golang.org/grpc/health"
  "google.golang.org/grpc/health/grpc_health_v1"
)

func main() {
  server := grpc.NewServer(/* interceptors */)

  // Register your application services
  pb.RegisterChargesServiceServer(server, &chargesServer{})
  pb.RegisterRefundsServiceServer(server, &refundsServer{})

  // Register the health service
  healthServer := health.NewServer()
  grpc_health_v1.RegisterHealthServer(server, healthServer)

  // Set initial status for each service
  healthServer.SetServingStatus("", grpc_health_v1.HealthCheckResponse_SERVING)
  healthServer.SetServingStatus(
    "payments.ChargesService",
    grpc_health_v1.HealthCheckResponse_SERVING,
  )
  healthServer.SetServingStatus(
    "payments.RefundsService",
    grpc_health_v1.HealthCheckResponse_SERVING,
  )

  // Background goroutine updates status based on dependency health
  go func() {
    for {
      time.Sleep(10 * time.Second)
      checkAndUpdateHealth(healthServer)
    }
  }()

  server.Serve(listener)
}

func checkAndUpdateHealth(hs *health.Server) {
  // Check database connectivity
  if err := db.Ping(); err != nil {
    // Database is down — mark both services as not serving
    hs.SetServingStatus("", grpc_health_v1.HealthCheckResponse_NOT_SERVING)
    hs.SetServingStatus("payments.ChargesService", grpc_health_v1.HealthCheckResponse_NOT_SERVING)
    log.Printf("Health: NOT_SERVING (DB error: %v)", err)
    return
  }

  // All dependencies healthy
  hs.SetServingStatus("", grpc_health_v1.HealthCheckResponse_SERVING)
  hs.SetServingStatus("payments.ChargesService", grpc_health_v1.HealthCheckResponse_SERVING)
  log.Printf("Health: SERVING")
}
```

**Graceful shutdown using the health server:**

```go
// On SIGTERM: mark as NOT_SERVING before stopping
// This signals load balancers to stop sending new requests
// while in-flight requests complete
c := make(chan os.Signal, 1)
signal.Notify(c, os.Interrupt, syscall.SIGTERM)

go func() {
  <-c
  log.Println("Received SIGTERM — marking NOT_SERVING")

  // Mark unhealthy first
  healthServer.SetServingStatus("", grpc_health_v1.HealthCheckResponse_NOT_SERVING)

  // Wait for load balancer to detect the status change
  // (probe interval + propagation time)
  time.Sleep(15 * time.Second)

  // Now gracefully stop (drains in-flight RPCs)
  server.GracefulStop()
}()
```

This pattern — mark NOT_SERVING, wait, then stop — ensures no new requests arrive during the shutdown window. Without it, the load balancer continues routing requests to the pod until after it stops, causing connection resets for new connections.

**Q12. How do you configure Kubernetes to use gRPC health checks instead of HTTP?**
A: Kubernetes 1.24+ supports gRPC probes natively using the `grpc` probe type:

```yaml
livenessProbe:
  grpc:
    port: 50051
    service: ""     # empty string = overall server health
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  grpc:
    port: 50051
    service: "payments.ChargesService"  # check specific service
  periodSeconds: 10
  failureThreshold: 3
  successThreshold: 2
```

For Kubernetes versions before 1.24, use `grpc-health-probe` as an exec probe:

```yaml
livenessProbe:
  exec:
    command:
      - /bin/grpc_health_probe
      - -addr=:50051
      - -service=
  periodSeconds: 10
  failureThreshold: 3
```

The `grpc-health-probe` binary is a small CLI tool that implements the gRPC health checking protocol and exits with code 0 (healthy) or non-zero (unhealthy). It must be included in the container image.

## Section 5: Health Check Patterns

**Q13. How do you implement graceful shutdown with health checks?**
A: Graceful shutdown is the counterpart to health-check-based startup — it ensures no new traffic arrives after the process begins shutting down, while in-flight requests complete. The pattern:

```typescript
// Node.js / NestJS graceful shutdown
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);

  // Register a flag that the readiness check reads
  let isShuttingDown = false;

  // Health controller reads this flag
  app.get(HealthController).setShutdownFlag(() => isShuttingDown);

  // Handle SIGTERM (sent by Kubernetes before pod termination)
  process.on('SIGTERM', async () => {
    console.log('SIGTERM received — starting graceful shutdown');

    // Step 1: Fail readiness immediately
    // Load balancer detects this within 1–2 probe intervals (10–20s)
    // and stops routing new requests to this pod
    isShuttingDown = true;

    // Step 2: Wait for load balancer to stop sending traffic
    // Must be > probe interval + LB propagation time
    const drainWaitMs = 15_000;
    console.log(`Waiting ${drainWaitMs}ms for load balancer drain...`);
    await sleep(drainWaitMs);

    // Step 3: Close the HTTP server (stop accepting new connections)
    // In-flight requests continue processing until complete
    await app.close();

    console.log('Graceful shutdown complete');
    process.exit(0);
  });
}
```

```typescript
// health.controller.ts — readiness reads the shutdown flag
@Get('ready')
@HealthCheck()
readiness(): Promise<HealthCheckResult> {
  if (this.isShuttingDown()) {
    throw new ServiceUnavailableException('Service is shutting down');
  }
  return this.health.check([
    () => this.db.isHealthy('database'),
    () => this.redis.isHealthy('redis'),
  ]);
}
```

**The timing must account for:**
- Kubernetes probe interval (default 10s).
- Load balancer propagation time (1–5s typically).
- Total drain wait: probe_interval + propagation + safety margin ≥ `terminationGracePeriodSeconds - shutdown_time`.

Configure `terminationGracePeriodSeconds` in the pod spec to be longer than the drain wait plus the maximum expected in-flight request duration:

```yaml
spec:
  terminationGracePeriodSeconds: 60   # default is 30; increase for slow shutdowns
  containers:
    - name: payment-service
```

**Q14. How do you implement dependency-level health checks with weighted severity?**
A: Not all dependency failures have the same impact. A cache miss is survivable (fall back to DB); a database failure is fatal; a metrics exporter failure is irrelevant to request processing. Health checks should reflect this:

```typescript
enum DependencySeverity {
  CRITICAL  = 'critical',    // affects readiness; service cannot function
  DEGRADED  = 'degraded',    // service functions with reduced capability
  OPTIONAL  = 'optional',    // failure logged but ignored for health status
}

interface DependencyCheck {
  name:     string;
  severity: DependencySeverity;
  check:    () => Promise<{ healthy: boolean; latencyMs: number; message?: string }>;
}

@Injectable()
export class HealthAggregator {
  private readonly checks: DependencyCheck[] = [
    {
      name: 'database',
      severity: DependencySeverity.CRITICAL,
      check: () => this.db.ping(),
    },
    {
      name: 'redis',
      severity: DependencySeverity.DEGRADED,    // falls back to DB if Redis is down
      check: () => this.redis.ping(),
    },
    {
      name: 'metrics-exporter',
      severity: DependencySeverity.OPTIONAL,
      check: () => this.metrics.ping(),
    },
  ];

  async getReadinessStatus(): Promise<{
    ready: boolean;
    status: 'healthy' | 'degraded' | 'unhealthy';
    checks: Record<string, unknown>;
  }> {
    const results: Record<string, unknown> = {};
    let hasCriticalFailure = false;
    let hasDegradedFailure = false;

    for (const dep of this.checks) {
      try {
        const result = await withTimeout(dep.check(), 3_000);
        results[dep.name] = { status: 'healthy', ...result };
      } catch (err) {
        results[dep.name] = { status: 'unhealthy', error: err.message };
        if (dep.severity === DependencySeverity.CRITICAL) hasCriticalFailure = true;
        if (dep.severity === DependencySeverity.DEGRADED) hasDegradedFailure = true;
        // OPTIONAL failures are ignored for status determination
      }
    }

    const ready = !hasCriticalFailure;
    const status = hasCriticalFailure ? 'unhealthy'
                 : hasDegradedFailure ? 'degraded'
                 : 'healthy';

    return { ready, status, checks: results };
  }
}
```

The readiness endpoint returns `503` only when a `CRITICAL` dependency fails. A `DEGRADED` failure changes the status to `"degraded"` in the body (useful for dashboards) but does not remove the instance from traffic rotation — the service continues operating in a reduced capacity mode.

**Q15. What are health check anti-patterns to avoid?**
A: Six anti-patterns that cause production incidents:

**1. Deep liveness checks** — checking database connectivity in the liveness probe. A database outage kills all pods in a restart loop, making recovery far harder. Keep liveness shallow.

**2. Health check timeout longer than probe period** — if `timeoutSeconds: 15` and `periodSeconds: 10`, a slow health check runs concurrently with itself, accumulating resource exhaustion. `timeoutSeconds` must be less than `periodSeconds`.

**3. Not caching health check results** — a health check that hits the database on every probe at 100 pods × 0.1 probes/second = 10 DB queries/second for probes alone. Cache results for 5–10 seconds.

**4. Health check endpoint on the same port as the application** — if the application is overloaded (all threads busy), the health check cannot get a thread to execute and fails, causing Kubernetes to kill the pod — exactly when you want it to stay alive and recover. Use a dedicated health check port on a separate HTTP server that runs on its own goroutine/thread pool.

```typescript
// Dedicated health check server on separate port
// Cannot be blocked by the main application's thread pool exhaustion
const healthApp = express();
healthApp.get('/health/live', (req, res) => res.json({ status: 'ok' }));
healthApp.listen(3001);  // dedicated port; separate from main app on 3000
```

**5. No graceful shutdown drain** — terminating the process immediately on SIGTERM causes connection resets for in-flight requests. Always implement the mark-unhealthy → wait → stop sequence.

**6. Health check that always returns 200** — a no-op health check defeats the purpose. Infrastructure assumes the instance is healthy and routes traffic to a deadlocked or dependency-starved instance. If you're going to have a health check endpoint, make it meaningful.

## Section 6: Observability Integration

**Q16. How do health check results integrate with monitoring and alerting?**
A: Health check failures are events that must be surfaced in monitoring:

**Metrics to emit from health check endpoints:**

```typescript
// Emit Prometheus metrics from the health check handler
const healthCheckDuration = new Histogram({
  name: 'health_check_duration_seconds',
  help: 'Duration of health check dependency probes',
  labelNames: ['dependency', 'status'],
});

const healthCheckStatus = new Gauge({
  name: 'health_check_status',
  help: 'Current health status per dependency (1=healthy, 0=unhealthy)',
  labelNames: ['dependency'],
});

// After each dependency check:
healthCheckDuration.observe(
  { dependency: 'database', status: result.healthy ? 'healthy' : 'unhealthy' },
  result.latencyMs / 1000
);
healthCheckStatus.set(
  { dependency: 'database' },
  result.healthy ? 1 : 0
);
```

**Alerting rules:**

```yaml
# Prometheus alert rules
groups:
  - name: health_checks
    rules:

      # Alert if any instance's health check has been failing
      - alert: ServiceReadinessCheckFailing
        expr: health_check_status{dependency="database"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Database health check failing on {{ $labels.instance }}"

      # Alert if health check itself is slow (potential cascading failure)
      - alert: HealthCheckLatencyHigh
        expr: >
          histogram_quantile(0.99,
            rate(health_check_duration_seconds_bucket[5m])
          ) > 2
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Health check p99 latency > 2s on {{ $labels.instance }}"

      # Alert if Kubernetes has removed instances from LB pool
      - alert: PodReadinessLow
        expr: >
          kube_deployment_status_replicas_ready /
          kube_deployment_spec_replicas < 0.5
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Less than 50% of pods ready for {{ $labels.deployment }}"
```

The `kube_deployment_status_replicas_ready` metric (from kube-state-metrics) tells you how many pods are currently passing their readiness probe and in the load balancer pool. If fewer than 50% are ready, the deployment is severely degraded.

## Section 7: Scenario Questions

**Q17. "All pods in your deployment are being restarted repeatedly every 2 minutes. How do you diagnose this?"**
A: Repeated pod restarts indicate the liveness probe is failing. Systematic diagnosis:

**Step 1: Check pod events.**
```bash
kubectl describe pod payment-service-abc123

# Look for:
Events:
  Warning  Unhealthy  2m  kubelet  Liveness probe failed:
    Get "http://10.0.1.5:3000/health/live": context deadline exceeded (Client.Timeout exceeded)
  Normal   Killing    2m  kubelet  Container payment-service failed liveness probe,
    will be restarted
```
The event tells you exactly which probe failed and why.

**Step 2: Check container logs before the restart.**
```bash
kubectl logs payment-service-abc123 --previous
# Shows logs from the container instance that just died
```
Look for: OOM killer messages, deadlock stack traces, panic output, "SIGKILL received."

**Step 3: Check if the health endpoint is responding.**
```bash
# Port-forward to the pod and test directly
kubectl port-forward pod/payment-service-abc123 3000:3000
curl -v http://localhost:3000/health/live
```
If this succeeds but Kubernetes is failing the probe, the issue is timing: the health check takes longer than `timeoutSeconds`. If it hangs, the event loop is blocked.

**Step 4: Check for a deep liveness check.**
If the liveness probe checks the database and the database is currently down or slow, the liveness probe fails → Kubernetes restarts the pod → the restarted pod also fails its liveness probe (because the database is still down) → infinite restart loop. Fix: move database checks to the readiness probe, not liveness.

**Step 5: Check resource limits.**
```bash
kubectl top pod payment-service-abc123
```
If the pod is hitting its memory limit, the OOM killer terminates it — Kubernetes shows this as a liveness failure. Fix: increase memory limits or investigate memory leak.

**Q18. "During a deployment, new pods pass their startup probe but fail their readiness probe indefinitely. The deployment is stuck. What are the likely causes?"**
A: The deployment is stuck because readiness never passes, so the old pods are never terminated (with `maxUnavailable: 0`), and the new pods never receive traffic.

**Likely causes and diagnosis:**

**Database migration blocking readiness:**
The new version runs a database migration on startup that takes longer than expected. The readiness check verifies the schema is correct, but the migration is still running. Check pod logs:
```bash
kubectl logs payment-service-new-xyz --follow
# Look for: "Running migration 20240723_add_column..."
```
Fix: run migrations as a Kubernetes Job before the deployment, not inside the application startup.

**New environment variable or secret missing:**
The new version requires a new environment variable (`PSP_API_KEY_V2`) that wasn't added to the deployment config. The service starts but the readiness check fails because it can't connect to the PSP. Check:
```bash
kubectl exec payment-service-new-xyz -- env | grep PSP
```

**Readiness check pointing to a wrong port or path:**
The new version changed the health check path from `/health` to `/health/ready` but the Kubernetes probe still points to `/health`. The probe gets `404 Not Found` → readiness fails. Check:
```bash
kubectl describe deployment payment-service | grep -A 20 "Readiness"
```

**Connection pool saturation:**
The new pods cannot acquire database connections because the pool is exhausted — all connections are held by the old pods. The `SELECT 1` in the readiness check times out. Fix: increase the connection pool size or reduce `maxSurge` so fewer new pods start simultaneously.

**Readiness `successThreshold` set too high:**
`successThreshold: 10` means 10 consecutive successful probes before the pod is considered ready — at `periodSeconds: 10`, that's 100 seconds of healthy operation before traffic begins. This is rarely intended and creates a long deployment time. Fix: set `successThreshold: 1` or `2`.

**Q19. "Your service depends on 5 external APIs. One of them (a fraud scoring API) is intermittently returning 503. Should this fail your readiness probe? What is the correct approach?"**
A: This is a deliberate design decision requiring business context:

**If fraud scoring is optional (degrade, don't fail):**
The service can process payments without fraud scoring — perhaps by falling back to rule-based fraud detection or by accepting slightly more risk temporarily. In this case:
- Classify fraud scoring as `DependencySeverity.DEGRADED`.
- The readiness check passes; traffic continues flowing.
- The response body includes `"fraudApi": {"status": "degraded"}`.
- An alert fires on the degraded status, but customers are not affected.
- Operations can choose to manually scale down or reroute traffic based on the alert.

**If fraud scoring is required (block readiness):**
Regulatory requirements or risk policy mandates that no payment is processed without fraud scoring. In this case:
- Classify fraud scoring as `DependencySeverity.CRITICAL`.
- Readiness fails when the fraud API is down → load balancer removes the instance from rotation.
- But: if all instances fail readiness simultaneously (the fraud API is globally down), no instance serves traffic. The service is completely unavailable. Is this the correct behavior?

**The nuanced answer at 5 YOE level:**
Rather than using the readiness probe to gate on the fraud API, implement this at the application level:
- Readiness probe passes as long as the service can process requests.
- The fraud check handler itself returns `503` to the caller when the fraud API is unavailable.
- The caller (checkout service) receives an explicit, actionable error rather than a connection reset from a removed-from-LB instance.
- Operations can monitor `fraud_api_errors_total` and decide to trigger a maintenance mode if the dependency is down for an extended period.

This approach is more surgical: the fraud API being down affects fraud-checking requests specifically, not all requests to the payment service. Using readiness to gate on a non-universal dependency is a blunt instrument that affects all callers.

## Quick Reference

| Probe | What it checks | On failure | Check depth |
|--- |--- |--- |--- |
| Startup | Has the container finished initializing? | Wait; restart after `failureThreshold` | Shallow (liveness endpoint) |
| Liveness | Is the process alive and not deadlocked? | Restart the container | Shallow — never check dependencies |
| Readiness | Can this instance handle traffic right now? | Remove from LB pool | Deep — check critical dependencies |

| Setting | Default | Recommendation |
|--- |--- |--- |
| `periodSeconds` | 10 | Keep at 10 for most services |
| `timeoutSeconds` | 1 | Set to 5; must be < `periodSeconds` |
| `failureThreshold` (liveness) | 3 | 3 (30s before restart at 10s period) |
| `failureThreshold` (readiness) | 3 | 3 (30s before LB removal) |
| `successThreshold` (readiness) | 1 | Set to 2 to prevent flapping |
| `terminationGracePeriodSeconds` | 30 | Increase to 60+ for slow shutdowns |

| Pattern | Purpose | Implementation |
|--- |--- |--- |
| Shallow liveness | Prevent restart loop on dependency failure | No dependency checks in `/health/live` |
| Cached readiness | Reduce dependency probe load | Cache check results for 5–10s; refresh on failure |
| Dedicated health port | Prevent LB failure during app thread exhaustion | Separate HTTP server on port 3001 |
| Graceful shutdown drain | Prevent connection resets on termination | Mark NOT_SERVING → wait 15s → stop |
| Severity-weighted checks | Degrade gracefully on non-critical failures | CRITICAL fails readiness; DEGRADED reports only |
| gRPC health protocol | Standard health checking for gRPC services | `grpc/health/v1` service; per-service status |

---

**Tip for the interview:** Health check questions at 5 YOE level test whether you understand the three-probe model deeply enough to design it correctly under constraints. The critical insight interviewers probe for: liveness must never check dependencies — a database outage causing all pods to restart simultaneously is worse than the original outage. The three scenarios that signal production depth: knowing that `successThreshold: 2` prevents readiness flapping, explaining the graceful shutdown drain timing (mark unhealthy → wait for probe interval + LB propagation → stop), and articulating why a deep check on an optional dependency should return a degraded status body rather than a `503`. On gRPC: the health protocol's `service` field (per-service granularity within one server) and the graceful shutdown pattern (SetServingStatus NOT_SERVING before GracefulStop) show you've actually operated gRPC services rather than just read about them.
