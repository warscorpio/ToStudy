# Deadlines and Cancellation — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the difference between a timeout, a deadline, and a cancellation?**
A: These three concepts are related but distinct:
- **Timeout**: a relative duration — "wait at most 500 milliseconds." A timeout is expressed as a duration from now and is local to a single call or resource acquisition. It is recalculated each time it is applied. A 500ms timeout on hop A and a 500ms timeout on hop B means the request chain can take up to 1000ms total.
- **Deadline**: an absolute point in time — "this entire operation must complete by T+500ms from the moment the request started." A deadline is computed once at the origin of the request and propagated through every hop in the call chain. Each downstream service computes the remaining budget (`deadline - now`) rather than starting a fresh timer. A deadline can travel across network boundaries; a timeout resets at each hop.
- **Cancellation**: an explicit signal that work should be abandoned, independent of time. A client might cancel because the user navigated away, because a parallel request succeeded first (hedged requests), or because a business rule determined the result is no longer needed. Cancellation is event-driven rather than time-driven — it fires immediately when the cancellation signal is sent, not after a delay.

All three converge on the same mechanism in most frameworks — a context or future that becomes "done" — but their semantics differ: deadlines enforce end-to-end latency budgets, timeouts bound individual hops, and cancellation expresses intent to abandon.

**Q2. Why do distributed systems require explicit deadline and cancellation propagation rather than relying on per-hop timeouts?**
A: Per-hop timeouts create two fundamental problems at the system level. First, **latency additivity**: if Service A has a 1s timeout on calls to B, and B has a 1s timeout on calls to C, a request to A can take up to 2s from A's caller's perspective — far beyond any reasonable SLA. The total latency ceiling is the sum of all hop timeouts in the worst case, not the maximum. Second, **orphaned work**: when A's timeout fires, A abandons its call to B and returns an error. But B doesn't know A has given up — it continues computing, calling C, writing to databases, and holding locks. These downstream operations produce results that nobody will read and hold resources that nobody will release. At scale, orphaned work is a primary cause of resource exhaustion during cascading failures.

Explicit deadline propagation solves both: the end-to-end deadline bounds the total request duration regardless of chain depth, and each downstream service can check the remaining budget before starting expensive work — abandoning it immediately if the budget is exhausted. The downstream service knows the upstream has given up and can skip pointless computation.

**Q3. What is a context in the software sense, and why is it the standard carrier for deadlines and cancellation signals?**
A: A context is a handle passed through a call chain that carries: (1) a **cancellation signal** — a mechanism (typically a channel or future) that can be closed to signal all parties holding the context that work should stop; (2) a **deadline** — an absolute time beyond which all work is considered cancelled; (3) a **key-value store** — arbitrary request-scoped values (request ID, auth token, trace ID) that should be available throughout the call chain without being passed as explicit parameters.

It is the standard carrier because: the context is immutable and forms a tree (child contexts can add constraints but never loosen them — a child can have an earlier deadline but not a later one); it propagates naturally through function calls as the first parameter; and because it's a single object, adding a deadline or cancellation to an existing call chain requires changing only one parameter rather than threading two separate objects through every function signature. In Go, `context.Context` is the canonical implementation; in Java, gRPC uses `io.grpc.Context`; other languages have similar constructs.

**Q4. How do deadlines and cancellation interact — what happens when both are active?**
A: Deadlines and cancellation are independent signals that both result in the context's `Done()` channel being closed (or equivalent signal). Either can fire first:
- **Deadline fires first**: `ctx.Err()` returns `context.DeadlineExceeded`. The remaining time budget expired before the operation completed or was explicitly cancelled.
- **Cancellation fires first**: `ctx.Err()` returns `context.Canceled`. An explicit cancel call was made before the deadline.
- **Neither fires**: the operation completed before the deadline and no explicit cancellation occurred.

After either signal, the context is permanently done — it cannot be "un-cancelled" or "deadline-extended." Any subsequent check of `ctx.Err()` returns the same value. In Go 1.20+, `context.Cause(ctx)` returns the first error that caused the context to be cancelled, distinguishing between a deadline expiry and an explicit `CancelCauseFunc` call with a custom error — enabling more precise error reporting in complex cancellation hierarchies.

## Section 2: Context Mechanics

**Q5. How does Go's `context.Context` implement deadline and cancellation propagation?**
A: Go's context package provides four constructors that build a context tree:

```go
// Cancellation only — explicit cancel call required
ctx, cancel := context.WithCancel(parent)
defer cancel()  // ALWAYS defer; prevents context leak

// Timeout — relative duration; computed as deadline = now + timeout
ctx, cancel := context.WithTimeout(parent, 500*time.Millisecond)
defer cancel()

// Deadline — absolute time
ctx, cancel := context.WithDeadline(parent, time.Now().Add(500*time.Millisecond))
defer cancel()

// Value — attach key-value pair; does not affect cancellation
ctx = context.WithValue(parent, requestIDKey, "req-abc-123")
```

The context tree works by derivation: `WithCancel(parent)` creates a child context that is cancelled when either (1) the child's `cancel()` is called, or (2) the parent context is cancelled (whichever comes first). The child never has a later deadline than the parent — `WithDeadline(parent, t)` only sets the deadline if `t` is before the parent's deadline; otherwise it inherits the parent's deadline silently. This ensures the budget can only shrink as it passes deeper into the call chain.

The `Done()` channel is closed when the context is done; `Err()` returns the cause; `Deadline()` returns the absolute deadline if one is set. The internal implementation uses a linked list of cancellation watchers — when a parent is cancelled, it walks its children and cancels them in sequence.

**Q6. What is a context leak and why is it one of the most common Go bugs?**
A: A context leak occurs when a cancellable context is created but its `cancel` function is never called. Every `WithCancel`, `WithTimeout`, and `WithDeadline` call allocates internal resources — goroutines, timers, and memory — to track the context's cancellation state and to propagate cancellation to children. These resources are released when `cancel()` is called. If `cancel()` is never called, those resources accumulate indefinitely.

The canonical Go leak pattern:
```go
// Leak: cancel is never called if doWork returns early
func processRequest(parent context.Context) error {
    ctx, cancel := context.WithTimeout(parent, 5*time.Second)
    // forgot defer cancel()
    result, err := doWork(ctx)
    if err != nil {
        return err  // cancel is never called on this path
    }
    return process(result)
}

// Correct:
func processRequest(parent context.Context) error {
    ctx, cancel := context.WithTimeout(parent, 5*time.Second)
    defer cancel()  // called on ALL return paths
    // ...
}
```

`defer cancel()` immediately after creating the context is the universal fix — `defer` guarantees the cancel call regardless of how the function returns (normal return, error return, or panic). The Go documentation explicitly states: "Failing to call the CancelFunc leaks the child and its children until the parent is canceled or the timer fires."

**Q7. How does a context propagate cancellation through a goroutine tree?**
A: Context cancellation propagates **downward** through the context tree — from parent to child — but never upward. When a parent context is cancelled, all child and descendant contexts are immediately cancelled in cascade. A child's cancellation does not affect its parent or siblings.

```go
func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()

    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)
        go func(i int) {
            defer wg.Done()
            worker(ctx, i)  // all workers share the same context
        }(i)
    }
    wg.Wait()
}

func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            // All workers receive this signal simultaneously when
            // the parent's 2-second deadline fires or cancel() is called
            return
        default:
            doWork(ctx, id)
        }
    }
}
```

This is the **fan-out with shared cancellation** pattern — one parent context controls the lifecycle of all spawned workers. When the deadline fires or the parent is explicitly cancelled, all workers receive the signal on their `ctx.Done()` channel and can clean up and exit. The parent goroutine then proceeds normally after the workers have stopped.

**Q8. What is `context.Background()` vs `context.TODO()`, and when should each be used?**
A: Both are non-cancellable, never-deadline root contexts that exist as the top of every context tree. The distinction is semantic and documentational:
- `context.Background()`: the intended root context for the application's top-level operations — the main function, the top of a server handler chain, the start of a long-running background job. It signals: "this is a deliberate root; there is no parent context to inherit from."
- `context.TODO()`: a placeholder used when the correct context is not yet known — during development, when refactoring code that doesn't yet accept a context, or in tests that haven't been updated. It signals: "this should eventually receive a real context; this is a known TODO item."

In production code, `context.TODO()` should be rare or absent — it indicates incomplete propagation. `context.Background()` should appear only at entry points (HTTP handlers, main, Kafka consumers) where no parent context exists. All other context creation should derive from an incoming context, never from `context.Background()` mid-request, which would sever the deadline and cancellation chain.

## Section 3: Deadlines in gRPC

**Q9. How does gRPC propagate deadlines on the wire?**
A: gRPC uses an HTTP/2 header called `grpc-timeout` to transmit the remaining deadline budget. When a gRPC client makes a call with a context that has a deadline, the framework computes the remaining duration (`deadline - now`) and encodes it as a duration string in the `grpc-timeout` header: `"500m"` (500 milliseconds), `"2S"` (2 seconds), `"1M"` (1 minute).

On the server side, the gRPC framework reads `grpc-timeout`, reconstructs the deadline as `now + timeout`, and creates a new context with that deadline. This reconstructed deadline is passed to the server handler as the request context. The server handler's context is therefore already deadline-aware — `ctx.Deadline()` returns the propagated deadline, and the gRPC framework automatically cancels the handler's context when the deadline fires, returning `DEADLINE_EXCEEDED` to the client.

This mechanism has an important implication: gRPC transmits the *remaining budget* (a duration), not the original absolute deadline (a timestamp). This avoids clock synchronization problems between client and server — even if their clocks differ by 100ms, the timeout is computed relative to the server's local clock. The cost: if the network transit time is significant, the server's effective deadline is slightly shorter than the client intended (by the one-way transit time). This is usually acceptable for practical values of network latency.

**Q10. What is the difference between `DEADLINE_EXCEEDED` and `CANCELLED` in gRPC, and how do you distinguish them?**
A: Both indicate the operation did not complete, but for different reasons:
- **`DEADLINE_EXCEEDED`**: the context deadline expired before the operation completed. The clock ran out. This is always time-driven — either the client's deadline fired or the server's own internal deadline fired.
- **`CANCELLED`**: the operation was explicitly cancelled. On the client side this occurs when the client context is cancelled (user action, competing request succeeded, parent context cancelled). On the server side, the gRPC framework sends a `RST_STREAM` HTTP/2 frame when the client cancels; the server's context is cancelled, and the server should return `CANCELLED`.

Distinguishing in Go:
```go
if err := ctx.Err(); err != nil {
    switch err {
    case context.DeadlineExceeded:
        // Time ran out — return DEADLINE_EXCEEDED
        return status.Error(codes.DeadlineExceeded, "operation timed out")
    case context.Canceled:
        // Explicitly cancelled — return CANCELLED
        return status.Error(codes.Canceled, "operation cancelled by client")
    }
}
```

The practical difference for clients: `DEADLINE_EXCEEDED` suggests the operation is too slow (tune the deadline, optimize the server, or retry with a fresh deadline for idempotent operations); `CANCELLED` is typically a client-initiated signal requiring no retry — the client itself decided to stop.

**Q11. How should a gRPC server check the remaining deadline budget before making downstream calls?**
A: Before any expensive operation or downstream call, check whether the deadline has already expired or the budget is too thin to succeed:

```go
func (s *OrderService) CreateOrder(ctx context.Context, req *pb.CreateOrderRequest) (*pb.Order, error) {
    // Check if deadline already passed (early exit)
    if err := ctx.Err(); err != nil {
        return nil, status.FromContextError(err).Err()
    }

    // Check remaining budget before calling downstream
    if deadline, ok := ctx.Deadline(); ok {
        remaining := time.Until(deadline)
        if remaining < 50*time.Millisecond {
            // Budget too small to succeed — fail fast
            return nil, status.Error(codes.DeadlineExceeded,
                "insufficient deadline remaining")
        }
    }

    // Reserve a portion of the budget for local processing
    inventoryCtx, cancel := context.WithTimeout(ctx,
        time.Duration(float64(time.Until(deadline(ctx))) * 0.6))
    defer cancel()

    // Call downstream with the bounded sub-context
    inv, err := s.inventoryClient.CheckInventory(inventoryCtx, ...)
    // ...
}
```

The key operations: (1) `ctx.Err()` — check if already cancelled or deadline exceeded; (2) `ctx.Deadline()` — retrieve the absolute deadline; (3) compute the remaining budget and reject if it's below a meaningful floor; (4) optionally create a sub-context that reserves budget for local processing (so the downstream call doesn't consume the entire remaining budget, leaving no time to process the response). This is the **budget slicing** pattern.

## Section 4: Cancellation Patterns

**Q12. What is the "first response wins" pattern with cancellation, and where is it used?**
A: The first-response-wins pattern (also called hedged requests) fans out the same request to multiple backends simultaneously and cancels all remaining requests as soon as the first successful response arrives:

```go
func hedgedGet(ctx context.Context, urls []string) ([]byte, error) {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()

    results := make(chan []byte, len(urls))
    errs := make(chan error, len(urls))

    for _, url := range urls {
        go func(u string) {
            body, err := fetchURL(ctx, u)
            if err != nil {
                errs <- err
                return
            }
            results <- body
        }(url)
    }

    received := 0
    for received < len(urls) {
        select {
        case body := <-results:
            cancel()  // cancel all remaining in-flight requests
            return body, nil
        case <-errs:
            received++
        case <-ctx.Done():
            return nil, ctx.Err()
        }
    }
    return nil, errors.New("all backends failed")
}
```

When the first goroutine returns a result, `cancel()` is called, which cancels the shared context. All other goroutines blocking on network I/O or checking `ctx.Done()` receive the cancellation signal and exit early. This is used for: latency reduction (issue to the fastest available replica), fault tolerance (mask one slow or failing backend by racing against others), and read-your-own-writes consistency (fan out to all replicas, take the first that has your data).

**Q13. How do you implement a fan-out operation that cancels all downstream calls when any one fails?**
A: This is the inverse of first-response-wins — fail fast if any downstream fails:

```go
func fanOutWithFailFast(ctx context.Context, services []ServiceClient, req *pb.Request) error {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()

    errc := make(chan error, len(services))

    for _, svc := range services {
        svc := svc  // capture for goroutine
        go func() {
            errc <- svc.Call(ctx, req)
        }()
    }

    for range services {
        if err := <-errc; err != nil {
            cancel()  // cancel all remaining calls immediately
            return err
        }
    }
    return nil
}
```

When one goroutine returns an error: `cancel()` is called, propagating cancellation to all other goroutines via their shared `ctx`. The other goroutines' calls to `svc.Call(ctx, req)` will be cancelled when the underlying HTTP/gRPC transport detects the context cancellation. The function returns the first error without waiting for the other calls to complete.

This pattern is essential for preventing wasted work: if one downstream call fails, there's no point waiting for the others to complete and no point using their results. The cancellation signal stops them as quickly as the transport layer allows.

**Q14. What is the "stop-signal channel" pattern for graceful shutdown, and how does it relate to context cancellation?**
A: Graceful shutdown requires signaling long-running workers to finish in-flight work and stop accepting new work. The stop-signal channel pattern uses a context derived from a signal handler:

```go
func main() {
    // Create a context cancelled on OS signals
    ctx, stop := signal.NotifyContext(context.Background(),
        os.Interrupt, syscall.SIGTERM)
    defer stop()

    server := grpc.NewServer()
    // ...

    go func() {
        <-ctx.Done()  // blocks until SIGTERM or Ctrl-C
        log.Println("shutdown signal received")

        // Give in-flight requests time to complete
        shutdownCtx, cancel := context.WithTimeout(
            context.Background(), 30*time.Second)
        defer cancel()

        server.GracefulStop()  // stops accepting new connections,
                               // waits for in-flight handlers to finish
    }()

    server.Serve(listener)
}
```

The OS signal cancels the `ctx`, triggering the shutdown goroutine. `GracefulStop()` is the gRPC equivalent of HTTP's `Shutdown()` — it closes the listener (no new connections), waits for in-flight handlers to complete, and then fully stops. The 30-second timeout ensures the process doesn't hang indefinitely if a handler is stuck. Each in-flight request's context is not cancelled by graceful stop — they are allowed to complete or reach their own deadlines naturally.

## Section 5: Server-Side Deadline and Cancellation Handling

**Q15. What does "respecting cancellation" mean in a server handler, and what are the key checkpoints?**
A: Respecting cancellation means checking `ctx.Done()` or `ctx.Err()` at every meaningful yield point and aborting computation if the context is done. A handler that ignores cancellation continues doing expensive work (DB queries, network calls, CPU-intensive processing) that will produce a result no client will receive. The checkpoints:

**Before any expensive operation**:
```go
if err := ctx.Err(); err != nil {
    return nil, status.FromContextError(err).Err()
}
result, err := expensiveOperation(ctx)
```

**In loops** (the most critical — without a check, a loop may run for much longer than the deadline):
```go
for _, item := range items {
    select {
    case <-ctx.Done():
        return nil, status.FromContextError(ctx.Err()).Err()
    default:
    }
    processItem(ctx, item)
}
```

**In goroutines spawned by the handler**:
```go
go func() {
    select {
    case result := <-workDone:
        resultChan <- result
    case <-ctx.Done():
        return  // don't leak the goroutine
    }
}()
```

**Before writes** (particularly important for non-idempotent writes — if the client has given up, should you still commit?):
```go
if err := ctx.Err(); err != nil {
    // Rollback; client won't receive the result anyway
    tx.Rollback()
    return nil, status.FromContextError(err).Err()
}
tx.Commit()
```

**Q16. How do database drivers handle context cancellation, and what happens when a query is cancelled mid-execution?**
A: Most modern database drivers are context-aware: they cancel the in-flight query when the context is cancelled. In Go's `database/sql`:

```go
// Context-aware query — cancelled automatically if ctx is done
rows, err := db.QueryContext(ctx, "SELECT * FROM orders WHERE customer_id = $1", customerID)
// If ctx is cancelled while the query is executing:
// - The driver sends a cancellation signal to the database
// - PostgreSQL: sends a cancel request packet to the backend
// - MySQL: closes the connection (less graceful than Postgres)
// - The QueryContext call returns with ctx.Err()
```

**PostgreSQL** supports in-flight query cancellation via a dedicated cancel request: the driver opens a secondary connection to the database and sends a cancel request referencing the backend PID of the executing query. PostgreSQL receives this and terminates the query, returning an error to the client. Efficient and clean — the query is truly stopped.

**MySQL** typically handles cancellation by closing the connection, which signals the server to stop processing that connection's current query. Less efficient (connection pool overhead) but functional.

**SQLite**: context cancellation is checked between SQL statements, not within a single long-running statement — a `SELECT` that runs for 10 seconds will not be interrupted mid-execution by context cancellation.

The critical point: even if the database cancels the query, resources it held (locks, table scans, temporary files) are released by the database's normal cleanup process. The application still needs to check the returned error and handle the cancellation — but it does not need to worry about the database being left in a bad state.

**Q17. How should a server handler clean up resources when its context is cancelled?**
A: Resource cleanup on cancellation requires distinguishing between resources that clean up automatically and those requiring explicit action:

**Automatic cleanup** (use `defer` for all):
```go
func (s *Service) ProcessOrder(ctx context.Context, req *pb.OrderRequest) (*pb.Order, error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return nil, err
    }
    defer tx.Rollback()  // no-op if already committed; rolls back on cancellation

    lock, err := s.lockManager.Acquire(ctx, req.OrderId)
    if err != nil {
        return nil, err
    }
    defer lock.Release()  // released whether we succeed, error, or are cancelled
    // ...
}
```

**Resources that need context-aware decisions**: a write to an external system (sending an email, charging a card) is non-idempotent. If the context is cancelled after the charge but before the response is sent, the client never sees the success. Options: (1) check `ctx.Err()` before non-idempotent side effects and skip them if already cancelled; (2) use an idempotency key pattern so the client can retry safely; (3) use a transactional outbox pattern so side effects commit atomically with the database transaction.

**Goroutine cleanup** — the most critical for avoiding goroutine leaks:
```go
func (s *Service) StreamData(ctx context.Context, req *pb.Request) (*pb.Response, error) {
    // Goroutine that may outlive the function call if ctx isn't checked
    errChan := make(chan error, 1)
    go func() {
        select {
        case errChan <- doWork(ctx):
        case <-ctx.Done():
            // Context was cancelled — goroutine exits cleanly
        }
    }()

    select {
    case err := <-errChan:
        return buildResponse(), err
    case <-ctx.Done():
        return nil, status.FromContextError(ctx.Err()).Err()
    }
}
```

## Section 6: HTTP and Non-gRPC Contexts

**Q18. How does Go's `net/http` package expose cancellation to HTTP handlers?**
A: Since Go 1.7, every `*http.Request` carries a context accessible via `r.Context()`. This context is cancelled when:
- The client closes the connection (navigates away, kills the process, network drops).
- The `ResponseWriter` is hijacked and the hijacked connection is closed.
- The server's `Shutdown()` or `Close()` is called.
- The HTTP handler returns (the context is cancelled after the handler returns).

Server handlers should pass `r.Context()` to all downstream operations:
```go
func orderHandler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()  // carries client's connection lifecycle

    // DB query is cancelled if client disconnects
    order, err := db.QueryContext(ctx, "SELECT * FROM orders WHERE id = $1", orderID)
    if err != nil {
        if ctx.Err() != nil {
            // Client disconnected — no point writing a response
            return
        }
        http.Error(w, "database error", http.StatusInternalServerError)
        return
    }
    // ...
}
```

HTTP/1.1 does not natively propagate timeouts from the client to the server (unlike gRPC's `grpc-timeout` header). The server's context is cancelled only when the TCP connection closes — it does not know the client's internal timeout. For REST APIs where propagating deadlines matters, the convention is a custom header (e.g., `X-Request-Timeout: 500ms`) that the server reads and uses to create a bounded sub-context: `context.WithTimeout(r.Context(), parsedTimeout)`.

**Q19. How does cancellation work in message queue consumers (e.g., Kafka)?**
A: Message queue consumers run in infinite loops reading messages and processing them. Cancellation/shutdown must be handled at the loop level:

```go
func consumeOrders(ctx context.Context, consumer *kafka.Consumer) error {
    for {
        // Poll returns when a message is available or the context is done
        msg, err := consumer.ReadMessage(ctx)
        if err != nil {
            if ctx.Err() != nil {
                // Context cancelled — graceful shutdown
                return nil
            }
            return fmt.Errorf("consumer error: %w", err)
        }

        // Process with a per-message deadline
        msgCtx, cancel := context.WithTimeout(ctx, 30*time.Second)
        err = processOrder(msgCtx, msg)
        cancel()

        if err != nil {
            if ctx.Err() != nil {
                return nil  // Shutdown, not a processing error
            }
            // Processing error — handle: dead-letter, retry, log
        }
    }
}
```

Key patterns: (1) the outer loop runs with the service-level context (cancelled on SIGTERM); (2) each message gets its own per-message deadline sub-context — a single stuck message doesn't block all subsequent messages indefinitely; (3) distinguish between "context cancelled because of shutdown" and "context cancelled because of per-message timeout" — only the former should trigger a clean shutdown, the latter should trigger per-message error handling.

## Section 7: Failure Modes & Anti-patterns

**Q20. What is "context not propagated" anti-pattern and what are its symptoms?**
A: The context-not-propagated anti-pattern is when a server receives a context (with a deadline and cancellation signal) but creates a new unrelated context for downstream calls instead of deriving from the received context:

```go
// Anti-pattern: severs the deadline chain
func (s *Service) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error) {
    // Creates a brand new context — ignores the incoming deadline!
    freshCtx := context.Background()
    freshCtx, cancel := context.WithTimeout(freshCtx, 10*time.Second)
    defer cancel()

    return s.userDB.Get(freshCtx, req.UserId)
}
```

Symptoms: (1) downstream calls continue executing after the client's deadline has fired — the client receives `DEADLINE_EXCEEDED` but the server is still running queries, holding locks, and consuming resources; (2) the 10-second local timeout fires even when the incoming deadline would have allowed stopping sooner; (3) monitoring shows gRPC handler completion time exceeding the client-configured deadline (the handler is doing orphaned work); (4) database lock contention increases because queries are held longer than clients are waiting.

Fix: always derive sub-contexts from the incoming context using `context.WithTimeout(ctx, ...)`, `context.WithDeadline(ctx, ...)`, or `context.WithCancel(ctx)` — where `ctx` is the incoming request context, not `context.Background()`.

**Q21. What is the "goroutine leak on cancellation" pattern and why is it dangerous at scale?**
A: A goroutine leak on cancellation happens when goroutines are spawned in a handler but are not linked to the request context — they continue running after the request ends, the context is cancelled, or the handler returns:

```go
// Leak: goroutine outlives the request
func (s *Service) ProcessOrder(ctx context.Context, req *pb.OrderRequest) (*pb.Order, error) {
    go func() {
        // This goroutine is NOT connected to ctx
        // It runs until sendNotification completes, regardless of cancellation
        sendNotification(req.UserId, "order processing")
    }()
    return s.processOrder(ctx, req)
}
```

If `ProcessOrder` is called 1000 times/second and `sendNotification` takes 5 seconds, there are 5000 concurrent leaked goroutines at steady state — each consuming 4–8KB of stack memory. Under load spikes, this grows unboundedly, eventually causing OOM crashes. Leaked goroutines also hold references to variables, preventing garbage collection of request data.

Fix: link goroutines to the request context:
```go
go func() {
    select {
    case <-time.After(5 * time.Second):
        sendNotification(req.UserId, "order processing")
    case <-ctx.Done():
        // Request was cancelled — skip notification or use a background context
        // If notification must always send: use a new background context with its own timeout
        bgCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
        defer cancel()
        sendNotification(req.UserId, "order processing")
    }
}()
```

**Q22. What is the "cancellation ignored by blocking call" anti-pattern?**
A: Calling a blocking function that doesn't accept a context — or that accepts one but doesn't honor it — inside a request handler causes the handler to block regardless of cancellation:

```go
// Anti-pattern: time.Sleep doesn't respect context
func (s *Service) RateLimitedCall(ctx context.Context, req *pb.Request) (*pb.Response, error) {
    time.Sleep(s.rateLimiter.WaitTime())  // BLOCKS — ignores ctx
    return s.backend.Call(ctx, req)
}

// Fix: use context-aware waiting
func (s *Service) RateLimitedCall(ctx context.Context, req *pb.Request) (*pb.Response, error) {
    select {
    case <-time.After(s.rateLimiter.WaitTime()):
        // Waited successfully
    case <-ctx.Done():
        return nil, status.FromContextError(ctx.Err()).Err()
    }
    return s.backend.Call(ctx, req)
}
```

Other common blocking calls that ignore context: `sync.Mutex.Lock()` (use `sync.Mutex` with a `select` + `ctx.Done()` to implement trylock), `channel sends and receives` without `select`, and third-party library calls that don't accept `context.Context`. When integrating with blocking third-party libraries, wrap them in goroutines with context-aware waiting:

```go
result := make(chan Result, 1)
go func() { result <- thirdParty.BlockingCall() }()

select {
case r := <-result:
    return r, nil
case <-ctx.Done():
    return nil, ctx.Err()
    // Note: the goroutine is leaked if thirdParty.BlockingCall() doesn't return
    // True fix requires the third-party library to be context-aware
}
```

**Q23. What is the "deadline too tight" vs "deadline too loose" failure mode, and how do you tune it?**
A: Both extremes cause problems:

**Too tight** (deadline shorter than p99 legitimate processing time): a significant fraction of legitimate requests fail with `DEADLINE_EXCEEDED` even when the server is healthy. Symptoms: `DEADLINE_EXCEEDED` error rates are elevated but the server shows normal latency histograms (because only the slow tail is being cut off). Clients may retry, amplifying load. The system performs worse under load than without deadlines.

**Too loose** (deadline much longer than expected processing time): the deadline provides no protection. When a downstream service degrades (latency increases to 10s instead of 100ms), threads/goroutines are held for the full deadline duration before releasing. Resources exhaust; the degradation cascades. Slow callers that have already given up are still being processed. The system is no more resilient than having no deadlines.

**Tuning approach**: (1) measure p50, p95, p99, p999 of the operation's latency under normal load; (2) set the deadline between p99 and p999 — accept normal tail latency, cut off truly anomalous requests; (3) for end-to-end deadlines, account for all hops in the chain (each hop consumes some budget); (4) implement latency-budget monitoring — alert when remaining budget at a given service consistently falls below a minimum threshold (the budget is being consumed too fast). Adjust per-service timeouts proportionally as the call chain deepens.

## Section 8: Trade-offs & Decision-Making

**Q24. When should you cancel work that has already started vs. let it complete?**
A: The decision depends on side effects and idempotency:

**Cancel and discard** when:
- The work is read-only and the result will be unused (a query for a user's feed when the user navigated away). Cancellation saves DB resources; the result serves no one.
- The work has not yet produced side effects. If no non-idempotent actions have been taken, cancellation is free.
- The work is at a checkpoint where rollback is cheap (before a database `COMMIT`).

**Allow to complete** when:
- The work has already produced non-idempotent side effects that must be consistent (a payment has been charged; the order record must be created to reflect it even if the client is gone).
- The remaining work is short (milliseconds remaining vs. seconds of cleanup cost).
- Cancellation would leave a resource in a partially-modified state that is harder to clean up than simply completing.

**The hybrid pattern** — complete critical atomic operations even after cancellation:
```go
func processPayment(ctx context.Context, req *pb.PaymentRequest) (*pb.Payment, error) {
    // Use incoming ctx for preparation
    validated, err := validatePayment(ctx, req)
    if err != nil {
        return nil, err
    }

    // For the atomic commit: use a new background context
    // This commit must complete regardless of client cancellation
    commitCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    return s.paymentDB.Commit(commitCtx, validated)
}
```

The rule: use the incoming request context for reversible/read operations; switch to a background context with its own bounded timeout for irreversible atomic commits.

**Q25. How do you handle cancellation correctly in a two-phase operation (acquire, then use)?**
A: Two-phase operations (acquire a lock or reservation, then perform a transaction) have a dangerous cancellation window between the two phases:

```go
func reserveAndBook(ctx context.Context, seatID string) error {
    // Phase 1: acquire reservation
    reservation, err := s.inventory.Reserve(ctx, seatID)
    if err != nil {
        return err
    }

    // --- CANCELLATION WINDOW ---
    // If ctx is cancelled here, we've reserved a seat but haven't booked it
    // The reservation will expire by TTL (hopefully), but there's a leak window

    // Phase 2: complete booking
    if err := ctx.Err(); err != nil {
        // Release the reservation explicitly before returning
        releaseCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        defer cancel()
        s.inventory.Release(releaseCtx, reservation.ID)
        return err
    }

    return s.booking.Confirm(ctx, reservation)
}
```

Between the two phases, the context may have been cancelled. If you return the cancellation error without releasing the reservation, the seat is reserved but not booked — a resource leak until the reservation's TTL expires. The fix: explicitly check `ctx.Err()` after phase 1 and clean up before returning if cancelled. Use a **separate background context for the cleanup** — the cleanup must complete even though the request context is done.

**Q26. What is deadline inheritance and when should you create an independent deadline instead?**
A: **Deadline inheritance** (the default — derive sub-contexts from the incoming context) is correct for operations that are part of the same logical request and should respect the original caller's time budget. If the caller has 500ms left, the downstream call should also have at most 500ms.

**Independent deadline** (creating from `context.Background()`) is appropriate when:
- The operation must complete regardless of the original caller's state — audit logs, billing records, critical compensating transactions.
- The operation has a different SLA from the request — a background cache warm-up triggered by a request should not inherit the request's tight deadline.
- The operation spans multiple original requests — a batch job that aggregates results from many requests should have its own lifecycle.
- You're implementing "fire and forget" — the original request context will be cancelled when the handler returns, but the spawned work should continue.

```go
// Audit logging must complete regardless of request outcome
func logAudit(requestCtx context.Context, event AuditEvent) {
    // Independent context: not tied to the request lifecycle
    auditCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    s.auditLogger.Log(auditCtx, event)
}
```

The key question: "If the caller cancels, should this work also be cancelled?" If yes — inherit. If no — use an independent context with its own bounded timeout.

## Section 9: Scenario / System Design Style Questions

**Q27. "Trace a request from a web browser through three gRPC service hops, showing exactly how the deadline is propagated and where it might be violated."**
A: End-to-end deadline trace:

```
Browser → API Gateway (HTTP, 2000ms timeout)
         → UserService (gRPC, grpc-timeout: 1800m)
         → ProfileService (gRPC, grpc-timeout: 1400m)
         → Database (SQL, QueryContext with 1200ms remaining)
```

**Step 1 — API Gateway receives HTTP request** (T=0ms):
- Creates: `context.WithTimeout(context.Background(), 2000*ms)`
- Deadline: T+2000ms

**Step 2 — Gateway calls UserService** (T=50ms):
- Computes remaining: 2000 - 50 = 1950ms
- Subtracts buffer for local processing: uses 1800ms for downstream
- Sends: `grpc-timeout: 1800m` in the gRPC request header
- UserService framework creates: deadline = T_userservice_now + 1800ms

**Step 3 — UserService calls ProfileService** (T=100ms from gateway start, T=50ms from UserService start):
- Remaining on UserService's context: ~1750ms
- Subtracts UserService processing buffer: uses 1400ms
- Sends: `grpc-timeout: 1400m`
- ProfileService creates: deadline = T_profileservice_now + 1400ms

**Step 4 — ProfileService queries database** (T=150ms from start):
- Remaining on ProfileService's context: ~1350ms
- `db.QueryContext(ctx, ...)` — context carries the deadline
- Database executes query; driver cancels if context fires

**Where violations occur**:
1. ProfileService forgets to use `ctx` in the DB call: `db.Query(...)` instead of `db.QueryContext(ctx, ...)` — the query runs past the deadline.
2. UserService derives from `context.Background()` instead of the incoming `ctx` — gateway's deadline doesn't propagate.
3. ProfileService's query takes 1500ms — ProfileService's context fires (1400ms budget), ProfileService returns `DEADLINE_EXCEEDED`, UserService receives it and propagates up. Browser sees a 504 response after ~1550ms — within the 2000ms gateway deadline.

**Q28. "A production gRPC service is seeing high rates of `DEADLINE_EXCEEDED` errors. Clients have a 1-second deadline. Server-side p99 latency is 800ms. Walk through your investigation."**
A: p99 at 800ms with a 1s deadline means 1% of requests time out — and that 1% represents 10ms of headroom. Under load, this headroom may vanish. Investigation:

**Step 1 — Separate client vs server perspective**:
- Check server-side handler latency histogram: is p99 actually 800ms or is that the client-measured latency?
- Network round-trip time (RTT) between client and server: 50ms RTT means the server has effectively 950ms, not 1000ms. Check with `ping` or distributed tracing.

**Step 2 — Check deadline propagation**:
- Is the 1-second deadline the client's configured timeout, or is it already a degraded deadline from an upstream service? Trace the full call chain.
- Is the server receiving the `grpc-timeout` correctly? Add logging of `ctx.Deadline()` at the start of handlers.

**Step 3 — Analyze the p99 latency spike**:
- Is the 800ms p99 stable or is there a bimodal distribution (most requests at 50ms, occasional spikes to 800ms+)?
- Bimodal suggests: GC pauses (JVM or Go GC stop-the-world), database lock contention causing occasional slow queries, connection pool exhaustion causing queuing, or cold cache paths.

**Step 4 — Reduce or eliminate the margin**:
- If the 800ms is genuine: increase the client deadline to 2s (if latency SLA allows) or optimize the server to reduce p99.
- If the 800ms is a spike: investigate root cause (GC tuning, DB index missing for slow query path, connection pool sizing).

**Step 5 — Add minimum budget guard on the server**:
```go
if deadline, ok := ctx.Deadline(); ok {
    if time.Until(deadline) < 100*time.Millisecond {
        return nil, status.Error(codes.DeadlineExceeded, "deadline too close")
    }
}
```
This fast-fails requests where the budget is already nearly exhausted on arrival, preventing partial processing that will definitely fail.

**Q29. "Design cancellation handling for a service that fans out to 10 downstream services and must return a partial result if some succeed and some fail or are cancelled."**
A:
```go
type FanoutResult struct {
    ServiceName string
    Data        *pb.Data
    Err         error
}

func fanoutWithPartialResults(ctx context.Context, services []ServiceClient,
    req *pb.Request) ([]FanoutResult, error) {

    // Don't cancel siblings on one failure — collect all results
    results := make(chan FanoutResult, len(services))

    for _, svc := range services {
        svc := svc
        go func() {
            // Each service gets its own sub-context for per-service deadline
            svcCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
            defer cancel()

            data, err := svc.Fetch(svcCtx, req)
            results <- FanoutResult{
                ServiceName: svc.Name(),
                Data:        data,
                Err:         err,
            }
        }()
    }

    // Collect all results with the parent deadline as the outer bound
    collected := make([]FanoutResult, 0, len(services))
    for i := 0; i < len(services); i++ {
        select {
        case r := <-results:
            collected = append(collected, r)
        case <-ctx.Done():
            // Parent deadline/cancellation: return what we have so far
            return collected, ctx.Err()
        }
    }

    // Classify results
    var failures []string
    for _, r := range collected {
        if r.Err != nil {
            failures = append(failures, fmt.Sprintf("%s: %v", r.ServiceName, r.Err))
        }
    }

    if len(failures) == len(services) {
        return nil, status.Error(codes.Internal, "all services failed")
    }

    // Return partial success with error context in response metadata
    return collected, nil
}
```

Key design decisions: (1) **per-service sub-context** with its own timeout — one slow service doesn't consume the entire parent budget; (2) **don't cancel siblings on failure** — collect all results for a partial response; (3) **parent context is the outer bound** — if the parent deadline fires, return whatever has been collected; (4) **return both results and an error** for partial success, allowing the caller to decide whether partial data is acceptable; (5) surface per-service errors in the results rather than discarding them — callers can log which services failed.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Deadline | Timeout | Cancellation |
|--- |--- |--- |--- |
| Type | Absolute time (`time.Time`) | Relative duration (`time.Duration`) | Explicit signal (event-driven) |
| Scope | End-to-end across all hops | Per-hop (restarts at each service) | Can be scoped to one request or propagated |
| Propagation | Passes across network boundaries as remaining budget | Does not propagate — each hop sets its own | Propagates downstream via context tree |
| Trigger | Clock reaches the deadline | Duration elapses | `cancel()` called, client disconnects, parent cancelled |
| `ctx.Err()` value | `context.DeadlineExceeded` | `context.DeadlineExceeded` | `context.Canceled` |
| gRPC code | `DEADLINE_EXCEEDED` | `DEADLINE_EXCEEDED` | `CANCELLED` |
| gRPC wire | `grpc-timeout` header (remaining duration) | `grpc-timeout` header (local timeout) | `RST_STREAM` HTTP/2 frame |
| Retryable? | If idempotent | If idempotent | No (client-initiated) |
| Best for | Multi-hop request chains with end-to-end SLA | Single-hop calls where chain depth is known | User-initiated stop, hedged requests, graceful shutdown |

| `context` function | What it creates | When to use |
|--- |--- |--- |
| `context.Background()` | Non-cancellable root | Entry points only (main, test setup, background jobs) |
| `context.TODO()` | Non-cancellable placeholder | Work in progress; must be replaced before production |
| `context.WithCancel(parent)` | Cancellable context | Fan-out operations, explicit cancellation control |
| `context.WithTimeout(parent, d)` | Deadline = now + d | Per-hop timeout when remaining budget is known |
| `context.WithDeadline(parent, t)` | Deadline = absolute t | When propagating an inherited absolute deadline |
| `context.WithValue(parent, k, v)` | Value-carrying context | Request ID, auth token, trace ID — no effect on cancellation |

## Key Concepts Cheat Sheet

| Term | One-line definition |
|--- |--- |
| Deadline | Absolute point in time by which an operation must complete; propagated across hops as remaining budget |
| Timeout | Relative duration; restarts fresh at each hop; does not propagate the end-to-end budget |
| Cancellation | Explicit signal to abandon work; propagates downward through context tree immediately |
| Context tree | Immutable parent-child hierarchy of contexts; child inherits parent deadline (can only be tighter) |
| `ctx.Done()` | Channel closed when context is cancelled or deadline fires; the universal select signal |
| `ctx.Err()` | Returns `context.DeadlineExceeded` or `context.Canceled` after context is done |
| `context.Cause(ctx)` | Go 1.20+: returns first cancellation cause, distinguishing deadline from explicit cancel |
| `defer cancel()` | Mandatory after every `WithCancel`/`WithTimeout`/`WithDeadline` call; prevents context leak |
| Context leak | Forgetting `cancel()` — internal goroutines and timers accumulate until parent is cancelled |
| Goroutine leak | Spawned goroutine not linked to context — continues running after request ends |
| `grpc-timeout` header | HTTP/2 header carrying remaining deadline budget as a duration string |
| Orphaned work | Work continuing on the server after the client has abandoned the request |
| Budget slicing | Creating sub-contexts with a fraction of the remaining deadline for each downstream call |
| First-response-wins | Fan-out to multiple backends; cancel all remaining when the first succeeds |
| Fail-fast fan-out | Cancel all siblings when any one fails |
| `signal.NotifyContext` | Go stdlib: context cancelled on OS signal (SIGTERM, SIGINT); used for graceful shutdown |
| `db.QueryContext(ctx, ...)` | Context-aware DB query; cancelled by the database driver when context fires |
| Background context for commit | Using `context.Background()` for irreversible atomic writes that must complete regardless of request cancellation |
| `GracefulStop()` | gRPC server shutdown: stops accepting new connections, waits for in-flight handlers to complete |

**Tip for the interview:** Deadlines and cancellation questions separate candidates who've read the documentation from those who've debugged production cascading failures. The signals interviewers look for: (1) immediately distinguishing deadline (absolute, propagated) from timeout (relative, per-hop) — and naming the "sum of all hop timeouts" failure that motivates deadlines; (2) knowing that `defer cancel()` is mandatory and what happens without it (context leak → goroutine/timer accumulation); (3) naming the "severing the deadline chain" anti-pattern (`context.Background()` inside a handler) and what it causes (orphaned work after client times out); (4) knowing which `ctx.Err()` value corresponds to which scenario (`DeadlineExceeded` vs `Canceled`) and the corresponding gRPC status codes; (5) the irreversible-write pattern — using a background context for atomic commits that must complete even if the request context is cancelled. Bonus: describing the goroutine fan-out with shared context, first-response-wins cancellation, and the database query cancellation mechanism (PostgreSQL's cancel request packet) shows hands-on production experience.
