# gRPC with Node.js (`@grpc/grpc-js`, `@grpc/proto-loader`) — Interview Q&A (5 YOE Level)

---

## Section 1: Setup and Fundamentals

**Q1. What are `@grpc/grpc-js` and `@grpc/proto-loader` and how do they relate?**
A: They are the two packages required for gRPC in modern Node.js and form a clear division of responsibility:

**`@grpc/proto-loader`** handles the `.proto` file — it dynamically loads and parses `.proto` files at runtime, converting them into JavaScript objects that describe service definitions, message types, and RPC method signatures. It does not make network calls; it only processes the schema.

**`@grpc/grpc-js`** is the core gRPC implementation — it handles the HTTP/2 transport, channel management, connection pooling, serialization/deserialization of Protobuf messages, interceptors, credentials, and the client/server lifecycle. It depends on `@grpc/proto-loader` to understand the schema of messages it will send and receive.

The older `grpc` package (native C extension) was deprecated. `@grpc/grpc-js` is a pure JavaScript reimplementation — no native binaries, no `node-gyp`, runs anywhere Node.js runs.

```
.proto file
    ↓ proto-loader.loadSync() or load()
JavaScript package definition object
    ↓ grpc-js.loadPackageDefinition()
gRPC service stubs + message constructors
    ↓
Client (stub) or Server (implementations)
```

**Q2. What is the difference between dynamic loading and static code generation?**
A: Two approaches to consuming `.proto` files in Node.js — with different trade-offs:

**Dynamic loading (proto-loader at runtime):**
```javascript
const protoLoader = require('@grpc/proto-loader');
const grpc = require('@grpc/grpc-js');

const packageDef = protoLoader.loadSync('./order.proto', {
  keepCase: true,
  longs: String,
  enums: String,
  defaults: true,
  oneofs: true
});
const proto = grpc.loadPackageDefinition(packageDef);
const OrderService = proto.order.OrderService;
```
The `.proto` is parsed at startup. No build step. Types are not available at compile time — `request.order_id` is untyped JavaScript. Changes to the `.proto` are picked up on next restart. Simple workflow for development and small projects.

**Static code generation (`protoc` + `ts-protoc-gen` or `protoc-gen-js`):**
```bash
# Generate TypeScript stubs from .proto
npx protoc \
  --plugin=protoc-gen-ts=./node_modules/.bin/protoc-gen-ts \
  --ts_out=./src/generated \
  --js_out=import_style=commonjs:./src/generated \
  --grpc_out=./src/generated \
  --plugin=protoc-gen-grpc=./node_modules/.bin/grpc_tools_node_protoc_plugin \
  order.proto
```
Generated TypeScript types provide compile-time validation, IDE autocompletion, and refactoring safety. Changes to `.proto` require regenerating stubs and will surface as type errors. Better for larger teams and production systems.

**Recommendation:** Dynamic loading for scripts, tools, and proof-of-concept. Static generation for production TypeScript services where type safety is a first-class concern.

**Q3. What are the key `proto-loader` options and what do they control?**
A: The `loadSync` / `load` options configure how the `.proto` is mapped to JavaScript:

```javascript
const packageDef = protoLoader.loadSync('./order.proto', {
  keepCase: true,     // preserve snake_case field names from .proto
                      // false → camelCase conversion (e.g., order_id → orderId)
                      // true → keep as order_id (matches proto field names exactly)

  longs: String,      // how to represent int64/uint64 fields
                      // String → JavaScript string (avoids precision loss)
                      // Number → JavaScript number (loses precision > 2^53)
                      // Long → long.js Long object (full precision)

  enums: String,      // represent enum values as string names ("PENDING")
                      // vs Number (0, 1, 2...)

  defaults: true,     // include default values for unset fields
                      // false → unset fields are undefined

  oneofs: true,       // represent oneof fields as a virtual field
                      // containing the name of the set field

  includeDirs: [      // search paths for imports within the .proto
    './proto',
    './node_modules/google-proto-files'
  ]
});
```

**`keepCase` is the most impactful option:** In protobuf convention, field names are `snake_case`. With `keepCase: false` (default), proto-loader converts them to `camelCase`. This causes a mismatch if your server writes `{ order_id: '123' }` but the client receives `{ orderId: '123' }`. Using `keepCase: true` ensures field names in JavaScript match the `.proto` exactly. Consistent `keepCase` setting across all services in the same system is critical.

## Section 2: Server Implementation

**Q4. How do you create a gRPC server in Node.js?**
A: A complete unary gRPC server implementation:

```javascript
// order.proto
// syntax = "proto3";
// package order;
// service OrderService {
//   rpc GetOrder(OrderRequest) returns (OrderResponse);
// }

const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');
const path = require('path');

// Step 1: Load the proto definition
const packageDef = protoLoader.loadSync(
  path.join(__dirname, 'protos/order.proto'),
  { keepCase: true, longs: String, enums: String, defaults: true, oneofs: true }
);
const proto = grpc.loadPackageDefinition(packageDef);

// Step 2: Implement the service methods
const orderServiceImpl = {
  getOrder: async (call, callback) => {
    const { order_id } = call.request;

    try {
      const order = await db.findOrder(order_id);
      if (!order) {
        return callback({
          code: grpc.status.NOT_FOUND,
          message: `Order ${order_id} not found`
        });
      }
      callback(null, {
        order_id: order.id,
        status: order.status,
        total_cents: order.totalCents,
        customer_id: order.customerId
      });
    } catch (err) {
      callback({
        code: grpc.status.INTERNAL,
        message: `Internal error: ${err.message}`
      });
    }
  }
};

// Step 3: Create and start the server
const server = new grpc.Server();
server.addService(proto.order.OrderService.service, orderServiceImpl);

server.bindAsync(
  '0.0.0.0:50051',
  grpc.ServerCredentials.createInsecure(),   // use createSsl() in production
  (error, port) => {
    if (error) throw error;
    console.log(`gRPC server running on port ${port}`);
    server.start();
  }
);
```

**Key points:**
- `server.addService(ServiceDefinition, implementation)` — the first argument is `proto.package.ServiceName.service` (the `.service` suffix extracts the descriptor); the second is a plain object mapping method names to handler functions.
- Handler function signature for unary: `(call, callback)` — `call` contains `call.request` (the incoming message) and metadata; `callback(error, response)` sends the response.
- `callback(null, response)` — success. `callback({ code, message })` — error.
- Method names in the implementation object follow `keepCase` — if the proto defines `GetOrder`, the implementation key is `getOrder` (camelCase regardless of `keepCase`).

**Q5. How do you implement server-side streaming in Node.js?**
A: Server streaming uses `call.write()` to send multiple messages and `call.end()` to close the stream:

```javascript
// .proto: rpc ListOrders(OrderStreamRequest) returns (stream OrderResponse);

const orderServiceImpl = {
  listOrders: async (call) => {
    const { customer_id, status_filter } = call.request;

    // call is a writable stream (ServerWritableStream)
    // No callback — server controls when to end the stream

    try {
      const cursor = await db.streamOrders(customer_id, status_filter);

      cursor.on('data', (order) => {
        // Check if client cancelled before writing
        if (call.cancelled) {
          cursor.destroy();
          return;
        }
        call.write({
          order_id: order.id,
          status: order.status,
          total_cents: order.totalCents
        });
      });

      cursor.on('end', () => {
        call.end();   // Signal: no more messages, close stream
      });

      cursor.on('error', (err) => {
        call.destroy(err);   // Close stream with error
      });

      // Handle client cancellation
      call.on('cancelled', () => {
        cursor.destroy();
      });

    } catch (err) {
      call.destroy({
        code: grpc.status.INTERNAL,
        message: err.message
      });
    }
  }
};
```

**async/await with for-await (cleaner pattern):**
```javascript
listOrders: async (call) => {
  const { customer_id } = call.request;

  try {
    for await (const order of db.streamOrders(customer_id)) {
      if (call.cancelled) break;
      call.write({ order_id: order.id, status: order.status });
    }
    call.end();
  } catch (err) {
    call.destroy({ code: grpc.status.INTERNAL, message: err.message });
  }
}
```

**Q6. How do you implement client streaming on the server side?**
A: Client streaming: the server reads from a readable stream `call` and sends one response via `callback`:

```javascript
// .proto: rpc CreateOrderBatch(stream OrderRequest) returns (BatchResponse);

const orderServiceImpl = {
  createOrderBatch: (call, callback) => {
    const orders = [];
    let totalCents = 0;

    // call is a readable stream (ServerReadableStream)
    call.on('data', (orderRequest) => {
      orders.push(orderRequest);
      totalCents += orderRequest.total_cents;
    });

    call.on('end', async () => {
      // Client finished sending — process all received orders
      try {
        const batchId = await db.createOrderBatch(orders);
        callback(null, {
          batch_id: batchId,
          order_count: orders.length,
          total_cents: totalCents
        });
      } catch (err) {
        callback({
          code: grpc.status.INTERNAL,
          message: `Batch creation failed: ${err.message}`
        });
      }
    });

    call.on('error', (err) => {
      // Stream error from client side
      console.error('Client stream error:', err);
    });
  }
};
```

**Q7. How do you implement bidirectional streaming on the server side?**
A: Bidirectional streaming: `call` is both readable and writable. The server reads incoming messages and writes responses independently:

```javascript
// .proto: rpc TrackOrders(stream OrderRequest) returns (stream OrderUpdate);

const orderServiceImpl = {
  trackOrders: (call) => {
    // call is a Duplex stream (ServerDuplexStream)
    // Both readable (client messages) and writable (server messages)

    const subscriptions = new Set();

    // Handle incoming subscription requests from client
    call.on('data', async (request) => {
      const { order_id } = request;
      subscriptions.add(order_id);

      // Subscribe to order status changes
      orderEventEmitter.on(`order:${order_id}`, (update) => {
        if (call.writable && !call.cancelled) {
          call.write({
            order_id: update.orderId,
            old_status: update.oldStatus,
            new_status: update.newStatus,
            updated_at: update.updatedAt
          });
        }
      });
    });

    // Client closed their send stream
    call.on('end', () => {
      // Server can keep sending until it decides to close
      // Or close immediately:
      call.end();
    });

    // Client disconnected or cancelled
    call.on('cancelled', () => {
      // Clean up subscriptions to prevent memory leaks
      subscriptions.forEach(orderId => {
        orderEventEmitter.removeAllListeners(`order:${orderId}`);
      });
    });

    call.on('error', (err) => {
      subscriptions.forEach(orderId => {
        orderEventEmitter.removeAllListeners(`order:${orderId}`);
      });
    });

    // Heartbeat to keep the stream alive
    const heartbeatInterval = setInterval(() => {
      if (!call.writable || call.cancelled) {
        clearInterval(heartbeatInterval);
        return;
      }
      call.write({ order_id: '__heartbeat__', new_status: 'ALIVE' });
    }, 30000);

    call.on('finish', () => clearInterval(heartbeatInterval));
  }
};
```

## Section 3: Client Implementation

**Q8. How do you create a gRPC client (stub) in Node.js?**
A: A complete client implementation calling unary and streaming RPCs:

```javascript
const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');

const packageDef = protoLoader.loadSync('./protos/order.proto', {
  keepCase: true, longs: String, enums: String, defaults: true, oneofs: true
});
const proto = grpc.loadPackageDefinition(packageDef);

// Create client stub — connects to the server address
const client = new proto.order.OrderService(
  'order-service:50051',
  grpc.credentials.createInsecure()  // use createSsl() with TLS in production
);

// Unary call — promisified
function getOrder(orderId) {
  return new Promise((resolve, reject) => {
    client.getOrder({ order_id: orderId }, (error, response) => {
      if (error) reject(error);
      else resolve(response);
    });
  });
}

// Usage
async function main() {
  try {
    const order = await getOrder('ord-123');
    console.log(`Order status: ${order.status}`);
  } catch (err) {
    console.error(`gRPC error [${err.code}]: ${err.message}`);
  }
}
```

**Q9. How do you call a server-streaming RPC from the Node.js client?**
A: Server streaming returns a readable stream — the client listens for `data` events:

```javascript
// Server streaming — returns a readable stream
function listOrders(customerId, statusFilter) {
  return new Promise((resolve, reject) => {
    const orders = [];
    const stream = client.listOrders({
      customer_id: customerId,
      status_filter: statusFilter
    });

    stream.on('data', (order) => {
      orders.push(order);
    });

    stream.on('end', () => {
      resolve(orders);   // all messages received
    });

    stream.on('error', (err) => {
      reject(err);
    });
  });
}

// Or process messages as they arrive (don't buffer all):
function streamOrders(customerId, onOrder) {
  const stream = client.listOrders({ customer_id: customerId });

  stream.on('data', onOrder);
  stream.on('end', () => console.log('Stream complete'));
  stream.on('error', (err) => console.error('Stream error:', err));

  // Return the stream so caller can cancel if needed
  return stream;
}

// Cancel a stream mid-flight
const activeStream = streamOrders('cust-42', processOrder);
// Later:
activeStream.cancel();   // sends CANCELLED status to server
```

**async/await with async iteration (Node.js 10+):**
```javascript
async function listOrdersAsync(customerId) {
  const stream = client.listOrders({ customer_id: customerId });

  for await (const order of stream) {
    console.log(`Received: ${order.order_id}`);
    await processOrder(order);   // process each as it arrives
  }
  console.log('All orders received');
}
```

**Q10. How do you call a client-streaming RPC from the Node.js client?**
A: Client streaming — the client calls `write()` multiple times, then `end()`:

```javascript
// Client streaming
function createOrderBatch(orders) {
  return new Promise((resolve, reject) => {
    const stream = client.createOrderBatch((error, response) => {
      // Callback fires after server sends its single response
      if (error) reject(error);
      else resolve(response);
    });

    // Send each order as a separate message
    for (const order of orders) {
      stream.write({
        customer_id: order.customerId,
        total_cents: order.totalCents,
        items: order.items
      });
    }

    // Signal end of client stream — server will now process and respond
    stream.end();
  });
}

// Usage
const result = await createOrderBatch(ordersToCreate);
console.log(`Batch ${result.batch_id}: ${result.order_count} orders created`);
```

**Q11. How do you call a bidirectional streaming RPC from the Node.js client?**
A: Bidirectional streaming — the client has both write and read sides:

```javascript
function trackOrders(orderIds, onUpdate) {
  const stream = client.trackOrders();

  // Receive updates from server
  stream.on('data', (update) => {
    if (update.order_id !== '__heartbeat__') {
      onUpdate(update);
    }
  });

  stream.on('end', () => console.log('Tracking stream closed by server'));
  stream.on('error', (err) => console.error('Track stream error:', err));

  // Send initial subscriptions
  for (const orderId of orderIds) {
    stream.write({ order_id: orderId });
  }

  // Return controls for the caller
  return {
    subscribe: (orderId) => stream.write({ order_id: orderId }),
    unsubscribe: (orderId) => stream.write({ order_id: orderId, unsubscribe: true }),
    close: () => stream.end(),
    cancel: () => stream.cancel()
  };
}

// Usage
const tracker = trackOrders(
  ['ord-123', 'ord-456'],
  (update) => console.log(`Order ${update.order_id}: ${update.new_status}`)
);

// Later add another subscription
setTimeout(() => tracker.subscribe('ord-789'), 5000);

// Eventually close
setTimeout(() => tracker.close(), 60000);
```

## Section 4: Metadata, Credentials, and TLS

**Q12. How do you pass metadata (headers) with gRPC calls in Node.js?**
A: gRPC metadata is equivalent to HTTP headers — key-value pairs sent alongside the request. Used for authentication tokens, request IDs, tracing context:

**Client sending metadata:**
```javascript
// Create metadata object
const metadata = new grpc.Metadata();
metadata.set('authorization', `Bearer ${accessToken}`);
metadata.set('x-request-id', requestId);
metadata.set('x-correlation-id', correlationId);

// Unary: pass metadata as second argument
client.getOrder({ order_id: 'ord-123' }, metadata, (error, response) => {
  // ...
});

// Streaming: pass metadata when initiating the stream
const stream = client.listOrders({ customer_id: 'cust-42' }, metadata);
```

**Server reading metadata:**
```javascript
const orderServiceImpl = {
  getOrder: (call, callback) => {
    // Access incoming metadata
    const metadata = call.metadata;
    const authHeader = metadata.get('authorization')[0];   // get() returns array
    const requestId = metadata.get('x-request-id')[0];

    if (!authHeader || !authHeader.startsWith('Bearer ')) {
      return callback({
        code: grpc.status.UNAUTHENTICATED,
        message: 'Missing or invalid authorization header'
      });
    }

    const token = authHeader.slice(7);
    // validate token...
  }
};
```

**Server sending response metadata (headers and trailers):**
```javascript
const orderServiceImpl = {
  getOrder: (call, callback) => {
    // Send initial metadata (headers) before response
    const responseMetadata = new grpc.Metadata();
    responseMetadata.set('x-server-id', process.env.INSTANCE_ID);
    call.sendMetadata(responseMetadata);

    // The callback's third argument sends trailing metadata
    const trailingMetadata = new grpc.Metadata();
    trailingMetadata.set('x-processing-time-ms', String(Date.now() - start));
    callback(null, response, trailingMetadata);
  }
};
```

**Q13. How do you configure TLS for production gRPC in Node.js?**
A: Production gRPC must use TLS. `@grpc/grpc-js` supports both mutual TLS (mTLS) and one-way TLS:

**Server with TLS:**
```javascript
const fs = require('fs');

const serverCredentials = grpc.ServerCredentials.createSsl(
  fs.readFileSync('./certs/ca.crt'),          // CA certificate (to verify clients for mTLS)
  [{
    cert_chain: fs.readFileSync('./certs/server.crt'),
    private_key: fs.readFileSync('./certs/server.key')
  }],
  true   // checkClientCertificate: true = require mTLS; false = one-way TLS
);

server.bindAsync('0.0.0.0:50051', serverCredentials, (err, port) => {
  if (err) throw err;
  server.start();
});
```

**Client with TLS (one-way — verify server certificate):**
```javascript
const clientCredentials = grpc.credentials.createSsl(
  fs.readFileSync('./certs/ca.crt')   // CA cert to verify server
);
const client = new proto.order.OrderService('order-service:50051', clientCredentials);
```

**Client with mTLS (mutual — both sides present certificates):**
```javascript
const clientCredentials = grpc.credentials.createSsl(
  fs.readFileSync('./certs/ca.crt'),       // CA cert to verify server
  fs.readFileSync('./certs/client.key'),   // client private key
  fs.readFileSync('./certs/client.crt')   // client certificate
);
```

**Combining TLS with per-call metadata (e.g., JWT token on top of mTLS):**
```javascript
const channelCredentials = grpc.credentials.createSsl(/* ... */);
const callCredentials = grpc.credentials.createFromMetadataGenerator(
  (params, callback) => {
    const metadata = new grpc.Metadata();
    metadata.set('authorization', `Bearer ${getAccessToken()}`);
    callback(null, metadata);
  }
);
const combinedCredentials = grpc.credentials.combineChannelCredentials(
  channelCredentials,
  callCredentials
);
const client = new proto.order.OrderService('order-service:50051', combinedCredentials);
```

## Section 5: Error Handling and Deadlines

**Q14. How do you handle gRPC errors on the client side in Node.js?**
A: gRPC errors arrive as objects with `code` (number), `message` (string), and optionally `metadata`:

```javascript
const { status } = require('@grpc/grpc-js');

async function getOrderSafe(orderId) {
  return new Promise((resolve, reject) => {
    const deadline = new Date();
    deadline.setSeconds(deadline.getSeconds() + 5);   // 5-second deadline

    client.getOrder(
      { order_id: orderId },
      { deadline },                // pass as call options, not metadata
      (error, response) => {
        if (error) {
          // error.code is a grpc.status enum value
          switch (error.code) {
            case status.NOT_FOUND:
              resolve(null);   // treat as "no order found", not an error
              break;
            case status.DEADLINE_EXCEEDED:
              reject(new Error(`getOrder timed out after 5s`));
              break;
            case status.UNAVAILABLE:
              // Transient — safe to retry
              reject(new RetryableError(`order-service unavailable: ${error.message}`));
              break;
            case status.UNAUTHENTICATED:
              // Token expired — refresh and retry
              reject(new AuthError('token expired'));
              break;
            default:
              reject(new Error(`gRPC error ${error.code}: ${error.message}`));
          }
          return;
        }
        resolve(response);
      }
    );
  });
}
```

**Rich error details:** Accessing structured error details attached to the status:
```javascript
const { Status } = require('@grpc/grpc-js/build/src/generated/google/rpc/status_pb');
const { fromStatusMessage } = require('@grpc/grpc-js');

client.getOrder({ order_id: orderId }, (error, response) => {
  if (error) {
    const metadata = error.metadata;
    if (metadata) {
      // Rich error details are in the 'grpc-status-details-bin' trailer
      const statusDetails = metadata.get('grpc-status-details-bin');
      if (statusDetails.length > 0) {
        // Parse the Status proto binary
        const statusProto = Status.deserializeBinary(statusDetails[0]);
        const details = statusProto.getDetailsList();
        // details contains structured error information (BadRequest, etc.)
      }
    }
  }
});
```

**Q15. How do you implement deadlines and cancellation in Node.js gRPC clients?**
A: Deadlines are set via call options. Cancellation uses an AbortController-like pattern:

```javascript
// Deadline via call options (preferred)
function getOrderWithDeadline(orderId, timeoutMs = 5000) {
  const deadline = new Date(Date.now() + timeoutMs);

  return new Promise((resolve, reject) => {
    client.getOrder(
      { order_id: orderId },
      { deadline },   // call options — distinct from metadata
      (error, response) => {
        if (error?.code === status.DEADLINE_EXCEEDED) {
          reject(new Error(`Timed out after ${timeoutMs}ms`));
        } else if (error) {
          reject(error);
        } else {
          resolve(response);
        }
      }
    );
  });
}

// Cancelling a streaming call
function streamOrdersWithTimeout(customerId, timeoutMs = 30000) {
  const stream = client.listOrders({ customer_id: customerId });
  const orders = [];

  const timeout = setTimeout(() => {
    stream.cancel();   // sends CANCELLED to server
  }, timeoutMs);

  return new Promise((resolve, reject) => {
    stream.on('data', (order) => orders.push(order));
    stream.on('end', () => {
      clearTimeout(timeout);
      resolve(orders);
    });
    stream.on('error', (err) => {
      clearTimeout(timeout);
      if (err.code === status.CANCELLED) {
        resolve(orders);   // partial results on cancel
      } else {
        reject(err);
      }
    });
  });
}
```

## Section 6: Interceptors and Middleware

**Q16. How do you implement gRPC interceptors in Node.js?**
A: `@grpc/grpc-js` supports client-side interceptors. Server-side interceptors are not natively supported — use wrapper functions instead:

**Client-side interceptor (logging + retry example):**
```javascript
// Interceptor factory — returns an interceptor function
function loggingInterceptor(options, nextCall) {
  return new grpc.InterceptingCall(nextCall(options), {
    start: function(metadata, listener, next) {
      const start = Date.now();
      const method = options.method_definition.path;

      next(metadata, {
        onReceiveMessage: function(message, next) {
          next(message);
        },
        onReceiveStatus: function(status, next) {
          const duration = Date.now() - start;
          console.log(`gRPC ${method} → ${status.code} (${duration}ms)`);
          next(status);
        }
      });
    }
  });
}

// Attach interceptors to the channel
const client = new proto.order.OrderService(
  'order-service:50051',
  grpc.credentials.createInsecure(),
  {
    interceptors: [loggingInterceptor]
  }
);
```

**Server-side middleware pattern (wrapper function):**
Since `@grpc/grpc-js` lacks server interceptors, wrap handler functions:

```javascript
// Auth middleware wrapper
function withAuth(handler) {
  return async (call, callback) => {
    const metadata = call.metadata;
    const authHeader = metadata.get('authorization')[0];

    if (!authHeader) {
      return callback({
        code: grpc.status.UNAUTHENTICATED,
        message: 'Authorization header required'
      });
    }

    try {
      const claims = await verifyToken(authHeader.replace('Bearer ', ''));
      call.user = claims;   // attach to call for handler access
      return handler(call, callback);
    } catch (err) {
      return callback({
        code: grpc.status.UNAUTHENTICATED,
        message: 'Invalid token'
      });
    }
  };
}

// Logging middleware wrapper
function withLogging(methodName, handler) {
  return async (call, callback) => {
    const start = Date.now();
    const wrappedCallback = (error, response) => {
      const duration = Date.now() - start;
      const code = error ? error.code : grpc.status.OK;
      console.log(`${methodName}: code=${code}, duration=${duration}ms`);
      callback(error, response);
    };
    return handler(call, wrappedCallback);
  };
}

// Compose middleware
const orderServiceImpl = {
  getOrder: withLogging('GetOrder', withAuth(async (call, callback) => {
    const { order_id } = call.request;
    // call.user is available from withAuth
    const order = await db.findOrder(order_id);
    callback(null, toProto(order));
  }))
};
```

## Section 7: Connection Management and Channels

**Q17. How does channel management work in `@grpc/grpc-js` and what are the performance implications?**
A: A gRPC channel represents a connection to a server endpoint. Channels are long-lived and manage the underlying HTTP/2 connections:

**Channel lifecycle:**
```javascript
// Creating a client creates (and lazily connects) a channel
const client = new proto.order.OrderService(
  'order-service:50051',
  grpc.credentials.createInsecure(),
  {
    // Channel options
    'grpc.keepalive_time_ms': 30000,              // send keepalive ping every 30s
    'grpc.keepalive_timeout_ms': 5000,            // wait 5s for keepalive ack
    'grpc.keepalive_permit_without_calls': 1,     // send keepalive even if no active calls
    'grpc.http2.max_pings_without_data': 0,       // unlimited pings
    'grpc.max_receive_message_length': 10485760,  // 10MB max message size
    'grpc.max_send_message_length': 10485760,
  }
);

// Graceful shutdown — wait for in-flight RPCs to complete
process.on('SIGTERM', () => {
  client.close();   // closes the channel after in-flight calls complete
});
```

**Connection state machine:** A channel transitions through states:
```
IDLE → CONNECTING → READY → TRANSIENT_FAILURE → IDLE (reconnect)
                          → SHUTDOWN (closed)
```

**Check channel state:**
```javascript
const channelState = client.getChannel().getConnectivityState(true);
// true = try to connect if IDLE
// Returns: 0=IDLE, 1=CONNECTING, 2=READY, 3=TRANSIENT_FAILURE, 4=SHUTDOWN

// Wait for channel to be ready
client.waitForReady(Date.now() + 5000, (err) => {
  if (err) console.error('Channel not ready:', err);
  else console.log('Channel ready');
});
```

**Singleton channel pattern — reuse across requests:**
```javascript
// BAD: creates a new channel per request — defeats connection pooling
app.get('/orders/:id', async (req, res) => {
  const client = new proto.order.OrderService(/* ... */);  // new channel per request
  const order = await getOrder(client, req.params.id);
  client.close();
  res.json(order);
});

// GOOD: create once at startup, reuse across all requests
const orderClient = new proto.order.OrderService(/* ... */);  // module-level singleton

app.get('/orders/:id', async (req, res) => {
  const order = await getOrder(orderClient, req.params.id);
  res.json(order);
});
```

**Q18. How do you implement retry logic for gRPC calls in Node.js?**
A: `@grpc/grpc-js` supports built-in retry configuration via service config, or you can implement it manually:

**Built-in retry via service config:**
```javascript
const client = new proto.order.OrderService(
  'order-service:50051',
  grpc.credentials.createInsecure(),
  {
    'grpc.service_config': JSON.stringify({
      methodConfig: [{
        name: [{ service: 'order.OrderService', method: 'GetOrder' }],
        retryPolicy: {
          maxAttempts: 3,
          initialBackoff: '0.1s',
          maxBackoff: '1s',
          backoffMultiplier: 2,
          retryableStatusCodes: ['UNAVAILABLE', 'DEADLINE_EXCEEDED']
        }
      }]
    })
  }
);
```

**Manual retry with exponential backoff:**
```javascript
async function withRetry(fn, maxAttempts = 3) {
  const retryableCodes = new Set([
    grpc.status.UNAVAILABLE,
    grpc.status.DEADLINE_EXCEEDED,
    grpc.status.RESOURCE_EXHAUSTED
  ]);

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      const isRetryable = retryableCodes.has(err.code);
      const isLastAttempt = attempt === maxAttempts;

      if (!isRetryable || isLastAttempt) throw err;

      const backoffMs = Math.min(100 * Math.pow(2, attempt - 1), 2000);
      const jitter = Math.random() * 100;
      await new Promise(resolve => setTimeout(resolve, backoffMs + jitter));

      console.warn(`Retry ${attempt}/${maxAttempts} after ${backoffMs}ms (code: ${err.code})`);
    }
  }
}

// Usage
const order = await withRetry(() => getOrder('ord-123'));
```

## Section 10: Scenario / System Design Style Questions

**Q22. "You're building a Node.js gRPC service that receives 50,000 unary RPC calls per second from downstream services. What optimizations do you apply?"**
A: High-throughput gRPC server optimization in Node.js:

**Connection and channel tuning:**
```javascript
const server = new grpc.Server({
  'grpc.max_concurrent_streams': 1000,    // max streams per HTTP/2 connection
  'grpc.http2.max_requests_per_connection': 0,  // unlimited requests per connection
  'grpc.keepalive_time_ms': 30000,
  'grpc.keepalive_timeout_ms': 5000,
});
```

**Worker threads for CPU-intensive handlers:**
Node.js is single-threaded. A CPU-intensive gRPC handler (cryptography, complex data transformation) blocks the event loop, starving other RPCs. Offload to worker threads:
```javascript
const { Worker, workerData, parentPort } = require('worker_threads');

// In the handler — offload CPU-intensive work
getOrder: (call, callback) => {
  const worker = new Worker('./orderWorker.js', {
    workerData: { orderId: call.request.order_id }
  });
  worker.on('message', (result) => callback(null, result));
  worker.on('error', (err) => callback({ code: grpc.status.INTERNAL, message: err.message }));
}
```

**Connection pooling from clients:** Ensure downstream callers maintain persistent channels (not creating a new channel per request). A single channel handles many concurrent RPCs via HTTP/2 multiplexing.

**Avoid synchronous operations in handlers:** Never use `fs.readFileSync`, `crypto.createHashSync`, or any blocking operation in a gRPC handler — it blocks the Node.js event loop for all concurrent RPCs.

**Message size limits:** Set `grpc.max_receive_message_length` and `grpc.max_send_message_length` to prevent unexpectedly large messages from overwhelming the process.

**Prometheus metrics:** Track `grpc_server_handled_total`, `grpc_server_handling_seconds` per method. Alert on P99 latency degradation to catch event loop blocking early.

**Q23. "A client reports intermittent 'Connection reset' errors when calling your Node.js gRPC server under load. Diagnose and fix."**
A: Intermittent connection resets under load have several common causes in Node.js gRPC:

**Cause 1 — Event loop lag causing timeout:**
A heavy workload on other parts of the Node.js process causes event loop delay. The gRPC keepalive ping isn't processed in time, causing the connection to be dropped. Diagnosis: measure event loop lag with `perf_hooks` or the `blocked-at` package. Fix: move CPU-intensive work to worker threads, reduce synchronous operations.

**Cause 2 — Server rejecting too many concurrent streams:**
`grpc.max_concurrent_streams` is too low for the peak concurrency. The server drops connections when the limit is hit. Diagnosis: check server logs for "Max concurrent stream limit exceeded". Fix: increase `grpc.max_concurrent_streams` or add more server instances.

**Cause 3 — Unhandled promise rejections in handlers:**
An unhandled promise rejection in a handler crashes the handler without calling `callback`. The stream hangs until the client times out, consuming resources. Eventually, accumulated hanging streams cause connection resets. Fix: always wrap async handlers in try-catch, always call `callback` on error.

```javascript
// BAD: unhandled rejection
getOrder: async (call, callback) => {
  const order = await db.findOrder(call.request.order_id);  // throws → uncaught
  callback(null, order);
}

// GOOD: always call callback on error
getOrder: async (call, callback) => {
  try {
    const order = await db.findOrder(call.request.order_id);
    callback(null, order);
  } catch (err) {
    callback({ code: grpc.status.INTERNAL, message: err.message });
  }
}
```

**Cause 4 — Keepalive misconfiguration between client and server:**
If client sends keepalive pings more frequently than the server's `grpc.http2.min_ping_interval_without_data_ms`, the server closes the connection with `GOAWAY (ENHANCE_YOUR_CALM)`. Match keepalive settings between client and server.

**Q24. "How would you design a Node.js gRPC service that calls three downstream gRPC services in parallel and aggregates results?"**
A: Parallel gRPC calls with Promise.all and proper deadline propagation:

```javascript
const { promisify } = require('util');

// Promisify client methods for cleaner async/await
const inventoryClient = new proto.inventory.InventoryService(/* ... */);
const pricingClient = new proto.pricing.PricingService(/* ... */);
const shippingClient = new proto.shipping.ShippingService(/* ... */);

const getInventory = promisify(inventoryClient.getInventory.bind(inventoryClient));
const getPrice = promisify(pricingClient.getPrice.bind(pricingClient));
const getShipping = promisify(shippingClient.getShippingOptions.bind(shippingClient));

const orderServiceImpl = {
  getOrderDetails: async (call, callback) => {
    const { order_id } = call.request;

    // Propagate the client's deadline to all downstream calls
    // This prevents downstream calls from outliving the client's timeout
    const deadline = call.metadata.get('deadline')[0]
      || new Date(Date.now() + 5000);

    const callOptions = { deadline };

    try {
      // Call all three services in parallel — total time = slowest, not sum
      const [inventory, price, shipping] = await Promise.all([
        getInventory({ order_id }, callOptions),
        getPrice({ order_id }, callOptions),
        getShipping({ order_id }, callOptions)
      ]);

      callback(null, {
        order_id,
        inventory_status: inventory.status,
        unit_price_cents: price.amount_cents,
        estimated_delivery: shipping.estimated_date
      });

    } catch (err) {
      // Map downstream errors to appropriate status codes
      if (err.code === grpc.status.NOT_FOUND) {
        callback({ code: grpc.status.NOT_FOUND, message: `Order ${order_id} not found` });
      } else if (err.code === grpc.status.DEADLINE_EXCEEDED) {
        callback({ code: grpc.status.DEADLINE_EXCEEDED, message: 'Downstream timeout' });
      } else {
        callback({ code: grpc.status.INTERNAL, message: `Aggregation failed: ${err.message}` });
      }
    }
  }
};
```

**Partial failure handling with `Promise.allSettled`:**
If some downstream services are optional (pricing is critical, shipping estimate is nice-to-have):
```javascript
const results = await Promise.allSettled([
  getInventory({ order_id }, callOptions),
  getPrice({ order_id }, callOptions),
  getShipping({ order_id }, callOptions)   // optional
]);

const [inventoryResult, priceResult, shippingResult] = results;

// Fail hard if critical services fail
if (inventoryResult.status === 'rejected' || priceResult.status === 'rejected') {
  return callback({ code: grpc.status.INTERNAL, message: 'Critical service failure' });
}

callback(null, {
  order_id,
  inventory_status: inventoryResult.value.status,
  unit_price_cents: priceResult.value.amount_cents,
  // Optional field — null if shipping service failed
  estimated_delivery: shippingResult.status === 'fulfilled'
    ? shippingResult.value.estimated_date
    : null
});
```

## Quick Reference: gRPC Node.js Patterns

| Pattern | Handler Signature | Key Methods |
|---|---|---|
| Unary | `(call, callback) => void` | `call.request`, `callback(err, response)` |
| Server streaming | `(call) => void` | `call.request`, `call.write(msg)`, `call.end()`, `call.cancelled` |
| Client streaming | `(call, callback) => void` | `call.on('data', fn)`, `call.on('end', fn)`, `callback(err, response)` |
| Bidirectional | `(call) => void` | `call.on('data', fn)`, `call.write(msg)`, `call.end()`, `call.on('end', fn)` |

| Client Call | Returns | How to Receive |
|---|---|---|
| Unary | `void` (callback) | `client.method(req, callback)` |
| Server streaming | `ClientReadableStream` | `.on('data', fn)`, `.on('end', fn)`, `for await` |
| Client streaming | `ClientWritableStream` | `stream.write(msg)`, `stream.end()`, callback receives response |
| Bidirectional | `ClientDuplexStream` | Both `.write()` and `.on('data')` |

---

**Tip for the interview:** Node.js gRPC questions almost always pivot to three areas: (1) `keepCase` confusion — candidates who haven't used it in production often don't know that proto field names arrive as `snake_case` in JavaScript when `keepCase: true`, and `camelCase` when `keepCase: false`; inconsistency between services causes silent field-name mismatches where `order_id` on the server arrives as `orderId` on the client or vice versa; always use `keepCase: true` and match across all services; (2) the singleton channel pattern — creating a new gRPC client per request is one of the most common performance bugs in Node.js gRPC code; channels are expensive to create and HTTP/2 connections are meant to be reused; creating one client at module level and reusing it is the correct pattern; (3) unhandled promise rejections in async handlers — forgetting to `try/catch` an `async` handler means a thrown error never calls `callback`, the RPC hangs until the client's deadline, and accumulated hanging RPCs eventually cause connection resets; always wrap async handlers in try-catch and always call `callback` on every code path.
