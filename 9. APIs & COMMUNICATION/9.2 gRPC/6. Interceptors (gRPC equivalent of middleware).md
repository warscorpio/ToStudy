# Interceptors (gRPC Equivalent of Middleware) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are gRPC interceptors and what problem do they solve?**
A: gRPC interceptors are composable middleware functions that wrap RPC calls — on the client side before a call is dispatched to the network, and on the server side before a call is routed to the handler. They intercept every RPC that flows through the channel or server, allowing cross-cutting concerns to be implemented once and applied uniformly rather than repeated in every service method.

The problem they solve is the same one HTTP middleware solves: in a service with 50 RPC methods, concerns like authentication, logging, metrics, tracing, retry logic, and rate limiting must not be implemented 50 times — once in each handler. Interceptors extract these concerns into a single, tested, reusable function that applies to all RPCs automatically.

Without interceptors:
```go
// Every handler repeats the same concerns
func (s *Server) CreateCharge(ctx context.Context, req *pb.CreateChargeRequest) (*pb.Charge, error) {
  // Auth check — repeated in every method
  if err := validateToken(ctx); err != nil {
    return nil, err
  }
  // Logging — repeated in every method
  log.Printf("CreateCharge called by %s", extractUserID(ctx))
  // Metrics — repeated in every method
  metrics.Increment("rpc.CreateCharge.calls")
  // Actual business logic
  return s.processCharge(req)
}
```

With interceptors:
```go
// Auth, logging, metrics handled once in interceptors
// Handler contains only business logic
func (s *Server) CreateCharge(ctx context.Context, req *pb.CreateChargeRequest) (*pb.Charge, error) {
  return s.processCharge(req)
}
```

**Q2. What are the four types of gRPC interceptors?**
A: Interceptors are split along two dimensions: client vs server, and unary vs streaming.

**Unary interceptors** — wrap RPCs where the client sends one request and receives one response (the most common pattern):
- `grpc.UnaryClientInterceptor` — runs on the client before sending the request.
- `grpc.UnaryServerInterceptor` — runs on the server before the handler is called.

**Stream interceptors** — wrap streaming RPCs (client-streaming, server-streaming, bidirectional):
- `grpc.StreamClientInterceptor` — wraps the client's stream object.
- `grpc.StreamServerInterceptor` — wraps the server's stream object.

```
Client                              Server
  │                                    │
  │  UnaryClientInterceptor            │  UnaryServerInterceptor
  │  ┌────────────────────────┐        │  ┌────────────────────────┐
  │  │  auth header injection │        │  │  token validation      │
  │  │  request logging       │        │  │  request logging       │
  │  │  timeout injection     │        │  │  metrics increment     │
  │  └──────────┬─────────────┘        │  └──────────┬─────────────┘
  │             │ network              │             │
  │             └─────────────────────►│             │ handler
  │                                    │             ▼
  │                                    │    CreateCharge(ctx, req)
```

Streaming interceptors are more complex — they wrap the `grpc.ClientStream` or `grpc.ServerStream` interfaces, allowing interception of individual messages as they flow through the stream, not just the call setup.

**Q3. How do gRPC interceptors differ from HTTP middleware conceptually?**
A: They are structurally analogous but differ in several ways that matter in practice:

**Method awareness:** gRPC interceptors receive the full method info — `info.FullMethod` gives the service and method name (e.g., `/payments.ChargesService/CreateCharge`). HTTP middleware typically operates on URL paths, which are less semantically structured. This makes gRPC interceptors more powerful for method-level routing decisions (e.g., skip auth for health check endpoints by exact method name, not by path pattern).

**Typed context:** gRPC passes a `context.Context` through every interceptor and into the handler. Context carries deadlines, cancellations, and metadata. HTTP middleware works with request/response objects that are HTTP-specific. gRPC's context model is cleaner for propagating values (trace IDs, user identity) without coupling to the transport.

**Metadata instead of headers:** gRPC uses `metadata.MD` (a string-keyed, string-valued map) rather than HTTP headers. Interceptors read and write metadata: `md, ok := metadata.FromIncomingContext(ctx)`. The concept is the same but the API differs.

**Streaming:** HTTP middleware doesn't naturally wrap streaming — SSE and WebSockets require different patterns. gRPC stream interceptors wrap the stream object itself, giving access to every individual message sent and received.

**Single interceptor per channel/server:** gRPC (in its base form) only accepts one `UnaryServerInterceptor` and one `StreamServerInterceptor`. Chaining multiple interceptors requires either a chain helper (`grpc.ChainUnaryInterceptor`) or a third-party package like `go-grpc-middleware`. HTTP frameworks typically accept a slice of middleware natively.

## Section 2: Server-Side Interceptors

**Q4. What is the function signature of a unary server interceptor and how does it work?**
A: In Go (the most common gRPC implementation), a unary server interceptor has this signature:

```go
type UnaryServerInterceptor func(
  ctx     context.Context,
  req     interface{},
  info    *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (interface{}, error)
```

- `ctx` — the request context; carries deadline, cancellation, and incoming metadata.
- `req` — the deserialized request protobuf message.
- `info` — contains `info.FullMethod` (e.g., `/payments.ChargesService/CreateCharge`) and `info.Server` (the server instance).
- `handler` — the next function in the chain; calling `handler(ctx, req)` either invokes the next interceptor or the actual RPC handler.
- Returns the response object and an error.

A concrete logging interceptor:

```go
func LoggingInterceptor(
  ctx context.Context,
  req interface{},
  info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (interface{}, error) {
  start := time.Now()

  // Pre-handler: log the incoming call
  log.Printf("[gRPC] %s | START", info.FullMethod)

  // Call the next interceptor or the actual handler
  resp, err := handler(ctx, req)

  // Post-handler: log the outcome and duration
  duration := time.Since(start)
  if err != nil {
    st, _ := status.FromError(err)
    log.Printf("[gRPC] %s | FAIL | code=%s | duration=%s | error=%s",
      info.FullMethod, st.Code(), duration, st.Message())
  } else {
    log.Printf("[gRPC] %s | OK | duration=%s", info.FullMethod, duration)
  }

  return resp, err
}
```

The structure mirrors HTTP middleware exactly: code before `handler(ctx, req)` runs on the way in; code after runs on the way out. The interceptor can:
- Inspect and modify `ctx` before passing it downstream.
- Inspect and modify `req` before passing it downstream.
- Inspect and modify `resp` and `err` before returning them upstream.
- Short-circuit by returning early without calling `handler` (e.g., auth rejection).

**Q5. How do you implement a server-side authentication interceptor?**
A: Authentication is the most common server interceptor — validate the JWT or API key before any RPC method executes:

```go
func AuthInterceptor(
  ctx context.Context,
  req interface{},
  info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (interface{}, error) {
  // Skip auth for public endpoints
  if isPublicMethod(info.FullMethod) {
    return handler(ctx, req)
  }

  // Extract the Authorization metadata
  md, ok := metadata.FromIncomingContext(ctx)
  if !ok {
    return nil, status.Error(codes.Unauthenticated, "missing metadata")
  }

  authHeader := md.Get("authorization")
  if len(authHeader) == 0 {
    return nil, status.Error(codes.Unauthenticated, "authorization header required")
  }

  token := strings.TrimPrefix(authHeader[0], "Bearer ")

  // Validate the token
  claims, err := validateJWT(token)
  if err != nil {
    return nil, status.Errorf(codes.Unauthenticated, "invalid token: %v", err)
  }

  // Inject validated identity into context for use by the handler
  ctx = context.WithValue(ctx, userIDKey{}, claims.UserID)
  ctx = context.WithValue(ctx, tenantIDKey{}, claims.TenantID)

  return handler(ctx, req)
}

// Handlers extract identity from context — no need to re-validate
func (s *Server) CreateCharge(ctx context.Context, req *pb.CreateChargeRequest) (*pb.Charge, error) {
  userID := ctx.Value(userIDKey{}).(string)   // safe: always present after auth interceptor
  // ... business logic
}

var publicMethods = map[string]bool{
  "/grpc.health.v1.Health/Check": true,
  "/payments.AuthService/Login":  true,
}

func isPublicMethod(fullMethod string) bool {
  return publicMethods[fullMethod]
}
```

gRPC status codes mirror HTTP: `codes.Unauthenticated` → HTTP 401; `codes.PermissionDenied` → HTTP 403; `codes.NotFound` → HTTP 404. Using the correct code is important — gRPC clients and gateways make routing decisions based on status codes just as HTTP infrastructure does.

**Q6. How do you implement a server-side metrics interceptor?**
A: Metrics interceptors emit per-method call counts, latencies, and error rates:

```go
func MetricsInterceptor(
  ctx context.Context,
  req interface{},
  info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (interface{}, error) {
  // Extract method and service name
  // info.FullMethod = "/payments.ChargesService/CreateCharge"
  parts := strings.SplitN(strings.TrimPrefix(info.FullMethod, "/"), "/", 2)
  service, method := parts[0], parts[1]

  // Increment in-flight gauge
  inFlightGauge.WithLabelValues(service, method).Inc()
  defer inFlightGauge.WithLabelValues(service, method).Dec()

  start := time.Now()

  resp, err := handler(ctx, req)

  duration := time.Since(start).Seconds()

  // Determine the gRPC status code
  code := codes.OK
  if err != nil {
    st, _ := status.FromError(err)
    code = st.Code()
  }

  // Record metrics
  requestCounter.WithLabelValues(service, method, code.String()).Inc()
  requestDuration.WithLabelValues(service, method, code.String()).Observe(duration)

  return resp, err
}

var (
  requestCounter = promauto.NewCounterVec(prometheus.CounterOpts{
    Name: "grpc_server_requests_total",
  }, []string{"service", "method", "code"})

  requestDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
    Name:    "grpc_server_request_duration_seconds",
    Buckets: []float64{.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10},
  }, []string{"service", "method", "code"})

  inFlightGauge = promauto.NewGaugeVec(prometheus.GaugeOpts{
    Name: "grpc_server_requests_in_flight",
  }, []string{"service", "method"})
)
```

This is a pattern so common that the `grpc-ecosystem/go-grpc-prometheus` package provides a production-ready implementation. Use the library rather than this homebrew version in production — it handles edge cases (stream interceptors, panics, context cancellation) that a naïve implementation misses.

**Q7. How do you implement a panic recovery interceptor?**
A: An unhandled panic in an RPC handler crashes the goroutine and closes the connection without returning a gRPC error — the client receives a connection reset, not a meaningful error. A recovery interceptor catches panics and converts them to `codes.Internal` errors:

```go
func RecoveryInterceptor(
  ctx context.Context,
  req interface{},
  info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (resp interface{}, err error) {
  // Deferred recover catches panics in the handler AND subsequent interceptors
  defer func() {
    if r := recover(); r != nil {
      // Log the panic with stack trace for debugging
      stack := debug.Stack()
      log.Printf("[PANIC] %s | recovered: %v\n%s", info.FullMethod, r, stack)

      // Emit a metric for panic alerting
      panicCounter.WithLabelValues(info.FullMethod).Inc()

      // Return a gRPC Internal error instead of crashing
      err = status.Errorf(codes.Internal, "internal server error")
    }
  }()

  return handler(ctx, req)
}
```

Recovery interceptors must be the outermost interceptor in the chain — they must wrap all other interceptors so they catch panics that occur anywhere in the chain. In most setups: recovery → auth → logging → metrics → handler (inner to outer on the way in; outer to inner on the way out).

## Section 3: Client-Side Interceptors

**Q8. What is the function signature of a unary client interceptor?**
A: The client-side unary interceptor signature:

```go
type UnaryClientInterceptor func(
  ctx     context.Context,
  method  string,
  req     interface{},
  reply   interface{},
  cc      *grpc.ClientConn,
  invoker grpc.UnaryInvoker,
  opts    ...grpc.CallOption,
) error
```

- `method` — the full RPC method name (e.g., `/payments.ChargesService/CreateCharge`).
- `req` — the request message (already serialized by the time interceptors run).
- `reply` — a pointer to the response message; the invoker populates it.
- `cc` — the client connection; useful for reading connection state.
- `invoker` — the next function in the chain; `invoker(ctx, method, req, reply, cc, opts...)` sends the actual RPC.

A concrete client-side auth interceptor that injects credentials:

```go
func ClientAuthInterceptor(token string) grpc.UnaryClientInterceptor {
  return func(
    ctx context.Context,
    method string,
    req, reply interface{},
    cc *grpc.ClientConn,
    invoker grpc.UnaryInvoker,
    opts ...grpc.CallOption,
  ) error {
    // Inject the auth token into outgoing metadata
    ctx = metadata.AppendToOutgoingContext(ctx, "authorization", "Bearer "+token)
    return invoker(ctx, method, req, reply, cc, opts...)
  }
}
```

Note the closure pattern: `ClientAuthInterceptor(token)` returns an interceptor. This is how client interceptors are typically parameterized — the outer function accepts configuration; the returned function is the actual interceptor.

**Q9. How do you implement client-side retry logic in an interceptor?**
A: Retry logic belongs in a client interceptor — it is transparent to the caller and applies to all RPC calls:

```go
func RetryInterceptor(maxAttempts int, retriableCodes ...codes.Code) grpc.UnaryClientInterceptor {
  retriableSet := make(map[codes.Code]bool)
  for _, c := range retriableCodes {
    retriableSet[c] = true
  }

  return func(
    ctx context.Context,
    method string,
    req, reply interface{},
    cc *grpc.ClientConn,
    invoker grpc.UnaryInvoker,
    opts ...grpc.CallOption,
  ) error {
    var lastErr error

    for attempt := 0; attempt < maxAttempts; attempt++ {
      if attempt > 0 {
        // Exponential backoff with jitter
        base := time.Duration(50*math.Pow(2, float64(attempt-1))) * time.Millisecond
        jitter := time.Duration(rand.Int63n(int64(base) / 2))
        delay := base + jitter
        if delay > 5*time.Second {
          delay = 5 * time.Second
        }

        select {
        case <-time.After(delay):
        case <-ctx.Done():
          return ctx.Err()
        }
      }

      lastErr = invoker(ctx, method, req, reply, cc, opts...)
      if lastErr == nil {
        return nil
      }

      // Only retry on retriable status codes
      st, ok := status.FromError(lastErr)
      if !ok || !retriableSet[st.Code()] {
        return lastErr
      }

      log.Printf("[retry] %s attempt %d/%d failed: %v", method, attempt+1, maxAttempts, st.Code())
    }

    return lastErr
  }
}

// Usage:
conn, _ := grpc.Dial(addr,
  grpc.WithUnaryInterceptor(RetryInterceptor(3,
    codes.Unavailable,
    codes.DeadlineExceeded,
    codes.ResourceExhausted,
  )),
)
```

**Which codes are retriable:**
- `codes.Unavailable` — server is temporarily unavailable (503 equivalent). Always retry.
- `codes.DeadlineExceeded` — timeout. Retry only if the parent context has remaining budget.
- `codes.ResourceExhausted` — rate limited (429 equivalent). Retry after backoff.
- `codes.Internal` — server error. Retry cautiously; some internals are transient.
- `codes.NotFound`, `codes.PermissionDenied`, `codes.InvalidArgument` — never retry; these are permanent failures that require a change in the request.

**Q10. How do you implement client-side distributed tracing in an interceptor?**
A: Tracing interceptors propagate trace context across service boundaries — they read the active span from the local context and inject its trace ID into the outgoing gRPC metadata, so the downstream service creates spans that are children of the upstream span:

```go
func TracingInterceptor(tracer trace.Tracer) grpc.UnaryClientInterceptor {
  return func(
    ctx context.Context,
    method string,
    req, reply interface{},
    cc *grpc.ClientConn,
    invoker grpc.UnaryInvoker,
    opts ...grpc.CallOption,
  ) error {
    // Start a child span for this RPC call
    ctx, span := tracer.Start(ctx, method,
      trace.WithSpanKind(trace.SpanKindClient),
      trace.WithAttributes(
        semconv.RPCSystemGRPC,
        semconv.RPCMethod(method),
      ),
    )
    defer span.End()

    // Inject the trace context into outgoing gRPC metadata
    // This propagates traceparent, tracestate headers to the server
    propagator := otel.GetTextMapPropagator()
    md, _ := metadata.FromOutgoingContext(ctx)
    mdCopy := md.Copy()
    propagator.Inject(ctx, &metadataCarrier{mdCopy})
    ctx = metadata.NewOutgoingContext(ctx, mdCopy)

    // Make the call
    err := invoker(ctx, method, req, reply, cc, opts...)

    // Record the outcome on the span
    if err != nil {
      st, _ := status.FromError(err)
      span.SetStatus(otelcodes.Error, st.Message())
      span.SetAttributes(semconv.RPCGRPCStatusCodeKey.Int(int(st.Code())))
    } else {
      span.SetStatus(otelcodes.Ok, "")
    }

    return err
  }
}

// metadataCarrier implements TextMapCarrier for gRPC metadata
type metadataCarrier struct{ md metadata.MD }

func (c *metadataCarrier) Get(key string) string {
  vals := c.md.Get(strings.ToLower(key))
  if len(vals) == 0 {
    return ""
  }
  return vals[0]
}

func (c *metadataCarrier) Set(key, val string) {
  c.md.Set(strings.ToLower(key), val)
}

func (c *metadataCarrier) Keys() []string {
  keys := make([]string, 0, len(c.md))
  for k := range c.md {
    keys = append(keys, k)
  }
  return keys
}
```

The server-side tracing interceptor mirrors this: extract the incoming trace context from metadata, create a child span, inject the span into the context for the handler to use.

## Section 4: Chaining Interceptors

**Q11. How do you chain multiple interceptors in gRPC?**
A: gRPC's base API accepts only a single interceptor per server/client. Chaining is handled by the `grpc.ChainUnaryInterceptor` function (added in gRPC-Go 1.36):

```go
server := grpc.NewServer(
  grpc.ChainUnaryInterceptor(
    RecoveryInterceptor,         // outermost: catches panics from all others
    TracingInterceptor(tracer),  // creates trace span around the full call
    LoggingInterceptor,          // logs request and response
    MetricsInterceptor,          // emits Prometheus metrics
    AuthInterceptor,             // validates token, injects user into context
    RateLimitInterceptor,        // checks rate limits per user
    // handler is innermost
  ),
  grpc.ChainStreamInterceptor(
    StreamRecoveryInterceptor,
    StreamTracingInterceptor(tracer),
    StreamAuthInterceptor,
  ),
)
```

Execution order for `ChainUnaryInterceptor`:
```
Request flow (in):   Recovery → Tracing → Logging → Metrics → Auth → RateLimit → Handler
Response flow (out): RateLimit → Auth → Metrics → Logging → Tracing → Recovery
```

The first interceptor listed is the outermost — it runs first on the way in and last on the way out. The last interceptor listed is the innermost — it runs last on the way in (immediately before the handler) and first on the way out.

**Ordering principles:**
- **Recovery must be outermost** — it needs to catch panics from all other interceptors and the handler.
- **Tracing before logging** — the trace span must exist before the logging interceptor reads the trace ID from context to include in log lines.
- **Auth before business interceptors** — rate limiting, ACL checks, and any interceptor that depends on user identity must run after auth injects the identity into context.
- **Logging after tracing** — so log lines include the trace ID for correlation.

**Q12. How do you implement chaining manually without `grpc.ChainUnaryInterceptor`?**
A: Understanding the manual chain reveals why ordering matters:

```go
func ChainUnaryServer(
  interceptors ...grpc.UnaryServerInterceptor,
) grpc.UnaryServerInterceptor {
  return func(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
  ) (interface{}, error) {
    // Build the chain from the innermost outward
    // The handler is the innermost "interceptor"
    chain := handler

    // Wrap from right to left so the first interceptor is outermost
    for i := len(interceptors) - 1; i >= 0; i-- {
      interceptor := interceptors[i]
      innerChain := chain
      chain = func(ctx context.Context, req interface{}) (interface{}, error) {
        return interceptor(ctx, req, info, innerChain)
      }
    }

    return chain(ctx, req)
  }
}
```

This makes explicit what `ChainUnaryInterceptor` does internally: it builds a nested closure where each interceptor wraps the next, with the actual handler at the innermost layer. The outermost closure (first interceptor) runs first; when it calls `handler(ctx, req)`, that invokes the second interceptor, which invokes the third, and so on until the actual handler is called.

## Section 5: Streaming Interceptors

**Q13. How do streaming interceptors differ from unary interceptors?**
A: Streaming interceptors wrap the stream object itself rather than a single request/response pair. They get one chance to intercept at stream creation, but individual messages flow through the stream's `Send` and `Recv` methods — intercepting individual messages requires wrapping those methods:

```go
type StreamServerInterceptor func(
  srv     interface{},
  ss      grpc.ServerStream,
  info    *grpc.StreamServerInfo,
  handler grpc.StreamHandler,
) error
```

`info.FullMethod` — the RPC method name.
`info.IsClientStream` — whether the client streams multiple messages.
`info.IsServerStream` — whether the server streams multiple messages.
`ss` — the stream; interceptors can wrap it to intercept individual `Send`/`Recv` calls.

A logging stream interceptor that logs stream open/close and message counts:

```go
func StreamLoggingInterceptor(
  srv interface{},
  ss grpc.ServerStream,
  info *grpc.StreamServerInfo,
  handler grpc.StreamHandler,
) error {
  start := time.Now()
  log.Printf("[stream] %s | OPEN", info.FullMethod)

  // Wrap the stream to count messages
  wrapped := &countingServerStream{ServerStream: ss}

  err := handler(srv, wrapped)

  duration := time.Since(start)
  if err != nil {
    log.Printf("[stream] %s | CLOSE | recv=%d sent=%d duration=%s error=%v",
      info.FullMethod, wrapped.recvCount, wrapped.sentCount, duration, err)
  } else {
    log.Printf("[stream] %s | CLOSE | recv=%d sent=%d duration=%s",
      info.FullMethod, wrapped.recvCount, wrapped.sentCount, duration)
  }

  return err
}

// countingServerStream wraps grpc.ServerStream to count messages
type countingServerStream struct {
  grpc.ServerStream
  recvCount int64
  sentCount int64
}

func (s *countingServerStream) RecvMsg(m interface{}) error {
  err := s.ServerStream.RecvMsg(m)
  if err == nil {
    atomic.AddInt64(&s.recvCount, 1)
  }
  return err
}

func (s *countingServerStream) SendMsg(m interface{}) error {
  err := s.ServerStream.SendMsg(m)
  if err == nil {
    atomic.AddInt64(&s.sentCount, 1)
  }
  return err
}
```

The wrapper pattern — embedding `grpc.ServerStream` and overriding `SendMsg`/`RecvMsg` — is the standard approach for per-message streaming interception. This is more complex than unary interception because messages arrive and depart asynchronously over the stream's lifetime, not as a single request/response pair.

## Section 6: NestJS gRPC Interceptors

**Q14. How do interceptors work in NestJS for gRPC services?**
A: NestJS uses the same interceptor concept (`NestInterceptor`) for both HTTP and gRPC. The interceptor wraps the handler via the `intercept` method, which receives an `ExecutionContext` and a `CallHandler`:

```typescript
import {
  Injectable, NestInterceptor, ExecutionContext, CallHandler
} from '@nestjs/common';
import { Observable, throwError } from 'rxjs';
import { catchError, tap, finalize } from 'rxjs/operators';
import { status as GrpcStatus } from '@grpc/grpc-js';
import { RpcException } from '@nestjs/microservices';

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const isGrpc = context.getType() === 'rpc';

    if (!isGrpc) return next.handle();  // only apply to gRPC calls

    const rpcContext = context.switchToRpc();
    const metadata = rpcContext.getContext();  // gRPC metadata
    const data = rpcContext.getData();          // request payload

    const handler = context.getHandler().name;  // method name
    const className = context.getClass().name;  // service class name

    const start = Date.now();
    console.log(`[gRPC] ${className}.${handler} | START`);

    return next.handle().pipe(
      tap(response => {
        const duration = Date.now() - start;
        console.log(`[gRPC] ${className}.${handler} | OK | ${duration}ms`);
      }),
      catchError(err => {
        const duration = Date.now() - start;
        console.error(`[gRPC] ${className}.${handler} | FAIL | ${duration}ms`, err);
        return throwError(() => err);
      }),
      finalize(() => {
        // cleanup regardless of success or failure
      })
    );
  }
}
```

**NestJS gRPC auth interceptor:**

```typescript
@Injectable()
export class GrpcAuthInterceptor implements NestInterceptor {
  constructor(private readonly jwtService: JwtService) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    if (context.getType() !== 'rpc') return next.handle();

    const grpcContext = context.switchToRpc().getContext();
    // grpcContext is the gRPC call metadata object
    const metadata = grpcContext.metadata || grpcContext;

    const authHeader = metadata.get('authorization')?.[0];
    if (!authHeader) {
      throw new RpcException({
        code: GrpcStatus.UNAUTHENTICATED,
        message: 'Missing authorization metadata',
      });
    }

    const token = authHeader.replace('Bearer ', '');

    try {
      const payload = this.jwtService.verify(token);
      // Attach to the request context for use in the handler
      grpcContext.userId = payload.sub;
      grpcContext.tenantId = payload.tenantId;
    } catch {
      throw new RpcException({
        code: GrpcStatus.UNAUTHENTICATED,
        message: 'Invalid or expired token',
      });
    }

    return next.handle();
  }
}
```

Register interceptors globally or per-controller:

```typescript
// Global — applies to all handlers (HTTP and gRPC)
app.useGlobalInterceptors(new LoggingInterceptor());

// Per-controller — applies only to this gRPC service
@UseInterceptors(LoggingInterceptor, GrpcAuthInterceptor)
@Controller()
export class ChargesController implements ChargesServiceController {
  @GrpcMethod('ChargesService', 'CreateCharge')
  createCharge(data: CreateChargeRequest, metadata: Metadata): Charge {
    // interceptors have already run; user is authenticated
  }
}
```

**Q15. How do NestJS Guards and Pipes differ from Interceptors for gRPC?**
A: NestJS has four pipeline stages for request handling, each with different responsibilities. For gRPC, all four apply:

```
Middleware → Guards → Interceptors (pre) → Pipes → Handler → Interceptors (post)
```

**Guards** (`CanActivate`) — authorize the request. Return `true` to allow, `false` or throw to deny. Used for authentication checks and permission validation. In gRPC, throw `RpcException` with `UNAUTHENTICATED` or `PERMISSION_DENIED` code. Guards run before interceptors.

```typescript
@Injectable()
export class GrpcAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    if (context.getType() !== 'rpc') return true;
    const grpcCtx = context.switchToRpc().getContext();
    const token = grpcCtx.metadata.get('authorization')?.[0];
    if (!validateToken(token)) {
      throw new RpcException({ code: GrpcStatus.UNAUTHENTICATED, message: 'Unauthorized' });
    }
    return true;
  }
}
```

**Pipes** (`PipeTransform`) — transform and validate request data. In gRPC, validate the incoming protobuf message fields. Used with `class-validator` decorators on DTOs. Run after guards but before the handler.

**Interceptors** — wrap the entire handler execution, including its response. Can modify the response, add timing, catch errors, log. Guards and pipes run before interceptors reach the handler; interceptors control the execution around the handler.

**Practical division for gRPC:**
- Auth → Guard (binary allow/deny decision)
- Rate limiting → Guard (deny if over limit)
- Logging → Interceptor (needs timing around the full call)
- Metrics → Interceptor (needs timing + response outcome)
- Tracing → Interceptor (needs to wrap full execution)
- Input validation → Pipe (transform and validate request fields)

## Section 7: Scenario Questions

**Q16. "You want all gRPC calls in your service to emit Prometheus metrics without modifying any handler. How do you implement this?"**
A: A server-side metrics interceptor applied globally at server creation, combined with a stream interceptor for streaming RPCs:

```go
// Unary metrics interceptor
func UnaryMetricsInterceptor(
  ctx context.Context,
  req interface{},
  info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler,
) (interface{}, error) {
  timer := prometheus.NewTimer(requestDuration.WithLabelValues(info.FullMethod))
  requestsInFlight.WithLabelValues(info.FullMethod).Inc()

  resp, err := handler(ctx, req)

  timer.ObserveDuration()
  requestsInFlight.WithLabelValues(info.FullMethod).Dec()

  code := codes.OK
  if err != nil {
    st, _ := status.FromError(err)
    code = st.Code()
  }
  requestsTotal.WithLabelValues(info.FullMethod, code.String()).Inc()

  return resp, err
}

// Register on the server — no handler changes needed
server := grpc.NewServer(
  grpc.ChainUnaryInterceptor(
    UnaryMetricsInterceptor,
    // other interceptors...
  ),
)
```

In practice: use `grpc-ecosystem/go-grpc-prometheus` which provides `grpc_prometheus.UnaryServerInterceptor` and `grpc_prometheus.StreamServerInterceptor`. These are battle-tested implementations with correct handling of streaming, cancellations, and context timeouts. The value of the interceptor pattern is precisely that `go-grpc-prometheus` exists at all — because all gRPC calls are funneled through interceptors, one library package handles metrics for the entire ecosystem.

**Q17. "A downstream gRPC service is flaky — it fails 10% of the time with `UNAVAILABLE`. How do you add retry logic without changing every call site?"**
A: A client-side retry interceptor applied when creating the connection:

```go
conn, err := grpc.Dial(
  downstreamAddr,
  grpc.WithTransportCredentials(creds),
  grpc.WithUnaryInterceptor(
    RetryInterceptor(
      3,                      // max attempts
      codes.Unavailable,      // retry on UNAVAILABLE
      codes.DeadlineExceeded, // retry on timeout
    ),
  ),
)

// All calls through this connection automatically retry
chargeClient := pb.NewChargesClient(conn)

// No retry logic here — the interceptor handles it transparently
charge, err := chargeClient.CreateCharge(ctx, req)
```

Key consideration for financial operations: the retry interceptor must work correctly with idempotency. If `CreateCharge` is called with an idempotency key, retrying is safe because the server deduplicates. If the idempotency key was not sent, retrying `CreateCharge` may double-charge. The retry interceptor itself doesn't know this — the decision of which methods are safe to retry must be encoded either in the interceptor configuration (a list of safe-to-retry method names) or in the idempotency key contract of the downstream API.

gRPC's built-in retry policy (configured in the service config JSON, not in interceptors) is an alternative — it handles retries in the channel layer before the interceptor chain and supports `waitForReady` semantics. But the interceptor approach gives more control over backoff and retry decision logic.

**Q18. "How would you implement request-level timeout enforcement across all gRPC calls in a service without touching each handler?"**
A: A server-side timeout interceptor that enforces a maximum handler duration:

```go
func TimeoutInterceptor(timeout time.Duration) grpc.UnaryServerInterceptor {
  return func(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
  ) (interface{}, error) {
    // Use the shorter of: the existing deadline or our enforced timeout
    deadline := time.Now().Add(timeout)
    if existingDeadline, ok := ctx.Deadline(); ok {
      if existingDeadline.Before(deadline) {
        deadline = existingDeadline  // client deadline is tighter; honor it
      }
    }

    ctx, cancel := context.WithDeadline(ctx, deadline)
    defer cancel()

    // Run the handler in a goroutine so we can timeout independently
    type result struct {
      resp interface{}
      err  error
    }
    done := make(chan result, 1)

    go func() {
      resp, err := handler(ctx, req)
      done <- result{resp, err}
    }()

    select {
    case res := <-done:
      return res.resp, res.err
    case <-ctx.Done():
      return nil, status.Errorf(codes.DeadlineExceeded,
        "handler exceeded deadline for %s", info.FullMethod)
    }
  }
}

// Different timeout per method type — configure at server creation
server := grpc.NewServer(
  grpc.ChainUnaryInterceptor(
    TimeoutInterceptor(30 * time.Second),   // global 30s timeout
    // other interceptors
  ),
)
```

Note: the goroutine approach has a subtle issue — the handler goroutine may continue running after the interceptor returns a timeout error, leaking resources. Production-grade timeout enforcement requires that the handler itself respects context cancellation:
```go
// Handler must check ctx.Done() for long-running operations
func (s *Server) LongRunningOperation(ctx context.Context, req *pb.Request) (*pb.Response, error) {
  for _, item := range largeDataset {
    select {
    case <-ctx.Done():
      return nil, ctx.Err()  // honors the timeout set by the interceptor
    default:
      process(item)
    }
  }
}
```

The timeout interceptor sets the deadline; the handler's context-awareness enforces it. Both are necessary.

## Quick Reference

| Type | Signature (Go) | When it runs |
|--- |--- |--- |
| `UnaryServerInterceptor` | `(ctx, req, info, handler) → (resp, err)` | Before each unary RPC handler on the server |
| `UnaryClientInterceptor` | `(ctx, method, req, reply, cc, invoker, opts) → err` | Before each unary RPC call on the client |
| `StreamServerInterceptor` | `(srv, ss, info, handler) → err` | At stream open on the server |
| `StreamClientInterceptor` | `(ctx, desc, cc, method, streamer, opts) → (ClientStream, err)` | At stream creation on the client |

| Concern | Interceptor type | Key detail |
|--- |--- |--- |
| Auth (server) | `UnaryServerInterceptor` | Extract metadata; validate token; inject identity into `ctx` |
| Auth (client) | `UnaryClientInterceptor` | Inject `authorization` into outgoing metadata |
| Logging | Both unary server | Log before and after `handler(ctx, req)`; include `info.FullMethod` |
| Metrics | Both unary server | Timer wraps `handler(ctx, req)`; label by method and gRPC status code |
| Tracing | Both client and server | Extract/inject W3C `traceparent` via `metadataCarrier` |
| Retry | `UnaryClientInterceptor` | Retry on `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED` |
| Panic recovery | `UnaryServerInterceptor` | Must be outermost; `defer recover()` converts panic to `codes.Internal` |
| Timeout | `UnaryServerInterceptor` | `context.WithDeadline`; handler must respect `ctx.Done()` |
| Ordering | Chain | Recovery → Tracing → Logging → Metrics → Auth → RateLimit → Handler |
| NestJS | `NestInterceptor` | `intercept(context, next)`; `context.getType() === 'rpc'` for gRPC |
| NestJS auth | Guard preferred | Guards run before interceptors; cleaner for auth deny decisions |

**Tip for the interview:** Interceptor questions at 5 YOE level probe whether you understand the pattern as an architectural tool, not just a syntax exercise. Lead with the cross-cutting concern problem — 50 handlers, one auth check — and why interceptors are the solution. The technical details that separate senior answers: knowing that gRPC accepts only one interceptor natively (hence `ChainUnaryInterceptor`), understanding the ordering principle (recovery outermost, auth before business logic interceptors, tracing before logging so log lines include the trace ID), and explaining the streaming interceptor wrapper pattern — embedding `grpc.ServerStream` and overriding `SendMsg`/`RecvMsg` to intercept individual messages. For NestJS specifically, knowing the distinction between Guards (allow/deny, before interceptors), Interceptors (wrap execution, including response), and Pipes (transform/validate request data) shows you understand the full NestJS request pipeline rather than treating everything as an interceptor. The financial systems angle: if asked about retry interceptors, immediately note that retrying financial RPCs is only safe when idempotency keys are in use — the interceptor doesn't know this; the API contract must guarantee it.
