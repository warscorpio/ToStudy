# Code Generation Workflow (gRPC) — Interview Q&A (5 YOE Level)

---

## Section 1: Protocol Buffers and the Schema-First Approach

**Q1. What is gRPC and why is code generation central to it?**
A: gRPC is a high-performance RPC framework from Google that uses HTTP/2 for transport and Protocol Buffers (Protobuf) as the Interface Definition Language (IDL) and binary serialisation format. Unlike REST, where the API contract is typically documentation (OpenAPI/Swagger) that exists separately from the implementation, gRPC's contract is a `.proto` file from which both the client stub and the server interface are **generated**. This schema-first, code-generation-centric approach produces several advantages:

- **Type safety across languages**: The same `.proto` file generates a Go client, a TypeScript client, and a Java server — all guaranteed to agree on field names, types, and method signatures because they derive from the same source.
- **No handwritten serialisation**: Protobuf handles encoding/decoding. Fields are encoded by number, not by name — compact binary, faster than JSON.
- **Contract-first development**: Teams agree on the `.proto` file before writing a single line of business logic. The generated code is the contract enforcer — calling a method that doesn't exist or passing the wrong type is a compile error, not a runtime bug.

Code generation is not optional in gRPC — it is the mechanism by which `.proto` definitions become usable code. Understanding the generation pipeline is as fundamental as understanding the proto language itself.

**Q2. What is the structure of a `.proto` file and what are its key constructs?**
A: A proto file defines the schema for a service's messages and RPCs:

```protobuf
syntax = "proto3";                              // always proto3 for new work

package orders.v1;                              // namespacing; dots map to directories

option go_package = "github.com/org/gen/orders/v1";  // language-specific options

import "google/protobuf/timestamp.proto";       // well-known types
import "google/protobuf/empty.proto";

// Message: the unit of data
message Order {
  string  id         = 1;                       // field number 1 (wire identity)
  string  user_id    = 2;
  repeated OrderItem items    = 3;              // repeated = array/list
  OrderStatus        status   = 4;
  google.protobuf.Timestamp created_at = 5;
}

message OrderItem {
  string product_id = 1;
  int32  quantity   = 2;
  int64  price_cents = 3;
}

// Enum: always define a zero value (UNSPECIFIED for proto3 default)
enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;                 // required: proto3 default is 0
  ORDER_STATUS_PENDING     = 1;
  ORDER_STATUS_CONFIRMED   = 2;
  ORDER_STATUS_SHIPPED     = 3;
}

// Service: the RPC interface
service OrderService {
  rpc GetOrder    (GetOrderRequest)    returns (Order);                    // unary
  rpc ListOrders  (ListOrdersRequest)  returns (stream Order);             // server streaming
  rpc CreateOrder (stream CreateOrderRequest) returns (Order);             // client streaming
  rpc WatchOrders (WatchOrdersRequest) returns (stream Order);             // server streaming
}

message GetOrderRequest  { string order_id = 1; }
message ListOrdersRequest { string user_id = 1; int32 page_size = 2; }
```

**Q3. Why are field numbers critical and what are the rules around them?**
A: Protobuf encodes fields by their number on the wire, not by name. The field name is for human readability only — the number is what identifies the field in the binary encoding. This has three critical implications:

- **Never reuse a field number**: If field 3 was `string old_name` and you delete it, never assign `3` to a new field. Clients that had `old_name` will misinterpret the new field's bytes as `old_name`. Mark deleted field numbers as `reserved`:

```protobuf
message Order {
  reserved 3, 7;                    // numbers never to be reused
  reserved "old_name", "temp_field"; // names never to be reused
  string id = 1;
  string user_id = 2;
  // field 3 deleted; field 7 deleted
}
```

- **Field 1–15 use one byte on the wire** (for the field tag); fields 16–2047 use two bytes. Put your most frequently-occurring fields in the 1–15 range for encoding efficiency — particularly `repeated` fields that appear in every message instance.
- **Field types can only be changed within compatible wire types** (e.g., `int32` → `int64` is safe; `string` → `int32` is not). When in doubt: don't change field types — add a new field.

**Q4. What are the four gRPC communication patterns and when is each appropriate?**
A:
- **Unary RPC**: Single request → single response. The standard pattern for most operations — create, get, update, delete. Semantically closest to a REST API call.
- **Server streaming**: Single request → stream of responses. The server sends a sequence of messages until it is done. Used for: real-time event feeds (`WatchOrders`), large result sets (paginating a million records without client-initiated polls), progress reporting for long-running operations.
- **Client streaming**: Stream of requests → single response. The client sends a sequence of messages; the server responds once after processing all of them. Used for: bulk data ingestion (`UploadChunk` stream → `UploadResult`), aggregation across a time window.
- **Bidirectional streaming**: Stream of requests ↔ stream of responses. Both sides send independently. Used for: real-time chat, collaborative editing, live auction bidding — any protocol where both sides need to send without waiting for the other.

In practice, unary RPCs cover 80% of use cases. Server streaming is the second most common. Client and bidirectional streaming are specialised and add client complexity — choose them deliberately, not by default.

## Section 2: The Code Generation Pipeline

**Q5. How does `protoc` work and what is the role of plugins?**
A: `protoc` is the Protocol Buffer compiler — the canonical tool that parses `.proto` files and produces output. It operates in two phases:

1. **Parsing**: `protoc` reads and validates `.proto` files, resolving imports, checking type references, and building an internal descriptor (a structured representation of the schema).
2. **Code generation via plugins**: `protoc` itself only generates a binary descriptor. Actual language-specific code is produced by plugins — separate executables that `protoc` spawns as subprocesses, passing them the descriptor over stdin and collecting generated files from stdout.

```bash
protoc \
  --proto_path=protos \                    # where to find .proto files (-I)
  --proto_path=third_party/protos \        # additional import paths
  --go_out=gen/go \                        # output dir for protoc-gen-go plugin
  --go_opt=paths=source_relative \         # plugin-specific option
  --go-grpc_out=gen/go \                   # output dir for protoc-gen-go-grpc plugin
  --go-grpc_opt=paths=source_relative \
  protos/orders/v1/orders.proto            # source file(s)
```

Each `--<lang>_out` flag tells `protoc` to use the `protoc-gen-<lang>` plugin (which must be on `$PATH`). The plugin model is language-agnostic — any language can be supported by writing a plugin that reads the protoc descriptor format.

**Q6. What does each plugin typically generate and what is the distinction between message code and service code?**
A: Most gRPC setups use two plugins — one for messages, one for services:

**Message plugin** (e.g., `protoc-gen-go`, `protoc-gen-js`, `ts-proto`): Generates:
- Data classes / interfaces for each `message`
- Serialise/deserialise logic (encode to binary, decode from binary)
- JSON mapping (for REST-compatible codecs)
- Comparison and copy utilities

**Service plugin** (e.g., `protoc-gen-go-grpc`, `protoc-gen-grpc-java`): Generates:
- **Server interface**: An abstract interface or base class the server must implement — one method per RPC. The server registers a concrete implementation of this interface with the gRPC framework.
- **Client stub**: A concrete class the client uses to call the remote service — wraps the HTTP/2 transport and handles serialisation transparently. The client calls it like a local function.

```
// TypeScript (generated by ts-proto):

// Message (from message plugin)
export interface Order { id: string; userId: string; status: OrderStatus; }

// Client stub (from service plugin)
export interface OrderServiceClient {
  getOrder(request: GetOrderRequest, metadata?: Metadata): Promise<GetOrderResponse>;
  listOrders(request: ListOrdersRequest, metadata?: Metadata): Observable<Order>;
}

// Server interface (from service plugin)
export interface OrderServiceImplementation {
  getOrder(request: GetOrderRequest, context: ServerCallContext): Promise<GetOrderResponse>;
  listOrders(request: ListOrdersRequest, context: ServerCallContext): AsyncIterable<Order>;
}
```

**Q7. What is the recommended directory structure for proto files in a multi-service project?**
A: The canonical convention mirrors the package namespace as a directory hierarchy:

```
protos/
├── buf.yaml                         # buf configuration at root
├── orders/
│   └── v1/
│       └── orders.proto             # package orders.v1
├── payments/
│   └── v1/
│       └── payments.proto           # package payments.v1
├── users/
│   ├── v1/
│   │   └── users.proto             # package users.v1 (stable)
│   └── v2/
│       └── users.proto             # package users.v2 (new major version)
└── common/
    └── v1/
        └── types.proto              # shared types: Money, Address, etc.

gen/                                 # generated code (checked in or gitignored)
├── go/
│   ├── orders/v1/
│   └── payments/v1/
└── ts/
    ├── orders/v1/
    └── payments/v1/
```

Key conventions: the proto package name (`package orders.v1`) must match the directory structure. Version the package from day one — `orders.v1` not `orders` — so a future breaking version (`orders.v2`) can coexist without import conflicts. `common` or `shared` packages hold types used across services (monetary amounts, addresses, error details).

## Section 3: buf — Modern Proto Tooling

**Q8. What is buf and why does it replace raw protoc in modern workflows?**
A: `buf` is a CLI tool from Buf Technologies that modernises the proto development workflow. Raw `protoc` has several operational pain points: plugins must be individually installed and version-managed, proto import paths require careful `--proto_path` management, there is no built-in lint or breaking-change detection, and dependency management (importing googleapis, grpc-gateway, etc.) requires manual file copying.

buf solves all of these:
- **Managed plugins**: `buf generate` downloads and caches plugins from the Buf Schema Registry (BSR) — no manual `protoc-gen-*` installation.
- **Dependency management**: `buf.yaml` declares dependencies (`deps: [buf.build/googleapis/googleapis]`); `buf dep update` resolves them. No more copying proto files into `third_party/`.
- **Built-in lint**: `buf lint` enforces a configurable style guide (field naming, enum prefix conventions, package conventions) — catches style issues before code review.
- **Breaking change detection**: `buf breaking` compares the current proto against a baseline (main branch, last release) and reports breaking changes — prevents accidentally shipping a wire-incompatible change.
- **Buf Schema Registry**: A hosted registry for publishing and consuming proto schemas, analogous to npm for JavaScript packages.

**Q9. Walk through a complete `buf.yaml` and `buf.gen.yaml` configuration.**
A:

```yaml
# buf.yaml — project-level configuration
version: v1
name: buf.build/myorg/myprotos  # BSR module name (optional, needed for push)

deps:
  - buf.build/googleapis/googleapis      # google.protobuf.*, google.api.*
  - buf.build/grpc-ecosystem/grpc-gateway  # HTTP transcoding annotations

lint:
  use:
    - DEFAULT          # all default rules (naming, packages, comments)
  except:
    - PACKAGE_VERSION_SUFFIX  # opt-out if not using v1/v2 versioning

breaking:
  use:
    - FILE             # file-level breaking change detection (recommended)
    # - WIRE           # only wire-incompatible changes (more permissive)
    # - PACKAGE        # package-level (most permissive)
```

```yaml
# buf.gen.yaml — code generation configuration
version: v1
managed:
  enabled: true                              # auto-manage language options
  go_package_prefix:
    default: github.com/myorg/gen            # sets go_package for all files

plugins:
  # Go: message types
  - plugin: buf.build/protocolbuffers/go
    out: gen/go
    opt: paths=source_relative

  # Go: gRPC service stubs
  - plugin: buf.build/grpc/go
    out: gen/go
    opt:
      - paths=source_relative
      - require_unimplemented_servers=false  # set true to force server interface implementation

  # TypeScript: using ts-proto
  - plugin: buf.build/community/stephenh-ts-proto
    out: gen/ts
    opt:
      - esModuleInterop=true
      - outputServices=grpc-js             # generate @grpc/grpc-js compatible stubs
      - useOptionals=messages              # message fields are optional (not required)
      - stringEnums=true                   # enums as string literals (vs numbers)
      - onlyTypes=false                    # include runtime code, not just types
```

```bash
# Run the full generation pipeline
buf generate

# Check for breaking changes against the main branch
buf breaking --against '.git#branch=main'

# Lint all proto files
buf lint

# Update dependencies
buf dep update
```

**Q10. What does `buf lint` enforce and what are the most impactful rules?**
A: `buf lint` enforces a proto style guide. The most impactful default rules:

- **`ENUM_VALUE_PREFIX`**: Enum values must be prefixed with the enum name: `ORDER_STATUS_PENDING` not `PENDING`. Without this, name conflicts across enums in the same package are common.
- **`ENUM_ZERO_VALUE_SUFFIX`**: The zero-value enum entry must end in `_UNSPECIFIED`: `ORDER_STATUS_UNSPECIFIED = 0`. Enforces that the default (zero) value is explicitly meaningless, not an accidental valid state.
- **`FIELD_LOWER_SNAKE_CASE`**: Fields must use `snake_case` — `user_id`, not `userId`. Protobuf generates camelCase in languages that prefer it; the proto source stays snake_case.
- **`MESSAGE_PASCAL_CASE`**: Messages are `PascalCase`.
- **`RPC_REQUEST_RESPONSE_UNIQUE`**: Each RPC should have its own unique request and response message types (not reuse `Order` directly as a request). Makes it easy to add fields to request/response without affecting the underlying model message.
- **`RPC_REQUEST_STANDARD_NAME`**: Request messages are named `<RpcName>Request`; responses are `<RpcName>Response`.
- **`PACKAGE_VERSION_SUFFIX`**: Package names must end in a version suffix (`orders.v1`, not just `orders`).

These rules reflect hard-won lessons about proto maintenance: enum prefix collisions, accidental default-value semantics, and the pain of changing a shared message type because a request needed a new field.

## Section 4: TypeScript and Node.js Code Generation

**Q11. What are the main TypeScript/Node.js code generation options and how do they differ?**
A: The TypeScript ecosystem has several competing approaches:

- **`ts-proto`** (recommended): Generates TypeScript interfaces (not classes) for messages and typed client/server interfaces. Output is framework-agnostic — works with `@grpc/grpc-js`, nice-grpc, or Connect. Generates zero-dependency runtime code; the generated types are pure TypeScript. Most actively maintained. The `outputServices` option controls the generated service code style: `grpc-js` for `@grpc/grpc-js`-compatible code, `nice-grpc` for the nice-grpc framework.

- **`@grpc/proto-loader` (dynamic loading)**: Loads `.proto` files at runtime without code generation. No generated files; the client is dynamically typed (`any`-heavy). Faster to set up; zero type safety. Suitable for quick prototyping or tooling scripts but not production service-to-service communication where type safety matters.

- **`protoc-gen-ts`**: Generates TypeScript classes (not interfaces) with Protobuf-compatible serialisation methods. More verbose; less idiomatic TypeScript. Less popular than ts-proto for gRPC.

- **`connectrpc` / `@connectrpc/connect`**: Connect is a modern protocol compatible with gRPC, gRPC-web, and plain HTTP/1.1+JSON. `protoc-gen-es` generates clean TypeScript. Connect allows calling gRPC services directly from browsers without a gRPC-web proxy. Gaining significant adoption for new projects.

For TypeScript NestJS services: ts-proto with `outputServices=grpc-js` is the standard production choice.

**Q12. What does ts-proto-generated code look like and how do you use it?**
A: Given `orders.proto`, ts-proto generates approximately:

```typescript
// gen/ts/orders/v1/orders.ts (generated — do not edit)

// ─── Enums ───────────────────────────────────────────────────────────────────
export const OrderStatus = {
  ORDER_STATUS_UNSPECIFIED: "ORDER_STATUS_UNSPECIFIED",
  ORDER_STATUS_PENDING:     "ORDER_STATUS_PENDING",
  ORDER_STATUS_CONFIRMED:   "ORDER_STATUS_CONFIRMED",
} as const;
export type OrderStatus = typeof OrderStatus[keyof typeof OrderStatus];

// ─── Messages ─────────────────────────────────────────────────────────────────
export interface Order {
  id:        string;
  userId:    string;           // snake_case → camelCase conversion
  items:     OrderItem[];
  status:    OrderStatus;
  createdAt: Date | undefined; // Timestamp → Date
}

export interface GetOrderRequest  { orderId: string; }
export interface GetOrderResponse { order:   Order | undefined; }

// ─── Client ───────────────────────────────────────────────────────────────────
export interface OrderServiceClient {
  getOrder(request: GetOrderRequest, metadata?: Metadata): Promise<GetOrderResponse>;
  listOrders(request: ListOrdersRequest, metadata?: Metadata): Observable<Order>;
}

// ─── Server ───────────────────────────────────────────────────────────────────
export interface OrderServiceImplementation<CallContextExt = {}> {
  getOrder(
    request:  GetOrderRequest,
    context:  CallContext & CallContextExt,
  ): Promise<DeepPartial<GetOrderResponse>>;

  listOrders(
    request:  ListOrdersRequest,
    context:  CallContext & CallContextExt,
  ): ServerStreamingMethodResult<DeepPartial<Order>>;
}
```

Usage in a service:

```typescript
import { credentials } from '@grpc/grpc-js';
import { createChannel, createClient } from 'nice-grpc';
import { OrderServiceDefinition } from '../gen/ts/orders/v1/orders';

const channel = createChannel('orders-service:5001', credentials.createInsecure());
const client  = createClient(OrderServiceDefinition, channel);

// Fully typed — IDE autocomplete, compile-time argument checking
const response = await client.getOrder({ orderId: 'ord_123' });
console.log(response.order?.status);  // OrderStatus
```

**Q13. How do you integrate gRPC code generation into a NestJS service?**
A: NestJS supports gRPC via `@nestjs/microservices`. Two approaches:

**Approach A — Dynamic proto loading (no codegen, less type safety)**:
```typescript
// main.ts
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.GRPC,
  options: {
    package: 'orders.v1',
    protoPath: join(__dirname, '../protos/orders/v1/orders.proto'),
    url: '0.0.0.0:5001',
  },
});

// Controller: no generated types; manual interface definitions
@Controller()
export class OrdersController {
  @GrpcMethod('OrderService', 'GetOrder')
  async getOrder(data: { orderId: string }): Promise<{ order: any }> { ... }
}
```

**Approach B — ts-proto generated types (recommended)**:
```typescript
// Generate types with ts-proto, import them in service code
import { GetOrderRequest, GetOrderResponse, OrderStatus } from '../gen/ts/orders/v1/orders';

@Controller()
export class OrdersController {
  @GrpcMethod('OrderService', 'GetOrder')
  async getOrder(data: GetOrderRequest): Promise<GetOrderResponse> {
    const order = await this.ordersService.findById(data.orderId);
    return {
      order: {
        id:        order.id,
        userId:    order.userId,
        status:    OrderStatus.ORDER_STATUS_CONFIRMED,
        items:     [],
        createdAt: order.createdAt,
      },
    };
  }
}

// Client (calling another gRPC service from NestJS)
@Module({
  imports: [
    ClientsModule.register([{
      name:      'ORDERS_PACKAGE',
      transport: Transport.GRPC,
      options: {
        package:   'orders.v1',
        protoPath: join(__dirname, '../protos/orders/v1/orders.proto'),
        url:       'orders-service:5001',
      },
    }]),
  ],
})
export class AppModule {}

@Injectable()
export class OrdersClientService implements OnModuleInit {
  private orderService: OrderServiceClient;  // ts-proto generated interface

  constructor(@Inject('ORDERS_PACKAGE') private client: ClientGrpc) {}

  onModuleInit() {
    this.orderService = this.client.getService<OrderServiceClient>('OrderService');
  }

  getOrder(id: string): Observable<GetOrderResponse> {
    return this.orderService.getOrder({ orderId: id });
  }
}
```

## Section 5: Breaking Changes and Versioning

**Q14. What changes to a proto file are safe vs. breaking?**
A: The wire compatibility rules are the foundation of proto versioning. "Breaking" means existing clients or servers will fail or produce incorrect behaviour:

**SAFE — backward and forward compatible:**
- Adding a new field with a new field number (old clients ignore unknown fields; old servers send defaults for missing fields)
- Adding a new enum value (unknown enum values are preserved as-is in proto3)
- Adding a new RPC method to a service (old clients simply don't call it)
- Adding a new message type
- Renaming a field (wire format uses numbers; names are not on the wire — but JSON serialisation breaks)
- Adding new options or comments
- Changing field names (wire-safe but breaks JSON; be cautious)

**BREAKING — will cause client/server failures:**
- Deleting a field (old clients that read that field will get a zero value; if another field is later assigned the old number, data corruption occurs)
- Changing a field number (the wire encoding changes; existing data is misread)
- Changing a field type incompatibly (`string` → `int32`; different wire type = parse error)
- Removing an RPC method (clients calling it get `UNIMPLEMENTED`)
- Changing an RPC's streaming mode (`unary` → `server streaming`) — different HTTP/2 framing
- Making a `repeated` field singular (loses multiple values)
- Changing a service name or package name (clients look up services by these names)

```protobuf
// SAFE evolution example
message Order {
  string  id      = 1;
  string  user_id = 2;
  reserved 3;                    // safely removed; field number protected
  reserved "legacy_field";       // name protected from reuse
  OrderStatus status = 4;
  string  notes  = 5;            // new field added safely
}
```

**Q15. How does `buf breaking` detect breaking changes and how do you integrate it into a PR workflow?**
A: `buf breaking` compares the current state of the proto files against a reference (a git branch, tag, or a pre-built buf image) and reports any changes that violate the configured rule set:

```bash
# Compare against main branch
buf breaking --against '.git#branch=main'

# Compare against a specific tag (for release-based workflows)
buf breaking --against '.git#tag=v1.2.0'

# Compare against a published BSR module version
buf breaking --against 'buf.build/myorg/myprotos:v1.2.0'
```

Output for a breaking change:
```
protos/orders/v1/orders.proto:12:3:Field "3" on message "Order" changed type from "TYPE_STRING" to "TYPE_INT32".
protos/orders/v1/orders.proto:8:1:Field "2" with name "user_id" on message "Order" was deleted.
```

CI integration:

```yaml
# .github/workflows/proto-check.yml
name: Proto Checks

on: [push, pull_request]

jobs:
  proto:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }     # full history needed for git comparison

      - uses: bufbuild/buf-setup-action@v1
        with: { version: '1.28.0' }

      - name: Lint
        run: buf lint

      - name: Check breaking changes
        run: buf breaking --against '.git#branch=main'

      - name: Verify generated code is up to date
        run: |
          buf generate
          git diff --exit-code gen/   # fails if generated files changed
```

The "verify generated code is up to date" step is critical in "check-in generated code" workflows — it ensures developers ran `buf generate` locally and committed the result. If they forgot, CI fails with a diff of the stale generated files.

**Q16. How do you manage proto versioning for a breaking API change?**
A: When a breaking change is unavoidable (a fundamental redesign of the API), the standard pattern is a parallel version package:

```
protos/
├── orders/
│   ├── v1/
│   │   └── orders.proto       # package orders.v1 — stable, never broken
│   └── v2/
│       └── orders.proto       # package orders.v2 — new design
```

```protobuf
// orders/v2/orders.proto
syntax = "proto3";
package orders.v2;             // different package = different generated types

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
  // new v2-only features here
}
```

The v1 service continues running. The v2 service is deployed alongside it. Clients migrate at their own pace by updating their import to `orders.v2`. Once all clients have migrated, v1 can be deprecated and eventually decommissioned. This is the same versioning model as REST's `/v1/` and `/v2/` URL prefixes, but enforced at the proto package level rather than the URL.

Never modify `v1` in a breaking way — even internal services. The `buf breaking` check in CI enforces this: the CI check for `v1/` files is configured to fail on any breaking change.

## Section 6: CI/CD and Team Workflows

**Q17. Should generated code be checked into source control or generated at build time? What are the trade-offs?**
A: Both approaches are used in production; the choice depends on team size and tooling maturity:

**Check in generated code:**
- Pros: IDEs work immediately without running generation; CI doesn't need proto tooling on every runner; generated code diffs are visible in PRs (reviewers see what the contract change actually produces); no risk of generation producing different output on different machines due to plugin version mismatches.
- Cons: PRs include generated file noise; developers must remember to regenerate after proto changes; risk of generated files drifting from protos if they forget.
- Mitigation: CI step that re-runs `buf generate` and fails if there's a diff (`git diff --exit-code gen/`).

**Generate at build time:**
- Pros: No generated file noise in PRs; generated code is always in sync; `gen/` can be in `.gitignore`.
- Cons: Every developer and CI runner needs `buf` + all plugins installed and version-pinned; build is slower; language server / IDE may not find generated types until after first build; debugging generation issues in CI is harder.
- Mitigation: Docker-based generation (`docker run --rm -v $(pwd):/workspace bufbuild/buf generate`) pins the exact version.

**Current industry consensus**: Check in generated code for polyglot teams, and add the CI drift check. Generate at build time only if the team is comfortable with the tooling overhead and uses a monorepo where everyone runs the same dev container.

**Q18. How do you structure a monorepo for multiple services sharing proto definitions?**
A: The cleanest monorepo structure separates proto definitions, generated code, and service implementations:

```
monorepo/
├── protos/                  # source of truth — proto files only
│   ├── buf.yaml
│   ├── buf.gen.yaml
│   ├── orders/v1/
│   ├── payments/v1/
│   └── common/v1/
│
├── gen/                     # checked-in generated code (never edit manually)
│   ├── go/
│   │   ├── orders/v1/       # Go generated types + stubs
│   │   └── payments/v1/
│   └── ts/
│       ├── orders/v1/       # TypeScript generated types + stubs
│       └── payments/v1/
│
├── services/
│   ├── orders-service/      # Node.js service; imports from ../../gen/ts/
│   ├── payments-service/    # Go service; imports from ../../gen/go/
│   └── api-gateway/         # REST gateway; imports from ../../gen/ts/
│
└── Makefile
    # gen: cd protos && buf generate
    # lint: cd protos && buf lint
    # breaking: cd protos && buf breaking --against .git#branch=main
```

The `protos/` directory is the only place `.proto` files live. Services import from `gen/` — never from `protos/` directly (that would require protoc/buf in the service's runtime). The `Makefile` or `package.json` scripts provide `make gen`, `make lint`, `make breaking` — one command to regenerate everything.

## Section 7: gRPC Error Handling and Interceptors

**Q19. How does gRPC error handling work and what status codes matter most?**
A: gRPC uses a set of standard status codes (analogous to HTTP status codes) transmitted as gRPC metadata alongside the response. Unlike HTTP, gRPC errors are strongly typed — the status code is an integer, and each has a defined semantic:

| Code | Name | Use case |
|---|---|---|
| 0 | OK | Success |
| 3 | INVALID_ARGUMENT | Client sent bad data (validation failure) — do not retry |
| 4 | DEADLINE_EXCEEDED | Request timed out — may retry with a new deadline |
| 5 | NOT_FOUND | Resource doesn't exist |
| 6 | ALREADY_EXISTS | Duplicate create attempt |
| 7 | PERMISSION_DENIED | Authorisation failure (user lacks permission) |
| 8 | RESOURCE_EXHAUSTED | Rate limited, quota exceeded |
| 13 | INTERNAL | Server-side bug — do not retry |
| 14 | UNAVAILABLE | Server temporarily down — retry with backoff |
| 16 | UNAUTHENTICATED | Missing or invalid credentials |

```typescript
import { status } from '@grpc/grpc-js';
import { RpcException } from '@nestjs/microservices';

// Throwing a typed gRPC error from a NestJS gRPC handler
@GrpcMethod('OrderService', 'GetOrder')
async getOrder(data: GetOrderRequest): Promise<GetOrderResponse> {
  if (!data.orderId) {
    throw new RpcException({
      code: status.INVALID_ARGUMENT,
      message: 'order_id is required',
    });
  }
  const order = await this.ordersService.findById(data.orderId);
  if (!order) {
    throw new RpcException({ code: status.NOT_FOUND, message: `Order ${data.orderId} not found` });
  }
  return { order };
}
```

Client-side, catch gRPC errors by checking `error.code`:
```typescript
try {
  const response = await client.getOrder({ orderId });
} catch (error: any) {
  if (error.code === status.NOT_FOUND) { /* handle */ }
  if (error.code === status.UNAVAILABLE) { /* retry */ }
}
```

**Q20. How do gRPC interceptors (middleware) work and what do you use them for?**
A: gRPC interceptors are middleware that wraps RPC calls on either the client or server side — analogous to Express middleware or NestJS guards/interceptors but at the transport layer:

**Server interceptors** (run on the gRPC server for every incoming RPC):
```typescript
// nice-grpc server interceptor example
const authInterceptor: ServerInterceptor = async (call, options, next) => {
  const token = call.metadata.get('authorization')?.[0];
  if (!token || !verifyJWT(token)) {
    throw new ServerError(status.UNAUTHENTICATED, 'Invalid token');
  }
  // Attach decoded user to context
  return next(call, { ...options, user: decodeJWT(token) });
};

const loggingInterceptor: ServerInterceptor = async (call, options, next) => {
  const start = Date.now();
  try {
    const result = await next(call, options);
    logger.info({ rpc: call.method, ms: Date.now() - start, status: 'ok' });
    return result;
  } catch (err) {
    logger.error({ rpc: call.method, ms: Date.now() - start, err });
    throw err;
  }
};

createServer({ interceptors: [loggingInterceptor, authInterceptor] });
```

**Client interceptors** (run on the gRPC client for every outgoing RPC):
```typescript
const deadlineInterceptor: ClientInterceptor = async (call, options, next) => {
  // Propagate deadline from inbound context to outbound calls
  const deadline = new Date(Date.now() + 5000); // 5s default
  return next(call, { ...options, deadline });
};

const retryInterceptor: ClientInterceptor = async (call, options, next) => {
  for (let attempt = 1; attempt <= 3; attempt++) {
    try {
      return await next(call, options);
    } catch (err: any) {
      if (err.code === status.UNAVAILABLE && attempt < 3) {
        await sleep(Math.pow(2, attempt) * 100);  // exponential backoff
        continue;
      }
      throw err;
    }
  }
};
```

Interceptors are the correct layer for: JWT validation, logging, metrics (Prometheus histogram per RPC), request tracing (propagate OpenTelemetry context), deadline propagation, and retry logic.

## Section 8: Scenario / System Design Questions

**Q21. "Your team has 3 microservices sharing proto definitions. A new engineer deletes a field from `Order` and pushes directly. What breaks and how do you prevent this in the future?"**
A: Deleting field 3 (`repeated OrderItem items`) is a breaking change on two axes:

**Wire-level break**: Any client or server that was built before the deletion and still uses the old generated code will either send field 3 (which the new server ignores — data silently lost) or expect field 3 in the response (receiving zero-value/empty-array — data silently missing). No error is thrown; the break is silent and data-corrupting.

**Generated-code break**: Services that import the generated types referencing the deleted field fail to compile — `order.items` is undefined in the new generated code.

**Prevention — four layers**:

1. **`buf breaking` in CI**: The PR check runs `buf breaking --against .git#branch=main`. The deleted field is detected and the check fails. The PR cannot merge without addressing the finding. This catches it at code review, before deployment.

2. **Reserved field numbers**: After deleting the field, the engineer adds `reserved 3; reserved "items";` to the proto. `buf lint` enforces the `RESERVED_FIELD` rule — catch the omission in lint.

3. **Branch protection + required checks**: Configure the repository so the `Proto Checks` CI job is required to pass before merging. No bypassing with a direct push to main.

4. **Field deprecation before deletion**: The correct process is to mark the field deprecated first (`[deprecated = true]`), coordinate all services to stop using it, wait at least one release cycle, then remove it. Teach this in the team's proto contribution guide.

**Q22. "You need to expose a gRPC service to a web browser (JavaScript). gRPC-over-HTTP/2 doesn't work natively in browsers. What are your options?"**
A: Browsers cannot make raw gRPC calls — HTTP/2 framing is not accessible from browser JavaScript (fetch/XHR use HTTP/1.1 or HTTP/2 HTTP semantics, not the raw binary gRPC framing). Three options:

**gRPC-Web**: A protocol extension that encodes gRPC calls in a way HTTP/1.1 can transport. Requires a proxy (Envoy, `grpcwebproxy`) between the browser and the gRPC server that translates gRPC-Web ↔ gRPC. Generated client code uses `protoc-gen-grpc-web`. The proxy adds operational overhead; limited to unary and server-streaming (no client or bidirectional streaming).

**Connect Protocol** (`@connectrpc/connect`): A newer protocol from Buf Technologies that is compatible with gRPC, gRPC-Web, and standard HTTP/1.1+JSON. The `protoc-gen-es` plugin generates a client that speaks all three protocols. A browser calling a Connect-compatible server (using `connect-es`) works without any proxy — the request is a standard HTTP POST with a Protobuf or JSON body. Connect is rapidly becoming the preferred choice for new browser-facing APIs.

**REST transcoding (gRPC-Gateway)**: Use `protoc-gen-grpc-gateway` to generate a REST reverse proxy from annotations in the `.proto` file. Browsers call REST endpoints; the gateway translates to gRPC internally:

```protobuf
import "google/api/annotations.proto";

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order) {
    option (google.api.http) = {
      get: "/v1/orders/{order_id}"   // REST endpoint annotation
    };
  }
}
```

For new projects: Connect is the cleanest solution. For existing gRPC services that must add browser support: gRPC-Web with Envoy proxy is the battle-tested path. For teams that prefer REST semantics for browser clients: gRPC-Gateway.

**Q24. "You're designing a gRPC API for an order service. The `GetOrder` RPC is called by 5 different services and is your highest-traffic endpoint. A request needs to support partial field selection to reduce payload size. How do you design this in proto?"**
A: Use `google.protobuf.FieldMask` — the standard proto pattern for partial field selection (Google uses this in their own APIs, including the Cloud APIs):

```protobuf
import "google/protobuf/field_mask.proto";

message GetOrderRequest {
  string order_id = 1;
  google.protobuf.FieldMask field_mask = 2;  // e.g., "order.id,order.status"
}

message GetOrderResponse {
  Order order = 1;
}
```

Client usage:
```typescript
const response = await client.getOrder({
  orderId: 'ord_123',
  fieldMask: { paths: ['order.id', 'order.status', 'order.created_at'] },
});
// Response: Order with only id, status, createdAt populated; other fields zero-valued
```

Server implementation:
```typescript
@GrpcMethod('OrderService', 'GetOrder')
async getOrder(req: GetOrderRequest): Promise<GetOrderResponse> {
  const order = await this.ordersService.findById(req.orderId);
  if (!req.fieldMask || req.fieldMask.paths.length === 0) {
    return { order };       // full order
  }
  // Apply field mask — only include requested paths
  const masked = applyFieldMask(order, req.fieldMask.paths);
  return { order: masked };
}
```

FieldMask is the correct tool here — not a custom `fields: string[]` array that reinvents the wheel. Callers that need full orders don't send a mask; callers that need only `status` for a dashboard polling every 5 seconds send `paths: ['order.status']` and get a tiny response. The savings compound at high traffic: a 5KB order payload becoming a 50-byte status-only response = 100× bandwidth reduction for polling consumers.

| Concept                     | Detail                                                                                       |
|---                          |---                                                                                           |
| `.proto` syntax             | `syntax = "proto3"` — always use proto3 for new services                                    |
| Field numbers               | Wire identity; never reuse; 1–15 = 1 byte; `reserved N;` guards deleted numbers            |
| Four RPC types              | Unary, server streaming, client streaming, bidirectional streaming                          |
| `protoc`                    | Proto compiler; uses plugins for language-specific output                                    |
| `buf generate`              | Modern replacement for raw `protoc`; managed plugins; no local install needed               |
| `buf lint`                  | Style enforcement: naming, enum prefixes, request/response uniqueness                       |
| `buf breaking`              | Breaking change detection against a baseline; run in CI on every PR                         |
| ts-proto                    | Best TypeScript codegen: interfaces, no classes, framework-agnostic                         |
| Safe proto changes          | Add field, add enum value, add RPC, rename field (wire-safe but JSON breaks)               |
| Breaking proto changes      | Remove field, change field number/type, remove RPC, change streaming mode                  |
| `reserved`                  | Protects field numbers and names from reuse after deletion                                  |
| Version packages            | `orders.v1` → `orders.v2` for breaking redesigns; run both in parallel                     |

| Browser + gRPC              | gRPC-Web (needs proxy) or Connect protocol (no proxy, native HTTP)                         |
| CI drift check              | `buf generate && git diff --exit-code gen/` — fails if generated code is stale             |

## The Core Mental Model

```
gRPC workflow = Proto-first contract → Generate → Implement → Deploy

The .proto file is the single source of truth.
  It defines the contract before any code is written.
  All generated code derives from it.
  Never edit generated files — edit the proto and regenerate.

The generation pipeline:
  .proto  →  buf generate  →  generated types + stubs
                               ↓
                         import in service code
                               ↓
                         implement server interface
                         use client stub

The three rules of proto maintenance:
  1. Never reuse a field number (use reserved)
  2. Never break existing fields (add new ones instead)
  3. Version your package from day one (orders.v1)

buf over protoc:
  buf lint      → style consistency across the team
  buf breaking  → safety net against accidental breaking changes
  buf generate  → reproducible, version-pinned codegen

The CI checklist:
  ✓ buf lint          (style)
  ✓ buf breaking      (wire safety)
  ✓ buf generate + git diff --exit-code  (no stale generated code)
  ✓ all three required to merge — no exceptions

When proto evolves:
  Safe   → add fields, add RPCs, add enum values
  Unsafe → delete anything, renumber anything, retype anything
  Breaking redesign → new package (v2), run both until all clients migrated
```

The strongest signal: knowing that adding a new field is safe (old clients get zero values, old servers ignore unknown fields) while deleting a field is silently data-corrupting — not a compile error. And knowing that `buf breaking` is what prevents this from reaching production. Connecting this to your NestJS experience — "in our service, we use ts-proto for generated types and `@GrpcMethod` decorators, and we run `buf lint + buf breaking` in CI on every PR" — shows you've done this in production, not just read about it.
