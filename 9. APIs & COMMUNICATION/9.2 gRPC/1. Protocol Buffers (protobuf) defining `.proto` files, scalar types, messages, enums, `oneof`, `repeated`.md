# Protocol Buffers: `.proto` Files, Types, Messages, and gRPC — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Protocol Buffers Exist

**Q1. What problems do Protocol Buffers solve that JSON and XML do not?**
A: JSON and XML are self-describing formats — field names travel with every message. This is convenient for human readability and ad-hoc tooling, but creates three problems at scale:

- **Wire size**: A JSON payment event `{"payment_id":"pay_001","amount":500.00,"currency":"INR","status":"PENDING"}` is ~70 bytes. The field names (`payment_id`, `amount`, `currency`, `status`) account for ~40 of those bytes — more than half the payload is schema, not data. In a system processing 10,000 payment events per second, that is 400KB/s of redundant schema information on the wire. Protobuf encodes only field numbers (integers) and values — the same message is 15–25 bytes.
- **Parsing cost**: JSON parsers scan byte-by-byte for delimiters, parse string field names, and perform string comparisons to dispatch to struct fields. Protobuf's binary format encodes type and field number in a single byte tag, enabling direct memory writes without string scanning. Protobuf deserialization is typically 5–10× faster than JSON for equivalent messages.
- **No schema enforcement at the format level**: JSON has no built-in type system. A field declared as an integer can carry a string; a required field can be absent; a new field added by a producer silently appears in the consumer's parsed object with no indication it was unexpected. Errors are runtime, not compile-time. Protobuf's `.proto` schema defines types, required/optional semantics, and field numbers — the schema is the contract, enforced by generated code.

Protobuf trades human readability (binary is not directly inspectable) and schema-per-message self-description for compactness, parsing speed, and schema-enforced contracts. These trade-offs make it the dominant serialization format for high-throughput internal service communication — the use case gRPC is built for.

**Q2. What is the relationship between Protocol Buffers and gRPC?**
A: Protocol Buffers and gRPC are separate but tightly integrated technologies, both developed at Google:

- **Protocol Buffers** is a serialization format and IDL (Interface Definition Language). It defines how data is encoded on the wire and provides a language-neutral schema definition system. Protobuf can be used without gRPC — as a storage format, a Kafka message payload, a file format.
- **gRPC** is an RPC framework built on top of HTTP/2 that uses Protocol Buffers as its default serialization format and IDL. A `.proto` file in a gRPC context defines both the data structures (messages) and the service interface (RPCs — Remote Procedure Calls). The `protoc` compiler generates both serialization code (from message definitions) and client/server stub code (from service definitions).

```
.proto file defines:
  message PaymentRequest { ... }    ← data structure (pure protobuf)
  message PaymentResponse { ... }   ← data structure (pure protobuf)

  service PaymentService {          ← gRPC service definition
    rpc CreatePayment (PaymentRequest) returns (PaymentResponse);
  }

protoc generates:
  PaymentRequest.js / PaymentRequest.java   ← serialization/deserialization
  PaymentServiceClient.js                   ← gRPC client stub
  PaymentServiceServer.js                   ← gRPC server interface
```

gRPC uses HTTP/2 as the transport layer, which gives it multiplexed streams, header compression, and binary framing. Protobuf provides the payload encoding. Together they form the standard for high-performance internal API communication in microservices — the alternative to REST/JSON for service-to-service calls where latency, throughput, and schema contracts matter.

## Section 2: `.proto` File Structure

**Q3. What is the structure of a `.proto` file and what are its required and optional elements?**
A: A `.proto` file is a schema definition document. Its structure:

```protobuf
// Syntax declaration — always the first non-comment line
syntax = "proto3";

// Package declaration — prevents name collisions across schemas
// In gRPC: becomes the namespace in generated code
package com.example.payments.v1;

// Import other .proto files
import "google/protobuf/timestamp.proto";
import "google/protobuf/wrappers.proto";

// Options — metadata for code generation
option java_package = "com.example.payments";
option java_outer_classname = "PaymentProto";
option go_package = "github.com/example/payments/proto/v1";

// Message definitions
message PaymentRequest {
  string payment_id  = 1;
  int64  amount      = 2;
  string currency    = 3;
}

// Enum definitions
enum PaymentStatus {
  PAYMENT_STATUS_UNSPECIFIED = 0;
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_APPROVED    = 2;
  PAYMENT_STATUS_FAILED      = 3;
}

// Service definition (gRPC-specific)
service PaymentService {
  rpc CreatePayment (PaymentRequest) returns (PaymentResponse);
}
```

**Required elements:**
- `syntax = "proto3";` — must be the first non-empty, non-comment line. Specifies proto3 syntax (the current standard; proto2 is legacy).

**Optional but conventionally present:**
- `package` — prevents naming conflicts; maps to namespaces in generated code.
- `option` directives — control code generation behavior per language.
- `import` — includes definitions from other `.proto` files.

**Key structural rules:**
- Comments use `//` (single-line) or `/* */` (block).
- Field numbers (the integers after `=`) must be unique within a message and cannot be reused once assigned.
- Reserved field numbers and names can be declared to prevent future reuse: `reserved 4, 5; reserved "old_field";`.

**Q4. What is the difference between proto2 and proto3, and why does proto3 matter for field defaults?**
A: Proto2 (the original) and proto3 (the current standard) differ in three significant ways:

**Required/optional field labels:**
- Proto2: fields are explicitly `required`, `optional`, or `repeated`. `required` fields must always be present; missing them is a parse error.
- Proto3: all singular fields are implicitly optional. There is no `required` keyword. A missing field is filled with its type's default value on deserialization.

**Default values:**
- Proto2: if a field is `optional` and absent, you can distinguish "absent" from "present with default value" — `hasField()` returns false for absent fields.
- Proto3: all singular fields have implicit defaults (0 for numbers, `""` for strings, `false` for bools). A field with value 0 is **not encoded on the wire** — it is indistinguishable from a missing field on deserialization. This is the most operationally significant difference.

```protobuf
// proto3
message Payment {
  int64 amount = 1;  // default: 0
}
// A Payment with amount=0 serializes identically to a Payment with amount absent.
// The receiver cannot tell whether 0 was set explicitly or the field was omitted.
```

This has real consequences: if `amount = 0` is a valid business value (a zero-value payment for free items), you cannot distinguish it from "amount was not set" in proto3 without using wrapper types (`google.protobuf.Int64Value`) or `oneof`.

**Unknown fields:**
- Proto2: unknown fields (from a newer schema version) were discarded by default.
- Proto3: unknown fields are preserved and re-serialized, enabling better forward compatibility — a message passed through an intermediary service that doesn't know about new fields will not lose them.

The production recommendation: always use proto3 for new schemas. The implicit-optional model simplifies schema evolution; the preserved unknown fields improve forward compatibility. Proto2 is maintained for backward compatibility with existing schemas.

## Section 3: Scalar Types

**Q5. What are the scalar types in proto3 and what are their encoding trade-offs?**
A: Proto3 has 15 scalar types, grouped by their wire encoding:

**Variable-length integers (varint encoding — 1 to 10 bytes):**

| Proto type | Wire size | Language mapping | Notes |
|---|---|---|---|
| `int32` | 1–5 bytes | int (Java), number (JS) | Negative values encoded as 10 bytes — use `sint32` for negatives |
| `int64` | 1–10 bytes | long (Java), bigint (JS) | Same negative-value problem — use `sint64` |
| `uint32` | 1–5 bytes | unsigned int | No negative encoding waste |
| `uint64` | 1–10 bytes | unsigned long | No negative encoding waste |
| `sint32` | 1–5 bytes | int | ZigZag encoding — efficient for negative values |
| `sint64` | 1–10 bytes | long | ZigZag encoding — efficient for negative values |
| `bool` | 1 byte | boolean | Encoded as 0 or 1 |

**Fixed-width integers (always 4 or 8 bytes):**

| Proto type | Wire size | Notes |
|---|---|---|
| `fixed32` | 4 bytes | Better than `uint32` for values always > 228 |
| `fixed64` | 8 bytes | Better than `uint64` for values always > 256 |
| `sfixed32` | 4 bytes | Fixed signed 32-bit |
| `sfixed64` | 8 bytes | Fixed signed 64-bit |

**Floating point (always 4 or 8 bytes):**

| Proto type | Wire size | Notes |
|---|---|---|
| `float` | 4 bytes | IEEE 754 single precision — never for money |
| `double` | 8 bytes | IEEE 754 double precision — never for money |

**Variable-length bytes:**

| Proto type | Wire size | Notes |
|---|---|---|
| `string` | Length-prefixed UTF-8 | Always valid UTF-8; use `bytes` for arbitrary binary |
| `bytes` | Length-prefixed | Arbitrary byte sequences; base64 in JSON mapping |

**The varint encoding mechanism:**
Varint is a variable-length encoding where each byte uses 7 bits for data and 1 bit to indicate if more bytes follow. Small integers encode efficiently: 1 encodes as `0x01` (1 byte); 300 encodes as `0xAC 0x02` (2 bytes); 2^28 encodes as 5 bytes. This is why `int32` is preferred over `fixed32` for values that are usually small (counters, IDs with short numeric value) — they encode more compactly.

**The money type warning:**
`float` and `double` are IEEE 754 floating point — they cannot represent most decimal fractions exactly. Never use them for monetary amounts. The correct approach:
- Store amounts as integer minor units: `int64 amount_paise = 1;` (100 paise = ₹1). Always unambiguous; no floating point error.
- Or use `google.protobuf.Bytes` with a `decimal` encoding convention — but the integer minor-unit approach is simpler and the industry standard.

**Q6. How does ZigZag encoding work for `sint32` and `sint64`, and when do you need it?**
A: Standard varint encoding of negative integers is pathological: -1 as a two's complement 32-bit integer is `0xFFFFFFFF`, which encodes as 10 bytes in varint (the full bit width). A message with `int32 balance = -500` wastes 10 bytes on a value that is semantically tiny.

ZigZag encoding maps signed integers to unsigned integers in a way that keeps small-magnitude values small:

```
ZigZag mapping:
   0 → 0
  -1 → 1
   1 → 2
  -2 → 3
   2 → 4
  -n → 2n - 1
   n → 2n

Formula: (n << 1) ^ (n >> 31)   for sint32
         (n << 1) ^ (n >> 63)   for sint64
```

After ZigZag, -1 becomes 1 (encodes as 1 byte), -500 becomes 999 (encodes as 2 bytes), -32768 becomes 65535 (encodes as 3 bytes). The varint encodes the ZigZag-transformed value — small magnitude in either direction = small wire size.

**When to use `sint32`/`sint64` over `int32`/`int64`:**
- Fields that frequently hold negative values: temperature deltas, relative positions, signed counters, credit/debit amounts where negative means debit.
- Fields where the sign is a common case, not an exception.

**When `int32`/`int64` is fine:**
- Fields that are always non-negative: IDs, counts, sizes, timestamps (epoch seconds).
- Fields where negative is rare or impossible.

The encoding choice is transparent to application code — generated getters/setters deal with normal signed integers. The difference is purely in wire size and is invisible to callers.

## Section 4: Messages

**Q7. How do nested messages work in proto3, and what are the design patterns for structuring them?**
A: Messages can be nested — a field's type can be another message. Nested messages encode as length-delimited byte sequences on the wire (wire type 2).

```protobuf
// Flat structure — all fields at top level
message PaymentFlat {
  string payment_id   = 1;
  int64  amount       = 2;
  string currency     = 3;
  string user_id      = 4;
  string user_email   = 5;
  string user_phone   = 6;
  string merchant_id  = 7;
  string merchant_name = 8;
}

// Nested structure — domain objects composed
message Payment {
  string  payment_id = 1;
  Money   amount     = 2;
  User    user       = 3;
  Merchant merchant  = 4;
  PaymentStatus status = 5;
}

message Money {
  int64  amount_minor = 1;  // e.g., 50000 = ₹500.00
  string currency     = 2;  // ISO 4217: "INR", "USD"
}

message User {
  string user_id = 1;
  string email   = 2;
  string phone   = 3;
}

message Merchant {
  string merchant_id = 1;
  string name        = 2;
}
```

**Nested message design patterns:**

**Reusable value types**: `Money`, `Address`, `PhoneNumber`, `DateRange` — types that appear in multiple messages. Define them once; import and reuse. Avoid copy-pasting fields across messages.

**Inline (locally scoped) nested messages**: When a message type is only meaningful in the context of its parent, define it inside the parent:
```protobuf
message Payment {
  message Metadata {
    string order_ref    = 1;
    string merchant_ref = 2;
  }
  Metadata metadata = 6;
}
// Referenced as Payment.Metadata in generated code
```

**Maps as nested messages**: Proto3's `map<K, V>` is syntactic sugar for a repeated nested message with `key` and `value` fields — `map<string, string>` compiles to a message type with a `key: string` field and a `value: string` field, repeated. Map fields do not guarantee ordering and cannot be `repeated` themselves.

```protobuf
message Payment {
  map<string, string> labels = 7;  // e.g., {"region": "south", "channel": "app"}
}
```

**Well-known types**: Google provides pre-defined messages for common types:
```protobuf
import "google/protobuf/timestamp.proto";
import "google/protobuf/duration.proto";
import "google/protobuf/wrappers.proto";

message Payment {
  google.protobuf.Timestamp created_at   = 8;   // structured UTC timestamp
  google.protobuf.Duration  timeout      = 9;   // duration value
  google.protobuf.Int64Value optional_amount = 10; // nullable int64 (see Q8)
}
```

**Q8. How do you represent optional/nullable fields in proto3, and what is the wrapper type pattern?**
A: Proto3's default behavior: a field with value 0 (or `""`, or `false`) is not encoded on the wire, making it indistinguishable from a missing field. For most fields this is fine — "amount not set" and "amount is 0" being the same is safe. But for truly nullable fields where 0 is a meaningful value, or where "set to false" is distinct from "not set", you need explicit optionality.

**Three approaches:**

**Approach 1 — `optional` keyword (proto3.15+):**
```protobuf
message Payment {
  optional int64 discount_amount = 1;  // has presence: can distinguish 0 from absent
}
```
The `optional` keyword restores field presence tracking — `hasDiscountAmount()` returns false if not set, true if set to 0. Available in proto3 since the 3.15 release; supported in protoc 3.12+. The cleanest solution for new schemas.

**Approach 2 — Well-known wrapper types:**
```protobuf
import "google/protobuf/wrappers.proto";

message Payment {
  google.protobuf.Int64Value  discount_amount  = 1;  // nullable int64
  google.protobuf.StringValue optional_ref     = 2;  // nullable string
  google.protobuf.BoolValue   is_test_payment  = 3;  // nullable bool
}
```
Wrapper types are messages with a single `value` field. A null is represented as the message being absent (no encoding); a zero is represented as the message present with `value = 0`. They work in all proto3 versions but are verbose and have JSON mapping quirks.

**Approach 3 — `oneof` for explicit nullability (see Q11):**
```protobuf
message Payment {
  oneof discount {
    google.protobuf.NullValue no_discount    = 1;
    int64                     discount_amount = 2;
  }
}
```
Explicit: either `no_discount` or `discount_amount` is set. Verbose but self-documenting.

**The production recommendation**: Use `optional` (proto3.15+) for numeric and bool fields that need presence tracking. Use wrapper types only when compatibility with older protoc versions is required. Avoid `oneof` for nullability unless the explicit documentation value is worth the verbosity.

## Section 5: Enums

**Q9. How do enums work in proto3 and what are the naming conventions and forward-compatibility rules?**
A: An enum defines a named set of integer constants. Every enum must have a zero value as its first entry — proto3 requires this because the default value for enum fields is always the zero value (matching the implicit default for unset fields).

```protobuf
enum PaymentStatus {
  // Convention: PREFIX_UNSPECIFIED for the zero value
  PAYMENT_STATUS_UNSPECIFIED = 0;
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_APPROVED    = 2;
  PAYMENT_STATUS_FAILED      = 3;
  PAYMENT_STATUS_REFUNDED    = 4;
  PAYMENT_STATUS_CANCELLED   = 5;
}

message Payment {
  PaymentStatus status = 1;  // defaults to PAYMENT_STATUS_UNSPECIFIED (0) if not set
}
```

**Naming conventions:**
- Enum names are `PascalCase`: `PaymentStatus`.
- Enum values are `UPPER_SNAKE_CASE` with the enum name as a prefix: `PAYMENT_STATUS_PENDING`, not just `PENDING`. This prefix is required because enum values are scoped to the package, not the enum type — two enums in the same package cannot have the same value name without the prefix disambiguating them.
- The zero value conventionally ends in `_UNSPECIFIED` or `_UNKNOWN` — it signals "this field was not intentionally set" rather than being a real business state.

**The `_UNSPECIFIED` zero value pattern:**
```protobuf
// BAD — zero value is a real state
enum PaymentStatus {
  PENDING  = 0;   // ← danger: unset field == PENDING; looks like PENDING was set
  APPROVED = 1;
}

// GOOD — zero value is sentinel for "not set"
enum PaymentStatus {
  PAYMENT_STATUS_UNSPECIFIED = 0;   // ← default: caller must explicitly set a real status
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_APPROVED    = 2;
}
```
With `_UNSPECIFIED` as zero, a receiver can detect that the sender did not set the status field — `status == PAYMENT_STATUS_UNSPECIFIED` means "this message did not carry a real status." Without it, `PENDING = 0` makes an unset field indistinguishable from intentionally-PENDING.

**Forward compatibility for enums — unknown values:**
Proto3 preserves unknown enum values received from a newer schema. If a consumer receives a message with `status = 6` (a value added in a later schema version it doesn't know about), proto3 represents it as the integer `6` in the field rather than crashing. The consumer's generated code must handle this with a default case:

```javascript
switch (payment.status) {
  case PaymentStatus.PAYMENT_STATUS_PENDING:   handlePending(); break;
  case PaymentStatus.PAYMENT_STATUS_APPROVED:  handleApproved(); break;
  default:
    // Future enum value: log and treat as unknown
    logger.warn(`Unknown payment status: ${payment.status}`);
    handleUnknown();
}
```

Never omit the `default` case in enum switch statements — a new status value added by a producer will silently fall through and cause undefined behavior if there is no default handling.

**`allow_alias` — multiple names for the same value:**
```protobuf
enum PaymentStatus {
  option allow_alias = true;
  PAYMENT_STATUS_UNSPECIFIED = 0;
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_AWAITING    = 1;  // alias for PENDING (same value)
}
```
Used when migrating from one name to another — both names are valid during the transition. Without `allow_alias = true`, duplicate values are a compile error.

## Section 6: `oneof`

**Q10. What is `oneof` and what problem does it solve?**
A: `oneof` declares that at most one field in a group can be set at a time. Setting a field in a `oneof` automatically clears any previously set field in the same group. It enforces mutual exclusivity at the message level.

```protobuf
message PaymentMethod {
  oneof method {
    CardDetails    card    = 1;
    UpiDetails     upi     = 2;
    NachDetails    nach    = 3;
    WalletDetails  wallet  = 4;
  }
}

message CardDetails {
  string last_four     = 1;
  string network       = 2;  // "VISA", "MASTERCARD", "RUPAY"
  string expiry_month  = 3;
  string expiry_year   = 4;
}

message UpiDetails {
  string vpa           = 1;  // e.g., "user@okaxis"
  string psp           = 2;  // "GPAY", "PHONEPE", "PAYTM"
}

message NachDetails {
  string account_number = 1;
  string ifsc_code      = 2;
  string mandate_id     = 3;
}
```

Without `oneof`, a message could technically have both `card` and `upi` fields set — the schema has no way to express the mutual exclusivity. `oneof` makes this constraint explicit and enforced: `setUpi()` clears `card` if it was previously set.

**Wire encoding of `oneof`:**
On the wire, only the set field is encoded — there is no `oneof` tag. The receiver determines which field is set by which field number is present in the encoded bytes. This means `oneof` has no wire overhead compared to regular optional fields; it is purely a semantic constraint enforced in generated code.

**`oneof` case detection in generated code:**
```javascript
// Node.js / TypeScript (generated)
const paymentMethod = response.getPaymentMethod();

switch (paymentMethod.getMethodCase()) {
  case PaymentMethod.MethodCase.CARD:
    const card = paymentMethod.getCard();
    console.log('Card:', card.getLastFour());
    break;
  case PaymentMethod.MethodCase.UPI:
    const upi = paymentMethod.getUpi();
    console.log('UPI VPA:', upi.getVpa());
    break;
  case PaymentMethod.MethodCase.METHOD_NOT_SET:
    throw new Error('Payment method not specified');
}
```

The `getMethodCase()` pattern lets the consumer detect which field is set without checking each field's presence individually.

**Q11. What are the constraints and gotchas of `oneof`?**
A: Several constraints in `oneof` that cause production surprises:

**`oneof` fields cannot be `repeated`:**
```protobuf
// INVALID — compile error
message Foo {
  oneof bar {
    repeated string names = 1;  // ← ERROR: repeated fields not allowed in oneof
  }
}
```
`oneof` is for mutually exclusive singular values. If you need mutually exclusive lists, use a `oneof` of message types where each message contains the list:
```protobuf
message Foo {
  oneof bar {
    NameList  names  = 1;
    EmailList emails = 2;
  }
}
message NameList  { repeated string values = 1; }
message EmailList { repeated string values = 1; }
```

**Setting a `oneof` field clears all others — silently:**
```javascript
const payment = new PaymentMethod();
payment.setCard(cardDetails);    // card is set
payment.setUpi(upiDetails);      // card is now cleared; only upi is set
// payment.getCard() → null
```
This silent clearing is by design but causes bugs when code sets multiple fields in a `oneof` across different functions without knowing they are mutually exclusive. Make `oneof` grouping visible in code reviews.

**`oneof` and schema evolution — field number reuse:**
If you remove a field from a `oneof` and add a new field with the same field number, old clients that receive a message with the new field will interpret it as the old field type — potentially crashing or silently misinterpreting data. Reserve removed field numbers:
```protobuf
message PaymentMethod {
  reserved 3;                 // ← was WalletDetails wallet = 3; now removed
  reserved "wallet";          // ← reserve the name too
  oneof method {
    CardDetails card = 1;
    UpiDetails  upi  = 2;
    // wallet removed; field number 3 reserved
  }
}
```

**`oneof` and default values:**
If no field in a `oneof` is set, all `getX()` calls return the default value for their type (null for messages, 0 for numbers, `""` for strings). The only way to distinguish "field set to default" from "no field set" is `getMethodCase()`. Always use case detection, not null checks on individual fields, when working with `oneof`.

## Section 7: `repeated` Fields

**Q12. How do `repeated` fields work, and how are they encoded on the wire?**
A: A `repeated` field declares that the field can hold zero or more values — the proto3 equivalent of an array or list. Ordering is preserved.

```protobuf
message BulkPaymentRequest {
  repeated PaymentRequest payments  = 1;
  repeated string         tags      = 2;
  repeated int64          amounts   = 3;
}
```

**Wire encoding — packed vs. unpacked:**

For scalar numeric types (`int32`, `int64`, `float`, `double`, `bool`, enums), proto3 uses **packed encoding** by default. All values are concatenated into a single length-delimited blob rather than one wire entry per value:

```
Unpacked encoding (proto2 default for repeated scalars):
  tag(field=3, wire_type=varint) value(100)
  tag(field=3, wire_type=varint) value(200)
  tag(field=3, wire_type=varint) value(300)
  → 3 separate tag-value pairs

Packed encoding (proto3 default for repeated scalars):
  tag(field=3, wire_type=length_delimited) length(N) value(100) value(200) value(300)
  → 1 tag + 1 length + N values
```

Packed encoding is more compact for repeated numeric fields — the field tag is written once instead of once per element. For a list of 100 payment amounts, packed saves ~200 bytes of tag overhead.

Repeated message fields are not packed — each message is a separate length-delimited blob:
```
tag(field=1, wire_type=length_delimited) length(N) [PaymentRequest bytes]
tag(field=1, wire_type=length_delimited) length(M) [PaymentRequest bytes]
```

**`repeated` vs. `map`:**
`repeated` preserves order and allows duplicate values. `map<K, V>` is an unordered set of unique-keyed pairs. Use `repeated` for ordered lists where duplicates may exist; use `map` for key-value lookup structures:
```protobuf
// Use repeated for ordered list of payments
repeated Payment payments = 1;

// Use map for key-value metadata
map<string, string> metadata = 2;

// Use repeated for list of pairs where key can repeat or order matters
repeated Label labels = 3;
message Label { string key = 1; string value = 2; }
```

**Empty `repeated` fields:**
An empty `repeated` field produces no bytes on the wire — it is indistinguishable from a `repeated` field that was never set. Unlike singular fields where 0 and "not set" may differ semantically, an empty list and a missing list are always equivalent in proto3. This is almost always the right semantic for lists (an empty list of payments and an absent list of payments mean the same thing), but note it if your API needs to distinguish the two.

**Q13. What are the performance implications of large `repeated` fields?**
A: Large repeated message fields are proto3's most significant performance concern because each element is serialized/deserialized independently with no streaming:

```
BulkPaymentRequest with 10,000 PaymentRequest messages:
  Serialization: 10,000 × (serialize PaymentRequest + write length prefix + write tag)
  Deserialization: 10,000 × (read tag + read length + deserialize PaymentRequest into object)
  Memory: 10,000 PaymentRequest objects allocated simultaneously
```

**Practical limits and mitigations:**

**Pagination for large collections:**
```protobuf
message ListPaymentsRequest {
  string page_token = 1;   // opaque cursor from previous response
  int32  page_size  = 2;   // max 100; server may return fewer
}

message ListPaymentsResponse {
  repeated Payment payments       = 1;
  string          next_page_token = 2;  // empty string = no more pages
  int32           total_count     = 3;
}
```
Never return unbounded `repeated` fields for collection APIs. Always paginate. 100 items per page is a common default; 1,000 is typically the maximum before response times degrade.

**Server streaming for bulk operations:**
gRPC's server-streaming RPC is the idiomatic solution for large result sets — the server sends a stream of individual messages rather than one message with a large `repeated` field:
```protobuf
service PaymentService {
  // Bad: one large response with all payments
  rpc ListAllPayments (ListRequest) returns (ListResponse);

  // Good: stream individual payments
  rpc StreamPayments (StreamRequest) returns (stream Payment);
}
```
With streaming, memory usage is bounded — the client processes each `Payment` as it arrives rather than waiting for all 10,000 to be deserialized before processing the first one.

**Batch size limits enforced server-side:**
```protobuf
message BulkCreateRequest {
  repeated PaymentRequest payments = 1;  // server enforces max 100 per request
}
```
Document and enforce maximum batch sizes. A `repeated` field with 100,000 entries will serialize to hundreds of megabytes, exceed gRPC's default 4MB message size limit, and cause `ResourceExhausted` errors.

## Section 8: gRPC Service Definitions and RPC Patterns

**Q14. What are the four gRPC communication patterns and how are they defined in `.proto`?**
A: gRPC leverages HTTP/2's bidirectional streaming to support four communication patterns, each expressed with different `stream` keywords in the service definition:

**1. Unary RPC — one request, one response:**
```protobuf
service PaymentService {
  rpc CreatePayment (CreatePaymentRequest) returns (CreatePaymentResponse);
}
```
The standard request/response pattern. Equivalent to a REST POST. The client sends one message; the server processes it and sends one message back. Most gRPC RPCs are unary.

**2. Server streaming — one request, stream of responses:**
```protobuf
service PaymentService {
  rpc StreamPaymentEvents (StreamRequest) returns (stream PaymentEvent);
}
```
The client sends one request; the server sends a sequence of responses over a single HTTP/2 stream, closing it when done. Use for: paginating large result sets, real-time event feeds (payment status updates), bulk export operations.

```javascript
// Client-side usage (Node.js)
const call = client.streamPaymentEvents({ user_id: 'usr_42' });
call.on('data', (event) => processEvent(event));
call.on('end',  ()      => console.log('Stream ended'));
call.on('error',(err)   => handleError(err));
```

**3. Client streaming — stream of requests, one response:**
```protobuf
service PaymentService {
  rpc BulkCreatePayments (stream CreatePaymentRequest) returns (BulkCreateResponse);
}
```
The client sends a stream of requests; the server accumulates them and sends one response when the client closes the stream. Use for: bulk ingestion (uploading thousands of payments), chunked file upload to a gRPC service.

```javascript
// Client-side usage (Node.js)
const call = client.bulkCreatePayments((err, response) => {
  if (err) handleError(err);
  else     console.log(`Created ${response.count} payments`);
});

for (const payment of payments) {
  call.write(payment);
}
call.end();
```

**4. Bidirectional streaming — stream of requests, stream of responses:**
```protobuf
service PaymentService {
  rpc ReconcilePayments (stream ReconcileRequest) returns (stream ReconcileResponse);
}
```
Both client and server can send messages independently on the same HTTP/2 stream. The streams are independent — the server can respond to request 1 before request 2 arrives; the client can send request 3 while still processing response 1. Use for: real-time bidirectional communication (chat, collaborative tools), pipeline processing where response can be sent as each item is processed.

**The HTTP/2 advantage:**
All four patterns multiplex over a single TCP connection. A gRPC client can have 100 concurrent in-flight RPCs on one TCP connection — no head-of-line blocking (HTTP/1.1's major limitation), no connection pool overhead. This makes gRPC dramatically more efficient than REST/HTTP1.1 for high-concurrency service-to-service communication.

**Q15. How do you handle errors in gRPC, and how does the status code system work?**
A: gRPC uses its own status code system, distinct from HTTP status codes. A gRPC response always carries a status code; a non-OK status replaces the response message (you either get data or an error, not both in most patterns).

**gRPC status codes (the most important ones):**

```
OK (0)                  → Success
CANCELLED (1)           → Client cancelled the RPC
UNKNOWN (2)             → Catch-all; unexpected server error
INVALID_ARGUMENT (3)    → Client sent invalid data (equivalent to HTTP 400/422)
DEADLINE_EXCEEDED (4)   → Operation timed out (client or server deadline)
NOT_FOUND (5)           → Resource does not exist (HTTP 404)
ALREADY_EXISTS (6)      → Resource already exists (HTTP 409)
PERMISSION_DENIED (7)   → Authenticated but not authorized (HTTP 403)
RESOURCE_EXHAUSTED (8)  → Rate limit exceeded; quota exhausted (HTTP 429)
FAILED_PRECONDITION (9) → Operation invalid for current state (payment not PENDING)
ABORTED (10)            → Concurrency conflict; retry at higher level (HTTP 409 optimistic lock)
OUT_OF_RANGE (11)       → Value out of valid range (page size > maximum)
UNIMPLEMENTED (12)      → RPC not implemented (HTTP 501)
INTERNAL (13)           → Internal server error (HTTP 500)
UNAVAILABLE (14)        → Server temporarily unavailable; safe to retry (HTTP 503)
DATA_LOSS (15)          → Unrecoverable data loss
UNAUTHENTICATED (16)    → Not authenticated (HTTP 401)
```

**Retryability:**
- **Safe to retry**: `UNAVAILABLE`, `DEADLINE_EXCEEDED` (if the operation is idempotent).
- **Not safe to retry without idempotency key**: `UNKNOWN`, `INTERNAL` (the operation may have succeeded).
- **Never retry**: `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED` — the error is deterministic; retrying will return the same error.

**Rich error details with `google.rpc.Status`:**
```protobuf
// google/rpc/status.proto (used by gRPC internally)
message Status {
  int32  code    = 1;  // gRPC status code
  string message = 2;  // human-readable error message
  repeated google.protobuf.Any details = 3;  // structured error details
}
```

The `details` field can carry typed error information using `google.rpc.*` types:
```protobuf
import "google/rpc/error_details.proto";

// For validation errors: which fields are invalid
google.rpc.BadRequest {
  repeated FieldViolation field_violations = 1;
  message FieldViolation {
    string field       = 1;  // e.g., "payment.amount"
    string description = 2;  // e.g., "Amount must be positive"
  }
}

// For rate limiting: when to retry
google.rpc.RetryInfo {
  google.protobuf.Duration retry_delay = 1;
}

// For quota errors: which quota was exceeded
google.rpc.QuotaFailure {
  repeated Violation violations = 1;
  message Violation {
    string subject     = 1;  // e.g., "payments/per_minute"
    string description = 2;  // e.g., "Exceeded 100 requests per minute"
  }
}
```

Using rich error details allows clients to extract structured information from errors without parsing strings — a validation error tells the client exactly which field is invalid; a quota error tells the client exactly which quota was hit and how long to wait.

## Section 9: Schema Evolution and Compatibility

**Q16. What are the rules for backward-compatible changes to `.proto` files?**
A: Proto3 schema evolution follows stricter rules than JSON because the binary encoding uses field numbers, not field names. The field number is the permanent identity of a field — changing it is always a breaking change, regardless of what the field is named.

**Safe changes (backward compatible):**

```protobuf
// Adding a new field — always safe
message Payment {
  string payment_id = 1;
  int64  amount     = 2;
  string currency   = 3;   // ← added in v2; old receivers ignore it (unknown field)
  string merchant_id = 4;  // ← added in v3; preserved by proto3 unknown field handling
}
```

Adding a new field with a new field number is always safe — old receivers skip unknown field numbers; new receivers get the new field. Never reuse field numbers.

**Safe changes table:**

| Change | Safe? | Reason |
|---|---|---|
| Add a new field (new number) | ✅ | Old receivers ignore unknown fields |
| Remove a field (reserve the number) | ✅ | New receivers get default for absent field |
| Rename a field | ✅ | Wire format uses field numbers, not names |
| Change field from `optional` to `repeated` | ⚠️ | Old sender sends one; new receiver sees list of one. Reverse breaks old receivers |
| Change `int32` to `int64` | ✅ | Both use varint encoding; compatible |
| Change `int32` to `fixed32` | ❌ | Different wire type; old values misinterpreted |
| Change `string` to `bytes` | ✅ | Same wire type (length-delimited) |
| Change `string` to `int32` | ❌ | Different wire types |
| Add a value to an enum | ✅ | Old receivers get the integer; must handle unknown in switch |
| Remove a value from an enum | ⚠️ | Old messages may carry the removed value; new receivers must handle it |
| Change message type of a field | ❌ | Wire encoding is incompatible |
| Add a `oneof` wrapping existing fields | ❌ | Changes semantics; concurrent set no longer allowed |

**The reserved keyword — the most important evolution safety tool:**
```protobuf
message Payment {
  reserved 3, 5 to 7;              // ← field numbers 3, 5, 6, 7 can never be reused
  reserved "old_status", "legacy"; // ← field names can never be reused

  string payment_id  = 1;
  int64  amount      = 2;
  // field 3 was string currency — removed; reserved so it's never reassigned
  string merchant_id = 4;
  // fields 5-7 were part of an old address block — removed; reserved range
}
```

If field number 3 (`currency`) is removed and a new developer adds `string country = 3;`, old clients that still have the old schema will interpret `country` data as `currency` — silently corrupting data. `reserved 3;` makes this a compile error. Always reserve removed field numbers and names.

## Section 10: Scenario / System Design Style Questions

**Q17. "Design the `.proto` schema for a payment service with payment creation, status retrieval, and a streaming event feed."**
A:

```protobuf
syntax = "proto3";

package com.example.payments.v1;

import "google/protobuf/timestamp.proto";

option java_package         = "com.example.payments.v1";
option java_multiple_files  = true;

// ─── Shared value types ───────────────────────────────────────────────────────

message Money {
  int64  amount_minor = 1;  // e.g., 50000 = ₹500.00 (in paise)
  string currency     = 2;  // ISO 4217: "INR", "USD"
}

enum PaymentStatus {
  PAYMENT_STATUS_UNSPECIFIED = 0;
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_PROCESSING  = 2;
  PAYMENT_STATUS_APPROVED    = 3;
  PAYMENT_STATUS_FAILED      = 4;
  PAYMENT_STATUS_REFUNDED    = 5;
  PAYMENT_STATUS_CANCELLED   = 6;
}

// ─── Payment method — mutually exclusive via oneof ────────────────────────────

message PaymentMethod {
  oneof method {
    CardPayment   card   = 1;
    UpiPayment    upi    = 2;
    NachPayment   nach   = 3;
  }
}

message CardPayment {
  string last_four    = 1;
  string network      = 2;  // "VISA", "MASTERCARD", "RUPAY"
  string expiry_month = 3;
  string expiry_year  = 4;
}

message UpiPayment {
  string vpa = 1;  // "user@okaxis"
  string psp = 2;  // "GPAY", "PHONEPE"
}

message NachPayment {
  string mandate_id     = 1;
  string account_number = 2;
  string ifsc_code      = 3;
}

// ─── Core payment message ─────────────────────────────────────────────────────

message Payment {
  string                    payment_id    = 1;
  string                    user_id       = 2;
  Money                     amount        = 3;
  PaymentStatus             status        = 4;
  PaymentMethod             method        = 5;
  string                    merchant_id   = 6;
  google.protobuf.Timestamp created_at    = 7;
  google.protobuf.Timestamp updated_at    = 8;
  map<string, string>       metadata      = 9;
  string                    failure_reason = 10; // non-empty only if status=FAILED
}

// ─── RPC request/response messages ───────────────────────────────────────────

message CreatePaymentRequest {
  string        user_id     = 1;
  Money         amount      = 2;
  PaymentMethod method      = 3;
  string        merchant_id = 4;
  string        idempotency_key = 5;  // client-generated UUID; deduplication
  map<string, string> metadata = 6;
}

message CreatePaymentResponse {
  Payment payment = 1;
}

message GetPaymentRequest {
  string payment_id = 1;
}

message GetPaymentResponse {
  Payment payment = 1;
}

message ListPaymentsRequest {
  string user_id    = 1;
  int32  page_size  = 2;  // max 100
  string page_token = 3;  // cursor from previous response
  repeated PaymentStatus status_filter = 4;  // filter by status
}

message ListPaymentsResponse {
  repeated Payment payments        = 1;
  string          next_page_token  = 2;  // empty = last page
  int32           total_count      = 3;
}

message StreamPaymentEventsRequest {
  string user_id   = 1;
  string from_payment_id = 2;  // start from this payment (empty = from beginning)
}

// ─── Service definition ───────────────────────────────────────────────────────

service PaymentService {
  // Unary: create a payment
  rpc CreatePayment (CreatePaymentRequest) returns (CreatePaymentResponse);

  // Unary: retrieve a specific payment
  rpc GetPayment (GetPaymentRequest) returns (GetPaymentResponse);

  // Unary with pagination: list payments
  rpc ListPayments (ListPaymentsRequest) returns (ListPaymentsResponse);

  // Server streaming: real-time payment event feed
  rpc StreamPaymentEvents (StreamPaymentEventsRequest) returns (stream Payment);
}
```

**Design decisions explained:**

- `Money` as a nested message with `amount_minor` (integer paise) and `currency` — avoids floating point, encodes compactly, reusable across all payment-related messages.
- `PaymentMethod` with `oneof` — enforces that exactly one payment method is present; the case detection pattern in generated code makes switch logic clean.
- `idempotency_key` in `CreatePaymentRequest` — gRPC has no built-in idempotency mechanism; the key must be in the message payload and the server must implement dedup logic (same pattern as the HTTP `Idempotency-Key` header).
- `repeated PaymentStatus status_filter` in `ListPaymentsRequest` — allows filtering by multiple statuses in one request without a separate field per status.
- `StreamPaymentEvents` as server streaming — bounded memory on the client (processes each `Payment` as it arrives); the server can push updates as status changes without polling.

**Q18. "A colleague adds a new field `risk_score` (float) to the Payment message for a fraud scoring feature. What problems do you identify and how do you fix them?"**
A: Three problems:

**Problem 1 — Wrong scalar type for a score field:**
`float` is 32-bit IEEE 754 — only ~7 significant decimal digits. A risk score might be `0.9234567` — representable as float, but if the score is later used in mathematical operations or comparisons, floating point drift accumulates. More importantly, the convention in proto3 for fields that interact with financial or precision-sensitive data is to use `double` (64-bit) or to encode scores as integers (e.g., `int32 risk_score_bps = N;` where bps = basis points, 10000 = 1.0).

```protobuf
// Avoid: float precision issues
float risk_score = 11;

// Better: double for decimal scores 0.0–1.0
double risk_score = 11;

// Best for financial precision: integer basis points
int32 risk_score_bps = 11;  // 9234 = 0.9234; lossless, compact
```

**Problem 2 — `float`/`double` default value is 0.0, not distinguishable from "not scored":**
A payment that has not been through fraud scoring will have `risk_score = 0.0` — the same as a payment that scored 0.0 (zero risk). Consumers cannot distinguish "not yet scored" from "scored zero risk." This is the proto3 default value problem for numeric fields.

```protobuf
// Fix: use optional to distinguish "not set" from 0.0
optional double risk_score = 11;

// Or: wrap in a message that can be absent
google.protobuf.DoubleValue risk_score = 11;

// Or: add a separate has_risk_score bool (ugly but explicit)
bool   has_risk_score = 11;
double risk_score     = 12;
```

**Problem 3 — No field number or reservation coordination:**
If the colleague picked field number 11 but another team member simultaneously added `string payment_gateway_ref = 11;` in a parallel branch, a field number collision occurs. When both changes are merged, two fields share the same number — one silently overwrites the other's data for all existing messages.

```protobuf
// Fix: field number registry in the .proto file comments or a central allocation table
// Reserve a range for each team/feature:
// 1-10:   core payment fields (reserved for this schema's maintainers)
// 11-20:  fraud and risk fields (fraud team)
// 21-30:  reporting fields (analytics team)
// 100+:   extension fields

// In the file, add:
reserved 12 to 20;   // fraud team range; only 11 is used so far
```

**Q19. "Your Node.js service receives a gRPC request, calls a downstream gRPC service, and the downstream call times out. How do you propagate the deadline and handle the error correctly?"**
A: gRPC deadlines are the distributed systems equivalent of timeouts, but they propagate through the call chain — a deadline set by the original client applies to the entire chain of calls, not just the first hop.

```javascript
// NestJS / Node.js gRPC deadline propagation

// Inbound handler
async createPayment(
  request: CreatePaymentRequest,
  metadata: Metadata,
  call: ServerUnaryCall<CreatePaymentRequest, CreatePaymentResponse>
): Promise<CreatePaymentResponse> {

  // Extract the deadline from the inbound call context
  // The deadline was set by the original caller and applies to everything we do
  const deadline = call.getDeadline(); // Date object or Infinity

  // Propagate deadline to downstream gRPC call
  // Do NOT set a fresh deadline — use the remaining time from the original deadline
  const remainingMs = deadline === Infinity
    ? 5000                                     // no deadline from caller; use service default
    : Math.max(0, deadline.getTime() - Date.now()) - 50; // 50ms buffer for overhead

  if (remainingMs <= 0) {
    // Deadline already exceeded before we could call downstream
    throw new RpcException({
      code: Status.DEADLINE_EXCEEDED,
      message: 'Deadline exceeded before downstream call',
    });
  }

  try {
    const downstreamDeadline = new Date(Date.now() + remainingMs);

    const fraudResult = await this.fraudServiceClient
      .scorePayment(request, { deadline: downstreamDeadline })
      .toPromise();

    return this.buildResponse(request, fraudResult);

  } catch (err) {
    if (err.code === Status.DEADLINE_EXCEEDED) {
      // Downstream timed out — re-throw as DEADLINE_EXCEEDED (same code)
      // The caller's deadline logic will handle it
      throw new RpcException({
        code: Status.DEADLINE_EXCEEDED,
        message: `Fraud scoring deadline exceeded`,
      });
    }

    if (err.code === Status.UNAVAILABLE) {
      // Downstream is down — this is retryable from the caller's perspective
      throw new RpcException({
        code: Status.UNAVAILABLE,
        message: 'Fraud service temporarily unavailable',
      });
    }

    // Internal error — do not expose downstream error details to caller
    this.logger.error('Downstream fraud service error', { err, payment_id: request.payment_id });
    throw new RpcException({
      code: Status.INTERNAL,
      message: 'Payment processing failed',
    });
  }
}
```

**Key principles demonstrated:**

- **Propagate, don't reset deadlines**: A fresh 5-second deadline on every hop means a chain of 10 services could take 50 seconds total — the original caller's 3-second deadline is meaningless. Always propagate the remaining deadline from the inbound call.
- **50ms buffer**: Reserve a small margin for serialization overhead and network RTT — a downstream call that uses exactly the remaining deadline will sometimes fail due to overhead even when there is technically time left.
- **Map status codes, don't expose internals**: A `DEADLINE_EXCEEDED` from fraud scoring propagates as `DEADLINE_EXCEEDED` to the caller (they know the chain timed out). An `INTERNAL` from fraud scoring becomes your service's `INTERNAL` with a generic message — your caller should not see fraud service error details.
- **`UNAVAILABLE` is retryable**: The caller can retry with the same request (if idempotent). `INTERNAL` from a downstream is not necessarily retryable — the operation may have succeeded before the error.

## The Core Mental Model

```
Protobuf = schema-first binary serialization

The field number is the identity, not the name:
  Field names exist for humans and generated code.
  The wire format uses only field numbers.
  Renaming a field is safe. Changing its number is always breaking.
  Reserved numbers are the safety fence — always reserve removed numbers.

Wire encoding intuition:
  Small integers → use int32/int64 (varint; small values = small bytes)
  Frequently negative → use sint32/sint64 (ZigZag; avoids 10-byte negatives)
  Money amounts → use int64 in minor units (paise, cents); never float/double
  Large fixed-size values → use fixed32/fixed64 (predictable; faster for search)
  Lists → repeated (packed for scalars; one entry per message for messages)
  Key-value → map<K, V>

oneof = mutual exclusivity enforced by the schema:
  Use for: payment method variants, response result vs error, union types
  Never use repeated inside oneof
  Always use getXCase() for detection, not null checks
  Reserve removed oneof field numbers — same rule as regular fields

proto3 default value trap:
  0, "", false, empty list, absent message — all identical on the wire
  A field set to 0 is NOT encoded; a missing field deserializes to 0
  These are indistinguishable without optional (proto3.15+) or wrapper types
  The _UNSPECIFIED zero enum value is the idiomatic guard against this trap

gRPC evolution contract:
  Unary for most things; server streaming for large result sets
  Deadline propagation is mandatory — never set fresh deadlines on each hop
  Status codes map to retryability: UNAVAILABLE=retry, INVALID_ARGUMENT=don't
  Rich error details (google.rpc.*) replace string-parsing for structured errors
  idempotency_key in the message payload — gRPC has no built-in dedup

Schema evolution is a shared contract:
  Producer and consumer teams must coordinate on field number allocation
  A central field number registry (comments or a separate document) prevents collisions
  Every removed field gets reserved — no exceptions
  Unknown fields are preserved in proto3 — forward compatibility is structural
```

**Tip for the interview:** Protobuf questions at 5 YOE almost always escalate to one of three places: (1) the field number permanence rule — knowing that field names can be freely renamed (wire format is numbers) but field numbers can never be reused, and that `reserved` is the mechanism that enforces this, signals you have operated schemas in production through multiple versions; (2) the proto3 default value trap — understanding that `int64 amount = 0` and "amount not set" are indistinguishable without `optional` or wrapper types, and that `PAYMENT_STATUS_UNSPECIFIED = 0` is not bureaucratic pedantry but the only way to detect an unset enum field, separates someone who has debugged silent data corruption from someone who has only read the spec; (3) `oneof` for mutually exclusive variants — knowing that `oneof` is the canonical way to model sum types (card payment OR UPI payment OR NACH payment, never more than one) and that the case-detection pattern (`getMethodCase()`) is required because null checks on individual fields are unreliable when the field's default and the absent case produce the same value. The fintech-specific callout: never use `float` or `double` for monetary amounts in proto — store amounts as `int64` in minor currency units (paise for INR, cents for USD) and let the application layer handle decimal conversion. This is non-negotiable for any schema that touches payment amounts.
