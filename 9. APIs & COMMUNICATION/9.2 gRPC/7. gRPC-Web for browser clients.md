# gRPC-Web for Browser Clients — Interview Q&A (5 YOE Level)

---

## Section 1: Why gRPC-Web Exists

**Q1. What is gRPC-Web, and what specific limitation of native gRPC does it solve?**
A: gRPC-Web is a JavaScript client library and server-side proxy protocol that brings gRPC semantics to browser clients. It solves a fundamental incompatibility: native gRPC requires HTTP/2's bidirectional streaming and trailer support at the transport layer, neither of which browsers expose through their JavaScript APIs.

The incompatibility in detail: native gRPC uses HTTP/2 framing with the following features browsers cannot access:
- **HTTP/2 trailers** — gRPC sends response metadata (status codes, error details) as HTTP/2 trailer frames, which arrive after the response body. The browser's `fetch` API and `XMLHttpRequest` do not expose HTTP/2 trailers to JavaScript. A gRPC response without trailers is semantically incomplete — the client cannot know whether the call succeeded or failed.
- **Full duplex streaming** — native gRPC supports client streaming (client sends multiple messages before getting a response) and bidirectional streaming (both sides send multiple messages simultaneously). Browser network APIs have no mechanism for this — `fetch` cannot stream the request body progressively to the server while simultaneously receiving the response.
- **HTTP/2 flow control** — native gRPC clients implement HTTP/2 flow control at the connection level. Browsers manage HTTP/2 connections internally and don't expose flow control primitives to JavaScript.

gRPC-Web works around these limitations by: using HTTP/1.1 or HTTP/2 as transport (without requiring trailer support), encoding gRPC trailers in the response body itself (a "trailers-only" body envelope), and restricting the streaming model to server-streaming only (client must send the full request before the server starts streaming, matching what `fetch` supports natively).

**Q2. What is the difference between gRPC, gRPC-Web, and REST+JSON at a protocol level?**
A: The three protocols occupy different points on the expressiveness vs compatibility spectrum:

**Native gRPC:**
- Transport: HTTP/2 (mandatory)
- Serialization: Protocol Buffers (default), MessagePack or JSON (possible but uncommon)
- Streaming: unary, client streaming, server streaming, bidirectional streaming
- Service contract: `.proto` file
- Used by: server-to-server communication, native mobile apps, CLI clients
- Not usable in browsers: requires HTTP/2 transport primitives browsers don't expose

**gRPC-Web:**
- Transport: HTTP/1.1 or HTTP/2 (no trailer requirement)
- Serialization: Protocol Buffers or JSON
- Streaming: unary and server streaming (no client streaming, no bidirectional)
- Service contract: `.proto` file (same as gRPC)
- Used by: browser clients, browser-compatible proxies
- Requires a translation proxy (Envoy, grpc-web proxy) between the browser and a native gRPC backend

**REST+JSON:**
- Transport: HTTP/1.1 or HTTP/2
- Serialization: JSON
- Streaming: Server-Sent Events (SSE) for server push, WebSockets for bidirectional (separate protocol)
- Service contract: OpenAPI (optional, not enforced)
- Used by: browsers, mobile apps, server-to-server, everything
- No proxy required; works natively in every environment

The key insight: gRPC-Web gives browser clients access to Protocol Buffers serialization and the `.proto` service contract discipline — the type safety, code generation, and binary efficiency of gRPC — at the cost of needing a translation proxy and not supporting bidirectional streaming.

**Q3. Why would a team choose gRPC-Web over REST+JSON for browser clients? What is the concrete value proposition?**
A: The value proposition of gRPC-Web over REST+JSON for browser clients comes from the same advantages gRPC has over REST generally, applied to the browser context:

**Strongly typed service contract (.proto):**
The `.proto` file is the single source of truth for the API contract. `protoc` generates type-safe client stubs in TypeScript automatically — no hand-written API client code, no drift between documentation and implementation, and compile-time detection of breaking changes. In a large TypeScript frontend, this eliminates an entire class of runtime type errors.

**Binary serialization efficiency:**
Protocol Buffers encode messages in a compact binary format — typically 3–10× smaller than equivalent JSON. For payloads with many numeric fields, the reduction is dramatic. In a mobile browser on a constrained connection, smaller payloads translate directly to faster page loads and lower data usage.

**Code generation eliminates client-side boilerplate:**
The generated TypeScript stub handles serialization, deserialization, and RPC invocation. A team does not write `fetch` wrappers, response parsers, or type assertion code:
```typescript
// Generated — no hand-written API client
const client = new OrderServiceClient('https://api.example.com');
const request = new GetOrderRequest();
request.setOrderId('order-123');
const response = await client.getOrder(request, {});
console.log(response.getOrderId(), response.getStatus()); // typed getters
```
vs a typical REST+JSON approach:
```typescript
// Hand-written, error-prone, types may be stale
const response = await fetch(`/api/orders/${orderId}`);
const data: Order = await response.json();  // cast, not guaranteed
```

**Schema evolution with backward compatibility:**
`.proto` field numbering provides automatic backward compatibility — adding a new field with a new number doesn't break old clients (they ignore unknown fields). In REST+JSON, backward compatibility is a convention; in Protocol Buffers, it's a type system constraint.

**When the value proposition is weaker:** small teams with a simple, stable API; organizations where protobuf tooling is not already established; APIs consumed by third parties who don't want to adopt the protobuf toolchain; teams where the `fetch` + `zod` (TypeScript schema validation) pattern already achieves sufficient type safety.

## Section 2: The Protocol

**Q4. How does gRPC-Web encode messages, and what is the "length-prefixed message" framing?**
A: gRPC-Web uses a binary framing format to encode messages within an HTTP response body, since it cannot use HTTP/2's native frame-based framing. Each message (request or response) is wrapped in a 5-byte header followed by the message bytes:

```
Byte 0:    Compression flag (0 = not compressed, 1 = compressed)
Bytes 1-4: Message length as a 4-byte big-endian unsigned integer
Bytes 5+:  Message payload (Protocol Buffers or JSON encoded)
```

For a response stream with 3 messages:
```
[0][0x00][0x00][0x00][0x42] [66 bytes of protobuf message 1]
[0][0x00][0x00][0x00][0x38] [56 bytes of protobuf message 2]
[0][0x00][0x00][0x00][0x1F] [31 bytes of protobuf message 3]
[1][0x00][0x00][0x00][0x1C] [28 bytes of trailer frame]
```

The trailer frame (compression flag bit 7 set to 1, i.e., the flag byte is `0x80`) carries the gRPC status and any response metadata:
```
Trailer frame: flag=0x80 (trailer marker), length=N, body=HTTP headers encoded as "key: value\r\n" pairs
```

This is gRPC-Web's workaround for the missing HTTP/2 trailer support: trailers are encoded inline in the response body as a special frame. The gRPC-Web client library reads the response body as a stream, parses each frame by its 5-byte header, processes message frames as RPC response messages, and processes the trailer frame as the final gRPC status. The HTTP response itself can have a `200 OK` status while the gRPC call failed — the actual gRPC status is in the trailer frame.

**Q5. What are the two gRPC-Web content types, and when do you use each?**
A: gRPC-Web supports two content types that determine the serialization format of the message payload within the framing envelope:

- **`application/grpc-web+proto`** — message payload is Protocol Buffers binary. Default and most efficient. The messages inside the 5-byte framing envelope are serialized protobuf bytes. Smaller payloads, faster serialization/deserialization, but not human-readable.

- **`application/grpc-web+json`** — message payload is JSON. The messages inside the 5-byte framing envelope are JSON strings. Larger payloads but human-readable in browser developer tools, useful during development and debugging.

The request `Content-Type` header tells the server which format the request message uses. The `Accept` header (or a format negotiation header) tells the server which format to use for responses. In practice, most gRPC-Web clients default to `application/grpc-web+proto` for production and `application/grpc-web+json` for development/debugging mode.

A third content type, `application/grpc-web-text`, base64-encodes the entire binary framing payload — enabling transmission over HTTP/1.1 infrastructures that might corrupt binary data. This is a legacy compatibility mode rarely needed in modern deployments.

**Q6. What is the role of a gRPC-Web proxy, and why is it required?**
A: A gRPC-Web proxy translates between the gRPC-Web protocol (what browsers send) and native gRPC (what backend services speak). The proxy is required because:

1. The browser sends an HTTP/1.1 or HTTP/2 request with the gRPC-Web content type and the in-body framing format.
2. The backend gRPC server speaks native gRPC — it expects HTTP/2 with trailers, not in-body trailer frames.
3. The proxy receives the gRPC-Web request, translates it to a native gRPC call to the backend, receives the native gRPC response (with HTTP/2 trailers), and re-encodes the response as a gRPC-Web response (with inline trailer frame in the body).

The proxy also handles:
- **CORS preflight** — gRPC-Web requests use custom headers (`grpc-web`, `content-type: application/grpc-web+proto`), triggering CORS preflight. The proxy responds correctly to `OPTIONS` requests and sets `Access-Control-Allow-Origin` and `Access-Control-Expose-Headers` (for gRPC status headers).
- **HTTP/1.1 to HTTP/2 upgrade** — if the browser connects over HTTP/1.1 and the backend requires HTTP/2, the proxy handles the connection upgrade.
- **Trailer extraction** — extracts HTTP/2 trailer frames from the backend's native gRPC response and encodes them as gRPC-Web inline trailer frames in the response body.

**Envoy proxy** is the reference implementation for gRPC-Web proxying, configured with the `grpc_web` filter. `grpc-web` proxies can also be run as standalone services (`improbable-eng/grpc-web`) or as a Node.js middleware. In a Kubernetes environment, Envoy as an ingress with the gRPC-Web filter is the standard architecture.

## Section 3: Implementation

**Q7. Walk through setting up a gRPC-Web TypeScript client from proto definition to working browser call.**
A:

**Step 1 — Define the service in a `.proto` file:**
```protobuf
// order_service.proto
syntax = "proto3";

package orders.v1;

option js_namespace = "orders.v1";

message GetOrderRequest {
  string order_id = 1;
}

message Order {
  string order_id     = 1;
  string status       = 2;
  int64  total_amount = 3;   // in cents
  string currency     = 4;
  string customer_id  = 5;
}

message ListOrdersRequest {
  string customer_id  = 1;
  int32  page_size    = 2;
  string page_cursor  = 3;
}

message ListOrdersResponse {
  repeated Order orders      = 1;
  string         next_cursor = 2;
  int32          total_count = 3;
}

service OrderService {
  // Unary RPC — single request, single response
  rpc GetOrder (GetOrderRequest) returns (Order);

  // Server streaming — single request, stream of responses
  rpc WatchOrders (ListOrdersRequest) returns (stream Order);

  // Unary list
  rpc ListOrders (ListOrdersRequest) returns (ListOrdersResponse);
}
```

**Step 2 — Generate TypeScript client stubs:**
```bash
# Install code generation tools
npm install -g protoc-gen-grpc-web

# Generate JavaScript + TypeScript type definitions
protoc \
  --proto_path=./proto \
  --js_out=import_style=commonjs,binary:./src/generated \
  --grpc-web_out=import_style=typescript,mode=grpcwebtext:./src/generated \
  ./proto/order_service.proto
```

This generates:
- `order_service_pb.js` + `order_service_pb.d.ts` — message classes (serialization)
- `OrderServiceClientPb.ts` — the typed client stub

**Step 3 — Use the generated client in a React component:**
```typescript
// orderService.ts — singleton client instance
import { OrderServiceClient } from './generated/OrderServiceClientPb';
import { GetOrderRequest, ListOrdersRequest, Order } from './generated/order_service_pb';
import { RpcError, StatusCode } from 'grpc-web';

// Point at the gRPC-Web proxy, not the backend directly
const client = new OrderServiceClient('https://api.example.com', null, null);

// Unary call — returns a Promise
export async function getOrder(orderId: string): Promise<Order> {
  const request = new GetOrderRequest();
  request.setOrderId(orderId);

  return new Promise((resolve, reject) => {
    client.getOrder(request, {}, (err: RpcError | null, response: Order | null) => {
      if (err) {
        reject(new Error(`gRPC error ${err.code}: ${err.message}`));
        return;
      }
      if (!response) {
        reject(new Error('No response received'));
        return;
      }
      resolve(response);
    });
  });
}

// Server streaming — returns an observable stream
export function watchOrders(customerId: string, onOrder: (order: Order) => void, onError: (err: RpcError) => void): () => void {
  const request = new ListOrdersRequest();
  request.setCustomerId(customerId);
  request.setPageSize(20);

  const stream = client.watchOrders(request, {});

  stream.on('data', (order: Order) => {
    onOrder(order);
  });

  stream.on('error', (err: RpcError) => {
    onError(err);
  });

  stream.on('end', () => {
    console.log('Stream ended');
  });

  // Return a cleanup function to cancel the stream
  return () => stream.cancel();
}
```

```typescript
// React component using the gRPC-Web client
import React, { useEffect, useState } from 'react';
import { Order } from './generated/order_service_pb';
import { getOrder, watchOrders } from './orderService';

function OrderDashboard({ customerId }: { customerId: string }) {
  const [orders, setOrders] = useState<Order[]>([]);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    // Start watching orders via server streaming
    const cancelStream = watchOrders(
      customerId,
      (order) => setOrders(prev => {
        const idx = prev.findIndex(o => o.getOrderId() === order.getOrderId());
        if (idx >= 0) {
          const updated = [...prev];
          updated[idx] = order;
          return updated;
        }
        return [...prev, order];
      }),
      (err) => setError(`Stream error: ${err.message}`)
    );

    // Cleanup: cancel the stream when component unmounts
    return () => cancelStream();
  }, [customerId]);

  if (error) return <div className="error">{error}</div>;

  return (
    <ul>
      {orders.map(order => (
        <li key={order.getOrderId()}>
          Order {order.getOrderId()} — {order.getStatus()} — {order.getTotalAmount()} {order.getCurrency()}
        </li>
      ))}
    </ul>
  );
}
```

**Q8. How do you handle authentication and authorization headers in gRPC-Web requests?**
A: gRPC-Web sends authentication metadata as HTTP headers. The generated client accepts a metadata object as the second argument to each RPC call:

```typescript
// auth.ts — inject token into every gRPC-Web call
import { OrderServiceClient } from './generated/OrderServiceClientPb';
import { GetOrderRequest } from './generated/order_service_pb';

const client = new OrderServiceClient('https://api.example.com');

// Per-call metadata
async function getOrderAuthenticated(orderId: string, token: string) {
  const request = new GetOrderRequest();
  request.setOrderId(orderId);

  const metadata = {
    'Authorization': `Bearer ${token}`,
    'x-request-id': crypto.randomUUID(),
  };

  return new Promise((resolve, reject) => {
    client.getOrder(request, metadata, (err, response) => {
      if (err) reject(err);
      else resolve(response);
    });
  });
}
```

For interceptor-style authentication (inject token into all calls automatically):
```typescript
// interceptor pattern — wraps the client to add auth headers
function createAuthenticatedClient(getToken: () => string) {
  const client = new OrderServiceClient('https://api.example.com');

  // Wrap each method to inject headers automatically
  return {
    getOrder: (request: GetOrderRequest) => {
      const metadata = { 'Authorization': `Bearer ${getToken()}` };
      return new Promise<Order>((resolve, reject) => {
        client.getOrder(request, metadata, (err, res) => {
          if (err) reject(err); else resolve(res!);
        });
      });
    },
    // ... other methods
  };
}
```

The Envoy proxy forwards all request headers (including `Authorization`) to the backend gRPC service. On the backend, gRPC server interceptors extract and validate the token from the incoming context metadata — the same way they handle authentication from non-browser gRPC clients.

For streaming calls, metadata is passed once at stream initiation and applies for the duration of the stream. There is no mechanism to refresh a token mid-stream — if a token expires during a long-lived stream, the client must cancel and re-establish the stream with a fresh token. This is an important operational consideration for server streaming use cases where streams run for minutes.

## Section 4: Error Handling

**Q9. How does gRPC status codes map to HTTP status codes in gRPC-Web, and how should clients handle errors?**
A: gRPC uses its own 16-status-code system, independent of HTTP status codes. In gRPC-Web, the HTTP response from the proxy is typically `200 OK` regardless of the gRPC status — the actual gRPC status is encoded in the trailer frame within the response body. The gRPC-Web client library reads the trailer frame and surfaces the gRPC status to the application.

gRPC status codes relevant to browser clients:

| gRPC Status | Code | Meaning | Browser client action |
|--- |--- |--- |--- |
| `OK` | 0 | Success | Process response |
| `CANCELLED` | 1 | Client cancelled the RPC | Often client-initiated (stream.cancel()) |
| `UNKNOWN` | 2 | Unclassified server error | Retry with backoff |
| `INVALID_ARGUMENT` | 3 | Bad request data | Display validation error to user; don't retry |
| `NOT_FOUND` | 5 | Resource not found | Display 404 state; don't retry |
| `ALREADY_EXISTS` | 6 | Duplicate create | Display conflict error |
| `PERMISSION_DENIED` | 7 | Insufficient permissions | Redirect to upgrade/contact page |
| `RESOURCE_EXHAUSTED` | 8 | Rate limited | Retry with exponential backoff + jitter |
| `FAILED_PRECONDITION` | 9 | State doesn't allow operation | Show state-specific error message |
| `UNAUTHENTICATED` | 16 | Auth required / token expired | Refresh token, retry; redirect to login if refresh fails |
| `UNAVAILABLE` | 14 | Service temporarily down | Retry with exponential backoff |
| `DEADLINE_EXCEEDED` | 4 | Request timeout | Retry if idempotent; show slow-connection message |
| `INTERNAL` | 13 | Server bug | Log to error tracker; show generic error |

```typescript
// error-handling.ts — typed gRPC error handler
import { RpcError, StatusCode } from 'grpc-web';

interface GrpcErrorResult {
  userMessage: string;
  shouldRetry: boolean;
  shouldRefreshAuth: boolean;
  logToErrorTracker: boolean;
}

export function handleGrpcError(err: RpcError): GrpcErrorResult {
  switch (err.code) {
    case StatusCode.UNAUTHENTICATED:
      return {
        userMessage: 'Your session has expired. Please log in again.',
        shouldRetry: false,
        shouldRefreshAuth: true,
        logToErrorTracker: false,
      };

    case StatusCode.PERMISSION_DENIED:
      return {
        userMessage: 'You do not have permission to perform this action.',
        shouldRetry: false,
        shouldRefreshAuth: false,
        logToErrorTracker: false,
      };

    case StatusCode.NOT_FOUND:
      return {
        userMessage: 'The requested resource was not found.',
        shouldRetry: false,
        shouldRefreshAuth: false,
        logToErrorTracker: false,
      };

    case StatusCode.INVALID_ARGUMENT:
      return {
        userMessage: err.message,   // server validation message is user-facing
        shouldRetry: false,
        shouldRefreshAuth: false,
        logToErrorTracker: false,
      };

    case StatusCode.RESOURCE_EXHAUSTED:
      return {
        userMessage: 'Too many requests. Please wait a moment.',
        shouldRetry: true,
        shouldRefreshAuth: false,
        logToErrorTracker: false,
      };

    case StatusCode.UNAVAILABLE:
    case StatusCode.DEADLINE_EXCEEDED:
      return {
        userMessage: 'Service temporarily unavailable. Retrying...',
        shouldRetry: true,
        shouldRefreshAuth: false,
        logToErrorTracker: false,
      };

    case StatusCode.INTERNAL:
    case StatusCode.UNKNOWN:
    default:
      return {
        userMessage: 'An unexpected error occurred. Please try again.',
        shouldRetry: false,
        shouldRefreshAuth: false,
        logToErrorTracker: true,  // unexpected errors go to Sentry/Datadog
      };
  }
}
```

**Q10. How does gRPC's `google.rpc.Status` type provide richer error details than a plain status code?**
A: The basic gRPC status (code + message string) is often insufficient for client-side error handling — the message is a human-readable string, not machine-parseable metadata. Google's `google.rpc.Status` proto (part of `googleapis/googleapis`) allows encoding structured error details in the gRPC error response:

```protobuf
// google/rpc/status.proto (already in googleapis dependency)
message Status {
  int32  code    = 1;   // gRPC status code
  string message = 2;  // human-readable message
  repeated google.protobuf.Any details = 3;  // structured error details
}

// Common detail types from google.rpc:
// ErrorInfo    — reason code + domain + metadata map
// RetryInfo    — when to retry
// BadRequest   — which fields failed validation and why
// QuotaFailure — which quota was exceeded
```

On the server (Go example for a validation error):
```go
import "google.golang.org/grpc/status"
import "google.golang.org/grpc/codes"
import errdetails "google.golang.org/genproto/googleapis/rpc/errdetails"

st, _ := status.New(codes.InvalidArgument, "Validation failed").
    WithDetails(
        &errdetails.BadRequest{
            FieldViolations: []*errdetails.BadRequest_FieldViolation{
                {Field: "title",  Description: "Title cannot be blank"},
                {Field: "amount", Description: "Amount must be greater than 0"},
            },
        },
    )
return nil, st.Err()
```

On the gRPC-Web client (TypeScript), the error details are in the `err.metadata` object under the `grpc-status-details-bin` key, base64-encoded:
```typescript
import { Status } from 'google-proto-files/google/rpc/status_pb';
import { BadRequest } from 'google-proto-files/google/rpc/error_details_pb';

function extractValidationErrors(err: RpcError): Record<string, string> {
  const detailsBin = err.metadata?.['grpc-status-details-bin'];
  if (!detailsBin) return {};

  const status = Status.deserializeBinary(
    Uint8Array.from(atob(detailsBin), c => c.charCodeAt(0))
  );

  const errors: Record<string, string> = {};
  for (const detail of status.getDetailsList()) {
    if (detail.getTypeUrl().includes('BadRequest')) {
      const br = BadRequest.deserializeBinary(detail.getValue_asU8());
      for (const violation of br.getFieldViolationsList()) {
        errors[violation.getField()] = violation.getDescription();
      }
    }
  }
  return errors;
}

// Usage in a form submission handler:
try {
  await createOrder(request);
} catch (err) {
  if (err instanceof RpcError && err.code === StatusCode.INVALID_ARGUMENT) {
    const fieldErrors = extractValidationErrors(err);
    setFormErrors(fieldErrors);
    // fieldErrors: { "title": "Title cannot be blank", "amount": "Amount must be greater than 0" }
  }
}
```

## Section 5: Server Streaming in the Browser

**Q11. How does server streaming work in gRPC-Web, and what browser API does it use under the hood?**
A: Server streaming in gRPC-Web allows the server to send multiple messages in response to a single client request — a real-time update pattern commonly used for live data feeds, progress tracking, and push notifications. The browser implementation uses the `fetch` API with `response.body.getReader()` (the Streams API) to read the response body incrementally as chunks arrive.

Under the hood:
1. The browser sends a single `fetch` POST request (the streaming RPC call).
2. The server responds with `Transfer-Encoding: chunked` (HTTP/1.1) or HTTP/2 streaming, keeping the connection open.
3. The gRPC-Web client reads the response body as a `ReadableStream`, buffering incoming bytes.
4. As complete 5-byte-header + payload frames arrive, the client emits `data` events for message frames.
5. When the trailer frame arrives (compression flag `0x80`), the client emits an `end` event and closes the stream.

```typescript
// Server streaming with cancellation and reconnection
function createOrderStream(
  customerId: string,
  onData: (order: Order) => void,
  onError: (err: RpcError) => void,
  onEnd: () => void
) {
  const client   = new OrderServiceClient('https://api.example.com');
  const request  = new ListOrdersRequest();
  request.setCustomerId(customerId);

  const stream   = client.watchOrders(request, { 'Authorization': `Bearer ${getToken()}` });
  let cancelled  = false;

  stream.on('data', (order: Order) => {
    if (!cancelled) onData(order);
  });

  stream.on('error', (err: RpcError) => {
    if (!cancelled) {
      if (err.code === StatusCode.CANCELLED) {
        // Client-initiated cancellation — not an error
        return;
      }
      onError(err);
    }
  });

  stream.on('end', () => {
    if (!cancelled) onEnd();
  });

  // Return cancel function
  return {
    cancel: () => {
      cancelled = true;
      stream.cancel();
    }
  };
}
```

**Reconnection pattern for long-lived streams:**
Server streaming connections can be dropped by proxies (load balancer idle timeout, Envoy stream reset), mobile network transitions, or server restarts. Clients should implement automatic reconnection with exponential backoff:

```typescript
function createReconnectingStream(
  customerId: string,
  onData: (order: Order) => void
) {
  let attempts = 0;
  let currentStream: { cancel: () => void } | null = null;
  let cancelled = false;

  function connect() {
    if (cancelled) return;

    currentStream = createOrderStream(
      customerId,
      (order) => {
        attempts = 0;  // reset backoff on successful data
        onData(order);
      },
      (err) => {
        if (cancelled) return;
        const delay = Math.min(1000 * Math.pow(2, attempts), 30000); // max 30s
        attempts++;
        console.warn(`Stream error (attempt ${attempts}), reconnecting in ${delay}ms`, err.message);
        setTimeout(connect, delay);
      },
      () => {
        // Stream ended cleanly — reconnect immediately
        if (!cancelled) setTimeout(connect, 0);
      }
    );
  }

  connect();

  return {
    cancel: () => {
      cancelled = true;
      currentStream?.cancel();
    }
  };
}
```

**Q12. What are the limitations of gRPC-Web compared to native gRPC that affect browser client design?**
A: Beyond the fundamental limitation (no client streaming, no bidirectional streaming), gRPC-Web in the browser has several practical constraints:

**No client streaming:**
A client cannot send a sequence of messages to the server over a single RPC call. Use cases that need client streaming (uploading a large file in chunks while the server processes and responds, audio streaming for transcription) cannot use gRPC-Web's streaming model. The workaround: use unary calls with chunked payloads (break the client upload into separate unary RPCs), or use WebSockets alongside gRPC-Web.

**No bidirectional streaming:**
A chat application, a collaborative document editor, or a real-time game cannot use gRPC-Web's streaming for bidirectional communication. These require WebSockets or the Connect protocol (see Q15). Bidirectional use cases must be architected differently for browser clients than for native gRPC clients.

**Connection concurrency limits:**
Browsers limit concurrent HTTP/1.1 connections to 6 per origin. Each server-streaming gRPC-Web call holds one connection open for its duration. More than 6 simultaneous streaming calls to the same origin will stall. With HTTP/2, this is less of a concern (HTTP/2 multiplexes over one connection), but the Envoy proxy configuration and server must correctly support HTTP/2 for browser-to-proxy communication.

**Token refresh on long-lived streams:**
As noted in Q8, authentication tokens cannot be refreshed mid-stream. For streams that may run for hours, the client must detect token expiry (via an `UNAUTHENTICATED` error), cancel the stream, refresh the token, and re-establish the stream. This adds complexity to the client's authentication lifecycle management.

**No browser-native fetch cancellation propagation:**
When `stream.cancel()` is called, the gRPC-Web library sends a `RST_STREAM` (HTTP/2) or aborts the `fetch` request. The Envoy proxy propagates this cancellation to the backend gRPC server. However, if the backend is in the middle of a database query or an external API call when cancellation arrives, behavior depends on the backend language's context cancellation support — not all backends handle gRPC cancellation gracefully.

## Section 6: gRPC-Web vs Alternatives

**Q13. What is the Connect protocol, and how does it improve on gRPC-Web for browser clients?**
A: Connect (connectrpc.com, from Buf and formerly Square) is a newer protocol for gRPC-compatible browser and server clients that addresses gRPC-Web's main friction points:

**No proxy required:**
Connect servers speak Connect, gRPC, and gRPC-Web natively — the same Go/Node.js/Java server handles all three protocols without a translation proxy. This eliminates the Envoy dependency, simplifying infrastructure significantly for teams that would otherwise need to operate Envoy exclusively for gRPC-Web translation.

**Standard HTTP semantics:**
Connect's unary calls use straightforward POST with `Content-Type: application/proto` or `Content-Type: application/json`. The response body is the serialized message directly — no 5-byte framing envelope. This makes Connect unary calls inspectable in browser developer tools without a special decoder. The response HTTP status code carries the error status (not buried in a trailer frame), making Connect errors visible to monitoring tools that inspect HTTP status codes.

**Full streaming support:**
Connect supports all streaming modes including bidirectional streaming in browsers, implemented over HTTP/2 with the `Content-Type: application/connect+proto` streaming variant. This is not limited by the browser's HTTP/2 handling in the same way native gRPC is, because Connect's streaming design works within the constraints of browser APIs.

**TypeScript-first code generation:**
Connect's `@connectrpc/connect` library generates TypeScript code with modern async/await APIs rather than callbacks:

```typescript
// Connect TypeScript client — modern async/await
import { createClient } from '@connectrpc/connect';
import { createConnectTransport } from '@connectrpc/connect-web';
import { OrderService } from './generated/order_service_connect';

const transport = createConnectTransport({
  baseUrl: 'https://api.example.com',
});

const client = createClient(OrderService, transport);

// Unary — clean async/await, no callbacks
const order = await client.getOrder({ orderId: 'order-123' });
console.log(order.orderId, order.status);

// Server streaming — async iteration
const stream = client.watchOrders({ customerId: 'user-42' });
for await (const order of stream) {
  console.log('Received order update:', order.orderId);
}
```

Compare to gRPC-Web's callback/event API from Q7 — Connect's async/await and `for await...of` streaming is significantly more ergonomic. The trade-off: Connect requires server-side library support (the backend must use a Connect-compatible server library); gRPC-Web works with any native gRPC backend plus Envoy.

**Q14. When do you choose gRPC-Web over REST+JSON, gRPC-Web over Connect, and Connect over gRPC-Web?**
A: The decision tree:

**gRPC-Web vs REST+JSON:**
Choose gRPC-Web when: the backend already uses gRPC (server-to-server), you want the TypeScript type safety and code generation of `.proto` files, the payload size reduction of Protocol Buffers is meaningful for your use case (mobile on constrained bandwidth, high-frequency updates), or multiple frontend clients (web + mobile + backend) must share a single service contract.

Choose REST+JSON when: the team is smaller and the protobuf toolchain overhead isn't worth the type safety gain, the API is public-facing and you want maximum client compatibility without requiring protobuf libraries, the resource model is simple and doesn't benefit from gRPC's streaming, or existing tooling (OpenAPI, Postman, curl) is heavily relied upon.

**gRPC-Web vs Connect:**
Choose Connect when: you are designing a new system from scratch and have the flexibility to choose the server library, you want to eliminate the Envoy proxy dependency, the TypeScript client ergonomics matter (async/await vs callbacks), or you need bidirectional streaming in the browser.

Choose gRPC-Web when: the backend is an existing gRPC service you don't control (third-party, another team, legacy system), Envoy is already in your infrastructure stack for other purposes, or the team is more familiar with the gRPC-Web ecosystem and tooling.

The trend: Connect is increasingly the preferred choice for new projects where both browser and server code is being written by the same team. gRPC-Web remains the standard for browser frontends communicating with existing gRPC backends controlled by others.

## Section 7: Operational Considerations

**Q15. What are the CORS configuration requirements for gRPC-Web, and what headers must be explicitly allowed?**
A: gRPC-Web requests are CORS-eligible (cross-origin) because: they use the `POST` method with a custom `Content-Type` (`application/grpc-web+proto`), they include custom headers (`grpc-web`, `x-grpc-web`, `x-user-agent`), and the browser sends `grpc-status` and `grpc-message` headers that must be exposed to JavaScript.

Required CORS configuration at the proxy (Envoy or standalone):

**Allowed request headers (preflight `Access-Control-Allow-Headers`):**
```
keep-alive
user-agent
cache-control
content-type
content-transfer-encoding
x-accept-content-transfer-encoding
x-accept-response-streaming
x-user-agent
x-grpc-web
grpc-timeout
Authorization          ← add if using auth headers
x-request-id          ← add if using custom trace headers
```

**Exposed response headers (`Access-Control-Expose-Headers`):**
These headers are set by the gRPC-Web proxy in the response and must be explicitly exposed for JavaScript to read them:
```
grpc-status
grpc-message
grpc-status-details-bin   ← for structured error details
```

Without `grpc-status` in `Access-Control-Expose-Headers`, the browser's CORS policy prevents JavaScript from reading the gRPC status — the gRPC-Web client library cannot determine whether the call succeeded. This is one of the most common gRPC-Web debugging issues: a call appears to hang or silently fail because the CORS configuration is missing the `grpc-status` exposure.

The symptom: gRPC-Web calls work in development (same-origin or CORS disabled) but silently fail in production (cross-origin). The fix is always in the Envoy CORS filter configuration.

**Q16. How do you debug a gRPC-Web call in browser developer tools?**
A: Debugging gRPC-Web in browser devtools requires understanding the binary framing and what to look for:

**Network tab — what you'll see:**
The request is a POST to the service path (e.g., `/orders.v1.OrderService/GetOrder`) with `Content-Type: application/grpc-web+proto`. The response is `200 OK` (even for gRPC errors — remember, gRPC status is in the body). The response body is binary (Protocol Buffers) — not directly readable as text.

**Decoding the binary response:**
Two approaches:
1. Switch to JSON mode during development: change the serialization to `application/grpc-web+json` by configuring the client with `format: 'text'` — responses become human-readable JSON wrapped in the 5-byte framing.
2. Use gRPC-Web devtools browser extensions (e.g., gRPC-Web Developer Tools by SafetyCulture) that decode binary frames and display messages as JSON in a separate devtools panel.

**gRPC-Web devtools extension:**
```
Extension: gRPC-Web Developer Tools
What it shows: each RPC call listed with:
  - Service and method name (parsed from URL)
  - Request message (decoded from binary)
  - Response messages (decoded, shown in sequence for streaming)
  - gRPC status from the trailer frame
  - Duration and message count for streaming calls
```

**Console debugging without extensions:**
```typescript
// Add logging middleware to the gRPC-Web client
function createLoggingClient() {
  const client = new OrderServiceClient('https://api.example.com');
  const original = client.getOrder.bind(client);

  client.getOrder = (request, metadata, callback) => {
    console.log('[gRPC] GetOrder request:', request.toObject());
    const start = Date.now();
    return original(request, metadata, (err, response) => {
      if (err) {
        console.error('[gRPC] GetOrder error:', { code: err.code, message: err.message });
      } else {
        console.log('[gRPC] GetOrder response:', response?.toObject(), `${Date.now() - start}ms`);
      }
      callback(err, response);
    });
  };

  return client;
}
```

## Section 8: Scenario Questions

**Q17. "Your team's gRPC-Web calls work locally but fail silently in production. How do you diagnose this?"**
A: "Fail silently" in gRPC-Web almost always means either CORS misconfiguration or a proxy configuration issue. Systematic diagnosis:

**Step 1 — Check the network tab for the CORS preflight:**
Every gRPC-Web call triggers a CORS preflight `OPTIONS` request. If the preflight fails, the browser blocks the actual call and no error reaches the gRPC-Web client library — the call appears to silently fail. Look for a failed `OPTIONS` request in the network tab with `CORS error` or a `net::ERR_FAILED` status.

Preflight failure causes: the Envoy proxy is not responding to `OPTIONS` requests correctly; the `Access-Control-Allow-Headers` is missing required gRPC-Web headers; the `Access-Control-Allow-Origin` doesn't match the production domain.

**Step 2 — Check if the actual POST is being sent:**
If the preflight succeeds but the call still fails, look at the POST request. If it's present with a `200 OK` response but the client receives an error, the gRPC status in the trailer frame may be non-OK. Read the `grpc-status` response header (if visible) — if it's absent, `grpc-status` is missing from `Access-Control-Expose-Headers`.

**Step 3 — Temporarily switch to JSON mode:**
Change `Content-Type: application/grpc-web+json` in the client to make the response human-readable. Look at the raw response body in the network tab — the error message from the server will be visible as text.

**Step 4 — Check Envoy proxy logs:**
Envoy logs each request with upstream and downstream status. A `503` from Envoy upstream means the backend gRPC service is unreachable. A `400` from Envoy means the request format is incorrect (mismatched content type, HTTP version issue).

**Step 5 — Verify HTTP/2 between Envoy and backend:**
In the Envoy configuration, the cluster connecting to the backend must have `http2_protocol_options: {}`. Without it, Envoy uses HTTP/1.1 to the backend — the backend gRPC server only speaks HTTP/2 and closes the connection, causing all calls to fail.

**Q18. "The product team asks you to add a real-time order status feed to the web dashboard that shows live updates as orders change. How do you implement this with gRPC-Web?"**
A: Real-time order updates are a server-streaming use case — the ideal fit for gRPC-Web server streaming.

**Proto definition:**
```protobuf
service OrderService {
  // Server streaming: client subscribes, server pushes updates
  rpc WatchOrderUpdates (WatchOrderUpdatesRequest) returns (stream OrderUpdate);
}

message WatchOrderUpdatesRequest {
  string customer_id  = 1;
  repeated string order_ids = 2;  // filter: only these order IDs (empty = all)
}

message OrderUpdate {
  string order_id      = 1;
  string status        = 2;
  string updated_at    = 3;
  OrderUpdateType type = 4;
}

enum OrderUpdateType {
  ORDER_UPDATE_TYPE_UNSPECIFIED = 0;
  ORDER_CREATED   = 1;
  STATUS_CHANGED  = 2;
  ITEM_ADDED      = 3;
  PAYMENT_RECEIVED = 4;
}
```

**React hook implementation:**
```typescript
// useOrderUpdates.ts — custom hook for live order updates
import { useEffect, useRef, useCallback } from 'react';
import { OrderServiceClient } from './generated/OrderServiceClientPb';
import { WatchOrderUpdatesRequest, OrderUpdate } from './generated/order_service_pb';
import { RpcError, StatusCode } from 'grpc-web';

const client = new OrderServiceClient('https://api.example.com');

export function useOrderUpdates(
  customerId: string,
  onUpdate: (update: OrderUpdate) => void
) {
  const streamRef  = useRef<{ cancel: () => void } | null>(null);
  const attemptsRef = useRef(0);
  const cancelledRef = useRef(false);

  const connect = useCallback(() => {
    if (cancelledRef.current) return;

    const request = new WatchOrderUpdatesRequest();
    request.setCustomerId(customerId);

    const stream = client.watchOrderUpdates(
      request,
      { 'Authorization': `Bearer ${getAuthToken()}` }
    );

    streamRef.current = {
      cancel: () => stream.cancel()
    };

    stream.on('data', (update: OrderUpdate) => {
      attemptsRef.current = 0;  // reset backoff on successful message
      onUpdate(update);
    });

    stream.on('error', (err: RpcError) => {
      if (cancelledRef.current || err.code === StatusCode.CANCELLED) return;

      const backoff = Math.min(1000 * 2 ** attemptsRef.current, 30000);
      attemptsRef.current++;

      if (err.code === StatusCode.UNAUTHENTICATED) {
        // Token expired — refresh and reconnect
        refreshAuthToken().then(() => setTimeout(connect, 0));
      } else {
        setTimeout(connect, backoff);
      }
    });

    stream.on('end', () => {
      // Server ended the stream — reconnect
      if (!cancelledRef.current) setTimeout(connect, 1000);
    });
  }, [customerId, onUpdate]);

  useEffect(() => {
    cancelledRef.current = false;
    connect();

    return () => {
      cancelledRef.current = true;
      streamRef.current?.cancel();
    };
  }, [connect]);
}
```

**Usage in the dashboard:**
```typescript
function OrderDashboard({ customerId }: { customerId: string }) {
  const [orderStatuses, setOrderStatuses] = useState<Map<string, string>>(new Map());

  useOrderUpdates(customerId, (update) => {
    setOrderStatuses(prev => {
      const next = new Map(prev);
      next.set(update.getOrderId(), update.getStatus());
      return next;
    });
  });

  return (
    <div>
      {Array.from(orderStatuses.entries()).map(([orderId, status]) => (
        <div key={orderId}>Order {orderId}: {status}</div>
      ))}
    </div>
  );
}
```

**Operational considerations for this implementation:**
- The stream holds one HTTP connection open per `useOrderUpdates` hook instance. If the dashboard mounts 20 of these simultaneously (e.g., 20 order cards each with their own hook), 20 connections are opened. Consider debouncing into a single stream with client-side filtering.
- The reconnect logic handles token expiry, network interruptions, and Envoy stream resets. The maximum backoff of 30 seconds prevents thundering herd reconnections on a server restart.
- `cancelledRef` prevents state updates on unmounted components — a common React memory leak with async operations.

| Dimension | gRPC-Web | Connect | REST+JSON | WebSockets |

|--- |--- |--- |

| `INTERNAL` | 13 | Log to error tracker; show generic error |

```
Byte 0:    0x00 = message frame | 0x80 = trailer frame

```
