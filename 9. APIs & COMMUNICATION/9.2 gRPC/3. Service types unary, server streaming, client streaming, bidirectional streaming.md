# gRPC Service Types: Unary, Server Streaming, Client Streaming, Bidirectional Streaming — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is gRPC and what makes it different from REST?**
A: gRPC (Google Remote Procedure Call) is an open-source, high-performance RPC framework that uses HTTP/2 as its transport and Protocol Buffers (Protobuf) as its interface definition language and default serialization format. It was developed at Google, open-sourced in 2016, and is widely used for internal microservice communication.

Key differences from REST:

**Protocol:** gRPC uses HTTP/2 — multiplexed streams, binary framing, header compression (HPACK), full-duplex communication. REST typically uses HTTP/1.1 — one request per connection (or HTTP/2 for some modern REST APIs, but without gRPC's streaming primitives).

**Serialization:** gRPC uses Protobuf — binary, compact, typed, schema-enforced. REST uses JSON — text-based, human-readable, loosely typed, schema-optional.

**Interface definition:** gRPC requires a `.proto` file defining services and message types — the contract is explicit and generates client and server stubs in multiple languages. REST relies on OpenAPI/Swagger for documentation, but it's not enforced at the framework level.

**Streaming:** gRPC has four built-in communication patterns (unary, server streaming, client streaming, bidirectional streaming) as first-class citizens. REST has no native streaming — workarounds include SSE and WebSockets outside the REST model.

**Typing and code generation:** gRPC generates typed client and server code from `.proto` files. A client in Python and a server in Go share the same contract by compiling the same `.proto`. REST clients are typically hand-written or generated from OpenAPI specs with variable quality.

**Q2. What is a `.proto` file and how does it define gRPC services?**
A: A `.proto` file is the Interface Definition Language (IDL) for gRPC. It defines message types (structured data) and service definitions (the RPC methods, their request types, response types, and streaming patterns). The `protoc` compiler generates client stubs and server interfaces from the `.proto` file in the target language.

```protobuf
syntax = "proto3";

package order;

// Message definitions
message OrderRequest {
  string order_id = 1;
  string customer_id = 2;
}

message OrderItem {
  string product_id = 1;
  int32 quantity = 2;
  int64 unit_price_cents = 3;
}

message OrderResponse {
  string order_id = 1;
  string status = 2;
  repeated OrderItem items = 3;    // repeated = array
  int64 total_cents = 4;
  string created_at = 5;
}

message OrderStreamRequest {
  string customer_id = 1;
  string status_filter = 2;
}

message OrderUpdate {
  string order_id = 1;
  string old_status = 2;
  string new_status = 3;
  string updated_at = 4;
}

// Service definition — all four RPC types
service OrderService {
  // Unary
  rpc GetOrder(OrderRequest) returns (OrderResponse);

  // Server streaming
  rpc ListOrders(OrderStreamRequest) returns (stream OrderResponse);

  // Client streaming
  rpc CreateOrderBatch(stream OrderRequest) returns (OrderResponse);

  // Bidirectional streaming
  rpc TrackOrders(stream OrderRequest) returns (stream OrderUpdate);
}
```

The `stream` keyword before a message type marks that argument as a stream. Its position (request, response, or both) determines the service type.

**Q3. What are the four gRPC service types?**
A: The four service types differ in whether the request, response, or both are single messages or streams:

| Service Type | Request | Response | `stream` keyword in .proto |
|---|---|---|---|
| Unary | Single message | Single message | Neither |
| Server streaming | Single message | Stream of messages | `returns (stream Response)` |
| Client streaming | Stream of messages | Single message | `rpc Method(stream Request)` |
| Bidirectional streaming | Stream of messages | Stream of messages | Both |

In HTTP/2 terms: all four types use the same underlying mechanism — HTTP/2 streams. The difference is in how many messages are sent over the request and response directions of that stream before the stream is closed.

## Section 2: Unary RPC

**Q4. What is unary RPC and when do you use it?**
A: Unary RPC is the simplest pattern — one request, one response. It mirrors a traditional function call: the client sends a single message, the server processes it and sends back a single message. The interaction is complete when the response is received.

```protobuf
rpc GetOrder(OrderRequest) returns (OrderResponse);
```

**Lifecycle:**
```
Client                          Server
  |                               |
  |-- OrderRequest -------------→ |
  |                               | (process)
  |← ------------- OrderResponse--|
  |                               |
```

**When to use:**
- Simple request-response interactions: look up a record, authenticate a user, create a resource, validate input.
- When the entire result fits in a single message and is produced at once.
- When the client needs to wait for the full result before proceeding.
- The vast majority of API operations — CRUD operations, authentication, configuration fetches.

**Server implementation (Go):**
```go
func (s *OrderServiceServer) GetOrder(
    ctx context.Context,
    req *pb.OrderRequest,
) (*pb.OrderResponse, error) {
    order, err := s.db.FindOrder(ctx, req.OrderId)
    if err != nil {
        return nil, status.Errorf(codes.NotFound, "order %s not found", req.OrderId)
    }
    return &pb.OrderResponse{
        OrderId:    order.ID,
        Status:     order.Status,
        TotalCents: order.TotalCents,
    }, nil
}
```

**Client call (Go):**
```go
conn, _ := grpc.Dial("order-service:50051", grpc.WithInsecure())
client := pb.NewOrderServiceClient(conn)

response, err := client.GetOrder(ctx, &pb.OrderRequest{
    OrderId: "ord-123",
})
if err != nil {
    // handle error
}
fmt.Println(response.Status)
```

**Q5. How does gRPC handle errors in unary RPC?**
A: gRPC has its own status code system (separate from HTTP status codes) defined in `google.golang.org/grpc/codes`. Every RPC returns a status that is either `OK` or an error with a code and message:

```go
import "google.golang.org/grpc/codes"
import "google.golang.org/grpc/status"

// Server returns a gRPC status error
return nil, status.Errorf(codes.NotFound, "order %s not found: %v", orderID, err)
return nil, status.Errorf(codes.InvalidArgument, "customer_id is required")
return nil, status.Errorf(codes.PermissionDenied, "insufficient permissions")
return nil, status.Errorf(codes.Internal, "database error")
return nil, status.Errorf(codes.Unavailable, "upstream service unavailable")
```

**Common gRPC status codes:**
- `OK` (0) — success.
- `CANCELLED` (1) — client cancelled the request.
- `UNKNOWN` (2) — unknown error (default for untyped errors).
- `INVALID_ARGUMENT` (3) — client sent invalid data (like HTTP 400).
- `NOT_FOUND` (5) — resource not found (like HTTP 404).
- `ALREADY_EXISTS` (6) — resource already exists (like HTTP 409).
- `PERMISSION_DENIED` (7) — not authorized (like HTTP 403).
- `RESOURCE_EXHAUSTED` (8) — quota exceeded / rate limited (like HTTP 429).
- `INTERNAL` (13) — server-side error (like HTTP 500).
- `UNAVAILABLE` (14) — server temporarily unavailable, safe to retry (like HTTP 503).
- `UNAUTHENTICATED` (16) — not authenticated (like HTTP 401).

**Richer errors with details:** gRPC supports attaching structured error details to a status — field violations, localized messages, retry information:
```go
st, _ := status.New(codes.InvalidArgument, "validation failed").
    WithDetails(&errdetails.BadRequest{
        FieldViolations: []*errdetails.BadRequest_FieldViolation{
            { Field: "customer_id", Description: "must not be empty" },
        },
    })
return nil, st.Err()
```

## Section 3: Server Streaming RPC

**Q6. What is server streaming RPC and when do you use it?**
A: In server streaming, the client sends a single request and the server responds with a stream of messages — sending multiple responses over a single long-lived connection until it has no more data to send, then it closes the stream.

```protobuf
rpc ListOrders(OrderStreamRequest) returns (stream OrderResponse);
```

**Lifecycle:**
```
Client                          Server
  |                               |
  |-- OrderStreamRequest --------→|
  |                               | (begins producing results)
  |←-- OrderResponse (1) ---------|
  |←-- OrderResponse (2) ---------|
  |←-- OrderResponse (3) ---------|
  |        ...                    |
  |←-- OrderResponse (N) ---------|
  |←-- [stream closed] -----------|
  |                               |
```

**When to use:**
- Returning a large dataset that would be too large to fit in a single message or too slow to collect all at once — paginate via streaming instead.
- Real-time data feeds where the server produces results progressively: price updates, log tailing, search results as they are found.
- Long-running query results: "find all orders in the last 5 years" — stream rows as they are scanned rather than buffering the full result.
- Push-based notifications from server to client (server initiates data, client is passive receiver).

**Server implementation (Go):**
```go
func (s *OrderServiceServer) ListOrders(
    req *pb.OrderStreamRequest,
    stream pb.OrderService_ListOrdersServer,
) error {
    cursor, err := s.db.QueryOrders(req.CustomerId, req.StatusFilter)
    if err != nil {
        return status.Errorf(codes.Internal, "query failed: %v", err)
    }
    defer cursor.Close()

    for cursor.Next() {
        order := cursor.Value()

        // Check if client cancelled (e.g., disconnected)
        if err := stream.Context().Err(); err != nil {
            return status.Errorf(codes.Cancelled, "client cancelled")
        }

        if err := stream.Send(&pb.OrderResponse{
            OrderId:    order.ID,
            Status:     order.Status,
            TotalCents: order.TotalCents,
        }); err != nil {
            // Client disconnected mid-stream
            return err
        }
    }
    return nil   // Close the stream cleanly
}
```

**Client consumption (Go):**
```go
stream, err := client.ListOrders(ctx, &pb.OrderStreamRequest{
    CustomerId:   "cust-42",
    StatusFilter: "CONFIRMED",
})
if err != nil {
    // handle error
}

for {
    order, err := stream.Recv()
    if err == io.EOF {
        break   // Server closed the stream — all messages received
    }
    if err != nil {
        // handle stream error
    }
    fmt.Printf("Order: %s, Status: %s\n", order.OrderId, order.Status)
}
```

**Q7. How does server streaming compare to REST pagination?**
A: Both patterns deliver large datasets to clients, but with different trade-offs:

**REST pagination (offset or cursor-based):**
- Client makes multiple requests, each returning a page of results.
- Each request is independent — can be cached, retried, or interrupted without losing progress (client resumes from last cursor).
- Requires the server to maintain a stable cursor across stateless requests.
- Multiple HTTP connections (or HTTP/2 request/response pairs) — overhead per page.
- Client controls pacing — fetches the next page when ready.

**gRPC server streaming:**
- Single request, continuous response over one HTTP/2 stream.
- Lower per-message overhead — no repeated request headers, no pagination cursor state.
- Faster for bulk transfers — data flows as fast as the server produces it.
- Less fault-tolerant — if the stream breaks mid-transfer, the client must restart from the beginning (no cursor position to resume from, unless the application layer tracks it).
- Server controls pacing (push model) — the client must consume at the server's rate or apply flow control.
- Not cacheable — streaming responses cannot be cached by HTTP intermediaries.

**Choose REST pagination when:** the client needs to control pacing, cache individual pages, or resume after interruption. **Choose server streaming when:** bulk transfer speed matters, the full dataset is produced by a single server-side operation, and the client can consume continuously.

## Section 4: Client Streaming RPC

**Q8. What is client streaming RPC and when do you use it?**
A: In client streaming, the client sends a stream of messages and the server responds with a single message after all client messages have been received (or after enough have been received to produce the response).

```protobuf
rpc CreateOrderBatch(stream OrderRequest) returns (BatchResponse);
```

**Lifecycle:**
```
Client                          Server
  |                               |
  |-- OrderRequest (1) ----------→|
  |-- OrderRequest (2) ----------→|
  |-- OrderRequest (3) ----------→|
  |        ...                    |
  |-- OrderRequest (N) ----------→|
  |-- [client closes stream] ----→|
  |                               | (processes all received messages)
  |←-- BatchResponse -------------|
  |                               |
```

**When to use:**
- Bulk data ingestion: uploading a large file in chunks, bulk-creating records, submitting a batch of sensor readings or log entries.
- Aggregation: client sends many data points, server returns a single aggregated result (sum, average, count, ML inference on a collected dataset).
- Large file upload: the client streams file chunks; the server reassembles and responds with the stored file's metadata.
- IoT device telemetry: a device streams sensor readings, the server processes and returns a summary or acknowledgment.

**Server implementation (Go):**
```go
func (s *OrderServiceServer) CreateOrderBatch(
    stream pb.OrderService_CreateOrderBatchServer,
) error {
    var orders []*pb.OrderRequest
    var totalCents int64

    for {
        req, err := stream.Recv()
        if err == io.EOF {
            break   // Client finished sending
        }
        if err != nil {
            return status.Errorf(codes.Internal, "stream recv error: %v", err)
        }
        orders = append(orders, req)
        totalCents += req.TotalCents
    }

    // Process all received orders
    batchID, err := s.db.CreateOrderBatch(stream.Context(), orders)
    if err != nil {
        return status.Errorf(codes.Internal, "batch creation failed: %v", err)
    }

    // Send single response after processing all input
    return stream.SendAndClose(&pb.BatchResponse{
        BatchId:     batchID,
        OrderCount:  int32(len(orders)),
        TotalCents:  totalCents,
    })
}
```

**Client sending (Go):**
```go
stream, err := client.CreateOrderBatch(ctx)
if err != nil {
    // handle error
}

orders := getOrdersToCreate()
for _, order := range orders {
    if err := stream.Send(&pb.OrderRequest{
        CustomerId: order.CustomerID,
        TotalCents: order.TotalCents,
    }); err != nil {
        // handle send error
    }
}

// Close the stream and receive the single response
response, err := stream.CloseAndRecv()
if err != nil {
    // handle error
}
fmt.Printf("Batch %s created with %d orders\n", response.BatchId, response.OrderCount)
```

**Q9. How does client streaming compare to a single large REST request?**
A: Both aggregate multiple items into one server operation, but the delivery mechanism differs:

**Single REST request (JSON array):**
```
POST /orders/batch
Content-Type: application/json
Body: [{ "customer_id": "...", ...}, { ... }, ...]   ← entire batch buffered in body
```
- Simple — one request, one response.
- Must buffer the entire batch in memory on both client and server before sending.
- Limited by HTTP body size limits and client/server memory.
- All-or-nothing: if the connection drops mid-upload, the entire batch must be resent.
- No backpressure from server — client must pace itself.

**gRPC client streaming:**
- Client sends messages one at a time as they are ready — no full buffering required.
- Natural for large batches: the client can read from a file or database and stream without loading everything into memory.
- HTTP/2 flow control provides backpressure: if the server's receive buffer is full, the client's `Send` call blocks until the server has consumed data.
- More resilient to large payloads: no single-message size limits (chunked delivery).
- More complex to implement than a single POST request.

**Choose REST batch endpoint for:** small, bounded batches where simplicity matters. **Choose client streaming for:** unbounded or very large batches, streaming uploads, or when backpressure is needed to prevent overwhelming the server.

## Section 5: Bidirectional Streaming RPC

**Q10. What is bidirectional streaming RPC and when do you use it?**
A: In bidirectional streaming, both the client and server send streams of messages independently and concurrently over a single HTTP/2 stream. Neither side needs to wait for the other to finish before sending. The interaction ends when both sides close their respective streams.

```protobuf
rpc TrackOrders(stream OrderRequest) returns (stream OrderUpdate);
```

**Lifecycle:**
```
Client                          Server
  |                               |
  |-- OrderRequest (subscribe 1)→ |
  |-- OrderRequest (subscribe 2)→ |
  |                               |
  |← OrderUpdate (order 1 ships)--|
  |                               |
  |-- OrderRequest (subscribe 3)→ |
  |                               |
  |← OrderUpdate (order 2 status)-|
  |← OrderUpdate (order 1 deliv.)--|
  |                               |
  |-- [client closes stream] ----→|
  |← [server closes stream] ------|
  |                               |
```

The streams are independent — the client can send requests at any time, and the server can send updates at any time. The ordering between client messages and server messages is not coupled.

**When to use:**
- Real-time bidirectional communication: chat applications, collaborative editing, live dashboards with user interaction.
- Subscribe-and-receive with dynamic subscription changes: client subscribes to additional entities mid-stream without closing and reopening the connection.
- Long-running interactive sessions: a multiplayer game, a code execution sandbox where the client sends code and receives output incrementally.
- Protocol-level negotiation: systems where client and server exchange control messages interleaved with data.
- Real-time feeds with client-driven acknowledgment: the server streams events; the client sends acknowledgments per event (a Kafka-like consumer pattern over gRPC).

**Server implementation (Go):**
```go
func (s *OrderServiceServer) TrackOrders(
    stream pb.OrderService_TrackOrdersServer,
) error {
    ctx := stream.Context()
    subscriptions := make(map[string]bool)
    updates := make(chan *pb.OrderUpdate, 100)

    // Goroutine 1: receive client subscription requests
    go func() {
        for {
            req, err := stream.Recv()
            if err == io.EOF || ctx.Err() != nil {
                close(updates)
                return
            }
            if err != nil {
                return
            }
            subscriptions[req.OrderId] = true
            // Register subscription with event bus
            s.eventBus.Subscribe(req.OrderId, updates)
        }
    }()

    // Goroutine 2: send updates to client as they arrive
    for update := range updates {
        if !subscriptions[update.OrderId] {
            continue   // not subscribed to this order
        }
        if err := stream.Send(update); err != nil {
            return err   // client disconnected
        }
    }
    return nil
}
```

**Client usage (Go):**
```go
stream, err := client.TrackOrders(ctx)
if err != nil {
    // handle error
}

// Goroutine 1: send subscription requests
go func() {
    orderIDs := []string{"ord-123", "ord-456", "ord-789"}
    for _, id := range orderIDs {
        stream.Send(&pb.OrderRequest{OrderId: id})
    }
    // Later, dynamically add more subscriptions
    time.Sleep(5 * time.Second)
    stream.Send(&pb.OrderRequest{OrderId: "ord-999"})
    // Close when done subscribing (server stream still open for updates)
    stream.CloseSend()
}()

// Goroutine 2: receive updates
for {
    update, err := stream.Recv()
    if err == io.EOF {
        break
    }
    if err != nil {
        // handle error
    }
    fmt.Printf("Order %s: %s → %s\n",
        update.OrderId, update.OldStatus, update.NewStatus)
}
```

**Q11. What is the difference between bidirectional streaming and WebSockets?**
A: Both provide full-duplex communication, but differ in protocol and ecosystem:

**WebSockets:**
- An application-layer protocol upgrade from HTTP/1.1 (via `Upgrade: websocket`).
- Raw byte stream — the application defines its own message framing, serialization, and protocol.
- Native browser support — no special client library needed.
- Works with any HTTP server with WebSocket support.
- No built-in request-response correlation, flow control, or multiplexing (each WebSocket connection is one stream).
- Common for browser-based real-time applications: chat, live sports scores, collaborative tools.

**gRPC bidirectional streaming:**
- Built on HTTP/2 streams — inherits HTTP/2's flow control, multiplexing (multiple streams per connection), and header compression.
- Message framing and serialization via Protobuf — typed, schema-enforced, binary.
- Generated client and server stubs — strongly typed, IDE-friendly.
- Native browser support limited — requires gRPC-Web (a proxy) or grpc-web library.
- Multiple concurrent bidirectional streams can share a single HTTP/2 connection.
- Flow control is built into HTTP/2 — backpressure automatic.
- Common for internal service-to-service real-time communication.

**Choose WebSockets for:** browser clients, applications requiring universal HTTP compatibility, or when the message protocol needs to be flexible (not schema-enforced). **Choose gRPC bidirectional streaming for:** internal microservices, strongly typed real-time APIs, or when Protobuf performance and schema enforcement are priorities.

## Section 6: HTTP/2 Foundations

**Q12. How does HTTP/2 enable gRPC streaming?**
A: gRPC is built entirely on HTTP/2. Understanding HTTP/2 is essential for understanding why gRPC streaming works the way it does:

**HTTP/2 streams:** HTTP/2 introduces the concept of multiplexed streams — multiple logical request/response exchanges can share a single TCP connection simultaneously. Each stream has a unique stream ID. A gRPC RPC corresponds to exactly one HTTP/2 stream.

**How each gRPC type maps to HTTP/2:**
- **Unary:** One HTTP/2 stream. Client sends `HEADERS` + `DATA` frames (request) + `END_STREAM`. Server sends `HEADERS` + `DATA` frames (response) + `END_STREAM`.
- **Server streaming:** One HTTP/2 stream. Client sends `HEADERS` + `DATA` + `END_STREAM` (closes its side). Server sends many `DATA` frames, each carrying a length-prefixed Protobuf message, then `END_STREAM`.
- **Client streaming:** One HTTP/2 stream. Client sends many `DATA` frames, then `END_STREAM` (closes its send side). Server waits, then sends `HEADERS` + `DATA` + `END_STREAM`.
- **Bidirectional streaming:** One HTTP/2 stream. Both client and server send `DATA` frames independently. Each closes with `END_STREAM` when done. The stream is fully closed only when both sides have sent `END_STREAM`.

**HTTP/2 flow control:** HTTP/2 has per-stream and per-connection flow control windows. A sender can only send up to the receiver's advertised window size. When the receiver's buffer is full, it stops advertising window space — the sender blocks. This is how gRPC streaming gets automatic backpressure: a slow consumer naturally slows the producer without any application-level coordination.

**Frame-level message framing in gRPC:**
gRPC adds its own 5-byte message framing on top of HTTP/2 DATA frames:
```
Byte 0:    Compression flag (0 = not compressed, 1 = compressed)
Bytes 1-4: Message length (big-endian uint32)
Bytes 5+:  Serialized Protobuf message
```
Multiple gRPC messages may be sent in one HTTP/2 DATA frame (for small messages) or one message may span multiple DATA frames (for large messages).

**Q13. What is flow control in gRPC streaming and why does it matter?**
A: Flow control prevents a fast producer from overwhelming a slow consumer — an essential property for any streaming system.

**HTTP/2-level flow control:**
- Each HTTP/2 stream has a flow control window (default 65,535 bytes, configurable).
- The sender can only send data up to the receiver's current window size.
- When the receiver processes data, it sends `WINDOW_UPDATE` frames to increase the window, allowing the sender to send more.
- If the window reaches zero, the sender's `DATA` frame sends block — automatic backpressure.

**gRPC-level flow control:**
- On top of HTTP/2, gRPC client libraries implement their own flow control for streaming responses — controlling how many messages the application has requested to receive (buffering limits).
- In Go, `grpc.WithInitialWindowSize()` and `grpc.WithInitialConnWindowSize()` configure window sizes.

**Practical implications:**
```go
// Slow consumer — gRPC + HTTP/2 flow control prevents producer from flooding
stream, _ := client.ListOrders(ctx, req)
for {
    order, err := stream.Recv()    // If receiver is slow here,
    if err == io.EOF { break }     // HTTP/2 flow control automatically
    time.Sleep(100 * time.Millisecond)  // slows the server's Send() calls
    process(order)
}
```

Without flow control, a server streaming 1M orders would buffer all of them in network buffers before the slow client can process them — potentially exhausting server memory. With HTTP/2 flow control, the server's `stream.Send()` blocks when the client can't keep up — the server only produces at the rate the client consumes.

## Section 7: Cross-Cutting Concerns

**Q14. How do you implement authentication and authorization in gRPC?**
A: gRPC uses metadata (key-value pairs, similar to HTTP headers) for authentication context. The most common pattern is Bearer token authentication via interceptors:

**Client — attach token to every call:**
```go
// Per-call credentials
creds := oauth.NewOauthAccess(&oauth2.Token{AccessToken: "Bearer " + token})
conn, _ := grpc.Dial("service:50051",
    grpc.WithTransportCredentials(tlsCredentials),
    grpc.WithPerRPCCredentials(creds))

// Or manually via metadata
ctx := metadata.AppendToOutgoingContext(ctx,
    "authorization", "Bearer "+token)
```

**Server — interceptor validates token for every RPC:**
```go
func authInterceptor(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
) (interface{}, error) {
    md, ok := metadata.FromIncomingContext(ctx)
    if !ok {
        return nil, status.Errorf(codes.Unauthenticated, "metadata missing")
    }
    tokens := md["authorization"]
    if len(tokens) == 0 {
        return nil, status.Errorf(codes.Unauthenticated, "authorization header missing")
    }
    claims, err := validateJWT(tokens[0])
    if err != nil {
        return nil, status.Errorf(codes.Unauthenticated, "invalid token: %v", err)
    }
    // Add claims to context for downstream handlers
    ctx = context.WithValue(ctx, userClaimsKey, claims)
    return handler(ctx, req)
}

server := grpc.NewServer(
    grpc.UnaryInterceptor(authInterceptor),
    grpc.StreamInterceptor(streamAuthInterceptor),  // separate for streaming RPCs
)
```

**TLS:** gRPC connections should always use TLS in production. The gRPC framework natively supports TLS via `grpc.WithTransportCredentials(credentials.NewTLS(tlsConfig))`.

**Q15. What is gRPC interceptor and how does it compare to REST middleware?**
A: gRPC interceptors are the equivalent of HTTP middleware — they wrap RPC handler calls to add cross-cutting concerns (auth, logging, tracing, rate limiting, metrics) without modifying business logic.

**Two interceptor types:**
- `UnaryInterceptor` — wraps unary RPC calls. Invoked once per unary call.
- `StreamInterceptor` — wraps streaming RPC calls. Invoked once when the stream is opened; the handler function manages the stream lifecycle.

```go
// Logging interceptor for unary RPCs
func loggingInterceptor(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
) (interface{}, error) {
    start := time.Now()
    resp, err := handler(ctx, req)   // call the actual handler
    log.Printf("RPC: %s, duration: %v, error: %v",
        info.FullMethod, time.Since(start), err)
    return resp, err
}

// Chaining multiple interceptors
import "github.com/grpc-ecosystem/go-grpc-middleware"

server := grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        loggingInterceptor,
        authInterceptor,
        metricsInterceptor,
        rateLimitInterceptor,
    ),
)
```

**vs REST middleware:** Functionally equivalent — both intercept requests before reaching handlers and responses before returning to clients. The key difference: gRPC has separate interceptor chains for unary and streaming, because streaming calls have a different lifecycle (the interceptor is entered once when the stream opens, but the handler processes many messages over the stream's lifetime).

**Q16. How do you implement deadlines and timeouts in gRPC?**
A: gRPC has first-class support for deadlines — a specific point in time by which the entire RPC (including all streaming messages) must complete. This propagates automatically across services:

```go
// Client sets a deadline for the entire RPC
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// For unary: the response must arrive within 5 seconds
response, err := client.GetOrder(ctx, &pb.OrderRequest{OrderId: "ord-123"})

// For streaming: the entire stream (all messages) must complete within 5 seconds
stream, err := client.ListOrders(ctx, &pb.OrderStreamRequest{CustomerId: "cust-42"})
```

**Deadline propagation:** When a gRPC call includes a deadline, the deadline is propagated in the HTTP/2 headers (`grpc-timeout`). The receiving server extracts it and applies it to its own context. If that server makes downstream gRPC calls, the remaining deadline propagates further. This creates a distributed timeout that applies across the entire call chain.

```
Client (deadline: T+5s)
  → Service A (receives deadline: T+5s, has T+3.2s remaining after processing)
    → Service B (receives deadline: T+3.2s, has T+1.8s remaining)
      → Service C (receives deadline: T+1.8s → times out → DEADLINE_EXCEEDED)
    ← Service A receives DEADLINE_EXCEEDED from B
  ← Client receives DEADLINE_EXCEEDED
```

**Server respecting the deadline:**
```go
func (s *Server) GetOrder(ctx context.Context, req *pb.OrderRequest) (*pb.OrderResponse, error) {
    // Check if client already cancelled before doing expensive work
    select {
    case <-ctx.Done():
        return nil, status.FromContextError(ctx.Err()).Err()
    default:
    }

    // Pass context through to DB — DB query is cancelled if deadline passes
    order, err := s.db.QueryContext(ctx, "SELECT...", req.OrderId)
    if err != nil {
        if ctx.Err() != nil {
            return nil, status.Errorf(codes.DeadlineExceeded, "deadline exceeded")
        }
        return nil, status.Errorf(codes.Internal, "db error: %v", err)
    }
    return toProto(order), nil
}
```

## Section 8: Trade-offs & Decision-Making

**Q17. When do you choose each gRPC service type?**
A: A decision framework based on data flow characteristics:

**Choose Unary when:**
- The request is a single logical action with a single definitive outcome.
- The response can be produced atomically and is bounded in size.
- You need request-response semantics with straightforward error handling.
- Rule of thumb: if it would be a single REST endpoint call, use unary gRPC.

**Choose Server Streaming when:**
- The server needs to push multiple items to the client over time.
- The result set is too large to fit in a single response message.
- The server produces results progressively (query scanning, event tail, live feed).
- The client is a passive receiver — it doesn't need to send anything mid-stream.
- Data flows in one direction (server → client) after an initial trigger.

**Choose Client Streaming when:**
- The client has a large amount of data to send that doesn't fit in one message.
- The server needs all (or most) client data before producing a result.
- Bulk upload, batch creation, large file transfer.
- Data flows in one direction (client → server) before one response.

**Choose Bidirectional Streaming when:**
- Both sides need to send data concurrently and independently.
- The interaction is inherently conversational or event-driven in both directions.
- Subscribe-and-receive with dynamic updates from both sides.
- A long-lived session where either side may send at any time.
- Rule of thumb: if it would require WebSockets in a browser context, bidirectional streaming is likely the right gRPC pattern.

**Q18. What are the operational challenges of gRPC streaming in production?**
A: Streaming introduces challenges not present in unary RPC:

**Long-lived connections:** A bidirectional stream may stay open for hours or days. This complicates:
- Load balancing: HTTP/2 connection-level load balancing means a long-lived stream is pinned to one server instance. If that instance is taken down for deployment, the stream breaks. Requires graceful shutdown with stream draining and client-side reconnection logic.
- Resource tracking: servers must track active streams and their associated memory/goroutines. Memory leaks in streaming handlers cause gradual resource exhaustion.
- Keepalives: idle streams may be silently dropped by network infrastructure (load balancers, NAT gateways). Configure `keepalive.ClientParameters` and `keepalive.ServerParameters` to send periodic pings.

**Partial failure handling:** In unary, failure is simple — the call fails. In streaming, a partial failure is possible: the server sends 50 of 100 messages, then encounters an error. The client has already processed 50 messages. The stream closes with an error — the client must decide whether to retry (and reprocess the first 50) or to resume (which requires server-side cursor support).

**Observability:** Distributed tracing for streaming RPCs is more complex than for unary — a single trace spans the lifetime of the stream, which may encompass many logical operations. Each message in the stream should be a child span of the stream-level span. Ensure your tracing library supports gRPC streaming (OpenTelemetry gRPC instrumentation handles this).

**Load balancing for streams:** Standard L4 load balancers (TCP-level) cannot balance individual gRPC streams over an HTTP/2 connection — they balance connections, not streams. An HTTP/2 connection may multiplex many streams to one backend, creating imbalance. Solutions:
- L7 (application-level) load balancers that understand HTTP/2 and can balance per-stream (Envoy, AWS ALB with gRPC support).
- Client-side load balancing: the gRPC client library balances across server instances at the connection level (with short-lived connections, this approximates per-stream balancing).
- For long-lived bidirectional streams specifically: client-side load balancing at stream creation time, with reconnect logic that rebalances.

**Q19. How does gRPC compare to REST for internal microservice communication?**
A: gRPC's advantages are most pronounced in internal (service-to-service) communication:

**Performance:** Protobuf binary encoding is 3–10× smaller than equivalent JSON for structured data. HTTP/2 multiplexing eliminates head-of-line blocking (multiple concurrent RPCs over one connection). For internal services making hundreds of calls per second to each other, this matters.

**Type safety:** Generated stubs mean a Go service and a Java service speak the same typed contract — compile-time errors if the contract is violated. REST with OpenAPI provides documentation-level contracts but not compilation-level enforcement.

**Streaming:** Internal services frequently need streaming patterns (bulk data transfer, live feed subscription) that gRPC handles natively. REST workarounds (SSE, WebSockets, chunked transfer) are less integrated.

**Ecosystem:** gRPC's interceptor ecosystem (grpc-ecosystem/go-grpc-middleware) provides production-ready interceptors for logging, tracing, Prometheus metrics, rate limiting, and retry — easy to compose.

**Trade-offs:**
- gRPC is harder to debug than REST (binary, requires tooling like grpcurl or Evans to test from CLI).
- Browser clients cannot natively call gRPC without gRPC-Web proxy.
- Streaming connection management adds operational complexity.
- Not cacheable at the HTTP infrastructure level.

**Rule of thumb:** Use gRPC for internal service-to-service communication; use REST (or GraphQL) for public-facing APIs. Many organizations use gRPC internally and expose a REST gateway (grpc-gateway or a translation layer) to external clients.

## Section 9: Scenario / System Design Style Questions

**Q20. "Design the gRPC service definition for a real-time order tracking system where clients subscribe to updates for specific orders and the server pushes status changes as they happen."**
A: This is a natural fit for bidirectional streaming — clients send subscription requests, server pushes updates:

```protobuf
syntax = "proto3";
package tracking;

message SubscribeRequest {
  string order_id = 1;
}

message UnsubscribeRequest {
  string order_id = 1;
}

message ClientMessage {
  oneof payload {
    SubscribeRequest subscribe   = 1;
    UnsubscribeRequest unsubscribe = 2;
  }
}

message OrderStatusUpdate {
  string order_id        = 1;
  string previous_status = 2;
  string current_status  = 3;
  string updated_at      = 4;
  string carrier         = 5;   // for SHIPPED status
  string tracking_number = 6;   // for SHIPPED status
  string delivery_eta    = 7;   // for SHIPPED status
}

message Heartbeat {
  string timestamp = 1;
}

message ServerMessage {
  oneof payload {
    OrderStatusUpdate update    = 1;
    Heartbeat heartbeat         = 2;
  }
}

service OrderTrackingService {
  // Bidirectional: client sends subscribe/unsubscribe, server pushes updates
  rpc TrackOrders(stream ClientMessage) returns (stream ServerMessage);
}
```

**Why bidirectional over server streaming:**
The client needs to dynamically add and remove subscriptions mid-stream (subscribe to order A, then later also subscribe to order B). With server streaming, a single request would specify all orders upfront — no ability to add more later. Bidirectional allows the client to send new subscription requests at any time, and the server reacts accordingly.

**Heartbeat messages:** The server sends periodic heartbeats (every 30 seconds) to keep the stream alive through network proxies that would otherwise close idle connections, and to let clients detect if the server has failed (no heartbeat for 2× interval → reconnect).

**Q21. "You're designing a bulk order import API that receives a CSV file of 100,000 orders. Walk through why you'd choose client streaming over a large REST POST, and how you'd handle partial failures."**
A: Client streaming is superior for this use case for several reasons:

**Why client streaming:**
- 100,000 orders as a JSON array in a single POST body could be hundreds of megabytes — HTTP body size limits apply, and both client and server must buffer the entire payload before processing.
- Client streaming allows the client to read the CSV line by line and stream orders as they are parsed — constant O(1) memory on the client regardless of file size.
- The server can begin processing orders as they arrive rather than waiting for the full batch — pipeline parallelism.
- HTTP/2 flow control provides automatic backpressure — if the server's import pipeline is slower than the client's CSV reading, the client's `Send()` naturally blocks.

**Handling partial failures:**

```protobuf
message ImportOrderRequest {
  string idempotency_key = 1;   // client-generated per order, stable for retry
  string customer_id     = 2;
  repeated OrderItem items = 3;
  int64 total_cents      = 4;
  int32 row_number       = 5;   // CSV row number for error reporting
}

message ImportOrdersResponse {
  int32 total_received    = 1;
  int32 total_succeeded   = 2;
  int32 total_failed      = 3;
  repeated ImportError errors = 4;
}

message ImportError {
  int32 row_number   = 1;
  string order_id    = 2;
  string error_code  = 3;
  string description = 4;
}
```

**Server strategy for partial failures:**
- Process each order independently. A validation error on row 5,000 should not fail the entire batch.
- Collect errors as they occur. Return a summary `ImportOrdersResponse` at the end with total counts and per-row error details.
- Use `idempotency_key` per order so clients can safely retry specific failed orders without risk of duplication — the server checks if the key was already processed before inserting.

**Client retry strategy:**
- On stream failure (network drop): the client checks the last acknowledged order (from a periodic `PROGRESS` message from the server, or by querying a `/imports/{batch_id}/status` endpoint). Resume streaming from that point using row numbers to skip already-processed orders.
- On import errors (validation): client logs the errors and optionally re-streams only failed rows after fixing the data.

**Q22. "A gRPC bidirectional stream-based chat service is experiencing memory leaks. What are the likely causes and how do you fix them?"**
A: Memory leaks in long-lived streaming handlers are a common production issue. Systematic diagnosis:

**Cause 1 — Goroutine leak (most common):**
A streaming handler spawns goroutines for concurrency (one to read, one to write) but doesn't properly synchronize their teardown:

```go
// LEAKING: goroutines not cleaned up on stream error
func (s *Server) Chat(stream pb.ChatService_ChatServer) error {
    go func() {
        for {
            msg, err := stream.Recv()  // goroutine blocks forever if stream breaks
            if err != nil { return }   // ← return, but the outer handler already returned
            process(msg)
        }
    }()
    // ... outer handler returns → goroutine is now orphaned
}

// FIXED: use context cancellation to clean up goroutines
func (s *Server) Chat(stream pb.ChatService_ChatServer) error {
    ctx := stream.Context()
    errCh := make(chan error, 1)

    go func() {
        for {
            msg, err := stream.Recv()
            if err != nil {
                errCh <- err
                return
            }
            process(msg)
        }
    }()

    select {
    case <-ctx.Done():
        return status.FromContextError(ctx.Err()).Err()
    case err := <-errCh:
        return err
    }
    // Goroutine exits because stream.Recv() errors when ctx is cancelled
}
```

**Cause 2 — Subscriber map not cleaned up:**
```go
// Server maintains a map of active subscribers
type Server struct {
    subscribers map[string]chan *Message   // stream_id → channel
    mu          sync.Mutex
}

// LEAKING: subscriber added but never removed on disconnect
func (s *Server) Chat(stream ChatStream) error {
    id := generateID()
    ch := make(chan *Message, 100)
    s.mu.Lock()
    s.subscribers[id] = ch   // added
    s.mu.Unlock()
    // ... if function returns without removing from map → memory leak
}

// FIXED: always defer removal
defer func() {
    s.mu.Lock()
    delete(s.subscribers, id)
    s.mu.Unlock()
}()
```

**Cause 3 — Unbounded channel buffers:**
Channels that buffer incoming messages fill up if the consumer is slow — effectively memory-leaking the unprocessed messages. Add backpressure: use bounded channels and drop or apply flow control when full.

**Monitoring:** Track `runtime.NumGoroutine()` as a Prometheus gauge. Steadily increasing goroutine count indicates a goroutine leak. Track memory via `runtime.MemStats`. Set Kubernetes memory limits and alert on OOM kills.

## Quick Reference: gRPC Service Type Comparison

| Aspect | Unary | Server Streaming | Client Streaming | Bidirectional Streaming |
|---|---|---|---|---|
| `.proto` syntax | `rpc M(Req) returns (Res)` | `rpc M(Req) returns (stream Res)` | `rpc M(stream Req) returns (Res)` | `rpc M(stream Req) returns (stream Res)` |
| Request messages | 1 | 1 | Many | Many |
| Response messages | 1 | Many | 1 | Many |
| HTTP/2 stream | 1 per call | 1 per call | 1 per call | 1 per call |
| Client sends | Once, then waits | Once, then receives | Many, then waits | Many, concurrently |
| Server sends | Once | Many | Once | Many, concurrently |
| Backpressure | N/A | HTTP/2 flow control | N/A | HTTP/2 flow control |
| Typical use | CRUD, auth, lookup | Large query results, live feeds | Bulk upload, batch create | Chat, subscriptions, real-time |
| Complexity | Low | Medium | Medium | High |
| Load balancing | Per-call | Per-call start | Per-call start | Per-stream (complex) |
| Partial failure | N/A | Resume from cursor | Collect errors in response | Application-level |

---

**Tip for the interview:** gRPC service type questions almost always escalate to three deeper areas: (1) HTTP/2 foundations — knowing that all four service types are the same HTTP/2 stream with different message counts, and that flow control provides automatic backpressure in streaming, shows you understand the mechanism not just the API; (2) operational challenges of streaming — long-lived connections, goroutine leaks, load balancing per-stream vs per-connection, and graceful shutdown are all production concerns that separate candidates who've used gRPC in production from those who've only read the documentation; (3) choosing the right type — the decision framework is simple once stated (unary = one call/one response, server streaming = push many results, client streaming = bulk upload + aggregate, bidirectional = concurrent two-way), but interviewers often frame it as a scenario ("design a real-time tracking system") expecting you to articulate why bidirectional fits rather than server streaming. The key insight: bidirectional is only necessary when the client needs to send messages after the initial request — if the client is purely a receiver after triggering the stream, server streaming is sufficient and simpler.
