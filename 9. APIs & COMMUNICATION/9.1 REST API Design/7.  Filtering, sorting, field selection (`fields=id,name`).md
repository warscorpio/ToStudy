# Filtering, Sorting, Field Selection (`?fields=id,name`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are filtering, sorting, and field selection, and why do all three belong on list endpoints?**
A: All three are mechanisms for the client to control what data is returned without requiring multiple specialized endpoints:

- **Filtering** narrows the result set: "give me only orders with `status=pending`." Without filtering, the client must download all records and discard irrelevant ones — wasting bandwidth, increasing latency, and overloading mobile clients.
- **Sorting** determines the order of results: "give me orders sorted by `created_at` descending." Without a defined sort order, results are non-deterministic — different calls to the same endpoint may return records in different orders, making pagination unreliable.
- **Field selection** (sparse fieldsets) narrows the shape of each record: "give me only `id`, `name`, and `email` for each user." Without field selection, every caller receives the full resource representation regardless of what they actually need — a list of 1000 users returning full profile objects including bio, avatar URL, and preferences when only the name is needed wastes bandwidth and often requires hitting additional joins or lookups for unused fields.

Together, they implement the principle of **minimum necessary data transfer**: the client requests exactly the records it needs, in the order it needs them, with only the fields it will use.

**Q2. Why should filtering, sorting, and field selection use query parameters rather than request body or headers?**
A: Query parameters are the correct HTTP mechanism for these three operations because: (1) **safe GET semantics** — list endpoints are read-only, making `GET` the correct method; `GET` requests conventionally carry no body, and infrastructure (caches, proxies, browsers) may ignore or strip `GET` bodies. Encoding filter/sort/fields in query parameters preserves proper `GET` semantics. (2) **cacheability** — HTTP caches key on URL (method + full URL including query string); filters and sort in the query string mean different filter combinations produce different cache keys, so responses are cached correctly per filter combination. A filter in the request body is opaque to caches — two requests with different body-encoded filters both look like the same URL to a cache. (3) **shareability and bookmarkability** — a URL with filters and sort is a complete, shareable link: `https://api.example.com/products?category=shoes&sort=-price&page=2`. A body-encoded equivalent cannot be shared or bookmarked. (4) **logging and debugging** — server access logs capture the full URL including query string; filter parameters in the URL appear in logs automatically, aiding debugging and traffic analysis.

**Q3. What is the interaction between filtering, sorting, and pagination, and why must all three be designed together?**
A: Filtering, sorting, and pagination are tightly coupled — a change in any one affects the others:
- **Filtering affects page content**: `GET /orders?status=pending&page=2` returns page 2 of pending orders. If `status=pending` is removed, page 2 is a different set of records entirely. Pagination is always relative to the filtered result set.
- **Sorting must be stable for pagination to work**: if the sort order is non-deterministic (e.g., no tiebreaker for records with the same `created_at`), two consecutive page fetches may return different orderings, causing records to appear on multiple pages or be skipped entirely. A stable sort (unique sort key or consistent tiebreaker) is required for correct pagination.
- **Cursor-based pagination is sort-dependent**: the cursor encodes a position in the sorted, filtered result set. Changing the sort order invalidates all existing cursors — cursors are not transferable across different sort configurations.
- **Filter + sort determines index selection**: a database query with `WHERE status='pending' ORDER BY created_at DESC` requires a compound index on `(status, created_at)` to be served efficiently. Designing these features in isolation leads to missing indexes and slow queries discovered only in production.

## Section 2: Filtering

**Q4. What are the three main syntax styles for expressing filter operators in query parameters?**
A:
- **LHS bracket notation** (Left-Hand Side): the operator is encoded in the parameter name using square brackets. `?price[gte]=10&price[lte]=100`. Clean separation of field name and operator. Popular in PHP ecosystems and adopted by many APIs (Strapi, Directus). The square bracket syntax requires URL encoding (`%5B`, `%5D`) in strict contexts.
- **RHS colon notation** (Right-Hand Side): the operator is a prefix in the parameter value. `?price=gte:10`. Simple to parse (split on first colon); no special characters in the key. Used by some internal APIs and FIQL-inspired designs.
- **Named parameters**: separate parameters per comparison bound. `?min_price=10&max_price=100`, `?created_after=2024-01-01&created_before=2024-12-31`. Most readable for common range filters; not generalizable to arbitrary operators on arbitrary fields. Best for a small, known set of filters; becomes verbose for complex filter sets.

All three are valid. The choice matters less than **consistency** — using LHS bracket notation for price but named parameters for dates in the same API is the anti-pattern. Pick one style and apply it uniformly. LHS bracket notation is the most general and scales to arbitrary fields and operators; named parameters are the most readable for simple, well-known ranges.

**Q5. What operators should a production filter system support and what does each mean?**
A: Standard operators for a REST filter system:

| Operator | LHS notation       | Meaning                                  | Example                          |
|---       |---                 |---                                       |---                               |
| `eq`     | `?status[eq]=active` | Exact equality (default, often implied) | `?status=active`                 |
| `ne`     | `?status[ne]=deleted` | Not equal                              | exclude deleted                  |
| `gt`     | `?price[gt]=100`   | Greater than (strict)                    | price > 100                      |
| `gte`    | `?price[gte]=100`  | Greater than or equal                    | price ≥ 100                      |
| `lt`     | `?price[lt]=50`    | Less than (strict)                       | price < 50                       |
| `lte`    | `?price[lte]=50`   | Less than or equal                       | price ≤ 50                       |
| `in`     | `?status[in]=active,pending` | Value in list                  | status ∈ {active, pending}       |
| `nin`    | `?status[nin]=deleted,archived` | Value not in list           | status ∉ {deleted, archived}     |
| `like`   | `?name[like]=john*` | Wildcard/prefix match                   | name starts with "john"          |
| `null`   | `?deleted_at[null]=true` | Is null / is not null              | field is NULL                    |
| `exists` | `?profile[exists]=true` | Field exists (for document stores)   | document has this field          |

For text search, `like` or a dedicated `q` / `search` parameter is preferred over exposing SQL `LIKE` directly. Limit which fields are filterable — not every field should be filterable, especially computed or unindexed ones.

**Q6. How do you support filtering on multiple values for the same field (OR within a field)?**
A: Three patterns for "status is active OR pending":

- **Comma-separated in-list**: `?status=active,pending`. Simple, compact. The server interprets a comma-separated value as a set membership test. Requires explicit documentation that commas separate values; breaks if a valid field value contains a comma.
- **Repeated parameter**: `?status=active&status=pending`. HTTP-standard — repeated parameters with the same name form an array. Most frameworks parse this natively (`req.query.status` is an array `["active", "pending"]`). Slightly more verbose but unambiguous.
- **Bracket notation list**: `?status[in]=active,pending` — explicit operator makes the intent clear. Combines the compactness of comma-separated with the clarity of an explicit operator.

The key design decision: choose one style for lists and document it. Mixing (`?status=active,pending` for OR but `?id=1&id=2` for repeated) creates inconsistency. The `in` operator with comma-separation is the most explicit and consistent choice. Provide an escape mechanism for values that contain commas (URL encoding: `%2C`).

**Q7. How do you implement AND vs. OR logic across multiple filter fields?**
A: By default in most REST APIs, multiple filter parameters are combined with **implicit AND**: `?status=active&category=footwear` means "status is active AND category is footwear." This covers the majority of filtering use cases without additional complexity.

OR across different fields is significantly harder to express cleanly in query parameters. Approaches:

- **Filter language in a single parameter**: `?filter=status:active OR (category:footwear AND price[lt]:100)`. Expressive but requires a full parser; complex to validate and document. Inspired by FIQL (Feed Item Query Language, RFC 4287) or RSQL.
- **POST to a search endpoint**: complex boolean logic belongs in a request body, not a URL. `POST /products/search` with a JSON filter object:
  ```json
  {
    "filter": {
      "or": [
        {"status": "active"},
        {"and": [{"category": "footwear"}, {"price": {"lt": 100}}]}
      ]
    }
  }
  ```
  Expressive, well-typed, and easy to validate. Trade-off: loses GET caching and URL shareability.
- **Precomputed filter aliases**: expose named filter presets for common OR combinations: `?preset=featured_or_on_sale`. Limited flexibility but zero parser complexity.

For the majority of APIs, implicit AND across fields covers the real use cases. If OR logic across fields is a genuine product requirement, `POST /search` with a structured filter body is the pragmatic choice.

**Q8. How should full-text search be exposed, and how does it differ from attribute filtering?**
A: Full-text search is a dedicated operator, not a filter on a specific field:

```
GET /products?q=running+shoes
GET /users?search=john
GET /articles?query=machine+learning
```

Common parameter names: `q` (most compact, used by Google, GitHub), `search`, `query`. Choose one and use it consistently across all searchable endpoints. The search parameter searches across multiple indexed text fields (name, description, tags) — unlike an attribute filter which targets a specific field.

Key distinctions from attribute filtering: (1) **relevance scoring** — search results are often sorted by relevance score, not a simple attribute; the sort parameter may not apply or may conflict with relevance ranking; (2) **index requirement** — full-text search requires a full-text index (Postgres `tsvector`, Elasticsearch, Solr), not a B-tree index; (3) **tokenization and stemming** — "running" matches "runner" and "ran" in a full-text index but not in an exact equality filter; (4) **highlighting** — search APIs often return match highlights alongside results, requiring a richer response schema.

Never implement search by mapping `?q=value` to `WHERE name LIKE '%value%'` — it is unindexable, slow at scale, and semantically different from true full-text search. Either use a proper full-text index or be explicit in documentation that the search is a prefix match.

## Section 3: Sorting

**Q9. What is the standard query parameter pattern for specifying sort order?**
A: The widely-adopted convention uses a `sort` parameter with a field name. Direction is indicated by a **minus prefix for descending**:

```
GET /products?sort=price           # price ascending (default)
GET /products?sort=-price          # price descending
GET /products?sort=-created_at     # most recent first
GET /products?sort=name            # alphabetical ascending
```

Multi-field sort uses a comma-separated list of sort keys (applied left to right — first key is primary, subsequent keys are tiebreakers):
```
GET /products?sort=category,-price  # category asc, then price desc
GET /users?sort=last_name,first_name  # alphabetical by last name, then first
```

Alternative patterns: `?sort_by=price&order=desc` (separate direction parameter — verbose but more explicit), `?orderBy=price DESC` (SQL-style — too implementation-revealing). The minus-prefix convention is the most compact and widely understood; it is used by JSON:API, GitHub, Stripe, and many others.

**Q10. What is sort stability and why is it critical for pagination correctness?**
A: A sort is **stable** if records with equal values for the sort key appear in a consistent, deterministic order across multiple queries. An unstable sort may return the same record on two different pages (if a record "moves up" between page 1 and page 2 requests due to non-deterministic ordering of ties), or skip a record entirely.

Example of instability: sorting 100 users by `country` where 30 users are from "US." If the database uses an arbitrary internal ordering for the 30 US users (e.g., heap order, which changes with vacuum/compaction), page 1 might return US users 1–10 and page 2 might return US users 5–15 — with users 5–10 appearing on both pages.

Fix: **always add a unique tiebreaker to the sort**. If the sort key is `country`, the actual sort is `ORDER BY country, id`. The `id` (or any unique field) guarantees a deterministic order for ties. For cursor-based pagination, the cursor must encode all sort key values including the tiebreaker: `cursor = base64({country: "US", id: 47})`. When the next page is requested, the query becomes `WHERE (country, id) > ('US', 47)`.

**Q11. How do you handle null values in sort order, and why does it matter for client behavior?**
A: Null values in a sorted field have no natural position — they are neither greater than nor less than non-null values in the mathematical sense. Different databases treat them differently: PostgreSQL sorts NULLs last in ascending order (`NULLS LAST`) and first in descending order (`NULLS FIRST`) by default; MySQL sorts NULLs first in ascending order; SQL Server sorts NULLs first in both directions.

This inconsistency is invisible to clients unless documented. A client rendering a sorted list of products where `discount_price` is null for non-discounted products may see all non-discounted products at the top or bottom depending on server database and sort direction — and this may change when the database is swapped.

Best practice: (1) **document your null-sort behavior** explicitly in API documentation; (2) expose explicit null position control if needed: `?sort=-price&null_position=last`; (3) make null behavior consistent regardless of underlying database (implement it in the application layer if needed); (4) consider whether null values should be excluded from the result set via a filter rather than included with undefined sort position: `?price[null]=false&sort=-price`.

**Q12. What is a computed or aliased sort key, and when is it appropriate?**
A: A computed sort key is a sort parameter value that doesn't directly correspond to a database column but represents a computed or derived ordering:

```
GET /articles?sort=relevance      # sort by full-text search relevance score
GET /products?sort=popularity     # sort by computed popularity score
GET /users?sort=activity          # sort by composite activity metric
GET /posts?sort=trending          # sort by trending algorithm score
```

Aliased sort keys are appropriate when: (1) the actual sort computation is complex (a ranking algorithm involving multiple columns) and exposing the implementation would leak internal details; (2) the sort is computed at query time (e.g., a relevance score from a search engine) and has no static column equivalent; (3) the business meaning of the sort is stable even if the underlying computation changes.

Implementation: maintain an allowlist of valid sort aliases mapping to their database/search equivalent. `"popularity" → "popularity_score DESC NULLS LAST"`. Reject sort values not in the allowlist — never pass the sort parameter directly to a database ORDER BY clause (SQL injection risk and column name exposure).

## Section 4: Field Selection

**Q13. What problem does field selection solve, and what is the performance argument for implementing it?**
A: Field selection (sparse fieldsets) allows clients to specify which fields they want in the response, receiving a subset of the full resource representation. The performance argument is multifaceted:

- **Bandwidth reduction**: a full user object might be 2KB (including bio, avatar URLs, social links, preferences, audit fields). A list of 100 users with full objects is 200KB. With `?fields=id,name,email`, each user might be 50 bytes — the list is 5KB. A 40× bandwidth reduction on mobile devices (where bandwidth is expensive and latency is high) is significant.
- **Serialization reduction**: the server doesn't serialize fields that aren't requested — less CPU for JSON marshaling.
- **Database query reduction**: if field selection is pushed to the database (`SELECT id, name, email FROM users` instead of `SELECT *`), the database reads fewer columns from disk/memory, and query result transfer from database to application is smaller. This is particularly impactful for wide tables with large text or JSONB columns.
- **Downstream service call reduction**: some fields in a resource representation require additional service calls to populate (e.g., a user's `subscription_plan` requires a call to the billing service). If the client didn't request `subscription_plan`, the server can skip that call entirely.

**Q14. What are the syntax options for specifying field selection?**
A: Three patterns for expressing which fields to include:

**Inclusion list** (whitelist — return only these fields):
```
GET /users?fields=id,name,email
GET /products?fields=id,name,price,category
```
The server returns only the listed fields. Unrecognized field names in the list: return a `400 Bad Request` with a clear error message listing the unknown field names.

**Exclusion list** (blacklist — return everything except these fields):
```
GET /users?exclude=password_hash,internal_notes,audit_trail
```
The server returns all fields minus the excluded ones. Simpler for clients who want "almost everything minus a few sensitive fields." Risk: new fields added to the resource are automatically included, which may surprise clients expecting a stable shape.

**JSON:API sparse fieldsets** (per-type field selection in compound documents):
```
GET /articles?fields[articles]=title,body&fields[people]=name
```
Specifies fields per resource type when the response includes related resources. Most appropriate when implementing the JSON:API specification.

**Recommendation**: inclusion list (`?fields=...`) for most APIs. It is explicit, safe (new fields are not accidentally returned), and easy to document. Exclusion lists are acceptable for convenience but should never be the only option — clients should always be able to request a minimal representation.

**Q15. How do you handle nested fields and relationship expansion in field selection?**
A: Two distinct operations that are often conflated:

**Nested field selection** — selecting specific sub-fields within an embedded object:
```
GET /users?fields=id,name,address.city,address.country
```
The `address` object is embedded in the user; the client wants only `city` and `country` from it. Dot notation is the conventional separator for nested paths.

**Relationship expansion / embedding** — including a related resource that would otherwise be represented as just an ID:
```
GET /orders?expand=customer,items
GET /orders?include=customer,items
```
Without expansion: `"customer_id": 42`. With expansion: `"customer": {"id": 42, "name": "Alice", ...}`. This is a separate concern from field selection — it controls whether related resources are embedded (avoiding N+1 round trips) rather than which fields of the current resource are returned.

Combining both:
```
GET /orders?fields=id,total,status&include=customer&fields[customer]=id,name
```
The order has `id`, `total`, `status`; the embedded customer has `id`, `name`. This is the JSON:API sparse fieldsets pattern made explicit. Not all APIs support this level of granularity — decide upfront how deep field selection applies to included resources, document it clearly, and be consistent.

**Q16. What is the security implication of field selection, and how do you prevent sensitive field exposure?**
A: Field selection must be implemented with an **allowlist of returnable fields per authentication context**, not a pure reflection of the database schema. Security risks:

- **Sensitive field leakage**: without allowlisting, a client requesting `?fields=password_hash,mfa_secret,admin_notes` could receive fields that should never be returned by the API. The server must validate every requested field against an allowlist of fields permitted for the current resource and the current caller's authorization level.
- **Privilege escalation via field selection**: an `admin_only: true` flag on a user might be visible to admin callers but not to regular users. Field selection must enforce authorization per field — not just per endpoint. If user U requests `?fields=is_admin`, and U is not an admin, the server should either omit `is_admin` from the response silently or return a `403` if explicitly requesting an unauthorized field.
- **Implementation pattern**: define a field allowlist per role per resource. The server intersects the requested field list with the caller's allowed fields. If a requested field is not in the allowlist, either silently ignore it (include only the intersection) or return a `400` identifying the disallowed field. Silent filtering is more forward-compatible but may confuse clients expecting their requested field to be present.

## Section 5: Pagination Interaction

**Q17. How does offset-based pagination interact with filtering and sorting?**
A: Offset pagination (`?page=2&page_size=20` or `?offset=40&limit=20`) executes as: "skip the first `offset` records from the filtered, sorted result set and return the next `limit` records." The database query is:

```sql
SELECT * FROM products
WHERE category = 'footwear' AND price <= 100
ORDER BY price ASC, id ASC
LIMIT 20 OFFSET 40
```

The filter (`WHERE`), sort (`ORDER BY`), and pagination (`LIMIT OFFSET`) are all coupled in this single query. Changing any parameter independently produces a different result set slice. The interaction to design carefully: **page 2 with different filters is not page 2 of the original results** — it is page 2 of the new filtered set. Clients must reset to page 1 when changing filters or sort. Many APIs enforce this by including the current filter and sort in the pagination metadata, so clients can detect when their context has changed.

**Q18. How does cursor-based pagination interact with filtering and sorting?**
A: Cursor-based pagination is more tightly coupled to the sort order than offset pagination. The cursor encodes the position in the sorted result set — specifically, the value(s) of the sort key(s) for the last record on the previous page:

```
# First page: GET /orders?status=pending&sort=-created_at&limit=20
# Response includes:
{
  "data": [...20 orders...],
  "pagination": {
    "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0xNVQxMDowMDowMFoiLCJpZCI6NDd9",
    "has_more": true
  }
}

# Second page: GET /orders?status=pending&sort=-created_at&limit=20&after=eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0xNVQxMDowMDowMFoiLCJpZCI6NDd9
```

The cursor decodes to `{created_at: "2024-01-15T10:00:00Z", id: 47}`. The server translates this to: `WHERE status='pending' AND (created_at, id) < ('2024-01-15T10:00:00Z', 47) ORDER BY created_at DESC, id DESC LIMIT 20`. This is a **keyset pagination** query — efficient because it uses an index seek rather than a full scan + skip.

Critical constraints: (1) the cursor is **sort-specific** — a cursor generated with `sort=-created_at` is invalid if the sort changes to `sort=price`; (2) the filter must remain the same between page requests — changing `status=pending` to `status=active` with the same cursor produces garbage results; (3) the cursor should be **opaque** to clients (base64-encoded, not raw SQL values) — this prevents clients from constructing or modifying cursors and allows the server to change cursor encoding without breaking the API contract.

**Q19. What metadata should a paginated, filtered, sorted response include?**
A: A complete pagination envelope:

```json
{
  "data": [...results...],
  "meta": {
    "total_count": 1847,
    "returned_count": 20,
    "filter": {"status": "pending"},
    "sort": "-created_at",
    "page_size": 20
  },
  "pagination": {
    "next_cursor": "eyJ...",
    "prev_cursor": "eyJ...",
    "has_next": true,
    "has_prev": false
  }
}
```

Key fields: `total_count` (total matching records across all pages — expensive to compute, so make it opt-in with `?count=true`), `returned_count` (records in this response), `next_cursor`/`prev_cursor` (for navigating pages), `has_next`/`has_prev` (for disabling UI navigation buttons). Echo the applied filter and sort back in `meta` — this confirms what the server actually applied, helping clients debug unexpected results.

Why `total_count` is opt-in: computing `COUNT(*)` with the full filter applied requires a separate database query (or a count-only index scan), which can be expensive for complex filter combinations. Most UIs only need `has_next` (for infinite scroll or "load more") — the exact total is needed only for "showing 41–60 of 1,847 results" display patterns. Make total_count opt-in rather than always computing it.

## Section 6: Implementation Patterns

**Q20. How do you safely map query parameters to database queries without enabling SQL injection?**
A: The core principle: **never interpolate raw query parameter values into SQL strings**. Two complementary defenses:

- **Parameterized queries / prepared statements**: always use query parameters: `WHERE price >= $1 AND price <= $2` with values `[10, 100]`. The database driver escapes values automatically — a filter value of `100; DROP TABLE products--` is safely passed as a literal string, not executed as SQL.
- **Field name allowlisting**: the field name part of a filter (`?price[gte]=100` — the "price" part) is more dangerous than the value — it is interpolated into the query structure (column name), not as a value. A filter like `?sql_injection_column[eq]=1; DROP TABLE users--` could construct an invalid column name reference. Maintain an explicit allowlist of filterable field names: `ALLOWED_FILTER_FIELDS = {"status", "price", "created_at", "category_id"}`. Reject any field name not in the allowlist with a `400` error.

Never derive the column name from the query parameter directly: `ORDER BY {sort_param}` is a SQL injection vector. Map all sort and filter parameter values through the allowlist before constructing the query.

**Q21. How do you push field selection down to the database layer, and when is it worth the complexity?**
A: Database-level field selection replaces `SELECT *` with explicit column lists:

```sql
-- Without field selection:
SELECT id, name, email, phone, bio, avatar_url, preferences, created_at, updated_at
FROM users WHERE id = 123

-- With ?fields=id,name,email:
SELECT id, name, email FROM users WHERE id = 123
```

Worth the complexity when: (1) the table has wide rows — many columns, large text fields, JSONB blobs — where selecting fewer columns significantly reduces I/O; (2) some columns require expensive JOIN or subquery to populate — if `subscription_plan` requires a JOIN to a billing table, skip the JOIN when `subscription_plan` isn't in the fields list; (3) the API is used by mobile clients where bandwidth matters.

Not worth the complexity when: (1) all columns are narrow scalar types — the savings are minimal; (2) the ORM/query builder makes dynamic column selection difficult to implement safely; (3) the API always returns a fixed set of fields and clients never use field selection.

Implementation: build the SQL column list dynamically from the requested fields intersected with the allowlist. Use the ORM's `.only()`, `.values()`, or raw `SELECT` with explicit columns. Cache the per-request column list to avoid re-computing it for each DB call in the request.

**Q22. How do you handle filtering on relationship fields or fields from joined tables?**
A: Filtering on relationship attributes (e.g., filtering orders by the customer's `country`) requires a JOIN in the underlying query. Two patterns:

**Flat filter parameters** (expose the filter with a dotted path):
```
GET /orders?customer.country=US&customer.tier=premium
```
The server interprets `customer.country` as a filter requiring a JOIN to the customers table. Clean for the client; requires the server to parse dotted paths and construct the JOIN.

**Nested resource filter** (use the relationship's own endpoint with filter, then cross-reference):
```
GET /customers?country=US&tier=premium → returns customer IDs [1, 2, 3]
GET /orders?customer_id[in]=1,2,3
```
Two requests, but each is simple and independently cacheable. For complex relationship filters, this avoids JOIN complexity at the cost of chattiness.

**Precomputed filter fields** (denormalize for filtering):
Add `customer_country` and `customer_tier` as denormalized columns on the orders table, updated asynchronously when the customer changes. Enables simple filtering without JOINs. Trade-off: data duplication and synchronization complexity.

For most APIs, flat dotted-path filters are the pragmatic choice for one-level relationship filters. Deeper or more complex relationship queries belong in a dedicated search endpoint (`POST /orders/search`) where a JSON body can express the full JOIN logic without URL encoding gymnastics.

## Section 7: Failure Modes & Anti-patterns

**Q23. What is the "unrestricted filter field" anti-pattern and what are its consequences?**
A: The unrestricted filter field anti-pattern is when any query parameter is treated as a potential filter without validation:

```python
# Dangerous: uses all query params as filters
filters = request.query_params.dict()
queryset = Order.objects.filter(**filters)
```

Consequences: (1) **SQL injection** if field names are interpolated into SQL without parameterization; (2) **internal field exposure** — `?created_by_admin=true` may filter on an internal field not intended for client use; (3) **DoS via unindexed columns** — `?internal_notes__contains=refund` triggers a full table scan on a large text field; (4) **information leakage** — error messages for invalid field names reveal schema details (`Invalid field name 'deleted_at_internal'`).

Fix: define an explicit allowlist of filterable fields. Every filter parameter is validated against this list before query construction. Unknown fields return `400 Bad Request` with a message identifying the unknown field name. Index the allowlisted fields appropriately.

**Q24. What is the "unlimited result set" anti-pattern and how do you prevent it?**
A: The unlimited result set anti-pattern is an API that returns all matching records when no pagination parameters are provided:

```
GET /orders → returns all 2,000,000 orders
GET /users  → returns all 500,000 users
```

Consequences: (1) unbounded memory usage on both server and client; (2) unbounded response time — a query scanning millions of rows may take minutes; (3) client-side crashes from attempting to deserialize a gigabyte JSON array; (4) cascading failures — the database is saturated by this query, degrading other requests.

Prevention: **enforce a maximum page size and default to a reasonable page size even when none is requested**. `GET /orders` should behave as `GET /orders?page=1&limit=20`. Enforce a hard ceiling (e.g., `max_limit=200` — no matter what `limit` the client requests, cap it at 200). Return a `Link: <next>` header or `pagination.next_cursor` so clients know there are more results. Return an error for `?limit=-1` or `?limit=0`. Never allow "give me everything" via a regular list endpoint; provide a dedicated export endpoint (`GET /orders/export`) with appropriate access controls and asynchronous delivery for bulk data access.

**Q25. What is the "leaking internal field names" anti-pattern and how does it affect API evolution?**
A: Leaking internal field names exposes database column names, ORM property names, or internal model attributes directly in the API:

```
GET /users?sort=updated_at_utc_internal  # internal column name
GET /orders?filter=fk_customer_id=42     # foreign key column name
GET /products?fields=is_deleted_soft     # internal soft-delete flag
```

Consequences: (1) **coupling clients to implementation**: changing a column name for a database refactoring breaks all clients using that column name as a filter or sort parameter; (2) **security information disclosure**: internal naming conventions reveal schema structure, relationships, and implementation choices that attackers can use to probe the system; (3) **confusing API surface**: `fk_customer_id` is a worse API name than `customer_id`; `updated_at_utc_internal` is worse than `updated_at`.

Fix: define an explicit mapping from public API field names to internal field names. `"customer_id" → "fk_customer_id"`, `"updated_at" → "updated_at_utc_internal"`. The mapping layer decouples the public API surface from the internal model — internal refactoring doesn't break the API, and the API surface uses clean domain-meaningful names.

**Q26. What is the "over-filtering" or "arbitrary predicate" anti-pattern?**
A: The over-filtering anti-pattern is exposing a filter interface so general that it effectively gives clients direct database query access:

```
GET /users?filter=age > 25 AND (city = 'NYC' OR city = 'SF')
GET /products?where=price < 100 AND stock > 0 AND tags LIKE '%sale%'
GET /reports?sql=SELECT id, name FROM users WHERE active=1
```

These expose SQL or SQL-like predicates directly. Consequences: (1) **SQL injection surface** even with sanitization — arbitrary predicate parsers are hard to secure completely; (2) **performance unpredictability** — clients can construct queries that scan the entire database; (3) **schema coupling** — the filter language exposes the exact database schema; (4) **impossible to evolve** — changing the schema or moving to a different database breaks the filter expressions clients depend on.

Fix: restrict filters to the explicitly allowlisted fields with allowlisted operators. If the use case genuinely requires ad-hoc analytical queries, expose a proper query interface (GraphQL, SQL endpoint with row-level security) with appropriate rate limiting and access controls, not a general predicate on a REST collection endpoint.

**Q27. What is the "inconsistent field naming" anti-pattern across filter, sort, and field selection parameters?**
A: Inconsistent field naming uses different names for the same field depending on where it appears in the API:

```
GET /users?sort=userName        # camelCase in sort
GET /users?filter[user_name]=alice  # snake_case in filter
GET /users?fields=username      # no separator in fields
Response: {"user_name": "alice"}    # snake_case in body
```

Four different names for the same field in one endpoint. Consequences: clients must remember which form applies to which context; documentation is confusing; auto-generated client SDKs can't map filter/sort parameters to response fields. The client can't write `response.fields[filter_field_name]` — the names don't match.

Fix: use the same field name in all three contexts: filter parameters, sort parameters, field selection, and response body. If the response body uses `user_name` (snake_case), then the filter is `?filter[user_name]=alice`, the sort is `?sort=user_name`, and the field selection is `?fields=user_name`. One name per field, applied consistently everywhere.

## Section 8: Trade-offs & Decision-Making

**Q28. When should complex filtering use `POST /search` instead of `GET` with query parameters?**
A: Use `POST /search` when:
- **The filter is complex**: multiple nested AND/OR conditions, multiple range operators, full-text queries with boosts and facets. A query with 15 parameters in the URL is hard to read, hard to debug, and may approach URL length limits.
- **The filter contains sensitive data**: a search that includes a user's personal data (SSN, health condition) in the URL is a security and privacy risk — URLs appear in server logs, browser history, and HTTP referrer headers. A POST body is not logged by default.
- **The filter needs to be saved or shared**: `POST /searches` creates a search resource with a stable ID; `GET /searches/{id}` retrieves the results for that saved search. Clients share the search ID, not the complex query string.
- **URL length limits are a concern**: browsers and some infrastructure cap URLs at 2,000–8,000 characters. A complex filter with many values can exceed this. POST body has no practical size limit.

Use `GET` with query parameters when:
- Filters are simple (3–5 parameters of simple equality and range operators).
- Cacheability matters — `GET /products?category=shoes&sort=-price` can be cached at CDN or reverse proxy level; `POST /search` cannot (POST responses are not cached by default).
- The API is intended to be bookmarkable, shareable, or linked.

**Q29. How do you design field selection for APIs that serve multiple client types (mobile, web, embedded)?**
A: Different client types have fundamentally different needs from the same resource:
- **Mobile**: minimal payload — battery, bandwidth, and CPU constrained. Needs: `id`, `title`, `thumbnail_url`, `price`.
- **Web (list view)**: moderate payload — needs most fields for rendering a card: `id`, `title`, `description`, `price`, `rating`, `review_count`, `image_url`.
- **Web (detail view)**: full payload — needs all fields including expanded relationships.
- **Embedded/IoT**: micro payload — might need only `id` and `status`.

Two strategies:

**Generic field selection** (`?fields=id,title,price`): the client specifies exactly what it needs. Maximally flexible; the server applies one implementation supporting all clients. Downside: each client team must independently discover and maintain the field list; mobile developers must explicitly request minimal fields (and often forget, defaulting to full objects).

**Named response profiles**: predefined sets of fields the server supports: `?view=compact`, `?view=summary`, `?view=full`. Easy for clients (no field enumeration required); stable (the server controls the profile definition); but inflexible (a client needing 8 of the 10 "summary" fields still gets all 10, and can't add a field not in the profile without a server-side change). Named profiles are appropriate when client types are stable and well-known; generic field selection is better for a public API with unknown client diversity.

**Q30. How does field selection interact with HTTP caching, and what is the cache key problem?**
A: HTTP caches key on URL by default. `GET /users/123?fields=id,name` and `GET /users/123?fields=id,name,email` are different URLs — they are cached as separate entries, each with their own TTL. This is correct behavior but has implications:

- **Cache fragmentation**: many distinct `?fields` combinations produce many distinct cache entries for the same underlying resource. A shared cache (CDN, reverse proxy) may hold hundreds of variants of `/users/123` with different field sets, none benefiting from each other's hits.
- **The `Vary` header**: if field selection is implemented via a header (not a query parameter), the `Vary` header must list that header to prevent caches from serving the wrong variant. `Vary: Fields` ensures each field set is cached separately.
- **Upstream caching strategy**: for field-selected responses, cache at the application level (Redis) using the full URL (including `?fields=...`) as the cache key. Don't rely on CDN-level caching for field-selected API responses — the fragmentation makes CDN hit rates low. CDN caching is more appropriate for non-parameterized or lightly parameterized endpoints.
- **Server-side aggregation**: cache the full resource in Redis (`/users/123 → full JSON`), then apply field selection in the application layer before returning to the client. This way, field selection doesn't fragment the resource cache — only one cache entry per resource ID, regardless of which fields are requested.

## Section 9: Scenario / System Design Style Questions

**Q31. "Design the filtering, sorting, and field selection interface for an e-commerce product catalog API with 5 million products across 200 categories."**
A:
**Filtering** (allowlisted fields with indexes):
```
GET /products
  ?category_id=42          # exact match (indexed)
  &brand_id[in]=1,2,3      # set membership (indexed)
  &price[gte]=50
  &price[lte]=500          # range (composite index: category_id, price)
  &rating[gte]=4.0         # range (indexed)
  &in_stock=true           # boolean (partial index)
  &q=running+shoes         # full-text search (FTS index)
  &available_date[lte]=2024-12-31  # date range
```

**Sorting** (allowlisted, all with `id` tiebreaker):
```
  &sort=-relevance         # FTS relevance score (default with q=)
  &sort=-rating            # rating desc, id desc
  &sort=price              # price asc, id asc
  &sort=-created_at        # newest first (default without q=)
  &sort=name               # alphabetical
```

**Field selection** (two tiers):
```
  &fields=id,name,price,rating,thumbnail_url   # list view
  &fields=id,name,price,description,rating,review_count,images,specifications  # detail view
  &include=brand,category  # expand relationships
```

**Pagination**: cursor-based with `limit` (default 20, max 100). Cursor encodes the sort key + id tiebreaker.

**Performance design**: composite indexes for common filter+sort combinations: `(category_id, price)`, `(category_id, rating)`, `(brand_id, price)`. FTS index (Elasticsearch or Postgres `tsvector`) for `q=`. Partial index on `in_stock=true` for stock filtering. Field selection pushed to DB (`SELECT` only requested columns). Cache full product objects in Redis; apply field selection in the app layer.

**Q32. "A client reports that `GET /users?sort=name&page=2` returns a user that was already on page 1. Diagnose and fix."**
A: Classic pagination instability — the sort is not deterministic for ties.

**Diagnosis**: `sort=name` orders users by the `name` column. Multiple users may share the same name (common names like "John Smith"). The database's ordering of records with equal `name` values is non-deterministic — it may vary between executions based on internal row storage order, query plan choices, or concurrent modifications. Page 1 fetched 20 users; by the time page 2 was fetched, the ordering of tied records shifted, and a user from the tied group "moved" to appear in both pages.

**Fix**: add a stable unique tiebreaker to all sorts. The sort `name` becomes `name, id` in the database:

```sql
-- Page 1: no cursor
SELECT id, name FROM users ORDER BY name ASC, id ASC LIMIT 20
-- Returns last record: {name: "John", id: 47}

-- Page 2: cursor = base64({name: "John", id: 47})
SELECT id, name FROM users
WHERE (name, id) > ('John', 47)
ORDER BY name ASC, id ASC LIMIT 20
```

The cursor encodes both sort key values. The `WHERE (name, id) > ('John', 47)` clause uses tuple comparison (supported in PostgreSQL and MySQL) to correctly seek to the next position. This requires a composite index on `(name, id)` for efficiency.

Expose this in the API: the `sort=name` parameter is mapped server-side to `ORDER BY name ASC, id ASC`. The cursor always includes all sort key values plus the tiebreaker. The client doesn't need to know about the tiebreaker — it's an implementation detail of the cursor.

**Q33. "Design the field selection implementation to prevent a user from requesting `?fields=password_hash,admin_token,internal_flags`."**
A: Three-layer defense:

**Layer 1 — Field allowlist per resource**: define all publicly returnable fields:
```python
USER_PUBLIC_FIELDS = {
    "id", "name", "email", "created_at", "avatar_url",
    "bio", "subscription_tier", "last_active_at"
}
USER_SENSITIVE_FIELDS = {"phone"}  # returnable only to the user themselves or admins
USER_INTERNAL_FIELDS = {"password_hash", "admin_token", "internal_flags"}  # never returned
```

**Layer 2 — Request validation**: when the client sends `?fields=id,name,password_hash`:
```python
def validate_fields(requested: set, user: User, auth: AuthContext) -> set:
    allowed = USER_PUBLIC_FIELDS.copy()
    if auth.user_id == user.id or auth.is_admin:
        allowed |= USER_SENSITIVE_FIELDS
    # USER_INTERNAL_FIELDS is never added to allowed

    unknown = requested - allowed - USER_INTERNAL_FIELDS
    if unknown:
        raise ValidationError(f"Unknown fields: {unknown}")  # 400

    disallowed = requested & USER_INTERNAL_FIELDS
    if disallowed:
        raise ValidationError(f"Fields not available: {disallowed}")  # 400 or 403

    return requested & allowed  # intersection with allowed
```

**Layer 3 — Response serialization**: even without explicit field selection, the serializer never emits internal fields — they are excluded at the serializer level as a second line of defense. Never rely solely on field selection validation; the serializer must independently never include sensitive fields.

**Behavior for unknown fields**: returning `400` with the unknown field names listed (`"Unknown fields: password_hash, admin_token"`) is correct — it gives the client actionable feedback. Note: this reveals that the field exists but is not accessible. If preventing the existence of a field from being confirmed is a security requirement (for fields like `is_under_investigation`), return `400 Unknown field` without enumerating which fields are unknown or available.

**Q34. "Your API documentation says filtering is supported, but a client reports that `GET /orders?customer_name=alice` returns all orders, not just Alice's. What's happening and how do you fix it?"**
A: The client is filtering on `customer_name` but the server isn't applying it — it's silently ignoring unrecognized filter parameters and returning the full result set.

**What's happening**: two possible root causes: (1) the server has no allowlist — it only processes known filter parameters and ignores others; `customer_name` isn't a known filter so it's silently dropped; (2) the server maps filter parameters to fields but `customer_name` is not in the field mapping — orders are filtered by `customer_id`, not `customer_name` (which is on the customer entity, not the order).

**Why it's bad**: silent filter dropping is dangerous — the client thinks they're getting filtered results and may make decisions (e.g., "Alice has no pending orders") based on an unfiltered result set. The API is untrustworthy.

**Fix 1 — Reject unknown filter parameters**: any query parameter that looks like a filter but isn't in the allowlist returns `400 Bad Request`:
```json
{"error": {"code": "INVALID_FILTER_FIELD", "message": "Unsupported filter field: customer_name. Supported fields: customer_id, status, created_at, total"}}
```

**Fix 2 — Support the intended filter**: if filtering by customer name is a legitimate use case, add it to the allowlist. Since `customer_name` is on the customer table, this requires a JOIN: `?customer_name=alice` → `JOIN customers ON orders.customer_id = customers.id WHERE customers.name ILIKE 'alice'`. Or support: `?customer_id=42` (the canonical filter by customer) and document that name-based lookup requires first resolving the customer ID.

**Fix 3 — Strict mode parameter validation**: add a validation middleware layer that checks every query parameter against the allowlist of known parameters (filter fields, sort, pagination, field selection) and rejects requests with unrecognized parameters.

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| LHS bracket notation          | Operator encoded in parameter name: `?price[gte]=10` — field on left, operator in brackets                 |
| RHS colon notation            | Operator encoded as value prefix: `?price=gte:10` — field in key, operator before colon in value           |
| Field allowlist               | Explicit set of fields that may be filtered, sorted, or selected; all others are rejected                   |
| Parameterized query           | SQL query with `$1`, `$2` placeholders for values; driver handles escaping — prevents SQL injection         |
| Stable sort                   | Sort with a unique tiebreaker ensuring deterministic ordering for equal keys; required for pagination        |
| Keyset pagination             | Cursor-based pagination using `WHERE (sort_key, id) > (last_sort_value, last_id)` — O(log N) seek           |
| Sparse fieldsets              | JSON:API term for per-type field selection in compound documents: `?fields[articles]=title,body`            |
| Cursor                        | Opaque base64-encoded token encoding position in sorted, filtered result set; sort-specific                 |
| Relationship expansion        | `?include=customer` embeds a related resource rather than returning just its ID                             |
| Dot notation                  | `address.city` in fields/filters to reference nested or related resource attributes                         |
| Full-text search parameter    | `?q=` or `?search=` — searches across multiple text fields via FTS index, not a single-field filter        |
| Total count opt-in            | `?count=true` triggers `COUNT(*)` for total results; omitted by default for performance                     |
| Named response profiles       | `?view=compact` — server-defined field sets for common client types; less flexible than generic field selection|
| Null sort behavior            | How null values are positioned in sort order; must be consistent and documented                             |
| Silent filter drop            | Anti-pattern: server ignores unknown filter parameters instead of rejecting them; causes data trust issues   |
| Computed sort alias           | `?sort=popularity` maps to a computed/derived sort not directly corresponding to a column                   |
| `Vary` header                 | HTTP header listing request headers that affect the response; tells caches to store separate entries per variant|
| Max page size                 | Hard ceiling on `limit` parameter regardless of what the client requests; prevents unbounded result sets    |

**Tip for the interview:** Filtering, sorting, and field selection interviews reveal whether candidates have thought about the operational and security dimensions, not just the syntax. The key points that separate senior candidates: (1) **allowlisting** — always validate filter and sort fields against an allowlist before touching the database (SQL injection and DoS prevention); (2) **stable sort** — naming the tiebreaker problem unprompted before discussing cursor pagination shows you've debugged pagination bugs in production; (3) **silent filter drop is an anti-pattern** — the API must reject unknown filter fields, not silently ignore them; (4) **field selection has a security dimension** — the server must intersect requested fields with auth-context-appropriate allowed fields, never trust the client's requested list blindly; (5) the **`POST /search` vs `GET` trade-off** — knowing when complex filters belong in a request body (sensitive data, URL length limits, boolean logic) vs query parameters (cacheable, simple, shareable) shows architectural judgment.
