# Versioning Strategies: URI Versioning, Header Versioning, Content Negotiation — Interview Q&A (5 YOE Level)

---

## Section 1: Why API Versioning Exists

**Q1. What problem does API versioning solve, and why is it unavoidable for long-lived APIs?**
A: API versioning solves the **backward compatibility problem**: the contract between an API and its consumers must remain stable, but the API's implementation must evolve. Without versioning, any breaking change to the API — removing a field, changing a field's type, renaming an endpoint, altering error codes — immediately breaks every client that depends on the old contract. This is unacceptable when clients are third parties (mobile apps with slow release cycles, partner integrations, public SDK users) who cannot update on the API team's schedule.

Versioning is unavoidable because:
- **Business requirements change** — a field that was optional becomes required, a resource is redesigned, a workflow is restructured. Not all changes can be made backward-compatibly.
- **Clients cannot be forced to update synchronously** — a mobile app user may not update for months after a new version is released. The old API version must remain operational during a long transition window.
- **Multiple client generations coexist** — an enterprise with a 5-year-old integration and a startup with a 2-week-old integration may both be active simultaneously. Both must work correctly.

The alternative to explicit versioning — relying entirely on backward-compatible evolution — is a discipline that reduces but does not eliminate the need for versioning. Some changes are inherently breaking (a resource model redesign, a security model change, a performance-driven restructuring), and no amount of additive evolution avoids them permanently.

**Q2. What is the difference between a "breaking change" and a "non-breaking change," and why does this distinction drive versioning decisions?**
A: A **breaking change** is any change that causes a correctly-implemented client to fail or behave incorrectly without modification. A **non-breaking (additive) change** is one that existing clients can safely ignore or handle without modification.

**Breaking changes (require a new API version):**
- Removing a field from a response.
- Renaming a field (same as removing the old and adding the new).
- Changing a field's data type (`string` → `integer`, `object` → `array`).
- Changing a field's nullability (was nullable, now required — existing clients may not send it).
- Removing or renaming an endpoint.
- Changing the semantics of an existing field (field `status` previously had values `['active', 'inactive']`, now uses `['enabled', 'disabled']`).
- Changing authentication or authorization model.
- Changing error response structure.
- Changing pagination behavior (cursor-based → offset-based).

**Non-breaking changes (do not require a new version):**
- Adding a new optional field to a response (well-implemented clients ignore unknown fields).
- Adding a new optional query parameter.
- Adding a new endpoint.
- Adding a new value to an enum (if clients are written to handle unknown enum values gracefully — this is a grey area).
- Relaxing a validation constraint (was required, now optional).
- Performance improvements with identical observable behavior.

The distinction drives versioning decisions because every new API version is an operational burden: it must be maintained, tested, monitored, and eventually deprecated. Teams that misclassify non-breaking changes as breaking (and create unnecessary versions) accumulate technical debt. Teams that misclassify breaking changes as non-breaking (and skip versioning) break clients silently — often with no immediate feedback, only discovered when a client reports a bug weeks later.

**Q3. What are the four main REST API versioning strategies, and what dimension does each one version along?**
A: The four strategies each version along a different axis of the HTTP request:

- **URI versioning** — the version is in the URL path: `GET /v2/orders`. Every client sees the version in the URL. Versions are explicit and visible at the routing/infrastructure layer.
- **Query parameter versioning** — the version is in a query string: `GET /orders?version=2`. Still URL-visible but path-agnostic. Used less frequently in REST; more common in older APIs and some Google APIs.
- **Header versioning** — the version is in a custom HTTP request header: `GET /orders` with `API-Version: 2`. The URL is clean and stable; version is in the request metadata. Explicit but not visible in URLs.
- **Content negotiation (Accept header versioning)** — the version is embedded in the `Accept` header's media type: `Accept: application/vnd.myapi.v2+json`. The most HTTP-standards-compliant approach. The version is part of the requested representation, not the resource identity.

Each strategy is a trade-off across: URL clarity, cacheability, client complexity, infrastructure routing complexity, and adherence to REST semantics. The choice matters most at scale — when there are hundreds of clients, dozens of endpoints, and multi-year deprecation timelines.

## Section 2: URI Versioning

**Q4. How does URI versioning work, and what does a versioned URL structure look like?**
A: URI versioning embeds the API version as a path segment, typically at the root of the API path:

```
https://api.example.com/v1/orders
https://api.example.com/v1/orders/{id}
https://api.example.com/v1/users/{id}/orders

https://api.example.com/v2/orders          ← new version
https://api.example.com/v2/orders/{id}
```

Less commonly, the version appears at a lower path level:
```
https://api.example.com/orders/v2          ← resource-level versioning
```
Resource-level versioning is rarely used because it creates inconsistency — different resources at different versions require clients to track per-resource version state, which is operationally complex.

The version identifier is almost always a major version number only (`v1`, `v2`, `v3`). Minor and patch versions are not exposed in URIs because they should only represent backward-compatible changes that don't require clients to change — exposing them in URIs forces URL changes for non-breaking updates, which defeats the purpose.

Infrastructure handling: the version prefix enables routing at the load balancer or API gateway layer — `/v1/*` routes to the v1 service or Lambda function; `/v2/*` routes to the v2 service. This is the simplest versioning strategy to route at the infrastructure layer, which is why it is by far the most widely adopted in practice.

**Q5. What are the arguments for URI versioning, and why do large-scale APIs (Stripe, Twilio, GitHub) predominantly use it?**
A: URI versioning is dominant in production APIs for a set of compounding practical reasons:

**Visibility and debuggability** — the version is in the URL, making it immediately obvious in: browser developer tools, server access logs, API gateway logs, HTTP client traces, and error messages. When an incident occurs at 3am, "the v1 endpoint is returning 500s" is instantly diagnosable from the access log. "The endpoint with `API-Version: 1` header is returning 500s" requires a log query with header filtering.

**Cacheability** — HTTP caches (CDN, reverse proxy, browser cache) key on URLs by default. A v1 and v2 response to the same resource are different URLs with different cache entries — they don't pollute each other's cache. Header-versioned endpoints require `Vary: API-Version` to correctly partition caches, which many CDN configurations handle poorly or ignore entirely.

**Copy-paste sharing** — when a developer shares a URL in Slack, a Jira ticket, or a Postman collection, the version is embedded. `https://api.example.com/v2/orders/12345` tells the recipient exactly what version they're calling. A URL without the version is ambiguous.

**Simple infrastructure routing** — `/v1/*` and `/v2/*` are trivially routed at the nginx/Kubernetes ingress/API gateway level without needing to inspect headers. No custom routing logic required.

**Gateway and proxy compatibility** — many API gateways (AWS API Gateway, Kong, Apigee) have first-class support for path-based routing and versioning. Header-based routing requires custom plugins or routing configurations that vary by gateway vendor.

Why Stripe, Twilio, and GitHub use it: large-scale public APIs prioritize developer experience over REST purity. URI versioning has the lowest cognitive overhead for API consumers — the version is right there in the URL, and the developer never has to remember to add a header.

**Q6. What are the criticisms of URI versioning from a REST purism perspective, and are they practically significant?**
A: The REST purist critique of URI versioning is rooted in Roy Fielding's original REST constraints:

**REST critique 1 — URIs should identify resources, not representations:**
`/v1/orders` and `/v2/orders` are the same resource (the collection of orders) — they differ only in the representation format returned. By REST principles, a URI should identify a resource uniquely; different representations of the same resource should be negotiated via `Accept` headers (content negotiation), not encoded in the URI. The `/v2/` prefix is not identifying a different resource — it's identifying a different contract.

**REST critique 2 — Version URIs break HATEOAS:**
Hypermedia as the Engine of Application State (HATEOAS) requires that responses include links to related resources. If a v1 response links to `/v1/orders/{id}/items` and a client follows that link, they'll call v1 — but they might have intended to call v2. Versioned URIs make cross-version linking and resource discovery brittle.

**Practical significance of these critiques:** low for most production APIs. HATEOAS is theoretically compelling but rarely fully implemented in practice. The "resources vs representations" argument is philosophically correct but has minimal operational impact — the version is a different contract that justifies a different URI in pragmatic terms. The developer experience and operational simplicity advantages of URI versioning consistently outweigh the theoretical elegance concerns in real-world API design.

The critiques matter in academic discussions and in APIs designed for extreme longevity (20+ years), where the correctness of HATEOAS navigation becomes genuinely important. For most product APIs with 3–5 year lifespans, URI versioning is the right pragmatic choice.

**Q7. How do you handle the URL structure for URI-versioned APIs in a Node.js Express application?**
A:

```javascript
// app.js — top-level Express application wiring
const express = require('express');
const app = express();

// V1 router — maintains backward compatibility indefinitely
const v1Router = require('./routes/v1');
// V2 router — new contract (restructured order response, new field names)
const v2Router = require('./routes/v2');

app.use('/v1', v1Router);
app.use('/v2', v2Router);

// Redirect unversioned requests to current stable version
// This is optional — many APIs simply 404 on /orders without a version
app.use('/orders', (req, res) => {
  res.redirect(301, `/v2${req.url}`);
});

module.exports = app;
```

```javascript
// routes/v2/orders.js — v2 order routes
const express  = require('express');
const router   = express.Router();
const { getOrder, listOrders } = require('../../controllers/v2/ordersController');

router.get('/orders',     listOrders);
router.get('/orders/:id', getOrder);

module.exports = router;
```

```javascript
// controllers/v2/ordersController.js
// V2 restructures the response: flattens nested address, renames 'created' to 'createdAt'
const orderService = require('../../services/orderService');

async function getOrder(req, res) {
  try {
    const order = await orderService.findById(req.params.id);
    if (!order) return res.status(404).json({ error: 'Order not found' });

    // V2 response shape
    res.json({
      id:          order.id,
      status:      order.status,
      totalAmount: order.total_amount,   // renamed from 'total' in v1
      currency:    order.currency,
      createdAt:   order.created_at,     // renamed from 'created' in v1
      customer: {
        id:    order.customer_id,
        email: order.customer_email,
      },
      // V2 flattens the shipping address (was nested object in v1)
      shippingStreet:  order.shipping_street,
      shippingCity:    order.shipping_city,
      shippingCountry: order.shipping_country,
    });
  } catch (err) {
    res.status(500).json({ error: 'Internal server error' });
  }
}

module.exports = { getOrder, listOrders };
```

Structurally: each version has its own router and controller directory. Shared business logic lives in the `services/` layer — versioning only affects the request/response transformation, not the core domain logic. This prevents code duplication in business logic while keeping API contract transformation explicit and version-isolated.

## Section 3: Header Versioning

**Q8. How does header versioning work, and what does a versioned request look like?**
A: Header versioning places the API version in a custom HTTP request header rather than in the URL. The URL stays stable and resource-centric; the version is metadata on the request:

```http
GET /orders/12345 HTTP/1.1
Host: api.example.com
API-Version: 2
Authorization: Bearer eyJhbGci...
Accept: application/json
```

The server reads the `API-Version` header and routes or dispatches accordingly. If the header is absent, the server applies a default version policy (usually the latest stable version or the first version — depends on the API's evolution philosophy).

There is no standardized header name — common choices include:
- `API-Version` (Salesforce, internal enterprise APIs)
- `X-API-Version` (the `X-` prefix signals a non-standard extension header; RFC 6648 deprecated this convention but it remains common)
- `Accept-Version` (used by some Node.js frameworks; semantically closer to content negotiation)

The version value is typically a major integer (`1`, `2`) or a date string (`2024-01-15` — Stripe's actual versioning scheme uses dates, not integers, which is a header-versioned approach that uniquely identifies the API contract by the date it was introduced).

**Q9. What are Stripe's API versioning design decisions, and what makes them notable?**
A: Stripe's versioning is one of the most thoughtfully designed in the industry and diverges from typical patterns in several ways:

**Date-based version identifiers:**
Stripe versions are dates, not integers: `Stripe-Version: 2023-10-16`. The date represents when the breaking change was introduced. This gives clients more information than `v2` — they can look at the changelog for `2023-10-16` and know exactly what changed on that date. Multiple changes may be bundled into the same date-version; each date represents a point-in-time snapshot of the entire API contract.

**Per-account version pinning:**
When a developer first creates a Stripe API key, their account is pinned to the current API version. Every API call from that account defaults to that pinned version — even years later, as Stripe ships new versions. The developer is never surprised by a breaking change unless they explicitly upgrade their version. To upgrade, they test their integration against the new version (using the `Stripe-Version` header to override), verify it works, and update the pinned version in their Stripe dashboard.

**Backwards-compatible by default:**
Stripe ships new API contract versions rarely — the majority of API changes are shipped as non-breaking additions (new endpoints, new optional fields, new event types). A date-version is created only for genuinely breaking changes. The discipline of minimizing breaking changes means the average Stripe customer may go years between forced upgrades.

**What makes this notable:** Stripe's API supports thousands of different version dates simultaneously across millions of customers. This requires a versioning implementation that is a routing/transformation layer rather than parallel codebases — the same underlying business logic serves all versions, with per-version transformation applied at the API layer. This is significantly harder to implement than URI versioning with separate route handlers but is operationally superior for a public API with extreme durability requirements.

**Q10. How do you implement header versioning in Node.js Express, including default version handling?**
A:

```javascript
// middleware/apiVersion.js — extracts and normalizes the API version from headers
const SUPPORTED_VERSIONS = [1, 2];
const DEFAULT_VERSION     = 2;      // latest stable version is the default
const DEPRECATED_VERSIONS = [1];    // still supported but emit deprecation warnings

function apiVersionMiddleware(req, res, next) {
  const rawVersion = req.headers['api-version'] ?? req.headers['x-api-version'];

  let version;
  if (rawVersion === undefined || rawVersion === null) {
    version = DEFAULT_VERSION;
    // Optionally: require explicit versioning and return 400 if absent
    // return res.status(400).json({
    //   error: 'API-Version header is required',
    //   supportedVersions: SUPPORTED_VERSIONS,
    // });
  } else {
    version = parseInt(rawVersion, 10);
    if (isNaN(version) || !SUPPORTED_VERSIONS.includes(version)) {
      return res.status(400).json({
        error:             'Unsupported API version',
        requestedVersion:  rawVersion,
        supportedVersions: SUPPORTED_VERSIONS,
      });
    }
  }

  req.apiVersion = version;

  // Warn clients using deprecated versions
  if (DEPRECATED_VERSIONS.includes(version)) {
    res.set('Sunset', 'Sat, 01 Jan 2027 00:00:00 GMT');   // RFC 8594
    res.set('Deprecation', 'true');                         // RFC 8594
    res.set('Link', '</v2/docs>; rel="successor-version"'); // RFC 8288
  }

  next();
}

module.exports = { apiVersionMiddleware };
```

```javascript
// app.js — apply version middleware globally
const express = require('express');
const { apiVersionMiddleware } = require('./middleware/apiVersion');
const ordersRouter = require('./routes/orders');

const app = express();
app.use(express.json());
app.use(apiVersionMiddleware);      // attaches req.apiVersion to every request
app.use('/orders', ordersRouter);

module.exports = app;
```

```javascript
// routes/orders.js — version-aware route handler
const express = require('express');
const router  = express.Router();
const v1      = require('../controllers/v1/ordersController');
const v2      = require('../controllers/v2/ordersController');

function versionedHandler(handlers) {
  return (req, res, next) => {
    const handler = handlers[req.apiVersion];
    if (!handler) {
      return res.status(400).json({
        error:  `Endpoint not available in API version ${req.apiVersion}`,
        latestVersion: 2,
      });
    }
    return handler(req, res, next);
  };
}

router.get('/',    versionedHandler({ 1: v1.listOrders,   2: v2.listOrders }));
router.get('/:id', versionedHandler({ 1: v1.getOrder,     2: v2.getOrder }));
router.post('/',   versionedHandler({ 1: v1.createOrder,  2: v2.createOrder }));

module.exports = router;
```

The `versionedHandler` utility dispatches to the version-appropriate controller based on `req.apiVersion`. The URL is identical for all versions — only the request header differs. The `Sunset` and `Deprecation` response headers follow RFC 8594, which standardizes how APIs communicate deprecation timelines to clients.

**Q11. What are the operational challenges of header versioning that don't exist with URI versioning?**
A: Header versioning introduces several operational concerns that URI versioning avoids:

**Caching complexity:**
HTTP caches (CDN, Varnish, nginx proxy_cache) key on the request URL by default. Two requests to `/orders/123` — one with `API-Version: 1` and one with `API-Version: 2` — have the same URL but expect different responses. Without proper cache configuration, a cache may return the v1 response to a v2 client (or vice versa), causing subtle bugs. The fix: `Vary: API-Version` response header tells the cache to include the `API-Version` header in the cache key. But many CDNs (CloudFront, Fastly, Cloudflare) either don't support `Vary` on custom headers or require explicit configuration, making this easy to misconfigure. URI versioning sidesteps this entirely — different URLs have separate cache entries by default.

**Load balancer and API gateway routing:**
Path-based routing (`/v1/*` → v1 backend) is a first-class feature of every load balancer and API gateway. Header-based routing (requests with `API-Version: 1` → v1 backend) requires custom configuration — Kubernetes ingress controllers, nginx location blocks, or API gateway routing rules that inspect request headers. This is feasible but adds infrastructure complexity and is a potential misconfiguration surface.

**Log filtering and debugging:**
Access logs at the load balancer, CDN, or application level typically capture the URL. To identify which API version is being called, engineers must either configure custom log fields for the `API-Version` header or add application-level logging. With URI versioning, `grep /v1/ access.log` is a one-liner.

**Client SDK complexity:**
Clients must always remember to include the version header. A client that forgets the header gets the default version — which may not be what the developer expected, causing silent behavioral differences. URI versioning makes it impossible to forget the version (it's in the URL). Header versioning is more fragile for consumer implementations.

## Section 4: Content Negotiation

**Q12. What is content negotiation versioning, and how does it use the `Accept` header?**
A: Content negotiation versioning embeds the API version in the `Accept` request header's media type, using a vendor-specific MIME type:

```http
GET /orders/12345 HTTP/1.1
Host: api.example.com
Accept: application/vnd.myapi.v2+json
Authorization: Bearer eyJhbGci...
```

The `vnd.` prefix denotes a vendor-specific media type (registered with IANA or used privately). The full media type encodes: the API vendor (`myapi`), the version (`v2`), and the serialization format (`+json`). The server reads the `Accept` header, selects the best matching representation, and returns it with a `Content-Type` header confirming the representation served:

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.myapi.v2+json
Vary: Accept
```

If the server cannot produce a representation matching any of the client's `Accept` values, it returns `406 Not Acceptable` — the HTTP-standard response for media type negotiation failure, in contrast to header versioning which requires custom error handling for unrecognized versions.

Content negotiation leverages the HTTP protocol's existing mechanism for resource representation negotiation (designed for format selection — JSON vs XML vs HTML), repurposing it for API version selection. The GitHub API (v3) uses this approach with `application/vnd.github.v3+json`.

**Q13. What are the advantages of content negotiation versioning from a REST correctness perspective?**
A: Content negotiation versioning is the most HTTP-standards-compliant versioning strategy, with several theoretical advantages:

**Correct URI semantics:**
`/orders/12345` refers to the same resource regardless of the API version. The version is a property of the *representation* requested (how the resource is described to the client), not of the resource itself. This is how HTTP was designed to work — `Accept: text/html` and `Accept: application/json` request different representations of the same resource. `Accept: application/vnd.myapi.v1+json` vs `application/vnd.myapi.v2+json` follows the same principle.

**Protocol-native negotiation:**
HTTP already has a well-defined negotiation mechanism (`406 Not Acceptable`, `Vary` header, quality factors in `Accept` values). Content negotiation reuses these semantics rather than inventing custom conventions. A client can even request multiple acceptable versions: `Accept: application/vnd.myapi.v2+json, application/vnd.myapi.v1+json;q=0.8` — "prefer v2 but accept v1 with lower quality."

**Caching correctness:**
The `Vary: Accept` response header correctly signals that the response varies by the `Accept` header value. This is standard HTTP caching behavior that every cache implementation understands — no custom configuration needed.

**Stable bookmarkable URLs:**
`/orders/12345` is a stable, version-agnostic URL. Documentation can link to it, Slack messages can share it, and the URL doesn't become stale when the API version changes. This is the most user-visible practical advantage over URI versioning.

**Q14. Why is content negotiation versioning rarely used in practice despite its theoretical superiority?**
A: Content negotiation versioning has theoretical correctness but low adoption in production APIs for a set of concrete practical reasons:

**Developer ergonomics:**
`GET /v2/orders` is immediately readable and requires no explanation. `GET /orders` with `Accept: application/vnd.myapi.v2+json` requires knowing the vendor MIME type string exactly. A typo in `vnd.myapi.v2+json` (wrong vendor name, wrong version format) results in a `406` or falls through to a default version silently. The cognitive overhead per API call is higher, and the value (`application/vnd.myapi.v2+json`) is not easily discoverable without reading documentation.

**Browser and tool compatibility:**
Browser address bars, `curl` without flags, Postman's default GET, and most API testing tools use the URL directly. They don't add custom `Accept` headers. Testing and exploring a URI-versioned API requires only a browser. Testing a content-negotiated API requires always configuring the `Accept` header — in every client, test, and tool.

**Proxy and intermediary stripping:**
Some HTTP intermediaries (older corporate proxies, certain CDN configurations, some API gateways) strip or normalize `Accept` headers. A client sending `Accept: application/vnd.myapi.v2+json` through such a proxy may arrive at the server with a transformed or missing `Accept` header — silently falling back to a default version.

**Logging and monitoring:**
Same as header versioning — the version is not in the URL, making access log analysis harder.

**The practical result:** content negotiation versioning is used by teams with strong REST principles and sophisticated API consumers (the GitHub API is a canonical example — its consumers are developers who work with HTTP daily and understand the `Accept` header). It is rarely the right choice for consumer-facing product APIs, mobile SDKs, or public APIs targeting developers of varying HTTP sophistication.

## Section 5: Deprecation and Sunset

**Q15. What is the "Sunset" header (RFC 8594), and how should it be implemented?**
A: The `Sunset` HTTP response header (RFC 8594) communicates to clients when an API version or endpoint will stop being available. Its value is an HTTP date:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Deprecation: true
Link: <https://api.example.com/v3/docs>; rel="successor-version"
```

The `Sunset` header standardizes what was previously communicated only in documentation or email. Clients that parse response headers can automate deprecation detection — SDK libraries can log warnings; monitoring tools can alert when a response includes a sunset date.

Implementation in the versioning middleware:

```javascript
// middleware/deprecation.js
const DEPRECATION_SCHEDULE = {
  1: {
    deprecatedAt: new Date('2025-01-01'),
    sunsetAt:     new Date('2027-01-01'),
    successorVersion: 2,
    successorDocs: 'https://api.example.com/v2/docs',
  },
};

function deprecationMiddleware(req, res, next) {
  const schedule = DEPRECATION_SCHEDULE[req.apiVersion];
  if (!schedule) return next();

  const now = new Date();

  if (now >= schedule.deprecatedAt) {
    // Set RFC 8594 headers
    res.set('Sunset',      schedule.sunsetAt.toUTCString());
    res.set('Deprecation', schedule.deprecatedAt.toUTCString());
    res.set('Link',
      `<${schedule.successorDocs}>; rel="successor-version", ` +
      `<https://api.example.com>; rel="deprecation"`
    );
  }

  if (now >= schedule.sunsetAt) {
    // Hard sunset: reject requests past the deadline
    return res.status(410).json({
      error:    'API version has been sunset',
      version:  req.apiVersion,
      sunsetAt: schedule.sunsetAt.toISOString(),
      message:  `Please upgrade to v${schedule.successorVersion}. See: ${schedule.successorDocs}`,
    });
  }

  next();
}

module.exports = { deprecationMiddleware };
```

The HTTP `410 Gone` response (not `404 Not Found`) correctly signals that the resource previously existed but has been permanently removed — the semantically correct status for a sunset API version.

**Q16. What is the versioning deprecation lifecycle, and what steps does it require from the API team?**
A: A well-managed deprecation lifecycle has four phases, each with specific activities:

**Phase 1 — New version launch:**
- Release the new API version (v2) alongside the existing version (v1).
- Publish a migration guide with explicit diff of breaking changes, before/after code examples for every breaking change, and a migration timeline.
- Add `Sunset` headers to v1 responses with a concrete end-of-life date (minimum 6 months out for internal clients; 12–24 months for public/partner APIs).
- Notify existing v1 clients via email, developer portal announcement, and SDK changelogs.

**Phase 2 — Active deprecation (most of the lifecycle):**
- Monitor v1 traffic volume, client count, and client identities (using `User-Agent` or API key attribution). Track the migration curve — what percentage of clients have moved to v2?
- Communicate proactively with clients still on v1, especially as the sunset date approaches (90 days, 30 days, 7 days before).
- Maintain v1 for security patches and critical bug fixes, but ship no new features to v1.
- Provide a migration support period: office hours, migration tooling, a dedicated support channel.

**Phase 3 — Sunset enforcement:**
- Return `410 Gone` for v1 requests after the sunset date.
- For high-value clients who haven't migrated: consider a private extension of their v1 deadline (documented, time-bounded, with a firm final date).
- Monitor for requests that break (clients that weren't identified during active deprecation — third-party tools, bots, forgotten integrations).

**Phase 4 — Cleanup:**
- Remove v1 code from the codebase after a defined period post-sunset (typically 3–6 months, to confirm no emergency need to un-sunset).
- Remove v1-specific infrastructure (separate service, route configurations).
- Archive v1 documentation with a clear "deprecated/sunset" banner rather than deleting it — developers may still need to understand the old contract for historical context.

A common failure: announcing a sunset date and then extending it without consequence because large clients haven't migrated. Every extension teaches clients that sunset dates aren't real, accelerating the cycle of deadline-driven inaction. The most effective approach: enforce the sunset date for new API keys (no new clients on v1) while negotiating individual extensions for existing high-value clients — making the deadline credible for most clients while handling exceptions explicitly.

## Section 6: Choosing a Strategy

**Q17. Given a new API, how do you choose between URI versioning, header versioning, and content negotiation?**
A: The choice is driven by three factors: client type, team priorities, and infrastructure constraints:

**Choose URI versioning when:**
- The API is public or has many third-party consumers — visibility and simplicity outweigh REST purity.
- Consumers include non-developer audiences (mobile apps, low-code tools, browser-based integrations) who benefit from version being obvious in the URL.
- The infrastructure team wants simple routing — path-based routing is universally supported.
- Access log analysis and debugging simplicity are priorities.
- The team is building a product API (not a platform API) and wants to move fast.

**Choose header versioning when:**
- The API is primarily consumed by sophisticated developers who reliably set request headers.
- Clean, stable URLs are a product requirement (the URL is shared in user-facing contexts like webhooks or deep links).
- The team is committed to managing `Vary: API-Version` caching correctly.
- The API is internal (within a company) where clients are controlled and can be updated to include the version header reliably.
- Stripe-style per-key version pinning is desired — a header is easier to override per-request than a URL prefix.

**Choose content negotiation when:**
- The team has strong REST principles and the API consumers are HTTP-sophisticated (developer tools, platform APIs).
- Multiple representation formats (JSON, XML, MessagePack) are already being negotiated via `Accept` and versioning fits naturally into the same mechanism.
- The API is designed for extreme longevity and correctness over developer convenience.
- Building an API for other API developers (developer tools, infrastructure APIs, platform APIs).

**The pragmatic recommendation for most teams:** URI versioning. It is adopted by the most successful public APIs (Stripe, Twilio, GitHub, AWS, Google APIs), has the best tooling support, and makes debugging and monitoring the simplest. The REST-purity arguments against it are real but rarely matter operationally.

**Q18. What is "version-free" API design, and can it eliminate the need for versioning?**
A: Version-free API design (sometimes called "versionless" or "evergreen" APIs) is the philosophy that all API changes should be backward-compatible, eliminating the need for explicit versioning. The strategy: only ever add, never remove or change existing fields and endpoints.

Techniques for version-free evolution:
- **Additive changes only** — new fields are always optional; old fields are never removed or renamed.
- **Tolerant reader pattern** — clients are built to ignore unknown fields (enabled by JSON's schemaless nature — well-implemented JSON parsers silently skip unknown keys).
- **Deprecation without removal** — old fields are marked deprecated in documentation and set to null/empty before eventual removal — though "eventual removal" eventually requires a version anyway.
- **Feature flags** — new behavior is gated behind optional request parameters, not new versions.

Can it eliminate versioning entirely? No — for several reasons:

- **Some changes are inherently breaking** — a complete data model redesign, a security model change (OAuth scopes restructuring), or a performance change that changes the observable semantics (synchronous to asynchronous) cannot be made backward-compatible. These require a version.
- **Dead weight accumulates** — a versionless API that never removes anything accumulates deprecated fields, obsolete endpoints, and legacy behaviors indefinitely. The API grows increasingly complex and difficult to document.
- **Clients misuse "deprecated" fields** — marking a field deprecated does not prevent clients from using it. Years after deprecation, some clients will still depend on it, making removal impossible without a version bump.

Version-free design reduces the frequency of major version bumps — Facebook's Graph API and many GraphQL APIs use this approach effectively. But it is a discipline that reduces versioning frequency, not a technique that eliminates it. Long-lived APIs will always eventually need a major version.

## Section 7: Versioning in Practice

**Q19. How do you version a REST API that uses an API gateway (Kong, AWS API Gateway) rather than application-level routing?**
A: API gateways add a routing layer between clients and backend services that intersects with versioning strategy:

**URI versioning with gateway path routing (most common):**
```yaml
# Kong route configuration
routes:
  - name: orders-v1
    paths: ["/v1/orders"]
    service: orders-v1-service   # points to v1 backend deployment

  - name: orders-v2
    paths: ["/v2/orders"]
    service: orders-v2-service   # points to v2 backend deployment
```
Each version is a separate backend service (or a separate Lambda function in AWS API Gateway). The gateway routes by path prefix. This is the most operationally clean approach — v1 and v2 are independently deployable and scalable.

**Header versioning with gateway header-based routing:**
```yaml
# Kong route with header matching
routes:
  - name: orders-v1-header
    paths: ["/orders"]
    headers:
      API-Version: ["1"]
    service: orders-v1-service

  - name: orders-v2-header
    paths: ["/orders"]
    headers:
      API-Version: ["2"]
    service: orders-v2-service
```
Kong and AWS API Gateway support header-based routing, but it's less universally supported and harder to configure than path-based routing. Requires `Vary: API-Version` on responses for correct CDN behavior.

**Single service with internal version dispatch:**
Instead of separate services per version, a single service handles all versions and dispatches internally (as shown in Q7 and Q10). The gateway routes all traffic to one service; the service handles version-specific logic. Simpler infrastructure but tighter coupling between versions in the codebase.

The gateway-level separation (separate services per version) is preferred for major versions with significantly different implementations — it allows independent scaling, independent rollouts, and clean deprecation (removing the v1 service when the version is sunset). The single-service dispatch is preferred when versions share the majority of their implementation and only differ in request/response transformation.

**Q20. What is "API versioning for internal microservices," and does the same strategy apply?**
A: Internal microservices versioning follows the same principles but with different trade-offs due to different client characteristics:

**Internal consumers are controlled — updates are coordinated:**
Unlike public API clients who update on their own schedule, internal service-to-service clients can be updated as part of a coordinated release. This makes aggressive deprecation timelines feasible (days to weeks, not months to years) and reduces the operational burden of maintaining multiple versions.

**Service mesh adds a versioning layer:**
A service mesh (Istio, Linkerd) can route traffic based on request labels, headers, or metadata at the infrastructure layer without requiring application code changes. Canary deployments and traffic splitting (10% of traffic to v2, 90% to v1) become infrastructure concerns, not application concerns. This is a form of versioning implemented at the network layer.

**Contract testing reduces the need for explicit versioning:**
Pact (consumer-driven contract testing) lets services publish their expectations of each other's APIs as tests. Breaking changes are caught at CI/CD time before deployment — not at runtime when clients break. With good contract testing, internal services can evolve more aggressively because breaking changes are detected early, reducing the need for long-lived parallel versions.

**Recommended approach for internal services:**
- URI versioning for services with multiple active consumers at different stages of adoption.
- Semver in headers or deployment metadata for single-consumer internal services (one team calling another).
- Aggressive deprecation: 2-week deprecation notice is acceptable for internal consumers; 6-month is appropriate for shared internal platforms.
- Contract testing as the primary safety net — versioning as a fallback for when breaking changes cannot be avoided.

## Section 8: Scenario Questions

**Q21. "A client is using v1 of your API and their request is now returning data from the v2 handler after a deployment. What went wrong?"**
A: This is a routing misconfiguration — the version dispatch mechanism is broken, causing v1 clients to receive v2 responses. Probable causes by strategy:

**URI versioning:** a deployment accidentally changed a route mapping — `/v1/orders` now routes to the v2 controller instead of v1. Check the router configuration and diff the deployment. Also common: a catch-all route (`app.use('/orders', v2Router)`) was added above the version-specific routes, shadowing them.

**Header versioning:** the `apiVersionMiddleware` has a bug in its default version logic — instead of returning v1 for clients that send `API-Version: 1`, it's returning `DEFAULT_VERSION` (v2) because the version header parsing is failing silently (parsing `"1"` as NaN, falling to default). Check the `parseInt` and `isNaN` logic in the middleware.

**Content negotiation:** the `Accept` header matching has an ordering bug — `application/json` (no version) matches a v2 handler before the v1-specific `application/vnd.myapi.v1+json` handler is checked. Check the media type matching priority in the negotiation logic.

**Detection:** this class of bug is caught by contract tests — each version's response shape should be tested with the version-specific contract. If `GET /v1/orders/1` returns `{ createdAt: ... }` instead of `{ created: ... }` (the v1 field name), a v1 contract test would fail. Without contract tests, it's caught by monitoring the response shape in production — field-level schema validation on API responses alerts on unexpected field names.

**Q22. "A client requests a resource using API version 1, but the resource was only introduced in API version 2. What HTTP status code do you return, and what does the response look like?"**
A: There are two reasonable interpretations and responses:

**Interpretation 1 — The resource type exists in v1 but this specific endpoint doesn't:**
If `/v1/orders` exists but a sub-resource `/v1/orders/{id}/analytics` was only introduced in v2:
```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "error": "Not Found",
  "message": "This endpoint is not available in API version 1. Upgrade to v2 to access order analytics.",
  "upgradeInfo": {
    "currentVersion": 1,
    "minimumRequiredVersion": 2,
    "docsUrl": "https://api.example.com/v2/docs/orders/analytics"
  }
}
```
`404` is correct because from the v1 client's perspective, the resource genuinely doesn't exist in their version of the API.

**Interpretation 2 — A more helpful variant uses `410 Gone` if the endpoint existed in v1 and was removed:**
If `/v1/recommendations` existed in v1 and was superseded by a new `/v2/personalized-feed` endpoint:
```http
HTTP/1.1 410 Gone
Content-Type: application/json

{
  "error": "Gone",
  "message": "The /recommendations endpoint has been removed in API v1. Use /v2/personalized-feed instead.",
  "successor": "https://api.example.com/v2/personalized-feed"
}
```

The important principle: the error response must be actionable. The client needs to know: what version they're on, what version introduces the resource they need, and where to find documentation for migrating. A bare `404` without context sends the developer on an unnecessary debugging chase.

**Q23. "Your API has been at v1 for three years with no versioning. The team now needs to make a breaking change. How do you approach this?"**
A: Adding versioning to an unversioned API is a migration, not a greenfield decision. The steps:

**Step 1 — Audit current client usage:**
Before introducing a version, understand who is calling the API and what they're calling. Query access logs for the past 90 days: unique client user agents or API keys, most-called endpoints, request/response field usage. This determines the migration complexity and identifies high-priority clients to notify.

**Step 2 — Decide on the versioning strategy:**
For an existing unversioned API, URI versioning is the least disruptive introduction because it doesn't require existing clients to change anything:
- The current unversioned API (`/orders`) continues to work as-is — this becomes "v1" implicitly.
- New endpoints (`/v2/orders`) are added for the new breaking changes.
- Existing clients make zero changes initially; they migrate to v2 on their own schedule.

Header versioning at this point would require every existing client to add a header they've never needed — more disruptive.

**Step 3 — Introduce the version prefix for the new contract only:**
```javascript
// The unversioned API remains intact — existing clients unaffected
app.use('/orders', legacyOrdersRouter);

// New versioned API for the breaking change
app.use('/v2/orders', v2OrdersRouter);
```

Optionally, add a response header to all unversioned responses identifying them as v1:
```
API-Version: 1
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Link: </v2/orders>; rel="successor-version"
```
This signals to clients that they're on a legacy path without changing their request behavior.

**Step 4 — Establish the versioning convention going forward:**
Document the versioning strategy, the deprecation policy, and the migration timeline. All future breaking changes will use `/v2/` → `/v3/` style URI versioning. Non-breaking changes ship without a version bump.

**Step 5 — Drive migration:**
Use API key attribution to identify which clients have not yet migrated. Proactively reach out to high-value clients. Add monitoring for the legacy unversioned endpoint's traffic volume — the migration is complete when it drops to zero (or near-zero for bots and forgotten integrations).

## Quick Reference

**Strategy Comparison:**

| Dimension | URI Versioning | Header Versioning | Content Negotiation |
|--- |--- |--- |--- |
| Version location | URL path (`/v2/orders`) | Request header (`API-Version: 2`) | Accept header (`application/vnd.api.v2+json`) |
| URL stability | No — URL changes per version | Yes — URL is stable | Yes — URL is stable |
| Cacheability | Excellent — cache key is URL | Requires `Vary: API-Version` | Requires `Vary: Accept` |
| Debuggability | Excellent — version in access log | Moderate — requires header logging | Moderate — requires header logging |
| Developer ergonomics | Excellent — obvious in URL | Good — familiar header pattern | Poor — complex media type string |
| REST correctness | Low — URI encodes representation | Medium — header is non-standard | High — uses HTTP content negotiation |
| Infrastructure routing | Trivial — path-based | Moderate — header-based | Moderate — Accept-based |
| Adoption | Dominant (Stripe, GitHub, AWS) | Common (Salesforce, internal APIs) | Rare (GitHub v3 media types) |
| Best for | Public APIs, mobile clients | Internal APIs, developer platforms | REST purists, HTTP-sophisticated consumers |

**Breaking vs Non-Breaking Cheat Sheet:**

| Change | Breaking? | Requires New Version? |
|--- |--- |--- |
| Remove a field | Yes | Yes |
| Rename a field | Yes | Yes |
| Change field type | Yes | Yes |
| Make optional field required | Yes | Yes |
| Change enum values | Yes | Yes |
| Add new optional field | No | No |
| Add new optional query param | No | No |
| Add new endpoint | No | No |
| Relax validation (required → optional) | No | No |
| Add new enum value | Grey area | Depends on client implementation |

**Deprecation Header Template:**
```http
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Deprecation: 2025-01-01T00:00:00Z
Link: <https://api.example.com/v2/docs>; rel="successor-version"
```

**Tip for the interview:** At 5 YOE level, API versioning questions are about judgment and trade-offs, not definitions. The strongest answers articulate *why* URI versioning dominates in practice despite its theoretical weaknesses (the operational visibility and routing simplicity arguments), and *when* you would deviate (internal APIs with controlled clients, Stripe-style date versioning for extreme durability). The most impressive addition is the operational dimension: deprecation lifecycle management, how you detect which clients are still on v1, the `Sunset` header as an RFC-standard mechanism, and what the runbook looks like for a client who breaks after a sunset. The war story that lands best: "we introduced v2 without sunsetting v1 and six months later v1 was still getting 40% of traffic — we hadn't notified clients early enough and hadn't made the sunset date credible. Here's the process change we put in place for v3."
