# Rate Limiting Headers: `X-RateLimit-*` and `Retry-After` — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Rate Limiting Exists

**Q1. What problems does rate limiting solve, and what breaks without it?**
A: Rate limiting is a server-side control that bounds how many requests a client can make within a time window. Without it, three failure modes emerge:

- **Resource exhaustion**: A single client — whether a runaway retry loop, a misconfigured job, or a deliberate attack — consumes enough CPU, memory, database connections, or downstream API quota to degrade or crash the service for all other clients. A payment gateway that allows unbounded requests will eventually saturate its connection pool or hit its own upstream limits, failing legitimate transactions.
- **Cost amplification in pay-per-use systems**: Services that call third-party APIs (JusPay, Razorpay, AWS, Twilio) incur per-request costs. An unbounded client can generate unexpected charges by burning through quota that the operator pays for, not the client.
- **Fairness collapse**: In a multi-tenant system, one tenant consuming disproportionate capacity starves all others. Rate limiting enforces the fair-use contract implicitly assumed by every tenant.

Rate limiting is the mechanism; rate limit headers are the protocol through which the server communicates the limit state to the client. Without headers, clients cannot distinguish a temporary rate limit (retry later) from a permanent error (fix the request), cannot adapt their request rate proactively, and cannot give operators visibility into their consumption against quota. Headers make the rate limiting contract explicit and machine-readable.

**Q2. What is the difference between rate limiting, throttling, and quotas?**
A: The three terms are related but describe different scopes:

- **Rate limiting**: Bounds requests per unit time — requests per second, per minute, per hour. A client hitting the rate limit is blocked temporarily; it can resume when the window resets. Rate limiting is a flow control mechanism — it shapes the request rate, not the total volume.
- **Throttling**: Often used interchangeably with rate limiting, but more precisely refers to degrading service (slowing responses, shedding non-essential work) rather than hard blocking. A throttled server might add artificial latency to heavy clients rather than rejecting them outright. In practice, most engineers use "rate limiting" and "throttling" as synonyms.
- **Quotas**: Bounds total usage over a longer period — API calls per month, storage GB per billing cycle. Quotas are business constraints, not traffic flow controls. Hitting a quota typically blocks access until the quota resets (monthly) or until the client upgrades to a higher tier. Quotas are enforced with `X-RateLimit-*` headers just like rate limits, but the reset is a billing cycle, not a rolling window.

In a fintech system, all three coexist:
- Rate limit: 100 payment creation requests per minute per API key (burst protection).
- Throttling: slow down bulk payment jobs during peak hours to protect OLTP query performance.
- Quota: 50,000 payment verifications per month on the Starter plan; 500,000 on the Enterprise plan.

## Section 2: Rate Limit Algorithms

**Q3. What are the main rate limiting algorithms and what are their trade-offs?**
A: Four algorithms are in common use, each with different burst characteristics and implementation complexity:

**Fixed window counter:**
```
Window: [00:00 - 01:00], limit: 100 requests
Counter resets at :00 of each minute.

Client sends 100 requests at 00:59 → all allowed (counter = 100)
Client sends 100 requests at 01:00 → all allowed (new window, counter resets to 0)
Result: 200 requests in 2 seconds — 2x the intended limit
```
Simple to implement (one Redis `INCR` + `EXPIRE`). The boundary problem: a client can send double the limit by straddling the window boundary. Suitable for coarse quotas where boundary bursts are acceptable.

**Sliding window log:**
```
Limit: 100 requests per minute
Store: sorted set of request timestamps per client

On each request:
  Remove timestamps older than now - 60s
  Count remaining entries
  If count < 100: allow, add current timestamp
  If count ≥ 100: reject
```
Precise — no boundary burst possible. Expensive in memory (stores every timestamp) and per-request work (sorted set operations). Used when precision matters more than throughput.

**Sliding window counter (hybrid):**
```
Limit: 100 requests per minute
Current window count: 70 (at 30s into the minute)
Previous window count: 40

Effective rate = previous_count × (time_remaining_in_prev_window / window_size)
              + current_count
             = 40 × (30/60) + 70 = 20 + 70 = 90

90 < 100 → allow
```
Approximates the sliding window log using two fixed window counters. Much more memory-efficient than the log; slightly less precise (can under- or over-count by a small margin). Cloudflare's published approach for their rate limiter. Good balance for production use.

**Token bucket:**
```
Bucket capacity: 100 tokens
Refill rate: 10 tokens/second

Client sends 100 requests instantly → bucket empties → all allowed (burst capacity)
Next 10 requests in the next second → each costs 1 token, refilled at 10/s → allowed
Request 11 in that second → bucket empty → rejected
```
Allows controlled bursts up to the bucket capacity, then enforces the steady-state rate. Natural fit for APIs that want to allow short bursts (a user submitting a batch of payments) while preventing sustained overload. Widely used in API gateways (AWS API Gateway, Nginx). Requires storing current token count and last refill timestamp per client.

**Leaky bucket:**
```
Queue capacity: 100 requests
Processing rate: 10 requests/second (fixed)

Requests enter the bucket; the bucket drains at a fixed rate.
If the bucket is full: new requests are rejected.
Consumers of the queue see a perfectly smooth request rate.
```
Smooths out bursts completely — the outflow is always at a fixed rate regardless of burst size. Useful for protecting downstream systems that cannot handle any burst (legacy APIs, batch processors). Less common for client-facing APIs because it queues requests rather than immediately rejecting them, adding latency.

**The production choice for most REST APIs**: token bucket or sliding window counter. Token bucket aligns with how clients naturally think about their allowance (I have N calls available); sliding window counter is easier to implement correctly in Redis without race conditions.

## Section 3: Rate Limit Headers

**Q4. What are the standard rate limit response headers and what does each communicate?**
A: There is no single universally mandated standard for rate limit headers — the IETF draft "RateLimit header fields for HTTP" (draft-ietf-httpapi-ratelimit-headers) is in standardization but not yet finalized. In practice, the de facto standard used by most APIs (GitHub, Stripe, Twilio, AWS) follows this set:

**`X-RateLimit-Limit`**: The maximum number of requests the client is allowed in the current window.
```http
X-RateLimit-Limit: 100
```
This is the policy — what the client is entitled to. It does not change within a window.

**`X-RateLimit-Remaining`**: The number of requests remaining in the current window.
```http
X-RateLimit-Remaining: 37
```
This decrements with each request. When it reaches 0, the next request will be rate limited. Clients use this to proactively throttle before hitting the limit.

**`X-RateLimit-Reset`**: When the current window resets and `X-RateLimit-Remaining` returns to `X-RateLimit-Limit`.
```http
X-RateLimit-Reset: 1705312200        ← Unix timestamp (most common)
X-RateLimit-Reset: 42                ← Seconds until reset (some APIs use this instead)
```
The Unix timestamp form is unambiguous — clients compute time-until-reset as `reset - now()`. The seconds-until-reset form is simpler to read but can skew if the response is delayed in transit.

**`X-RateLimit-Used`** (less common, used by GitHub):
```http
X-RateLimit-Used: 63
```
How many requests have been consumed in the current window. Redundant if both `Limit` and `Remaining` are present (`Used = Limit - Remaining`), but some APIs provide it for clarity.

**`X-RateLimit-Resource`** (GitHub-specific):
```http
X-RateLimit-Resource: core
X-RateLimit-Resource: search
```
Which rate limit pool this request counted against. APIs with multiple independent rate limit buckets (e.g., search API vs. core API, or per-endpoint limits) use this to tell clients which bucket is exhausted.

**Full example — a successful response with rate limit headers:**
```http
HTTP/1.1 200 OK
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 36
X-RateLimit-Reset: 1705312200
Content-Type: application/json

{ "payment_id": "pay_001", "status": "PENDING" }
```

**Q5. What is the `Retry-After` header, when is it sent, and what formats does it support?**
A: `Retry-After` is a standard HTTP header (RFC 9110) that tells the client how long to wait before making another request. It is sent with two response codes:

- **429 Too Many Requests**: The client has exceeded the rate limit. `Retry-After` tells it when it can try again.
- **503 Service Unavailable**: The server is temporarily overloaded or down for maintenance. `Retry-After` tells clients when to retry rather than hammering a recovering service.

It also appears with:
- **301/302 redirects** (rare): Indicating a delay before following the redirect.
- **Retry-After on 429** is the most operationally important use in API contexts.

**Two formats:**

**HTTP date format (RFC 1123):**
```http
Retry-After: Wed, 15 Jan 2024 10:30:00 GMT
```
An absolute point in time. Unambiguous about when to retry. Requires the client's clock to be reasonably synchronized with the server's (NTP-level accuracy is sufficient).

**Delay in seconds:**
```http
Retry-After: 42
```
A relative delay — wait 42 seconds from the time of this response. Simpler to compute; avoids clock skew issues. The most commonly used format for rate limiting because it is independent of client clock accuracy.

**The critical operational requirement**: `Retry-After` must be present on every 429 response. A 429 without `Retry-After` leaves the client guessing — it may retry immediately (creating a retry storm) or back off for an arbitrary duration. The `Retry-After` value transforms a 429 from an opaque rejection into a scheduling instruction.

```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1705312200
Retry-After: 42
Content-Type: application/json

{
  "error": "rate_limit_exceeded",
  "message": "You have exceeded the rate limit of 100 requests per minute.",
  "retry_after_seconds": 42,
  "limit": 100,
  "reset_at": "2024-01-15T10:30:00Z"
}
```

The response body duplicates the header information in a human-readable and machine-readable form — both headers and body should be consistent. Clients that parse JSON get the body; HTTP infrastructure (load balancers, SDKs) reads the headers.

**Q6. What is the emerging IETF standard for rate limit headers and how does it differ from the `X-RateLimit-*` convention?**
A: The IETF draft `draft-ietf-httpapi-ratelimit-headers` proposes dropping the `X-` prefix and standardizing three headers:

**`RateLimit-Limit`**: The quota policy. Can express multiple windows:
```http
RateLimit-Limit: 100, 100;w=60, 1000;w=3600
```
This single header communicates: 100 requests per (default window), 100 per 60-second window, 1000 per 3600-second window. More expressive than the current convention's single-window `X-RateLimit-Limit`.

**`RateLimit-Remaining`**: Remaining quota in the current window.
```http
RateLimit-Remaining: 36
```

**`RateLimit-Reset`**: Seconds until the quota resets (always in seconds, not timestamp).
```http
RateLimit-Reset: 42
```

The draft also proposes `RateLimit-Policy` for communicating the full policy document separately from per-request status.

**Why the `X-` prefix is being dropped**: RFC 6648 (2012) deprecated the convention of using `X-` to indicate non-standard headers, because de facto standards routinely became standards while keeping the `X-` prefix, creating permanent naming inconsistency. `X-Forwarded-For` became standard as-is; the intent is to avoid the same problem for rate limit headers.

**Current production reality**: The `X-RateLimit-*` convention is so widely adopted (GitHub, Stripe, Twitter/X, Twilio, AWS) that it will coexist with the standardized form for years. When building a new API today, it is reasonable to support both — send `X-RateLimit-Limit` for backward compatibility and `RateLimit-Limit` for forward compatibility. When consuming APIs, expect `X-RateLimit-*`.

## Section 4: Client-Side Handling

**Q7. How should a well-behaved HTTP client handle rate limit headers proactively — before hitting 429?**
A: The difference between a naive client and a production-grade client is whether it waits for a 429 or adapts before hitting the limit. Proactive handling using `X-RateLimit-Remaining` and `X-RateLimit-Reset`:

```javascript
class RateLimitAwareClient {
  constructor(baseUrl, options = {}) {
    this.baseUrl = baseUrl;
    this.remaining = Infinity;  // unknown until first response
    this.resetAt = null;
    this.limit = null;
    this.minRemaining = options.minRemaining ?? 5; // proactive throttle threshold
  }

  updateFromHeaders(headers) {
    if (headers['x-ratelimit-limit'])
      this.limit = parseInt(headers['x-ratelimit-limit']);
    if (headers['x-ratelimit-remaining'])
      this.remaining = parseInt(headers['x-ratelimit-remaining']);
    if (headers['x-ratelimit-reset'])
      this.resetAt = new Date(parseInt(headers['x-ratelimit-reset']) * 1000);
  }

  async waitIfNeeded() {
    // Proactive throttle: if remaining is low, pause until reset
    if (this.remaining <= this.minRemaining && this.resetAt) {
      const waitMs = Math.max(0, this.resetAt - Date.now()) + 100; // +100ms buffer
      console.log(`Proactive throttle: ${this.remaining} remaining, waiting ${waitMs}ms`);
      await sleep(waitMs);
    }
  }

  async request(path, options = {}) {
    await this.waitIfNeeded();

    const response = await fetch(`${this.baseUrl}${path}`, options);
    this.updateFromHeaders(response.headers);

    if (response.status === 429) {
      // Reactive: 429 despite proactive throttle (race condition or miscalculation)
      const retryAfter = parseInt(response.headers.get('retry-after') ?? '60');
      console.log(`429 received, waiting ${retryAfter}s`);
      await sleep(retryAfter * 1000);
      return this.request(path, options); // single retry after waiting
    }

    return response;
  }
}
```

The `minRemaining` threshold (5 in the example) is a safety margin — the client starts pausing when 5 requests remain rather than waiting until 0. This protects against concurrent requests from the same client that might all read `remaining: 1` and all proceed, causing a burst of 429s.

**Q8. How should a client implement retry logic when it receives a 429 with `Retry-After`?**
A: Correct retry logic for 429 has four components: respect `Retry-After`, add jitter, cap retries, and never retry non-retryable errors.

```javascript
async function requestWithRetry(url, options, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.ok) return response;

    // Non-retryable client errors: fail immediately
    if (response.status >= 400 && response.status < 429) {
      throw new ClientError(response.status, await response.json());
    }

    // Rate limited: respect Retry-After
    if (response.status === 429) {
      if (attempt === maxRetries) {
        throw new RateLimitError('Max retries exceeded', response);
      }

      const retryAfterHeader = response.headers.get('retry-after');
      const retryAfterSeconds = retryAfterHeader
        ? parseRetryAfter(retryAfterHeader)  // handles both timestamp and seconds
        : Math.pow(2, attempt) * 1;           // fallback: exponential backoff

      // Add jitter: ±10% of the wait time to prevent thundering herd
      const jitter = retryAfterSeconds * 0.1 * (Math.random() * 2 - 1);
      const waitMs = Math.round((retryAfterSeconds + jitter) * 1000);

      console.log(`429 on attempt ${attempt + 1}, waiting ${waitMs}ms`);
      await sleep(waitMs);
      continue;
    }

    // Server errors (500, 502, 503, 504): exponential backoff
    if (response.status >= 500) {
      if (attempt === maxRetries) {
        throw new ServerError(response.status, await response.json());
      }
      const waitMs = Math.pow(2, attempt) * 1000; // 1s, 2s, 4s
      await sleep(waitMs);
      continue;
    }
  }
}

function parseRetryAfter(header) {
  // Try parsing as integer (seconds)
  const seconds = parseInt(header);
  if (!isNaN(seconds)) return seconds;

  // Try parsing as HTTP date
  const date = new Date(header);
  if (!isNaN(date.getTime())) {
    return Math.max(0, (date.getTime() - Date.now()) / 1000);
  }

  return 60; // default fallback
}
```

**Key decisions in this implementation:**

- **Only retry 429 and 5xx** — never retry 4xx errors (except 429). A 400/422/404 will return the same result on retry; retrying wastes quota.
- **Respect `Retry-After` exactly** — do not use shorter backoff than instructed. The server computed this value for a reason (window reset time, downstream recovery estimate).
- **Add jitter** — if 1000 clients all hit the rate limit at the same time and all wait exactly `Retry-After` seconds, they all retry simultaneously, recreating the spike. Jitter desynchronizes them. Full jitter (`random(0, retry_after)`) or decorrelated jitter are alternatives to the ±10% approach shown.
- **Cap total retries** — do not retry indefinitely. After `maxRetries`, propagate the error to the caller. The caller decides whether to surface it to the user, queue for later, or escalate.
- **Carry the idempotency key through retries** — for POST requests, the same `Idempotency-Key` header must be sent on every retry attempt. The idempotency key makes the POST safe to retry; without it, each retry creates a new resource.

**Q9. What is a "thundering herd" in the context of rate limiting and how do headers help prevent it?**
A: A thundering herd occurs when a large number of clients hit the rate limit simultaneously, wait for the same `Retry-After` duration, and then retry at the same moment — recreating the exact spike that caused the rate limit in the first place. The rate limiter blocks them again, they wait again, and the cycle repeats.

```
T=0:  1000 clients hit the limit simultaneously → all receive 429, Retry-After: 60
T=60: 1000 clients retry simultaneously → spike recreated → all hit limit again
T=60: 1000 clients receive 429, Retry-After: 60
T=120: 1000 clients retry simultaneously → spike again → infinite loop
```

**Prevention mechanisms:**

**Jitter on the client side (the most important mitigation):**
Instead of waiting exactly `Retry-After` seconds, each client waits `Retry-After + random(-10%, +10%)`. Clients desynchronize gradually — after a few cycles the retry load is spread across the window.

**Variable `Retry-After` from the server:**
The server can send different `Retry-After` values to different clients, spreading the retry load:
```javascript
// Server-side: spread retries across the reset window
function computeRetryAfter(clientId, windowResetAt) {
  const baseWait = Math.max(0, windowResetAt - Date.now()) / 1000;
  // Hash the client ID to a stable offset within [0, 30] seconds
  const clientOffset = hashToRange(clientId, 0, 30);
  return Math.ceil(baseWait + clientOffset);
}
```
Client A gets `Retry-After: 42`; client B gets `Retry-After: 58`. Their retries are spread across 16 seconds rather than concentrated at one instant.

**Queue-based rate limiting with backpressure:**
Instead of rejecting at the limit, the server queues requests and processes them at the allowed rate. The client receives a `202 Accepted` and polls a status endpoint. No thundering herd because no mass rejection event triggers simultaneous retries. Higher complexity; appropriate for long-running operations.

## Section 5: Server-Side Implementation

**Q10. How do you implement rate limiting in a distributed Node.js/NestJS service using Redis?**
A: In a distributed system (multiple instances of the same service), rate limiting state must live in a shared store — Redis is the standard choice. A sliding window counter implementation:

```typescript
// rate-limiter.service.ts (NestJS)
import { Injectable } from '@nestjs/common';
import { Redis } from 'ioredis';

@Injectable()
export class RateLimiterService {
  constructor(private readonly redis: Redis) {}

  async checkLimit(
    key: string,           // e.g., "ratelimit:api_key:ak_123"
    limit: number,         // e.g., 100
    windowSeconds: number  // e.g., 60
  ): Promise<{
    allowed: boolean;
    remaining: number;
    limit: number;
    resetAt: number;       // Unix timestamp
  }> {
    const now = Date.now();
    const windowStart = now - windowSeconds * 1000;
    const resetAt = Math.ceil(now / 1000 / windowSeconds) * windowSeconds;

    // Lua script: atomic sliding window log in Redis sorted set
    // Returns [count_in_window, was_incremented]
    const luaScript = `
      local key = KEYS[1]
      local now = tonumber(ARGV[1])
      local window_start = tonumber(ARGV[2])
      local limit = tonumber(ARGV[3])
      local window_seconds = tonumber(ARGV[4])

      -- Remove entries outside the window
      redis.call('ZREMRANGEBYSCORE', key, '-inf', window_start)

      -- Count current entries
      local count = redis.call('ZCARD', key)

      if count < limit then
        -- Add current request timestamp (score = timestamp, member = timestamp+random)
        redis.call('ZADD', key, now, now .. math.random())
        redis.call('EXPIRE', key, window_seconds + 1)
        return {count + 1, 1}   -- new count, allowed
      else
        return {count, 0}        -- current count, rejected
      end
    `;

    const [count, allowed] = await this.redis.eval(
      luaScript, 1, key,
      now, windowStart, limit, windowSeconds
    ) as [number, number];

    return {
      allowed: allowed === 1,
      remaining: Math.max(0, limit - count),
      limit,
      resetAt,
    };
  }
}
```

**NestJS guard that adds rate limit headers:**
```typescript
// rate-limit.guard.ts
import { Injectable, CanActivate, ExecutionContext, HttpException, HttpStatus } from '@nestjs/common';

@Injectable()
export class RateLimitGuard implements CanActivate {
  constructor(private readonly rateLimiter: RateLimiterService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request  = context.switchToHttp().getRequest();
    const response = context.switchToHttp().getResponse();

    const apiKey = request.headers['x-api-key'] ?? request.ip;
    const key    = `ratelimit:${apiKey}`;
    const limit  = 100;
    const window = 60; // seconds

    const result = await this.rateLimiter.checkLimit(key, limit, window);

    // Always set headers — on allowed AND rejected requests
    response.setHeader('X-RateLimit-Limit',     result.limit);
    response.setHeader('X-RateLimit-Remaining', result.remaining);
    response.setHeader('X-RateLimit-Reset',     result.resetAt);

    if (!result.allowed) {
      const retryAfter = result.resetAt - Math.floor(Date.now() / 1000);
      response.setHeader('Retry-After', retryAfter);

      throw new HttpException(
        {
          error:               'rate_limit_exceeded',
          message:             `Rate limit of ${limit} requests per minute exceeded`,
          retry_after_seconds: retryAfter,
          limit,
          reset_at:            new Date(result.resetAt * 1000).toISOString(),
        },
        HttpStatus.TOO_MANY_REQUESTS
      );
    }

    return true;
  }
}
```

**Why the Lua script is necessary:**
The check-then-increment pattern has a race condition without atomicity:
```
Client A reads count = 99 (below limit 100) → allowed
Client B reads count = 99 (below limit 100) → allowed, simultaneously
Client A increments → count = 100
Client B increments → count = 101  ← over the limit, but both were allowed
```
The Lua script runs atomically on the Redis server — no other command executes between the `ZCARD` and `ZADD`. This eliminates the race condition. Always use Lua scripts or Redis transactions (`MULTI`/`EXEC`) for rate limiter logic.

**Q11. What are the key identifiers used to scope rate limits, and what are the trade-offs of each?**
A: Rate limiting is only as fair and precise as the identifier used to bucket requests. Common identifiers, from coarsest to finest:

**IP address:**
```
ratelimit:ip:203.0.113.42 → 100 req/min
```
Simple and always available. Problems: multiple users behind a corporate NAT or VPN share one IP — a single heavy user blocks everyone behind that IP. IPv6 complicates matching (clients may rotate through a /64 block). A client can rotate IPs (proxies, VPN). IP-based limiting is a baseline defense against unauthenticated traffic, not a fair multi-tenant policy.

**API key:**
```
ratelimit:apikey:ak_live_abc123 → 100 req/min
```
The standard for authenticated APIs. One limit per key; clients control their own consumption. Rotating a key gets a fresh limit — intended for key expiry, but exploitable for limit bypass if key rotation is cheap. The correct scoping for most REST API rate limiting.

**User ID:**
```
ratelimit:user:usr_42 → 100 req/min
```
Ties the limit to the authenticated user regardless of which API key or client they use. Prevents the same user from splitting their traffic across multiple keys to multiply their effective limit. Requires authentication to be resolved before rate limiting (cannot rate limit the authentication endpoint itself by user ID).

**Tenant / organization:**
```
ratelimit:tenant:org_fintech_corp → 1000 req/min
```
For multi-tenant SaaS: the limit applies to the entire organization, not individual users. One power user in the org cannot starve others in the same org (user-level sub-limits), but the org as a whole has a fair share of total capacity.

**Per-endpoint:**
```
ratelimit:apikey:ak_123:endpoint:POST:/payments → 10 req/min
ratelimit:apikey:ak_123:endpoint:GET:/payments  → 100 req/min
```
Different endpoints have different costs. `POST /payments` touches the payment processor (external call, billing cost); `GET /payments/status` is a database read. Per-endpoint limits prevent a client from burning all their quota on expensive operations while appearing within the global limit.

**The production pattern — layered rate limiting:**
```
Global limit:    1000 req/min per API key (burst protection)
Per-endpoint:    POST /payments: 10/min (cost protection)
                 POST /bulk-payments: 2/min (very expensive operation)
                 GET  *: 200/min (reads are cheap)
Per-user:        100 req/min per user within a tenant (fairness within org)
```
Each layer is enforced independently; a request must pass all applicable limits. Headers reflect the most restrictive active limit — if the user is approaching the per-user limit but not the global limit, `X-RateLimit-Remaining` reflects the per-user remaining count.

## Section 6: Rate Limiting in Specific Contexts

**Q12. How do you handle rate limiting when calling third-party APIs (JusPay, Razorpay, Twilio) from your service?**
A: When your service is the client of a third-party API, you inherit their rate limits — exceeding them causes 429s from the third party, which must not propagate as 5xx errors to your own clients. Three layers of handling:

**Layer 1 — Read and store third-party rate limit headers:**
```typescript
class JusPayClient {
  private remaining = Infinity;
  private resetAt: number | null = null;

  async makeRequest<T>(path: string, options: RequestInit): Promise<T> {
    const response = await fetch(`https://api.juspay.in${path}`, {
      ...options,
      headers: {
        ...options.headers,
        'Authorization': `Basic ${this.apiKey}`,
      },
    });

    // Read JusPay's rate limit headers after every call
    const remaining = response.headers.get('x-ratelimit-remaining');
    const reset     = response.headers.get('x-ratelimit-reset');
    if (remaining) this.remaining = parseInt(remaining);
    if (reset)     this.resetAt   = parseInt(reset);

    if (response.status === 429) {
      const retryAfter = parseInt(response.headers.get('retry-after') ?? '10');
      throw new ExternalRateLimitError('JusPay', retryAfter);
    }

    return response.json();
  }
}
```

**Layer 2 — Pre-emptive throttling before the third-party limit is reached:**
```typescript
async createPayment(payload: CreatePaymentDto): Promise<Payment> {
  // Don't wait for a 429; slow down proactively at 10% remaining
  if (this.jusPayClient.remaining < this.jusPayClient.limit * 0.10) {
    const waitUntil = this.jusPayClient.resetAt;
    if (waitUntil) await sleep(waitUntil * 1000 - Date.now() + 200);
  }

  return this.jusPayClient.makeRequest('/v2/order/create', {
    method: 'POST',
    body: JSON.stringify(payload),
  });
}
```

**Layer 3 — Circuit breaker for sustained 429s:**
If the third-party API is consistently rate limiting your service (sustained quota exhaustion, not transient bursts), a circuit breaker opens and stops all calls for a recovery window — returning a fast `503 Service Temporarily Unavailable` to your clients rather than slow timeouts or cascading retries:
```typescript
// Nest a circuit breaker around the third-party client
// Open after 3 consecutive 429s; half-open after 30 seconds
const circuitBreaker = new CircuitBreaker(jusPayClient.createPayment, {
  errorThresholdPercentage: 50,
  resetTimeout: 30000,
  errorFilter: (err) => err instanceof ExternalRateLimitError,
});
```

**The critical design principle**: a third-party 429 must never silently become your service's 5xx. Your clients need to know whether to retry (a transient capacity issue) or slow down (they are indirectly causing the third-party limit to be reached). Map the upstream 429 to a meaningful error response:
```json
{
  "error": "payment_processor_capacity",
  "message": "Payment processing is temporarily capacity-constrained. Please retry in 30 seconds.",
  "retry_after_seconds": 30,
  "retry_at": "2024-01-15T10:31:00Z"
}
```

**Q13. How does rate limiting interact with load balancers and multiple service instances?**
A: Without shared state, each service instance maintains its own rate limit counter. With 3 instances, the effective limit becomes 3× the configured limit — each instance allows 100 req/min, so a client routing across all three can make 300 req/min total:

```
Client → Load Balancer → Instance 1 (counter: 40/100)
                       → Instance 2 (counter: 35/100)
                       → Instance 3 (counter: 25/100)

Effective rate: 40 + 35 + 25 = 100/100 per instance
                             = 300 per minute across all instances
```

**Solution: centralized rate limit state in Redis:**
All instances share one Redis cluster for rate limit counters. Every request, regardless of which instance handles it, increments the same counter:
```
GET /payments → Instance 1 → ZADD ratelimit:ak_123 ... → Redis
GET /payments → Instance 2 → ZADD ratelimit:ak_123 ... → Redis (same key)
GET /payments → Instance 3 → ZADD ratelimit:ak_123 ... → Redis (same key)

Redis sees all three; limit is enforced globally.
```

**Trade-off — Redis as a synchronous dependency:**
Every request now has a Redis round-trip on the critical path. For a service handling 10,000 req/s, this is 10,000 Redis operations per second. Redis can typically sustain 100,000+ ops/second, so the capacity is not usually the concern — latency is. A Redis round-trip adds 0.5–2ms per request in the same data center, which is acceptable for most APIs but measurable.

**Mitigation — local cache with Redis sync:**
Accept a small tolerance for over-counting in exchange for reduced Redis calls:
```typescript
// Local token bucket — cheap, in-memory
// Syncs to Redis every N requests or every T milliseconds
class HybridRateLimiter {
  private localCount = 0;
  private syncThreshold = 10; // sync to Redis every 10 requests

  async check(key: string, limit: number): Promise<boolean> {
    this.localCount++;

    if (this.localCount % this.syncThreshold === 0) {
      // Sync local count to Redis; get authoritative global count
      const globalCount = await this.syncToRedis(key, this.syncThreshold);
      if (globalCount > limit) return false;
    }

    // Local approximate check (may allow up to syncThreshold extra requests globally)
    return true;
  }
}
```
This reduces Redis calls by 10× at the cost of allowing up to `syncThreshold × numInstances` excess requests — a controlled inaccuracy acceptable for most non-financial rate limiting. For financial APIs (where exceeding the limit has billing or abuse consequences), pay the Redis round-trip cost for exact counting.

**Q15. "A client is reporting intermittent 429 errors even though they believe they are within their rate limit. How do you diagnose this?"**
A: "Within their rate limit" usually means the client is reading `X-RateLimit-Remaining` on success responses and seeing positive values — but still occasionally receiving 429s. Four root causes:

**Root cause 1 — Concurrent requests from the same client:**
The client sends 10 requests in parallel. Each reads `X-RateLimit-Remaining: 5` from the previous response before any of the parallel requests complete. All 10 proceed simultaneously, exhausting the remaining 5 slots and causing 5 of the 10 to receive 429.

```
Request 1 → server: remaining=5 → proceeds
Request 2 → server: remaining=5 → proceeds (parallel, before 1 completes)
...both requests see remaining=5, but only 5 slots exist
```

Diagnosis: look at request timestamps in server logs. If multiple 429s occur within milliseconds of each other from the same API key, it is a concurrency issue. Fix: implement a client-side semaphore limiting concurrent in-flight requests.

**Root cause 2 — Multiple processes or instances sharing one API key:**
Three deployment instances of the client application share one API key. Each instance monitors its own `X-RateLimit-Remaining` but does not know about the others' consumption. Together they exceed the limit.

Diagnosis: correlate 429 timestamps with deployment instance logs. Fix: either give each instance its own API key (with proportionally divided limits), or implement a shared rate limit token pool (a centralized counter for all instances).

**Root cause 3 — Clock skew between client and server causing incorrect reset time parsing:**
The client parses `X-RateLimit-Reset: 1705312200` (Unix timestamp) and computes `time_until_reset = 1705312200 - client_now`. If the client's clock is 30 seconds ahead of the server, it believes the window has reset 30 seconds before it actually has, and starts sending requests into the tail of the previous window.

Diagnosis: compare `Date` response header (server time) with client clock. Fix: compute `time_until_reset` using the server's `Date` header as the reference, not the client's local clock:
```javascript
const serverNow  = new Date(response.headers.get('date')).getTime() / 1000;
const resetAt    = parseInt(response.headers.get('x-ratelimit-reset'));
const waitSeconds = Math.max(0, resetAt - serverNow);
```

**Root cause 4 — Per-endpoint limits the client is unaware of:**
The API has a global limit of 1000 req/min (client monitors `X-RateLimit-Remaining` and sees 600 remaining) but also a per-endpoint limit of 10 req/min on `POST /payments` (the client never reads this). The client sends its 11th payment creation and receives a 429 — from a limit it did not know existed.

Diagnosis: check whether the 429 is from a different limit dimension than the one the client monitors. The 429 response body should include `"limit_type": "endpoint"` to make this diagnosable. Fix: the server's 429 response must clearly identify which limit was hit; the client must handle limits on each dimension it uses.

**Q16. "You are building a webhook delivery system. How do you apply rate limiting and use `Retry-After` to protect your downstream webhook consumers?"**
A: A webhook delivery system is the inverse of the usual case — you are the client calling your users' webhook endpoints, and you must respect their capacity limits. The `Retry-After` header now comes from the webhook consumer (the third party), not from your own API.

```
Architecture:
  Event source → Kafka topic: webhook.events
               → Webhook Dispatcher (your service)
               → Consumer's endpoint: https://merchant.example.com/webhook

Rate limiting concerns:
  1. Per-consumer delivery rate: don't flood one merchant's endpoint
  2. Global dispatch rate: don't overwhelm your own outbound connection pool
  3. Retry handling: when consumer returns 429 or 503, respect their Retry-After

Per-consumer rate limiting (outbound):
  Limit: 100 webhook deliveries per second per consumer endpoint
  Key: ratelimit:outbound:{consumer_id}
  If limit reached: pause the consumer's delivery queue; other consumers unaffected

Retry handling on 429 from consumer:
  Consumer returns: HTTP 429  Retry-After: 60

  Webhook dispatcher logic:
    if response.status === 429 || response.status === 503:
      retryAfter = parseRetryAfter(response.headers['retry-after']) ?? 60
      // Schedule retry: put event back in delayed queue with
      // earliest_retry_at = now + retryAfter
      await delayedQueue.enqueue(event, {
        retryAt: Date.now() + retryAfter * 1000,
        attempt: event.attempt + 1,
      });
      // Do NOT retry other pending events for this consumer during this window
      await pauseConsumerDelivery(consumer.id, retryAfter);

Pause-all on rate limit:
  When consumer returns 429, pause ALL pending events for that consumer,
  not just the one that was rejected. Continuing to deliver other events
  while one was rate-limited will cause all of them to be rate-limited too —
  wasting retries and increasing load on an already-stressed consumer.

Delivery attempt tracking (in Redis or DB):
  webhook_delivery:{event_id}: {
    consumer_id:   "consumer_42",
    attempt:       3,
    last_status:   429,
    next_retry_at: 1705312260,
    retry_history: [
      { attempt: 1, status: 200, at: 1705312100 },
      { attempt: 2, status: 429, retry_after: 60 },
      { attempt: 3, status: 429, retry_after: 60 }
    ]
  }

Giving up after max retries:
  After 5 attempts (or 24 hours), mark delivery as failed.
  Notify the consumer (email/dashboard) that webhook delivery failed.
  Retain the event payload for manual replay.
  A consumer that consistently returns 429 should have their
  delivery rate limit automatically reduced (circuit-break the rate).
```

The webhook delivery case is one where rate limit headers from downstream must be respected as strictly as those from upstream APIs — your service's reliability depends on your consumers' health. A dispatcher that ignores `Retry-After` and hammers a consumer's endpoint will cause that consumer to block your IP, escalate the outage, and damage the business relationship.

## Quick Reference

| Header | Direction | Meaning |
|--------|-----------|---------|
| `X-RateLimit-Limit` | Response | Max requests allowed in the current window |
| `X-RateLimit-Remaining` | Response | Requests remaining before limit is hit |
| `X-RateLimit-Reset` | Response | Unix timestamp (or seconds) until window resets |
| `X-RateLimit-Used` | Response | Requests consumed so far (GitHub convention) |
| `Retry-After` | Response | Seconds (or HTTP date) to wait before retrying |
| `RateLimit-Limit` | Response | IETF draft standard; same as X-RateLimit-Limit |
| `RateLimit-Remaining` | Response | IETF draft standard; same as X-RateLimit-Remaining |
| `RateLimit-Reset` | Response | IETF draft standard; always seconds (not timestamp) |

| Algorithm | Burst | Precision | Memory | Redis Ops |
|-----------|-------|-----------|--------|-----------|
| Fixed window | 2× at boundary | Low | O(1) | 2 (INCR + EXPIRE) |
| Sliding window log | None | High | O(requests) | 3 (ZREMRANGE + ZCARD + ZADD) |
| Sliding window counter | ~1.1× | Medium | O(1) | 4 (two counters + weights) |
| Token bucket | Up to capacity | Medium | O(1) | 2 (GET + SET) |
| Leaky bucket | Queued | High | O(queue) | Queue ops |

| Status Code | Meaning for Rate Limiting |
|-------------|--------------------------|
| 429 Too Many Requests | Rate limit exceeded; must include `Retry-After` |
| 503 Service Unavailable | Server overloaded; may include `Retry-After` |
| 200–299 | Success; always include `X-RateLimit-*` headers |

## The Core Mental Model

```
Rate limiting headers = a machine-readable contract between server and client

Server responsibilities:
  Every response (success and error) carries X-RateLimit-Limit, Remaining, Reset.
  Every 429 carries Retry-After — never omit it.
  The 429 body identifies which limit was hit (global/endpoint/tier).
  Rate limit state lives in Redis (shared across all service instances).
  Lua scripts enforce atomic check-and-increment (no race conditions).
  Thundering herd is the server's responsibility too: vary Retry-After per client.

Client responsibilities:
  Read X-RateLimit-Remaining on every response, not just 429s.
  Proactively throttle at low-remaining threshold (e.g., < 5% remaining).
  On 429: wait exactly Retry-After (+ small jitter), then retry once.
  Carry the same Idempotency-Key through all retries of a POST.
  Never retry 4xx errors (except 429). Fix the request.
  Cap total retry attempts; escalate after exhaustion.

The hierarchy of rate limit checks (layered limits):
  Global limit → endpoint limit → user limit → tier limit
  All must pass; headers reflect the most constrained active limit.
  A request near the endpoint limit but far from the global limit
  shows endpoint limit in headers — that is the actionable constraint.

The jitter rule:
  Retry-After tells clients when the window resets.
  Without jitter, all clients retry simultaneously → thundering herd.
  Always add ±10-20% random jitter to Retry-After before sleeping.
  Full jitter (random(0, retry_after)) is the most effective desynchronizer.

The third-party rate limit rule:
  Your service is rate-limited by every API you call.
  Read their X-RateLimit-* headers and pre-emptively throttle at 10% remaining.
  Map their 429 to a meaningful error for your own clients — never propagate a
  raw upstream 429 as your own 5xx.
  Circuit break after sustained upstream rate limiting:
  fast-fail your clients rather than slow-fail with cascading retries.

The webhook inversion rule:
  Webhook delivery = you are the client, your consumer is the server.
  Their 429 + Retry-After must pause ALL delivery to that consumer,
  not just the rejected event. One 429 signals capacity exhaustion;
  continuing other deliveries makes it worse.
```

**Tip for the interview:** Rate limiting questions at 5 YOE almost always escalate to one of three places: (1) the distributed rate limiter implementation — knowing that per-instance counters multiply the effective limit by instance count, that Redis is the shared store, and that Lua scripts are necessary for atomic check-and-increment (because `GET + INCR` without atomicity allows concurrent over-admission) signals production experience; (2) `Retry-After` correctness — knowing that omitting `Retry-After` on a 429 causes retry storms, that jitter is the client's responsibility to prevent thundering herds, and that `Retry-After` should be parsed for both Unix timestamp and seconds formats because different APIs use different conventions; (3) layered rate limits — the nuance that a single request may be subject to global, per-endpoint, per-user, and per-tier limits simultaneously, and that the headers should reflect the most constrained active limit (not the global limit by default) is what separates someone who has designed rate limiting for multi-tenant APIs from someone who has only read about it. The fintech-specific callout: for payment APIs, per-endpoint limits on `POST /payments` are not optional — the endpoint calls an external processor that has its own rate limits and per-call billing costs, making unbounded POST rate a financial risk, not just an availability risk.
