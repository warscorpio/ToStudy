# JSON:API Specification — Interview Q&A (5 YOE Level)

---

## Section 1: What JSON:API Is and Why It Exists

**Q1. What is the JSON:API specification, and what problem does it solve?**
A: JSON:API (jsonapi.org, current version 1.1) is a specification for how clients and servers should structure HTTP API requests and responses that exchange JSON documents. It defines: the format of resource objects, how to express relationships between resources, how to include related resources in a single response, how to request sparse fieldsets and sorting, and how to format error responses.

The problem it solves is **API bikeshedding** — the repeated, inconsistent, team-by-team reinvention of the same structural decisions. Every team building a REST API without a standard faces the same questions: how do I represent a collection of resources? How do I include related objects without N+1 requests? How do I paginate? How do I communicate which fields changed in a PATCH? Without a shared standard, the answers vary across teams, SDKs, and products, requiring consumers to learn a new set of conventions for each API they integrate with.

JSON:API answers all of these questions with a single consistent specification. An API consumer who learns JSON:API once can work with any compliant API without reading its documentation for structural conventions — only for the domain-specific semantics (what fields mean, what operations are allowed). This is similar to how SQL lets developers work with any relational database without relearning query syntax: the mechanism is standardized; only the schema varies.

**Q2. What is the core philosophy behind JSON:API's design, and how does it differ from ad-hoc REST?**
A: JSON:API's design philosophy rests on two principles: **compound documents** (related resources should travel together to reduce round-trips) and **client-driven queries** (clients should be able to request exactly the shape of data they need — sparse fieldsets, included relationships, filtered and sorted collections — without the server needing to anticipate every query pattern).

Ad-hoc REST APIs solve these problems inconsistently:
- Some use nested objects for relationships (embed the entire author object inside a post); others use IDs (just include `author_id`). The embedded approach causes over-fetching; the ID-only approach causes N+1 requests.
- Some support `?fields=name,email` for sparse fieldsets; many don't. Some support `?include=author,comments`; most don't standardize the syntax.
- Error response structures are entirely bespoke — `{error: "not found"}`, `{message: "not found"}`, `{errors: [{code: 404, detail: "..."}]}` are all common and none are interchangeable.

JSON:API standardizes all of these. The tradeoff: JSON:API documents are more verbose than a minimal hand-rolled response, and the specification has a learning curve for both API implementers and consumers. The philosophical bet is that consistency across APIs is worth the verbosity overhead — a bet that pays off at scale (many APIs, many consumers, shared tooling) and loses at small scale (one API, one team, one consumer).

**Q3. How does JSON:API relate to other API specifications like OpenAPI (Swagger), GraphQL, and OData?**
A: They operate at different layers and solve different problems:

- **OpenAPI (Swagger)** — a specification for *documenting* APIs: endpoints, parameters, request/response schemas, authentication methods. It doesn't prescribe the *structure* of the JSON body — an OpenAPI spec can describe any JSON shape. JSON:API and OpenAPI are complementary: a JSON:API-compliant API can have an OpenAPI spec that describes its compound document structures.

- **GraphQL** — a query language and runtime that solves the same over-fetching and N+1 problems as JSON:API, but via a fundamentally different mechanism: clients write graph traversal queries; the server resolves them. GraphQL solves the client-driven query problem more flexibly than JSON:API but requires a different transport (not standard HTTP verbs/status codes), a schema definition language, and a resolver architecture. JSON:API is closer to REST and works with standard HTTP tooling; GraphQL requires a dedicated runtime.

- **OData** — Microsoft's Open Data Protocol, similar in goals to JSON:API (standardized querying, relationships, metadata) but considerably more complex, with SQL-like filter expressions (`$filter=name eq 'John'`), XML and JSON support, and a heavier metadata model. OData is common in enterprise Microsoft ecosystems (Dynamics, SharePoint, Power BI); JSON:API is more common in web/mobile application backends.

The practical positioning: JSON:API is the specification of choice for teams that want REST semantics with standardized structure and client-driven querying, without the architectural shift that GraphQL requires.

## Section 2: Document Structure

**Q4. What is the top-level structure of a JSON:API document?**
A: Every JSON:API document is a JSON object with a small set of defined top-level members. At the top level, a document must contain at least one of:

- **`data`** — the document's "primary data": a single resource object, an array of resource objects, or `null` (for an empty single-resource response).
- **`errors`** — an array of error objects. Mutually exclusive with `data`.
- **`meta`** — a meta object containing non-standard information. Can appear without `data` or `errors`.

Optional top-level members:
- **`included`** — an array of resource objects that are related to the primary data and included in the compound document (to avoid N+1 requests). Only present if the client requested included relationships.
- **`links`** — a links object with pagination links (`self`, `first`, `last`, `prev`, `next`) and other URL references.
- **`jsonapi`** — an object describing the server's JSON:API implementation version.

Minimal valid single-resource response:
```json
{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": {
      "title": "Introduction to JSON:API",
      "body": "JSON:API is a specification..."
    }
  }
}
```

Minimal valid collection response:
```json
{
  "data": [
    {
      "type": "articles",
      "id": "1",
      "attributes": { "title": "Introduction to JSON:API" }
    },
    {
      "type": "articles",
      "id": "2",
      "attributes": { "title": "Advanced JSON:API" }
    }
  ],
  "links": {
    "self": "https://api.example.com/articles?page[number]=1",
    "next": "https://api.example.com/articles?page[number]=2",
    "last": "https://api.example.com/articles?page[number]=5"
  },
  "meta": {
    "totalCount": 47
  }
}
```

**Q5. What is a resource object, and what are its required and optional members?**
A: A resource object is the fundamental unit of JSON:API — it represents a single domain entity. Required members:

- **`type`** — the resource type (a string, always plural by convention: `"articles"`, `"users"`, `"comments"`). The type is the key by which resources are identified in the compound document's `included` array.
- **`id`** — the resource's unique identifier within its type (a string). Required in responses; optional in create requests (if the server assigns IDs).

Optional members:
- **`attributes`** — an object containing the resource's domain data (title, body, createdAt, etc.). Does NOT include the resource's ID (that's the top-level `id`) or relationship foreign keys (those go in `relationships`).
- **`relationships`** — an object where each key is a relationship name and each value is a relationship object (described in Q7).
- **`links`** — a links object, typically containing a `self` link to the resource.
- **`meta`** — a meta object for non-standard resource-level information.

Full resource object example:
```json
{
  "type": "articles",
  "id": "1",
  "attributes": {
    "title": "Introduction to JSON:API",
    "body": "JSON:API is a specification...",
    "publishedAt": "2026-01-15T09:00:00Z",
    "wordCount": 1247
  },
  "relationships": {
    "author": {
      "links": {
        "self": "/articles/1/relationships/author",
        "related": "/articles/1/author"
      },
      "data": { "type": "people", "id": "42" }
    },
    "tags": {
      "data": [
        { "type": "tags", "id": "5" },
        { "type": "tags", "id": "12" }
      ]
    }
  },
  "links": {
    "self": "/articles/1"
  }
}
```

**Q6. Why does JSON:API separate `attributes` from `relationships`, and why are foreign keys not in `attributes`?**
A: The separation enforces a structural distinction between a resource's own data (things that describe the resource itself) and its associations to other resources (relationships). This distinction enables:

**Relationship-level operations:** JSON:API allows clients to read and modify a relationship independently of the resource's attributes. `GET /articles/1/relationships/author` returns only the author relationship data (just the ID linkage); `PATCH /articles/1/relationships/author` updates who the author is without touching any attributes. This is a clean separation that would be muddy if `author_id` lived in `attributes`.

**Included resource linkage:** when a client requests `?include=author`, the server includes the full author resource object in the top-level `included` array. The article's `relationships.author.data` contains the resource linkage (`{ "type": "people", "id": "42" }`) — a pointer into the `included` array. If `author_id` were in `attributes`, there would be no standardized way to express this pointer-to-included-resource linkage.

**Clarity for consumers:** attributes are the resource's intrinsic data. Relationships are its extrinsic connections. A consumer building a form to edit an article knows to look in `attributes` for editable fields (title, body) and in `relationships` for associated entities (author, category). This structural contract is consistent across all JSON:API resources.

**Practical implication:** if you're migrating a hand-rolled API to JSON:API, foreign key fields like `author_id`, `category_id`, and `tag_ids` are moved out of the body and into the `relationships` structure. They don't disappear — they become the `id` fields inside relationship data objects.

**Q7. How do relationships work in JSON:API, and what is the difference between a to-one and a to-many relationship?**
A: A relationship in JSON:API is an object within `relationships` that describes a resource's association to one or more other resources. It can contain up to three members:

- **`links`** — URLs for reading (`related`) and manipulating (`self`) the relationship.
- **`data`** — the resource linkage: the identity of the related resource(s). This is what allows compound document resolution.
- **`meta`** — non-standard metadata about the relationship.

**To-one relationship (belongs-to):**
`data` is a single resource identifier object (`{ "type": "people", "id": "42" }`) or `null` (relationship exists but is currently empty):
```json
"author": {
  "links": {
    "self": "/articles/1/relationships/author",
    "related": "/articles/1/author"
  },
  "data": { "type": "people", "id": "42" }
}
```

**To-many relationship (has-many):**
`data` is an array of resource identifier objects (empty array if no related resources):
```json
"comments": {
  "links": {
    "self": "/articles/1/relationships/comments",
    "related": "/articles/1/comments"
  },
  "data": [
    { "type": "comments", "id": "5" },
    { "type": "comments", "id": "12" },
    { "type": "comments", "id": "17" }
  ]
}
```

The `related` link URL serves as the endpoint for fetching the full related resource(s). The `self` link URL serves as the endpoint for manipulating the relationship (changing which resources are related) without modifying the resources themselves. This two-endpoint model (relationship endpoint vs related resource endpoint) is one of JSON:API's more nuanced — and frequently misunderstood — design decisions.

## Section 3: Compound Documents and Sparse Fieldsets

**Q8. What is a compound document, and how does it solve the N+1 request problem?**
A: A compound document is a JSON:API response that includes both the primary requested resource(s) AND related resource objects in a single HTTP response, using the top-level `included` array. Without compound documents, fetching an article with its author and tags would require three HTTP requests: one for the article, one for the author, one for the tags. With compound documents, all three are returned in one response.

The client requests inclusion with the `include` query parameter:
```
GET /articles/1?include=author,tags
```

The server responds with a compound document:
```json
{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": {
      "title": "Introduction to JSON:API"
    },
    "relationships": {
      "author": {
        "data": { "type": "people", "id": "42" }
      },
      "tags": {
        "data": [
          { "type": "tags", "id": "5" },
          { "type": "tags", "id": "12" }
        ]
      }
    }
  },
  "included": [
    {
      "type": "people",
      "id": "42",
      "attributes": {
        "firstName": "Jane",
        "lastName": "Doe",
        "email": "jane@example.com"
      }
    },
    {
      "type": "tags",
      "id": "5",
      "attributes": { "name": "engineering" }
    },
    {
      "type": "tags",
      "id": "12",
      "attributes": { "name": "architecture" }
    }
  ]
}
```

The client resolves the article's author by matching `relationships.author.data.id = "42"` with the object in `included` where `type = "people"` and `id = "42"`. This is JSON:API's compound document resolution algorithm — clients traverse the `included` array by type+id tuples rather than by position.

Efficiency properties of compound documents:
- **Deduplication** — if 10 articles in a collection all have the same author, the author object appears once in `included`, not 10 times.
- **Depth control** — `?include=comments.author` requests nested inclusion: include comments, and for each comment also include its author. The depth is controlled by the client, not hardcoded by the server.
- **Partial inclusion** — `?include=author` includes the author but not the tags. The client gets exactly what it needs, not everything.

**Q9. What are sparse fieldsets, and how do you request them?**
A: Sparse fieldsets allow clients to request only specific fields (attributes and relationships) for resource types, reducing response payload size. The query parameter is `fields[type]=field1,field2`:

```
GET /articles?include=author&fields[articles]=title,publishedAt&fields[people]=firstName,lastName
```

This requests:
- For articles: only the `title` and `publishedAt` attributes (not `body`, `wordCount`, etc.)
- For people (the included authors): only `firstName` and `lastName` (not `email`, `bio`, etc.)

Server response includes only the requested fields for each type:
```json
{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": {
      "title": "Introduction to JSON:API",
      "publishedAt": "2026-01-15T09:00:00Z"
    },
    "relationships": {
      "author": {
        "data": { "type": "people", "id": "42" }
      }
    }
  },
  "included": [
    {
      "type": "people",
      "id": "42",
      "attributes": {
        "firstName": "Jane",
        "lastName": "Doe"
      }
    }
  ]
}
```

Sparse fieldsets are particularly valuable for:
- **Mobile clients on constrained bandwidth** — a list view needs only `title` and `publishedAt`; the full `body` (potentially kilobytes) is not downloaded until the user opens the article.
- **List endpoints with many resources** — requesting 100 articles with all fields vs requesting only `title,thumbnail,publishedAt` can be a 10× response size difference.
- **Performance optimization** — servers that implement sparse fieldsets correctly can avoid querying or serializing unneeded fields, reducing database load and serialization time.

**Q10. How does a server correctly implement the `include` query parameter to avoid N+1 database queries?**
A: The `include` parameter is a client-driven directive that requires the server to eagerly fetch related resources — a form of explicit join or eager loading. Naive implementation causes N+1: fetch articles, then for each article fetch its author (N+1 queries). Correct implementation:

**SQL-level eager loading:**
```javascript
// Example: Sequelize ORM with include
async function getArticle(req, res) {
  const includeParam = req.query.include?.split(',') ?? [];
  const sequelizeIncludes = [];

  if (includeParam.includes('author')) {
    sequelizeIncludes.push({ model: Person, as: 'author' });
  }
  if (includeParam.includes('tags')) {
    sequelizeIncludes.push({ model: Tag, through: { attributes: [] } });
  }
  if (includeParam.includes('comments')) {
    const commentInclude = { model: Comment };
    // Nested: comments.author
    if (includeParam.includes('comments.author')) {
      commentInclude.include = [{ model: Person, as: 'author' }];
    }
    sequelizeIncludes.push(commentInclude);
  }

  const article = await Article.findByPk(req.params.id, {
    include: sequelizeIncludes,
  });

  // Serialize to JSON:API format
  res.json(serialize(article, includeParam));
}
```

**Dataloader pattern (for GraphQL-style resolution):**
If the server uses a resolver architecture, use a dataloader (batching + caching) to avoid N+1 even when includes are resolved individually:
```javascript
const authorLoader = new DataLoader(async (authorIds) => {
  const authors = await Person.findAll({ where: { id: authorIds } });
  return authorIds.map(id => authors.find(a => a.id === id));
});
// Instead of N queries for N articles' authors, batches into one WHERE id IN (...) query
```

**Query complexity limiting:**
Nested includes (`?include=comments.author.articles.comments`) can cause exponential query complexity. Implement a maximum include depth (typically 2–3 levels) and a maximum number of distinct include paths to prevent denial-of-service via query complexity.

## Section 4: CRUD Operations

**Q11. How do you create a resource using JSON:API, and what does the request/response look like?**
A: Resource creation uses `POST` to the resource's collection endpoint. The request body is a JSON:API document with a `data` member containing the resource to create:

```http
POST /articles HTTP/1.1
Content-Type: application/vnd.api+json
Accept: application/vnd.api+json

{
  "data": {
    "type": "articles",
    "attributes": {
      "title": "My New Article",
      "body": "Content here..."
    },
    "relationships": {
      "author": {
        "data": { "type": "people", "id": "42" }
      }
    }
  }
}
```

Key points:
- **`id` is omitted** when the server assigns IDs (client-generated IDs are also allowed by the spec — include `id` in the request if the client generates UUIDs).
- **`Content-Type: application/vnd.api+json`** is the JSON:API MIME type — required on all JSON:API requests with a body. Servers must respond with `415 Unsupported Media Type` if the `Content-Type` is wrong.
- **`Accept: application/vnd.api+json`** tells the server the client expects a JSON:API response.

Success response is `201 Created` with the created resource (including server-assigned ID and any server-set default values):
```http
HTTP/1.1 201 Created
Content-Type: application/vnd.api+json
Location: https://api.example.com/articles/99

{
  "data": {
    "type": "articles",
    "id": "99",
    "attributes": {
      "title": "My New Article",
      "body": "Content here...",
      "publishedAt": null,
      "createdAt": "2026-07-15T10:00:00Z"
    },
    "relationships": {
      "author": {
        "data": { "type": "people", "id": "42" }
      }
    },
    "links": {
      "self": "/articles/99"
    }
  }
}
```

If the server accepts the request but cannot respond with the full resource (for async creation), it returns `202 Accepted`. If the client sends a client-generated ID that already exists, the server returns `409 Conflict`.

**Q12. What is the difference between `PATCH` on a resource vs `PATCH` on a relationship endpoint?**
A: This is one of JSON:API's most important and often-missed distinctions:

**`PATCH /articles/1` — updates the resource itself:**
Modifies the resource's attributes and/or its relationships. The request body includes only the members being changed — JSON:API `PATCH` is a partial update (unlike `PUT` which replaces the entire resource):

```json
PATCH /articles/1

{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": {
      "title": "Updated Title"
    }
  }
}
```

This updates only the title. Other attributes and all relationships are unchanged. The server returns `200 OK` with the full updated resource, or `204 No Content` if it chooses not to return the resource body.

**`PATCH /articles/1/relationships/author` — updates the relationship only:**
Replaces the relationship without touching the resource's attributes. Changes *which* person is the article's author, not any article data:

```json
PATCH /articles/1/relationships/author

{
  "data": { "type": "people", "id": "9" }
}
```

This changes the author to person 9. The article's title, body, and other attributes are untouched. For a to-many relationship, `PATCH` completely replaces the set: `PATCH /articles/1/relationships/tags` with `{"data": [{"type":"tags","id":"5"}]}` replaces all current tags with only tag 5.

**`POST /articles/1/relationships/tags` — adds to a to-many relationship:**
Appends to the set without replacing it. `POST /articles/1/relationships/tags` with `{"data": [{"type":"tags","id":"20"}]}` adds tag 20 to the existing tags.

**`DELETE /articles/1/relationships/tags` — removes from a to-many relationship:**
Removes specific members. `DELETE /articles/1/relationships/tags` with `{"data": [{"type":"tags","id":"5"}]}` removes only tag 5 from the tags set.

This three-level operation model (resource CRUD + relationship CRUD + related resource CRUD) is what makes JSON:API's relationship handling uniquely expressive — relationships are first-class HTTP resources with their own endpoints and operations.

## Section 5: Filtering, Sorting, and Pagination

**Q13. How does JSON:API specify filtering, sorting, and pagination, and why are these "implementation-specific"?**
A: JSON:API defines the *parameter naming conventions* for filtering, sorting, and pagination but intentionally leaves their semantics to the implementation. This is a pragmatic acknowledgment that filtering semantics are domain-specific — a financial API's date range filter is different from a search API's full-text filter — and no single filter DSL would satisfy all use cases.

**Sorting (`sort` parameter):**
The specification is precise here: `sort=field` for ascending order, `sort=-field` for descending (leading minus sign), comma-separated for multiple fields: `sort=-publishedAt,title` (newest first, then alphabetically by title). This convention is part of the spec.

**Pagination (`page` parameter):**
The spec recommends using the `page` namespace for pagination parameters and defines the links for pagination (`first`, `last`, `prev`, `next`), but the actual pagination strategy is implementation-defined. Common strategies:
- Page-based: `page[number]=2&page[size]=25`
- Cursor-based: `page[cursor]=eyJpZCI6MTAwfQ&page[size]=25`
- Offset-based: `page[offset]=50&page[limit]=25`

**Filtering (`filter` parameter):**
The spec only reserves the `filter` parameter namespace. The filter syntax is entirely implementation-defined. Common conventions:
- Simple equality: `filter[status]=published`
- Multiple values: `filter[status]=published,draft`
- Range (common extension): `filter[createdAt][gte]=2026-01-01`
- Complex filter (JSON API extension for jsonapi.org): `filter={"status":{"$eq":"published"}}`

The intentional vagueness of filtering is a spec weakness that libraries like `json-api-query-parser` and `@nestjs/platform-json-api` fill with their own conventions. When adopting JSON:API, document your filter syntax explicitly since it is the most likely source of consumer confusion.

**Q14. Show what a complete list request with filtering, sorting, sparse fieldsets, inclusion, and pagination looks like.**
A:

```
GET /articles?filter[status]=published
            &sort=-publishedAt,title
            &page[number]=2
            &page[size]=10
            &fields[articles]=title,publishedAt,wordCount
            &fields[people]=firstName,lastName
            &include=author
```

URL-decoded for readability — in practice the brackets are percent-encoded:
```
GET /articles?filter%5Bstatus%5D=published&sort=-publishedAt%2Ctitle&page%5Bnumber%5D=2&page%5Bsize%5D=10&fields%5Barticles%5D=title%2CpublishedAt%2CwordCount&fields%5Bpeople%5D=firstName%2ClastName&include=author
```

Response:
```json
{
  "data": [
    {
      "type": "articles",
      "id": "47",
      "attributes": {
        "title": "Advanced JSON:API",
        "publishedAt": "2026-07-10T14:00:00Z",
        "wordCount": 2340
      },
      "relationships": {
        "author": {
          "data": { "type": "people", "id": "42" }
        }
      },
      "links": { "self": "/articles/47" }
    },
    {
      "type": "articles",
      "id": "38",
      "attributes": {
        "title": "Building Scalable APIs",
        "publishedAt": "2026-07-08T09:30:00Z",
        "wordCount": 1890
      },
      "relationships": {
        "author": {
          "data": { "type": "people", "id": "15" }
        }
      },
      "links": { "self": "/articles/38" }
    }
  ],
  "included": [
    {
      "type": "people",
      "id": "42",
      "attributes": { "firstName": "Jane", "lastName": "Doe" }
    },
    {
      "type": "people",
      "id": "15",
      "attributes": { "firstName": "John", "lastName": "Smith" }
    }
  ],
  "links": {
    "self": "/articles?filter[status]=published&sort=-publishedAt,title&page[number]=2&page[size]=10",
    "first": "/articles?filter[status]=published&sort=-publishedAt,title&page[number]=1&page[size]=10",
    "prev": "/articles?filter[status]=published&sort=-publishedAt,title&page[number]=1&page[size]=10",
    "next": "/articles?filter[status]=published&sort=-publishedAt,title&page[number]=3&page[size]=10",
    "last": "/articles?filter[status]=published&sort=-publishedAt,title&page[number]=5&page[size]=10"
  },
  "meta": {
    "totalCount": 47,
    "pageCount": 5
  }
}
```

Note that the deduplication of the `included` array works correctly here — even though articles 47 and 38 have different authors, each author appears once in `included`. If two articles had the same author, that author would still appear only once in the `included` array.

## Section 6: Error Handling

**Q15. What does a JSON:API error response look like, and what fields does each error object contain?**
A: Errors in JSON:API are expressed as an `errors` array at the top level (never alongside `data`). Each error object may contain:

- **`id`** — a unique identifier for this specific occurrence of the error (useful for support tickets: "the error with id abc-123").
- **`status`** — the HTTP status code applicable to this error, as a string (`"422"`, `"404"`).
- **`code`** — an application-specific error code string (machine-readable, for client-side error handling logic).
- **`title`** — a short, human-readable summary of the error. Should be stable across occurrences of the same error type (don't include variable data in the title).
- **`detail`** — a human-readable explanation specific to this occurrence. Can include variable data (the specific field value that failed validation).
- **`source`** — an object indicating the source of the error:
  - `pointer` — a JSON Pointer (RFC 6901) to the field in the request document that caused the error: `/data/attributes/title` or `/data/relationships/author/data/id`.
  - `parameter` — the name of the query parameter that caused the error: `"filter[status]"`.
- **`links`** — a links object, typically containing an `about` link to documentation for this error type.
- **`meta`** — non-standard error metadata.

Validation error example (multiple errors in one response — JSON:API allows returning all validation errors at once, not just the first):
```json
{
  "errors": [
    {
      "status": "422",
      "code":   "VALIDATION_REQUIRED_FIELD",
      "title":  "Required field missing",
      "detail": "The 'title' attribute is required and cannot be blank.",
      "source": {
        "pointer": "/data/attributes/title"
      }
    },
    {
      "status": "422",
      "code":   "VALIDATION_MAX_LENGTH",
      "title":  "Field exceeds maximum length",
      "detail": "The 'body' attribute must be 10,000 characters or fewer. Received 12,847 characters.",
      "source": {
        "pointer": "/data/attributes/body"
      }
    },
    {
      "status": "422",
      "code":   "VALIDATION_RELATIONSHIP_NOT_FOUND",
      "title":  "Related resource not found",
      "detail": "The author with id '999' does not exist.",
      "source": {
        "pointer": "/data/relationships/author/data/id"
      }
    }
  ]
}
```

The `pointer` field is particularly powerful for client-side form validation — the client can parse the `source.pointer`, extract the field path, and display the error message adjacent to the correct form field without writing custom error-to-field mapping logic.

**Q16. How does JSON:API handle the HTTP status code for an errors response containing multiple errors of different severities?**
A: When multiple errors are returned (e.g., several validation failures), each error object has its own `status` field. For the HTTP response status code, the spec says: use the most generally applicable HTTP error code for the response. In practice:

- If all errors are the same status: use that status (all 422 → `HTTP 422`).
- If errors span multiple 4xx codes: use `400 Bad Request` as the generic client error.
- If some errors are 4xx and some are 5xx: this is unusual; use `500` and document clearly.

The key principle: the HTTP status code is a summary for intermediaries (proxies, monitoring tools) that don't parse the body. The detailed per-error status codes in the `errors` array are for the client. An intelligent client reads the array; an unintelligent intermediary reads the HTTP status.

## Section 7: Implementation Considerations

**Q17. What are the common Node.js libraries for implementing JSON:API, and what do they handle?**
A: Building a JSON:API implementation from scratch is verbose and error-prone — the spec has many edge cases (compound document deduplication, sparse fieldset filtering, relationship link generation). Libraries handle the serialization/deserialization layer:

**`jsonapi-serializer` (Node.js):**
A serializer that transforms plain JavaScript objects into JSON:API document format:
```javascript
const { Serializer } = require('jsonapi-serializer');

const ArticleSerializer = new Serializer('articles', {
  attributes: ['title', 'body', 'publishedAt', 'author', 'tags'],
  author: {
    ref: 'id',                    // serialize as relationship linkage
    attributes: ['firstName', 'lastName', 'email'],
  },
  tags: {
    ref: 'id',
    attributes: ['name'],
  },
  keyForAttribute: 'camelCase',   // convert snake_case DB fields to camelCase
  pluralizeType: true,            // 'article' → 'articles'
});

// In a route handler:
const article = await Article.findByPk(id, { include: [Person, Tag] });
res.json(ArticleSerializer.serialize(article));
```

**`@jsonapi-nestjs/core` (NestJS):**
A full JSON:API framework module for NestJS that handles routing, serialization, deserialization, and query parsing:
```typescript
@JsonApiController({
  entity: Article,
  type: 'articles',
})
export class ArticlesController extends JsonApiController<Article> {}
// Generates all JSON:API endpoints, handles include/fields/filter/sort/page parsing
```

**`json-api-query-parser` / `qs`:**
Query string parsers that handle the `filter[status]`, `page[number]`, `fields[articles]` bracket notation, which standard query string parsers (`querystring`, `qs`) handle differently:
```javascript
const qs = require('qs');
// qs correctly parses: { filter: { status: 'published' }, page: { number: '2' } }
app.use((req, res, next) => {
  req.query = qs.parse(req.url.split('?')[1]);
  next();
});
```

**Q18. What are the performance considerations specific to implementing JSON:API at scale?**
A: JSON:API introduces specific performance concerns that don't exist in simpler REST APIs:

**Compound document deduplication cost:**
Building the `included` array requires deduplicating related resources across all primary resources in the response. For a collection of 100 articles with shared authors, the server must track which author IDs have already been added to `included`. This is an in-memory set operation (O(n) where n is the number of included resources) that is negligible for small responses but non-trivial for large collections with many included resources.

**Sparse fieldset query optimization:**
A correctly implemented server should only fetch the requested fields from the database — not fetch all fields and then filter in the serializer. This requires passing the `fields` parameter through to the query layer:
```javascript
// Naive (wrong) — fetches all fields, filters in serializer
const articles = await Article.findAll();
return applySparseFieldsets(articles, req.query.fields);

// Correct — only selects requested fields from DB
const requestedFields = parseFieldsets(req.query.fields?.articles);
const articles = await Article.findAll({
  attributes: requestedFields,   // SELECT only requested columns
});
```

**Include depth limiting:**
`?include=comments.author.articles.comments.author` generates recursive queries that can hit the database dozens of times or produce enormous result sets. Always enforce a maximum include depth (2–3 levels) and a maximum number of included resources per response.

**`application/vnd.api+json` Content-Type parsing:**
Express's built-in JSON parser recognizes `application/json` but not `application/vnd.api+json`. Configure the body parser to accept the JSON:API content type:
```javascript
app.use(express.json({ type: ['application/json', 'application/vnd.api+json'] }));
```
A missing body parser configuration for the JSON:API MIME type is one of the most common implementation bugs — all POST/PATCH requests silently receive an empty `req.body`.

## Section 8: Trade-offs and Scenario Questions

**Q19. What are the strongest arguments against adopting JSON:API, and when is it the wrong choice?**
A: JSON:API is not universally the right choice. The strongest arguments against:

**Verbosity overhead:**
A simple resource that would be 200 bytes as a hand-rolled JSON response is 600+ bytes as a JSON:API document. For mobile applications on constrained bandwidth, this matters. The counter-argument (sparse fieldsets) requires implementation effort that many teams skip. For high-frequency, low-complexity APIs (a websocket message, a metrics endpoint, a health check), the structural overhead of JSON:API is pure waste.

**Learning curve for consumers:**
A developer who has never seen JSON:API needs to understand: the `data`/`included`/`links`/`meta` structure, the compound document resolution algorithm (matching by type+id into `included`), the relationship vs related-resource endpoint distinction, and the query parameter conventions. This is a non-trivial upfront investment. For a simple public API consumed by a broad developer audience, the unfamiliarity of JSON:API may increase integration friction more than its consistency reduces it.

**Library ecosystem maturity:**
JSON:API libraries exist for all major languages and frameworks but vary in quality and maintenance status. A team adopting JSON:API without a well-maintained library will write a lot of serialization/deserialization boilerplate. This overhead is less acceptable for a small team building an MVP than for a platform team building shared infrastructure.

**Overkill for simple use cases:**
A CRUD API for a mobile app with 5 resource types, no complex relationships, and a single client doesn't need JSON:API's relationship management and compound document machinery. The overhead of conforming to the spec (including generating `links`, implementing `relationships`, supporting `include` and `fields`) is disproportionate for simple APIs.

**When to use it:** multi-consumer APIs with complex resource graphs; platform APIs used by many clients with diverse query needs; teams that want to use off-the-shelf client libraries (ember-data, redux-json-api) that have native JSON:API support; APIs where consistency and discoverability across many resource types matters more than minimal payload size.

**Q20. "Your team is building a new API for a mobile app and a web dashboard. A teammate proposes JSON:API. How do you evaluate this?"**
A: This is a trade-off evaluation, not a yes/no answer. Key questions to ask:

**How complex is the resource graph?**
If the app has 3 simple resources with no meaningful relationships (a blog with articles, no authors or tags to load), JSON:API's compound document machinery adds verbosity without benefit. If the app has a social feed where posts have authors, media attachments, likes, and comments — each potentially needing to be included — compound documents save meaningful round-trips.

**Who are the consumers and how many?**
Two consumers (mobile + web), both controlled by your team, can adapt quickly if the API contract changes. The shared tooling benefit of JSON:API is higher if there are many consumers on different schedules. For two internal consumers, a well-documented bespoke API may have lower total cost.

**What client framework is being used?**
Ember.js has native JSON:API support via ember-data — adopting JSON:API would eliminate custom data-fetching code entirely. React/Redux apps can use `redux-json-api` or `react-admin` with JSON:API support. If the client framework has native JSON:API support, adoption cost drops significantly.

**What is the team's API discipline?**
JSON:API enforces consistency — it is hard to make inconsistent structural choices when the spec prescribes them. For a team that otherwise tends toward ad-hoc API design (inconsistent pagination, varying error formats, bespoke relationship representations), JSON:API's constraints produce a better outcome than the alternative. For a disciplined team with strong API design standards, the constraint overhead may not be worth it.

**Recommendation framework:** adopt JSON:API if: the resource graph is complex (3+ resources with meaningful relationships), client includes/sparse fieldsets would provide measurable performance benefit, or the client framework has native JSON:API support. Skip it if: the resource graph is simple, the API has one controlled consumer, or payload size is highly constrained (IoT, bandwidth-sensitive mobile).

**Q21. "A consumer is making 5 API calls to build a single page (the article, the author, the tags, the comments, and the comment authors). How does JSON:API help, and how would you implement the fix?"**
A: This is the classic N+1 request problem from the client's perspective — five separate HTTP requests to compose a single view. JSON:API's `include` parameter collapses this to one request:

**Before (5 requests):**
```
GET /articles/1
GET /people/42              (author)
GET /articles/1/tags
GET /articles/1/comments
GET /people/7,15,22         (comment authors — N requests or awkward batch)
```

**After (1 compound document request):**
```
GET /articles/1?include=author,tags,comments,comments.author
               &fields[articles]=title,body,publishedAt
               &fields[people]=firstName,lastName,avatarUrl
               &fields[tags]=name
               &fields[comments]=body,createdAt
```

The server implementation must:
1. Parse the `include` parameter: `['author', 'tags', 'comments', 'comments.author']`
2. Detect the nested include: `comments.author` means include comments AND for each comment include its author
3. Execute a single query (or batched queries) using eager loading:
```javascript
const article = await Article.findByPk(id, {
  include: [
    { model: Person, as: 'author' },
    { model: Tag },
    {
      model: Comment,
      include: [{ model: Person, as: 'author' }]  // nested include
    },
  ],
});
```
4. Build the `included` array with deduplication — if two comments have the same author, include that person object once
5. Apply sparse fieldsets — only serialize the requested fields for each type

The result: the client makes one HTTP request with a predictable response time (one database round-trip with proper JOIN/eager loading) instead of five serial requests. For a typical mobile client on a 100ms-latency mobile connection, this is the difference between a 500ms page load (1 request) and a 2.5-second page load (5 serial requests at 500ms each).

## Quick Reference

**JSON:API Document Structure:**
```
{
  "data":     resource object | resource object[] | null   ← primary data
  "errors":   error object[]                               ← mutually exclusive with data
  "included": resource object[]                            ← compound document related resources
  "links":    { self, first, last, prev, next }            ← pagination + self
  "meta":     { totalCount, ... }                          ← non-standard metadata
  "jsonapi":  { "version": "1.1" }                         ← spec version
}
```

**Resource Object Structure:**
```
{
  "type":          "articles",             ← required, plural
  "id":            "1",                    ← required in responses
  "attributes":    { title, body, ... }    ← resource's own data
  "relationships": {                       ← associations to other resources
    "author": { "data": { "type": "people", "id": "42" } },
    "tags":   { "data": [ { "type": "tags", "id": "5" } ] }
  },
  "links":         { "self": "/articles/1" },
  "meta":          { ... }
}
```

**Query Parameter Cheat Sheet:**

| Parameter | Purpose | Example |
|--- |--- |--- |
| `include` | Compound document inclusions | `include=author,comments.author` |
| `fields[type]` | Sparse fieldsets | `fields[articles]=title,body` |
| `sort` | Sort fields (- prefix = desc) | `sort=-publishedAt,title` |
| `page[number]` | Page-based pagination | `page[number]=2&page[size]=25` |
| `page[cursor]` | Cursor-based pagination | `page[cursor]=xyz&page[size]=25` |
| `filter[field]` | Filtering (impl-defined) | `filter[status]=published` |

**HTTP Methods and Endpoints:**

| Operation | Method | URL | Body |
|--- |--- |--- |--- |
| List resources | GET | `/articles` | — |
| Fetch resource | GET | `/articles/1` | — |
| Create resource | POST | `/articles` | `{data: {type, attributes, relationships}}` |
| Update resource | PATCH | `/articles/1` | `{data: {type, id, attributes}}` |
| Delete resource | DELETE | `/articles/1` | — |
| Fetch related | GET | `/articles/1/author` | — |
| Fetch relationship | GET | `/articles/1/relationships/author` | — |
| Update to-one rel | PATCH | `/articles/1/relationships/author` | `{data: {type, id}}` |
| Add to to-many rel | POST | `/articles/1/relationships/tags` | `{data: [{type, id}]}` |
| Remove from to-many | DELETE | `/articles/1/relationships/tags` | `{data: [{type, id}]}` |
| Replace to-many rel | PATCH | `/articles/1/relationships/tags` | `{data: [{type, id}]}` |

**Required MIME Type:**
```
Content-Type: application/vnd.api+json
Accept:       application/vnd.api+json
```

**Tip for the interview:** At 5 YOE level, JSON:API questions are about understanding the *why* behind the spec's design decisions, not just the structure. The strongest answers connect the spec features to the problems they solve: compound documents eliminate N+1 requests; sparse fieldsets solve over-fetching; the `source.pointer` in errors enables form validation without custom mapping; the relationship endpoint vs related resource endpoint distinction enables relationship-as-a-resource semantics. The most impressive addition is the trade-off discussion — when JSON:API's consistency overhead is worth paying and when it's overkill. The war story format works well: "we migrated a mobile app's data layer to JSON:API with ember-data and dropped our average page load time from 800ms to 200ms by replacing 4 serial API calls with one compound document request — but the same spec choice would have been wrong for our high-frequency IoT metrics endpoint where the structural overhead was 10× the payload size."
