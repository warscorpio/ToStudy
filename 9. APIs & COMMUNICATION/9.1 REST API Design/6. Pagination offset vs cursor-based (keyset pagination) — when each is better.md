# Pagination: Offset vs Cursor-Based (Keyset) — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Pagination Exists

**Q1. Why is pagination necessary rather than returning all records?**
A: Returning an unbounded result set from an API creates compounding problems across every layer:
- **Network**: Transferring 100,000 records in a single response consumes bandwidth, blocks the connection for the full transfer duration, and times out mobile clients.
- **Memory**: The server must materialise the entire result set in memory — serialise it, hold it while writing to the socket. At scale, this is the primary vector for OOM-kills on API servers.
- **Database**: Even if the query is fast, fetching all rows means the database holds the result cursor open, consuming connections and buffer pool memory.
- **Client**: The browser or mobile app must parse, store, and render everything at once — UI freezes, janky scroll, wasted render cycles on off-screen items.

Pagination bounds all four: a single page request transfers a fixed, predictable amount of data. The challenge is choosing the right pagination strategy — the wrong choice causes different but equally serious problems at scale.

**Q2. What are the two main pagination strategies and what is the fundamental difference between them?**
A: The two strategies differ in how they express "where in the result set am I":

**Offset pagination**: Expresses position as a numeric skip count — "skip the first N rows, return the next M." The position is a count from the beginning. The client passes `page=5&limit=20` or `offset=80&limit=20`, and the server translates this to `LIMIT 20 OFFSET 80`.

**Cursor-based (keyset) pagination**: Expresses position as a reference to a specific record — "give me records that come after this one." The position is anchored to a concrete row in the data, not a count. The client passes `after=<opaque_cursor>&limit=20`, and the server translates this to a `WHERE` clause that filters to rows after the cursor's encoded position.

The difference is not just syntactic — it reflects different database operations: offset counts rows from the beginning every time; keyset seeks directly to the cursor position via an index. This produces radically different performance and consistency properties at scale.

## Section 2: Offset Pagination

**Q3. How does offset pagination work at the SQL level?**
A: Offset pagination maps directly to SQL's `LIMIT` and `OFFSET` clauses:

```sql
-- Page 1: first 20 items
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- Page 4: skip the first 60 items, return items 61-80
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 60;
```

The REST API typically exposes either `page` + `limit` (human-friendly) or `offset` + `limit` (lower-level):

```
GET /posts?page=4&limit=20
GET /posts?offset=60&limit=20   ← offset = (page - 1) * limit
```

The response typically includes metadata for the client to render navigation controls:

```json
{
  "data": [ ... ],
  "pagination": {
    "page": 4,
    "per_page": 20,
    "total_items": 1053,
    "total_pages": 53,
    "has_next_page": true,
    "has_prev_page": true
  }
}
```

**Q4. What does the database actually do when processing a large OFFSET?**
A: This is the core performance problem. `LIMIT 20 OFFSET 10000` does not mean "jump to row 10000 and read 20." It means:
1. Sort the result set (or use an index for ordered access)
2. **Scan and discard** the first 10,000 rows
3. Return the next 20

The database cannot skip directly to row 10,000 using a standard B-tree index — it must traverse the index from the beginning, counting rows as it goes. At `OFFSET 10000`, the query reads 10,020 rows and throws away 10,000. At `OFFSET 1,000,000`, it reads 1,000,020 rows and throws away 1,000,000.

```sql
EXPLAIN ANALYZE
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
-- Output: Index Scan ... rows=10020, actual time=245ms
--         (10020 index entries traversed to deliver 20 rows)

EXPLAIN ANALYZE
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 0;
-- Output: Index Scan ... rows=20, actual time=0.3ms
--         (20 index entries traversed to deliver 20 rows)
```

The time to serve page N scales linearly with N — the last page of a million-record table takes roughly 50,000× longer than the first page.

## Section 3: The Problems with Offset Pagination

**Q5. What is the "drifting page" problem and what user-visible bugs does it cause?**
A: Offset pagination anchors position to a count from the beginning of the result set. That count is only stable if the underlying data doesn't change between requests. In any live system, it changes constantly — and causes two distinct anomalies:

**Item duplication**: A user loads page 1 (items 1–20, sorted by `created_at DESC`). While they scroll, 5 new items are inserted at the top. They request page 2 (`OFFSET 20`). The 5 new items pushed the original items 1–5 down to positions 6–10. The query at `OFFSET 20` now returns original items 1–5 again — the user sees duplicates.

**Item skipping**: A user loads page 1 (items 1–20). While they scroll, 5 items are deleted from the result set. They request page 2 (`OFFSET 20`). The deletions shifted the remaining items up — original items 16–20 are now in positions 11–15. The query at `OFFSET 20` skips them entirely.

Both bugs are silent from the server's perspective — the query executes correctly; it's the semantics that are broken. For a product feed or social timeline, this means users see a confusing, inconsistent view of the world. For an admin table processing records, it means some records are processed twice and some are never processed.

**Q6. Why is the `total_count` in offset pagination responses expensive?**
A: To show "Page 4 of 53" or "1,053 total results," the server must run a `COUNT(*)` query alongside the data query:

```sql
SELECT COUNT(*) FROM posts WHERE user_id = $1;       -- total count
SELECT * FROM posts WHERE user_id = $1
ORDER BY created_at DESC LIMIT 20 OFFSET 60;         -- page data
```

On a large table with complex `WHERE` conditions, `COUNT(*)` requires a full index scan of all matching rows — it cannot be satisfied from the index alone without examining every matching entry. In PostgreSQL, MVCC means the database cannot use approximate row counts from `pg_class.reltuples` for a filtered count; it must count actual visible rows. On a table with millions of rows, this can add 200–500ms to every paginated request.

Practical mitigations:
- **Remove total count**: Most UIs don't actually need "of 1,053" — just `has_next_page: true` is sufficient for "load more" UIs.
- **Approximate count**: Use `pg_class.reltuples` or `EXPLAIN` estimated rows for a fast, approximate total (±a few percent) suitable for display purposes.
- **Cache the count**: Cache `COUNT(*)` with a short TTL (30s–60s) at the cost of slight staleness.
- **Counter table**: Maintain a denormalized count in a separate table, incremented/decremented on writes. Exact and fast; adds write overhead.

**Q7. Does offset pagination perform well on indexed columns? Why isn't the index enough?**
A: An index helps with ordering and filtering but does not eliminate the offset scan. Consider:

```sql
-- Index exists on (created_at DESC, id DESC)
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 50000;
```

The index allows the database to traverse rows in `created_at DESC` order without a sort operation. But it still traverses 50,020 index entries to count 50,000 discards before reaching the 20 it returns. The index makes the scan faster than a full table scan, but the fundamental `O(offset)` complexity remains. At `OFFSET 500,000`, even a perfectly-structured index scan takes hundreds of milliseconds.

The index cannot skip to the Nth entry without counting — B-trees support range lookups ("everything after this key") but not position lookups ("the entry at position N"). This is exactly the gap that keyset pagination exploits.

## Section 4: Cursor-Based (Keyset) Pagination

**Q8. How does keyset pagination work at the SQL level?**
A: Keyset pagination replaces the `OFFSET` clause with a `WHERE` clause that filters to rows "after" the last seen row, based on the values of the sort columns:

```sql
-- First page (no cursor)
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Last row: { created_at: '2025-01-15 12:00:00', id: 1042 }

-- Second page (cursor encodes the last row's values)
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ('2025-01-15 12:00:00', 1042)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Third page (cursor encodes the new last row's values)
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ('2025-01-14 09:30:00', 987)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

The `WHERE (created_at, id) < ($1, $2)` clause is a tuple comparison — it matches rows where either `created_at < $1`, or `created_at = $1 AND id < $2`. With a composite index on `(created_at DESC, id DESC)`, the database performs a direct **index seek** to the cursor position and reads exactly `LIMIT` rows forward — scanning 20 rows to return 20 rows, regardless of how deep into the result set the cursor is.

**Q9. Why does keyset pagination require a composite cursor column and what happens without one?**
A: If you cursor on a single column that is not strictly unique (e.g., `created_at` alone), rows with identical values at the page boundary cause incorrect results:

```
posts sorted by created_at DESC:
  Row A: created_at=2025-01-15 12:00:00
  Row B: created_at=2025-01-15 12:00:00   ← same timestamp as A
  Row C: created_at=2025-01-15 12:00:00   ← same timestamp as A
  Row D: created_at=2025-01-14 09:00:00
```

If page 1 ends with Row A and the cursor encodes `created_at=2025-01-15 12:00:00`, the next page query `WHERE created_at < '2025-01-15 12:00:00'` skips Rows B and C entirely — they have the same timestamp as the cursor boundary.

The fix: always include a unique column (typically `id`) as the tiebreaker in both the `ORDER BY` and the cursor:

```sql
ORDER BY created_at DESC, id DESC
WHERE (created_at, id) < ($cursor_created_at, $cursor_id)
```

The composite tuple comparison handles ties correctly: rows with the same `created_at` are disambiguated by `id`. No rows are skipped or duplicated regardless of how many share the same timestamp.

**Q10. How does keyset pagination provide consistency guarantees that offset pagination cannot?**
A: Keyset pagination anchors to a specific row's values, not a count from the beginning. When rows are inserted or deleted:

- **Insertions**: New rows inserted "before" the cursor (newer timestamps in a DESC sort) don't affect what comes "after" the cursor. The next page returns exactly the rows that logically follow the last seen row.
- **Deletions**: A row deleted from the result set between page requests doesn't shift other rows' cursor positions. The next keyset query continues from the same position regardless.

The cursor is an **absolute position** in value space, not a relative position in row count. A user scrolling through a live social feed sees no duplications or skips — every item appears exactly once, regardless of how frequently new items arrive or old ones are deleted. This is the fundamental semantic difference: offset says "skip N rows from now," which can only be consistent if N never changes; keyset says "start after this value," which is stable regardless of mutations.

## Section 5: Implementation Details

**Q11. How do you encode and decode a cursor in a REST API?**
A: The cursor should be **opaque** to the client — they should not need to understand or construct it; they just pass it back as-is. The standard approach is base64-encoding a JSON payload of the sort column values:

```typescript
interface CursorPayload {
  created_at: string;   // ISO 8601 string
  id: number;
}

function encodeCursor(lastItem: Post): string {
  const payload: CursorPayload = {
    created_at: lastItem.created_at.toISOString(),
    id: lastItem.id,
  };
  return Buffer.from(JSON.stringify(payload)).toString('base64url');
}

function decodeCursor(cursor: string): CursorPayload {
  try {
    return JSON.parse(Buffer.from(cursor, 'base64url').toString('utf8'));
  } catch {
    throw new BadRequestException('Invalid pagination cursor');
  }
}

// In the service
async getPosts(after?: string, limit = 20): Promise<PostPage> {
  let whereClause = '';
  let params: any[] = [limit];

  if (after) {
    const { created_at, id } = decodeCursor(after);
    whereClause = 'WHERE (created_at, id) < ($2, $3)';
    params = [limit, created_at, id];
  }

  const rows = await db.query(
    `SELECT * FROM posts ${whereClause}
     ORDER BY created_at DESC, id DESC
     LIMIT $1`,
    params,
  );

  const nextCursor = rows.length === limit
    ? encodeCursor(rows[rows.length - 1])
    : null;

  return { data: rows, next_cursor: nextCursor, has_next: nextCursor !== null };
}
```

Opacity prevents clients from constructing arbitrary cursors, protects internal schema details (column names, data types), and allows the cursor format to change without a breaking API change (clients never parse it).

**Q12. Should you sign or encrypt cursors? When does it matter?**
A: Plain base64 cursors are reversible — any client can decode them and see the underlying column values. Whether this matters depends on your data:

- **Expose nothing sensitive**: If the cursor encodes `{ created_at, id }` where `id` is a publicly visible integer, opacity is convention, not security. No need to sign.
- **Prevent cursor forgery for security**: If the `WHERE` clause generated from the cursor could be used to access records outside the user's permission scope (e.g., cursor-based traversal of another user's private data), sign or HMAC the cursor to prevent tampering.
- **Hide internal schema**: If the cursor reveals column names or data types you'd rather not expose (internal pricing tiers, UUID structure that reveals system internals), encrypt it.

```typescript
import { createHmac } from 'crypto';

function signCursor(payload: CursorPayload, secret: string): string {
  const data = JSON.stringify(payload);
  const sig  = createHmac('sha256', secret).update(data).digest('base64url');
  return Buffer.from(JSON.stringify({ data, sig })).toString('base64url');
}

function verifyCursor(cursor: string, secret: string): CursorPayload {
  const { data, sig } = JSON.parse(Buffer.from(cursor, 'base64url').toString('utf8'));
  const expected = createHmac('sha256', secret).update(data).digest('base64url');
  if (sig !== expected) throw new BadRequestException('Cursor tampered');
  return JSON.parse(data);
}
```

For most REST APIs, signed cursors are sufficient. Full encryption is warranted only when column values themselves are sensitive.

**Q13. How do you implement a "previous page" with cursor pagination?**
A: Moving backwards in a keyset result requires reversing the sort direction. For a result sorted `ORDER BY created_at DESC, id DESC`, "previous page" means "items that come before the first item on the current page" — i.e., items with *larger* `created_at` or `id` values:

```typescript
// Expose both after and before cursors
GET /posts?limit=20           → first page; response includes next_cursor
GET /posts?after=<cursor>&limit=20  → forward navigation
GET /posts?before=<cursor>&limit=20 → backward navigation (prev page)
```

```sql
-- Before cursor: get the 20 rows "above" the current page's first item
-- Using a subquery to re-sort into the correct DESC display order
SELECT * FROM (
  SELECT * FROM posts
  WHERE (created_at, id) > ($cursor_created_at, $cursor_id)  -- inverted comparison
  ORDER BY created_at ASC, id ASC                             -- inverted sort for LIMIT
  LIMIT 20
) sub
ORDER BY created_at DESC, id DESC;  -- re-sort for consistent display
```

The response returns both a `next_cursor` (derived from the last item) and a `prev_cursor` (derived from the first item). Many APIs simplify this by not supporting `before` at all — UIs that only need "load more" scrolling only need forward navigation. Bidirectional navigation is required for "previous page" buttons in paginated table UIs built on keyset pagination.

## Section 6: REST API Design

**Q14. What should the response envelope look like for each pagination strategy?**
A:

**Offset pagination response**:
```json
{
  "data": [ { "id": 101, "title": "..." }, "..." ],
  "pagination": {
    "page": 4,
    "per_page": 20,
    "total_items": 1053,
    "total_pages": 53,
    "has_next_page": true,
    "has_prev_page": true
  },
  "links": {
    "self":  "/posts?page=4&limit=20",
    "next":  "/posts?page=5&limit=20",
    "prev":  "/posts?page=3&limit=20",
    "first": "/posts?page=1&limit=20",
    "last":  "/posts?page=53&limit=20"
  }
}
```

**Cursor pagination response**:
```json
{
  "data": [ { "id": 101, "title": "..." }, "..." ],
  "pagination": {
    "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNS0wMS0xNVQxMjowMDowMFoiLCJpZCI6MTA0Mn0",
    "prev_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNS0wMS0xNVQxNDowMDowMFoiLCJpZCI6MTA2MX0",
    "has_next_page": true,
    "has_prev_page": false
  }
}
```

Key differences: offset responses expose `total_items` and absolute page numbers; cursor responses expose only relative navigation (next/prev). Cursor responses deliberately omit total counts — they're expensive and semantically less meaningful ("there are N items after this cursor" is not useful to display).

**Q15. What are the HTTP Link header conventions for pagination?**
A: RFC 5988 (Web Linking) defines a standard `Link` response header for pagination that decouples pagination metadata from the response body — cleaner for clients that parse headers and bodies separately:

```
# Offset pagination
Link: <https://api.example.com/posts?page=5&limit=20>; rel="next",
      <https://api.example.com/posts?page=3&limit=20>; rel="prev",
      <https://api.example.com/posts?page=1&limit=20>; rel="first",
      <https://api.example.com/posts?page=53&limit=20>; rel="last"

# Cursor pagination
Link: <https://api.example.com/posts?after=eyJjcmVhdGVkX...&limit=20>; rel="next",
      <https://api.example.com/posts?before=eyJjcmVhdGVkX...&limit=20>; rel="prev"
```

GitHub's API uses this convention. The `rel` values `next`, `prev`, `first`, `last` are standardized. Clients parse the header and follow links rather than constructing URLs — this decouples the client from the URL structure and allows the server to change pagination implementation without breaking clients that follow links rather than construct them.

Whether to use Link headers vs. a response body envelope is a design choice: body envelopes are more discoverable and easier to parse in most client libraries; Link headers are more REST-pure and don't pollute the response body schema.

**Q16. How do you handle the `limit` parameter safely?**
A: The client controls `limit`, but the server must enforce bounds to prevent abuse:

```typescript
// TypeScript/NestJS example
@Get()
findAll(
  @Query('limit', new DefaultValuePipe(20), ParseIntPipe) rawLimit: number,
  @Query('after') after?: string,
) {
  const limit = Math.min(Math.max(rawLimit, 1), 100);  // clamp: 1–100
  return this.postsService.getPosts({ after, limit });
}
```

Without an upper bound, a client requesting `limit=100000` effectively bypasses pagination. Without a lower bound, `limit=0` returns nothing and confuses the cursor logic. A documented maximum (typically 100–200 for most APIs) with a default of 20–50 is the standard approach. Some APIs return an error on out-of-range limits; others silently clamp — clamping is more user-friendly; erroring is stricter for API contract enforcement.

## Section 7: When to Use Each

**Q17. When is offset pagination the right choice?**
A: Five scenarios where offset pagination is clearly better:

- **Arbitrary page navigation**: The UI shows "Page 5 of 53" with clickable page numbers. Users need to jump to page 47 directly. Cursor pagination cannot support this — cursors are sequential; there is no cursor for "page 47" without traversing pages 1–46 first.
- **Small, relatively static datasets**: A list of 200 product categories, a dropdown of 50 countries. The offset scan cost is negligible; the implementation simplicity of offset is valuable.
- **Dynamic sort order**: Users can sort the table by any column — name, price, date, status. Keyset pagination requires a cursor that encodes the sort column values. Supporting arbitrary sort columns with keyset means managing cursor formats for every sort combination. Offset handles any `ORDER BY` trivially.
- **Admin / back-office UIs**: Ops tools, CMS admin panels, data tables with search and filter. Users expect page numbers, per-page controls, "showing 61–80 of 1,053 results." The UX pattern assumes offset semantics.
- **Export / batch processing with stable data**: Exporting all records in batches where the data is not mutated during the export. Offset is consistent enough for this use case and simpler to implement correctly.

**Q18. When is cursor (keyset) pagination clearly better?**
A: Five scenarios where keyset pagination is unambiguously correct:

- **Infinite scroll / "load more"**: Mobile apps, social feeds, activity logs. Users scroll forward sequentially; no page jumping. Keyset is the only model that doesn't produce duplicates or skipped items as new content arrives.
- **High-traffic APIs with deep pagination**: A public API that serves millions of requests where clients frequently paginate deeply (pages 50+, 100+). Offset's O(offset) scan cost makes deep pages expensive enough to cause timeout errors under load. Keyset delivers consistent O(limit) performance at any depth.
- **Real-time or frequently-mutated data**: A notification feed, order history, audit log — data where rows are inserted, updated, or soft-deleted constantly. Offset produces duplicate/skipped items; keyset doesn't.
- **Compliance and correctness requirements**: Processing every record exactly once for billing, reconciliation, or audit. The drifting page problem in offset pagination means records can be skipped or double-processed. Keyset's stable position guarantees every record appears exactly once across the page sequence.
- **Large datasets approaching millions+ of rows**: At 10M+ rows, `OFFSET 5000000` scans 5 million index entries. Keyset at equivalent depth scans 20. The performance gap is not marginal — it is the difference between a 20ms response and a 30-second timeout.

**Q19. Is there a hybrid approach that combines the benefits of both?**
A: Yes — a few patterns:

**Keyset for traversal, offset for "page N" jump**: Implement keyset pagination for sequential next/prev navigation. For "jump to page N" requirements (rare in modern UIs), compute the cursor for page N by running a keyset query N times server-side on demand, or by materialising page-N cursors in a cache (expensive but possible for bounded datasets). This gives keyset's performance for 99% of requests and supports page jumping for the rare case.

**Time-window pagination**: Paginate by time windows rather than row count — "give me items from the last 24 hours, then the 24 hours before that." Each window is a natural cursor (a timestamp boundary). This is keyset-like without the sequential traversal constraint and naturally supports jumping to "last week."

**Seek method (numeric ID only)**: If the primary key is a sequential integer (`BIGSERIAL`, auto-increment), keyset pagination simplifies to `WHERE id < $last_id ORDER BY id DESC LIMIT 20`. No composite cursor needed. This is the simplest keyset case and the recommended starting point before adding complexity for multi-column sort.

## Section 8: Edge Cases and Advanced Patterns

**Q20. What happens when the sort column has many duplicate values and how do you handle it?**
A: If the cursor column has low cardinality (e.g., `status` with 5 distinct values, `category_id` with 20 values), many rows share the same cursor values. The composite cursor approach handles this correctly with a unique tiebreaker — always include `id` as the final sort column:

```sql
-- Sorting by status (low cardinality), tiebreaker by id
ORDER BY status ASC, id ASC
WHERE (status, id) > ($cursor_status, $cursor_id)

-- Sorting by score (float, high duplicate risk), tiebreaker by id  
ORDER BY score DESC, id DESC
WHERE (score, id) < ($cursor_score, $cursor_id)
```

The `id` column (assuming a unique integer or UUID) ensures no two rows have the same `(sort_col, id)` combination, making the cursor uniquely stable regardless of how many rows share the primary sort value.

**Q21. How do you implement the tuple comparison in databases that don't support it natively?**
A: PostgreSQL supports tuple comparison directly: `WHERE (created_at, id) < ($1, $2)`. MySQL (before 8.0) does not optimise tuple comparisons efficiently. The portable alternative uses an expanded OR form:

```sql
-- MySQL-compatible (also works in PostgreSQL)
WHERE created_at < $1
   OR (created_at = $1 AND id < $2)
```

For three columns (a three-level tiebreaker):
```sql
WHERE col_a < $1
   OR (col_a = $1 AND col_b < $2)
   OR (col_a = $1 AND col_b = $2 AND id < $3)
```

This is logically equivalent to the tuple comparison but more verbose. For MySQL, ensure the composite index `(col_a, col_b, id)` exists — the OR form still benefits from index lookups when the query planner handles it correctly. In practice, testing with `EXPLAIN` on the specific database version is essential — the query planner's handling of this OR pattern varies significantly.

**Q22. What happens to existing cursors when the sort order changes or columns are added?**
A: Cursors are tightly coupled to the current sort configuration. If you add a new sort column to the `ORDER BY` clause, existing cursors encoded without that column's value are invalid — decoding them produces an incomplete `WHERE` clause.

Handle this with cursor versioning:

```typescript
interface CursorV1 { v: 1; created_at: string; id: number }
interface CursorV2 { v: 2; score: number; created_at: string; id: number }

function decodeCursor(cursor: string): CursorV1 | CursorV2 {
  const payload = JSON.parse(Buffer.from(cursor, 'base64url').toString('utf8'));
  return payload; // version in payload.v
}

function buildWhereClause(cursor: CursorV1 | CursorV2) {
  if (cursor.v === 1) {
    return { sql: 'WHERE (created_at, id) < ($1, $2)', params: [cursor.created_at, cursor.id] };
  }
  if (cursor.v === 2) {
    return { sql: 'WHERE (score, created_at, id) < ($1, $2, $3)',
             params: [cursor.score, cursor.created_at, cursor.id] };
  }
}
```

On the transition: document cursor expiry (cursors older than 24 hours are invalid — require a fresh first-page request). API clients should handle `400 Bad Request` with `"error": "cursor_expired"` gracefully by restarting from page 1.

## Section 9: Scenario / System Design Questions

**Q23. "Your social media app has a home feed endpoint. Users scroll infinitely through posts sorted by `created_at DESC`. At 10M+ posts, page 500 takes 8 seconds. Diagnose and fix."**
A: The 8-second response at page 500 is the classic offset scan problem. Page 500 at 20 items per page is `OFFSET 9980` — the database scans 10,000 rows and returns 20. At 10M posts with concurrent users hitting deep pages, this creates full index scans competing for I/O.

Fix: migrate to keyset pagination. The migration path for an existing API:

```typescript
// Old: GET /feed?page=500&limit=20
// New: GET /feed?after=<cursor>&limit=20

// Migration step 1: add cursor output to existing response (non-breaking)
{
  "data": [...],
  "pagination": {
    "page": 500,          // keep for backward compat
    "next_cursor": "...", // add new field
  }
}

// Migration step 2: accept cursor input alongside page input
// If cursor present: use keyset; if page present: use offset (with deprecation warning)

// Migration step 3: deprecate page param; update clients
```

SQL after migration:
```sql
-- O(20) regardless of depth
SELECT * FROM posts
WHERE (created_at, id) < ($cursor_created_at, $cursor_id)
  AND user_id = ANY($followed_user_ids)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Index required
CREATE INDEX idx_posts_feed ON posts (created_at DESC, id DESC)
WHERE deleted_at IS NULL;
```

Result: all pages respond in ~5ms regardless of depth. The 8-second timeout disappears. Infinite scroll users who only navigate forward never experience the problem.

**Q24. "An admin panel shows all orders for a merchant, paginated with page numbers, sorting by any column (amount, date, status, customer name). Which pagination strategy, and how do you handle sort flexibility?"**
A: Offset pagination is correct here. Three requirements make keyset impractical:

- **Arbitrary page jumping**: The admin clicks "Page 47 of 200" — impossible with keyset without traversing pages 1–46 server-side.
- **Dynamic sort columns**: Sorting by `customer_name ASC` requires a cursor that encodes `customer_name` — but the admin can switch to `amount DESC` mid-session, invalidating all cursors. With offset, any `ORDER BY` clause works trivially.
- **Dataset stability**: Admin order lists are relatively stable (orders don't insert and delete continuously during a merchant's browsing session), so drifting pages are not a real concern.

Mitigations for offset's performance problem on large merchant histories:
- Add a `WHERE merchant_id = $1` filter index — significantly reduces the effective scan size to that merchant's orders only.
- Limit maximum `OFFSET`: If merchant has 500K orders, cap at `OFFSET 50000` (page 2500 at 20/page) with an explanatory message to use search/filter to narrow results.
- Cache `COUNT(*)` per merchant with a 60-second TTL — avoids the expensive count on every page.

**Q25. "You're building a data export job that processes all 5M user records in batches of 1,000. A colleague suggests `SELECT * FROM users LIMIT 1000 OFFSET N`. What's wrong with this and what do you use instead?"**
A: Three problems with offset-based batch processing:

- **Performance degrades to unusable**: The final batch at `OFFSET 4,999,000` scans 5M rows and returns 1,000. On a 5M-row table, the last batch can take minutes. Total scan cost for the full export is `O(N²)` — proportional to the square of the table size.
- **Data drift**: If users are inserted or deleted during the export (likely for a multi-hour job), rows are skipped or duplicated. A billing export that skips 1,000 users because of concurrent inserts is a serious business problem.
- **Lock amplification**: At high `OFFSET` values, the repeated large scans compete with normal traffic for buffer pool and I/O.

Use keyset pagination for batch processing:
```sql
-- Process by id (seeking, not scanning)
SELECT * FROM users
WHERE id > $last_processed_id
ORDER BY id ASC
LIMIT 1000;
```

This requires `id` to be sequential (auto-increment integer or ULID). Each batch does an index seek to `$last_processed_id` and reads exactly 1,000 rows — O(1) seek regardless of how far through the table you are. Total export is O(N) not O(N²). New users inserted with higher IDs during the export are included; deletions don't cause skips in already-processed ranges.

For tables without a sequential ID (UUID primary keys with random distribution), use a `created_at` + `uuid` composite cursor. UUIDs sort lexicographically — predictable but not insertion-ordered, so new rows may appear in the middle of the keyset traversal. For exports that must be consistent snapshots, use a database snapshot/transaction instead.

**Q26. "A notification API returns the user's last 100 notifications. The mobile app implements infinite scroll. New notifications arrive while the user scrolls. Design the pagination."**
A: This is the textbook case for cursor pagination. New notifications arrive at the top of the feed (sorted `created_at DESC, id DESC`). If the user is on page 3 of their notifications and 5 new ones arrive, offset would re-show the first 5 notifications on page 3 (duplication). Keyset does not — the cursor anchors to the last seen notification, and new arrivals above the cursor don't affect what comes below it.

Design:

```typescript
// First load (app opens)
GET /notifications?limit=20
// Response:
{
  "data": [
    { "id": 1050, "type": "like",    "created_at": "2025-01-15T14:00:00Z" },
    { "id": 1049, "type": "comment", "created_at": "2025-01-15T13:55:00Z" },
    ...
  ],
  "pagination": {
    "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNS0wMS0xNVQxMzozMDowMFoiLCJpZCI6MTAzMX0",
    "has_next": true,
    "newest_cursor": "eyJpZCI6MTA1MH0"   // encode id of newest item for "refresh" polling
  }
}

// User scrolls down — load more (forward cursor)
GET /notifications?after=<next_cursor>&limit=20

// User pulls to refresh — new items since last load (reverse query using newest_cursor)
GET /notifications?since=<newest_cursor>&limit=20
// Uses WHERE id > $newest_id ORDER BY id ASC to get new items
// Prepended to the top of the existing list on the client
```

The `since` parameter for pull-to-refresh is a separate pattern from the forward `after` cursor — it retrieves items newer than a reference point rather than older. The client maintains two cursors: `newest` (for refresh) and `oldest` (for load-more). This is the standard pattern used by Twitter/X, Instagram, and notification systems.

## Quick Reference: Offset vs Cursor

| Dimension                    | Offset Pagination                          | Cursor (Keyset) Pagination                    |
|---                           |---                                         |---                                            |
| SQL mechanism                | `LIMIT N OFFSET M`                         | `WHERE (col, id) < ($v1, $v2) LIMIT N`        |
| Database operation           | Scan-and-discard M rows                    | Index seek to cursor position                 |
| Deep page performance        | O(offset) — degrades linearly              | O(limit) — constant regardless of depth       |
| Consistency on mutation      | Pages drift on insert/delete               | Stable — cursor is value-anchored             |
| Arbitrary page jump          | ✅ Trivial (`page=47`)                      | ❌ Not supported                               |
| Total count                  | Possible (expensive `COUNT(*)`)            | Not meaningful; omit or approximate           |
| Sort flexibility             | ✅ Any `ORDER BY` works                     | ❌ Cursor tied to sort columns                 |
| Duplicate items on mutation  | ✅ Possible (insert before cursor)          | ❌ Never                                       |
| Skipped items on mutation    | ✅ Possible (delete before cursor)          | ❌ Never                                       |
| Previous page support        | ✅ Trivial (`page - 1`)                     | ⚠️  Requires reverse sort + subquery           |
| Implementation complexity    | Low                                        | Medium                                        |
| Right for                    | Admin UIs, sort flexibility, small data    | Feeds, large data, real-time, infinite scroll |

## The Core Mental Model

```
Offset = "Skip N rows from the start"
  The position is a count. Counts change when rows are inserted or deleted.
  Database must scan N rows every time to know where N is.
  Scales linearly with depth. Correct only on immutable data.

Keyset = "Start after this specific value"
  The position is a value. Values don't shift when other rows change.
  Database seeks directly to the value using an index.
  Scales constantly with depth. Correct on live data.

Decision rule:
  User can jump to arbitrary page?              → Offset  (UX requires it)
  Data changes while users paginate?            → Keyset  (correctness requires it)
  Dataset > ~100K rows and deep pages likely?   → Keyset  (performance requires it)
  Infinite scroll or "load more" UX?            → Keyset  (the only correct model)
  Sort changes dynamically per user request?    → Offset  (keyset cursor is sort-specific)
  Batch processing / export?                    → Keyset  (never use offset for this)

The cursor is:
  base64(JSON({ sort_col_1: val, sort_col_2: val, id: val }))
  Always include a unique tiebreaker (id)
  Always opaque to the client
  Version it if the sort schema may change

The composite index to create:
  CREATE INDEX ON table (sort_col DESC, id DESC);
  ← This is what makes keyset O(limit) instead of O(offset + limit)
```

**Tip for the interview:** Pagination questions at 5 YOE almost always contain a hidden performance or consistency trap — look for them. "Offset works fine for us" is the setup for "until page 500 starts timing out" or "until users noticed duplicate posts." The two sharpest interview signals: (1) explaining *why* offset degrades (the scan-and-discard, not just "it's slow") — because the database cannot skip to position N in a B-tree index; and (2) explaining *why* keyset is stable on mutations (value-anchored, not count-anchored). The strongest 5 YOE answer proposes keyset by default, mentions the one case where offset genuinely wins (arbitrary page jumping in admin UIs), and knows that batch processing should **never** use offset. Mentioning that `total_count` is expensive and that most UIs don't actually need it — just `has_next_page: true` — signals you've thought about the full cost model, not just the query mechanism.
