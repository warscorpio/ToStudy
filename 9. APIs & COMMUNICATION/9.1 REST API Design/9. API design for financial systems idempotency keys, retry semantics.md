# API Design for Financial Systems: Idempotency Keys, Retry Semantics — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does API design for financial systems require stricter guarantees than general-purpose APIs?**
A: General-purpose APIs can tolerate occasional duplicate operations — a duplicate "add to cart" or "send notification" is a minor nuisance. In financial systems, a duplicate operation has direct monetary consequences: a customer is double-charged, a transfer is executed twice, an account is debited without a corresponding credit. These are not bugs to fix in the next deploy — they are incidents requiring manual reconciliation, regulatory disclosure, and customer compensation.

Three properties make financial API design categorically different:

**Money is not idempotent by nature.** Running a charge twice on a credit card produces two charges. The API must impose idempotency on top of a non-idempotent underlying operation.

**Errors are expensive in both directions.** A false negative (thinking a charge failed when it succeeded) leads to a retry that double-charges. A false positive (thinking a charge succeeded when it failed) leads to fulfilling an order without collecting payment. Both are bad; neither is acceptable as a "normal error rate."

**The distributed systems failure modes are exactly the cases that matter most.** A network timeout between "charge succeeded at PSP" and "update order status to paid" is the case you most need to handle correctly — and it is exactly the case that is hardest to handle. Every design decision must account for this boundary.

**Q2. What is the fundamental problem that idempotency keys solve?**
A: The fundamental problem is that in a distributed system, the outcome of a network call is not binary — it is not "succeeded" or "failed." It is actually three-valued: "succeeded," "failed," and "unknown (timed out or network error before response arrived)." For a client that receives a timeout, the operation may have succeeded on the server before the timeout, or it may not have executed at all.

```
Client                          Server
  │                                │
  │── POST /charges ──────────────►│
  │                                │  Server processes charge
  │                                │  Charge succeeds at PSP
  │  ✗ Network timeout             │  Server about to respond
  │                                │
  │  Client doesn't know:          │
  │  Did the charge happen or not? │
```

Without an idempotency mechanism, the client has two bad choices:
- **Retry blindly**: risk double-charging if the first attempt succeeded.
- **Don't retry**: risk failing to charge if the first attempt failed.

With idempotency keys, the client retries safely — the server recognizes the retry as the same logical operation and returns the original outcome without executing the operation again.

## Section 2: Idempotency Keys

**Q3. What is an idempotency key and what are its design requirements?**
A: An idempotency key is a client-generated unique identifier that the client attaches to a request and includes on all retries of that same logical operation. The server uses it to detect and deduplicate retried requests.

Design requirements:

**Uniqueness per logical operation.** Each distinct financial operation must have a distinct key. A key must be unique within the client's namespace — a UUID v4 is the standard choice (122 bits of randomness makes collisions negligible). The key must be stable across retries: the client generates it once and reuses it on every retry of the same operation.

**Client-generated, not server-generated.** The client must generate the key before making the first attempt, because the key must be the same on retries — including retries where the first response was never received. If the server generated the key, the client would need to make a separate pre-request to get the key, which itself is not idempotent.

**Scoped to a time window.** Idempotency keys expire after a defined TTL (typically 24–72 hours). After expiry, reusing a key is treated as a new operation. This bounds the storage cost of the deduplication table. The TTL must be documented in the API contract — clients must not reuse keys after TTL expiry expecting deduplication.

**Tied to a specific operation and payload.** The key is bound to one operation. Sending the same key with a different payload (amount changed, different account) is a client bug, not a retry. The server must detect and reject this (see Q6).

**Q4. What is the canonical server-side implementation of idempotency keys?**
A: The server maintains a durable idempotency table with the following schema and lookup logic:

```sql
CREATE TABLE idempotency_keys (
  key              TEXT NOT NULL,
  client_id        TEXT NOT NULL,          -- scope keys per API client; prevent collisions
  request_hash     TEXT NOT NULL,          -- SHA-256 of normalized request body
  status           TEXT NOT NULL,          -- PROCESSING | COMPLETED | FAILED
  response_status  INT,                    -- HTTP status of the original response
  response_body    JSONB,                  -- original response body
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at       TIMESTAMPTZ NOT NULL,   -- now() + interval '72 hours'
  PRIMARY KEY (client_id, key)
);
CREATE INDEX ON idempotency_keys(expires_at);  -- for TTL cleanup job
```

Request handling algorithm:

```typescript
async function handleCharge(req: Request): Promise<Response> {
  const idempotencyKey = req.headers['idempotency-key'];
  const clientId = req.auth.clientId;

  if (!idempotencyKey) {
    return respond(400, { error: 'idempotency_key_required' });
  }

  const requestHash = sha256(canonicalize(req.body));

  return await db.transaction(async (tx) => {
    // Attempt to insert the key — atomic "first writer wins"
    const inserted = await tx.query(`
      INSERT INTO idempotency_keys
        (key, client_id, request_hash, status, expires_at)
      VALUES ($1, $2, $3, 'PROCESSING', now() + interval '72 hours')
      ON CONFLICT (client_id, key) DO NOTHING
      RETURNING key
    `, [idempotencyKey, clientId, requestHash]);

    if (inserted.rowCount === 0) {
      // Key already exists — this is a retry (or a conflict)
      const existing = await tx.query(`
        SELECT status, request_hash, response_status, response_body
        FROM idempotency_keys
        WHERE client_id = $1 AND key = $2
        FOR UPDATE
      `, [clientId, idempotencyKey]);

      const record = existing.rows[0];

      // Detect same key, different payload — client bug
      if (record.request_hash !== requestHash) {
        return respond(422, {
          error: 'idempotency_key_reuse',
          message: 'This idempotency key was used with a different request payload.'
        });
      }

      // Operation still in progress on another thread — concurrent retry
      if (record.status === 'PROCESSING') {
        return respond(409, {
          error: 'request_in_flight',
          message: 'A request with this idempotency key is already being processed.'
        });
      }

      // Operation already completed — return original response
      return respond(record.response_status, record.response_body);
    }

    // First request for this key — execute the operation
    try {
      const result = await executeCharge(req.body);
      const responseBody = buildSuccessResponse(result);

      await tx.query(`
        UPDATE idempotency_keys
        SET status = 'COMPLETED',
            response_status = 200,
            response_body = $1
        WHERE client_id = $2 AND key = $3
      `, [responseBody, clientId, idempotencyKey]);

      return respond(200, responseBody);

    } catch (err) {
      const errorBody = buildErrorResponse(err);
      const statusCode = classifyError(err);

      await tx.query(`
        UPDATE idempotency_keys
        SET status = 'FAILED',
            response_status = $1,
            response_body = $2
        WHERE client_id = $3 AND key = $4
      `, [statusCode, errorBody, clientId, idempotencyKey]);

      return respond(statusCode, errorBody);
    }
  });
}
```

The `ON CONFLICT DO NOTHING` + `FOR UPDATE` pattern is the atomicity guarantee: only one thread proceeds to execute the operation for a given key; all others read the result from the stored record.

**Q5. Should idempotency keys be required or optional?**
A: For any endpoint that executes a financial operation (create charge, initiate transfer, create refund, issue credit), idempotency keys should be **required** — returning `400 Bad Request` if absent. Making them optional creates a class of clients that don't send them, who will inevitably experience double-charge incidents.

The argument for optional: "clients that don't need to retry don't need to generate a key." The counter-argument: clients can't predict whether they'll need to retry — network failures are not scheduled. A client that "doesn't retry" will retry exactly when there's an incident (network degradation, client crash, mobile app killed mid-request).

Stripe, Braintree, and Adyen all require idempotency keys on all mutating financial endpoints. This is the industry standard.

For read-only endpoints (`GET /charges/ch_123`), idempotency keys are unnecessary — `GET` requests are inherently idempotent.

**Q6. How do you handle the "same key, different payload" case?**
A: A client sends idempotency key `key-abc` with `{"amount": 100}`. Later, a different thread (or a bug in client code) sends `key-abc` with `{"amount": 200}`. The server must not silently execute the second request as a retry — that would process a different financial operation under the guise of deduplication.

Detection: store a `request_hash` — a SHA-256 hash of the canonicalized request body — alongside the idempotency key. On every request, compute the hash of the incoming body and compare to the stored hash. If they differ, return `422 Unprocessable Entity`:

```json
{
  "error": "idempotency_key_reuse",
  "message": "Idempotency key 'key-abc' was previously used with a different request payload. Generate a new key for a different operation.",
  "hint": "Each unique operation requires a unique idempotency key."
}
```

Canonicalization matters for the hash: `{"amount":100,"currency":"USD"}` and `{"currency":"USD","amount":100}` are semantically identical but produce different hashes if field order is not normalized. Canonicalize by sorting keys alphabetically and normalizing whitespace before hashing.

**Q7. How do idempotency keys interact with database transactions?**
A: The idempotency key insert and the business operation must be in the same database transaction. If they are separate:

```
Scenario (wrong — separate transactions):
  1. Insert idempotency key (committed)
  2. Execute charge at PSP — succeeds
  3. Commit charge to DB — fails (DB error)
  → Key is marked PROCESSING but operation never completed
  → Retry sees PROCESSING and returns 409 forever
  → The charge DID happen at PSP but is never recorded
```

Correct approach: the key insert, business operation, and key status update are a single atomic transaction:

```
Scenario (correct — one transaction):
  1. BEGIN TRANSACTION
  2. INSERT idempotency key (status = PROCESSING)
  3. INSERT charge record to DB
  4. [After transaction commits]: call PSP (external; cannot be in DB transaction)
  5. UPDATE idempotency key (status = COMPLETED, response = {...})
  6. COMMIT

  If step 4 (PSP call) fails: rollback or mark FAILED in a separate transaction
  If step 6 fails: recovery job detects PROCESSING keys older than threshold
                   re-queries PSP with same PSP idempotency key
                   updates key status
```

The PSP call cannot be inside a database transaction (it's an external network call that may take seconds and holds DB locks). The pattern: persist intent before the PSP call; persist outcome after; use a recovery job for the crash-between-the-two case.

## Section 3: Retry Semantics

**Q8. What makes an operation safely retryable vs not retryable?**
A: An operation is safely retryable if executing it multiple times with the same parameters produces the same outcome as executing it once. In HTTP terms:

**Safe and idempotent by definition:**
- `GET` — read-only; no state change; retrying is always safe.
- `HEAD` — same as GET without body.
- `OPTIONS` — metadata query; no state change.

**Idempotent by HTTP spec (but verify in practice):**
- `PUT` — replacing a resource with a specific state; sending it twice should produce the same state. Safe to retry if the server is correctly implemented.
- `DELETE` — deleting a resource; the second delete should return `404` or succeed silently. Safe to retry if the server returns `404` rather than an error on re-delete of an already-deleted resource.

**Not idempotent without explicit design:**
- `POST` — creating a resource or triggering an action. Without an idempotency key, retrying `POST /charges` creates two charges. With an idempotency key, retrying is safe.
- `PATCH` — partial update; depends on semantics. `PATCH /account {"balance": 100}` is idempotent (sets balance to 100). `PATCH /account {"balance": {"$increment": 10}}` is not (each retry adds 10).

For financial systems, the practical rule: **any endpoint that moves money is not idempotent without an explicit idempotency mechanism**, regardless of HTTP method.

**Q9. What is the correct retry strategy for financial API calls?**
A: A retry strategy has four components: which errors to retry, how many times, how long to wait between retries, and how long to keep trying overall.

**Which errors to retry:**

```typescript
function isRetriable(error: ApiError): boolean {
  // Network-level errors (no response received) — always retry
  if (error.type === 'network_timeout' || error.type === 'connection_refused') {
    return true;
  }

  // Server errors — retry (server may have recovered)
  if (error.status === 503) return true;  // Service Unavailable
  if (error.status === 504) return true;  // Gateway Timeout
  if (error.status === 429) return true;  // Rate Limited (after Retry-After)

  // 500 Internal Server Error — retry cautiously
  // (may be a transient crash; idempotency key prevents double processing)
  if (error.status === 500) return true;

  // Client errors — do NOT retry (fix the request first)
  if (error.status >= 400 && error.status < 500) return false;
    // 400 Bad Request: fix the payload
    // 401 Unauthorized: refresh credentials
    // 403 Forbidden: don't retry; access won't change
    // 404 Not Found: resource doesn't exist
    // 409 Conflict: resolve the conflict first
    // 422 Validation Error: fix the input

  return false;
}
```

**Exponential backoff with jitter:**

```typescript
function retryWithBackoff(
  operation: () => Promise<Response>,
  idempotencyKey: string,
  options = { maxAttempts: 4, baseDelayMs: 500, maxDelayMs: 30000 }
): Promise<Response> {
  let attempt = 0;

  async function attempt(): Promise<Response> {
    try {
      return await operation();
    } catch (err) {
      if (attempt >= options.maxAttempts) throw err;
      if (!isRetriable(err)) throw err;

      const exponentialDelay = options.baseDelayMs * Math.pow(2, attempt);
      const jitter = Math.random() * exponentialDelay * 0.3;  // ±30% jitter
      const delay = Math.min(exponentialDelay + jitter, options.maxDelayMs);

      // Honor Retry-After header for 429 / 503
      const retryAfter = err.headers?.['retry-after'];
      const actualDelay = retryAfter
        ? Math.max(delay, parseInt(retryAfter) * 1000)
        : delay;

      await sleep(actualDelay);
      attempt++;
      return attempt();
    }
  }

  return attempt();
}
```

**Why jitter is mandatory for financial systems:** without jitter, all clients that received a `503` at the same moment retry at the same time — sending a synchronized wave of requests that overwhelms the recovering server (a retry storm). Jitter desynchronizes retries, spreading load. This is not a nice-to-have; it is the difference between a server that recovers and a server that crashes again under the retry load.

**Q10. What is the total delivery timeout and why does it matter more than retry count?**
A: Retry count alone does not bound the total time spent attempting a financial operation. `maxAttempts: 10` with exponential backoff could mean 30+ minutes of retrying. For financial operations, the total time budget is the correct control:

```typescript
interface RetryPolicy {
  deliveryTimeoutMs: number;   // total time budget for all attempts
  baseDelayMs:       number;   // first retry delay
  maxDelayMs:        number;   // cap on any single delay
  maxAttempts:       number;   // hard cap on retry count (secondary bound)
}

const CHARGE_RETRY_POLICY: RetryPolicy = {
  deliveryTimeoutMs: 30_000,   // 30 seconds total — user is waiting
  baseDelayMs:       200,
  maxDelayMs:        5_000,
  maxAttempts:       5
};

const PAYOUT_RETRY_POLICY: RetryPolicy = {
  deliveryTimeoutMs: 300_000,  // 5 minutes — async; user not waiting
  baseDelayMs:       1_000,
  maxDelayMs:        30_000,
  maxAttempts:       8
};
```

Different financial operations have different timeout budgets:
- **Synchronous charge** (user is at checkout): 30 seconds maximum — the user is staring at a loading spinner. After 30 seconds, show an error and let the user try again.
- **Async payout** (background transfer): 5 minutes — the user is not watching; retry more aggressively.
- **Batch reconciliation**: hours — low priority; retry indefinitely with long delays.

**Q11. What should a client do after exhausting all retries?**
A: After exhausting retries, the client has an unknown state — the operation may have succeeded (and the idempotency key exists on the server with a COMPLETED status) or failed (never executed). The client must not silently assume failure.

**Recommended pattern — the "verify before giving up" step:**

```typescript
async function chargeWithVerification(
  amount: number,
  customerId: string
): Promise<ChargeResult> {
  const idempotencyKey = generateIdempotencyKey();

  try {
    return await retryWithBackoff(
      () => apiClient.post('/charges', { amount, customerId }, {
        headers: { 'Idempotency-Key': idempotencyKey }
      }),
      idempotencyKey
    );
  } catch (finalError) {
    // Retries exhausted — verify the operation's status before giving up
    // The server may have succeeded on one of the attempts
    const existingCharge = await lookupByIdempotencyKey(idempotencyKey);

    if (existingCharge) {
      // Operation succeeded — at least one attempt went through
      return existingCharge;
    }

    // Confirmed failure — safe to surface error to user or trigger fallback
    throw new ChargeFailedError(finalError, idempotencyKey);
  }
}
```

The verification step queries the server using the idempotency key as a lookup: `GET /charges?idempotency_key=key-abc`. If a record exists, the operation succeeded — return it. If not, the operation genuinely failed and the error can be surfaced. This eliminates the "unknown outcome" state after retry exhaustion.

## Section 4: API Response Design

**Q12. What should a financial API response include beyond the operation result?**
A: Financial API responses should include enough metadata to support debugging, reconciliation, and audit without requiring a second request:

```json
{
  "id": "ch_01H9KX...",
  "object": "charge",
  "status": "succeeded",
  "amount": 10000,
  "currency": "usd",
  "customerId": "cust_abc",
  "description": "Order #98432",

  "idempotencyKey": "key-abc",        // echo back for client verification
  "requestId": "req_xyz456",          // server-generated trace ID; for support tickets

  "createdAt": "2024-07-23T14:03:00.042Z",
  "processedAt": "2024-07-23T14:03:00.891Z",

  "pspReference": "PSP-TX-789",       // PSP's own transaction ID; for reconciliation
  "pspResponse": {                    // raw PSP outcome; useful for debugging
    "authCode": "AUTH123",
    "avsResult": "Y",
    "cvvResult": "M"
  },

  "metadata": {                       // client-provided pass-through metadata
    "orderId": "order-98432",
    "platform": "web"
  }
}
```

Key fields and why they matter:

**`idempotencyKey` echoed back** — the client can verify that the response corresponds to the intended operation (not a cached response for a different key). Stripe does this.

**`requestId`** — a server-generated ID present in logs. When a customer calls support about a failed charge, the developer searches logs for `requestId: req_xyz456` to find the exact server-side trace.

**`pspReference`** — the payment processor's own transaction ID. Reconciliation matches this against the PSP's settlement file. Without it, correlating your internal records to the PSP's records requires matching by amount + timestamp, which is fragile.

**`processedAt` vs `createdAt`** — `createdAt` is when the API received the request; `processedAt` is when the PSP confirmed the charge. The gap between them is the PSP latency. Both are needed for accurate financial reporting.

**Q13. How do you design error responses for financial APIs?**
A: Financial API errors must be: machine-parseable (for client retry logic), human-readable (for developer debugging), actionable (what must the client do to resolve), and non-disclosing (no internal details).

```json
{
  "error": {
    "code":    "card_declined",
    "message": "The card was declined by the issuing bank.",
    "declineCode": "insufficient_funds",

    "requestId":      "req_xyz456",
    "idempotencyKey": "key-abc",

    "retryable":   false,
    "userMessage": "Your card was declined. Please try a different payment method.",

    "documentation": "https://api.example.com/docs/errors/card_declined"
  }
}
```

**`code`** — machine-readable error identifier. Clients switch on this, not on `message`. Keep codes stable across API versions — changing a code is a breaking change.

**`retryable`** — explicit signal to the client's retry logic. Removes ambiguity about whether to retry. `card_declined` is `false`; `upstream_timeout` is `true`.

**`userMessage`** — a safe, user-facing string that the client can display directly. Distinct from `message` (developer-facing, may contain technical detail). Never return `message` directly to end users.

**`declineCode`** — for card declines specifically, the PSP's decline reason code. Helps the application decide: show "try a different card" vs "call your bank" vs "card expired."

**No stack traces, no SQL, no internal IPs.** The `requestId` is the only link to internal details — support uses it to pull logs.

**Q14. How do you version financial APIs to avoid breaking clients?**
A: Financial API versioning is more conservative than general API versioning because clients often cannot upgrade quickly — they have their own release cycles, compliance reviews, and risk aversion around financial code changes.

**URL versioning for major versions** (`/v1/`, `/v2/`): explicit, easy to route at the gateway layer, and unambiguous about which contract applies. Clients pin to a version; the old version remains supported for an extended period (12–24 months minimum for financial APIs).

**Additive changes within a version (non-breaking):**
- Adding new optional fields to responses — always safe.
- Adding new optional request parameters — always safe.
- Adding new enum values — technically breaking (clients that `switch` on enums without a default case break). Document that clients must handle unknown values.
- Adding new endpoints — always safe.

**Breaking changes require a new major version:**
- Removing fields from responses.
- Renaming fields.
- Changing field types.
- Changing error codes that clients rely on for retry logic.
- Changing idempotency key semantics.

**Sunset headers for deprecation:**
```
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Jan 2026 00:00:00 GMT
Link: <https://api.example.com/v2/charges>; rel="successor-version"
```

The `Sunset` header (RFC 8594) tells clients when the old version will stop working. The `Link` header points to the replacement. Monitoring for `Deprecation: true` in responses is how well-written client SDKs warn developers about upcoming breaking changes.

## Section 5: Security and Compliance Concerns

**Q15. What authentication and authorization patterns are specific to financial APIs?**
A: Financial APIs require authentication patterns that go beyond "is this a valid JWT":

**API key scoping** — API keys must be scoped to specific operations. A key that can read charges must not be able to create charges or issue refunds. Scope claims: `charges:read`, `charges:write`, `refunds:write`, `payouts:write`. Issuing refunds requires a separate, more privileged scope than creating charges — an attacker who compromises a read key cannot issue refunds.

**Request signing** (for highest-value operations): beyond bearer tokens, require that the request body be signed with the client's private key. The server verifies the signature before processing. This prevents replay attacks (a captured request cannot be replayed) and proves the body has not been tampered with in transit. Stripe uses HMAC-SHA256 signing on webhooks; some financial institutions require request signing for all mutating operations.

**Mutual TLS (mTLS)**: both the client and server present certificates. The server verifies the client's certificate before processing any request. Used in bank-to-bank integrations, card network connections, and high-security financial APIs.

**IP allowlisting**: restrict API key usage to known IP ranges. A key leaked through a code repository can only be used from the attacker's network if they also have the allowlisted IP — significantly raises the bar for misuse.

**Q16. How do you prevent replay attacks on financial API calls?**
A: A replay attack captures a valid request and re-sends it later. For a financial API, replaying a `POST /charges` request executes a duplicate charge. Mitigations:

**Idempotency key expiry** — idempotency keys expire after 24–72 hours. A captured request replayed after expiry is treated as a new operation (no deduplication). This limits the replay window but doesn't eliminate it within the window.

**Request timestamps with tolerance** — require a `X-Timestamp` header containing the current Unix timestamp. The server rejects requests where the timestamp is more than N seconds (typically 300 seconds / 5 minutes) in the past or future:

```typescript
function validateTimestamp(req: Request): void {
  const timestamp = parseInt(req.headers['x-timestamp']);
  const now = Math.floor(Date.now() / 1000);

  if (Math.abs(now - timestamp) > 300) {
    throw new ApiError(400, 'request_expired',
      'Request timestamp is too old or in the future. Max skew: 300 seconds.');
  }
}
```

**Nonce + timestamp combination** — include both a `X-Timestamp` and a `X-Nonce` (a random unique value) in the request. The server stores seen nonces for the tolerance window (5 minutes). A request with a seen nonce is rejected even within the tolerance window. After the window, nonces expire and storage is bounded.

**HTTPS** — TLS prevents passive eavesdropping and replay in transit. Without TLS, request signing and nonces are the only protection. TLS is mandatory for all financial APIs — HTTP is not an option.

## Section 6: Webhooks and Event Delivery

**Q17. How should a financial API deliver payment events to clients via webhooks?**
A: Webhooks are the mechanism for pushing payment events (charge succeeded, refund processed, dispute opened) to client systems without the client polling. Financial webhook design:

**Signed payloads** — every webhook must be signed so the receiver can verify it originated from your system (not an attacker injecting fake payment events):

```typescript
// Sender: sign the webhook payload
function signWebhook(payload: string, secret: string): string {
  const timestamp = Math.floor(Date.now() / 1000);
  const signedContent = `${timestamp}.${payload}`;
  const signature = hmacSha256(secret, signedContent);
  return `t=${timestamp},v1=${signature}`;
}

// Header on outgoing webhook:
// Stripe-Signature: t=1721740980,v1=abc123def456...

// Receiver: verify the webhook signature
function verifyWebhook(
  payload: string,
  header: string,
  secret: string,
  toleranceSec = 300
): boolean {
  const { t, v1 } = parseSignatureHeader(header);
  const now = Math.floor(Date.now() / 1000);

  // Reject replayed webhooks
  if (Math.abs(now - parseInt(t)) > toleranceSec) return false;

  const expected = hmacSha256(secret, `${t}.${payload}`);
  return timingSafeEqual(v1, expected);  // prevent timing attacks
}
```

**At-least-once delivery with idempotent receivers** — webhook delivery is at-least-once (network failures cause retries from the sender). The receiver must be idempotent: processing the same `charge.succeeded` event twice must not credit the customer twice. Use the event `id` as an idempotency key on the receiver side:

```sql
INSERT INTO processed_events (event_id, event_type, processed_at)
VALUES ($1, $2, now())
ON CONFLICT (event_id) DO NOTHING;
-- If 0 rows inserted: this event was already processed; skip
```

**Return `200` immediately; process async** — webhook processors that do synchronous DB writes and business logic in the HTTP handler timeout. Return `200 OK` within 5 seconds, enqueue the event, process asynchronously:

```typescript
app.post('/webhooks/payments', async (req, res) => {
  if (!verifyWebhook(req.body, req.headers['stripe-signature'], WEBHOOK_SECRET)) {
    return res.status(400).send('Invalid signature');
  }

  // Acknowledge immediately
  res.status(200).send('OK');

  // Process asynchronously (don't await)
  queue.enqueue({ event: req.body, receivedAt: Date.now() });
});
```

If the handler takes > 30 seconds, the sender retries — producing a duplicate delivery. The fast acknowledgment + async processing pattern prevents this.

## Section 7: Scenario Questions

**Q18. "A client reports they were charged twice for the same order. They sent the same `Idempotency-Key` on both requests. How do you investigate?"**
A: This is the most serious financial incident type. Investigation:

**Step 1: Verify the idempotency key was actually the same.**
Pull the server's access logs for this client around the incident time. Check whether both requests carried identical `Idempotency-Key` values. Clients sometimes generate a new key on retry (a bug in their retry logic) while believing they're using the same key.

**Step 2: Check the idempotency table.**
```sql
SELECT key, client_id, status, request_hash, response_status,
       response_body, created_at
FROM idempotency_keys
WHERE client_id = 'client_abc'
  AND key = 'key-reported-by-client';
```
If only one row exists with `status = COMPLETED`, the server correctly deduplicated. The double charge must have a different cause (see step 4). If two rows exist (impossible with the `UNIQUE` constraint) — there is a database integrity bug.

**Step 3: Check the charges table.**
```sql
SELECT id, idempotency_key, customer_id, amount, status, created_at
FROM charges
WHERE customer_id = 'cust-xyz'
  AND created_at BETWEEN '2024-07-23T14:00:00Z' AND '2024-07-23T14:10:00Z';
```
If two charge records exist with the same idempotency key, the deduplication logic has a bug (race condition in the `ON CONFLICT` insert). If two records exist with different idempotency keys, the client sent two requests with different keys (client-side retry bug).

**Step 4: Check the PSP.**
Pull the PSP's transaction log for this customer. Did the PSP receive two separate charge requests with different PSP idempotency keys? If yes: the server executed the charge twice despite having the same API idempotency key — the PSP idempotency key generation is not tied to the API idempotency key correctly.

**Step 5: Immediate remediation.**
Refund the duplicate charge immediately (don't wait for root cause). Issue the refund, notify the customer, and escalate root cause analysis. Financial incidents require remediation before investigation is complete.

**Q19. "Your payment API has a 30-second timeout. A client's charge request gets a 504 after 29 seconds. The client retries with the same idempotency key. What happens on the retry, and what could go wrong?"**
A: The 504 means the API gateway timed out waiting for the backend. Two sub-scenarios:

**Sub-scenario A: The backend never received the request (gateway timeout before routing).**
The idempotency key was never inserted; the charge never executed. The retry arrives, inserts the key, executes normally. No issue.

**Sub-scenario B: The backend received the request and is still processing it.**
The backend is executing the PSP call (which can take 10–30 seconds for some PSPs). The idempotency key is in the database with `status = PROCESSING`. The 30-second gateway timeout fired before the backend responded.

The retry arrives. The backend looks up the idempotency key — finds it with `status = PROCESSING`. Correct implementation returns `409 Conflict` ("request in flight"). The client should not retry immediately; it should wait and poll or retry with exponential backoff.

**What can go wrong:**

*The `PROCESSING` record is never updated.* If the backend crashes after the PSP call succeeds but before updating the record to `COMPLETED`, the key remains `PROCESSING` indefinitely. The retry returns `409` forever. The customer was charged but the system doesn't know it.

Fix: the recovery job detects `PROCESSING` records older than a threshold (e.g., 2 minutes), re-queries the PSP using the stored PSP idempotency key, and updates the record based on the PSP's response.

*The gateway timeout is shorter than the backend timeout.* The gateway returns `504` after 30 seconds, but the backend continues processing for another 10 seconds and completes. The client retries, sees `PROCESSING`, waits, retries again — this time gets `COMPLETED` and the stored response. Correct behavior, but the client had a confusing intermediate `409`.

*The client does not retry with the same idempotency key.* A bug in the client generates a new key on retry. The second request executes as a new charge. Double charge occurs. This is a client bug, but the server can mitigate it by exposing a `GET /charges?idempotency_key={key}` endpoint that lets the client verify whether a previous attempt succeeded before retrying with a new key.

**Q20. "Design the idempotency system for a batch payment API that processes 10,000 transfers in a single request."**
A: A batch payment request creates a fundamentally different idempotency problem — there is one request but 10,000 operations. Three design options:

**Option 1: One idempotency key per batch (request-level).**
The entire batch is deduplicated as a unit. If the client retries the batch, the server either: (a) already completed all 10,000 transfers and returns the aggregate result, or (b) is still processing and returns `202 Accepted` with a status URL.

Limitation: if the batch partially fails (transfers 1–5,000 succeed, 5,001–10,000 fail due to a transient error), a retry re-submits all 10,000. The server must be smart enough to skip already-completed transfers within the batch.

```sql
CREATE TABLE batch_transfer_items (
  batch_id       TEXT NOT NULL,
  item_index     INT NOT NULL,         -- position in the batch
  transfer_id    TEXT,                 -- null until processed
  status         TEXT NOT NULL DEFAULT 'PENDING',
  error_code     TEXT,
  PRIMARY KEY (batch_id, item_index)
);
```

On retry: re-process only items with `status = PENDING` or `status = FAILED`. Skip `COMPLETED` items. Return the aggregate result including which items succeeded and which failed.

**Option 2: Client-supplied idempotency key per item.**
Each item in the batch carries its own idempotency key:
```json
{
  "transfers": [
    {"idempotencyKey": "xfer-key-1", "amount": 100, "to": "acct-1"},
    {"idempotencyKey": "xfer-key-2", "amount": 200, "to": "acct-2"},
    ...
  ]
}
```
Each item is deduplicated individually. The batch is processed idempotently because each transfer's idempotency key deduplicates at the item level. Partial batch retries are safe. The client can retry the full batch or just the failed items.

**Option 3: Server-assigned idempotency keys.**
The client submits the batch without item-level keys. The server assigns a deterministic key per item based on the batch idempotency key and item index: `item_key = hash(batch_key + ":" + item_index)`. Retrying the batch with the same batch key produces the same item keys, enabling item-level deduplication without the client tracking individual keys.

**Recommendation for production:** Option 2 (client-supplied per-item keys) is most flexible and gives the client the most control. Option 3 (server-assigned) is a good default when clients cannot easily generate per-item keys (simpler client SDK). Option 1 (request-level) is suitable when the batch is truly atomic — either all succeed or none do — which is rarely the case for transfers.

## Quick Reference

| Concern | Mechanism | Key detail |
|--- |--- |--- |
| Idempotency key | Client-generated UUID; sent on all retries | Required on all mutating endpoints; expires after 72h |
| Key storage | `(client_id, key)` unique in `idempotency_keys` table | `ON CONFLICT DO NOTHING` + `FOR UPDATE` for atomicity |
| Request hash | SHA-256 of canonicalized body | Detect same key, different payload → `422` |
| `PROCESSING` status | Key inserted but operation not yet complete | Recovery job resolves stale PROCESSING records via PSP re-query |
| Retry decision | Network error / 500 / 503 / 504 / 429 → retry | 4xx (except 429) → do not retry; fix the request |
| Exponential backoff | `delay = base * 2^attempt + jitter` | Jitter is mandatory to prevent retry storms |
| Total delivery timeout | Bound total retry duration, not just attempt count | Different budgets: 30s (sync charge), 5m (async payout) |
| Verify before giving up | `GET /charges?idempotency_key=key` after retry exhaustion | Confirms whether any attempt succeeded before surfacing error |
| Error `code` field | Stable machine-readable string | Clients switch on `code`; changing codes is a breaking change |
| `retryable` field | Boolean in error response | Explicit retry signal; removes ambiguity |
| Webhook signing | HMAC-SHA256 of `timestamp.payload` | Verify before processing; reject if timestamp > 5 min old |
| Webhook receiver | Idempotent on `event_id`; return 200 immediately | Process async; never do slow work in the webhook handler |
| API versioning | URL versioning (`/v1/`, `/v2/`); `Sunset` header | 12–24 month deprecation window for financial APIs |
| Request replay prevention | Timestamp tolerance (300s) + nonce | Limits replay window; nonces stored for tolerance window only |

**Tip for the interview:** Financial API questions at 5 YOE level are really distributed systems correctness questions wearing a payments costume. The core insight interviewers probe for: a timeout is not a failure — it is an unknown outcome, and all financial API design flows from handling that correctly. The details that separate senior answers: knowing that the idempotency key insert and business operation must be in the same database transaction (but the PSP call cannot be), explaining why jitter is mandatory for retry backoff (retry storms amplify incidents), and articulating the "verify before giving up" pattern after retry exhaustion (don't assume failure without confirming). On idempotency key misuse: knowing that the `request_hash` is what catches "same key, different payload" — and that without it, a client bug could silently execute the wrong operation under deduplication cover. If asked about webhooks, the three non-negotiables are: HMAC signature verification, idempotent processing keyed on `event_id`, and returning `200` immediately before doing any async work.
