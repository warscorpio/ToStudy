# REST Constraints: Uniform Interface, Statelessness, HATEOAS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is REST and where does it come from?**
A: REST (Representational State Transfer) is an architectural style for distributed hypermedia systems, defined by Roy Fielding in his 2000 doctoral dissertation. It is not a protocol, a standard, or a specification — it is a set of architectural constraints. A system that satisfies all constraints is called RESTful. A system that satisfies some but not all is not RESTful by definition, though the term is widely (and loosely) applied to any HTTP JSON API.

Fielding derived REST by observing the properties that made the World Wide Web scale to billions of users and identifying the architectural decisions that enabled those properties. REST is essentially the architectural model of the web, distilled into six constraints that any distributed hypermedia system can adopt to gain the same properties — scalability, simplicity, modifiability, visibility, portability, and reliability.

**Q2. What are the six REST constraints?**
A: Fielding defined six constraints. A system must satisfy all six to be truly RESTful:

**1. Client-Server:** Separation of UI concerns (client) from data storage concerns (server). The client and server evolve independently. The interface between them is the only coupling point.

**2. Statelessness:** Every request from client to server must contain all information necessary to understand the request. Session state is kept entirely on the client. The server holds no client session state between requests.

**3. Cacheability:** Responses must define themselves as cacheable or non-cacheable. Cacheable responses may be reused by clients and intermediaries, improving scalability and reducing latency.

**4. Layered System:** A client cannot tell whether it is connected directly to the end server or to an intermediary (proxy, load balancer, CDN, gateway). This enables transparent deployment of intermediaries for security, scalability, and caching.

**5. Code on Demand (optional):** Servers can extend client functionality by transferring executable code (JavaScript, applets). The only optional constraint — REST systems need not implement it.

**6. Uniform Interface:** The central constraint that distinguishes REST from other network-based styles. Defines a standardized way to interact with resources regardless of the specific service. Comprises four sub-constraints: resource identification, manipulation through representations, self-descriptive messages, and HATEOAS.

**Q3. Why does Fielding say most "REST APIs" are not actually RESTful?**
A: Fielding has publicly stated (in blog posts and interviews) that most APIs called "REST" violate multiple constraints, most commonly HATEOAS. His specific critique: an API that requires the client to construct URLs based on documentation (rather than following links embedded in responses) is not RESTful — it is an RPC-style API using HTTP as a transport.

The practical gap between Fielding's definition and industry usage is significant:
- Industry usage: any HTTP API that uses JSON, has resource-like URLs, and uses GET/POST/PUT/DELETE is called "REST."
- Fielding's definition: HATEOAS is non-negotiable. If the client must know in advance what URLs to call, the system is not REST.

For interview purposes: understand both definitions. Know what the six constraints are. Know what HATEOAS requires and why most APIs omit it. Be able to discuss the practical trade-offs of full REST compliance vs "REST-like" HTTP APIs.

## Section 2: Uniform Interface

**Q4. What is the Uniform Interface constraint and why is it central to REST?**
A: The Uniform Interface is the defining characteristic of REST — it's what makes REST different from RPC styles like SOAP, gRPC, or XML-RPC. It mandates that all interaction between client and server follows a standardized interface, regardless of the specific resources or operations involved.

The Uniform Interface has four sub-constraints:

**Resource Identification in Requests:** Resources are identified using stable identifiers (URIs in HTTP). The resource itself (a user, an order, a product) is conceptually separate from its representation (JSON, XML, HTML). The URI `GET /users/42` identifies a user; the response body is a representation of that user.

**Manipulation of Resources Through Representations:** When a client holds a representation of a resource (including metadata), it has enough information to modify or delete the resource. `GET /orders/123` returns the current state; that representation, sent back with `PUT /orders/123`, updates the resource.

**Self-Descriptive Messages:** Each message contains enough information to describe how to process it. HTTP Content-Type (`application/json`, `text/html`) tells the receiver how to parse the body. HTTP method (`GET`, `POST`, `PUT`, `DELETE`) conveys semantics. Status codes convey outcome. An intermediary (proxy, cache) can process the message correctly without knowing anything specific about the application.

**Hypermedia as the Engine of Application State (HATEOAS):** Clients navigate the application entirely by following links embedded in server responses — not by constructing URLs from external documentation. This is what makes REST truly "representational state transfer" — the client's state transitions are driven by hyperlinks in representations, exactly as a user navigates a website by clicking links.

**Q5. How does the Uniform Interface simplify the overall system at the cost of per-request efficiency?**
A: Fielding explicitly acknowledges this trade-off in his dissertation. The Uniform Interface is optimized for large-grained hypermedia data transfer — the kind of data the web serves. It is not optimized for fine-grained, performance-critical APIs.

**Simplification gains:**
- A client that understands HTTP can interact with any RESTful server without prior knowledge of that server's specific API.
- Intermediaries (CDNs, proxies, caches, gateways) understand the standardized interface and can process, cache, and transform messages without application-specific knowledge.
- Independent evolvability — server can change resource representations and URL structure as long as HATEOAS links remain valid; clients follow links, not hardcoded URLs.

**Efficiency cost:**
- HTTP's standardized headers, status codes, and verbs impose overhead compared to a purpose-built binary protocol (gRPC, Thrift).
- Resources may carry more data than a specific client needs (over-fetching) because the interface is generic, not client-specific.
- Multiple round trips may be needed to navigate a HATEOAS API before reaching the desired resource, whereas an RPC call accesses it directly.

This is why gRPC is often preferred for internal service-to-service communication (performance matters, clients are controlled) while REST-like HTTP APIs are used for public-facing APIs (clients are diverse, discoverability and simplicity matter).

**Q6. What are the correct semantics for HTTP methods in a RESTful API?**
A: HTTP methods carry standardized semantics that all RESTful APIs must respect:

**GET:** Retrieve a representation of a resource. Safe (no side effects) and idempotent (calling it N times has the same effect as calling it once). Responses are cacheable by default.

**POST:** Submit data to be processed by the resource. Not safe, not idempotent. Used for creating subordinate resources (`POST /orders` creates a new order), triggering processing actions, or any operation that doesn't fit PUT's semantics. Response may not be cacheable.

**PUT:** Replace the entire resource with the submitted representation. Not safe, but idempotent — `PUT /orders/123` with the same body N times results in the same resource state. The client supplies the full representation; the server replaces the resource with it.

**PATCH:** Partial update — apply a partial modification to a resource. Not safe. Idempotency depends on the patch semantics (a patch that sets a field to a value is idempotent; a patch that increments a counter is not). `Content-Type: application/merge-patch+json` or `application/json-patch+json` are standard formats.

**DELETE:** Remove the resource identified by the URI. Not safe, but idempotent — deleting an already-deleted resource should return 404 or 204 (both are acceptable), not an error that changes behavior.

**HEAD:** Same as GET but returns only the response headers, not the body. Used to check resource existence, get metadata (e.g., `Content-Length` for download size estimation), or check cache freshness.

**OPTIONS:** Describe the communication options for the target resource. Used by browsers for CORS preflight requests. Returns `Allow` header listing supported methods.

**Q7. What makes a resource design RESTful vs RPC-like?**
A: REST resources are nouns; RPC endpoints are verbs. The distinction:

**RPC-like (action-oriented, non-RESTful):**
```
POST /getUser?id=42
POST /createOrder
POST /cancelOrder?id=123
POST /sendInvoice?orderId=123
POST /calculateShippingCost
```
Every operation is a POST to a verb-named endpoint. HTTP is just a transport — the method carries no semantics.

**RESTful (resource-oriented):**
```
GET    /users/42                   → retrieve user 42
POST   /orders                     → create a new order
DELETE /orders/123                 → cancel order 123 (or: PATCH /orders/123 { status: cancelled })
POST   /orders/123/invoices        → send invoice for order 123 (creates the invoice resource)
GET    /shipping-rates?origin=...  → calculate shipping cost (idempotent read, GET is correct)
```

**Where it gets nuanced:** Not all operations map cleanly to CRUD on resources. Business actions (approve, reject, publish, archive) often feel more like verbs than nouns. Common approaches:
- Model the action's result as a resource: `POST /orders/123/cancellations` creates a cancellation resource.
- Use a sub-resource for the state: `PUT /orders/123/status { "status": "cancelled" }`.
- Accept pragmatic exceptions: `POST /orders/123/cancel` is widely used in practice even though it's not strictly RESTful. The alternative (sub-resource) adds complexity with marginal benefit.

## Section 3: Statelessness

**Q8. What does the statelessness constraint require exactly?**
A: The statelessness constraint requires that every client request must contain all information necessary for the server to process it, without relying on any stored context from prior requests. The server must not store session state between requests on behalf of any client.

Concretely:
- No server-side sessions. A user's authentication state, shopping cart contents, or multi-step workflow progress must not be stored in server memory keyed by a session ID.
- Every request is self-contained. If a resource requires authentication, the credentials or token must be in every request — not established in a "login" request and implicitly remembered for subsequent requests.
- The server treats each request as if it arrived from a fresh connection from an anonymous client.

**Example — stateful (violates REST):**
```
Request 1: POST /login { username, password }
Server stores: session["user_id"] = 42, session["cart"] = [...] in Redis
Response: Set-Cookie: session_id=abc123

Request 2: GET /checkout
Cookie: session_id=abc123
Server looks up session: user_id=42, cart=[...]
→ Server-side session state required to process request 2.
```

**Example — stateless (compliant with REST):**
```
Request 1: POST /auth/token { username, password }
Response: { "access_token": "eyJhbGciOiJSUzI1NiJ9..." }

Request 2: GET /checkout
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
→ JWT contains user_id, roles, expiry. Server validates signature and extracts
  user context. No server-side session needed.
```

**Q9. What are the benefits of the statelessness constraint?**
A: Statelessness directly enables several critical system properties:

**Horizontal scalability:** Any server instance can handle any request — there is no session affinity requirement. A load balancer can route each request to any available instance without regard for which instance handled the previous request. Adding instances immediately increases capacity.

**Fault tolerance:** If a server instance crashes, no client session data is lost (it was never stored there). The client's next request goes to any surviving instance and is processed normally.

**Visibility for monitoring:** Every request contains its complete context. An intermediary (proxy, firewall, monitoring tool) can understand each request in isolation — it doesn't need to correlate across a session to know what a request is doing.

**Reliability:** Requests can be retried safely (if idempotent) by the client without risk of server-side state becoming inconsistent, because the server holds no state to become inconsistent.

**Simplified server design:** No session management, no session expiry, no session storage system to maintain, no session clustering for multi-instance deployments.

**Q10. What are the costs of statelessness, and how do real systems address them?**
A: Statelessness transfers state burden from the server to the client (or to each request), which has costs:

**Increased per-request payload:** Authentication tokens, user context, and request metadata must be sent with every request. A JWT can be 500–2,000 bytes; multiplied across millions of requests, this is significant bandwidth overhead compared to a 16-byte session ID cookie.

**Repeated authentication overhead:** With cookie-based sessions, authentication cost is paid once. With JWT Bearer tokens, the server validates the token signature (cryptographic operation) on every request. Mitigated by caching public keys and using fast algorithms (RS256 with cached key material).

**Client state management complexity:** The client must manage its own state — storing tokens, refreshing them before expiry, managing multi-step form state, shopping cart contents. This complexity is moved to the client (browser localStorage, mobile keychain, SPA state management).

**How real systems address these costs:**
- **JWTs** for stateless authentication — cryptographically signed, self-contained tokens validated server-side without a session lookup.
- **Short-lived access tokens + refresh tokens** — access tokens (stateless, 15-minute TTL) + refresh tokens (long-lived, stored in an httpOnly cookie or secure storage, exchanged for new access tokens).
- **Client-side state for multi-step flows** — wizard state stored in browser storage or encoded in the URL; each "step" request includes the accumulated state.
- **Shared external state for genuinely shared data** — distributed caches (Redis) or databases store data shared across requests (e.g., rate limit counters, shopping carts that must be accessible from multiple devices). This is not server session state — it's persisted data, accessible to any server instance.

**Q11. Is server-side caching a violation of the statelessness constraint?**
A: No — this is a common misconception. The statelessness constraint specifically refers to session state — state that is specific to a client's interaction history. Server-side caching (Redis, Memcached, application-level cache) stores data that is not client-specific and is derived from durable state (database records):

- **Session state (violates statelessness):** `session["cart_items"] = [...]` — specific to one client's interaction. If the session store is unavailable, the client's in-progress interaction is broken.
- **Cached data (does not violate statelessness):** `cache["product:42"] = {...}` — a cached representation of a resource that exists in the database. If the cache is unavailable, the server fetches from the database. The cache is an optimization, not a requirement for correctness.

The distinction: if removing the server-side store would break client interactions (because the server can no longer reconstruct the client's context), it's session state. If removing it would only increase load on the database (the data is still there), it's a cache — and caching is explicitly one of the six REST constraints (constraint #3, Cacheability).

## Section 4: HATEOAS

**Q12. What is HATEOAS and what problem does it solve?**
A: HATEOAS (Hypermedia As The Engine Of Application State) is the fourth sub-constraint of the Uniform Interface. It requires that a RESTful client interact with the server entirely through hypermedia links provided dynamically by the server — the client needs no prior knowledge of application URLs, no out-of-band documentation to discover available operations.

**The problem it solves — URL coupling:**
In a typical HTTP API (non-HATEOAS), the client must know in advance what URLs to call:
```
"To cancel an order, call DELETE /orders/{order_id}.
To get an invoice, call GET /orders/{order_id}/invoices."
```
This knowledge is encoded in client code and documentation. When the server changes a URL structure (`/orders/{id}` becomes `/v2/orders/{id}`), all clients must update. The server and client are coupled through URL structure.

**The solution — navigation through links:**
A HATEOAS response includes links representing valid transitions from the current state:
```json
{
  "order_id": "ord-123",
  "status": "CONFIRMED",
  "total_cents": 5999,
  "_links": {
    "self":    { "href": "/orders/ord-123", "method": "GET" },
    "cancel":  { "href": "/orders/ord-123/cancellations", "method": "POST" },
    "invoice": { "href": "/orders/ord-123/invoices", "method": "GET" },
    "items":   { "href": "/orders/ord-123/items", "method": "GET" }
  }
}
```
The client follows the `cancel` link to cancel the order — it never hardcodes the URL. If the server changes the cancellation URL, the client receives the new URL in the next response automatically. The client only needs to know the entry point URL (e.g., `GET /` returns all available starting links).

**Q13. How does HATEOAS enable independent server evolution?**
A: HATEOAS decouples the client from the server's URL structure — the most powerful form of loose coupling in distributed systems. Consequences:

**Server can change URLs without breaking clients:** The server changes `POST /orders/123/cancellations` to `POST /v2/cancel/orders/123`. The client, which navigates by following the `cancel` link, receives the new URL in the next response. Zero client change required.

**Server controls available actions:** The server only includes links for operations that are currently valid. A `CONFIRMED` order has a `cancel` link; a `SHIPPED` order does not. The client's UI can render buttons only for valid operations without implementing business rules:
```json
// Order in CONFIRMED state
"_links": { "cancel": {...}, "invoice": {...} }

// Order in SHIPPED state — no cancel link
"_links": { "track": {...}, "invoice": {...} }
```

**Discovery-driven development:** A new client can discover the full API by starting at the entry point and following links — like a web browser exploring a website. No API documentation required for the basic structure.

**Q14. What are the standard hypermedia formats for HATEOAS?**
A: Several media types have been standardized for expressing hypermedia links in REST APIs:

**HAL (Hypertext Application Language) — `application/hal+json`:**
The most widely adopted. Reserves `_links` for link objects and `_embedded` for inline resource representations:
```json
{
  "order_id": "ord-123",
  "status": "CONFIRMED",
  "_links": {
    "self":   { "href": "/orders/ord-123" },
    "cancel": { "href": "/orders/ord-123/cancellations" }
  },
  "_embedded": {
    "items": [
      { "product_id": "prod-1", "quantity": 2,
        "_links": { "self": { "href": "/products/prod-1" } } }
    ]
  }
}
```

**JSON:API — `application/vnd.api+json`:**
More opinionated structure with `data`, `relationships`, and `links` sections. Strong conventions for pagination, filtering, and sparse fieldsets:
```json
{
  "data": {
    "type": "orders",
    "id": "ord-123",
    "attributes": { "status": "CONFIRMED", "total_cents": 5999 },
    "relationships": {
      "items": { "links": { "related": "/orders/ord-123/items" } }
    },
    "links": { "self": "/orders/ord-123" }
  }
}
```

**Siren — `application/vnd.siren+json`:**
Includes `actions` (forms) in addition to links — models both navigational links and state-changing operations with their required fields:
```json
{
  "class": ["order"],
  "properties": { "order_id": "ord-123", "status": "CONFIRMED" },
  "actions": [{
    "name": "cancel-order",
    "method": "POST",
    "href": "/orders/ord-123/cancellations",
    "fields": [{ "name": "reason", "type": "text" }]
  }],
  "links": [{ "rel": ["self"], "href": "/orders/ord-123" }]
}
```

**JSON-LD — `application/ld+json`:**
Linked Data format used by schema.org and semantic web applications. Links resources to vocabularies that define their meaning. More complex but semantically richer.

**Q15. Why do most production REST APIs not implement HATEOAS?**
A: HATEOAS is the most commonly violated REST constraint in industry — for pragmatic reasons:

**Client-side complexity:** A browser or mobile app navigating links dynamically must implement a generic link-following engine rather than hardcoded API calls. This is complex to build, debug, and maintain. Most client teams find it simpler to encode API knowledge directly in the client.

**Documentation tooling gap:** API documentation tools (Swagger/OpenAPI) are designed around the assumption that clients know URLs and schemas in advance. HATEOAS APIs are harder to document, explore, and test with standard tooling. OpenAPI has limited HATEOAS support.

**Performance overhead:** HATEOAS responses are larger (links add payload). Clients must make a request to discover links before they can act — additional round trips compared to knowing the URL in advance. For mobile clients on slow networks, this is a real concern.

**Versioning as an alternative:** Most teams handle the "URL coupling" problem that HATEOAS solves via explicit API versioning (`/v1/`, `/v2/`). Breaking changes are introduced in a new version; old clients continue using the old version. Simpler to implement and document than HATEOAS, though it requires coordinated deprecation.

**When HATEOAS makes sense:** Large public APIs with diverse, unknown clients that should be able to discover functionality programmatically. Hypermedia-native applications (publishing platforms, content management systems) where the document model already includes links. Long-lived APIs where server-side evolvability is a first-class concern.

## Section 5: Practical REST Design

**Q16. What HTTP status codes should a RESTful API use and what do they mean?**
A: Status codes are part of the self-descriptive messages sub-constraint — they communicate the outcome of a request without requiring clients to parse the body:

**2xx — Success:**
- `200 OK` — request succeeded, response body contains result. Default for GET, PUT, PATCH responses.
- `201 Created` — resource created successfully. Include `Location` header pointing to the new resource URI. Used for successful POST that creates a resource.
- `202 Accepted` — request accepted for async processing. The resource doesn't exist yet; a `Location` or `Content-Location` header may point to a status endpoint.
- `204 No Content` — success with no response body. Used for DELETE and PUT/PATCH when the server doesn't return the updated resource.

**3xx — Redirection:**
- `301 Moved Permanently` — resource has moved to the URI in `Location`. Clients should update their bookmark. Cacheable.
- `302 Found` — temporary redirect. Client should use the original URI for future requests.
- `304 Not Modified` — response to a conditional GET (If-None-Match / If-Modified-Since). Client's cached copy is still valid. No body.

**4xx — Client Errors:**
- `400 Bad Request` — malformed request syntax, invalid fields, validation failure. Include error details in the body.
- `401 Unauthorized` — authentication required or invalid credentials. Client should authenticate and retry.
- `403 Forbidden` — authenticated but not authorized. The client's identity is known but lacks permission. Do not expose whether the resource exists if existence itself is sensitive.
- `404 Not Found` — resource doesn't exist (or server deliberately obscures existence for security).
- `405 Method Not Allowed` — HTTP method not supported for this resource. Include `Allow` header listing supported methods.
- `409 Conflict` — conflict with current resource state (duplicate resource, optimistic locking failure, version mismatch).
- `410 Gone` — resource existed but was permanently deleted. Unlike 404, implies it will never come back.
- `422 Unprocessable Entity` — syntactically correct request but semantically invalid (business rule violation, invalid state transition). Preferred over 400 for semantic validation errors.
- `429 Too Many Requests` — rate limit exceeded. Include `Retry-After` header.

**5xx — Server Errors:**
- `500 Internal Server Error` — unexpected server-side failure. Don't expose stack traces.
- `502 Bad Gateway` — upstream service failure (the server acting as gateway received invalid response from upstream).
- `503 Service Unavailable` — server temporarily unable to handle requests. Include `Retry-After` header if known.

**Q17. How should a RESTful API handle pagination?**
A: Pagination is a read concern — several patterns exist, each with different properties:

**Offset-based pagination (simplest):**
```
GET /orders?limit=20&offset=40
Response: {
  "data": [...],
  "meta": { "total": 1543, "limit": 20, "offset": 40 },
  "_links": {
    "self":  { "href": "/orders?limit=20&offset=40" },
    "next":  { "href": "/orders?limit=20&offset=60" },
    "prev":  { "href": "/orders?limit=20&offset=20" },
    "first": { "href": "/orders?limit=20&offset=0" },
    "last":  { "href": "/orders?limit=20&offset=1540" }
  }
}
```
Simple to implement and understand. Problem: if records are inserted or deleted between page requests, the client may see duplicates or skip records ("page drift"). Total count query is expensive on large datasets.

**Cursor-based pagination (preferred for large datasets):**
```
GET /orders?limit=20&cursor=eyJpZCI6IjEyMyJ9
Response: {
  "data": [...],
  "_links": {
    "next": { "href": "/orders?limit=20&cursor=eyJpZCI6IjE0MyJ9" },
    "prev": { "href": "/orders?limit=20&cursor=eyJpZCI6IjEwMyJ9" }
  }
}
```
Cursor is an opaque, base64-encoded pointer (typically `{ "id": "last_seen_id" }` or `{ "created_at": "timestamp", "id": "tiebreak_id" }`). No page drift — the cursor anchors to a specific position. No total count. Cannot jump to arbitrary pages.

**HATEOAS pagination links:**
Both patterns above include `_links` with `next` and `prev` — this is HATEOAS in action. The client follows the `next` link to get the next page; it doesn't construct the pagination URL itself.

**Q18. How do you design error responses in a RESTful API?**
A: Error responses are part of self-descriptive messages — the body must explain what went wrong clearly enough for the client to handle it programmatically. The RFC 9457 (Problem Details for HTTP APIs) standard provides a widely adopted structure:

```json
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "The request body contains invalid field values.",
  "instance": "/orders/requests/req-uuid-123",
  "errors": [
    {
      "field": "shipping_address.postal_code",
      "code": "INVALID_FORMAT",
      "message": "Postal code must be 6 digits for IN country code."
    },
    {
      "field": "line_items[0].quantity",
      "code": "OUT_OF_RANGE",
      "message": "Quantity must be between 1 and 100."
    }
  ]
}
```

**Key fields:**
- `type` — a URI that identifies the error type (not necessarily dereferenceable, but unique and stable).
- `title` — human-readable summary of the error type. Same for all instances of this error type.
- `status` — the HTTP status code as an integer (repeated for clients that process the body without headers).
- `detail` — human-readable explanation specific to this occurrence.
- `instance` — URI identifying this specific error occurrence (useful for support correlation).
- `errors` — extension field for multiple validation errors.

**What to avoid:**
- Returning `200 OK` with an error in the body (extremely common anti-pattern in older APIs). Breaks HTTP semantics — caches may cache the "success" response, monitoring tools won't alert on 200s.
- Exposing stack traces, internal error codes, or database error messages in production responses — security risk.
- Generic `400 Bad Request` for everything — prevents clients from handling errors programmatically.

## Section 6: Trade-offs & Decision-Making

**Q19. When should you use REST vs gRPC vs GraphQL?**
A: Each style optimizes for different concerns:

**REST (HTTP + JSON):**
- Best for: public-facing APIs, APIs with diverse unknown clients, CRUD operations on resources, systems where HTTP caching is a first-class concern.
- Strengths: universal client support (any HTTP client works), human-readable payloads, native browser support, excellent tooling (OpenAPI, Postman, Swagger UI), HTTP caching works transparently.
- Weaknesses: over-fetching (response includes fields the client doesn't need), under-fetching (multiple round trips to aggregate data from related resources), no strong typing contract, binary encoding not supported natively.

**gRPC (HTTP/2 + Protobuf):**
- Best for: internal service-to-service communication, high-throughput low-latency APIs, strongly typed contracts, streaming (bidirectional, server-streaming, client-streaming).
- Strengths: binary encoding (smaller, faster than JSON), strong typing with generated client/server stubs, native streaming, excellent performance.
- Weaknesses: not human-readable (binary), limited browser support (requires gRPC-Web proxy), harder to debug without tooling, more complex setup than REST.

**GraphQL:**
- Best for: APIs serving diverse clients with different data needs (mobile vs web vs third-party), aggregation layers over multiple backend services, flexible query APIs where clients specify exactly what data they need.
- Strengths: client specifies exact data shape (no over/under-fetching), single endpoint, introspection (self-documenting), natural fit for graph-shaped data.
- Weaknesses: caching is complex (queries are POST, vary by body not URL), N+1 query problem (requires DataLoader or similar), complex authorization (field-level permissions), higher server complexity.

**Decision matrix:**
- Public API, unknown clients → REST.
- Internal microservices, performance-critical → gRPC.
- Frontend-driven, diverse client data needs → GraphQL.
- Mobile with limited bandwidth, many data types → GraphQL.
- Streaming, bidirectional communication → gRPC.

**Q20. How does API versioning work in practice, and which strategy do you recommend?**
A: API versioning is the practical alternative to HATEOAS for managing breaking changes:

**URL versioning (`/v1/orders`, `/v2/orders`):**
- Most visible — version is in the URL.
- Easy to route at the API gateway level.
- Violates REST purity (the URL should identify a resource, not a version of an API).
- Most common in practice. Widely understood by clients and developers.

**Header versioning (`API-Version: 2` or `Accept: application/vnd.myapi.v2+json`):**
- Cleaner URLs — the resource URL is stable.
- Harder to test in a browser (must set headers).
- `Accept` header versioning is more RESTful (uses content negotiation).
- Less commonly adopted despite being more architecturally correct.

**Query parameter versioning (`/orders?version=2`):**
- Simple to implement.
- Query parameters should represent filter/sort criteria, not API versions — semantic mismatch.
- Cacheable (different version = different URL from caching perspective).
- Rarely recommended.

**Recommendation for production systems:**
URL versioning for public APIs — it's explicit, widely understood, easy to route, and simple to document. Major version in URL (`/v1/`, `/v2/`); minor version changes (backward-compatible additions) without a URL change. Maintain old versions for a published deprecation window (6–12 months for public APIs). Use `Sunset` and `Deprecation` HTTP headers to signal deprecation to clients.

**Q21. What is the "REST maturity model" and what level do most production APIs achieve?**
A: The Richardson Maturity Model (Leonard Richardson, 2008) describes four levels of REST maturity:

**Level 0 — The Swamp of POX (Plain Old XML):**
HTTP as a transport tunnel. One endpoint, one method (POST), all operations encoded in the request body. Classic SOAP/XML-RPC pattern.
```
POST /orderService
{ "action": "getOrder", "orderId": "123" }
```

**Level 1 — Resources:**
Individual resources have their own URIs. Multiple endpoints, but methods are not used semantically (typically POST for everything).
```
POST /orders/123  (to get order 123)
POST /orders/123  (to cancel order 123)
```

**Level 2 — HTTP Verbs:**
HTTP methods used according to their semantics. Different methods for different operations on the same resource. Status codes used correctly.
```
GET    /orders/123   → retrieve
DELETE /orders/123   → cancel
POST   /orders       → create
```
**Most production "REST" APIs operate at Level 2.** This is often called "REST" in practice, though Fielding would disagree.

**Level 3 — Hypermedia Controls (HATEOAS):**
Responses include hypermedia links driving client navigation. Clients don't need out-of-band documentation to discover operations.
```json
GET /orders/123
{
  "order_id": "123",
  "_links": {
    "self":   { "href": "/orders/123" },
    "cancel": { "href": "/orders/123/cancellations" },
    "items":  { "href": "/orders/123/items" }
  }
}
```
Few production APIs fully implement Level 3. Those that do are typically large public platforms (GitHub's REST API has some HATEOAS elements; the Paypal REST API implemented HAL).

**For interview purposes:** Know all four levels. When asked about REST, most interviewers mean Level 2. Be ready to discuss why Level 3 (HATEOAS) is the theoretically correct definition and why most APIs stop at Level 2.

**Q22. "Design the REST API for an order management system. Define the resource model, endpoints, and HTTP methods."**

**Resource hierarchy:**
```

POST   /orders                       Create a new order → 201 + Location: /orders/ord-123

GET    /orders/{id}/invoices         Get invoice (generated on demand or stored)
GET    /orders/{id}/shipments        Get shipment tracking info
```

**Q23. "A colleague proposes using POST for all operations because 'it's simpler.' What are the concrete problems with this approach?"**
A: The "all-POST" approach is Level 0 REST (the Swamp of POX). Concrete problems:

**Caching breaks:** GET requests are cacheable by HTTP intermediaries (CDNs, browsers, proxies). POST requests are not cacheable by default. An `GET /products/42` response can be cached by CloudFront; a `POST /getProduct { id: 42 }` cannot. Every client fetches from the origin — no CDN offload, no browser cache, higher latency and server load for read-heavy APIs.

**Idempotency and retries are unsafe:** GET and PUT are idempotent — safe to retry on network failure without side effects. All-POST means every retry risks a duplicate operation. Middleware (load balancers, service meshes) knows GET is safe to retry automatically; POST is not — it must not auto-retry.

**Semantic confusion:** HTTP method conveys intent to every intermediary in the network. A POST to `/users/42` doesn't tell a proxy, firewall, or monitoring tool whether this is a read, create, update, or delete. Standard tooling (API gateways, WAFs, rate limiters) cannot apply method-based rules.

**Monitoring and observability gaps:** Log analysis, metrics dashboards, and APM tools group requests by method and path. `GET /orders 200 OK` (read) and `DELETE /orders/123 204 No Content` (delete) are clearly distinct. `POST /orders 200 OK` is ambiguous — is this a successful create, a successful read, or a successful delete?

**Tooling incompatibility:** OpenAPI/Swagger, Postman collections, API testing tools, and documentation generators are built around REST conventions. An all-POST API requires custom tooling or significant workarounds.

**Q24. "Your REST API is being called by a mobile client that needs only a subset of fields from a large resource to minimize bandwidth. How do you handle this while remaining RESTful?"**
A: Several approaches, with different trade-offs:

**Sparse fieldsets (query parameter, REST-compatible):**
```
GET /orders/ord-123?fields=order_id,status,total_cents
Response: { "order_id": "ord-123", "status": "CONFIRMED", "total_cents": 5999 }
```
Simple to implement. REST-compatible (GET with query params). Client specifies required fields. Server projects the response. Used by JSON:API (`fields[orders]=status,total`), Google APIs (`fields=order_id,status`).

**Multiple representations via content negotiation:**
Define a compact media type and a full media type:
```
GET /orders/ord-123
Accept: application/vnd.myapi.order.summary+json
→ Returns only summary fields

Accept: application/vnd.myapi.order.full+json
→ Returns full representation
```
More RESTful (uses content negotiation as Fielding intended) but requires defining and documenting multiple media types.

**GraphQL as an overlay:**
For extreme flexibility, expose a GraphQL endpoint alongside the REST API. Mobile clients use GraphQL to specify exactly what they need; other clients use REST. This is a common pattern in large platforms (GitHub offers both).

**Recommendation:** Sparse fieldsets with query parameters (`?fields=...`) for simple cases — minimal implementation effort, widely understood. Consider GraphQL if mobile clients have highly variable data requirements across many resources — the flexibility justifies the additional complexity.

**Q25. "Your REST API has grown organically and you've received complaints that it's inconsistent — some resources use camelCase, others use snake_case; some use `/v1/` in the URL, others don't; some return errors as 200 with an error field. How do you fix this without breaking existing clients?"**
A: A consistency remediation plan that respects existing clients:

**Step 1 — Audit and document the current state:**
Catalog all endpoints, their naming conventions, versioning, response shapes, and error formats. Identify which are public (external clients) vs internal (controlled clients). Public endpoints require backward compatibility; internal endpoints can be changed with coordination.

**Step 2 — Publish an API style guide:**
Define the target state: snake_case for JSON fields, `/v{N}/` URL versioning for breaking changes, RFC 9457 Problem Details for errors, standard pagination response shape. Get team agreement before implementing.

**Step 3 — Introduce new behaviors under versioning, not alongside old:**
For breaking changes (case convention change, error format change):
- Introduce `/v2/` endpoints with the new conventions.
- Keep `/v1/` endpoints unchanged until clients migrate.
- Set deprecation headers on `/v1/` endpoints: `Deprecation: true`, `Sunset: Sat, 01 Jan 2027 00:00:00 GMT`.

**Step 4 — Fix non-breaking issues immediately:**
Non-breaking fixes (adding `_links` to responses, adding optional fields, fixing incorrect status codes where the new code is more semantically correct) can be deployed without versioning. Adding a `Retry-After` header to 429 responses is non-breaking — existing clients ignore unknown headers.

**Step 5 — Automated enforcement going forward:**
Add API linting to the CI pipeline (Spectral, Vacuum) with rules enforcing the style guide. PRs that introduce new endpoints are automatically checked for consistency. Prevent drift from the moment the style guide is in place.

## Quick Reference: REST Constraints Summary

| Constraint | What It Requires | Primary Benefit |
|---|---|---|
| Client-Server | UI concerns separated from data concerns | Independent evolvability |
| Statelessness | No server-side session state; every request self-contained | Horizontal scalability, fault tolerance |
| Cacheability | Responses declare themselves cacheable or not | Scalability, reduced latency |
| Layered System | Client unaware of intermediaries | Security, scalability, transparent caching |
| Code on Demand | Server may transfer executable code (optional) | Client extensibility |
| Uniform Interface | Standardized interaction via resources, representations, self-descriptive messages, HATEOAS | Simplicity, decoupling, discoverability |

**Tip for the interview:** REST questions at senior level have two reliable depth probes: (1) the statelessness vs caching question — candidates who say "Redis violates statelessness" demonstrate a misconception; statelessness is about session state, not cached data; (2) HATEOAS — most candidates know the acronym but can't explain what it solves (URL coupling) or why it's widely omitted in practice (client complexity, tooling gap, versioning as a simpler alternative). Knowing the Richardson Maturity Model (Level 2 = what industry calls REST, Level 3 = what Fielding actually means) positions you correctly when the interviewer asks "is your API truly RESTful?" The correct answer is almost always "it's Level 2 RESTful — we use proper HTTP methods and status codes but don't implement HATEOAS, choosing API versioning instead for managing breaking changes."
