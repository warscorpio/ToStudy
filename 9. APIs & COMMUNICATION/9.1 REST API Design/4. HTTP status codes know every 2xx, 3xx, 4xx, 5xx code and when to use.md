# HTTP Status Codes — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the structure of HTTP status codes and what do the hundreds digits mean?**
A: HTTP status codes are three-digit integers defined in RFC 9110. The first digit classifies the response category; the last two narrow the specific meaning:

- **1xx — Informational**: the request was received and is being processed; the client should continue or wait.
- **2xx — Success**: the request was received, understood, and accepted. The specific code conveys what was done (created, accepted for async processing, no content to return, etc.).
- **3xx — Redirection**: further action is needed to complete the request — follow a different URL, use a cached response, or apply a method change.
- **4xx — Client Error**: the request contains an error that the client is responsible for fixing before retrying — bad syntax, missing auth, forbidden resource, not found.
- **5xx — Server Error**: the server failed to fulfil a valid request. The client's request was fine; the server is at fault.

The most important distinction to internalize: **4xx = client's fault, 5xx = server's fault**. A 4xx response should never be retried blindly — the same request will produce the same error until the client changes something. A 5xx response may be retried (with exponential backoff) since the server may have recovered.

**Q2. What is the difference between a status code and an error response body?**
A: The status code is a machine-readable signal for clients, load balancers, CDNs, and monitoring systems — it tells infrastructure how to handle the response (cache it, retry it, alert on it) without parsing the body. The response body is a human-readable (and structured) explanation for developers and end users.

Both are necessary:
```
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_failed",
  "message": "The request body is invalid.",
  "details": [
    { "field": "email", "issue": "must be a valid email address" },
    { "field": "amount", "issue": "must be greater than 0" }
  ]
}
```

The `422` tells the client's retry logic "don't retry — this is a client error requiring a fix." The body tells the developer exactly which fields failed validation. Using `200 OK` with `{"success": false, "error": "..."}` in the body breaks every monitoring tool, CDN cache rule, and client SDK that relies on status codes — a common antipattern in legacy APIs.

## Section 2: 2xx — Success

**Q3. When do you use `200 OK`?**
A: The default success code for any request that succeeded and has a response body to return. Use `200` when:
- A `GET` request returns the requested resource.
- A `PUT` or `PATCH` request updated a resource and returns the updated state.
- A `POST` request performed an action (not creation) and returns a result.
- A `DELETE` request succeeded and returns a body confirming what was deleted (though `204` is more common for bodyless deletes).

`200` is the correct code when the operation succeeded and there is something meaningful to return in the body. Do not use `200` for resource creation — that is `201`.

**Q4. When do you use `201 Created`?**
A: Use `201` when a `POST` (or occasionally `PUT`) request results in the creation of a new resource. The response must include a `Location` header pointing to the URL of the newly created resource, and typically includes the created resource in the body:

```
POST /orders
Content-Type: application/json
{"customerId": "cust-42", "items": [...]}

HTTP/1.1 201 Created
Location: /orders/98432
Content-Type: application/json

{"id": "98432", "status": "pending", "customerId": "cust-42", ...}
```

The `Location` header is the key difference between `200` and `201` — it tells the client where the new resource lives. Without the `Location` header, `201` is technically malformed. Use `201` instead of `200` for creation so clients can distinguish "this operation returned data" from "this operation created something new."

**Q5. When do you use `202 Accepted`?**
A: Use `202` when the request has been accepted for processing but the processing has not completed — and will not complete synchronously. The server has queued the work; the client must check back later for the result.

```
POST /videos/transcode
{"videoId": "vid-123", "targetFormats": ["720p", "1080p"]}

HTTP/1.1 202 Accepted
Content-Type: application/json

{
  "jobId": "job-xyz789",
  "status": "queued",
  "statusUrl": "/jobs/job-xyz789",
  "estimatedCompletion": "2024-07-23T14:10:00Z"
}
```

The body should include a `statusUrl` or `jobId` that the client can use to poll for completion. `202` is the correct code for: bulk import jobs, video transcoding, report generation, email campaigns, anything that runs asynchronously. Do not use `200` for async operations — it implies completion.

**Q6. When do you use `204 No Content`?**
A: Use `204` when the operation succeeded but there is no body to return. The most common cases:
- `DELETE` requests that successfully deleted a resource.
- `PUT` or `PATCH` requests that updated a resource but the response body would be redundant (the client already knows what it sent).
- Idempotent operations where no feedback is needed beyond "it worked."

```
DELETE /orders/98432

HTTP/1.1 204 No Content
```

No body, no `Content-Type` header. The HTTP spec requires that `204` responses have an empty body — sending a body with `204` is a protocol violation. If you want to return the deleted resource for confirmation, use `200` with a body instead.

**Q7. When do you use `206 Partial Content`?**
A: Use `206` when responding to a `Range` request — the client requested only a portion of a resource (common in video streaming, large file downloads, and resumable uploads):

```
GET /videos/movie.mp4
Range: bytes=0-1048575

HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1048575/104857600
Content-Length: 1048576
Content-Type: video/mp4

[first 1MB of the video file]
```

`206` tells the client this is a partial response (so it can append it to what it already has) rather than the full resource (which would be `200`). Required for: HLS/DASH video segment serving, resumable file downloads (where the client resumes from a byte offset after a connection drop), and range-based pagination of binary data.

## Section 3: 3xx — Redirection

**Q8. When do you use `301 Moved Permanently` vs `302 Found`?**
A:
**`301 Moved Permanently`** — the resource has moved to a new URL permanently. Clients (and search engines) should update their bookmarks/links; future requests should go to the new URL directly. The `Location` header gives the new URL. Browsers typically cache `301` responses permanently (or for a long time), so the old URL is rarely re-requested.

**`302 Found`** — the resource is temporarily at a different URL. The client should use the `Location` URL for this request but continue using the original URL for future requests. Not cached by default; the redirect may change. Use for: A/B testing where the target URL changes, maintenance redirects, feature-flag-based redirects.

```
GET /blog/old-slug

HTTP/1.1 301 Moved Permanently
Location: https://example.com/blog/new-slug
Cache-Control: max-age=31536000
```

Common mistake: using `301` when the redirect may change — a `301` cached aggressively by a browser means the user will never hit the original URL again, even after you remove the redirect.

**Q9. When do you use `303 See Other`?**
A: Use `303` after a `POST` (or `PUT`/`DELETE`) request to redirect the client to a `GET` resource for the result. This is the **Post/Redirect/Get (PRG)** pattern:

```
POST /checkout
{"cartId": "cart-123", "paymentMethod": "card"}

HTTP/1.1 303 See Other
Location: /orders/98432/confirmation
```

The browser follows the redirect with a `GET` request to `/orders/98432/confirmation`. If the user presses refresh on the confirmation page, it re-issues a `GET` — not the original `POST`. Without `303`, a browser refresh would re-submit the form, potentially double-charging the user. `303` forces a method change from `POST` to `GET` on the redirect — unlike `301`/`302` where the behavior is browser-dependent.

**Q10. When do you use `304 Not Modified`?**
A: Use `304` in response to a conditional `GET` request when the resource hasn't changed since the client last fetched it. The client sends `If-None-Match: "etag-value"` or `If-Modified-Since: <date>`; the server checks whether the resource has changed:

```
GET /products/42
If-None-Match: "abc123def456"

HTTP/1.1 304 Not Modified
ETag: "abc123def456"
Cache-Control: max-age=3600
```

No body is sent — the client uses its cached copy. `304` is the foundation of HTTP caching for API responses and static assets. Without it, every `GET` request transfers the full resource body even when nothing has changed, wasting bandwidth and increasing latency. On an API with heavily read data (product catalog, user profiles), correct `ETag` + `304` handling can eliminate 80–90% of data transfer.

**Q11. When do you use `307 Temporary Redirect` vs `308 Permanent Redirect`?**
A: `307` and `308` are the modern counterparts to `302` and `301`, with one crucial difference: they explicitly preserve the HTTP method on redirect.

- **`302 Found`** — says "temporary redirect" but browsers historically changed `POST` to `GET` on follow. The spec eventually blessed this behavior. Ambiguous for non-GET methods.
- **`307 Temporary Redirect`** — explicitly requires the client to use the same method (a `POST` redirected with `307` must re-`POST` to the new URL). Not cached. Use for: APIs that temporarily redirect `POST`/`PUT` requests (e.g., redirecting writes to a different datacenter).
- **`308 Permanent Redirect`** — same as `301` but preserves the method. Use for: permanently moving an API endpoint that receives `POST`/`PUT` requests without wanting clients to switch to `GET`.

In REST APIs: prefer `307`/`308` over `302`/`301` when non-`GET` methods are involved, to avoid the ambiguity around method preservation.

## Section 4: 4xx — Client Errors

**Q12. When do you use `400 Bad Request`?**
A: Use `400` when the request is malformed — the server cannot parse or process it because the client sent syntactically or semantically invalid data:
- Malformed JSON body (`{"key": }` — syntax error).
- Missing required query parameter.
- Type mismatch (`amount: "foo"` where a number is required).
- Business rule violation that is the client's responsibility to know about upfront (e.g., end date before start date).

`400` is the generic client error. Use more specific codes (`422`, `409`, `413`) when they apply — a specific code is more informative to clients than a generic `400`. Return a body that explains what was wrong and how to fix it.

**Q13. When do you use `401 Unauthorized` vs `403 Forbidden`?**
A: This is one of the most commonly confused pairs:

**`401 Unauthorized`** — the request lacks valid authentication credentials. The client is not authenticated (or provided invalid credentials). The name is misleading — "Unauthorized" means "unauthenticated." The `WWW-Authenticate` header should be included to tell the client what authentication scheme is expected:
```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api.example.com"
```
Use `401` for: missing or expired JWT token, invalid API key, wrong username/password. The implication: "provide valid credentials and you may be allowed in."

**`403 Forbidden`** — the client IS authenticated but does not have permission to perform this action. The server understood the request and knows who the client is, but access is denied regardless. The `WWW-Authenticate` header is NOT included — re-authenticating won't help.
```
HTTP/1.1 403 Forbidden
{"error": "insufficient_permissions", "required": "admin", "current": "viewer"}
```
Use `403` for: authenticated user trying to access another user's data, viewer role trying to delete a resource, IP allowlist violation. The implication: "you are known, but you are not allowed."

**The decision tree:** Is the client identified (authenticated)? No → `401`. Yes → is access denied? Yes → `403`.

**Q14. When do you use `404 Not Found`?**
A: Use `404` when the requested resource does not exist at the given URL. The most common case, but with nuances:

- `GET /orders/99999` where order 99999 does not exist → `404`.
- `GET /users/42/preferences` where user 42 exists but has no preferences set → `404` (the resource does not exist, even if the parent does).
- `GET /nonexistent-endpoint` where the route is not defined → `404`.

**Do not use `404` to hide unauthorized resources.** If a user requests `/orders/42` and order 42 exists but belongs to another user, returning `404` instead of `403` leaks the fact that the resource exists. Security-sensitive APIs sometimes return `404` for forbidden resources intentionally (to avoid enumeration attacks) — this is a deliberate security trade-off, not a mistake, but should be a conscious decision.

**`410 Gone`** is the stronger version of `404`: the resource existed but has been permanently deleted and will not be available again. Use `410` for tombstoned resources; use `404` for resources that never existed or whose existence is unknown.

**Q15. When do you use `405 Method Not Allowed`?**
A: Use `405` when the HTTP method used is not supported for the requested resource. The response must include an `Allow` header listing the permitted methods:

```
DELETE /users/42/email

HTTP/1.1 405 Method Not Allowed
Allow: GET, PUT
```

Use `405` for: trying to `DELETE` a read-only resource, trying to `POST` to a resource that only accepts `GET`, or using `PATCH` on a resource that only supports `PUT`. Distinct from `404` — the URL exists, but the method is wrong.

**Q16. When do you use `408 Request Timeout`?**
A: Use `408` when the server timed out waiting for the client to send the full request. The client started a request but didn't complete it within the server's timeout window — for example, sending headers but never sending the body.

Different from `504 Gateway Timeout` — `408` is the server waiting for the client; `504` is a proxy waiting for an upstream server. `408` is relatively rare in API contexts (more common in TCP-level connection management); more commonly seen in file upload scenarios where a slow client fails to stream the full body within the timeout.

**Q17. When do you use `409 Conflict`?**
A: Use `409` when the request conflicts with the current state of the resource — the request is valid, but the server cannot fulfil it without the conflict being resolved:

- Creating a resource that already exists (duplicate unique constraint): `POST /users` where the email already exists → `409`.
- Optimistic locking conflict: `PUT /documents/42` with `If-Match: "old-etag"` where the document has since been updated → `409`.
- Business state conflict: trying to cancel an order that has already been shipped → `409`.

```
POST /users
{"email": "user@example.com"}

HTTP/1.1 409 Conflict
{"error": "duplicate_email", "message": "A user with this email already exists"}
```

Distinct from `400`: a `400` means the request itself is invalid; a `409` means the request is valid but conflicts with existing state.

**Q18. When do you use `410 Gone`?**
A: Use `410` when a resource previously existed at this URL but has been permanently deleted or removed and will not return. It is a permanent `404` — the server is explicitly telling clients (and search engines) that this is not a transient absence:

```
GET /legacy-api/v1/users/42

HTTP/1.1 410 Gone
{"error": "resource_deleted", "message": "This resource has been permanently removed. See /api/v2/users/42"}
```

Use `410` for: deprecated API endpoints that have been shut down, deleted user accounts that must not be re-created at the same URL, permanently removed content. Search engines delist `410` pages more quickly than `404` pages — important for SEO and API deprecation clarity.

**Q19. When do you use `413 Content Too Large`?**
A: Use `413` when the request body exceeds the server's configured size limit. Common scenarios: file upload exceeding `100MB` limit, JSON body exceeding the API gateway's body size limit, batch request with too many items.

```
POST /uploads
Content-Length: 524288000  (500MB)

HTTP/1.1 413 Content Too Large
{"error": "file_too_large", "maxSize": "100MB", "received": "500MB"}
```

The response should include the maximum allowed size in the body so the client knows what to correct. Distinct from `400` — the content is potentially valid; it just exceeds size limits.

**Q20. When do you use `415 Unsupported Media Type`?**
A: Use `415` when the client sends a request body in a format the server cannot process — specified via the `Content-Type` header:

```
POST /orders
Content-Type: text/xml
<order>...</order>

HTTP/1.1 415 Unsupported Media Type
{"error": "unsupported_media_type", "supported": ["application/json"]}
```

Distinct from `400` — the content itself may be perfectly formed XML, but the server only accepts JSON. Include the list of supported media types in the response body.

**Q21. When do you use `422 Unprocessable Entity`?**
A: Use `422` when the request body is syntactically correct (valid JSON/XML) but semantically invalid — the server understands the structure but cannot process the content:

- JSON is valid but field values fail business validation (`amount: -50`, `email: "not-an-email"`).
- Required fields are missing from an otherwise valid JSON body.
- Cross-field validation failure (`end_date` is before `start_date`).

```
POST /orders
{"customerId": "cust-42", "amount": -50, "items": []}

HTTP/1.1 422 Unprocessable Entity
{
  "error": "validation_failed",
  "details": [
    {"field": "amount", "issue": "must be greater than 0"},
    {"field": "items", "issue": "must contain at least one item"}
  ]
}
```

The `400` vs `422` distinction: `400` for malformed requests (can't parse the body); `422` for well-formed requests with invalid content. In practice many APIs use `400` for both — `422` is the semantically correct choice for validation failures on parseable payloads.

**Q22. When do you use `429 Too Many Requests`?**
A: Use `429` when a client has exceeded a rate limit. The response should include `Retry-After` (seconds to wait before retrying) and rate limit context headers:

```
GET /api/products

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1721741010

{"error": "rate_limit_exceeded", "retryAfter": 30}
```

`Retry-After` can be a number of seconds or an HTTP date. Well-behaved clients implement exponential backoff when they receive `429`; the `Retry-After` header gives them a server-suggested minimum wait time. Use `429` consistently across your API — rate limiting logic (in API gateways, middleware) must return `429`, not `503`.

**Q23. What are other important 4xx codes to know?**
A: Several less-common but interview-relevant 4xx codes:

**`406 Not Acceptable`** — the server cannot produce a response matching the `Accept` headers sent by the client (e.g., client requests `Accept: application/xml` but server only produces JSON). Should include what content types are available.

**`411 Length Required`** — the server requires a `Content-Length` header that the client didn't send. Rare in modern HTTP/1.1 where chunked transfer encoding is common.

**`412 Precondition Failed`** — a conditional request (`If-Match`, `If-Unmodified-Since`) failed — the precondition was not met. Used for optimistic locking (see `409`). The distinction: `409` for general state conflicts; `412` specifically for failed conditional request headers.

**`414 URI Too Long`** — the request URI exceeds the server's maximum length. Typically caused by excessively long query strings; suggest pagination or moving query params to the body.

**`451 Unavailable For Legal Reasons`** — the resource is unavailable due to legal demands (government censorship, DMCA takedown, court order). Named after Fahrenheit 451. Include a `Link` header pointing to a resource explaining the legal reason.

## Section 5: 5xx — Server Errors

**Q24. When do you use `500 Internal Server Error`?**
A: Use `500` when the server encounters an unexpected condition that prevented it from fulfilling the request — a catch-all for server-side failures with no more specific code available. Unhandled exceptions, null pointer dereferences, unexpected data states, and bugs all produce `500`.

```
GET /orders/42

HTTP/1.1 500 Internal Server Error
{"error": "internal_error", "requestId": "req-abc123"}
```

**Do not expose internal details in the body** — stack traces, SQL queries, file paths, or internal server names. Include only a `requestId` that operations can use to correlate to server logs. Stack traces in `500` responses are a security vulnerability (information disclosure) and a support anti-pattern.

`500` should alert your monitoring system — every `500` is unexpected and requires investigation. A spike in `500` responses is an incident indicator.

**Q25. When do you use `501 Not Implemented`?**
A: Use `501` when the server does not support the functionality required to fulfil the request — usually when an HTTP method is used that the server does not implement at all (not for a specific resource, but globally):

```
PATCH /orders/42

HTTP/1.1 501 Not Implemented
{"error": "not_implemented", "message": "PATCH method is not supported by this server"}
```

Distinct from `405 Method Not Allowed`: `405` means the method is not allowed for this specific resource (but the server supports the method elsewhere); `501` means the server does not implement this method at all. `501` is also appropriate for features that are declared in the API contract but not yet built ("coming soon" stubs).

**Q26. When do you use `502 Bad Gateway`?**
A: Use `502` when a server acting as a proxy or gateway received an invalid response from an upstream server. The proxy or load balancer is working; the upstream it's forwarding to is returning garbage or an error that can't be interpreted:

```
GET /api/products

HTTP/1.1 502 Bad Gateway
{"error": "upstream_error", "message": "Upstream service returned an invalid response"}
```

Common causes: the upstream service returned a malformed response, crashed mid-response, returned an HTTP/0.9 response when HTTP/1.1 was expected. Seen in: Nginx returning `502` when a Node.js backend process crashed; API gateway returning `502` when a Lambda function timed out without sending a response.

Distinct from `503` and `504`: `502` is about an invalid/unexpected upstream response (not unavailability or timeout).

**Q27. When do you use `503 Service Unavailable`?**
A: Use `503` when the server is temporarily unable to handle the request — typically due to being overloaded or undergoing maintenance. Include `Retry-After` to indicate when the service may be available:

```
HTTP/1.1 503 Service Unavailable
Retry-After: 120
{"error": "service_unavailable", "message": "Server is undergoing maintenance. Retry after 2 minutes."}
```

Use `503` for: circuit breaker open (the service has detected an upstream is unhealthy and is failing fast), rate limiting at the infrastructure level (distinct from per-client `429`), planned maintenance mode, autoscaling lag (all instances are at capacity before new ones spin up), dependency outage causing the service to be unable to function.

`503` is retryable — the client should retry with backoff. Well-configured load balancers and service meshes remove a `503`-returning instance from the rotation.

**Q28. When do you use `504 Gateway Timeout`?**
A: Use `504` when a proxy or gateway did not receive a timely response from an upstream server. The upstream is reachable (unlike `502`) but took too long to respond:

```
POST /payments

HTTP/1.1 504 Gateway Timeout
{"error": "gateway_timeout", "message": "Upstream payment service did not respond within 30s"}
```

Common causes: an API gateway or Nginx proxy has a 30-second timeout; the backend application is slow (database query running long, external API slow); the backend is alive but under heavy load and cannot respond within the configured timeout. Seen in: Nginx returning `504` when a Django app has a slow database query; API gateway timing out a Lambda that's under heavy load.

Distinct from `408 Request Timeout` (server waiting for client) and `503 Service Unavailable` (server explicitly unavailable). `504` specifically means a proxy's upstream timed out.

**Q29. What are other 5xx codes worth knowing?**
A:

**`505 HTTP Version Not Supported`** — the server doesn't support the HTTP protocol version in the request. Rare in practice; seen in clients that send HTTP/2 to servers that only support HTTP/1.1.

**`507 Insufficient Storage`** — the server cannot store the representation needed to complete the request (WebDAV origin; used in storage APIs). Use when a file upload fails because the storage backend is full, rather than returning the less specific `500`.

**`511 Network Authentication Required`** — the client must authenticate to gain network access — typically used by captive portals (hotel WiFi login pages). Not a standard server error in the traditional sense; used by network infrastructure rather than application servers.

## Section 6: Common Mistakes and Antipatterns

**Q30. What are the most common HTTP status code mistakes in production APIs?**
A: Six antipatterns seen repeatedly in production codebases:

**1. Returning `200` for errors (`200 OK` with `{"success": false}`):**
Every monitoring tool, CDN, API gateway, and client SDK interprets status codes. A `200` with an error body disables all of these. Circuit breakers don't open, error rate alerts don't fire, and CDNs cache the error response. Fix: use the appropriate 4xx or 5xx code.

**2. Using `500` for client errors:**
An unhandled exception in validation code that throws instead of returning `400`. All client errors that crash the application become `500` — alert fatigue, false incident signals. Fix: structured error handling with proper status codes at every layer.

**3. Using `404` for validation errors:**
`GET /users?email=notanemail` returns `404 Not Found` when it should return `400 Bad Request` or `422 Unprocessable Entity`. The resource doesn't not-exist; the query is invalid. Fix: distinguish "resource not found" (`404`) from "invalid request" (`400`/`422`).

**4. Not returning `201` for resource creation:**
`POST /users` that creates a user returns `200` without a `Location` header. Clients can't distinguish "found something" from "created something." Fix: return `201 Created` with `Location: /users/42`.

**5. Returning `403` for unauthenticated requests:**
The client has no token and gets `403`. But `403` implies "I know who you are and you're not allowed." The correct code for "I don't know who you are" is `401`. Fix: check authentication first (`401`), then authorization (`403`).

**6. Swallowing `429` and retrying immediately:**
Client receives `429`, ignores `Retry-After`, and immediately retries — creating a retry storm that makes the rate limiting problem worse. Fix: honor `Retry-After` header; implement exponential backoff with jitter.

**Q31. How do status codes interact with caching?**
A: HTTP caching behaviour is determined partly by the status code. Not all successful responses are cacheable by default:

| Status | Default cacheability | Notes |
|--- |--- |--- |
| `200` | Cacheable (if headers permit) | Most common cached response |
| `201` | Not cached by default | Created resources may change immediately |
| `204` | Not cached (no body) | Nothing to cache |
| `206` | Cacheable with `Content-Range` | Range responses for partial content |
| `301` | Cached permanently | Browsers cache `301` aggressively |
| `302` | Not cached by default | Temporary; must be re-fetched |
| `304` | Not applicable (uses cached body) | Validates; body served from cache |
| `307` | Not cached by default | Temporary redirect |
| `308` | Cached permanently | Like `301` with method preservation |
| `400` | Not cached | Client must fix and retry |
| `404` | Cacheable (configurable) | Can cache "not found" to reduce load |
| `410` | Cacheable (permanent gone) | Should be cached; resource won't return |
| `429` | Not cached | Rate limit state is per-client, dynamic |
| `500` | Not cached | Transient; would cache a broken response |
| `503` | Not cached (usually) | `Retry-After` signals temporary |

A misconfigured CDN that caches `500` responses is a serious incident — all subsequent requests get the cached error even after the server recovers. Always ensure error responses have `Cache-Control: no-store` or appropriate `no-cache` directives.

| **451** | Unavailable For Legal Reasons | Legal demand (censorship, DMCA) |
| **500** | Internal Server Error | Unexpected server error; never expose details |
| **501** | Not Implemented | Method/feature not supported server-wide |
| **502** | Bad Gateway | Proxy got invalid response from upstream |
| **503** | Service Unavailable | Server overloaded or in maintenance |
| **504** | Gateway Timeout | Proxy's upstream timed out |

---

**Tip for the interview:** At 5 YOE level, interviewers don't test whether you can recite all status codes — they probe whether you use them correctly in design discussions. The three pairs that come up most: `401 vs 403` (unauthenticated vs unauthorized — the name "Unauthorized" misleadingly means unauthenticated), `400 vs 422` (malformed vs valid-but-invalid — most APIs use `400` for both; know the distinction even if you unify them), and `502 vs 503 vs 504` (upstream returned garbage vs server unavailable vs upstream timed out — these come up in system design when discussing gateway error handling). Know that `429` requires `Retry-After`, `201` requires `Location`, and `204` requires an empty body — these are the specific details that turn a "knows the codes" answer into a "uses them correctly in production" answer.
