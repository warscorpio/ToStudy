# Resource Naming Conventions and Anti-Patterns (REST API) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "resource" mean in REST, and why is naming the central design decision?**
A: In REST (Representational State Transfer), a resource is any concept that can be addressed, named, and interacted with — a user, an order, a product, a relationship between entities, or even an abstract concept like a search result or a report. Resources are the nouns of your API: the things clients operate on. The URL is the resource's address; the HTTP method is the verb applied to it.

Naming is the central design decision because the URL is part of your public contract. Once published and adopted by clients, a URL is nearly impossible to change without breaking integrations. Poor naming choices — verbs in paths, inconsistent casing, arbitrary nesting — compound over time into a sprawling surface that is confusing to integrate, difficult to document, and expensive to version. A well-named API surface is self-documenting, predictable, and extensible without breaking changes.

**Q2. What are Roy Fielding's original REST constraints, and which ones directly affect naming decisions?**
A: Fielding's six constraints: client-server, statelessness, cacheability, uniform interface, layered system, and code-on-demand (optional). The **uniform interface** constraint most directly shapes naming. It requires: resource identification via URIs, manipulation through representations, self-descriptive messages, and HATEOAS (hypermedia as the engine of application state). In practice: a URI must unambiguously identify exactly one resource, the HTTP method on that URI must follow its standard semantics, and the representation (JSON, XML) must be self-describing.

Naming violations break the uniform interface: a verb in a URL (`/getUser`) makes the URI encode both the resource and the action — the HTTP method is redundant or contradictory. An inconsistently pluralized API (`/users` vs `/order`) is not self-descriptive — clients can't infer patterns. REST naming conventions exist to enforce the uniform interface in practice.

**Q3. What is the single most important rule for REST resource naming?**
A: **Use nouns, not verbs.** The HTTP method (GET, POST, PUT, PATCH, DELETE) is the verb. The URL is the noun — the resource being acted upon. The combination of URL + method fully specifies what is happening without encoding the action in the path.

| Wrong (verb in URL)             | Right (noun + HTTP method)              |
|---                              |---                                      |
| `GET /getUser/123`              | `GET /users/123`                        |
| `POST /createOrder`             | `POST /orders`                          |
| `DELETE /deleteAccount/456`     | `DELETE /accounts/456`                  |
| `GET /fetchProductList`         | `GET /products`                         |
| `POST /sendInvoice`             | `POST /invoices` or `POST /invoices/{id}/send` |

The verb-in-URL anti-pattern is the most pervasive REST mistake. It typically signals RPC (Remote Procedure Call) thinking applied to HTTP — treating the URL as a function name rather than a resource address.

**Q4. What is the difference between REST and RPC, and why does the distinction matter for naming?**
A: **REST** models interactions as operations on resources: `GET /orders/123` (retrieve the order resource with ID 123). The URL identifies a thing; the method specifies what to do to it. **RPC** (Remote Procedure Call) models interactions as function calls: `POST /getOrder` with `{"orderId": 123}` in the body. The URL identifies an operation; the body carries the parameters.

The distinction matters because HTTP infrastructure (caches, load balancers, CDNs, browsers) is built around REST semantics. Caches key on URL + method; a `GET /getOrder` is indistinguishable from `GET /createOrder` structurally — both are GET requests to different paths. RPC-over-HTTP loses caching benefits (since meaningful requests are POSTs with opaque bodies), misuses HTTP status codes (RPC errors often return `200 OK` with an error body), and confuses intermediaries. REST naming conventions preserve the HTTP contract that infrastructure relies on.

## Section 2: URL Structure & Hierarchy

**Q5. Should resources be plural or singular, and why?**
A: **Plural** for collections, **consistent** across the API. Use `/users`, `/orders`, `/products` — not `/user`, `/order`, `/product`. Reasoning:

- A collection of users is conceptually plural: `GET /users` returns many users. `GET /users/123` returns one user from the collection. The singular member URL (`/users/123`) is already clearly singular by its ID — no ambiguity.
- Plural URLs are more natural in English and more consistent: `GET /users` (list all), `POST /users` (create one), `GET /users/123` (get one), `PUT /users/123` (update one), `DELETE /users/123` (delete one). All five operations share the same base path — simpler to document and remember.
- Mixing singular and plural creates inconsistency: if `/user` returns a single user by session context and `/users` returns all users, clients must remember which form applies where — a cognitive burden and a source of bugs.

The only legitimate exception: singleton resources — resources that exist exactly once in context. `/users/{id}/profile` (a user has exactly one profile) uses singular; `/users/{id}/preferences` is debatable but often singular when it represents a single preference document.

**Q6. How deep should URL nesting go, and what is the rule for when to nest vs. use query parameters?**
A: **Maximum two levels of nesting** is the widely-adopted convention: `/{resource}/{id}/{sub-resource}`. Beyond two levels, URLs become brittle, hard to read, and couple the client tightly to the resource hierarchy. `GET /companies/42/departments/7/employees/99/tasks/3/comments` is a six-level URL — navigating it requires traversing four parent IDs that the client must already know.

The rule for nesting vs. query parameters: **nest when the sub-resource has no meaningful existence outside its parent** (a user's address is only meaningful in the context of a user); **use query parameters when the sub-resource can be independently addressed or filtered** (orders can exist independently of users, so `GET /orders?userId=42` is often preferable to `GET /users/42/orders`).

Both patterns are valid for relationships; choose based on: (1) whether the sub-resource has its own canonical identity; (2) whether clients need to access the sub-resource across multiple parents; (3) whether the nesting adds clarity or complexity. Many mature APIs expose both: `GET /users/42/orders` as a convenience shortcut and `GET /orders?userId=42` as the canonical address.

**Q7. What casing convention should URL paths and query parameters use?**
A: URL paths: **lowercase with hyphens (kebab-case)**. `GET /user-profiles`, not `GET /userProfiles` (camelCase) or `GET /user_profiles` (snake_case). Reasoning: URLs are case-sensitive on most servers (except the scheme and host); uppercase letters in paths risk inconsistency (`/Users` vs `/users`) and are easily mistyped. Hyphens are the conventional word separator in URLs (per RFC 3986 and Google's URL guidelines); underscores are invisible when text is underlined in browsers and are sometimes treated as word separators inconsistently by search engines.

Query parameter names: **snake_case** is conventional in many APIs (`?user_id=42&page_size=20`), though some APIs use camelCase (`?userId=42&pageSize=20`). The critical rule is **consistency**: pick one and apply it everywhere across the API. Mixing `user_id` and `userId` in different endpoints is the anti-pattern.

JSON response body field names: **camelCase** (`"userId"`, `"createdAt"`) is conventional for JSON APIs (JavaScript clients expect camelCase). Some APIs use snake_case (`"user_id"`, `"created_at"`) — common in Python-backend APIs. Again, consistency matters more than which you choose.

**Q8. What is a "canonical URL" and why should every resource have exactly one?**
A: A canonical URL is the single, definitive address for a resource — the one URL that unambiguously identifies it. Every resource should have exactly one canonical URL: `GET /users/123` is the canonical address for user 123. Aliases (e.g., `GET /me` for the currently authenticated user, or `GET /users/current`) are acceptable as convenience shortcuts, but they should redirect to or respond identically to the canonical form, and clients should not build persistent references to aliases.

Why it matters: (1) **caching** — HTTP caches key on URL; two URLs for the same resource cause double caching with no invalidation coordination; (2) **API clients** — clients that discover resource URLs (via HATEOAS links or documentation) must consistently receive the same form; (3) **logging and analytics** — two URLs for the same resource split access logs, making traffic analysis misleading. When providing aliases, respond with a `Location` header pointing to the canonical URL or include the canonical URL in the response body's `links` object.

## Section 3: HTTP Methods & Their Semantics

**Q9. What are the semantics of each HTTP method and what properties must they satisfy?**
A: Each method has defined semantics from the HTTP specification (RFC 7231), which REST APIs must respect:

- **GET**: retrieve a resource. **Safe** (no side effects) and **idempotent** (multiple identical requests produce the same result). Never use GET for mutations — it breaks caching (caches may return cached responses for repeated GETs) and violates expectations (browser preloading and link-following assume GET is safe).
- **POST**: create a subordinate resource or trigger a non-idempotent action. **Not safe, not idempotent**. `POST /orders` creates a new order; repeated calls create multiple orders. Used for resource creation and for operations that don't fit CRUD (search with complex body, RPC-style actions).
- **PUT**: replace a resource entirely with the provided representation. **Idempotent** (multiple identical PUTs produce the same final state). The client sends the complete resource; the server replaces whatever was there. Missing fields are set to null or default — not preserved.
- **PATCH**: partially update a resource. **Not necessarily idempotent** (depends on whether the patch is absolute or relative). The client sends only the fields to change. Safer than PUT for partial updates — clients don't need to know the full resource state.
- **DELETE**: remove a resource. **Idempotent** (deleting an already-deleted resource should return 404 or 204, not an error that prevents retry). Once deleted, the resource is gone.

**Q10. What is idempotency and why does it matter for API design and client behavior?**
A: Idempotency means that making the same request N times produces the same result as making it once. Formally, `f(f(x)) = f(x)`. For HTTP: `PUT /users/123` with the same body applied 10 times leaves the user in the same state as applying it once. `DELETE /users/123` applied 10 times has the same final state (user is deleted) regardless of repetition.

Why it matters: (1) **retry safety** — clients and infrastructure (load balancers, service meshes) can safely retry idempotent requests on failure without risk of duplicate side effects. A network timeout on a PUT can be safely retried; a timeout on a POST cannot (the resource may have been created). (2) **at-least-once delivery guarantees** — distributed systems often guarantee at-least-once delivery; idempotent endpoints handle duplicate deliveries gracefully. (3) **resilience** — APIs with non-idempotent operations that clients must retry need idempotency keys to prevent duplicate actions.

For non-idempotent POST operations (payments, order creation), the solution is an **idempotency key** header (`Idempotency-Key: {uuid}`). The server stores the response for the first request with a given key; subsequent requests with the same key return the cached response without re-executing the operation.

**Q11. When is it appropriate to use POST for an action that isn't creating a resource?**
A: Some operations don't map cleanly to CRUD but are still REST-compatible using POST on an action sub-resource. This is the **controller resource** pattern — the sub-resource represents an action or transition:

```
POST /orders/{id}/cancel         # cancel an order
POST /users/{id}/activate        # activate a user account
POST /accounts/{id}/freeze       # freeze an account
POST /invoices/{id}/send         # send an invoice to the recipient
POST /payments/{id}/refund       # refund a payment
```

These are preferable to encoding the action in a query parameter (`POST /orders/{id}?action=cancel`) or in the request body (`POST /orders/{id}` with `{"action": "cancel"}`). The URL clearly identifies what is happening; the HTTP method (POST) signals a state-changing, non-idempotent operation.

Keep the sub-resource a noun where possible (`/cancellation` rather than `/cancel`) — though the verb form is widely accepted and often more readable for actions. The key principle: the URL should identify a resource (even if that resource is an abstract state transition), and POST should be used when the operation is non-idempotent and changes state.

## Section 4: Anti-Patterns

**Q12. What are the five most common REST naming anti-patterns?**
A:
1. **Verbs in URLs**: `/getUsers`, `/createOrder`, `/deleteAccount`, `/fetchProductList`. Encodes the action in the URL when it belongs in the HTTP method.
2. **Inconsistent pluralization**: mixing `/users` and `/order` in the same API. Clients can't predict the pattern; documentation must enumerate every endpoint.
3. **Deep nesting beyond two levels**: `/companies/1/departments/2/teams/3/members/4` — brittle, verbose, and exposes internal data model hierarchy.
4. **CRUD function names as endpoints**: `/api/user/read`, `/api/order/update` — RPC verbs dressed as URL paths. Often appears when developers treat REST as "HTTP + JSON" without applying resource modeling.
5. **Mixing concerns in the same endpoint**: `/api/data` that returns different types based on query parameters (`?type=user`, `?type=order`) — one URL, multiple resources. Violates the one-URL-one-resource principle.

**Q13. What is the "RPC disguised as REST" anti-pattern and what does it look like in practice?**
A: RPC disguised as REST is when an API uses HTTP as a transport for function calls, not as a resource-oriented interface. Recognizable patterns:

```
POST /api/getOrderDetails       # should be GET /orders/{id}
POST /api/updateUserEmail       # should be PATCH /users/{id}
POST /api/processPayment        # acceptable: POST /payments
POST /api/sendNotification      # better: POST /notifications
GET  /api/execute?query=SELECT* # SQL over HTTP — not REST at all
POST /api/do?action=delete&id=5 # encoding action in query param
```

All operations are POST (because the team wants to send a body for everything). HTTP status codes are often ignored — errors return `200 OK` with `{"success": false, "error": "not found"}` in the body. The API is not cacheable (POST responses aren't cached), not explorable (no predictable URL structure), and not self-documenting.

The root cause: teams building REST APIs who are more familiar with RPC patterns (gRPC, SOAP, internal function calls). Fix: audit the API surface for verb URLs and POST-everything patterns; redesign around resources with appropriate methods.

**Q14. What is the "chatty API" anti-pattern and what are its consequences?**
A: A chatty API requires many sequential requests to accomplish a single user-facing action. Example: to render a user's profile page, the client must call:
1. `GET /users/123` — get user details
2. `GET /users/123/address` — get address
3. `GET /users/123/preferences` — get preferences
4. `GET /users/123/subscription` — get subscription
5. `GET /subscriptions/{sub_id}/plan` — get plan details

Five round trips, each blocked on the previous, to render one page. On a mobile device over LTE, each round trip is 50–100ms — 250–500ms of serial latency from API calls alone, before any rendering.

Consequences: high latency, increased server load (connection overhead multiplied by request count), client complexity (must orchestrate many requests and handle partial failures). Mitigations: **composite/aggregation endpoints** (`GET /users/123?include=address,preferences,subscription`), **GraphQL** (client specifies exactly what data it needs in one query), or **Backend for Frontend (BFF)** pattern (a server-side aggregation layer tailored to each client's needs). The chatty pattern is the most common performance complaint in mobile API integration.

**Q15. What is the "God endpoint" anti-pattern, the opposite of the chatty API?**
A: The god endpoint is a single URL that handles many different operations or returns many different resource types, controlled by request body or query parameters:

```
POST /api/v1/process
Body: {"type": "createUser", "data": {...}}

POST /api/v1/process
Body: {"type": "cancelOrder", "orderId": 123}

POST /api/v1/process
Body: {"type": "sendInvoice", "invoiceId": 456}
```

Or in GET form: `GET /api/data?resource=user&id=123&fields=name,email,orders`.

Consequences: one endpoint does everything — impossible to document clearly, impossible to apply different rate limits or auth policies per operation, impossible to cache (same URL returns different data based on body parameters GET doesn't cache on body), and a single point of failure for all operations. Errors from any operation mix in the same logs, and the API surface is opaque to tooling (OpenAPI, client generators). Breaks the uniform interface — clients can't predict behavior from the URL alone.

**Q16. What is the "leaking internal implementation" anti-pattern?**
A: URLs that expose internal data model structure, database table names, or system architecture decisions:

```
GET /mysql/users/table/row/123       # exposes database type
GET /v1/db/accounts/select/active    # SQL operation in URL
GET /api/legacy/crm_users/123        # exposes system name
GET /microservice-user/api/user/123  # exposes service name
POST /service-bus/publish/event      # exposes infrastructure
GET /internal/cache/user/123         # exposes implementation detail
```

Also: exposing database primary keys directly when they carry implementation meaning (`GET /users/uuid-a3f8bc...` when auto-increment IDs are `GET /users/42` — the auto-increment structure leaks insertion order and record count, a business intelligence risk called "enumerable IDs").

Fix: use opaque IDs for public-facing resources (UUIDs or hash IDs instead of sequential integers), use domain-meaningful URL paths that reflect the business model not the database schema, and namespace APIs by business domain (`/commerce/`, `/identity/`) not by implementation detail.

**Q17. What is the "boolean flags as query parameters" anti-pattern?**
A: Using query parameters to toggle the shape or type of the response:

```
GET /users?includeDeleted=true
GET /orders?format=detailed
GET /products?type=physical&type=digital
GET /reports?expanded=true&flat=false
```

The problem: these parameters fundamentally change what resource is being returned, making the URL ambiguous. `GET /users` and `GET /users?includeDeleted=true` return different resources — they aren't the same resource with a filter, they're different sets. Caches may serve the wrong version. Documentation becomes complex ("this endpoint returns X, unless you pass Y, in which case it returns Z").

Better approaches: (1) use separate endpoints when the representations differ significantly (`GET /users` vs `GET /users/deleted`); (2) use the `Accept` header or versioning for format changes; (3) use `fields` or `include` parameters for the specific case of field inclusion (`GET /users/123?fields=name,email,orders`), which is an accepted pattern for reducing response payload. The line: parameter is acceptable when it narrows/shapes the same resource type; parameter is an anti-pattern when it changes what type of resource is returned.

## Section 5: Versioning

**Q18. What are the three main API versioning strategies, and what are the trade-offs of each?**
A:
- **URL path versioning** (`/v1/users`, `/v2/users`): the most common approach. Version is explicit, visible, easily routable (different path prefixes can route to different service versions), and trivially cacheable. Downside: the version becomes part of the resource's canonical URL — `GET /v1/users/123` and `GET /v2/users/123` are different URLs for conceptually the same resource, which violates REST purity (a resource should have one canonical URL). Practically, this is the trade-off most teams accept — simplicity outweighs purity.
- **Accept/Content-Type header versioning** (`Accept: application/vnd.myapi.v2+json`): REST-pure — the URL remains stable (`GET /users/123`), and the version is in the content negotiation header. Clean separation of resource identity (URL) from representation version (header). Downside: not visible in browser URLs, harder to test with curl/Postman without setting headers, harder to route at the infrastructure level (load balancers and API gateways route on URL, not headers by default), and documentation is less obvious.
- **Custom header versioning** (`API-Version: 2`): similar trade-offs to Accept header versioning but uses a custom header rather than the standard `Accept` mechanism. Easier to test than content negotiation (simpler header syntax) but still not visible in URLs and requires header-aware routing.

The pragmatic recommendation: URL path versioning for public APIs (clarity and toolability over purity); header versioning for internal APIs or when preserving stable canonical URLs is important.

**Q19. When should you increment the API version, and what changes are "breaking"?**
A: A breaking change is any change that requires existing clients to modify their code to continue functioning. Breaking changes mandate a version increment:
- **Removing a field** from the response — clients reading that field get null or a deserialization error.
- **Renaming a field** — old field name disappears; clients break.
- **Changing a field's type** — `"count": 5` → `"count": "five"` breaks typed clients.
- **Removing an endpoint** — clients calling it get 404 or 410.
- **Changing required request fields** — clients not sending the now-required field get 400 or 422.
- **Changing URL structure** — `/users/{id}/orders` renamed to `/users/{id}/purchases`.
- **Changing error response format** — clients parsing error bodies break.
- **Changing HTTP method** — `POST /users/activate` → `PUT /users/{id}/activate`.

Non-breaking changes (additive, safe without version increment): adding new optional response fields, adding new optional request fields, adding new endpoints, adding new optional query parameters, relaxing validation (accepting more values), and adding new enum values (with caution — clients doing exhaustive enum matching may break).

**Q20. What is "API versioning via sunset headers" and why is it important for lifecycle management?**
A: Sunset headers are HTTP response headers that communicate the deprecation and eventual removal timeline for an API version:

```http
Sunset: Sat, 31 Dec 2025 23:59:59 GMT
Deprecation: Mon, 01 Jan 2024 00:00:00 GMT
Link: <https://api.example.com/v2/users>; rel="successor-version"
```

`Deprecation` announces that this version is no longer recommended (but still available). `Sunset` announces the date it will stop being available. `Link` with `rel="successor-version"` points clients to the replacement.

Why important: without structured deprecation communication, API providers must either maintain old versions forever (operational burden) or break clients unexpectedly (trust violation). Sunset headers give clients a machine-readable signal to detect and act on deprecation — monitoring tools can alert on deprecated API usage, developer portals can display warnings, and automated client update pipelines can be triggered. RFC 8594 formalizes the `Sunset` header; `Deprecation` is a related draft RFC.

## Section 6: Query Parameters, Filtering & Pagination

**Q21. What is the convention for filtering, sorting, and pagination via query parameters?**
A: These are the accepted conventions for standard query parameter semantics:

**Filtering**: use resource attribute names as parameter keys.
```
GET /orders?status=pending
GET /users?role=admin&country=US
GET /products?min_price=10&max_price=100&category=electronics
```

**Sorting**: `sort` or `order_by` parameter with field name; prefix with `-` for descending.
```
GET /products?sort=price            # ascending by price
GET /products?sort=-created_at      # descending by creation date
GET /products?sort=category,-price  # category asc, price desc
```

**Pagination**: two main patterns — **offset-based** (`page` + `page_size` or `offset` + `limit`) and **cursor-based** (`cursor` or `after` with `limit`):
```
GET /users?page=2&page_size=50        # offset-based (simple, less stable)
GET /users?after=cursor_xyz&limit=50  # cursor-based (stable, preferred)
```

**Field selection (sparse fieldsets)**: `fields` parameter to reduce payload:
```
GET /users/123?fields=id,name,email
```

Naming these parameters consistently across every endpoint matters as much as the conventions themselves. An API where `/users` uses `page` but `/orders` uses `offset` is unpredictable and increases integration friction.

**Q22. When should filtering be a query parameter vs. a path segment?**
A: **Path segment**: when the value is an identifier for a specific resource instance — it uniquely addresses one resource.
```
GET /users/123        # 123 is the user's identity
GET /orders/abc-456   # abc-456 is the order's identity
```

**Query parameter**: when the value narrows a collection — it filters or shapes a list response.
```
GET /users?role=admin             # filter by attribute
GET /orders?status=pending        # filter by state
GET /products?category=footwear   # filter by category
```

The distinction: path segments identify; query parameters filter. A path segment implies the URL is the canonical address of a specific resource; a query parameter implies the URL is a collection address with optional narrowing. Mixed usage (`GET /users/admin` where "admin" is a role, not an ID) is the anti-pattern — it makes "admin" look like a user ID, breaks the pattern for addressing a specific user, and makes it ambiguous whether "admin" can also be a valid user ID.

**Q23. What is the correct way to handle search endpoints, and what are the common anti-patterns?**
A: Search is a common operation that doesn't fit cleanly into CRUD. Two acceptable patterns:

**Simple search via query parameters**:
```
GET /products?q=running+shoes&category=footwear&min_price=50
```
Works for simple keyword + filter combinations. Constraints: query string length limits (browsers cap URLs at ~2000 characters), no support for complex search expressions.

**Search as a resource** (for complex search):
```
POST /search/products
Body: {"query": "running shoes", "filters": {...}, "sort": {...}}
```
Or a saved search pattern:
```
POST /searches          # create a search, returns search ID
GET  /searches/{id}     # retrieve results for a saved search
```

Anti-patterns: `GET /search?type=product&q=...` where `type` changes what resource is searched (chatty and unclear), `GET /users/search?q=...` (search as a sub-resource of a collection is acceptable but `GET /users?q=...` is simpler), and `POST /api/executeSearch` (RPC pattern).

The `POST /searches` pattern has an advantage for complex searches: the search itself becomes a resource that can be paginated, cached (by search ID), and shared. The trade-off: `POST` is not idempotent and not cached by default. For simple cases, `GET /resources?q=...` is preferred for cacheability.

## Section 7: Status Codes & Response Design

**Q24. What are the most important HTTP status codes and when is each appropriate?**
A: The commonly needed codes, grouped by meaning:

**2xx — Success**:
- `200 OK`: standard success for GET, PUT, PATCH — returns the resource.
- `201 Created`: resource was created (POST, sometimes PUT). Include `Location` header pointing to the new resource's URL.
- `204 No Content`: success with no response body — DELETE, or PUT/PATCH when the updated resource is not returned.
- `206 Partial Content`: response is a subset of the full resource (paginated or range-requested content).

**4xx — Client error**:
- `400 Bad Request`: malformed request syntax, invalid parameters — the request cannot be parsed or is structurally invalid.
- `401 Unauthorized`: authentication required and not provided (despite the name, this is authentication, not authorization).
- `403 Forbidden`: authenticated but not authorized — the server understood the request but refuses to execute it.
- `404 Not Found`: resource doesn't exist — also used to hide existence of protected resources (return 404 instead of 403 to avoid confirming the resource exists).
- `409 Conflict`: request conflicts with current resource state — e.g., creating a resource that already exists, concurrent modification conflict.
- `410 Gone`: resource existed but was permanently deleted — more specific than 404 for intentional removal.
- `422 Unprocessable Entity`: the request is syntactically valid but semantically invalid — e.g., a business rule validation failure (order quantity cannot be negative).
- `429 Too Many Requests`: rate limit exceeded. Include `Retry-After` header.

**5xx — Server error**:
- `500 Internal Server Error`: unexpected server failure — never expose stack traces or internal details.
- `503 Service Unavailable`: server is temporarily unable to handle requests (overload, maintenance). Include `Retry-After` if recovery time is known.

**Q25. What is the "200 OK for everything" anti-pattern and why is it harmful?**
A: The "200 OK for everything" anti-pattern returns HTTP 200 for all responses — including errors — and encodes success/failure in the response body:

```json
HTTP/1.1 200 OK
{
  "success": false,
  "error": "User not found",
  "code": 404
}
```

Harmful because: (1) **HTTP infrastructure is blind to errors** — caches cache the "error" response as if it were a valid resource, CDNs don't trigger error handling, load balancers can't detect backend failures; (2) **monitoring is broken** — error rate monitoring based on HTTP status codes shows 0% errors even when the application is returning business errors in every response; (3) **client code is more complex** — clients must parse every response body to determine success/failure instead of relying on the status code; (4) **retry logic fails** — middleware that auto-retries on 5xx never retries because everything is 200.

The correct pattern: use HTTP status codes semantically. Return `404` for not found, `400` for validation failures, `500` for server errors. The body can and should include structured error details (error code, message, documentation URL), but the HTTP status code must reflect the outcome.

**Q26. What should a well-structured error response body contain?**
A: A consistent, machine-parseable error format:

```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "No user with ID 123 exists",
    "details": [
      {
        "field": "id",
        "issue": "Resource does not exist"
      }
    ],
    "request_id": "req_abc123xyz",
    "documentation_url": "https://docs.example.com/errors/USER_NOT_FOUND"
  }
}
```

Key elements: (1) **machine-readable error code** (`USER_NOT_FOUND`, not a free-text message) — clients can programmatically switch on this; (2) **human-readable message** for debugging and display; (3) **field-level details** for validation errors (which field failed and why — essential for form rendering); (4) **request ID** — allows the client to report a specific failing request for server-side debugging; (5) **documentation URL** — links to how to fix the error. The `request_id` should also appear in the response headers (`X-Request-ID`) for correlation with server logs.

Never expose: stack traces, internal error messages, database query details, or server infrastructure information in error responses. These are security vulnerabilities and operational leaks.

## Section 8: Trade-offs & Decision-Making

**Q27. How do you handle resources with complex state machines (e.g., orders that can be approved, shipped, cancelled)?**
A: Three patterns, chosen based on complexity:

**Sub-resource actions** (best for simple state transitions):
```
POST /orders/{id}/approve
POST /orders/{id}/ship
POST /orders/{id}/cancel
```
Each transition is a POST to a verb-named sub-resource (controller pattern). The URL clearly communicates the action. This is the most readable pattern for a small number of transitions.

**PATCH with explicit state** (best for direct state updates):
```
PATCH /orders/{id}
Body: {"status": "shipped"}
```
Simple and REST-pure — the status is a field being updated. Downside: the server must validate that the transition is legal (can't ship an already-cancelled order). The HTTP layer doesn't communicate which transitions are allowed.

**Transition resource** (best for complex transitions with side effects or metadata):
```
POST /orders/{id}/transitions
Body: {"to": "shipped", "tracking_number": "1Z999AA1...", "carrier": "UPS"}
GET  /orders/{id}/transitions  # full transition history
```
The transition itself is a first-class resource with its own data (who approved, when, what tracking number was attached). Supports auditing and full transition history. More complex but appropriate when transitions carry rich metadata.

**Q28. How do you design bulk operations in a REST API?**
A: Bulk operations (creating, updating, or deleting many resources in one request) have several patterns:

**Bulk create**:
```
POST /users/bulk
Body: [{"name": "Alice", ...}, {"name": "Bob", ...}]
→ 207 Multi-Status with per-item results
```

**Bulk update**:
```
PATCH /users
Body: [{"id": 123, "status": "active"}, {"id": 456, "status": "inactive"}]
→ 207 Multi-Status
```

**Bulk delete**:
```
DELETE /users
Body: {"ids": [123, 456, 789]}
→ 207 Multi-Status or 204 No Content
```
Note: DELETE with a body is technically valid per HTTP spec but some clients and intermediaries don't support it. An alternative: `POST /users/deletions` with the ID list.

The `207 Multi-Status` response code is designed for this: it returns a body with per-item status codes, allowing partial success (some items created, some failed). For truly atomic bulk operations (all succeed or all fail), use a transaction semantics approach and return either `200`/`201` (all succeeded) or `400`/`422` (all failed) — never 207.

**Q29. How should you handle singleton sub-resources (a resource with exactly one instance per parent)?**
A: Use the singular form for sub-resources that have exactly one instance per parent:

```
GET  /users/{id}/profile        # a user has one profile
PUT  /users/{id}/profile        # replace the profile
PATCH /users/{id}/profile       # update the profile
DELETE /users/{id}/profile      # remove the profile

GET  /organizations/{id}/settings   # one settings document per org
GET  /devices/{id}/location         # current location of a device
```

Singleton sub-resources use singular form (not `profiles` or `locations`) because there is no collection to enumerate — `GET /users/{id}/profiles` implies there could be multiple profiles. The absence of an ID segment (no `/{profile_id}`) further signals there's only one. `PUT` is preferred over `PATCH` for replacing a singleton entirely; `PATCH` for partial updates. `POST /users/{id}/profile` for initial creation if the singleton can be absent (not yet created).

**Q30. What is HATEOAS and how much of it should a practical REST API implement?**
A: HATEOAS (Hypermedia as the Engine of Application State) is the REST constraint requiring that responses include hyperlinks to available actions — the client discovers what it can do next from the response itself, rather than having this knowledge baked in. A fully HATEOAS response:

```json
{
  "id": 123,
  "status": "pending",
  "_links": {
    "self": {"href": "/orders/123"},
    "approve": {"href": "/orders/123/approve", "method": "POST"},
    "cancel": {"href": "/orders/123/cancel", "method": "POST"},
    "items": {"href": "/orders/123/items"}
  }
}
```

The client uses the `_links` to determine what actions are available (if `"cancel"` is not in `_links`, the client knows cancellation is not allowed for this order's current state).

Practical reality: full HATEOAS is rarely implemented because: (1) it requires significant client investment to consume dynamically (most clients are statically typed and have the URLs hardcoded); (2) the tooling ecosystem (OpenAPI, Postman, code generators) is built around static URL documentation, not runtime discovery; (3) the benefits (client-server decoupling, self-discovery) are rarely needed by teams who control both client and server.

The pragmatic recommendation: include `self` links always (helps clients construct references), include links for related resources (`next_page`, `items`, `user`), and include available action links for state-dependent operations. Skip full HATEOAS unless building a truly public API intended to be consumed by clients you don't control with no prior URL knowledge.

## Section 9: Scenario / System Design Style Questions

**Q31. "Review this API design and identify all naming violations: `POST /api/getUser?id=123`, `GET /api/updateEmail`, `POST /api/v1/user/Delete/456`, `GET /orders/list?userId=123`."**
A: Violations in each:

`POST /api/getUser?id=123`:
- Verb in URL (`getUser`) — should be the resource noun.
- Wrong HTTP method: GET is safe/idempotent; retrieving a user should be `GET`.
- ID in query parameter instead of path segment: `/users/123`.
- Correct form: `GET /api/v1/users/123`.

`GET /api/updateEmail`:
- Verb in URL (`updateEmail`) — encodes the action in the path.
- Wrong HTTP method: updating a resource is not a safe operation; use PATCH or PUT.
- No resource identifier — which user's email?
- Correct form: `PATCH /api/v1/users/{id}` with body `{"email": "new@example.com"}` or `PATCH /api/v1/users/{id}/email`.

`POST /api/v1/user/Delete/456`:
- Verb in URL (`Delete`) — and capitalized, violating lowercase convention.
- Wrong HTTP method: deletion should use DELETE.
- Singular `user` — should be plural `users`.
- The ID comes after the verb, not after the resource noun.
- Correct form: `DELETE /api/v1/users/456`.

`GET /orders/list?userId=123`:
- Redundant verb in URL (`list`) — a GET to a collection path is already a list operation.
- `userId` as a query parameter is acceptable (filtering), but the URL with `/list` is redundant.
- Correct form: `GET /orders?user_id=123` or `GET /users/123/orders`.

**Q32. "Design the URL structure for a project management API with: users, organizations, projects (belonging to orgs), tasks (belonging to projects), and comments (on tasks)."**
A: Applying nesting depth limit (max 2 levels) and the nest-vs-query-param rule:

**Users** (independent resource):
```
GET    /users             # list users
POST   /users             # create user
GET    /users/{user_id}   # get user
PATCH  /users/{user_id}   # update user
DELETE /users/{user_id}   # delete user
```

**Organizations** (independent resource):
```
GET    /organizations
POST   /organizations
GET    /organizations/{org_id}
PATCH  /organizations/{org_id}
DELETE /organizations/{org_id}
GET    /organizations/{org_id}/members      # org membership
POST   /organizations/{org_id}/members     # add member
DELETE /organizations/{org_id}/members/{user_id}
```

**Projects** (belongs to org, but also independently addressable):
```
GET    /projects?org_id={org_id}     # filter by org (canonical)
POST   /organizations/{org_id}/projects  # create project within org
GET    /projects/{project_id}        # canonical project address
PATCH  /projects/{project_id}
DELETE /projects/{project_id}
```

**Tasks** (belongs to project):
```
GET    /tasks?project_id={project_id}
POST   /projects/{project_id}/tasks  # create task within project
GET    /tasks/{task_id}              # canonical task address
PATCH  /tasks/{task_id}
DELETE /tasks/{task_id}
POST   /tasks/{task_id}/assign       # assign task (controller pattern)
POST   /tasks/{task_id}/complete     # mark complete
```

**Comments** (on tasks — 3 levels deep avoided by making comments independently addressable):
```
GET    /comments?task_id={task_id}
POST   /tasks/{task_id}/comments     # create comment on task (2 levels)
GET    /comments/{comment_id}        # canonical comment address
PATCH  /comments/{comment_id}
DELETE /comments/{comment_id}
```

Note: `GET /organizations/1/projects/2/tasks/3/comments` (6 levels deep) is avoided by keeping comments' canonical address at `/comments/{id}` and using query params for filtering by parent.

**Q33. "A team is building an API for a payment system. They propose: `POST /api/makePayment`, `GET /api/getBalance`, `POST /api/refundPayment`, `POST /api/checkTransactionStatus`. Redesign this."**
A: The original is entirely RPC-over-HTTP. Redesigned:

**Payments** (the core transactional resource):
```
POST   /payments                    # initiate a payment (was /makePayment)
GET    /payments/{payment_id}       # get payment details + status
GET    /payments?account_id={id}    # list payments for an account
```

**Status is a property of the payment**, not a separate endpoint:
```
GET /payments/{payment_id}          # response includes "status": "completed"
# was /checkTransactionStatus — status is just a field on the payment resource
```

**Refunds** (a sub-resource or action):
```
POST   /payments/{payment_id}/refund   # initiate refund (was /refundPayment)
GET    /refunds/{refund_id}            # get refund status
GET    /payments/{payment_id}/refunds  # list refunds for a payment
```

**Balances** (a singleton sub-resource of an account):
```
GET    /accounts/{account_id}/balance  # current balance (was /getBalance)
GET    /accounts/{account_id}/balance/history  # balance history
```

**Idempotency**: `POST /payments` must accept an `Idempotency-Key` header — retrying a failed payment creation must not double-charge. The server stores the response keyed on the idempotency key and returns the cached response for duplicate requests.

**Q34. "Your team is debating whether to use URL versioning (`/v1/`) or header versioning (`API-Version: 1`). Make the case for each and give your recommendation."**
A: **Case for URL versioning**:
- Explicit and visible — developers immediately see which version they're using from the URL.
- Trivial to route — API gateways, load balancers, and CDNs route on URL path natively.
- Easy to test — `curl https://api.example.com/v2/users` needs no extra headers.
- Easy to document — OpenAPI specs can use the base URL to indicate version.
- Browser-friendly — users can navigate to versioned endpoints in a browser.
- De facto industry standard — Stripe, Twilio, GitHub, Slack, AWS all use URL versioning.

**Case for header versioning**:
- REST-pure — the resource's canonical URL doesn't change between versions (`/users/123` is always `/users/123`); only the representation changes.
- Cleaner client code — the base URL is stable; updating the version requires changing one header value, not restructuring all URL-building code.
- Supports content negotiation — `Accept: application/vnd.myapi.v2+json` aligns with HTTP's built-in negotiation mechanism.
- Easier to deprecate specific versions without URL redirects.

**Recommendation**: URL versioning for public, developer-facing APIs. The toolability, visibility, and industry familiarity outweigh the purity argument. Header versioning for internal APIs or cases where URL stability is a hard requirement (when URLs are stored as canonical identifiers in external systems). Whichever you choose: be consistent across the entire API, document the versioning strategy in the API's root documentation page, and implement `Deprecation` + `Sunset` headers from day one.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                        | Correct Pattern                                         | Anti-Pattern                                              |
|---                            |---                                                      |---                                                        |
| Resource identification       | Noun: `GET /users/123`                                  | Verb: `GET /getUser?id=123`                               |
| Collection URL                | Plural: `/users`, `/orders`                             | Mixed: `/user`, `/getOrders`                              |
| URL casing                    | Lowercase kebab: `/user-profiles`                       | camelCase: `/userProfiles`, mixed case: `/User_Profiles`  |
| Nesting depth                 | Max 2 levels: `/users/{id}/orders`                      | Deep: `/orgs/{id}/depts/{id}/teams/{id}/members/{id}`     |
| HTTP method for read          | `GET /resources/{id}`                                   | `POST /getResource`                                       |
| HTTP method for create        | `POST /resources`                                       | `GET /createResource` or `POST /createResource`           |
| HTTP method for replace       | `PUT /resources/{id}`                                   | `POST /updateResource`                                    |
| HTTP method for partial update| `PATCH /resources/{id}`                                 | `POST /patchResource` or `PUT` with partial body          |
| HTTP method for delete        | `DELETE /resources/{id}`                                | `POST /deleteResource` or `GET /delete?id=123`            |
| State transitions             | `POST /orders/{id}/cancel`                              | `PUT /orders/{id}` with `{"action":"cancel"}` in body     |
| Error codes                   | Semantic HTTP status (404, 422, 500)                    | `200 OK` with `{"success":false}` in body                 |
| Versioning                    | `/v1/users` or `API-Version: 1` header                  | No versioning; changing URLs breaking clients             |
| Filtering                     | `GET /orders?status=pending`                            | `GET /orders/pending` (status value in path segment)      |
| Pagination                    | `GET /users?cursor=xyz&limit=20`                        | `GET /users/page/2`                                       |
| Internal structure exposure   | `/users/123`                                            | `/mysql/users/table/123` or `/service-user/api/get`       |

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Resource                      | A named concept that can be addressed and manipulated via a URL — the noun of REST                           |
| Uniform interface             | REST constraint: URIs identify resources, HTTP methods are the verbs, representations are self-describing   |
| Safe method                   | HTTP method with no server-side effects (GET, HEAD, OPTIONS) — safe to call repeatedly without consequences |
| Idempotent method             | Same request N times = same result as once (GET, PUT, DELETE) — safe to retry on failure                   |
| Controller resource           | Sub-resource representing an action/transition: `POST /orders/{id}/cancel`                                  |
| Singleton sub-resource        | A sub-resource with exactly one instance per parent: `GET /users/{id}/profile` (not `/profiles`)           |
| Canonical URL                 | The single definitive address for a resource; aliases should redirect to or mirror it                       |
| HATEOAS                       | Hypermedia as the Engine of Application State — responses include links to available actions                |
| Chatty API                    | Requires many sequential requests to accomplish one user action; causes high latency                        |
| God endpoint                  | One URL handles all operations; breaks caching, monitoring, and documentation                               |
| RPC disguised as REST         | Verb URLs, POST for everything, semantic status codes ignored — HTTP used as a transport, not a protocol    |
| Versioning via URL            | `/v1/`, `/v2/` prefix — explicit, visible, easy to route; most common in public APIs                       |
| Breaking change               | Any API change requiring clients to modify their code: removing fields, changing types, renaming URLs       |
| `207 Multi-Status`            | HTTP status for bulk operations with per-item results — allows partial success                              |
| Idempotency key               | Client-generated unique ID in a request header; server uses it to deduplicate non-idempotent POST requests |
| `Sunset` header               | RFC 8594 header announcing when an API version will stop being available                                    |
| Enumerable IDs                | Sequential integer IDs that expose record count and insertion order; mitigated by UUIDs or hash IDs         |
| Kebab-case                    | Lowercase words separated by hyphens: `user-profile`, `order-items` — conventional for URL paths            |
| Sparse fieldsets              | `?fields=id,name,email` to request only needed fields — reduces payload, saves bandwidth                   |
| `422 Unprocessable Entity`    | Syntactically valid request but fails business rule validation; preferred over 400 for semantic errors      |

**Tip for the interview:** REST naming questions reveal whether candidates have designed APIs that real teams had to live with over years, or just built toy projects. The depth interviewers probe: the difference between `400` and `422` (structural vs. semantic validation failure), why `POST /getUser` is wrong on two levels (verb AND method), and the segment-vs-query-parameter rule (path = identity, query = filter). For senior roles, expect questions about versioning trade-offs (URL vs. header), how to handle state machines without RPC-style verbs (`/orders/{id}/cancel`), and how to design for idempotency (idempotency keys for POST, `ZADD GT` equivalent for PUT). The clearest signal of experience: knowing that API design is a public contract and that naming mistakes made at launch are extraordinarily expensive to fix.
