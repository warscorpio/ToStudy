# Socket.io: Rooms, Namespaces, Events, Acknowledgements — Interview Q&A (5 YOE Level)

---

## Section 1: Foundations

**Q1. What is Socket.io, and what problem does it solve that plain WebSockets don't?**
A: Socket.io is a real-time communication library built on top of WebSockets (with automatic fallback to HTTP long-polling) that adds a structured event system, automatic reconnection, room-based broadcasting, namespace isolation, acknowledgement callbacks, and horizontal scaling support. It solves several problems that raw WebSocket APIs leave to the developer:

**Reliability:** WebSockets are a thin transport — if the connection drops, the client is simply disconnected. Socket.io automatically reconnects with configurable backoff, transparently re-establishing the connection without the application needing to implement reconnection logic. It also handles the initial connection when WebSockets are unavailable (firewalls, older proxies) by falling back to HTTP long-polling, upgrading to WebSocket when possible.

**Structure:** A raw WebSocket sends and receives binary or text frames with no inherent message structure — distinguishing message types requires application-level framing (usually JSON with a `type` field). Socket.io provides a named event system where both client and server emit typed events (`socket.emit('order:update', payload)`) that the other side listens to by name (`socket.on('order:update', handler)`). This is multiplexing over a single connection without manual framing.

**Broadcasting:** WebSockets are point-to-point — a message goes to one client. Broadcasting to multiple clients requires the server to iterate over all connections and send individually. Socket.io's room system enables `io.to('room-name').emit(...)` — broadcasting to all sockets in a room with a single call, and the library handles the iteration and fan-out.

**Scaling:** A raw WebSocket server cannot easily broadcast to clients connected to a different server process. Socket.io's adapter pattern (Redis adapter, Postgres adapter) enables pub-sub between server instances so `io.to('room').emit(...)` reaches clients regardless of which server process they're connected to.

**Q2. What is the Socket.io transport upgrade process, and why does it matter for production deployments?**
A: Socket.io always begins with an HTTP long-polling connection, then attempts to upgrade to WebSocket. The upgrade sequence:

1. Client sends an HTTP GET to `/socket.io/?EIO=4&transport=polling`. The server responds with a session ID (`sid`) and a list of available upgrades.
2. Client begins HTTP long-polling: it sends GET requests that the server holds open until a message is available, then responds. This establishes the initial bidirectional communication.
3. Client attempts a WebSocket upgrade: sends an HTTP `Upgrade: websocket` request using the same `sid`.
4. If the server accepts the WebSocket upgrade, the client sends a probe packet over WebSocket. If the server echoes the probe, the WebSocket is established and the long-polling connection is closed.
5. If the WebSocket upgrade fails (network, proxy), the client continues long-polling without an error to the application layer.

Why this matters for production:

**Sticky sessions are required for long-polling:** during the polling phase, each HTTP request may hit a different server instance. But the server needs to maintain the polling session state. Without sticky sessions (all polling requests from a client routed to the same server), the server receiving the request won't find the session and will reject it. Sticky sessions must be configured at the load balancer level (`ip_hash` in nginx, `stickiness` in ALB) during the polling phase. Once upgraded to WebSocket, the connection is persistent — a single TCP connection — and sticky sessions are irrelevant for that connection's duration.

**`transports: ['websocket']` to skip polling:** if the deployment environment guarantees WebSocket support (all clients are modern browsers, no hostile proxies), configure the client with `transports: ['websocket']` to skip the polling phase entirely. This eliminates the sticky session requirement and reduces connection establishment time.

**Q3. What is the Socket.io protocol, and how does it differ from the WebSocket protocol?**
A: The WebSocket protocol (RFC 6455) provides a full-duplex binary or text frame transport over TCP. It is deliberately minimal — frames have no semantic meaning beyond being sent and received. The application defines everything above the frame level.

Socket.io's protocol (currently Engine.IO v4 + Socket.IO v5) is a message format layered on top of the WebSocket transport (or HTTP polling):

**Engine.IO layer** (transport-agnostic):
```
Packet type (1 char): 0=open, 1=close, 2=ping, 3=pong, 4=message, 5=upgrade, 6=noop
Payload: the data for that packet type
Example: "4hello" = message packet containing "hello"
```

**Socket.IO layer** (semantic layer, on top of Engine.IO message packets):
```
Packet type (digit): 0=CONNECT, 1=DISCONNECT, 2=EVENT, 3=ACK, 4=CONNECT_ERROR, 5=BINARY_EVENT, 6=BINARY_ACK
Namespace (optional): "/chat" or "/" (default)
Event name + data: ["eventName", ...args] (JSON-encoded)
Ack ID (optional): integer for acknowledgement correlation

Example socket.io packet: 2["order:update",{"orderId":"123","status":"shipped"}]
= type 2 (EVENT), namespace "/" (default), event "order:update", data {...}

With ack: 2426["create:order",{"amount":100}]
= type 2 (EVENT), ack ID 426, event "create:order"

Ack response: 3426[{"success":true,"orderId":"456"}]
= type 3 (ACK), ack ID 426, ack data
```

The key difference: Socket.io messages carry semantic meaning (event names, namespaces, ack IDs) that plain WebSocket frames don't. A Socket.io client cannot directly communicate with a plain WebSocket server and vice versa — the protocols are incompatible at the message level.

## Section 2: Events

**Q4. How does Socket.io's event system work, and what are the reserved event names?**
A: Socket.io uses an EventEmitter-style pattern where both server and client can emit named events and register handlers for named events. The API is symmetric:

```javascript
// Server side
io.on('connection', (socket) => {
  // Emit an event to this specific client
  socket.emit('welcome', { message: 'Connected successfully', socketId: socket.id });

  // Listen for events from this client
  socket.on('chat:message', (data) => {
    console.log('Received message:', data);
  });

  // Listen for disconnection
  socket.on('disconnect', (reason) => {
    console.log('Client disconnected:', reason);
  });
});
```

```javascript
// Client side
const socket = io('https://api.example.com');

// Listen for events from server
socket.on('welcome', (data) => {
  console.log(data.message);
});

// Emit events to server
socket.emit('chat:message', { text: 'Hello world', userId: currentUserId });

// Built-in lifecycle events
socket.on('connect',           () => console.log('Connected'));
socket.on('disconnect',        (reason) => console.log('Disconnected:', reason));
socket.on('connect_error',     (err) => console.error('Connection error:', err));
socket.on('reconnect',         (attempt) => console.log('Reconnected after', attempt, 'attempts'));
socket.on('reconnect_attempt', (attempt) => console.log('Reconnecting, attempt', attempt));
socket.on('reconnect_error',   (err) => console.error('Reconnect error:', err));
socket.on('reconnect_failed',  () => console.error('Reconnection failed permanently'));
```

Reserved event names — these are owned by Socket.io and cannot be used as application event names:
- **Server-side:** `connection` (new client connected), `disconnect`, `error`
- **Client-side:** `connect`, `disconnect`, `connect_error`, `reconnect`, `reconnect_attempt`, `reconnect_error`, `reconnect_failed`
- **Both sides:** `ping`, `pong`, `newListener`, `removeListener`

Using reserved names for application events is a common bug — `socket.emit('connect', data)` on the client does nothing meaningful because the client's `connect` event is fired by the library internally, not receivable from server emissions.

**Q5. What is event multiplexing, and how does it differ from having multiple WebSocket connections?**
A: Event multiplexing means multiple distinct event channels share a single underlying WebSocket connection. A Socket.io client has one TCP connection to the server regardless of how many event types it subscribes to. `socket.on('order:update', ...)` and `socket.on('chat:message', ...)` both receive events over the same connection — the Socket.io protocol's event name field routes incoming packets to the correct handler.

The alternative — a separate WebSocket connection per event type — would be wasteful and impractical: each connection has its own TCP handshake, TLS negotiation, and server-side memory allocation. A browser with 10 separate WebSocket connections for 10 event types would consume 10× the resources of a single multiplexed connection.

Event naming conventions that encode semantics:
```javascript
// Flat naming — unclear scope
socket.on('update', handler)        // update of what?
socket.on('message', handler)       // from where?

// Namespaced naming — clear scope
socket.on('order:status:update', handler)
socket.on('chat:room:message', handler)
socket.on('notification:payment:received', handler)

// Versioned naming — for evolving APIs
socket.on('v2:order:update', handler)
```

The naming convention is just a string — Socket.io doesn't enforce structure. But `entity:action` or `entity:event` is the most widely adopted convention in production systems.

**Q6. How do you handle event validation and typing in a Node.js + TypeScript production system?**
A: Without validation, every incoming event is `any` — a source of runtime bugs that TypeScript can't catch. Production systems should validate event payloads at the socket boundary:

```typescript
// events.ts — centralized event type definitions
import { z } from 'zod';

// Define schemas for each event's payload
export const ChatMessageSchema = z.object({
  text:      z.string().min(1).max(2000),
  roomId:    z.string().uuid(),
  userId:    z.string().uuid(),
  clientId:  z.string().uuid(),  // client-generated idempotency key
});

export const OrderUpdateSchema = z.object({
  orderId:   z.string().uuid(),
  status:    z.enum(['pending', 'confirmed', 'shipped', 'delivered', 'cancelled']),
  updatedAt: z.string().datetime(),
});

// Server-to-client events (what the server can emit)
export interface ServerToClientEvents {
  'chat:message':        (payload: z.infer<typeof ChatMessageSchema>) => void;
  'order:status:update': (payload: z.infer<typeof OrderUpdateSchema>) => void;
  'notification':        (payload: { type: string; message: string }) => void;
  'error':               (payload: { code: string; message: string }) => void;
}

// Client-to-server events (what the client can emit)
export interface ClientToServerEvents {
  'chat:send':       (payload: unknown, ack: AckCallback) => void;
  'order:subscribe': (payload: unknown, ack: AckCallback) => void;
  'order:cancel':    (payload: unknown, ack: AckCallback) => void;
}

type AckCallback = (response: AckResponse) => void;
type AckResponse = { success: true; data?: unknown } | { success: false; error: string; code: string };

// Typed socket server
import { Server } from 'socket.io';
const io = new Server<ClientToServerEvents, ServerToClientEvents>();
```

```typescript
// server.ts — validated event handler
import { io } from './socketServer';
import { ChatMessageSchema, AckResponse } from './events';

io.on('connection', (socket) => {

  socket.on('chat:send', (rawPayload: unknown, ack: (res: AckResponse) => void) => {
    // Validate incoming payload before touching it
    const result = ChatMessageSchema.safeParse(rawPayload);

    if (!result.success) {
      return ack({
        success: false,
        error:   'Invalid payload',
        code:    'VALIDATION_ERROR',
      });
    }

    const payload = result.data;  // fully typed, validated

    // Process the message
    try {
      io.to(payload.roomId).emit('chat:message', payload);
      ack({ success: true });
    } catch (err) {
      ack({
        success: false,
        error:   'Failed to send message',
        code:    'INTERNAL_ERROR',
      });
    }
  });
});
```

This pattern — `unknown` incoming, Zod validate, typed access — is the correct production approach. Trusting incoming Socket.io event data without validation is equivalent to trusting user-submitted HTTP form data without validation.

## Section 3: Rooms

**Q7. What is a Socket.io room, and how does it differ from a namespace?**
A: A room is a named channel within a namespace that sockets can join and leave dynamically. Rooms are server-side only — the client has no direct API to join rooms; the server controls which rooms a socket belongs to. Multiple sockets can be in the same room; a socket can be in multiple rooms simultaneously.

The key distinction from namespaces:
- **Namespace** — a connection-level grouping. A client explicitly connects to a namespace using a separate socket instance. Namespaces are separate connection endpoints (`/chat`, `/notifications`). A client in one namespace cannot receive events from another namespace.
- **Room** — a broadcast grouping within a namespace. A client connects once to a namespace; the server then uses rooms to control who receives specific broadcasts. Rooms have no corresponding client connection concept — they're purely a server-side routing abstraction.

```
io (default namespace "/")
  ├── room: "order-99123"     ← sockets subscribed to this order's updates
  ├── room: "user-user42"     ← the socket(s) for user 42
  └── room: "global"          ← all authenticated sockets

io.of('/notifications')       ← separate namespace
  └── room: "tier-premium"    ← premium user notifications
```

Every socket automatically joins a room named after its own `socket.id`. This is how the server sends events to a specific socket: `io.to(socket.id).emit(...)` uses the auto-room.

**Q8. Show the complete API for joining, leaving, and broadcasting to rooms, including the common patterns.**
A:

```javascript
// server.js — room operations

io.on('connection', (socket) => {

  // JOIN a room — server-side only
  socket.join('order-99123');
  socket.join(['room-a', 'room-b', 'room-c']);   // join multiple at once

  // LEAVE a room
  socket.leave('order-99123');

  // LIST rooms this socket is in
  console.log(socket.rooms);
  // Set { 'abc123' (own socket id), 'order-99123', 'user-42' }

  // ------- BROADCASTING -------

  // Emit to ALL sockets in a room (including the sender)
  io.to('order-99123').emit('order:update', { status: 'shipped' });

  // Emit to ALL sockets in a room EXCEPT the sender
  socket.to('order-99123').emit('order:update', { status: 'shipped' });

  // Emit to multiple rooms at once (union of all sockets in all rooms)
  io.to('room-a').to('room-b').emit('announcement', { text: '...' });

  // Emit to ALL sockets in a room EXCEPT those in another room
  io.to('all-users').except('muted-users').emit('broadcast', { text: '...' });

  // Emit to ALL connected sockets (across all rooms)
  io.emit('server:announcement', { text: 'Scheduled maintenance in 5 minutes' });

  // Emit to all sockets EXCEPT the sender (broadcast)
  socket.broadcast.emit('user:joined', { userId: socket.data.userId });

  // Fetch all sockets in a room (for diagnostics, presence, etc.)
  const sockets = await io.in('order-99123').fetchSockets();
  console.log('Sockets in order room:', sockets.map(s => s.id));

  // Count sockets in a room
  const count = (await io.in('order-99123').fetchSockets()).length;

  // Disconnect all sockets in a room
  io.in('room-a').disconnectSockets(true);  // true = close underlying connection
});
```

Common room patterns:

**Per-user room** — join a room named after the user's ID on connection. This enables sending to a specific user regardless of which socket (tab, device) they're connected from:
```javascript
io.on('connection', (socket) => {
  const userId = socket.data.userId;   // set during auth middleware
  socket.join(`user:${userId}`);        // always in their own room
});

// Send to a specific user across all their connections
io.to(`user:${targetUserId}`).emit('notification', payload);
```

**Per-resource room** — join a room when subscribing to a resource's updates:
```javascript
socket.on('order:subscribe', (orderId, ack) => {
  socket.join(`order:${orderId}`);
  ack({ success: true });
});

socket.on('order:unsubscribe', (orderId) => {
  socket.leave(`order:${orderId}`);
});

// When the order updates, broadcast to all subscribers
function onOrderUpdated(order) {
  io.to(`order:${order.id}`).emit('order:update', order);
}
```

**Q9. How do rooms interact with the `except` modifier, and what is the common use case?**
A: The `except` modifier excludes a room (or list of rooms) from a broadcast that would otherwise include them:

```javascript
// Broadcast to all users except those who have muted notifications
io.to('all-users')
  .except('notification-muted')
  .emit('announcement', { text: 'New feature available' });

// Broadcast to a team except the specific member who triggered the event
// (their own socket is in both the team room and their personal room)
socket.to(`team:${teamId}`)
  .except(`user:${socket.data.userId}`)  // same as socket.broadcast but for rooms
  .emit('team:member:updated', payload);
```

The canonical use case is **presence broadcasting**: when user A joins a room, notify all others in the room but not user A themselves:

```javascript
io.on('connection', (socket) => {
  socket.on('room:join', (roomId) => {
    socket.join(roomId);

    // Tell everyone else in the room that this user joined
    socket.to(roomId).emit('presence:user:joined', {
      userId:   socket.data.userId,
      username: socket.data.username,
    });

    // Tell this user who is already in the room
    const existingSockets = await io.in(roomId).fetchSockets();
    const presentUsers = existingSockets
      .filter(s => s.id !== socket.id)
      .map(s => ({ userId: s.data.userId, username: s.data.username }));

    socket.emit('presence:users', { roomId, users: presentUsers });
  });
});
```

## Section 4: Namespaces

**Q10. What are namespaces for, and when should you create a new namespace vs a new room?**
A: A namespace is a named endpoint within the Socket.io server — a logical partitioning of the socket connection space. Clients must explicitly connect to a specific namespace using a separate socket instance. The default namespace is `/`.

```javascript
// Server — defining namespaces
const chatNamespace          = io.of('/chat');
const notificationsNamespace = io.of('/notifications');
const adminNamespace         = io.of('/admin');

// Each namespace has its own event handlers, middleware, and room isolation
chatNamespace.on('connection', (socket) => {
  console.log('Connected to /chat namespace:', socket.id);
  socket.on('message', handleChatMessage);
});

notificationsNamespace.on('connection', (socket) => {
  console.log('Connected to /notifications namespace:', socket.id);
});
```

```javascript
// Client — connecting to different namespaces (separate socket instances)
const chatSocket          = io('https://api.example.com/chat');
const notificationSocket  = io('https://api.example.com/notifications');

// These are two independent socket connections, each with their own lifecycle
chatSocket.on('message', handleMessage);
notificationSocket.on('notification', handleNotification);
```

**Namespace vs room — the decision:**

Create a **namespace** when:
- Different parts of your application have entirely different event contracts (chat vs notifications vs admin) and should not accidentally receive each other's events.
- You need different middleware (authentication, rate limiting) per logical domain — middleware is applied per-namespace.
- You want clean separation of concerns at the server code level — each namespace has its own `io.of('/namespace').on('connection', ...)` handler.
- The event sets are large enough that having them all in one namespace would be confusing.

Use **rooms** (within one namespace) when:
- Clients need to subscribe to different subsets of events within the same logical domain (different order IDs, different chat rooms, different user feeds).
- Membership is dynamic — clients join and leave at runtime based on user actions.
- The event types are the same; what differs is who receives them.

Rule of thumb: **namespaces are for architectural separation; rooms are for dynamic routing.** A real-world app might have one namespace per major product area (`/app`, `/admin`) with rooms for dynamic subscriptions within each.

**Q11. How do you apply middleware to a namespace, and what does authentication middleware look like in practice?**
A: Namespace middleware runs once per connection attempt, before the `connection` event fires. It has access to the socket's handshake data (headers, query params, auth token) and can either allow the connection or reject it with an error:

```javascript
// auth-middleware.ts — JWT authentication for socket connections
import jwt from 'jsonwebtoken';
import { Socket } from 'socket.io';

interface AuthHandshake {
  auth: { token?: string };
  headers: Record<string, string>;
}

async function authMiddleware(socket: Socket, next: (err?: Error) => void) {
  // Token can come from: socket.handshake.auth.token (preferred)
  // or Authorization header (for environments where auth object isn't available)
  const token = socket.handshake.auth?.token
    ?? extractBearerToken(socket.handshake.headers.authorization);

  if (!token) {
    return next(new Error('AUTHENTICATION_REQUIRED'));
  }

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET!) as JwtPayload;

    // Attach user data to socket for use in event handlers
    socket.data.userId   = payload.sub;
    socket.data.username = payload.username;
    socket.data.roles    = payload.roles;

    next();  // allow connection
  } catch (err) {
    if (err instanceof jwt.TokenExpiredError) {
      next(new Error('TOKEN_EXPIRED'));
    } else {
      next(new Error('INVALID_TOKEN'));
    }
  }
}

function extractBearerToken(authHeader?: string): string | undefined {
  return authHeader?.startsWith('Bearer ') ? authHeader.slice(7) : undefined;
}

// Apply middleware to a namespace
io.of('/app').use(authMiddleware);
io.of('/admin').use(authMiddleware);
io.of('/admin').use(adminRoleMiddleware);  // chain multiple middleware
```

```javascript
// Client — sending auth token on connection
const socket = io('https://api.example.com/app', {
  auth: {
    token: localStorage.getItem('auth_token'),
  },
});

// Handle auth errors from middleware rejection
socket.on('connect_error', (err) => {
  if (err.message === 'TOKEN_EXPIRED') {
    // Refresh the token and reconnect
    refreshToken().then((newToken) => {
      socket.auth.token = newToken;
      socket.connect();  // manually reconnect with new token
    });
  } else if (err.message === 'AUTHENTICATION_REQUIRED') {
    redirectToLogin();
  }
});
```

**Dynamic namespaces** — matching any namespace matching a pattern:
```javascript
// Handle any namespace matching /room-{id}
const dynamicNamespace = io.of(/^\/room-\d+$/);

dynamicNamespace.on('connection', (socket) => {
  const namespace = socket.nsp.name;  // e.g., "/room-42"
  console.log('Connected to dynamic namespace:', namespace);
});
```

## Section 5: Acknowledgements

**Q12. What is an acknowledgement in Socket.io, and how does it differ from a request-response pattern over plain WebSockets?**
A: An acknowledgement (ack) is a callback-based mechanism that turns a normally fire-and-forget event emission into a request-response round trip. The emitter includes a callback function; the receiver calls that callback with a response. Socket.io tracks the ack ID in the protocol and routes the response back to the original callback.

Over plain WebSockets, implementing request-response requires: generating a unique correlation ID per message, including it in both request and response, maintaining a map of pending callbacks keyed by correlation ID, and implementing timeout logic. Socket.io's acknowledgement system handles all of this internally.

```javascript
// Server — receiving an event and sending an acknowledgement
socket.on('order:create', (payload, ack) => {
  // ack is a function provided by Socket.io if the client sent a callback
  // If the client didn't send a callback, ack is undefined — always check

  try {
    const order = createOrder(payload);
    ack({ success: true,  orderId: order.id });
  } catch (err) {
    ack({ success: false, error: err.message, code: 'CREATE_FAILED' });
  }
});

// Server — emitting an event and waiting for client's acknowledgement
// (the server can also request acks from clients)
socket.emit('server:challenge', { challengeToken: generateToken() }, (response) => {
  if (response?.verified) {
    socket.data.verified = true;
  }
});
```

```javascript
// Client — callback-style acknowledgement
socket.emit('order:create', { amount: 100, currency: 'USD' }, (response) => {
  if (response.success) {
    console.log('Order created:', response.orderId);
  } else {
    console.error('Order creation failed:', response.error);
  }
});
```

The critical operational detail: **if the server's event handler doesn't call `ack`, the client's callback never fires**. There is no built-in timeout — the callback waits indefinitely. This is a common source of silent hangs in Socket.io applications. Always call `ack` in every code path, including error handlers and early returns.

**Q13. How do you implement Promise-based acknowledgements in modern Socket.io (v4+)?**
A: Socket.io v4.6+ introduced `emitWithAck`, which wraps the callback-based ack in a Promise:

```typescript
// Client — Promise-based ack (Socket.io v4.6+)
try {
  const response = await socket.emitWithAck('order:create', {
    amount: 100,
    currency: 'USD',
  });

  if (response.success) {
    navigateTo(`/orders/${response.orderId}`);
  } else {
    showError(response.error);
  }
} catch (err) {
  // Fires if socket disconnects before ack arrives, or timeout exceeded
  showError('Request failed — connection lost');
}
```

```typescript
// Add timeout to prevent indefinite waiting
import { Socket } from 'socket.io-client';

async function emitWithTimeout<T>(
  socket: Socket,
  event: string,
  payload: unknown,
  timeoutMs = 5000
): Promise<T> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      reject(new Error(`Event '${event}' ack timed out after ${timeoutMs}ms`));
    }, timeoutMs);

    socket.emit(event, payload, (response: T) => {
      clearTimeout(timer);
      resolve(response);
    });
  });
}

// Usage
const response = await emitWithTimeout<OrderCreateResponse>(
  socket,
  'order:create',
  { amount: 100 },
  5000
);
```

Socket.io v4.6+ also supports server-side timeout on acks:
```javascript
// Server — emit to client with built-in timeout
try {
  const response = await socket
    .timeout(5000)
    .emitWithAck('client:verify', { challengeToken });
  console.log('Client verified:', response.verified);
} catch (err) {
  // Timeout — client didn't respond in 5 seconds
  socket.disconnect();
}
```

**Q14. What is the "missed ack" problem, and how does it relate to at-least-once delivery?**
A: The missed ack problem occurs when: the server emits an event with an ack callback, the client processes the event but the ack response is lost in transit (disconnection between ack send and server receipt), and the server's callback never fires. From the server's perspective, the event was not acknowledged — it cannot know if the client processed it.

This creates an at-most-once delivery scenario for server-to-client emissions: the server emits once; if the ack is lost, the event may never be retried. For events that are safe to re-send (idempotent), the server should implement retry logic:

```javascript
// Server — reliable emit with retry on ack timeout
async function reliableEmit(socket, event, payload, maxAttempts = 3, timeoutMs = 5000) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      const response = await socket.timeout(timeoutMs).emitWithAck(event, payload);
      return response;  // ack received
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      console.warn(`Ack timeout for ${event}, retrying (${attempt}/${maxAttempts})`);
      await sleep(Math.min(1000 * attempt, 5000));
    }
  }
}
```

For genuinely critical at-least-once delivery (a payment notification that must reach the client), Socket.io's ack mechanism is insufficient on its own — the client could disconnect and reconnect with a new socket ID, losing any in-flight acks. Production solutions for critical delivery use:

- **Persistent message queue** — store the event in a database before emitting. On reconnect, the server queries for unacknowledged events and re-emits them to the new socket.
- **Client-side reconnection fetch** — on reconnect, the client explicitly fetches any events it may have missed (REST endpoint returns missed notifications since `lastReceivedEventId`).
- **Kafka/Redis streams as source of truth** — socket emission is a delivery mechanism, not a storage mechanism. The event lives in a durable queue; socket delivery is best-effort with fallback to polling.

## Section 6: Scaling

**Q15. How do you scale Socket.io across multiple server instances, and what is the adapter pattern?**
A: A single Socket.io server process holds all socket connections and room memberships in memory. When `io.to('order-99123').emit(...)` is called, it iterates over in-memory socket references and delivers the event. This breaks when clients are distributed across multiple server processes — `io.to('order-99123')` on process A only sees sockets connected to process A, missing sockets connected to processes B and C.

The adapter pattern solves this: an adapter is a pub-sub intermediary that, when process A emits to a room, publishes the emission to a shared channel (Redis pub-sub, a Postgres notification, a Kafka topic). All other server processes subscribe to the channel; they receive the emission and deliver it to their local sockets in that room.

**Redis adapter (most common):**
```javascript
// server.js — Redis adapter for horizontal scaling
import { Server } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const pubClient = createClient({ url: process.env.REDIS_URL });
const subClient = pubClient.duplicate();

await Promise.all([pubClient.connect(), subClient.connect()]);

const io = new Server(httpServer, {
  adapter: createAdapter(pubClient, subClient),
  // Sticky sessions still needed for the polling transport upgrade phase
});

// Now io.to('room').emit() works correctly across all server instances
// The Redis adapter publishes to a channel; all processes deliver locally
```

**What the Redis adapter does:**
1. Process A calls `io.to('order-99123').emit('update', data)`.
2. The adapter serializes the emission and publishes it to Redis channel `socket.io#/order-99123#`.
3. All processes (including A) subscribed to that channel receive the message.
4. Each process delivers the event to its locally-connected sockets in room `order-99123`.
5. Sockets on process A receive the event directly; sockets on processes B and C receive it via Redis pub-sub.

**Room membership and `fetchSockets` with adapters:**
`io.in('room').fetchSockets()` returns all sockets in the room across all server instances when using the Redis adapter. The adapter queries all processes for their local socket lists and aggregates the results. `io.in('room').socketsJoin('another-room')` also works across processes — the adapter broadcasts the join instruction to all processes.

**Q16. What is the `socket.io-sticky` approach vs the stateless adapter approach, and when do you need each?**
A: These solve overlapping but distinct scaling problems:

**Sticky sessions (required for HTTP long-polling):**
During the HTTP polling phase (before WebSocket upgrade), each request from a client must reach the same server process that holds its polling session. Load balancers route requests by session cookie, IP hash, or a custom header. This is a transport-layer requirement that exists only during the polling phase.

If `transports: ['websocket']` is configured on the client, the polling phase is skipped entirely and sticky sessions are not required — WebSocket connections are persistent and route to the same process naturally.

**Redis adapter (required for multi-process broadcasting):**
The adapter is needed whenever a server process must reach sockets connected to other processes — broadcasting to rooms, emitting to specific user sockets, `fetchSockets`, etc. This is a messaging requirement independent of the transport.

**Both can be needed simultaneously:**
```
Client → Load Balancer (sticky, for polling phase)
  → Server A (handles this client's WebSocket connection)
  → Redis (adapter, for cross-process emissions from Server B or C)
```

When `transports: ['websocket']` is used in a Kubernetes deployment where all clients connect directly to the WebSocket endpoint, sticky sessions can be dropped and only the Redis adapter is needed. This simplifies the load balancer configuration significantly.

## Section 7: Production Patterns

**Q17. How do you implement a presence system (who's online) using Socket.io rooms?**
A:

```typescript
// presence.ts — tracking online users across connections and reconnections

// Redis stores the source of truth for presence (handles multi-process)
import { redis } from './redis';
import { io } from './socketServer';

const PRESENCE_TTL_SECONDS = 30;  // auto-expire if heartbeats stop

async function userConnected(socket: Socket) {
  const userId = socket.data.userId;
  const roomId = socket.data.currentRoomId;

  // Add to Redis presence set with TTL-based expiry
  await redis.setex(`presence:user:${userId}`, PRESENCE_TTL_SECONDS, socket.id);
  await redis.sadd(`presence:room:${roomId}`, userId);

  // Join per-user room (for targeted emissions)
  socket.join(`user:${userId}`);
  socket.join(`room:${roomId}`);

  // Notify others in the room
  socket.to(`room:${roomId}`).emit('presence:joined', {
    userId,
    username: socket.data.username,
    joinedAt: new Date().toISOString(),
  });

  // Send current online users to the newly connected socket
  const onlineUserIds = await redis.smembers(`presence:room:${roomId}`);
  socket.emit('presence:current', { userIds: onlineUserIds });
}

async function userDisconnected(socket: Socket) {
  const userId = socket.data.userId;
  const roomId = socket.data.currentRoomId;

  // Check if user has other active connections (multiple tabs)
  const otherSockets = await io.in(`user:${userId}`).fetchSockets();
  const hasOtherConnections = otherSockets.some(s => s.id !== socket.id);

  if (!hasOtherConnections) {
    // Last connection — user is truly offline
    await redis.del(`presence:user:${userId}`);
    await redis.srem(`presence:room:${roomId}`, userId);

    io.to(`room:${roomId}`).emit('presence:left', {
      userId,
      disconnectedAt: new Date().toISOString(),
    });
  }
  // If other connections exist: user is still online, no presence change
}

io.on('connection', async (socket) => {
  await userConnected(socket);

  // Heartbeat to keep Redis presence TTL alive
  const heartbeatInterval = setInterval(async () => {
    await redis.expire(`presence:user:${socket.data.userId}`, PRESENCE_TTL_SECONDS);
  }, 10_000);  // every 10 seconds

  socket.on('disconnect', async () => {
    clearInterval(heartbeatInterval);
    await userDisconnected(socket);
  });
});
```

The multi-connection check (`io.in('user:userId').fetchSockets()`) is the critical piece — without it, a user with three browser tabs would appear offline when closing one tab, even though two connections remain. With the Redis adapter, `fetchSockets` aggregates across all server processes.

**Q18. How do you implement rate limiting on Socket.io events to prevent abuse?**
A:

```typescript
// rate-limiter.ts — per-socket, per-event rate limiting
import { RateLimiterRedis } from 'rate-limiter-flexible';
import { redis } from './redis';

// Different limits for different event types
const chatRateLimiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix:   'rl:chat',
  points:      10,       // 10 messages
  duration:    10,       // per 10 seconds
  blockDuration: 30,     // block for 30 seconds if exceeded
});

const subscribeRateLimiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix:   'rl:subscribe',
  points:      20,       // 20 subscription changes
  duration:    60,       // per 60 seconds
});

// Middleware factory for event-level rate limiting
function rateLimitMiddleware(limiter: RateLimiterRedis) {
  return async (socket: Socket, event: string, args: unknown[], next: () => void) => {
    try {
      await limiter.consume(`${socket.data.userId}`);
      next();
    } catch (rejRes) {
      // Rate limit exceeded
      const waitMs = Math.ceil((rejRes as any).msBeforeNext ?? 0);

      // If the last arg is an ack callback, call it with an error
      const lastArg = args[args.length - 1];
      if (typeof lastArg === 'function') {
        lastArg({
          success: false,
          error:   `Rate limit exceeded. Retry after ${Math.ceil(waitMs / 1000)}s.`,
          code:    'RATE_LIMITED',
          retryAfterMs: waitMs,
        });
      } else {
        socket.emit('error', {
          code:    'RATE_LIMITED',
          message: `Too many requests. Wait ${Math.ceil(waitMs / 1000)} seconds.`,
          event,
        });
      }
    }
  };
}

// Apply event-level middleware (Socket.io v4.6+ onAny middleware or manual)
io.on('connection', (socket) => {
  // Global rate limit: all events from this socket
  const globalLimiter = new RateLimiterRedis({
    storeClient: redis,
    keyPrefix:   'rl:global',
    points:      100,
    duration:    60,
  });

  socket.use(async ([event, ...args], next) => {
    try {
      await globalLimiter.consume(socket.data.userId);
      next();
    } catch {
      next(new Error('RATE_LIMITED'));
    }
  });

  // Per-event rate limiting
  socket.on('chat:send', async (payload, ack) => {
    try {
      await chatRateLimiter.consume(socket.data.userId);
      // process message
      ack({ success: true });
    } catch {
      ack({ success: false, error: 'Chat rate limit exceeded', code: 'RATE_LIMITED' });
    }
  });
});
```

**Q19. How do you handle Socket.io in a Next.js (or similar SSR framework) deployment where the server is frequently restarted?**
A: Server restarts are the enemy of stateful WebSocket connections — all connected clients are disconnected on restart. In a Next.js deployment (Vercel serverless, or a Node.js server with hot reload), Socket.io requires a persistent server process, not a serverless function.

Key considerations:

**Serverless is incompatible with WebSockets:**
Serverless functions (Vercel Edge Functions, AWS Lambda) are short-lived processes that terminate after handling one HTTP request. WebSocket connections require a persistent process. Socket.io cannot run in a serverless function. Solutions: use a separate, always-on WebSocket server (Railway, Fly.io, Render, an EC2 instance) alongside the serverless Next.js deployment, or use a managed WebSocket service (Ably, Pusher, Liveblocks) that provides a WebSocket server as a service.

**Next.js with a custom server:**
```javascript
// server.js — custom Next.js server with Socket.io
const { createServer } = require('http');
const { Server }       = require('socket.io');
const next             = require('next');

const app    = next({ dev: process.env.NODE_ENV !== 'production' });
const handle = app.getRequestHandler();

app.prepare().then(() => {
  const httpServer = createServer(handle);
  const io         = new Server(httpServer, {
    cors: {
      origin:      process.env.NEXT_PUBLIC_APP_URL,
      credentials: true,
    },
  });

  io.on('connection', (socket) => {
    // Socket.io logic here
  });

  httpServer.listen(3000, () => {
    console.log('Server running on :3000');
  });
});
```

**Graceful shutdown to minimize client disruption:**
```javascript
process.on('SIGTERM', async () => {
  console.log('SIGTERM received — graceful shutdown');

  // Notify connected clients before disconnecting
  io.emit('server:shutdown', {
    message:      'Server restarting. Reconnecting shortly.',
    reconnectIn:  3000,
  });

  // Give clients time to receive the message
  await sleep(1000);

  // Close Socket.io server (stops accepting new connections)
  io.close(() => {
    httpServer.close(() => {
      process.exit(0);
    });
  });
});
```

Socket.io clients automatically reconnect after a disconnection — the reconnection logic (exponential backoff, configurable attempts) handles server restarts transparently from the user's perspective, though there will be a brief connection gap.

## Section 8: Scenario Questions

**Q20. "Your Socket.io server is running on 4 instances behind a load balancer. Some clients report missing real-time updates. What's wrong and how do you fix it?"**
A: Missing updates in a multi-instance Socket.io deployment is almost always one of two issues:

**Issue 1 — No Redis adapter (most likely):**
When process A emits to a room, only sockets on process A receive the event. Sockets on processes B, C, D miss it. No error is thrown — the emission simply doesn't reach them. Diagnosis: check if `createAdapter` is configured. If `io.adapter()` returns the default in-memory adapter, that's the problem. Fix: add the Redis adapter as shown in Q15.

**Issue 2 — Missing sticky sessions during polling phase:**
A client using the polling transport sends sequential GET/POST requests. Without sticky sessions, request 1 hits process A (which creates the polling session), request 2 hits process B (which has no session for this client and creates a new one), resulting in duplicate sessions or dropped connections. The client appears connected but receives no events. Diagnosis: check the load balancer configuration. If round-robin routing is active with no session stickiness, this is the cause. Fix: enable sticky sessions at the load balancer, or configure clients with `transports: ['websocket']` to skip the polling phase.

**Verification approach:**
```javascript
// Diagnostic — log which process handles each connection
io.on('connection', (socket) => {
  console.log(`Socket ${socket.id} connected to process PID ${process.pid}`);
  socket.emit('debug:process', { pid: process.pid });
});

// If clients report missing events, add emission logging
socket.to('order-99123').emit('order:update', data);
console.log(`Emitted order:update to room order-99123 from PID ${process.pid}`);
// If this log appears on process A but clients on processes B-D don't receive,
// the adapter is missing.
```

**Q21. "Design the Socket.io architecture for a collaborative document editor where multiple users edit simultaneously."**
A: A collaborative editor requires real-time change broadcasting to all co-editors, presence tracking, and conflict resolution. The Socket.io layer:

**Namespaces and rooms:**
```
io.of('/editor')          ← single namespace for all editor connections
  ├── room: "doc:doc-123" ← all sockets editing document doc-123
  ├── room: "doc:doc-456"
  └── room: "user:{userId}" ← per-user room for targeted messages
```

**Events:**
```typescript
// Client → Server
'doc:join'       (docId: string, ack)                       → join document room, receive current state
'doc:operation'  (op: Operation, ack)                       → apply an edit operation
'doc:cursor'     (position: CursorPosition)                 → broadcast cursor position (no ack needed)
'doc:leave'      (docId: string)                            → leave document room

// Server → Client
'doc:state'      (state: DocumentState)                     → full document state on join
'doc:operation'  (op: Operation, fromUserId: string)        → operation from another user
'doc:cursor'     (userId: string, position: CursorPosition) → cursor update from another user
'presence:joined' (user: UserInfo)                          → another user joined
'presence:left'   (userId: string)                          → another user left
'doc:conflict'   (conflictedOp: Operation)                  → server rejected an operation
```

**Server implementation:**
```typescript
const editorNamespace = io.of('/editor');
editorNamespace.use(authMiddleware);

editorNamespace.on('connection', (socket) => {

  socket.on('doc:join', async (docId: string, ack) => {
    // Auth check: does this user have access to docId?
    const hasAccess = await documentService.checkAccess(socket.data.userId, docId);
    if (!hasAccess) {
      return ack({ success: false, error: 'Access denied', code: 'PERMISSION_DENIED' });
    }

    socket.join(`doc:${docId}`);
    socket.data.currentDocId = docId;

    // Send current document state to the newly joined user
    const docState = await documentService.getState(docId);
    socket.emit('doc:state', docState);

    // Notify others of the new co-editor
    socket.to(`doc:${docId}`).emit('presence:joined', {
      userId:   socket.data.userId,
      username: socket.data.username,
    });

    ack({ success: true, documentVersion: docState.version });
  });

  socket.on('doc:operation', async (op: Operation, ack) => {
    const docId = socket.data.currentDocId;
    if (!docId) return ack({ success: false, error: 'Not in a document' });

    try {
      // Apply operation via OT/CRDT engine — handles conflict resolution
      const transformedOp = await documentService.applyOperation(docId, op, socket.data.userId);

      // Broadcast the transformed operation to all co-editors EXCEPT sender
      socket.to(`doc:${docId}`).emit('doc:operation', transformedOp, socket.data.userId);

      ack({ success: true, appliedVersion: transformedOp.version });
    } catch (err) {
      if (err instanceof ConflictError) {
        ack({ success: false, error: 'Operation conflicted', code: 'CONFLICT', serverOp: err.serverOp });
      } else {
        ack({ success: false, error: 'Apply failed', code: 'INTERNAL_ERROR' });
      }
    }
  });

  // Cursor positions: fire-and-forget, no ack (high frequency, loss is acceptable)
  socket.on('doc:cursor', (position: CursorPosition) => {
    const docId = socket.data.currentDocId;
    if (docId) {
      socket.to(`doc:${docId}`).emit('doc:cursor', socket.data.userId, position);
    }
  });

  socket.on('disconnect', async () => {
    const docId = socket.data.currentDocId;
    if (docId) {
      editorNamespace.to(`doc:${docId}`).emit('presence:left', socket.data.userId);
    }
  });
});
```

The key design decisions: operations use acknowledgements (the server must confirm application and conflict resolution before the client advances); cursor positions use fire-and-forget (high frequency, loss is tolerable — a slight cursor position lag is acceptable; losing an operation is not).

## Quick Reference

**Socket.io API Cheat Sheet:**

```javascript
// === EMITTING ===
socket.emit('event', data)                    // to this socket only
io.to('room').emit('event', data)             // to all in room (incl. sender if in room)
socket.to('room').emit('event', data)         // to all in room EXCEPT sender
io.emit('event', data)                        // to ALL sockets everywhere
socket.broadcast.emit('event', data)          // to ALL sockets EXCEPT sender
io.to('a').to('b').emit('event', data)        // union of rooms a and b
io.to('all').except('muted').emit(...)        // room minus excluded room

// === ROOMS ===
socket.join('room')                           // join (server-side only)
socket.leave('room')                          // leave
socket.rooms                                  // Set of room names this socket is in
await io.in('room').fetchSockets()            // all sockets in room (cross-process with adapter)
io.in('room').socketsJoin('another')          // make all sockets in room join another room
io.in('room').socketsLeave('another')
io.in('room').disconnectSockets(true)

// === ACKNOWLEDGEMENTS ===
socket.emit('event', data, (response) => {})                      // callback ack
await socket.emitWithAck('event', data)                           // promise ack (v4.6+)
await socket.timeout(5000).emitWithAck('event', data)             // with timeout
socket.on('event', (data, ack) => { ack({ success: true }); })    // server receives + acks

// === MIDDLEWARE ===
io.use((socket, next) => { next() })          // server-level middleware
io.of('/ns').use((socket, next) => {})        // namespace middleware
socket.use(([event, ...args], next) => {})    // per-socket event middleware
```

**Room vs Namespace Decision:**

| Need | Use |
|--- |--- |
| Different auth/middleware per domain | Namespace |
| Different event contracts | Namespace |
| Dynamic subscription to resource updates | Room |
| Broadcast to a subset of users | Room |
| Send to a specific user (across tabs) | Room (`user:{userId}`) |
| Separate client connection per feature | Namespace |
| Group users who joined same chat room | Room |

**Common Failure Modes:**

| Symptom | Cause | Fix |
|--- |--- |--- |
| Client never receives ack | Server handler doesn't call `ack()` in some code path | Audit every `socket.on` that receives ack — ensure always called |
| Events missing in multi-server | No Redis adapter | Add `@socket.io/redis-adapter` |
| Polling fails on multi-server | No sticky sessions | Configure load balancer sticky sessions or use `transports: ['websocket']` |
| Connection drops on deploy | No graceful shutdown | Emit `server:shutdown` event, then close after delay |
| Auth token expired mid-stream | No reconnect token refresh | Handle `connect_error` with `TOKEN_EXPIRED` to refresh and reconnect |
| User appears offline when still connected | No multi-connection check on disconnect | Check `io.in('user:{id}').fetchSockets()` before marking offline |
| Broadcast storms on reconnect | All clients reconnect simultaneously after restart | Add jitter to client reconnect delay |

The strongest answers show you understand the production failure modes: what breaks when you add a second server process (missing adapter), why sticky sessions exist and when they can be dropped (polling phase only, skip with `transports: ['websocket']`), why acks always need to be called (the silent hang), and why presence tracking needs a Redis-backed check for multi-connection users (closing one tab shouldn't mark you offline). The war story format lands well: "we had a production incident where a user closing one tab showed as offline in a shared document even though they had two other tabs open — we were checking local socket count, not querying across all processes via `fetchSockets`.
