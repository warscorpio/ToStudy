# Long Polling: Implementation and Drawbacks — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Where Long Polling Fits

**Q1. What is long polling, how does it differ from regular polling, and what problem does it solve?**
A: Long polling is a technique for simulating server-push over HTTP by having the server hold a request open until it has data to send, rather than responding immediately with whatever it has (or nothing). It sits between two extremes:

**Regular (short) polling** — client asks repeatedly on a fixed interval:
```
Client: GET /updates  → Server: 200 { data: null }    (nothing new)
Client: GET /updates  → Server: 200 { data: null }    (nothing new)
Client: GET /updates  → Server: 200 { data: null }    (nothing new)
Client: GET /updates  → Server: 200 { data: event_1 } (finally something)
```
Every request incurs a full HTTP round-trip. If the poll interval is 1 second and events arrive once per minute, 59 of 60 requests return empty — 98% waste. If the interval is 30 seconds, events arrive up to 30 seconds late. There is no interval that is both efficient and low-latency simultaneously.

**Long polling** — server holds the request until data is available:
```
Client: GET /updates  
                      ← server holds this request open
                      ← (no response yet — event not happened)
                      ← (still holding...)
                      ← event_1 arrives on the server
Server: 200 { data: event_1 }   ← responds immediately when data is ready
Client: GET /updates  ← immediately opens a new long-poll request
                      ← (server holds again...)
```
The client sends a request; the server holds it open — blocking the response — until an event occurs or a timeout fires. When the server responds, the client immediately sends a new request. This gives near-real-time delivery (latency = server processing time + network RTT, not poll interval) while remaining pure HTTP/1.1 — no protocol upgrades, no persistent TCP beyond the held request.

**What it solves**: real-time data delivery on infrastructure that only supports HTTP/1.1 and cannot use WebSocket (corporate proxies that terminate WebSocket upgrades, environments where the client is HTTP-only, or fallback behavior when WebSocket is unavailable).

**Q2. Where does long polling sit in the spectrum of real-time techniques, and when is it the right choice today?**
A: The real-time technique spectrum, from simplest to most capable:

```
Short polling → Long polling → Server-Sent Events → WebSocket → gRPC streaming

Complexity:        low           medium               medium       high           highest
Infrastructure:    any HTTP      any HTTP             HTTP/1.1+    HTTP upgrade   HTTP/2
Browser support:   universal     universal            universal    universal      via gRPC-Web
Bidirectional:     no            no (HTTP)            no           yes            yes
Connection reuse:  no            no (new per event)   yes          yes            yes
Server resources:  low (brief)   high (held open)     medium       medium         medium
```

**When long polling is the right choice today:**

- **WebSocket is blocked or unavailable**: Some corporate proxies and older network appliances intercept HTTP but block WebSocket upgrades. Long polling is the universal fallback — it works everywhere HTTP works. Socket.io uses long polling as its initial transport and upgrades to WebSocket when possible, precisely because long polling is universally compatible.
- **Extremely simple server infrastructure**: A serverless function (AWS Lambda, Cloudflare Workers) cannot hold a WebSocket connection open — the execution model terminates the function after the response is sent. But a Lambda function can hold a response for up to 29 seconds (API Gateway timeout) — sufficient to implement long polling for low-frequency events.
- **Very low event frequency**: If events arrive once every few minutes per client, the overhead of a persistent WebSocket connection (keepalive frames, connection state on the server) outweighs the simplicity of a long-poll request that runs infrequently.
- **Legacy system integration**: An existing REST API infrastructure with no WebSocket support can add near-real-time delivery via long polling without architectural changes to the server framework.

In most greenfield applications in 2024+, WebSocket (or SSE for unidirectional streams) is preferred over long polling. Long polling is primarily a fallback mechanism and a topic of study for understanding the evolution of real-time HTTP.

## Section 2: Implementation

**Q3. Walk through a correct server-side long polling implementation in Node.js/NestJS.**
A: A long polling server must handle: holding the request open, responding when an event arrives, timeout-based responses when no event arrives, client reconnection, and concurrent subscriber management.

**Core implementation — the subscriber pattern:**

```typescript
// long-poll.service.ts
import { Injectable } from '@nestjs/common';
import { Response }   from 'express';

interface Subscriber {
  res:       Response;
  userId:    string;
  timeoutId: NodeJS.Timeout;
  since:     number;           // client's last-seen event ID/timestamp
}

@Injectable()
export class LongPollService {
  // Map of userId → list of waiting subscribers (multiple tabs/devices)
  private subscribers = new Map<string, Subscriber[]>();

  // Timeout after which we respond with empty (to prevent proxy/firewall kills)
  private readonly HOLD_TIMEOUT_MS = 25_000; // 25 seconds

  /**
   * Register a waiting client and hold the response open.
   * Called when client hits GET /poll?since=<lastEventId>
   */
  subscribe(userId: string, since: number, res: Response): void {
    // Check for events that already arrived since the client's last-seen ID
    // (handles the race condition where event arrives between client receives
    //  response and sends next long-poll request)
    const pendingEvent = this.getPendingEvent(userId, since);
    if (pendingEvent) {
      // Event already waiting — respond immediately, no holding needed
      res.json({ events: [pendingEvent], timestamp: Date.now() });
      return;
    }

    // No event yet — hold the response open
    const subscriber: Subscriber = {
      res,
      userId,
      since,
      timeoutId: setTimeout(() => {
        // Timeout: respond with empty payload so client knows to reconnect
        this.removeSubscriber(userId, subscriber);
        if (!res.headersSent) {
          res.json({ events: [], timestamp: Date.now() });
        }
      }, this.HOLD_TIMEOUT_MS),
    };

    // Register the subscriber
    if (!this.subscribers.has(userId)) {
      this.subscribers.set(userId, []);
    }
    this.subscribers.get(userId)!.push(subscriber);

    // Handle client disconnect (browser tab closed, network drop)
    res.on('close', () => {
      clearTimeout(subscriber.timeoutId);
      this.removeSubscriber(userId, subscriber);
    });
  }

  /**
   * Push an event to all waiting subscribers for a user.
   * Called when a payment event, status update, etc. occurs.
   */
  publish(userId: string, event: unknown): void {
    const subs = this.subscribers.get(userId) ?? [];

    // Deliver to all waiting connections for this user (multiple devices/tabs)
    for (const sub of subs) {
      clearTimeout(sub.timeoutId);
      if (!sub.res.headersSent) {
        sub.res.json({ events: [event], timestamp: Date.now() });
      }
    }

    // Remove delivered subscribers — they will reconnect with a new long-poll
    this.subscribers.delete(userId);
  }

  private removeSubscriber(userId: string, target: Subscriber): void {
    const subs = this.subscribers.get(userId);
    if (!subs) return;
    const filtered = subs.filter(s => s !== target);
    if (filtered.length === 0) this.subscribers.delete(userId);
    else                        this.subscribers.set(userId, filtered);
  }

  private getPendingEvent(userId: string, since: number): unknown | null {
    // Check an event store (Redis, DB) for events after `since`
    // This is the buffer that handles the reconnect race condition
    // Implementation depends on your event store
    return null; // placeholder
  }
}
```

**Controller:**
```typescript
// long-poll.controller.ts
import { Controller, Get, Query, Req, Res, UseGuards } from '@nestjs/common';
import { Request, Response } from 'express';

@Controller('poll')
export class LongPollController {
  constructor(private readonly longPollService: LongPollService) {}

  @Get()
  @UseGuards(JwtAuthGuard)
  async poll(
    @Query('since') since: string,
    @Req()  req: Request,
    @Res()  res: Response,
  ): Promise<void> {
    const userId    = req.user.id;
    const sinceMs   = parseInt(since ?? '0', 10);

    // Prevent response from being auto-sent by NestJS
    // (we are managing the response lifecycle manually)
    res.setHeader('Content-Type', 'application/json');
    res.setHeader('Cache-Control', 'no-cache, no-store, must-revalidate');
    res.setHeader('X-Accel-Buffering', 'no'); // disable Nginx response buffering

    this.longPollService.subscribe(userId, sinceMs, res);
    // Do NOT return — the response is held open by the service
    // It will be sent when: event arrives, timeout fires, or client disconnects
  }
}
```

**Client-side implementation:**
```javascript
class LongPollClient {
  constructor(url, onEvent, options = {}) {
    this.url        = url;
    this.onEvent    = onEvent;
    this.since      = options.since ?? 0;
    this.active     = false;
    this.retryDelay = 1000;
    this.maxDelay   = 30_000;
    this.controller = null;
  }

  start() {
    this.active = true;
    this.poll();
  }

  stop() {
    this.active = false;
    if (this.controller) this.controller.abort();
  }

  async poll() {
    if (!this.active) return;

    this.controller = new AbortController();

    try {
      const response = await fetch(
        `${this.url}?since=${this.since}`,
        {
          signal:  this.controller.signal,
          headers: { 'Authorization': `Bearer ${getAuthToken()}` },
        }
      );

      if (!response.ok) {
        // 401: re-authenticate; 503: server down — back off
        await this.backoff();
        this.poll();
        return;
      }

      const { events, timestamp } = await response.json();

      // Reset backoff on successful response
      this.retryDelay = 1000;

      // Process received events
      for (const event of events) {
        this.onEvent(event);
      }

      // Update cursor — next poll asks for events after this timestamp
      this.since = timestamp;

      // Immediately open the next long-poll request
      // (no delay — we want near-real-time delivery)
      this.poll();

    } catch (err) {
      if (err.name === 'AbortError') return; // intentional stop

      // Network error, timeout, or server error — back off before retry
      console.error('Long poll error:', err);
      await this.backoff();
      this.poll();
    }
  }

  async backoff() {
    await sleep(this.retryDelay + Math.random() * 500); // jitter
    this.retryDelay = Math.min(this.retryDelay * 2, this.maxDelay);
  }
}

// Usage
const poller = new LongPollClient(
  '/api/poll',
  (event) => handlePaymentEvent(event),
  { since: lastKnownTimestamp }
);
poller.start();
```

**Q4. What is the reconnect race condition in long polling and how do you solve it?**
A: The reconnect race condition is the most subtle correctness problem in long polling. It occurs in the window between the server sending a response and the client sending its next poll request:

```
Timeline:

T=0:  Client sends GET /poll?since=100
T=1:  Server holds request (no events yet)
T=2:  Event A (id=101) arrives → server responds: { events: [A], timestamp: 101 }
T=2:  Client receives response, begins processing
T=3:  Event B (id=102) arrives on server ← RACE WINDOW
      No client is currently waiting — B has nowhere to go
T=4:  Client sends GET /poll?since=101
T=5:  Server holds request (B already happened at T=3, is it still available?)
      If B was only held in-memory and discarded after T=3: CLIENT MISSES EVENT B
      If B is held in a short-term buffer: server checks buffer, finds B, responds immediately
```

The race window (T=2 to T=4) is the gap between the server sending a response and the client reconnecting. Any event that arrives in this window is at risk of being lost if the server does not buffer it.

**Solution — server-side event buffer with cursor-based delivery:**

```typescript
// Event buffer: holds recent events for a configurable window
// Allows clients arriving late (after the event) to still receive it
@Injectable()
export class EventBufferService {
  // userId → list of { id, event, expiresAt }
  private buffer = new Map<string, Array<{ id: number; event: unknown; expiresAt: number }>>();
  private readonly BUFFER_TTL_MS = 60_000; // keep events for 60 seconds

  /**
   * Store an event in the buffer when it is published.
   * This covers the reconnect race window.
   */
  bufferEvent(userId: string, eventId: number, event: unknown): void {
    if (!this.buffer.has(userId)) this.buffer.set(userId, []);

    this.buffer.get(userId)!.push({
      id:        eventId,
      event,
      expiresAt: Date.now() + this.BUFFER_TTL_MS,
    });

    // Trim expired events
    this.pruneExpired(userId);
  }

  /**
   * Get all buffered events for a user that arrived after `since`.
   * Called at the start of each long-poll to catch events that arrived
   * during the reconnect window.
   */
  getEventsSince(userId: string, since: number): unknown[] {
    this.pruneExpired(userId);
    return (this.buffer.get(userId) ?? [])
      .filter(e => e.id > since)
      .map(e => e.event);
  }

  private pruneExpired(userId: string): void {
    const now    = Date.now();
    const events = this.buffer.get(userId);
    if (!events) return;
    const fresh = events.filter(e => e.expiresAt > now);
    if (fresh.length === 0) this.buffer.delete(userId);
    else                     this.buffer.set(userId, fresh);
  }
}

// Modified subscribe: always check buffer first
subscribe(userId: string, since: number, res: Response): void {
  // Check buffer for events that arrived during reconnect window
  const bufferedEvents = this.eventBuffer.getEventsSince(userId, since);
  if (bufferedEvents.length > 0) {
    res.json({ events: bufferedEvents, timestamp: Date.now() });
    return; // respond immediately — no holding needed
  }

  // No buffered events — hold the request open
  // ... (rest of subscribe logic from Q3)
}

// Modified publish: buffer the event AND deliver to waiting subscribers
publish(userId: string, eventId: number, event: unknown): void {
  // Always buffer — covers the reconnect race window
  this.eventBuffer.bufferEvent(userId, eventId, event);

  // Deliver to currently waiting subscribers
  const subs = this.subscribers.get(userId) ?? [];
  for (const sub of subs) {
    clearTimeout(sub.timeoutId);
    if (!sub.res.headersSent) {
      sub.res.json({ events: [event], timestamp: eventId });
    }
  }
  this.subscribers.delete(userId);
}
```

The buffer covers the race window: an event published at T=3 is stored in the buffer. When the client reconnects at T=4 and asks for events since T=101, the server checks the buffer, finds event B (id=102), and responds immediately without holding the request open. No events are lost.

## Section 3: Drawbacks

**Q5. What are the server resource costs of long polling at scale?**
A: Long polling's resource profile is fundamentally different from short polling and WebSocket, and this difference becomes the dominant operational concern at scale.

**Connections held open:**
Each waiting long-poll request occupies:
- A TCP connection in the server's socket table (a file descriptor).
- An HTTP connection in the server framework's connection handler.
- A response object in memory — in Node.js, an `express.Response` object with its associated buffers, headers, and stream state. Approximately 4–8KB per waiting request in a typical Node.js server.
- A pending timeout handle in the event loop.

For 10,000 concurrent users with active long-poll connections:
```
10,000 × 8KB response objects     = ~80MB memory (just response objects)
10,000 × file descriptors         = 10,000 (default Linux ulimit: 65,536 — manageable)
10,000 × timeout handles          = 10,000 timer entries in the event loop
```

Compared to 10,000 active users with short polling (1-second interval):
```
10,000 requests/second → server handles 10,000 req/s continuously
Each request: TCP handshake + HTTP parse + handler + response + TCP close
→ Far higher CPU than long polling (which processes events only when they occur)
→ But no open connections or held response objects
```

Compared to 10,000 WebSocket connections:
```
10,000 × ~50KB per WebSocket connection = ~500MB (WebSocket has more per-connection state)
10,000 × file descriptors               = 10,000
No timeout handles                       (ping/pong is the keepalive)
```

**The critical Node.js constraint — event loop blocking:**
Node.js is single-threaded. With 10,000 open long-poll connections, any synchronous operation that blocks the event loop delays all 10,000 pending response flushes simultaneously. A 100ms blocking operation = 100ms latency spike for all 10,000 waiting clients simultaneously. This does not affect WebSocket (which uses the same event loop) but is more visible in long polling because all held requests respond in near-simultaneous bursts when an event is published.

**Connection count limits at the load balancer:**
Each long-poll request is an open HTTP connection to the load balancer. AWS ALB default: 3,000 connections per target. A fleet of 5 long-poll server instances × 3,000 connections = 15,000 maximum concurrent long-poll connections per ALB. WebSocket connections have the same limit but are established once per client; long-poll connections are re-established frequently.

**Q6. What is the "thundering herd" problem specific to long polling, and how does it manifest?**
A: The thundering herd in long polling occurs when a large number of held connections respond simultaneously — either because a high-fan-out event is published, or because all connections hit their timeout at approximately the same time.

**Scenario 1 — Simultaneous timeout expiry:**
```
At T=0: 10,000 clients connect, all start a long-poll with 25s timeout
At T=25s: all 10,000 timeouts fire simultaneously
  → 10,000 response writes to 10,000 connections in the same event loop tick
  → 10,000 clients receive empty responses
  → 10,000 clients immediately send new requests
  → server receives 10,000 new long-poll requests in a very short window
  → 10,000 new connections, 10,000 new response objects, 10,000 new timeouts
  → CPU spike: JSON serialization × 10,000 + request parsing × 10,000
```

This is a predictable wave that repeats every 25 seconds, making server CPU graphs look like a saw wave rather than a steady load.

**Prevention — jittered timeouts:**
```typescript
// Instead of a fixed 25 second timeout:
const HOLD_TIMEOUT_MS = 25_000 + Math.random() * 10_000;
// Range: 25–35 seconds, uniformly distributed
// 10,000 clients: timeouts spread over a 10-second window
//   → ~1,000 timeouts per second instead of 10,000 at once
//   → flat CPU instead of spike
```

**Scenario 2 — High-fan-out event:**
```
At T=0: 5,000 clients are waiting for events in the 'system-announcement' channel
At T=10s: admin publishes a system announcement
  → publish() iterates 5,000 subscriber objects
  → sends 5,000 JSON responses simultaneously
  → 5,000 clients receive the announcement
  → 5,000 clients immediately send new long-poll requests
  → server receives 5,000 new connections nearly simultaneously
```

**Prevention — chunked delivery for bulk notifications:**
```typescript
async function broadcastToWaiters(event: unknown, subscribers: Subscriber[]): Promise<void> {
  const CHUNK = 500;
  for (let i = 0; i < subscribers.length; i += CHUNK) {
    const chunk = subscribers.slice(i, i + CHUNK);
    for (const sub of chunk) {
      clearTimeout(sub.timeoutId);
      if (!sub.res.headersSent) sub.res.json({ events: [event] });
    }
    // Yield to the event loop between chunks
    // Spreads the response writes and the resulting reconnect requests over time
    await new Promise(resolve => setImmediate(resolve));
  }
}
```

**Q7. How does long polling interact with proxies, load balancers, and CDNs, and what breaks?**
A: The held-open HTTP connection in long polling violates assumptions made by nearly every piece of infrastructure between the client and server.

**HTTP proxies — response buffering:**
Many HTTP proxies (Nginx, Squid, corporate forward proxies) buffer the entire response before forwarding it to the client. A long-poll response held for 25 seconds appears, from the proxy's perspective, as a server taking 25 seconds to send the response body — the proxy holds the connection open while waiting for the full response, then forwards it when the server finally sends data. This can cause:
- Proxy timeout: the proxy gives up after its own read timeout (often 60 seconds, but sometimes much shorter) and returns a 502/504 to the client.
- Double buffering: the proxy buffers the response until the server closes the response body, then sends it to the client in one burst — no streaming behavior.

**Prevention:**
```typescript
// Disable response buffering at the proxy level
res.setHeader('X-Accel-Buffering', 'no');        // Nginx proxy buffering
res.setHeader('X-Content-Type-Options', 'nosniff');

// Set Cache-Control to prevent any proxy from caching the response
res.setHeader('Cache-Control', 'no-cache, no-store, must-revalidate');
res.setHeader('Pragma', 'no-cache');
```

**Nginx configuration for long polling upstream:**
```nginx
location /api/poll {
  proxy_pass         http://backend;
  proxy_http_version 1.1;
  proxy_buffering    off;              # disable response buffering
  proxy_read_timeout 35s;             # longer than server's hold timeout (25s)
  proxy_send_timeout 35s;
  proxy_cache        off;
  keepalive_timeout  60s;
}
```

**CDNs — aggressive timeouts and caching:**
CDN edge nodes (Cloudflare, CloudFront) are designed for short, cacheable requests. A long-poll request that holds the connection open for 25 seconds may be terminated by the CDN's own origin timeout (Cloudflare default: 100 seconds, but some tiers lower). CDNs also cannot cache long-poll responses (they are dynamic and per-user). Long-polling endpoints should bypass CDN caching entirely:

```
Cloudflare Page Rule:
  URL: /api/poll*
  Cache Level: Bypass
  Origin Cache Control: On
```

Or route long-poll requests to a separate subdomain that bypasses the CDN entirely (`realtime.api.example.com` without Cloudflare proxying).

**Load balancer connection limits and timeout:**
AWS ALB idle connection timeout defaults to 60 seconds. A long-poll request held for 25 seconds is fine. But if the server's hold timeout is 55 seconds (close to ALB's 60-second limit), the ALB may close the connection before the server sends its response — the client receives a 504. Set the server's hold timeout to at least 10 seconds less than the load balancer's idle timeout:

```
ALB idle timeout:     60 seconds (configurable up to 4000s)
Server hold timeout:  25–50 seconds (leaves buffer)
Client timeout:       server hold timeout + 10 seconds (network RTT buffer)
```

**Q8. How does long polling compare to Server-Sent Events (SSE) for the same use case?**
A: SSE and long polling solve the same problem (server-push over HTTP) but with meaningfully different implementations and trade-offs:

**Protocol model:**
- Long polling: request/response cycle repeated per event. Each event delivery requires a new HTTP request.
- SSE: one HTTP response held open indefinitely; the server streams `data:` lines to the client as events occur. One connection per client for the lifetime of the session.

```
Long polling connection lifecycle per event:
  Client → Request → Server (hold) → Event arrives → Response → Client → Request → ...
  N events = N HTTP requests = N TCP handshakes (without keep-alive) or N reuses

SSE connection lifecycle:
  Client → Request → Server (hold open indefinitely)
  Server → data: event_1\n\n →
  Server → data: event_2\n\n →
  Server → data: event_3\n\n →
  ...one connection, unlimited events
```

**Resource consumption comparison:**

| Dimension | Long Polling | SSE |
|---|---|---|
| Connections per client | 1 per event cycle | 1 total |
| Memory per connected client | ~8KB (response obj) | ~8KB (response obj) |
| Connection churn | High (reconnect per event/timeout) | None (persistent) |
| Server memory for N clients | Similar | Similar |
| Proxy buffering problem | Yes (response not sent until event) | No (streaming response) |
| Bidirectional | No | No |
| Browser reconnect | Manual (client code) | Automatic (browser's EventSource) |
| IE/Edge legacy support | Yes | No (IE only, with polyfill) |

**Proxy buffering — SSE's key advantage:**
SSE uses `Content-Type: text/event-stream` and sends data incrementally. Proxies that understand streaming responses do not buffer them — each `data:` line is forwarded to the client as it arrives. Long polling's response is not sent until the server calls `res.json()` — until that moment, the proxy sees an open connection with no response body, which many proxies treat as buffering.

```javascript
// SSE server implementation for comparison
app.get('/events', (req, res) => {
  res.setHeader('Content-Type',  'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection',    'keep-alive');

  // Send events as they arrive — no reconnect needed
  const sendEvent = (event) => {
    res.write(`data: ${JSON.stringify(event)}\n\n`);
  };

  eventEmitter.on(`user:${req.user.id}`, sendEvent);

  req.on('close', () => {
    eventEmitter.off(`user:${req.user.id}`, sendEvent);
  });
});
```

**When to still choose long polling over SSE:**
- Legacy browsers (Internet Explorer) that have no `EventSource` support.
- Environments where the `text/event-stream` content type is blocked by a proxy.
- Existing infrastructure where the polling endpoint is already built and SSE migration is not justified.
- Need for bidirectional communication where you want a simpler model than WebSocket — long polling for server-push + regular POST for client-to-server is a coherent pattern.

## Section 4: Long Polling in Real Systems

**Q9. How does Socket.io use long polling, and what is the upgrade flow to WebSocket?**
A: Socket.io always starts with long polling (HTTP) as its initial transport and upgrades to WebSocket when both sides support it. This design ensures universal compatibility — if WebSocket is unavailable, Socket.io degrades gracefully to long polling rather than failing entirely.

**The Socket.io connection sequence:**
```
Step 1: Initial HTTP handshake (long polling)
  Client → POST /socket.io/?EIO=4&transport=polling
           { "type": "open" }
  Server → 200 { "sid": "abc123", "upgrades": ["websocket"], "pingInterval": 25000 }

Step 2: Client starts long polling immediately
  Client → GET /socket.io/?EIO=4&transport=polling&sid=abc123
           (held open by server)

Step 3: Server delivers buffered messages via long poll
  Server → 200 [array of buffered Socket.io packets]
  Client → GET /socket.io/?EIO=4&transport=polling&sid=abc123 (next long poll)

Step 4: Client probes WebSocket upgrade
  Client → WebSocket upgrade request:
           GET /socket.io/?EIO=4&transport=websocket&sid=abc123
           Upgrade: websocket
           Sec-WebSocket-Key: ...

  If upgrade succeeds:
    Client → { "type": "probe" }  (over WebSocket)
    Server → { "type": "probe_response" } (over WebSocket)

Step 5: Both sides switch to WebSocket
  Client pauses long polling
  Server acknowledges upgrade
  All subsequent communication: WebSocket frames
  Long polling transport is closed

Step 6: Long polling is retained as fallback
  If WebSocket connection drops: Socket.io falls back to long polling automatically
  The session (sid) is preserved — no re-authentication needed for downgrade
```

**Why Socket.io starts with long polling rather than trying WebSocket first:**
The WebSocket handshake (HTTP upgrade) can fail silently — a proxy may accept the HTTP GET but ignore the `Upgrade` header, returning a 200 OK (treating it as a regular GET request). If Socket.io tried WebSocket first and the upgrade silently failed, the connection would appear established but no data would flow. By starting with long polling, Socket.io establishes a working transport immediately, then upgrades to WebSocket in the background without risking a broken initial connection.

**Q10. How was long polling used in early real-time systems before WebSocket existed, and what did those implementations look like?**
A: Before WebSocket (standardized in 2011), long polling was the state of the art for real-time web applications. Several landmark systems used it at scale:

**Facebook Chat (2008):** Facebook's initial chat system used a technique called "Comet" (the umbrella term for server-push over HTTP). Each browser tab held an open XHR request to a long-poll endpoint. Facebook ran a dedicated tier of lightweight HTTP servers (Erlang-based, later replaced) specifically for holding these connections — separate from the application servers that handled regular page requests. The key architectural insight: connection holding requires concurrency (many open connections) not CPU throughput (processing per request), so the two workloads needed separate infrastructure.

**Gmail (2006):** Google's Gmail used a technique sometimes called "Hanging GET" — the same pattern as long polling. The JavaScript client held an XHR request open; the server flushed script tags (`<script>window.deliverMessage(...)</script>`) down the response to deliver messages. The client's page evaluated these script tags as they arrived. This was before `XMLHttpRequest` could stream responses reliably, so flushing JavaScript into an iframe was the workaround.

**BOSH (Bidirectional-streams Over Synchronous HTTP, XEP-0124):** A formal specification for long polling used in XMPP (the Jabber instant messaging protocol) to enable web-based XMPP clients before WebSocket. BOSH defined: connection session IDs, simultaneous request limits (2 requests open at once — one for each direction), empty response semantics, and error recovery. Many of the patterns in BOSH became informal conventions in subsequent long polling implementations.

**The infrastructure evolution those systems drove:**
Early long polling implementations discovered the "C10K problem" — a single server handling 10,000 concurrent open connections. Traditional threaded servers (Apache with one thread per connection) could not scale to 10,000 connections because each thread consumed ~1MB of stack space (10,000 threads = 10GB). This drove the development of event-driven non-blocking servers: Nginx, Node.js, Tornado (Python), Netty (Java) — all designed around the insight that connection holding is I/O-bound, not CPU-bound, and requires an event loop, not threads.

**Q11. "Design a long polling implementation for payment status updates in a NestJS backend. A user initiates a payment and the frontend polls until it gets a terminal status (APPROVED or FAILED)."**
A:

```
Use case: user initiates POST /payments → receives payment_id
          frontend polls GET /poll/payment/{paymentId}
          server holds until payment reaches APPROVED or FAILED
          frontend shows result to user

This is a targeted long poll: one specific resource, one waiting client,
terminal states end the polling. Different from the general event stream.

Server implementation:

@Injectable()
export class PaymentStatusPollService {
  // paymentId → { res, timeoutId }
  private waiters = new Map<string, { res: Response; timeoutId: NodeJS.Timeout }>();

  private readonly HOLD_TIMEOUT_MS = 20_000;  // 20s hold; client retries if empty

  /**
   * Hold client until payment reaches a terminal state.
   */
  waitForStatus(paymentId: string, res: Response): void {
    // First: check if already in a terminal state
    const cached = this.terminalStatusCache.get(paymentId);
    if (cached) {
      res.json({ status: cached.status, payment_id: paymentId });
      return;
    }

    // Not terminal yet — hold the response
    const timeoutId = setTimeout(() => {
      this.waiters.delete(paymentId);
      if (!res.headersSent) {
        // Empty response = "still processing, please retry"
        res.json({ status: 'PENDING', payment_id: paymentId });
      }
    }, this.HOLD_TIMEOUT_MS);

    this.waiters.set(paymentId, { res, timeoutId });

    res.on('close', () => {
      clearTimeout(timeoutId);
      this.waiters.delete(paymentId);
    });
  }

  /**
   * Called when payment processor webhook delivers the final status.
   * Also called when internal payment state machine transitions to terminal state.
   */
  onPaymentTerminated(paymentId: string, status: 'APPROVED' | 'FAILED'): void {
    // Cache terminal status for 5 minutes (covers reconnect race)
    this.terminalStatusCache.set(paymentId, { status, resolvedAt: Date.now() });

    const waiter = this.waiters.get(paymentId);
    if (waiter) {
      clearTimeout(waiter.timeoutId);
      this.waiters.delete(paymentId);
      if (!waiter.res.headersSent) {
        waiter.res.json({ status, payment_id: paymentId });
      }
    }
  }
}

@Controller('poll/payment')
export class PaymentPollController {
  @Get(':paymentId')

  async pollPaymentStatus(

  async function waitForPaymentResult(paymentId) {
    const MAX_TOTAL_WAIT = 5 * 60 * 1000; // 5 minutes max
    const startTime      = Date.now();

    while (Date.now() - startTime < MAX_TOTAL_WAIT) {
      const response = await fetch(`/api/poll/payment/${paymentId}`);
      const { status } = await response.json();

      if (status === 'APPROVED') {
        showSuccessUI();
        return;
      }
      if (status === 'FAILED') {
        showFailureUI();
        return;
      }
      // status === 'PENDING': server timed out, retry immediately

Design decisions:
  - One waiter per paymentId: a payment can only be in one terminal state once;
    multiple clients polling the same payment_id all wait in the same slot
    (replace with a list if multiple clients can watch same payment)
  - Terminal status cache: covers the reconnect race — if APPROVED arrives
    between client receiving PENDING and client sending next request,
    the cache delivers it immediately on reconnect
  - 20s hold, not 25s: leaves 5s headroom before the 25s load balancer timeout
  - No Redis: this is single-instance state; for multi-instance,
    publish payment status via Redis pub/sub to reach all waiting instances
```

**Q12. "Compare long polling, SSE, and WebSocket for a real-time fraud alert system. Choose one and justify."**
A:

```
Requirements:
  - Fraud analysts watch a dashboard showing live fraud alerts
  - Alerts are server-initiated (analyst doesn't trigger them)
  - Alert volume: 5–50 alerts per minute per analyst (medium frequency)
  - Analysts need to acknowledge alerts (client → server)
  - Dashboard runs in browser
  - Infrastructure: existing NestJS + Redis + Kubernetes (no special load balancer)

Analysis:

Long polling:
  ✅ Works everywhere; no proxy issues
  ✅ Simple to implement with existing HTTP infrastructure
  ❌ Connection churn: 5–50 reconnects per minute per analyst × 100 analysts
     = 500–5,000 reconnect events per minute — significant overhead
  ❌ Alert acknowledgment requires a separate POST request (no bidirectional)
  ❌ Reconnect race condition requires buffering logic
  ❌ Thundering herd risk if many analysts' timeouts align

SSE (Server-Sent Events):
  ✅ Persistent connection — no reconnect per alert
  ✅ Browser's EventSource handles reconnection automatically with Last-Event-ID
  ✅ Works through HTTP proxies (streaming response)
  ✅ Lower server overhead than long polling (no reconnect churn)
  ❌ Unidirectional: alert acknowledgments still need separate POST requests
  ❌ Browser opens max 6 connections per domain; if analyst has 6 other tabs,
     SSE may fail to connect (HTTP/2 mitigates this)
  ❌ Scaling across instances requires same Redis pub/sub adapter as WebSocket

WebSocket:
  ✅ Bidirectional: acknowledge alerts on the same connection
  ✅ Persistent connection; lowest overhead per event
  ✅ Binary or text frames; efficient for high-frequency updates
  ❌ Requires WebSocket-aware load balancing (handled by Kubernetes Ingress with Nginx)
  ❌ Higher implementation complexity than SSE for this unidirectional-dominant use case
  ❌ Proxy issues in some corporate environments (mitigated by Socket.io fallback)

Decision: SSE
  Rationale:
    - Server → client is the dominant direction (alerts flow server to analyst)
    - Alert acknowledgment is infrequent and tolerates a separate POST
    - SSE's persistent connection eliminates the connection churn of long polling
    - Browser's native EventSource handles reconnection with Last-Event-ID cursor,
      covering the reconnect race condition automatically
    - Lower operational complexity than WebSocket (no upgrade negotiation,
      no WebSocket-specific load balancer configuration)
    - Redis pub/sub adapter exists for SSE (same pattern as Socket.io adapter)

  If requirements changed to: high-frequency bidirectional (analyst sends
  contextual queries that affect which alerts they see, real-time collaboration
  between analysts on the same alert) → WebSocket would be the right choice.

SSE implementation sketch:
  GET /api/fraud-alerts/stream
    Content-Type: text/event-stream
    Cache-Control: no-cache

    id: alert_001
    data: {"alert_id":"alt_001","severity":"HIGH","merchant":"merch_42"}

    id: alert_002
    data: {"alert_id":"alt_002","severity":"LOW","merchant":"merch_17"}

  Browser EventSource:
    const es = new EventSource('/api/fraud-alerts/stream');
    es.onmessage = (e) => renderAlert(JSON.parse(e.data));
    // On reconnect: browser sends Last-Event-ID: alert_002
    // Server resumes from alert_003

  Acknowledgment (separate HTTP):
    POST /api/fraud-alerts/alt_001/acknowledge
    → 204 No Content
```

**Q13. "Your long polling endpoint is causing high memory usage on the server. CPU is low but RSS memory grows linearly with concurrent users and never drops. What is causing this and how do you fix it?"**
A:

```
Symptom: Memory grows linearly with users, never decreases.
         This is a leak, not expected per-connection memory usage
         (which would also grow linearly but stay flat per connection).

The key question: does memory drop when clients disconnect?
  Yes → memory is correctly per-connection; leak is elsewhere
  No  → subscribers/response objects are not being cleaned up on disconnect

Root cause diagnosis:

Cause 1 — Missing disconnect handler (most common):
  If res.on('close', cleanup) is not registered,
  disconnected clients remain in the subscribers map forever.

  Check:
    Log subscriber map size periodically
    Disconnect a known client → check if subscriber count decreases

  Fix:
    res.on('close', () => {
      clearTimeout(subscriber.timeoutId);
      this.removeSubscriber(userId, subscriber);
    });

Cause 2 — Event buffer growing unboundedly:
  The reconnect race buffer (Q4) stores events per user indefinitely
  if TTL pruning is not implemented or not triggered.

  Check:
    Log eventBuffer.buffer.size periodically
    If it grows and never shrinks: pruning is broken or not called

  Fix:
    Ensure pruneExpired is called on every bufferEvent and getEventsSince
    Set a reasonable BUFFER_TTL_MS (60 seconds is enough for reconnect race)
    Add a periodic global prune (every 5 minutes, prune all expired entries):

    setInterval(() => {
      for (const [userId] of this.buffer) {
        this.pruneExpired(userId);
      }
    }, 5 * 60 * 1000);

Cause 3 — Response objects retaining closure references:
  Node.js: if the subscriber object or response object captures a large
  closure (e.g., a reference to the entire request context, database connection,
  or large data structure), the GC cannot collect it even after res.json() is called.

  Check:
    Node.js heap snapshot (--inspect → Chrome DevTools → Memory → Heap Snapshot)
    Look for: large number of Response, IncomingMessage, or Socket objects
    Identify what is holding references to them

  Fix:
    Store only what is needed in the subscriber object (res, timeoutId, userId)
    Do not capture the full req object in closures

Cause 4 — Timeout handles keeping references alive:
  clearTimeout is not called before calling res.json() in the publish path,
  or clearTimeout is called after an await (the timeout fires before clear):

  BAD:
    async publish(userId, event) {
      await someAsyncOperation(); // ← timeout may fire here
      clearTimeout(sub.timeoutId); // ← too late; timeout already fired
      sub.res.json(event);         // ← headersSent=true; response already sent
    }

  FIX:
    publish(userId, event) {
      clearTimeout(sub.timeoutId); // ← synchronously first, before any await
      if (!sub.res.headersSent) {
        sub.res.json(event);
      }
      this.removeSubscriber(userId, sub); // ← cleanup before any async
    }

Monitoring additions:
  setInterval(() => {
    const subscriberCount = [...this.subscribers.values()]
      .reduce((sum, subs) => sum + subs.length, 0);
    logger.info('LongPoll health', {
      subscriberCount,
      bufferSize: this.eventBuffer.buffer.size,
      memoryMB:   Math.round(process.memoryUsage().rss / 1024 / 1024),
    });
    metrics.gauge('longpoll.subscribers', subscriberCount);
    metrics.gauge('process.memory.rss_mb', process.memoryUsage().rss / 1024 / 1024);
  }, 30_000);
```

## Quick Reference

| Property | Short Polling | Long Polling | SSE | WebSocket |
|---|---|---|---|---|
| Protocol | HTTP | HTTP | HTTP | HTTP upgrade → WS |
| Connection | New per poll | New per event | Persistent | Persistent |
| Direction | Client pull | Server push (simulated) | Server push | Bidirectional |
| Latency | = poll interval | ≈ event propagation time | ≈ event propagation time | ≈ event propagation time |
| Empty responses | Many | None (timeout → empty) | None | None |
| Proxy compatibility | Universal | Needs buffering disabled | Streaming-aware proxies | Needs WS support |
| Server connections | Brief | Long-held | Long-held | Persistent |
| Reconnect race | N/A | Yes — needs buffering | Handled by EventSource | Manual |
| Thundering herd risk | Low | High (timeout alignment) | Low | Low |
| Browser support | Universal | Universal | Universal (no IE) | Universal |

| Long polling concern | Mitigation |
|---|---|
| Simultaneous timeout expiry | Jitter: `HOLD_TIMEOUT + random(0, 10_000)ms` |
| Reconnect race condition | Server-side event buffer with cursor, TTL-pruned |
| Proxy buffering | `X-Accel-Buffering: no`; Nginx `proxy_buffering off` |
| Load balancer timeout | Hold timeout < LB idle timeout by ≥ 10s |
| Memory leak | `res.on('close', cleanup)`; clearTimeout synchronously; prune buffer |
| High connection count | Separate long-poll server tier (async, event-loop based) |
| Fan-out thundering herd | Chunk delivery with `setImmediate` between chunks |

## The Core Mental Model

```
Long polling = hold the HTTP response open until something worth sending arrives.

The lifecycle:
  Client → GET /poll?since=T
  Server → holds res object open
  Event arrives → server calls res.json(event) → response sent
  Client receives → immediately sends GET /poll?since=T+1
  No event in N seconds → server sends res.json({ events: [] }) (timeout)
  Client receives empty → immediately sends GET /poll?since=T (same cursor)

The three correctness requirements:
  1. Buffer events for the reconnect race window
     (event arrives between server responding and client reconnecting)
  2. Register res.on('close') to clean up disconnected clients
     (missing this causes the memory leak every implementation hits)
  3. Jitter the hold timeout
     (same timeout for all clients = thundering herd every N seconds)

Where long polling still belongs:
  WebSocket upgrade blocked by proxy → long polling fallback (Socket.io does this)
  Serverless (Lambda): 29s max execution → long polling fits, WebSocket doesn't
  IE11 legacy requirement → no EventSource; long polling is the only option
  Simple one-shot wait (payment result, job status): long polling for one event,
    not a persistent stream

Where to prefer SSE or WebSocket instead:
  Persistent stream of events → SSE (one connection, no reconnect churn)
  Bidirectional communication → WebSocket (long polling + POST is two mechanisms)
  High event frequency (>1/sec) → WebSocket or SSE (reconnect churn too high)
  Modern infrastructure with no legacy constraints → SSE or WebSocket

The infrastructure checklist for long polling in production:
  ✅ Hold timeout < load balancer idle timeout (by ≥ 10 seconds)
  ✅ X-Accel-Buffering: no (disable Nginx proxy buffering)
  ✅ Cache-Control: no-cache (prevent proxy response caching)
  ✅ res.on('close') registered before holding (clean up on disconnect)
  ✅ clearTimeout called synchronously before res.json() in publish path
  ✅ Event buffer with TTL pruning (reconnect race coverage)
  ✅ Jittered hold timeout (thundering herd prevention)
  ✅ Separate server tier or process pool for holding connections
     (don't mix with CPU-intensive request handlers)
```

**Tip for the interview:** Long polling questions at 5 YOE almost always escalate to one of three places: (1) the reconnect race condition — being able to describe precisely what happens when an event arrives in the window between the server sending a response and the client sending its next request, and that the fix is a server-side event buffer (not a client retry delay), demonstrates you have debugged this failure mode in a real system; (2) the memory leak from missing `res.on('close')` — every long polling implementation that runs in production eventually encounters this leak, and knowing exactly why it happens (disconnect does not call the timeout; the subscriber stays in the map; the response object is never GC'd) and how to fix it is the kind of operational detail that separates someone who has shipped long polling from someone who has only designed it; (3) when not to use long polling — knowing that SSE is strictly better for persistent server-push streams (no connection churn, no reconnect race, automatic cursor-based reconnect via `Last-Event-ID`) and that long polling's value today is primarily as a WebSocket fallback and for serverless environments, is the architectural judgment that shows you understand the full spectrum rather than reaching for one technique as a hammer.
