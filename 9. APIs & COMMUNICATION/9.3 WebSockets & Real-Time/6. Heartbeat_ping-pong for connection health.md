# Heartbeat / Ping-Pong for Connection Health — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a heartbeat mechanism and what problem does it solve?**
A: A heartbeat is a periodic signal — a message, packet, or probe — sent between two connected parties to confirm that the connection is still alive and that the remote party is still responsive. It solves the problem of "half-open connections": TCP connections that appear open in one party's socket table but have actually been silently dropped by a NAT device, firewall, load balancer, or network failure, without either endpoint receiving a FIN or RST packet.

The problem manifests as "dead connections that look alive." Without a heartbeat:

```
Client                    NAT / Firewall           Server
  │                            │                      │
  │── TCP SYN ────────────────►│── TCP SYN ──────────►│
  │◄── TCP SYN-ACK ────────────│◄── TCP SYN-ACK ──────│
  │── TCP ACK ────────────────►│── TCP ACK ──────────►│
  │                            │                      │
  │  [Connection idle for 4 minutes]                  │
  │                            │                      │
  │                     NAT table entry               │
  │                     expires silently              │
  │                            │                      │
  │── Application data ───────►│  DROPPED (no entry)  │
  │  [No response]             │                      │
  │  [Client waits]            │                      │
  │  [TCP retransmits]         │                      │
  │  [Eventually times out     │                      │
  │   after minutes]           │                      │
```

The client's socket shows `ESTABLISHED`; the server's socket shows `ESTABLISHED`; but no data can flow. The client may wait minutes before its TCP retransmit timer expires and the connection is declared dead. During this time, if the client tries to send a request, it hangs — and any thread or goroutine waiting on the response is blocked.

With a heartbeat: the client sends a small ping message every 30 seconds. If the NAT entry has expired, the ping gets no response. After 2–3 missed pings, the client declares the connection dead and reconnects — detecting the failure in ~60–90 seconds instead of minutes, and without a blocking application thread.

**Q2. Why is TCP's built-in keepalive insufficient for application-layer heartbeats?**
A: TCP has a built-in keepalive mechanism (`SO_KEEPALIVE` socket option), but it is inadequate for most production use cases:

**TCP keepalive defaults are too slow.** The Linux default: keepalive starts after 2 hours of idle (`tcp_keepalive_time = 7200`), then sends 9 probes at 75-second intervals (`tcp_keepalive_intvl = 75`, `tcp_keepalive_probes = 9`). That is 2 hours + 11.25 minutes before a dead connection is detected. Unacceptable for an application that needs to detect failures in seconds.

**TCP keepalive only detects dead hosts, not dead applications.** TCP keepalive is sent by the kernel; it confirms the remote host is alive and the TCP stack is responding. It cannot detect: the application process is deadlocked (kernel is running but app is hung), the application's event loop is blocked (the OS sends TCP keepalive ACKs automatically), or the remote service has crashed but the OS is still running.

**TCP keepalive is not portable or configurable.** `SO_KEEPALIVE` behavior varies by OS; some environments (certain cloud load balancers, container runtimes) strip or ignore keepalive packets. Application-layer heartbeats are sent as ordinary application data — they traverse the same path as real messages and are not filtered.

**TCP keepalive cannot carry application context.** An application-layer ping can include timestamps (for round-trip latency measurement), sequence numbers (to detect missed pings), or version information (for protocol negotiation). A TCP keepalive carries no payload.

The practical rule: use `SO_KEEPALIVE` as a last-resort safety net (it is still useful for detecting truly dead hosts at the OS level), but implement application-layer heartbeats for real-time connection health detection.

**Q3. What is the ping-pong pattern and how does it differ from one-directional heartbeats?**
A: The ping-pong pattern is a bidirectional exchange: one party sends a `PING` message; the other responds with a `PONG`. The sender measures the round-trip time and confirms:
1. The connection is alive (the message was delivered and a response arrived).
2. The remote party's application is responsive (the app generated the PONG, not just the OS).
3. The approximate round-trip latency (useful for detecting degraded connections).

A one-directional heartbeat (sometimes called a "beacon" or "keepalive frame") is sent by one party without expecting a response — the sender confirms only that the connection is open for writes, not that the remote end is reading and responding.

```
Ping-Pong (bidirectional — confirms remote responsiveness):
  Client ──── PING (seq=1, timestamp=T1) ────────────► Server
  Client ◄─── PONG (seq=1, timestamp=T1) ──────────── Server
  RTT = now() - T1 = 4ms ✓

One-directional heartbeat (confirms write-side is open):
  Client ──── HEARTBEAT ──────────────────────────────► Server
  [No response expected]
  [Client only knows the write succeeded; server may not be reading]
```

Ping-pong is stronger: it verifies both the send path and the receive path. One-directional heartbeats are used when the protocol is inherently asymmetric (SSE, unidirectional streams) or when the response overhead is undesirable at very high connection counts.

**Q4. What is a "half-open connection" and why is it dangerous for connection pools?**
A: A half-open connection is a TCP connection that one endpoint believes is established while the other endpoint considers it closed (or the connection has been silently dropped by network infrastructure). The connection is "half-open" because one side's view is inconsistent with the other's.

Danger in connection pools — the classic scenario:

```
Database connection pool: 20 idle connections

Night scenario:
  22:00 — Last request processed; all 20 connections go idle
  22:05 — AWS RDS maintenance: brief network interruption
            RDS closes all connections on its side (TCP RST sent)
            But... the RST is blocked by the VPC NAT gateway
            Connection pool still sees 20 "ESTABLISHED" connections
            RDS sees 0 connections

  08:00 — Morning traffic spike
  08:00:01 — App picks connection #1 from pool (looks ESTABLISHED)
  08:00:01 — App sends SQL query over connection #1
  08:00:01 — RDS receives the packet: "SYN without prior handshake?"
              RDS sends RST
  08:00:01 — App receives RST: connection is dead
  08:00:01 — Pool discards connection #1; creates a new connection
  08:00:01 — App retries query on new connection ← this is recoverable
             But: if the pool doesn't retry automatically, the request fails
             And: if all 20 connections are dead, 20 requests fail simultaneously
```

The "morning thundering herd" of connection errors from a database pool with stale connections is a well-known production incident pattern — the system looks healthy overnight and explodes on first traffic after a period of idle. Heartbeats on idle connections detect and replace dead connections before they are needed, preventing this failure mode entirely.

## Section 2: WebSocket Heartbeats

**Q5. How does the WebSocket protocol implement ping-pong?**
A: The WebSocket protocol (RFC 6455) defines ping and pong as dedicated control frame types at the protocol level — they are not application messages but protocol-level frames:

- **Ping frame** — opcode `0x9`; may carry up to 125 bytes of application data.
- **Pong frame** — opcode `0xA`; must echo the payload data from the ping frame.
- A pong may also be sent unsolicited (without a preceding ping) as a unidirectional keepalive.

WebSocket libraries send pings and generate pongs automatically at the protocol layer — application code does not need to inspect or generate pong frames. The payload data in the ping (typically a timestamp) is echoed in the pong, enabling round-trip measurement.

**Server-side WebSocket heartbeat implementation (Node.js / ws library):**

```typescript
import WebSocket, { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 8080 });

const PING_INTERVAL_MS = 30_000;   // ping every 30 seconds
const PONG_TIMEOUT_MS  = 10_000;   // expect pong within 10 seconds of ping

wss.on('connection', (ws: WebSocket) => {
  // Track whether this client is alive
  let isAlive = true;
  let pingTimer: NodeJS.Timeout;
  let pongTimeoutTimer: NodeJS.Timeout;

  // Client responded to our ping
  ws.on('pong', () => {
    isAlive = true;
    clearTimeout(pongTimeoutTimer);
    schedulePing();   // schedule the next ping after this pong arrives
  });

  function sendPing(): void {
    if (ws.readyState !== WebSocket.OPEN) return;

    isAlive = false;  // assume dead until pong arrives

    // Send a ping with the current timestamp as payload
    ws.ping(Buffer.from(Date.now().toString()));

    // If no pong arrives within PONG_TIMEOUT_MS, terminate
    pongTimeoutTimer = setTimeout(() => {
      if (!isAlive) {
        console.log(`[WS] Client ${ws.id} did not respond to ping — terminating`);
        ws.terminate();   // forcibly close; don't wait for handshake
      }
    }, PONG_TIMEOUT_MS);
  }

  function schedulePing(): void {
    clearTimeout(pingTimer);
    pingTimer = setTimeout(sendPing, PING_INTERVAL_MS);
  }

  // Start the heartbeat cycle
  schedulePing();

  ws.on('close', () => {
    clearTimeout(pingTimer);
    clearTimeout(pongTimeoutTimer);
  });

  ws.on('message', (data) => {
    // Normal message handling
    handleMessage(ws, data);
  });
});
```

**Client-side ping response (browser WebSocket API):**

The browser's native WebSocket API responds to pings automatically — the browser's WebSocket implementation sends pong frames without any JavaScript code. However, browsers cannot send ping frames (only servers can initiate pings in the WebSocket protocol). For client-initiated heartbeats (to detect server failure), use application-level messages:

```typescript
// Browser client: application-level heartbeat (not WebSocket protocol ping)
class WebSocketClient {
  private ws: WebSocket;
  private pingInterval: number;
  private pongTimeout: number;
  private lastPongAt: number = Date.now();

  constructor(url: string) {
    this.connect(url);
  }

  private connect(url: string): void {
    this.ws = new WebSocket(url);

    this.ws.onopen = () => {
      this.startHeartbeat();
    };

    this.ws.onmessage = (event) => {
      const msg = JSON.parse(event.data);
      if (msg.type === 'pong') {
        this.lastPongAt = Date.now();
        clearTimeout(this.pongTimeout);
      } else {
        this.handleMessage(msg);
      }
    };

    this.ws.onclose = () => {
      this.cleanup();
      // Reconnect with exponential backoff
      setTimeout(() => this.connect(url), this.getBackoffDelay());
    };
  }

  private startHeartbeat(): void {
    this.pingInterval = window.setInterval(() => {
      if (this.ws.readyState !== WebSocket.OPEN) return;

      this.ws.send(JSON.stringify({
        type: 'ping',
        timestamp: Date.now()
      }));

      // If no pong within 10 seconds, assume connection is dead
      this.pongTimeout = window.setTimeout(() => {
        console.warn('[WS] Pong timeout — closing dead connection');
        this.ws.close();  // triggers onclose → reconnect
      }, 10_000);

    }, 30_000);
  }

  private cleanup(): void {
    clearInterval(this.pingInterval);
    clearTimeout(this.pongTimeout);
  }
}
```

**Q6. What is the correct heartbeat interval and timeout for WebSocket connections?**
A: The interval and timeout must account for the environment's NAT table timeout — the most common cause of silent connection drops:

**NAT table timeouts by environment:**
- AWS NAT Gateway: 350 seconds (~5.8 minutes) for idle TCP connections.
- AWS ALB idle timeout: 60 seconds by default (configurable to 4000 seconds).
- Many corporate firewalls: 60–120 seconds.
- Mobile networks: 30–90 seconds (highly variable).

**Rule of thumb:** heartbeat interval must be less than the minimum expected NAT timeout in any environment the client might be in. Since mobile networks can drop idle connections in 30 seconds, a 25–30 second interval is the safe default for internet-facing WebSocket services.

```
Recommended configuration for internet-facing services:
  Ping interval:   25–30 seconds    (safely below 30s mobile NAT timeout)
  Pong timeout:    10 seconds        (reasonable RTT for any global connection)
  Max missed:      2–3 pings         (60–90 seconds before declaring dead)

For internal services (same datacenter):
  Ping interval:   60 seconds        (no NAT concern; just liveness detection)
  Pong timeout:    5 seconds          (datacenter RTT is < 1ms; 5s is generous)
  Max missed:      3                  (3 minutes before declaring dead)
```

**Adaptive interval based on observed RTT:**

```typescript
// Adjust ping interval based on connection quality
class AdaptiveHeartbeat {
  private baseIntervalMs = 30_000;
  private recentRtts: number[] = [];

  onPongReceived(pingTimestamp: number): void {
    const rtt = Date.now() - pingTimestamp;
    this.recentRtts = [...this.recentRtts.slice(-9), rtt];  // keep last 10

    const avgRtt = this.recentRtts.reduce((a, b) => a + b, 0) / this.recentRtts.length;

    if (avgRtt > 500) {
      // Connection is degraded; ping more frequently to detect failure faster
      this.scheduleNextPing(15_000);
    } else {
      this.scheduleNextPing(this.baseIntervalMs);
    }
  }
}
```

## Section 3: TCP Keepalive and Connection Pool Heartbeats

**Q7. How do you configure TCP keepalive correctly for production services?**
A: While application-layer heartbeats are preferred, TCP keepalive provides a safety net for connections that are not actively sending application data. The default values must be overridden:

**Linux kernel parameters (system-wide):**
```bash
# Start keepalive probes after 60 seconds of idle (not 7200)
sysctl -w net.ipv4.tcp_keepalive_time=60

# Send probes every 10 seconds (not 75)
sysctl -w net.ipv4.tcp_keepalive_intvl=10

# 6 probes before declaring dead (60s + 6×10s = 120s total detection time)
sysctl -w net.ipv4.tcp_keepalive_probes=6
```

**Per-socket in application code (Go):**
```go
import (
  "net"
  "syscall"
  "time"
)

func setKeepalive(conn net.Conn) error {
  tcpConn, ok := conn.(*net.TCPConn)
  if !ok {
    return fmt.Errorf("not a TCP connection")
  }

  // Enable keepalive
  if err := tcpConn.SetKeepAlive(true); err != nil {
    return err
  }

  // Start keepalive after 60s of idle
  if err := tcpConn.SetKeepAlivePeriod(60 * time.Second); err != nil {
    return err
  }

  return nil
}
```

**Per-socket in Node.js:**
```typescript
import net from 'net';

const socket = new net.Socket();
socket.connect(5432, 'db.internal');

// Enable TCP keepalive: start after 60s, probe every 10s
socket.setKeepAlive(true, 60_000);
```

**Q8. How do database connection pools implement heartbeats to prevent stale connections?**
A: Database connection pools use two complementary strategies to keep connections healthy:

**Strategy 1: Idle connection validation (test-on-borrow).**
Before handing a connection to an application thread, execute a lightweight test query to confirm the connection is still alive:

```typescript
// pg (node-postgres) pool configuration
import { Pool } from 'pg';

const pool = new Pool({
  host: 'db.internal',
  database: 'production',
  max: 20,

  // Execute this query before returning a connection from the pool
  // If it fails, the connection is discarded and a new one is created
  // pg does this automatically via its built-in health check mechanism
});

// For manual implementation in other libraries:
async function getHealthyConnection(pool: Pool): Promise<PoolClient> {
  let attempts = 0;
  while (attempts < 3) {
    const client = await pool.connect();
    try {
      await client.query('SELECT 1');  // test the connection
      return client;                   // connection is alive
    } catch (err) {
      client.release(true);            // discard this connection (true = destroy)
      attempts++;
    }
  }
  throw new Error('Failed to obtain a healthy database connection');
}
```

**Strategy 2: Keepalive queries on idle connections.**
Periodically execute a keepalive query on idle connections to prevent them from being dropped by NAT or firewall rules:

```typescript
// HikariCP-style keepalive (Java, translated to TypeScript concept)
class PooledConnection {
  private keepaliveTimer: NodeJS.Timeout;
  private readonly KEEPALIVE_INTERVAL_MS = 30_000;

  constructor(private conn: DatabaseConnection) {
    this.startKeepalive();
  }

  private startKeepalive(): void {
    this.keepaliveTimer = setInterval(async () => {
      if (this.isIdle()) {
        try {
          await this.conn.query('SELECT 1');   // keepalive query
          this.conn.lastValidated = Date.now();
        } catch (err) {
          // Connection is dead; remove from pool
          this.invalidate();
        }
      }
    }, this.KEEPALIVE_INTERVAL_MS);
  }

  invalidate(): void {
    clearInterval(this.keepaliveTimer);
    pool.remove(this);
    this.conn.destroy();
  }
}
```

**PostgreSQL-specific: `keepalives` connection parameter.**
PostgreSQL's `libpq` client library supports TCP keepalive configuration via connection parameters — no application code changes required:

```typescript
const pool = new Pool({
  connectionString: 'postgresql://user:pass@db:5432/mydb',
  // libpq keepalive parameters
  keepAlives: true,
  keepAlivesIdle: 60,    // seconds before first keepalive probe
  keepAlivesInterval: 10, // seconds between probes
  keepAlivesCount: 6,     // probes before declaring dead
});
```

## Section 4: gRPC Keepalive

**Q9. How does gRPC implement keepalive and what are the correct settings?**
A: gRPC uses HTTP/2 PING frames for keepalive — the same mechanism as application-layer ping-pong but standardized within the HTTP/2 protocol. gRPC's keepalive is controlled by `keepalive.ClientParameters` (client side) and `keepalive.ServerParameters` (server side):

```go
import "google.golang.org/grpc/keepalive"

// Client-side keepalive
conn, err := grpc.Dial(addr,
  grpc.WithKeepaliveParams(keepalive.ClientParameters{
    // Send a ping if no activity for 30 seconds
    Time: 30 * time.Second,

    // Wait 10 seconds for pong before declaring the connection dead
    Timeout: 10 * time.Second,

    // Send pings even when there are no active RPCs
    // (critical for detecting dead connections on idle clients)
    PermitWithoutStream: true,
  }),
)

// Server-side keepalive — what the server expects from clients
server := grpc.NewServer(
  grpc.KeepaliveParams(keepalive.ServerParameters{
    // If a client is idle for 5 minutes, send a ping
    Time: 5 * time.Minute,

    // Wait 20 seconds for the client to respond
    Timeout: 20 * time.Second,

    // Maximum age of any connection; forces reconnect to rebalance
    MaxConnectionAge: 30 * time.Minute,

    // Grace period after MaxConnectionAge before force-closing
    MaxConnectionAgeGrace: 5 * time.Second,
  }),

  // Enforce policy: reject clients that ping too aggressively
  grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{
    // Minimum time between client pings
    MinTime: 15 * time.Second,

    // Allow pings when there are no active streams
    PermitWithoutStream: true,
  }),
)
```

**The `PermitWithoutStream: true` flag is critical.** Without it, the gRPC library only sends keepalive pings when there is an active RPC in progress — which means idle connections (no ongoing RPCs) are never checked. A connection that has been idle for 5 minutes and is silently dead will not be detected until the next RPC is attempted, which then fails. With `PermitWithoutStream: true`, the client pings even on completely idle connections, detecting dead connections before they are needed.

**`MaxConnectionAge` for load balancing:**
Load balancers distribute connections across backend instances at connection time. A client that connected 2 hours ago may be pinned to a backend that is now heavily overloaded while others are idle. `MaxConnectionAge` forces all connections to reconnect periodically, allowing the load balancer to redistribute them across the current set of healthy backends. This is essential for horizontally scaled gRPC services — without it, the load distribution skews over time.

**Q10. What is the GOAWAY frame in gRPC/HTTP2 and how does it relate to keepalive?**
A: `GOAWAY` is an HTTP/2 frame sent by either party to initiate graceful connection termination. It communicates "I will stop processing new streams on this connection; finish your current streams and reconnect."

gRPC sends `GOAWAY` when:
- `MaxConnectionAge` is reached (server forces reconnect for load balancing).
- The server is shutting down gracefully (`server.GracefulStop()`).
- The server is about to restart or be replaced.

The client receives `GOAWAY`, completes any in-flight RPCs on that connection, then creates a new connection. Requests that would have used the dying connection are automatically retried on the new connection (if `WaitForReady` is set). This makes `GOAWAY` the graceful counterpart to connection termination — where keepalive detects dead connections, `GOAWAY` gracefully retires live ones.

```
Server sends GOAWAY (MaxConnectionAge reached):

Client                          Server
  │                                │
  │  [Active RPCs in progress]     │
  │                                │
  │◄── GOAWAY (last_stream=42) ────│  "Stop sending new streams"
  │                                │
  │  [Completes streams ≤ 42]      │  [Closes streams > 42 with REFUSED_STREAM]
  │  [Opens new connection]        │
  │── NEW CONNECTION ─────────────►│ (new server instance or rebalanced)
  │── In-flight RPCs (retried) ───►│
```

## Section 5: Redis and Message Queue Heartbeats

**Q11. How do Redis clients maintain connection health?**
A: Redis uses a single TCP connection per client (or a pool of connections). The Redis protocol has a built-in PING command that serves as both a keepalive and a liveness check:

```
Client ──── PING ────────────────────────────────────► Redis
Client ◄─── +PONG ─────────────────────────────────── Redis
```

**ioredis (Node.js) heartbeat configuration:**

```typescript
import Redis from 'ioredis';

const redis = new Redis({
  host: 'redis.internal',
  port: 6379,

  // Send PING every 10 seconds to keep the connection alive
  // ioredis calls this "keepAlive" but it is application-layer PING
  keepAlive: 10_000,          // milliseconds between pings

  // Connection pool for cluster / sentinel
  maxRetriesPerRequest: 3,    // retry failed commands up to 3 times

  // Reconnect behavior when a connection is lost
  reconnectOnError: (err) => {
    const targetErrors = ['READONLY', 'ECONNRESET', 'ECONNREFUSED'];
    return targetErrors.some(e => err.message.includes(e));
  },

  retryStrategy: (times) => {
    if (times > 10) return null;  // stop retrying after 10 attempts
    return Math.min(times * 200, 5_000);  // exponential backoff up to 5s
  },
});

// ioredis automatically handles reconnection; emit events for monitoring
redis.on('error', (err) => {
  console.error('[Redis] Connection error:', err);
  metrics.increment('redis.connection.error');
});

redis.on('reconnecting', () => {
  console.warn('[Redis] Reconnecting...');
  metrics.increment('redis.connection.reconnect');
});

redis.on('ready', () => {
  console.log('[Redis] Connection ready');
});
```

**Manual PING for connection validation:**

```typescript
async function validateRedisConnection(redis: Redis): Promise<boolean> {
  try {
    const start = Date.now();
    const result = await redis.ping();  // returns 'PONG'
    const latencyMs = Date.now() - start;

    if (result !== 'PONG') return false;
    if (latencyMs > 100) {
      console.warn(`[Redis] High PING latency: ${latencyMs}ms`);
      metrics.histogram('redis.ping.latency_ms', latencyMs);
    }

    return true;
  } catch (err) {
    return false;
  }
}
```

**Q12. How does Kafka handle connection health for consumers and producers?**
A: Kafka clients use two distinct mechanisms for connection health:

**Producer/consumer heartbeats to the coordinator (consumer groups):**
Kafka consumers send heartbeats to the group coordinator (a broker) via the `HeartbeatRequest` API at `heartbeat.interval.ms` intervals (default: 3 seconds). The coordinator uses these to detect consumer failures and trigger rebalances. If a consumer misses enough heartbeats (`session.timeout.ms`, default: 45 seconds), the coordinator removes it from the group and reassigns its partitions.

```
Consumer                    Group Coordinator (Broker)
  │                                │
  │── HeartbeatRequest ───────────►│  "Still alive; processing partition 3"
  │◄── HeartbeatResponse ──────────│  "OK; no rebalance needed"
  │                                │
  │  [Consumer crashes]            │
  │  [No more heartbeats]          │
  │                                │  45s timeout expires
  │                                │  → Trigger rebalance
  │                                │  → Reassign partition 3 to another consumer
```

**Broker-level connection health (TCP-level):**
Kafka clients maintain persistent TCP connections to brokers. The Kafka protocol does not have an application-layer PING/PONG — instead, clients detect dead broker connections through failed request/response cycles. If a request to a broker times out (`request.timeout.ms`, default: 30 seconds), the client marks the broker as unavailable, closes the connection, and reconnects.

**Connections.max.idle.ms:**
```properties
# Close idle broker connections after 9 minutes
# (before NAT tables expire on cloud networks)
connections.max.idle.ms=540000
```

This configuration proactively closes connections that have been idle for 9 minutes — just before most cloud NAT tables would drop them silently. The next request automatically reconnects. This prevents the "stale connection" pattern where a request to an idle connection fails because the NAT entry has expired.

## Section 6: Reconnection and Backoff

**Q13. How do you implement reconnection with exponential backoff after heartbeat failure?**
A: Reconnection must use exponential backoff with jitter — without it, all clients that lost their connection simultaneously attempt to reconnect at the same time, overwhelming the server that is trying to recover (a reconnect storm):

```typescript
class ReconnectingConnection {
  private ws: WebSocket | null = null;
  private reconnectAttempt = 0;
  private readonly BASE_DELAY_MS  = 1_000;
  private readonly MAX_DELAY_MS   = 60_000;
  private readonly JITTER_FACTOR  = 0.3;    // ±30% jitter

  private heartbeatInterval: number | null = null;
  private pongTimeout: number | null = null;

  connect(url: string): void {
    this.ws = new WebSocket(url);

    this.ws.onopen = () => {
      console.log('[WS] Connected');
      this.reconnectAttempt = 0;   // reset on successful connection
      this.startHeartbeat();
    };

    this.ws.onclose = (event) => {
      this.stopHeartbeat();
      if (!event.wasClean) {
        this.scheduleReconnect(url);
      }
    };

    this.ws.onerror = () => {
      // onerror is always followed by onclose; reconnect in onclose handler
    };
  }

  private startHeartbeat(): void {
    this.heartbeatInterval = window.setInterval(() => {
      if (this.ws?.readyState !== WebSocket.OPEN) return;

      this.ws.send(JSON.stringify({ type: 'ping', ts: Date.now() }));

      this.pongTimeout = window.setTimeout(() => {
        console.warn('[WS] Heartbeat timeout — closing connection');
        this.ws?.close();    // triggers onclose → reconnect
      }, 10_000);
    }, 30_000);
  }

  private stopHeartbeat(): void {
    if (this.heartbeatInterval) clearInterval(this.heartbeatInterval);
    if (this.pongTimeout) clearTimeout(this.pongTimeout);
    this.heartbeatInterval = null;
    this.pongTimeout = null;
  }

  private scheduleReconnect(url: string): void {
    const exponentialDelay = this.BASE_DELAY_MS * Math.pow(2, this.reconnectAttempt);
    const cappedDelay = Math.min(exponentialDelay, this.MAX_DELAY_MS);

    // Jitter: random value in range [cappedDelay * (1 - JITTER_FACTOR),
    //                                 cappedDelay * (1 + JITTER_FACTOR)]
    const jitter = cappedDelay * this.JITTER_FACTOR * (Math.random() * 2 - 1);
    const delay = Math.max(this.BASE_DELAY_MS, cappedDelay + jitter);

    console.log(`[WS] Reconnecting in ${Math.round(delay)}ms (attempt ${this.reconnectAttempt + 1})`);

    setTimeout(() => {
      this.reconnectAttempt++;
      this.connect(url);
    }, delay);
  }
}

// Reconnect delay progression (without jitter, for illustration):
// Attempt 1:  1s
// Attempt 2:  2s
// Attempt 3:  4s
// Attempt 4:  8s
// Attempt 5: 16s
// Attempt 6: 32s
// Attempt 7: 60s (capped)
// Attempt 8: 60s (capped)
// ...
```

**Maximum reconnect attempts** — for user-facing connections (chat, dashboards), reconnect indefinitely (the user wants the connection back). For background service-to-service connections where a dead connection represents a genuine service failure, limit attempts and alert:

```typescript
if (this.reconnectAttempt >= 10) {
  console.error('[WS] Max reconnect attempts reached — giving up');
  metrics.increment('ws.connection.permanent_failure');
  // Alert oncall; the remote service may be down
  return;
}
```

**Q14. What is the "thundering herd" problem in reconnection and how does jitter prevent it?**
A: The thundering herd problem occurs when many clients simultaneously lose their connections (a server restart, a brief network outage, a NAT table flush) and then all reconnect at the same time — overloading the server that is trying to recover.

```
Without jitter: server restarts at T=0

T=30s: All 10,000 clients' heartbeat timeouts fire simultaneously
T=30s: 10,000 simultaneous reconnect attempts hit the server
T=30s: Server is overwhelmed; rejects most connections
T=30s: Clients receive connection refused → immediately retry (base delay = 1s)
T=31s: 10,000 simultaneous retry attempts
T=31s: Server still overwhelmed...
[Retry storm continues; server cannot recover]

With jitter: server restarts at T=0

T=28s–32s: Each client's pong timeout fires at a slightly different time
            (natural spread from different network paths)
T=29s–35s: Each client reconnects after its individual jittered delay
            Reconnect attempts spread over ~10-second window
            Server handles ~1,000 reconnects/second instead of 10,000 at once
            Server recovers; all clients eventually reconnect
```

Jitter converts a synchronized spike into a smooth distribution. The correct formula:

```typescript
// Full jitter (recommended for reconnection storms)
const delay = Math.random() * Math.min(MAX_DELAY, BASE_DELAY * 2^attempt);

// Equal jitter (keeps some base backoff, randomizes the rest)
const temp = Math.min(MAX_DELAY, BASE_DELAY * 2^attempt);
const delay = temp / 2 + Math.random() * (temp / 2);
```

"Full jitter" (AWS's recommendation for exponential backoff) performs best in load tests — it maximizes the spread of reconnect attempts and minimizes server load during recovery.

## Section 7: Scenario Questions

**Q15. "After every weekend, the first database requests on Monday morning fail with connection errors. By Tuesday the system is healthy. What is causing this and how do you fix it?"**
A: This is the "stale pool connections" problem caused by the weekend idle period. The connection pool maintains connections that were alive on Friday but have been silently dropped by network infrastructure (NAT table expiry, RDS maintenance, firewall idle timeout) over the weekend.

**Root cause sequence:**
1. Friday evening: all 20 pool connections go idle.
2. Weekend: connections idle for 60+ hours. NAT table entries expire (typically after 30 minutes to a few hours on cloud NAT). RDS may perform maintenance that closes and reopens connections. No heartbeat queries are sent; the pool doesn't notice.
3. Monday morning: first request picks a connection from the pool. The connection is half-open. The SQL query is sent to a dead socket. The OS retransmits for 1–3 minutes. The application thread is blocked. Eventually the TCP timeout fires and the pool discards the dead connection and creates a new one.

**Fix — multiple complementary mechanisms:**

```typescript
// 1. Keepalive queries on idle connections
const pool = new Pool({
  idleTimeoutMillis: 30_000,   // close connections idle > 30s
                                // prevents accumulation of stale connections

  // pg-specific: validates connections before use
  allowExitOnIdle: false,
});

// 2. Connection validation before returning to application
pool.on('connect', (client) => {
  client.query('SET SESSION idle_in_transaction_session_timeout = 5000');
});

// 3. Scheduled keepalive for the pool
setInterval(async () => {
  const client = await pool.connect();
  try {
    await client.query('SELECT 1');   // keepalive query
  } finally {
    client.release();
  }
}, 60_000);   // every 60 seconds; prevent NAT expiry

// 4. TCP keepalive on the underlying socket (belt and suspenders)
// Configured in pg connection parameters:
// keepAlives: true, keepAlivesIdle: 30
```

The idle timeout (`idleTimeoutMillis: 30_000`) is often the simplest fix: connections idle for more than 30 seconds are closed and returned to the OS. The pool creates fresh connections as needed. No stale connection can survive long enough for the NAT entry to expire.

**Q16. "In a chat system, users report that messages stop arriving but the WebSocket connection appears open in the browser. What is happening and how do you diagnose it?"**
A: This is a classic half-open connection symptom: the browser's WebSocket API reports `readyState === 1` (OPEN) because the TCP connection appears established from the client's perspective, but the server can no longer send messages to the client — either because the NAT entry expired, the server closed the connection without a proper FIN, or the network path is broken.

**Diagnosis steps:**

Step 1 — check if the server is sending messages at all:
```javascript
// In browser console: instrument the WebSocket
const origSend = ws.send.bind(ws);
ws.onmessage = (e) => console.log('[WS] Received:', e.data);
console.log('[WS] readyState:', ws.readyState);
// If messages are sent server-side but never arrive → network path broken
// If messages are not sent server-side → server believes the client disconnected
```

Step 2 — check whether the server's ping reaches the client:
If the server sends a WebSocket ping and receives no pong within the timeout, it should have already terminated the connection. If it's not terminating, the server-side heartbeat is missing or misconfigured.

Step 3 — check NAT timeout:
How long has this user's connection been idle (no messages)? If it's been > 5 minutes and the client is on a mobile network, the NAT entry likely expired. The client's TCP stack shows ESTABLISHED but NAT dropped the state.

**Fix:**

Implement the server-side heartbeat (server pings every 25 seconds). If the client's NAT entry has expired, the ping frame gets no pong → server terminates the connection. The client's `onclose` event fires → client reconnects → connection is fresh.

Separately, implement client-side heartbeat (client sends application-level ping every 25 seconds). If the server receives no ping for 60 seconds, it closes its end of the connection, triggering the client's `onclose`.

Both-sides heartbeat is belt-and-suspenders: either party detecting the dead connection triggers a reconnect.

**Q17. "Your gRPC client makes 1 request per hour to a low-traffic service. After extended idle periods, the first request consistently takes 5+ seconds. How do you diagnose and fix this?"**
A: A 5-second delay on the first request after an idle period is a connection re-establishment penalty. The client's persistent connection has been dropped (NAT expiry, server-side idle timeout, `MaxConnectionAge`), but the client doesn't know until it tries to use it. It then waits for TCP retransmits to fail before giving up on the dead connection, creating a new connection, and retrying — taking several seconds.

**Diagnosis:**
```bash
# Enable gRPC verbose logging
GRPC_GO_LOG_VERBOSITY_LEVEL=99 GRPC_GO_LOG_SEVERITY_LEVEL=info ./service

# Look for:
# "transport: http2Server.HandleStreams: ... EOF"  ← server closed connection
# "ClientTransport.Dial: ..."                      ← client re-connecting
# Time gap between close and dial = the 5-second delay
```

**Fix — gRPC keepalive with `PermitWithoutStream: true`:**

```go
conn, _ := grpc.Dial(addr,
  grpc.WithKeepaliveParams(keepalive.ClientParameters{
    Time:                30 * time.Second,   // ping after 30s idle
    Timeout:             10 * time.Second,   // pong timeout
    PermitWithoutStream: true,               // ← CRITICAL: ping on idle connections
  }),
)
```

Without `PermitWithoutStream: true`, gRPC only sends pings when there is an active RPC in progress. An idle connection (no RPCs for 1 hour) is never pinged, never detected as dead, and fails on the next RPC. With this flag, the client pings every 30 seconds even with no active RPCs — detecting the dead connection and reconnecting before the application needs it. The first hourly request finds a live connection and completes in < 10ms instead of 5+ seconds.

Additionally, set `WaitForReady(true)` on the call itself:
```go
response, err := client.SomeMethod(ctx, req,
  grpc.WaitForReady(true),   // wait for connection to be ready, don't fail immediately
)
```

`WaitForReady` causes the call to wait for the connection to be re-established rather than immediately failing. Combined with keepalive, the connection is rarely dead when the call arrives; if it is, `WaitForReady` transparently handles reconnection.

## Quick Reference

| Mechanism | Layer | Detects | Does NOT detect |
|--- |--- |--- |--- |
| TCP keepalive (`SO_KEEPALIVE`) | OS / TCP stack | Remote host is unreachable | App deadlock; event loop blocked; app crash with OS still running |
| WebSocket ping/pong (RFC 6455) | WebSocket protocol | Connection alive; remote WS stack responds | Application logic deadlock; slow processing |
| Application-level ping/pong | Application | Connection alive; remote app responds | Network path issues below app layer |
| gRPC HTTP/2 PING | HTTP/2 protocol | Connection alive; remote HTTP/2 stack responds | App handler deadlock |
| Database `SELECT 1` | Application | DB accepts queries; auth valid; schema accessible | Network issues between queries |
| Redis `PING` | Redis protocol | Redis responds to commands | App-level correctness |

| Setting | Typical value | Rationale |
|--- |--- |--- |
| WS ping interval | 25–30s | Below mobile NAT timeout (~30s) |
| WS pong timeout | 10s | Generous for global RTT |
| WS max missed pings | 2–3 | 60–90s before reconnect |
| gRPC `Time` | 30s | Below AWS NAT timeout (350s) |
| gRPC `Timeout` | 10s | Generous for datacenter RTT |
| gRPC `MaxConnectionAge` | 30m | Force reconnect for load rebalancing |
| Pool idle timeout | 30s | Below NAT timeout; prevents stale connections |
| TCP `keepalive_time` | 60s | Override default 7200s |
| Reconnect base delay | 1s | Fast first retry |
| Reconnect max delay | 60s | Cap to prevent indefinite wait |
| Reconnect jitter | ±30% | Prevent thundering herd |
