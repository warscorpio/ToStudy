# SSE (Server-Sent Events): When to Prefer Over WebSockets — Interview Q&A (5 YOE Level)

---

## Section 1: The Protocol Fundamentals

**Q1. What is SSE and how does it work at the HTTP level?**
A: Server-Sent Events is a browser-native protocol for unidirectional server-to-client streaming over a single, persistent HTTP connection. The client opens one HTTP request and the server never closes the response — it keeps writing newline-delimited event frames into the response body, indefinitely.

**The wire format — what the server actually sends:**
```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no       ← disable Nginx buffering (critical)

data: {"payment_id":"pay_001","status":"APPROVED"}\n\n

event: payment.status_changed\n
data: {"payment_id":"pay_002","status":"PENDING"}\n\n

id: evt_0042\n
event: payment.approved\n
data: {"amount":5000,"currency":"INR"}\n
retry: 3000\n\n
```

**The four SSE frame fields:**
- `data:` — the payload (string; use JSON.stringify for structured data)
- `event:` — named event type (optional; defaults to `"message"`)
- `id:` — event ID; browser stores this as `lastEventId`; sent as `Last-Event-ID` header on reconnect
- `retry:` — reconnect delay in milliseconds (browser honours this)

A frame ends with a **blank line** (`\n\n`). Fields without a blank line between them belong to the same event.

**The browser API (EventSource):**
```javascript
const es = new EventSource('/api/payments/stream', { withCredentials: true });

// Default 'message' event (no event: field in frame)
es.addEventListener('message', (e) => {
  const data = JSON.parse(e.data);
  console.log('received:', data);
});

// Named event
es.addEventListener('payment.approved', (e) => {
  const data = JSON.parse(e.data);
  renderApprovalBanner(data);
});

// Connection state
es.addEventListener('open',  () => console.log('SSE connected'));
es.addEventListener('error', (e) => {
  if (e.target.readyState === EventSource.CLOSED) {
    console.log('SSE closed by server');
  }
});

// Cleanup
es.close();
```

**What the browser does automatically:**
- Reconnects on disconnect with the `retry:` delay (default ~3 seconds)
- Sends `Last-Event-ID: <last received id>` header on reconnect — enabling the server to replay missed events

**Q2. How does SSE differ from WebSocket at the protocol and transport layer?**
A: SSE and WebSocket solve adjacent problems — both give you a persistent server-to-client channel — but they differ at every layer of the stack:

| Dimension | SSE | WebSocket |
|---|---|---|
| Protocol | Plain HTTP/1.1 or HTTP/2 | Separate WS protocol (starts as HTTP upgrade) |
| Direction | Unidirectional: server → client only | Bidirectional: server ↔ client |
| Transport | HTTP response body (chunked transfer) | Framed binary/text messages over TCP |
| Client API | `EventSource` (browser built-in) | `WebSocket` (browser built-in) |
| Auth on reconnect | Standard HTTP headers (cookies, Authorization) | Must re-send auth in handshake or first message |
| Proxy/firewall compatibility | High — it is HTTP | Lower — HTTP upgrade can be blocked |
| HTTP/2 multiplexing | Yes — many SSE streams share one TCP connection | No — each WebSocket is its own TCP connection |
| Auto-reconnect | Built into `EventSource` (browser-native) | Must implement manually or use a library |
| Last-Event-ID replay | Built-in (`id:` field + `Last-Event-ID` header) | Must implement manually in application layer |
| Text only? | Text frames only (UTF-8) | Text and binary frames |
| Server complexity | Any HTTP server (just write to response) | Needs WebSocket upgrade handling |
| Horizontal scaling | Stateless HTTP — easy with standard LBs | Stateful — requires sticky sessions or adapter |

**The protocol upgrade difference:**
WebSocket starts with an HTTP request that requests an upgrade:
```
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```
If the proxy or firewall does not understand `Upgrade: websocket`, the connection is refused. SSE is just a long-lived `GET` — it goes through every HTTP proxy without special handling.

**Q3. Why does SSE over HTTP/2 change the connection model significantly?**
A: Over HTTP/1.1, each SSE stream is one TCP connection. A merchant dashboard with 5 independent SSE streams (payments, settlements, disputes, analytics, system alerts) would open 5 TCP connections. Browsers enforce a per-origin connection limit of 6 for HTTP/1.1 — so 5 SSE streams consume most of the budget, leaving only 1 TCP connection for all API requests.

Over HTTP/2, all streams are multiplexed over a single TCP connection. The browser's per-origin limit does not apply to HTTP/2 streams — a single TCP connection can carry hundreds of SSE streams simultaneously.

```
HTTP/1.1 — 5 SSE streams:
  TCP conn 1: /stream/payments
  TCP conn 2: /stream/settlements
  TCP conn 3: /stream/disputes
  TCP conn 4: /stream/analytics
  TCP conn 5: /stream/alerts
  TCP conn 6: (last remaining for API requests)
  → browser limit hit; next API call queues

HTTP/2 — 5 SSE streams:
  TCP conn 1 (multiplexed):
    Stream 1: /stream/payments
    Stream 3: /stream/settlements
    Stream 5: /stream/disputes
    Stream 7: /stream/analytics
    Stream 9: /stream/alerts
  → all API requests use the same TCP conn on additional streams
  → no connection limit problem
```

This is one of the strongest arguments for SSE in modern architectures: when your API gateway is HTTP/2, SSE scales better than WebSocket for multiple independent streams because WebSocket cannot be multiplexed over HTTP/2.

## Section 2: When to Choose SSE Over WebSocket

**Q4. What are the concrete criteria for choosing SSE over WebSocket?**
A: The decision reduces to two questions: (1) Does the client need to send data to the server through this channel? (2) Do you need binary frame support? If both answers are no, SSE is likely the right choice. The full criteria:

**Choose SSE when:**

1. **Communication is unidirectional** — the server pushes data; the client only reads. Payment status updates, trade execution feeds, dashboard metric streams, notification feeds, log tailing, CI/CD build output. The client never needs to push back through the same channel.

2. **You want automatic reconnection and replay for free** — `EventSource` reconnects on disconnect and sends `Last-Event-ID`. Implementing equivalent reliability in WebSocket requires a custom protocol layer (track event IDs, reconnect logic, replay endpoint). SSE gives this at zero application code cost.

3. **Infrastructure does not support WebSocket** — corporate proxies, some API gateways, HTTP/1.1-only reverse proxies block the `Upgrade` header. SSE traverses these without modification.

4. **You want stateless servers** — SSE connections are HTTP requests. Any server instance can handle any client's reconnect (assuming a shared event source like Redis Streams or Kafka). WebSocket connections are stateful — the same socket must stay connected to the same instance (or you need a Redis adapter).

5. **You are running many concurrent streams per user** — over HTTP/2, hundreds of SSE streams share one TCP connection. Each WebSocket is a separate TCP connection.

6. **Your backend is HTTP/REST already** — adding SSE requires adding one route that writes chunked response. Adding WebSocket requires new infrastructure (WebSocket server, load balancer upgrade, sticky sessions, or Socket.io adapter).

**Choose WebSocket when:**

1. **The client sends frequent messages to the server** — chat, collaborative editing, real-time multiplayer, trading order entry. The round-trip for "client sends → server responds" would require a separate `fetch()` call per user action with SSE.

2. **You need binary frames** — audio/video streaming, binary protocol payloads, file chunk transfer. SSE is text-only; sending binary requires base64 encoding, adding ~33% overhead.

3. **You need sub-100ms bidirectional latency** — WebSocket frames have less overhead than HTTP headers on every client send. For high-frequency bidirectional data (FX tick-level trading, cursor sharing), WebSocket frame overhead matters.

4. **You need custom subprotocols** — STOMP over WebSocket, MQTT over WebSocket, proprietary binary protocols.

**Q5. What is the practical overhead comparison for a payment status feed specifically?**
A: For a read-only payment status feed (a merchant dashboard watching their transactions update in real time), SSE is strictly better on every dimension:

```
Payment status update event:
  Payload: { payment_id, status, amount, timestamp }
  JSON size: ~120 bytes

WebSocket per-frame overhead:
  Frame header: 2–10 bytes
  No HTTP headers per message (headers only on upgrade)
  Client → server: mask bit required (4-byte masking key)
  Server → client: no masking required

SSE per-event overhead:
  "data: " prefix: 6 bytes
  "\n\n" suffix:   2 bytes
  Optional "id: " line: ~15 bytes
  Optional "event: " line: ~25 bytes
  Total metadata: ~48 bytes per event

For a payment dashboard receiving 10 status updates/second:
  WebSocket: HTTP upgrade (one-time) + bare frames
  SSE: one HTTP request (one-time) + chunked response chunks

Both have negligible message overhead at 10 events/second.
The meaningful differences are operational, not bytes-per-message.
```

**Where SSE wins operationally:**

```
WebSocket payment status feed (minimal viable):
  1. WebSocket server setup (ws or Socket.io)
  2. Load balancer: enable WebSocket (ALB: 'HTTP/WebSocket' protocol)
  3. Horizontal scaling: sticky sessions or Redis adapter
  4. Auth: custom JWT validation in handshake or first message
  5. Reconnect: custom logic in client code
  6. Replay on reconnect: custom event-ID tracking + replay API
  7. Monitoring: custom metrics (connections, frames, errors)

SSE payment status feed (minimal viable):
  1. One GET route that writes to res (Express/NestJS)
  2. Load balancer: zero change (it's HTTP)
  3. Horizontal scaling: stateless; any instance handles any reconnect
  4. Auth: standard middleware (cookie, Authorization header)
  5. Reconnect: EventSource handles it (browser built-in)
  6. Replay on reconnect: check Last-Event-ID header; replay from Kafka/DB
  7. Monitoring: standard HTTP metrics (requests, duration, status codes)

Infrastructure delta for a team already running HTTP services:
  WebSocket: new load balancer config, sticky sessions or Redis adapter, custom client library
  SSE: one new route, zero infrastructure changes
```

## Section 3: Implementation Patterns

**Q6. How do you implement a production-grade SSE endpoint in NestJS?**
A: NestJS does not have a built-in SSE abstraction for production use — the documented `@Sse()` decorator works for simple cases but bypasses proper connection lifecycle management. For production, manage the response directly:

```typescript
// payment-stream.controller.ts
import { Controller, Get, Req, Res, UseGuards } from '@nestjs/common';
import { Request, Response }                     from 'express';
import { JwtAuthGuard }                          from '../auth/jwt-auth.guard';
import { PaymentStreamService }                  from './payment-stream.service';

@Controller('payments')
export class PaymentStreamController {
  constructor(private readonly streamService: PaymentStreamService) {}

  @Get('stream')
  @UseGuards(JwtAuthGuard)
  async stream(@Req() req: Request, @Res() res: Response): Promise<void> {
    const merchantId = req.user.merchantId;
    const lastEventId = req.headers['last-event-id'] as string | undefined;

    // Set SSE headers
    res.setHeader('Content-Type',  'text/event-stream');
    res.setHeader('Cache-Control', 'no-cache');
    res.setHeader('Connection',    'keep-alive');
    res.setHeader('X-Accel-Buffering', 'no'); // disable Nginx buffering

    // Flush headers immediately — client sees connection as open
    res.flushHeaders();

    // Replay missed events if Last-Event-ID was sent
    if (lastEventId) {
      await this.streamService.replayMissed(res, merchantId, lastEventId);
    }

    // Register this connection and get a cleanup function
    const unsubscribe = this.streamService.subscribe(merchantId, (event) => {
      writeSSEEvent(res, event);
    });

    // Heartbeat — prevents proxies from closing idle connections (every 25s)
    const heartbeat = setInterval(() => {
      res.write(': heartbeat\n\n'); // comment line — EventSource ignores it
    }, 25_000);

    // Cleanup on client disconnect
    req.on('close', () => {
      clearInterval(heartbeat);
      unsubscribe();
    });
  }
}

// Helper: write a structured SSE event to the response
function writeSSEEvent(
  res:   Response,
  event: { id: string; type: string; data: unknown },
): void {
  res.write(`id: ${event.id}\n`);
  res.write(`event: ${event.type}\n`);
  res.write(`data: ${JSON.stringify(event.data)}\n`);
  res.write(`\n`); // blank line = end of event
}
```

```typescript
// payment-stream.service.ts
import { Injectable }    from '@nestjs/common';
import { Redis }         from 'ioredis';
import { InjectRedis }   from '@nestjs-modules/ioredis';
import { Response }      from 'express';
import { PaymentEvent }  from './payment-event.interface';

type Subscriber = (event: PaymentEvent) => void;

@Injectable()
export class PaymentStreamService {
  // In-process subscriber map: merchantId → Set of subscriber callbacks
  private subscribers = new Map<string, Set<Subscriber>>();

  constructor(@InjectRedis() private readonly redis: Redis) {
    this.startRedisListener();
  }

  subscribe(merchantId: string, callback: Subscriber): () => void {
    if (!this.subscribers.has(merchantId)) {
      this.subscribers.set(merchantId, new Set());
    }
    this.subscribers.get(merchantId)!.add(callback);

    // Return unsubscribe function
    return () => {
      const subs = this.subscribers.get(merchantId);
      if (subs) {
        subs.delete(callback);
        if (subs.size === 0) this.subscribers.delete(merchantId);
      }
    };
  }

  async replayMissed(res: Response, merchantId: string, lastEventId: string): Promise<void> {
    // Read from Redis Stream: events after lastEventId for this merchant
    const events = await this.redis.xrange(
      `merchant:${merchantId}:events`,
      `(${lastEventId}`, // exclusive start
      '+',               // to latest
      'COUNT', '100',
    );

    for (const [id, fields] of events) {
      const data = JSON.parse(fields[1]); // fields: ['data', '<json>']
      res.write(`id: ${id}\nevent: ${data.type}\ndata: ${JSON.stringify(data)}\n\n`);
    }
  }

  private startRedisListener(): void {
    // Subscribe to Redis channel for payment events
    // (published by payment service via redis-emitter or direct PUBLISH)
    const subClient = this.redis.duplicate();
    subClient.psubscribe('payment:events:*');

    subClient.on('pmessage', (_pattern, channel, message) => {
      const merchantId = channel.split(':')[2]; // payment:events:<merchantId>
      const event: PaymentEvent = JSON.parse(message);

      // Deliver to all local SSE connections for this merchant
      const subs = this.subscribers.get(merchantId);
      if (subs) {
        for (const callback of subs) {
          callback(event);
        }
      }
    });
  }
}
```

**Q7. How does horizontal scaling work for SSE — and why is it simpler than WebSocket?**
A: SSE connections are long-lived HTTP responses, but the server holding an SSE connection is just writing to a response stream. The scaling challenge is: when a payment event arrives, it must reach every SSE connection across all server instances that have a subscriber for that merchant — not just the instance that processed the payment.

**The architecture (simpler than WebSocket because no Redis adapter library is needed):**

```
Payment Service
    │
    │ On PaymentApproved:
    │   PUBLISH payment:events:<merchantId>  <event JSON>
    ▼
[Redis Pub/Sub]
    │
    ├──────────────────────────────────────────┐
    ▼                                          ▼
[SSE Instance 1]                       [SSE Instance 2]
  psubscribe('payment:events:*')         psubscribe('payment:events:*')
    │                                          │
    │ receives PUBLISH                         │ receives PUBLISH
    │ merchantId = merch_42                    │ merchantId = merch_42
    │                                          │
    │ this.subscribers.get('merch_42')         │ this.subscribers.get('merch_42')
    │   → [res_A, res_B] (2 SSE connections)  │   → [res_C] (1 SSE connection)
    │                                          │
    │ writes event to res_A, res_B             │ writes event to res_C
    ▼                                          ▼
Merchant on Browser Tab 1, 2           Merchant on Browser Tab 3
receive payment.approved               receives payment.approved
```

**Why this is simpler than WebSocket scaling:**

```
WebSocket requires:
  - @socket.io/redis-adapter (or equivalent)
  - Two Redis connections per instance (pub + sub)
  - Room membership tracked in Redis
  - Socket ID routing across instances
  - Sticky sessions or the adapter handles cross-instance delivery

SSE requires:
  - One Redis pub/sub channel per merchant (or pattern subscribe)
  - One Redis sub connection per SSE instance
  - Zero room management (connection = HTTP response, cleanup on req.close)
  - No sticky sessions (each reconnect is a fresh HTTP request, goes to any instance)
  - Standard HTTP load balancing
```

**The key insight:** SSE connections are stateless from the load balancer's perspective. When a client reconnects after a crash, it can land on any instance. That instance subscribes to the Redis channel and starts delivering from wherever `Last-Event-ID` indicates. No session affinity required.

**Q8. How do you implement the Last-Event-ID replay pattern with a Redis Stream as the durable log?**
A: The SSE `id:` field and `Last-Event-ID` reconnect header together give you a replay mechanism that requires minimal application code:

```typescript
// Publishing to Redis Stream (from payment service)
async function publishPaymentEvent(
  redis:     Redis,
  merchantId: string,
  event:     PaymentEvent,
): Promise<string> {
  // XADD to Redis Stream: auto-generates a stream ID (timestamp-sequence)
  const eventId = await redis.xadd(
    `merchant:${merchantId}:events`,  // stream key
    'MAXLEN', '~', '10000',           // trim to ~10k entries (approximate)
    '*',                              // auto-generate ID
    'type', event.type,
    'data', JSON.stringify(event),
  );
  // eventId: "1718000000000-0" (millisecond timestamp + sequence)

  // Also publish for live delivery (Redis pub/sub for low latency)
  await redis.publish(
    `payment:events:${merchantId}`,
    JSON.stringify({ ...event, id: eventId }),
  );

  return eventId!;
}
```

```typescript
// SSE endpoint: reconnect with Last-Event-ID
@Get('stream')
@UseGuards(JwtAuthGuard)
async stream(@Req() req: Request, @Res() res: Response): Promise<void> {
  const merchantId  = req.user.merchantId;
  const lastEventId = req.headers['last-event-id'] as string | undefined;

  res.setHeader('Content-Type',      'text/event-stream');
  res.setHeader('Cache-Control',     'no-cache');
  res.setHeader('X-Accel-Buffering', 'no');
  res.flushHeaders();

  // Replay: read from Redis Stream starting after the last received event
  if (lastEventId) {
    const missed = await this.redis.xrange(
      `merchant:${merchantId}:events`,
      `(${lastEventId}`,   // exclusive: events AFTER lastEventId
      '+',                 // to the latest
      'COUNT', '500',      // max 500 replayed events
    );

    for (const [id, fields] of missed) {
      // fields: ['type', '<type>', 'data', '<json>']
      const data = JSON.parse(fields[3]);
      res.write(`id: ${id}\n`);
      res.write(`event: ${fields[1]}\n`);
      res.write(`data: ${JSON.stringify(data)}\n\n`);
    }
  }

  // Subscribe to live events via Redis pub/sub
  const unsubscribe = this.streamService.subscribe(merchantId, (event) => {
    res.write(`id: ${event.id}\n`);
    res.write(`event: ${event.type}\n`);
    res.write(`data: ${JSON.stringify(event.data)}\n\n`);
  });

  const heartbeat = setInterval(() => res.write(': \n\n'), 25_000);
  req.on('close', () => { clearInterval(heartbeat); unsubscribe(); });
}
```

**The reconnect flow:**
```
Client receives event id: 1718000042000-0
EventSource stores lastEventId = "1718000042000-0"

Client disconnects (network blip, 8 seconds)
  → during disconnect: events 1718000043000-0 through 1718000049000-0 published

Client reconnects (EventSource auto-reconnects after retry: delay):
  GET /payments/stream
  Last-Event-ID: 1718000042000-0

Server:
  XRANGE merchant:merch_42:events (1718000042000-0 +
  → returns events 1718000043000-0 through 1718000049000-0
  → writes them to SSE response immediately (replay burst)
  → then subscribes to Redis pub/sub for live events

Client receives 7 missed events seamlessly, then live stream resumes
```

## Section 4: Authentication and Security

**Q9. How does SSE authentication differ from WebSocket authentication, and why is SSE's approach simpler?**
A: SSE connections use standard HTTP request authentication — the same mechanisms that work for every REST API endpoint work for SSE without modification.

**SSE authentication:**
```typescript
// Works exactly like any REST endpoint
@Get('stream')
@UseGuards(JwtAuthGuard)    // standard NestJS guard
async stream(@Req() req: Request, @Res() res: Response) {
  // req.user is populated by JwtAuthGuard
  // Cookies are sent automatically by the browser
  // Authorization: Bearer <token> header works via withCredentials
}

// Client: credentials sent automatically (cookies) or via header
const es = new EventSource('/payments/stream', { withCredentials: true });
// withCredentials: true → browser sends cookies with the SSE request
```

**WebSocket authentication (more complex):**
```typescript
// Option A: token in query string (INSECURE — logged in access logs)
const ws = new WebSocket('wss://api.example.com/ws?token=eyJ...');

// Option B: token in first message after connect (application protocol)
const ws = new WebSocket('wss://api.example.com/ws');
ws.onopen = () => ws.send(JSON.stringify({ type: 'auth', token: getToken() }));
// Problem: window between connect and auth message — must buffer events

// Option C: custom header in initial handshake (browser limitation)
// Browser WebSocket API does NOT support custom headers — cannot send
// Authorization: Bearer in the upgrade request from browser

// NestJS WebSocket auth must use Socket.io middleware:
io.use(async (socket, next) => {
  const token = socket.handshake.auth.token;  // must pass in auth object
  const user = await validateJwt(token);
  if (!user) return next(new Error('Unauthorized'));
  socket.user = user;
  next();
});
```

**The operational difference:**
With SSE, your JWT guard, cookie session, or any auth middleware handles the SSE endpoint identically to a REST endpoint. JWTs expire and rotate normally — on reconnect, the new request carries the new token. With WebSocket, you must re-implement auth at the socket handshake layer, handle token refresh (the socket is persistent — when the JWT expires, you need to force a reconnect or implement a token refresh sub-protocol), and build middleware that sits outside the standard HTTP middleware chain.

**Q10. How do you handle JWT expiry for long-lived SSE connections?**
A: A JWT with a 15-minute expiry poses no problem for SSE — the client simply reconnects when the EventSource fires an error or when the server sends a `401` and closes the connection. Contrast this with WebSocket, where the socket is persistent and you must implement an in-band token refresh protocol.

```typescript
// Server: validate JWT on each SSE connection (including reconnects)
// If JWT is expired: close the response with an error event
@Get('stream')
async stream(@Req() req: Request, @Res() res: Response): Promise<void> {
  let user: User;
  try {
    user = await this.jwtService.verifyAsync(
      extractBearerToken(req) ?? req.cookies['auth_token']
    );
  } catch {
    // JWT expired or invalid — close SSE stream immediately
    res.setHeader('Content-Type', 'text/event-stream');
    res.flushHeaders();
    res.write('event: auth_error\ndata: {"code":"TOKEN_EXPIRED"}\n\n');
    res.end();
    return;
  }

  // ... normal SSE setup
}
```

```javascript
// Client: refresh token and reconnect on auth_error
const es = new EventSource('/payments/stream', { withCredentials: true });

es.addEventListener('auth_error', async () => {
  es.close(); // close current stream
  await refreshToken(); // refresh JWT (hits /auth/refresh)
  reconnect();          // open new EventSource
});

function reconnect() {
  // New EventSource automatically sends Last-Event-ID from previous session
  window.currentStream = new EventSource('/payments/stream', { withCredentials: true });
  // re-attach listeners...
}
```

## Section 5: Failure Modes and Operational Concerns

**Q11. What are the failure modes specific to SSE, and how do you mitigate them?**
A:

**Failure 1 — Proxy or load balancer buffering:**
Nginx and many proxies buffer HTTP responses. An SSE connection that goes through a buffering proxy does not deliver events until the buffer fills — which for a streaming endpoint that sends small events may never happen. The client sees no events despite the server writing them.

```
Symptom: Events deliver fine in development (direct connection);
         no events in production (Nginx reverse proxy in front).

Fix (Nginx):
  location /payments/stream {
    proxy_pass          http://upstream;
    proxy_buffering     off;           ← disable response buffering
    proxy_cache         off;
    proxy_http_version  1.1;           ← required for chunked transfer
    proxy_set_header    Connection '';
    proxy_read_timeout  3600s;         ← prevent Nginx from closing idle SSE connections
    chunked_transfer_encoding on;
  }

Fix (application):
  res.setHeader('X-Accel-Buffering', 'no'); // tells Nginx to disable buffering for this response
  res.setHeader('Content-Type', 'text/event-stream');
```

**Failure 2 — Load balancer idle timeout:**
AWS ALB default idle timeout is 60 seconds. An SSE connection with no events for 61 seconds is silently closed by the load balancer. The client's EventSource sees the disconnect and reconnects — but merchants see periodic connection drops.

```
Fix: Send a heartbeat comment line every 25 seconds
  Server:
    setInterval(() => res.write(': heartbeat\n\n'), 25_000);
    // ': ' prefix = SSE comment line; EventSource ignores it but counts as activity

  Also: increase ALB idle timeout to 3600s for the SSE target group
    aws elbv2 modify-target-group-attributes \
      --target-group-arn <arn> \
      --attributes Key=deregistration_delay.timeout_seconds,Value=30 \
                   Key=stickiness.enabled,Value=false
```

**Failure 3 — Memory leak from uncleaned connections:**
If the `req.on('close')` cleanup is not registered or throws an error, the subscriber callback for that connection remains in the in-process `Map`. The response object stays referenced. Over hours, terminated connections accumulate and the process leaks memory.

```typescript
// Correct: always register cleanup before any async operation that might fail
req.on('close', () => {
  clearInterval(heartbeat);
  unsubscribe();           // remove from subscribers Map
  // res is automatically garbage-collected once no more references exist
});

// Monitor: track active connection count
gauge('sse.connections.active', this.subscribers.size);
// Alert: if count grows unboundedly over 24h without proportional user growth → leak
```

**Failure 4 — HTTP/1.1 connection limit (browser):**
Browsers limit HTTP/1.1 connections to the same origin to 6. If your app opens more than 6 SSE streams (or SSE streams compete with API requests), requests queue.

```
Fix: serve SSE over HTTP/2
  Any modern reverse proxy (Nginx, Caddy, Envoy) supports HTTP/2 termination.
  SSE streams over HTTP/2 are multiplexed — no 6-connection limit.
  Browser: negotiates HTTP/2 via ALPN in TLS handshake — no client code change.
```

**Failure 5 — EventSource does not support custom headers (browser API limitation):**
The browser `EventSource` API has no option to set custom headers. This means `Authorization: Bearer <token>` cannot be sent on the SSE request from the browser. Workarounds:

```
Option A: Use cookies for auth (recommended)
  Set-Cookie: auth_token=<jwt>; HttpOnly; Secure; SameSite=Strict
  new EventSource('/stream', { withCredentials: true })
  → browser sends the cookie automatically with the SSE request

Option B: Pass token as query parameter (acceptable for short-lived tokens only)
  new EventSource(`/stream?token=${shortLivedToken}`)
  → token appears in server access logs; use short TTL (< 5 minutes)
  → server validates query param token, issues event with ID immediately
  → client gets a session token via first event, uses it for API calls

Option C: Use fetch() with ReadableStream (non-EventSource approach)
  const res = await fetch('/stream', {
    headers: { 'Authorization': `Bearer ${jwt}` }
  });
  const reader = res.body.getReader();
  // manually parse SSE frames from the reader
  // loses EventSource's built-in reconnect and Last-Event-ID
  // only use if Option A and B are infeasible
```

**Q12. How do you handle backpressure — a slow SSE client that cannot consume events fast enough?**
A: Node.js `res.write()` returns `false` when the underlying TCP send buffer is full — the client is not consuming fast enough. Writing more data after a `false` return queues it in Node.js's internal buffer, which grows unboundedly if the client is very slow or disconnected but the connection has not yet timed out.

```typescript
function writeSSEEvent(res: Response, event: unknown): boolean {
  const data = `data: ${JSON.stringify(event)}\n\n`;
  const canContinue = res.write(data);

  if (!canContinue) {
    // Client is slow: TCP send buffer full
    // Option A: wait for drain event before writing more
    res.once('drain', () => {
      // safe to write again
    });

    // Option B: drop events and log — for ephemeral streams (live feeds)
    metrics.increment('sse.events.dropped.backpressure');
    return false;
  }
  return true;
}

// For a subscriber callback:
const unsubscribe = streamService.subscribe(merchantId, (event) => {
  if (!writeSSEEvent(res, event)) {
    // Slow client: close the connection and let them reconnect
    // They will replay missed events via Last-Event-ID
    res.end();
    unsubscribe();
  }
});
```

For payment dashboards, the right policy is usually: close the slow connection, let EventSource reconnect, and replay missed events from the Redis Stream. A forced reconnect is preferable to accumulating queued events in the Node.js process heap.

## Section 6: SSE in a Fintech / Microservices Context

**Q13. How does a payment service emit SSE events to clients in a microservices architecture?**
A: In a microservices architecture, the service that generates the event (payment service) and the service that holds SSE connections (SSE/gateway service) are separate processes. The payment service cannot write to the SSE response directly. The pattern mirrors the WebSocket emitter pattern but is simpler because SSE is just HTTP:

```
[Payment Service] ──(publishes)──▶ [Redis Pub/Sub or Kafka] ──(consumed by)──▶ [SSE Gateway]
                                                                                    │
                                                                                    │ writes to
                                                                                    ▼
                                                                            SSE response streams
                                                                            (merchant browsers)
```

**Option 1 — Redis Pub/Sub (low latency, fire-and-forget):**
```typescript
// In payment service (NestJS): after payment state change
@Injectable()
export class PaymentApprovalService {
  constructor(@InjectRedis() private redis: Redis) {}

  async approvePayment(paymentId: string): Promise<void> {
    // ... business logic, DB write

    const event = {
      id:         `evt_${Date.now()}`,
      type:       'payment.approved',
      payment_id: paymentId,
      merchant_id: payment.merchantId,
      amount:     payment.amount,
      approved_at: new Date().toISOString(),
    };

    // Publish for immediate delivery to SSE gateway
    await this.redis.publish(
      `payment:events:${payment.merchantId}`,
      JSON.stringify(event),
    );

    // Also write to Redis Stream for replay durability
    await this.redis.xadd(
      `merchant:${payment.merchantId}:events`,
      'MAXLEN', '~', '10000',
      '*',
      'data', JSON.stringify(event),
    );
  }
}
```

**Option 2 — Kafka consumer in SSE gateway (durable, ordered):**
```typescript
// SSE gateway: Kafka consumer drives SSE delivery
@Injectable()
export class PaymentEventConsumer implements OnApplicationBootstrap {
  constructor(
    @InjectKafka()              private kafka:         Kafka,
    private readonly streamSvc: PaymentStreamService,
  ) {}

  async onApplicationBootstrap() {
    const consumer = this.kafka.consumer({ groupId: 'sse-gateway' });
    await consumer.connect();
    await consumer.subscribe({ topic: 'payment.events', fromBeginning: false });

    await consumer.run({
      eachMessage: async ({ message }) => {
        const event = JSON.parse(message.value!.toString()) as PaymentEvent;
        // Deliver to all local SSE connections for this merchant
        this.streamSvc.publish(event.merchantId, event);
      },
    });
  }
}
```

**The trade-off between pub/sub and Kafka:**

| Aspect | Redis Pub/Sub | Kafka |
|---|---|---|
| Latency | ~1ms | ~10–50ms |
| Durability | No (fire-and-forget) | Yes (log retention) |
| Replay on reconnect | Via Redis Stream sidecar | Via Kafka offset management |
| Consumer groups | No (all subscribers get all messages) | Yes (SSE gateway scales as consumer group) |
| Operational complexity | Low | Higher |
| Recommendation | Real-time ephemeral feeds | Financial events requiring durability |

**For NACH payment status, settlement notifications, mandate confirmations: use Kafka** as the durable event bus, with Redis pub/sub as a low-latency sidecar for immediate delivery. The SSE gateway reads from Kafka for replay and subscribes to Redis pub/sub for live events — same pattern as Q8 but with Kafka replacing Redis Stream as the durable log.

**Q14. When should a fintech system use SSE, WebSocket, or plain polling?**
A:

```
Use Case → Recommended Transport

Payment status feed (merchant dashboard):
  - Read-only, server → client
  - Occasional events (1–10/second per merchant)
  → SSE ✅ (simpler, stateless, auto-replay)

Live order book / FX tick feed (trading):
  - High frequency (100+ updates/second)
  - Client also sends orders
  → WebSocket ✅ (bidirectional, lower per-frame overhead at high frequency)

Chat / collaborative document editing:
  - Frequent client → server messages
  - Sub-100ms bidirectional latency required
  → WebSocket ✅ (SSE would need separate fetch() per user keystroke)

KYC document processing status:
  - One or two events per document (submitted → verified → approved)
  - Low frequency, read-only
  → SSE ✅ or polling (SSE is cleaner; polling is simpler if events are rare)

Bulk NACH batch progress (% complete):
  - Read-only, slow events (1 event per % completion)
  - Large number of concurrent merchants watching
  → SSE ✅ (stateless, easy to scale, fan-out via Redis Pub/Sub)

Admin operational dashboard (alerts, system events):
  - Low frequency, read-only
  - Admin may filter which events they see
  → SSE ✅ with named event types for client-side filtering

Loan EMI calculation (user changes values, gets instant result):
  - Client drives every interaction
  - No persistent stream needed
  → Polling or REST fetch() ✅ (SSE/WebSocket adds complexity for no benefit)

Multi-party transaction signing (two parties must both confirm):
  - Both parties need to see each other's state
  - State change on one side must appear on the other in < 1 second
  → SSE ✅ for read (server pushes mutual state); REST POST for write (confirm action)
```

**Q15. "Design an SSE-based payment status feed for a merchant dashboard with 10,000 concurrent merchant sessions."**
A:

```
Scale requirements:
  10,000 concurrent SSE connections
  Average 2 connections per merchant (multiple browser tabs)
  Events: 50–500 payment status updates/second across all merchants
  Sub-500ms delivery latency from payment event to client browser
  At-least-once delivery (missed events replayed on reconnect)

Architecture:

┌──────────────────────────────────────────────────────────────────┐
│                    Nginx (HTTP/2 termination)                     │
│    proxy_buffering off; proxy_read_timeout 3600s;                 │
└─────────────────────┬────────────────────────────────────────────┘

          ┌───────────┴──────────┐
          ▼                      ▼

  NestJS + ioredis          NestJS + ioredis
  5,000 connections         5,000 connections
  HPA: 2–10 pods            HPA: 2–10 pods

Each instance:
  - psubscribe('payment:events:*') on Redis sub client
  - In-process Map<merchantId, Set<SSEResponseCallback>>
  - On Redis message: delivers to local SSE connections for that merchantId
  - Heartbeat: writes ': \n\n' every 25s to all connections

Redis:
  - Pub/Sub: payment:events:<merchantId> (live delivery)
  - Streams: merchant:<merchantId>:events (MAXLEN 10000, replay on reconnect)
  - Sentinel: 3-node for HA

Payment Service:
  - On payment state change:
      PUBLISH payment:events:<merchantId> <event JSON>
      XADD merchant:<merchantId>:events ...

Client:
  EventSource('/payments/stream', { withCredentials: true })

Connection math:
  10,000 connections / 2 instances = 5,000 per instance
  5,000 × ~8KB RSS per HTTP response = 40MB per instance (comfortable)
  Each SSE connection = one open file descriptor; check ulimit -n (set to 65536+)
  Redis: 2 connections per instance (pub + sub) × 2 instances = 4 connections (trivial)

Delivery latency breakdown:
  Payment service → Redis PUBLISH:   ~0.5ms
  Redis → SSE instance subscriber:   ~0.5ms
  SSE instance → res.write():         ~0ms
  TCP → client browser:              ~20–80ms (network RTT)
  Total: < 100ms for same-region clients
```

**Q16. "Your SSE stream works in the browser but mobile Safari users report they never receive events. What's wrong?"**
A: Mobile Safari has specific behaviors around background tabs and network changes that cause SSE connections to break in ways desktop browsers do not.

```
Diagnosis:

Issue 1 — App backgrounded: iOS aggressively kills network connections
when the browser is backgrounded. EventSource is silently closed.
Symptom: events stop after user switches apps; resume only after
         explicit page reload (EventSource does not always reconnect
         on iOS when foregrounded).

Issue 2 — Network change (WiFi → cellular): iOS drops and re-establishes
the network interface. The existing TCP connection is terminated. EventSource
reconnects, but on iOS the reconnect can be delayed or fail silently.

Issue 3 — iOS 16 and below: EventSource in WKWebView (used by all
iOS browsers including Chrome/Firefox on iOS — they all use WebKit)
has a known bug where it does not send the Last-Event-ID header on
reconnect, defeating the replay mechanism.

Fixes:

Fix 1: Implement a heartbeat with client-side connection health check
  Server: send ': heartbeat\n\n' every 10 seconds (shorter than desktop 25s)
  Client: if no message received in 15 seconds, close and re-open EventSource

  let lastHeartbeat = Date.now();
  const HEARTBEAT_TIMEOUT = 15_000;

  es.addEventListener('message', () => { lastHeartbeat = Date.now(); });
  es.addEventListener('heartbeat', () => { lastHeartbeat = Date.now(); }); // named heartbeat

  setInterval(() => {
    if (Date.now() - lastHeartbeat > HEARTBEAT_TIMEOUT) {
      es.close();
      reconnect(); // re-opens EventSource with stored lastEventId
    }
  }, 5_000);

Fix 2: Store lastEventId in localStorage; pass it manually on reconnect
  es.addEventListener('message', (e) => {
    if (e.lastEventId) localStorage.setItem('lastPaymentEventId', e.lastEventId);
  });

  function reconnect() {
    const lastId = localStorage.getItem('lastPaymentEventId');
    // EventSource sends Last-Event-ID automatically for its own tracking,
    // but iOS bug workaround: pass it as a query param too
    const url = lastId
      ? `/payments/stream?lastEventId=${lastId}`
      : `/payments/stream`;
    window.currentStream = new EventSource(url, { withCredentials: true });
  }

  // Server: check both Last-Event-ID header and query param
  const lastEventId =
    req.headers['last-event-id'] ??
    (req.query.lastEventId as string | undefined);

Fix 3: Page Visibility API — reconnect when tab becomes visible
  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible') {
      // Reconnect in case iOS killed the connection while backgrounded
      if (!es || es.readyState === EventSource.CLOSED) {
        reconnect();
      }
    }
  });
```

## Quick Reference

| Dimension | SSE | WebSocket |
|---|---|---|
| Direction | Server → Client only | Bidirectional |
| Protocol | HTTP (plain) | WS (upgrade) |
| Proxy compatibility | High | Lower |
| HTTP/2 multiplexing | Yes | No |
| Auto-reconnect | Browser-native (EventSource) | Manual / library |
| Last-Event-ID replay | Browser-native | Manual |
| Auth | Standard HTTP (cookies, headers) | Custom (handshake or first message) |
| Binary support | No (text only) | Yes |
| Horizontal scaling | Stateless HTTP | Sticky sessions or Redis adapter |
| Browser connection limit | Multiplexed over HTTP/2 | 1 TCP per WebSocket |

| SSE is the right choice when... | WebSocket is the right choice when... |
|---|---|
| Server pushes, client only reads | Client sends frequent messages |
| You want free reconnect + replay | You need binary frames |
| Infrastructure is HTTP-only | You need sub-100ms bidirectional latency |
| You want stateless servers | You need custom wire protocols |
| Multiple streams per client (HTTP/2) | High-frequency tick-level data |

| Failure mode | Symptom | Fix |
|---|---|---|
| Proxy buffering | No events received | `proxy_buffering off`; `X-Accel-Buffering: no` |
| LB idle timeout | Connections drop every 60s | Heartbeat comment line every 25s; increase ALB timeout |
| Uncleaned `req.close` handler | Memory leak over hours | Always register cleanup; monitor `subscribers.size` |
| HTTP/1.1 6-connection limit | Requests queue in browser | Serve over HTTP/2 |
| `EventSource` no custom headers | Cannot send `Authorization: Bearer` | Use cookies with `withCredentials: true` |
| iOS backgrounding | Events stop on mobile Safari | Page Visibility API reconnect; shorten heartbeat |
| Slow client backpressure | Node.js heap grows | Drop events or force reconnect on `res.write() === false` |

## The Core Mental Model

```
SSE in one sentence:
  The client makes one HTTP GET; the server never finishes writing the response;
  each write is an event. That's it.

When SSE wins over WebSocket — the three tests:
  Test 1: Does the client ever need to send data through this channel?
           If no → SSE is sufficient; WebSocket is overhead.
  Test 2: Does the client need binary frames?
           If no → SSE works; WebSocket adds nothing.
  Test 3: Is your infrastructure HTTP already?
           If yes → SSE is zero new infrastructure; WebSocket requires
           WS-capable LB, sticky sessions, and a socket adapter library.

The two-client mistake (SSE does NOT have this):
  WebSocket Redis adapter requires two Redis connections (pub + sub).
  SSE needs one sub connection per SSE gateway instance.
  Subscribed Redis clients cannot run other commands — SSE avoids this complexity.

Replay is built in, not bolted on:
  SSE: server writes `id: evt_001\n`; browser stores it; on reconnect sends
       `Last-Event-ID: evt_001`; server replays from Redis Stream starting there.
  WebSocket: you implement this entire protocol yourself.

The HTTP/2 multiplexing advantage:
  5 WebSockets  = 5 TCP connections (browser limit: 6 total per origin)
  5 SSE streams = 5 HTTP/2 streams sharing 1 TCP connection
  Under HTTP/2, SSE scales better than WebSocket for multiple concurrent streams.

The fintech rule:
  Payment status feeds, settlement notifications, batch completion events,
  KYC processing status → SSE.
  Order entry, live order book, collaborative audit tools → WebSocket.
  The signal: if the client POSTs to send and GETs to receive,
  those can be separate channels — use SSE for the receive channel.

Redis Stream + SSE = at-least-once delivery for financial events:
  XADD to stream on publish → XRANGE on reconnect → replay missed events
  Redis Stream survives Redis restart (with AOF); EventSource reconnects automatically
  Zero custom protocol code on the client — just EventSource + last-event-id
```

**Tip for the interview:** SSE questions at 5 YOE reliably go to one of three depth probes: (1) the HTTP/1.1 six-connection limit and how HTTP/2 changes it — knowing that `EventSource` over HTTP/2 multiplexes all streams on one TCP connection and that this makes SSE scale better than WebSocket for multi-stream dashboards signals you understand the transport layer, not just the API; (2) the `Last-Event-ID` replay contract — explaining that the browser stores the last `id:` field value and sends it as `Last-Event-ID` on every reconnect, and that the server uses this to replay from a Redis Stream or Kafka offset, demonstrates that you can design a reliable delivery system without library magic; (3) the proxy buffering gotcha — `X-Accel-Buffering: no` and `proxy_buffering off` in Nginx, and why SSE silently fails without them (the response body is buffered; the client sees nothing until the buffer flushes), is the production detail that separates someone who has actually deployed SSE from someone who tested it only on localhost. The fintech callout: for payment status feeds and NACH batch notifications, SSE is architecturally superior to WebSocket — stateless servers, standard auth middleware, HTTP/2 multiplexing, and built-in replay at zero application protocol cost.
