# Scaling WebSockets Across Multiple Servers — Redis Adapter for Socket.io — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Single-Server WebSockets Break at Scale

**Q1. What breaks when you scale a WebSocket server horizontally without any adaptation?**
A: A single WebSocket server holds all active connections in a process-local data structure — a `Map`, a `Set`, or the socket library's internal registry. Scaling horizontally means running multiple server instances. The moment you add a second instance, three things break:

- **Message delivery fails for connections on other instances**: Instance A holds the WebSocket connection for user `usr_42`. The payment service publishes a status update for `usr_42`. If the publish call reaches Instance B, Instance B has no connection for `usr_42` in its local registry — the message is silently dropped. The user never receives the update.
- **Room and channel broadcasts are incomplete**: If users can subscribe to "payment channel for merchant X", and 100 users are connected across 3 instances, a broadcast to that channel from Instance 1 reaches only the users connected to Instance 1. The other two instances' connections receive nothing.
- **State diverges across instances**: Any in-memory state — who is in which room, who is authenticated, rate limit counters — lives on one instance. Operations on that state from another instance operate on stale data or miss it entirely.

The root cause is the same in every case: the connection registry is local to each process. Horizontal scaling requires the registry and the message routing to become shared across all instances. Redis, as a low-latency shared store with native pub/sub, is the standard solution.

**Q2. What is Socket.io and how does it relate to raw WebSocket?**
A: Socket.io is a library built on top of raw WebSocket (and other transports) that adds:

- **Automatic reconnection**: The client reconnects on disconnect with configurable backoff, re-joining rooms and re-authenticating transparently.
- **Rooms and namespaces**: Server-side grouping abstractions. A room is a named channel; a namespace is an isolated context within the same server (like a virtual server). Events emitted to a room reach all sockets in that room — on any server instance, if a distributed adapter is used.
- **Event-based API**: Instead of raw frame bytes, Socket.io operates on named events (`socket.emit('payment.approved', payload)`, `socket.on('subscribe', handler)`) — an application-level protocol on top of WebSocket framing.
- **Fallback transports**: If WebSocket is unavailable (some corporate proxies block HTTP upgrade), Socket.io falls back to HTTP long-polling on the same connection. The application code is unchanged.
- **Acknowledgements**: `socket.emit('create_payment', data, (response) => {...})` — the server can acknowledge receipt with a return value, turning a fire-and-forget emit into a request-response pattern.

Socket.io's relationship to raw WebSocket: it establishes a WebSocket connection using the standard HTTP upgrade handshake, then sends Socket.io protocol frames (a JSON envelope with event name + payload) over the WebSocket channel. Raw WebSocket clients cannot communicate directly with a Socket.io server without understanding the Socket.io protocol layer.

The **Socket.io adapter** is the pluggable component that determines how events emitted to rooms are distributed across server instances. The default adapter (`in-memory`) routes only within the current process. The Redis adapter replaces this with Redis pub/sub to route across all instances.

## Section 2: The Redis Adapter — Architecture

**Q3. How does the Socket.io Redis adapter work internally?**
A: The Redis adapter replaces Socket.io's in-memory room registry and broadcast mechanism with Redis pub/sub and Redis data structures. Every Socket.io server instance subscribes to a shared Redis channel; when any instance emits to a room or a specific socket, it publishes to Redis, and all instances receive the message and deliver it to whichever of their local connections should receive it.

**The three components of the Redis adapter:**

**Component 1 — Room membership in Redis:**
When a socket joins a room (`socket.join('merchant:merch_42')`), the adapter writes to Redis:
```
SADD socket.io:rooms:merchant:merch_42  <socketId>        ← which sockets are in this room
SADD socket.io:sockets:<socketId>:rooms merchant:merch_42 ← which rooms this socket is in
```
These sets are the shared source of truth — any instance can query who is in a room.

**Component 2 — Pub/Sub for event delivery:**
When an instance emits to a room (`io.to('merchant:merch_42').emit('payment.approved', data)`):
```
PUBLISH socket.io#<namespace>  {
  uid:   "instance-1-uuid",
  type:  "broadcast",
  data:  {
    opts: { rooms: ["merchant:merch_42"], flags: {} },
    packet: { type: 2, nsp: "/", data: ["payment.approved", { ... }] }
  }
}
```
All instances (including the publisher itself) receive this message on their subscriber connection. Each instance:
1. Checks which of its locally connected sockets are in `merchant:merch_42`.
2. Delivers the event to those local connections.
3. Ignores the message if none of its local connections are in the room.

**Component 3 — Across-instance socket operations:**
Disconnect a specific socket, make it join/leave a room — operations that may need to reach a socket on another instance. The adapter serializes these as pub/sub messages of type `"fetch_sockets"`, `"add_sockets"`, `"del_sockets"`, `"disconnect_sockets"`, etc.

**Data flow diagram:**
```
Payment service
    │
    │  io.to('merchant:merch_42').emit('payment.approved', data)
    ▼
[Socket.io Instance 1]
    │ Redis adapter intercepts the emit
    │
    ├─ PUBLISH socket.io#/ { rooms: ['merchant:merch_42'], packet: [...] }
    │
    ▼
[Redis Pub/Sub Channel: socket.io#/]
    │
    ├──────────────────────────────────────────┐
    ▼                                          ▼
[Instance 1 subscriber]              [Instance 2 subscriber]
    │                                          │
    │ local sockets in room?                   │ local sockets in room?
    │ → ws_A (usr_10) ✅                       │ → ws_C (usr_42) ✅
    │ → ws_B (usr_17) ✅                       │ → ws_D (usr_88) ✅
    │                                          │
    ▼                                          ▼
usr_10 receives payment.approved     usr_42 receives payment.approved
usr_17 receives payment.approved     usr_88 receives payment.approved
```

**Q4. What is the difference between `socket.io-adapter/redis` (legacy) and `@socket.io/redis-adapter` (current), and what changed architecturally?**
A: Two separate packages exist for different Socket.io versions, with significantly different internal architectures:

**Legacy: `socket.io-redis` (Socket.io v2/v3):**
Used a single Redis pub/sub channel for all messages across all namespaces. Every adapter instance subscribed to one channel and received every message from every instance — including messages for rooms it had no connections to. At scale, this meant every instance processed a large volume of pub/sub messages to discard most of them. Also used `socket.io-emitter` as a separate package for emitting from non-Socket.io processes.

**Current: `@socket.io/redis-adapter` (Socket.io v4+):**
```bash
npm install @socket.io/redis-adapter
```

Architectural improvements:

- **Per-namespace channels**: Each Socket.io namespace gets its own Redis pub/sub channel (`socket.io#<namespace>#`). Instances subscribed to namespace `/payments` only receive messages for that namespace, reducing irrelevant traffic.
- **Redis Streams support** (optional): Can use Redis Streams instead of pub/sub for message delivery, providing message persistence and ordered delivery — important for reliably delivering missed events after reconnect.
- **Built-in emitter**: `@socket.io/redis-emitter` for publishing events from any process (not just Socket.io server instances) — payment services, background jobs, and other microservices can emit Socket.io events without running a Socket.io server.
- **Rooms stored per-instance**: Room membership is tracked per-server-instance in Redis hashes (not a global set), enabling efficient cleanup when an instance crashes.

```javascript
// Current setup (@socket.io/redis-adapter, Socket.io v4)
const { createServer } = require('http');
const { Server }       = require('socket.io');
const { createAdapter } = require('@socket.io/redis-adapter');
const { createClient } = require('redis');

const httpServer = createServer();
const io         = new Server(httpServer, { cors: { origin: '*' } });

// Two Redis clients: one for pub, one for sub
// (Redis subscriber connections cannot be used for other commands)
const pubClient = createClient({ url: process.env.REDIS_URL });
const subClient = pubClient.duplicate();

await Promise.all([pubClient.connect(), subClient.connect()]);

io.adapter(createAdapter(pubClient, subClient));

httpServer.listen(3000);
```

## Section 3: Redis Pub/Sub vs Redis Streams for Socket.io

**Q5. When should you use Redis Streams instead of Redis Pub/Sub as the Socket.io adapter backend?**
A: The choice between pub/sub and streams reflects the durability and ordering requirements of your message delivery:

**Redis Pub/Sub (the default):**
- Fire-and-forget: if an instance is temporarily disconnected from Redis when a message is published, it misses that message permanently.
- No message history: a new Socket.io instance that starts after a message was published cannot retrieve that message.
- Low latency: messages are delivered in-memory without disk writes.
- Appropriate when: messages are ephemeral (live event feeds, presence updates, typing indicators) and missing one due to a brief Redis hiccup is acceptable.

**Redis Streams (optional, `@socket.io/redis-adapter` with `streamName` option):**
- Persistent log: messages are written to a Redis Stream (an append-only log), retained for a configurable duration.
- Consumer groups: each Socket.io instance is a consumer in a Redis consumer group — it reads messages sequentially, acknowledges processed messages, and can resume from its last position after reconnect.
- At-least-once delivery: a message published while an instance was down is delivered when the instance reconnects and reads from the stream.
- Higher latency: stream reads add a round-trip; acknowledgment adds another.
- Appropriate when: missed messages are a business problem (payment status updates that must reach the client, financial notifications, alert deliveries).

```javascript
// Redis Streams adapter setup
const { createAdapter } = require('@socket.io/redis-adapter');

io.adapter(createAdapter(pubClient, subClient, {
  streamName:  'socket.io',   // Redis Stream key
  maxLen:      10_000,        // MAXLEN — trim stream to last 10k messages
  readCount:   100,           // read 100 messages per batch
  sessionKeyPrefix: 'sio:',
}));
```

**The fintech recommendation**: use Redis Streams for any WebSocket channel carrying payment state changes. A payment status update (`PENDING → APPROVED`) that is missed during a 2-second Redis hiccup represents a user seeing incorrect state until they manually refresh. Streams give you at-least-once delivery and the ability to replay missed messages on reconnect — a meaningful reliability improvement for financial dashboards.

## Section 4: Rooms and Namespaces in a Distributed Context

**Q6. How do Socket.io rooms work across multiple instances with the Redis adapter?**
A: A room is a named group that sockets can join and leave. Events emitted to a room are delivered to all sockets in that room — across all instances, because the Redis adapter distributes the emit.

**Room operations:**
```javascript
// Server-side: add a socket to a room when it subscribes
io.on('connection', (socket) => {
  socket.on('subscribe', ({ merchantId }) => {
    // Joins the room 'merchant:merch_42'
    // Adapter writes to Redis: SADD sio:rooms:merchant:merch_42 <socketId>
    socket.join(`merchant:${merchantId}`);
    socket.emit('subscribed', { room: `merchant:${merchantId}` });
  });

  socket.on('unsubscribe', ({ merchantId }) => {
    socket.leave(`merchant:${merchantId}`);
  });

  // Socket automatically leaves all rooms on disconnect
  // Adapter cleans up Redis membership on disconnect
});

// Emitting to a room from anywhere in the process:
io.to('merchant:merch_42').emit('payment.approved', { payment_id: 'pay_001' });

// From the payment service (different process, using redis-emitter):
const { Emitter } = require('@socket.io/redis-emitter');
const emitter = new Emitter(redisClient);
emitter.to('merchant:merch_42').emit('payment.approved', { payment_id: 'pay_001' });
```

**What happens on the wire when `socket.join('merchant:merch_42')` is called:**
```
Instance receives socket.join call
  ↓
Adapter adds socketId to local room map (in-memory, this instance)
  ↓
Adapter writes to Redis:
  SADD sio:rooms:merchant:merch_42 <socketId>
  SADD sio:sids:<socketId>         merchant:merch_42

When the socket disconnects:
  Adapter removes from in-memory map
  SREM sio:rooms:merchant:merch_42 <socketId>
  SREM sio:sids:<socketId>         merchant:merch_42
  If set becomes empty: DEL sio:rooms:merchant:merch_42
```

**Room membership query across instances:**
```javascript
// How many sockets are in this room, across all instances?
const sockets = await io.in('merchant:merch_42').fetchSockets();
console.log(`${sockets.length} connections watching merchant merch_42`);

// Get socket IDs in a room (Redis query under the hood):
const socketIds = await io.in('merchant:merch_42').allSockets();
```

**Q7. What are Socket.io namespaces and when do you use them over rooms?**
A: Namespaces are isolated Socket.io contexts within the same server — each namespace has its own event handlers, middleware, and room set. Clients connect to a specific namespace at the URL level:

```javascript
// Server: define namespaces
const paymentsNs = io.of('/payments');  // namespace for payment events
const adminNs    = io.of('/admin');     // namespace for admin dashboard

paymentsNs.on('connection', (socket) => {
  socket.on('subscribe', ({ merchantId }) => socket.join(`merchant:${merchantId}`));
});

adminNs.use(adminAuthMiddleware);  // different auth for admin namespace
adminNs.on('connection', (socket) => {
  socket.join('admin-broadcast');
});

// Client: connect to a specific namespace
const paymentsSocket = io('https://api.example.com/payments');
const adminSocket    = io('https://api.example.com/admin',
                           { auth: { token: adminToken } });
```

**Rooms vs. Namespaces — the decision:**

| Dimension | Rooms | Namespaces |
|---|---|---|
| Scope | Dynamic groups within a namespace | Fixed contexts defined at server startup |
| Auth/middleware | Shared with namespace | Per-namespace (different auth per namespace) |
| Event isolation | Events can leak across rooms with `io.emit` | Events in namespace A never reach namespace B |
| Redis channels | Share the namespace's pub/sub channel | Each namespace has its own Redis channel |
| Client connection | One connection, join/leave rooms dynamically | Separate connection per namespace |
| Use case | User subscriptions to entities (merchants, payments) | Logical separation of concerns (payments vs. admin) |

**The production pattern**: namespaces for top-level concerns that need independent middleware and authentication (`/payments`, `/admin`, `/internal`); rooms for dynamic subscriptions within a namespace (`merchant:merch_42`, `payment:pay_001:watchers`).

## Section 5: The Redis Emitter — Publishing from External Services

**Q8. What is `@socket.io/redis-emitter` and why is it necessary in a microservices architecture?**
A: The `@socket.io/redis-emitter` allows any process — a payment service, a background job, a Kafka consumer — to emit Socket.io events to connected clients without being a Socket.io server itself. It publishes the event to the Redis channel that all Socket.io server instances subscribe to; they receive it and deliver it to the appropriate connections.

Without the emitter, the only way to trigger a Socket.io event is from within the Socket.io server process itself. This is fine for a monolith but breaks in a microservices architecture where the payment service (which knows a payment was approved) is a separate process from the WebSocket server (which holds client connections).

```javascript
// In the payment service (NestJS microservice — NOT a Socket.io server)
import { Emitter } from '@socket.io/redis-emitter';
import { createClient } from 'redis';

@Injectable()
export class PaymentNotificationService {
  private emitter: Emitter;

  constructor() {
    const redisClient = createClient({ url: process.env.REDIS_URL });
    redisClient.connect();
    this.emitter = new Emitter(redisClient);
  }

  async notifyPaymentApproved(payment: Payment): Promise<void> {
    // Emit to the 'merchant:merch_42' room across all WebSocket server instances
    this.emitter
      .of('/payments')              // target namespace
      .to(`merchant:${payment.merchantId}`)  // target room
      .emit('payment.approved', {
        payment_id:  payment.id,
        amount:      payment.amount,
        currency:    payment.currency,
        approved_at: new Date().toISOString(),
      });
    // No await needed — publish to Redis is fire-and-forget for pub/sub adapter
    // Use Streams adapter if you need delivery confirmation
  }

  async notifyUserDirectly(userId: string, event: string, data: unknown): Promise<void> {
    // Emit to a specific socket (user's connection)
    // Requires that socket.join(`user:${userId}`) was called on connect
    this.emitter
      .of('/payments')
      .to(`user:${userId}`)
      .emit(event, data);
  }
}
```

**The full message path with the emitter:**
```
[Payment Service]
  emitter.to('merchant:merch_42').emit('payment.approved', data)
    │
    │ Emitter publishes to Redis:
    │ PUBLISH socket.io#/payments#
    │   { uid: "emitter-uuid", type: "broadcast",
    │     data: { opts: { rooms: ["merchant:merch_42"] },
    │             packet: { data: ["payment.approved", {...}] } } }
    ▼
[Redis Pub/Sub]
    │
    ├─────────────────────────────────────┐
    ▼                                     ▼
[WS Instance 1]                    [WS Instance 2]
  Receives pub/sub message           Receives pub/sub message
  Checks local sockets in room       Checks local sockets in room
  merchant:merch_42                  merchant:merch_42
  → socket_A: delivers ✅            → socket_C: delivers ✅
  → socket_B: delivers ✅            → (no other local sockets)
```

**Q9. How do you emit to a specific user (not a room) across instances?**
A: Socket IDs are instance-local — a socket ID generated on Instance 1 is meaningless on Instance 2. Emitting to a socket ID directly works only if the target socket is on the same instance. For cross-instance delivery to a specific user, the pattern is: **join each user to a personal room named by their user ID** on connection.

```javascript
// Server: on connect, join personal room
io.of('/payments').on('connection', (socket) => {
  const userId = socket.handshake.auth.userId; // from JWT validation

  // Personal room — one per user, named by user ID
  socket.join(`user:${userId}`);

  // Entity rooms — user subscribes dynamically
  socket.on('watch_payment', ({ paymentId }) => {
    socket.join(`payment:${paymentId}:watchers`);
  });
});

// Payment service: emit to a specific user across all instances
emitter.of('/payments').to(`user:${userId}`).emit('payment.status', data);
```

**What this achieves:**
```
User usr_42 connected to Instance 2:
  socket.join('user:usr_42')  → Redis: SADD sio:rooms:user:usr_42 <socketId>

Payment service emits to user:usr_42:
  PUBLISH socket.io#/payments# { rooms: ['user:usr_42'], packet: [...] }

Instance 1 receives: no local socket in room user:usr_42 → ignored
Instance 2 receives: socket <socketId> is in room user:usr_42 → delivered ✅
```

**Handling multiple sessions (same user on multiple devices):**
The `user:${userId}` room contains all socket IDs for that user — if they are logged in on two browser tabs or two devices, both sockets are in the room. Emitting to the room delivers to all active sessions simultaneously. This is usually the desired behavior (a payment approval should appear on all the user's open dashboards), but if you need to target a specific session, you need a more granular room key (`user:${userId}:session:${sessionId}`).

## Section 6: State Management and Failure Handling

**Q10. What happens to room memberships and in-flight messages when a Socket.io server instance crashes?**
A: An instance crash without a clean shutdown (OS kill, OOM, hardware failure) has several consequences that the Redis adapter must handle:

**Problem 1 — Stale room membership in Redis:**
The crashed instance cannot clean up its sockets' room memberships — the `SREM` calls in the disconnect handler never run. Redis retains the now-defunct socket IDs in the room sets:
```
sio:rooms:merchant:merch_42:  { socket_A, socket_B, socket_DEAD_1, socket_DEAD_2 }
                                                     ↑ these still in Redis
```
Future emits to `merchant:merch_42` are published to Redis. The surviving instances check their local connections — they have no socket matching `socket_DEAD_1` or `socket_DEAD_2`, so they silently ignore them. The stale entries cause no delivery failure, but they consume Redis memory and make `fetchSockets()` return inaccurate counts.

**Cleanup mechanism:**
The `@socket.io/redis-adapter` addresses this with server IDs and cleanup on startup/heartbeat:
```
Each instance registers on startup:
  SETEX sio:servers:<serverId>  30  "alive"   ← TTL heartbeat

Background task (every 10s):
  KEYS sio:servers:*  → find all registered servers
  Servers not seen recently (TTL expired) → crashed
  For each crashed server: clean up its room memberships

On controlled shutdown (SIGTERM):
  io.close()  → Socket.io disconnects all local sockets (runs disconnect handlers)
             → Adapter cleans up Redis membership for all local sockets
             → DEL sio:servers:<serverId>
```

**Problem 2 — In-flight pub/sub messages lost:**
If Instance 2 crashes while a pub/sub message is being delivered to one of its sockets, that delivery attempt is lost. With the pub/sub adapter, there is no retry — the message was received by the instance's subscriber connection but the instance died before delivering it. The client on that crashed connection will reconnect (Socket.io automatic reconnection) but will not receive the missed event.

**This is the fundamental limitation of the pub/sub adapter — messages are not durable.**

Mitigation:
- **Client-side: request missed events on reconnect:**
  ```javascript
  // Client: on reconnect, send last received event timestamp
  socket.on('connect', () => {
    const lastEventAt = localStorage.getItem('lastPaymentEventAt');
    if (lastEventAt) {
      socket.emit('replay_missed_events', { since: lastEventAt });
    }
  });

  // Server: serve missed events from Kafka or DB
  socket.on('replay_missed_events', async ({ since }) => {
    const missed = await paymentEventRepo.findSince(since, socket.merchantId);
    missed.forEach(event => socket.emit('payment.status_changed', event));
  });
  ```
- **Server-side: Redis Streams adapter** (Q5) for at-least-once delivery.
- **Idempotent event handling on the client**: even if an event is delivered twice (once from the stream, once from the reconnect replay), the client should handle duplicates gracefully by checking the event's unique ID.

**Q11. How do you handle Socket.io reconnection in a multi-instance environment?**
A: Socket.io's automatic reconnection is built into the client library — on disconnect, it attempts to reconnect with exponential backoff. In a multi-instance environment, the reconnection may land on a different instance than the original connection.

**What reconnecting to a different instance means:**
- The socket gets a new socket ID (the old one was on the crashed/overloaded instance).
- Room memberships are lost from the new instance's perspective — `socket.join()` was called on the old instance.
- Any in-memory state on the old instance (rate limit counters, pending work) is gone.

**The solution: stateless server design + re-join on reconnect:**

```javascript
// Server: handle reconnect by re-establishing state from the client's auth token
io.of('/payments').use(async (socket, next) => {
  // Authentication on every connection (including reconnects)
  const token    = socket.handshake.auth.token;
  const user     = await validateJwt(token);
  if (!user) return next(new Error('Authentication failed'));

  socket.userId     = user.id;
  socket.merchantId = user.merchantId;
  next();
});

io.of('/payments').on('connection', async (socket) => {
  // Always join personal rooms on connection (works for first connect AND reconnect)
  socket.join(`user:${socket.userId}`);
  socket.join(`merchant:${socket.merchantId}`);

  // Restore entity subscriptions from persistent store (not in-memory)
  const subscriptions = await redis.smembers(`user:${socket.userId}:subscriptions`);
  for (const room of subscriptions) {
    socket.join(room);
  }

  // Inform client of its new socket ID (for tracking/debugging)
  socket.emit('session', {
    socketId:   socket.id,
    userId:     socket.userId,
    merchantId: socket.merchantId,
  });
});

// When a user subscribes to a payment — store in Redis, not just socket.join
socket.on('watch_payment', async ({ paymentId }) => {
  const room = `payment:${paymentId}:watchers`;
  socket.join(room);
  // Persist so it survives reconnect
  await redis.sadd(`user:${socket.userId}:subscriptions`, room);
  await redis.expire(`user:${socket.userId}:subscriptions`, 86400); // 24h TTL
});

socket.on('disconnect', async () => {
  // Don't clean up subscriptions on disconnect — they persist for reconnect
  // They'll be cleaned by TTL expiry or explicit unsubscribe
});
```

**Client-side reconnection with missed event recovery:**
```javascript
const socket = io('https://api.example.com/payments', {
  auth: { token: getAuthToken() },
  reconnectionDelay:    1000,     // initial backoff: 1s
  reconnectionDelayMax: 30000,    // max backoff: 30s
  reconnectionAttempts: Infinity, // retry forever
});

let lastEventId = localStorage.getItem('lastEventId') ?? null;

socket.on('payment.status_changed', (data) => {
  // Track last received event for replay on reconnect
  lastEventId = data.event_id;
  localStorage.setItem('lastEventId', lastEventId);
  renderPaymentUpdate(data);
});

socket.on('connect', () => {
  // Request missed events since last received
  if (lastEventId) {
    socket.emit('replay_since', { last_event_id: lastEventId });
  }
});
```

## Section 7: Operational Concerns

**Q12. What Redis configuration is required for production Socket.io deployments, and what are the failure modes?**
A: Redis is now on the critical path for every WebSocket message delivery — its failure modes become your WebSocket service's failure modes.

**Required Redis configuration:**

**Persistence:**
Socket.io room membership data and the server registry live in Redis. If Redis restarts without persistence and loses all keys:
- Room membership is gone — all active subscriptions are lost until sockets re-join.
- Server registry is gone — stale membership cleanup cannot identify crashed servers.

```
# redis.conf
save 900 1      # RDB snapshot: save if 1 key changed in 900 seconds
save 300 10     # save if 10 keys changed in 300 seconds
appendonly yes  # AOF persistence: log every write command
appendfsync everysec  # fsync AOF file every second (balance of durability vs perf)
```

For pub/sub only (no stream adapter), persistence is less critical — room membership is rebuilt as sockets reconnect. For Streams adapter, AOF persistence is important so messages in the stream survive Redis restarts.

**Memory management:**
Socket.io room membership sets and the stream can grow unboundedly. Configure `maxmemory` and an eviction policy:
```
maxmemory        2gb
maxmemory-policy allkeys-lru   # evict least-recently-used keys when memory is full
```
With `allkeys-lru`, Redis may evict room membership sets under memory pressure — causing silent message loss. Monitor Redis memory usage and set `maxmemory` high enough to never trigger eviction in normal operation.

**Two Redis connections per Socket.io instance:**
The Redis adapter requires two clients — one for publishing (`PUBLISH`), one for subscribing (`SUBSCRIBE`). A subscribed Redis client cannot execute other commands (it is in subscription mode). With 10 Socket.io instances, that is 20 Redis connections. At 50 instances, 100 connections. This is well within Redis's connection capacity (default `maxclients: 10000`), but monitor Redis's `connected_clients` metric.

**Redis failure handling:**
```javascript
pubClient.on('error', (err) => {
  logger.error('Redis publisher error', { err });
  // Socket.io continues serving local connections during Redis outage
  // Cross-instance delivery stops — only connections on this instance receive emits
  metrics.increment('redis.pub.errors');
});

subClient.on('error', (err) => {
  logger.error('Redis subscriber error', { err });
  // This instance stops receiving events from other instances
  // Most critical failure mode — monitor this
  metrics.increment('redis.sub.errors');
});

// Reconnection: ioredis reconnects automatically
// On reconnect, re-subscribe to all channels (ioredis does this automatically)
```

**Redis Sentinel or Cluster for high availability:**
```javascript
// Redis Sentinel: automatic failover to replica if primary fails
const pubClient = new Redis({
  sentinels: [
    { host: 'sentinel-1', port: 26379 },
    { host: 'sentinel-2', port: 26379 },
    { host: 'sentinel-3', port: 26379 },
  ],
  name: 'mymaster',
});

// Redis Cluster: horizontal sharding of data
// Note: Redis Cluster pub/sub broadcasts to ALL nodes
// Socket.io Redis adapter works with Cluster but with higher network traffic
const pubClient = new Redis.Cluster([
  { host: 'redis-node-1', port: 6379 },
  { host: 'redis-node-2', port: 6379 },
  { host: 'redis-node-3', port: 6379 },
]);
```

**Q13. How do you monitor the health of a scaled Socket.io deployment?**
A: Monitoring a distributed WebSocket system requires visibility into three layers: connection state, message delivery, and Redis health.

**Key metrics to instrument:**

```javascript
// Connection metrics — on each instance
io.of('/payments').on('connection', (socket) => {
  metrics.gauge('websocket.connections.active', io.of('/payments').sockets.size);
  metrics.increment('websocket.connections.total');

  socket.on('disconnect', (reason) => {
    metrics.gauge('websocket.connections.active', io.of('/payments').sockets.size);
    metrics.increment(`websocket.disconnections.${reason}`);
    // reason: 'transport close', 'ping timeout', 'server namespace disconnect', etc.
  });
});

// Message delivery metrics
io.of('/payments').on('connection', (socket) => {
  const originalEmit = socket.emit.bind(socket);
  socket.emit = (event, ...args) => {
    metrics.increment(`websocket.messages.sent.${event}`);
    return originalEmit(event, ...args);
  };
});

// Redis adapter metrics
const adapter = io.of('/payments').adapter;
adapter.on('error', (err) => {
  metrics.increment('redis.adapter.errors');
  logger.error('Redis adapter error', { err });
});
```

**Alerts to configure:**

```
Alert: websocket.connections.active drops > 20% in 5 minutes
  → Probable cause: instance crash, load balancer issue, or mass client disconnect
  → Action: check instance health, load balancer logs, client error rates

Alert: redis.adapter.errors > 0 for 60 seconds
  → Probable cause: Redis connection issue
  → Action: check Redis health, network connectivity between instances and Redis

Alert: websocket.disconnections.ping_timeout rate > 5% of connections/minute
  → Probable cause: network issues, client-side keep-alive problems
  → Action: check network stability, load balancer idle timeout configuration

Alert: redis.sub.errors > 0
  → Probable cause: subscriber connection dropped
  → Action: critical — cross-instance delivery is broken; restart instance if needed

Alert: P99 message delivery latency > 500ms
  → Probable cause: Redis latency spike, instance overload
  → Action: check Redis latency (redis-cli --latency), instance CPU/memory
```

**Synthetic monitoring — end-to-end delivery test:**
```javascript
// Canary: every 30 seconds, send a test event and verify delivery
setInterval(async () => {
  const testId     = `canary-${Date.now()}`;
  const startTime  = Date.now();

  // Listen for the canary event to come back via the Redis adapter
```

## Section 8: Scenario / System Design Style Questions

**Q14. "Design the complete scaled WebSocket architecture for a payment dashboard serving 50,000 concurrent merchant connections across multiple regions."**
A:

```
Scale requirements:
  50,000 concurrent connections
  ~20 instances of the WebSocket service (2,500 connections per instance — safe headroom)
  Sub-100ms message delivery from payment event to client browser
  99.9% uptime for the WebSocket service

Architecture:

┌─────────────────────────────────────────────────────────┐
│                    CDN / Global LB                       │
│   (Route to nearest region; GeoDNS or Anycast)          │
└─────────────┬─────────────────────────┬─────────────────┘
              │                         │
    ┌─────────▼──────────┐   ┌─────────▼──────────┐
    │   Region: Mumbai    │   │   Region: Singapore │
    │                     │   │                     │
    │  ALB (WebSocket)    │   │  ALB (WebSocket)    │
    │  Idle timeout: 3600s│   │  Idle timeout: 3600s│
    │  Sticky: cookie     │   │  Sticky: cookie     │
    │                     │   │                     │
    │  WS Instances (10)  │   │  WS Instances (10)  │
    │  NestJS + Socket.io │   │  NestJS + Socket.io │
    │  HPA: 2-20 pods     │   │  HPA: 2-20 pods     │
    │                     │   │                     │
    │  Redis Cluster      │   │  Redis Cluster      │
    │  (3 shards, 3 replicas each)                  │
    └─────────────────────┘   └─────────────────────┘
              │                         │
    ┌─────────▼─────────────────────────▼─────────────────┐
    │              Kafka: payment.events topic              │
    │   (cross-region replication for global consistency)   │
    └─────────────────────────────────────────────────────-┘

WebSocket service (per instance):

  Namespaces:
    /payments  — merchant-facing; JWT auth; rate limited
    /admin     — internal; mTLS auth; for ops team

  On connection:
    1. Validate JWT → extract merchantId, userId
    2. socket.join(`merchant:${merchantId}`)
    3. socket.join(`user:${userId}`)
    4. Restore subscriptions from Redis
    5. Emit 'session' event with socketId

  Rooms:
    merchant:{merchantId}          — all sockets for a merchant
    user:{userId}                  — specific user across devices
    payment:{paymentId}:watchers   — all users watching a specific payment

  Adapter:
    @socket.io/redis-adapter with Redis Streams
    (durability for payment events; at-least-once delivery)

  Emitter (in payment service):
    @socket.io/redis-emitter
    On PaymentApproved domain event:
      emitter.to(`merchant:${merchantId}`).emit('payment.approved', payload)
      emitter.to(`payment:${paymentId}:watchers`).emit('payment.status_changed', payload)

Kafka consumer (in WebSocket service):
  Consumes payment.events topic
  For each event:
    emitter.of('/payments').to(`merchant:${event.merchantId}`)
           .emit('payment.status_changed', event)

  Why Kafka as source of truth (not just Redis emitter from payment service):
    - Payment service may crash mid-emission — Kafka consumer ensures delivery
    - All events are in Kafka regardless of how many WS instances exist
    - WS service can replay missed events from Kafka on reconnect

Reconnect + replay:
  Client sends: { type: 'replay_since', last_event_id: 'evt_001' }
  Server fetches from Kafka (or DB): all events for merchantId since evt_001
  Delivers as burst, then resumes streaming

Connection counts:
  50,000 connections / 20 instances = 2,500 per instance
  2,500 × ~50KB per connection = 125MB per instance (manageable; Node.js v8 heap)
  Node.js single-threaded: 2,500 connections with async I/O is fine at low message rate
  CPU: spikes on bulk broadcasts (all 50k merchants on a system-wide announcement)
       mitigated by chunked broadcasting with setImmediate between batches
```

**Q15. "You deploy a new Socket.io server instance and merchants start complaining that they stop receiving payment updates. The issue disappears when you scale back to the original instance count. What's wrong?"**
A: This is a classic symptom of load balancer misconfiguration combined with WebSocket state mismatch. The diagnostic sequence:

```
Symptom: Adding instances breaks event delivery for existing connections.
          Removing new instances restores delivery.
          → Existing connections are being routed to new instances on subsequent requests

Step 1: Check if sticky sessions are configured
  Inspect load balancer config:
    AWS ALB: Target Group → Attributes → Stickiness: Enabled?
    If disabled: round-robin routing sends subsequent requests to any instance
    → WebSocket upgrade went to Instance 1; subsequent requests go to Instance 2
    → Socket.io's HTTP long-polling fallback (if active) goes to wrong instance

  Check if clients are using WebSocket or long-polling:
    Browser DevTools → Network → Filter: WS or XHR
    If XHR with 'polling' in URL: Socket.io is in long-polling mode
    → Long-polling REQUIRES sticky sessions (each poll is a new HTTP request)
    → WebSocket is a persistent connection (doesn't need sticky, but doesn't hurt)

Step 2: Verify the Redis adapter is configured on the new instance
  The new instance may be starting without the Redis adapter:
    Check startup logs: "Redis adapter connected" message present?
    Check environment variables on the new instance: REDIS_URL set?
    If missing: new instance has in-memory adapter → no cross-instance delivery

  Verify Redis connectivity from new instance:
    redis-cli -u $REDIS_URL ping → PONG?
    Check Redis subscriber connections: redis-cli CLIENT LIST | grep sub

Step 3: Check Redis pub/sub channel subscription
  redis-cli PUBSUB CHANNELS 'socket.io*'
  → Should show channels for each namespace
  → Count should increase when new instance starts (new subscriber)
  → If count doesn't increase: new instance is not subscribing to Redis

Step 4: Check for version mismatch
  If new instances have a different version of @socket.io/redis-adapter:
    Pub/sub message format may differ between versions
    Old instances publish in format A; new instance expects format B
    → Messages from old instances are ignored by new instance and vice versa

  npm ls @socket.io/redis-adapter  (on each instance)
  → All instances must use the same major version

Fixes:
  If sticky sessions missing:
    Enable application-based sticky sessions on ALB
    Or switch to WebSocket-only (no long-polling) — WebSocket itself is persistent

  If Redis adapter missing on new instance:
    Fix deployment configuration (environment variables, Docker image)
    Add startup health check that verifies Redis connection before marking instance ready

  If version mismatch:
    Pin @socket.io/redis-adapter to a specific version in package.json
    Redeploy all instances with the same version

Prevention:
  Add a startup check:
    On startup, publish a test message to Redis and verify receipt via subscriber
    If verification fails: refuse to start (fail readiness probe in Kubernetes)
    This prevents an instance without a working Redis adapter from
    being added to the load balancer rotation
```

**Q16. "A bulk payment batch completes and you need to notify all 10,000 merchants simultaneously. How do you handle this without overwhelming the WebSocket servers or Redis?"**
A: Broadcasting to 10,000 rooms simultaneously — each room potentially containing multiple sockets — creates a Redis pub/sub spike and a per-instance CPU spike for serializing and sending frames. Naive implementation:

```javascript
// NAIVE — avoid: publishes 10,000 messages to Redis simultaneously
for (const merchantId of approvedMerchantIds) {
  emitter.to(`merchant:${merchantId}`).emit('batch.completed', summary);
  // 10,000 PUBLISH commands in a tight loop
  // Redis: 10,000 pub/sub deliveries in milliseconds
  // WS instances: receive 10,000 messages nearly simultaneously
  // → CPU spike; potential Redis connection timeout; possible OOM
}
```

**Controlled broadcast with chunking and backpressure:**

```javascript
async function broadcastBatchCompletion(merchantIds: string[], summary: BatchSummary) {
  const CHUNK_SIZE  = 100;   // publish 100 per batch
  const CHUNK_DELAY = 50;    // 50ms between batches → 10k merchants over 5 seconds

  for (let i = 0; i < merchantIds.length; i += CHUNK_SIZE) {
    const chunk = merchantIds.slice(i, i + CHUNK_SIZE);

    // Publish this chunk to Redis
    await Promise.all(
      chunk.map(merchantId =>
        emitter
          .of('/payments')
          .to(`merchant:${merchantId}`)
          .emit('batch.completed', summary)
      )
    );

    // Yield between chunks: prevents Redis connection saturation
    // and gives WS instances time to process the previous chunk's deliveries
    if (i + CHUNK_SIZE < merchantIds.length) {
      await sleep(CHUNK_DELAY);
    }
  }
}
// Total time: (10,000 / 100) × 50ms = 5 seconds
// Redis load: 100 PUBLISH commands per 50ms — easily handled
// WS instances: 100 messages per 50ms per instance — negligible CPU
```

**Alternative: single broadcast to a meta-room:**
If all 10,000 merchants should always receive batch events, don't emit to individual rooms — maintain a single room that all merchants join:

```javascript
// On connection: join the batch notifications room
socket.join('batch-notifications');  // all merchants join this

// On batch completion: one emit, not 10,000
emitter.of('/payments').to('batch-notifications').emit('batch.completed', summary);
// Redis: 1 PUBLISH
// WS instances: each delivers to all local sockets in 'batch-notifications'
```

This is O(1) in Redis pub/sub messages regardless of merchant count. The WS instances still do O(connections) work to serialize and send the frame to each socket, but this is distributed across all instances and is simple iteration — far more efficient than 10,000 Redis publishes.

**The trade-off:**
Single meta-room is efficient but inflexible — every member gets every event regardless of filtering preference. Per-merchant rooms are filterable but expensive at large fan-out. The production pattern: per-merchant rooms for targeted notifications (a specific merchant's payment approved), meta-rooms or topic-based rooms for system-wide events (batch completion, scheduled maintenance notification).

## Quick Reference

| Component | Role | Failure if missing |
|---|---|---|
| `@socket.io/redis-adapter` | Routes events across instances via Redis pub/sub | Events only reach sockets on the emitting instance |
| `@socket.io/redis-emitter` | Allows non-Socket.io processes to emit events | Payment service cannot push to WebSocket clients |
| Pub Redis client | Publishes events to Redis channel | This instance cannot send events to other instances |
| Sub Redis client | Receives events from other instances | This instance cannot receive events from other instances |
| Sticky sessions | Routes a client's HTTP requests to the same instance | Long-polling breaks; WebSocket unaffected but cleaner |
| Room: `user:{userId}` | Per-user delivery target | Cannot target specific users across instances |
| Room: `merchant:{id}` | Per-merchant broadcast | Cannot broadcast to all of a merchant's connections |

| Pub/Sub adapter | Streams adapter |
|---|---|
| Fire-and-forget | At-least-once delivery |
| No persistence | Messages survive Redis restart |
| Lower latency | Higher latency (stream read + ack) |
| Lost if instance offline at publish time | Delivered when instance reconnects |
| Use for: ephemeral events, presence, typing | Use for: payment events, financial notifications |

| Failure mode | Symptom | Fix |
|---|---|---|
| No sticky sessions (long-polling) | Events received intermittently | Enable ALB sticky sessions |
| Redis adapter misconfigured | Events only reach local connections | Check REDIS_URL env var; verify adapter setup |
| Redis sub connection lost | No cross-instance events | Monitor sub client; auto-resubscribe on reconnect |
| ALB idle timeout (60s default) | Connections drop after 1 minute | Increase to 3600s; enable WS ping/pong |
| Stale room membership | `fetchSockets()` over-counts | Server heartbeat + TTL-based cleanup |
| Mass broadcast spike | Redis/CPU spike on bulk emit | Chunk broadcast with delay between chunks |

## The Core Mental Model

```
The scaling problem in one sentence:
  Socket A is on Instance 1; the event for Socket A arrives at Instance 2;
  Instance 2 has no Socket A → silent message loss.

The Redis adapter solution in one sentence:
  Every emit → PUBLISH to Redis → all instances receive → only the instance
  with the target socket delivers → every socket gets its message.

The two Redis connections (always required):
  pubClient:  sends events to Redis (can run other commands too)
  subClient:  receives events from Redis (CANNOT run other commands — in sub mode)
  Never share one connection for both — subscribing blocks all other commands.

The room pattern for addressability:
  socket.join(`user:${userId}`)        ← join on every connect (idempotent)
  socket.join(`merchant:${merchantId}`) ← join on every connect
  socket.join(`payment:${id}:watchers`) ← join on user request (persist in Redis)

  emitter.to(`user:${userId}`).emit(...)     ← target specific user, any instance
  emitter.to(`merchant:${merchantId}`).emit() ← target all of a merchant's connections
  emitter.emit(...)                          ← broadcast to all connected clients

The four layers of reconnection safety:
  1. Socket.io auto-reconnection with exponential backoff
  2. Re-join rooms on connect (always, not just first connect)
  3. Persist subscriptions in Redis (survive instance crash)
  4. Replay missed events on reconnect (from Kafka or DB)

The broadcast scaling rule:
  1 emit to meta-room = 1 Redis PUBLISH (regardless of subscribers)
  N emits to N rooms  = N Redis PUBLISHes (linear cost)
  For system-wide events: meta-room (batch-notifications, system-announcements)
  For targeted events: per-entity rooms (merchant:{id}, payment:{id}:watchers)

Redis health = WebSocket health:
  Redis pub client down  → this instance cannot emit to others
  Redis sub client down  → this instance receives no events from others
  Both are critical path; monitor both; alert on error; reconnect automatically
  Use Redis Sentinel or Cluster for HA; never rely on single Redis node in production
```

**Tip for the interview:** Scaling WebSocket questions at 5 YOE almost always escalate to one of three places: (1) the two-Redis-client requirement — knowing that a Redis subscriber connection cannot be used for publishing (it is in blocking subscription mode) and that `pubClient.duplicate()` is the pattern, and understanding why this matters (using one client for both causes `SUBSCRIBE` to block all other commands), signals you have actually implemented this rather than just read about it; (2) the personal room pattern for cross-instance user targeting — `socket.join('user:${userId}')` on every connect, then `emitter.to('user:${userId}').emit(...)` for targeted delivery, and the insight that this also handles multi-device sessions (all devices in the same room, all receive the same event) is the answer that shows distributed systems intuition; (3) the reconnect + replay contract — knowing that Socket.io auto-reconnection restores the transport layer but not the application state (room memberships, subscriptions) and that `socket.join()` must be called unconditionally on every connection event (not just the first) is the production detail that separates someone who has debugged silent reconnect failures from someone who has only read the Socket.io docs. The fintech-specific callout: for NACH payment status updates, settlement notifications, and mandate confirmation events — use the Redis Streams adapter (not pub/sub), because a missed notification during a 5-second Redis blip is a user who sees incorrect payment state and calls support. The at-least-once delivery guarantee of Streams, combined with the replay-on-reconnect pattern, is the reliability floor for financial event delivery over WebSocket.
