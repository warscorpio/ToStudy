# Contract Testing: Consumer-Driven Contract Testing with Pact — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is consumer-driven contract testing, and what gap in the testing pyramid does it fill?**
A: Consumer-driven contract testing is a technique where the consumer of an API (the service that calls another) defines the contract — the exact requests it will make and the response shape it needs — and publishes that contract for the provider (the service that serves the API) to verify against. It fills the gap between unit tests and full E2E tests: unit tests with mocks verify that the consumer uses its mock correctly, but they cannot detect when the provider's real response changes in a breaking way. E2E tests catch this, but they are slow, flaky, and require the entire system to be running simultaneously. Contract tests catch provider-breaking changes fast, without deploying all services:

```
Unit tests        → verify internal logic, but mocks can drift from reality
Contract tests    → verify the consumer–provider interface without E2E infrastructure
Integration tests → verify one service against a real dependency (testcontainers)
E2E tests         → verify the entire system, slowest and most expensive
```

The specific problem contract testing solves: Service A mocks Service B's `/loans` endpoint in its unit tests. Service B's team changes the response shape — renames `loanAmount` to `principalAmount`. Service A's unit tests still pass (they test against the old mock). No one notices until a production deployment breaks. Contract testing makes this failure surface in Service B's CI pipeline before it ships.

**Q2. What is Pact, and how does it implement consumer-driven contract testing?**
A: Pact is the most widely adopted consumer-driven contract testing framework. Its implementation has three phases:

**Phase 1 — Consumer test (generates the pact file):**
The consumer writes a test that defines what it expects from the provider — specific request shapes and the minimum response fields it needs. Pact runs a mock provider server during this test. The test passes if the consumer code correctly calls the mock and handles the response. Pact records the interaction as a JSON file called a **pact file** (the contract).

**Phase 2 — Pact Broker (stores and shares contracts):**
The pact file is published to a Pact Broker (self-hosted or PactFlow). The broker stores versioned contracts, tracks which consumer versions are compatible with which provider versions, and provides a webhook system to trigger provider verification when a new pact is published.

**Phase 3 — Provider verification (validates against the real provider):**
The provider runs a verification test that replays every interaction recorded in the pact file against the real provider code. If the provider's actual response matches the consumer's expectation, verification passes. If the provider changed its response in a way the consumer didn't expect, verification fails — and the provider team knows before shipping.

**Q3. What is a pact file, and what does it contain?**
A: A pact file is a JSON document that records every interaction a consumer defines in its contract tests. Each interaction contains:

```json
{
  "consumer": { "name": "loan-application-service" },
  "provider": { "name": "credit-bureau-service" },
  "interactions": [
    {
      "description": "a request for a credit score for a valid PAN",
      "providerState": "a borrower with PAN ABCDE1234F exists",
      "request": {
        "method": "GET",
        "path": "/credit-score/ABCDE1234F",
        "headers": { "Authorization": "Bearer <token>" }
      },
      "response": {
        "status": 200,
        "headers": { "Content-Type": "application/json" },
        "body": {
          "pan": "ABCDE1234F",
          "score": 750,
          "bureau": "CIBIL"
        }
      }
    }
  ],
  "metadata": {
    "pactSpecification": { "version": "2" }
  }
}
```

The consumer defines the minimum response it needs — it should not assert on fields it doesn't use. If the provider adds new fields, that's not a breaking change and shouldn't fail verification. If the provider removes `score` or renames it, that is a breaking change and verification fails.

**Q4. What is the Pact Broker, and why is it necessary for contract testing at scale?**
A: The Pact Broker is a centralised server that stores pact files and tracks compatibility between consumer and provider versions. Without it, you would need to manually copy pact files between service repositories — untenable at scale. The Broker provides:
- **Versioned pact storage** — every published pact is tagged with the consumer's version (git SHA, semantic version).
- **Compatibility matrix** — a table showing which consumer version is compatible with which provider version. This is the source of truth for deployment decisions.
- **Webhooks** — when a consumer publishes a new pact, the Broker triggers the provider's CI pipeline to run verification immediately.
- **`can-i-deploy`** — a CLI command that queries the Broker's compatibility matrix to answer "can this version of service A be deployed to production given what's currently in production?" before a deployment.
- **PactFlow** — the SaaS-hosted version with additional features (bi-directional contract testing, teams, secrets). PactFlow is to Pact Broker what GitHub is to a self-hosted Git server.

**Q5. What is the difference between a consumer test and a provider verification test in Pact?**
A: They run in different repositories, at different times, with different responsibilities:

| Aspect               | Consumer test                                               | Provider verification                                          |
|----------------------|-------------------------------------------------------------|----------------------------------------------------------------|
| Where it runs        | Consumer's repository and CI pipeline                       | Provider's repository and CI pipeline                          |
| What it tests        | That the consumer correctly calls the provider and handles the response | That the provider's real code satisfies every recorded consumer interaction |
| What it produces     | A pact file (JSON contract)                                 | A verification result (pass/fail) published back to the Broker |
| Mock or real?        | Real consumer code + Pact mock provider                     | Real provider code + Pact replays consumer requests            |
| Who owns it?         | Consumer team                                               | Provider team                                                  |
| When does it run?    | On every consumer PR                                        | On every provider PR, and when a new pact is published         |

The asymmetry is intentional: the consumer defines what it needs, the provider proves it can deliver it. The provider doesn't get a vote on what the consumer test says — but the provider verification result tells both teams whether the contract holds.

## Section 2: Writing Consumer Tests

**Q6. How do you write a Pact consumer test in a NestJS/TypeScript service using `@pact-foundation/pact`?**
A:
```typescript
// src/credit-bureau/credit-bureau.client.spec.pact.ts
import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import path from 'path';
import { CreditBureauClient } from './credit-bureau.client';

const { like, integer, string } = MatchersV3;

const provider = new PactV3({
  consumer: 'loan-application-service',
  provider: 'credit-bureau-service',
  dir: path.resolve(process.cwd(), 'pacts'), // where the pact file is written
  port: 8081,                                // mock provider port
});

describe('CreditBureauClient (Pact consumer)', () => {
  describe('getCreditScore()', () => {
    it('returns a credit score for a valid PAN', async () => {
      await provider
        .given('a borrower with PAN ABCDE1234F exists')
        .uponReceiving('a request for the credit score')
        .withRequest({
          method: 'GET',
          path: '/credit-score/ABCDE1234F',
          headers: { Authorization: like('Bearer some-token') },
        })
        .willRespondWith({
          status: 200,
          headers: { 'Content-Type': 'application/json' },
          body: {
            pan: string('ABCDE1234F'),
            score: integer(750),
            bureau: string('CIBIL'),
          },
        })
        .executeTest(async (mockServer) => {
          const client = new CreditBureauClient({ baseUrl: mockServer.url });
          const result = await client.getCreditScore('ABCDE1234F');

          expect(result.score).toBe(750);
          expect(result.bureau).toBe('CIBIL');
        });
    });
  });
});
```

Key points: the `CreditBureauClient` is the real production class — Pact only replaces the HTTP server it talks to. The test verifies that the client makes the correct HTTP call and correctly parses the response. The pact file is written to the `pacts/` directory and published to the Broker in the CI step.

**Q7. What are Pact matchers, and why should you prefer them over exact value matching?**
A: Pact matchers define flexible expectations on response fields rather than requiring exact values. Using exact values in a contract is brittle — the provider test fails if it returns `score: 720` instead of the consumer's hardcoded `score: 750`, even though `720` is a perfectly valid credit score. Matchers express the intent:

| Matcher                      | What it checks                                     | Example                                    |
|------------------------------|----------------------------------------------------|--------------------------------------------|
| `like(value)`                | Type and structure match; exact value ignored      | `like(750)` — any number passes            |
| `integer(value)`             | Must be an integer; value is example only          | `integer(750)` — any integer passes        |
| `string(value)`              | Must be a string; value is example only            | `string('CIBIL')` — any string passes      |
| `regex(pattern, value)`      | Must match the regex pattern                       | `regex(/^[A-Z]{5}\d{4}[A-Z]$/, 'ABCDE1234F')` |
| `eachLike(template)`         | Array where each element matches the template      | `eachLike({ loanId: string('l1') })`       |
| `atLeastOneLike(template)`   | Non-empty array matching the template              | for required collections                   |
| `datetime(format, example)`  | Must match a datetime format                       | `datetime("yyyy-MM-dd'T'HH:mm:ss", ...)` |

Rule of thumb: assert on type and structure for fields your consumer uses; omit fields entirely if your consumer doesn't use them. A consumer that asserts on 3 of 15 response fields makes the provider free to add, rename, or remove the other 12 without breaking the contract.

**Q8. What is a provider state, and how do you use it to set up different test scenarios?**
A: A provider state is a string label that tells the provider "before verifying this interaction, put your system into this state." It is the Pact equivalent of a test fixture or seed — it decouples the consumer's expectation from the provider's current data. Without provider states, the provider would need to have specific data already in its database for verification to pass, which creates a hidden coupling to a specific database state.

Consumer side — declare the state:
```typescript
provider
  .given('a borrower with PAN ABCDE1234F exists and has a score of 750')
  .uponReceiving('a request for the credit score')
  // ...
```

Provider side — implement the state handler:
```typescript
// In the provider verification setup
stateHandlers: {
  'a borrower with PAN ABCDE1234F exists and has a score of 750': async () => {
    await db.query(`
      INSERT INTO borrower (pan, score, bureau)
      VALUES ('ABCDE1234F', 750, 'CIBIL')
      ON CONFLICT (pan) DO UPDATE SET score = 750
    `);
  },
  'no borrower exists with PAN ZZZZZ9999Z': async () => {
    await db.query(`DELETE FROM borrower WHERE pan = 'ZZZZZ9999Z'`);
  },
},
```

Provider states are run before each interaction during verification. They should be idempotent — running them multiple times should not corrupt the verification database.

**Q9. What interactions should a consumer test cover, and what is the risk of over-specifying?**
A: Consumer tests should cover every interaction the consumer actually makes in production — happy paths, specific error responses the consumer handles, and edge cases the consumer has branching logic for. What they should not cover: error cases the consumer doesn't explicitly handle (a `503` that's caught by a generic error handler is not a contract — it's just "the provider can fail"), fields the consumer never reads, and provider-internal business rules.

Over-specifying examples:
- Asserting on exact values (`score: 750`) instead of type matchers (`integer()`) — locks the provider to specific data.
- Asserting on response headers the consumer never reads — creates false coupling.
- Asserting on a specific error message string in a 400 body — the provider may rephrase it without breaking the consumer.
- Defining interactions for endpoints the consumer doesn't currently call — speculative contracts that test nothing real.

The contract should be the minimum specification that ensures the consumer works correctly with the provider's responses. Every field and assertion in the contract is a constraint on the provider — keep them minimal and purposeful.

## Section 3: Provider Verification

**Q10. How do you set up provider verification in a NestJS service?**
A:
```typescript
// test/pact/provider.pact.spec.ts
import { Verifier } from '@pact-foundation/pact';
import { Test } from '@nestjs/testing';
import { INestApplication } from '@nestjs/common';
import { AppModule } from '../../src/app.module';

describe('CreditBureauService (Pact provider verification)', () => {
  let app: INestApplication;
  let server: any;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleRef.createNestApplication();
    await app.init();
    server = app.getHttpServer();
  }, 30_000);

  afterAll(async () => {
    await app.close();
  });

  it('validates all consumer pacts', async () => {
    const verifier = new Verifier({
      provider: 'credit-bureau-service',
      providerBaseUrl: `http://localhost:${server.address().port}`,

      // Fetch pacts from the Broker
      pactBrokerUrl: process.env.PACT_BROKER_URL,
      pactBrokerToken: process.env.PACT_BROKER_TOKEN,
      consumerVersionSelectors: [
        { mainBranch: true },      // verify against consumer's main branch
        { deployedOrReleased: true }, // verify what's currently in production
      ],

      // Provider state handlers — set up DB fixtures per interaction
      stateHandlers: {
        'a borrower with PAN ABCDE1234F exists': async () => {
          await seedBorrower({ pan: 'ABCDE1234F', score: 750, bureau: 'CIBIL' });
        },
        'no borrower exists with PAN ZZZZZ9999Z': async () => {
          await deleteBorrowerByPan('ZZZZZ9999Z');
        },
      },

      // Publish verification results back to the Broker
      publishVerificationResult: process.env.CI === 'true',
      providerVersion: process.env.GIT_COMMIT_SHA,
      providerVersionBranch: process.env.GIT_BRANCH,
    });

    await verifier.verifyProvider();
  }, 120_000);
});
```

`consumerVersionSelectors` controls which consumer pacts are verified — always verify `mainBranch` (latest consumer code) and `deployedOrReleased` (what's currently live). Only publish results in CI (`publishVerificationResult: process.env.CI === 'true'`) — local runs should not pollute the Broker's compatibility matrix.

**Q11. How does Pact handle authentication during provider verification?**
A: During verification, Pact replays the consumer's recorded requests against the real provider. If the provider requires authentication (JWT, API key, mutual TLS), the consumer test's recorded `Authorization` header will be a mock value — the real provider will reject it. Solutions:

**Option 1 — Request filter (modify requests before verification):**
```typescript
requestFilter: (req, res, next) => {
  // Replace the consumer's mock token with a real test token
  req.headers['authorization'] = `Bearer ${generateTestJwt({ sub: 'pact-verifier' })}`;
  next();
},
```

**Option 2 — Disable auth for the test server:**
Override the auth guard in the NestJS test module to pass all requests:
```typescript
const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
  .overrideGuard(JwtAuthGuard)
  .useValue({ canActivate: () => true })
  .compile();
```

**Option 3 — Use a dedicated verification API key:**
Add a bypass mechanism controlled by an env variable that's only set in the test environment. This is the most production-representative approach because real middleware runs, just with a pre-authorised credential.

Option 2 is the most common in practice — it's simple, explicit, and doesn't require a real auth token during verification. Document why the guard is overridden so future developers don't remove it.

**Q12. What is `can-i-deploy`, and where does it fit in a CI/CD pipeline?**
A: `can-i-deploy` is a Pact CLI command that queries the Pact Broker's compatibility matrix to determine whether a specific version of a service is safe to deploy alongside other services currently in a given environment. It answers: "given that production currently has version X of the provider, can I deploy version Y of the consumer?"

```bash
# In the consumer's deployment pipeline — before deploying to production
npx pact-broker can-i-deploy \
  --pacticipant loan-application-service \
  --version $GIT_COMMIT_SHA \
  --to-environment production

# Exit code 0 = safe to deploy
# Exit code 1 = not safe — compatibility matrix shows a verification failure
```

Where it fits in CI/CD:
```
Consumer pipeline:
  1. Unit tests
  2. Build
  3. Publish pact to Broker          ← new pact triggers provider verification webhook
  4. can-i-deploy (consumer)         ← blocks deployment if provider hasn't verified
  5. Deploy to production
  6. Record deployment in Broker     ← npx pact-broker record-deployment

Provider pipeline:
  1. Unit tests
  2. Build
  3. Provider verification           ← verifies all consumer pacts; publishes result
  4. can-i-deploy (provider)         ← blocks deployment if any consumer is broken
  5. Deploy to production
  6. Record deployment in Broker
```

`record-deployment` is the step that updates the Broker's record of what's currently deployed in each environment — this is what `can-i-deploy` queries. Without `record-deployment`, the Broker doesn't know what's in production and `can-i-deploy` can't give a reliable answer.

## Section 4: Pact in a Microservices Architecture

**Q13. How do you manage Pact in a fintech platform where a single provider (e.g., a credit bureau adapter) has multiple consumers?**
A: With multiple consumers, the provider verification step must verify all consumer pacts simultaneously. The `consumerVersionSelectors` in the provider verification config handles this — it fetches pacts from all registered consumers:

```typescript
consumerVersionSelectors: [
  { mainBranch: true },
  { deployedOrReleased: true },
  { branch: 'feat/new-emi-flow', consumer: 'emi-service' }, // verify a specific branch
],
```

The provider verification runs all interactions from all consumers in one pass. If any single interaction fails, the provider verification fails — the provider cannot ship a change that breaks any consumer, even one it wasn't aware of. This is the "consumer-driven" guarantee: the provider doesn't choose which consumers to care about; the Broker enforces it. For a fintech platform, this means the credit bureau adapter team cannot rename a field without first coordinating with every consumer team that has a published pact — the compatibility matrix makes the dependency graph explicit and enforceable.

**Q14. How does Pact handle versioning when a provider needs to make a breaking change?**
A: A breaking change — removing a field, changing a type, renaming an endpoint — will fail verification for any consumer that depends on it. The Pact workflow for managing breaking changes:

**Step 1 — Identify affected consumers:**
The Pact Broker's compatibility matrix shows exactly which consumer versions use the field being changed. The provider team knows who to coordinate with before making the change.

**Step 2 — Consumer updates its contract first:**
The consumer team updates its code and its consumer test to use the new field name, publishes the updated pact to the Broker.

**Step 3 — Provider ships the breaking change:**
Once the consumer's updated pact is published and the provider verification passes against the new pact, the provider can ship. The `can-i-deploy` check on the provider side will pass once the new consumer pact is verified.

**Step 4 — Pending pacts (for gradual migration):**
If the provider needs to ship before the consumer is ready, use the **pending pacts** feature. A pact from a consumer branch (not `main`) is treated as "pending" — the provider verification runs it, reports failures as warnings, but does not fail the provider's build. Once the consumer merges to main, the pact becomes non-pending and starts blocking the provider.

```typescript
enablePending: true,  // pending pacts warn but don't fail
includeWipPactsSince: '2024-01-01', // include work-in-progress pacts from this date
```

**Q15. How do you contract-test an event-driven interface (Kafka messages) rather than an HTTP API?**
A: Pact was originally designed for HTTP, but Pact's message pact feature handles async, event-driven interfaces — Kafka messages, SQS events, SNS notifications. The consumer defines the message shape it expects to receive; the provider verifies it can produce that shape:

**Consumer side — define the expected message:**
```typescript
import { MessageConsumerPact, synchronousBodyHandler } from '@pact-foundation/pact';

const messagePact = new MessageConsumerPact({
  consumer: 'emi-service',
  provider: 'loan-service',
  dir: path.resolve(process.cwd(), 'pacts'),
});

describe('EmiService Kafka consumer (Pact)', () => {
  it('processes a loan.approved event', async () => {
    await messagePact
      .given('a loan has been approved')
      .expectsToReceive('a loan.approved Kafka event')
      .withContent({
        loanId: string('loan-123'),
        userId: string('user-456'),
        principalAmount: integer(500000),
        tenureMonths: integer(24),
        approvedAt: datetime("yyyy-MM-dd'T'HH:mm:ssXXX", '2025-06-01T09:00:00+05:30'),
      })
      .withMetadata({ 'content-type': 'application/json' })
      .verify(synchronousBodyHandler(async (message) => {
        // Real consumer handler — tests that it correctly processes the message
        await emiService.handleLoanApproved(message);
        expect(emiRepo.create).toHaveBeenCalledWith(
          expect.objectContaining({ loanId: 'loan-123' })
        );
      }));
  });
});
```

**Provider side — verify it produces the correct message:**
```typescript
const verifier = new MessageProviderPact({
  provider: 'loan-service',
  pactBrokerUrl: process.env.PACT_BROKER_URL,
  messageProviders: {
    'a loan.approved Kafka event': async () => {
      // Return the real message the producer would publish
      return loanService.buildApprovalEvent('loan-123', 'user-456');
    },
  },
});
await verifier.verify();
```

The Kafka broker is not involved — Pact tests the message schema contract, not the transport. Real Kafka integration (topic routing, consumer group behaviour, offset management) is tested separately with a Kafka `testcontainers` setup.

## Section 5: Pitfalls and Anti-patterns

**Q16. What is "pact coupling," and how does over-specification in consumer tests cause it?**
A: Pact coupling is when the consumer's contract is so specific that it constrains the provider's implementation far beyond what the consumer actually needs. The most common form: exact value matching on fields the consumer only reads to confirm type. If the consumer checks `if (response.score > 700)`, it needs `score` to be a number — not specifically `750`. A consumer test that asserts `score: 750` means the provider's verification test must always return exactly 750 for that interaction — the provider's state handler must seed exactly that value, and any provider test data change breaks verification. Over a large microservices estate, pact coupling can make provider changes nearly impossible because dozens of consumer contracts pin specific values. Fix: always use type matchers (`integer()`, `string()`, `like()`) instead of exact values. Reserve exact value assertions for fields where the exact value is part of the contract — enum values, fixed identifiers, protocol constants.

**Q17. What happens when a consumer test passes but provider verification fails, and how do you diagnose it?**
A: This is the intended failure mode — Pact is designed to surface exactly this situation. The consumer test passes because it runs against Pact's mock server, which always returns what the consumer asked for. Provider verification fails because the real provider implementation does not return what the consumer recorded. Diagnostic steps:

1. **Read the verification failure output** — Pact prints the exact interaction that failed, the expected response (from the pact file), and the actual response (from the real provider). The diff immediately shows the breaking change.
2. **Check the provider state** — did the state handler correctly seed the data the interaction requires? A missing or incorrect state handler produces a verification failure that looks like a schema mismatch but is actually a missing fixture.
3. **Check the interaction description** — the consumer's interaction description must exactly match the description string in the pact file. A typo means the state handler is never invoked.
4. **Reproduce locally** — run the provider verification locally against the pact file (`pactUrls` option instead of `pactBrokerUrl`) to iterate without hitting the Broker.

**Q18. Why should consumer tests not be written as "the provider should do X" — and what is the right framing?**
A: Consumer tests should be framed entirely from the consumer's perspective: "when I call this endpoint, I need at minimum this response shape to do my job." They should never be framed as requirements on the provider's internal behaviour. The wrong framing — "the provider should return all loan fields including `interestRate`, `processingFee`, and `insurancePremium`" — means the consumer is specifying the provider's full API surface rather than its own minimum needs. If the consumer only uses `interestRate`, the contract should only assert on `interestRate`. The right framing: "given my code, what is the minimum response I need to not throw an exception and return a correct result?" Every field in the contract beyond that minimum is unnecessary coupling. In practice, write the consumer test after writing the consumer code — read the actual response-parsing logic and contract only what is parsed.

**Q19. What is the difference between contract testing and schema testing (e.g., with JSON Schema or OpenAPI), and when would you use each?**
A: Schema testing (OpenAPI, JSON Schema) validates that a response matches a defined schema — it is provider-centric. The provider team owns the schema and validates that their API conforms to it. Contract testing is consumer-centric — the consumer defines what it needs, and the provider proves it delivers that. The key differences:

| Dimension             | Schema / OpenAPI testing                               | Pact contract testing                                         |
|-----------------------|--------------------------------------------------------|---------------------------------------------------------------|
| Who defines the spec  | Provider team                                          | Consumer team                                                 |
| What it validates     | Provider response matches the published schema         | Provider response satisfies each consumer's minimum needs     |
| Breaking change detection | Provider knows when its own schema changes       | Provider knows when a change breaks a specific consumer       |
| Consumer specificity  | All consumers must handle the full schema              | Each consumer specifies only what it uses                     |
| Tooling               | OpenAPI validator, Spectral, JSON Schema validator     | Pact, PactFlow                                                |

Use OpenAPI/schema testing to validate that your API is internally consistent and matches its published documentation. Use Pact to verify that specific consumer–provider pairs are compatible. They are complementary — PactFlow's bi-directional contract testing feature combines both: the provider publishes an OpenAPI spec, the consumer publishes a Pact file, and PactFlow cross-validates them without requiring the provider to run a verification test.

**Q20. What is "Pact test pollution," and how does running provider verification against a shared staging database cause it?**
A: Pact test pollution occurs when provider state handlers modify a shared database that other tests or services also depend on — the state handler's setup or teardown bleeds into concurrent or subsequent test runs. In a shared staging DB scenario: the state handler inserts a borrower row for verification; a concurrent integration test reads the borrower count and gets an unexpected extra row; the integration test fails intermittently. The fix: run provider verification against its own isolated database — a `testcontainers` PostgreSQL instance, a separate schema, or a dedicated test database with no other concurrent users. The provider verification test should be as hermetic as any other integration test: it owns its data, manages its state handlers with full isolation, and leaves no side effects.

## Section 6: Scenario / System Design Style Questions

**Q21. "Your team is splitting a monolith into microservices. The loan application service will now call a new credit bureau adapter service over HTTP. How do you introduce Pact into this split without slowing down the migration?"**
A: Introduce Pact as a step in the migration, not a prerequisite to it. Practical sequence:

**Step 1 — Write the consumer test first (even before the provider exists):**
The loan application service team writes a Pact consumer test against the agreed API contract. This generates a pact file immediately — the provider doesn't need to exist yet. The consumer test becomes the specification for the new service.

**Step 2 — Publish the pact file to the Broker:**
The consumer team publishes the pact. The Broker shows the pact as unverified — no provider verification has run yet.

**Step 3 — Build the provider against the pact:**
The credit bureau adapter team implements the endpoint with the pact file as the specification. They run provider verification locally against the pact file during development. The pact drives the implementation.

**Step 4 — Wire up CI:**
Once the provider has a basic implementation, add provider verification to its CI pipeline. The consumer adds `can-i-deploy` to its deployment gate. From this point, the compatibility matrix is enforced automatically.

**Step 5 — Do not write an E2E test for this interface:**
The Pact contract replaces the need for an E2E test of this specific consumer–provider pair. This is the migration benefit — each extracted service pair gets a contract test, and the E2E test surface shrinks. The full E2E suite validates user-facing flows, not individual service interfaces.

**Q22. "A senior engineer on your team argues that Pact adds overhead without enough benefit because 'we already have integration tests with testcontainers.' How do you respond?"**
A: The integration tests with `testcontainers` are testing one service against a real database — they verify that the service's internal logic and its database interaction are correct. They don't test the inter-service HTTP contract. The specific gap: if the credit bureau service team changes their response from `{ score: 750 }` to `{ creditScore: 750 }`, the loan application service's `testcontainers` integration test won't catch it — because the DB fixture in that test still returns the old shape, and the consumer code still works against its own fixtures. The test suite says green; production breaks.

Pact closes this gap: the consumer's pact records `score`, the provider's verification replays that expectation against real provider code, and the rename fails verification in the provider's CI before it ships. The overhead is real — consumer tests, provider verification, Broker setup — but it is bounded. Once the scaffolding exists, each new interaction is one `given().uponReceiving().withRequest().willRespondWith()` block. The alternative overhead — a full E2E test environment where both services run simultaneously — is unbounded in cost, flakiness, and maintenance. Contract testing replaces a class of E2E tests, it doesn't add to them.

**Q23. "Production has an incident: the EMI service is failing to process loan.approved Kafka events because the loan service changed its event schema. How do you prevent this with Pact going forward?"**
A: This is exactly the failure mode Pact message contracts prevent. Remediation and prevention:

**Immediate fix:**
Align the event schemas — either the loan service reverts the change or the EMI service updates its consumer. Fix whichever is faster given the incident window.

**Prevention — introduce Pact message contracts:**

1. **EMI service writes a message consumer pact** — defines the minimum shape of `loan.approved` it needs:
   ```typescript
   .expectsToReceive('a loan.approved Kafka event')
   .withContent({
     loanId: string(),
     userId: string(),
     principalAmount: integer(),
   })
   ```

2. **Loan service adds message provider verification** — verifies that its actual Kafka producer output satisfies the EMI service's pact.

3. **Pact Broker enforces it in CI** — when the loan service team changes the event schema, provider verification fails. The build is blocked. The incident cannot happen again without a deliberate, coordinated contract update.

4. **`can-i-deploy` gates deployment** — even if the verification is bypassed locally, `can-i-deploy` in the loan service's deployment pipeline blocks production deployment until the EMI service's pact is satisfied.

The root cause of the incident was invisible coupling — the loan service didn't know who depended on its event schema, and the EMI service didn't know the schema could change. Pact makes the dependency graph explicit, versioned, and machine-enforced.

**Q24. "Design the complete Pact CI/CD integration for a NestJS fintech platform with five microservices: loan-service, emi-service, credit-bureau-adapter, notification-service, and payment-gateway-adapter."**
A: The complete integration across five services:

**Pact Broker setup:**
Self-host on an EC2/ECS instance or use PactFlow. Store the URL and token in CI secrets (`PACT_BROKER_URL`, `PACT_BROKER_TOKEN`). Tag each pacticipant with its environment on deployment.

**Consumer pact publishing (all consumer pipelines):**
```yaml
# .github/workflows/consumer-pact.yml (runs on every PR and merge to main)
- name: Run consumer pact tests
  run: npm run test:pact:consumer

- name: Publish pact to Broker
  run: |
    npx pact-broker publish ./pacts \
      --broker-base-url $PACT_BROKER_URL \
      --broker-token $PACT_BROKER_TOKEN \
      --consumer-app-version $GITHUB_SHA \
      --branch $GITHUB_REF_NAME
```

**Provider verification (all provider pipelines):**
```yaml
# Triggered by: provider PR, and Pact Broker webhook on new consumer pact
- name: Run provider pact verification
  run: npm run test:pact:provider
  env:
    PACT_BROKER_URL: ${{ secrets.PACT_BROKER_URL }}
    PACT_BROKER_TOKEN: ${{ secrets.PACT_BROKER_TOKEN }}
    GIT_COMMIT_SHA: ${{ github.sha }}
    GIT_BRANCH: ${{ github.ref_name }}
    CI: true
```

**Deployment gates (all service pipelines, before each environment deploy):**
```yaml
- name: Can I deploy?
  run: |
    npx pact-broker can-i-deploy \
      --pacticipant $SERVICE_NAME \
      --version $GITHUB_SHA \
      --to-environment production \
      --broker-base-url $PACT_BROKER_URL \
      --broker-token $PACT_BROKER_TOKEN

- name: Deploy to production
  run: ./deploy.sh

- name: Record deployment
  run: |
    npx pact-broker record-deployment \
      --pacticipant $SERVICE_NAME \
      --version $GITHUB_SHA \
      --environment production \
      --broker-base-url $PACT_BROKER_URL \
      --broker-token $PACT_BROKER_TOKEN
```

**Service dependency graph (who is consumer, who is provider):**

```
loan-service        → credit-bureau-adapter  (HTTP: GET /credit-score)
loan-service        → payment-gateway-adapter (HTTP: POST /disburse)
emi-service         → loan-service            (Kafka: loan.approved event)
notification-service→ loan-service            (Kafka: loan.approved, loan.rejected events)
notification-service→ emi-service             (Kafka: emi.due event)
```

Each arrow represents a consumer pact published by the left service and verified by the right service. The Broker's compatibility matrix covers all six relationships. `can-i-deploy` for any single service checks all relationships it participates in before allowing a deployment. The full matrix makes it impossible to deploy a breaking change to any service without first satisfying every consumer's contract.

Have one concrete story — a schema drift incident you prevented, a Kafka event contract you introduced after a production incident, or a `can-i-deploy` gate that blocked a breaking provider deploy. That's the answer that lands at this level.
