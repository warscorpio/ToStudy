# Why Contract Tests Matter in Microservices — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a contract test, and why does it exist specifically in a microservices architecture?**
A: A contract test verifies that two services — a consumer and a provider — agree on the shape, semantics, and behaviour of their shared API boundary. It exists because microservices introduce a problem that monoliths don't have: **the integration surface is distributed across independently deployed services, each evolving on its own release cycle.**

In a monolith, a compiler or type checker catches a breaking interface change immediately — rename a method and the call site fails at build time in the same codebase. In microservices, `PaymentService` can ship a response that renames `txnId` to `transactionId` and the `NotificationService` consuming it will only break at runtime, in production, after both services have been independently deployed.

Contract tests fill this gap by:
- Capturing what each consumer *actually uses* from a provider's response (not just what the provider thinks it exposes).
- Running those expectations against the provider *before deployment*, without both services being live at the same time.
- Giving the provider team confidence that a change doesn't break any downstream consumer.

Without contract tests in microservices, the only safety net is end-to-end tests against a full environment — which are slow, expensive to maintain, and catch the breakage too late in the pipeline.

**Q2. What is the difference between a contract test, an integration test, and an end-to-end test?**
A: The three sit at different points in the testing pyramid and catch different failure modes:

| Dimension | Contract Test | Integration Test | End-to-End Test |
|---|---|---|---|
| **What it tests** | API contract between two services | A service's internal integration with its DB, queue, cache | A full user journey across all services |
| **Environment** | No running services required (mocks + replayed interactions) | Real DB, real queue, mocked external services | All services running, often in a staging environment |
| **Speed** | Milliseconds–seconds | Seconds–minutes | Minutes–hours |
| **Failure signal** | "Consumer expects field X; provider no longer returns it" | "Service can't write to its own DB correctly" | "The checkout flow is broken end-to-end" |
| **When it catches issues** | Before deployment, in CI | Before deployment, in CI | After deployment, in staging |
| **Ownership** | Shared: consumer writes; provider verifies | Single team | Shared or QA-owned |

The key insight: contract tests don't test business logic. They test the *boundary agreement*. A passing contract test means the consumer and provider can talk to each other; it says nothing about whether the business logic is correct.

**Q3. What are the two models of contract testing — provider-driven and consumer-driven — and which is more useful?**
A: 

**Provider-driven contracts:** The provider publishes a specification (OpenAPI/Swagger, JSON Schema) describing what it offers. Consumers are expected to conform to it. If the spec says a field is nullable, the consumer must handle null. The provider's spec is the source of truth.

**Consumer-driven contracts (CDC):** Each consumer publishes what *it* actually uses from the provider. The provider runs all consumer contracts as tests before releasing. The consumer's actual usage is the source of truth.

Consumer-driven contracts are far more useful in practice for one critical reason: **provider-driven specs describe what the provider offers; CDC describes what consumers break if you remove.** A provider might return 50 fields; a consumer uses 3. Provider-driven testing can't tell you those 3 fields are critical — CDC can.

The canonical tool for CDC is **Pact**. The workflow:

```
Consumer team                          Provider team
─────────────────                      ─────────────────────────────
Write consumer test         →  Pact file (contract)  →  Provider verifies contract
  "I send POST /payments"                                 "Does my API satisfy this?"
  "I expect { txnId, status }"                           Before every release
```

The provider gets a precise, automated answer: "these are the exact fields your consumers depend on; any change to them is a breaking change."

**Q4. What is a "pact" in the context of Pact testing, and what does a pact file contain?**
A: A pact is a JSON file — the contract artifact — generated by the consumer-side test. It contains a set of *interactions*: each interaction describes one request the consumer makes and the response it expects. The pact file is the shared artefact that travels from consumer CI to provider CI:

```json
{
  "consumer": { "name": "NotificationService" },
  "provider": { "name": "PaymentService" },
  "interactions": [
    {
      "description": "a request for payment status by transaction ID",
      "request": {
        "method": "GET",
        "path":   "/v1/payments/txn_001",
        "headers": { "Authorization": "Bearer <token>" }
      },
      "response": {
        "status": 200,
        "headers": { "Content-Type": "application/json" },
        "body": {
          "txnId":    "txn_001",
          "status":   "completed",
          "amount":   5000,
          "currency": "INR"
        },
        "matchingRules": {
          "$.body.txnId":  { "match": "type" },
          "$.body.amount": { "match": "type" }
        }
      }
    }
  ],
  "metadata": { "pactSpecification": { "version": "2.0.0" } }
}
```

Key elements:
- **Interactions** — each consumer expectation is one interaction. A consumer with 5 different usage patterns produces 5 interactions.
- **Matching rules** — instead of exact value matching, rules like `"match": "type"` mean "any string" or "any number." This makes pacts flexible — the provider can return `txnId: "txn_xyz"` and the contract still passes because the type (string) matches.
- **Minimum surface** — the consumer only specifies fields it *uses*. If the provider adds new fields, existing pacts still pass (additive changes are non-breaking).

**Q5. What is the Pact Broker, and why is it necessary beyond just sharing pact files?**
A: The Pact Broker is a central service (open source or Pactflow SaaS) that stores pact files, tracks verification results, and enables the `can-i-deploy` check — the feature that makes CDC genuinely useful in a CI/CD pipeline.

Without a broker, you'd need to manually copy pact files from consumer repos to provider repos — fragile, doesn't scale across many consumer-provider pairs, and gives no cross-version visibility.

With the Pact Broker:

```
Consumer CI:
  1. Run consumer pact test → generates pact file
  2. Publish pact to broker (tagged with consumer version + branch)

Provider CI:
  1. Fetch all consumer pacts for this provider from broker
  2. Run provider verification against each pact
  3. Publish verification results back to broker

Before any deployment (consumer or provider):
  pact-broker can-i-deploy --pacticipant PaymentService --version 2.3.1 --to-environment production
  → "Yes" only if all consumer pacts for this version are verified
```

`can-i-deploy` is the killer feature: it gives a binary, automated answer to "is it safe to deploy this version?" by checking whether every consumer that talks to this provider has a verified, passing contract. No manual coordination between teams required.

## Section 2: Consumer-Side Contract Tests

**Q6. Walk through writing a Pact consumer test for a Node.js service in TypeScript.**
A:

```typescript
// services/notification-service/src/clients/payment.client.ts
import axios from "axios";

export interface PaymentStatus {
  txnId:    string;
  status:   "pending" | "completed" | "failed";
  amount:   number;
  currency: string;
}

export class PaymentClient {
  constructor(private readonly baseUrl: string) {}

  async getPaymentStatus(txnId: string): Promise<PaymentStatus> {
    const response = await axios.get<PaymentStatus>(
      `${this.baseUrl}/v1/payments/${txnId}`,
      { headers: { Authorization: `Bearer ${process.env.INTERNAL_TOKEN}` } }
    );
    return response.data;
  }
}
```

```typescript
// services/notification-service/src/clients/payment.client.pact.spec.ts
import { PactV3, MatchersV3 } from "@pact-foundation/pact";
import { PaymentClient }      from "./payment.client";
import path                   from "path";

const { like, string, integer, regex } = MatchersV3;

// Pact instance — defines the consumer-provider pair
const provider = new PactV3({
  consumer: "NotificationService",
  provider: "PaymentService",
  dir:      path.resolve(__dirname, "../../pacts"),  // where pact file is written
  port:     8080,
});

describe("PaymentClient — Pact consumer tests", () => {
  describe("getPaymentStatus", () => {
    it("should return payment status for a valid transaction ID", async () => {
      // Arrange — define the interaction: what the consumer sends and what it expects back
      await provider
        .given("a payment with txnId txn_001 exists and is completed")
        .uponReceiving("a request for payment status by transaction ID")
        .withRequest({
          method:  "GET",
          path:    "/v1/payments/txn_001",
          headers: { Authorization: like("Bearer some-token") },  // type match, not exact
        })
        .willRespondWith({
          status:  200,
          headers: { "Content-Type": "application/json" },
          body: {
            txnId:    like("txn_001"),    // any string — not pinned to this exact value
            status:   regex("pending|completed|failed", "completed"),
            amount:   integer(5000),     // any integer
            currency: like("INR"),       // any string
          },
        })
        .executeTest(async (mockServer) => {
          // Act — real client code against the Pact mock server
          const client = new PaymentClient(mockServer.url);
          const result = await client.getPaymentStatus("txn_001");

          // Assert — consumer-side assertions (not the pact's job; this is extra)
          expect(result.txnId).toBe("txn_001");
          expect(result.status).toBe("completed");
          expect(result.amount).toBe(5000);
        });
    });

    it("should handle a 404 when the payment does not exist", async () => {
      await provider
        .given("no payment with txnId txn_999 exists")
        .uponReceiving("a request for a non-existent payment")
        .withRequest({
          method:  "GET",
          path:    "/v1/payments/txn_999",
          headers: { Authorization: like("Bearer some-token") },
        })
        .willRespondWith({
          status: 404,
          body: {
            error:   like("Payment not found"),
            code:    like("NOT_FOUND"),
          },
        })
        .executeTest(async (mockServer) => {
          const client = new PaymentClient(mockServer.url);

          await expect(client.getPaymentStatus("txn_999"))
            .rejects.toThrow();
        });
    });
  });
});
```

Running this test:
1. Starts a local Pact mock server on port 8080.
2. Runs the real `PaymentClient` code against that mock server.
3. Verifies the client's requests match the interaction definition.
4. Writes a `pact/NotificationService-PaymentService.json` file containing all interactions.

The generated pact file is then published to the Pact Broker and becomes the provider's test suite.

**Q7. What are Pact matching rules, and why are exact value matches almost always wrong?**
A: Matching rules control how the provider verification compares actual response values to the pact's expected values. Without them, every field is compared exactly — meaning the pact for `txnId: "txn_001"` would fail provider verification unless the provider's test state produces exactly `"txn_001"`. That's brittle and requires tight coupling between consumer test data and provider test state.

Matching rules make pacts portable and maintainable:

```typescript
// ❌ Exact matching — brittle; provider test must produce exactly this value
body: {
  txnId:     "txn_001",
  amount:    5000,
  createdAt: "2024-01-15T10:00:00Z",
}

// ✅ Type matching — any string, any number, any ISO date string
body: {
  txnId:     like("txn_001"),           // any string
  amount:    integer(5000),             // any integer
  createdAt: string("2024-01-15T..."),  // any string (or use datetime matcher)
}

// ✅ Regex matching — for constrained formats
body: {
  currency: regex("^[A-Z]{3}$", "INR"),   // any 3-letter currency code
  status:   regex("pending|completed|failed", "completed"),
}

// ✅ Array matching — "at least one element of this shape"
body: {
  items: eachLike({
    sku:      like("SKU-001"),
    quantity: integer(1),
    price:    decimal(99.99),
  }),
}
```

The rule of thumb: use `like()` (type matching) for IDs, names, and strings where only the type matters; use `regex()` for formatted values (currency codes, UUIDs, date formats); use `integer()` / `decimal()` for numeric fields; use `eachLike()` for arrays.

**Q8. What are provider states, and how do you use them to test multiple scenarios?**
A: A provider state is a named precondition string in the pact interaction — `"given('a payment with txnId txn_001 exists')"` — that tells the provider's verification harness what DB/state setup to perform before verifying that interaction. Provider states are the bridge between the consumer's scenario and the provider's test environment.

Consumer side (declares the state):
```typescript
provider
  .given("a completed payment with txnId txn_001 exists")     // state name
  .uponReceiving("a GET request for payment status")
  .withRequest({ method: "GET", path: "/v1/payments/txn_001" })
  .willRespondWith({ status: 200, body: { status: like("completed") } })
```

Provider side (implements the state):
```typescript
// In the provider verification setup — a state handler map
const stateHandlers: StateHandlers = {
  "a completed payment with txnId txn_001 exists": async () => {
    // Seed the test DB with this specific state
    await paymentRepo.save({
      txnId:  "txn_001",
      status: "completed",
      amount: 5000,
    });
  },
  "no payment with txnId txn_999 exists": async () => {
    // Ensure txn_999 is NOT in the DB — delete if it exists
    await paymentRepo.delete({ txnId: "txn_999" });
  },
  "the payment gateway is unavailable": async () => {
    // Activate a feature flag or inject a mock that makes the gateway fail
    await featureFlagService.set("gateway_circuit_open", true);
  },
};
```

Provider states let you test the full range of scenarios — success, not-found, error conditions — without hardcoding specific data into the pact file. The state name is a human-readable contract between the consumer test author and the provider state handler author.

## Section 3: Provider-Side Verification

**Q9. Walk through provider-side pact verification in a NestJS service.**
A:

```typescript
// services/payment-service/src/pact/payment.provider.pact.spec.ts
import { Verifier, VerifierOptions } from "@pact-foundation/pact";
import { Test, TestingModule }        from "@nestjs/testing";
import { INestApplication }           from "@nestjs/common";
import { ValidationPipe }             from "@nestjs/common";
import { getRepositoryToken }         from "@nestjs/typeorm";
import { Repository }                 from "typeorm";
import { AppModule }                  from "../app.module";
import { Payment }                    from "../payments/payment.entity";
import { applyGlobalConfig }          from "../app.setup";
import path                           from "path";

describe("PaymentService — Pact Provider Verification", () => {
  let app:            INestApplication;
  let paymentRepo:    Repository<Payment>;

  beforeAll(async () => {
    const module: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app         = module.createNestApplication();
    paymentRepo = module.get<Repository<Payment>>(getRepositoryToken(Payment));

    applyGlobalConfig(app);
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it("should satisfy all consumer pacts", async () => {
    const options: VerifierOptions = {
      provider:           "PaymentService",
      providerBaseUrl:    `http://localhost:${app.getHttpServer().address().port}`,

      // Where to fetch pacts from — local files or Pact Broker
      pactUrls: [
        path.resolve(__dirname, "../../pacts/NotificationService-PaymentService.json"),
        path.resolve(__dirname, "../../pacts/BREService-PaymentService.json"),
      ],
      // OR fetch from broker:
      // pactBrokerUrl: process.env.PACT_BROKER_URL,
      // consumerVersionSelectors: [{ mainBranch: true }, { deployedOrReleased: true }],

      // State handler: maps state names to setup functions
      stateHandlers: {
        "a completed payment with txnId txn_001 exists": async () => {
          await paymentRepo.clear();
          await paymentRepo.save({
            txnId:    "txn_001",
            status:   "completed",
            amount:   5000,
            currency: "INR",
            userId:   "u1",
          });
        },
        "no payment with txnId txn_999 exists": async () => {
          await paymentRepo.delete({ txnId: "txn_999" });
        },
      },

      // Request filter: add auth headers so the provider doesn't reject the pact runner
      requestFilter: (req, _res, next) => {
        req.headers["authorization"] = `Bearer ${process.env.INTERNAL_SERVICE_TOKEN}`;
        next();
      },

      publishVerificationResult: process.env.CI === "true",  // only publish on CI
      providerVersion:           process.env.GIT_COMMIT,
      providerVersionBranch:     process.env.GIT_BRANCH,
    };

    await new Verifier(options).verifyProvider();
  });
});
```

What happens during `verifyProvider()`:
1. For each interaction in each pact file, Pact runs the corresponding state handler.
2. Makes the real HTTP request (as defined in the pact) against the running NestJS app.
3. Compares the real response to the pact's expected response, applying matching rules.
4. Reports pass/fail per interaction, per consumer.
5. Publishes results back to the broker if `publishVerificationResult: true`.

**Q10. How does the provider verification handle authentication headers that weren't in the original pact?**
A: Consumer pact tests typically use a placeholder auth header (`like("Bearer some-token")`) — they can't know the real internal service token. During provider verification, the Pact runner sends this placeholder, but the real provider's auth middleware will reject it.

Three solutions:

**Solution 1 — `requestFilter` (most common):** Intercept every pact request and inject a real (test-environment) token:
```typescript
requestFilter: (req, _res, next) => {
  req.headers["authorization"] = `Bearer ${process.env.TEST_SERVICE_TOKEN}`;
  next();
},
```

**Solution 2 — Disable auth in provider verification:** Override the auth guard in the test module:
```typescript
// In the provider verification test module setup
.overrideGuard(JwtAuthGuard)
.useValue({ canActivate: () => true })
```
Acceptable for contract testing (auth is tested separately in unit tests); the contract test only cares about the response shape, not whether auth works.

**Solution 3 — Use a test-only provider state that bypasses auth:** Include a global state handler that disables or mocks the auth layer before verification. Less clean than `requestFilter` but works for complex auth scenarios.

## Section 4: Schema-Based Contracts

**Q11. What is schema-based contract testing (OpenAPI), and how does it differ from Pact?**
A: Schema-based contract testing uses a shared API specification — typically OpenAPI/Swagger — as the contract. Consumers and providers both validate against the schema. The provider validates that its responses conform to the schema it published; consumers validate that their requests conform to the schema they depend on.

```yaml
# openapi.yaml — the shared contract
paths:
  /v1/payments/{txnId}:
    get:
      parameters:
        - name: txnId
          in:   path
          required: true
          schema: { type: string }
      responses:
        "200":
          content:
            application/json:
              schema:
                type:     object
                required: [txnId, status, amount, currency]
                properties:
                  txnId:    { type: string }
                  status:   { type: string, enum: [pending, completed, failed] }
                  amount:   { type: integer }
                  currency: { type: string, pattern: "^[A-Z]{3}$" }
```

Key differences vs Pact:

| Dimension | Pact (CDC) | OpenAPI schema |
|---|---|---|
| **Source of truth** | Consumer's actual usage | Provider's published spec |
| **Granularity** | Per-consumer, per-interaction | All consumers share one spec |
| **What it catches** | Provider removing a field a consumer uses | Both sides deviating from the shared spec |
| **Breaking change detection** | Consumer-specific — knows exactly which consumer breaks | Schema-wide — can't tell which consumers are affected |
| **Tooling** | Pact libraries, Pact Broker | `swagger-parser`, `openapi-validator`, `dredd`, `schemathesis` |
| **Best for** | Internal microservices with many consumers | Public APIs, third-party integrations, cross-team spec-first design |

The practical recommendation for internal microservices: Pact for service-to-service contracts (gives the most precise breaking-change signal); OpenAPI for public-facing APIs and developer portals (gives discoverability and documentation).

**Q12. How do you validate an OpenAPI schema against a running service in CI?**
A: Two tools do this well:

**`dredd` — runs API description tests against a live server:**
```bash
# Generate a dredd config from your OpenAPI spec
dredd init

# dredd.yml
dry-run: false
hookfiles: ./dredd-hooks.js
language: nodejs
server: npm start
server-wait: 3
reporting: xunit
output: test-results.xml
path: ./openapi.yaml
```

**`schemathesis` — property-based testing against OpenAPI (more powerful):**
```bash
# Automatically generates test cases from the schema and fires them at the API
schemathesis run openapi.yaml \
  --url http://localhost:3000 \
  --checks all \
  --header "Authorization: Bearer ${TEST_TOKEN}"
```

`schemathesis` is particularly valuable because it generates edge-case inputs (boundary values, null fields, unexpected types) automatically from the schema — catching validation gaps that manual tests miss.

For NestJS, `@nestjs/swagger` + the `class-validator` decorators on DTOs mean the OpenAPI spec is generated from the code — but you still need to validate the generated spec is accurate by running schema tests against the live service.

## Section 5: Contract Testing in Practice

**Q13. How do you integrate contract tests into a CI/CD pipeline across multiple microservices?**
A: The pipeline has two independent but coordinated flows:

**Consumer CI pipeline:**
```
Push to branch
  → Run unit tests
  → Run consumer pact tests         ← generates pact file
  → Publish pact to broker           ← tagged with branch + version
  → can-i-deploy check               ← is it safe to deploy?
  → Deploy to staging
```

**Provider CI pipeline:**
```
Push to branch
  → Run unit tests
  → Run integration tests
  → Fetch all consumer pacts from broker ← all consumers of this provider
  → Run provider verification            ← does this version satisfy all pacts?
  → Publish verification results         ← pass/fail per consumer
  → can-i-deploy check                   ← all consumers verified?
  → Deploy to staging
```

**`can-i-deploy` is the gate that ties both pipelines together:**
```bash
# PaymentService wants to deploy version 2.3.1 to production
pact-broker can-i-deploy \
  --pacticipant PaymentService \
  --version 2.3.1 \
  --to-environment production

# Broker checks: for every consumer of PaymentService,
# is there a verified pact between that consumer's production version
# and PaymentService 2.3.1?
# If yes → "Computer says yes"
# If no  → "Computer says no" + reason (which consumer's pact failed)
```

This prevents the deployment of any service version that would break a consumer currently running in production — regardless of which team owns each service.

**Q14. How do you manage contract tests when a provider needs to make a breaking change?**
A: A breaking change (removing a field, changing a type, renaming a field) will fail the consumer's pact. The process:

**Step 1 — Identify which consumers are affected:**
The Pact Broker's network diagram shows exactly which consumers depend on the field being changed. If only `NotificationService` uses `txnId` and it's being renamed to `transactionId`, only `NotificationService` needs updating.

**Step 2 — Coordinate the migration:**
Two options:

**Option A — Parallel field (expand/contract pattern):**
```json
// Phase 1: Provider adds the new field while keeping the old one
{ "txnId": "txn_001", "transactionId": "txn_001" }  // both present

// Phase 2: Consumers migrate to transactionId, update their pacts, redeploy
// Phase 3: Provider removes txnId once no consumer pact references it
{ "transactionId": "txn_001" }  // old field removed
```
The expand/contract pattern allows zero-downtime migration with no coordination window — each phase is independently deployable.

**Option B — Versioned endpoints:**
```
/v1/payments/:txnId    ← old contract (kept until consumers migrate)
/v2/payments/:txnId    ← new contract (consumers migrate on their schedule)
```
Consumers migrate independently; the old endpoint is deprecated and removed once all pacts targeting it are gone.

**Step 3 — Verify migration is complete:**
```bash
# Check if any consumer still references the old field
pact-broker can-i-deploy \
  --pacticipant PaymentService \
  --version 2.4.0 \               # version with txnId removed
  --to-environment production
# "Computer says no" until all consumers have updated pacts passing verification
```

**Q15. How do contract tests interact with API versioning strategies?**
A: Contract tests and API versioning are complementary — versioning is the migration mechanism; contract tests are the safety mechanism that tells you when the migration is complete and safe.

**URI versioning** (`/v1/`, `/v2/`):
```typescript
// Consumer pact pins to the version path
.withRequest({ method: "GET", path: "/v2/payments/txn_001" })
// Provider maintains both /v1 and /v2 route handlers
// Once no consumer pact references /v1, that handler can be removed
```

**Header versioning** (`Accept: application/vnd.api+json;version=2`):
```typescript
.withRequest({
  method:  "GET",
  path:    "/v1/payments/txn_001",
  headers: { "Accept": "application/vnd.api+json;version=2" },
})
```

**Content negotiation** via `consumerVersionSelectors` in Pact Broker:
```typescript
// Provider verification fetches pacts for consumers in specific environments
consumerVersionSelectors: [
  { mainBranch: true },         // latest from main branch
  { deployedOrReleased: true }, // versions currently in production/staging
]
```
This means the provider only needs to satisfy pacts from consumer versions that are actually deployed — not every historical version — which prevents the "pact museum" problem of accumulating stale contracts.

## Section 6: What Contract Tests Don't Cover

**Q16. What are the limitations of contract tests, and what must you test elsewhere?**
A: Contract tests are deliberately narrow — they verify the *protocol agreement*, not the *business correctness*. Being clear about what they don't cover is as important as knowing what they do:

**Business logic correctness:**
A contract test verifies that `POST /v1/payments` returns `{ txnId: string, status: string }`. It does not verify that the payment was actually debited, that the correct amount was deducted, or that the ledger entry is correct. Business logic lives in unit tests and integration tests.

**Semantic contract violations:**
A consumer expects `status: "completed"` when it queries a paid transaction. The provider's pact test uses a regex `pending|completed|failed` match — the pact passes. But if the provider ships a bug that always returns `status: "pending"` even for completed payments, the contract test passes (the type matches) while the semantic contract is violated. Contract tests verify shape, not meaning.

**Performance and load behaviour:**
A contract test makes one request in a clean environment. It cannot tell you whether the provider handles 500 concurrent requests for that endpoint within SLA.

**Auth and authorisation logic:**
Provider verification typically bypasses auth (via `requestFilter` or guard overrides). The contract test doesn't verify that unauthenticated consumers are correctly rejected. Auth is tested in unit tests of the guard and in integration tests of the protected route.

**Third-party service contracts:**
Pact works between services you own. If `PaymentService` depends on JusPay's API, you can write a consumer pact for what you expect from JusPay — but JusPay won't run your pact as their CI gate. Here, the contract test is one-sided: it protects you from *your code* diverging from the documented JusPay spec, but not from JusPay changing their API unexpectedly.

**Q17. What is the "pact museum" anti-pattern, and how do you prevent it?**
A: The pact museum is when the Pact Broker accumulates hundreds of stale pact files — from old consumer versions, deprecated interactions, services that no longer exist — and the provider's CI fails on pacts for consumers that were decommissioned 6 months ago. It's the contract testing equivalent of dead code — it creates noise and slows down CI without providing any safety.

Prevention strategies:

**1. `consumerVersionSelectors` — only verify what's deployed:**
```typescript
consumerVersionSelectors: [
  { mainBranch: true },           // consumer's latest main branch version
  { deployedOrReleased: true },   // versions actually running in any environment
]
// Pacts from old branches or decommissioned versions are ignored automatically
```

**2. Record deployments with the broker:**
```bash
# When NotificationService v1.2.0 is deployed to production:
pact-broker record-deployment \
  --pacticipant NotificationService \
  --version 1.2.0 \
  --environment production
```
This tells the broker which consumer versions are live, making `deployedOrReleased` selectors accurate.

**3. Delete pacts for decommissioned services:**
When a service is retired, remove it from the broker explicitly — don't let its pacts linger as false gates.

**4. Tag-based lifecycle management:**
Use Pact tags (`prod`, `staging`, `main`) to control which pacts are fetched for verification, and clean up tags when environments are torn down.

## Section 7: Scenario / System Design Style Questions

**Q18. "Your team has 8 microservices and no contract tests. Every deployment involves a manual coordination meeting to check nothing is broken. How do you introduce contract testing incrementally?"**
A: An incremental rollout — big-bang adoption fails because it requires all teams to change simultaneously:

**Phase 1 — Start with one high-traffic consumer-provider pair (week 1–2):**
Pick the pair with the most historical integration bugs or the tightest coupling. Write consumer pact tests for the existing interactions — not new ones. This is just encoding what already works as a contract.

**Phase 2 — Set up the Pact Broker and publish (week 2–3):**
Deploy the open-source Pact Broker (Docker Compose for simplicity) or use Pactflow. Add pact publish to the consumer's CI pipeline. Add provider verification to the provider's CI pipeline. No `can-i-deploy` gate yet — just observation.

**Phase 3 — Enable `can-i-deploy` as a warning, not a gate (week 3–4):**
Run `can-i-deploy` in CI but don't fail the build. Teams see the results without being blocked. This builds trust in the tool and surfaces false positives.

**Phase 4 — Make `can-i-deploy` a hard gate for the first pair (week 4–5):**
The coordination meeting for this pair becomes optional. Measure: did incidents from this pair's deployments drop?

**Phase 5 — Roll out to remaining pairs (month 2–3):**
Each team adopts the pattern using the existing broker. By the time all 8 services are covered, the coordination meeting is genuinely unnecessary.

The key framing for leadership: **contract tests replace synchronous human coordination with asynchronous automated verification**. The coordination meeting is risk management. Contract tests are cheaper, faster, and more reliable risk management.

**Q19. "The PaymentService team wants to change the response structure of their most-used endpoint. Four teams depend on it. How do you manage this with contract tests?"**
A: Use the pact network diagram as the starting point — it shows exactly which consumer interactions reference the endpoint and which fields they use.

**Step 1 — Audit the impact before writing a line of code:**
```bash
# Which consumers have verified pacts against the current version?
pact-broker describe-version \
  --pacticipant PaymentService \
  --version $(git rev-parse HEAD)
# Shows: NotificationService, BREService, ReportingService, WebhookService
# each with their specific interactions and fields used
```

**Step 2 — Apply the expand/contract pattern across all four consumers:**

*PaymentService ships Phase 1 (expand — new field added alongside old):*
```json
{
  "txnId":         "txn_001",      // old field — kept for backward compat
  "transactionId": "txn_001"       // new field — consumers migrate to this
}
```

*Each consumer team, on their own schedule:*
1. Updates their client code to use `transactionId`.
2. Updates their consumer pact to reference `transactionId` instead of `txnId`.
3. Publishes the new pact to the broker.
4. PaymentService's `can-i-deploy` check now shows this consumer is ready for Phase 2.

*PaymentService ships Phase 2 (contract — old field removed) only when:*
```bash
pact-broker can-i-deploy \
  --pacticipant PaymentService \
  --version 2.5.0 \    # version with txnId removed
  --to-environment production
# Only "yes" when all 4 consumers' production versions have verified pacts
# that reference transactionId and not txnId
```

This gives the PaymentService team precise, automated visibility into when it's safe to complete the migration — without a spreadsheet, a Slack thread, or a coordination meeting.

**Q20. "You're designing the testing strategy for a new NACH payment microservice that will be consumed by the BRE, the webhook service, and a reporting service. Where do contract tests fit in your overall testing pyramid?"**
A:

```
                    ┌─────────────────────────────┐
                    │   End-to-End Tests (few)    │ ← Full NACH mandate flow
                    │   Staging environment        │   from BRE → NACH → webhook
                    └─────────────────────────────┘
               ┌───────────────────────────────────────┐
               │     Contract Tests (medium)           │
               │  BRE-NACHService pact                 │ ← "BRE sends mandate payload;
               │  WebhookService-NACHService pact      │    NACH returns ackId + status"
               │  ReportingService-NACHService pact    │ ← each consumer's actual usage
               └───────────────────────────────────────┘
          ┌─────────────────────────────────────────────────┐
          │     HTTP Integration Tests (per service)        │
          │  NACHService: POST /mandates → DB persisted     │ ← supertest + real DB
          │  BRE: evaluateMandate() → NACHClient mocked     │ ← verifies internal wiring
          └─────────────────────────────────────────────────┘
     ┌───────────────────────────────────────────────────────────┐
     │              Unit Tests (many)                            │
     │  MandateProcessor: status machine logic                   │ ← pure logic
     │  NACHApiClient: retry/backoff/error mapping               │ ← jest.fn() mocks
     │  DeduplicationService: hash comparison logic              │
     └───────────────────────────────────────────────────────────┘
```

Contract tests sit above HTTP integration tests and below E2E tests — they're the cheapest way to verify cross-service compatibility. For the NACH service specifically:

- **BRE → NACHService pact:** BRE sends `{ mandateId, accountNumber, amount, ifscCode }` and expects `{ ackId, status: "accepted"|"rejected" }`. BRE writes the consumer pact; NACH verifies it.
- **WebhookService → NACHService pact:** Webhook service polls NACH for mandate status updates and expects `{ mandateId, status, processedAt }`. Webhook writes the consumer pact.
- **ReportingService → NACHService pact:** Reporting service reads mandate summaries and expects `{ mandateId, amount, userId, createdAt, status }`. Any field the reporting service doesn't use is irrelevant to the contract.

The NACH team can confidently change internal implementation details — query restructuring, column renaming in the DB, caching layer changes — as long as `can-i-deploy` passes. The three consumer teams can deploy independently, knowing the pact verification gates protect them from silent breakage.

**Q21. "A senior engineer on your team says 'we don't need contract tests because we have end-to-end tests in staging.' How do you respond?"**
A: Acknowledge what E2E tests do well, then make the case for why they don't substitute for contract tests:

**What E2E tests in staging do well:**
- Verify full user journeys work end-to-end.
- Catch environmental issues (wrong config, network policies, infra mismatches).
- Give high confidence that the whole system works together.

**Where they fall short as a substitute for contract tests:**

*Speed and feedback loop:* E2E tests in staging run after deployment, not before. A breaking change to `PaymentService` is caught after `NotificationService` is already deployed to staging and breaking. Contract tests catch it in PR CI — before any deployment happens.

*Deployment coordination cost:* To test `PaymentService` in staging, you need `NotificationService`, `BREService`, `WebhookService`, and their dependencies all deployed and healthy simultaneously. On a team of 4 services with independent deploy cycles, a stable staging window is hard to guarantee. Contract tests need zero other services running.

*Failure localisation:* An E2E test failure in staging says "the checkout flow is broken." It doesn't say which service is at fault. A Pact verification failure says "PaymentService 2.3.1 breaks the interaction `'a request for payment status'` from NotificationService 1.4.2 because field `txnId` is missing." The diagnosis is done.

*Cost at scale:* 8 services × 8 consumers each = 64 integration surfaces. Maintaining E2E test coverage for all 64 pairs is combinatorially expensive. Contract tests scale linearly with consumer-provider pairs — each consumer owns its own pact independently.

The framing that lands: *E2E tests verify the system works; contract tests verify the team can ship independently*. Both are necessary; neither substitutes for the other.

## Quick Reference: Contract Testing Decision Guide

| Question | Answer |
|---|---|
| **When should I write a consumer pact?** | Whenever my service makes an HTTP call to another service I don't own |
| **What fields should I include in the pact?** | Only fields my code actually reads — nothing more |
| **Should I use exact or type matching?** | Type matching (`like()`) for almost everything; exact only for enum values |
| **Where does the pact file live?** | Generated locally, published to the Pact Broker from CI |
| **Who runs the provider verification?** | The provider team, in their own CI pipeline, against every consumer pact |
| **What does `can-i-deploy` check?** | Whether this version is verified against all consumer pacts for the target environment |
| **When is a breaking change safe to ship?** | When `can-i-deploy` returns yes — meaning all consumers are either verified or not deployed |
| **Does a passing contract mean the integration works?** | No — it means the shape is compatible; business logic correctness is tested elsewhere |
| **Pact vs OpenAPI schema testing?** | Pact for internal service-to-service; OpenAPI schema tests for public APIs |
| **What does the expand/contract pattern solve?** | Zero-downtime migration of breaking changes across independent deploy cycles |

---

**Tip for the interview:** At 5 YOE, contract testing questions test architectural judgement, not library syntax. The answers that land name the real problem precisely — "E2E tests catch the breakage after deployment; contract tests catch it before" — and connect it to the business cost: deployment coordination meetings, staging environment stability, the combinatorial explosion of integration surfaces. Have one story ready about a real integration breakage in a microservices system — a renamed field, a missing property, a changed status enum — and walk through how a contract test would have caught it in CI. That's the framing that signals senior-level systems thinking.
