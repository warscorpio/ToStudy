# Provider Verification — Contract Testing, Pact & Consumer-Driven Contracts — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is provider verification, and what problem does it solve?**
A: Provider verification is the practice of confirming that a service (the "provider") fulfils the expectations that its consumers have expressed about its interface — without requiring all parties to be running simultaneously. It is the provider-side half of **contract testing**.

The problem it solves: in a microservice architecture, services evolve independently. A provider team changes a response field name, removes an endpoint, or alters an error shape. Consumer teams discover the break only when their service fails in a shared integration environment — or worse, in production. The feedback loop is slow (broken integration environment, delayed deployment pipeline), the blast radius is large (every downstream consumer is affected at once), and the root cause is often unclear (which provider change broke which consumer?).

Provider verification shortens this feedback loop to the provider's own CI pipeline. Before a provider change is merged, the provider's tests replay every consumer's recorded expectations against the new implementation. If any expectation fails, the provider knows immediately — in its own pipeline, before any consumer is affected, with a precise failure message identifying which consumer and which interaction broke.

**Q2. What is a contract in the context of contract testing?**
A: A contract is a formal, machine-readable document that describes what a consumer expects from a provider. It captures:
- The **request** the consumer sends: HTTP method, path, headers, query parameters, and request body.
- The **response** the consumer expects back: status code, headers, and response body — described either as exact values or as flexible matchers (e.g., "any string", "any positive integer", "this JSON structure with these keys present").

A contract is not a full API specification (like an OpenAPI document) — it is scoped to what a *specific consumer* actually uses. If a consumer only reads `id` and `email` from a `GET /users/:id` response, the contract only specifies those two fields. The provider is free to add, rename, or restructure other fields without breaking this consumer's contract.

This scoping is the critical insight: contracts are **consumer-centric**. They grow from the consumer's real usage, not from the provider's full capability. A provider can have ten consumers with ten different contracts against the same endpoint, each specifying only the subset of the response that consumer uses.

**Q3. What is the difference between consumer-driven contract testing and provider-driven contract testing?**
A:
- **Consumer-driven contract testing (CDCT)** — the consumer writes the contract by recording its expectations (what it sends, what it needs back). The provider's job is to verify it can satisfy those expectations. The consumer is in the driver's seat: if the consumer doesn't use a field, the field isn't in the contract, and the provider can remove it freely. Pact is the primary tool for CDCT.
- **Provider-driven contract testing** — the provider publishes a specification of what it offers (often an OpenAPI document), and consumers verify their usage conforms to the spec. The provider is in the driver's seat: any field in the spec is a commitment the provider makes, whether or not consumers use it.

CDCT is generally superior in microservice architectures because:
- It eliminates over-specification — only actually-used fields are under contract.
- It gives providers precise, consumer-attributed feedback ("Consumer X will break if you remove field Y").
- It scales to many consumers without a central spec-maintenance burden.

Provider-driven contracts have their place when consumers are external / third-party (you can't ask them to write Pact tests) or when the provider is a public API where the spec itself is the product.

**Q4. What is Pact, and what are its core components?**
A: Pact is an open-source consumer-driven contract testing framework available for most major languages (JavaScript/TypeScript, Java, Go, Python, Ruby, .NET). Its core components:

- **Consumer test** — a test written in the consumer's codebase that uses a Pact mock server to simulate the provider. Running the consumer test against the mock server generates the contract file (a `.json` "pact file") that records what the consumer sent and what it expected back.
- **Pact file** — the contract artefact. A JSON document containing one or more "interactions" (request/response pairs). Generated by the consumer test; consumed by the provider verification.
- **Provider verification** — a test (or test suite) in the provider's codebase that replays each interaction in the pact file against the real provider implementation. For each interaction, Pact sends the recorded request and compares the real response against the consumer's expectation. Pass = provider satisfies the consumer; fail = breaking change detected.
- **Pact Broker** — a service (self-hosted or Pactflow SaaS) that stores pact files, tracks verification results, and manages the "can I deploy?" question: given the current state of all pacts and verifications, is it safe to deploy provider version X alongside consumer version Y?

**Q5. What is the Pact workflow end to end — from consumer test to provider deployment gate?**
A: The full lifecycle:

```
Consumer codebase                         Provider codebase
─────────────────                         ────────────────
1. Write consumer Pact test               
   (defines expected interactions)        
2. Run consumer test against              
   Pact mock server                       
3. Pact file (.json) generated            
4. Publish pact file to Pact Broker ───►  
                                          5. Provider CI picks up pact file
                                             from Pact Broker
                                          6. Provider verification test
                                             replays interactions against
                                             real provider
                                          7. Verification result published
                                             back to Pact Broker
                                    ◄───  
8. can-i-deploy check:                    8. can-i-deploy check:
   "Is my consumer version safe              "Is my provider version safe
   to deploy with current provider?"         to deploy with current consumers?"
9. Deploy consumer if safe                9. Deploy provider if safe
```

The `can-i-deploy` check is the deployment gate. It queries the Pact Broker: given the consumer version about to be deployed and the provider versions it will run alongside in the target environment, does a passing verification exist for every pact? If yes, deploy. If no, block.

## Section 2: Writing Consumer Tests

**Q6. How do you write a Pact consumer test in TypeScript?**
A: Using `@pact-foundation/pact` (v10+ uses the Rust-based core):

```typescript
// src/clients/__tests__/userService.pact.spec.ts
import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import path from 'path';
import { UserServiceClient } from '../userService.client';

const { like, string, integer, eachLike } = MatchersV3;

const provider = new PactV3({
  consumer: 'OrderService',
  provider: 'UserService',
  dir: path.resolve(__dirname, '../../../pacts'),  // where pact files are written
  logLevel: 'warn',
});

describe('UserService Pact', () => {
  describe('GET /users/:id', () => {
    it('returns user details for a valid user ID', async () => {
      await provider
        .given('user with ID 123 exists')          // provider state
        .uponReceiving('a request for user 123')   // interaction description
        .withRequest({
          method: 'GET',
          path: '/users/123',
          headers: { Accept: 'application/json' },
        })
        .willRespondWith({
          status: 200,
          headers: { 'Content-Type': like('application/json') },
          body: {
            id: integer(123),
            email: string('user@example.com'),     // any string — not this exact value
            name: string('Test User'),
            role: like('customer'),
            isVerified: like(true),
          },
        })
        .executeTest(async (mockServer) => {
          // Point the real client at the Pact mock server
          const client = new UserServiceClient(mockServer.url);
          const user = await client.getUser(123);

          // Assert on the consumer's own logic, not just the HTTP call
          expect(user.id).toBe(123);
          expect(user.email).toBeDefined();
        });
    });

    it('returns 404 for a non-existent user', async () => {
      await provider
        .given('user with ID 999 does not exist')
        .uponReceiving('a request for a non-existent user')
        .withRequest({ method: 'GET', path: '/users/999' })
        .willRespondWith({
          status: 404,
          body: { error: like('User not found') },
        })
        .executeTest(async (mockServer) => {
          const client = new UserServiceClient(mockServer.url);
          await expect(client.getUser(999)).rejects.toThrow('User not found');
        });
    });
  });
});
```

Running this test generates `pacts/OrderService-UserService.json` — the contract file.

**Q7. What are Pact matchers, and why are they preferable to exact value matching?**
A: Matchers allow the consumer to express *structural* expectations about the response rather than exact values. This makes contracts robust — provider tests pass even when example data changes (different IDs in different environments, timestamps, random values):

| Matcher | What it asserts | Use case |
|--|--|--|
| `like(value)` | Same type as value; ignores the exact value | Any string, any boolean, any object of this shape |
| `string('example')` | Must be a string; example value used in mock | Email addresses, names, tokens |
| `integer(42)` | Must be an integer | IDs, counts, amounts in paise |
| `decimal(3.14)` | Must be a decimal number | Prices, rates, coordinates |
| `boolean(true)` | Must be a boolean | Flags, status fields |
| `eachLike(item)` | Array where every element matches `item` | Lists of objects |
| `atLeastOneLike(item, 2)` | Array with at least 2 elements matching | Non-empty lists |
| `regex(pattern, example)` | String matching the regex | UUIDs, phone numbers, postal codes |
| `iso8601DateTime()` | Valid ISO 8601 datetime string | `createdAt`, `updatedAt` fields |
| `uuid()` | Valid UUID v4 string | Entity IDs |

```typescript
// ❌ Exact matching — brittle, breaks if the provider returns a different ID
body: { id: 123, email: 'specific@example.com', createdAt: '2024-01-15T10:00:00Z' }

// ✅ Matcher-based — resilient, tests structure not specific values
body: {
  id: integer(123),
  email: string('user@example.com'),
  createdAt: iso8601DateTime(),
  address: like({
    city: string('Mumbai'),
    pincode: regex(/^\d{6}$/, '400001'),
  }),
}
```

Exact matching is appropriate only when the consumer's logic genuinely depends on a specific value — for example, if the consumer checks that `status === 'active'` and treats any other value differently, then the contract should specify the string `'active'` exactly, not `like('active')`.

**Q8. What is a provider state, and how does it set up the preconditions a consumer test requires?**
A: A provider state is a named precondition declared in the consumer test (`.given('user with ID 123 exists')`) that tells the provider "before you replay this interaction, put your system into this state." It bridges the consumer's assumption ("this user exists") with the provider's responsibility ("create that user before the test runs").

On the provider side, provider states are implemented as state handlers — functions that the provider verification framework calls before each interaction:

```typescript
// Provider verification setup
stateHandlers: {
  'user with ID 123 exists': async () => {
    await userRepository.save({
      id: 123,
      email: 'user@example.com',
      name: 'Test User',
      role: 'customer',
      isVerified: true,
    });
  },
  'user with ID 999 does not exist': async () => {
    await userRepository.delete({ id: 999 }); // ensure it's absent
  },
  'no users exist': async () => {
    await userRepository.clear();
  },
}
```

Provider states are the seeding mechanism for provider verification. They are the equivalent of `beforeEach` setup, but driven by the consumer's declarations rather than the provider's own test code. Well-named states read as business requirements: "given a suspended user", "given an order with a failed payment", "given the rate limit has been reached".

## Section 3: Provider Verification In Depth

**Q9. How do you set up provider verification for a NestJS/Express API?**
A: Provider verification runs the real provider application and replays consumer interactions against it. Using `@pact-foundation/pact`:

```typescript
// src/__tests__/provider.pact.spec.ts
import { Verifier } from '@pact-foundation/pact';
import { Test } from '@nestjs/testing';
import { INestApplication } from '@nestjs/common';
import { AppModule } from '../app.module';

describe('UserService Provider Verification', () => {
  let app: INestApplication;
  let server: http.Server;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleRef.createNestApplication();
    await app.init();
    server = app.getHttpServer();
  });

  afterAll(async () => {
    await app.close();
  });

  it('validates consumer contracts', async () => {
    const verifier = new Verifier({
      provider: 'UserService',
      providerBaseUrl: `http://localhost:${(server.address() as AddressInfo).port}`,

      // Fetch pacts from Pact Broker
      pactBrokerUrl: process.env.PACT_BROKER_URL,
      pactBrokerToken: process.env.PACT_BROKER_TOKEN,

      // Which pacts to verify: all consumers, or a specific version
      consumerVersionSelectors: [
        { mainBranch: true },             // latest on consumer's main branch
        { deployedOrReleased: true },     // versions currently deployed anywhere
      ],

      // Tag this verification with the provider's current branch/version
      providerVersion: process.env.GIT_COMMIT_SHA,
      providerVersionBranch: process.env.GIT_BRANCH,

      // State handler setup
      stateHandlers: {
        'user with ID 123 exists': async () => {
          await seedUser({ id: 123, email: 'user@example.com', role: 'customer' });
        },
        'user with ID 999 does not exist': async () => {
          await deleteUser(999);
        },
        'no users exist': async () => {
          await truncateUsers();
        },
      },

      // Called before each interaction to clean up state
      beforeEach: async () => {
        await truncateTestData();
      },

      logLevel: 'warn',
      publishVerificationResult: process.env.CI === 'true', // only publish in CI
    });

    await verifier.verifyProvider();
  });
});
```

**Q10. What is `consumerVersionSelectors` and why is it the right way to specify which pacts to verify?**
A: `consumerVersionSelectors` tells the Pact Broker which consumer pact versions to fetch for verification. It replaces the older `pactUrls` (hardcoded file paths) and `tags` (deprecated) approaches. The key selectors:

| Selector | What it fetches | When to use |
|--|--|--|
| `{ mainBranch: true }` | Latest pact from each consumer's main branch | Always — this is the source of truth |
| `{ deployedOrReleased: true }` | Pacts from consumer versions deployed to any environment | Always — ensures backwards compatibility with what's live |
| `{ branch: 'feature/xyz' }` | Pact from a specific consumer branch | During consumer feature branch development |
| `{ matchingBranch: true }` | Pact from the consumer branch with the same name as the provider's current branch | For co-developing provider and consumer changes together |

The combination of `mainBranch: true` and `deployedOrReleased: true` is the production-safe minimum: verify you don't break the latest consumer code, and verify you don't break any consumer version that is currently running in any environment.

`matchingBranch: true` is the key to the "feature branch workflow" — if a consumer team has a branch `feature/new-payment-flow` and the provider team has a branch with the same name, the provider verification on that branch will automatically pick up the consumer's feature branch pact, enabling coordinated development without merging either branch first.

**Q11. How does Pact handle verification of message-based (async/event-driven) interactions, not just HTTP?**
A: Pact supports asynchronous message contracts via its **message pact** feature, which covers Kafka, RabbitMQ, SNS/SQS, and any event-based integration:

**Consumer side** — defines what the consumer expects the message payload to look like:
```typescript
// OrderService consumes UserCreated events from UserService
import { MessageConsumerPact, asynchronousBodyHandler } from '@pact-foundation/pact';

const messagePact = new MessageConsumerPact({
  consumer: 'OrderService',
  provider: 'UserService',
  dir: path.resolve(__dirname, '../../../pacts'),
});

it('handles a UserCreated event', async () => {
  await messagePact
    .given('a new user was created')
    .expectsToReceive('a UserCreated event')
    .withContent({
      eventType: like('USER_CREATED'),
      userId: uuid(),
      email: string('user@example.com'),
      createdAt: iso8601DateTime(),
    })
    .withMetaData({ contentType: 'application/json' })
    .verify(
      asynchronousBodyHandler(async (message: UserCreatedEvent) => {
        // Test that the consumer correctly handles the message
        const result = await handleUserCreated(message);
        expect(result.userId).toBe(message.userId);
      })
    );
});
```

**Provider side** — instead of an HTTP server, the provider verification calls a function that produces the message:
```typescript
// In provider verification setup:
messageProviders: {
  'a UserCreated event': async () => {
    // Return the actual message the provider would publish
    return {
      eventType: 'USER_CREATED',
      userId: 'a8f29d3e-1234-4567-89ab-cdef01234567',
      email: 'newuser@example.com',
      createdAt: new Date().toISOString(),
    };
  },
},
```

Pact does not send the message through a real broker — it verifies only the message payload shape. The broker infrastructure (Kafka, RabbitMQ) is tested separately at the integration level. This separation keeps message contract tests fast and independent of broker availability.

**Q12. What is the Pact Broker, and what does it enable beyond simple file sharing?**
A: The Pact Broker is a centralised repository and coordination service for pact files and verification results. Beyond storing JSON files, it enables:

- **`can-i-deploy` queries** — the most important feature. Given a service version and a target environment, the Broker answers: "Are all the pacts this version participates in (as consumer or provider) verified as passing by compatible counterpart versions?" This is the deployment gate.
- **Network graph** — the Broker builds a live graph of which services depend on which other services, based on existing pacts. Teams can see their blast radius before making a change.
- **Webhook triggers** — when a consumer publishes a new pact, the Broker can trigger the provider's CI pipeline via webhook to run verification immediately, without waiting for the provider's next scheduled build.
- **Version tracking** — pacts are versioned and tagged (now: branch-based). The Broker tracks which consumer version is deployed to which environment, enabling the `deployedOrReleased` selector.
- **Pending pacts** — a pact from a new consumer that has never been verified yet is marked "pending." The provider's verification suite picks it up but does not fail if it can't satisfy it — this prevents a new consumer from blocking the provider's pipeline before coordination has happened.
- **WIP (Work In Progress) pacts** — pacts from consumer feature branches that are not yet merged. The provider verifies them but treats failures as informational, not blocking.

**Pactflow** is the SaaS-hosted version of the Pact Broker with additional features: bidirectional contract testing (for OpenAPI providers), RBAC, and enterprise SSO. Pact Broker is self-hostable and open-source.

## Section 4: Advanced Patterns

**Q13. What are "pending pacts" and "WIP pacts," and how do they solve the chicken-and-egg problem?**
A: The chicken-and-egg problem: a new consumer team wants to write a Pact for a provider that doesn't know about them yet. If the new pact is immediately treated as a hard failure in the provider's pipeline, the provider is blocked by a consumer they haven't agreed to support. Neither team can move forward.

**Pending pacts** solve this for new consumer/provider relationships. A pact is "pending" if it has never had a successful verification published for the current provider branch. In pending state:
- The provider verification suite picks up the pact and tries to verify it.
- If verification fails, the provider's CI does **not** fail — the failure is reported as informational.
- Once the provider publishes a successful verification, the pact transitions from pending to non-pending. From that point on, failures in this pact **do** fail the provider's CI.

This gives the provider team time to implement the new endpoint without being blocked, while keeping the consumer informed of the verification status.

**WIP (Work In Progress) pacts** extend this to feature branches. A consumer branch pact that is not on the consumer's main branch (not yet merged, not deployed anywhere) is WIP. The provider verifies it but treats failures as informational — the consumer's feature isn't live yet, so there's no production risk.

Together, pending and WIP pacts make contract testing practical in organisations where consumer and provider teams move at different speeds and don't coordinate every change upfront.

**Q14. What is the `can-i-deploy` tool, and how do you integrate it into a CI pipeline?**
A: `can-i-deploy` is a Pact Broker CLI command that answers a binary question: "Given the version of service X I'm about to deploy, and the environment I'm deploying to, is it safe to proceed?" It checks:

1. Does a pact file exist between X and every service it interacts with?
2. For every such pact, does a passing verification result exist from a compatible version of the counterpart service?
3. Is that counterpart version already deployed in the target environment (or is it also being deployed now)?

```yaml
# .github/workflows/deploy.yml
jobs:
  deploy:
    steps:
      - name: Run tests with coverage
        run: npm test

      - name: Publish pacts (consumer) or verification results (provider)
        run: npx pact-broker publish ./pacts
          --broker-base-url ${{ secrets.PACT_BROKER_URL }}
          --broker-token ${{ secrets.PACT_BROKER_TOKEN }}
          --consumer-app-version ${{ github.sha }}
          --branch ${{ github.ref_name }}

      - name: Check can-i-deploy
        run: npx pact-broker can-i-deploy
          --pacticipant UserService
          --version ${{ github.sha }}
          --to-environment production
          --broker-base-url ${{ secrets.PACT_BROKER_URL }}
          --broker-token ${{ secrets.PACT_BROKER_TOKEN }}

      - name: Deploy
        if: success()
        run: ./scripts/deploy.sh production

      - name: Record deployment
        run: npx pact-broker record-deployment
          --pacticipant UserService
          --version ${{ github.sha }}
          --environment production
          --broker-base-url ${{ secrets.PACT_BROKER_URL }}
          --broker-token ${{ secrets.PACT_BROKER_TOKEN }}
```

The `record-deployment` step is critical — it tells the Broker which version is currently in production, enabling the `deployedOrReleased` selector in future verifications and keeping the Broker's environment state accurate.

**Q15. What is bidirectional contract testing (BDCT), and how does it differ from Pact's consumer-driven approach?**
A: Bidirectional contract testing (introduced by Pactflow) is an approach where:
- The **consumer** generates a consumer contract (from Pact consumer tests, or from an OpenAPI specification of what it uses).
- The **provider** publishes its own OpenAPI specification (its full API description).
- Pactflow **cross-validates** the two: does the provider's spec satisfy the consumer's contract? If yes, the contract is verified — without the provider running any Pact-specific test code.

| Dimension | Standard Pact (CDCT) | Bidirectional (BDCT) |
|--|--|--|
| Provider effort | Must write state handlers and run Pact verification | Publishes existing OpenAPI spec |
| Consumer effort | Writes Pact consumer tests | Writes Pact consumer tests (same) |
| Verification mechanism | Provider replays interactions against real code | Pactflow cross-validates specs statically |
| Catches runtime bugs | Yes — runs real provider code | No — only checks specs match |
| Provider adoption barrier | High (write state handlers, run verification) | Low (publish existing OpenAPI) |
| Best for | Internal services with full control | Third-party providers; providers already maintaining OpenAPI |

BDCT trades depth (it doesn't run real code) for adoption ease (the provider only needs an OpenAPI spec). It is particularly valuable when onboarding a provider team that already maintains an OpenAPI document but can't invest in writing Pact state handlers.

**Q16. How do you test a provider that has authentication — JWT, API keys, or OAuth — in Pact verification?**
A: Authentication in provider verification must be bypassed or pre-configured, because the Pact verification framework sends the exact request the consumer recorded — including whatever auth header the consumer test included. Three approaches:

**Approach 1 — Include a valid test token in the consumer interaction**
The consumer test includes a pre-shared test API key or a fixed-format JWT that the provider's test environment accepts:
```typescript
// Consumer test
.withRequest({
  method: 'GET',
  path: '/users/123',
  headers: {
    Authorization: like('Bearer test-token'), // provider accepts this in test env
  },
})
```
The provider's test configuration accepts any `Bearer test-*` token without signature validation.

**Approach 2 — Request filter: inject auth before the interaction is replayed**
The provider verification setup intercepts each request and adds a valid auth header before forwarding it:
```typescript
// Provider verification
requestFilter: (req, res, next) => {
  // Add a valid token to every verification request
  req.headers['Authorization'] = `Bearer ${generateTestJwt({ sub: 'pact-verifier' })}`;
  next();
},
```
This keeps auth out of the pact file entirely — the consumer doesn't need to specify auth headers, and the provider handles them transparently during verification.

**Approach 3 — Disable auth middleware for the verification test environment**
The provider boots with auth middleware disabled when `NODE_ENV === 'pact'`:
```typescript
// app.module.ts
if (process.env.NODE_ENV !== 'pact') {
  app.use(jwtAuthMiddleware);
}
```
Simple but requires disciplined environment configuration — the `pact` environment must not be accessible outside the test process.

Approach 2 (request filter) is the cleanest for most scenarios: it keeps pact files free of environment-specific tokens, and the auth logic is encapsulated in the verification setup rather than spread across consumer tests.

## Section 5: Tradeoffs, Pitfalls & Best Practices

**Q17. What are the common pitfalls when adopting Pact in a team, and how do you avoid them?**
A:

**Pitfall 1 — Treating Pact as a replacement for integration tests**
Pact verifies the contract (request/response shape); it does not verify business logic. A provider that returns the right JSON shape but wrong data (incorrect calculation, wrong user data) passes Pact verification. Pact and integration tests are complementary, not substitutes.

**Pitfall 2 — Over-specifying in consumer tests (exact value matching everywhere)**
```typescript
// ❌ Exact matching — breaks every time the provider's seed data changes
body: { id: 123, email: 'john@example.com', createdAt: '2024-01-15T10:00:00.000Z' }
```
Fix: use matchers for anything that is not semantically significant to the consumer's logic.

**Pitfall 3 — Verifying against a mocked database instead of a real one**
If provider verification runs against an in-memory mock instead of a real (test) database, it may pass despite real SQL queries being broken. Provider state handlers should use the same DB layer as production — Testcontainers or a seeded test database.

**Pitfall 4 — Not publishing verification results to the Broker**
Teams run `verifier.verifyProvider()` locally but don't publish results to the Broker. `can-i-deploy` has no data to work with and either blocks all deployments or is skipped. Always set `publishVerificationResult: process.env.CI === 'true'`.

**Pitfall 5 — Writing pact tests for every endpoint instead of every interaction pattern**
Contract tests have a maintenance cost. Don't write a pact test for every permutation of every endpoint — write one for each *type of interaction* the consumer has: happy path, 404, validation error, auth failure. Coverage of edge cases belongs in unit and integration tests, not contract tests.

**Pitfall 6 — Provider state handlers that are too coupled to implementation**
```typescript
// ❌ State handler reaches into internals
'user with ID 123 exists': async () => {
  await db.query(`INSERT INTO users VALUES (123, 'john@example.com', ...)`);
}
```
If the schema changes, every state handler breaks. Fix: use the same factory functions as the rest of the test suite — `await createUser(db, { id: 123 })` — so schema changes are handled in one place.

**Q18. How does provider verification relate to semantic versioning and breaking changes?**
A: Pact verification answers a more precise question than semver alone: "Does provider version X satisfy consumer version Y's contract?" Semver communicates intent (a major bump signals a breaking change) but doesn't verify it. A provider that claims a minor version bump may still break a consumer's contract if a field was removed or renamed.

Provider verification makes breaking changes detectable before deployment:
- **Additive changes** (new fields, new endpoints) — always safe; existing consumers' contracts don't specify the new fields, so verification passes.
- **Renaming a field** (`user_id` → `userId`) — breaks any consumer that specifies `user_id` in their contract. Verification fails for that consumer.
- **Removing a field** — same as renaming: fails for any consumer that expects the field.
- **Changing a field type** (`amount: integer` → `amount: string`) — fails for any consumer using `integer()` matcher on that field.
- **Changing status codes** (200 → 201) — fails for any consumer expecting the original code.

The workflow: before merging a provider change, run `can-i-deploy`. If it fails, the provider must either: coordinate with the affected consumer to update the contract, maintain backwards compatibility (keep the old field alongside the new one during a transition period), or acknowledge this is an intentional breaking change requiring a consumer update.

**Q19. What is the difference between contract testing and schema validation (e.g., JSON Schema, OpenAPI validation)?**
A: Both check the shape of API responses, but at different times and with different scope:

| Dimension | Contract testing (Pact) | Schema validation (JSON Schema / OpenAPI) |
|--|--|--|
| When | Before deployment (CI gate) | At runtime (request/response validation) |
| Perspective | Consumer-centric (what each consumer uses) | Provider-centric (full API surface) |
| Failure signal | "Consumer X will break if you deploy" | "This response does not match the spec" |
| Coverage | Only what consumers actually use | Full specification |
| Catches | Breaking changes before they reach consumers | Invalid responses reaching users |
| Latency of feedback | Pre-deployment | Post-deployment (production traffic) |

They are complementary: contract testing prevents breaking changes from being deployed; schema validation catches runtime deviations (bugs, incomplete implementation, edge cases) in the deployed service. A mature API infrastructure uses both — Pact as the pre-deployment gate, OpenAPI request/response validation as the runtime safety net.

**Q20. When should you NOT use Pact, and what are the alternatives?**
A: Pact is not always the right tool:

- **Third-party / public APIs** — you can't ask Stripe, Twilio, or Razorpay to run your Pact verification. Use recorded HTTP cassettes (VCR pattern via `nock`, `msw`, or `polly.js`) to replay real API responses in tests, and monitor the real API for breaking changes.
- **Highly volatile internal APIs** — if an API changes multiple times per sprint, the overhead of maintaining pact files and state handlers may exceed the benefit. Consider stabilising the API first or using integration tests against a shared test environment.
- **Schema-first / design-first APIs** — if the provider team already maintains a rigorous OpenAPI document and both teams trust it, bidirectional contract testing against the spec may be sufficient without implementing full Pact.
- **Monorepos where consumer and provider are deployed together** — if consumer and provider are always deployed as a unit, the contract testing problem doesn't exist. Use integration tests instead.
- **GraphQL APIs** — Pact support for GraphQL is immature. Better alternatives: schema diffing tools (`graphql-inspector`), integration tests against the GraphQL layer, or Apollo's contract testing tooling.

## Section 6: Scenario / System Design Style Questions

**Q21. "The provider team says they can't adopt Pact because it's too much work to write state handlers for 50 consumer interactions. How do you respond?"**
A: Acknowledge the concern — state handlers are the highest-friction part of Pact adoption — then offer a practical path forward:

**Reframe the scope**: 50 interactions doesn't mean 50 unique state handlers. Group interactions by shared preconditions:
- "user exists" covers every interaction that needs any user — one handler, parameterised.
- "order in status X" covers every order-status interaction — one handler with a parameter.
In practice, 50 interactions typically collapse to 8–12 distinct states.

**Parameterise state handlers** to reduce duplication:
```typescript
stateHandlers: {
  'a user exists': async (params: { id?: number; role?: string }) => {
    await createUser(db, { id: params.id ?? 123, role: params.role ?? 'customer' });
  },
}
// Consumer test uses: .given('a user exists', { id: 456, role: 'admin' })
```

**Offer to pair**: the consumer team knows what state each interaction needs. A half-day pairing session between consumer and provider engineers to map interactions to states is usually enough to unblock the entire adoption.

**Offer BDCT as a stepping stone**: if the provider already has an OpenAPI spec, Pactflow's bidirectional mode requires zero state handlers from the provider. Use it initially; migrate to full Pact as teams get comfortable.

The underlying point to make: the cost of writing 12 state handlers once is far lower than the cost of one production outage caused by a breaking change that contract testing would have caught.

**Q22. "A consumer team changed their Pact and the provider's CI is now failing. The provider team is angry because they didn't know about the change. How do you fix the process?"**
A: The root problem is a lack of coordination — the consumer changed their contract without notifying the provider. Fix it at the process level:

**Immediate fix — enable webhooks**
Configure the Pact Broker to trigger the provider's CI pipeline automatically whenever a consumer publishes a new or changed pact:
```json
// Pact Broker webhook config
{
  "events": [{ "name": "contract_content_changed" }],
  "request": {
    "method": "POST",
    "url": "https://ci.company.com/api/trigger/UserService",
    "headers": { "Authorization": "Bearer {{ secrets.CI_TOKEN }}" },
    "body": {
      "message": "Pact changed by {{ consumer.name }} — please verify"
    }
  }
}
```
Now the provider's pipeline runs automatically the moment the consumer changes the pact — no manual notification needed.

**Structural fix — pending pacts**
Enable pending pacts on the provider side. New or changed pacts are pending until the provider has published a passing verification. This means the provider's pipeline doesn't fail on the consumer's change — it picks up the new pact, tries to verify it, and reports the result as informational. The provider team has time to implement the new expectation without being blocked.

**Cultural fix — consumer responsibilities**
The consumer team should treat a pact change with the same care as an API change: notify the provider in advance, open a ticket, or pair on the implementation. A pact change that requires the provider to add a new endpoint or change its response is a **cross-team API contract negotiation**, not a unilateral consumer decision.

**Q23. "You're designing a contract testing strategy for a fintech platform with 12 microservices — payments, KYC, fraud, notifications, ledger, auth, and six others. Where do you start, and how do you prioritise?"**
A: A 12-service platform is too large to instrument all at once. Prioritise by two axes: **traffic volume** (high-traffic integrations break more users) and **failure cost** (payment and ledger failures have financial and regulatory consequences):

**Phase 1 — Critical financial flows (weeks 1–4)**
Start with the integrations that, if broken, cause financial loss or regulatory exposure:
- `PaymentService` → `LedgerService` (debits and credits)
- `PaymentService` → `FraudService` (transaction scoring)
- `PaymentService` → `NotificationService` (payment confirmations)

These three provider/consumer pairs cover the most critical path. Instrument the consumer tests, set up the Pact Broker, implement state handlers for the three providers, and wire `can-i-deploy` into the deployment pipelines for all six services.

**Phase 2 — Auth and KYC (weeks 5–8)**
Auth is a dependency of every service — a breaking change in `AuthService` affects all 11 consumers simultaneously. KYC state is read by payments and fraud. Add:
- All consumers → `AuthService` (token validation, user identity)
- `PaymentService` → `KYCService` (verification status checks)

**Phase 3 — Remaining integrations (weeks 9–16)**
Add contracts for the remaining integrations, using the Pact Broker's network graph to identify which pairs have the highest interaction frequency.

**Infrastructure to set up in Phase 1 and reuse for all phases:**
- Self-hosted Pact Broker (or Pactflow) with webhooks configured for all services.
- A shared `stateHandlerFactory` utility that all provider teams import — standardises how state handlers seed test data using the common factory functions.
- A CI template (reusable GitHub Actions workflow) for provider verification — provider teams copy one file, fill in service name and state handlers, and are fully integrated.

**Q24. "During provider verification, an interaction fails because the provider returns an extra field the consumer didn't specify. Should this fail?**
A: No — and by default, Pact correctly does not fail on extra fields in the response body. This is one of Pact's most important design decisions: **consumer contracts are not exhaustive specifications**. The consumer only asserts on the fields it uses. Extra fields from the provider are irrelevant to the consumer's correctness.

```json
// Consumer expected:
{ "id": 123, "email": "user@example.com" }

// Provider returned:
{ "id": 123, "email": "user@example.com", "createdAt": "2024-01-15", "updatedAt": "2024-01-20" }

// Result: PASS — extra fields do not constitute a contract violation
```

This property is what allows providers to add new fields freely — additive changes are always safe. It is also why contract testing scales in organisations where many consumers read the same endpoint: each consumer specifies only its own subset, and the provider can evolve its response without coordinating with every consumer.

The exception: if the consumer tests use `exact` matching instead of `like()` or structural matchers, extra fields will fail. This is almost always a mistake in the consumer test — the fix is to replace `exact` matching with appropriate matchers, not to remove fields from the provider.

**Q25. "Walk me through how you would handle a scenario where PaymentService (consumer) needs OrderService (provider) to add a new field `gatewayTransactionId` to the order response, and OrderService hasn't implemented it yet."**
A: This is the standard workflow for coordinating a provider change from the consumer side:

**Step 1 — Consumer adds the expectation to their Pact test**
```typescript
.willRespondWith({
  status: 200,
  body: {
    id: integer(123),
    status: like('confirmed'),
    amount: integer(10000),
    gatewayTransactionId: string('pay_abc123'), // new field — consumer needs this
  },
})
```
The consumer runs their Pact test. The test passes (against the Pact mock server, which returns whatever the consumer specifies). A new pact file is generated including the `gatewayTransactionId` expectation.

**Step 2 — Consumer publishes the updated pact to the Broker**
The Pact Broker receives the new pact. Because `OrderService` has not yet verified this version of the pact, it is marked **pending**.

**Step 3 — Broker webhook triggers OrderService CI**
OrderService's pipeline is triggered automatically. Provider verification runs. The `gatewayTransactionId` field is not yet in the response. Verification fails — but because the pact is pending, the provider's CI does **not** fail. The result is published as a failing verification, visible in the Broker's dashboard.

**Step 4 — OrderService implements the new field**
The OrderService team sees the failing verification in the Broker, picks up the ticket, and implements `gatewayTransactionId` in the order response. They update the state handler if needed.

**Step 5 — OrderService runs verification again**
Verification passes. The result is published to the Broker. The pact transitions from pending to non-pending. From now on, if `gatewayTransactionId` is removed from the response, OrderService's verification will fail their CI — the contract is now enforced.

**Step 6 — can-i-deploy clears for both sides**
PaymentService's `can-i-deploy` check now passes (OrderService has a passing verification for the new pact). OrderService's `can-i-deploy` also passes. Both services can deploy safely.

This workflow — consumer writes expectation, pact is pending, provider implements, verification passes, both deploy — is the intended happy path for coordinated API evolution in a Pact-based system.

## Quick Reference Table

| Concept | Definition | Key detail |
|--|--|--|
| **Consumer** | Service that calls another service's API | Writes Pact consumer tests; generates pact files |
| **Provider** | Service that exposes an API | Runs provider verification against consumer pacts |
| **Pact file** | Machine-readable contract (JSON) | Generated by consumer tests; verified by provider |
| **Provider state** | Named precondition for an interaction | `.given('user exists')` → state handler seeds the DB |
| **Matcher** | Structural assertion (not exact value) | `like()`, `string()`, `integer()`, `uuid()`, `regex()` |
| **Pact Broker** | Central store for pacts and verification results | Enables `can-i-deploy`; tracks deployments |
| **can-i-deploy** | CLI check: is it safe to deploy this version? | Queries Broker for passing verifications in target env |
| **Pending pact** | Pact never successfully verified on this branch | Failures are informational; does not block provider CI |
| **WIP pact** | Pact from a consumer feature branch | Verified but non-blocking; for in-progress consumer work |
| **CDCT** | Consumer-driven contract testing | Consumer writes contract; provider verifies it |
| **BDCT** | Bidirectional contract testing (Pactflow) | Provider publishes OpenAPI; Pactflow cross-validates |
| **consumerVersionSelectors** | Which consumer pact versions to verify | `mainBranch: true` + `deployedOrReleased: true` minimum |
| **record-deployment** | Tells Broker which version is deployed where | Required for `deployedOrReleased` selector to work |
| **Message pact** | Contract for async event payloads | Verifies message shape, not broker infrastructure |

**Tip for the interview:** At the 5 YOE level, "what is contract testing" won't be asked alone — it surfaces in system design ("how do you prevent breaking changes in a microservice architecture?"), in reliability discussions ("how do you catch API regressions before they reach production?"), and in team process conversations ("how do you coordinate API changes across teams?"). The strongest signal you can give is understanding the full feedback loop — from consumer writing an expectation, to pending pact, to provider implementing the change, to `can-i-deploy` clearing for both sides. Have a concrete story about a breaking change that contract testing caught before production, or a coordination problem (consumer changed a pact silently) and the webhook-based process that fixed it. Knowing when *not* to use Pact (third-party APIs, monorepos, GraphQL) and what to use instead shows the senior-level judgement interviewers are looking for.
