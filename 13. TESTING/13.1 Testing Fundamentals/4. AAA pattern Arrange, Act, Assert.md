# Testing: AAA Pattern (Arrange, Act, Assert) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the AAA pattern, and why does it exist?**
A: AAA (Arrange, Act, Assert) is a structural convention for writing test cases that separates a test into three clearly bounded phases:

- **Arrange** — set up all preconditions: instantiate the subject under test (SUT), configure dependencies (real or mocked), seed data, and establish the starting state the test assumes.
- **Act** — invoke the single behaviour being tested. Typically one function call, one method invocation, or one HTTP request.
- **Assert** — verify the outcome matches expectations: return values, state changes, side effects, errors thrown.

It exists because tests have two audiences — the test runner (correctness) and the next engineer (documentation). Without a consistent structure, tests become dense, hard to scan, and hard to debug when they fail. AAA makes the *what* (Assert), *how* (Act), and *given* (Arrange) immediately visible at a glance, without reading the entire test body.

**Q2. What are the boundaries between the three phases, and how strict should they be?**
A: In simple unit tests the boundaries are clear and rigid — a blank line between each phase is the conventional signal:

```typescript
it("should return the discounted price for a premium user", () => {
  // Arrange
  const user    = { id: "u1", tier: "premium" };
  const product = { id: "p1", basePrice: 1000 };

  // Act
  const price = calculatePrice(product, user);

  // Assert
  expect(price).toBe(800);
});
```

In integration or end-to-end tests, the boundaries blur legitimately: a single test may need multiple Act steps to reach the state being tested (e.g., create an order, then confirm it, then assert the confirmation state). The rule of thumb: **one primary Act per test**. Multiple Acts are a signal that either the test is doing too much (split it) or the prior Acts are really part of Arrange (rename them accordingly).

**Q3. What belongs in Arrange vs what belongs in `beforeEach`?**
A: The distinction is **specificity vs commonality**:

- **`beforeEach`** — setup that is identical across all tests in the suite: instantiating the SUT, resetting mocks, seeding shared fixtures, opening DB connections. It's factored out because it would be noise if duplicated in every test.
- **Arrange inside the test** — setup that is *specific to this test case*: the particular input values, the specific mock return value for this scenario, the edge-case state. This must stay in the test body because it's part of the test's documentation — it tells the reader *why* this case is different.

Putting everything in `beforeEach` makes each test unreadable in isolation. Putting everything in each test body creates massive duplication. The split: shared scaffolding in `beforeEach`, distinctive inputs and mock configurations in Arrange.

**Q4. Why should the Act phase typically be a single line?**
A: The Act phase exists to isolate *exactly one behaviour* under test. If Act requires multiple calls, it usually means:
- You're testing more than one thing (split into separate tests).
- The prior calls are setup (move them to Arrange).
- The system has a design problem — the behaviour requires too many steps to invoke (a signal for the developer, not just the tester).

Single-line Act also has a practical debugging benefit: when a test fails, the failure is unambiguously caused by that one call — not by an interaction between multiple calls in a multi-step Act.

**Q5. What is the difference between state-based and interaction-based assertions in the Assert phase?**
A:

- **State-based assertions** — verify the observable output or state after the Act: return values, object properties, DB records, file contents. These are preferred — they test *what* the system does, not *how* it does it.

```typescript
// State-based: assert the result
expect(result.status).toBe("approved");
expect(result.amount).toBe(5000);
```

- **Interaction-based assertions** — verify that specific calls were made to dependencies: which mock was called, with what arguments, how many times. These test *how* the system achieves its result, making tests brittle to refactoring.

```typescript
// Interaction-based: assert the collaboration
expect(paymentGateway.charge).toHaveBeenCalledWith({
  amount: 5000,
  currency: "INR",
  userId: "u1",
});
```

Both have legitimate uses, but the rule is: **prefer state-based; use interaction-based only when side effects (calls to external systems) are the behaviour under test** and there's no state to inspect. Overusing interaction-based assertions couples the test to implementation details — renaming an internal method breaks the test even if the behaviour is identical.

## Section 2: AAA in Unit Tests

**Q6. Walk through a complete unit test for a service method in NestJS using AAA.**
A:

```typescript
// src/payments/payment.service.ts
@Injectable()
export class PaymentService {
  constructor(
    private readonly gatewayClient: GatewayClient,
    private readonly ledgerRepo:    LedgerRepository,
  ) {}

  async processPayment(payload: PaymentPayload): Promise<PaymentResult> {
    const charge = await this.gatewayClient.charge(payload);
    if (charge.status !== "success") {
      throw new PaymentFailedError(charge.reason);
    }
    await this.ledgerRepo.record({
      txnId:  charge.txnId,
      amount: payload.amount,
      userId: payload.userId,
    });
    return { txnId: charge.txnId, status: "completed" };
  }
}
```

```typescript
// src/payments/payment.service.spec.ts
describe("PaymentService", () => {
  let service:       PaymentService;
  let gatewayClient: jest.Mocked<GatewayClient>;
  let ledgerRepo:    jest.Mocked<LedgerRepository>;

  beforeEach(() => {
    // Shared scaffolding — same for every test in this suite
    gatewayClient = { charge: jest.fn() } as jest.Mocked<GatewayClient>;
    ledgerRepo    = { record: jest.fn() } as jest.Mocked<LedgerRepository>;
    service       = new PaymentService(gatewayClient, ledgerRepo);
  });

  describe("processPayment", () => {
    it("should record the ledger entry and return completed status on successful charge", async () => {
      // Arrange — specific to this success case
      const payload: PaymentPayload = { userId: "u1", amount: 5000, currency: "INR" };
      gatewayClient.charge.mockResolvedValue({ status: "success", txnId: "txn_abc" });

      // Act
      const result = await service.processPayment(payload);

      // Assert
      expect(result).toEqual({ txnId: "txn_abc", status: "completed" });
      expect(ledgerRepo.record).toHaveBeenCalledWith({
        txnId:  "txn_abc",
        amount: 5000,
        userId: "u1",
      });
    });

    it("should throw PaymentFailedError and not record the ledger when the gateway declines", async () => {
      // Arrange — specific to the failure case
      const payload: PaymentPayload = { userId: "u1", amount: 5000, currency: "INR" };
      gatewayClient.charge.mockResolvedValue({ status: "failed", reason: "insufficient_funds" });

      // Act & Assert — combined only when testing that an async call throws
      await expect(service.processPayment(payload)).rejects.toThrow(PaymentFailedError);
      expect(ledgerRepo.record).not.toHaveBeenCalled();
    });
  });
});
```

Key observations:
- `beforeEach` handles the SUT instantiation — identical for all tests.
- Each test's Arrange configures the *specific* mock response for that scenario.
- The failure test combines Act and Assert because `rejects.toThrow` wraps both — the one legitimate exception to the single-Act rule.

**Q7. How do you handle multiple assertions in the Assert phase without violating the "one assertion per test" rule?**
A: "One assertion per test" is a guideline, not a law — and it's often misunderstood. The real principle is **one behaviour under test per test case**. A single behaviour can legitimately produce multiple observable outcomes that all need asserting:

```typescript
it("should return the processed order with correct status, total, and audit timestamp", () => {
  // Arrange
  const items   = [{ sku: "A", qty: 2, price: 500 }];
  const now     = new Date("2024-01-15T10:00:00Z");
  jest.setSystemTime(now);

  // Act
  const order = processOrder({ items, userId: "u1" });

  // Assert — all three are properties of the same behaviour
  expect(order.status).toBe("pending");
  expect(order.total).toBe(1000);
  expect(order.createdAt).toEqual(now);
});
```

The smell to avoid is asserting *unrelated* behaviours in one test — e.g., asserting the return value AND that an unrelated cache was updated AND that a Slack notification was sent. That's three tests masquerading as one.

When you find yourself writing `// Assert part 1` and `// Assert part 2` for clearly different outcomes, split the test. When all assertions describe facets of the same observable result, keep them together.

**Q8. How do you test a function that has randomness or time dependency using AAA?**
A: Both randomness and time are external dependencies — make them injectable or mockable so Arrange can control them:

```typescript
// ❌ Untestable — directly calls Date.now()
function generateTransactionId(): string {
  return `txn_${Date.now()}_${Math.random().toString(36).slice(2)}`;
}

// ✅ Testable — clock and random are injected
function generateTransactionId(
  clock:  () => number = Date.now,
  random: () => number = Math.random,
): string {
  return `txn_${clock()}_${random().toString(36).slice(2)}`;
}

// Test:
it("should generate a transaction ID with the current timestamp", () => {
  // Arrange
  const fixedTime   = 1705312800000;
  const fixedRandom = 0.123456789;
  const clock       = () => fixedTime;
  const random      = () => fixedRandom;

  // Act
  const txnId = generateTransactionId(clock, random);

  // Assert
  expect(txnId).toBe(`txn_${fixedTime}_${fixedRandom.toString(36).slice(2)}`);
});
```

Alternative: Jest's `jest.useFakeTimers()` and `jest.setSystemTime()` for `Date`-based code you can't refactor. For `Math.random`, `jest.spyOn(Math, "random").mockReturnValue(0.5)` works. The principle: **Arrange must have full control over anything non-deterministic; the SUT must never reach out and grab global state directly.**

**Q9. How do you apply AAA when testing error handling paths?**
A: Error path tests follow the same structure — the Arrange sets up the condition that causes the error, Act invokes the SUT, Assert verifies the error type, message, and any side effects (e.g., that a rollback was called):

```typescript
it("should throw InsufficientFundsError with the shortfall amount when balance is too low", async () => {
  // Arrange
  const accountRepo = {
    findById: jest.fn().mockResolvedValue({ id: "acc1", balance: 200 }),
  } as jest.Mocked<AccountRepository>;
  const service = new WithdrawalService(accountRepo);

  // Act + Assert (async throw pattern)
  await expect(
    service.withdraw({ accountId: "acc1", amount: 500 })
  ).rejects.toThrow(
    expect.objectContaining({
      name:      "InsufficientFundsError",
      shortfall: 300,   // 500 - 200
    })
  );
});
```

Two patterns for asserting throws:
- **Async:** `await expect(asyncFn()).rejects.toThrow(ErrorClass)` — the cleanest form; Act and Assert are one expression.
- **Sync:** Wrap in `expect(() => syncFn()).toThrow(ErrorClass)` — same pattern for synchronous throws.

Avoid the try/catch pattern in tests:
```typescript
// ❌ Fragile — if the function doesn't throw, the test passes silently
try {
  await service.withdraw({ accountId: "acc1", amount: 500 });
} catch (err) {
  expect(err).toBeInstanceOf(InsufficientFundsError);
}
```
If the throw doesn't happen, the `expect` is never reached and the test passes — a false positive. Always use Jest's `.rejects.toThrow()` or `.toThrow()` wrappers.

**Q10. What is a test fixture, and how does it fit into the Arrange phase?**
A: A fixture is a pre-built piece of test data — an object, record, or state — that represents a valid, realistic entity without requiring the test to construct every field from scratch. Fixtures reduce noise in the Arrange phase by establishing defaults while letting each test override only what's relevant to its scenario:

```typescript
// fixtures/user.fixture.ts
export function buildUser(overrides: Partial<User> = {}): User {
  return {
    id:        "user-001",
    name:      "Test User",
    email:     "test@example.com",
    tier:      "standard",
    kycStatus: "verified",
    createdAt: new Date("2024-01-01"),
    ...overrides,   // test-specific overrides applied last
  };
}

// In a test:
it("should apply premium discount for premium-tier users", () => {
  // Arrange — only override what this test cares about
  const user    = buildUser({ tier: "premium" });
  const product = { id: "p1", basePrice: 1000 };

  // Act
  const price = calculatePrice(product, user);

  // Assert
  expect(price).toBe(800);
});
```

The fixture pattern keeps Arrange focused on the *differentiating factor* of each test case rather than boilerplate object construction. The reader immediately sees: "this test is about premium-tier behaviour" — not buried in a wall of object literals.

## Section 3: AAA in Integration Tests

**Q11. How does AAA apply to integration tests that involve a real database?**
A: The structure is identical but the Arrange phase expands significantly — it must seed the DB with the exact state the test assumes, and cleanup must happen after to avoid cross-test contamination:

```typescript
// Using Jest + TypeORM + a test PostgreSQL instance
describe("LedgerRepository (integration)", () => {
  let dataSource: DataSource;
  let repo:       LedgerRepository;

  beforeAll(async () => {
    // One-time: connect to the test DB
    dataSource = await createTestDataSource();
    repo       = new LedgerRepository(dataSource);
  });

  afterAll(async () => {
    await dataSource.destroy();
  });

  beforeEach(async () => {
    // Shared: wipe the table before each test for isolation
    await dataSource.getRepository(LedgerEntry).delete({});
  });

  it("should persist a ledger entry and retrieve it by transaction ID", async () => {
    // Arrange — seed specific data for this test
    const entry: CreateLedgerEntryDto = {
      txnId:  "txn_001",
      userId: "u1",
      amount: 5000,
      type:   "debit",
    };

    // Act
    await repo.record(entry);

    // Assert — query the DB directly, not via the repo under test
    const raw = await dataSource
      .getRepository(LedgerEntry)
      .findOne({ where: { txnId: "txn_001" } });

    expect(raw).toBeDefined();
    expect(raw!.amount).toBe(5000);
    expect(raw!.type).toBe("debit");
  });
});
```

Key integration-test AAA rules:
- **Assert against raw DB state**, not the repo's own find methods — otherwise you're testing the read path with the write path, which masks bugs in both.
- **Truncate between tests** (`DELETE` or `TRUNCATE`) — not between suites. Each test must be an independent slice of reality.
- **Use a dedicated test DB** — never run integration tests against staging or production data.

**Q12. How do you apply AAA to HTTP-level integration tests using Supertest in NestJS?**
A:

```typescript
// src/payments/payment.controller.integration.spec.ts
describe("POST /v1/payments (integration)", () => {
  let app:          INestApplication;
  let dataSource:   DataSource;
  let gatewayStub:  jest.Mocked<GatewayClient>;

  beforeAll(async () => {
    gatewayStub = { charge: jest.fn() } as jest.Mocked<GatewayClient>;

    const module = await Test.createTestingModule({
      imports: [AppModule],
    })
      .overrideProvider(GatewayClient)
      .useValue(gatewayStub)           // stub the external gateway; real DB
      .compile();

    app = module.createNestApplication();
    app.useGlobalPipes(new ValidationPipe());
    await app.init();

    dataSource = module.get(DataSource);
  });

  afterAll(async () => {
    await app.close();
  });

  beforeEach(async () => {
    await dataSource.getRepository(LedgerEntry).delete({});
    jest.clearAllMocks();
  });

  it("should return 201 and persist the ledger entry when the gateway succeeds", async () => {
    // Arrange
    const payload = { userId: "u1", amount: 5000, currency: "INR" };
    gatewayStub.charge.mockResolvedValue({ status: "success", txnId: "txn_xyz" });

    // Act
    const response = await request(app.getHttpServer())
      .post("/v1/payments")
      .send(payload)
      .set("Authorization", "Bearer test-token");

    // Assert — HTTP response
    expect(response.status).toBe(201);
    expect(response.body).toMatchObject({ txnId: "txn_xyz", status: "completed" });

    // Assert — DB side effect (the behaviour extends beyond the HTTP response)
    const entry = await dataSource
      .getRepository(LedgerEntry)
      .findOne({ where: { txnId: "txn_xyz" } });
    expect(entry).toBeDefined();
    expect(entry!.amount).toBe(5000);
  });

  it("should return 422 and not persist anything when the gateway declines", async () => {
    // Arrange
    const payload = { userId: "u1", amount: 5000, currency: "INR" };
    gatewayStub.charge.mockResolvedValue({ status: "failed", reason: "card_declined" });

    // Act
    const response = await request(app.getHttpServer())
      .post("/v1/payments")
      .send(payload)
      .set("Authorization", "Bearer test-token");

    // Assert — HTTP response
    expect(response.status).toBe(422);

    // Assert — no side effect
    const count = await dataSource.getRepository(LedgerEntry).count();
    expect(count).toBe(0);
  });
});
```

This is the most realistic test layer for a fintech API: the HTTP stack, validation, DI wiring, and DB are all real; only the external gateway is stubbed (because it's not under your control and has costs/side effects in test environments).

**Q13. How do you handle test data dependencies between tests without coupling tests to each other?**
A: The golden rule: **each test must own its data from creation to cleanup**. Tests that read data created by a prior test are implicitly ordered and fail in unpredictable ways when order changes or a prior test fails.

Three patterns:

**Pattern 1 — Create in Arrange, clean in `afterEach`:**
```typescript
afterEach(async () => {
  await dataSource.getRepository(User).delete({ email: Like("testuser_%") });
});

it("should find a user by email", async () => {
  // Arrange — this test owns this user
  const user = await userRepo.create({ email: "testuser_find@example.com", name: "Test" });

  // Act
  const found = await userRepo.findByEmail("testuser_find@example.com");

  // Assert
  expect(found?.id).toBe(user.id);
});
```

**Pattern 2 — Truncate the entire table in `beforeEach`:** Simpler but requires tests not to run in parallel (parallel tests sharing a truncated table race). Use `--runInBand` for DB integration tests.

**Pattern 3 — Use DB transactions that are rolled back per test:**
```typescript
let queryRunner: QueryRunner;

beforeEach(async () => {
  queryRunner = dataSource.createQueryRunner();
  await queryRunner.startTransaction();
});

afterEach(async () => {
  await queryRunner.rollbackTransaction(); // all writes vanish
  await queryRunner.release();
});
```
The most elegant approach: each test runs inside a transaction that's always rolled back — zero cleanup code, perfect isolation, fast (no actual deletes). The constraint: the SUT must accept or use the same queryRunner (requires dependency injection of the transaction context).

## Section 4: AAA Anti-Patterns

**Q14. What is a "mystery guest," and how does it violate AAA?**
A: A mystery guest is when a test depends on external state — a file, a DB record, a global variable, an environment variable — that isn't set up in the test's own Arrange phase. The test passes in one environment and fails in another with no obvious explanation:

```typescript
// ❌ Mystery guest — relies on a DB record seeded by a migration or another test
it("should return the default tax rate for INR", async () => {
  // No Arrange — assumes a "TAX_RATE_INR" config record already exists in the DB

  // Act
  const rate = await configService.getTaxRate("INR");

  // Assert
  expect(rate).toBe(0.18);
});
```

The fix: make the dependency explicit in Arrange:
```typescript
it("should return the default tax rate for INR", async () => {
  // Arrange — this test owns its data
  await configRepo.upsert({ key: "TAX_RATE_INR", value: "0.18" });

  // Act
  const rate = await configService.getTaxRate("INR");

  // Assert
  expect(rate).toBe(0.18);
});
```

**Q15. What is an "eager test" (or "overspecified test"), and how does it hurt maintainability?**
A: An eager test asserts more than it needs to — it specifies implementation details in the Assert phase that have nothing to do with the behaviour under test. The most common form is excessive interaction-based assertions:

```typescript
// ❌ Overspecified — asserts internal call count and argument structure
it("should send a welcome email on user registration", async () => {
  const payload = { email: "new@example.com", name: "Alice" };

  await registrationService.register(payload);

  // Over-assertion: the number of internal helper calls is not the behaviour
  expect(emailService.buildTemplate).toHaveBeenCalledTimes(1);
  expect(emailService.buildTemplate).toHaveBeenCalledWith("welcome", { name: "Alice" });
  expect(emailService.send).toHaveBeenCalledTimes(1);
  expect(emailService.send).toHaveBeenCalledWith({
    to:      "new@example.com",
    subject: "Welcome to the platform",
    body:    expect.any(String),
  });
  expect(logger.info).toHaveBeenCalledWith("Registration complete", { email: "new@example.com" });
});

// ✅ Right-sized — asserts the externally observable behaviour
it("should send a welcome email on user registration", async () => {
  const payload = { email: "new@example.com", name: "Alice" };

  await registrationService.register(payload);

  expect(emailService.send).toHaveBeenCalledWith(
    expect.objectContaining({ to: "new@example.com" })
  );
});
```

The overspecified test breaks every time you rename a private method, change the logging format, or refactor the template-building logic — even if the observable behaviour (a welcome email is sent to the right address) is unchanged.

**Q16. What is the "assertion roulette" anti-pattern?**
A: Assertion roulette occurs when a test has many assertions with no labels, and a failure message gives no indication of *which* assertion failed or *why* it matters:

```typescript
// ❌ Assertion roulette — failure says "expected false to be true" with no context
it("should process the order correctly", () => {
  const order = processOrder(payload);

  expect(order.status === "pending").toBe(true);
  expect(order.total > 0).toBe(true);
  expect(order.items.length).toBe(2);
  expect(order.createdAt instanceof Date).toBe(true);
});

// ✅ Use Jest matchers — failure messages are self-documenting
it("should process the order correctly", () => {
  const order = processOrder(payload);

  expect(order.status).toBe("pending");           // "expected 'cancelled' to be 'pending'"
  expect(order.total).toBeGreaterThan(0);          // "expected 0 to be greater than 0"
  expect(order.items).toHaveLength(2);             // "expected array of length 1 to have length 2"
  expect(order.createdAt).toBeInstanceOf(Date);    // "expected null to be an instance of Date"
});
```

The fix is two-fold: use rich Jest matchers (`.toBe`, `.toEqual`, `.toHaveLength`, `.toBeInstanceOf`) that generate descriptive failure messages, and add custom messages where the assertion's purpose isn't self-evident: `expect(order.total).toBeGreaterThan(0, "order total must be positive after applying discounts")`.

**Q17. What is "test logic in tests," and why is it dangerous?**
A: Test logic in tests means putting conditional branches, loops, or computed expected values *inside* the test body. Tests that contain logic need to be tested themselves — it's turtles all the way down:

```typescript
// ❌ Test logic — if the logic is wrong, the test always passes
it("should apply tier-based discounts correctly", () => {
  const tiers = ["standard", "premium", "vip"];

  for (const tier of tiers) {
    const user    = buildUser({ tier });
    const product = { basePrice: 1000 };
    const price   = calculatePrice(product, user);
    // Computing the expected value with the same logic as the SUT — always matches
    const expected = tier === "premium" ? 800 : tier === "vip" ? 700 : 1000;
    expect(price).toBe(expected);
  }
});

// ✅ Explicit, table-driven — each case is a row with literal expected values
it.each([
  { tier: "standard", basePrice: 1000, expected: 1000 },
  { tier: "premium",  basePrice: 1000, expected: 800  },
  { tier: "vip",      basePrice: 1000, expected: 700  },
])("should return $expected for a $tier user on a $basePrice product", ({ tier, basePrice, expected }) => {
  // Arrange
  const user    = buildUser({ tier });
  const product = { basePrice };

  // Act
  const price = calculatePrice(product, user);

  // Assert
  expect(price).toBe(expected);
});
```

`it.each` (or `describe.each`) gives you parametrized tests without logic: each row is an independent test case with its own result in the test runner output.

**Q18. What is "slow Arrange" and how does it damage the test suite?**
A: Slow Arrange is when the setup phase does real I/O, makes real network calls, or runs expensive computations that belong to the Act phase. Common culprits:

- **Calling the real external API in Arrange** to get a fixture token (instead of using a fixed test token or mocking the auth service).
- **Seeding 10,000 DB rows** to test a pagination edge case (instead of seeding exactly the boundary: 11 rows if page size is 10).
- **Running a full data migration** as Arrange for a migration test (instead of testing the migration function directly with a minimal schema fixture).

Slow Arrange compounds across a test suite: 100 tests × 500ms Arrange = 50 seconds just in setup. The fix is to keep Arrange as lightweight as possible — mock external calls, seed only the minimum data required, and use in-memory fakes where I/O isn't what's being tested.

## Section 5: AAA in Specific Testing Contexts

**Q19. How do you apply AAA to testing NestJS Guards and Interceptors?**
A: Guards and Interceptors wrap request handling — test them by constructing a minimal `ExecutionContext` mock rather than spinning up the full HTTP stack:

```typescript
// src/auth/jwt-auth.guard.spec.ts
describe("JwtAuthGuard", () => {
  let guard:         JwtAuthGuard;
  let jwtService:    jest.Mocked<JwtService>;

  beforeEach(() => {
    jwtService = { verify: jest.fn() } as jest.Mocked<JwtService>;
    guard      = new JwtAuthGuard(jwtService);
  });

  function buildContext(token: string | null): ExecutionContext {
    return {
      switchToHttp: () => ({
        getRequest: () => ({
          headers: token ? { authorization: `Bearer ${token}` } : {},
        }),
      }),
    } as ExecutionContext;
  }

  it("should allow the request and attach the user payload when the token is valid", () => {
    // Arrange
    const payload = { sub: "u1", email: "user@example.com" };
    jwtService.verify.mockReturnValue(payload);
    const context = buildContext("valid.jwt.token");

    // Act
    const canActivate = guard.canActivate(context);

    // Assert
    expect(canActivate).toBe(true);
    expect(context.switchToHttp().getRequest().user).toEqual(payload);
  });

  it("should throw UnauthorizedException when the token is missing", () => {
    // Arrange
    const context = buildContext(null);

    // Act & Assert
    expect(() => guard.canActivate(context)).toThrow(UnauthorizedException);
  });
});
```

**Q20. How do you apply AAA to testing event-driven / async workflows (e.g., BullMQ job processors)?**
A: Queue job processors are plain functions — test the processor directly with a mock job object, without a real queue:

```typescript
// src/jobs/mandate-processor.spec.ts
describe("MandateProcessor", () => {
  let processor:   MandateProcessor;
  let nachClient:  jest.Mocked<NachApiClient>;
  let mandateRepo: jest.Mocked<MandateRepository>;

  beforeEach(() => {
    nachClient  = { submitDebit: jest.fn() } as jest.Mocked<NachApiClient>;
    mandateRepo = { updateStatus: jest.fn() } as jest.Mocked<MandateRepository>;
    processor   = new MandateProcessor(nachClient, mandateRepo);
  });

  it("should submit the debit and mark the mandate as processed on success", async () => {
    // Arrange
    const job = {
      data: { mandateId: "m1", accountNumber: "1234567890", amount: 2500 },
      id:   "job-001",
    } as Job<MandateJobData>;

    nachClient.submitDebit.mockResolvedValue({ ackId: "ack_xyz", status: "accepted" });

    // Act
    await processor.process(job);

    // Assert
    expect(nachClient.submitDebit).toHaveBeenCalledWith({
      accountNumber: "1234567890",
      amount:        2500,
    });
    expect(mandateRepo.updateStatus).toHaveBeenCalledWith("m1", "processed", { ackId: "ack_xyz" });
  });

  it("should mark the mandate as failed when the NACH API returns an error", async () => {
    // Arrange
    const job = {
      data: { mandateId: "m1", accountNumber: "1234567890", amount: 2500 },
    } as Job<MandateJobData>;
    nachClient.submitDebit.mockRejectedValue(new NachApiError("bank_unavailable"));

    // Act & Assert
    await expect(processor.process(job)).rejects.toThrow(NachApiError);
    expect(mandateRepo.updateStatus).toHaveBeenCalledWith("m1", "failed", expect.any(Object));
  });
});
```

**Q21. How do you apply AAA to testing database repository methods with query complexity (e.g., complex JOINs, aggregations)?**
A: For complex query logic, unit tests with mocked DB clients are insufficient — the query itself is what needs verification. Use a real test DB:

```typescript
describe("LedgerRepository.getMonthlyStatement (integration)", () => {
  let repo:       LedgerRepository;
  let dataSource: DataSource;

  beforeAll(async () => {
    dataSource = await createTestDataSource();
    repo       = new LedgerRepository(dataSource);
  });

  afterAll(() => dataSource.destroy());
  beforeEach(() => dataSource.getRepository(LedgerEntry).delete({}));

  it("should return summed debits and credits grouped by day for the given month", async () => {
    // Arrange — seed exactly the entries needed to exercise the aggregation
    await dataSource.getRepository(LedgerEntry).save([
      { userId: "u1", type: "debit",  amount: 1000, date: new Date("2024-01-10") },
      { userId: "u1", type: "debit",  amount: 500,  date: new Date("2024-01-10") },
      { userId: "u1", type: "credit", amount: 2000, date: new Date("2024-01-15") },
      { userId: "u2", type: "debit",  amount: 999,  date: new Date("2024-01-10") }, // different user — must be excluded
    ]);

    // Act
    const statement = await repo.getMonthlyStatement("u1", 2024, 1);

    // Assert
    expect(statement).toEqual([
      { date: "2024-01-10", totalDebit: 1500, totalCredit: 0    },
      { date: "2024-01-15", totalDebit: 0,    totalCredit: 2000 },
    ]);
  });
});
```

The seed data is *minimal and intentional*: two debit entries on the same day test aggregation, one credit on a different day tests multi-row output, one entry for a different user tests the `WHERE userId =` filter. Every row has a purpose — that's the hallmark of well-written Arrange.

## Section 6: Scenario / System Design Style Questions

**Q22. "You're reviewing a PR where a junior engineer has written tests that all pass but the team keeps discovering production bugs in the same module. What do you look for in the tests?"**
A: A structured review checklist:

**1. Are tests testing the real thing?** — Check if the SUT is over-mocked. If `paymentService.processPayment` is mocked inside a test *of* `paymentService`, the test proves nothing. Mocks belong on *dependencies* of the SUT, not on the SUT itself.

**2. Is Arrange representative?** — Are test inputs trivially simple (`amount: 1`, `userId: ""`) when production data is complex (`amount: 999999.99`, Unicode user IDs, INR vs USD amounts)? Happy-path-only Arrange misses the failure modes.

**3. Are assertions shallow?** — `expect(result).toBeDefined()` is almost always useless. Look for assertions that verify the *shape and values* of the result, not just its existence.

**4. Are error paths tested?** — Count the ratio of success-path tests to failure-path tests. For a payment module, there should be tests for: gateway timeout, gateway decline, DB write failure, duplicate transaction, invalid payload. If all tests are sunny-day, that's the gap.

**5. Are side effects asserted?** — If `processPayment` is supposed to send a webhook and record a ledger entry, does the test verify both? Missing side-effect assertions are the most common cause of "tests pass, production breaks."

**6. Is there test isolation?** — Run the tests in random order (`--randomize` in Jest). If any fail, tests are sharing state (mystery guests or missing cleanup in `afterEach`).

**Q23. "You're setting up a test strategy for a new BRE (Business Rules Engine) module that evaluates 15 different rules against an applicant's profile. How do you structure the tests using AAA?"**
A: A BRE with 15 rules has a combinatorial space — the testing strategy has three layers:

**Layer 1 — Unit tests per rule (pure function tests):**
Each rule is a function `(applicantProfile) => { passed: boolean, reason?: string }`. Test each in isolation with `it.each` covering: clearly passing input, clearly failing input, boundary values, and null/missing fields.

```typescript
describe("PanVerificationRule", () => {
  it.each([
    { panStatus: "verified",    kyc: "complete", expected: true  },
    { panStatus: "unverified",  kyc: "complete", expected: false },
    { panStatus: "verified",    kyc: "pending",  expected: false },
    { panStatus: null,          kyc: "complete", expected: false },
  ])("should return $expected for panStatus=$panStatus kyc=$kyc", ({ panStatus, kyc, expected }) => {
    // Arrange
    const profile = buildApplicantProfile({ panStatus, kycStatus: kyc });

    // Act
    const result = panVerificationRule(profile);

    // Assert
    expect(result.passed).toBe(expected);
  });
});
```

**Layer 2 — Integration tests for the rule engine orchestration:**
Test that the engine evaluates all 15 rules and aggregates results correctly — don't re-test each rule's logic here, just the composition:

```typescript
it("should reject the application if any rule fails, and list all failing rules", () => {
  // Arrange — a profile that fails exactly 2 of 15 rules
  const profile = buildApplicantProfile({
    panStatus:  "unverified",   // fails PanVerificationRule
    debtRatio:  0.65,           // fails DebtRatioRule (threshold: 0.60)
    // all other fields: valid defaults from buildApplicantProfile
  });

  // Act
  const decision = breEngine.evaluate(profile);

  // Assert
  expect(decision.approved).toBe(false);
  expect(decision.failedRules).toEqual(
    expect.arrayContaining(["PanVerificationRule", "DebtRatioRule"])
  );
  expect(decision.failedRules).toHaveLength(2);
});
```

**Layer 3 — Contract / snapshot tests for rule output format:**
The BRE output is consumed downstream (NACH eligibility, Account Aggregator decisioning). Snapshot test the output shape to catch accidental format changes:

```typescript
it("should produce a decision object matching the documented contract", () => {
  const profile  = buildApplicantProfile(); // all-valid defaults
  const decision = breEngine.evaluate(profile);
  expect(decision).toMatchSnapshot();
});
```

**Q24. "A test suite that used to run in 30 seconds now takes 8 minutes. How do you diagnose and fix it using AAA as a lens?"**
A: AAA phases are where time is spent — diagnose by phase:

**Slow Arrange:**
- Tests making real HTTP calls (to external APIs, auth services) in setup.
- `beforeAll` running DB migrations per suite instead of once globally.
- Fixtures loading large files from disk on every test.
- Fix: mock external calls, run migrations once in a global Jest setup file (`globalSetup`), use in-memory data structures for non-DB tests.

**Slow Act:**
- The SUT itself is slow (not a test problem — a production performance problem surfaced by tests).
- DB integration tests running without indexes on the test DB (test DB schema differs from production schema).
- Fix: ensure test DB schema matches production (run migrations, not manual CREATE TABLE); add `EXPLAIN ANALYZE` to queries taking >10ms in tests.

**Slow Assert:**
- `toMatchSnapshot()` reading from disk on every test (acceptable for a handful; problematic at scale).
- Polling/retry assertions that wait for async state to settle (e.g., `waitFor` with long timeouts).
- Fix: prefer direct async/await over polling; cap `waitFor` timeouts tightly.

**Cross-cutting:**
- Tests not running in parallel because they share DB state (running with `--runInBand`). Fix: isolate test DB state per test (transaction rollback pattern) to enable parallel runs.
- `beforeEach` doing full `DELETE FROM` on large tables. Fix: transaction rollback per test, or scope test data with unique prefixes and delete by prefix.

Profiling command: `jest --verbose --detectOpenHandles --logHeapUsage` — reveals which suites are slowest and whether handles are being left open (a common cause of tests hanging).

## Quick Reference: AAA Checklist

| Phase | Green signal | Red signal |
|---|---|---|
| **Arrange** | Sets up only what this test needs; uses fixtures with minimal overrides; mocks are on dependencies, not the SUT | Calls real external services; seeds unnecessary data; SUT is mocked |
| **Act** | Single method/function call; one line | Multiple sequential calls; loop over multiple inputs |
| **Assert** | Specific values; rich Jest matchers; verifies side effects when relevant | `.toBeDefined()` only; `expect(true).toBe(true)`; silent try/catch |
| **Overall** | Test is readable without context; fails with a clear message; passes in any order; runs fast | Depends on test order; passes when the SUT is broken; takes >1s for a unit test |

---

**Tip for the interview:** At 5 YOE, interviewers don't ask "what does AAA stand for" — they ask you to review a test and explain what's wrong with it, or to write a test for a tricky scenario (async throws, DB side effects, time-dependent logic). The answers that land are the ones that name the anti-pattern precisely (mystery guest, eager test, assertion roulette), explain *why* it causes production bugs (not just why it's stylistically bad), and demonstrate the fix with code. Have a concrete story ready about a production bug that a better-structured test would have caught — that's the framing that resonates at senior level.
