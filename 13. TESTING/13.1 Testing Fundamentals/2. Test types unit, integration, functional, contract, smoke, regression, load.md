# JavaScript / Testing: Test Types — Unit, Integration, Functional, Contract, Smoke, Regression, Load — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why do we categorize tests into types at all?**
A: Different test types answer different questions, operate at different speeds, and catch different failure modes. Conflating them leads to test suites that are slow, fragile, or misleading. Categorizing tests lets you reason about:
- **What** is being verified (a function, a service boundary, a user flow, a contract).
- **How fast** feedback arrives (milliseconds for unit tests, minutes for integration, hours for load).
- **When** they run (every commit, every PR, nightly, pre-release).
- **Who** owns them (developers for unit/integration, QA or a dedicated team for functional/regression).

A well-structured test strategy layers these types intentionally — which is why the **Testing Pyramid** (Mike Cohn) and its variants exist: many fast unit tests at the base, fewer integration tests in the middle, even fewer slow E2E/functional tests at the top.

**Q2. What is the Testing Pyramid, and is it still the right mental model?**
A: The classic pyramid: many unit tests → fewer integration tests → even fewer E2E tests. It was designed to push the cost/speed tradeoff downward — unit tests are cheap and fast; E2E tests are expensive and slow.

In practice, the pyramid has been revised for modern architectures:
- **Microservices** shift weight toward integration and contract tests, because units in isolation say little about cross-service behavior.
- **Frontend-heavy apps** (React/Vue/Angular) benefit from the **Testing Trophy** (Kent C. Dodds): the heaviest layer is integration tests (component + mocked API), not unit tests.
- **API-first backends** may invest heavily in functional/contract tests at the expense of pure unit tests.

The pyramid is still a useful heuristic — faster tests should outnumber slower ones — but the exact proportions depend on the architecture.

**Q3. What is the cost of a test, and how do you think about it?**
A: The cost of a test is not just the time it takes to write — it's the ongoing cost of:
- **Execution time** — slow tests delay CI feedback loops, which delays every merge.
- **Maintenance burden** — brittle tests that break on unrelated refactors cost more than they save.
- **Confidence delivered** — a fast test that doesn't catch real bugs is pure cost with no benefit.
- **Setup/teardown complexity** — tests that require a database, network, or container to run add infrastructure cost.

The goal is maximum confidence per unit of cost. Unit tests have the best ratio for pure logic; contract tests have the best ratio for cross-service trust; load tests have no substitute for capacity validation. Each type earns its place by answering a question no cheaper test can answer.

## Section 2: Unit Tests

**Q4. What is a unit test?**
A: A unit test verifies a single unit of logic — typically a function, method, or class — in complete isolation from its dependencies. All external dependencies (databases, network, file system, other modules) are replaced with test doubles (mocks, stubs, spies, or fakes). Unit tests are:
- **Fast** — milliseconds per test; thousands run in seconds.
- **Deterministic** — no network, no clock drift, no external state.
- **Narrowly scoped** — a failure points directly at the unit under test.

**Q5. What is the difference between a mock, stub, spy, and fake?**
A: These terms are often conflated; the canonical definitions (from Gerard Meszaros' *xUnit Test Patterns*):
- **Stub** — returns pre-configured responses to calls; doesn't record how it was called. Used to control the dependency's output.
  ```js
  const getUserStub = jest.fn().mockResolvedValue({ id: 1, name: "Alice" });
  ```
- **Mock** — a stub that also verifies interactions: how many times it was called, with what arguments. The test *asserts* on the mock's call history.
  ```js
  expect(getUserMock).toHaveBeenCalledWith(1);
  ```
- **Spy** — wraps the *real* implementation but records calls. Unlike a mock, the real code runs.
  ```js
  const spy = jest.spyOn(mailer, "send");
  // mailer.send actually executes; you just observe it
  ```
- **Fake** — a simplified but working implementation of a dependency (e.g., an in-memory database instead of PostgreSQL). Heavier than a stub but more realistic.

**Q6. What makes a unit test bad?**
A: Common anti-patterns:
- **Testing implementation, not behavior** — asserting internal state or which private methods were called; breaks on refactor even when behavior is unchanged.
- **Too many mocks** — if you're mocking 6 things to test one function, the unit is doing too much; that's a design signal.
- **Non-determinism** — using `Date.now()`, `Math.random()`, or timers without mocking them; the test becomes a flaky test.
- **Testing the framework** — verifying that Jest or a library works as advertised, rather than your own logic.
- **One test per method** — writing tests to cover lines rather than behaviors; misses edge cases and over-specifies implementation.

**Q7. What is the "Arrange, Act, Assert" (AAA) pattern?**
A: A structure for writing readable, maintainable unit tests:
```js
test("calculates discounted price correctly", () => {
  // Arrange — set up inputs and dependencies
  const product = { price: 100 };
  const discountRate = 0.2;

  // Act — invoke the unit under test
  const result = applyDiscount(product, discountRate);

  // Assert — verify the outcome
  expect(result.price).toBe(80);
});
```
Each section should be visually distinct. If the "Arrange" section is enormous, the function under test likely has too many dependencies — another design signal.

**Q8. When should you *not* write a unit test?**
A: Unit tests are weakest when:
- The code is mostly **glue** — wiring up framework components with little logic of its own (an Express router that just calls a controller; a React component that renders props without transformation).
- The **behavior only emerges from integration** — e.g., a database query's behavior under specific index conditions can't be unit-tested with a fake.
- The **logic is trivial** — a one-line getter that returns a property; the test adds maintenance cost with near-zero confidence gain.
- The code is **likely to change** — testing a prototype or a feature under active design churn creates tests that break before they've proven their value.

## Section 3: Integration Tests

**Q9. What is an integration test?**
A: An integration test verifies that two or more components work correctly *together* — with real (or near-real) dependencies rather than mocks. The goal is catching issues that unit tests can't: network protocol mismatches, database schema drift, serialization bugs at boundaries, and middleware interaction failures.

Typical integration test scope examples:
- A service layer talking to a real (test) database.
- An Express route handler processing a real HTTP request (using `supertest`).
- A message queue consumer handling a real message from a test broker.

**Q10. How do you write an integration test for an Express endpoint in Node.js?**
A:
```js
import request from "supertest";
import app from "../app.js";
import db from "../db.js";

beforeAll(async () => {
  await db.migrate.latest();   // real migrations on a test DB
  await db.seed.run();
});

afterAll(async () => {
  await db.destroy();
});

test("GET /users/:id returns the correct user", async () => {
  const res = await request(app).get("/users/1");

  expect(res.status).toBe(200);
  expect(res.body).toMatchObject({ id: 1, name: "Alice" });
});
```
This test exercises the real route handler, middleware chain, service layer, and database — with no mocks. A failure here that doesn't show in unit tests reveals a real integration bug.

**Q11. What is the biggest challenge with integration tests?**
A: **Speed and isolation.** Integration tests are slower (real I/O) and stateful (shared database). Key problems:
- **Test pollution** — test A writes data that test B reads unexpectedly; tests pass in isolation but fail in sequence.
- **Slow feedback** — hundreds of integration tests can take minutes in CI, delaying every merge.
- **Environment dependency** — you need a running database, maybe a Redis instance, maybe a message broker. This adds CI infrastructure complexity.

Mitigations: run each test in a transaction rolled back afterward; use Docker Compose for CI dependencies; parallelize with separate test databases per worker.

**Q12. How do you decide what to integration-test vs unit-test?**
A: A useful rule of thumb: **unit-test the logic, integration-test the seams.**
- If the code makes a decision (branches, transforms, validates), unit-test it.
- If the code crosses a process or network boundary (reads a DB, calls an API, writes a file), integration-test it.
- If you find yourself mocking your ORM's query builder in a unit test, that's a signal to write an integration test instead — the mock gives you false confidence about SQL behavior.

## Section 4: Functional Tests

**Q13. What is a functional test?**
A: A functional test (also called an end-to-end or E2E test) verifies the system from the *user's perspective* — it drives the actual UI or public API through complete user scenarios, with all layers running: frontend, backend, database, external services (or realistic stubs thereof). The question it answers: "Does the system do what the user expects?" rather than "Does this function return the right value?"

```
Browser → Frontend → API → Database → API → Frontend → Browser
         [all real components, no mocks of your own code]
```

**Q14. What are common frameworks for functional/E2E testing in JavaScript?**
A:
- **Playwright** (Microsoft) — modern, cross-browser, supports network interception, excellent for complex SPAs. Preferred choice for new projects.
- **Cypress** — developer-friendly, strong DX, real browser, good for component + E2E testing. Limited to Chromium-based browsers in some configurations.
- **Selenium / WebdriverIO** — older, language-agnostic, supports all browsers; more verbose and slower than Playwright/Cypress.
- **Puppeteer** — low-level Chromium automation; good for scraping or custom tooling, less ergonomic for test suites.

**Q15. What is a Page Object Model (POM), and why does it matter in functional tests?**
A: POM is a design pattern that abstracts UI interactions into reusable objects, one per page or major UI component. Instead of scattering `page.click("#submit-btn")` across every test:
```js
// Without POM — brittle, duplicated
test("login works", async () => {
  await page.fill("#email", "alice@example.com");
  await page.fill("#password", "secret");
  await page.click("#submit-btn");
});

// With POM — resilient, readable
class LoginPage {
  async login(email, password) {
    await this.page.fill("#email", email);
    await this.page.fill("#password", password);
    await this.page.click("#submit-btn");
  }
}

test("login works", async () => {
  await loginPage.login("alice@example.com", "secret");
});
```
When the `#submit-btn` selector changes, you fix it in one place — not in every test that touches login.

**Q16. What are the main failure modes of functional tests in CI?**
A:
- **Flakiness** — timing-dependent assertions (`waitForTimeout(2000)` instead of `waitForSelector`) cause intermittent failures that erode trust in the entire suite.
- **Slow execution** — a suite of 200 E2E tests can take 30–60 minutes serially; this destroys feedback loop velocity.
- **Environment drift** — tests that pass locally fail in CI because of Docker networking differences, missing seed data, or different browser versions.
- **Cascading failures** — a single seed data bug causes 50 tests to fail; root cause is buried under noise.

Mitigations: parallelize across browser workers; use deterministic test data setup per test; prefer `waitForSelector`/`waitForResponse` over fixed delays; tag and run a smoke subset on every commit and the full suite nightly.

## Section 5: Contract Tests

**Q17. What is a contract test?**
A: A contract test verifies that a **provider** (a service that exposes an API) and a **consumer** (a service that calls that API) agree on the shape and semantics of their interface — *without* requiring both services to run simultaneously. The "contract" is a formal description of the API expectations (request shape, response shape, status codes, field types) that both sides verify independently.

This is especially critical in microservices where teams deploy independently and can inadvertently break each other's integrations.

**Q18. What is consumer-driven contract testing, and how does Pact implement it?**
A: In **consumer-driven** contract testing, the *consumer* defines the contract — it specifies exactly what it needs from the provider — and the provider verifies it can fulfill those requirements. This inverts the traditional approach (provider publishes docs, consumer hopes for the best).

Pact workflow:
```
1. Consumer writes a Pact test → generates a pact file (JSON contract)
2. Pact file is published to a Pact Broker
3. Provider CI pulls the pact file → runs provider verification tests
4. Both sides get a pass/fail on their CI pipeline
```

```js
// Consumer side (Jest + Pact)
const interaction = {
  uponReceiving: "a request for user 1",
  withRequest: { method: "GET", path: "/users/1" },
  willRespondWith: {
    status: 200,
    body: like({ id: integer(), name: string() }),
  },
};
```
The `like()` and `integer()` matchers mean the contract checks *type and structure*, not exact values — making contracts resilient to test-data variation.

**Q19. How is a contract test different from an integration test?**
A:

| Dimension              | Integration Test                               | Contract Test                                      |
|---                     |---                                             |---                                                 |
| Services required      | Both must be running                           | Each side runs independently                       |
| What it verifies       | Real behavior across the boundary              | Agreement on interface shape                       |
| Speed                  | Slower (real network/DB)                       | Fast (mocked server on consumer side)              |
| Failure localization   | "Something broke at the boundary"              | "The provider changed the response shape"          |
| Best for               | Verifying behavior of a known-good integration | Preventing breaking changes across team boundaries |

Contract tests don't replace integration tests — they complement them. Use contract tests to catch interface drift early; use integration tests to verify the behavior of the integration itself.

**Q20. When would you *not* use contract tests?**
A:
- **Single-team, single-repo monolith** — no cross-team interface to protect; integration tests suffice.
- **Third-party APIs you don't control** — you can't run provider verification against Stripe's CI pipeline. Use integration tests with recorded/replayed responses (VCR-style with tools like `nock` or `msw`).
- **Very stable, versioned internal APIs** — if the provider is versioned and backward-compatible by policy, contract tests may add overhead without proportional value.
- **Rapidly evolving interfaces** — during early design, the contract changes so often that maintaining it adds cost before the interface stabilizes.

## Section 6: Smoke Tests

**Q21. What is a smoke test?**
A: A smoke test is a minimal, fast subset of tests that verifies the most critical paths of a system are functioning after a deployment or environment change. The name comes from hardware testing — you power on a circuit board and check if it smokes (catastrophically fails) before running full diagnostics. In software:
- It does *not* verify correctness in depth.
- It verifies that the system is *alive* and the critical user paths are *reachable*.
- It runs in minutes (or seconds), not hours.

Typical smoke test checks: can the app start? Is the health endpoint responding? Can a user log in? Can a core resource be created and retrieved?

**Q22. When do smoke tests run, and who defines them?**
A:
- **Post-deployment** — immediately after deploying to staging or production, before routing user traffic or removing the previous version.
- **On every commit to `main`** — a fast gate that catches build-breaking changes before the full test suite runs.
- **In canary deployments** — smoke tests run against the canary pod/instance before the rollout proceeds to 100%.
- **In CDK/Terraform pipelines** — after infrastructure changes, smoke tests verify that services are reachable in the new environment.

Ownership: typically defined by the team that owns the deployment pipeline, drawing from the highest-value functional tests. A common pattern is tagging existing E2E or functional tests with `@smoke` and running only that tagged subset in the post-deploy gate.

**Q23. What makes a good smoke test?**
A:
- **Fast** — the entire smoke suite should complete in under 2 minutes; ideally under 60 seconds.
- **Definitive** — a smoke test failure must be an unambiguous "do not proceed" signal; no false positives.
- **Critical path only** — covers the 3–5 flows that, if broken, make the system unusable for most users (login, core resource CRUD, payment, etc.).
- **Environment-independent** — uses stable test accounts and seed data that exist in every environment; never depends on data created by a previous test run.
- **Alerting-integrated** — smoke test failures should page the on-call engineer immediately, not sit in a CI dashboard.

**Q24. How is a smoke test different from a sanity test?**
A: The terms are often used interchangeably, but the distinction when it's drawn:
- **Smoke test** — run after a build/deployment to check "is it basically working?" Broad but shallow — touches many areas minimally.
- **Sanity test** — run after a bug fix or specific change to check "did this fix solve the problem without breaking nearby behavior?" Narrow and targeted — deep in one area.

In modern CI/CD practice, the terms are mostly collapsed: both refer to a fast, focused subset run in a gate before slower, broader test suites.

## Section 7: Regression Tests

**Q25. What is a regression test?**
A: A regression test verifies that a previously working feature has not been broken by a recent change — a new feature, a refactor, a dependency upgrade, or a bug fix. "Regression" means a system going *backward* in quality. Regression tests are not a distinct technical category — they're any existing test (unit, integration, functional) that is run to catch regressions. What defines them is their *purpose*: maintaining the quality floor.

**Q26. How do you build a regression test suite?**
A: Two sources:
1. **Bug-driven regression tests** — every time a bug is found in production, a test is written that would have caught it. The test is added to the suite *before* the fix is written (TDD-style), so it starts red and turns green when the fix lands. This test then guards against that exact bug recurring.
2. **Feature-driven regression tests** — when a feature ships, its acceptance tests become regression tests for all future changes.

The result is a suite that grows with the history of defects — it's effectively a changelog of "things that have gone wrong."

**Q27. What is "test flakiness," and why is it particularly damaging in regression suites?**
A: A flaky test is one that passes and fails non-deterministically without any code change — due to timing dependencies, shared state, network variability, or random data. In regression suites this is especially damaging because:
- **Engineers learn to ignore failures** — "that one always fails sometimes" erodes the entire suite's credibility.
- **Real regressions get missed** — when failures are expected, a real regression blends into the noise and ships to production.
- **CI becomes a ritual, not a gate** — engineers hit "retry" as a workflow instead of investigating failures.

Tracking flakiness with a flake rate metric (failures when no code changed / total runs) and quarantining flaky tests into a separate suite until they're fixed is a necessary discipline in mature teams.

**Q28. How do visual regression tests work, and when do you use them?**
A: Visual regression testing captures screenshots of UI components or pages and pixel-diffs them against a stored baseline. If the diff exceeds a threshold, the test fails:
- **Tools**: Percy (BrowserStack), Chromatic (Storybook), BackstopJS, Playwright's built-in `toHaveScreenshot()`.
- **Use when**: you have a design-critical UI (a data visualization, a checkout flow, a branded marketing page) where layout shifts or style changes would go undetected by behavior-only tests.
- **Tradeoffs**: high maintenance cost (baselines need updating for every intentional UI change); can be noisy (font rendering differences across OS/CI environments cause false positives); valuable primarily for components that carry high visual contract guarantees.

## Section 8: Load Tests

**Q29. What is a load test?**
A: A load test measures a system's behavior — response time, error rate, throughput — under a defined volume of concurrent traffic. Unlike unit or functional tests that verify *correctness*, a load test verifies *performance*: can the system handle the expected number of users? Where does it degrade? What is its capacity ceiling?

Load testing is a superset that includes several sub-types (see ramping patterns): stress tests (push beyond capacity), spike tests (sudden bursts), and soak tests (sustained load over time).

**Q30. What is the difference between load testing and performance testing?**
A: **Performance testing** is the broad category: any test that measures system performance characteristics (speed, scalability, reliability under load). **Load testing** is a specific type within it — applying a defined concurrent user load and measuring the response. Other types under the performance testing umbrella:
- **Stress testing** — find the breaking point by exceeding expected load.
- **Volume testing** — test behavior with large amounts of data (large database tables, large file uploads), not necessarily high concurrency.
- **Scalability testing** — verify that performance improves linearly (or acceptably) as resources (CPU, instances) are added.

**Q31. What are the key metrics in a load test, and why use percentiles instead of averages?**
A: Key metrics:
- **Response time percentiles** — p50 (median), p95, p99, p99.9.
- **Throughput** — requests per second (RPS) successfully processed.
- **Error rate** — percentage of requests returning 4xx/5xx or timing out.
- **Saturation indicators** — CPU, memory, DB connections, thread pool queue depth.

**Why percentiles, not averages:** the average response time masks the tail. If 99% of requests complete in 100ms but 1% take 10 seconds, the average might be 200ms — which looks fine in a dashboard while 1% of your users experience a terrible experience. At 1,000 RPS, that's 10 users per second hitting a 10-second response. p99 and p99.9 surface this directly.

**Q32. Where does load testing fit in the CI/CD pipeline?**
A: Load tests are too slow and infrastructure-intensive to run on every commit. Typical placement:
- **Nightly or weekly** — a full load test suite runs against a staging environment on a schedule.
- **Pre-release gate** — a load test is required to pass before production deployment of a major feature.
- **Post-deploy verification** — a short load test (5–10 minutes at expected peak) runs against production after a deploy, before traffic is fully shifted.
- **Performance regression gate** — a minimal load test (linear ramp, 2 minutes, checks that p99 hasn't regressed by more than 20%) can run on PRs that touch performance-critical code paths.

## Section 9: Pitfalls & Best Practices Across All Types

**Q33. What is the "ice cream cone" anti-pattern?**
A: The inverted testing pyramid — few unit tests, some integration tests, and a massive layer of slow E2E tests at the top. Teams fall into this when:
- Unit testing feels too abstract and they skip it in favor of "real" tests.
- E2E tests are added reactively every time a bug is found, without a thought for what could have caught it lower in the stack.
- The test suite becomes slow, flaky, and expensive to maintain — a "manual testing" layer often sits above the cone, completing the anti-pattern.

**Q34. How do you decide when a test belongs in unit vs integration vs functional?**
A: Apply these questions in order:
1. Does the behavior only emerge from multiple components working together? → Integration or functional.
2. Does it involve a real network call, database, or file system? → Integration.
3. Does it require a running browser or simulate a full user session? → Functional.
4. Does it verify pure logic within a single function or class? → Unit.
5. Is it verifying an interface contract between services? → Contract.
6. Is it a gate on "is the system alive after a deploy?" → Smoke.
7. Is it preventing a previously fixed bug from returning? → Regression.

**Q35. What does "test isolation" mean, and why does it matter across test types?**
A: Test isolation means that each test is independent — it can run in any order, in parallel, and its outcome is not affected by any other test. Without isolation:
- Tests pass in isolation but fail in a specific sequence (order-dependent tests).
- Parallel test runs produce random failures due to shared state.
- A flaky test infects nearby tests with noise.

Isolation techniques by type: unit tests — mock all external dependencies; integration tests — wrap in a transaction and rollback, or use a separate schema per test worker; functional tests — create fresh test data per test and clean up after; load tests — isolate the load environment from production to avoid impacting real users.

## Quick Comparison Table

| Type        | What it verifies                     | Speed       | Dependencies          | Run when               | Primary failure caught                     |
|---          |---                                   |---          |---                    |---                     |---                                         |
| Unit        | Logic in a single function/class     | Very fast   | Mocked                | Every commit           | Logic errors, edge cases                   |
| Integration | Two or more components together      | Medium      | Real (DB, API, queue) | Every commit / PR      | Boundary bugs, schema drift, middleware    |
| Functional  | Full user flow end-to-end            | Slow        | All real              | PR / nightly           | UX regressions, cross-layer failures       |
| Contract    | Interface agreement between services | Fast        | Mocked (per side)     | Every commit           | Breaking API changes across team boundaries|
| Smoke       | Critical paths alive post-deploy     | Very fast   | Real (prod/staging)   | Post-deploy            | Catastrophic deploy failures               |
| Regression  | Previously working feature still works| Varies     | Varies                | Every commit           | Unintentional breakage of existing features|
| Load        | Performance under concurrent traffic | Slow        | Real (load env)       | Nightly / pre-release  | Capacity limits, memory leaks, latency SLA |

---

**Tip for the interview:** At 5 YOE, you won't be asked "what is a unit test?" in isolation — the real questions look like: "your integration test suite takes 45 minutes; how do you fix it?", "a bug shipped that your unit tests didn't catch — what type of test would have caught it?", or "how do you set up a testing strategy for a new microservice?" Know the *tradeoff* between each type — speed, confidence, maintenance cost — and have a concrete story about a time you chose one type over another and why. The ability to reason about the testing pyramid and say "we were ice-cream-coning and here's what we did about it" signals exactly the experience level this question is probing for.
