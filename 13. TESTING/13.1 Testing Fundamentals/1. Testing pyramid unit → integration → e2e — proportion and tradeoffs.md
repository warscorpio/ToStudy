# Testing Pyramid: Unit → Integration → E2E — Proportion & Tradeoffs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the testing pyramid, and what is it trying to communicate?**
A: The testing pyramid (originally described by Mike Cohn) is a mental model for balancing test suite composition. It has three layers:
- **Unit tests** (base — widest layer) — test a single function, class, or module in isolation; fast, numerous, cheap.
- **Integration tests** (middle layer) — test how multiple units collaborate: a service + its DB, an HTTP handler + middleware chain, a queue consumer + its downstream.
- **E2E tests** (apex — narrowest layer) — test the full system from the user's perspective, through a real browser or API client, against a production-like environment.

The pyramid's shape communicates **proportion**: write many unit tests, fewer integration tests, and very few E2E tests. The underlying principle is that lower-layer tests are faster, cheaper to write, easier to maintain, and give more precise failure signals — so you want as much coverage as possible at the lowest layer that can still catch a given class of bug.

**Q2. What is a unit test, precisely? Where do engineers commonly draw the boundary?**
A: A unit test exercises a single "unit" of behavior in complete isolation — all external dependencies (DB, network, filesystem, clock, random) are replaced with test doubles (mocks, stubs, fakes). The definition of "unit" is deliberately fuzzy; the practical boundary is:
- **Narrow unit** — a single function or class; every collaborator is mocked.
- **Sociable unit** (London vs Chicago school debate) — a cluster of closely related classes tested together, as long as no I/O crosses the boundary.

The key property is **speed and determinism**: unit tests must run in milliseconds, with zero external setup, and produce the same result on every machine. Anything that touches a real network socket, real file, or real process clock is no longer a unit test — it's at minimum an integration test.

**Q3. What is an integration test, and what distinguishes it from a unit test?**
A: An integration test verifies that two or more components behave correctly *together* — it crosses at least one real boundary that a unit test mocks out. Typical integration test boundaries:
- Service ↔ real database (running in Docker / Testcontainers)
- HTTP handler ↔ real middleware stack (no mocked request object)
- Message consumer ↔ real broker (Kafka, RabbitMQ in-process or container)
- Two microservices communicating over a real HTTP call (narrow integration) or via a contract test

Integration tests are slower (seconds, not milliseconds), require environment setup, and can fail for environmental reasons (port conflict, network timeout). In exchange, they catch a class of bugs that no amount of unit testing can find: SQL query syntax errors, ORM misconfiguration, serialization mismatches, and middleware ordering bugs.

**Q4. What is an E2E test, and what makes it uniquely valuable and uniquely painful?**
A: An E2E test drives the entire system as a real user would — typically via a browser automation tool (Playwright, Cypress) or an API client — against a fully deployed, production-like environment. It validates that all the layers (frontend, API gateway, services, databases, third-party integrations) work together to produce the right user-visible outcome.

Unique value: only E2E tests can catch bugs that arise from the *composition* of all layers — a correct frontend + a correct API + a correct DB that nonetheless produce a broken user flow because of an undocumented contract between them.

Unique pain: they are slow (seconds to minutes per test), flaky (timing-dependent DOM interactions, network races, test data pollution), expensive to maintain (UI changes break selectors), and when they fail, the failure message ("button not found") is far from the root cause. A failing E2E test tells you *something* is broken but rarely *what* or *where*.

**Q5. What is the practical proportion guideline for the testing pyramid?**
A: There's no universal ratio, but a commonly cited guideline is roughly **70% unit / 20% integration / 10% E2E** — often simplified to "lots, some, few." The real principle is that each layer should have *only the tests that layer is uniquely suited to catch* — no more, no less:
- Unit: logic, edge cases, error handling, branching — anything that doesn't require real infrastructure.
- Integration: schema correctness, query behavior, middleware contracts, message serialization.
- E2E: critical user journeys (login, checkout, onboarding) — high-value flows, not exhaustive coverage.

The anti-pattern is an inverted pyramid (ice cream cone): a thin unit layer, a thin integration layer, and a massive E2E suite that takes 45 minutes to run. This is common in legacy codebases and indicates that the team historically reached for the highest-confidence (but highest-cost) tool instead of pushing tests down to the lowest appropriate layer.

## Section 2: Unit Tests In Depth

**Q6. What is the difference between a mock, a stub, a spy, and a fake?**
A: These are all "test doubles" (Gerard Meszaros's term), but they serve different purposes:

| Double | What it does | When to use it |
|--|--|--|
| **Stub** | Returns a canned response; no assertions about how it was called | You need a collaborator to return a value so the unit under test can proceed |
| **Mock** | A stub that also *asserts* it was called in a specific way (method, args, times) | You want to verify a side effect — e.g., that an email was sent with specific args |
| **Spy** | Wraps the real implementation but records calls for later assertion | You want real behavior *and* call verification; common with `jest.spyOn` |
| **Fake** | A lightweight real implementation (in-memory DB, fake mailer) | Stubs are too brittle; you want real logic without real infrastructure |

Over-mocking is a common mistake: when a test mocks every collaborator, it's really testing the mock configuration, not the unit. Prefer stubs for inputs and fakes for infrastructure; reserve mocks for deliberate interaction assertions.

**Q7. What makes a unit test "good"? What are the FIRST properties?**
A: The FIRST acronym:
- **Fast** — runs in milliseconds. A slow unit test signals hidden I/O.
- **Independent** — tests don't share state; any test can run in isolation or in any order.
- **Repeatable** — same result every run, every environment (no `Date.now()`, `Math.random()`, or network calls).
- **Self-validating** — the test itself contains the assertion; no human inspection required.
- **Timely** — written at the same time as the code (ideally TDD), not months later when the implementation details are forgotten.

At the 5 YOE level the most commonly violated property is **Independent** — test files that share a module-level singleton (a cache, a DB pool, a config object) and produce different results depending on which test runs first.

**Q8. When is it correct to *not* write a unit test?**
A: Several cases:
- **Pure glue code** — a one-line function that delegates entirely to a library. Testing it only tests the library.
- **Config and wiring** — dependency injection setup, module registration. Better caught by an integration test that boots the actual application.
- **Trivial getters/setters** — if there's no logic, there's nothing to assert.
- **Code under active refactoring** — unit tests coupled to implementation details slow refactors. During a rewrite, keep integration/E2E coverage, delete brittle unit tests, and re-add unit tests once the new shape stabilizes.

The key question is: *does this test give me information I can't get from a lower-cost alternative, or protect against a real regression?* If no, skip it.

## Section 3: Integration Tests In Depth

**Q9. How do you run integration tests against a real database without polluting shared state?**
A: Several strategies, from simple to robust:

- **Transaction rollback per test** — wrap each test in a DB transaction, run the test, then roll back. Fast and clean. Limitation: doesn't work for tests that assert on committed state, or that span multiple transactions (e.g., read-after-write across connections).
- **Truncate between tests** — after each test, `TRUNCATE` all tables. Slower than rollback but works for multi-connection tests. Can be parallelized if each test gets a separate DB schema.
- **Separate DB per test suite** — each test file gets its own ephemeral DB created at suite start and dropped at suite end. Enables parallelism; requires a fast DB provisioning mechanism (Testcontainers, a local Postgres in Docker).
- **Testcontainers** — spin up a real DB (Postgres, MySQL, Redis) in Docker per test run, programmatically, from within the test process. Guarantees environment parity; the DB is identical to production's version/config. Slower to start (~5–10s) but amortized across the suite.

**Q10. What is a contract test, and where does it sit in the testing pyramid?**
A: A contract test verifies that two services (a consumer and a provider) agree on the shape and semantics of their shared interface — without requiring both to be running simultaneously. It sits between integration and E2E in the pyramid:
- The **consumer** writes tests that record what it expects from the provider (the "contract" — specific request/response shapes).
- The **provider** runs those recorded contracts against its own real implementation and verifies it satisfies them.

Tools: **Pact** (consumer-driven), **Spring Cloud Contract**. Contract tests are especially valuable in microservice architectures where E2E tests are expensive and integration tests can't span team boundaries. They catch breaking API changes before deployment, not after.

**Q11. What is the difference between a narrow integration test and a broad integration test?**
A:
- **Narrow integration test** — tests the integration between one service and one dependency in isolation; everything else is mocked. Example: test your repository class against a real Postgres container, but mock the HTTP layer and the service calling the repository. Fast (only one real boundary), precise failure signal.
- **Broad integration test** — tests multiple services and dependencies together; closer to E2E but without a real browser. Example: boot your API, its DB, its Redis cache, and a stubbed third-party service; drive it via HTTP. Slower, more setup, but catches cross-service contract bugs.

The pyramid recommends preferring narrow over broad. Broad integration tests often become a maintenance burden as complex test harnesses grow and flakiness accumulates — many of their benefits can be achieved with contract tests + narrow integration tests at lower cost.

## Section 4: E2E Tests In Depth

**Q12. What is test flakiness, and why are E2E tests disproportionately prone to it?**
A: A flaky test is one that sometimes passes and sometimes fails without any code change — non-deterministic. E2E tests are flaky-prone because:
- **Timing** — browser rendering, animations, network round trips, and async state updates have variable latency. A `click()` on a button before it's fully interactive causes false failures.
- **Test data pollution** — a previous test leaves dirty state in the DB, causing the next test to see unexpected data.
- **Shared environment** — parallel test runs mutate the same records (same user account, same product ID) and interfere.
- **Third-party instability** — real payment providers, email services, or SSO providers that the E2E test calls can be unavailable.
- **DOM selector fragility** — a CSS class or element ID changes in a UI refactor, breaking every test that selected on it.

Mitigations: use `data-testid` attributes (decoupled from styling), wait for explicit conditions (`waitForSelector`, not `sleep(500)`), isolate test data per run (unique email per test), and stub third-party services at the network level (Playwright's route interception).

**Q13. What is the "testing trophy" alternative to the pyramid, and when does it make sense?**
A: Kent C. Dodds proposed the testing trophy for frontend-heavy stacks:
- A small foundation of **static analysis** (TypeScript, ESLint) — not tests but catches a class of bugs for free.
- A thin layer of **unit tests** — only for complex pure logic (parsers, formatters, reducers).
- A wide **integration test** layer (the trophy's middle bulk) — using tools like React Testing Library that test components at the user-interaction level without a real browser.
- A thin **E2E layer** for critical flows.

The trophy inverts the pyramid's unit/integration proportion. It makes sense when: your "unit" is a UI component (testing it in isolation with all dependencies mocked produces fragile, implementation-coupled tests), and React Testing Library allows you to test the component's user-visible behavior with minimal mocking at near-unit-test speed. For pure backend services, the classic pyramid proportion still applies.

**Q14. How do you decide which user flows deserve E2E test coverage?**
A: Apply a risk-weighted cost/benefit filter:
- **High business value + high change frequency** — core flows (login, signup, checkout, core CRUD) are the best candidates. They break often enough and matter enough to justify E2E cost.
- **High business value + low change frequency** — consider E2E for peace of mind on critical paths (payment processing, auth tokens), but don't add more E2E tests than you can maintain.
- **Low business value** — no E2E, regardless of change frequency. Cover with unit/integration instead.
- **Flows that exercise third-party integrations** — stub the third party at the network layer; don't run real payment charges or send real emails in E2E.

A useful heuristic: if a bug in this flow would wake someone up at 2am, it deserves an E2E test. If it would generate a support ticket that can wait until morning, it probably doesn't.

## Section 5: Tradeoffs, Anti-patterns & Best Practices

**Q15. What are the three axes on which unit, integration, and E2E tests differ?**
A: Confidence, speed, and precision — and they trade off against each other:

| Axis           | Unit                              | Integration                       | E2E                                  |
|--              |--                                 |--                                  |--                                    |
| **Confidence** | Low-medium (mocks diverge from reality) | Medium-high (real boundaries) | Highest (tests the real system)     |
| **Speed**      | Milliseconds (thousands/sec)       | Seconds (tens to hundreds/suite)  | Minutes (tens per suite)             |
| **Precision**  | High (failure pinpoints the line)  | Medium (failure narrows to layer) | Low (failure says "something broke") |
| **Cost to write** | Low                            | Medium                            | High                                 |
| **Cost to maintain** | Low–medium                  | Medium                            | High                                 |
| **Flakiness**  | Near-zero                         | Low (containerized infra)         | High                                 |

**Q16. What is the "ice cream cone" anti-pattern and how does a codebase get there?**
A: The ice cream cone is an inverted testing pyramid: almost no unit tests, a thin integration layer, and a large, slow E2E suite. Codebases arrive here through:
- **Legacy growth without discipline** — QA teams write Selenium/Cypress tests because that's the only way to test a legacy monolith with no seams for unit testing.
- **Fear of refactoring** — developers avoid adding unit tests to tangled code and instead add E2E tests because "at least I know the user flow works."
- **Misaligned incentives** — a separate QA team that isn't responsible for test runtime has no incentive to keep the suite fast.
- **Manual → automation** — a company automating its manual test plan produces E2E scripts that mirror the manual scenarios, not a pyramid.

The cost: a 45-minute CI pipeline, flaky failures that block every PR, and developers who skip running tests locally. The fix is a multi-sprint effort to add unit tests to core logic and convert broad E2E tests to narrow integration tests, one flow at a time.

**Q17. When should you *not* follow the pyramid and instead emphasize integration tests?**
A: The pyramid is a guideline, not a law. Push toward a flatter distribution (more integration, fewer unit tests) when:
- **The domain is mostly I/O orchestration** — a data pipeline service that reads from S3, transforms, and writes to a DB has little pure logic to unit-test; integration tests against real (or emulated) storage are where the real bugs live.
- **You're testing infrastructure code** — a custom Kafka consumer framework, a database migration runner, or an HTTP retry library is best validated against the real system it wraps.
- **Unit tests require extensive mocking** — if a unit test requires 15 mock setups to exercise a single code path, the abstraction is wrong, not the test. Refactor or drop to integration level.
- **The cost of a missed integration bug is high** — fintech, healthcare: a bug in how your ORM generates a SQL WHERE clause can have regulatory consequences. Integration tests against real DB replicas are worth the cost.

**Q18. How does test coverage percentage relate to the pyramid, and is 100% coverage a good goal?**
A: Coverage measures how many lines/branches are *executed* by tests — not whether they're *correctly tested*. 100% coverage is achievable with meaningless tests (call every function, assert nothing) and is actively harmful as a goal because:
- It incentivizes writing tests to hit lines, not to catch bugs.
- It discourages deleting dead code (removing code drops coverage).
- It treats all lines as equally worth testing (a `return null` and a payment processing branch count the same).

A more useful framing: **coverage as a floor, not a ceiling**. Set a lower bound (e.g., 80%) to catch obviously untested modules, but don't optimize for the number. Instead, track **mutation testing score** (does the test suite catch artificially introduced bugs?) for a deeper signal on test quality. Tools: **Stryker** (JS/TS), **PIT** (Java).

## Section 6: Scenario / System Design Style Questions

**Q19. "Our CI pipeline takes 40 minutes and the team has stopped running tests locally. What's wrong and how do you fix it?"**
A: This is a classic ice cream cone symptom. Diagnosis and fix in phases:

**Phase 1 — Measure (week 1)**
- Profile which tests are slowest: `jest --verbose --reporters=default` or CI timing reports. Identify the top 20% of tests consuming 80% of time.
- Categorize: are they E2E, broad integration, or slow unit tests (the last suggests hidden I/O in "unit" tests)?

**Phase 2 — Parallelize (week 1–2)**
- Split tests into shards across CI workers (GitHub Actions matrix, Jest `--shard=1/4`). This halves or quarters wall-clock time without changing test quality.

**Phase 3 — Push tests down (weeks 3–8)**
- For each slow E2E test, ask: *can this be covered by a narrow integration test?* Convert where possible.
- For each broad integration test that boots the full app, ask: *can this be a contract test + narrow integration test?*
- Add missing unit tests so the E2E tests are no longer the primary safety net.

**Phase 4 — Enforce the pyramid going forward**
- Add a CI check that fails if E2E test count grows beyond a threshold (enforces discipline).
- Create a fast "smoke" stage (unit tests only, < 2 minutes) that runs on every commit; full suite only on merge to main.

**Q20. "You're starting a greenfield Node.js + PostgreSQL API. How do you structure your test suite from day one?"**
A: Opinionated structure for a NestJS/Express + TypeORM/Prisma + PostgreSQL service:

```
src/
  modules/
    payments/
      payments.service.ts
      payments.service.spec.ts        ← unit: business logic only, DB mocked
      payments.controller.ts
      payments.controller.spec.ts     ← unit: HTTP layer, service mocked
  test/
    integration/
      payments.repository.spec.ts     ← integration: real Postgres via Testcontainers
      payments.api.spec.ts            ← narrow integration: full HTTP stack, real DB
    e2e/
      checkout-flow.spec.ts           ← E2E: critical user journey via Playwright/supertest
```

Key decisions:
- **Testcontainers** for integration tests — real Postgres, same version as production, spun up per test suite, truncated between tests.
- **Supertest** for HTTP-level integration tests (no real browser, drives the Express/NestJS app directly).
- **Playwright** for true E2E (only for flows that require browser rendering).
- `NODE_ENV=test` loads a test config that disables external HTTP calls (stubbed via `msw` or `nock`).
- CI pipeline: unit tests (< 2min) → integration tests (< 8min) → E2E tests (< 15min), each stage gated on the previous.

**Q21. "A senior engineer says 'we should delete all our unit tests and only write integration tests.' How do you respond?"**
A: Don't dismiss it — it's a defensible position in certain contexts (see Q17), but it needs scrutiny:

First, understand the motivation: *why* does she want to delete unit tests? Common real grievances:
- Unit tests are coupled to implementation, breaking on every refactor → the tests are badly written, not inherently wrong.
- Unit tests give false confidence because mocks don't match reality → the mocking boundary is drawn wrong; fix the boundary.
- Integration tests already cover the same cases → if true, the unit tests are redundant and *should* be deleted.

Then reason about the tradeoffs she's implicitly accepting:
- Integration tests are 10–100× slower. If the unit suite has 500 tests running in 3s, replacing them with integration tests running in 5min changes the feedback loop dramatically.
- Integration test failures are harder to diagnose — a test that boots the DB and fires 8 queries doesn't pinpoint which query is wrong.
- Some logic (complex algorithms, edge cases in parsers, financial rounding) genuinely belongs in unit tests with fine-grained assertions.

Likely right answer: **a hybrid** — delete the badly written unit tests that mock every collaborator and assert on implementation details; keep unit tests for pure logic; write integration tests for the I/O layer. She's probably reacting to bad unit tests, not unit tests in principle.

**Q22. "How would you test a service that processes Kafka messages and writes results to Postgres?"**
A: Layer the tests:

**Unit (majority)**
- Test the message handler function with a plain JavaScript object as input — no Kafka, no DB. Assert the transformation logic, error handling, and retry decisions.
- Test the DB repository class with a mocked DB client — assert the SQL/ORM method is called with correct args.

**Narrow integration (most of the remaining coverage)**
- Spin up a real Postgres via Testcontainers; test the repository class against it. Assert that the schema handles edge cases (NULL, uniqueness constraints, concurrent writes).
- Spin up a real Kafka broker (or use `kafkajs` in-memory test mode); test the consumer lifecycle: consumer subscribes, processes one message, commits offset.

**Broad integration (a few key scenarios)**
- Run the full consumer + Postgres together. Produce N messages to the test topic, let the consumer process them, assert the Postgres rows.
- Test the failure path: produce a malformed message, assert that the consumer writes to the dead-letter topic and does not commit offset.

**E2E (smoke only)**
- One test in staging: produce a real event, wait for the downstream side-effect (an HTTP callback, a notification), assert it arrived. Runs post-deploy, not in CI.

**Q23. "How do you handle test data management across a large integration test suite?"**
A: Test data management is one of the hardest parts of a mature test suite. Patterns ranked by reliability:

- **Builder pattern / test factories** — a `UserFactory.create({ role: 'admin' })` function inserts a user with sensible defaults, letting each test declare only the fields it cares about. Libraries: `fishery`, `factory-bot` equivalents. Keeps tests readable and decoupled from schema changes.
- **Database reset strategy** — choose one: transaction rollback (fastest), table truncation (works for multi-connection), or per-suite fresh DB (safest, slowest). Be consistent — mixing strategies causes flakiness.
- **Avoid shared fixtures** — a fixtures file that pre-seeds 50 rows for all tests creates hidden dependencies. When one test modifies a shared row, another test breaks. Prefer test-local inserts.
- **Deterministic IDs in tests** — use fixed UUIDs or predictable sequences in test data rather than auto-generated IDs. Makes assertions on foreign keys readable and avoids off-by-one confusion.
- **Seeding order from dependencies** — if your schema has FK constraints, factories must insert in dependency order (User before Order before OrderItem). A factory library handles this via traits and associations.

**Q24. "Your E2E suite has 200 tests and 30% are flaky. What's your remediation plan?"**
A: A 30% flakiness rate means the suite is generating noise — developers stop trusting failures, so real bugs get ignored. Remediation:

**Step 1 — Quarantine immediately**
- Move all known-flaky tests into a separate suite that runs in "observation mode" — results are reported but don't block CI. Stop the bleeding.

**Step 2 — Classify flakiness causes** (one week of investigation)
- **Timing** — async state not awaited; fix with explicit `waitFor` conditions.
- **Data pollution** — tests share DB state; fix with per-test data isolation.
- **Selector fragility** — fix by migrating to `data-testid` attributes.
- **Third-party dependency** — stub at network layer (Playwright's `page.route()`).

**Step 3 — Fix or delete**
- For each quarantined test: fix the root cause if the test covers something no other test covers; delete it if the coverage exists elsewhere. Deleting is always an option — a deleted test doesn't create false confidence.

**Step 4 — Prevent recurrence**
- Track flakiness rate as a metric in CI (percentage of test runs that include at least one retry-passed test).
- Require a flakiness review before merging new E2E tests (same as a code review).
- Set a `--retries=0` policy in CI (no automatic retries) — retries hide flakiness instead of fixing it.

**Q25. "Walk me through how you'd review a PR that adds 15 new E2E tests for a feature that already has unit and integration test coverage."**
A: The review has two parts: the tests themselves, and the *decision* to use E2E.

**On the decision:**
- First ask: what does each E2E test cover that the existing unit/integration tests don't? If the answer is "nothing new — it's extra confidence," push back. Extra E2E tests have a real cost: CI time, maintenance burden, and flakiness risk. Extra confidence that duplicates existing coverage isn't worth the cost.
- Check if any of the 15 could be integration tests instead — e.g., a test that clicks a form and asserts a DB row was inserted can be an HTTP-level integration test (supertest) that's 10× faster and less fragile.

**On the tests themselves:**
- Are waits explicit (`waitForSelector`, `waitForResponse`) or are there `sleep()` calls? (sleep = future flakiness)
- Are test data created fresh per test, or shared? (shared = flakiness)
- Are selectors based on `data-testid` attributes or on CSS classes / text content? (CSS/text = fragile)
- Is the test asserting user-visible outcomes (page content, navigation) or implementation details (class names, internal state)?
- Does the test clean up after itself, or does it leave DB state that could affect other tests?

Feedback to give: suggest converting the coverage-duplicating tests to integration level; keep only the E2E tests that exercise genuine browser-specific behavior (file upload, clipboard, navigation, auth redirect flows).

## Quick Reference Table

| Property            | Unit                              | Integration                        | E2E                                |
|--                   |--                                 |--                                  |--                                  |
| Scope               | Single function/class             | Multiple components + real infra   | Full stack, real browser/client    |
| Speed               | Milliseconds                      | Seconds                            | Tens of seconds to minutes         |
| Flakiness           | Near-zero                         | Low                                | High                               |
| Confidence          | Low–medium                        | Medium–high                        | Highest                            |
| Failure precision   | High (exact line)                 | Medium (layer)                     | Low ("something broke")            |
| Setup complexity    | None                              | DB/broker container                | Full environment                   |
| Best for catching   | Logic bugs, edge cases            | Schema, query, contract bugs       | Composition bugs, UX regressions   |
| Proportion (pyramid)| ~70%                              | ~20%                               | ~10%                               |
| Tools (JS/TS)       | Jest, Vitest                      | Jest + Testcontainers, Supertest   | Playwright, Cypress                |

---

**Tip for the interview:** At the 5 YOE level, "what is the testing pyramid" won't be asked directly — it surfaces in system design ("how would you test this service?"), in code review discussions ("is this test at the right layer?"), and in engineering process questions ("why is your CI so slow?"). Know the vocabulary cold (mock vs stub vs fake, flakiness, ice cream cone anti-pattern), have a concrete story about converting a slow E2E test to a fast integration test and the CI time you saved, and be able to articulate *why* a specific bug can only be caught at a specific layer — that's what distinguishes a senior engineer from someone who just knows the triangle diagram.
