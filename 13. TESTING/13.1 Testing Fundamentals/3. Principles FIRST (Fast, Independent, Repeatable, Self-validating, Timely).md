# Testing Principles: FIRST (Fast, Independent, Repeatable, Self-validating, Timely) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are the FIRST principles of testing, and why do they exist as a set?**
A: FIRST is a mnemonic for the five properties that make a test suite trustworthy and sustainable:
- **F**ast — tests run quickly enough to be executed on every code change.
- **I**ndependent — tests do not depend on each other's state or execution order.
- **R**epeatable — tests produce the same result every time, regardless of environment or time.
- **S**elf-validating — tests produce a clear pass/fail signal without human interpretation.
- **T**imely — tests are written at the right time relative to the code they verify.

They exist as a set because each property guards against a specific failure mode that erodes trust in a test suite. A suite that is fast but not repeatable gives you fast wrong answers. A suite that is repeatable but not independent gives you order-dependent failures that are impossible to debug in isolation. All five must hold together for the suite to be genuinely useful as a development safety net.

**Q2. What is the cost model that makes "Fast" the first principle?**
A: Speed is first because it governs the feedback loop — the time between making a change and knowing whether it broke something. The cost model: if a full suite takes 30 minutes, developers run it once before a PR and never during active development. Bugs compound over many changes before being caught. If the suite takes 30 seconds, developers run it after every meaningful change — bugs are caught at the moment of introduction, which is the cheapest possible time to fix them. The concrete rule of thumb from Clean Code: unit tests should run in milliseconds, the full unit suite in under a minute. Integration and end-to-end suites can be slower, but slowness should be a conscious decision backed by a proportional confidence gain.

**Q3. How do the FIRST principles apply differently across the test pyramid layers?**
A: The principles apply at all layers but their weight and achievability varies:

| Principle       | Unit tests                                  | Integration tests                                   | E2E tests                                         |
|-----------------|---------------------------------------------|-----------------------------------------------------|---------------------------------------------------|
| Fast            | Must be — target milliseconds per test      | Harder — DB/network I/O adds real time              | Accepted trade-off — seconds per test is fine     |
| Independent     | Easily achieved — pure functions, mocks     | Requires DB teardown/transaction rollback per test  | Hardest — shared browser state, auth sessions     |
| Repeatable      | Trivial if no I/O                           | Requires seeded data and controlled external calls  | Fragile — UI timing, browser quirks               |
| Self-validating | Always — `expect` assertions               | Always                                              | Always, but flakiness can masquerade as failure   |
| Timely          | TDD enforces it; retrofitting is expensive  | Often written after feature — acceptable            | Usually written after — acceptable                |

Understanding this layering is the 5 YOE answer — not just reciting definitions.

**Q4. What is the relationship between FIRST principles and test suite maintainability?**
A: Violations of FIRST principles create compound maintenance debt. A slow suite gets skipped. A non-independent suite produces cascade failures that take hours to debug. A non-repeatable suite produces flaky tests that developers learn to ignore — and once developers learn to ignore test failures, the suite's safety net value is zero. The FIRST principles are not quality ideals; they are the minimum requirements for a test suite that developers will actually trust and run. At 5 YOE, the relevant question isn't "do you know FIRST?" — it's "can you diagnose which principle a broken suite is violating and fix it?"

## Section 2: Fast

**Q5. What are the most common causes of slow unit tests in a Node.js/NestJS backend?**
A: Slow unit tests in a Node.js/NestJS service almost always trace back to one of:
- **Real I/O in unit tests** — hitting an actual database, Redis, or HTTP endpoint instead of a mock. A single real DB call adds 5–50ms; at 500 tests this is 2.5–25 seconds of avoidable latency.
- **NestJS application bootstrap per test** — calling `NestFactory.create()` in a `beforeAll` for a unit test spins up the full DI container, loads all modules, and runs lifecycle hooks. Cost: 500ms–2s per suite file. Unit tests should instantiate the class under test directly, not the full app.
- **Real `setTimeout`/`setInterval` in business logic** — tests that exercise code with real timers wait out the actual delay. Fix: use Jest's fake timers (`jest.useFakeTimers()`).
- **No parallelism** — Jest runs test files in parallel by default but runs tests within a file serially. If a single file has 200 tests and one of them takes 2 seconds, it blocks all 200. Split large test files.
- **Logging overhead** — libraries like Winston or Pino write to stdout/file during tests. Suppress with `LOG_LEVEL=silent` or a null transport in test config.

**Q6. How do you keep integration tests fast when they require a real database?**
A: Several techniques, used in combination:
- **Transaction rollback per test** — wrap each test in a transaction, do all assertions, then roll back. The DB state is reset with no truncation cost. Works cleanly with TypeORM's `QueryRunner` or Knex's transaction API. Caveat: doesn't work if the code under test commits its own transaction.
- **In-memory DB for development** — use SQLite in-memory (for simple schemas) or a Postgres container (`testcontainers`) that's spun up once per suite run and reused.
- **Shared schema, isolated data** — use a per-test unique prefix or tenant ID to keep data isolated without resetting the entire schema between tests.
- **`testcontainers`** — spin up a real Postgres Docker container programmatically, run the suite, destroy it. Slower than in-memory but production-equivalent schema and behaviour.
- **Parallelise at the file level** — run each test file against its own DB schema/tenant so files run truly in parallel without interfering.

**Q7. What is the "test doubles" hierarchy, and how does it relate to test speed?**
A: Test doubles are objects that replace real dependencies during testing. In order of increasing fidelity (and decreasing speed):
- **Dummy** — passed but never used; just satisfies a parameter requirement.
- **Stub** — returns a hardcoded response; no real logic. `jest.fn().mockResolvedValue({ id: 1 })`.
- **Fake** — a working but simplified implementation. An in-memory repository instead of a real DB.
- **Spy** — a real object where some calls are intercepted and recorded. `jest.spyOn(service, 'send')`.
- **Mock** — a pre-programmed object with expectations that also verifies calls were made correctly.

The speed rule: prefer dummies and stubs for pure unit tests (zero I/O), fakes for integration tests (fast I/O), and reserve real dependencies for integration/E2E tests where the fidelity gain justifies the speed cost.

## Section 3: Independent

**Q8. What does test independence mean in practice, and what are the most common violations?**
A: Independence means: the result of test B must not depend on whether test A ran, what test A did to shared state, or what order A and B execute in. A suite is independent if every test can run in isolation and in any order and produce the same result. Common violations:
- **Shared module-level variables** — `let userCache = {}` declared outside `beforeEach`, mutated by test A, and read by test B.
- **Database state not reset** — test A inserts a row; test B's `findAll` count includes A's row; B passes only when A runs first.
- **Singleton with persistent state** — a caching service or event emitter whose state accumulates across tests in the same Jest worker.
- **File system side effects** — test A writes a file; test B reads it; both pass together, B fails alone.
- **Global mock not restored** — `jest.spyOn` without `jest.restoreAllMocks()` leaks the mock into subsequent tests.

**Q9. How does Jest's test isolation model work, and what are its limits?**
A: Jest runs each test *file* in a separate worker process with its own Node.js module registry — `require`/`import` caches are completely fresh per file. This means module-level side effects don't bleed between files. Within a file, however, Jest runs tests serially in declaration order, sharing the same module instances. So module-level state (a singleton service, a global variable) *does* bleed between tests in the same file unless explicitly reset in `beforeEach`/`afterEach`. The limits: `--runInBand` (single process) removes even file-level isolation; workers can still share the filesystem and external resources (DB, Redis); `jest.resetModules()` inside a test resets the module registry mid-file but is slow and rarely necessary if the code is designed testably.

**Q10. How do you enforce independence for tests that interact with a shared PostgreSQL database?**
A: Four approaches, each with different trade-offs:

1. **Transaction rollback** — begin a transaction in `beforeEach`, run the test, rollback in `afterEach`. Fast (no actual writes committed), but only works if the code under test doesn't manage its own transactions.
2. **Truncation** — `TRUNCATE table1, table2 RESTART IDENTITY CASCADE` in `afterEach`. Slower than rollback but universal. Expensive on large tables — keep test data small.
3. **Schema-per-test** — create a separate schema (`CREATE SCHEMA test_<uuid>`) per test run, run all migrations against it, drop it after. Fully isolated, but the highest setup cost.
4. **Factory-based unique data** — instead of resetting, use unique identifiers per test (e.g., `userId = uuid()` in `beforeEach`) so tests never read each other's data even if the DB isn't reset. Simplest but accumulates data in long-running test databases.

In a fintech NestJS backend, transaction rollback with a `QueryRunner` passed through the request context is the most common production-grade approach.

**Q11. What is the difference between `beforeAll` and `beforeEach`, and when does choosing `beforeAll` violate independence?**
A: `beforeAll` runs once per test file before any test. `beforeEach` runs before every individual test. Choosing `beforeAll` for state setup violates independence when the setup creates mutable state — test A modifies it, and test B sees the modified version. The rule: use `beforeAll` only for **immutable, expensive setup** (spinning up a DB container, compiling a schema, creating an HTTP server). Use `beforeEach` for **any mutable state** (inserting seed rows, instantiating the class under test, resetting mocks). The failure mode of using `beforeAll` for mutable state: tests pass in alphabetical order but fail when Jest changes the execution order, which happens non-deterministically based on file change detection.

## Section 4: Repeatable

**Q12. What are the main sources of test flakiness, and how do you eliminate each?**
A: Flakiness is non-repeatability — a test that sometimes passes and sometimes fails with no code change. Sources and fixes:

| Source                          | Manifestation                                              | Fix                                                                 |
|---------------------------------|------------------------------------------------------------|---------------------------------------------------------------------|
| Real time / `Date.now()`        | Token expiry check fails depending on machine speed        | Inject a clock; use `jest.setSystemTime()` in tests                 |
| Network calls                   | Test fails when third-party API is slow or down            | Mock at the HTTP layer (MSW, `nock`) or use a contract test         |
| Random / UUID generation        | Assertions on exact values fail non-deterministically      | Seed the RNG; or assert structure, not exact value                  |
| Test ordering assumption        | Passes in suite, fails in isolation                        | Enforce independence (Section 3 above)                              |
| Race condition in async code    | `await service.process()` but result not yet visible       | Await the assertion explicitly; use `waitFor` or retry assertions   |
| Shared external state (DB, Redis)| Row left by previous test changes count/query result       | Reset state in `afterEach`                                          |
| Timing-dependent assertions     | `expect(spy).toHaveBeenCalled()` before async callback fires | Flush microtasks with `await Promise.resolve()` or fake timers     |

**Q13. How do you handle `Date` and time in tests to make them repeatable?**
A: Never let production code call `new Date()` or `Date.now()` directly in business logic — this creates a hidden, uncontrollable dependency on the wall clock. Instead, inject a clock:

```typescript
// Production code
@Injectable()
export class LoanService {
  constructor(private readonly clock: ClockService) {}

  isEmiOverdue(dueDate: Date): boolean {
    return this.clock.now() > dueDate;
  }
}

// Test
const fixedNow = new Date('2025-06-01T10:00:00Z');
const mockClock = { now: jest.fn().mockReturnValue(fixedNow) };
const service = new LoanService(mockClock as any);

expect(service.isEmiOverdue(new Date('2025-05-01'))).toBe(true);
```

For tests that use Jest's timer system rather than an injected clock, `jest.useFakeTimers()` + `jest.setSystemTime(new Date('2025-06-01'))` freezes `Date.now()` and `new Date()` globally for the duration of the test. Always call `jest.useRealTimers()` in `afterEach` to restore.

**Q14. How do you make tests that call external HTTP APIs repeatable without hitting the real endpoint?**
A: Three approaches, in order of preference for a Node.js/NestJS service:

1. **Mock Service Worker (MSW)** — intercepts HTTP requests at the network level (not at the library level), so it works regardless of whether you use `fetch`, `axios`, or `got`. Define handlers that return fixed responses; the test is completely isolated from the real API. Best for service-level integration tests.
2. **`nock`** — intercepts Node.js `http`/`https` module calls. Simpler for unit/integration tests against a specific URL pattern. Less portable than MSW (only works in Node, not in a browser).
3. **Manual mocking** — mock the HTTP client module (`jest.mock('axios')`) and stub its return value. Fastest to write, but only tests that the code *calls* axios correctly — not that it handles real response shapes correctly.

For fintech external calls (CIBIL, NACH, UPI), MSW or `nock` with a fixture library of real-shaped (anonymised) responses gives the best balance of repeatability and fidelity.

**Q15. What is a "hermetic test," and why is it the gold standard for repeatability?**
A: A hermetic test is fully self-contained — it brings up everything it needs (seed data, configuration, service instances), runs its assertion, and tears down completely, with zero reliance on pre-existing external state. A hermetic test can be run on any machine, in any CI environment, in any order, at any time, and produce exactly the same result. It's the gold standard because it eliminates the entire class of environment-dependent flakiness. The cost: hermetic tests are typically harder to write and slower to run (they set up more state). The trade-off: hermetic integration tests using `testcontainers` (fresh Postgres per run) are slower than tests against a shared staging DB but orders of magnitude more trustworthy. For a fintech backend handling loan state machines, hermetic tests are worth the cost — a flaky test in a payment flow is worse than a slow test.

## Section 5: Self-Validating

**Q16. What does "self-validating" mean, and what are the failure modes when it's violated?**
A: A self-validating test produces an unambiguous, automated pass/fail result with no human inspection required. Failure modes when this is violated:
- **Tests that only log output** — `console.log(result)` with no `expect()` call. The test always passes; a human must read the output to know if anything is wrong.
- **Tests with too-broad assertions** — `expect(result).toBeDefined()` when the test should assert on specific field values. The test passes even when the result is structurally wrong.
- **Snapshot tests that are never reviewed** — Jest snapshots auto-update on `--updateSnapshot`; if no one reviews the diff, the snapshot becomes a rubber stamp.
- **Tests that assert the wrong thing** — testing an implementation detail (`expect(spy).toHaveBeenCalledTimes(3)`) instead of the observable output (`expect(result.status).toBe('APPROVED')`). The test passes even when the output is wrong, as long as the internal call count matches.

**Q17. What is the difference between asserting on outcomes vs. asserting on implementation details, and why does it matter?**
A: Outcome assertions test what the system produces — the return value, the DB state after the call, the event emitted. Implementation assertions test how the system produces it — which internal method was called, how many times, with what arguments. Asserting on implementation details:
- Breaks when you refactor (rename a method, change the call structure) even if the behaviour is identical.
- Gives false confidence — the test passes even if the output is wrong, as long as the internal mechanism is the same.
- Creates tight coupling between the test and the implementation, making refactoring painful.

Rule: assert on the observable contract — what the caller receives, what the DB contains, what the event payload says. Reserve spy/call-count assertions for cases where the *side effect itself* is the contract (e.g., verifying an email was sent, a Kafka message was published).

**Q18. How do you write self-validating tests for asynchronous operations like Kafka message publishing or async queue processing?**
A: Async operations complete out of band, making naive assertions race. The patterns:

```typescript
// Pattern 1: Mock the publisher, assert it was called with the right payload
const publishSpy = jest.spyOn(kafkaProducer, 'send').mockResolvedValue(undefined);
await loanService.approveLoan(loanId);
expect(publishSpy).toHaveBeenCalledWith(
  expect.objectContaining({
    topic: 'loan.approved',
    messages: [expect.objectContaining({ value: expect.stringContaining(loanId) })]
  })
);

// Pattern 2: For real consumers in integration tests, poll for the side effect
await loanService.approveLoan(loanId);
await waitFor(
  async () => {
    const loan = await loanRepo.findById(loanId);
    expect(loan.status).toBe('DISBURSED'); // set by the consumer
  },
  { timeout: 5000, interval: 200 }
);
```

`waitFor` (from `@testing-library` or a custom implementation) retries the assertion on an interval until it passes or times out. This is self-validating — it fails with a clear message if the async operation never completes — rather than using a raw `setTimeout` that always passes.

## Section 6: Timely

**Q19. What does "Timely" mean in the context of FIRST, and what goes wrong when tests are written late?**
A: Timely means tests are written at the right moment relative to the code they cover — ideally before or alongside the code (TDD), not weeks after the feature ships. Writing tests late produces several compounding problems:
- **Untestable code** — production code written without tests in mind tends to acquire hard dependencies (direct `new` instantiation, static method calls, global state) that make it difficult to unit test without refactoring. The test reveals the design flaw retroactively.
- **Specification drift** — the developer has to reconstruct what the correct behaviour *should* have been, rather than encoding it as a failing test before writing the implementation. Memory is unreliable; edge cases are missed.
- **Low coverage of error paths** — when writing code first, developers tend to test the happy path only. TDD forces you to write the error path test first, so it gets implemented.
- **False confidence** — tests written to make existing code pass (rather than to specify expected behaviour) are biased to confirm what the code does, not what it should do.

**Q20. What is TDD (Test-Driven Development), and what does the red-green-refactor cycle produce?**
A: TDD is the practice of writing a failing test before writing the implementation code. The cycle:
1. **Red** — write the smallest test that captures the next piece of required behaviour; run it; watch it fail (confirms the test is actually testing something).
2. **Green** — write the minimum implementation to make the test pass; don't over-engineer.
3. **Refactor** — clean up the implementation (extract methods, rename, remove duplication) with the passing test as a safety net; rerun to confirm it still passes.

What the cycle produces: tests that are guaranteed to have been failing before the implementation existed (so they actually test something), and production code designed for testability from the start. At 5 YOE the nuance: TDD is most valuable for business logic and domain rules. It's less practical for infrastructure code (DB migrations, Kafka topic setup) and UI integration tests — apply it selectively.

**Q21. What is the difference between TDD and BDD (Behaviour-Driven Development), and when would you use each?**
A: TDD focuses on the developer's perspective — write a unit test that specifies a small piece of code's behaviour. BDD is a communication-first extension of TDD — tests are written in natural language (Given/When/Then) to serve as a shared specification between developers, QA, and business stakeholders. BDD tools: Cucumber, Gherkin, Jest-Cucumber. When to use each:
- **TDD** — for pure business logic, domain services, utility functions, any code with clear inputs and outputs. Most of a fintech backend's EMI calculation, eligibility engine, or risk scoring logic.
- **BDD** — when the acceptance criteria must be agreed on with a non-technical stakeholder, the scenario is complex enough to warrant a structured language specification, and the team has the discipline to keep Gherkin up to date. Caution: Gherkin that's not maintained becomes misleading documentation.
In practice, at 5 YOE in a product engineering team, TDD for unit tests and plain Jest `describe/it` blocks for integration tests (written with BDD spirit but without Gherkin) is the most common and pragmatic combination.

## Section 7: Pitfalls & Anti-patterns

**Q22. What is a "test that always passes" anti-pattern, and how do you catch it in a Node.js/Jest codebase?**
A: A test that always passes regardless of production code behaviour gives false confidence — it makes the coverage metric green while providing zero safety. Common forms:
- **Missing `return` on a promise assertion** — `expect(asyncFn()).resolves.toBe(true)` without `await` or `return`; Jest doesn't wait for the promise, so the assertion never runs and the test passes.
- **`expect.assertions(0)`** or no `expect.assertions(n)` guard in an async test — if the assertion inside a `.then()` or callback is never reached, the test passes silently.
- **`try/catch` swallowing failures** — `try { await riskyOp(); } catch {}` where the catch block is empty; if the operation throws, the assertion after it is never reached.

Detection: `expect.assertions(n)` at the top of every async test declares how many assertions *must* run — if fewer run, Jest fails the test. Also: mutation testing (e.g., Stryker) changes the production code and verifies that tests start failing — any test that still passes after a mutation is not actually testing that code path.

**Q23. What is "over-mocking," and how does it cause tests to pass while the system is broken?**
A: Over-mocking is mocking so many dependencies that the test only verifies the test doubles, not the actual code. Example: a test for a `LoanService.approve()` method that mocks the repository, mocks the eligibility checker, mocks the event publisher, and mocks the notification service, then asserts that each mock was called — this test would pass even if the real `approve()` method was replaced with an empty function that just called each mock. The test is testing the mock setup, not the business logic. Signs of over-mocking: the test has more `jest.mock()` lines than assertion lines; removing business logic from the production function doesn't cause the test to fail; the test breaks whenever you rename an internal method (it's testing wiring, not behaviour). Fix: write tests at the boundary of the real unit (assert on the output/state), use fakes instead of mocks for repositories, and reserve mocks for external side effects (email, Kafka).

**Q24. What is the "ice cream cone" anti-pattern in test suites, and how does it relate to FIRST?**
A: The ice cream cone is an inverted test pyramid — a suite dominated by slow E2E tests at the top with few unit tests at the bottom. It's the natural outcome of teams that add tests reactively after bugs (bugs are caught in production → add an E2E test to prevent regression) without investing in unit test coverage. The FIRST violations it causes: the suite is **slow** (E2E tests dominate; the suite takes hours), **not repeatable** (E2E tests are the most flakiness-prone layer), and **not timely** (E2E tests are written after features, not alongside). The fix: invert the pyramid deliberately — for every E2E test you add, ask "what unit and integration tests would catch this bug at a lower level?" and add those too. Over time, push coverage down the pyramid, not up.

## Section 8: Scenario / System Design Style Questions

**Q25. "Your NestJS fintech backend's test suite takes 18 minutes to run in CI. The team is skipping tests locally because of this. Walk me through how you'd diagnose and fix the suite."**
A: Systematic approach:

**Step 1 — Profile the suite:**
Run `jest --verbose --testPathPattern=""` with timing output. Jest reports per-file duration. Identify the slowest 10% of files — they likely account for 50–80% of total runtime (Pareto).

**Step 2 — Classify the slow tests:**
For each slow file, determine why it's slow:
- Is it bootstrapping the full NestJS app with `NestFactory.create()`? → Switch to direct class instantiation for unit tests.
- Is it doing real DB calls? → Introduce transaction rollback or `testcontainers`.
- Is it sleeping or using real timers? → Replace with `jest.useFakeTimers()`.
- Is it making real HTTP calls to external APIs? → Add MSW or `nock` interceptors.

**Step 3 — Enforce fast unit tests:**
Create a `jest.unit.config.ts` that only runs unit tests (files matching `*.spec.ts` in `src/`, excluding `*.integration.spec.ts`). These should run in under 60 seconds. Run these on every local save and on every PR.

**Step 4 — Parallelise integration tests:**
Integration tests should run in parallel using Jest's `--maxWorkers` with a worker per DB schema (using `testcontainers` or schema namespacing). Each worker owns its own schema — no shared state between workers.

**Step 5 — Stratify CI:**
```
PR CI: unit tests only (< 60s) — blocks merge
Merge to main: unit + integration (< 5 min) — blocks deploy
Nightly: full suite including E2E (18 min) — alerts on failure
```
This gives fast feedback where it matters (PR review loop) without abandoning broader coverage.

**Step 6 — Add a speed gate:**
Add a Jest `testTimeout` of 5000ms and a custom reporter that fails the build if any individual test exceeds 500ms without a documented exception. This prevents future slow tests from creeping in.

**Q26. "You're reviewing a PR for a loan disbursement service. The tests all pass in CI but you're not confident they'd catch a regression. What do you look for in the test code?"**
A: A structured review against FIRST principles:

**Fast:** Are any tests bootstrapping the full NestJS app unnecessarily? Any real `setTimeout` calls without fake timers?

**Independent:** Are tests using `beforeAll` to insert seed data without resetting between tests? Any `let sharedState` declared at module level and mutated across tests?

**Repeatable:** Is `Date.now()` called in business logic without injection? Are there any `Math.random()` calls in the code under test that aren't seeded? Are any tests hitting real external APIs (NACH, CIBIL sandbox)?

**Self-validating:** Are async tests missing `await` on `expect(...).resolves`? Is `expect.assertions(n)` used in tests with conditional assertion paths? Are assertions specific — `expect(disbursement.amount).toBe(50000)` — or broad — `expect(disbursement).toBeDefined()`?

**Timely:** Are error paths (insufficient balance, KYC failure, bureau decline) covered, or only the happy path? Missing error path coverage is the signature of tests written after the fact, to make existing code pass.

**Red flags specific to fintech:** No test for idempotency (duplicate disbursement request), no test for concurrent approval race condition, no test for partial failure (DB write succeeds but Kafka publish fails — does the loan get stuck?).

## Quick Reference: FIRST Violations and Fixes

| Principle        | Common violation                                         | Fix                                                                  |
|------------------|----------------------------------------------------------|----------------------------------------------------------------------|
| Fast             | Full NestJS app bootstrapped in unit tests               | Direct class instantiation; mock dependencies                        |
| Fast             | Real DB calls in unit tests                              | In-memory fake repository or stub                                    |
| Fast             | Real timers (`setTimeout`) in tests                      | `jest.useFakeTimers()` + `jest.runAllTimers()`                       |
| Independent      | Shared mutable state in `beforeAll`                      | Move to `beforeEach`; reset all mutable state                        |
| Independent      | DB not reset between tests                               | Transaction rollback or `TRUNCATE` in `afterEach`                    |
| Independent      | `jest.spyOn` not restored                                | `jest.restoreAllMocks()` in `afterEach`                              |
| Repeatable       | `Date.now()` in business logic                           | Inject a `ClockService`; use `jest.setSystemTime()` in tests         |
| Repeatable       | Real HTTP calls to external APIs                         | MSW or `nock` interceptors with fixture responses                    |
| Repeatable       | Order-dependent test execution                           | Run `jest --randomize` to surface; then fix independence violations  |
| Self-validating  | Missing `await` on async assertions                      | Always `await expect(...).resolves/rejects`                          |
| Self-validating  | Over-broad assertions (`toBeDefined`)                    | Assert on specific field values and types                            |
| Self-validating  | Tests that only log, no `expect()`                       | Add `expect.assertions(n)` as a guard                                |
| Timely           | Only happy path covered                                  | Write error-path test first (TDD); use mutation testing to find gaps |
| Timely           | Tests written after the bug is found in production       | Establish pre-PR test coverage gate in CI                            |

**Tip for the interview:** At the 5 YOE level, FIRST will not be asked as "define each letter." It comes up inside harder questions: why is your CI slow, why are tests flaky, why did a regression slip through despite 80% coverage, how do you review a PR's test quality. The answer that lands is always the same structure — name the principle being violated, show the concrete symptom in the codebase, give the specific fix. Have one story ready for each principle: a slow test suite you profiled and fixed, a flaky test you traced to a shared clock or DB state, a self-validating issue you caught in a PR review (missing `await` on an async assertion), a codebase where tests were added reactively and how you shifted left. That's the answer at this level.
