# Integration Testing: `testcontainers-node` for PostgreSQL, Redis, MongoDB — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is `testcontainers-node`, and what problem does it solve over a shared staging database?**
A: `testcontainers-node` is a Node.js library that programmatically starts and stops real Docker containers from within your test code. It solves the core problem of integration test isolation: a shared staging or CI database is a global mutable resource — test A's writes are visible to test B, tests that run in parallel corrupt each other's data, and a failed test can leave the database in a state that breaks every subsequent test in the suite. With `testcontainers`, each test suite (or each test file in parallel Jest workers) gets its own ephemeral container — a real PostgreSQL, Redis, or MongoDB instance that starts fresh, runs the suite, and is destroyed when the suite ends. The container is not mocked or simulated; it is the real engine, which means query planner behaviour, index usage, constraint enforcement, and wire protocol correctness are all tested exactly as they would be in production.

**Q2. What are the alternatives to `testcontainers`, and why would you choose `testcontainers` over each?**
A:

| Alternative                     | What it is                                                    | Why `testcontainers` wins                                                            |
|---------------------------------|---------------------------------------------------------------|--------------------------------------------------------------------------------------|
| Shared staging DB               | A persistent, shared database environment                     | No isolation — tests pollute each other; parallel runs corrupt data                  |
| In-memory SQLite                | Lightweight SQL engine that runs in-process                   | Different SQL dialect, no PostgreSQL-specific features (JSONB, arrays, window fns)   |
| `jest-mock-extended` / stubs    | Mocked repository layer                                       | Tests the mock contract, not the real DB behaviour; misses query plan bugs           |
| `pg-mem`                        | In-memory PostgreSQL emulator in JavaScript                   | Incomplete dialect coverage; doesn't exercise the real wire protocol or extensions   |
| Docker Compose (manual)         | Pre-started containers managed outside the test process       | Not self-contained — requires external setup; containers outlive test runs           |
| `testcontainers`                | Containers started and stopped by the test process itself     | Hermetic, automatic, production-equivalent, parallel-safe, no external coordination  |

The one legitimate case for an alternative: if your CI environment cannot run Docker (some restricted CI systems), `pg-mem` or SQLite are acceptable fallbacks for schema validation tests — but not for production-critical query behaviour.

**Q3. How does `testcontainers-node` communicate with Docker, and what does it require in the environment?**
A: `testcontainers-node` uses the Docker daemon via the Docker socket (`/var/run/docker.sock` on Linux/macOS) or the Docker Desktop API on Windows. It requires:
- **Docker installed and running** — the daemon must be accessible. On CI (GitHub Actions, GitLab CI, CircleCI), Docker is available by default on most Linux runners.
- **The `testcontainers` npm package** — `npm install --save-dev testcontainers`.
- **Image availability** — the container image (`postgres:15`, `redis:7`, `mongo:6`) must be pullable from Docker Hub or a private registry. On first run, images are pulled and cached. Subsequent runs use the local cache.
- **Ryuk (resource cleanup)** — `testcontainers` starts a companion container called Ryuk that tracks and destroys containers if the test process exits unexpectedly (crash, `kill -9`). This is the mechanism that prevents orphaned containers accumulating on CI. Ryuk can be disabled with `TESTCONTAINERS_RYUK_DISABLED=true` for environments where it causes issues.

**Q4. What is the container lifecycle in `testcontainers-node`, and how does it map to Jest's `beforeAll`/`afterAll` hooks?**
A: The container lifecycle has four stages: **build** (instantiate the container object with configuration), **start** (pull the image if needed, create the container, start the process, wait for the readiness check), **use** (run tests against the running container), **stop** (stop and remove the container). This maps directly to Jest hooks:

```typescript
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';

describe('LoanRepository (integration)', () => {
  let container: StartedPostgreSqlContainer;
  let dataSource: DataSource;

  beforeAll(async () => {
    container = await new PostgreSqlContainer('postgres:15')
      .withDatabase('testdb')
      .withUsername('testuser')
      .withPassword('testpass')
      .start(); // pulls image, starts container, waits for readiness

    dataSource = await createDataSource(container.getConnectionUri()).initialize();
    await runMigrations(dataSource);
  }, 60_000); // extend timeout — container start can take 10–30s on first pull

  afterAll(async () => {
    await dataSource.destroy();
    await container.stop(); // stops and removes the container
  });

  afterEach(async () => {
    await dataSource.query('TRUNCATE loan RESTART IDENTITY CASCADE');
  });

  it('persists a loan application', async () => { ... });
});
```

`beforeAll` owns the container (start once, share across tests). `afterAll` stops it. `afterEach` resets data between tests — the container lives, but its data is wiped. This is the correct allocation: container start is expensive (10–30s), data reset is cheap (milliseconds).

**Q5. What is a "wait strategy," and why is it critical for container reliability?**
A: A wait strategy is the mechanism by which `testcontainers` determines that the container is actually ready to accept connections — not just that the process started. Without a wait strategy, your test code connects immediately after the Docker container is created, before the database engine has finished initialising, and gets a connection refused error. `testcontainers-node` built-in wait strategies:
- **`Wait.forLogMessage(pattern)`** — waits until a specific string appears in the container logs (e.g., `"database system is ready to accept connections"` for PostgreSQL).
- **`Wait.forHealthCheck()`** — uses the Docker health check defined in the image.
- **`Wait.forListeningPort()`** — waits until the container's exposed port is accepting TCP connections.
- **`Wait.forSuccessfulCommand(cmd)`** — runs a command inside the container and waits for exit code 0.

The module-specific containers (`@testcontainers/postgresql`, `@testcontainers/redis`, `@testcontainers/mongodb`) configure the correct wait strategy automatically — this is the primary reason to use the typed modules over the generic `GenericContainer`.

## Section 2: PostgreSQL with `testcontainers`

**Q6. How do you set up a PostgreSQL `testcontainers` instance with TypeORM migrations in a NestJS integration test?**
A:
```typescript
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { DataSource } from 'typeorm';

describe('LoanRepository (integration)', () => {
  let container: StartedPostgreSqlContainer;
  let dataSource: DataSource;

  beforeAll(async () => {
    container = await new PostgreSqlContainer('postgres:15-alpine')
      .withDatabase('fintech_test')
      .withUsername('app')
      .withPassword('secret')
      .start();

    dataSource = new DataSource({
      type: 'postgres',
      host: container.getHost(),
      port: container.getMappedPort(5432), // random host port mapped to container's 5432
      database: container.getDatabase(),
      username: container.getUsername(),
      password: container.getPassword(),
      entities: [Loan, User, Emi],
      migrations: ['src/migrations/*.ts'],
      synchronize: false, // always use migrations — never synchronize in tests
    });

    await dataSource.initialize();
    await dataSource.runMigrations(); // applies real migration files
  }, 60_000);

  afterAll(async () => {
    await dataSource.destroy();
    await container.stop();
  });
});
```

Key detail: `container.getMappedPort(5432)` — `testcontainers` maps the container's port 5432 to a random available host port to avoid conflicts when multiple test files run in parallel. Always use `getMappedPort()`, never hardcode port 5432.

**Q7. How do you handle schema isolation when multiple Jest worker processes run PostgreSQL integration tests in parallel?**
A: Two approaches, in order of preference:

**Option 1 — One container per worker (full isolation):**
Each Jest worker process starts its own PostgreSQL container. Workers never share a database. The trade-off: N containers running simultaneously (N = `--maxWorkers`), which uses significant memory but gives complete isolation.

```typescript
// jest.config.ts
export default {
  maxWorkers: 4,
  globalSetup: './test/global-setup.ts',   // optional: pre-pull images
  testTimeout: 60_000,
};

// Each test file's beforeAll starts its own container
```

**Option 2 — One container, schema-per-worker:**
Start one PostgreSQL container in Jest's `globalSetup`, then create a separate schema per worker using the Jest worker ID:

```typescript
// test/global-setup.ts
import { PostgreSqlContainer } from '@testcontainers/postgresql';

export default async () => {
  const container = await new PostgreSqlContainer('postgres:15').start();
  process.env.TEST_DB_HOST = container.getHost();
  process.env.TEST_DB_PORT = String(container.getMappedPort(5432));
  (global as any).__PG_CONTAINER__ = container;
};

// test/global-teardown.ts
export default async () => {
  await (global as any).__PG_CONTAINER__.stop();
};

// In each test file's beforeAll — create an isolated schema
const schemaName = `test_${process.env.JEST_WORKER_ID}`;
await dataSource.query(`CREATE SCHEMA IF NOT EXISTS "${schemaName}"`);
await dataSource.query(`SET search_path TO "${schemaName}"`);
await dataSource.runMigrations();
```

Option 2 uses less memory but is more complex to implement. Option 1 is simpler and recommended for most teams.

**Q8. What is the `TRUNCATE ... RESTART IDENTITY CASCADE` pattern, and when is it preferable to transaction rollback for test isolation?**
A: `TRUNCATE table RESTART IDENTITY CASCADE` removes all rows from the table, resets all sequences (auto-increment IDs) back to 1, and cascades to dependent tables via foreign keys. It is the blunt-instrument reset — after it runs, the table is in exactly the same state as after the initial migration.

Compared to transaction rollback:

| Aspect                          | Transaction rollback                               | `TRUNCATE RESTART IDENTITY CASCADE`                |
|---------------------------------|----------------------------------------------------|----------------------------------------------------|
| Speed                           | Fastest — no actual writes committed               | Fast — faster than `DELETE`, but slower than rollback |
| Works when code commits its own transaction | No                                   | Yes                                                |
| Resets sequences                | No — ID sequences advance even if rolled back      | Yes — sequences reset to 1                         |
| Works with `testcontainers`     | Requires passing `QueryRunner` through all layers  | Works on any connection                            |
| Risk of missed tables           | N/A                                                | Must list all tables or use dynamic discovery      |

In a `testcontainers` setup, `TRUNCATE` in `afterEach` is the more practical choice because the container's real PostgreSQL engine enforces MVCC isolation — you don't need to fight with transaction propagation through NestJS's DI system. Transaction rollback is elegant in theory but requires the entire request stack to share one `QueryRunner`, which is difficult to achieve in a NestJS service layer without significant refactoring.

**Q9. How do you seed reference data (static lookup tables) once per container start rather than before every test?**
A: Use `beforeAll` for immutable seed data — data that tests read but never modify:

```typescript
beforeAll(async () => {
  container = await new PostgreSqlContainer('postgres:15').start();
  dataSource = await initDataSource(container);
  await dataSource.runMigrations();

  // Seed reference data once — tests only read these
  await dataSource.getRepository(LoanProduct).save([
    { id: 'HOME_LOAN', name: 'Home Loan', maxLtv: 0.80 },
    { id: 'PERSONAL_LOAN', name: 'Personal Loan', maxLtv: null },
  ]);
  await dataSource.getRepository(State).save(indianStates);
});

afterEach(async () => {
  // Only truncate transactional tables — never the reference tables
  await dataSource.query('TRUNCATE loan, emi, user RESTART IDENTITY CASCADE');
  // loan_product and state are NOT truncated — they persist for all tests
});
```

The invariant: if a test modifies a reference table, it is responsible for restoring it in `afterEach`. In practice, structure tests so they never modify reference data — treat those tables as read-only in tests, exactly as they are in production.

## Section 3: Redis with `testcontainers`

**Q10. How do you start a Redis container with `testcontainers` and connect `ioredis` to it?**
A:
```typescript
import { RedisContainer, StartedRedisContainer } from '@testcontainers/redis';
import Redis from 'ioredis';

describe('SessionService (integration)', () => {
  let container: StartedRedisContainer;
  let redis: Redis;

  beforeAll(async () => {
    container = await new RedisContainer('redis:7-alpine').start();

    redis = new Redis({
      host: container.getHost(),
      port: container.getMappedPort(6379),
      lazyConnect: false,
    });

    await redis.ping(); // confirm connection
  }, 30_000);

  afterAll(async () => {
    await redis.quit();
    await container.stop();
  });

  afterEach(async () => {
    await redis.flushdb(); // clear all keys between tests
  });

  it('stores and retrieves a session', async () => {
    await sessionService.set('user:1', { role: 'BORROWER' }, 300);
    const session = await sessionService.get('user:1');
    expect(session.role).toBe('BORROWER');
  });
});
```

`redis.flushdb()` in `afterEach` is the Redis equivalent of `TRUNCATE` — it deletes all keys in the current database. It's a microsecond operation and gives each test a clean key space. Use `flushdb()` (current database) not `flushall()` (all databases) — in a shared Redis instance, `flushall()` would wipe other databases; even in a container, `flushdb()` is the safer habit.

**Q11. How do you test TTL-based expiry behaviour with a real Redis container without waiting real time?**
A: Two approaches:

**Option 1 — Use very short TTLs in tests:**
Set TTLs in milliseconds for test fixtures and use `PEXPIRE` / `PTTL` (millisecond precision). Wait a few milliseconds with a small `await`:

```typescript
it('expires the OTP key after the TTL elapses', async () => {
  await redis.set('otp:user-1', '123456', 'PX', 100); // 100ms TTL
  expect(await redis.get('otp:user-1')).toBe('123456');

  await new Promise(resolve => setTimeout(resolve, 150)); // real wait — 150ms
  expect(await redis.get('otp:user-1')).toBeNull();
});
```

Acceptable for TTL tests specifically — 150ms is short enough to be FIRST-compliant and tests the real Redis expiry engine.

**Option 2 — Test the TTL value, not the expiry event:**
Assert on the TTL that was set, rather than waiting for the key to actually expire:

```typescript
it('sets a 10-minute TTL on the OTP key', async () => {
  await otpService.generate('user-1');
  const ttl = await redis.ttl('otp:user-1'); // seconds remaining
  expect(ttl).toBeGreaterThan(595); // ~600 seconds, accounting for test execution time
  expect(ttl).toBeLessThanOrEqual(600);
});
```

Option 2 is faster and more precise — it tests the contract (the TTL was set correctly) without depending on real clock elapse. Use Option 1 only when you specifically need to test the expiry behaviour itself (key disappears, downstream read returns null).

**Q12. How do you test a Redis-based rate limiter with `testcontainers` to verify the Lua script executes atomically?**
A: Lua scripts in Redis execute atomically — no other command can interleave. This atomicity is a real engine behaviour that cannot be tested with a mock. With a real Redis container, you can test the Lua script directly:

```typescript
// Production code — Lua-based atomic rate limiter
const RATE_LIMIT_SCRIPT = `
  local key = KEYS[1]
  local limit = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  local current = redis.call('INCR', key)
  if current == 1 then
    redis.call('EXPIRE', key, window)
  end
  return current
`;

// Test
it('atomically increments and enforces the rate limit', async () => {
  const key = 'ratelimit:user-1:2025060110'; // keyed by user + minute window
  const limit = 5;
  const windowSeconds = 60;

  // Run 5 requests — all should be allowed
  for (let i = 1; i <= 5; i++) {
    const count = await redis.eval(RATE_LIMIT_SCRIPT, 1, key, limit, windowSeconds);
    expect(count).toBe(i);
  }

  // 6th request — limit exceeded
  const count = await redis.eval(RATE_LIMIT_SCRIPT, 1, key, limit, windowSeconds);
  expect(count).toBe(6); // service layer checks count > limit

  // TTL should be set
  const ttl = await redis.ttl(key);
  expect(ttl).toBeGreaterThan(0);
  expect(ttl).toBeLessThanOrEqual(60);
});
```

## Section 4: MongoDB with `testcontainers`

**Q13. How do you start a MongoDB container with `testcontainers` and connect Mongoose to it?**
A:
```typescript
import { MongoDBContainer, StartedMongoDBContainer } from '@testcontainers/mongodb';
import mongoose from 'mongoose';

describe('AuditLogRepository (integration)', () => {
  let container: StartedMongoDBContainer;

  beforeAll(async () => {
    container = await new MongoDBContainer('mongo:6').start();

    await mongoose.connect(container.getConnectionString(), {
      directConnection: true, // required for standalone (non-replica set) containers
    });
  }, 60_000);

  afterAll(async () => {
    await mongoose.disconnect();
    await container.stop();
  });

  afterEach(async () => {
    // Drop all collections between tests
    const collections = await mongoose.connection.db.listCollections().toArray();
    await Promise.all(
      collections.map(col => mongoose.connection.db.dropCollection(col.name))
    );
  });

  it('persists an audit log entry with the correct schema', async () => {
    const entry = await AuditLog.create({
      userId: 'user-1',
      action: 'LOAN_APPROVED',
      timestamp: new Date(),
      metadata: { loanId: 'loan-123', amount: 500000 },
    });

    const found = await AuditLog.findById(entry._id);
    expect(found?.action).toBe('LOAN_APPROVED');
    expect(found?.metadata.loanId).toBe('loan-123');
  });
});
```

The `directConnection: true` option is required because the default MongoDB container runs as a standalone instance, not a replica set — Mongoose's default connection mode expects replica set topology for transactions. For tests that require MongoDB transactions, use `MongoDBContainer` with a replica set configuration or the `@testcontainers/mongodb` replica set helper.

**Q14. How do you test MongoDB aggregation pipelines with `testcontainers` to verify they return the correct results?**
A: Aggregation pipelines are notoriously difficult to test with mocks because the pipeline stages interact with real data shapes, indexes, and MongoDB's aggregation engine. `testcontainers` gives you a real engine to test against:

```typescript
describe('EmiReportRepository.getDueEmiSummary()', () => {
  beforeEach(async () => {
    // Seed test data
    await Emi.insertMany([
      { userId: 'u1', loanId: 'l1', amount: 5000, dueDate: new Date('2025-06-01'), status: 'PENDING' },
      { userId: 'u1', loanId: 'l2', amount: 3000, dueDate: new Date('2025-06-01'), status: 'PENDING' },
      { userId: 'u2', loanId: 'l3', amount: 8000, dueDate: new Date('2025-06-01'), status: 'PAID' },
      { userId: 'u1', loanId: 'l4', amount: 2000, dueDate: new Date('2025-07-01'), status: 'PENDING' },
    ]);
  });

  it('sums pending EMI amounts per user for the given due date', async () => {
    const result = await emiRepo.getDueEmiSummary(new Date('2025-06-01'));

    expect(result).toHaveLength(1); // only u1 has pending EMIs on this date
    expect(result[0]).toMatchObject({
      userId: 'u1',
      totalPending: 8000, // 5000 + 3000
      emiCount: 2,
    });
  });
});
```

This test would be impossible to write meaningfully with a mocked repository — the mock would return whatever you told it to return. The container tests the actual `$group`, `$match`, and `$sum` pipeline behaviour.

## Section 5: Performance, Parallelism, and CI

**Q15. How do you speed up `testcontainers` test suites that are slow due to image pull times on CI?**
A: Image pull time is the dominant startup cost on a cold CI runner. Several mitigations:

**Pre-pull images in `globalSetup`:**
```typescript
// test/global-setup.ts
import { pullImage } from 'testcontainers';

export default async () => {
  await Promise.all([
    pullImage('postgres:15-alpine'),
    pullImage('redis:7-alpine'),
  ]);
  // Images are now in the local Docker cache — container.start() is fast
};
```

**Use `-alpine` variants:** Alpine-based images are significantly smaller than the default `debian` variants — `postgres:15-alpine` is ~80MB vs ~400MB for `postgres:15`. Pull time is proportional to image size.

**Cache Docker layers in CI:** GitHub Actions supports Docker layer caching:
```yaml
- name: Cache Docker images
  uses: ScribeMD/docker-cache@0.3.3
  with:
    key: docker-${{ runner.os }}-${{ hashFiles('**/package.json') }}
```

**Reuse containers across test files (singleton pattern):**
```typescript
// test/containers/postgres.ts — singleton container shared across all test files
let container: StartedPostgreSqlContainer;

export async function getPostgresContainer() {
  if (!container) {
    container = await new PostgreSqlContainer('postgres:15-alpine').start();
  }
  return container;
}
```

Use this with Jest's `globalSetup`/`globalTeardown` to start one container for the entire Jest run and reuse it across files — at the cost of requiring stricter data isolation between tests.

**Q16. How do you configure Jest to support `testcontainers` with parallel workers correctly?**
A:
```typescript
// jest.config.ts
import type { Config } from 'jest';

const config: Config = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  testMatch: ['**/*.integration.spec.ts'],
  testTimeout: 60_000,        // containers need time to start
  maxWorkers: 4,              // each worker gets its own container
  forceExit: false,           // should be false — if containers aren't closed, fix afterAll
  detectOpenHandles: true,    // surfaces unreleased connections and containers
  globalSetup: './test/global-setup.ts',    // optional: pre-pull images
  globalTeardown: './test/global-teardown.ts',
};

export default config;
```

Separate the `jest.config.ts` for integration tests from the unit test config — integration tests need the longer timeout and different worker strategy. Run them as a separate Jest project or with a separate npm script: `jest --config jest.integration.config.ts`.

**Q17. What does Ryuk do, and when would you disable it?**
A: Ryuk is a companion container that `testcontainers` starts automatically alongside your containers. It maintains a registry of containers started by your test process and destroys any that are still running if the test process dies unexpectedly — a crash, `SIGKILL`, or `--forceExit`. Without Ryuk, a crashed test process leaves containers running indefinitely, consuming memory and ports on the CI runner. Disable Ryuk (`TESTCONTAINERS_RYUK_DISABLED=true`) only in environments where:
- The CI runner doesn't have permission to start Ryuk (some locked-down Kubernetes pod environments).
- You're using a remote Docker daemon where Ryuk can't connect back to the test process.
- You've implemented your own container cleanup (e.g., `--rm` flag plus guaranteed `afterAll`).

In standard CI environments (GitHub Actions, GitLab CI with Docker-in-Docker), leave Ryuk enabled — it is the safety net for cleanup.

## Section 6: Advanced Patterns

**Q18. How do you use `testcontainers` with a custom Docker image that has pre-applied migrations?**
A: For large schemas where running migrations on every test suite start is slow, build a custom Docker image with migrations pre-applied and use it as the base image:

```dockerfile
# Dockerfile.test-pg
FROM postgres:15-alpine

# Copy migration SQL files
COPY ./migrations /docker-entrypoint-initdb.d/

# Files in initdb.d are run in alphabetical order on container first start
```

Build and push to your private ECR/registry as part of your CI pipeline:
```bash
docker build -f Dockerfile.test-pg -t your-ecr/fintech-testdb:latest .
docker push your-ecr/fintech-testdb:latest
```

Use in tests:
```typescript
container = await new PostgreSqlContainer('your-ecr/fintech-testdb:latest').start();
// Schema is already applied — no migration step needed
```

Trade-off: the image must be rebuilt whenever migrations change (add it to your migration CI step). The benefit: container start time drops from 5–10 seconds (migration application) to under 2 seconds.

**Q19. How do you test a service that uses both PostgreSQL and Redis together with `testcontainers`?**
A: Start both containers in `beforeAll` and wire them into the service together:

```typescript
describe('LoanApprovalService (integration)', () => {
  let pgContainer: StartedPostgreSqlContainer;
  let redisContainer: StartedRedisContainer;
  let dataSource: DataSource;
  let redis: Redis;
  let service: LoanApprovalService;

  beforeAll(async () => {
    // Start both containers in parallel — no dependency between them
    [pgContainer, redisContainer] = await Promise.all([
      new PostgreSqlContainer('postgres:15-alpine').start(),
      new RedisContainer('redis:7-alpine').start(),
    ]);

    dataSource = await initDataSource(pgContainer).initialize();
    await dataSource.runMigrations();

    redis = new Redis({
      host: redisContainer.getHost(),
      port: redisContainer.getMappedPort(6379),
    });

    service = new LoanApprovalService(
      dataSource.getRepository(Loan),
      new CacheService(redis),
      new EligibilityService(dataSource),
    );
  }, 90_000); // extra time for two containers

  afterAll(async () => {
    await redis.quit();
    await dataSource.destroy();
    // Stop both containers in parallel
    await Promise.all([pgContainer.stop(), redisContainer.stop()]);
  });

  afterEach(async () => {
    await dataSource.query('TRUNCATE loan, user RESTART IDENTITY CASCADE');
    await redis.flushdb();
  });

  it('caches the eligibility result in Redis after approving a loan', async () => {
    await seedUser(dataSource, { id: 'user-1', kycStatus: 'VERIFIED' });

    await service.approve('loan-123', 'user-1');

    // Assert DB state
    const loan = await dataSource.getRepository(Loan).findOneBy({ id: 'loan-123' });
    expect(loan?.status).toBe('APPROVED');

    // Assert Redis cache was populated
    const cached = await redis.get('eligibility:user-1');
    expect(JSON.parse(cached!).eligible).toBe(true);
  });
});
```

Starting both containers with `Promise.all` reduces the combined startup time from sequential (sum of both) to parallel (max of both) — typically saving 5–15 seconds.

**Q20. How do you implement a reusable `testcontainers` setup to avoid duplicating container boilerplate across many test files?**
A: Extract the container setup into a shared test helper that encapsulates the lifecycle:

```typescript
// test/helpers/pg-container.helper.ts
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { DataSource } from 'typeorm';
import { entities } from '../../src/entities';

export interface PgTestContext {
  container: StartedPostgreSqlContainer;
  dataSource: DataSource;
}

export async function startPgTestContext(): Promise<PgTestContext> {
  const container = await new PostgreSqlContainer('postgres:15-alpine')
    .withDatabase('testdb')
    .start();

  const dataSource = new DataSource({
    type: 'postgres',
    host: container.getHost(),
    port: container.getMappedPort(5432),
    database: container.getDatabase(),
    username: container.getUsername(),
    password: container.getPassword(),
    entities,
    migrations: ['src/migrations/*.ts'],
    synchronize: false,
  });

  await dataSource.initialize();
  await dataSource.runMigrations();

  return { container, dataSource };
}

export async function stopPgTestContext(ctx: PgTestContext): Promise<void> {
  await ctx.dataSource.destroy();
  await ctx.container.stop();
}

// Usage in any test file
describe('EmiService (integration)', () => {
  let ctx: PgTestContext;

  beforeAll(async () => {
    ctx = await startPgTestContext();
  }, 60_000);

  afterAll(async () => {
    await stopPgTestContext(ctx);
  });

  afterEach(async () => {
    await ctx.dataSource.query('TRUNCATE emi, loan RESTART IDENTITY CASCADE');
  });
});
```

This pattern ensures the container configuration (image version, credentials, migration path) is defined once and never drifts between test files.

## Section 7: Pitfalls and Anti-patterns

**Q21. What happens if you put `container.start()` in `beforeEach` instead of `beforeAll`, and how do you diagnose it?**
A: Starting a container in `beforeEach` means a new container is pulled, created, started, and the readiness wait is performed before every single test. Each start costs 5–30 seconds — a 20-test suite takes 100–600 seconds of pure overhead. The symptoms: the test suite completes correctly but takes orders of magnitude longer than expected; CI times balloon; developers stop running the integration suite locally. Diagnosis: add a `console.time('container-start')` / `console.timeEnd('container-start')` around the start call and observe it firing N times instead of once. Fix: move to `beforeAll`. The container is not a per-test resource — it is per-suite infrastructure.

**Q22. What causes "port already in use" errors when running `testcontainers` tests in parallel, and how does `getMappedPort()` prevent it?**
A: If container startup hardcodes a fixed host port (`-p 5432:5432`), two parallel Jest workers trying to bind the same host port simultaneously will collide — the second worker's container fails to start with `EADDRINUSE`. `testcontainers` avoids this by default: it exposes the container's internal port (5432) on a random available host port, unique per container instance. `container.getMappedPort(5432)` retrieves this dynamically assigned port. As long as you always use `getMappedPort()` rather than hardcoding the internal port, parallel workers each get their own port with no conflicts.

**Q23. Why should `forceExit: false` be the rule for integration test suites using `testcontainers`, and what does `forceExit: true` mask?**
A: `jest --forceExit` terminates the Jest process after all tests complete, regardless of whether the event loop has drained. Teams add it as a quick fix when Jest "hangs" after the test suite — but the hang is a symptom, not the problem. The actual problem is an open handle: a database connection that was never closed, a Redis client that was never quit, or a container that was never stopped in `afterAll`. `forceExit: true` kills the process before cleanup runs, which means:
- The container may not be stopped cleanly (Ryuk handles this, but it's not instantaneous).
- Open DB connections are not returned to the pool — on subsequent runs, the pool may be exhausted.
- File handles, timers, and sockets are not closed — Node.js leak detection can't report them.

The correct fix: run with `detectOpenHandles: true` in Jest config, identify the specific handle (Jest names the handle type and location), and add the corresponding `afterAll` cleanup. A suite that passes `detectOpenHandles` without `forceExit` is a clean suite.

## Section 8: Scenario / System Design Style Questions

**Q24. "Your team's integration test suite takes 8 minutes in CI. Investigation shows 12 test files each starting their own PostgreSQL container sequentially. How do you fix it?"**
A: The problem is sequential container starts — 12 containers × ~30 seconds each = 360 seconds. Two complementary fixes:

**Fix 1 — Parallelise with Jest workers:**
Ensure Jest runs test files in parallel (`maxWorkers: 4` or higher). Each worker gets its own container and they start simultaneously. Effective parallelism: 12 files across 4 workers = 3 rounds × 30s = 90 seconds instead of 360.

```typescript
// jest.integration.config.ts
export default {
  maxWorkers: '50%', // use half of available CPUs
  testTimeout: 60_000,
};
```

**Fix 2 — Shared container via `globalSetup` + schema-per-worker isolation:**
Start one PostgreSQL container in `globalSetup`, store the connection details in environment variables, and create a separate schema per worker:

```typescript
// test/global-setup.ts
export default async () => {
  const container = await new PostgreSqlContainer('postgres:15-alpine').start();
  process.env.PG_HOST = container.getHost();
  process.env.PG_PORT = String(container.getMappedPort(5432));
  process.env.PG_USER = container.getUsername();
  process.env.PG_PASS = container.getPassword();
  process.env.PG_DB = container.getDatabase();
  (global as any).__PG_CONTAINER__ = container;
};

// test/global-teardown.ts
export default async () => {
  await (global as any).__PG_CONTAINER__.stop();
};

// In each test file's beforeAll
const schema = `test_worker_${process.env.JEST_WORKER_ID ?? '1'}`;
await dataSource.query(`CREATE SCHEMA IF NOT EXISTS "${schema}"`);
await dataSource.query(`SET search_path TO "${schema}"`);
await dataSource.runMigrations();
```

Result: one container start (30s) instead of twelve. Combined with parallelism, a suite that took 8 minutes can drop to under 90 seconds.

**Q25. "You're onboarding a new microservice in your fintech platform — a NACH debit processing service that writes debit requests to PostgreSQL and caches processing state in Redis. Design the complete `testcontainers` integration test strategy from scratch."**
A: A complete strategy covering setup, isolation, data management, and CI:

**Layer 1 — Test configuration:**
```typescript
// jest.integration.config.ts
export default {
  testMatch: ['**/*.integration.spec.ts'],
  testTimeout: 90_000,
  maxWorkers: 2, // balance CI memory with parallelism
  globalSetup: './test/setup/global-setup.ts',
  globalTeardown: './test/setup/global-teardown.ts',
  detectOpenHandles: true,
  forceExit: false,
};
```

**Layer 2 — Global container lifecycle:**
```typescript
// test/setup/global-setup.ts
export default async () => {
  const [pg, redis] = await Promise.all([
    new PostgreSqlContainer('postgres:15-alpine').start(),
    new RedisContainer('redis:7-alpine').start(),
  ]);

  process.env.TEST_PG_HOST = pg.getHost();
  process.env.TEST_PG_PORT = String(pg.getMappedPort(5432));
  process.env.TEST_PG_USER = pg.getUsername();
  process.env.TEST_PG_PASS = pg.getPassword();
  process.env.TEST_PG_DB = pg.getDatabase();
  process.env.TEST_REDIS_HOST = redis.getHost();
  process.env.TEST_REDIS_PORT = String(redis.getMappedPort(6379));

  (global as any).__CONTAINERS__ = { pg, redis };
};

// test/setup/global-teardown.ts
export default async () => {
  const { pg, redis } = (global as any).__CONTAINERS__;
  await Promise.all([pg.stop(), redis.stop()]);
};
```

**Layer 3 — Per-suite setup (in each `.integration.spec.ts`):**
```typescript
describe('NachDebitService (integration)', () => {
  let dataSource: DataSource;
  let redisClient: Redis;
  let service: NachDebitService;

  const schema = `nach_test_${process.env.JEST_WORKER_ID ?? '0'}`;

  beforeAll(async () => {
    dataSource = await buildDataSource(schema).initialize();
    await dataSource.query(`CREATE SCHEMA IF NOT EXISTS "${schema}"`);
    await dataSource.query(`SET search_path TO "${schema}"`);
    await dataSource.runMigrations();

    redisClient = new Redis({
      host: process.env.TEST_REDIS_HOST,
      port: Number(process.env.TEST_REDIS_PORT),
    });

    service = new NachDebitService(
      dataSource.getRepository(DebitRequest),
      new DebitCacheService(redisClient),
    );
  }, 60_000);

  afterAll(async () => {
    await redisClient.quit();
    await dataSource.query(`DROP SCHEMA "${schema}" CASCADE`);
    await dataSource.destroy();
  });

  afterEach(async () => {
    await dataSource.query('TRUNCATE debit_request RESTART IDENTITY CASCADE');
    await redisClient.flushdb();
  });

  // Tests — assert on real DB state and real Redis state
  it('persists a debit request and caches its processing state', async () => { ... });
  it('marks a debit as FAILED after 3 retries and evicts the cache entry', async () => { ... });
  it('is idempotent — duplicate debit requests with the same idempotency key are deduplicated', async () => { ... });
});
```

**Layer 4 — CI configuration:**
```yaml
# .github/workflows/integration-tests.yml
- name: Run integration tests
  run: npm run test:integration
  env:
    TESTCONTAINERS_RYUK_DISABLED: false
    DOCKER_BUILDKIT: 1
```

The complete strategy gives: full data isolation via schema-per-worker (PostgreSQL) and `flushdb` (Redis), real engine behaviour for both stores, parallel execution with no port conflicts, automatic cleanup via Ryuk, and a clear separation between unit tests (fast, mocked) and integration tests (real containers, slower, run separately).
