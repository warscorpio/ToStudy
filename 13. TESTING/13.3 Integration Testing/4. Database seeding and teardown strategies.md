# Database Seeding & Teardown Strategies — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is database seeding in the context of testing, and why is it necessary?**
A: Database seeding is the act of populating a database with a known, controlled set of data before tests run. It is necessary because most application logic is data-dependent — a query that fetches orders, a validation that checks for duplicate emails, a fraud rule that fires above a transaction threshold — and the test must control what the DB contains to make assertions deterministic.

Without seeding, tests share whatever data happens to be in the database, which means:
- Test outcomes depend on execution order (earlier tests leave data that later tests see).
- Tests interfere with each other when run in parallel (two tests insert a row with the same unique key).
- A "clean" environment on one machine differs from another, so tests pass locally and fail in CI.

Seeding solves all three by giving each test (or test suite) a private, predictable starting state. The corollary is that seeding is always paired with **teardown** — a strategy for removing or resetting that state so the next test starts equally clean.

**Q2. What is database teardown, and what are the three fundamental strategies for it?**
A: Teardown is the act of undoing the state changes a test made to the database so the next test inherits a clean slate. The three fundamental strategies differ in speed, isolation strength, and implementation complexity:

- **Transaction rollback** — wrap each test in a database transaction; roll it back at the end instead of committing. The DB returns to exactly its pre-test state, atomically. Fast (no actual writes persist), strong isolation, but requires tests to share a single connection and cannot test code that commits its own transactions.
- **Truncation** — after each test (or suite), issue `TRUNCATE` (or `DELETE FROM`) on all relevant tables. Slower than rollback (real writes must be undone), but works when tests span multiple connections or commit their own transactions.
- **Database recreation** — drop and recreate the entire database (or schema) between test runs. The strongest isolation — completely fresh state — but the slowest. Practical per-suite, not per-test.

Most production test suites combine strategies: transaction rollback for unit-level DB tests, truncation for integration tests that commit transactions, and recreation for E2E test runs.

**Q3. What is the difference between seeding for development, seeding for testing, and seeding for staging?**
A: The three share a mechanism (inserting rows into a database) but differ fundamentally in intent, data volume, and lifecycle:

| Dimension | Development seed | Test seed | Staging seed |
|--|--|--|--|
| **Purpose** | Realistic dataset for local exploration and UI work | Minimal, controlled data for specific test assertions | Production-representative volume for performance and UAT |
| **Volume** | Medium (enough to look realistic) | Minimal (exactly what the test needs, no more) | Large (mirrors production cardinality) |
| **Determinism** | Not required — variety is desirable | Required — same data every run | Semi-deterministic — refreshed from prod snapshots |
| **Lifecycle** | Seeded once, manually refreshed | Seeded and torn down per test/suite | Refreshed on a schedule (nightly, weekly) |
| **Sensitive data** | Fake data | Fake data | Anonymised production data or synthetic data |
| **Owner** | Developer tooling / `npm run db:seed` | Test framework lifecycle hooks | DevOps / CI pipeline |

Conflating these causes real problems: using a staging-style large seed in unit tests makes tests slow; using a test-style minimal seed in development makes the UI look empty; using real production data in any test environment is a compliance and security problem.

**Q4. What is a fixture, and how does it relate to seeding?**
A: A fixture is a piece of pre-defined data used as a test's starting state — the specific records that must exist in the database before the test logic runs. Seeding is the act of loading fixtures into the database.

Fixtures come in three forms:
- **Static fixture files** — JSON, YAML, or SQL files checked into the repository. Simple and version-controlled, but brittle: they drift from the schema as columns are added or renamed.
- **Factory functions** — code that generates fixture data programmatically, accepting overrides for the fields the test cares about. Flexible, maintainable, and schema-change-resilient.
- **Builder pattern** — a fluent API that constructs fixture graphs (entities and their relationships) declaratively. The most ergonomic for complex relational data.

Static files are appropriate for small, stable reference data (countries, currency codes, permission types). Factory functions are the right choice for most application entities — they keep tests readable by expressing only the fields that matter for a given scenario.

**Q5. What properties must a seeding and teardown strategy have to support a reliable test suite?**
A: Five properties, in order of importance:

- **Deterministic** — the same test always starts with the same DB state, regardless of what other tests ran before it or in parallel. Non-determinism is the root cause of flaky tests.
- **Isolated** — one test's writes cannot affect another test's reads. Achieved by rollback, per-test schemas, or strict truncation ordering.
- **Fast** — teardown must be cheap enough to run between every test without making the suite slow. Transaction rollback is microseconds; full DB recreation is seconds. Choose accordingly per test layer.
- **Complete** — teardown must remove all state the test created — not just the primary table, but cascade effects (audit logs, event records, foreign-keyed children). Incomplete teardown accumulates state across tests.
- **Honest** — the seeded state must accurately represent the scenarios the test claims to cover. A test that seeds a "premium user" but doesn't set the fields that make the user premium is testing the wrong thing.

## Section 2: Seeding Strategies

**Q6. What is the factory pattern for test data, and how do you implement it in TypeScript?**
A: A factory is a function that creates a valid entity with sensible defaults for every field, accepting an optional partial override for the fields the test cares about. The test only specifies what is relevant; everything else is generated:

```typescript
// src/test/factories/user.factory.ts
import { v4 as uuidv4 } from 'uuid';
import type { User } from '../../entities/user.entity';

let sequence = 0;

export const buildUser = (overrides: Partial<User> = {}): User => {
  sequence++;
  return {
    id: uuidv4(),
    email: `user-${sequence}@example.com`,    // unique by default — avoids UNIQUE constraint violations
    name: `Test User ${sequence}`,
    role: 'customer',
    isVerified: true,
    createdAt: new Date('2024-01-01T00:00:00Z'),
    updatedAt: new Date('2024-01-01T00:00:00Z'),
    ...overrides,                               // caller overrides only what matters
  };
};

// Variant: also inserts into the DB and returns the persisted entity
export const createUser = async (
  db: DataSource,
  overrides: Partial<User> = {}
): Promise<User> => {
  const user = buildUser(overrides);
  return db.getRepository(User).save(user);
};
```

Usage in a test:
```typescript
test('admin can deactivate any user', async () => {
  const admin = await createUser(db, { role: 'admin' });
  const target = await createUser(db, { role: 'customer', isVerified: true });

  await deactivateUser(admin, target.id);

  const updated = await db.getRepository(User).findOneBy({ id: target.id });
  expect(updated?.isVerified).toBe(false);
});
```

The test is self-documenting: the only fields specified are the ones that affect the test outcome. Everything else is boilerplate hidden in the factory.

**Q7. How do you handle relational data in factories — seeding entities with foreign key dependencies?**
A: Factories for entities with FK relationships accept or create their dependencies automatically:

```typescript
// src/test/factories/order.factory.ts
import { buildUser, createUser } from './user.factory';
import type { Order } from '../../entities/order.entity';

export const buildOrder = (overrides: Partial<Order> & { userId?: string } = {}): Order => {
  return {
    id: uuidv4(),
    userId: overrides.userId ?? buildUser().id,   // generates a placeholder if not provided
    amount: 1000,
    currency: 'INR',
    status: 'pending',
    createdAt: new Date('2024-01-15T00:00:00Z'),
    ...overrides,
  };
};

// The create variant handles the dependency graph automatically
export const createOrder = async (
  db: DataSource,
  overrides: Partial<Order> & { userId?: string } = {}
): Promise<Order> => {
  // If caller didn't provide a userId, create a user first
  const userId = overrides.userId ?? (await createUser(db)).id;
  const order = buildOrder({ ...overrides, userId });
  return db.getRepository(Order).save(order);
};
```

Usage:
```typescript
test('refund reduces order balance', async () => {
  // Creates a user automatically, then an order for that user
  const order = await createOrder(db, { amount: 5000, status: 'confirmed' });

  await processRefund(order.id, 2000);

  const updated = await db.getRepository(Order).findOneBy({ id: order.id });
  expect(updated?.amount).toBe(3000);
});

test('user can view their own orders', async () => {
  const user = await createUser(db);
  // Attach the order to a specific user by passing userId
  await createOrder(db, { userId: user.id, status: 'confirmed' });
  await createOrder(db, { userId: user.id, status: 'pending' });

  const orders = await getOrdersForUser(user.id);
  expect(orders).toHaveLength(2);
});
```

The key design principle: the factory creates the minimum dependency graph needed to satisfy FK constraints, but the test controls the exact fields that affect the assertion.

**Q8. What are static fixture files, and when are they appropriate over factories?**
A: Static fixture files are JSON, YAML, or SQL files checked into the repository that define a fixed dataset loaded before tests run. They are appropriate for:

- **Reference / lookup data** — currency codes, country names, permission types, product categories. This data is stable (rarely changes), small, and shared across many tests.
- **Migration testing** — testing that a specific migration transforms a known input schema into the correct output schema. The "before" state is a static fixture representing a known DB state.
- **Snapshot-style regression tests** — verifying that a complex query against a known dataset returns the expected result set. The fixture is the ground truth.

They are inappropriate when:
- The data changes as the schema evolves (fixtures drift silently — a new `NOT NULL` column breaks every fixture that omits it).
- Different tests need different variants of the same entity (factories handle this naturally; fixtures require multiple files or templating).
- The fixture set grows large (hundreds of rows) — becomes hard to reason about which test depends on which rows.

```typescript
// src/test/fixtures/currencies.json
[
  { "code": "INR", "name": "Indian Rupee", "symbol": "₹", "decimals": 2 },
  { "code": "USD", "name": "US Dollar", "symbol": "$", "decimals": 2 },
  { "code": "EUR", "name": "Euro", "symbol": "€", "decimals": 2 }
]

// src/test/helpers/loadFixtures.ts
export const loadCurrencies = async (db: DataSource) => {
  const currencies = await import('../fixtures/currencies.json');
  await db.getRepository(Currency).insert(currencies);
};
```

**Q9. What is the "builder pattern" for test data, and how does it improve on plain factory functions?**
A: The builder pattern wraps factory logic in a fluent API that makes complex entity construction readable and composable:

```typescript
// src/test/builders/user.builder.ts
export class UserBuilder {
  private data: Partial<User> = {};
  private db: DataSource;

  constructor(db: DataSource) {
    this.db = db;
  }

  asAdmin(): this {
    this.data.role = 'admin';
    this.data.permissions = ['read', 'write', 'delete'];
    return this;
  }

  asPremium(): this {
    this.data.tier = 'premium';
    this.data.isVerified = true;
    this.data.kycStatus = 'verified';
    return this;
  }

  withEmail(email: string): this {
    this.data.email = email;
    return this;
  }

  suspended(): this {
    this.data.status = 'suspended';
    this.data.suspendedAt = new Date();
    return this;
  }

  async build(): Promise<User> {
    return createUser(this.db, this.data);
  }
}

// Usage — reads like a specification, not a config object
test('suspended premium user cannot place orders', async () => {
  const user = await new UserBuilder(db)
    .asPremium()
    .suspended()
    .build();

  await expect(placeOrder(user.id, cart)).rejects.toThrow('Account suspended');
});
```

The builder pattern is especially valuable for entities with many interrelated fields that must be set consistently — setting `tier: 'premium'` in isolation without `kycStatus: 'verified'` might create an invalid state. The builder's named methods (`asPremium()`) encapsulate the correct combination.

## Section 3: Teardown Strategies

**Q10. How does transaction rollback teardown work, and what are its exact limitations?**
A: In rollback-based teardown, the test framework opens a database transaction at the start of each test, runs all test logic inside it, then rolls it back at the end — regardless of whether the test passed or failed. The DB is returned to its pre-test state with zero net writes:

```typescript
// TypeORM + Jest example
let dataSource: DataSource;
let queryRunner: QueryRunner;

beforeAll(async () => {
  dataSource = await AppDataSource.initialize();
  await runMigrations(dataSource); // schema is set up once
});

beforeEach(async () => {
  queryRunner = dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();
});

afterEach(async () => {
  await queryRunner.rollbackTransaction(); // undo everything the test did
  await queryRunner.release();
});

afterAll(async () => {
  await dataSource.destroy();
});
```

**Limitations — where rollback teardown breaks down:**

1. **The code under test commits its own transaction** — if `placeOrder()` internally opens and commits a transaction, the rollback of the outer test transaction doesn't undo it. The committed write persists.

2. **Multiple connections** — if the service opens a second DB connection (e.g., through a connection pool), writes on that connection are not visible to the rollback on the test's connection until committed, and the rollback on the test connection doesn't affect the other connection's writes.

3. **DDL statements** — `CREATE TABLE`, `ALTER TABLE`, `TRUNCATE` auto-commit in most databases (PostgreSQL included), breaking the outer transaction.

4. **External side effects** — the rollback undoes DB state but not any side effects triggered by the DB write — events published to a queue, emails sent, cache entries written. These must be cleaned up separately.

When any of these apply, switch to truncation-based teardown.

**Q11. How does truncation-based teardown work, and how do you handle foreign key constraints during truncation?**
A: Truncation teardown deletes all rows from relevant tables after each test (or suite). Unlike rollback, it works regardless of how many transactions or connections the test code opened:

```typescript
// src/test/helpers/truncate.ts
import { DataSource } from 'typeorm';

// Tables in dependency order — children before parents (FK constraints)
const TABLE_ORDER = [
  'order_items',
  'orders',
  'payment_intents',
  'audit_logs',
  'sessions',
  'users',
  'currencies',   // reference data — may want to keep this
];

export const truncateAll = async (db: DataSource): Promise<void> => {
  const runner = db.createQueryRunner();
  await runner.connect();

  try {
    // Disable FK checks during truncation (PostgreSQL)
    await runner.query('SET session_replication_role = replica');

    await Promise.all(
      TABLE_ORDER.map(table => runner.query(`TRUNCATE TABLE "${table}" CASCADE`))
    );

    await runner.query('SET session_replication_role = DEFAULT');
  } finally {
    await runner.release();
  }
};
```

**Foreign key handling approaches:**

- **`CASCADE` on `TRUNCATE`** — PostgreSQL's `TRUNCATE ... CASCADE` automatically truncates all dependent tables in one statement. Convenient, but can truncate tables you didn't intend to clear if FK relationships aren't well understood.
- **Explicit ordering** — truncate child tables before parent tables, in FK dependency order. More verbose but explicit and safe.
- **Disable FK checks temporarily** — `SET session_replication_role = replica` in PostgreSQL (or `SET FOREIGN_KEY_CHECKS = 0` in MySQL) during the truncation window. Fast and order-independent, but must be re-enabled reliably (use `try/finally`).
- **`DELETE` instead of `TRUNCATE`** — `DELETE FROM table` respects FK constraints and triggers, rolls back with the transaction, but is slower. Useful when the test is wrapped in a transaction that handles cleanup.

**Q12. What is per-test schema isolation, and when is it worth the overhead?**
A: Per-test schema isolation creates a separate PostgreSQL schema (a namespace within the same database) for each test or test worker. Tests run entirely within their own schema and have zero chance of interfering with each other, enabling full parallelism:

```typescript
// src/test/helpers/schemaIsolation.ts
import { DataSource } from 'typeorm';
import { v4 as uuidv4 } from 'uuid';

export const createIsolatedSchema = async (
  baseDataSource: DataSource
): Promise<{ schema: string; db: DataSource }> => {
  const schema = `test_${uuidv4().replace(/-/g, '_')}`;

  // Create the schema
  await baseDataSource.query(`CREATE SCHEMA "${schema}"`);

  // Create a new DataSource scoped to this schema
  const db = new DataSource({
    ...baseDataSource.options,
    schema,                        // all tables created/queried in this schema
  });
  await db.initialize();
  await db.runMigrations();        // apply full schema within the isolated namespace

  return { schema, db };
};

export const dropIsolatedSchema = async (
  baseDataSource: DataSource,
  schema: string
): Promise<void> => {
  await baseDataSource.query(`DROP SCHEMA "${schema}" CASCADE`);
};
```

Worth the overhead when:
- Tests run in parallel (Jest workers, parallel CI jobs) and share a database — schema isolation is the only safe way to fully parallelize without interference.
- The test suite exercises code that uses advisory locks, sequences, or other schema-level state that can't be rolled back.
- Flakiness from shared state is already a documented problem and simpler strategies haven't resolved it.

Not worth it when:
- Tests run serially (rollback or truncation is sufficient and faster).
- Schema creation and migration take longer than the tests themselves — the overhead exceeds the benefit.
- The database doesn't support schema namespacing (MySQL's schema model differs from PostgreSQL's).

**Q13. What is Testcontainers, and how does it change the teardown story?**
A: Testcontainers is a library that spins up real Docker containers (PostgreSQL, MySQL, Redis, Kafka, etc.) programmatically from within the test process. The container is created at the start of the test run and destroyed at the end — the teardown story becomes "kill the container":

```typescript
// src/test/setup/database.ts
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { DataSource } from 'typeorm';

let container: StartedPostgreSqlContainer;
let dataSource: DataSource;

export const startTestDatabase = async (): Promise<DataSource> => {
  container = await new PostgreSqlContainer('postgres:16-alpine')
    .withDatabase('testdb')
    .withUsername('test')
    .withPassword('test')
    .start();

  dataSource = new DataSource({
    type: 'postgres',
    host: container.getHost(),
    port: container.getMappedPort(5432),
    database: container.getDatabase(),
    username: container.getUsername(),
    password: container.getPassword(),
    entities: ['src/entities/**/*.ts'],
    synchronize: true,           // or runMigrations() for production parity
  });

  await dataSource.initialize();
  return dataSource;
};

export const stopTestDatabase = async (): Promise<void> => {
  await dataSource?.destroy();
  await container?.stop();
};
```

```typescript
// src/test/integration/payments.spec.ts
import { startTestDatabase, stopTestDatabase } from '../setup/database';

let db: DataSource;

beforeAll(async () => { db = await startTestDatabase(); }, 60_000); // allow container startup time
afterAll(async () => { await stopTestDatabase(); });
afterEach(async () => { await truncateAll(db); }); // per-test cleanup within the container
```

The teardown model: the container lifetime is per-suite (start once in `beforeAll`, stop in `afterAll`); per-test cleanup inside the container is still truncation or rollback. The container approach eliminates environment-specific DB config and guarantees the test runs against the exact PostgreSQL version as production.

## Section 4: Seeding Patterns for Specific Scenarios

**Q14. How do you seed and tear down data for tests that verify audit logs or event sourcing?**
A: Audit logs and event stores are append-only — every write is intentional and permanent. Teardown must remove the audit records created during a test, but must not remove pre-existing records that establish the historical baseline:

```typescript
// Pattern: record a "high-water mark" before the test, clean up after
let auditBaselineCount: number;

beforeEach(async () => {
  // Seed prerequisite state
  await createUser(db, { id: 'user-1', role: 'admin' });
  // Record how many audit rows exist before the test adds any
  auditBaselineCount = await db.getRepository(AuditLog).count();
});

afterEach(async () => {
  // Remove only the audit rows created by this test
  const currentCount = await db.getRepository(AuditLog).count();
  if (currentCount > auditBaselineCount) {
    // Delete the N most recent rows
    await db.query(`
      DELETE FROM audit_logs
      WHERE id IN (
        SELECT id FROM audit_logs
        ORDER BY created_at DESC
        LIMIT $1
      )
    `, [currentCount - auditBaselineCount]);
  }
  await truncateAll(db); // clean up other tables
});

test('admin action is recorded in audit log', async () => {
  await deactivateUser('admin-1', 'user-1');

  const logs = await db.getRepository(AuditLog).find({
    where: { actorId: 'admin-1', action: 'DEACTIVATE_USER' },
    order: { createdAt: 'DESC' },
  });

  expect(logs).toHaveLength(1);
  expect(logs[0].targetId).toBe('user-1');
});
```

For event sourcing systems, the same principle applies: record the event stream position before the test (`lastEventId`) and clean up events with ID > lastEventId in teardown. Alternatively, give each test a unique aggregate ID so events are naturally isolated by aggregate.

**Q15. How do you seed data for multi-tenant applications where rows are scoped to a tenant?**
A: Multi-tenant data requires that every seeded entity includes a `tenantId`, and teardown must be scoped to the tenant used in the test — not delete other tenants' data:

```typescript
// src/test/factories/tenant.factory.ts
let tenantSequence = 0;

export const createTestTenant = async (db: DataSource): Promise<Tenant> => {
  tenantSequence++;
  return db.getRepository(Tenant).save({
    id: uuidv4(),
    slug: `test-tenant-${tenantSequence}`,
    name: `Test Tenant ${tenantSequence}`,
    plan: 'basic',
  });
};

// All factories accept tenantId
export const createTenantUser = async (
  db: DataSource,
  tenantId: string,
  overrides: Partial<User> = {}
): Promise<User> => {
  return createUser(db, { ...overrides, tenantId });
};
```

```typescript
// Teardown: delete only data belonging to the test tenant
afterEach(async () => {
  if (testTenant) {
    // Delete in FK dependency order within the tenant
    await db.query(`DELETE FROM orders WHERE tenant_id = $1`, [testTenant.id]);
    await db.query(`DELETE FROM users WHERE tenant_id = $1`, [testTenant.id]);
    await db.query(`DELETE FROM tenants WHERE id = $1`, [testTenant.id]);
  }
});
```

An alternative is to use schema-per-tenant (each tenant has its own PostgreSQL schema) — then the teardown is simply `DROP SCHEMA test_tenant_xyz CASCADE`, which is clean and complete regardless of FK complexity.

**Q16. How do you handle seeding for tests that verify database constraints — UNIQUE, NOT NULL, CHECK?**
A: Constraint tests intentionally try to violate the constraint and assert the DB rejects the write. The seeding must establish the state the constraint protects:

```typescript
// Testing UNIQUE constraint on email
test('rejects duplicate email at DB level', async () => {
  // Seed: create the first user with a specific email
  await createUser(db, { email: 'duplicate@example.com' });

  // Act: attempt to insert a second user with the same email
  await expect(
    db.getRepository(User).save(buildUser({ email: 'duplicate@example.com' }))
  ).rejects.toThrow(/duplicate key value violates unique constraint/);
});

// Testing CHECK constraint on amount
test('rejects negative transaction amount at DB level', async () => {
  const user = await createUser(db);
  await expect(
    db.getRepository(Transaction).save({
      userId: user.id,
      amount: -500,      // violates CHECK (amount > 0)
      currency: 'INR',
    })
  ).rejects.toThrow(/violates check constraint/);
});
```

Key design decision: constraint tests should reach the DB directly (bypassing application-layer validation) to verify the constraint exists in the schema, not just in the application code. A constraint that is enforced only in TypeScript is not enforced if someone runs a raw SQL query, a migration script, or a different service against the same DB.

## Section 5: Tradeoffs, Anti-patterns & Best Practices

**Q17. What is "test data pollution," and what are its symptoms?**
A: Test data pollution occurs when data created by one test is visible to another test that didn't expect it. It is the primary cause of order-dependent test failures — tests that pass alone but fail when run as a suite, or that pass in one order and fail in another.

Symptoms:
- **"Works locally, fails in CI"** — CI runs tests in a different order or in parallel; pollution that was harmless in local serial execution causes interference.
- **"Fails on second run but passes on first"** — a test leaves rows in the DB; the next run finds unexpected rows that trigger a UNIQUE violation or a wrong count assertion.
- **Flaky count assertions** — `expect(await getUserCount()).toBe(3)` passes when the test runs first (only its 3 users exist) and fails when another test that also creates users ran before it.
- **Tests that pass individually but fail together** — the classic sign of shared mutable state between tests.

Detection: run the suite with `--randomize` (randomise test order). Failures that appear only in certain orderings are pollution symptoms. Run individual tests in isolation (`jest --testNamePattern="specific test"`) — if an isolated test fails but the suite passes, the test depends on state created by earlier tests.

**Q18. What are the most common seeding anti-patterns, and what is the fix for each?**
A:

**Anti-pattern 1 — Shared global seed run once before all tests**
```typescript
// ❌ One seed run for the entire suite — tests share all this data
beforeAll(async () => {
  await seedDatabase(); // inserts 50 users, 200 orders, etc.
});
```
Problem: any test that modifies this data affects every test that reads it. Fix: seed per-test or per-suite, with teardown between each.

**Anti-pattern 2 — Hardcoded IDs in fixtures**
```typescript
// ❌ Every test that touches user 1 interferes with every other such test
const user = await db.getRepository(User).findOneBy({ id: 1 });
```
Problem: hardcoded IDs create hidden coupling. Test A modifies user 1; Test B reads user 1 and sees unexpected state. Fix: generate fresh IDs per test using factories; never seed with predictable integer IDs unless the test specifically tests ID-dependent behavior.

**Anti-pattern 3 — Seeding more data than the test needs**
```typescript
// ❌ Seeds 20 orders to "be realistic" but the test only cares about status
await seedOrders(20, { userId: user.id });
const activeOrders = await getActiveOrders(user.id);
expect(activeOrders.length).toBeGreaterThan(0); // vague assertion on noisy data
```
Problem: excess data makes assertions vague and hides intent. Fix: seed the minimum — exactly the rows that affect the assertion.

**Anti-pattern 4 — Relying on seed order for FK resolution**
```typescript
// ❌ Assumes users are seeded before orders without making it explicit
await seedOrders(); // will fail if users table is empty
await seedUsers();
```
Fix: make dependency explicit in factory functions (see Q7). The factory creates dependencies automatically if not provided.

**Anti-pattern 5 — Not seeding the "empty state"**
```typescript
// ❌ This test only works if no other test has left users in the DB
test('returns empty array when no users exist', async () => {
  const users = await getAllUsers();
  expect(users).toHaveLength(0); // fails if another test created a user
});
```
Fix: ensure teardown is complete before each test (rollback or truncation), then the empty state is guaranteed.

**Q19. How do you seed data for performance / load tests, and how does that differ from unit test seeding?**
A: Performance test seeding has the opposite goals from unit test seeding:

| Dimension | Unit / integration test seed | Performance test seed |
|--|--|--|
| **Volume** | Minimal — exactly what the test needs | Large — mirrors production cardinality |
| **Speed of seeding** | Fast is fine (a few inserts) | Must be fast (bulk insert thousands of rows) |
| **Determinism** | Exact values matter | Distribution matters, exact values don't |
| **Teardown** | Complete, per test | Typically not torn down between runs |
| **Realism** | Structural correctness | Statistical realism (realistic value distributions) |

Bulk seeding strategies for performance tests:
```typescript
// Batch insert via COPY (PostgreSQL) — fastest option
export const bulkSeedOrders = async (
  db: DataSource,
  count: number,
  userId: string
): Promise<void> => {
  // Generate in-memory, insert in batches of 1000
  const batchSize = 1000;
  for (let i = 0; i < count; i += batchSize) {
    const batch = Array.from({ length: Math.min(batchSize, count - i) }, (_, j) => ({
      id: uuidv4(),
      userId,
      amount: Math.floor(Math.random() * 100000) + 100,
      currency: 'INR',
      status: ['pending', 'confirmed', 'failed'][j % 3],
      createdAt: new Date(Date.now() - Math.random() * 30 * 24 * 60 * 60 * 1000),
    }));

    await db.getRepository(Order).insert(batch); // bulk insert, not save()
  }
};
```

For very large datasets (millions of rows), use PostgreSQL's `COPY` command via a CSV pipe — it bypasses ORM overhead and is 10–100× faster than batched `INSERT`.

**Q20. What is the `--forceExit` Jest flag, and why is it a sign of a teardown problem?**
A: `--forceExit` tells Jest to forcibly terminate the Node.js process after all tests complete, even if there are open handles (DB connections, HTTP servers, timers). It is a commonly added "fix" when Jest hangs after the test suite finishes.

Why it is a sign of a teardown problem, not a fix:
- The open handle is almost always an unclean teardown — a DB connection pool that was never destroyed, a Testcontainer that wasn't stopped, an HTTP server that wasn't closed.
- `--forceExit` masks the problem: the test suite finishes, but resources are leaked in every run. In CI, this means Docker containers may not be cleaned up, DB connections may not be released, and port conflicts may accumulate.

Finding the real issue:
```bash
# Jest's built-in leak detector
npx jest --detectOpenHandles
```

This prints which handles (timers, network sockets, DB connections) are preventing Jest from exiting cleanly. The fix is always to close those handles in `afterAll`:

```typescript
afterAll(async () => {
  await dataSource.destroy();    // close DB connection pool
  await redisClient.quit();      // close Redis connection
  await app.close();             // close HTTP server
  await container.stop();        // stop Testcontainer
});
```

Replace `--forceExit` with `--detectOpenHandles` during debugging, fix the actual leak, then remove both flags from the production CI command.

## Section 6: Scenario / System Design Style Questions

**Q21. "Our integration test suite takes 12 minutes and is getting slower as we add tests. DB seeding and teardown are identified as the bottleneck. How do you fix it?"**
A: A 12-minute integration suite with seeding as the bottleneck is typically one of three problems:

**Problem A — Per-test full truncation on a large schema**
Truncating 40 tables after every test is slow. Fix: switch to transaction rollback for tests whose code doesn't commit its own transactions (the majority). Reserve truncation for the subset that commits. Profile to confirm: add timing to `afterEach` hooks.

**Problem B — Serial test execution across workers**
If tests run on a single Jest worker, seeding and teardown are sequential. Fix: enable parallel workers (`--maxWorkers=4`) with schema-per-worker isolation. Each worker gets its own PostgreSQL schema, initialized once:

```typescript
// jest.config.ts
export default {
  maxWorkers: 4,
  globalSetup: './src/test/setup/globalSetup.ts',   // create 4 schemas
  globalTeardown: './src/test/setup/globalTeardown.ts', // drop 4 schemas
};
```

**Problem C — Redundant migrations per test file**
If each test file runs migrations from scratch, and migrations are slow (many files), the per-file startup cost dominates. Fix: run migrations once in `globalSetup`, then truncate between tests within the already-migrated schema.

```typescript
// globalSetup.ts — runs once for the entire suite, not per file
export default async () => {
  const db = await createRootDataSource();
  await db.runMigrations();  // once, not per test file
  await db.destroy();
};
```

Combined: rollback for simple tests, parallel workers with schema isolation for integration tests, migrations once in globalSetup. This typically reduces a 12-minute suite to 2–3 minutes.

**Q22. "You're designing the test infrastructure for a payments API that handles UPI, cards, and wallets — each with their own DB tables and FK relationships. How do you design the seeding layer?"**
A: Design the seeding layer in three tiers:

**Tier 1 — Reference data (loaded once, never torn down)**
```typescript
// globalSetup.ts
await loadFixtures(db, [
  'currencies.json',         // INR, USD, EUR
  'paymentMethods.json',     // upi, card, wallet, netbanking
  'banks.json',              // HDFC, SBI, ICICI ...
]);
```
This data is stable, shared, and idempotent — insert with `ON CONFLICT DO NOTHING`.

**Tier 2 — Entity factories (per-test, per-scenario)**
```typescript
// Hierarchy: User → PaymentMethod → Transaction → RefundRequest
// Each factory creates its dependencies if not provided

createUpiPaymentMethod(db, { userId, vpa: 'test@okicici' });
createCardPaymentMethod(db, { userId, last4: '4242', network: 'VISA' });
createWalletAccount(db, { userId, provider: 'paytm', balance: 50000 });

createTransaction(db, {
  userId,
  paymentMethodId,
  amount: 1000,
  currency: 'INR',
  gateway: 'razorpay',
  status: 'captured',
});
```

**Tier 3 — Scenario builders (named, reusable scenarios)**
```typescript
// Encapsulates complex multi-entity scenarios
const scenarios = {
  userWithAllPaymentMethods: async (db: DataSource) => {
    const user = await createUser(db, { kycStatus: 'verified' });
    const upi = await createUpiPaymentMethod(db, { userId: user.id });
    const card = await createCardPaymentMethod(db, { userId: user.id });
    const wallet = await createWalletAccount(db, { userId: user.id, balance: 50000 });
    return { user, upi, card, wallet };
  },

  failedTransactionWithRefundPending: async (db: DataSource) => {
    const { user, card } = await scenarios.userWithAllPaymentMethods(db);
    const transaction = await createTransaction(db, {
      userId: user.id,
      paymentMethodId: card.id,
      status: 'failed',
      gatewayError: 'INSUFFICIENT_FUNDS',
    });
    const refund = await createRefundRequest(db, {
      transactionId: transaction.id,
      status: 'pending',
    });
    return { user, card, transaction, refund };
  },
};

// Test reads like a specification
test('failed transaction refund is processed correctly', async () => {
  const { transaction, refund } = await scenarios.failedTransactionWithRefundPending(db);
  await processRefund(refund.id);
  // assertions...
});
```

**Q23. "A test that verifies KYC document upload leaves files in an S3-compatible bucket even though the DB is rolled back. How do you handle teardown for external side effects?"**
A: DB rollback only undoes database writes — it cannot undo network calls, file uploads, or messages already sent. Handle external side effects with one of three approaches:

**Approach 1 — Mock the external service in unit/integration tests (preferred)**
Replace the real S3 client with a mock or fake in tests. No real uploads occur; nothing to clean up:
```typescript
// src/storage/__mocks__/s3.client.ts
const uploadedFiles = new Map<string, Buffer>();

export const upload = jest.fn(async (key: string, data: Buffer) => {
  uploadedFiles.set(key, data);
  return { key, url: `https://fake-s3/${key}` };
});

export const __getUploadedFiles = () => uploadedFiles;
export const __reset = () => uploadedFiles.clear();
```

**Approach 2 — Use a localstack or MinIO container for integration tests that must test real uploads**
```typescript
// Testcontainers localstack for S3-compatible storage
const localstack = await new LocalstackContainer()
  .withServices(['s3'])
  .start();

// Configure AWS SDK to point to localstack
process.env.AWS_ENDPOINT_URL = localstack.getEndpointUrl();

afterAll(async () => {
  await localstack.stop(); // container destruction deletes all uploaded files
});
```

**Approach 3 — Explicit cleanup registry for E2E tests that use real infrastructure**
```typescript
const uploadedKeys: string[] = [];

afterEach(async () => {
  // Delete all files uploaded during the test
  await Promise.all(
    uploadedKeys.map(key => s3Client.deleteObject({ Bucket: testBucket, Key: key }))
  );
  uploadedKeys.length = 0; // clear the registry
});

// Track uploads during the test
jest.spyOn(s3Client, 'upload').mockImplementation(async (params) => {
  const result = await realS3Client.upload(params);
  uploadedKeys.push(params.Key);
  return result;
});
```

The general principle: prefer mocking external services at the boundary for integration tests; use real services with containerized or test-account infrastructure for E2E tests, with an explicit cleanup registry for teardown.

**Q24. "How do you ensure database seeds stay in sync with schema migrations as the project evolves?"**
A: Schema drift between migrations and seeds is one of the most common long-term maintenance problems in test infrastructure. Defences:

**1 — Run seeds after migrations in the same pipeline**
Never seed before migrating. The seed load always follows the migration run, so the schema is always in the state the seeds expect:
```typescript
// globalSetup.ts
await db.runMigrations();          // apply all pending migrations first
await loadReferenceFixtures(db);   // then seed reference data
```

**2 — Use factories instead of static SQL/JSON for entity seeds**
Static SQL seeds (`INSERT INTO users (id, name, email) VALUES (...)`) break the moment a `NOT NULL` column is added to `users`. Factory functions that use the ORM's `save()` method fail fast with a type error at the TypeScript level when a required field is missing — earlier feedback than a runtime SQL error.

**3 — Run the test suite's `beforeAll` in CI as a smoke test**
If the migration + seed pipeline is part of `globalSetup`, any incompatibility between the latest migration and the seed data causes `globalSetup` to throw — failing CI before any test runs. This makes the incompatibility immediately visible rather than hiding in a specific test.

**4 — Seed reference data idempotently**
Reference data seeds should use `INSERT ... ON CONFLICT DO NOTHING` or an ORM equivalent. This makes them safe to run multiple times (after each migration), not just once:
```typescript
await db.getRepository(Currency).upsert(currencies, ['code']);
```

**5 — Review factory files in schema-changing PRs**
Add a PR template checklist item: "If this PR adds/removes/renames a database column, update the affected factory files." Factories are source code — they should be reviewed alongside migration files.

**Q25. "Walk me through the complete test database lifecycle for a NestJS + TypeORM + PostgreSQL project — from `jest globalSetup` to individual test teardown."**
A: A production-ready lifecycle with Testcontainers:

```
jest globalSetup
  └── Start PostgreSQL Testcontainer (port mapped to random host port)
  └── Store connection config in process.env (TEST_DB_HOST, TEST_DB_PORT, ...)
  └── Run all migrations once against the container

Per test FILE (beforeAll / afterAll):
  └── beforeAll: DataSource.initialize() — connect to the running container
  └── beforeAll: loadReferenceFixtures() — seed currencies, paymentMethods, banks
  └── afterAll: DataSource.destroy() — release connections

Per TEST (beforeEach / afterEach):
  └── beforeEach: begin a transaction on a dedicated QueryRunner
  └── [test runs — all DB operations go through this QueryRunner's transaction
      OR: test logic uses the shared DataSource (for code that commits its own txns)]
  └── afterEach: rollback the transaction (for non-committing tests)
           OR: truncateAll() (for tests whose code commits)
  └── afterEach: reset all jest mocks (jest.resetAllMocks())

jest globalTeardown
  └── Stop and destroy the Testcontainer
      (all data, schemas, and files in the container are gone)
```

In code:

```typescript
// jest.config.ts
export default {
  globalSetup: './src/test/setup/globalSetup.ts',
  globalTeardown: './src/test/setup/globalTeardown.ts',
  setupFilesAfterFramework: ['./src/test/setup/testSetup.ts'],
  testEnvironment: 'node',
  resetMocks: true,
};

// globalSetup.ts
import { PostgreSqlContainer } from '@testcontainers/postgresql';
export default async () => {
  const container = await new PostgreSqlContainer('postgres:16-alpine').start();
  process.env.TEST_DB_HOST = container.getHost();
  process.env.TEST_DB_PORT = String(container.getMappedPort(5432));
  process.env.TEST_DB_NAME = container.getDatabase();
  process.env.TEST_DB_USER = container.getUsername();
  process.env.TEST_DB_PASS = container.getPassword();
  process.env.TEST_CONTAINER_ID = container.getId(); // for globalTeardown to stop it

  const db = await initDataSource();
  await db.runMigrations();
  await db.destroy();
};

// globalTeardown.ts
import { DockerContainer } from 'testcontainers';
export default async () => {
  const container = new DockerContainer(process.env.TEST_CONTAINER_ID!);
  await container.stop();
};

// testSetup.ts (runs before each test file)
import { initDataSource } from './dataSource';
import { loadReferenceFixtures } from './fixtures';

let db: DataSource;

beforeAll(async () => {
  db = await initDataSource();
  await loadReferenceFixtures(db);
  // expose db to tests via a module-level export or DI
});

afterAll(async () => {
  await db.destroy();
});

afterEach(async () => {
  await truncateAll(db); // or rollback — depending on test type
});
```

This lifecycle gives: full environment parity (real PostgreSQL, same version as production), complete isolation (container destroyed after the suite), fast per-test cleanup (truncation inside the long-lived container), and zero configuration drift (connection strings are injected by the container at runtime, not hardcoded).

## Quick Reference Table

| Strategy | Speed | Isolation | Works with multi-connection? | Works when code commits own txn? |
|--|--|--|--|--|
| **Transaction rollback** | Fastest (µs) | Strong | No — single connection | No |
| **Truncation** | Fast (ms) | Strong | Yes | Yes |
| **Schema-per-test** | Medium (schema create + migrate) | Strongest | Yes | Yes |
| **DB recreation** | Slowest (seconds) | Strongest | Yes | Yes |
| **Testcontainer (per suite)** | Medium startup, fast per-test | Complete after suite | Yes | Yes |

| Seeding pattern | Best for | Avoid when |
|--|--|--|
| **Factory functions** | Most application entities | Never — prefer over static files |
| **Static fixture files** | Reference/lookup data, migration tests | Entity data that changes with schema |
| **Builder pattern** | Complex relational graphs, named scenarios | Simple single-entity setup |
| **Bulk insert / COPY** | Performance test seeding | Unit/integration test seeding (overkill) |
| **Scenario builders** | Reusable named multi-entity states | One-off single-test scenarios |

The strongest answers connect seeding strategy to the test layer it serves (rollback for unit-adjacent DB tests, Testcontainers for full integration tests), demonstrate awareness of the common failure modes (pollution, hardcoded IDs, incomplete teardown, `--forceExit` masking leaks), and show that you've designed a factory layer before — one where the test specifies only what it cares about and the factory provides everything else. Have a concrete story about a flaky test that turned out to be a pollution problem, and the truncation or rollback strategy that fixed it.
