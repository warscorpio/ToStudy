# HTTP Integration Testing: `supertest` with Express / NestJS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is HTTP integration testing, and how does it differ from unit testing a controller?**
A: HTTP integration testing exercises the full request-response cycle — routing, middleware, guards, pipes, serialisation, error filters, and the handler — all wired together exactly as they are in production. A unit test of a controller method calls the method directly as a function; an HTTP integration test sends a real HTTP request and asserts on the HTTP response.

The distinction matters because most production bugs don't live in isolated logic — they live at the seams: a `ValidationPipe` that rejects a payload the controller logic never even sees, a guard that silently blocks a route, a response interceptor that transforms the shape the controller returned, a global exception filter that maps an unhandled error to a 500 instead of a 422. Unit tests of the controller miss all of these; HTTP integration tests catch them by exercising the full stack.

The tradeoff: HTTP integration tests are slower than unit tests (they boot the application or at least the HTTP layer) and require more setup (DB seed, auth tokens, module wiring). The right model is the testing pyramid — unit tests for logic, HTTP integration tests for HTTP contract verification, true end-to-end tests sparingly.

**Q2. What is `supertest`, and how does it work under the hood?**
A: `supertest` is a Node.js HTTP assertion library built on top of `superagent`. It accepts an `http.Server` instance (or anything that implements `listen()`) and binds it to an ephemeral port for the duration of the test — no need to pick a port, start a real server, or tear it down manually. Each `request(app)` call opens a connection to the bound server, fires the HTTP request, waits for the response, and closes the connection.

```typescript
import request from "supertest";
import express from "express";

const app = express();
app.get("/ping", (req, res) => res.json({ status: "ok" }));

// supertest binds app to a random port, makes the GET, asserts, closes
const response = await request(app).get("/ping");
// response.status, response.body, response.headers are all available
```

What `supertest` is *not*: a browser, a full end-to-end test runner, or a load generator. It makes real HTTP requests via Node's `http` module — network stack included — but the server runs in the same process as the test. This means no CORS, no TLS, and no cross-process communication overhead — which is exactly what makes it fast and reliable for integration testing.

**Q3. What is the difference between testing an Express app and a NestJS app with `supertest`?**
A: Express is a plain `http.Server` — you pass the `app` instance directly. NestJS wraps Express (or Fastify) inside its own application lifecycle; you need to call `app.init()` before the HTTP server is ready, and access the underlying HTTP adapter to pass to `supertest`:

```typescript
// Express — minimal setup
import express from "express";
const app = express();
// ... register routes, middleware
await request(app).get("/health"); // works immediately

// NestJS — requires full application bootstrap
import { Test, TestingModule } from "@nestjs/testing";
import { INestApplication }    from "@nestjs/common";

let app: INestApplication;
const module: TestingModule = await Test.createTestingModule({
  imports: [AppModule],
}).compile();

app = module.createNestApplication();
app.useGlobalPipes(new ValidationPipe());   // must replicate production config
await app.init();

await request(app.getHttpServer()).get("/health"); // getHttpServer() returns the http.Server
```

The NestJS `TestingModule` is the key difference — it boots the DI container, wires all providers, and optionally allows overriding individual providers with mocks. `getHttpServer()` returns the raw Node `http.Server` that `supertest` needs.

**Q4. What is `app.getHttpServer()` and why must you use it instead of `app` directly in NestJS?**
A: `app` in NestJS is an `INestApplication` instance — it wraps the HTTP adapter but is not itself an `http.Server`. `supertest`'s `request()` function expects something it can call `.address()` on (an `http.Server` or an Express-compatible callable). Passing `app` directly either fails or produces incorrect behaviour because `INestApplication` doesn't implement the Node `http.Server` interface.

`app.getHttpServer()` returns the underlying `http.Server` (when using the Express adapter) or the equivalent for Fastify. This is the object `supertest` needs:

```typescript
// ❌ Wrong — app is INestApplication, not http.Server
await request(app).get("/users");

// ✅ Correct — getHttpServer() returns the raw http.Server
await request(app.getHttpServer()).get("/users");
```

A subtle but important nuance: `getHttpServer()` returns `null` until `app.init()` has been called. Always `await app.init()` before using `getHttpServer()` in tests.

**Q5. Why is test isolation critical in HTTP integration tests, and what are the two main strategies?**
A: HTTP integration tests that share state — DB records, in-memory caches, module-level singletons — produce flaky, order-dependent results: a test passes when run alone but fails when run after another test that left the DB in a different state. At scale, a 200-test integration suite with implicit shared state is effectively untestable.

Two main strategies:

- **Truncate/seed per test** — `beforeEach` deletes all rows in relevant tables and seeds exactly what the test needs. Simple to implement, but slow for large schemas and incompatible with parallel test execution (two workers truncating the same table race).
- **Transaction rollback per test** — each test runs inside a DB transaction that is always rolled back in `afterEach`, leaving the DB exactly as it was. Zero cleanup code, no race conditions, fast. The constraint: the SUT must participate in the same transaction (requires passing the transaction context via DI or AsyncLocalStorage).

The right choice depends on the ORM and whether the SUT can accept an injected transaction. For NestJS + TypeORM, the transaction rollback pattern is achievable with `QueryRunner`; for Prisma, it requires `$transaction` injection. For tests where transaction injection is too invasive, truncate-per-test with `--runInBand` is the pragmatic fallback.

## Section 2: Setting Up Supertest with Express

**Q6. Walk through a complete Express + supertest setup with proper lifecycle management.**
A:

```typescript
// src/app.ts
import express, { Application } from "express";
import { userRouter }            from "./routes/user.routes";
import { errorHandler }          from "./middleware/error.handler";

export function createApp(): Application {
  const app = express();
  app.use(express.json());
  app.use("/v1/users", userRouter);
  app.use(errorHandler);           // global error handler must be last
  return app;
}

// src/routes/user.routes.ts
import { Router }         from "express";
import { UserController } from "../controllers/user.controller";
import { UserService }    from "../services/user.service";
import { UserRepository } from "../repositories/user.repository";
import { db }             from "../db";

export const userRouter = Router();
const repo       = new UserRepository(db);
const service    = new UserService(repo);
const controller = new UserController(service);

userRouter.get("/:id", controller.getById.bind(controller));
userRouter.post("/",   controller.create.bind(controller));
```

```typescript
// src/routes/user.routes.integration.spec.ts
import request          from "supertest";
import { createApp }    from "../../app";
import { db }           from "../../db";
import { Application }  from "express";

describe("User Routes (integration)", () => {
  let app: Application;

  beforeAll(async () => {
    // createApp() is a factory — same function production uses; tests use the same wiring
    app = createApp();
    await db.migrate.latest();     // run migrations on test DB
  });

  afterAll(async () => {
    await db.destroy();            // close DB connection pool
  });

  beforeEach(async () => {
    await db("users").truncate();  // clean slate per test
  });

  describe("GET /v1/users/:id", () => {
    it("should return 200 and the user object when the user exists", async () => {
      // Arrange
      const [userId] = await db("users").insert(
        { name: "Alice", email: "alice@example.com" },
        ["id"]
      );

      // Act
      const response = await request(app)
        .get(`/v1/users/${userId}`)
        .set("Accept", "application/json");

      // Assert
      expect(response.status).toBe(200);
      expect(response.body).toMatchObject({
        id:    userId,
        name:  "Alice",
        email: "alice@example.com",
      });
    });

    it("should return 404 when the user does not exist", async () => {
      const response = await request(app)
        .get("/v1/users/99999")
        .set("Accept", "application/json");

      expect(response.status).toBe(404);
      expect(response.body).toMatchObject({ error: "User not found" });
    });
  });

  describe("POST /v1/users", () => {
    it("should return 201 and the created user with a generated ID", async () => {
      // Arrange
      const payload = { name: "Bob", email: "bob@example.com" };

      // Act
      const response = await request(app)
        .post("/v1/users")
        .send(payload)
        .set("Content-Type", "application/json");

      // Assert
      expect(response.status).toBe(201);
      expect(response.body).toMatchObject({ name: "Bob", email: "bob@example.com" });
      expect(response.body.id).toBeDefined();

      // Assert DB side effect — query directly, not via the API
      const row = await db("users").where({ id: response.body.id }).first();
      expect(row).toBeDefined();
      expect(row.email).toBe("bob@example.com");
    });

    it("should return 422 when the email is missing", async () => {
      const response = await request(app)
        .post("/v1/users")
        .send({ name: "Bob" })           // missing email
        .set("Content-Type", "application/json");

      expect(response.status).toBe(422);
      expect(response.body.errors).toContainEqual(
        expect.objectContaining({ field: "email" })
      );
    });
  });
});
```

Key pattern: `createApp()` is a factory function — the same function the production entry point (`src/main.ts`) calls. Tests use the identical wiring, guaranteeing that the tested behaviour is exactly what runs in production.

**Q7. How do you test Express middleware in isolation with supertest?**
A: Mount the middleware on a minimal test app — only the middleware under test, nothing else. This isolates the middleware's behaviour from routing and other middleware:

```typescript
// src/middleware/rate-limiter.middleware.ts
import rateLimit from "express-rate-limit";

export const rateLimiter = rateLimit({
  windowMs: 60_000,
  max:      5,
  message:  { error: "Too many requests" },
});

// src/middleware/rate-limiter.middleware.spec.ts
import request    from "supertest";
import express    from "express";
import { rateLimiter } from "./rate-limiter.middleware";

describe("rateLimiter middleware", () => {
  const buildTestApp = () => {
    const app = express();
    app.use(rateLimiter);
    app.get("/test", (_req, res) => res.json({ ok: true }));
    return app;
  };

  it("should allow requests under the rate limit", async () => {
    const app = buildTestApp();

    const response = await request(app).get("/test");

    expect(response.status).toBe(200);
    expect(response.headers["x-ratelimit-remaining"]).toBe("4");
  });

  it("should return 429 after exceeding the rate limit", async () => {
    const app = buildTestApp();

    // Make 5 allowed requests
    for (let i = 0; i < 5; i++) {
      await request(app).get("/test");
    }

    // 6th request should be blocked
    const response = await request(app).get("/test");

    expect(response.status).toBe(429);
    expect(response.body).toMatchObject({ error: "Too many requests" });
  });
});
```

Note: `buildTestApp()` is called fresh per test (or per `describe` block) so the rate limit counter starts from zero. This is the Express equivalent of the NestJS `beforeEach` re-initialisation pattern.

## Section 3: Setting Up Supertest with NestJS

**Q8. Walk through a complete NestJS + supertest setup for a controller integration test.**
A:

```typescript
// src/payments/payment.controller.ts
@Controller("v1/payments")
@UseGuards(JwtAuthGuard)
export class PaymentController {
  constructor(private readonly paymentService: PaymentService) {}

  @Post()
  @HttpCode(201)
  async initiatePayment(
    @Body() dto: InitiatePaymentDto,
    @Request() req: AuthenticatedRequest,
  ): Promise<PaymentResponseDto> {
    return this.paymentService.initiate(dto, req.user.id);
  }

  @Get(":txnId")
  async getPayment(@Param("txnId") txnId: string): Promise<PaymentResponseDto> {
    return this.paymentService.findByTxnId(txnId);
  }
}

import { JwtAuthGuard }          from "../auth/jwt-auth.guard";
import { getRepositoryToken }    from "@nestjs/typeorm";
import { Payment }               from "./payment.entity";
import { DataSource }            from "typeorm";

describe("PaymentController (HTTP integration)", () => {
  let app:            INestApplication;
  let dataSource:     DataSource;
  let paymentService: jest.Mocked<PaymentService>;

  beforeAll(async () => {
    const mockPaymentService: jest.Mocked<PaymentService> = {
      initiate:      jest.fn(),
      findByTxnId:   jest.fn(),

    const module: TestingModule = await Test.createTestingModule({
      controllers: [PaymentController],
      providers: [
        { provide: PaymentService, useValue: mockPaymentService },
      ],
    })
      // Override the guard to inject a known user — no real JWT verification
      .overrideGuard(JwtAuthGuard)
      .useValue({ canActivate: (ctx) => {
        const req = ctx.switchToHttp().getRequest();
        req.user  = { id: "user-001", email: "alice@example.com" };
        return true;
      }})
      .compile();

    app = module.createNestApplication();
    // ⚠️ Replicate ALL production global config — missing these is the #1 setup bug
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));
    await app.init();

    paymentService = module.get(PaymentService);
  });

  afterAll(async () => {
    await app.close();
  });

  beforeEach(() => {
    jest.clearAllMocks();
  });

  describe("POST /v1/payments", () => {
    it("should return 201 and the payment result on valid input", async () => {
      // Arrange

      expect(paymentService.initiate).toHaveBeenCalledWith(dto, "user-001");
    });

    it("should return 400 when amount is missing", async () => {
      // Arrange — ValidationPipe will reject this before the service is called
      const dto = { currency: "INR", recipientId: "r1" }; // missing amount

      // Act
      const response = await request(app.getHttpServer())
        .post("/v1/payments")
        .send(dto)
        .set("Authorization", "Bearer test-token");

      // Assert
      expect(response.status).toBe(400);
      expect(response.body.message).toContain("amount");
      expect(paymentService.initiate).not.toHaveBeenCalled(); // pipe rejected before handler
    });

    it("should return 400 when a non-whitelisted property is sent", async () => {
      const dto = { amount: 5000, currency: "INR", recipientId: "r1", __proto__: {} };

      const response = await request(app.getHttpServer())
        .post("/v1/payments")
        .send(dto)
        .set("Authorization", "Bearer test-token");

      const payment = { txnId: "txn_xyz", status: "completed", amount: 5000 };

      // Act
      const response = await request(app.getHttpServer())

    });

      paymentService.findByTxnId.mockRejectedValue(

      // Act
      const response = await request(app.getHttpServer())
        .get("/v1/payments/nonexistent")
        .set("Authorization", "Bearer test-token");

      // Assert
      expect(response.status).toBe(404);
      expect(response.body.message).toBe("Payment not found");
    });
  });
});
```

**Q9. What global configuration must be replicated in the test application, and what breaks if you forget?**
A: NestJS global configuration applied in `main.ts` is not automatically applied in `Test.createTestingModule()` — you must apply each piece explicitly in the test setup. Missing any of them means the test application behaves differently from production:

| Configuration | What breaks if omitted |
|---|---|
| `app.useGlobalPipes(new ValidationPipe())` | Validation is skipped — invalid payloads reach the handler; 400 tests pass when they should fail |
| `app.useGlobalFilters(new HttpExceptionFilter())` | Custom error response shape not applied — error body assertions fail |
| `app.useGlobalInterceptors(new TransformInterceptor())` | Response wrapped differently — `response.body.data` vs `response.body` assertions wrong |
| `app.setGlobalPrefix("api")` | All routes shifted — `GET /v1/users` returns 404 because correct path is `GET /api/v1/users` |
| `app.enableCors()` | CORS headers absent — not usually an issue for supertest but breaks browser-level E2E tests |
| `app.useGlobalGuards(...)` | Guards not applied globally — authenticated routes open to unauthenticated requests in tests |

The safest pattern is to extract the application configuration into a shared bootstrap function and call it in both `main.ts` and the test setup:

```typescript
// src/app.setup.ts
export function applyGlobalConfig(app: INestApplication): void {
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));
  app.useGlobalFilters(new AllExceptionsFilter());
  app.useGlobalInterceptors(new TransformInterceptor());
  app.setGlobalPrefix("api");
}

// src/main.ts
const app = await NestFactory.create(AppModule);
applyGlobalConfig(app);
await app.listen(3000);

// In tests:
app = module.createNestApplication();
applyGlobalConfig(app);
await app.init();
```

**Q10. How do you handle authentication in supertest tests — specifically JWT-guarded routes?**
A: Three strategies, each appropriate for a different test scope:

**Strategy 1 — Override the guard (unit-scope HTTP test):**
Best when testing the controller logic and HTTP contract, not the auth flow itself:
```typescript
.overrideGuard(JwtAuthGuard)
.useValue({
  canActivate: (context: ExecutionContext) => {
    const req = context.switchToHttp().getRequest();
    req.user  = { id: "u1", email: "alice@example.com", roles: ["user"] };
    return true;
  },
})
```
The guard is bypassed entirely; a known user is injected into `req.user`. Tests run without any JWT library involvement.

**Strategy 2 — Issue a real test token in `beforeAll` (integration-scope HTTP test):**
Best when testing the full auth flow including token validation:
```typescript
beforeAll(async () => {
  // Use the real JwtService from the module to sign a test token
  const jwtService = module.get<JwtService>(JwtService);
  authToken = jwtService.sign(
    { sub: "u1", email: "alice@example.com" },
    { secret: process.env.JWT_SECRET, expiresIn: "1h" }
  );
});

// In tests:
const response = await request(app.getHttpServer())
  .get("/v1/profile")
  .set("Authorization", `Bearer ${authToken}`);
```

**Strategy 3 — Login via the API and capture the token (E2E-scope HTTP test):**
Best for true end-to-end flows that begin at the login endpoint:
```typescript
beforeAll(async () => {
  const loginResponse = await request(app.getHttpServer())
    .post("/v1/auth/login")
    .send({ email: "alice@example.com", password: "test-password" });

  authToken = loginResponse.body.accessToken;
});
```

Rule of thumb: use Strategy 1 for controller HTTP contract tests (fastest, most focused), Strategy 2 for auth-adjacent feature tests, Strategy 3 only for explicit auth flow tests.

## Section 4: Asserting HTTP Responses

**Q11. What supertest assertion methods are available and when do you use each?**
A: Supertest provides both a chainable `.expect()` API and returns a `Response` object for manual assertions with Jest matchers. Both styles are valid; the mixed approach is the most readable:

```typescript
// Supertest's own chainable assertions — good for status and simple headers
const response = await request(app)
  .get("/v1/users/1")
  .expect(200)                              // status
  .expect("Content-Type", /application\/json/)  // header (regex or string)
  .expect({ id: 1, name: "Alice" });        // exact body match (deep equal)

// Jest matchers on the response object — good for partial matching and complex assertions
const response = await request(app).get("/v1/users/1");

expect(response.status).toBe(200);
expect(response.headers["content-type"]).toMatch(/json/);
expect(response.body).toMatchObject({ id: 1, name: "Alice" }); // partial match
expect(response.body.createdAt).toBeDefined();
expect(response.body).not.toHaveProperty("passwordHash");       // sensitive field excluded
```

Prefer Jest matchers (second style) for most assertions — they produce descriptive failure messages and support the full matcher library (`toMatchObject`, `expect.arrayContaining`, `expect.objectContaining`). Use supertest's chainable `.expect(statusCode)` as a quick first line, then switch to Jest for body assertions.

**Q12. How do you assert on response headers, cookies, and redirects?**
A:

```typescript
// Headers
const response = await request(app).post("/v1/payments").send(payload);

expect(response.headers["x-request-id"]).toBeDefined();
expect(response.headers["cache-control"]).toBe("no-store");
expect(response.headers["location"]).toBe("/v1/payments/txn_001"); // for 201 Created

// Cookies — supertest exposes Set-Cookie header as an array
const loginResponse = await request(app)
  .post("/v1/auth/login")
  .send({ email: "alice@example.com", password: "secret" });

expect(loginResponse.headers["set-cookie"]).toBeDefined();
const cookie = loginResponse.headers["set-cookie"][0];
expect(cookie).toMatch(/refreshToken=/);
expect(cookie).toMatch(/HttpOnly/);
expect(cookie).toMatch(/SameSite=Strict/);

// Carry the cookie to a subsequent request
const profileResponse = await request(app)
  .get("/v1/profile")
  .set("Cookie", loginResponse.headers["set-cookie"]);
expect(profileResponse.status).toBe(200);

// Redirects — supertest does NOT follow redirects by default
const redirectResponse = await request(app).get("/v1/old-path");
expect(redirectResponse.status).toBe(301);
expect(redirectResponse.headers["location"]).toBe("/v1/new-path");

// To follow redirects, chain .redirects(n):
const followedResponse = await request(app).get("/v1/old-path").redirects(1);
expect(followedResponse.status).toBe(200);
```

**Q13. How do you test file uploads with supertest?**
A:

```typescript
// src/documents/document.controller.integration.spec.ts
import path from "path";
import fs   from "fs";

it("should return 201 and the file metadata after a successful upload", async () => {
```

**Q14. How do you assert that a response does NOT contain sensitive fields?**
A: Explicitly assert the absence of sensitive properties — never rely on the field "probably not being there":

```typescript
it("should not expose password hash or internal IDs in the user response", async () => {
  // Arrange
  await db("users").insert({
    id:           1,
    name:         "Alice",
    email:        "alice@example.com",
    password_hash: "$2b$10$...",
    internal_ref: "INT-001",
  });

  // Act
  const response = await request(app).get("/v1/users/1");

  // Assert — what IS present
  expect(response.body).toMatchObject({ id: 1, name: "Alice", email: "alice@example.com" });

  // Assert — what is NOT present
  expect(response.body).not.toHaveProperty("passwordHash");
  expect(response.body).not.toHaveProperty("password_hash");
  expect(response.body).not.toHaveProperty("internalRef");

  // Assert the total key set when security is critical (catches accidental leaks)
  const allowedKeys = ["id", "name", "email", "createdAt"];
  expect(Object.keys(response.body)).toEqual(expect.arrayContaining(allowedKeys));
  expect(Object.keys(response.body).length).toBe(allowedKeys.length);
});
```

This is especially important for fintech services — a single `SELECT *` that leaks a PAN number or bank account in the API response is a compliance incident, not just a bug.

## Section 5: Database Integration in HTTP Tests

**Q15. How do you structure a NestJS HTTP integration test that hits a real database?**
A:

```typescript
// src/users/user.controller.db.integration.spec.ts
import { Test, TestingModule }   from "@nestjs/testing";
import { INestApplication }      from "@nestjs/common";
import { ValidationPipe }        from "@nestjs/common";
import { TypeOrmModule }         from "@nestjs/typeorm";
import { getDataSourceToken }    from "@nestjs/typeorm";
```

**Q16. What is the transaction rollback pattern for HTTP integration tests, and how do you implement it with TypeORM?**
A: The transaction rollback pattern wraps each test in a DB transaction that is always rolled back — leaving the DB clean without any explicit `DELETE` or `TRUNCATE`. It's faster and more reliable than truncating, but requires the SUT to use the injected transaction rather than opening its own:

```typescript
// src/test/utils/transaction.helper.ts
import { DataSource, QueryRunner } from "typeorm";

export async function withRollback(
  dataSource: DataSource,
  testFn: (queryRunner: QueryRunner) => Promise<void>,
): Promise<void> {
  const queryRunner = dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    await testFn(queryRunner);
  } finally {
    await queryRunner.rollbackTransaction();
    await queryRunner.release();
  }
}

// In tests — override the TypeORM data source to use the test transaction
describe("PaymentRepository (transaction rollback)", () => {
  let dataSource:   DataSource;
  let queryRunner:  QueryRunner;

  beforeEach(async () => {
    queryRunner = dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();

    // Override the EntityManager used by the SUT with the transaction's manager
    jest.spyOn(dataSource, "createEntityManager")
        .mockReturnValue(queryRunner.manager);
  });

  afterEach(async () => {
    await queryRunner.rollbackTransaction();
    await queryRunner.release();
    jest.restoreAllMocks();
  });

  it("should persist and retrieve a payment within the same transaction", async () => {
    const repo = new PaymentRepository(queryRunner.manager);

    await repo.save({ txnId: "txn_001", amount: 5000, userId: "u1" });
    const found = await repo.findByTxnId("txn_001");

    expect(found!.amount).toBe(5000);
    // After afterEach rollback, this row will not exist in the DB
  });
});
```

The HTTP-level variant is more complex — the HTTP request creates its own execution context. The cleanest approach is to expose a `QueryRunner` or connection override via `AsyncLocalStorage` so the entire request lifecycle shares the test transaction.

**Q17. How do you test pagination endpoints with supertest?**

```typescript
describe("GET /v1/transactions (pagination)", () => {

      page:       1,
      limit:      10,
      total:      25,
      totalPages: 3,
      hasNext:    true,
      hasPrev:    false,
    });
  });

  it("should return the last page with 5 items", async () => {
    const response = await request(app.getHttpServer())
      .get("/v1/transactions")
      .query({ page: 3, limit: 10 })
      .set("Authorization", `Bearer ${authToken}`);

    expect(response.status).toBe(200);
    expect(response.body.data).toHaveLength(5);
    expect(response.body.meta).toMatchObject({ hasNext: false, hasPrev: true });
  });

  it("should return 400 for a page number beyond the last page", async () => {
    const response = await request(app.getHttpServer())
      .get("/v1/transactions")
      .query({ page: 99, limit: 10 })
      .set("Authorization", `Bearer ${authToken}`);

    expect(response.status).toBe(400);
  });
});
```

The seed count is intentional — 25 records with a page size of 10 gives exactly 3 pages (10, 10, 5), which exercises the first page, a middle page, and the boundary last page without over-seeding.

## Section 6: Anti-Patterns and Pitfalls

**Q18. What are the most common mistakes in supertest integration tests?**
A:

**1. Not awaiting `app.init()` — the most common NestJS supertest bug:**
```typescript
// ❌ getHttpServer() returns null if init() hasn't resolved
app = module.createNestApplication();
await app.init();   // ← must be awaited; without this, getHttpServer() returns null
```

**2. Not closing the app in `afterAll` — connection pool leak:**
```typescript
// ❌ DB connections and server handles stay open; Jest reports "open handles"
// ✅ Always close
afterAll(async () => {
  await app.close();    // closes HTTP server, DI container, DB connections
});
```

**3. Not replicating global pipes — validation silently skipped:**
```typescript
// ❌ ValidationPipe not applied — invalid payloads reach the handler
app = module.createNestApplication();
await app.init();

// ✅ Replicate all global config
app = module.createNestApplication();
app.useGlobalPipes(new ValidationPipe({ whitelist: true }));
await app.init();
```

**4. Asserting on the exact error message string — brittle:**
```typescript
// ❌ Breaks when error message wording changes
expect(response.body.message).toBe("email must be an email");

// ✅ Assert on structure and approximate content
expect(response.status).toBe(400);
expect(response.body.message).toEqual(expect.arrayContaining([
  expect.stringContaining("email"),
]));
```

**5. Using `beforeAll` for DB seeding instead of `beforeEach` — cross-test contamination:**
```typescript
// ❌ Test A modifies the user seeded in beforeAll; Test B reads stale state
beforeAll(async () => {
  await db.insert(user);
});

// ✅ Fresh state for every test
beforeEach(async () => {
  await db.clear();
  await db.insert(user);
});
```

**6. Not asserting DB side effects — missing coverage of the write path:**
```typescript
// ❌ Only asserts the HTTP response — misses whether the DB was actually written
expect(response.status).toBe(201);

// ✅ Assert both the response and the DB state
expect(response.status).toBe(201);
const row = await dataSource.getRepository(Payment).findOne({ where: { txnId } });
expect(row).toBeDefined();
```

**Q19. What is the "application per suite vs application per test" tradeoff?**
A: Booting a NestJS application takes 200ms–2s depending on module complexity. The choice of when to boot it determines both test speed and isolation:

- **`beforeAll` (one app per suite, default)** — boot once, reuse across all tests in the `describe` block. Fast. Risk: module-level singletons (in-memory caches, connection pools) accumulate state between tests unless explicitly reset.
- **`beforeEach` (one app per test)** — boot fresh for every test. Perfect isolation — no shared module state. Cost: adds 200ms–2s per test; a 100-test suite adds 20–200 seconds of overhead.

The pragmatic split: use `beforeAll` for the vast majority of HTTP integration tests (accept that you need `beforeEach` DB cleanup), and `beforeEach` only for tests that are sensitive to module-level singleton state (feature flag caches, connection pool state, in-memory rate limiters).

```typescript
// Pragmatic pattern — one app per suite, DB cleanup per test
describe("UserController", () => {
  let app: INestApplication;

  beforeAll(async () => {
    app = await bootstrapTestApp();   // slow; done once
  });

  afterAll(async () => {
    await app.close();
  });

  beforeEach(async () => {
    await clearDatabase();            // fast; done per test
  });

  // tests...
});
```

## Section 7: Scenario / System Design Style Questions

**Q20. "You're writing HTTP integration tests for a payment initiation endpoint that calls JusPay. You can't call JusPay in tests. How do you structure the test and what do you assert?"**
A: Three-layer approach:

**Layer 1 — HTTP contract test (supertest + mocked JusPay client):**
The JusPay client is replaced via `overrideProvider`. Test the HTTP contract — status codes, response shape, validation — without any real external call:

```typescript
const mockJusPayClient: jest.Mocked<JusPayClient> = {
  initiatePayment: jest.fn(),
  getStatus:       jest.fn(),
};

// Override in TestingModule
.overrideProvider(JusPayClient)
.useValue(mockJusPayClient)

// Test the success path
mockJusPayClient.initiatePayment.mockResolvedValue({
  orderId: "jp_ord_001",
  status:  "PENDING",
  paymentLink: "https://api.juspay.in/pay/jp_ord_001",
});

const response = await request(app.getHttpServer())
  .post("/v1/payments/initiate")
  .send({ amount: 5000, currency: "INR", userId: "u1" });

expect(response.status).toBe(201);
expect(response.body.paymentLink).toBeDefined();
expect(response.body.orderId).toMatch(/^jp_ord_/);

// Test the failure path — JusPay declines
mockJusPayClient.initiatePayment.mockRejectedValue(
  new JusPayError("AUTHENTICATION_FAILED", 401)
);

const failResponse = await request(app.getHttpServer())
  .post("/v1/payments/initiate")
  .send({ amount: 5000, currency: "INR", userId: "u1" });

expect(failResponse.status).toBe(502); // upstream error → 502 Bad Gateway
expect(failResponse.body.code).toBe("PAYMENT_GATEWAY_ERROR");
```

**Layer 2 — Contract verification (runs in isolated environment with real JusPay sandbox):**
Weekly or pre-release: call the real JusPay sandbox and assert the response shape matches what the mock returns. If JusPay changes their response schema, this test catches it.

**Layer 3 — DB side effect assertions:**
After a successful initiation, assert that the payment record was persisted with the correct `orderId`, `status: "pending"`, and `gatewayRef`:
```typescript
const payment = await dataSource
  .getRepository(Payment)
  .findOne({ where: { orderId: "jp_ord_001" } });
expect(payment!.status).toBe("pending");
expect(payment!.gatewayRef).toBe("jp_ord_001");
```

**Q21. "Your NestJS integration test suite takes 4 minutes to run. CI is slow and developers skip running tests locally. How do you fix it?"**
A: Diagnose by phase, fix by category:

**1. Identify the slow tests:**
```bash
jest --verbose --testNamePattern="" 2>&1 | grep -E "✓|✗|●" | sort -t"m" -k2 -n
# or use jest-slow-test-reporter
```

**2. App bootstrap overhead** — if 50 test files each boot NestJS independently, 50 × 500ms = 25s just in bootstrap:
- Lift the app bootstrap into `globalSetup` (a Jest global that runs once across all workers) using a shared HTTP port:
```typescript
// jest.globalSetup.ts
export default async () => {
  const app = await bootstrapTestApp();
  await app.listen(0);                       // random port
  process.env.TEST_APP_PORT = app.getHttpServer().address().port;
  global.__TEST_APP__ = app;                 // store for globalTeardown
};
```
- Now all test files share one app instance; `request("http://localhost:${process.env.TEST_APP_PORT}")` in tests.

**3. DB operations overhead** — `TRUNCATE` on many tables in `beforeEach` across 200 tests adds up:
- Switch to transaction rollback pattern (fast; no real writes committed).
- If not feasible, run DB integration tests in a separate Jest project (`jest.config.ts` with `projects`) so they don't block unit and HTTP contract tests.

**4. Serial execution** — `--runInBand` forces all tests to run in one process:
- Remove `--runInBand` for tests that don't share DB state.
- Use separate test DBs per worker (`TEST_DATABASE_URL_1`, `TEST_DATABASE_URL_2`) for true parallel DB integration tests.

**5. Module compilation overhead** — `Test.createTestingModule().compile()` re-compiles TypeScript per suite:
- Cache the compiled module across tests using `beforeAll` at the file level (already the default if structured correctly).

**Q22. "How do you test a webhook endpoint that expects an HMAC signature header?"**
A: Reproduce the HMAC signing logic in the test's Arrange phase — the same logic the webhook provider (Razorpay, JusPay, etc.) uses to sign requests:

```typescript
// src/webhooks/razorpay-webhook.controller.integration.spec.ts
import crypto from "crypto";

const WEBHOOK_SECRET = "test-webhook-secret-key";

function signPayload(payload: string, secret: string): string {
  return crypto
    .createHmac("sha256", secret)
    .update(payload)
    .digest("hex");
}

describe("POST /v1/webhooks/razorpay", () => {
  it("should return 200 and process the payment event with a valid signature", async () => {
    // Arrange
    const payload = JSON.stringify({
      event:  "payment.captured",
      payload: {
        payment: { entity: { id: "pay_001", amount: 5000, status: "captured" } },
      },
    });
    const signature = signPayload(payload, WEBHOOK_SECRET);

    // Act
    const response = await request(app.getHttpServer())
      .post("/v1/webhooks/razorpay")
      .set("Content-Type", "application/json")
      .set("x-razorpay-signature", signature)   // header the controller validates
      .send(payload);

    // Assert
    expect(response.status).toBe(200);
    // Assert DB side effect — payment status updated
    const payment = await dataSource
      .getRepository(Payment)
      .findOne({ where: { gatewayRef: "pay_001" } });
    expect(payment!.status).toBe("captured");
  });

  it("should return 401 when the signature is invalid", async () => {
    const payload   = JSON.stringify({ event: "payment.captured" });
    const badSig    = "invalid-signature";

    const response = await request(app.getHttpServer())
      .post("/v1/webhooks/razorpay")
      .set("Content-Type", "application/json")
      .set("x-razorpay-signature", badSig)
      .send(payload);

    expect(response.status).toBe(401);
  });

  it("should return 401 when the signature header is missing entirely", async () => {
    const payload = JSON.stringify({ event: "payment.captured" });

    const response = await request(app.getHttpServer())
      .post("/v1/webhooks/razorpay")
      .set("Content-Type", "application/json")
      .send(payload);                            // no signature header

    expect(response.status).toBe(401);
  });
});
```

The `WEBHOOK_SECRET` in tests should come from the test environment config — the same secret the test NestJS app is configured with, so the signing and verification use the same key.

## Quick Reference: Supertest Cheat Sheet

```typescript
// Basic request methods
request(app).get("/path")
request(app).post("/path").send(body)
request(app).put("/path").send(body)
request(app).patch("/path").send(body)
request(app).delete("/path")

// Headers
.set("Authorization", "Bearer token")
.set("Content-Type", "application/json")
.set("Accept", "application/json")
.set("Cookie", "session=abc123")

// Query params
.query({ page: 1, limit: 10, filter: "active" })

// File upload
.attach("fieldName", "/path/to/file")
.field("key", "value")

// Response access
response.status          // number
response.body            // parsed JSON
response.headers         // object
response.text            // raw string body
response.type            // Content-Type

// Supertest chainable assertions
.expect(200)                              // status
.expect("Content-Type", /json/)          // header
.expect({ key: "value" })                // exact body

// NestJS-specific
request(app.getHttpServer())              // always use getHttpServer()
await app.init()                          // must await before getHttpServer()
await app.close()                         // always in afterAll
module.get<ServiceType>(ServiceToken)     // access providers after compile
```
