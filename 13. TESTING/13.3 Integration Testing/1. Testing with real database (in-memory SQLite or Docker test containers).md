# JavaScript / Testing: Testing with Real Databases — In-Memory SQLite & Docker Test Containers — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why test against a real database at all? Why not just mock the data layer?**
A: Mocking the data layer gives you fast, isolated tests, but it can't verify several categories of behavior that only emerge when real SQL executes against a real engine:

- **Query correctness** — an ORM query that looks right can produce wrong SQL. Knex, Sequelize, TypeORM, and Prisma all have edge cases where the generated SQL doesn't match developer intent. Only running the query against a real engine confirms it does what it's supposed to.
- **Schema constraints** — `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK` constraints, and cascade rules are enforced by the database, not your application code. A mock that returns `{ id: 1 }` for every insert can't tell you that two inserts with the same email will violate a unique constraint.
- **Migration correctness** — your migration files define the actual schema. Running them against a real engine is the only way to know they apply cleanly, in order, without destructive conflicts.
- **Index behavior** — query plans and index usage can't be tested in memory with a mock. Slow queries that would be caught by `EXPLAIN ANALYZE` in a test environment won't surface until production.
- **Transaction semantics** — rollback behavior, isolation levels, deadlock handling, and savepoints are engine-specific. A mock that stubs `db.transaction()` can't verify that your code actually rolls back on error.

The cost of mocking the data layer is false confidence: tests are green, migrations run, but the application fails in production because the mock never exercised what the database actually does.

**Q2. What are the two main approaches to running a real database in tests?**
A:
- **In-memory SQLite** — a lightweight, file-optional database engine embedded directly in the Node process via the `better-sqlite3` or `sql.js` npm packages. No external process required; the database lives and dies with the test run. Fast to start, zero infrastructure, but not the same engine as production if you're running PostgreSQL or MySQL.
- **Docker test containers** — a real instance of your production database engine (PostgreSQL, MySQL, MongoDB, Redis) spun up in a Docker container for the duration of the test run, then torn down. Exact engine parity with production, but requires Docker and adds startup time (typically 3–10 seconds for the container to be ready).

Both approaches give you a real database with real SQL execution. They differ on the **fidelity vs speed** axis — SQLite is faster and simpler; containers give you exact production parity.

**Q3. What is the fundamental test isolation problem with a shared database, and what are the standard solutions?**
A: If tests share a database and one test writes data, subsequent tests may read that data and produce different outcomes depending on execution order. This makes the test suite:
- **Order-dependent** — tests pass in sequence A→B but fail in sequence B→A.
- **Parallel-unsafe** — two workers writing and reading the same table interfere with each other.
- **Non-deterministic** — a test passes on one run, fails on the next, with no code change.

Standard solutions, in order of preference:

- **Transaction rollback** — wrap each test in a database transaction; roll it back in `afterEach`. Data written during the test is never committed, so the next test sees a clean slate. Fast, zero cleanup code, but requires the ORM/query layer to support injecting a transaction.
- **Truncation** — `TRUNCATE` (or `DELETE FROM`) all tables in `beforeEach`. Simpler to implement than transaction injection but slower (real I/O on every test) and order-sensitive if your truncation doesn't respect foreign key constraints.
- **Per-test database / schema** — give each test worker its own database or schema. Eliminates all sharing; tests run safely in parallel. Higher setup cost but the most robust isolation.
- **Snapshot + restore** — take a database snapshot at a known clean state; restore it before each test. Used with SQLite (copy the `.db` file) or PostgreSQL (template databases).

## Section 2: In-Memory SQLite

**Q4. What is in-memory SQLite, and what npm packages provide it?**
A: SQLite is a self-contained, serverless database engine that can operate entirely in memory — no file, no process, no port. The database is created when the connection opens and destroyed when it closes.

Primary Node.js packages:
- **`better-sqlite3`** — synchronous API, native bindings, very fast. The standard choice for Node.js applications. Does not support async/await natively (all operations are blocking, which is fine in tests).
- **`sql.js`** — SQLite compiled to WebAssembly; works in both Node and browser; no native compilation step. Slightly slower than `better-sqlite3` but useful in environments where native binaries are problematic (CI without build tools, browser-based tests).
- **`@databases/sqlite`** — async wrapper around `better-sqlite3`; useful if your production code uses an async database interface and you want the test database to match the same API surface.

**Q5. How do you set up an in-memory SQLite database for a Jest test suite using Knex?**
A:

```js
// test/setup/db.js — shared test database factory
import knex from "knex";

export function createTestDb() {
  return knex({
    client: "better-sqlite3",
    connection: { filename: ":memory:" },  // ← in-memory, no file
    useNullAsDefault: true,                // SQLite doesn't support DEFAULT for all types
  });
}
```

```js
// test/users.test.js
import { createTestDb } from "./setup/db.js";
import { UserRepository } from "../src/repositories/UserRepository.js";

let db;
let userRepo;

beforeAll(async () => {
  db = createTestDb();
  await db.migrate.latest();   // run all migrations against the in-memory DB
  await db.seed.run();         // optional: seed reference data
});

afterAll(async () => {
  await db.destroy();          // close the connection — prevents open handle warnings
});

beforeEach(async () => {
  // Truncate in dependency order (children before parents) to respect FK constraints
  await db("order_items").truncate();
  await db("orders").truncate();
  await db("users").truncate();
});

test("creates a user and retrieves it by id", async () => {
  userRepo = new UserRepository(db);

  const created = await userRepo.create({ name: "Alice", email: "alice@example.com" });
  const found   = await userRepo.findById(created.id);

  expect(found).toMatchObject({ name: "Alice", email: "alice@example.com" });
});
```

**Q6. What are the key limitations of SQLite vs PostgreSQL that can produce false-positive or false-negative tests?**
A: SQLite is deliberately permissive — it accepts SQL that PostgreSQL rejects, and it handles types differently. Using SQLite to test code that runs on PostgreSQL in production is a real-fidelity risk:

| Behavior                         | SQLite                                        | PostgreSQL                                      |
|---                               |---                                            |---                                              |
| Type enforcement                 | Dynamic — `TEXT` column accepts integers      | Strict — column type is enforced                |
| `RETURNING` clause               | Supported since 3.35 (2021)                   | Fully supported                                 |
| `BOOLEAN` type                   | Stored as `0`/`1` integers                    | Native `TRUE`/`FALSE`                           |
| JSON operators (`->`, `->>`)     | Limited support                               | Full `jsonb` operator set                       |
| `FULL OUTER JOIN`                | Not supported (pre-3.39)                      | Supported                                       |
| Window functions                 | Supported since 3.25                          | Full support                                    |
| Concurrent writes                | Serialized — one writer at a time             | MVCC — concurrent writers                       |
| `SERIAL` / `IDENTITY` columns    | `INTEGER PRIMARY KEY` only                    | `SERIAL`, `BIGSERIAL`, `IDENTITY`               |
| `ON CONFLICT` / upsert syntax    | `INSERT OR REPLACE` / `ON CONFLICT DO UPDATE` | `ON CONFLICT DO UPDATE` (slightly different syntax)|
| Schema name support              | Limited                                       | Full `schema.table` support                     |

**Q7. When is in-memory SQLite the right choice, and when is it the wrong choice?**
A:
**Right choice when:**
- Your production database *is* SQLite (common in Electron apps, mobile backends, or edge deployments).
- You're testing pure data-layer logic (CRUD, associations, constraints) that doesn't use PostgreSQL-specific features.
- You need the absolute fastest feedback loop — SQLite starts in microseconds vs Docker's 3–10 seconds.
- CI infrastructure is constrained — no Docker available, or you're running in a serverless build environment.
- You're testing an ORM abstraction layer that is designed to be database-agnostic.

**Wrong choice when:**
- Your production database is PostgreSQL/MySQL and your queries use engine-specific features (JSON operators, CTEs with specific syntax, advisory locks, `LISTEN`/`NOTIFY`, PostGIS, full-text search with `tsvector`).
- You need to test migration files that use PostgreSQL-specific DDL (`CREATE EXTENSION`, `ENUM` types, partial indexes).
- Concurrent write behavior matters (SQLite serializes all writes; PostgreSQL uses MVCC).
- You're testing database-level constraints that differ between engines.

**Q8. How do you inject the test database connection into your application code without modifying production code?**
A: The key pattern is **dependency injection** — the repository or service receives the database connection as a constructor argument or function parameter rather than importing it directly. This lets tests pass a test database while production code passes the real connection:

```js
// ✗ Hard-coded dependency — untestable without module mocking
import db from "../db.js"; // imports the production singleton

export class UserRepository {
  async findById(id) {
    return db("users").where({ id }).first(); // always uses production db
  }
}

// ✓ Injected dependency — testable with any connection
export class UserRepository {
  constructor(db) {
    this.db = db; // caller provides the connection
  }

  async findById(id) {
    return this.db("users").where({ id }).first();
  }
}
```

```js
// Test — inject the in-memory test database
const repo = new UserRepository(testDb);

// Production — inject the real connection pool
const repo = new UserRepository(productionDb);
```

If your codebase already uses a module-level singleton (`import db from "../db"`), you can still test it with `jest.mock("../db", () => testDb)` — but the constructor injection pattern is cleaner and doesn't require mocking the module system.

## Section 3: Docker Test Containers

**Q9. What is `testcontainers-node`, and how does it work?**
A: `testcontainers-node` (`@testcontainers/testcontainers` on npm) is a library that programmatically starts and stops Docker containers from within your test code. You describe the container (image, ports, environment variables, health check), the library starts it, waits until it's healthy, and returns the connection details (host, port). When the test is done, the library stops and removes the container.

```js
import { PostgreSqlContainer } from "@testcontainers/postgresql";

const container = await new PostgreSqlContainer("postgres:16-alpine")
  .withDatabase("testdb")
  .withUsername("testuser")
  .withPassword("testpass")
  .start();

const connectionUri = container.getConnectionUri();
// → "postgresql://testuser:testpass@localhost:54321/testdb"

// ... run tests ...

await container.stop();
```

The library handles: pulling the image if not cached, mapping container ports to random available host ports (avoiding collisions with other running services), polling the health check until the database accepts connections, and cleaning up on stop.

**Q10. How do you structure a Jest test suite that uses a Docker PostgreSQL container?**
A:

```js
// test/integration/users.test.js
import { PostgreSqlContainer } from "@testcontainers/postgresql";
import { Client }               from "pg";
import knex                     from "knex";

let container;
let db;

// globalSetup alternative: start once for the entire suite
beforeAll(async () => {
  // Pull + start the container — allow up to 60s for slow CI environments
  container = await new PostgreSqlContainer("postgres:16-alpine")
    .withDatabase("testdb")
    .withUsername("test")
    .withPassword("test")
    .start();

  db = knex({
    client: "pg",
    connection: container.getConnectionUri(),
    pool: { min: 1, max: 5 },
  });

  await db.migrate.latest();  // apply all migrations
}, 60_000);                   // override Jest's 5s timeout for container startup

afterAll(async () => {
  await db.destroy();         // close connection pool first
  await container.stop();     // then stop the container
});

beforeEach(async () => {
  // Wrap each test in a transaction — rolled back in afterEach
  await db.raw("BEGIN");
});

afterEach(async () => {
  await db.raw("ROLLBACK");
});

test("inserts and retrieves a user", async () => {
  const [user] = await db("users")
    .insert({ name: "Alice", email: "alice@example.com" })
    .returning("*");

  const found = await db("users").where({ id: user.id }).first();

  expect(found).toMatchObject({ name: "Alice", email: "alice@example.com" });
});

test("enforces unique email constraint", async () => {
  await db("users").insert({ name: "Alice", email: "alice@example.com" });

  await expect(
    db("users").insert({ name: "Alice2", email: "alice@example.com" })
  ).rejects.toThrow(/unique/i);
});
```

**Q11. How do you share a single Docker container across an entire Jest test suite (not just one file)?**
A: Use Jest's `globalSetup` and `globalTeardown` hooks — they run once before and after the entire test run, in the main Jest process (not in a worker). You store the container reference and connection details in a temp file or environment variable that worker processes can read:

```js
// jest.config.js
export default {
  globalSetup:    "./test/globalSetup.js",
  globalTeardown: "./test/globalTeardown.js",
  testEnvironment: "node",
};
```

```js
// test/globalSetup.js
import { PostgreSqlContainer } from "@testcontainers/postgresql";
import fs from "fs/promises";
import os from "os";
import path from "path";

export default async function globalSetup() {
  const container = await new PostgreSqlContainer("postgres:16-alpine")
    .withDatabase("testdb")
    .withUsername("test")
    .withPassword("test")
    .start();

  // Persist container state for workers and teardown
  const state = {
    connectionUri:  container.getConnectionUri(),
    containerId:    container.getId(),
  };

  const stateFile = path.join(os.tmpdir(), "jest-db-state.json");
  await fs.writeFile(stateFile, JSON.stringify(state));

  // Store for globalTeardown — process.env survives to teardown in the same process
  process.env.__TEST_DB_URI__       = state.connectionUri;
  process.env.__TEST_CONTAINER_ID__ = state.containerId;
}
```

```js
// test/globalTeardown.js
import { DockerContainerClient } from "@testcontainers/testcontainers";

export default async function globalTeardown() {
  // Stop via the container id saved in globalSetup
  // Alternative: re-read the state file and stop via the SDK
  await DockerContainerClient.stopContainer(process.env.__TEST_CONTAINER_ID__);
}
```

```js
// test/helpers/db.js — used in every test file
import knex from "knex";

export function getTestDb() {
  return knex({
    client: "pg",
    connection: process.env.__TEST_DB_URI__,
    pool: { min: 1, max: 3 },
  });
}
```

**Q12. How do you run integration tests in parallel without test files interfering with each other's data?**
A: Two approaches:

**Per-worker schema isolation** — create a separate PostgreSQL schema for each Jest worker. Each worker gets a prefix (`worker_1`, `worker_2`, etc.) and runs all migrations within its own schema. Tests in different workers never touch the same tables:

```js
// test/helpers/workerDb.js
import knex from "knex";

const workerId = process.env.JEST_WORKER_ID ?? "1"; // Jest sets this automatically

export async function createWorkerDb(baseUri) {
  const schemaName = `test_worker_${workerId}`;
  const db = knex({ client: "pg", connection: baseUri });

  await db.raw(`CREATE SCHEMA IF NOT EXISTS ??`, [schemaName]);
  await db.raw(`SET search_path TO ??`, [schemaName]);
  await db.migrate.latest();

  return db;
}
```

**Per-worker database** — create a separate database per worker. More isolated than schemas (no cross-schema leakage possible), but requires `CREATE DATABASE` permissions and slightly more setup:

```js
const dbName = `testdb_worker_${process.env.JEST_WORKER_ID}`;
await adminDb.raw(`CREATE DATABASE ??`, [dbName]);
```

For most teams, per-worker schema isolation is the right balance between isolation and setup complexity.

## Section 4: Transaction Rollback Isolation

**Q13. How does transaction rollback isolation work, and why is it the preferred pattern?**
A: Before each test, open a database transaction. All SQL executed during the test — inserts, updates, deletes — runs inside that transaction but is never committed to the database. After each test, roll back the transaction. From the next test's perspective, the database is exactly as it was before the previous test ran — no cleanup code needed, no truncation, no seed re-run:

```
beforeEach: BEGIN TRANSACTION
  test body: INSERT, UPDATE, SELECT, etc.
afterEach:  ROLLBACK  ← all test data vanishes instantly
```

This is faster than truncation (a rollback is a single log operation; truncation scans tables), safer (no risk of truncating in the wrong order and violating FK constraints), and completely silent — tests don't need to know about the cleanup mechanism.

**Q14. How do you implement transaction rollback isolation when the code under test manages its own transactions?**
A: This is the hard case. If your application code calls `db.transaction(async trx => { ... })` internally, the inner transaction commits when the callback resolves — the outer test transaction can't roll it back, because the inner commit happened first.

The solution is **savepoints** (nested transactions in PostgreSQL):

```js
// Instead of BEGIN/ROLLBACK, use SAVEPOINT/ROLLBACK TO SAVEPOINT
beforeEach(async () => {
  await db.raw("SAVEPOINT test_boundary");
});

afterEach(async () => {
  await db.raw("ROLLBACK TO SAVEPOINT test_boundary");
});
```

Or intercept the transaction factory and replace it with a function that creates a savepoint instead:

```js
// Wrap the real transaction method to use savepoints in tests
const realTransaction = db.transaction.bind(db);
db.transaction = async (callback) => {
  await db.raw("SAVEPOINT nested_tx");
  try {
    const result = await callback(db); // pass the outer connection, not a new transaction
    await db.raw("RELEASE SAVEPOINT nested_tx");
    return result;
  } catch (err) {
    await db.raw("ROLLBACK TO SAVEPOINT nested_tx");
    throw err;
  }
};
```

This pattern is more complex but preserves full isolation even when the code under test believes it's using real transactions.

**Q15. What is the difference between `TRUNCATE` and `DELETE` for test cleanup, and when do you use each?**
A:

| Dimension                    | `TRUNCATE`                                      | `DELETE FROM`                                  |
|---                           |---                                              |---                                             |
| Speed                        | Very fast — bypasses row-by-row processing      | Slower — scans rows                            |
| Auto-increment reset         | Resets sequences in PostgreSQL (with `RESTART IDENTITY`) | Does not reset sequences              |
| `WHERE` clause               | Not supported — truncates entire table          | Supported — can delete specific rows           |
| Foreign key awareness        | Requires `CASCADE` or correct order             | Requires correct order or `CASCADE`            |
| Triggers                     | Does not fire `DELETE` triggers                 | Fires `DELETE` triggers                        |
| Transaction rollback         | Cannot be rolled back in some engines (MySQL)   | Can always be rolled back                      |
| SQLite support               | Not supported — use `DELETE FROM`               | Supported                                      |

**Rule of thumb:** use `TRUNCATE ... RESTART IDENTITY CASCADE` in PostgreSQL for full table resets; use `DELETE FROM` in SQLite or when you need trigger-firing semantics; prefer transaction rollback over either when possible.

## Section 5: Migration Testing

**Q16. Why should migrations be part of the test suite, not just run before tests?**
A: Migrations are production code — they define the schema your application runs against. Untested migrations cause several classes of production incidents:
- A migration that works in development fails in production because of data that exists in production but not locally.
- Two migrations conflict when applied together (e.g., both attempt to rename the same column).
- A rollback migration is broken or missing, discovered only during an incident.
- The schema after migration doesn't match what the ORM expects — a column was renamed in the migration but the model wasn't updated.

Testing migrations means running `migrate.latest()` against a real database in CI, seeding realistic data, and verifying that the schema is exactly what the application expects. Some teams also test rollbacks: `migrate.rollback()` followed by `migrate.latest()` to verify the round-trip.

**Q17. How do you test that a data migration (not just a schema migration) is correct?**
A: A data migration transforms existing rows — backfilling a column, splitting a field, computing a derived value. Test it by inserting the *before* state, running the migration, and asserting on the *after* state:

```js
test("migration 20240615: backfills full_name from first_name + last_name", async () => {
  // Insert pre-migration data (with full_name column absent or null)
  await db.raw(`
    INSERT INTO users (id, first_name, last_name, full_name)
    VALUES (1, 'Alice', 'Smith', NULL),
           (2, 'Bob',   'Jones', NULL)
  `);

  // Run only the specific migration under test
  await db.migrate.up({ name: "20240615_backfill_full_name.js" });

  const users = await db("users").select("id", "full_name").orderBy("id");

  expect(users).toStrictEqual([
    { id: 1, full_name: "Alice Smith" },
    { id: 2, full_name: "Bob Jones"  },
  ]);
});
```

**Q18. How do you test that a migration is idempotent (safe to run twice)?**
A: Run `migrate.latest()` twice and assert that the second run completes without error and the schema is unchanged:

```js
test("migrations are idempotent", async () => {
  await db.migrate.latest(); // first run
  await expect(db.migrate.latest()).resolves.not.toThrow(); // second run — no error

  // Schema should still be valid
  const tables = await db.raw(`
    SELECT table_name FROM information_schema.tables
    WHERE table_schema = 'public'
    ORDER BY table_name
  `);
  expect(tables.rows.map(r => r.table_name)).toContain("users");
});
```

## Section 6: Pitfalls & Best Practices

**Q19. What is the "open handle" problem in database tests, and how do you prevent it?**
A: Jest reports "Jest did not exit one second after the test run has completed" when a Node.js resource — like a database connection pool — is still active after all tests finish. Connection pools keep TCP connections alive (waiting for new queries), which prevents the process from exiting naturally.

Prevention checklist:
```js
afterAll(async () => {
  await db.destroy();        // Knex — drains and closes the pool
  await pool.end();          // node-postgres (pg) — closes all clients
  await mongoose.disconnect(); // Mongoose — closes the MongoDB connection
  await container.stop();    // testcontainers — stops the Docker container
});
```

Common mistakes:
- Calling `db.destroy()` without `await` — the pool closes asynchronously, but Jest exits before it finishes, causing a "Cannot use a pool after calling end on the pool" error on the next run.
- Forgetting to call `container.stop()` — the Docker container keeps running after the test suite exits, accumulating zombie containers on the host.
- Running `afterAll` cleanup in a `describe` block instead of at the test file level — other `describe` blocks in the same file may run after the connection is already closed.

**Q20. How do you handle foreign key constraint ordering during table truncation?**
A: Foreign key constraints prevent truncating a parent table while child rows reference it. You must truncate in dependency order (children first) or disable constraints temporarily:

```js
// Option 1 — truncate in reverse dependency order (children before parents)
async function truncateAll(db) {
  await db("order_items").truncate();    // child of orders
  await db("orders").truncate();         // child of users
  await db("product_variants").truncate(); // child of products
  await db("products").truncate();
  await db("users").truncate();
}

// Option 2 — disable FK checks temporarily (MySQL)
async function truncateAll(db) {
  await db.raw("SET FOREIGN_KEY_CHECKS = 0");
  await Promise.all([
    db("users").truncate(),
    db("orders").truncate(),
    db("order_items").truncate(),
  ]);
  await db.raw("SET FOREIGN_KEY_CHECKS = 1");
}

// Option 3 — CASCADE in PostgreSQL (truncates referencing tables automatically)
async function truncateAll(db) {
  await db.raw("TRUNCATE users, orders, order_items RESTART IDENTITY CASCADE");
}
```

Option 3 (PostgreSQL `CASCADE`) is the most concise and reliable. Option 1 (manual ordering) works across all engines but requires updating the list whenever new tables or FK relationships are added. Maintain a `TRUNCATION_ORDER` constant in a shared test helper so the ordering is defined once.

**Q21. What is the risk of using `beforeAll` for seeding data instead of `beforeEach`?**
A: `beforeAll` seeds run once before all tests in a file. If any test modifies the seeded data — updates a user's email, deletes a product, increments a counter — subsequent tests see the modified state, not the original. This causes:
- **Order-dependent tests** — test B expects Alice's email to be `alice@example.com`, but test A updated it to `alice@new.com`.
- **Cumulative state** — a counter that's supposed to start at 0 is at 5 by the fifth test.
- **Intermittent failures** — pass when tests run in one order, fail in another.

**Rule:** Seed in `beforeEach` (or use transaction rollback, which achieves the same thing faster). Use `beforeAll` only for data that is read-only throughout the entire suite — reference tables, lookup data, static configuration.

**Q22. How do you prevent tests from hitting a production database accidentally?**
A: Multiple layers of defense:

```js
// Layer 1 — assert the connection string in test setup
beforeAll(() => {
  const uri = process.env.DATABASE_URL;
  if (!uri.includes("localhost") && !uri.includes("127.0.0.1") && !uri.includes("test")) {
    throw new Error(
      `DATABASE_URL "${uri}" does not look like a test database. Refusing to run.`
    );
  }
});

// Layer 2 — use a dedicated test environment variable
// .env.test (loaded by Jest via setupFiles or dotenv)
DATABASE_URL=postgresql://test:test@localhost:5432/myapp_test

// Layer 3 — never share credentials between environments
// Production DB credentials exist only in production secret management (AWS Secrets Manager, Vault)
// Test DB credentials are throwaway values in .env.test or CI environment variables

// Layer 4 — CI runs against a container with no network access to production
// The Docker network the container runs in has no route to production endpoints
```

**Q23. How do you configure Jest to run database tests separately from unit tests?**
A: Use Jest's `projects` or `testPathPattern` to separate fast unit tests from slow database integration tests:

```js
// jest.config.js
export default {
  projects: [
    {
      displayName: "unit",
      testMatch: ["**/__tests__/unit/**/*.test.js"],
      testEnvironment: "node",
    },
    {
      displayName: "integration",
      testMatch: ["**/__tests__/integration/**/*.test.js"],
      testEnvironment: "node",
      testTimeout: 30_000,   // longer timeout for container startup
      maxWorkers: 2,         // fewer workers to avoid exhausting DB connections
    },
  ],
};
```

CI pipeline separation:
```yaml
# .github/workflows/ci.yml
- name: Unit tests (fast, every commit)
  run: npx jest --selectProjects unit

- name: Integration tests (slower, every PR)
  run: npx jest --selectProjects integration
```

## Section 7: Scenario / System Design Style Questions

**Q24. "Your team's integration test suite takes 8 minutes. Developers skip it locally and it only runs in CI. How do you fix it?"**
A: Eight minutes is a feedback loop problem — slow tests don't get run, so they don't provide value. Attack it at multiple levels:

1. **Profile first** — `jest --verbose` and timing output reveal which files are slow. Often 20% of test files account for 80% of the time.
2. **Container reuse** — if a new Docker container starts for every test file, that's 5–10 seconds of overhead per file multiplied by every file. Share one container across the entire run via `globalSetup`/`globalTeardown`.
3. **Transaction rollback over truncation** — replacing `beforeEach` truncation with transaction rollback cuts per-test overhead significantly.
4. **Parallelize** — increase `--maxWorkers` with per-worker schema isolation. 4 workers typically halve wall-clock time.
5. **Split the suite** — unit tests run on every commit (fast); integration tests run on every PR (acceptable at 2–3 minutes). PR-blocking only for the integration suite; unit suite blocks on every push.
6. **Identify serial bottlenecks** — tests that share global state and can't be parallelized. Refactor to make them independent.

Target: integration tests under 2 minutes locally so developers actually run them.

**Q25. "A bug was reported in production: a unique constraint violation on the `email` column that your test suite didn't catch. Your tests use mocked repositories. What change do you make?"**
A: The mock can't enforce constraints — it's the database that does. The fix is an integration test that runs the actual insert against a real database engine with the real schema:

```js
// This test would have caught the bug
test("rejects duplicate email with a unique constraint error", async () => {
  await db("users").insert({ name: "Alice", email: "alice@example.com" });

  await expect(
    db("users").insert({ name: "Alice2", email: "alice@example.com" })
  ).rejects.toMatchObject({
    message: expect.stringMatching(/unique/i),
    // PostgreSQL specific — check the constraint name if your error handling depends on it
    constraint: "users_email_unique",
  });
});
```

More broadly: use mocks for unit-testing logic (branching, computation, transformation); use real database tests for anything that relies on database-level behavior (constraints, cascades, transaction semantics). The rule: if the database would behave differently from the mock, write a real database test.

**Q26. "You're setting up a CI pipeline for a Node.js API that uses PostgreSQL. Walk through the full database testing strategy."**
A: A production-grade setup:

```
┌─────────────────────────────────────────────────────────────────┐
│  On every commit (< 30 seconds)                                 │
│  → jest --selectProjects unit                                   │
│  → In-memory SQLite for data-layer unit tests                   │
│  → No Docker dependency                                         │
├─────────────────────────────────────────────────────────────────┤
│  On every PR (< 3 minutes)                                      │
│  → jest --selectProjects integration                            │
│  → PostgreSQL 16 via testcontainers (shared across suite)       │
│  → globalSetup starts container + runs migrations               │
│  → Per-worker schema isolation (JEST_WORKER_ID)                 │
│  → Transaction rollback per test                                │
│  → globalTeardown stops container                               │
├─────────────────────────────────────────────────────────────────┤
│  Nightly (uncapped time)                                        │
│  → Full E2E suite against a staging environment                 │
│  → Load tests against a dedicated load-test environment         │
│  → Migration smoke test: fresh DB → migrate.latest() → seed     │
└─────────────────────────────────────────────────────────────────┘
```

Key decisions:
- **Why SQLite for unit tests?** Speed. Data-layer logic (repository pattern) that uses standard SQL can be tested against SQLite with near-zero startup cost.
- **Why PostgreSQL containers for integration tests?** Constraint enforcement, PostgreSQL-specific features (`RETURNING`, `ON CONFLICT`, `jsonb`), and real transaction semantics need the real engine.
- **Why shared container?** Starting one container in `globalSetup` (once per run) vs one per test file (N times per run) is the single biggest lever on integration test speed.
- **Why per-worker schemas?** Allows `--maxWorkers=4` without tests interfering with each other's data.
- **Why transaction rollback?** Fastest isolation mechanism — microseconds per test vs milliseconds for truncation.

## Quick Reference

```js
// ── In-memory SQLite (Knex) ───────────────────────────────────
const db = knex({
  client: "better-sqlite3",
  connection: { filename: ":memory:" },
  useNullAsDefault: true,
});
await db.migrate.latest();
await db.destroy(); // in afterAll

// ── Docker container (PostgreSQL + testcontainers) ────────────
import { PostgreSqlContainer } from "@testcontainers/postgresql";

const container = await new PostgreSqlContainer("postgres:16-alpine")
  .withDatabase("testdb").withUsername("test").withPassword("test")
  .start();

const db = knex({ client: "pg", connection: container.getConnectionUri() });
await db.migrate.latest();

await db.destroy();      // afterAll — close pool first
await container.stop();  // afterAll — then stop container

// ── Transaction rollback isolation ────────────────────────────
beforeEach(async () => { await db.raw("BEGIN"); });
afterEach(async ()  => { await db.raw("ROLLBACK"); });

// ── Truncation (when rollback isn't possible) ─────────────────
// PostgreSQL
await db.raw("TRUNCATE users, orders, order_items RESTART IDENTITY CASCADE");
// SQLite
await db("order_items").delete();
await db("orders").delete();
await db("users").delete();

// ── Per-worker schema isolation ───────────────────────────────
const schema = `test_worker_${process.env.JEST_WORKER_ID}`;
await db.raw("CREATE SCHEMA IF NOT EXISTS ??", [schema]);
await db.raw("SET search_path TO ??", [schema]);

// ── Production database guard ─────────────────────────────────
if (!process.env.DATABASE_URL.includes("localhost")) {
  throw new Error("Refusing to run tests against non-local database");
}
```

## Common Mistakes at a Glance

| Mistake                                            | Symptom                                            | Fix                                                            |
|---                                                 |---                                                 |---                                                             |
| Using SQLite to test PostgreSQL-specific SQL       | Tests pass, production fails                       | Use Docker + PostgreSQL for engine-specific features           |
| `db.destroy()` without `await` in `afterAll`       | Open handle warning; zombie connections            | Always `await` teardown                                        |
| `beforeAll` seeding with mutable data              | Order-dependent, flaky tests                       | Seed in `beforeEach` or use transaction rollback               |
| Truncating parent before child table               | FK constraint error during cleanup                 | Truncate children first, or use `CASCADE`                      |
| No guard against production DATABASE_URL           | Tests run against production data                  | Assert `localhost` in URL before suite starts                  |
| One Docker container per test file                 | 8+ minute integration suite                        | Share one container via `globalSetup`/`globalTeardown`         |
| Tests sharing a single schema in parallel workers  | Flaky, data-collision failures                     | Per-worker schema or database                                  |
| Missing `container.stop()` in teardown             | Zombie Docker containers accumulating on the host  | Always stop in `afterAll`; add `--detectOpenHandles` to debug  |
