# JavaScript / Testing: Testing Transaction Rollback — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "testing transaction rollback" mean, and why does it need its own treatment?**
A: It means two distinct but related things, and conflating them is a common source of confusion:

- **Using rollback as a test isolation mechanism** — wrapping each test in a database transaction that is rolled back in `afterEach`, so every test starts with a clean slate without truncating tables. This is *how* you structure tests.
- **Testing that your application code rolls back correctly** — verifying that when an error occurs mid-transaction, your production code rolls back all partial writes and leaves the database in a consistent state. This is *what* you're asserting.

Both are covered here. The first is an infrastructure pattern that makes every database test suite faster and safer. The second is a functional correctness requirement: your application promises atomicity ("all or nothing"), and you need tests that prove it keeps that promise. The reason both need careful treatment is that they interact in non-obvious ways — a test that uses rollback for isolation can inadvertently hide a bug in the code under test that also uses transactions.

**Q2. What is a database transaction, and what four properties does it guarantee?**
A: A transaction is a unit of work that groups one or more SQL statements so they succeed or fail together. The four guarantees are **ACID**:

- **Atomicity** — all statements in the transaction are applied, or none are. There is no partial state: a transaction that fails mid-way leaves the database exactly as it was before the transaction started.
- **Consistency** — a transaction can only bring the database from one valid state to another. Constraints (unique, foreign key, check) are enforced at commit time; a transaction that would violate a constraint is rejected in full.
- **Isolation** — concurrent transactions do not see each other's uncommitted changes. The degree of isolation is configurable (read uncommitted → read committed → repeatable read → serializable) and affects what anomalies are possible.
- **Durability** — once a transaction commits, the changes survive crashes, power failures, and restarts. Committed data is written to durable storage.

In testing, **atomicity** is what you rely on for isolation (rollback undoes everything), and **isolation** is what determines whether two parallel test workers can interfere with each other.

**Q3. What are the three things that can end a transaction, and which ones matter for testing?**
A:
- **`COMMIT`** — makes all changes permanent and visible to other transactions. In testing, a commit means the data persists past the current test — exactly what you want to *avoid* for isolation.
- **`ROLLBACK`** — discards all changes since the transaction began. In testing, this is the cleanup mechanism: roll back instead of commit and the test leaves no trace.
- **Implicit rollback on error** — if a transaction encounters an unhandled error (a constraint violation, a server crash, an explicit `RAISE`), the database automatically rolls back. In production code, this is the behavior you're testing for; in test setup, it's a trap — if the database rolls back your test transaction due to an error, your `afterEach` `ROLLBACK` has nothing to roll back, and subsequent tests may see a dirty or inconsistent state.

Understanding all three is essential because production code manages its own transactions, and your test harness manages its own — and these two layers interact.

## Section 2: Rollback as a Test Isolation Mechanism

**Q4. How does the transaction rollback isolation pattern work?**
A: The pattern wraps every test in a transaction that is never committed — only rolled back:

```
beforeEach: BEGIN
  test body:
    INSERT INTO users ...   ← write 1 (inside the transaction)
    UPDATE orders ...       ← write 2 (inside the transaction)
    SELECT * FROM users ... ← reads see the uncommitted writes above
    expect(...)             ← assert on the result
afterEach: ROLLBACK         ← write 1 and write 2 are discarded atomically
```

The next test runs `BEGIN` against a database identical to the one before the previous test's writes. No truncation, no re-seeding, no manual cleanup — the rollback handles everything in a single log operation.

**Q5. How do you implement transaction rollback isolation in Jest with Knex?**
A:

```js
// test/helpers/transactionContext.js
import knex from "knex";

export function createTransactionContext(db) {
  let trx;

  async function begin() {
    trx = await db.transaction();   // start a transaction, get a transaction object
    return trx;                     // tests use trx instead of db directly
  }

  async function rollback() {
    if (trx && !trx.isCompleted()) {
      await trx.rollback();         // discard all writes from this test
    }
  }

  return { begin, rollback };
}
```

```js
// test/users.test.js
import { createTestDb }           from "./helpers/db.js";
import { createTransactionContext } from "./helpers/transactionContext.js";
import { UserRepository }          from "../src/repositories/UserRepository.js";

const db = createTestDb();
const { begin, rollback } = createTransactionContext(db);

let trx;
let userRepo;

beforeAll(async () => {
  await db.migrate.latest();
});

afterAll(async () => {
  await db.destroy();
});

beforeEach(async () => {
  trx = await begin();
  userRepo = new UserRepository(trx); // inject the transaction as the connection
});

afterEach(async () => {
  await rollback();
});

test("creates a user", async () => {
  const user = await userRepo.create({ name: "Alice", email: "alice@example.com" });
  expect(user).toMatchObject({ name: "Alice", email: "alice@example.com" });
  // afterEach rolls back — user row never committed
});

test("finds no users in a clean state", async () => {
  const users = await trx("users").select("*");
  expect(users).toHaveLength(0); // Alice from the previous test is gone
});
```

**Q6. Why is transaction rollback isolation faster than table truncation?**
A: Truncation performs real I/O — it scans and removes rows, updates statistics, resets sequences, and writes to the WAL (write-ahead log). For large tables or many tables it is measurably slow. A rollback is a single log operation: the database discards the transaction's log entries, and no table data is touched. For a test suite with 200 tests, the difference between 10ms of truncation and <1ms of rollback per test compounds to seconds of savings — and unlike truncation, rollback requires no knowledge of table dependency order (no FK constraint violations to manage).

**Q7. What is the critical requirement for transaction rollback isolation to work?**
A: Every database call in the test — in the test body, in the code under test, in helper functions — must use the *same* transaction object. If any piece of code opens its own separate connection and issues SQL outside the transaction, those writes are not covered by the rollback:

```js
// ✗ Broken — the repository opens its own connection, not the test transaction
class UserRepository {
  constructor() {
    this.db = require("../db"); // imports the module-level singleton
  }
  async create(data) {
    return this.db("users").insert(data); // uses a different connection — not rolled back
  }
}

// ✓ Correct — the transaction is injected and all SQL goes through it
class UserRepository {
  constructor(db) {
    this.db = db; // the caller decides which connection to use
  }
  async create(data) {
    return this.db("users").insert(data); // uses whatever was injected (trx in tests)
  }
}
```

This is the single biggest reason to use dependency injection for database access — it's not just about testability in the abstract, it's about being able to inject the test transaction and have the isolation guarantee hold.

## Section 3: Testing Application Rollback Behavior

**Q8. What is the difference between testing rollback as isolation vs testing rollback as behavior?**
A: These are orthogonal concerns that look similar but test completely different things:

- **Rollback as isolation** — your *test harness* rolls back after every test. The code under test may never call `ROLLBACK` itself. You're using the database's transaction machinery as a cleanup tool.
- **Rollback as behavior** — your *application code* starts a transaction, does multiple writes, encounters an error, and calls `ROLLBACK` (or allows the database to do it implicitly). You're asserting that this rollback actually happened — that none of the partial writes persisted.

```js
// Testing rollback as BEHAVIOR — this is what the application is supposed to do
test("rolls back all writes when payment fails", async () => {
  const orderCountBefore = await db("orders").count("id as n").first();

  // This function opens a transaction internally, writes an order,
  // then calls a payment gateway — if payment fails, it should roll back
  await expect(
    placeOrder({ items: [...], paymentMethod: "failing-card" })
  ).rejects.toThrow(PaymentError);

  const orderCountAfter = await db("orders").count("id as n").first();

  // The order should not have been persisted — rollback happened
  expect(orderCountAfter.n).toBe(orderCountBefore.n);
});
```

**Q9. What is the fundamental pattern for asserting that a rollback occurred?**
A: Capture the state *before*, trigger the failure, then assert the state *after* matches the state *before*:

```js
// The before-after pattern
test("rolls back partial writes on error", async () => {
  // 1. Capture state before
  const [usersBefore, walletsBefore] = await Promise.all([
    db("users").count("id as n").first(),
    db("wallets").count("id as n").first(),
  ]);

  // 2. Trigger the operation that should fail and roll back
  await expect(
    registerUserWithWallet({ email: "alice@example.com", initialBalance: -1 })
  ).rejects.toThrow(ValidationError);

  // 3. Assert state after matches state before
  const [usersAfter, walletsAfter] = await Promise.all([
    db("users").count("id as n").first(),
    db("wallets").count("id as n").first(),
  ]);

  expect(usersAfter.n).toBe(usersBefore.n);    // no user was created
  expect(walletsAfter.n).toBe(walletsBefore.n); // no wallet was created
});
```

The key insight: you're not asserting what error was thrown (though you should also assert that) — you're asserting on the *database state* after the failure. A test that only checks `rejects.toThrow(ValidationError)` doesn't tell you whether the partial writes were cleaned up.

**Q10. How do you write the application code that the rollback behavior test is verifying?**
A: The production code wraps multiple writes in an explicit transaction and re-throws errors so the transaction is rolled back:

```js
// src/services/userService.js
export async function registerUserWithWallet(db, { email, initialBalance }) {
  return db.transaction(async (trx) => {
    // Write 1 — create the user
    const [user] = await trx("users")
      .insert({ email })
      .returning("*");

    // Validation that could fail after the first write
    if (initialBalance < 0) {
      throw new ValidationError("initialBalance must be non-negative");
      // ↑ throwing inside db.transaction() causes Knex to automatically ROLLBACK
      // the user row created above is discarded
    }

    // Write 2 — create the wallet (only reached if no error above)
    await trx("wallets").insert({ userId: user.id, balance: initialBalance });

    return user;
  });
  // If the callback throws, Knex calls trx.rollback() before re-throwing
  // If the callback resolves, Knex calls trx.commit()
}
```

The test verifies that when `ValidationError` is thrown inside the transaction, the `users` row created in Write 1 is not present after the function returns.

**Q11. What is a partial write, and why is testing for it specifically important?**
A: A partial write is a database write that completes (succeeds at the SQL level) but should be undone because a subsequent step in the same logical operation fails. Partial writes are the bug that transactions prevent — but only if the code actually uses transactions correctly.

Consider a bank transfer: debit account A (Write 1), credit account B (Write 2). If Write 2 fails and the code doesn't roll back, account A is debited but account B is never credited. The money disappears. A test that only verifies the error is thrown would pass — but the data corruption would still happen:

```js
// ✗ Insufficient — only checks the error, not the data integrity
test("transfer fails on invalid amount", async () => {
  await expect(transfer({ from: 1, to: 2, amount: -100 })).rejects.toThrow();
});

// ✓ Complete — checks error AND data integrity
test("transfer rolls back debit when credit fails", async () => {
  await db("accounts").insert([
    { id: 1, balance: 500 },
    { id: 2, balance: 100 },
  ]);

  await expect(
    transfer({ from: 1, to: 2, amount: -100 }) // invalid amount triggers error after debit
  ).rejects.toThrow(ValidationError);

  const [accountA, accountB] = await Promise.all([
    db("accounts").where({ id: 1 }).first(),
    db("accounts").where({ id: 2 }).first(),
  ]);

  expect(accountA.balance).toBe(500); // unchanged — debit rolled back
  expect(accountB.balance).toBe(100); // unchanged — credit never happened
});
```

## Section 4: The Nested Transaction Problem

**Q12. What is the nested transaction problem in database tests?**
A: The nested transaction problem occurs when your test harness uses a transaction for isolation (the outer transaction, managed by `beforeEach`/`afterEach`) and the code under test also opens its own transaction internally (the inner transaction). In most databases, true nested transactions are not supported — what happens instead depends on the engine and ORM:

- **PostgreSQL with Knex** — calling `db.transaction()` when a transaction is already open starts a new *connection* with its own transaction. The inner transaction commits independently of the outer transaction. When `afterEach` rolls back the outer transaction, the inner transaction's commits are already permanent — the test isolation is broken.
- **SQLite** — attempting to `BEGIN` inside an existing `BEGIN` raises `SQLITE_ERROR: cannot start a transaction within a transaction`.

The result: writes made by the inner transaction survive the outer rollback, leaking data between tests.

**Q13. What is a savepoint, and how does it solve the nested transaction problem?**
A: A savepoint is a named marker within an existing transaction. You can `ROLLBACK TO SAVEPOINT name` to undo all changes since the savepoint without ending the outer transaction, and `RELEASE SAVEPOINT name` to discard the savepoint marker (without rolling back — the work is retained in the outer transaction). This gives you the semantics of nested transactions:

```sql
BEGIN;                          -- outer transaction (test harness)
  SAVEPOINT before_operation;   -- mark the state before the operation
  INSERT INTO users ...;        -- write A
  INSERT INTO orders ...;       -- write B
  ROLLBACK TO SAVEPOINT before_operation; -- undo write A and write B
  -- outer transaction is still open; database is at state before write A
ROLLBACK;                       -- outer rollback (afterEach)
```

PostgreSQL, MySQL (InnoDB), and SQLite all support savepoints. They are the mechanism that lets your test harness wrap everything in a transaction even when the code under test creates its own.

**Q14. How do you implement savepoint-based isolation so that application transaction calls use savepoints instead of real nested transactions?**
A: The approach is to intercept the ORM's transaction method in tests and replace it with a savepoint-backed equivalent. For Knex:

```js
// test/helpers/savepointTransaction.js
let savepointCounter = 0;

export function wrapWithSavepoints(trx) {
  // Replace trx.transaction() with a savepoint-based version
  const originalTransaction = trx.transaction.bind(trx);

  trx.transaction = async (callback) => {
    const savepointName = `sp_${++savepointCounter}`;

    await trx.raw(`SAVEPOINT ??`, [savepointName]);

    try {
      // Pass trx (the outer transaction) to the callback, not a new connection
      const result = await callback(trx);
      await trx.raw(`RELEASE SAVEPOINT ??`, [savepointName]);
      return result;
    } catch (err) {
      await trx.raw(`ROLLBACK TO SAVEPOINT ??`, [savepointName]);
      throw err; // re-throw so the application's error handling still works
    }
  };

  return trx;
}
```

```js
// test/users.test.js
beforeEach(async () => {
  trx = await db.transaction();
  wrapWithSavepoints(trx); // patch trx.transaction() to use savepoints

  // Now when application code calls trx.transaction(callback),
  // it gets a savepoint instead of a real new transaction
  userService = new UserService(trx);
});

afterEach(async () => {
  await trx.rollback(); // outer rollback cleans everything up
});
```

**Q15. How do you verify that the savepoint-based approach correctly tests application rollback logic?**
A: Write a test where the application code *should* roll back (due to an error), and assert that neither the writes before the error nor the writes after it persist — just as you would without savepoints:

```js
test("application rollback works correctly through savepoints", async () => {
  // Pre-condition: no users exist
  const before = await trx("users").count("id as n").first();
  expect(before.n).toBe(0);

  // Application code: starts its own "transaction" (now a savepoint)
  // inserts a user, then throws — triggering the savepoint rollback
  await expect(
    userService.createWithMandatoryProfile({
      email: "alice@example.com",
      profileData: null, // null triggers error after user insert
    })
  ).rejects.toThrow(ValidationError);

  // Assert: the user insert was rolled back (savepoint rollback worked)
  const after = await trx("users").count("id as n").first();
  expect(after.n).toBe(0); // savepoint rolled back the user insert
});
```

If this test passes, both the savepoint mechanism and the application's rollback logic are verified simultaneously.

## Section 5: Testing Specific Rollback Scenarios

**Q16. How do you test rollback on a constraint violation?**
A: Constraint violations (unique, foreign key, not null, check) cause the database to implicitly abort the current statement — and in PostgreSQL, abort the entire transaction. Test by inserting a row that violates a constraint and asserting that neither the violating row nor any rows inserted before it in the same transaction persist:

```js
test("rolls back entire transaction on unique constraint violation", async () => {
  // Seed an existing user
  await db("users").insert({ id: 1, email: "alice@example.com" });

  const countBefore = await db("orders").count("id as n").first();

  // This function inserts an order, then tries to insert a user with a duplicate email
  // The unique constraint violation should roll back both writes
  await expect(
    placeOrderForExistingEmail({
      email: "alice@example.com", // duplicate — will violate unique constraint
      orderData: { total: 50 },
    })
  ).rejects.toThrow(/unique/i);

  const countAfter = await db("orders").count("id as n").first();

  // The order write that happened before the constraint violation was also rolled back
  expect(countAfter.n).toBe(countBefore.n);
});
```

Note: in PostgreSQL, after a constraint violation the transaction is in an **aborted state** — any subsequent SQL in the same transaction raises `ERROR: current transaction is aborted, commands ignored until end of transaction block`. This is why application code must catch the error and explicitly `ROLLBACK` (or use a savepoint) rather than trying to continue.

**Q17. How do you test rollback when a downstream service call fails mid-transaction?**
A: Mock the downstream service to throw at a specific point, then assert the database state is clean:

```js
import { paymentGateway } from "../src/services/paymentGateway.js";

jest.mock("../src/services/paymentGateway.js");

test("rolls back order creation when payment gateway throws", async () => {
  paymentGateway.charge.mockRejectedValue(new PaymentError("Card declined"));

  const orderCountBefore = await db("orders").count("id as n").first();
  const itemCountBefore  = await db("order_items").count("id as n").first();

  await expect(
    checkout({
      userId: 1,
      items: [{ sku: "ABC", qty: 2, price: 25 }],
      paymentToken: "tok_declined",
    })
  ).rejects.toThrow(PaymentError);

  const orderCountAfter = await db("orders").count("id as n").first();
  const itemCountAfter  = await db("order_items").count("id as n").first();

  // Both the order header and its line items were rolled back
  expect(orderCountAfter.n).toBe(orderCountBefore.n);
  expect(itemCountAfter.n).toBe(itemCountBefore.n);
});
```

This test verifies the critical invariant: the database is never in a state where an order exists with no payment, or where order items reference an order that was rolled back.

**Q18. How do you test idempotency — that retrying a failed operation doesn't create duplicate data?**
A: Run the operation twice (simulating a retry), assert that the second call either succeeds cleanly or fails gracefully, and verify the expected data exists exactly once:

```js
test("retrying a failed create is idempotent — no duplicate rows", async () => {
  const payload = { name: "Alice", email: "alice@example.com" };

  // First attempt — fails partway through
  paymentGateway.charge.mockRejectedValueOnce(new Error("timeout"));
  await expect(registerAndCharge(payload)).rejects.toThrow();

  // Second attempt — succeeds
  paymentGateway.charge.mockResolvedValueOnce({ transactionId: "txn_123" });
  const user = await registerAndCharge(payload);

  expect(user.email).toBe("alice@example.com");

  // Assert no duplicate users were created
  const allUsers = await db("users").where({ email: "alice@example.com" });
  expect(allUsers).toHaveLength(1);
});
```

**Q19. How do you test rollback in a multi-service saga pattern where each service has its own database?**
A: True distributed transactions (two-phase commit) are rare in modern architectures. Sagas use compensating transactions instead — each step has a corresponding undo operation. Testing a saga means verifying that compensating transactions are called when a step fails:

```js
// The saga: create order → reserve inventory → charge payment
// If charge fails, compensation: release inventory → cancel order

test("saga compensates correctly when payment fails", async () => {
  inventoryService.reserve.mockResolvedValue({ reservationId: "res_1" });
  paymentService.charge.mockRejectedValue(new PaymentError("insufficient funds"));

  // Compensation mocks
  inventoryService.release.mockResolvedValue({ released: true });
  orderService.cancel.mockResolvedValue({ cancelled: true });

  await expect(
    placeOrderSaga({ userId: 1, items: [...], paymentToken: "tok_fail" })
  ).rejects.toThrow(PaymentError);

  // Assert compensating transactions were called
  expect(inventoryService.release).toHaveBeenCalledWith({ reservationId: "res_1" });
  expect(orderService.cancel).toHaveBeenCalledWith(expect.objectContaining({ userId: 1 }));

  // Assert local database state is clean
  const orders = await db("orders").where({ userId: 1 });
  expect(orders).toHaveLength(0);
});
```

## Section 6: Pitfalls & Best Practices

**Q20. What is the "aborted transaction" trap in PostgreSQL, and how do you avoid it?**
A: In PostgreSQL, once a transaction encounters an error, it enters an **aborted state**. Any further SQL within that transaction raises `ERROR: current transaction is aborted, commands ignored until end of transaction block` — even if the SQL itself would be valid. This means you cannot catch an error inside a transaction and continue writing:

```js
// ✗ Broken — PostgreSQL aborts the transaction on the first error
await db.raw("BEGIN");
try {
  await db("users").insert({ email: "duplicate@example.com" }); // violates UNIQUE
} catch (err) {
  // Transaction is now ABORTED — any SQL here will fail
  await db("users").insert({ email: "fallback@example.com" }); // ERROR: transaction is aborted
}
await db.raw("ROLLBACK");

// ✓ Correct — use a savepoint to recover from a specific error
await db.raw("BEGIN");
await db.raw("SAVEPOINT before_insert");
try {
  await db("users").insert({ email: "duplicate@example.com" });
  await db.raw("RELEASE SAVEPOINT before_insert");
} catch (err) {
  await db.raw("ROLLBACK TO SAVEPOINT before_insert"); // recover, don't abort
  // transaction is still alive — continue with fallback logic
  await db("users").insert({ email: "fallback@example.com" });
}
await db.raw("COMMIT");
```

In tests, this trap manifests as mysterious failures where a test that deliberately triggers a constraint violation causes the next SQL statement in the same test to fail with the aborted-transaction error.

**Q21. What is the "rollback of a rollback" problem, and when does it appear?**
A: When `afterEach` calls `ROLLBACK` but the transaction was already rolled back (because the application code rolled it back due to an error), the rollback command has nothing to roll back. Depending on the driver, this either silently succeeds or throws `"There is no transaction in progress"`. If the driver throws, the test suite crashes on cleanup even though the test itself passed:

```js
// ✗ Fragile — throws if the transaction was already rolled back
afterEach(async () => {
  await db.raw("ROLLBACK"); // throws if no active transaction
});

// ✓ Safe — check before rolling back
afterEach(async () => {
  if (trx && !trx.isCompleted()) {
    await trx.rollback();
  }
});
```

Knex's `trx.isCompleted()` returns `true` if the transaction was already committed or rolled back. The equivalent for raw `pg` clients is checking whether the client's transaction state is idle.

**Q22. What does `expect.assertions(n)` protect against in rollback tests specifically?**
A: Rollback tests often have assertions inside `catch` blocks or inside `try` blocks that only run if a throw happens. Without `expect.assertions(n)`, a test where the function unexpectedly *succeeds* (no throw, no rollback) would skip the assertions in the `catch` and pass silently:

```js
// ✗ Dangerous — if placeOrder doesn't throw, the catch never runs, 0 assertions execute
test("rolls back on payment failure", async () => {
  try {
    await placeOrder({ paymentToken: "failing" });
  } catch {
    const count = await db("orders").count("id as n").first();
    expect(count.n).toBe(0); // only runs if placeOrder throws
  }
});

// ✓ Safe — fails if the catch block is never reached
test("rolls back on payment failure", async () => {
  expect.assertions(2); // error assertion + count assertion

  await expect(
    placeOrder({ paymentToken: "failing" })
  ).rejects.toThrow(PaymentError); // assertion 1

  const count = await db("orders").count("id as n").first();
  expect(count.n).toBe(0); // assertion 2
});
```

Prefer the `.rejects.toThrow()` pattern over `try/catch` — it doesn't require `expect.assertions` because `rejects` fails automatically if the Promise resolves.

**Q23. How do you test rollback behavior without polluting the test isolation transaction?**
A: This is the deepest conflict in database test design. If you use the outer transaction for isolation, and the code under test rolls back an inner transaction (via savepoint), the savepoint rollback undoes the test's setup data too — unless setup and the operation under test are in different savepoints:

```js
test("rolls back transfer but preserves account balances", async () => {
  // Setup data — inserted in the outer transaction (before any savepoint)
  await trx("accounts").insert([
    { id: 1, balance: 500 },
    { id: 2, balance: 100 },
  ]);

  // The transfer opens its own "transaction" (savepoint sp_1)
  // It debits account 1 (inside sp_1), fails, rolls back sp_1
  // Account 1 balance is restored to 500 (savepoint rolled back)
  await expect(
    accountService.transfer({ from: 1, to: 2, amount: -50 })
  ).rejects.toThrow(ValidationError);

  // The setup data (inserted before sp_1) is still visible
  // because the savepoint rollback only undid changes *since* the savepoint
  const [a1, a2] = await Promise.all([
    trx("accounts").where({ id: 1 }).first(),
    trx("accounts").where({ id: 2 }).first(),
  ]);

  expect(a1.balance).toBe(500); // debit was rolled back by the savepoint
  expect(a2.balance).toBe(100); // credit never happened
});
```

When savepoints are implemented correctly, the outer transaction (and its setup data) survives the inner savepoint rollback. The outer `afterEach` rollback then discards both the setup data and any surviving writes from the test.

## Section 7: Scenario / System Design Style Questions

**Q24. "A bug report says that when a user registration fails halfway through, orphaned rows appear in the `email_verifications` table. The code has a `db.transaction()` call. What went wrong and how do you write a test that catches it?"**
A: The most common cause: the `email_verifications` insert is happening *outside* the transaction — either before the transaction starts, after it's committed, or on a separate connection that wasn't included in the transaction scope. The transaction rolls back the `users` insert but the `email_verifications` insert was already committed independently.

The test:
```js
test("no orphaned email_verifications row when registration fails", async () => {
  // Force failure at the payment step (after user and email_verification are written)
  mockStripe.createCustomer.mockRejectedValue(new Error("Stripe unavailable"));

  const verificationCountBefore = await db("email_verifications")
    .count("id as n").first();

  await expect(
    registerUser({ email: "alice@example.com", plan: "pro" })
  ).rejects.toThrow();

  const verificationCountAfter = await db("email_verifications")
    .count("id as n").first();

  // This assertion fails if email_verifications is written outside the transaction
  expect(verificationCountAfter.n).toBe(verificationCountBefore.n);
});
```

The fix: ensure every write in the registration flow uses the same transaction object. Audit the service code for any `db(...)` calls that use the module-level connection instead of the injected transaction.

**Q25. "You're designing the test suite for a payment service. Payments involve five database writes across three tables. How do you structure rollback tests to cover it thoroughly?"**
A: Structure tests around the failure points — there are five writes, so there are five scenarios where a failure after write N should roll back writes 1 through N:

```js
describe("payment rollback coverage", () => {
  // Helper — counts rows across all three tables
  async function snapshot() {
    const [payments, ledger, audit] = await Promise.all([
      db("payments").count("id as n").first(),
      db("ledger_entries").count("id as n").first(),
      db("audit_log").count("id as n").first(),
    ]);
    return {
      payments: payments.n,
      ledger: ledger.n,
      audit: audit.n,
    };
  }

  test("fails at write 1 (payment header) — all tables unchanged", async () => {
    db.mockFailAt("payments", "insert");
    const before = await snapshot();
    await expect(processPayment(validPayload)).rejects.toThrow();
    expect(await snapshot()).toStrictEqual(before);
  });

  test("fails at write 3 (ledger debit) — payments and prior ledger entries rolled back", async () => {
    db.mockFailAt("ledger_entries", "insert", { onCall: 1 }); // first ledger insert
    const before = await snapshot();
    await expect(processPayment(validPayload)).rejects.toThrow();
    expect(await snapshot()).toStrictEqual(before); // all rolled back, not just the failed write
  });

  test("fails at write 5 (audit log) — all previous writes rolled back", async () => {
    db.mockFailAt("audit_log", "insert");
    const before = await snapshot();
    await expect(processPayment(validPayload)).rejects.toThrow();
    expect(await snapshot()).toStrictEqual(before);
  });

  test("succeeds — all five writes committed", async () => {
    const before = await snapshot();
    await processPayment(validPayload);
    const after = await snapshot();

    expect(after.payments).toBe(before.payments + 1);
    expect(after.ledger).toBe(before.ledger + 2);    // debit + credit
    expect(after.audit).toBe(before.audit + 1);
  });
});
```

The `snapshot()` helper makes the before-after pattern concise and extends automatically when new tables are added to the payment flow. Each failure-point test verifies the full rollback, not just that the specific write was undone.

**Q26. "A colleague argues that testing rollback is redundant because the database guarantees it — if you use `db.transaction()`, the database will always roll back on error. Do you agree?"**
A: Partially — the database *does* guarantee that a transaction's writes are rolled back if the transaction is rolled back. But the application code might not actually use `db.transaction()` correctly in all cases. Tests catch the following real-world bugs that "the database guarantees it" does not protect against:

- **Writes outside the transaction** — a function that calls `db.transaction(callback)` but also makes writes to a second table using the module-level `db` connection directly. The second write is not in the transaction and survives the rollback.
- **Swallowed errors** — a `try/catch` inside the transaction that catches the error and *doesn't* re-throw. Knex doesn't know the error occurred; it commits the transaction. The "rollback" never happens.
- **Wrong connection passed** — a service that accepts a `db` argument but ignores it and uses `this.db` (the module singleton) instead. All its writes go outside the transaction.
- **Async timing errors** — a `Promise` that is fired inside the transaction callback but not `await`ed. The write may execute after the transaction has committed or rolled back.
- **Saga compensation bugs** — in multi-service operations, "rollback" means calling compensating transactions on other services. The database has no knowledge of these — your code (and your tests) are the only thing that verifies compensation happens.

The guarantee is real but narrow: *if* the right connection is used, *if* errors are re-thrown, *if* all writes are awaited, *then* the database rolls back correctly. Tests verify all those "ifs."

## Quick Reference

```js
// ── Rollback isolation (beforeEach / afterEach) ───────────────
beforeEach(async () => { trx = await db.transaction(); });
afterEach(async ()  => { if (!trx.isCompleted()) await trx.rollback(); });

// ── Savepoint-based nested transaction (for code that calls db.transaction()) ──
trx.transaction = async (callback) => {
  const sp = `sp_${++counter}`;
  await trx.raw("SAVEPOINT ??", [sp]);
  try {
    const result = await callback(trx);
    await trx.raw("RELEASE SAVEPOINT ??", [sp]);
    return result;
  } catch (err) {
    await trx.raw("ROLLBACK TO SAVEPOINT ??", [sp]);
    throw err;
  }
};

// ── Before-after snapshot pattern ────────────────────────────
async function countAll() {
  const [a, b] = await Promise.all([
    db("table_a").count("id as n").first(),
    db("table_b").count("id as n").first(),
  ]);
  return { a: a.n, b: b.n };
}

test("rolls back both tables on error", async () => {
  const before = await countAll();
  await expect(operation()).rejects.toThrow();
  expect(await countAll()).toStrictEqual(before);
});

// ── Guard against aborted transaction (PostgreSQL) ────────────
// Use savepoints to recover from a specific error without aborting the transaction
await trx.raw("SAVEPOINT sp");
try { await trx("t").insert(data); await trx.raw("RELEASE SAVEPOINT sp"); }
catch { await trx.raw("ROLLBACK TO SAVEPOINT sp"); }

// ── Safe afterEach rollback ───────────────────────────────────
afterEach(async () => {
  if (trx && !trx.isCompleted()) await trx.rollback();
});

// ── expect.assertions guard for rollback tests ────────────────
test("rolls back and throws", async () => {
  expect.assertions(2);
  await expect(op()).rejects.toThrow(SomeError); // assertion 1
  expect(await db("t").count("id as n").first()).toMatchObject({ n: 0 }); // assertion 2
});
```

## Common Mistakes at a Glance

| Mistake                                                  | Symptom                                                       | Fix                                                                   |
|---                                                       |---                                                            |---                                                                    |
| Code under test uses a different DB connection           | Writes survive the rollback; tests pollute each other         | Inject the transaction; use dependency injection throughout           |
| No savepoint wrapping for nested `db.transaction()` calls| Inner transaction commits; outer rollback doesn't undo it     | Patch `trx.transaction` to use savepoints in test setup               |
| `afterEach` rollback on already-rolled-back transaction  | "No transaction in progress" error crashes the suite          | Guard with `if (!trx.isCompleted())` before rolling back              |
| Only asserting on the thrown error, not the DB state     | Partial write bug ships to production                         | Always assert DB state after failure, not just the error type         |
| PostgreSQL aborted-transaction state not handled         | Subsequent SQL in the same transaction fails unexpectedly     | Use savepoints for error recovery; never continue after abort         |
| `expect.assertions` missing in try/catch rollback tests  | Test passes silently when function doesn't throw              | Add `expect.assertions(n)` or switch to `rejects.toThrow()` pattern   |
| Saga compensation not tested                             | Compensation code is broken, discovered in production         | Mock each step's failure and assert compensation calls + DB state      |
