# JavaScript / Testing: Async Testing — `async/await`, `resolves`/`rejects` Matchers — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is async code harder to test than synchronous code?**
A: Synchronous tests are simple: call a function, inspect the return value. Async code introduces a gap between *invoking* an operation and *when its result is available* — and Jest, by default, doesn't wait. If Jest finishes executing a test function before the async work completes, it marks the test as passed regardless of what the async code does or asserts:

```js
// ✗ Silently broken — Jest finishes before the Promise resolves
test("fetches user", () => {
  fetchUser(1).then(user => {
    expect(user.name).toBe("Alice"); // runs after Jest has already moved on
  });
});
```

The test above always passes — even if `fetchUser` rejects, or returns a user named "Bob", or never resolves at all. Async testing is fundamentally about *signaling to Jest that it must wait* before evaluating the test outcome.

**Q2. What are the three mechanisms Jest provides for handling async tests?**
A:
- **Returning a Promise** — if the test function returns a Promise, Jest waits for it to settle. The oldest pattern; still valid but verbose.
- **`async/await`** — syntactic sugar over returning a Promise; the most readable and most commonly used pattern today.
- **`resolves`/`rejects` matchers** — Jest's built-in matchers for asserting directly on a Promise's resolved value or rejection reason, used *with* `await`.

All three ultimately tell Jest the same thing: "wait for this Promise before deciding pass or fail." They differ in readability, error message quality, and how much of the assertion work they carry.

**Q3. What happens if you forget `await` in an async test?**
A: The test passes unconditionally — a silent false positive. Without `await`, the `expect()` call returns an unresolved Promise that Jest never waits on:

```js
// ✗ Always passes — the rejected Promise floats away uncaught
test("rejects on invalid input", async () => {
  expect(processData(null)).rejects.toThrow("invalid"); // missing await
});

// ✓ Correct — Jest waits for the assertion Promise to settle
test("rejects on invalid input", async () => {
  await expect(processData(null)).rejects.toThrow("invalid");
});
```

Forgetting `await` on a `.rejects` assertion is particularly dangerous because even a *passing* test — one where the function correctly rejects — will show green. The `expect.assertions(n)` guard is the safety net: it fails the test if the declared number of assertions were never reached.

**Q4. What is `expect.assertions(n)`, and when is it essential?**
A: `expect.assertions(n)` declares that exactly `n` assertions must be called during the test. If fewer are called — because an async branch was never reached, a Promise never settled, or a catch block was skipped — Jest fails the test even though no individual assertion threw:

```js
test("catch block is actually reached", async () => {
  expect.assertions(1); // test fails if the catch is never entered

  try {
    await operationThatShouldReject();
  } catch (err) {
    expect(err.message).toContain("timeout"); // this must run
  }
});
```

It's most essential in `try/catch` async tests where the `catch` block contains the assertion — without the guard, a function that resolves instead of rejecting causes zero assertions to run, and the test passes silently. Less necessary (but still useful as documentation) when using `.rejects` directly, since an unexpected resolution causes `.rejects` to fail on its own.

## Section 2: `async/await` in Tests

**Q5. What is the canonical pattern for testing a Promise-returning function with `async/await`?**
A: Mark the test callback `async`, `await` the async call, and assert on the resolved value:

```js
import { fetchUser } from "../api/users.js";

test("fetchUser returns the correct user", async () => {
  const user = await fetchUser(1);

  expect(user).toStrictEqual({ id: 1, name: "Alice", role: "admin" });
});
```

Jest sees that the test function is `async`, so it receives a Promise from the function call and waits for it to resolve or reject before scoring the test. If `fetchUser` rejects unexpectedly, the `await` re-throws and Jest marks the test as failed with the rejection reason — no extra boilerplate needed.

**Q6. How do you test the *happy path* and *error path* of the same async function?**
A: Two separate tests — one for resolution, one for rejection. Mixing both paths in one test muddies the failure message and violates the "one behavior per test" principle:

```js
// Happy path
test("resolves with user data for a valid id", async () => {
  const user = await fetchUser(1);
  expect(user.name).toBe("Alice");
});

// Error path
test("rejects with NotFoundError for an unknown id", async () => {
  await expect(fetchUser(999)).rejects.toThrow(NotFoundError);
});
```

**Q7. How do you test an async function that has side effects (e.g., writes to a database)?**
A: `await` the call, then separately assert on the side effect using another async query or a spy:

```js
test("createUser persists the user to the database", async () => {
  await createUser({ name: "Bob", email: "bob@example.com" });

  const saved = await db("users").where({ email: "bob@example.com" }).first();
  expect(saved).toMatchObject({ name: "Bob", email: "bob@example.com" });
});
```

For unit tests where the database is mocked, assert on the mock call instead:

```js
test("createUser calls db.insert with correct data", async () => {
  const insertMock = jest.fn().mockResolvedValue({ id: 42 });
  db.insert = insertMock;

  await createUser({ name: "Bob", email: "bob@example.com" });

  expect(insertMock).toHaveBeenCalledWith(
    expect.objectContaining({ name: "Bob", email: "bob@example.com" })
  );
});
```

**Q8. How do you test multiple sequential async operations?**
A: `await` each one in order. Since `async/await` is sequential by default, each `await` waits for the previous operation before continuing:

```js
test("order lifecycle: create → pay → fulfill", async () => {
  const order = await createOrder({ items: [{ sku: "ABC", qty: 2 }] });
  expect(order.status).toBe("pending");

  const paid = await payOrder(order.id, { method: "card" });
  expect(paid.status).toBe("paid");

  const fulfilled = await fulfillOrder(order.id);
  expect(fulfilled.status).toBe("fulfilled");
});
```

If operations are *independent* and can run in parallel, use `Promise.all` — but note that if one assertion fails, `Promise.all` rejects immediately and the remaining assertions don't run, which can make debugging harder:

```js
// Parallel — faster, but first failure short-circuits the rest
const [userA, userB] = await Promise.all([fetchUser(1), fetchUser(2)]);
expect(userA.name).toBe("Alice");
expect(userB.name).toBe("Bob");
```

**Q9. How do you handle `async` `beforeEach` / `afterEach` / `beforeAll` / `afterAll`?**
A: Mark the lifecycle callback `async` and Jest waits for it just as it does for test callbacks:

```js
let db;

beforeAll(async () => {
  db = await connectToTestDatabase();
  await db.migrate.latest();
  await db.seed.run();
});

afterAll(async () => {
  await db.destroy(); // close connection pool — critical to prevent open handle warnings
});

beforeEach(async () => {
  await db("users").truncate(); // reset state between tests
});

test("finds a user", async () => {
  await db("users").insert({ id: 1, name: "Alice" });
  const user = await findUser(1);
  expect(user.name).toBe("Alice");
});
```

A common mistake: forgetting `await` in `afterAll` for teardown (like `db.destroy()`). Jest will warn "A worker process has failed to exit gracefully" — an open handle warning caused by a still-running database connection pool that was never closed.

**Q10. What is a Jest "open handle" warning, and how does async cleanup cause it?**
A: Jest reports "Jest did not exit one second after the test run has completed" when there are lingering async resources — open database connections, active HTTP servers, unresolved timers — that prevent the Node.js process from exiting. Common causes:
- `afterAll` teardown that isn't awaited (connection pool stays open).
- An HTTP server started in `beforeAll` that isn't `close()`d in `afterAll`.
- A `setInterval` or `setTimeout` not cleared after the test.

```js
// ✗ Causes open handle — destroy() is called but not awaited
afterAll(() => {
  db.destroy(); // fire-and-forget — connection pool stays open
});

// ✓ Properly awaited
afterAll(async () => {
  await db.destroy();
});
```

Run Jest with `--detectOpenHandles` to identify which resource is keeping the process alive.

## Section 3: `resolves` Matcher

**Q11. What does the `resolves` matcher do?**
A: `resolves` unwraps a Promise and applies the chained matcher to the resolved value. It must be `await`ed — without `await`, the assertion Promise floats away and the test always passes:

```js
// Equivalent assertions — resolves vs async/await
test("with resolves", async () => {
  await expect(fetchUser(1)).resolves.toStrictEqual({ id: 1, name: "Alice" });
});

test("with async/await", async () => {
  const user = await fetchUser(1);
  expect(user).toStrictEqual({ id: 1, name: "Alice" });
});
```

Both patterns are valid. `resolves` is more concise for single-value assertions; `async/await` is more flexible when you need the resolved value for multiple assertions or further operations.

**Q12. What is the full chain syntax for `resolves`?**
A: `await expect(promise).resolves.matcher(expected)` — the matcher after `.resolves` can be any Jest matcher:

```js
await expect(fetchUser(1)).resolves.toBe(cachedUserRef);          // reference equality
await expect(getCount()).resolves.toBe(42);                        // primitive
await expect(fetchConfig()).resolves.toEqual({ timeout: 5000 });   // deep equal (lenient)
await expect(fetchConfig()).resolves.toStrictEqual({ timeout: 5000 }); // deep equal (strict)
await expect(fetchProfile()).resolves.toMatchObject({ name: "Alice" }); // subset
await expect(getTags()).resolves.toContain("featured");             // membership
await expect(validateForm(data)).resolves.toBeTruthy();            // truthy check
```

**Q13. When should you prefer `resolves` over `async/await`?**
A: `resolves` has a readability advantage for **single-assertion, single-value** tests — the intention is expressed in one line without a variable:

```js
// resolves — concise, reads like a sentence
await expect(getTemperature("London")).resolves.toBeCloseTo(18.5, 1);

// async/await — requires a variable even for one assertion
const temp = await getTemperature("London");
expect(temp).toBeCloseTo(18.5, 1);
```

Prefer `async/await` when:
- You need the resolved value for **multiple assertions**.
- You need to **pass the value to another function** before asserting.
- The assertion is inside a **conditional or loop** (uncommon but valid in parameterized tests).
- **Readability** is better with the value named — complex return shapes are easier to follow with a named variable.

**Q14. Can `resolves` be chained with `.not`?**
A: Yes — `await expect(promise).resolves.not.toContain("error")` is valid. But be careful: `.resolves.not` asserts that the Promise resolves *and* the resolved value does not match. It does *not* assert that the Promise rejects. To assert a Promise doesn't reject at all, just `await` it directly — if it rejects, `await` re-throws and the test fails:

```js
// ✓ Asserts resolves to a value that doesn't contain "error"
await expect(fetchStatus()).resolves.not.toContain("error");

// ✓ Asserts the Promise resolves without rejecting (simplest form)
await expect(fetchStatus()).resolves.toBeDefined();

// Or just — if fetchStatus() rejects, the await throws and the test fails
await fetchStatus();
```

**Q15. What error message does `resolves` produce when a Promise rejects unexpectedly?**
A: When a Promise passed to `.resolves` rejects instead of resolving, Jest throws with a message like:

```
Received promise rejected instead of resolved
Rejected to value: [Error: Network timeout]
```

This is more informative than a raw `UnhandledPromiseRejection` in the terminal because Jest frames it as a test failure — the rejection reason is clearly displayed, the test is marked failed, and the stack trace points to the failing assertion line rather than deep inside the async call stack.

## Section 4: `rejects` Matcher

**Q16. What does the `rejects` matcher do?**
A: `rejects` asserts that a Promise *rejects* and applies the chained matcher to the rejection reason (the thrown error). Like `resolves`, it must be `await`ed:

```js
await expect(fetchUser(999)).rejects.toThrow(NotFoundError);
await expect(fetchUser(999)).rejects.toThrow("User not found");
await expect(processPayment({ amount: -1 })).rejects.toThrow(/invalid amount/i);
```

If the Promise resolves instead of rejecting, Jest fails the test with:
```
Received promise resolved instead of rejected
Resolved to value: { id: 999, name: "Ghost" }
```

**Q17. What matchers are most useful after `.rejects`?**
A:

```js
// toThrow — checks error class, message substring, or regex
await expect(op()).rejects.toThrow(ValidationError);
await expect(op()).rejects.toThrow("must be positive");
await expect(op()).rejects.toThrow(/must be (positive|non-zero)/i);

// toMatchObject — assert on error properties beyond message
await expect(op()).rejects.toMatchObject({
  message: "Validation failed",
  field: "amount",
  code: "OUT_OF_RANGE",
});

// toBeInstanceOf — when you care about the class but not the message
await expect(op()).rejects.toBeInstanceOf(NetworkError);

// toHaveProperty — pick a single property off the rejection
await expect(op()).rejects.toHaveProperty("statusCode", 422);
```

`toMatchObject` after `.rejects` is the most powerful pattern for custom error classes with structured metadata — it lets you assert on any combination of error fields without requiring an exact match on the entire error object.

**Q18. How do you test that a function rejects with specific error metadata (not just the message)?**
A: Two approaches depending on how much you need to assert:

```js
// Option 1 — rejects.toMatchObject (concise, covers most cases)
await expect(createOrder({ quantity: -1 })).rejects.toMatchObject({
  name: "ValidationError",
  field: "quantity",
  code: "NEGATIVE_VALUE",
  statusCode: 400,
});

// Option 2 — catch manually for full access to the error object
expect.assertions(4);
try {
  await createOrder({ quantity: -1 });
} catch (err) {
  expect(err).toBeInstanceOf(ValidationError);
  expect(err.field).toBe("quantity");
  expect(err.code).toBe("NEGATIVE_VALUE");
  expect(err.statusCode).toBe(400);
}
```

Option 1 is preferred — less boilerplate, requires no `expect.assertions` guard because `rejects` fails automatically if the Promise resolves. Option 2 is useful when assertions depend on the error value computed at runtime (e.g., `expect(err.retryAfter).toBeGreaterThan(Date.now())`).

**Q19. How is `rejects.toThrow` different from wrapping the call in `try/catch`?**
A:

| Dimension                   | `rejects.toThrow`                           | `try/catch` with assertion                       |
|---                          |---                                          |---                                               |
| Boilerplate                 | One line                                    | 5+ lines                                         |
| Safety if no rejection      | Fails automatically ("resolved instead of rejected") | Passes silently without `expect.assertions` |
| Error object access         | Limited to matcher interface                | Full access to the `err` object                  |
| Readability                 | High — intent is explicit                   | Lower — catch block indirection                  |
| Best for                    | Most rejection tests                        | Complex assertions on error properties at runtime|

Use `rejects.toThrow` (or `rejects.toMatchObject`) as the default. Reach for `try/catch` only when you need to compute something from the error that a matcher can't express.

**Q20. What happens when you use `rejects` on a synchronous function that throws?**
A: `rejects` only handles Promises — it cannot catch a synchronous throw. A synchronous function that throws will throw *before* a Promise is created, so `expect(syncFn()).rejects` receives the throw as an uncaught exception, not a rejected Promise:

```js
function parsePositive(n) {
  if (n < 0) throw new RangeError("must be positive");
  return n;
}

// ✗ Wrong — parsePositive throws synchronously, no Promise involved
await expect(parsePositive(-1)).rejects.toThrow("must be positive");
// → TypeError: expect(...).rejects is not valid here

// ✓ Correct — use toThrow for synchronous throws
expect(() => parsePositive(-1)).toThrow("must be positive");
```

The rule: `toThrow` is for synchronous functions; `rejects.toThrow` is for async functions and Promise-returning functions.

## Section 5: Mocking Async Dependencies

**Q21. How do you mock a Promise-returning function with Jest?**
A: Use `jest.fn().mockResolvedValue(value)` for the happy path and `jest.fn().mockRejectedValue(error)` for the error path. These are shorthand for `jest.fn().mockReturnValue(Promise.resolve(value))` and `jest.fn().mockReturnValue(Promise.reject(error))`:

```js
// Happy path mock
const fetchUser = jest.fn().mockResolvedValue({ id: 1, name: "Alice" });

// Error path mock
const fetchUser = jest.fn().mockRejectedValue(new NotFoundError("User not found"));

// Different resolution on each call
const fetchUser = jest.fn()
  .mockResolvedValueOnce({ id: 1, name: "Alice" })  // first call
  .mockResolvedValueOnce({ id: 2, name: "Bob" })    // second call
  .mockRejectedValueOnce(new Error("rate limited")); // third call
```

**Q22. How do you mock a module's async function with `jest.mock()`?**
A:

```js
// api/users.js — the module under test imports this
import { fetchUser } from "../api/users.js";

jest.mock("../api/users.js", () => ({
  fetchUser: jest.fn(),
}));

test("displays user name on load", async () => {
  fetchUser.mockResolvedValue({ id: 1, name: "Alice" });

  const result = await loadUserProfile(1);

  expect(result.displayName).toBe("Alice");
  expect(fetchUser).toHaveBeenCalledWith(1);
});
```

Each test should configure the mock's resolved/rejected value via `mockResolvedValue` or `mockRejectedValue` within the test body — not at the module mock level — so tests are independent. Use `beforeEach(() => jest.clearAllMocks())` to reset call history between tests.

**Q23. How do you test retry logic in an async function?**
A: Configure the mock to reject a specified number of times before resolving, then assert on both the final result and the number of attempts:

```js
test("retries up to 3 times before succeeding", async () => {
  const fetchWithRetry = require("./fetchWithRetry");
  const mockFetch = jest.fn()
    .mockRejectedValueOnce(new Error("timeout"))
    .mockRejectedValueOnce(new Error("timeout"))
    .mockResolvedValueOnce({ data: "ok" });

  global.fetch = mockFetch;

  const result = await fetchWithRetry("https://api.example.com/data");

  expect(result).toEqual({ data: "ok" });
  expect(mockFetch).toHaveBeenCalledTimes(3);
});

test("throws after exhausting all retries", async () => {
  const mockFetch = jest.fn().mockRejectedValue(new Error("timeout"));
  global.fetch = mockFetch;

  await expect(fetchWithRetry("https://api.example.com/data"))
    .rejects.toThrow("timeout");

  expect(mockFetch).toHaveBeenCalledTimes(3); // or however many retries are configured
});
```

**Q24. How do you test a function that uses `setTimeout` or `setInterval` internally?**
A: Use Jest's fake timers — `jest.useFakeTimers()` replaces the real timer APIs with synchronous Jest-controlled ones, letting you advance time without actually waiting:

```js
test("resolves after 1 second delay", async () => {
  jest.useFakeTimers();

  const promise = delayedGreeting("Alice"); // internally calls setTimeout(resolve, 1000)

  jest.advanceTimersByTime(1000); // synchronously advance the fake clock

  const result = await promise;
  expect(result).toBe("Hello, Alice!");

  jest.useRealTimers(); // always restore — or use afterEach
});
```

For functions that use `setInterval` or poll until a condition is met, `jest.runAllTimers()` fires all pending timers to their completion. Use `jest.runAllTimersAsync()` (Jest 29+) when timers create new Promises that themselves need to resolve.

## Section 6: Common Pitfalls

**Q25. What is the "floating Promise" anti-pattern?**
A: A floating Promise is one that is neither `await`ed nor `.catch()`ed — it executes, but its outcome (resolution or rejection) is disconnected from the surrounding code. In tests, this means Jest never waits for the assertion:

```js
// ✗ Floating Promise — test always passes
test("creates a user", () => {
  // returned Promise is ignored by Jest because test fn is not async and returns nothing
  createUser({ name: "Alice" }).then(user => {
    expect(user.id).toBeDefined();
  });
});

// ✓ Return the Promise — Jest will wait for it
test("creates a user", () => {
  return createUser({ name: "Alice" }).then(user => {
    expect(user.id).toBeDefined();
  });
});

// ✓ Better — use async/await
test("creates a user", async () => {
  const user = await createUser({ name: "Alice" });
  expect(user.id).toBeDefined();
});
```

**Q26. What is "Promise chaining" in tests, and why should you prefer `async/await` over it?**
A: Promise chaining (`.then().then().catch()`) was the pre-`async/await` pattern for sequential async test steps. It's still valid but has significant readability and safety disadvantages:

```js
// ✗ Promise chain — hard to follow, easy to miss returning the chain
test("user creation flow", () => {
  return createUser({ name: "Alice" })
    .then(user => {
      expect(user.name).toBe("Alice");
      return updateUser(user.id, { role: "admin" });
    })
    .then(updated => {
      expect(updated.role).toBe("admin");
      return deleteUser(updated.id);
    })
    .then(result => {
      expect(result.deleted).toBe(true);
    });
});

// ✓ async/await — linear, readable, each step clearly awaited
test("user creation flow", async () => {
  const user = await createUser({ name: "Alice" });
  expect(user.name).toBe("Alice");

  const updated = await updateUser(user.id, { role: "admin" });
  expect(updated.role).toBe("admin");

  const result = await deleteUser(updated.id);
  expect(result.deleted).toBe(true);
});
```

The chain version requires `return` at the top level (easy to forget) and each `.then` callback to `return` the next Promise (also easy to forget — a silent floating Promise in the middle of the chain). `async/await` removes both failure modes.

**Q27. Why do `rejects` assertions sometimes pass when they should fail?**
A: The most common cause is a missing `await`. Without `await`, `expect(promise).rejects.toThrow()` returns a Promise that Jest never waits on — the assertion's outcome is never evaluated:

```js
// ✗ Missing await — always passes, regardless of what the Promise does
test("rejects on null input", async () => {
  expect(process(null)).rejects.toThrow("invalid"); // no await — floats away
});

// ✓ With await — fails correctly if process(null) resolves
test("rejects on null input", async () => {
  await expect(process(null)).rejects.toThrow("invalid");
});
```

Secondary causes: the function throws synchronously instead of returning a rejected Promise (use `toThrow` instead), or the function resolves with an error-shaped object instead of rejecting (a design issue — errors should be rejections, not resolved values).

**Q28. How do you debug a test that is timing out?**
A: A Jest timeout (`Exceeded timeout of 5000ms`) in an async test usually means the Promise never settled. Debugging steps:
1. Add a `console.log` immediately after the `await` — if it never prints, the Promise is hanging.
2. Check if the mocked dependency was configured to resolve. `jest.fn()` without `mockResolvedValue` returns `undefined` by default — `await undefined` resolves instantly, but `await jest.fn()()` returns `undefined` synchronously — so the issue is usually an un-awaited *inner* Promise or a mock that returns a never-settling Promise.
3. Check for an unclosed database connection, HTTP server, or event listener that is keeping the event loop alive after the Promise should have resolved.
4. Temporarily increase the timeout for diagnosis: `test("...", async () => { ... }, 30000)` — the third argument overrides Jest's default 5-second timeout. If it still hangs at 30s, the Promise is genuinely never settling.
5. Run with `--detectOpenHandles` to identify lingering handles.

## Section 7: Scenario / System Design Style Questions

**Q29. "A colleague says they tested an async function and all the tests pass, but the feature is broken in production. You look at the test and see no `await` anywhere. What do you explain?"**
A: Without `await`, the test function returns immediately after firing the async operations — Jest scores the test as passed before any assertions run. The assertions exist in `.then()` callbacks or after un-awaited Promises, and those callbacks fire *after* Jest has already moved on. This is the floating Promise anti-pattern at its most dangerous: 100% green tests with zero actual coverage of async behavior. The fix is straightforward — mark the test `async` and `await` every assertion and every operation whose result is asserted on. Add `expect.assertions(n)` as a permanent guard in tests with conditional branches.

**Q30. "You're reviewing a PR that tests error handling using this pattern: `expect(asyncFn()).rejects.toThrow()` without `await`, and the CI is green. How do you explain the risk and what change do you request?"**
A: The CI is green precisely *because* the assertion is never evaluated — a missing `await` turns the `.rejects.toThrow()` into a floating Promise that resolves (or rejects) without Jest ever checking the outcome. The test would pass even if `asyncFn` resolved successfully, or if it threw the wrong error, or if it never settled at all. Request two changes:
1. Add `await`: `await expect(asyncFn()).rejects.toThrow()`.
2. Add `expect.assertions(1)` above it as a belt-and-suspenders guard — if somehow the assertion is still skipped (e.g., in a future refactor), the test fails with a clear "expected 1 assertion, received 0" message instead of silently passing.

**Q31. "You're building a test suite for a payment service. The `chargeCard` function is async and can reject with three different error types: `InsufficientFundsError`, `CardDeclinedError`, and `NetworkError`. How do you structure the tests?"**
A: One test per rejection type, each asserting on the error class and any meaningful metadata:

```js
describe("chargeCard", () => {
  test("resolves with a transaction id on success", async () => {
    mockPaymentGateway.mockResolvedValue({ transactionId: "txn_123" });

    const result = await chargeCard({ amount: 50, cardToken: "tok_valid" });

    expect(result).toMatchObject({ transactionId: expect.stringMatching(/^txn_/) });
  });

  test("rejects with InsufficientFundsError when balance is too low", async () => {
    mockPaymentGateway.mockRejectedValue(new InsufficientFundsError("Balance: $10"));

    await expect(chargeCard({ amount: 100, cardToken: "tok_lowbal" }))
      .rejects.toBeInstanceOf(InsufficientFundsError);
  });

  test("rejects with CardDeclinedError and includes the decline code", async () => {
    mockPaymentGateway.mockRejectedValue(
      Object.assign(new CardDeclinedError("Card declined"), { declineCode: "do_not_honor" })
    );

    await expect(chargeCard({ amount: 50, cardToken: "tok_declined" }))
      .rejects.toMatchObject({
        name: "CardDeclinedError",
        declineCode: "do_not_honor",
      });
  });

  test("rejects with NetworkError and is safe to retry", async () => {
    mockPaymentGateway.mockRejectedValue(
      Object.assign(new NetworkError("timeout"), { retryable: true })
    );

    await expect(chargeCard({ amount: 50, cardToken: "tok_valid" }))
      .rejects.toMatchObject({ name: "NetworkError", retryable: true });
  });
});
```

Each test mocks the gateway's behavior for that specific failure mode, asserts on the error class (for type narrowing in application code), and asserts on any metadata callers need (`declineCode`, `retryable`) — keeping the tests independent, focused, and informative.

**Q32. "Your integration test suite for async database operations is slow and flaky. What strategies do you apply?"**
A: Flakiness and slowness in async integration tests typically share the same root causes:

- **Shared state** — tests reading data written by other tests. Fix: wrap each test in a transaction that's rolled back in `afterEach`, or truncate tables in `beforeEach`. Each test must own its data.
- **Race conditions** — parallel tests sharing a single database connection pool. Fix: allocate a separate database schema or database per Jest worker (`--maxWorkers=4` with unique `DB_NAME` per worker via `globalSetup`).
- **Unresolved Promises from teardown** — `afterEach` or `afterAll` not `await`ing cleanup, leaving connections open for the next test. Fix: always `await` teardown operations.
- **Real network calls** — tests hitting a live external API. Fix: intercept with `msw` (Mock Service Worker) or `nock` at the HTTP layer, or replace the network client with a mock at the module boundary.
- **Timeout thresholds too tight** — integration tests legitimately need more than 5 seconds for DB operations under load. Fix: set a per-suite timeout in `jest.config.js` (`testTimeout: 15000`) and distinguish it from unit test config.

```js
// ── async/await ──────────────────────────────────────────────
test("resolves", async () => {
  const result = await asyncFn();
  expect(result).toStrictEqual(expected);
});

test("rejects", async () => {
  await expect(asyncFn()).rejects.toThrow(SomeError);
});

// ── resolves matcher ─────────────────────────────────────────
await expect(asyncFn()).resolves.toStrictEqual(expected);
await expect(asyncFn()).resolves.toMatchObject({ key: "value" });
await expect(asyncFn()).resolves.toBe(42);

// ── rejects matcher ──────────────────────────────────────────
await expect(asyncFn()).rejects.toThrow(ErrorClass);
await expect(asyncFn()).rejects.toThrow("message substring");
await expect(asyncFn()).rejects.toThrow(/regex/i);
await expect(asyncFn()).rejects.toMatchObject({ field: "x", code: "Y" });
await expect(asyncFn()).rejects.toBeInstanceOf(ErrorClass);

// ── assertion guard ──────────────────────────────────────────
expect.assertions(1); // fail if exactly 1 assertion isn't reached

// ── mock async dependencies ──────────────────────────────────
jest.fn().mockResolvedValue(value);         // always resolves
jest.fn().mockRejectedValue(new Error());   // always rejects
jest.fn()
  .mockResolvedValueOnce(firstValue)        // first call
  .mockRejectedValueOnce(new Error());      // second call

// ── fake timers ──────────────────────────────────────────────
jest.useFakeTimers();
const p = asyncFnWithTimeout();
jest.advanceTimersByTime(5000);
await expect(p).resolves.toBe("done");
jest.useRealTimers();
```

## Common Mistakes at a Glance

| Mistake                                          | Symptom                              | Fix                                                      |
|---                                               |---                                   |---                                                       |
| Missing `await` on `resolves`/`rejects`          | Test always passes                   | Add `await` before `expect(...)`                         |
| `async` test fn with no `await` inside           | Test passes before assertions run    | `await` every async call; add `expect.assertions(n)`     |
| Using `rejects` on a sync-throwing function      | `TypeError` — not a Promise          | Use `toThrow(() => syncFn())` instead                    |
| Forgetting `return` in a `.then()` chain         | Floating inner Promise               | Switch to `async/await`                                  |
| No `await` in `afterAll` teardown                | Open handle warning; next test leaks | `await` all teardown operations                          |
| `jest.fn()` without `mockResolvedValue`          | `await undefined` — no error, wrong value | Always configure mock return value in the test      |
| Shared mutable state between async tests         | Flaky, order-dependent failures      | Truncate/rollback in `beforeEach`; isolate per worker    |

Know the missing-`await` false-positive cold — it's the single most common async testing bug — understand when `rejects.toMatchObject` beats `try/catch`, and have a real story about tracking down a floating Promise or an open handle warning.
