# JavaScript / Testing: Matchers — `toBe`, `toEqual`, `toStrictEqual`, `toMatchObject`, `toContain`, `toThrow` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a matcher in Jest?**
A: A matcher is the method chained onto `expect()` that defines *how* the received value should be compared against the expected value. `expect(received).matcher(expected)` is the full shape of an assertion. Jest ships with ~50 built-in matchers; libraries like `jest-extended` and `@testing-library/jest-dom` add domain-specific ones. Choosing the wrong matcher is one of the most common sources of false-positive tests — tests that pass when they shouldn't, because the comparison is too loose.

**Q2. What is the difference between `expect` and a matcher?**
A: `expect(value)` wraps the *received* value and returns an expectation object — it does nothing on its own. The matcher method called on that object performs the actual assertion and throws if it fails:
```js
// expect() alone — no assertion, no failure, this test always passes (a silent bug)
test("silent bug", () => {
  expect(someValue); // ← no matcher; Jest never evaluates anything
});

// expect() + matcher — real assertion
test("real assertion", () => {
  expect(someValue).toBe(42); // ← now Jest actually checks something
});
```
This is why Jest's `expect.assertions(n)` guard exists — it verifies that *n* assertions were actually called in a test, catching the case where a matcher was never reached (common in async tests where a promise branch is never exercised).

**Q3. What is the `.not` modifier, and how does it interact with matchers?**
A: `.not` inverts the matcher's pass/fail condition. It works with every matcher:
```js
expect(result).not.toBe(null);
expect(arr).not.toContain("forbidden");
expect(fn).not.toThrow();
```
`.not` does not change *how* the comparison is done — only whether passing or failing is the expected outcome. Prefer specific positive assertions over `.not` when possible: `expect(value).toBe(0)` is clearer than `expect(value).not.toBe(1)`, because the positive form states exactly what you expect, not just what you don't.

**Q4. How does Jest's matcher equality differ from JavaScript's `==` and `===`?**
A: Jest matchers do not use `==` (abstract equality with coercion) at all. The divide is between reference equality and deep structural equality:
- `===` (strict equality) — same value for primitives; same *reference* for objects. `{} === {}` is `false`.
- `Object.is()` — like `===` but handles `NaN` correctly (`Object.is(NaN, NaN)` is `true`) and distinguishes `+0` from `-0`. `toBe` uses `Object.is`.
- **Deep equality** — recursively compares every property and nested value. `toEqual` and `toStrictEqual` use this.

Understanding this divide explains 80% of "why is my assertion failing/passing unexpectedly" questions.

## Section 2: `toBe`

**Q5. What does `toBe` do?**
A: `toBe` uses `Object.is()` — the strictest possible equality check. It passes if and only if the received value and expected value are *the same value*: identical primitive values or the exact same object reference.

```js
// Primitives — passes when values are identical
expect(2 + 2).toBe(4);               // ✓
expect("hello").toBe("hello");        // ✓
expect(null).toBe(null);              // ✓
expect(NaN).toBe(NaN);               // ✓ (Object.is handles NaN correctly)

// Objects — passes only for same reference
const obj = { a: 1 };
expect(obj).toBe(obj);               // ✓ same reference
expect(obj).toBe({ a: 1 });          // ✗ different reference, even with same content
```

**Q6. When should you use `toBe` vs `toEqual`?**
A: Use `toBe` for **primitives** (numbers, strings, booleans, `null`, `undefined`) and for **identity checks** (verifying a function returns the exact same object reference it received, for example). Use `toEqual` for **objects and arrays** where you care about structural equality, not reference identity. A common mistake:
```js
// ✗ Wrong — always fails for objects
expect(getConfig()).toBe({ timeout: 5000, retries: 3 });

// ✓ Correct — compares structure
expect(getConfig()).toEqual({ timeout: 5000, retries: 3 });
```
The mistake of using `toBe` on an object is immediately caught by Jest, which provides a helpful error message: "If it should pass with deep equality, replace `toBe` with `toStrictEqual`."

**Q7. How does `toBe` handle `+0` and `-0`?**
A: `Object.is(+0, -0)` is `false`, so `toBe` distinguishes them — unlike `===`, which treats them as equal:
```js
expect(+0).toBe(-0);  // ✗ fails — Object.is(+0, -0) is false
expect(+0 === -0).toBe(true); // ✓ passes — === treats them as equal
```
This matters in numeric computation tests where the sign of zero carries semantic meaning (e.g., in graphics or physics engines). In practice it rarely matters for business logic, but it's a reliable interview question to separate engineers who understand `Object.is` from those who assume `toBe` is just `===`.

**Q8. What does `toBe` do with `undefined`?**
A:
```js
expect(undefined).toBe(undefined); // ✓
```
This is valid and useful — but watch out: a test that asserts `toBe(undefined)` on an object property may be passing because the property was never set (the key doesn't exist) *or* because it was explicitly set to `undefined`. If that distinction matters, use `toStrictEqual` (which differentiates between a missing key and a key set to `undefined`) or assert on `Object.keys()` separately.

## Section 3: `toEqual`

**Q9. What does `toEqual` do?**
A: `toEqual` performs a **deep recursive equality check** — it traverses every property of objects and every element of arrays, comparing values at every level. Two values pass `toEqual` if their structures and leaf values are identical, regardless of whether they are the same object reference.

```js
expect({ a: 1, b: { c: 2 } }).toEqual({ a: 1, b: { c: 2 } }); // ✓ deep equal
expect([1, [2, 3]]).toEqual([1, [2, 3]]);                        // ✓ deep equal
expect({ a: 1 }).toEqual({ a: 1, b: undefined });                // ✓ (see Q10)
```

**Q10. What is the key difference between `toEqual` and `toStrictEqual`?**
A: `toEqual` **ignores** keys with `undefined` values and **ignores** the distinction between a sparse array slot and an explicit `undefined` element. `toStrictEqual` treats these as meaningful differences:

```js
// Object with undefined value vs missing key
expect({ a: 1, b: undefined }).toEqual({ a: 1 });         // ✓ passes — toEqual ignores undefined values
expect({ a: 1, b: undefined }).toStrictEqual({ a: 1 });   // ✗ fails — b is present (even if undefined)

// Sparse array vs explicit undefined
expect([1, , 3]).toEqual([1, undefined, 3]);               // ✓ passes — toEqual treats them the same
expect([1, , 3]).toStrictEqual([1, undefined, 3]);         // ✗ fails — sparse slot ≠ explicit undefined

// Class instances — prototype chain
class Dog { constructor(name) { this.name = name; } }
expect(new Dog("Rex")).toEqual({ name: "Rex" });           // ✓ passes — toEqual ignores prototype
expect(new Dog("Rex")).toStrictEqual({ name: "Rex" });     // ✗ fails — different constructor
```

**Q11. When is `toEqual`'s lenience a feature vs a bug?**
A: It's a **feature** when testing API response shapes where `undefined` values on optional fields are irrelevant — you only care that the present fields are correct. It's a **bug** when:
- You're testing serialization code where `undefined` fields have semantic meaning (JSON serialization drops `undefined` values; if your serializer is supposed to drop them and it's not, `toEqual` won't catch it).
- You're testing factory functions that should produce a specific, complete object — `toEqual` lets missing keys (set to `undefined`) pass as if they were intentionally absent.
- You're testing classes where the prototype chain matters (a `Dog` instance should not be equal to a plain object with the same properties).

In all these cases, reach for `toStrictEqual` instead.

**Q12. Does `toEqual` work with `Date`, `Map`, `Set`, and other built-ins?**
A: Yes — Jest's deep equality handles built-in types specially:
```js
expect(new Date("2024-01-01")).toEqual(new Date("2024-01-01")); // ✓ compares by time value
expect(new Map([["a", 1]])).toEqual(new Map([["a", 1]]));       // ✓ compares entries
expect(new Set([1, 2, 3])).toEqual(new Set([1, 2, 3]));         // ✓ compares values
```
`RegExp` objects are compared by their source and flags. `Error` objects are compared by message. Functions are compared by reference (two functions with identical source code are not `toEqual` unless they're the same function object).

## Section 4: `toStrictEqual`

**Q13. What does `toStrictEqual` add on top of `toEqual`?**
A: `toStrictEqual` applies three additional checks that `toEqual` skips:
1. **`undefined` properties are significant** — a key explicitly set to `undefined` is not equal to a missing key.
2. **Sparse array slots are significant** — `[1, , 3]` is not equal to `[1, undefined, 3]`.
3. **Object type (prototype/constructor) is checked** — `new Dog("Rex")` is not equal to `{ name: "Rex" }` even if all enumerable own properties match.

```js
// All three differences demonstrated
class Point { constructor(x, y) { this.x = x; this.y = y; } }

expect(new Point(1, 2)).toStrictEqual(new Point(1, 2)); // ✓ same class, same values
expect(new Point(1, 2)).toStrictEqual({ x: 1, y: 2 });  // ✗ fails — different constructor
```

**Q14. Should `toStrictEqual` be the default, or should you use `toEqual` by default?**
A: This is a matter of team convention, but the defensible position is: **use `toStrictEqual` as the default** for object assertions, and only drop down to `toEqual` when you have a specific reason to tolerate `undefined`-key differences or prototype mismatch. The reasoning: `toStrictEqual` fails loudly on distinctions that matter in production code (serialization, class identity, object completeness). `toEqual` silently passes on those cases, which can mask real bugs. Teams that default to `toStrictEqual` tend to have less "the test passed but the feature is broken" situations. The tradeoff: `toStrictEqual` requires your test fixtures to be more precise, which adds setup cost.

**Q15. When does `toStrictEqual` matter for class-based code?**
A: Any time your code returns a class instance and callers care about calling methods on it — not just reading properties. Consider a service that should return a `User` instance:
```js
class User {
  constructor(data) { Object.assign(this, data); }
  fullName() { return `${this.firstName} ${this.lastName}`; }
}

// If getUser() accidentally returns a plain object instead of a User instance:
const result = getUser(1);

expect(result).toEqual({ firstName: "Alice", lastName: "Lee" });         // ✓ passes — misses the bug
expect(result).toStrictEqual(new User({ firstName: "Alice", lastName: "Lee" })); // ✗ fails — catches it
```
The plain object passes `toEqual` perfectly, but `result.fullName()` would throw `TypeError: result.fullName is not a function` in production. `toStrictEqual` catches the wrong type at test time.

## Section 5: `toMatchObject`

**Q16. What does `toMatchObject` do?**
A: `toMatchObject` checks that the received object contains *at least* the properties specified in the expected object — it's a **subset match**. Extra properties on the received object are ignored. This makes it ideal for asserting on the parts of a response you care about without specifying the entire object:

```js
const response = {
  id: 42,
  name: "Alice",
  createdAt: "2024-01-15T10:00:00Z",
  updatedAt: "2024-06-20T14:32:00Z",
};

// Only assert on what matters — ignore dynamic timestamps
expect(response).toMatchObject({ id: 42, name: "Alice" }); // ✓
```

**Q17. How does `toMatchObject` handle arrays?**
A: When the expected value is an **array**, `toMatchObject` checks that every element in the expected array has a match at the same index in the received array — but extra elements in the received array are allowed:
```js
// Array subset check — received can have more elements
expect([{ id: 1, name: "Alice" }, { id: 2, name: "Bob" }, { id: 3 }])
  .toMatchObject([{ id: 1 }, { id: 2 }]); // ✓ — only checks first two elements, ignores third

// Nested object subset within array
expect([{ user: { id: 1, role: "admin", token: "abc123" } }])
  .toMatchObject([{ user: { id: 1, role: "admin" } }]); // ✓ — token ignored
```
Note the asymmetry: extra elements in the received array are ignored, but extra elements in the *expected* array cause failure. The expected array defines the minimum; the received array must satisfy every element in it.

**Q18. When should you use `toMatchObject` over `toEqual`?**
A: Use `toMatchObject` when:
- The received object contains **dynamic fields** you can't predict (auto-generated `id`, timestamps, tokens, UUIDs) but you want to assert on the stable fields.
- You're testing **API responses** where the server may add new fields over time and you don't want the test to break every time a new field is added.
- You're testing **a list of items** where you only care that certain entries are present with certain properties, not that the list is exactly this and nothing more.
- You're building **partial fixture matching** — e.g., checking that an audit log entry contains at least `{ action: "DELETE", resourceId: 5 }` without caring about the `performedBy` or `timestamp` fields.

Use `toEqual` (or `toStrictEqual`) when the object must match *exactly* — no extra properties allowed.

**Q19. Can `toMatchObject` be nested with `expect.any()` and `expect.stringContaining()`?**
A: Yes — Jest's **asymmetric matchers** are designed to compose inside `toMatchObject` (and `toEqual`/`toStrictEqual`):
```js
expect(response).toMatchObject({
  id: expect.any(Number),                          // any number
  name: expect.stringContaining("Ali"),            // string that contains "Ali"
  email: expect.stringMatching(/^[\w.]+@\w+\.\w+$/), // matches regex
  roles: expect.arrayContaining(["admin"]),        // array that contains "admin"
  createdAt: expect.any(String),                   // any string (for ISO dates)
});
```
This is the most expressive pattern for testing realistic API responses: assert on structure and type without hardcoding dynamic values.

**Q20. What is a common pitfall with `toMatchObject` on arrays?**
A: Assuming it works like `toContain` — checking if a specific item exists *anywhere* in the array. It doesn't. `toMatchObject` with an array checks positionally:
```js
const users = [{ id: 2, name: "Bob" }, { id: 1, name: "Alice" }];

// ✗ Fails — it checks index 0, finds id:2, not id:1
expect(users).toMatchObject([{ id: 1 }]);

// ✓ Use expect.arrayContaining for order-independent subset matching
expect(users).toEqual(expect.arrayContaining([{ id: 1, name: "Alice" }]));
```
When you need "this object exists somewhere in this array" use `expect.arrayContaining()`, not `toMatchObject([...])`.

## Section 6: `toContain`

**Q21. What does `toContain` do?**
A: `toContain` checks membership: it passes if an array contains the expected item, or if a string contains the expected substring. It uses `Object.is()` for array item comparison — the same strict reference/value equality as `toBe`.

```js
// Arrays — uses Object.is for each element
expect([1, 2, 3]).toContain(2);           // ✓
expect(["a", "b", "c"]).toContain("b");   // ✓
expect([1, 2, 3]).toContain("2");         // ✗ type mismatch — Object.is(2, "2") is false

// Strings — substring check
expect("Hello, world").toContain("world"); // ✓
expect("Hello, world").toContain("World"); // ✗ case-sensitive
```

**Q22. Why does `toContain` fail for objects even when the content matches?**
A: Because `toContain` uses `Object.is()` — reference equality — for array items. Two objects with identical content are not `Object.is`-equal:
```js
const items = [{ id: 1 }, { id: 2 }];

expect(items).toContain({ id: 1 });          // ✗ fails — different object reference

// Use toEqual with expect.arrayContaining for deep equality membership
expect(items).toEqual(expect.arrayContaining([{ id: 1 }]));  // ✓
```
This is the single most common `toContain` mistake. If you're checking whether an array of objects contains an object with certain properties, `toContain` is the wrong tool — `expect.arrayContaining` with `toEqual`/`toStrictEqual` is correct.

**Q23. What is the difference between `toContain` and `toContainEqual`?**
A: `toContainEqual` uses deep equality (like `toEqual`) for array item comparison instead of `Object.is`. It's the correct matcher when checking if an array contains an object matching a value:
```js
const items = [{ id: 1, name: "Alice" }, { id: 2, name: "Bob" }];

expect(items).toContain({ id: 1, name: "Alice" });      // ✗ fails — reference check
expect(items).toContainEqual({ id: 1, name: "Alice" }); // ✓ deep equality check
```
`toContainEqual` is less well known than `toContain` but is strictly more useful for arrays of objects. Its limitation vs `expect.arrayContaining`: it checks for an exact deep match of the entire element, not a subset match — the element must match completely, not partially.

**Q24. When would you use `toContain` on a string?**
A: For error messages, log output, rendered HTML, or any text where you care that a specific substring is present without specifying the exact full string:
```js
// Error message contains the field name
expect(validationError.message).toContain("email");

// Rendered output contains a key phrase
expect(renderToString(<Alert type="error" />)).toContain("role=\"alert\"");

// Log output records the event
expect(logger.lastMessage).toContain("Payment processed");
```
For regex-based substring matching, use `toMatch` instead: `expect(str).toMatch(/payment processed/i)`.

## Section 7: `toThrow`

**Q25. What does `toThrow` do?**
A: `toThrow` asserts that the received **function** throws when called. It must be passed a *function* — not the result of calling a function:

```js
// ✓ Correct — wrap the call in a function
expect(() => JSON.parse("invalid json")).toThrow();

// ✗ Wrong — JSON.parse throws before expect() even receives a value
expect(JSON.parse("invalid json")).toThrow(); // Test errors out, not fails
```
This wrapping requirement is the number-one `toThrow` mistake. Jest calls the wrapper function itself, catches any thrown error, and evaluates whether it meets the matcher's condition.

**Q26. What forms does `toThrow` accept as its argument?**
A: Four forms, each more specific than the last:

```js
// 1. No argument — just checks that something is thrown
expect(() => riskyOperation()).toThrow();

// 2. Error class — checks that the thrown error is an instance of the class
expect(() => riskyOperation()).toThrow(TypeError);
expect(() => riskyOperation()).toThrow(CustomValidationError);

// 3. String — checks that the error message contains the substring
expect(() => riskyOperation()).toThrow("invalid input");

// 4. RegExp — checks that the error message matches the pattern
expect(() => riskyOperation()).toThrow(/invalid (input|value)/i);

// 5. Error object — checks class AND message
expect(() => riskyOperation()).toThrow(new TypeError("invalid input"));
```
Use the most specific form that is stable. Checking `toThrow(ValidationError)` is better than `toThrow("must be a string")` — error messages change; error types (should) change less often.

**Q27. How do you use `toThrow` with async functions?**
A: Async functions return rejected Promises — they don't throw synchronously. `toThrow` doesn't catch rejected promises. Use `rejects.toThrow` instead:
```js
// Async function that rejects
async function fetchUser(id) {
  if (!id) throw new Error("id is required");
  return await api.get(`/users/${id}`);
}

// ✗ Wrong — toThrow doesn't handle async
expect(() => fetchUser(null)).toThrow("id is required");

// ✓ Correct — rejects.toThrow awaits the rejection
await expect(fetchUser(null)).rejects.toThrow("id is required");
await expect(fetchUser(null)).rejects.toThrow(Error);

// ✓ Also correct for callbacks/Promises
await expect(fetchUser(null)).rejects.toMatchObject({
  message: "id is required",
});
```
Forgetting `await` before `expect(...).rejects.toThrow(...)` is a silent failure — the test passes regardless of whether the function throws, because the unresolved Promise is never evaluated.

**Q28. How do you assert on the thrown error's properties beyond just the message?**
A: Catch the error manually and assert on it, or combine `.rejects` with `toMatchObject`:
```js
// Option 1 — try/catch with manual assertion (synchronous)
let thrownError;
try {
  validateUser({ age: -1 });
} catch (err) {
  thrownError = err;
}
expect(thrownError).toBeInstanceOf(ValidationError);
expect(thrownError.field).toBe("age");
expect(thrownError.code).toBe("OUT_OF_RANGE");

// Option 2 — rejects.toMatchObject (async, or thenable)
await expect(validateUserAsync({ age: -1 })).rejects.toMatchObject({
  name: "ValidationError",
  field: "age",
  code: "OUT_OF_RANGE",
});

// Option 3 — expect.assertions guard ensures the catch block was reached
expect.assertions(3);
try {
  validateUser({ age: -1 });
} catch (err) {
  expect(err).toBeInstanceOf(ValidationError);
  expect(err.field).toBe("age");
  expect(err.code).toBe("OUT_OF_RANGE");
}
```
Option 3 requires `expect.assertions(3)` — without it, if `validateUser` doesn't throw, the `catch` block is never reached, no assertions run, and the test passes silently.

## Section 8: Choosing the Right Matcher — Decision Guide

**Q29. How do you pick the right equality matcher for a given assertion?**
A:

```
Is the value a primitive (number, string, boolean, null, undefined, Symbol)?
  └── Yes → toBe

Is it an object or array?
  ├── Do you want exact full equality, and does the prototype/class matter?
  │     └── Yes → toStrictEqual
  ├── Do you want exact full equality, but don't care about prototype or undefined keys?
  │     └── Yes → toEqual
  └── Do you only care that certain properties are present (subset match)?
        └── Yes → toMatchObject
```

**Q30. When would you combine multiple matchers in one test?**
A: When a single assertion can't express all the constraints:
```js
test("createUser returns a valid user object", () => {
  const user = createUser({ name: "Alice", email: "alice@example.com" });

  // Type assertions
  expect(user).toBeInstanceOf(User);

  // Structural subset — ignore auto-generated id and timestamp
  expect(user).toMatchObject({ name: "Alice", email: "alice@example.com" });

  // Dynamic field type checks
  expect(user.id).toEqual(expect.any(Number));
  expect(user.createdAt).toEqual(expect.any(Date));

  // String membership
  expect(["active", "pending"]).toContain(user.status);
});
```
Each assertion tests a different facet. Combining them in one test is fine as long as each assertion is independently meaningful — they shouldn't be redundant with each other.

## Section 9: Pitfalls, Anti-Patterns & Best Practices

**Q31. What is a "false positive" test, and which matchers are most prone to producing them?**
A: A false positive is a test that passes when the behavior it's supposed to verify is actually broken. Matchers ranked by false-positive risk:
- **`toMatchObject`** — highest risk; only checks a subset. A completely wrong object can pass if it happens to contain the asserted subset.
- **`toContain`** (string) — checks substring presence; a completely wrong string passes as long as the substring appears.
- **`toEqual`** — medium risk; `undefined`-key leniency can mask missing fields.
- **`toBe`** — low risk for primitives; always fails on objects (accidental false negative, not positive).
- **`toStrictEqual`** — lowest risk for objects; the strictest comparison.

The practical implication: use `toStrictEqual` as the default for object assertions; only drop to looser matchers when you have an explicit reason.

**Q32. What is the danger of `expect.assertions()` being absent in async tests?**
A: Without `expect.assertions(n)`, an async test where the assertion is inside a `.catch()` or `try/catch` block will pass silently if the async operation never rejects — the assertions inside the catch are never reached:
```js
// ✗ Dangerous — if fetchUser resolves instead of rejecting, no assertions run
test("rejects for invalid id", async () => {
  try {
    await fetchUser(null);
  } catch (err) {
    expect(err.message).toContain("id is required"); // never reached if no throw
  }
});

// ✓ Safe — test fails if exactly 1 assertion isn't reached
test("rejects for invalid id", async () => {
  expect.assertions(1);
  try {
    await fetchUser(null);
  } catch (err) {
    expect(err.message).toContain("id is required");
  }
});

// ✓ Even better — use rejects directly
test("rejects for invalid id", async () => {
  await expect(fetchUser(null)).rejects.toThrow("id is required");
});
```

**Q33. Should you assert on implementation details (internal state, private method calls) vs observable behavior?**
A: Assert on **observable behavior** — the outputs and side effects that callers of the unit actually depend on. Asserting on internal state or private method calls:
- Breaks on refactor even when behavior is unchanged — the most common cause of brittle test suites.
- Doesn't verify that the unit actually does what it's supposed to do — only that it does it a particular way.
- Creates a tight coupling between the test and the implementation, making the test an obstacle rather than a safety net.

The practical rule: if you're asserting `expect(instance._privateCache).toEqual(...)` or `expect(privateSpy).toHaveBeenCalled()`, ask "would a caller ever know or care about this?" If the answer is no, the test is over-specified.

**Q34. What does "test one behavior per test" mean for matcher choice?**
A: Each `test()` block should have a single, clear behavioral claim. This guides matcher choice: if you find yourself needing five `toMatchObject` calls in one test because you're checking five different concerns, that's a sign to split into five tests — each with a clear, single `expect`. The benefit: when a test fails, you know *exactly* which behavior broke without reading through five assertions to find which one failed.

```js
// ✗ One test, multiple concerns — failure message is unclear
test("createOrder works", () => {
  const order = createOrder(cart);
  expect(order).toMatchObject({ status: "pending" });
  expect(order.items).toHaveLength(3);
  expect(order.total).toBe(150);
  expect(order.createdAt).toBeInstanceOf(Date);
});

// ✓ One test per behavior — failure is immediately localized
test("new order has pending status", () => {
  expect(createOrder(cart)).toMatchObject({ status: "pending" });
});
test("new order total matches cart", () => {
  expect(createOrder(cart).total).toBe(150);
});
```

## Quick Comparison Table

| Matcher          | Equality type          | Objects: exact or subset? | `undefined` keys matter? | Prototype/class matters? | Primary use case                                      |
|---               |---                     |---                        |---                       |---                       |---                                                    |
| `toBe`           | `Object.is` (reference)| N/A — fails on objects    | N/A                      | N/A                      | Primitives, reference identity checks                 |
| `toEqual`        | Deep recursive         | Exact                     | No (ignored)             | No                       | Objects/arrays where prototype and `undefined` don't matter |
| `toStrictEqual`  | Deep recursive (strict)| Exact                     | Yes                      | Yes                      | Default for objects; class instances; serialization   |
| `toMatchObject`  | Deep recursive (subset)| Subset only               | No                       | No                       | Partial assertion on large objects; API responses     |
| `toContain`      | `Object.is` (per item) | N/A                       | N/A                      | N/A                      | Array membership (primitives); string substring       |
| `toContainEqual` | Deep recursive         | N/A                       | No                       | No                       | Array membership for objects (deep equal)             |
| `toThrow`        | N/A                    | N/A                       | N/A                      | N/A                      | Synchronous throws; use `rejects.toThrow` for async   |

**Tip for the interview:** At 5 YOE, "what does `toBe` do?" won't come up standalone — the real questions look like: "your test passes but the feature is broken, how is that possible?" (false positive from `toMatchObject` or `toEqual` leniency), "why is this `toContain` failing even though the item is clearly in the array?" (object reference vs deep equality), or "how do you test that an async function throws?" (`rejects.toThrow` + the `await` you must not forget). Know the `toBe`-vs-`toEqual`-vs-`toStrictEqual` distinction cold — especially the `undefined` key and prototype behavior of `toStrictEqual` — and have a concrete story about a false-positive test you caught or a `toThrow` async trap you debugged. That's the level of answer that signals real test-writing experience at 5 YOE.
