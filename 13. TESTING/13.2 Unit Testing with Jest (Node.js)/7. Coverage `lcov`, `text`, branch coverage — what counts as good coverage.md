# Test Coverage: `lcov`, `text`, Branch Coverage & What Counts as Good — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is test coverage, and what does it actually measure?**
A: Test coverage is a family of metrics that measure what fraction of the production codebase is *executed* during a test suite run. A coverage tool instruments the source — inserting counters at strategic points — and reports which counters were hit and which were not.

"Coverage" is not a single number. It is a collection of related but distinct metrics, each answering a different question:

| Metric | Question answered | What is counted |
|--|--|--|
| **Statement coverage** | Was this statement executed? | Individual executable statements |
| **Line coverage** | Was this line touched? | Source lines (may group multiple statements) |
| **Branch coverage** | Was every outcome of every decision taken? | True/false arms of `if`, `switch` cases, ternaries, `&&`/`\|\|` short-circuits |
| **Function coverage** | Was this function called at least once? | Function and method declarations |

The critical constraint: coverage measures *execution*, not *correctness*. A line is "covered" the moment any test causes it to run — regardless of whether that test asserts anything meaningful about its output. This is the gap that mutation testing closes (see the mutation testing guide), but it's worth being explicit about in any coverage discussion.

**Q2. What is statement coverage vs line coverage, and when do they diverge?**
A: Statement coverage counts individual executable statements; line coverage counts source lines. They diverge when multiple statements share a line, or when a single statement spans multiple lines:

```typescript
// One line, two statements — line is covered if either runs,
// but statement coverage tracks them independently
let x = 0; if (condition) x = 1;

// One statement, multiple lines — all lines hit when statement executes
const result = someArray
  .filter(isActive)       // line covered
  .map(transform)         // line covered
  .reduce(accumulate, 0); // line covered
```

In practice, most JavaScript/TypeScript coverage tools (Istanbul/`c8`) report **line coverage** as the headline number because it maps naturally to what developers see in their editor. Statement coverage can differ by a few percentage points and is rarely reported separately. For interview purposes, treat "line coverage" and "statement coverage" as effectively synonymous unless the question specifically distinguishes them.

**Q3. What is branch coverage, and why does it matter more than line coverage?**
A: Branch coverage requires that every possible *outcome* of every decision point is exercised — not just that the decision point was reached. Each `if` has two branches (true and false); each `switch` case is its own branch; each `&&` and `||` has a short-circuit branch:

```typescript
function applyDiscount(price: number, isPremium: boolean): number {
  if (isPremium) {                    // branch 1: true, branch 2: false
    return price * 0.8;
  }
  return price;
}
```

A single test calling `applyDiscount(100, true)` gives **100% line coverage** — every line runs. But **branch coverage is 50%** — the `isPremium = false` path was never taken. A bug introduced in the `return price` path (e.g., `return price * 1.2` — accidentally applying a surcharge) would survive with full line coverage but be exposed by a second test that covers the false branch.

Branch coverage is more demanding and more informative than line coverage. It is the minimum bar recommended for business logic. 100% line coverage with low branch coverage is a common false comfort in mature codebases.

**Q4. What are the four standard coverage metrics Istanbul (the tool underlying Jest) reports, and what do the thresholds mean?**
A: Istanbul (used by Jest via `@jest/coverage-provider` backed by `istanbul` or `c8`) reports four metrics:

- **Statements** — percentage of executable statements hit
- **Branches** — percentage of decision outcomes hit
- **Functions** — percentage of functions/methods called
- **Lines** — percentage of source lines touched

These map to the `coverageThreshold` configuration in `jest.config.ts`:

```typescript
// jest.config.ts
export default {
  collectCoverage: true,
  coverageThreshold: {
    global: {
      statements: 80,
      branches: 75,
      functions: 80,
      lines: 80,
    },
    // Per-file thresholds for critical modules:
    './src/finance/': {
      statements: 95,
      branches: 90,
      functions: 95,
      lines: 95,
    },
  },
};
```

When a threshold is set, Jest exits with a non-zero code if any metric falls below it — failing CI. The threshold is a **floor**, not a target. A well-configured project sets different floors for different directories: stricter for core domain logic (payments, auth, fraud detection), looser for infrastructure wiring (DI setup, config loading).

**Q5. What is the difference between collecting coverage and enforcing thresholds?**
A: Collecting coverage (`collectCoverage: true`) runs the instrumented suite and generates a report. Enforcing thresholds (`coverageThreshold`) fails the CI run if the reported numbers fall below the configured minimums.

They are independent:
- Collect without enforce → useful during onboarding (see where you are, no pressure yet).
- Enforce without historical context → arbitrary number that may be too low (gives false confidence) or too high (blocks legitimate PRs).
- Best practice: collect from day one, set a floor equal to the current score, and ratchet it up incrementally as the team adds tests. Never let the threshold go backwards — that's the primary value of enforcement.

The `coveragePathIgnorePatterns` config is equally important — it excludes files that shouldn't count toward the score (generated code, migration files, index barrel files, type-only files):

```typescript
coveragePathIgnorePatterns: [
  '/node_modules/',
  '/dist/',
  '\\.d\\.ts$',
  'src/migrations/',
  'src/index\\.ts$',           // barrel re-exports have no logic to test
  'src/types/',                 // type-only files
],
```

## Section 2: Coverage Reporters

**Q6. What is the `text` coverage reporter, and what does its output tell you?**
A: The `text` reporter prints a coverage summary table directly to the terminal after the test run. It is the fastest feedback loop — no file to open, no browser to launch:

```
------------------------|---------|----------|---------|---------|-------------------
File                    | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
------------------------|---------|----------|---------|---------|-------------------
All files               |   84.21 |    76.47 |   88.00 |   84.61 |
 src/finance            |         |          |         |         |
  interest.ts           |  100.00 |    83.33 |  100.00 |  100.00 | 24
  amortization.ts       |   78.26 |    62.50 |   80.00 |   78.26 | 45-52, 67
 src/utils              |         |          |         |         |
  validator.ts          |   90.00 |    80.00 |   85.71 |   90.00 | 33, 41
------------------------|---------|----------|---------|---------|-------------------
```

Reading the output:
- The **Uncovered Line #s** column is the most actionable field — it tells you exactly which lines were never executed. Line 24 in `interest.ts` is uncovered despite 100% statement coverage, which means there's a branch on that line (one arm was never taken).
- A file showing `100.00` statements but `83.33` branches indicates untested conditional branches — the most common gap pattern.
- The `text-summary` variant prints only the aggregate row, useful for CI log brevity.

**Q7. What is the `lcov` reporter, and what is it used for?**
A: `lcov` generates a `coverage/lcov.info` file — a plain-text format originally defined for the Linux Kernel Coverage tool (`lcov`). It is the **lingua franca of coverage data** — understood by virtually every coverage aggregation and visualization tool in the ecosystem:

```
# lcov.info format (excerpt)
TN:                                    # Test name (empty = whole suite)
SF:src/finance/interest.ts             # Source file
FN:5,accrueInterest                    # Function name and start line
FN:18,calculateCompound                # Another function
FNDA:12,accrueInterest                 # Function hit count (called 12 times)
FNDA:0,calculateCompound               # Never called
FNF:2                                  # Functions found
FNH:1                                  # Functions hit
BRDA:8,0,0,5                           # Branch data: line, block, branch, hit count
BRDA:8,0,1,0                           # Line 8, block 0, branch 1: never taken
DA:5,1                                 # Line 5 executed (hit count: 1)
DA:18,0                                # Line 18 never executed
LF:20                                  # Lines found
LH:17                                  # Lines hit
end_of_record
```

Primary consumers of `lcov.info`:
- **Codecov / Coveralls** — CI coverage tracking services that read `lcov.info`, compute trends over time, and post coverage diffs to PRs.
- **SonarQube / SonarCloud** — code quality platforms that ingest `lcov.info` alongside other metrics.
- **`genhtml`** — the `lcov` CLI tool that renders `lcov.info` into a browsable HTML report.
- **VS Code Coverage Gutters extension** — reads `lcov.info` and highlights covered/uncovered lines inline in the editor, turning coverage from a report into a real-time coding tool.

**Q8. What is the `html` reporter, and how does it differ from `lcov`?**
A: The `html` reporter generates a self-contained `coverage/lcov-report/` directory with an interactive HTML site. Unlike `lcov.info` (machine-readable data), the HTML report is human-readable — you navigate by file, see line-by-line highlighting (green = covered, red = uncovered, yellow = partial branch), and drill into exactly which branches were missed.

The HTML report is the right tool for:
- **Local investigation** — opening `coverage/index.html` in a browser to understand why branch coverage is low on a specific file.
- **PR review in teams** — a team member can inspect a coverage artifact uploaded by CI to understand exactly what the new tests cover (or don't).
- **Reporting to stakeholders** — a visual representation of coverage state for non-technical audiences.

The `lcov` reporter is the right tool for:
- **CI integration** — uploading to Codecov/Coveralls for trend tracking and PR commenting.
- **Toolchain interoperability** — feeding coverage data into SonarQube, IDE extensions, or other downstream consumers.

In practice, most projects configure both:
```typescript
coverageReporters: ['text', 'lcov', 'html'],
```

**Q9. What is the `clover` reporter, and when would you use it over `lcov`?**
A: `clover` generates a `clover.xml` file in Atlassian's Clover format — an XML-based coverage report originally from Atlassian's commercial Clover tool. It is consumed by:
- **Jenkins** (via the Clover plugin) — the primary reason to use it; Jenkins has native Clover support but requires additional plugins for `lcov`.
- **Atlassian Bamboo** — Atlassian's own CI system.
- **Some SonarQube configurations** — though SonarQube now preferentially supports `lcov`.

For most modern projects (GitHub Actions, GitLab CI, CircleCI), `lcov` is the correct choice. `clover` is relevant only when the CI infrastructure specifically requires it. Configuring both is cheap:
```typescript
coverageReporters: ['text', 'lcov', 'clover', 'html'],
```

**Q10. How do you configure Jest to collect coverage only from files under test, and why does the default behaviour mislead you?**
A: By default, Jest only instruments files that are *imported* by at least one test. This gives an artificially high coverage number — files with no tests at all are invisible and don't drag down the score:

```typescript
// If src/services/fraud.ts has no tests and is never imported by tests,
// the default config doesn't include it in coverage — as if it doesn't exist.
// Reported coverage: 85% — looks healthy.
// Actual coverage: 60% — fraud.ts is entirely untested but not counted.
```

Fix with `collectCoverageFrom`:
```typescript
// jest.config.ts
export default {
  collectCoverageFrom: [
    'src/**/*.ts',
    '!src/**/*.spec.ts',
    '!src/**/*.test.ts',
    '!src/**/*.d.ts',
    '!src/migrations/**',
    '!src/index.ts',
  ],
};
```

With `collectCoverageFrom`, every matching file is instrumented whether or not any test imports it. Untested files show 0% coverage and drag down the aggregate score, which is the *honest* picture. This is the configuration you want in production — optimistic defaults hide the real state of your test suite.

## Section 3: Branch Coverage In Depth

**Q11. What constructs count as branches in JavaScript/TypeScript, and which ones surprise engineers?**
A: Istanbul counts branches at every decision point, including several that engineers don't intuitively think of as "branches":

```typescript
// Obvious branches — if/else
if (isValid) { doA(); } else { doB(); }   // 2 branches

// Switch — each case is a branch, including default
switch (status) {
  case 'active': return activate();       // branch 1
  case 'suspended': return suspend();     // branch 2
  default: return noop();                 // branch 3 (often untested!)
}

// Ternary — two branches
const label = isError ? 'Error' : 'OK';  // 2 branches

// Logical AND short-circuit — two branches
user && sendEmail(user);                  // branch: user falsy (short-circuits), user truthy

// Logical OR short-circuit — two branches
const name = input || 'Anonymous';        // branch: input truthy, input falsy

// Optional chaining — two branches
const city = user?.address?.city;         // branch: user nullish, user defined

// Nullish coalescing — two branches
const timeout = config.timeout ?? 5000;  // branch: config.timeout nullish, defined

// Default parameter — two branches
function connect(host: string, port = 5432) { }  // branch: port provided, port omitted
```

The non-obvious ones — `&&`, `||`, `??`, `?.`, default parameters — are the most commonly missed. A function that uses `user?.profile?.avatar ?? defaultAvatar` has six hidden branches from three operators.

**Q12. What is a "partial branch" and how does Istanbul report it?**
A: A partial branch (shown as yellow in the HTML report) means a branch *node* was reached but not all its arms were exercised. The most common case is an `if` without an `else` where the `if` body ran but the implicit "else" (the skip path) was never tested:

```typescript
function notifyOnFailure(result: Result): void {
  if (result.status === 'failed') {   // branch: true arm covered, false arm (skip) not
    alertTeam(result.error);
  }
  // no else — the "do nothing" path is an implicit branch Istanbul tracks
}
```

Istanbul reports this as `1/2` branches covered on that line. The HTML report shows the `if` line in yellow. The text reporter shows the line number in the `Uncovered Line #s` column with an `I` suffix (for "if" branch) to distinguish it from a fully uncovered line.

Understanding partial branches is important: a function with 100% line coverage and 50% branch coverage almost always has partial branches from unguarded `if` statements where the skip path was never exercised.

**Q13. How do you increase branch coverage without writing low-value tests?**
A: The key is targeting branches that represent *behaviorally distinct paths*, not checking boxes:

**High-value branch tests:**
- **Error paths** — the `else` of a validation check (`if (!isValid) throw`), the `catch` block of a try/catch. These are the paths most likely to harbor bugs and least likely to be exercised by happy-path tests.
- **Default/fallback values** — `const x = config.value ?? default`. Test with `config.value` explicitly `null` or `undefined` to exercise the nullish coalescing branch.
- **Boundary conditions** — `if (amount > limit)` should have tests at `limit - 1`, `limit`, and `limit + 1`.
- **Switch default cases** — the `default` arm of a switch is almost always untested. If it's a no-op, it deserves a test that confirms it doesn't throw for unexpected input.

**Low-value branch tests (worth skipping):**
- Branches in logging statements (`if (debug) logger.verbose(...)`) — the behavior difference between logging and not logging is rarely worth an assertion.
- Defensive null checks on data that structurally cannot be null given TypeScript's type system and test setup.
- Branches in configuration-loading boilerplate that is tested by integration tests anyway.

The discipline is: add a branch test when a bug in that branch would have a user-visible effect. Skip it when the branch is truly inconsequential.

## Section 4: What Counts as Good Coverage

**Q14. Is there a universally correct coverage target, and what is the danger of treating a percentage as a goal?**
A: No universal target is correct for all codebases. The commonly cited figure of **80% lines + 75% branches** is a reasonable floor for general-purpose applications, not a definition of "good." The danger of treating any percentage as a goal:

- **Goodhart's Law** — "When a measure becomes a target, it ceases to be a good measure." Teams that optimize for the percentage write tests designed to execute lines, not to catch bugs. Result: 85% coverage, low mutation score, continued production incidents.
- **Equal weighting of unequal code** — 100% coverage on a `formatCurrency` utility and 40% coverage on a fraud detection algorithm both count the same. A high aggregate number can mask critical gaps in high-risk code.
- **Coverage of the wrong layer** — 80% unit coverage doesn't tell you anything about whether the integration between layers is tested. A service that routes correctly but queries the DB incorrectly can have high unit coverage and a broken production flow.

The healthier framing: coverage is a **detection tool**, not a quality certificate. Use it to find gaps, not to declare success.

**Q15. How do you set differentiated thresholds for different parts of the codebase, and why is this better than a single global threshold?**
A: A single global threshold treats a `dateFormatter` utility and a `paymentProcessor` service as equally important. Differentiated thresholds apply rigor where it matters:

```typescript
// jest.config.ts
export default {
  coverageThreshold: {
    global: {
      statements: 75,
      branches: 70,
      functions: 75,
      lines: 75,
    },
    // Critical domain — high standards
    './src/finance/': {
      statements: 95,
      branches: 90,
      functions: 95,
      lines: 95,
    },
    './src/auth/': {
      statements: 95,
      branches: 90,
      functions: 100,
      lines: 95,
    },
    // Infrastructure wiring — lower bar, tested by integration tests
    './src/config/': {
      statements: 60,
      branches: 50,
      functions: 60,
      lines: 60,
    },
  },
};
```

This approach encodes the team's actual risk model in configuration. It also prevents the global threshold from being dragged down by legitimately hard-to-test infrastructure code, while keeping the pressure high on business-critical logic.

**Q16. What is the relationship between coverage, mutation score, and production bug rate — and which predicts quality best?**
A: The three metrics measure progressively deeper aspects of test quality:

| Metric | What it measures | Predictive value |
|--|--|--|
| **Line/statement coverage** | Code execution | Low — execution ≠ assertion |
| **Branch coverage** | Decision path execution | Medium — more paths = more meaningful |
| **Mutation score** | Test suite's defect detection rate | High — directly measures whether tests catch bugs |
| **Production bug rate** | Actual outcomes | Ground truth — what all metrics approximate |

Research on the relationship (notably by Gopinath et al. and studies on large open-source projects) consistently finds:
- Line coverage has a **weak correlation** with bug detection — high coverage does not reliably predict low bug rates.
- Branch coverage has a **moderate correlation** — better than line, but still imperfect.
- Mutation score has the **strongest correlation** with actual defect detection — a suite that kills more mutants is more likely to catch real bugs.

The practical takeaway: use coverage as a fast, cheap signal to find untested code; use mutation testing as a periodic deep audit to evaluate whether the tests that exist are actually effective.

**Q17. What does "100% coverage" actually guarantee, and what doesn't it?**
A: 100% line and branch coverage guarantees only that every line was executed and every branch arm was taken at least once during the test run. It does NOT guarantee:

- **Correct assertions** — tests can execute every line without asserting anything about the results.
- **Correct behavior** — a function that returns `a - b` instead of `a + b` can have 100% coverage if the test calls it without checking the return value.
- **Integration correctness** — unit tests with mocked dependencies can achieve 100% coverage while the real integration is broken.
- **Edge case handling** — 100% branch coverage on `if (x > 0)` means you tested one positive and one non-positive value. The boundary (`x = 0`), large values, `NaN`, and `-Infinity` may all be uncovered despite 100% branch coverage.
- **Concurrency correctness** — race conditions, deadlocks, and ordering bugs are invisible to coverage analysis.
- **Performance correctness** — a function can be correct but fatally slow; coverage doesn't measure this.

The most useful mental model: coverage tells you where your tests *haven't looked*. It says nothing about whether the tests that did look were looking carefully.

## Section 5: CI Integration & Tooling

**Q18. How do you integrate coverage reporting into a CI pipeline and track trends over time?**
A: A complete CI coverage pipeline has three stages:

**Stage 1 — Generate coverage data**
```yaml
# .github/workflows/test.yml
- name: Run tests with coverage
  run: npx jest --coverage --coverageReporters=lcov,text-summary

- name: Upload coverage to Codecov
  uses: codecov/codecov-action@v4
  with:
    files: ./coverage/lcov.info
    flags: unit
    fail_ci_if_error: true
```

**Stage 2 — Enforce thresholds (inline, via Jest config)**
Jest's `coverageThreshold` handles this — the test step exits non-zero if thresholds are missed, failing the CI job automatically. No separate step needed.

**Stage 3 — Track trends (Codecov / Coveralls)**
Codecov reads `lcov.info`, stores historical scores per commit and branch, and posts a PR comment showing:
- Overall coverage delta (e.g., `+0.42%` or `-1.23%`)
- File-level changes (which files got better/worse)
- A flag if the PR drops coverage below the configured gate

```yaml
# codecov.yml (in project root)
coverage:
  status:
    project:
      default:
        target: 80%          # absolute minimum
        threshold: 1%        # allow 1% drop before failing
    patch:
      default:
        target: 85%          # new code in PRs must hit 85%
```

The `patch` target is particularly valuable: it requires that new code added in a PR meets a higher bar than the historical average, preventing gradual erosion without blocking legacy code improvements.

**Q19. How do you use the VS Code Coverage Gutters extension with `lcov`, and why is it valuable?**
A: The Coverage Gutters extension (by Ryan Luker) reads `lcov.info` and renders coverage inline in the editor — green gutters for covered lines, red for uncovered, yellow for partial branches. It transforms coverage from a report you look at after tests into a live signal as you write code:

Setup:
```bash
# 1. Install extension: "Coverage Gutters" by ryanluker in VS Code

# 2. Configure Jest to output lcov
# jest.config.ts
coverageReporters: ['lcov', 'text'],

# 3. Run tests with coverage
npx jest --coverage

# 4. In VS Code: Cmd+Shift+P → "Coverage Gutters: Display Coverage"
# lcov.info is auto-detected at coverage/lcov.info
```

The value: when you open a file and see red gutters on lines 45–52, you can write a test for exactly that path immediately, without switching to a browser or terminal. Branch coverage gaps appear as yellow gutters, pinpointing the exact line where an arm was missed. This tight feedback loop is the fastest way to improve coverage quality because the developer context is still fresh.

**Q20. What is the `c8` coverage provider, and how does it differ from Istanbul?**
A: `c8` is an alternative coverage provider available in Jest (via `coverageProvider: 'v8'`) that uses V8's built-in coverage instrumentation instead of Istanbul's source-level instrumentation:

| Dimension | Istanbul (default) | c8 / V8 |
|--|--|--|
| Instrumentation | Source transformation (adds counters to AST) | Native V8 engine coverage API |
| Accuracy | High for transpiled code (TypeScript, Babel) | Higher accuracy for native ESM; lower for heavily transpiled code |
| Performance | Adds ~10–20% overhead | Lower overhead (native) |
| Source maps | Relies on source map quality | Also relies on source maps; edge cases differ |
| Branch coverage | Tracks all Istanbul branch types | May miss some implicit branches in transpiled code |
| Config | `coverageProvider: 'babel'` (default) | `coverageProvider: 'v8'` |

For most TypeScript projects using `ts-jest` or `babel-jest`, Istanbul remains the better choice — its source-level instrumentation understands TypeScript constructs more reliably after transpilation. `c8` is preferable for projects running native ESM without transpilation, where it avoids instrumentation artifacts.

## Section 6: Scenario / System Design Style Questions

**Q21. "Our CI reports 82% line coverage but we had three production bugs last month in covered code. How do you diagnose and address the quality gap?"**
A: The symptom — bugs in covered code — is the textbook sign of the coverage/quality gap: tests that execute code without asserting its correctness. Diagnosis in three steps:

**Step 1 — Run mutation testing on the affected modules**
```bash
npx stryker run --mutate "src/payments/**,src/fraud/**"
```
A module with 82% line coverage and 40% mutation score tells the story precisely: tests execute the code but don't detect defects. The surviving mutants are a direct list of which specific behaviors are unasserted.

**Step 2 — Review the tests that "cover" the buggy code**
Open the coverage HTML report, navigate to the files where bugs occurred, and look at the tests mapped to the covered lines. Specifically check: does any test assert on the *return value* or *side effects* of the covered function, or does it only call the function and move on?

**Step 3 — Check branch coverage separately from line coverage**
The team may be reporting only line coverage. Run with `--coverage` and inspect the `% Branch` column in the text report. A file with 82% lines and 55% branches has large untested decision paths — exactly where subtle bugs hide.

Remediation: add an assertion-gap review to the PR process (not just "does coverage go up" but "do the new tests have meaningful `expect()` calls?"), add mutation testing to CI for critical modules, and shift the threshold metric from line to branch coverage.

**Q22. "A junior engineer wants to add `/* istanbul ignore next */` comments to skip coverage on several error-handling blocks. How do you respond?"**
A: `/* istanbul ignore next */` is a legitimate escape hatch — Istanbul honours it and excludes the annotated block from coverage counts. It is appropriate in narrow cases:

**When it is correct:**
- Generated code or boilerplate that can't be meaningfully tested (e.g., a `switch` default that handles exhaustive TypeScript discriminated unions — the branch is structurally unreachable).
- Error handlers for scenarios that are impossible to trigger in a test environment (e.g., a `process.on('uncaughtException')` handler that would crash the process to test).
- Platform-specific code paths (`if (process.platform === 'win32')`) that the CI environment can't exercise.

**When it is incorrect (and the likely intent of the junior engineer):**
- Error paths that *can* be tested but are awkward to set up — force the error in a test rather than ignoring the path. A `catch` block that handles a DB connection failure is important code; mock the DB to throw and test the handler.
- "I don't know how to write this test" — the comment papers over a test gap without fixing it. The right response is pairing to write the test, not ignoring the line.

**Practical guidance to give:**
"The `ignore` comment is the right call for genuinely untestable code — show me the block and we'll decide together. If it's an error handler, let's write the test first; error paths are where the most impactful bugs live. If after that it truly can't be triggered, add the comment with an inline explanation of why: `/* istanbul ignore next — unreachable: TypeScript exhaustive check */`."

Require that every `ignore` comment has an explanatory suffix. A repository search for uncommented `istanbul ignore` comments in a PR should be a blocking review concern.

**Q23. "You're setting coverage thresholds for a new fintech API from scratch. Walk through how you decide on the numbers."**
A: A structured approach — not picking 80% because it "sounds right":

**Step 1 — Establish a baseline**
Run coverage with no threshold on the current codebase. This gives you the actual numbers to start from. Never set a threshold above the current score — it immediately breaks CI and poisons the team's relationship with the tool.

**Step 2 — Classify modules by risk**
Map the codebase into risk tiers:
- **Tier 1 — Critical domain logic**: payment processing, interest calculation, fraud scoring, authentication, authorization. Statement: 95%, Branch: 90%.
- **Tier 2 — Core API layer**: controllers, request validation, service orchestration. Statement: 85%, Branch: 80%.
- **Tier 3 — Infrastructure wiring**: DI configuration, DB pool setup, environment config, logging setup. Statement: 60%, Branch: 50% (covered by integration tests, not unit tests).
- **Tier 4 — Generated/external**: migrations, generated API clients, third-party type stubs. Excluded via `coveragePathIgnorePatterns`.

**Step 3 — Combine line and branch**
Branch coverage is the more meaningful metric; don't set a high line threshold and a low branch threshold. The branch threshold should be at most 5–10 points below the line threshold.

**Step 4 — Set a ratchet**
Configure Codecov's `patch` target at 5% above the global threshold for new code. This means existing code can stay at the baseline while all new code is held to a higher standard — practical for brownfield projects.

**Step 5 — Review quarterly**
Coverage thresholds are not set-and-forget. As the codebase grows and tests improve, increase the thresholds. Document the change in `CHANGELOG.md` — "Raised branch coverage floor from 70% to 80%" is a meaningful engineering milestone.

**Q24. "How do you explain to a product manager why the team has 88% coverage but you're still not confident in releasing a critical new payment flow?"**
A: Frame it in terms the PM understands — execution vs verification:

"Coverage tells us that our tests *ran* 88% of the code — like a quality inspector walking down every aisle of a factory and confirming the machines are turned on. What it doesn't tell us is whether the inspector checked that each machine was producing the right output.

For this payment flow specifically, I ran a deeper analysis [mutation testing] that found our tests would miss about 35% of realistic bugs we could introduce — a wrong comparison sign, a missing confirmation email, an off-by-one on the fee calculation. These are the kinds of bugs that pass all our tests today but break for real users tomorrow.

What I need before I'm confident releasing:
1. Tests that explicitly verify the fee calculation is correct for each pricing tier — not just that the function runs.
2. A test that confirms a payment confirmation is sent to the user — currently our tests don't check this side effect.
3. A test for the refund path when authorization succeeds but capture fails.

That's two or three days of work on the right tests, not more tests for coverage's sake. After that, I'll be confident."

This reframes the conversation from "the number isn't high enough" to "these specific scenarios aren't verified" — which is actionable and credible.

**Q25. "Walk me through setting up a complete coverage pipeline for a TypeScript monorepo with Jest — from configuration to CI to PR gating."**
A: A production-ready setup for a Nx or Turborepo TypeScript monorepo:

**Step 1 — Root Jest config (base, extended per package)**
```typescript
// jest.base.config.ts (shared)
import type { Config } from 'jest';

const base: Config = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  coverageProvider: 'babel',          // Istanbul for TypeScript accuracy
  collectCoverageFrom: [
    'src/**/*.ts',
    '!src/**/*.spec.ts',
    '!src/**/*.d.ts',
    '!src/index.ts',
    '!src/migrations/**',
  ],
  coverageReporters: ['text', 'lcov', 'html'],
  coverageThreshold: {
    global: { statements: 80, branches: 75, functions: 80, lines: 80 },
  },
};

export default base;
```

```typescript
// packages/payments/jest.config.ts (stricter for critical package)
import base from '../../jest.base.config';
export default {
  ...base,
  coverageThreshold: {
    global: { statements: 95, branches: 90, functions: 95, lines: 95 },
  },
};
```

**Step 2 — CI workflow**
```yaml
# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - name: Test all packages with coverage
        run: npx turbo test -- --coverage
        # Each package's jest.config.ts enforces its own thresholds

      - name: Merge lcov reports
        run: |
          npm install -g lcov-result-merger
          lcov-result-merger 'packages/*/coverage/lcov.info' coverage/lcov.info

      - name: Upload to Codecov
        uses: codecov/codecov-action@v4
        with:
          files: coverage/lcov.info
          token: ${{ secrets.CODECOV_TOKEN }}
          fail_ci_if_error: true
```

**Step 3 — Codecov config for PR gating**
```yaml
# codecov.yml
coverage:
  status:
    project:
      default:
        target: auto          # must not drop below current main branch score
        threshold: 0.5%       # allow up to 0.5% drop (floating point noise)
    patch:
      default:
        target: 85%           # new lines added in PR must have 85% coverage
  ignore:
    - "packages/*/src/migrations"
    - "packages/*/src/index.ts"

comment:
  layout: "reach, diff, flags, files"
  behavior: default
  require_changes: true       # only comment when coverage changes
```

**Step 4 — Developer workflow**
```bash
# Run a single package's tests with coverage and open the HTML report
cd packages/payments
npx jest --coverage && open coverage/lcov-report/index.html

# Run only changed files' tests (fast feedback during development)
npx jest --coverage --changedSince=main

# Check what the CI would see before pushing
npx jest --coverage --ci   # --ci disables interactive mode, treats threshold failures as errors
```

The result: every PR gets automated coverage enforcement (per-package thresholds), trend tracking (Codecov PR comment), and a merged `lcov.info` for the full monorepo — giving both local and CI visibility into coverage state at every level.

## Quick Reference Table

| Reporter | Output | Best used for |
|--|--|--|
| `text` | Terminal table with uncovered lines | Fast local feedback; CI log summary |
| `text-summary` | Single aggregate row | Terse CI log output |
| `lcov` | `coverage/lcov.info` | Codecov / Coveralls upload; VS Code gutters; SonarQube |
| `html` | `coverage/lcov-report/` site | Local investigation; visual PR artifact |
| `clover` | `clover.xml` | Jenkins Clover plugin; Atlassian Bamboo |
| `json` | `coverage-final.json` | Custom tooling; merging monorepo reports |
| `cobertura` | `cobertura-coverage.xml` | Azure DevOps; GitLab native coverage display |

| Coverage type | What it tracks | Minimum recommended |
|--|--|--|
| Statement | Executable statements hit | 80% global; 95% critical modules |
| Branch | Decision outcomes taken | 75% global; 90% critical modules |
| Function | Functions called at least once | 80% global; 95% critical modules |
| Line | Source lines touched | 80% global; 95% critical modules |

The strongest signal you can give is knowing the coverage/quality gap cold — that execution is not assertion, that branch coverage is more meaningful than line coverage, and that mutation score is the honest measure underneath both.
