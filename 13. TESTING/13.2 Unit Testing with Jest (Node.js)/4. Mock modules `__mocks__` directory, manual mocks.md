# Mock Modules: `__mocks__` Directory & Manual Mocks — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a module mock, and why do you need one?**
A: A module mock replaces an entire imported module — or specific exports from it — with a controlled substitute during testing. Instead of executing the real implementation, every call to the module goes through the mock, which returns predictable values, records calls, or simulates error conditions on demand.

You need module mocks when the real module:
- **Crosses an I/O boundary** — filesystem reads, network calls, DB queries. Real I/O makes tests slow, non-deterministic, and environment-dependent.
- **Has side effects you can't allow in tests** — sending real emails, charging real payment cards, writing to production queues.
- **Is non-deterministic** — `Date`, `Math.random()`, timers. Tests that depend on the real clock produce different results depending on when they run.
- **Is a third-party dependency** — you don't own the code, can't control its behavior, and don't want your tests to be coupled to its internals or network availability.

The goal is **isolation**: a unit test should assert the behavior of the module under test, not the behavior of its dependencies. Module mocks provide the seam at which you cut the dependency graph.

**Q2. What is the `__mocks__` directory in Jest, and where does it live?**
A: `__mocks__` is a special directory that Jest recognizes as the home for **manual mocks** — developer-written replacement implementations for modules. Jest uses the directory's *location* relative to the module being mocked to determine scope:

- **Adjacent to `node_modules`** (typically at the project root): mocks for third-party npm packages. Place `__mocks__/axios.js` next to `node_modules/` to mock the `axios` package. For scoped packages (`@org/pkg`), the directory mirrors the scope: `__mocks__/@org/pkg.js`.
- **Adjacent to the module being mocked** (anywhere in `src/`): mocks for local modules. Place `src/utils/__mocks__/db.ts` to provide a manual mock for `src/utils/db.ts`.

```
project-root/
├── __mocks__/               ← third-party mocks (auto-used for some, explicit for others)
│   ├── axios.js
│   └── @stripe/
│       └── stripe-js.js
├── node_modules/
└── src/
    ├── utils/
    │   ├── db.ts
    │   └── __mocks__/
    │       └── db.ts        ← local module manual mock
    └── services/
        └── mailer.ts
```

**Q3. What is the difference between `jest.mock()` and a `__mocks__` directory file — when is each automatically applied?**
A: The two mechanisms work differently depending on whether the module is local or third-party:

| Scenario | `__mocks__` file present | `jest.mock('module')` call needed? |
|--|--|--|
| **Third-party module** (e.g. `axios`) | Yes, in root `__mocks__/` | **Yes** — Jest does NOT auto-apply third-party mocks; you must call `jest.mock('axios')` to activate |
| **Local module** (e.g. `./utils/db`) | Yes, in sibling `__mocks__/` | **No** — Jest auto-applies local manual mocks when the `__mocks__` file exists |
| **No `__mocks__` file** | No | `jest.mock('./path')` auto-mocks (replaces with `jest.fn()` stubs for every export) |

The asymmetry between local and third-party is a common source of confusion. The rationale: local mocks are opt-in by the developer placing the file; third-party mocks still require an explicit opt-in call to avoid accidentally silencing a real dependency without intention.

**Q4. What does Jest's automatic mock (`jest.mock('module')` with no factory) actually produce?**
A: When called with no factory function, `jest.mock()` triggers Jest's **automocking** system, which:
1. Loads the real module to inspect its shape.
2. Replaces every exported function with `jest.fn()` — a spy that records calls and returns `undefined` by default.
3. Replaces every exported class with a mock class whose constructor and all methods are `jest.fn()`.
4. Preserves the module's export structure (named exports, default export) so import statements don't break.

What it does NOT do: copy implementation logic. The resulting mock is a structural skeleton — it has the right shape but does nothing. You must configure return values explicitly with `.mockReturnValue()`, `.mockResolvedValue()`, etc.

```typescript
// src/services/email.ts
export const sendEmail = async (to: string, subject: string) => { /* real SMTP */ };
export const validateAddress = (email: string): boolean => { /* real regex */ };

// In a test file:
jest.mock('../services/email');
import { sendEmail, validateAddress } from '../services/email';

// sendEmail and validateAddress are now jest.fn() — no implementation
// sendEmail() returns undefined (or a resolved Promise<undefined> for async)
// validateAddress() returns undefined (not boolean)
```

**Q5. What is a manual mock, and when do you choose it over `jest.mock()` with a factory?**
A: A manual mock is a module you write by hand in `__mocks__/`, designed to be a reusable, maintainable substitute for the real module across multiple test files. Choose a manual mock when:

- **The mock is complex** — a fake in-memory database, a stubbed HTTP client with realistic response shapes, a fake event emitter. Rewriting this inline with a factory in every test file is duplicative and inconsistent.
- **The mock needs to be shared** — many test files mock the same module (e.g., a `db` client, a `logger`, an `s3` client). A `__mocks__` file is defined once and activated per-file with a single `jest.mock()` call.
- **The mock needs its own test-facing API** — a manual mock can expose helper functions (`__setResponse()`, `__getCallCount()`) that let individual tests configure its behavior without reimplementing the mock logic.

Choose an inline factory (`jest.mock('./module', () => ({ ... }))`) when the mock is simple, one-off, and the behavior varies significantly between test files.

## Section 2: Writing Manual Mocks

**Q6. How do you write a manual mock for a local module with named exports?**
A: Mirror the real module's export structure in the `__mocks__` file, replacing real implementations with `jest.fn()` or controlled fakes:

```typescript
// src/utils/db.ts (real module)
import { Pool } from 'pg';

const pool = new Pool();

export const query = async <T>(sql: string, params?: unknown[]): Promise<T[]> => {
  const result = await pool.query(sql, params);
  return result.rows;
};

export const transaction = async <T>(fn: (client: PoolClient) => Promise<T>): Promise<T> => {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (e) {
    await client.query('ROLLBACK');
    throw e;
  } finally {
    client.release();
  }
};
```

```typescript
// src/utils/__mocks__/db.ts (manual mock)
export const query = jest.fn().mockResolvedValue([]);

export const transaction = jest.fn().mockImplementation(
  async (fn: (client: unknown) => Promise<unknown>) => fn({})
);

// Test-facing helper: lets individual tests set the next query result
export const __setQueryResult = (rows: unknown[]) => {
  query.mockResolvedValueOnce(rows);
};
```

In a test file:
```typescript
// Jest auto-applies this because __mocks__/db.ts exists adjacent to db.ts
import { query, __setQueryResult } from '../utils/db';
import { getUserById } from '../services/userService';

// No jest.mock() call needed for local modules with __mocks__ files

test('getUserById returns user from DB', async () => {
  __setQueryResult([{ id: 1, name: 'Aditya', email: 'a@example.com' }]);
  const user = await getUserById(1);
  expect(user.name).toBe('Aditya');
  expect(query).toHaveBeenCalledWith(
    expect.stringContaining('SELECT'),
    [1]
  );
});
```

**Q7. How do you write a manual mock for a third-party module — say, `axios`?**
A: Place the mock at `__mocks__/axios.js` (root level, adjacent to `node_modules`). Third-party mocks must also be explicitly activated with `jest.mock('axios')` in each test file that uses them.

```javascript
// __mocks__/axios.js
const mockAxios = {
  get: jest.fn(),
  post: jest.fn(),
  put: jest.fn(),
  delete: jest.fn(),
  create: jest.fn(() => mockAxios), // axios.create() returns an axios instance
  interceptors: {
    request: { use: jest.fn(), eject: jest.fn() },
    response: { use: jest.fn(), eject: jest.fn() },
  },
  defaults: { headers: { common: {} } },
};

export default mockAxios;
```

In a test file:
```typescript
jest.mock('axios'); // activates __mocks__/axios.js
import axios from 'axios';
import { fetchUser } from '../services/userService';

test('fetchUser calls correct endpoint', async () => {
  (axios.get as jest.Mock).mockResolvedValueOnce({
    data: { id: 1, name: 'Aditya' },
    status: 200,
  });

  const user = await fetchUser(1);

  expect(axios.get).toHaveBeenCalledWith('/users/1');
  expect(user.name).toBe('Aditya');
});
```

**Q8. How do you mock a module that exports a class?**
A: Mock the class constructor and its prototype methods. The pattern differs between `jest.mock()` with a factory and a `__mocks__` file:

```typescript
// src/services/mailer.ts
export class Mailer {
  constructor(private apiKey: string) {}
  async send(to: string, subject: string, body: string): Promise<void> { /* real SMTP */ }
  async sendBulk(recipients: string[], subject: string): Promise<void> { /* real SMTP */ }
}
```

**Option A — Inline factory (one-off):**
```typescript
jest.mock('../services/mailer', () => ({
  Mailer: jest.fn().mockImplementation(() => ({
    send: jest.fn().mockResolvedValue(undefined),
    sendBulk: jest.fn().mockResolvedValue(undefined),
  })),
}));
```

**Option B — `__mocks__` file (shared across test files):**
```typescript
// src/services/__mocks__/mailer.ts
const mockSend = jest.fn().mockResolvedValue(undefined);
const mockSendBulk = jest.fn().mockResolvedValue(undefined);

export const Mailer = jest.fn().mockImplementation(() => ({
  send: mockSend,
  sendBulk: mockSendBulk,
}));

// Expose mock instances for assertions in tests
export const __getMockMailerInstance = () => ({
  send: mockSend,
  sendBulk: mockSendBulk,
});
```

```typescript
// In a test:
import { Mailer, __getMockMailerInstance } from '../services/mailer';
import { sendWelcomeEmail } from '../services/onboarding';

test('sendWelcomeEmail sends to the new user', async () => {
  await sendWelcomeEmail({ email: 'a@example.com', name: 'Aditya' });
  const { send } = __getMockMailerInstance();
  expect(send).toHaveBeenCalledWith(
    'a@example.com',
    'Welcome!',
    expect.stringContaining('Aditya')
  );
});
```

**Q9. How do you reset, clear, and restore mocks between tests, and what is the difference between `clearMocks`, `resetMocks`, and `restoreMocks`?**
A: Three distinct operations, each going one level deeper:

| Operation | What it does | Jest config | Manual call |
|--|--|--|--|
| **`clearMocks`** | Clears call history, instances, results — does NOT reset implementation | `clearMocks: true` | `jest.clearAllMocks()` |
| **`resetMocks`** | Clears + resets implementation to `jest.fn()` (removes `.mockReturnValue` etc.) | `resetMocks: true` | `jest.resetAllMocks()` |
| **`restoreMocks`** | Reset + restores the original implementation (only works for `jest.spyOn`) | `restoreMocks: true` | `jest.restoreAllMocks()` |

In `jest.config.ts`, enabling `resetMocks: true` globally is a strong default for module mocks — each test starts with a clean `jest.fn()` and must configure its own return values explicitly. This prevents tests from relying on implementation setup that leaked from a previous test:

```typescript
// jest.config.ts
export default {
  resetMocks: true,  // recommended for projects using __mocks__ heavily
  clearMocks: true,  // implied by resetMocks, but explicit for clarity
};
```

## Section 3: Advanced Patterns

**Q10. How do you partially mock a module — keeping some real exports and replacing others?**
A: Use `jest.requireActual()` inside a factory to import the real module, then spread it and override only the exports you want to mock:

```typescript
// src/utils/crypto.ts
export const hash = (input: string): string => bcrypt.hashSync(input, 10); // slow, real
export const generateToken = (): string => crypto.randomUUID();            // non-deterministic
export const isValidFormat = (token: string): boolean => /^[a-z0-9-]{36}$/.test(token); // pure, keep real

// In a test:
jest.mock('../utils/crypto', () => ({
  ...jest.requireActual('../utils/crypto'), // keep isValidFormat real
  hash: jest.fn().mockReturnValue('$2b$10$hashedvalue'),
  generateToken: jest.fn().mockReturnValue('00000000-0000-0000-0000-000000000001'),
}));
```

The same pattern works in a `__mocks__` file:
```typescript
// src/utils/__mocks__/crypto.ts
const actual = jest.requireActual('../utils/crypto');

export const { isValidFormat } = actual; // real implementation
export const hash = jest.fn().mockReturnValue('$2b$10$hashedvalue');
export const generateToken = jest.fn().mockReturnValue('00000000-0000-0000-0000-000000000001');
```

**Q11. How do you mock ES modules vs CommonJS modules, and where does the difference matter?**
A: The difference surfaces in how `jest.mock()` hoisting interacts with the module system:

**CommonJS** — `jest.mock()` replaces the module in Node's `require()` cache before the test file runs. Straightforward, no special handling needed.

**ES modules (native)** — Jest's default transformer (Babel or `ts-jest`) transpiles ES module syntax to CommonJS before running, so `jest.mock()` hoisting works as expected in most projects. However, with `--experimental-vm-modules` (native ESM support in Jest), hoisting doesn't apply and you must use a different pattern:

```typescript
// Native ESM — jest.mock() must be called before imports, which isn't possible with static imports.
// Use dynamic imports instead:
const { default: axios } = await import('axios');
jest.unstable_mockModule('axios', () => ({ default: { get: jest.fn() } }));
```

**The practical rule for most TypeScript projects**: Babel or `ts-jest` handles the transpilation, native ESM quirks don't apply, and `jest.mock()` + `__mocks__` work as documented. If you switch to `type: "module"` in `package.json` with native ESM, be prepared to migrate to `jest.unstable_mockModule` and dynamic imports.

**Q12. How does `jest.mock()` hoisting work, and what are the implications for variable declarations in factories?**
A: Jest's Babel plugin (or `ts-jest`) hoists `jest.mock()` calls to the top of the file — above all `import` statements — at compile time. This ensures the mock is in place before the module under test is loaded. The implication:

```typescript
// What you write:
import { sendWelcomeEmail } from '../services/onboarding';
jest.mock('../services/mailer');

// What Jest actually executes (after hoisting):
jest.mock('../services/mailer');
import { sendWelcomeEmail } from '../services/onboarding';
```

The dangerous consequence: **variables declared before `jest.mock()` are NOT in scope at the point the factory runs**, because the factory executes before the import declarations:

```typescript
// ❌ This silently fails — mockSend is undefined when the factory runs
const mockSend = jest.fn();
jest.mock('../services/mailer', () => ({
  Mailer: jest.fn(() => ({ send: mockSend })), // mockSend is undefined here!
}));

// ✅ Correct — declare inside the factory, or use the MOCK_prefix exception
jest.mock('../services/mailer', () => ({
  Mailer: jest.fn(() => ({ send: jest.fn() })), // self-contained
}));
```

The one exception: Jest allows variables prefixed with `mock` (exactly `mock`, case-sensitive) to be referenced in factory functions — it's a special carve-out in the hoisting transform. Name your variable `mockSend` (not `sendMock`) and it can be referenced inside the factory.

**Q13. How do you mock a module differently in different tests within the same file?**
A: Three techniques, depending on the degree of variation needed:

**Option A — `mockReturnValueOnce` / `mockResolvedValueOnce`**
Configure the mock to return different values on sequential calls. Clean for testing error paths after a happy path:
```typescript
jest.mock('../utils/db');
import { query } from '../utils/db';

test('retries on first failure', async () => {
  (query as jest.Mock)
    .mockRejectedValueOnce(new Error('Connection timeout'))
    .mockResolvedValueOnce([{ id: 1 }]);

  const result = await getUserWithRetry(1);
  expect(result.id).toBe(1);
  expect(query).toHaveBeenCalledTimes(2);
});
```

**Option B — `mockImplementation` inside each test**
Override the mock's behavior per test using `beforeEach` reset + per-test configuration:
```typescript
beforeEach(() => jest.resetAllMocks());

test('returns user on success', async () => {
  (query as jest.Mock).mockResolvedValue([{ id: 1, name: 'Aditya' }]);
  // ...
});

test('throws on DB error', async () => {
  (query as jest.Mock).mockRejectedValue(new Error('DB unavailable'));
  // ...
});
```

**Option C — `jest.doMock()` for per-test module replacement**
`jest.doMock()` is the non-hoisted version of `jest.mock()`. Combined with `jest.resetModules()`, it lets you completely re-require a module with a different mock in the same file — useful when the mock needs to differ structurally (different export shape) between tests:
```typescript
test('uses feature flag variant', async () => {
  jest.resetModules();
  jest.doMock('../config/flags', () => ({ ENABLE_NEW_FLOW: true }));
  const { processOrder } = await import('../services/orders');
  // ...
});
```

**Q14. How do you mock timers and dates in Jest, and how does that relate to module mocking?**
A: Timers and dates are global, not module exports, so they use a different Jest API — but the concept (replacing non-deterministic behavior with controlled substitutes) is identical:

```typescript
describe('session expiry', () => {
  beforeEach(() => {
    jest.useFakeTimers();
    jest.setSystemTime(new Date('2024-01-15T10:00:00Z'));
  });

  afterEach(() => {
    jest.useRealTimers();
  });

  test('session expires after 30 minutes', () => {
    const session = createSession(userId);
    expect(session.isValid()).toBe(true);

    jest.advanceTimersByTime(31 * 60 * 1000); // fast-forward 31 minutes

    expect(session.isValid()).toBe(false);
  });

  test('createdAt timestamp uses controlled clock', () => {
    const session = createSession(userId);
    expect(session.createdAt).toEqual(new Date('2024-01-15T10:00:00Z'));
  });
});
```

The interplay with module mocks: if a module internally calls `new Date()` or `setTimeout()`, fake timers affect it transparently — you don't need to mock the module, just control time globally. But if a module caches the date at import time (`const NOW = Date.now()` at the top level), fake timers won't help — you must mock the module to control that cached value.

## Section 4: Real-World Patterns & Architecture

**Q15. What is a "fake" as opposed to a mock, and when do you prefer a fake in `__mocks__`?**
A: A **fake** is a working implementation that uses simpler mechanisms than production — an in-memory store instead of a real DB, an in-process message bus instead of Kafka. It's distinct from a mock (`jest.fn()` with configured return values) in that it has real logic:

```typescript
// src/repositories/__mocks__/userRepository.ts
// A fake — has real logic, just no real DB

const store = new Map<number, User>();
let nextId = 1;

export const findById = jest.fn(async (id: number): Promise<User | null> => {
  return store.get(id) ?? null;
});

export const save = jest.fn(async (user: Omit<User, 'id'>): Promise<User> => {
  const newUser = { ...user, id: nextId++ };
  store.set(newUser.id, newUser);
  return newUser;
});

export const __reset = () => {
  store.clear();
  nextId = 1;
  findById.mockClear();
  save.mockClear();
};
```

Prefer a fake when:
- The module has **stateful behavior** — a DB that must return what was previously inserted. A `jest.fn().mockReturnValue()` can't model this without duplicating the logic in every test.
- Multiple tests in a suite need to **interact with shared state** — test A inserts a record, test B reads it.
- The mock would otherwise require **complex, duplicated setup** in every test file that uses it.

Prefer `jest.fn()` mocks when the behavior is stateless and the test only needs to verify a call was made with specific arguments.

**Q16. How do you handle modules with side effects at import time in Jest mocks?**
A: Some modules execute side effects when first imported — database connection pool initialisation, process signal handlers, singleton registrations. These are problematic in tests because:
1. The side effect runs even if the module is mocked.
2. `jest.mock()` prevents the real implementation from running but the import itself still triggers module evaluation.

Solutions:

**Lazy initialization** (fix in the module itself):
```typescript
// Bad — side effect at import time
const pool = new Pool({ connectionString: process.env.DATABASE_URL }); // runs on import

// Good — lazy initialization
let pool: Pool | null = null;
export const getPool = () => {
  if (!pool) pool = new Pool({ connectionString: process.env.DATABASE_URL });
  return pool;
};
```

**Mock the entire module** — if the module must have side effects, mock it entirely in `__mocks__/` so the real code never runs during tests.

**`jest.isolateModules()`** — if you need the real module in some tests and a clean slate in others, use `jest.isolateModules()` to reset the module registry for a specific block, preventing cached side-effect state from leaking:
```typescript
test('initializes pool on first call', () => {
  jest.isolateModules(() => {
    const { getPool } = require('../utils/db');
    const pool = getPool();
    expect(pool).toBeDefined();
  });
});
```

**Q17. How do you mock environment variables, and how does that interact with module mocks?**
A: Environment variables (`process.env`) are read at module evaluation time in some modules and at call time in others — the behavior depends on where the read happens:

```typescript
// Pattern A — read at module evaluation (import time)
const API_KEY = process.env.STRIPE_API_KEY!; // locked in at import
export const charge = (amount: number) => stripe.charge(API_KEY, amount);

// Pattern B — read at call time
export const charge = (amount: number) =>
  stripe.charge(process.env.STRIPE_API_KEY!, amount); // fresh read each call
```

For Pattern A, changing `process.env.STRIPE_API_KEY` after importing the module has no effect — the value is captured. You must set the env variable before the import, or use `jest.resetModules()` + re-import to get a fresh evaluation:

```typescript
describe('with valid API key', () => {
  beforeEach(() => {
    jest.resetModules();
    process.env.STRIPE_API_KEY = 'sk_test_valid';
  });

  test('charge uses configured key', async () => {
    const { charge } = await import('../services/stripe'); // fresh import
    // ...
  });
});
```

For Pattern B, `process.env` assignment works directly because it's read on each call. A cleaner approach across both patterns is to centralise config in a dedicated `config.ts` module and mock that:

```typescript
// src/config.ts
export const config = {
  stripeApiKey: process.env.STRIPE_API_KEY!,
  dbUrl: process.env.DATABASE_URL!,
};

// src/__mocks__/config.ts — mock the whole config module
export const config = {
  stripeApiKey: 'sk_test_mock',
  dbUrl: 'postgres://localhost:5432/testdb',
};
```

## Section 5: Tradeoffs, Pitfalls & Anti-patterns

**Q18. What are the main risks of over-mocking, and how does it manifest in a test suite?**
A: Over-mocking happens when the test mocks so many collaborators that it no longer tests meaningful behavior — it tests the mock configuration. Signs:

- **Tests that only verify mock calls, never outcomes** — `expect(mockDb.save).toHaveBeenCalled()` without also asserting the returned value or side effect. If the mock is called but produces the wrong result and nothing checks the result, the test is hollow.
- **Mocks that mirror the implementation** — the mock is configured to return exactly what the real code would return, making the test pass by construction. Change the implementation, and the test passes anyway because the mock still returns the old value.
- **100% coverage, surviving mutants** — the classic symptom from mutation testing. The code is executed (coverage hit) but not meaningfully asserted upon (mutation survives).
- **Test suite passes when the system is broken** — if you mock `axios` and the real endpoint changes its response schema, your tests stay green while production fails.

The corrective lens: for each mock, ask "what would change in this test if the module under test had a bug?" If the answer is "nothing," the mock is too aggressive.

**Q19. What is "mock drift," and how do you prevent it?**
A: Mock drift is the gradual divergence between a manual mock in `__mocks__/` and the real module it replaces. As the real module evolves — new exports, renamed methods, changed signatures — the mock becomes stale. Tests that use the stale mock continue to pass while the real integration is broken.

Prevention strategies:

- **Type the mock with the real module's types** — if `__mocks__/db.ts` exports `jest.fn()` typed as `typeof db.query`, TypeScript will error when the real signature changes:
```typescript
// src/utils/__mocks__/db.ts
import type * as RealDb from '../db'; // import types only — no runtime import

export const query: jest.MockedFunction<typeof RealDb.query> =
  jest.fn().mockResolvedValue([]);

export const transaction: jest.MockedFunction<typeof RealDb.transaction> =
  jest.fn().mockImplementation(async (fn) => fn({}));
```

- **`jest.mocked()` helper** — wraps an import in `jest.Mocked<T>` for type-safe access to mock methods:
```typescript
import { query } from '../utils/db';
import { jest } from '@jest/globals';

const mockQuery = jest.mocked(query); // TypeScript knows this is jest.MockedFunction<typeof query>
mockQuery.mockResolvedValue([{ id: 1 }]); // fully typed
```

- **Contract tests** — for third-party mocks (`__mocks__/axios.js`), run a separate contract test against the real API in a non-unit test environment to verify the mock still matches the real interface.

**Q20. When is it wrong to use a module mock, and what should you do instead?**
A: Three situations where a module mock is the wrong tool:

- **The module has no boundary worth isolating** — mocking a pure utility (`lodash`, `date-fns`, a local `formatCurrency` function) adds mock overhead without isolation benefit. Import and use the real function; it's deterministic and has no side effects.
- **You're testing the integration itself** — if the point of the test is to verify that your code and the DB work correctly together, mocking the DB defeats the purpose. Use a real DB (Testcontainers) and call it an integration test.
- **The mock is hiding a design problem** — if you need 8 mocks to test a single function, the function has too many dependencies. The right fix is to refactor (extract a pure core, inject dependencies) so the unit can be tested with at most 1–2 doubles. Reaching for more mocks papers over the design smell.

## Section 6: Scenario / System Design Style Questions

**Q21. "A test file imports `stripe` from a third-party SDK and makes real API calls. How do you fix it without rewriting the service?"**
A: Layer the mocking without touching the service code:

**Step 1 — Create `__mocks__/stripe.js`** at the project root:
```javascript
// __mocks__/stripe.js
const stripe = jest.fn().mockImplementation(() => ({
  paymentIntents: {
```

**Q22. "Two test files mock the same `db` module differently, and they interfere when run in the same Jest worker. How do you diagnose and fix this?"**
A: Jest runs each test *file* in isolation (separate worker, separate module registry by default), so two files with different `db` mocks should not interfere — unless:

1. **`--runInBand` mode** — tests run sequentially in a single process, sharing the module registry. One file's `jest.mock()` can bleed into the next if the registry isn't reset between files.
2. **`globalSetup` / `setupFiles` pollution** — a global setup configures a mock that persists across all files.
3. **Shared in-memory state in a manual mock** — the `__mocks__/db.ts` fake stores state in a module-level `Map`. Module-level state in a `__mocks__` file is shared across all tests within the same file but not across files — unless `--runInBand` collapses them into one process.

Diagnosis:
```bash
# Run only the two conflicting files together in band to reproduce
npx jest --testPathPattern="fileA|fileB" --runInBand --verbose
```

Fix options:
- Add `__reset()` to the manual mock and call it in `afterEach` / `afterAll` in each test file.
- Add `jest.resetModules()` in `afterEach` in global setup to force a fresh module registry per test.
- Ensure the manual mock has no module-level mutable state — initialise state inside a factory function called at the start of each test instead.

**Q23. "You're onboarding a new service that calls three external APIs (payment gateway, KYC provider, notification service). How do you structure the `__mocks__` directory for the project?"**
A: Design the mock layer to mirror the real service layer's structure:

```
project-root/
├── __mocks__/                        ← third-party SDK mocks
│   ├── axios.ts                      ← base HTTP client (if used directly)
│   └── @sendgrid/
│       └── mail.ts                   ← SendGrid notification SDK
│
└── src/
    ├── integrations/
    │   ├── payment/
    │   │   ├── razorpay.client.ts
    │   │   └── __mocks__/
    │   │       └── razorpay.client.ts  ← fake with __setPaymentResult()
    │   ├── kyc/
    │   │   ├── digio.client.ts
    │   │   └── __mocks__/
    │   │       └── digio.client.ts     ← fake with __setKycStatus()
    │   └── notifications/
    │       ├── fcm.client.ts
    │       └── __mocks__/
    │           └── fcm.client.ts       ← spy with __getSentNotifications()
    └── ...
```

Design principles for each mock:
- **Razorpay fake** — stateful: `__setPaymentResult('success' | 'failure' | 'pending')` configures the next response; test can assert on `capture.toHaveBeenCalledWith(expectedOrderId)`.
- **Digio KYC fake** — stateful: `__setKycStatus(panNumber, 'verified' | 'rejected')` lets tests simulate different KYC outcomes without real API calls.
- **FCM notification spy** — stateless: `jest.fn()` with a `__getSentNotifications()` helper that returns call args for assertion.

Global Jest config:
```typescript
// jest.config.ts

  setupFilesAfterFramework: ['./jest.setup.ts'],

import { __reset as resetPayment } from './src/integrations/payment/__mocks__/razorpay.client';
import { __reset as resetKyc } from './src/integrations/kyc/__mocks__/digio.client';

  resetPayment();
  resetKyc();
});
```

**Q24. "A mutation testing run shows that deleting the `logger.error(err)` call in your catch block survives all tests. The logger is injected via `__mocks__`. What went wrong and how do you fix it?"**
A: The survival tells you the logger mock is being called (coverage hit) but no test asserts that `logger.error` was invoked with the right arguments — or at all — in the error path.

Root cause: the error-path test probably only asserts the function throws or returns an error response, but never checks the side effect:

```typescript
// Test that passes but doesn't kill the mutation:
test('returns 500 on DB error', async () => {
  (query as jest.Mock).mockRejectedValue(new Error('DB unavailable'));
  const response = await request(app).get('/users/1');
  expect(response.status).toBe(500); // passes even if logger.error is never called
});
```

Fix — add the assertion on the side effect:
```typescript
import { logger } from '../utils/logger'; // auto-uses __mocks__/logger.ts

test('logs error when DB fails', async () => {
  const dbError = new Error('DB unavailable');
  (query as jest.Mock).mockRejectedValue(dbError);

  await request(app).get('/users/1');

  expect(logger.error).toHaveBeenCalledWith(
    expect.stringContaining('Failed to fetch user'),
    expect.objectContaining({ error: dbError })
  );
});
```

The broader lesson: for every mock that represents a side effect (logger, mailer, audit service, metrics emitter), each test that exercises that code path should assert the side effect happened — not just that the return value was correct. Side-effect assertions are the most commonly missing assertions in mock-heavy test suites, and mutation testing reliably surfaces them.

**Q25. "Your team is debating whether to use `__mocks__` files or always use inline `jest.mock()` factories. What factors guide the decision, and what would you recommend?"**
A: The decision is fundamentally about **reuse vs explicitness**. Frame it around three questions:

**1. How many test files share this mock?**
- One or two files → inline factory. The mock is local knowledge; keeping it co-located with the test that needs it is more readable.
- Three or more files → `__mocks__` file. The same mock logic written three times in three factories will drift; a shared `__mocks__` file is the single source of truth.

**2. How complex is the mock?**
- Simple (one function, one return value) → inline. `jest.mock('./mailer', () => ({ send: jest.fn() }))` is one line and self-documenting.
- Complex (stateful fake, multiple methods, test-facing helpers) → `__mocks__`. Inline factories for a 50-line fake make tests hard to read and the mock impossible to maintain.

**3. Does the mock need a test-facing API?**
- If tests need to configure mock behavior per-test (`__setQueryResult([...])`) or inspect side effects (`__getSentNotifications()`), the mock needs exported helper functions that can't be accessed from an inline factory. → `__mocks__` file, always.

**Recommendation for a mature codebase:**
- Infrastructure modules (DB, HTTP clients, logger, mailer, queue producers) → `__mocks__` files. These are used everywhere, their mocks are complex, and consistency across the test suite is valuable.
- Third-party SDKs with complex initialization (Stripe, AWS SDK) → `__mocks__` files at root.
- One-off, simple collaborators in a specific test → inline `jest.mock()` factory.
- Pure utility functions (formatters, validators, pure math) → no mock at all; use the real implementation.

Document the convention in `CONTRIBUTING.md` so new engineers don't have to guess: "infrastructure adapters are mocked via `__mocks__`; test-local collaborators use inline factories."

## Quick Reference Table

| Scenario | Mechanism | Auto-applied? | Notes |
|--|--|--|--|
| Local module, `__mocks__` sibling exists | `__mocks__/module.ts` | Yes (no `jest.mock()` needed) | Jest detects adjacent `__mocks__` automatically |
| Third-party package, `__mocks__` at root | Root `__mocks__/pkg.js` + `jest.mock('pkg')` | No — `jest.mock()` required | Must opt in per test file |
| No `__mocks__` file, all exports mocked | `jest.mock('./path')` | N/A — explicit call | Automock: every export → `jest.fn()` |
| Partial mock (keep some real exports) | `jest.requireActual()` in factory | N/A | Spread real, override specific exports |
| Per-test behavior variation | `mockReturnValueOnce` / `mockImplementation` | N/A | Reset with `jest.resetAllMocks()` in `beforeEach` |
| Non-hoisted mock (per-test module replace) | `jest.doMock()` + `jest.resetModules()` | N/A | Dynamic import required after `doMock` |
| Typed mock (prevent drift) | `jest.mocked()` / `jest.MockedFunction<typeof fn>` | N/A | TypeScript catches signature changes |
| Timer / date control | `jest.useFakeTimers()` / `jest.setSystemTime()` | N/A | Global, not module-scoped |

Know the local vs third-party auto-application asymmetry cold, understand hoisting and the `mockVariable` naming exception, and have a concrete story about finding a mock that diverged from the real module and caused a production incident — preferably with the `jest.MockedFunction<typeof realFn>` pattern as the fix.
