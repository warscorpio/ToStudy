# Jest Fake Timers: `jest.useFakeTimers()`, `jest.advanceTimersByTime()` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do fake timers solve, and why is real-time waiting in tests a FIRST violation?**
A: Production code frequently uses `setTimeout`, `setInterval`, `Date.now()`, and `new Date()` to drive time-dependent behaviour — retry delays, token expiry, scheduled jobs, debouncing, rate limiting windows. Without fake timers, a test that exercises a 30-second retry loop must actually wait 30 seconds — this violates the **Fast** principle and makes the suite unusable at scale. One 30-second wait in a suite of 500 tests doesn't matter in isolation, but accumulated across dozens of timer-dependent tests, the suite becomes too slow to run on every commit. Fake timers replace the real timer APIs with synchronous, controllable substitutes — the test controls what time "is" and how fast it advances, with no wall-clock waiting. The test runs in milliseconds regardless of how long the simulated time span is.

**Q2. What does `jest.useFakeTimers()` actually replace, and what does it leave untouched?**
A: `jest.useFakeTimers()` replaces the following globals with Jest-controlled fakes:
- `setTimeout` / `clearTimeout`
- `setInterval` / `clearInterval`
- `setImmediate` / `clearImmediate`
- `Date` (including `Date.now()` and `new Date()`)
- `queueMicrotask` (depending on Jest version and configuration)
- `process.nextTick` (opt-in — controlled by the `doNotFake` option or `@sinonjs/fake-timers` config)

What it leaves untouched by default:
- Real async operations — `fetch`, DB queries, filesystem calls still use real time.
- `Promise` resolution — microtasks still resolve naturally.
- Worker threads and child processes — they have their own timer contexts.

The critical implication: fake timers control *when callbacks fire*, but they do not pause or accelerate real I/O. A `setTimeout(() => db.query(...), 1000)` with fake timers will fire the callback immediately when you advance time, but the `db.query()` inside it still runs at real speed.

**Q3. What is the difference between `jest.useFakeTimers('legacy')` and the default (modern) mode?**
A: In Jest 27+, the default fake timer implementation is backed by `@sinonjs/fake-timers`, which is more accurate and feature-complete. The `'legacy'` mode uses Jest's older, custom implementation. Key differences:

| Feature                          | Legacy                            | Modern (default, `@sinonjs/fake-timers`) |
|----------------------------------|-----------------------------------|------------------------------------------|
| `Date` mocking                   | Partial                           | Full — `Date.now()`, `new Date()`, `performance.now()` |
| `process.nextTick` faking        | No                                | Optional (`advanceTimers: true`)         |
| `queueMicrotask` faking          | No                                | Yes                                      |
| Timer accuracy                   | Approximate                       | Precise, handles timer ordering correctly|
| `jest.setSystemTime()`           | Not available                     | Available                                |

At 5 YOE, the practical rule: use the default (modern) mode unless you're on an older codebase locked to Jest <27. The modern mode's `jest.setSystemTime()` is essential for testing `Date`-dependent code cleanly.

**Q4. Where in the test lifecycle should `jest.useFakeTimers()` and `jest.useRealTimers()` be called?**
A: The safest pattern is to call `jest.useFakeTimers()` in `beforeEach` and `jest.useRealTimers()` in `afterEach` — this ensures fake timers are scoped exactly to the duration of one test and never leak into adjacent tests:

```typescript
describe('RetryService', () => {
  beforeEach(() => {
    jest.useFakeTimers();
  });

  afterEach(() => {
    jest.useRealTimers();
  });

  it('retries after 5 seconds', () => {
    // fake timers active here
  });
});
```

Alternatively, configure `fakeTimers: { enableGlobally: true }` in `jest.config.ts` to enable fake timers for the entire suite without per-file boilerplate — and call `jest.useRealTimers()` only in the rare test that needs real timers. Never call `jest.useFakeTimers()` inside an `it` block without a corresponding `afterEach` restore — the fake timer state will leak into subsequent tests in the same file, causing cascading failures that are difficult to trace.

**Q5. What does `jest.advanceTimersByTime(ms)` do, and how does it differ from `jest.runAllTimers()` and `jest.runOnlyPendingTimers()`?**
A: All three advance the fake timer queue, but with different scope:

- **`jest.advanceTimersByTime(ms)`** — advances the fake clock by exactly `ms` milliseconds, firing all callbacks whose delay falls within that window, in order. Does not fire callbacks scheduled beyond the window. Precise and predictable — the right choice for most timer tests.
- **`jest.runAllTimers()`** — fires every pending timer callback, including timers created by those callbacks (recursive timers), until no timers remain. Dangerous with `setInterval` — an infinite loop that never terminates. Use only when you know the timer tree is finite.
- **`jest.runOnlyPendingTimers()`** — fires only timers that are currently queued at the moment of the call — does not fire timers created as a side effect of firing those callbacks. Safe for one iteration of a `setInterval` or one step of a recursive retry sequence. Use this to advance one tick at a time through a complex timer sequence.

| Method                        | Fires callbacks beyond window? | Safe with infinite `setInterval`? | Controls exact time? |
|-------------------------------|-------------------------------|-----------------------------------|----------------------|
| `advanceTimersByTime(ms)`     | No                            | Yes (stops at ms boundary)        | Yes                  |
| `runAllTimers()`              | Yes (all of them)             | No — infinite loop                | No                   |
| `runOnlyPendingTimers()`      | No (only current queue)       | Yes (one tick)                    | No                   |

## Section 2: `jest.advanceTimersByTime()` in Practice

**Q6. How do you test a simple `setTimeout`-based retry with `advanceTimersByTime()`?**
A: The pattern is: trigger the async operation, advance time to the retry threshold, then assert on the retry behaviour:

```typescript
// Production code
export class ApiClient {
  async fetchWithRetry(url: string, retryDelayMs = 5000): Promise<Response> {
    try {
      return await fetch(url);
    } catch {
      await new Promise(resolve => setTimeout(resolve, retryDelayMs));
      return fetch(url); // one retry
    }
  }
}

// Test
it('retries the request after 5 seconds on failure', async () => {
  const fetchMock = jest
    .fn()
    .mockRejectedValueOnce(new Error('network error'))
    .mockResolvedValueOnce({ status: 200 } as Response);

  global.fetch = fetchMock;

  const promise = client.fetchWithRetry('/api/loans');

  // At this point the first fetch has failed and a 5s setTimeout is pending.
  // Advance the clock — fires the setTimeout callback, resolving the inner Promise.
  jest.advanceTimersByTime(5000);

  const result = await promise;

  expect(fetchMock).toHaveBeenCalledTimes(2);
  expect(result.status).toBe(200);
});
```

The key pattern: start the async operation (get a promise), advance the clock, then `await` the promise. If you `await` first, execution blocks waiting for the timer that never fires because you haven't advanced the clock yet — a deadlock.

**Q7. Why does the order of `jest.advanceTimersByTime()` and `await` matter, and what deadlock does getting it wrong produce?**
A: When production code `await`s a `setTimeout`-based delay, it suspends execution at that point. The promise that wraps the `setTimeout` will not resolve until the timer fires. The timer will not fire until `jest.advanceTimersByTime()` is called. If you `await` the outer promise first, you never reach the `advanceTimersByTime()` call — the test hangs indefinitely. The correct order:

```typescript
// CORRECT — start, advance, then await
const promise = service.doWithDelay(); // starts, hits setTimeout, suspends
jest.advanceTimersByTime(3000);        // fires the timer, unblocks the await inside
const result = await promise;          // now resolves
expect(result).toBeDefined();

// DEADLOCK — await blocks before clock is advanced
const result = await service.doWithDelay(); // blocks here forever
jest.advanceTimersByTime(3000);             // never reached
```

The mental model: think of `advanceTimersByTime` as "pumping" the fake clock to unblock any awaiting code. Start the operation, pump the clock, collect the result.

**Q8. How do you test a multi-stage retry with exponential backoff using `advanceTimersByTime()`?**
A: Advance the clock in increments matching each backoff stage:

```typescript
// Production code — exponential backoff: 1s, 2s, 4s
export async function fetchWithBackoff(url: string): Promise<Response> {
  for (let attempt = 0; attempt < 3; attempt++) {
    try {
      return await fetch(url);
    } catch {
      if (attempt === 2) throw new Error('All retries exhausted');
      const delay = 1000 * Math.pow(2, attempt); // 1000, 2000
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
  throw new Error('unreachable');
}

// Test
it('retries with exponential backoff and succeeds on the third attempt', async () => {
  const fetchMock = jest
    .fn()
    .mockRejectedValueOnce(new Error('fail'))  // attempt 1
    .mockRejectedValueOnce(new Error('fail'))  // attempt 2
    .mockResolvedValueOnce({ status: 200 } as Response); // attempt 3

  global.fetch = fetchMock;
  const promise = fetchWithBackoff('/api');

  // After attempt 1 fails, a 1000ms timer is pending
  jest.advanceTimersByTime(1000);
  await Promise.resolve(); // flush microtask queue so attempt 2 starts

  // After attempt 2 fails, a 2000ms timer is pending
  jest.advanceTimersByTime(2000);
  await Promise.resolve(); // flush so attempt 3 starts

  const result = await promise;
  expect(fetchMock).toHaveBeenCalledTimes(3);
  expect(result.status).toBe(200);
});
```

The `await Promise.resolve()` calls between timer advances are critical — they flush the microtask queue so that the next `async`/`await` continuation in the production code runs before you advance the clock again. Without them, the clock advances before the next retry attempt is even scheduled.

**Q9. How do you test `setInterval`-based polling with fake timers?**
A: Use `jest.advanceTimersByTime()` to trigger as many interval ticks as needed, or use `jest.runOnlyPendingTimers()` to tick one interval at a time:

```typescript
// Production code — polls every 2 seconds, stops after finding a result
export class LoanStatusPoller {
  private intervalId?: NodeJS.Timer;

  poll(loanId: string, onResolved: (status: string) => void): void {
    this.intervalId = setInterval(async () => {
      const status = await loanRepo.getStatus(loanId);
      if (status === 'DISBURSED' || status === 'REJECTED') {
        clearInterval(this.intervalId);
        onResolved(status);
      }
    }, 2000);
  }
}

// Test
it('polls until loan is disbursed and calls the callback', async () => {
  const getStatusMock = jest
    .fn()
    .mockResolvedValueOnce('PENDING')   // tick 1
    .mockResolvedValueOnce('PENDING')   // tick 2
    .mockResolvedValueOnce('DISBURSED') // tick 3 — stops polling

  jest.spyOn(loanRepo, 'getStatus').mockImplementation(getStatusMock);
  const onResolved = jest.fn();

  poller.poll('loan-123', onResolved);

  // Tick 1: advance 2s, flush async continuation
  jest.advanceTimersByTime(2000);
  await Promise.resolve();

  // Tick 2
  jest.advanceTimersByTime(2000);
  await Promise.resolve();

  // Tick 3 — status is DISBURSED, interval cleared, callback fires
  jest.advanceTimersByTime(2000);
  await Promise.resolve();

  expect(onResolved).toHaveBeenCalledWith('DISBURSED');
  expect(getStatusMock).toHaveBeenCalledTimes(3);
});
```

**Q10. What is `jest.advanceTimersByTimeAsync(ms)` and when do you need it over `advanceTimersByTime(ms)`?**
A: `jest.advanceTimersByTimeAsync(ms)` (Jest 29.5+) is the async variant — it advances the clock and also awaits any promises that are resolved as a result of the timer callbacks firing. This removes the need for manual `await Promise.resolve()` flushes between timer advances. The difference:

```typescript
// Without async variant — must manually flush microtasks
jest.advanceTimersByTime(2000);
await Promise.resolve(); // flush
jest.advanceTimersByTime(2000);
await Promise.resolve(); // flush

// With async variant — flushes automatically
await jest.advanceTimersByTimeAsync(2000);
await jest.advanceTimersByTimeAsync(2000);
```

Use `advanceTimersByTimeAsync` whenever timer callbacks contain `async`/`await` or return promises — which is almost always the case in a Node.js/NestJS backend. The non-async version requires manual microtask flushing which is error-prone and produces subtle test failures when missed. If your Jest version supports it, prefer the async variant by default.

## Section 3: `jest.setSystemTime()` and Date Mocking

**Q11. What is `jest.setSystemTime()`, and how does it differ from advancing timers?**
A: `jest.setSystemTime(date)` sets the fake clock to a specific point in time — it controls what `Date.now()` and `new Date()` return without affecting pending timers. `jest.advanceTimersByTime(ms)` moves the clock *forward by a relative amount* and fires any pending timer callbacks that fall within that window. They serve different purposes:
- **`setSystemTime`** — for testing date-dependent logic: "what does this code do when today is 2025-04-01?" Sets an absolute anchor.
- **`advanceTimersByTime`** — for testing timer-dependent logic: "what happens after 5 seconds?" Moves time forward relative to now.

They compose: you can `setSystemTime` to fix the starting date and then `advanceTimersByTime` to simulate elapsed time from that anchor:

```typescript
beforeEach(() => {
  jest.useFakeTimers();
  jest.setSystemTime(new Date('2025-04-01T00:00:00Z')); // fix start date
});

it('marks EMI as overdue after 3 days', () => {
  const emi = new Emi({ dueDate: new Date('2025-04-01') });
  jest.advanceTimersByTime(3 * 24 * 60 * 60 * 1000); // advance 3 days
  expect(emi.isOverdue()).toBe(true);
});
```

**Q12. How do you test code that uses `Date.now()` for token expiry validation with fake timers?**
A: Fix the system time at a known anchor, then advance to cross the expiry threshold:

```typescript
// Production code
export class JwtService {
  isExpired(token: DecodedToken): boolean {
    return Date.now() > token.exp * 1000; // exp is Unix seconds
  }
}

// Test
describe('JwtService.isExpired()', () => {
  beforeEach(() => {
    jest.useFakeTimers();
    jest.setSystemTime(new Date('2025-06-01T12:00:00Z'));
  });

  afterEach(() => {
    jest.useRealTimers();
  });

  it('returns false when token has not yet expired', () => {
    const token = { exp: new Date('2025-06-01T13:00:00Z').getTime() / 1000 }; // expires in 1hr
    expect(service.isExpired(token)).toBe(false);
  });

  it('returns true after the token expiry time is passed', () => {
    const token = { exp: new Date('2025-06-01T13:00:00Z').getTime() / 1000 };
    jest.advanceTimersByTime(60 * 60 * 1000 + 1); // advance 1hr + 1ms past expiry
    expect(service.isExpired(token)).toBe(true);
  });
});
```

Without fake timers, this test would depend on real wall-clock time — it would pass at 11:59 AM and fail at 1:01 PM. With `setSystemTime`, the test is hermetic and repeatable regardless of when it runs.

**Q13. How do you test a rate limiter that uses a sliding window based on `Date.now()`?**
A: Fix the start time, submit requests, advance time to cross the window boundary, and verify the counter resets:

```typescript
// Production code — 5 requests per 60 seconds per user
export class RateLimiter {
  private windows = new Map<string, number[]>();

  isAllowed(userId: string): boolean {
    const now = Date.now();
    const windowStart = now - 60_000;
    const timestamps = (this.windows.get(userId) ?? []).filter(t => t > windowStart);
    if (timestamps.length >= 5) return false;
    timestamps.push(now);
    this.windows.set(userId, timestamps);
    return true;
  }
}

// Test
it('allows requests again after the window expires', () => {
  jest.setSystemTime(new Date('2025-01-01T00:00:00Z'));

  // Exhaust the limit
  for (let i = 0; i < 5; i++) limiter.isAllowed('user-1');
  expect(limiter.isAllowed('user-1')).toBe(false);

  // Advance past the 60s window
  jest.advanceTimersByTime(61_000);
  expect(limiter.isAllowed('user-1')).toBe(true); // window reset
});
```

This test would be impossible without fake timers — you cannot wait 60 seconds in a unit test suite.

## Section 4: Async Code and Microtask Flushing

**Q14. What is the microtask queue, and why does it matter when using `advanceTimersByTime()` with async code?**
A: The JavaScript event loop processes tasks (macrotasks — `setTimeout`, `setInterval` callbacks) and microtasks (promise continuations — `.then()`, `async`/`await` continuations) in a specific order: after each macrotask completes, the entire microtask queue is drained before the next macrotask runs. When `jest.advanceTimersByTime()` fires a timer callback, it fires the macrotask. But if that callback creates a promise (e.g., calls an async function), the promise continuation is a microtask that queues up — it will not run until the current synchronous execution yields. This means: after `advanceTimersByTime()`, you must yield execution to let microtasks drain before the next assertion or the next `advanceTimersByTime()` call:

```typescript
jest.advanceTimersByTime(1000);
// Timer callback fired — but async code inside it hasn't continued yet
await Promise.resolve(); // yield — microtask queue drains, async continuation runs
// Now the code that runs after the await inside the timer callback has executed
```

Without this yield, assertions run before the async continuation completes, producing false failures.

**Q15. What does `jest.runAllTicks()` do, and how is it different from `await Promise.resolve()`?**
A: `jest.runAllTicks()` drains the `process.nextTick` queue — callbacks registered with `process.nextTick` are flushed synchronously. It does *not* drain promise microtasks (`.then()` chains, `async`/`await` continuations). `await Promise.resolve()` yields to the microtask queue, allowing promise continuations to run, but does not explicitly flush `nextTick` callbacks. In practice:
- Use `await Promise.resolve()` (or `await jest.advanceTimersByTimeAsync()`) to flush promise continuations after advancing timers.
- Use `jest.runAllTicks()` only if the production code explicitly uses `process.nextTick` — uncommon in application-level NestJS code but relevant in lower-level infrastructure code (streams, custom schedulers).

In most NestJS service tests, `await Promise.resolve()` or the async timer advance variants are sufficient.

## Section 5: Real-World Patterns in a NestJS/Fintech Context

**Q16. How do you test a NestJS scheduled job (`@Cron`) with fake timers?**
A: NestJS `@nestjs/schedule` uses `node-cron` under the hood, which uses real `setTimeout`/`setInterval`. The cleanest testing approach is to bypass the cron scheduling entirely in tests — extract the job logic into a plain method and test that directly with fake timers if it contains timer-dependent code:

```typescript
// Production code
@Injectable()
export class EmiSchedulerService {
  constructor(private readonly emiService: EmiService) {}

  @Cron('0 9 * * *') // 9 AM daily
  async handleCron() {
    await this.runDailyEmiJob(); // logic extracted
  }

  async runDailyEmiJob() {
    const today = new Date();
    const dueEmis = await this.emiService.getDueEmis(today);
    await Promise.all(dueEmis.map(emi => this.emiService.initDebit(emi)));
  }
}

// Test — call runDailyEmiJob() directly, use setSystemTime for the date
it('processes EMIs due on the current date', async () => {
  jest.setSystemTime(new Date('2025-06-15T09:00:00Z'));
  jest.spyOn(emiService, 'getDueEmis').mockResolvedValue([mockEmi]);
  jest.spyOn(emiService, 'initDebit').mockResolvedValue(undefined);

  await scheduler.runDailyEmiJob();

  expect(emiService.getDueEmis).toHaveBeenCalledWith(new Date('2025-06-15T09:00:00Z'));
  expect(emiService.initDebit).toHaveBeenCalledWith(mockEmi);
});
```

This approach tests the job logic (which is what matters) without fighting the cron scheduler's internal timer machinery.

**Q17. How do you test an OTP service that generates a token with a 10-minute expiry?**
A: Fix the system time at generation, then advance past the expiry window to test the validation path:

```typescript
// Production code
export class OtpService {
  generate(userId: string): StoredOtp {
    return {
      code: Math.floor(100000 + Math.random() * 900000).toString(),
      userId,
      expiresAt: new Date(Date.now() + 10 * 60 * 1000), // 10 minutes from now
    };
  }

  validate(storedOtp: StoredOtp, submittedCode: string): boolean {
    if (Date.now() > storedOtp.expiresAt.getTime()) return false;
    return storedOtp.code === submittedCode;
  }
}

// Tests
describe('OtpService', () => {
  beforeEach(() => {
    jest.useFakeTimers();
    jest.setSystemTime(new Date('2025-06-01T10:00:00Z'));
  });

  afterEach(() => jest.useRealTimers());

  it('validates a correct OTP within the expiry window', () => {
    const otp = service.generate('user-1');
    expect(service.validate(otp, otp.code)).toBe(true);
  });

  it('rejects a valid OTP submitted after expiry', () => {
    const otp = service.generate('user-1');
    jest.advanceTimersByTime(10 * 60 * 1000 + 1); // 10min + 1ms
    expect(service.validate(otp, otp.code)).toBe(false);
  });

  it('rejects an incorrect code regardless of timing', () => {
    const otp = service.generate('user-1');
    expect(service.validate(otp, '000000')).toBe(false);
  });
});
```

**Q18. How do you test a debounce utility with `advanceTimersByTime()`?**
A: Debounce delays execution until a quiet period has elapsed — multiple rapid calls should only trigger the callback once after the wait:

```typescript
// Production code
export function debounce<T extends (...args: any[]) => void>(fn: T, waitMs: number): T {
  let timer: NodeJS.Timeout;
  return ((...args: any[]) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), waitMs);
  }) as T;
}

// Tests
describe('debounce()', () => {
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  it('fires the callback once after the wait period', () => {
    const callback = jest.fn();
    const debounced = debounce(callback, 300);

    debounced('a');
    debounced('b');
    debounced('c'); // only this call should fire

    expect(callback).not.toHaveBeenCalled(); // not yet — still within wait period

    jest.advanceTimersByTime(300);
    expect(callback).toHaveBeenCalledTimes(1);
    expect(callback).toHaveBeenCalledWith('c');
  });

  it('fires again if called after the debounce window', () => {
    const callback = jest.fn();
    const debounced = debounce(callback, 300);

    debounced('first');
    jest.advanceTimersByTime(300);
    expect(callback).toHaveBeenCalledTimes(1);

    debounced('second');
    jest.advanceTimersByTime(300);
    expect(callback).toHaveBeenCalledTimes(2);
  });
});
```

## Section 6: Pitfalls and Anti-patterns

**Q19. What is the "fake timer leak" problem, and how does it corrupt subsequent tests?**
A: If `jest.useFakeTimers()` is called without a corresponding `jest.useRealTimers()` in `afterEach`, the fake timer state persists into every subsequent test in the same file. Tests that don't expect fake timers will have their `setTimeout` and `Date` calls silently replaced — `Date.now()` returns a frozen value, `setTimeout` callbacks never fire without explicit advancement, and async code that depends on real timers hangs indefinitely. The failure mode is particularly insidious: the affected tests appear to hang or produce wrong values with no obvious connection to the original fake timer call. Fix: always pair `jest.useFakeTimers()` with `jest.useRealTimers()` in `afterEach`, or configure `restoreAllMocks: true` globally (which does not restore timers — timers require explicit `useRealTimers()`). Note: `jest.clearAllMocks()` and `jest.restoreAllMocks()` do **not** restore real timers — only `jest.useRealTimers()` does.

**Q20. Why does `jest.runAllTimers()` infinite-loop on code with `setInterval`, and how do you avoid it?**
A: `jest.runAllTimers()` is designed to run all pending timers, including timers that are created by running other timers. A `setInterval` callback reschedules itself every tick by definition — each tick creates a new timer, which `runAllTimers()` then runs, creating another timer, and so on without end. The result is an infinite loop that hangs the test process. The fix: use `jest.advanceTimersByTime(N)` to run exactly as many ticks as the test needs, or use `jest.runOnlyPendingTimers()` to fire one tick at a time with explicit control over how many ticks run:

```typescript
// Safe — runs exactly 3 interval ticks (600ms at 200ms interval)
jest.advanceTimersByTime(600);

// Also safe — fires the currently queued tick only
jest.runOnlyPendingTimers(); // tick 1
jest.runOnlyPendingTimers(); // tick 2
jest.runOnlyPendingTimers(); // tick 3

// DANGEROUS with setInterval — infinite loop
jest.runAllTimers(); // hangs forever
```

**Q21. What happens when you use fake timers with a library that has its own internal timer management (e.g., `axios-retry`, `bull`, `ioredis`)?**
A: Libraries that schedule their own timeouts internally (retry libraries, queue processors, connection keep-alives) will have their timers replaced by Jest fakes as well — since `jest.useFakeTimers()` replaces the global `setTimeout`. This means their timers won't fire automatically during tests unless you advance the clock. In some cases this is useful (you can test retry behaviour directly). In others, it causes the library to appear broken (a Redis connection keep-alive timer never fires, the client disconnects). The safe approach: for libraries you don't need to test timers against, mock the entire library module (`jest.mock('ioredis')`) so it has no real timer machinery at all. Only enable fake timers for tests that specifically exercise your own timer-dependent code.

**Q22. Why does `jest.advanceTimersByTime()` not work as expected when the production code uses `async/await` inside a timer callback, and what is the fix?**
A: When a timer callback contains `async/await`, firing the callback via `advanceTimersByTime` starts the async function but does not complete it — it suspends at the first `await` and queues a microtask continuation. `advanceTimersByTime` is synchronous — it fires the callback and returns without waiting for any async work to complete. So assertions made immediately after `advanceTimersByTime()` run before the async continuation inside the timer callback has finished. Three fixes:

```typescript
// Fix 1: await Promise.resolve() to flush the microtask queue manually
jest.advanceTimersByTime(1000);
await Promise.resolve();
expect(result).toBeDefined();

// Fix 2: use jest.advanceTimersByTimeAsync() (Jest 29.5+) — flushes automatically
await jest.advanceTimersByTimeAsync(1000);
expect(result).toBeDefined();

// Fix 3: use multiple Promise.resolve() flushes for deeply nested async chains
jest.advanceTimersByTime(1000);
await Promise.resolve(); // first await in callback
await Promise.resolve(); // second await (if callback has two await points)
expect(result).toBeDefined();
```

## Section 7: Scenario / System Design Style Questions

**Q23. "You're testing a loan disbursement service that retries failed NACH debit attempts three times with delays of 1 minute, 5 minutes, and 15 minutes. The test currently sleeps for real time. How do you rewrite it?"**
A: The real-sleep test is a FIRST violation — it takes 21 minutes. Rewrite using fake timers and the start-advance-await pattern:

```typescript
describe('NachDebitService.attemptDebitWithRetry()', () => {
  const RETRY_DELAYS = [60_000, 300_000, 900_000]; // 1min, 5min, 15min

  beforeEach(() => {
    jest.useFakeTimers();
    jest.setSystemTime(new Date('2025-06-01T09:00:00Z'));
  });

  afterEach(() => jest.useRealTimers());

  it('succeeds on the first attempt with no retries', async () => {
    nachGateway.debit.mockResolvedValue({ status: 'SUCCESS' });
    const result = await service.attemptDebitWithRetry(emiId);
    expect(result.status).toBe('SUCCESS');
    expect(nachGateway.debit).toHaveBeenCalledTimes(1);
  });

  it('retries after 1min and 5min delays and succeeds on the third attempt', async () => {
    nachGateway.debit
      .mockRejectedValueOnce(new Error('NACH_TIMEOUT'))
      .mockRejectedValueOnce(new Error('NACH_TIMEOUT'))
      .mockResolvedValueOnce({ status: 'SUCCESS' });

    const promise = service.attemptDebitWithRetry(emiId);

    // Advance through retry 1 (1 minute delay)
    await jest.advanceTimersByTimeAsync(RETRY_DELAYS[0]);
    // Advance through retry 2 (5 minute delay)
    await jest.advanceTimersByTimeAsync(RETRY_DELAYS[1]);

    const result = await promise;
    expect(result.status).toBe('SUCCESS');
    expect(nachGateway.debit).toHaveBeenCalledTimes(3);
  });

  it('throws after all retries are exhausted', async () => {
    nachGateway.debit.mockRejectedValue(new Error('NACH_TIMEOUT'));

    const promise = service.attemptDebitWithRetry(emiId);

    await jest.advanceTimersByTimeAsync(RETRY_DELAYS[0]);
    await jest.advanceTimersByTimeAsync(RETRY_DELAYS[1]);
    await jest.advanceTimersByTimeAsync(RETRY_DELAYS[2]);

    await expect(promise).rejects.toThrow('All NACH retry attempts exhausted');
    expect(nachGateway.debit).toHaveBeenCalledTimes(3);
  });
});
```

Total test runtime: milliseconds. The 21-minute real-sleep version is eliminated entirely.

**Q24. "A developer on your team says 'fake timers don't work with our Redis-based session TTL logic because Redis uses real time.' How do you fix the architecture to make it testable?"**
A: The developer is right that Redis's internal TTL countdown uses real wall-clock time — `jest.useFakeTimers()` cannot intercept Redis's internal server-side timer. The fix is an architectural one: separate the responsibility of computing the TTL from the responsibility of setting it. The service should derive the TTL value from an injectable clock, making it deterministic in tests:

```typescript
// Anti-pattern — TTL computed directly from real Date inside the method
async setSession(userId: string, data: SessionData): Promise<void> {
  const ttlSeconds = Math.floor((expiresAt.getTime() - Date.now()) / 1000);
  await this.redis.set(`session:${userId}`, JSON.stringify(data), 'EX', ttlSeconds);
}

// Testable pattern — inject a clock
@Injectable()
export class SessionService {
  constructor(
    private readonly redis: Redis,
    private readonly clock: ClockService, // injectable
  ) {}

  async setSession(userId: string, data: SessionData, expiresAt: Date): Promise<void> {
    const ttlSeconds = Math.floor((expiresAt.getTime() - this.clock.now()) / 1000);
    await this.redis.set(`session:${userId}`, JSON.stringify(data), 'EX', ttlSeconds);
  }
}

// Test
it('sets the correct TTL based on the expiry date', async () => {
  jest.setSystemTime(new Date('2025-06-01T10:00:00Z'));
  const expiresAt = new Date('2025-06-01T10:30:00Z'); // 30 minutes from now
  const redisSpy = jest.spyOn(redis, 'set').mockResolvedValue('OK');

  await sessionService.setSession('user-1', sessionData, expiresAt);

  expect(redisSpy).toHaveBeenCalledWith(
    'session:user-1',
    expect.any(String),
    'EX',
    1800, // 30 * 60 seconds
  );
});
```

The test asserts on the TTL value passed to Redis, not on Redis's internal expiry behaviour — which is the correct boundary. Real Redis TTL behaviour is tested in integration tests against a real Redis instance.

**Q25. "Your NestJS service has a `CircuitBreaker` that opens after 5 consecutive failures and resets after a 30-second cooldown. Design the complete test suite for the state transitions using fake timers."**
A:

```typescript
describe('CircuitBreaker', () => {
  let breaker: CircuitBreaker;

  beforeEach(() => {
    jest.useFakeTimers();
    jest.setSystemTime(new Date('2025-01-01T00:00:00Z'));
    breaker = new CircuitBreaker({ failureThreshold: 5, cooldownMs: 30_000 });
  });

  afterEach(() => jest.useRealTimers());

  describe('CLOSED state (normal operation)', () => {
    it('starts in CLOSED state', () => {
      expect(breaker.state).toBe('CLOSED');
    });

    it('remains CLOSED after fewer than 5 consecutive failures', () => {
      for (let i = 0; i < 4; i++) breaker.recordFailure();
      expect(breaker.state).toBe('CLOSED');
    });
  });

  describe('OPEN state (tripped)', () => {
    beforeEach(() => {
      for (let i = 0; i < 5; i++) breaker.recordFailure();
    });

    it('opens after 5 consecutive failures', () => {
      expect(breaker.state).toBe('OPEN');
    });

    it('rejects calls immediately while OPEN', () => {
      expect(() => breaker.call(() => 'ok')).toThrow('Circuit is OPEN');
    });

    it('remains OPEN within the 30s cooldown window', () => {
      jest.advanceTimersByTime(29_999);
      expect(breaker.state).toBe('OPEN');
    });
  });

  describe('HALF_OPEN state (probing)', () => {
    beforeEach(() => {
      for (let i = 0; i < 5; i++) breaker.recordFailure();
      jest.advanceTimersByTime(30_000); // cooldown elapsed
    });

    it('transitions to HALF_OPEN after cooldown', () => {
      expect(breaker.state).toBe('HALF_OPEN');
    });

    it('transitions back to CLOSED on a successful probe call', () => {
      breaker.recordSuccess();
      expect(breaker.state).toBe('CLOSED');
    });

    it('re-opens and resets cooldown on a failed probe call', () => {
      breaker.recordFailure();
      expect(breaker.state).toBe('OPEN');

      // Cooldown must elapse again before HALF_OPEN
      jest.advanceTimersByTime(29_999);
      expect(breaker.state).toBe('OPEN');

      jest.advanceTimersByTime(1);
      expect(breaker.state).toBe('HALF_OPEN');
    });
  });

  describe('failure counter reset', () => {
    it('resets consecutive failure count after a success in CLOSED state', () => {
      for (let i = 0; i < 4; i++) breaker.recordFailure();
      breaker.recordSuccess();
      for (let i = 0; i < 4; i++) breaker.recordFailure();
      expect(breaker.state).toBe('CLOSED'); // would be OPEN without reset
    });
  });
});
```

Each `describe` maps to a circuit breaker state. `setSystemTime` anchors the test at a known date. `advanceTimersByTime` drives state transitions through the cooldown boundary. The `29_999` vs `30_000` boundary tests confirm the exact millisecond threshold — a level of precision only possible with fake timers.

## Quick Reference: Fake Timer API

| API                                     | What it does                                                                     | When to use                                              |
|-----------------------------------------|---------------------------------------------------------------------------------|----------------------------------------------------------|
| `jest.useFakeTimers()`                  | Replaces `setTimeout`, `setInterval`, `Date`, etc. with controllable fakes       | `beforeEach` of any test with timer-dependent code       |
| `jest.useRealTimers()`                  | Restores all real timer implementations                                          | `afterEach` — always paired with `useFakeTimers()`       |
| `jest.setSystemTime(date)`              | Sets the fake clock to a specific Date/timestamp                                 | When code uses `Date.now()` or `new Date()`              |
| `jest.advanceTimersByTime(ms)`          | Advances clock by ms, fires callbacks in that window synchronously               | Precise timer advancement; safe with `setInterval`       |
| `jest.advanceTimersByTimeAsync(ms)`     | Same, but also flushes promise microtasks                                        | Whenever timer callbacks contain `async/await`           |
| `jest.runAllTimers()`                   | Fires all pending timers recursively until none remain                           | Only for finite, non-recursive timer trees               |
| `jest.runOnlyPendingTimers()`           | Fires only currently queued timers (not newly created ones)                      | One tick of `setInterval`; step-through retry sequences  |
| `jest.runAllTicks()`                    | Flushes `process.nextTick` queue                                                 | Code that uses `process.nextTick` directly               |
| `jest.clearAllTimers()`                 | Cancels all pending timers without firing them                                   | Cleanup when you want to discard scheduled work          |
| `jest.getTimerCount()`                  | Returns the number of pending fake timers                                        | Asserting that all timers were fired or cancelled        |
| `jest.now()`                            | Returns the current fake clock value (equivalent to `Date.now()` with fakes)     | Assertions on the current fake time within a test        |

---

**Tip for the interview:** At 5 YOE, fake timer questions don't come as "what does `useFakeTimers` do?" — they come as debugging scenarios: "why does this async retry test hang," "why is this timer test flaky," "how do you test a 15-minute cooldown without waiting 15 minutes?" The answer is always the same three-part structure: fix the system time with `setSystemTime` if the code reads `Date`, use `advanceTimersByTime` (async variant if the callback is async) to drive time forward, and flush microtasks between advances. Have one concrete fintech story — OTP expiry, NACH retry delays, circuit breaker cooldown, rate limit window reset — and walk through the exact test structure. That's the answer that lands at this level.
