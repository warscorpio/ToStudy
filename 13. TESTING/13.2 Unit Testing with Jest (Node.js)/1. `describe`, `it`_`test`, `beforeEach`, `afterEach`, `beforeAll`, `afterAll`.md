# Jest Test Structure & Lifecycle Hooks: `describe`, `it`/`test`, `beforeEach`, `afterEach`, `beforeAll`, `afterAll` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the role of `describe` in a Jest test file, and what does it actually do at runtime?**
A: `describe` is a block that groups related tests under a shared label. At runtime, Jest collects all `describe` callbacks during a synchronous discovery pass before executing any test — it builds a tree of suites and their contained tests first, then runs them. `describe` itself does not run the tests; it registers them. This has a subtle but important consequence: code written directly inside a `describe` callback (not inside a hook or test) runs during the collection phase, not during test execution — meaning it runs before any `beforeAll` or `beforeEach` hook fires. The practical rule: never put setup logic or side-effectful code directly in a `describe` body; always put it in a hook.

**Q2. What is the difference between `it` and `test`, and when would you prefer one over the other?**
A: `it` and `test` are identical — they are aliases for the same Jest function. The difference is purely stylistic and communicative:
- `test('returns 401 when token is missing', ...)` reads as a standalone statement.
- `it('should return 401 when token is missing', ...)` reads naturally inside a `describe` block as a sentence: "describe LoanController → it should return 401 when token is missing."

The convention at 5 YOE: use `describe` + `it` together for BDD-style grouping where the describe label is a noun (the subject) and the `it` label completes a sentence about its behaviour. Use bare `test` for standalone test files or utility tests where no describe nesting adds value. Whichever you choose, be consistent within a codebase — mixing both without a convention produces inconsistent test output.

**Q3. What are the four lifecycle hooks Jest provides, and what is their purpose?**
A: Jest provides four hooks for managing test state:
- **`beforeAll(fn)`** — runs once before the first test in the current `describe` scope. Use for expensive, immutable setup: starting a database container, creating an HTTP server, compiling a schema.
- **`afterAll(fn)`** — runs once after the last test in the current `describe` scope. Use for tearing down what `beforeAll` created: closing DB connections, stopping servers.
- **`beforeEach(fn)`** — runs before every individual test in the current scope. Use for resetting mutable state: re-instantiating the class under test, clearing mocks, seeding fresh DB rows.
- **`afterEach(fn)`** — runs after every individual test in the current scope. Use for cleanup that must happen regardless of pass/fail: rolling back a DB transaction, restoring spies, clearing event listeners.

The distinction that matters most: `beforeAll`/`afterAll` are for **shared, immutable infrastructure**; `beforeEach`/`afterEach` are for **per-test, mutable state**.

**Q4. In what order do Jest hooks and tests execute when `describe` blocks are nested?**
A: Jest executes hooks in a strict outside-in (for before hooks) and inside-out (for after hooks) order:

```
describe outer
  beforeAll outer
    describe inner
      beforeAll inner
        beforeEach outer
        beforeEach inner
          test
        afterEach inner
        afterEach outer
      afterAll inner
  afterAll outer
```

The before hooks cascade inward — the outermost `beforeAll` fires first, then the inner. The after hooks unwind outward — the innermost `afterEach` fires first, then the outer. This mirrors how a call stack unwinds and ensures that the most specific setup/teardown wraps the test closest. In practice, the most common gotcha: `afterEach` at the outer scope runs *after* `afterEach` at the inner scope — which means an outer cleanup can interfere with an inner cleanup if both touch the same resource.

**Q5. What happens during Jest's "collection phase," and why does it matter for how you write test files?**
A: Jest's collection phase is a synchronous pass through the entire test file where it evaluates all `describe` callbacks and registers all `it`/`test` callbacks — without executing any of them. During this phase:
- All code directly inside `describe` bodies runs immediately and synchronously.
- All `it`/`test` callbacks are registered but not called.
- All `beforeAll`, `afterAll`, `beforeEach`, `afterEach` callbacks are registered but not called.

This matters because any expensive or side-effectful code placed directly in a `describe` body (e.g., `const server = new Server()`) runs during collection, before any hook, and runs once globally — not per test. The collection phase is also why you cannot use `await` at the top level of a `describe` block — it's synchronous. All async work must be deferred into hooks.

## Section 2: `describe` — Structuring Suites

**Q6. How do you use `describe` nesting to express a test hierarchy for a NestJS service?**
A: A well-structured service test uses nested `describe` blocks to mirror the service's method surface, and nests further for different scenarios per method:

```typescript
describe('LoanService', () => {
  // shared setup for all LoanService tests

  describe('approveLoan()', () => {
    describe('when the applicant meets eligibility criteria', () => {
      it('should update loan status to APPROVED', async () => { ... });
      it('should publish a loan.approved event to Kafka', async () => { ... });
    });

    describe('when the credit score is below threshold', () => {
      it('should update loan status to REJECTED', async () => { ... });
      it('should not publish any event', async () => { ... });
    });
  });

  describe('disburseLoan()', () => {
    it('should transfer funds via the payment gateway', async () => { ... });
    it('should throw if loan is not in APPROVED state', async () => { ... });
  });
});
```

Each nesting level adds one dimension: the outer `describe` names the unit under test, the middle names the method, the inner names the scenario. Test output reads like a specification, and failures identify method and scenario immediately without reading the test body.

**Q7. What is `describe.only` (`fdescribe`) and `describe.skip` (`xdescribe`), and when are they appropriate?**
A:
- **`describe.only`** — runs only the `describe` blocks marked with `.only` in the file (or across files if combined with `--testPathPattern`). Use during active development to focus on one suite without commenting out others. **Never commit** `describe.only` — it silently skips all other tests and gives a false green CI.
- **`describe.skip`** — skips the entire block; its tests are reported as "skipped" (not passing). Appropriate for temporarily disabling a suite that's broken by a known external dependency (e.g., a third-party sandbox is down) while a fix is in progress. Still a code smell if left in for more than a day or two — prefer fixing the test or tracking the skip as a tech debt ticket.
- **`describe.each`** — runs the same `describe` block for multiple input sets. Useful for parameterised test suites (e.g., testing the same EMI calculation logic against different loan tenures and amounts) without duplicating structure.

**Q8. What is `test.each` / `it.each`, and how does it differ from multiple `it` blocks?**
A: `test.each` runs the same test function against multiple input-output pairs, reducing duplication for data-driven tests:

```typescript
describe('EmiCalculator.calculate()', () => {
  test.each([
    [100000, 12, 8.5, 8745],   // [principal, months, rate, expectedEmi]
    [500000, 24, 10.0, 23072],
    [1000000, 60, 9.0, 20758],
  ])('principal=%i months=%i rate=%f → EMI=%i', (principal, months, rate, expected) => {
    expect(EmiCalculator.calculate(principal, months, rate)).toBe(expected);
  });
});
```

Compared to multiple `it` blocks: `test.each` enforces the same test shape for all cases (no accidental variation), produces clear parameterised output in the test report, and makes adding new cases a one-line change. Use multiple `it` blocks when each scenario has meaningfully different setup, context, or assertions — not just different data values.

## Section 3: `beforeAll` and `afterAll`

**Q9. When is `beforeAll` the right choice over `beforeEach`, and what is the risk of choosing wrong?**
A: `beforeAll` is right when the setup is **expensive, slow, and produces immutable state** that no test will modify. Classic examples: starting a Docker database container, creating an HTTP server, compiling a TypeScript module, seeding a large read-only reference dataset. The risk of choosing `beforeAll` for mutable state: test A modifies the shared object (adds a property, changes a value, inserts a row), and test B reads the modified version — now test B's result depends on test A having run first. This is an independence violation that produces order-dependent failures, which are among the hardest bugs to diagnose in a test suite because they only surface when tests run in a specific order.

**Q10. How do you use `beforeAll` and `afterAll` to manage a real database connection in an integration test suite?**
A: A clean pattern for a NestJS integration test with TypeORM:

```typescript
describe('LoanRepository (integration)', () => {
  let dataSource: DataSource;
  let loanRepo: LoanRepository;

  beforeAll(async () => {
    dataSource = await createTestDataSource(); // connects to test DB, runs migrations
    loanRepo = new LoanRepository(dataSource);
  });

  afterAll(async () => {
    await dataSource.destroy(); // closes all connections — prevents open handle warnings
  });

  afterEach(async () => {
    // Per-test cleanup — rolls back data, not the connection
    await dataSource.query('TRUNCATE loan RESTART IDENTITY CASCADE');
  });

  it('should persist a new loan application', async () => {
    const loan = await loanRepo.save(buildLoanFixture());
    const found = await loanRepo.findById(loan.id);
    expect(found.status).toBe('PENDING');
  });
});
```

`beforeAll` owns the connection (expensive, shared). `afterAll` closes it. `afterEach` owns the data reset (cheap, per-test). This separation is the pattern — never put connection logic in `beforeEach` (too slow) or data reset in `afterAll` (too late — tests share dirty state).

**Q11. What causes "open handles" warnings in Jest, and how does `afterAll` fix them?**
A: Jest warns about open handles when something keeps the Node.js event loop alive after all tests complete — a DB connection pool, an HTTP server, a `setInterval`, a Kafka consumer still polling. These are resources created during the test suite that were never explicitly closed. `afterAll` is the correct place to close them:

```typescript
afterAll(async () => {
  await app.close();         // NestJS: closes HTTP server + runs onModuleDestroy hooks
  await dataSource.destroy(); // TypeORM: closes connection pool
  await kafkaConsumer.disconnect();
});
```

Without this, Jest exits with `--forceExit` (often added as a workaround that masks the real problem) or waits the full `--testTimeout` period. The underlying issue is always a resource that was opened and not closed — `afterAll` is not a workaround, it's the contract.

**Q12. Can `beforeAll` be async, and how does Jest handle a `beforeAll` that throws?**
A: Yes — `beforeAll` accepts an async function and Jest `await`s it before running any test. If `beforeAll` throws (or its promise rejects), Jest marks every test in that `describe` scope as **failed** with the setup error — the tests are not skipped, they are failed. This is intentional: if the shared infrastructure didn't set up correctly, the tests cannot be trusted to produce meaningful results, so they should fail loudly, not silently pass. The practical implication: a flaky DB connection in `beforeAll` can cause an entire suite of 30 tests to fail spuriously. If this is a concern, add retry logic inside `beforeAll` itself rather than relying on Jest's test retry mechanism.

## Section 4: `beforeEach` and `afterEach`

**Q13. What should `beforeEach` always do in a unit test suite, and what should it never do?**
A: **Always do:**
- Re-instantiate the class under test with fresh mocks so each test starts from a known clean state.
- Call `jest.clearAllMocks()` or `jest.resetAllMocks()` to clear call history and mock return values from the previous test.
- Reset any module-level mutable state the code under test might read.

**Never do:**
- Open a real database connection or make a real network call — this belongs in `beforeAll` (once) or should be mocked.
- Set up immutable shared infrastructure — this runs N times (once per test) for something that only needs to run once.
- Put assertions — `beforeEach` is setup; assertions belong in `it` blocks.

```typescript
describe('LoanEligibilityService', () => {
  let service: LoanEligibilityService;
  let bureauClient: jest.Mocked<BureauClient>;

  beforeEach(() => {
    bureauClient = { fetchScore: jest.fn() } as jest.Mocked<BureauClient>;
    service = new LoanEligibilityService(bureauClient);
    // each test gets a fresh service instance and a fresh mock
  });

  it('should approve when score >= 700', async () => {
    bureauClient.fetchScore.mockResolvedValue(750);
    const result = await service.check('PAN123');
    expect(result.eligible).toBe(true);
  });
});
```

**Q14. What is the difference between `jest.clearAllMocks()`, `jest.resetAllMocks()`, and `jest.restoreAllMocks()`, and which belongs in `beforeEach`?**
A:

| Method                      | Clears call history | Resets return values / implementations | Restores original implementation |
|-----------------------------|---------------------|----------------------------------------|----------------------------------|
| `jest.clearAllMocks()`      | Yes                 | No                                     | No                               |
| `jest.resetAllMocks()`      | Yes                 | Yes (back to `jest.fn()` with no impl) | No                               |
| `jest.restoreAllMocks()`    | Yes                 | Yes                                    | Yes (only for `jest.spyOn`)      |

- **`clearAllMocks`** — use when mock implementations are set up in `beforeEach` (so they'll be re-applied next run) and you only need to clear the call records between tests.
- **`resetAllMocks`** — use when some tests set their own mock implementations (`mockReturnValue` inside an `it`) and you want the next test to start with a no-op mock, not the previous test's implementation.
- **`restoreAllMocks`** — use in `afterEach` when you've used `jest.spyOn` on a real object and need to restore the original method. Without this, the spy persists into subsequent tests.

Best practice: configure `clearMocks: true` and `restoreMocks: true` in `jest.config.ts` so this happens automatically — no per-suite `beforeEach` boilerplate needed.

**Q15. How do `beforeEach` and `afterEach` interact when a test throws — does `afterEach` still run?**
A: Yes — `afterEach` always runs regardless of whether the test passed, failed, or threw. This is the critical guarantee that makes `afterEach` suitable for cleanup: you can depend on it to execute even when the test itself errors out. The same applies to `afterAll` — it runs even if some tests in the suite fail. This is intentional: cleanup must be unconditional, or a single failing test can leave the environment dirty for all subsequent tests. The implication for database tests: put your transaction rollback or `TRUNCATE` in `afterEach`, not at the end of each `it` block — if the test fails mid-way, the code at the end of `it` won't run, but `afterEach` will.

**Q16. How do nested `beforeEach` hooks compose, and how can they create subtle coupling?**
A: Outer `beforeEach` hooks run before inner `beforeEach` hooks. This means the outer hook's setup is available to the inner hook, and the inner hook can build on it:

```typescript
describe('LoanController', () => {
  let app: INestApplication;

  beforeEach(async () => {
    app = await createTestApp(); // outer: shared app setup
  });

  afterEach(async () => {
    await app.close();
  });

  describe('POST /loans', () => {
    let authToken: string;

    beforeEach(async () => {
      authToken = await getTestAuthToken(app); // inner: builds on outer's app
    });

    it('should create a loan', async () => {
      const res = await request(app.getHttpServer())
        .post('/loans')
        .set('Authorization', `Bearer ${authToken}`)
        .send(loanPayload);
      expect(res.status).toBe(201);
    });
  });
});
```

The subtle coupling risk: if the outer `beforeEach` creates state that the inner `beforeEach` implicitly depends on but doesn't declare explicitly, moving the inner `describe` to another file breaks it silently. Rule: inner hooks should be self-sufficient or explicitly document their dependency on the outer scope.

## Section 5: Scope, Closure, and Variable Sharing

**Q17. What is the correct pattern for sharing variables between hooks and tests, and what anti-patterns should you avoid?**
A: The correct pattern is to declare variables with `let` in the `describe` scope and assign them inside hooks:

```typescript
describe('DisburseService', () => {
  let service: DisburseService;
  let mockGateway: jest.Mocked<PaymentGateway>;

  beforeEach(() => {
    mockGateway = createMockGateway();
    service = new DisburseService(mockGateway);
  });

  it('calls the gateway with the correct amount', async () => {
    await service.disburse(loanId, 50000);
    expect(mockGateway.transfer).toHaveBeenCalledWith(50000, expect.any(String));
  });
});
```

Anti-patterns to avoid:
- **`const` in `describe` body** — `const service = new DisburseService()` runs once at collection time, is never re-instantiated, and accumulates state across tests.
- **Assigning in `beforeAll` when the value is mutable** — the single instance is shared and mutated by every test.
- **Closing over variables from an outer scope and mutating them inside `it`** — test A sets `sharedResult = 'approved'`, test B reads it — this is an implicit dependency between tests.

**Q18. How does TypeScript interact with Jest's hook-based variable sharing pattern?**
A: TypeScript infers `let service: DisburseService | undefined` if you don't provide a type annotation — because at the declaration site it has no value. The fix is to use the non-null assertion operator or a definite assignment assertion:

```typescript
// Option 1: type annotation with definite assignment
let service!: DisburseService; // tells TS "trust me, it'll be set before use"

// Option 2: type assertion in the hook
let service: DisburseService;
beforeEach(() => {
  service = new DisburseService(mockGateway); // TS sees this as definite assignment
});
```

`let service!: DisburseService` is the idiomatic NestJS/Jest pattern — it removes the `undefined` from the union type and avoids non-null assertions (`service!.method()`) at every call site inside the tests. Use it only where you know `beforeEach` genuinely guarantees the assignment.

## Section 6: Async Hooks

**Q19. How do you handle async setup in `beforeEach` when one async operation depends on the result of another?**
A: Chain them sequentially with `await` inside the async hook:

```typescript
beforeEach(async () => {
  // Step 1: create user first
  const user = await userRepo.save(buildUserFixture({ kycStatus: 'VERIFIED' }));

  // Step 2: create loan linked to that user
  loan = await loanRepo.save(buildLoanFixture({ userId: user.id }));

  // Step 3: create the service with fresh mocks after DB state is ready
  service = new LoanService(loanRepo, mockEventBus);
});
```

The hook is awaited in full before the first test runs. If any `await` inside the hook rejects, the hook is considered failed and all tests in the scope are marked failed. Do not use `Promise.all` for operations that have ordering dependencies — use `Promise.all` only when operations are truly independent and their results are needed simultaneously.

**Q20. What happens if you forget `async`/`await` in a `beforeEach` that performs async operations?**
A: If you omit `async` or forget to `await` a promise inside the hook, the hook function returns before the async operation completes. Jest sees the hook as done (it returned synchronously or returned a resolved promise immediately) and starts running the test. The async operation continues in the background — your DB insert, server startup, or mock setup hasn't finished yet. The result: tests run against incomplete state, producing false failures that are extremely hard to diagnose because the test code looks correct. The tell: intermittent failures that correlate with machine speed (faster machines finish the async op before the test gets to it by coincidence; slower ones don't). Fix: always `async`/`await` in hooks, or return the promise explicitly: `beforeEach(() => return asyncSetup())`.

## Section 7: Pitfalls and Anti-patterns

**Q21. What is the "setup in `describe` body" anti-pattern, and what does it produce?**
A: Placing setup logic directly in a `describe` body rather than in a hook:

```typescript
// Anti-pattern
describe('PaymentService', () => {
  const gateway = new RealPaymentGateway(); // runs at collection time, before any hook
  const service = new PaymentService(gateway); // same — runs once, never reset

  it('should process a payment', async () => {
    // service is the same instance across every test in this file
    // state accumulated by previous tests is visible here
  });
});
```

What this produces: a single shared instance across all tests (independence violation), any state the service accumulates (call counts, internal caches, error flags) bleeds across tests, and the gateway is instantiated even if the test is skipped or filtered out. Fix: always move instantiation into `beforeEach`.

**Q22. Why is `afterAll` the wrong place to reset per-test data, and what does it allow to happen?**
A: `afterAll` runs once after the last test in the scope — so if test 1 inserts rows and `afterAll` truncates the table, tests 2 through N all run against data left by test 1 (and 2, and 3...). By the time `afterAll` cleans up, all the damage to test independence is already done. `afterAll` is only appropriate for tearing down infrastructure (close the connection), not for resetting data state. Per-test data reset belongs in `afterEach`. The failure mode of getting this wrong: tests pass individually, fail in sequence, produce different results depending on which test ran first — classic order-dependent test failures.

**Q23. What does `jest.isolateModules` do, and when would you use it in the context of `beforeEach`?**
A: `jest.isolateModules` creates a fresh module registry for the code inside its callback, forcing `require`/`import` to re-evaluate the module from scratch rather than returning the cached version. This is needed when you want to test a module that has side effects at import time (e.g., reads an environment variable and computes a constant, registers a singleton, sets up a connection on load):

```typescript
describe('config module', () => {
  let config: typeof import('../config');

  beforeEach(() => {
    jest.isolateModules(() => {
      config = require('../config'); // fresh module, re-runs top-level code
    });
  });

  it('should use the TEST_DB_URL env var', () => {
    process.env.DB_URL = 'postgres://test';
    jest.isolateModules(() => {
      const freshConfig = require('../config');
      expect(freshConfig.dbUrl).toBe('postgres://test');
    });
  });
});
```

Use sparingly — it's expensive (module re-evaluation) and indicates the code under test has import-time side effects, which is itself a design smell. In NestJS, the DI system handles this more cleanly via module overrides in `Test.createTestingModule`.

## Section 8: Scenario / System Design Style Questions

**Q24. "You're reviewing a PR with 40 tests in a single `describe` block, all sharing one `beforeAll` that creates a user, an account, and three loans. Half the tests are failing intermittently. Walk me through diagnosing the problem."**
A: Shared mutable state in `beforeAll` with 40 tests is the textbook recipe for intermittent order-dependent failures. Diagnostic approach:

**Step 1 — Confirm order-dependency:**
Run `jest --randomize` to shuffle test execution order within the file. If different tests fail on each run, order-dependency is confirmed.

**Step 2 — Identify the shared state:**
Read the `beforeAll` carefully — what does it create, and is any of it mutable? Entities with IDs, arrays, objects, or DB rows that tests are expected to read in a specific state are all candidates. Trace which tests modify this shared state (update a loan status, delete a record, change an object property).

**Step 3 — Classify the fix:**
- For tests that only *read* the shared state → `beforeAll` is appropriate; these tests are probably fine.
- For tests that *mutate* the shared state → they need their own setup. Move setup to `beforeEach` for those tests, or split them into their own `describe` block with isolated setup.
- For DB-backed state → add `afterEach` with `TRUNCATE` or transaction rollback so each test starts with a clean slate.

**Step 4 — Restructure:**
```typescript
describe('LoanController', () => {
  let dataSource: DataSource;

  beforeAll(async () => {
    dataSource = await createTestDataSource(); // immutable — stays in beforeAll
  });

  afterAll(async () => {
    await dataSource.destroy();
  });

  afterEach(async () => {
    await dataSource.query('TRUNCATE loan, account, user RESTART IDENTITY CASCADE');
  });

  beforeEach(async () => {
    // seed fresh per test — move out of beforeAll
    await seedTestUser(dataSource);
  });

  it('...', async () => { ... });
});
```

**Q25. "A junior developer's integration test suite takes 4 minutes for 50 tests. You look at the code and see `beforeEach(() => app = await NestFactory.create(AppModule))`. What's wrong, and how do you fix it?"**
A: `NestFactory.create(AppModule)` bootstraps the entire application — it loads all modules, runs all `onModuleInit` lifecycle hooks, opens DB connections, and starts the HTTP listener. This takes 1–5 seconds per invocation. At 50 tests with `beforeEach`, that's 50–250 seconds of pure overhead — before a single line of business logic runs.

**What's wrong:** Application bootstrap is expensive and immutable (the app structure doesn't change between tests) — it belongs in `beforeAll`, not `beforeEach`.

**The fix:**
```typescript
describe('LoanController (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    })
      .overrideProvider(BureauClient)
      .useValue(mockBureauClient)
      .compile();

    app = moduleRef.createNestApplication();
    await app.init();
  });

  afterAll(async () => {
    await app.close(); // closes server + runs onModuleDestroy
  });

  afterEach(async () => {
    // only reset data — not the app
    await dataSource.query('TRUNCATE loan RESTART IDENTITY CASCADE');
    jest.clearAllMocks();
  });

  it('POST /loans returns 201', async () => {
    const res = await request(app.getHttpServer()).post('/loans').send(payload);
    expect(res.status).toBe(201);
  });
});
```

Result: one app bootstrap for the entire suite (~2–5s), plus cheap per-test data reset. 50 tests that took 4 minutes should drop to under 30 seconds.

**Q26. "Design the full test lifecycle structure for a NestJS `EmiSchedulerService` that runs a cron job, writes EMI records to PostgreSQL, and publishes a Kafka event per EMI due. What goes in each hook?"**
A: The lifecycle layers follow the "what's shared, what's mutable, what's per-test" model:

```typescript
describe('EmiSchedulerService (integration)', () => {
  // ── Shared infrastructure (beforeAll / afterAll) ──────────────────────────
  let dataSource: DataSource;
  let kafkaProducer: jest.Mocked<KafkaProducer>;
  let service: EmiSchedulerService;

  beforeAll(async () => {
    // Expensive, immutable: DB connection + migrations
    dataSource = await createTestDataSource();
    await runMigrations(dataSource);
  });

  afterAll(async () => {
    await dataSource.destroy(); // close connection pool — prevents open handle warning
  });

  // ── Per-test state (beforeEach / afterEach) ───────────────────────────────
  beforeEach(async () => {
    // Fresh mock per test — Kafka has no real I/O in integration tests
    kafkaProducer = { publish: jest.fn().mockResolvedValue(undefined) } as any;

    // Fresh service instance per test — captures fresh mock
    service = new EmiSchedulerService(dataSource, kafkaProducer);

    // Seed data specific to the happy path — individual tests override as needed
    await seedActiveLoansWithEmisDue(dataSource);
  });

  afterEach(async () => {
    // Reset DB state — must be unconditional (runs even if test throws)
    await dataSource.query('TRUNCATE emi, loan, user RESTART IDENTITY CASCADE');
    // Reset mock state
    jest.clearAllMocks();
  });

  // ── Tests ─────────────────────────────────────────────────────────────────
  describe('when EMIs are due today', () => {
    it('should mark each EMI as PENDING_DEBIT in the database', async () => {
      await service.runDailyEmiJob();
      const emis = await dataSource.query(`SELECT status FROM emi WHERE due_date = CURRENT_DATE`);
      expect(emis.every((e: any) => e.status === 'PENDING_DEBIT')).toBe(true);
    });

    it('should publish one Kafka event per due EMI', async () => {
      await service.runDailyEmiJob();
      const dueCount = await countDueEmis(dataSource);
      expect(kafkaProducer.publish).toHaveBeenCalledTimes(dueCount);
    });
  });

  describe('when no EMIs are due today', () => {
    beforeEach(async () => {
      // Override: clear the default seed and insert loans with future due dates
      await dataSource.query('TRUNCATE emi, loan, user RESTART IDENTITY CASCADE');
      await seedActiveLoansWithFutureDueDates(dataSource);
    });

    it('should not publish any Kafka events', async () => {
      await service.runDailyEmiJob();
      expect(kafkaProducer.publish).not.toHaveBeenCalled();
    });
  });
});
```

The allocation: `beforeAll` owns the DB connection (once, shared). `afterAll` closes it. `beforeEach` owns the service instance + mock + default seed data. `afterEach` owns the data reset + mock clear. The inner `beforeEach` in the "no EMIs due" scenario overrides the default seed cleanly within its own scope, without touching the outer hooks.

## Quick Reference: Hook Decision Table

| Question                                              | Answer                               |
|-------------------------------------------------------|--------------------------------------|
| Is the setup expensive and shared across all tests?   | `beforeAll`                          |
| Does the setup create mutable state?                  | `beforeEach` — never `beforeAll`     |
| Must teardown happen even if the test fails?          | `afterEach` (always runs)            |
| Am I closing a connection / server?                   | `afterAll`                           |
| Am I resetting DB rows between tests?                 | `afterEach`                          |
| Am I clearing mocks?                                  | `beforeEach` or configure globally   |
| Am I restoring `jest.spyOn` spies?                    | `afterEach` with `restoreAllMocks()` |
| Is my setup async?                                    | Mark the hook `async`, always `await`|
| Do I need the same test run with multiple data sets?  | `test.each` / `describe.each`        |
| Is a test temporarily broken by an external issue?    | `describe.skip` (not `describe.only`)|

---

**Tip for the interview:** At 5 YOE, hook questions don't come as "what does `beforeEach` do?" — they come embedded in debugging scenarios: "why are these tests flaky," "why does the suite take 4 minutes," "why does test B fail only when test A runs first." The answer is always the same diagnostic path — identify whether the violation is Fast (bootstrap in `beforeEach`), Independent (`beforeAll` for mutable state, no `afterEach` reset), Repeatable (async hook without `await`), or Self-validating (teardown not running on failure). Know the execution order cold — outer-before to inner-before, inner-after to outer-after — because the interviewer will draw a nesting diagram on a whiteboard and ask you to trace through it.
