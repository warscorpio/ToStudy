# Mocking: `jest.fn()`, `jest.spyOn()`, `jest.mock()` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is mocking, and why is it necessary in a well-structured test suite?**
A: Mocking is the practice of replacing a real dependency — a database client, an HTTP service, a file system call, a timer — with a controlled substitute that behaves exactly as the test dictates. It exists to solve three problems:

- **Isolation** — the unit under test should fail or pass based on *its own logic*, not on whether a third-party API is reachable or a DB seed is correctly set up.
- **Determinism** — real dependencies are unpredictable (network latency, DB state, current time). Mocks make test outcomes deterministic: same inputs, same outputs, every run.
- **Speed** — a real HTTP call or DB query takes 10–500ms; a mock returns in microseconds. A 500-test suite where each test makes one real DB call takes minutes; with mocks, seconds.

The discipline is knowing *what to mock*: mock things you don't own (external APIs, payment gateways, email services), mock things that are slow or have side effects (DB, file I/O, queues), and mock *collaborators* of the unit under test — not the unit itself.

**Q2. What are the three Jest mocking primitives and when does each apply?**
A: Jest provides three distinct tools, each operating at a different scope:

| Primitive | Scope | Primary use |
|---|---|---|
| `jest.fn()` | Single function | Create a standalone mock function from scratch; inject as a dependency |
| `jest.spyOn()` | Method on an existing object | Intercept a real method, observe calls, optionally override return value — while keeping the original intact by default |
| `jest.mock()` | Entire module | Replace all exports of a module at import time, before any test code runs |

The mental model: `jest.fn()` creates, `jest.spyOn()` wraps, `jest.mock()` hijacks. Choosing the wrong one usually leads to either over-mocking (mocking things that should be real) or under-mocking (the real implementation still runs when it shouldn't).

**Q3. What is the difference between a mock, a stub, a spy, and a fake?**
A: These terms come from Gerard Meszaros' *xUnit Test Patterns* and are often used interchangeably in practice, but they have distinct meanings:

- **Stub** — returns canned values; no behaviour verification. `jest.fn().mockReturnValue(42)` used only in Arrange is a stub. You don't care if it was called — you just need it to return something.
- **Mock** — a stub with expectations: you assert it was called, with specific arguments, a specific number of times. `jest.fn()` used with `expect(fn).toHaveBeenCalledWith(...)` is a mock.
- **Spy** — wraps a real implementation; records calls without replacing behaviour. `jest.spyOn(obj, "method")` without `.mockImplementation()` is a spy — the real method still runs; you're just observing.
- **Fake** — a working implementation with simplified behaviour (in-memory DB instead of PostgreSQL, local filesystem instead of S3). Not directly a Jest construct; you'd build fakes manually and inject them.

Jest blurs the lines: `jest.fn()` can be a stub or mock depending on whether you assert on it; `jest.spyOn()` can be a spy or mock depending on whether you override the implementation. The vocabulary matters in interviews and code reviews — "I stubbed the return value" vs "I mocked the dependency" signals precision.

## Section 2: `jest.fn()` — Creating Mock Functions

**Q4. What does `jest.fn()` return and what can you do with it?**
A: `jest.fn()` returns a `JestMockFn` — a function that, by default, returns `undefined` when called, but records every invocation. Every recorded call is available on the `.mock` property:

```typescript
const mockFn = jest.fn();

mockFn("a", 1);
mockFn("b", 2);

console.log(mockFn.mock.calls);
// [["a", 1], ["b", 2]]

console.log(mockFn.mock.results);
// [{ type: "return", value: undefined }, { type: "return", value: undefined }]

console.log(mockFn.mock.instances);
// [undefined, undefined] — populated when used as a constructor (new mockFn())
```

The `.mock` property is what powers Jest's assertion matchers:
- `expect(mockFn).toHaveBeenCalled()` — checks `.mock.calls.length > 0`
- `expect(mockFn).toHaveBeenCalledWith("a", 1)` — checks `.mock.calls[n]`
- `expect(mockFn).toHaveBeenCalledTimes(2)` — checks `.mock.calls.length`
- `expect(mockFn).toHaveBeenNthCalledWith(1, "a", 1)` — checks a specific call index

**Q5. What are the different ways to control what a `jest.fn()` returns?**
A: Five methods, each for a different scenario:

```typescript
// 1. mockReturnValue — always returns the same value
const fn1 = jest.fn().mockReturnValue(42);
fn1(); // 42
fn1(); // 42

// 2. mockReturnValueOnce — returns the value only on the next call; falls through to default after
const fn2 = jest.fn()
  .mockReturnValueOnce("first")
  .mockReturnValueOnce("second")
  .mockReturnValue("default");
fn2(); // "first"
fn2(); // "second"
fn2(); // "default"
fn2(); // "default"

// 3. mockResolvedValue — shorthand for mockReturnValue(Promise.resolve(...))
const fn3 = jest.fn().mockResolvedValue({ id: "u1", name: "Alice" });
await fn3(); // { id: "u1", name: "Alice" }

// 4. mockRejectedValue — shorthand for mockReturnValue(Promise.reject(...))
const fn4 = jest.fn().mockRejectedValue(new Error("DB connection failed"));
await fn4(); // throws Error("DB connection failed")

// 5. mockImplementation — full custom implementation for complex behaviour
const fn5 = jest.fn().mockImplementation((userId: string) => {
  if (userId === "banned") throw new ForbiddenError("User is banned");
  return { id: userId, status: "active" };
});
fn5("u1");      // { id: "u1", status: "active" }
fn5("banned");  // throws ForbiddenError

// mockImplementationOnce — same one-shot variant as mockReturnValueOnce
const fn6 = jest.fn()
  .mockImplementationOnce(() => ({ status: "pending" }))
  .mockImplementation(() => ({ status: "completed" }));
```

Rule of thumb: use `mockReturnValue` / `mockResolvedValue` for simple canned values; use `mockImplementation` when the mock needs to branch, throw conditionally, or capture arguments for later use.

**Q6. How do you inject a `jest.fn()` into a class under test in TypeScript without losing type safety?**
A: Use `jest.Mocked<T>` to type the mock object so TypeScript knows every method is a `jest.fn()`:

```typescript
// src/payments/payment.service.ts
export class PaymentService {
  constructor(private readonly gateway: GatewayClient) {}

  async charge(payload: ChargePayload): Promise<ChargeResult> {
    return this.gateway.charge(payload);
  }
}

// src/payments/payment.service.spec.ts
describe("PaymentService", () => {
  let service: PaymentService;
  let gateway: jest.Mocked<GatewayClient>;

  beforeEach(() => {
    // Build a typed mock object: each method is a jest.fn()
    gateway = {
      charge:  jest.fn(),
      refund:  jest.fn(),
      status:  jest.fn(),
    } as jest.Mocked<GatewayClient>;

    service = new PaymentService(gateway);
  });

  it("should return the charge result from the gateway", async () => {
    // Arrange
    const payload: ChargePayload = { amount: 5000, currency: "INR", userId: "u1" };
    gateway.charge.mockResolvedValue({ txnId: "txn_001", status: "success" });

    // Act
    const result = await service.charge(payload);

    // Assert
    expect(result).toEqual({ txnId: "txn_001", status: "success" });
    expect(gateway.charge).toHaveBeenCalledWith(payload);
  });
});
```

`jest.Mocked<GatewayClient>` gives you full autocomplete on `.mockResolvedValue()`, `.mockImplementation()`, and all other mock methods — TypeScript will error if you pass the wrong argument shape to `gateway.charge.mockResolvedValue(...)`.

**Q7. What is `mockFn.mockClear()` vs `mockFn.mockReset()` vs `mockFn.mockRestore()`, and when do you use each?**
A: These three methods clean up a mock at different depths:

| Method | Clears call history | Resets implementation | Restores original |
|---|---|---|---|
| `mockClear()` | ✅ | ❌ | ❌ |
| `mockReset()` | ✅ | ✅ | ❌ |
| `mockRestore()` | ✅ | ✅ | ✅ (spies only) |

```typescript
const fn = jest.fn().mockReturnValue(42);
fn();
fn();

fn.mockClear();
// fn.mock.calls is now []
// fn() still returns 42 — implementation preserved

fn.mockReset();
// fn.mock.calls is now []
// fn() now returns undefined — implementation wiped

// mockRestore() only works on jest.spyOn() mocks:
const spy = jest.spyOn(Math, "random").mockReturnValue(0.5);
spy.mockRestore();
// Math.random is the real implementation again
```

In practice:
- Use `jest.clearAllMocks()` in `beforeEach` (configured via `clearMocks: true` in `jest.config.ts`) — clears call history between tests without resetting implementations (useful when mock return values are set in `beforeEach` and should persist).
- Use `mockReset()` when a test needs a clean mock with no prior configuration — typically when a test sets up its own `mockImplementation` and a prior test's setup would conflict.
- Use `mockRestore()` in `afterEach` for `jest.spyOn()` calls — restores the real implementation so other test files aren't affected.

**Q8. How do you mock a constructor and assert on instance method calls?**
A: When the SUT calls `new SomeClass()` internally, you need to mock the constructor and the methods of the resulting instance:

```typescript
// src/notifications/notification.service.ts
import { EmailClient } from "./email.client";

export class NotificationService {
  async sendWelcomeEmail(email: string, name: string): Promise<void> {
    const client = new EmailClient();          // instantiated internally
    await client.send({ to: email, subject: `Welcome, ${name}!`, body: "..." });
  }
}

// src/notifications/notification.service.spec.ts
import { EmailClient } from "./email.client";
jest.mock("./email.client");                   // mock the module

describe("NotificationService", () => {
  let service: NotificationService;
  let mockSend: jest.Mock;

  beforeEach(() => {
    jest.clearAllMocks();

    // EmailClient is now a mock constructor — configure the instance methods
    mockSend = jest.fn().mockResolvedValue(undefined);
    (EmailClient as jest.Mock).mockImplementation(() => ({
      send: mockSend,
    }));

    service = new NotificationService();
  });

  it("should send a welcome email with the correct subject", async () => {
    // Act
    await service.sendWelcomeEmail("alice@example.com", "Alice");

    // Assert
    expect(EmailClient).toHaveBeenCalledTimes(1);        // constructor called
    expect(mockSend).toHaveBeenCalledWith(
      expect.objectContaining({ to: "alice@example.com", subject: "Welcome, Alice!" })
    );
  });
});
```

The pattern: `jest.mock("./email.client")` replaces the class with a mock constructor; `.mockImplementation(() => ({ send: mockSend }))` controls what the constructed instance looks like.

## Section 3: `jest.spyOn()` — Wrapping Real Implementations

**Q9. What does `jest.spyOn()` do, and how is it fundamentally different from `jest.fn()`?**
A: `jest.spyOn(object, methodName)` reaches into an existing object, replaces the named method with a `jest.fn()` wrapper, and returns that wrapper — *while preserving a reference to the original*. By default, the real implementation still runs; you're just observing:

```typescript
const calculator = {
  add: (a: number, b: number) => a + b,
};

const spy = jest.spyOn(calculator, "add");

const result = calculator.add(2, 3);
// result is 5 — real implementation ran

expect(spy).toHaveBeenCalledWith(2, 3);  // observation ✅
expect(result).toBe(5);                  // real result ✅

spy.mockRestore(); // put the real add back
```

`jest.fn()` creates a function with no real implementation. `jest.spyOn()` wraps one that exists. The difference matters when: you want to verify a real method was called (spy), vs replace a dependency entirely (mock).

**Q10. When should you use `jest.spyOn()` instead of replacing the dependency with a `jest.fn()`?**
A: Four scenarios where `spyOn` is the right tool:

**1. Observing calls to a method you want to keep running:**
```typescript
// You want to verify the cache was checked, but the real cache logic should run
const spy = jest.spyOn(cacheService, "get");
await service.getUser("u1");
expect(spy).toHaveBeenCalledWith("user:u1");
// cacheService.get ran for real — test verifies the call path
```

**2. Partially mocking a module — most methods real, one overridden:**
```typescript
import * as dateUtils from "../utils/date.utils";

// Most dateUtils functions are real; freeze just the one that reads the clock
jest.spyOn(dateUtils, "getNow").mockReturnValue(new Date("2024-01-15T00:00:00Z"));
```

**3. Mocking class methods on a prototype:**
```typescript
// Mock UserRepository.findById without constructing a full mock object
jest.spyOn(UserRepository.prototype, "findById")
  .mockResolvedValue({ id: "u1", name: "Alice" });
```

**4. Mocking built-in or third-party methods:**
```typescript
// Mock Math.random without importing it as a dependency
jest.spyOn(Math, "random").mockReturnValue(0.42);

// Mock console.error to assert it was called (and suppress noisy output)
jest.spyOn(console, "error").mockImplementation(() => {});
```

The key: prefer `spyOn` when the object already exists and you need surgical control over one method; prefer `jest.fn()` injection when the dependency is injected via constructor or parameter (DI pattern).

**Q11. What happens if you forget to call `mockRestore()` on a `jest.spyOn()`, and how do you prevent the issue at scale?**
A: Forgetting `mockRestore()` leaves the spy in place on the object across tests — all subsequent tests in *any* test file that imports the same module will see the mocked version, not the real one. This causes ghost failures: test B fails because test A left a spy on `Math.random` that returns `0.5` instead of a real random value.

Prevention strategies:

```typescript
// Strategy 1: afterEach restore (manual, per-spy)
describe("MyService", () => {
  let spy: jest.SpyInstance;

  beforeEach(() => {
    spy = jest.spyOn(Math, "random").mockReturnValue(0.5);
  });

  afterEach(() => {
    spy.mockRestore();  // real Math.random restored for the next test
  });
});

// Strategy 2: jest.config.ts — restoreAllMocks: true
// Automatically calls mockRestore() on every spy after each test
export default {
  restoreAllMocks: true,   // restore spies
  clearMocks:      true,   // clear call history
  resetMocks:      false,  // don't wipe implementations (set per test if needed)
};
```

`restoreAllMocks: true` in `jest.config.ts` is the safest default for a team — it ensures no spy leaks between tests regardless of whether individual tests clean up after themselves.

**Q12. How do you spy on a named export from an ES module in Jest (the module binding problem)?**
A: ES module named exports are live bindings — you can't reassign them directly from outside the module. `jest.spyOn` only works on object properties, so you must import the module as a namespace:

```typescript
// src/utils/id.utils.ts
export function generateId(): string {
  return crypto.randomUUID();
}

// src/orders/order.service.ts
import { generateId } from "../utils/id.utils";

export class OrderService {
  createOrder(payload: CreateOrderDto) {
    return { id: generateId(), ...payload, status: "pending" };
  }
}

// src/orders/order.service.spec.ts
import * as idUtils from "../utils/id.utils";   // import as namespace
import { OrderService } from "./order.service";

describe("OrderService", () => {
  it("should include the generated ID in the created order", () => {
    // Arrange
    jest.spyOn(idUtils, "generateId").mockReturnValue("fixed-id-001");
    const service = new OrderService();

    // Act
    const order = service.createOrder({ userId: "u1", amount: 500 });

    // Assert
    expect(order.id).toBe("fixed-id-001");
  });
});
```

**Critical caveat:** This only works because Jest transforms modules to CommonJS (CJS) by default (via Babel or `ts-jest`), making named exports mutable properties of the module object. With native ESM (`"type": "module"` in `package.json` + `--experimental-vm-modules`), this pattern breaks — you'd need `jest.mock()` with a factory instead. This is a known Jest/ESM pain point that frequently comes up in interviews.

## Section 4: `jest.mock()` — Module-Level Mocking

**Q13. What does `jest.mock()` do, and what is the "hoisting" behaviour?**
A: `jest.mock(modulePath)` replaces an entire module's exports with auto-mocked versions — all exported functions become `jest.fn()`, all exported classes become mock constructors with mocked methods — before any `import` statements in the test file are evaluated.

The hoisting behaviour is critical and often misunderstood: Jest moves `jest.mock()` calls to the top of the file at compile time (via Babel transform), even if you write them after your `import` statements:

```typescript
// What you write:
import { sendEmail } from "./email.service";
jest.mock("./email.service");

// What Jest actually executes (hoisted):
jest.mock("./email.service");
import { sendEmail } from "./email.service";
// sendEmail is now a jest.fn()
```

Because of hoisting, you **cannot** use a variable defined in the test file inside `jest.mock()` — the `jest.mock()` call runs before variable initialisation:

```typescript
// ❌ This does NOT work — variable is not yet initialised when jest.mock() runs
const mockSend = jest.fn();
jest.mock("./email.service", () => ({
  sendEmail: mockSend,   // ReferenceError: mockSend is not defined
}));

// ✅ Correct — define the mock inside the factory function
jest.mock("./email.service", () => ({
  sendEmail: jest.fn(),
}));

// Then access it via the imported module reference:
import { sendEmail } from "./email.service";
// sendEmail IS the jest.fn() from the factory
```

The one exception: variables prefixed with `mock` are hoisting-safe (a Jest Babel transform special case):
```typescript
const mockSendEmail = jest.fn();   // "mock" prefix makes this hoisting-safe
jest.mock("./email.service", () => ({
  sendEmail: mockSendEmail,        // ✅ works because of the prefix convention
}));
```

**Q14. What is the difference between `jest.mock()` with no factory, with a factory, and with `jest.requireActual()`?**
A: Three usage modes, each appropriate for a different scenario:

```typescript
// Mode 1: Auto-mock (no factory)
// Jest replaces every export with jest.fn() automatically
jest.mock("./payment.gateway");
import { GatewayClient } from "./payment.gateway";
// GatewayClient is now a mock constructor; GatewayClient.prototype.charge is jest.fn()

// Mode 2: Factory function — full manual control
jest.mock("./payment.gateway", () => ({
  GatewayClient: jest.fn().mockImplementation(() => ({
    charge: jest.fn().mockResolvedValue({ status: "success", txnId: "txn_001" }),
    refund: jest.fn().mockResolvedValue({ status: "refunded" }),
  })),
}));

// Mode 3: Partial mock with jest.requireActual — keep real exports, override specific ones
jest.mock("./config/app.config", () => ({
  ...jest.requireActual("./config/app.config"),  // real exports as base
  PAYMENT_TIMEOUT_MS: 100,                        // override just this one value
  IS_TEST_ENV:        true,
}));
```

When to use each:
- **Auto-mock** — quick, for when you only need the mock to exist (injected into DI container) but will configure return values per-test with `.mockResolvedValue()`.
- **Factory** — when auto-mock doesn't produce the right shape (complex class hierarchies, default exports, mixed named/default), or when you want consistent base behaviour across all tests in the file.
- **`requireActual`** — when you need most of the real module but want to freeze one export (config values, date utilities, feature flags).

**Q15. How do you mock a module that has both default and named exports?**
A: The factory must explicitly reproduce the full export shape:

```typescript
// src/clients/razorpay.client.ts
export default class RazorpayClient {
  charge(payload: ChargePayload): Promise<ChargeResult> { /* ... */ }
}
export const RAZORPAY_API_VERSION = "v1";
export function buildSignature(payload: string, secret: string): string { /* ... */ }

// In your test file:
jest.mock("../clients/razorpay.client", () => {
  const mockCharge = jest.fn();

  return {
    // Default export: use __esModule: true + default key
    __esModule: true,
    default: jest.fn().mockImplementation(() => ({
      charge: mockCharge,
    })),
    // Named exports
    RAZORPAY_API_VERSION: "v1",
    buildSignature:       jest.fn().mockReturnValue("mock-signature"),
  };
});

import RazorpayClient, { buildSignature } from "../clients/razorpay.client";

it("should call charge with the correct payload", async () => {
  const client = new RazorpayClient();          // mock constructor
  await client.charge({ amount: 1000 });
  expect(client.charge).toHaveBeenCalledWith({ amount: 1000 });
});
```

`__esModule: true` is required when mocking a module that uses `export default` — without it, Jest won't properly wire the `default` property through Babel's interop layer.

**Q16. How do you reset or change a `jest.mock()` implementation between tests within the same file?**
A: `jest.mock()` applies at file scope — the same mock is shared by all tests in the file. Per-test customisation happens by accessing the imported mock reference and calling mock methods on it:

```typescript
jest.mock("./email.service");
import { sendEmail } from "./email.service";

const mockSendEmail = sendEmail as jest.Mock;

describe("NotificationService", () => {
  beforeEach(() => {
    jest.clearAllMocks();  // clear call history between tests
  });

  it("should send a welcome email on registration", async () => {
    // Arrange — configure return value for this test
    mockSendEmail.mockResolvedValue({ messageId: "msg_001" });

    // Act
    await notificationService.sendWelcome("alice@example.com");

    // Assert
    expect(mockSendEmail).toHaveBeenCalledWith(
      expect.objectContaining({ to: "alice@example.com" })
    );
  });

  it("should throw NotificationError when email delivery fails", async () => {
    // Arrange — different behaviour for this test
    mockSendEmail.mockRejectedValue(new Error("SMTP connection refused"));

    // Act & Assert
    await expect(
      notificationService.sendWelcome("alice@example.com")
    ).rejects.toThrow("NotificationError");
  });
});
```

If you need to change the mock's *entire shape* between tests (not just the return value), use `jest.doMock()` — the non-hoisted version of `jest.mock()` that can be called inside test bodies. It requires a dynamic `require()` to re-import the module with the new mock:

```typescript
it("should handle a completely different module shape", () => {
  jest.doMock("./config", () => ({ featureFlags: { newFlow: true } }));
  const { configService } = require("./config.service"); // re-require with new mock
  // ...
  jest.resetModules();  // clean up for subsequent tests
});
```

**Q17. How do you mock a Node.js built-in module like `fs` or `crypto`?**
A:

```typescript
// Mocking 'fs' — must pass the module name exactly as imported
jest.mock("fs");
import fs from "fs";

it("should read the config file and parse it as JSON", () => {
  // Arrange
  (fs.readFileSync as jest.Mock).mockReturnValue(
    JSON.stringify({ timeout: 5000, retries: 3 })
  );

  // Act
  const config = loadConfig("/etc/app/config.json");

  // Assert
  expect(config.timeout).toBe(5000);
  expect(fs.readFileSync).toHaveBeenCalledWith("/etc/app/config.json", "utf-8");
});

// Mocking 'crypto' — partial mock to freeze randomUUID
jest.mock("crypto", () => ({
  ...jest.requireActual("crypto"),
  randomUUID: jest.fn().mockReturnValue("fixed-uuid-1234"),
}));
```

For `fs`, the auto-mock (`jest.mock("fs")`) works well because Node's `fs` exports are plain functions. For `crypto`, a partial mock with `requireActual` is preferable — you don't want to mock hashing or signing primitives your SUT uses internally.

## Section 5: Advanced Patterns

**Q18. How do you mock a module differently in different test files?**
A: `jest.mock()` is scoped to the test file — each test file gets an independent module registry. Two files can mock the same module differently with no interference:

```typescript
// payment.service.spec.ts
jest.mock("../gateway/razorpay", () => ({
  charge: jest.fn().mockResolvedValue({ status: "success" }),
}));

// refund.service.spec.ts
jest.mock("../gateway/razorpay", () => ({
  charge: jest.fn().mockRejectedValue(new Error("Gateway down")),
}));
```

Each file runs in its own Jest worker with its own module registry — the mocks are completely independent. This is why Jest isolates test files: shared module state (singletons, caches) would cause exactly the cross-test contamination that isolation prevents.

**Q19. How do you test a module that uses `setTimeout` or `setInterval`?**
A: Use Jest's fake timers — they replace the global timer functions with mock implementations that you control:

```typescript
// src/retry/retry.utils.ts
export async function retryWithBackoff<T>(
  fn:          () => Promise<T>,
  maxAttempts: number,
  delayMs:     number,
): Promise<T> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      await new Promise((resolve) => setTimeout(resolve, delayMs * attempt));
    }
  }
  throw new Error("Unreachable");
}

// src/retry/retry.utils.spec.ts
describe("retryWithBackoff", () => {
  beforeEach(() => {
    jest.useFakeTimers();
  });

  afterEach(() => {
    jest.useRealTimers();
  });

  it("should retry the function and resolve on the third attempt", async () => {
    // Arrange
    const fn = jest.fn()
      .mockRejectedValueOnce(new Error("attempt 1 failed"))
      .mockRejectedValueOnce(new Error("attempt 2 failed"))
      .mockResolvedValue({ data: "success" });

    // Act — start the retry (don't await yet; it's waiting on timers)
    const resultPromise = retryWithBackoff(fn, 3, 100);

    // Advance timers to skip the delays without real waiting
    await jest.runAllTimersAsync();   // Jest 29+; use jest.runAllTimers() in older versions

    const result = await resultPromise;

    // Assert
    expect(fn).toHaveBeenCalledTimes(3);
    expect(result).toEqual({ data: "success" });
  });
});
```

Key fake timer methods:
- `jest.useFakeTimers()` — replace `setTimeout`, `setInterval`, `Date`, etc.
- `jest.runAllTimers()` — synchronously exhaust all pending timers.
- `jest.runAllTimersAsync()` — same but for timers that involve Promises (Jest 29+).
- `jest.advanceTimersByTime(ms)` — advance the fake clock by a specific duration.
- `jest.useRealTimers()` — restore real implementations (put in `afterEach`).

**Q20. How do you capture and assert on arguments passed across multiple calls to the same mock?**
A: Access `.mock.calls` directly for complex multi-call assertions that Jest's built-in matchers don't cover cleanly:

```typescript
it("should emit audit events for each step of the payment flow", async () => {
  // Arrange
  const auditLogger = { log: jest.fn() };
  const service     = new PaymentService(gateway, auditLogger);
  gateway.charge.mockResolvedValue({ status: "success", txnId: "txn_001" });

  // Act
  await service.processPayment({ userId: "u1", amount: 5000 });

  // Assert — specific calls by index
  expect(auditLogger.log.mock.calls[0][0]).toMatchObject({
    event:  "payment.initiated",
    userId: "u1",
  });
  expect(auditLogger.log.mock.calls[1][0]).toMatchObject({
    event: "payment.gateway.charged",
    txnId: "txn_001",
  });
  expect(auditLogger.log.mock.calls[2][0]).toMatchObject({
    event:  "payment.completed",
    userId: "u1",
    txnId:  "txn_001",
  });
  expect(auditLogger.log).toHaveBeenCalledTimes(3);
});
```

For asserting that a mock was called with a matching subset of properties (without specifying the full object), `expect.objectContaining()` is essential:

```typescript
expect(auditLogger.log).toHaveBeenCalledWith(
  expect.objectContaining({ event: "payment.initiated" })
);
```

**Q21. How do you mock an entire NestJS service inside a NestJS testing module?**
A: Use `overrideProvider` in the `Test.createTestingModule` builder — this replaces the DI token with your mock without using `jest.mock()` at the module level:

```typescript
// src/auth/auth.controller.spec.ts
describe("AuthController", () => {
  let controller:  AuthController;
  let authService: jest.Mocked<AuthService>;

  beforeEach(async () => {
    const mockAuthService: jest.Mocked<AuthService> = {
      login:        jest.fn(),
      validateUser: jest.fn(),
      refreshToken: jest.fn(),
    } as jest.Mocked<AuthService>;

    const module: TestingModule = await Test.createTestingModule({
      controllers: [AuthController],
      providers:   [AuthService],
    })
      .overrideProvider(AuthService)
      .useValue(mockAuthService)         // inject mock instead of real AuthService
      .compile();

    controller  = module.get<AuthController>(AuthController);
    authService = module.get(AuthService) as jest.Mocked<AuthService>;
  });

  it("should return an access token on successful login", async () => {
    // Arrange
    const dto = { email: "alice@example.com", password: "secret" };
    authService.login.mockResolvedValue({ accessToken: "jwt.token.here" });

    // Act
    const result = await controller.login(dto);

    // Assert
    expect(result).toEqual({ accessToken: "jwt.token.here" });
    expect(authService.login).toHaveBeenCalledWith(dto);
  });
});
```

This is the idiomatic NestJS testing pattern — it respects the DI container, tests the controller in isolation from the real service, and keeps mock configuration close to the test that needs it.

## Section 6: Common Pitfalls

**Q22. Why does your mock not work even though you called `jest.mock()`?**
A: The six most common causes:

**1. Wrong module path** — `jest.mock("./email.service")` vs `jest.mock("../email.service")`. The path must exactly match what the SUT imports. If the SUT does `import { sendEmail } from "@app/email/email.service"` (path alias), the mock path must use the same alias.

**2. Mocking after import in an ESM context** — in native ESM, module evaluation is static; `jest.mock()` hoisting only works in CommonJS/Babel-transformed environments. With native ESM, imports are already bound before any runtime code runs.

**3. Mocking the wrong export shape** — if the module uses `export default` and your factory returns `{ sendEmail: jest.fn() }` without `__esModule: true` and a `default` key, the import will be undefined.

**4. Not clearing mocks between tests** — a `mockResolvedValue` set in test A bleeds into test B if `clearMocks: true` isn't set or `beforeEach` doesn't reset it.

**5. Mocking a module the SUT doesn't import** — the SUT imports `lodash/debounce` but you mocked `lodash`. Jest mocks are per-exact-import-path.

**6. Circular dependency** — the mocked module depends on the SUT module, which depends on the mock, causing Jest's module resolution to return an empty object.

**Q23. What is the difference between `jest.mock()` and manual mocks (`__mocks__` directory)?**
A: Manual mocks are mock implementations stored in a `__mocks__` directory adjacent to the module (or adjacent to `node_modules` for third-party packages). Jest automatically uses them when `jest.mock("moduleName")` is called — no factory function needed:

```
src/
  services/
    email.service.ts
    __mocks__/
      email.service.ts     ← manual mock; used when jest.mock("./email.service") is called
```

```typescript
// src/services/__mocks__/email.service.ts
export const sendEmail = jest.fn().mockResolvedValue({ messageId: "mock-id" });
export const getEmailStatus = jest.fn().mockResolvedValue("delivered");
```

```typescript
// In test files — just call jest.mock() without a factory
jest.mock("./email.service");   // Jest automatically uses __mocks__/email.service.ts
```

For Node.js built-ins and `node_modules`, the `__mocks__` directory goes at the root (next to `node_modules`):
```
__mocks__/
  fs.js          ← mocks Node's built-in fs
  axios.js       ← mocks the axios package
```

**When to use manual mocks vs inline factory:** use `__mocks__` when the same mock implementation is reused across many test files — DRY principle for mocks. Use inline factories when the mock is specific to one test file or scenario.

**Q24. How does mocking interact with TypeScript's type system, and how do you avoid `as jest.Mock` casts everywhere?**
A: The `as jest.Mock` cast is needed whenever TypeScript doesn't know a function is a mock. Three approaches to minimise it:

```typescript
// Approach 1: jest.Mocked<T> — type the whole dependency as mocked upfront
const emailService = {
  sendEmail:      jest.fn(),
  getEmailStatus: jest.fn(),
} as jest.Mocked<EmailService>;
// Now emailService.sendEmail.mockResolvedValue(...) works without casting

// Approach 2: jest.mocked() helper (Jest 27+) — wraps an imported mock with correct types
jest.mock("./email.service");
import { sendEmail } from "./email.service";

const mockedSendEmail = jest.mocked(sendEmail);   // typed as jest.MockedFunction<typeof sendEmail>
mockedSendEmail.mockResolvedValue({ messageId: "msg_001" });  // fully typed, no cast needed

// Approach 3: Type the module mock explicitly with ModuleMock
jest.mock("./email.service");
import * as EmailServiceModule from "./email.service";

const emailServiceMock = EmailServiceModule as jest.Mocked<typeof EmailServiceModule>;
emailServiceMock.sendEmail.mockResolvedValue({ messageId: "msg_001" });
```

`jest.mocked()` (approach 2) is the modern preferred approach in Jest 27+ — it's explicitly designed to solve this problem and is the least verbose.

## Section 7: Scenario / System Design Style Questions

**Q25. "You're reviewing a PR where a developer has used `jest.mock()` to mock the entire `UserRepository` in a test of `PaymentService`. The test passes but the team says they're still finding payment bugs in production. What's the problem?"**
A: Three likely issues with over-mocking a repository:

**1. The mock returns data the real system never would.** If the mock returns `{ id: "u1", balance: 99999 }` but the real `UserRepository.findById()` can also return `null` (user not found), an expired session, or a user with `status: "suspended"` — and those paths aren't tested — bugs hide in the gap between mock and reality.

**2. The `PaymentService` logic is verified against a fictional contract.** If `UserRepository` changes its return shape (e.g., renames `balance` to `availableBalance` after a schema migration), the `PaymentService` test still passes (mock returns the old shape) but production breaks immediately.

**3. Missing integration coverage.** Unit tests with mocked repositories verify logic; they can't catch SQL query bugs, missing DB indexes causing timeouts under load, or transaction isolation issues. Payment bugs often live at the DB boundary.

Recommended fix: keep unit tests with mock repositories for pure logic, but add integration tests that run `PaymentService` against a real (test) DB — these catch the contract and query bugs the unit tests structurally cannot.

**Q26. "You need to test a service that calls three external APIs in sequence: PAN verification, credit bureau check, and NACH eligibility. All three are rate-limited and cost money per call. How do you structure the mocks?"**
A: Layer the mocks by test type:

**Unit tests — mock all three at the service client level:**
```typescript
// Isolate the orchestration logic entirely
const panClient     = { verify: jest.fn() } as jest.Mocked<PanApiClient>;
const bureauClient  = { check:  jest.fn() } as jest.Mocked<BureauApiClient>;
const nachClient    = { check:  jest.fn() } as jest.Mocked<NachApiClient>;
const service       = new OnboardingService(panClient, bureauClient, nachClient);

// Test each orchestration path:
// - all three pass → approved
// - PAN fails → early exit, bureau not called
// - PAN passes, bureau fails → rejected, nach not called
// - all pass → NACH check made
```

**Contract tests — verify your mock matches the real API shape:**
Run once (not on every CI push) against the real APIs in a sandboxed environment, asserting that the response shape your mocks return matches what the real API actually returns. If the real `PanApiClient.verify()` response changes, the contract test catches it; your unit tests remain fast.

**Integration tests — use recorded fixtures (VCR pattern):**
Record real API responses once (in a controlled test run), store them as JSON fixtures, and replay them in integration tests:
```typescript
// jest.mock replaces the HTTP transport with fixture replay
jest.mock("../http/api.client", () => ({
  get:  jest.fn().mockImplementation((url) => loadFixture(url)),
  post: jest.fn().mockImplementation((url, body) => loadFixture(url, body)),
}));
```
This gives integration-level coverage (real response shapes, real field names) without real API calls.

**Q27. "A test that mocks `Date.now()` is causing flakiness in CI — it passes locally but fails intermittently on the CI server. What are the possible causes?"**
A: Flakiness in mocked-timer tests usually comes from one of four sources:

**1. `mockRestore()` not called — timer mock leaks into the next test:**
If a prior test mocked `Date.now()` and didn't restore it, the current test starts with the leaked mock. The value it returns depends on execution order, which can differ between local and CI.

**2. `jest.useFakeTimers()` not applied before the tested code starts:**
If the SUT caches `Date.now()` at module import time (e.g., `const startedAt = Date.now()` at module level), the fake timer doesn't intercept it — the real value is captured before the mock is installed.

**3. Real async operations racing with fake timers:**
`jest.runAllTimers()` is synchronous — it doesn't advance the event loop. If the SUT uses `setTimeout` inside a Promise chain, the timer fires but the Promise continuation doesn't resolve in the same tick. Use `jest.runAllTimersAsync()` (Jest 29+) or `await Promise.resolve()` to flush the microtask queue.

**4. System clock difference between local and CI:**
If the test isn't using fake timers and is comparing against real `Date.now()` values with a tolerance (e.g., `expect(timestamp).toBeGreaterThan(Date.now() - 1000)`), clock skew or test execution time differences on a slower CI machine cause the comparison to fail. Fix: always mock the clock in tests that involve time — never rely on real `Date.now()` in deterministic assertions.

## Quick Reference: Choosing the Right Tool

| Scenario | Tool | Pattern |
|---|---|---|
| Mock an injected dependency (DI pattern) | `jest.fn()` | Build a typed mock object: `{ method: jest.fn() } as jest.Mocked<T>` |
| Observe calls to a real method without replacing it | `jest.spyOn()` | `jest.spyOn(obj, "method")` — real impl runs |
| Replace a method on an existing object | `jest.spyOn()` + `.mockImplementation()` | Replaces impl; `mockRestore()` brings it back |
| Replace an entire module for a test file | `jest.mock()` | Auto-mock or factory; applied at file scope |
| Partially mock a module (keep most real) | `jest.mock()` + `jest.requireActual()` | Spread real, override specific exports |
| Reuse the same mock across many test files | Manual mock (`__mocks__/`) | Checked into repo; activated by `jest.mock()` |
| Mock timers / `Date` | `jest.useFakeTimers()` | Always pair with `jest.useRealTimers()` in `afterEach` |
| Test different module behaviour per test | `jest.doMock()` + `jest.resetModules()` | Non-hoisted; requires dynamic `require()` |
| Type-safe access to mock methods | `jest.mocked()` (Jest 27+) | Wraps an auto-mocked import with correct types |
