# NestJS Testing: Mocking Providers, Repositories, Services — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a mock, and how does it differ from a stub, a fake, and a spy?**
A: All four are test doubles — objects that replace real dependencies during tests — but they serve distinct purposes and make different trade-offs:

- **Stub** — returns hardcoded responses for specific calls; has no logic; does not record calls. Used when the test needs a dependency to return a value but doesn't care whether or how the dependency was called. `jest.fn().mockResolvedValue({ score: 750 })` with no assertion on the call is a stub.
- **Mock** — a stub that also records calls and verifies expectations. Used when the test cares both about what the dependency returns *and* whether it was called correctly. `jest.fn()` in Jest is both — it stubs the return value and records call history for `.toHaveBeenCalledWith()`.
- **Fake** — a working but simplified implementation. An in-memory `Map`-backed repository that actually stores and retrieves objects is a fake. It has real logic, just not production-grade infrastructure. Fakes are more expensive to build but produce more realistic tests — they catch integration-style bugs (like saving then reading back the same object) that stubs cannot.
- **Spy** — wraps a real implementation and intercepts calls. The original method still runs; the spy records the call. `jest.spyOn(service, 'method')` without `.mockImplementation()` is a spy. Used when you want to observe calls to a real method without replacing it.

At 5 YOE the relevant nuance: Jest's `jest.fn()` is colloquially called a "mock" but it is technically a stub when used with `.mockReturnValue()` and a mock when paired with `expect(...).toHaveBeenCalledWith()`. Understanding this distinction helps you reason about *what your test is actually verifying* — return value contract, call contract, or both.

**Q2. Why is mocking necessary in a NestJS service test, and what makes NestJS specifically challenging to mock?**
A: NestJS services are designed around constructor injection — every dependency is declared in the constructor and resolved by the DI container at runtime. This creates two testing challenges:

First, you cannot instantiate `new LoanService()` without satisfying the full constructor signature, which may include repositories, config services, event buses, HTTP clients, and other services — each of which may have their own deep dependency chains. Instantiating the real graph pulls in database connections, external API clients, and infrastructure that should not run in a unit test.

Second, NestJS uses decorators (`@Injectable()`, `@InjectRepository()`, `@Inject()`) to drive DI wiring. The injection tokens these decorators register are not always the class itself — `@InjectRepository(Loan)` registers under the token `getRepositoryToken(Loan)`, not `Repository`. If you mock the wrong token, the real dependency is injected silently and the mock is never used.

The solution to both: `Test.createTestingModule()` with precisely typed mocks provided under the exact injection tokens the service declares. This gives you a real DI-resolved service instance wired to controlled test doubles.

**Q3. What is the relationship between injection tokens and mocking in NestJS?**
A: An injection token is the key NestJS uses to look up a provider in its DI container. For class-based providers, the token is the class constructor reference. For custom providers (string tokens, symbol tokens, TypeORM repositories), the token is whatever is passed to `@Inject()` or generated by a factory function like `getRepositoryToken()`. Mocking a provider means registering a test double under the same token the service under test expects — if the token doesn't match, NestJS silently uses the real provider or throws a "cannot find provider" error.

```typescript
// Service declares this dependency
@Injectable()
export class LoanService {
  constructor(
    @InjectRepository(Loan)
    private readonly loanRepo: Repository<Loan>,     // token: getRepositoryToken(Loan)

    @Inject('BUREAU_CLIENT')
    private readonly bureauClient: BureauClient,     // token: 'BUREAU_CLIENT'

    private readonly configService: ConfigService,   // token: ConfigService (class)
  ) {}
}

// Test must mock under the exact same tokens
providers: [
  LoanService,
  { provide: getRepositoryToken(Loan), useValue: mockLoanRepo },   // matches @InjectRepository
  { provide: 'BUREAU_CLIENT', useValue: mockBureauClient },        // matches @Inject('BUREAU_CLIENT')
  { provide: ConfigService, useValue: mockConfigService },         // matches class token
]
```

Token mismatch is one of the most common sources of confusing test failures — the test compiles, the DI container resolves, but the real dependency runs and throws because it requires infrastructure that isn't present.

**Q4. What are the three ways Jest's `jest.fn()` can be configured, and when do you use each in a mocking context?**
A:

**1. Return value configuration — for controlling what the mock returns:**
```typescript
jest.fn().mockReturnValue(value)            // synchronous, same value every call
jest.fn().mockResolvedValue(value)          // async, resolves with value every call
jest.fn().mockReturnValueOnce(value)        // synchronous, only on the next call
jest.fn().mockResolvedValueOnce(value)      // async, only on the next call
jest.fn().mockRejectedValue(new Error())    // async, always rejects
jest.fn().mockRejectedValueOnce(new Error()) // async, rejects only on the next call
```

**2. Implementation configuration — for logic-bearing mocks:**
```typescript
jest.fn().mockImplementation((id: string) => {
  if (id === 'not-found') return null;
  return buildLoanFixture({ id });
})
jest.fn().mockImplementationOnce(() => null) // only on the next call
```

**3. Sequential return values — for retry or multi-step scenarios:**
```typescript
jest.fn()
  .mockResolvedValueOnce(null)          // first call: not found
  .mockResolvedValueOnce(buildLoan())   // second call: found after retry
  .mockRejectedValueOnce(new Error())   // third call: throws
```

The `Once` variants are essential for testing retry logic, idempotency, and multi-step flows where a dependency behaves differently on successive calls. Using the base (non-`Once`) variant alongside `Once` variants sets the default for all calls after the `Once` sequence is exhausted.

## Section 2: Mocking Services

**Q5. How do you build a fully typed `jest.Mocked<T>` service mock and wire it into `createTestingModule`?**
A: The correct pattern uses `jest.Mocked<T>` for type safety and a typed `let` declaration for access across hooks and tests:

```typescript
import { Test, TestingModule } from '@nestjs/testing';
import { LoanService } from './loan.service';
import { EligibilityService } from '../eligibility/eligibility.service';
import { NotificationService } from '../notification/notification.service';

describe('LoanService', () => {
  let service: LoanService;
  let eligibilityService: jest.Mocked<EligibilityService>;
  let notificationService: jest.Mocked<NotificationService>;

  beforeEach(async () => {
    // Build mocks before module — same references passed to useValue and captured in closure
    eligibilityService = {
      check: jest.fn(),
      getScore: jest.fn(),
    } as jest.Mocked<EligibilityService>;

    notificationService = {
      send: jest.fn(),
      sendBulk: jest.fn(),
    } as jest.Mocked<NotificationService>;

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        LoanService,
        { provide: EligibilityService, useValue: eligibilityService },
        { provide: NotificationService, useValue: notificationService },
      ],
    }).compile();

    service = module.get<LoanService>(LoanService);
  });

  afterEach(() => jest.clearAllMocks());

  it('sends an approval notification when eligibility passes', async () => {
    eligibilityService.check.mockResolvedValue({ eligible: true, score: 750 });
    notificationService.send.mockResolvedValue(undefined);

    await service.processApplication('app-123', 'user-456');

    expect(notificationService.send).toHaveBeenCalledWith(
      'user-456',
      expect.objectContaining({ type: 'LOAN_APPROVED' })
    );
  });

  it('does not send a notification when eligibility fails', async () => {
    eligibilityService.check.mockResolvedValue({ eligible: false, score: 550 });

    await service.processApplication('app-123', 'user-456');

    expect(notificationService.send).not.toHaveBeenCalled();
  });
});
```

The reference identity between the `useValue` object and the `eligibilityService` variable in the closure is what enables you to call `.mockResolvedValue()` inside `it` blocks after the module is compiled. If you build the mock inside the `providers` array literal and don't capture the reference, you lose the ability to configure it per-test.

**Q6. How do you mock a NestJS service that uses `@Inject()` with a string or symbol token?**
A: String and symbol tokens are common for third-party clients, configuration objects, and feature flags. The mock must be provided under the exact same string or symbol:

```typescript
// Production service
@Injectable()
export class CreditBureauService {
  constructor(
    @Inject('CIBIL_HTTP_CLIENT') private readonly httpClient: HttpClient,
    @Inject(BUREAU_CONFIG_TOKEN) private readonly config: BureauConfig,
  ) {}
}

// Test
const mockHttpClient: jest.Mocked<HttpClient> = {
  get: jest.fn(),
  post: jest.fn(),
};

const mockConfig: BureauConfig = {
  baseUrl: 'http://mock-bureau.test',
  apiKey: 'test-key',
  timeoutMs: 3000,
};

const module = await Test.createTestingModule({
  providers: [
    CreditBureauService,
    { provide: 'CIBIL_HTTP_CLIENT', useValue: mockHttpClient },       // string token
    { provide: BUREAU_CONFIG_TOKEN, useValue: mockConfig },           // symbol token
  ],
}).compile();
```

For symbol tokens, import the symbol from its declaration file — never recreate it with `Symbol('name')`. Two `Symbol('name')` calls produce different symbols even with the same description, so the tokens won't match and the mock won't be injected.

**Q7. How do you mock a service that is provided as part of an imported `NestJS` module you don't control?**
A: When a service is declared inside an imported module (e.g., `ConfigModule` provides `ConfigService`, `ScheduleModule` provides `SchedulerRegistry`), you cannot override it by listing it in `providers` — the module's own declaration takes precedence. Use `overrideProvider()` before `.compile()`:

```typescript
const mockConfigService = {
  get: jest.fn((key: string) => ({
    DB_URL: 'postgres://localhost/test',
    JWT_SECRET: 'test-secret',
    MAX_LOAN_AMOUNT: 1000000,
  }[key])),
  getOrThrow: jest.fn((key: string) => {
    const val = { DB_URL: 'postgres://localhost/test' }[key];
    if (!val) throw new Error(`Config key ${key} not found`);
    return val;
  }),
};

const module = await Test.createTestingModule({
  imports: [AppModule],           // ConfigModule is inside AppModule's import tree
})
  .overrideProvider(ConfigService)
  .useValue(mockConfigService)
  .compile();
```

A common refinement: when `ConfigService.get()` is called with many different keys across many services, a dynamic mock implementation that returns test-appropriate values for all keys is cleaner than `mockReturnValue` per call. The factory pattern with a lookup object (`{ KEY: 'value' }[key]`) handles this cleanly.

**Q8. What is `jest.createMockFromModule()` (formerly `jest.genMockFromModule()`), and when is it useful for mocking services?**
A: `jest.createMockFromModule(modulePath)` automatically generates a mock version of a module — all functions replaced with `jest.fn()`, all classes replaced with mocked versions of their methods. It saves the boilerplate of manually listing every method when a service has a large interface:

```typescript
// Auto-generate a mock for a large service
const mockEligibilityService = jest.createMockFromModule<EligibilityService>(
  '../eligibility/eligibility.service'
);

// All methods are jest.fn() automatically — configure only what the test needs
mockEligibilityService.check = jest.fn().mockResolvedValue({ eligible: true });
```

The limitation: `createMockFromModule` reflects the module at import time and may not correctly mock async methods (it doesn't know they're async unless the source declares them with `async`). It's most useful for large, stable interfaces. For most NestJS service mocks in a team codebase, the hand-rolled object literal is preferred — it's explicit about which methods the service under test actually calls, which is itself documentation.

## Section 3: Mocking Repositories

**Q9. How do you mock a TypeORM `Repository<T>` in NestJS, and what methods should you always include?**
A: TypeORM's `Repository<T>` is injected under the token `getRepositoryToken(EntityClass)`. The mock must use this exact token and provide jest functions for every method the service under test calls:

```typescript
import { getRepositoryToken } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Loan } from './loan.entity';

describe('LoanService (unit)', () => {
  let service: LoanService;
  let loanRepo: jest.Mocked<Repository<Loan>>;

  beforeEach(async () => {
    loanRepo = {
      findOne: jest.fn(),
      findOneBy: jest.fn(),
      find: jest.fn(),
      findAndCount: jest.fn(),
      save: jest.fn(),
      create: jest.fn(),
      update: jest.fn(),
      delete: jest.fn(),
      count: jest.fn(),
      createQueryBuilder: jest.fn(),
    } as unknown as jest.Mocked<Repository<Loan>>;

    const module = await Test.createTestingModule({
      providers: [
        LoanService,
        { provide: getRepositoryToken(Loan), useValue: loanRepo },
      ],
    }).compile();

    service = module.get<LoanService>(LoanService);
  });
```

The `as unknown as jest.Mocked<Repository<Loan>>` cast is necessary because `Repository<T>` has many more methods than you mock — TypeScript would reject a partial object literal without the cast. Mock only the methods the service actually calls; adding others is unnecessary noise.

**Q10. How do you mock `createQueryBuilder` for a service that uses the TypeORM query builder?**
A: The query builder uses a fluent chain of method calls — `createQueryBuilder().where().andWhere().orderBy().getMany()`. Each method returns `this`, so the mock must return a self-referential object:

```typescript
// Production code
async findOverdueLoans(daysOverdue: number): Promise<Loan[]> {
  return this.loanRepo
    .createQueryBuilder('loan')
    .where('loan.status = :status', { status: 'ACTIVE' })
    .andWhere('loan.dueDate < :cutoff', { cutoff: subDays(new Date(), daysOverdue) })
    .orderBy('loan.dueDate', 'ASC')
    .getMany();
}

// Test — mock the full query builder chain
const mockQueryBuilder = {
  where: jest.fn().mockReturnThis(),
  andWhere: jest.fn().mockReturnThis(),
  orWhere: jest.fn().mockReturnThis(),
  select: jest.fn().mockReturnThis(),
  leftJoin: jest.fn().mockReturnThis(),
  leftJoinAndSelect: jest.fn().mockReturnThis(),
  orderBy: jest.fn().mockReturnThis(),
  addOrderBy: jest.fn().mockReturnThis(),
  skip: jest.fn().mockReturnThis(),
  take: jest.fn().mockReturnThis(),
  setParameter: jest.fn().mockReturnThis(),
  getMany: jest.fn(),
  getOne: jest.fn(),
  getManyAndCount: jest.fn(),
  getRawMany: jest.fn(),
  getCount: jest.fn(),
};

loanRepo = {
  createQueryBuilder: jest.fn().mockReturnValue(mockQueryBuilder),
} as unknown as jest.Mocked<Repository<Loan>>;

// In the test
mockQueryBuilder.getMany.mockResolvedValue([
  buildLoanFixture({ status: 'ACTIVE', dueDate: subDays(new Date(), 10) }),
]);

const result = await service.findOverdueLoans(5);
expect(result).toHaveLength(1);
```

The `mockReturnThis()` pattern is what enables the method chain — each method returns the same mock object, so the chain resolves to the final terminal method (`getMany`, `getOne`). Mock the terminal method with `mockResolvedValue()` to control what the query "returns."

**Q11. How do you mock a custom repository class (not TypeORM's generic `Repository<T>`) in NestJS?**
A: Custom repositories — classes that extend `Repository<T>` or are plain `@Injectable()` classes wrapping a TypeORM repository — are simpler to mock because their injection token is the class itself, not `getRepositoryToken()`:

```typescript
// Production custom repository
@Injectable()
export class LoanRepository {
  constructor(
    @InjectRepository(Loan)
    private readonly repo: Repository<Loan>,
  ) {}

  async findActiveLoansByUser(userId: string): Promise<Loan[]> {
    return this.repo.find({ where: { userId, status: 'ACTIVE' } });
  }

  async findByIdempotencyKey(key: string): Promise<Loan | null> {
    return this.repo.findOneBy({ idempotencyKey: key });
  }
}

// Test — mock the custom repository class directly
const mockLoanRepository: jest.Mocked<LoanRepository> = {
  findActiveLoansByUser: jest.fn(),
  findByIdempotencyKey: jest.fn(),
  save: jest.fn(),
} as jest.Mocked<LoanRepository>;

const module = await Test.createTestingModule({
  providers: [
    LoanService,
    { provide: LoanRepository, useValue: mockLoanRepository }, // token is the class itself
  ],
}).compile();
```

This is cleaner than mocking `Repository<T>` directly — the custom repository's interface is smaller and domain-specific, so the mock has fewer methods to define and tests are more readable. Pushing the `Repository<T>` complexity behind a custom repository class is a design pattern that pays dividends in testability.

**Q12. How do you mock a Mongoose model in a NestJS service that uses `@InjectModel()`?**
A: Mongoose models are injected under the token `getModelToken(ModelName)` from `@nestjs/mongoose`. The mock must replicate the Mongoose model's chainable query API:

```typescript
import { getModelToken } from '@nestjs/mongoose';
import { Model } from 'mongoose';
import { AuditLog, AuditLogDocument } from './audit-log.schema';

describe('AuditLogService (unit)', () => {
  let service: AuditLogService;
  let auditLogModel: jest.Mocked<Model<AuditLogDocument>>;

  beforeEach(async () => {
    // Mongoose queries are chainable — exec() resolves the query
    const mockQuery = {
      sort: jest.fn().mockReturnThis(),
      limit: jest.fn().mockReturnThis(),
      skip: jest.fn().mockReturnThis(),
      select: jest.fn().mockReturnThis(),
      populate: jest.fn().mockReturnThis(),
      lean: jest.fn().mockReturnThis(),
      exec: jest.fn(),
    };

    auditLogModel = {
      find: jest.fn().mockReturnValue(mockQuery),
      findById: jest.fn().mockReturnValue(mockQuery),
      findOne: jest.fn().mockReturnValue(mockQuery),
      findOneAndUpdate: jest.fn().mockReturnValue(mockQuery),
      create: jest.fn(),
      countDocuments: jest.fn(),
      aggregate: jest.fn(),
      // Constructor — for `new this.auditLogModel(data).save()` pattern
      prototype: { save: jest.fn() },
    } as unknown as jest.Mocked<Model<AuditLogDocument>>;

    const module = await Test.createTestingModule({
      providers: [
        AuditLogService,
        {
          provide: getModelToken(AuditLog.name),  // token from @nestjs/mongoose
          useValue: auditLogModel,
        },
      ],
    }).compile();

    service = module.get<AuditLogService>(AuditLogService);
  });

  it('retrieves audit logs sorted by timestamp descending', async () => {
    const mockLogs = [buildAuditLogFixture(), buildAuditLogFixture()];
    auditLogModel.find().exec.mockResolvedValue(mockLogs);

    const result = await service.getRecentLogs('user-1', 10);

    expect(auditLogModel.find).toHaveBeenCalledWith({ userId: 'user-1' });
    expect(result).toHaveLength(2);
  });
});
```

The `exec()` mock is the terminal method for Mongoose queries — always mock it with `mockResolvedValue()`. The chainable methods (`sort`, `limit`, `lean`) use `mockReturnThis()` so the chain resolves correctly.

## Section 4: Fake Implementations

**Q13. When should you use a fake (in-memory implementation) instead of a `jest.fn()` mock for a repository?**
A: Use a fake when the test needs the dependency to behave with real logic — not just return a hardcoded value. The signal: when you find yourself writing a sequence of `mockResolvedValueOnce` calls that model state (save, then read back, then update, then read again), a fake is cleaner and more representative:

```typescript
// Fake in-memory LoanRepository
class FakeLoanRepository implements Partial<LoanRepository> {
  private store = new Map<string, Loan>();

  async save(loan: Loan): Promise<Loan> {
    const saved = { ...loan, id: loan.id ?? randomUUID() };
    this.store.set(saved.id, saved);
    return saved;
  }

  async findById(id: string): Promise<Loan | null> {
    return this.store.get(id) ?? null;
  }

  async findAll(): Promise<Loan[]> {
    return Array.from(this.store.values());
  }

  async delete(id: string): Promise<void> {
    this.store.delete(id);
  }

  // Reset between tests
  clear(): void {
    this.store.clear();
  }
}

// Usage in tests
describe('LoanApprovalService', () => {
  let fakeLoanRepo: FakeLoanRepository;
  let service: LoanApprovalService;

  beforeEach(async () => {
    fakeLoanRepo = new FakeLoanRepository();

    const module = await Test.createTestingModule({
      providers: [
        LoanApprovalService,
        { provide: LoanRepository, useValue: fakeLoanRepo },
      ],
    }).compile();

    service = module.get<LoanApprovalService>(LoanApprovalService);
  });

  afterEach(() => fakeLoanRepo.clear());

  it('cannot approve a loan that is already approved', async () => {
    // The fake actually stores and retrieves — this tests real state flow
    const loan = await fakeLoanRepo.save(buildLoanFixture({ status: 'APPROVED' }));

    await expect(service.approve(loan.id)).rejects.toThrow('Loan is already approved');
  });
});
```

Fakes are most valuable when: the business logic involves reading state previously written by the same service (event sourcing, state machine transitions, idempotency checks), multiple service methods interact through a shared repository within one test, or the test verifies a sequence of operations rather than a single call.

**Q14. How do you build a fake that resets cleanly between tests without leaking state?**
A: Two patterns, depending on whether the module is created in `beforeAll` or `beforeEach`:

**Pattern 1 — `beforeEach` module creation (simplest):**
```typescript
beforeEach(async () => {
  fakeLoanRepo = new FakeLoanRepository(); // fresh instance every test
  // ... build module with new instance
});
```
A new instance per test means zero state leakage. The cost: module compilation on every test (acceptable for unit tests; too slow for integration tests).

**Pattern 2 — `beforeAll` module creation + explicit reset:**
```typescript
beforeAll(async () => {
  fakeLoanRepo = new FakeLoanRepository();
  // ... build module once
});

afterEach(() => {
  fakeLoanRepo.clear(); // explicit reset — call before each test
});
```

Add a `clear()` or `reset()` method to the fake that wipes all internal state. If the fake has multiple stores (e.g., `loans`, `users`, `events`), `clear()` must wipe all of them. Document the method with a comment — it exists only for testing and should not be on the production interface.

## Section 5: Spying on Real Implementations

**Q15. How do you use `jest.spyOn()` in the context of `createTestingModule`, and when is it preferable to a full mock?**
A: `jest.spyOn(object, 'method')` wraps an existing method on an object — the original implementation still runs unless you also call `.mockImplementation()`. In a `createTestingModule` context, use it when you want to observe calls to a real service method without replacing its logic:

```typescript
describe('LoanService', () => {
  let service: LoanService;
  let eligibilityService: EligibilityService; // real instance

  beforeEach(async () => {
    const module = await Test.createTestingModule({
      providers: [LoanService, EligibilityService, /* real deps of EligibilityService */],
    }).compile();

    service = module.get<LoanService>(LoanService);
    eligibilityService = module.get<EligibilityService>(EligibilityService);
  });

  it('calls eligibility check with the correct PAN', async () => {
    const spy = jest.spyOn(eligibilityService, 'check');
    // Real eligibilityService.check() runs — but we can assert on the call
    await service.processApplication({ pan: 'ABCDE1234F', amount: 500000 });
    expect(spy).toHaveBeenCalledWith('ABCDE1234F', 500000);
  });
});
```

Prefer `jest.spyOn()` over full mocks when: the real implementation is fast and has no I/O (pure computation, format validation), you want to verify that the service calls a dependency with exact arguments while still getting a real return value, or you are testing a method that should *not* be called and want to assert zero invocations on the real object.

Always call `jest.restoreAllMocks()` in `afterEach` (or configure `restoreMocks: true` in `jest.config.ts`) — without it, spies on real objects persist into subsequent tests and the original implementation is never restored.

**Q16. How do you spy on a private method in a NestJS service, and when is doing so a design smell?**
A: TypeScript's `private` keyword is compile-time only — at runtime, the method is a regular property. You can spy on it by casting to `any`:

```typescript
const calculateFeeSpy = jest.spyOn(service as any, 'calculateProcessingFee');
```

But doing so is almost always a design smell. A private method is an implementation detail — its existence, name, and signature are subject to change without it being a breaking change to the service's public contract. A test that asserts on a private method is coupled to the implementation, not the behaviour. If the test breaks when you rename `calculateProcessingFee` to `computeFee`, the test is wrong, not the refactoring.

The correct alternative: test the private method's effect through the public method that calls it. If the private method is complex enough that it needs its own dedicated test, that is a signal it should be extracted into a separate class — which can then be tested directly and injected as a dependency.

**Q17. How do you assert that a mocked method was NOT called, and when is this assertion meaningful?**
A: Use `expect(mock).not.toHaveBeenCalled()` or `expect(mock).not.toHaveBeenCalledWith(args)`:

```typescript
it('does not charge a processing fee for pre-approved customers', async () => {
  eligibilityService.check.mockResolvedValue({ eligible: true, preApproved: true });

  await service.processApplication('user-vip-1', 500000);

  expect(feeCalculator.calculate).not.toHaveBeenCalled();
  expect(notificationService.send).toHaveBeenCalledWith(
    'user-vip-1',
    expect.objectContaining({ feeWaived: true })
  );
});
```

This assertion is meaningful when: the service has branching logic where one path skips a step, and you want to verify the skip (not just the final result). It is less meaningful when: you're asserting that *every* mock was not called in a test that does nothing — that's a tautology. The signal for a good "not called" assertion: there is production code with an `if` condition that, when true, bypasses the mocked dependency. The assertion documents and protects that conditional bypass.

## Section 6: Advanced Mocking Patterns

**Q18. How do you mock a NestJS `EventEmitter2` or custom event bus to test that events are published correctly?**
A: Event buses are straightforward to mock because their interface is narrow — typically `emit(event, payload)` or `publish(event)`:

```typescript
import { EventEmitter2 } from '@nestjs/event-emitter';

describe('LoanService', () => {
  let mockEventEmitter: jest.Mocked<EventEmitter2>;

  beforeEach(async () => {
    mockEventEmitter = {
      emit: jest.fn(),
      emitAsync: jest.fn().mockResolvedValue([]),
      on: jest.fn(),
      off: jest.fn(),
    } as unknown as jest.Mocked<EventEmitter2>;

    const module = await Test.createTestingModule({
      providers: [
        LoanService,
        { provide: EventEmitter2, useValue: mockEventEmitter },
        { provide: LoanRepository, useValue: mockLoanRepo },
      ],
    }).compile();

    service = module.get<LoanService>(LoanService);
  });

  it('emits loan.approved event with the correct payload', async () => {
    mockLoanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'PENDING' }));
    mockLoanRepo.save.mockResolvedValue(buildLoanFixture({ status: 'APPROVED' }));

    await service.approveLoan('loan-123');

    expect(mockEventEmitter.emitAsync).toHaveBeenCalledWith(
      'loan.approved',
      expect.objectContaining({
        loanId: 'loan-123',
        approvedAt: expect.any(Date),
      })
    );
  });
});
```

For Kafka producers or SNS publishers, the same pattern applies — mock the `publish` or `send` method and assert on the payload. Asserting on the event payload with `expect.objectContaining()` instead of exact object equality allows the service to add non-breaking new fields without failing the test.

**Q19. How do you mock `HttpService` (Axios wrapper) in NestJS for services that make external HTTP calls?**
A: NestJS's `HttpService` wraps Axios and returns RxJS `Observable`s. The mock must return an observable, not a plain promise:

```typescript
import { HttpService } from '@nestjs/axios';
import { of, throwError } from 'rxjs';
import { AxiosResponse } from 'axios';

describe('BureauAdapterService', () => {
  let service: BureauAdapterService;
  let mockHttpService: jest.Mocked<HttpService>;

  beforeEach(async () => {
    mockHttpService = {
      get: jest.fn(),
      post: jest.fn(),
      axiosRef: {} as any,
    } as unknown as jest.Mocked<HttpService>;

    const module = await Test.createTestingModule({
      providers: [
        BureauAdapterService,
        { provide: HttpService, useValue: mockHttpService },
      ],
    }).compile();

    service = module.get<BureauAdapterService>(BureauAdapterService);
  });

  it('returns the credit score from the bureau API', async () => {
    const mockResponse: AxiosResponse = {
      data: { pan: 'ABCDE1234F', score: 750, bureau: 'CIBIL' },
      status: 200,
      statusText: 'OK',
      headers: {},
      config: {} as any,
    };

    mockHttpService.get.mockReturnValue(of(mockResponse)); // RxJS Observable, not a Promise

    const result = await service.getCreditScore('ABCDE1234F');

    expect(result.score).toBe(750);
    expect(mockHttpService.get).toHaveBeenCalledWith(
      'https://bureau.api/credit-score/ABCDE1234F',
      expect.objectContaining({ headers: expect.objectContaining({ 'X-Api-Key': expect.any(String) }) })
    );
  });

  it('throws a BureauUnavailableException when the API returns a 503', async () => {
    mockHttpService.get.mockReturnValue(
      throwError(() => ({ response: { status: 503 } }))  // RxJS error observable
    );

    await expect(service.getCreditScore('ABCDE1234F')).rejects.toThrow(BureauUnavailableException);
  });
});
```

`of(mockResponse)` creates an observable that emits one value and completes. `throwError(() => error)` creates an observable that immediately errors. These are the two RxJS primitives needed for the vast majority of `HttpService` mock scenarios.

**Q20. How do you mock a service that uses `ConfigService` with many different keys, and what pattern avoids brittle per-call stubs?**
A: Mocking `ConfigService` with individual `mockReturnValue` calls per key is fragile — adding a new `configService.get('NEW_KEY')` call in the service breaks every existing test because the mock doesn't know about `NEW_KEY`. The robust pattern is a lookup-based mock implementation:

```typescript
// Fragile — breaks when service adds a new config key
mockConfigService.get.mockReturnValueOnce('postgres://test');
mockConfigService.get.mockReturnValueOnce('3000');
// Third call returns undefined — silently wrong

// Robust — handles any key, returns undefined for unknown keys
const testConfig: Record<string, any> = {
  DB_URL: 'postgres://localhost:5432/testdb',
  REDIS_URL: 'redis://localhost:6379',
  JWT_SECRET: 'test-jwt-secret',
  MAX_LOAN_AMOUNT: 1_000_000,
  BUREAU_API_KEY: 'test-bureau-key',
  NACH_GATEWAY_URL: 'http://nach.test',
};

mockConfigService = {
  get: jest.fn((key: string) => testConfig[key]),
  getOrThrow: jest.fn((key: string) => {
    if (testConfig[key] === undefined) throw new Error(`Missing config: ${key}`);
    return testConfig[key];
  }),
} as jest.Mocked<ConfigService>;
```

Keep the `testConfig` object in a shared test helper file — all unit tests import the same config map, so adding a new key to the production service is a one-line change in the shared helper, not a change in every test file.

## Section 7: Pitfalls and Anti-patterns

**Q21. What is "mock drift," and how does it cause tests to pass while production is broken?**
A: Mock drift is when the mock's interface diverges from the real dependency's interface over time. The service under test calls `bureauClient.fetchCreditScore(pan)`, but the real `BureauClient` was refactored to `bureauClient.getScore({ pan, includeHistory: false })` — the mock still has `fetchCreditScore`, the test still passes, and production calls the nonexistent method and throws `TypeError: bureauClient.fetchCreditScore is not a function`.

The causes: mocks built as plain object literals without TypeScript enforcement, real service interfaces changed without updating tests, or mocks in a separate file that no one remembers to update. Prevention:
- Always type mocks as `jest.Mocked<RealInterface>` — TypeScript enforces that the mock's methods match the real interface.
- Enable `strict: true` in `tsconfig.json` — missing mock methods produce compile errors.
- Use `jest.createMockFromModule()` for large, stable interfaces — it auto-reflects the current interface.
- Contract testing (Pact) for cross-service mocks — the provider's real implementation is verified against the consumer's recorded expectations.

**Q22. What is the "mock everything" anti-pattern, and how does it produce tests that always pass?**
A: The "mock everything" anti-pattern is when a test mocks every dependency — including the class under test's own internal calls — such that the test only verifies that mocks were called, not that the system produces correct output. The test becomes a mirror of the implementation:

```typescript
// Anti-pattern — tests implementation, not behaviour
it('processes a loan application', async () => {
  jest.spyOn(service as any, 'validateApplication').mockResolvedValue(true);
  jest.spyOn(service as any, 'runEligibilityCheck').mockResolvedValue({ eligible: true });
  jest.spyOn(service as any, 'persistApplication').mockResolvedValue(savedApp);
  jest.spyOn(service as any, 'publishEvent').mockResolvedValue(undefined);

  await service.processApplication(dto);

  expect((service as any).validateApplication).toHaveBeenCalled();
  expect((service as any).runEligibilityCheck).toHaveBeenCalled();
  expect((service as any).persistApplication).toHaveBeenCalled();
  expect((service as any).publishEvent).toHaveBeenCalled();
});
```

This test would still pass if `processApplication` returned `null` — because it only checks that private methods were called, not what the method produced. The correct approach: mock only external dependencies (repositories, HTTP clients, event buses), let the service's internal logic run, and assert on the observable output (return value, repository calls with specific payloads, events emitted with specific content).

**Q23. Why does `jest.clearAllMocks()` not restore spies, and what happens if you forget `jest.restoreAllMocks()`?**
A: `jest.clearAllMocks()` resets mock call history and return values — it does not restore the original implementation of a `jest.spyOn()` spy. `jest.restoreAllMocks()` does both — it clears history and restores the original method. The failure mode of forgetting `restoreAllMocks()`:

```typescript
it('test A — spies on the real method', () => {
  jest.spyOn(emailService, 'send').mockImplementation(() => undefined);
  // test passes
}); // spy is NOT restored after this test

it('test B — expects real method to run', async () => {
  await notificationService.notifyUser('user-1'); // calls emailService.send internally
  // emailService.send is still mocked from test A — the real send() never runs
  // test may pass or fail depending on whether it asserts on send's side effects
});
```

Configure `restoreMocks: true` in `jest.config.ts` to restore all spies automatically after each test — this is the correct default for any codebase that uses `jest.spyOn()`. With `restoreMocks: true`, you never need to call `jest.restoreAllMocks()` manually in `afterEach`. Combine with `clearMocks: true` and `resetMocks: false` for the most common safe configuration.

**Q24. What is the danger of using `mockResolvedValue` on a mock that is called multiple times in the same service method, and how do you handle it?**
A: `mockResolvedValue(value)` sets the return value for *every* call to the mock function for the remainder of the test. If a service method calls the same repository method twice — once to check existence, once to fetch details — a single `mockResolvedValue` returns the same object for both calls, which may not reflect realistic behaviour:

```typescript
// Service calls loanRepo.findOneBy() twice:
// 1. Check if loan exists (expects null if not found)
// 2. Fetch loan after creating it (expects the created loan)

// Wrong — both calls return the same value
loanRepo.findOneBy.mockResolvedValue(buildLoanFixture()); // both calls get the fixture

// Correct — sequence the return values
loanRepo.findOneBy
  .mockResolvedValueOnce(null)                     // first call: loan doesn't exist yet
  .mockResolvedValueOnce(buildLoanFixture({ id: 'loan-new' })); // second: after creation
```

The `Once` variants are essential for any service method that calls the same dependency function more than once with different expected results. Ignoring this produces tests that pass for the wrong reason — the second call gets the first call's return value, masking the fact that the service might not even make the second call.

## Section 8: Scenario / System Design Style Questions

**Q25. "You're writing a unit test for a `DisbursementService.disburse()` method that: checks idempotency via Redis, fetches the loan from PostgreSQL, calls an external NACH gateway, updates the loan status in PostgreSQL, and publishes a Kafka event. How do you structure the mocks?"**
A: Each dependency is mocked at its interface boundary, independently:

```typescript
describe('DisbursementService.disburse()', () => {
  let service: DisbursementService;
  let idempotencyCache: jest.Mocked<IdempotencyCacheService>;
  let loanRepo: jest.Mocked<LoanRepository>;
  let nachGateway: jest.Mocked<NachGatewayClient>;
  let kafkaProducer: jest.Mocked<KafkaProducer>;

  beforeEach(async () => {
    idempotencyCache = {
      get: jest.fn(),
      set: jest.fn(),
      delete: jest.fn(),
    } as jest.Mocked<IdempotencyCacheService>;

    loanRepo = {
      findById: jest.fn(),
      updateStatus: jest.fn(),
    } as jest.Mocked<LoanRepository>;

    nachGateway = {
      initiate: jest.fn(),
      getStatus: jest.fn(),
    } as jest.Mocked<NachGatewayClient>;

    kafkaProducer = {
      publish: jest.fn().mockResolvedValue(undefined),
    } as jest.Mocked<KafkaProducer>;

    const module = await Test.createTestingModule({
      providers: [
        DisbursementService,
        { provide: IdempotencyCacheService, useValue: idempotencyCache },
        { provide: LoanRepository, useValue: loanRepo },
        { provide: NachGatewayClient, useValue: nachGateway },
        { provide: KafkaProducer, useValue: kafkaProducer },
      ],
    }).compile();

    service = module.get<DisbursementService>(DisbursementService);
  });

  afterEach(() => jest.clearAllMocks());

  describe('idempotency', () => {
    it('returns the cached result without calling the gateway for a duplicate request', async () => {
      const cached = buildDisbursementResult({ status: 'SUCCESS' });
      idempotencyCache.get.mockResolvedValue(cached);

      const result = await service.disburse('loan-123', 'idem-key-1');

      expect(result).toEqual(cached);
      expect(nachGateway.initiate).not.toHaveBeenCalled();
      expect(kafkaProducer.publish).not.toHaveBeenCalled();
    });
  });

  describe('happy path', () => {
    beforeEach(() => {
      idempotencyCache.get.mockResolvedValue(null); // no cached result
      loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'APPROVED', amount: 500000 }));
      nachGateway.initiate.mockResolvedValue({ reference: 'nach-ref-1', status: 'ACCEPTED' });
      loanRepo.updateStatus.mockResolvedValue(undefined);
    });

    it('calls the NACH gateway with the correct loan amount', async () => {
      await service.disburse('loan-123', 'idem-key-2');
      expect(nachGateway.initiate).toHaveBeenCalledWith(
        expect.objectContaining({ amount: 500000, loanId: 'loan-123' })
      );
    });

    it('updates loan status to DISBURSED after gateway accepts', async () => {
      await service.disburse('loan-123', 'idem-key-2');
      expect(loanRepo.updateStatus).toHaveBeenCalledWith('loan-123', 'DISBURSED');
    });

    it('publishes a disbursement.completed Kafka event', async () => {
      await service.disburse('loan-123', 'idem-key-2');
      expect(kafkaProducer.publish).toHaveBeenCalledWith(
        expect.objectContaining({
          type: 'disbursement.completed',
          loanId: 'loan-123',
          gatewayReference: 'nach-ref-1',
        })
      );
    });

    it('caches the result for idempotency after success', async () => {
      await service.disburse('loan-123', 'idem-key-2');
      expect(idempotencyCache.set).toHaveBeenCalledWith(
        'idem-key-2',
        expect.objectContaining({ status: 'SUCCESS' }),
        expect.any(Number) // TTL
      );
    });
  });

  describe('failure paths', () => {
    it('does not update loan status when the gateway rejects', async () => {
      idempotencyCache.get.mockResolvedValue(null);
      loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'APPROVED' }));
      nachGateway.initiate.mockRejectedValue(new Error('NACH_TIMEOUT'));

      await expect(service.disburse('loan-123', 'idem-key-3')).rejects.toThrow('NACH_TIMEOUT');

      expect(loanRepo.updateStatus).not.toHaveBeenCalled();
      expect(kafkaProducer.publish).not.toHaveBeenCalledWith(
        expect.objectContaining({ type: 'disbursement.completed' })
      );
    });

    it('throws when the loan is not in APPROVED status', async () => {
      idempotencyCache.get.mockResolvedValue(null);
      loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'PENDING' }));

      await expect(service.disburse('loan-123', 'idem-key-4'))
        .rejects.toThrow('Loan must be in APPROVED status to disburse');

      expect(nachGateway.initiate).not.toHaveBeenCalled();
    });
  });
});
```

The structure: one `describe` per logical scenario (idempotency, happy path, failure paths). Shared happy-path mock setup in an inner `beforeEach` so individual happy-path tests don't repeat setup. Each test asserts on exactly one observable outcome. `not.toHaveBeenCalled()` assertions on downstream mocks verify that failed paths short-circuit correctly.

**Q26. "You inherit a codebase where service tests have 30+ lines of mock setup in each `it` block, repeated across 40 tests. How do you refactor this into maintainable mock infrastructure?"**
A: A systematic refactoring in four steps:

**Step 1 — Extract builder functions for mock objects:**
```typescript
// test/builders/loan.builder.ts
export function buildLoanFixture(overrides: Partial<Loan> = {}): Loan {
  return {
    id: 'loan-default-id',
    userId: 'user-default',
    amount: 100000,
    status: 'PENDING',
    createdAt: new Date('2025-01-01'),
    ...overrides,
  };
}
```

**Step 2 — Extract shared mock factories:**
```typescript
// test/mocks/loan-repo.mock.ts
export function createMockLoanRepository(): jest.Mocked<LoanRepository> {
  return {
    findById: jest.fn(),
    save: jest.fn(),
    updateStatus: jest.fn(),
    findActiveLoansByUser: jest.fn(),
  } as jest.Mocked<LoanRepository>;
}

// test/mocks/nach-gateway.mock.ts
export function createMockNachGateway(): jest.Mocked<NachGatewayClient> {
  return {
    initiate: jest.fn(),
    getStatus: jest.fn(),
  } as jest.Mocked<NachGatewayClient>;
}
```

**Step 3 — Move default happy-path setups to `beforeEach`:**
```typescript
beforeEach(() => {
  // Default: happy path — individual tests override only what differs
  loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'APPROVED' }));
  nachGateway.initiate.mockResolvedValue({ reference: 'ref-1', status: 'ACCEPTED' });
  kafkaProducer.publish.mockResolvedValue(undefined);
});
```

**Step 4 — Use `describe` nesting to group tests by scenario, each with targeted overrides:**
```typescript
describe('when the loan is PENDING (not approvable)', () => {
  beforeEach(() => {
    // Override just the part that differs — everything else stays from the outer beforeEach
    loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'PENDING' }));
  });

  it('throws InvalidStatusException', async () => { ... });
  it('does not call the gateway', async () => { ... });
});
```

The result: each `it` block contains only the assertion. Setup is in `beforeEach` at the right scope level. Mock factories are importable across test files. Fixture builders handle entity construction. The 30-line setup per `it` collapses to 1–3 lines of targeted overrides.

## Quick Reference: Mocking Patterns by Dependency Type

| Dependency type                     | Token to mock                          | Mock pattern                                             |
|-------------------------------------|----------------------------------------|----------------------------------------------------------|
| NestJS `@Injectable()` service      | Class reference                        | `{ provide: ServiceClass, useValue: mockObj }`           |
| TypeORM `Repository<T>`             | `getRepositoryToken(Entity)`           | `{ provide: getRepositoryToken(Entity), useValue: mockRepo }` |
| Custom repository class             | Class reference                        | `{ provide: CustomRepo, useValue: mockObj }`             |
| Mongoose `Model<T>`                 | `getModelToken(Model.name)`            | `{ provide: getModelToken(Model.name), useValue: mockModel }` |
| String/symbol token (`@Inject()`)   | Exact string or symbol                 | `{ provide: 'TOKEN', useValue: mockObj }`                |
| `ConfigService`                     | `ConfigService`                        | Lookup-based mock implementation                         |
| `HttpService` (Axios/RxJS)          | `HttpService`                          | `mockReturnValue(of(axiosResponse))`                     |
| `EventEmitter2`                     | `EventEmitter2`                        | Mock `emit` / `emitAsync` methods                        |
| Provider in imported module         | Any token (use `overrideProvider`)     | `.overrideProvider(Token).useValue(mock)`                |
| Guard                               | Guard class (use `overrideGuard`)      | `.overrideGuard(Guard).useValue({ canActivate: ... })`   |
| `DataSource` (TypeORM transactions) | `DataSource`                           | Mock `createQueryRunner()` chain with `mockReturnThis()` |
| Query builder                       | Returned by `createQueryBuilder()`     | Chainable mock with `mockReturnThis()` + terminal mock   |

---

**Tip for the interview:** At 5 YOE, mocking questions come wrapped in real scenarios — "why does this test pass when the service is broken," "how do you test a method that calls the same repository function twice," "what's wrong with mocking private methods." The answer structure that lands at this level is always: identify the dependency boundary, use the correct injection token, type the mock as `jest.Mocked<Interface>` so TypeScript enforces interface compliance, configure return values as close to the assertion as possible using `mockResolvedValueOnce` for sequential calls, and assert on observable output rather than internal call wiring. Have a concrete story ready — mock drift you caught by typing mocks properly, a query builder chain you debugged by adding `mockReturnThis()`, or a `ConfigService` mock refactor that eliminated 200 lines of per-test stub setup. That's the answer that lands at this level.
