# JavaScript / Testing: E2E Tests with `@nestjs/testing` + Supertest — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the difference between a unit test, an integration test, and an E2E test in a NestJS context?**
A: The distinction matters more in NestJS than in a plain Express app because NestJS has an explicit module system that creates natural test boundaries:

- **Unit test** — a single class (service, guard, pipe, interceptor) tested in isolation. All dependencies are replaced with Jest mocks. The NestJS DI container is not involved at all — you instantiate the class directly with mocked constructor arguments.
- **Integration test** — a subset of the NestJS module graph is instantiated using `@nestjs/testing`. Real classes wire together, but some dependencies (external APIs, databases) are replaced with test doubles. You test that the module's internal wiring is correct — services call repositories correctly, guards interact with services correctly — without going through HTTP.
- **E2E test** — the full NestJS application boots, including the HTTP adapter (Express or Fastify), all middleware, guards, pipes, interceptors, and exception filters. HTTP requests are fired against the running app using Supertest. The test observes the application from the outside — exactly as a real client would.

The `@nestjs/testing` module is used for both integration and E2E tests; the difference is whether you boot a full HTTP server (E2E) or just instantiate the module graph (integration).

**Q2. What is `@nestjs/testing`, and what problem does it solve?**
A: `@nestjs/testing` provides a `TestingModule` builder — `Test.createTestingModule()` — that spins up the NestJS dependency injection container in a test environment, without starting a real HTTP server. It solves the problem of instantiating the DI container outside of a `main.ts` bootstrap: in production, `NestFactory.create(AppModule)` starts the full server; in tests, `Test.createTestingModule()` builds the same module graph but gives you programmatic control over overrides, and returns the app reference so you can attach Supertest.

```js
// Production bootstrap (main.ts)
const app = await NestFactory.create(AppModule);
await app.listen(3000);

// Test bootstrap (@nestjs/testing)
const moduleRef = await Test.createTestingModule({
  imports: [AppModule],
}).compile();

const app = moduleRef.createNestApplication();
await app.init(); // boots the app without binding to a port
```

The test app is functionally identical to the production app — same middleware, same guards, same pipes — but it listens on no port and is controlled entirely by Supertest.

**Q3. What is Supertest, and how does it interact with the NestJS test application?**
A: Supertest is an HTTP assertion library built on top of `superagent`. It accepts a Node.js `http.Server` instance (or an Express/Fastify app) and fires real HTTP requests against it — without binding to a port. Requests go through the full HTTP stack (routing, middleware, body parsing, response serialization) as they would in production.

```js
import * as request from "supertest";

// request(app.getHttpServer()) returns a Supertest agent bound to the NestJS HTTP server
const response = await request(app.getHttpServer())
  .post("/users")
  .send({ name: "Alice", email: "alice@example.com" })
  .expect(201);

expect(response.body).toMatchObject({ name: "Alice" });
```

`app.getHttpServer()` returns the underlying `http.Server` that NestJS created internally. Supertest intercepts the server's request handling before any port binding — making tests fast (no TCP overhead) and port-collision-free (no `EADDRINUSE` errors when tests run in parallel).

**Q4. What is the lifecycle of a NestJS E2E test suite?**
A: Five phases, each with corresponding Jest hooks:

```
beforeAll  → build the module, init the app, run migrations, seed data
beforeEach → reset test state (truncate tables / rollback transaction)
  test     → fire HTTP request via Supertest, assert response + DB state
afterEach  → cleanup if not using transaction rollback
afterAll   → close the app (triggers OnModuleDestroy), destroy DB pool, stop containers
```

The most expensive phase is `beforeAll` — booting the NestJS module graph, connecting to the database, and running migrations. This is why the app is created once per suite (in `beforeAll`) and shared across all tests, rather than recreated per test. Recreating per test would multiply boot time by the number of tests, making the suite impractically slow.

## Section 2: Setting Up the Test Module

**Q5. How do you bootstrap a full NestJS application for E2E testing?**
A:

```js
// test/app.e2e-spec.ts
import { Test, TestingModule }   from "@nestjs/testing";
import { INestApplication }      from "@nestjs/common";
import { AppModule }             from "../src/app.module";
import * as request              from "supertest";

describe("AppController (e2e)", () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleRef: TestingModule = await Test.createTestingModule({
      imports: [AppModule],   // import the real root module
    }).compile();

    app = moduleRef.createNestApplication();

    // Register the same global middleware, pipes, filters as main.ts
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
    app.useGlobalFilters(new HttpExceptionFilter());
    app.setGlobalPrefix("api");

    await app.init();
  });

  afterAll(async () => {
    await app.close(); // triggers OnModuleDestroy on all providers
  });

  it("GET /api/health returns 200", async () => {
    await request(app.getHttpServer())
      .get("/api/health")
      .expect(200)
      .expect({ status: "ok" });
  });
});
```

**Q6. Why must you manually re-register global pipes, filters, and interceptors in the test bootstrap, and how do you avoid the duplication?**
A: NestJS's global middleware registered in `main.ts` via `app.useGlobalPipes()`, `app.useGlobalFilters()`, and `app.useGlobalInterceptors()` is applied to the application instance, not the module. When you create a new application instance for testing, that instance starts fresh — the `main.ts` registrations don't transfer.

The duplication is a real maintenance risk: if you add a global pipe in `main.ts` but forget to add it to the test bootstrap, E2E tests run without it — they pass on inputs that the real application would reject.

**The solution — extract bootstrap configuration into a shared function:**

```js
// src/app.setup.ts — single source of truth for app configuration
import { INestApplication, ValidationPipe } from "@nestjs/common";
import { HttpExceptionFilter }              from "./common/filters/http-exception.filter";

export function configureApp(app: INestApplication): void {
  app.useGlobalPipes(
    new ValidationPipe({ whitelist: true, transform: true, forbidNonWhitelisted: true })
  );
  app.useGlobalFilters(new HttpExceptionFilter());
  app.setGlobalPrefix("api/v1");
  app.enableCors({ origin: process.env.ALLOWED_ORIGIN });
}
```

```js
// src/main.ts
const app = await NestFactory.create(AppModule);
configureApp(app);
await app.listen(3000);

// test/setup/createTestApp.ts
export async function createTestApp(module: TestingModule): Promise<INestApplication> {
  const app = module.createNestApplication();
  configureApp(app); // same function — guaranteed parity
  await app.init();
  return app;
}
```

**Q7. How do you override a specific provider (e.g., a database connection or an external API client) in the test module?**
A: Use `.overrideProvider()` on the `TestingModule` builder before calling `.compile()`:

```js
const moduleRef = await Test.createTestingModule({
  imports: [AppModule],
})
  .overrideProvider(DatabaseService)
  .useValue(testDatabaseService)       // replace with a test double

  .overrideProvider(StripeService)
  .useValue({ charge: jest.fn().mockResolvedValue({ id: "ch_test" }) })

  .overrideProvider(getRepositoryToken(User)) // TypeORM repository token
  .useValue(mockUserRepository)

  .compile();
```

Three override strategies:
- **`useValue`** — replace with a static object or Jest mock. Best for external services you don't want to call in tests.
- **`useClass`** — replace with an alternative class. Best when you want a fake implementation with real logic (an in-memory repository).
- **`useFactory`** — replace with a factory function that receives injected dependencies. Best when the override itself has dependencies.

**Q8. How do you retrieve a provider instance from the test module after compilation?**
A: Use `moduleRef.get()` — it pulls the provider out of the DI container by its injection token:

```js
// Retrieve a service to configure it or assert on it
const usersService = moduleRef.get<UsersService>(UsersService);

// Retrieve a repository (TypeORM token)
const userRepository = moduleRef.get<Repository<User>>(getRepositoryToken(User));

// Retrieve a mocked provider and configure it per-test
const stripeService = moduleRef.get<StripeService>(StripeService);
jest.spyOn(stripeService, "charge").mockResolvedValue({ id: "ch_test_123" });
```

`moduleRef.get()` looks up providers in the root module context. For providers scoped to a request or specific submodule, use `moduleRef.resolve()` — which creates a new DI sub-context and is `async`.

## Section 3: Writing E2E Tests

**Q9. What is the full anatomy of a Supertest assertion?**
A: A Supertest call is a fluent chain that builds the request, fires it, and asserts on the response:

```js
const response = await request(app.getHttpServer())
  // ── Request builder ─────────────────────────────
  .post("/api/v1/users")                          // method + path
  .set("Authorization", `Bearer ${token}`)        // headers
  .set("Accept", "application/json")
  .send({ name: "Alice", email: "alice@example.com" }) // body (auto-sets Content-Type: application/json)
  .query({ locale: "en" })                        // query string params

  // ── Response assertions (checked before the Promise resolves) ──
  .expect(201)                                    // status code
  .expect("Content-Type", /application\/json/)    // header regex
  .expect({ id: 1, name: "Alice" });              // exact body match

// ── Further assertions on the response object ────
expect(response.body).toMatchObject({
  name:      "Alice",
  email:     "alice@example.com",
  id:        expect.any(Number),
  createdAt: expect.any(String),
});
expect(response.headers["location"]).toMatch(/\/api\/v1\/users\/\d+/);
```

The `.expect()` calls chained on the Supertest fluent API throw if the assertion fails, before the Promise resolves. Assertions on `response.body` with Jest matchers happen after `await` and give richer error messages (full Jest diff output).

**Q10. How do you test authenticated endpoints that require a JWT?**
A: Two approaches depending on how deep you want the test to go:

**Approach 1 — generate a real token using the same AuthService:**
```js
let jwtToken: string;

beforeAll(async () => {
  // ... create app ...

  // Generate a real JWT using the app's own auth service
  const authService = moduleRef.get<AuthService>(AuthService);
  jwtToken = await authService.signIn({ email: "test@example.com", password: "secret" });
});

it("GET /api/users/me returns the authenticated user", async () => {
  await request(app.getHttpServer())
    .get("/api/users/me")
    .set("Authorization", `Bearer ${jwtToken}`)
    .expect(200)
    .expect(res => {
      expect(res.body.email).toBe("test@example.com");
    });
});
```

**Approach 2 — mock the JWT guard for tests that don't care about auth:**
```js
const moduleRef = await Test.createTestingModule({
  imports: [AppModule],
})
  .overrideGuard(JwtAuthGuard)
  .useValue({ canActivate: () => true }) // always allow
  .compile();
```

Approach 1 is preferred for auth-specific tests and integration confidence. Approach 2 is useful when the test is about business logic, not authentication, and you don't want JWT setup to obscure the test's intent.

**Q11. How do you test request validation — that your DTOs reject invalid input?**
A: Fire requests with invalid payloads and assert on the 400 response body. This is one of the most valuable E2E tests because it verifies that `ValidationPipe` is correctly configured and that DTO decorators are wired up:

```js
describe("POST /api/users — validation", () => {
  it("returns 400 when email is missing", async () => {
    const res = await request(app.getHttpServer())
      .post("/api/users")
      .send({ name: "Alice" }) // no email
      .expect(400);

    expect(res.body).toMatchObject({
      statusCode: 400,
      message:    expect.arrayContaining([expect.stringContaining("email")]),
    });
  });

  it("returns 400 when email format is invalid", async () => {
    const res = await request(app.getHttpServer())
      .post("/api/users")
      .send({ name: "Alice", email: "not-an-email" })
      .expect(400);

    expect(res.body.message).toEqual(
      expect.arrayContaining([expect.stringContaining("email must be an email")])
    );
  });

  it("returns 400 and strips unknown fields when forbidNonWhitelisted is true", async () => {
    const res = await request(app.getHttpServer())
      .post("/api/users")
      .send({ name: "Alice", email: "alice@example.com", hackField: "injected" })
      .expect(400);

    expect(res.body.message).toEqual(
      expect.arrayContaining([expect.stringContaining("hackField")])
    );
  });
});
```

**Q12. How do you test that your exception filters return the correct error shape?**
A: Trigger the conditions that cause each exception and assert on the response body structure. This verifies that your global `HttpExceptionFilter` (or custom filters) transforms exceptions into the expected API error format:

```js
it("returns 404 with correct error shape for unknown user", async () => {
  const res = await request(app.getHttpServer())
    .get("/api/users/99999")
    .set("Authorization", `Bearer ${jwtToken}`)
    .expect(404);

  expect(res.body).toStrictEqual({
    statusCode: 404,
    error:      "Not Found",
    message:    "User with id 99999 not found",
    timestamp:  expect.any(String),
    path:       "/api/users/99999",
  });
});

it("returns 403 when a non-admin accesses an admin endpoint", async () => {
  const userToken = await authService.signIn({ email: "user@example.com", password: "pass" });

  const res = await request(app.getHttpServer())
    .delete("/api/admin/users/1")
    .set("Authorization", `Bearer ${userToken}`)
    .expect(403);

  expect(res.body).toMatchObject({
    statusCode: 403,
    message:    expect.stringContaining("Forbidden"),
  });
});
```

**Q13. How do you test paginated endpoints?**
A: Assert on the response envelope structure, the correct number of items, and that pagination metadata matches the query parameters:

```js
describe("GET /api/users — pagination", () => {
  beforeEach(async () => {
    // Seed 25 users for pagination tests
    await Promise.all(
      Array.from({ length: 25 }, (_, i) =>
        db("users").insert({ name: `User${i}`, email: `user${i}@example.com` })
      )
    );
  });

  it("returns the first page with correct metadata", async () => {
    const res = await request(app.getHttpServer())
      .get("/api/users")
      .query({ page: 1, limit: 10 })
      .set("Authorization", `Bearer ${jwtToken}`)
      .expect(200);

    expect(res.body).toMatchObject({
      data: expect.arrayContaining([expect.objectContaining({ name: expect.any(String) })]),
      meta: { total: 25, page: 1, limit: 10, totalPages: 3 },
    });
    expect(res.body.data).toHaveLength(10);
  });

  it("returns the last page with remaining items", async () => {
    const res = await request(app.getHttpServer())
      .get("/api/users")
      .query({ page: 3, limit: 10 })
      .set("Authorization", `Bearer ${jwtToken}`)
      .expect(200);

    expect(res.body.data).toHaveLength(5); // 25 total, 20 already on pages 1-2
    expect(res.body.meta.page).toBe(3);
  });
});
```

## Section 4: Database Integration in E2E Tests

**Q14. How do you connect a real database to a NestJS E2E test suite?**
A: The cleanest pattern is to configure the database module to read from environment variables, set those variables to a test database in the Jest environment, and let NestJS boot normally — the test database is just a different connection string:

```js
// test/setup/globalSetup.ts
import { PostgreSqlContainer } from "@testcontainers/postgresql";
import knex                    from "knex";

export default async function globalSetup() {
  const container = await new PostgreSqlContainer("postgres:16-alpine")
    .withDatabase("e2e_test").withUsername("test").withPassword("test")
    .start();

  process.env.DATABASE_URL          = container.getConnectionUri();
  process.env.__TEST_CONTAINER_ID__ = container.getId();

  // Run migrations once — the NestJS app connects to this database on boot
  const db = knex({ client: "pg", connection: container.getConnectionUri() });
  await db.migrate.latest();
  await db.destroy();
}
```

```js
// test/setup/globalTeardown.ts
export default async function globalTeardown() {
  if (process.env.__TEST_CONTAINER_ID__) {
    const { GenericContainer } = await import("testcontainers");
    await GenericContainer.stopContainer(process.env.__TEST_CONTAINER_ID__);
  }
}
```

**Q15. How do you reset database state between E2E tests?**
A: The same three options as in any database test, with one NestJS-specific consideration — access the database connection through the NestJS module to ensure you're cleaning up through the same connection pool the app is using:

```js
// Option 1 — transaction rollback (preferred, fastest)
let queryRunner: QueryRunner;

beforeEach(async () => {
  const dataSource = moduleRef.get<DataSource>(DataSource); // TypeORM
  queryRunner = dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();
});

afterEach(async () => {
  await queryRunner.rollbackTransaction();
  await queryRunner.release();
});

// Option 2 — truncation between tests (simpler, slower)
beforeEach(async () => {
  const dataSource = moduleRef.get<DataSource>(DataSource);
  await dataSource.query(`SET session_replication_role = 'replica'`); // disable FK checks
  await Promise.all(
    dataSource.entityMetadatas.map(e =>
      dataSource.query(`TRUNCATE "${e.tableName}" RESTART IDENTITY`)
    )
  );
  await dataSource.query(`SET session_replication_role = 'origin'`);
});
```

**Q16. How do you seed test data for E2E tests without coupling every test to the same seed?**
A: Use a layered seeding strategy:

- **Global seed (once in `beforeAll`)** — reference data that never changes and is read-only throughout the suite: roles, plan tiers, permission definitions.
- **Suite-level seed (in a `describe` block's `beforeAll`)** — data a group of related tests all need: a test user account, a test organization.
- **Test-level seed (in `beforeEach`)** — data specific to a single test or that gets mutated. Seeded after the transaction opens so it is rolled back automatically.

```js
describe("UsersController (e2e)", () => {
  let adminToken: string;
  let testUserId: number;

  // Suite-level — an admin user shared across all tests in this describe block
  beforeAll(async () => {
    const authService = moduleRef.get<AuthService>(AuthService);
    await authService.createUser({ email: "admin@test.com", role: "admin", password: "admin" });
    adminToken = await authService.signIn({ email: "admin@test.com", password: "admin" });
  });

  beforeEach(async () => {
    // Test-level — a fresh user per test (rolled back in afterEach)
    const res = await request(app.getHttpServer())
      .post("/api/users")
      .set("Authorization", `Bearer ${adminToken}`)
      .send({ name: "TestUser", email: `user_${Date.now()}@test.com` });

    testUserId = res.body.id;
  });

  it("GET /api/users/:id returns the seeded user", async () => {
    await request(app.getHttpServer())
      .get(`/api/users/${testUserId}`)
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(200)
      .expect(res => expect(res.body.id).toBe(testUserId));
  });
});
```

## Section 5: Testing Guards, Interceptors, and Pipes

**Q17. How do you test that a guard correctly blocks unauthorized access?**
A: Test the rejection path (no token, invalid token, insufficient role) and the acceptance path (valid token with correct role) as separate tests:

```js
describe("RolesGuard", () => {
  it("returns 401 when no token is provided", async () => {
    await request(app.getHttpServer())
      .get("/api/admin/users")
      .expect(401);
  });

  it("returns 403 when token is valid but role is insufficient", async () => {
    const userToken = await getTokenForRole("user");

    await request(app.getHttpServer())
      .get("/api/admin/users")
      .set("Authorization", `Bearer ${userToken}`)
      .expect(403);
  });

  it("returns 200 when token has the admin role", async () => {
    const adminToken = await getTokenForRole("admin");

    await request(app.getHttpServer())
      .get("/api/admin/users")
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(200);
  });
});
```

**Q18. How do you test a response interceptor — for example, one that wraps all responses in a `{ data, meta }` envelope?**
A: Assert on the response shape from a representative endpoint — the envelope is part of the API contract:

```js
it("wraps response in the standard envelope", async () => {
  const res = await request(app.getHttpServer())
    .get("/api/users/1")
    .set("Authorization", `Bearer ${adminToken}`)
    .expect(200);

  expect(res.body).toMatchObject({
    data: expect.objectContaining({ id: 1 }),
    meta: expect.objectContaining({
      timestamp: expect.any(String),
      requestId: expect.any(String),
    }),
  });

  // Verify the actual payload is correct within the envelope
  expect(res.body.data.name).toBe("Alice");
});
```

**Q19. How do you test a custom pipe that transforms or validates a route parameter?**
A: Send requests with valid and invalid parameter values and assert on the outcome. The pipe runs as part of the full request lifecycle:

```js
describe("ParsePositiveIntPipe on :id parameter", () => {
  it("allows valid positive integer ids", async () => {
    await request(app.getHttpServer())
      .get("/api/users/42")
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(res => expect([200, 404]).toContain(res.status));
  });

  it("returns 400 for non-numeric id", async () => {
    await request(app.getHttpServer())
      .get("/api/users/abc")
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(400);
  });

  it("returns 400 for negative id", async () => {
    await request(app.getHttpServer())
      .get("/api/users/-1")
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(400);
  });

  it("returns 400 for zero", async () => {
    await request(app.getHttpServer())
      .get("/api/users/0")
      .set("Authorization", `Bearer ${adminToken}`)
      .expect(400);
  });
});
```

## Section 6: Common Pitfalls

**Q20. Why do E2E tests sometimes pass locally but fail in CI, and what are the common causes?**
A: Local-vs-CI failures in NestJS E2E tests cluster around four root causes:

- **Missing global configuration in the test bootstrap** — a pipe or filter registered in `main.ts` that isn't in the test setup. Fix: the shared `configureApp()` function (Q6).
- **Environment variable differences** — a service reads `process.env.JWT_SECRET` which exists locally but isn't set in CI. NestJS silently initializes with `undefined`. Fix: a `.env.test` file committed to the repo (without secrets) and loaded by Jest's `setupFiles`.
- **Timing and startup races** — in CI, the Docker container or database takes longer to be ready. A `beforeAll` that starts the app before the database is healthy causes connection errors. Fix: health-check polling in `globalSetup` before the app boots.
- **Port collisions** — tests that bind to a fixed port clash when multiple test workers run in parallel. Fix: Supertest's in-process approach (`app.getHttpServer()` with no `.listen()`) avoids port binding entirely.

**Q21. What happens if you forget to call `await app.close()` in `afterAll`?**
A: The Node.js process stays alive after Jest finishes — Jest reports "Jest did not exit one second after the test run has completed." The cause is open handles: the NestJS HTTP server socket, the database connection pool, any scheduled jobs or event emitters started by modules. `app.close()` triggers `OnModuleDestroy` on all providers, closes the HTTP server, and drains connection pools. Without it:
- Database connection pools stay open (open handle warning).
- `OnModuleDestroy` hooks don't fire, so any cleanup logic in providers is skipped.
- The next test run may encounter stale connections or locked resources.

```js
afterAll(async () => {
  await app.close(); // ← essential; triggers all OnModuleDestroy hooks
});
```

**Q22. How do you avoid test pollution when multiple E2E test files share the same NestJS application instance?**
A: Two strategies depending on whether you share the app across files or create one per file:

**Per-file app instance (simpler, slower):** each test file creates and destroys its own app. No pollution possible — files are completely isolated. Slower because each file pays the full boot cost.

**Shared app across files (faster, more complex):** use a Jest global setup/teardown to create the app once. Each test file is responsible for its own data cleanup via transaction rollback or truncation. The critical rule: if a test configures a mock via `jest.spyOn()` and doesn't restore it (`jest.restoreAllMocks()` in `afterEach`), the mock bleeds into subsequent tests in other files:

```js
// Correct pattern for shared-app mock management
beforeEach(() => {
  jest.spyOn(stripeService, "charge").mockResolvedValue({ id: "ch_test" });
});

afterEach(() => {
  jest.restoreAllMocks(); // ← essential when the app is shared across files
});
```

**Q23. How do you debug a failing E2E test when the response body gives no useful information?**
A: Five debugging techniques in escalating depth:

```js
// 1. Log the full response when an assertion fails
const res = await request(app.getHttpServer()).post("/api/orders").send(payload);
if (res.status !== 201) {
  console.log("Status:",  res.status);
  console.log("Body:",    JSON.stringify(res.body, null, 2));
  console.log("Headers:", res.headers);
}
expect(res.status).toBe(201);

// 2. Enable NestJS logger in tests to see internal app behaviour
app = moduleRef.createNestApplication();
app.useLogger(new Logger()); // pipe NestJS logs to stdout

// 3. Run Jest single-threaded so debugger breakpoints work
// jest --runInBand --testNamePattern="failing test name"

// 4. Inspect DB state directly after the request
const rows = await db.raw("SELECT * FROM orders WHERE user_id = 1");
console.log("DB state:", rows.rows);

// 5. Add a catch-all debug exception filter that logs the full stack
app.useGlobalFilters(new DebugExceptionFilter()); // logs before responding
```

## Section 7: Scenario / System Design Style Questions

**Q24. "Your NestJS E2E suite takes 4 minutes, and the team skips it locally. Walk through how you'd reduce it to under 90 seconds."**
A: Four-minute E2E suites are almost always caused by per-file app boot and no parallelism. Attack in this order:

1. **Profile** — `jest --verbose --runInBand` with timing shows which files are slowest. The slowest 20% usually account for most of the time.
2. **Share the app across files** — move `beforeAll`/`afterAll` to `globalSetup`/`globalTeardown`. One boot, one database connection, shared across all test files. This alone typically cuts time by 50–70%.
3. **Share the database container** — if each file boots a new Docker container (a common mistake when container setup is in `beforeAll`), move it to `globalSetup`. One container for the entire run.
4. **Transaction rollback over truncation** — replace `beforeEach` truncation (real I/O per test) with transaction rollback (single log operation per test).
5. **Parallelize with `--maxWorkers`** — with a shared container and per-worker schema isolation, run 2–4 workers in parallel. Wall-clock time scales roughly with `1/workers` until the DB connection pool becomes the bottleneck.
6. **Run only a smoke subset locally** — tag the 5–10 most critical E2E tests with `@smoke` and run `jest --testNamePattern=@smoke` as the local pre-commit check. Full suite runs in CI on PR.

**Q25. "You're writing an E2E test for a checkout endpoint that sends an email, charges a credit card, and writes to three database tables. How do you structure it?"**
A: The test needs to verify the HTTP response, the database writes, and that side effects (email, payment) were triggered — without actually charging a card or sending an email:

```js
describe("POST /api/checkout", () => {
  let stripeService:  StripeService;
  let mailerService:  MailerService;

  beforeAll(async () => {
    stripeService = moduleRef.get<StripeService>(StripeService);
    mailerService = moduleRef.get<MailerService>(MailerService);
  });

  beforeEach(() => {
    jest.spyOn(stripeService, "charge").mockResolvedValue({ id: "ch_test_123" });
    jest.spyOn(mailerService, "sendOrderConfirmation").mockResolvedValue(undefined);
  });

  afterEach(() => { jest.restoreAllMocks(); });

  it("returns 201 with order details on valid checkout", async () => {
    const res = await request(app.getHttpServer())
      .post("/api/checkout")
      .set("Authorization", `Bearer ${userToken}`)
      .send({ items: [{ sku: "ABC", qty: 2 }], paymentToken: "tok_visa" })
      .expect(201);

    // Assert HTTP response shape
    expect(res.body).toMatchObject({ orderId: expect.any(Number), status: "confirmed" });

    // Assert database writes
    const order = await db("orders").where({ id: res.body.orderId }).first();
    expect(order).toMatchObject({ status: "confirmed", userId: testUser.id });

    const items = await db("order_items").where({ orderId: res.body.orderId });
    expect(items).toHaveLength(1);
    expect(items[0]).toMatchObject({ sku: "ABC", quantity: 2 });

    const payment = await db("payments").where({ orderId: res.body.orderId }).first();
    expect(payment).toMatchObject({ stripeChargeId: "ch_test_123", status: "succeeded" });

    // Assert side effects were triggered
    expect(stripeService.charge).toHaveBeenCalledWith(
      expect.objectContaining({ token: "tok_visa" })
    );
    expect(mailerService.sendOrderConfirmation).toHaveBeenCalledWith(
      expect.objectContaining({ orderId: res.body.orderId })
    );
  });

  it("returns 402 and rolls back all writes when payment fails", async () => {
    jest.spyOn(stripeService, "charge").mockRejectedValue(new PaymentError("card declined"));

    const orderCountBefore = await db("orders").count("id as n").first();

    await request(app.getHttpServer())
      .post("/api/checkout")
      .set("Authorization", `Bearer ${userToken}`)
      .send({ items: [{ sku: "ABC", qty: 2 }], paymentToken: "tok_declined" })
      .expect(402);

    // Assert rollback — no partial writes persisted
    expect((await db("orders").count("id as n").first()).n).toBe(orderCountBefore.n);

    // Assert email was not sent
    expect(mailerService.sendOrderConfirmation).not.toHaveBeenCalled();
  });
});
```

**Q26. "A new developer asks why you have both unit tests for `UsersService` and E2E tests for `POST /api/users`. Isn't that duplication?" How do you answer?**
A: They test at different levels and catch different classes of bugs — they are complementary, not redundant:

The **unit test for `UsersService`** verifies pure business logic in isolation: does `createUser()` hash the password before persisting? Does it throw `ConflictException` if the email already exists? Does it call the mailer after creation? All dependencies are mocked — the test runs in milliseconds and gives precise failure localization.

The **E2E test for `POST /api/users`** verifies the full request lifecycle: does the route exist? Does `ValidationPipe` reject missing fields? Does the guard allow unauthenticated creation or require a token? Does the controller correctly pass the DTO to the service? Does the exception filter convert `ConflictException` into a 409 response with the right body shape? None of these are covered by the unit test — they emerge from the wiring of the NestJS module graph and the HTTP layer.

A unit test that passes does not tell you that `POST /api/users` returns 201 with the right body. An E2E test that passes does not tell you that the password hashing logic is correct. Both are necessary; neither substitutes for the other.

## Common Mistakes at a Glance

| Mistake                                                  | Symptom                                                    | Fix                                                                   |
|---                                                       |---                                                         |---                                                                    |
| Global pipes/filters not in test bootstrap               | Validation passes in tests, fails in production            | Extract `configureApp()` and call it in both `main.ts` and test setup |
| `await app.close()` missing in `afterAll`                | Open handle warning; DB pool and HTTP server stay alive    | Always `await app.close()` in `afterAll`                              |
| Per-file app bootstrap instead of shared                 | Suite takes 5+ minutes; team skips it locally              | Move bootstrap to `globalSetup`; share across files                   |
| Mock not restored between tests                          | Mock bleeds into other files; order-dependent failures     | `jest.restoreAllMocks()` in `afterEach`                               |
| Asserting only HTTP response, not DB state               | Partial write bugs ship to production                      | Assert DB state for every write operation                             |
| `.listen(3000)` instead of using `getHttpServer()`       | `EADDRINUSE` in parallel test runs                         | Use `app.getHttpServer()` — Supertest handles binding internally       |
| Not guarding against production `DATABASE_URL`           | Tests accidentally run against production data             | Assert `localhost` in the URL before the suite starts                 |
| `moduleRef.get()` on a request-scoped provider           | Wrong instance returned or exception thrown                | Use `moduleRef.resolve()` for request-scoped providers                |
