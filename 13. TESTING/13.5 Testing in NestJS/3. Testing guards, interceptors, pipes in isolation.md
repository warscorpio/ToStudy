# Testing Guards, Interceptors, and Pipes in Isolation — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why test guards, interceptors, and pipes in isolation rather than only through controller integration tests?**
A: Guards, interceptors, and pipes are middleware-like components that wrap every request passing through the NestJS pipeline. Testing them only through controller integration tests creates two problems:

**Coverage gaps:** An integration test exercises the guard in one context — one controller, one route, one set of conditions. Testing the guard in isolation lets you systematically cover every decision branch: token missing, token expired, token valid but wrong role, token valid but user suspended. You can't reasonably cover all combinations through controller tests without the test suite exploding in size.

**Diagnosis speed:** When an integration test fails, the failure could be in the guard, the pipe, the interceptor, or the controller. When a guard unit test fails, the diagnosis is immediate — the guard logic is broken. Fast, isolated failures are what make a test suite useful rather than a slow oracle.

**Regression precision:** Guards and interceptors often change independently of controllers — a new role is added, a new header requirement is introduced, a response shape is standardised. Isolated tests catch these regressions without requiring the entire HTTP stack to be running.

The testing model: **unit tests in isolation for correctness of each component's logic; HTTP integration tests (supertest) for verifying they're wired together correctly.** Both layers are necessary; neither substitutes for the other.

**Q2. What is the `ExecutionContext` in NestJS, and why is mocking it the central skill for testing these components?**
A: `ExecutionContext` is the abstraction NestJS passes to guards, interceptors, and (via `ArgumentsHost`) exception filters. It provides access to the underlying request, response, and handler metadata without coupling component code to a specific HTTP transport (Express vs Fastify) or non-HTTP contexts (WebSockets, gRPC, microservices).

Its interface:

```typescript
interface ExecutionContext extends ArgumentsHost {
  getClass<T = any>(): Type<T>;            // controller class
  getHandler(): Function;                  // route handler method
  getArgs<T extends Array<any> = any[]>(): T;
  getArgByIndex<T = any>(index: number): T;
  switchToHttp(): HttpArgumentsHost;       // { getRequest(), getResponse(), getNext() }
  switchToRpc(): RpcArgumentsHost;
  switchToWs(): WsArgumentsHost;
  getType<TContext extends string = ContextType>(): TContext;
}
```

Testing guards and interceptors means providing a fake `ExecutionContext` that returns exactly the request state each test case requires. The pattern is consistent across all three component types:

```typescript
// Reusable factory — build a mock ExecutionContext for HTTP scenarios
function createMockExecutionContext(
  requestOverrides: Partial<Request> = {},
  handlerMetadata:  Record<string, any> = {},
): ExecutionContext {
  const mockRequest = {
    headers:    {},
    user:       null,
    params:     {},
    query:      {},
    body:       {},
    ...requestOverrides,
  };

  return {
    switchToHttp: () => ({
      getRequest:  () => mockRequest,
      getResponse: () => ({ header: jest.fn(), status: jest.fn() }),
      getNext:     () => jest.fn(),
    }),
    getHandler: () => jest.fn(),
    getClass:   () => jest.fn(),
    getType:    () => "http",
  } as unknown as ExecutionContext;
}
```

Mastering this factory is what makes guard, interceptor, and pipe isolation tests tractable — you build it once per test suite and parameterise the parts each test needs to vary.

**Q3. What is the NestJS request lifecycle, and where do guards, pipes, and interceptors sit in it?**
A: The lifecycle determines execution order — which matters for both understanding what each component can access and for writing tests that simulate the correct state:

```
Incoming Request
      │
      ▼
 Middleware          ← app.use() / @Module middleware; runs before guards
      │
      ▼
  Guards             ← canActivate() → true (continue) or false/throw (reject)
      │
      ▼
  Interceptors       ← before handler: transform request, log, start timer
      │
      ▼
  Pipes              ← transform and validate route params, body, query
      │
      ▼
  Route Handler      ← the @Get() / @Post() controller method
      │
      ▼
  Interceptors       ← after handler: transform response, log duration
      │
      ▼
 Exception Filters   ← catch thrown exceptions, map to HTTP responses
      │
      ▼
Outgoing Response
```

Key implications for testing:
- Guards run before pipes — a guard test doesn't need a valid DTO body because pipes haven't run yet.
- Interceptors run before AND after the handler — test both the `next.handle()` pre-call logic and the `pipe(map(...))` post-call logic.
- Pipes receive the already-extracted value (from `@Body()`, `@Param()`, etc.) — pipe tests pass raw values directly, not full requests.

## Section 2: Testing Guards

**Q4. Walk through testing a JWT auth guard in complete isolation.**
A:

```typescript
// src/auth/guards/jwt-auth.guard.ts
import { Injectable, CanActivate, ExecutionContext, UnauthorizedException } from "@nestjs/common";
import { JwtService } from "@nestjs/jwt";
import { Request }    from "express";

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwtService: JwtService) {}

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<Request>();
    const token   = this.extractToken(request);

    if (!token) {
      throw new UnauthorizedException("No token provided");
    }

    try {
      const payload = this.jwtService.verify(token);
      request.user  = payload;       // attach decoded payload for downstream use
      return true;
    } catch {
      throw new UnauthorizedException("Invalid or expired token");
    }
  }

  private extractToken(request: Request): string | null {
    const [type, token] = request.headers.authorization?.split(" ") ?? [];
    return type === "Bearer" ? token : null;
  }
}
```

```typescript
      jwtService.verify.mockImplementation(() => {

      // Act & Assert
      expect(() => guard.canActivate(context)).toThrow(UnauthorizedException);
```

**Q5. How do you test a roles-based guard that reads custom metadata from the route handler?**
A: Role guards use `Reflector` to read metadata set by decorators like `@Roles("admin")`. Testing this requires mocking both the `ExecutionContext` and the `Reflector`:

```typescript
// src/auth/guards/roles.guard.ts
import { Injectable, CanActivate, ExecutionContext, ForbiddenException } from "@nestjs/common";
import { Reflector } from "@nestjs/core";

export const ROLES_KEY = "roles";

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    // Read the @Roles() metadata from the handler or the controller class
    const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);

    // No @Roles() decorator → route is open to all authenticated users
    if (!requiredRoles || requiredRoles.length === 0) {
      return true;
    }

    const { user } = context.switchToHttp().getRequest();

    if (!user) {
      throw new ForbiddenException("User not authenticated");
    }

    const hasRole = requiredRoles.some((role) => user.roles?.includes(role));
    if (!hasRole) {
      throw new ForbiddenException(
        `Required role(s): ${requiredRoles.join(", ")}`
      );
    }

    return true;
  }
}
```

```typescript
// src/auth/guards/roles.guard.spec.ts

    // Act & Assert
    expect(() => guard.canActivate(context)).toThrow(ForbiddenException);
    expect(() => guard.canActivate(context)).toThrow("Required role(s): admin");
  });

  it("should throw ForbiddenException when req.user is null", () => {
    // Arrange — guard runs after JwtAuthGuard failed or was bypassed
    reflector.getAllAndOverride.mockReturnValue(["admin"]);
    const context = buildContext(null); // no user on request

    // Act & Assert
    expect(() => guard.canActivate(context)).toThrow(ForbiddenException);
    expect(() => guard.canActivate(context)).toThrow("User not authenticated");
  });

  it("should return true when the user has any one of multiple required roles", () => {
    // Arrange — @Roles("admin", "moderator")
    reflector.getAllAndOverride.mockReturnValue(["admin", "moderator"]);
    const context = buildContext({ id: "u1", roles: ["moderator"] });

    // Act & Assert
    expect(guard.canActivate(context)).toBe(true);
  });

  it("should check handler metadata before class metadata via getAllAndOverride", () => {
    // Arrange
    reflector.getAllAndOverride.mockReturnValue(["admin"]);
    const context = buildContext({ id: "u1", roles: ["admin"] });

    guard.canActivate(context);

    // Assert Reflector was called with handler first (method-level takes priority)
    expect(reflector.getAllAndOverride).toHaveBeenCalledWith(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
  });
});
```

**Q6. How do you test a guard that makes an asynchronous call — for example, checking a token against a database?**
A:

```typescript
// src/auth/guards/api-key.guard.ts
@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(private readonly apiKeyService: ApiKeyService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    const apiKey  = request.headers["x-api-key"] as string;

    if (!apiKey) {
      throw new UnauthorizedException("API key missing");
    }

    const keyRecord = await this.apiKeyService.findValidKey(apiKey);

    if (!keyRecord) {
      throw new UnauthorizedException("Invalid API key");
    }

    if (keyRecord.expiresAt < new Date()) {
      throw new UnauthorizedException("API key expired");
    }

    request.user = { id: keyRecord.userId, scope: keyRecord.scope };
    return true;
  }
}
```

## Section 3: Testing Interceptors

**Q7. What makes interceptors harder to test than guards, and what is the core testing pattern?**
A: Interceptors are harder because they wrap the route handler via RxJS `Observable` — specifically `next.handle()` which returns an `Observable<any>` representing the handler's eventual response. Testing an interceptor in isolation means:

1. Providing a mock `CallHandler` whose `handle()` returns a controlled `Observable`.
2. Subscribing to the `Observable` the interceptor returns.
3. Asserting on what came out of the pipe before and after the handler ran.

The pattern:

```typescript
import { of, throwError, lastValueFrom } from "rxjs";
import { CallHandler }                   from "@nestjs/common";

// Mock CallHandler — the interceptor calls next.handle() to invoke the route handler
function buildCallHandler(response: any): CallHandler {
  return { handle: () => of(response) };
}

function buildErrorCallHandler(error: any): CallHandler {
  return { handle: () => throwError(() => error) };
}

// Test an interceptor:
const result = await lastValueFrom(
  interceptor.intercept(context, buildCallHandler({ data: "hello" }))
);
expect(result).toEqual({ data: "hello", timestamp: expect.any(String) });
```

`lastValueFrom` (from `rxjs`) converts the `Observable` to a `Promise`, letting you `await` it in Jest. This is the idiomatic way to assert on interceptor output in an async test.

**Q8. Walk through testing a response-transform interceptor that wraps all responses in a standard envelope.**
A:

```typescript
// src/common/interceptors/transform.interceptor.ts
import {
  Injectable, NestInterceptor, ExecutionContext, CallHandler,
} from "@nestjs/common";
import { Observable } from "rxjs";
import { map }        from "rxjs/operators";

export interface ApiResponse<T> {
  data:      T;
  success:   boolean;
  timestamp: string;
  requestId: string;
}

@Injectable()
export class TransformInterceptor<T>
  implements NestInterceptor<T, ApiResponse<T>>
{
  intercept(
    context:     ExecutionContext,
    next:        CallHandler<T>,
  ): Observable<ApiResponse<T>> {
    const requestId = context
      .switchToHttp()
      .getRequest()
      .headers["x-request-id"] ?? "no-id";

    return next.handle().pipe(
      map((data) => ({
        data,
        success:   true,
        timestamp: new Date().toISOString(),
        requestId,
      }))
    );
  }
}
```

**Q9. How do you test a logging interceptor that measures request duration and logs after the handler completes?**
A: The duration measurement requires controlling time — fake timers. The post-handler logic requires verifying the Observable completes and triggers the logging side effect:

```typescript
// src/common/interceptors/logging.interceptor.ts
import {
  Injectable, NestInterceptor, ExecutionContext, CallHandler, Logger,
} from "@nestjs/common";
import { Observable } from "rxjs";
import { tap }        from "rxjs/operators";

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger(LoggingInterceptor.name);

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request   = context.switchToHttp().getRequest();
    const method    = request.method;
    const url       = request.url;
    const startTime = Date.now();

    this.logger.log(`→ ${method} ${url}`);

    return next.handle().pipe(
      tap({
        next: () => {
          const duration = Date.now() - startTime;
          this.logger.log(`← ${method} ${url} ${duration}ms`);
        },
        error: (err) => {
          const duration = Date.now() - startTime;
          this.logger.error(`← ${method} ${url} ${duration}ms — ${err.message}`);
        },
      })
    );
  }
}
```

```typescript
    const context = buildContext("POST", "/v1/payments");

        jest.advanceTimersByTime(150);
        return of({ txnId: "txn_001" });

    // Act
    await lastValueFrom(interceptor.intercept(context, handler));

    // Assert — two log calls: incoming + outgoing
    expect(logSpy).toHaveBeenCalledTimes(2);

    expect(logSpy).toHaveBeenNthCalledWith(2, "← POST /v1/payments 150ms");
  });

  it("should log an error line when the handler throws", async () => {
    // Arrange
    const context = buildContext("GET", "/v1/users/99");

      handle: () => {
        jest.advanceTimersByTime(50);
        return throwError(() => error);
      },
    };

    // Act — the interceptor propagates the error; we catch it here
    await expect(
      lastValueFrom(interceptor.intercept(context, handler))
    ).rejects.toThrow("User not found");

    // Assert — error was logged with duration
    expect(errorSpy).toHaveBeenCalledWith(
      "← GET /v1/users/99 50ms — User not found"
    );
    expect(logSpy).toHaveBeenCalledTimes(1); // only the incoming log, not a success log
  });
});
```

**Q10. How do you test a caching interceptor that short-circuits the handler on a cache hit?**
A: The cache hit path means `next.handle()` is never called — the interceptor returns an `Observable` from the cache instead. This is the most important case to test because it's the one that can silently swallow handler calls:

```typescript
// src/common/interceptors/cache.interceptor.ts
@Injectable()
export class HttpCacheInterceptor implements NestInterceptor {
  constructor(private readonly cacheService: CacheService) {}

  async intercept(
    context: ExecutionContext,
    next:    CallHandler,
  ): Promise<Observable<any>> {
    const request  = context.switchToHttp().getRequest<Request>();

    // Only cache GET requests
    if (request.method !== "GET") {
      return next.handle();
    }

    const cacheKey = `http:${request.url}`;
    const cached   = await this.cacheService.get(cacheKey);

    if (cached !== null) {
      return of(cached);          // short-circuit: handler never runs
    }

    return next.handle().pipe(
      tap((response) => {
        this.cacheService.set(cacheKey, response, 60); // TTL 60s
      })
    );
  }
}
```

## Section 4: Testing Pipes

**Q11. What makes pipes the simplest NestJS component to test in isolation?**
A: Pipes are pure transformers — their `transform(value, metadata)` method takes a raw input value and either returns a transformed value or throws a validation exception. There's no `ExecutionContext`, no `CallHandler`, no RxJS — just a function call:

```typescript
// The entire testing surface
const result = await pipe.transform(inputValue, metadata);
// or
expect(() => pipe.transform(inputValue, metadata)).toThrow(BadRequestException);
```

The `ArgumentMetadata` object (the second argument) describes where the value came from:

```typescript
interface ArgumentMetadata {
  type:     "body" | "query" | "param" | "custom";
  metatype?: Type<any>;   // the DTO class, if using class-validator
  data?:    string;       // the parameter name, e.g. "id" for @Param("id")
}
```

Most custom pipes only use `type` or `data` — and often not even that. The metadata is there for pipes that need to know the context (like `ValidationPipe` using `metatype` to know which DTO class to validate against).

**Q12. Walk through testing a custom validation pipe that parses and validates a UUID parameter.**
A:

```typescript
// src/common/pipes/parse-uuid.pipe.ts
import { PipeTransform, Injectable, BadRequestException, ArgumentMetadata } from "@nestjs/common";
import { validate as isUuid } from "uuid";

@Injectable()
export class ParseUuidPipe implements PipeTransform<string, string> {
  transform(value: string, metadata: ArgumentMetadata): string {
    if (typeof value !== "string" || !isUuid(value)) {
      throw new BadRequestException(
        `Validation failed: '${value}' is not a valid UUID (param: ${metadata.data})`
      );
    }
    return value.toLowerCase(); // normalise to lowercase
  }
}
```

**Q13. How do you test NestJS's built-in `ValidationPipe` with a custom DTO?**

```typescript
// src/payments/dto/initiate-payment.dto.ts
import { IsNumber, IsString, IsPositive, IsISO4217CurrencyCode, IsOptional, Min } from "class-validator";
import { Type } from "class-transformer";

export class InitiatePaymentDto {
  @IsNumber()
  @IsPositive()
  @Min(100)           // minimum 100 paise (₹1)
  @Type(() => Number)
  amount: number;

  @IsString()
  @IsISO4217CurrencyCode()
  currency: string;

  @IsString()
  recipientId: string;

  @IsOptional()
  @IsString()
  note?: string;
}
```

**Q14. How do you test a transformation pipe that sanitises and enriches data before it reaches the handler?**
A:

```typescript
// src/common/pipes/sanitize-string.pipe.ts
import { PipeTransform, Injectable, BadRequestException, ArgumentMetadata } from "@nestjs/common";

@Injectable()
export class SanitizeStringPipe implements PipeTransform<string, string> {
  private readonly maxLength: number;

  constructor(maxLength = 255) {
    this.maxLength = maxLength;
  }

  transform(value: unknown, metadata: ArgumentMetadata): string {
    if (typeof value !== "string") {
      throw new BadRequestException(
        `${metadata.data ?? "Value"} must be a string`
      );
    }

    const trimmed = value.trim();

    if (trimmed.length === 0) {
      throw new BadRequestException(
        `${metadata.data ?? "Value"} must not be empty after trimming`
      );
    }

    if (trimmed.length > this.maxLength) {
      throw new BadRequestException(
        `${metadata.data ?? "Value"} must not exceed ${this.maxLength} characters`
      );
    }

    // Strip HTML tags to prevent XSS in stored strings
    return trimmed.replace(/<[^>]*>/g, "");
  }
}
```

```typescript
  });
```

## Section 5: Cross-Cutting Patterns

**Q15. How do you test that multiple guards are applied in the correct order on a route, without running the full HTTP stack?**
A: Guards are evaluated sequentially in NestJS — the first guard to return `false` or throw short-circuits the rest. Testing the composition requires verifying each guard's interaction with the others:

```typescript
// src/auth/guards/composite-auth.guard.spec.ts
// Test strategy: guards compose via the request object — first guard attaches user;
// second guard reads it. Test each guard independently (covered in Q4–Q6),
// then test the integration of the request object state they share.

describe("Guard composition: JwtAuthGuard then RolesGuard", () => {
  let jwtGuard:   JwtAuthGuard;
  let rolesGuard: RolesGuard;
  let jwtService: jest.Mocked<JwtService>;
  let reflector:  jest.Mocked<Reflector>;

  // Shared request object — this is what connects the two guards
  let mockRequest: { headers: any; user: any };

  function buildContext(): ExecutionContext {
    return {
      switchToHttp: () => ({
        getRequest: () => mockRequest,
      }),
      getHandler: jest.fn(),
      getClass:   jest.fn(),
    } as unknown as ExecutionContext;
  }

  beforeEach(() => {
    jwtService  = { verify: jest.fn() }    as jest.Mocked<JwtService>;
    reflector   = { getAllAndOverride: jest.fn() } as jest.Mocked<Reflector>;
    jwtGuard    = new JwtAuthGuard(jwtService);
    rolesGuard  = new RolesGuard(reflector);
    mockRequest = { headers: {}, user: null };
  });

  it("should allow access when JWT is valid and user has the required role", () => {
    // Arrange
    const payload = { sub: "u1", roles: ["admin"] };
    jwtService.verify.mockReturnValue(payload);
    reflector.getAllAndOverride.mockReturnValue(["admin"]);
    mockRequest.headers.authorization = "Bearer valid.token";

    const context = buildContext();

    // Act — simulate NestJS running guards in sequence
    const jwtResult   = jwtGuard.canActivate(context);   // attaches req.user
    const rolesResult = rolesGuard.canActivate(context); // reads req.user

    // Assert
    expect(jwtResult).toBe(true);
    expect(rolesResult).toBe(true);
    expect(mockRequest.user).toEqual(payload); // side effect from JwtGuard
  });

  it("should deny access at the JWT stage if token is invalid, not reaching RolesGuard", () => {
    // Arrange
    jwtService.verify.mockImplementation(() => { throw new Error("jwt expired"); });
    mockRequest.headers.authorization = "Bearer expired.token";
    const context = buildContext();

    // Act — JwtGuard throws; RolesGuard never runs
    expect(() => jwtGuard.canActivate(context)).toThrow(UnauthorizedException);
    // RolesGuard is not invoked when JWT fails
    expect(reflector.getAllAndOverride).not.toHaveBeenCalled();
  });
});
```

**Q16. How do you write a shared `ExecutionContext` mock factory that covers all your test suites?**

```typescript
// src/test/utils/execution-context.factory.ts
import { ExecutionContext } from "@nestjs/common";

export interface MockRequestOptions {
  headers?:  Record<string, string>;
  user?:     Record<string, any> | null;

  query?:    Record<string, string>;
  body?:     Record<string, any>;
  method?:   string;
  url?:      string;
  ip?:       string;
}

export interface MockResponseOptions {
  headerFn?: jest.Mock;
  statusFn?: jest.Mock;
}

export function createMockExecutionContext(
  requestOptions:  MockRequestOptions  = {},
  responseOptions: MockResponseOptions = {},
): ExecutionContext & { getMockRequest: () => any } {
  const mockRequest = {
    headers: {},
    user:    null,
    params:  {},
    query:   {},
    body:    {},
    method:  "GET",
    url:     "/test",
    ip:      "127.0.0.1",
    ...requestOptions,
  };

  const mockResponse = {
    header: responseOptions.headerFn ?? jest.fn(),
    status: responseOptions.statusFn ?? jest.fn().mockReturnThis(),
    json:   jest.fn().mockReturnThis(),
  };

  const context = {
    switchToHttp: () => ({

      getResponse: () => mockResponse,
```

**Q17. How do you test an interceptor that handles errors — for example, mapping internal errors to sanitised HTTP responses?**
A:

```typescript
// src/common/interceptors/error-sanitizer.interceptor.ts
@Injectable()
export class ErrorSanitizerInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      catchError((err) => {
        // Don't leak internal error messages to clients
        if (err instanceof HttpException) {
          throw err;   // NestJS HTTP exceptions are safe to re-throw as-is
        }

        // Internal errors — sanitise before throwing
        throw new InternalServerErrorException({
          message:   "An unexpected error occurred",
          requestId: context.switchToHttp().getRequest().headers["x-request-id"],
        });
      })
    );
  }
}
```

```typescript
// src/common/interceptors/error-sanitizer.interceptor.spec.ts

  function buildContext(requestId = "req-001"): ExecutionContext {
    return {
      switchToHttp: () => ({
        getRequest: () => ({ headers: { "x-request-id": requestId } }),
      }),
    } as unknown as ExecutionContext;
  }

  beforeEach(() => {
    interceptor = new ErrorSanitizerInterceptor();
  });

  it("should pass through the response unchanged when the handler succeeds", async () => {
    const context = buildContext();
    const handler: CallHandler = { handle: () => of({ data: "ok" }) };

    const result = await lastValueFrom(interceptor.intercept(context, handler));

    expect(result).toEqual({ data: "ok" });

  it("should re-throw NestJS HttpExceptions without modification", async () => {
    const context   = buildContext();

    const handler: CallHandler = { handle: () => throwError(() => original) };

    await expect(
      lastValueFrom(interceptor.intercept(context, handler))
    ).rejects.toThrow(NotFoundException);

    await expect(
      lastValueFrom(interceptor.intercept(context, handler))
    ).rejects.toThrow("Resource not found");  // original message preserved
  });

  it("should replace internal errors with a sanitised InternalServerErrorException", async () => {

    const context       = buildContext("req-xyz");

    // Act & Assert

      await lastValueFrom(interceptor.intercept(context, handler));
      fail("Expected interceptor to throw");
    } catch (err) {
      expect(err).toBeInstanceOf(InternalServerErrorException);

      expect(response.message).toBe("An unexpected error occurred");
      expect(response.requestId).toBe("req-xyz");
      // Original internal message must NOT appear in the sanitised response
```

## Section 6: Anti-Patterns

**Q18. What are the most common mistakes when testing guards, interceptors, and pipes in isolation?**
A:

**1. Constructing the full NestJS testing module when it isn't needed:**
```typescript
// ❌ Overkill for a guard unit test — boots the DI container unnecessarily
const module = await Test.createTestingModule({
  providers: [JwtAuthGuard, JwtService],
}).compile();
const guard = module.get(JwtAuthGuard);

// ✅ Direct instantiation with a mocked dependency
const jwtService = { verify: jest.fn() } as jest.Mocked<JwtService>;
const guard      = new JwtAuthGuard(jwtService);
```
`Test.createTestingModule` is for integration tests. Isolation tests should construct the component directly.

**2. Forgetting to `await` interceptor results:**
```typescript
// ❌ Observable is never subscribed to — test always passes vacuously
const result = interceptor.intercept(context, handler); // returns Observable, not the value
expect(result).toBeDefined(); // trivially true

// ✅ Resolve the Observable
const result = await lastValueFrom(interceptor.intercept(context, handler));
expect(result).toEqual({ data: "ok" });
```

**3. Not testing the `request.user` side effect in guard tests:**
```typescript
// ❌ Only asserts the return value — misses that user wasn't attached to req
expect(guard.canActivate(context)).toBe(true);

// ✅ Also assert the critical side effect
expect(guard.canActivate(context)).toBe(true);
expect(context.switchToHttp().getRequest().user).toEqual(expectedPayload);
```

**4. Using exact string matching on error messages:**
```typescript
// ❌ Breaks if the message wording is tweaked
expect(() => guard.canActivate(context)).toThrow("No token provided");

// ✅ Assert error type first; use partial match for message
expect(() => guard.canActivate(context)).toThrow(UnauthorizedException);
expect(() => guard.canActivate(context)).toThrow(/token/i);
```

**5. Not resetting fake timers in interceptor tests:**
```typescript
// ❌ Leaked fake timers break unrelated tests in the same file
beforeEach(() => { jest.useFakeTimers(); });
// Missing afterEach(() => { jest.useRealTimers(); });

// ✅ Always pair useFakeTimers with useRealTimers
afterEach(() => { jest.useRealTimers(); });
```

**6. Sharing the mock request object across tests:**
```typescript
// ❌ Test A mutates mockRequest.user; Test B reads stale state
const mockRequest = { headers: {}, user: null };
// mockRequest defined outside describe — shared across all tests

// ✅ Fresh object per test via beforeEach or inline factory
beforeEach(() => {
  mockRequest = { headers: {}, user: null }; // reset per test
});
```

## Section 7: Scenario / System Design Style Questions

**Q19. "You're reviewing a PR where the JwtAuthGuard has no unit tests but is covered by 15 controller integration tests. What argument do you make for adding isolated guard tests?"**
A: Frame it around three concrete costs of the current approach:

**Coverage gaps the integration tests can't express cleanly:** The 15 integration tests each represent one route in one scenario. To cover all guard logic branches — missing header, wrong scheme (`Basic` instead of `Bearer`), expired token, signature invalid, valid token but user suspended mid-session — you need 5+ test variants per route, or you assume those branches work correctly everywhere because they work on one route. Isolated guard tests cover all branches once, independently of how many routes the guard protects.

**Diagnosis speed when the guard breaks:** If a JWT library is upgraded and token verification changes, all 15 integration tests fail simultaneously with messages like `"expected 200, got 401"`. The failing tests don't localise the problem — you have to trace through the full request lifecycle to find the guard. One failing guard unit test with `"expected verify() to be called with the token from the Authorization header"` localises it in seconds.

**Documentation of guard contract:** A guard unit test documents exactly what the guard does — what headers it reads, what it attaches to `req.user`, what it throws and when. That's information a developer reading an integration test failure has to reverse-engineer from the stack trace. Make the argument that unit tests are executable documentation — they live closer to the code they document than the integration tests that happen to exercise the same path.

**Q20. "A new interceptor is being added that reads a request-scoped correlation ID from AsyncLocalStorage and appends it to every response. How do you test it in isolation?"**
A:

```typescript
// src/common/interceptors/correlation-id.interceptor.ts
import { AsyncLocalStorage } from "async_hooks";

export const correlationStore = new AsyncLocalStorage<{ correlationId: string }>();

@Injectable()
export class CorrelationIdInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request       = context.switchToHttp().getRequest();
    const correlationId = request.headers["x-correlation-id"] ?? randomUUID();

    // Make it available to the entire request lifecycle via ALS
    return new Observable((subscriber) => {
      correlationStore.run({ correlationId }, () => {
        next.handle().pipe(
          map((data) => ({ ...data, correlationId })),
          tap({
            error: (err) => { err.correlationId = correlationId; },
          }),
        ).subscribe(subscriber);
      });
    });
  }
}
```

**Q21. "You're building a rate-limiting pipe that checks how many times a user has called an endpoint in the last minute. The pipe reads from Redis. How do you test it without a real Redis connection?"**
A:

```typescript
// src/common/pipes/rate-limit.pipe.ts
@Injectable()
export class RateLimitPipe implements PipeTransform {
  constructor(
    private readonly redisService: RedisService,
    private readonly limit:        number = 60,  // requests per minute
  ) {}

  async transform(value: any, metadata: ArgumentMetadata): Promise<any> {
    // userId is expected to come from a prior guard that set req.user
    const userId  = metadata.data; // passed via custom decorator
    const key     = `rate_limit:${userId}:${Math.floor(Date.now() / 60_000)}`;
    const current = await this.redisService.incr(key);

    if (current === 1) {
      // First call in this window — set TTL so key auto-expires
      await this.redisService.expire(key, 60);
    }

    if (current > this.limit) {
      throw new HttpException(
        { error: "Rate limit exceeded", retryAfter: 60 },
        429,
      );
    }

    return value;
  }
}
```

```typescript
describe("RateLimitPipe", () => {
```

## Quick Reference: Testing Each Component Type

```typescript
// ─── GUARDS ─────────────────────────────────────────────────────────────────
// Pattern: build mock ExecutionContext → call canActivate() → assert bool or throw
const guard   = new MyGuard(mockDependency);
const context = buildMockContext({ headers: { authorization: "Bearer token" } });

expect(guard.canActivate(context)).toBe(true);
expect(() => guard.canActivate(context)).toThrow(UnauthorizedException);
await expect(guard.canActivate(context)).rejects.toThrow(ForbiddenException); // async guard

// Assert side effect (user attached to request)
const req = context.switchToHttp().getRequest();
expect(req.user).toMatchObject({ id: "u1" });

// ─── INTERCEPTORS ────────────────────────────────────────────────────────────
// Pattern: build mock CallHandler → call intercept() → lastValueFrom() → assert
import { of, throwError, lastValueFrom } from "rxjs";

const handler: CallHandler = { handle: () => of(handlerResponse) };
const result = await lastValueFrom(interceptor.intercept(context, handler));
expect(result).toMatchObject(expectedEnvelope);

// Error path:
const errHandler: CallHandler = { handle: () => throwError(() => new Error("fail")) };
await expect(lastValueFrom(interceptor.intercept(context, errHandler))).rejects.toThrow();

// Cache short-circuit (handler must NOT be called):
const mockHandler = { handle: jest.fn().mockReturnValue(of({})) };
await lastValueFrom(interceptor.intercept(context, mockHandler));
expect(mockHandler.handle).not.toHaveBeenCalled();

// ─── PIPES ──────────────────────────────────────────────────────────────────
// Pattern: call transform() directly with value + ArgumentMetadata → assert result or throw
const metadata: ArgumentMetadata = { type: "param", data: "id" };

expect(pipe.transform("valid-input", metadata)).toBe("expected-output");
expect(() => pipe.transform("bad-input", metadata)).toThrow(BadRequestException);
await expect(pipe.transform("async-bad", metadata)).rejects.toThrow(BadRequestException);

// Validate NestJS ValidationPipe with a DTO:
const pipe = new ValidationPipe({ whitelist: true, transform: true });
const dto  = await pipe.transform(plainObject, { type: "body", metatype: MyDto });
expect(dto).toBeInstanceOf(MyDto);
```

**Tip for the interview:** At 5 YOE, isolation tests for guards, interceptors, and pipes come up as code review or debugging scenarios — "why does this guard test always pass even when the token is invalid?" (forgot to assert the throw), "why does the interceptor test pass but fail in integration?" (global pipe not applied). The answers that land are the ones that explain the exact contract of each component — guards return `boolean` or throw, interceptors wrap an `Observable` and must be subscribed to via `lastValueFrom`, pipes are pure `transform(value, metadata)` functions with no HTTP context — and demonstrate that isolation tests are faster and more precise diagnostic tools than integration tests for these cross-cutting components.
