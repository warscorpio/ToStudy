# NestJS Testing: `Test.createTestingModule()` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is `Test.createTestingModule()`, and what problem does it solve for testing NestJS services?**
A: `Test.createTestingModule()` is NestJS's built-in factory for creating an isolated, test-scoped version of the application's dependency injection container. It solves the fundamental mismatch between NestJS's DI-first architecture and plain unit testing: because NestJS services declare their dependencies via constructor injection and decorators, you cannot simply call `new LoanService()` in a test without satisfying every dependency in its constructor chain — which can be deep, circular, or require infrastructure (database connections, config modules) that shouldn't run in a unit test. `Test.createTestingModule()` lets you declare exactly which providers to include, replace real dependencies with mocks or fakes, and get a fully wired, DI-resolved instance of the class under test — without bootstrapping the entire application or connecting to any real infrastructure.

**Q2. What is the difference between `Test.createTestingModule()` and `NestFactory.create()`?**
A: Both create a NestJS module context backed by the DI container, but they serve different purposes:

| Aspect                        | `Test.createTestingModule()`                             | `NestFactory.create()`                                      |
|-------------------------------|----------------------------------------------------------|-------------------------------------------------------------|
| Purpose                       | Test-scoped DI container                                 | Full application bootstrap                                  |
| HTTP server                   | None by default — opt-in with `createNestApplication()` | Always starts an HTTP server                                |
| Lifecycle hooks               | Not run by default                                       | `onModuleInit`, `onApplicationBootstrap` run automatically  |
| Module imports                | You choose exactly what to include                       | Full `AppModule` and its entire import tree                 |
| Speed                         | Milliseconds (no I/O, no server)                        | Seconds (full bootstrap, connections, middleware)           |
| Overrides                     | `overrideProvider`, `overrideModule`, `overrideGuard`   | Not applicable                                              |
| Use case                      | Unit and integration tests                               | Production startup, E2E tests                               |

The key distinction at 5 YOE: `Test.createTestingModule()` is the right tool for unit and integration tests of individual services, repositories, and controllers. `NestFactory.create()` (or `moduleRef.createNestApplication()` in tests) is only needed for E2E tests where you need a running HTTP server.

**Q3. What is the full lifecycle of `Test.createTestingModule()` from declaration to getting a provider instance?**
A: Four steps, each with a distinct role:

```typescript
// Step 1 — Declare: define the test module's providers and imports
const moduleRef = await Test.createTestingModule({
  imports: [ConfigModule],               // real modules, imported as-is
  providers: [
    LoanService,                         // real class under test
    {
      provide: LoanRepository,
      useValue: mockLoanRepository,      // fake/mock replacing the real dep
    },
  ],
}).compile(); // Step 2 — Compile: resolves the DI graph, wires providers together

// Step 3 — Get: retrieve a resolved instance from the container
const service = moduleRef.get(LoanService);

// Step 4 — Teardown (optional but correct)
await moduleRef.close(); // runs onModuleDestroy hooks, closes connections
```

`.compile()` is where NestJS resolves the dependency graph — it instantiates providers in dependency order, injects dependencies into constructors, and runs `onModuleInit` hooks if present. It returns a `TestingModule` (a subtype of `ModuleRef`) that you use to retrieve instances. Always `await` the `.compile()` call — it is async because module init hooks may be async.

**Q4. What does `.get()` do, and how does it differ from `.resolve()`?**
A: Both retrieve instances from the DI container, but they handle scope differently:

- **`.get(token)`** — returns the singleton instance of a provider. For `@Injectable()` providers with default (singleton) scope, this is the same instance every time. Suitable for the vast majority of tests — services, repositories, and guards are almost always singletons.
- **`.resolve(token)`** — creates a new instance of a scoped provider (`REQUEST` or `TRANSIENT` scope) in a fresh DI sub-context. Returns a promise. Used when the provider under test is declared with `scope: Scope.REQUEST` (e.g., a per-request tenant context, a request-scoped logger). Rarely needed in tests unless you specifically test scoped provider behaviour.

```typescript
// Singleton (most cases)
const service = moduleRef.get(LoanService);
const sameInstance = moduleRef.get(LoanService);
// service === sameInstance → true

// Scoped (rarely needed)
const scopedService = await moduleRef.resolve(RequestScopedService);
const anotherInstance = await moduleRef.resolve(RequestScopedService);
// scopedService === anotherInstance → false — fresh instance each time
```

**Q5. What is a `ModuleRef`, and why does `TestingModule` extend it?**
A: `ModuleRef` is NestJS's programmatic interface to the DI container — it lets you retrieve providers, create scoped instances, and interact with the module's dependency graph imperatevely (outside of constructor injection). `TestingModule` extends `ModuleRef` so that tests can retrieve any provider in the module by its injection token without needing a class that declares the dependency in its constructor. This is important in tests because you often need to access multiple providers — the service under test, its mock dependencies (to set up return values and assert on calls), and sometimes infrastructure providers (the `DataSource`, the `EventBus`) — all from the same module context.

## Section 2: Declaring Providers and Imports

**Q6. When should you import a full NestJS module vs listing providers individually in `createTestingModule`?**
A: Import a full module when the module encapsulates configuration or cross-cutting infrastructure that is genuinely needed by the service under test and is impractical to mock individually. List providers individually when you want precise control over exactly what is included — which is the correct default for unit tests.

**Import a full module when:**
- The module configures something structural, like `ConfigModule.forRoot()` — the `ConfigService` it provides is deeply embedded and mocking it requires duplicating its interface.
- You are writing an integration test that intentionally tests the full module wiring.
- The module has no side effects at init time (no real DB connections, no external API calls on startup).

**List providers individually when:**
- Writing a unit test — include only the class under test and mock providers for its dependencies.
- The real module has side effects (opens a DB connection, starts a cron job) that shouldn't run in a unit test.
- You want to control exactly which dependencies are real and which are mocked.

```typescript
// Unit test — precise control
await Test.createTestingModule({
  providers: [
    LoanService,              // real
    { provide: LoanRepository, useValue: mockRepo }, // mock
    { provide: EventBus, useValue: mockEventBus },   // mock
  ],
}).compile();

// Integration test — import the real module
await Test.createTestingModule({
  imports: [LoanModule, ConfigModule.forRoot({ isGlobal: true })],
}).compile();
```

**Q7. What are the four provider definition syntaxes in `createTestingModule`, and when do you use each?**
A:

**1. Class reference — real provider, resolved by DI:**
```typescript
providers: [LoanService]
// Equivalent to: { provide: LoanService, useClass: LoanService }
// Use: the class under test; any real dep you want DI to instantiate
```

**2. `useValue` — replace with a pre-built object (mock, stub, fake):**
```typescript
providers: [{ provide: LoanRepository, useValue: mockLoanRepository }]
// Use: jest.Mocked objects, hand-rolled fakes, simple stubs
// Most common for mocking dependencies in unit tests
```

**3. `useClass` — replace with a different class:**
```typescript
providers: [{ provide: PaymentGateway, useClass: MockPaymentGateway }]
// Use: when the replacement has its own logic or state (fake implementations)
// DI instantiates MockPaymentGateway and injects its dependencies
```

**4. `useFactory` — replace with a factory function:**
```typescript
providers: [{
  provide: ConfigService,
  useFactory: () => ({
    get: (key: string) => ({ DB_URL: 'postgres://test', REDIS_URL: 'redis://test' })[key],
  }),
}]
// Use: when the mock needs to be constructed dynamically, or when it depends
// on other providers (inject them via the factory's parameter list)
```

**5. `useExisting` — alias one token to another:**
```typescript
providers: [{ provide: 'LEGACY_SERVICE', useExisting: LoanService }]
// Use: when two injection tokens should resolve to the same instance
```

At 5 YOE, `useValue` with `jest.Mocked<T>` objects covers 80% of unit test cases. `useFactory` is the right reach when the mock needs access to test-scope variables or other providers.

**Q8. How do you correctly type a `jest.Mocked<T>` dependency and use it in `createTestingModule`?**
A:
```typescript
import { Test, TestingModule } from '@nestjs/testing';
import { LoanService } from './loan.service';
import { LoanRepository } from './loan.repository';
import { EventBus } from '../events/event-bus';

describe('LoanService', () => {
  let service: LoanService;
  let loanRepo: jest.Mocked<LoanRepository>;
  let eventBus: jest.Mocked<EventBus>;

  beforeEach(async () => {
    // Build typed mocks before passing to the module
    loanRepo = {
      findById: jest.fn(),
      save: jest.fn(),
      findAllPending: jest.fn(),
    } as jest.Mocked<LoanRepository>;

    eventBus = {
      publish: jest.fn(),
    } as jest.Mocked<EventBus>;

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        LoanService,
        { provide: LoanRepository, useValue: loanRepo },
        { provide: EventBus, useValue: eventBus },
      ],
    }).compile();

    service = module.get<LoanService>(LoanService);
  });

  it('publishes a loan.approved event when approval succeeds', async () => {
    loanRepo.findById.mockResolvedValue(buildLoanFixture({ status: 'PENDING' }));
    loanRepo.save.mockResolvedValue(buildLoanFixture({ status: 'APPROVED' }));
    eventBus.publish.mockResolvedValue(undefined);

    await service.approveLoan('loan-123');

    expect(eventBus.publish).toHaveBeenCalledWith(
      expect.objectContaining({ type: 'loan.approved', loanId: 'loan-123' })
    );
  });
});
```

The typed mock is declared with `let loanRepo: jest.Mocked<LoanRepository>` so TypeScript knows all methods are `jest.MockedFunction` — giving you autocomplete on `.mockResolvedValue()`, `.mockReturnValue()`, and `.toHaveBeenCalledWith()`. Build the mock object before the module so the same reference is captured both in `useValue` and in the test's closure — this is what lets you call `loanRepo.findById.mockResolvedValue(...)` inside each `it` block.

## Section 3: `overrideProvider`, `overrideModule`, `overrideGuard`, `overridePipe`

**Q9. When do you need `overrideProvider()` instead of listing a replacement in `providers`?**
A: `overrideProvider()` is necessary when the provider you want to replace is declared inside an imported module — not in your test's `providers` array. If you import `LoanModule` (which internally declares `LoanRepository`), you cannot override `LoanRepository` by listing it in `providers` — NestJS would see two registrations and the module-declared one wins. `overrideProvider()` intercepts the token in the DI graph and replaces it regardless of where it was declared:

```typescript
// LoanModule internally declares LoanRepository and CreditBureauClient
// You want to test LoanService with a real LoanModule but mock CreditBureauClient

const module = await Test.createTestingModule({
  imports: [LoanModule],           // imports real module
})
  .overrideProvider(CreditBureauClient)   // replaces a provider declared inside LoanModule
  .useValue(mockCreditBureauClient)
  .overrideProvider(ConfigService)
  .useFactory({
    factory: () => ({ get: jest.fn().mockReturnValue('test-value') }),
  })
  .compile();
```

The chaining syntax (`.overrideProvider().useValue().overrideProvider().useClass()`) lets you override multiple providers before `.compile()`. Each call to `overrideProvider()` returns the `TestingModuleBuilder` so the chain stays fluent.

**Q10. How do you use `overrideGuard()` to bypass authentication in a controller integration test?**
A: Guards run as part of the NestJS request pipeline — in a controller test with a running HTTP server, authentication guards will reject requests unless you provide valid credentials or bypass them. `overrideGuard()` replaces a guard class with a stub that always allows (or always denies) the request:

```typescript
const module = await Test.createTestingModule({
  imports: [LoanModule],
})
  .overrideGuard(JwtAuthGuard)
  .useValue({
    canActivate: (context: ExecutionContext) => {
      // Inject a mock user into the request so @CurrentUser() decorators work
      const req = context.switchToHttp().getRequest();
      req.user = { sub: 'test-user-id', role: 'BORROWER' };
      return true;
    },
  })
  .compile();

const app = module.createNestApplication();
await app.init();

const response = await request(app.getHttpServer())
  .post('/loans')
  .send(loanPayload);

expect(response.status).toBe(201);
```

Injecting a mock user into `req.user` is critical — many controllers use `@CurrentUser()` decorators that read from `req.user`. Without it, controller logic that depends on the authenticated user will fail with a `TypeError: Cannot read properties of undefined`.

**Q11. How do you override a pipe, interceptor, and filter in a test module?**
A: NestJS provides `overridePipe()`, `overrideInterceptor()`, and `overrideFilter()` following the same pattern as `overrideGuard()`:

```typescript
const module = await Test.createTestingModule({
  imports: [LoanModule],
})
  // Remove validation for controller tests that focus on business logic
  .overridePipe(ValidationPipe)
  .useValue({ transform: (value: any) => value })  // pass-through

  // Remove logging interceptor to keep test output clean
  .overrideInterceptor(LoggingInterceptor)
  .useValue({ intercept: (_ctx: any, next: any) => next.handle() })

  // Replace error filter with one that lets errors propagate naturally
  .overrideFilter(HttpExceptionFilter)
  .useValue({ catch: (_exception: any, host: any) => {
    throw _exception; // rethrow for test assertion
  }})
  .compile();
```

In practice: override `ValidationPipe` when testing controllers for business logic (you don't need to test that NestJS validates DTOs — that's framework behaviour). Keep the real `ValidationPipe` when writing tests that specifically verify your DTO validation rules. Override interceptors and filters when they add noise (logging, metrics) that clutters test output or changes the response shape in ways that make assertions harder.

**Q12. How do you override an entire module in a test to replace a third-party or infrastructure module?**
A: `overrideModule()` replaces an entire imported module with a test double module. This is useful when an imported module has side effects at init time — opens a DB connection, starts a scheduler, registers webhooks:

```typescript
// TypeOrmModule opens a real DB connection on init — replace it entirely
const module = await Test.createTestingModule({
  imports: [LoanModule], // LoanModule imports TypeOrmModule internally
})
  .overrideModule(TypeOrmModule)
  .useModule({
    module: class FakeTypeOrmModule {},
    providers: [
      { provide: getRepositoryToken(Loan), useValue: mockLoanRepo },
      { provide: getRepositoryToken(User), useValue: mockUserRepo },
    ],
    exports: [
      { provide: getRepositoryToken(Loan), useValue: mockLoanRepo },
      { provide: getRepositoryToken(User), useValue: mockUserRepo },
    ],
  })
  .compile();
```

A more common pattern: override the specific TypeORM repository tokens using `overrideProvider(getRepositoryToken(Loan))` — this is simpler than overriding the entire `TypeOrmModule` and avoids having to re-export all repository tokens.

## Section 4: Testing Controllers, Guards, and Interceptors

**Q13. How do you test a NestJS controller with `Test.createTestingModule()` — with and without a running HTTP server?**
A: Two approaches, each for a different test scope:

**Without HTTP server — test the controller class directly:**
```typescript
// Tests controller method logic without HTTP serialisation, routing, or middleware
const module = await Test.createTestingModule({
  controllers: [LoanController],
  providers: [
    { provide: LoanService, useValue: mockLoanService },
  ],
}).compile();

const controller = module.get<LoanController>(LoanController);

it('returns the created loan', async () => {
  mockLoanService.create.mockResolvedValue(buildLoanFixture({ id: 'loan-123' }));
  const result = await controller.createLoan(createLoanDto, mockUser);
  expect(result.id).toBe('loan-123');
});
```

**With HTTP server — test the full request pipeline:**
```typescript
// Tests routing, guards, pipes, interceptors, and response serialisation
const module = await Test.createTestingModule({
  imports: [LoanModule],
})
  .overrideGuard(JwtAuthGuard).useValue({ canActivate: () => true })
  .overrideProvider(LoanService).useValue(mockLoanService)
  .compile();

const app = module.createNestApplication();
app.useGlobalPipes(new ValidationPipe({ transform: true, whitelist: true }));
await app.init();

it('returns 201 with the created loan', async () => {
  mockLoanService.create.mockResolvedValue(buildLoanFixture({ id: 'loan-123' }));

  const res = await request(app.getHttpServer())
    .post('/loans')
    .set('Authorization', 'Bearer test-token')
    .send({ amount: 500000, tenure: 24 });

  expect(res.status).toBe(201);
  expect(res.body.id).toBe('loan-123');
});

afterAll(async () => await app.close());
```

Rule: test controllers without HTTP for unit-level logic tests (guard logic, response mapping, error handling). Test with HTTP for integration-level tests that verify routing, DTO validation, response serialisation, and the interaction of multiple middleware layers.

**Q14. What is `createNestApplication()` on a `TestingModule`, and what does it give you that bare `moduleRef` doesn't?**
A: `module.createNestApplication()` wraps the compiled `TestingModule` in a full NestJS application instance — adding the HTTP adapter (Express or Fastify), middleware pipeline, exception filters, and interceptors. It's the equivalent of `NestFactory.create()` but using the already-compiled test module instead of a production module. What it gives you:
- A real HTTP server (`app.getHttpServer()`) that `supertest` can make requests against.
- Global middleware registration (`app.use(helmet())`, `app.useGlobalPipes()`).
- Application lifecycle hooks (`onApplicationBootstrap`, `onApplicationShutdown`).
- `app.close()` — cleanly shuts down the HTTP server and runs destroy hooks.

What it does not do automatically: start listening on a port. `supertest` uses the `http.Server` reference directly and handles port binding internally — you never need to call `app.listen()` in a test. Always call `await app.init()` before making requests and `await app.close()` in `afterAll`.

## Section 5: Lifecycle Hooks and Teardown

**Q15. When does `onModuleInit` run in a `TestingModule`, and how does it affect test setup?**
A: `onModuleInit` runs as part of `.compile()` — specifically at the end of the compile step, after all providers are instantiated and wired. If any provider implements `OnModuleInit` and its `onModuleInit()` method is async, `compile()` awaits it before returning. This has two important implications for tests:

**Implication 1 — Side effects at compile time:**
If a provider's `onModuleInit` opens a database connection, registers a cron job, or makes an HTTP call, this happens inside your `beforeEach` when you call `.compile()`. This is usually wrong for a unit test — you didn't intend to open a real DB connection. Fix: mock the provider that has the `onModuleInit` side effect, or use `overrideModule` to replace the offending module.

**Implication 2 — Init logic is tested automatically:**
If the class under test uses `onModuleInit` to perform required setup (e.g., loading configuration, warming a cache), that setup runs during compile. Your test can assert on the post-init state immediately after `.compile()` without any additional triggering.

```typescript
// If LoanService.onModuleInit() loads loan products from DB
it('loads loan products during module init', async () => {
  mockLoanRepo.findAllProducts.mockResolvedValue([mockProduct]);

  const module = await Test.createTestingModule({
    providers: [LoanService, { provide: LoanRepository, useValue: mockLoanRepo }],
  }).compile(); // onModuleInit runs here — mockLoanRepo.findAllProducts is called

  const service = module.get<LoanService>(LoanService);
  expect(service.cachedProducts).toHaveLength(1); // already populated
});
```

**Q16. When should you call `moduleRef.close()` and what does it do?**
A: `moduleRef.close()` runs `onModuleDestroy` lifecycle hooks on all providers in the module, then disposes of the module context. You should call it in `afterAll` for any `TestingModule` that:
- Has providers with `onModuleDestroy` hooks (e.g., a service that closes a connection, cancels scheduled jobs, or flushes a buffer).
- Wraps a running NestJS application — `app.close()` calls `moduleRef.close()` internally.
- Was created with `beforeAll` (shared across tests) — it should be closed exactly once after all tests finish.

For `TestingModule` created in `beforeEach` (fresh per test), `afterEach` should call `.close()`. In practice many teams skip this for pure unit test modules (no I/O, no side effects) and only call it when the module has real connections or scheduled tasks. The symptom of skipping it when you shouldn't: Jest's `detectOpenHandles` reports hanging interval or connection handles.

```typescript
describe('EmiSchedulerService', () => {
  let module: TestingModule;
  let service: EmiSchedulerService;

  beforeAll(async () => {
    module = await Test.createTestingModule({
      providers: [EmiSchedulerService, { provide: EmiRepository, useValue: mockRepo }],
    }).compile();
    service = module.get(EmiSchedulerService);
  });

  afterAll(async () => {
    await module.close(); // runs onModuleDestroy — stops cron intervals
  });
});
```

## Section 6: TypeORM and Repository Testing Patterns

**Q17. How do you mock TypeORM repositories in `createTestingModule` using `getRepositoryToken()`?**
A: TypeORM repositories in NestJS are provided under a token generated by `getRepositoryToken(EntityClass)`. You must use this exact token to override them — providing a plain `Repository` class won't match:

```typescript
import { getRepositoryToken } from '@nestjs/typeorm';
import { Repository } from 'typeorm';

describe('LoanRepository (unit)', () => {
  let service: LoanService;
  let ormRepo: jest.Mocked<Repository<Loan>>;

  beforeEach(async () => {
    ormRepo = {
      findOne: jest.fn(),
      save: jest.fn(),
      create: jest.fn(),
      find: jest.fn(),
      createQueryBuilder: jest.fn(),
    } as unknown as jest.Mocked<Repository<Loan>>;

    const module = await Test.createTestingModule({
      providers: [
        LoanService,
        {
          provide: getRepositoryToken(Loan), // exact token TypeORM uses
          useValue: ormRepo,
        },
      ],
    }).compile();

    service = module.get<LoanService>(LoanService);
  });

  it('finds a loan by ID', async () => {
    ormRepo.findOne.mockResolvedValue(buildLoanFixture({ id: 'loan-123' }));
    const result = await service.findById('loan-123');
    expect(result.id).toBe('loan-123');
  });
});
```

`as unknown as jest.Mocked<Repository<Loan>>` is the correct TypeScript pattern — `Repository<Loan>` has many methods, and building a complete typed object literal would require mocking every one. Cast through `unknown` to tell TypeScript you're intentionally providing a partial implementation. Only mock the methods your service actually calls.

**Q18. How do you test a service that uses `DataSource` or `QueryRunner` for transactions?**
A: Services that manage transactions directly via `DataSource` require mocking the transaction chain — `dataSource.createQueryRunner()`, `queryRunner.connect()`, `queryRunner.startTransaction()`, `queryRunner.commitTransaction()`, `queryRunner.rollbackTransaction()`, and `queryRunner.release()`:

```typescript
describe('DisbursementService (unit)', () => {
  let service: DisbursementService;
  let mockDataSource: jest.Mocked<DataSource>;
  let mockQueryRunner: jest.Mocked<QueryRunner>;

  beforeEach(async () => {
    mockQueryRunner = {
      connect: jest.fn(),
      startTransaction: jest.fn(),
      commitTransaction: jest.fn(),
      rollbackTransaction: jest.fn(),
      release: jest.fn(),
      manager: {
        save: jest.fn(),
        findOne: jest.fn(),
      },
    } as unknown as jest.Mocked<QueryRunner>;

    mockDataSource = {
      createQueryRunner: jest.fn().mockReturnValue(mockQueryRunner),
    } as unknown as jest.Mocked<DataSource>;

    const module = await Test.createTestingModule({
      providers: [
        DisbursementService,
        { provide: DataSource, useValue: mockDataSource },
      ],
    }).compile();

    service = module.get<DisbursementService>(DisbursementService);
  });

  it('rolls back the transaction on payment gateway failure', async () => {
    mockQueryRunner.manager.findOne.mockResolvedValue(buildLoanFixture());
    mockQueryRunner.manager.save.mockResolvedValue(undefined);
    // Simulate the payment gateway throwing after the DB write
    jest.spyOn(service['paymentGateway'], 'transfer').mockRejectedValue(
      new Error('GATEWAY_TIMEOUT')
    );

    await expect(service.disburse('loan-123')).rejects.toThrow('GATEWAY_TIMEOUT');

    expect(mockQueryRunner.rollbackTransaction).toHaveBeenCalled();
    expect(mockQueryRunner.release).toHaveBeenCalled(); // must always be called
  });
});
```

The `release()` assertion is important — a transaction test should verify that `queryRunner.release()` is always called, even on the failure path. A missing `release()` call in production is a connection pool leak.

## Section 7: Pitfalls and Anti-patterns

**Q19. What is the "full AppModule in unit tests" anti-pattern, and what does it produce?**
A: Importing `AppModule` (the root application module) into `createTestingModule` for a unit test gives you the entire application — every module, every provider, every connection, every cron job — when you only needed one service. Consequences:
- **Slow tests** — `AppModule` imports `TypeOrmModule`, which opens a real DB connection, and `ScheduleModule`, which starts a cron scheduler. A unit test suite that imports `AppModule` takes seconds per test file instead of milliseconds.
- **Environmental dependency** — the test requires a real database to be running, or it fails with a connection error before the first assertion.
- **Hidden dependencies** — because everything is available, the service under test may use a provider you didn't intend to include, masking the fact that your service has too many dependencies.
- **Open handle warnings** — the DB connection and cron scheduler stay open after the test unless `moduleRef.close()` is called, causing Jest to warn about open handles or hang on exit.

Fix: include only the service under test and mock providers for its declared dependencies. The test module should be the smallest possible graph that makes the test compile and run.

**Q20. Why does calling `module.get()` after `compile()` in a `beforeAll` work safely, but reassigning the result inside a `beforeEach` cause independence violations?**
A: `module.get()` returns the singleton instance from the DI container. The instance itself is the same object across all tests — it is not reset between tests. If tests share this instance and that instance accumulates state (a cached result, an in-memory counter, a spy call record), test B reads the state left by test A — a classic independence violation. The correct pattern for a `beforeAll` + `module.get()` combination is to pair it with `beforeEach` mock resets:

```typescript
describe('LoanService', () => {
  let module: TestingModule;
  let service: LoanService;
  let mockRepo: jest.Mocked<LoanRepository>;

  // BAD — module created once, mocks not reset between tests
  beforeAll(async () => {
    mockRepo = { findById: jest.fn(), save: jest.fn() } as any;
    module = await Test.createTestingModule({
      providers: [LoanService, { provide: LoanRepository, useValue: mockRepo }],
    }).compile();
    service = module.get(LoanService);
  });

  // GOOD — add this to reset mock state between tests
  afterEach(() => {
    jest.clearAllMocks(); // clears call history and return values
  });
});
```

Alternatively, create the entire module in `beforeEach` (fresh instance per test) — this is the safest pattern for unit tests where the module is cheap to compile. Use `beforeAll` only when the module is expensive to compile (e.g., it imports a real module with `onModuleInit` work).

**Q21. What happens when you forget to `await` the `.compile()` call, and how does the failure manifest?**
A: Without `await`, `module` is assigned a `Promise<TestingModule>` rather than a `TestingModule`. The subsequent `module.get(LoanService)` call is then `Promise.get()` — which is `undefined` — and TypeScript may or may not catch this depending on your type annotations. At runtime: `service` is `undefined`, the first test that calls `service.someMethod()` throws `TypeError: Cannot read properties of undefined (reading 'someMethod')`, which looks like a module wiring problem but is actually a missing `await`. The fix is trivial but the error message is confusing. TypeScript catches it if you type `module` as `TestingModule` rather than `any` — `Promise<TestingModule>` is not assignable to `TestingModule`. Always use explicit types on variables holding `TestingModule` instances.

**Q22. How do circular dependency issues manifest in `Test.createTestingModule()`, and how do you resolve them?**
A: Circular dependencies — `ServiceA` depends on `ServiceB` which depends on `ServiceA` — cause NestJS's DI container to fail during `.compile()` with an error like `Nest cannot create the ServiceA instance. The module at index [0] of the ServiceA "providers" array is undefined`. The error is the same in production and in `createTestingModule`. Resolution options:

**Option 1 — `forwardRef()` (NestJS's official solution):**
```typescript
@Injectable()
export class ServiceA {
  constructor(
    @Inject(forwardRef(() => ServiceB))
    private readonly serviceB: ServiceB,
  ) {}
}
```
And in the module:
```typescript
providers: [
  { provide: ServiceA, useClass: ServiceA },
  { provide: ServiceB, useClass: ServiceB },
]
```

**Option 2 — Redesign (preferred):**
Circular dependencies are a design smell — they usually indicate that two services should be merged, or that a third service should extract the shared logic. In tests, a circular dependency makes mocking harder because you must mock both sides of the circle. If the circular dependency only appears in tests, it's a sign the production code should be refactored.

**Option 3 — Break the cycle in tests by mocking one side:**
```typescript
// Mock ServiceB entirely — the circle is broken at the mock boundary
providers: [
  ServiceA,
  { provide: ServiceB, useValue: { methodUsedByA: jest.fn() } },
]
```

## Section 8: Scenario / System Design Style Questions

**Q23. "A junior developer's NestJS unit test suite takes 45 seconds per file. You open a test file and see `imports: [AppModule]` in every `createTestingModule` call. Walk me through fixing it."**
A: `AppModule` pulls in the full application — TypeORM (opens a real DB connection), ScheduleModule (starts cron jobs), and every other module in the app. The fix is to strip the test down to only what the unit under test needs.

**Step 1 — Identify the class under test and its direct dependencies:**
```typescript
// The class under test
@Injectable()
export class EmiService {
  constructor(
    private readonly emiRepo: EmiRepository,
    private readonly loanRepo: LoanRepository,
    private readonly notificationService: NotificationService,
  ) {}
}
```

**Step 2 — Replace `AppModule` with exactly those providers:**
```typescript
// Before — 45 seconds
const module = await Test.createTestingModule({
  imports: [AppModule],
}).compile();

// After — milliseconds
const module = await Test.createTestingModule({
  providers: [
    EmiService,
    { provide: EmiRepository, useValue: { findDue: jest.fn(), save: jest.fn() } },
    { provide: LoanRepository, useValue: { findById: jest.fn() } },
    { provide: NotificationService, useValue: { send: jest.fn() } },
  ],
}).compile();
```

**Step 3 — Handle ConfigService if the service reads config:**
`AppModule` is often imported because the service reads from `ConfigService`. Replace it:
```typescript
{
  provide: ConfigService,
  useValue: { get: jest.fn((key) => ({ DB_URL: 'test', MAX_EMI_AMOUNT: 100000 })[key]) },
}
```

**Step 4 — For tests that genuinely need an integration module:**
Split into two test files: `emi.service.spec.ts` (unit, milliseconds) and `emi.service.integration.spec.ts` (imports `EmiModule`, uses `testcontainers`). Keep them in separate Jest configs with separate run commands.

**Step 5 — Enforce going forward:**
Add an ESLint rule or a PR review checklist item: "No `AppModule` in unit test files." A `jest.config.ts` `testPathPattern` can separate unit and integration test runs so the CI feedback loop stays fast.

**Q24. "You're reviewing a PR for a NestJS loan approval flow. The test creates a `TestingModule` with `LoanService` but also imports `TypeOrmModule.forRoot()` directly in `createTestingModule`. The test author says 'I needed the real repository.' What's the problem, and what's the right architecture?"**
A: Importing `TypeOrmModule.forRoot()` in a unit test creates a real database connection — which means the test requires a running database, is slow (DB connection overhead), non-hermetic (results depend on what's in the DB), and non-repeatable (state leaks between tests). The test author conflated "I need to test the service with a repository" with "I need a real database."

**The problem at each layer:**
- If the intent is to unit test `LoanService` — mock the repository entirely. The service's logic is what's under test, not the DB.
- If the intent is to integration test the repository — use `testcontainers` for a real DB, but test the repository class directly, not through the service.
- If the intent is to integration test the service + repository together — `testcontainers` provides the DB; `TypeOrmModule.forRoot()` connects to it. But this is an integration test, not a unit test.

**The right architecture:**
```
loan.service.spec.ts              → unit test; mocked repo; no DB; milliseconds
loan.repository.integration.spec.ts → integration test; testcontainers DB; real TypeORM
loan.service.integration.spec.ts  → integration test; testcontainers DB; tests the pair
```

Each layer tests different things. Unit tests verify business logic. Integration tests verify persistence correctness. Mixing them — real DB in a "unit" test — gets the worst of both: the test is slow but it still doesn't catch query plan bugs because the DB schema may not match production.

## Quick Reference: `Test.createTestingModule()` Cheat Sheet

| Task                                         | How                                                                                 |
|----------------------------------------------|-------------------------------------------------------------------------------------|
| Create a test module                         | `Test.createTestingModule({ providers: [...] }).compile()`                          |
| Get a singleton provider                     | `module.get(ServiceClass)` or `module.get<ServiceClass>(ServiceClass)`              |
| Get a scoped provider                        | `await module.resolve(ScopedService)`                                               |
| Mock a dependency with a value               | `{ provide: Dep, useValue: mockDep }`                                               |
| Mock a dependency with a factory             | `{ provide: Dep, useFactory: () => mockDep }`                                       |
| Override a provider in an imported module    | `.overrideProvider(Token).useValue(mock)` before `.compile()`                       |
| Bypass a guard                               | `.overrideGuard(GuardClass).useValue({ canActivate: () => true })`                  |
| Remove a pipe                                | `.overridePipe(PipeClass).useValue({ transform: (v) => v })`                        |
| Mock a TypeORM repository                    | `{ provide: getRepositoryToken(Entity), useValue: mockRepo }`                       |
| Create an HTTP server for E2E               | `module.createNestApplication()` then `await app.init()`                            |
| Close the module                             | `await module.close()` in `afterAll`                                                |
| Close the HTTP server                        | `await app.close()` in `afterAll`                                                   |
| Avoid open handle warnings                   | Always `close()` modules and apps; use `detectOpenHandles: true` in Jest config     |

**Tip for the interview:** At 5 YOE, `Test.createTestingModule()` questions come wrapped in debugging scenarios — "why is the unit test slow," "why does this test need a real database," "how do you test a controller that has an auth guard." The answer always starts from the same diagnosis: identify what the test is actually testing, strip the module to the minimum graph that supports it, replace infrastructure with typed mocks, and use `overrideGuard`/`overrideProvider` when imports bring in providers you don't control. Have a concrete story ready — a full `AppModule` test suite you refactored to isolated providers (cutting compile time from 10 seconds to milliseconds), a controller test you fixed by overriding the `JwtAuthGuard` and injecting a mock user into the request context, or a transaction rollback test where you mocked the `QueryRunner` chain and asserted that `release()` was called on the failure path. That's the depth that lands at this level.
