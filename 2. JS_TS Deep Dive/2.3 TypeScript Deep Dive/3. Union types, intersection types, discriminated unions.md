---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Union Types

**Q1. What is a union type in TypeScript, and what does it mean semantically?**
A: A union type `A | B` means a value can be **either type A or type B** (or both, in the case of objects with overlapping shapes). TypeScript tracks that the value is *one of* the listed types but doesn't know *which one* at the point of the union — narrowing is required before accessing type-specific members. Unions model the common situation where a function accepts or returns values of different shapes, or where a variable can be in multiple states.

```ts
type StringOrNumber = string | number;
type Status = 'pending' | 'fulfilled' | 'rejected'; // literal union — a common idiom

function format(value: string | number): string {
  // TypeScript knows 'value' is string | number here
  // Can only access members common to BOTH types:
  return value.toString(); // ✓ — .toString() exists on both string and number

  // value.toFixed(2); // ❌ — .toFixed() only exists on number
}
```

**Q2. What is "narrowing," and what are the standard narrowing techniques for union types?**
A: Narrowing is the process of **refining a union type to a more specific type** within a block of code, based on a runtime check that TypeScript can verify statically. After narrowing, TypeScript knows which specific branch of the union is active and allows access to type-specific members.

Standard narrowing techniques:
1. **`typeof` guard**: for primitive types (`string`, `number`, `boolean`, `bigint`, `symbol`, `undefined`, `function`).
2. **`instanceof` guard**: for class instances.
3. **`in` operator**: checks whether a property key exists on an object.
4. **Equality narrowing**: comparing against specific literal values.
5. **Truthiness narrowing**: filtering out `null`/`undefined`/falsy values.
6. **Custom type predicates** (`x is Type` return type): user-defined narrowing functions.
7. **Discriminant property**: comparing a shared literal-typed property — see Section 3.

```ts
type Result = { kind: 'ok'; value: number } | { kind: 'err'; message: string };

function handleResult(r: Result): string {
  // typeof: primitives
  if (typeof r.value === 'number') { /* narrowed */ }

  // in: property existence
  if ('value' in r) return `Value: ${r.value}`; // TypeScript knows r has .value

  // Equality: literal comparison
  if (r.kind === 'ok') return `OK: ${r.value}`; // narrowed to ok branch
  return `Error: ${r.message}`;                  // narrowed to err branch
}

// Custom type predicate
function isString(x: unknown): x is string {
  return typeof x === 'string';
}

function process(x: string | number[]) {
  if (isString(x)) {
    x.toUpperCase(); // TypeScript knows x is string here
  } else {
    x.map(n => n * 2); // TypeScript knows x is number[] here
  }
}
```

**Q3. What is the difference between `unknown`, `any`, and a wide union like `string | number | boolean | object | ...`?**
A:
- **`any`**: opt-out of type checking entirely — TypeScript allows any operation on an `any` value, including operations that would fail at runtime. It's contagious: `any + number = any`. Avoid in new code; appears in legacy code or when interacting with untyped JS.
- **`unknown`**: the type-safe alternative to `any`. A value of type `unknown` cannot be used in any operation until it has been narrowed to a more specific type. Appropriate for values whose type is genuinely not known at compile time (e.g., API responses, `JSON.parse()` results, `catch` block error variables).
- **Wide union** (`string | number | boolean`): explicitly lists the permitted types. TypeScript knows which specific types are possible and can narrow between them. More restrictive than `unknown` (can't assign a `Date` to `string | number | boolean`), but also more informative than `unknown` (TypeScript can guide narrowing based on the known possibilities).

```ts
function dangerousAny(x: any) {
  x.toUpperCase();        // ✓ compiles, may blow up at runtime
  x * 2;                  // ✓ compiles, may blow up at runtime
}

function safeUnknown(x: unknown) {
  x.toUpperCase();        // ❌ TypeScript error: Object is of type 'unknown'
  if (typeof x === 'string') {
    x.toUpperCase();      // ✓ now narrowed to string
  }
}

// The catch variable is unknown in TS4.4+:
try { /* ... */ } catch (err) {
  // err is unknown — must narrow before using
  if (err instanceof Error) console.log(err.message);
  else console.log(String(err));
}
```

### Section 2: Intersection Types

**Q4. What is an intersection type in TypeScript, and what does it mean semantically?**
A: An intersection type `A & B` means a value must satisfy **both type A and type B simultaneously**. For object types, the intersection is equivalent to an object that has all the properties of both types (their "union of fields"). For primitive types, intersection between incompatible primitives produces `never` (since no value can be both `string` and `number`).

```ts
type Named = { name: string };
type Aged  = { age: number };
type Person = Named & Aged; // { name: string; age: number }

const person: Person = { name: 'Alice', age: 30 }; // ✓ must have BOTH name and age
const partial: Named = { name: 'Alice' };           // ❌ not assignable to Person (missing age)

// Primitive intersection = never (no value is simultaneously string AND number):
type Impossible = string & number; // type is never
```

**Q5. What are the primary use cases for intersection types in practice?**
A: Three main patterns:

1. **Mixins and trait composition**: combining capability types that each add specific fields/methods, then composing them.
2. **Branding / opaque types**: intersecting a base type with a unique phantom type to create a nominally distinct type that the type system treats differently even if structurally identical.
3. **Extending third-party types without inheritance**: adding properties to an existing type from a library without modifying or extending the original.

```ts
// 1. Mixin composition
type Serializable = { serialize(): string };
type Loggable     = { log(msg: string): void };
type Plugin = Serializable & Loggable & { name: string };

// 2. Branding: prevent raw strings from being used where a "UserId" is expected
type UserId = string & { readonly __brand: 'UserId' };
type PostId = string & { readonly __brand: 'PostId' };

function fetchUser(id: UserId): Promise<User> { /* ... */ }

const rawId = 'abc123';
fetchUser(rawId);                         // ❌ — string is not UserId
fetchUser(rawId as UserId);               // ✓ — explicit brand assertion
fetchUser('wrong-id' as unknown as PostId); // ❌ — PostId is not UserId ✓ (intentional)

// 3. Extending third-party types
import type { Request } from 'express';
type AuthenticatedRequest = Request & { user: { id: string; roles: string[] } };

function protectedRoute(req: AuthenticatedRequest) {
  console.log(req.user.id); // TypeScript knows this exists
}
```

**Q6. What is the difference between interface `extends` and intersection types, and when should you prefer each?**
A: Both combine types, but they differ in declaration semantics and error message quality:
- **Interface `extends`**: creates a named type with its own identity in the type system. Declaration merging applies (two interfaces with the same name merge). Error messages reference the interface name. Better for public APIs and cases where the combined type needs a standalone name.
- **Intersection `&`**: creates an anonymous structural combination. Can be used inline. No declaration merging. Error messages may be harder to read for complex intersections. Better for one-off type combinations, generic constraints, and mixin patterns.

A critical difference with **conflicting property types**: if two intersected types have the same property name but different types (e.g., both have `id` but one as `string` and one as `number`), the intersection's `id` property becomes `string & number = never` — silently making the type uninhabitable. An `extends`-based interface would produce a clear compile error at the `extends` declaration. Always watch for accidental `never` properties in intersections.

```ts
type A = { id: string };
type B = { id: number };
type C = A & B;
// C.id is string & number = never — any attempt to use C.id produces an error

// With interface extends: explicit error at declaration
interface D extends A, B {} // ❌ Error: Types of property 'id' are incompatible
```

### Section 3: Discriminated Unions

**Q7. What is a discriminated union, and what three elements make it work?**
A: A discriminated union (also called a "tagged union" or "algebraic data type") is a union of object types where each member has a **shared discriminant property** — a property with a **literal type** that uniquely identifies that union member. This enables TypeScript to narrow the type precisely based on comparing that discriminant property. Three required elements:
1. **A shared property name** present on every member of the union.
2. **A unique literal type** for that property on each member (`'circle'`, `'square'`, `'triangle'` — no two members share the same literal).
3. **Narrowing via equality check** on the discriminant property — TypeScript then knows exactly which union member you're dealing with.

```ts
type Circle   = { kind: 'circle';   radius: number };
type Square   = { kind: 'square';   side: number };
type Triangle = { kind: 'triangle'; base: number; height: number };

type Shape = Circle | Square | Triangle;

function area(shape: Shape): number {
  switch (shape.kind) { // narrow via discriminant
    case 'circle':   return Math.PI * shape.radius ** 2;    // shape: Circle ✓
    case 'square':   return shape.side ** 2;                // shape: Square ✓
    case 'triangle': return 0.5 * shape.base * shape.height; // shape: Triangle ✓
  }
}
```

**Q8. What is "exhaustiveness checking," and how do you implement it with a discriminated union?**
A: Exhaustiveness checking ensures that every possible union variant is handled — the TypeScript compiler will produce an error if a new variant is added to the union but the switch/if-chain isn't updated. The standard technique assigns the discriminated value to `never` in the default branch: since `never` is the bottom type (no value is assignable to it), TypeScript errors if any union variant flows into the default case (because that variant's type would be assignable to `never`, which is impossible).

```ts
// Method 1: assertNever helper function
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(x)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':   return Math.PI * shape.radius ** 2;
    case 'square':   return shape.side ** 2;
    case 'triangle': return 0.5 * shape.base * shape.height;
    default:         return assertNever(shape); // compile error if any case is unhandled
  }
}

// Now add a new variant:
type Rectangle = { kind: 'rectangle'; width: number; height: number };
type Shape = Circle | Square | Triangle | Rectangle; // ← added Rectangle

// area() now has a TypeScript error on assertNever(shape):
// ❌ Argument of type 'Rectangle' is not assignable to parameter of type 'never'
// This is the exhaustiveness check catching the missing case ✓

// Method 2: using the never type directly in the default case variable
function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':   return Math.PI * shape.radius ** 2;
    case 'square':   return shape.side ** 2;
    case 'triangle': return 0.5 * shape.base * shape.height;
    default: {
      const _exhaustive: never = shape; // error if shape is not never here
      throw new Error(`Unknown shape: ${_exhaustive}`);
    }
  }
}
```

**Q9. How does TypeScript narrow discriminated unions in `if/else` chains versus `switch` statements — is there a preference?**
A: TypeScript narrows discriminated unions equally well in both `switch` and `if/else` chains — both are sound. Preference is stylistic and contextual:
- **`switch`**: cleaner for multiple variants, especially with `break`-free `switch` using `return` in each case. The `default` + exhaustiveness check pattern is very natural here.
- **`if/else`**: more flexible when the discriminant check is combined with other conditions, or when the narrowing condition is more complex than a simple equality.

```ts
// if/else with discriminant:
function describe(shape: Shape): string {
  if (shape.kind === 'circle') {
    return `Circle with radius ${shape.radius}`;
  } else if (shape.kind === 'square') {
    return `Square with side ${shape.side}`;
  } else if (shape.kind === 'triangle') {
    return `Triangle`;
  } else {
    const _: never = shape; // exhaustiveness check works in if/else too
    throw new Error(`Unknown: ${_}`);
  }
}
```

**Q10. What happens to the discriminated union if the discriminant property has the same literal type on two members?**
A: If two members share the same discriminant value (e.g., both have `kind: 'circle'`), narrowing on `shape.kind === 'circle'` narrows to the **union of both those members** — not to a single member. TypeScript can only narrow to one specific member when the discriminant uniquely identifies it. This is a subtle design bug that TypeScript cannot warn about automatically — it's up to the developer to ensure discriminant values are unique across all union members.

```ts
type A = { kind: 'x'; a: string };
type B = { kind: 'x'; b: number }; // same discriminant value as A — BUG

type Union = A | B;

function handle(u: Union) {
  if (u.kind === 'x') {
    // u is narrowed to A | B — still a union, NOT fully narrowed!
    u.a; // ❌ Property 'a' does not exist on type 'A | B'
    u.b; // ❌ Property 'b' does not exist on type 'A | B'
    // You still need to further narrow with 'a' in u or 'b' in u
  }
}
```

### Section 4: Advanced Patterns

**Q11. What is the `Extract` and `Exclude` utility types, and how do they operate on union types?**
A: Both are built-in TypeScript utility types for filtering union members:
- **`Extract<T, U>`**: keeps only the union members of `T` that are **assignable to `U`**.
- **`Exclude<T, U>`**: removes from `T` the union members that are **assignable to `U`**.

They're implemented as **distributive conditional types** — TypeScript distributes the condition over each member of the union individually and collects the results.

```ts
type AllShapes = 'circle' | 'square' | 'triangle' | 'rectangle';

type RoundShapes = Extract<AllShapes, 'circle'>;                  // 'circle'
type FlatShapes  = Extract<AllShapes, 'square' | 'rectangle'>;   // 'square' | 'rectangle'
type NotRound    = Exclude<AllShapes, 'circle'>;                  // 'square' | 'triangle' | 'rectangle'

// On object union types:
type Events = { type: 'click'; x: number } | { type: 'keydown'; key: string } | { type: 'scroll' };
type MouseEvents = Extract<Events, { type: 'click' | 'scroll' }>;
// → { type: 'click'; x: number } | { type: 'scroll' }

type NonScrollEvents = Exclude<Events, { type: 'scroll' }>;
// → { type: 'click'; x: number } | { type: 'keydown'; key: string }
```

**Q12. What is a distributive conditional type, and how does it interact with unions?**
A: A conditional type `T extends U ? X : Y` is distributive over union members of `T` when `T` is a **naked type parameter** (not wrapped in a tuple, array, or mapped type). TypeScript evaluates the condition for each union member individually and unions the results:

```ts
// Distributive: T is a naked type parameter
type IsString<T> = T extends string ? true : false;
type R1 = IsString<string | number>; // true | false (= boolean) — distributed!

// Non-distributive: wrap T in a tuple to prevent distribution
type IsStringExact<T> = [T] extends [string] ? true : false;
type R2 = IsStringExact<string | number>; // false (whole union checked at once)

// Practical use: filter a union
type FilterOut<T, U> = T extends U ? never : T; // distributive Exclude
type OnlyStrings = FilterOut<string | number | boolean, number | boolean>; // string

// Built-in NonNullable uses this:
type NonNullable<T> = T extends null | undefined ? never : T;
type SafeString = NonNullable<string | null | undefined>; // string
```

**Q13. How do you model a result type (success/failure) using discriminated unions, and why is it better than throwing?**
A: A `Result<T, E>` type encodes success and failure as a union of two discriminated variants — callers are **forced by the type system** to handle both cases before accessing the value or error, unlike throwing where errors can propagate silently without the type system's help.

```ts
type Ok<T>  = { success: true;  value: T };
type Err<E> = { success: false; error: E };
type Result<T, E = Error> = Ok<T> | Err<E>;

// Constructor helpers
const ok  = <T>(value: T): Ok<T>   => ({ success: true,  value });
const err = <E>(error: E): Err<E>  => ({ success: false, error });

// Return type makes it explicit that this can fail:
async function fetchUser(id: string): Promise<Result<User, string>> {
  const res = await fetch(`/users/${id}`);
  if (!res.ok) return err(`HTTP ${res.status}`);
  return ok(await res.json());
}

// Caller MUST handle both cases — TypeScript enforces it:
const result = await fetchUser('42');
if (result.success) {
  renderUser(result.value); // TypeScript knows value exists here ✓
} else {
  showError(result.error);  // TypeScript knows error exists here ✓
}

// TypeScript prevents accessing .value without checking:
result.value; // ❌ Property 'value' does not exist on type 'Result<User, string>'
              // (because Err<string> has no .value)
```

**Q14. What are "template literal types" in union contexts, and how do they generate unions automatically?**
A: Template literal types can be combined with unions to automatically generate all combinations of literal string unions — the result is a union of all possible concatenations. This is a powerful compile-time string manipulation feature that eliminates the need to manually list every string variant.

```ts
type Direction = 'top' | 'bottom' | 'left' | 'right';
type Padding = `padding-${Direction}`;
// → 'padding-top' | 'padding-bottom' | 'padding-left' | 'padding-right'

type EventName = 'click' | 'focus' | 'blur';
type HandlerName = `on${Capitalize<EventName>}`;
// → 'onClick' | 'onFocus' | 'onBlur'

// Cross-product of two unions:
type Color = 'red' | 'blue';
type Shade = 'light' | 'dark';
type ColorShade = `${Shade}-${Color}`;
// → 'light-red' | 'light-blue' | 'dark-red' | 'dark-blue'
```

### Section 5: Scenario / Interview-Style Questions

**Q15. "You have a function that processes user input which can be a string, a number, or null. How do you type it safely and handle each case?"**
A: Type the parameter as `string | number | null` and use narrowing to handle each case. The order of narrowing matters — check `null` first (since it's the most restrictive), then use `typeof` for the primitive distinction:

```ts
function processInput(input: string | number | null): string {
  if (input === null) return 'No input provided';
  if (typeof input === 'string') return input.trim().toUpperCase();
  return input.toFixed(2); // TypeScript knows: only number left
}

// TypeScript narrows exhaustively — no `default` case needed here
// because after all three checks, all variants are handled.
```

**Q16. "A colleague uses `type` with `&` everywhere instead of `interface extends`. What's your advice?"**
A: Both work, and for many cases the choice is stylistic. I'd guide them toward `interface extends` when: (1) the combined type needs a stable, reusable name visible in error messages; (2) they're defining public library API types where declaration merging might be needed; (3) conflicting property types should produce an immediate, clear error at the declaration (not a silent `never` property). Use `&` for: (1) inline one-off type combinations; (2) generic constraints; (3) branding patterns; (4) mixing in utility types that aren't themselves interfaces. The critical thing to watch for with `&` is **accidental `never` properties** from conflicting field types — TypeScript won't warn, and the type becomes uninhabitable.

**Q17. "How would you add a new variant to a discriminated union safely — what steps ensure nothing is missed?"**
A: The exhaustiveness-checking pattern (Q8) makes this mechanical:
1. Add the new type to the union.
2. TypeScript immediately errors on every `switch`/`if-else` that uses `assertNever` or a `never`-typed default.
3. Fix each error by adding the missing case.
4. Compile again to confirm all errors are resolved.

This is the main reason to invest in exhaustiveness checking — it turns "add a new variant" from a manual search-and-update process into a compiler-driven task where TypeScript tells you exactly what needs updating.

**Q18. "How do discriminated unions compare to class inheritance for modeling polymorphic data in TypeScript?"**
A: Both can model "one of several shapes of data" but with different trade-offs:
- **Discriminated unions** are **data-focused**: pure plain-object types with no behavior, easy to serialize/deserialize (JSON-safe), pattern-matched via `switch`, natural for functional/immutable patterns. Adding a new variant requires updating all match sites (compiler-enforced). Adding a new operation (new function over the union) requires no changes to existing types.
- **Class inheritance** is **behavior-focused**: instances carry methods, support `instanceof` narrowing, can have private state. Adding a new operation (new method) requires updating every subclass. Adding a new subclass is easy but doesn't force updating callers.

In TypeScript's ecosystem (especially with React, Redux, and functional patterns), discriminated unions are far more common than class hierarchies for modeling domain data. Classes are preferred when instances need private mutable state, identity semantics (`===` comparing), or method inheritance.

## Problem 1 — Type-Safe Event System with Discriminated Unions

### Problem
Build a type-safe event emitter where: (1) each event has a specific payload type, (2) the listener callback receives the correctly typed payload for the event it listens to, (3) emitting an event with the wrong payload type is a compile error.

```ts
// Should work:
emitter.emit('click', { x: 10, y: 20 });
emitter.on('click', (payload) => console.log(payload.x)); // payload is { x: number; y: number }

// Should fail at compile time:
emitter.emit('click', { key: 'a' });   // ❌ wrong payload type
emitter.on('click', (p) => p.key);    // ❌ 'key' doesn't exist on click payload
emitter.emit('unknownevent', {});      // ❌ unknown event name
```

### Pattern Recognition
Discriminated union of event types + mapped type to extract payloads by event name + generic constraints to tie event name and payload together.

### Key Insight
Define a map type `EventMap` from event name to payload type, then use it to constrain `emit` and `on` generically: `<K extends keyof EventMap>(event: K, payload: EventMap[K])`. TypeScript resolves `EventMap[K]` to the specific payload type when `K` is inferred from the first argument.

### Solution

```ts
// 1. Define the event registry — all possible events and their payload types
interface EventMap {
  click:    { x: number; y: number };
  keydown:  { key: string; code: string; shiftKey: boolean };
  submit:   { formId: string; values: Record<string, string> };
  resize:   { width: number; height: number };
}

// 2. Type-safe EventEmitter
class TypedEventEmitter {
  // Listeners stored per event name — typed via EventMap
  private listeners = {} as {
    [K in keyof EventMap]?: Array<(payload: EventMap[K]) => void>;
  };

  on<K extends keyof EventMap>(
    event: K,
    listener: (payload: EventMap[K]) => void
  ): void {
    if (!this.listeners[event]) {
      this.listeners[event] = [];
    }
    this.listeners[event]!.push(listener);
  }

  off<K extends keyof EventMap>(
    event: K,
    listener: (payload: EventMap[K]) => void
  ): void {
    const list = this.listeners[event];
    if (list) {
      this.listeners[event] = list.filter(l => l !== listener) as typeof list;
    }
  }

  emit<K extends keyof EventMap>(event: K, payload: EventMap[K]): void {
    this.listeners[event]?.forEach(listener => listener(payload));
  }
}

// 3. Usage and verification
const emitter = new TypedEventEmitter();

// ✓ Correct usage — TypeScript infers K='click', payload: { x: number; y: number }
emitter.on('click', (payload) => {
  console.log(payload.x, payload.y); // ✓ both exist
  // payload.key;                    // ❌ 'key' does not exist on click payload
});

emitter.emit('click', { x: 10, y: 20 }); // ✓

// ❌ These all fail at compile time:
emitter.emit('click', { key: 'a' });           // ❌ missing x, y; has wrong key
emitter.emit('click', { x: 1, y: 2, z: 3 });  // ❌ excess property 'z'
emitter.on('keydown', (p) => p.x);            // ❌ 'x' does not exist on keydown payload
emitter.emit('mouseenter', { x: 1, y: 2 });   // ❌ 'mouseenter' not in EventMap
```

### Verification

```ts
// TypeScript infers payload types correctly:
emitter.on('keydown', (p) => {
  p.key;     // ✓ string
  p.code;    // ✓ string
  p.shiftKey; // ✓ boolean
});

emitter.on('submit', (p) => {
  p.formId;  // ✓ string
  p.values;  // ✓ Record<string, string>
});

// Adding a new event to EventMap automatically makes it available:
// interface EventMap { ...; custom: { data: unknown } }
// emitter.emit('custom', { data: 'anything' }); // ✓ immediately typeable
```

### Edge Cases
- **Extending the EventMap**: adding a new entry to `EventMap` automatically makes it available in `emit` and `on` without any changes to `TypedEventEmitter` itself — the generic constraints pick it up.
- **Wildcard listeners**: if you want a listener for all events, the type would need to be `(event: keyof EventMap, payload: EventMap[keyof EventMap]) => void` — which is sound but loses specific payload types inside the listener.

### Follow-up Questions
- "How would you make this work with `once` (fire-and-forget listener)?" → Add an `once` method that wraps the listener to call `off` after the first invocation, using the same `<K extends keyof EventMap>` generic pattern.
- "How would you serialize/log events without losing type information?" → Store events as discriminated union objects `{ type: K; payload: EventMap[K] }` — the `type` field acts as the discriminant for type-safe event replay.

## Problem 2 — Discriminated Union for API Response States

### Problem
Model the state of an asynchronous API call — idle, loading, success (with data), and error (with error info) — as a discriminated union. Implement a `render` function that handles all states and has compile-time exhaustiveness checking.

```ts
// All four states, no optional fields, no runtime undefined checks
type ApiState<T> = IdleState | LoadingState | SuccessState<T> | ErrorState;

function renderUser(state: ApiState<User>): string { /* exhaustive */ }
```

### Pattern Recognition
Discriminated union with a `status` discriminant, generic for the data type, exhaustiveness checking via `assertNever`.

### Key Insight
Using a discriminant property (`status`) with unique literal values and NO optional properties means TypeScript can narrow the type perfectly — there are no undefined field accesses, no `?` checks needed, and adding a new state produces a compile error on all `switch` statements that use `assertNever`.

### Solution

```ts
// Each state has ALL its fields required — no optional properties
type IdleState    = { status: 'idle' };
type LoadingState = { status: 'loading' };
type SuccessState<T> = { status: 'success'; data: T;   timestamp: number };
type ErrorState   = { status: 'error';   message: string; code: number };

type ApiState<T> = IdleState | LoadingState | SuccessState<T> | ErrorState;

// Exhaustiveness helper
function assertNever(x: never): never {
  throw new Error(`Unhandled state: ${JSON.stringify(x)}`);
}

// User type for the example
interface User { id: string; name: string; email: string }

// Exhaustive render function
function renderUserState(state: ApiState<User>): string {
  switch (state.status) {
    case 'idle':
      return 'Click to load user';

    case 'loading':
      return 'Loading...';

    case 'success':
      // TypeScript knows state is SuccessState<User> here:
      return `User: ${state.data.name} (${state.data.email}) — loaded at ${new Date(state.timestamp).toISOString()}`;

    case 'error':
      // TypeScript knows state is ErrorState here:
      return `Error ${state.code}: ${state.message}`;

    default:
      return assertNever(state); // compile error if any case is unhandled
  }
}

// State transitions — type-safe constructors
const idle:    ApiState<User> = { status: 'idle' };
const loading: ApiState<User> = { status: 'loading' };
const success: ApiState<User> = { status: 'success', data: { id: '1', name: 'Alice', email: 'alice@example.com' }, timestamp: Date.now() };
const error:   ApiState<User> = { status: 'error', message: 'Not found', code: 404 };
```

### Verification

```ts
// All four states render correctly:
renderUserState(idle);    // 'Click to load user'
renderUserState(loading); // 'Loading...'
renderUserState(success); // 'User: Alice (alice@...) — loaded at ...'
renderUserState(error);   // 'Error 404: Not found'

// TypeScript errors on invalid state access:
const s: ApiState<User> = loading;
s.data;    // ❌ Property 'data' does not exist on type 'ApiState<User>'
s.message; // ❌ Same

// After narrowing, TypeScript knows exactly what's available:
if (s.status === 'success') s.data.name; // ✓

// Adding a new state breaks the switch until handled:
// type RefreshingState = { status: 'refreshing'; previousData: User };
// type ApiState<T> = ... | RefreshingState;
// → assertNever(state) becomes a compile error ✓
```

### Edge Cases
- **Optional intermediate states**: if `SuccessState` should also be "refreshing" (loading new data while showing old), model it as a separate state `{ status: 'refreshing'; previousData: T }` rather than adding optional fields to `SuccessState` — keeps the discriminated union clean.
- **Generic parameter**: `ApiState<T>` is generic over the data type so it can be reused for `ApiState<User>`, `ApiState<Post[]>`, etc. without duplicating the state machine.

### Follow-up Questions
- "How would you implement a state machine for this (prevent invalid transitions, e.g., can't go from idle directly to error)?" → Define a `transition(state: ApiState<T>, action: Action): ApiState<T>` function with a switch on the current state's `status`, returning only valid next states — TypeScript enforces that you handle all current states and return a valid `ApiState<T>`.

## Problem 3 — Intersection Types for Role-Based Capabilities

### Problem
Model a system where users can have different roles (`Admin`, `Editor`, `Viewer`), and certain functions require specific combinations of roles. Use intersection types so TypeScript rejects calls with insufficient capabilities.

```ts
// Only a user with Admin AND Editor capabilities can call this:
function publishAndDelete(user: AdminUser & EditorUser): void { /* ... */ }
```

### Pattern Recognition
Intersection types as capability constraints — each role type carries its specific fields/methods, and intersection requires all of them simultaneously.

### Key Insight
Branded role types (intersection with a phantom type) let TypeScript statically track which roles a user has been verified to possess, preventing incorrect calls without runtime instanceof checks.

### Solution

```ts
// Base user type
interface BaseUser {
  id: string;
  email: string;
  name: string;
}

// Role capability types (each adds role-specific fields AND a brand)
interface AdminCapability {
  readonly __adminRole: unique symbol;
  deleteUser(userId: string): Promise<void>;
  grantRole(userId: string, role: string): Promise<void>;
}

interface EditorCapability {
  readonly __editorRole: unique symbol;
  publishPost(postId: string): Promise<void>;
  editPost(postId: string, content: string): Promise<void>;
}

interface ViewerCapability {
  readonly __viewerRole: unique symbol;
  viewPost(postId: string): Promise<string>;
}

// Role-specific user types
type AdminUser  = BaseUser & AdminCapability;
type EditorUser = BaseUser & EditorCapability;
type ViewerUser = BaseUser & ViewerCapability;

// A user can have multiple roles
type AdminEditorUser = BaseUser & AdminCapability & EditorCapability;

// Functions with capability requirements
function deleteUser(admin: AdminUser, targetId: string): Promise<void> {
  return admin.deleteUser(targetId); // ✓ admin has deleteUser
}

function publishPost(editor: EditorUser, postId: string): Promise<void> {
  return editor.publishPost(postId); // ✓ editor has publishPost
}

// Requires BOTH Admin AND Editor capabilities:
function publishAndDelete(
  user: AdminUser & EditorUser,
  postId: string,
  targetId: string
): Promise<void> {
  // Both capabilities available:
  return Promise.all([
    user.publishPost(postId),   // from EditorCapability
    user.deleteUser(targetId)   // from AdminCapability
  ]).then(() => {});
}

// Role verification (runtime → compile-time bridge)
function verifyAdmin(user: BaseUser): AdminUser {
  // Runtime check (in real code, verify from session/JWT/DB)
  if (!hasAdminRole(user)) throw new Error('Insufficient permissions');
  return user as AdminUser; // brand assertion after runtime verification
}

declare function hasAdminRole(user: BaseUser): boolean;

// Usage:
async function handleAdminAction(rawUser: BaseUser) {
  const admin = verifyAdmin(rawUser); // may throw at runtime
  await admin.deleteUser('user-123'); // ✓ — type-safe after verification

  // TypeScript prevents calling admin-only functions without verification:
  // rawUser.deleteUser('user-123'); // ❌ 'deleteUser' does not exist on BaseUser
}
```

### Verification

```ts
// A ViewerUser cannot be used where AdminUser is required:
declare const viewer: ViewerUser;
deleteUser(viewer, 'target');  // ❌ ViewerUser is not assignable to AdminUser
publishPost(viewer, 'post-1'); // ❌ ViewerUser is not assignable to EditorUser

// An AdminEditorUser works where either is required:
declare const adminEditor: AdminEditorUser;
deleteUser(adminEditor, 'target');          // ✓ (has AdminCapability)
publishPost(adminEditor, 'post-1');         // ✓ (has EditorCapability)
publishAndDelete(adminEditor, 'p1', 'u2');  // ✓ (has both)
```

### Edge Cases
- **`unique symbol` brands**: using `readonly __adminRole: unique symbol` rather than `__adminRole: 'admin'` prevents two roles with the same literal string from being accidentally substituted for each other.
- **At runtime**: the brand is just a type-level phantom — no actual `__adminRole` property exists at runtime. The `as AdminUser` cast after `verifyAdmin` is the runtime→type-system bridge. TypeScript trusts that you've done the runtime check correctly.

### Follow-up Questions
- "What if a user's roles can change dynamically?" → The intersection type approach models static, compile-time role knowledge. For dynamic roles, use a runtime `Set<Role>` and check it in guard functions, or use conditional types to model permissions.

## Problem 4 — Extract, Map, and Transform a Union

### Problem
Given a union of event types, produce: (1) the union of all event names, (2) the payload type for a specific event by name, (3) a mapped object type of handlers for all events.

```ts
type AppEvent =
  | { type: 'USER_LOGIN';  payload: { userId: string; timestamp: number } }
  | { type: 'PAGE_VIEW';   payload: { url: string; referrer: string } }
  | { type: 'PURCHASE';    payload: { amount: number; currency: string } };

// Derive these from AppEvent:
type EventName       = /* 'USER_LOGIN' | 'PAGE_VIEW' | 'PURCHASE' */;
type LoginPayload    = /* { userId: string; timestamp: number } */;
type AllHandlers     = /* { USER_LOGIN: (p: LoginPayload) => void; PAGE_VIEW: ...; PURCHASE: ... } */;
```

### Pattern Recognition
`Extract` utility type, indexed access types, mapped types over union members — the standard toolkit for transforming and indexing union types.

### Key Insight
`AppEvent['type']` extracts the union of all `type` literal values. `Extract<AppEvent, { type: K }>['payload']` extracts the payload type for a specific event name `K`. A mapped type over `EventName` builds the handler map by indexing into the event union per key.

### Solution

```ts
type AppEvent =
  | { type: 'USER_LOGIN';  payload: { userId: string; timestamp: number } }
  | { type: 'PAGE_VIEW';   payload: { url: string; referrer: string } }
  | { type: 'PURCHASE';    payload: { amount: number; currency: string } };

// 1. Extract all event names as a union
type EventName = AppEvent['type'];
// → 'USER_LOGIN' | 'PAGE_VIEW' | 'PURCHASE'

// 2. Extract payload for a specific event name
type EventPayload<K extends EventName> =
  Extract<AppEvent, { type: K }>['payload'];

type LoginPayload   = EventPayload<'USER_LOGIN'>;
// → { userId: string; timestamp: number }

type PageViewPayload = EventPayload<'PAGE_VIEW'>;
// → { url: string; referrer: string }

// 3. Build a mapped handler object — one handler per event type
type EventHandlers = {
  [K in EventName]: (payload: EventPayload<K>) => void;
};
// → {
//     USER_LOGIN: (payload: { userId: string; timestamp: number }) => void;
//     PAGE_VIEW:  (payload: { url: string; referrer: string }) => void;
//     PURCHASE:   (payload: { amount: number; currency: string }) => void;
//   }

// 4. Build a generic dispatch function using the derived types
function createDispatcher(handlers: EventHandlers) {
  return function dispatch(event: AppEvent): void {
    // TypeScript knows handlers[event.type] is a valid function:
    const handler = handlers[event.type];
    // But we need a cast here because TypeScript can't correlate
    // event.type with event.payload without extra work:
    (handler as (payload: AppEvent['payload']) => void)(event.payload);
  };
}

// 5. Usage — all handler types are inferred:
const dispatcher = createDispatcher({
  USER_LOGIN: (p) => console.log(`User ${p.userId} logged in`), // p: LoginPayload ✓
  PAGE_VIEW:  (p) => console.log(`Viewed ${p.url}`),            // p: PageViewPayload ✓
  PURCHASE:   (p) => console.log(`$${p.amount} ${p.currency}`), // p: PurchasePayload ✓
});

dispatcher({ type: 'USER_LOGIN', payload: { userId: '42', timestamp: Date.now() } });
```

### Verification

```ts
// EventName is derived correctly:
type Check1 = EventName; // 'USER_LOGIN' | 'PAGE_VIEW' | 'PURCHASE' ✓

// EventPayload extracts correctly:
type Check2 = EventPayload<'PURCHASE'>; // { amount: number; currency: string } ✓

// EventHandlers has correct per-handler types:
type Check3 = EventHandlers['PAGE_VIEW']; // (payload: { url: string; referrer: string }) => void ✓

// Adding a new event to AppEvent automatically:
// - Adds its name to EventName
// - Makes EventPayload<'NEW_EVENT'> work
// - Requires adding it to EventHandlers (TypeScript errors if createDispatcher is missing a handler)
```

### Edge Cases
- **Adding a new event**: `EventName`, `EventPayload`, and `EventHandlers` all update automatically — `createDispatcher` callers get a TypeScript error if the new event's handler is missing from the object literal (excess property checking).
- **The correlation problem**: in the `dispatch` function, TypeScript can't always correlate `event.type` (as the indexing key) with `event.payload` (as the argument) without the cast — this is a known TypeScript limitation for "correlated union" patterns. The cast is safe here because the types ARE actually correlated at runtime.

### Follow-up Questions
- "How would you make EventHandlers have optional handlers (not all events need to be handled)?" → `type PartialHandlers = Partial<EventHandlers>` — each handler becomes optional. The `dispatch` function would need to check `handlers[event.type]?.()` before calling.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve TypeScript types that need to represent
"one of several shapes" or "a combination of multiple requirements"?
│
├── VALUE CAN BE ONE OF SEVERAL UNRELATED TYPES?
│   └── Union type: A | B | C
│       → Use typeof, instanceof, 'in', or equality narrowing to distinguish
│
├── UNION MEMBERS ARE OBJECTS WITH A SHARED LITERAL PROPERTY?
│   └── Discriminated union: { kind: 'a'; ... } | { kind: 'b'; ... }
│       → narrow via switch(x.kind) or if(x.kind === 'a')
│       → add assertNever() in default for exhaustiveness checking
│       → CRITICAL: each member's discriminant value must be UNIQUE
│
├── VALUE MUST SATISFY MULTIPLE TYPES SIMULTANEOUSLY?
│   └── Intersection type: A & B
│       → For objects: combines all fields from both
│       → For primitives: usually produces never (incompatible primitives)
│       → Watch for accidental never from conflicting property types
│
├── NEED TO FILTER OR TRANSFORM A UNION?
│   ├── Keep only matching members → Extract<Union, Filter>
│   ├── Remove matching members   → Exclude<Union, Filter>
│   └── Custom filter             → T extends U ? never : T  (distributive)
│
├── NEED PAYLOAD TYPE BY EVENT/CASE NAME?
│   └── Extract<Union, { discriminant: K }>['payloadField']
│       — select the member whose discriminant = K, then index into its payload
│
├── NEED A MAPPED OBJECT TYPE FROM A UNION?
│   └── { [K in UnionLiterals]: SomeType<K> }
│       — one key per union member, each typed specifically for that member
│
├── NEED COMPILE-TIME SAFETY FOR UNKNOWN VALUES (API responses, JSON)?
│   └── unknown (not any) — must narrow before use
│       → typeof, instanceof, or custom type predicate (x is T)
│
└── NEED TO PREVENT RUNTIME ERRORS FROM MISSING CASES?
    └── assertNever() in switch default — becomes compile error
        when a new union member is added and the switch isn't updated
```

## Common Bugs Checklist

Before shipping TypeScript code with union/intersection/discriminated union types, verify:

1. **Intersection with conflicting property types produces `never`, not an error?** — `type A = { id: string } & { id: number }` silently makes `A.id: never`. Always check for accidental `never` properties after intersections by hovering over the type in your editor or using `type Check = A['id']` to inspect.

2. **Discriminant property values are UNIQUE across all union members?** — Two members with the same discriminant value prevent full narrowing. There's no TypeScript warning for this — verify by inspection or tests.

3. **`assertNever()` is actually called on the narrowed value — not on a property?** — `assertNever(shape)` (the whole narrowed object) is correct; `assertNever(shape.kind)` (a string property) only checks the `kind` type, not that all shape variants are handled.

4. **`Array.map` with union return types doesn't silently collapse?** — `arr.map(x => x > 0 ? x : null)` returns `(number | null)[]`, not `number[]`. Intentional? Use `.filter(Boolean)` or explicit type assertions with `NonNullable` if you mean to remove nulls.

5. **`unknown` in catch clauses: not directly using `err.message`?** — In TypeScript 4.4+, `catch (err)` types `err` as `unknown`. Always narrow: `if (err instanceof Error)` before accessing `.message`, `.stack`, etc.

6. **Template literal union combinations: cross-product is intentional?** — `type T = `${A | B}-${C | D}`` produces a 4-member union. For large unions, this can produce hundreds of literal types. Ensure the combinatorial explosion is actually needed.

7. **Distributive conditional types: is `T` a naked type parameter?** — `type Dist<T> = T extends X ? A : B` distributes over unions in `T`. Wrap in a tuple `[T] extends [X]` to prevent distribution if you need the whole union tested at once.

8. **Excess property checking applies to object literals but not variables?** — `const x: { a: string } = { a: '1', b: 2 }` errors (excess property check on literal). But `const obj = { a: '1', b: 2 }; const x: { a: string } = obj;` is valid (structural compatibility). This affects intersection types too — building up objects via variables can bypass expected excess property errors.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to recognize the three patterns immediately from a problem description — "one-of-many" → union, "all-of-these" → intersection, "one-of-many-with-a-tag" → discriminated union — and to state the key implication of each before writing a single line of type code. For discriminated unions specifically, the two things that signal genuine fluency are: (1) proactively adding `assertNever` in the default case as standard practice, not as an afterthought; and (2) knowing that accidental `never` properties in intersections are the most common silent type system pitfall (not caught by TypeScript directly, doesn't error until you try to use that property). Being able to articulate why the discriminant property's literal values must be unique per member — and what happens when they're not — is the depth of understanding that separates correct usage from rote pattern recall.
