# TypeScript: Interfaces vs Type Aliases — When to Use Which — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

## Topic A: Fundamentals

### Section A1: What They Are

**Q1. What is a `type` alias in TypeScript, and what can it name?**
A: A `type` alias assigns a name to any TypeScript type expression. "Any" is the operative word — type aliases can name primitives, unions, intersections, tuples, mapped types, conditional types, template literal types, and object shapes. They are purely a compile-time construct: they emit no JavaScript and leave no runtime artifact.

```ts
// Primitive alias
type ID = string;

// Union
type Status = 'active' | 'inactive' | 'pending';

// Tuple
type Pair<T> = [T, T];

// Object shape
type Point = { x: number; y: number };

// Intersection
type Named = { name: string };
type Aged  = { age: number };
type Person = Named & Aged;

// Conditional
type Unwrap<T> = T extends Promise<infer U> ? U : T;

// Mapped
type Readonly<T> = { readonly [K in keyof T]: T[K] };

// Template literal
type EventName<T extends string> = `on${Capitalize<T>}`;
// EventName<'click'> → 'onClick'
```

**Q2. What is an `interface` in TypeScript, and what makes it structurally different from a type alias?**
A: An `interface` declares a named object type — specifically a shape that objects, classes, and other interfaces can implement or extend. Interfaces are restricted to describing object shapes (including function call signatures and construct signatures), which is narrower than what `type` can express. In exchange for that narrowness, interfaces gain two capabilities that type aliases lack:

1. **Declaration merging**: multiple `interface` declarations with the same name in the same scope are merged into a single type.
2. **`implements` clause**: classes can state they implement an interface, which the compiler verifies.

```ts
interface Point {
  x: number;
  y: number;
}

interface Point {          // merges with the declaration above
  z?: number;
}
// Point is now { x: number; y: number; z?: number }

class Point3D implements Point {
  constructor(public x: number, public y: number, public z = 0) {}
}
```

**Q3. What is declaration merging, and why does it only apply to interfaces?**
A: Declaration merging is TypeScript's ability to combine multiple declarations of the same name into a single type. When you write two `interface Foo { ... }` blocks in the same scope, TypeScript merges their members — the resulting interface has all members from all declarations. This cannot happen with type aliases: redeclaring `type Foo = ...` in the same scope is a compile error.

Declaration merging exists for interfaces (and namespaces, enums, and classes) because those constructs were designed to be *open* — they can be extended after the fact. This is the mechanism that makes library augmentation possible:

```ts
// In your code — augmenting a library's interface:
// express/index.d.ts declares:  interface Request { ... }
// You add a property:
declare module 'express' {
  interface Request {
    currentUser?: User; // merged into Express's Request type
  }
}
// Now req.currentUser is typed throughout your app

// The same is IMPOSSIBLE with type:
// type Request = ... // ERROR: Duplicate identifier 'Request'
```

**Q4. What are the syntactic and semantic similarities between interfaces and type aliases for object shapes?**
A: For plain object shapes — the most common use case in both — interfaces and type aliases are nearly interchangeable. Both produce structurally equivalent types that TypeScript compares by shape, not by name. Both support optional properties (`?:`), readonly modifiers, index signatures, call signatures, and generics.

```ts
// Equivalent object shapes:
interface IUser {
  id: number;
  name: string;
  email?: string;
  readonly createdAt: Date;
}

type TUser = {
  id: number;
  name: string;
  email?: string;
  readonly createdAt: Date;
};

// Both work identically as function parameters:
function greet(user: IUser) { /* ... */ }
function greetT(user: TUser) { /* ... */ }

// An IUser satisfies TUser and vice versa (structural typing):
const u: IUser = { id: 1, name: 'Alice', createdAt: new Date() };
const v: TUser = u; // valid — same shape
```

The compiler treats them identically in most contexts: error messages, type checking, assignability — all work the same.

### Section A2: Key Differences

**Q5. What are the six concrete differences between interfaces and type aliases?**
A: The differences that actually matter in practice:

**1. Declaration merging (interface only)**
Interfaces merge; type aliases produce an error on redeclaration.

**2. `implements` / `extends` in class declarations**
Both work, but `extends` in a class context is only allowed with an interface or a class — not a complex type alias. An interface can be used in `implements` and `extends` freely; a type alias can only be used in `implements` if it resolves to an object type (not a union).

```ts
type UnionType = { a: string } | { b: number };
// class Foo implements UnionType {} // ERROR — can't implement a union
interface IObjType { a: string }
class Bar implements IObjType { a = '' } // OK
```

**3. Expressiveness (type alias wins)**
Type aliases can express unions, intersections, tuples, conditional types, mapped types, template literal types — anything that is a valid TypeScript type. Interfaces cannot express unions or tuple types directly.

```ts
type StringOrNumber = string | number;     // only possible with type
type Triple<T> = [T, T, T];               // only possible with type
type Nullable<T> = T | null;              // only possible with type
type Keys = keyof { a: 1; b: 2 };        // both work, but type is more natural
```

**4. Computed / recursive types (type alias wins)**
Conditional types, recursive types, and mapped types require type aliases. Interfaces can be recursive for simple self-referential object shapes, but cannot express complex computed types.

```ts
// Recursive type — works with both for simple cases:
interface TreeNode { value: number; children: TreeNode[] }
type TreeNode2 = { value: number; children: TreeNode2[] };

// Conditional recursion — type alias only:
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

**5. Error message readability**
Interfaces display their name in error messages; type aliases for complex types often "expand" into their full definition, making errors longer and harder to read. This is an ergonomic advantage for interfaces when used in large codebases.

```ts
interface IUser { id: number; name: string }
type TUser = { id: number; name: string }

function fn(u: IUser) {}
fn({ id: 1 }); // Error: Property 'name' is missing in type '{ id: number; }' but required in type 'IUser'
// vs. for TUser: Error: ...required in type '{ id: number; name: string; }'
// Interface names are preserved; type aliases may be expanded
```

**6. `interface` can extend multiple interfaces; type uses intersection**
Both achieve multi-type composition, but syntax differs:

```ts
interface A { a: string }
interface B { b: number }
interface AB extends A, B {}          // interface: extends
type AB2 = A & B;                     // type alias: intersection
// Both produce { a: string; b: number }
```

**Q6. Can a `type` alias extend an interface, and can an interface extend a type alias?**
A: Yes to both — TypeScript's structural type system doesn't distinguish between a shape defined via `interface` and one defined via `type` when it comes to extension:

```ts
type HasId = { id: number };
interface Named { name: string }

// Interface extending a type alias:
interface User extends HasId {   // OK — HasId is an object type
  name: string;
}

// Type alias "extending" an interface (via intersection):
type Admin = Named & {           // OK — intersection includes Named
  role: string;
};

// Even mixing:
interface SuperUser extends HasId, Named {
  permissions: string[];
}
// SuperUser = { id: number; name: string; permissions: string[] }
```

The restriction: an `interface` can only `extends` something that resolves to an object type. It cannot extend a union type — `interface Foo extends string | number {}` is an error.

**Q7. How do `interface` and `type` differ when used with generics?**
A: Both support generics equally for most cases. The difference emerges with **default type parameters in complex expressions** and with **constraints in mapped/conditional types**, which only `type` supports:

```ts
// Both work identically for basic generics:
interface Box<T> { value: T }
type Box2<T> = { value: T };

// Conditional generics — type alias only:
type NonNullable<T> = T extends null | undefined ? never : T;

// Distributive conditionals over unions — type alias only:
type IsString<T> = T extends string ? true : false;
// IsString<string | number> → boolean (distributes: true | false)

// Mapped types — type alias only (interfaces can't use mapped type syntax directly):
type Optional<T> = { [K in keyof T]?: T[K] };

// Interface with generic constraint — works fine:
interface Comparable<T> {
  compareTo(other: T): number;
}
```

## Topic B: When to Use Each

### Section B1: The Decision Rules

**Q8. What is the single most practical rule for choosing between interface and type?**
A: **Use `interface` for public API contracts (anything that will be `implement`ed, `extend`ed, or augmented by consumers); use `type` for everything else — especially unions, intersections, utility types, and complex computed types.**

The secondary rule: when in doubt and the thing you're describing is a plain object shape with no need for merging or augmentation, either works — pick the one your team's style guide dictates and be consistent. Inconsistency is more costly than the "wrong" choice.

**Q9. When should you always use `interface`?**
A: Four situations where `interface` is clearly the right choice:

**1. Library public API / `.d.ts` declarations** — consumers need to augment your types via declaration merging. If you use `type`, they can't. React's `HTMLAttributes`, Express's `Request`, and virtually every major library uses interfaces for this reason.

```ts
// Library: form-validator/index.d.ts
export interface ValidationRule {
  validate(value: unknown): boolean;
  message: string;
}
// User can augment:
declare module 'form-validator' {
  interface ValidationRule {
    asyncValidate?(value: unknown): Promise<boolean>; // added by user
  }
}
```

**2. Class contracts** — when you're defining what a class must implement, `interface` is semantically cleaner. Using `implements SomeInterface` is more expressive than implementing a type alias.

```ts
interface Repository<T, ID> {
  findById(id: ID): Promise<T | null>;
  save(entity: T): Promise<T>;
  delete(id: ID): Promise<void>;
}

class UserRepository implements Repository<User, number> {
  // TypeScript verifies all three methods are implemented
}
```

**3. Object shapes that need to extend other object shapes** — when the shape IS-A relationship matters and you want the extended declaration to be clearly readable.

```ts
interface Animal { name: string; sound(): string }
interface Dog extends Animal { breed: string; fetch(): void }
// Reads as: "A Dog is an Animal with extra properties"
```

**4. When working in a codebase that already uses interfaces consistently** — consistency within a codebase is more important than any individual choice.

**Q10. When should you always use `type`?**
A: Six situations where `type` is required or clearly superior:

**1. Union types** — the most common and clear-cut case.
```ts
type Result<T> = { ok: true; value: T } | { ok: false; error: Error };
type Direction = 'north' | 'south' | 'east' | 'west';
```

**2. Tuple types**
```ts
type Coordinate = [number, number];
type NamedCoordinate = [name: string, x: number, y: number]; // labeled tuple
type UseState<T> = [T, (newValue: T) => void]; // useState return type pattern
```

**3. Mapped types and conditional types**
```ts
type Partial<T>  = { [K in keyof T]?: T[K] };
type Required<T> = { [K in keyof T]-?: T[K] };
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Exclude<T, U> = T extends U ? never : T;
```

**4. Template literal types**
```ts
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';
type ApiRoute<M extends HttpMethod, Path extends string> = `${M} ${Path}`;
type GetUser = ApiRoute<'GET', '/users/:id'>; // 'GET /users/:id'
```

**5. Utility / transformation types that compose other types**
```ts
type DeepPartial<T> = { [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K] };
type Awaited<T> = T extends Promise<infer U> ? Awaited<U> : T;
```

**6. Aliasing primitives or complex expressions for documentation**
```ts
type UserID = string;   // documents intent, not just 'string'
type Milliseconds = number;
type Callback = (err: Error | null, result?: string) => void;
```

### Section B2: The Grey Zone

**Q11. What are the cases where the choice genuinely doesn't matter, and how should you handle them?**
A: For plain object shapes that are internal to a module, never extended by consumers, and don't need merging — both `interface` and `type` produce identical results. The choice reduces to style:

```ts
// These are genuinely equivalent for internal use:
interface Config { host: string; port: number; timeout: number }
type Config = { host: string; port: number; timeout: number };
```

How to handle the grey zone:
1. **Follow the team style guide**. If one exists, use it.
2. **If starting fresh**: use `interface` for everything that is an object shape; use `type` for everything else (unions, primitives, complex types). This is the most common professional convention and matches the TypeScript team's own recommendations.
3. **Never mix within the same conceptual group**: if `UserProfile` is an `interface`, `AdminProfile extends UserProfile` should also be an `interface` — not a `type AdminProfile = UserProfile & { ... }`.

**Q12. Why does the TypeScript team's own style guide recommend `interface` over `type` for object shapes?**
A: The TypeScript team recommends using `interface` over `type` for object shape declarations because:

1. **Better error messages**: interface names are preserved in error output; type alias shapes are sometimes expanded inline, producing verbose errors.
2. **Declaration merging availability**: even if you don't currently need merging, using `interface` leaves the door open for augmentation without a breaking change.
3. **Semantic clarity**: `interface` communicates "this is a contract / object shape"; `type` communicates "this is any arbitrary type" — the narrower tool conveys clearer intent.
4. **Performance on very large codebases**: the TypeScript compiler caches interface types more aggressively than type alias resolutions in some scenarios, improving compilation speed in very large projects (though this is a marginal consideration for most codebases).

That said, the team also acknowledges that for most practical purposes, the choice is stylistic.

**Q13. How do intersection types (`&`) with `type` differ from `extends` with `interface`, and when does the difference matter?**
A: Both `type C = A & B` and `interface C extends A, B {}` create a type with all members of `A` and `B`. The difference emerges with **conflicting property types**:

- **`extends`**: conflicting property types produce a compile error at the point of declaration.
- **`&` (intersection)**: conflicting property types silently produce `never` for the conflicting property — TypeScript resolves the conflict by intersecting the types, which for incompatible types (e.g., `string & number`) yields `never`.

```ts
interface A { x: string }
interface B { x: number }

interface C extends A, B {}
// ERROR: Property 'x' in type 'B' is not assignable to the same property in base type 'A'.
// (Caught at declaration — good!)

type D = A & B;
// No error at declaration — D.x has type: string & number = never
// (Silently wrong — a property of type 'never' can never be assigned)

const d: D = { x: 'hello' }; // Error only here: 'string' is not assignable to 'never'
```

**Use `extends` (interface) when you want conflicts to be caught immediately at the type definition. Use `&` (type) when you know the types don't conflict, or when you intentionally want the intersection semantics.**

## Topic C: Advanced Patterns and Edge Cases

### Section C1: Fundamentals

**Q14. How do interfaces and type aliases behave differently with self-referential (recursive) types?**
A: Both support recursion, but there are historical differences that have largely been resolved in modern TypeScript (4.1+):

```ts
// Both work for simple recursive structures:
interface JsonValue {
  [key: string]: string | number | boolean | null | JsonValue | JsonValue[];
}

type JsonValue2 =
  | string
  | number
  | boolean
  | null
  | { [key: string]: JsonValue2 }
  | JsonValue2[];

// Complex recursive mapped types — type alias only (still):
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends (infer U)[]
    ? DeepReadonly<U>[]
    : T[K] extends object
    ? DeepReadonly<T[K]>
    : T[K];
};
```

In early TypeScript versions, certain recursive type aliases caused "Type alias circularly references itself" errors that interfaces didn't. Modern TypeScript handles both well for most common patterns — the edge cases that still differ are in highly complex generic recursive types used in functional programming libraries.

**Q15. What is the `interface` index signature, and does `type` support the same thing?**
A: An index signature defines the type for arbitrary string or number keys. Both `interface` and `type` support it:

```ts
interface StringMap {
  [key: string]: string;
}

type StringMap2 = {
  [key: string]: string;
};

// Both are equivalent. Index signatures have one important restriction:
// All known properties must be assignable to the index signature's value type.
interface Problematic {
  [key: string]: string;
  count: number; // ERROR: 'number' is not assignable to 'string'
}

// Fix:
interface Flexible {
  [key: string]: string | number;
  count: number; // OK — 'number' is assignable to 'string | number'
}
```

The modern alternative that avoids index signature quirks: use `Record<string, T>` (a type alias):
```ts
type StringMap3 = Record<string, string>; // equivalent to {[key: string]: string}
```

**Q16. How do function type definitions differ between `interface` and `type`?**
A: Both can describe function types, but the syntax differs and has slightly different semantics:

```ts
// Type alias — shorter, more natural for "just a function":
type Predicate<T> = (value: T) => boolean;
type Transformer<T, U> = (input: T) => U;

// Interface — call signature syntax:
interface Predicate2<T> {
  (value: T): boolean;
}

// The interface form enables BOTH being callable AND having properties:
interface Formatter {
  (value: string): string;  // call signature
  locale: string;           // property on the function itself
  reset(): void;            // method on the function itself
}
// A value of type Formatter is a callable function with .locale and .reset()
// The type alias equivalent:
type Formatter2 = {
  (value: string): string;
  locale: string;
  reset(): void;
};

// For plain function types with no extra properties, use type alias — cleaner:
type Handler = (event: MouseEvent) => void; // ✓ clear
interface IHandler { (event: MouseEvent): void } // ✓ works but more verbose
```

### Section C2: Advanced Patterns

**Q17. How do you augment a third-party library's types, and why does this require interfaces?**
A: Module augmentation allows you to add properties to types from external libraries. It requires the library to have declared those types as interfaces (or for you to add interface declarations that merge with the library's types):

```ts
// Augmenting Express to add a custom property to every Request:
import 'express';

declare module 'express-serve-static-core' {
  interface Request {
    currentUser?: {
      id: string;
      role: 'admin' | 'user';
    };
  }
}

// Now in your route handlers:
app.get('/profile', (req, res) => {
  req.currentUser; // TypeScript knows this property exists!
});

// Augmenting window in a browser environment:
declare global {
  interface Window {
    analytics: AnalyticsInstance;
    __APP_CONFIG__: AppConfig;
  }
}
window.analytics; // now typed

// Augmenting an npm package's type:
declare module 'some-lib' {
  interface SomeLibOptions {
    myCustomOption?: boolean; // add an option the library doesn't know about
  }
}
```

This pattern is impossible with type aliases — you cannot redeclare a `type` alias. It is one of the strongest practical reasons to use `interface` in any code that ships as a library or that might be augmented.

**Q18. What is the "open" vs "closed" type distinction, and how do interfaces and type aliases embody each?**
A: Types can be thought of as "open" (can be extended/augmented after declaration) or "closed" (fixed at declaration time):

- **`interface` = open**: consumers can add members via declaration merging. The type's definition is not finalized until all declarations are merged. This openness is what makes library augmentation possible and why React, Express, and virtually all major TypeScript libraries use interfaces for their public types.

- **`type` alias = closed**: once declared, a type alias cannot be augmented. Its definition is final. This is actually desirable for internal application types — you don't want `type UserState = { ... }` in your Redux reducer to be accidentally extended by some other file.

The closed nature of type aliases provides a form of encapsulation — no part of your codebase can silently add properties to a type alias. For application code (as opposed to library code), closedness is usually a feature, not a limitation.

**Q19. How do `interface` and `type` interact with TypeScript's structural type system, and are there any cases where they produce different types?**
A: TypeScript uses structural typing — two types are compatible if they have the same shape, regardless of how they were declared. An `interface` and a `type` alias describing the same shape are fully interchangeable in all assignments and function calls.

The only cases that produce genuinely different behavior:

```ts
// 1. Interface names are preserved in error messages (ergonomic, not semantic):
interface IPoint { x: number; y: number }
type TPoint = { x: number; y: number };
// Errors for IPoint mention 'IPoint'; errors for TPoint expand the full type

// 2. Class implements:
type Union = { a: string } | { b: number };
class Foo implements Union {} // ERROR — can't implement a union type
interface IObj { a: string }
class Bar implements IObj { a = '' } // OK

// 3. Declaration merging (structural effect):
interface Merged { a: string }
interface Merged { b: number }
// Merged = { a: string; b: number } — the types are merged
// type aliases cannot merge — this is impossible

// 4. Excess property checking edge case with type aliases and intersection:
type A = { x: number };
type B = { y: string };
type AB = A & B;
const obj: AB = { x: 1, y: 'hello', z: true }; // ERROR: excess 'z'
// Identical with interface — both trigger excess property checking in object literals

// Summary: for structural compatibility, they are identical.
// Differences are ergonomic (error messages), syntactic (what can be expressed),
// and meta-programming (merging, augmentation).
```

**Q20. What are `abstract class` and how do they compare to `interface` as a contract mechanism?**
A: Abstract classes occupy the middle ground between interfaces and concrete classes:

| Feature | `interface` | `abstract class` | `class` |
|---|---|---|---|
| Runtime artifact | None | Yes (class) | Yes (class) |
| Multiple inheritance | Yes (`implements` many) | No (extends one) | No |
| Default implementations | No | Yes | Yes |
| Constructor | No | Optional | Yes |
| `instanceof` check | No | Yes | Yes |

Use `abstract class` when:
- You need to provide **default method implementations** that subclasses can inherit or override.
- You need **`instanceof`** to work at runtime.
- The relationship is genuinely IS-A (inheritance) rather than CAN-DO (interface).

Use `interface` when:
- You're defining a **pure contract** with no implementation.
- A class needs to satisfy **multiple unrelated contracts** (`implements A, B, C`).
- You don't want to force consumers into an inheritance hierarchy.

```ts
// Abstract class: some implementation provided
abstract class Shape {
  abstract area(): number;   // must be implemented by subclass
  toString(): string {       // default implementation — optional to override
    return `Shape with area ${this.area()}`;
  }
}

// Interface: pure contract
interface Measurable {
  area(): number;
  perimeter(): number;
}

// A class can implement many interfaces but extend only one abstract class:
class Circle extends Shape implements Measurable {
  constructor(private r: number) { super(); }
  area() { return Math.PI * this.r ** 2; }
  perimeter() { return 2 * Math.PI * this.r; }
}
```

## Topic D: Cross-Topic & Interview-Style Questions

**Q21. "Your team is starting a new TypeScript project. What conventions do you recommend for interface vs type, and why?"**
A: Three conventions that balance consistency, correctness, and long-term maintainability:

**Convention 1 — `interface` for public contracts, `type` for everything else**:
- All exported object shapes that describe a class contract or public API → `interface`.
- All unions, intersections, utility types, mapped types, conditional types, primitives with aliases → `type`.
- Internal application state shapes → either, but be consistent within a file/module.

**Convention 2 — If your code ships as a library, use `interface` for all exported types**. Consumers will thank you when they need to augment your types. The cost is zero for you; the benefit to consumers can be significant.

**Convention 3 — Enforce with ESLint**. The `@typescript-eslint/consistent-type-definitions` rule enforces either `interface` or `type` across the codebase. Pick one for object shapes and stick with it. Mixing both for the same conceptual category (sometimes `interface User`, sometimes `type User`) is the worst outcome — it confuses the team about when to use what.

**Q22. "Can you convert every `interface` to a `type` alias and vice versa?"**
A: Almost — but with important exceptions:

**`interface` → `type` is always possible** for the type itself, but loses:
- Declaration merging capability (consumers can no longer augment it).
- The `extends` keyword (must use `&` instead).

**`type` → `interface` is NOT always possible**:
- Union types (`type A = B | C`) have no interface equivalent.
- Tuple types (`type Pair = [string, number]`) have no interface equivalent.
- Conditional types, mapped types, template literal types — none have interface equivalents.
- Primitive aliases (`type ID = string`) have no interface equivalent.

So the conversion is asymmetric: `interface` can always be expressed as `type` (losing some meta capabilities), but `type` cannot always be expressed as `interface` (some type expressions are impossible to write as interfaces).

**Q23. "What does TypeScript's own standard library use — interfaces or types — and what can we learn from it?"**
A: TypeScript's `lib.*.d.ts` standard library files use both, deliberately and consistently:

- **Built-in objects and their prototypes**: `interface String`, `interface Array<T>`, `interface Promise<T>` — all interfaces. This allows library authors and framework users to augment these (e.g., adding a `flatMap` polyfill type, extending `Array.prototype`).

- **Utility types**: `type Partial<T>`, `type Readonly<T>`, `type Record<K,V>`, `type Pick<T,K>` — all type aliases. They use mapped/conditional types which require `type`.

- **DOM types**: `interface Element`, `interface HTMLElement`, `interface Event` — all interfaces. Critical for augmentation (e.g., adding custom attributes to elements in framework code).

The lesson: the TypeScript team itself uses interfaces for anything that is a named object shape that might be augmented, and type aliases for computed/utility types. This is the convention most TypeScript codebases should follow.

**Q24. "How do you handle the case where you need both a union type and a class contract for the same domain concept?"**
A: A common pattern: define the union with `type`, define the members with `interface`, and define the class contract as a separate `interface`:

```ts
// The individual variants as interfaces (extensible, clear contract):
interface CircleShape {
  kind: 'circle';
  radius: number;
}

interface RectShape {
  kind: 'rect';
  width: number;
  height: number;
}

// The discriminated union as a type:
type Shape = CircleShape | RectShape;

// The class contract as an interface:
interface Drawable {
  draw(ctx: CanvasRenderingContext2D): void;
  area(): number;
}

// A class implementing the contract and holding a shape:
class Circle implements Drawable {
  constructor(private shape: CircleShape) {}
  area() { return Math.PI * this.shape.radius ** 2; }
  draw(ctx: CanvasRenderingContext2D) { /* ... */ }
}

// Type guard using the discriminated union:
function processShape(shape: Shape) {
  if (shape.kind === 'circle') {
    shape.radius; // TypeScript narrows to CircleShape
  }
}
```

This pattern — `interface` for each variant, `type` for the union — combines the best of both: the variants are extensible (can be augmented), the union is expressive (can only be done with `type`), and the class contract is clear.

**Q25. "In one sentence each, when would you use `interface`, `type`, and `abstract class`?"**
A:
- **`interface`**: when defining a named object shape that is a public contract — especially one that may be implemented by classes, extended by other interfaces, or augmented by library consumers via declaration merging.
- **`type`**: when expressing anything that cannot be an interface — unions, intersections, tuples, mapped types, conditional types, template literal types, primitive aliases — or any type that should be closed/non-augmentable by design.
- **`abstract class`**: when defining a contract that also provides partial default implementations, needs `instanceof` support at runtime, or represents a true inheritance hierarchy where subclasses share concrete behavior.

## Problem 1 — Model a REST API Response with Discriminated Unions

### Problem
Model a REST API response that can be one of three states: loading, success (with typed data), or error (with a message and code). The model should be usable as a type guard and work with a generic `DataFetcher<T>` class that consumers can implement.

### Pattern Recognition
Discriminated union → `type` (union required). Individual variant shapes → `interface` (clean contracts, potentially augmentable). Class contract → `interface` with generics.

### Key Insight
The union itself must be a `type` — there is no interface equivalent. Each arm of the union is a simple object shape that benefits from being an `interface` because: (a) they could be extended later (e.g., a "loading with progress" variant extending `LoadingState`), and (b) their names appear clearly in error messages. The class contract `DataFetcher<T>` is an `interface` because it's a public API that classes implement.

### Solution

```ts
// ── Variant shapes as interfaces (extensible, clear names in errors) ──

interface LoadingState {
  status: 'loading';
}

interface SuccessState<T> {
  status: 'success';
  data: T;
  timestamp: Date;
}

interface ErrorState {
  status: 'error';
  message: string;
  code: number;
}

// ── The union as a type alias (only way to express a union) ──

type ApiState<T> = LoadingState | SuccessState<T> | ErrorState;

// ── The class contract as an interface (implementable, extendable) ──

interface DataFetcher<T> {
  state: ApiState<T>;
  fetch(url: string): Promise<void>;
  reset(): void;
}

// ── Type guards — work because of the discriminant 'status' property ──

function isLoading<T>(state: ApiState<T>): state is LoadingState {
  return state.status === 'loading';
}

function isSuccess<T>(state: ApiState<T>): state is SuccessState<T> {
  return state.status === 'success';
}

function isError<T>(state: ApiState<T>): state is ErrorState {
  return state.status === 'error';
}

// ── A concrete class implementing the interface ──

class UserFetcher implements DataFetcher<User> {
  state: ApiState<User> = { status: 'loading' };

  async fetch(url: string): Promise<void> {
    this.state = { status: 'loading' };
    try {
      const res = await fetch(url);
      if (!res.ok) {
        this.state = {
          status: 'error',
          message: res.statusText,
          code: res.status
        };
        return;
      }
      const data: User = await res.json();
      this.state = { status: 'success', data, timestamp: new Date() };
    } catch (err) {
      this.state = {
        status: 'error',
        message: err instanceof Error ? err.message : 'Unknown error',
        code: 0
      };
    }
  }

  reset(): void {
    this.state = { status: 'loading' };
  }
}

interface User { id: number; name: string; email: string }

// ── Usage with exhaustive narrowing ──

function render<T>(state: ApiState<T>, renderData: (data: T) => string): string {
  switch (state.status) {
    case 'loading':  return 'Loading...';
    case 'success':  return renderData(state.data);
    case 'error':    return `Error ${state.code}: ${state.message}`;
    // No default needed — TypeScript knows all cases are covered
  }
}

// ── Extension via interface merging (library augmentation pattern) ──

// In a different file/module, a consumer adds a 'progress' variant:
interface LoadingState {
  progress?: number; // merged into LoadingState — now optional on all LoadingState values
}

// This augmentation is possible ONLY because LoadingState is an interface.
// If it were: type LoadingState = { status: 'loading' }
// the merge would be a compile error.
```

### Why This Structure Works
- `LoadingState | SuccessState<T> | ErrorState` requires `type ApiState<T>` — unions are impossible with interface syntax.
- Each variant being an `interface` means: error messages say "missing property in LoadingState" (not the full expanded object), consumers can add properties (like `progress`), and the `status` discriminant is clearly visible.
- `DataFetcher<T>` as an `interface` means: any class can `implements DataFetcher<User>` and TypeScript verifies all members.

## Problem 2 — Build a Typed Event System

### Problem
Build a fully typed event emitter where event names and their payload types are defined in a single `EventMap` type. Subscribing to an event should give the callback the correctly typed payload. Emitting an event should enforce the correct payload type. No `any` allowed.

### Pattern Recognition
`type` for the event map (it will be used as a generic parameter and as a mapped type). `interface` for the emitter contract (implementable, extensible for augmentation). Generic mapped type manipulation requires `type`.

### Solution

```ts
// ── The event map: a type alias mapping event names to payload types ──
// Must be `type` because it will be used in mapped types and generics

type EventMap = {
  userLogin:   { userId: string; timestamp: Date };
  userLogout:  { userId: string };
  pageView:    { path: string; referrer?: string };
  error:       { message: string; stack?: string };
};

// ── Helper types — require type aliases (mapped/conditional types) ──

// All valid event names:
type EventNames<Map extends EventMap> = keyof Map & string;

// Payload type for a specific event:
type EventPayload<Map extends EventMap, E extends EventNames<Map>> = Map[E];

// A typed listener callback:
type EventListener<Map extends EventMap, E extends EventNames<Map>> =
  (payload: EventPayload<Map, E>) => void;

// ── The emitter contract: interface (implementable, augmentable) ──

interface TypedEventEmitter<Map extends EventMap> {
  on<E extends EventNames<Map>>(
    event: E,
    listener: EventListener<Map, E>
  ): this;

  off<E extends EventNames<Map>>(
    event: E,
    listener: EventListener<Map, E>
  ): this;

  once<E extends EventNames<Map>>(
    event: E,
    listener: EventListener<Map, E>
  ): this;

  emit<E extends EventNames<Map>>(
    event: E,
    payload: EventPayload<Map, E>
  ): boolean;
}

// ── Concrete implementation ──

class EventEmitter<Map extends EventMap> implements TypedEventEmitter<Map> {
  // Internal: map from event name to set of listeners
  private listeners = new Map<string, Set<Function>>();

  on<E extends EventNames<Map>>(event: E, listener: EventListener<Map, E>): this {
    if (!this.listeners.has(event)) this.listeners.set(event, new Set());
    this.listeners.get(event)!.add(listener);
    return this;
  }

  off<E extends EventNames<Map>>(event: E, listener: EventListener<Map, E>): this {
    this.listeners.get(event)?.delete(listener);
    return this;
  }

  once<E extends EventNames<Map>>(event: E, listener: EventListener<Map, E>): this {
    const wrapper = (payload: EventPayload<Map, E>) => {
      this.off(event, wrapper as EventListener<Map, E>);
      listener(payload);
    };
    return this.on(event, wrapper as EventListener<Map, E>);
  }

  emit<E extends EventNames<Map>>(event: E, payload: EventPayload<Map, E>): boolean {
    const cbs = this.listeners.get(event);
    if (!cbs || cbs.size === 0) return false;
    cbs.forEach(cb => cb(payload));
    return true;
  }
}

// ── Usage — fully typed, no 'any' ──

const emitter = new EventEmitter<EventMap>();

// TypeScript knows the payload type from the event name:
emitter.on('userLogin', ({ userId, timestamp }) => {
  // userId: string, timestamp: Date  ← correctly inferred
  console.log(`User ${userId} logged in at ${timestamp}`);
});

emitter.emit('userLogin', {
  userId: '123',
  timestamp: new Date()
  // missing or extra properties → compile error
});

emitter.emit('userLogin', { userId: 123, timestamp: new Date() });
// ERROR: 'number' is not assignable to 'string' ← caught at compile time!

// ── Library augmentation: adding new events ──
// Because TypedEventEmitter is an interface, consumers can augment it.
// To add events to the EventMap itself, consumers define their own EventMap:

type AppEventMap = EventMap & {
  cartUpdated: { itemCount: number; total: number };
};

const appEmitter = new EventEmitter<AppEventMap>();
appEmitter.on('cartUpdated', ({ itemCount, total }) => {
  console.log(`Cart: ${itemCount} items, $${total}`);
});
```

### Why This Structure Works
- `EventMap` as a `type` (not interface): it's used as a generic constraint and in mapped type operations (`keyof Map`). An interface *can* be used as a generic constraint, but using `type` here is cleaner since `EventMap` is a data mapping, not a contract.
- Helper types (`EventNames`, `EventPayload`, `EventListener`) are `type` aliases — they use mapped types and conditional logic.
- `TypedEventEmitter<Map>` as an `interface`: it's a class contract. `implements TypedEventEmitter<EventMap>` reads clearly. It can be augmented.
- The implementation uses private `Map<string, Set<Function>>` for runtime flexibility — the type safety lives entirely at the `TypedEventEmitter<Map>` interface level.

## Problem 3 — Design a Plugin System with Declaration Merging

### Problem
Design a plugin system where the base library defines a core set of options, but third-party plugins can register their own typed options. The final options type should automatically include all registered plugin options — without the core library needing to know about the plugins in advance.

### Pattern Recognition
This is a textbook declaration merging use case. The core options must be an `interface` so plugins can merge their options into it. Plugins use `declare module` augmentation. This is impossible with `type` — it's the single clearest example of where `interface` is not just preferred but required.

### Solution

```ts
// ── core/index.ts ── Core library ──

// Core options as an interface — MUST be interface for merging
export interface PluginOptions {
  debug?: boolean;
  timeout?: number;
}

// Core plugin interface
export interface Plugin {
  name: string;
  setup(options: PluginOptions): void;
}

// The plugin registry type: maps names to their options
// Note: PluginOptions is an interface so it can be merged later
export interface PluginRegistry {
  // Initially empty — plugins register themselves here via merging
}

// Core function — accepts merged PluginOptions
export function createApp(options: PluginOptions = {}): App {
  return new App(options);
}

export class App {
  private plugins: Plugin[] = [];

  constructor(private options: PluginOptions) {}

  use(plugin: Plugin): this {
    plugin.setup(this.options);
    this.plugins.push(plugin);
    return this;
  }
}

// ── analytics-plugin/index.ts ── Third-party plugin ──

// Import the core module to augment it:
import type { PluginOptions, Plugin } from 'core';

// Augment PluginOptions to add analytics-specific options:
declare module 'core' {
  interface PluginOptions {
    analytics?: {
      trackingId: string;
      sampleRate?: number;
    };
  }
}

// The analytics plugin implementation:
export const analyticsPlugin: Plugin = {
  name: 'analytics',
  setup(options: PluginOptions) {
    if (options.analytics) {
      // options.analytics is now typed!
      console.log(`Analytics: trackingId=${options.analytics.trackingId}`);
    }
  }
};

// ── auth-plugin/index.ts ── Another plugin ──

declare module 'core' {
  interface PluginOptions {
    auth?: {
      provider: 'oauth' | 'jwt' | 'basic';
      secret?: string;
    };
  }
}

import type { Plugin } from 'core';

export const authPlugin: Plugin = {
  name: 'auth',
  setup(options) {
    if (options.auth) {
      console.log(`Auth provider: ${options.auth.provider}`);
    }
  }
};

// ── app.ts ── Consumer code ──

import { createApp } from 'core';
import { analyticsPlugin } from 'analytics-plugin';
import { authPlugin } from 'auth-plugin';

// After importing both plugins, PluginOptions is merged to include:
// { debug?, timeout?, analytics?: {...}, auth?: {...} }

const app = createApp({
  debug: true,
  analytics: {
    trackingId: 'UA-12345',
    sampleRate: 0.1
  },
  auth: {
    provider: 'jwt',
    secret: 'my-secret'
  }
  // TypeScript knows all these options because of declaration merging
});

app.use(analyticsPlugin).use(authPlugin);
```

### Why This Requires `interface`
If `PluginOptions` were a `type`:
```ts
export type PluginOptions = { debug?: boolean; timeout?: number };

// In analytics-plugin:
declare module 'core' {
  interface PluginOptions { ... } // ERROR: Cannot augment a type alias
}
```

The augmentation `declare module 'core' { interface X { ... } }` only works if `X` is declared as an `interface` in the module. This is the definitive, irreplaceable use case for interfaces.

## Problem 4 — Utility Type Library with Inference

### Problem
Implement a small utility type library: `DeepPartial<T>`, `DeepReadonly<T>`, `Prettify<T>` (flattens intersection types for readability), and `PickByValue<T, ValueType>` (picks keys whose values extend a given type). These must be implemented as type aliases.

### Pattern Recognition
All four require mapped types, conditional types, or complex type-level operations — none of which can be expressed as interfaces. These are canonical `type` alias territory.

### Solution

```ts
// ── DeepPartial<T>: recursively makes all properties optional ──

type DeepPartial<T> = T extends (infer U)[]
  ? DeepPartial<U>[]           // handle arrays
  : T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }  // recurse into objects
  : T;                         // primitives unchanged

// Usage:
interface Config {
  server: { host: string; port: number; ssl: boolean };
  database: { url: string; poolSize: number };
}
type PartialConfig = DeepPartial<Config>;
// { server?: { host?: string; port?: number; ssl?: boolean }; database?: { ... } }

const partial: PartialConfig = { server: { host: 'localhost' } }; // valid


// ── DeepReadonly<T>: recursively makes all properties readonly ──

type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;

// Usage:
type ReadonlyConfig = DeepReadonly<Config>;
// { readonly server: { readonly host: string; readonly port: number; ... }; ... }

const config: ReadonlyConfig = {
  server: { host: 'localhost', port: 8080, ssl: false },
  database: { url: 'postgres://...', poolSize: 10 }
};
// config.server.host = 'other'; // ERROR: Cannot assign to 'host' — readonly


// ── Prettify<T>: expands intersection types to a single flat object ──
// Invaluable for making complex intersection types readable in IDE tooltips.

type Prettify<T> = { [K in keyof T]: T[K] } & {};
// The `& {}` forces TypeScript to evaluate/expand the type

// Usage:
type HasName = { name: string };
type HasAge  = { age: number };
type HasRole = { role: 'admin' | 'user' };

// Without Prettify — IDE shows: HasName & HasAge & HasRole
type PersonRaw = HasName & HasAge & HasRole;

// With Prettify — IDE shows: { name: string; age: number; role: 'admin' | 'user' }
type Person = Prettify<HasName & HasAge & HasRole>;

// Identical in type system terms — difference is purely ergonomic (IDE display)


// ── PickByValue<T, ValueType>: pick keys whose values extend ValueType ──

type PickByValue<T, ValueType> = {
  [K in keyof T as T[K] extends ValueType ? K : never]: T[K]
};
// Uses `as` clause in mapped type (key remapping) — type alias only

// Usage:
interface MixedRecord {
  id: number;
  name: string;
  age: number;
  active: boolean;
  email: string;
  score: number;
}

type StringFields  = PickByValue<MixedRecord, string>;
// { name: string; email: string }

type NumericFields = PickByValue<MixedRecord, number>;
// { id: number; age: number; score: number }

type BoolFields    = PickByValue<MixedRecord, boolean>;
// { active: boolean }


// ── Putting it all together: a typed form builder ──

interface FormSchema {
  username:  string;
  age:       number;
  email:     string;
  agreeToTOS: boolean;
  profilePic?: string;
}

// Which fields are text inputs (string values):
type TextFields = PickByValue<FormSchema, string | undefined>;
// { username: string; email: string; profilePic?: string }

// An initial form state where all fields are optional:
type FormState = DeepPartial<FormSchema>;

// A submitted form where all fields are locked:
type SubmittedForm = DeepReadonly<FormSchema>;

// The form config type — prettified so IDE shows flat object:
type FormConfig = Prettify<
  DeepPartial<FormSchema> & {
    onSubmit: (data: FormSchema) => Promise<void>;
    validate?: (data: FormSchema) => Record<string, string>;
  }
>;
// IDE shows: { username?: string; age?: number; ...; onSubmit: ...; validate?: ... }
```

### Why All Four Must Be Type Aliases
- **`DeepPartial` and `DeepReadonly`**: use mapped types (`[K in keyof T]`) and conditional recursion — impossible to express as an interface.
- **`Prettify`**: uses a mapped type over `keyof T` — interface syntax cannot do this.
- **`PickByValue`**: uses the `as` clause in a mapped type for key remapping (`[K in keyof T as T[K] extends ValueType ? K : never]`) — interface syntax has no equivalent.

All four are transformations *on* a type `T`, not descriptions *of* an object shape. This is the essence of why they must be type aliases.

## Quick Reference — Interface vs Type Decision Guide

```
ALWAYS use `interface` when:
  ✓ Defining a class contract (something will be `implements`-ed)
  ✓ Writing a public library API (consumers may need to augment via merging)
  ✓ Augmenting third-party types (declare module + interface = declaration merging)
  ✓ The shape IS-A relationship — Dog extends Animal — explicit inheritance
  ✓ You want clear names in TypeScript error messages

ALWAYS use `type` when:
  ✓ Union types:           type Result = Success | Failure
  ✓ Tuple types:           type Pair = [string, number]
  ✓ Mapped types:          type Partial<T> = { [K in keyof T]?: T[K] }
  ✓ Conditional types:     type NonNull<T> = T extends null ? never : T
  ✓ Template literal:      type OnEvent<T extends string> = `on${Capitalize<T>}`
  ✓ Primitive aliases:     type ID = string; type Ms = number
  ✓ Utility transformers:  DeepPartial, DeepReadonly, PickByValue, Prettify
  ✓ Intersection shorthand: type AB = A & B (when no conflict catching needed)

THE GREY ZONE — plain internal object shapes:
  Both work. Pick one and be consistent. Common convention:
  → `interface` for any named object shape (most common professional default)
  → `type` for anything that isn't a plain object shape
  → ESLint: @typescript-eslint/consistent-type-definitions to enforce the choice

KEY DIFFERENCES:
  interface     │ Declaration merging: YES ← defines the choice for library APIs
  type          │ Declaration merging: NO

  interface     │ Union types: NO ← defines the choice for union/discriminated union
  type          │ Union types: YES

  interface     │ Extends keyword: YES (interface extends interface/type)
  type          │ Intersection (&): equivalent, but conflicts produce 'never' not error

  interface     │ Error messages: shows name ("missing in IUser")
  type          │ Error messages: may expand full shape ("missing in {id: number; ...}")

  interface     │ `implements` in class: YES (always)
  type          │ `implements` in class: YES only if resolves to object type (not union)
```

## Common Bugs Checklist

Before finalizing any TypeScript type design, verify:

1. **Using `type` for a public API shape that consumers need to augment?** — If your library exports `type UserOptions = { ... }` and a consumer needs to add a property, they cannot. Change it to `interface UserOptions { ... }` so they can use `declare module` augmentation. This is the most common library design mistake.

2. **Using `interface` for a union type?** — Interfaces cannot express unions. `interface Status = 'active' | 'inactive'` is a syntax error. Use `type Status = 'active' | 'inactive'`.

3. **Using `&` intersection when property conflicts should be caught early?** — `type C = A & B` where A and B have the same property with different types silently produces `never` for that property. If you want the conflict caught at declaration time, use `interface C extends A, B {}`.

4. **Inconsistent mixing — sometimes `interface User`, sometimes `type User` for the same concept?** — Pick one for object shapes and enforce it with `@typescript-eslint/consistent-type-definitions`. Inconsistency is the primary source of confusion in codebases that "just used whichever felt right at the time."

5. **Forgetting that `interface` extends require compatible types?** — `interface B extends A` where B redefines a property with a narrower type must be assignable to A's version of that property. Narrowing is allowed; incompatible types are not. Catch this at declaration time.

6. **Using a complex type alias where an `interface` would give cleaner error messages?** — If `type UserWithPermissions = User & Permissions & Auditable` and you're getting long error messages, wrap it: `interface UserWithPermissions extends User, Permissions, Auditable {}` — errors now mention the clean name.

7. **Augmenting a type alias (impossible) vs. augmenting an interface (possible)?** — `declare module 'lib' { type X = ... }` is not augmentation — it would redeclare `X` if it's a type alias (error) or be ignored. Only `declare module 'lib' { interface X { ... } }` performs a merge. If the library uses a `type` for the thing you need to augment, you can't — it's a library limitation.

8. **Using `interface` for recursive complex types when `type` handles it better?** — For `DeepPartial`, `DeepReadonly`, and similar patterns that recursively apply mapped types, `type` is not just preferable — it's the only option. Attempting to write these as interfaces results in syntax errors.

---

**Final Tip:** The single question that resolves 90% of interface-vs-type decisions in real codebases: *"Will consumers of this type ever need to add properties to it without modifying the original declaration?"* If yes — library authors, plugin systems, framework extension points, global type augmentation — use `interface`. If no — internal application types, discriminated unions, utility types, computed types — use `type` (or `interface` for plain object shapes, consistently). Everything else — conflicting member detection, error message clarity, class contracts — are secondary factors that refine the choice but rarely reverse it.
