## Topic A: Type Inference Mechanics

### Section A1: How TypeScript Infers Types

**Q1. What is type inference, and when should you use explicit annotations instead?**

A: Type inference is TypeScript's ability to determine the type of an expression automatically from its value, context, or usage — without requiring an explicit `: Type` annotation. TypeScript assigns types during compilation; at runtime, all type information is erased. Inference is not guessing — it applies deterministic rules to the syntax tree.

Use explicit annotations when: (1) **function parameters** — TypeScript cannot infer parameter types without either an annotation or contextual typing; (2) **public API contracts** — an explicit return type annotation is a commitment, not just a description; if inference changes due to implementation changes, a regression is caught; (3) **complex inferred types are wrong** — inference occasionally widens or narrows too aggressively; (4) **improving readability** — deeply nested inferred types are sometimes clearer with an explicit name.

```typescript
// TypeScript infers — no annotation needed:
const x = 42;           // x: 42       (literal, const)
let y = 'hello';        // y: string   (widened, let)
const arr = [1, 2, 3];  // arr: number[]

// Explicit annotation required — TS cannot infer parameter types:
function add(a: number, b: number) { return a + b; } // return type: number (inferred)

// Explicit return type — API contract, not just description:
function getUser(id: string): Promise<User> {  // explicit: any change to return type is an error
  return db.findUser(id);
}

// Inference is wrong — fix with annotation:
const flags = ['read', 'write'];    // string[] — too wide
const flags2: ('read' | 'write')[] = ['read', 'write']; // ✓
```

**Q2. What is "type widening," why does `let` widen but `const` doesn't, and what are the rules?**

A: Type widening is the process of expanding a literal type to its base type. When you write `let x = 'hello'`, TypeScript widens the type from the literal `'hello'` to `string` — because `let` allows reassignment, and assigning `x = 'world'` must be valid. `const x = 'hello'` cannot be reassigned, so TypeScript keeps the literal type `'hello'`.

Widening rules: (1) `let` / `var` with a literal initializer → widened to base type. (2) `const` with a primitive value → literal type preserved. (3) `const` with an object or array → the container is const but property values are still mutable, so object property types are widened to base types (not literals). (4) `as const` → suppresses all widening, preserves every literal.

```typescript
const a = 'hello';            // a: "hello"         — literal preserved (const)
let   b = 'hello';            // b: string           — widened (let, reassignable)
let   c: 'hello' = 'hello';  // c: "hello"          — explicit literal overrides widening

const obj  = { x: 1 };       // obj: { x: number }  — property widened (mutable)
const obj2 = { x: 1 } as const; // obj2: { readonly x: 1 } — literal preserved

const arr  = [1, 2, 3];       // arr: number[]       — element type widened
const arr2 = [1, 2, 3] as const; // arr2: readonly [1, 2, 3] — tuple with literals

// Widening in practice — common source of type errors:
function paintColor(color: 'red' | 'blue') { /* ... */ }
const chosen = 'red';      // type: "red" ✓ (const keeps literal)
let   chosen2 = 'red';     // type: string ✗ (widened — can't pass to paintColor)
paintColor(chosen);        // ✓
paintColor(chosen2);       // ✗ Argument of type 'string' is not assignable to parameter of type '"red" | "blue"'
```

**Q3. How does TypeScript infer function return types, and when can inference break down?**

A: TypeScript infers the return type of a function by computing the union of the types of all `return` expressions in the function body. If a function has a `return 'hello'` path and a `return 42` path, the inferred return type is `string | number`. A function with no `return` statement (or only `return;`) gets inferred return type `void`. An infinite loop or always-throws function gets `never`. Inference breaks down in four cases: (1) **recursive functions** — TypeScript cannot infer the return type when the function calls itself before the type is known (implicit `any` or error); (2) **overloaded functions** — inference only sees the implementation signature; (3) **complex conditional logic** — the inferred union may be wider than intended; (4) **when you want to enforce a contract** — inference accepts accidental widening.

```typescript
// Inference works well:
function greet(name: string) {
  return `Hello, ${name}`; // inferred: string
}

function getStatus(code: number) {
  if (code === 200) return 'ok';   // 'ok'
  if (code === 404) return null;   // null
  return code;                     // number
} // inferred return type: "ok" | null | number

// Inference fails for recursive functions (requires explicit annotation):
function fibonacci(n: number): number {  // ← explicit required
  return n <= 1 ? n : fibonacci(n - 1) + fibonacci(n - 2);
  // Without ': number', TypeScript sees return type referencing fibonacci()
  // before it's finished computing the type → error or implicit any
}

// Inference widens unintentionally — use explicit to lock the contract:
function createAction(type: string) {
  return { type, payload: null }; // inferred: { type: string, payload: null }
  // Callers can pass any string — may want: 'increment' | 'decrement'
}
function createAction2(type: 'increment' | 'decrement') {
  return { type } as const; // return type: { type: 'increment' | 'decrement' } (as const)
}
```

**Q4. What is contextual typing, and what language features trigger it?**

A: Contextual typing (also called "pushdown typing") occurs when TypeScript uses the **expected type** of an expression (from context) to infer types of sub-expressions. It's the reverse of normal inference: instead of inferring from a value upward, TypeScript pushes the known expected type downward into the expression. This allows callbacks to have parameter types inferred from the function they're passed to, object properties to have types from their interface, and initializers to have types from their declared type.

Contextual typing triggers when an expression appears in a position where a type is already known: callback parameters in `.map()`, `.filter()`, `addEventListener`; object literals assigned to a typed variable; function expressions assigned to a typed variable; default parameter values; return expressions in a typed function.

```typescript
// Contextual typing via Array.map callback:
const nums = [1, 2, 3];
const doubled = nums.map(n => n * 2); // n: number — inferred from nums: number[]
                                       // TypeScript pushes 'number' down to the parameter

// Contextual typing via typed variable assignment:
type Handler = (event: MouseEvent) => void;
const onClick: Handler = (e) => {
  // e: MouseEvent — inferred from Handler type, no annotation needed on 'e'
  console.log(e.clientX, e.clientY); // ✓ MouseEvent properties accessible
};

// Contextual typing via addEventListener:
document.addEventListener('click', (e) => {
  // e: MouseEvent — TypeScript knows 'click' events produce MouseEvent
  e.preventDefault(); // ✓ no annotation on 'e'
});

// Contextual typing pushes type into object literal:
interface Config { port: number; host: string; }
const serverConfig: Config = {
  port: 3000,     // checked against Config.port: number ✓
  host: 'localhost', // checked against Config.host: string ✓
  // extra: 'value' // ✗ excess property check — unknown property
};
```

**Q5. What is the `as const` assertion, what types does it produce, and how does it compare to type annotations?**

A: `as const` is a type assertion that tells TypeScript to infer the most specific (literal) type possible and make everything readonly. For objects: each property gets its literal type and becomes `readonly`. For arrays: the array becomes a `readonly` tuple with literal element types. For primitives: the expression gets its literal type (usually not needed since `const` already does this for simple declarations).

`as const` differs from a type annotation: an annotation widens the inferred type to match the annotation (you lose literal specificity); `as const` preserves literal specificity while still allowing TypeScript to infer the shape. `as const satisfies T` (TypeScript 4.9+) combines both: `satisfies` validates the shape against `T`, while `as const` preserves literal types.

```typescript
// Without as const:
const config = { env: 'production', port: 3000 };
// config: { env: string; port: number } — literals lost

// With as const:
const config = { env: 'production', port: 3000 } as const;
// config: { readonly env: "production"; readonly port: 3000 } — literals preserved

// Arrays:
const methods = ['GET', 'POST', 'PUT'];
// methods: string[] — literals lost, not a tuple

const methods2 = ['GET', 'POST', 'PUT'] as const;
// methods2: readonly ["GET", "POST", "PUT"] — tuple with literals ✓

// Enum-like pattern with as const:
const Direction = { Up: 'UP', Down: 'DOWN', Left: 'LEFT', Right: 'RIGHT' } as const;
type Direction = typeof Direction[keyof typeof Direction]; // 'UP' | 'DOWN' | 'LEFT' | 'RIGHT'

// as const vs annotation:
const c1: { port: number } = { port: 3000 };       // c1.port: number (annotation widens)
const c2 = { port: 3000 } as const;                 // c2.port: 3000 (literal preserved)
const c3 = { port: 3000 } satisfies { port: number }; // c3.port: 3000 (satisfies validates, keeps literal)
```

## Topic B: Generic Type Inference

### Section B1: Inference Through Generics

**Q6. How does TypeScript infer generic type parameters, and what are the constraints?**

A: When a generic function is called without explicit type arguments, TypeScript infers the type arguments from the actual arguments passed (or from the expected return type in some cases). The inference works by unification: TypeScript matches the call site argument types against the generic parameter positions in the function's type signature. If multiple arguments constrain the same type parameter, TypeScript computes the best common type (union) of the inferences. Inference fails (falls back to `unknown` or `{}`) when the type parameter isn't used in the argument positions — TypeScript can't infer it from a return position alone.

```typescript
function identity<T>(x: T): T { return x; }
identity(42);        // T inferred as 42 (literal for const context) or number
identity('hello');   // T inferred as string

function pair<A, B>(a: A, b: B): [A, B] { return [a, b]; }
pair(1, 'two');      // A = number, B = string → [number, string]

// Multiple constraints — best common type:
function first<T>(arr: T[]): T | undefined { return arr[0]; }
first([1, 2, 3]);    // T = number
first(['a', 'b']);   // T = string

// Inference from array with mixed types:
function zip<T, U>(a: T[], b: U[]): [T, U][] {
  return a.map((item, i) => [item, b[i]] as [T, U]);
}
zip([1, 2], ['a', 'b']); // T = number, U = string → [number, string][]

// Inference fails — T not in argument position:
function create<T>(): T { return {} as T; } // T cannot be inferred from call site
create();         // T = unknown (no argument to infer from)
create<User>();   // must provide explicit type argument
```

**Q7. What is the `infer` keyword in conditional types, and what does it extract?**

A: `infer` introduces a type variable that is captured ("inferred") during conditional type evaluation. It appears in the extends clause of a conditional type and is bound to whatever part of the matched type occupies that position. It enables extracting components of complex types: the return type of a function, the element type of an array, the value type of a Promise, parameter types, etc.

```typescript
// Built-in utility types using infer:
type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
// If T is a function type, R is inferred to be its return type.

type Awaited<T> = T extends Promise<infer V> ? V : T;
// If T is Promise<V>, extract V. Otherwise return T as-is.

type ElementType<T> = T extends (infer E)[] ? E : never;
// Extract the element type of an array.

type Parameters<T extends (...args: any[]) => any> =
  T extends (...args: infer P) => any ? P : never;
// Extract parameter types as a tuple.

// Practical examples:
type R1 = ReturnType<() => string>;          // string
type R2 = ReturnType<(x: number) => void>;   // void
type R3 = Awaited<Promise<User>>;            // User
type R4 = Awaited<Promise<Promise<number>>>; // number (recursive)
type R5 = ElementType<string[]>;             // string
type R6 = Parameters<(id: string, count: number) => void>; // [string, number]

// Custom usage — extract the second argument of a function:
type SecondArg<T extends (a: any, b: any, ...rest: any[]) => any> =
  T extends (a: any, b: infer B, ...rest: any[]) => any ? B : never;

type Fn = (id: string, options: { limit: number }) => void;
type SA = SecondArg<Fn>; // { limit: number }
```

**Q8. What is the `satisfies` operator (TypeScript 4.9+), and what problem does it solve that neither annotation nor `as const` alone solves?**

A: `satisfies` validates that an expression matches a type WITHOUT widening the expression to that type. Before `satisfies`, developers faced a trade-off: using a type annotation widens the type (you lose literal precision); omitting the annotation keeps literal precision but loses validation (no error if the shape is wrong). `satisfies` gives you both simultaneously — TypeScript checks the shape against the constraint type, but the inferred type remains the precise literal type of the expression.

```typescript
type Route = { path: string; method: 'GET' | 'POST' | 'PUT' | 'DELETE' };

// Annotation only — shape checked, but literals lost:
const r1: Route = { path: '/users', method: 'GET' };
// r1.method: 'GET' | 'POST' | 'PUT' | 'DELETE' — widened ✗
// r1.method === 'GET' needs no error, but so does r1.method === 'PATCH' — wrong

// as const only — literals preserved, but shape NOT checked:
const r2 = { path: '/users', method: 'MISPELLED' } as const;
// No error! 'MISPELLED' is accepted — shape not validated ✗

// satisfies — shape checked AND literals preserved:
const r3 = { path: '/users', method: 'GET' } satisfies Route;
// r3.method: "GET" — literal type preserved ✓
// r3.method: 'MISPELLED' satisfies Route — ERROR: Type '"MISPELLED"' is not assignable to... ✓

// Real-world: config object where you want both validation AND literal access:
type PaletteColors = 'primary' | 'secondary' | 'error';
type ColorConfig = Record<PaletteColors, string | { light: string; dark: string }>;

const palette = {
  primary: { light: '#60a5fa', dark: '#1d4ed8' },
  secondary: '#8b5cf6',
  error: '#ef4444',
} satisfies ColorConfig;

// palette.primary is { light: string; dark: string } — not string | { light... }
// palette.secondary is string — not string | { light... }
// With annotation ': ColorConfig', both would be string | { light: string; dark: string }
palette.primary.light; // ✓ TypeScript knows this is an object, not a string
```

## Topic C: Type Narrowing Techniques

### Section C1: The Six Built-In Narrowing Mechanisms

**Q9. What is control flow analysis, and how does TypeScript track types through code branches?**

A: Control flow analysis (CFA) is TypeScript's ability to infer the type of a variable at each specific point in the code based on the code that has executed before that point. TypeScript builds a type graph for each function: at each node, it tracks which types each variable can have given the conditions that must have been true to reach that node. Type narrowing is the process of reducing a variable's type from a wider set to a narrower set at a particular node.

CFA handles: `if/else` branches (each branch has its own narrowed type), `switch/case`, `while`/`for` loops, ternary expressions, logical `&&`/`||`/`??` operators, early returns (after `return`, the remaining code has the non-returning type), and assignments (assigning `x = 'hello'` narrows x to `string` at that point). TypeScript reassembles ("joins") the types at merge points (end of if/else, end of switch) with the union of the narrowed types from each branch.

```typescript
function process(x: string | number | null) {
  // x: string | number | null

  if (x === null) {
    return; // ← early return
  }
  // x: string | number (null excluded after early return)

  if (typeof x === 'string') {
    // x: string
    return x.toUpperCase();
  }
  // x: number (string excluded above)

  return x.toFixed(2); // x is definitely number here
}

// Assignment narrowing:
let value: string | number = getFromApi(); // string | number
value = 42;  // After this line: value: 42 (narrowed to literal)
value.toFixed(2); // ✓ — TypeScript knows it's 42 (or at least number)
value = 'hello'; // After this line: value: string
value.toUpperCase(); // ✓

// Logical operator narrowing:
function logName(user: User | null) {
  user && console.log(user.name); // user: User in the right operand
  user?.name; // Optional chaining — same semantics
}
```

**Q10. What are the six built-in narrowing mechanisms TypeScript supports?**

A:

**1. `typeof` narrowing** — discriminates primitive types: `'string'`, `'number'`, `'boolean'`, `'bigint'`, `'symbol'`, `'undefined'`, `'function'`. Note: `typeof null === 'object'` (a historical JavaScript bug) — `null` is not narrowed out by `typeof x === 'object'`; you must additionally check `x !== null`.

**2. `instanceof` narrowing** — checks class instance: `x instanceof Date` narrows x to `Date`. Works with any constructor function. Does not work with plain object interfaces (no runtime representation).

**3. `in` operator narrowing** — checks property existence: `'radius' in shape` narrows shape to types that have a `radius` property. Works for discriminating union members by a unique property.

**4. Truthiness narrowing** — `if (x)`, `if (x != null)`, `Boolean(x)`: falsy values (`false`, `0`, `''`, `null`, `undefined`, `NaN`) are excluded. `x != null` (loose equality) excludes both `null` AND `undefined`.

**5. Equality narrowing** — `x === 'literal'` narrows x to `'literal'`; `x === y` where y is a narrowed type narrows x to that type; `x !== null` narrows x to exclude null.

**6. Assignment narrowing** — after `x = expr`, TypeScript narrows x to the type of `expr` at that point, within the scope.

```typescript
function demo(x: string | number | null | undefined) {
  // 1. typeof:
  if (typeof x === 'string') { x; /* string */ }

  // 2. instanceof (works with classes, not interfaces):
  const d: Date | string = getDate();
  if (d instanceof Date) { d.getFullYear(); /* Date */ }

  // 3. in operator:
  type Circle = { kind: 'circle'; radius: number };
  type Rect   = { kind: 'rect'; width: number; height: number };
  function area(s: Circle | Rect) {
    if ('radius' in s) { s; /* Circle */ }
  }

  // 4. Truthiness:
  if (x) { x; /* string | number (falsy values excluded — but 0 and '' are truthy? no, they're excluded by if(x)) */ }
  // x: string | number | null | undefined after the if (x) check filters all falsy
  // Actually: after if(x), x is string | number (but 0 and '' would be excluded too)
  if (x != null) { x; /* string | number */ } // excludes null and undefined

  // 5. Equality:
  if (x === null) { x; /* null */ }
  else { x; /* string | number | undefined */ }

  // 6. Assignment:
  let y: string | number = maybeString();
  y = 42; // After: y is 42 (number literal type — or at least number)
}
```

**Q11. What is a user-defined type guard, when is it needed, and what is its key risk?**

A: A user-defined type guard is a function whose return type is a **type predicate** of the form `param is Type`. When TypeScript evaluates a call to this function in a conditional, it narrows the type of `param` to `Type` in the true branch. Type guards are needed when: (1) the value has type `unknown` or `any` and must be narrowed to a specific interface (which `instanceof` and `typeof` can't do); (2) the narrowing logic is complex and must be reused; (3) you need to narrow a union member that lacks a discriminant property.

The key risk: TypeScript **trusts the return type annotation unconditionally**. If the runtime check doesn't match the type predicate, TypeScript will happily narrow to the wrong type — and you get a runtime crash with no TypeScript error. Type predicates must be kept in sync with the actual runtime check manually.

```typescript
interface User { id: string; name: string; email: string; }
interface Admin extends User { role: 'admin'; permissions: string[]; }

// User-defined type guard — narrows unknown to User:
function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    typeof (x as any).id === 'string' &&
    typeof (x as any).name === 'string' &&
    typeof (x as any).email === 'string'
  );
}

// Usage:
const data: unknown = await fetch('/api/me').then(r => r.json());
if (isUser(data)) {
  // data: User — narrowed by the type guard ✓
  console.log(data.name);
}

// THE RISK — wrong predicate, TypeScript trusts it:
function isBrokenUser(x: unknown): x is User {
  return typeof x === 'object'; // too permissive! null passes, {id:1} passes
}
const evil: unknown = { id: 1, name: 2 }; // id is number, not string!
if (isBrokenUser(evil)) {
  evil.email.toUpperCase(); // ← TypeScript says ✓, runtime says CRASH (email is undefined)
}

// Safer alternative for simple cases — using assertion functions (Q17):
function assertIsUser(x: unknown): asserts x is User {
  if (!isUser(x)) throw new TypeError('Expected User object');
}

// Generic non-null guard — extremely useful:
function isNonNullable<T>(x: T): x is NonNullable<T> {
  return x !== null && x !== undefined;
}
const maybeUsers: (User | null)[] = getUsers();
const users: User[] = maybeUsers.filter(isNonNullable); // ✓ — filter's type predicate accepted
```

**Q12. What is a discriminated union, how does TypeScript narrow it, and what makes a good discriminant property?**

A: A discriminated union (also called a tagged union or algebraic data type) is a union where every member has a common property — the **discriminant** — that holds a unique literal type per member. TypeScript uses the discriminant's value in conditions (`=== 'circle'`, `switch (shape.kind)`) to narrow to exactly one union member. This is the most powerful and reliable narrowing mechanism because: (1) the discriminant is present on all union members (no `in` check needed), (2) literal types make the narrowing complete, and (3) exhaustiveness checking via `never` catches missing cases.

A good discriminant property is: (a) present on every union member with no optional members, (b) typed as a unique literal on each member (`string` or `number` literal, not a union), (c) named consistently (`kind`, `type`, `tag`, `status` are common conventions), (d) a string literal for switch/case readability.

```typescript
type Shape =
  | { kind: 'circle';    radius: number }
  | { kind: 'rectangle'; width: number; height: number }
  | { kind: 'triangle';  base: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':
      // shape: { kind: 'circle'; radius: number }
      return Math.PI * shape.radius ** 2;

    case 'rectangle':
      // shape: { kind: 'rectangle'; width: number; height: number }
      return shape.width * shape.height;

    case 'triangle':
      // shape: { kind: 'triangle'; base: number; height: number }
      return 0.5 * shape.base * shape.height;

    default:
      // shape: never (all cases handled — TypeScript knows this is unreachable)
      return assertUnreachable(shape);
  }
}

function assertUnreachable(x: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(x)}`);
}

// When you add a new union member:
type Shape2 = Shape | { kind: 'ellipse'; radiusX: number; radiusY: number };
// area() now has a TypeScript error at 'assertUnreachable(shape)':
// "Argument of type '{ kind: "ellipse"; ... }' is not assignable to parameter of type 'never'"
// ← exhaustiveness check works! ✓
```

## Topic D: Advanced Narrowing & Interview-Style

**Q13. What is the `never` type, and how does it enable exhaustiveness checking?**

A: `never` is the "bottom type" — a type that has no values. It represents computations that never produce a value: infinite loops, functions that always throw, `process.exit()`. In the type system, `never` is a subtype of every type but no type is a subtype of `never` (except `never` itself). After narrowing all possible union members, the remaining type should be `never` — because there are no values left. An `assertUnreachable(x: never)` function exploits this: if you call it with a value, TypeScript checks that the value has type `never`. If any union case is not handled, the value still has a non-`never` type, and TypeScript reports an error at the `assertUnreachable` call.

```typescript
// never as return type — function never returns:
function fail(message: string): never {
  throw new Error(message); // never returns a value
}

// never in exhaustiveness checking:
type Status = 'pending' | 'active' | 'cancelled';
function handleStatus(status: Status): string {
  if (status === 'pending')   return 'Waiting...';
  if (status === 'active')    return 'Processing';
  if (status === 'cancelled') return 'Cancelled';

  // status: never here — all cases handled
  // Without this line, if we add 'expired' to Status, no error is reported:
  return assertUnreachable(status); // compile-time safety net ✓
}

// Add 'expired' to Status:
type Status2 = 'pending' | 'active' | 'cancelled' | 'expired';
// handleStatus now errors: "Argument of type '"expired"' is not assignable to 'never'"
// ← compile-time reminder to handle the new case

// never in conditional types — filter out types:
type NonNullable<T> = T extends null | undefined ? never : T;
// If T is null or undefined → never. Otherwise → T.
// NonNullable<string | null | undefined> = string (null/undefined become never, removed from union)

// never in mapped types — remove properties:
type OmitNever<T> = { [K in keyof T as T[K] extends never ? never : K]: T[K] };
```

**Q14. What is the difference between `typeof`, `instanceof`, and `in` for narrowing — which to use when?**

A:

**`typeof`** — use for JavaScript primitive types. Guards against `string`, `number`, `boolean`, `bigint`, `symbol`, `undefined`, `function`. Does NOT distinguish between different object types (everything non-primitive is `'object'` — including `null`, arrays, dates, class instances). Always the right choice for primitives.

**`instanceof`** — use for class instances. Checks the prototype chain: `x instanceof ClassName` is true if `ClassName.prototype` is anywhere in x's prototype chain. Works for: built-in classes (`Date`, `Error`, `Map`, `Set`, `Array`), custom classes. Does NOT work for TypeScript interfaces (no runtime representation) or plain objects. Best for: error handling (`err instanceof TypeError`), date checking, class hierarchy narrowing.

**`in`** — use for objects with distinguishing properties, especially when working with interfaces (not classes). `'radius' in shape` is true if the `radius` property exists on the object (own or inherited). Best for: discriminating union members when there's no class hierarchy, checking for optional properties, narrowing when `instanceof` isn't applicable.

```typescript
// typeof — primitives only:
function handleInput(x: string | number | boolean | null) {
  if (typeof x === 'string')  { /* x: string */ }
  if (typeof x === 'number')  { /* x: number */ }
  if (typeof x === 'boolean') { /* x: boolean */ }
  // null: typeof null === 'object' — NOT narrowed! Must use x === null
}

// instanceof — class instances:
function handleError(e: unknown) {
  if (e instanceof TypeError)   { /* e: TypeError */ }
  if (e instanceof RangeError)  { /* e: RangeError */ }
  if (e instanceof Error)       { /* e: Error */ } // catches all Error subclasses
  // TypeScript interfaces (User, Config) — NOT usable with instanceof (no constructor)
}

// in — interface/object discrimination:
type Cat = { name: string; meow(): void };
type Dog = { name: string; bark(): void };
function makeSound(animal: Cat | Dog) {
  if ('meow' in animal) { animal.meow(); /* animal: Cat */ }
  else                  { animal.bark(); /* animal: Dog */ }
}
// Works for interfaces that don't have class constructors
```

**Q15. What are assertion functions (`asserts condition`), how do they differ from type guards, and when should you use them?**

A: Assertion functions return `void` (not `boolean`) but have a special return type signature: `asserts condition` or `asserts param is Type`. Unlike type guards (which return `true`/`false` and narrow in the `if` branch), assertion functions **throw** when the condition fails and narrow **all code after the call** — they assert unconditionally. This is useful for validation at function entry points: if the data is invalid, throw immediately; if the function continues, TypeScript knows the assertion held.

```typescript
// Type guard (return boolean — narrows in if branch):
function isString(x: unknown): x is string {
  return typeof x === 'string';
}
const val: unknown = getVal();
if (isString(val)) {
  val.toUpperCase(); // ← narrowed only inside the if
}
// val: unknown here — no narrowing outside the if

// Assertion function (throws on failure — narrows AFTER the call):
function assertIsString(x: unknown): asserts x is string {
  if (typeof x !== 'string') throw new TypeError(`Expected string, got ${typeof x}`);
}
assertIsString(val);
val.toUpperCase(); // ← narrowed here — all code after the call ✓

// Boolean assertion (asserts the argument is true):
function assert(condition: boolean, message?: string): asserts condition {
  if (!condition) throw new Error(message ?? 'Assertion failed');
}
const user: User | null = getUser();
assert(user !== null, 'User must exist at this point');
user.name; // ← narrowed: user is User (not null) ✓

// Using assertion functions vs type guards:
// Type guard: when you need to branch (true → do X, false → do Y)
// Assertion: when failure means the program state is invalid — crash immediately
// Assertion is common in: constructors, validation at API entry points, test helpers

// NestJS-style usage in a controller guard:
function assertAuthenticated(req: Request): asserts req is AuthenticatedRequest {
  if (!req.user) throw new UnauthorizedException('Not authenticated');
}
@Get('/profile')
async getProfile(@Req() req: Request) {
  assertAuthenticated(req); // after this line: req is AuthenticatedRequest ✓
  return req.user.profile;
}
```

**Q16. What is the "narrowing in callbacks" problem, and how does TypeScript handle it?**

A: TypeScript's control flow analysis is conservative inside callbacks: it does not assume that a variable's narrowed type from before the callback is still valid inside the callback, because the callback could be called at any time (before or after the narrowing condition changes). TypeScript treats callbacks as potentially escaping the current control flow — the variable may have been reassigned between the narrowing check and the callback invocation.

```typescript
let user: User | null = getUser();

if (user !== null) {
  // user: User here ✓
  Promise.resolve().then(() => {
    // user: User | null ← TypeScript re-widens! The callback may run after user is reassigned
    user.name; // ✗ Error: 'user' is possibly null
  });

  // Fix 1: capture in const before the callback:
  const u = user; // u: User — const can't be reassigned
  Promise.resolve().then(() => {
    u.name; // ✓ u is const, TypeScript knows it's still User
  });

  // Fix 2: add a guard inside the callback:
  Promise.resolve().then(() => {
    if (user !== null) user.name; // ✓ re-narrow inside callback
  });
}

// This is intentional — TypeScript is correct to be cautious:
let value: string | null = 'hello';
if (value !== null) {
  setTimeout(() => console.log(value.toUpperCase()), 1000); // ← value might be null after 1s!
  value = null; // ← user reassigns value before the setTimeout fires
}
// TypeScript protecting you from this real bug ✓
```

**Q17. What is the "type predicate abuse" anti-pattern, and how do you write defensive type guards?**

A: Type predicate abuse is writing a function that returns `x is SomeType` but performs an inadequate runtime check — TypeScript trusts the predicate regardless. This creates a false sense of type safety where the types say "string" but the runtime value is a number. Defensive type guards: check every property expected by the interface, check types recursively, and use `unknown` (not `any`) for the input parameter so TypeScript forces you to check before using.

```typescript
// Anti-pattern: lazy predicate
function isUser(x: any): x is User {
  return !!x; // ← only checks truthiness! Objects, arrays, "hello" all pass
}

// Defensive: check the full shape
function isUser(x: unknown): x is User {
  if (typeof x !== 'object' || x === null) return false;
  const u = x as Record<string, unknown>; // safe cast to checkable form
  return (
    typeof u.id === 'string' &&
    typeof u.name === 'string' &&
    typeof u.email === 'string' &&
    (u.role === undefined || typeof u.role === 'string') // optional fields
  );
}

// Pattern: use a schema validation library and derive the type guard from it:
// Zod:
import { z } from 'zod';
const UserSchema = z.object({ id: z.string(), name: z.string(), email: z.string() });
type User = z.infer<typeof UserSchema>; // type derived from schema
function parseUser(x: unknown): User {
  return UserSchema.parse(x); // throws ZodError with details if invalid
}
// Or: UserSchema.safeParse(x) → { success: boolean; data?: User; error?: ZodError }
```

**Q18. In one sentence each, state what each type narrowing mechanism does.**

A:
- **`typeof` narrowing**: checks the JavaScript runtime type of a value and narrows to the corresponding TypeScript primitive type.
- **`instanceof` narrowing**: checks the prototype chain and narrows to a class constructor's instance type.
- **`in` operator narrowing**: checks property existence and narrows to union members that have that property.
- **Truthiness narrowing**: excludes falsy values (`null`, `undefined`, `false`, `0`, `''`, `NaN`) from the type in the truthy branch.
- **Equality narrowing**: narrows by exact value comparison, eliminating all union members that don't match the compared literal.
- **Assignment narrowing**: after `x = expr`, narrows `x` to the type of `expr` at that point in the code.
- **User-defined type guard (`is` predicate)**: delegates narrowing to a custom runtime check; TypeScript trusts the predicate's return type unconditionally.
- **Discriminated union narrowing**: narrows a union via a shared literal-typed discriminant property — the most reliable and exhaustive narrowing mechanism.
- **`never` exhaustiveness check**: after all union members are handled, the remaining type is `never`; passing it to an `assertUnreachable(x: never)` function catches missing cases at compile time.
- **Assertion function (`asserts`)**: throws on failure and narrows all code after the call — unlike type guards that only narrow the `if` branch.

## Implementation 2 — Discriminated Union: API Response with Exhaustive Narrowing

### Challenge
Model an API response as a discriminated union with three states (loading, error, success). Implement a renderer that handles all cases with compile-time exhaustiveness checking — adding a new state automatically causes a compile error in the handler.

### Implementation

```typescript
// ═══ TYPE DEFINITIONS ════════════════════════════════════════════════════

type ApiState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error';   error: Error; retryCount: number }
  | { status: 'success'; data: T; timestamp: Date };

// Discriminant: 'status' property with unique literal on each member ✓

// ═══ EXHAUSTIVENESS HELPER ═══════════════════════════════════════════════

function assertUnreachable(x: never, message?: string): never {
  throw new Error(message ?? `Unhandled case: ${JSON.stringify(x)}`);
}

// ═══ HANDLER WITH EXHAUSTIVE SWITCH ══════════════════════════════════════

function renderApiState<T>(
  state: ApiState<T>,
  renderData: (data: T) => string
): string {
  switch (state.status) {
    case 'idle':
      // state: { status: 'idle' }
      return 'Ready.';

    case 'loading':
      // state: { status: 'loading' }
      return 'Loading...';

    case 'error':
      // state: { status: 'error'; error: Error; retryCount: number }
      return `Error: ${state.error.message} (attempt ${state.retryCount})`;

    case 'success':
      // state: { status: 'success'; data: T; timestamp: Date }
      return `[${state.timestamp.toISOString()}] ${renderData(state.data)}`;

    default:
      // state: never — all cases handled
      return assertUnreachable(state, 'Unknown ApiState status');
  }
}

// ═══ NARROWING IN CONDITIONAL EXPRESSIONS ════════════════════════════════

function getDataOrThrow<T>(state: ApiState<T>): T {
  if (state.status !== 'success') {
    // state: { status: 'idle' } | { status: 'loading' } | { status: 'error'; ... }
    throw new Error(`Cannot get data in state: ${state.status}`);
  }
  // state: { status: 'success'; data: T; timestamp: Date } — narrowed ✓
  return state.data; // ← TypeScript knows data exists here
}

// ═══ TYPE-SAFE STATE TRANSITIONS ══════════════════════════════════════════

function transition<T>(
  current: ApiState<T>,
  event:
    | { type: 'FETCH' }
    | { type: 'SUCCESS'; data: T }
    | { type: 'ERROR'; error: Error }
    | { type: 'RESET' }
): ApiState<T> {
  switch (event.type) {
    case 'FETCH':
      return { status: 'loading' };

    case 'SUCCESS':
      // event: { type: 'SUCCESS'; data: T }
      return { status: 'success', data: event.data, timestamp: new Date() };

    case 'ERROR':
      // event: { type: 'ERROR'; error: Error }
      const retryCount = current.status === 'error' ? current.retryCount + 1 : 1;
      // current.status === 'error' → current: { status: 'error'; retryCount: number }
      // TypeScript narrows current inside the ternary ✓
      return { status: 'error', error: event.error, retryCount };

    case 'RESET':
      return { status: 'idle' };

    default:
      return assertUnreachable(event);
  }
}
```

### Implementation

```typescript

// ═══ PRIMITIVE TYPE GUARDS ════════════════════════════════════════════════

function isNonNullable<T>(value: T): value is NonNullable<T> {
  return value !== null && value !== undefined;
}

// Usage with Array.filter:
const raw: (string | null | undefined)[] = ['a', null, 'b', undefined, 'c'];
const clean: string[] = raw.filter(isNonNullable); // ✓ — filter accepts type predicate

// ═══ STRUCTURAL TYPE GUARDS ═══════════════════════════════════════════════

interface User {
  id: string;
  name: string;
  email: string;
  role: 'admin' | 'user' | 'moderator';
}

// Safe validation: returns boolean, narrows in if branch:
function isUser(x: unknown): x is User {
  if (typeof x !== 'object' || x === null) return false;
  const obj = x as Record<string, unknown>;
  return (
    typeof obj.id === 'string' &&
    typeof obj.name === 'string' &&
    typeof obj.email === 'string' &&
    (obj.role === 'admin' || obj.role === 'user' || obj.role === 'moderator')
  );
}

      issues.push(`Expected object, got ${x === null ? 'null' : typeof x}`);

      const obj = x as Record<string, unknown>;
      if (typeof obj.id !== 'string')    issues.push(`id: expected string, got ${typeof obj.id}`);
      if (typeof obj.name !== 'string')  issues.push(`name: expected string`);
      if (typeof obj.email !== 'string') issues.push(`email: expected string`);
    }
    throw new TypeError(`Invalid User: ${issues.join('; ')}`);
  }
}

// ═══ USAGE COMPARISON ════════════════════════════════════════════════════

  // data: User — narrowed ✓
  console.log(data.name);
} else {
  console.error('Invalid user data from API');
}

// Pattern 2 — assertion (throw on invalidity):
assertUser(data); // throws if invalid with descriptive error
// data: User — narrowed for all subsequent code ✓
console.log(data.name); // ✓ no if block needed

// ═══ ZOD INTEGRATION (PREFERRED IN PRODUCTION) ════════════════════════════

const UserSchema = z.object({
  id:    z.string(),
  name:  z.string(),
  email: z.string().email(),
  role:  z.enum(['admin', 'user', 'moderator']),
});

type UserFromSchema = z.infer<typeof UserSchema>; // identical to User interface

// Safe parse — returns { success: boolean; data?: User; error?: ZodError }:
const result = UserSchema.safeParse(data);
if (result.success) {
  // result.data: User — narrowed by discriminated union on result.success ✓
  console.log(result.data.name);
}

// Strict parse — throws ZodError with full issue list:
const user = UserSchema.parse(data); // user: User ✓

// ═══ GUARD FOR DISCRIMINATED UNION ════════════════════════════════════════

type ApiError = { type: 'ApiError'; status: number; message: string };

}

function handleError(e: AppError): string {
  if (isApiError(e)) {
    return `HTTP ${e.status}: ${e.message}`; // e: ApiError ✓
  }
```

```typescript
    // event: { type: 'click'; target: HTMLElement; x: number; y: number }
    if (event.x < 0 || event.y < 0) {
      console.log('Out of bounds click');
      return;
    }
    // After the if: event.x >= 0 AND event.y >= 0 (TypeScript tracks sign? No — only equality/typeof)
    // But: no error — x and y are still number
    handleClick(event.target, event.x, event.y);

  } else if (event.type === 'keypress') {
    // event: { type: 'keypress'; key: string; ctrlKey: boolean }
    if (event.ctrlKey && event.key === 'c') {
      handleCopy();
    }

  } else {
    // event: { type: 'scroll'; deltaX: number; deltaY: number }
    // TypeScript eliminated 'click' and 'keypress' — only 'scroll' remains
    handleScroll(event.deltaX, event.deltaY);
  }
}

// ═══ THE CALLBACKS-WIDEN PROBLEM AND FIX ══════════════════════════════════

function riskyWithCallback(user: User | null): void {
  if (!user) return;
  // user: User here ✓

  // setTimeout callback — TypeScript widens:
  setTimeout(() => {
    user.name; // ✗ TypeScript error: Object is possibly 'null'
    // TypeScript re-widens because: 'user' could be reassigned between
    // the null check and when the callback fires (it's mutable)
  }, 1000);

  // Fix 1: Capture in a const before the callback:
  const u = user; // const — cannot be reassigned
  setTimeout(() => {
    u.name; // ✓ — u is const, TypeScript keeps it as User
  }, 1000);

  // Fix 2: Or use a closure that captures the already-narrowed type:
  // The function parameter approach works too:
  scheduleUserEmail(user); // user: User passed as argument — narrows at the call site
}

function scheduleUserEmail(user: User): void { // parameter is typed User, not User | null
  setTimeout(() => {
    user.name; // ✓ — parameter type is User, not narrowed from outer scope
  }, 1000);
}

// ═══ LOOP NARROWING ══════════════════════════════════════════════════════

function processItems(items: (string | number)[]): string[] {
  const results: string[] = [];

  for (const item of items) {
    // item: string | number

    if (typeof item === 'number') {
      results.push(item.toFixed(2)); // item: number ✓
      continue; // ← TypeScript knows string is handled in the else
    }

    // item: string (number was continued above) ✓
    results.push(item.toUpperCase());
  }

  return results;
}
```

## Implementation 6 — Real-World: NestJS Route Config with `as const satisfies`

### Challenge
Build a type-safe route configuration system for a NestJS application using `as const satisfies` — validate routes against a schema at compile time while preserving literal types for route matching and code generation.

### Implementation

```typescript
// ═══ TYPE DEFINITIONS ════════════════════════════════════════════════════

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
type AuthStrategy = 'public' | 'jwt' | 'api-key' | 'admin-only';

interface RouteDefinition {
  path:        string;
  method:      HttpMethod;
  auth:        AuthStrategy;
  rateLimit?:  number; // requests per minute (undefined = unlimited)
  version?:    `v${number}`; // v1, v2, etc.
  deprecated?: boolean;
}

// ═══ ROUTE CONFIGURATION WITH AS CONST SATISFIES ══════════════════════════

const API_ROUTES = [
  // Users
  { path: '/users',          method: 'GET',    auth: 'jwt',        rateLimit: 100 },
  { path: '/users',          method: 'POST',   auth: 'jwt',        rateLimit: 10  },
  { path: '/users/:id',      method: 'GET',    auth: 'jwt'                         },
  { path: '/users/:id',      method: 'PATCH',  auth: 'jwt',        rateLimit: 20  },
  { path: '/users/:id',      method: 'DELETE', auth: 'admin-only'                  },

  // Auth
  { path: '/auth/login',     method: 'POST',   auth: 'public',     rateLimit: 5   },
  { path: '/auth/refresh',   method: 'POST',   auth: 'jwt',        rateLimit: 30  },
  { path: '/auth/logout',    method: 'POST',   auth: 'jwt'                         },

  // Loans (Aditya's domain)
  { path: '/loans',          method: 'GET',    auth: 'jwt',        rateLimit: 50  },
  { path: '/loans',          method: 'POST',   auth: 'jwt',        rateLimit: 5   },
  { path: '/loans/:id',      method: 'GET',    auth: 'jwt'                         },
  { path: '/loans/:id/disbursement', method: 'POST', auth: 'admin-only', rateLimit: 1 },
] as const satisfies RouteDefinition[];

// WHAT WE GET:
// 1. Compile-time validation — typo in method/auth → immediate error ✓
// 2. Literal types preserved — each route's types are specific literals ✓
// 3. Readonly — array and nested objects cannot be mutated ✓

// ═══ DERIVED TYPES FROM THE CONFIG ════════════════════════════════════════

// Extract union of all paths:
type AppRoute = typeof API_ROUTES[number];
type AppPath = AppRoute['path'];
// "/users" | "/users/:id" | "/auth/login" | "/auth/refresh" | ... (all literal paths)

// Extract routes by auth strategy:
type PublicRoute = Extract<AppRoute, { auth: 'public' }>;
// { path: '/auth/login'; method: 'POST'; auth: 'public'; rateLimit: 5 }

type AdminRoute = Extract<AppRoute, { auth: 'admin-only' }>;
// { path: '/users/:id'; method: 'DELETE'; ... } | { path: '/loans/:id/disbursement'; ... }

// ═══ TYPE-SAFE ROUTE LOOKUP ═══════════════════════════════════════════════

// Find a route by path and method — returns the specific route type or undefined:
type FindRoute<P extends string, M extends HttpMethod> = Extract<
  AppRoute,
  { path: P; method: M }
>;

type GetUsers = FindRoute<'/users', 'GET'>;
// { readonly path: "/users"; readonly method: "GET"; readonly auth: "jwt"; readonly rateLimit: 100 }

// Function to get route config — fully typed:
function getRouteConfig<P extends AppPath, M extends HttpMethod>(
  path: P,
  method: M
): FindRoute<P, M> | undefined {
  return API_ROUTES.find(
    (r): r is FindRoute<P, M> => r.path === path && r.method === method
  );
}

const config = getRouteConfig('/auth/login', 'POST');
// config: FindRoute<'/auth/login', 'POST'> | undefined
// config?.auth: 'public' — literal type! ✓
// config?.rateLimit: 5 — literal type! ✓

// ═══ GENERATING OPENAPI PATHS FROM CONFIG ══════════════════════════════════

function buildSwaggerPaths(): Record<string, object> {
  const paths: Record<string, Record<string, object>> = {};

  for (const route of API_ROUTES) {
    // route is narrowed to each specific readonly tuple element as we iterate
    const swaggerPath = route.path.replace(/:(\w+)/g, '{$1}');
    const method = route.method.toLowerCase();

    if (!paths[swaggerPath]) paths[swaggerPath] = {};
    paths[swaggerPath][method] = {
      security: route.auth === 'public' ? [] : [{ bearerAuth: [] }],
      'x-rate-limit': 'rateLimit' in route ? route.rateLimit : 'unlimited',
      deprecated: 'deprecated' in route ? route.deprecated : false,
    };
  }

  return paths;
}

// ═══ MIDDLEWARE GENERATOR USING ROUTE CONFIG ══════════════════════════════

// TypeScript ensures only valid paths/methods can be passed:
function attachMiddleware<P extends AppPath, M extends HttpMethod>(
  path: P, method: M,
  middleware: (req: Request, res: Response, next: Function) => void
): void {
  const route = getRouteConfig(path, method);
  if (!route) throw new Error(`Route ${method} ${path} not found in API_ROUTES`);
  // route.auth: literal type — enables compile-time-checked conditional:
  if (route.auth === 'public') {
    app.use(path, middleware); // no auth middleware
  } else {
    app.use(path, authMiddleware(route.auth), middleware);
  }
}
```

## Quick Reference — Inference & Narrowing Decision Tree

```
TYPE INFERENCE DECISIONS:
│
├── SHOULD I ANNOTATE OR INFER?
│   ├── Function parameters → ANNOTATE (TypeScript cannot infer)
│   ├── Public API return types → ANNOTATE (contract, not description)
│   ├── Recursive function return → ANNOTATE (inference fails)
│   └── Everything else → INFER (less noise, same safety)
│
├── LET vs CONST INFERENCE BEHAVIOR:
│   ├── const primitive → literal type ("hello", 42, true)
│   ├── let primitive → widened base type (string, number, boolean)
│   ├── const object → properties widened (even with const)
│   └── const x = { ... } as const → all properties readonly + literal ✓
│
└── AS CONST vs SATISFIES vs ANNOTATION:
    ├── Need shape validation only → : Type annotation
    ├── Need literal preservation only → as const
    ├── Need both → as const satisfies Type
    └── Need Zod/runtime validation → z.object({}).parse() + z.infer<>

TYPE NARROWING DECISIONS:
│
├── WHAT TYPE IS x?
│   ├── Primitive (string/number/boolean) → typeof x === '...'
│   ├── Null or undefined → x === null, x != null, x !== undefined
│   ├── Class instance (Date, Error) → instanceof
│   └── Interface/object shape → 'property' in x, or discriminant check
│
├── NARROWING A DISCRIMINATED UNION:
│   └── switch (x.discriminant) with assertUnreachable in default ✓
│
├── NARROWING unknown/any FROM EXTERNAL SOURCE:
│   ├── Simple: isUser(x): x is User — manual structural check
│   ├── Throw on failure: assertUser(x): asserts x is User
│   └── Production: UserSchema.parse(x) with Zod (validates + narrows)
│
├── NARROWING INSIDE CALLBACKS:
│   └── Capture in const before the callback (const u = user) ✓
│
└── EXHAUSTIVENESS CHECKING:
    └── Add default: return assertUnreachable(x) to every discriminated
        union switch. Adding a union member → compile error in handler. ✓
```

## Common Bugs Checklist

Before shipping TypeScript code, verify:

1. **`let` widens but you needed a literal type?** — `let status = 'pending'` gives `string`, not `'pending'`. Either use `const`, annotate `let status: 'pending' | 'active'`, or use `as const` on the value if it's in an object.

2. **Object properties widened even with `const`?** — `const x = { port: 3000 }` gives `{ port: number }`, not `{ port: 3000 }`. The `const` prevents reassigning `x`, not reassigning `x.port`. Use `as const` to get `readonly port: 3000`.

3. **Type guard predicate doesn't match the runtime check?** — `function isUser(x: any): x is User { return !!x; }` TypeScript trusts the `is` predicate completely. A too-permissive check causes runtime crashes with TypeScript's blessing. Always check every property the interface requires, or use Zod's `safeParse`.

4. **Forgotten case in a discriminated union switch?** — Without `assertUnreachable` in the `default` branch, adding a new union member silently creates an unhandled path. Always add `default: return assertUnreachable(x)` to every exhaustive switch.

5. **`instanceof` used for an interface (not a class)?** — TypeScript interfaces have no runtime representation. `x instanceof User` doesn't compile if `User` is an interface. Use `'id' in x` or a type guard for interface narrowing.

6. **`typeof null === 'object'` — the historical JavaScript bug?** — `typeof x === 'object'` does NOT narrow out `null`. You must additionally check `x !== null`. The full pattern: `typeof x === 'object' && x !== null`.

7. **Narrowing lost in a callback?** — After `if (user !== null)`, inside a setTimeout/Promise/forEach callback, TypeScript re-widens `user` to `User | null` because it can't guarantee the variable hasn't been reassigned. Capture in `const u = user` before the callback.

8. **`as const` applied to a variable, not an expression?** — `const arr = [val] as const` — if `val` is a mutable `let` with type `string`, `arr` becomes `readonly [string]`, not `readonly ["hello"]`. `as const` operates on the expression's current type, not its original literal. Put `as const` on the full literal: `const arr = ['hello'] as const`.

9. **`satisfies` without `as const` still widens string/number properties?** — `{ port: 3000 } satisfies Config` — `port` is `number` because object property inference widens numbers. Add `as const` to preserve `3000`: `{ port: 3000 } as const satisfies Config`.

10. **`infer` used outside a conditional type?** — `infer R` is only valid in the `extends` clause of a conditional type (`T extends ... infer R ? ... : ...`). Using it elsewhere is a syntax error. If you want to "extract" a type outside a conditional, use `typeof`, `keyof`, or indexed access (`T['property']`).

11. **Assertion function not declared with explicit return type `asserts ...`?** — TypeScript requires the `asserts` keyword in the return type annotation for the narrowing to work. `function assertUser(x: unknown) { if (!isUser(x)) throw new Error(); }` — without `asserts x is User`, the call to this function does NOT narrow the type of `x` in subsequent code.

12. **`Array.filter` with a type guard predicate does not narrow the return type?** — `arr.filter(x => x !== null)` returns `(T | null)[]`, not `T[]`. The filter callback must be a proper type guard: `arr.filter((x): x is T => x !== null)` or `arr.filter(isNonNullable)` where `isNonNullable` has a type predicate signature.

---

**Final Tip:** At the 5 YOE level, the decisive signal for inference and narrowing is articulating **the mechanism, not just the syntax**. For widening: *"`let x = 'hello'` gives `string`, not `"hello"`, because TypeScript widens literal types on mutable bindings — reassigning `x = 'world'` must be valid. I use `as const` to suppress widening when I need literal types preserved, and `satisfies` when I also need shape validation against a known type."* For narrowing: *"TypeScript builds a type graph through each function — at each node, the type of each variable is the intersection of all constraints the control flow has imposed. After `if (x === null) return`, the type of x in subsequent code has `null` removed because TypeScript knows that code path only runs when x was not null."* For discriminated unions: *"I add a `default: return assertUnreachable(x)` to every switch over a discriminated union. The parameter type at that point must be `never` — TypeScript can only prove this if every union member has a `case`. Adding a new member changes the default's type from `never` to the new member, causing a compile error — a mechanical reminder that the handler is incomplete."*
