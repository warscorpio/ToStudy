# Type Guards: `typeof`, `instanceof`, Custom Type Guards with `is` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is type narrowing and why does TypeScript need type guards at all?**
A: TypeScript's type system is static — it assigns types at compile time. But real programs deal with values whose specific type isn't known until runtime: a value from `JSON.parse()` is `unknown`; a function parameter typed as `string | number | null` can be any of those; a discriminated union member depends on which variant is present. Without a mechanism to refine these broad types to specific ones, you can't access type-specific members without a compile error.

Type narrowing is TypeScript's process of refining a type within a specific code branch, based on runtime checks. Type guards are the checks that trigger narrowing:

```typescript
function processInput(value: string | number) {
    value.toUpperCase();    // Error: 'toUpperCase' doesn't exist on 'string | number'
    value.toFixed(2);       // Error: 'toFixed' doesn't exist on 'string | number'

    if (typeof value === 'string') {
        value.toUpperCase();  // OK: narrowed to string in this branch
    } else {
        value.toFixed(2);     // OK: narrowed to number in this branch
    }
}
```

TypeScript's control flow analysis tracks narrowing through `if/else`, ternaries, `switch` statements, early returns, throw statements, and logical operators — the type of a variable can be different at different points in the same function.

**Q2. What is the complete set of narrowing mechanisms TypeScript supports, and how do they relate to each other?**
A: TypeScript narrows types through eight distinct mechanisms:

1. **`typeof` checks**: narrows primitives (`string`, `number`, `boolean`, `bigint`, `symbol`, `undefined`, `function`)
2. **`instanceof` checks**: narrows class instances against constructor functions
3. **`in` operator**: narrows to types that have a specific property
4. **Equality checks** (`===`, `!==`, `==`, `!=`): narrows against literal values and `null`/`undefined`
5. **Truthiness checks**: narrows away `null`, `undefined`, `0`, `""`, `false`
6. **Discriminated union narrowing**: narrows via a shared literal-type discriminant property
7. **Custom type guards** (`is` predicates): user-defined functions that teach TypeScript how to narrow an arbitrary type
8. **Assertion functions** (`asserts`): functions that throw if a condition fails, narrowing the surviving path

All of these are detected by TypeScript's control flow analysis — the compiler traces the possible types through each branch of your code and applies the narrowing effect of each guard.

## Section 2: `typeof` Type Guards

**Q3. How does `typeof` narrowing work and what are its exact values?**
A: `typeof` is a JavaScript operator that returns a string describing the runtime type of a value. TypeScript's control flow analysis treats `typeof` checks as narrowing guards, refining the type in the `true` branch:

```typescript
// The full set of typeof results:
typeof undefined === 'undefined'   // narrows to undefined
typeof null === 'object'           // DOES NOT narrow to null! (JavaScript bug)
typeof true === 'boolean'          // narrows to boolean
typeof 42 === 'number'             // narrows to number
typeof 'hello' === 'string'        // narrows to string
typeof 9007199254740991n === 'bigint' // narrows to bigint
typeof Symbol() === 'symbol'       // narrows to symbol
typeof function(){} === 'function' // narrows to function (callable)
typeof {} === 'object'             // narrows to object (arrays, objects — NOT null)

// TypeScript narrowing in action:
function stringify(value: string | number | boolean | null | undefined): string {
    if (typeof value === 'string') {
        return value;                 // value: string
    }
    if (typeof value === 'number') {
        return value.toFixed(2);     // value: number
    }
    if (typeof value === 'boolean') {
        return value ? 'yes' : 'no'; // value: boolean
    }
    if (value === null) {
        return 'null';               // Need === null for null (typeof null === 'object')
    }
    return 'undefined';              // value: undefined (only option left)
}

// Narrowing in the else branch:
function processName(name: string | undefined) {
    if (typeof name === 'undefined') {
        return 'Anonymous';    // name: undefined
    }
    return name.toUpperCase(); // name: string (narrowed in else)
}
```

**Q4. What are the limitations of `typeof` and what can it NOT narrow?**
A: `typeof` is limited to JavaScript's primitive type tags — it cannot distinguish between different object types, between arrays and plain objects, or between class instances:

```typescript
// typeof cannot distinguish objects:
typeof [] === 'object'         // true — arrays
typeof {} === 'object'         // true — plain objects
typeof new Date() === 'object' // true — Date instances
typeof null === 'object'       // true — THE FAMOUS BUG

// Cannot narrow:
function process(value: string[] | string) {
    if (typeof value === 'object') {
        value;  // Still string[] | string... wait, string has typeof 'string'
        // Actually this works because string's typeof is 'string', not 'object'
        // But: string[] vs Map vs Set — all have typeof 'object'
    }
}

// typeof cannot distinguish class instances:
class Dog { bark() {} }
class Cat { meow() {} }

function makeNoise(animal: Dog | Cat) {
    if (typeof animal === 'object') {
        // animal: Dog | Cat — no help! Both are objects
    }
}
// Use instanceof instead for class instances

// typeof and null — the notorious case:
function process(value: string | null) {
    if (typeof value === 'object') {
        // value: null — because typeof null === 'object'!
        // But TypeScript IS smart enough to know that 'string | null'
        // with typeof === 'object' must be null
        value;  // value: null (TypeScript narrows correctly here)
    }
    if (typeof value === 'string') {
        value;  // value: string
    }
}
```

## Section 3: `instanceof` Type Guards

**Q5. How does `instanceof` narrowing work and what are its exact semantics?**
A: `instanceof` checks whether a value's prototype chain includes the constructor's `.prototype` property. TypeScript uses this as a narrowing guard for class instances:

```typescript
class NetworkError extends Error {
    constructor(
        message: string,
        public statusCode: number,
        public endpoint: string
    ) {
        super(message);
        this.name = 'NetworkError';
    }
}

class ValidationError extends Error {
    constructor(
        message: string,
        public field: string,
        public constraint: string
    ) {
        super(message);
        this.name = 'ValidationError';
    }
}

function handleError(error: Error) {
    if (error instanceof NetworkError) {
        // error: NetworkError — can access .statusCode, .endpoint
        console.log(`HTTP ${error.statusCode} from ${error.endpoint}: ${error.message}`);
        if (error.statusCode >= 500) {
            alertOpsTeam(error);
        }
    } else if (error instanceof ValidationError) {
        // error: ValidationError — can access .field, .constraint
        return { field: error.field, message: `Invalid ${error.field}: ${error.constraint}` };
    } else {
        // error: Error — neither subclass, just base Error
        console.error('Unexpected error:', error.message);
    }
}
```

**Q6. What are the limitations of `instanceof` and when does it fail?**
A: `instanceof` has three significant failure modes:

```typescript
// Limitation 1: Cross-realm failures
// Objects created in different JavaScript environments (iframes, vm contexts,
// Node.js worker_threads, different bundler chunks) have different constructors
const iframe = document.createElement('iframe');
document.body.appendChild(iframe);
const IframeArray = iframe.contentWindow!.Array;
const arr = new IframeArray();
arr instanceof Array;        // false! Different Array constructor
Array.isArray(arr);          // true  — works cross-realm (checks internal tag)

// Limitation 2: Only works with class constructors, not interfaces or type aliases
interface Serializable { serialize(): string; }
// Cannot write: value instanceof Serializable — interfaces don't exist at runtime

// Limitation 3: Prototype chain manipulation
class Animal { breathe() {} }
class Dog extends Animal { bark() {} }
const rex = new Dog();

rex instanceof Dog;    // true
rex instanceof Animal; // true — walks the chain

Object.setPrototypeOf(rex, null);   // Corrupt the chain
rex instanceof Dog;    // false now — chain broken

// Limitation 4: Object.create edge cases
const dogLike = Object.create(Dog.prototype);
dogLike instanceof Dog;  // true — prototype matches, but no constructor ran

// Limitation 5: Symbol.hasInstance override
class Even {
    static [Symbol.hasInstance](value: unknown): value is number {
        return typeof value === 'number' && value % 2 === 0;
    }
}
4 instanceof Even;   // true — not a real Even instance, but symbol overrides check
5 instanceof Even;   // false
```

**Q7. When should you use `instanceof` vs `typeof` vs a custom type guard?**
A: A decision framework:

```typescript
// Use typeof when: checking JavaScript primitive types (string, number, boolean, etc.)
function isString(value: unknown): value is string {
    return typeof value === 'string';
}

// Use instanceof when: narrowing class instances you know were constructed with new
function handleError(err: unknown) {
    if (err instanceof Error) { ... }  // Works: Error is a class
}

// Use Array.isArray when: checking for arrays (typeof [] === 'object' doesn't help)
function processArray(value: string | string[]) {
    if (Array.isArray(value)) {
        value;  // string[] — TypeScript knows
    }
}

// Use in when: checking for presence of a property to distinguish object shapes
function move(animal: Fish | Bird) {
    if ('swim' in animal) {
        animal.swim();  // Fish
    } else {
        animal.fly();   // Bird
    }
}

// Use custom type guard (is) when:
// 1. Checking plain objects/interfaces (no class, can't use instanceof)
// 2. Validating external data (API responses, JSON.parse output)
// 3. Combining multiple checks into a reusable, named guard
// 4. instanceof fails (cross-realm, interface narrowing needed)
function isApiResponse(value: unknown): value is ApiResponse {
    return typeof value === 'object' && value !== null &&
           'data' in value && 'status' in value;
}
```

## Section 4: The `in` Operator and Discriminated Unions

**Q8. How does the `in` operator narrow types?**
A: The `in` operator checks whether a property exists on an object and its prototype chain. TypeScript uses it as a narrowing guard — after `'property' in obj`, TypeScript knows `obj` has that property:

```typescript
interface Fish { swim(): void; bubbles: number; }
interface Bird { fly(): void; wingspan: number; }
interface Mammal { breathe(): void; heartRate: number; }

function getMovement(animal: Fish | Bird | Mammal): string {
    if ('swim' in animal) {
        // animal: Fish — only Fish has 'swim'
        return `Swimming with ${animal.bubbles} bubbles`;
    }
    if ('fly' in animal) {
        // animal: Bird — only Bird has 'fly'
        return `Flying with ${animal.wingspan}cm wingspan`;
    }
    // animal: Mammal — must have 'breathe'
    return `Walking at ${animal.heartRate}bpm`;
}

// in narrowing with optional properties — caution needed:
interface A { x: string; y?: number; }
interface B { x: number; z?: string; }

function process(value: A | B) {
    if ('y' in value) {
        // value: A — y is defined in A (even though optional)
        // TypeScript includes A here because 'y' could exist on A
        // BUT 'y' is optional — this only proves y EXISTS now, not that it's defined
        value.y;  // number | undefined — still optional within the narrowed type
    }
}

// The in operator and null/undefined:
function hasProperty<T extends object>(obj: T, key: string): boolean {
    return key in obj;  // Can't use 'in' on primitives — must check obj is object first
}
```

**Q9. What are discriminated unions and how do they enable exhaustiveness checking?**
A: A discriminated union is a union type where every member has a literal-type property with the same name but different values — the "discriminant." TypeScript narrows based on this property:

```typescript
// Each member has 'kind' as the discriminant:
type Shape =
    | { kind: 'circle'; radius: number }
    | { kind: 'rectangle'; width: number; height: number }
    | { kind: 'triangle'; base: number; height: number };

function area(shape: Shape): number {
    switch (shape.kind) {
        case 'circle':
            // shape: { kind: 'circle'; radius: number }
            return Math.PI * shape.radius ** 2;
        case 'rectangle':
            // shape: { kind: 'rectangle'; width: number; height: number }
            return shape.width * shape.height;
        case 'triangle':
            // shape: { kind: 'triangle'; base: number; height: number }
            return 0.5 * shape.base * shape.height;
        // TypeScript: all cases handled — no default needed
    }
}

// Exhaustiveness checking with never:
function assertNever(value: never): never {
    throw new Error(`Unhandled case: ${JSON.stringify(value)}`);
}

function describe(shape: Shape): string {
    switch (shape.kind) {
        case 'circle':    return `Circle with radius ${shape.radius}`;
        case 'rectangle': return `Rectangle ${shape.width}x${shape.height}`;
        // FORGOT 'triangle'!
        default:
            // shape is now 'triangle' variant — error! { kind: 'triangle'; ... } is not 'never'
            return assertNever(shape);
            // Error: Argument of type '{ kind: "triangle"; base: number; height: number; }'
            //        is not assignable to parameter of type 'never'
    }
}
// This compile error tells you: you added a new Shape variant but forgot to handle it
// Adding type Shape = ... | { kind: 'polygon'; sides: number } forces a compiler error
// until you add the 'polygon' case everywhere assertNever is used
```

## Section 5: Custom Type Guards with `is`

**Q10. What is a user-defined type guard and what does the `is` keyword do?**
A: A user-defined type guard is a function whose return type is a "type predicate" — `parameterName is Type`. When this function returns `true`, TypeScript narrows the parameter to that type in the calling scope. The `is` keyword is what makes a function a type guard rather than just a boolean-returning function:

```typescript
// Regular boolean function — TypeScript learns nothing from calling this:
function checkString(value: unknown): boolean {
    return typeof value === 'string';
}

function process(value: unknown) {
    if (checkString(value)) {
        value.toUpperCase();  // Error! TypeScript still sees value as unknown
        // TypeScript doesn't know what checkString returning true means for types
    }
}

// User-defined type guard — TypeScript narrows based on the return:
function isString(value: unknown): value is string {
    return typeof value === 'string';
}

function process(value: unknown) {
    if (isString(value)) {
        value.toUpperCase();  // OK! Narrowed to string in this branch
    }
    // value is still unknown here
}

// The mechanics: `parameterName is Type` is a type predicate
// - parameterName: must be one of the function's parameters
// - Type: any valid TypeScript type
// When the function returns true: TypeScript narrows parameterName to Type
// When the function returns false: TypeScript knows parameterName is NOT Type

function isNotNull<T>(value: T | null): value is T {
    return value !== null;
}

const items: (string | null)[] = ['a', null, 'b', null, 'c'];
const nonNull: string[] = items.filter(isNotNull);  // Works! filter infers string[]
// Without the predicate, items.filter(x => x !== null) returns (string | null)[]
```

**Q11. How do you implement type guards for complex object types (interfaces, not classes)?**
A: Custom type guards shine when `instanceof` won't work — for plain objects satisfying interfaces, for API responses, or for runtime validation of external data:

```typescript
// Basic interface type guard:
interface User {
    id: string;
    name: string;
    email: string;
    role: 'admin' | 'user' | 'guest';
}

function isUser(value: unknown): value is User {
    if (typeof value !== 'object' || value === null) return false;
    const obj = value as Record<string, unknown>;

    return (
        typeof obj.id === 'string' &&
        typeof obj.name === 'string' &&
        typeof obj.email === 'string' &&
        (obj.role === 'admin' || obj.role === 'user' || obj.role === 'guest')
    );
}

// Usage with unknown data (API responses, JSON.parse):
async function fetchUser(id: string): Promise<User> {
    const response = await fetch(`/api/users/${id}`);
    const data: unknown = await response.json();

    if (!isUser(data)) {
        throw new Error(`Invalid user data received: ${JSON.stringify(data)}`);
    }
    return data;  // data: User — narrowed by the type guard
}

// Nested object type guard:
interface Address {
    street: string;
    city: string;
    country: string;
}

interface UserWithAddress extends User {
    address: Address;
}

function isAddress(value: unknown): value is Address {
    if (typeof value !== 'object' || value === null) return false;
    const obj = value as Record<string, unknown>;
    return typeof obj.street === 'string' &&
           typeof obj.city === 'string' &&
           typeof obj.country === 'string';
}

function isUserWithAddress(value: unknown): value is UserWithAddress {
    return isUser(value) && isAddress((value as any).address);
}
```

**Q12. How do you use type guards with generic types?**
A: Generic type guards can narrow to parameterized types, though the implementation must use the right approach depending on what T is:

```typescript
// Generic type guard for arrays:
function isArrayOf<T>(
    value: unknown,
    elementGuard: (el: unknown) => el is T
): value is T[] {
    return Array.isArray(value) && value.every(elementGuard);
}

const data: unknown = ['alice', 'bob', 'carol'];
if (isArrayOf(data, isString)) {
    data;  // string[] — fully narrowed
    data.map(s => s.toUpperCase());  // Works!
}

// Generic type guard for Record types:
function isRecord(value: unknown): value is Record<string, unknown> {
    return typeof value === 'object' && value !== null && !Array.isArray(value);
}

// Combining for nested validation:
function isRecordOf<V>(
    value: unknown,
    valueGuard: (v: unknown) => v is V
): value is Record<string, V> {
    if (!isRecord(value)) return false;
    return Object.values(value).every(valueGuard);
}

const scores: unknown = { alice: 95, bob: 87, carol: 92 };
if (isRecordOf(scores, isNumber)) {
    scores;  // Record<string, number>
    const total = Object.values(scores).reduce((sum, n) => sum + n, 0);
}

// The limitation: T cannot be checked directly at runtime (type erasure)
function isT<T>(value: unknown): value is T {
    // WRONG: Cannot check what T is at runtime — generics are erased
    // The only option is to pass a guard function (as above)
}

// Correct pattern: pass a runtime check function for T
function parseAs<T>(
    data: unknown,
    guard: (v: unknown) => v is T
): T {
    if (!guard(data)) throw new Error(`Data does not match expected type`);
    return data;
}
const user = parseAs(apiData, isUser);  // user: User, throws if invalid
```

**Q13. What is the danger of incorrect type guard implementations and how do you detect them?**
A: TypeScript trusts your type guard implementation — if your implementation is wrong, the narrowing is wrong, and you get a runtime error that TypeScript's type checker missed:

```typescript
// DANGEROUS: type guard that lies to TypeScript
function isCat(animal: unknown): animal is Cat {
    // WRONG: just checks if it's an object, not specifically a Cat
    return typeof animal === 'object' && animal !== null;
    // This will "narrow" Dog objects to Cat type — silent runtime error
}

function makeSound(animal: unknown) {
    if (isCat(animal)) {
        animal.meow();  // TypeScript says OK, but animal might be a Dog!
        // Runtime: TypeError: animal.meow is not a function
    }
}

// CORRECT: guard must check all distinguishing properties
interface Cat { meow(): void; purrs: boolean; }
interface Dog { bark(): void; fetchesSticks: boolean; }

function isCat(animal: unknown): animal is Cat {
    return typeof animal === 'object' &&
           animal !== null &&
           'meow' in animal && typeof (animal as any).meow === 'function' &&
           'purrs' in animal && typeof (animal as any).purrs === 'boolean';
}

// Detection strategies:
// 1. Unit test your type guards with invalid inputs:
describe('isCat', () => {
    it('returns false for non-cats', () => {
        expect(isCat(null)).toBe(false);
        expect(isCat({ bark: () => {}, fetchesSticks: true })).toBe(false);
        expect(isCat('meow')).toBe(false);
    });
    it('returns true for cats', () => {
        expect(isCat({ meow: () => {}, purrs: true })).toBe(true);
    });
});

// 2. Consider using runtime validation libraries that generate type guards:
// zod, io-ts, valibot — they generate both TypeScript types AND runtime validators,
// eliminating the possibility of them diverging:
import { z } from 'zod';
const CatSchema = z.object({
    meow: z.function(),
    purrs: z.boolean()
});
type Cat = z.infer<typeof CatSchema>;  // TypeScript type derived from the schema

function isCat(value: unknown): value is Cat {
    return CatSchema.safeParse(value).success;
}
// Now the type guard is derived from the same schema as the TypeScript type
// — they can never diverge
```

## Section 6: Assertion Functions

**Q14. What are assertion functions (`asserts`) and how do they differ from type predicates (`is`)?**
A: Assertion functions use the `asserts` keyword in their return type to declare "if this function returns (doesn't throw), the condition holds." They narrow the type for all code after the assertion call, unlike `is` predicates which only narrow inside `if` blocks:

```typescript
// Type predicate (is): narrows inside if block only
function isString(value: unknown): value is string {
    return typeof value === 'string';
}

// Assertion function (asserts): narrows for ALL code after the call
function assertString(value: unknown): asserts value is string {
    if (typeof value !== 'string') {
        throw new TypeError(`Expected string, got ${typeof value}`);
    }
    // If we reach here, value is string — TypeScript narrows it for the caller
}

// Comparing the two:
function process(value: unknown) {
    // Using type predicate:
    if (isString(value)) {
        value.toUpperCase();  // OK inside the if
    }
    value.toUpperCase();      // Error: still unknown outside

    // Using assertion function:
    assertString(value);      // Throws if not string
    value.toUpperCase();      // OK everywhere after — TypeScript knows it's string
    value.length;             // Also OK — narrowed for the rest of the function
}

// Asserting truthiness / existence:
function assert(condition: boolean, message?: string): asserts condition {
    if (!condition) throw new Error(message ?? 'Assertion failed');
}

function assertNonNull<T>(value: T | null | undefined, name: string): asserts value is NonNullable<T> {
    if (value === null || value === undefined) {
        throw new Error(`${name} must not be null or undefined`);
    }
}

function processUser(userId: string | null) {
    assertNonNull(userId, 'userId');
    userId.toUpperCase();  // OK — narrowed to string after assertion
}

// Node.js's built-in assert:
import assert from 'node:assert';
function processNumber(value: unknown) {
    assert(typeof value === 'number');
    value.toFixed(2);  // OK — TypeScript recognizes Node's assert as an assertion function
}
```

**Q15. What is `asserts condition` (without `is`) and when is it used?**
A: `asserts condition` (where `condition` is a boolean parameter) narrows all values that the condition checks, rather than a specific variable:

```typescript
// asserts condition — narrows based on the truthiness of the condition parameter
function invariant(condition: boolean, message: string): asserts condition {
    if (!condition) throw new Error(`Invariant violated: ${message}`);
}

function processData(value: string | number | null) {
    invariant(typeof value === 'string', 'value must be string');
    // After this line: TypeScript knows typeof value === 'string' holds
    value.toUpperCase();  // OK — TypeScript narrowed based on the condition

    // More complex conditions:
    invariant(value.length > 0, 'value must not be empty');
    // After: value is string (already narrowed) AND length > 0 holds
}

// Common pattern in testing and application code:
function processConfig(config: unknown) {
    invariant(
        typeof config === 'object' && config !== null,
        'config must be an object'
    );
    // After: TypeScript knows config is a non-null object
    invariant(
        'apiKey' in config,
        'config must have apiKey'
    );
    // After: config has apiKey property
    const key = (config as any).apiKey;
    invariant(typeof key === 'string', 'apiKey must be a string');
    key.startsWith('sk-');  // OK — key is string
}
```

## Section 7: Control Flow Analysis

**Q16. How does TypeScript's control flow analysis track type narrowing through complex code paths?**
A: TypeScript's control flow analysis (CFA) tracks the possible types of every variable at every point in the code, based on the control flow graph. It handles early returns, throws, assignments, and logical operators:

```typescript
function demonstrateCFA(value: string | number | null) {
    // Point A: value is string | number | null

    if (value === null) return 'null';
    // Point B: value is string | number (null eliminated by early return)

    if (typeof value === 'string') {
        // Point C: value is string
        if (value.length === 0) throw new Error('empty string');
        // Point D (after throw): value is string AND length > 0 (but CFA doesn't know length)
        return value.toUpperCase();  // OK
    }
    // Point E: value is number (string branch returned)

    return value.toFixed(2);  // OK — value: number
}

// Narrowing through assignment:
function assignmentNarrowing() {
    let value: string | number = getRandomValue();
    // value: string | number

    if (typeof value === 'string') {
        // value: string
    }

    value = 42;
    // value: number (assignment narrows to the assigned type's literal type then widens)
    // Actually: value: 42 | number → number

    value.toFixed();  // OK — TypeScript knows value is number after assignment
}

// Narrowing through logical operators:
function logicalNarrowing(value: string | null, other: number | undefined) {
    const result = value && value.toUpperCase();
    // value && ... — left side must be truthy (not null, not empty string)
    // value.toUpperCase() is safe because && short-circuits on falsy left side

    const fallback = other ?? 0;
    // fallback: number — ?? narrows away null/undefined from left side

    const sure = other!;
    // Non-null assertion (!) — tells TypeScript: trust me, this is not null/undefined
    // TypeScript narrows but YOU are responsible — if other IS undefined, runtime error
}

// Narrowing with closures — a subtle limitation:
function closureLimitation(value: string | null) {
    if (value !== null) {
        // value: string here

        const later = () => {
            value;  // value: string | null (reverted to outer union!)
            // CFA can't guarantee value is still string when `later` runs
            // because something could have re-assigned value between now and then
        };

        value;  // value: string (safe here — CFA knows we're in the narrowed scope)
    }
}
```

**Q17. What is the "truthiness" narrowing and what types does it affect?**
A: TypeScript narrows based on the truthy/falsy value of an expression. The falsy values in JavaScript that TypeScript recognizes for narrowing: `false`, `0`, `""`, `null`, `undefined`, `NaN`, `0n`:

```typescript
function truthinessNarrowing(value: string | null | undefined) {
    if (value) {
        // value: string (null and undefined are falsy, narrows away)
        // CAREFUL: empty string "" is also falsy!
        // If empty string is a valid string value, this guard is wrong
        value.toUpperCase();  // OK
    }

    // Better for "exists and non-empty":
    if (value !== null && value !== undefined) {
        // value: string — strictly excludes only null and undefined
        value;  // Could be ""
    }

    if (value !== undefined && value !== null && value !== '') {
        value;  // string — guaranteed non-empty
    }
}

// The 0 falsy trap:
function countItems(count: number | null) {
    if (count) {
        // count: number (null removed by truthiness)
        // BUT: count could be 0! And 0 is falsy!
        // If the caller passes 0, this branch won't execute
        // "there are 0 items" would be incorrectly skipped
    }

    // Correct check:
    if (count !== null) {
        // count: number — includes 0
    }
}

// Truthiness with arrays:
function processArray(arr: string[] | null) {
    if (arr) {
        // arr: string[] (null narrowed away)
        // But empty array [] is truthy! So arr.length could be 0
        arr.forEach(item => item.toUpperCase());  // OK, even for empty array
    }

    if (arr?.length) {
        // arr: string[] AND length > 0 (both checks via optional chaining + truthiness)
    }
}
```

## Section 8: Advanced Narrowing Patterns

**Q18. How do you use type guards to narrow `unknown` and validate external data?**
A: `unknown` is the type-safe replacement for `any` — it forces you to narrow before using a value. Type guards are the mechanism for that narrowing:

```typescript
// The standard validation pattern for API data:
interface ApiResponse<T> {
    data: T;
    status: number;
    message: string;
}

function isApiResponse<T>(
    value: unknown,
    dataGuard: (data: unknown) => data is T
): value is ApiResponse<T> {
    if (typeof value !== 'object' || value === null) return false;
    const obj = value as Record<string, unknown>;
    return (
        typeof obj.status === 'number' &&
        typeof obj.message === 'string' &&
        'data' in obj &&
        dataGuard(obj.data)
    );
}

// Composing validation for complex nested types:
interface Product {
    id: string;
    name: string;
    price: number;
    inStock: boolean;
    tags: string[];
}

function isProduct(value: unknown): value is Product {
    if (typeof value !== 'object' || value === null) return false;
    const obj = value as Record<string, unknown>;
    return (
        typeof obj.id === 'string' &&
        typeof obj.name === 'string' &&
        typeof obj.price === 'number' &&
        typeof obj.inStock === 'boolean' &&
        Array.isArray(obj.tags) &&
        obj.tags.every((tag): tag is string => typeof tag === 'string')
        //       ↑ inline type guard as filter callback
    );
}

// Using in async contexts:
async function fetchProducts(): Promise<Product[]> {
    const response = await fetch('/api/products');
    const raw: unknown = await response.json();

    if (!Array.isArray(raw)) throw new Error('Expected array');
    if (!raw.every(isProduct)) throw new Error('Invalid product data');

    return raw;  // raw: Product[] — narrowed by .every(isProduct)
}
```

**Q19. What is the "never" type's role in exhaustiveness checking and how does it interact with type guards?**
A: `never` is TypeScript's bottom type — a value that can never exist. It appears as the result of narrowing a union to the point where no members remain. Exhaustiveness checking exploits this: if you handle all union members, the remaining type is `never`, and passing it to a function expecting `never` is a compile error if you missed a case:

```typescript
type Result<T, E extends Error = Error> =
    | { success: true; value: T }
    | { success: false; error: E };

function handleResult<T>(result: Result<T>): T {
    if (result.success === true) {
        return result.value;  // result: { success: true; value: T }
    }
    if (result.success === false) {
        throw result.error;   // result: { success: false; error: Error }
    }
    // result: never — both cases handled
    const _exhaustive: never = result;  // Would error if Result had more cases
    throw new Error('Impossible');
}

// More robust: dedicated helper
function assertNever(value: never, message = 'Unhandled case'): never {
    throw new Error(`${message}: ${JSON.stringify(value)}`);
}

// When you add a new event type:
type UserEvent =
    | { type: 'login'; userId: string }
    | { type: 'logout'; userId: string }
    | { type: 'purchase'; userId: string; amount: number };
    // Later you add: | { type: 'refund'; userId: string; amount: number };

function processEvent(event: UserEvent): void {
    switch (event.type) {
        case 'login':    logLogin(event.userId); break;
        case 'logout':   logLogout(event.userId); break;
        case 'purchase': recordPurchase(event.userId, event.amount); break;
        default:
            assertNever(event);
            // After adding 'refund' to UserEvent, this line gives:
            // Error: Argument of type '{ type: "refund"; ... }' is not assignable to type 'never'
            // Compile error forces you to add the 'refund' case!
    }
}
```

**Q20. How do type guards interact with array filtering and reduce operations?**
A: Type guards compose with array methods, enabling type-safe filtering and transformation:

```typescript
const mixed: (string | number | null | undefined)[] = ['a', 1, null, 'b', 2, undefined, 'c'];

// Array.filter with type guard — preserves the narrowed type:
const strings: string[] = mixed.filter((x): x is string => typeof x === 'string');
// Without the type predicate: filter returns (string | number | null | undefined)[]

const defined: (string | number)[] = mixed.filter(
    (x): x is string | number => x !== null && x !== undefined
);

// Pattern: filter out null and undefined (very common)
function isNonNull<T>(value: T | null | undefined): value is NonNullable<T> {
    return value !== null && value !== undefined;
}
const nonNullStrings = mixed.filter(isNonNull);  // (string | number)[]

// Type-narrowing with reduce:
const categorized = mixed.reduce<{ strings: string[]; numbers: number[] }>(
    (acc, item) => {
        if (typeof item === 'string') acc.strings.push(item);
        else if (typeof item === 'number') acc.numbers.push(item);
        return acc;
    },
    { strings: [], numbers: [] }
);

// Type guard arrays — an array where each element knows its type:
const guards = [isString, isNumber] as const;
type GuardedType<T extends (v: unknown) => v is any> =
    T extends (v: unknown) => v is infer U ? U : never;

// flatMap with type narrowing:
const apiResults: (User | null)[] = await Promise.all(ids.map(fetchUser));
const users: User[] = apiResults.flatMap(u => u ? [u] : []);
// flatMap with empty array effectively filters + flattens, TypeScript narrows correctly
```

## Section 9: Scenario-Based Questions

**Q21. "What does TypeScript infer for each marked line, and why?"**

```typescript
type Event =
    | { type: 'click'; x: number; y: number }
    | { type: 'keydown'; key: string; ctrlKey: boolean }
    | { type: 'resize'; width: number; height: number };

function handleEvent(event: Event) {
    if (event.type === 'click') {
        console.log(event);           // A
        console.log(event.x);         // B
    }

    if ('key' in event) {
        console.log(event);           // C
        console.log(event.ctrlKey);   // D
    }

    const { type, ...rest } = event;
    console.log(type);                // E
    console.log(rest);                // F

    if (event.type !== 'resize') {
        console.log(event);           // G
    }
}
```

A: Tracing each line:

- **A**: `{ type: 'click'; x: number; y: number }` — narrowed by `=== 'click'`
- **B**: `number` — safe access since event is narrowed to click variant
- **C**: `{ type: 'keydown'; key: string; ctrlKey: boolean }` — only the keydown variant has `'key'`, `in` narrows to it
- **D**: `boolean` — ctrlKey is on the narrowed keydown type
- **E**: `'click' | 'keydown' | 'resize'` — the union of all possible type discriminants
- **F**: `{ x: number; y: number } | { key: string; ctrlKey: boolean } | { width: number; height: number }` — the rest of each variant with `type` removed (TypeScript distributes the destructuring over the union)
- **G**: `{ type: 'click'; x: number; y: number } | { type: 'keydown'; key: string; ctrlKey: boolean }` — narrowed by `!== 'resize'` to the two remaining variants

**Q22. "Design a type-safe error handling system using custom type guards and discriminated unions."**
A: A production-grade error handling system:

```typescript
// Error hierarchy as discriminated union:
type AppError =
    | { kind: 'network'; status: number; url: string; retryable: boolean }
    | { kind: 'validation'; field: string; constraint: string; received: unknown }
    | { kind: 'auth'; reason: 'expired' | 'invalid' | 'missing'; redirectTo?: string }
    | { kind: 'business'; code: string; message: string; userFacing: boolean }
    | { kind: 'unexpected'; error: unknown; context: string };

// Type guards for each variant:
function isNetworkError(e: AppError): e is Extract<AppError, { kind: 'network' }> {
    return e.kind === 'network';
}
function isValidationError(e: AppError): e is Extract<AppError, { kind: 'validation' }> {
    return e.kind === 'validation';
}
function isAuthError(e: AppError): e is Extract<AppError, { kind: 'auth' }> {
    return e.kind === 'auth';
}

// Guard for unknown → AppError (validates external errors):
function isAppError(value: unknown): value is AppError {
    if (typeof value !== 'object' || value === null) return false;
    const obj = value as Record<string, unknown>;
    const validKinds = ['network', 'validation', 'auth', 'business', 'unexpected'];
    return typeof obj.kind === 'string' && validKinds.includes(obj.kind);
}

// Error handler using exhaustive discrimination:
function handleAppError(error: AppError): Response {
    switch (error.kind) {
        case 'network':
            if (error.retryable) scheduleRetry();
            return Response.json({ error: 'Network error' }, { status: error.status });
        case 'validation':
            return Response.json(
                { field: error.field, message: `Invalid ${error.constraint}` },
                { status: 400 }
            );
        case 'auth':
            if (error.redirectTo) {
                return Response.redirect(error.redirectTo, 302);
            }
            return Response.json({ error: 'Unauthorized' }, { status: 401 });
        case 'business':
            const status = error.userFacing ? 422 : 500;
            const body = error.userFacing ? { error: error.message } : { error: 'Internal error' };
            return Response.json(body, { status });
        case 'unexpected':
            logError(error.error, error.context);
            return Response.json({ error: 'Internal server error' }, { status: 500 });
        default:
            return assertNever(error);  // Compile error if new kind added without handling
    }
}

// Safe error boundary — catches unknown, narrows:
async function safeApiCall<T>(fn: () => Promise<T>): Promise<[T, null] | [null, AppError]> {
    try {
        const result = await fn();
        return [result, null];
    } catch (caught: unknown) {
        if (isAppError(caught)) {
            return [null, caught];
        }
        return [null, {
            kind: 'unexpected',
            error: caught,
            context: fn.toString()
        }];
    }
}
```

**Q23. "Implement a type-safe event system where subscribers know the exact payload type for each event."**
A: Combining discriminated unions with custom type guards for a fully typed event bus:

```typescript
// Event map: event name → payload type
interface EventPayloads {
    'user:created': { userId: string; email: string; timestamp: Date };
    'user:deleted': { userId: string; reason: string };
    'order:placed': { orderId: string; items: string[]; total: number };
    'payment:failed': { orderId: string; error: string; retryAt?: Date };
}

type EventName = keyof EventPayloads;

// Type guard for event names:
function isEventName(name: string): name is EventName {
    const validEvents: EventName[] = [
        'user:created', 'user:deleted', 'order:placed', 'payment:failed'
    ];
    return validEvents.includes(name as EventName);
}

// Typed event bus:
class TypedEventBus {
    private handlers = new Map<string, Set<(payload: unknown) => void>>();

    on<E extends EventName>(
        event: E,
        handler: (payload: EventPayloads[E]) => void
    ): () => void {
        if (!this.handlers.has(event)) {
            this.handlers.set(event, new Set());
        }
        this.handlers.get(event)!.add(handler as (payload: unknown) => void);
        return () => this.handlers.get(event)?.delete(handler as (payload: unknown) => void);
    }

    emit<E extends EventName>(event: E, payload: EventPayloads[E]): void {
        this.handlers.get(event)?.forEach(handler => handler(payload));
    }

    // Type-safe wildcard subscription with narrowing:
    onAny(handler: <E extends EventName>(event: E, payload: EventPayloads[E]) => void): void {
        // ...
    }
}

// Usage — fully type-safe:
const bus = new TypedEventBus();

bus.on('user:created', ({ userId, email, timestamp }) => {
    // userId: string, email: string, timestamp: Date — fully typed
    console.log(`New user ${userId} (${email}) at ${timestamp.toISOString()}`);
});

bus.emit('order:placed', {
    orderId: 'ord-123',
    items: ['item-1', 'item-2'],
    total: 99.99
});
// TypeScript catches typos in event names and payload shape mismatches
bus.emit('order:palced', { orderId: 'x', items: [], total: 0 });  // Error: typo in name
bus.emit('order:placed', { orderId: 'x' });  // Error: missing items and total
```

## Quick Reference Table

| Type Guard | Syntax | Narrows to | Limitations |
|---|---|---|---|
| `typeof` | `typeof x === 'string'` | Primitives: string, number, boolean, bigint, symbol, undefined, function | Can't distinguish objects; `typeof null === 'object'` |
| `instanceof` | `x instanceof ClassName` | Class instances | Cross-realm failures; only for classes, not interfaces |
| `in` | `'prop' in x` | Types that have the property | Optional props still include/exclude inconsistently |
| Equality | `x === null`, `x === 'literal'` | Specific literal values, null, undefined | Only literal and null/undefined checks |
| Truthiness | `if (x)` | Non-falsy subset | `0`, `""`, `false` are falsy — may exclude valid values |
| Type predicate | `fn(x): x is T` | Any type T | TypeScript trusts you — wrong impl = silent bug |
| `asserts` | `fn(x): asserts x is T` | Narrows after call (throws on failure) | Same trust issue as type predicates |
| Discriminated union | `x.kind === 'circle'` | The specific union member | Requires a shared literal discriminant property |
| `never` exhaustion | `assertNever(x)` | Compile error if cases missed | Only useful as the default/else case |

---

**Tip for interviews:** Five things separate strong candidates on type guards: (1) knowing that **`typeof null === 'object'`** (Q3) is a JavaScript bug — not being surprised by it, knowing that `typeof` doesn't narrow `null` to `null` (you need `=== null`), and knowing TypeScript is smart enough to handle this in `string | null` unions with a `typeof === 'object'` check; (2) being able to explain why **incorrect type guard implementations cause silent runtime errors** (Q13) and what techniques prevent this (testing guards with invalid inputs, using schema validation libraries like Zod); (3) understanding the difference between **`is` predicates and `asserts`** (Q14) — predicates narrow inside `if` blocks, assertions narrow for all subsequent code in the function — and knowing when each is appropriate; (4) implementing **exhaustiveness checking with `never`** and `assertNever` (Q9, Q19) — adding a new union member forces compile errors at every `switch`/`if` that doesn't handle it, which is a key architectural safety mechanism; and (5) knowing that **TypeScript reverts narrowing inside closures** (Q16) because closures may be called later when the outer narrowing is no longer guaranteed — this is a subtle limitation that frequently causes "TypeScript says it's fine but it isn't" bugs in production code.
