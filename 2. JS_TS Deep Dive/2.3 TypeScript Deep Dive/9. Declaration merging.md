# TypeScript: Declaration Merging — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is declaration merging in TypeScript, and why does it exist?**
A: Declaration merging is TypeScript's behavior of **combining multiple separate declarations of the same name into a single entity**. When two or more declarations share the same name in the same scope, TypeScript (where permitted) merges them into one definition that incorporates all declared members. It exists primarily to support two real-world needs: (1) **progressive enhancement of existing JavaScript** — allowing type information to be added to pre-existing JS constructs that span multiple files or are composed dynamically; and (2) **augmenting third-party types** — allowing library consumers to add type definitions to a library's existing interfaces without modifying the original source.

Declaration merging is fundamentally a compile-time mechanism — the merged entity exists only in the type system; the JavaScript runtime sees whatever the actual JS declarations produce, independent of how TypeScript merges them.

**Q2. Which declarations can be merged, and which explicitly cannot?**
A: Not every TypeScript declaration supports merging. The rules:

**Mergeable with same-kind declarations:**
- **Interface + Interface** → merged into one interface (the most common and intentional use case)
- **Namespace + Namespace** → merged into one namespace
- **Enum + Enum** → merged into one enum (with caveats — see Q10)

**Mergeable across different kinds (hybrid merging):**
- **Namespace + Class** → namespace adds static members to a class
- **Namespace + Function** → namespace adds properties to a function object
- **Namespace + Enum** → namespace adds static methods/properties to an enum

**Never mergeable:**
- **Type alias + anything** → `type Foo = ...` cannot be merged; a second `type Foo = ...` always errors
- **Class + Class** → two class declarations with the same name always error
- **Variable + most things** → `let`/`const`/`var` declarations of the same name conflict (except `var` within namespaces, which is intentional)

```ts
// ✓ Interface merging — allowed:
interface Dog { name: string; }
interface Dog { breed: string; }
// Merged Dog: { name: string; breed: string; }

// ❌ Type alias merging — never allowed:
type Cat = { name: string; };
type Cat = { breed: string; }; // Error: Duplicate identifier 'Cat'

// ❌ Class merging — never allowed:
class Bird { fly() {} }
class Bird { swim() {} } // Error: Duplicate identifier 'Bird'
```

**Q3. How does interface merging work specifically, and what are the ordering rules for merged members?**
A: When two interfaces with the same name are declared, TypeScript combines all their members into a single interface containing everything from both. Key rules governing the merged result:

1. **Non-function members**: must have identical types across all declarations. Declaring the same property name with different types is an error.
2. **Function members (overloads)**: later declarations' function signatures appear first in the merged interface's overload list. This means later declarations get priority in overload resolution — a design choice that allows libraries to be patched by adding declarations after the original.
3. **Within a single interface declaration**: overload order within one block is preserved as-is (not reversed).

```ts
interface Formatter {
  format(input: string): string;  // original declaration
}

interface Formatter {
  format(input: number): string;  // merged later
  format(input: Date): string;
}

// Resulting merged type (later declaration's signatures come first):
interface Formatter {
  format(input: number): string;  // from later declaration
  format(input: Date): string;    // from later declaration
  format(input: string): string;  // from earlier declaration
}
```

**Q4. What is the difference between declaration merging and `interface extends`?**
A: Both produce a type combining multiple sources, but differ in semantics:
- **Declaration merging**: requires the **same name** across separate declaration sites. TypeScript finds and merges them implicitly. Supports the "augmentation" use case (adding to a type you don't own).
- **`interface extends`**: creates a **new named type** that inherits from the specified types. The original types are unchanged. Requires naming the base types explicitly. Produces a nominal (named) child relationship rather than an implicit identity merge.

A critical practical difference: merging allows **conflicting property types** to produce a `never`-typed property (caught at use-site, not declaration-site) while `extends` with conflicting types errors immediately at the `extends` clause. Additionally, only declaration merging (not `extends`) works for module augmentation of third-party types.

### Section 2: Namespace Merging

**Q5. How does namespace merging work, and what does it enable?**
A: Multiple namespace declarations with the same name merge their **exported members** into a single namespace. This is how TypeScript allows a namespace to be split across multiple files or built up incrementally. Non-exported members in each declaration remain local to that declaration block and are not shared between merged declarations — only `export`ed members are visible in the merged namespace.

```ts
// First declaration
namespace Validation {
  export interface StringValidator {
    isAcceptable(s: string): boolean;
  }
  const lettersRegexp = /^[A-Za-z]+$/; // NOT exported — stays local to this block
}

// Second declaration (same namespace, possibly different file)
namespace Validation {
  export class LettersOnlyValidator implements StringValidator {
    isAcceptable(s: string) {
      return /^[A-Za-z]+$/.test(s); // can't use lettersRegexp from the other block
    }
  }
}

// Merged result:
Validation.LettersOnlyValidator; // ✓ accessible
// Validation.StringValidator used as type ✓
```

**Q6. What is the "namespace + function" merging pattern, and what real-world scenario does it model?**
A: JavaScript functions are objects and can have properties attached to them — a common pattern in JS libraries where a function is also used as a namespace (e.g., `jQuery.ajax`, `moment.utc`). TypeScript models this by allowing a namespace declaration to merge with a function declaration of the same name, adding the namespace's exported members as properties on the function's type.

```ts
// Model a function that also has properties (like a jQuery-style API)
function createWidget(selector: string): Widget { /* ... */ }

namespace createWidget {
  export interface Options {
    theme: 'light' | 'dark';
    animated: boolean;
  }

  export function fromElement(el: HTMLElement): Widget { /* ... */ }

  export const VERSION = '2.0.0' as const;
}

// Usage — function and namespace members coexist:
const w = createWidget('#app');                          // function call ✓
const opts: createWidget.Options = { theme: 'dark', animated: true }; // namespace type ✓
const w2 = createWidget.fromElement(document.body);     // namespace member function ✓
console.log(createWidget.VERSION);                      // '2.0.0' ✓
```

**Q7. What is the "namespace + class" merging pattern, and what does it add to a class?**
A: When a namespace merges with a class of the same name, the namespace's exported members become **static members** on the class. This models the common JavaScript pattern of attaching properties and inner classes to a constructor function.

```ts
class ValidationError extends Error {
  constructor(public field: string, message: string) {
    super(message);
    this.name = 'ValidationError';
  }
}

// Merge a namespace to add "inner types" and factory methods as statics:
namespace ValidationError {
  export type Code = 'REQUIRED' | 'TOO_SHORT' | 'INVALID_FORMAT';

  export function required(field: string): ValidationError {
    return new ValidationError(field, `${field} is required`);
  }

  export function tooShort(field: string, min: number): ValidationError {
    return new ValidationError(field, `${field} must be at least ${min} characters`);
  }
}

// Usage:
const err = ValidationError.required('email');          // static factory ✓
const code: ValidationError.Code = 'REQUIRED';         // inner type ✓
err instanceof ValidationError;                        // ✓
```

### Section 3: Module Augmentation

**Q8. What is module augmentation, and how does it differ from global declaration merging?**
A: Module augmentation is the pattern of **adding members to an existing module's exported types** from a separate file, without modifying the module's source. It's one of the most practically important uses of declaration merging, enabling:
- Adding types to third-party libraries.
- Extending Express `Request`/`Response` types with app-specific fields.
- Augmenting Vue/React component options types.

The syntax requires an `import` (to make the current file a module) and a `declare module 'module-name'` block:

```ts
// augment-express.d.ts
import 'express'; // must import to be treated as a module (not a script)

declare module 'express' {
  interface Request {
    // Add app-specific fields to Express's Request type
    user?: { id: string; roles: string[] };
    requestId: string;
  }
}
```

**Global declaration merging** differs in that it uses `declare global { }` (inside a module file) or just top-level declarations (in a `.d.ts` script file without any imports/exports). Global merging adds to types visible globally across all files, whereas module augmentation is scoped to a specific module's types.

```ts
// global-augmentation.d.ts (no imports — this is a script, not a module)
interface Window {
  analytics: AnalyticsInstance;
  featureFlags: Record<string, boolean>;
}

// OR, inside a module file (.ts with imports):
export {}; // make this file a module

declare global {
  interface Window {
    analytics: AnalyticsInstance;
  }
}
```

**Q9. What is the critical syntax requirement for module augmentation to work, and what happens if it's missing?**
A: The file doing the augmentation must be a **module** (not a script). TypeScript distinguishes between a "module" (a file that contains at least one `import` or `export` statement) and a "script" (a file with no `import`/`export`, which contributes to the global scope). If a file doing `declare module 'foo'` has no imports or exports, it's treated as a script, and `declare module 'foo'` is interpreted as a module's *ambient declaration* (describing that module to the compiler), not as an augmentation of an existing module.

The fix is always to add a dummy export or the relevant import:

```ts
// ❌ Missing module marker — this is a SCRIPT, not an augmentation:
declare module 'some-library' {
  interface Options { debug: boolean; } // This REPLACES the module's types, not augments!
}

// ✓ With export — this is a MODULE, performing augmentation:
export {}; // makes this file a module
declare module 'some-library' {
  interface Options { debug: boolean; } // Now this AUGMENTS some-library's types
}

// ✓ Even better — import what you're augmenting, making the relationship explicit:
import 'some-library';
declare module 'some-library' {
  interface Options { debug: boolean; }
}
```

### Section 4: Enum Merging

**Q10. How does enum merging work, and what are its significant limitations?**
A: Two `enum` declarations with the same name can be merged, but with a major restriction: **only one of them can have non-const-expression values**. In practice, this means only one `enum` block per merged enum can have members with auto-incremented numeric values or computed string values; all subsequent merged blocks must use explicit literal values.

Additionally, enum merging requires that one block precede the other in a way that doesn't create circular member references. It's rarely used in practice — its primary purpose is allowing enums to be extended across files in ambient declarations (`.d.ts` files), where TypeScript doesn't generate code and the restriction on initializer values doesn't apply in the same way.

```ts
// First declaration
enum Direction {
  Up = 0,
  Down = 1
}

// Second declaration — extending the enum (must use explicit values)
enum Direction {
  Left = 2,   // ✓ explicit value required in a merged block
  Right = 3   // ✓
}

// Merged: Direction.Up=0, Direction.Down=1, Direction.Left=2, Direction.Right=3
console.log(Direction.Left); // 2

// ❌ This would error (auto-incremented in a merged block):
enum Direction {
  Forward,  // Error: In an enum with multiple declarations, one declaration must provide an initializer for this member
  Back
}
```

### Section 5: Advanced Patterns

**Q11. How do you augment a third-party library's types in practice, and what are the pitfalls?**
A: The standard workflow for augmenting a library (using Express as the canonical example):

```ts
// src/types/express-augmentations.d.ts

// Step 1: Import the original module (makes this a module file)
import { ParamsDictionary, Query } from 'express-serve-static-core';

// Step 2: Declare module augmentation targeting the module to augment
declare module 'express-serve-static-core' {
  // Step 3: Extend the interface — only merge-able declarations (interface, namespace)
  interface Request {
    user?: {
      id: string;
      email: string;
      roles: Array<'admin' | 'editor' | 'viewer'>;
    };
    startTime: number;
    correlationId: string;
  }

  interface Response {
    sendSuccess<T>(data: T, statusCode?: number): void;
    sendError(message: string, statusCode?: number): void;
  }
}
```

Common pitfalls:
1. **Augmenting the wrong module**: Express's `Request` type lives in `express-serve-static-core`, not in `express` — check the source `.d.ts` to find where an interface is actually declared.
2. **File treated as a script**: forgetting the `import` or `export {}` makes the file a script and the `declare module` block replaces instead of augmenting.
3. **Adding non-optional required fields**: adding a required field (no `?`) to a merged interface means existing code satisfying the original interface now technically violates the merged version — use optional properties unless the field is truly guaranteed to exist.
4. **TypeScript not picking up the augmentation**: the augmentation file must be included in the project's `tsconfig.json` (under `include` or `files`) or imported somewhere in the project — TypeScript won't automatically scan arbitrary `.d.ts` files.

**Q12. How does declaration merging interact with `strict` mode and structural typing?**
A: Merging is a structural operation — it creates a type with more members. This interacts with `strict` mode in that once a member is merged into an interface, code that was previously satisfying that interface (with the original fewer members) may now fail to satisfy it if the merged member is required (non-optional). Additionally, merged members participate in structural compatibility checks just like any other member — a class implementing a merged interface must implement all merged members, not just those from one declaration.

**Q13. What is "ambient module augmentation" used in declaration files (`.d.ts`), and how is it different from regular augmentation?**
A: Ambient module augmentation appears in `.d.ts` files to describe the shape of JavaScript modules that don't have TypeScript source. There are two distinct uses of `declare module`:

1. **Ambient module declaration** (in a script `.d.ts`): describes a module from scratch — useful for typing untyped JS packages. The module has no existing TypeScript source, and this `.d.ts` file defines its entire API.
2. **Module augmentation** (in a module `.d.ts` or `.ts` with imports): extends an existing module's types by adding to its interfaces/namespaces.

```ts
// ambient-declarations.d.ts (script file, no imports — describes a whole module)
declare module 'legacy-library' {
  export function doThing(x: string): number;
  export const VERSION: string;
  // This DEFINES the module's types (it's not augmenting anything existing)
}

// augmentation.d.ts (module file, has imports — adds to existing module)
import 'legacy-library';
declare module 'legacy-library' {
  // This ADDS to what we just declared in ambient-declarations.d.ts
  export function doThingBetter(x: string, options?: object): number;
}
```

### Section 6: Scenario / Interview-Style Questions

**Q14. "You're using Express and want TypeScript to know that `req.user` is available after your authentication middleware. How do you set this up?"**
A: Module augmentation on `express-serve-static-core`'s `Request` interface. Create a `.d.ts` file (e.g., `src/types/express.d.ts`), ensure it's included in `tsconfig.json`, and augment the `Request` interface with the `user` field. The field should be optional (`user?`) since it doesn't exist before the auth middleware runs — routes that are protected can then cast or use type predicates for the non-optional version.

```ts
// src/types/express.d.ts
import 'express';

declare module 'express-serve-static-core' {
  interface Request {
    user?: {
      id: string;
      email: string;
      roles: string[];
    };
  }
}

// src/middleware/auth.ts
import { Request, Response, NextFunction } from 'express';

export function requireAuth(req: Request, res: Response, next: NextFunction) {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'Unauthorized' });

  try {
    req.user = verifyToken(token); // ✓ TypeScript knows req.user can be set
    next();
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
}

// src/routes/profile.ts
import { Request, Response } from 'express';

export function getProfile(req: Request, res: Response) {
  if (!req.user) return res.status(401).json({ error: 'Not authenticated' });
  res.json({ id: req.user.id, email: req.user.email }); // ✓ TypeScript knows user fields
}
```

**Q15. "A teammate declares the same interface twice with a conflicting property type. What happens?"**
A: The property with conflicting types becomes typed as `never` in the merged result — TypeScript doesn't error at the declaration sites but silently makes that property impossible to use. This is a notable contrast to `interface extends` with conflicting types, which errors immediately at the `extends` clause. The silence of the merge-time conflict makes it particularly insidious — the bug doesn't surface until someone tries to assign a value to or read from that property, at which point the error message about `never` may not obviously point back to the duplicate declarations.

```ts
interface Config { timeout: number; }
interface Config { timeout: string; } // same name, different type — no error here

const c: Config = { timeout: 5000 }; // ❌ Type 'number' is not assignable to type 'never'
const c2: Config = { timeout: 'long' }; // ❌ Type 'string' is not assignable to type 'never'
// Config.timeout is now `number & string = never` — completely unusable
```

**Q16. "Why can't you use declaration merging with `type` aliases to achieve the same effect as interface merging?"**
A: Type aliases represent **structural type expressions**, not declarations — they are a compile-time name for a type, not a named entity that TypeScript can find and combine across declaration sites. TypeScript's type system has no mechanism for merging two independently-declared type expressions under the same name; the second declaration is treated as a redeclaration of the same binding, which is an error. Interfaces, by contrast, are first-class named entities in the type system specifically designed to accumulate members across declaration sites. For code that needs augmentability (library types, extensible option bags), always prefer `interface` over `type`.

## Problem 1 — Extending a Third-Party Library's Interface (Module Augmentation)

### Problem
Your application uses a logging library that exports a `Logger` interface and a `createLogger` factory function. You want to add a `context` field to every `Logger` instance throughout your app, typed as `Record<string, unknown>`, without modifying the library's source code.

```ts
// Library exports (cannot modify):
// export interface Logger {
//   info(msg: string): void;
//   error(msg: string): void;
// }
// export function createLogger(name: string): Logger;

// Goal: after augmentation, TypeScript should know about .context:
const log = createLogger('app');
log.context = { requestId: 'abc-123', userId: '42' }; // ✓
log.info('Processing request');                        // ✓ (original method)
```

### Pattern Recognition
Module augmentation — extending an interface in an existing module by merging additional members under the same interface name in a `declare module` block.

### Key Insight
TypeScript's interface merging works across module boundaries via `declare module` augmentation. Since `Logger` is an `interface` (not a `type` alias or `class`), it can be merged. The augmentation file must be a module (require an `import` or `export {}`) to avoid accidentally replacing the library's entire type definition.

### Approach
1. Create a dedicated `.d.ts` augmentation file.
2. Import the library to make the file a module.
3. Use `declare module 'logging-library'` to augment its `Logger` interface with the `context` property.
4. Ensure the file is picked up by TypeScript (via `tsconfig.json`).

### Solution

```ts
// src/types/logger-augmentation.d.ts

// Import the library — this makes the file a MODULE (not a script),
// which is required for augmentation (as opposed to replacement) semantics:
import 'logging-library';

declare module 'logging-library' {
  // Augment the Logger interface — TypeScript merges this with the original:
  interface Logger {
    // Optional: existing loggers don't have this until explicitly set
    context?: Record<string, unknown>;

    // Optional helper: create a child logger with merged context
    withContext(ctx: Record<string, unknown>): Logger;
  }
}

// src/middleware/logging.ts
import { Request, Response, NextFunction } from 'express';
import { createLogger } from 'logging-library';

const log = createLogger('http');

export function requestLogging(req: Request, res: Response, next: NextFunction) {
  // TypeScript now knows about .context on Logger:
  log.context = {
    requestId: req.headers['x-request-id'] ?? crypto.randomUUID(),
    method: req.method,
    path: req.path
  };

  log.info(`${req.method} ${req.path}`); // ✓ original method still works

  const childLog = log.withContext({ userId: req.user?.id }); // ✓ augmented method
  req.logger = childLog; // pass contextual logger down to route handlers

  next();
}
```

### Verification

```ts
import { createLogger, Logger } from 'logging-library';

const log = createLogger('test');

// Original interface members still work:
log.info('test message');  // ✓
log.error('error message'); // ✓

// Augmented members are now type-safe:
log.context = { env: 'test' };              // ✓ Record<string, unknown>
log.context = 'not-an-object';             // ❌ Type 'string' is not assignable

// TypeScript infers the merged interface:
type CheckLogger = Logger['context']; // Record<string, unknown> | undefined ✓

// The original interface is unchanged (augmentation, not replacement):
// If we import Logger in the library's own files, they don't see our augmentation
// (module augmentation only affects files that include our augmentation file)
```

### Edge Cases
- **`context` as non-optional**: if `context` were required (no `?`), any code creating a `Logger` without setting `context` would fail the interface check. For augmentation of third-party types, always prefer optional fields unless you control all `Logger` creation points.
- **`tsconfig.json` coverage**: the augmentation file must be within the `include` glob or explicitly listed in `files`. Augmentation files in `node_modules` or outside the project root are ignored by default.
- **Which module to augment**: logging libraries sometimes re-export from an inner module. Always check the original `.d.ts` to find where `Logger` is declared (e.g., `logging-library/dist/types`) and augment that specific module path.

### Follow-up Questions
- "How would you verify at runtime that the `context` and `withContext` actually exist?" → The augmentation is a type-only addition — the implementation must be provided separately (e.g., by monkey-patching the prototype in an initialization file, or by using a wrapper class). TypeScript trusts that you've provided the implementation; it only adds type-level knowledge.
- "What if the library uses `type Logger = { ... }` instead of `interface Logger`?" → Type aliases cannot be merged. Alternatives: (1) file a bug/PR to change it to an interface; (2) wrap the library's type: `type AppLogger = Logger & { context?: Record<string, unknown> }` and use `AppLogger` throughout your app; (3) use a type assertion at use-sites.

## Problem 2 — Namespace + Function Merging for a Builder API

### Problem
Model a `css` tagged template function (like styled-components' internals) that also has utility methods accessible as properties on the function itself. TypeScript should understand both the call signature and the static methods.

```ts
const styles = css`color: red; font-size: 14px;`; // function call
css.compose(styleA, styleB);                       // static method on the function
const cls: css.ClassName = 'header-style';         // namespace type
```

### Pattern Recognition
Namespace + function declaration merging — the namespace's exports become properties on the function type, modeling the JavaScript pattern of a function with attached properties.

### Key Insight
In JavaScript, a function is an object. A function defined as `function foo() {}` can have `foo.bar = ...` attached to it. TypeScript models this with the `namespace + function` merge: the function declaration provides the call signature, and the namespace declaration provides the named properties. Both must be exported from the same module.

### Approach
Declare the function with its call signature. Declare a namespace with the same name containing the types and utility functions that will live as properties. TypeScript merges them into a single type that is callable AND has property access.

### Solution

```ts
// css.ts

// The ClassName branded type (used inside the namespace)
type CSSClassName = string & { readonly __cssClassName: unique symbol };

// Step 1: declare the function
function css(
  strings: TemplateStringsArray,
  ...values: (string | number)[]
): CSSClassName {
  const result = strings.reduce((acc, str, i) => {
    return acc + str + (values[i] ?? '');
  }, '');
  // In a real implementation, this would hash the CSS and inject a stylesheet
  return `css-${hashString(result)}` as CSSClassName;
}

// Step 2: merge a namespace — its exports become properties on `css`
namespace css {
  // Exported type — accessible as css.ClassName
  export type ClassName = CSSClassName;

  // Exported function — accessible as css.compose(...)
  export function compose(...classNames: CSSClassName[]): CSSClassName {
    return classNames.join(' ') as CSSClassName;
  }

  // Exported function — accessible as css.global(...)
  export function global(styles: string): void {
    // Inject global styles into the document
    const el = document.createElement('style');
    el.textContent = styles;
    document.head.appendChild(el);
  }

  // Exported constant — accessible as css.VERSION
  export const VERSION = '3.0.0' as const;
}

function hashString(s: string): string {
  let hash = 0;
  for (let i = 0; i < s.length; i++) {
    hash = (hash << 5) - hash + s.charCodeAt(i);
    hash |= 0;
  }
  return Math.abs(hash).toString(36);
}

export default css;

// consumer.ts
import css from './css';

// Call signature — template literal usage:
const headerStyle = css`
  font-size: 24px;
  font-weight: bold;
  color: #333;
`; // ✓ type: css.ClassName (= CSSClassName)

const bodyStyle = css`
  font-size: 14px;
  line-height: 1.6;
`;

// Namespace-provided static methods:
const combined = css.compose(headerStyle, bodyStyle); // ✓ type: css.ClassName
css.global('* { box-sizing: border-box; }');          // ✓ void
console.log(css.VERSION);                             // ✓ '3.0.0'

// Namespace-provided type:
const myClass: css.ClassName = headerStyle;           // ✓
const invalid: css.ClassName = 'literal-class-name';  // ❌ not branded as CSSClassName
```

### Verification

```ts
// TypeScript understands the merged type:
type CssType = typeof css;
// CssType is both callable AND has static properties:
// {
//   (strings: TemplateStringsArray, ...values: (string | number)[]): css.ClassName;
//   compose(...classNames: css.ClassName[]): css.ClassName;
//   global(styles: string): void;
//   VERSION: '3.0.0';
// }

// Hovering over css in an editor shows the merged type ✓
css``; // ✓ — the function signature
css.compose; // ✓ — the namespace member
css.ClassName; // ✓ — the namespace type (used as a value-level namespace member would be)
```

### Edge Cases
- **Import/export**: the merged `css` function and `css` namespace must be exported together. When using `export default css`, the namespace merges with the default export. Named exports also work: `export { css }`.
- **Order in file**: the function declaration should precede the namespace declaration (or be at the same level) — TypeScript's declaration merging doesn't care about order within a file, but some linters prefer function-first for readability.
- **Class instead of function**: if using a class, `namespace + class` merging would add static members. The pattern is identical; only the keyword changes.

### Follow-up Questions
- "Why not just attach the methods to the function object directly (`css.compose = function() {}`)?" → You can, and TypeScript 3.1+ sometimes infers such assignments. But the namespace merging approach is more explicit, works with both function declarations and function expressions, and produces a cleaner type signature in IDE tooltips and documentation.

## Problem 3 — Incremental Interface Building Across Files (Interface Merging)

### Problem
A large application has a global configuration object typed as `AppConfig`. Multiple modules each contribute their own configuration keys. Without a central registry file, each module should be able to declare its own config slice, and the TypeScript type should include all of them.

```ts
// database.ts contributes: { db: { host: string; port: number } }
// auth.ts contributes:     { auth: { secret: string; expiresIn: string } }
// cache.ts contributes:    { cache: { ttl: number; maxSize: number } }

// The merged AppConfig should have ALL keys:
const config: AppConfig = {
  db: { host: 'localhost', port: 5432 },
  auth: { secret: 'xxx', expiresIn: '1d' },
  cache: { ttl: 3600, maxSize: 1000 }
};
```

### Pattern Recognition
Interface declaration merging across multiple files — each module augments a shared `AppConfig` interface in a global declaration file or shared module, contributing its own fields.

### Key Insight
A shared interface in a dedicated types file can be augmented by any module in the project using `declare module` (or `declare global` for global types). Each module adds exactly the fields it "owns," keeping configuration type definitions co-located with the modules they describe. The TypeScript compiler merges all contributions into a single `AppConfig` type.

### Approach
Define a base `AppConfig` interface (empty or with required core fields) in a shared types file. Each feature module augments `AppConfig` with its own configuration section. The final `AppConfig` type is the merge of all augmentations.

### Solution

```ts
// src/types/config.ts — base definition (shared module)
export interface AppConfig {
  readonly env: 'development' | 'staging' | 'production';
  readonly port: number;
}

// src/database/config.ts — database module augments AppConfig
import 'src/types/config'; // import to make this a module

declare module 'src/types/config' {
  interface AppConfig {
    db: {
      host: string;
      port: number;
      name: string;
      ssl: boolean;
    };
  }
}

export interface DatabaseConfig {
  host: string;
  port: number;
  name: string;
  ssl: boolean;
}

export function createConnection(config: DatabaseConfig) {
  /* ... */
}

// src/auth/config.ts — auth module augments AppConfig
import 'src/types/config';

declare module 'src/types/config' {
  interface AppConfig {
    auth: {
      jwtSecret: string;
      expiresIn: string;
      refreshTokenTtl: number;
    };
  }
}

// src/cache/config.ts — cache module augments AppConfig
import 'src/types/config';

declare module 'src/types/config' {
  interface AppConfig {
    cache: {
      ttl: number;
      maxSize: number;
      strategy: 'lru' | 'lfu';
    };
  }
}

// src/app.ts — uses the fully merged AppConfig
import { AppConfig } from 'src/types/config';
// Import augmentation files to activate their contributions:
import 'src/database/config';
import 'src/auth/config';
import 'src/cache/config';

function initializeApp(config: AppConfig) {
  console.log(config.env);                 // ✓ from base interface
  console.log(config.db.host);             // ✓ from database augmentation
  console.log(config.auth.jwtSecret);      // ✓ from auth augmentation
  console.log(config.cache.strategy);      // ✓ from cache augmentation

  // TypeScript catches missing or wrong fields:
  const partial: AppConfig = {
    env: 'development',
    port: 3000,
    db: { host: 'localhost', port: 5432, name: 'mydb', ssl: false },
    // ❌ Error: Property 'auth' is missing in type
  };
}
```

### Verification

```ts
import { AppConfig } from 'src/types/config';
import 'src/database/config';
import 'src/auth/config';
import 'src/cache/config';

// TypeScript merges all four declarations:
type Keys = keyof AppConfig;
// → 'env' | 'port' | 'db' | 'auth' | 'cache'

// Each field is correctly typed:
type DbHost = AppConfig['db']['host']; // string ✓
type Strategy = AppConfig['cache']['strategy']; // 'lru' | 'lfu' ✓

// Full config object satisfies the merged type:
const config: AppConfig = {
  env: 'production',
  port: 8080,
  db: { host: 'db.example.com', port: 5432, name: 'prod', ssl: true },
  auth: { jwtSecret: process.env.JWT_SECRET!, expiresIn: '24h', refreshTokenTtl: 604800 },
  cache: { ttl: 3600, maxSize: 10000, strategy: 'lru' }
}; // ✓ all fields required and correctly typed
```

### Edge Cases
- **Import order**: augmentations are only active when their files are imported. If `src/cache/config.ts` is never imported, `AppConfig.cache` doesn't exist in the merged type for that compilation unit. The `app.ts` entry point must import all augmentation files to get the full merged type.
- **Circular imports**: if augmentation files import from each other, circular dependencies can arise. Keep augmentation declarations separate from runtime logic to avoid this.
- **Conflicting keys**: if two modules both try to add an `id` field to `AppConfig` with different types, the merge produces `id: T1 & T2`. If the types are incompatible, `id` becomes `never`. Use distinct namespace keys per module to prevent this (e.g., `db`, `auth`, `cache` rather than flat fields).

### Follow-up Questions
- "Is there a way to enforce that all augmentations are imported before using the config?" → Not directly via TypeScript's type system, but you can create a barrel file (`src/config/index.ts`) that imports all augmentation files and re-exports `AppConfig`, making it the single import point — consumers import from the barrel and automatically get all augmentations.

## Quick Reference — Pattern Decision Tree

```
Do you need to combine or extend type declarations in TypeScript?
│
├── SAME-KIND DECLARATIONS WITH THE SAME NAME (in same scope)?
│   ├── Interface + Interface → MERGES (most common, intended use case)
│   │   → non-function members must have identical types
│   │   → function overloads: later declarations appear first in overload order
│   ├── Namespace + Namespace → MERGES (only exported members are shared)
│   ├── Enum + Enum → MERGES (later blocks need explicit values)
│   ├── Type + Type → ❌ ERRORS (type aliases never merge)
│   └── Class + Class → ❌ ERRORS (classes never merge)
│
├── DIFFERENT-KIND DECLARATIONS WITH THE SAME NAME?
│   ├── Namespace + Function → MERGES (namespace exports become function properties)
│   ├── Namespace + Class → MERGES (namespace exports become class static members)
│   └── Namespace + Enum → MERGES (namespace exports become enum properties)
│
├── NEED TO ADD TYPES TO A THIRD-PARTY MODULE?
│   └── Module Augmentation:
│       import 'the-library';
│       declare module 'the-library' { interface Target { newField: Type; } }
│       → file MUST have import or export to be a module (not a script)
│       → only interface and namespace can be augmented (not type, class, function)
│
├── NEED TO ADD TO GLOBAL TYPES (Window, Array, etc.)?
│   ├── In a SCRIPT file (.d.ts with no imports): declare directly at top level
│   │   interface Window { myProp: string; }
│   └── In a MODULE file (.ts/.d.ts with imports): use declare global {}
│       export {};
│       declare global { interface Window { myProp: string; } }
│
├── CONFLICTING PROPERTY TYPES IN MERGED INTERFACES?
│   └── The property becomes `never` — NO error at declaration sites
│       → Errors only when you try to assign or read the property
│       → Use distinct property names or check interface extends (errors immediately)
│
└── WANT AUGMENTABILITY IN YOUR OWN CODE?
    └── Always declare extensible types as interface (not type alias)
        interface MyOptions { /* ... */ }  // ✓ consumers can extend this
        type MyOptions = { /* ... */ }     // ❌ consumers cannot extend this
```

## Common Bugs Checklist

Before shipping any code that relies on declaration merging, verify:

1. **Module vs. script file for augmentation: does the augmentation file have at least one `import` or `export`?** — Without it, `declare module 'foo'` in the file is an ambient module declaration (defining the module from scratch) rather than augmenting the existing module. Add `import 'foo'` or `export {}` to make it a module.

2. **Augmenting the correct module path: is the target interface defined where you think it is?** — Many libraries re-export types from inner modules. `express`'s `Request` lives in `express-serve-static-core`. Augmenting `'express'` instead of `'express-serve-static-core'` may silently do nothing (or produce a separate type the original library code never uses). Check the library's `.d.ts` with "Go to Definition."

3. **Conflicting property types producing `never`: have you checked with `getOwnPropertyDescriptor` or a type-level test?** — Two merged interfaces with the same property name but different types produce `never` for that property — silently, with no error at the declaration site. Test with `type Check = MergedInterface['propertyName']` to see what the type actually resolved to.

4. **Augmentation file not included in tsconfig: is the augmentation file within the `include` glob?** — TypeScript won't automatically scan your project for all `.d.ts` files outside the configured `include` directories. Check `tsconfig.json` and verify the augmentation file is covered.

5. **Using `type` alias instead of `interface` for something you need to augment later: is this intentional?** — Type aliases cannot be merged. If you're building a library or framework with extension points (option bags, plugin systems, event registries), always use `interface` for the extensible types.

6. **Namespace merging sharing non-exported members: are you expecting access to a `let`/`const` from the other namespace block?** — Only `export`ed members are shared across merged namespace declarations. Local variables stay local to each declaration block. If you need to share state between blocks, export it.

7. **Enum merging with auto-incremented values: does every merged block after the first use explicit values?** — The second and subsequent merged enum blocks must provide explicit numeric values. Auto-incremented values (bare names with no initializer) in a merged block produce a compile error.

8. **Function + namespace merge: is the function a declaration (not an expression)?** — `function foo() {}` can be merged with `namespace foo {}`. But `const foo = function() {}` or `const foo = () => {}` cannot directly merge with a namespace. Use `Object.assign(foo, { ... })` for arrow function + properties, or switch to a function declaration.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to know that declaration merging is TypeScript's mechanism for two distinct real-world needs: **progressive type enhancement** (adding types to JS constructs that span files or are built dynamically) and **third-party augmentation** (extending library types without touching the source). The distinction between module augmentation and ambient module declaration — and specifically the critical role of the `import`/`export` in determining which one you get — is the detail that separates fluent understanding from surface-level recall. The other key insight is when to reach for `interface` over `type`: any extensible type (option objects, event maps, plugin registries, request/response types) should be declared as an `interface` specifically because `interface` supports merging and `type` does not. Articulating this as a deliberate architectural choice — not just a style preference — demonstrates production-level TypeScript judgment.
