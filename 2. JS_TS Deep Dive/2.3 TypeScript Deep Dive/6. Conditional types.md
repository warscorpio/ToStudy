# TypeScript: Conditional Types & the `infer` Keyword — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a conditional type in TypeScript?**
A: A conditional type is a type-level `if/else` expression that selects one of two types based on whether a type relationship holds. The syntax mirrors the JavaScript ternary operator:

```ts
T extends U ? X : Y
```

Read as: "If `T` is assignable to `U`, resolve to type `X`; otherwise resolve to type `Y`."

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<string>;  // true
type B = IsString<number>;  // false
type C = IsString<'hello'>; // true  ('hello' extends string)
```

Conditional types operate at the type level — they are evaluated by the TypeScript compiler during type-checking, not at runtime. They enable expressing type relationships that cannot be captured by simple unions, intersections, or generics alone.

**Q2. What does `T extends U` mean in the context of a conditional type?**
A: In a conditional type, `T extends U` means "`T` is assignable to `U`" — i.e., every value of type `T` is also a valid value of type `U`. It is a structural compatibility check, not a class inheritance check.

```ts
// These all evaluate to true because T is assignable to U:
type C1 = 'hello' extends string ? true : false;       // true — literal extends its base
type C2 = string extends string | number ? true : false; // true — narrower extends wider
type C3 = never extends string ? true : false;          // true — never is assignable to anything
type C4 = { a: number; b: string } extends { a: number } ? true : false; // true — structural
type C5 = string[] extends any[] ? true : false;        // true — specific extends general

// These evaluate to false:
type C6 = string extends number ? true : false;  // false
type C7 = any extends string ? true : false;     // boolean (special case — see Q3)
```

**Q3. What is the special behavior of `any` in conditional types?**
A: `any` is special — TypeScript treats it ambiguously in conditional types. When the checked type is `any`, the conditional type resolves to a union of BOTH branches — both `X` and `Y`:

```ts
type IsString<T> = T extends string ? 'yes' : 'no';

type A = IsString<any>; // 'yes' | 'no'  ← both branches!
type B = IsString<never>; // never         ← never distributes to never

// Why: 'any' is simultaneously assignable to everything and a supertype of everything.
// TypeScript can't pick just one branch, so it picks both.
```

This is an important gotcha — if you're writing a type utility that should work cleanly on `any`, you may need to explicitly handle it.

**Q4. What is distributive conditional types, and when does distribution occur?**
A: When the checked type `T` is a **naked type parameter** (not wrapped in `[]`, `{}`, or any other type), a conditional type **distributes** over union types. Each member of the union is evaluated separately through the conditional, and the results are unioned:

```ts
type Unwrap<T> = T extends Promise<infer R> ? R : T;

// With a union input — DISTRIBUTES:
type A = Unwrap<Promise<string> | Promise<number> | boolean>;
// = Unwrap<Promise<string>> | Unwrap<Promise<number>> | Unwrap<boolean>
// = string | number | boolean

// Contrast: without a union input — single evaluation:
type B = Unwrap<Promise<string>>; // string
```

Distribution happens automatically when `T` is a "bare" (naked) type parameter. To **prevent distribution**, wrap `T` in a tuple:

```ts
type IsNever<T> = [T] extends [never] ? true : false;
// Without the tuple brackets: IsNever<never> = never (distributes over empty union)
// With tuple brackets:        IsNever<never> = true  (single check, no distribution)
```

**Q5. What is the `infer` keyword, and what problem does it solve?**
A: `infer` introduces a type variable **within** the `extends` clause of a conditional type — it "infers" (captures) a portion of the matched type and makes it available in the `true` branch. It solves the problem of extracting type information that is embedded inside another type.

Without `infer`, you cannot "reach into" a type and extract a piece of it. With `infer`, you can declare "if this type matches this pattern, capture the matching piece as a new type variable":

```ts
// Problem: how to extract the return type of a function type?
type MyFunc = () => string;

// Without infer — no way to extract:
// type ReturnType<T> = T extends Function ? ??? : never; // can't get the return type

// With infer — extract the return type:
type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type A = ReturnType<() => string>;          // string
type B = ReturnType<(x: number) => boolean>; // boolean
type C = ReturnType<string>;                 // never (string doesn't match function pattern)
```

The `infer R` clause says: "if `T` is a function type, let `R` be the type of its return value." `R` is only available in the `true` branch.

### Section 2: The `infer` Keyword Deep Dive

**Q6. What is the syntax and scope of `infer`?**
A: `infer` can only appear in the `extends` clause of a conditional type. The inferred type variable is in scope only in the `true` branch (the type after `?`):

```ts
type Example<T> =
  T extends SomeType<infer R>  // ← infer R declared here in the extends clause
    ? R                         // ← R available here (true branch)
    : never;                    // ← R NOT available here (false branch)

// Multiple infer variables in one conditional:
type FunctionShape<T> =
  T extends (arg: infer A) => infer R
    ? { argument: A; returnType: R }  // both A and R available
    : never;

type F = FunctionShape<(x: number) => string>;
// { argument: number; returnType: string }
```

**Q7. How does `infer` work with arrays, tuples, and nested types?**
A: `infer` can match any position in a structural type pattern — including array elements, tuple positions, object property types, and nested generics:

```ts
// Array element type
type ArrayElement<T> = T extends (infer E)[] ? E : never;
type A = ArrayElement<string[]>;        // string
type B = ArrayElement<(number | boolean)[]>; // number | boolean

// First element of a tuple
type Head<T> = T extends [infer H, ...any[]] ? H : never;
type C = Head<[string, number, boolean]>; // string

// Last element of a tuple
type Last<T> = T extends [...any[], infer L] ? L : never;
type D = Last<[string, number, boolean]>; // boolean

// Tail of a tuple (everything after first)
type Tail<T> = T extends [any, ...infer Rest] ? Rest : never;
type E = Tail<[string, number, boolean]>; // [number, boolean]

// Nested generic parameter
type Awaited<T> = T extends Promise<infer R> ? Awaited<R> : T; // recursive
type F = Awaited<Promise<Promise<string>>>; // string

// Object property type
type PropType<T, K extends keyof T> = T extends { [key in K]: infer V } ? V : never;
type G = PropType<{ name: string; age: number }, 'name'>; // string
```

**Q8. When `infer` appears in multiple positions for the same variable, how are they combined?**
A: When `infer R` appears in multiple co-variant positions (positions that produce values, like return types or array elements), TypeScript infers the union of all matched types. When `infer R` appears in contra-variant positions (positions that consume values, like function parameter types), TypeScript infers the intersection:

```ts
// Co-variant positions → union
type Foo<T> = T extends { a: infer U; b: infer U } ? U : never;
type A = Foo<{ a: string; b: number }>; // string | number

// Contra-variant positions → intersection
type Bar<T> = T extends { fn: (x: infer U) => void } ? U : never;
// With overloaded functions (multiple contra-variant positions):
type Baz<T> = T extends {
  (x: infer U): void;
  (x: infer U): void;
} ? U : never;
// U is inferred as intersection of all contra-variant U positions
```

In practice, you'll most often encounter the co-variant union case. The intersection case matters when building utilities that work with function overloads (like `ObtainLastCallSignature`).

**Q9. What is the difference between `infer` at co-variant vs contra-variant positions for TypeScript 4.7+?**
A: TypeScript 4.7 introduced variance annotations on type parameters. For conditional type inference:

- **Co-variant position** (producing values — return types, read properties): inference creates a **union** of all matched types.
- **Contra-variant position** (consuming values — parameter types, write properties): inference creates an **intersection** of all matched types.

```ts
// Co-variant: return type — union
type ReturnTypes<T> =
  T extends { a(): infer R; b(): infer R }
    ? R : never;
type A = ReturnTypes<{ a(): string; b(): number }>; // string | number

// Contra-variant: parameter type — intersection
type ParamTypes<T> =
  T extends { fn(x: infer P): void }
    ? P : never;
// Used in overload resolution:
type OverloadParams<T> =
  T extends {
    (x: infer P): void;
    (x: infer P): void;
  } ? P : never;
// P = intersection of both parameter types
```

### Section 3: Built-in Utility Types Using Conditional Types & `infer`

**Q10. Which built-in TypeScript utility types use conditional types and `infer`?**
A: Several built-in utilities are implemented with conditional types:

```ts
// ReturnType<T> — return type of a function
type ReturnType<T extends (...args: any) => any> =
  T extends (...args: any) => infer R ? R : any;

// Parameters<T> — tuple of parameter types
type Parameters<T extends (...args: any) => any> =
  T extends (...args: infer P) => any ? P : never;

// ConstructorParameters<T> — constructor parameter tuple
type ConstructorParameters<T extends abstract new (...args: any) => any> =
  T extends abstract new (...args: infer P) => any ? P : never;

// InstanceType<T> — instance type from a constructor
type InstanceType<T extends abstract new (...args: any) => any> =
  T extends abstract new (...args: any) => infer R ? R : any;

// Awaited<T> — unwraps Promise recursively (TS 4.5+)
type Awaited<T> =
  T extends null | undefined ? T :
  T extends object & { then(onfulfilled: infer F, ...args: any[]): any }
    ? F extends (value: infer V, ...args: any[]) => any
      ? Awaited<V>
      : never
    : T;

// NonNullable<T> — removes null and undefined
type NonNullable<T> = T extends null | undefined ? never : T;

// Extract<T, U> — extract union members assignable to U
type Extract<T, U> = T extends U ? T : never;

// Exclude<T, U> — remove union members assignable to U
type Exclude<T, U> = T extends U ? never : T;
```

**Q11. How does `Exclude` and `Extract` work via distributive conditional types?**
A: Both `Exclude` and `Extract` rely on distribution over union members to filter a union:

```ts
type Exclude<T, U> = T extends U ? never : T;
type Extract<T, U> = T extends U ? T : never;

// Example:
type Result1 = Exclude<'a' | 'b' | 'c', 'a' | 'c'>;
// Distributes: Exclude<'a','a'|'c'> | Exclude<'b','a'|'c'> | Exclude<'c','a'|'c'>
// = never | 'b' | never
// = 'b'

type Result2 = Extract<string | number | boolean, string | boolean>;
// = Extract<string,...> | Extract<number,...> | Extract<boolean,...>
// = string | never | boolean
// = string | boolean
```

The key insight: returning `never` in the `true` branch (for `Exclude`) or `false` branch (for `Extract`) effectively removes that union member, since `never | X = X`.

### Section 4: Advanced Patterns

**Q12. How do you build a recursive conditional type?**
A: Conditional types can reference themselves — enabling recursive type transformations. TypeScript 4.1+ supports recursive conditional types directly:

```ts
// Deeply unwrap nested Promises
type DeepAwaited<T> =
  T extends Promise<infer R>
    ? DeepAwaited<R>   // recurse if it's still a Promise
    : T;               // base case: not a Promise

type A = DeepAwaited<Promise<Promise<Promise<string>>>>; // string

// Deep readonly
type DeepReadonly<T> =
  T extends (infer E)[]           ? ReadonlyArray<DeepReadonly<E>> :
  T extends object                 ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;

type B = DeepReadonly<{ a: { b: { c: number[] } } }>;
// { readonly a: { readonly b: { readonly c: ReadonlyArray<number> } } }

// Flatten nested arrays
type FlatArray<T> =
  T extends (infer E)[]
    ? FlatArray<E>  // recurse
    : T;            // base case

type C = FlatArray<string[][][]>; // string
```

**Q13. What is "template literal type inference" with `infer`?**
A: TypeScript 4.1+ allows `infer` inside template literal types — extracting string segments from literal type patterns:

```ts
// Extract route parameters from a URL template
type RouteParams<T extends string> =
  T extends `${string}:${infer Param}/${infer Rest}`
    ? Param | RouteParams<`/${Rest}`>
    : T extends `${string}:${infer Param}`
      ? Param
      : never;

type Params = RouteParams<'/users/:userId/posts/:postId'>;
// 'userId' | 'postId'

// Extract before/after a delimiter
type BeforeColon<T extends string> =
  T extends `${infer Before}:${string}` ? Before : T;
type AfterColon<T extends string> =
  T extends `${string}:${infer After}` ? After : T;

type B = BeforeColon<'hello:world'>; // 'hello'
type C = AfterColon<'hello:world'>;  // 'world'

// Capitalize words using template literal + infer
type CapitalizeWords<T extends string> =
  T extends `${infer Word} ${infer Rest}`
    ? `${Capitalize<Word>} ${CapitalizeWords<Rest>}`
    : Capitalize<T>;

type D = CapitalizeWords<'hello world foo'>; // 'Hello World Foo'
```

**Q14. How do you handle the `never` edge case in distributive conditional types?**
A: Because `never` is an empty union, distributive conditional types applied to `never` immediately distribute over zero members — producing `never` regardless of the branches:

```ts
type IsNeverNaive<T> = T extends never ? true : false;
type A = IsNeverNaive<never>; // never — not 'true'!
// Because: distributing over empty union = no iterations = never

// Fix: prevent distribution by wrapping in tuples
type IsNever<T> = [T] extends [never] ? true : false;
type B = IsNever<never>; // true ✓
type C = IsNever<string>; // false ✓

// Similarly for checking 'any':
type IsAny<T> = 0 extends (1 & T) ? true : false;
// 1 & any = any, and 0 extends any → true
// 1 & string = never, and 0 extends never → false
type D = IsAny<any>;    // true
type E = IsAny<string>; // false
```

**Q15. What are "type-level computations" enabled by conditional types + `infer`?**
A: Conditional types with `infer` enable a form of type-level programming — computing types from other types at compile time. This includes:

```ts
// Length of a tuple
type Length<T extends any[]> = T['length'];
type L = Length<[string, number, boolean]>; // 3

// Zip two tuples together
type Zip<A extends any[], B extends any[]> =
  A extends [infer AH, ...infer AT]
    ? B extends [infer BH, ...infer BT]
      ? [[AH, BH], ...Zip<AT, BT>]
      : []
    : [];
type Z = Zip<[1, 2, 3], ['a', 'b', 'c']>; // [[1, 'a'], [2, 'b'], [3, 'c']]

// Reverse a tuple
type Reverse<T extends any[]> =
  T extends [infer H, ...infer R]
    ? [...Reverse<R>, H]
    : [];
type R = Reverse<[1, 2, 3]>; // [3, 2, 1]

// Convert union to intersection
type UnionToIntersection<U> =
  (U extends any ? (x: U) => void : never) extends (x: infer I) => void
    ? I
    : never;
type UI = UnionToIntersection<{ a: string } | { b: number }>;
// { a: string } & { b: number }
```

### Section 5: Common Pitfalls & Edge Cases

**Q16. What is the "eager evaluation" pitfall in conditional types?**
A: TypeScript evaluates conditional types eagerly when the type argument is fully known, but defers evaluation when the checked type is an unresolved generic parameter. This means within a generic function body, conditional types may not simplify as you'd expect:

```ts
type IsString<T> = T extends string ? 'yes' : 'no';

function test<T>(val: T): IsString<T> {
  // TypeScript can't simplify IsString<T> here because T is generic
  // The conditional type stays "deferred"

  // This DOESN'T work — TypeScript won't narrow IsString<T> for you:
  if (typeof val === 'string') {
    return 'yes'; // Error: Type '"yes"' is not assignable to type 'IsString<T>'
  }
  return 'no'; // Error: same
}

// Fix: use overloads or assertions for the implementation
function testFixed<T>(val: T): IsString<T>;
function testFixed(val: unknown): 'yes' | 'no' {
  return typeof val === 'string' ? 'yes' : 'no';
}
```

This is a common source of confusion — conditional types are powerful for type-level manipulation, but the TypeScript checker doesn't automatically use them to narrow values inside function bodies.

**Q17. What is the "default constraint" of an `infer` variable?**
A: An inferred type variable has an implicit `unknown` constraint unless you add one explicitly. TypeScript 4.7+ allows adding constraints to `infer` variables:

```ts
// TypeScript < 4.7: constraint on infer R not directly supported
type GetString<T> =
  T extends { value: infer R }
    ? R extends string ? R : never  // extra conditional to constrain
    : never;

// TypeScript 4.7+: infer with constraint
type GetStringNew<T> =
  T extends { value: infer R extends string }
    ? R    // R is already constrained to string
    : never;

type A = GetStringNew<{ value: 'hello' }>;    // 'hello'
type B = GetStringNew<{ value: number }>;     // never
type C = GetStringNew<{ value: string | number }>; // never (number doesn't extend string)
```

This makes complex type utilities more concise by eliminating the nested conditional needed to constrain an inferred type.

**Q18. How do conditional types interact with mapped types?**
A: Conditional types are often combined with mapped types to transform object types property by property:

```ts
// Filter object properties by value type
type FilterByType<T, U> = {
  [K in keyof T as T[K] extends U ? K : never]: T[K]
};

type Obj = { a: string; b: number; c: string; d: boolean };
type StringProps = FilterByType<Obj, string>;
// { a: string; c: string }

// Make optional all properties that are strings
type OptionalStrings<T> = {
  [K in keyof T]: T[K] extends string ? T[K] | undefined : T[K]
};

// Create a "nullable" version of each property
type Nullable<T> = {
  [K in keyof T]: T[K] extends object ? Nullable<T[K]> : T[K] | null
};
```

The `as` clause in mapped types (TypeScript 4.1+) accepts a conditional type, enabling key remapping based on value types — a powerful combination for building transformative type utilities.

### Section 6: Scenario / Interview-Style Questions

**Q19. "Explain how `infer` differs from just using a generic type parameter."**
A: A generic type parameter is declared at the function/type level and must be explicitly provided or inferred from an argument. `infer` is declared locally inside a conditional type's `extends` clause and is automatically inferred from the structural pattern match — it doesn't require explicit provision.

```ts
// Generic type parameter — declared at type level, must flow in from outside
type Unwrap<T, R> = T extends Promise<R> ? R : never;
// Problem: caller must provide R — defeats the purpose of extracting it

// infer — declared inside the conditional, automatically matched
type UnwrapInfer<T> = T extends Promise<infer R> ? R : never;
// R is automatically deduced from the structure of T — no extra type arg needed

type A = UnwrapInfer<Promise<string>>; // string — R was inferred as string
```

The key conceptual difference: generic type parameters are holes in a type that must be filled by the caller. `infer` creates a type variable that TypeScript fills automatically by pattern-matching against the type being checked.

**Q20. "When would you use a conditional type vs function overloads?"**
A: The choice depends on whether you need compile-time type-level computation or runtime-level dispatch:

**Use conditional types** when: the output type is deterministically computable from the input type at compile time, and you want the type system to automatically determine the output type. No runtime decision needed.

```ts
// Return type is determined by input type — conditional type is right
type ProcessInput<T> =
  T extends string ? { kind: 'text'; length: number } :
  T extends number ? { kind: 'num'; doubled: number } :
  never;

// But implementing this requires overloads or assertions — conditional type is for CALLERS
```

**Use function overloads** when: you need to express that different call signatures return different types, and you want the compiler to narrow the return type based on argument types. The implementation handles the actual dispatch.

```ts
// Overloads — caller gets the right return type, implementation does the work
function process(input: string): { kind: 'text'; length: number };
function process(input: number): { kind: 'num'; doubled: number };
function process(input: string | number) {
  if (typeof input === 'string') return { kind: 'text', length: input.length };
  return { kind: 'num', doubled: input * 2 };
}
```

In practice, they're complementary: conditional types describe the type relationship, overloads provide the implementation. Many libraries define return types using conditional types and implement them with a single overloaded function signature.

**Q21. "Walk me through implementing `DeepPartial<T>` using conditional types."**
A: `DeepPartial<T>` makes every property at every level of nesting optional:

```ts
type DeepPartial<T> =
  // Is T an array? Make a DeepPartial array
  T extends (infer E)[]
    ? DeepPartial<E>[]
    // Is T an object? Map each property to DeepPartial, making it optional
    : T extends object
      ? { [K in keyof T]?: DeepPartial<T[K]> }
      // T is a primitive — return as-is
      : T;

// Usage:
type Config = {
  server: {
    host: string;
    port: number;
    ssl: { cert: string; key: string };
  };
  logging: { level: string; output: string[] };
};

type PartialConfig = DeepPartial<Config>;
// {
//   server?: {
//     host?: string;
//     port?: number;
//     ssl?: { cert?: string; key?: string };
//   };
//   logging?: { level?: string; output?: (string | undefined)[] };
// }

const config: PartialConfig = {
  server: { port: 3000 } // all other fields optional
};
```

The conditional chain handles three cases: arrays (recurse on element type), objects (map over keys with `?` and recurse on values), and primitives (return directly). The order matters — arrays are objects in JavaScript, so the array check must come first.

## Problem 1 — `ReturnType` (Rebuild from Scratch)

### Problem
Without using TypeScript's built-in `ReturnType`, implement it yourself. The type should extract the return type of a function type `T`.

```ts
type MyReturnType<T> = /* your implementation */;

type A = MyReturnType<() => string>;           // string
type B = MyReturnType<(x: number) => boolean>; // boolean
type C = MyReturnType<string>;                 // never (not a function)
type D = MyReturnType<() => void>;             // void
type E = MyReturnType<<T>(x: T) => T>;         // unknown (generic return)
```

### Pattern Recognition
Classic `infer` application — match against a function type pattern and capture the return type position.

### Key Insight
A function type in TypeScript has the pattern `(...args: any[]) => ReturnType`. The `infer` keyword in the return position captures whatever type appears there. The `...args: any[]` matches any parameter list.

### Step-by-Step Derivation

```ts
// Step 1: What pattern does a function type match?
// (...args: any[]) => R  where R is the return type

// Step 2: Use infer to capture R
type MyReturnType<T> =
  T extends (...args: any[]) => infer R
    ? R      // T is a function — R is the return type
    : never; // T is not a function

// Step 3: Test each case mentally:
// T = () => string         → matches, R = string        → string ✓
// T = (x: number) => bool → matches, R = boolean       → boolean ✓
// T = string               → no match                   → never ✓
// T = () => void           → matches, R = void          → void ✓
```

### Complete Solution

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

// Usage:
type A = MyReturnType<() => string>;           // string
type B = MyReturnType<(x: number) => boolean>; // boolean
type C = MyReturnType<string>;                 // never
type D = MyReturnType<() => void>;             // void
type E = MyReturnType<() => Promise<number>>;  // Promise<number>
type F = MyReturnType<typeof Math.random>;     // number

// Works with complex functions:
declare function fetchUser(id: number): Promise<{ name: string; age: number }>;
type FetchResult = MyReturnType<typeof fetchUser>; // Promise<{ name: string; age: number }>
```

### Type Traces

```ts
// Trace: MyReturnType<(x: number, y: string) => boolean[]>
// T = (x: number, y: string) => boolean[]
// Condition: (x: number, y: string) => boolean[] extends (...args: any[]) => infer R
//   → matches: (x: number, y: string) matches (...args: any[])
//   → R = boolean[]
// Result: boolean[]

// Trace: MyReturnType<never>
// T = never (empty union) → distributes → never
// Result: never

// Trace: MyReturnType<(() => string) | (() => number)>
// Distributes: MyReturnType<() => string> | MyReturnType<() => number>
// = string | number
```

### Edge Cases

```ts
// Async functions:
type G = MyReturnType<async () => string>; // Promise<string>
// (async function types are still "() => Promise<T>" at the type level)

// Generator functions:
function* gen() { yield 1; }
type H = MyReturnType<typeof gen>; // Generator<number, void, unknown>

// Overloaded functions: only the LAST overload signature is matched
declare function overloaded(x: string): string;
declare function overloaded(x: number): number;
type I = MyReturnType<typeof overloaded>; // string | number
// (TypeScript intersects overloads for typeof, so the conditional distributes)
```

### Follow-up Questions
- "What if you want the return type of the LAST overload only?" → Use the `ObtainLastCallSignature` pattern, which exploits the contra-variant position merging of function overloads.
- "How does this differ from the built-in `ReturnType`?" → The built-in adds a constraint `T extends (...args: any) => any` (note: `any` not `any[]`) on the type parameter to prevent calling it with non-function types. The difference is subtle — using `any[]` vs `any` for the rest parameter.

## Problem 2 — `UnpackPromise` — Recursive Unwrapping

### Problem
Implement `UnpackPromise<T>` that recursively unwraps nested Promises, returning the innermost non-Promise type.

```ts
type UnpackPromise<T> = /* your implementation */;

type A = UnpackPromise<string>;                        // string
type B = UnpackPromise<Promise<string>>;               // string
type C = UnpackPromise<Promise<Promise<string>>>;      // string
type D = UnpackPromise<Promise<Promise<Promise<number | boolean>>>>;  // number | boolean
type E = UnpackPromise<string | Promise<number>>;      // string | number (distributes)
```

### Pattern Recognition
Recursive conditional type with `infer` — check if `T` is a `Promise`, extract the inner type, then recurse. Distribution over unions gives us `E` for free.

### Key Insight
`Promise<T>` has the pattern `Promise<infer R>`. If `T` matches, recurse on `R`. If not, return `T` as the base case. The recursion terminates when `T` is no longer a Promise.

### Step-by-Step Derivation

```ts
// Step 1: Base pattern — match a Promise and extract its type parameter
type UnpackPromise<T> =
  T extends Promise<infer R>
    ? R       // it's a Promise — but R might also be a Promise
    : T;      // not a Promise — base case

// UnpackPromise<Promise<Promise<string>>> = Promise<string> (only one level)

// Step 2: Add recursion — recurse on R
type UnpackPromise<T> =
  T extends Promise<infer R>
    ? UnpackPromise<R>  // recurse until not a Promise
    : T;

// UnpackPromise<Promise<Promise<string>>>
// = UnpackPromise<Promise<string>>  (R = Promise<string>)
// = UnpackPromise<string>           (R = string)
// = string                          (not a Promise → base case)
```

### Complete Solution

```ts
type UnpackPromise<T> = T extends Promise<infer R> ? UnpackPromise<R> : T;

// Usage:
type A = UnpackPromise<string>;                               // string
type B = UnpackPromise<Promise<string>>;                      // string
type C = UnpackPromise<Promise<Promise<string>>>;             // string
type D = UnpackPromise<Promise<Promise<number | boolean>>>;   // number | boolean

// Distribution over unions:
type E = UnpackPromise<string | Promise<number>>;
// = UnpackPromise<string> | UnpackPromise<Promise<number>>
// = string | number

// With complex types:
type F = UnpackPromise<Promise<{ name: string; age: number }>>;
// { name: string; age: number }

// In function signatures:
declare function getData(): Promise<Promise<{ id: number }>>;
type GetDataResult = UnpackPromise<ReturnType<typeof getData>>;
// { id: number }
```

```ts
// → UnpackPromise<Promise<Promise<string>>>

// → UnpackPromise<Promise<string>>
```

### Follow-up Questions
- "How does this differ from the built-in `Awaited<T>`?" → `Awaited<T>` handles ANY thenable (objects with a `.then` method), not just `Promise`. It's more robust for real-world async interop. `UnpackPromise` is simpler and works only for `Promise<T>` instances.
- "Can this cause infinite recursion?" → TypeScript has a recursion depth limit (~100 levels). For pathological nesting, it would fail with a "Type instantiation is excessively deep" error. In practice, no real code nests Promises 100 levels deep.

## Problem 3 — `FunctionParameters` and `ArgumentTypes`

### Problem
Implement types to extract individual parameter types from a function:
1. `Parameters<T>` — return all parameters as a tuple (rebuild built-in)
2. `FirstParam<T>` — return the type of the first parameter
3. `LastParam<T>` — return the type of the last parameter
4. `DropFirstParam<T>` — return a tuple of all parameters except the first

```ts
type A = Parameters<(a: string, b: number, c: boolean) => void>;    // [string, number, boolean]
type B = FirstParam<(a: string, b: number, c: boolean) => void>;    // string

type D = DropFirstParam<(a: string, b: number, c: boolean) => void>; // [number, boolean]
```

### Pattern Recognition
`infer` on the `...args` rest parameter captures a tuple of all parameter types. Combined with tuple head/tail patterns from Problem 7.

### Key Insight
`(...args: infer P) => any` captures all parameters as a tuple in `P`. Then use tuple manipulation with `infer` to extract individual elements or sub-tuples.

### Complete Solution

```ts
// 1. All parameters as tuple
type MyParameters<T> =
  T extends (...args: infer P) => any ? P : never;

// 2. First parameter
type FirstParam<T> =
  T extends (first: infer F, ...rest: any[]) => any ? F : never;
// Alternative: head of the parameters tuple
type FirstParam2<T> = MyParameters<T> extends [infer F, ...any[]] ? F : never;

// 3. Last parameter
type LastParam<T> =
  MyParameters<T> extends [...any[], infer L] ? L : never;

// 4. All parameters except the first
type DropFirstParam<T> =
  T extends (first: any, ...rest: infer R) => any ? R : never;
// Alternative:
type DropFirstParam2<T> =
  MyParameters<T> extends [any, ...infer R] ? R : never;

// Usage:
type F1 = (a: string, b: number, c: boolean) => void;

type A = MyParameters<F1>;    // [string, number, boolean]
type B = FirstParam<F1>;      // string
type C = LastParam<F1>;       // boolean
type D = DropFirstParam<F1>;  // [number, boolean]

// Real-world: currying type signature
type Curry<F> =
  F extends (first: infer A, ...rest: infer R) => infer Ret
    ? R extends []
      ? F  // no more args to curry — return as-is
      : (arg: A) => Curry<(...args: R) => Ret>
    : never;

declare function add(a: number, b: number): number;
type CurriedAdd = Curry<typeof add>;
// (arg: number) => (arg: number) => number
```

## Problem 4 — `DeepReadonly` and `DeepPartial`

### Problem
Implement `DeepReadonly<T>` that makes every nested property readonly, and `DeepPartial<T>` that makes every nested property optional. Handle arrays, nested objects, and primitive types correctly.

```ts
type Config = {
  server: { host: string; port: number; ssl: boolean };
  db: { url: string; pool: { min: number; max: number } };
  tags: string[];
};

type A = DeepReadonly<Config>;
// {
//   readonly server: { readonly host: string; readonly port: number; readonly ssl: boolean };
//   readonly db: { readonly url: string; readonly pool: { readonly min: number; readonly max: number } };
//   readonly tags: readonly string[];
// }

type B = DeepPartial<Config>;
// {
//   server?: { host?: string; port?: number; ssl?: boolean };
//   db?: { url?: string; pool?: { min?: number; max?: number } };
//   tags?: (string | undefined)[];  // or string[]? depending on impl
// }
```

### Pattern Recognition
Recursive conditional + mapped types. Check type category in order (array first, then object, then primitive), handle each with recursion. Order matters since arrays are objects.

### Key Insight
The three-case dispatch:
1. `T extends (infer E)[]` — array: make a readonly/partial array of `DeepReadonly<E>`/`DeepPartial<E>`
2. `T extends object` — object: map over keys with modifier, recurse on values
3. Primitive: return `T` as-is

### Complete Solution

```ts
// ── DeepReadonly ─────────────────────────────────────────────────────────

type DeepReadonly<T> =
  // Case 1: T is an array — make it a readonly array of DeepReadonly elements
  T extends (infer E)[]
    ? ReadonlyArray<DeepReadonly<E>>
    // Case 2: T is an object (but not a primitive) — map with readonly
    : T extends object
      ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
      // Case 3: T is a primitive — return as-is
      : T;

// ── DeepPartial ──────────────────────────────────────────────────────────

type DeepPartial<T> =
  // Case 1: T is an array — make each element optionally undefined
  T extends (infer E)[]
    ? (DeepPartial<E> | undefined)[]
    // Case 2: T is an object — make each property optional and recurse
    : T extends object
      ? { [K in keyof T]?: DeepPartial<T[K]> }
      // Case 3: T is a primitive — return as-is
      : T;

// ── Usage ─────────────────────────────────────────────────────────────────

type Config = {
  server: { host: string; port: number };
  tags: string[];
};

type ReadonlyConfig = DeepReadonly<Config>;
// {
//   readonly server: { readonly host: string; readonly port: number };
//   readonly tags: ReadonlyArray<string>;
// }

// Verify readonly:
const config: ReadonlyConfig = { server: { host: 'x', port: 80 }, tags: ['a'] };
config.server.host = 'y'; // Error: cannot assign to readonly property

type PartialConfig = DeepPartial<Config>;
// {
//   server?: { host?: string; port?: number };
//   tags?: (string | undefined)[];
// }

const partial: PartialConfig = {}; // all optional
const partial2: PartialConfig = { server: { port: 3000 } }; // partial nested
```

### Type Traces

```ts
// T = { a: { b: string[] } } — matches 'object' branch
// Result: { readonly a: DeepReadonly<{ b: string[] }> }
//   → { readonly a: DeepReadonly_step2 }
//   DeepReadonly<{ b: string[] }>:
//     T = { b: string[] } — object branch
//     Result: { readonly b: DeepReadonly<string[]> }
//       DeepReadonly<string[]>:
//         T = string[] — array branch (infer E = string)
//         Result: ReadonlyArray<DeepReadonly<string>>
//           DeepReadonly<string>:
//             T = string — not array, not object → string
// Final: { readonly a: { readonly b: ReadonlyArray<string> } } ✓
```

### Edge Cases

```ts

// Note: loses tuple structure — use a more sophisticated implementation for tuples

// Functions: treated as objects (they are), but mapped type on functions = never
// Better to exclude functions from deep transformation:
type DeepReadonlyV2<T> =
  T extends (...args: any[]) => any  // is it a function?
    ? T                              // leave functions alone
    : T extends (infer E)[]
      ? ReadonlyArray<DeepReadonlyV2<E>>
      : T extends object
        ? { readonly [K in keyof T]: DeepReadonlyV2<T[K]> }

type Primitive = string | number | boolean | bigint | symbol | null | undefined;
```

## Problem 5 — `UnionToIntersection` and `UnionToTuple`

### Problem
Implement:
1. `UnionToIntersection<U>` — convert a union type to an intersection
2. Explain why this works using contra-variance

```ts
type A = UnionToIntersection<{ a: string } | { b: number }>;
// { a: string } & { b: number }

type B = UnionToIntersection<string | number>;
// string & number = never (no value is both string and number)

type C = UnionToIntersection<((x: string) => void) | ((x: number) => void)>;
// ((x: string) => void) & ((x: number) => void)
// = a function that accepts both string and number
```

### Pattern Recognition
This is the advanced "contra-variant inference creates intersection" pattern. Requires understanding that function parameter positions are contra-variant — when TypeScript infers `R` from multiple contra-variant positions, it intersects them.

### Key Insight
The trick: convert each union member `U` into a function type `(x: U) => void`. Then infer the parameter type from this intersection of function types. TypeScript infers the parameter as the intersection of all input types because function parameters are contra-variant.

```
Union U = A | B | C
→ Map each to: (x: A) => void | (x: B) => void | (x: C) => void
→ (x: A) => void | (x: B) => void extends (x: infer R) => void
   In a contra-variant position (function parameter), R is inferred as A & B & C
→ R = A & B & C = intersection
```

### Step-by-Step Derivation

```ts
// Step 1: Map union members to function types
// U extends any triggers distribution over U:
// For each member M of union U: (x: M) => void
type Step1<U> = U extends any ? (x: U) => void : never;
// Step1<A | B> = ((x: A) => void) | ((x: B) => void)

// Step 2: Check if Step1 extends a single function type with infer R
// In a union of function types, the parameter position is contra-variant
// TypeScript infers R as the intersection when matching multiple function types
type Step2<U> =
  (U extends any ? (x: U) => void : never) extends (x: infer R) => void
    ? R : never;

// Why intersection? Contra-variance:
// A single function (x: R) => void must be compatible with BOTH (x: A) and (x: B)
// → R must accept both A and B
// → R must be a supertype of both A and B... wait, that's union?
// Actually: a function (x: A|B) => void can be used where (x: A) => void is expected
// But we're going from ((x:A) => void) | ((x:B) => void) to a single (x: infer R) => void
// TypeScript resolves this contra-variantly as intersection: R = A & B
```

### Complete Solution

```ts
type UnionToIntersection<U> =
  // Step 1: distribute U into function types (contra-variant position)
  // Step 2: infer R from the intersection of all these function types
  (U extends any ? (x: U) => void : never) extends (x: infer R) => void
    ? R
    : never;

// Usage:
type A = UnionToIntersection<{ a: string } | { b: number }>;
// { a: string } & { b: number }
// = object that has both 'a' and 'b'

type B = UnionToIntersection<string | number>;
// string & number = never

type C = UnionToIntersection<{ greet(): void } | { greet(name: string): void }>;
// { greet(): void } & { greet(name: string): void }
// = an object with an overloaded greet method

// Practical use: merge option objects
type MergedOptions<T extends object[]> =
  UnionToIntersection<T[number]>; // T[number] = union of all array elements
type D = MergedOptions<[{ timeout: number }, { retries: number }, { verbose: boolean }]>;
// { timeout: number } & { retries: number } & { verbose: boolean }
```

### Type Traces

```ts
// Trace: UnionToIntersection<{ a: string } | { b: number }>
// U = { a: string } | { b: number }

// Step 1: (U extends any ? (x: U) => void : never)
// Distributes:
// = ((x: { a: string }) => void) | ((x: { b: number }) => void)

// Step 2: Does this extend (x: infer R) => void?
// TypeScript needs R such that (x: R) => void is assignable to both:
//   (x: { a: string }) => void  → R must be assignable from { a: string }
//   (x: { b: number }) => void  → R must be assignable from { b: number }
// In contra-variance, R = { a: string } & { b: number }

// Result: { a: string } & { b: number } ✓
```

### Edge Cases

```ts
// never input → empty union → no distribution → never
type E = UnionToIntersection<never>; // never

// Single type → intersection with nothing → itself
type F = UnionToIntersection<string>; // string
// (x: string) => void extends (x: infer R) => void → R = string

// any → intersection involving any = any
type G = UnionToIntersection<any>; // unknown (complex interaction with any)

// Function unions → creates overloaded intersection
type H = UnionToIntersection<(x: string) => string | (x: number) => number>;
// ((x: string) => string) & ((x: number) => number)
// = an overloaded function accepting string or number
```

### Follow-up Questions
- "Why does this use contra-variance? Can you explain contra-variance in simple terms?" → A function `(x: Cat) => void` is assignable to `(x: Animal) => void` — a function that accepts a more general type can substitute for one that accepts a more specific type. Contra-variance means the direction flips. When TypeScript infers from multiple function parameter positions simultaneously, it finds the type that is assignable FROM all positions — which is the intersection.
- "Can you implement `UnionToTuple`?" → Yes, but it requires `UnionToIntersection` to extract the last union member. This is an advanced technique involving `LastInUnion` and recursion — worth knowing exists but rarely needed in production.

## Problem 6 — `ExtractRouteParams` (Template Literal Inference)

### Problem
Implement `ExtractRouteParams<T>` that extracts route parameter names from an Express-style route string as a union of string literal types.

```ts
type A = ExtractRouteParams<'/users/:userId'>;              // 'userId'
```

### Pattern Recognition
Template literal type with `infer` and recursion — match the `:paramName` pattern, extract the param name, recurse on the rest of the string.

### Key Insight
Template literals can be deconstructed with `infer`. The pattern `${string}:${infer Param}/${infer Rest}` matches a string containing `:param/more` and captures both the param name and the rest. Handle the case where the param is at the end (no trailing `/`).

### Step-by-Step Derivation

```ts
// Step 1: Match a single param in the middle of a route
type HasParam<T extends string> =
  T extends `${string}:${infer Param}/${string}` ? Param : never;

// Step 2: Match a param at the END of a route
type HasParamAtEnd<T extends string> =
  T extends `${string}:${infer Param}` ? Param : never;

// Step 3: Combine and recurse for multiple params
// Problem: HasParam only gets the FIRST match, not all
// Need recursion: extract first param, then recurse on the remainder
```

### Complete Solution

```ts
    // Case 2: param at the end of the route (/:param)
    : T extends `${string}/:${infer Param}`
      ? Param
      // Case 3: no more params
      : never;

// 'userId'

type C = ExtractRouteParams<'/static/page'>;

// → 'a' | ExtractRouteParams<'/:b/:c'>
// → 'a' | 'b' | ExtractRouteParams<'/:c'>
// → 'a' | 'b' | 'c' ✓
```

- "How would you type the route builder function that constructs URLs with params?" → `type BuildRoute<T extends string, P extends RouteParamObject<T>> = T extends `${infer Before}:${infer Param}/${infer After}` ? ...` — recursive template replacement.

## Problem 7 — `PickByValue` and `OmitByValue`

### Problem
Implement `PickByValue<T, V>` that picks only properties whose value type is assignable to `V`, and `OmitByValue<T, V>` that omits them.

```ts
type Obj = {
  id: number;
  name: string;
  email: string;
  active: boolean;
  createdAt: Date;
};

type A = PickByValue<Obj, string>;
// { name: string; email: string }

type B = PickByValue<Obj, string | number>;
// { id: number; name: string; email: string }

type C = OmitByValue<Obj, string>;
// { id: number; active: boolean; createdAt: Date }
```

### Pattern Recognition
Mapped type with `as` key remapping + conditional type — remap keys to `never` for properties that don't match the value type filter.

### Key Insight
Use the mapped type `as` clause (TypeScript 4.1+) with a conditional type: if the value type extends the filter type `V`, keep the key; otherwise remap to `never` (which drops the key from the resulting type).

### Complete Solution

```ts
// ── PickByValue ─────────────────────────────────────────────────────────
type PickByValue<T, V> = {
  [K in keyof T as T[K] extends V ? K : never]: T[K]
};
// For each key K: if the value type T[K] extends V, include K; else drop it (never)

// ── OmitByValue ─────────────────────────────────────────────────────────
type OmitByValue<T, V> = {
  [K in keyof T as T[K] extends V ? never : K]: T[K]
};
// Opposite: drop keys where T[K] extends V, keep the rest

// Usage:
type Obj = {
  id: number;
  name: string;
  email: string;
  active: boolean;
  createdAt: Date;
};

type StringProps = PickByValue<Obj, string>;
// { name: string; email: string }

type NonStringProps = OmitByValue<Obj, string>;
// { id: number; active: boolean; createdAt: Date }

type StringOrNumberProps = PickByValue<Obj, string | number>;
// { id: number; name: string; email: string }

// Practical: extract only optional properties
type OptionalKeys<T> = {
  [K in keyof T as undefined extends T[K] ? K : never]: T[K]
};
type RequiredKeys<T> = {
  [K in keyof T as undefined extends T[K] ? never : K]: T[K]
};

type Form = {
  name: string;
  email: string;
  phone?: string;
  age?: number;
};
type OptionalFormFields = OptionalKeys<Form>;   // { phone?: string; age?: number }
type RequiredFormFields = RequiredKeys<Form>;   // { name: string; email: string }

// Flatten intersection types for readability:
type Prettify<T> = { [K in keyof T]: T[K] } & {};
type NicePick = Prettify<PickByValue<Obj, string>>;
// { name: string; email: string }
```

### Type Traces

```ts
// Trace: PickByValue<{ a: string; b: number; c: string }, string>
// Mapped type with as-remapping:
// K = 'a': T['a'] = string, string extends string → keep 'a'
// K = 'b': T['b'] = number, number extends string → false → remap to never → dropped
// K = 'c': T['c'] = string, string extends string → keep 'c'
// Result: { a: string; c: string } ✓

// Trace: PickByValue<{ x: string | number }, string>
// K = 'x': T['x'] = string | number
// Does string | number extend string? NO (number doesn't extend string)
// → 'x' remapped to never → dropped
// Result: {} (empty object)

// So PickByValue picks properties where the value type is EXACTLY assignable to V,
// not properties where V is a subset of the value type.
// To pick properties where the value type OVERLAPS with V, use Extract:
type PickOverlapping<T, V> = {
  [K in keyof T as Extract<T[K], V> extends never ? never : K]: T[K]
};
// Pick properties where T[K] and V have at least one common member
```

### Edge Cases

```ts
// undefined/null in value types:
type WithOptional = { a?: string; b: string; c: string | undefined };
type D = PickByValue<WithOptional, string>;
// { b: string }
// Note: a?: string means type is string | undefined → doesn't extend string
// c: string | undefined → same → doesn't extend string
// Only 'b' has exactly 'string' ✓

// Supertype filter:
type E = PickByValue<Obj, object>;
// object includes Date but not primitives
// createdAt: Date (Date extends object → included)
// NOT: id, name, email, active (primitives)
// But Date also extends object, so:
// { createdAt: Date }

// Function properties:
type WithFn = { fn: () => void; count: number; name: string };
type F = PickByValue<WithFn, (...args: any[]) => any>;
// { fn: () => void }
```

### Follow-up Questions
- "What's the difference between `PickByValue<T, string>` and `Pick<T, { [K in keyof T]: T[K] extends string ? K : never }[keyof T]>`?" → They're equivalent in result, but `PickByValue` using the `as` clause is cleaner and more readable. The latter is the "pre-TS4.1" approach before `as` key remapping was available.
- "How would you implement `KeysOfType<T, V>` that returns just the key names as a union?" → `type KeysOfType<T, V> = { [K in keyof T]: T[K] extends V ? K : never }[keyof T]` — index into the mapped type with `[keyof T]` to convert to a union.

## Quick Reference — Conditional Types & `infer` Cheat Sheet

```
BASIC SYNTAX
  T extends U ? X : Y
  Read: "if T is assignable to U, resolve to X, otherwise Y"

INFER SYNTAX
  T extends SomeGeneric<infer R> ? UseR : Fallback
  Read: "if T matches the pattern SomeGeneric<R>, capture R and use it in the true branch"
  Rule: infer ONLY in extends clause; inferred var ONLY in true branch

DISTRIBUTION
  Triggers when: T is a naked (unwrapped) type parameter AND T is a union
  Effect: each union member is evaluated separately; results are re-unioned
  Prevent: wrap in tuple → [T] extends [U] ? X : Y

KEY PATTERNS
  Extract return type:    T extends (...args: any[]) => infer R ? R : never
  Extract params:         T extends (...args: infer P) => any ? P : never
  Unwrap array:           T extends (infer E)[] ? E : T
  Unwrap promise:         T extends Promise<infer R> ? R : T (recursive for deep)
  Tuple head:             T extends [infer H, ...any[]] ? H : never
  Tuple tail:             T extends [any, ...infer T] ? T : never
  Tuple last:             T extends [...any[], infer L] ? L : never
  Template literal:       T extends `${string}:${infer Param}/${infer Rest}` ? ...
  Union → Intersection:   (U extends any ? (x: U) => void : never) extends (x: infer R) => void ? R : never
  Pick by value:          { [K in keyof T as T[K] extends V ? K : never]: T[K] }

EDGE CASES
  never:  IsNever<T> = [T] extends [never] ? true : false   (prevent distribution)
  any:    IsAny<T>   = 0 extends (1 & T) ? true : false
  both branches fire when checking type is any
  infer constraints (TS 4.7+): infer R extends string

CO-VARIANT vs CONTRA-VARIANT INFERENCE
  Same infer var in co-variant positions (return types) → union of matches
  Same infer var in contra-variant positions (params)   → intersection of matches
```

## Common Bugs Checklist

Before finalizing any conditional type or `infer` usage, verify:

1. **`infer` is only in the `extends` clause** — placing `infer` in the true or false branch is a syntax error. `T extends (infer R extends string) ? R : never` is valid (TS 4.7+ constraint). `T extends string ? infer R : never` is invalid.

2. **Distribution is intended when using union inputs** — if you write `type IsArray<T> = T extends any[] ? true : false`, then `IsArray<string | number[]>` = `false | true` = `boolean`, not `false`. Wrap in `[]` to prevent: `[T] extends [any[]]`.

3. **The `never` distribution trap** — `type Foo<T> = T extends string ? 'yes' : 'no'` applied to `never` returns `never`, not `'no'`. Use `[T] extends [never]` to check for `never`.

4. **Array vs tuple pattern order** — in recursive types, check array pattern `(infer E)[]` before object pattern `object`. Arrays ARE objects; checking `object` first would match arrays before the array branch.

5. **`infer R` scope is ONLY the true branch** — trying to use `R` in the false branch: `T extends Foo<infer R> ? never : R` → `R` in the false branch is an error. Must restructure the logic.

6. **Template literal `infer` greedy matching** — in `T extends `${infer A}:${infer B}` ? ...`, both `A` and `B` are inferred greedily but TypeScript tries the shortest match for `A`. For complex template patterns, test edge cases where delimiters appear multiple times in the string.

The highest-signal answer always starts by identifying the **structural pattern** being matched: "I need to match any function type, so the pattern is `(...args: any[]) => any`, and `infer R` in the return position captures the return type." Then trace through one or two concrete inputs to verify. The advanced questions — `UnionToIntersection`, template literal extraction, distributive `never` handling — are where candidates separate themselves.
