# Generics: Functions, Classes, Constraints (`<T extends SomeType>`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do generics solve and why is `any` an inadequate substitute?**
A: Generics solve the problem of writing code that works correctly across multiple types without sacrificing type safety. Without generics, you face a false choice: either duplicate code for each type (a `reverseStrings` function, a `reverseNumbers` function, a `reverseUsers` function…) or use `any`, which works for all types but destroys type information — the compiler can no longer check correctness:

```typescript
// Without generics: code duplication
function reverseStrings(arr: string[]): string[] { return [...arr].reverse(); }
function reverseNumbers(arr: number[]): number[] { return [...arr].reverse(); }
// Same logic, N copies for N types — maintenance burden, violates DRY

// With `any`: compiles but loses all type information
function reverseAny(arr: any[]): any[] { return [...arr].reverse(); }
const result = reverseAny([1, 2, 3]);
result[0].toUpperCase();  // No compile error! But crashes at runtime.
// TypeScript can't help you here — you've opted out of type checking.

// With generics: one implementation, full type safety
function reverse<T>(arr: T[]): T[] { return [...arr].reverse(); }
const strs = reverse(['a', 'b', 'c']);   // strs: string[]
const nums = reverse([1, 2, 3]);         // nums: number[]
nums[0].toUpperCase();  // Compile error: Property 'toUpperCase' does not exist on type 'number'
// TypeScript preserved the type T through the transformation.
```

The essential distinction: `any` says "I don't care about the type." Generics say "I don't know the type yet, but I'll preserve whatever type you give me." Generics give you flexibility without sacrificing the compiler's ability to catch errors.

**Q2. What is a type parameter and how does it differ from a regular function parameter?**
A: A type parameter (like `T`, `K`, `V`) is a placeholder for a type, declared in angle brackets. Regular parameters hold runtime values; type parameters hold compile-time types:

```typescript
// Regular parameter: holds a value at runtime
function identity(value: string): string { return value; }

// Type parameter: holds a type at compile time
function identity<T>(value: T): T { return value; }
//                ↑           ↑ ↑
//           declared    used  used
//          type param   twice (return type matches input type)

// Multiple type parameters:
function pair<A, B>(first: A, second: B): [A, B] {
    return [first, second];
}
const p = pair('hello', 42);  // p: [string, number]
const q = pair(true, ['x']);   // q: [boolean, string[]]
```

Type parameters exist purely in TypeScript's type system — they are erased at compile time and produce no JavaScript output. The `<T>` syntax is a compile-time mechanism that tells TypeScript "this type will be determined by the caller."

## Section 2: Generic Functions

**Q3. How does TypeScript infer generic type parameters, and when must you specify them explicitly?**
A: TypeScript infers type parameters from the arguments passed to a generic function — usually you don't need to write `<string>` explicitly:

```typescript
function wrap<T>(value: T): { value: T } { return { value }; }

// Inference: TypeScript infers T from the argument
const a = wrap(42);           // T inferred as 42 (literal type), result: { value: 42 }
const b = wrap('hello');      // T inferred as "hello" (literal type)
const c = wrap([1, 2, 3]);    // T inferred as number[], result: { value: number[] }

// Explicit: when inference doesn't give the type you want
const d = wrap<number>(42);   // T explicitly = number (not literal type 42)
const e = wrap<string | number>('hello');  // T explicitly = union

// When you MUST specify explicitly:
function createArray<T>(length: number, fill: T): T[] {
    return Array.from({ length }, () => fill);
}
// No argument to infer from — TypeScript can't infer T from `length`
// If you omit fill, T would be unknown. Must specify:
const arr = createArray<string>(5, 'x');  // ['x', 'x', 'x', 'x', 'x']

// Another case: generic return type with no generic input
function getDefault<T>(): T {
    return undefined as any;  // Caller must specify T:
}
const s = getDefault<string>();  // Must be explicit — no argument to infer from
```

Inference failure happens when TypeScript has insufficient information — no generic arguments, or the generic type only appears in the return type. When inference is wrong (gives a literal type when you wanted a wider type), explicit specification overrides it.

**Q4. What is the difference between a generic function and a function that takes a union type?**
A: A union type says "the argument can be one of these types, and the return type is also one of these types (possibly a different one)." A generic type says "the argument and return type are the same type, and TypeScript tracks which one it is":

```typescript
// Union: loses the connection between input and output types
function processUnion(value: string | number): string | number {
    return value;
}
const result = processUnion('hello');
// result: string | number  — TypeScript forgot it was specifically string
result.toUpperCase();  // Error: 'toUpperCase' doesn't exist on 'string | number'
// We have to narrow (type guard) to use it as string

// Generic: preserves the specific type through the function
function processGeneric<T extends string | number>(value: T): T {
    return value;
}
const result = processGeneric('hello');
// result: 'hello' (literal type!) — TypeScript remembers exactly what was passed
result.toUpperCase();  // Works — TypeScript knows result is string (specifically 'hello')

// The practical implication: generics are for type-preserving transformations
// Use union types when: the function's behavior genuinely differs per type
// Use generics when: the function treats all types the same but must preserve type identity
```

**Q5. What are generic arrow functions in TypeScript, and what is the JSX disambiguation issue?**
A: Generic arrow functions use the same syntax as regular generic functions but with a known syntax collision in `.tsx` files:

```typescript
// Generic arrow function:
const reverse = <T>(arr: T[]): T[] => [...arr].reverse();

// In .tsx files: the compiler confuses <T> with JSX opening tag
// This FAILS in .tsx:
const identity = <T>(value: T): T => value;
// Error: JSX element 'T' has no corresponding closing tag.

// Solutions for .tsx files:
// 1. Add a trailing comma after T (signals "this is a type parameter list, not JSX")
const identity = <T,>(value: T): T => value;

// 2. Add a constraint (also disambiguates from JSX):
const identity = <T extends unknown>(value: T): T => value;

// 3. Use function declaration instead of arrow (no ambiguity):
function identity<T>(value: T): T { return value; }

// 4. Rename to .ts if JSX isn't needed in that file

// The trailing comma approach is the most common fix:
const getFirst = <T,>(arr: T[]): T | undefined => arr[0];
const pair = <A, B>(a: A, b: B): [A, B] => [a, b];  // Multiple params: no issue
```

**Q6. What is function overloading with generics and when does it produce cleaner types than a single generic signature?**
A: Sometimes a function has a different output type depending on the input type, and a single generic signature doesn't capture this relationship clearly. Overloads with generics give callers more precise return types:

```typescript
// Single generic: imprecise — caller gets string | number back
function parse<T extends string | number>(value: string): T {
    // This has a type cast smell — the caller must specify T explicitly
    return Number(value) as any as T;
}

// Better: overloads that capture the specific relationship
function wrapValue(value: string): { type: 'string'; data: string };
function wrapValue(value: number): { type: 'number'; data: number };
function wrapValue(value: string | number) {
    return typeof value === 'string'
        ? { type: 'string' as const, data: value }
        : { type: 'number' as const, data: value };
}
const s = wrapValue('hello');  // { type: 'string'; data: string }
const n = wrapValue(42);       // { type: 'number'; data: number }
// TypeScript knows the specific discriminated union variant without a cast

// Combining overloads WITH generics for maximum precision:
function mapValue<T>(value: T[], transform: (item: T) => string): string[];
function mapValue<T, U>(value: T[], transform: (item: T) => U): U[];
function mapValue<T, U>(value: T[], transform: (item: T) => U): U[] {
    return value.map(transform);
}
const strings = mapValue([1, 2, 3], n => String(n));   // string[]
const numbers = mapValue(['1', '2'], s => parseInt(s)); // number[]
```

## Section 3: Generic Constraints

**Q7. What is `<T extends SomeType>` and what does "extends" mean in a constraint context?**
A: In generic constraints, `extends` does NOT mean the same as class inheritance — it means "is assignable to" or "is a structural subtype of." `<T extends SomeType>` means: "T can be any type, as long as it has at least the structure/members that `SomeType` has." It's an upper bound on what T can be:

```typescript
// Without constraint: T is completely unconstrained — TypeScript knows nothing about it
function getLength<T>(arg: T): number {
    return arg.length;  // Error: Property 'length' does not exist on type 'T'
    // T could be anything — a number, a boolean — neither has .length
}

// With constraint: T must have a `length` property of type number
interface HasLength { length: number; }
function getLength<T extends HasLength>(arg: T): number {
    return arg.length;  // Now valid — TypeScript knows T has .length
}

getLength('hello');          // OK: string has .length
getLength([1, 2, 3]);        // OK: arrays have .length
getLength({ length: 10 });   // OK: satisfies HasLength structurally
getLength(42);               // Error: number doesn't have .length
getLength({ name: 'x' });    // Error: { name: string } missing .length

// "extends" in constraints vs inheritance:
// class Dog extends Animal { }  — Dog IS an Animal, inherits members
// <T extends Animal>           — T must be structurally compatible with Animal
//                               (could be Animal, or Dog, or { name: string; speak(): void })
```

**Q8. What is keyof and how does it work with generic constraints for type-safe property access?**
A: `keyof T` produces a union type of all public property keys of type `T`. Combined with generics, it enables type-safe dynamic property access — one of the most common and powerful generic constraint patterns:

```typescript
// Type-safe property getter
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
    //          ↑
    // Return type T[K] is the type of obj[key] — exact property type preserved
}

const user = { name: 'Alice', age: 30, isAdmin: false };

const name = getProperty(user, 'name');     // type: string
const age = getProperty(user, 'age');       // type: number
const admin = getProperty(user, 'isAdmin'); // type: boolean
getProperty(user, 'email');                 // Error: 'email' not in keyof User

// K extends keyof T ensures:
// 1. key must be a valid property name of obj (no typos)
// 2. The return type is precisely T[K] — the exact type of that property

// Type-safe property setter:
function setProperty<T, K extends keyof T>(obj: T, key: K, value: T[K]): void {
    obj[key] = value;
}
setProperty(user, 'age', 31);      // OK
setProperty(user, 'age', 'old');   // Error: string not assignable to number
setProperty(user, 'name', true);   // Error: boolean not assignable to string

// Picking subset of properties type-safely:
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
    return keys.reduce((acc, key) => {
        acc[key] = obj[key];
        return acc;
    }, {} as Pick<T, K>);
}
const partial = pick(user, ['name', 'age']);
// type: { name: string; age: number }
// isAdmin is excluded — TypeScript knows exactly which keys were picked
```

**Q9. What is a conditional type constraint and when do you use `T extends X ? Y : Z`?**
A: Conditional types use the ternary operator at the type level to select one type or another based on whether a type satisfies a constraint:

```typescript
// Basic conditional type:
type IsString<T> = T extends string ? true : false;
type A = IsString<string>;  // true
type B = IsString<number>;  // false
type C = IsString<'hello'>; // true (literal type extends string)

// Practical: extract the element type from an array
type ElementOf<T> = T extends (infer U)[] ? U : never;
type E1 = ElementOf<string[]>;  // string
type E2 = ElementOf<number[]>;  // number
type E3 = ElementOf<string>;    // never (string is not an array)

// Unwrap a Promise:
type Awaited<T> = T extends Promise<infer U> ? Awaited<U> : T;
type P1 = Awaited<Promise<string>>;           // string
type P2 = Awaited<Promise<Promise<number>>>;  // number (recursive unwrap)

// Conditional types distribute over unions:
type ToArray<T> = T extends any ? T[] : never;
type D = ToArray<string | number>;  // string[] | number[]
// Not (string | number)[] — distributes over each union member

// NonNullable implementation:
type NonNullable<T> = T extends null | undefined ? never : T;
type N = NonNullable<string | null | undefined>;  // string

// Function return type extraction:
type ReturnType<T extends (...args: any) => any> =
    T extends (...args: any) => infer R ? R : never;
type R = ReturnType<() => Promise<string>>;  // Promise<string>
```

**Q10. What is the `infer` keyword and how does it extract type components from complex types?**
A: `infer` declares a type variable that TypeScript infers from matching a type pattern. It only works inside conditional type expressions and lets you "capture" a component of a matched type:

```typescript
// infer basic pattern:
type FirstArgument<T> = T extends (first: infer F, ...rest: any[]) => any ? F : never;
type FA = FirstArgument<(x: string, y: number) => void>;  // string
type FB = FirstArgument<(n: number) => boolean>;           // number

// Extract Promise value:
type UnwrapPromise<T> = T extends Promise<infer Value> ? Value : T;
type UV = UnwrapPromise<Promise<{ id: number }>>;  // { id: number }

// Extract tuple element types:
type Head<T extends any[]> = T extends [infer H, ...any[]] ? H : never;
type Tail<T extends any[]> = T extends [any, ...infer T] ? T : never;
type H = Head<[string, number, boolean]>;  // string
type Tl = Tail<[string, number, boolean]>; // [number, boolean]

// Extract the value type from a Map:
type MapValue<T> = T extends Map<any, infer V> ? V : never;
type MV = MapValue<Map<string, { id: number }>>;  // { id: number }

// Multiple infer in one conditional:
type ChangeFirstArg<T, NewFirst> =
    T extends (first: any, ...rest: infer Rest) => infer Return
        ? (first: NewFirst, ...rest: Rest) => Return
        : never;
type CFn = ChangeFirstArg<(x: string, y: number) => boolean, Date>;
// (first: Date, y: number) => boolean
```

## Section 4: Generic Classes

**Q11. How do generic classes work and what is their relationship to generic interfaces?**
A: Generic classes apply type parameters to the entire class, making all members use consistent types. The type parameter is part of the class's contract:

```typescript
// Generic class: type parameter applies to all members
class Stack<T> {
    private items: T[] = [];

    push(item: T): void {
        this.items.push(item);
    }

    pop(): T | undefined {
        return this.items.pop();
    }

    peek(): T | undefined {
        return this.items[this.items.length - 1];
    }

    get size(): number {
        return this.items.length;
    }

    isEmpty(): boolean {
        return this.items.length === 0;
    }
}

const numStack = new Stack<number>();
numStack.push(1);
numStack.push('hello');  // Error: string not assignable to number

const strStack = new Stack<string>();
strStack.push('hello');   // OK
const top = strStack.peek();  // top: string | undefined — type preserved

// Implementing a generic interface:
interface Repository<T, ID> {
    findById(id: ID): Promise<T | null>;
    findAll(): Promise<T[]>;
    save(entity: T): Promise<T>;
    delete(id: ID): Promise<void>;
}

class UserRepository implements Repository<User, string> {
    async findById(id: string): Promise<User | null> { ... }
    async findAll(): Promise<User[]> { ... }
    async save(user: User): Promise<User> { ... }
    async delete(id: string): Promise<void> { ... }
}

// The type parameters are fixed when you implement the interface —
// the implementing class is no longer generic (it specifies concrete types).
// Alternatively, the implementing class can itself be generic:
class GenericRepository<T, ID> implements Repository<T, ID> {
    // T and ID are still open — further specialized by the concrete subclass
}
```

**Q12. What are static members and generic type parameters — why can't static members use the class's type parameter?**
A: Static members belong to the class itself, not to instances. Generic type parameters are resolved per-instance at instantiation time — but static members exist before any instance is created, so they have no instance type parameter to use:

```typescript
class Container<T> {
    static defaultValue: T;  // Error: Static members cannot reference class type parameters.

    // Why? Consider:
    // Container<string>.defaultValue vs Container<number>.defaultValue
    // These would be the SAME static property (there's only one Container class in JS)
    // but with different types — impossible.

    // Static methods can have their OWN type parameters:
    static create<U>(value: U): Container<U> {
        return new Container(value);
    }

    // Or use concrete types:
    static empty: Container<unknown> = new Container(undefined);

    constructor(public value: T) {}
}

// Correct usage of static with own generic parameter:
Container.create<string>('hello');  // Container<string>
Container.create(42);               // Container<number> (inferred)

// The pattern for "default value per type" uses a different approach:
class TypedRegistry<T> {
    private static instances = new Map<string, TypedRegistry<any>>();

    static getInstance<U>(key: string): TypedRegistry<U> {
        if (!TypedRegistry.instances.has(key)) {
            TypedRegistry.instances.set(key, new TypedRegistry<U>());
        }
        return TypedRegistry.instances.get(key)!;
    }

    private items = new Map<string, T>();
    register(id: string, item: T): void { this.items.set(id, item); }
    get(id: string): T | undefined { return this.items.get(id); }
}
```

**Q13. How do you use generic constraints in classes, and how do you extend a generic class?**
A: Generic classes can constrain their type parameters and be extended by more specific classes:

```typescript
// Constrained generic class:
interface Identifiable {
    id: string;
}

class EntityStore<T extends Identifiable> {
    private store = new Map<string, T>();

    add(entity: T): void {
        this.store.set(entity.id, entity);  // Safe: T has .id because T extends Identifiable
    }

    findById(id: string): T | undefined {
        return this.store.get(id);
    }

    getAll(): T[] {
        return Array.from(this.store.values());
    }
}

interface User extends Identifiable {
    name: string;
    email: string;
}

const userStore = new EntityStore<User>();
userStore.add({ id: '1', name: 'Alice', email: 'alice@example.com' });
const user = userStore.findById('1');  // user: User | undefined

// Extending a generic class — three patterns:
// 1. Subclass fixes the type parameter:
class UserEntityStore extends EntityStore<User> {
    // T is now always User in this class
    findByEmail(email: string): User | undefined {
        return this.getAll().find(u => u.email === email);
    }
}

// 2. Subclass keeps it generic (narrowed constraint):
class TimestampedStore<T extends Identifiable & { createdAt: Date }>
    extends EntityStore<T> {
    findRecent(after: Date): T[] {
        return this.getAll().filter(e => e.createdAt > after);
    }
}

// 3. Subclass adds its own type parameters:
class MappedStore<T extends Identifiable, Summary> extends EntityStore<T> {
    constructor(private summarize: (entity: T) => Summary) {
        super();
    }
    getSummary(id: string): Summary | undefined {
        const entity = this.findById(id);
        return entity ? this.summarize(entity) : undefined;
    }
}
```

## Section 5: Advanced Generic Patterns

**Q14. What are utility types and how are they implemented using generics?**
A: TypeScript's built-in utility types are generic types that transform other types. Understanding their implementation reveals how generics, `keyof`, conditional types, and `infer` work together:

```typescript
// Partial<T>: makes all properties optional
type Partial<T> = {
    [K in keyof T]?: T[K];
};
type PartialUser = Partial<User>;  // { name?: string; age?: number; ... }

// Required<T>: makes all properties required
type Required<T> = {
    [K in keyof T]-?: T[K];  // -? removes optionality
};

// Readonly<T>: makes all properties readonly
type Readonly<T> = {
    readonly [K in keyof T]: T[K];
};

// Pick<T, K>: extracts a subset of properties
type Pick<T, K extends keyof T> = {
    [P in K]: T[P];
};
type NameAndAge = Pick<User, 'name' | 'age'>;  // { name: string; age: number }

// Omit<T, K>: excludes specific properties
type Omit<T, K extends keyof T> = Pick<T, Exclude<keyof T, K>>;
type WithoutAge = Omit<User, 'age'>;  // { name: string; email: string; ... }

// Record<K, V>: object type with specific keys and values
type Record<K extends keyof any, V> = { [P in K]: V };
type RoleMap = Record<'admin' | 'user' | 'guest', { permissions: string[] }>;

// Exclude<T, U>: removes union members assignable to U
type Exclude<T, U> = T extends U ? never : T;
type WithoutString = Exclude<string | number | boolean, string>;  // number | boolean

// Extract<T, U>: keeps only union members assignable to U
type Extract<T, U> = T extends U ? T : never;
type OnlyString = Extract<string | number | boolean, string | number>;  // string | number

// NonNullable<T>: removes null and undefined
type NonNullable<T> = T extends null | undefined ? never : T;

// ReturnType<T>: extracts function return type
type ReturnType<T extends (...args: any) => any> =
    T extends (...args: any) => infer R ? R : any;

// Parameters<T>: extracts function parameter types as tuple
type Parameters<T extends (...args: any) => any> =
    T extends (...args: infer P) => any ? P : never;
type P = Parameters<(name: string, age: number) => void>;  // [string, number]

// ConstructorParameters<T>: extracts constructor parameter types
type ConstructorParameters<T extends new (...args: any) => any> =
    T extends new (...args: infer P) => any ? P : never;

// InstanceType<T>: extracts the instance type of a constructor
type InstanceType<T extends new (...args: any) => any> =
    T extends new (...args: any) => infer R ? R : any;
```

**Q15. What are mapped types and how do they work with generic type parameters?**
A: Mapped types iterate over the keys of a type and transform each property — they're the foundation of most utility types:

```typescript
// Basic mapped type pattern:
// { [K in KeysType]: ValueType }

// Transforming property types:
type Stringify<T> = {
    [K in keyof T]: string;  // every property becomes string
};
type StringUser = Stringify<{ name: string; age: number }>;
// { name: string; age: string }

// Key remapping (as clause, TypeScript 4.1+):
type Getters<T> = {
    [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
type UserGetters = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }

// Filtering keys via conditional type in as clause:
type OnlyStringProperties<T> = {
    [K in keyof T as T[K] extends string ? K : never]: T[K];
};
type StringOnly = OnlyStringProperties<{ name: string; age: number; active: boolean }>;
// { name: string }  — age and active are filtered out

// Deep partial (recursive mapped type):
type DeepPartial<T> = {
    [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
type DP = DeepPartial<{ user: { name: string; address: { city: string } } }>;
// { user?: { name?: string; address?: { city?: string } } }

// Making specific keys required, rest optional (Partial + Required combination):
type PartialExcept<T, K extends keyof T> = Omit<Partial<T>, K> & Required<Pick<T, K>>;
type UserDraft = PartialExcept<User, 'name'>;
// { name: string; age?: number; email?: string }
```

**Q16. What is variance in generic types — covariance, contravariance, and invariance?**
A: Variance describes how a generic type `Box<T>` relates to its type argument when types have a subtype relationship. If `Dog extends Animal`, how does `Box<Dog>` relate to `Box<Animal>`?

```typescript
// Setup: type hierarchy
class Animal { name: string = ''; }
class Dog extends Animal { bark(): void {} }
// Dog is a subtype of Animal (Dog extends Animal)

// COVARIANCE: if Dog extends Animal, then Box<Dog> extends Box<Animal>
// "If a type is a subtype, the container is also a subtype"
// Read-only containers are covariant:
type ReadonlyBox<T> = { readonly value: T };
const dogBox: ReadonlyBox<Dog> = { value: new Dog() };
const animalBox: ReadonlyBox<Animal> = dogBox;  // OK: covariant — safe to read
// Safe because: if you read from a ReadonlyBox<Dog>, you get a Dog (which is an Animal)

// CONTRAVARIANCE: if Dog extends Animal, then Consumer<Animal> extends Consumer<Dog>
// "If a type is a subtype, the consumer of that type is a supertype"
// Write-only (consumer) containers are contravariant:
type Consumer<T> = { consume: (value: T) => void };
const animalConsumer: Consumer<Animal> = { consume: (a: Animal) => {} };
const dogConsumer: Consumer<Dog> = animalConsumer;  // OK: contravariant — safe to write
// Safe because: a Consumer<Animal> can accept any Animal, including a Dog

// INVARIANCE: a read-write container is invariant — neither assignment is safe
class Box<T> { constructor(public value: T) {} }
const dogB = new Box(new Dog());
const animalB: Box<Animal> = dogB;  // Error! Not safe — can write non-Dog Animals:
// animalB.value = new Animal();    // would corrupt dogB if assignment were allowed

// TypeScript's function variance:
// Function parameters are contravariant (in strict mode, checked via --strictFunctionTypes)
type Handler<T> = (value: T) => void;
const handleAnimal: Handler<Animal> = (a) => {};
const handleDog: Handler<Dog> = handleAnimal;  // OK: Handler<Animal> extends Handler<Dog>
// A function that accepts Animal accepts Dog too (Dog IS an Animal)

// Function return types are covariant:
type Provider<T> = () => T;
const provideDog: Provider<Dog> = () => new Dog();
const provideAnimal: Provider<Animal> = provideDog;  // OK: Provider<Dog> extends Provider<Animal>
// A function returning Dog returns an Animal too (Dog IS an Animal)
```

## Section 6: Common Patterns in Production Code

**Q17. What is the generic "builder" pattern and how does TypeScript track its state through the build chain?**
A: Generic builders use the type system to track which properties have been set, making invalid builds compile-time errors:

```typescript
// Simple: a builder that becomes more specific as you chain
class QueryBuilder<T extends object, Selected extends keyof T = never> {
    private filters: Partial<T> = {};
    private selectedKeys: (keyof T)[] = [];

    where<K extends keyof T>(key: K, value: T[K]): QueryBuilder<T, Selected> {
        this.filters[key] = value;
        return this;
    }

    select<K extends keyof T>(
        ...keys: K[]
    ): QueryBuilder<T, Selected | K> {
        this.selectedKeys.push(...keys);
        return this as QueryBuilder<T, Selected | K>;
    }

    build(): Pick<T, Selected> extends never
        ? T[]
        : Pick<T, Selected>[] {
        // ...implementation
        return [] as any;
    }
}

interface User {
    id: number;
    name: string;
    email: string;
    age: number;
}

const query = new QueryBuilder<User>()
    .where('age', 30)
    .select('name', 'email');
// query: QueryBuilder<User, 'name' | 'email'>

const results = query.build();
// results: Pick<User, 'name' | 'email'>[] = { name: string; email: string }[]
```

**Q18. What is the "generic event emitter" pattern and how does it provide type-safe event handling?**
A: A typed event emitter uses mapped types to ensure that event names and their payload types are always consistent:

```typescript
// Type-safe event emitter using generics and mapped types
type EventMap = Record<string, any>;

class TypedEventEmitter<Events extends EventMap> {
    private listeners: {
        [K in keyof Events]?: Array<(payload: Events[K]) => void>;
    } = {};

    on<K extends keyof Events>(
        event: K,
        listener: (payload: Events[K]) => void
    ): this {
        if (!this.listeners[event]) {
            this.listeners[event] = [];
        }
        this.listeners[event]!.push(listener);
        return this;
    }

    off<K extends keyof Events>(
        event: K,
        listener: (payload: Events[K]) => void
    ): this {
        this.listeners[event] = this.listeners[event]?.filter(l => l !== listener);
        return this;
    }

    emit<K extends keyof Events>(event: K, payload: Events[K]): void {
        this.listeners[event]?.forEach(listener => listener(payload));
    }
}

// Usage: define all events and their payload types
interface AppEvents {
    userLoggedIn: { userId: string; timestamp: Date };
    orderCreated: { orderId: string; items: string[]; total: number };
    pageViewed: { url: string; duration: number };
}

const emitter = new TypedEventEmitter<AppEvents>();

// All of these are fully type-safe:
emitter.on('userLoggedIn', ({ userId, timestamp }) => {
    console.log(userId, timestamp);  // userId: string, timestamp: Date
});

emitter.emit('orderCreated', {
    orderId: 'abc',
    items: ['item1'],
    total: 99.99
});

emitter.emit('userLoggedIn', { userId: 123 });  // Error: number not assignable to string
emitter.on('nonexistent', () => {});            // Error: 'nonexistent' not in AppEvents
```

**Q19. What is the "generic middleware/pipeline" pattern for type-safe transformations?**
A: Pipelines transform data through a series of steps, with generics tracking how the type changes at each step:

```typescript
// Middleware pipeline: input type flows through transformations
type Middleware<In, Out> = (input: In) => Out | Promise<Out>;

class Pipeline<T> {
    constructor(private value: T | Promise<T>) {}

    pipe<U>(fn: Middleware<T, U>): Pipeline<U> {
        const next = Promise.resolve(this.value).then(fn);
        return new Pipeline<U>(next);
    }

    async run(): Promise<T> {
        return Promise.resolve(this.value);
    }
}

// Usage: type changes at each transformation step
const result = await new Pipeline({ id: 1, name: 'Alice' })
    .pipe(user => ({ ...user, displayName: user.name.toUpperCase() }))
    // now: { id: number; name: string; displayName: string }
    .pipe(async user => {
        const permissions = await fetchPermissions(user.id);
        return { ...user, permissions };
    })
    // now: { id: number; name: string; displayName: string; permissions: string[] }
    .run();

// The type of `result` is inferred through the entire chain
// TypeScript knows the exact shape at each step
```

## Section 7: Inference and Edge Cases

**Q20. How does TypeScript infer generic types from complex nested structures?**
A: TypeScript's type inference is remarkably powerful for nested generics, but has specific rules and limits:

```typescript
// Inferring from nested generic arguments:
function extractId<T extends { id: K }, K>(objects: T[]): K[] {
    return objects.map(obj => obj.id);
}

const ids = extractId([{ id: 1, name: 'Alice' }, { id: 2, name: 'Bob' }]);
// K inferred as number, T inferred as { id: number; name: string }
// ids: number[]

// Inferring from callback argument types:
function transform<T, U>(
    arr: T[],
    callback: (item: T, index: number) => U
): U[] {
    return arr.map(callback);
}

const lengths = transform(['hello', 'world'], (s) => s.length);
// T inferred as string (from arr type), U inferred as number (from callback return)
// lengths: number[]

// Context-sensitive typing — TypeScript uses the expected type to infer:
const handlers: { onClick: (event: MouseEvent) => void } = {
    onClick: (e) => console.log(e.clientX),  // e inferred as MouseEvent from context
};

// When inference fails and you need to help:
function createPair<T, U>(a: T, b: U): { first: T; second: U } {
    return { first: a, second: b };
}
// This works fine with inference:
const p = createPair(1, 'hello');  // { first: number; second: string }

// But what if you want to specify one and infer the other? Partial explicit not possible:
// createPair<number>('hello', 'world')  — must specify both or neither

// Workaround: separate the type parameter into a curried function:
function createPairFirst<T>(a: T) {
    return function<U>(b: U): { first: T; second: U } {
        return { first: a, second: b };
    };
}
const makePair = createPairFirst<number>(42);
const pair = makePair('hello');  // { first: number; second: string }
// Specified T = number explicitly, U inferred from 'hello' as string
```

**Q21. What are some common generic pitfalls and anti-patterns?**
A: Generics can be misused in ways that reduce clarity without adding value:

```typescript
// ANTI-PATTERN 1: Generic when union type is clearer
// Unnecessary generic:
function process<T extends string | number>(value: T): void {
    if (typeof value === 'string') { /* ... */ }
    if (typeof value === 'number') { /* ... */ }
}
// Better — if you don't need to preserve the exact type, just use union:
function process(value: string | number): void { /* ... */ }

// ANTI-PATTERN 2: Too-unconstrained generic
function badGeneric<T>(value: T): T {
    // Can't do anything useful with T — no constraints
    return value.toString() as any;  // Fighting the type system
}

// ANTI-PATTERN 3: Generic used like any
function almostAny<T = any>(value: T): T { return value; }
// T defaults to any — defeats the purpose. Use unknown or a real constraint.

// ANTI-PATTERN 4: Overusing generics when a specific type is always meant
// If this function ALWAYS works with users, don't make it generic:
function getUser<T>(id: string): Promise<T> { /* ... */ }
// Better:
function getUser(id: string): Promise<User> { /* ... */ }

// ANTI-PATTERN 5: Too many type parameters making signatures unreadable
function doSomething<A, B, C, D, E, F>(a: A, b: B, c: C): [D, E, F] { /* ... */ }
// This is a design smell — split into smaller functions

// CORRECT PATTERN: generic only when you need to preserve and relate types
// These are all valid uses of generics:
function identity<T>(x: T): T { return x; }  // preserve exact type
function first<T>(arr: T[]): T | undefined { return arr[0]; }  // preserve element type
function map<T, U>(arr: T[], fn: (x: T) => U): U[]  // transform type A to type B
function zip<T, U>(a: T[], b: U[]): [T, U][]  // combine two types
```

## Section 8: Scenario-Based Questions

**Q22. "Implement a type-safe `deepGet` function that retrieves nested properties using a path array."**
A: This requires recursive conditional types to build the expected return type:

```typescript
// Define the recursive type that follows a path through an object
type DeepGet<T, Path extends string[]> =
    Path extends [infer First, ...infer Rest]
        ? First extends keyof T
            ? Rest extends string[]
                ? DeepGet<T[First & keyof T], Rest>
                : T[First & keyof T]
            : never
        : T;

function deepGet<T extends object, Path extends string[]>(
    obj: T,
    path: [...Path]  // 'as const' tuple inference
): DeepGet<T, Path> {
    return path.reduce((current: any, key) => current?.[key], obj) as any;
}

// Usage:
const config = {
    database: {
        primary: {
            host: 'localhost',
            port: 5432
        }
    },
    cache: {
        ttl: 300
    }
};

const host = deepGet(config, ['database', 'primary', 'host']);
// host: string — TypeScript traced the path

const port = deepGet(config, ['database', 'primary', 'port']);
// port: number

const ttl = deepGet(config, ['cache', 'ttl']);
// ttl: number

deepGet(config, ['database', 'nonexistent']);
// Return type: never — TypeScript knows this path doesn't exist
```

**Q23. "Design a typed API client where route types are inferred from a route definition object."**
A: This pattern is used by tRPC, Hono, and similar frameworks to provide end-to-end type safety:

```typescript
// Define route shapes
type RouteDefinition = {
    [path: string]: {
        input?: unknown;
        output: unknown;
    };
};

// Build a typed client from route definitions
type ApiClient<Routes extends RouteDefinition> = {
    [Path in keyof Routes]: Routes[Path]['input'] extends undefined
        ? () => Promise<Routes[Path]['output']>
        : (input: Routes[Path]['input']) => Promise<Routes[Path]['output']>;
};

function createClient<Routes extends RouteDefinition>(
    baseUrl: string,
    routes: Routes  // Route definition is just for type inference
): ApiClient<Routes> {
    return new Proxy({} as ApiClient<Routes>, {
        get(_, path: string) {
            return async (input?: unknown) => {
                const response = await fetch(`${baseUrl}/${path}`, {
                    method: input ? 'POST' : 'GET',
                    body: input ? JSON.stringify(input) : undefined,
                    headers: { 'Content-Type': 'application/json' }
                });
                return response.json();
            };
        }
    });
}

// Define your API's route shapes
const routeSchema = {
    'users/list': { output: [] as Array<{ id: string; name: string }> },
    'users/create': {
        input: {} as { name: string; email: string },
        output: {} as { id: string; name: string; email: string }
    },
    'users/delete': {
        input: {} as { id: string },
        output: {} as { success: boolean }
    }
} satisfies RouteDefinition;

const client = createClient('https://api.example.com', routeSchema);

// Fully typed — TypeScript infers input and output types:
const users = await client['users/list']();
// users: Array<{ id: string; name: string }>

const created = await client['users/create']({ name: 'Alice', email: 'a@example.com' });
// created: { id: string; name: string; email: string }

await client['users/create']({ name: 'Alice' });  // Error: 'email' is required
await client['users/list']({ extra: true });        // Error: no argument expected
```

**Q24. "What does this code output, and what is the type of `result`?"**

```typescript
type UnwrapArray<T> = T extends (infer U)[] ? UnwrapArray<U> : T;

function flatten<T>(arr: T[]): UnwrapArray<T[]> {
    return arr.flat(Infinity) as any;
}

const nested = [[1, 2], [3, [4, 5]]];
const result = flatten(nested);
```

A: Tracing the type resolution:

`nested` is inferred as `(number[] | (number | number[])[])[]` by TypeScript (it struggles with deeply nested arrays without explicit annotation — in practice TypeScript infers `number[][]` for simple cases).

For a cleaner analysis, consider:
```typescript
const nested: number[][][] = [[[1, 2], [3, 4]]];
const result = flatten(nested);
// T = number[][][]
// UnwrapArray<number[][][]>
// = number[][][] extends (infer U)[] ? UnwrapArray<U> : number[][][]
// = UnwrapArray<number[][]>    (U = number[][])
// = UnwrapArray<number[]>      (U = number[])
// = UnwrapArray<number>        (U = number)
// = number (not an array, base case)
// result: number
```

`UnwrapArray` recursively unwraps arrays until it reaches a non-array type. The `result`'s type is the innermost element type — `number` in this case. The runtime value is `[1, 2, 3, 4]` (the flat array).

Note: TypeScript's recursive type evaluation has a depth limit (typically around 50 levels) — very deeply nested types can cause "type instantiation is excessively deep" errors.

## Quick Reference Table

| Syntax | Name | Purpose |
|---|---|---|
| `<T>` | Type parameter declaration | Declares a type variable |
| `<T extends SomeType>` | Constrained type parameter | T must be assignable to SomeType |
| `<T = DefaultType>` | Default type parameter | T defaults to DefaultType if not specified |
| `keyof T` | Key query | Union of T's property keys |
| `T[K]` | Indexed access | Type of T's property K |
| `[K in keyof T]: ...` | Mapped type | Transforms each property of T |
| `T extends X ? Y : Z` | Conditional type | Type-level ternary |
| `T extends X ? infer U : Z` | Infer in conditional | Extract type component U from T |
| `Partial<T>` | Make all optional | `{ [K in keyof T]?: T[K] }` |
| `Required<T>` | Make all required | `{ [K in keyof T]-?: T[K] }` |
| `Readonly<T>` | Make all readonly | `{ readonly [K in keyof T]: T[K] }` |
| `Pick<T, K>` | Select properties | `{ [P in K]: T[P] }` |
| `Omit<T, K>` | Exclude properties | `Pick<T, Exclude<keyof T, K>>` |
| `Record<K, V>` | Key-value map type | `{ [P in K]: V }` |
| `ReturnType<T>` | Function return type | Via infer in conditional |
| `Parameters<T>` | Function params tuple | Via infer in conditional |

**Tip for interviews:** Five things separate strong candidates on TypeScript generics: (1) explaining **why `any` is inadequate** precisely (Q1) — not just "generics are better than any" but articulating that `any` destroys type information while generics preserve it, so the compiler can still catch errors; (2) knowing **`keyof T` + indexed access `T[K]`** as a pair (Q8) — `K extends keyof T` enabling type-safe property access is the single most common production generic pattern and being able to write and explain it on demand is a strong signal; (3) being precise about **what `extends` means in constraints** (Q7) — it means "structurally assignable to," not "inherits from" — this distinction matters for structural typing and often comes up in interviews with candidates from Java/C# backgrounds; (4) understanding **why static members can't use class type parameters** (Q12) with a clear explanation (static members belong to the class, not instances; there's only one class object at runtime regardless of how many type parameters exist); and (5) being able to implement a **simple utility type from scratch** (Q14) — writing `Pick<T, K>` or `Partial<T>` by hand demonstrates real understanding of mapped types and `keyof`, not just memorization of the built-in types.
