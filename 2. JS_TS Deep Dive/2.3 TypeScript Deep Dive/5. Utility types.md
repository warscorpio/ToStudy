## Topic A: Property Transformation Utilities

### Section A1: Mapped Types and Modifiers

**Q1. What is a mapped type, and what are its three structural components?**

A: A mapped type creates a new object type by iterating over a set of keys and defining a value type for each. The syntax `{ [K in KeyType]: ValueType }` has three components: **(1) the key iterator** `K in KeyType` — `K` is a type variable that takes on each member of `KeyType` in turn (typically `keyof T`, a union of string literal types); **(2) the key variable** `K` — available on both the left side (the key name) and the right side (to index into `T[K]`); **(3) the value type** `ValueType` — an expression using `K` and the source type `T` to compute the property's type. Optionally, mapping modifiers (`?`, `-?`, `readonly`, `-readonly`) appear between `{` and `[K in ...]` to mutate property attributes. Every built-in transformation utility (`Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`) is implemented as a mapped type — understanding the template unlocks all of them.

```ts
// General form:
{ [K in KeyType]?: ValueType }      // optional modifier
{ readonly [K in KeyType]: ValueType } // readonly modifier
{ [K in keyof T]: T[K] }            // identity (copy of T)

// Example — annotate every property with its key name:
type Annotated<T> = {
  [K in keyof T]: { key: K; value: T[K] };
};
type X = Annotated<{ a: number; b: string }>;
// → { a: { key: 'a'; value: number }; b: { key: 'b'; value: string } }
```

**Q2. What does `Partial<T>` do, what mapped type implements it, and what is its common misuse?**

A: `Partial<T>` produces a type identical to `T` but with every property made optional (all `?`). Implementation: `{ [K in keyof T]?: T[K] }` — the `?` after `]` is the optional modifier, applied to every key in the iteration. Common misuse: using `Partial<T>` as a function parameter type when the intent is a "partial update" — this is correct, but it hides that `{}` (empty object) is also assignable, so any required-property check must be done at runtime. `Partial` is also shallow — nested object properties remain as they were; `{ a: { b: string } }` becomes `{ a?: { b: string } }`, not `{ a?: { b?: string } }`. For deeply nested optional types, a recursive `DeepPartial` is needed.

```ts
type Partial<T> = {
  [K in keyof T]?: T[K];
};

interface User { id: number; name: string; email: string; }

type PartialUser = Partial<User>;
// { id?: number; name?: string; email?: string }

// Correct use — update function:
function updateUser(id: number, changes: Partial<User>): void { /* patch */ }
updateUser(1, { name: 'Ada' }); // ✓ only name provided
updateUser(1, {});               // ✓ compiles, but nothing changes at runtime

// Shallow: this is NOT DeepPartial
type Config = { server: { host: string; port: number }; debug: boolean };
type P = Partial<Config>;
// { server?: { host: string; port: number }; debug?: boolean }
//                ^^^^ host and port are still REQUIRED inside server ✗
```

**Q3. What does `Required<T>` do, and what does the `-?` modifier specifically remove?**

A: `Required<T>` produces a type identical to `T` but with every optional property made required — the inverse of `Partial`. Implementation: `{ [K in keyof T]-?: T[K] }`. The `-?` modifier is a *mapping modifier remover*: the `-` prefix removes the `?` modifier from each property, making it required. Similarly, `+?` explicitly adds the optional modifier (though `?` alone is idiomatic). TypeScript's modifier system: `+`/`-` are addition/removal prefixes; `?` and `readonly` are the two modifiable attributes. `Required<T>` is less common than `Partial` because most types start required; it's useful when a type was defined with many optional fields for flexibility, but a specific function requires all of them to be present.

```ts
type Required<T> = {
  [K in keyof T]-?: T[K]; // -? removes the optional modifier
};

type Options = { timeout?: number; retries?: number; verbose?: boolean };
type FullOptions = Required<Options>;
// { timeout: number; retries: number; verbose: boolean } — all required

// Demonstration of mapping modifier symmetry:
type A = { x?: number; y?: string };
type B = { [K in keyof A]+?: A[K] };  // same as Partial (adds ?)
type C = { [K in keyof A]-?: A[K] };  // same as Required (removes ?)
type D = { readonly [K in keyof A]: A[K] };  // adds readonly
type E = { -readonly [K in keyof A]: A[K] }; // removes readonly (= Mutable)
```

**Q4. What does `Readonly<T>` do, and how does it differ from JavaScript's `Object.freeze`?**

A: `Readonly<T>` produces a type where every property is annotated `readonly` — assignment after initialization is a compile-time error. Implementation: `{ readonly [K in keyof T]: T[K] }`. The critical difference from `Object.freeze`: `Readonly<T>` is a *compile-time type constraint* only — at runtime, the object is a plain mutable JavaScript object. `Object.freeze` provides *runtime immutability* but TypeScript's inferred type after `Object.freeze(obj)` is `Readonly<T>`. Neither provides deep immutability — a `Readonly<{ a: { b: number } }>` prevents reassigning `a`, but `obj.a.b = 99` compiles and runs fine. For deep immutability: `DeepReadonly<T>` (recursive mapped type, see Q24).

```ts
type Readonly<T> = {
  readonly [K in keyof T]: T[K];
};

type Config = Readonly<{ host: string; port: number }>;
const c: Config = { host: 'localhost', port: 3000 };
c.host = 'other'; // ✗ Error: Cannot assign to 'host' because it is a read-only property

// Runtime: the object is still mutable in JS!
const cfg = { host: 'a', port: 1 } as Config;
(cfg as any).host = 'b'; // no runtime error — Readonly is type-only

// Shallow: nested objects can still be mutated
type Nested = Readonly<{ user: { name: string } }>;
const n: Nested = { user: { name: 'Ada' } };
n.user = { name: 'Bob' };  // ✗ Error: user is readonly
n.user.name = 'Bob';       // ✓ Compiles! user.name is NOT readonly
```

**Q5. What are mapping modifiers, what four modifier combinations exist, and which built-in types use each?**

A: Mapping modifiers prefix `?` or `readonly` with `+` (add) or `-` (remove). The four combinations: **`?`** (or `+?`): add optional modifier → `Partial<T>` uses this. **`-?`**: remove optional modifier → `Required<T>` uses this. **`readonly`** (or `+readonly`): add readonly modifier → `Readonly<T>` uses this. **`-readonly`**: remove readonly modifier → no built-in uses this, but a custom `Mutable<T>` type can. These modifiers are independent and composable: `{ -readonly [K in keyof T]-?: T[K] }` produces a type with all properties writable AND required — a "fully mutable, fully required" version of T.

```ts
// Summary table:
type Partial<T>    = { [K in keyof T]+?: T[K] };        // +? (optional added)
type Required<T>   = { [K in keyof T]-?: T[K] };        // -? (optional removed)
type Readonly<T>   = { +readonly [K in keyof T]: T[K] }; // +readonly
type Mutable<T>    = { -readonly [K in keyof T]: T[K] }; // -readonly (custom)
type WritableOptional<T> = { -readonly [K in keyof T]+?: T[K] }; // both

// Verify: Mutable removes readonly
type Immutable = { readonly a: number; readonly b: string };
type Mutable2  = Mutable<Immutable>;
// { a: number; b: string } — readonly removed ✓
```

**Q6. Why is `Required<Partial<T>>` not necessarily the same as `T` in TypeScript's structural type system?**

A: `Required<Partial<T>>` produces a type that makes every property required and non-optional — which appears identical to `T`. However, there is one significant case where they differ: when `T` has properties typed as `X | undefined`. A property `a: string | undefined` in `T` is *required* (the key must be present) but its value can be `undefined`. After `Partial<T>`, `a` becomes `a?: string | undefined` (optional AND can be undefined). After `Required<Partial<T>>`, `a` becomes `a: string | undefined` again (required, but still accepts `undefined` as a value). So `Required<Partial<T>> = T` in this case, but the intermediate `Partial<T>` representation differs. The subtlety: `?` modifies whether the *key* can be absent; `| undefined` in the type allows `undefined` as a *value* — these are distinct. TypeScript has `exactOptionalPropertyTypes` strict mode, where `?` does NOT automatically add `| undefined`, making `T` vs `Required<Partial<T>>` diverge more clearly.

```ts
type T = { a: string | undefined; b: string };

type Step1 = Partial<T>;
// { a?: string | undefined; b?: string }
// a's type: string | undefined (value) AND optional (key may be absent)

type Step2 = Required<Partial<T>>;
// { a: string | undefined; b: string }
// ≡ T in this case ✓

// With exactOptionalPropertyTypes:
type T2 = { a?: string }; // a can be absent OR string (NOT string | undefined)
type P2 = Partial<T2>;    // { a?: string } — same
type R2 = Required<P2>;   // { a: string } — undefined no longer allowed for a
// T2 allows a to be absent; R2 requires a: string — different!
```

### Section A2: Pick, Omit, Record

**Q7. What does `Pick<T, K>` do, and how does `K extends keyof T` enforce type safety?**

A: `Pick<T, K>` creates a new type containing only the properties of `T` whose keys are in `K`. Implementation: `{ [P in K]: T[P] }` where `K extends keyof T`. The constraint `K extends keyof T` is critical: it ensures that every key in `K` actually exists in `T`, preventing `Pick<User, 'nonexistent'>` from compiling. `K` can be a single string literal (`'name'`), a union (`'name' | 'email'`), or any subtype of `keyof T`. The result type contains exactly those properties, preserving their optionality, readonly modifiers, and types. `Pick` is the primary tool for creating "view types" — a subset of a larger entity type for use in a specific context (e.g., a `UserSummary` that shows only `id` and `name`).

```ts
type Pick<T, K extends keyof T> = {
  [P in K]: T[P]; // iterate over K (not keyof T), preserving each T[P]
};

interface User { id: number; name: string; email: string; role: 'admin' | 'user'; }

type UserSummary = Pick<User, 'id' | 'name'>;
// { id: number; name: string }

type PublicUser = Pick<User, 'name' | 'role'>;
// { name: string; role: 'admin' | 'user' }

// K extends keyof T enforces valid keys at compile time:
type Bad = Pick<User, 'id' | 'password'>; // ✗ Error: 'password' not in keyof User

// Pick preserves modifiers:
interface A { readonly x: number; y?: string }
type PA = Pick<A, 'x' | 'y'>;
// { readonly x: number; y?: string } — readonly and ? preserved ✓
```

**Q8. What does `Omit<T, K>` do, how is it implemented, and why does it accept `keyof any` not `keyof T`?**

A: `Omit<T, K>` creates a new type containing all properties of `T` *except* those in `K`. Implementation: `Pick<T, Exclude<keyof T, K>>` — it picks from `T` all keys that are NOT in `K`. The constraint on `K` is `keyof any` (which equals `string | number | symbol`), not `keyof T`. This is intentional: it allows `Omit<User, 'nonexistent'>` to compile (silently ignoring nonexistent keys), unlike `Pick` which enforces valid keys. This design decision is debated — Lodash's types use a stricter version. The implementation chain: (1) `keyof T` = union of all keys; (2) `Exclude<keyof T, K>` = keys of T that aren't in K; (3) `Pick<T, ...>` = type with only those keys.

```ts
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
// Step by step:
// Exclude<keyof T, K> = keys of T not in K
// Pick<T, those keys> = object type with only those keys

interface User { id: number; name: string; email: string; password: string; }

type PublicUser = Omit<User, 'password'>;
// { id: number; name: string; email: string }

// No error for nonexistent key (unlike Pick):
type Safe = Omit<User, 'nonexistent'>;
// { id: number; name: string; email: string; password: string } — same as User

// Multiple omissions:
type DTO = Omit<User, 'password' | 'email'>;
// { id: number; name: string }

// Implementation trace for Omit<User, 'password'>:
// 1. keyof User = 'id' | 'name' | 'email' | 'password'
// 2. Exclude<'id'|'name'|'email'|'password', 'password'> = 'id' | 'name' | 'email'
// 3. Pick<User, 'id'|'name'|'email'> = { id: number; name: string; email: string }
```

**Q9. What does `Record<K, V>` do, and when is it better than an index signature `{ [key: string]: V }`?**

A: `Record<K, V>` creates an object type where every key in `K` maps to type `V`. Implementation: `{ [P in K]: V }` where `K extends keyof any`. The key advantage over an index signature: `Record` allows a *specific set of keys* to be required. `Record<'a' | 'b', number>` means exactly the keys `'a'` and `'b'`, both required. An index signature `{ [key: string]: number }` allows any string key and doesn't require any specific key to be present. `Record` is the tool for exhaustive mappings (all possible cases must be handled), enum-keyed objects, and lookup tables. The difference is enforced at compile time: accessing `rec.nonexistent` on a `Record<'a' | 'b', number>` is a type error; on `{ [key: string]: number }` it is typed as `number` (potentially wrong at runtime).

```ts
type Record<K extends keyof any, T> = {
  [P in K]: T; // no ? or readonly — all keys are required
};

// Specific key set — exhaustive mapping:
type Role = 'admin' | 'editor' | 'viewer';
const permissions: Record<Role, string[]> = {
  admin:  ['read', 'write', 'delete'],
  editor: ['read', 'write'],
  viewer: ['read'],
  // Missing 'viewer' → compile error; extra 'superuser' → compile error
};

// Vs index signature — any key, no specific keys required:
const permissionsAny: { [key: string]: string[] } = {
  admin: ['read'], // compiles; 'viewer' and 'editor' can be missing
};
permissionsAny.nonexistent; // types as string[] | undefined (actually string[] in TS)

// Record as a typed lookup table:
type StatusCode = 200 | 404 | 500;
const messages: Record<StatusCode, string> = {
  200: 'OK', 404: 'Not Found', 500: 'Server Error'
};
// messages[999] → Type error: 999 not assignable to StatusCode ✓
```

**Q10. What is `keyof T`, what type does it produce, and how does it behave with intersections and unions?**

A: `keyof T` produces a union of the literal types of all *known* public property keys of `T`. For `{ a: number; b: string }`, `keyof` yields `'a' | 'b'`. For `keyof string`, it yields all string method and property names (`'length' | 'charAt' | 'toUpperCase' | ...`). For `keyof any`, it yields `string | number | symbol` (all possible key types). Behavior with type algebra: **`keyof (A & B)` = `keyof A | keyof B`** (intersection of types has union of keys — you get keys from both). **`keyof (A | B)` = `keyof A & keyof B`** (union of types has only the keys common to both — only safe to access on either). This seems counterintuitive: intersection types have MORE keys (`|`), while union types have FEWER keys (`&`).

```ts
type A = { a: number; c: boolean };
type B = { b: string; c: number };

type KeysOfIntersection = keyof (A & B); // 'a' | 'b' | 'c' — all keys from both
type KeysOfUnion        = keyof (A | B); // 'c' — only keys common to BOTH A and B

// Intuition:
// A & B: an object with all properties of A AND B → has all keys of A | B
// A | B: could be either A or B → only keys guaranteed to exist on BOTH
//        accessing obj.a on an A | B is unsafe if obj might be a B (which has no 'a')

// With index signatures:
type WithIndex = { [key: string]: number; a: number };
type K = keyof WithIndex; // string | number (any string is a valid key)
// Note: number is included because array indices are numbers that JS coerces to strings
```

**Q11. What is the `Omit` pitfall with discriminated unions, and what is the correct fix?**

A: `Omit<DiscriminatedUnion, K>` does NOT distribute over union members — it applies to the *whole union as a single type*, then extracts keys, then picks. The result loses the discriminant information, collapsing all union members into one merged object type. This destroys the discriminated union's exhaustive pattern-matching capability. The fix: use a *distributive* version that applies `Omit` to each union member individually: `type DistributiveOmit<T, K extends keyof any> = T extends any ? Omit<T, K> : never`. The `T extends any ? ... : never` forces distribution over the union members.

```ts
type Shape =
  | { kind: 'circle';    radius: number }
  | { kind: 'rectangle'; width: number; height: number };

// WRONG: Omit applied to the whole union
type ShapeNoKind = Omit<Shape, 'kind'>;
// → { radius?: number; width?: number; height?: number }
// The discriminant 'kind' and member-specific keys are all merged — WRONG

// CORRECT: distribute Omit over union members
type DistributiveOmit<T, K extends keyof any> = T extends any ? Omit<T, K> : never;
type ShapeNoKindFixed = DistributiveOmit<Shape, 'kind'>;
// → { radius: number } | { width: number; height: number }
// Each member is Omit'd independently ✓

// Same problem exists with Pick:
type DistributivePick<T, K extends keyof T> = T extends any ? Pick<T, Extract<keyof T, K>> : never;
```

**Q12. How does `keyof any` differ from `keyof T`, and why does `Record<keyof any, V>` not restrict to string keys only?**

A: `keyof any` is `string | number | symbol` — the full set of possible property key types in JavaScript. JavaScript object keys are fundamentally strings or symbols; `number` keys are coerced to strings at runtime. TypeScript includes `number` in `keyof any` because array index access (`obj[0]`) is common and typed. `keyof T` for a plain object type is typically a union of string literal types (the actual property names). `Record<keyof any, V>` is therefore equivalent to `{ [K in string | number | symbol]: V }` — accepting any key. When you write `Record<string, V>`, only string keys are accepted. Using `K extends keyof any` as a constraint (as in `Omit` and `Record`) allows the most permissive set of key types.

```ts
// keyof any:
type AllKeyTypes = keyof any; // string | number | symbol

// Record with specific key types:
type R1 = Record<string, number>;        // { [k: string]: number }
type R2 = Record<'a' | 'b', number>;    // { a: number; b: number }
type R3 = Record<number, string>;        // { [k: number]: string } (array-like)
type R4 = Record<symbol, boolean>;       // { [k: symbol]: boolean }

// Why Omit uses `K extends keyof any` not `K extends keyof T`:
// Allows Omit<T, 'missingKey'> without compile error
// Allows Omit<Union, string> for flexible key removal
```

## Topic B: Distribution and Introspection Utilities

### Section B1: Extract, Exclude, NonNullable

**Q13. What does `Exclude<T, U>` do, and what conditional type implements it?**

A: `Exclude<T, U>` removes from the union type `T` all members that are assignable to `U`. Implementation: `T extends U ? never : T`. When `T` is a union, the conditional type *distributes* over each member: each member is independently checked against `U`; those assignable to `U` become `never` (which dissolves from a union); those not assignable survive. The result is a subset of `T`. `Exclude` is used to filter union types: remove a specific literal type, remove a category of types (e.g., remove all `string` members), or subtract one union from another. It is the type-level analog of a set difference operation.

```ts
type Exclude<T, U> = T extends U ? never : T;

// Removing specific members:
type Status = 'draft' | 'published' | 'archived';
type ActiveStatus = Exclude<Status, 'archived'>;
// → 'draft' | 'published'

// Distribution trace:
// Exclude<'draft'|'published'|'archived', 'archived'>
// = ('draft' extends 'archived' ? never : 'draft')
// | ('published' extends 'archived' ? never : 'published')
// | ('archived' extends 'archived' ? never : 'archived')
// = 'draft' | 'published' | never
// = 'draft' | 'published' ✓

// Removing a category:
type Mixed = string | number | boolean | null;
type NoStrings = Exclude<Mixed, string>;
// → number | boolean | null

// Removing a union:
type A = 'a' | 'b' | 'c' | 'd';
type B = 'b' | 'd';
type OnlyA = Exclude<A, B>;
// → 'a' | 'c'
```

**Q14. What does `Extract<T, U>` do, and how is it the dual of `Exclude`?**

A: `Extract<T, U>` *keeps* only those members of union `T` that are assignable to `U` — the exact complement of `Exclude`. Implementation: `T extends U ? T : never`. Where `Exclude` filters out matching members, `Extract` filters out non-matching members. `Extract` computes a set *intersection* at the type level — the result is the intersection of T and U viewed as sets of types. Common uses: narrowing a union to a specific shape, extracting all function types from a union, getting the subset of union members that extend a particular interface.

```ts
type Extract<T, U> = T extends U ? T : never;

// Keep only string members:
type Mixed = string | number | boolean | null;
type OnlyStrings = Extract<Mixed, string>;
// → string

// Extract functions from a union:
type AnyFn = (...args: any[]) => any;
type Callbacks = string | ((x: number) => void) | number | ((s: string) => string);
type JustFunctions = Extract<Callbacks, AnyFn>;
// → ((x: number) => void) | ((s: string) => string)

// Extract union members matching a shape:
type Event =
  | { type: 'click'; x: number; y: number }
  | { type: 'keydown'; key: string }
  | { type: 'scroll'; delta: number };

type MouseEvents = Extract<Event, { type: 'click' | 'scroll' }>;
// → { type: 'click'; x: number; y: number } | { type: 'scroll'; delta: number }

// Dual relationship:
// Exclude<T, U> = T - U  (members of T not in U)
// Extract<T, U> = T ∩ U  (members of T also in U)
// Exclude<T, U> | Extract<T, U> = T  (always, for any T and U)
```

**Q15. What does `NonNullable<T>` do, and what are its two possible implementations?**

A: `NonNullable<T>` removes `null` and `undefined` from the union type `T`. Two valid implementations: (1) **Conditional type**: `T extends null | undefined ? never : T` — distributes over the union and filters out `null` and `undefined` members. (2) **Intersection type** (TypeScript 4.8+): `T & {}` — since `null` and `undefined` are not assignable to `{}` (the empty object type), the intersection eliminates them. TypeScript's actual built-in uses the second form (`T & {}`), which is more accurate in edge cases involving generic constraints. Both produce the same result for practical union types but differ subtly when `T` is generic and unconstrained.

```ts
// Implementation 1: conditional type
type NonNullable1<T> = T extends null | undefined ? never : T;

// Implementation 2: intersection (TypeScript's built-in since 4.8)
type NonNullable2<T> = T & {};

// Usage:
type MaybeString  = string | null | undefined;
type DefiniteStr  = NonNullable<MaybeString>;
// → string

type Mixed = string | number | null | undefined | boolean;
type Clean = NonNullable<Mixed>;
// → string | number | boolean

// Practical use: assertions and narrowing
function processValue(val: string | null | undefined): void {
  const clean: string = val!;    // runtime assertion (unsafe)
  const safe: NonNullable<typeof val> = val as string; // type-only
}

// With conditional trace (impl 1):
// NonNullable<string | null | undefined>
// = (string extends null|undefined ? never : string)  → string
// | (null extends null|undefined ? never : null)      → never
// | (undefined extends null|undefined ? never : undefined) → never
// = string | never | never = string ✓
```

**Q16. What is a distributive conditional type, and why does distribution matter for `Exclude` and `Extract`?**

A: A conditional type `T extends U ? X : Y` is *distributive* when `T` is a *naked* (unwrapped) generic type parameter. "Naked" means `T` appears directly in the extends clause, not inside a tuple, array, or other wrapper. When `T` is a union `A | B | C`, distribution applies the conditional to each member independently: `(A extends U ? X : Y) | (B extends U ? X : Y) | (C extends U ? X : Y)`. Distribution is why `Exclude` works on unions at all — without it, `'a' | 'b' | 'c' extends 'a'` would check the whole union against `'a'` as one check (which would be `false` since `'b'` is not `'a'`), and the result would always be either all-X or all-Y, never filtering individual members. Distribution transforms a type-level union check into n individual member checks, enabling filtering.

```ts
// Distribution in action:
type IsString<T> = T extends string ? 'yes' : 'no';

type A = IsString<string | number | boolean>;
// With distribution (T is naked generic — YES, distributive):
// = IsString<string> | IsString<number> | IsString<boolean>
// = 'yes' | 'no' | 'no'
// = 'yes' | 'no'

// What WOULD happen without distribution (hypothetically):
// = (string | number | boolean) extends string ? 'yes' : 'no'
// = 'no'  ← wrong! the whole union is not assignable to string

// Key: distribution requires a NAKED type parameter in the extends position
type Distributive<T>    = T extends string ? true : false;  // distributes ✓
type NotDistributive<T> = [T] extends [string] ? true : false; // does NOT distribute
// NotDistributive<string | number> = false (no distribution)
// Distributive<string | number>   = boolean (true | false)
```

**Q17. How do you prevent distribution in conditional types, and when would you want to?**

A: Wrap the type in a tuple `[T]` to prevent distribution: `[T] extends [U] ? X : Y`. The wrapping makes `T` no longer "naked" — the extends check compares the tuple `[T]` to the tuple `[U]` as a unit, without distributing over union members. Prevention is useful when: (1) you want to check if a *whole union* is assignable to something rather than any individual member; (2) implementing `IsNever<T>` — `T extends never ? true : false` distributes over an empty union and produces `never`, not `true`; wrapping with `[T] extends [never]` correctly returns `true` for `T = never`; (3) implementing equality checks between types.

```ts
// IsNever: must prevent distribution (never is the empty union)
type IsNeverBad<T>  = T extends never ? true : false;
type TestBad        = IsNeverBad<never>;  // → never (not true!)
// Why: distributing over an empty union yields empty union (never)

type IsNever<T>     = [T] extends [never] ? true : false;
type TestGood       = IsNever<never>;     // → true ✓
type TestNotNever   = IsNever<string>;    // → false ✓

// IsEqual: requires preventing distribution
type IsEqual<A, B>  = [A] extends [B] ? [B] extends [A] ? true : false : false;
type Eq1 = IsEqual<string, string>;         // → true
type Eq2 = IsEqual<string | number, number>;// → false
type Eq3 = IsEqual<never, never>;           // → true ✓

// When you DO want distribution (most utility types):
type ExcludeBad<T, U> = [T] extends [U] ? never : T;
// ExcludeBad<'a' | 'b', 'a'> = [never | never] → wrong
// Always use naked T for filtering unions
```

### Section B2: Function and Class Introspection

**Q18. What does `ReturnType<T>` do, and how does `infer` extract the return type from a function?**

A: `ReturnType<T>` extracts the return type of a function type `T`. Implementation: `T extends (...args: any) => infer R ? R : any`. The `infer R` keyword instructs TypeScript: "when pattern-matching this conditional type, capture whatever type occupies the return type position of the function and bind it to the name `R`." If `T` matches the function pattern, the result is `R` (the inferred return type); otherwise `any`. `infer` is exclusively valid in the `extends` clause of a conditional type — it performs *structural pattern matching* on a type, extracting sub-types that would be determined by the type's structure. The constraint `T extends (...args: any) => any` ensures `T` is a function type before the pattern match.

```ts
type ReturnType<T extends (...args: any) => any> =
  T extends (...args: any) => infer R ? R : any;
//                                 ^^^^ infer: "capture and name the return type"

// Resolution trace:
// ReturnType<() => string>
// = (() => string) extends (...args: any) => infer R ? R : any
//   Pattern match: fn matches (...args: any) => infer R
//   infer R → R is bound to 'string'
// = string ✓

// Common uses:
function fetchUser(): Promise<{ id: number; name: string }> { /* ... */ return null!; }
type FetchResult = ReturnType<typeof fetchUser>; // Promise<{ id: number; name: string }>
// Note: typeof fetchUser gets the function TYPE; ReturnType then extracts from it

function createStore<T>(initial: T): { get: () => T; set: (v: T) => void } { return null!; }
type Store = ReturnType<typeof createStore<number>>;
// { get: () => number; set: (v: number) => void }

// Overloaded functions: ReturnType gets the LAST overload's return type (TS limitation)
```

**Q19. What does `Parameters<T>` do, what type does it produce, and how do you access individual parameters?**

A: `Parameters<T>` extracts the parameter types of a function type `T` as a *tuple type*. Implementation: `T extends (...args: infer P) => any ? P : never`. The `...args: infer P` pattern captures the parameter list as a tuple — including parameter names (labeled tuple elements in TypeScript 4+). `Parameters<(a: string, b: number) => void>` returns `[a: string, b: number]`, a labeled tuple. To access individual parameters: index the tuple type — `Parameters<T>[0]` gives the first parameter's type, `Parameters<T>[1]` the second. `Parameters<T>['length']` gives the number of parameters as a literal number type. This is particularly useful for higher-order functions, decorators, and middleware patterns where the wrapper function must match the wrapped function's signature.

```ts
type Parameters<T extends (...args: any) => any> =
  T extends (...args: infer P) => any ? P : never;

function createUser(name: string, age: number, role: 'admin' | 'user'): void {}

type CreateUserParams = Parameters<typeof createUser>;
// [name: string, age: number, role: 'admin' | 'user']

type FirstParam  = CreateUserParams[0]; // string
type SecondParam = CreateUserParams[1]; // number
type ThirdParam  = CreateUserParams[2]; // 'admin' | 'user'
type ParamCount  = CreateUserParams['length']; // 3

// Practical: wrapper function that preserves signature
function withLogging<T extends (...args: any) => any>(fn: T) {
  return (...args: Parameters<T>): ReturnType<T> => {
    console.log('calling with', args);
    return fn(...args);
  };
}

// Note: Parameters<T>[number] gives the UNION of all parameter types:
type AnyParam = CreateUserParams[number]; // string | number | 'admin' | 'user'
```

**Q20. What does `InstanceType<T>` do, when is it needed, and how does it differ from just using the class name directly?**

A: `InstanceType<T>` extracts the *instance type* of a constructor function type `T` — the type of objects created by `new T()`. Implementation: `T extends abstract new (...args: any) => infer R ? R : any`. When you have a class `Foo`, TypeScript creates two distinct types: the *instance type* `Foo` (the type of objects created by `new Foo()`), and the *constructor type* `typeof Foo` (the type of the class itself). `InstanceType<typeof Foo>` is therefore equivalent to `Foo`. `InstanceType` is needed when you have a *generic* type parameter `T` constrained to be a constructor, and you need to express the instance type without knowing the specific class.

```ts
type InstanceType<T extends abstract new (...args: any) => any> =
  T extends abstract new (...args: any) => infer R ? R : any;

class Connection {
  constructor(public host: string) {}
  query(sql: string): Promise<any[]> { return null!; }
}

// When you hold a constructor reference:
function createAndUse<T extends new (...args: any) => any>(
  Ctor: T,
  ...args: ConstructorParameters<T>
): InstanceType<T> {
  return new Ctor(...args);
}

const conn = createAndUse(Connection, 'localhost');
// conn is typed as InstanceType<typeof Connection> = Connection ✓

// InstanceType<typeof Foo> = Foo (for known class, not generic)
type ConnInstance = InstanceType<typeof Connection>; // Connection

// Use in a factory registry:
type ClassMap = { db: typeof Connection; [key: string]: new (...args: any) => any };
function get<K extends keyof ClassMap>(registry: ClassMap, key: K): InstanceType<ClassMap[K]> {
  return new registry[key]() as any;
}
```

**Q21. What is `infer`, what constraint governs its placement, and what problems does it solve?**

A: `infer` is a type-level keyword that declares a *type variable* to be inferred from a pattern match during conditional type resolution. Constraint: `infer` can only appear in the `extends` clause of a conditional type — `T extends [something involving infer R]`. When TypeScript resolves the conditional, if `T` is assignable to the pattern, `R` is bound to the portion of `T`'s structure corresponding to where `infer R` appears. `infer` solves the fundamental problem of *structural decomposition*: extracting sub-types from a compound type without knowing the exact type in advance. It enables `ReturnType`, `Parameters`, `InstanceType`, and custom utilities like extracting `Promise` inner types, array element types, and object value types.

```ts
// Extracting the element type of an array:
type UnpackArray<T> = T extends (infer Element)[] ? Element : T;
type Nums = UnpackArray<number[]>; // number
type Str  = UnpackArray<string>;   // string (not an array → returns T as-is)

// Extracting the resolved type of a Promise:
type Awaited<T> = T extends Promise<infer U> ? Awaited<U> : T; // recursive
type Inner = Awaited<Promise<Promise<string>>>; // string

// Extracting the first element of a tuple:
type Head<T extends any[]> = T extends [infer H, ...any[]] ? H : never;
type First = Head<[string, number, boolean]>; // string

// Multiple infer in one conditional:
type ExtractFn<T> = T extends (arg: infer A) => infer R ? [A, R] : never;
type FnInfo = ExtractFn<(x: string) => number>; // [string, number]

// infer constraints (TypeScript 4.7+):
type ToNumber<T> = T extends `${infer N extends number}` ? N : never;
type N = ToNumber<'42'>; // 42 (numeric literal, not string '42')
```

**Q22. What are `ConstructorParameters<T>`, `Awaited<T>`, and `ThisParameterType<T>`?**

A: Three additional built-in utility types extending the introspection repertoire: **`ConstructorParameters<T>`** extracts the constructor's parameter types as a tuple: `T extends abstract new (...args: infer P) => any ? P : never`. Symmetrical with `Parameters` but for constructors. **`Awaited<T>`** (TypeScript 4.5+) recursively unwraps `Promise` and `PromiseLike` until the inner non-Promise type is reached: `Awaited<Promise<Promise<string>>>` = `string`. This replaced the older `ReturnType<...>` workaround for async function return types. **`ThisParameterType<T>`** extracts the type of the `this` parameter if a function has one explicitly declared: `T extends (this: infer U, ...args: any[]) => any ? U : unknown`. Used in decorator factories and `Function.prototype.bind` type inference.

```ts
class Http {
  constructor(public baseUrl: string, public timeout: number) {}
}

// ConstructorParameters:
type HttpArgs = ConstructorParameters<typeof Http>; // [baseUrl: string, timeout: number]
const args: HttpArgs = ['https://api.example.com', 5000];
const http = new Http(...args);

// Awaited:
async function fetchUser(): Promise<{ name: string }> { return { name: 'Ada' }; }
type UserType = Awaited<ReturnType<typeof fetchUser>>; // { name: string }
// Before TS 4.5: ReturnType gave Promise<{name:string}>; manual unwrap was needed

// ThisParameterType:
function greet(this: { name: string }, greeting: string): string {
  return `${greeting}, ${this.name}!`;
}
type ThisType = ThisParameterType<typeof greet>; // { name: string }
// OmitThisParameter<T> removes the this parameter from a function type
```

## Topic C: Composition and Mental Models

**Q23. How do you compose utility types, and what are the three composition patterns?**

A: Three patterns for combining utility types: (1) **Sequential (pipeline)**: apply one utility type and use the result as input to another — `Partial<Omit<User, 'password'>>` first omits `password`, then makes remaining properties optional. (2) **Conditional composition**: use conditional types to choose between utility types — `T extends string ? Exclude<T, 'error'> : T`. (3) **Mapped composition**: apply utility types inside a mapped type to transform each property — `{ [K in keyof T]: T[K] extends object ? Readonly<T[K]> : T[K] }` makes only object-valued properties readonly. Order matters in sequential composition: `Omit<Partial<T>, K>` differs from `Partial<Omit<T, K>>` — the former omits from an already-partial type (so K's optional status doesn't matter); the latter first omits then optionalizes (cleaner).

```ts
// Pattern 1: Sequential pipeline
type UserInput = Omit<User, 'id' | 'createdAt'>; // remove auto-generated fields
type CreateUserInput = Required<UserInput>;        // all remaining must be provided
type UpdateUserInput = Partial<UserInput>;          // all remaining are optional

// Pattern 2: Conditional utility application
type FlexibleOption<T> = T extends undefined ? Required<T> : Partial<T>;

// Pattern 3: Mapped utility composition
// Apply Readonly to object values, keep primitives as-is:
type ShallowReadonlyValues<T> = {
  [K in keyof T]: T[K] extends object ? Readonly<T[K]> : T[K];
};

// Real-world: typing an API layer
interface UserEntity { id: number; name: string; email: string; password: string; createdAt: Date }

type UserDTO       = Omit<UserEntity, 'password'>;        // safe to return
type CreateRequest = Omit<UserEntity, 'id' | 'createdAt'>; // user provides these
type UpdateRequest = Partial<Omit<UserEntity, 'id'>>;      // id immutable; rest optional
type PatchRequest  = Pick<UserEntity, 'id'> & UpdateRequest; // must include id for patching
```

**Q24. What custom utility types are frequently asked about in TypeScript interviews, and what is each's implementation?**

A: Five commonly requested custom types: **`DeepPartial<T>`**: recursively makes all properties optional, including nested objects. **`Mutable<T>`** (or `Writeable<T>`): removes `readonly` from all top-level properties. **`NonFunctionKeys<T>`** (or `ValueOf<T>`): extracts only the non-function property keys. **`UnionToIntersection<T>`**: converts a union type to an intersection type using contravariance. **`FlattenObject<T>`**: flattens a nested object type into dot-notation string keys.

```ts
// 1. DeepPartial — recursive Partial
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;
// T extends object guard prevents infinitely recursing into primitives

// 2. Mutable — removes readonly
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

// 3. ValueOf — union of all value types
type ValueOf<T> = T[keyof T];
// ValueOf<{ a: string; b: number }> = string | number

// 4. UnionToIntersection — uses function argument contravariance
type UnionToIntersection<U> =
  (U extends any ? (x: U) => void : never) extends (x: infer I) => void ? I : never;
// UnionToIntersection<{ a: string } | { b: number }> = { a: string } & { b: number }

// 5. Prettify — flattens intersection types for display (structural identity):
type Prettify<T> = { [K in keyof T]: T[K] } & {};
// Prettify<{ a: string } & { b: number }> = { a: string; b: number } (displayed flat)

// 6. PickByValue — pick properties by their value type
type PickByValue<T, V> = {
  [K in keyof T as T[K] extends V ? K : never]: T[K];
};
// PickByValue<{ a: string; b: number; c: string }, string> = { a: string; c: string }
```

**Q25. State a one-sentence mental model for each of the 12 utility types.**

A:
- **`Partial<T>`**: produces T with every property wrapped in `?`, making all fields optional — useful for update/patch payloads.
- **`Required<T>`**: produces T with every `?` stripped using `-?`, making all fields required — the inverse of Partial.
- **`Readonly<T>`**: produces T with `readonly` added to every property, preventing reassignment at compile time (not runtime).
- **`Pick<T, K>`**: produces a new object type containing only the K-named properties of T, with K constrained to `keyof T`.
- **`Omit<T, K>`**: produces a new object type with every property of T *except* those named in K, implemented as `Pick<T, Exclude<keyof T, K>>`.
- **`Record<K, V>`**: produces an object type where every key in K (a union of string/number/symbol literals) maps to value type V, requiring all K keys to be present.
- **`Exclude<T, U>`**: produces a subset of union T containing only members NOT assignable to U, via distributing `T extends U ? never : T`.
- **`Extract<T, U>`**: produces a subset of union T containing only members assignable to U, via distributing `T extends U ? T : never` — the complement of Exclude.
- **`NonNullable<T>`**: produces T with `null` and `undefined` removed, implemented as `T & {}` (or conditionally excluding null/undefined).
- **`ReturnType<T>`**: extracts the return type of function type T using `infer R` in the extends clause of a conditional type.
- **`Parameters<T>`**: extracts the parameter types of function type T as a labeled tuple, using `infer P` on the parameter list.
- **`InstanceType<T>`**: extracts the instance type produced by calling `new T()`, using `infer R` on the constructor's return position — equal to the class name itself when T is a known class.

## Problem 1 — Implement Property Transformation Utilities from Scratch

### Problem

Without using the built-in versions, implement `MyPartial<T>`, `MyRequired<T>`, `MyReadonly<T>`, and `MyMutable<T>` (removes readonly). Verify each produces the correct type using `extends` checks.

```ts
interface Config { host: string; port: number; debug?: boolean }

type A = MyPartial<Config>;  // { host?: string; port?: number; debug?: boolean }
type B = MyRequired<Config>; // { host: string; port: number; debug: boolean }
type C = MyReadonly<Config>; // { readonly host: string; readonly port: number; readonly debug?: boolean }
type D = MyMutable<C>;       // { host: string; port: number; debug?: boolean } — readonly removed
```

### Pattern Recognition
All four are mapped types over `keyof T`. Each applies or removes a specific mapping modifier (`?`, `-?`, `readonly`, `-readonly`). No conditional types or `infer` needed — these are the simplest utility types.

### Key Insight
The modifier goes between `{` and `[K in keyof T]`. Remove-modifiers use `-` prefix: `-?` removes optional, `-readonly` removes readonly. The value type `T[K]` is always the same — only the modifiers on the key change.

### Solution

```ts
// MyPartial — adds ? to every property
type MyPartial<T> = {
  [K in keyof T]?: T[K];
  // Equivalent to: [K in keyof T]+?: T[K]
};

// MyRequired — removes ? from every property
type MyRequired<T> = {
  [K in keyof T]-?: T[K]; // -? explicitly removes the optional modifier
};

// MyReadonly — adds readonly to every property
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K]; // equivalent to +readonly
};

// MyMutable — removes readonly from every property (no built-in equivalent)
type MyMutable<T> = {
  -readonly [K in keyof T]: T[K]; // -readonly removes the readonly modifier
};

// Verification:
interface Config { host: string; port: number; debug?: boolean }

type PA = MyPartial<Config>;
// { host?: string | undefined; port?: number | undefined; debug?: boolean | undefined }
// (all are now optional)

type RQ = MyRequired<Config>;
// { host: string; port: number; debug: boolean }
// (debug was optional → now required)

type RO = MyReadonly<Config>;
// { readonly host: string; readonly port: number; readonly debug?: boolean }
// (all have readonly added; optionality of debug preserved)

type MU = MyMutable<RO>;
// { host: string; port: number; debug?: boolean }
// (readonly removed; debug is still optional since Readonly didn't change that)

// Type-level assertion helper:
type Assert<T extends true> = T;
type IsEqual<A, B> = [A] extends [B] ? [B] extends [A] ? true : false : false;
type Test1 = Assert<IsEqual<MyPartial<{ a: string }>, { a?: string }>>;        // true ✓
type Test2 = Assert<IsEqual<MyRequired<{ a?: string }>, { a: string }>>;       // true ✓
```

### Resolution Trace

```ts
// Trace: MyRequired<{ host: string; port: number; debug?: boolean }>

// Step 1: keyof { host: string; port: number; debug?: boolean }
//       = 'host' | 'port' | 'debug'

// Step 2: iterate with [K in 'host' | 'port' | 'debug']-?:
//   K='host':  [host]-?: string   → host: string       (was required; -? no-op)
//   K='port':  [port]-?: number   → port: number       (was required; -? no-op)
//   K='debug': [debug]-?: boolean → debug: boolean     (was optional; -? REMOVES ?)

// Result: { host: string; port: number; debug: boolean } ✓
```

### Edge Cases
- `MyPartial<{ a: string | undefined }>` → `{ a?: string | undefined }` — note: `?` makes the key optional, and `| undefined` is also added by TypeScript (unless `exactOptionalPropertyTypes` is enabled).
- `MyRequired<never>` → `never` (empty union stays empty).
- `MyMutable` on a type without `readonly` properties: no-op (produces the same type).

### Follow-up Questions
- "How does `MyPartial<Required<T>>` differ from `T`?" — They're structurally the same for regular types, but the intermediate `Required<T>` step strips `| undefined` from property value types in `exactOptionalPropertyTypes` mode.
- "Can you combine modifiers?" — Yes: `{ -readonly [K in keyof T]-?: T[K] }` makes every property both writable AND required in one mapped type.

## Problem 2 — Implement Selection and Mapping Utilities from Scratch

### Problem

Implement `MyPick<T, K>`, `MyOmit<T, K>`, and `MyRecord<K, V>` without using the built-ins. Include the correct type constraints for each.

```ts
interface User { id: number; name: string; email: string; role: 'admin' | 'user' }

type Summary = MyPick<User, 'id' | 'name'>;         // { id: number; name: string }
type NoEmail  = MyOmit<User, 'email'>;               // { id: number; name: string; role: '...' }
type Map      = MyRecord<'a' | 'b', number>;         // { a: number; b: number }
```

### Pattern Recognition
`MyPick`: mapped type iterating over `K` (not `keyof T`); `K extends keyof T` constraint. `MyOmit`: composition of `MyPick` and `MyExclude` (or built-in `Exclude`). `MyRecord`: mapped type iterating over `K` with a fixed value type `V`; no reference to an existing type.

### Key Insight
`MyPick` iterates `[P in K]` (over the *subset* K) while looking up `T[P]`. `MyOmit` = `MyPick<T, Exclude<keyof T, K>>`. `MyRecord` is the simplest — no source type T; just map every key in K to the value type V.

### Solution

```ts
// MyPick — K must be a subset of keyof T
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P]; // iterate over K, look up T[P] for each key
};

// MyExclude (needed for MyOmit) — conditional type, distributes over union
type MyExclude<T, U> = T extends U ? never : T;

// MyOmit — K is any key type (not constrained to keyof T)
type MyOmit<T, K extends keyof any> = MyPick<T, MyExclude<keyof T, K>>;

// MyRecord — maps every key in K to type V
type MyRecord<K extends keyof any, V> = {
  [P in K]: V; // no T; value type is always V
};

// --- Verification ---

interface User { id: number; name: string; email: string; role: 'admin' | 'user' }

type Summary = MyPick<User, 'id' | 'name'>;
// { id: number; name: string } ✓

type NoEmail = MyOmit<User, 'email'>;
// MyExclude<'id'|'name'|'email'|'role', 'email'> = 'id'|'name'|'role'
// MyPick<User, 'id'|'name'|'role'> = { id: number; name: string; role: 'admin'|'user' } ✓

type StatusMap = MyRecord<'active' | 'inactive' | 'pending', boolean>;
// { active: boolean; inactive: boolean; pending: boolean } ✓

// MyPick enforces valid keys — compile error for invalid keys:
type Bad = MyPick<User, 'id' | 'password'>; // ✗ Error: 'password' not in keyof User

// MyOmit is permissive — no error for missing keys:
type Lenient = MyOmit<User, 'nonexistent'>; // ✓ silently same as User
```

### Resolution Trace

```ts
// Trace: MyOmit<User, 'email'>

// Step 1: keyof User = 'id' | 'name' | 'email' | 'role'

// Step 2: MyExclude<'id'|'name'|'email'|'role', 'email'>
//   'id' extends 'email'?    No → 'id'
//   'name' extends 'email'?  No → 'name'
//   'email' extends 'email'? Yes → never
//   'role' extends 'email'?  No → 'role'
//   = 'id' | 'name' | never | 'role' = 'id' | 'name' | 'role'

// Step 3: MyPick<User, 'id'|'name'|'role'>
//   [P in 'id'|'name'|'role']: User[P]
//   P='id':   User['id']   = number
//   P='name': User['name'] = string
//   P='role': User['role'] = 'admin' | 'user'

// Result: { id: number; name: string; role: 'admin' | 'user' } ✓
```

### Edge Cases
- `MyPick<T, never>` → `{}` (empty object type — no keys iterated).
- `MyRecord<never, V>` → `{}` (same — no keys).
- `MyOmit<T, keyof T>` → `{}` (all keys excluded → empty object).
- Preserves optionality: `MyPick<{ a?: number; b: string }, 'a'>` → `{ a?: number }`.

### Follow-up Questions
- "Why does TypeScript's `Omit` use `keyof any` instead of `keyof T`?" — To allow omitting keys that might not exist in T, so `Omit<T, 'missingKey'>` compiles without error. This is a design tradeoff: safety (error on invalid keys) vs ergonomics (permissive).
- "Implement `DistributiveOmit` for discriminated unions?" — `type DistributiveOmit<T, K extends keyof any> = T extends any ? Omit<T, K> : never`.

## Problem 3 — Implement Filtering Utilities from Scratch

### Problem

Implement `MyExclude<T, U>`, `MyExtract<T, U>`, and `MyNonNullable<T>` without built-ins. Demonstrate distribution over union types.

```ts
type A = MyExclude<'a' | 'b' | 'c', 'a' | 'b'>; // 'c'
type B = MyExtract<string | number | boolean, string | boolean>; // string | boolean
type C = MyNonNullable<string | null | undefined | number>; // string | number
```

### Pattern Recognition
All three are distributive conditional types — `T extends U ? ... : ...` where `T` is a naked type parameter. `Exclude` returns `T` when NOT matching U (filter out). `Extract` returns `T` when matching U (keep). `NonNullable` excludes `null` and `undefined` using either conditional or intersection.

### Key Insight
The `never` type in union position dissolves: `'a' | never = 'a'`. This is the mechanism: make unwanted members `never` in the conditional's true or false branch, and they disappear from the union. Both `Exclude` and `Extract` use `never` as the "discard" result in one branch.

### Solution

```ts
// MyExclude: keep members of T NOT assignable to U
type MyExclude<T, U> = T extends U ? never : T;
//                     ^^^^^^^^^^^^ distributed over each member of T
//                                  if member extends U → never (discard)
//                                  else → T (keep)

// MyExtract: keep members of T that ARE assignable to U
type MyExtract<T, U> = T extends U ? T : never;
//                                   ^ keep the member itself
//                                      ^ discard non-matching members

// MyNonNullable v1: conditional (explicit null/undefined exclusion)
type MyNonNullable1<T> = T extends null | undefined ? never : T;

// MyNonNullable v2: intersection (TypeScript's actual implementation)
type MyNonNullable2<T> = T & {};
// null & {} = never; undefined & {} = never; string & {} = string

// Verification:
type Ex1 = MyExclude<'a' | 'b' | 'c', 'a' | 'b'>; // 'c' ✓
type Ex2 = MyExtract<string | number | boolean, string | boolean>; // string | boolean ✓
type Ex3 = MyNonNullable1<string | null | undefined | number>; // string | number ✓
type Ex4 = MyNonNullable2<string | null | undefined | number>; // string | number ✓

// Dual relationship: Exclude and Extract are complements
// MyExclude<T, U> | MyExtract<T, U> = T (always true for any T, U)
type Verify<T, U> = [MyExclude<T, U>] extends [never]
  ? [MyExtract<T, U>] extends [T] ? true : false
  : true;
```

### Resolution Trace

```ts
// Trace: MyExclude<'a' | 'b' | 'c', 'a' | 'b'>

// T = 'a' | 'b' | 'c', U = 'a' | 'b'. T is naked → distributes.

// Per member:
//   'a' extends 'a' | 'b'? YES → never
//   'b' extends 'a' | 'b'? YES → never
//   'c' extends 'a' | 'b'? NO  → 'c'

// Union of results: never | never | 'c' = 'c' ✓

// Trace: MyNonNullable2<string | null | undefined | number>
// = (string | null | undefined | number) & {}
// = (string & {}) | (null & {}) | (undefined & {}) | (number & {})
// = string | never | never | number
// = string | number ✓
```

### Edge Cases
- `MyExclude<string, string>` → `never` (entire type excluded).
- `MyExtract<string, number>` → `never` (no overlap).
- `MyNonNullable<never>` → `never` (distributing over empty union gives never).
- `MyExclude<string | number, string | number>` → `never` (all members excluded).
- `MyExtract<'a' | 'b', string>` → `'a' | 'b'` (literal types extend their base type).

### Follow-up Questions
- "Why does `MyExclude<never, string>` produce `never`?" — `never` is the empty union; distributing over it yields `never` (no members to iterate). The conditional type simply has nothing to evaluate.
- "Implement `SymmetricDifference<A, B>`?" — `Exclude<A, B> | Exclude<B, A>` — members in A not in B, plus members in B not in A.

## Problem 4 — Implement Function Introspection Utilities from Scratch

### Problem

Implement `MyReturnType<T>`, `MyParameters<T>`, and `MyInstanceType<T>` without built-ins. Use `infer` for structural decomposition.

```ts
function add(a: number, b: number): number { return a + b; }
class Timer { constructor(public ms: number) {} start() {} }

type RT  = MyReturnType<typeof add>;      // number
type P   = MyParameters<typeof add>;      // [a: number, b: number]
type IT  = MyInstanceType<typeof Timer>;  // Timer
```

### Pattern Recognition
All three use `infer` inside a conditional `extends` clause to extract sub-types from compound types. `ReturnType` places `infer R` in the return position. `Parameters` places `infer P` in the parameter list position with spread. `InstanceType` places `infer R` in the constructor return position with `new`.

### Key Insight
`infer` is a placeholder for "whatever type TypeScript finds at this position in the pattern." The structural patterns are: function type `(...args: any) => infer R` (return position), `(...args: infer P) => any` (parameter list position), and constructor type `new (...args: any) => infer R` (constructed type position). The constraint before the conditional (`T extends (...args: any) => any`) ensures the pattern is applicable; if T doesn't match, the `never`/`any` fallback is used.

### Solution

```ts
// MyReturnType — infer the return type R from a function type
type MyReturnType<T extends (...args: any) => any> =
  T extends (...args: any) => infer R
    ? R    // R is bound to the return type of T
    : any; // fallback (shouldn't reach; constraint guarantees T is a function)

// MyParameters — infer the parameter tuple P from a function type
type MyParameters<T extends (...args: any) => any> =
  T extends (...args: infer P) => any
    ? P    // P is bound to the full parameter tuple [a: typeA, b: typeB, ...]
    : never;

// MyInstanceType — infer the instance type R from a constructor type
type MyInstanceType<T extends abstract new (...args: any) => any> =
  T extends abstract new (...args: any) => infer R
    ? R    // R is the type returned by `new T()`
    : any;

// Verification:
function add(a: number, b: number): number { return a + b; }
class Timer { constructor(public ms: number) {} start() {} }
async function fetchData(): Promise<string[]> { return []; }

type RT1 = MyReturnType<typeof add>;         // number ✓
type RT2 = MyReturnType<typeof fetchData>;   // Promise<string[]> ✓

type P1  = MyParameters<typeof add>;         // [a: number, b: number] ✓
type P10 = MyParameters<typeof add>[0];      // number (first param type) ✓
type P11 = MyParameters<typeof add>[1];      // number (second param type) ✓
type PLen = MyParameters<typeof add>['length']; // 2 ✓

type IT1 = MyInstanceType<typeof Timer>;     // Timer ✓

// Note: typeof is needed to get the TYPE of a value (function or class):
// ReturnType<add>         // ✗ Error: 'add' refers to a value, not a type
// ReturnType<typeof add>  // ✓
```

### Resolution Trace

```ts
// Trace: MyReturnType<typeof add>
// typeof add = (a: number, b: number) => number

// Check: (a: number, b: number) => number extends (...args: any) => infer R?
//   YES — the pattern matches any function shape
//   infer R is bound to: number (the return type position)
// Result: R = number → MyReturnType<typeof add> = number ✓

// Trace: MyParameters<typeof add>
// typeof add = (a: number, b: number) => number

// Check: (a: number, b: number) => number extends (...args: infer P) => any?
//   YES — ...args: infer P captures the parameter list
//   infer P is bound to: [a: number, b: number] (labeled tuple)
// Result: P = [a: number, b: number] ✓

// Trace: MyInstanceType<typeof Timer>
// typeof Timer (constructor type) = new (ms: number) => Timer

// Check: new (ms: number) => Timer extends abstract new (...args: any) => infer R?
//   YES — constructor pattern matches
//   infer R is bound to: Timer (the return type of the constructor = instance type)
// Result: R = Timer ✓
```

### Edge Cases
- `MyReturnType<() => never>` → `never` (function returns never; `infer R = never`).
- `MyReturnType<() => void>` → `void` (void is the return type).
- `MyParameters<() => void>` → `[]` (empty tuple — zero parameters).
- `MyInstanceType<typeof Array>` → `any[]` (Array's constructor returns an array).
- Overloaded functions: TypeScript resolves to the *last* overload's signature for `infer`-based types.

### Follow-up Questions
- "Implement `Awaited<T>` (unwrap nested Promise)?" — `type Awaited<T> = T extends Promise<infer U> ? Awaited<U> : T` (recursive).
- "Implement `Head<T>` (first element of a tuple)?" — `type Head<T extends any[]> = T extends [infer H, ...any[]] ? H : never`.
- "Implement `Tail<T>` (all but first element)?" — `type Tail<T extends any[]> = T extends [any, ...infer Rest] ? Rest : []`.

## Problem 5 — Deep Utility Types

### Problem

Implement `DeepPartial<T>`, `DeepReadonly<T>`, and `DeepRequired<T>` — recursive versions of the shallow utility types that transform nested object properties as well.

```ts
type Config = {
  server: { host: string; port: number };
  db: { url: string; pool: { min: number; max: number } };
  debug: boolean;
};

type DP = DeepPartial<Config>;
// { server?: { host?: string; port?: number }; db?: { url?: string; pool?: { min?: number; max?: number } }; ... }

type DR = DeepReadonly<Config>;
// { readonly server: { readonly host: string; readonly port: number }; ... }
```

### Pattern Recognition
Recursive conditional mapped types — check if the value type is an object; if so, apply the utility recursively; if not (primitive, array, function), return it unchanged. The `T extends object` check at the top determines whether to recurse or stop.

### Key Insight
The recursion base cases: primitive types (`string`, `number`, `boolean`, `symbol`, `bigint`), `null`, `undefined`, `Date`, arrays, and functions should not be recursed into. `T extends object` catches these correctly — but note that arrays ARE objects. For a production-quality implementation, add explicit array handling. Also: TypeScript allows recursive generic type aliases via deferred resolution — the type definition can reference itself as long as the recursion terminates on concrete types.

### Solution

```ts
// DeepPartial — recursively make all object properties optional
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T; // base case: non-object types (string, number, Date, fn) returned as-is

// DeepReadonly — recursively add readonly to all object properties
type DeepReadonly<T> = T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;

// DeepRequired — recursively make all object properties required
type DeepRequired<T> = T extends object
  ? { [K in keyof T]-?: DeepRequired<T[K]> }
  : T;

// DeepMutable — recursively remove readonly from all object properties
type DeepMutable<T> = T extends object
  ? { -readonly [K in keyof T]: DeepMutable<T[K]> }
  : T;

// Verification:
type Config = {
  server: { host: string; port: number };
  options?: { timeout: number; retries?: number };
};

type DP = DeepPartial<Config>;
// {
//   server?: { host?: string; port?: number }; // ← nested objects also partial
//   options?: { timeout?: number; retries?: number };
// }

type DR = DeepReadonly<Config>;
// {
//   readonly server: { readonly host: string; readonly port: number };
//   readonly options?: { readonly timeout: number; readonly retries?: number };
// }

// Handling arrays (arrays are objects — deep partial applies to elements):
type WithArray = DeepPartial<{ tags: string[]; meta: { key: string } }>;
// { tags?: DeepPartial<string[]> → string[] (string is not object, stops);
//   Actually: string[] is an object → Array methods become partial — usually undesirable
// Production fix: add array guard before the object check:
type DeepPartialSafe<T> =
  T extends Array<infer Item>
    ? Array<DeepPartialSafe<Item>> // recurse into array elements
    : T extends object
      ? { [K in keyof T]?: DeepPartialSafe<T[K]> }
      : T;
```

### Resolution Trace

```ts
// Trace: DeepPartial<{ server: { host: string; port: number }; debug: boolean }>

// T = { server: { host: string; port: number }; debug: boolean }
// T extends object? YES → map with ?:

// K='server': T['server'] = { host: string; port: number }
//   → [server]?: DeepPartial<{ host: string; port: number }>
//     inner T extends object? YES → map again:
//     K='host':  [host]?: DeepPartial<string>  → string extends object? NO → string
//     K='port':  [port]?: DeepPartial<number>  → number extends object? NO → number
//     → { host?: string; port?: number }
//   → server?: { host?: string; port?: number } ✓

// K='debug': T['debug'] = boolean
//   → [debug]?: DeepPartial<boolean>  → boolean extends object? NO → boolean
//   → debug?: boolean ✓

// Result: { server?: { host?: string; port?: number }; debug?: boolean } ✓
```

### Edge Cases
- `DeepPartial<Date>` — `Date extends object` is `true`, so all Date methods would become optional. Use the safe version with explicit Date handling: add `T extends Date ? T :` before `T extends object`.
- `DeepReadonly<() => void>` — functions extend object; their properties (like `.call`, `.bind`) would become readonly. Typically acceptable but unusual.
- `null` and `undefined` — not objects; the base case returns them unchanged.

### Follow-up Questions
- "How do you write `DeepPartial<T>` that skips arrays?" — Add `T extends readonly any[] ? T :` before the object check.
- "What is the TypeScript recursion depth limit?" — TypeScript limits instantiation depth (default ~100 levels) to prevent infinite loops. Very deeply nested types hit this limit with an "Excessively deep and possibly infinite" error.

## Problem 6 — API Type Derivation with Utility Types

### Problem

A REST API for a blog platform has a `Post` entity. Using only utility types (no new `interface` definitions allowed), derive all the related types needed for the API layer: the full entity, a creation request, an update request, a public response (without internal fields), and a list summary.

```ts
interface Post {
  id: string;
  title: string;
  content: string;
  authorId: string;
  tags: string[];
  publishedAt: Date | null;
  createdAt: Date;
  updatedAt: Date;
  internalScore: number; // internal ranking, not exposed
}

// Derive:
// CreatePostRequest: everything except auto-generated fields (id, createdAt, updatedAt, internalScore)
// UpdatePostRequest: like CreatePostRequest but all fields optional; must include id
// PublicPost: Post without internalScore; readonly
// PostSummary: only id, title, authorId, tags, publishedAt
// PostIndex: Record mapping post id to PostSummary
```

### Pattern Recognition
Sequential composition of `Omit`, `Partial`, `Pick`, `Required`, `Readonly`, and `Record`. Each derived type is built by composing two or three utility types. The `&` (intersection) operator combines types when you need to add required fields back.

### Key Insight
The "must include id but everything else optional" pattern is: `Pick<T, 'id'> & Partial<Omit<T, 'id'>>`. This is a common update-payload pattern — the identifier is required (for routing) and all other fields are optional (user updates only what changed). The intersection ensures `id` is required even though `Partial` would make it optional.

### Solution

```ts
interface Post {
  id: string; title: string; content: string; authorId: string;
  tags: string[]; publishedAt: Date | null;
  createdAt: Date; updatedAt: Date; internalScore: number;
}

// Type aliases for sets of auto-managed keys (documentation + reuse):
type AutoFields    = 'id' | 'createdAt' | 'updatedAt';
type InternalFields = 'internalScore';

// CreatePostRequest: user provides everything except auto-generated fields
type CreatePostRequest = Omit<Post, AutoFields | InternalFields>;
// { title: string; content: string; authorId: string; tags: string[]; publishedAt: Date | null }

// UpdatePostRequest: id required (for routing), everything else optional
type UpdatePostRequest = Pick<Post, 'id'> & Partial<Omit<Post, AutoFields | InternalFields>>;
// { id: string; title?: string; content?: string; authorId?: string; ... }

// PublicPost: strip internal score, make readonly (immutable from API consumer's perspective)
type PublicPost = Readonly<Omit<Post, InternalFields>>;
// { readonly id: string; readonly title: string; ... (no internalScore) }

// PostSummary: just the list-view fields
type PostSummary = Pick<Post, 'id' | 'title' | 'authorId' | 'tags' | 'publishedAt'>;
// { id: string; title: string; authorId: string; tags: string[]; publishedAt: Date | null }

// PostIndex: map from post ID to its summary (for O(1) lookup by ID)
type PostIndex = Record<string, PostSummary>;
// { [id: string]: PostSummary }

// API function signatures — types compose naturally:
declare function createPost(data: CreatePostRequest): Promise<PublicPost>;
declare function updatePost(data: UpdatePostRequest): Promise<PublicPost>;
declare function getPostList(): Promise<PostSummary[]>;
declare function getPostIndex(): Promise<PostIndex>;

// Validation: CreatePostRequest must have all required fields
const validCreate: CreatePostRequest = {
  title: 'Hello World', content: '...', authorId: 'u1',
  tags: ['intro'], publishedAt: null
}; // ✓

// Validation: UpdatePostRequest requires id, rest optional
const validUpdate: UpdatePostRequest = { id: 'p1', title: 'Updated Title' }; // ✓
const badUpdate: UpdatePostRequest  = { title: 'No ID' }; // ✗ Error: id required
```

### Resolution Trace

```ts
// Trace: UpdatePostRequest
// = Pick<Post, 'id'> & Partial<Omit<Post, AutoFields | InternalFields>>

// Step 1: AutoFields | InternalFields = 'id'|'createdAt'|'updatedAt'|'internalScore'

// Step 2: Omit<Post, 'id'|'createdAt'|'updatedAt'|'internalScore'>
//       = { title: string; content: string; authorId: string; tags: string[]; publishedAt: Date|null }

// Step 3: Partial<step 2>
//       = { title?: string; content?: string; authorId?: string; tags?: string[]; publishedAt?: Date|null }

// Step 4: Pick<Post, 'id'>
//       = { id: string }

// Step 5: step4 & step3 (intersection)
//       = { id: string; title?: string; content?: string; authorId?: string; ... }
//         ^^^required^^  ^^^^all optional from Partial ^^^^^^^^^^^^^^^^^^^^^^^^^^^
// ✓
```

### Edge Cases
- `Partial<Omit<Post, 'id'>> & Pick<Post, 'id'>` is the same type as above — intersection is commutative for property types.
- `Record<Post['id'], PostSummary>` (using the ID's type directly) is equivalent to `Record<string, PostSummary>` since `Post['id'] = string`.
- Deep nesting: if `Post` had nested objects that also need partial treatment in `UpdatePostRequest`, use `DeepPartial` instead of `Partial`.

### Follow-up Questions
- "How would you type a `PATCH /posts/:id` endpoint that can update any subset of fields?" — `UpdatePostRequest` exactly models this pattern.
- "Type a response that includes either the full post or an error?" — `PublicPost | { error: string; code: number }` (union type).

## Problem 7 — Form State and Validation Typing

### Problem

Type a generic form system where each form field can be in different states. Use utility types to derive error, touched, and dirty state types from the form value type. No new interfaces allowed — derive everything from the base type.

```ts
type LoginForm = {
  email: string;
  password: string;
  rememberMe: boolean;
};

// Derive:
// FormErrors<T>    — same keys as T, all optional, each a string error message
// FormTouched<T>   — same keys as T, all optional, each a boolean
// FormDirty<T>     — same keys as T, all required, each a boolean
// FormState<T>     — the full form state: values + errors + touched + dirty
// FieldNames<T>    — union of all field names as a string literal type
```

### Pattern Recognition
`Record` for fixed-value mappings (`boolean` for each key). `Partial` for optional entries. `keyof T` for field names. `Mapped types with fixed value types` for homogeneous schemas. Composition via object intersection for `FormState`.

### Key Insight
When every key maps to the same value type (like `boolean` or `string`), that is exactly what `Record<K, V>` models. But here the keys must match `keyof T` — so the pattern is `{ [K in keyof T]: FixedType }` (a mapped type with a fixed value, not `T[K]`). For optional entries, add `?`. `FieldNames<T>` is simply `keyof T` with a string constraint.

### Solution

```ts
// FormErrors: same keys as T, all optional, value is an error message string
type FormErrors<T> = {
  [K in keyof T]?: string; // optional: if no error, key is absent
};

// FormTouched: same keys as T, all optional, value is boolean (was field touched?)
type FormTouched<T> = {
  [K in keyof T]?: boolean; // optional: absent means "not yet touched"
};

// FormDirty: same keys as T, all required, value is boolean (has field changed?)
type FormDirty<T> = {
  [K in keyof T]: boolean; // required: every field has a dirty status
};

// FieldNames: union of all field name strings
type FieldNames<T> = Extract<keyof T, string>;
// Extract removes number and symbol from keyof T — keeps only string keys

// FormState: composed form metadata type
type FormState<T> = {
  values:    T;              // current values
  errors:    FormErrors<T>;  // optional validation errors
  touched:   FormTouched<T>; // optional touched flags
  dirty:     FormDirty<T>;   // required dirty flags (initialized to false)
  isValid:   boolean;
  isSubmitting: boolean;
};

// Derived types for LoginForm:
type LoginForm = { email: string; password: string; rememberMe: boolean };

type LoginErrors  = FormErrors<LoginForm>;
// { email?: string; password?: string; rememberMe?: string }

type LoginTouched = FormTouched<LoginForm>;
// { email?: boolean; password?: boolean; rememberMe?: boolean }

type LoginDirty   = FormDirty<LoginForm>;
// { email: boolean; password: boolean; rememberMe: boolean }

type LoginState   = FormState<LoginForm>;
type LoginField   = FieldNames<LoginForm>; // 'email' | 'password' | 'rememberMe'

// Factory function — types compose directly:
function createFormState<T extends Record<string, unknown>>(
  initialValues: T
): FormState<T> {
  return {
    values: initialValues,
    errors: {},                        // FormErrors<T>: empty object is valid (all optional)
    touched: {},                       // FormTouched<T>: empty object is valid (all optional)
    dirty: Object.fromEntries(         // FormDirty<T>: all required, all false
      Object.keys(initialValues).map(k => [k, false])
    ) as FormDirty<T>,
    isValid: true,
    isSubmitting: false,
  };
}

// Field-level update helper — type-safe field name and value:
function setFieldValue<T, K extends FieldNames<T>>(
  state: FormState<T>,
  field: K,
  value: T[K]                    // value type matches the field's type in T
): FormState<T> {
  return {
    ...state,
    values:  { ...state.values, [field]: value },
    dirty:   { ...state.dirty,  [field]: true },
    touched: { ...state.touched, [field]: true },
  };
}

// Type-safe: field name enforced, value type enforced
const initial = createFormState<LoginForm>({ email: '', password: '', rememberMe: false });
const updated = setFieldValue(initial, 'email', 'ada@example.com'); // ✓
const bad     = setFieldValue(initial, 'email', 42);               // ✗ Error: 42 not string
const worse   = setFieldValue(initial, 'username', 'ada');         // ✗ Error: 'username' not a field
```

### Resolution Trace

```ts
// Trace: FormDirty<LoginForm>
// type FormDirty<T> = { [K in keyof T]: boolean }
// T = LoginForm = { email: string; password: string; rememberMe: boolean }
// keyof T = 'email' | 'password' | 'rememberMe'

// Map each key to boolean:
// K='email':      email: boolean
// K='password':   password: boolean
// K='rememberMe': rememberMe: boolean

// Result: { email: boolean; password: boolean; rememberMe: boolean } ✓

// Trace: FieldNames<LoginForm>
// = Extract<keyof LoginForm, string>
// keyof LoginForm = 'email' | 'password' | 'rememberMe' (all strings in this case)
// Extract<'email'|'password'|'rememberMe', string>
// = each member extends string → all kept
// = 'email' | 'password' | 'rememberMe' ✓
```

### Edge Cases
- `FormErrors<T>` values are `string | undefined` at runtime (optional); accessing `errors.nonexistent` is `undefined`.
- `FormDirty<T>` requires ALL keys — creating an initial state with `{}` is a type error. Must explicitly initialize all fields to `false`.
- `FieldNames<T>` with `Extract<keyof T, string>`: `keyof T` may include `number` (for array types) or `symbol`; `Extract` removes these to give only string key names.

### Follow-up Questions
- "Type a `validateField<T, K>(field: K, value: T[K]): string | undefined` function?" — The signature uses `K extends FieldNames<T>` and `T[K]` for the value type, then returns an error message or undefined.
- "How would `FormErrors` differ if errors could be arrays of strings?" — Change the value type: `type FormErrors<T> = { [K in keyof T]?: string[] }`.

## Quick Reference — Utility Type Decision Tree

```
What do you need to do with a type?
│
├── TRANSFORM PROPERTY MODIFIERS (optional, required, readonly)?
│   ├── Make ALL properties optional     → Partial<T>
│   ├── Make ALL properties required     → Required<T>
│   ├── Make ALL properties readonly     → Readonly<T>
│   └── Remove readonly from properties  → custom Mutable<T> = { -readonly [K in keyof T]: T[K] }
│
├── SELECT OR EXCLUDE PROPERTIES?
│   ├── Keep specific named properties   → Pick<T, 'a' | 'b'>
│   ├── Remove specific named properties → Omit<T, 'a' | 'b'>
│   └── On a discriminated union:        → DistributiveOmit/DistributivePick
│         type DistributiveOmit<T,K> = T extends any ? Omit<T,K> : never
│
├── CREATE AN OBJECT TYPE WITH KNOWN KEYS?
│   ├── Specific literal keys, same value type  → Record<'a' | 'b', V>
│   ├── Any string key, same value type         → Record<string, V>
│   └── Per-key value type from another type    → { [K in keyof T]: ... } (mapped type)
│
├── FILTER MEMBERS OF A UNION TYPE?
│   ├── Remove members assignable to U → Exclude<T, U>  (T - U)
│   ├── Keep members assignable to U   → Extract<T, U>  (T ∩ U)
│   └── Remove null and undefined      → NonNullable<T>
│
├── INTROSPECT A FUNCTION TYPE?
│   ├── Get the return type             → ReturnType<typeof fn>
│   ├── Get the parameter tuple         → Parameters<typeof fn>
│   ├── Get a specific parameter        → Parameters<typeof fn>[N]
│   └── Get resolved async return      → Awaited<ReturnType<typeof fn>>
│
├── INTROSPECT A CLASS (CONSTRUCTOR) TYPE?
│   ├── Get the instance type           → InstanceType<typeof MyClass>
│   └── Get the constructor params      → ConstructorParameters<typeof MyClass>
│
├── APPLY TRANSFORMATIONS RECURSIVELY (nested objects too)?
│   ├── Deep Partial    → type DeepPartial<T> = T extends object ? {[K in keyof T]?: DeepPartial<T[K]>} : T
│   ├── Deep Readonly   → type DeepReadonly<T> = T extends object ? {readonly [K in keyof T]: DeepReadonly<T[K]>} : T
│   └── Deep Required   → type DeepRequired<T> = T extends object ? {[K in keyof T]-?: DeepRequired<T[K]>} : T
│
├── COMPOSE MULTIPLE UTILITY TYPES?
│   ├── Pipeline: Partial<Omit<T, 'id'>>
│   ├── Add required fields back: Pick<T,'id'> & Partial<Omit<T,'id'>>
│   └── Conditional: T extends string ? Exclude<T,'error'> : T
│
└── EXTRACT A SUB-TYPE FROM A COMPOUND TYPE (infer)?
    ├── From array element: T extends (infer E)[] ? E : never
    ├── From Promise:       T extends Promise<infer U> ? U : T
    ├── From tuple head:    T extends [infer H, ...any[]] ? H : never
    └── From union:         Use Extract/Exclude instead of infer
```

## Common Bugs Checklist

Before writing or using utility types, verify:

1. **Using `ReturnType<fn>` instead of `ReturnType<typeof fn>`?** — `fn` without `typeof` refers to the *value* (the function itself, not its type). TypeScript generic parameters expect types, not values. `ReturnType<fn>` is a type error: `fn` is a value. Always use `typeof fn` to get the type of a function value: `ReturnType<typeof fn>`. Same for `Parameters`, `InstanceType`, and `ConstructorParameters`.

2. **Applying `Omit` to a discriminated union and losing the discriminant?** — `Omit<UnionType, 'someKey'>` applies `Omit` to the merged union structure, collapsing all members into one type. The discriminant (`kind`, `type`, `tag`) and member-specific properties are all merged. Use `DistributiveOmit<T, K> = T extends any ? Omit<T, K> : never` to apply `Omit` per union member, preserving each member's structure independently.

3. **`Partial<T>` not making nested properties optional?** — `Partial` is *shallow* — it only adds `?` to the top-level properties. `Partial<{ server: { host: string } }>` produces `{ server?: { host: string } }` — `host` inside `server` is still required. For deep optionality, implement or import `DeepPartial` (recursive conditional mapped type).

4. **Using `|` instead of `&` to combine a required field with optional fields?** — `{ id: string } | Partial<Omit<T, 'id'>>` is a UNION (either an id-only object OR a partial T), not the intended intersection. Use `{ id: string } & Partial<Omit<T, 'id'>>` — an INTERSECTION — to get an object that requires `id` AND allows the other fields optionally.

5. **`keyof (A | B)` giving fewer keys than expected?** — `keyof (A | B)` = `keyof A & keyof B` — only the keys common to BOTH types. To get all keys: use `keyof A | keyof B`, or work with `keyof (A & B)` = `keyof A | keyof B`. The mnemonic: union types have FEWER accessible keys (only shared ones are safe); intersection types have MORE accessible keys (all of both are available).

6. **Preventing distribution accidentally — wrapping `T` in a tuple when you want distribution?** — `[T] extends [U] ? X : Y` prevents distribution. If you're writing a utility type intended to filter a union (like `Exclude` or `Extract`), do NOT wrap `T` in a tuple or array — keep it "naked" in the extends clause. Wrapping stops distribution and causes the whole union to be checked at once.

7. **`Extract<T, U>` returning `never` when you expect members?** — Verify that the members of T are actually *assignable* to U. String literals are assignable to `string`, so `Extract<'a' | 'b', string>` = `'a' | 'b'`. But `Extract<string, 'a' | 'b'>` = `never` — `string` is NOT assignable to `'a' | 'b'` (the base type doesn't extend the literal). The relationship is one-directional: literal extends base, not base extends literal.

8. **Using `Record<string, T>` when specific keys are required?** — `Record<string, T>` accepts any string key and doesn't require any to be present; `{}` is a valid `Record<string, T>`. If specific keys must all be present, use `Record<'a' | 'b' | 'c', T>` — TypeScript enforces all three keys are present and no others are (in exact object literal checks).

9. **`InstanceType<MyClass>` instead of `InstanceType<typeof MyClass>`?** — `MyClass` is the *instance* type of the class; `typeof MyClass` is the *constructor* type. `InstanceType<typeof MyClass>` = `MyClass` (the instance type). `InstanceType<MyClass>` attempts to use the instance type as a constructor — this is a type error since instances are not constructors.

10. **Forgetting that `infer` only works in the `extends` clause of a conditional type?** — `type Foo<T> = infer R` is a syntax error. `type Foo<T> = T extends Promise<infer R> ? R : never` is correct. `infer` declares a type variable *during pattern matching* — it has no meaning outside of a `T extends Pattern<infer R>` expression.

---

**Final Tip:** At the 5 YOE level, the decisive signal for TypeScript utility type questions is knowing *which of the two underlying mechanisms each type uses* — and deriving the implementation from that mechanism rather than memorizing syntax. The two mechanisms: **mapped types** (`{ [K in keyof T]?: T[K] }`) for transforming *object property modifiers and structure* — all of `Partial`, `Required`, `Readonly`, `Pick`, `Omit`, and `Record` are mapped types; and **distributive conditional types** (`T extends U ? X : Y`) for *filtering union members* — `Exclude`, `Extract`, and `NonNullable` are all `T extends U ? ... : ...` patterns that distribute over union members. `ReturnType`, `Parameters`, and `InstanceType` combine both: a conditional type with `infer` to extract sub-types from a structural pattern. The `infer` keyword is the bridge: *"in the extends clause, pattern-match the type and capture the sub-type at this position into R."* Understanding this: *"Exclude distributes because T is naked in the extends position; wrapping T in [T] stops distribution; `never` in a union dissolves; `infer R` captures whatever occupies that structural position"* — these four principles let you derive any utility type implementation from first principles at the whiteboard.
