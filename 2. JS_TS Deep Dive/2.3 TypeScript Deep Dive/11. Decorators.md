## Topic A: Decorator Fundamentals

### Section A1: Core Mechanics

**Q1. What is a decorator, what problem does it solve, and what TypeScript configuration enables it?**

A: A decorator is a special kind of declaration prefixed with `@` that attaches to a class, method, property, or parameter and can observe, modify, or replace it at class-definition time. Decorators solve the **cross-cutting concern** problem: logic like logging, validation, rate limiting, dependency injection, and routing registration must be applied consistently across many methods/classes — decorators allow this logic to be written once and applied declaratively. Without decorators, this code lives in every method body or in manual wrapper functions. Two `tsconfig.json` flags enable them:

```json
{
  "compilerOptions": {
    "experimentalDecorators": true,    // enables @Decorator syntax
    "emitDecoratorMetadata": true      // emits type metadata for reflect-metadata
  }
}
```

`emitDecoratorMetadata` instructs the TypeScript compiler to emit calls to `Reflect.metadata` for design-time type information (`design:type`, `design:paramtypes`, `design:returntype`) — this is the foundation NestJS uses for dependency injection. Without it, the runtime has no knowledge of TypeScript's compile-time types. The `reflect-metadata` polyfill package must also be imported once at the application entry point: `import 'reflect-metadata'`.

**Q2. What are the four decorator types, and what arguments does each receive at runtime?**

A: Each decorator type receives a different set of arguments that identifies the decoration target:

```ts
// CLASS DECORATOR — receives the constructor function
function ClassDec(target: Function) { }
// target: the class constructor itself (not an instance)

// METHOD DECORATOR — receives target, method name, and descriptor
function MethodDec(
  target: object,            // prototype (instance method) or constructor (static method)
  propertyKey: string | symbol, // method name
  descriptor: PropertyDescriptor // { value, writable, enumerable, configurable }
) { }

// PROPERTY DECORATOR — receives target and property name
function PropDec(
  target: object,               // prototype (instance) or constructor (static)
  propertyKey: string | symbol  // property name
) { }
// Note: no descriptor, no return value used — metadata storage is the primary use

// PARAMETER DECORATOR — receives target, method name, and parameter index
function ParamDec(
  target: object,               // prototype or constructor
  propertyKey: string | symbol | undefined, // undefined for constructor params
  parameterIndex: number        // 0-based position of the parameter
) { }
```

**Q3. What is a decorator factory, and why does NestJS use it almost exclusively?**

A: A decorator factory is a function that *returns* a decorator function. Calling `@Injectable()` invokes `Injectable` as a factory (note the parentheses) which returns the actual decorator. The factory pattern enables **parameterized decorators** — passing configuration to the decorator at the call site: `@Throttle({ limit: 10, ttl: 60 })` passes the throttle configuration into the factory, which captures it in a closure before returning the actual decorator function. NestJS uses factories almost exclusively because: (1) every `@Controller('/path')`, `@Get(':id')`, `@Injectable()` carries configuration; (2) factories allow the same decorator to behave differently based on parameters; (3) even `@Injectable()` with no arguments uses a factory so the API is consistent and future parameters can be added without a breaking change.

```ts
// Direct decorator (no arguments):
function Injectable(target: Function) {
  Reflect.defineMetadata('injectable', true, target);
}
@Injectable  // no parentheses — applied directly

// Decorator factory (arguments supported):
function Injectable(options?: { scope?: 'singleton' | 'transient' }) {
  return function(target: Function) {         // returns the actual decorator
    Reflect.defineMetadata('injectable', true, target);
    Reflect.defineMetadata('scope', options?.scope ?? 'singleton', target);
  };
}
@Injectable()           // parentheses — factory called → decorator returned → applied
@Injectable({ scope: 'transient' })  // with options
```

**Q4. What is the evaluation and application order when multiple decorators are stacked?**

A: Stacked decorators follow two distinct phases that run in opposite directions: **Evaluation (top to bottom)**: factory functions are called in the order they appear, top to bottom. **Application (bottom to top)**: the decorator functions returned by the factories are applied from innermost (closest to the target) to outermost. This means the bottom decorator executes first, and the top decorator "wraps" all others — analogous to function composition `f(g(h(x)))`.

```ts
@D1  // factory D1 called first; decorator D1 applied LAST (outermost wrapper)
@D2  // factory D2 called second; decorator D2 applied second
@D3  // factory D3 called third; decorator D3 applied FIRST (innermost)
class Example {}

// Execution order: D1 factory → D2 factory → D3 factory → D3 applied → D2 applied → D1 applied

// Within a single class definition, the FULL ordering across all decorator types:
// 1. Parameter decorators (for constructors)
// 2. Property decorators (each property in source order)
// 3. Method decorators (each method in source order)
// 4. Parameter decorators (for each method, evaluated bottom to top by parameter)
// 5. Class decorator (last, after all members)
```

**Q5. What does a class decorator receive, what can it return, and what are the two patterns for using it?**

A: A class decorator receives the **constructor function** (`target: Function`). It can return: (1) **`undefined` or `void`** — modifies the class in-place (adds to prototype, sets metadata) without replacing the constructor; (2) **a new constructor** — replaces the class entirely; the returned constructor must be compatible with the original (same signature or extend it). Two patterns: **Metadata pattern** (most common in NestJS): store metadata on the constructor using `Reflect.defineMetadata`, which NestJS reads later to configure routes, DI, guards, etc. **Wrapping pattern**: return a subclass that extends the original constructor to augment behavior.

```ts
// Pattern 1: Metadata (NestJS style)
function Controller(path: string) {
  return function(target: Function) {
    Reflect.defineMetadata('path', path, target);
    Reflect.defineMetadata('isController', true, target);
    // target itself is unchanged; metadata is attached externally
  };
}

// Pattern 2: Constructor wrapping (returns a new class)
function Sealed<T extends new (...args: any[]) => {}>(target: T): T {
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      Object.seal(this);  // prevent property addition after construction
    }
  };
}

// IMPORTANT: the returned class must be assignable to T
// TypeScript checks this via the generic constraint
```

**Q6. What does a method decorator receive, and how does mutating the `PropertyDescriptor` wrap the method?**

A: A method decorator receives `target` (prototype or constructor), `propertyKey` (method name), and `descriptor` (a `PropertyDescriptor` with the method as `descriptor.value`). To wrap the method: save a reference to `descriptor.value` (the original method), reassign `descriptor.value` to a new function that calls the original via `.apply(this, args)`, and return the modified `descriptor`. The return value of the decorator replaces the descriptor for that property. Using `originalMethod.apply(this, args)` is critical: `this` is the *caller's* `this` (the object instance), not captured at decoration time — using an arrow function for the replacement would freeze `this` to the wrong scope.

```ts
function Log(target: object, key: string, descriptor: PropertyDescriptor): PropertyDescriptor {
  const original = descriptor.value; // save reference to original method

  descriptor.value = function(this: unknown, ...args: unknown[]) {
    // `this` here is the CALLING instance — correct because this is a regular function
    console.log(`→ ${key}(${JSON.stringify(args)})`);
    const result = original.apply(this, args); // call original with correct `this`
    console.log(`← ${key} returned:`, result);
    return result;
  };

  return descriptor; // returning descriptor replaces the property definition
  // Alternatively: modify descriptor.value in-place (same effect since descriptor is a reference)
}

// WRONG: arrow function loses caller's `this`:
// descriptor.value = (...args) => original.apply(this, args);
// `this` here is captured from the outer scope (the decorator's context), not the instance
```

**Q7. What does a property decorator receive, why can't it return a useful value, and how is it used in practice?**

A: A property decorator receives `target` (prototype for instance properties) and `propertyKey` (property name). It cannot receive a `PropertyDescriptor` because TypeScript does not create descriptor objects for class properties at decoration time — property declarations like `name: string` are just type annotations; no runtime value is created until an instance sets one. The return value of a property decorator is **ignored** (by specification). The primary use is **storing metadata**: `Reflect.defineMetadata('design:type', ...)` alongside custom metadata like validation rules. The metadata is later read by class-level decorators or utility functions that know to look for it.

```ts
// WRONG expectation — can't intercept property get/set this way:
function Readonly(target: object, key: string) {
  // return { writable: false }; // ← IGNORED by TypeScript
}

// CORRECT — store metadata for later use:
function Required(target: object, key: string) {
  // Get existing required fields list (may have been set by previous @Required on another field)
  const fields: string[] = Reflect.getOwnMetadata('required_fields', target) ?? [];
  fields.push(key);
  Reflect.defineMetadata('required_fields', fields, target);
}

// To intercept get/set, use Object.defineProperty on the prototype:
function DefaultValue(value: unknown) {
  return function(target: object, key: string) {
    Object.defineProperty(target, key, {
      get() { return this[`__${key}`] ?? value; },
      set(v) { this[`__${key}`] = v; },
      enumerable: true, configurable: true,
    });
  };
}
```

**Q8. What does a parameter decorator receive, how is `parameterIndex` used, and what is the constructor parameter special case?**

A: A parameter decorator receives: `target` (the class prototype, or the constructor itself for static method parameters), `propertyKey` (the method name containing the parameter — `undefined` when decorating a constructor parameter), and `parameterIndex` (the 0-based index of the parameter in the method's parameter list). The decorator cannot change what value the parameter receives — it can only *store metadata* indicating how the parameter should be resolved. The framework (NestJS, tsyringe, etc.) reads this metadata when calling the method to determine how to populate each argument.

```ts
// Storing which parameter index wants what data:
function Body(target: object, key: string, index: number) {
  const params: number[] = Reflect.getOwnMetadata('body_params', target, key) ?? [];
  params.push(index);
  Reflect.defineMetadata('body_params', params, target, key);
}

// Constructor parameter example (propertyKey is undefined):
function Inject(token: string) {
  return function(target: Function, key: undefined, index: number) {
    // key is undefined — decorating a constructor parameter, not a method param
    const tokens: Map<number, string> = Reflect.getOwnMetadata('inject_tokens', target) ?? new Map();
    tokens.set(index, token);
    Reflect.defineMetadata('inject_tokens', target, tokens);
  };
}

class UserService {
  constructor(
    @Inject('DATABASE_URL') private dbUrl: string,  // index=0, key=undefined
    @Body() private body: any,                       // ← WRONG context: Body is for methods
  ) {}
}
```

**Q9. What is `reflect-metadata`, what does `emitDecoratorMetadata` emit, and what are the three design-time metadata keys?**

A: `reflect-metadata` is a polyfill for the [Metadata Reflection API](https://rbuckton.github.io/reflect-metadata/) — it extends the global `Reflect` object with `defineMetadata`, `getMetadata`, `getOwnMetadata`, and `hasMetadata` methods. It provides a WeakMap-backed store that associates arbitrary key-value metadata with a class or class member. `emitDecoratorMetadata: true` instructs the TypeScript compiler to automatically emit `Reflect.metadata(...)` calls that record three type information keys: **`design:type`** — the declared type of a property; **`design:paramtypes`** — an array of constructor/method parameter types; **`design:returntype`** — the return type of a method. These are the only TypeScript type information that survives to runtime, making them the foundation of NestJS's dependency injection.

```ts
import 'reflect-metadata';

class DatabaseService { query(sql: string): any[] { return []; } }

class UserService {
  constructor(private db: DatabaseService) {}
  findAll(): string[] { return []; }
}

// TypeScript emits (equivalent to):
Reflect.metadata('design:paramtypes', [DatabaseService])(UserService);
Reflect.metadata('design:returntype', Array)(UserService.prototype, 'findAll');

// Reading at runtime:
const paramTypes = Reflect.getMetadata('design:paramtypes', UserService);
// → [DatabaseService]  ← the CONSTRUCTOR FUNCTION for DatabaseService
// NestJS reads this to know it must resolve a DatabaseService instance to inject

const returnType = Reflect.getMetadata('design:returntype', UserService.prototype, 'findAll');
// → Array

// Custom metadata:
Reflect.defineMetadata('my_key', 'my_value', UserService);
Reflect.getMetadata('my_key', UserService); // 'my_value'
Reflect.getOwnMetadata('my_key', UserService); // 'my_value' (doesn't walk prototype chain)
```

### Section A2: Metadata and NestJS Foundation

**Q10. How does `design:paramtypes` enable constructor injection in NestJS, and what are its limitations?**

A: NestJS reads `design:paramtypes` from each `@Injectable()` class to determine what to inject into the constructor. The resolved value is an array of constructor functions — one per parameter — which NestJS uses as DI tokens to look up registered providers. This creates an automatic injection system where no `@Inject()` decorator is needed for class-typed dependencies: TypeScript's type annotation `private db: DatabaseService` becomes `[DatabaseService]` in `design:paramtypes`, and NestJS resolves `DatabaseService` from its IoC container automatically. Limitations: (1) **Interface types erase to `Object`** — TypeScript interfaces have no runtime representation; `private svc: IUserService` emits `Object`, not `IUserService`. Use `@Inject('TOKEN')` with a string or symbol token for interfaces. (2) **Circular dependencies** produce `undefined` in `design:paramtypes` — use `forwardRef(() => ServiceClass)`. (3) **Primitive types** emit as their wrapper constructor (`String`, `Number`, `Boolean`) — always inject primitives with `@Inject('CONFIG_TOKEN')`.

```ts
@Injectable()
class UserController {
  constructor(
    private userService: UserService,    // design:paramtypes → [UserService, ...]
    private dbService: DatabaseService,  // design:paramtypes → [..., DatabaseService]
    @Inject('CONFIG') private config: AppConfig // @Inject needed: AppConfig is an interface
  ) {}
}

// What TypeScript emits:
Reflect.metadata('design:paramtypes', [UserService, DatabaseService, Object])(UserController);
//                                       ↑ class ref   ↑ class ref    ↑ interface → Object (lost!)
// NestJS resolves UserService and DatabaseService by their constructor;
// for 'CONFIG', it uses the string token from @Inject
```

**Q11. What is the full decorator execution order within a class definition, and why does it matter?**

A: Within a class definition, TypeScript evaluates decorators in this order: (1) **Parameter decorators for each instance method**, in order of source appearance; (2) **Method decorators for each instance method**, in order of source appearance; (3) **Property decorators for each instance property**, in order of source appearance; (4) **Parameter decorators for the constructor**; (5) **The class decorator** (always last). For stacked decorators on a single target, factory functions are called top-to-bottom and decorator functions are applied bottom-to-top. This order matters for metadata: the class decorator always runs after all property and method decorators, so it can aggregate metadata already written by those member decorators.

```ts
@ClassDec      // Applied 8th (last)
class Example {
  @PropDec     // Applied 3rd
  name: string;

  @MethodDec   // Applied 5th (after parameter decorators of this method)
  greet(
    @ParamDec1 a: string, // Applied 4th (bottom-to-top: ParamDec2 before ParamDec1)
    @ParamDec2 b: number  // Applied (evaluated after ParamDec1 but applied first)
  ) {}

  @MethodDec2  // Applied 7th
  other(
    @ParamDec3 c: boolean // Applied 6th
  ) {}
}

// Key insight: @ClassDec can read ALL metadata set by ALL member decorators
// because member decorators have already executed when @ClassDec runs.
```

**Q12. What is the `Reflect.getMetadata` vs `Reflect.getOwnMetadata` distinction, and why does it matter for class inheritance?**

A: `Reflect.getMetadata(key, target)` walks the prototype chain — it checks `target` first, then each prototype in order, returning the first match. `Reflect.getOwnMetadata(key, target)` only checks `target` itself, not the chain. For decorators on class hierarchies: if a base class stores metadata and a subclass inherits, `getMetadata` on the subclass finds the base class's metadata; `getOwnMetadata` returns `undefined` (the subclass has no own metadata). This distinction is critical for NestJS guards and interceptors: `getMetadata` on an instance's constructor correctly finds metadata set on a parent class, allowing guards to apply to inherited methods.

```ts
@Roles('admin')
class BaseController {
  @Get('/')
  base() {}
}

class UserController extends BaseController {
  // No @Roles decorator here
  @Get('/users')
  list() {}
}

// Checking roles on UserController:
Reflect.getMetadata('roles', UserController);    // 'admin' (inherited from BaseController)
Reflect.getOwnMetadata('roles', UserController); // undefined (not defined on UserController itself)

// NestJS guards use getMetadata to correctly inherit class-level metadata in subclasses
```

## Topic B: NestJS Decorator Patterns

### Section B1: Core NestJS Decorators Internals

**Q13. How does `@Injectable()` work under the hood to register a class in NestJS's DI container?**

A: `@Injectable()` does two things: (1) stores a metadata flag `IS_INJECTABLE` on the class constructor so NestJS can verify the class is DI-managed; (2) marks the class for `design:paramtypes` metadata emission — TypeScript emits this metadata for any decorated class when `emitDecoratorMetadata` is on. NestJS's `ModuleRef` and `NestContainer` read `design:paramtypes` at module compilation time to build a dependency graph. The actual DI container stores the class as a provider, resolves its dependencies recursively, and instantiates it (lazily or eagerly depending on module scope). `@Injectable()` itself doesn't *register* the class — it must also appear in a `@Module({ providers: [...] })` for NestJS to know the class is part of the application graph.

```ts
// Simplified @Injectable implementation:
const INJECTABLE_WATERMARK = 'injectable';

function Injectable(): ClassDecorator {
  return function(target: Function) {
    // Mark as injectable (guards against injecting non-decorated classes)
    Reflect.defineMetadata(INJECTABLE_WATERMARK, true, target);
    // TypeScript already emits design:paramtypes for decorated classes,
    // so NestJS can read constructor dependencies automatically
  };
}

// At module compilation, NestJS does roughly:
function resolve<T>(token: new (...args: any[]) => T): T {
  const paramTypes: Function[] = Reflect.getMetadata('design:paramtypes', token) ?? [];
  const deps = paramTypes.map(dep => resolve(dep)); // recursive resolution
  return new token(...deps);
}
```

**Q14. How do `@Controller()` and `@Get()`, `@Post()` etc. register routes using metadata?**

A: `@Controller(path)` stores the base path as metadata on the class. Each HTTP method decorator (`@Get`, `@Post`, etc.) stores the sub-path and HTTP method on the method. NestJS's router reads these two layers of metadata to register routes with the underlying HTTP framework (Express or Fastify). The key insight: NestJS iterates all methods of the controller, reads method-level metadata, prepends the class-level path, and calls `app.get(fullPath, handler)` (or equivalent). This entirely separates route declaration from route registration logic.

```ts
const PATH_METADATA      = 'path';
const METHOD_METADATA    = 'method';
const IS_CONTROLLER_META = 'isController';

function Controller(path = ''): ClassDecorator {
  return (target) => {
    Reflect.defineMetadata(PATH_METADATA, path, target);
    Reflect.defineMetadata(IS_CONTROLLER_META, true, target);
  };
}

function createMethodDecorator(method: string) {
  return (path = ''): MethodDecorator =>
    (target, key, descriptor) => {
      Reflect.defineMetadata(PATH_METADATA,   path,   descriptor.value!);
      Reflect.defineMetadata(METHOD_METADATA, method, descriptor.value!);
      return descriptor;
    };
}

const Get  = createMethodDecorator('GET');
const Post = createMethodDecorator('POST');
const Put  = createMethodDecorator('PUT');

// NestJS router registration (simplified):
function registerController(app: any, ControllerClass: new () => any) {
  const basePath    = Reflect.getMetadata(PATH_METADATA, ControllerClass) ?? '';
  const instance    = new ControllerClass();
  const prototype   = Object.getPrototypeOf(instance);

  Object.getOwnPropertyNames(prototype)
    .filter(key => key !== 'constructor')
    .forEach(key => {
      const handler = prototype[key];
      const route   = Reflect.getMetadata(PATH_METADATA,   handler);
      const method  = Reflect.getMetadata(METHOD_METADATA, handler);
      if (route !== undefined && method) {
        app[method.toLowerCase()](`${basePath}${route}`, handler.bind(instance));
      }
    });
}
```

**Q15. How do `@Body()`, `@Param()`, `@Query()` parameter decorators work in NestJS?**

A: These route parameter decorators mark specific constructor arguments for extraction from the HTTP request. Each stores metadata on the method, recording the parameter's index and what part of the request to extract from. When NestJS calls the route handler, it reads this metadata for all parameters and builds the argument array before invoking the method. The metadata key typically encodes both the extraction type and the optional sub-key (e.g., `Param('id')` → extract `req.params.id`).

```ts
// Metadata structure: { paramtype: 'BODY'|'PARAM'|'QUERY', key?: string, index: number }[]

const ROUTE_ARGS_METADATA = 'route_args';

function createRouteParamDecorator(paramtype: string) {
  return (key?: string): ParameterDecorator =>
    (target, methodKey, paramIndex) => {
      const existing: any[] =
        Reflect.getOwnMetadata(ROUTE_ARGS_METADATA, target, methodKey!) ?? [];
      existing.unshift({ paramtype, key, index: paramIndex });
      Reflect.defineMetadata(ROUTE_ARGS_METADATA, existing, target, methodKey!);
    };
}

const Body  = createRouteParamDecorator('BODY');
const Param = createRouteParamDecorator('PARAM');
const Query = createRouteParamDecorator('QUERY');

// When NestJS calls a handler, it resolves parameters by reading metadata:
function resolveArgs(request: any, response: any, target: object, methodKey: string): any[] {
  const paramsMeta: any[] = Reflect.getOwnMetadata(ROUTE_ARGS_METADATA, target, methodKey) ?? [];
  return paramsMeta
    .sort((a, b) => a.index - b.index) // ensure correct positional order
    .map(({ paramtype, key }) => {
      if (paramtype === 'BODY')  return key ? request.body[key]   : request.body;
      if (paramtype === 'PARAM') return key ? request.params[key] : request.params;
      if (paramtype === 'QUERY') return key ? request.query[key]  : request.query;
    });
}
```

**Q16. How do `@UseGuards()`, `@UseInterceptors()`, and `@UsePipes()` attach execution pipeline stages?**

A: These decorators attach arrays of pipeline components (guards, interceptors, pipes) as metadata on either a class (applies to all methods) or a specific method. NestJS reads the metadata at request time to build the execution pipeline. Class-level and method-level metadata are both read and merged, with method-level metadata taking precedence for overrides. The NestJS request lifecycle executes each stage in order: middleware → guards → interceptors (before) → pipes → route handler → interceptors (after) → exception filters.

```ts
const GUARDS_METADATA      = 'guards';
const INTERCEPTORS_METADATA = 'interceptors';

function UseGuards(...guards: any[]): ClassDecorator & MethodDecorator {
  return (target: any, key?: string | symbol, descriptor?: PropertyDescriptor) => {
    if (descriptor) {
      // Method decorator: apply to specific method
      Reflect.defineMetadata(GUARDS_METADATA, guards, descriptor.value);
      return descriptor;
    }
    // Class decorator: apply to all methods in the class
    Reflect.defineMetadata(GUARDS_METADATA, guards, target);
  };
}

// At request time, NestJS resolves guards by reading from most-specific to least-specific:
function resolveGuards(handler: Function, controllerClass: Function): any[] {
  const classGuards  = Reflect.getMetadata(GUARDS_METADATA, controllerClass) ?? [];
  const methodGuards = Reflect.getMetadata(GUARDS_METADATA, handler) ?? [];
  return [...classGuards, ...methodGuards]; // class guards run first
}
```

**Q17. How does `@Inject()` with a custom token override the automatic `design:paramtypes` resolution?**

A: When `design:paramtypes` emits `Object` for a parameter (interfaces, abstract types, primitives), NestJS can't infer the correct provider. `@Inject(token)` stores an explicit DI token at the parameter's index, which NestJS checks first before falling back to `design:paramtypes`. The token can be a string, symbol, or class — NestJS uses it to look up the registered provider by that token rather than by class type.

```ts
// NestJS's @Inject implementation (simplified):
const SELF_DECLARED_DEPS_METADATA = 'self:paramtypes';

function Inject(token: string | symbol | Function): ParameterDecorator {
  return (target, _key, index) => {
    const deps: Array<{ index: number; token: any }> =
      Reflect.getOwnMetadata(SELF_DECLARED_DEPS_METADATA, target) ?? [];
    deps.push({ index, token });
    Reflect.defineMetadata(SELF_DECLARED_DEPS_METADATA, deps, target);
  };
}

// Resolution logic: @Inject tokens override design:paramtypes
function getConstructorDependencies(target: Function): any[] {
  const paramTypes: Function[] = Reflect.getMetadata('design:paramtypes', target) ?? [];
  const overrides: { index: number; token: any }[] =
    Reflect.getOwnMetadata(SELF_DECLARED_DEPS_METADATA, target) ?? [];

  return paramTypes.map((type, i) => {
    const override = overrides.find(o => o.index === i);
    return override ? override.token : type; // @Inject token takes priority
  });
}
```

### Section B2: Custom Decorators and Advanced Patterns

**Q18. How do you create a custom parameter decorator using NestJS's `createParamDecorator`?**

A: `createParamDecorator` is a NestJS factory that takes a callback `(data, ctx) => value` and returns a parameter decorator. The callback is invoked at *request time* (not at decoration time) with the decorator's argument (`data`) and the current `ExecutionContext`. The ExecutionContext provides access to the HTTP request/response, WebSocket context, or RPC context depending on the transport. Custom param decorators integrate with NestJS's pipe system — they can be combined with `@UsePipes()` or have pipes applied directly: `@CurrentUser(new ValidationPipe())`.

```ts
// createParamDecorator implementation (simplified):
function createParamDecorator<T = any>(
  factory: (data: T, ctx: ExecutionContext) => any
): (data?: T) => ParameterDecorator {
  return (data?: T): ParameterDecorator =>
    (target, key, index) => {
      const params: any[] = Reflect.getOwnMetadata('custom_params', target, key!) ?? [];
      params.push({ index, factory, data });
      Reflect.defineMetadata('custom_params', params, target, key!);
    };
}

// Usage — extract user from request:
const CurrentUser = createParamDecorator(
  (field: keyof User | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest<Request & { user: User }>();
    return field ? request.user[field] : request.user;
  }
);

// In controller:
@Get('/profile')
getProfile(@CurrentUser() user: User) { return user; }

@Get('/name')
getName(@CurrentUser('name') name: string) { return name; }
// `data` = 'name' → request.user.name is extracted
```

**Q19. What is the NestJS request handling lifecycle, and how do decorators at each stage contribute?**

A: The lifecycle defines a strict order of execution for each incoming request, with decorators populating each stage's metadata:

```
Incoming Request
      ↓
[1] Middleware          @Module({ imports: ... }), app.use(fn)
      ↓
[2] Guards             @UseGuards(AuthGuard) — canActivate() → true or throw UnauthorizedException
      ↓
[3] Interceptors       @UseInterceptors(LogInterceptor) — intercept() before handler
      ↓
[4] Pipes              @UsePipes(ValidationPipe), @Body(new ParseIntPipe())
      ↓
[5] Route Handler      @Get('/path') method(@Body() dto, @Param('id') id)
      ↓
[6] Interceptors       @UseInterceptors — intercept() after handler (Observable tap)
      ↓
[7] Exception Filters  @UseFilters(HttpExceptionFilter) — catches and transforms errors
      ↓
Outgoing Response
```

Guards short-circuit the pipeline (return `false` → `403 Forbidden`). Interceptors wrap the entire handler in an RxJS Observable. Pipes transform/validate individual parameters. All stages are configured via decorators that store metadata, read at runtime by NestJS's reflector.

**Q20. What are `SetMetadata` and the `Reflector` class in NestJS, and how do they enable custom guard logic?**

A: `SetMetadata(key, value)` is NestJS's built-in custom metadata decorator factory — it stores arbitrary metadata on a class or method. The `Reflector` service is injected into guards and interceptors to read this metadata at request time, combining class-level and method-level metadata. The canonical example: `@Roles('admin')` stores required roles as metadata; the `RolesGuard` uses `Reflector` to read the roles and compare with the authenticated user's roles.

```ts
// Custom @Roles decorator using SetMetadata:
const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// Guard that reads role metadata:
@Injectable()
class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    // getAllAndOverride: reads from method first, falls back to class
    const requiredRoles = this.reflector.getAllAndOverride<string[]>('roles', [
      context.getHandler(), // method-level metadata (more specific)
      context.getClass(),   // class-level metadata (fallback)
    ]);
    if (!requiredRoles) return true; // no roles required — allow

    const { user } = context.switchToHttp().getRequest();
    return requiredRoles.some(role => user.roles.includes(role));
  }
}

// Usage:
@Controller('/admin')
@Roles('admin')         // class-level: all methods require admin
class AdminController {
  @Get('/stats')
  @Roles('superadmin') // method-level: overrides class — requires superadmin

}
```

**Q21. What are the TypeScript 5.0 "new decorators" (Stage 3 proposal), and how do they differ from experimental decorators?**

A: TypeScript 5.0 introduced a new decorator implementation based on the TC39 Stage 3 decorator proposal — a breaking redesign from the experimental (Stage 1) decorators NestJS currently uses. Key differences: (1) **No `experimentalDecorators` flag needed** — they are standard JavaScript, not experimental TypeScript; (2) **No `reflect-metadata`** — new decorators don't emit design-time type metadata; `design:paramtypes` etc. do not exist in the new system; (3) **Different arguments** — class decorator receives a `ClassDecoratorContext` object; method decorator receives `ClassMethodDecoratorContext`; they carry `name`, `kind`, and `addInitializer` instead of `PropertyDescriptor`; (4) **`addInitializer`** — decorators can schedule code to run when the class is instantiated; (5) **NestJS compatibility** — NestJS still uses experimental decorators and has not migrated to the new system as of 2024, so `experimentalDecorators: true` remains necessary for NestJS projects. Using `"experimentalDecorators": false` (or omitting it in TS 5.x) activates new decorators.

```ts
// NEW decorators (TS 5.0+, Stage 3 proposal):
function log<T>(
  target: (this: ThisType<T>, ...args: any[]) => any,
  context: ClassMethodDecoratorContext
) {
  return function(this: T, ...args: any[]) {
    console.log(`Calling ${String(context.name)}`);
    return target.apply(this, args);
  };
}

class Example {
  @log
  greet(name: string) { return `Hello, ${name}`; }
}

// EXPERIMENTAL decorators (still used by NestJS):
// function log(target: object, key: string, descriptor: PropertyDescriptor): PropertyDescriptor
// — different signature, different semantics
```

**Q22. What is the "circular dependency" problem with decorators and `design:paramtypes`, and what is the fix?**

A: When module A imports module B which imports module A, TypeScript/Node.js module loading creates a cycle. At the time `design:paramtypes` is emitted for class A's constructor, class B may not yet be defined (its module hasn't fully loaded), so `design:paramtypes` includes `undefined` instead of the `B` constructor. This causes NestJS's DI to fail with "unknown dependency" or inject `undefined`. The fix: NestJS's `forwardRef(() => ServiceClass)` wraps the dependency in a thunk that is resolved lazily after all modules finish loading.

```ts
// Problem: circular dependency A → B → A
@Injectable()
class ServiceA {
  constructor(private b: ServiceB) {} // ServiceB might be undefined at this point
}

@Injectable()
class ServiceB {
  constructor(private a: ServiceA) {}
}

// Fix: use forwardRef on BOTH sides
@Injectable()
class ServiceA {
  constructor(
    @Inject(forwardRef(() => ServiceB)) private b: ServiceB
  ) {}
}

@Injectable()
class ServiceB {
  constructor(
    @Inject(forwardRef(() => ServiceA)) private a: ServiceA
  ) {}
}

// Module: also use forwardRef in imports/providers if in separate modules:
@Module({
  imports: [forwardRef(() => BModule)],
  providers: [ServiceA],
  exports: [ServiceA],
})
class AModule {}
```

**Q23. What is accessor (`get`/`set`) decoration, and what constraint prevents certain `PropertyDescriptor` mutations?**

A: Accessor decorators apply to `get`/`set` pairs. They receive the same `(target, key, descriptor)` signature as method decorators, but `descriptor` has `get` and/or `set` properties instead of `value`. The critical constraint: a `PropertyDescriptor` **cannot** simultaneously have both `value`/`writable` and `get`/`set` — these are two exclusive descriptor forms. Attempting to return a descriptor with both `value` and `get` throws a TypeError at decoration time.

```ts
function Memoize(
  target: object,
  key: string,
  descriptor: PropertyDescriptor
): PropertyDescriptor {
  const getter = descriptor.get!;
  const cacheKey = Symbol(`memoize_${key}`);

  descriptor.get = function(this: any) {
    if (!Object.prototype.hasOwnProperty.call(this, cacheKey)) {
      Object.defineProperty(this, cacheKey, {
        value: getter.call(this),
        writable: false,
        enumerable: false,
        configurable: false,
      });
    }
    return (this as any)[cacheKey];
  };

  return descriptor;
}

class Circle {
  constructor(private radius: number) {}

  @Memoize
  get circumference() { return 2 * Math.PI * this.radius; }
}

// WRONG: return { value: ..., get: ... } → TypeError (can't mix data and accessor descriptor)
```

**Q25. State the invariant for each decorator type in one sentence each, and name the one operation each cannot do.**

A:
- **Class decorator**: receives the constructor and runs after all member decorators — it can add prototype methods, return a subclass, or store class-level metadata; it **cannot** directly alter the types of instance properties as TypeScript sees them.
- **Method decorator**: receives `PropertyDescriptor` and can replace `descriptor.value` with a wrapper function — it can intercept every invocation; it **cannot** change the method's TypeScript signature (parameter/return types remain unchanged for callers).
- **Property decorator**: receives only target and key — it can store metadata about a property; it **cannot** initialize a property value or intercept property access/assignment (use a getter/setter via `Object.defineProperty` for that).
- **Parameter decorator**: receives the parameter's index within its method — it can record how a parameter should be resolved at call time; it **cannot** change the value that the parameter receives (parameter values are determined by the caller, not the decorator).
- **Decorator factory**: receives user-supplied configuration and returns one of the above decorators — it can capture arguments in a closure; it **cannot** access the target class or method at factory-evaluation time (only the returned decorator runs on the target).

## Problem 1 — `@Log()` Method Decorator with Factory

### Problem

Implement a `@Log(prefix?)` method decorator factory that wraps any method to log its name, arguments, return value, and execution time. Support synchronous and async (Promise-returning) methods.

```ts
class UserService {
  @Log('SERVICE')
  async findUser(id: string): Promise<User> {
    return await db.find(id);
  }

  @Log()
  computeScore(values: number[]): number {
    return values.reduce((a, b) => a + b, 0);
  }
}

// On call:
// [SERVICE] findUser called with: ["user-123"]
// [SERVICE] findUser resolved in 15ms: { id: "user-123", name: "Ada" }
```

### Pattern Recognition
Decorator factory returning a method decorator. `PropertyDescriptor.value` replacement with a wrapper function. `apply(this, args)` for correct `this` binding. `Promise.resolve(result)` wrapping to handle both sync and async uniformly.

### Key Insight
The wrapper function must be a regular function expression (not an arrow function) so `this` correctly refers to the calling instance at runtime, not the outer scope at decoration time. Wrapping the result in `Promise.resolve` allows uniform async handling — for sync methods, `Promise.resolve` wraps the value; for async methods, it returns the existing Promise.

### Solution

```ts
function Log(prefix = 'LOG'): MethodDecorator {
  return function(
    target: object,
    propertyKey: string | symbol,
    descriptor: PropertyDescriptor
  ): PropertyDescriptor {
    const originalMethod = descriptor.value as (...args: unknown[]) => unknown;
    const methodName = String(propertyKey);

    descriptor.value = function(this: unknown, ...args: unknown[]) {
      const tag = `[${prefix}] ${methodName}`;
      console.log(`${tag} called with:`, JSON.stringify(args));
      const start = Date.now();

      // Invoke the original method with correct `this` and args
      const result = originalMethod.apply(this, args);

      // Handle both synchronous and async methods uniformly:
      return Promise.resolve(result)
        .then(value => {
          console.log(`${tag} resolved in ${Date.now() - start}ms:`, value);
          return value;
        })
        .catch(err => {
          console.error(`${tag} threw after ${Date.now() - start}ms:`, err.message);
          throw err; // re-throw so callers still see the error
        });
      // For sync methods: Promise.resolve wraps the value → .then logs → unwrapped by caller
      // For async methods: the existing Promise is forwarded through .then/.catch
    };

    return descriptor;
  };
}
```

### Trace

```ts

  add(a: number, b: number): number { return a + b; }

  @Log('MATH')

    return 42;
  }
}

const c = new Calc();

}
```

## Problem 2 — `@Memoize()` Method Decorator

### Problem

Implement a `@Memoize()` method decorator that caches method results by a serialized key of the arguments. Subsequent calls with the same arguments return the cached result without re-executing the method. Support optional TTL (time-to-live in ms).

```ts
class PriceService {
  @Memoize({ ttl: 5000 })
  async fetchPrice(symbol: string): Promise<number> {
    return await api.getPrice(symbol); // expensive API call
  }
}

const svc = new PriceService();
await svc.fetchPrice('BTC'); // API called
await svc.fetchPrice('BTC'); // cache hit — API NOT called
await svc.fetchPrice('ETH'); // API called (different key)
```

### Pattern Recognition
Method decorator wrapping `descriptor.value`. Per-instance cache stored on `this` (so different instances have independent caches). Cache key from `JSON.stringify(args)`. Optional TTL requires storing expiry timestamps alongside cached values.

### Key Insight
The cache must be per-instance (not per-class), so it's stored on `this` using a `Symbol` key — Symbols prevent key collisions with user-defined properties. The `Symbol` is created once (at decoration time, outside the wrapper function) and captured in the closure. Each class instance gets its own cache object lazily initialized on first call.

### Solution

```ts
interface MemoizeOptions { ttl?: number }

function Memoize(options: MemoizeOptions = {}): MethodDecorator {
  return function(target, propertyKey, descriptor: PropertyDescriptor): PropertyDescriptor {
    const original = descriptor.value as (...args: unknown[]) => unknown;
    const cacheSymbol = Symbol(`memoize_${String(propertyKey)}`); // unique per method
    const { ttl } = options;

    descriptor.value = function(this: Record<symbol, Map<string, { value: unknown; expires: number }>>,
                                ...args: unknown[]) {
      // Lazily initialize the per-instance cache:
      if (!this[cacheSymbol]) {
        this[cacheSymbol] = new Map();
      }
      const cache = this[cacheSymbol];

      const cacheKey = JSON.stringify(args); // serialize arguments as lookup key
      const now = Date.now();
      const cached = cache.get(cacheKey);

      if (cached && (!ttl || cached.expires > now)) {
        return cached.value; // cache hit — return immediately
      }

      // Cache miss or expired: call original and store result
      const result = original.apply(this, args);

      // Handle async: cache the resolved value, not the Promise itself
      if (result instanceof Promise) {
        return result.then(value => {
          cache.set(cacheKey, { value, expires: now + (ttl ?? Infinity) });
          return value;
        });
      }

      cache.set(cacheKey, { value: result, expires: now + (ttl ?? Infinity) });
      return result;
    };

    return descriptor;
  };
}
```

### Trace

```ts
class Calc {
  callCount = 0;

  @Memoize({ ttl: 1000 })
  square(n: number): number {
    this.callCount++;
    return n * n;
  }
}

const c = new Calc();
c.square(5);  // cache miss → callCount=1, stores {value:25, expires: now+1000}
c.square(5);  // cache hit  → callCount=1 (no increment) → returns 25
c.square(6);  // cache miss for key '[6]' → callCount=2, stores {value:36}
c.square(5);  // cache hit  → callCount=2 → returns 25

// After 1000ms (TTL expires):
// c.square(5); → cache miss (expires < now) → callCount=3

// Per-instance isolation:
const c2 = new Calc();
c2.square(5); // c2's own cache (cacheSymbol), c.callCount unchanged, c2.callCount=1
```

### Edge Cases
- `JSON.stringify` fails for circular objects or Symbols → guard: wrap in try/catch and use a fallback key.
- Async: storing the `Promise` (not the resolved value) would cause a subsequent concurrent call to get the pending Promise — this implementation waits for resolution before caching, so concurrent calls may all invoke the original. For concurrent deduplication, store the Promise itself: check for pending Promises too.
- `options.ttl` undefined: `Infinity` expiry — cache lives forever.

### Follow-up Questions
- "How would you add a `clear()` method to the class to reset memoization?" — Add to prototype: `target.prototype.clearMemoCache = function() { delete this[cacheSymbol]; }`.
- "What if arguments contain class instances that don't stringify correctly?" — Accept a custom key generator: `@Memoize({ keyFn: (args) => args[0].id })`.

## Problem 3 — `@Singleton()` Class Decorator

### Problem

Implement a `@Singleton()` class decorator that ensures only one instance of the class is ever created. Subsequent calls to `new` return the existing instance regardless of the arguments passed.

```ts
@Singleton()
class DatabaseConnection {
  constructor(public url: string) {
    console.log('Connecting to', url);
  }
}

const db1 = new DatabaseConnection('postgresql://host1/db');
// → 'Connecting to postgresql://host1/db'
const db2 = new DatabaseConnection('postgresql://host2/other');
// → (no log — constructor NOT called)
console.log(db1 === db2); // true
console.log(db2.url);     // 'postgresql://host1/db'
```

### Pattern Recognition
Class decorator returning a subclass that wraps the constructor. Instance is stored in the outer closure (not on the class prototype, to avoid enumeration). The subclass's constructor checks for an existing instance before calling `super`.

### Key Insight
The trick: returning from a constructor with a non-`this` value (specifically, an object) causes `new` to return that object instead of `this`. `return instance` inside a constructor — when `instance` is an object — causes `new ClassName()` to return `instance`. The subclass first checks if an instance exists; if so, it returns it immediately without calling `super()`.

### Solution

```ts
function Singleton<T extends new (...args: any[]) => object>(): (target: T) => T {
  return function(target: T): T {
    let instance: InstanceType<T> | null = null;

    // Return a new class that extends the original
    const Singleton = class extends target {
      constructor(...args: any[]) {
        if (instance) {
          // JavaScript: returning an object from a constructor makes `new` return THAT object
          return instance;
        }
        super(...args);          // call original constructor (populates `this`)
        instance = this as InstanceType<T>; // store the first instance
      }
    };

    // Preserve the original class name for debugging:
    Object.defineProperty(Singleton, 'name', { value: target.name });

    return Singleton as T;
  };
}

// Simpler version without factory (direct decorator):
function SingletonDirect<T extends new (...args: any[]) => object>(target: T): T {
  let instance: InstanceType<T> | null = null;
  return class extends target {
    constructor(...args: any[]) {
      if (instance) return instance;
      super(...args);
      instance = this as InstanceType<T>;
    }
  } as T;
}
```

### Trace

```ts
@Singleton()
class Logger { constructor(public level: string) { console.log('Logger created:', level); } }

new Logger('INFO');   // → 'Logger created: INFO'. instance = Logger{level:'INFO'}
new Logger('DEBUG');  // constructor runs: instance !== null → returns instance immediately
new Logger('ERROR');  // same → returns same instance

const l1 = new Logger('A');
const l2 = new Logger('B');
console.log(l1 === l2);   // true ✓
console.log(l2.level);    // 'INFO' (first instance, first args) ✓
console.log(Logger.name); // 'Logger' (name preserved) ✓

// Class hierarchy: subclass has its OWN singleton (own closure):

  constructor(public path: string) { super('FILE'); }
}
const f1 = new FileLogger('/app.log');
const f2 = new FileLogger('/other.log');
console.log(f1 === f2); // true ✓ (FileLogger's own singleton)
console.log(f1 === l1); // false ✓ (different singletons for different classes)
```

### Edge Cases
- `instance` is in the closure — it's not reset when the class is "re-imported" in module systems that cache imports. Testing singletons requires either module reset or a `reset()` method.
- The singleton instance survives class garbage collection attempts — the closure holds a reference, preventing GC.
- TypeScript type: `@Singleton()` returns `T`, so `new Logger()` still types correctly as `Logger`.

### Follow-up Questions
- "How would you add a `reset()` method for testing?" — Expose via a static method on the returned class: `static resetInstance() { instance = null; }`.
- "How does this differ from NestJS's `@Injectable({ scope: Scope.DEFAULT })`?" — NestJS singletons are scoped to a NestJS module's lifetime; they're not JavaScript-level singletons and don't survive module destruction.

## Problem 4 — Property Validator with Class + Property Decorators

### Problem

Implement a `@Required`, `@MinLength(n)`, `@Email` property decorator system and a `validate(obj)` function that reads the metadata and returns validation errors.

```ts
class CreateUserDto {
  @Required
  @MinLength(3)
  name: string;

  @Required
  @Email
  email: string;

  age?: number;
}

validate(new CreateUserDto());
// → { name: ['required'], email: ['required', 'invalid email'] }

const dto = new CreateUserDto();
dto.name = 'A'; dto.email = 'not-an-email';
validate(dto);
// → { name: ['minLength: must be at least 3 chars (got 1)'], email: ['invalid email'] }
```

### Pattern Recognition
Property decorators write validation rules as metadata arrays per-property. A `validate()` function reads all property metadata from the target object's class prototype, evaluates each rule against the property's current value, and collects errors.

### Key Insight
Each property decorator appends a validator descriptor to a metadata array stored on the *prototype* with the property name as a sub-key. Reading the prototype's metadata (not the instance's) allows the validator to enumerate all decorated properties regardless of instance state. The metadata stores *rule descriptors* (not values) — actual validation happens at `validate()` call time against live values.

### Solution

```ts
import 'reflect-metadata';

const VALIDATORS_KEY = 'validators';

type Validator = (value: unknown, key: string) => string | null;

function addValidator(target: object, key: string | symbol, validator: Validator) {
  const existing: Validator[] =
    Reflect.getOwnMetadata(VALIDATORS_KEY, target, key) ?? [];
  existing.push(validator);
  Reflect.defineMetadata(VALIDATORS_KEY, existing, target, key);
}

// Property decorators — each adds a validator rule to the property's metadata:
function Required(target: object, key: string) {
  addValidator(target, key, (value) =>
    value === undefined || value === null || value === ''
      ? 'required'
      : null
  );
}

function MinLength(min: number) {
  return function(target: object, key: string) {
    addValidator(target, key, (value) =>
      typeof value === 'string' && value.length < min
        ? `minLength: must be at least ${min} chars (got ${(value as string).length})`
        : null
    );
  };
}

function Email(target: object, key: string) {
  addValidator(target, key, (value) =>
    typeof value === 'string' && !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value)
      ? 'invalid email'
      : null
  );
}

// validate() reads metadata and runs all validators:
function validate<T extends object>(obj: T): Record<string, string[]> {
  const proto = Object.getPrototypeOf(obj);
  const errors: Record<string, string[]> = {};

  // Enumerate all own metadata keys stored on the prototype:
  const properties = Reflect.getMetadataKeys(proto)
    .filter(key => key === VALIDATORS_KEY // only our keys
      // Actually: enumerate per-property keys:
    );

  // Better: iterate all property names and check for metadata:
  const allKeys = new Set([
    ...Object.getOwnPropertyNames(obj),
    ...Object.getOwnPropertyNames(proto),
  ]);

  for (const key of allKeys) {
    const validators: Validator[] = Reflect.getOwnMetadata(VALIDATORS_KEY, proto, key) ?? [];
    if (!validators.length) continue;

    const value = (obj as Record<string, unknown>)[key];
    const fieldErrors = validators
      .map(v => v(value, key))
      .filter((e): e is string => e !== null);

    if (fieldErrors.length) errors[key] = fieldErrors;
  }

  return errors;
}
```

### Trace

```ts
  @MinLength(3)          // adds validator: length < 3 → 'minLength...'

//   minlength_fn('A') = 'minLength: must be at least 3 chars (got 1)'
// key='email': value='notvalid'
//   required_fn('notvalid') = null
//   email_fn('notvalid') = 'invalid email'
// → { name: ['minLength: ...'], email: ['invalid email'] }
```

### Edge Cases
- Property order: validators are applied in the order they're added; stacked decorators are applied bottom-to-top, so `@Required @MinLength(3)` applies `MinLength` first. Adjust if order matters.
- Inherited properties: `Object.getPrototypeOf(proto)` would need to be traversed for inherited validators (use `getMetadata` instead of `getOwnMetadata`).
- Class decorator integration: `@ValidateOnConstruct` could call `validate(this)` in a constructor wrapper.

### Follow-up Questions
- "How does NestJS's `class-validator` work differently?" — It uses the same metadata mechanism but with `@IsEmail()`, `@IsNotEmpty()` etc. from `class-validator`; `ValidationPipe` calls `plainToClass` + `validate()` from `class-transformer`/`class-validator` automatically.
- "How would you add a `@Pattern(regex)` validator?" — Same pattern: `addValidator(target, key, value => !regex.test(value) ? 'invalid format' : null)`.

## Problem 5 — Custom NestJS-Style Parameter Decorator

### Problem

Implement `createParamDecorator` (NestJS's built-in) and use it to build `@CurrentUser()` and `@RequestId()` custom parameter decorators that integrate with a simple route handler system.

```ts
const CurrentUser = createParamDecorator(
  (field: string | undefined, req: Request) => field ? req.user[field] : req.user
);

const RequestId = createParamDecorator(
  (_data, req: Request) => req.headers['x-request-id'] ?? crypto.randomUUID()
);

class UserController {
  @Get('/me')
  getMe(
    @CurrentUser() user: User,
    @RequestId() requestId: string,
    @CurrentUser('name') name: string,
  ) {
    return { user, requestId, name };
  }
}
```

### Pattern Recognition
`createParamDecorator` returns a function that returns a parameter decorator. The parameter decorator stores `{ index, factory, data }` as metadata on the method. At call time, the router reads this metadata and invokes each factory to build the argument array.

### Key Insight
There are two distinct times: *decoration time* (when `@CurrentUser()` is evaluated) and *call time* (when the route handler is invoked). The parameter decorator stores a *recipe* (the factory + data) at decoration time. The router executes the *recipe* at call time, with access to the live request object. This separation is what makes custom param decorators composable with pipes — the factory result is passed through any configured pipe before reaching the handler.

### Solution

```ts
const CUSTOM_PARAMS_META = 'custom_params';

type ParamFactory<TData = any> = (data: TData, request: any) => any;

interface ParamMetadata {
  index: number;
  factory: ParamFactory;
  data: unknown;
}

function createParamDecorator<TData = any>(factory: ParamFactory<TData>) {
  return (data?: TData): ParameterDecorator =>
    (target: object, methodKey: string | symbol, paramIndex: number) => {
      const existing: ParamMetadata[] =
        Reflect.getOwnMetadata(CUSTOM_PARAMS_META, target, methodKey!) ?? [];
      existing.push({ index: paramIndex, factory, data });
      Reflect.defineMetadata(CUSTOM_PARAMS_META, existing, target, methodKey!);
    };
}

// Custom decorators built with createParamDecorator:
interface User { id: string; name: string; roles: string[] }

const CurrentUser = createParamDecorator(
  (field: keyof User | undefined, req: { user: User }) =>
    field ? req.user[field] : req.user
);

const RequestId = createParamDecorator(
  (_data: undefined, req: { headers: Record<string, string> }) =>
    req.headers['x-request-id'] ?? Math.random().toString(36).slice(2)
);

// Router that resolves custom params and calls the handler:
function callHandler(
  instance: object,
  methodKey: string,
  request: any,
  regularArgs: any[] // args resolved from @Body, @Param, etc.
): any {
  const customMeta: ParamMetadata[] =
    Reflect.getOwnMetadata(CUSTOM_PARAMS_META, Object.getPrototypeOf(instance), methodKey) ?? [];

  // Merge custom params into the args array at correct indices:
  const args = [...regularArgs];
  for (const { index, factory, data } of customMeta) {
    args[index] = factory(data, request); // invoke factory with request context
  }

  return (instance as any)[methodKey](...args);
}
```

- Parameter index ordering: metadata array may not be in index order; sort by `index` before building the args array.
- Interaction with regular param decorators (`@Body`, `@Param`): both write to different metadata keys and are merged at call time.

## Problem 6 — Mini NestJS Route Registration System

### Problem

Implement a minimal `@Controller(path)`, `@Get(path)`, `@Post(path)` decorator system and a `registerRoutes(app, ControllerClass)` function that reads the metadata and registers routes with an Express-like app.

```ts
@Controller('/users')
class UserController {
  @Get()
  findAll() { return [{ id: 1, name: 'Ada' }]; }

  @Get('/:id')
  findOne(@Param('id') id: string) { return { id }; }

  @Post()
  create(@Body() dto: CreateUserDto) { return { ...dto, id: 2 }; }
}

registerRoutes(app, UserController);
// Registers: GET /users, GET /users/:id, POST /users
```

### Pattern Recognition
Class decorator stores the base path. Method decorators store sub-paths and HTTP methods on each handler function. `registerRoutes` reads both layers of metadata and composes full route paths before registering with the HTTP framework.

### Key Insight
Metadata is stored on the *function object* (`descriptor.value`), not on the prototype key. This means route metadata can be read by passing the handler function reference directly to `Reflect.getMetadata`. The function object is the target because multiple methods share the same prototype — storing on the prototype with the method name as a sub-key is equivalent but less idiomatic for HTTP method decorators.

### Solution

```ts
import 'reflect-metadata';

const CONTROLLER_PATH  = Symbol('controller:path');
const ROUTE_PATH       = Symbol('route:path');
const ROUTE_METHOD     = Symbol('route:method');
const ROUTE_PARAM_META = Symbol('route:params');

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';

// Class decorator:
function Controller(path = ''): ClassDecorator {
  return (target) => {
    Reflect.defineMetadata(CONTROLLER_PATH, `/${path}`.replace('//', '/'), target);
  };
}

// Method decorator factory:
function createMethodDecorator(method: HttpMethod) {
  return (path = ''): MethodDecorator =>
    (_target, _key, descriptor: PropertyDescriptor) => {
      Reflect.defineMetadata(ROUTE_PATH,   path,   descriptor.value);
      Reflect.defineMetadata(ROUTE_METHOD, method, descriptor.value);
      return descriptor;
    };
}
const Get    = createMethodDecorator('GET');
const Post   = createMethodDecorator('POST');
const Put    = createMethodDecorator('PUT');
const Delete = createMethodDecorator('DELETE');

// Route registration:
function registerRoutes(app: any, ControllerClass: new () => any) {
  const basePath = Reflect.getMetadata(CONTROLLER_PATH, ControllerClass) as string ?? '';
  const instance = new ControllerClass();
  const proto    = Object.getPrototypeOf(instance);

  Object.getOwnPropertyNames(proto)
    .filter(name => name !== 'constructor')
    .forEach(name => {
      const handler: Function = proto[name];
      const routePath   = Reflect.getMetadata(ROUTE_PATH,   handler) as string;
      const routeMethod = Reflect.getMetadata(ROUTE_METHOD, handler) as HttpMethod;

      if (routePath === undefined || !routeMethod) return; // not a route

      const fullPath = `${basePath}${routePath ? `/${routePath}`.replace('//', '/') : ''}`;
      console.log(`Registering: ${routeMethod} ${fullPath}`);

      app[routeMethod.toLowerCase()](fullPath, async (req: any, res: any) => {
        try {
          const result = await handler.call(instance, req, res);
          res.json(result);
        } catch (err: any) {
          res.status(500).json({ error: err.message });
        }
      });
    });
}
```

## Problem 7 — Mini Dependency Injection Container

### Problem

Implement `@Injectable()` class decorator and a `Container.resolve<T>(token)` method that reads `design:paramtypes` metadata to recursively resolve and inject constructor dependencies automatically.

```ts
@Injectable()
class DatabaseService {
  query(sql: string) { return [`result for: ${sql}`]; }
}

@Injectable()
class UserRepository {
  constructor(private db: DatabaseService) {}
  findAll() { return this.db.query('SELECT * FROM users'); }
}

@Injectable()
class UserService {
  constructor(private repo: UserRepository) {}
  getUsers() { return this.repo.findAll(); }
}

const svc = Container.resolve(UserService);
svc.getUsers(); // → ['result for: SELECT * FROM users']
```

### Pattern Recognition
Class decorator marks classes as resolvable. Container reads `design:paramtypes` to discover constructor dependencies, recursively resolves each, and constructs the class with injected dependencies. Singleton scope: cache instances to avoid creating duplicates.

### Key Insight
`design:paramtypes` is an array of constructor functions — the actual class references, not strings. The container uses these constructor references as tokens for lookup and recursive resolution. The recursion terminates at classes with no dependencies (empty `design:paramtypes`).

### Solution

```ts
import 'reflect-metadata';

const INJECTABLE_META = 'injectable';

function Injectable(): ClassDecorator {
  return (target) => {
    Reflect.defineMetadata(INJECTABLE_META, true, target);
    // `emitDecoratorMetadata: true` causes TypeScript to emit:
    // Reflect.metadata('design:paramtypes', [Dep1, Dep2, ...])(target)
    // automatically — we don't need to write it manually
  };
}

function Inject(token: Function | string | symbol): ParameterDecorator {
  return (target, _key, index) => {
    const overrides: Map<number, any> =
      Reflect.getOwnMetadata('inject:overrides', target) ?? new Map();
    overrides.set(index, token);
    Reflect.defineMetadata('inject:overrides', overrides, target);
  };
}

class Container {
  private static instances = new Map<Function, any>(); // singleton cache

  static resolve<T>(token: new (...args: any[]) => T): T {
    // Check singleton cache first:
    if (this.instances.has(token)) {
      return this.instances.get(token) as T;
    }

    // Verify the class is marked as injectable:
    const isInjectable = Reflect.getMetadata(INJECTABLE_META, token);
    if (!isInjectable) {
      throw new Error(`${token.name} is not @Injectable(). Did you forget the decorator?`);
    }

    // Read constructor parameter types from TypeScript-emitted metadata:
    const paramTypes: (new (...args: any[]) => any)[] =
      Reflect.getMetadata('design:paramtypes', token) ?? [];

    // Check for @Inject() overrides (for non-class tokens):
    const overrides: Map<number, any> =
      Reflect.getOwnMetadata('inject:overrides', token) ?? new Map();

    // Recursively resolve each dependency:
    const deps = paramTypes.map((depType, index) => {
      const override = overrides.get(index);
      if (override) return this.resolveToken(override);
      if (depType === undefined) {
        throw new Error(
          `${token.name}'s parameter at index ${index} resolved to undefined. ` +
          `Possible circular dependency — use forwardRef.`
        );
      }
      return this.resolve(depType); // recursive resolution
    });

    // Construct with all dependencies injected:
    const instance = new token(...deps);

    // Cache in singleton store:
    this.instances.set(token, instance);

    return instance;
  }

  private static resolveToken(token: any): any {
    if (typeof token === 'function') return this.resolve(token);
    throw new Error(`Cannot resolve non-class token '${String(token)}' without explicit registration`);
  }

  static register<T>(token: any, value: T): void {
    this.instances.set(token, value);
  }

  static reset(): void { this.instances.clear(); } // for testing
}
```

## Quick Reference — Decorator Decision Tree

```
What do you need a decorator for?
│
├── TRANSFORM OR OBSERVE THE ENTIRE CLASS?
│   └── CLASS DECORATOR — receives the constructor
│       ├── Store metadata about the class         → Reflect.defineMetadata('key', val, target)
│       ├── Wrap or replace the constructor        → return class extends target { ... }
│       ├── Add prototype methods                  → target.prototype.method = fn
│       └── Examples: @Injectable(), @Controller(), @Singleton(), @Sealed()
│
├── INTERCEPT OR TRANSFORM METHOD CALLS?
│   └── METHOD DECORATOR — receives PropertyDescriptor
│       ├── Wrap the method (logging, timing, retry)
│       │   → save original = descriptor.value
│       │   → descriptor.value = function(...args) { ... original.apply(this, args) ... }
│       │   → return descriptor
│       ├── Store metadata about the method        → Reflect.defineMetadata on descriptor.value
│       ├── Make method read-only                  → descriptor.writable = false
│       └── Examples: @Get(), @Log(), @Memoize(), @UseGuards(), @Throttle()
│
├── ANNOTATE A PROPERTY WITH METADATA?
│   └── PROPERTY DECORATOR — receives target and key
│       ├── Store validation rules                 → Reflect.defineMetadata('validators', [...], target, key)
│       ├── Define a getter/setter via Object.defineProperty
│       ├── Record serialization config            → Reflect.defineMetadata('serializable', true, target, key)
│       └── Examples: @Required, @MinLength(n), @Column(), @IsEmail()
│       ⚠️  Cannot initialize values (return value is ignored)
│
├── MARK HOW A PARAMETER SHOULD BE RESOLVED?
│   └── PARAMETER DECORATOR — receives target, methodKey, and parameterIndex
│       ├── Mark injection token                   → Reflect.defineMetadata('inject', token, target)
│       ├── Mark request extraction               → Reflect.defineMetadata('param_type', 'BODY', ...)
│       └── Examples: @Body(), @Param(), @Query(), @Inject(), @CurrentUser()
│       ⚠️  Cannot change the parameter's value at decoration time
│
├── CONFIGURE DECORATOR BEHAVIOR PER USAGE?
│   └── DECORATOR FACTORY — function returning a decorator
│       @Dec(options)  →  function Dec(options) { return function(target, ...) { ... } }
│       └── Always prefer factories for NestJS (consistent API, future-proof)
│
├── WHICH reflect-metadata METHOD?
│   ├── Store metadata            → Reflect.defineMetadata(key, value, target, propertyKey?)
│   ├── Read (walks prototype)    → Reflect.getMetadata(key, target, propertyKey?)
│   ├── Read (own only)           → Reflect.getOwnMetadata(key, target, propertyKey?)
│   ├── Check existence           → Reflect.hasMetadata(key, target, propertyKey?)
│   └── List keys                 → Reflect.getMetadataKeys(target, propertyKey?)
│
└── NestJS-SPECIFIC METADATA KEYS TO KNOW:
    PATH_METADATA       → route path (@Controller, @Get, etc.)
    METHOD_METADATA     → HTTP method (@Get → 'GET')
    GUARDS_METADATA     → guards (@UseGuards)
    INTERCEPTORS_METADATA → interceptors (@UseInterceptors)
    PIPES_METADATA      → pipes (@UsePipes)
    ROLES_KEY           → custom roles (via SetMetadata)
    design:paramtypes   → constructor/method param types (TypeScript emitted)
    design:returntype   → method return type (TypeScript emitted)
    design:type         → property type (TypeScript emitted)
```

## Common Bugs Checklist

Before shipping decorator code, verify:

1. **Missing `experimentalDecorators: true` or `emitDecoratorMetadata: true` in tsconfig?** — Decorators are a TypeScript opt-in feature; omitting `experimentalDecorators` produces "Decorators are not valid here" syntax errors. Omitting `emitDecoratorMetadata` means `design:paramtypes` is never emitted — `Reflect.getMetadata('design:paramtypes', SomeClass)` returns `undefined`, breaking all DI. Both flags are required for NestJS. Also: `import 'reflect-metadata'` must appear *once* at the application entry point (e.g., `main.ts`) before any decorated class is loaded.

2. **Using an arrow function as the method wrapper — losing the caller's `this`?** — Inside a method decorator, `descriptor.value = (...args) => original.apply(this, args)` captures `this` from the *decorator's execution context* (the class definition scope), not the caller's context. At runtime, `this` will be wrong (the module scope or undefined). Always use a regular function expression: `descriptor.value = function(...args) { return original.apply(this, args); }`. The `this` inside a regular function is determined at call time — which is exactly the instance the method is called on.

3. **Expecting property decorators to initialize or intercept property values?** — Property decorators receive no `PropertyDescriptor` and their return value is ignored. `return { value: 42 }` in a property decorator does nothing. To intercept property access: use `Object.defineProperty(target, key, { get() {...}, set(v) {...} })` inside the property decorator. To initialize a default value: store it in metadata and use a class decorator or factory to set up instances.

4. **Reading stale metadata in a class decorator that runs before member decorators have stored theirs?** — Class decorators run LAST — after all property, method, and parameter decorators have already executed. This is the correct behavior (class decorator can safely read all member metadata). If you observe missing metadata in the class decorator, check that the member decorators are actually writing to the same key/target pair.

5. **Storing metadata with the wrong `target` for instance vs static members?** — For instance members: `target` is the class *prototype* (not the constructor). For static members: `target` is the constructor function itself. Metadata set on `target` (prototype) must be read from the prototype; metadata set on `target.constructor` (class itself) must be read from the class. NestJS route decorators store on `descriptor.value` (the function object), which is independent of prototype vs constructor.

6. **`design:paramtypes` returns `[Object]` instead of the actual class — injecting wrong dependency?** — This happens when injecting an *interface* or *abstract type* (both erase to `Object` at runtime), or when a circular dependency causes the class to be `undefined` at emit time. Fix: use `@Inject('CONCRETE_TOKEN')` with string/symbol tokens for interfaces; use `forwardRef(() => ConcreteClass)` for circular dependencies.

7. **Decorator application order confusion — expecting top decorator to execute innermost?** — Decorators are *applied* bottom-to-top: the bottom decorator's wrapper is the innermost. `@D1 @D2 method()` means `D2` wraps the original, then `D1` wraps `D2`'s wrapper. D1 is the outermost — it executes first on any call and last on return. When stacking `@UseGuards` and `@UseInterceptors`, the order determines which runs "outside" which.

8. **Forgetting `return descriptor` in a method decorator that modifies it?** — Modifying `descriptor.value` in-place (e.g., `descriptor.value = newFn`) works with or without returning — the descriptor object is mutated. But if you create a *new* descriptor object (`const newDesc = { ...descriptor, value: newFn }`), you MUST return it; otherwise TypeScript ignores the new object and uses the original. Be consistent: always `return descriptor` from method decorators.

9. **Using the same metadata key for both class-level and method-level storage — overwriting class metadata with method metadata?** — `Reflect.defineMetadata('key', value, target)` on the prototype (method decorator target) and `Reflect.defineMetadata('key', value, ControllerClass)` (class decorator target) use different targets and don't conflict. But if both use `Reflect.defineMetadata('key', value, SomeClass)` without different targets, the last write wins. Use consistent target conventions: method metadata on `descriptor.value` (the function), class metadata on the constructor.

10. **Not handling `undefined` in `design:paramtypes` for circular or unresolvable dependencies?** — `design:paramtypes` silently emits `undefined` entries (not an error) when a constructor parameter's type is circular or cannot be resolved at emit time. A DI container that blindly does `new token(...deps)` with an `undefined` dep will silently inject `undefined`, causing subtle runtime errors. Always validate `design:paramtypes` entries and throw a descriptive error: `if (depType === undefined) throw new Error('Circular dependency detected...')`.

---

**Final Tip:** At the 5 YOE level, the decisive signal for decorator questions is naming *what each decorator type stores and when* — understanding that decorators are **two-time entities**: they execute once at class-definition time (storing metadata or wrapping behavior), and their effects manifest later at runtime (during DI resolution, route registration, or method invocation). For method decorators: *"the wrapper function is created once at decoration time and installed permanently as the method — `this` inside it must be a regular function so it receives the caller's context at each invocation; the original is captured in a closure and called via `.apply(this, args)` to preserve both context and arguments."* For property and parameter decorators: *"they cannot change runtime behavior directly — their only job is to store metadata; the framework (NestJS, class-validator, tsyringe) reads this metadata separately to configure injection, validation, or extraction."* For the metadata system: *"`design:paramtypes` is the only bridge between TypeScript's compile-time type system and JavaScript's runtime — it works only for class-typed constructor parameters with `emitDecoratorMetadata: true`, erases interfaces to `Object`, and becomes `undefined` for circular dependencies — these three limitations drive the need for `@Inject()`, `forwardRef()`, and explicit token registration in any production-grade DI container."*
