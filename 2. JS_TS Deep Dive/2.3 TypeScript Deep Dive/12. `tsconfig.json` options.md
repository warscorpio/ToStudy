# TypeScript: `tsconfig.json` Options — `strict`, `esModuleInterop`, `paths`, `baseUrl`, `declaration` — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: `tsconfig.json` Fundamentals

**Q1. What is `tsconfig.json` and what is its role in a TypeScript project?**
A: `tsconfig.json` is the configuration file that instructs the TypeScript compiler (`tsc`) how to compile your project. It controls three categories of behavior:

- **Type-checking behavior**: how strict the type system is, which type checks to enable or disable.
- **Emit behavior**: whether to output JavaScript, where to put it, which JavaScript version to target, whether to generate declaration files (`.d.ts`), source maps, etc.
- **Project scope**: which files to include or exclude, module resolution strategy, path aliases.

When you run `tsc` in a directory, TypeScript looks for `tsconfig.json` and applies all its settings. Build tools (Webpack, Vite, esbuild, Babel, ts-jest) read `tsconfig.json` for type-checking configuration even when they handle the actual transpilation themselves.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

**Q2. What is the relationship between `tsconfig.json`, `tsconfig.base.json`, and extended configs?**
A: TypeScript supports config inheritance via the `extends` field. A child config inherits all settings from a parent and can override specific options. This enables:

- **Monorepos**: a root `tsconfig.base.json` with shared settings; each package extends it and adds project-specific overrides.
- **Environment-specific configs**: `tsconfig.prod.json` and `tsconfig.dev.json` extending a base with different output or strictness settings.
- **Shared presets**: community configs like `@tsconfig/node20`, `@tsconfig/strictest` that provide sensible defaults for specific environments.

```json
// tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "strict": true,
    "moduleResolution": "bundler"
  }
}

// packages/api/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src"]
}
```

### Section 2: `strict` Mode

**Q3. What does `"strict": true` actually enable?**
A: `"strict": true` is a shorthand flag that enables a collection of individual strictness checks simultaneously. As of TypeScript 5.x, it enables:

| Flag | What it checks |
|---|---|
| `strictNullChecks` | `null` and `undefined` are not assignable to other types |
| `strictFunctionTypes` | Function parameter types are checked contra-variantly |
| `strictBindCallApply` | `.bind()`, `.call()`, `.apply()` are type-checked against the function signature |
| `strictPropertyInitialization` | Class properties must be initialized in the constructor |
| `noImplicitAny` | Variables with inferred `any` type must be annotated explicitly |
| `noImplicitThis` | `this` expressions typed as `any` are errors |
| `alwaysStrict` | Emits `"use strict"` in all output files |
| `useUnknownInCatchVariables` | Catch clause variables are typed as `unknown` (not `any`) |

Enabling individual flags overrides `strict`. Setting `"strict": true, "noImplicitAny": false` enables all strict flags except `noImplicitAny`.

**Q4. What is `strictNullChecks` and why is it arguably the most important strict flag?**
A: `strictNullChecks` makes `null` and `undefined` their own distinct types, not assignable to every other type. Without it, TypeScript allows you to assign `null` or `undefined` to `string`, `number`, etc. — silently permitting the most common category of runtime errors ("Cannot read property of null/undefined").

```ts
// WITHOUT strictNullChecks:
let name: string = null;    // ✓ no error — null is assignable to string
name.toUpperCase();          // runtime TypeError: Cannot read property 'toUpperCase' of null
                             // TypeScript didn't warn you!

// WITH strictNullChecks:
let name: string = null;    // Error: Type 'null' is not assignable to type 'string'
let maybeName: string | null = null; // ✓ explicit nullable type
maybeName.toUpperCase();    // Error: Object is possibly 'null' — must check first

if (maybeName !== null) {
  maybeName.toUpperCase();  // ✓ TypeScript narrowed it to string
}
```

Many senior engineers consider `strictNullChecks` the single highest-value TypeScript feature — it eliminates an entire class of production runtime errors at compile time.

**Q5. What does `noImplicitAny` do and when is it acceptable to disable it?**
A: `noImplicitAny` requires explicit type annotations when TypeScript would otherwise infer `any`. This prevents "silent any" — code that passes type-checking but carries no type information.

```ts
// noImplicitAny: true (with strict)
function process(data) { // Error: Parameter 'data' implicitly has an 'any' type
  return data.value;
}

// Fix: add explicit annotation
function process(data: { value: string }) {
  return data.value; // now typed correctly
}

// Or use explicit any if you truly don't know:
function process(data: any) { // ✓ explicit any — intentional escape hatch
  return data.value;
}
```

It's acceptable to temporarily disable `noImplicitAny` when:
- **Migrating a large JavaScript codebase to TypeScript incrementally**: you can't type everything at once. Start with `noImplicitAny: false`, add types gradually, then enable it.
- **Working with dynamically structured data** where the shape genuinely can't be known at compile time (use `unknown` instead of disabling — then at least you're forced to narrow before use).

**Q6. What is `useUnknownInCatchVariables` and why does it matter?**
A: Before TypeScript 4.0, catch clause variables were implicitly typed as `any`, allowing dangerous code:

```ts
// Before useUnknownInCatchVariables (or with strict: false):
try {
  throw "something went wrong"; // can throw anything
} catch (err) {
  err.message; // No error! err is 'any' — but strings don't have .message
  // Runtime error: TypeError: Cannot read property 'message' of undefined
}

// With useUnknownInCatchVariables (part of strict in TS 4.4+):
try {
  throw new Error("bad");
} catch (err) {
  // err is typed as 'unknown'
  err.message; // Error: Object is of type 'unknown'

  // Must narrow first:
  if (err instanceof Error) {
    console.log(err.message); // ✓ TypeScript knows it's an Error
  } else {
    console.log(String(err)); // handle non-Error throws
  }
}
```

This matters because JavaScript allows throwing anything — strings, numbers, plain objects, not just `Error` instances. Typing catch variables as `unknown` forces you to handle non-Error throws safely.

**Q7. What is `strictPropertyInitialization` and how do you handle cases where properties are initialized outside the constructor?**
A: `strictPropertyInitialization` requires that all declared class properties are either:
- Assigned a value in their declaration.
- Assigned in the constructor.
- Marked as optional (`?`) or explicitly typed to allow `undefined`.

```ts
// Error: strictPropertyInitialization
class User {
  name: string;  // Error: Property 'name' has no initializer and is not
                 // definitely assigned in the constructor
  constructor() {
    // name is not set here → error
  }
}

// Fixes:
class UserFixed {
  // Option 1: default value
  name: string = '';

  // Option 2: assign in constructor
  name: string;
  constructor(name: string) { this.name = name; }

  // Option 3: definite assignment assertion (!) — tells TS "trust me"
  name!: string; // ← use when framework initializes (Angular, TypeORM, etc.)

  // Option 4: make optional
  name?: string; // now string | undefined

  // Option 5: include undefined in the type
  name: string | undefined;
}
```

The `!` (definite assignment assertion) is the escape hatch for frameworks like Angular (where properties are set by the DI framework) or TypeORM (where columns are set by the ORM). It tells TypeScript "I know this looks uninitialized, but I guarantee it will be set before use." Use it sparingly — misuse defeats the purpose of the flag.

### Section 3: `esModuleInterop`

**Q8. What problem does `esModuleInterop` solve?**
A: `esModuleInterop` fixes the impedance mismatch between CommonJS (CJS) modules and ES module (ESM) import syntax. Without it, importing CJS modules that use `module.exports = someValue` (a "default export" in CJS terms) requires awkward syntax or breaks at runtime.

The fundamental issue: ES modules have named and default exports as separate concepts. CommonJS uses `module.exports` for a single export value. Many popular Node.js libraries (express, lodash, etc.) use `module.exports = value` — which doesn't map cleanly to ES module default imports.

**Q9. What specifically does `esModuleInterop` enable?**
A: With `esModuleInterop: false` (the historical default):

```ts
// CommonJS module: const express = require('express')
// module.exports = function createApp() { ... }

// Without esModuleInterop — must use namespace import:
import * as express from 'express';
const app = express();

// Trying default import FAILS:
import express from 'express'; // Error at runtime: express is not a function
// (Because TypeScript compiles this to: const express_1 = require('express');
//  but then uses express_1.default — which doesn't exist on the CJS module)
```

With `esModuleInterop: true`, TypeScript:
1. Generates a `__importDefault` helper that wraps CJS modules: if the module doesn't have `__esModule: true`, the entire `module.exports` is wrapped as `{ default: module.exports }`.
2. Allows default import syntax for CJS modules: `import express from 'express'` works correctly.
3. Also enables `allowSyntheticDefaultImports` (required for the type checking side).

```ts
// WITH esModuleInterop: true
import express from 'express';       // ✓ works
import { Router } from 'express';    // ✓ named imports still work

import _ from 'lodash';              // ✓ lodash's entire export as default
import { map } from 'lodash';        // ✓ named imports still work
```

**Q10. What is `allowSyntheticDefaultImports` and how does it relate to `esModuleInterop`?**
A: `allowSyntheticDefaultImports` affects only the **type-checking** side — it tells TypeScript's type checker to allow default imports from modules that don't have a declared default export, without generating any interop helpers. It's useful when the runtime bundler (Webpack, Babel) already handles the CJS/ESM interop.

`esModuleInterop` affects both type-checking AND **emit** (generated JavaScript). It implies `allowSyntheticDefaultImports` automatically.

```
allowSyntheticDefaultImports: true
  → Type checking: allows default import syntax from CJS modules
  → Emit: NO change — assumes bundler handles it

esModuleInterop: true
  → Type checking: allows default import syntax (same as allowSyntheticDefaultImports)
  → Emit: generates __importDefault and __importStar helpers in output JS
```

When to use which:
- **When `tsc` is both type-checking AND transpiling**: use `esModuleInterop: true` — you need the emitted helpers.
- **When using Babel/esbuild/Vite for transpilation and `tsc` only for type-checking**: use `allowSyntheticDefaultImports: true` instead — no helpers needed since the bundler handles interop.

**Q11. What does `esModuleInterop` mean for `import * as` syntax?**
A: With `esModuleInterop: true`, TypeScript also generates a `__importStar` helper for `import * as name from 'module'`. Without this helper:

```ts
// CJS module that exports a function:
// module.exports = function() {}
// module.exports.helper = function() {}

import * as lib from './cjs-lib';
lib();          // Without esModuleInterop: works
lib.helper();   // Without esModuleInterop: works

// With esModuleInterop, namespace import wraps the module properly
// ensuring the namespace object has the right shape per the ES module spec
```

The `__importStar` helper ensures the namespace object created from `import * as` properly reflects the CJS module's exports while also handling modules that ARE true ES modules (those with `__esModule: true`).

### Section 4: `paths` and `baseUrl`

**Q12. What is `baseUrl` and what does it enable?**
A: `baseUrl` sets the root directory for resolving bare (non-relative) module imports. When set, TypeScript treats the specified directory as the root for module resolution — allowing you to import files using paths relative to that base without `../../../` traversal.

```json
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": "./src"
  }
}
```

```ts
// Without baseUrl (relative paths — fragile, hard to read):
import { UserService } from '../../../services/UserService';
import { validateEmail } from '../../utils/validation';

// With baseUrl: "./src" (absolute-style from src root):
import { UserService } from 'services/UserService';
import { validateEmail } from 'utils/validation';
```

`baseUrl` alone enables absolute-style imports. The configured directory becomes the implicit prefix for all non-relative imports. This makes imports cleaner and refactoring easier (moving a file doesn't require updating all relative paths).

**Q13. What is `paths` and how does it differ from `baseUrl`?**
A: `paths` creates explicit import aliases — mapping a prefix (or exact string) to one or more file system locations. It's more powerful than `baseUrl` alone because:

- It creates named aliases that can map to any location (including `node_modules`).
- It supports wildcard patterns.
- It supports multiple fallback locations per alias.

`paths` requires `baseUrl` to be set (it uses `baseUrl` as the root for path resolution).

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@app/*": ["src/app/*"],
      "@utils/*": ["src/utils/*"],
      "@components/*": ["src/components/*"],
      "@config": ["src/config/index.ts"],
      "lodash": ["node_modules/lodash-es"]
    }
  }
}
```

```ts
// With the above paths config:
import { Button } from '@components/Button';     // → src/components/Button
import { format } from '@utils/date';            // → src/utils/date
import config from '@config';                    // → src/config/index.ts
import { map } from 'lodash';                    // → node_modules/lodash-es (redirect!)
```

**Q14. What is the critical limitation of `paths` that every developer must know?**
A: `paths` in `tsconfig.json` is **type-checking only** — it does NOT affect the runtime module resolution. When TypeScript compiles your code to JavaScript, the path aliases are NOT automatically rewritten in the output. The `@components/Button` import in your TypeScript source appears as `@components/Button` in the compiled JavaScript output, which Node.js (or a browser) won't understand.

This is the #1 gotcha with `paths`. You must separately configure your bundler or runtime to resolve the same aliases:

```js
// Webpack — webpack.config.js
resolve: {
  alias: {
    '@components': path.resolve(__dirname, 'src/components'),
    '@utils': path.resolve(__dirname, 'src/utils'),
  }
}

// Vite — vite.config.ts
import { defineConfig } from 'vite';
import path from 'path';

export default defineConfig({
  resolve: {
    alias: {
      '@components': path.resolve(__dirname, 'src/components'),
      '@utils': path.resolve(__dirname, 'src/utils'),
    }
  }
});

// Node.js (without a bundler) — use tsconfig-paths or tsc-alias
// tsconfig-paths: register at runtime
// node -r tsconfig-paths/register dist/index.js

// tsc-alias: rewrite paths in compiled output
// Run after tsc: tsc-alias -p tsconfig.json
```

**Q15. What is the wildcard pattern `*` in `paths` and how does it work?**
A: The `*` wildcard in paths captures the rest of the import string after the matched prefix:

```json
{
  "paths": {
    "@app/*": ["src/app/*"]
  }
}
```

When you write `import { Foo } from '@app/components/Foo'`, TypeScript:
1. Matches `@app/*` with `*` = `components/Foo`
2. Substitutes: `src/app/components/Foo`
3. Resolves the file: `src/app/components/Foo.ts` (or `.tsx`, `/index.ts`, etc.)

Multiple fallback paths (array) are tried in order until one resolves:
```json
{
  "paths": {
    "@shared/*": [
      "packages/shared/src/*",   // try this first
      "packages/shared/dist/*"   // fallback if first doesn't exist
    ]
  }
}
```

### Section 5: `declaration` and Related Emit Options

**Q16. What does `"declaration": true` do?**
A: `declaration: true` tells the TypeScript compiler to generate `.d.ts` (declaration) files alongside the compiled JavaScript output. Declaration files contain only type information — no runtime code — describing the shapes of all exported types, functions, classes, and variables in the corresponding JavaScript file.

```ts
// src/math.ts
export function add(a: number, b: number): number {
  return a + b;
}

export type Operation = (a: number, b: number) => number;
```

With `declaration: true`, compiling produces:
```
dist/
  math.js          ← runtime code (the compiled JavaScript)
  math.d.ts        ← type information only
```

```ts
// dist/math.d.ts (auto-generated)
export declare function add(a: number, b: number): number;
export declare type Operation = (a: number, b: number) => number;
```

**Q17. Who needs `declaration: true` and who doesn't?**
A: You need `declaration: true` when:

- **Publishing an npm package**: consumers of your package who use TypeScript need `.d.ts` files to get type information. Without them, the entire library is untyped (essentially `any`).
- **Building a library used by other TypeScript projects** in a monorepo (via package-to-package references).
- **Sharing types between packages** without requiring consumers to compile your source TypeScript.

You do NOT need `declaration: true` when:

- **Building an application** (not a library) — the final bundled output isn't consumed by other TypeScript projects.
- **Your bundler (Vite, Next.js, Webpack)** handles transpilation and consumers don't import your source TypeScript directly.

```json
// Library tsconfig.json — needs declaration
{
  "compilerOptions": {
    "declaration": true,
    "declarationDir": "./types",
    "outDir": "./dist"
  }
}

// Application tsconfig.json — doesn't need declaration
{
  "compilerOptions": {
    "noEmit": true   // don't emit JS at all — let Vite/Webpack handle it
  }
}
```

**Q18. What are `declarationMap` and `declarationDir`, and when do you use them?**
A: These options refine how declaration files are generated:

**`declarationMap: true`**: generates `.d.ts.map` files alongside `.d.ts` files. These source maps link the declaration file back to the original TypeScript source. This enables "Go to Definition" in IDEs to navigate to the actual `.ts` source file (not the `.d.ts` shim) when developing within a monorepo where source is available.

```
dist/
  math.js
  math.d.ts
  math.d.ts.map    ← generated with declarationMap: true
```

**`declarationDir: "./types"`**: outputs all `.d.ts` files to a separate directory instead of alongside the `.js` files. Useful for clean separation:

```json
{
  "compilerOptions": {
    "outDir": "./dist",        // JS files go here
    "declarationDir": "./types" // .d.ts files go here
  }
}
```

The `package.json` of your library would reference both:
```json
{
  "main": "./dist/index.js",
  "types": "./types/index.d.ts"
}
```

**Q19. What is `emitDeclarationOnly` and when is it used?**
A: `emitDeclarationOnly: true` makes `tsc` output ONLY `.d.ts` files — no JavaScript. This is used when:

- A bundler (esbuild, Babel, SWC) handles the JavaScript transpilation.
- You want `tsc` to serve only as the type checker and `.d.ts` generator.
- You want to avoid running two separate tools that both generate `.js` files, potentially conflicting.

```json
// Library: let esbuild generate JS, tsc generates .d.ts
{
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true,
    "outDir": "./dist"
  }
}
```

```
# build script
esbuild src/index.ts --bundle --outfile=dist/index.js  # fast JS bundling
tsc --emitDeclarationOnly                               # .d.ts generation
```

**Q20. What is `composite: true` and project references?**
A: `composite: true` is part of TypeScript's project references system, designed for large monorepos. It enables incremental builds and cross-project references. When `composite: true` is set:

1. `declaration: true` is automatically enabled (required).
2. `declarationMap: true` is recommended (for IDE navigation).
3. TypeScript generates a `.tsbuildinfo` file (incremental build cache).
4. Other projects can reference this project via `references` in their `tsconfig.json`.

```json
// packages/shared/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "outDir": "./dist",
    "rootDir": "./src"
  }
}

// packages/app/tsconfig.json
{
  "compilerOptions": { "strict": true },
  "references": [
    { "path": "../shared" }  // declares dependency on shared package
  ]
}
```

Running `tsc --build` respects project references, rebuilding only the projects that have changed — dramatically faster in large monorepos.

### Section 6: Scenario / Interview-Style Questions

**Q21. "You're migrating a large JavaScript codebase to TypeScript. What `tsconfig.json` options do you start with, and how do you tighten them over time?"**
A: A practical migration strategy:

**Phase 1 — Minimum viable TypeScript (accept everything)**:
```json
{
  "compilerOptions": {
    "allowJs": true,           // allow .js files alongside .ts
    "checkJs": false,          // don't type-check .js yet
    "noImplicitAny": false,    // allow implicit any during migration
    "strict": false,           // disable all strict checks initially
    "target": "ES2022",
    "module": "CommonJS",
    "esModuleInterop": true,   // fix CJS import issues immediately
    "skipLibCheck": true       // don't check .d.ts in node_modules
  },
  "include": ["src/**/*"]
}
```

**Phase 2 — Tighten incrementally**:
```json
{
  "compilerOptions": {
    "allowJs": false,          // all files should be .ts now
    "strictNullChecks": true,  // enable the most impactful flag first
    "noImplicitAny": true,     // force explicit types
    // Leave other strict flags for later
  }
}
```

**Phase 3 — Full strict**:
```json
{
  "compilerOptions": {
    "strict": true             // all strict flags enabled
  }
}
```

The key is enabling flags one at a time with team agreement and fixing errors immediately. `strictNullChecks` first because it catches the most runtime bugs. `noImplicitAny` second because it forces type thinking. Other strict flags are lower-risk and can be enabled together.

**Q22. "A junior developer is getting 'Cannot find module' errors for path aliases like `@utils/date`. What are all the possible causes?"**
A: Five categories of failure:

1. **`paths` configured in `tsconfig.json` but no `baseUrl`**: `paths` requires `baseUrl`. Without it, TypeScript ignores the `paths` config silently (or errors in newer versions).

2. **`paths` configured correctly but bundler doesn't know about it**: TypeScript's `paths` only affects type-checking. Webpack, Vite, Jest, Node.js — all need their own alias configuration. The most common oversight.

3. **Wrong wildcard pattern**: `@utils/*` maps to the import `@utils/date` where `*` = `date`. The target must be `["src/utils/*"]` not `["src/utils/"]` (missing wildcard in the target).

4. **`baseUrl` is wrong**: if `baseUrl` is `"src"` but the path target is `["src/utils/*"]`, TypeScript resolves relative to `baseUrl` — so it looks for `src/src/utils/*`. Should be `["utils/*"]` when `baseUrl` is already `"src"`.

5. **File extension in path**: `@utils/date` resolves via TypeScript's module resolution rules — it tries `.ts`, `.tsx`, `.d.ts`, `/index.ts` etc. If the file is `date.tsx` but the import says `@utils/date`, this usually works. But if there are resolution ordering issues, an explicit extension in the paths target may be needed.

**Q23. "Your npm package has TypeScript users complaining that they get no type information — everything is `any`. What's missing?"**
A: The `.d.ts` files are missing or not referenced correctly. Checklist:

1. **`declaration: true` missing from `tsconfig.json`**: compile without it and no `.d.ts` files are generated.

2. **`types` or `typings` field missing from `package.json`**: TypeScript looks for type declarations at the package root or in the `types` / `typings` field. Without it, TypeScript may not find the `.d.ts` files even if they exist.

```json
// package.json — correct configuration
{
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",    // ← tell TypeScript where to find types
  "exports": {
    ".": {
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js",
      "types": "./dist/index.d.ts"  // ← also in exports map (TypeScript 4.7+)
    }
  }
}
```

3. **`.d.ts` files excluded from npm publish**: check `.npmignore` or `package.json` `"files"` field — the `dist/` or `types/` directory must be included.

4. **`skipLibCheck: true` on the consumer side**: if the consumer has `skipLibCheck: true`, TypeScript skips checking `.d.ts` files entirely — errors in your declarations are silently ignored. But if the `.d.ts` files don't exist at all, imports will be typed as `any`.

5. **TypeScript version mismatch**: if you used TypeScript 5.0 features in your `.d.ts` files but the consumer is on TypeScript 4.x, their compiler can't parse the declarations.

## Problem 1 — Diagnosing `strict: true` Errors

### Problem
A team just enabled `"strict": true` on a previously unstrict codebase. They get hundreds of errors. Given these code snippets, explain each error and the minimal fix for each.

```ts
// Error 1:
function getUser(id) {  // Error: Parameter 'id' implicitly has an 'any' type
  return fetch(`/api/users/${id}`);
}

// Error 2:
class DatabaseConnection {
  pool: Pool;           // Error: Property 'pool' has no initializer
  connect() {
    this.pool = new Pool();
  }
}

// Error 3:
const users = [{ name: 'Alice' }, { name: 'Bob' }];
const found = users.find(u => u.name === 'Alice');
console.log(found.name); // Error: Object is possibly 'undefined'

// Error 4:
try {
  JSON.parse(userInput);
} catch (err) {
  console.log(err.message); // Error: 'err' is of type 'unknown'
}

// Error 5:
function processItems(items: string[] | null) {
  return items.length; // Error: Object is possibly 'null'
}
```

### Error Analysis and Fixes

```ts
// ── Error 1: noImplicitAny ─────────────────────────────────────────────
// CAUSE: 'id' has no type annotation → TypeScript can't infer it → implicit any

// Fix 1a: add explicit type
function getUser(id: string | number) {
  return fetch(`/api/users/${id}`);
}

// Fix 1b: if truly unknown type, use explicit any (intentional escape)
function getUser(id: any) {
  return fetch(`/api/users/${id}`);
}

// Fix 1c: use unknown for safer typing (must narrow before use)
function getUser(id: unknown) {
  if (typeof id !== 'string' && typeof id !== 'number') {
    throw new Error('id must be string or number');
  }
  return fetch(`/api/users/${id}`);
}

// ── Error 2: strictPropertyInitialization ──────────────────────────────
// CAUSE: 'pool' declared but not initialized in constructor

// Fix 2a: initialize in declaration
class DatabaseConnection {
  pool: Pool = new Pool(); // initialized at declaration
}

// Fix 2b: initialize in constructor
class DatabaseConnection {
  pool: Pool;
  constructor() {
    this.pool = new Pool();
  }
}

// Fix 2c: definite assignment assertion (!) for framework-initialized props
class DatabaseConnection {
  pool!: Pool; // trust me — it will be set before use
  // (appropriate for ORMs, DI frameworks that set properties externally)
}

// Fix 2d: make it optional
class DatabaseConnection {
  pool?: Pool; // now Pool | undefined — must check before use
  connect() {
    this.pool = new Pool();
  }
  query() {
    if (!this.pool) throw new Error('Not connected');
    return this.pool.query();
  }
}

// ── Error 3: strictNullChecks — Array.find returns T | undefined ────────
// CAUSE: Array.find() can return undefined if no element matches
// found: { name: string } | undefined
// found.name → Error: Object is possibly 'undefined'

// Fix 3a: null check before use
if (found !== undefined) {
  console.log(found.name); // ✓ TypeScript narrowed to { name: string }
}

// Fix 3b: optional chaining (if undefined is acceptable)
console.log(found?.name); // string | undefined

// Fix 3c: non-null assertion (!) — if you're certain it exists
console.log(found!.name); // ✓ but dangerous — throws if found is undefined

// Fix 3d: provide a fallback
console.log(found?.name ?? 'Not found');

// ── Error 4: useUnknownInCatchVariables ────────────────────────────────
// CAUSE: With strict, catch variables are typed as 'unknown', not 'any'
// err.message → Error: Property 'message' does not exist on type 'unknown'

// Fix 4a: instanceof check
try {
  JSON.parse(userInput);
} catch (err) {
  if (err instanceof Error) {
    console.log(err.message); // ✓ err narrowed to Error
  } else {
    console.log('Unknown error:', String(err));
  }
}

// Fix 4b: type guard helper
function isError(err: unknown): err is Error {
  return err instanceof Error;
}
try {
  JSON.parse(userInput);
} catch (err) {
  if (isError(err)) console.log(err.message);
}

// Fix 4c: type assertion (less safe)
try {
  JSON.parse(userInput);
} catch (err) {
  console.log((err as Error).message); // ✓ but could fail if err isn't Error
}

// ── Error 5: strictNullChecks — nullable parameter ─────────────────────
// CAUSE: 'items' is string[] | null — null doesn't have .length

// Fix 5a: null check
function processItems(items: string[] | null) {
  if (items === null) return 0;
  return items.length; // ✓ narrowed to string[]
}

// Fix 5b: nullish coalescing
function processItems(items: string[] | null) {
  return (items ?? []).length;
}

// Fix 5c: make parameter non-nullable (if null is unexpected)
function processItems(items: string[]) { // remove null from signature
  return items.length;
}
// Callers must ensure they don't pass null — TypeScript enforces this
```

### The Pattern Behind All These Errors

All five errors stem from just two strict flags:
- `noImplicitAny` → Error 1 (untyped parameter)
- `strictPropertyInitialization` → Error 2 (uninitialized property)
- `strictNullChecks` → Errors 3, 4, 5 (null/undefined not handled)
- `useUnknownInCatchVariables` → Error 4 (catch clause typing)

Enabling `strictNullChecks` alone typically generates 70–80% of migration errors in real codebases. The vast majority follow the same pattern: a value that could be `null` or `undefined` is used without a check. The fix is always one of: check first, provide a default, or change the type to reflect that it can't be null.

### Follow-up Questions
- "How do you enable strict mode incrementally across a large codebase without fixing all errors at once?" → Use `@ts-ignore` or `@ts-expect-error` as temporary suppressors for known issues, then track them in a counter — enforce that the count doesn't increase (new code must be strict) while the team chips away at the existing errors.

## Problem 2 — Configuring `esModuleInterop` for a Mixed CJS/ESM Project

### Problem
A Node.js project uses TypeScript and imports both CJS packages (`express`, `lodash`) and ESM packages. The team gets runtime errors when importing some packages. Configure `tsconfig.json` correctly and explain what each option does.

```ts
// Current code — runtime errors:
import express from 'express';   // Runtime: TypeError: express is not a function
import _ from 'lodash';          // Runtime: TypeError: _ is not a function
import { readFileSync } from 'fs'; // Works fine (named import from CJS)
import got from 'got';           // got is ESM — different issue
```

### Diagnosis

```
Root cause analysis:

1. express and lodash are CommonJS modules:
   - They use: module.exports = function() { ... }
   - NO __esModule marker
   - When TypeScript compiles 'import express from "express"' WITHOUT esModuleInterop:
     → const express_1 = require('express');
     → const _default = express_1.default;  ← express_1 IS the function, no .default
     → calling _default() fails — it's undefined!

2. fs is also CJS but uses named exports:
   - require('fs') returns { readFileSync: fn, writeFileSync: fn, ... }
   - Named import works: const { readFileSync } = require('fs') ✓

3. got@12 is pure ESM — separate issue unrelated to esModuleInterop
```

### Solution

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "CommonJS",        // output CommonJS for Node.js
    "moduleResolution": "node16", // or "bundler" for modern setups

    // FIX 1: Enable esModuleInterop
    "esModuleInterop": true,
    // → Generates __importDefault helper for default imports of CJS modules
    // → Allows: import express from 'express' (syntactic sugar now works)
    // → Implies allowSyntheticDefaultImports: true

    // FIX 2: skipLibCheck (optional — avoid .d.ts errors from packages)
    "skipLibCheck": true,

    "strict": true,
    "outDir": "./dist"
  }
}
```

### What `esModuleInterop` Generates

```ts
// Your TypeScript source:
import express from 'express';
import _ from 'lodash';

// Without esModuleInterop — generated JS (BROKEN):
"use strict";
const express_1 = require("express");
const lodash_1 = require("lodash");
express_1.default();  // undefined()! — express has no .default
lodash_1.default.map; // undefined! — lodash has no .default

// With esModuleInterop — generated JS (CORRECT):
"use strict";
var __importDefault = (this && this.__importDefault) || function (mod) {
  return (mod && mod.__esModule) ? mod : { "default": mod };
  // If mod doesn't have __esModule flag → wrap it: { default: mod }
  // Now mod.default = the actual module.exports value
};
const express_1 = __importDefault(require("express"));
const lodash_1 = __importDefault(require("lodash"));
express_1.default();    // ✓ express function
lodash_1.default.map;   // ✓ lodash object
```

### Handling Pure ESM Packages (`got@12`)

```json
// For pure ESM packages like got@12, the solution is different:
{
  "compilerOptions": {
    "module": "ESNext",          // Output ESM to support ESM packages
    "moduleResolution": "node16" // or "nodenext" for package.json "exports" support
  }
}
```

Or use dynamic import for CJS to import ESM:
```ts
// In a CJS project: use dynamic import for ESM packages
const got = await import('got');
const response = await got.default.get('https://example.com');
```

### Package.json for a Pure ESM Project

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "type": "module"  // ← tells Node.js all .js files are ESM
}
```

```json
// tsconfig.json for pure ESM Node.js project
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "node16",
    "esModuleInterop": true,
    "strict": true,
    "outDir": "./dist"
  }
}
```

### Follow-up Questions
- "What's the difference between `module: "CommonJS"` and `module: "ESNext"` in tsconfig?" → `CommonJS` compiles `import/export` to `require()`/`module.exports` — runs in Node.js without flags. `ESNext` keeps native `import/export` — requires Node.js 12+ with `.mjs` or `"type": "module"` in package.json, or a bundler.

## Problem 3 — Path Aliases Not Working at Runtime

### Problem
A developer configured path aliases in `tsconfig.json`, TypeScript type-checking passes, but the built application throws `Cannot find module '@utils/format'` at runtime. Fix the configuration for three different environments: Webpack, Vite, and Node.js (without bundler).

```json
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@utils/*": ["src/utils/*"],
      "@components/*": ["src/components/*"],
      "@api/*": ["src/api/*"]
    }
  }
}
```

### Root Cause

```
tsconfig.json "paths" → TypeScript type checking ONLY
                      ↓
Compiled JavaScript still contains: import { format } from '@utils/format'
                                                               ↑
                         Node.js/browser has no idea what '@utils' means
                                               ↓
                              Cannot find module '@utils/format' ← runtime error
```

### Fix 1 — Webpack

```js
// webpack.config.js
const path = require('path');

module.exports = {
  // ...
  resolve: {
    alias: {
      // Mirror EXACTLY what's in tsconfig.json "paths"
      '@utils': path.resolve(__dirname, 'src/utils'),
      '@components': path.resolve(__dirname, 'src/components'),
      '@api': path.resolve(__dirname, 'src/api'),
    },
    extensions: ['.ts', '.tsx', '.js', '.jsx']
  }
};
```

### Fix 2 — Vite

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import path from 'path';

export default defineConfig({
  resolve: {
    alias: {
      '@utils': path.resolve(__dirname, './src/utils'),
      '@components': path.resolve(__dirname, './src/components'),
      '@api': path.resolve(__dirname, './src/api'),
    }
  }
});
```

**Better approach for Vite: use `vite-tsconfig-paths` plugin to auto-sync:**
```ts
// vite.config.ts
import { defineConfig } from 'vite';
import tsconfigPaths from 'vite-tsconfig-paths';

export default defineConfig({
  plugins: [
    tsconfigPaths() // ← automatically reads paths from tsconfig.json!
  ]
});
// Now you only maintain one source of truth: tsconfig.json
```

### Fix 3 — Node.js Without Bundler

**Option A: `tsc-alias` (rewrite paths at compile time)**

```json
// package.json scripts
{
  "scripts": {
    "build": "tsc && tsc-alias",
    "dev": "ts-node -r tsconfig-paths/register src/index.ts"
  },
  "devDependencies": {
    "tsc-alias": "^1.8.0",
    "tsconfig-paths": "^4.0.0",
    "ts-node": "^10.0.0"
  }
}
```

`tsc-alias` post-processes the compiled `.js` files, rewriting `@utils/format` to `../../utils/format` — the actual relative path — after `tsc` runs.

**Option B: `tsconfig-paths` (runtime resolver)**

```ts
// src/index.ts — add at the very top of the entry point
// OR use: node -r tsconfig-paths/register dist/index.js

// For ts-node:
// ts-node -r tsconfig-paths/register src/index.ts
```

`tsconfig-paths` hooks into Node's module resolver at runtime, reading `paths` from `tsconfig.json` and resolving aliases dynamically.

**Option C: Reconfigure to avoid aliases entirely**

Use `baseUrl` without `paths` for simple absolute imports:
```json
{
  "compilerOptions": {
    "baseUrl": "./src"
  }
}
```

```ts
// Now works WITHOUT any bundler config:
import { format } from 'utils/format';    // → src/utils/format.ts
import { Button } from 'components/Button'; // → src/components/Button.ts
```

With `baseUrl` only (no `paths`), Node.js module resolution is changed: TypeScript resolves bare imports from `./src`. But this ONLY works when `tsc` is the sole transpiler — bundlers still need their alias config.

### The "Single Source of Truth" Pattern

```ts
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]  // simple: everything under src is @/...
    }
  }
}

// vite.config.ts (with tsconfigPaths plugin):
// No alias config needed — plugin reads tsconfig.json

// jest.config.js:
{
  "moduleNameMapper": {
    "^@/(.*)$": "<rootDir>/src/$1"  // mirror the paths pattern
  }
}
```

### Follow-up Questions
- "Why does TypeScript even have `paths` if it doesn't affect runtime?" → TypeScript's role is type-checking, not module bundling. `paths` tells the type-checker where to find types for aliased imports. The runtime resolution is the bundler's responsibility. This separation of concerns means you can swap bundlers (Webpack → Vite → Rollup) without changing TypeScript configuration.

## Problem 4 — Publishing a TypeScript Library with Correct `declaration` Config

### Problem
You're publishing an npm library written in TypeScript. Configure `tsconfig.json` and `package.json` so that TypeScript consumers get full type information, including source navigation (Go to Definition) in IDEs, and CJS/ESM consumers both work.

### Requirements
- TypeScript consumers get full type information
- `Go to Definition` navigates to the `.ts` source (not `.d.ts` shim)
- Both CJS and ESM consumers work
- esbuild handles transpilation (fast), tsc handles types only

### Solution

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,

    // Declaration output:
    "declaration": true,          // generate .d.ts files
    "declarationMap": true,       // generate .d.ts.map for "Go to Definition"
    "emitDeclarationOnly": true,  // only .d.ts — esbuild generates .js
    "declarationDir": "./dist/types",

    // Source configuration:
    "rootDir": "./src",
    "outDir": "./dist",           // (not used since emitDeclarationOnly)

    // Module interop:
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"],
  "exclude": ["node_modules", "dist", "**/*.test.ts", "**/*.spec.ts"]
}
```

```json
// package.json
{
  "name": "my-library",
  "version": "1.0.0",

  // CJS entry point:
  "main": "./dist/cjs/index.js",

  // ESM entry point:
  "module": "./dist/esm/index.js",

  // TypeScript types:
  "types": "./dist/types/index.d.ts",

  // Modern package exports (Node 12+, bundlers):
  "exports": {
    ".": {
      "import": {
        "types": "./dist/types/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types": "./dist/types/index.d.ts",
        "default": "./dist/cjs/index.js"
      }
    }
  },

  // Ensure these directories are published:
  "files": ["dist"],

  "scripts": {
    // Fast transpilation with esbuild:
    "build:cjs": "esbuild src/index.ts --bundle=false --format=cjs --outdir=dist/cjs",
    "build:esm": "esbuild src/index.ts --bundle=false --format=esm --outdir=dist/esm",
    // Type declaration generation:
    "build:types": "tsc --emitDeclarationOnly",
    // Run all:
    "build": "npm run build:cjs && npm run build:esm && npm run build:types",
    "typecheck": "tsc --noEmit"
  }
}
```

### Resulting File Structure

```
my-library/
├── src/
│   └── index.ts          ← source (TypeScript)
├── dist/
│   ├── cjs/
│   │   └── index.js      ← compiled CommonJS
│   ├── esm/
│   │   └── index.js      ← compiled ES modules
│   └── types/
│       ├── index.d.ts    ← type declarations
│       └── index.d.ts.map ← maps .d.ts → .ts source
└── package.json
```

### How `declarationMap` Enables "Go to Definition"

```
IDE: user Ctrl+clicks on a symbol from your library
  → IDE reads types from dist/types/index.d.ts
  → Sees index.d.ts.map pointing to: "sources": ["../../src/index.ts"]
  → Navigates to the actual TypeScript source
  → User sees real source code, not the generated .d.ts stub
```

Without `declarationMap`: Go to Definition → sees the `.d.ts` file (declarations without implementation). With `declarationMap`: Go to Definition → sees the original `.ts` source file — significantly better developer experience.

### Consumer Experience

```ts
// Consumer (TypeScript user):
import { createWidget } from 'my-library';
//       ^^^^^^^^^^^
// Ctrl+click → navigates to src/index.ts (the real source!)
// TypeScript reads types from dist/types/index.d.ts

const widget = createWidget({ title: 'Hello' });
//    ^^^^^^
// Fully typed: TypeScript knows the shape of widget
```

### Follow-up Questions
- "What's the difference between `types` and `typings` in package.json?" → Identical — both point to the main declaration file. `types` is the preferred modern spelling; `typings` is the legacy name. TypeScript honors both.
- "What if the library has multiple entry points (e.g., `my-library/utils`)?" → Add multiple exports in `package.json` exports map: `"./utils": { "import": "./dist/esm/utils.js", "types": "./dist/types/utils.d.ts" }`.

```json
// tsconfig.base.json (root — shared settings)
{
  "compilerOptions": {
```

```json
    { "path": "./packages/web" }
  ]
}
```

### Build Scripts

```json
// root package.json
{
  "scripts": {
    // Type-check all packages respecting dependencies:
    "typecheck": "tsc --build --noEmit",

    // Build all packages in dependency order:
    "build": "tsc --build",

    // Build only specific package:
    "build:shared": "tsc --build packages/shared",

    // Watch mode (incremental):
    "watch": "tsc --build --watch"
  }
}
```

### How `references` Work

```
tsc --build (at root)
  1. Reads root tsconfig.json → sees references to all three packages
  2. Resolves dependency order:
     shared (no references) → built first
     api (references shared) → built second
     web (references shared) → built third (could parallel with api)
  3. For each package:
     - Checks if .tsbuildinfo is up to date
     - If up to date: skip (fast!)
     - If changed: recompile, update .tsbuildinfo
  4. Total time for unchanged code: milliseconds
     (vs minutes for full recompile without --build)
```

### Follow-up Questions
- "What does `"files": []` in the root tsconfig do?" → Without `"files": []` or `"include": []`, TypeScript would try to compile all `.ts` files found from the root — including source from all packages — with the root config. Setting `"files": []` makes the root config compile NOTHING on its own; it only serves as a reference coordinator for `tsc --build`.

## Quick Reference — `tsconfig.json` Options Cheat Sheet

```
strict (enables all strict flags):
  strictNullChecks          → null/undefined not assignable to other types
  noImplicitAny             → parameters must be explicitly typed
  strictPropertyInitialization → class props must be initialized
  useUnknownInCatchVariables → catch variables typed as unknown
  strictFunctionTypes       → function parameters checked contra-variantly
  strictBindCallApply       → bind/call/apply type-checked
  alwaysStrict              → emit "use strict"
  noImplicitThis            → this: any is an error

esModuleInterop:
  true  → generates __importDefault/__importStar helpers
          allows: import express from 'express'
          implies: allowSyntheticDefaultImports
  false → require namespace imports for CJS: import * as express from 'express'

allowSyntheticDefaultImports:
  true  → type-checking only — no helpers emitted
          use when bundler handles CJS/ESM interop
  (implied by esModuleInterop: true)

paths:
  requires baseUrl
  affects TYPE-CHECKING ONLY — not runtime
  bundlers need their own alias config (webpack.alias, vite.resolve.alias)
  wildcard: "@utils/*": ["src/utils/*"]

baseUrl:
  root for resolving non-relative imports
  (".": project root, "./src": src folder)

declaration:
  true  → generate .d.ts files (required for npm packages)
  false → no .d.ts (for applications)

declarationMap:
  true  → generate .d.ts.map — enables IDE "Go to Definition" to .ts source
  (especially valuable in monorepos and published libraries)

declarationDir:
  separate directory for .d.ts files
  (useful for publishing: types in ./types, js in ./dist)

emitDeclarationOnly:
  true  → only generate .d.ts — no .js output
  (use with esbuild/swc for faster builds)

composite:
  true  → for project references (monorepos)
          implies: declaration: true
          generates: .tsbuildinfo (incremental build cache)

noEmit:
  true  → type-check only, no output
  (for app builds where bundler handles transpilation)
```

## Common Bugs Checklist

Before finalizing `tsconfig.json`, verify:

1. **`paths` without `baseUrl`** — `paths` silently does nothing (or errors in recent TypeScript) without `baseUrl`. Always set `baseUrl` when using `paths`. Most commonly set to `"."` (project root) or `"./src"`.

2. **Path aliases not configured in bundler** — TypeScript `paths` is type-checking only. Check webpack `resolve.alias`, Vite `resolve.alias`, Jest `moduleNameMapper`, and any other tool that resolves modules. All need matching alias configuration.

3. **`declaration: true` without `rootDir`** — without `rootDir`, TypeScript may infer a wider root (including test files or node_modules), generating incorrect `.d.ts` directory structure. Always set `rootDir` when using `declaration`.

4. **`declarationDir` path relative to `tsconfig.json`** — paths in tsconfig are relative to the location of `tsconfig.json`. If `tsconfig.json` is in `packages/mylib/` and `declarationDir` is `"./dist/types"`, the output goes to `packages/mylib/dist/types/`. Verify the path resolves where you expect.

5. **`esModuleInterop: false` with default imports from CJS packages** — the symptom is runtime errors like "X is not a function" or "X is not a constructor" for packages like express, lodash, chalk, etc. Solution: `esModuleInterop: true`. If using a bundler that already handles interop, `allowSyntheticDefaultImports: true` suffices for type-checking.

6. **`strict: true` with legacy code** — enabling strict on a large existing codebase without a plan causes hundreds of errors that block the entire team. Either: (a) migrate incrementally by enabling one flag at a time, or (b) use `@ts-ignore` suppressors tracked by count to ensure no regression while allowing gradual cleanup.
