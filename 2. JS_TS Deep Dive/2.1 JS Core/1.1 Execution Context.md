# JavaScript Core (Fundamentals): Execution Context — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an execution context?**
A: An execution context is the environment in which JavaScript code is evaluated and run. It holds everything needed to execute a chunk of code: variable/function declarations, the scope chain, and the value of `this`. Every time a function is invoked, a new execution context is created for that call.

**Q2. What are the different types of execution context?**
A:
- **Global Execution Context (GEC)** — created once, when the script first runs. There's only one, and it creates the global object (`window` in browsers, `global`/`globalThis` in Node) and binds `this` to it (in non-strict mode, sloppy code).
- **Function Execution Context (FEC)** — created every time a function is invoked. Each call gets its own context, even for recursive calls.
- **Eval Execution Context** — created when code runs inside `eval()`. Rarely relevant day-to-day, but interviewers sometimes mention it for completeness.

**Q3. What is the Execution Context Stack (a.k.a. Call Stack)?**
A: It's a LIFO (last-in-first-out) stack that tracks execution contexts. The Global Execution Context sits at the bottom, and every function call pushes a new Function Execution Context on top. When a function returns, its context is popped off. This stack is also what you see when you read a stack trace or an error's `.stack`.

**Q4. What does an execution context actually contain?**
A: Three main components:
1. **Variable Environment** — where `var` declarations and function declarations live.
2. **Lexical Environment** — where `let`/`const` declarations live, plus a reference to the *outer* lexical environment (this reference is what forms the scope chain).
3. **`this` binding** — determined by how the function was called (not where it was defined, except for arrow functions).

**Q5. What are the two phases every execution context goes through?**
A:
- **Creation (Memory Creation / Hoisting) phase** — the JS engine scans the code and allocates memory for variables and functions before any code actually runs. `var` variables are initialized to `undefined`, function declarations are stored in full, and `let`/`const` are created but left in the "Temporal Dead Zone" (uninitialized).
- **Execution phase** — the engine runs the code line by line, assigning actual values and executing statements.

## Section 2: Creation Phase, Hoisting & the Temporal Dead Zone

**Q6. Why does `console.log(x); var x = 5;` print `undefined` instead of throwing an error?**
A: Because of the creation phase — `var x` is hoisted and initialized to `undefined` before execution starts. By the time `console.log(x)` runs, `x` already exists in memory (as `undefined`), so there's no `ReferenceError`, just an "unexpected" value.

**Q7. Why does the same pattern with `let` throw an error?**
A: `let` and `const` are also hoisted (memory is allocated in the creation phase), but they aren't initialized — they stay in the **Temporal Dead Zone (TDZ)** from the start of the block until the line where they're declared. Accessing them before that line throws a `ReferenceError: Cannot access 'x' before initialization`.

**Q8. Are function declarations and function expressions hoisted the same way?**
A: No.
- **Function declarations** (`function foo() {}`) are fully hoisted — the entire function body is available in memory during the creation phase, so you can call `foo()` before its line in the file.
- **Function expressions** (`const foo = function() {}` or `const foo = () => {}`) follow the hoisting rules of the variable they're assigned to (`var`/`let`/`const`), so the function itself isn't callable until the assignment line actually executes.

**Q9. What happens if a `var` and a function declaration share the same name?**
A: The function declaration wins during the creation phase (function declarations take priority over plain `var` hoisting), but a later assignment in the execution phase (e.g., `var foo = 10;`) will overwrite it, since execution happens top-to-bottom after hoisting is done.

**Q10. Is hoisting a "bug" or a deliberate design choice?**
A: It's a natural consequence of how the two-phase (creation + execution) model works — it's not magic, it's memory being allocated ahead of time. Understanding it as "creation phase pre-scans the code" rather than "JS moves declarations to the top" avoids a lot of confusion, especially around TDZ.

## Section 3: Scope Chain & Lexical Environment

**Q11. What is the scope chain, and how does it relate to execution context?**
A: Every execution context's lexical environment keeps a reference to its outer (parent) lexical environment. When a variable isn't found in the current context, the engine walks up this chain of references — this walk is the scope chain. It's resolved lexically (based on where the code is *written*), not dynamically (based on who *calls* it).

**Q12. What's the difference between lexical scope and dynamic scope?**
A: JavaScript uses lexical scope — a function's access to outer variables is determined by where it's *defined* in the source code, not by where or how it's *called*. This is why a function can "remember" variables from its defining scope even when invoked somewhere completely different (this is the mechanism behind closures).

**Q13. What is a closure, in terms of execution context?**
A: A closure is what happens when a function retains a reference to its outer lexical environment even after that outer function's execution context has been popped off the call stack. The inner function's execution context still points to the (now "detached") outer variable environment, keeping those variables alive in memory instead of letting them be garbage collected.

**Q14. Classic interview trap — what does this log, and why?**
```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```
A: It logs `3, 3, 3`. `var` is function/global-scoped, not block-scoped, so all three closures created inside the loop share the *same* variable `i` in the *same* execution context's variable environment. By the time the callbacks run (after the loop finishes and the call stack clears), `i` has already reached `3`.

**Q15. How would you fix Q14 to log `0, 1, 2`?**
A: Use `let` instead of `var`. `let` is block-scoped, so the `for` loop creates a *new* lexical environment (and a fresh binding of `i`) on every iteration. Each closure captures its own iteration's `i`. (An older pre-ES6 fix was wrapping the body in an IIFE to manually create a new scope per iteration.)

## Section 4: `this` Binding

**Q16. How is `this` determined inside a regular function?**
A: By *how the function is called*, not where it's defined — this is called "dynamic" or "call-site" binding. The four common rules, in order of precedence:
1. `new Foo()` → `this` is the newly created object.
2. `foo.call(obj)` / `foo.apply(obj)` / `foo.bind(obj)` → `this` is explicitly set to `obj`.
3. `obj.foo()` (method call) → `this` is `obj`.
4. Plain `foo()` call → `this` is `undefined` in strict mode, or the global object in non-strict mode.

**Q17. How does `this` work differently in arrow functions?**
A: Arrow functions don't create their own `this` binding at all — they don't have their own execution context's `this`; they lexically capture `this` from the *enclosing* execution context at the time they're defined. This is why arrow functions are commonly used for callbacks inside methods, to avoid losing the outer `this`.

**Q18. Classic trap — why does `this` become `undefined` here?**
```js
const obj = {
  name: "Alice",
  greet() {
    setTimeout(function () {
      console.log(this.name);
    }, 100);
  }
};
obj.greet();
```
A: The callback passed to `setTimeout` is a regular function, and it's invoked by the timer mechanism as a plain function call (`callback()`), not as `obj.callback()`. So rule 4 applies — `this` is `undefined` (strict mode) or the global object, and `this.name` is `undefined` or throws. Fixing it: use an arrow function for the callback (captures `greet`'s `this`), or `bind(this)`, or store `const self = this` beforehand.

**Q19. Does `bind()` create a new function with a new execution context every time it's called?**
A: `bind()` returns a new function object, but that new function, when invoked, still creates a normal execution context — the difference is that its `this` is permanently fixed at creation time and can't be overridden later by `call`/`apply`/method-call syntax.

## Section 5: Async Code & the Event Loop (Where Execution Context Meets Concurrency)

**Q20. If JavaScript is single-threaded with one call stack, how does async code (like `setTimeout` or `fetch`) not block everything?**
A: The call stack itself is single-threaded, but the surrounding runtime (browser or Node) has additional pieces — Web APIs / libuv thread pool, a callback/task queue (and a separate microtask queue), and the event loop. Async work is handed off outside the call stack; once it completes, its callback is queued, and the event loop pushes it onto the call stack (creating a fresh execution context for it) only when the stack is empty.

**Q21. What's the difference between the microtask queue and the macrotask (callback) queue, in terms of execution context ordering?**
A: After the currently running execution context finishes and the call stack is empty, the event loop drains the **entire microtask queue** (Promise `.then`/`.catch`/`.finally` callbacks, `queueMicrotask`) before picking even one task from the **macrotask queue** (`setTimeout`, `setInterval`, I/O callbacks). This is why `Promise.resolve().then(...)` logs before a `setTimeout(..., 0)` callback, even though both are "async."

**Q22. Does `async`/`await` create new execution contexts differently than regular functions?**
A: An `async` function still gets a normal Function Execution Context on the call stack. The difference is that hitting an `await` suspends that context — it's popped off the stack (control returns to the caller) — and when the awaited promise settles, the remainder of the function resumes in a new turn of the event loop, scheduled as a microtask, effectively re-entering (a continuation of) that context.

**Q23. Why can a long-running synchronous loop "freeze" the UI, even if you have async callbacks pending?**
A: Because the call stack must be completely empty before the event loop will process the next queued task or microtask. A synchronous execution context that runs a long `for` loop or heavy computation blocks the single thread — no timers fire, no promises resolve, no UI repaints — until that execution context finishes and is popped.

## Section 6: Trade-offs, Memory & Debugging

**Q24. How can closures/execution contexts cause memory leaks?**
A: If a closure keeps a reference to an outer execution context's variables (e.g., a large array or DOM node) and that closure is itself kept alive (assigned to a long-lived variable, an event listener that's never removed, a timer that never clears), the JS engine can't garbage-collect that outer context's memory — it's still "reachable." This is a common source of leaks in single-page apps with unremoved event listeners.

**Q25. What causes a "Maximum call stack size exceeded" error?**
A: Unbounded recursion — each recursive call pushes a new Function Execution Context onto the call stack without ever popping enough of them off (no proper base case, or a base case that's never reached). The stack has a finite size, and once it's exceeded, the engine throws instead of crashing the process.

**Q26. Scenario: "A junior engineer wrote a callback that reads `this.state` inside a class method used as an event handler in vanilla JS (no framework), and it's `undefined` in production. What's happening, and how do you fix it?"**
A: The method is likely being passed as a bare reference (e.g., `element.addEventListener('click', obj.handleClick)`), which strips it from `obj` — when the DOM invokes it, it's a plain function call, so rule 4 applies and `this` isn't `obj`. Fixes: bind it in the constructor (`this.handleClick = this.handleClick.bind(this)`), convert it to a class property arrow function (`handleClick = () => {...}`), or wrap it at the call site (`() => obj.handleClick()`).

**Q27. Scenario: "You're debugging a production issue where variables from a completed API callback seem to have stale/old values several requests later." What execution-context-related concept explains this, and what would you check?**
A: Classic closure-over-shared-state bug — if the callback closes over a variable declared in an outer scope that's being *reused* or *mutated* across multiple calls (e.g., a shared loop variable, or a module-level variable being reassigned) rather than freshly created per invocation, every closure will see the *latest* mutated value instead of a snapshot at creation time. Check whether the captured variable is declared with `var` vs `let`/`const` in the right scope, and whether it's being shared across concurrent async operations that weren't isolated per-call.

**Q28. Is it worth memorizing every event-loop detail for a 5 YOE interview, or does judgment matter more here too?**
A: Like most senior-level topics, interviewers care more about whether you can *reason* about execution order, `this` bugs, and closures live on a whiteboard than whether you can recite the spec. Be ready to trace through a small snippet line-by-line — creation phase first, then execution phase, tracking the call stack and any queued micro/macrotasks — and explain *why* the output is what it is.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                 | Global Execution Context           | Function Execution Context                      |
|---                     |---                                  |---                                              |
| Created                | Once, when script starts           | Every time a function is invoked                |
| `this` (non-strict)    | Global object                      | Depends on call site (or lexical, if arrow fn)  |
| Variable Environment   | Global `var`/function declarations | Local `var`/function declarations, `arguments`  |
| Lexical Environment    | Top of the scope chain             | Points to outer (defining) lexical environment  |
| Popped off stack       | Only when program/tab ends         | When the function returns                       |
| Count at any time      | Exactly one                        | Zero to many (one per active/nested call)       |

---

**Tip for the interview:** At the 5 YOE level, interviewers usually skip "define hoisting" and go straight to tracing tricky snippets (loop closures, `this` in callbacks, async ordering) and asking you to explain the *output*, not just the term. Practice narrating: "creation phase happens first → then execution phase runs top-to-bottom → this call pushes a new context → this callback got queued as a micro/macrotask" out loud on a few classic snippets until it's automatic. Also have one real debugging story ready (a `this`-binding bug, a closure-in-a-loop bug, or a memory leak from an unremoved listener) — that's usually worth more than a textbook-perfect definition.
