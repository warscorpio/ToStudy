## Topic A: Destructuring

### Section A1: Fundamentals

**Q1. What is destructuring, and what structural invariant does it rely on?**

A: Destructuring is syntax that "unpacks" values from arrays or properties from objects into individual variables in a single binding declaration. The invariant: array destructuring matches by **position** (index 0, 1, 2…); object destructuring matches by **key name**. Missing positions or keys silently produce `undefined` (unless a default is supplied); extra positions or keys are silently ignored. Destructuring is purely syntactic — it compiles down to individual property lookups and there is no "magic" involved beyond that translation. The entire operation happens at assignment time: the right-hand-side expression is evaluated first (once), then the unpacking is applied to the result.

```js
// Array: position-based matching
const [a, b, c] = [10, 20, 30];         // a=10, b=20, c=30
const [x,  , z] = [10, 20, 30];         // x=10, z=30 (skip index 1 with comma)
const [p, q, r] = [1, 2];               // p=1, q=2, r=undefined

// Object: key-name-based matching
const { name, age } = { name: 'Ada', age: 36, role: 'dev' };
// name='Ada', age=36 — 'role' is silently ignored

// Invariant: order of declared variables doesn't affect object destructuring
const { age: a2, name: n2 } = { name: 'Ada', age: 36 };
// n2='Ada', a2=36 — same result regardless of declaration order
```

**Q2. How do default values in destructuring work, and what is the critical "undefined-only" trigger?**

A: Default values in destructuring are applied *only* when the extracted value is exactly `undefined` — not when it is `null`, `0`, `''`, `false`, or `NaN`. This surprises many developers who expect defaults to replace any "empty" value. The default expression is not evaluated at all if the extracted value is not `undefined` (lazy evaluation) — so `const { fn = expensiveCompute() } = obj` only calls `expensiveCompute()` if `obj.fn` is `undefined`. Default values work identically in both array and object destructuring.

```js
const { a = 1, b = 2, c = 3, d = 4 } = { a: null, b: 0, c: '', d: undefined };
// a = null    ← NOT 1. null ≠ undefined; default skipped
// b = 0       ← NOT 2. 0 ≠ undefined; default skipped
// c = ''      ← NOT 3. '' ≠ undefined; default skipped
// d = 4       ← YES. undefined → default applied

// Same rule in arrays:
const [x = 10, y = 20] = [null, undefined];
// x = null (not 10), y = 20 ✓

// Default expressions are lazily evaluated:
let sideEffect = 0;
const { val = (sideEffect++, 99) } = { val: 0 };
// sideEffect remains 0 — expression never ran (val was 0, not undefined)
```

**Q3. What is the rename (alias) syntax in object destructuring, and why is it frequently misread?**

A: Object destructuring uses `: newName` to rename a property as it's extracted: `const { originalKey: myVar } = obj`. This reads left-to-right as "take property `originalKey` from the object, bind it to variable `myVar`." The confusion: the colon looks like an assignment (`value: variable`), but it means the *opposite* — `originalKey` is the *source* (what's looked up in the object) and `myVar` is the *target* (what's created in local scope). Combining rename with a default: `const { a: myA = 5 } = obj` — source key is `a`, local name is `myA`, default is 5 if `obj.a` is `undefined`.

```js
const user = { firstName: 'Ada', lastName: 'Lovelace' };

// Rename:
const { firstName: first, lastName: last } = user;
// first = 'Ada', last = 'Lovelace'
// WRONG mental model: "first is the property, 'Ada' is the alias"
// RIGHT mental model: "firstName (source key) → first (variable name)"

// Rename + default:
const { role: userRole = 'viewer' } = user;
// userRole = 'viewer' (user.role is undefined → default applied)

// Common confusion — this is a SyntaxError:
// const { firstName } = user; firstName = 'changed'; // can't reassign const
// This is fine with let:
let { firstName: fn } = user;
fn = 'changed'; // OK — fn is a separate variable, user.firstName unchanged
```

**Q4. How does destructuring in function parameters work, and what default must be added for optional argument objects?**

A: Destructuring directly in parameter position unpacks the argument at call time, eliminating the need for `const name = options.name` lines inside the function body. The pattern `{ key = default }` in a parameter position reads as: extract `key` from the argument object, using `default` if `key` is `undefined`. The critical guard: `function f({ key } = {})` — the `= {}` at the end means the entire parameter defaults to an empty object if the caller passes nothing (or passes `undefined`). Without this, `f()` throws `TypeError: Cannot destructure property 'key' of undefined`.

```js
// Without destructuring:
function greet(options) {
  const name = options.name || 'World';
  const lang = options.lang || 'en';
  return `Hello, ${name}!`;
}

// With destructuring + defaults in params:
function greet({ name = 'World', lang = 'en', ...rest } = {}) {
  // name, lang, rest are immediately available
  // rest holds any extra passed properties
  return `Hello, ${name}!`;
}

greet({ name: 'Ada' });       // 'Hello, Ada!'
greet({ name: 'Ada', age: 5}); // rest = { age: 5 }
greet();                       // 'Hello, World!' — = {} kicks in
greet(undefined);              // 'Hello, World!' — also safe

// Without = {} at the end:
function unsafe({ name = 'World' }) { return name; }
unsafe();           // TypeError: Cannot destructure property 'name' of undefined
unsafe(undefined);  // same error
```

**Q5. What is nested destructuring, and what invariant must the shape satisfy?**

A: Nested destructuring unpacks deeply into a structure: `const { a: { b, c } } = obj` extracts `obj.a.b` into `b` and `obj.a.c` into `c`. The invariant: every level of the destructuring pattern must find a non-null, non-undefined value to unpack from — if `obj.a` is `null` or `undefined`, the inner destructuring `{ b, c }` throws a `TypeError`. Provide default values at each level to guard against missing intermediate nodes: `const { a: { b, c } = {} } = obj` — if `obj.a` is undefined, the inner pattern destructures from `{}` instead of throwing.

```js
const response = { data: { user: { name: 'Ada', role: 'admin' } } };

// Nested destructuring:
const { data: { user: { name, role } } } = response;
// name = 'Ada', role = 'admin'

// With defaults at each level:
const { data: { user: { name: n = 'Anonymous', role: r = 'viewer' } = {} } = {} } = response ?? {};

// Array nesting:
const [[x, y], [a, b]] = [[1, 2], [3, 4]];
// x=1, y=2, a=3, b=4

// DANGER: no default on intermediate level
const bad = { data: null };
const { data: { user: { name: n2 } } } = bad;
// TypeError: Cannot destructure property 'user' of null
// Fix: const { data: { user: { name: n2 } = {} } = {} } = bad;
```

**Q6. What is rest in destructuring, and how does it compare to simply accessing `obj` directly?**

A: Rest in destructuring (`const { a, b, ...rest } = obj`) creates a *new object* containing all enumerable own properties of `obj` *except* those already destructured. This is a shallow copy of the remaining properties. Contrast with just using `obj`: `obj` still includes `a` and `b`; `rest` does not. Rest must appear last in both object and array destructuring patterns. In arrays, `const [first, ...remaining] = arr` makes `remaining` a new array with all elements after `first`. Rest in destructuring is the most natural way to implement "pick and omit" patterns — extract the properties you need while collecting everything else for forwarding.

```js
const { type, id, ...payload } = event;
// type and id are extracted individually
// payload is a new object with everything else — type and id excluded

// Use case: forwarding props in React (omit component-specific props)
function Button({ onClick, disabled, children, ...htmlProps }) {
  return <button onClick={onClick} disabled={disabled} {...htmlProps}>{children}</button>;
  // htmlProps contains only the remaining DOM-valid attributes
}

// Array rest:
const [first, second, ...rest] = [1, 2, 3, 4, 5];
// first=1, second=2, rest=[3, 4, 5]

// Rest gives a NEW array/object — not a view of the original:
const original = { a: 1, b: 2, c: 3 };
const { a, ...others } = original;
others.b = 99;
console.log(original.b); // Still 2 — others is a separate (shallow) copy
```

### Section A2: Advanced Patterns

**Q7. What are computed property keys in destructuring, and when are they needed?**

A: Computed property keys (`const { [expr]: localName } = obj`) allow the property name to be a runtime expression rather than a literal identifier. This is necessary when the key is stored in a variable, computed from a function, or is not a valid JS identifier. The local variable name must always be explicitly provided with `: localName` when using computed keys — unlike regular destructuring where `const { name } = obj` implicitly creates a `name` variable, computed keys have no implicit binding.

```js
const key = 'name';
const { [key]: value } = { name: 'Ada' };
// value = 'Ada'

// Dynamic key based on condition:
const field = isAdmin ? 'adminToken' : 'userToken';
const { [field]: token } = auth;

// In a function:
function extract(obj, propName) {
  const { [propName]: extracted = 'default' } = obj;
  return extracted;
}
extract({ color: 'red' }, 'color'); // 'red'
extract({}, 'color');               // 'default'
```

**Q8. How does destructuring interact with iterables beyond arrays?**

A: Array destructuring works on any *iterable*, not just arrays — `Set`, `Map` (its entries), generator results, `String`, custom iterables with `[Symbol.iterator]`. Object destructuring works only on objects (non-null, non-undefined). Destructuring from a `Map` destructures the iterator's yielded items, not the map's key-value pairs as an object.

```js
// String (iterable):
const [first, , third] = 'hello'; // first='h', third='l'

// Set:
const [a, b] = new Set([1, 2, 3]); // a=1, b=2

// Map: iterates as [key, value] pairs
const map = new Map([['x', 1], ['y', 2]]);
const [[k1, v1], [k2, v2]] = map; // k1='x', v1=1, k2='y', v2=2

// Generator:
function* gen() { yield 1; yield 2; yield 3; }
const [p, q] = gen(); // p=1, q=2 (generator only advances to what's needed)

// NOT iterable — object destructuring ONLY for objects:
const { length } = 'hello'; // length = 5 (string IS an object with length)
```

**Q9. What are the three most commonly confused behaviors when destructuring nested undefined paths?**

A: (1) **Null vs undefined**: `const { a = 1 } = { a: null }` gives `a = null`, not 1 — null does not trigger defaults. (2) **Missing intermediate key**: `const { a: { b } } = { a: undefined }` throws — need `{ a: { b } = {} }` as guard. (3) **Destructuring `null` directly**: `const { a } = null` always throws TypeError — null and undefined cannot be destructured at all; only objects and iterables can. Before destructuring any potentially-null value, use `?? {}` or optional chaining.

```js
// 1. null ≠ undefined for defaults
const x = null;
const { x: val = 5 } = { x };     // val = null (not 5!)

// 2. Missing intermediate throws without default
const data = { user: undefined };
const { user: { name } } = data;   // TypeError
const { user: { name } = {} } = data; // name = undefined ✓

// 3. Can't destructure null/undefined at top level
const obj = null;
const { a } = obj;                  // TypeError: Cannot destructure property 'a' of null
const { a: safeA } = obj ?? {};     // safeA = undefined ✓
```

## Topic B: Spread / Rest Operators

### Section B1: Spread

**Q10. What does the spread operator do in each of its three syntactic contexts?**

A: Spread (`...`) appears in three positions with slightly different semantics: (1) **Array literals**: `[...arr1, ...arr2]` — concatenates iterables into a new array, equivalent to `arr1.concat(arr2)` but more composable; (2) **Object literals**: `{ ...obj1, ...obj2 }` — merges own enumerable properties of each object into a new object; (3) **Function call arguments**: `fn(...args)` — passes array elements as individual positional arguments, equivalent to `fn.apply(null, args)`. In all three cases, spread "unpacks" a collection into individual items. Spread in object literals is not standard iteration — it uses the object's own enumerable properties, not `[Symbol.iterator]`.

```js
// 1. Array literal — concatenation, flattening:
const a = [1, 2], b = [3, 4];
const merged = [...a, ...b];             // [1, 2, 3, 4]
const withExtra = [0, ...a, 2.5, ...b]; // [0, 1, 2, 2.5, 3, 4]

// 2. Object literal — property merging:
const defaults = { color: 'red', size: 'M' };
const overrides = { size: 'L', weight: 100 };
const config = { ...defaults, ...overrides }; // { color:'red', size:'L', weight:100 }

// 3. Function call — spread as arguments:
const nums = [1, 5, 3, 2, 4];
Math.max(...nums);     // 5 — equivalent to Math.max(1,5,3,2,4)
Math.max(nums);        // NaN — passes the ARRAY as one argument

// Spread works on any iterable in array context:
const str = 'hello';
const chars = [...str]; // ['h','e','l','l','o']
```

**Q11. What is the shallow copy behavior of object spread, and what does "shallow" mean precisely?**

A: Object spread (`{ ...obj }`) creates a **new** top-level object, but all property *values* that are objects, arrays, or functions are copied as references — not new copies. "Shallow" means exactly one level deep: primitive values (strings, numbers, booleans) are safely copied by value; nested objects/arrays still point to the same reference in memory as the original. This means mutating a nested property in the copy also mutates the original, since they share the same nested object.

```js
const original = { count: 0, tags: ['a', 'b'], meta: { version: 1 } };
const copy = { ...original };

// Safe: top-level primitive — different value
copy.count = 99;
console.log(original.count); // 0 ✓ (primitive was copied by value)

// UNSAFE: nested reference is shared
copy.tags.push('c');
console.log(original.tags);  // ['a','b','c'] ✗ (same array reference!)

copy.meta.version = 2;
console.log(original.meta.version); // 2 ✗ (same object reference!)

// Deep copy alternatives:
const deep1 = structuredClone(original);           // modern, handles Date/Map/Set
const deep2 = JSON.parse(JSON.stringify(original)); // lossy: drops functions/undefined/Date
```

**Q12. What is the key precedence rule when spreading objects, and how does it enable the "defaults then overrides" pattern?**

A: In an object literal, **later keys overwrite earlier keys** of the same name. This gives spread a clear precedence rule: whatever appears rightmost wins. The pattern `{ ...defaults, ...userConfig }` means userConfig overrides defaults — exactly what's needed for configuration merging. The reverse `{ ...userConfig, ...defaults }` would mean defaults overwrite user config — rarely intended. Inline key-value pairs follow the same rule: `{ ...obj, key: 'override' }` always uses `'override'` for `key` regardless of what `obj.key` was; `{ key: 'override', ...obj }` can have `obj.key` silently overwrite the intended override.

```js
const defaults = { color: 'red', size: 'M', visible: true };
const user     = { size: 'XL', fontWeight: 'bold' };

// User overrides defaults:
const config = { ...defaults, ...user };
// { color:'red', size:'XL', visible:true, fontWeight:'bold' }

// Inline override (always wins because it's last):
const withCustom = { ...config, size: 'S' };
// { color:'red', size:'S', visible:true, fontWeight:'bold' }

// TRAP: inline before spread — can be overwritten:
const unsafe = { size: 'S', ...config };
// size becomes 'XL' from config! The spread came AFTER the inline 'S'
```

### Section B2: Rest

**Q13. What is the difference between the rest parameter and the `arguments` object?**

A: Rest (`...params`) and `arguments` both capture function arguments, but they differ in four critical ways: (1) **Scope**: `arguments` is not available in arrow functions — rest works everywhere; (2) **Type**: `arguments` is array-*like* (has `.length` and indices but lacks `.map`, `.filter`, etc.) — rest is a genuine `Array`; (3) **Scope**: `arguments` captures *all* arguments; rest captures only the arguments *not named before it*; (4) **Name**: `arguments` is fixed — rest can be named anything meaningful. In modern code, always prefer rest over `arguments`. Arrow functions must use rest to capture their own arguments (accessing `arguments` inside an arrow function refers to the outer function's arguments).

```js
// arguments — old style, avoid:
function oldSum() {
  return Array.from(arguments).reduce((s, n) => s + n, 0);
  // Must convert to array; verbose; not available in arrow functions
}

// Rest — modern:
const sum = (...nums) => nums.reduce((s, n) => s + n, 0);
// nums is already a real Array; works in arrow functions

// Rest captures only the "extra" arguments after named params:
function log(level, ...messages) {
  console[level](messages.join(' '));
}
log('warn', 'disk', 'is', 'full'); // level='warn', messages=['disk','is','full']

// Arrow function — arguments refers to OUTER function's arguments:
function outer() {
  const inner = () => console.log(arguments); // outer's arguments, not inner's
}
function outerWithRest() {
  const inner = (...args) => console.log(args); // inner's own arguments via rest
}
```

**Q14. Where must rest appear, and what are the three positions where it is valid?**

A: Rest must always appear **last** — placing anything after `...rest` is a SyntaxError. The three valid positions: (1) **Function parameters**: `function f(a, b, ...rest)` — rest collects all arguments after `a` and `b`; (2) **Array destructuring**: `const [first, ...tail] = arr` — tail collects remaining elements; (3) **Object destructuring**: `const { a, b, ...others } = obj` — others collects remaining own-enumerable properties. In all positions, rest creates a new array (positions 1 and 2) or new object (position 3) — it never returns a reference to the original container.

```js
// ✓ Valid positions — rest is last:
function f(a, b, ...rest) {}
const [first, ...tail] = [1, 2, 3];
const { x, ...rest2 } = { x: 1, y: 2, z: 3 };

// ✗ SyntaxErrors — rest not last:
// function f(...rest, last) {}          // SyntaxError
// const [...init, last] = [1, 2, 3];   // SyntaxError
// const { ...rest, x } = obj;          // SyntaxError

// Rest creates a NEW collection (not a view or reference):
const arr = [1, 2, 3, 4];
const [, ...copy] = arr;
copy.push(99);
console.log(arr); // [1, 2, 3, 4] — arr unchanged ✓
```

**Q15. What is the pack/unpack duality between rest and spread?**

A: Rest **packs** (many → one): it collects multiple individual values into a single array or object. Spread **unpacks** (one → many): it expands a single collection into individual items. They are inverse operations — rest is the mirror image of spread. This duality is most visible at function boundaries: rest packs caller-supplied arguments into an array at the function definition; spread unpacks that array back into arguments at a call site. The terms themselves hint at this: "rest" = collect the rest into one thing; "spread" = spread one thing into many.

```js
// REST (packs) at definition:    SPREAD (unpacks) at call site:
function f(...args)            { return args; }
const result = f(...[1,2,3]);  // same as f(1, 2, 3)
// args = [1, 2, 3] (packed by rest)
// [1,2,3] was unpacked by spread to become 1, 2, 3 individually

// Array creation and consumption mirror:
const arr = [1, 2, 3];
const copy = [...arr];          // unpack arr into new array → pack back up
const [a, b, ...rest] = copy;  // unpack copy → a=1, b=2, rest=[3] (repacked)

// Object equivalent:
const obj = { a: 1, b: 2, c: 3 };
const { a: taken, ...leftover } = { ...obj, d: 4 };
// spread unpacks obj + adds d; rest packs the non-'a' properties into leftover
```

## Topic C: Template Literals

**Q16. What are template literals, and what three problems do they solve over string concatenation?**

A: Template literals (backtick strings with `${expression}` interpolation) solve: (1) **Readability** — `Hello, ${name}` is immediately scannable vs `'Hello, ' + name`; (2) **Multiline strings** — newlines inside backticks are literal, eliminating `\n` or string array joins; (3) **Expression embedding** — any JavaScript expression (function calls, ternaries, arithmetic, nested templates) can appear inside `${}`, not just variable references. The expression is evaluated and coerced to a string via `.toString()`. Template literals evaluate eagerly at the point of the backtick — there's no lazy evaluation or reuse. Nesting backticks requires escaping: `\`` or switching to tagged template syntax.

```js
// Before ES6 — multiple concatenations:
const greeting = 'Hello, ' + user.name + '! You have ' + msgs.length + ' messages.';

// Template literal:
const greeting = `Hello, ${user.name}! You have ${msgs.length} messages.`;

// Multiline (whitespace is significant!):
const html = `
  <div class="card">
    <h1>${title}</h1>
    <p>${description}</p>
  </div>
`;

// Any expression in ${}:
const result = `${a > b ? 'bigger' : 'smaller'}, ${fn(x).toFixed(2)}, ${arr.join(', ')}`;

// Nested template:
const rows = items.map(item => `<li class="${item.active ? 'active' : ''}">${item.name}</li>`);
const list = `<ul>${rows.join('')}</ul>`;
```

**Q17. What are tagged templates, what is the tag function's signature, and what are they used for?**

A: A tagged template calls a function with the static string parts and evaluated dynamic values as separate arguments. The tag function signature: `function tag(strings, ...values)` — `strings` is a frozen array of the literal text fragments (with a `.raw` property containing the unescaped versions); `values` contains the evaluated interpolated expressions in order. The invariant: `strings.length === values.length + 1` always, because expressions always appear *between* string parts (there's always a potentially-empty string before and after each expression). Tagged templates are the mechanism behind styled-components CSS interpolation, internationalization/l10n libraries, SQL query parameterization, and HTML sanitization.

```js
function highlight(strings, ...values) {
  return strings.reduce((result, str, i) =>
    result + str + (values[i] !== undefined ? `<mark>${values[i]}</mark>` : ''),
    ''
  );
}

const name = 'Ada', score = 99;
highlight`Hello, ${name}! Score: ${score}.`;
// strings = ['Hello, ', '! Score: ', '.']  (length 3)
// values  = ['Ada', 99]                    (length 2)
// → 'Hello, <mark>Ada</mark>! Score: <mark>99</mark>.'

// strings.raw — unescaped backslashes:
function raw(strings) { return strings.raw[0]; }
raw`Line1\nLine2`;   // 'Line1\\nLine2' (the \n is NOT a newline)
String.raw`\n\t`;    // '\\n\\t' (built-in tag for raw strings)

// Real-world: SQL parameterization (see Problem 4 below)
// Real-world: styled-components
const Button = styled.button`
  background: ${props => props.primary ? 'blue' : 'white'};
  padding: 0.5em 1em;
`;
```

**Q18. What are the three most common template literal pitfalls?**

A: (1) **Whitespace is literal**: the indentation inside a multiline template is part of the string — a `<div>` indented 4 spaces produces 4 leading spaces in the output. Use `.trim()` or adjust indentation to the start of lines. (2) **Expression coercion**: `${{}}` calls `.toString()` on the object, producing `'[object Object]'` — always stringify intentionally with `JSON.stringify()` or by accessing specific properties. (3) **Tagged template misconception**: the tag function receives the unprocessed interpolated values — it does NOT automatically produce a string. The tag must explicitly build and return a string (or any other value — tagged templates can return objects, arrays, or DOM elements).

```js
// Pitfall 1: Unintended whitespace
function getHtml() {
  return `
    <div>           ← 4 spaces of indentation are IN the string
      <p>Hello</p>
    </div>
  `;  // also includes a trailing newline before closing backtick
}

// Pitfall 2: Object coercion
const obj = { x: 1 };
`Value: ${obj}`;    // 'Value: [object Object]' ← almost never intended
`Value: ${JSON.stringify(obj)}`; // 'Value: {"x":1}' ← explicit

// Pitfall 3: Tagged template must return a value
function broken(strings, ...vals) {
  // Does not return anything
}
const result = broken`hello ${name}`; // result = undefined !
```

## Topic D: Optional Chaining & Nullish Coalescing

### Section D1: Optional Chaining

**Q19. What is optional chaining, what does `?.` replace, and what exactly does it check?**

A: Optional chaining (`?.`) short-circuits to `undefined` when the left-hand side is `null` or `undefined`, rather than throwing a `TypeError`. It replaces nested null-guard chains like `a && a.b && a.b.c`. The critical precision: `?.` checks for **both** `null` **and** `undefined` (it uses abstract equality `== null` internally, which catches both), but nothing else — `0`, `''`, `false`, and `NaN` are not treated as absent and will be accessed normally. Optional chaining does NOT catch runtime errors inside the accessed property or method — only the case where the receiver itself is null or undefined.

```js
// Before: verbose null-guards
const street = user && user.address && user.address.street;
// After: optional chaining
const street = user?.address?.street;

// ?? null check precision:
const obj = { a: 0 };
obj?.a;        // 0 ✓ — a exists, return its value (even if 0)
obj?.b;        // undefined — b doesn't exist
null?.a;       // undefined — null short-circuits
undefined?.a;  // undefined — undefined short-circuits
false?.a;      // TypeError — false IS accessed (not null/undefined)
// ↑ This is different from: (false && false.a) which returns false

// Does NOT catch errors inside the property:
const arr = null;
arr?.[someThrowingFn()]; // undefined — fn NOT called (left side was null)
const obj2 = { get prop() { throw new Error(); } };
obj2?.prop; // throws! obj2 is not null; accessing .prop throws
```

**Q20. What are the four syntactic forms of optional chaining, and when is each used?**

A: (1) **Property access**: `obj?.prop` or `obj?.['prop']` — accesses property if obj is not null/undefined; (2) **Method call**: `obj?.method(args)` — calls method if obj is not null/undefined; (3) **Function call**: `fn?.()` — calls fn only if fn itself is not null/undefined (useful for optional callbacks); (4) **Array/computed access**: `arr?.[index]` — accesses element if arr is not null/undefined. All four produce `undefined` on short-circuit. Note that `?.` only guards the *immediately preceding* receiver — in `a?.b.c`, if `a?.b` succeeds but `b.c` would access `c` on undefined, there's no protection for that part; you need `a?.b?.c`.

```js
// 1. Property access:
user?.profile?.avatar?.url       // chains multiple optional accesses

// 2. Method call:
element?.addEventListener('click', handler)  // safe even if element is null

// 3. Function call — optional callback:
function process(data, onComplete) {
  // ... do work ...
  onComplete?.(); // calls onComplete if it was provided
}

// 4. Computed / array:
const users = null;
users?.[0];           // undefined
users?.[0]?.name;     // undefined

// Chaining with ?.method:
response?.json?.();   // calls .json() only if response is not null AND .json exists
// ↑ Two optional guards: response might be null, and .json might not exist

// Common mistake — needs BOTH ?.
const a = { b: null };
a?.b.c;   // TypeError: Cannot read property 'c' of null (a.b was null, not guarded)
a?.b?.c;  // undefined ✓
```

**Q21. What is optional chaining's short-circuit behavior — what is and isn't evaluated?**

A: When `?.` short-circuits (left side is null/undefined), the **entire right-hand portion is not evaluated at all** — including any argument expressions, computed property expressions, or function calls that appear to the right. This is important for understanding side effects: `user?.save()` will not call `save()` if `user` is null. `config?.[computeKey()]` will not call `computeKey()` if `config` is null. The short-circuit extends to the end of the optional chain expression — it doesn't stop at the next `.`.

```js
let callCount = 0;
function sideEffect() { callCount++; return 'key'; }

const obj = null;
obj?.[sideEffect()];    // sideEffect() is NOT called. callCount = 0
obj?.method(sideEffect()); // sideEffect() is NOT called
console.log(callCount); // 0 — entire right side was skipped

// The short-circuit ends at the EXPRESSION boundary, not the chain:
const user = null;
user?.save() ?? doSomething(); // user?.save() = undefined; doSomething() IS called
// The ?? is outside the optional chain expression — it evaluates normally

// Method calls on results of optional chaining:
user?.getName().toLowerCase(); // If user is null → undefined.toLowerCase() → TypeError!
user?.getName()?.toLowerCase(); // ✓ both parts protected
```

### Section D2: Nullish Coalescing

**Q22. What is the precise difference between `??` and `||`, and why does it matter for valid falsy values?**

A: `||` (logical OR) returns the right operand when the left is **any falsy value**: `false`, `0`, `''`, `null`, `undefined`, `NaN`. `??` (nullish coalescing) returns the right operand only when the left is specifically **`null` or `undefined`** — nothing else. This distinction is critical when `0`, `''`, or `false` are valid, meaningful values that should NOT be replaced by a default. The mnemonic: `??` means "use this default only if the value is truly absent (null or undefined)"; `||` means "use this default if the value is falsy (which includes 0, '', false)."

```js
const count = 0;
const name  = '';
const active = false;

// || treats valid values as "missing":
count  || 10;    // 10  ← WRONG if count=0 is valid
name   || 'n/a'; // 'n/a' ← WRONG if empty string is valid
active || true;  // true  ← WRONG if false is a valid "inactive" state

// ?? preserves valid falsy values:
count  ?? 10;    // 0   ✓
name   ?? 'n/a'; // ''  ✓
active ?? true;  // false ✓

// Both behave the same for null/undefined:
null      || 'default'; // 'default'
null      ?? 'default'; // 'default'
undefined || 'default'; // 'default'
undefined ?? 'default'; // 'default'

// Rule of thumb:
// Use ?? when 0, false, or '' are valid values (common with configs, counts, settings)
// Use || when any falsy value should be replaced (boolean flags, existence checks)
```

**Q23. What are the logical assignment operators (`??=`, `||=`, `&&=`), and when are they useful?**

A: Logical assignment operators combine a logical operation with assignment, and critically they **short-circuit** — the right side is only evaluated if the assignment actually happens. `a ??= b` assigns `b` to `a` only if `a` is `null` or `undefined` (lazy initialization). `a ||= b` assigns `b` to `a` only if `a` is falsy (ensure truthy). `a &&= b` assigns `b` to `a` only if `a` is truthy (update only if present). These differ from `a = a ?? b` in that the `=` doesn't execute at all if the condition isn't met — relevant for properties with setters.

```js
// ??= : initialize if absent
let cache = {};
cache.data ??= fetchExpensiveData(); // fetch ONLY if cache.data is null/undefined
// If cache.data already has a value (even 0 or false), fetchExpensiveData() is NOT called

// ||= : ensure truthy
function ensure(config) {
  config.timeout ||= 5000;  // set timeout only if falsy (0, undefined, null, '')
  config.name    ||= 'default';
  return config;
}

// &&= : update only if currently set
let user = { name: 'Ada', score: 99 };
user.score &&= user.score * 2;  // double score only if score is truthy (not 0, null, etc.)

// Short-circuit matters with setters:
class Store {
  set value(v) { console.log('setter called'); this._value = v; }
  get value()  { return this._value; }
}
const store = new Store();
store.value = 5;
store.value ??= 10; // setter NOT called — value is 5, not null/undefined
store.value  = null;
store.value ??= 10; // setter IS called — value was null
```

**Q24. How do you combine `?.` and `??` for robust nested property access with meaningful defaults?**

A: The canonical combination is `obj?.deep?.property ?? 'default'` — `?.` handles safe navigation (returns `undefined` at any null/undefined step without throwing), and `??` provides the fallback when navigation produces `undefined`. This cleanly separates two concerns: "can I navigate there?" (`?.`) from "what if I can't?" (`??`). The order matters: `?.` must come before `??` in the chain. You can also combine them with destructuring: extract the nested value with safe navigation and provide defaults at the destructuring level.

```js
// Pattern: safe navigation + meaningful default
const city = user?.address?.city ?? 'Unknown';
const port = config?.server?.port ?? 3000;
const count = response?.data?.users?.length ?? 0;

// Chained with method call:
const initials = user?.name?.split(' ')?.map(w => w[0])?.join('') ?? '??';

// In object construction:
const stats = {
  total:   data?.totals?.all  ?? 0,
  active:  data?.totals?.active ?? 0,
  ratio:   data?.meta?.ratio?.toFixed(2) ?? 'N/A',
};

// With destructuring:
const { name = 'Anonymous', role = 'viewer' } = user ?? {};
// If user is null/undefined, destructure from {}; defaults fill in

// Layered defaults: chain ?? for multiple fallback sources
const timeout = config?.timeout ?? userPrefs?.timeout ?? DEFAULT_TIMEOUT;
```

**Q25. State the invariant for `?.` and `??` in one sentence each, and state when to prefer each operator pair.**

A:
- **Optional chaining (`?.`) invariant**: the expression evaluates to `undefined` if and only if any receiver along the `?.` chain is `null` or `undefined`; all other values (including `0`, `false`, `''`) are accessed normally and the expression proceeds.
- **Nullish coalescing (`??`) invariant**: returns the right operand if and only if the left operand is `null` or `undefined`; all other left-operand values — including every valid falsy value — are returned as-is.
- **Prefer `?.` over** `&&`-chained guards when navigating multiple levels of a potentially-absent object structure.
- **Prefer `??` over `||`** when `0`, `false`, or `''` are valid values that should be preserved, not replaced by a fallback.
- **Prefer `??=` over `||=`** when initializing properties that might validly be `0` or `false` (e.g., counts, boolean flags, empty strings).

## Problem 3 — Immutable Array Operations with Spread

### Problem

Implement three pure (non-mutating) array utility functions: `insertAt(arr, index, value)`, `removeAt(arr, index)`, and `updateAt(arr, index, value)`. Each must return a new array and leave the original unchanged.

```js
insertAt([1,2,3,4], 2, 99)   → [1,2,99,3,4]
removeAt([1,2,3,4], 1)        → [1,3,4]
updateAt([1,2,3,4], 2, 99)   → [1,2,99,4]
```

### Pattern Recognition
Array spread for composing new arrays from slices; slice + spread for non-mutating operations that would otherwise require splice. This is the foundational pattern for React/Redux immutable state updates.

### Key Insight
`Array.prototype.splice` is a common trap — it mutates in place and returns removed elements (not the new array). The spread-based approach composes the result from parts without touching the original. `arr.slice(0, i)` is the elements before index i; `arr.slice(i)` is from index i onward; these two can be spread with new content in between.

### Solution

```js
// Insert: [before index] + [new value] + [from index onward]
const insertAt = (arr, index, value) => [
  ...arr.slice(0, index),
  value,
  ...arr.slice(index),
];

// Remove: [before index] + [after index, skipping the removed element]
const removeAt = (arr, index) => [
  ...arr.slice(0, index),
  ...arr.slice(index + 1),
];

// Update: [before index] + [new value] + [after index, skipping old value]
const updateAt = (arr, index, value) => [
  ...arr.slice(0, index),
  value,
  ...arr.slice(index + 1),
];

// Equivalent using spread of the whole array with targeted override:
const updateAtAlt = (arr, index, value) =>
  arr.map((item, i) => i === index ? value : item);

// Immutable object update (for state management):
const updateNestedArr = (state, id, changes) => ({
  ...state,
  users: state.users.map(user =>
    user.id === id ? { ...user, ...changes } : user
  ),
});
```

### Trace

```js

// insertAt([1,2,3,4], 2, 99):
// slice(0, 2) = [1, 2]
// value = 99
// slice(2)    = [3, 4]
// result: [...[1,2], 99, ...[3,4]] = [1,2,99,3,4] ✓
// arr unchanged: [1,2,3,4] ✓

// removeAt([1,2,3,4], 1):
// slice(0, 1) = [1]
// slice(2)    = [3, 4]
// result: [...[1], ...[3,4]] = [1,3,4] ✓

// updateAt([1,2,3,4], 2, 99):
// slice(0, 2) = [1, 2]
// value = 99
// slice(3)    = [4]
// result: [...[1,2], 99, ...[4]] = [1,2,99,4] ✓

// Nested update trace:

updateNestedArr(state, 1, { name: 'Alan' })
// → { count:2, users:[{id:1,name:'Alan'}, {id:2,name:'Bob'}] }
// state.users still [{id:1,name:'Ada'}, ...] ✓
```

### Edge Cases
- `insertAt(arr, 0, x)` — `slice(0,0) = []`, so `[x, ...arr]`. Inserts at front.
- `insertAt(arr, arr.length, x)` — `slice(arr.length) = []`, so `[...arr, x]`. Appends to end.
- `removeAt(arr, arr.length - 1)` — removes last element. `slice(arr.length) = []`.
- Objects inside array: spread creates a shallow copy of the array — the objects themselves are still the same references. Use `{ ...user, ...changes }` to also immutably update the objects.

### Follow-up Questions
- "What about `splice` for performance on very large arrays?" — `slice` + spread creates two intermediate arrays; for large arrays, consider structural sharing data structures (Immutable.js). In practice, spread is fine up to tens of thousands of elements.
- "Multi-element insert?" — `insertAt(arr, i, ...values)` with rest: `[...arr.slice(0,i), ...values, ...arr.slice(i)]`.

## Problem 4 — Tagged Template: XSS-Safe HTML Builder

### Problem

Implement an `html` tagged template function that escapes HTML entities in interpolated values, making it safe to render user-provided strings without XSS risk. Fixed static parts of the template should NOT be escaped.

```js
const username = '<script>alert("xss")</script>';
const safeOutput = html`<div class="user">Hello, ${username}!</div>`;
// → '<div class="user">Hello, &lt;script&gt;alert(&quot;xss&quot;)&lt;/script&gt;!</div>'
//    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ raw static part ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                                                       ^^^^^^^^^^^^^^^^ escaped dynamic value
```

### Pattern Recognition
Tagged template literal — the tag function receives static string parts and dynamic interpolated values separately, allowing different treatment of each.

### Key Insight
Tagged templates give us exactly the information needed for safe HTML: the *static* parts (written by the developer, trusted) and the *dynamic* parts (may contain user input, untrusted). By escaping only the dynamic values and interleaving them with the raw static parts, we achieve security without losing readability. The invariant `strings.length === values.length + 1` means we can zip them together with `strings[i] + escape(values[i])`.

### Solution

```js
function escapeHtml(str) {
  // Replace HTML special characters with their entity equivalents
  return String(str)
    .replace(/&/g, '&amp;')   // must be first (to avoid double-escaping)
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}

function html(strings, ...values) {
  // strings: ['<div class="user">Hello, ', '!</div>']  (static, trusted)
  // values:  ['<script>alert("xss")</script>']         (dynamic, escape these)

  return strings.reduce((result, str, i) => {
    const value = values[i];
    // str = static part (safe, append as-is)
    // value = dynamic interpolation (escape before appending)
    return result + str + (value !== undefined ? escapeHtml(value) : '');
  }, '');
}

// Usage:
const username = '<script>alert("xss")</script>';
const count = 42;
const output = html`<div>Hello ${username}, you have ${count} messages.</div>`;
// → '<div>Hello &lt;script&gt;alert(&quot;xss&quot;)&lt;/script&gt;, you have 42 messages.</div>'

// Mark already-safe values to skip escaping (trusted HTML):
function safeHtml(str) { return { __safe: true, value: str }; }
function htmlWithTrust(strings, ...values) {
  return strings.reduce((result, str, i) => {
    const val = values[i];
    const escaped = val?.__safe ? val.value : (val !== undefined ? escapeHtml(val) : '');
    return result + str + escaped;
  }, '');
}
const icon = safeHtml('<svg>...</svg>');
htmlWithTrust`<button>${icon} Click ${username}</button>`;
```

// strings = ['<div>Hello ', '!</div>']   ← 2 elements
// values  = ['<script>alert("xss")</script>']  ← 1 element
// strings.length (2) = values.length (1) + 1 ✓

// i=0: result='' + strings[0]='<div>Hello ' + escapeHtml(values[0])

//            = '<div>Hello &lt;script&gt;alert(&quot;xss&quot;)&lt;/script&gt;'

## Problem 5 — Configuration Cascade with `??` and Spread

### Problem

Implement a `resolveConfig(env, userConfig, cliFlags)` function that merges three sources of configuration with correct precedence: CLI flags override user config, which overrides env defaults. Values from any source that are `null` or explicitly set to `false` or `0` must be preserved — only absent (`undefined`) values should fall through to the next source.

```js
const defaults  = { port: 3000, debug: false, timeout: 5000, workers: 4 };
const userConf  = { port: 8080, debug: false, timeout: null };
const cliFlags  = { port: undefined, debug: true, workers: 0 };

resolveConfig(defaults, userConf, cliFlags)
→ { port: 8080, debug: true, timeout: null, workers: 0 }
// port:    8080 (user overrides env; cli is undefined → falls back)
// debug:   true (cli overrides user's false)
// timeout: null (user explicitly set null — preserved, not fallen through to 5000)
// workers: 0   (cli sets 0 — preserved, not fallen through to 4)
```

### Pattern Recognition
`??` per-property rather than whole-object spread for cascade; the difference between "key present with value `undefined`" vs "key absent" for determining which source wins; spread for merging while respecting the precedence order.

### Key Insight
Plain object spread `{ ...defaults, ...user, ...cli }` doesn't work here — spread copies ALL keys including those with `undefined` values, and `undefined` from CLI would incorrectly override the user's real value. We need per-property nullish coalescing: `cli.port ?? user.port ?? defaults.port`. For a full cascade, iterate over the union of all keys and apply `??` at each level.

### Solution

```js
function resolveConfig(defaults, userConfig, cliFlags) {
  // Collect all possible keys from all sources
  const allKeys = new Set([
    ...Object.keys(defaults),
    ...Object.keys(userConfig),
    ...Object.keys(cliFlags),
  ]);

  const result = {};
  for (const key of allKeys) {
    // Per-key cascade: cli wins over user wins over defaults
    // ?? ensures undefined is the only "absent" signal, not null/0/false
    result[key] = cliFlags[key] !== undefined
      ? cliFlags[key]
      : userConfig[key] !== undefined
        ? userConfig[key]
        : defaults[key];
  }
  return result;
}

// More concise with reduce:
const resolveConfigV2 = (defaults, userConfig, cliFlags) =>

      [key]: [cliFlags, userConfig, defaults].find(src => key in src && src[key] !== undefined)?.[key]
    }), {});

// Why NOT this: { ...defaults, ...userConfig, ...cliFlags }
// → port would be undefined (from cliFlags) overwriting 8080 (from userConfig)
// → workers would be 0 ✓ but debug from cliFlags.debug=true overwrites userConfig.debug=false
//   → actually that's correct in this case, but "port: undefined" in cliFlags overwrites 8080 ✗
```

### Trace

```js
resolveConfig(
  { port: 3000, debug: false, timeout: 5000, workers: 4 },
  { port: 8080, debug: false, timeout: null },
  { port: undefined, debug: true, workers: 0 }
)

// allKeys = { port, debug, timeout, workers }

// key = 'port':
//   cliFlags.port = undefined → skip
//   userConfig.port = 8080 (not undefined) → result.port = 8080 ✓

// key = 'debug':
//   cliFlags.debug = true (not undefined) → result.debug = true ✓

// key = 'timeout':
//   cliFlags.timeout = undefined (key absent) → skip
//   userConfig.timeout = null (NOT undefined, explicitly set) → result.timeout = null ✓
//   (does NOT fall through to defaults.timeout = 5000)

// key = 'workers':
//   cliFlags.workers = 0 (not undefined) → result.workers = 0 ✓
//   (0 is preserved — || would have fallen through to 4!)

// → { port: 8080, debug: true, timeout: null, workers: 0 } ✓
```

### Edge Cases
- A key in `cliFlags` with value `undefined` is treated as "not set" (use the next source). If you need to distinguish "explicitly undefined" from "not present", check `'key' in obj` instead of `obj.key !== undefined`.
- `false` in user config: `false !== undefined` → preserved (correct — user explicitly turned something off).

### Follow-up Questions
- "How would you deep merge nested config objects?" — For nested objects, recurse: `typeof src[key] === 'object' ? resolveConfig(def[key] ?? {}, usr[key] ?? {}, cli[key] ?? {}) : ...`.
- "Difference between `key in obj` and `obj[key] !== undefined`?" — `'a' in { a: undefined }` is `true`; `{ a: undefined }.a !== undefined` is `false`. Use `in` when you need to detect explicit presence of a key even with `undefined` value.

## Problem 6 — Swap, Extract, and Reshape with Destructuring

### Problem

Solve three classic JavaScript tasks using only destructuring syntax: (1) swap two variables without a temp; (2) extract the first and last elements of an array while collecting the middle; (3) reshape a flat object into a nested one.

```js
// 1. Swap:
let a = 1, b = 2;
// → a = 2, b = 1

// 2. Extract first/middle/last:
const arr = [10, 20, 30, 40, 50];
// → first=10, last=50, middle=[20,30,40]

// 3. Reshape:
const flat = { firstName: 'Ada', lastName: 'Lovelace', age: 36, city: 'London' };
// → { name: { first: 'Ada', last: 'Lovelace' }, age: 36, location: { city: 'London' } }
```

### Pattern Recognition
Array destructuring for swap (rhs is evaluated first as a complete tuple); rest for extracting middle elements; object destructuring with rename for reshape.

### Key Insight
For the swap: the right-hand side `[b, a]` is fully evaluated as a NEW array `[2, 1]` *before* any assignment happens — this is why the swap works without a temp variable. For extract-first-last: rest only goes at the end, so you can't directly capture the last element alongside rest. Work around with `slice(-1)` or a two-step approach. For reshape: use destructuring with rename to extract fields and spread them into the new nested structure.

### Solution

```js
// 1. Swap — RHS evaluated atomically before LHS assignments:
let a = 1, b = 2;
[a, b] = [b, a]; // [b,a] = [2,1] created first, then a=2, b=1
console.log(a, b); // 2 1

// 2. First, middle, last extraction:
const arr = [10, 20, 30, 40, 50];

// Option A — can't do [first, ...middle, last] directly (rest must be last):
const [first, ...rest] = arr;
const last = rest.pop(); // mutates rest! Usually undesirable
const middle = rest;

// Option B — immutable, using destructure then slice:
const [firstB, ...restB] = arr;
const lastB   = arr.at(-1);   // or arr[arr.length - 1]
const middleB = arr.slice(1, -1); // [20, 30, 40]

// Option C — purely functional with slice:
const [head, ...tail] = arr;
const [lastC, ...revMiddle] = [...tail].reverse();
const middleC = revMiddle.reverse();

// 3. Reshape flat → nested:
const flat = { firstName: 'Ada', lastName: 'Lovelace', age: 36, city: 'London' };
const { firstName: first, lastName: last, age, city, ...otherProps } = flat;
const shaped = {
  name:     { first, last },
  age,
  location: { city, ...otherProps },
};
// { name: { first:'Ada', last:'Lovelace' }, age:36, location:{ city:'London' } }
```

### Trace

```js
// Swap trace — order of evaluation:
let a = 1, b = 2;
[a, b] = [b, a];
// Step 1: evaluate RHS: [b, a] → [2, 1]  (b=2, a=1 at this moment)
// Step 2: assign LHS from result:
//         a = 2   (from position 0 of [2,1])
//         b = 1   (from position 1 of [2,1])
// a=2, b=1 ✓

// Reshape trace:
const flat = { firstName: 'Ada', lastName: 'Lovelace', age: 36, city: 'London' };
const { firstName: first, lastName: last, age, city } = flat;
// first='Ada', last='Lovelace', age=36, city='London'

const shaped = { name: { first, last }, age, location: { city } };
// { name: { first:'Ada', last:'Lovelace' }, age:36, location:{ city:'London' } }
// ✓ flat object unchanged (destructuring is read-only on the source)
```

### Edge Cases
- Swap with `const`: `const a=1, b=2; [a,b]=[b,a]` → TypeError (can't reassign const). Use `let`.
- `arr.at(-1)` for last element: available in Node 16.6+ and modern browsers; polyfill with `arr[arr.length - 1]` for older environments.
- Reshape with computed keys: `const { [dynamicKey]: extracted }` works for dynamic field names.

### Follow-up Questions
- "Multiple swap at once?" — `[a, b, c] = [c, a, b]` works — the entire RHS is evaluated before any LHS assignment.
- "Circular reference in reshape?" — Won't happen with destructuring since it's just reading properties, not creating new object graphs.

## Problem 7 — Event Emitter with Optional Handlers

### Problem

Implement a minimal `EventEmitter` class that uses optional chaining, nullish coalescing, spread, and destructuring internally. The class must safely handle: adding and removing listeners, emitting events with arguments, one-time listeners, and calling a handler at most once.

```js
const emitter = new EventEmitter();
emitter.on('data', (x) => console.log('A', x));
emitter.once('data', (x) => console.log('B', x)); // only fires once
emitter.emit('data', 42);   // logs "A 42" then "B 42"
emitter.emit('data', 99);   // logs "A 99" (B already removed)
emitter.off('data');         // removes all 'data' listeners
emitter.emit('data', 1);    // nothing — no listeners
```

### Pattern Recognition
Optional chaining for safe handler lookup and invocation; nullish coalescing for initializing listener arrays; spread for calling handlers with variable arguments; destructuring for clean method signatures.

### Key Insight
`this.listeners[event]` might not exist yet — `??= []` initializes it only on first access. When emitting, `this.listeners[event] ?? []` prevents "forEach on undefined" if the event was never registered. Optional chaining on `handler?.call(this, ...args)` safely handles the case where a handler was removed mid-emit.

### Solution

```js
class EventEmitter {
  #listeners = {}; // private field: { eventName: [{ fn, once }] }

  on(event, fn) {
    this.#listeners[event] ??= []; // initialize array only if absent
    this.#listeners[event].push({ fn, once: false });
    return this; // chainable
  }

  once(event, fn) {
    this.#listeners[event] ??= [];
    this.#listeners[event].push({ fn, once: true });
    return this;
  }

  off(event, fn) {
    if (!fn) {
      // Remove ALL listeners for this event:
      delete this.#listeners[event];
    } else {
      // Remove specific listener:
      this.#listeners[event] = this.#listeners[event]?.filter(l => l.fn !== fn) ?? [];
    }
    return this;
  }

  emit(event, ...args) {
    // Safe access: if event has no listeners, use empty array (no-op)
    const listeners = [...(this.#listeners[event] ?? [])]; // copy: safe to modify original during loop

    // Remove 'once' listeners BEFORE calling (in case handler re-emits):
    this.#listeners[event] = this.#listeners[event]?.filter(l => !l.once) ?? [];

    for (const { fn } of listeners) {
      fn?.(...args); // optional chaining: fn might have been removed mid-emit
    }

    return this;
  }

  listenerCount(event) {
    return this.#listeners[event]?.length ?? 0;
  }
}
```

### Trace

```js
const emitter = new EventEmitter();
// #listeners = {}

emitter.on('data', fnA);
// 'data' ??= [] → initializes. #listeners = { data: [{ fn:fnA, once:false }] }

emitter.once('data', fnB);
// #listeners = { data: [{ fn:fnA, once:false }, { fn:fnB, once:true }] }

emitter.emit('data', 42):
// listeners = [...#listeners.data] = copy of both entries
// filter to remove 'once': #listeners.data = [{ fn:fnA, once:false }]
// loop: fnA(42) → "A 42"; fnB(42) → "B 42"
// #listeners.data = [{ fn:fnA, once:false }]  (fnB permanently removed)

emitter.emit('data', 99):
// listeners = [{ fn:fnA, once:false }]
// fnA(99) → "A 99"  (fnB is gone)

emitter.off('data'):
// no fn arg → delete #listeners['data']
// #listeners = {}

emitter.emit('data', 1):
// #listeners['data'] is undefined
// listeners = [...(undefined ?? [])] = [...[]] = []
// loop runs 0 times — silent no-op ✓
```

### Edge Cases
- Emitting while removing handlers (re-entrant emit): copying listeners before iterating (`[...array]`) prevents issues when a handler calls `off()`.
- `off` with no listeners registered: `?. filter` returns undefined `?? []` = `[]` (no crash).
- `listenerCount` for unregistered event: `undefined?.length ?? 0` = `0` ✓.

### Follow-up Questions
- "Why `??=` instead of `||=` for `#listeners[event]`?" — `||=` would also replace `[]` with a new `[]` if the array is empty (empty array is falsy... wait, actually `[]` is truthy in JavaScript, so `||=` also works here). But `??=` is more semantically precise: "initialize only if truly absent (null/undefined)."
- "What does the private `#listeners` field give us over a regular property?" — True encapsulation: external code cannot access or tamper with the listeners map directly. Accessing `emitter.#listeners` from outside the class is a SyntaxError.

## Quick Reference — Pattern Decision Tree

```
Which ES6+ feature applies to this scenario?
│
├── EXTRACTING VALUES from an object or array?
│   ├── From an ARRAY (by position)
│   │   const [a, b, c] = arr            basic positional
│   │   const [a, , c]  = arr            skip elements
│   │   const [a = 1]   = arr            with default (fires only on undefined)
│   │   const [first, ...rest] = arr     first + collect remaining
│   └── From an OBJECT (by key name)
│       const { name, age }     = obj   basic
│       const { name: n }       = obj   rename: source key → local variable
│       const { name = 'A' }    = obj   with default (fires only on undefined)
│       const { a, b, ...rest } = obj   extract named + collect remaining
│       const { [key]: val }    = obj   computed/dynamic key
│
├── ACCESSING POTENTIALLY ABSENT nested properties?
│   ├── Property might not exist (null/undefined at any level)
│   │   obj?.prop     obj?.method()     arr?.[i]     fn?.()
│   │   Chain:        a?.b?.c?.d   (each ?. independently guards)
│   └── Need a FALLBACK VALUE when access returns undefined/null?
│       value ?? 'default'      (null/undefined ONLY → use when 0/false are valid)
│       value || 'default'      (any falsy → use when 0/false should fall through)
│       a?.b?.c ?? 'fallback'   (safe navigation + default combined)
│
├── MERGING or COPYING objects/arrays?
│   ├── Arrays: [...arr1, ...arr2]              concatenate
│   │          [...arr.slice(0,i), x, ...arr.slice(i)]  immutable insert
│   └── Objects: { ...defaults, ...overrides }  merge (right wins on collision)
│               { ...obj, key: 'override' }      targeted override
│               Note: SHALLOW only — nested objects are still shared references
│               Deep copy: structuredClone(obj)
│
├── BUILDING STRINGS with expressions?
│   ├── Simple interpolation:  `Hello, ${name}!`
│   ├── Multi-line:            `line1\nline2`  or literal newlines
│   ├── Computed expressions:  `${a > b ? 'yes' : 'no'}`
│   └── SANITIZING interpolated values? → Tagged template
│       function tag(strings, ...values) { /* escape values, return strings */ }
│       tag`Hello ${userInput}`
│
├── FUNCTION PARAMETER HANDLING?
│   ├── Variable number of args  →  ...rest (last param)
│   │   const sum = (...nums) => nums.reduce((a,b)=>a+b, 0)
│   ├── Options object  →  destructure in param position
│   │   function f({ a, b = 1, ...rest } = {}) {}  ← = {} guards against undefined arg
│   └── Passing array as positional args  →  spread at call site
│       Math.max(...arr);  fn(...args)
│
├── INITIALIZING or UPDATING values conditionally?
│   ├── obj.prop ??= defaultVal    (set if null/undefined)
│   ├── obj.prop ||= fallback      (set if falsy)
│   └── obj.prop &&= transform()   (update only if truthy)
│
└── DISTINGUISHING INTENT: ?? vs || quick test
    Ask: "Is [0 / false / ''] a VALID value here that should be preserved?"
    YES → use ??    (nullish only)
    NO  → use ||    (any falsy)
```

## Common Bugs Checklist

Before submitting any code using these ES6+ features, verify:

1. **Destructuring `null` or `undefined` directly throws — not a default?** — `const { a } = null` throws `TypeError`. The default value in destructuring (`const { a = 1 } = obj`) only guards against `obj.a` being `undefined` — it does NOT guard against `obj` itself being `null` or `undefined`. Add `?? {}` at the object level before destructuring: `const { a = 1 } = potentiallyNull ?? {}`.

2. **Using `||` when `??` is needed — silently discarding valid falsy values?** — If `count`, `price`, `enabled`, or any flag can legitimately be `0`, `false`, or `''`, using `||` replaces them with the default, causing subtle bugs. Audit every `value || default` expression and ask: "is this value ever validly falsy?" If yes, change to `??`.

3. **Object spread only copies ONE level deep — mutations share nested references?** — `const copy = { ...obj }` is safe for primitives but NOT for nested objects or arrays. After copying, mutations to `copy.nestedObj.prop` affect `obj.nestedObj.prop`. Use `structuredClone(obj)` for true deep copy when needed.

4. **Object spread key precedence: inline override before spread gets overwritten?** — `{ key: 'mine', ...obj }` — if `obj` has a `key` property, it wins (right side of spread wins). The intended override `'mine'` is silently lost. Put your overrides AFTER the spread: `{ ...obj, key: 'mine' }`.

5. **Rename syntax confusion: `const { a: b } = obj` — which is the variable?** — `b` is the local variable, `a` is the object's key. The mnemonic: "colon points from source (left) to target (right)." Common mistake: thinking `a` is the new variable name and `b` is the property to extract — this is exactly backwards.

6. **Missing `= {}` default for optional options parameter causes crash when argument is omitted?** — `function f({ name }) {}` throws if called as `f()` or `f(undefined)`. Always add `= {}` to destructured object parameters that are optional: `function f({ name } = {})`.

7. **`?.` does NOT prevent errors inside the accessed property/method?** — `obj?.prop` only guards when `obj` is null/undefined. If `obj` exists but `obj.prop` throws an error (e.g., a getter that throws), `?.` does not catch that. Optional chaining is specifically for null/undefined receivers, not for general error handling.

8. **`arguments` object used in an arrow function expecting local args?** — Arrow functions do NOT have their own `arguments` object. `const f = () => console.log(arguments)` refers to the enclosing function's `arguments` (or throws in module/strict scope). Always use `...rest` in arrow functions to capture arguments.

9. **Template literal interpolation with objects: `${someObject}` produces `[object Object]`?** — Any object interpolated into a template literal has `.toString()` called on it, which for plain objects returns `'[object Object]'`. Explicitly serialize: `${JSON.stringify(obj)}` or access the specific properties you need: `${obj.name}`.

10. **Tagged template: forgetting that `strings.length === values.length + 1`, not equal?** — In a tag function `(strings, ...values)`, there is always one more string fragment than interpolated value (even if some fragments are empty strings `''`). Iterating `for (let i = 0; i < values.length; i++)` and accessing `strings[i + 1]` correctly pairs each value with its surrounding strings. Using `strings.length` as the loop bound and trying to access `values[i]` will access one `undefined` at the end.

---

**Final Tip:** At the 5 YOE level, the decisive signal for ES6+ feature questions is naming *the invariant that each feature enforces*, not just knowing the syntax. For destructuring defaults: *"the default fires if and only if the extracted value is exactly `undefined` — not `null`, not `0`, not `false` — so using `??` vs destructuring defaults is a deliberate choice based on whether `null` should trigger a fallback."* For spread: *"spread creates a new top-level container, but all nested object and array values are still the same references — shallow copy is a hard invariant, not a performance shortcut, and the first question to ask before spreading is whether any consumer mutates nested properties."* For `??` vs `||`: *"`??` returns the right operand if and only if the left is `null` or `undefined` — the single most useful rule is to ask at every `||` operator: can this left-hand side ever be `0`, `false`, or `''` as a valid value? If yes, use `??`."* For optional chaining: *"`?.` short-circuits to `undefined` — not `null`, not `false` — when the receiver is null or undefined; it is purely a null-guard, not a general error-suppressor, and it composes with `??` to form the complete safe-navigation-with-default pattern `deep?.chain?.property ?? fallback` that replaces multi-line null checks."*
