## Part 1 — Theory & Interview Q&A

## Topic A: Proxy Fundamentals

### Section A1: Fundamentals

**Q1. What is a Proxy in JavaScript, and what problem does it solve?**
A: A `Proxy` is an object that wraps another object (the *target*) and intercepts fundamental operations on it — property reads, writes, deletions, function calls, `in` checks, `Object.keys()`, and more. Every intercepted operation is handled by a *trap* function defined in a *handler* object. If no trap is defined for an operation, the operation falls through to the target unchanged.

The core problem it solves: objects in JavaScript are normally transparent — you can't observe or modify what happens when someone reads or writes a property, without changing the object's source code. Proxy provides a meta-programming seam: you can inject behavior *around* property access without altering the target object itself.

```js
const target = { name: 'Alice', age: 30 };

const proxy = new Proxy(target, {
  get(target, prop) {
    console.log(`Reading property: ${prop}`);
    return Reflect.get(target, prop);
  }
});

proxy.name; // Logs: "Reading property: name" → "Alice"
proxy.age;  // Logs: "Reading property: age"  → 30
target.name; // No log — direct access bypasses the proxy
```

**Q2. What are the 13 available traps, and how do they map to language operations?**
A: Each trap corresponds to one internal method of the ECMAScript specification (the `[[InternalMethod]]` notation). All 13:

| Trap | Intercepts | Equivalent JS operation |
|---|---|---|
| `get` | `[[Get]]` | `proxy.prop`, `proxy['prop']` |
| `set` | `[[Set]]` | `proxy.prop = val` |
| `has` | `[[HasProperty]]` | `'prop' in proxy` |
| `deleteProperty` | `[[Delete]]` | `delete proxy.prop` |
| `apply` | `[[Call]]` | `proxy()`, `proxy.call()`, `proxy.apply()` |
| `construct` | `[[Construct]]` | `new proxy()` |
| `getPrototypeOf` | `[[GetPrototypeOf]]` | `Object.getPrototypeOf(proxy)` |
| `setPrototypeOf` | `[[SetPrototypeOf]]` | `Object.setPrototypeOf(proxy, proto)` |
| `isExtensible` | `[[IsExtensible]]` | `Object.isExtensible(proxy)` |
| `preventExtensions` | `[[PreventExtensions]]` | `Object.preventExtensions(proxy)` |
| `getOwnPropertyDescriptor` | `[[GetOwnProperty]]` | `Object.getOwnPropertyDescriptor(proxy, prop)` |
| `defineProperty` | `[[DefineOwnProperty]]` | `Object.defineProperty(proxy, prop, desc)` |
| `ownKeys` | `[[OwnPropertyKeys]]` | `Object.keys()`, `Object.getOwnPropertyNames()`, `for...in` |

The traps you'll use in 95% of real-world code: `get`, `set`, `has`, `deleteProperty`, `apply`, and `ownKeys`.

**Q3. What is the handler object, and what happens when a trap is missing?**
A: The handler is a plain object whose methods are the trap functions. Each method name corresponds to one of the 13 trap names. When an operation is performed on the proxy and the matching trap is absent from the handler, the operation is *forwarded* directly to the target — as if the proxy weren't there. An empty handler `{}` creates a transparent (no-op) proxy that faithfully forwards all operations to the target.

```js
const handler = {
  get(target, prop, receiver) { /* intercept reads */ },
  set(target, prop, value, receiver) { /* intercept writes */ }
  // No other traps — all other operations pass through to target
};

const proxy = new Proxy(target, handler);

// delete proxy.x → no deleteProperty trap → forwarded to target
// 'x' in proxy  → no has trap → forwarded to target
```

**Q4. What is the `receiver` parameter in `get` and `set` traps, and when does it matter?**
A: The `receiver` is the object on which the operation was originally invoked — usually the proxy itself, but can differ when prototypes are involved. It matters critically when using `Reflect.get` or `Reflect.set` inside traps, because `receiver` determines what `this` is bound to when a getter/setter property is accessed.

```js
const base = {
  get value() { return this._v; }
};

const child = Object.create(base);
child._v = 42;

const proxy = new Proxy(child, {
  get(target, prop, receiver) {
    // receiver === proxy (not target)
    // Without passing receiver:
    return Reflect.get(target, prop);          // this inside getter = target → child._v
    // With passing receiver:
    return Reflect.get(target, prop, receiver); // this inside getter = receiver → proxy._v
    // For this example, both work. But for deeper prototype chains, receiver matters.
  }
});
```

The rule of thumb: **always pass `receiver` to `Reflect.get` and `Reflect.set`** inside traps — it's the safe default that preserves the correct `this` binding for inherited getters and setters.

**Q5. What invariants must Proxy traps respect, and what happens if they are violated?**
A: The ECMAScript specification mandates *invariants* — constraints that every trap implementation must honor to maintain object-model consistency. Violating them throws a `TypeError` at runtime. Key invariants:

- **`get` trap**: if the target property is a non-writable, non-configurable data property, the trap must return the same value as the actual property value. You cannot lie about its value.
- **`set` trap**: must return `true` (success) or `false` (failure, triggers `TypeError` in strict mode). Cannot return `true` if the target property is non-writable and non-configurable.
- **`has` trap**: cannot report `false` for a non-configurable property that actually exists on the target.
- **`deleteProperty` trap**: cannot return `true` (claim deletion succeeded) for a non-configurable property.
- **`ownKeys` trap**: the returned list must include all non-configurable own properties of the target.

```js
const target = {};
Object.defineProperty(target, 'x', { value: 1, writable: false, configurable: false });

const proxy = new Proxy(target, {
  get(t, prop) { return 2; } // tries to lie about 'x'
});

proxy.x; // TypeError: 'get' on proxy: property 'x' is a read-only and non-configurable
          // data property — the proxy returned 2 but must return 1
```

### Section A2: Advanced Patterns

**Q6. What is a revocable proxy, and when is it useful?**
A: `Proxy.revocable(target, handler)` returns `{ proxy, revoke }`. Calling `revoke()` severs the proxy from its target — any subsequent operation on the proxy throws a `TypeError`. The target is also freed for garbage collection (no more reference from the proxy internals).

Revocable proxies are useful for: (1) **capability-based security** — grant a third-party module a proxy to an object, then revoke access when the module's task is done; (2) **session-scoped access** — provide access to a resource for the duration of a request and revoke it after; (3) **API key / token expiry simulation** in test environments.

```js
const { proxy, revoke } = Proxy.revocable({ secret: 42 }, {});

console.log(proxy.secret); // 42 — works fine

revoke(); // sever the connection

console.log(proxy.secret); // TypeError: Cannot perform 'get' on a proxy that has been revoked
```

**Q7. How do you build a "negative array index" proxy that supports `arr[-1]` for last element access?**
A: Intercept `get` and convert negative indices to their equivalent positive indices:

```js
function createNegativeIndexArray(arr) {
  return new Proxy(arr, {
    get(target, prop, receiver) {
      // Convert string prop to number; if negative, wrap around
      const index = Number(prop);
      if (Number.isInteger(index) && index < 0) {
        return Reflect.get(target, target.length + index, receiver);
      }
      return Reflect.get(target, prop, receiver);
    }
  });
}

const arr = createNegativeIndexArray([10, 20, 30, 40]);
console.log(arr[-1]);  // 40 (last element)
console.log(arr[-2]);  // 30 (second-to-last)
console.log(arr[0]);   // 10 (positive index — unchanged)
console.log(arr.length); // 4 (non-numeric prop — passes through)
```

**Q8. How do you create a "default-value" proxy that returns a fallback for missing properties instead of `undefined`?**
A: Intercept `get` and check whether the property exists on the target before deciding what to return:

```js
function withDefaults(target, defaultValue) {
  return new Proxy(target, {
    get(t, prop, receiver) {
      // Return default for own missing properties
      // But still allow prototype chain methods (toString, etc.)
      if (prop in t) return Reflect.get(t, prop, receiver);
      return typeof defaultValue === 'function'
        ? defaultValue(prop)  // dynamic default (e.g., return prop name)
        : defaultValue;       // static default (e.g., 0 or '')
    }
  });
}

const config = withDefaults({ host: 'localhost' }, 'NOT_SET');
console.log(config.host);    // "localhost" (exists)
console.log(config.port);    // "NOT_SET" (missing)
console.log(config.timeout); // "NOT_SET" (missing)
```

**Q9. How do you implement a deep-observable object using nested Proxies?**
A: A single proxy only intercepts operations on the proxied object directly — it doesn't intercept operations on nested objects. To observe deeply, wrap returned sub-objects in proxies lazily (on each `get`):

```js
function observable(target, onChange) {
  return new Proxy(target, {
    get(t, prop, receiver) {
      const value = Reflect.get(t, prop, receiver);
      // Lazily wrap nested objects
      if (value !== null && typeof value === 'object') {
        return observable(value, onChange); // wrap the nested object too
      }
      return value;
    },
    set(t, prop, value, receiver) {
      const oldValue = t[prop];
      const result = Reflect.set(t, prop, value, receiver);
      if (result && value !== oldValue) {
        onChange({ target: t, prop, oldValue, newValue: value });
      }
      return result;
    },
    deleteProperty(t, prop) {
      const oldValue = t[prop];
      const result = Reflect.deleteProperty(t, prop);
      if (result) onChange({ target: t, prop, oldValue, newValue: undefined });
      return result;
    }
  });
}

const state = observable({ user: { name: 'Alice' } }, (change) => {
  console.log(`Changed: ${change.prop} → ${change.newValue}`);
});

state.user.name = 'Bob'; // Logs: "Changed: name → Bob"
state.count = 1;          // Logs: "Changed: count → 1"
```

The key: returning `observable(value, onChange)` inside `get` creates a new proxy on-the-fly each time a nested object is accessed. This is correct but has a subtlety: the proxy wraps the same target `value`, so mutations via the proxy are visible on the original object — but the proxy object returned on each `get` is a different object reference. This can cause `===` identity checks to fail on nested objects.

**Q10. What are the performance implications of Proxy, and when should you avoid it?**
A: Proxy adds a layer of indirection to every intercepted operation. The overhead:

- **Property access**: 2–10× slower than direct property access in V8 (JIT optimizations that assume stable object shapes are defeated by proxies).
- **Property write**: similar overhead — the engine cannot apply hidden-class optimization to proxy targets when writes are intercepted.
- **In hot loops**: proxies inside tight inner loops can cause significant performance regression — cache the proxied value or unwrap the target before the loop.
- **Prototype chains**: proxies break some engine optimizations that rely on the prototype chain being static and analyzable at compile time.

When to avoid: (1) objects accessed in performance-critical inner loops; (2) objects used as keys in WeakMaps (works, but the proxy and target are separate keys); (3) library APIs where the performance contract is tight (e.g., high-frequency trading systems, game loops, binary parsers). When to embrace: developer tooling, validation layers, Vue.js-style reactivity systems, ORM model proxies, mock objects in tests — places where developer ergonomics outweigh raw throughput.

## Topic B: Reflect API

### Section B1: Fundamentals

**Q11. What is the Reflect API, and why does it exist alongside Proxy?**
A: `Reflect` is a built-in object (not a constructor — cannot be called with `new`) that exposes the same 13 fundamental operations as Proxy traps, but as explicit method calls rather than operator syntax. It has two complementary roles:

1. **Companion to Proxy**: inside a trap, use `Reflect.get(target, prop, receiver)` instead of `target[prop]` — it correctly handles `receiver` for inherited getters and respects the ECMAScript specification's precise semantics (including returning the right boolean from set, etc.).

2. **Unified introspection API**: replaces various `Object.*` and `Function.*` methods with a single, coherent namespace. `Reflect.ownKeys(obj)` = `Object.getOwnPropertyNames(obj).concat(Object.getOwnPropertySymbols(obj))`. `Reflect.has(obj, prop)` = `prop in obj`. These return consistent boolean results (Reflect methods that used to throw now return `false`).

```js
// Old way — inconsistent: Object.defineProperty throws on failure
// New way — consistent: Reflect.defineProperty returns false on failure
const success = Reflect.defineProperty(obj, 'x', { value: 1 });
if (!success) { /* handle gracefully */ }

// vs.
try {
  Object.defineProperty(obj, 'x', { value: 1 }); // throws if non-configurable
} catch (e) { /* handle */ }
```

**Q12. What are all the Reflect methods, and what do they return?**
A: All 13 Reflect methods mirror the 13 Proxy traps:

| Method | Returns | Notes |
|---|---|---|
| `Reflect.get(target, prop, receiver?)` | value | Safe replacement for `target[prop]` |
| `Reflect.set(target, prop, value, receiver?)` | boolean | `true` = success |
| `Reflect.has(target, prop)` | boolean | Equivalent to `prop in target` |
| `Reflect.deleteProperty(target, prop)` | boolean | `true` = deletion succeeded |
| `Reflect.apply(target, thisArg, args)` | return value | Replaces `Function.prototype.apply.call(fn, ...)` |
| `Reflect.construct(target, args, newTarget?)` | new instance | Replaces `new target(...args)` with `new.target` support |
| `Reflect.getPrototypeOf(target)` | prototype or null | Replaces `Object.getPrototypeOf` |
| `Reflect.setPrototypeOf(target, proto)` | boolean | Returns false instead of throwing |
| `Reflect.isExtensible(target)` | boolean | Replaces `Object.isExtensible` |
| `Reflect.preventExtensions(target)` | boolean | Returns false instead of throwing |
| `Reflect.getOwnPropertyDescriptor(target, prop)` | descriptor or undefined | Replaces `Object.getOwnPropertyDescriptor` |
| `Reflect.defineProperty(target, prop, descriptor)` | boolean | Returns false instead of throwing |
| `Reflect.ownKeys(target)` | array of keys | All own keys (strings + symbols) |

**Q13. Why should you use `Reflect.*` inside Proxy traps instead of directly manipulating the target?**
A: Three reasons:

1. **Correct `receiver` propagation**: `Reflect.get(target, prop, receiver)` passes the `receiver` to inherited getters, preserving the correct `this` binding. `target[prop]` loses the receiver.

2. **Return value semantics**: `Reflect.set` and `Reflect.deleteProperty` return booleans indicating success/failure. Proxy `set` and `deleteProperty` traps are required to return booleans — using `Reflect.*` naturally provides this. Forgetting to return a boolean from `set` (returning `undefined` instead of `true`) causes a `TypeError` in strict mode.

3. **Default forwarding**: `Reflect` provides the exact default behavior the engine would use without a proxy. This makes "forward with a side-effect" traps trivially correct:

```js
// Correct: Reflect handles all edge cases
set(target, prop, value, receiver) {
  console.log(`Setting ${prop}`);
  return Reflect.set(target, prop, value, receiver); // returns boolean, preserves receiver
}

// Fragile: misses receiver, doesn't return correct boolean reliably
set(target, prop, value) {
  console.log(`Setting ${prop}`);
  target[prop] = value; // loses receiver; always returns undefined (not boolean)
  return true;          // manually returning true — works but misses edge cases
}
```

**Q14. What is `Reflect.apply`, and how does it differ from `Function.prototype.apply`?**
A: `Reflect.apply(target, thisArg, argumentsList)` calls `target` as a function with the given `thisArg` and argument list. It is equivalent to `Function.prototype.apply.call(target, thisArg, argumentsList)` but more concise and works even when `target.apply` has been overridden or doesn't exist.

```js
// Old, verbose (works even if target.apply is overridden):
Function.prototype.apply.call(Math.max, null, [1, 2, 3]); // 3

// New, clean:
Reflect.apply(Math.max, null, [1, 2, 3]); // 3

// In an apply trap:
apply(target, thisArg, argumentsList) {
  console.log(`Called with args: ${argumentsList}`);
  return Reflect.apply(target, thisArg, argumentsList); // correct forwarding
}
```

**Q15. What is `Reflect.construct`, and how does its `newTarget` parameter enable `class`-level patterns?**
A: `Reflect.construct(Target, args, NewTarget)` creates a new instance as if `new NewTarget(...args)` were called, but allocates the instance using `Target`'s constructor. The `new.target` value inside the constructor is `NewTarget`. This enables "superclass constructor calling subclass initializers" patterns without actual class syntax:

```js
class Foo {
  constructor() {
    this.type = new.target.name; // captures the actual class being instantiated
  }
}
class Bar extends Foo {}

// Without Reflect.construct:
const f = new Foo(); console.log(f.type); // "Foo"
const b = new Bar(); console.log(b.type); // "Bar"

// Using Reflect.construct to replicate: Foo's body, but new.target = Bar
const c = Reflect.construct(Foo, [], Bar);
console.log(c instanceof Bar); // true  (prototype is Bar.prototype)
console.log(c.type);           // "Bar" (new.target.name = Bar)

// Critical use: a construct trap that changes the actual constructor but preserves new.target:
construct(target, args, newTarget) {
  // target = original class, newTarget = what 'new' was called on
  return Reflect.construct(target, args, newTarget); // preserves instanceof correctly
}
```

### Section B2: Advanced Patterns

**Q16. How do Proxy and Reflect work together to implement a validation layer?**
A: The classic combination: use `set` trap + `Reflect.set` to validate incoming values before they're written to the target. The proxy enforces invariants; Reflect handles the actual write if validation passes.

```js
function createValidated(target, schema) {
  return new Proxy(target, {
    set(t, prop, value, receiver) {
      if (prop in schema) {
        const validate = schema[prop];
        const error = validate(value);
        if (error) throw new TypeError(`Validation failed for '${prop}': ${error}`);
      }
      return Reflect.set(t, prop, value, receiver); // only write if valid
    }
  });
}

const user = createValidated({}, {
  age:   v => typeof v !== 'number' || v < 0 ? 'must be a non-negative number' : null,
  email: v => typeof v !== 'string' || !v.includes('@') ? 'must be a valid email' : null,
});

user.name = 'Alice';   // no schema → passes through
user.age  = 25;        // valid → written
user.age  = -5;        // TypeError: Validation failed for 'age': must be a non-negative number
user.email = 'bad';    // TypeError: Validation failed for 'email': must be a valid email
```

**Q17. How do you use Proxy to implement method chaining / fluent interfaces lazily?**
A: A proxy can intercept property accesses and return the proxy itself (or a new proxy), enabling an infinite chain of method-like property accesses without defining actual methods:

```js
function createQueryBuilder(tableName) {
  const clauses = { table: tableName, conditions: [], fields: ['*'], limit: null };

  return new Proxy({}, {
    get(_, prop) {
      if (prop === 'build') return () => buildSQL(clauses);

      // Return a function that sets the clause and returns the proxy (for chaining)
      return (...args) => {
        if (prop === 'where')   clauses.conditions.push(args[0]);
        if (prop === 'select')  clauses.fields = args;
        if (prop === 'limit')   clauses.limit = args[0];
        return proxy; // return self for chaining
      };
    }
  });

  // proxy defined outside for self-reference
  var proxy = new Proxy({}, { get(_, prop) { /* same as above */ } });
  return proxy;
}

// Result: arbitrarily chainable without pre-defining method names:
// query('users').select('id','name').where('age > 18').limit(10).build()
```

**Q18. How does Vue 3's reactivity system use Proxy, and what are the key design decisions?**
A: Vue 3's `reactive()` function wraps objects in a Proxy with `get` and `set` traps that integrate with a dependency-tracking system (`track` and `trigger`):

```js
// Simplified Vue 3 reactive internals:
function reactive(target) {
  return new Proxy(target, {
    get(t, prop, receiver) {
      track(t, prop); // record that the current effect depends on this property
      const value = Reflect.get(t, prop, receiver);
      if (typeof value === 'object' && value !== null) {
        return reactive(value); // deep reactivity: wrap nested objects
      }
      return value;
    },
    set(t, prop, value, receiver) {
      const oldValue = t[prop];
      const result = Reflect.set(t, prop, value, receiver);
      if (result && value !== oldValue) {
        trigger(t, prop); // notify all effects that depend on this property
      }
      return result;
    }
  });
}
```

Key design decisions in Vue 3's actual implementation:
- **Lazy wrapping**: nested objects are only wrapped in a proxy when accessed (in `get`), not eagerly — avoids proxying the entire object tree up front.
- **Separate `readonly` proxy**: a second proxy variant prevents mutations, using a `set` trap that logs warnings and returns `false`.
- **WeakMap for caching**: `proxyMap = new WeakMap<target, proxy>` prevents creating multiple proxies for the same target — each target has exactly one proxy, enabling identity checks to work correctly.
- **Skip non-plain objects**: Date, Map, Set, and other built-ins are handled with separate instrumentation, not generic proxies — Proxy doesn't intercept built-in internal slots (e.g., `[[MapData]]`) reliably.

## Topic C: Common Interview Patterns and Pitfalls

### Section C1: Fundamentals

**Q19. What is the "Proxy transparency" problem, and when does it manifest?**
A: A Proxy is not identical to its target — `proxy !== target`. Code that checks identity (using `===` or checking `if (obj === originalTarget)`) will behave differently through a proxy. This manifests in several ways:

```js
const target = { x: 1 };
const proxy = new Proxy(target, {});

// Identity failure:
console.log(proxy === target); // false — different objects

// WeakMap / WeakSet:
const wm = new WeakMap();
wm.set(target, 'hello');
wm.get(proxy);  // undefined — proxy is a different key than target
wm.get(target); // 'hello'

// instanceof:
class Foo {}
const f = new Foo();
const p = new Proxy(f, {});
console.log(p instanceof Foo); // true — instanceof uses getPrototypeOf trap ✓
// (this one actually works — instanceof respects the proxy's prototype chain)

// Built-in methods with internal slots (Map, Set, Date, Promise):
const m = new Map();
const pm = new Proxy(m, {});
pm.set('key', 'val'); // TypeError: Method Map.prototype.set called on incompatible receiver
// Map.prototype.set accesses [[MapData]] internal slot, which only 'm' has, not 'pm'
```

The internal-slot problem is the most significant: methods of `Map`, `Set`, `Date`, `Promise`, `ArrayBuffer`, `RegExp`, and other built-ins access internal slots directly — they check "does this object have `[[MapData]]`?" — and proxies don't have the target's internal slots. The workaround: forward calls to the target explicitly inside the `get` trap.

**Q20. How do you proxy a `Map` correctly, working around the internal slot problem?**
A: Bind all method accesses to the original target when they are functions — this ensures Map's internal methods are called with `this` pointing to the actual Map (which has `[[MapData]]`), not the proxy:

```js
function proxyMap(map, onChange) {
  return new Proxy(map, {
    get(target, prop, receiver) {
      const value = Reflect.get(target, prop, receiver);
      // If it's a Map method, bind it to the target (not the proxy)
      if (typeof value === 'function') {
        return value.bind(target); // bind to real Map, not proxy
      }
      return value;
    }
  });
}

const m = proxyMap(new Map(), () => {});
m.set('a', 1); // works — set is bound to the real Map
m.get('a');    // 1 — works
```

The trade-off: binding to `target` means that if `set` triggers other method calls, they happen on the target (not the proxy) — so any `get` trap that should observe those operations won't fire. For deep interception of Map/Set operations, the standard approach is to intercept at the Map/Set method level explicitly, not at the property-access level.

**Q21. What is the difference between `Proxy` and `Object.defineProperty` for intercepting property access?**
A: `Object.defineProperty` with a getter/setter was the pre-Proxy mechanism for intercepting property access, with significant limitations:

| Capability | `Object.defineProperty` | `Proxy` |
|---|---|---|
| Intercept reads | ✅ (getter) | ✅ (`get` trap) |
| Intercept writes | ✅ (setter) | ✅ (`set` trap) |
| Intercept `in` operator | ❌ | ✅ (`has` trap) |
| Intercept `delete` | ❌ | ✅ (`deleteProperty` trap) |
| Intercept non-existent properties | ❌ | ✅ (`get` trap catches any prop) |
| Intercept `Object.keys()` | ❌ | ✅ (`ownKeys` trap) |
| Intercept function calls | ❌ | ✅ (`apply` trap) |
| Apply retroactively to existing object | ❌ (must redefine each prop) | ✅ (wraps entire object) |
| Performance | Better (JIT-optimized) | Worse (defeats JIT) |
| Array index interception | ❌ (limited) | ✅ |
| Revocable | ❌ | ✅ (`Proxy.revocable`) |

Vue 2 used `Object.defineProperty` (with significant workarounds for arrays and new properties); Vue 3 switched to `Proxy` (dropping IE11 support) precisely because Proxy handles all these cases uniformly.

### Section C2: Advanced Patterns

**Q22. How do you implement a Proxy-based memoization wrapper for functions?**
A: Use the `apply` trap on a function proxy to intercept calls and cache results:

```js
function memoize(fn) {
  const cache = new Map();

  return new Proxy(fn, {
    apply(target, thisArg, args) {
      const key = JSON.stringify(args); // simple key; use a better hasher for complex args
      if (cache.has(key)) {
        return cache.get(key);
      }
      const result = Reflect.apply(target, thisArg, args);
      cache.set(key, result);
      return result;
    }
  });
}

const expensiveCalc = memoize((n) => {
  console.log(`Computing ${n}...`);
  return n * n;
});

expensiveCalc(4); // Logs "Computing 4..." → 16
expensiveCalc(4); // No log (cached)          → 16
expensiveCalc(5); // Logs "Computing 5..." → 25
```

The Proxy approach preserves the function's identity and all other properties (`name`, `length`, `toString`) — unlike a wrapper function which would lose them.

**Q23. What is a "membrane" pattern, and how do Proxy and Reflect implement it?**
A: A membrane is a boundary between two realms of objects (e.g., trusted and untrusted code) that uses proxies to intercept all object crossings. Every object that crosses the boundary is wrapped in a proxy; the proxies ensure that:
- Objects from the untrusted realm cannot directly access trusted realm internals.
- Values returned by the untrusted realm are themselves wrapped before entering the trusted realm.
- The membrane can enforce security policies (e.g., "untrusted code cannot access property `__secret__`").

```js
class Membrane {
  constructor() {
    this.wetToWrap = new WeakMap(); // wet object → wrapped (dry) proxy
    this.wrapToWet = new WeakMap(); // wrapped proxy → wet object
  }

  wrap(wet) {
    if (wet === null || typeof wet !== 'object') return wet; // primitives pass through
    if (this.wetToWrap.has(wet)) return this.wetToWrap.get(wet); // cache hit

    const membrane = this;
    const dry = new Proxy(wet, {
      get(target, prop, receiver) {
        return membrane.wrap(Reflect.get(target, prop, receiver)); // wrap returned values
      },
      set(target, prop, value, receiver) {
        // Unwrap dry values before setting on the wet target
        return Reflect.set(target, prop, membrane.unwrap(value), receiver);
      }
    });

    this.wetToWrap.set(wet, dry);
    this.wrapToWet.set(dry, wet);
    return dry;
  }

  unwrap(dry) {
    return this.wrapToWet.has(dry) ? this.wrapToWet.get(dry) : dry;
  }
}
```

Membranes are the foundation of secure sandboxing systems (SES — Secure ECMAScript), Salesforce's Locker Service, and similar cross-realm isolation frameworks.

**Q24. "In one sentence each, state what Proxy and Reflect each add to the language."**
A:
- **Proxy**: adds the ability to intercept and redefine fundamental language operations on any object, enabling transparent behavioral wrappers without modifying the wrapped object.
- **Reflect**: adds a unified, consistent API for performing those same fundamental operations programmatically, returning booleans instead of throwing and correctly preserving receiver semantics — serving as the "default forwarding behavior" inside Proxy traps.

**Q25. "Walk through what happens when you do `proxy.foo = 5` on a proxy with a `set` trap."**
A: Step by step through the ECMAScript machinery:

1. JavaScript evaluates `proxy.foo = 5` — this invokes the `[[Set]]` internal method on `proxy`.
2. The engine sees `proxy` is a Proxy object, so it looks for a `set` trap in the handler.
3. If found, it calls `handler.set(target, 'foo', 5, proxy)` — where `target` is the unwrapped target, `'foo'` is the property key, `5` is the new value, and `proxy` is the receiver.
4. The trap runs the user's code (validation, logging, etc.).
5. When the trap calls `Reflect.set(target, 'foo', 5, receiver)`, this invokes the `[[Set]]` internal method on the raw `target` — bypassing the proxy this time (since `target` is not a proxy).
6. `Reflect.set` sets `target.foo = 5` (using `receiver` for inherited setter `this` binding) and returns `true` if successful.
7. The trap returns this boolean to the engine.
8. If the trap returned `false` (or the trap is missing and the underlying set fails) in strict mode, a `TypeError` is thrown at the assignment site.
9. If successful, the assignment expression `proxy.foo = 5` evaluates to `5` (assignment expressions evaluate to the right-hand side value, regardless of what the trap returns).

## Problem 1 — Read-Only Object Proxy

### Problem
Implement a `makeReadOnly(obj)` function that returns a proxy of `obj` where any attempt to set, delete, or define a property throws a `TypeError` with a descriptive message. Reads should pass through normally.

```js
const obj = makeReadOnly({ x: 1, y: { z: 2 } });

console.log(obj.x);     // 1
console.log(obj.y.z);   // 2  (read — allowed)
obj.x = 10;             // TypeError: Cannot set property 'x' on a read-only object
delete obj.x;           // TypeError: Cannot delete property 'x' on a read-only object
obj.w = 5;              // TypeError: Cannot set property 'w' on a read-only object
```

### Pattern Recognition
`set`, `deleteProperty`, and `defineProperty` traps — block all write operations with descriptive errors. `get` trap needed for deep read-only (recursively wrap nested objects). Use `Reflect` for pass-through reads.

### Key Insight
A shallow read-only proxy only protects the top-level properties — `obj.y.z = 99` would succeed because `obj.y` returns the raw nested object (not a proxy). For deep read-only, the `get` trap must recursively wrap nested objects. Both shallow and deep variants are valid depending on requirements — implement both and explain the trade-off.

### Solution

```js
function makeReadOnly(obj) {
  return new Proxy(obj, {
    // Block property writes
    set(target, prop, value) {
      throw new TypeError(`Cannot set property '${String(prop)}' on a read-only object`);
    },

    // Block property deletion
    deleteProperty(target, prop) {
      throw new TypeError(`Cannot delete property '${String(prop)}' on a read-only object`);
    },

    // Block property (re)definition
    defineProperty(target, prop, descriptor) {
      throw new TypeError(`Cannot define property '${String(prop)}' on a read-only object`);
    },

    // Block prototype change
    setPrototypeOf(target, proto) {
      throw new TypeError('Cannot change prototype of a read-only object');
    },

    // Block making extensible again (allow preventExtensions — that's a restriction)
    // (isExtensible and preventExtensions pass through — those are read-only-friendly)

    // READ: pass through, recursively wrapping nested objects for deep read-only
    get(target, prop, receiver) {
      const value = Reflect.get(target, prop, receiver);
      if (value !== null && typeof value === 'object') {
        return makeReadOnly(value); // deep: wrap nested objects too
      }
      return value;
    }
  });
}
```

### Dry Run

```js
const obj = { x: 1, y: { z: 2 } };
const ro = makeReadOnly(obj);

// Read operations — pass through:
ro.x
  → get trap: Reflect.get(obj, 'x') = 1 (primitive) → return 1 ✓

ro.y
  → get trap: Reflect.get(obj, 'y') = { z: 2 } (object) → return makeReadOnly({ z: 2 })
  → returns a NEW proxy wrapping { z: 2 }

ro.y.z
  → [on the { z: 2 } proxy]:
  → get trap: Reflect.get({ z: 2 }, 'z') = 2 (primitive) → return 2 ✓

// Write operations — blocked:
ro.x = 10
  → set trap: prop='x', value=10
  → throw TypeError: "Cannot set property 'x' on a read-only object" ✓

ro.y.z = 99
  → [on the { z: 2 } proxy]:
  → set trap: prop='z', value=99
  → throw TypeError: "Cannot set property 'z' on a read-only object" ✓
  (Deep read-only works because ro.y returns a proxy, not the raw { z: 2 })

delete ro.x
  → deleteProperty trap: prop='x'
  → throw TypeError: "Cannot delete property 'x' on a read-only object" ✓
```

### Complexity
- Space: O(d) per read of nested objects — each `get` that returns an object creates a new proxy wrapper (not cached). For repeated reads of the same nested object, consider caching with a WeakMap.
- Performance: each `get` on a non-primitive triggers proxy wrapping — avoid in hot paths.

### Edge Cases
- Symbol properties: `String(prop)` correctly handles both string and symbol keys in error messages.
- `null` values: `value !== null && typeof value === 'object'` correctly excludes `null` (which has `typeof null === 'object'`).
- Functions: `typeof value === 'object'` is false for functions — they pass through without wrapping. If function properties should also be protected, add `typeof value === 'function'` to the wrapping condition.
- Arrays: `makeReadOnly([1,2,3])` works — arrays are objects; mutations like `arr.push(4)` internally call `[[Set]]` on index properties, which the `set` trap blocks.

### Follow-up Questions
- "Make it shallow (only protect top-level properties)?" → Remove the `get` trap entirely — nested objects are returned raw.
- "Allow reads on prototype methods (e.g., `toString`)?" → The current `get` trap wraps ALL objects including function values if updated — add a check to not wrap inherited methods.
- "Support `Object.freeze` semantics?"→ Also call `preventExtensions` on the proxy and return `false` from `isExtensible` — `Object.freeze` additionally prevents property reconfiguration (already handled by `defineProperty` trap) and makes all properties non-writable (handled by `set` trap).

## Problem 2 — Schema-Validated Object

### Problem
Implement `createSchema(schema)` that returns a factory function. The factory creates objects whose property writes are validated against the schema. Invalid writes throw `TypeError`. Reads pass through. Unknown properties (not in schema) are allowed without validation.

```js
const PersonSchema = createSchema({
  name:  { type: 'string', minLength: 1 },
  age:   { type: 'number', min: 0, max: 150 },
  email: { type: 'string', pattern: /\S+@\S+\.\S+/ }
});

const alice = PersonSchema({ name: 'Alice', age: 30 });

alice.name = 'Bob';   // valid — passes
alice.age  = 200;     // TypeError: 'age' must be at most 150
alice.email = 'bad';  // TypeError: 'email' must match pattern /\S+@\S+\.\S+/
alice.role = 'admin'; // valid — 'role' not in schema, passes through
```

### Pattern Recognition
`set` trap with schema-driven constraint checking — validate value against the schema entry for the property name before forwarding to the target via `Reflect.set`. Factory function (closure) captures the schema.

### Key Insight
The schema is captured in the closure, not the proxy handler — the handler accesses it via the outer scope. The `set` trap is the only one needed: reads never need validation, deletions are domain-specific (allow or block based on requirements). The trap must return `true` on success and throw on failure (not return `false`) — throwing gives a clear error message, while returning `false` produces a generic `TypeError` in strict mode.

### Solution

```js
function createSchema(schema) {
  // Returns a factory that produces validated objects
  return function(initial = {}) {
    // Start with validated initial values
    const target = {};

    // Handler captures schema via closure
    const handler = {
      set(t, prop, value, receiver) {
        // Only validate properties that appear in the schema
        if (Object.prototype.hasOwnProperty.call(schema, prop)) {
          const rules = schema[prop];
          validate(prop, value, rules); // throws TypeError on failure
        }
        return Reflect.set(t, prop, value, receiver);
      },
      get(t, prop, receiver) {
        return Reflect.get(t, prop, receiver);
      }
    };

    const proxy = new Proxy(target, handler);

    // Apply initial values through the proxy (so they get validated too)
    for (const [key, val] of Object.entries(initial)) {
      proxy[key] = val;
    }

    return proxy;
  };
}

function validate(prop, value, rules) {
  // Type check
  if (rules.type && typeof value !== rules.type) {
    throw new TypeError(`'${prop}' must be of type ${rules.type}, got ${typeof value}`);
  }
  // String constraints
  if (rules.minLength !== undefined && value.length < rules.minLength) {
    throw new TypeError(`'${prop}' must have length >= ${rules.minLength}`);
  }
  if (rules.maxLength !== undefined && value.length > rules.maxLength) {
    throw new TypeError(`'${prop}' must have length <= ${rules.maxLength}`);
  }
  if (rules.pattern && !rules.pattern.test(value)) {
    throw new TypeError(`'${prop}' must match pattern ${rules.pattern}`);
  }
  // Number constraints
  if (rules.min !== undefined && value < rules.min) {
    throw new TypeError(`'${prop}' must be at least ${rules.min}`);
  }
  if (rules.max !== undefined && value > rules.max) {
    throw new TypeError(`'${prop}' must be at most ${rules.max}`);
  }
}
```

### Dry Run

```js
const PersonSchema = createSchema({
  name:  { type: 'string', minLength: 1 },
  age:   { type: 'number', min: 0, max: 150 },
  email: { type: 'string', pattern: /\S+@\S+\.\S+/ }
});

const alice = PersonSchema({ name: 'Alice', age: 30 });

// Initial values — applied through proxy:
// proxy['name'] = 'Alice' → set trap → validate('name','Alice',{type:'string',minLength:1}) → ok
// proxy['age']  = 30      → set trap → validate('age',30,{...}) → 30≥0 and 30≤150 → ok
// target = { name: 'Alice', age: 30 }

alice.age = 200;
// set trap: prop='age', value=200
// schema['age'] exists → validate('age', 200, {type:'number',min:0,max:150})
// 200 > 150 → throw TypeError("'age' must be at most 150") ✓

alice.email = 'bad';
// set trap: prop='email', value='bad'
// validate('email', 'bad', {type:'string', pattern:/\S+@\S+\.\S+/})
// typeof 'bad' === 'string' ✓
// /\S+@\S+\.\S+/.test('bad') = false → throw TypeError("'email' must match pattern...") ✓

alice.role = 'admin';
// set trap: prop='role', value='admin'
// schema['role'] does not exist → skip validation
// Reflect.set(target, 'role', 'admin') → target.role = 'admin' ✓
```

### Complexity
- Time: O(R) per write where R = number of rules in the schema entry. O(1) per read.
- Space: O(1) per write (no caching).

### Edge Cases
- Initial values: passing invalid initial values through the factory throws immediately during construction — good for fail-fast initialization.
- Inherited properties in schema: `Object.prototype.hasOwnProperty.call(schema, prop)` correctly excludes inherited schema properties (e.g., `toString`).
- `undefined` values: `typeof undefined === 'undefined'` — if a type rule is specified, setting a property to `undefined` will fail the type check. Explicitly allow `undefined` if the property should be deletable.
- Symbol keys: schema keys are typically strings; if `prop` is a Symbol, `schema[prop]` will be `undefined` (no Symbol-keyed schema entries), so the validation is skipped — usually the desired behavior.

### Follow-up Questions
- "Add required field validation?" → On a `deleteProperty` trap, check if the deleted property is marked `required: true` in the schema and throw if so.
- "Validate on read too (e.g., sanitize returned values)?" → Add a `get` trap that runs a `sanitize` or `transform` function on the returned value.
- "Support nested schema (schema for nested objects)?" → On `set`, if the schema rule has a `schema` sub-key, wrap the assigned value in a `createSchema(rules.schema)({...value})` before storing.

## Problem 3 — Observable Store

### Problem
Implement `createStore(initialState)` that returns a store with `state` (a proxy) and `subscribe(prop, callback)`. Whenever `state.prop` is written, all registered callbacks for that property are called with `(newValue, oldValue)`. Callbacks are not called if the value doesn't change.

```js
const store = createStore({ count: 0, name: 'Alice' });

store.subscribe('count', (next, prev) => {
  console.log(`count changed: ${prev} → ${next}`);
});

store.state.count = 1;  // Logs: "count changed: 0 → 1"
store.state.count = 1;  // No log (value unchanged)
store.state.name = 'Bob'; // No log (no subscriber for 'name')
```

### Pattern Recognition
`set` trap — on each write, compare new value to old, notify subscribers for the changed property. Map of `prop → Set<callback>` for subscriber management. `Reflect.set` for the actual write.

### Key Insight
The "no notification on same value" optimization requires knowing the *old* value before the write — read it from the target (not the proxy, to avoid re-triggering the `get` trap) before calling `Reflect.set`. The subscriber map is kept external to the proxy (in the closure) — it's part of the store infrastructure, not the proxied state object.

### Solution

```js
function createStore(initialState) {
  // Map from property name → Set of callback functions
  const subscribers = new Map();

  const state = new Proxy({ ...initialState }, {
    set(target, prop, newValue, receiver) {
      const oldValue = target[prop]; // read from raw target — no trap re-entry

      // Perform the write first
      const result = Reflect.set(target, prop, newValue, receiver);

      // Notify only if write succeeded AND value actually changed
      if (result && newValue !== oldValue) {
        const cbs = subscribers.get(prop);
        if (cbs) {
          for (const cb of cbs) {
            cb(newValue, oldValue);
          }
        }
      }

      return result; // must return boolean
    }
  });

  function subscribe(prop, callback) {
    if (!subscribers.has(prop)) {
      subscribers.set(prop, new Set());
    }
    subscribers.get(prop).add(callback);

    // Return an unsubscribe function
    return function unsubscribe() {
      subscribers.get(prop)?.delete(callback);
    };
  }

  return { state, subscribe };
}
```

### Dry Run

```js
const store = createStore({ count: 0, name: 'Alice' });

// After creation:
// state proxy wraps { count: 0, name: 'Alice' }
// subscribers = Map {}

const unsub = store.subscribe('count', (next, prev) => {
  console.log(`count changed: ${prev} → ${next}`);
});
// subscribers = Map { 'count' → Set { [callback] } }

store.state.count = 1;
// set trap: target={count:0,name:'Alice'}, prop='count', newValue=1
// oldValue = target['count'] = 0
// Reflect.set(target, 'count', 1) → target.count = 1, returns true
// result=true, newValue(1) !== oldValue(0) → notify
// subscribers.get('count') = Set{cb}
// cb(1, 0) → logs "count changed: 0 → 1" ✓

store.state.count = 1;
// set trap: oldValue = target['count'] = 1
// Reflect.set → returns true
// newValue(1) === oldValue(1) → no notification ✓

store.state.name = 'Bob';
// set trap: prop='name', newValue='Bob', oldValue='Alice'
// Reflect.set → true, 'Bob' !== 'Alice'
// subscribers.get('name') = undefined → no notification ✓

unsub(); // removes the callback from subscribers
store.state.count = 99;
// subscribers.get('count') = Set{} (empty after unsub)
// No notification ✓
```

### Complexity
- Time: O(C) per write where C = number of callbacks for the changed property.
- Space: O(S) where S = total number of subscriptions.

### Edge Cases
- Object values: `newValue !== oldValue` uses reference equality for objects — two different objects with identical contents are considered "changed." Use `JSON.stringify` or a deep-equal function if structural equality is desired.
- `NaN` values: `NaN !== NaN` in JavaScript — two NaN writes would trigger notifications even though the value is "the same." Fix: `if (result && !Object.is(newValue, oldValue))` — `Object.is` handles NaN correctly.
- Unsubscribe on non-existent prop: `subscribers.get(prop)?.delete(callback)` uses optional chaining — safe if the prop was never subscribed.
- Subscribing to array indices: `subscribe('0', cb)` — array index mutations (like `state.arr[0] = x`) do call the `set` trap with string prop `'0'`. Works correctly but requires subscribing to the string form of the index.

### Follow-up Questions
- "Subscribe to ALL property changes?" → Add a wildcard subscriber: `subscribe('*', cb)` — in the `set` trap, always check and notify wildcard subscribers after checking property-specific ones.
- "Add computed properties that auto-update?" → On `get`, detect computed property keys, track which state properties they depend on (Vue-style dependency tracking), and re-run the computation when those dependencies change.
- "Batch updates (notify once after multiple writes)?" → Buffer notifications in a `pendingNotifications` set, then flush them all in a `queueMicrotask` or `Promise.resolve().then(flush)`. Prevents redundant re-renders when multiple properties change in one synchronous block.

## Problem 4 — API Rate-Limiter Proxy

### Problem
Implement `createRateLimitedProxy(target, options)` where `options = { maxCalls, windowMs }`. The proxy wraps an object whose methods can be called at most `maxCalls` times per `windowMs` milliseconds. Calls exceeding the limit throw an error. Calls that are within the limit pass through normally. Non-function properties pass through without rate limiting.

```js
const api = createRateLimitedProxy({
  fetchUser: (id) => `User ${id}`,
  fetchData: (key) => `Data for ${key}`
}, { maxCalls: 3, windowMs: 1000 });

api.fetchUser(1); // "User 1"
api.fetchUser(2); // "User 2"
api.fetchUser(3); // "User 3"
api.fetchUser(4); // Error: Rate limit exceeded. Max 3 calls per 1000ms.
```

### Pattern Recognition
`get` trap wrapping method accesses — when a function property is accessed, return a wrapped version that enforces the rate limit before delegating to the original function. Maintain a per-method call-timestamp log to implement the sliding window rate limit.

### Key Insight
Rate limiting is enforced at *call time*, not at property-access time. The `get` trap returns a wrapper function (not the result of calling the function) — the wrapper checks the rate limit when invoked. Maintaining per-method state (call timestamps) requires a `Map<methodName, timestamps[]>` in the closure. A sliding window implementation: at each call, prune timestamps older than `windowMs` and check if the count exceeds `maxCalls`.

### Solution

```js
function createRateLimitedProxy(target, { maxCalls, windowMs }) {
  // Per-property call history: prop → array of timestamps
  const callHistory = new Map();

  return new Proxy(target, {
    get(t, prop, receiver) {
      const value = Reflect.get(t, prop, receiver);

      // Only wrap function properties
      if (typeof value !== 'function') return value;

      // Return a rate-limited wrapper around the original function
      return function rateLimitedMethod(...args) {
        const now = Date.now();

        // Get or create call history for this method
        if (!callHistory.has(prop)) callHistory.set(prop, []);
        const timestamps = callHistory.get(prop);

        // Sliding window: remove timestamps outside the current window
        const windowStart = now - windowMs;
        while (timestamps.length > 0 && timestamps[0] < windowStart) {
          timestamps.shift();
        }

        // Check rate limit
        if (timestamps.length >= maxCalls) {
          throw new Error(
            `Rate limit exceeded for '${String(prop)}'. Max ${maxCalls} calls per ${windowMs}ms.`
          );
        }

        // Record this call and invoke the original function
        timestamps.push(now);
        return Reflect.apply(value, receiver, args);
      };
    }
  });
}
```

### Dry Run

```js
const api = createRateLimitedProxy(
  { fetchUser: (id) => `User ${id}` },
  { maxCalls: 3, windowMs: 1000 }
);
// callHistory = Map {}

api.fetchUser(1);
// get trap: prop='fetchUser', value=function, return rateLimitedMethod
// rateLimitedMethod(1):
//   now = T₀ (e.g., 1000)
//   callHistory: Map { 'fetchUser' → [] }
//   windowStart = T₀ - 1000 = 0. No old timestamps to prune.
//   timestamps.length(0) < maxCalls(3) → ok
//   timestamps.push(T₀) → [T₀]
//   Reflect.apply(fetchUser, receiver, [1]) → "User 1" ✓

api.fetchUser(2); // timestamps=[T₀, T₁] → "User 2" ✓
api.fetchUser(3); // timestamps=[T₀, T₁, T₂] → "User 3" ✓

api.fetchUser(4);
// rateLimitedMethod(4):
//   now = T₃ (still within same 1000ms window as T₀)
//   windowStart = T₃ - 1000 (all T₀,T₁,T₂ are within window)
//   After pruning: timestamps = [T₀, T₁, T₂]
//   timestamps.length(3) >= maxCalls(3) → THROW
//   Error: "Rate limit exceeded for 'fetchUser'. Max 3 calls per 1000ms." ✓

// After 1000ms from T₀:
// windowStart = T₄ - 1000 > T₀ → T₀ is pruned
// timestamps = [T₁, T₂] → 2 calls in window → call allowed again
```

### Complexity
- Time per call: O(K) where K = calls in the current window (the pruning loop). O(1) amortized since each timestamp is added and removed at most once.
- Space: O(P × maxCalls) where P = number of distinct methods called — at most `maxCalls` timestamps per method at any time.

### Edge Cases
- `maxCalls = 0`: every call throws immediately — valid if you want to disable a method entirely.
- Calls to non-function properties (`api.someString`): `typeof value !== 'function'` returns it directly — no rate limiting.
- Concurrent calls at the same millisecond (`Date.now()` returns the same value): all count separately — `timestamps.push(now)` adds duplicates, correctly counting them as separate calls.
- Prototype methods (`api.toString()`): `Reflect.get` with `receiver` correctly handles inherited methods — they're wrapped and rate-limited too if they return functions.
- `this` binding: the wrapper uses `Reflect.apply(value, receiver, args)` where `receiver` is the proxy — ensures methods that use `this` internally behave correctly.

### Follow-up Questions
- "Rate limit globally (all method calls combined, not per method)?" → Replace `callHistory.get(prop)` with a single shared `globalTimestamps` array — all method calls draw from the same budget.
- "Return a queued promise instead of throwing on limit?" → Change the throw to `return new Promise((resolve) => setTimeout(() => resolve(rateLimitedMethod(...args)), delay))` — adds queuing behavior with back-pressure.
- "Log all rate limit violations?" → Add `onLimitExceeded: (prop, count) => void` to the options; call it before throwing.

## Quick Reference — Proxy & Reflect Patterns

```
What operation do you need to intercept?
│
├── PROPERTY READ (obj.x or obj['x'])?
│   └── get(target, prop, receiver) trap
│       Always: return Reflect.get(target, prop, receiver)
│       Use for: default values, access logging, lazy initialization,
│                negative array indices, deep read-only, deep observable
│
├── PROPERTY WRITE (obj.x = val)?
│   └── set(target, prop, value, receiver) trap
│       Always: return Reflect.set(target, prop, value, receiver) [boolean!]
│       Use for: validation, change notification, read-only enforcement,
│                rate limiting, schema enforcement
│
├── PROPERTY EXISTENCE ('x' in obj)?
│   └── has(target, prop) trap
│       Use for: hiding internal/private properties from 'in' checks,
│                simulating virtual properties
│
├── PROPERTY DELETION (delete obj.x)?
│   └── deleteProperty(target, prop) trap
│       Return: Reflect.deleteProperty(target, prop) [boolean]
│       Use for: preventing deletion, logging deletions, required-field enforcement
│
├── FUNCTION CALL (fn() or fn.call() or fn.apply())?
│   └── apply(target, thisArg, argumentsList) trap
│       Always: return Reflect.apply(target, thisArg, argumentsList)
│       Use for: memoization, logging, rate limiting, argument validation,
│                before/after hooks on function calls
│
├── CONSTRUCTOR CALL (new Fn())?
│   └── construct(target, argumentsList, newTarget) trap
│       Always: return Reflect.construct(target, argumentsList, newTarget)
│       Use for: singleton enforcement, constructor argument validation,
│                factory interception
│
├── ENUMERATE OWN KEYS (Object.keys, for...in)?
│   └── ownKeys(target) trap
│       Must include all non-configurable own keys of target
│       Use for: hiding private ('_') properties, virtual key lists
│
└── NEED TO REVOKE ACCESS LATER?
    └── const { proxy, revoke } = Proxy.revocable(target, handler)
        revoke() → proxy becomes inert, throws on any operation
        Use for: capability-based security, session-scoped access

ALWAYS USE Reflect INSIDE TRAPS:
  Reflect.get(target, prop, receiver)       ← not target[prop]
  Reflect.set(target, prop, value, receiver) ← not target[prop] = value (returns boolean)
  Reflect.apply(target, thisArg, args)      ← not target.apply(thisArg, args)
  Reason: correct receiver binding, correct return values, correct error semantics

COMMON PITFALLS:
  ✗ Forgetting receiver in get/set → wrong 'this' for inherited getters/setters
  ✗ Forgetting to return boolean from set/deleteProperty trap → TypeError in strict mode
  ✗ Proxying Map/Set/Date directly → internal slot access fails (bind methods to target)
  ✗ proxy !== target → identity checks, WeakMap keys, some instanceof checks differ
  ✗ Deep observation: get trap must recursively wrap returned objects
  ✗ Using Proxy in tight loops → defeats JIT optimizations, 2-10x slower
```

## Common Bugs Checklist

Before submitting any Proxy/Reflect solution, verify:

1. **`set` trap returns a boolean?** — `set(target, prop, value, receiver)` must return `true` (success) or `false` (failure). Returning nothing (implicitly `undefined`) causes a `TypeError` in strict mode: "Trap returned falsy for property 'x'." Always end with `return Reflect.set(target, prop, value, receiver)` or explicitly `return true`/`return false`.

2. **`receiver` passed to `Reflect.get` and `Reflect.set`?** — `Reflect.get(target, prop)` without `receiver` loses the correct `this` binding for inherited getters. `Reflect.get(target, prop, receiver)` passes the original receiver (usually the proxy) — correct for all cases. Make this a habit: always pass `receiver` as the third argument to `Reflect.get` and `Reflect.set`.

3. **Not using `target[prop]` for reads inside `get` trap?** — `target[prop]` instead of `Reflect.get(target, prop, receiver)` inside the `get` trap is wrong for two reasons: it bypasses the receiver, and for inherited getters it calls them with `this = target` instead of `this = receiver`. Always use `Reflect.get`.

4. **Deep interception requires recursive wrapping in the `get` trap?** — A proxy only intercepts operations on the proxied object, not on objects returned from it. If `get` returns a raw nested object, mutations on that nested object are not intercepted. For deep observability/read-only/validation, the `get` trap must return `makeProxy(value)` when `value` is an object.

5. **Map/Set/Date methods bound to target, not proxy?** — `proxy.set('key', val)` where `proxy` wraps a `Map` calls `Map.prototype.set` with `this = proxy` — which lacks `[[MapData]]` → TypeError. Inside the `get` trap, `if (typeof value === 'function') return value.bind(target)` ensures Map methods are called with the correct `this`.

6. **`Proxy.revocable` — never using the proxy after `revoke()`?** — After `revoke()`, any operation on the proxy throws a `TypeError`. Check that your code doesn't cache the proxy reference and use it after revocation.

7. **`ownKeys` trap returning all non-configurable own keys?** — If the target has non-configurable own properties, the `ownKeys` trap must include them in its return value. Returning a list that omits non-configurable keys throws a `TypeError` (invariant violation). When in doubt, start with `Reflect.ownKeys(target)` and filter/extend from there.

8. **Trap handlers referencing stale closure variables?** — If a handler is shared across multiple proxies (created once and reused), closured variables may refer to the wrong target. Each proxy should either have its own handler instance or the handler should rely only on the `target` parameter (which is always the correct target for the specific proxy).

**Final Tip:** In interviews, Proxy and Reflect questions typically test two things: (1) knowing which trap to use for which operation — nail this with the 13-trap table; and (2) understanding *why* `Reflect` is used inside traps rather than direct property access — the answer is always "correct `receiver` propagation for inherited getters/setters, and consistent boolean return values for `set` and `deleteProperty`." Beyond that, the most impressive answers connect Proxy to real-world use cases: Vue 3's reactivity, validation layers, membrane security patterns, and revocable capabilities — showing you understand not just the API mechanics but the *design problems* that motivated it.
