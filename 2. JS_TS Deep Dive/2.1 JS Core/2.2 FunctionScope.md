# JavaScript Core (Fundamentals): Scope — Function Scope — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is function scope?**
A: Function scope means that variables declared inside a function are only accessible within that function and any functions nested inside it — they are invisible to the outside world. Every function invocation creates a brand new scope: its own variable environment, isolated from the caller and from sibling functions. In JavaScript, `var` is the canonical function-scoped declaration keyword — it doesn't care about blocks (`if`, `for`, `{}`), only about the nearest enclosing function boundary.

**Q2. What is the practical difference between function scope and block scope?**
A: Block scope (introduced with `let`/`const` in ES6) creates a new scope at every `{}` — `if`, `for`, `while`, standalone blocks. Function scope only creates a new scope at function boundaries. The consequence: a `var` declared inside an `if` block is visible throughout the entire enclosing function (not just inside the `if`), while a `let`/`const` is confined to that block. This distinction is one of the most frequent sources of bugs in legacy JS code.

```js
function example() {
  if (true) {
    var x = 1;   // function-scoped — visible outside the if block
    let y = 2;   // block-scoped — invisible outside the if block
  }
  console.log(x); // 1
  console.log(y); // ReferenceError
}
```

**Q3. Why does `var` ignore block boundaries?**
A: Because `var` was designed before block scoping was part of the language. The spec defines `var` declarations as belonging to the nearest enclosing *function* (or global scope if there's no enclosing function). Blocks (`{}`) are transparent to `var` — the JS engine hoists `var` declarations to the top of their function scope during the creation phase, regardless of which block they're written in.

**Q4. What does "lexical scope" mean, and how does it apply to function scope?**
A: Lexical scope means scope is determined at *write time* (by where the code is written in the source), not at *run time* (by how or where the function is called). A function's access to outer variables is fixed when the function is defined — it looks up the scope chain of its *defining* context, not its *calling* context. This is the foundation of closures: a function "remembers" the scope it was born in, regardless of where it's invoked later.

**Q5. Is a new function scope created on every function *call*, or just on every function *definition*?**
A: Every *call*. A function definition creates a template for a scope; each invocation of that function creates a fresh, independent scope instance with its own variable bindings. This is why recursive functions work — each call has its own `n`, its own local state — and why two concurrent async calls to the same function don't share local variables.

## Section 2: Hoisting Within Function Scope

**Q6. How does hoisting work inside a function?**
A: During the creation phase of a function's execution context, the JS engine scans the function body and allocates memory for all `var` declarations (initialized to `undefined`) and all inner function declarations (stored in full). This happens before any line of the function body actually executes. So within a function, `var` variables and function declarations are "hoisted" to the top of that function's scope.

**Q7. What does this print, and why?**
```js
function run() {
  console.log(a); // ?
  var a = 10;
  console.log(a); // ?
}
run();
```
A: Prints `undefined`, then `10`. During the creation phase, `var a` is hoisted and initialized to `undefined`. When `console.log(a)` runs first, `a` exists but holds `undefined`. The assignment `a = 10` happens in the execution phase, so the second log sees `10`.

**Q8. What happens when a function declaration and a `var` share the same name inside a function?**
A: The function declaration wins during the creation phase — it takes priority over `var` hoisting because function declarations are fully initialized (not just set to `undefined`). However, any subsequent assignment in the execution phase (e.g., `var foo = 5`) will overwrite the function with `5` when that line is reached:
```js
function test() {
  console.log(typeof foo); // "function" — function declaration wins hoisting
  var foo = 5;
  console.log(typeof foo); // "number" — assignment overwrites it
  function foo() {}
}
test();
```

**Q9. Does `let`/`const` hoist inside a function?**
A: They are hoisted (memory is allocated in the creation phase), but unlike `var` they are not initialized — they sit in the Temporal Dead Zone (TDZ) from the start of their enclosing scope (block or function) until the line where they're declared. Accessing them before that line throws `ReferenceError: Cannot access 'x' before initialization`. The practical rule: treat `let`/`const` as if they don't hoist — never access them before their declaration.

**Q10. Are function parameters part of function scope?**
A: Yes — parameters are treated as `var`-like local variables in the function's scope, initialized with the argument values passed at the call site. They behave as if declared at the top of the function. Interestingly, in non-strict mode with simple parameters, there's a live binding between the `arguments` object and named parameters — mutating one updates the other. In strict mode (or with rest/default/destructured parameters), that link is severed and `arguments` is a static snapshot.

## Section 3: Closures & Function Scope

**Q11. What is a closure, in terms of function scope?**
A: A closure is a function that retains a live reference to the variable environment of its *defining* function scope, even after that outer function has returned and its execution context has been popped off the call stack. The inner function "closes over" the outer scope's variables — keeping them alive in memory as long as the inner function itself is reachable.

**Q12. Trace what happens to function scope when this runs:**
```js
function makeCounter() {
  let count = 0;
  return function () {
    count++;
    return count;
  };
}
const counter = makeCounter();
counter(); // 1
counter(); // 2
```
A: `makeCounter()` creates a function scope with `count = 0`. The returned inner function closes over that scope. When `makeCounter()` returns, its execution context is popped — but the inner function still holds a reference to the lexical environment containing `count`, so that environment stays alive on the heap. Each `counter()` call increments the same `count` in that preserved scope. If you call `makeCounter()` again, a fresh scope with its own `count = 0` is created — the two counters are completely independent.

**Q13. Classic interview trap — what does this log, and how do you fix it?**
```js
for (var i = 0; i < 3; i++) {
  setTimeout(function () { console.log(i); }, 0);
}
```
A: Logs `3, 3, 3`. `var i` is function-scoped (or global-scoped if this is at the top level) — there is only *one* `i` shared across all three iterations. By the time the `setTimeout` callbacks fire (after the loop finishes), `i` is already `3`. All three closures reference the *same* variable in the *same* scope, not a snapshot of its value.

Fixes:
- **`let` instead of `var`** — `let` creates a new block-scoped binding per iteration, so each closure captures its own `i`.
- **IIFE per iteration** — wrap the body in `(function(j) { setTimeout(() => console.log(j), 0); })(i)` to create a new function scope and capture the current value as `j`.
- **`setTimeout`'s third argument** — `setTimeout(function(j) { console.log(j); }, 0, i)` passes `i` as an argument, evaluated immediately.

**Q14. How does function scope interact with the module pattern?**
A: The module pattern (pre-ES modules) exploits function scope to create private state. An IIFE creates a function scope that's entered once and immediately exited, but the returned object holds closures over that scope's variables — making those variables effectively "private" (inaccessible from outside) while exposing only what's returned:
```js
const counter = (function () {
  let _count = 0;          // private — function-scoped, never exposed
  return {
    increment() { _count++; },
    value() { return _count; }
  };
})();
counter.increment();
counter.value(); // 1
// _count is inaccessible from outside — true encapsulation via function scope
```

**Q15. Can two sibling functions (defined in the same outer scope) access each other's local variables?**
A: No. Each function invocation creates its own isolated scope. Sibling functions share access to their *common outer scope* via the scope chain, but a variable declared inside function `A` is invisible to function `B` — even if they were defined next to each other. Only parent → child (outer → inner) visibility exists, not sibling → sibling.

## Section 4: `this` Inside Function Scope

**Q16. How does `this` behave inside a regular function, and why is it separate from scope?**
A: `this` is determined by the *call site* (how the function is invoked), not by the scope chain (which is determined by where the function is written). They're independent concepts: scope controls variable lookup; `this` is a separate binding in the execution context set fresh on every call. A function can have the same lexical scope as another but a completely different `this` depending on how it's called.

**Q17. What is the `this` value in a plain (non-method) function call?**
A: In non-strict mode: the global object (`window` in browsers). In strict mode: `undefined`. This is one of the most common sources of `TypeError: Cannot read properties of undefined` bugs — a function intended to be called as a method gets detached and called as a plain function, and `this` is no longer the expected object.

**Q18. How do `call`, `apply`, and `bind` relate to function scope?**
A: They don't affect scope (lexical scope is fixed at definition time and can't be changed). They only affect `this`. `call(obj, arg1, arg2)` and `apply(obj, [args])` invoke the function immediately with `this` set to `obj`. `bind(obj)` returns a *new* function with `this` permanently locked to `obj` — useful for preserving a method's `this` when passing it as a callback where it would otherwise lose its call-site binding.

**Q19. Why do arrow functions behave differently for `this` in terms of function scope?**
A: Arrow functions don't create their own `this` binding at all — they *lexically* inherit `this` from their enclosing function scope at definition time, just like any other variable. This makes them ideal for callbacks inside methods: the arrow function's `this` is whatever the surrounding method's `this` was, regardless of how the callback is eventually invoked. It also means `call`/`apply`/`bind` cannot change an arrow function's `this`.

## Section 5: Practical Patterns & Pitfalls

**Q20. What is an IIFE, and what problem does it solve with function scope?**
A: An Immediately Invoked Function Expression creates a temporary function scope that's entered and exited immediately, keeping its internal declarations from leaking into the surrounding (often global) scope:
```js
(function () {
  var privateVar = "hidden";
  // do setup work
})();
// privateVar is not accessible here
```
Before ES modules and `let`/`const`, IIFEs were the primary tool for scope isolation in libraries and large scripts. Today they're mostly obsolete for that purpose — ES modules give you file-level scope isolation for free — but they still appear in legacy codebases and occasionally for intentional scoping tricks.

**Q21. What is the "function scope as a namespace" anti-pattern, and why does it fail at scale?**
A: Relying on function scope to simulate namespacing (grouping related logic inside a single large function) breaks down because it either forces everything to be a closure over that outer function (tight coupling, memory retention), or requires returning everything via the module pattern (verbose, manual wiring). ES modules provide genuine, tool-friendly namespacing without these trade-offs — `import`/`export` makes dependencies explicit, enables tree-shaking, and doesn't require closure tricks for encapsulation.

**Q22. What is variable "shadowing" in the context of function scope, and when is it a bug vs intentional?**
A: Shadowing is when an inner function declares a variable with the same name as one in an outer scope, making the outer variable inaccessible by that name within the inner scope. It's *intentional* when used to give a local context-appropriate name (e.g., a parameter named `event` that shadows a rarely-used outer `event`). It's a *bug* when accidental — a developer meant to update the outer variable but declared a new one instead, causing silent divergence:
```js
let total = 0;
function addItems(items) {
  var total = 0; // BUG: shadows outer total — outer total is never updated
  items.forEach(i => total += i);
}
```

**Q23. How does function scope interact with `try`/`catch`/`finally`?**
A: `var` inside a `try`, `catch`, or `finally` block is hoisted to the enclosing *function* scope — not contained within the block. The `catch` clause's error parameter (e.g., `catch (e)`) is block-scoped to the `catch` block in modern JS (ES2015+), so `e` doesn't leak out. `let`/`const` inside any of these blocks are properly block-scoped. A practical implication: declaring `var result` inside a `try` block and accessing it in the same function after the `try`/`catch` is valid (the `var` is hoisted up) — though using `let` outside the block and assigning inside is cleaner and less confusing.

## Section 6: Scenario / System Design Style Questions

**Q24. "A developer reports that a loop-driven async operation in a legacy codebase produces wrong results — all callbacks see the same value. You open the file and see `var` in a `for` loop. Walk through your diagnosis and fix."**
A: Classic function-scope closure trap. `var` in a `for` loop doesn't create a new binding per iteration — all iterations share the same variable in the enclosing function scope. By the time the async callbacks run, the loop has completed and the variable holds its final value.

Diagnosis: confirm `var` is used (not `let`), confirm the callback closes over the loop variable rather than receiving it as an argument.

Fix options (in order of preference for modern code):
1. Change `var` to `let` — the simplest, most readable fix; `let` creates a fresh binding per iteration.
2. Extract to a named function that takes the value as a parameter — makes the capture explicit and works in older environments.
3. Wrap with an IIFE inside the loop body to force a new scope per iteration — legacy approach, less readable.

**Q25. "You're reviewing a large function (200+ lines) and notice that `var` declarations are scattered throughout — some inside `if` blocks, some inside `for` loops, some at the top. What risk does this pose, and how would you address it?"**
A: All those `var` declarations, regardless of where they appear in the function body, are hoisted to the function's top — they all live in the same flat function scope. Risks:
- Re-declaration of the same name in two different blocks silently merges into one variable (no error), causing unexpected value sharing.
- Reading a `var` before its "logical" declaration reads `undefined` (hoisted but not yet assigned), which can be a subtle bug if the developer expected block-scoping.
- The 200-line function itself is a smell — it likely does too much and should be refactored into smaller, well-named functions with tighter scopes.

Remediation: mechanically replace `var` with `let`/`const` (a linter like ESLint's `no-var` rule can flag all of them), run tests to catch any logic that relied on re-declaration or hoisting quirks, then progressively extract sub-functions to reduce the overall function length.

**Q26. "A teammate asks why their module pattern broke: they added a second `<script>` tag with the same IIFE variable name and now the first module's private data is being overwritten." What's actually happening?**
A: The IIFE itself correctly creates a private function scope — the internal variables aren't leaking. The likely issue is that both IIFEs are assigning their public API to the *same global variable name* (e.g., `window.Utils = (function() { ... })()`). Since both classic `<script>` tags share the global scope, the second assignment overwrites the first. The function scope did its job; the global namespace collision is the actual problem. Fix: use unique names, namespace under a single app-level global (`window.MyApp.Utils`), or migrate to ES modules where each file has its own module scope and explicit imports replace global names entirely.

**Q27. "You need to write a rate-limiter factory — each call to `createLimiter(n)` should return a function that allows at most `n` calls per second, with its own independent counter. How does function scope support this design?"**
A: Function scope is exactly the right tool here — each call to `createLimiter` creates a fresh function scope with its own `count` and `resetTimer` variables. The returned limiter function closes over that scope, keeping the state private and independent per limiter:
```js
function createLimiter(maxCalls) {
  let count = 0;
  let timer = null;

  return function limiter(fn) {
    if (count >= maxCalls) return; // silently drop or throw
    count++;
    fn();
    if (!timer) {
      timer = setTimeout(() => {
        count = 0;
        timer = null;
      }, 1000);
    }
  };
}

const limitTo3 = createLimiter(3);
const limitTo10 = createLimiter(10);
// limitTo3 and limitTo10 each have their own count and timer — no shared state
```
This is closure-based encapsulation via function scope: no class, no WeakMap, no module-level variables — just a fresh scope per factory call.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                        | `var` (Function Scope)                        | `let` / `const` (Block Scope)                  |
|---                            |---                                             |---                                              |
| Scope boundary                | Nearest enclosing function (or global)        | Nearest enclosing block `{}`                    |
| Hoisted?                      | Yes, initialized to `undefined`               | Yes, but TDZ (uninitialized)                    |
| Accessible before declaration?| Yes (reads `undefined`)                       | No (`ReferenceError`)                           |
| Re-declarable in same scope?  | Yes (silent)                                  | No (`SyntaxError`)                              |
| Leaked from `for` loop?       | Yes — shared across all iterations            | No — fresh binding per iteration                |
| Attached to global object?    | Yes (if in global scope)                      | No                                              |
| Closure capture behavior      | Captures the one shared variable              | Captures the per-iteration binding              |
| Use in new code?              | Avoid — use `let`/`const`                     | Preferred                                       |

---

**Tip for the interview:** At the 5 YOE level, "function scope" almost never appears as a standalone question — it surfaces inside closure bugs (the `var`-in-a-loop trap), IIFE / module pattern questions, or `this`-binding problems where scope and `this` get conflated. The highest-value thing to demonstrate is knowing exactly *why* `var`'s function scope causes the loop closure bug, and being able to offer all three fixes fluently. Also be ready to articulate why `let`/`const` replaced `var` in practice — not just "it's block-scoped" but what specific class of bugs that eliminates and why the mental model is easier. Have one real example ready of a `var`-in-a-loop or shadowing bug you caught in a review or debugged in production.
