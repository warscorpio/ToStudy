# JavaScript: `Object.defineProperty` & Property Descriptors — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is `Object.defineProperty`, and what problem does it solve that regular property assignment cannot?**
A: `Object.defineProperty(obj, prop, descriptor)` defines a new property or modifies an existing one on an object, with **fine-grained control over the property's behavior** — specifically its mutability, enumerability, and configurability. Regular property assignment (`obj.foo = 'bar'`) always creates a property that is writable, enumerable, and configurable by default. `Object.defineProperty` lets you break any or all of these defaults — creating properties that can't be overwritten, won't appear in `for...in` loops, or can't be reconfigured/deleted. This is the mechanism underpinning getters/setters, read-only constants, non-enumerable internal properties, and many of the behaviors built into standard library objects.

```js
const obj = {};

// Regular assignment — all defaults on:
obj.name = 'Alice';
// Equivalent to:
Object.defineProperty(obj, 'name', {
  value: 'Alice',
  writable: true,
  enumerable: true,
  configurable: true
});

// Fine-grained control:
Object.defineProperty(obj, 'id', {
  value: 42,
  writable: false,     // cannot be changed
  enumerable: false,   // won't show in for...in / Object.keys()
  configurable: false  // cannot be deleted or reconfigured
});
```

**Q2. What are the two types of property descriptors, and what makes them mutually exclusive?**
A: Every JavaScript property is described by exactly one of two descriptor types:
1. **Data descriptor**: has `value` and/or `writable`. Represents a property that stores a concrete value.
2. **Accessor descriptor**: has `get` and/or `set`. Represents a property whose value is computed via getter/setter functions — no stored value exists.

They are **mutually exclusive** — you cannot combine `value`/`writable` with `get`/`set` in the same descriptor. Attempting to do so throws a `TypeError`. The distinction exists because a property either holds a value directly (data) or delegates to functions for getting/setting it (accessor) — there's no in-between.

```js
// VALID: data descriptor
Object.defineProperty(obj, 'count', { value: 0, writable: true });

// VALID: accessor descriptor
Object.defineProperty(obj, 'doubled', {
  get() { return this.count * 2; }
});

// INVALID: mixing both types — throws TypeError
Object.defineProperty(obj, 'bad', {
  value: 5,
  get() { return 5; } // ❌ TypeError: cannot define both value and get
});
```

**Q3. What are the six possible fields in a property descriptor, and what is each field's default when not specified during a fresh property definition?**
A: A property descriptor can contain up to six fields, split across the two types:

| Field | Type | Default (when creating) | Meaning |
|---|---|---|---|
| `value` | Data | `undefined` | The property's value |
| `writable` | Data | `false` | Can the value be changed with `=`? |
| `enumerable` | Both | `false` | Does it appear in `for...in`, `Object.keys()`, spread, etc.? |
| `configurable` | Both | `false` | Can the descriptor be changed or the property deleted? |
| `get` | Accessor | `undefined` | Function called on property read |
| `set` | Accessor | `undefined` | Function called on property write |

The **most important nuance**: defaults apply when `Object.defineProperty` creates a **new** property — they are all `false`/`undefined`. When `Object.defineProperty` **modifies** an existing property, only the explicitly-provided fields change; unspecified fields retain their current values.

**Q4. What does `writable: false` actually enforce, and how is "strict mode" relevant?**
A: A `writable: false` property silently ignores assignment attempts in non-strict mode (`obj.foo = newVal` does nothing, no error thrown, the value stays unchanged). In **strict mode**, the same assignment throws a `TypeError`. This silent-vs-throwing distinction is a classic source of bugs — code that "works" in non-strict mode (by silently swallowing an assignment that should fail) may behave differently if strict mode is enabled later. Always test immutability-dependent code in strict mode.

```js
'use strict';
const obj = {};
Object.defineProperty(obj, 'PI', { value: 3.14159, writable: false });
obj.PI = 999; // TypeError in strict mode; silent failure in sloppy mode
console.log(obj.PI); // 3.14159 (unchanged regardless of strict mode)
```

### Section 2: Configurability & Mutability Rules

**Q5. What does `configurable: false` prevent, specifically?**
A: A `configurable: false` property cannot be:
- **Deleted** (`delete obj.prop` silently fails in sloppy mode, throws in strict mode).
- **Reconfigured** — you cannot change its `configurable`, `enumerable`, or `get`/`set` fields.
- **Converted** between data and accessor descriptor types.

One important **exception**: a non-configurable **data** property can still have its `writable` changed from `true` to `false` (but NOT from `false` to `true`). This is a one-way ratchet — you can lock it down further but not unlock it.

```js
const obj = {};
Object.defineProperty(obj, 'x', { value: 1, configurable: false, writable: true });

// This IS allowed (tightening writable from true → false):
Object.defineProperty(obj, 'x', { writable: false }); // ✓

// These all throw TypeError:
Object.defineProperty(obj, 'x', { configurable: true });   // ❌ can't re-enable configurable
Object.defineProperty(obj, 'x', { enumerable: true });     // ❌ can't change enumerable
delete obj.x;                                               // ❌ can't delete (strict: throws)
```

**Q6. What is the relationship between `Object.preventExtensions`, `Object.seal`, and `Object.freeze`, and how do they each use property descriptor concepts internally?**
A: These three methods provide increasingly strict levels of whole-object immutability, all implemented in terms of property descriptor flags:
- **`Object.preventExtensions(obj)`**: marks the object as non-extensible — new properties cannot be added. Existing properties are unchanged (still writable, configurable per their individual descriptors).
- **`Object.seal(obj)`**: calls `preventExtensions` AND sets `configurable: false` on every existing property. Properties can still be read and written (if `writable: true`), but cannot be deleted, reconfigured, or new ones added.
- **`Object.freeze(obj)`**: calls `seal` AND sets `writable: false` on every existing data property. No property can be added, removed, reconfigured, or changed in value. Produces a "fully frozen" (shallowly immutable) object.

```js
const config = Object.freeze({ host: 'localhost', port: 3000 });
config.host = 'example.com'; // silently fails (or throws in strict mode)
config.newProp = 'x';        // silently fails
console.log(config.host);   // 'localhost'

// Note: freeze is SHALLOW — nested objects are not frozen
const nested = Object.freeze({ inner: { value: 1 } });
nested.inner.value = 99; // works! the reference is frozen, not the nested object
```

**Q7. Can you ever "unfreeze" a frozen object or re-enable a disabled capability?**
A: No — these operations are permanent and irreversible on a given object. Once `configurable: false` is set, it cannot be changed back to `true`. Once `writable: false` is set on a non-configurable property, it cannot be changed back to `true`. Once an object is made non-extensible, it cannot be made extensible again. This irreversibility is intentional — it gives library authors and runtime engines a strong guarantee that certain properties will never change behavior after being locked down. The only escape hatch is to work with a copy of the object instead of the original.

### Section 3: Getters & Setters

**Q8. How do accessor descriptors (getters/setters) work, and what is the `this` context inside them?**
A: An accessor descriptor defines `get` and/or `set` as functions. When the property is read, `get` is called with `this` pointing to the object on which the property access occurred (the **receiver**). When the property is written to, `set` is called with `this` as the receiver and the new value as its first argument. No value is stored directly on the property — the getter/setter pair is responsible for all storage, typically using a separate "backing" variable (often a closure variable or another property with a different name).

```js
function createTemperature(celsius) {
  let _celsius = celsius;

  return Object.defineProperty({}, 'fahrenheit', {
    get() {
      return _celsius * 9 / 5 + 32; // computed from backing variable
    },
    set(value) {
      _celsius = (value - 32) * 5 / 9; // write in Fahrenheit, store in Celsius
    },
    enumerable: true,
    configurable: true
  });
}

const temp = createTemperature(100);
console.log(temp.fahrenheit); // 212
temp.fahrenheit = 32;
console.log(temp.fahrenheit); // 32 (celsius is now 0)
```

**Q9. What is the shorthand syntax for getters/setters in object literals, and how does it relate to `Object.defineProperty`?**
A: ES5 introduced getter/setter shorthand directly in object literal syntax using `get`/`set` keywords. This is **syntactic sugar** that creates accessor descriptors identical to what `Object.defineProperty` would create, with `enumerable: true` and `configurable: true` (object-literal properties default to both being `true`).

```js
// Shorthand syntax (object literal)
const circle = {
  _radius: 5,
  get area() {
    return Math.PI * this._radius ** 2;
  },
  set radius(r) {
    if (r < 0) throw new RangeError('Radius cannot be negative');
    this._radius = r;
  }
};

// Equivalent using defineProperty:
const circle2 = { _radius: 5 };
Object.defineProperty(circle2, 'area', {
  get() { return Math.PI * this._radius ** 2; },
  enumerable: true,
  configurable: true
});
Object.defineProperty(circle2, 'radius', {
  set(r) {
    if (r < 0) throw new RangeError('Radius cannot be negative');
    this._radius = r;
  },
  enumerable: true,
  configurable: true
});
```

**Q10. How do getters/setters interact with class syntax, and what happens to their descriptors?**
A: Class syntax also supports getter/setter shorthand, but they are defined on the **prototype** (not the instance) and have `enumerable: false` by default — unlike object-literal getter/setters which default to `enumerable: true`. This means class-defined getters/setters don't show up in `for...in` or `Object.keys()` on instances, which is generally the desired behavior for methods and computed properties.

```js
class Rectangle {
  constructor(width, height) {
    this._width = width;
    this._height = height;
  }

  get area() {
    return this._width * this._height;
  }

  get perimeter() {
    return 2 * (this._width + this._height);
  }
}

const rect = new Rectangle(4, 3);
console.log(rect.area);       // 12
console.log(Object.keys(rect)); // ['_width', '_height'] — 'area' and 'perimeter' not included

// Check the descriptor on the prototype:
const desc = Object.getOwnPropertyDescriptor(Rectangle.prototype, 'area');
console.log(desc.enumerable);   // false
console.log(desc.configurable); // true
console.log(typeof desc.get);   // 'function'
```

### Section 4: Inspection Methods

**Q11. What is `Object.getOwnPropertyDescriptor`, and how does it differ from property access?**
A: `Object.getOwnPropertyDescriptor(obj, prop)` returns the **full descriptor object** for a property — including all six possible fields — rather than just the property's value. This is the only way to inspect a property's `writable`, `enumerable`, `configurable`, `get`, and `set` attributes programmatically. It only looks at **own** properties (not inherited ones via the prototype chain), and returns `undefined` if the property doesn't exist on the object itself.

```js
const obj = { name: 'Alice' };
Object.getOwnPropertyDescriptor(obj, 'name');
// → { value: 'Alice', writable: true, enumerable: true, configurable: true }

const frozenObj = Object.freeze({ x: 1 });
Object.getOwnPropertyDescriptor(frozenObj, 'x');
// → { value: 1, writable: false, enumerable: true, configurable: false }

Object.getOwnPropertyDescriptor(obj, 'toString'); // → undefined (inherited, not own)
Object.getOwnPropertyDescriptor(Object.prototype, 'toString');
// → { value: [Function: toString], writable: true, enumerable: false, configurable: true }
```

**Q12. What does `Object.getOwnPropertyDescriptors` (plural) return, and what is its key use case?**
A: `Object.getOwnPropertyDescriptors(obj)` returns a map of **all own property names** to their full descriptors. Its canonical use case is **complete, faithful cloning of an object including all its accessor and non-enumerable properties** — something that `Object.assign()` and the spread operator (`{...obj}`) cannot achieve, since those only copy enumerable own properties and invoke the getter (copying the current value, not the getter function itself).

```js
const source = {
  _x: 0,
  get x() { return this._x; },
  set x(val) { this._x = val; }
};

// Shallow spread: copies the current VALUE of x, not the getter/setter
const spreadCopy = { ...source };
Object.getOwnPropertyDescriptor(spreadCopy, 'x');
// → { value: 0, writable: true, enumerable: true, configurable: true }
// The getter/setter is LOST

// Complete clone preserving getters/setters:
const faithfulCopy = Object.defineProperties(
  {},
  Object.getOwnPropertyDescriptors(source)
);
Object.getOwnPropertyDescriptor(faithfulCopy, 'x');
// → { get: [Function: get x], set: [Function: set x], enumerable: true, configurable: true }
// Getter/setter is PRESERVED
```

**Q13. How does `enumerable: false` affect different property-discovery mechanisms?**
A: Non-enumerable properties are hidden from most iteration and serialization APIs, but remain accessible by direct property access and are inspectable via `getOwnPropertyDescriptor`:

| Method/Operation | Includes non-enumerable? |
|---|---|
| `for...in` loop | ❌ No (also skips inherited non-enumerable) |
| `Object.keys()` | ❌ No (own only) |
| `Object.values()` | ❌ No |
| `Object.entries()` | ❌ No |
| Spread `{ ...obj }` | ❌ No |
| `JSON.stringify()` | ❌ No |
| `Object.assign(target, src)` | ❌ No |
| `obj.prop` (direct access) | ✅ Yes |
| `Object.getOwnPropertyNames()` | ✅ Yes (own, all) |
| `Object.getOwnPropertyDescriptors()` | ✅ Yes (own, all) |
| `Reflect.ownKeys()` | ✅ Yes (own, including Symbols) |

Non-enumerable properties are a standard technique for attaching "internal" metadata to objects — things like tracking IDs, internal counters, or type tags that should not pollute the object's visible interface.

### Section 5: `Object.defineProperties` & Patterns

**Q14. What is `Object.defineProperties` (plural), and what is its relationship to `Object.defineProperty`?**
A: `Object.defineProperties(obj, descriptorsMap)` defines multiple properties at once, accepting a map of property names to their descriptors. It's functionally equivalent to calling `Object.defineProperty` in a loop, just more concise and atomic-feeling (though not actually atomic — if one descriptor is invalid, properties defined before the error still get applied).

```js
const api = {};

Object.defineProperties(api, {
  version: {
    value: '1.0.0',
    writable: false,
    enumerable: true,
    configurable: false
  },
  _cache: {
    value: new Map(),
    writable: false,
    enumerable: false,  // internal detail, hidden from iteration
    configurable: false
  },
  get: {
    value: function(key) { return this._cache.get(key); },
    writable: false,
    enumerable: true,
    configurable: false
  }
});
```

**Q15. What is the "lazy getter" (memoization via `defineProperty` inside a getter) pattern, and why is it useful?**
A: A lazy getter computes an expensive value on first access, then **replaces itself** with a data property holding the computed value — subsequent accesses read the pre-computed value directly without re-invoking the getter. The self-replacement is done using `Object.defineProperty` inside the getter itself, overwriting the accessor descriptor with a data descriptor.

```js
function createModule() {
  return {
    get heavyData() {
      // Expensive computation done once on first access
      const result = Array.from({ length: 1_000_000 }, (_, i) => i * 2);

      // Replace this accessor with a plain data property:
      Object.defineProperty(this, 'heavyData', {
        value: result,
        writable: false,
        enumerable: true,
        configurable: false
      });

      return result;
    }
  };
}

const mod = createModule();
console.log(mod.heavyData[999999]); // computed once (expensive)
console.log(mod.heavyData[999999]); // read from data property (instant)
```

This pattern is widely used in browser APIs and Node.js module systems for performance — the property starts as an accessor (cheap to define), pays the computation cost only when actually needed, and then caches the result permanently with no ongoing getter overhead.

**Q16. How is `Object.defineProperty` used to implement "protected" or "private-like" properties in plain JavaScript (before private class fields)?**
A: Before `#privateField` class syntax, the standard pattern for "private by convention but not enforcement" properties combined a naming convention (underscore prefix) with non-enumerability — the property wasn't truly private but wouldn't appear in `for...in`, `Object.keys()`, or `JSON.stringify()`, reducing its visibility in logs and serializations.

```js
function Person(name, age) {
  Object.defineProperty(this, '_age', {
    value: age,
    writable: true,
    enumerable: false,   // hidden from iteration/serialization
    configurable: false  // can't be reconfigured or deleted
  });
  this.name = name;     // enumerable, public
}

Person.prototype.getAge = function() { return this._age; };

const person = new Person('Alice', 30);
console.log(JSON.stringify(person));   // {"name":"Alice"} — _age not serialized
console.log(Object.keys(person));      // ['name'] — _age not listed
console.log(person._age);             // 30 — still directly accessible by name
```

Note: this is **not true encapsulation** — the property is still accessible via `person._age` and inspectable via `getOwnPropertyDescriptor`. True encapsulation in modern JavaScript uses class `#privateFields`.

### Section 6: Advanced Patterns & Proxy Interaction

**Q17. How does `Object.defineProperty` interact with the prototype chain, and does it ever affect inherited properties?**
A: `Object.defineProperty` always defines/modifies a property on the **specific object** passed as its first argument — it never touches the prototype chain. When you call `Object.defineProperty(obj, 'foo', ...)`, even if `foo` is inherited from a prototype, the operation creates a new **own property** named `foo` directly on `obj` (shadowing the prototype's property), rather than modifying the prototype's property. To modify an inherited property's descriptor, you must call `Object.defineProperty` on the actual prototype object where that property lives.

```js
function Animal(name) { this.name = name; }
Animal.prototype.type = 'generic';

const dog = new Animal('Rex');
// dog.type is inherited — NOT an own property
Object.getOwnPropertyDescriptor(dog, 'type'); // → undefined

// defineProperty on dog creates a SHADOW own property:
Object.defineProperty(dog, 'type', { value: 'canine', writable: false, enumerable: true, configurable: false });
Object.getOwnPropertyDescriptor(dog, 'type'); // → { value: 'canine', ... }
Animal.prototype.type; // → 'generic' (prototype unchanged)
```

**Q18. How does the `Proxy` object relate to `Object.defineProperty`, and what trap handles `defineProperty` calls on a proxy?**
A: A `Proxy` object wraps a target and intercepts operations on it via "traps." The trap for `Object.defineProperty(proxy, prop, desc)` calls is named `defineProperty` — if present, it intercepts any call to define a property on the proxy, allowing you to reject, redirect, or modify the definition.

```js
const validator = new Proxy({}, {
  defineProperty(target, prop, descriptor) {
    if (typeof descriptor.value === 'string' && descriptor.value.length > 50) {
      throw new Error(`Property '${prop}' value exceeds 50 character limit`);
    }
    return Reflect.defineProperty(target, prop, descriptor);
  }
});

validator.name = 'Alice';      // works (short string)
validator.bio = 'x'.repeat(51); // throws: "Property 'bio' value exceeds 50 character limit"
```

`Reflect.defineProperty` is the function-form counterpart to `Object.defineProperty` — it has the same parameters but returns a boolean instead of throwing on failure, making it better suited for use inside Proxy traps where you want to forward the operation to the underlying target.

### Section 7: Scenario / Interview-Style Questions

**Q19. "You're building a configuration object where some properties should be read-only after initialization, and others should be hidden from `JSON.stringify`. How do you model this?"**
A: Use `Object.defineProperty` (or `Object.defineProperties`) with targeted descriptor settings: `writable: false, configurable: false` for read-only properties, and `enumerable: false` for properties that should be hidden from serialization (since `JSON.stringify` skips non-enumerable properties). For the truly public-and-mutable properties, a plain assignment is fine.

```js
function createConfig({ host, port, apiKey }) {
  const config = {};

  // Public, read-only, visible properties
  Object.defineProperties(config, {
    host: { value: host, writable: false, enumerable: true, configurable: false },
    port: { value: port, writable: false, enumerable: true, configurable: false }
  });

  // Secret, non-enumerable — won't appear in JSON or logs
  Object.defineProperty(config, 'apiKey', {
    value: apiKey,
    writable: false,
    enumerable: false,
    configurable: false
  });

  return Object.preventExtensions(config); // no new properties can be added
}

const cfg = createConfig({ host: 'api.example.com', port: 443, apiKey: 'secret-xyz' });
JSON.stringify(cfg);  // '{"host":"api.example.com","port":443}' — apiKey hidden
cfg.host = 'other'; // silently fails (throws in strict mode)
cfg.debug = true;   // throws TypeError — not extensible
```

**Q20. "How would you implement a watched/observable property that triggers a callback whenever it's changed?"**
A: Define an accessor property whose setter both stores the new value and invokes the callback. The backing storage uses a different (non-enumerable) own property or a closure variable.

```js
function makeWatched(obj, prop, callback) {
  let _value = obj[prop]; // save current value

  Object.defineProperty(obj, prop, {
    get() { return _value; },
    set(newVal) {
      const oldVal = _value;
      _value = newVal;
      callback(prop, oldVal, newVal);
    },
    enumerable: true,
    configurable: true // configurable: true so it can be re-observed if needed
  });

  return obj;
}

const user = { name: 'Alice', score: 0 };
makeWatched(user, 'score', (prop, old, next) => {
  console.log(`${prop} changed: ${old} → ${next}`);
});

user.score = 10; // logs: "score changed: 0 → 10"
user.score = 25; // logs: "score changed: 10 → 25"
```

This is the conceptual foundation behind Vue 2's reactivity system, Knockout.js's observables, and similar frameworks that transparently intercept property writes to trigger UI updates.

**Q21. "Why does `Object.assign` sometimes produce surprising results when copying from source objects with getters, and how do you fix it?"**
A: `Object.assign` enumerates the source's **own enumerable properties** and copies their **values** to the target — it calls each property's getter (if it has one) and assigns the returned value to the target as a plain data property. This "flattens" accessor properties into plain values, losing the getter/setter entirely. If the getter has side effects or returns dynamic values, you get a one-time snapshot, not a live accessor.

```js
const source = {
  _x: 5,
  get x() { return this._x * 2; }
};

const copy = Object.assign({}, source);
copy.x;          // 10 (correct current value)
copy._x = 100;   // but changing _x doesn't update x in the copy:
copy.x;          // 10 still — x is now a plain data property, not a getter

// Fix: use getOwnPropertyDescriptors to preserve the getter:
const trueCopy = Object.defineProperties({}, Object.getOwnPropertyDescriptors(source));
trueCopy._x = 100;
trueCopy.x;      // 200 — getter is live, reads the new _x
```

## Problem 1 — Create a Read-Only, Non-Deletable Property

### Problem
Define a property `MAX_SIZE` on an object `limits` with value `100` such that: (1) the value cannot be changed, (2) the property cannot be deleted, (3) the property cannot be reconfigured, but (4) it should be visible in `for...in` loops (enumerable).

```js
const limits = {};
// ... your code ...
limits.MAX_SIZE = 200; // should silently fail (or throw in strict mode)
delete limits.MAX_SIZE; // should silently fail (or throw in strict mode)
console.log(limits.MAX_SIZE); // 100
```

### Pattern Recognition
Data descriptor with `writable: false` and `configurable: false`, but `enumerable: true`.

### Key Insight
`writable: false` prevents value changes; `configurable: false` prevents deletion and reconfiguration; `enumerable: true` keeps it visible in iteration. All three must be explicitly set since `Object.defineProperty` defaults `writable`, `configurable`, and `enumerable` all to `false` — here we want to override `enumerable` to `true`.

### Solution

```js
const limits = {};

Object.defineProperty(limits, 'MAX_SIZE', {
  value: 100,
  writable: false,      // assignment attempts are no-ops (or throw in strict mode)
  enumerable: true,     // visible in for...in, Object.keys(), etc.
  configurable: false   // cannot be deleted or reconfigured
});

// Verification
console.log(limits.MAX_SIZE);        // 100

limits.MAX_SIZE = 200;               // silently ignored
console.log(limits.MAX_SIZE);        // 100 (unchanged)

delete limits.MAX_SIZE;              // silently ignored
console.log(limits.MAX_SIZE);        // 100 (still present)

console.log(Object.keys(limits));   // ['MAX_SIZE'] — enumerable: true ✓

const desc = Object.getOwnPropertyDescriptor(limits, 'MAX_SIZE');
console.log(desc.writable);         // false ✓
console.log(desc.configurable);     // false ✓
console.log(desc.enumerable);       // true ✓

// Attempting to redefine the property:
try {
  Object.defineProperty(limits, 'MAX_SIZE', { value: 999 }); // ❌ throws
} catch (e) {
  console.log(e.message); // "Cannot redefine property: MAX_SIZE"
}
```

### Edge Cases
- In strict mode: `limits.MAX_SIZE = 200` and `delete limits.MAX_SIZE` both throw `TypeError` immediately rather than silently doing nothing — verify in both modes if strict mode correctness is required.
- Attempting `Object.defineProperty` to modify a non-configurable property to any new descriptor (even the same values with slight changes) throws a `TypeError` — the only allowed change to a `configurable: false` data property is tightening `writable` from `true` to `false`.

### Follow-up Questions
- "What if you want the property completely hidden from all iteration including `Object.getOwnPropertyNames()`?" → That's not possible with standard properties. `Object.getOwnPropertyNames()` always includes all own properties regardless of enumerability. Only **Symbol-keyed** properties are excluded from `Object.getOwnPropertyNames()` (they appear only in `Object.getOwnPropertySymbols()`).
- "How is this different from `Object.freeze(limits)`?" → `Object.freeze` applies `writable: false` and `configurable: false` to ALL existing properties at once, and also marks the object itself as non-extensible. Using `Object.defineProperty` gives per-property control without affecting other properties.

## Problem 2 — Implement a Computed / Derived Property with a Getter

### Problem
Build a `rectangle` object with `width` and `height` data properties, and a `area` property that is **automatically computed** from `width × height` whenever it's accessed. `area` should not be directly settable.

```js
const rect = createRectangle(4, 3);
console.log(rect.area); // 12
rect.width = 5;
console.log(rect.area); // 15 — reflects the updated width
rect.area = 100;        // should be silently ignored (no setter)
console.log(rect.area); // 15
```

### Pattern Recognition
Accessor descriptor with only a `get` function and no `set` — a pure computed property that reads from sibling data properties.

### Key Insight
An accessor property with `get` but no `set` is effectively read-only at the property level (assignment is silently ignored, or throws in strict mode). The `get` function's `this` refers to the object on which the property is accessed, so it can read `this.width` and `this.height` dynamically.

### Approach
Create the object with `width` and `height` as plain data properties, then use `Object.defineProperty` to add the `area` accessor.

### Solution

```js
function createRectangle(width, height) {
  const rect = { width, height }; // plain data properties

  Object.defineProperty(rect, 'area', {
    get() {
      return this.width * this.height; // computed fresh on every access
    },
    // no 'set' defined — attempts to write are silently ignored
    enumerable: true,
    configurable: true // allow re-definition later if needed
  });

  return rect;
}

const rect = createRectangle(4, 3);

console.log(rect.area);  // 12
rect.width = 5;
console.log(rect.area);  // 15 — getter re-runs, picks up new width ✓

rect.area = 100;         // silently ignored (no setter)
console.log(rect.area);  // 15 (unchanged) ✓

// Inspection
const desc = Object.getOwnPropertyDescriptor(rect, 'area');
console.log(typeof desc.get);  // 'function' ✓
console.log(desc.set);         // undefined ✓
console.log('value' in desc);  // false — accessor, not data descriptor ✓
```

### Edge Cases
- If `configurable: true`, the property can be converted to a data property later (e.g., if you add a `set`). Use `configurable: false` to prevent this if the computed nature should be permanent.
- Setting `enumerable: false` would hide `area` from `Object.keys()` and serialization — appropriate for "internal" computations, but here keeping it enumerable makes it behave like a normal visible property.
- If `this.width` or `this.height` is `undefined` (e.g., if the object is used as a prototype and an instance doesn't define them), the getter returns `NaN` — add defensive checks if needed.

### Follow-up Questions
- "Add a `perimeter` property the same way." → `Object.defineProperty(rect, 'perimeter', { get() { return 2 * (this.width + this.height); }, enumerable: true, configurable: true })`.
- "What if you also want `area` to be settable, updating `width` and `height` proportionally?" → Add a `set(value)` function that computes new `width`/`height` from the given area and the current aspect ratio, and assigns them to `this.width` and `this.height`.

## Problem 3 — Observable Property (Setter with Side Effect)

### Problem
Write a function `observe(obj, prop, callback)` that wraps a property of an existing object so that whenever it's set to a new value, `callback(newValue, oldValue)` is called. The property should still be readable and writable as before.

```js
const state = { count: 0 };
observe(state, 'count', (next, prev) => console.log(`count: ${prev} → ${next}`));
state.count = 5;  // logs: "count: 0 → 5"
state.count = 10; // logs: "count: 5 → 10"
console.log(state.count); // 10
```

### Pattern Recognition
Replace an existing data property with an accessor descriptor that uses a closure variable as the backing store — the setter triggers the callback, the getter returns the stored value.

### Key Insight
The property must be `configurable: true` on the original object to allow replacement with an accessor descriptor. The old value is saved in a closure variable (`_value`) before redefining the property, so the getter/setter share it without collision with other properties.

### Solution

```js
function observe(obj, prop, callback) {
  const descriptor = Object.getOwnPropertyDescriptor(obj, prop);

  // Guard: can't wrap non-configurable properties
  if (descriptor && !descriptor.configurable) {
    throw new TypeError(`Cannot observe non-configurable property '${prop}'`);
  }

  // Capture the current value in a closure
  let _value = descriptor ? descriptor.value : undefined;

  Object.defineProperty(obj, prop, {
    get() {
      return _value;
    },
    set(newValue) {
      const oldValue = _value;
      _value = newValue;
      callback(newValue, oldValue); // invoke observer
    },
    enumerable: descriptor ? descriptor.enumerable : true,
    configurable: true // keep configurable so it can be un-observed later
  });
}

// Verification
const state = { count: 0 };
observe(state, 'count', (next, prev) => {
  console.log(`count: ${prev} → ${next}`);
});

state.count = 5;  // logs: "count: 0 → 5"
state.count = 10; // logs: "count: 5 → 10"
console.log(state.count); // 10

// Property still behaves normally:
console.log(Object.keys(state)); // ['count'] — still enumerable ✓
JSON.stringify(state);           // '{"count":10}' — still serializes ✓
```

### Verification

```js
// Edge: wrap a property that doesn't exist yet on the object:
const obj = {};
observe(obj, 'name', (n, o) => console.log(`name: "${o}" → "${n}"`));
obj.name = 'Alice'; // logs: name: "undefined" → "Alice"
obj.name = 'Bob';   // logs: name: "Alice" → "Bob"

// Edge: trying to observe a non-configurable property:
const locked = {};
Object.defineProperty(locked, 'x', { value: 1, configurable: false });
try {
  observe(locked, 'x', () => {}); // throws TypeError
} catch (e) {
  console.log(e.message); // "Cannot observe non-configurable property 'x'"
}
```

### Edge Cases
- **Property doesn't exist yet**: `getOwnPropertyDescriptor` returns `undefined` — handle gracefully by defaulting `_value` to `undefined`.
- **Property is already an accessor**: the current descriptor has `get`/`set` instead of `value`. To wrap an existing accessor, the getter should call the original getter and the setter should call the original setter before/after invoking the callback.
- **Multiple observers**: this implementation replaces with a single setter — a second call to `observe` wraps the first observer's accessor, producing nested closures (which works but can be error-prone). A more robust implementation maintains an array of callbacks in the closure.

### Follow-up Questions
- "How would you undo the observation (restore the original property)?" → Keep a reference to the original descriptor in the closure, and return an `unobserve()` function from `observe()` that calls `Object.defineProperty(obj, prop, originalDescriptor)` to restore it.
- "How does this compare to Vue 2's reactivity system?" → Vue 2 uses the same `Object.defineProperty` getter/setter wrapping technique on every data property during component initialization, notifying subscribers (watchers/computed properties/template renderer) via a dependency-tracking system whenever a setter fires. Vue 3 switched to `Proxy` for more complete interception (including new property additions and array index mutations, which `Object.defineProperty` cannot intercept).

## Problem 4 — Lazy Getter (One-Time Computed Property)

### Problem
Implement a `lazyCompute(obj, prop, computeFn)` utility that installs a getter for `prop` on `obj`. The first time the property is accessed, `computeFn()` is called, the result is cached by replacing the accessor with a plain data property, and subsequent accesses return the cached value without calling `computeFn` again.

```js
let computeCount = 0;
const data = {};
lazyCompute(data, 'result', () => {
  computeCount++;
  return 42 * 42; // expensive computation (simulated)
});

console.log(computeCount);   // 0 — not yet computed
console.log(data.result);    // 1764 — computed now
console.log(computeCount);   // 1
console.log(data.result);    // 1764 — from cache
console.log(computeCount);   // 1 (NOT called again)
```

### Pattern Recognition
Self-rewriting getter — the accessor descriptor replaces itself with a data descriptor on first invocation, permanently caching the result.

### Key Insight
The getter's `this` is the object on which the access occurs. `Object.defineProperty(this, prop, ...)` inside the getter creates/replaces the own property on that specific object — turning the accessor into a plain cached data property. For this to work, the initial descriptor must be `configurable: true` (so it can be replaced), and the new data descriptor should typically be `configurable: false` (to prevent accidental cache invalidation).

### Solution

```js
function lazyCompute(obj, prop, computeFn) {
  Object.defineProperty(obj, prop, {
    get() {
      // Compute the value once
      const value = computeFn();

      // Replace this accessor with a permanent data property
      Object.defineProperty(this, prop, {
        value,
        writable: false,      // cache is immutable
        enumerable: true,
        configurable: false   // no further reconfiguration of this property
      });

      return value;
    },
    enumerable: true,
    configurable: true // MUST be true so the getter can redefine itself
  });
}

// Verification
let calls = 0;
const mod = {};
lazyCompute(mod, 'heavyResult', () => {
  calls++;
  return calls * 1000; // would be expensive in reality
});

console.log(calls);         // 0
console.log(mod.heavyResult); // 1000 (calls=1)
console.log(calls);         // 1
console.log(mod.heavyResult); // 1000 (from data property, calls unchanged)
console.log(calls);         // 1 ✓ — computeFn was called exactly once

// After first access, it's a plain data property:
const desc = Object.getOwnPropertyDescriptor(mod, 'heavyResult');
console.log(desc.value);       // 1000
console.log(typeof desc.get);  // 'undefined' — no longer an accessor ✓
```

### Edge Cases
- **Object used as a prototype**: if `obj` is a prototype and `this` inside the getter refers to an instance (not the prototype itself), `Object.defineProperty(this, prop, ...)` caches the value on the **instance**, not the prototype — each instance computes and caches independently. This is usually the desired behavior (per-instance memoization).
- **`computeFn` throws**: if the computation throws, the accessor is NOT replaced (since `Object.defineProperty` is never reached), and subsequent accesses retry the computation — which may be desirable (retry on failure) or may compound failures (avoid by handling errors inside `computeFn`).
- **Concurrent access in synchronous JS**: JS is single-threaded, so there's no race condition here — the getter runs to completion before anything else executes.

### Follow-up Questions
- "What if the lazy-computed value can change over time (needs re-computation)?" → Don't replace with a data property — keep the getter but add a manual invalidation mechanism (e.g., a `clearCache()` function that re-installs the getter) or use a timeout-based expiry.
- "How does this pattern appear in real codebases?" → Node.js uses this internally for modules (computed properties resolved once on first require), browser environments use it for API detection (e.g., computing feature flags once and caching), and Babel/TypeScript use it in decorator output for memoized properties.

## Quick Reference — Pattern Decision Tree

```
Do you need control over a JavaScript property's behavior beyond simple value assignment?
│
├── NEED THE PROPERTY TO BE READ-ONLY (prevent assignment)?
│   └── Data descriptor with writable: false
│       (also set configurable: false to prevent re-enabling writability)
│
├── NEED THE PROPERTY HIDDEN FROM ITERATION / SERIALIZATION?
│   └── Any descriptor with enumerable: false
│       → hidden from for...in, Object.keys(), {...spread}, JSON.stringify()
│       → still accessible by direct property access and getOwnPropertyDescriptor
│
├── NEED THE PROPERTY TO BE COMPLETELY LOCKED (no changes, no deletion)?
│   └── Data descriptor with writable: false AND configurable: false
│       (or use Object.freeze() to apply this to all properties at once)
│
├── NEED A COMPUTED / DERIVED PROPERTY (value calculated on access)?
│   └── Accessor descriptor with get() function only (no set → effectively read-only)
│
├── NEED TO INTERCEPT / OBSERVE ASSIGNMENTS (side effect on write)?
│   └── Accessor descriptor with both get() and set()
│       → get: return the backing variable
│       → set: update backing variable AND trigger side effect
│
├── NEED EXPENSIVE COMPUTATION CACHED AFTER FIRST ACCESS?
│   └── Lazy getter: accessor descriptor that replaces itself on first access
│       via Object.defineProperty(this, prop, { value: result, ... }) inside get()
│       → requires configurable: true initially
│
├── NEED TO INSPECT A PROPERTY'S EXACT FLAGS?
│   └── Object.getOwnPropertyDescriptor(obj, prop)
│       → returns { value, writable, enumerable, configurable } or { get, set, enumerable, configurable }
│
├── NEED A FAITHFUL DEEP CLONE PRESERVING GETTERS/SETTERS?
│   └── Object.defineProperties(target, Object.getOwnPropertyDescriptors(source))
│       → Object.assign / spread LOSE getters/setters (copy the value, not the accessor)
│
└── APPLYING IMMUTABILITY TO A WHOLE OBJECT?
    ├── preventExtensions: no new properties can be added
    ├── seal: preventExtensions + configurable:false on all existing properties
    └── freeze: seal + writable:false on all existing data properties (SHALLOW)
```

## Common Bugs Checklist

Before shipping any `Object.defineProperty` usage, verify:

1. **Descriptor type conflict: not mixing `value`/`writable` with `get`/`set`?** — This throws a `TypeError` immediately; the error message is clear but easy to introduce accidentally when building descriptors dynamically.

2. **Default flags awareness: is `writable`, `enumerable`, `configurable` explicitly set to the intended value?** — `Object.defineProperty` defaults ALL flags to `false` for new properties; forgetting `enumerable: true` silently hides the property from `Object.keys()`, `for...in`, and `JSON.stringify()`.

3. **Existing property modification: are you inadvertently assuming unset fields default to `false`?** — When modifying an EXISTING property, unspecified fields RETAIN their current values — only the explicitly specified fields change. This is the opposite of the new-property default behavior.

4. **Non-configurable property re-definition: are you trying to re-define a property that is already `configurable: false`?** — This throws a `TypeError`; check with `getOwnPropertyDescriptor` before attempting to redefine if the property's configurability is uncertain.

5. **Lazy getter: is the initial descriptor `configurable: true`?** — Without `configurable: true`, the getter cannot replace itself with a data property (`Object.defineProperty` inside the getter would throw a `TypeError`).

6. **Getter/setter `this` context: called via a different receiver than expected?** — If the accessor is defined on a prototype and accessed via an instance, `this` is the instance. If the accessor is extracted and called as a standalone function (`const fn = obj.__lookupGetter__('prop'); fn()`), `this` is `undefined` in strict mode. Arrow functions cannot be used as `get`/`set` because they capture lexical `this` — always use regular `function` syntax for accessors.

7. **`Object.freeze` / `Object.seal` is SHALLOW — nested objects are NOT frozen?** — A common mistake is assuming `Object.freeze(config)` makes all nested objects immutable. Only the top-level properties are frozen; nested object references themselves are frozen (can't be reassigned) but their properties are still mutable.

8. **`Object.assign` / spread loses accessor properties: is a faithful copy intended?** — When copying objects with getters/setters, use `Object.defineProperties({}, Object.getOwnPropertyDescriptors(source))` instead of `Object.assign` or spread. The difference only manifests when the source has accessor properties, making it easy to miss in testing if test inputs happen to use only data properties.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to know that JavaScript properties are not just values — they are described by a **descriptor object** with up to six fields, that `Object.defineProperty` is the API for reading and writing these descriptors, and that the `writable`/`enumerable`/`configurable` flags each do one specific thing (not vague "immutability"). The most important distinction to state clearly is the **data vs. accessor descriptor dichotomy** and the fact that they are mutually exclusive. Practically, the three most common uses of `Object.defineProperty` in real codebases are: (1) defining non-enumerable internal properties, (2) defining read-only constants, and (3) implementing lazy getters or observable properties — being able to implement any of these from scratch under interview conditions, and to articulate why the specific descriptor flags chosen are necessary, is the marker of genuine fluency with this API.
