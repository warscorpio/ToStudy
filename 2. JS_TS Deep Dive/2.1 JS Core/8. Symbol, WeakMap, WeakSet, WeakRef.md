## Part 1 — Theory & Interview Q&A

### Section 1: Symbol — Fundamentals

**Q1. What is a Symbol, and what problem does it solve?**
A: A Symbol is a primitive data type introduced in ES6 whose primary guarantee is **guaranteed uniqueness** — every call to `Symbol()` produces a value that is not equal to any other value, ever, including other Symbols created with the same description. This solves the namespace collision problem: when multiple pieces of code need to add properties to the same object without risking overwriting each other's keys, Symbols provide keys that are guaranteed not to conflict.

```js
const id1 = Symbol('id');
const id2 = Symbol('id');

console.log(id1 === id2); // false — always, regardless of same description
console.log(typeof id1);  // "symbol" — a distinct primitive type
```

The description `'id'` passed to `Symbol()` is purely a debugging label — it appears in `Symbol.toString()` and DevTools but has no effect on uniqueness or equality.

**Q2. What are the key behavioral properties of Symbols?**
A: Four properties define Symbol's behavior:

- **Uniqueness**: `Symbol() !== Symbol()` always. No two Symbols are ever equal.
- **Non-enumerable when used as property keys**: Symbol-keyed properties do not appear in `for...in` loops, `Object.keys()`, `Object.values()`, `Object.entries()`, or `JSON.stringify()`. They are accessible via `Object.getOwnPropertySymbols()`.
- **Non-coercible to string**: attempting `'prefix_' + Symbol('x')` throws `TypeError`. Must explicitly call `.toString()` or `.description`. This prevents accidental string conversions.
- **Not auto-converted to string in template literals**: `` `${Symbol('x')}` `` also throws `TypeError` — same reason.

```js
const sym = Symbol('key');
const obj = { [sym]: 'secret', visible: 'public' };

console.log(Object.keys(obj));        // ['visible'] — Symbol hidden
console.log(JSON.stringify(obj));     // '{"visible":"public"}' — Symbol hidden
console.log(obj[sym]);                // 'secret' — accessible directly
console.log(Object.getOwnPropertySymbols(obj)); // [Symbol(key)]
```

**Q3. What is `Symbol.for()` and how does it differ from `Symbol()`?**
A: `Symbol.for(key)` looks up a **global Symbol registry** by the string `key`. If a Symbol with that key already exists in the registry, it returns the existing Symbol; otherwise it creates and registers a new one. This enables sharing the same Symbol across different modules, iframes, and even service workers within the same runtime.

```js
const s1 = Symbol.for('app.userId');
const s2 = Symbol.for('app.userId');
console.log(s1 === s2); // true — same registry entry

const local = Symbol('app.userId');
console.log(local === s1); // false — not in registry, always unique

// Retrieve the key for a registered Symbol
console.log(Symbol.keyFor(s1));    // 'app.userId'
console.log(Symbol.keyFor(local)); // undefined — not registered
```

Use `Symbol()` for truly private, per-module unique keys. Use `Symbol.for()` when the same Symbol needs to be shared across modules or iframes.

**Q4. What are well-known Symbols, and why do they matter?**
A: Well-known Symbols are built-in Symbols on the `Symbol` object (e.g., `Symbol.iterator`, `Symbol.toPrimitive`, `Symbol.hasInstance`) that JavaScript uses internally as "hook points" — objects can implement these to customize language-level behavior without adding string-keyed methods that might conflict with future JavaScript APIs.

```js
// Symbol.iterator: makes any object iterable
class Range {
  constructor(start, end) { this.start = start; this.end = end; }

  [Symbol.iterator]() {         // define iteration behavior
    let current = this.start;
    const end = this.end;
    return {
      next() {
        return current <= end
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      }
    };
  }
}

for (const n of new Range(1, 4)) console.log(n); // 1, 2, 3, 4
console.log([...new Range(1, 4)]); // [1, 2, 3, 4]

// Symbol.toPrimitive: control type coercion
class Money {
  constructor(amount, currency) { this.amount = amount; this.currency = currency; }

  [Symbol.toPrimitive](hint) {
    if (hint === 'number') return this.amount;
    if (hint === 'string') return `${this.amount} ${this.currency}`;
    return this.amount; // default
  }
}

const price = new Money(42, 'USD');
console.log(+price);        // 42   (numeric hint)
console.log(`${price}`);    // "42 USD" (string hint)
console.log(price + 10);    // 52  (default hint)

// Symbol.hasInstance: customize instanceof
class EvenNumber {
  static [Symbol.hasInstance](num) {
    return Number.isInteger(num) && num % 2 === 0;
  }
}

console.log(4 instanceof EvenNumber);  // true
console.log(5 instanceof EvenNumber);  // false
```

Other important well-known Symbols: `Symbol.asyncIterator` (async iteration), `Symbol.species` (subclass construction), `Symbol.toStringTag` (customize `Object.prototype.toString` output), `Symbol.isConcatSpreadable` (control `Array.prototype.concat` spreading).

**Q5. What is the practical use of Symbol as a "private-ish" property key?**
A: Symbols provide "soft privacy" — properties keyed by Symbols are hidden from the most common forms of property enumeration and serialization, making them practically private for most use cases. They're not truly private (accessible via `Object.getOwnPropertySymbols()` and `Reflect.ownKeys()`), but they won't appear in normal JSON serialization, `for...in`, or `Object.keys()`.

```js
// Library metadata — hidden from users of the object
const _version = Symbol('version');
const _internal = Symbol('internal');

class Widget {
  constructor(config) {
    this[_version] = '2.0.1';
    this[_internal] = { renderCount: 0 };
    this.name = config.name; // public
  }

  render() {
    this[_internal].renderCount++;
    console.log(`Rendering ${this.name} (v${this[_version]})`);
  }
}

const w = new Widget({ name: 'Button' });
console.log(JSON.stringify(w)); // {"name":"Button"} — internal state hidden
console.log(Object.keys(w));   // ['name'] — Symbols not enumerated
```

For true private fields, use ES2022 class private fields (`#field`) — those are genuinely inaccessible outside the class. Symbols are the historical approach to "soft privacy" before private fields were standardized.

### Section 2: WeakMap — Fundamentals

**Q6. What is a WeakMap, and how does it differ from a regular Map?**
A: A WeakMap is a collection of key-value pairs where **keys must be objects** (or non-registered Symbols in ES2023+) and the references to those keys are **weak** — they do not prevent the key objects from being garbage collected. When a key object has no other strong references pointing to it, the GC can collect it, and the corresponding entry is automatically removed from the WeakMap. The WeakMap "lets go" of entries when their keys become unreachable.

Key differences from Map:

| Aspect | Map | WeakMap |
|---|---|---|
| Key types | Any value (primitives or objects) | Objects only (+ non-registered Symbols in ES2023) |
| Reference type | Strong (prevents GC) | Weak (allows GC) |
| Enumerable | Yes (`forEach`, `keys()`, `values()`, `entries()`) | No — not iterable |
| `size` property | Yes | No |
| GC interaction | Holds keys alive | Allows keys to be GC'd |
| Serializable | Yes (via iteration) | No |

```js
const map = new Map();
const weakMap = new WeakMap();

let obj = { name: 'Alice' };
map.set(obj, 'data');
weakMap.set(obj, 'data');

obj = null; // remove the strong reference

// map still holds obj alive — memory leak potential
// weakMap allows obj to be GC'd — entry removed automatically
```

**Q7. What operations does WeakMap support?**
A: WeakMap has exactly four methods — no iteration, no size:

```js
const wm = new WeakMap();
const key = {};

wm.set(key, 'value');    // associate value with key object
wm.get(key);             // retrieve value for key → 'value'
wm.has(key);             // check if key is present → true
wm.delete(key);          // remove the entry → true (success)

// NOT available:
// wm.size        — undefined
// wm.forEach()   — not a function
// wm.keys()      — not iterable
```

The intentional absence of enumeration is not an oversight — it's fundamental to the WeakMap contract. If you could enumerate WeakMap keys, the runtime would need to keep track of all keys (preventing GC). Non-enumerability enables the weak reference semantics.

**Q8. What are the canonical use cases for WeakMap?**
A: Three core use cases:

**1. Storing private data associated with objects (pre-ES2022 class private fields)**:
```js
const _private = new WeakMap();

class SecureCounter {
  constructor() {
    _private.set(this, { count: 0 }); // stored privately, outside the instance
  }

  increment() { _private.get(this).count++; }
  get value() { return _private.get(this).count; }
}

const c = new SecureCounter();
c.increment();
console.log(c.value); // 1
console.log(_private.get(c)); // accessible if you have the WeakMap reference
// But the WeakMap module isn't exported, so external code can't access it
```

When a `SecureCounter` instance is GC'd, the WeakMap entry is automatically cleaned up — no manual teardown needed.

**2. Caching/memoization keyed by objects**:
```js
const cache = new WeakMap();

function processExpensive(obj) {
  if (cache.has(obj)) return cache.get(obj); // cache hit

  const result = /* expensive computation */ obj.data.reduce(...);
  cache.set(obj, result);                    // cache miss — store result
  return result;
}

// When 'obj' is no longer needed elsewhere,
// its cache entry is automatically evicted — no cache invalidation needed
```

If the cache were a regular Map, holding references to `obj` would prevent GC, creating a memory leak. WeakMap avoids this entirely.

**3. Metadata/augmentation without modifying the object**:
```js
const metadata = new WeakMap();

function trackClicks(element) {
  metadata.set(element, { clickCount: 0, lastClick: null });
  element.addEventListener('click', () => {
    const data = metadata.get(element);
    data.clickCount++;
    data.lastClick = new Date();
  });
}

// When element is removed from DOM and has no other references,
// WeakMap entry and click tracking data are automatically cleaned up
```

### Section 3: WeakSet — Fundamentals

**Q9. What is a WeakSet, and what problem does it solve?**
A: A WeakSet is a collection of **unique objects** (no primitive values) with weak references — objects in the WeakSet can be garbage collected when they have no other strong references. Unlike WeakMap (key → value), WeakSet is a set — it just tracks membership (is this object in the set?), with no associated values.

```js
const ws = new WeakSet();
const obj = { name: 'Alice' };

ws.add(obj);    // add object
ws.has(obj);    // true
ws.delete(obj); // remove
ws.has(obj);    // false

// Not available: ws.size, ws.forEach(), iteration
```

**Q10. What are the canonical use cases for WeakSet?**
A: Two primary use cases:

**1. Tracking object membership without preventing GC**:
```js
const processedRequests = new WeakSet();

function handleRequest(req) {
  if (processedRequests.has(req)) {
    console.log('Already processed');
    return;
  }

  processedRequests.add(req);
  // ... process request
}
// When 'req' object is discarded after the request cycle,
// it's automatically removed from processedRequests — no cleanup needed
```

**2. Preventing circular recursion / marking objects as "visited"**:
```js
const seen = new WeakSet();

function deepClone(obj) {
  if (seen.has(obj)) throw new Error('Circular reference detected');
  seen.add(obj);

  const clone = {};
  for (const [key, val] of Object.entries(obj)) {
    clone[key] = typeof val === 'object' && val !== null
      ? deepClone(val)
      : val;
  }
  // No need to remove from seen — WeakSet cleans up when obj is GC'd
  return clone;
}
```

**3. Tagging DOM elements for special treatment without polluting them**:
```js
const animating = new WeakSet();

function startAnimation(element) {
  if (animating.has(element)) return; // already animating — skip
  animating.add(element);
  element.classList.add('animating');
}

function stopAnimation(element) {
  animating.delete(element);
  element.classList.remove('animating');
}

// When element is removed from DOM, WeakSet entry auto-removed — no leak
```

### Section 4: WeakRef — Fundamentals

**Q11. What is WeakRef and when was it introduced?**
A: `WeakRef` (ES2021) provides a weak reference to an object — it allows you to hold a reference to an object without preventing it from being garbage collected. Unlike WeakMap and WeakSet (which hold weak references implicitly as internal implementation details), `WeakRef` gives the developer **direct access to a potentially-collected reference** via the `.deref()` method.

```js
let obj = { name: 'ephemeral' };
const ref = new WeakRef(obj); // weak reference — doesn't prevent GC

// Dereference: returns the object if still alive, undefined if GC'd
const live = ref.deref();
if (live !== undefined) {
  console.log(live.name); // 'ephemeral' — still alive
} else {
  console.log('Object was garbage collected');
}

obj = null; // remove the strong reference
// Now the object MAY be GC'd — ref.deref() may return undefined
```

**Q12. What are the key caveats and guarantees of WeakRef?**
A: `WeakRef` comes with important caveats that make it different from all other JS primitives:

- **No timing guarantee**: the GC may collect the object at any time after all strong references are dropped. You cannot predict or control when `deref()` will return `undefined`. Between two calls to `deref()`, the result can change from the object to `undefined`.
- **Always check before using**: every use of `ref.deref()` must check for `undefined`. Failing to check causes `TypeError` when trying to access properties of `undefined`.
- **Not guaranteed to be collected**: the GC is not required to collect an object just because only weak references remain. In practice, objects are collected eventually, but the spec allows them to remain alive indefinitely. Don't use `WeakRef` as a guarantee that memory will be freed at a specific time.
- **The GC is non-deterministic**: in the same JavaScript engine, two runs of the same code may produce different deref() results at the same line, depending on GC timing.

```js
const ref = new WeakRef({ data: [1, 2, 3] });

// WRONG — unsafe access without null check
console.log(ref.deref().data); // may throw TypeError if GC'd

// CORRECT — always check
const obj = ref.deref();
if (obj) {
  console.log(obj.data);
} else {
  // handle the case where the object was collected
  console.log('Object no longer available');
}
```

**Q13. What is `FinalizationRegistry` and how does it complement WeakRef?**
A: `FinalizationRegistry` (ES2021, same proposal as WeakRef) allows you to register a callback that fires after a registered object is garbage collected. It's the mechanism to "react to GC" — useful for cleanup operations.

```js
const registry = new FinalizationRegistry((heldValue) => {
  // called AFTER the registered object is GC'd
  // heldValue is the second argument passed to register()
  console.log(`Object was GC'd. Cleanup token: ${heldValue}`);
});

let obj = { name: 'tracked' };
registry.register(obj, 'cleanup-token-42'); // register with cleanup data

obj = null; // remove strong reference
// At some future GC cycle: "Object was GC'd. Cleanup token: cleanup-token-42"
```

**Important constraints**:
- The callback is called asynchronously after GC — you cannot rely on exact timing.
- The callback receives the `heldValue` (second arg to `register()`), NOT the collected object (which is already gone by the time the callback fires).
- The callback may never fire at all if the program ends before the GC runs.
- Do not use `FinalizationRegistry` for logic that must execute — only for best-effort cleanup (e.g., closing a file handle that wasn't explicitly closed, logging).

```js
// Practical: cache with automatic cleanup notification
class CacheWithCleanup {
  #cache = new Map();
  #registry = new FinalizationRegistry((key) => {
    this.#cache.delete(key); // clean up stale key
    console.log(`Cache entry for ${key} auto-expired`);
  });

  set(key, obj) {
    const ref = new WeakRef(obj);
    this.#cache.set(key, ref);
    this.#registry.register(obj, key); // when obj is GC'd, delete cache entry
  }

  get(key) {
    const ref = this.#cache.get(key);
    if (!ref) return undefined;
    const obj = ref.deref();
    if (obj === undefined) {
      this.#cache.delete(key); // proactively clean up
      return undefined;
    }
    return obj;
  }
}
```

### Section 5: Comparison, Memory & Patterns

**Q14. Compare WeakMap, WeakSet, and WeakRef — when do you use each?**
A:

| Tool | Stores | Access Pattern | Use Case |
|---|---|---|---|
| `WeakMap` | key → value (key is object) | `get(key)` when you have the key | Private data, caching, metadata keyed by objects |
| `WeakSet` | set of objects (membership only) | `has(obj)`, `add(obj)`, `delete(obj)` | Tracking "seen" objects, dedup, tagging |
| `WeakRef` | single object reference | `deref()` — may return undefined | Optional cache, large object references with fallback |

Choose based on what you're associating:
- Need to associate **data with an object** → `WeakMap`
- Need to track **whether an object is in a group** → `WeakSet`
- Need a **direct optional handle** to an object → `WeakRef`

**Q15. Why can't WeakMap, WeakSet, or WeakRef hold primitive values?**
A: Primitives (numbers, strings, booleans, null, undefined, Symbols from the global registry) are either:
- Immortal (null, undefined, true, false — a finite set, never GC'd)
- Interned or pooled (small integers, string literals — shared instances)
- Value-type semantics (comparing two strings `"abc" === "abc"` is true regardless of identity)

Weak references are meaningful only for objects — where identity matters (`{} !== {}` even with the same content) and where GC is relevant (objects live on the heap and are collected when unreachable). A weak reference to a primitive would be semantically meaningless (primitives aren't "collected") and would make the `has()` / `get()` lookup ambiguous (which `"hello"` would you be checking for?).

**Q16. How do WeakMap and WeakSet interact with the garbage collector — what is a "weak reference" at the engine level?**
A: A strong reference is a pointer that the GC's reachability analysis considers when deciding whether an object is live. A weak reference is a pointer that the GC's reachability analysis **ignores** — it does not prevent the referent from being collected.

When the GC runs its mark phase: it starts from roots (global variables, call stack, closures) and follows strong references to mark all reachable objects. WeakMap entries and WeakSet entries whose keys/objects are not marked as reachable (only weakly referenced) are then eligible for collection and are pruned during the sweep phase. The entry disappears from the WeakMap/WeakSet — future `has()` or `get()` calls return `false`/`undefined` for that key.

V8 (Chrome/Node) implements this with "ephemeron" tables — WeakMap entries where the key is not reachable are treated as garbage even during incremental GC, without blocking progress.

**Q17. What is the "associated metadata" pattern with WeakMap?**
A: A well-known architectural pattern: instead of adding properties directly to objects (which modifies them) or using a regular Map (which prevents GC), use a WeakMap to associate metadata with objects you don't own:

```js
// PATTERN: library augments third-party objects without modifying them
const eventListeners = new WeakMap(); // DOM element → listener registry

export function addTrackedListener(element, type, handler) {
  if (!eventListeners.has(element)) {
    eventListeners.set(element, {});
  }
  const listeners = eventListeners.get(element);
  if (!listeners[type]) listeners[type] = [];
  listeners[type].push(handler);
  element.addEventListener(type, handler);
}

export function removeAllListeners(element) {
  const listeners = eventListeners.get(element);
  if (!listeners) return;
  for (const [type, handlers] of Object.entries(listeners)) {
    handlers.forEach(h => element.removeEventListener(type, h));
  }
  eventListeners.delete(element);
}

// When element is removed from DOM and garbage collected,
// the WeakMap entry and all listener data are freed automatically
```

### Section 6: Scenario / Interview-Style Questions

**Q18. "Explain the difference between `Symbol()` and `Symbol.for()` and when you'd use each."**
A: `Symbol()` creates a new unique Symbol every time — it is NEVER equal to any other Symbol, even one created with the same description. Use it when you need a key that is guaranteed not to conflict with anything else, private to the module that creates it (since only code with access to the Symbol variable can use it as a key).

`Symbol.for(key)` looks up or creates a Symbol in a shared global registry. Two calls to `Symbol.for('app.user')` in different modules return the exact same Symbol. Use it when the same Symbol needs to be shared: between multiple modules that coordinate using a protocol, between the main page and iframes (they share the global registry), or when implementing a well-known Symbol-based protocol across a codebase.

The decision rule: if you need the Symbol to be recognizable across module boundaries or contexts → `Symbol.for()`. If you need a unique per-module key that's safe from external interference → `Symbol()`.

**Q19. "When would you use a WeakMap over a regular Map for caching?"**
A: Use WeakMap for caching when the **cache lifetime should be tied to the lifetime of the key objects**. If the objects being cached are DOM nodes, request objects, or any other object that gets discarded when no longer needed, a regular Map would hold those objects alive indefinitely (memory leak). A WeakMap's entries are automatically evicted when the key objects are GC'd.

Use a regular Map when:
- Cache keys are primitives (strings, numbers) — WeakMap doesn't support primitives.
- You need to enumerate the cache (WeakMap is not iterable).
- You need cache size management (LRU eviction, TTL) — WeakMap provides no enumeration for such bookkeeping.
- Cache entries should persist even if the key object has no other references (rare, but valid use case).

**Q20. "You're reviewing a PR where a developer uses `new WeakRef(obj)` and accesses `ref.deref().property` directly. What's wrong?"**
A: The direct access `ref.deref().property` has no null check between `deref()` and the property access. If the object has been GC'd, `deref()` returns `undefined`, and accessing `.property` on `undefined` throws `TypeError: Cannot read properties of undefined`. Since the GC is non-deterministic, this may work in development (where GC runs infrequently and objects stay alive) but fail sporadically in production (under memory pressure, GC runs more aggressively). The fix:

```js
// WRONG
ref.deref().property; // TypeError if GC'd

// CORRECT
const obj = ref.deref();
if (obj !== undefined) {
  obj.property;
} else {
  // handle the stale reference case
}

// OR with optional chaining (but be careful — undefined result may be ambiguous)
ref.deref()?.property; // returns undefined if GC'd OR if property is undefined
```

Also flag: why is `WeakRef` needed here? If the object is frequently needed, a strong reference is more appropriate. `WeakRef` is for optional caching scenarios where the object can be dropped and recomputed.

**Q21. "Describe a situation where Symbol-keyed properties are the right solution vs class private fields (#)."**
A: **Use Symbols when**:
- You need to add "hidden" metadata to objects you don't control (third-party objects, plain objects from external sources).
- You're building a mixin or decorator that needs to store state on an object without namespace conflicts — class private fields can't do this across multiple classes.
- You want soft privacy that can still be inspected by debugging tools via `Object.getOwnPropertySymbols()`.
- You're implementing or hooking into well-known Symbol protocols (`Symbol.iterator`, etc.).

**Use class private fields (`#`) when**:
- Truly private state on instances of a specific class — no access from outside, ever.
- The field only needs to be on instances of one class (not across arbitrary objects).
- You want hard privacy (inaccessible even via reflection).

```js
// Symbol: cross-object metadata (any object can have this)
const _meta = Symbol('meta');
function attach(obj, data) { obj[_meta] = data; }

// Class private field: strictly per-class
class User {
  #password; // only User instances have this, truly private
  constructor(pass) { this.#password = pass; }
  verify(pass) { return this.#password === pass; }
}
```

**Q22. "What are the risks of overusing WeakRef and FinalizationRegistry?"**
A: Several serious risks:

- **Non-deterministic behavior**: GC timing varies between engines, devices, and memory states. Code that works in Chrome may behave differently in Firefox, Node, or Deno. Features implemented with `WeakRef` become hard to test and debug.
- **Logic depending on GC timing**: if your application's correctness depends on the FinalizationRegistry callback firing at a specific time, you have a latent bug. The callback may fire late, early relative to other async operations, or not at all before process exit.
- **Test complexity**: unit tests can't reliably trigger GC at specific points, making WeakRef-dependent paths hard to test. Some engines expose `gc()` in test environments, but it's not standard.
- **Obfuscated lifecycle**: WeakRef makes object lifetimes implicit. When reading code, a strong reference tells you explicitly "this object is kept alive here." WeakRef hides this, making memory profiling harder.

The TC39 advice: treat `WeakRef` and `FinalizationRegistry` as tools of last resort for specific memory optimization scenarios, not as general-purpose features. For most caching scenarios, an explicit eviction strategy (LRU, TTL, manual delete) is more predictable.

## Problem 1 — Non-Colliding Extension Keys with Symbol

### Problem
You're building a library that adds metadata to user-provided objects. The library shouldn't modify any string properties of the object (to avoid conflicts with user properties), and the metadata should be hidden from `JSON.stringify` and `for...in` enumeration.

```js
// User's object — you don't control its structure
const userObj = { name: 'Alice', role: 'admin' };

// Library usage
attachMeta(userObj, { createdAt: Date.now(), source: 'api' });
getMeta(userObj); // → { createdAt: ..., source: 'api' }

JSON.stringify(userObj); // → '{"name":"Alice","role":"admin"}' — no leakage
for (const key in userObj) console.log(key); // only 'name', 'role' — no leakage
```

### Pattern Recognition
Symbol as property key — guarantees uniqueness (no collision with user's string keys), non-enumerable by default (hidden from `for...in` and `JSON.stringify`).

### Key Insight
A Symbol key is unique and non-enumerable. Storing library metadata under a Symbol key doesn't modify any string-keyed property and stays invisible to the most common inspection operations. The Symbol is module-private (not exported), so external code can't access it by name.

### Solution

```js
// Internal Symbol — unique to this module, never exported
// Using Symbol() not Symbol.for() — we don't want sharing across modules
const META_KEY = Symbol('libraryMeta');

function attachMeta(obj, metadata) {
  // Symbol-keyed assignment — non-enumerable, non-colliding
  obj[META_KEY] = metadata;
}

function getMeta(obj) {
  return obj[META_KEY]; // undefined if never attached
}

function hasMeta(obj) {
  return META_KEY in obj; // 'in' operator checks Symbol keys too
}

function removeMeta(obj) {
  delete obj[META_KEY];
}

// ─── Usage ────────────────────────────────────────────────────────────────

const user = { name: 'Alice', role: 'admin' };

attachMeta(user, { createdAt: 1700000000000, source: 'api' });

console.log(getMeta(user));      // { createdAt: 1700000000000, source: 'api' }
console.log(hasMeta(user));      // true

// Hidden from common enumeration
console.log(JSON.stringify(user)); // '{"name":"Alice","role":"admin"}'
console.log(Object.keys(user));    // ['name', 'role']
for (const k in user) console.log(k); // 'name', 'role'

// Still accessible via reflection
console.log(Object.getOwnPropertySymbols(user)); // [Symbol(libraryMeta)]
console.log(Reflect.ownKeys(user));  // ['name', 'role', Symbol(libraryMeta)]
```

### Dry Run

```
META_KEY = Symbol('libraryMeta')  ← created once when module loads

user = { name: 'Alice', role: 'admin' }

attachMeta(user, { createdAt: 1700000000000, source: 'api' }):
  user[Symbol('libraryMeta')] = { createdAt: 1700000000000, source: 'api' }
  user is now: {
    name: 'Alice',           ← string key, enumerable
    role: 'admin',           ← string key, enumerable
    [Symbol('libraryMeta')]: { ... }  ← Symbol key, non-enumerable
  }

JSON.stringify(user):
  serializes only string-keyed enumerable properties
  → '{"name":"Alice","role":"admin"}'  ✓

getMeta(user):
  user[META_KEY] → { createdAt: 1700000000000, source: 'api' }  ✓
```

### Gotchas
- `Object.getOwnPropertySymbols()` and `Reflect.ownKeys()` CAN see the Symbol key — not truly private, just non-enumerable. For truly private, use ES2022 class private fields or a WeakMap.
- If you `JSON.parse(JSON.stringify(user))`, the metadata is lost — the round-trip strips Symbol keys. This is often desirable (serialized form is clean) but can surprise developers.
- `Object.assign({}, user)` and spread `{...user}` copy string enumerable properties but NOT Symbol-keyed ones. Again, often desired but worth knowing.

### Follow-up Questions
- "What if you need the metadata to survive a `JSON.stringify` round-trip?" → Store metadata in a separate WeakMap keyed by the object instead of on the object itself.
- "What if two different library versions both use `Symbol('libraryMeta')`?" → No conflict — each `Symbol()` call produces a unique Symbol regardless of the description. Two library instances will each have their own unique META_KEY.

## Problem 2 — Private Class State with WeakMap

### Problem
Implement a `BankAccount` class where the balance is truly inaccessible from outside the class (no string property that can be read or written directly). Account instances should be GC-friendly — when an instance is no longer referenced, its private data should also be freed.

```js
const account = new BankAccount(100);
account.deposit(50);
account.withdraw(30);
console.log(account.balance); // 120
account.balance = 9999;       // should have no effect
console.log(account.balance); // still 120
```

### Pattern Recognition
WeakMap for private state — the canonical pre-ES2022 pattern for truly module-private data. The WeakMap is declared in the module scope (not on the class), so external code has no reference to it and cannot access the private state.

### Key Insight
The WeakMap stores `instance → privateData` mappings. Since the WeakMap variable is not exported, external code has no way to call `weakMap.get(account)`. The WeakMap reference type also means private data is freed when the instance is GC'd — no memory leak even if instances are abandoned.

### Solution

```js
// Module-private WeakMap — inaccessible from outside this module
const _state = new WeakMap();

class BankAccount {
  constructor(initialBalance) {
    if (initialBalance < 0) throw new Error('Initial balance cannot be negative');

    // Store private state in the WeakMap keyed by 'this'
    _state.set(this, {
      balance: initialBalance,
      transactions: []
    });
  }

  deposit(amount) {
    if (amount <= 0) throw new Error('Deposit amount must be positive');
    const state = _state.get(this);
    state.balance += amount;
    state.transactions.push({ type: 'deposit', amount, time: Date.now() });
    return this; // enable chaining
  }

  withdraw(amount) {
    if (amount <= 0) throw new Error('Withdrawal amount must be positive');
    const state = _state.get(this);
    if (amount > state.balance) throw new Error('Insufficient funds');
    state.balance -= amount;
    state.transactions.push({ type: 'withdrawal', amount, time: Date.now() });
    return this;
  }

  get balance() {
    return _state.get(this).balance; // read-only via getter
    // No setter defined — assignment is silently ignored (non-strict)
    // or throws in strict mode if we define it
  }

  get transactionHistory() {
    // Return a copy — prevent external mutation of internal array
    return [..._state.get(this).transactions];
  }

  toString() {
    return `BankAccount(balance: ${this.balance})`;
  }
}

// ─── Usage ────────────────────────────────────────────────────────────────

const account = new BankAccount(100);
account.deposit(50).withdraw(30); // chaining
console.log(account.balance);     // 120

account.balance = 9999;           // no setter — silently ignored
console.log(account.balance);     // still 120

// No way to access _state from outside the module
// _state is not accessible, WeakMap is not exported
console.log(Object.keys(account));    // [] — no enumerable properties
console.log(JSON.stringify(account)); // '{}'

// Private data auto-freed when account is GC'd
let acc2 = new BankAccount(500);
acc2.deposit(100);
acc2 = null; // _state entry for acc2 is automatically removed
```

### Dry Run

```
_state = WeakMap {} ← module-level, not exported

new BankAccount(100):
  _state.set(this, { balance: 100, transactions: [] })
  _state = WeakMap { BankAccount#1 → { balance: 100, transactions: [] } }

account.deposit(50):
  state = _state.get(account) → { balance: 100, transactions: [] }
  state.balance = 150
  state.transactions.push({ type: 'deposit', amount: 50, ... })
  return account (this)

account.withdraw(30):
  state = _state.get(account) → { balance: 150, ... }
  150 >= 30 → ok
  state.balance = 120
  state.transactions.push({ type: 'withdrawal', amount: 30, ... })

account.balance:
  _state.get(account).balance → 120  ✓

account.balance = 9999:
  no setter defined → no-op (strict mode: TypeError, sloppy mode: silently ignored)
  _state.get(account).balance → still 120  ✓
```

### Comparison: WeakMap vs Class Private Fields

```js
// Modern ES2022+ — class private fields (preferred for new code)
class BankAccountModern {
  #balance;
  #transactions = [];

  constructor(initial) { this.#balance = initial; }

  deposit(amount) { this.#balance += amount; return this; }
  get balance() { return this.#balance; }

  // Outside access: account.#balance → SyntaxError (hard private)
}
```

Class private fields (`#`) are now the preferred approach — they're truly private (SyntaxError to access from outside), syntax is cleaner, and no WeakMap overhead. Use WeakMap pattern for: older codebase/targets without private field support, cross-object private state, or mixin patterns where a single WeakMap tracks state across multiple different class types.

### Gotchas
- The WeakMap key is `this` — if `this` is ever null or undefined (e.g., method called without proper binding), `_state.get(this)` returns `undefined` and accessing `.balance` on it throws. Arrow methods or explicit binding prevent this.
- Subclass instances: if a subclass calls `super()`, `this` is the subclass instance — `_state.set(this, ...)` stores under the subclass instance. Each call to `new SubBankAccount()` correctly stores the state under that specific instance.

### Follow-up Questions
- "Why not just use a closure?" → Closures store private state per-instance in the closure scope, requiring a factory function instead of a class. WeakMap separates private state from the class structure, allowing proper inheritance and prototype-based methods.
- "What's the memory overhead of WeakMap?" → One WeakMap entry per instance. Comparable to any property access. The overhead is the WeakMap infrastructure itself (hash table), which is fixed per WeakMap.

## Problem 3 — Implementing Symbol.iterator (Custom Iterable)

### Problem
Implement a `LinkedList` class that is iterable using `for...of`, spread operator, and destructuring assignment. The list should not expose its internal node structure.

```js
const list = new LinkedList();
list.push(1).push(2).push(3);

for (const val of list) console.log(val); // 1, 2, 3
console.log([...list]);                   // [1, 2, 3]
const [first, second] = list;
console.log(first, second);              // 1, 2
```

### Pattern Recognition
`Symbol.iterator` — the well-known Symbol that makes any object iterable. By implementing `[Symbol.iterator]()` on the class, the object plugs into the JavaScript iteration protocol used by `for...of`, spread, destructuring, `Array.from()`, etc.

### Key Insight
The iteration protocol requires `[Symbol.iterator]()` to return an iterator object with a `next()` method that returns `{ value, done }` pairs. Using a generator function (`function*`) makes implementing this trivial — `yield` handles the `{ value, done }` wrapping automatically.

### Solution

```js
class Node {
  constructor(value) {
    this.value = value;
    this.next = null;
  }
}

class LinkedList {
  #head = null;
  #tail = null;
  #size = 0;

  push(value) {
    const node = new Node(value);
    if (!this.#tail) {
      this.#head = this.#tail = node;
    } else {
      this.#tail.next = node;
      this.#tail = node;
    }
    this.#size++;
    return this; // enable chaining
  }

  get size() { return this.#size; }

  // ── Symbol.iterator: makes LinkedList iterable ────────────────────────
  [Symbol.iterator]() {
    let current = this.#head; // captured in closure — iteration state

    return {
      next() {
        if (current === null) {
          return { value: undefined, done: true }; // exhausted
        }
        const value = current.value;
        current = current.next; // advance
        return { value, done: false };
      },

      // Optional: make the iterator itself iterable (common convention)
      [Symbol.iterator]() { return this; }
    };
  }

  // ── Generator-based equivalent (cleaner syntax) ────────────────────
  *[Symbol.iterator]() {            // generator method shorthand
    let current = this.#head;
    while (current !== null) {
      yield current.value;           // yield = next() returning { value, done:false }
      current = current.next;
    }
    // generator return = { value: undefined, done: true } automatically
  }
}

// ─── Usage ────────────────────────────────────────────────────────────

const list = new LinkedList();
list.push(10).push(20).push(30);

// for...of uses [Symbol.iterator]()
for (const val of list) console.log(val); // 10, 20, 30

// Spread uses [Symbol.iterator]()
console.log([...list]); // [10, 20, 30]

// Destructuring uses [Symbol.iterator]()
const [a, b, c] = list;
console.log(a, b, c); // 10, 20, 30

// Array.from uses [Symbol.iterator]()
console.log(Array.from(list)); // [10, 20, 30]

// Multiple independent iterations (each creates a fresh iterator)
const iter1 = list[Symbol.iterator]();
const iter2 = list[Symbol.iterator]();
console.log(iter1.next()); // { value: 10, done: false }
console.log(iter2.next()); // { value: 10, done: false } — independent state
console.log(iter1.next()); // { value: 20, done: false }
```

### Dry Run

```
list = LinkedList { #head → Node(10) → Node(20) → Node(30) → null }

for (const val of list):
  JS calls list[Symbol.iterator]() → returns iterator with current=Node(10)

  Iteration 1: iterator.next()
    current = Node(10), not null
    value = 10, advance current to Node(20)
    return { value: 10, done: false }
    → val = 10, console.log(10)

  Iteration 2: iterator.next()
    current = Node(20)
    return { value: 20, done: false }
    → val = 20, console.log(20)

  Iteration 3: iterator.next()
    current = Node(30)
    return { value: 30, done: false }

  Iteration 4: iterator.next()
    current = null
    return { value: undefined, done: true }
    → loop terminates

[...list]:
  Same iteration, collected into array → [10, 20, 30] ✓
```

### Gotchas
- Each `list[Symbol.iterator]()` call must return a **new** iterator with its own state (the `current` pointer). Sharing state between iterators would cause `[...list]` to behave differently when called multiple times on the same list.
- The generator version (`*[Symbol.iterator]()`) handles this automatically — each `list[Symbol.iterator]()` call creates a fresh generator object with its own execution context.
- Modifying the list during iteration (adding/removing nodes) is a concurrent modification — behavior depends on your implementation. The simple closure-based iterator will reflect changes after the current node.

### Follow-up Questions
- "Implement async iteration (`for await...of`)?" → Implement `[Symbol.asyncIterator]()` returning an async iterator whose `next()` returns a `Promise<{ value, done }>`.
- "Make it support `Symbol.iterator` both forward and backward?" → Implement two methods: `[Symbol.iterator]()` for forward, `reverseIterator()` or another Symbol for backward.

## Problem 4 — Memoization Cache with WeakRef and FinalizationRegistry

### Problem
Implement a `memoize` function that caches results keyed by object arguments. The cache should not prevent objects from being GC'd (no memory leaks), and stale cache entries should be automatically cleaned up.

```js
function computeStats(dataSet) { /* expensive */ }
const memoized = memoize(computeStats);

let data = { values: [1, 2, 3, 4, 5] };
memoized(data); // computed
memoized(data); // cache hit
data = null;    // cache entry for old data should eventually free itself
```

### Pattern Recognition
WeakRef + FinalizationRegistry — WeakRef allows the cache key object to be GC'd; FinalizationRegistry cleans up the stale cache entry after GC. This pattern creates a "best-effort" cache that doesn't hold objects alive.

### Key Insight
We can't use a WeakMap here because we need to enumerate or check cache entries for cleanup. Instead, use a regular Map with WeakRef keys. When an object is GC'd, the FinalizationRegistry fires and we delete the stale Map entry using a unique token.

### Solution

```js
function memoize(fn) {
  // Regular Map from unique token → { ref: WeakRef, result }
  const cache = new Map();

  // Counter to generate unique tokens per cache entry
  let tokenCounter = 0;

  // WeakRef keys: we need a way to look up cache entry from the object
  // We'll store the token ON the object via Symbol (module-private)
  const TOKEN_KEY = Symbol('cacheToken');

  // FinalizationRegistry: called when a cached object is GC'd
  const registry = new FinalizationRegistry((token) => {
    cache.delete(token); // remove the now-stale cache entry
    // Optional: log or track cache misses for metrics
  });

  return function memoized(obj) {
    if (typeof obj !== 'object' || obj === null) {
      throw new Error('memoize only supports object arguments in this implementation');
    }

    // Check if this object already has a cache token
    let token = obj[TOKEN_KEY];

    if (token !== undefined && cache.has(token)) {
      const entry = cache.get(token);
      const cached = entry.ref.deref();

      if (cached !== undefined) {
        // Cache hit — object still alive, return stored result
        return entry.result;
      } else {
        // Object was GC'd but registry hasn't fired yet
        // (This is a race condition window — handle defensively)
        cache.delete(token);
      }
    }

    // Cache miss — compute and store
    token = ++tokenCounter;
    obj[TOKEN_KEY] = token; // stamp the object with its token (via Symbol)

    const result = fn(obj);

    cache.set(token, {
      ref: new WeakRef(obj), // weak reference — allows GC
      result
    });

    // Register for cleanup when obj is GC'd
    registry.register(obj, token);

    return result;
  };
}

// ─── Usage ────────────────────────────────────────────────────────────────

let callCount = 0;
function expensiveCompute(data) {
  callCount++;
  return data.values.reduce((a, b) => a + b, 0);
}

const memoized = memoize(expensiveCompute);

let dataset = { values: [1, 2, 3, 4, 5] };

console.log(memoized(dataset)); // 15 (computed, callCount=1)
console.log(memoized(dataset)); // 15 (cache hit, callCount still 1)
console.log(memoized(dataset)); // 15 (cache hit, callCount still 1)

dataset = null; // strong reference removed
// At some future GC: FinalizationRegistry fires, cache.delete(1) called
// cache is now empty again
```

### Gotchas
- **Race condition window**: between when an object is GC'd and when FinalizationRegistry fires, `cache.get(token)` returns an entry whose `ref.deref()` returns `undefined`. The defensive check handles this.
- **FinalizationRegistry timing is unpredictable**: in tests, you can't reliably verify that the cache was cleaned up (no way to trigger GC on demand in standard JS). Test the logic paths (cache hit, cache miss) but not the GC cleanup.
- **Symbol stamping modifies the object**: using `obj[TOKEN_KEY] = token` adds a (Symbol-keyed) property to the object. This is acceptable for this pattern but should be noted — some truly immutable or sealed objects (`Object.freeze()`, `Object.seal()`) would throw on this assignment.
- **Not suitable for production caching**: the non-deterministic cleanup means cache size is not predictable. For production, combine with explicit size limits and LRU eviction.

### Follow-up Questions
- "How would you test this without triggering actual GC?" → Mock the `FinalizationRegistry` — inject a fake registry that stores callbacks and call them manually in tests. Test the cache hit/miss logic separately from the GC cleanup logic.
- "Why not just use a WeakMap directly?" → WeakMap provides automatic key-based cleanup but requires you to have the key object to do a lookup. Memoization with WeakMap works when the argument IS the key — `cache.get(obj)`. This is actually simpler:

```js
// Simpler memoize using WeakMap directly (no FinalizationRegistry needed)
function memoizeSimple(fn) {
  const cache = new WeakMap();
  return function(obj) {
    if (cache.has(obj)) return cache.get(obj);
    const result = fn(obj);
    cache.set(obj, result);
    return result;
  };
}
// WeakMap entry is auto-cleaned when obj is GC'd — no FinalizationRegistry needed!
```

This simpler WeakMap approach is usually preferable. `WeakRef` + `FinalizationRegistry` is needed when the cache key can't be the object itself (e.g., you need to cache by a serialized string key but still want GC-friendly behavior for the values).

## Problem 5 — Cross-Module Protocol with Symbol.for

### Problem
You're building a plugin system where plugins from different npm packages need to agree on a shared interface. Implement a "serializable" protocol using `Symbol.for` so that any object implementing `[SERIALIZABLE]()` can be automatically serialized by a central serializer, regardless of which package defined the Symbol.

```js
// package-a/index.js
const widget = new Widget('button');
// package-b/serializer.js
serialize(widget); // should work even though Widget and serialize are from different packages

// Both packages use Symbol.for('app.serializable') to agree on the interface
```

### Pattern Recognition
`Symbol.for()` — global registry enables cross-module protocol agreements. Any package that does `Symbol.for('app.serializable')` gets the same Symbol, enabling duck-typing across package boundaries.

### Key Insight
`Symbol.for('app.serializable')` is the same Symbol in all modules loaded in the same JavaScript context, regardless of which module calls it or how many times. This makes it suitable for defining protocols that span module boundaries — exactly like how `Symbol.iterator` is a built-in shared protocol.

### Solution

```js
// ─── shared-protocol.js (or can be duplicated in each package) ────────────
// Both packages call Symbol.for() — they get the SAME Symbol
export const SERIALIZABLE = Symbol.for('myapp.serializable');
export const SCHEMA_VERSION = Symbol.for('myapp.schemaVersion');

// ─── package-a/widget.js ─────────────────────────────────────────────────
import { SERIALIZABLE, SCHEMA_VERSION } from './shared-protocol.js';
// OR directly: const SERIALIZABLE = Symbol.for('myapp.serializable');
// Both give the same Symbol — no import needed if you use Symbol.for directly

class Widget {
  constructor(type, config = {}) {
    this.type = type;
    this.config = config;
    this[SCHEMA_VERSION] = '1.0';
  }

  // Implement the serializable protocol
  [SERIALIZABLE]() {
    return {
      __type: 'Widget',
      __version: this[SCHEMA_VERSION],
      type: this.type,
      config: this.config
    };
  }

  static deserialize(data) {
    return new Widget(data.type, data.config);
  }
}

// ─── package-b/serializer.js ─────────────────────────────────────────────
const SERIALIZABLE = Symbol.for('myapp.serializable'); // same Symbol
const SCHEMA_VERSION = Symbol.for('myapp.schemaVersion');

function serialize(obj) {
  if (obj === null || obj === undefined) return JSON.stringify(obj);

  if (typeof obj[SERIALIZABLE] === 'function') {
    // Object implements the protocol — use it
    const data = obj[SERIALIZABLE]();
    return JSON.stringify(data);
  }

  // Fallback: default JSON serialization
  return JSON.stringify(obj);
}

function isSerializable(obj) {
  return obj !== null &&
         typeof obj === 'object' &&
         typeof obj[SERIALIZABLE] === 'function';
}

// ─── Usage ────────────────────────────────────────────────────────────────

const btn = new Widget('button', { label: 'Click me', color: 'blue' });

console.log(isSerializable(btn)); // true
console.log(serialize(btn));
// '{"__type":"Widget","__version":"1.0","type":"button","config":{"label":"Click me","color":"blue"}}'

// Non-serializable object — fallback
const plain = { x: 1, y: 2 };
console.log(serialize(plain)); // '{"x":1,"y":2}'

// Verify Symbol.for returns the same Symbol across "different modules"
const KEY_A = Symbol.for('myapp.serializable'); // simulating package-a
const KEY_B = Symbol.for('myapp.serializable'); // simulating package-b
console.log(KEY_A === KEY_B); // true — same Symbol from global registry
console.log(Symbol.keyFor(KEY_A)); // 'myapp.serializable'
```

### Dry Run

```
// Both packages call Symbol.for('myapp.serializable')
// JS engine checks global Symbol registry:
//   First call: 'myapp.serializable' not in registry → create Symbol, register it
//   Second call: 'myapp.serializable' found in registry → return same Symbol

KEY_A = Symbol(myapp.serializable)  ← registered
KEY_B = Symbol(myapp.serializable)  ← same reference returned
KEY_A === KEY_B  → true  ✓

// Widget implements [Symbol.for('myapp.serializable')]():
btn[SERIALIZABLE]():
  return { __type: 'Widget', __version: '1.0', type: 'button', config: {...} }

serialize(btn):
  typeof btn[SERIALIZABLE] === 'function'? → true
  data = btn[SERIALIZABLE]() → { __type: 'Widget', ... }
  JSON.stringify(data) → '{"__type":"Widget",...}'  ✓
```

### Gotchas
- **Namespace collisions**: `Symbol.for('myapp.serializable')` is global. If two completely unrelated libraries both use the same string key, they'll conflict. Use sufficiently namespaced keys (reverse domain notation: `'com.mycompany.myapp.serializable'`).
- **Key must be a string**: `Symbol.for(42)` coerces 42 to `'42'` — strings only for the registry key. Always use string literals to be explicit.
- **Across iframes**: `Symbol.for()` shares the registry within a single realm (global scope). Cross-origin iframes have separate realms and separate Symbol registries. For true cross-iframe sharing, use `postMessage` with agreed-upon string protocols.

### Follow-up Questions
- "Why not just use a string key like `'__serializable'` instead of a Symbol?" → String keys appear in `for...in`, `Object.keys()`, and `JSON.stringify()`. They can collide with user-defined properties or future JavaScript APIs. Symbol keys are invisible to standard enumeration and guaranteed unique across versions and packages.
- "What's the difference between this and a mixin or interface pattern?" → Symbols enable structural typing across independently-developed code without shared base classes or imported interfaces. Any object that implements `[SERIALIZABLE]()` works, regardless of its class hierarchy.

## Quick Reference — Symbol, WeakMap, WeakSet, WeakRef

```
SYMBOL
  Symbol()        → always unique, never equal to anything else
  Symbol.for(k)   → global registry lookup/create — shared across modules
  Symbol.keyFor() → retrieve key string for a registered Symbol
  Non-enumerable as property key: hidden from JSON.stringify, Object.keys, for...in
  Not coercible to string: 'prefix' + Symbol() throws TypeError
  Well-known Symbols: Symbol.iterator, Symbol.toPrimitive, Symbol.hasInstance, etc.

WEAKMAP
  Keys: objects only (no primitives)
  Methods: set(k,v), get(k), has(k), delete(k) — NO iteration, NO size
  Weak references: key objects can be GC'd; entry auto-removed
  Use for: private data, caching, metadata on objects you don't own

WEAKSET
  Values: objects only
  Methods: add(o), has(o), delete(o) — NO iteration, NO size
  Weak references: objects can be GC'd; auto-removed from set
  Use for: tracking membership without preventing GC

WEAKREF (ES2021)
  const ref = new WeakRef(obj)   — hold weak reference
  ref.deref()                    — returns obj or undefined (if GC'd)
  ALWAYS check deref() !== undefined before using
  Non-deterministic GC timing — cannot rely on when deref() returns undefined

FINALIZATIONREGISTRY (ES2021)
  const registry = new FinalizationRegistry(callback)
  registry.register(obj, heldValue)  — called after obj is GC'd
  Callback receives heldValue (not obj — it's already gone)
  Best-effort only — may not fire before program exit
  Use for: optional cleanup, logging — NOT for required logic

DECISION GUIDE
  Need unique non-colliding key? → Symbol()
  Need shared cross-module key? → Symbol.for()
  Need to customize language behavior? → Well-known Symbol
  Associate data with object, GC-friendly? → WeakMap
  Track object membership, GC-friendly? → WeakSet
  Optional handle to object (may be GC'd)? → WeakRef
  React to object being GC'd? → FinalizationRegistry
```

## Common Bugs Checklist

Before finalizing any code using these features, verify:

1. **WeakRef: always check `deref()` before accessing properties** — `ref.deref()?.property` (optional chaining) or an explicit `!== undefined` check. Accessing properties on a potentially-undefined deref result is the most common `WeakRef` bug — it fails silently in development (where GC rarely runs) and crashes intermittently in production.

2. **WeakMap/WeakSet: keys must be objects** — passing a primitive as a WeakMap key throws `TypeError: Invalid value used as weak map key`. Add a guard or assertion when the key type is not guaranteed.

3. **Symbol: use `Symbol()` not `Symbol.for()` for module-private keys** — using `Symbol.for('myKey')` when you intend module-private behavior exposes the key to any code that also calls `Symbol.for('myKey')`. Use `Symbol()` for per-module uniqueness.

4. **Symbol: `typeof` check before using as key** — if a function accepts either string or Symbol keys, check `typeof key === 'symbol'` before using. Symbol and string keys are both valid property keys but have different enumeration behaviors.

5. **FinalizationRegistry: do not store a strong reference to the registered object in the held value** — `registry.register(obj, obj)` defeats the purpose (the heldValue holds obj alive, preventing GC). The heldValue should be a token, ID, or other cleanup hint — NOT the object itself.

6. **WeakMap as cache: handle the stale-ref window** — between when a WeakRef's target is collected and when FinalizationRegistry fires, `cache.has(token)` returns true but `ref.deref()` returns undefined. Always check both: `cache.has(key) && cache.get(key).ref.deref() !== undefined`.
