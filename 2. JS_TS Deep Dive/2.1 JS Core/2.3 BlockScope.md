# JavaScript Core (Fundamentals): Scope — Block Scope — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is block scope?**
A: Block scope means a variable is only accessible within the `{}` block in which it is declared — and any nested blocks inside it. A "block" is any pair of curly braces: `if`, `else`, `for`, `while`, `switch`, `try`/`catch`/`finally`, or even a standalone `{}`. `let` and `const` are block-scoped; `var` is not — it ignores block boundaries and hoists to the nearest enclosing function or global scope.

**Q2. When was block scope introduced to JavaScript, and why?**
A: `let` and `const` (and block-scoped `class`) were introduced in ES6 (ES2015). Before that, JavaScript had only function scope and global scope — there was no native way to confine a variable to a block. The absence of block scope was a long-standing source of bugs (particularly the `var`-in-`for`-loop closure trap) and made JS feel unpredictable to developers coming from block-scoped languages like C, Java, or Python. ES6 filled that gap rather than changing `var` (breaking backward compatibility) by adding two new keywords.

**Q3. What is the difference between `let`, `const`, and `var` in terms of scoping?**
A:
- **`var`** — function-scoped (or global-scoped); hoisted and initialized to `undefined`; re-declarable; leaks out of blocks.
- **`let`** — block-scoped; hoisted but not initialized (TDZ); not re-declarable in the same scope; re-assignable.
- **`const`** — block-scoped; hoisted but not initialized (TDZ); not re-declarable; not re-assignable (the binding is constant, not the value — objects/arrays can still be mutated).

**Q4. What counts as a "block" in JavaScript?**
A: Any statement or clause delimited by `{}`:
- Control flow: `if`/`else if`/`else`, `for`, `while`, `do...while`, `switch`
- Error handling: `try`, `catch`, `finally`
- Functions (but function bodies create *function scope*, not just block scope)
- Standalone blocks: `{ let x = 1; }` — valid and useful for intentional scoping
- Class bodies and module bodies are also delimited by `{}` but follow their own scoping rules

A standalone block with no keyword in front of it (`{ }`) is perfectly legal JS — useful occasionally to scope a `let`/`const` tightly without needing a function.

**Q5. Is block scope lexical?**
A: Yes — like all scope in JavaScript, block scope is lexical (static). The scope of a `let`/`const` is determined entirely by where it appears in the source code, not by any runtime condition. Even if a block is never entered at runtime (e.g., an `if (false) { let x = 1; }`), the engine still recognizes `x` as scoped to that block during the creation phase and would throw a TDZ error if somehow accessed before initialization.

## Section 2: `let`, `const`, and the Temporal Dead Zone

**Q6. What is the Temporal Dead Zone (TDZ)?**
A: The TDZ is the period between the start of a block scope and the line where a `let` or `const` variable is declared. During the TDZ, the variable's binding exists (memory was allocated in the creation phase) but is uninitialized — accessing it throws `ReferenceError: Cannot access 'x' before initialization`. The TDZ ends the moment the declaration line is reached and the variable is initialized.

```js
{
  console.log(x); // ReferenceError — x is in TDZ
  let x = 5;
  console.log(x); // 5 — TDZ ended at declaration line
}
```

**Q7. Why does the TDZ exist — wasn't it just simpler to initialize `let`/`const` to `undefined` like `var`?**
A: The TDZ is a deliberate design choice to catch bugs early. Initializing `let`/`const` to `undefined` (like `var`) would silently allow reading a variable before its assignment, hiding logic errors. The TDZ forces a `ReferenceError` immediately, making the mistake loud and obvious rather than a subtle "wrong value" bug that surfaces much later. It enforces the intent: `let`/`const` should only be read after they're initialized.

**Q8. Does `const` guarantee immutability?**
A: No — `const` only guarantees that the *binding* (the variable name's reference) cannot be reassigned. The *value* it points to can still be mutated if it's an object or array:
```js
const user = { name: "Alice" };
user.name = "Bob";    // fine — mutating the object, not reassigning the binding
user = { name: "Bob" }; // TypeError — reassigning the const binding
```
For true immutability, use `Object.freeze()` (shallow) or a deep-freeze utility, or use immutable data structures from a library.

**Q9. Can `let` and `const` be re-declared in the same block scope?**
A: No — re-declaring `let` or `const` with the same name in the same scope throws a `SyntaxError` at parse time (before any code runs). This is stricter than `var`, which allows silent re-declaration. This catches a whole class of copy-paste or refactoring errors early:
```js
let x = 1;
let x = 2; // SyntaxError: Identifier 'x' has already been declared
```
Note that a `let` in an inner block *shadows* an outer `let` of the same name — that's not a re-declaration, it's a new binding in a new scope.

**Q10. Can you use `typeof` on a `let`/`const` variable before its declaration without a TDZ error?**
A: No — unlike with undeclared variables (where `typeof undeclaredVar` safely returns `"undefined"`), using `typeof` on a `let`/`const` in its TDZ still throws a `ReferenceError`. This surprises developers who expect `typeof` to always be safe:
```js
console.log(typeof x); // ReferenceError — x is let, currently in TDZ
let x = 5;
```
This is one of the sharper edges of the TDZ design and a common interview gotcha.

## Section 3: Block Scope in Loops

**Q11. How does `let` in a `for` loop differ from `var` in terms of scope?**
A: `let` in a `for` loop creates a *new, independent binding* for each iteration. Each closure formed inside the loop captures its own copy of the loop variable. `var` creates a single binding in the enclosing function scope shared across all iterations — so all closures see the same variable and its final value.

```js
// var — all callbacks share one 'i'
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3, 3, 3
}

// let — each iteration gets its own 'i'
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 0, 1, 2
}
```

**Q12. How does JavaScript actually implement per-iteration `let` bindings — is a new scope really created each time?**
A: Yes — the spec defines that a `for` loop with `let` creates a new lexical environment (a new scope) for *each iteration*, and the loop variable is copied into that fresh scope at the start of each pass. This is why closures formed inside the loop body each capture a distinct binding. Under the hood, V8 and other engines implement this efficiently — it doesn't literally allocate a new environment object per iteration in most optimized cases, but the observable behavior matches the spec exactly.

**Q13. Does `const` work in a `for` loop?**
A: It depends on the loop type:
- **`for...of` and `for...in`**: `const` works fine — a new binding is created each iteration and never reassigned within that iteration.
- **C-style `for` loop** (`for (const i = 0; i < 3; i++)`): throws a `TypeError` on the first iteration because `i++` tries to reassign the `const` binding.

```js
for (const item of ["a", "b", "c"]) {
  console.log(item); // works — new const binding each iteration
}

for (const i = 0; i < 3; i++) { // TypeError on first i++
}
```

**Q14. What happens to a `let` declared in a `for` loop's init — is it scoped to the loop header or the loop body?**
A: It's scoped to the entire `for` construct — both the header (init, condition, update expressions) and the body. A `let` in the init is not visible outside the loop at all, but it *is* visible in the condition and update expressions:
```js
for (let i = 0; i < 3; i++) { /* i accessible here */ }
console.log(i); // ReferenceError — i doesn't exist outside the for block
```

**Q15. How does block scope affect `switch` statements?**
A: The entire `switch` body (`{ }`) is a single block — all `case` clauses share the same block scope. This means a `let`/`const` declared in one `case` is technically in scope for other cases too (though it's in TDZ until its declaration line is reached), which can cause surprising TDZ errors if cases fall through. The idiomatic fix is wrapping each `case` body in its own block:
```js
switch (action) {
  case "A": {
    let result = computeA(); // scoped only to this case's block
    break;
  }
  case "B": {
    let result = computeB(); // separate binding — no conflict
    break;
  }
}
```

## Section 4: Block Scope & Closures

**Q16. How does block scope interact with closures?**
A: A closure captures the *lexical environment* of the scope where it's defined — and that scope can be a block scope, not just a function scope. A function defined inside an `if` block or `for` loop body closes over the block-scoped variables in that block:
```js
let fns = [];
for (let i = 0; i < 3; i++) {
  fns.push(() => i); // each arrow fn closes over its own block-scoped i
}
fns[0](); // 0
fns[1](); // 1
fns[2](); // 2
```

**Q17. Can a block-scoped variable be kept alive after its block exits, via a closure?**
A: Yes — if a function is defined inside a block and that function outlives the block (stored in an outer variable, returned, passed as a callback), the GC keeps the block-scoped variable alive as long as the closure is reachable. Block scope controls *access* (where it can be named), not *lifetime* (how long it lives in memory). Lifetime is governed by the GC's reachability rules.

```js
let getX;
{
  let x = 42;
  getX = () => x; // closure over block-scoped x
}
// x is no longer accessible by name here
getX(); // 42 — x is still alive in memory, held by the closure
```

**Q18. Does using `let` instead of `var` always fix closure-in-loop bugs?**
A: For standard `for` loops, yes — `let` creates a per-iteration binding that closures capture independently. But `while` loops and `do...while` loops don't automatically create per-iteration bindings for loop-external variables. If you close over a `let` declared *outside* a `while` loop, you still get one shared binding:
```js
let i = 0;
let fns = [];
while (i < 3) {
  fns.push(() => i); // all close over the same outer let i
  i++;
}
fns[0](); // 3 — same shared variable
```
For `while` loops, you need to manually create a new scope per iteration (inner `let` binding or IIFE) if you want independent captures.

## Section 5: Practical Patterns & Pitfalls

**Q19. What is a standalone block, and when would you actually use one?**
A: A standalone block is a bare `{}` with no keyword. It creates a block scope for `let`/`const` declarations inside it, preventing them from leaking into the surrounding scope. Practical uses:
- Isolating a temporary variable used for a one-off computation inside a larger function, making it clear it's not needed beyond that point.
- Avoiding name conflicts in long functions where the same temporary name would be useful in multiple unrelated sections.
- Making intent explicit in code that initializes a complex value in multiple steps.

```js
function processData(data) {
  let result;

  { // isolated setup block
    const temp = data.filter(Boolean);
    const sorted = temp.sort();
    result = sorted[0];
  }
  // temp and sorted are gone — can't accidentally use them below
  return result;
}
```

**Q20. What is "block scope as documentation" — and why does preferring `const` over `let` matter?**
A: Choosing `const` by default (and only using `let` when reassignment is genuinely needed) communicates intent to readers: a `const` binding tells you the value won't be reassigned in this scope, reducing the mental load of tracking mutations. Combined with tight block scoping, a reader can safely reason about a `const` variable just by looking at its block — it won't change, and it won't escape. This is a form of self-documenting code. Many style guides (Airbnb, Google) enforce `prefer-const` via ESLint for exactly this reason.

**Q21. How does block scope interact with `class` declarations?**
A: `class` declarations are block-scoped (like `let`) — not hoisted to a usable state (they're in TDZ from the start of the block until the declaration line). This is different from function declarations (which are fully hoisted). Two consequences: you cannot use a class before its declaration line (unlike a function declaration), and a class declared inside a block doesn't leak out:
```js
{
  class Animal {}
  const a = new Animal(); // fine
}
const b = new Animal(); // ReferenceError — Animal not in scope here
```

**Q22. How does block scope work inside `catch` clauses?**
A: The `catch` clause creates its own block scope for the error parameter — the caught error variable (e.g., `catch (e)`) is scoped to the `catch` block and doesn't leak into the surrounding function. `let`/`const` inside the `catch` block are also scoped to it. `var` inside `catch` still hoists to the enclosing function, as always. Since ES2019, you can omit the binding entirely (`catch { }`) when you don't need the error value.

**Q23. Can block scope help prevent issues with variable re-use in long functions?**
A: Yes — wrapping logically separate sections of a long function in standalone blocks forces discipline. Variables used only in one section can't accidentally bleed into another, and the engine may optimize their memory lifetime more aggressively since their scope is narrower. It's not a substitute for extracting sub-functions (which is usually better), but it's a useful intermediate step when refactoring incrementally.

## Section 6: Scenario / System Design Style Questions

**Q24. "A junior developer converted all `var`s in a large file to `let`, and now there are ReferenceErrors in production that didn't exist before. What likely happened?"**
A: The code was relying on `var`'s hoisting and function-scoping behaviors that `let` doesn't share. Common culprits:
- Code that read a `var` before its declaration line (relied on `undefined` from hoisting) now hits a TDZ `ReferenceError` with `let`.
- Code that declared the same variable in multiple `case` branches of a `switch` (worked with `var` because re-declaration is silently allowed; now a `SyntaxError` with `let`).
- Code that relied on a `var` declared inside an `if` block being visible outside it — now scoped to the block with `let`.

Fix strategy: don't do a blind find-and-replace. Use ESLint's `no-var` rule to flag occurrences, then review each one individually — check for pre-declaration reads, re-declarations, and cross-block access before converting.

**Q25. "You're doing a code review and see this pattern used in an `if`/`else` chain — is there a block-scope concern?"**
```js
if (condition) {
  var message = "success";
} else {
  var message = "failure";
}
console.log(message);
```
A: With `var`, this technically works but has two issues: the `var message` re-declaration is silent (no error, just redundancy), and `message` leaks into the enclosing function scope even though it's only meaningful inside the conditional. A cleaner block-scope-aware version:
```js
const message = condition ? "success" : "failure";
console.log(message);
```
Or, if the branches are more complex:
```js
let message;
if (condition) {
  message = "success";
} else {
  message = "failure";
}
```
Declare `let message` outside the block (where it needs to be accessible), assign inside — `let` prevents leaking beyond the enclosing scope, and the single declaration makes intent clear.

**Q26. "A teammate argues that block scope has a performance cost because the engine creates a new environment object per loop iteration. Should you avoid `let` in hot loops for performance?"**
A: This was a reasonable concern in early ES6 engine implementations, but it's largely obsolete today. Modern JS engines (V8, SpiderMonkey, JavaScriptCore) optimize `let`-in-loops aggressively — they detect when no closure is formed over the loop variable and avoid allocating a new environment object per iteration entirely, reducing it to essentially the same cost as `var`. The performance concern is only real if closures are actually formed inside the loop (capturing the per-iteration binding), in which case the allocation is *necessary* for correctness anyway. Profile before optimizing; don't avoid `let` on speculative performance grounds.

**Q27. "You're building a plugin system where third-party code runs in the same JS environment. How does block scope help you isolate plugin initialization code?"**
A: Block scope alone isn't sufficient for true isolation between untrusted plugins — they still share the same global object and can clobber each other's globals. But within a trusted codebase (where you control all plugins), wrapping each plugin's initialization in a block (or better, a module) prevents its `let`/`const` setup variables from bleeding into the shared scope:
```js
// Plugin A initialization
{
  const config = loadConfig("pluginA");
  const instance = new PluginA(config);
  registry.register("pluginA", instance);
}

// Plugin B initialization — 'config' and 'instance' names are reusable
{
  const config = loadConfig("pluginB");
  const instance = new PluginB(config);
  registry.register("pluginB", instance);
}
```
For true third-party isolation (sandboxing), you'd need iframes, Web Workers, or a VM context (in Node) — block scope is a code organization tool, not a security boundary.

**Tip for the interview:** At the 5 YOE level, block scope questions almost always arrive disguised as something else — a `let`-in-`for` closure question, a `const` immutability misconception, a `switch` TDZ gotcha, or a "why did the `var`-to-`let` migration break prod?" post-mortem. The highest-signal answer you can give is one that connects block scope to a concrete bug you caught or fixed — a `var`-in-loop closure in a real feature, a `switch` case collision, or a `const` object mutation that surprised a teammate. Knowing the mechanics cold (TDZ, per-iteration bindings, standalone blocks) matters, but demonstrating that you reach for `const` by default, use `let` deliberately, and understand *why* the rules exist is what separates a 5 YOE answer from a 1 YOE one.
