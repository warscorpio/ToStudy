# JavaScript Core (Fundamentals): Closures — Definition, Use Cases, Common Pitfalls — Interview Q&A (5 YOE Level)

---

## Section 1: Definition & Mechanics

**Q1. What is a closure?**
A: A closure is the combination of a function and the lexical environment in which it was defined. When a function is created, it captures a live reference to its surrounding scope's variable environment — not a snapshot of the values, but a reference to the actual bindings. Even after the outer function returns and its execution context is popped off the call stack, the inner function retains access to those bindings as long as the inner function itself is reachable. The outer scope's variables are kept alive in memory by the closure, not copied into it.

**Q2. What is the difference between a closure "capturing a reference" vs "capturing a value"?**
A: JavaScript closures always capture *references* to variables (the binding itself), never a copy of the value at the moment of capture. This means if the variable changes after the closure is created, the closure sees the updated value — not the value at capture time:
```js
function makeMultiplier() {
  let factor = 2;
  const multiply = (n) => n * factor;
  factor = 10; // changes after closure is created
  return multiply;
}
makeMultiplier()(5); // 50 — not 10. Closure sees factor = 10, the current value
```
This reference semantics is the root cause of the loop closure bug and many other subtle issues.

**Q3. How does the JavaScript engine keep the outer scope alive after the outer function returns?**
A: When the outer function returns, its execution context is popped off the call stack — but the lexical environment object it created is not immediately garbage collected if any inner function still holds a reference to it. The GC traces reachability from roots: the inner function is reachable (stored somewhere), and it holds a reference to the outer lexical environment, so that environment stays alive on the heap. Only when the last closure referencing it becomes unreachable does the environment become eligible for collection.

**Q4. Is every function in JavaScript a closure?**
A: Technically yes — every function retains a reference to the lexical environment in which it was defined, including the global scope. In practice, "closure" as a meaningful concept refers to functions that capture variables from an *enclosing function scope* (not just global scope), because that's where the interesting behavior — state retention, data privacy, delayed execution — emerges. A function that only uses its own local variables and globals isn't typically called a closure in conversation, even though it technically is one.

**Q5. What is the difference between a closure and a pure function?**
A: A pure function's output depends only on its explicit inputs — it has no side effects and captures no external mutable state. A closure, by definition, captures and can read or mutate variables from an outer scope — so it has implicit inputs (the closed-over variables). A closure *can* be pure if the variables it captures are never mutated after creation, but in practice closures are used precisely for their ability to maintain and mutate private state across multiple calls, which is impure behavior.

## Section 2: How Closures Work Under the Hood

**Q6. What is a lexical environment, and how does it relate to closures?**
A: A lexical environment is the internal data structure the engine creates for each scope — it maps identifier names to their current values (bindings) and holds a reference to the outer lexical environment (forming the scope chain). When a function is created, it stores an internal `[[Environment]]` slot pointing to the lexical environment of the scope where it was defined. When the function is later called, a new execution context is created with its local lexical environment's outer pointer set to that stored `[[Environment]]` — this is the mechanism that makes closure lookup work across calls.

**Q7. Do closures over the same outer scope share the same environment, or get separate copies?**
A: They share the same environment. Multiple inner functions created within the same outer function all close over the *same* lexical environment object. Mutating a closed-over variable via one inner function is visible to all other inner functions sharing that environment:
```js
function makeCounter() {
  let count = 0;
  return {
    increment: () => ++count,
    decrement: () => --count,
    value: () => count
  };
}
const c = makeCounter();
c.increment();
c.increment();
c.decrement();
c.value(); // 1 — all three methods share the same 'count' binding
```
This shared environment is what makes the module pattern work — and it's what makes the loop closure bug happen.

**Q8. What does V8 actually store in a closure — the full outer scope, or only the variables actually used?**
A: V8 optimizes: during compilation it performs a "context allocation" analysis to determine which variables are actually captured by inner functions. Variables that aren't referenced by any inner function may be stack-allocated and never promoted to the heap-based lexical environment. However, variables that *are* captured all live in the same context object — V8 doesn't yet do per-variable escape analysis to separate them. This means a closure that only uses one variable from a large outer scope keeps the *entire* context object (and all its other variables) alive, which is relevant for memory leak analysis.

**Q9. How does the scope chain work during a closure call?**
A: When a closure is called, the engine creates a new execution context for that call. The lexical environment of this new context has its outer pointer set to the closure's stored `[[Environment]]` (the captured outer scope). Variable lookup follows the chain: local scope first → captured outer scope → that scope's outer → ... → global scope. The key insight: this lookup traverses the *defining* scope chain, not the *calling* scope chain — which is what makes closures lexically scoped, not dynamically scoped.

## Section 3: Use Cases

**Q10. What is the "module pattern," and how do closures enable it?**
A: The module pattern uses an IIFE to create a function scope that's entered once and immediately exits, but the returned object holds closures over that scope's private variables — creating genuine encapsulation without classes or ES modules:
```js
const bankAccount = (function() {
  let balance = 0; // private — not accessible outside

  return {
    deposit(amount) { balance += amount; },
    withdraw(amount) {
      if (amount > balance) throw new Error("Insufficient funds");
      balance -= amount;
    },
    getBalance() { return balance; }
  };
})();

bankAccount.deposit(100);
bankAccount.withdraw(30);
bankAccount.getBalance(); // 70
// balance is inaccessible directly — true private state via closure
```

**Q11. How do closures enable factory functions?**
A: A factory function is a function that returns a new function (or object with methods) configured by the outer call's arguments. Each call to the factory creates a fresh closure with its own independent captured state:
```js
function createValidator(min, max) {
  return function validate(value) {
    return value >= min && value <= max;
  };
}
const isValidAge = createValidator(0, 120);
const isValidScore = createValidator(0, 100);

isValidAge(25);   // true
isValidScore(105); // false
// isValidAge and isValidScore are independent — different min/max captures
```

**Q12. How do closures implement memoization?**
A: Memoization caches the result of expensive function calls. A closure over a `cache` object (or `Map`) lets the memoized function remember previous results across calls without exposing the cache externally:
```js
function memoize(fn) {
  const cache = new Map();
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}
const expensiveCalc = memoize(function(n) {
  // ... heavy computation
  return n * n;
});
expensiveCalc(10); // computed
expensiveCalc(10); // cache hit — returns immediately
```

**Q13. How do closures power event handlers and callbacks with private context?**
A: Event handlers often need access to context that isn't available at the time they fire. Closures let the handler "remember" the relevant context from when it was created:
```js
function attachLogger(element, label) {
  element.addEventListener("click", function() {
    console.log(`${label} was clicked`); // 'label' from outer scope
  });
}
attachLogger(document.getElementById("btn"), "Submit Button");
// The handler closes over 'label' — no need to store it on the DOM element
```

**Q14. How are closures used in partial application and currying?**
A: Partial application fixes some arguments of a function, returning a new function that takes the rest. Closures store the fixed arguments in the outer scope:
```js
function multiply(a, b) { return a * b; }

function partial(fn, ...fixedArgs) {
  return function(...remainingArgs) {
    return fn(...fixedArgs, ...remainingArgs); // fixedArgs from closure
  };
}
const double = partial(multiply, 2);
const triple = partial(multiply, 3);

double(5);  // 10
triple(5);  // 15
```
Currying is the more formal version — transforming a multi-argument function into a chain of single-argument functions, each returning a closure over previously received arguments.

**Q15. How do closures relate to React hooks like `useState` and `useEffect`?**
A: React hooks rely heavily on closures. Each render of a component creates a fresh closure over that render's props and state. `useEffect`'s callback closes over the state/props values at the time of that render — which is why stale closure bugs occur: if a `useEffect` references state but has an empty dependency array, the effect's callback closes over the *initial* render's state values and never sees updates. Understanding that React hooks are closures over render-time values is essential for debugging stale closure issues in functional components.

## Section 4: The Loop + Closure Bug

**Q16. Explain the classic loop closure bug.**
A: The bug occurs when closures are created inside a loop that uses `var` for the loop variable. Because `var` is function-scoped, there is only *one* binding for the loop variable shared across all iterations. All closures created in the loop close over the *same* binding — so when they're eventually called (after the loop completes), they all see the variable's final value:
```js
for (var i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i); // all print 5 — not 0, 1, 2, 3, 4
  }, i * 1000);
}
```
The five callbacks all share the one `var i` in the enclosing function scope. By the time any callback fires, the loop has completed and `i` is `5`.

**Q17. What are all the ways to fix the loop closure bug?**
A: Five approaches, from most to least preferred in modern code:

**Fix 1 — `let` (best, ES6+):**
```js
for (let i = 0; i < 5; i++) {
  setTimeout(() => console.log(i), i * 1000); // 0, 1, 2, 3, 4
}
```
`let` creates a new, independent binding per iteration — each closure captures its own `i`.

**Fix 2 — `const` in `for...of`:**
```js
const delays = [0, 1, 2, 3, 4];
for (const i of delays) {
  setTimeout(() => console.log(i), i * 1000); // 0, 1, 2, 3, 4
}
```

**Fix 3 — IIFE per iteration (pre-ES6 classic):**
```js
for (var i = 0; i < 5; i++) {
  (function(j) {
    setTimeout(function() { console.log(j); }, j * 1000);
  })(i); // immediately pass current i as j — new scope, new binding
}
```

**Fix 4 — factory function:**
```js
function makeLogger(i) {
  return function() { console.log(i); };
}
for (var i = 0; i < 5; i++) {
  setTimeout(makeLogger(i), i * 1000);
}
```
`i` is passed as an argument to `makeLogger`, creating a new `i` binding in each `makeLogger` call's scope.

**Fix 5 — `setTimeout`'s third argument:**
```js
for (var i = 0; i < 5; i++) {
  setTimeout(function(j) { console.log(j); }, i * 1000, i);
}
```
The third argument to `setTimeout` is passed as an argument to the callback when it fires — evaluated immediately, so each callback gets the correct value.

**Q18. Does the loop closure bug only affect `setTimeout`?**
A: No — `setTimeout` is just the most common illustration because it makes the asynchronous delay obvious. The same bug occurs with any pattern where closures created in a loop are called *after* the loop completes: `addEventListener` callbacks, Promise chains inside loops, array methods that return functions, event emitter handlers, and any other deferred or async callback:
```js
const handlers = [];
for (var i = 0; i < 3; i++) {
  handlers.push(() => i); // all return 3
}
handlers[0](); // 3 — bug exists even without async
```

**Q19. Does the bug occur with `forEach` and `var`?**
A: `forEach` passes a fresh function call per iteration — each callback is a separate invocation with its own `i` parameter. So `forEach` with an inline callback does *not* have the loop closure bug, because the loop variable is passed as a function argument (a new binding per call), not closed over from a shared outer `var`:
```js
[0, 1, 2].forEach(function(i) {
  setTimeout(() => console.log(i), 0); // 0, 1, 2 — correct
});
```
The bug only manifests in C-style `for`/`while` loops where the loop variable is a shared `var` in the outer scope.

**Q20. What is the "stale closure" problem in React, and how is it related to the loop bug?**
A: Both stem from the same root: a closure captures a *reference to a binding at a point in time*, and that binding later holds a different value than expected. In React, each render creates a new closure over that render's state/props. If an effect or event handler from render N is still alive during render N+3, it closes over stale state from render N — not the current state. The parallel to the loop bug: both involve a closure being called in a context where the captured variable has moved on from the value the developer expected.

The fix in React: include the variable in the `useEffect` dependency array (so a fresh closure is created when it changes), use `useRef` to hold a mutable reference that doesn't trigger re-renders but always reflects the latest value, or use the functional form of `setState` (which receives the current state as an argument, bypassing the stale closure entirely).

## Section 5: Memory, Performance & Pitfalls

**Q21. How can closures cause memory leaks?**
A: A closure keeps its entire captured lexical environment alive as long as the closure itself is reachable. If a closure is stored somewhere long-lived (a global variable, a module-level cache, an event listener never removed, a timer never cleared), the entire outer scope it captured stays in memory — even if most of that scope's variables are no longer needed:
```js
function setup() {
  const hugeData = new Array(1_000_000).fill("x"); // 1M entries
  const tiny = hugeData[0]; // only need the first entry

  element.addEventListener("click", function() {
    console.log(tiny); // closes over entire scope, keeping hugeData alive
  });
}
```
Fix: extract only what the closure needs into a local variable *before* the closure is created, then let the larger data go out of scope:
```js
function setup() {
  const hugeData = new Array(1_000_000).fill("x");
  const tiny = hugeData[0];
  // hugeData reference not captured by the closure below
  element.addEventListener("click", function() {
    console.log(tiny);
  });
  // hugeData can now be GC'd after setup() returns
}
```

**Q22. Does every closure allocation hurt performance?**
A: In hot paths, yes — creating closure objects has overhead (heap allocation for the context, GC pressure). But modern engines (V8) optimize extensively: closures that don't escape the local scope may be stack-allocated; captured variables that are never mutated may be inlined. In practice, closure overhead only matters in very tight loops running millions of iterations. The correctness and readability benefits of closures vastly outweigh micro-optimization concerns in typical application code — profile before optimizing.

**Q23. What is a "closure over a large DOM subtree," and why is it dangerous?**
A: If a closure captures a reference to a DOM node (directly or via an outer variable), it keeps that node and its entire subtree alive in memory — even after the node is removed from the document. The GC sees the node as reachable (via the closure) and won't collect it. This is especially harmful with event listeners attached to removed nodes, or with framework component cleanup that forgets to remove listeners:
```js
function bindActions(container) {
  const items = container.querySelectorAll(".item"); // large NodeList
  document.addEventListener("keydown", function(e) {
    items.forEach(item => item.classList.toggle("active")); // items kept alive
  });
  // document-level listener never removed — items and their DOM subtree never GC'd
}
```

**Q24. What is "closure over `this`" and what are its pitfalls?**
A: Regular functions have their own dynamic `this` binding (set by call site). When a regular function is used as a callback, `this` is often lost — it becomes `undefined` (strict mode) or the global object. Developers sometimes work around this by closing over `this` via a variable:
```js
function Timer() {
  const self = this; // capture 'this' in closure
  this.count = 0;
  setInterval(function() {
    self.count++; // uses closed-over 'self', not 'this' of the callback
  }, 1000);
}
```
Arrow functions solve this more cleanly — they don't have their own `this` and lexically inherit it from the enclosing scope, which is exactly what closure-over-`this` was manually achieving. The `const self = this` pattern is now considered legacy.

**Q25. What happens when you create closures inside a `switch` statement — any pitfalls?**
A: The entire `switch` body is a single block scope. If closures are created in multiple `case` branches that share `let`/`const` variable names, those names resolve to different TDZ/initialized bindings depending on which `case` ran first — but all bindings live in the same block scope. The real risk: a closure created in one `case` branch that references a variable declared in another `case` (that may never have executed) will hit TDZ or `undefined`. The fix is to wrap each `case` in its own block `{}` to properly isolate bindings — and be cautious about creating closures in `switch` cases that reference cross-case variables.

## Section 6: Scenario / System Design Style Questions

**Q26. "You're building a button click counter for 10 buttons — each should track its own count. A junior wrote this and all buttons show the same count. Why, and how do you fix it?"**
```js
var buttons = document.querySelectorAll("button");
var count = 0;
for (var i = 0; i < buttons.length; i++) {
  buttons[i].addEventListener("click", function() {
    count++;
    console.log("Button " + i + " clicked " + count + " times");
  });
}
```
A: Two bugs, both rooted in `var`'s function-scoped single binding:
1. All handlers share one `count` — clicks on any button increment the same counter.
2. All handlers share one `i` — after the loop, `i` is `buttons.length`, so every click logs "Button 10 clicked...".

Fix: use `let` for `i` (per-iteration binding), and move `count` inside the loop or into a closure per button:
```js
const buttons = document.querySelectorAll("button");
for (let i = 0; i < buttons.length; i++) {
  let count = 0; // fresh per-iteration binding
  buttons[i].addEventListener("click", function() {
    count++;
    console.log(`Button ${i} clicked ${count} times`);
  });
}
```

**Q27. "Design a rate limiter using closures — `createRateLimiter(limit, windowMs)` should return a function that returns `true` if the call is within the rate limit and `false` if it exceeds it."**
A: Closures are the natural fit — each limiter instance has its own private state (call timestamps) captured in the outer scope:
```js
function createRateLimiter(limit, windowMs) {
  const calls = []; // private — closed over by the returned function

  return function isAllowed() {
    const now = Date.now();
    // remove calls outside the current window
    while (calls.length > 0 && now - calls[0] > windowMs) {
      calls.shift();
    }
    if (calls.length < limit) {
      calls.push(now);
      return true;
    }
    return false;
  };
}

const limiter = createRateLimiter(3, 1000); // 3 calls per second
limiter(); // true
limiter(); // true
limiter(); // true
limiter(); // false — limit reached
```
`calls` is private state — inaccessible from outside, independent per limiter instance, persisted across calls via closure.

**Q28. "A colleague is debugging a React `useEffect` that's always reading the initial value of a state variable, even after multiple updates. Explain what's happening and how to fix it."**
A: Classic stale closure in React. When `useEffect` runs with an empty dependency array (`[]`), the effect callback is created once — during the first render — and closes over that render's state snapshot. Subsequent state updates trigger re-renders and create new state values, but the effect's closure was never re-created (the dependency array told React not to). So the callback always references the state binding from render 1.

Three fixes:
1. **Add the variable to the dependency array** — `[stateVar]` tells React to re-run the effect and create a fresh closure whenever `stateVar` changes.
2. **Use a `ref`** — store the value in a `useRef`. Refs are mutable objects that persist across renders; accessing `ref.current` inside the closure always returns the latest value without triggering re-renders.
3. **Functional state update** — if the issue is inside a `setState` call, use the functional form: `setState(prev => prev + 1)` receives the actual current state as an argument, bypassing the stale closure entirely.

**Q29. "You need to implement a private class-like object with `deposit`, `withdraw`, and `getBalance` methods, without using ES6 `class` or `#` private fields. How do closures help?"**
A: The closure-based module pattern achieves genuine private state — not convention-private (prefixed `_`), not WeakMap-private, but truly inaccessible:
```js
function createAccount(initialBalance) {
  let balance = initialBalance; // truly private — no external access path

  function validateAmount(amount) {
    if (typeof amount !== "number" || amount <= 0) throw new Error("Invalid amount");
  }

  return {
    deposit(amount) {
      validateAmount(amount);
      balance += amount;
      return balance;
    },
    withdraw(amount) {
      validateAmount(amount);
      if (amount > balance) throw new Error("Insufficient funds");
      balance -= amount;
      return balance;
    },
    getBalance() {
      return balance;
    }
  };
}

const account = createAccount(100);
account.deposit(50);  // 150
account.withdraw(30); // 120
account.getBalance(); // 120
account.balance;      // undefined — no direct access to the closure variable
```
`balance` and `validateAmount` are genuinely private — they exist only in the closure's captured scope, unreachable by any external code.

**Tip for the interview:** At the 5 YOE level, "what is a closure" is purely the warm-up — every candidate can define it. The real signal questions are: tracing the loop bug and offering *all* fixes fluently, explaining stale closures in React from first principles (not just "add it to the dep array"), designing a factory or module using closures under constraints, and diagnosing a memory leak caused by a long-lived closure. The highest-value thing to demonstrate is explaining closures as "live references to bindings, not value snapshots" — that single framing unlocks every closure bug pattern. Have one real story ready: a loop closure bug caught in review, a stale closure in a React hook that caused a production issue, or a memory leak traced to an unremoved event listener holding a large closure scope alive.
