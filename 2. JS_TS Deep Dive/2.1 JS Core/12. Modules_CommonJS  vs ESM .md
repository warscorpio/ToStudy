# Modules: CommonJS (`require/module.exports`) vs ESM (`import/export`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do modules solve and why did JavaScript need them?**
A: Before modules, JavaScript had no mechanism to split code across files while controlling scope. Browser scripts all shared one global scope — every variable and function defined in any `<script>` tag was global, creating three intractable problems: (1) **namespace collisions**: library A defining `var utils = ...` would overwrite library B's `var utils = ...` — whoever loaded last won; (2) **dependency ordering**: if library B needed library A, `<script>` tags had to appear in exactly the right order, and this ordering was implicit, fragile, and undocumented; (3) **encapsulation**: there was no way to have private implementation details — everything was visible to everything.

The module systems that emerged (CommonJS in 2009 for Node.js, then AMD for browsers, then ESM standardized in ES2015) all solve the same problem: each file should have its own private scope, with an explicit mechanism for declaring what it exports (makes public) and what it imports from other files (its dependencies).

**Q2. What is CommonJS (CJS) and where did it come from?**
A: CommonJS is a module specification created in 2009 by Kevin Dangoor as part of the "ServerJS" project, adopted by Node.js as its native module system. It was designed for server-side use, not browsers. The core API:

```javascript
// Importing (consumer):
const fs = require('fs');                          // Node.js built-in
const lodash = require('lodash');                   // npm package
const utils = require('./utils');                   // relative path (local module)
const config = require('../config/settings.json'); // JSON auto-parsed

// Exporting (producer) — two equivalent patterns:

// Pattern 1: assign to module.exports
module.exports = function add(a, b) { return a + b; };
// Entire export IS the function — consumer: const add = require('./add')

// Pattern 2: add properties to exports shorthand
exports.add = function(a, b) { return a + b; };
exports.subtract = function(a, b) { return a - b; };
// Consumer: const { add, subtract } = require('./math')
```

CJS runs in Node.js without any build step — `require` is synchronous and works immediately. It was not designed for browsers (no browser had a file system to load from synchronously), which led to AMD (Asynchronous Module Definition) for browser bundles.

**Q3. What is ESM and why is it different in nature from CommonJS?**
A: ESM (ECMAScript Modules) is the module system standardized in ES2015 (ES6) as part of the JavaScript language specification itself — not a library or a convention, but a formal part of the language. The core API:

```javascript
// Importing (consumer):
import fs from 'fs';                              // default import
import { readFile, writeFile } from 'fs';         // named imports
import * as fsAll from 'fs';                      // namespace import
import { readFile as rf } from 'fs';              // aliased import
import './side-effects-only.js';                  // side-effect-only import

// Exporting (producer):
export function add(a, b) { return a + b; }       // named export (inline)
export const PI = 3.14159;                        // named export (const)

const subtract = (a, b) => a - b;
export { subtract };                               // named export (declaration)
export { subtract as minus };                     // exported with alias

export default class Calculator { ... }           // default export (only one per module)

// Re-exporting (aggregation pattern):
export { add, subtract } from './math.js';        // re-export from another module
export * from './utils.js';                       // re-export all named exports
export { default } from './logger.js';            // re-export the default
```

ESM is fundamentally different from CJS in one critical way: it is **statically analyzable**. All `import` and `export` statements are top-level, have no control flow around them, and their identifiers are resolved before any code runs. This static structure — the module graph — is determined at parse time, not at runtime.

## Section 2: Loading and Execution Mechanics

**Q4. How does CommonJS `require()` execute — what happens step by step?**
A: `require()` is a synchronous function call. The full execution sequence:

```javascript
// When Node.js encounters: const utils = require('./utils.js')

// Step 1: Resolve the path
// Node resolves './utils.js' relative to current file
// Tries: utils.js, utils/index.js, utils.json

// Step 2: Check the module cache
// require.cache[resolvedPath] exists? → return module.exports immediately (cached)

// Step 3: Create a new module object
// module = { id: resolvedPath, exports: {}, loaded: false, children: [] }

// Step 4: Register in cache BEFORE execution
// require.cache[resolvedPath] = module  ← important for circular dependency handling

// Step 5: Wrap the file in the module wrapper function:
(function(exports, require, module, __filename, __dirname) {
    // The actual contents of utils.js go here
    exports.greet = function(name) { return `Hello, ${name}`; };
    module.exports.double = function(n) { return n * 2; };
});
// This wrapper provides: the `exports` shorthand, access to `require`,
// the `module` object, and `__filename`/__dirname as file-local variables

// Step 6: Execute the wrapper — code runs synchronously

// Step 7: module.loaded = true

// Step 8: return module.exports to the caller
```

**The module wrapper function** is why `module`, `exports`, `require`, `__filename`, and `__dirname` are available in every Node.js file without being global — they're injected as function parameters, not global variables.

**Q5. How does ESM loading work — why is it "asynchronous" even when it looks synchronous?**
A: ESM loading has three distinct phases that are intentionally separated:

```
Phase 1: PARSE (Construction)
  - The entry point file is downloaded/read
  - Parsed to find all import statements (static analysis)
  - Each imported module file is fetched/read
  - That file is parsed to find its imports
  - Recursively repeat until all modules in the graph are parsed
  - Result: a complete module graph (a DAG) — no code has executed yet

Phase 2: LINK (Instantiation)
  - The module graph is evaluated bottom-up
  - For each module: allocate memory for all exported bindings (variables)
  - Wire up import bindings to the memory slots of the exporting module
  - Bindings are "live" references — they point to the same memory location
  - Result: all modules are "linked" — imports know exactly where to find exports

Phase 3: EVALUATE (Execution)
  - Execute each module's top-level code in dependency order (leaves first)
  - Assignments to exported variables fill the pre-allocated memory slots
  - Importers see the live values through their live bindings
```

This three-phase process is what enables ESM's live bindings (Q7) and what makes it fundamentally incompatible with runtime-dependent imports (you can't `import` inside an `if` statement because the import must be resolved before any code runs). It also enables async loading in browsers (modules are fetched in parallel during Phase 1).

**Q6. What is the practical meaning of "synchronous" CJS vs "asynchronous" ESM loading, and when does the distinction matter?**
A: CJS `require()` blocks — the current module's execution literally halts until the required module is fully loaded and executed. This works in Node.js because file reads are cheap on a local filesystem (typically microseconds). It would be catastrophic in a browser where "files" are HTTP requests taking 100ms each. Requiring 50 modules would mean 50 sequential HTTP requests before any code runs.

ESM's three-phase loading enables browsers to fetch all module files in parallel during Phase 1 (the parser discovers `import 'foo.js'` and `import 'bar.js'` simultaneously, fetches both in parallel), dramatically reducing total load time. The "asynchronous" nature of ESM is what makes it viable for browsers without a bundler.

In Node.js (file system): both CJS and ESM load from disk synchronously at the OS level, but ESM maintains the three-phase structure as a language guarantee regardless of environment. This means:
- Top-level `await` is only possible in ESM (because Phase 3/Evaluate can be awaited)
- CJS can never have top-level `await` (it's designed to be synchronous)

```javascript
// ESM only — top-level await (no wrapping async function needed):
// config.js (ESM)
const response = await fetch('https://api.example.com/config');
const config = await response.json();
export default config;

// Any module importing config.js automatically waits for this await:
import config from './config.js';  // config is fully resolved before this module continues
```

## Section 3: Exports and Imports In Depth

**Q7. What is the "live binding" difference between CJS and ESM exports, and why does it matter?**
A: This is the most important semantic difference between CJS and ESM. CJS exports a value (a copy at the time of `module.exports` assignment); ESM exports a live binding (a reference to the variable's memory location that stays updated):

```javascript
// === CommonJS: exports VALUES (static snapshots) ===
// counter.cjs
let count = 0;
module.exports.count = count;    // exports the VALUE 0
module.exports.increment = function() { count++; };

// consumer.cjs
const { count, increment } = require('./counter.cjs');
console.log(count);    // 0
increment();
console.log(count);    // STILL 0 — the destructured `count` is a copy of the value
                       // it was copied at require() time and count is NOT updated
// To see updates: require('./counter.cjs').count — re-reads from module.exports

// === ESM: exports LIVE BINDINGS (live references) ===
// counter.mjs
export let count = 0;
export function increment() { count++; }

// consumer.mjs
import { count, increment } from './counter.mjs';
console.log(count);    // 0
increment();
console.log(count);    // 1 — LIVE binding: count IS updated
                       // import { count } is a live reference to counter.mjs's `count` variable
```

Why live bindings matter: they enable the "module as state" pattern where multiple importers of a module see each other's mutations. They also enable a singleton pattern — every importer of a module gets the same live view of the module's state. In CJS, you'd need to export a getter function or access the property through the module object to get updated values.

Additionally, live bindings are **read-only** on the import side — you cannot assign to an imported binding:
```javascript
import { count } from './counter.mjs';
count = 10;  // TypeError: Assignment to constant variable
             // The binding is live but the importer cannot set it
increment(); // The exporting module can modify it through exported functions
```

**Q8. What is the difference between `exports` and `module.exports` in CommonJS, and what is the trap?**
A: `exports` is a shorthand reference that starts pointing to the same object as `module.exports`. Adding properties to `exports` adds them to `module.exports`. But reassigning `exports` breaks the link — it no longer points to `module.exports`, so the reassignment has no effect on what is actually exported:

```javascript
// At module start (Node.js sets this up):
// exports === module.exports === {} (same empty object)

// SAFE: adding properties to exports
exports.add = function(a, b) { return a + b; };
exports.PI = 3.14;
// module.exports is now { add: [Function], PI: 3.14 }

// TRAP: reassigning exports breaks the link
exports = { add: (a, b) => a + b };  // exports now points to a NEW object
// module.exports is STILL {} (empty!) — exports reassignment is ignored
// Consumer gets: const math = require('./math') → math === {}

// CORRECT: to export a single value (function, class, object), use module.exports:
module.exports = function add(a, b) { return a + b; };
// Consumer: const add = require('./add') → add is the function

// CORRECT: to export multiple named values, use module.exports object:
module.exports = {
    add: (a, b) => a + b,
    PI: 3.14
};
// Consumer: const { add, PI } = require('./math')
```

The rule: `exports.x = ...` is safe for adding named exports. `module.exports = ...` is required for replacing the entire export value (exporting a single function, class, or explicitly structured object).

**Q9. What are named exports vs default exports in ESM, and what are the design trade-offs?**
A: Named exports and default exports serve different purposes and have different ergonomics:

```javascript
// === Named exports: multiple, explicitly named ===
// math.js
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }
export const PI = 3.14159;

// Consumer — must use the exact exported name (or alias):
import { add, multiply, PI } from './math.js';
import { add as sum } from './math.js';  // aliased

// === Default export: one per module, any name on import ===
// Logger.js
export default class Logger {
    log(msg) { console.log(`[LOG] ${msg}`); }
}

// Consumer — names it whatever they want:
import Logger from './Logger.js';
import MyLogger from './Logger.js';  // same import, different local name — both valid

// === Combining: one default + named ===
// api.js
export default function fetchData(url) { return fetch(url); }
export const BASE_URL = 'https://api.example.com';
export function buildUrl(path) { return `${BASE_URL}${path}`; }

import fetchData, { BASE_URL, buildUrl } from './api.js';  // both in one statement
```

Design trade-offs:
- **Named exports** are more explicit (the consumer must use the correct name) and more tooling-friendly (tree-shaking, auto-import, refactoring tools know exactly what's exported). They're the standard recommendation for utility libraries.
- **Default exports** allow the consumer to name the import freely — convenient but can lead to inconsistent naming across a codebase (`import Logger from './Logger'` in one file, `import Log from './Logger'` in another). They're conventional for React components (`export default function Button() {...}`) and for modules that represent a single entity.
- **The controversy**: many style guides (Airbnb, Google) and tooling experts discourage default exports for library code because they hurt tree-shaking, auto-import, and rename refactoring (no canonical name to find). Named exports are generally preferred for shared utilities.

## Section 4: Module Resolution

**Q10. How does Node.js resolve module paths in CJS, and what is the resolution algorithm?**
A: Node.js's CJS path resolution (`require.resolve()`) follows a specific algorithm depending on the string passed to `require()`:

**Bare specifiers** (no `./`, `../`, or `/` prefix) → resolved as a package:
```javascript
require('lodash')  // looks in node_modules/

// Resolution for bare specifiers:
// 1. Check for Node.js built-in: 'fs', 'path', 'http', etc.
// 2. Walk up directory tree, checking node_modules at each level:
//    ./node_modules/lodash
//    ../node_modules/lodash
//    ../../node_modules/lodash  ... until filesystem root
// 3. In the found package directory:
//    a. Read package.json's "main" field (default: "index.js")
//    b. Try: lodash.js, lodash/index.js
```

**Relative/absolute paths** (`./`, `../`, `/`) → file resolution:
```javascript
require('./utils')  // exact file or with extensions tried in order

// Resolution for relative paths:
// 1. Try exact path: ./utils (if it exists as a file)
// 2. Try with extensions: ./utils.js, ./utils.json, ./utils.node
// 3. Try as directory:
//    a. ./utils/package.json "main" field
//    b. ./utils/index.js, ./utils/index.json, ./utils/index.node
```

**Q11. How does ESM module resolution differ from CJS, and what is the "mandatory file extension" requirement?**
A: ESM in Node.js enforces stricter resolution rules than CJS:

**File extensions are mandatory** in ESM (Node.js):
```javascript
// CJS: extension can be omitted
const utils = require('./utils');  // Node tries .js, .json, .node

// ESM: extension is required
import utils from './utils';      // ERROR: cannot find module './utils'
import utils from './utils.js';   // CORRECT: exact path required

// Why? The ESM spec was designed for browsers, where URLs are exact.
// 'fetch("./utils")' doesn't automatically try './utils.js'
// Node.js ESM follows the spec for consistency.
```

**The `exports` field in `package.json`** — ESM introduced a new package.json field that overrides the legacy `main` field and provides fine-grained control over what a package exports and to whom:
```json
{
    "name": "my-package",
    "exports": {
        ".": {
            "import": "./dist/index.mjs",
            "require": "./dist/index.cjs",
            "types": "./dist/index.d.ts"
        },
        "./utils": {
            "import": "./dist/utils.mjs",
            "require": "./dist/utils.cjs"
        }
    }
}
```
This `exports` map: (1) provides different entry points for CJS vs ESM consumers; (2) prevents access to internal files (if `./internal` is not in the map, `import 'my-package/internal'` fails — packages can now enforce their public API); (3) enables conditional exports for browser vs Node.js environments.

## Section 5: Static vs Dynamic

**Q12. What does "static" mean in ESM and why is it significant for tooling?**
A: "Static" means that all `import` and `export` statements are top-level declarations with fixed, literal string module specifiers — no computation, no variables, no conditionals, no function calls around them. The complete module dependency graph can be determined by reading source code without executing it:

```javascript
// STATIC: always at top level, string literal, always resolved
import { readFile } from 'fs';
import { helper } from './helper.js';
export function process() { ... }

// INVALID in ESM (syntax errors or restricted):
if (condition) {
    import { tool } from './tool.js';  // SyntaxError: import in block
}

const path = './dynamic';
import { fn } from path;  // SyntaxError: computed module specifier

function loadModule() {
    import { fn } from './tool.js';  // SyntaxError: import in function
}
```

This static structure enables the tooling that makes modern JavaScript development possible:
- **Tree shaking** (dead code elimination): a bundler can analyze which exports are actually imported and eliminate unused exports at build time — impossible with CJS where `require()` is a runtime function call.
- **Static import analysis / auto-import**: IDEs can know exactly what a module exports without running it, enabling reliable auto-import suggestions and jump-to-definition.
- **Circular dependency detection**: static analysis can detect and warn about circular dependencies in the graph before runtime.
- **Bundle splitting / code splitting**: bundlers can determine which modules are shared between entry points and split them into separate chunks.

**Q13. What is dynamic `import()` and how does it differ from static `import`?**
A: Dynamic `import()` is a function-like syntax (not an actual function) that loads a module at runtime, returning a `Promise` that resolves to the module's namespace object. It was added to ESM specifically to enable use cases that static imports can't handle:

```javascript
// Dynamic import: runtime, conditional, returns Promise
async function loadFeature(featureName) {
    // Computed specifier — impossible with static import
    const module = await import(`./features/${featureName}.js`);
    module.initialize();
}

// Conditional loading:
if (process.env.NODE_ENV === 'development') {
    const { devTools } = await import('./dev-tools.js');
    devTools.enable();
}

// Lazy loading in React (code splitting):
const HeavyChart = React.lazy(() => import('./HeavyChart.jsx'));
// HeavyChart's module isn't loaded until the component is first rendered

// The namespace object returned by dynamic import:
const math = await import('./math.js');
math.add(1, 2);       // named export
math.default(1, 2);   // default export is on .default property
```

Dynamic `import()` works in both ESM and non-ESM contexts (you can use `import()` inside CJS `require()` files in Node.js). It is genuinely asynchronous (always returns a `Promise`) — this is the right tool for: lazy loading large optional dependencies, environment-specific module loading, plugin systems where module paths are determined at runtime, and code splitting in bundlers (webpack's dynamic `import()` creates separate chunk boundaries).

**Q14. What is `require()` in CJS and can it do anything dynamic import() can't?**
A: `require()` is genuinely dynamic — it's a normal function call that runs at runtime, so it has capabilities static `import` doesn't:

```javascript
// CJS: fully runtime-dynamic
const path = condition ? './module-a' : './module-b';
const module = require(path);  // computes path at runtime — valid CJS

// CJS inside functions (load-on-demand without async):
function getLogger() {
    if (!loggerInitialized) {
        const { Logger } = require('./logger');  // synchronous lazy load
        logger = new Logger();
        loggerInitialized = true;
    }
    return logger;
}

// CJS can introspect the cache:
delete require.cache[require.resolve('./module.js')];  // bust the cache
require('./module.js');  // forces re-execution of the module

// CJS can require JSON natively:
const config = require('./config.json');  // auto-parsed as object

// CJS package requires conditional:
const impl = process.platform === 'win32'
    ? require('./windows-impl')
    : require('./unix-impl');
```

CJS's synchronous dynamic loading is actually a practical advantage in some scenarios (CLI tools, plugin systems, test frameworks that want synchronous module loading). But it's the exact property that prevents tree shaking: if `require()` calls depend on runtime values, no static tool can know in advance which modules will be loaded, so it can't eliminate unused code.

## Section 6: Circular Dependencies

**Q15. How do CommonJS circular dependencies behave, and what is the "partial export" problem?**
A: CJS handles circular dependencies by returning whatever `module.exports` currently contains at the time of the cycle — which may be an incomplete (partially populated) object:

```javascript
// a.cjs
console.log('a starts');
const b = require('./b.cjs');
console.log('in a, b.done =', b.done);
module.exports.done = true;
console.log('a done');

// b.cjs
console.log('b starts');
const a = require('./a.cjs');  // ← circular: a is still loading
console.log('in b, a.done =', a.done);  // a.done is UNDEFINED here
module.exports.done = true;
console.log('b done');

// Entry point: require('./a.cjs')
// Output:
// a starts
// b starts
// in b, a.done = undefined   ← a's exports are incomplete at this point
// b done
// in a, b.done = true        ← b is complete by the time a reads it
// a done
```

Why: when `a.cjs` requires `b.cjs`, Node.js registers `a.cjs` in the cache with its current (empty) `module.exports` before `a.cjs` finishes executing. When `b.cjs` then requires `a.cjs`, Node.js finds it in the cache and returns the partially-populated `module.exports`. Any properties `a.cjs` adds after the circular require point won't be in the snapshot `b.cjs` receives.

The classic fix: restructure to avoid the circular dependency (preferred), or use late binding (access the circular module inside functions that run after both modules have finished loading — by then the exports are complete):

```javascript
// b.cjs (fixed with late binding)
const aModule = require('./a.cjs');  // still gets the partial object
module.exports.doSomething = function() {
    // By the time this function is CALLED (not when module loads),
    // a.cjs has finished loading and aModule.done is true
    return aModule.done;  // works correctly at call time
};
```

**Q16. How does ESM handle circular dependencies differently from CJS?**
A: ESM's three-phase loading model handles circular dependencies more predictably, but with different constraints. Because ESM links all bindings before executing any code (Phase 2/Link happens before Phase 3/Evaluate), the module graph can be fully constructed even with cycles. Exports are pre-allocated memory slots — a circular import always has a valid binding to the memory slot, even if that slot hasn't been filled yet:

```javascript
// a.mjs
import { bDone } from './b.mjs';
export let aDone = false;
console.log('a starts, bDone:', bDone);  // bDone exists but may be false (initial value)
aDone = true;

// b.mjs
import { aDone } from './a.mjs';
export let bDone = false;
console.log('b starts, aDone:', aDone);  // aDone is live binding — reads current value
bDone = true;
```

ESM's key advantage: because `aDone` is a live binding (not a copy), `b.mjs` always reads the current value of `a.mjs`'s `aDone` — even across circular dependencies. When the binding is accessed after `a.mjs` has set it to `true`, `b.mjs` sees `true`. This is more predictable than CJS's snapshot behavior, but the same rule applies: if you read a binding in module initialization code (not inside a function) before it's been set, you get the initial value.

The reliable pattern for both CJS and ESM circular dependencies: access circular imports inside functions (not at module level) — by the time those functions are called, all modules have completed initialization.

## Section 7: Interoperability

**Q17. How do CJS and ESM interoperate in Node.js, and what are the rules?**
A: Node.js determines module type by file extension and `package.json`:

```
File extensions:
  .js      → follows package.json "type" field ("commonjs" or "module")
  .cjs     → always CommonJS
  .mjs     → always ESM (ES Module)
  (default package.json "type": "commonjs" if not specified)
```

**ESM importing CJS** (works, with limitations):
```javascript
// utils.cjs
module.exports = { add: (a, b) => a + b, PI: 3.14 };

// main.mjs (ESM importing CJS)
import utils from './utils.cjs';           // default import gets entire module.exports
const { add, PI } = utils;                // destructure manually

// Named imports DON'T work for CJS (Node.js cannot statically analyze CJS exports):
import { add } from './utils.cjs';         // May fail or may work (Node.js has limited
                                           // static CJS export detection since v12.22)
// Rule of thumb: always use default import for CJS modules, then destructure
```

**CJS importing ESM** (DOES NOT WORK — fundamental incompatibility):
```javascript
// main.cjs
const utils = require('./utils.mjs');  // ERROR: require() of ES Module not supported
```

Why CJS can't `require()` ESM: CJS `require()` is synchronous, but ESM loading is always asynchronous (even from the filesystem in Node.js, to maintain the three-phase spec semantics). A synchronous function cannot await an asynchronous operation.

**The workaround** — CJS can use dynamic `import()` to load ESM asynchronously:
```javascript
// main.cjs — using dynamic import() to load an ESM module
async function loadESMModule() {
    const { default: utils, helper } = await import('./utils.mjs');
    console.log(utils.PI);
    helper();
}
loadESMModule();

// Or using `.then()` at module level:
import('./utils.mjs').then(({ default: utils }) => {
    utils.init();
});
```

**Q18. How do you write a package that supports both CJS and ESM consumers?**
A: The "dual package" pattern uses the `exports` field in `package.json` to provide different entry points for CJS and ESM consumers:

**Option 1 — Dual package (two separate builds)**:
```json
{
    "name": "my-library",
    "version": "1.0.0",
    "main": "./dist/index.cjs",
    "module": "./dist/index.mjs",
    "exports": {
        ".": {
            "import": "./dist/index.mjs",
            "require": "./dist/index.cjs",
            "default": "./dist/index.cjs"
        },
        "./utils": {
            "import": "./dist/utils.mjs",
            "require": "./dist/utils.cjs"
        }
    }
}
```
Build tools (tsup, rollup, esbuild) generate both `.cjs` and `.mjs` from the same TypeScript/ESM source. Both builds contain the same code with different module syntax. The `exports` map routes ESM consumers (`import`) to the `.mjs` file and CJS consumers (`require`) to the `.cjs` file automatically.

**Option 2 — ESM-only package with CJS wrapper**:
```javascript
// dist/index.cjs (thin CJS wrapper)
const mod = require('./index-cjs-bridge.cjs');
module.exports = mod;
// Or use a build tool that generates this automatically
```

**Option 3 — CJS-only package** (if the package can't support ESM yet): most widely compatible, no tree shaking, but works everywhere. Acceptable for internal tools, CLIs, and packages that don't benefit from tree shaking.

**The "dual package hazard"**: if both the CJS and ESM builds of a package export stateful singletons (like a singleton database connection, a logger instance, or a global event emitter), a consumer using both CJS and ESM paths could get two separate singleton instances — state is not shared between them. Mitigation: design stateful singletons as a separate CJS-only package (or use the `package.json` `exports` map to ensure only one code path is ever loaded).

## Section 8: Tree Shaking and Bundlers

**Q19. What is tree shaking and why does CJS prevent it?**
A: Tree shaking is a bundler optimization that eliminates unused exports from the final bundle. If you `import { add } from './math.js'` but `math.js` also exports `subtract`, `multiply`, and `divide`, tree shaking removes those three unused exports from the bundle — potentially saving significant bytes:

```javascript
// math.js (ESM — tree-shakeable)
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }
export function multiply(a, b) { return a * b; }

// consumer.js
import { add } from './math.js';  // only `add` is imported

// After tree shaking (bundle only contains):
// function add(a, b) { return a + b; }
// (subtract and multiply are eliminated — ~30% bundle size reduction)
```

Why CJS prevents tree shaking:
```javascript
// math.cjs (CJS — not tree-shakeable)
module.exports = {
    add: (a, b) => a + b,
    subtract: (a, b) => a - b,
    multiply: (a, b) => a * b
};

// consumer.cjs
const { add } = require('./math.cjs');  // runtime destructuring
// The bundler can't know at build time what this destructuring will produce
// because require() could return anything at runtime

// Even if the bundler is smart enough to analyze this specific case,
// CJS allows patterns like:
const which = Math.random() > 0.5 ? 'add' : 'subtract';
const fn = require('./math')[which];  // dynamic property access — impossible to tree-shake
```

The bundler (webpack, rollup, esbuild) needs to know at build time which exports will definitely not be used. ESM's static structure provides this guarantee; CJS's runtime nature does not.

**Q20. What is the `sideEffects` field in `package.json` and how does it work with tree shaking?**
A: Tree shaking only removes exports that are never imported — but bundlers are conservative about removing entire modules because a module might have side effects (code that runs for global effect, not for its exports):

```javascript
// sideEffect.js — has side effects even without being imported
import './polyfill.js';       // adds methods to global objects
import 'css-file.css';       // injects styles
window.MyGlobal = 'hello';  // modifies global state
```

The `sideEffects` field tells bundlers which files are safe to remove if their exports are unused:

```json
{
    "sideEffects": false
}
// "All files in this package have no side effects"
// The bundler can safely eliminate any file whose exports aren't imported

// Or specify which files DO have side effects:
{
    "sideEffects": [
        "./src/polyfills.js",
        "*.css",
        "./src/global-setup.js"
    ]
}
```

Without `"sideEffects": false`, webpack's tree shaking is conservative — it keeps all modules that are referenced anywhere in the import graph, even if their exports are unused. With `"sideEffects": false`, a module whose exports are completely unused can be entirely removed from the bundle, including its module-level code.

This is why popular libraries (React, lodash-es, date-fns) include `"sideEffects": false` in their `package.json` — it enables users to import only the specific utilities they need without pulling in the entire library.

## Section 9: Node.js-Specific Concerns

**Q21. How do you configure a Node.js project to use ESM, and what are the common gotchas?**
A: Three ways to enable ESM in Node.js:

**Method 1 — `"type": "module"` in `package.json`** (recommended for ESM-first projects):
```json
{
    "type": "module"
}
```
All `.js` files in the package are now treated as ESM. Use `.cjs` extension for any files that must be CJS.

**Method 2 — `.mjs` file extension**: individual files with `.mjs` are always ESM, regardless of `package.json`. No package-level config change needed.

**Method 3 — `--input-type=module` flag** (for stdin or direct eval only).

**Common gotchas**:

```javascript
// Gotcha 1: __dirname and __filename don't exist in ESM
// CJS: __dirname and __filename are injected by the module wrapper
// ESM: no such injection — use import.meta.url instead
import { fileURLToPath } from 'url';
import { dirname } from 'path';
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// Gotcha 2: require() doesn't exist in ESM
// Use createRequire() if you need to require a CJS module:
import { createRequire } from 'module';
const require = createRequire(import.meta.url);
const lodash = require('lodash');  // now usable

// Gotcha 3: JSON imports require an assertion (Node 17.5+ / ESM spec)
import config from './config.json' assert { type: 'json' };
// Or use createRequire (above) for JSON in older Node versions

// Gotcha 4: Named exports from CJS packages are not guaranteed
// Instead of:
import { readFileSync } from 'fs';  // works (Node.js special-cases built-ins)
import { map } from 'lodash';       // may NOT work (CJS package)
// Use:
import lodash from 'lodash';
const { map } = lodash;

// Gotcha 5: Top-level await changes module timing
// If a module uses top-level await, ALL modules that import it
// wait for its await to resolve before their own code runs
```

**Q22. What is `import.meta` in ESM and what properties does it expose?**
A: `import.meta` is an object available inside ESM modules that provides module-specific context information — analogous to CJS's `__filename`, `__dirname`, and `module` object but as a single meta object:

```javascript
// import.meta.url — the current module's URL (file:// in Node, https:// in browsers)
console.log(import.meta.url);
// Node.js: 'file:///home/user/project/src/utils.mjs'
// Browser: 'https://example.com/src/utils.js'

// import.meta.resolve() (Node.js 20.6+) — resolve a specifier relative to current module
const resolvedPath = await import.meta.resolve('./helper.js');

// import.meta.env (Vite) — environment variables exposed to the client bundle
console.log(import.meta.env.VITE_API_URL);

// Deriving __dirname equivalent:
import { fileURLToPath } from 'url';
import { dirname, join } from 'path';
const __dirname = dirname(fileURLToPath(import.meta.url));
const configPath = join(__dirname, 'config.json');  // same as CJS

// import.meta.main (Deno equivalent of require.main === module in CJS):
// In Deno: if (import.meta.main) { main(); } — detect if file is entry point
```

## Section 10: Scenario-Based Questions

**Q23. "What does this code output, and why?"**

```javascript
// logger.cjs
let instanceCount = 0;
function Logger(name) {
    instanceCount++;
    this.name = name;
    this.id = instanceCount;
}
Logger.prototype.log = function(msg) {
    console.log(`[${this.name}#${this.id}] ${msg}`);
};
module.exports = Logger;

// a.cjs
const Logger = require('./logger.cjs');
const logA = new Logger('A');
module.exports = { logA };

// b.cjs
const Logger = require('./logger.cjs');
const logB = new Logger('B');
module.exports = { logB };

// main.cjs
const { logA } = require('./a.cjs');
const { logB } = require('./b.cjs');
logA.log('hello');
logB.log('world');
console.log(logA instanceof require('./logger.cjs'));
```

A: Walking through the execution order:
1. `require('./a.cjs')` → `a.cjs` requires `logger.cjs` → `logger.cjs` executes, `instanceCount = 0`, registers in cache. Returns `Logger` constructor. `a.cjs` creates `new Logger('A')`: `instanceCount++` → 1, `logA.id = 1`. `a.cjs` exports `{ logA }`.
2. `require('./b.cjs')` → `b.cjs` requires `logger.cjs` → **cache hit** — same module object returned, `instanceCount` is **shared** (still 1 from step 1, on the already-loaded module). Creates `new Logger('B')`: `instanceCount++` → 2, `logB.id = 2`.
3. `logA.log('hello')` → `[A#1] hello`
4. `logB.log('world')` → `[B#2] world`
5. `logA instanceof require('./logger.cjs')` → requires `logger.cjs` → **cache hit** again, same `Logger` function. `logA.__proto__ === Logger.prototype` → **`true`**

Output:
```
[A#1] hello
[B#2] world
true
```

Key insight: CJS module caching means `instanceCount` is shared across all `require('./logger.cjs')` calls — the module is a singleton. `logA.id = 1` and `logB.id = 2` because both modules share the same `instanceCount` variable from the one cached module execution.

**Q24. "A library author is migrating a utility package from CJS to ESM. The package exports 50 utility functions. What are the key decisions and potential breaking changes?"**
A: A structured migration analysis:

**Step 1 — Define the target state**:
Decide between: (a) ESM-only (simplest, breaks CJS consumers until they update), (b) dual CJS+ESM package (`exports` map with both paths — maximum compatibility, more build complexity), or (c) CJS with added `.mjs` files (easiest transition). For a utility package with broad adoption, dual package is correct.

**Step 2 — The `package.json` changes**:
```json
{
    "main": "./dist/index.cjs",
    "module": "./dist/index.mjs",
    "exports": {
        ".": {
            "import": "./dist/index.mjs",
            "require": "./dist/index.cjs"
        }
    },
    "sideEffects": false
}
```
Adding `sideEffects: false` is safe for a pure utility package and enables tree shaking for ESM consumers.

**Step 3 — Named exports are the right choice** (not a default export): 50 utility functions should be named exports. A default export of an object (`export default { fn1, fn2, ... }`) would prevent tree shaking (the bundler can't tell which functions are unused). Named exports let consumers import only what they use.

**Step 4 — Breaking changes to warn consumers about**:
- CJS consumers using `const utils = require('my-lib')` and calling `utils.fn1()` still work (ESM's named exports become properties of the `module.exports` object in the CJS build).
- `require.resolve('my-lib')` behavior changes if the `exports` map restricts sub-path access.
- Any `require('my-lib/internal/helper')` (deep imports to non-exported paths) **break** — the `exports` map makes only explicitly listed paths accessible. This is intentional (enforcing the public API) but a breaking change for consumers accessing internals.
- The singleton behavior changes for ESM consumers: ESM modules with `"type": "module"` get live bindings instead of value copies — any exported mutable state behaves differently.

**Step 5 — Build tooling**:
Use `tsup`, `rollup`, or `esbuild` configured to output both `.cjs` and `.mjs` from the same source. Include a type declaration file (`.d.ts`) via the `types` field in the `exports` map.

**Q25. "A developer is debugging why their bundle size hasn't decreased after switching from `import lodash from 'lodash'` to named imports from lodash-es. What might be wrong?"**
A: Several possible causes, each revealing a different aspect of tree shaking:

**Cause 1 — Using `lodash` (CJS) instead of `lodash-es` (ESM)**:
```javascript
import { map } from 'lodash';  // WRONG: lodash is CJS, no tree shaking possible
import { map } from 'lodash-es';  // CORRECT: ESM version, tree shakeable
```

**Cause 2 — The consuming file is in a non-ESM context**:
Tree shaking requires the bundler to process the imports as ESM. If `babel-preset-env` is configured with `modules: 'commonjs'`, Babel converts `import` statements to `require()` before the bundler sees them — destroying tree shaking. Fix: `modules: false` in Babel config to preserve ESM syntax for the bundler.

**Cause 3 — Missing `"sideEffects": false` in lodash-es**:
Check `node_modules/lodash-es/package.json` — if there's no `"sideEffects": false`, webpack keeps all touched modules. Modern `lodash-es` versions include this, but older versions may not.

**Cause 4 — Webpack's `optimization.usedExports` is not enabled**:
Tree shaking in webpack requires `mode: 'production'` (which enables `optimization.usedExports: true` and `optimization.minimize: true`) or manually setting these options. Development mode doesn't tree shake (for faster rebuild speed).

**Cause 5 — Dynamic property access**:
```javascript
const fn = lodashEs[someVariable];  // webpack can't tree shake this
```

**Cause 6 — Re-exports breaking tree shaking in some configurations**:
Some barrel file patterns (`export * from './map'`) can confuse webpack's tree shaking analysis. Check if lodash-es's entry point is a barrel file and whether the bundler correctly resolves to individual function files.

## Quick Reference Table

| Dimension | CommonJS (CJS) | ESM |
|---|---|---|
| Syntax | `require()` / `module.exports` | `import` / `export` |
| Loading | Synchronous, runtime | Async phases: parse, link, evaluate |
| Binding type | Value copy at `require()` time | Live binding (reference) |
| Top-level `await` | ❌ Not possible | ✅ Supported |
| `import()` dynamic | ✅ Via `import()` async | ✅ `import()` is ESM-native |
| Tree shakeable | ❌ (runtime require) | ✅ (static analysis) |
| Circular deps | Partial exports (snapshot) | Live bindings (updatable) |
| `__filename` / `__dirname` | ✅ Injected automatically | ❌ Use `import.meta.url` |
| JSON import | ✅ `require('./config.json')` | ✅ With `assert { type: 'json' }` |
| Browser native | ❌ Needs bundler | ✅ `<script type="module">` |
| Node.js default | ✅ (without `"type": "module"`) | ✅ (with `.mjs` or `"type": "module"`) |
| CJS → ESM | `import()` (async only) | ✅ Direct |
| ESM → CJS | ✅ Via default import | — |

**Tip for interviews:** Five things separate strong candidates on CJS vs ESM: (1) explaining **live bindings vs value copies** (Q7) with a concrete counter example — this is the most surprising semantic difference and demonstrates you've actually used both in production rather than just read documentation; (2) knowing the **`exports` vs `module.exports` trap** (Q8) and being able to explain *why* reassigning `exports` silently fails — this is a classic Node.js gotcha that appears in real codebases; (3) articulating **why tree shaking requires static analysis** (Q19) and precisely why CJS can't be tree-shaken — not just "ESM is better" but the specific mechanism (runtime `require()` vs compile-time `import` resolution); (4) knowing that **CJS cannot `require()` ESM** (Q17) but ESM can import CJS with limitations — and knowing the dynamic `import()` workaround for the reverse — this is essential for modern Node.js package development; and (5) being aware of the **dual package hazard** (Q18) for stateful singletons — this demonstrates experience with the actual operational complexity of supporting both module systems, not just the syntax differences.
