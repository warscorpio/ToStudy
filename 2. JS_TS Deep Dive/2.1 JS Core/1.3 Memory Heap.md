# JavaScript Core (Fundamentals): Memory Heap — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the memory heap?**
A: The memory heap is an unstructured region of memory where the JavaScript engine dynamically allocates memory for objects, arrays, functions, and closures at runtime. Unlike the call stack (which is ordered and size-constrained), the heap is a large, flexible pool — things are allocated and freed in no particular order, managed by the garbage collector rather than by a rigid push/pop discipline.

**Q2. What's the difference between the heap and the call stack in terms of what gets stored where?**
A: The call stack stores primitive values (numbers, booleans, `null`, `undefined`, strings — small, fixed-size) and references (pointers) to objects. The actual objects, arrays, functions, and closures live on the heap. So `const obj = { a: 1 }` puts the reference to `obj` on the stack (or in the variable environment), and the object `{ a: 1 }` itself is allocated on the heap.

**Q3. Is that "primitives on the stack, objects on the heap" rule always exactly true?**
A: It's a useful mental model, but engines optimize aggressively. V8 may inline small objects, store certain values in registers, or use techniques like pointer tagging (encoding small integers directly in a pointer without a heap allocation). The rule describes the conceptual model — what matters in interviews is the behavioral consequence: primitives are copied by value, objects are passed by reference (pointer to the heap allocation).

**Q4. Who manages heap memory in JavaScript — the developer or the engine?**
A: The engine, via its garbage collector. Unlike C/C++ where you `malloc`/`free` manually, JS developers never explicitly deallocate memory. The GC periodically identifies objects that are no longer reachable and reclaims their heap space. This removes a whole class of bugs (use-after-free, double-free) but introduces a different one: memory leaks, where objects stay reachable (via a reference you forgot to clear) longer than intended.

**Q5. What does "heap size" mean, and is it bounded?**
A: Heap size is the total memory the engine has allocated for all live objects. It's bounded — V8 has a default heap size limit (~1.5 GB on 64-bit, less on 32-bit) that can be raised via `--max-old-space-size` in Node. Exceeding it throws a fatal `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` crash — unlike a stack overflow, this is often caused by a true memory leak rather than a coding logic error.

## Section 2: Garbage Collection

**Q6. What is garbage collection (GC), and what algorithm does V8 use?**
A: Garbage collection is the automatic process of finding heap objects that are no longer reachable from any live reference and reclaiming their memory. V8 uses a **generational garbage collector** with two main regions:
- **Young generation (Nursery / "Scavenger")** — new allocations go here first; GC runs frequently and fast (minor GC).
- **Old generation (Tenured)** — objects that survive one or more young-gen collections are promoted here; GC runs less often but is more expensive (major GC / Mark-Sweep-Compact).

**Q7. What is the Mark-and-Sweep algorithm?**
A: The core algorithm behind most major GC passes:
1. **Mark** — starting from "GC roots" (global variables, the call stack, CPU registers), the GC traverses all reachable object references and marks every reachable object.
2. **Sweep** — any heap object that wasn't marked is unreachable, so its memory is freed and returned to the allocator.
3. **Compact** (optional) — surviving objects may be compacted together to reduce heap fragmentation, at the cost of updating all references to moved objects.

**Q8. What are GC roots?**
A: The starting points the garbage collector uses to trace which heap objects are reachable. Roots include: global variables, variables in active stack frames (the call stack), CPU registers, and VM internals. Anything reachable by following references from a root is considered live; everything else is collectible.

**Q9. What is generational GC, and why does it help performance?**
A: It exploits the "generational hypothesis" — most objects die young (they're temporary values created and discarded quickly). By dividing the heap into young and old generations, the GC can run fast, small collections on the young generation (where most garbage is) very frequently, without touching the much larger old generation. Old-gen collections (major GC) happen rarely but pause longer — V8 uses incremental and concurrent techniques to spread that work out and reduce pause time.

**Q10. What is "stop-the-world" GC, and does modern V8 suffer from it?**
A: A stop-the-world GC pause halts all JS execution while the GC runs, causing noticeable jank (frame drops, frozen UI). Early GC implementations were fully stop-the-world. Modern V8 minimizes this with:
- **Incremental GC** — breaks major GC work into small slices interleaved with JS execution.
- **Concurrent GC** — performs marking/sweeping on background threads in parallel with JS execution.
- **Parallel GC** — uses multiple threads during the stop-the-world portion to finish it faster.
The result: major GC pauses are much shorter than they used to be, but they still exist and can still cause frame drops in animation-heavy code.

## Section 3: Memory Leaks

**Q11. What is a memory leak in JavaScript?**
A: A memory leak is when heap-allocated objects that are no longer needed by application logic remain reachable (via some live reference the developer forgot to clear), so the GC can't collect them. The heap keeps growing over time until the app slows down, the tab crashes, or the Node process hits the heap limit.

**Q12. What are the most common causes of memory leaks in JavaScript?**
A: Five patterns account for most real-world leaks:
1. **Forgotten event listeners** — adding a listener to a DOM node (or an emitter) and never removing it keeps the callback (and everything it closes over) alive as long as the node exists.
2. **Closures holding large outer scope references** — a closure capturing a large variable (a big array, a DOM tree) stays in memory as long as the closure is reachable, even if the outer function finished.
3. **Detached DOM nodes** — removing a node from the DOM but keeping a JS reference to it (`const el = document.querySelector(...)`) keeps the node and its entire subtree alive on the heap.
4. **Global variables** — accidentally assigning to an undeclared variable in non-strict mode creates a global (`this.leak = bigData`), which is a GC root and never collected.
5. **Timers/intervals not cleared** — a `setInterval` callback keeps a reference to everything it closes over alive indefinitely if `clearInterval` is never called.

**Q13. Why is a detached DOM node a leak, even though it's not in the document?**
A: The GC traces reachability from roots, not from the DOM tree. If a JS variable holds a reference to a removed DOM node, that node is still reachable from the call stack or a closure — so the GC considers it live. The entire subtree of that detached node is also kept alive (since the node holds references to its children). The fix is to null out the JS reference (`el = null`) once you no longer need it.

**Q14. How does an unremoved event listener cause a leak?**
A: When you do `element.addEventListener('click', handler)`, the element holds a reference to `handler`. `handler` (a closure) holds a reference to everything in its outer scope. As long as `element` itself is alive (in the DOM), `handler` and its entire closure scope are GC-unreachable for collection. If you later remove `element` from the DOM but don't call `removeEventListener`, modern engines may still collect it (if no other reference to `element` exists), but in older engines or when `element` is kept alive elsewhere, this is a classic leak.

**Q15. What is a "closure leak," and how does it differ from a normal closure?**
A: A closure is only a leak when it's kept alive longer than necessary while holding a large object in scope. Example: a factory function builds a large buffer, returns a tiny callback that only uses one field, but the callback's closure keeps the *entire* buffer in memory because V8's closure captures the full variable environment of the outer scope, not just the variables the inner function actually touches. The fix is to extract only what you need into a local variable before the closure, so the large object can be collected when the outer function returns.

## Section 4: Identifying & Fixing Leaks

**Q16. How do you identify a memory leak in a browser app?**
A: Chrome DevTools workflow:
1. **Memory tab → Heap Snapshot** — take a snapshot of the current heap, perform actions that might cause a leak, take another snapshot, compare. Objects that grew or weren't collected between snapshots are suspects.
2. **Memory tab → Allocation Timeline** — records heap allocations over time; shows a pattern of increasing retained memory (blue bars that never get collected).
3. **Performance tab** — the "Memory" checkbox shows JS heap size over time on the timeline; a consistently rising sawtooth (allocations go up, GC brings it down less each time) signals a leak.

**Q17. What is "retained size" vs "shallow size" in a heap snapshot?**
A: 
- **Shallow size** — the memory occupied by the object itself (its own fields/slots), not counting anything it points to.
- **Retained size** — the total memory that would be freed if this object were collected, including everything in the subgraph of objects that are only reachable through it. The retained size is what matters for diagnosing leaks — a small object with a huge retained size is holding a lot of other memory hostage.

**Q18. What is the "detached DOM tree" view in heap snapshots, and why is it useful?**
A: In Chrome's heap snapshot, you can filter by "Detached DOM trees" — nodes that have been removed from the live document but are still retained in JS memory. This is one of the fastest ways to catch the detached-node leak pattern, since it isolates exactly the problematic objects without you having to dig through the entire heap.

**Q19. How do you detect a memory leak in a Node.js service?**
A: Several approaches:
- Monitor process memory over time: `process.memoryUsage().heapUsed` — a consistently growing value under stable load is a signal.
- Use `--inspect` flag + Chrome DevTools remote debugging to take heap snapshots of a Node process.
- Use `node --heap-prof` or the `v8-profiler-next` / `heapdump` npm packages to generate heap snapshots programmatically.
- Under production load, watch for the process's RSS (resident set size) growing unboundedly — a typical sign of a leak in a long-running server.

**Q20. What does `WeakMap` / `WeakRef` have to do with memory management?**
A: `WeakMap` and `WeakSet` hold *weak references* to their keys — the GC does not consider a `WeakMap` key as a "live reference" for reachability purposes. If the only remaining references to an object are in a `WeakMap`, the GC can collect it and the `WeakMap` entry silently disappears. This is the right data structure for metadata caches keyed by object identity (e.g., DOM node → metadata) because the metadata is automatically cleaned up when the node is collected, preventing the leak. `WeakRef` (ES2021) similarly allows holding a "weak" reference you can dereference — but the object may have been collected, so you always check if it's still alive.

## Section 5: Advanced & Engine Internals

**Q21. What is heap fragmentation, and why does it matter?**
A: Fragmentation happens when freed memory is scattered in small non-contiguous chunks that can't be reused for a large allocation, even though the total free space is sufficient. The GC's compaction step addresses this by moving live objects together and updating references, but compaction is expensive (it's a stop-the-world operation). High fragmentation can cause seemingly unexplained out-of-memory errors even when `heapUsed` looks manageable — the heap is free, but not contiguously.

**Q22. What is V8's "hidden class" (Shape/Map) system, and what does it have to do with heap layout?**
A: V8 creates an internal "hidden class" (also called a Shape or Map) for every object structure it sees. Objects with the same properties in the same order share a hidden class and are stored in a memory-efficient, array-like layout (fast properties). When you add properties to an object in inconsistent order, or delete properties, V8 has to create new hidden classes and may fall back to a slower dictionary-mode layout (storing properties in a hash map on the heap). From a memory perspective: monomorphic, consistently structured objects are compact and fast; polymorphic objects with unpredictable shapes use more memory and are slower to access.

**Q23. What is the difference between "shallow heap" memory and "native memory" in Node.js, and why might `heapUsed` look fine while the process still consumes a lot of RAM?**
A: `process.memoryUsage().heapUsed` only covers the V8-managed JS heap. Node processes also consume:
- **Native memory** — memory allocated by native addons or Node's own internals (libuv, OpenSSL) outside the V8 heap.
- **Buffer/ArrayBuffer** — Node's `Buffer` and typed arrays backed by `ArrayBuffer` are allocated outside the V8 heap (in "external" or "array buffer" memory), so they don't show up in `heapUsed` even though they count toward RSS. A process streaming large files or handling binary data can have a low `heapUsed` but a high RSS precisely because of this.

**Q24. What is `ArrayBuffer` and typed arrays' relationship to the heap?**
A: `ArrayBuffer` represents a fixed-length raw binary data buffer allocated *outside* the normal V8 heap (in external memory). Typed arrays (`Uint8Array`, `Float64Array`, etc.) are views into an `ArrayBuffer`. This means large binary data doesn't bloat the V8 heap — but it still consumes process memory and must be managed carefully. `Buffer` in Node is a subclass of `Uint8Array` backed by the same external allocation model.

## Section 6: Scenario / System Design Style Questions

**Q25. "A long-running Node.js API server gradually consumes more and more memory over 24 hours until it OOMs and restarts. How do you investigate?"**
A: Structured approach:
1. Confirm it's a leak: graph `heapUsed` over time (via a metrics agent or periodic `process.memoryUsage()` logging) — if it grows monotonically without plateauing, it's a leak.
2. Narrow to heap vs external: also check `external` and `arrayBuffers` fields in `memoryUsage()` — if it's external memory, suspect Buffers or native modules.
3. Take heap snapshots at T=0, T=1hr, T=8hr using `--inspect` + Chrome DevTools or a heapdump. Compare — which constructor names / object types are growing?
4. Check for the classic patterns: long-lived caches without eviction (LRU?), event emitters where listeners accumulate, closures in request handlers capturing request objects, or global Maps/Sets that grow with each request.
5. Once identified, verify the fix by running the patched service under the same load and confirming `heapUsed` stabilizes.

**Q26. "A React SPA feels sluggish after being left open for several hours, but a page refresh fixes it. What would you look at?"**
A: Classic long-lived SPA leak symptoms. Investigation path:
- Record a heap allocation timeline in DevTools while navigating the app for a few minutes — look for memory that's allocated but never freed across route changes.
- Check for components that register global event listeners (`window.addEventListener`) in `useEffect` without returning a cleanup function — listeners accumulate with each mount.
- Check for timers (`setInterval`, `setTimeout`) not cleared on unmount.
- Look for a global store (Redux, Zustand, a module-level cache) that keeps growing — e.g., caching every API response ever fetched without an eviction policy.
- Take two heap snapshots (fresh load vs after an hour of use), filter by "Objects allocated between snapshots," and sort by retained size to find the culprit.

**Q27. "You have a utility function that processes large files and returns a small summary object. A colleague reports that memory usage spikes and doesn't fully recover after each call. What might be wrong?"**
A: Several suspects:
- The large file content (a `Buffer` or string) is being captured in a closure or stored in a module-level cache/variable that's never cleared — keeping the large allocation live even after the function returns.
- A `Promise` chain or async generator is keeping intermediate large objects alive longer than expected due to how closures capture the surrounding scope.
- The summary object holds a reference (directly or indirectly) to the original large data — e.g., a slice of a Buffer still pins the entire underlying `ArrayBuffer`.
Fix: explicitly null out large intermediate variables before returning, avoid capturing them in closures, and consider using streaming APIs (`fs.createReadStream`) instead of loading entire files into memory at once.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                  | Memory Heap                                        | Call Stack                                    |
|---                      |---                                                  |---                                            |
| What lives here         | Objects, arrays, functions, closures               | Primitive values, references, stack frames    |
| Structure               | Unstructured / dynamic                             | Ordered LIFO                                  |
| Size limit              | Large (~1.5 GB default in V8, configurable)        | Small (~10k–15k frames)                       |
| Managed by              | Garbage collector (automatic)                      | Engine (push/pop on function call/return)     |
| Overflow error          | `Heap out of memory` (OOM crash)                  | `RangeError: Maximum call stack size exceeded`|
| Allocation speed        | Slower (GC overhead, fragmentation)                | Faster (simple pointer increment)             |
| Lifetime of data        | Until GC collects (no live references)             | Until function returns (frame popped)         |
| Leak risk               | High (forgotten references prevent collection)     | Low (frames auto-popped on return)            |

---

**Tip for the interview:** At the 5 YOE level, heap questions almost always land on one of two angles: *how GC works* (generational, mark-and-sweep, what makes something collectable) or *diagnosing leaks* (the five common patterns and the DevTools workflow to find them). The whiteboard trap to watch for is conflating "the object isn't referenced anymore" with "the GC has freed it" — they're not the same moment. Be ready to describe a real leak you've hunted: what the symptom was, how you confirmed it was a leak (growing heap over time), how you found the culprit (snapshot diff, retained size), and what you changed to fix it. That story is worth more than a perfect recitation of the mark-and-sweep algorithm.
