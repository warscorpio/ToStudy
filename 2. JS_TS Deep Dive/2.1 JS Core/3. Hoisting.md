# JavaScript Core (Fundamentals): Hoisting — `var` vs `let` vs `const` Behavior — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is hoisting?**
A: Hoisting is the observable result of JavaScript's two-phase execution model. During the **creation phase** of an execution context, the engine scans the code and allocates memory for variable and function declarations *before* any code runs. The term "hoisting" is a mental shorthand — declarations are not physically moved; rather, memory is set aside for them before the execution phase begins. The behavior differs significantly between `var`, `let`/`const`, and function declarations.

**Q2. What are the two phases of execution that make hoisting possible?**
A:
- **Creation phase (Memory Allocation / Compilation phase)** — the engine scans the current scope, finds all declarations (`var`, `let`, `const`, `function`, `class`), and allocates memory for them. `var` is initialized to `undefined`; `let`/`const`/`class` are allocated but left *uninitialized* (TDZ); function declarations are stored in full.
- **Execution phase** — code runs line by line. Assignments happen, functions are called, and values are computed in source order.

**Q3. Is "hoisting" an official spec term?**
A: No — it's a community shorthand that doesn't appear in the ECMAScript specification. The spec describes the behavior in terms of binding instantiation and environment records. "Hoisting" is a useful mental model for interviews and everyday communication, but at a deep level what's actually happening is: during scope creation, the engine processes all declarations and creates bindings in the lexical/variable environment before stepping through code.

**Q4. What is the single most important practical difference between how `var` and `let`/`const` are hoisted?**
A: `var` is hoisted *and initialized to `undefined`* — so reading it before its assignment returns `undefined` without error. `let` and `const` are hoisted but *left uninitialized*, placing them in the Temporal Dead Zone — reading them before their declaration line throws a `ReferenceError`. In short: `var` hoisting is silently permissive; `let`/`const` hoisting is loudly restrictive.

**Q5. Why do all three technically "hoist" if `let`/`const` throw on early access?**
A: Because the binding itself *is* created at scope creation time — the engine knows about the variable before the declaration line executes. The proof: if `let`/`const` didn't hoist at all, an inner block referencing a same-named outer `let` would fall through to the outer binding. Instead it throws a TDZ error, proving the inner binding was created (and is blocking the lookup) even before the declaration line:
```js
let x = "outer";
{
  console.log(x); // ReferenceError — NOT "outer"
  let x = "inner"; // the inner binding exists from block start, TDZ until here
}
```
If `let` didn't hoist, `console.log(x)` would find the outer `x` and print `"outer"`. The TDZ error proves the inner binding was already registered.

## Section 2: `var` Hoisting in Depth

**Q6. What exactly happens to a `var` declaration during hoisting?**
A: During the creation phase, the engine finds `var x` anywhere in the function (or global scope) and:
1. Creates a binding named `x` in the variable environment.
2. Initializes it to `undefined` immediately.

At runtime, only the *assignment* (`x = 5`) stays in place at its original line. Reading `x` before the assignment is valid but returns `undefined`.

```js
function demo() {
  console.log(a); // undefined — binding exists, value not yet assigned
  var a = 10;
  console.log(a); // 10
}
```
Mentally equivalent to:
```js
function demo() {
  var a = undefined; // hoisted + initialized
  console.log(a);   // undefined
  a = 10;           // assignment stays in place
  console.log(a);   // 10
}
```

**Q7. Does `var` hoist to the top of its block, or the top of its function?**
A: The top of its *function* (or global scope if there's no enclosing function) — `var` is completely transparent to block boundaries. A `var` declared inside an `if`, `for`, `while`, or any other block hoists all the way up to the nearest enclosing function:
```js
function run() {
  console.log(x); // undefined — hoisted past the if block
  if (false) {
    var x = 99;   // never executes, but the declaration was hoisted
  }
  console.log(x); // undefined — assignment never ran
}
```

**Q8. Can `var` be declared multiple times in the same scope?**
A: Yes — `var` silently allows re-declaration in the same scope. The second declaration is effectively ignored (the binding already exists), but any assignment on the re-declaration line still executes:
```js
var count = 1;
var count = 2; // no error — just an assignment
console.log(count); // 2
```
This is a common source of bugs in large files where two developers unknowingly pick the same variable name.

**Q9. What happens when a `var` is declared inside a `for` loop — how does hoisting affect it?**
A: The `var` hoists to the enclosing function scope. There is only *one* binding shared across all loop iterations. This is the root cause of the classic closure-in-loop bug:
```js
function makeAdders() {
  var fns = [];
  for (var i = 0; i < 3; i++) {
    fns.push(function() { return i; });
  }
  return fns;
}
makeAdders()[0](); // 3 — all functions share the one hoisted 'i'
```

**Q10. Does `var` hoist across `try`/`catch`/`finally` blocks?**
A: Yes — `var` is function-scoped, so it hoists through `try`, `catch`, and `finally` block boundaries to the enclosing function. The error parameter in `catch (e)` is block-scoped to the `catch` clause, but any `var` declared *inside* `catch` still hoists to the function. This means a `var result` inside a `try` block is accessible after the `try`/`catch` completes — a sometimes-useful but often-confusing behavior that `let`/`const` eliminate.

## Section 3: `let` and `const` Hoisting & the Temporal Dead Zone

**Q11. What is the Temporal Dead Zone (TDZ) exactly?**
A: The TDZ is the period from the *start of the scope* (block or module) that contains a `let`/`const` declaration to the *exact line* where that declaration is encountered during execution. During this window, the binding exists (was registered at scope creation) but is uninitialized. Any read or write attempt throws `ReferenceError: Cannot access 'x' before initialization`. The TDZ ends the instant the declaration line executes and the variable is initialized.

**Q12. What is the difference in TDZ between `let` and `const`?**
A: Both enter the TDZ from the start of their block and exit when their declaration line executes. The only difference after the TDZ ends: `let` can be reassigned; `const` cannot. There is no difference in TDZ behavior between them — both throw the same `ReferenceError` if accessed during TDZ.

**Q13. Can a function defined in a block reference a `let` from the same block before the `let`'s declaration line?**
A: The function *definition* is fine — defining a function in a block that closes over a `let` is valid even if the `let` appears later in the block. The TDZ only applies when the function is *called* before the `let` is initialized:
```js
{
  function greet() {
    console.log(name); // valid to define — closes over 'name'
  }
  greet(); // ReferenceError — called while 'name' is in TDZ
  let name = "Alice";
  greet(); // "Alice" — TDZ has ended
}
```
This is a subtle TDZ edge case that trips up even experienced developers.

**Q14. Does the TDZ apply to function parameters?**
A: Default parameter values are evaluated left-to-right and can reference earlier parameters — earlier parameters are initialized before later ones. But a default value cannot reference a later parameter (it's in TDZ at that point):
```js
function foo(a = 1, b = a) { return [a, b]; }
foo(); // [1, 1] — fine, 'a' is initialized before 'b' default evaluates

function bar(a = b, b = 2) { return [a, b]; }
bar(); // ReferenceError — 'b' is in TDZ when 'a' default is evaluated
```

**Q15. Is there any way to observe that `let`/`const` are hoisted (other than the TDZ shadowing trick in Q5)?**
A: Yes — the same-name-in-inner-block proof from Q5 is the clearest. Another observable: in a module, `let`/`const` at the module's top level are known to the module's scope from the start, so circular imports can observe a TDZ error on the imported binding if the importing module runs code before the exporting module's declaration line executes. This is distinct from `var` (which would be `undefined`, not a TDZ error) and proves the binding was registered before execution began.

## Section 4: Function Declaration Hoisting

**Q16. How are function declarations hoisted differently from `var`?**
A: Function declarations are hoisted *completely* — both the name binding and the full function body are available from the start of the scope. This is why you can call a function declaration before its line in the source:
```js
greet(); // "Hello" — works, fully hoisted
function greet() { console.log("Hello"); }
```
`var` by contrast is only partially hoisted — the name exists but the value is `undefined` until the assignment line. Function expressions (assigned to a `var`/`let`/`const`) follow the hoisting rules of their variable, not function-declaration rules.

**Q17. What is the hoisting priority when a function declaration and a `var` share the same name?**
A: The function declaration takes priority during the creation phase — the binding is initialized with the function, not `undefined`. A subsequent `var` of the same name is effectively ignored (the binding already exists). However, if the execution phase encounters an assignment (`foo = 5`), it overwrites the function:
```js
console.log(typeof foo); // "function" — function declaration wins hoisting
var foo = 5;
console.log(typeof foo); // "number" — assignment at runtime overwrites it
function foo() {}
```

**Q18. Are function declarations inside blocks hoisted? Is this behavior reliable?**
A: This is one of the most inconsistent corners of the spec. In strict mode and ES modules, block-level function declarations are block-scoped (like `let`) — they don't hoist to the enclosing function. In non-strict (sloppy) mode classic scripts, browser implementations differ significantly — V8 applies a legacy compatibility behavior that partially hoists the name to the function scope as `undefined` while keeping the full binding block-scoped. The bottom line: **never rely on block-level function declarations in non-strict code**. Always use `const fn = function() {}` or `const fn = () => {}` inside blocks for predictable block scope.

**Q19. How are function expressions hoisted?**
A: Function expressions follow the hoisting behavior of their declaring keyword — not function-declaration rules:
- `var fn = function() {}` → `fn` is hoisted to `undefined`; the function isn't available until the assignment line.
- `let fn = function() {}` → `fn` is in TDZ until the assignment line.
- `const fn = function() {}` → same as `let` for hoisting; also can't be reassigned.

```js
console.log(typeof a); // "undefined" — var hoisted, function not yet assigned
console.log(typeof b); // ReferenceError — let in TDZ
var a = function() {};
let b = function() {};
```

## Section 5: Common Pitfalls & Tricky Patterns

**Q20. What does this print, and why?**
```js
var x = 1;
function outer() {
  console.log(x); // ?
  var x = 2;
}
outer();
console.log(x); // ?
```
A: Prints `undefined`, then `1`. Inside `outer`, `var x` is hoisted to the top of `outer`'s function scope — it *shadows* the global `x`. So `console.log(x)` inside `outer` reads `outer`'s local `x`, which is `undefined` at that point (hoisted but not yet assigned). The global `x` is untouched, so the second `console.log` outside `outer` prints `1`. A classic trap: the local `var` shadows the outer one even before its assignment line.

**Q21. What does this print?**
```js
let x = 1;
{
  console.log(x); // ?
  let x = 2;
}
```
A: `ReferenceError`. As proven in Q5, the inner `let x` is hoisted to the start of its block and enters TDZ. `console.log(x)` hits the TDZ of the *inner* `x` — it does not fall through to the outer `x = 1`. This surprises developers who expect it to print `1`.

**Q22. What does this print?**
```js
function test() {
  console.log(typeof fn); // ?
  var fn = function() { return 1; };
  console.log(typeof fn); // ?
}
test();
```
A: `"undefined"`, then `"function"`. `var fn` is hoisted and initialized to `undefined` in the creation phase. The function expression `function() { return 1; }` is only assigned to `fn` at runtime when that line executes. Before the assignment, `fn` exists but holds `undefined`.

**Q23. Why can this pattern fail unexpectedly with `const`?**
```js
const obj = {};
// ... many lines later in same scope ...
const obj = { key: "value" }; // ?
```
A: `SyntaxError: Identifier 'obj' has already been declared` — thrown at *parse time*, before any code runs. `const` (and `let`) do not allow re-declaration in the same scope. The error surfaces even before execution begins, unlike `var` which silently accepts re-declaration. This is intentional — it catches copy-paste or merge-conflict errors as early as possible.

**Q24. What is the "dead zone" for `class` declarations?**
A: `class` declarations behave identically to `let` for hoisting purposes — they're block-scoped and have a TDZ. You cannot instantiate a class before its declaration line:
```js
const a = new Animal(); // ReferenceError — Animal is in TDZ
class Animal {}
const b = new Animal(); // fine
```
This catches people who are used to function declarations (fully hoisted) and assume `class` works the same way. It doesn't — `class` follows `let`/`const` rules, not function-declaration rules.

**Q25. Does hoisting occur in ES modules?**
A: Yes — within a module, declarations are hoisted within the module's scope following the same rules (`var` to module scope, `let`/`const` TDZ within their blocks). But modules also introduce *live bindings* for exports — an imported binding is a live read-only view of the exporting module's variable, which means circular dependency issues can surface as TDZ errors on imported `let`/`const` bindings if the importer runs code before the exporter's declaration executes.

## Section 6: Scenario / System Design Style Questions

**Q26. "A developer reports a bug: a config value reads as `undefined` at the top of a function even though it's assigned a few lines later. They used `var`. Explain the bug and prescribe a fix."**
A: Textbook `var` hoisting. The `var config` declaration is hoisted to the top of the function and initialized to `undefined` before the function body executes. Any code that reads `config` before the assignment line encounters `undefined`, not the intended value. The fix options in order of preference:
1. Move the `var` declaration (and assignment) to the top of the function, before any code that reads it — respects how `var` actually works.
2. Replace `var` with `const` or `let` — if the read is genuinely before the assignment, this turns the silent `undefined` bug into a loud `ReferenceError`, making the mistake immediately obvious.
3. Restructure the function so config is loaded at the entry point and passed into any sub-operations that need it, rather than declared mid-function.

**Q27. "During a code review you spot this. What's wrong, and how would you fix it?"**
```js
function processQueue(queue) {
  for (var i = 0; i < queue.length; i++) {
    var item = queue[i];
    setTimeout(function() {
      sendToServer(item, i);
    }, i * 100);
  }
}
```
A: Two hoisting / scope problems:
1. `var i` — hoisted to `processQueue`'s function scope. All `setTimeout` callbacks close over the *same* `i`, which is `queue.length` by the time any callback fires.
2. `var item` — same problem. All callbacks share one `item` binding, which holds the last `queue[i]` assigned before the loop ended.

Both callbacks will call `sendToServer(lastItem, queue.length)` for every item — almost certainly a bug.

Fix: replace `var` with `let` — `let i` and `let item` create fresh per-iteration bindings that each closure captures independently:
```js
function processQueue(queue) {
  for (let i = 0; i < queue.length; i++) {
    const item = queue[i];
    setTimeout(function() {
      sendToServer(item, i);
    }, i * 100);
  }
}
```

**Q28. "A team migrated a codebase from non-strict to strict mode and immediately got ReferenceErrors on lines that worked fine before. The lines access variables declared with `let` earlier in the same file. What's likely happening?"**
A: The most likely cause is that the "earlier in the file" declarations are inside a different block scope than the access site — and the developer was relying on `var`-style function-scoped visibility. With `let`, a declaration in one block is invisible in a sibling or parent block that comes later in execution. Alternatively, the code might have function declarations in blocks that were partially hoisted in sloppy mode but are now fully block-scoped in strict mode — making previously "available" functions disappear.

Diagnostic steps: read the full `ReferenceError` message (it distinguishes "not defined" from "cannot access before initialization" — the former is a missing binding, the latter is TDZ). Use the scope panel in DevTools to confirm what's in scope at the error line. Then either restructure the code so declarations are in the right scope, or hoist the `let`/`const` declaration to the shared parent scope and assign inside the block.

**Q29. "You're reviewing a PR where a developer used a function declaration inside an `if` block to conditionally define behavior. Flag the risk and suggest an alternative."**
```js
if (featureFlag) {
  function handleEvent(e) { /* new behavior */ }
} else {
  function handleEvent(e) { /* old behavior */ }
}
element.addEventListener("click", handleEvent);
```
A: Block-level function declarations are one of the most browser-inconsistent behaviors in JS. In strict mode they're block-scoped and `handleEvent` won't be visible at the `addEventListener` line. In sloppy mode, different browsers apply different legacy hoisting rules — V8's behavior differs from older engines. The result: this code may work in Chrome dev builds but fail in production, or work in the browser but fail in Node tests.

Safe, predictable alternative:
```js
const handleEvent = featureFlag
  ? function(e) { /* new behavior */ }
  : function(e) { /* old behavior */ };
element.addEventListener("click", handleEvent);
```
Or with a `let` and explicit assignment:
```js
let handleEvent;
if (featureFlag) {
  handleEvent = function(e) { /* new behavior */ };
} else {
  handleEvent = function(e) { /* old behavior */ };
}
element.addEventListener("click", handleEvent);
```
Both approaches use `const`/`let` which are block-scoped and predictable across all environments.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                              | `var`                              | `let`                                | `const`                              | Function Declaration              |
|---                                  |---                                  |---                                    |---                                    |---                                 |
| Hoisted?                            | Yes                                | Yes                                   | Yes                                   | Yes                                |
| Initialized at hoist?               | Yes — `undefined`                  | No — TDZ                              | No — TDZ                              | Yes — full function body           |
| Accessible before declaration?      | Yes (returns `undefined`)          | No — `ReferenceError`                 | No — `ReferenceError`                 | Yes — fully callable               |
| Scope of hoist                      | Function (or global)               | Block                                 | Block                                 | Function (or global)*              |
| Re-declarable?                      | Yes (silent)                       | No — `SyntaxError`                    | No — `SyntaxError`                    | Yes (overwrites silently)          |
| Re-assignable?                      | Yes                                | Yes                                   | No (binding)                          | Yes (via assignment)               |
| `typeof` before declaration         | `"undefined"` (safe)              | `ReferenceError` (TDZ)                | `ReferenceError` (TDZ)                | `"function"` (safe)                |
| Per-iteration binding in `for`?     | No                                 | Yes                                   | Yes (`for...of`/`for...in` only)      | N/A                                |

*Block-level function declarations in sloppy mode are inconsistent across engines — avoid.

**Tip for the interview:** At the 5 YOE level, "explain hoisting" is just the warm-up. The real signal questions are the tricky snippet traces — the shadowing TDZ trap (Q21), the `var`-inside-function shadowing outer scope (Q20), function declaration vs function expression hoisting (Q22), and the `for`-loop closure bug (Q27). Practice narrating each one out loud in two layers: first what the *creation phase* sets up, then what the *execution phase* does line by line. Interviewers at this level want to hear "during the creation phase, the engine allocates…" not just "it's hoisted." Also have a concrete story ready — a `var`-hoisting bug you caught in review, a TDZ error that revealed a structural scope problem, or a block-level function declaration that behaved differently across environments. That anchors the theory in real judgment.
