# JavaScript Core (Fundamentals): Scope — Global Scope — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is scope in JavaScript?**
A: Scope is the set of rules that determines where a variable or function is accessible — which parts of the code can "see" and use a given identifier. JavaScript uses **lexical (static) scope**, meaning scope is determined by where code is *written* in the source, not by how or where it's *called* at runtime.

**Q2. What is the global scope?**
A: The global scope is the outermost scope in a JavaScript program — the scope that exists before any function or block is entered and persists for the entire lifetime of the program. Variables and functions declared at the top level (outside any function or block) live in the global scope and are accessible from anywhere in the codebase.

**Q3. What is the global object, and how does it relate to the global scope?**
A: The global object is the concrete object that backs the global scope — its properties *are* the global variables. In a browser it's `window`; in Node.js it's `global`; `globalThis` (ES2020) is the standard cross-environment reference. When you declare `var x = 1` at the top level of a script, `x` becomes a property of the global object (`window.x === 1` in a browser). `let` and `const` at the top level do *not* attach to the global object — they live in the global scope's declarative record but aren't properties of `window`/`global`.

**Q4. Why don't `let` and `const` attach to the global object, but `var` does?**
A: It comes down to how the spec separates the global environment record into two parts:
- **Object environment record** — backed by the global object; `var` declarations and function declarations land here (which is why they appear as `window.foo`).
- **Declarative environment record** — a separate, hidden store; `let`, `const`, and `class` declarations go here. They're globally scoped (accessible everywhere in the module/script), but they're not properties of `window`/`global`, so you can't accidentally conflict with or overwrite built-in globals like `window.name` by declaring `const name = "Alice"`.

**Q5. Is the global scope the same across all JavaScript environments?**
A: No. The global object and what it pre-populates differ:
- **Browser** — `window` includes DOM APIs (`document`, `fetch`, `setTimeout`, `alert`, etc.).
- **Node.js** — `global` includes `process`, `__dirname`, `__filename`, `Buffer`, `require`, etc. But notably, Node modules are each wrapped in a module function, so a bare `var x` at the top of a `.js` file is *not* truly global — it's local to that module wrapper. Only explicit `global.x = ...` assignments reach the true global.
- **Web Workers** — the global is `self`, with no `window` or DOM access.
- **`globalThis`** — ES2020 standard way to reference the global object without caring which environment you're in.

## Section 2: Variable Declarations & the Global Scope

**Q6. What is an "accidental global," and why is it dangerous?**
A: An accidental global happens when you assign to a variable that was never declared — in non-strict mode, JavaScript silently creates a property on the global object instead of throwing:
```js
function setName() {
  name = "Alice"; // no var/let/const — creates window.name in a browser
}
setName();
console.log(window.name); // "Alice"
```
It's dangerous because: the variable persists for the entire page lifetime (memory leak potential), it may silently overwrite an existing global (e.g., `window.name` is a real browser property), and it's invisible until something mysteriously reads the wrong value from the wrong place. `"use strict"` turns this into an immediate `ReferenceError`.

**Q7. How does `"use strict"` affect the global scope?**
A: In strict mode, undeclared variable assignments throw a `ReferenceError` immediately instead of creating an implicit global. It also changes `this` inside globally-called functions from the global object to `undefined`, making it safer to write functions that shouldn't be accidentally called as methods of the global object. Strict mode is applied per-script or per-function, not globally — ES modules are always in strict mode by default.

**Q8. What happens when `var`, `let`, and `const` are all declared at the global level?**
A: All three are accessible throughout the program (global scope), but they differ in three ways:

|                            | `var`                           | `let`         | `const` |
|--                         -|--                              -|--            -|---           |
| Attached to global object? | Yes (`window.x`)                | No            | No           |
| Hoisted?                   | Yes, initialized to `undefined` | Yes, but TDZ  | Yes, but TDZ |
| Re-declarable?             | Yes                             | No            | No           |
| Re-assignable?             | Yes                             | Yes           | No           |

**Q9. Does a function declaration at the top level go into the global scope?**
A: Yes — a top-level function declaration is hoisted and stored in the global object's object environment record (same as `var`), so `function foo() {}` at the top level makes `window.foo` available in a browser script. Inside a block (`if`, `for`, etc.), function declarations behave inconsistently across environments — it's safer to use `const foo = function() {}` inside blocks.

**Q10. Can you delete a global variable?**
A: It depends on how it was created:
- `var` declarations and function declarations at the top level: **cannot** be deleted (`delete window.x` returns `false` for declared vars — they have a `[[Configurable]]: false` property descriptor).
- Properties assigned directly to the global object (`window.x = 1` or accidental globals): **can** be deleted (`delete window.x` returns `true`).
- `let`/`const` globals: not on the global object at all, so `delete` is irrelevant — you can't delete them.

## Section 3: Scope Chain & Variable Lookup

**Q11. How does the scope chain work from within a nested function back to the global scope?**
A: Every execution context has a lexical environment that holds a reference to its outer environment. When the engine can't find a variable in the current scope, it walks up this chain — function scope → enclosing function scope → ... → global scope. If it reaches the global scope and still can't find the variable, it throws a `ReferenceError` (in strict mode) or, for assignments only, creates an accidental global (in non-strict mode).

**Q12. What is "variable shadowing," and what does it mean for the global scope?**
A: Shadowing occurs when an inner scope declares a variable with the same name as an outer (or global) scope variable. The inner declaration takes precedence within its scope, making the outer variable temporarily inaccessible by name — it's "shadowed." The global variable still exists and is unchanged; it just can't be reached by name from within the shadowing scope:
```js
var config = "global";
function init() {
  var config = "local"; // shadows the global
  console.log(config);  // "local"
}
init();
console.log(config);    // "global" — untouched
```
In a browser, `window.config` still reaches the global one from anywhere.

**Q13. What is the difference between a `ReferenceError` and reading `undefined` when accessing a global?**
A: A `ReferenceError` is thrown when the identifier itself doesn't exist anywhere in the scope chain — the engine can't find it at all. Reading `undefined` happens when the identifier *does* exist (e.g., a `var` that was declared but not yet assigned, or an explicit `= undefined` assignment). The practical difference: `console.log(x)` where `x` was never declared → `ReferenceError`; `var x; console.log(x)` → `undefined`.

## Section 4: Global Scope in Modules vs Scripts

**Q14. How does ES module scope differ from classic script scope?**
A: In an ES module (`<script type="module">` or `.mjs` files in Node), the top level is *module scope*, not global scope. Top-level `var`, `let`, `const`, and function declarations are local to the module — they don't become properties of `window`/`global` and aren't accessible to other scripts unless explicitly `export`ed. Modules are also always in strict mode. This is a fundamental shift from classic scripts, where all top-level declarations pollute the global object.

**Q15. If two classic `<script>` tags declare the same `var` name, what happens?**
A: In classic scripts (no modules), all scripts share the same global scope. The second `var` declaration of the same name is treated as a re-declaration (since `var` is re-declarable) — no error, and the value depends on execution order. This is a common source of bugs in legacy multi-script pages where two libraries both declare `var utils = ...` and one silently overwrites the other.

**Q16. How does CommonJS (Node.js `require`) handle the global scope vs ES modules?**
A: In CommonJS, every file is wrapped by Node in a function like:
```js
(function(exports, require, module, __filename, __dirname) {
  // your file content here
});
```
So a `var x` at the top of a CJS module is actually local to that wrapper function — it's *not* a true global. Only `global.x = ...` creates a real global in Node. ES modules in Node (`.mjs` or `"type": "module"` in `package.json`) follow the same module-scope isolation as in the browser.

**Q17. What is the `globalThis` proposal, and when would you actually use it?**
A: `globalThis` (ES2020) is a standardized reference to the global object across environments — it works in browsers (`window`), Node (`global`), Web Workers (`self`), and Deno. You use it when writing environment-agnostic utility code that needs to attach to or check the global object without sniffing the environment. In well-structured module-based codebases, direct use of `globalThis` is rare — it's mostly relevant in polyfills, universal libraries, or legacy code.

## Section 5: Pitfalls, Anti-patterns & Best Practices

**Q18. Why is polluting the global scope considered bad practice?**
A: Several reasons:
- **Name collisions** — two libraries or scripts using the same global name silently overwrite each other (the latter wins).
- **Implicit coupling** — code that reads from the global scope creates hidden dependencies that are invisible in function signatures and hard to trace.
- **Memory** — globals are GC roots and live for the entire page/process lifetime; large objects stored globally are never collected.
- **Testing difficulty** — global state shared between tests causes flaky, order-dependent test suites unless carefully reset between runs.
- **Security (in browsers)** — global variables are accessible to any injected script or third-party code running on the same page.

**Q19. What patterns do large legacy codebases use to avoid global namespace pollution?**
A: Before ES modules, several patterns emerged:
- **IIFE (Immediately Invoked Function Expression)** — wrap the entire library in `(function() { ... })()` to create a private function scope; only explicitly export things by attaching them to a single global namespace object (`window.MyLib = ...`).
- **Namespace object** — `var MyApp = MyApp || {}; MyApp.utils = { ... };` — a single global with everything nested inside it.
- **Revealing module pattern** — an IIFE that returns a public API object, storing private state in the function's closure.
- **AMD / CommonJS** — module systems that encapsulated files in functions before ES modules existed.

**Q20. What is the "single global variable" pattern, and is it still relevant?**
A: It's the practice of exposing exactly one name on the global object (e.g., `window.jQuery`, `window._`, `window.React` in old setups) and putting everything else inside it. It was the responsible approach in the pre-module era. Today it's largely irrelevant for new code (ES modules handle encapsulation), but it's still common in CDN-delivered libraries that need to work in environments without a module bundler.

**Q21. How do you safely check if a global variable exists without throwing a `ReferenceError`?**
A: Three safe approaches:
```js
// 1. typeof — never throws, even for undeclared identifiers
if (typeof someGlobal !== "undefined") { ... }

// 2. Direct property check on the global object — safe and explicit
if ("someGlobal" in window) { ... }   // browser
if ("someGlobal" in globalThis) { ... } // universal

// 3. Optional chaining on globalThis
if (globalThis.someGlobal) { ... }
```
Avoid a bare `if (someGlobal)` — if `someGlobal` was never declared, this throws a `ReferenceError` in strict mode.

## Section 6: Scenario / System Design Style Questions

**Q22. "A bug report says that one feature works fine in isolation but breaks when a certain third-party script is loaded on the same page. How would you investigate a global scope conflict?"**
A: Systematic approach:
1. Open DevTools console, search for the variable/function name in question — `window.x` — to see its current value and confirm it's on the global object.
2. Add a breakpoint or `Object.defineProperty(window, 'x', { set(v) { debugger; } })` to catch the moment something overwrites it.
3. Check both scripts for top-level `var` declarations or direct `window.x = ...` assignments with the same name.
4. Long-term fix: migrate the in-house code to ES modules (isolated scope by default), or namespace all globals under a unique prefix (`window.MyApp.x`).

**Q23. "You're reviewing a PR from a junior developer. You see `var userData = fetchUser()` at the top of a script file (not a module). What concerns do you raise?"**
A: Several:
- `var userData` at the top level of a classic script becomes `window.userData` — a global that persists for the page's lifetime, is accessible to any other script on the page (including ads, analytics, third-party widgets), and will never be garbage collected.
- If `fetchUser()` returns a large object or triggers a fetch, this couples the side effect to the global scope.
- If another script anywhere on the page happens to use `userData` as a variable name, one will silently overwrite the other.
- Suggested fixes: wrap in a module, move inside a function/class, use `let`/`const` (which at least won't attach to `window`), and separate the data fetching from its storage.

**Q24. "You're building a cross-environment utility (works in browser, Node, and Web Workers). How do you safely reference the global object and attach a polyfill to it?"**
A: Use `globalThis` — the only truly universal reference:
```js
(function (global) {
  if (!global.myPolyfill) {
    global.myPolyfill = function () { /* ... */ };
  }
})(globalThis);
```
Avoid `window`, `global`, or `self` directly — they'll throw `ReferenceError` in environments where they don't exist. Before `globalThis` was widely supported, libraries used a fallback chain: `typeof window !== "undefined" ? window : typeof global !== "undefined" ? global : this` — ugly but correct.

**Q25. "A Node.js microservice has a subtle bug: it occasionally serves stale data to users. After investigation you find `var cache = {}` at the top of `server.js` (CJS module). Is this actually a global? Could that be the bug?"**
A: In CJS, `var cache = {}` at the top of a file is *not* a true Node global — it's local to the module wrapper function. But it *is* module-level state — the same `cache` object is shared across every request handled by that module, because Node caches `require()`d modules and returns the same export object every time. So `cache` persists across requests for the lifetime of the process. If cache invalidation logic is missing or broken, every request reads from the same stale in-memory object. Fix: add TTL-based eviction, use a proper caching library (`lru-cache`, Redis), or explicitly clear stale entries per request — not a global scope problem per se, but a module-singleton state problem with the same practical effect.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                        | `var` (global)               | `let` / `const` (global)         | Explicit `window.x = ...`        |
|---                            |---                            |---                                |---                                |
| Attached to global object?    | Yes                          | No                                | Yes                               |
| Accessible globally?          | Yes                          | Yes (same script/module)          | Yes                               |
| Hoisted?                      | Yes (`undefined`)            | Yes (TDZ)                         | No (assigned at runtime)          |
| Deletable via `delete`?       | No                           | No                                | Yes                               |
| Overwritten by re-declaration?| Yes (silent)                 | No (`SyntaxError`)                | Yes (silent)                      |
| Strict mode changes behavior? | No (still global)            | No                                | No                                |
| Risk of name collision?       | High                         | Lower (not on `window`)           | High                              |

---

**Tip for the interview:** At the 5 YOE level, "what is global scope" won't come up as a standalone question — it shows up embedded in harder questions: why a legacy multi-script app has a collision bug, why `this` is the global object in a plain function call, why a Node module's top-level variable isn't accessible in another file, or why a test suite has flaky shared state. Know the `var`-vs-`let`/`const` distinction on the global object cold, understand the module vs classic script split, and have a real story about tracking down a global namespace collision or accidental global — that's the level of answer that lands at 5 YOE.
