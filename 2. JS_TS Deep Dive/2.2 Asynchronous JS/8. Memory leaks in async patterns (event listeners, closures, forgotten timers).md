# JavaScript: Memory Leaks in Async Patterns — Event Listeners, Closures, Forgotten Timers — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals of Memory Leaks

**Q1. What is a memory leak in JavaScript?**
A: A memory leak occurs when the JavaScript engine allocates memory for objects that are no longer needed by the application's logic, but those objects remain reachable through some reference chain — preventing the garbage collector from reclaiming the memory. The heap grows over time until the process either crashes (Node.js OOM), the browser tab freezes or crashes, or performance degrades catastrophically.

The key word is "reachable" — the GC's rule is simple: anything reachable from a root (global variables, call stack, closures, event listeners) is kept alive. A memory leak is not a GC bug; it's a developer bug where the code accidentally keeps references alive longer than intended.

```
Not a leak: object created, used, all references dropped → GC collects it ✓
Leak:       object created, used, one reference forgotten → GC can't collect it ✗
```

**Q2. What are the GC roots in a JavaScript runtime?**
A: Garbage collection starts from "roots" — objects that are always considered reachable, regardless of other references. Everything reachable by following references from any root is considered live and will not be collected. The main roots are:

- **Global object** (`window` in browsers, `global` in Node.js) — all global variables, including accidentally created globals.
- **Currently executing call stack** — all local variables and parameters in active function calls.
- **Closures** — variables captured by any currently live function's outer scope.
- **Event listeners** — any callback registered with an event target (DOM element, EventEmitter, etc.) is reachable as long as the event target is reachable.
- **Timers** — `setTimeout` and `setInterval` callbacks and everything they close over, as long as the timer is active.
- **Native code references** — objects held by browser internals, WebWorker messages, etc.

**Q3. What are the five most common sources of memory leaks in JavaScript async patterns?**
A:
1. **Forgotten event listeners** — adding listeners to long-lived objects (DOM, EventEmitters) without removing them when they're no longer needed. The listener closure keeps everything it captures alive.
2. **Forgotten timers** — `setInterval` callbacks that are never `clearInterval`-ed, or `setTimeout` chains that never terminate.
3. **Closure over large outer scope** — a small callback captures an enormous outer scope, keeping megabytes of data alive far beyond its useful lifetime.
4. **Detached DOM nodes** — nodes removed from the DOM but still referenced by JavaScript variables or event listeners, keeping the entire subtree alive.
5. **Unbounded caches** — Maps, Sets, arrays, or objects that grow indefinitely without eviction, acting as a permanent reference to everything ever added.

**Q4. What is the difference between a "logical leak" and a "GC-prevented collection"?**
A: A **logical leak** is when the application's intent is to discard an object, but due to a coding error, a reference is inadvertently kept. The GC is working correctly — it correctly identifies the object as reachable — but the developer didn't mean to keep it alive. This is the classic memory leak.

A **GC-prevented collection** is when the developer explicitly intends to keep an object alive (e.g., a cache entry), but the object is never explicitly removed — growing unboundedly. Technically not a GC bug, but functionally a leak because the application's memory grows without bound.

Both cause the same symptom (growing memory, eventual OOM) and require the same fix (ensure objects are dereferenced when no longer needed).

### Section 2: Event Listener Leaks

**Q5. Why do event listeners cause memory leaks, and what is the full scope of what they keep alive?**
A: When you call `element.addEventListener('click', handler)`, the DOM element holds a strong reference to `handler`. If `handler` is a closure, it holds strong references to everything in its captured scope — the entire lexical environment chain from the point of its definition. If that scope contains large objects, arrays, or references to other DOM subtrees, all of it stays alive as long as the element AND the listener exist.

The leak chain is:
```
Root (DOM tree) → element → event listener → handler closure → captured scope → large objects
```

If the element is removed from the DOM but a JavaScript variable still holds a reference to it, the element stays alive — along with ALL its listeners and ALL the scopes those listeners captured. This is the "detached DOM node with listeners" pattern:

```js
function setup() {
  const element = document.getElementById('btn');
  const hugeData = new Array(1_000_000).fill('data'); // 1M strings

  element.addEventListener('click', function() {
    console.log(hugeData.length); // captures hugeData in its closure scope
  });

  document.body.removeChild(element); // remove from DOM
  // BUT: if 'element' variable is still in scope (or the listener holds it),
  // both element AND hugeData remain in memory
}
```

**Q6. How does the "accumulating listeners" pattern cause leaks in React and component-based frameworks?**
A: In component-based frameworks, components are created and destroyed many times. If a component registers a global event listener on mount but doesn't remove it on unmount, a new listener is added every time the component mounts — but none are removed. After n mount/unmount cycles, n listeners accumulate:

```js
// LEAKY React component
function SearchBox() {
  useEffect(() => {
    // Registers a new listener every time SearchBox mounts
    window.addEventListener('keydown', handleKeydown);
    // No cleanup! Each remount adds another listener
  }, []);

  function handleKeydown(e) {
    if (e.key === 'Escape') clearSearch();
  }
  // ...
}

// After 10 mount/unmount cycles: 10 listeners on window.keydown
// Each listener keeps the component's closure scope alive
// 'clearSearch' and its entire scope × 10 instances

// CORRECT:
function SearchBox() {
  useEffect(() => {
    window.addEventListener('keydown', handleKeydown);
    return () => window.removeEventListener('keydown', handleKeydown); // cleanup!
  }, []);
}
```

**Q7. Why does `removeEventListener` require the exact same function reference to work?**
A: `removeEventListener(type, handler)` removes the listener only if `handler` is referentially equal (`===`) to the originally registered function. This is because internally the browser maintains a list of `[type, handler, options]` tuples per element — to remove one, it must find an exact match.

```js
// BUG: new function reference created each time
element.addEventListener('click', function() { doWork(); });
element.removeEventListener('click', function() { doWork(); }); // DIFFERENT function! No-op.

// BUG: same pattern with arrow functions
element.addEventListener('click', () => doWork()); // anonymous
element.removeEventListener('click', () => doWork()); // different reference — no-op

// CORRECT: store the reference
const handler = () => doWork();
element.addEventListener('click', handler);
element.removeEventListener('click', handler); // same reference ✓

// CORRECT with bind: store the bound version
this.boundHandler = this.handler.bind(this); // store in a variable
element.addEventListener('click', this.boundHandler);
element.removeEventListener('click', this.boundHandler); // same bound reference ✓
```

This is why React's `useEffect` cleanup must be careful: the handler function created inside `useEffect` must be captured in a variable that persists between the setup and cleanup callbacks.

**Q8. How does the Node.js EventEmitter leak, and what is the "MaxListenersExceededWarning"?**
A: Node.js `EventEmitter` has a built-in leak detection mechanism: if more than 10 (default) listeners are added to a single event on a single emitter, Node.js prints a `MaxListenersExceededWarning`. This is a heuristic — it doesn't guarantee a leak exists (some legitimate use cases have many listeners), but it's a strong signal.

Common EventEmitter leak pattern:
```js
// Each HTTP request adds a listener that never gets removed
http.createServer((req, res) => {
  process.on('uncaughtException', (err) => { // adds listener per request!
    res.end('Error: ' + err.message);
  });
  // When the request finishes, the listener stays on process forever
  // After 1000 requests: 1000 uncaughtException listeners
});
```

Fix: add the listener once (outside the request handler), or explicitly `removeListener` after use:
```js
// CORRECT: one-time listener
const handler = (err) => { /* ... */ };
process.once('uncaughtException', handler); // 'once' auto-removes after first fire
```

### Section 3: Timer Leaks

**Q9. How do forgotten `setInterval` timers cause memory leaks?**
A: An active `setInterval` is a GC root — the JavaScript runtime holds a strong reference to the callback function to ensure it can fire. Everything the callback closure captures stays alive for as long as the interval runs. Since `setInterval` never stops on its own, if `clearInterval` is never called, the callback — and all of its captured references — live for the entire lifetime of the process/page.

```js
function startPolling(userId) {
  const userState = { id: userId, data: new Array(100_000).fill(0) }; // large

  const id = setInterval(() => {
    fetchUpdates(userState); // captures userState — 100K items alive forever
  }, 5000);

  // If clearInterval(id) is never called:
  // → userState is never collected
  // → fetchUpdates closure is never collected
  // → id is never collected
  // This runs until process death or tab close
}

// After calling startPolling() 10 times without cleanup:
// 10 intervals × 100K items each = 1M items permanently in memory
```

**Q10. How do `setTimeout` chains leak?**
A: A single `setTimeout` is not a leak by itself — it fires once and is done. But a common pattern — `setTimeout` that reschedules itself in its callback — creates an eternal chain that holds its closure alive indefinitely:

```js
function startAutoSave(documentRef) {
  setTimeout(function save() {
    saveDocument(documentRef); // captures documentRef
    setTimeout(save, 30000);   // reschedules — eternal chain
  }, 30000);

  // Even if documentRef is "done with" elsewhere,
  // this chain keeps it alive forever
  // The chain can only be broken by not rescheduling
}
```

Fix: make the reschedule conditional, or use a cancellation token:

```js
function startAutoSave(documentRef) {
  let cancelled = false;

  function save() {
    if (cancelled) return; // don't reschedule
    saveDocument(documentRef);
    setTimeout(save, 30000); // reschedule only if not cancelled
  }

  setTimeout(save, 30000);
  return () => { cancelled = true; }; // return cancel function
}

const cancel = startAutoSave(myDoc);
// Later:
cancel(); // breaks the chain, allows documentRef to be GC'd
```

**Q11. What is the "interval + fetch" leak pattern in React SPAs?**
A: A particularly common production leak in React single-page applications:

```js
// LEAKY pattern
function UserDashboard({ userId }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    const id = setInterval(async () => {
      const result = await fetch(`/api/users/${userId}`);
      const json = await result.json();
      setData(json); // ← setData called after component unmounts → React warning
                     // ← But worse: the fetch and closure keep userId alive
    }, 10000);

    // NO CLEANUP → interval runs after component unmounts
    // After navigating away: interval still fires every 10 seconds
    // Each fire: network request, closure over userId, setState call on dead component
  }, [userId]);
}

// CORRECT:
useEffect(() => {
  let active = true; // cancellation flag
  const id = setInterval(async () => {
    const result = await fetch(`/api/users/${userId}`);
    const json = await result.json();
    if (active) setData(json); // guard: only update if still mounted
  }, 10000);

  return () => {
    active = false;
    clearInterval(id);
  };
}, [userId]);
```

### Section 4: Closure Leaks

**Q12. What is the "closure over large scope" leak, and why is it non-obvious?**
A: A closure captures the entire variable environment of its defining scope — not just the variables it actually uses. In V8 specifically, the compiler performs escape analysis and may only keep variables the closure actually references. But in some cases, especially with `eval` or complex code, the entire scope is retained. Even without this engine behavior, the most common form is accidentally capturing a large variable when only a small piece of it is needed:

```js
function processReport(report) {
  const allData = report.rawData;        // 50MB of data
  const summary = summarize(allData);    // small summary object

  // LEAK: this closure captures the entire processReport scope,
  // which includes 'allData' (50MB) — even though only 'summary' is used
  const displayFn = function() {
    return summary.totalCount; // only uses summary, but allData stays alive
  };

  return displayFn; // returned closure keeps allData alive
}

// FIX: extract only what's needed before creating the closure
function processReportFixed(report) {
  const allData = report.rawData;
  const summary = summarize(allData);
  const { totalCount } = summary; // destructure — primitive value, no object reference

  const displayFn = function() {
    return totalCount; // only captures the primitive
  };

  return displayFn;
  // allData and summary are now collectable — only totalCount is kept
}
```

**Q13. How do closures in loops create unexpected memory retention?**
A: When closures are created inside loops and stored (e.g., in an array of handlers), each closure captures the loop's scope — including loop variables and anything else in that scope. If the loop variable changes, all closures see the new value (the classic `var`-in-loop bug). But for memory leaks specifically, the issue is that all closures share a reference to the same scope object, keeping all of its variables alive as long as ANY one of the closures is alive:

```js
function attachHandlers(elements) {
  const largeSharedResource = loadResource(); // 10MB resource

  elements.forEach((el, i) => {
    el.addEventListener('click', function() {
      // Each handler captures the forEach scope, which includes largeSharedResource
      doAction(i);
    });
  });

  // largeSharedResource is kept alive by ALL handlers on ALL elements
  // Even though no handler actually uses largeSharedResource
  // It's captured because it's in the same scope
}
```

Fix: isolate the large resource from the closure's scope:

```js
function attachHandlers(elements) {
  const largeSharedResource = loadResource();
  processResource(largeSharedResource); // use it
  // Don't let the resource be in scope where closures are created

  // Create closures in a separate scope
  elements.forEach((el, i) => {
    el.addEventListener('click', makeHandler(i));
  });
}

function makeHandler(index) {
  // This scope has no reference to largeSharedResource
  return function() { doAction(index); };
}
```

**Q14. What is the "subscriber callback accumulation" pattern in pub/sub systems?**
A: Event-driven architectures often have components subscribing to events from a central bus or store. If subscriptions aren't cleaned up when components are destroyed, subscribers accumulate indefinitely:

```js
// EventBus singleton
class EventBus {
  constructor() { this._listeners = {}; }

  on(event, listener) {
    if (!this._listeners[event]) this._listeners[event] = [];
    this._listeners[event].push(listener);
  }

  emit(event, data) {
    (this._listeners[event] || []).forEach(l => l(data));
  }

  off(event, listener) {
    if (!this._listeners[event]) return;
    this._listeners[event] = this._listeners[event].filter(l => l !== listener);
  }
}

const bus = new EventBus(); // global singleton

// Component that leaks
class Widget {
  constructor() {
    this.data = new Array(10_000).fill('widget-data'); // sizable

    // LEAK: registers listener on global bus, never removes it
    bus.on('update', (payload) => {
      this.handleUpdate(payload); // captures 'this' → keeps Widget alive
    });
  }

  handleUpdate(payload) { /* ... */ }
  destroy() { /* forgot to call bus.off() */ }
}

// Create and "destroy" 100 widgets:
for (let i = 0; i < 100; i++) {
  const w = new Widget();
  w.destroy(); // w goes out of scope but bus still holds a reference!
}
// bus._listeners['update'] now has 100 listeners
// Each listener holds a reference to its Widget instance
// 100 Widget instances × 10K items each → 1M items alive
```

### Section 5: Detection & Debugging

**Q15. How do you detect a memory leak in a browser application?**
A: Chrome DevTools is the primary tool. Three workflows:

**Workflow 1 — Heap Snapshot Comparison**:
1. DevTools → Memory → Heap Snapshot → Take snapshot (baseline).
2. Perform the action suspected of leaking (navigate, click, mount/unmount).
3. Take another heap snapshot.
4. Select the second snapshot and choose "Comparison" view.
5. Sort by "# New" — objects that were created in snapshot 2 but not 1. Growing counts of component instances, listeners, or closures indicate leaks.

**Workflow 2 — Allocation Timeline**:
1. DevTools → Memory → Allocation instrumentation on timeline → Start recording.
2. Perform operations.
3. Stop recording. Examine "Allocation stack" to see where long-lived objects were allocated.

**Workflow 3 — Performance Monitor**:
1. DevTools → More Tools → Performance Monitor.
2. Watch "JS Heap Size" and "DOM Nodes" metrics in real time while using the app.
3. A consistently rising JS heap size (not sawtooth GC pattern) indicates a leak.

**Q16. How do you detect a memory leak in Node.js?**
A: Several complementary approaches:

**`process.memoryUsage()` monitoring**:
```js
setInterval(() => {
  const mem = process.memoryUsage();
  console.log({
    heapUsed: Math.round(mem.heapUsed / 1024 / 1024) + 'MB',
    heapTotal: Math.round(mem.heapTotal / 1024 / 1024) + 'MB',
    rss: Math.round(mem.rss / 1024 / 1024) + 'MB',
    external: Math.round(mem.external / 1024 / 1024) + 'MB',
  });
}, 10000);
// Consistently growing heapUsed under stable load = leak
```

**Node.js `--inspect` + Chrome DevTools**: start Node with `node --inspect app.js`, open `chrome://inspect`, connect, and use the Memory panel exactly like browser debugging.

**`heapdump` npm package**: programmatically take heap snapshots and compare in Chrome DevTools.

**`node --expose-gc` + manual GC**: force GC between operations to eliminate false positives from normal heap growth patterns.

**Q17. How do you use the "retained size" vs "shallow size" distinction to find leaks?**
A: In a heap snapshot:

- **Shallow size**: memory occupied by the object itself (its own fields) — not counting objects it references.
- **Retained size**: total memory that would be freed if this object AND everything exclusively reachable through it were collected — the "cost" of this object's existence.

Leaks typically show up as objects with **small shallow size but large retained size** — a tiny closure or listener that holds a reference chain to megabytes of data. Sort the heap snapshot by "Retained Size" descending to find the "cost leaders" — objects that are keeping the most memory alive.

```
Example in a heap snapshot:
Object: EventListener (shallow: 64 bytes, retained: 52MB)
  → This listener is keeping 52MB alive through its closure
  → It's the "root" of a large retained object graph
  → Fixing this listener = freeing 52MB
```

### Section 6: Scenario / Interview-Style Questions

**Q18. "Walk me through how you'd diagnose a memory leak in a React SPA that slows down after 30 minutes of use."**
A: Systematic five-step process:

1. **Confirm it's a memory leak**: open DevTools Performance Monitor, watch "JS Heap Size" and "DOM Nodes" over time while using the app normally. A consistently rising baseline (not just GC sawtooth) confirms a leak.

2. **Identify the growth pattern**: navigate between routes, open/close modals, interact with widgets. Notice which action correlates with the steepest memory growth. Isolate to a specific component or feature.

3. **Heap snapshot comparison**: take a snapshot before the suspicious action, perform it 5 times, take another snapshot. In Comparison view, look for:
   - Growing counts of React fiber nodes (component instances not being cleaned up).
   - Accumulating `EventListener` objects.
   - Arrays or Maps growing without bound.
   - Detached DOM elements (filter by "Detached" in the Heap Snapshot).

4. **Trace the retention path**: click on a leaked object in the snapshot → look at the "Retainers" panel. This shows the reference chain from a GC root to the leaked object. Follow it upward to find the "forgotten" reference.

5. **Fix and verify**: address the leak (add `removeEventListener`, add `clearInterval`, fix the unbounded cache). Take snapshots again after the fix to confirm the comparison shows no new accumulation of that object type.

**Q19. "A colleague says their Node.js server's memory grows steadily for the first hour then plateaus. Is this definitely a leak?"**
A: Not necessarily. Several normal behaviors cause initial memory growth that plateaus:

- **V8 lazy compilation**: functions are compiled JIT on first execution. The first few thousand requests compile many code paths, growing the heap. This plateaus once all hot paths are compiled.
- **Node.js module cache**: `require()` caches modules permanently. Initial module loading grows memory; it plateaus once all modules are loaded.
- **V8 heap tuning**: V8 starts with a small heap and grows it as needed. Once the steady-state heap size is established, it stops growing.
- **Connection pools**: database/HTTP connection pools initialize on first use and reach their max size, then plateau.

A true leak grows continuously without plateau (or plateaus at a much higher level than expected and then slowly creeps upward). To distinguish: monitor `process.memoryUsage().heapUsed` (not just `rss`) over 24+ hours under stable load. A plateau followed by stability = likely normal behavior. Continued growth after 2+ hours of stable load = likely a leak.

**Q20. "What is the difference between a memory leak caused by a closure vs one caused by a retained DOM node? How would you fix each?"**
A: Two distinct patterns:

**Closure leak**: a function closure captures a variable that should have been freed.
- Symptom: heap snapshot shows growing `Closure` or `(closure)` objects; their retained size is large.
- Root cause: a long-lived callback (event listener, timer, Promise chain) capturing a short-lived large object.
- Fix: (1) Extract only necessary values from the scope before creating the closure. (2) Nullify the captured reference once it's no longer needed. (3) Ensure the callback itself is removed (breaking the reference chain).

**Retained DOM node**: a node removed from the DOM but still referenced in JavaScript.
- Symptom: heap snapshot → "Detached DOM tree" filter shows subtrees of nodes marked as detached.
- Root cause: a JS variable holds a reference to a DOM element that was removed from the document tree; the element and its entire subtree (and all their listeners) cannot be GC'd.
- Fix: (1) Nullify the JS variable (`let element = document.getElementById('x'); ...; element = null`). (2) Remove event listeners before removing from DOM. (3) Use WeakRef or WeakMap for caches of DOM node metadata.

```js
// CLOSURE LEAK FIX
// Before:
const bigObj = { data: new Array(1_000_000) };
element.addEventListener('click', () => process(bigObj)); // captures bigObj

// After:
const bigObj = { data: new Array(1_000_000) };
const processedSummary = process(bigObj); // extract needed result
const bigObjCopy = null; // not possible with let/const, but signals intent
// Create closure over only what's needed:
element.addEventListener('click', () => display(processedSummary)); // small closure

// DETACHED DOM FIX
// Before:
let modal = document.getElementById('modal');
modal.addEventListener('submit', handleSubmit);
document.body.removeChild(modal);
// modal variable still holds the removed node!

// After:
let modal = document.getElementById('modal');
modal.addEventListener('submit', handleSubmit);
modal.removeEventListener('submit', handleSubmit); // remove listener first
document.body.removeChild(modal);
modal = null; // explicitly release the reference
```

## Problem 1 — React Component with Accumulating Event Listeners

### Problem
The following React component registers a global keyboard shortcut. Users report the app getting slower after heavy navigation. Identify and fix the leak.

```js
// LEAKY VERSION
function CommandPalette({ onCommand }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  useEffect(() => {
    function handleKeydown(e) {
      if (e.ctrlKey && e.key === 'k') {
        fetchCommands(query).then(r => setResults(r));
      }
      if (e.key === 'Escape') {
        setQuery('');
        setResults([]);
      }
    }

    window.addEventListener('keydown', handleKeydown);
    // No cleanup!
  }, []); // runs once on mount — never cleans up

  return (/* ... */);
}
```

### Leak Identification

**What leaks**: every time `CommandPalette` mounts, a new `handleKeydown` function is created and added to `window`'s keydown listeners. When `CommandPalette` unmounts (e.g., user closes the palette), the listener is NOT removed. Next time it mounts, another listener is added.

**The retention chain**:
```
window (GC root)
  → window._eventListeners['keydown'] (internal browser structure)
    → [handleKeydown_1, handleKeydown_2, handleKeydown_3, ...]  ← accumulates
      → each handleKeydown closure
        → query state (string)
        → setResults function
        → setQuery function
        → fetchCommands reference
        → onCommand prop reference
        → the entire component fiber subtree (via React internal references)
```

After 10 mount/unmount cycles: 10 live handlers, each keeping a React fiber context alive.

### Memory Diagram

```
window.keydown listeners after 10 mount/unmount cycles:

window ──► [handler1] ──► closure scope { query:"", setResults:fn, ... } → Component#1 state
       ──► [handler2] ──► closure scope { query:"ab", setResults:fn, ... } → Component#2 state
       ──► [handler3] ──► closure scope { query:"", setResults:fn, ... } → Component#3 state
       ... × 10 handlers

All 10 component states kept alive even though only 1 component is mounted.
Each active handler also fires on every keydown — 10 fetches instead of 1!
(functional bug AND memory leak)
```

### Fixed Code

```js
function CommandPalette({ onCommand }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  // FIX 1: Stable reference — store handler to use exact same reference for removal
  // Use useCallback to memoize the handler (avoids re-registering on every render)
  const handleKeydown = useCallback(
    function handleKeydown(e) {
      if (e.ctrlKey && e.key === 'k') {
        fetchCommands(query).then(r => setResults(r));
      }
      if (e.key === 'Escape') {
        setQuery('');
        setResults([]);
      }
    },
    [query] // re-create when query changes (needed for fetchCommands(query))
  );

  useEffect(() => {
    window.addEventListener('keydown', handleKeydown);

    // FIX 2: Cleanup function — removes the SAME function reference
    return () => {
      window.removeEventListener('keydown', handleKeydown);
    };
  }, [handleKeydown]); // re-register when handler changes (when query changes)

  return (/* ... */);
}
```

**Alternative: use `useRef` for a stable handler that reads latest state**:
```js
function CommandPalette({ onCommand }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const queryRef = useRef(query);

  // Keep ref in sync with state (no re-registration needed)
  useEffect(() => { queryRef.current = query; }, [query]);

  useEffect(() => {
    function handleKeydown(e) {
      if (e.ctrlKey && e.key === 'k') {
        // Read from ref — always gets current value without stale closure
        fetchCommands(queryRef.current).then(r => setResults(r));
      }
      if (e.key === 'Escape') {
        setQuery('');
        setResults([]);
      }
    }

    window.addEventListener('keydown', handleKeydown);
    return () => window.removeEventListener('keydown', handleKeydown);
  }, []); // only registers/unregisters once — no stale closure, no re-registration
}
```

### Verification

```js
// Before fix: add this to verify accumulation
window.addEventListener('keydown', () => {
  const listeners = getEventListeners(window).keydown; // Chrome DevTools API
  console.log('Keydown listeners:', listeners.length);
});
// Mount/unmount CommandPalette 5 times → logs 1, 2, 3, 4, 5 ← leak confirmed

// After fix:
// Mount/unmount CommandPalette 5 times → always logs 1 ← fixed

// Heap snapshot verification:
// Before: "Comparison" shows accumulating handleKeydown functions and React fiber contexts
// After: mount/unmount 10 times → no new Closure objects retained in comparison
```

### Gotchas
- **`useCallback` creates a new function when deps change** — if `query` changes rapidly, `handleKeydown` is recreated frequently, causing rapid remove/re-add cycles. Use `useRef` pattern for truly stable registration.
- **`removeEventListener` must match the exact third argument (`options/useCapture`)** — if you add with `{ capture: true }`, you must remove with `{ capture: true }`. Mismatched options = silent no-op.
- **`AbortController` signal pattern**: modern alternative for bulk listener cleanup:
```js
useEffect(() => {
  const controller = new AbortController();
  window.addEventListener('keydown', handleKeydown, { signal: controller.signal });
  // No need for removeEventListener — just abort:
  return () => controller.abort(); // automatically removes all listeners added with this signal
}, []);
```

### Follow-up Questions
- "What if 100 different components need to listen to keyboard events?" → Implement a centralized keyboard manager that adds ONE listener to `window` and dispatches to all registered components. Components register/unregister from the manager (O(n) dispatch but O(1) listeners on `window`).

## Problem 2 — Node.js Server with EventEmitter Accumulation

### Problem
A Node.js HTTP server creates a new database connection per request and registers error handlers. Under load, the server memory grows steadily. Identify and fix the leak.

```js
// LEAKY VERSION
const http = require('http');
const { DatabasePool } = require('./db');
const pool = new DatabasePool();

http.createServer(async (req, res) => {
  const conn = await pool.getConnection();

  // LEAK 1: registers new listener on process per request
  process.on('uncaughtException', (err) => {
    conn.release(); // capture conn in closure
    res.end('Error occurred');
  });

  // LEAK 2: registers new listener on conn per request
  conn.on('error', (err) => {
    console.error('DB error:', err);
    res.end('DB Error');
  });

  try {
    const data = await conn.query('SELECT * FROM users');
    res.end(JSON.stringify(data));
    conn.release();
  } catch (err) {
    res.end('Query failed');
    conn.release();
  }
  // LEAK: neither process nor conn listener is removed after request
}).listen(3000);
```

### Leak Identification

**Leak 1 — `process.on('uncaughtException', ...)` per request**:
- `process` is a global GC root that lives for the process lifetime.
- Each request adds a new listener capturing `conn` and `res` from that request's scope.
- After 1000 requests: 1000 `uncaughtException` listeners, each holding a connection object and response object alive.
- Node.js prints `MaxListenersExceededWarning` after 10 listeners.

**Leak 2 — `conn.on('error', ...)` without cleanup**:
- `conn` objects may be returned to the pool and reused for subsequent requests.
- Each time a `conn` is reused without removing the previous listener, a new error listener is added.
- After 100 reuses: a single `conn` has 100 `'error'` listeners, each capturing a different request's `res` object — keeping 100 response objects alive.

### Memory Diagram

```
process (GC root, permanent)
  → uncaughtException listeners: [fn1, fn2, fn3, ...fn1000]
    → fn1 closure: { conn: Connection#1, res: Response#1 }
    → fn2 closure: { conn: Connection#2, res: Response#2 }
    ...
    → Each Response holds: headers, body, socket reference, ...

pool._connections
  → Connection#1 (reused for many requests)
    → error listeners: [fn1, fn2, fn3, ...fn100]
      → fn1 closure: { res: Response#1 } ← dead response!
      → fn100 closure: { res: Response#100 } ← only this is current
```

### Fixed Code

```js
const http = require('http');
const { DatabasePool } = require('./db');
const pool = new DatabasePool();

// FIX 1: Global error handler — registered ONCE, not per request
process.on('uncaughtException', (err) => {
  console.error('Unhandled exception:', err);
  // Can't access per-request conn/res from here — that's the point
  // Per-request cleanup should happen in try/finally, not here
});

http.createServer(async (req, res) => {
  const conn = await pool.getConnection();

  // FIX 2: Scoped error handler — stored for removal, or use 'once'
  const connErrorHandler = (err) => {
    console.error('DB connection error during request:', err);
    if (!res.headersSent) res.end('DB Error');
    conn.release();
  };
  conn.once('error', connErrorHandler); // 'once' auto-removes after first fire

  try {
    const data = await conn.query('SELECT * FROM users');
    res.end(JSON.stringify(data));
  } catch (err) {
    if (!res.headersSent) res.end('Query failed');
  } finally {
    // FIX 3: Always clean up in finally — guaranteed execution
    conn.removeListener('error', connErrorHandler); // remove if not fired
    conn.release();
  }
}).listen(3000);
```

**Alternative: AbortController for request-scoped cleanup**:
```js
http.createServer(async (req, res) => {
  const conn = await pool.getConnection();
  const controller = new AbortController();
  const { signal } = controller;

  // All listeners added with this signal are removed when controller.abort() is called
  conn.addEventListener('error', connErrorHandler, { signal });
  req.on('close', () => controller.abort(), { signal }); // self-referential cleanup

  try {
    const data = await conn.query('SELECT * FROM users', { signal });
    res.end(JSON.stringify(data));
  } finally {
    controller.abort(); // removes all signal-attached listeners
    conn.release();
  }
}).listen(3000);
```

### Verification

```js

  console.log('process uncaughtException listeners:', process.listenerCount('uncaughtException'));
  console.log('pool active connections:', pool.activeCount);
}, 5000);

// Load test: send 100 requests
// Before fix: uncaughtException count grows to 100
// After fix: uncaughtException count stays at 1

// Check EventEmitter listener counts

for (let i = 0; i < 10; i++) {
  conn.on('error', () => {});
}
console.log(conn.listenerCount('error')); // Before fix: grows; After fix: max 1 with 'once'
```

### Gotchas
- **`conn.once` vs `conn.on`**: `once` removes the listener after it fires once. If the error never fires, the listener must still be explicitly removed in the `finally` block — `once` only auto-removes on fire, not on normal completion.
- **`res.headersSent` check**: if the response was already sent (headers sent), calling `res.end()` again throws. Always guard with `if (!res.headersSent)`.
- **Connection pool reuse**: when `conn.release()` returns the connection to the pool, any remaining listeners on it persist. The pool should call `conn.removeAllListeners()` before returning the connection to ensure no request-scoped listeners survive into the next request.

### Follow-up Questions
- "How would you detect this in production without adding debug code?" → Monitor `process.listenerCount('uncaughtException')` via a metrics endpoint or APM tool. Alert when it exceeds 15 (well above Node's default 10 warning threshold). Also track heap size trend with a monitoring service.

## Problem 3 — Unbounded Cache Growing Without Eviction

### Problem
A production API memoizes expensive database lookups for performance. After a few days, the Node.js process is killed by OOM. Identify the leak and implement a proper bounded cache.

```js
// LEAKY VERSION — unbounded cache
const cache = new Map(); // grows forever

async function getUserProfile(userId) {
  if (cache.has(userId)) {
    return cache.get(userId); // cache hit
  }

  const profile = await db.query(`SELECT * FROM profiles WHERE id = ?`, [userId]);
  cache.set(userId, profile); // LEAK: never evicted
  return profile;
}

// In a system with 10M users, cache eventually holds 10M profiles in memory
// Each profile: ~2KB → 10M × 2KB = 20GB → OOM
```

### Leak Identification

The `cache` Map is a GC root (module-level variable → permanent root). Every entry added with `cache.set()` is held strongly. Since there is no eviction logic:
- New user IDs are added indefinitely.
- Old entries are never removed.
- The Map grows without bound.
- Profile objects (the values) and userId strings (the keys) are all kept alive.

This is an **unbounded cache** — a classic "intentional accumulation" that becomes a leak when the dataset is larger than available memory.

### Fixed Code — LRU Cache

```js
class LRUCache {
  #capacity;
  #cache = new Map(); // Map preserves insertion/access order

  constructor(capacity) {
    this.#capacity = capacity;
  }

  get(key) {
    if (!this.#cache.has(key)) return undefined;

    // Move to end (most recently used)
    const value = this.#cache.get(key);
    this.#cache.delete(key);
    this.#cache.set(key, value);
    return value;
  }

  set(key, value) {
    if (this.#cache.has(key)) {
      this.#cache.delete(key); // remove to re-insert at end
    } else if (this.#cache.size >= this.#capacity) {
      // Evict the LEAST recently used (first entry in Map)
      const lruKey = this.#cache.keys().next().value;
      this.#cache.delete(lruKey);
    }

    this.#cache.set(key, value); // insert at end (most recently used)
  }

  has(key) { return this.#cache.has(key); }
  get size() { return this.#cache.size; }
  clear() { this.#cache.clear(); }
}

// LRU cache bounded to 10,000 entries
const cache = new LRUCache(10_000);

async function getUserProfile(userId) {
  const cached = cache.get(userId);
  if (cached !== undefined) return cached;

  const profile = await db.query(`SELECT * FROM profiles WHERE id = ?`, [userId]);
  cache.set(userId, profile); // evicts LRU if at capacity
  return profile;
}
```

### Fixed Code — TTL Cache (Time-To-Live)

```js
class TTLCache {
  #store = new Map();  // key → { value, expiresAt }
  #ttlMs;
  #cleanupInterval;

  constructor(ttlMs, cleanupIntervalMs = ttlMs) {
    this.#ttlMs = ttlMs;

    // Periodic cleanup of expired entries
    this.#cleanupInterval = setInterval(() => this.#cleanup(), cleanupIntervalMs);

    // Allow Node.js to exit even with active interval
    if (this.#cleanupInterval.unref) this.#cleanupInterval.unref();
  }

  set(key, value) {
    this.#store.set(key, {
      value,
      expiresAt: Date.now() + this.#ttlMs
    });
  }

  get(key) {
    const entry = this.#store.get(key);
    if (!entry) return undefined;
    if (Date.now() > entry.expiresAt) {
      this.#store.delete(key); // lazy expiry on access
      return undefined;
    }
    return entry.value;
  }

  has(key) {
    return this.get(key) !== undefined; // reuse expiry check
  }

  #cleanup() {
    const now = Date.now();
    for (const [key, entry] of this.#store) {
      if (now > entry.expiresAt) this.#store.delete(key);
    }
  }

  destroy() {
    clearInterval(this.#cleanupInterval); // IMPORTANT: clear timer to allow GC
    this.#store.clear();
  }
}

// 5-minute TTL, clean up every 5 minutes
const cache = new TTLCache(5 * 60 * 1000);

async function getUserProfile(userId) {
  const cached = cache.get(userId);
  if (cached !== undefined) return cached;

  const profile = await db.query(`SELECT * FROM profiles WHERE id = ?`, [userId]);
  cache.set(userId, profile);
  return profile;
}
```

### Fixed Code — WeakRef Cache (GC-Friendly)

```js
// For cases where you want the cache to be evicted when memory is needed
const weakCache = new Map(); // key → WeakRef(value)

async function getUserProfile(userId) {
  const ref = weakCache.get(userId);
  if (ref) {
    const cached = ref.deref();
    if (cached !== undefined) return cached; // still alive
    // else: GC collected it — treat as cache miss
  }

  const profile = await db.query(`SELECT * FROM profiles WHERE id = ?`, [userId]);
  weakCache.set(userId, new WeakRef(profile)); // weak reference — allows GC
  return profile;
}

// Note: weakCache Map itself still grows (keys are strings — not weakly held)
// For full cleanup, pair with FinalizationRegistry:
const registry = new FinalizationRegistry((userId) => {
  weakCache.delete(userId); // remove stale key when profile is GC'd
});

// In the setter: registry.register(profile, userId);
```

### Comparison: When to Use Each Cache Type

```
LRU Cache:    fixed memory footprint, evicts least-used entries
              best when: all entries equally likely to be re-accessed
              worst case: hot entries evicted by large burst of cold requests

TTL Cache:    entries expire after fixed time
              best when: data has a known validity period
              risk: cleanup interval timer must be cleared to avoid leak!

WeakRef Cache: entries evicted under memory pressure (GC decides)
              best when: cache is optional (can always recompute)
              risk: non-deterministic eviction, WeakRef adds complexity

Bounded Map:  simple max-size map, evict oldest on overflow
              best when: simplest solution needed, access pattern unknown
```

### Verification

```js
// Monitor cache size over time
setInterval(() => {
  console.log(`Cache size: ${cache.size}`);
  console.log(`Heap used: ${Math.round(process.memoryUsage().heapUsed / 1024 / 1024)}MB`);
}, 60000);

// After LRU fix: cache.size never exceeds 10,000
// After TTL fix: cache.size drops periodically after expiry
// Memory stabilizes instead of growing linearly with unique userIds
```

### Gotchas
- **TTL cache timer must be cleared** — the `setInterval` in `TTLCache.cleanup` holds a reference to the `TTLCache` instance (through the callback closure). If the cache is meant to be garbage collected, call `cache.destroy()` first to clear the interval. Without this, the interval keeps the cache alive forever — the cleanup interval itself becomes the leak.
- **LRU Map iteration order**: JavaScript `Map` maintains insertion order. By deleting and re-inserting on access, we maintain LRU order. `Map.keys().next().value` gives the oldest (LRU) key efficiently.
- **WeakRef cache: keys still in Map** — only the values are weakly held. The keys (userId strings) accumulate in the Map. Pair with `FinalizationRegistry` to remove stale keys.

### Follow-up Questions
- "How would you implement cache invalidation when user profile is updated?" → Expose a `cache.delete(userId)` method, called from the profile update code path (or via a pub/sub event).
- "What cache size limit should you use?" → Profile memory per entry × desired max memory ÷ memory per entry = entries. For 2KB profiles and 100MB cache budget: 50,000 entries.

## Problem 4 — Async Generator Leak (Promise Chain Without Termination)

### Problem
A log aggregator reads data from a stream using an async iterator. A bug causes the stream subscription to persist after the aggregator is "closed." Identify and fix the leak.

```js
// LEAKY VERSION
class LogAggregator {
  constructor(stream) {
    this.stream = stream;
    this.logs = [];
    this.closed = false;
    this.startConsuming(); // starts an async loop
  }

  async startConsuming() {
    // LEAK: this async loop runs forever even after closed = true
    // because 'for await' does not check this.closed between awaits
    for await (const chunk of this.stream) {
      this.logs.push(chunk);
    }
  }

  close() {
    this.closed = true;
    // LEAK: setting closed = true doesn't stop the for-await loop
    // The loop is awaiting the next chunk — it will process it, loop again, etc.
    // The stream and its closure are kept alive indefinitely
  }
}

const stream = createLogStream(); // external stream
const agg = new LogAggregator(stream);
// Later:
agg.close(); // doesn't actually stop anything
// stream is still being consumed, logs still growing, aggregator still alive
```

### Leak Identification

The `for await...of` loop inside `startConsuming` runs as long as the stream provides values. Setting `this.closed = true` doesn't interrupt the `await` inside the loop — the loop resumes from the `await` when the next chunk arrives, processes it, then checks no condition because there's no `if (this.closed) break` guard.

The async function `startConsuming` holds a reference to `this` (the `LogAggregator`), `this.stream`, and `this.logs`. As long as the function is alive (awaiting), nothing is collected.

### Fixed Code

```js
class LogAggregator {
  #stream;
  #logs = [];
  #abortController = new AbortController();

  constructor(stream) {
    this.#stream = stream;
    this.#startConsuming();
  }

  async #startConsuming() {
    const { signal } = this.#abortController;

    try {
      for await (const chunk of this.#stream) {
        if (signal.aborted) break; // FIX 1: check abort signal between chunks

        this.#logs.push(chunk);
      }
    } catch (err) {
      if (err.name !== 'AbortError') throw err; // FIX 2: swallow abort errors
    } finally {
      // Cleanup runs when loop exits for any reason
      this.#stream = null; // release stream reference
    }
  }

  getLogs() { return [...this.#logs]; }

  close() {
    this.#abortController.abort(); // FIX 3: signal the loop to stop
    this.#logs = []; // release log references
  }
}

// Alternative: use AbortSignal-aware stream consumption
class LogAggregatorAlt {
  #stream;
  #logs = [];
  #active = true;

  constructor(stream) {
    this.#stream = stream;
    this.#startConsuming();
  }

  async #startConsuming() {
    for await (const chunk of this.#stream) {
      if (!this.#active) break; // check flag on each iteration

      this.#logs.push(chunk);
    }
    this.#stream = null; // cleanup after loop exits
  }

  close() {
    this.#active = false;
    // The loop will break on the next iteration
    // The stream will advance one more chunk before stopping —
    // this is acceptable for log aggregation
  }
}
```

### Memory Diagram — Before Fix

```
JavaScript heap:
  agg (local var — but closure of async fn keeps it alive!)
    → #startConsuming async frame (paused at 'await')
      → this = agg (strong reference from async frame)
      → this.stream = LogStream (entire stream kept alive)
      → this.logs = [...] (all collected logs kept alive)

LogStream
  → underlying socket/file handle (OS resource)
  → chunk buffer
  → all registered data/end/error listeners

Even after agg goes "out of scope" and we expect it to be GC'd:
  → The async frame is still alive (awaiting next chunk)
  → The async frame holds 'this' (the aggregator)
  → The aggregator holds the stream
  → Nothing is collected ← LEAK
```

### Memory Diagram — After Fix

```
agg.close() called:
  #active = false (or AbortController.abort())

Next iteration of for-await:
  chunk arrives → `if (!this.#active) break` → exits loop
  finally block: this.#stream = null

Async frame completes (function returns):
  → No more reference to this from async frame
  → agg becomes collectable if no other references
  → stream becomes collectable (stream reference in agg is nulled)
  → All log data becomes collectable (agg.#logs = [])

GC cycle: stream, logs, aggregator all freed ✓
```

### Verification

```js

await new Promise(r => setTimeout(r, 100)); // let it collect some logs
agg.close();
agg = null; // drop local reference

// Force GC (Node.js with --expose-gc flag)

// Should return to baseline — if still elevated, stream or logs are retained

// Verify stream is no longer active
// (stream should have no active consumers after close)
```

### Gotchas
- **One extra chunk after close**: the `if (!this.#active) break` check runs at the TOP of each iteration — after the previous `await` resumes. If a chunk arrives after `close()` is called but before the next iteration check, it's processed. This is usually acceptable for log aggregation; for strict cutoff, destroy the stream directly.
- **Error handling**: `for await...of` does NOT automatically catch errors from the async iterator. Wrap in `try/catch` and handle both abort errors and real errors.
- **AbortController.abort()**: in newer Node.js versions, passing `{ signal }` to stream operations automatically throws `AbortError` when aborted, breaking the loop without needing an explicit `if (!active)` check.

### Follow-up Questions
- "What if the stream is an external API (e.g., a WebSocket) — how do you close it?" → Call `stream.destroy()` or `socket.close()` in `close()` — this causes the `for await` to exit with an error (or with `done: true` if the stream handles clean close). Still need the `try/catch` to handle the error.

## Problem 5 — Closure Capturing Unnecessary Scope

### Problem
A report generator processes large datasets. After processing, the report summary is kept for display, but the raw data should be freed. Identify why the raw data is retained and fix it.

```js
// LEAKY VERSION
function generateReport(rawData) {
  // rawData: 50MB array of records

  const summary = {
    count: rawData.length,
    total: rawData.reduce((sum, r) => sum + r.value, 0),
    average: 0,
  };
  summary.average = summary.total / summary.count;

  // LEAK: formatSummary closure captures the entire generateReport scope,
  // which includes rawData (50MB). V8 may optimize this away,
  // but it's risky and non-obvious.
  const formatSummary = () => {
    return `Count: ${summary.count}, Avg: ${summary.average.toFixed(2)}`;
  };

  // rawData is no longer needed after summary is computed
  // but formatSummary closure MAY keep it alive via scope capture

  return { summary, formatSummary };
}

const { formatSummary } = generateReport(hugeDataset);
// hugeDataset (50MB) may be retained by formatSummary's closure
```

### Leak Identification

JavaScript closures capture the **entire variable environment** of their defining scope, not just the variables they explicitly reference. In V8, the compiler performs escape analysis and often (but not always) avoids retaining variables that the closure doesn't use. However:

1. This optimization is not guaranteed.
2. With `eval()` in scope, ALL variables are retained (eval can access any variable by name).
3. Debugging tools and certain complex code patterns defeat the optimization.
4. The intent of the code is not clear to other developers who might add references later.

The safer practice is to always explicitly release large data when it's no longer needed, and to create closures in isolated scopes.

### Fixed Code

```js
// FIX 1: Create the closure in a scope that doesn't contain rawData
function computeSummary(rawData) {
  return {
    count: rawData.length,
    total: rawData.reduce((sum, r) => sum + r.value, 0),
    average: rawData.reduce((sum, r) => sum + r.value, 0) / rawData.length
  };
  // rawData goes out of scope when computeSummary returns
}

function generateReport(rawData) {
  const summary = computeSummary(rawData); // compute in separate scope
  // rawData is NOT in scope here — can't be captured by formatSummary

  const formatSummary = () => {
    // Only captures 'summary' — rawData is inaccessible from this scope
    return `Count: ${summary.count}, Avg: ${summary.average.toFixed(2)}`;
  };

  return { summary, formatSummary };
}

// FIX 2: Explicitly null out the reference if you must keep rawData in scope
function generateReportV2(rawData) {
  const summary = computeSummary(rawData);

  // Explicitly signal that rawData should be released
  rawData = null; // NOT reliable for preventing closure capture,
                  // but good for documentation and prevents use after this point

  const formatSummary = () => {
    return `Count: ${summary.count}, Avg: ${summary.average.toFixed(2)}`;
  };

  return { summary, formatSummary };
}

// FIX 3: Extract only needed values as primitives before closing
function generateReportV3(rawData) {
  const count = rawData.length;                                // primitive
  const total = rawData.reduce((sum, r) => sum + r.value, 0); // primitive
  const average = total / count;                              // primitive
  // rawData is done — all needed values extracted as primitives

  const summary = { count, total, average }; // only primitives

  const formatSummary = () => {
    // Captures count, total, average — all primitives (no object references)
    return `Count: ${count}, Avg: ${average.toFixed(2)}`;
  };

  return { summary, formatSummary };
  // When this function returns, rawData has no references pointing to it
  // (assuming caller doesn't hold it) → eligible for GC
}
```

### Verification

```js
// Test closure scope capture

  const large = new Array(1_000_000).fill('x');
  const small = 'needed';

  const fn = () => small; // only uses 'small'
  return fn;
}
```

### Gotchas
- **V8 optimization is not a guarantee**: in debug builds, all variables may be captured. In minified production builds with dead code elimination, the capture may be removed. Don't rely on engine behavior — write code that makes capture explicit.
- **The `eval()` footgun**: any `eval()` anywhere in the same function forces V8 to retain ALL variables in scope (since `eval` might reference any of them). Avoid `eval` in functions with large local variables.
- **Object references vs primitives**: a closure capturing `{ count: 100, total: 500, average: 5.0 }` holds a reference to the object (which is small). Capturing the rawData array (50MB) is vastly different. Prefer extracting to primitives.

### Follow-up Questions
- "How does `let x = null` help with memory in closures?" → It removes the binding's value, but the binding itself still exists in the scope. V8 may still retain the scope (and thus see `x = null`) rather than GC-ing it. It helps readability (signals intent) and prevents *use* of the variable, but is not a reliable technique for freeing closure-captured memory. The reliable fix is scope isolation (separate function).

## Problem 6 — Debugging and Fixing a Production Memory Leak

### Problem
You're given a Node.js Express server that processes user reports. Memory grows ~10MB every minute under normal load. Using the following information from a heap snapshot comparison, identify the leak and write the fix.

```
Heap Snapshot Comparison (Snapshot 1 → Snapshot 2, 5 minutes apart):
  +1,247 Report objects (shallow: 2KB each, retained: 8MB each)
  +1,247 'process' function objects (these are request handlers)
  +1,247 Closure {query, userId, reportType} objects

The "Retainers" path for a leaked Report object:
  Report → Closure → process handler → Router._handlers[0] → Router → app

Server code (simplified):
```

```js
// app.js
const express = require('express');
const app = express();

app.get('/report', async (req, res) => {
  const { userId, reportType } = req.query;

  // Build an expensive report
  const report = await buildReport(userId, reportType);

  // SOMEWHERE IN HERE IS THE LEAK
  app.get('/download/' + report.id, (req, res) => { // ← AHA
    res.download(report.filePath); // captures 'report'
  });

  res.json({ reportId: report.id, downloadUrl: `/download/${report.id}` });
});
```

### Leak Identification

The leak is `app.get('/download/' + report.id, handler)`. Every time a user requests a report:
1. A new Express route is dynamically added to the application.
2. The handler closure captures `report` (8MB of report data).
3. Express stores route handlers in `app._router.stack` — a permanent array.
4. Routes are NEVER removed from Express after being added.

After 1,247 requests: 1,247 routes with 1,247 captured `report` objects → 1,247 × 8MB = ~10GB of accumulated report data. Express route lookup also slows down (O(n) route matching for n registered routes).

### Retainer Chain Explained

```
GC roots:
  app (Express application — module-level, permanent root)
    → app._router.stack (array of route layers — grows with each request)
      → Route { path: '/download/123', handle: fn }
        → fn (the download handler closure)
          → report (the 8MB report object)
            → report.data (the actual report content)

app is permanent → stack is permanent → all routes are permanent →
all report closures are permanent → all report objects are permanent
```

### Fixed Code

```js
// FIX 1: Use a Map to store reports; route reads from Map
const reportStore = new Map(); // reportId → { filePath, expires }

app.get('/report', async (req, res) => {
  const { userId, reportType } = req.query;

  const report = await buildReport(userId, reportType);

  // Store in Map — not in route closures
  reportStore.set(report.id, {
    filePath: report.filePath,
    createdAt: Date.now()
  });

  // Schedule cleanup of the report after 1 hour
  setTimeout(() => {
    reportStore.delete(report.id);
    // Also delete the file if needed:
    fs.unlink(report.filePath, () => {});
  }, 60 * 60 * 1000).unref(); // unref: don't prevent Node exit

  res.json({ reportId: report.id, downloadUrl: `/download/${report.id}` });
});

// ONE static route — no dynamic registration
app.get('/download/:reportId', (req, res) => {
  const entry = reportStore.get(req.params.reportId);

  if (!entry) {
    return res.status(404).json({ error: 'Report not found or expired' });
  }

  res.download(entry.filePath);
});
```

**FIX 2: Alternative — use signed, short-lived URLs instead of server-side storage**:
```js
const crypto = require('crypto');
const SECRET = process.env.DOWNLOAD_SECRET;

function signReportId(reportId, expiry) {
  const payload = `${reportId}:${expiry}`;
  const sig = crypto.createHmac('sha256', SECRET).update(payload).digest('hex');
  return `${payload}:${sig}`;
}

function verifyToken(token) {
  const [reportId, expiry, sig] = token.split(':');
  const expected = signReportId(reportId, expiry);
  if (token !== expected) return null;
  if (Date.now() > parseInt(expiry)) return null;
  return reportId;
}

app.get('/report', async (req, res) => {
  const report = await buildReport(req.query.userId, req.query.reportType);
  const expiry = Date.now() + 3600000; // 1 hour
  const token = signReportId(report.id, expiry);
  res.json({ downloadUrl: `/download?token=${encodeURIComponent(token)}` });
  // report goes out of scope here — GC can collect it
});

app.get('/download', async (req, res) => {
  const reportId = verifyToken(req.query.token);
  if (!reportId) return res.status(401).json({ error: 'Invalid or expired token' });
  // Retrieve report from database/file system by ID (not from closure)
  const filePath = await getReportPath(reportId);
  res.download(filePath);
});
```

### Gotchas
- **`setTimeout(...).unref()`**: without `unref()`, the cleanup timers prevent Node.js from exiting cleanly when all work is done (useful in tests). `unref()` marks the timer as "non-blocking" — Node exits if timers are the only remaining work.
- **Map-based store also needs eviction**: `reportStore` grows with reports that were never downloaded (user generated but didn't download). The TTL cleanup handles this, but a crashed Node process loses the cleanup timers — implement persistent cleanup (cron job, DB TTL, etc.) for production.
- **File system cleanup**: `reportStore.delete()` removes the Map entry but `fs.unlink()` must be called separately to free disk space. Forgetting this creates a different kind of "leak" (disk space, not heap).

- "How would you find this leak without the heap snapshot data given in the problem?" → First, notice `app._router.stack.length` growing via the monitoring interval. Then profile with `node --inspect` and take heap snapshots, filtering by "Route" and "Closure" objects, examining their retainer paths to find that `app._router` holds them.

## Quick Reference — Memory Leak Patterns and Fixes

```
PATTERN                    | LEAK CAUSE                        | FIX
───────────────────────────────────────────────────────────────────────────────
Event listener not removed | Long-lived emitter holds callback | removeEventListener / off()
                           | closure keeps scope alive         | in cleanup / finally / useEffect return

setInterval never cleared  | Timer is GC root; callback never  | clearInterval() when done
                           | unreachable                       | store ID, clear in cleanup

setTimeout chain           | Self-rescheduling indefinitely    | Cancellation flag / AbortController

Closures capturing scope   | Large variables in closure scope  | Create closures in isolated scope
                           | even if not used                  | Extract needed values as primitives

Detached DOM nodes         | JS var holds removed node;        | null the variable after removeChild
                           | node+listeners+subtree kept alive | WeakRef/WeakMap for DOM caches

Unbounded Map/Set/Array    | Growing without eviction          | LRU cap / TTL / WeakRef values

Dynamic route registration | Framework stores handlers         | Use params/Map, not dynamic routes
                           | permanently (Express, etc.)       | Static routes + runtime lookup

EventEmitter per-request   | Global emitter accumulates        | once() / removeListener in finally
                           | per-request listeners             | process.on() only once per server

Async loop without exit    | for-await holds async frame alive | Cancellation signal / active flag
                           | which holds all captured refs     | break on cancel check per iteration
```

## Common Bugs Checklist

Before shipping any async code, verify:

1. **Every `addEventListener` has a paired `removeEventListener` in cleanup code** — specifically in React `useEffect` return functions, class component `componentWillUnmount`, and Node.js server connection close handlers. The remove call must use the EXACT SAME function reference (stored variable, not re-created anonymous function).

2. **Every `setInterval` ID is stored and `clearInterval` is called in all exit paths** — including error paths. Use `try/finally` to guarantee cleanup: `const id = setInterval(fn, ms); try { ... } finally { clearInterval(id); }`.

3. **Every `process.on()` inside a request handler is a red flag** — per-request registration on the global `process` object accumulates indefinitely. Add process-level handlers once at startup, not per request.

4. **Every Map/Set/object used as a cache has a size limit or eviction policy** — unbounded caches are memory leaks waiting to happen. Implement LRU, TTL, or use WeakRef values for automatic GC-based eviction.

5. **Every async loop (`for await`, recursive setTimeout) has an explicit exit condition** — setting `active = false` after the loop was designed to "stop" doesn't stop it immediately. Use `AbortController`, check the flag between iterations, or destroy the underlying stream/source.

6. **TTL cache cleanup intervals are `unref()`-ed and the cache exposes a `destroy()` method** — a cache with a cleanup `setInterval` that is itself never cleaned up is a timer leak. The `destroy()` method should call `clearInterval` and be called when the cache is no longer needed.

**Final Tip:** At the 5 YOE level, memory leak questions are tested on two dimensions: can you identify the leak from code (pattern recognition), and can you explain the retention chain (GC understanding). The highest-signal answer doesn't just say "add `removeEventListener`" — it traces: "window is a GC root, it holds the listener, the listener closure holds the component scope, the component scope holds the state and DOM refs, so removing the listener breaks the chain and allows everything downstream to be collected." Practice drawing the retention diagram for each pattern: root → holder → listener/timer → closure → large data. The fix is always about breaking one link in that chain. The six problems above cover the patterns that appear most frequently in interviews at companies with React frontends or Node.js backends.
