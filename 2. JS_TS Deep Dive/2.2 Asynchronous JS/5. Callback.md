## Topic A: Anatomy of Callback Hell

### Section A1: Recognition & Root Causes

**Q1. What is callback hell, and what visual and structural patterns identify it?**

A: Callback hell (also "callback pyramid," "pyramid of doom," or "callback spaghetti") is a code pattern where deeply nested callback functions make asynchronous sequential logic visually and structurally complex. Each async step requires nesting inside the previous step's callback — because the result is only available inside that callback. The indentation grows rightward with every step, creating the characteristic pyramid shape. The code is "hellish" not just visually but structurally: error handling must be repeated at every level, the "happy path" is tangled with error paths, shared state must be threaded through closures, and the linear sequence of steps A→B→C→D is expressed as a tree of nested functions.

```js
// Callback hell: a simple four-step sequence looks like a pyramid:
doA(function(err, a) {
  if (err) return handleError(err);
  doB(a, function(err, b) {
    if (err) return handleError(err);
    doC(b, function(err, c) {
      if (err) return handleError(err);
      doD(c, function(err, d) {
        if (err) return handleError(err);
        finish(d);  // ← the actual goal, buried 4 levels deep
      });
    });
  });
});

// Same logic as async/await: four lines, no nesting:
try {
  const a = await doA();
  const b = await doB(a);
  const c = await doC(b);
  const d = await doD(c);
  finish(d);
} catch (err) {
  handleError(err);
}
```

**Q2. What are the three root causes of callback hell?**

A:

**1. Sequential async dependency, expressed as nesting**: humans think sequentially — "do A, then B, then C." Callbacks express this as "do A; in A's callback, do B; in B's callback, do C." The logical sequence becomes syntactic nesting. Each step that needs the previous step's result must live inside the previous step's callback, because that result only exists in that scope.

**2. Inversion of control**: instead of calling a function and getting back a value (synchronous model), you pass your continuation (the next thing to do) to a function and hope it calls it correctly. You've surrendered control over when, how many times, and with what arguments your code runs. This makes composition — combining smaller async tasks into larger ones — structurally difficult.

**3. Error handling verbosity**: each callback must independently check for errors. With N async steps, you write N identical-looking `if (err) return callback(err)` guards. This boilerplate obscures the intent, is easy to forget at any level, and makes errors at deeply nested levels difficult to surface cleanly.

```js
// Root cause #1 — sequential dependency forces nesting:
getUser(id, function(err, user) {        // need user to...
  getPosts(user.id, function(err, posts) { // need posts to...
    getComments(posts[0].id, function(err, comments) { // ...etc
    });
  });
});

// Root cause #3 — error boilerplate repeated at every level:
step1(function(err, r1) {
  if (err) return cb(err);  // ← copy-pasted guard
  step2(r1, function(err, r2) {
    if (err) return cb(err); // ← copy-pasted guard
    step3(r2, function(err, r3) {
      if (err) return cb(err); // ← copy-pasted guard
    });
  });
});
```

**Q3. What is "inversion of control" in callbacks, and what trust problems does it create?**

A: Inversion of control (IoC) means transferring responsibility for calling your code to an external party. When you pass a callback to `thirdPartyLib.doSomething(myCallback)`, you've handed control to that library. You must trust it to: call `myCallback` exactly once (not zero or multiple times), call it asynchronously (not synchronously — see Q4), call it with the correct arguments in the correct order, handle any exceptions thrown by `myCallback`, and not call it after you've cleaned up resources that `myCallback` depends on. In practice, third-party libraries may violate any of these. Promises invert this back: instead of you giving them a callback, they give you a Promise — a value you hold that represents the future result. The Promise specification guarantees all the trust properties that arbitrary callbacks don't.

```js
// With callbacks — you trust the library to behave:
paymentLib.charge(card, amount, function(err, result) {
  // Will this be called once? Synchronously? If it throws, does the error propagate?
  // You have no control. You can't verify any of these properties.
  db.save(result); // if called twice, you'd insert two records
});

// With Promises — the Promise spec guarantees correct behavior:
paymentLib.chargeAsync(card, amount)
  .then(result => db.save(result)) // guaranteed: called once, async, errors caught
  .catch(err => handleError(err));
```

**Q4. What is the "Zalgo" problem, and why does it destabilize callback-based code?**

A: "Releasing Zalgo" (named from a blog post by Isaac Schlueter) describes a function that **sometimes calls its callback synchronously and sometimes asynchronously** — the timing is non-deterministic. This breaks a critical assumption: callers expect callbacks to be either always-sync or always-async, never both. When a function is inconsistent, callers can't write correct code around it — state set after the call may not be set yet if the callback fires synchronously. Libraries that check a cache (sync if cached, async if not) are the classic example. Promises are always async — `.then()` callbacks always run as microtasks, even if the Promise is already settled when `.then()` is called. This eliminates Zalgo entirely.

```js
// Zalgo: inconsistent callback timing
function readUser(id, callback) {
  if (cache[id]) {
    callback(null, cache[id]); // ← SYNC: calls callback before returning!
  } else {
    db.query(id, function(err, user) {
      cache[id] = user;
      callback(err, user); // ← ASYNC: called later
    });
  }
}

// The caller can't safely write this:
let dataReady = false;
readUser(42, function(err, user) {
  console.log('dataReady:', dataReady); // true if async, false if sync — unpredictable!
  render(user);
});
dataReady = true;

// Fix: always defer, even if synchronous:
function readUser(id, callback) {
  if (cache[id]) {
    process.nextTick(() => callback(null, cache[id])); // always async ✓
  } else {
    db.query(id, function(err, user) { cache[id] = user; callback(err, user); });
  }
}
// Or: just return a Promise (which is always async by spec).
```

**Q5. What specific software quality problems does callback hell create beyond visual nesting?**

A: Five concrete problems beyond appearance:

**Untestability**: anonymous inline callbacks can't be tested in isolation. You can't import, stub, or unit-test a function that exists only as a literal expression inside another function's argument list.

**Debugging opacity**: before async stack traces, callback-based code produced traces like `anonymous → anonymous → anonymous`. The actual call chain was invisible. Promises (and later, async/await) restored meaningful stack traces.

**Closure variable shadowing**: nested callbacks with the same parameter name (`err`, `result`) shadow outer ones. A typo in the wrong scope silently uses the outer `err` instead of catching the inner error.

**The "lost error" pattern**: if any single `if (err) return callback(err)` guard is forgotten, the error is silently swallowed and execution continues with `undefined` data.

**Composition impossibility**: extracting a sub-chain for reuse requires carefully threading all closed-over variables (the `callback`, any shared connection, accumulated data) through function parameters — what should be a simple function extraction becomes a coordination problem.

## Topic B: Refactoring Techniques

### Section B1: The Refactoring Ladder

**Q6. What is the "named functions" refactor, what does it solve, and what does it not solve?**

A: The named functions refactor replaces anonymous inline callback functions with named function declarations or expressions. It solves: stack traces now show function names; each callback can be read, documented, and tested independently; code is visually less nested (functions are defined at the top level, called by name). It does NOT solve: the fundamental inversion of control (you still hand a callback to someone else), the Zalgo problem, error handling repetition (you still write `if (err)` at each level), or variable-threading (shared state like `connection` and `callback` must still be passed through parameters or kept in a shared outer scope). It's a useful first step but leaves the structural problems intact.

```js
// Before: anonymous pyramid
function registerUser(data, callback) {
  fs.readFile('./config.json', 'utf8', function(err, raw) {
    if (err) return callback(err);
    db.connect(JSON.parse(raw).dsn, function(err, conn) {
      if (err) return callback(err);
      conn.query('SELECT 1 FROM users WHERE email = ?', [data.email], function(err, rows) {
        if (err) return callback(err);
        if (rows.length) return callback(new Error('Email taken'));
        callback(null, { conn, data });
      });
    });
  });
}

// After: named functions — flatter visually, but structurally identical
function registerUser(data, callback) {
  fs.readFile('./config.json', 'utf8', onConfigRead);

  function onConfigRead(err, raw) {
    if (err) return callback(err);
    db.connect(JSON.parse(raw).dsn, onDbConnected);
  }

  function onDbConnected(err, conn) {
    if (err) return callback(err);
    conn.query('SELECT 1 FROM users WHERE email = ?', [data.email], onEmailChecked.bind(null, conn));
  }

  function onEmailChecked(conn, err, rows) {
    if (err) return callback(err);
    if (rows.length) return callback(new Error('Email taken'));
    callback(null, { conn, data }); // still threading conn and callback through closures/params
  }
}
```

**Q7. What is promisification, and how do you convert any callback-based function to return a Promise?**

A: Promisification wraps a callback-based function so it returns a Promise instead. The standard pattern: create a `new Promise` whose executor calls the original callback function; in the callback, call `reject(err)` on error and `resolve(result)` on success. This one-time wrapper converts the function permanently from the callback model to the Promise model, unlocking `.then()` chaining and `await`. The wrapper must be written once per function; afterward, the promisified version is used everywhere.

The pattern is mechanical for Node.js error-first callbacks (`callback(err, result)`) — so mechanical that `util.promisify` (Q8) automates it. Non-standard callbacks (callbacks called multiple times, with multiple results, or with non-standard argument order) require custom handling.

```js
// Manual promisification of any callback function:
function promisify(fn) {
  return function(...args) {
    return new Promise((resolve, reject) => {
      fn(...args, function(err, result) {   // assume error-first callback convention
        if (err) reject(err);
        else resolve(result);
      });
    });
  };
}

// Usage:
const readFile  = promisify(fs.readFile);
const dbConnect = promisify(db.connect);
const dbQuery   = promisify(connection.query.bind(connection));

// Now usable with .then() or await:
readFile('./config.json', 'utf8')
  .then(raw => dbConnect(JSON.parse(raw).dsn))
  .then(conn => dbQuery('SELECT 1 FROM users WHERE email = ?', [email]))
  .catch(err => console.error(err));

// Manual promisification for non-standard callback (e.g., success callback before error):
function weirdAsync(arg, successCb, errorCb) { /* ... */ }
function weirdAsyncPromise(arg) {
  return new Promise((resolve, reject) => weirdAsync(arg, resolve, reject));
}
```

**Q8. What is `util.promisify`, what convention must the target function follow, and when is it insufficient?**

A: `util.promisify` (Node.js built-in) converts a function that follows the Node.js callback convention — last argument is `callback(err, value)` — into a function that returns a Promise. It's not magic: it does exactly the same thing as the manual `promisify` in Q7, but automatically. The function must have the callback as its last parameter, and the callback must receive `(err, result)` in that exact order.

It is insufficient when: (1) the callback receives multiple result arguments (`callback(err, result1, result2)`) — only `result1` is captured; use `[util.promisify.custom]` to define a custom promisifier. (2) The callback is called multiple times (event emitters, progress callbacks) — a Promise can only resolve once. (3) The callback convention is non-standard (callback not last, error not first). (4) Cancellation is needed — Promises have no built-in cancellation; you'd need `AbortController` alongside.

```js
const { promisify } = require('util');
const fs = require('fs');

// Standard usage — fs.readFile uses (err, data) convention:
const readFile = promisify(fs.readFile);
const writeFile = promisify(fs.writeFile);

const data = await readFile('./config.json', 'utf8');  // ✓

// Custom promisifier for multi-argument callbacks:
function multiCallback(arg, callback) { callback(null, 'result1', 'result2'); }
multiCallback[util.promisify.custom] = function(arg) {
  return new Promise((resolve, reject) => {
    multiCallback(arg, (err, r1, r2) => {
      if (err) reject(err);
      else resolve({ r1, r2 }); // pack multiple results into an object
    });
  });
};
const multiAsync = promisify(multiCallback);
const { r1, r2 } = await multiAsync('arg'); // ✓

// fs/promises — modern Node.js ships promise-native APIs, no promisification needed:
const { readFile: readFilePromise } = require('fs/promises');
// or: import { readFile } from 'fs/promises';
```

**Q9. How does async/await eliminate nesting, and what is its fundamental relationship to Promises?**

A: `async/await` is syntactic sugar over Promises — every `async function` returns a Promise, and every `await expr` pauses the function's execution until `expr`'s Promise settles, then resumes with the resolved value (or throws the rejection). The JavaScript engine transforms the async function body into a Promise chain at compile time. The visual result: sequential async logic reads as sequential synchronous logic, with no nesting. The full depth of a 5-step sequential async pipeline is 5 lines, regardless of dependencies between steps.

The key insight: `await` doesn't block the thread — it yields execution back to the event loop (like a Promise `.then()`), then resumes when the awaited Promise settles. `async/await` eliminates nesting but does not change the asynchronous nature of the code — it's still non-blocking.

```js
// Promise chain (no nesting, but still chained):
function registerUser(data) {
  return readConfig()
    .then(cfg  => db.connect(cfg.dsn))
    .then(conn => conn.query('SELECT 1 FROM users WHERE email=?', [data.email])
                       .then(rows => ({ conn, rows })))  // ← mini-nesting for passing conn
    .then(({ conn, rows }) => {
      if (rows.length) throw new Error('Email taken');
      return bcrypt.hash(data.password, 10).then(hash => ({ conn, hash }));
    });
}

// async/await (truly flat — reads like synchronous code):
async function registerUser(data) {
  const cfg  = await readConfig();
  const conn = await db.connect(cfg.dsn);
  const rows = await conn.query('SELECT 1 FROM users WHERE email=?', [data.email]);

  if (rows.length) throw new Error('Email taken');

  const hash   = await bcrypt.hash(data.password, 10);
  const result = await conn.insert('users', { email: data.email, password: hash });

  return { id: result.insertId, email: data.email };
}
```

**Q10. What is the parallel execution pattern — how does it evolve from callbacks through Promises to async/await?**

A: Sequential async patterns (each step waits for the previous) are natural in all paradigms. The complexity difference shows most clearly in **parallel** execution — running independent async operations simultaneously and waiting for all to complete.

**Callbacks**: the "counter pattern" — track how many operations have completed; when all are done, call the final callback. Error handling adds additional complexity: if one fails, should you call the callback immediately or wait for others?

**Promises**: `Promise.all([op1(), op2(), op3()])` — one line, built-in fail-fast semantics, result array in input order.

**async/await**: `await Promise.all([op1(), op2(), op3()])` — identical to the Promise version, but integrable with surrounding `async` code. The common mistake: using sequential `await op1(); await op2();` for independent operations (2x slower than parallel).

```js
// CALLBACKS — parallel with counter (verbose, fragile):
function fetchDashboard(userId, callback) {
  let done = 0, hasError = false;
  const results = {};

  function check() {
    if (++done === 3 && !hasError) callback(null, results);
  }

  fetchUser(userId, function(err, user) {
    if (err) { if (!hasError) { hasError = true; callback(err); } return; }
    results.user = user; check();
  });
  fetchStats(userId, function(err, stats) {
    if (err) { if (!hasError) { hasError = true; callback(err); } return; }
    results.stats = stats; check();
  });
  fetchNotifications(userId, function(err, notes) {
    if (err) { if (!hasError) { hasError = true; callback(err); } return; }
    results.notes = notes; check();
  });
}

// PROMISE.ALL — one line, same semantics:
function fetchDashboard(userId) {
  return Promise.all([fetchUser(userId), fetchStats(userId), fetchNotifications(userId)])
    .then(([user, stats, notes]) => ({ user, stats, notes }));
}

// ASYNC/AWAIT — parallel, but watch the anti-pattern:
async function fetchDashboard(userId) {
  // ✗ ANTI-PATTERN — sequential, not parallel (3x slower):
  const user  = await fetchUser(userId);
  const stats = await fetchStats(userId);
  const notes = await fetchNotifications(userId);

  // ✓ CORRECT — parallel (max latency of the three):
  const [user, stats, notes] = await Promise.all([
    fetchUser(userId), fetchStats(userId), fetchNotifications(userId),
  ]);
  return { user, stats, notes };
}
```

## Topic C: Error Handling Evolution

### Section C1: From Callbacks to try/catch

**Q11. What is the Node.js error-first callback convention, and what are its inherent problems?**

A: The Node.js error-first (or "errback") convention: callback functions always receive the error as the first argument (`callback(err, result)`). If the operation succeeded, `err` is `null`/`undefined` and `result` holds the value. If it failed, `err` is an `Error` instance and `result` may be undefined. Every caller must check `err` before using `result`. The convention is a community standard, not a language feature — nothing enforces it. Problems: (1) easy to forget the `if (err)` check — no compiler or runtime warning; (2) error handling at every single level; (3) errors thrown inside a callback are not caught by the outer error-first callback — they become uncaught exceptions; (4) the check/early-return pattern (`if (err) return callback(err)`) is semantic noise that dominates the codebase; (5) no way to handle errors from multiple async steps in one place.

```js
// Error-first convention — correct usage:
fs.readFile('data.txt', 'utf8', function(err, data) {
  if (err) return callback(err); // ← must check every time
  process(data);
});

// The forgotten check — silent data corruption:
fs.readFile('data.txt', 'utf8', function(err, data) {
  // forgot if (err)! process() receives undefined as data
  process(data); // ← undefined passed — may fail silently or corrupt downstream
});

// Throw inside callback — unhandled exception, not caught by errback:
fs.readFile('data.txt', 'utf8', function(err, data) {
  if (err) return callback(err);
  throw new Error('parse failed'); // ← NOT caught by callback convention — crashes Node.js!
  // Fix: wrap in try/catch and call callback(e)
});
```

**Q12. How does Promise error handling improve on callback error handling?**

A: Promises centralize error handling through `.catch()`. Any rejection anywhere in a `.then()` chain propagates forward automatically, skipping all fulfillment handlers, until a `.catch()` (or rejection handler) is reached. You write error handling once at the end of the chain, not at every step. Additionally: errors thrown inside `.then()` handlers become rejections automatically — no manual try/catch needed around handler code. Unhandled rejections are detectable at the runtime level (`unhandledRejection` event) — better than silently swallowed callback errors.

```js
// Callback error handling — repeated boilerplate at every level:
step1(function(err, r1) {
  if (err) return callback(err); // level 1
  step2(r1, function(err, r2) {
    if (err) return callback(err); // level 2
    step3(r2, function(err, r3) {
      if (err) return callback(err); // level 3
      callback(null, r3);
    });
  });
});

// Promise error handling — one catch for all levels:
step1()
  .then(r1 => step2(r1))
  .then(r2 => step3(r2))
  .catch(err => callback(err)); // ← catches ANY error from step1, step2, or step3

// Throw inside .then() becomes rejection automatically:
Promise.resolve(data)
  .then(d => { if (!d.valid) throw new Error('invalid'); return process(d); })
  .then(result => save(result))
  .catch(err => console.error(err)); // catches both the throw and any rejection from process/save
```

**Q13. How does `try/catch` with `async/await` provide the cleanest error handling, and what does it unify?**

A: `try/catch` with `async/await` unifies synchronous and asynchronous error handling into the same syntax. A single `try/catch` block catches: synchronous throws, `await`ed Promise rejections, and JSON parse errors — all in one place, with a linear call stack readable in the catch block. This eliminates the dual-mode error handling of older Node.js code where sync errors needed try/catch and async errors needed errback conventions. The stack trace in the `catch` block shows the actual source line that caused the error, because async stack traces in modern V8 show the await chain.

```js
// async/await — one try/catch for all error types:
async function registerUser(data) {
  try {
    const raw  = await fs.promises.readFile('./config.json', 'utf8');
    const cfg  = JSON.parse(raw);       // ← synchronous throw — caught here too ✓
    const conn = await db.connect(cfg.dsn);
    const rows = await conn.query('SELECT 1 FROM users WHERE email=?', [data.email]);

    if (rows.length) throw new Error('Email already registered'); // ← caught here too ✓

    const hash = await bcrypt.hash(data.password, 10);
    await conn.insert('users', { email: data.email, password: hash });
  } catch (err) {
    // Single handler for: file not found, JSON syntax error, DB connection failure,
    // query error, 'Email already registered', bcrypt error, insert error.
    // All five async and two sync error types — one catch block.
    logger.error('Registration failed:', err);
    throw err; // re-throw to preserve error for the caller
  }
}
```

**Q14. What are the async/await error handling gotchas — what errors does `try/catch` miss?**

A: Three categories of errors that `try/catch` in an `async` function does NOT catch:

**1. Floating Promises** — an `async` call that is not `await`ed: `sendEmail()` (no await). The returned Promise rejects but no one handles it — unhandled rejection.

**2. Errors in non-awaited parallel operations inside `Promise.all`**: if one of the operations in `Promise.all` rejects AND the outer `try/catch` catches a different error first, the remaining promises may reject after the `catch` has already handled something — those become unhandled.

**3. Errors in async event handlers or callbacks passed to synchronous APIs**: a `setTimeout(async () => { throw new Error('oops'); }, 0)` — the error is in an async callback, not in the `await` chain of the outer function. The outer `try/catch` cannot reach it.

```js
async function risky() {
  try {
    await goodOp();

    badOp(); // ← NO await — rejection is unhandled! try/catch won't see it.

    const [a, b] = await Promise.all([op1(), op2()]);
    // If op1 rejects and try/catch runs, op2's rejection is now unhandled.
    // Fix: use Promise.allSettled or individual try/catch per operation.

    setTimeout(async () => {
      throw new Error('from timeout'); // ← NOT caught by outer try/catch!
    }, 1000);

  } catch (err) {
    console.error(err); // only catches: await rejections and sync throws in this function
  }
}

// Fix pattern — always await async calls, even fire-and-forget:
badOp().catch(err => logger.error('badOp failed:', err)); // explicit non-critical error handling
```

**Q15. What is the "async error boundary" pattern for wrapping async Express/NestJS route handlers?**

A: In Express, route handlers are synchronous functions — async errors (rejected Promises) are not automatically passed to `next(err)`. Without a wrapper, an unhandled rejection in an `async` route handler crashes the process. The async error boundary pattern: wrap every async handler in a higher-order function that catches any rejection and forwards it to `next(err)`.

NestJS solves this at the framework level — all exceptions from controllers and interceptors are caught by its exception filter pipeline. But knowing the pattern explains why frameworks like Express 5 (which auto-catches async errors) and NestJS exist.

```js
// The problem in Express 4:
app.get('/users/:id', async (req, res, next) => {
  const user = await db.findUser(req.params.id); // if this rejects → unhandled rejection!
  res.json(user);
});

// Fix: async wrapper (the "asyncHandler" pattern):
const asyncHandler = fn => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next); // forwards rejection to Express error handler

app.get('/users/:id', asyncHandler(async (req, res) => {
  const user = await db.findUser(req.params.id); // rejection → next(err) ✓
  res.json(user);
}));

// Express 5 (async-native — no wrapper needed):
app.get('/users/:id', async (req, res) => {
  const user = await db.findUser(req.params.id); // auto-forwarded to error handler ✓
  res.json(user);
});

// NestJS equivalent — exceptions automatically handled by exception filters:
@Get(':id')
async getUser(@Param('id') id: string) {
  return this.usersService.findOne(id); // can throw HttpException, all caught by filter ✓
}
```

## Topic D: Advanced Patterns & Interview-Style

**Q16. When are callbacks still the right tool despite async/await being available?**

A: Four situations where callbacks remain correct or preferable:

**1. Multiple invocations**: callbacks can be called many times; Promises resolve once. Event handlers (`button.addEventListener('click', fn)`), stream data events (`readable.on('data', fn)`), and WebSocket message handlers are inherently multi-shot — they must be callbacks (or converted to observables/async iterators for pipeline use).

**2. Synchronous callbacks for pure data transformation**: `Array.prototype.map`, `filter`, `sort`, `forEach` take synchronous callbacks. These are not async operations — no Promise is needed or appropriate. An `async` callback passed to `.map()` returns a `Promise[]` not the resolved values.

**3. Node.js core internals and performance-critical code**: the overhead of Promise creation (though minimal) matters at very high throughput. Node.js internal streams and native addons use callbacks for performance.

**4. Legacy codebases**: when interfacing with legacy callback-based code that can't be changed, wrapping everything in Promises adds overhead. Sometimes a single promisification at the boundary is cleaner than threading Promises through legacy code.

**Q17. Walk through your decision process when you encounter callback hell in a codebase.**

A: A pragmatic four-step process:

**Step 1 — Assess scope**: Is this a one-off script or production code? How deeply nested? How many distinct async operations? If it's a 2-level nesting in a script that runs once, named functions may suffice. If it's a critical production service with 5+ levels, go straight to async/await.

**Step 2 — Check available APIs**: Does Node.js already have a Promise-native API? (`fs/promises`, `dns/promises`, etc.) Use those directly — no promisification needed. Does the library have a `.then()`-returning version? (Most modern libraries do.) Can you `util.promisify` the remaining callbacks?

**Step 3 — Refactor bottom-up**: start with the innermost callbacks — the deepest nesting — and promisify each async function. Work outward. Each promisified function can now be used with `await`. You don't need to refactor everything at once.

**Step 4 — Flatten with async/await**: once all async operations return Promises, replace the `.then()` chains with `async/await`. Add a single `try/catch` at each logical unit (one function = one try/catch). Extract parallel operations to `Promise.all`. Test after each step.

**Q18. In one sentence each, state what problem each refactoring approach solves.**

A:
- **Named functions**: replaces anonymous callbacks with named ones — improves readability, testability, and stack traces, but leaves the structural callback problems intact.
- **Promisification (`new Promise` wrapper)**: converts a callback-based function to return a Promise — enabling `.then()` chaining and `await`, inverting control back to the caller.
- **`util.promisify`**: automates promisification for functions following the Node.js error-first callback convention — eliminating manual wrapper boilerplate.
- **Promise chaining (`.then()`)**: flattens sequential async dependencies from deep nesting to a horizontal chain — with centralized error handling via `.catch()`.
- **`async/await`**: makes sequential async code read as sequential synchronous code with no nesting — and unifies sync and async error handling into a single `try/catch`.
- **`Promise.all`**: replaces the callback counter pattern — runs independent async operations in parallel and collects all results or fails fast on the first rejection.
- **`Promise.allSettled`**: runs all operations regardless of failure — delivers every result, success or failure, for batch processing without abort-on-failure.
- **Async error boundary wrapper**: adapts `async` functions to synchronous-callback frameworks (like Express 4) — ensuring all rejections are routed to the error handler rather than becoming unhandled rejections.

## Implementation 1 — The Baseline: Callback Hell (User Registration)

### Challenge
A user registration flow: read config → connect to DB → check for duplicate email → hash password → insert user → send welcome email. Six sequential steps, each depending on the previous result. This is the canonical callback hell scenario.

### Pattern
Baseline — the problem to solve. Shows the pyramid, repeated error guards, variable threading through closures.

### Key Insight
Each step depends on the previous result, forcing nesting. The six-step sequence becomes six levels deep. The `if (err) return callback(err)` guard appears five times. The final result (`{ id, email }`) is six function calls away from where it's returned.

### Implementation

```js
const fs       = require('fs');
const bcrypt   = require('bcrypt');
const db       = require('./db');          // hypothetical callback-based driver
const mailer   = require('./mailer');

// registerUser: 6 async steps, 5 levels of nesting, 5 repeated error guards.
function registerUser(userData, callback) {
  // Step 1: Read database config from file
  fs.readFile('./config.json', 'utf8', function(configErr, rawConfig) {
    if (configErr) return callback(configErr); // guard #1

    let config;
    try {
      config = JSON.parse(rawConfig); // synchronous throw — not caught by callback!
    } catch (parseErr) {
      return callback(parseErr);       // manual try/catch required
    }

    // Step 2: Connect to database
    db.connect(config.connectionString, function(connErr, connection) {
      if (connErr) return callback(connErr); // guard #2

      // Step 3: Check if email already exists
      connection.query(
        'SELECT id FROM users WHERE email = ?',
        [userData.email],
        function(queryErr, rows) {
          if (queryErr) return callback(queryErr); // guard #3

          if (rows.length > 0) {
            return callback(new Error(`Email ${userData.email} is already registered`));
          }

          // Step 4: Hash the password
          bcrypt.hash(userData.password, 12, function(hashErr, hashedPassword) {
            if (hashErr) return callback(hashErr); // guard #4

            // Step 5: Insert the new user
            connection.query(
              'INSERT INTO users (email, password, name, created_at) VALUES (?, ?, ?, NOW())',
              [userData.email, hashedPassword, userData.name],
              function(insertErr, result) {
                if (insertErr) return callback(insertErr); // guard #5

                const newUser = { id: result.insertId, email: userData.email, name: userData.name };

                // Step 6: Send welcome email (non-critical — log error but don't fail registration)
                mailer.send({
                  to:      userData.email,
                  subject: 'Welcome to the platform!',
                  body:    `Hi ${userData.name}, your account is ready.`,
                }, function(mailErr) {
                  if (mailErr) {
                    // Email failure is non-critical: log it but still return success
                    console.error('Welcome email failed:', mailErr.message);
                  }
                  // Success: return the new user regardless of email result
                  callback(null, newUser); // ← the actual result, buried 6 levels deep
                });
              }
            );
          });
        }
      );
    });
  });
}

// Usage:
registerUser({ name: 'Alice', email: 'alice@example.com', password: 'secret' },
  function(err, user) {
    if (err) return console.error('Registration failed:', err.message);
    console.log('Registered:', user);
  }
);
```

- **Lines of code**: ~50 lines for 6 steps + error handling. async/await version: ~20 lines.

## Implementation 2 — Refactor Step 1: Named Functions

### Challenge
Same user registration flow, same callback-based APIs — but anonymous callbacks are extracted to named functions. Shows what named functions improve and what they leave unchanged.

### Pattern
Named function extraction — reduces nesting visually, enables individual function naming and testing, but retains the callback structure.

### Key Insight
The nesting depth is reduced visually: functions are defined at the same level and called by name. But the structural problems remain — `userData`, `callback`, and intermediate values like `connection` must still be threaded through function parameters or closed over from the outer scope.

### Implementation

```js
function registerUser(userData, callback) {
  // Step 1: read config — handler is named, not anonymous
  fs.readFile('./config.json', 'utf8', onConfigRead);

  // Named: readable in stack traces, can be documented independently
  function onConfigRead(configErr, rawConfig) {
    if (configErr) return callback(configErr);
    let config;
    try { config = JSON.parse(rawConfig); } catch (e) { return callback(e); }
    db.connect(config.connectionString, onConnected);
  }

  // Still closing over: userData, callback (from outer scope)
  // Still threading: connection (via bind or inner closure)
  function onConnected(connErr, connection) {
    if (connErr) return callback(connErr);
    connection.query(
      'SELECT id FROM users WHERE email = ?',
      [userData.email],
      onEmailChecked.bind(null, connection) // threading connection via bind
    );
  }

  function onEmailChecked(connection, queryErr, rows) {
    if (queryErr) return callback(queryErr);
    if (rows.length > 0) return callback(new Error(`Email ${userData.email} is already registered`));
    bcrypt.hash(userData.password, 12, onPasswordHashed.bind(null, connection));
  }

  function onPasswordHashed(connection, hashErr, hashedPassword) {
    if (hashErr) return callback(hashErr);
    connection.query(
      'INSERT INTO users (email, password, name, created_at) VALUES (?, ?, ?, NOW())',
      [userData.email, hashedPassword, userData.name],
      onUserInserted
    );
  }

  function onUserInserted(insertErr, result) {
    if (insertErr) return callback(insertErr);
    const newUser = { id: result.insertId, email: userData.email, name: userData.name };
    mailer.send({ to: userData.email, subject: 'Welcome!', body: `Hi ${userData.name}.` }, onMailSent.bind(null, newUser));
  }

  function onMailSent(newUser, mailErr) {
    if (mailErr) console.error('Email failed:', mailErr.message); // non-critical
    callback(null, newUser); // ✓
  }
}
```

### What Improved vs What Didn't

```
IMPROVED:
  ✓ Stack traces now show: onConfigRead → onConnected → onEmailChecked → ...
  ✓ Each step can be read in isolation
  ✓ Nesting depth: 1 (all inner functions at same level as outer)
  ✓ onEmailChecked could theoretically be exported and unit-tested

NOT IMPROVED:
  ✗ Still passing userData and callback through closure from outer scope
  ✗ Still threading connection through every function (via .bind or extra param)
  ✗ Still 5 repeated if (err) return callback(err) guards
  ✗ Still inversion of control — all the trust problems remain
  ✗ Synchronous throws still need manual try/catch
  ✗ Non-critical mailer error handling still awkward
  ✗ Parallel operations still require the counter pattern
```

## Implementation 3 — Refactor Step 2: Promisification

### Challenge
Convert each callback-based API to return a Promise. Chain the steps with `.then()`. Error handling is centralized. Shows the intermediate state between callbacks and async/await.

### Pattern
Promisification + Promise chaining — each API is wrapped once; the chain reads left-to-right rather than inside-out.

### Key Insight
Once each function returns a Promise, sequential dependencies become a flat `.then()` chain. A single `.catch()` handles all errors from all steps. Returning a Promise from `.then()` sequences the steps — the next `.then()` waits for the returned Promise to settle before running.

### Implementation

```js
const { promisify } = require('util');
const fs = require('fs');

// Step 1: Promisify callback-based APIs once, use everywhere:
const readFile = promisify(fs.readFile);
// db.connect and connection.query have non-standard APIs — manual promisify:
function connectDb(dsn) {
  return new Promise((resolve, reject) =>
    db.connect(dsn, (err, conn) => err ? reject(err) : resolve(conn))
  );
}
function query(conn, sql, params) {
  return new Promise((resolve, reject) =>
    conn.query(sql, params, (err, rows) => err ? reject(err) : resolve(rows))
  );
}
const hashPassword = promisify(bcrypt.hash);
function sendEmail(options) {
  return new Promise((resolve, reject) =>
    mailer.send(options, (err) => err ? reject(err) : resolve())
  );
}

// Registration function: flat chain, single catch
function registerUser(userData) {
  let connection; // shared across chain steps — still requires outer variable

  return readFile('./config.json', 'utf8')
    .then(raw => JSON.parse(raw))               // JSON.parse throws → becomes rejection ✓
    .then(cfg => connectDb(cfg.connectionString))
    .then(conn => {
      connection = conn;                         // thread connection through outer var
      return query(conn, 'SELECT id FROM users WHERE email = ?', [userData.email]);
    })
    .then(rows => {
      if (rows.length > 0) throw new Error(`Email ${userData.email} is already registered`);
      return hashPassword(userData.password, 12);
    })
    .then(hash =>
      query(connection, 'INSERT INTO users (email, password, name) VALUES (?, ?, ?)',
        [userData.email, hash, userData.name])
    )
    .then(result => {
      const newUser = { id: result.insertId, email: userData.email, name: userData.name };
      // Non-critical email: start it but don't block — don't return the Promise
      sendEmail({ to: userData.email, subject: 'Welcome!', body: `Hi ${userData.name}.` })
        .catch(err => console.error('Email failed (non-critical):', err.message));
      return newUser; // resolve chain with newUser immediately
    })
    .catch(err => {
      // Single handler for ALL errors from ALL steps above ✓
      // Re-throw to let the caller handle it:
      throw err;
    });
}

// Usage — caller handles rejection:
registerUser({ name: 'Alice', email: 'alice@example.com', password: 'secret' })
  .then(user => console.log('Registered:', user))
  .catch(err => console.error('Registration failed:', err.message));
```

### What Improved vs What Didn't

```
IMPROVED:
  ✓ Flat chain — no nesting; steps read left-to-right
  ✓ Single .catch() for all step errors
  ✓ JSON.parse throw automatically caught as rejection
  ✓ Non-critical email handled cleanly without blocking
  ✓ Caller uses .then()/.catch() — standard, composable

STILL NOT IDEAL:
  ~ `connection` outer variable: a minor structural wart.
    Because .then() handlers are separate functions, shared mutable state
    (like `connection`) requires an outer variable or careful return value bundling.
  ~ chain is less readable than sequential code — you must track what each .then() receives
  ~ Error types can't easily be classified per-step without intermediate .catch() handlers
```

## Implementation 4 — Refactor Step 3: async/await (Final Form)

### Challenge
The same registration flow using `async/await` — the cleanest form. Sequential steps read sequentially. One `try/catch` for all errors. No nesting, no shared outer variables.

### Pattern
async/await with single `try/catch` — the final, idiomatic modern form.

### Key Insight
Sequential `await` expressions remove both the nesting and the outer variable threading. `connection` is declared with `const` inside the `try` block — no shared mutable outer state. The `try/catch` block cleanly separates the happy path from error handling.

### Implementation

```js
// Promisified APIs from Implementation 3 are reused.
// The async function itself: clean, flat, sequential.

async function registerUser(userData) {
  // Single try/catch covers all async and sync errors in the happy path:
  try {
    // Step 1: Read and parse config (JSON.parse throw is caught by try/catch ✓)
    const raw    = await readFile('./config.json', 'utf8');
    const config = JSON.parse(raw); // sync throw → caught by outer try/catch ✓

    // Step 2: Connect to database
    const connection = await connectDb(config.connectionString); // const! no outer var needed

    // Step 3: Check for duplicate email
    const existing = await query(connection,
      'SELECT id FROM users WHERE email = ?', [userData.email]);

    if (existing.length > 0) {
      throw new Error(`Email ${userData.email} is already registered`);
    }

    // Step 4: Hash password
    const hashedPassword = await hashPassword(userData.password, 12);

    // Step 5: Insert user
    const result = await query(connection,
      'INSERT INTO users (email, password, name) VALUES (?, ?, ?)',
      [userData.email, hashedPassword, userData.name]);

    const newUser = { id: result.insertId, email: userData.email, name: userData.name };

    // Step 6: Non-critical welcome email — fire and forget with explicit error handling
    sendEmail({ to: userData.email, subject: 'Welcome!', body: `Hi ${userData.name}.` })
      .catch(err => console.error('Welcome email failed (non-critical):', err.message));
    // Note: NOT awaited — registration completes immediately; email sends in background ✓

    return newUser;

  } catch (err) {
    // Centralized error logging and classification:
    if (err.code === 'ENOENT') throw new Error('Server configuration missing');
    if (err.code === 'ECONNREFUSED') throw new Error('Database unavailable');
    if (err.message.includes('already registered')) throw err; // pass through business errors
    // Unexpected errors: log and re-throw
    console.error('Unexpected registration error:', err);
    throw err;
  }
}

// Caller — async context:
// In Express with asyncHandler wrapper (from Q15):
app.post('/register', asyncHandler(async (req, res) => {
  const user = await registerUser(req.body);
  res.status(201).json({ success: true, user });
}));

// Standalone script with top-level await (Node.js 14.8+):
try {
  const user = await registerUser({ name: 'Alice', email: 'alice@example.com', password: 'secret' });
  console.log('Registered:', user);
} catch (err) {
  console.error('Registration failed:', err.message);
  process.exit(1);
}
```

## Implementation 5 — Parallel Operations: Callbacks vs Promise.all

### Challenge
For a user dashboard, fetch three independent data sources simultaneously: user profile, activity stats, and recent notifications. Show the callback "counter pattern" versus the clean `Promise.all` approach.

### Pattern
Parallel async execution — the counter pattern (callbacks) vs `Promise.all` (Promises/async/await).

### Key Insight
The callback counter pattern requires: a shared mutable counter, shared results object, shared error flag (to prevent calling back multiple times on multi-failure), and careful synchronization. `Promise.all` replaces all of this with a single line.

### Implementation

```js
// ─── CALLBACK VERSION: The Counter Pattern ─────────────────────────────────

function fetchDashboard(userId, callback) {
  let completedCount = 0;
  let errorReported  = false; // prevent double-callback on multiple failures
  const results = { user: null, stats: null, notifications: null };

  function onComplete(err) {
    if (err) {
      if (!errorReported) {
        errorReported = true;
        callback(err); // first error wins — others ignored
      }
      return;
    }
    if (++completedCount === 3 && !errorReported) {
      callback(null, results); // all three done and no errors
    }
  }

  // Three requests fire simultaneously:
  fetchUser(userId, function(err, user) {
    if (err) return onComplete(err);
    results.user = user;
    onComplete(null);
  });

  fetchStats(userId, function(err, stats) {
    if (err) return onComplete(err);
    results.stats = stats;
    onComplete(null);
  });

  fetchNotifications(userId, function(err, notifications) {
    if (err) return onComplete(err);
    results.notifications = notifications;
    onComplete(null);
  });
}

// ─── PROMISE.ALL VERSION ───────────────────────────────────────────────────

function fetchDashboardPromise(userId) {
  return Promise.all([
    fetchUserAsync(userId),
    fetchStatsAsync(userId),
    fetchNotificationsAsync(userId),
  ]).then(([user, stats, notifications]) => ({ user, stats, notifications }));
}

// ─── ASYNC/AWAIT VERSION — the anti-pattern vs the correct pattern ──────────

async function fetchDashboardAsync(userId) {
  // ✗ ANTI-PATTERN: sequential (3x slower than necessary):
  const user          = await fetchUserAsync(userId);          // waits ~200ms
  const stats         = await fetchStatsAsync(userId);         // then waits ~150ms
  const notifications = await fetchNotificationsAsync(userId); // then waits ~100ms
  // Total: ~450ms

  // ✓ CORRECT: parallel — all start simultaneously:
  const [user, stats, notifications] = await Promise.all([
    fetchUserAsync(userId),
    fetchStatsAsync(userId),
    fetchNotificationsAsync(userId),
  ]);
  // Total: ~200ms (dominated by slowest, not sum of all)

  return { user, stats, notifications };
}

// ─── PARTIAL FAILURE: allSettled for graceful degradation ──────────────────

async function fetchDashboardGraceful(userId) {
  const [userResult, statsResult, notesResult] = await Promise.allSettled([
    fetchUserAsync(userId),
    fetchStatsAsync(userId),
    fetchNotificationsAsync(userId),
  ]);

  // User is critical — fail if unavailable:
  if (userResult.status === 'rejected') throw userResult.reason;

  return {
    user:          userResult.value,
    stats:         statsResult.status === 'fulfilled' ? statsResult.value : null,
    notifications: notesResult.status === 'fulfilled'  ? notesResult.value  : [],
    warnings:      [
      statsResult.status === 'rejected' ? 'Stats unavailable' : null,
      notesResult.status === 'rejected'  ? 'Notifications unavailable' : null,
    ].filter(Boolean),
  };
}
```

## Implementation 6 — Real-World: Express Middleware Chain Refactoring

### Challenge
An Express middleware chain that validates a JWT token, loads the user from the database, and checks a permission — three sequential async steps all written as callback-based middleware. Refactor to async middleware with proper error forwarding.

### Pattern
Express middleware refactoring — the callback-hell problem in a framework-specific form; shows the `asyncHandler` wrapper and proper error handling in NestJS/Express context.

### Implementation

```js
// ─── BEFORE: Callback-based middleware chain ────────────────────────────────

// Middleware 1: JWT validation
function validateToken(req, res, next) {
  jwt.verify(req.headers.authorization, process.env.JWT_SECRET, function(err, decoded) {
    if (err) return next(err);         // async error → forwarded to Express error handler
    req.tokenPayload = decoded;
    next();                            // success → call next middleware
  });
}

// Middleware 2: Load user (depends on Middleware 1's result)
function loadUser(req, res, next) {
  db.findById(req.tokenPayload.userId, function(err, user) {
    if (err) return next(err);
    if (!user) return next(new Error('User not found'));
    req.user = user;
    next();
  });
}

// Middleware 3: Check permission (depends on Middleware 2's result)
function requirePermission(permission) {
  return function(req, res, next) {
    permissionService.check(req.user.id, permission, function(err, hasPermission) {
      if (err) return next(err);
      if (!hasPermission) {
        const error = new Error(`Forbidden: requires ${permission}`);
        error.status = 403;
        return next(error);
      }
      next();
    });
  };
}

// Route handler
function getAdminData(req, res, next) {
  adminService.getData(req.user.id, function(err, data) {
    if (err) return next(err);
    res.json(data);
  });
}

app.get('/admin/data', validateToken, loadUser, requirePermission('admin:read'), getAdminData);

// ─── AFTER: async middleware with asyncHandler wrapper ─────────────────────

const asyncHandler = fn => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

// Promisified APIs:
const verifyToken    = promisify(jwt.verify);
const findUserById   = (id) => User.findById(id); // assuming Mongoose (already Promise-native)
const checkPerm      = promisify(permissionService.check);

// Middleware 1: JWT validation — async, flat, no callback
const validateTokenAsync = asyncHandler(async (req, res, next) => {
  try {
    req.tokenPayload = await verifyToken(req.headers.authorization, process.env.JWT_SECRET);
  } catch (err) {
    const error = new Error('Invalid or expired token');
    error.status = 401;
    throw error; // asyncHandler catches and forwards to next(err)
  }
  next();
});

// Middleware 2: Load user
const loadUserAsync = asyncHandler(async (req, res, next) => {
  const user = await findUserById(req.tokenPayload.userId);
  if (!user) {
    const err = Object.assign(new Error('User not found'), { status: 404 });
    throw err;
  }
  req.user = user;
  next();
});

// Middleware 3: Check permission (factory)
const requirePermissionAsync = (permission) =>
  asyncHandler(async (req, res, next) => {
    const hasPermission = await checkPerm(req.user.id, permission);
    if (!hasPermission) {
      throw Object.assign(new Error(`Forbidden: requires ${permission}`), { status: 403 });
    }
    next();
  });

// Route handler — clean, no callback
const getAdminDataAsync = asyncHandler(async (req, res) => {
  const data = await adminService.getDataAsync(req.user.id);
  res.json(data);
});

// Route registration — identical API, cleaner implementation:
app.get('/admin/data',
  validateTokenAsync,
  loadUserAsync,
  requirePermissionAsync('admin:read'),
  getAdminDataAsync
);

// Centralized error handler (added once to Express app):
app.use((err, req, res, next) => {
  const status = err.status || 500;
  res.status(status).json({
    error: { message: err.message, ...(process.env.NODE_ENV === 'development' && { stack: err.stack }) }
  });
});

// ─── NestJS equivalent (Aditya's actual stack) ─────────────────────────────
// NestJS handles all of this automatically:
// - Guards (AuthGuard, RolesGuard) replace middleware for auth/permission
// - Exception filters replace the error middleware
// - All controller methods can be async — no wrapper needed

@UseGuards(AuthGuard('jwt'), RolesGuard)
@Roles('admin:read')
@Get('admin/data')
async getAdminData(@CurrentUser() user: User): Promise<AdminDataDto> {

}
```

## Quick Reference — Refactoring Decision Tree

```
Encountering callback-based async code — what to do?
│
├── IS IT A ONE-OFF SCRIPT OR RARELY-CHANGED CODE?
│   └── Named functions refactor is sufficient.
│       Visual improvement without structural investment.
│
├── IS THE API CALLBACK-BASED (fs, db drivers, older npm packages)?
│   ├── Does Node.js have a native Promise API?
│   │   └── YES → use fs/promises, dns/promises, crypto.subtle, etc. directly.
│   ├── Does the library have a .promise() or Bluebird wrapper?
│   │   └── YES → use that.
│   └── Manual promisify needed?
│       ├── Error-first callback, single result → util.promisify(fn)
│       ├── Error-first, multiple results → manual wrap, return object
│       └── Non-standard or multi-shot → manual new Promise() per call site
│
├── ARE THE STEPS SEQUENTIAL (each depends on the previous)?
│   └── async/await with sequential awaits.
│       Each step on its own line. Single try/catch.
│
├── ARE THE STEPS PARALLEL (independent of each other)?
│   ├── All must succeed → Promise.all([op1(), op2(), op3()])
│   ├── Want all results even if some fail → Promise.allSettled([...])
│   ├── Need first success → Promise.any([...])
│   └── Need first settlement (timeout pattern) → Promise.race([...])
│
├── IS THIS AN EXPRESS ROUTE HANDLER OR MIDDLEWARE?
│   └── Wrap with asyncHandler: fn => (req,res,next) => Promise.resolve(fn(...)).catch(next)
│       Or upgrade to Express 5 / use NestJS (handles async natively).
│
├── ARE THERE NON-CRITICAL SIDE EFFECTS (email, analytics, metrics)?
│   └── Fire-and-forget: call the async function WITHOUT await.
│       Attach explicit .catch() to prevent unhandled rejection.
│       sideEffect().catch(err => logger.warn('side effect failed:', err))
│
└── IS THE CALLBACK CALLED MULTIPLE TIMES (event emitters, streams)?
    └── Do NOT promisify — convert to:
        Async generator / for await...of (for sequential consumption)
        Observable (RxJS) for reactive, composable multi-event streams
        Node.js Readable/Writable streams for I/O pipelines
```

## Common Bugs Checklist

Before refactoring or shipping async code, verify:

1. **Missing `return` before `callback(err)` in callback code?** — `if (err) callback(err)` without `return` allows execution to continue after the callback is called — the next line runs with `undefined` data. Always `if (err) return callback(err)`. Equally: in `.then()` handlers, forgetting `return` before `throw new Error()` doesn't stop execution either — `throw` does, but `callback()` without `return` does not.

2. **Synchronous throws inside callbacks not caught by the error-first convention?** — `fs.readFile(path, function(err, data) { const parsed = JSON.parse(data); ... })` — if `JSON.parse` throws, the error is not passed to the outer callback; it becomes an uncaught exception. Always wrap synchronous operations inside callbacks with `try/catch`, or eliminate callbacks by switching to `async/await` where the outer `try/catch` handles both.

3. **Parallel async operations using sequential `await`?** — `const a = await op1(); const b = await op2();` when `op1` and `op2` are independent is a performance bug — they run sequentially even though parallelism is available. Use `const [a, b] = await Promise.all([op1(), op2()])` for truly parallel execution.

4. **Async function called without `await` and without `.catch()`?** — `sendEmail(data)` (no `await`, no `.catch()`) — if `sendEmail` rejects, it becomes an unhandled rejection. For fire-and-forget operations, always attach a `.catch()`: `sendEmail(data).catch(err => logger.error(err))`.

5. **`asyncHandler` wrapper missing from Express route handlers?** — In Express 4, an unhandled rejection inside an `async` route handler does not call `next(err)` — it becomes an unhandled rejection and the response hangs. Every `async` handler in Express 4 must be wrapped or you must use Express 5.

6. **Double callback in error handling (callback called multiple times)?** — In the parallel counter pattern, if two operations fail simultaneously, the callback may be called twice without the `errorReported` guard. Always use a flag: `if (hasError) return; hasError = true; callback(err)`. Better: use `Promise.all` which handles this correctly.

7. **Closing over a loop variable with `var` inside callbacks?** — `for (var i = 0; i < 3; i++) { setTimeout(function() { console.log(i); }, 100); }` prints `3 3 3`, not `0 1 2`. The classic closure bug — `var` is function-scoped, `i` is shared. Fix: use `let` (block-scoped) or `IIFE` to capture the current value. With `async/await` and `for...of`, the loop variable is naturally scoped.

8. **Not handling the Zalgo problem when writing your own async utilities?** — If you write a function that sometimes calls its callback synchronously (cached result) and sometimes asynchronously (fresh fetch), callers cannot reliably depend on the timing. Always use `process.nextTick(() => callback(null, cached))` for the synchronous path, or return a Promise (which is always async by spec).

9. **`try/catch` not catching errors in floating async calls inside an `async` function?** — `async function foo() { try { bar(); await baz(); } catch (e) { ... } }` — if `bar()` is an async function that rejects, the rejection is NOT caught by the outer `try/catch` because `bar()` is not awaited. The `try/catch` only catches: synchronous throws, and rejections from `await`ed Promises. Floating Promises (unawaited) are invisible to `try/catch`.

10. **Promisified function losing `this` context?** — `promisify(connection.query)` — when `connection.query` is called without `connection` as `this`, it may fail with "Cannot read property of undefined." Fix: `promisify(connection.query.bind(connection))` or use an arrow function wrapper: `(sql, params) => new Promise((res, rej) => connection.query(sql, params, (e, r) => e ? rej(e) : res(r)))`.

11. **`util.promisify` on a function with multiple result arguments?** — `fs.read` has `callback(err, bytesRead, buffer)` — `promisify(fs.read)` only gives you `bytesRead`, discarding `buffer`. Use `fs.promises.read` instead, or manually promisify with `resolve({ bytesRead, buffer })`.

12. **Error subclass check in catch blocks after refactoring?** — When refactoring from callbacks to Promises, you may change `Error` types — a DB connection error was previously a raw string (old driver) but is now an `Error` object with `.code = 'ECONNREFUSED'`. Update `catch` blocks that pattern-match on error properties after promisification changes the error shape.

**Final Tip:** At the 5 YOE level, the decisive signal for callback hell refactoring is articulating **the exact trust violation** the original code has and **which guarantee the refactored version restores**. For inversion of control: *"With callbacks, I hand my continuation to the library and trust it to call my function exactly once, asynchronously, with correct arguments. With `async/await`, I hold a Promise — I decide when to observe its result, the spec guarantees it settles at most once, and `.then()` handlers are always async."* For error handling: *"Each callback level in the original repeats `if (err) return callback(err)` — if any one guard is missing, execution continues with undefined data. With `async/await` and a single `try/catch`, any throw or rejection at any step routes to the one handler — I can't accidentally skip a guard."* For parallel operations: *"The callback counter pattern requires shared mutable state, double-callback prevention, and error flag coordination — 20 lines of coordination code for a simple semantic: wait for all three. `Promise.all` is that exact semantic — one line."* Naming the defect precisely and the guarantee that fixes it, before touching a line of code, is the mark of a senior who refactors correctly rather than just differently.
