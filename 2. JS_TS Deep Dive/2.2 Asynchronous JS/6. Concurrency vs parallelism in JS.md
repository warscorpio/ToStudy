# Concurrency vs Parallelism in JavaScript — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the difference between concurrency and parallelism, and which does JavaScript natively support?**
A: Concurrency and parallelism both deal with doing multiple things at once, but they are fundamentally different:

**Concurrency** is about *dealing with* multiple tasks — managing the structure of a program so it can handle multiple things in overlapping time periods. It's about composition: tasks are in progress simultaneously, but they may not be executing at the same physical instant. One worker switches between tasks.

**Parallelism** is about *doing* multiple tasks simultaneously — executing multiple computations at the exact same instant on separate processing units. It requires actual physical separation (multiple CPU cores, multiple threads).

The analogy: concurrency is one barista taking orders, making drinks, and accepting payment — switching between tasks as each step completes. Parallelism is three baristas each working their own station simultaneously.

JavaScript in a single thread is concurrent but not parallel — it can handle thousands of in-flight operations (network requests, timers, I/O) by interleaving their progress, but only one piece of JavaScript code runs at any instant. True parallelism in JavaScript requires explicit multi-threading mechanisms: Web Workers (browser) or Worker Threads (Node.js).

**Q2. Why is JavaScript single-threaded and why was this the right design decision?**
A: JavaScript was designed by Brendan Eich in 10 days in 1995 as a scripting language to run simple interactivity on web pages — manipulating the DOM, handling button clicks. A single-threaded model was chosen for three reasons:

1. **DOM is inherently single-threaded**: if two threads could simultaneously modify the DOM, you'd need locks everywhere — every element read/write would require synchronization. Race conditions in UI code are notoriously hard to reason about and debug.

2. **Simplicity for the target use case**: web page scripts in 1995 didn't need to parallelize CPU-intensive computation — they needed to react to events (clicks, keypresses, load events). Event-driven single-threaded concurrency is simple to reason about: no shared mutable state between concurrent operations, no data races, no deadlocks.

3. **Natural fit for I/O-bound workloads**: most of what a JavaScript program does is wait for I/O — waiting for the network, waiting for the user, waiting for the file system. Single-threaded async I/O (the Node.js model) handles I/O-bound workloads as efficiently as multi-threading, without synchronization overhead.

The tradeoff: JavaScript's single thread becomes a bottleneck for CPU-intensive computation (image processing, video encoding, cryptography, ML inference). This is precisely the gap Web Workers and Worker Threads fill.

## Section 2: The Event Loop

**Q3. What is the event loop and what problem does it solve?**
A: The event loop is the mechanism that enables JavaScript's single thread to handle concurrency — to have thousands of in-progress operations without blocking. Without it, a single `fetch()` call waiting for a network response would freeze the entire browser tab for the duration of the request.

The event loop solves this by separating *initiating* an operation from *handling its result*. When you call `setTimeout(fn, 1000)`, JavaScript registers the callback with a timer system (outside of JavaScript — in the browser's C++ runtime or Node.js's libuv), then immediately returns. The current JavaScript code continues running. When the timer fires, the runtime places `fn` in a queue. The event loop picks it up when the call stack is empty.

The event loop's job in pseudocode:
```
while (true) {
    // 1. Execute all synchronous code until the call stack is empty
    runCurrentTask()

    // 2. Process ALL microtasks (until microtask queue is empty)
    while (microtaskQueue.isNotEmpty()) {
        runMicrotask(microtaskQueue.dequeue())
    }

    // 3. If a render is needed (browser only): run rendering steps
    renderIfNeeded()

    // 4. Pick ONE task from the macrotask queue (if any)
    if (macrotaskQueue.isNotEmpty()) {
        runTask(macrotaskQueue.dequeue())
        // Then go back to step 2 (drain microtasks after each macrotask)
    }
}
```

**Q4. What is the call stack, and what happens when it overflows?**
A: The call stack is a LIFO (Last In, First Out) data structure that tracks the currently executing function calls. When a function is called, a stack frame is pushed (containing the function's local variables and return address). When the function returns, its frame is popped.

```javascript
function c() { console.log('c'); }        // pushed third, popped first
function b() { c(); }                     // pushed second
function a() { b(); }                     // pushed first
a();
// Stack at deepest point: [a → b → c]
// Unwinds: c returns → b returns → a returns → stack empty
```

Stack overflow — infinite recursion exceeds the maximum stack depth (typically ~10,000-15,000 frames in V8):
```javascript
function recurse() { recurse(); }
recurse();  // RangeError: Maximum call stack size exceeded

// Fix with tail call optimization (TCO) — only in strict mode in V8,
// and only when the recursive call is the last operation:
function recurse(n = 0) {
    if (n > 100000) return n;
    return recurse(n + 1);  // tail position — TCO applies (theory vs practice)
}
// In practice: TCO in V8 is limited; use iterative approaches for deep recursion
```

The call stack being empty is the event loop's signal to process the next macrotask. An infinitely-running synchronous function blocks the event loop forever — no callbacks fire, no UI updates happen, the browser tab appears frozen ("unresponsive script" warning).

**Q5. What are the two types of task queues, and what is the crucial difference between macrotasks and microtasks?**
A: JavaScript has two distinct queues with radically different priority:

**Macrotask queue** (also called "task queue" or "callback queue"): contains callbacks from I/O events, timers (`setTimeout`, `setInterval`), `setImmediate` (Node.js), UI events (click, load), `MessageChannel`. The event loop processes **exactly ONE** macrotask per iteration before checking microtasks.

**Microtask queue** (also called "job queue"): contains callbacks from `Promise.then/catch/finally`, `queueMicrotask()`, `MutationObserver` callbacks, `async/await` continuations (each `await` resumes as a microtask). The event loop processes **ALL** microtasks before moving to the next macrotask — it completely drains the queue, including any new microtasks added while processing:

```javascript
console.log('1 - synchronous start');

setTimeout(() => console.log('5 - macrotask (setTimeout)'), 0);

Promise.resolve()
    .then(() => console.log('3 - microtask (Promise.then 1)'))
    .then(() => console.log('4 - microtask (Promise.then 2, chained'));

queueMicrotask(() => console.log('3.5 - microtask (queueMicrotask)'));

console.log('2 - synchronous end');

// Output order:
// 1 - synchronous start
// 2 - synchronous end
// 3 - microtask (Promise.then 1)
// 3.5 - microtask (queueMicrotask)
// 4 - microtask (Promise.then 2, chained)
// 5 - macrotask (setTimeout)
```

The critical rule: **after every macrotask (and after the initial synchronous code), ALL microtasks are processed before the next macrotask begins**. Microtasks have higher priority than macrotasks.

**Q6. What is the practical implication of microtasks being fully drained before the next macrotask? What can go wrong?**
A: The draining behavior means: if microtasks keep generating new microtasks, the event loop never proceeds to the next macrotask — starving UI rendering, timer callbacks, and I/O events:

```javascript
// Infinite microtask loop — starves the event loop:
function infiniteMicrotasks() {
    Promise.resolve().then(infiniteMicrotasks);  // queues itself as a microtask
}
infiniteMicrotasks();
// The microtask queue is never empty — setTimeout callbacks never fire,
// UI never renders, the tab appears frozen.

// Compare with infinite macrotask loop:
function infiniteMacrotasks() {
    setTimeout(infiniteMacrotasks, 0);  // queues itself as a macrotask
}
infiniteMacrotasks();
// Each iteration gets ONE shot before UI can render — tab stays responsive
// (though setTimeout with 0 will be clamped to 4ms minimum in browsers)

// Practical concern: deep Promise chain with synchronous-like data:
function processLargeArray(arr) {
    return arr.reduce(
        (promise, item) => promise.then(() => processItem(item)),
        Promise.resolve()
    );
}
// If arr has 100,000 elements, this creates 100,000 chained .then() calls
// running as microtasks — no macrotask, UI update, or I/O callback fires
// until all 100,000 items are processed.
// Fix: break into chunks with setTimeout(nextChunk, 0) to yield between chunks
```

## Section 3: Async/Await and Concurrency

**Q7. How does `async/await` interact with the event loop, and what does "suspending a function" mean mechanically?**
A: `async/await` is syntactic sugar over Promises. Each `await` suspends the current `async` function (pops its frame off the call stack, allowing other code to run) and schedules its continuation as a microtask when the awaited value resolves:

```javascript
async function fetchUser(id) {
    console.log('A: before await');           // synchronous
    const user = await getUser(id);           // SUSPENDS here
    console.log('B: after await', user.name); // resumes as microtask
    return user;
}

console.log('1: before call');
const promise = fetchUser(42);               // starts executing synchronously
console.log('2: after call');               // runs BEFORE 'B' because fetchUser suspended

// Output:
// 1: before call
// A: before await     ← synchronous part of fetchUser runs immediately
// 2: after call       ← control returns to caller when fetchUser hits await
// B: after await Alice ← microtask when getUser(42) resolves
```

Mechanically: `await expr` is equivalent to:
```javascript
return expr.then(value => {
    // continuation of the async function after the await
});
```

Each `await` creates a new `.then()` callback — a microtask. This means the code after each `await` runs in a separate microtask checkpoint, not synchronously after the await expression. The suspension allows the event loop to process other pending work (other microtasks, then macrotasks) between each `await`.

**Q8. What is the difference between sequential and concurrent async operations, and how do you write each?**
A: A critical distinction that directly affects application performance:

```javascript
// SEQUENTIAL: each await waits for the previous to complete
// Total time = time(getUser) + time(getProfile) + time(getOrders) ≈ 3 × 100ms = 300ms
async function loadUserDataSequential(userId) {
    const user = await getUser(userId);        // 100ms
    const profile = await getProfile(userId);  // 100ms (starts after getUser completes)
    const orders = await getOrders(userId);    // 100ms (starts after getProfile completes)
    return { user, profile, orders };
}

// CONCURRENT: all three start immediately, await their completion
// Total time = max(time(getUser), time(getProfile), time(getOrders)) ≈ 100ms
async function loadUserDataConcurrent(userId) {
    const [user, profile, orders] = await Promise.all([
        getUser(userId),        // starts immediately
        getProfile(userId),     // starts immediately (same tick as getUser)
        getOrders(userId)       // starts immediately
    ]);
    return { user, profile, orders };
}
```

The sequential version is the most common performance mistake in async JavaScript: `await`ing each promise serially when the operations are independent. Always ask: "do these operations depend on each other's results?" If not, run them concurrently.

```javascript
// Common mistake: sequential when concurrent is possible
async function getDashboard(userId) {
    // BAD: each waits for the previous — 3× the latency of the slowest
    const user = await db.getUser(userId);
    const stats = await analytics.getStats(userId);
    const notifications = await notifier.getUnread(userId);

    // GOOD: concurrent — latency = max(user, stats, notifications)
    const [user, stats, notifications] = await Promise.all([
        db.getUser(userId),
        analytics.getStats(userId),
        notifier.getUnread(userId)
    ]);
}
```

**Q9. What is the difference between `Promise.all`, `Promise.allSettled`, `Promise.race`, and `Promise.any`?**
A: The four static combinators for concurrent Promise execution, each with different failure semantics:

```javascript
// Promise.all — succeeds when ALL succeed; fails fast on first rejection
const results = await Promise.all([p1, p2, p3]);
// If p2 rejects: immediately rejects with p2's error — p1, p3 continue running
// but their results are discarded. Use when: ALL must succeed to proceed.

// Promise.allSettled — waits for ALL to settle (resolve or reject), never rejects
const results = await Promise.allSettled([p1, p2, p3]);
// results = [
//   { status: 'fulfilled', value: v1 },
//   { status: 'rejected', reason: e2 },
//   { status: 'fulfilled', value: v3 }
// ]
// Use when: you need ALL results regardless of failure (send N emails, log each outcome)

// Promise.race — settles with the FIRST to settle (resolve OR reject)
const result = await Promise.race([p1, p2, p3]);
// If p2 resolves first: result = p2's value. Other promises continue but are ignored.
// If p2 rejects first: race rejects with p2's reason.
// Classic use: timeout wrapper
const withTimeout = (promise, ms) => Promise.race([
    promise,
    new Promise((_, reject) => setTimeout(() => reject(new Error('Timeout')), ms))
]);

// Promise.any — succeeds with the FIRST to RESOLVE; rejects only if ALL reject
const result = await Promise.any([p1, p2, p3]);
// If p1 rejects, p2 resolves: result = p2's value (ignores p1's rejection)
// If all reject: AggregateError containing all rejection reasons
// Use when: trying multiple sources and any success is acceptable
//           (e.g., try multiple CDN mirrors, use whichever responds first)
```

**Q10. What is the "async iteration" pattern with `for await...of` and when is it used?**
A: `for await...of` iterates over an async iterable — a source that produces values asynchronously, one at a time. Each iteration `await`s the next value before proceeding:

```javascript
// Async generator — produces values asynchronously
async function* paginatedUsers(pageSize = 100) {
    let cursor = null;
    while (true) {
        const { users, nextCursor } = await db.getUsers({ cursor, pageSize });
        yield* users;                     // yield each user
        if (!nextCursor) break;           // no more pages
        cursor = nextCursor;
    }
}

// Consumer — processes each user as it arrives, one page at a time
async function processAllUsers() {
    for await (const user of paginatedUsers(100)) {
        await processUser(user);          // process one user at a time
    }
}

// Node.js streams are async iterables:
import { createReadStream } from 'fs';
async function readFile() {
    const stream = createReadStream('./large-file.txt', { encoding: 'utf8' });
    for await (const chunk of stream) {
        process(chunk);  // processes each chunk as it arrives from disk
    }
}

// Kafka consumer (conceptual):
async function consumeMessages() {
    for await (const message of kafkaConsumer) {
        await handleMessage(message);
        await kafkaConsumer.commit();
    }
}
```

`for await...of` is appropriate when: values are produced one-at-a-time (pagination, streaming), memory constraints prevent loading all values at once, or you want backpressure (the next value is only fetched after the current one is processed).

## Section 4: The Event Loop in Node.js

**Q11. How does Node.js's event loop differ from the browser's, and what are its distinct phases?**
A: Node.js uses libuv for its event loop, which has a more structured, multi-phase model compared to the browser's simpler two-queue model. Node.js's event loop has six phases, executed in order:

```
┌─────────────────────────────────────────────┐
│               Node.js Event Loop            │
│                                             │
│  ┌──────────┐   ┌──────────┐               │
│  │  timers  │ → │ pending  │               │
│  │ (setTimeout│   │ callbacks│               │
│  │ setInterval)│  │ (I/O err)│               │
│  └──────────┘   └──────────┘               │
│        │                │                  │
│  ┌──────────┐   ┌──────────┐               │
│  │  idle,   │   │  poll    │               │
│  │  prepare │   │ (I/O)    │               │
│  └──────────┘   └──────────┘               │
│        │                │                  │
│  ┌──────────┐   ┌──────────┐               │
│  │  check   │ ← │  close   │               │
│  │(setImmed)│   │ callbacks│               │
│  └──────────┘   └──────────┘               │
│                                             │
│  Between EACH phase: drain microtask queue  │
│  (nextTick first, then Promises)            │
└─────────────────────────────────────────────┘
```

**Phase 1 — Timers**: executes `setTimeout` and `setInterval` callbacks whose threshold has elapsed.

**Phase 2 — Pending callbacks**: I/O callbacks from previous iteration that were deferred (e.g., some TCP errors).

**Phase 3/4 — Idle, Prepare**: internal libuv use.

**Phase 5 — Poll**: retrieves new I/O events and executes their callbacks. If no timers are pending, Node.js waits here for new I/O events (blocking the event loop until one arrives or a timer is ready). This is the phase where most application I/O callbacks run (file reads, network responses).

**Phase 6 — Check**: `setImmediate` callbacks execute here (after poll, before next timer phase).

**Phase 7 — Close callbacks**: `close` events (e.g., `socket.on('close', ...)`, `process.on('exit', ...)`).

**Between each phase**: Node.js drains the microtask queue — first all `process.nextTick` callbacks, then all Promise microtasks (`.then`, `async/await` continuations).

**Q12. What is `process.nextTick()` and how is it different from `Promise.resolve().then()`?**
A: Both are microtasks that run before the next macrotask/event loop phase, but `process.nextTick()` runs *before* Promise microtasks — it has the highest priority in Node.js's microtask processing:

```javascript
setImmediate(() => console.log('5 - setImmediate (check phase)'));

setTimeout(() => console.log('6 - setTimeout (timers phase)'), 0);

Promise.resolve().then(() => console.log('3 - Promise.then (microtask)'));

process.nextTick(() => console.log('2 - nextTick (highest priority microtask)'));

console.log('1 - synchronous');

queueMicrotask(() => console.log('4 - queueMicrotask'));

// Output:
// 1 - synchronous
// 2 - nextTick          ← nextTick runs before Promise microtasks
// 3 - Promise.then      ← Promise microtasks run after nextTick queue drains
// 4 - queueMicrotask    ← same queue as Promise
// 5 - setImmediate      ← macrotask (check phase)
// 6 - setTimeout        ← macrotask (timers phase)
```

Node.js processes nextTick callbacks as a separate queue that is fully drained *before* the Promise microtask queue. Both are processed between event loop phases.

**When to use `process.nextTick()`**: when you need a callback to run before any I/O in the current event loop iteration but after the current synchronous code. Common use: making an API consistent that is sometimes synchronous and sometimes asynchronous:

```javascript
// ANTI-PATTERN: inconsistent async — sometimes synchronous, sometimes not
function readData(key, callback) {
    if (cache.has(key)) {
        callback(null, cache.get(key));  // synchronous! — breaks callers expecting async
    } else {
        fs.readFile(key, (err, data) => callback(err, data));  // async
    }
}

// FIX: always async with nextTick
function readData(key, callback) {
    if (cache.has(key)) {
        process.nextTick(() => callback(null, cache.get(key)));  // deferred, but before I/O
    } else {
        fs.readFile(key, (err, data) => callback(err, data));
    }
}
```

**Q13. What is the difference between `setImmediate` and `setTimeout(fn, 0)` in Node.js?**
A: Both schedule a callback to run "soon" but in different phases, and their relative order is non-deterministic when called from the main module but deterministic inside I/O callbacks:

```javascript
// Called from the main module (outside any callback):
setTimeout(() => console.log('setTimeout'), 0);
setImmediate(() => console.log('setImmediate'));
// Order is NON-DETERMINISTIC — depends on when the event loop starts
// and OS timer precision. Could be either order.

// Called from within an I/O callback:
fs.readFile('file.txt', () => {
    setTimeout(() => console.log('setTimeout'), 0);    // always second
    setImmediate(() => console.log('setImmediate'));    // always first
});
// setImmediate is ALWAYS first here because:
// The readFile callback runs in the poll phase.
// After poll: check phase (setImmediate) runs before next timers phase (setTimeout).
```

Rule of thumb: inside I/O callbacks, `setImmediate` runs before `setTimeout(fn, 0)`. In the main module entry point, the order is unpredictable. Prefer `setImmediate` when you want "run after current I/O, before next timer" semantics; use `Promise.resolve().then()` or `queueMicrotask()` when you want "run before any I/O."

## Section 5: True Parallelism with Workers

**Q14. What are Web Workers (browser) and Worker Threads (Node.js), and what problem do they solve?**
A: Workers provide true parallelism in JavaScript by running code on separate OS threads. Each worker has its own JavaScript engine, own event loop, own memory — completely isolated from the main thread. They solve the one problem the event loop can't: CPU-intensive computation that would block the main thread for a noticeable duration.

```javascript
// Browser: Web Worker
// main.js
const worker = new Worker('./heavy-computation.js');

worker.postMessage({ type: 'COMPUTE', data: largeArray });

worker.onmessage = (event) => {
    console.log('Result:', event.data.result);  // result arrived from worker thread
};

// heavy-computation.js (runs in separate thread — no DOM access)
self.onmessage = (event) => {
    if (event.data.type === 'COMPUTE') {
        const result = expensiveSortAlgorithm(event.data.data);
        self.postMessage({ result });  // send result back to main thread
    }
};

// Node.js: Worker Threads
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

if (isMainThread) {
    // Main thread: create worker
    const worker = new Worker('./worker.mjs', {
        workerData: { array: largeArray }
    });
    worker.on('message', (result) => console.log('Result:', result));
    worker.on('error', (err) => console.error('Worker error:', err));
} else {
    // Worker thread: execute computation
    const result = heavyComputation(workerData.array);
    parentPort.postMessage(result);
}
```

**Q15. How do workers communicate with the main thread, and what is the structured clone algorithm?**
A: Workers communicate exclusively through message passing — `postMessage()` to send, `onmessage` / `message` event to receive. There is no shared memory by default. Data passed via `postMessage` is **deep-copied** using the structured clone algorithm:

```javascript
// Structured clone: deep copies most values
worker.postMessage({
    number: 42,          // cloned
    string: 'hello',     // cloned
    array: [1, 2, 3],    // deep cloned (new array, new contents)
    object: { x: 1 },   // deep cloned (new object)
    date: new Date(),    // cloned as Date
    map: new Map(),      // cloned (ES6 Maps and Sets are supported)
    buffer: buffer,      // ArrayBuffer TRANSFERRED (see below, not cloned)
});

// What CAN'T be structured-cloned (throw DataCloneError):
worker.postMessage(() => {});     // Functions — not cloneable
worker.postMessage(document.body); // DOM nodes — main thread only
worker.postMessage(new Error());  // Error objects — cloneable but lose stack

// Transferable objects — MOVED (not copied), zero-copy:
const buffer = new ArrayBuffer(1024 * 1024 * 100);  // 100MB
worker.postMessage({ buffer }, [buffer]);  // Transfer ownership
// After postMessage: buffer in main thread is detached (byteLength = 0)
// buffer is now in the worker — no 100MB copy made
// Use for: large binary data (images, audio, video frames)
```

The structured clone algorithm is deeper than `JSON.stringify/parse` (handles circular references, Date objects, Map, Set, TypedArray) but still has limits (no functions, no Proxy objects, no DOM nodes).

**Q16. What is a `SharedArrayBuffer` and when should you use it over message passing?**
A: `SharedArrayBuffer` is a fixed-size binary buffer that is literally shared — the same physical memory is accessible from both the main thread and workers simultaneously, with no copying:

```javascript
// Main thread: create a shared buffer
const sharedBuffer = new SharedArrayBuffer(4 * Int32Array.BYTES_PER_ELEMENT);
const sharedArray = new Int32Array(sharedBuffer);
sharedArray[0] = 100;  // write initial value

// Send the buffer to workers (zero-copy — same physical memory)
const worker = new Worker('./worker.js');
worker.postMessage({ sharedBuffer });  // SharedArrayBuffer is shared, not cloned

// Worker:
// worker.js
self.onmessage = (event) => {
    const sharedArray = new Int32Array(event.data.sharedBuffer);
    sharedArray[0]++;  // modifies the SAME memory the main thread reads
    self.postMessage('done');
};

// Main thread after worker signals completion:
worker.onmessage = () => {
    console.log(sharedArray[0]);  // 101 — modified by worker in place
};
```

**The need for `Atomics`**: because both threads access the same memory, concurrent writes create race conditions. `Atomics` provides thread-safe operations:

```javascript
// UNSAFE: two workers both do sharedArray[0]++ simultaneously
// Read-modify-write is not atomic — both may read 100, both write 101 → lost update

// SAFE: Atomics.add is atomic (happens in one uninterruptible operation)
Atomics.add(sharedArray, 0, 1);   // atomically: sharedArray[0] += 1

// Atomics.wait / Atomics.notify: mutex-like coordination
// In worker: Atomics.wait(sharedArray, 0, expectedValue)  // block until value changes
// In main thread: Atomics.notify(sharedArray, 0, 1)       // wake one waiting worker
```

Use `SharedArrayBuffer` + `Atomics` when: you need high-frequency, low-latency communication between workers (copying would be too slow), or when sharing a large dataset that multiple workers read (avoiding copying 1GB to 8 workers separately).

**Note**: `SharedArrayBuffer` requires cross-origin isolation headers (`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`) in browsers, due to Spectre vulnerability mitigations.

## Section 6: Concurrency Patterns

**Q17. What is the "async queue with concurrency limit" pattern and why is it necessary?**
A: `Promise.all()` runs all operations concurrently with no limit — fine for 3-10 operations, but launching 10,000 concurrent HTTP requests will overwhelm servers, exhaust connection pools, and potentially crash your process. Controlled concurrency limits the maximum number of in-flight operations:

```javascript
// Process an array with at most `concurrency` operations running simultaneously
async function asyncPool(concurrency, items, asyncFn) {
    const executing = new Set();
    const results = [];

    for (const [index, item] of items.entries()) {
        // Start the async operation
        const promise = asyncFn(item).then(result => {
            executing.delete(promise);
            return result;
        });
        executing.add(promise);
        results.push(promise);

        // If at concurrency limit, wait for one to complete before continuing
        if (executing.size >= concurrency) {
            await Promise.race(executing);
        }
    }

    return Promise.all(results);
}

// Usage: process 1000 URLs, max 5 simultaneous HTTP requests
const results = await asyncPool(5, urls, async (url) => {
    const response = await fetch(url);
    return response.json();
});
```

This pattern: maintains a "pool" of in-flight operations, adds a new one when one completes, and blocks when the pool is full. It's the correct approach for: bulk file processing, rate-limited API calls, database operations with a connection pool limit, or any batch job where unbounded concurrency causes resource exhaustion.

**Q18. What is the async mutex / lock pattern for preventing concurrent modification of shared state?**
A: Even in single-threaded JavaScript, async operations create race conditions in stateful code — if two async operations read-modify-write the same state with `await` in between, the state can be corrupted:

```javascript
// RACE CONDITION: two concurrent calls interleave during await
let balance = 100;

async function withdraw(amount) {
    const current = await db.getBalance();  // ← await here — suspends
    // Another withdraw() can run between this await and the next one
    if (current >= amount) {
        await db.setBalance(current - amount);  // operates on stale `current`
    }
}

// Concurrent calls:
// withdraw(60) reads 100, suspends...
// withdraw(60) reads 100, suspends... (both saw balance as 100!)
// withdraw(60) writes 40
// withdraw(60) writes 40 (instead of -20 which should have been rejected)
// Result: 40 instead of the correct behavior (second withdrawal rejected)

// FIX: async mutex ensures sequential execution
class AsyncMutex {
    constructor() { this._queue = Promise.resolve(); }
    lock(fn) {
        const next = this._queue.then(fn);
        this._queue = next.catch(() => {});  // prevent unhandled rejection from blocking
        return next;
    }
}

const mutex = new AsyncMutex();

async function safeWithdraw(amount) {
    return mutex.lock(async () => {
        const current = await db.getBalance();
        if (current < amount) throw new Error('Insufficient funds');
        await db.setBalance(current - amount);
    });
}
// Now concurrent calls are serialized: second call waits for first to complete
```

The mutex works by chaining promises on `this._queue`: each call to `lock()` receives a promise that resolves only after the previous lock's `fn` completes. This creates a single-entry queue without any actual OS-level locking.

## Section 7: Edge Cases and Gotchas

**Q19. What is "Promise hell" and how does it differ from "callback hell"?**
A: Callback hell is deeply nested callbacks:
```javascript
// Callback hell
getData(function(a) {
    getMoreData(a, function(b) {
        getMoreData(b, function(c) {
            getMoreData(c, function(d) {
                console.log(d);
            });
        });
    });
});
```

Promise hell is similar nesting but with Promises and then-chains that still become deeply nested when operations depend on previous results:
```javascript
// Promise hell (still nested, still hard to read)
getData()
    .then(a => {
        return getMoreData(a)
            .then(b => {
                return getMoreData(b)
                    .then(c => {
                        return getMoreData(c).then(d => console.log(d));
                    });
            });
    });

// The solution: flatten with async/await
async function fetchAll() {
    const a = await getData();
    const b = await getMoreData(a);
    const c = await getMoreData(b);
    const d = await getMoreData(c);
    console.log(d);
}
```

But `async/await` introduces its own anti-pattern — sequential `await` when operations are independent (Q8). The discipline: use `async/await` for sequential operations, `Promise.all()` for concurrent independent ones, and async generators (`for await`) for streaming values.

**Q20. What is an "unhandled Promise rejection" and how does it lead to silent failures?**
A: Promises that reject without a `.catch()` handler or a rejected `await` in a non-try/catch context create unhandled rejections. In older Node.js versions, these were silently ignored — a major source of bugs where errors disappeared completely:

```javascript
// DANGEROUS: rejection silently disappears
async function processOrder(id) {
    const order = await db.getOrder(id);   // throws if id doesn't exist
    await chargeCustomer(order);            // throws if charge fails
    await notifyCustomer(order);
}

// Calling without handling the returned promise:
processOrder(999);  // Promise rejects, nobody catches it → silent failure
// In Node.js 15+: process crashes with UnhandledPromiseRejection
// In Node.js < 15: silent swallowing (unless --unhandled-rejections=throw)

// ALSO DANGEROUS: async function inside a non-async context
setTimeout(async () => {
    await riskyOperation();  // if this throws, the rejection is unhandled
}, 1000);

// FIX: always handle rejections at the call site
processOrder(999).catch(err => {
    logger.error('Order processing failed:', err);
    alertOps(err);
});

// Or wrap with explicit error handling:
async function safeProcessOrder(id) {
    try {
        await processOrder(id);
    } catch (err) {
        logger.error('Failed:', err);
    }
}

// Node.js: global handler for unhandled rejections (safety net, not primary handler)
process.on('unhandledRejection', (reason, promise) => {
    logger.error('Unhandled rejection:', reason);
    process.exit(1);  // fail fast
});
```

**Q21. What is the event loop lag problem and how do you measure and mitigate it?**
A: Event loop lag (also called "event loop blocking" or "tick time") is the delay between when a callback is scheduled and when it actually runs. In a healthy event loop, this should be < 1ms. Large synchronous operations block all callbacks:

```javascript
// Measuring event loop lag in Node.js:
function measureEventLoopLag() {
    const start = process.hrtime.bigint();
    setImmediate(() => {
        const lag = Number(process.hrtime.bigint() - start) / 1_000_000;  // ms
        console.log(`Event loop lag: ${lag}ms`);
        // Healthy: < 10ms. Warning: 10-100ms. Critical: > 100ms.
        measureEventLoopLag();  // continuous measurement
    });
}

// Common blocking operations that cause lag:
// 1. Synchronous file operations in the hot path
fs.readFileSync('./large-file.txt');  // blocks for duration of read

// 2. CPU-intensive synchronous computation
function findPrimes(max) {
    // Sieve of Eratosthenes on a large range — takes 500ms+
    const sieve = new Uint8Array(max);
    for (let i = 2; i < max; i++) { ... }
}
findPrimes(10_000_000);  // blocks for 500ms — nothing else can run

// 3. Large JSON parsing
JSON.parse(jsonString);  // 100MB JSON takes ~1 second

// MITIGATIONS:
// a) Offload to a Worker Thread (Q14)
// b) Break into chunks with setImmediate between chunks:
async function chunkProcess(array, chunkSize = 1000) {
    for (let i = 0; i < array.length; i += chunkSize) {
        const chunk = array.slice(i, i + chunkSize);
        processChunk(chunk);
        await new Promise(resolve => setImmediate(resolve));  // yield to event loop
    }
}
```

## Section 8: Scenario-Based Questions

**Q22. "What does this output and why?"**

```javascript
async function first() {
    console.log('B');
    await Promise.resolve();
    console.log('D');
    await Promise.resolve();
    console.log('F');
}

console.log('A');
first();
console.log('C');
Promise.resolve().then(() => console.log('E'));
```

A: Tracing through execution:

1. `console.log('A')` — synchronous → **A**
2. `first()` is called — enters the async function synchronously
3. `console.log('B')` — synchronous within `first()` → **B**
4. `await Promise.resolve()` — suspends `first()`, schedules its continuation as microtask #1. Returns to caller.
5. `console.log('C')` — synchronous, back in main code → **C**
6. `Promise.resolve().then(() => console.log('E'))` — schedules microtask #2
7. Synchronous code complete. Event loop drains microtask queue:
8. Microtask #1 (continuation of `first()` after first `await`): `console.log('D')` → **D**
9. `await Promise.resolve()` — suspends again, schedules continuation as microtask #3
10. Microtask #2: `console.log('E')` → **E**
11. Microtask #3 (continuation of `first()` after second `await`): `console.log('F')` → **F**

**Output: A B C D E F**

Key insight: each `await Promise.resolve()` creates exactly ONE microtask checkpoint, allowing other microtasks to run between each pair of `await`s in `first()`. The Promise.resolve().then() callback for E runs between the two `await`s in `first()`.

**Q23. "Design a rate limiter that allows N operations per second using JavaScript's concurrency model."**
A: A token bucket rate limiter using async/await and the event loop:

```javascript
class RateLimiter {
    constructor(maxPerSecond) {
        this.maxPerSecond = maxPerSecond;
        this.tokens = maxPerSecond;         // start with full bucket
        this.lastRefill = Date.now();
        this.queue = [];                    // waiting callers
        this._refill();
    }

    _refill() {
        setInterval(() => {
            const now = Date.now();
            this.tokens = this.maxPerSecond;  // refill to max every second
            this.lastRefill = now;
            this._flush();
        }, 1000);
    }

    _flush() {
        // Release waiting callers up to available token count
        while (this.queue.length > 0 && this.tokens > 0) {
            const resolve = this.queue.shift();
            this.tokens--;
            resolve();
        }
    }

    async acquire() {
        if (this.tokens > 0) {
            this.tokens--;
            return;  // immediately available
        }
        // No tokens: wait in queue until refill
        await new Promise(resolve => this.queue.push(resolve));
    }
}

// Usage:
const limiter = new RateLimiter(10);  // 10 operations per second

async function makeApiCall(url) {
    await limiter.acquire();          // waits if rate limit is hit
    return fetch(url);
}

// 100 concurrent calls, all will be rate-limited to 10/second:
await Promise.all(urls.map(url => makeApiCall(url)));
```

This uses JavaScript's single-threaded concurrency model correctly: the `queue` is an array of resolve functions from pending Promises. No mutex is needed (no shared state mutation between `await` points within the critical section). The `_flush` runs synchronously during `setInterval` and processes waiting callers before any of them can re-interleave.

**Q24. "You have a CPU-intensive image processing function that takes 500ms to run. How would you integrate it into a Node.js web server without degrading response times for other requests?"**
A: A 500ms synchronous function in a Node.js request handler blocks the event loop — all other requests wait 500ms before any of them can respond. The solution is Worker Threads:

```javascript
// image-processor.worker.mjs
import { parentPort, workerData } from 'worker_threads';
import { processImage } from './image-processing.js';

// This runs in a separate thread — blocking here doesn't affect main thread
const result = processImage(workerData.imageBuffer);
parentPort.postMessage(result, [result.buffer]);  // transfer ownership (zero-copy)

// worker-pool.mjs — reuse workers across requests
import { Worker } from 'worker_threads';
import { cpus } from 'os';

class WorkerPool {
    constructor(workerScript, size = cpus().length) {
        this.workers = Array.from({ length: size }, () => ({
            worker: new Worker(workerScript),
            idle: true
        }));
        this.queue = [];
    }

    run(data, transferList = []) {
        return new Promise((resolve, reject) => {
            const idleWorker = this.workers.find(w => w.idle);
            if (idleWorker) {
                this._dispatch(idleWorker, data, transferList, resolve, reject);
            } else {
                this.queue.push({ data, transferList, resolve, reject });
            }
        });
    }

    _dispatch(workerEntry, data, transferList, resolve, reject) {
        workerEntry.idle = false;
        const { worker } = workerEntry;

        worker.once('message', result => {
            resolve(result);
            workerEntry.idle = true;
            if (this.queue.length > 0) {
                const next = this.queue.shift();
                this._dispatch(workerEntry, next.data, next.transferList, next.resolve, next.reject);
            }
        });
        worker.once('error', err => {
            reject(err);
            workerEntry.idle = true;
        });
        worker.postMessage(data, transferList);
    }
}

// server.mjs
import express from 'express';
const app = express();
const pool = new WorkerPool('./image-processor.worker.mjs');

app.post('/process-image', async (req, res) => {
    try {
        // Dispatch to worker thread — this request's handler suspends
        // but the event loop continues serving other requests
        const result = await pool.run(req.body.imageBuffer);
        res.json({ success: true, result });
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});
```

Key design decisions: (1) a **worker pool** matching CPU count avoids over-subscribing CPU with too many threads — `cpus().length` workers means maximum throughput without thrashing; (2) **transferring** the ArrayBuffer (not copying) makes the handoff zero-cost for large images; (3) the **queue** handles more requests than workers — requests wait in the queue rather than spawning unlimited workers.
