# JavaScript: `setTimeout`, `setInterval`, `setImmediate`, `process.nextTick` — Execution Order — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: The Event Loop Foundation

**Q1. What is the event loop, and why does it exist?**
A: JavaScript is single-threaded — only one piece of code executes at a time. The event loop is the runtime mechanism that enables asynchronous behavior on this single thread. It sits in an infinite loop watching two things: the call stack (currently executing code) and a set of queues holding callbacks ready to run. When the call stack is empty, the event loop picks the next callback from the appropriate queue and pushes it onto the stack.

The event loop exists because I/O operations (network, disk, timers) are inherently slow — if JavaScript blocked the thread waiting for them, the entire program would freeze. Instead, the runtime hands the I/O work to the OS or a thread pool, registers a callback, and keeps the main thread free to handle other events. When the I/O completes, the callback is queued and the event loop delivers it to the call stack when the stack is idle.

**Q2. What are the different queues in the Node.js event loop, and in what order are they processed?**
A: Node.js uses `libuv` for its event loop, which has multiple phases. Each phase has its own queue. The phases execute in this order per loop tick:

```
   ┌──────────────────────────────────┐
   │           timers                 │  ← setTimeout, setInterval callbacks
   │  (callbacks scheduled >= their  │
   │   threshold time)               │
   └──────────────┬───────────────────┘
                  │
   ┌──────────────▼───────────────────┐
   │       pending callbacks          │  ← I/O errors deferred from prev tick
   └──────────────┬───────────────────┘
                  │
   ┌──────────────▼───────────────────┐
   │           idle, prepare          │  ← internal use only
   └──────────────┬───────────────────┘
                  │
   ┌──────────────▼───────────────────┐
   │             poll                 │  ← retrieve new I/O events; execute I/O
   │                                  │    callbacks (excluding timers, setImmediate)
   └──────────────┬───────────────────┘
                  │
   ┌──────────────▼───────────────────┐
   │             check                │  ← setImmediate callbacks
   └──────────────┬───────────────────┘
                  │
   ┌──────────────▼───────────────────┐
   │         close callbacks          │  ← socket.on('close', ...) etc.
   └──────────────┬───────────────────┘
                  │
        (back to timers for next tick)
```

**Between every phase** — including between individual callbacks within a phase — Node.js processes two special queues:
1. **`process.nextTick` queue** (not technically a libuv phase)
2. **Promise microtask queue** (`then`/`catch`/`finally` callbacks)

These two queues are drained completely before the event loop advances to the next phase or picks the next callback from the current phase.

**Q3. What is the microtask queue, and how does it differ from the macrotask queue?**
A: The terminology "microtask" and "macrotask" comes from the HTML spec (browser event loop) and is widely used to describe the Node.js queues too:

- **Microtasks**: callbacks that run immediately after the current operation completes, before the event loop advances. In Node.js: `process.nextTick` callbacks and Promise `.then/.catch/.finally` callbacks. Microtasks are always fully drained before the event loop moves on.

- **Macrotasks** (or tasks): callbacks scheduled for a future event loop iteration. In Node.js: timer callbacks (`setTimeout`, `setInterval`), I/O callbacks, `setImmediate` callbacks. Only one macrotask is picked per event loop phase iteration; then microtasks are checked again.

The critical rule: **microtasks always run before the next macrotask**, regardless of how many microtasks queue up. A microtask can queue more microtasks (e.g., a `.then` returning another Promise), and all of them run before any macrotask.

**Q4. Where exactly does `process.nextTick` fit in the event loop — is it a phase?**
A: `process.nextTick` is NOT a phase of the libuv event loop. It's a Node.js-specific queue processed by the JavaScript engine itself, outside of libuv's control. The `nextTick` queue is drained at two points:

1. **After the current synchronous operation completes** (when the call stack empties for the first time).
2. **Between every callback execution** within any event loop phase.

This means `nextTick` callbacks run before any Promise microtasks in Node.js (a Node-specific ordering), and both run before any libuv phase (timers, poll, check, etc.).

```
Call stack empties →
  drain process.nextTick queue completely →
    drain Promise microtask queue completely →
      [nextTick may have been added by Promises, drain again] →
        advance event loop phase
```

### Section 2: Each Timer in Detail

**Q5. How does `setTimeout` work, and what does the delay parameter actually mean?**
A: `setTimeout(callback, delay)` schedules `callback` to run after at least `delay` milliseconds. The delay is a **minimum**, not an exact time. When the delay expires, the callback is moved to the **timers queue**. It runs only when:
1. The specified delay has elapsed.
2. The event loop is in the timers phase.
3. The call stack is empty.

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// Output: A, C, B
// 'B' waits for synchronous code to finish, even with 0ms delay
```

The minimum delay is clamped to at least 1ms in most environments (and 4ms for nested setTimeouts beyond 5 levels in browsers). A delay of 0 does NOT mean "run immediately" — it means "run as soon as possible after the current synchronous code and all microtasks finish."

**Q6. How does `setInterval` work, and what are its pitfalls?**
A: `setInterval(callback, interval)` schedules `callback` to run repeatedly with at least `interval` milliseconds between invocations. Under the hood, after each execution, it reschedules the callback `interval` ms later. Key pitfalls:

- **Drift**: if the callback takes longer than `interval` to execute, invocations can "pile up" or drift. `setInterval` doesn't wait for the callback to finish — it fires on a fixed schedule regardless.
- **Skipped intervals**: if the main thread is busy (long synchronous code) when an interval fires, the callback is queued but runs late, potentially back-to-back with subsequent intervals.
- **Long-running callbacks**: if the callback takes longer than the interval, the next callback fires immediately after the previous one finishes (not simultaneously, since JS is single-threaded, but without the intended gap).

```js
// Safer pattern: self-scheduling setTimeout avoids drift
function runWithInterval(callback, interval) {
  function schedule() {
    callback();
    setTimeout(schedule, interval); // reschedule AFTER callback completes
  }
  setTimeout(schedule, interval);
}
```

**Q7. What is `setImmediate`, and in what environment does it exist?**
A: `setImmediate(callback)` is a Node.js-specific API (and some legacy browsers via polyfills) that schedules `callback` to run in the **check phase** of the current event loop iteration — after the poll phase completes, before moving to close callbacks. It has no delay parameter: it's designed to run "immediately after I/O" but after the current poll phase.

`setImmediate` does NOT exist in standard browser JavaScript. In browsers, the closest equivalent is `MessageChannel` or `queueMicrotask` (though these have different semantics). In Node.js, `setImmediate` is the idiomatic way to run code after the current event loop iteration's I/O callbacks.

**Q8. What is `process.nextTick`, and why is it "not really part of the event loop"?**
A: `process.nextTick(callback)` schedules `callback` to run at the end of the current operation — before the event loop advances at all. It's implemented in Node's JavaScript layer (not in libuv), and callbacks are processed from the `nextTick` queue before any libuv phase runs.

"Not really part of the event loop" means: `process.nextTick` is not a phase you can see in the libuv diagram. It's a queue that Node.js processes between every operation — between every callback in every phase. The spec says the nextTick queue is always fully drained before moving forward.

```js
process.nextTick(() => console.log('nextTick 1'));
process.nextTick(() => console.log('nextTick 2'));
Promise.resolve().then(() => console.log('Promise'));
setTimeout(() => console.log('setTimeout'), 0);

// Output:
// nextTick 1
// nextTick 2
// Promise
// setTimeout
```

### Section 3: Execution Order Rules

**Q9. State the definitive execution order rules for all four timer types.**
A: The canonical order from highest to lowest priority:

```
Priority 1: Synchronous code (current call stack)
Priority 2: process.nextTick callbacks (drained completely)
Priority 3: Promise microtasks .then/.catch/.finally (drained completely)
            [Steps 2+3 repeat until both queues are empty]
Priority 4: setTimeout / setInterval (timers phase — next loop iteration)
Priority 5: setImmediate (check phase — after poll)
```

Within priorities 4 and 5, the relative order of `setTimeout(fn, 0)` vs `setImmediate` depends on context:
- **Outside I/O callbacks**: `setTimeout` vs `setImmediate` order is **non-deterministic** (depends on OS timer resolution and system load).
- **Inside an I/O callback**: `setImmediate` ALWAYS runs before `setTimeout(fn, 0)` — because we're already past the timers phase; the check phase comes next.

**Q10. Trace the output of this code and explain each step.**
```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

process.nextTick(() => console.log('4'));

console.log('5');
```
A: Output: `1, 5, 4, 3, 2`

Step-by-step:
1. `console.log('1')` — synchronous, runs immediately → **prints 1**
2. `setTimeout(...)` — registers callback in timers queue (after ≥0ms); call stack continues
3. `Promise.resolve().then(...)` — queues callback in Promise microtask queue
4. `process.nextTick(...)` — queues callback in nextTick queue
5. `console.log('5')` — synchronous → **prints 5**
6. Call stack is now empty. Check nextTick queue → run `console.log('4')` → **prints 4**
7. nextTick queue empty. Check Promise microtask queue → run `console.log('3')` → **prints 3**
8. Both microtask queues empty. Event loop advances to timers phase.
9. setTimeout delay has elapsed → run `console.log('2')` → **prints 2**

**Q11. Trace this more complex example.**
```js
setTimeout(() => {
  console.log('timeout 1');
  process.nextTick(() => console.log('nextTick inside timeout'));
  Promise.resolve().then(() => console.log('promise inside timeout'));
}, 0);

setTimeout(() => console.log('timeout 2'), 0);

process.nextTick(() => console.log('nextTick 1'));
Promise.resolve().then(() => console.log('promise 1'));
```
A: Output: `nextTick 1, promise 1, timeout 1, nextTick inside timeout, promise inside timeout, timeout 2`

Detailed trace:
1. Both `setTimeout`s registered. Both `nextTick` and `Promise.resolve()` queued.
2. Call stack empties. nextTick queue: drain → **`nextTick 1`**
3. Promise microtask queue: drain → **`promise 1`**
4. Event loop: timers phase. Both timeout callbacks are ready.
5. Pick first timeout callback, run it → **`timeout 1`**
   - During this callback: queues `nextTick inside timeout` and `promise inside timeout`
6. **Before picking the second timeout callback**: drain nextTick queue → **`nextTick inside timeout`**
7. Drain Promise microtask queue → **`promise inside timeout`**
8. Now pick second timeout callback → **`timeout 2`**

This demonstrates the critical rule: **microtasks run between individual macrotask callbacks**, not just between full event loop phases.

**Q12. What is the `setTimeout` vs `setImmediate` non-determinism issue, and how do you demonstrate it?**
A: When both `setTimeout(fn, 0)` and `setImmediate(fn)` are called from the main module (not inside an I/O callback), their relative execution order is non-deterministic:

```js
// Run this multiple times — output varies
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// Sometimes: timeout, immediate
// Sometimes: immediate, timeout
```

Why non-deterministic: when the Node.js process starts, it enters the timers phase. If the OS timer for `setTimeout(0)` has already elapsed by the time the timers phase is checked, `setTimeout` runs first. If the timer hasn't elapsed yet (OS timing granularity varies — often 1ms minimum), the event loop falls through to the check phase, running `setImmediate` first.

However, inside an I/O callback, the order IS deterministic — `setImmediate` always runs first:

```js
const fs = require('fs');
fs.readFile(__filename, () => {
  // Inside I/O callback: we've already passed the timers phase
  // Next is check phase (setImmediate) before looping back to timers
  setTimeout(() => console.log('timeout'), 0);    // runs SECOND
  setImmediate(() => console.log('immediate'));   // runs FIRST, always
});
// Always: immediate, timeout
```

**Q13. How does `process.nextTick` starvation work, and why is it dangerous?**
A: If `process.nextTick` callbacks recursively enqueue more `process.nextTick` callbacks, the nextTick queue never empties and the event loop never advances — the program appears to freeze ("starvation" of I/O, timers, and all other operations):

```js
function infiniteNextTick() {
  process.nextTick(infiniteNextTick); // always re-queues itself
}
infiniteNextTick();
// setTimeout callbacks never run
// I/O never completes
// Program is alive but unresponsive
```

This is why the Node.js documentation warns against recursive `process.nextTick` without a termination condition. `setImmediate` does NOT have this problem — it only runs once per event loop iteration (check phase), so even recursive `setImmediate` allows I/O and timers to run between iterations.

```js
// Safe recursive async: use setImmediate instead of nextTick
function safeRecursive() {
  setImmediate(safeRecursive); // runs once per event loop tick — I/O still works
}
```

### Section 4: Browser vs Node.js Differences

**Q14. How does the browser event loop differ from Node.js?**
A: The browser also has microtasks and macrotasks but with different APIs and slightly different phase structures:

| Aspect | Browser | Node.js |
|---|---|---|
| Microtasks | `Promise`, `queueMicrotask`, `MutationObserver` | `process.nextTick`, `Promise` |
| Macrotasks | `setTimeout`, `setInterval`, `MessageChannel`, `requestAnimationFrame` | `setTimeout`, `setInterval`, `setImmediate`, I/O callbacks |
| `process.nextTick` | Not available | Runs before Promise microtasks |
| `setImmediate` | Not standard (some legacy browsers polyfill it) | Runs in check phase after I/O |
| `queueMicrotask` | Yes (ES2019) | Yes (Node.js 11+) |
| Rendering | Between macrotasks (if scheduled) | Not applicable |

In browsers, `process.nextTick` doesn't exist — `queueMicrotask` is the closest equivalent (it queues a microtask, like a resolved Promise). The ordering between `queueMicrotask` and Promise microtasks is FIFO within the microtask queue — they share the same queue in browsers.

In Node.js, `process.nextTick` callbacks run BEFORE Promise microtasks — they have higher priority. This is a Node-specific quirk not present in browsers.

**Q15. What is `queueMicrotask` and when would you use it over `Promise.resolve().then()`?**
A: `queueMicrotask(callback)` (ES2019, available in both modern browsers and Node.js 11+) directly queues a microtask without creating a Promise object. It's semantically equivalent to `Promise.resolve().then(callback)` but:

- **No Promise overhead**: no `Promise` object allocated, no `.then` method lookup.
- **No error wrapping**: exceptions thrown in a `queueMicrotask` callback are uncaught exceptions (not caught by `.catch()` on a Promise). This is a meaningful difference for error handling.
- **Explicitly communicates intent**: `queueMicrotask` clearly signals "I want to defer to the microtask queue" without the implication that something async is happening.

```js
// Equivalent in scheduling behavior, different in semantics:
Promise.resolve().then(() => doSomething()); // allocates a Promise
queueMicrotask(() => doSomething());         // no allocation, more explicit

// Error handling difference:
queueMicrotask(() => { throw new Error('oops'); }); // unhandledRejection? No — uncaughtException
Promise.resolve().then(() => { throw new Error('oops'); }); // UnhandledPromiseRejection
```

### Section 5: `setInterval` Patterns & Pitfalls

**Q16. What is the difference between `setInterval` and a self-rescheduling `setTimeout`, and when does each matter?**
A: Two patterns for repeated execution:

```js
// Pattern 1: setInterval
setInterval(callback, 1000);
// Fires at: t=1000, t=2000, t=3000, ...
// If callback takes 800ms: fires at t=1000 (starts), t=2000 (starts while prev running?)
// → No: JS is single-threaded. t=2000 fires AFTER t=1000 completes (at ~t=1800)
//   but the NEXT interval is still scheduled at t=2000 from the original start
//   If callback takes > interval: callbacks pile up in the queue

// Pattern 2: Self-rescheduling setTimeout
function repeat(callback, interval) {
  setTimeout(function tick() {
    callback();
    setTimeout(tick, interval); // reschedule AFTER callback completes
  }, interval);
}
// Fires at: t=1000, t=1000+interval (from when callback FINISHED)
// If callback takes 800ms: t=1000, t=1000+800+1000=t=2800, ...
// Gap between executions is always >= interval — no pileup
```

Use `setInterval` when you need a fixed-rate schedule and the callback is guaranteed to be shorter than the interval. Use self-rescheduling `setTimeout` when:
- Callback duration is variable or potentially long.
- You want a consistent pause *between* callbacks (not a fixed rate).
- You need to conditionally stop the loop based on the result of each callback.

**Q17. How do you properly clean up `setInterval` to avoid memory leaks?**
A: Always store the interval ID and call `clearInterval` when done:

```js
// Store the ID
const intervalId = setInterval(() => {
  doWork();
}, 1000);

// Clear when no longer needed
function cleanup() {
  clearInterval(intervalId);
}

// In React: clear in useEffect cleanup
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id); // cleanup function
}, []);

// Common mistake: losing the ID
setInterval(() => doWork(), 1000); // ID discarded — can never be cleared!
```

A forgotten `setInterval` (ID not stored, or ID stored but `clearInterval` never called) continues running forever, holding closures alive and potentially causing memory leaks, unintended side effects after component unmount, or behavior in "destroyed" contexts.

### Section 6: Scenario / Interview-Style Questions

**Q18. "Explain why `await Promise.resolve()` yields to the microtask queue but not to the macrotask queue."**
A: `await Promise.resolve()` suspends the async function and queues its resumption as a Promise microtask. When the current synchronous code finishes (and the call stack empties), the microtask queue is processed — the async function resumes. This happens before any `setTimeout` or `setImmediate` callback.

```js
async function run() {
  console.log('A');
  await Promise.resolve(); // suspends here — queues resumption as microtask
  console.log('B');        // resumes here — still in microtask processing
}

run();
setTimeout(() => console.log('C'), 0);
console.log('D');

// Output: A, D, B, C
// A: synchronous inside run()
// D: synchronous after run() call
// B: microtask (resumption of await)
// C: macrotask (setTimeout)
```

`await` is syntactic sugar for `.then()` — it queues the continuation as a Promise microtask, not a macrotask. To yield to the macrotask queue (letting timers and I/O run), you'd need `await new Promise(resolve => setTimeout(resolve, 0))`.

**Q19. "A colleague says `setTimeout(fn, 0)` guarantees `fn` runs as soon as the call stack is empty. Correct this."**
A: Partially correct, but incomplete in two important ways:

1. **Microtasks run first**: before `fn` runs, all pending `process.nextTick` callbacks and all Promise microtasks are processed. If those recursively enqueue more microtasks, they all run first. `fn` runs only after ALL microtasks are drained.

2. **Timer precision**: the 0ms delay is processed by the OS timer subsystem, which has a minimum granularity (typically 1–4ms). The callback may be delayed slightly beyond 0ms. Additionally, if the system is busy, the callback may be delayed further.

3. **Event loop phase**: the timer callback runs in the timers phase of the next event loop iteration — not just "as soon as the stack is empty." If there are pending I/O callbacks, `setImmediate` callbacks, or other phase work queued before the timers phase, those run first.

The correct statement: "`setTimeout(fn, 0)` guarantees `fn` runs no earlier than the next timers phase of the event loop, after all currently queued synchronous code and all microtasks have completed."

**Q20. "When should you use `process.nextTick` vs `setImmediate` in Node.js?"**
A: The Node.js documentation itself addresses this:

Use `process.nextTick` when you need to:
- Run a callback after the current operation but before any I/O, even before Promises.
- Emit events or trigger callbacks synchronously from constructors (so the object is fully constructed by the time the callback fires).
- Handle errors before I/O starts.

```js
class EventEmitter {
  on(event, listener) { /* ... */ }
  emit(event) { /* ... */ }
}

class MyReadable extends EventEmitter {
  constructor() {
    super();
    // Can't emit 'data' here — subscribers haven't attached yet
    process.nextTick(() => this.emit('data', 'initial chunk')); // safe
  }
}

const r = new MyReadable();
r.on('data', chunk => console.log(chunk)); // this runs before nextTick fires
```

Use `setImmediate` when you need to:
- Run code after the current I/O events in the poll phase.
- Allow I/O and timers to run between iterations of a recursive operation.
- Avoid `nextTick` starvation in recursive patterns.

```js
// Recursive work: use setImmediate to avoid starving I/O
function processLargeArray(arr, callback) {
  if (arr.length === 0) return callback();
  const chunk = arr.splice(0, 100); // process 100 items
  chunk.forEach(processItem);
  setImmediate(() => processLargeArray(arr, callback)); // yield between chunks
}
```

**Q21. "Predict the output of this code and explain your reasoning."**
```js
setImmediate(() => console.log('setImmediate'));
setTimeout(() => console.log('setTimeout'), 0);
Promise.resolve().then(() => console.log('Promise'));
process.nextTick(() => console.log('nextTick'));
```
A: The output is deterministic in this case for `nextTick` and `Promise` relative to the timers, but `setImmediate` vs `setTimeout` is non-deterministic (see Q12).

Guaranteed order: `nextTick` → `Promise` → [either `setTimeout` or `setImmediate`] → [the other]

Most likely output: `nextTick, Promise, setTimeout, setImmediate` OR `nextTick, Promise, setImmediate, setTimeout`

Reasoning:
1. `setImmediate` and `setTimeout` are registered. `Promise.resolve().then` queues a microtask. `nextTick` queues a nextTick callback.
2. Synchronous code finishes. Drain nextTick queue → **`nextTick`**
3. Drain Promise microtask queue → **`Promise`**
4. Event loop timers phase: if timer has elapsed → **`setTimeout`**, then check phase → **`setImmediate`**
   OR: timer hasn't elapsed, skip timers, poll phase, check phase → **`setImmediate`**, loop back to timers → **`setTimeout`**

## Problem 1 — Classic Order Prediction

### Problem
Predict the exact output:

```js
console.log('start');

setTimeout(() => {
  console.log('setTimeout 1');
}, 0);

setImmediate(() => {
  console.log('setImmediate');
});

process.nextTick(() => {
  console.log('nextTick 1');
});

Promise.resolve().then(() => {
  console.log('promise 1');
});

process.nextTick(() => {
  console.log('nextTick 2');
});

Promise.resolve().then(() => {
  console.log('promise 2');
});

console.log('end');
```

### Pattern Recognition
Mixed queue types — requires knowing the complete priority order: synchronous → nextTick → Promise microtasks → macrotasks (timers/setImmediate).

### Key Insight
All synchronous code runs first. Then nextTick queue is fully drained (both nextTick callbacks). Then Promise microtask queue is fully drained (both promise callbacks). Then macrotasks run. `setTimeout` vs `setImmediate` order is non-deterministic from the main module.

### Step-by-Step Trace

```
Synchronous execution phase:
  1. console.log('start')               → print "start"
  2. setTimeout(cb, 0)                  → register in timers (≥0ms)
  3. setImmediate(cb)                   → register in check phase
  4. process.nextTick(cb1)              → add cb1 to nextTick queue
  5. Promise.resolve().then(cb2)        → add cb2 to microtask queue
  6. process.nextTick(cb3)              → add cb3 to nextTick queue
  7. Promise.resolve().then(cb4)        → add cb4 to microtask queue
  8. console.log('end')                 → print "end"

Call stack empty. Process microtasks:
  nextTick queue: [cb1, cb3]
  9.  run cb1 → print "nextTick 1"
  10. run cb3 → print "nextTick 2"
  nextTick queue empty.

  Promise microtask queue: [cb2, cb4]
  11. run cb2 → print "promise 1"
  12. run cb4 → print "promise 2"
  Microtask queue empty.

Event loop — macrotasks:
  [Non-deterministic: setTimeout vs setImmediate]
  Option A (setTimeout first):
    13. print "setTimeout 1"
    14. print "setImmediate"
  Option B (setImmediate first):
    13. print "setImmediate"
    14. print "setTimeout 1"
```

### Output

```
start
end
nextTick 1
nextTick 2
promise 1
promise 2
[either] setTimeout 1
[either] setImmediate
```

Lines 1–6 are always in this exact order. Lines 7–8 can swap.

### Why It Matters
Real-world code often mixes Promises with `setTimeout`. Understanding that Promise handlers run before ANY timer callback prevents bugs where code assumes a timer has fired by the time a Promise resolves (or vice versa). Common bug: setting up a timer in synchronous code and reading its result in a `.then()` — the `.then()` runs before the timer.

### Follow-up Questions
- "What if you replace `process.nextTick` with `queueMicrotask`?" → `queueMicrotask` runs in the Promise microtask queue (same level as `.then`), not the nextTick queue. Output changes: `start, end, promise 1, queueMicrotask 1, promise 2, queueMicrotask 2` — interleaved with Promises in FIFO order.
- "What if the Promises are rejected instead of resolved?" → `.catch()` handlers are also Promise microtasks — same queue, same order. The rejection status doesn't affect scheduling priority.

## Problem 2 — Nested Callbacks and Queue Interaction

### Problem
Predict the exact output:

```js
setTimeout(() => {
  console.log('timeout outer');

  process.nextTick(() => {
    console.log('nextTick inside timeout');
  });

  Promise.resolve().then(() => {
    console.log('promise inside timeout');
  });

  setTimeout(() => {
    console.log('timeout inner');
  }, 0);
}, 0);

process.nextTick(() => {
  console.log('nextTick outer');

  process.nextTick(() => {
    console.log('nextTick nested');
  });
});

Promise.resolve().then(() => {
  console.log('promise outer');
});
```

### Pattern Recognition
Nested microtask scheduling — a `nextTick` callback can schedule another `nextTick`, and the inner one runs before Promise microtasks. A `setTimeout` callback can schedule `nextTick` and `Promise` callbacks, and those run between macrotask callbacks.

### Key Insight — nextTick Nesting
When a `nextTick` callback schedules another `nextTick`, the inner one is added to the end of the current nextTick queue. The queue is drained completely before Promises run, so nested nextTick callbacks all run before any Promise microtask.

### Step-by-Step Trace

```
Synchronous execution:
  Register setTimeout(outer, 0)

```


### Why It Matters
This demonstrates that microtask processing happens **between individual macrotask callbacks**, not just between complete event loop phases. This is crucial for Node.js applications where a single HTTP request might fire multiple timer callbacks — knowing that each callback gets its own microtask "flush" prevents subtle ordering bugs in middleware chains.

### Follow-up Questions
- "Would replacing `process.nextTick` with `queueMicrotask` change the output?" → Yes — `queueMicrotask` goes in the Promise microtask queue, not the nextTick queue. `nextTickNested` would run after `promiseOuter` (they'd be in the same microtask queue, interleaved).
- "What if `setTimeout(inner, 0)` was `setImmediate` instead?" → The inner callback would go to the check phase, running after all timers in the current timers phase. Output would be the same since `timeout outer` is the only timer.

## Problem 3 — `setInterval` Timing and Cleanup

### Problem
Implement a reliable countdown timer that counts from `n` to 0, logs each second, and cleans itself up. The timer must not drift over long periods and must stop exactly when it reaches 0.

```js
countdown(5);
// Expected output (approximately 1 second apart):
// 5
// 4
// 3
// 2
// 1
// Done!
```

### Pattern Recognition
Self-rescheduling `setTimeout` pattern — for a countdown where timing accuracy and proper cleanup matter, `setInterval` can drift if the callback takes variable time. A self-rescheduling `setTimeout` guarantees at least `interval` ms between each execution.

### Key Insight
`setInterval` fires at fixed wall-clock intervals regardless of callback duration. For a countdown, we want exactly one second between outputs — measured from when each number is logged. Self-rescheduling `setTimeout` measures the gap from callback end to next callback start, preventing pileup and ensuring predictable behavior.

Also: the countdown must handle clearing itself when done. Using `setInterval`, you must call `clearInterval` from inside the callback. Using self-rescheduling `setTimeout`, you simply don't reschedule when done.

### Solution — Both Approaches

```js
// ── Approach 1: setInterval (simpler but can drift) ─────────────────────
function countdownInterval(n) {
  let count = n;
  const id = setInterval(() => {
    console.log(count);
    count--;
    if (count < 0) {
      clearInterval(id); // must manually clear
      console.log('Done!');
    }
  }, 1000);
  return id; // return for external cancellation
}

// ── Approach 2: self-rescheduling setTimeout (preferred) ────────────────
function countdown(n) {
  let count = n;

  function tick() {
    console.log(count);
    count--;

    if (count >= 0) {
      setTimeout(tick, 1000); // reschedule only if not done
    } else {
      console.log('Done!');
      // No rescheduling — timer stops automatically
    }
  }

  setTimeout(tick, 1000); // first fire after 1 second
}

// ── Approach 3: Promise-based (modern, cancellable) ─────────────────────
function countdownAsync(n) {
  const delay = ms => new Promise(resolve => setTimeout(resolve, ms));
  let cancelled = false;

  async function run() {
    for (let i = n; i >= 0; i--) {
      if (cancelled) return;
      if (i > 0) console.log(i);
      else console.log('Done!');
      if (i > 0) await delay(1000);
    }
  }

  run();

  return { cancel: () => { cancelled = true; } };
}
```

### Dry Run — Self-Rescheduling setTimeout

```
countdown(3) called:
  Register setTimeout(tick, 1000) — ID stored in closure

t=0ms:   synchronous execution complete
t≈1000ms: timers phase — tick fires
  print "3"
  count = 2
  count >= 0 → setTimeout(tick, 1000) registered

Between callbacks: nextTick and Promise queues drained (empty)

t≈2000ms: tick fires
  print "2"
  count = 1
  setTimeout(tick, 1000) registered

t≈3000ms: tick fires
  print "1"
  count = 0
  setTimeout(tick, 1000) registered

t≈4000ms: tick fires
  print "0" — wait, count=0 here...
  Let me re-examine the condition:

  tick():
    console.log(count)  ← logs current count
    count--
    if (count >= 0) → reschedule
    else → print Done!

  With n=3:
  tick1: log 3, count→2, 2>=0 → reschedule
  tick2: log 2, count→1, 1>=0 → reschedule
  tick3: log 1, count→0, 0>=0 → reschedule
  tick4: log 0, count→-1, -1<0 → print "Done!"

Output:
  t≈1000ms: 3
  t≈2000ms: 2
  t≈3000ms: 1
  t≈4000ms: 0
  Done!

(If n starts the countdown from n, not n+1, adjust the loop)
```

### Comparison: setInterval vs Self-Rescheduling setTimeout

```
setInterval with fast callback (< 1000ms): nearly identical
setInterval with slow callback (> 1000ms): can cause pileup/drift

Example with 1200ms callback, 1000ms interval:
  setInterval:
    t=0:    interval fires, callback starts (takes 1200ms)
    t=1000: interval fires again → queued (callback still running!)
    t=1200: first callback ends
    t=1200: queued callback starts immediately (no 1s gap!)
    t=2400: second callback ends
    t=2000: another interval fires → queued
    ...gap between callbacks: 0ms, 800ms, 0ms, ... (chaotic)

  self-rescheduling setTimeout:
    t=0:    setTimeout(tick, 1000) registered
    t=1000: tick fires, callback starts (takes 1200ms)
    t=2200: callback ends, setTimeout(tick, 1000) registered
    t=3200: tick fires again
    ...gap between callbacks: always 1000ms (consistent)
```

### Why It Matters
Production countdown timers (polling intervals, health checks, retry logic) must not pile up when the operation takes longer than expected. `setInterval` is safe only when the callback is reliably faster than the interval. Self-rescheduling `setTimeout` is safer for real-world scenarios.

### Follow-up Questions
- "How do you implement a countdown that can be paused and resumed?" → Store the remaining count in a variable; `clearTimeout` to pause; re-schedule to resume.
- "What if you need millisecond-accurate timing?" → `setTimeout` is not accurate to milliseconds (system load, GC, event loop pressure). For high-accuracy timing, use `performance.now()` and compensate for drift: `setTimeout(tick, interval - (performance.now() - lastTick) % interval)`.

## Problem 4 — Promise + setTimeout Race Pattern

### Problem
Implement a `withTimeout` utility: given a Promise and a timeout in milliseconds, return a new Promise that resolves with the original Promise's value if it settles within the timeout, or rejects with a `TimeoutError` if it doesn't.

```js
const slowOp = new Promise(resolve => setTimeout(() => resolve('done'), 5000));

withTimeout(slowOp, 1000)
  .then(result => console.log('Result:', result))
  .catch(err => console.log('Error:', err.message));
// After 1000ms: "Error: Operation timed out"
```

### Pattern Recognition
`Promise.race` with a timeout Promise — understanding that `setTimeout` creates a macrotask that races against the original Promise's microtask. The first to settle wins the race.

### Key Insight
`Promise.race([p1, p2])` resolves/rejects with whichever Promise settles first. Creating a "timeout Promise" that rejects after `n` ms and racing it against the original operation gives clean timeout behavior. The timeout timer should be cleared if the original operation completes first to avoid resource leaks.

### Solution

```js
class TimeoutError extends Error {
  constructor(ms) {
    super(`Operation timed out after ${ms}ms`);
    this.name = 'TimeoutError';
  }
}

function withTimeout(promise, ms) {
  // Create the timeout promise
  let timeoutId;
  const timeoutPromise = new Promise((_, reject) => {
    timeoutId = setTimeout(() => {
      reject(new TimeoutError(ms));
    }, ms);
  });

  // Race: original vs timeout
  return Promise.race([promise, timeoutPromise])
    .finally(() => {
      // CRITICAL: clear the timeout if original resolves first
      // Without this, the timer fires later (even after the race is settled)
      // and Node.js process stays alive until the timer fires
      clearTimeout(timeoutId);
    });
}

// ─── Usage ────────────────────────────────────────────────────────────────

// Fast operation (completes before timeout)
const fast = new Promise(resolve => setTimeout(() => resolve('fast result'), 100));
withTimeout(fast, 1000)
  .then(v => console.log(v))       // "fast result" at ~100ms
  .catch(e => console.log(e.message));

// Slow operation (exceeds timeout)
const slow = new Promise(resolve => setTimeout(() => resolve('slow result'), 5000));
withTimeout(slow, 1000)
  .then(v => console.log(v))
  .catch(e => console.log(e.message)); // "Operation timed out after 1000ms" at ~1000ms
```

### Execution Order Trace

```
withTimeout(slowOp, 1000):
  Creates timeoutPromise — registers setTimeout(reject, 1000)
  Promise.race([slowOp, timeoutPromise]) — returns racePromise

t=0ms: synchronous code complete
t=1000ms: timers phase — timeout fires
  reject(new TimeoutError(1000))
  timeoutPromise transitions to REJECTED
  Promise.race sees first settled promise → racePromise REJECTS with TimeoutError
  Microtask queued: run .finally() callback
  Microtask queued: run .catch() callback

Microtask processing:
  .finally(): clearTimeout(timeoutId) — timer already fired, no-op here
  .catch(): console.log("Operation timed out after 1000ms")

t=5000ms: original slow setTimeout fires
  resolve('slow result') called
  But slowOp's resolution is too late — racePromise already settled
  Promise resolution is idempotent — ignored silently
```

### Common Bug: Forgetting `clearTimeout`

```js
// BUGGY VERSION — missing clearTimeout
function withTimeoutBuggy(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new TimeoutError(ms)), ms)
  );
  return Promise.race([promise, timeout]);
  // If promise resolves before ms: the timeout timer still fires at ms
  // In Node.js: the process stays alive for ms ms even after resolution
  // In browsers: harmless but wastes a timer slot
}

// Example of the bug:
withTimeoutBuggy(Promise.resolve('immediate'), 5000)
  .then(v => console.log(v)); // resolves immediately
// But Node.js process waits 5 seconds before exiting (timer still pending!)
```

### Why It Matters
The `clearTimeout` in `.finally()` is the difference between a well-behaved utility and one that keeps the Node.js process alive indefinitely or accumulates pending timers. This is a classic interview question on the intersection of Promise and timer semantics.

### Follow-up Questions
- "What if the original Promise never settles (neither resolves nor rejects)?" → `withTimeout` still works — the timeout fires, rejects the race, and the `finally` callback clears the timer. The original Promise is silently abandoned (no reject/resolve ever fires for it, but since nothing holds a reference, it's GC'd eventually).
- "Make it cancellable (cancel the original operation, not just the race)?" → The caller must provide a cancellation mechanism (e.g., an `AbortController` signal). `withTimeout` can wire the timeout to the signal: `setTimeout(() => { controller.abort(); reject(...) }, ms)`.

## Problem 5 — Event Loop Starvation and Chunked Processing

### Problem
You have a large array of items to process synchronously. Processing all at once blocks the event loop for too long. Implement a chunked processor that processes items in batches, yielding to the event loop between batches.

```js
const items = Array.from({length: 100000}, (_, i) => i);

processInChunks(items, 1000, item => item * 2, (results) => {
  console.log('Done! Results:', results.length); // 100000
});
// Should process without blocking UI or I/O for more than ~1ms per chunk
```

### Pattern Recognition
Event loop starvation prevention using `setImmediate` — processing large datasets in chunks, yielding between each chunk to allow I/O callbacks, timer callbacks, and rendering (in browsers) to run.

### Key Insight
`setImmediate` runs in the check phase — after I/O callbacks in the poll phase. Using `setImmediate` to schedule the next chunk yields to the entire event loop (allowing all pending callbacks to run) without introducing a timer delay. Using `setTimeout(fn, 0)` would also work but introduces a minimum 1ms delay per chunk. `setImmediate` is faster for this pattern in Node.js.

In browsers, use `setTimeout(fn, 0)` or `MessageChannel` (which has lower latency than `setTimeout(fn, 0)` due to 4ms clamping for nested timers).

### Solution

```js
// ── Node.js version using setImmediate ───────────────────────────────────
function processInChunks(items, chunkSize, transform, onComplete) {
  const results = [];
  let index = 0;

  function processChunk() {
    const end = Math.min(index + chunkSize, items.length);

    // Process one chunk synchronously
    while (index < end) {
      results.push(transform(items[index]));
      index++;
    }

    if (index < items.length) {
      // More items remain — yield to event loop, then continue
      setImmediate(processChunk);
      // setImmediate chosen over setTimeout(fn, 0):
      //   - no minimum delay
      //   - runs after I/O (better for Node.js server scenarios)
      //   - slightly lower overhead
    } else {
      // All done — call completion callback
      onComplete(results);
    }
  }

  // Start processing (use setImmediate so caller's code runs first)
  setImmediate(processChunk);
}

// ── Browser version using MessageChannel (low latency) ───────────────────
function processInChunksBrowser(items, chunkSize, transform, onComplete) {
  const results = [];
  let index = 0;
  const channel = new MessageChannel();

  channel.port1.onmessage = function processChunk() {
    const end = Math.min(index + chunkSize, items.length);

    while (index < end) {
      results.push(transform(items[index]));
      index++;
    }

    if (index < items.length) {
      channel.port2.postMessage(null); // schedule next chunk via MessageChannel
    } else {
      onComplete(results);
    }
  };

  channel.port2.postMessage(null); // kick off first chunk
}

// ── Modern version using async/await ─────────────────────────────────────
async function processInChunksAsync(items, chunkSize, transform) {
  const results = [];

  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    results.push(...chunk.map(transform));

    // Yield to event loop between chunks
    await new Promise(resolve => setImmediate(resolve));
    // Or: await new Promise(resolve => setTimeout(resolve, 0));
  }

  return results;
}
```

### Dry Run

```
processInChunks([0..9], chunkSize=3, x=>x*2, callback)

Call stack: setImmediate(processChunk) registered, returns immediately

Event loop — check phase:
  processChunk():
    index=0, end=min(3,10)=3
    results=[0, 2, 4] (items 0,1,2 × 2)
    index=3
    3 < 10 → setImmediate(processChunk) — yield!

  [Event loop can process pending I/O, timers here]

Event loop — check phase:
  processChunk():
    index=3, end=min(6,10)=6
    results=[0,2,4,6,8,10]
    index=6
    6 < 10 → setImmediate(processChunk)

  [Event loop can process pending I/O here]

Event loop — check phase:
  processChunk():
    index=6, end=min(9,10)=9
    results=[...,12,14,16]
    index=9
    9 < 10 → setImmediate(processChunk)

Event loop — check phase:
  processChunk():
    index=9, end=min(12,10)=10
    results=[...,18]
    index=10
    10 >= 10 → onComplete(results)!
    callback: console.log('Done! Results:', 10)

Total: 4 check-phase iterations, 3 event loop yields
```

### Comparing `setImmediate` vs `setTimeout(fn, 0)` vs `process.nextTick` for Chunking

```
process.nextTick: runs BEFORE I/O — starves I/O if used recursively!
  process.nextTick(processChunk) inside processChunk:
  → nextTick queue never empties → I/O never runs → starvation

setTimeout(fn, 0): introduces 1ms+ delay per chunk
  100,000 items / 1000 per chunk = 100 chunks × 1ms = 100ms+ overhead

setImmediate: runs after I/O, before next timer check
  → allows I/O to interleave, no artificial delay
  → 100 chunks with minimal overhead

Winner for Node.js chunked processing: setImmediate ✓
Winner for browser chunked processing: MessageChannel or requestAnimationFrame
```

### Why It Matters
Long-running synchronous loops block the Node.js event loop, causing request timeouts, dropped WebSocket frames, and unresponsive processes. Chunked processing with `setImmediate` is the idiomatic Node.js solution for CPU-intensive work that must coexist with I/O-heavy workloads.

### Follow-up Questions
- "Why not use `worker_threads` instead?" → For CPU-bound work, `worker_threads` is the right solution (runs in a separate thread, no event loop blocking at all). Chunked `setImmediate` is for cases where the work is light per chunk but voluminous in total, or when worker overhead isn't justified.
- "How do you measure if you're blocking the event loop?" → Measure event loop lag: check how late a `setTimeout(fn, 0)` actually fires vs when it was scheduled. `performance.eventLoopUtilization()` in Node.js 12.19+ gives precise utilization metrics.

## Problem 6 — Execution Order with Async/Await

### Problem
Predict the output:

```js
async function main() {
  console.log('1');

  await null; // or: await Promise.resolve()

  console.log('2');

  await new Promise(resolve => setTimeout(resolve, 0));

  console.log('3');
}

console.log('A');
main();
console.log('B');

setTimeout(() => console.log('C'), 0);
Promise.resolve().then(() => console.log('D'));
```

### Pattern Recognition
`async/await` desugared — `await expr` suspends the function and queues its resumption as a microtask (if `expr` is already resolved) or when `expr` settles (could be a macrotask later). Understanding where `await` points in the event loop determines the output.

### Key Insight
`await null` is equivalent to `await Promise.resolve(null)` — the function suspends and its resumption is queued as a microtask. `await new Promise(resolve => setTimeout(resolve, 0))` suspends the function until the timeout fires (macrotask), then queues the resumption as a microtask.

### Step-by-Step Trace

```
Synchronous execution:
  console.log('A')                      → print "A"
  main() called:
    console.log('1')                    → print "1"
    await null → suspend main()
      → queue main's resumption as microtask (since null is already resolved)
    main() returns a pending Promise
  console.log('B')                      → print "B"
  setTimeout(()=>log('C'), 0)           → register timer
  Promise.resolve().then(()=>log('D'))  → queue 'D' as microtask

Call stack empty. Drain microtasks:
  Microtask queue: [main-resumption, 'D' callback]
  (Note: main was suspended before 'D' was queued, but both are microtasks)

  Run main-resumption:
    console.log('2')                    → print "2"
    await new Promise(resolve => setTimeout(resolve, 0))
    → register setTimeout(resolve, 0) → timer registered
    → suspend main() again
    (main's resumption is NOT yet queued — waiting for timer)

  Microtask queue still has: ['D' callback]
  Run 'D' callback:
    console.log('D')                    → print "D"

  Microtask queue empty.

Event loop — timers phase:
  Two timers ready: setTimeout('C', 0) and setTimeout(resolve, 0)
  [Timer registration order determines which fires first]
  Both registered at ~same time:
    'C' was registered before main's await, so it fires first:
    Run 'C' timer: console.log('C')     → print "C"

  Microtask check (between timer callbacks):
    Nothing queued.

    Run resolve timer: calls resolve()
    → main-resumption queued as microtask

  Drain microtasks:
    Run main-resumption:
      console.log('3')                  → print "3"
      main() returns (async function ends)

Microtask check after 'C' timer:
  Actually: after resolve fires, main resumption runs as microtask
  So: C fires, then microtask drains (3 prints), THEN process continues
```

### Output

```
A
1
B
2
D
C
3
```

Explanation of key ordering:
- `A` and `B`: synchronous, in order
- `1`: synchronous inside `main()` before first `await`
- `2`: microtask resumption (first `await null` resumes)
- `D`: microtask queued after `main` suspends (FIFO: `main-resumption` ran first, then `D`)
- `C`: macrotask (setTimeout)
- `3`: microtask after `C`'s timer fires the `resolve` → microtask drains before next macrotask

### Why It Matters
`async/await` creates invisible microtask boundaries that affect ordering with other Promises and timers. A common bug: assuming code after `await Promise.resolve()` runs before `setTimeout(fn, 0)` callbacks — it does, but only because the resumption is a microtask. Changing `await Promise.resolve()` to `await new Promise(resolve => setTimeout(resolve))` changes the resumption to a macrotask, shifting the output significantly.

### Follow-up Questions
- "What if you move `Promise.resolve().then(() => console.log('D'))` inside `main()` before the `await`?" → `D` would be queued synchronously (before the first `await`), then run before `main`'s resumption: output becomes `A, 1, B, D, 2, C, 3`.
- "What's the difference between `await null` and `await Promise.resolve()`?" → Both create a microtask for resumption. `await null` implicitly wraps `null` in `Promise.resolve(null)`. The behavior is identical.

## Quick Reference — Execution Order Cheat Sheet

```
PRIORITY ORDER (highest to lowest):
  1. Synchronous code (current call stack)
  2. process.nextTick queue        [Node.js only — NOT in browsers]
  3. Promise microtask queue       (.then, .catch, .finally, queueMicrotask, await resumption)
     [Steps 2+3 repeat until both empty — a nextTick can add Promises, and vice versa]
  4. Macrotasks (one at a time):
     a. setTimeout / setInterval callbacks (timers phase)
     b. I/O callbacks (poll phase)
     c. setImmediate callbacks (check phase)   [Node.js only]
  → After each macrotask: repeat steps 2+3

KEY RULES:
  □ Microtasks drain COMPLETELY before any macrotask runs
  □ Microtasks run BETWEEN individual macrotask callbacks (not just between phases)
  □ process.nextTick runs BEFORE Promise microtasks (Node.js specific)
  □ setTimeout(fn, 0) vs setImmediate: NON-DETERMINISTIC from main module
  □ setTimeout(fn, 0) vs setImmediate inside I/O callback: setImmediate ALWAYS first
  □ Recursive nextTick → starvation; recursive setImmediate → safe (one per tick)
  □ await expr: suspends function, queues resumption as microtask (if already resolved)
                or as microtask after macrotask (if expr is a pending setTimeout-based Promise)

BROWSER DIFFERENCES:
  □ No process.nextTick — use queueMicrotask (runs with Promise microtasks)
  □ No setImmediate (standard) — use MessageChannel for low-latency macrotask
  □ Rendering happens between macrotasks (after microtasks drain)
```

## Common Bugs Checklist

Before finalizing any async code involving timers, verify:

1. **Forgetting `clearTimeout`/`clearInterval` causing process hangs or memory leaks** — always store timer IDs and clear them in cleanup logic. In React, clear in `useEffect` return function. In Node.js servers, clear on connection close or process exit.

2. **Using `process.nextTick` recursively without a termination condition** — this starves I/O and all other event loop activity. The symptom: your code runs forever but nothing else in the process works. Switch to `setImmediate` for recursive scheduling.

3. **Assuming `setTimeout(fn, 0)` runs before or after Promise `.then()` without checking** — `setTimeout` is always a macrotask; `.then()` is always a microtask. Promise callbacks ALWAYS run before timer callbacks, regardless of which was registered first.

4. **Relying on `setTimeout` vs `setImmediate` order outside I/O callbacks** — this is explicitly non-deterministic in Node.js. Never write code whose correctness depends on which fires first in the main module context. Move the code inside an I/O callback if you need `setImmediate`-before-`setTimeout` guarantee.

5. **WeakRef/stale closure in `setInterval` callbacks** — the closure captures variables at creation time. If those variables are reassigned (e.g., `let data = ...` then `data = null`), the interval callback may operate on the old reference. Capture by value when needed: `const capturedData = data; setInterval(() => use(capturedData), 1000)`.

6. **Not handling `setInterval` callback duration exceeding the interval** — for any callback that might take longer than the interval (network calls, file I/O, computation), use self-rescheduling `setTimeout` instead to prevent callback pileup.
