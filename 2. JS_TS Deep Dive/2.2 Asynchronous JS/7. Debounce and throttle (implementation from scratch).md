## Part 1 — Theory & Interview Q&A

## Topic A: Debounce

### Section A1: Fundamentals

**Q1. What is debounce, and what timing invariant does it preserve?**

A: Debounce delays a function's invocation until a specified quiet period has elapsed since the *last* call. Every new call resets the timer — only after calls stop arriving for `delay` milliseconds does the function actually fire. The invariant: *within any burst of calls spaced less than `delay` ms apart, the wrapped function fires at most once* — on the trailing edge (last call + delay), the leading edge (first call), or both, depending on configuration. Without debounce, a search input's `onChange` fires on every keystroke; with debounce, it fires once the user pauses. The term comes from electronics — debouncing a physical button prevents registering multiple clicks from a single mechanical press whose contacts briefly "bounce."

```
calls:   •──•──•──•────────────────•──•────────────•
time:  ──┼──┼──┼──┼────────────────┼──┼────────────┼──────→ ms
                     ↑ fires             ↑ fires      ↑ fires (pending)
         delay=300  [burst 1 ends]  [burst 2 ends]  [in progress]

Without debounce: fn fires 8 times
With debounce:    fn fires at most once per quiet period ✓
```

**Q2. How do `clearTimeout` and `setTimeout` implement trailing debounce, and what is the role of each step?**

A: The mechanism is two lines working together: `clearTimeout(timerId)` cancels any pending invocation from the previous call; `setTimeout(...)` schedules a new invocation `delay` ms in the future. The result: the timer is always reset to `delay` ms from the *most recent* call. `timerId` is the only shared state — it represents the identity of the currently pending timeout, allowing it to be cancelled. After the function fires, `timerId` is set to `null` to reflect that no invocation is pending. The arrow function in the setTimeout callback captures `this` and `args` lexically — without an arrow function, `this` inside the callback would be the global object or `undefined` in strict mode.

```js
function debounce(fn, delay) {
  let timerId = null; // shared state: identity of current pending timeout

  return function debounced(...args) {
    clearTimeout(timerId);            // Step 1: cancel the previous pending call
    timerId = setTimeout(() => {      // Step 2: schedule a new call (delay ms from now)
      timerId = null;                 // Step 3: mark as no longer pending
      fn.apply(this, args);           // Step 4: invoke with correct context and args
    }, delay);
    // `this` inside arrow fn = `debounced`'s `this` (captured lexically)
  };
}

// Each call restarts the timer from zero:
// t=0:   call → clearTimeout(null), set timer for t=300
// t=100: call → clearTimeout(t=300 timer), set timer for t=400
// t=200: call → clearTimeout(t=400 timer), set timer for t=500
// t=500: timer fires → fn() called once ✓
```

**Q3. What is the leading-edge debounce, and what problem does it solve that trailing cannot?**

A: Leading-edge debounce fires the function *immediately* on the first call of a burst, then blocks further invocations until the quiet period elapses. This is optimal when the goal is *instant response to the first event* — preventing double-submits, immediate visual feedback, or responding the moment a user starts an action rather than after they finish. The implementation check: `if (timerId === null)` identifies "the first call of a burst" (no timer running) — fire immediately and set a timer to prevent subsequent calls. Trailing debounce is right for "respond after user finishes"; leading is right for "respond the moment user starts."

```
Leading edge (first call fires, rest blocked):
calls:   •──•──•──•──────────•──•──────
time:  ──┼──┼──┼──┼──────────┼──┼──────→
         ↑fires               ↑fires
         (immediately)        (immediately, new burst)

Trailing edge (last call fires after silence):
calls:   •──•──•──•──────────•──•──────
time:  ──┼──┼──┼──┼──────────┼──┼──────→
                    ↑fires          ↑fires (pending)
                    (after delay)

Use leading for: button click handlers (prevent double-submit), showing loading state immediately
Use trailing for: search autocomplete, auto-save, resize recalculation
```

**Q4. How does the combined leading + trailing debounce work, and what is its single-call edge case?**

A: Combined debounce fires on the *leading edge* (first call of a burst) and *again* on the trailing edge (last call + delay) — but only if additional calls arrived after the leading invocation. The key edge case: a single isolated call with `{ leading: true, trailing: true }` fires **only once** (on leading) — the trailing invocation is suppressed when no new calls followed the leading fire. This avoids double-invocation for isolated clicks. The implementation tracks this with `lastArgs`: set `lastArgs = args` before leading fires, then invoke and `lastArgs = null` after. The trailing timer only invokes if `lastArgs !== null` (meaning new calls arrived after the leading invocation).

```js
// Invariant for lastArgs:
// lastArgs = null → leading just fired, no subsequent calls yet → trailing should skip
// lastArgs = args → new calls arrived after leading → trailing should fire

// Single call with leading+trailing:
// t=0:   call → leading fires, lastArgs=null, timer set
// t=300: timer fires → lastArgs===null → trailing SKIPPED ✓ (no double fire)

// Multiple calls with leading+trailing:
// t=0:   call → leading fires ('a'), lastArgs=null, timer set
// t=100: call → lastArgs='b', timer reset
// t=400: timer fires → lastArgs='b' !== null → trailing fires ('b') ✓
```

**Q5. What are `cancel()` and `flush()`, and what real-world scenarios require each?**

A: **`cancel()`** clears the pending timer and resets all state, preventing the debounced function from firing. Required when: (1) a React component unmounts (clear pending timers to prevent state updates on unmounted components and memory leaks); (2) the search query is cleared by the user (no point running a search for an empty string); (3) a form is reset. **`flush()`** immediately invokes the function with the most recent arguments, bypassing the remaining delay. Required when: (1) a user explicitly submits a form that has a debounced validation (submit should trigger validation now, not after the delay); (2) a "save immediately" button should bypass the auto-save debounce; (3) a navigation away from a page should trigger a final auto-save synchronously. Both methods are part of the debounced function's public interface — the returned function is both a function and an object.

```js
// React cleanup pattern — prevents memory leak and state-on-unmounted-component:
useEffect(() => {
  const debouncedSearch = debounce(search, 300);
  input.addEventListener('input', debouncedSearch);
  return () => {
    debouncedSearch.cancel(); // ← crucial: clears pending timer on unmount
    input.removeEventListener('input', debouncedSearch);
  };
}, []);

// Flush on submit:
const debouncedValidate = debounce(validate, 500);
form.addEventListener('submit', () => {
  debouncedValidate.flush(); // run validation immediately, then submit
});
```

**Q6. What closure state does a debounce implementation require, and what is each variable's role?**

A: A full-featured debounce (leading + trailing + cancel + flush) captures five variables in its closure: **`timerId`** — the current pending timer ID; `null` means no invocation is scheduled (enables the "is this the first call of a burst?" check for leading edge); **`lastArgs`** — the arguments from the most recent call; used by the trailing invocation and by `flush()`; `null` after a leading invocation (signals "no new calls since leading fired"); **`lastContext`** — the `this` context from the most recent call; must be stored separately because `this` is not capturable across async boundaries without explicit storage; **`leading`** and **`trailing`** flags — booleans from options; control which edge(s) fire. Each call to `debounce()` creates a new closure with its own independent state — this is why creating a new debounced function on every render breaks the debounce effect (each closure has a fresh `timerId = null`, so `clearTimeout` never cancels anything meaningful).

```js
function debounce(fn, delay, { leading = false, trailing = true } = {}) {
  // --- Closure state ---
  let timerId     = null;  // pending timer ID; null = burst ended or not started
  let lastArgs    = null;  // most recent call's args; null = leading just fired
  let lastContext = null;  // most recent call's this

  // Shared invoke helper:
  const invoke = (ctx, args) => { lastArgs = null; lastContext = null; fn.apply(ctx, args); };

  return function debounced(...args) {
    const isFirstCall = timerId === null; // no active timer = start of new burst

    lastArgs    = args;
    lastContext = this;
    clearTimeout(timerId);

    if (leading && isFirstCall) invoke(this, args); // immediate: clears lastArgs

    timerId = setTimeout(() => {
      timerId = null;
      if (trailing && lastArgs !== null) invoke(lastContext, lastArgs); // only if new calls came
      lastArgs = lastContext = null;
    }, delay);
  };
}
```

**Q7. What is `maxWait`, and how does it create a hybrid debounce + throttle behavior?**

A: `maxWait` sets the maximum time the debounced function is allowed to be delayed regardless of incoming calls. Without `maxWait`, a function debounced at 300ms that receives calls every 200ms will *never fire* — new calls keep resetting the timer indefinitely. With `maxWait = 2000`, the function fires at least once every 2000ms, even if calls never stop. The implementation adds a second timer: on the first call of a burst, record `burstStart = Date.now()`; in subsequent calls, if `Date.now() - burstStart >= maxWait`, fire immediately (invoke like a leading call) and reset `burstStart`. The resulting behavior is: "wait up to 300ms of silence (debounce), but fire at least every 2000ms (throttle)" — the best of both patterns. This is exactly how Lodash implements `debounce(fn, 300, { maxWait: 2000 })`.

```
Without maxWait — function NEVER fires during continuous input:
calls:   •••••••••••••••••••••••••••••••••••••••••
time:  ──┼──────────────────────────────────────→
         (timer keeps resetting, fn never fires)

With maxWait=2000:
calls:   •••••••••••••••••••••••••••••••••••••••
time:  ──┼──────────────────2s──────────────────→
                              ↑fires (maxWait hit)
         (fn fires every 2s even during continuous input)

Rule: fires at min(quiet period after last call, maxWait from burst start)
```

**Q8. How does async debounce work, and what must happen to the Promise from a superseded call?**

A: A standard debounce discards superseded calls silently. An async debounce wraps each invocation in a `Promise`, so callers can `await` the result — useful for `fetch` calls in search autocomplete. The challenge: when a new call arrives and resets the timer, the old call's Promise must be resolved/rejected (or left as a "forever pending" Promise, which causes memory leaks and unresolved `await`s). The two options: (1) **Reject with a supersession sentinel** — call the old Promise's `reject` with a custom error (e.g., `{ superseded: true }`); callers filter this error class. (2) **Leave unresolved** — simpler but leaks memory if Promises accumulate. Option 1 is correct for production. The implementation stores `{ resolve, reject }` in the closure and calls `reject` before clearing the old timer.

```js
function asyncDebounce(fn, delay) {
  let timerId = null;
  let pending = null; // { resolve, reject } for the current in-flight Promise

  return function debounced(...args) {
    // Supersede the previous pending call:
    if (pending) {
      pending.reject(Object.assign(new Error('Debounced: superseded'), { superseded: true }));
    }
    clearTimeout(timerId);

    return new Promise((resolve, reject) => {
      pending = { resolve, reject };
      const captured = pending;

      timerId = setTimeout(() => {
        timerId = null;
        pending = null;
        Promise.resolve(fn.apply(this, args)).then(captured.resolve, captured.reject);
      }, delay);
    });
  };
}

// Usage — only the final call's result resolves:
const debouncedSearch = asyncDebounce(fetchResults, 300);
input.addEventListener('input', async (e) => {
  try {
    const results = await debouncedSearch(e.target.value);
    renderResults(results);
  } catch (err) {
    if (err.superseded) return; // silently ignore superseded calls
    handleError(err);
  }
});
```

**Q9. What is the precise invocation count guarantee for debounce with each configuration?**

A: Given n calls arriving within one burst (all within `delay` ms of each other): **`{ leading: false, trailing: true }`** (default): exactly 1 invocation — on the trailing edge. **`{ leading: true, trailing: false }`**: exactly 1 invocation — on the leading edge. **`{ leading: true, trailing: true }`**: exactly 1 invocation if n=1 (leading only, trailing suppressed); exactly 2 invocations if n≥2 (leading on first, trailing on last). **`{ leading: false, trailing: false }`**: 0 invocations — a no-op (nonsensical but valid configuration). Across b distinct bursts separated by more than `delay` ms: the total invocation count is at most b (trailing) or exactly b (leading) or at most 2b (leading+trailing). The debounce invariant is strictly an invocation-count guarantee, not a timing guarantee — "at most once per quiet period."

### Section A2: Advanced Patterns

**Q10. How do you test debounce reliably, and why does real `setTimeout` make tests non-deterministic?**

A: Real `setTimeout` makes debounce tests require `await new Promise(r => setTimeout(r, delay + buffer))` — slow, fragile, and sensitive to system load. Jest and Vitest provide fake timer APIs (`jest.useFakeTimers()`) that replace global `setTimeout`, `clearTimeout`, and `Date.now` with synchronous, controllable implementations. After calling the debounced function, `jest.advanceTimersByTime(delay)` synchronously advances the fake clock, causing the scheduled callback to fire immediately. Key patterns: (1) verify the function has NOT been called before `advanceTimersByTime`; (2) verify it HAS been called after; (3) verify multiple rapid calls only produce one invocation; (4) test `cancel()` by calling it before advancing time and verifying no invocation occurs.

```js
describe('debounce', () => {
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  test('fires once after delay, not during burst', () => {
    const fn = jest.fn();
    const debounced = debounce(fn, 300);

    debounced('a'); debounced('b'); debounced('c'); // rapid burst

    expect(fn).not.toHaveBeenCalled(); // not yet — timer pending

    jest.advanceTimersByTime(299);
    expect(fn).not.toHaveBeenCalled(); // still pending

    jest.advanceTimersByTime(1); // total: 300ms
    expect(fn).toHaveBeenCalledTimes(1); // fired exactly once
    expect(fn).toHaveBeenCalledWith('c'); // with most recent args
  });

  test('cancel() prevents invocation', () => {
    const fn = jest.fn();
    const debounced = debounce(fn, 300);
    debounced('a');
    debounced.cancel();
    jest.advanceTimersByTime(500);
    expect(fn).not.toHaveBeenCalled(); // ✓
  });
});
```

**Q11. What memory and lifecycle cleanup issues does debounce create?**

A: Three categories: (1) **Pending timer after component unmount**: the timeout callback fires after the component is gone, calling `setState` on an unmounted component (React warning) or accessing DOM elements that no longer exist. Fix: always call `debounced.cancel()` in cleanup. (2) **Closure over stale variables**: if `fn` is recreated per render (e.g., an inline arrow function), a new debounced function is created per render but the old timer may still reference the old `fn`. The timer fires the old callback, which may reference outdated state. Fix: stable function reference with `useCallback` or external definition. (3) **Event listeners not removed**: if the debounced function is added as an event listener but the original function is kept elsewhere, `removeEventListener` won't find it (they're different references). Always store the debounced function reference and remove it by the same reference.

**Q12. What is the per-render anti-pattern with debounce in React, and what are the three valid fixes?**

A: The anti-pattern: creating the debounced function inside the component body (not in a ref or memo), so a new closure is created on every render. Each new debounced function has a fresh `timerId = null`, meaning `clearTimeout` of a new `timerId` never cancels the *previous render's* pending timer. In practice: rapid state changes cause rapid re-renders, each spawning a new debounced function, none of which cancel each other — the debounce is completely defeated.

```jsx
// WRONG — new debounce instance per render:
function Search() {
  const handleChange = debounce(search, 300); // ← recreated every render
  return <input onChange={handleChange} />;
}

// Fix 1 — useCallback with stable dependency:
const handleChange = useCallback(debounce(search, 300), []); // ← one instance

// Fix 2 — useRef for stable reference:
const debounced = useRef(debounce(search, 300)).current;

// Fix 3 — define outside component:
const debouncedSearch = debounce(search, 300); // module scope
function Search() { return <input onChange={debouncedSearch} />; }
```

## Topic B: Throttle

### Section B1: Fundamentals

**Q13. What is throttle, and what timing invariant does it preserve?**

A: Throttle ensures a function is invoked **at most once per `limit` milliseconds**, regardless of how many times the throttled wrapper is called. Unlike debounce which waits for silence, throttle creates a regular "pulse" — the function fires at a controlled maximum rate as long as calls keep arriving. The invariant: *at most one invocation per `limit` ms window, measured from the previous invocation*. Throttle is appropriate when events arrive continuously (scroll, mousemove, resize, game loop) and you want regular processing — not just a single fire after the activity stops. A scroll handler throttled at 16ms (~60fps) runs smoothly during scrolling; the same handler debounced at 16ms would never fire during active scrolling.

```
calls:   •••••••••••••••••••••••••••••••••••••••
time:  ──┼──────────────────────────────────────→
         ↑fire  ↑fire  ↑fire  ↑fire  ↑fire
         [limit][limit][limit][limit][limit]

Guarantee: at most 1 invocation per `limit` ms
Unlike debounce: fires DURING continuous input, not after it stops
```

**Q14. What is the difference between timestamp-based and timer-based throttle?**

A: **Timestamp-based** throttle compares `Date.now()` to the time of the last invocation — if enough time has elapsed, invoke and update `lastCallTime`. This is purely reactive: it fires synchronously when called if the window has passed. Advantages: simple, exact timing relative to actual calls, no pending timers. Disadvantage: leading-edge only — if calls stop arriving, the last in-window call is silently dropped. **Timer-based** throttle uses `setTimeout` to schedule the next invocation a fixed delay after the current one. Advantages: can guarantee trailing-edge firing (last call always eventually fires), more predictable timing. Disadvantage: the timer's 4ms minimum delay in browsers means 16ms rAF-style throttles are imprecise. In practice: use timestamp for simple leading-edge throttle; use timestamp + timer for leading + trailing; use rAF for visual updates.

```js
// Timestamp-based (leading only):
function throttle(fn, limit) {
  let lastCall = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastCall >= limit) { // window has passed: invoke
      lastCall = now;
      return fn.apply(this, args);
    }
    // else: silently drop the call
  };
}
// Drawback: calls arriving near the end of a window are dropped — no trailing guarantee
```

**Q15. Why does the trailing edge matter for throttle, and what happens without it?**

A: Without trailing-edge guarantee, the last call in a burst is silently dropped if it arrives within the throttle window. For a scroll handler: the user scrolls, the handler fires at 60fps — but the scroll stops while the handler is "blocked." The final scroll position never triggers a fire because there's no call after the window expires. The UI stays slightly out of sync. With trailing edge: when a call arrives within the window, schedule a future fire for when the window expires. This guarantees the last observed state is always processed eventually. The trailing timer uses `remaining = limit - (now - lastCall)` to fire at exactly the window boundary, not `limit` ms from now — minimizing additional delay.

```
Without trailing — last scroll position is lost:
scrolls: ────•──•──•──•──•──•──(stop)────────────
fires:   ────↑──────↑──────↑─────────────────────→
             T=0   T=limit T=2×limit  (last pos never processed!)

With trailing — last position always fires:
scrolls: ────•──•──•──•──•──•──(stop)────────────
fires:   ────↑──────↑──────↑─────→↑───────────────
             T=0   T=limit T=2×limit  (trailing fires after last call)
```

**Q16. What is requestAnimationFrame throttle, and when is it strictly better than `throttle(fn, 16)`?**

A: `requestAnimationFrame` (rAF) asks the browser to call a function before its next paint, which occurs at the display's refresh rate (~60Hz → ~16.7ms). rAF throttle is better than `throttle(fn, 16)` for three reasons: (1) **Paint alignment**: rAF fires are synchronized with the actual display refresh — updating layout or canvas inside rAF avoids unnecessary work between paints; `setTimeout(fn, 16)` fires independently of the display, potentially causing redundant frames. (2) **Background tab pausing**: rAF pauses automatically when the tab is hidden, saving CPU; `setTimeout` continues firing. (3) **No accumulated timer drift**: rAF is scheduled relative to the browser's internal clock; `setTimeout(16)` accumulates drift (each call is ≥16ms but may be much more under load). Use rAF throttle for all visual updates; use timestamp throttle for non-visual rate limiting (API calls, analytics).

```js
function rafThrottle(fn) {
  let rafId = null;

  const throttled = function(...args) {
    if (rafId !== null) return; // already scheduled for next frame — drop this call

    rafId = requestAnimationFrame(() => {
      rafId = null;
      fn.apply(this, args);
    });
  };

  throttled.cancel = () => {
    if (rafId !== null) { cancelAnimationFrame(rafId); rafId = null; }
  };

  return throttled;
}
// Rate: at most once per display frame (~60fps on 60Hz displays)
// Fires: at the start of the next animation frame, not on a fixed timer
// Pauses: automatically when tab is background — saves battery/CPU
```

**Q17. What is the leading + trailing combined throttle, and what is its guarantee compared to each variant alone?**

A: Combined (leading + trailing) throttle guarantees: (1) **immediate response** to the first call in a window (leading), and (2) **no dropped last event** — if any call arrived during a window, the last one fires at the end of the window (trailing). This is the default behavior of Lodash's `throttle`. The invariant: given continuous input, the wrapped function fires at the *start* of each window (leading) — so calls are processed on a regular schedule. Additionally, if the last call in a burst arrived mid-window, it fires after the window closes (trailing), ensuring the final value is processed. Leading-only drops last values; trailing-only delays first values; combined gives both immediate responsiveness and no dropped tail.

### Section B2: Analysis

**Q18. When does a leading throttle prevent "double-fire on first click" in UI patterns?**

A: If a button's click handler is expensive (network call, heavy computation), a user double-clicking fires it twice almost simultaneously. Leading throttle fires the first click immediately and blocks the second click (which arrives within `limit` ms). Unlike debounce: leading throttle fires *immediately* on the first click and then becomes available again after `limit` ms. Leading debounce also fires immediately but blocks for `delay` ms of silence — for a fast user, this blocks the button too long. For UI buttons, leading throttle (say, 1000ms) gives exactly one immediate response per second: instant feedback, not blocked by a quiet period. Leading debounce would not re-enable until a second after the *last* click — potentially never if the user keeps clicking.

**Q19. What happens when calls stop arriving mid-window in trailing throttle — does the trailing timer still fire?**

A: Yes — the trailing timer fires at the end of the current throttle window regardless of whether calls continue. Once scheduled, the trailing timer runs to completion. If after the trailing fire there are no new calls, the timer is not rescheduled and the throttle becomes idle. This behavior is intentional: it guarantees the last call is always processed. The edge case: if `cancel()` is called before the trailing timer fires, it clears the pending timer, and the last call's arguments are discarded. This is by design — `cancel()` means "abandon all pending work."

**Q20. What is the fundamental behavioral contrast when input is continuous vs bursty?**

A: **Continuous input** (scroll, mousemove — calls never stop): debounce without `maxWait` *never fires*; throttle fires regularly at rate 1/limit. **Bursty input** (typing, window resize with pauses): debounce fires once after each quiet period; throttle fires on the leading edge of each burst (and trailing if configured). The rule of thumb: if the user is "doing something" and you want to track it while they do it → throttle. If you only care about the result after they stop → debounce. This manifests clearly: scroll events call for throttle (update while scrolling); search input calls for debounce (search once user finishes typing a word).

## Topic C: Comparison, Patterns & Advanced

**Q21. What is the "pulse vs silence" distinction between throttle and debounce?**

A: Throttle creates a **regular pulse** at 1/limit Hz — as long as calls arrive, invocations are evenly spaced. Think of it as a metronome that fires while you press the key. Debounce waits for **silence** — the wrapped function only fires after the stream of calls has stopped for `delay` ms. Think of it as an echo that only sounds after the noise stops. The mental model: throttle is *during* activity; debounce is *after* activity ends. A useful test: "should this function fire if the user holds down a key continuously for 10 seconds?" Yes → throttle (fires every `limit` ms for 10 seconds). No → debounce (fires once, 300ms after the user releases the key).

**Q22. What is the practical decision matrix for choosing debounce vs throttle vs neither?**

A:

| Scenario | Pattern | Why |
|---|---|---|
| Search autocomplete | Debounce | Wait for user to finish typing; continuous queries waste resources |
| Window resize layout | Debounce | Recalculate only after resize stops; intermediate sizes unnecessary |
| Auto-save draft | Debounce | Save after user stops editing; not on every keystroke |
| Form validation on input | Debounce | Validate after user finishes a field, not mid-word |
| Scroll position update | Throttle | Track position while scrolling; debounce misses the journey |
| mousemove tooltip | Throttle | Update cursor position regularly, not only after mouse stops |
| Infinite scroll trigger | Throttle | Check scroll position regularly, not only at rest |
| Button click (prevent double-submit) | Leading throttle | Immediate first response; block duplicates for 1s |
| Canvas animation | rAF throttle | Sync with display refresh; pause when tab hidden |
| API rate limiting | Throttle | Ensure at most N requests per second |
| No rate limit needed | Neither | Plain function — rate limiting adds unnecessary complexity |

**Q23. What is the "last call guarantee" — which pattern ensures the final event always fires?**

A: The last call guarantee means: "even if a call arrives inside a throttle/debounce window, it will eventually be processed." **Trailing debounce** provides this by definition — it fires on the *last* call of each burst. **Trailing throttle** provides it by scheduling a timer for the end of the current window when a mid-window call arrives. **Leading-only throttle** does NOT provide it — calls inside the window are silently dropped. Failing to provide this guarantee is the most common production bug in scroll handlers: the scroll stops at an intermediate position, the handler never fires for the final position, and the UI shows stale data (a loading spinner that never resolves, a virtual list that shows the wrong range, a sticky header in the wrong state). For scroll, resize, and input handlers, always ensure trailing edge behavior unless you have an explicit reason not to.

**Q24. How does Lodash's debounce differ from a naive implementation in edge-case handling?**

A: Lodash's debounce handles five edge cases a naive implementation misses: (1) **Recursive calls**: if the debounced function's callback invokes the debounced function again, Lodash detects the recursion and doesn't fire within the same tick; naive implementations may loop. (2) **`this` binding**: Lodash stores `lastContext` on every call and uses it in the trailing invocation — naive implementations using `fn.apply(this, args)` inside `setTimeout` may lose the correct `this`. (3) **`maxWait`**: built-in hybrid throttling for continuous input. (4) **Return value**: Lodash's debounced function returns the result of the last successful invocation (cached from the trailing call); naive implementations return `undefined`. (5) **Clock skew**: uses `Date.now()` internally to detect when system sleep/resume causes timer misfires, falling back to re-scheduling rather than double-firing.

**Q25. State the invariant for debounce and throttle each in one sentence, then state when neither applies.**

A:
- **Debounce invariant**: the wrapped function fires at most once per contiguous burst of calls spaced less than `delay` ms apart — specifically on the leading edge (first call of the burst), the trailing edge (last call + delay), or both, depending on configuration; calls entirely within the burst that are neither the first nor last are discarded.
- **Throttle invariant**: the wrapped function fires at most once per `limit` ms window measured from the previous invocation; calls arriving within the window are either discarded (leading-only) or scheduled as a single trailing call (leading+trailing).
- **When neither applies**: (1) when the function is called at most once anyway (no rate-limiting needed); (2) when the caller explicitly controls the call rate (e.g., a `setInterval` that already fires at the desired rate — adding throttle just adds overhead); (3) when every call must be processed and none dropped (use a queue/batch instead: collect all events, process them on a schedule, never discard any); (4) when the rate-limiting logic belongs in the server/API layer rather than the client.

## Problem 1 — Trailing Debounce

### Problem

Implement `debounce(fn, delay)` — a function that returns a debounced wrapper. The wrapper delays invoking `fn` until `delay` milliseconds have elapsed since the *last* call. Every call within `delay` ms of the previous resets the timer.

```js
const log = debounce(console.log, 300);
log('a'); // t=0
log('b'); // t=100 — resets timer
log('c'); // t=200 — resets timer
// ... silence for 300ms ...
// → console.log('c') fires at t=500 (200ms + 300ms delay)
```

### Pattern Recognition
Closure over a timer ID; `clearTimeout` on every call (cancel previous); `setTimeout` on every call (schedule new); arrow function in setTimeout to preserve `this`.

### Key Insight
`clearTimeout(null)` is a no-op — safe to call even when no timer is pending. This means the implementation never needs to check `if (timerId !== null) clearTimeout(timerId)` — just call `clearTimeout` unconditionally. Setting `timerId = null` after the function fires is not strictly necessary for correctness but signals "no pending timer" for features like `flush()` and `cancel()` that will be added later.

### Solution

```js
function debounce(fn, delay) {
  let timerId = null; // tracks the pending timeout; null = nothing scheduled

  return function debounced(...args) {
    // Step 1: Cancel any previously scheduled invocation
    clearTimeout(timerId);

    // Step 2: Schedule a new invocation `delay` ms from now
    // Arrow function: `this` refers to debounced's call-site `this` (lexical capture)
    timerId = setTimeout(() => {
      timerId = null;         // mark as no longer pending
      fn.apply(this, args);   // invoke with correct context and latest arguments
    }, delay);
  };
}
```

### Trace

```js
const fn = jest.fn();
const debounced = debounce(fn, 300);

t=0:   debounced('a')
       → clearTimeout(null)  [no-op]
       → timerId = setTimeout(fn('a'), 300)  [timer A set for t=300]

t=100: debounced('b')
       → clearTimeout(timer A)  [timer A cancelled — fn('a') will never fire]
       → timerId = setTimeout(fn('b'), 300)  [timer B set for t=400]

t=200: debounced('c')
       → clearTimeout(timer B)  [timer B cancelled]
       → timerId = setTimeout(fn('c'), 300)  [timer C set for t=500]

t=500: timer C fires
       → timerId = null
       → fn.apply(ctx, ['c'])  → fn('c') ✓

Total invocations: 1 (fn('c') only)
Dropped: fn('a') and fn('b') — correct, they were superseded
```

### Edge Cases
- `delay = 0`: still defers to next event loop tick (setTimeout with 0 is async); not the same as calling `fn` synchronously. Each call still cancels the previous.
- Two distinct debounced functions from the same `fn`: each has its own closure with its own `timerId` — independent state, no interference.
- Calling after the timer has fired: `timerId = null` after firing, so the next call correctly schedules a fresh timer.

### Follow-up Questions
- "What does `fn.apply(this, args)` do vs just `fn(...args)`?" — `fn.apply(this, args)` preserves the call-site `this` context. `fn(...args)` calls `fn` with `this = undefined` (strict mode) or global (sloppy mode). For methods on objects (`element.debounced = debounce(element.method, 300)`), `this` must be preserved.
- "Can you implement without `timerId = null`?" — Yes, it still works; `clearTimeout` of an already-fired timer ID is a no-op. But omitting cleanup prevents future features from detecting "nothing is pending."

## Problem 2 — Full-Featured Debounce (Leading Edge, Cancel, Flush)

### Problem

Extend `debounce` to support:
- `{ leading: false, trailing: true }` options (defaults: trailing only)
- `debounced.cancel()` — clears pending timer
- `debounced.flush()` — immediately invokes with latest args, even before delay expires

```js
const d = debounce(fn, 300, { leading: true, trailing: true });
d('a'); // fires immediately (leading)
d('b'); // resets timer
d('c'); // resets timer
// 300ms later: fires with 'c' (trailing, since new calls came after leading)
d.cancel(); // clears any pending timer
d.flush();  // forces immediate invocation if timer is pending
```

### Pattern Recognition
Leading edge requires "is this the first call of a burst?" (`timerId === null`). Trailing edge requires storing `lastArgs` (most recent arguments) because the trailing timer fires long after the original call. `cancel` and `flush` need access to the same closure state.

### Key Insight
`lastArgs === null` serves as a sentinel: after a leading-edge invocation, set `lastArgs = null`. The trailing timer only invokes if `lastArgs !== null` — meaning new calls arrived after the leading fire. This prevents the double-invocation on single isolated calls.

### Solution

```js
function debounce(fn, delay, options = {}) {
  const { leading = false, trailing = true } = options;

  let timerId     = null;
  let lastArgs    = null;   // null = leading just fired, no new calls yet
  let lastContext = null;

  // Shared invoke: calls fn, clears lastArgs/lastContext
  function invoke() {
    const ctx  = lastContext;
    const args = lastArgs;
    lastArgs    = null;
    lastContext = null;
    fn.apply(ctx, args);
  }

  function debounced(...args) {
    lastArgs    = args;
    lastContext = this;

    const isFirstCall = timerId === null; // true = start of a new burst
    clearTimeout(timerId);

    if (leading && isFirstCall) {
      invoke(); // fires immediately; sets lastArgs = null
    }

    timerId = setTimeout(() => {
      timerId = null;
      // Only invoke trailing if: trailing is on AND new calls arrived since leading
      if (trailing && lastArgs !== null) invoke();
      lastArgs = lastContext = null;
    }, delay);
  }

  debounced.cancel = function() {
    clearTimeout(timerId);
    timerId = lastArgs = lastContext = null;
  };

  debounced.flush = function() {
    if (timerId === null) return;    // nothing pending — no-op
    clearTimeout(timerId);
    timerId = null;
    if (lastArgs !== null) invoke(); // invoke with most recent args immediately
  };

  return debounced;
}
```

### Trace

```js
const fn = jest.fn();
const d = debounce(fn, 300, { leading: true, trailing: true });

// — Scenario A: single call —
d('a');
// isFirstCall=true, leading=true → invoke() → fn('a'). lastArgs=null.
// timerId set for t=300.
// Timer fires: lastArgs===null → trailing skipped.
// fn called: 1 time ('a' only) ✓

// — Scenario B: two calls —
d('x');
// isFirstCall=true → invoke() → fn('x'). lastArgs=null. timer set.
d('y');
// isFirstCall=false (timer active). lastArgs='y'. timer reset.
// Timer fires: lastArgs='y' !== null → invoke() → fn('y').
// fn called: 2 times ('x' leading, 'y' trailing) ✓

// — Scenario C: flush() —
d('m');          // leading fires fn('m'). lastArgs=null. timer set.
d('n');          // lastArgs='n'. timer reset.
d.flush();       // clearTimeout; lastArgs='n' !== null → invoke() → fn('n') immediately ✓
// Timer never fires. fn called: 2 times ('m' leading, 'n' via flush) ✓

// — Scenario D: cancel() —
d('p');          // leading fires fn('p'). lastArgs=null. timer set.
d('q');          // lastArgs='q'. timer reset.
d.cancel();      // clearTimeout; lastArgs=null.
// Timer never fires. fn called: 1 time ('p' leading only) ✓
```

### Edge Cases
- `{ leading: true, trailing: false }`: invoke on first call, block all subsequent calls in burst.
- `{ leading: false, trailing: false }`: zero invocations — debounce becomes a no-op.
- `flush()` when `timerId === null` (no pending timer): no-op — the timer already fired.
- `cancel()` during the trailing timer's "fire" callback: the callback accesses `timerId` which is already `null` by then — no state corruption.

### Follow-up Questions
- "What if `fn` itself calls `debounced()` from inside?" — Recursive call: `timerId` is null when `invoke()` runs (it was cleared at line `timerId = null`). So recursive calls start fresh, scheduling a new trailing timer — potentially infinite. Guard with a `isInvoking` flag if recursion is possible.
- "What if `delay` is 0?" — Leading fires synchronously; trailing fires on the next event loop tick. Still correct but the quiet period is effectively "next microtask/macrotask."

## Problem 3 — Throttle (Timestamp-Based)

### Problem

Implement `throttle(fn, limit)` — a function that ensures `fn` is called at most once per `limit` milliseconds. This is a leading-edge throttle: the first call fires immediately, subsequent calls within `limit` ms are silently dropped.

```js
const throttled = throttle(fn, 1000);
throttled('a'); // t=0   → fires immediately
throttled('b'); // t=300 → dropped (within 1000ms of last fire)
throttled('c'); // t=700 → dropped
throttled('d'); // t=1100 → fires (1100ms > 1000ms since last fire)
```

### Pattern Recognition
Timestamp comparison: `Date.now() - lastCallTime >= limit` determines if the throttle window has passed. No timer needed — purely reactive to calls. State: only `lastCallTime` (a number, initialized to 0 so the first call always fires).

### Key Insight
`lastCallTime = 0` as initialization ensures the first call always fires: `Date.now() - 0` is a very large number (milliseconds since epoch), which is always ≥ any reasonable `limit`. This is cleaner than using a boolean flag.

### Solution

```js
function throttle(fn, limit) {
  let lastCallTime = 0; // timestamp of last invocation; 0 → first call always fires

  return function throttled(...args) {
    const now = Date.now();
    const elapsed = now - lastCallTime;

    if (elapsed >= limit) {
      lastCallTime = now;         // update BEFORE invoking (prevents recursive re-entry)
      return fn.apply(this, args);
    }
    // else: within throttle window — silently drop this call
  };
}
```

### Trace

```js
const fn = jest.fn();
const throttled = throttle(fn, 1000);

t=0:    throttled('a'). elapsed = 0ms - 0 = big number >= 1000 → fire. lastCallTime=0ms.
t=300:  throttled('b'). elapsed = 300ms - 0ms = 300 < 1000 → drop.
t=700:  throttled('c'). elapsed = 700ms - 0ms = 700 < 1000 → drop.
t=1100: throttled('d'). elapsed = 1100ms - 0ms = 1100 >= 1000 → fire. lastCallTime=1100ms.
t=1500: throttled('e'). elapsed = 1500ms - 1100ms = 400 < 1000 → drop.
t=2200: throttled('f'). elapsed = 2200ms - 1100ms = 1100 >= 1000 → fire.

fn called 3 times: 'a', 'd', 'f'. Dropped: 'b', 'c', 'e'.
Rate: at most once per 1000ms ✓
```

### Edge Cases
- **No "last call guarantee"**: if 'd' is the last call, it fires. But if 'b' (at t=300) is the last call before silence, it is dropped — the UI may never reflect that state.
- **Concurrent throttled instances**: each call to `throttle()` creates a new closure with its own `lastCallTime` — independent state, no shared mutation.
- **`limit = 0`**: `elapsed >= 0` is always true → every call fires. Throttle becomes a pass-through (no rate limiting).

### Follow-up Questions
- "Is there a risk of the same call firing twice due to floating point?" — No: `Date.now()` returns integer milliseconds. `elapsed >= limit` is an integer comparison, no floating-point rounding.
- "What if the system clock jumps backward (e.g., NTP adjustment)?" — `elapsed` could become negative → `elapsed >= limit` fails → all calls are throttled until the clock catches up. A minor real-world edge case; Lodash guards against it with an extra check.

## Problem 4 — Throttle with Trailing Edge

### Problem

Extend throttle to also guarantee the **last call fires** even if it arrives within the throttle window. When a call arrives during the window, schedule it as a trailing call at the window's expiry.

```js
const throttled = throttle(fn, 1000);
throttled('a'); // t=0   → fires immediately (leading)
throttled('b'); // t=300 → in window: scheduled for t=1000 (trailing)
throttled('c'); // t=700 → in window: replaces scheduled trailing call with 'c'
// t=1000: trailing fires with 'c'
```

### Pattern Recognition
Combine timestamp comparison (leading) with `setTimeout` (trailing). The trailing timer fires `remaining = limit - elapsed` ms from now — at the exact moment the current window expires. Clearing the previous trailing timer ensures at most one trailing call fires.

### Key Insight
`remaining = limit - (now - lastCallTime)` is the time until the current window expires. The trailing timer fires at that exact moment, not `limit` ms from now — preventing an extra delay. Updating `lastCallTime` inside the trailing timer (not just on leading calls) ensures the next leading call correctly measures from the trailing fire's time.

### Solution

```js
function throttle(fn, limit) {
  let lastCallTime = 0;
  let timerId      = null;

  return function throttled(...args) {
    const context  = this;
    const now      = Date.now();
    const elapsed  = now - lastCallTime;

    if (elapsed >= limit) {
      // Leading call: execute immediately
      if (timerId) { clearTimeout(timerId); timerId = null; }
      lastCallTime = now;
      fn.apply(context, args);
    } else {
      // Within window: schedule/reschedule the trailing call
      // remaining = time until current window expires
      clearTimeout(timerId);
      timerId = setTimeout(() => {
        lastCallTime = Date.now();
        timerId = null;
        fn.apply(context, args); // fires with the LATEST args (from most recent call)
      }, limit - elapsed);
    }
  };
}
```

### Trace

```js
const fn = jest.fn();
const t = throttle(fn, 1000);

t=0:    t('a'). elapsed=0ms>=1000→false? No wait: elapsed=Date.now()-0 = very large >=1000 → leading.
        lastCallTime=0ms. fn('a'). timerId=null.

t=300:  t('b'). elapsed=300ms-0ms=300 < 1000 → within window.
        clearTimeout(null). Schedule trailing: setTimeout(fn('b'), 1000-300=700ms) → fires at t=1000.

t=700:  t('c'). elapsed=700-0=700 < 1000 → within window.
        clearTimeout(timer for 'b' at t=1000).  ← 'b' is cancelled!
        Schedule trailing: setTimeout(fn('c'), 1000-700=300ms) → fires at t=1000.

t=1000: trailing timer fires. lastCallTime=1000ms. fn('c'). timerId=null.

t=1500: t('d'). elapsed=1500-1000=500 < 1000 → within window.
        Schedule trailing at t=2000.

t=2000: trailing fires. fn('d').

Total fn calls: 'a' (t=0), 'c' (t=1000), 'd' (t=2000). ✓
Dropped: 'b' (superseded by 'c' in same window). Last call in each window always fires.
```

### Edge Cases
- Trailing timer arg captures `args` at schedule time, not timer-fire time — correct, since we want the latest args from that window.
- If leading and trailing fire within the same ms (elapsed exactly equals limit): the `else` branch is not taken — only leading fires. Trailing is not additionally scheduled.

### Follow-up Questions
- "What if there are no more calls after the leading fire? Does the trailing fire unnecessarily?" — No: the trailing timer is only scheduled when a call arrives within the window. If no calls arrive, `timerId = null` and nothing fires after the leading call.
- "How would you add a `cancel()` method?" — `debounced.cancel = () => { clearTimeout(timerId); timerId = null; };` — identical pattern to debounce cancel.

## Problem 5 — requestAnimationFrame Throttle

### Problem

Implement `rafThrottle(fn)` — a throttled wrapper that uses `requestAnimationFrame` to rate-limit `fn` to one call per display frame (~60fps on 60Hz displays). The throttle should drop calls that arrive before the current frame has been processed.

```js
const update = rafThrottle(renderFrame);
window.addEventListener('scroll', update);
// During fast scrolling: renderFrame is called at most once per browser frame
// When tab is hidden: renderFrame pauses automatically (rAF pauses in hidden tabs)
```

### Pattern Recognition
`requestAnimationFrame` + boolean gate (`rafId !== null` = "already scheduled for this frame"). No `setTimeout`, no `Date.now()`. Cancel with `cancelAnimationFrame`. Leading-frame-edge: the first call schedules execution; subsequent calls in the same frame are dropped.

### Key Insight
`rafId !== null` is the throttle gate — it's set when a frame is scheduled and cleared when the frame fires. The gate stays closed for at most one frame duration (~16.7ms). Unlike `throttle(fn, 16)`, the timing is driven by the browser's internal scheduler, not JavaScript timers, aligning exactly with actual screen refreshes.

### Solution

```js
function rafThrottle(fn) {
  let rafId = null; // null = no frame scheduled; non-null = frame pending

  function throttled(...args) {
    if (rafId !== null) return; // already scheduled for this frame — drop

    // Schedule fn to run at the next animation frame:
    rafId = requestAnimationFrame(() => {
      rafId = null;              // reset gate: ready to accept next call
      fn.apply(this, args);      // execute with captured context and args
    });
  }

  throttled.cancel = function() {
    if (rafId !== null) {
      cancelAnimationFrame(rafId);
      rafId = null;
    }
  };

  return throttled;
}

// Usage: smooth scroll handler
const onScroll = rafThrottle((event) => {
  const scrollY = window.scrollY;
  updateParallax(scrollY);
  checkInfiniteScrollTrigger(scrollY);
});

window.addEventListener('scroll', onScroll, { passive: true });
// Cleanup:
window.removeEventListener('scroll', onScroll);
onScroll.cancel();
```

### Trace

```js
// Timeline (assuming 60fps → frame every ~16.7ms):
t=0ms:    scroll event → rafId=null: schedule rAF. rafId=<id_A>.
t=2ms:    scroll event → rafId=id_A (non-null): DROP.
t=8ms:    scroll event → rafId=id_A: DROP.
t=16.7ms: rAF fires → rafId=null. fn() executes. Ready for next frame.
t=17ms:   scroll event → rafId=null: schedule rAF. rafId=<id_B>.
t=25ms:   scroll event → DROP.
t=33.4ms: rAF fires → fn(). etc.

// When tab hidden (background):
// rAF callbacks pause → fn() pauses → no wasted CPU/battery ✓
// setTimeout(fn, 16) would continue firing every 16ms — wasteful ✗
```

### Edge Cases
- `this` context: arrow function inside rAF callback captures `throttled`'s `this` lexically — correct.
- `args` inside rAF callback: `args` is the closure-captured value from the *first* call in this frame. Subsequent calls in the same frame with different args are dropped — only the first frame's args are used. If latest-args behavior is needed: store `lastArgs` in the closure and update it on every call, use `lastArgs` inside the rAF callback.
- Server-side rendering (Node.js): `requestAnimationFrame` doesn't exist. Guard: `typeof requestAnimationFrame !== 'undefined'` before using, or inject via dependency.

### Follow-up Questions
- "What if we want the *latest* args from the frame, not the first?" — Store `let lastArgs` in closure; update `lastArgs = args` on every call; use `fn.apply(this, lastArgs)` inside the rAF callback.
- "Can you throttle to 30fps instead of 60?" — Yes: only call `fn` on every other frame by tracking a frame counter: `if (frameCount++ % 2 === 0) fn(...)`.

## Problem 6 — Async Debounce Returning a Promise

### Problem

Implement `asyncDebounce(fn, delay)` where `fn` is an async function (or returns a Promise). The returned debounced function also returns a Promise for each call. When a new call supersedes a pending one, the old call's Promise rejects with a special `{ superseded: true }` error. The latest call's Promise resolves/rejects with `fn`'s actual result.

```js
const search = asyncDebounce(fetchResults, 300);

// User types "a", "ab", "abc":
search('a');   // → Promise (rejected: superseded)
search('ab');  // → Promise (rejected: superseded)
search('abc'); // → Promise (resolves: fetchResults('abc') result after 300ms)
```

### Pattern Recognition
Each call creates a new `Promise`. The old Promise's `reject` must be called when a new call arrives. The `pending` closure variable stores `{ resolve, reject }` for the currently outstanding Promise. The `setTimeout` callback resolves or rejects the currently pending Promise.

### Key Insight
A superseded Promise that is never resolved or rejected causes memory leaks and unresolved `await`s. Always explicitly reject superseded Promises. Callers filter the rejection: `catch(err => { if (err.superseded) return; throw err; })`. The `captured = pending` local variable is essential — by the time the `setTimeout` callback fires, `pending` in the closure may have been reassigned by a new call; `captured` holds the correct reference.

### Solution

```js
function asyncDebounce(fn, delay) {
  let timerId = null;
  let pending  = null; // { resolve, reject } for the current in-flight Promise

  return function debounced(...args) {
    // Step 1: Supersede any existing pending Promise
    if (pending) {
      pending.reject(
        Object.assign(new Error('Debounced: call superseded'), { superseded: true })
      );
      pending = null;
    }
    clearTimeout(timerId);

    // Step 2: Create a new Promise for this call
    return new Promise((resolve, reject) => {
      pending = { resolve, reject }; // store in closure
      const captured = pending;      // snapshot: timer callback MUST use this, not `pending`

      timerId = setTimeout(() => {
        timerId = null;
        pending = null; // clear before invoking fn, in case fn calls debounced recursively

        // Step 3: Invoke fn and route its result to captured Promise
        Promise.resolve()
          .then(() => fn.apply(this, args))
          .then(captured.resolve, captured.reject);
      }, delay);
    });
  };
}

// Usage:
const debouncedSearch = asyncDebounce(fetchResults, 300);

async function onInput(query) {
  try {
    const results = await debouncedSearch(query);
    renderResults(results);
  } catch (err) {
    if (err.superseded) return; // silently drop superseded calls
    showError(err);             // real errors (network failure, etc.) propagate
  }
}
```

### Trace

```js
// User types 'a', 'ab', 'abc' rapidly:

t=0:   debouncedSearch('a')
       → pending=null, no previous to supersede
       → Promise_A created. pending={resolve_A, reject_A}. timer set t=300.
       → returns Promise_A (caller awaits)

t=100: debouncedSearch('ab')
       → pending={..._A}: REJECT with {superseded:true}. Promise_A rejects immediately.
       → pending=null. timer cleared.
       → Promise_B created. pending={resolve_B, reject_B}. timer set t=400.
       → returns Promise_B

t=200: debouncedSearch('abc')
       → pending={..._B}: REJECT. Promise_B rejects immediately.
       → pending=null. timer cleared.
       → Promise_C created. pending={resolve_C, reject_C}. timer set t=500.
       → returns Promise_C

t=500: timer fires. timerId=null. pending=null. captured={resolve_C, reject_C}.
       → fetchResults('abc') called
       → If resolves with data: resolve_C(data) → Promise_C resolves ✓
       → If rejects with error: reject_C(error) → Promise_C rejects ✓

// Caller for 'a' and 'ab': catches err.superseded=true → silently returns
// Caller for 'abc': gets actual results ✓
```

### Edge Cases
- `fn` throwing synchronously: `Promise.resolve().then(() => fn(...))` wraps any synchronous throw in a rejection — it routes to `captured.reject`.
- Multiple concurrent callers of the same debounced function: all share the same `pending`. All calls during a burst get superseded except the last — correct, since they're all awaiting the same debounced fetch.
- `cancel()` method: set `pending.reject({ superseded: true }); pending = null; clearTimeout(timerId); timerId = null;`.

### Follow-up Questions
- "What if callers don't want to handle `superseded` rejections?" — Wrap with a helper: `const safeDebouncedSearch = (...args) => debouncedSearch(...args).catch(err => { if (!err.superseded) throw err; })`.
- "Could you use AbortController with asyncDebounce?" — Yes: pass an `AbortSignal` to `fn` and call `abortController.abort()` in the supersede step — this also cancels in-flight network requests, not just the pending Promise.

## Problem 7 — Per-Key Debounce Map

### Problem

Implement `debounceByKey(fn, delay)` — a debounce that creates separate timer states for each unique key, allowing concurrent independent debounces. Useful for debouncing updates to multiple independent entities simultaneously.

```js
const savePost = debounceByKey(saveToAPI, 500);

savePost('post-1', 'Draft v1'); // timer for 'post-1' set
savePost('post-2', 'Another post'); // timer for 'post-2' set (INDEPENDENT)
savePost('post-1', 'Draft v2'); // timer for 'post-1' RESET (not 'post-2')
// After 500ms:
// → saveToAPI('post-1', 'Draft v2') fires
// → saveToAPI('post-2', 'Another post') fires
```

### Pattern Recognition
`Map<key, timerId>` instead of a single `timerId`. Each key gets its own timer state. Cleanup: remove the key from the Map when its timer fires (prevents unbounded Map growth). Optional `cancelAll()` for cleanup on component unmount.

### Key Insight
A single debounce closure cannot handle multiple independent keys — each needs its own `timerId`. A `Map` from key → timerId is the natural data structure. The key (first argument) is used for lookup; the remaining arguments are passed to `fn`.

### Solution

```js
function debounceByKey(fn, delay) {
  const timers = new Map(); // key → timerId

  function debounced(key, ...args) {
    // Cancel existing timer for this key (if any)
    if (timers.has(key)) clearTimeout(timers.get(key));

    // Schedule new timer for this key
    const id = setTimeout(() => {
      timers.delete(key); // cleanup: remove key once timer fires
      fn.apply(this, [key, ...args]);
    }, delay);

    timers.set(key, id);
  }

  // Cancel a specific key's pending timer
  debounced.cancel = function(key) {
    if (key === undefined) {
      // Cancel ALL pending timers
      for (const id of timers.values()) clearTimeout(id);
      timers.clear();
    } else {
      if (timers.has(key)) { clearTimeout(timers.get(key)); timers.delete(key); }
    }
  };

  // Flush: immediately invoke for a specific key
  debounced.flush = function(key, ...args) {
    if (timers.has(key)) {
      clearTimeout(timers.get(key));
      timers.delete(key);
      fn.apply(this, [key, ...args]);
    }
  };

  debounced.pendingKeys = () => [...timers.keys()];

  return debounced;
}

// Real-world: auto-save multiple form fields independently
const autoSave = debounceByKey(saveField, 500);

document.querySelectorAll('[data-field]').forEach(input => {
  input.addEventListener('input', e => {
    autoSave(e.target.dataset.field, e.target.value);
    // Each field gets its own 500ms timer — independent of other fields
  });
});

// On unmount/cleanup:
autoSave.cancel(); // clears all pending saves
```

### Edge Cases
- Map growth: `timers.delete(key)` inside the setTimeout callback prevents memory leaks — completed timers don't linger in the Map.
- Object keys: the `key` is used as a Map key. Objects use reference equality — use strings or numbers as keys for predictable lookup.
- Many concurrent keys: each key has its own independent timer; 1000 concurrent saves create 1000 setTimeout handles. This is fine for typical usage but monitor for pathological cases.

### Follow-up Questions
- "Could you use a `WeakMap` instead of `Map`?" — No: `WeakMap` keys must be objects; strings and numbers are primitives and can't be `WeakMap` keys. `WeakMap` also has no `clear()` method.
- "What if you want per-key *throttle* instead?" — Replace the debounce logic with per-key timestamp tracking: `const lastCalls = new Map(); // key → lastCallTime`.

## Quick Reference — Debounce vs Throttle Decision Tree

```
Do you need to rate-limit a function? →
│
├── Does EVERY call need to eventually be processed (none can be dropped)?
│   └── Use a QUEUE instead of debounce/throttle.
│       Collect events, process in batches. Neither debounce nor throttle guarantees all fire.
│
├── Is input CONTINUOUS (scroll, mousemove, resize — calls keep arriving)?
│   ├── Fire at most once per interval while active → THROTTLE
│   │   ├── Visual/animation update → rafThrottle (browser-synced, pauses in background)
│   │   ├── API calls during drag → throttle with trailing (last state always fires)
│   │   └── Button click (prevent double-submit) → throttle({ leading:true }) at 1000ms
│   └── Fire only AFTER activity stops → DEBOUNCE with maxWait
│       (prevents never-firing during very long continuous input)
│
├── Is input BURSTY (typing, window resize — bursts with pauses)?
│   ├── Respond to RESULT (after user finishes) → DEBOUNCE (trailing)
│   │   ├── Search autocomplete → debounce(search, 300)
│   │   ├── Auto-save → debounce(save, 500)
│   │   └── Form validation on field → debounce(validate, 400)
│   └── Respond IMMEDIATELY, then block → DEBOUNCE (leading)
│       ├── Show loading state immediately → leading debounce
│       └── Trigger an action on first keypress (not last) → leading debounce
│
├── Multiple independent series of calls (by key)?
│   └── debounceByKey(fn, delay) — separate timer per key
│
└── Quick decision table:
    "Should it fire DURING the activity?"    → THROTTLE
    "Should it fire AFTER the activity?"     → DEBOUNCE
    "Should it fire IMMEDIATELY on start?"   → LEADING edge (either)
    "Should the last call always fire?"      → TRAILING edge (either)
    "Guarantee: never fire more than once/N ms" → THROTTLE
    "Guarantee: fire at most once per quiet period" → DEBOUNCE
```

## Common Bugs Checklist

Before shipping any debounce or throttle implementation, verify:

1. **Creating a new debounced/throttled function on every render?** — The most common React bug. `const debounced = debounce(fn, 300)` inside a component body creates a fresh closure (with `timerId = null`) on every render. Every call clears an empty timer and schedules a new one — `clearTimeout` never cancels anything. Fix: define outside the component, use `useRef`, or wrap with `useCallback(() => debounce(fn, 300), [])`.

2. **Using `||` (falsy) instead of `?? {}` for options defaulting?** — `const { leading = false } = options || {}` treats `options = 0` as missing. Prefer `options ?? {}` to guard against only null/undefined, or use a proper default parameter: `function debounce(fn, delay, { leading = false } = {})`.

3. **Not updating `lastCallTime` inside the trailing timer in throttle?** — After the trailing timer fires, `lastCallTime` must be updated to `Date.now()`. Without this, the very next call after a trailing fire has `elapsed = now - oldLastCallTime` which may already be ≥ `limit` (making it a "leading" call) even though the trailing fire just happened — potentially double-firing. Update `lastCallTime` in both leading and trailing branches.

4. **Memory leak: not calling `cancel()` on component unmount?** — A pending `setTimeout` callback captures a closure over state and functions. After unmount, calling `setState` or accessing unmounted DOM inside the timer callback causes React errors or silent corruption. Always return a cleanup function from `useEffect`: `return () => debouncedFn.cancel()`.

5. **`this` context lost in trailing invocation?** — If `lastContext = this` is stored but `fn.apply(lastContext, lastArgs)` is not used in the trailing timer callback, `this` defaults to `undefined` (strict mode) or the global object. Always use `fn.apply(context, args)` instead of `fn(...args)` to preserve the call-site context.

6. **Leading + trailing debounce double-fires on a single call?** — Without the `lastArgs = null` sentinel after the leading invocation, the trailing timer fires for every call including single isolated ones. The fix: set `lastArgs = null` immediately after leading fires; the trailing timer only invokes if `lastArgs !== null` (new calls arrived after leading).

7. **Not clearing the trailing timer when a leading call fires in throttle?** — If a trailing timer is pending from a previous in-window call, and the throttle window then expires, a new leading call fires — but the old trailing timer still runs. This causes double-firing: one leading fire + one stale trailing fire. Fix: `if (timerId) { clearTimeout(timerId); timerId = null; }` at the start of every leading-call branch.

8. **Async debounce: abandoned Promises from superseded calls?** — Every call to an async debounced function creates a new Promise. When a new call supersedes the old, the old Promise must be explicitly rejected (not left pending). Leaving Promises pending causes memory leaks, prevents `async/await` code from continuing, and causes `UnhandledPromiseRejection` if the Promise later rejects due to garbage collection.

9. **rafThrottle: not using `cancelAnimationFrame` for cleanup?** — `clearTimeout` and `cancelAnimationFrame` are different APIs. Calling `clearTimeout(rafId)` does nothing (rafId is an animation frame ID, not a timer ID). Always `cancelAnimationFrame(rafId)` in `cancel()` and on cleanup. Forgetting this means the rAF callback fires after the component unmounts or the handler is "cancelled."

10. **Per-key debounce: not deleting the key after the timer fires?** — Without `timers.delete(key)` inside the setTimeout callback, the Map grows unboundedly with completed (stale) timer IDs. The stale entries have no effect (their timers already fired and their IDs are no longer valid), but they consume memory proportional to the number of unique keys ever used. Always delete the key from the Map in the timer callback.

**Final Tip:** At the 5 YOE level, the decisive signal for any debounce/throttle question is stating *the invariant the pattern enforces and why that invariant matches the problem's semantics* before writing any code. For debounce: *"the invariant is at most one invocation per contiguous burst of calls spaced less than `delay` ms apart — the implementation enforces this by cancelling the pending timer on every call and rescheduling; clearTimeout is the entire mechanism, not a guard but the core operation itself."* For throttle: *"the invariant is at most one invocation per `limit` ms window from the last invocation — the timestamp comparison `Date.now() - lastCallTime >= limit` is the gate; updating `lastCallTime` before invoking (not after) prevents re-entrant calls from slipping through."* And for the leading/trailing distinction: *"leading fires on the first call of a burst to provide immediate responsiveness; trailing fires on the last call of a burst to process the final state; combined fires both but suppresses trailing for single isolated calls (the `lastArgs = null` sentinel after leading prevents double-invocation)."* The candidate who can state these invariants and then derive the implementation from them — rather than memorizing the implementation — demonstrates the kind of reasoning that distinguishes a senior engineer.
