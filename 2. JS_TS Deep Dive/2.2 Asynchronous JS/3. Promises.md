## Topic A: Promise Fundamentals

### Section A1: States, Executor & Timing

**Q1. What is a Promise, what are its three states, and what invariants govern state transitions?**

A: A Promise is an object representing the eventual result of an asynchronous operation. It is always in exactly one of three states:

**Pending**: the initial state — the async operation is still in progress. The Promise holds neither a value nor a reason.

**Fulfilled**: the operation completed successfully. The Promise holds an immutable value, accessible via `.then(onFulfilled)`.

**Rejected**: the operation failed. The Promise holds an immutable reason (typically an `Error`), accessible via `.then(undefined, onRejected)` or `.catch(onRejected)`.

Four invariants that cannot be violated: (1) **One transition only** — a Promise transitions from pending to fulfilled or rejected exactly once; it can never go backward or change again. (2) **Immutable settlement** — once fulfilled or rejected, the value/reason is frozen; future `.then()` calls on the same Promise always receive the exact same value. (3) **Asynchronous delivery** — `.then()` handlers are always called asynchronously (as microtasks), even if the Promise is already settled when the handler is attached. (4) **Single value** — a Promise carries exactly one value or one reason, never multiple.

```js
const p = Promise.resolve(42);
// p is permanently fulfilled with 42.

p.then(v => console.log(v)); // logs 42 (asynchronously — microtask)
p.then(v => console.log(v)); // also logs 42 — same value, forever

// Calling resolve/reject multiple times — only first call counts:
const q = new Promise((resolve, reject) => {
  resolve(1);   // ← this one wins
  resolve(2);   // ignored
  reject('oops'); // ignored
});
q.then(v => console.log(v)); // 1
```

**Q2. What does the Promise constructor's executor function do, when does it run, and how does it interact with the resolve and reject functions?**

A: The executor is the function passed to `new Promise(executor)`. It runs **synchronously** — during the constructor call, before the constructor returns. It receives two functions: `resolve(value)` and `reject(reason)`, injected by the Promise implementation. Calling `resolve(value)` transitions the Promise to fulfilled with `value`. Calling `reject(reason)` transitions it to rejected with `reason`. The first call wins; subsequent calls are silently ignored. Throwing inside the executor is equivalent to calling `reject(thrownError)` — the Promise is rejected with the thrown value.

```js
console.log('before');

const p = new Promise((resolve, reject) => {
  console.log('inside executor');  // ← runs SYNCHRONOUSLY, before constructor returns
  resolve(42);                     // transitions Promise to fulfilled
  console.log('after resolve');    // ← still runs! resolve() doesn't stop executor
});

console.log('after new Promise');

p.then(v => console.log('then:', v)); // ← scheduled as microtask

console.log('end of sync code');

// Output order:
// before
// inside executor
// after resolve
// after new Promise
// end of sync code
// then: 42        ← microtask runs after all sync code
```

**Q3. What is the microtask queue, how does it differ from the macrotask queue, and what are the scheduling rules for Promise callbacks?**

A: JavaScript's event loop manages two types of queues: **macrotask queue** (also called task queue) and **microtask queue**. After the current script (or macrotask) finishes, the event loop drains the entire microtask queue before pulling the next macrotask. This means microtasks run to completion before any macrotask, rendering, or I/O callback fires.

Promise `.then()` / `.catch()` / `.finally()` callbacks are microtasks. `setTimeout`, `setInterval`, I/O callbacks, and `requestAnimationFrame` are macrotasks. `queueMicrotask()` explicitly schedules a microtask.

```js
console.log('1 - sync');

setTimeout(() => console.log('5 - setTimeout (macrotask)'), 0);

Promise.resolve()
  .then(() => console.log('3 - promise microtask 1'))
  .then(() => console.log('4 - promise microtask 2'));

queueMicrotask(() => console.log('2 - queueMicrotask'));

// Output:
// 1 - sync              ← current task (sync code)
// 2 - queueMicrotask    ← microtask queue drained first
// 3 - promise microtask 1
// 4 - promise microtask 2
// 5 - setTimeout        ← only now does the next macrotask run

// Key rule: after EVERY task (macrotask), ALL pending microtasks run before the next task.
// New microtasks added during microtask processing also run before the next macrotask.
```

**Q4. What is the `.then()` contract — what can its handlers return, and what promise does it produce?**

A: `.then(onFulfilled, onRejected)` always returns a **new** Promise (never the same one). The new Promise's state is determined by what the called handler returns or throws:

| Handler action | New Promise state |
|---|---|
| Returns a non-thenable value `v` | Fulfilled with `v` |
| Returns `undefined` (no explicit return) | Fulfilled with `undefined` |
| Throws an error `e` | Rejected with `e` |
| Returns a Promise P | Adopts P's state (flattened — see Q7) |
| Returns any thenable | Assimilated — adopts that thenable's eventual state |
| Handler is `null`/`undefined`/not a function | State passes through (input fulfillment/rejection propagates to output) |

```js
Promise.resolve(1)
  .then(v => v + 1)          // returns 2 → new promise fulfilled with 2
  .then(v => { throw v; })   // throws 2 → new promise rejected with 2
  .then(v => v * 10)         // skipped (rejection passes through this fulfillment handler)
  .catch(e => e * 10)        // catches 2 → returns 20 → new promise fulfilled with 20
  .then(v => console.log(v)) // 20

// Pass-through for non-functions:
Promise.reject('error')
  .then(null, undefined)     // not functions → rejection passes through
  .catch(e => console.log(e)); // 'error'
```

**Q5. How does `.catch()` differ from passing a rejection handler as the second argument to `.then()`, and why does the difference matter?**

A: `.catch(fn)` is exactly equivalent to `.then(undefined, fn)` — it only attaches a rejection handler, leaving the fulfillment handler slot empty. The critical behavioral difference concerns error propagation within the same `.then()` call:

`.then(onFulfilled, onRejected)` — if `onFulfilled` **throws**, the `onRejected` in the same call does **NOT** catch it. The `onRejected` only catches rejections from the Promise the `.then()` is called on, not errors thrown by `onFulfilled`.

`.then(onFulfilled).catch(onRejected)` — the `.catch()` is a separate step; it catches both rejections from the original Promise (that propagated through the `.then()`) AND errors thrown by `onFulfilled`.

```js
// Scenario: onFulfilled throws an error:

// Pattern 1: .then(f, r) — onRejected does NOT catch f's throws:
Promise.resolve('ok')
  .then(
    v => { throw new Error('oops'); }, // throws!
    e => console.log('caught:', e)      // NOT called — this catches input rejection only
  )
  .catch(e => console.log('outer catch:', e.message)); // 'outer catch: oops' ← catches it

// Pattern 2: .then(f).catch(r) — catch handles BOTH:
Promise.resolve('ok')
  .then(v => { throw new Error('oops'); }) // throws
  .catch(e => console.log('caught:', e.message)); // 'caught: oops' ✓

// Best practice: use .catch() separately for error recovery in chains.
// Use .then(f, r) only when you need to treat input-rejection differently from f's errors.
```

## Topic B: Promise Chaining

### Section B1: Chaining Mechanics

**Q6. How does promise chaining work — how do values and rejections thread through a chain?**

A: Each `.then()` / `.catch()` / `.finally()` returns a new Promise, making chaining possible. Values and errors flow through the chain according to simple rules: **fulfilled values skip rejection handlers** (`.catch()`), and **rejections skip fulfillment handlers** (`.then(onFulfilled)`), until a compatible handler is found. Once a handler runs, the chain continues from the value it returns (or the error it throws). A `.catch()` that returns normally "recovers" — the chain continues in a fulfilled state from that point.

```
Promise.resolve(1)        (fulfilled: 1)
  .then(v => v + 1)       (fulfilled: 2)  ← runs
  .then(v => v * 10)      (fulfilled: 20) ← runs
  .then(v => { throw v }) (rejected: 20)  ← throws
  .then(v => v + 1)       (rejected: 20)  ← SKIPPED (fulfillment handler, but rejected)
  .catch(e => e - 5)      (fulfilled: 15) ← catches, returns 15 → recovered!
  .then(v => v * 2)       (fulfilled: 30) ← runs again ✓

// A critical pattern — returning from catch recovers the chain:
fetch('/api/data')
  .then(r => r.json())
  .catch(() => ({ items: [] }))  // on failure, use a default value
  .then(data => render(data));   // always runs, with real or default data
```

**Q7. What is "promise flattening" (assimilation), and why can't `Promise<Promise<T>>` exist?**

A: When a `.then()` handler returns a Promise (or any thenable), the outer Promise does **not** fulfill with that inner Promise as its value — instead it **waits** for the inner Promise to settle and adopts its state. This "assimilation" or "flattening" is built into the Promise specification. `Promise.resolve(promise)` also flattens — it returns `promise` itself if `promise` is a native Promise. This design prevents accidental nesting of Promises and makes async chain composition natural: you return a Promise from a handler to sequence asynchronous steps.

```js
// Without flattening (hypothetical):
// .then(v => fetch('/api')) would produce Promise<Promise<Response>> — awkward.

// With flattening (actual behavior):
fetch('/api/user')
  .then(r => r.json())           // returns a Promise<user>
  .then(user => fetch(`/api/posts/${user.id}`))  // returns a Promise<Response>
  // ↑ chain waits for the inner Promise — NOT fulfilled with Promise<Response>
  .then(r => r.json())           // called with the Response, not a Promise
  .then(posts => console.log(posts)); // called with the parsed data ✓

// Promise.resolve flattening:
const p = Promise.resolve(42);
const q = Promise.resolve(p); // q === p (same reference for native Promises)
console.log(p === q); // true

// Thenable assimilation (any object with .then):
Promise.resolve({
  then(resolve) { resolve('from thenable'); }
}).then(v => console.log(v)); // 'from thenable' — thenable was assimilated
```

**Q8. What does `.finally()` do, how does it differ from `.then(f, f)`, and what is its "pass-through" behavior?**

A: `.finally(fn)` registers a handler called when the Promise **settles** — regardless of whether it fulfilled or rejected. The handler receives **no arguments** (it can't see the value or reason). Its crucial characteristic: it passes the **original** value or reason through to the next handler in the chain, unless the `finally` handler itself throws or returns a rejected Promise.

`.then(f, f)` (same function for both) is **not** equivalent: the function receives the value/reason as an argument, and its return value determines the next state — effectively replacing the original value.

```js
// .finally() passes through the original value:
Promise.resolve(42)
  .finally(() => console.log('cleanup'))  // logs 'cleanup', returns undefined
  .then(v => console.log(v));             // 42 — original value passed through ✓

// .then(f, f) replaces the value:
Promise.resolve(42)
  .then(
    () => console.log('done'),  // returns undefined
    () => console.log('done')   // same function
  )
  .then(v => console.log(v));  // undefined — original value 42 is LOST ✗

// .finally() also passes through rejections:
Promise.reject('error')
  .finally(() => console.log('cleanup')) // logs 'cleanup'
  .catch(e => console.log(e));           // 'error' — rejection passed through ✓

// .finally() CAN override if it throws or rejects:
Promise.resolve(42)
  .finally(() => { throw new Error('finally error'); }) // overrides the 42
  .catch(e => console.log(e.message)); // 'finally error' — original 42 discarded

// Practical use: always close resources, commit metrics, hide spinners:
showSpinner();
fetch('/api/data')
  .then(r => r.json())
  .then(render)
  .catch(handleError)
  .finally(() => hideSpinner()); // always hides, whether success or failure
```

**Q9. What are the error propagation rules in a promise chain, and how do you recover from a rejection mid-chain?**

A: Rejections propagate "forward" through the chain, **skipping** all `.then(onFulfilled)` handlers until a rejection handler (`.catch()` or `.then(_, onRejected)`) is reached. Once a rejection handler runs, its return value determines the next state:

- Returns a non-throwing value → chain recovers, continues as fulfilled.
- Throws or returns a rejected Promise → rejection continues propagating with the new reason.

This creates two modes: **recovery** (`.catch()` returns a fallback value) and **re-throw** (`.catch()` throws or explicitly returns `Promise.reject()`). A `.catch()` that does not re-throw always recovers the chain — this is a common bug when developers write a `.catch()` expecting the chain to remain rejected.

```js
// Recovery vs re-throw:

// Recovery: chain continues as fulfilled after .catch()
Promise.reject(new Error('fail'))
  .catch(e => 'fallback')          // returns 'fallback' → fulfilled
  .then(v => console.log(v));      // 'fallback' ✓

// Re-throw: rejection propagates with new reason
Promise.reject(new Error('original'))
  .catch(e => {
    console.error('logging:', e.message);
    throw new Error('wrapped'); // re-throw!
  })
  .catch(e => console.log(e.message)); // 'wrapped'

// Accidental recovery (common bug):
Promise.reject(new Error('fail'))
  .catch(e => console.log('handled:', e.message)) // RETURNS undefined → recovers!
  .then(v => console.log('fulfilled with:', v));   // 'fulfilled with: undefined' ← surprise!
// Fix: if you want rejection to continue, always re-throw or return Promise.reject()
```

**Q10. What are unhandled promise rejections, and how should they be handled?**

A: An unhandled rejection occurs when a Promise rejects and no rejection handler (`.catch()`) is attached before the event loop tick ends (in practice, before the microtask queue for that rejection drains). Node.js emits an `unhandledRejection` event; browsers dispatch an `unhandledrejection` event on `window`. Modern Node.js (v15+) terminates the process with a non-zero exit code on unhandled rejections. The fix: always attach a `.catch()` at the end of any promise chain, or use `async/await` with `try/catch`. For application-level safety, register a global handler as a last resort — but this should never replace per-chain handling.

```js
// Risky: rejection with no catch
const p = Promise.reject(new Error('unhandled')); // triggers unhandledRejection event
// Fix:
const q = Promise.reject(new Error('handled')).catch(e => logError(e));

// Global fallback (last resort — not a substitute for proper handling):
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled rejection:', reason);
  process.exit(1); // optional: exit on any unhandled rejection
});

// Common cause — async function's returned promise is not awaited:
async function riskyOp() { throw new Error('oops'); }
riskyOp(); // returned Promise is ignored → unhandled rejection
// Fix:
riskyOp().catch(e => console.error(e));
// or: await riskyOp() inside an async function with try/catch
```

## Topic C: Static Combinators

### Section C1: The Four Combinators

**Q11. How does `Promise.all` work, and what is the fail-fast behavior?**

A: `Promise.all(iterable)` takes any iterable of promises (or values) and returns a single Promise that:

- **Fulfills** when **all** input promises fulfill → the result value is an array of all fulfilled values, **in the same order as the input** (not arrival order).
- **Rejects** immediately when **any** input promise rejects → rejects with that first rejection reason.

The fail-fast behavior: if one promise rejects, `Promise.all` rejects immediately without waiting for the others. The other promises are **not cancelled** — they continue running (JavaScript has no native Promise cancellation). Their results are simply ignored.

```js
// Fulfilled when all fulfill:
Promise.all([
  Promise.resolve(1),
  Promise.resolve(2),
  Promise.resolve(3),
]).then(([a, b, c]) => console.log(a, b, c)); // 1 2 3 — in INPUT order, not arrival order

// Rejects on first rejection:
Promise.all([
  Promise.resolve(1),
  Promise.reject('error'), // rejects immediately
  Promise.resolve(3),      // this will still resolve but result is discarded
]).catch(e => console.log('rejected:', e)); // 'rejected: error'

// Values (non-promises) are wrapped in Promise.resolve():
Promise.all([1, 'two', Promise.resolve(3)]).then(console.log); // [1, 'two', 3]

// Empty iterable fulfills immediately with []:
Promise.all([]).then(v => console.log(v)); // []
```

**Q12. How does `Promise.allSettled` work, and when should you use it instead of `Promise.all`?**

A: `Promise.allSettled(iterable)` returns a Promise that fulfills when **all** input promises have settled (fulfilled or rejected). It **never rejects**. The result is an array of "outcome objects" — one per input, in input order:

- `{ status: 'fulfilled', value: <value> }` for fulfilled promises.
- `{ status: 'rejected', reason: <reason> }` for rejected promises.

Use `Promise.allSettled` when operations are **independent** and you need all results regardless of partial failure — batch processing, firing multiple side effects, sending metrics. Use `Promise.all` when operations must **all succeed** for the result to be usable and a single failure makes the whole thing meaningless.

```js
const results = await Promise.allSettled([
  fetch('/api/user').then(r => r.json()),
  fetch('/api/stats').then(r => r.json()),
  fetch('/api/broken-endpoint').then(r => r.json()), // will fail
]);

// results is always an array, always fulfilled:
results.forEach((outcome, i) => {
  if (outcome.status === 'fulfilled') {
    console.log(`Request ${i} succeeded:`, outcome.value);
  } else {
    console.error(`Request ${i} failed:`, outcome.reason);
  }
});

// Extract successes and failures:
const successes = results.filter(r => r.status === 'fulfilled').map(r => r.value);
const failures  = results.filter(r => r.status === 'rejected').map(r => r.reason);
```

**Q13. How does `Promise.race` work, what is the "abandoned promise" problem, and what happens with an empty iterable?**

A: `Promise.race(iterable)` returns a Promise that adopts the state of whichever input promise **settles first** — fulfilled or rejected. All other promises continue running but their results are discarded. The "abandoned promise" problem: the other promises aren't cancelled — they run to completion, consuming resources (network connections, CPU), just without any consumer. This is especially problematic for timeout patterns where a slow fetch continues consuming resources even after the timeout fires.

Empty iterable edge case: `Promise.race([])` returns a Promise that **never settles** — it stays pending forever. This is a common source of silent bugs (a function that's supposed to resolve never does).

```js
// Race between two resolvers:
Promise.race([
  new Promise(r => setTimeout(() => r('slow'), 1000)),
  new Promise(r => setTimeout(() => r('fast'), 100)),
]).then(v => console.log(v)); // 'fast' — arrives first ✓

// Race adopts FIRST SETTLEMENT — including rejections:
Promise.race([
  new Promise((_, r) => setTimeout(() => r('rejected fast'), 50)),
  new Promise(r => setTimeout(() => r('fulfilled slow'), 1000)),
]).catch(e => console.log('rejected:', e)); // 'rejected: rejected fast' ✓

// Empty iterable — NEVER SETTLES (pending forever):
Promise.race([]).then(() => console.log('never')); // this log never happens!

// Abandoned promise problem with timeout:
function fetchWithTimeout(url, ms) {
  const controller = new AbortController(); // solution: use AbortController
  const timeout = setTimeout(() => controller.abort(), ms);

  return Promise.race([
    fetch(url, { signal: controller.signal }),
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error('Timeout')), ms)
    ),
  ]).finally(() => clearTimeout(timeout)); // always clear the timer
}
```

**Q14. How does `Promise.any` work, when does it reject, and how does it differ from `Promise.race`?**

A: `Promise.any(iterable)` (ES2021) returns a Promise that fulfills with the **first fulfillment** among its inputs, ignoring rejections unless **all** inputs reject. If all reject, it rejects with an `AggregateError` — a special error subclass that wraps all individual rejection reasons in an array (`.errors` property).

`Promise.any` vs `Promise.race`: race adopts the first **settlement** (fulfilled or rejected — whichever settles first); `any` only adopts the first **fulfillment** (ignores rejections until none remain). Use `any` when you want "first success" semantics; use `race` when you also want to react to fast failures.

```js
// First fulfillment wins (rejections ignored):
Promise.any([
  Promise.reject('fail 1'),              // rejected — ignored
  new Promise(r => setTimeout(() => r('slow ok'), 500)), // fulfilled late
  new Promise(r => setTimeout(() => r('fast ok'), 100)), // fulfilled fast
]).then(v => console.log(v)); // 'fast ok' ✓

// ALL reject → AggregateError:
Promise.any([
  Promise.reject('error A'),
  Promise.reject('error B'),
  Promise.reject('error C'),
]).catch(err => {
  console.log(err instanceof AggregateError); // true
  console.log(err.message);  // 'All promises were rejected'
  console.log(err.errors);   // ['error A', 'error B', 'error C']
});

// Empty iterable → rejects immediately with AggregateError:
Promise.any([]).catch(e => console.log('empty:', e.message)); // 'All promises were rejected'
```

**Q15. How do the four static combinators compare on fulfillment condition, rejection condition, and result shape?**

A:

| Combinator | Fulfills when | Rejects when | Fulfillment result | Rejection reason |
|---|---|---|---|---|
| `Promise.all` | **ALL** fulfill | **ANY ONE** rejects | Array of values (input order) | First rejection reason |
| `Promise.allSettled` | **ALL settle** (never rejects) | — | Array of `{status, value/reason}` | — |
| `Promise.race` | **FIRST** settles (fulfilled) | **FIRST** settles (rejected) | First fulfilled value | First rejection reason |
| `Promise.any` | **FIRST** fulfills | **ALL** reject | First fulfilled value | `AggregateError` of all reasons |

```
Mnemonic:
  all:         AND logic for fulfillment, OR logic for rejection
  allSettled:  always fulfills — gives you everything
  race:        first to FINISH (fulfilled or rejected)
  any:         first to SUCCEED — last resort for rejection
```

## Topic D: Advanced & Interview-Style Questions

**Q16. What is the exact relationship between `async/await` and Promises?**

A: `async/await` is syntactic sugar over Promises — it compiles down to Promise chains. An `async function` always returns a Promise: if the function body returns a value `v`, the returned Promise fulfills with `v`; if it throws, the returned Promise rejects with the thrown error. `await expr` pauses the async function's execution, waits for `expr` to settle (wrapping non-Promises in `Promise.resolve()`), and resumes with the fulfilled value — or throws the rejection reason, which `try/catch` can intercept.

Understanding the desugaring: `await` in an async function is the equivalent of `.then()` where the code after `await` is the fulfillment handler. An uncaught rejection from `await` is the equivalent of `.catch()`. Every `async` function is a generator-like state machine that yields control to the event loop when it hits an `await`, and is resumed (via microtask) when the awaited Promise settles.

```js
// These are semantically equivalent:

// async/await style:
async function fetchUser(id) {
  try {
    const res  = await fetch(`/api/user/${id}`);
    const user = await res.json();
    return user;
  } catch (e) {
    throw new Error(`Failed to fetch user: ${e.message}`);
  }
}

// Promise chain equivalent:
function fetchUserChain(id) {
  return fetch(`/api/user/${id}`)
    .then(res => res.json())
    .catch(e => Promise.reject(new Error(`Failed to fetch user: ${e.message}`)));
}

// async/await pitfalls:
async function parallel() {
  // WRONG: sequential (awaits each before starting the next):
  const a = await fetch('/a');
  const b = await fetch('/b'); // starts only after /a completes

  // RIGHT: parallel (starts both, then awaits both):
  const [ra, rb] = await Promise.all([fetch('/a'), fetch('/b')]);
}
```

**Q17. What are the most common Promise anti-patterns, and what replaces each?**

A:

**1. The Promise Constructor Anti-Pattern** (also called "the deferred anti-pattern"): wrapping a function that already returns a Promise inside `new Promise()`. Redundant, hides errors (the outer executor can't catch rejections from the inner Promise), and creates unnecessary complexity.

```js
// Anti-pattern: double-wrapping
function fetchData(url) {
  return new Promise((resolve, reject) => {  // ← unnecessary!
    fetch(url)
      .then(r => r.json())
      .then(resolve)
      .catch(reject);
  });
}

// Fix: just return the existing promise
function fetchData(url) {
  return fetch(url).then(r => r.json());
}
```

**2. Missing `return` in `.then()` handler**: if you forget `return`, the handler returns `undefined`, breaking the chain.

```js
// Bug: forgot return
fetch('/api/data')
  .then(r => { r.json(); })  // returns undefined — json() result lost!
  .then(data => render(data)); // data is undefined

// Fix:
  .then(r => r.json())  // or: r => { return r.json(); }
```

**3. Swallowing errors in `.catch()`**: a `.catch()` that doesn't re-throw converts a rejection into a fulfilled `undefined`, silently hiding errors.

```js
// Bug: silent swallow
fetch('/api/data')
  .catch(e => console.error(e)) // logs error but returns undefined
  .then(data => render(data));   // render(undefined) — may cause silent bugs
```

**4. `await` inside a `forEach`**: `async` callbacks inside `.forEach()` are not awaited — the `forEach` returns before any of the async work completes.

```js
// Bug: forEach doesn't await
async function processAll(items) {
  items.forEach(async item => { await process(item); }); // ← won't wait!
}

// Fix: for...of, or Promise.all with map:
async function processAll(items) {
  for (const item of items) { await process(item); }      // sequential
  // or: await Promise.all(items.map(item => process(item))); // parallel
}
```

**Q18. In one sentence each, state what each Promise method does.**

A:
- **`new Promise(executor)`**: creates a Promise and immediately runs `executor(resolve, reject)` synchronously to start the async operation.
- **`.then(onFulfilled, onRejected)`**: returns a new Promise; calls `onFulfilled` with the value if fulfilled or `onRejected` with the reason if rejected; passes through if the relevant handler is absent.
- **`.catch(onRejected)`**: shorthand for `.then(undefined, onRejected)` — handles only rejections; fulfillments pass through.
- **`.finally(fn)`**: calls `fn` (with no arguments) on any settlement; passes the original value or reason through to the next handler unless `fn` throws or returns a rejected Promise.
- **`Promise.resolve(v)`**: returns a Promise fulfilled with `v`, or returns `v` itself if `v` is already a native Promise.
- **`Promise.reject(r)`**: returns a Promise that is already rejected with `r`; always attach `.catch()`.
- **`Promise.all(iter)`**: fulfills with an array of all values when all settle fulfilled; rejects immediately on the first rejection.
- **`Promise.allSettled(iter)`**: always fulfills (never rejects) after all promises settle; delivers an array of `{status, value/reason}` outcome objects.
- **`Promise.race(iter)`**: adopts the state (fulfilled or rejected) of whichever promise settles first; never settles if given an empty iterable.
- **`Promise.any(iter)`**: fulfills with the first fulfilled value, ignoring rejections; rejects with `AggregateError` only if all promises reject.

## Implementation 1 — Sequential Pipeline with Error Recovery

### Challenge
Fetch a user, then their posts, then enrich each post with comments — a three-step sequential dependency chain where each step depends on the previous result. Handle partial failures gracefully: if comments fail for a post, use an empty array rather than failing the whole request.

### Pattern
Promise chaining for sequential async steps — return a Promise from each `.then()` to sequence dependent operations; use intermediate `.catch()` for per-step recovery.

### Key Insight
Returning a Promise from a `.then()` handler causes the chain to wait for that inner Promise before proceeding — this is the flattening behavior. Intermediate `.catch()` handlers can recover partial failures without aborting the entire chain.

### Implementation

```js
// Simulate API calls (replace with real fetch in production):
const api = {
  getUser: (id)    => fetch(`/api/users/${id}`).then(r => { if (!r.ok) throw new Error(`User ${id} not found`); return r.json(); }),
  getPosts: (uid)  => fetch(`/api/posts?userId=${uid}`).then(r => r.json()),
  getComments: (pid) => fetch(`/api/comments?postId=${pid}`).then(r => r.json()),
};

function fetchUserFeed(userId) {
  return api.getUser(userId)                        // Step 1: fetch user
    .then(user => {
      // Step 2: fetch posts for this user
      return api.getPosts(user.id)                  // ← returning Promise sequences the chain
        .then(posts => ({ user, posts }));           // bundle user + posts together
    })
    .then(({ user, posts }) => {
      // Step 3: enrich each post with comments — parallel within a sequential step
      const enrichedPosts = posts.map(post =>
        api.getComments(post.id)
          .then(comments => ({ ...post, comments }))
          .catch(() => ({ ...post, comments: [] }))  // per-post recovery: empty array on failure
      );
      return Promise.all(enrichedPosts)              // wait for ALL comment fetches
        .then(posts => ({ user, posts }));
    })
    .catch(err => {
      // Top-level catch: user not found, network error, etc.
      console.error('Feed fetch failed:', err.message);
      throw err; // re-throw — don't swallow, let the caller handle
    });
}

// Usage:

  .then(({ user, posts }) => {
    console.log(`${user.name} has ${posts.length} posts`);
    posts.forEach(p => console.log(`  "${p.title}": ${p.comments.length} comments`));
  })
  .catch(err => showError(err.message));
```

- **Latency**: sum of sequential steps (user → posts → parallel comments). Total ≈ 3 RTTs (user + posts + comments in parallel).

- **Failure modes**: user-not-found → entire chain rejects; comments fail → per-post recovery (empty array); posts fail → chain rejects (no recovery added, by design).

### Edge Cases
- **User with 0 posts**: `Promise.all([])` fulfills immediately with `[]`. Feed has `posts: []`.
- **No internet**: `fetch()` rejects immediately. Top-level `.catch()` catches and re-throws.
- **User step succeeds but posts step rejects**: the `.catch()` inside step 2's `.then()` is not present — rejection propagates to the top-level `.catch()`. Intentional: without posts, the feed is meaningless.

### Extensions
- **Pagination**: replace `getPosts` with an async generator that pages through results.
- **Caching**: wrap each `api.*` call with a memoize layer that returns a cached Promise if the same ID was fetched recently.
- **Cancellation**: pass an `AbortSignal` to each `fetch()` call and check it before each step.

## Implementation 2 — Parallel Data Fetching with `Promise.all`

### Challenge
Fetch independent data for a dashboard — user profile, activity stats, and notifications — as fast as possible. All three are needed before rendering; a single failure should abort the whole render with a clear error.

### Pattern
`Promise.all` for parallel independent fetches — start all requests simultaneously, wait for all to complete, destructure the results array.

### Key Insight
Sequential `await` chains are the most common async performance anti-pattern: `const a = await fetch('/a'); const b = await fetch('/b')` takes 2 RTTs. `Promise.all([fetch('/a'), fetch('/b')])` takes 1 RTT (the longer of the two). For N independent requests, parallel is O(max latency) vs sequential O(sum of latencies).

### Implementation

```js
async function loadDashboard(userId) {
  // Start ALL three requests simultaneously — do NOT await individually
  const [user, stats, notifications] = await Promise.all([
    fetchUser(userId),
    fetchStats(userId),
    fetchNotifications(userId),
  ]);
  // Arrives here when ALL three have completed. Any rejection aborts all.
  return { user, stats, notifications };
}

// With typed error handling and request labeling:
async function loadDashboardSafe(userId) {
  const requests = {
    user:          fetchUser(userId),
    stats:         fetchStats(userId),
    notifications: fetchNotifications(userId),
  };

  try {
    const [user, stats, notifications] = await Promise.all(Object.values(requests));
    return { user, stats, notifications };
  } catch (err) {
    // Identify which request failed:
    const results = await Promise.allSettled(Object.values(requests));
    const failed = Object.keys(requests)
      .filter((_, i) => results[i].status === 'rejected')
      .map((key, i) => `${key}: ${results[i].reason?.message}`);
    throw new Error(`Dashboard load failed (${failed.join(', ')})`);
  }
}

// Anti-pattern comparison:
async function loadDashboardSlow(userId) {
  const user          = await fetchUser(userId);          // ← waits 200ms
  const stats         = await fetchStats(userId);         // ← waits ANOTHER 150ms
  const notifications = await fetchNotifications(userId); // ← waits ANOTHER 100ms
  return { user, stats, notifications };
  // Total: ~450ms  vs  ~200ms with Promise.all (dominated by slowest)
}
```

            Promise.all still pending (waiting for user)

### Complexity
- **Latency**: O(max(t₁, t₂, ..., tₙ)) — total time equals the slowest request.
- **Concurrency**: all N requests in flight simultaneously.
- **Failure**: any single rejection → entire Promise.all rejects. Other requests continue but results ignored.

### Edge Cases
- **One request consistently fails**: use `Promise.allSettled` if you want partial results. Use `Promise.all` only when all results are required.
- **Large N (100+ parallel requests)**: may overwhelm the server or hit browser connection limits (~6 concurrent per origin). Use a concurrency limiter (e.g., process in batches of 10).
- **Non-promise values in the array**: `Promise.all([1, Promise.resolve(2)])` works — plain values are wrapped in `Promise.resolve()`.

### Extensions
- **Concurrency limit**: implement a pool that keeps at most N requests in flight, starting new ones as others complete.
- **Progress reporting**: use `Promise.allSettled` with a `.then()` on each individual promise to track which have resolved so far.

## Implementation 3 — Timeout Pattern with `Promise.race`

### Challenge
Fetch data from an API but give up after 5 seconds, failing with a meaningful `TimeoutError`. Properly clean up the pending fetch when the timeout fires (avoid leaked connections).

### Pattern
`Promise.race` between the real operation and a delayed rejection — whichever settles first wins; use `AbortController` to cancel the losing request.

### Key Insight
The timeout Promise is a "canary" that rejects after a delay. If the real fetch hasn't settled by then, race picks up the rejection. Without `AbortController`, the fetch continues consuming a network connection even after the timeout — race discards the result but doesn't cancel the HTTP request. `AbortController` signals the fetch to terminate early, freeing the connection.

### Implementation

```js
class TimeoutError extends Error {
  constructor(ms) {
    super(`Operation timed out after ${ms}ms`);
    this.name = 'TimeoutError';
    this.timeout = ms;
  }
}

function withTimeout(promise, ms) {
  let timeoutId;

  const timeout = new Promise((_, reject) => {
    timeoutId = setTimeout(
      () => reject(new TimeoutError(ms)),
      ms
    );
  });

  return Promise.race([promise, timeout])
    .finally(() => clearTimeout(timeoutId)); // always clear timer — prevents memory leak
}

// Fetch with built-in abort on timeout:
async function fetchWithTimeout(url, ms = 5000, options = {}) {
  const controller = new AbortController();
  let timeoutId;

  const timeout = new Promise((_, reject) => {
    timeoutId = setTimeout(() => {
      controller.abort();  // cancel the actual HTTP request
      reject(new TimeoutError(ms));
    }, ms);
  });

  try {
    const result = await Promise.race([
      fetch(url, { ...options, signal: controller.signal }),
      timeout,
    ]);
    clearTimeout(timeoutId); // fetch won — cancel the pending timeout timer
    return result;
  } catch (err) {
    clearTimeout(timeoutId);
    if (err.name === 'AbortError') throw new TimeoutError(ms); // normalize abort error
    throw err;
  }
}

// Usage:
async function loadData() {
  try {
    const res  = await fetchWithTimeout('/api/slow-endpoint', 3000);
    const data = await res.json();
    return data;
  } catch (err) {
    if (err instanceof TimeoutError) {
      console.warn('Request timed out — showing cached data');
      return getCachedData();
    }
    throw err;
  }
}
```

### Execution Trace

```
fetchWithTimeout('/api/slow-endpoint', 3000) called.

t=0ms:
  AbortController created.
  setTimeout(3000) scheduled → will fire at t=3000ms.
  fetch('/api/slow-endpoint', {signal}) starts.
  Promise.race([fetchPromise, timeoutPromise]) created.
  await suspends. Both fetch and timeout timer now running.

Scenario A — fetch resolves at t=800ms:
  t=800ms: fetch response arrives.
  Promise.race fulfills with Response (fetch wins).
  clearTimeout called → timer at 3000ms is cancelled.
  .finally() chain: clearTimeout. Return response.
  [setTimeout at 3000ms was cancelled — never fires ✓]

Scenario B — fetch is slow (t > 3000ms):
  t=3000ms: setTimeout fires.
    controller.abort() called → browser sends abort signal to fetch.
    reject(new TimeoutError(3000)) called.
  Promise.race rejects with TimeoutError (timeout wins).
  .catch() runs: clears timeoutId (already fired, clearTimeout is safe).
    err.name === 'AbortError'? Possibly — fetch may throw AbortError.
    Normalize to TimeoutError. throw new TimeoutError(ms).
  The fetch's AbortError (from controller.abort()) is swallowed.

  At t=3500ms: server response arrives (hypothetically).
    Fetch was aborted — response is ignored. Connection freed. ✓
    (Without AbortController, browser holds the TCP connection until t=3500ms.)
```

### Complexity
- **Happy path**: O(actual_fetch_time) — timeout never fires.
- **Timeout path**: O(timeout_ms) — deterministic upper bound on wait time.
- **Resource usage without AbortController**: fetch continues until server responds; race discards the result but TCP connection persists.
- **Resource usage with AbortController**: TCP connection terminated at timeout. Proper cleanup.

### Edge Cases
- **Timeout fires AFTER fetch resolves but BEFORE `.finally()` runs**: both the fetch result and the timeout rejection are produced. Promise.race already settled with the fetch result; the timeout's `reject()` is a no-op (Promise.race is already settled). `clearTimeout` in `.finally()` cleans up.
- **`ms = 0`**: timeout fires immediately (in the next macrotask). Fetch almost never wins unless it resolves synchronously (never for network requests).
- **`Promise.race([])` (empty)**: never settles. Don't call `withTimeout` with an empty race — the timeout provides the fallback but only if `promise` is included.

### Extensions
- **Configurable retry on timeout**: catch `TimeoutError`, increase timeout, retry once.
- **Multiple timeouts per-phase**: set a different timeout for DNS resolution, connection, first byte, total download.

## Implementation 4 — Batch Operations with `Promise.allSettled`

### Challenge
Send 50 records to an API for update. Some will succeed, some may fail (validation errors, conflicts). Process all regardless of partial failure, and return a detailed report of successes and failures — never abort the batch on a single failure.

### Pattern
`Promise.allSettled` for fault-tolerant batch processing — all operations fire in parallel; the combinator waits for all to settle; results are classified and reported.

### Key Insight
`Promise.allSettled` never rejects — it always fulfills with an array of outcome objects. This is exactly what batch processing needs: you want the result of every operation, not just the first failure. The outcome objects' `status` field enables clean classification without try/catch per item.

### Implementation

```js
async function bulkUpdateRecords(records, { concurrency = 10 } = {}) {
  // Process in chunks to avoid overwhelming the API:
  const chunks = chunkArray(records, concurrency);
  const allOutcomes = [];

  for (const chunk of chunks) {
    const outcomes = await Promise.allSettled(
      chunk.map(record => updateRecord(record)
        .then(result => ({ record, result })) // tag success with original record
      )
    );
    allOutcomes.push(...outcomes);
  }

  // Classify outcomes:
  const succeeded = [];
  const failed    = [];

  allOutcomes.forEach((outcome, i) => {
    if (outcome.status === 'fulfilled') {
      succeeded.push(outcome.value);
    } else {
      failed.push({
        record: records[i],
        error: outcome.reason,
        retryable: isRetryable(outcome.reason),
      });
    }
  });

  return {
    total:      records.length,
    succeeded:  succeeded.length,
    failed:     failed.length,
    successRate: `${((succeeded.length / records.length) * 100).toFixed(1)}%`,
    failures:   failed,
  };
}

function chunkArray(arr, size) {
  const chunks = [];
  for (let i = 0; i < arr.length; i += size) chunks.push(arr.slice(i, i + size));
  return chunks;
}

function isRetryable(error) {
  // Retry on server errors (5xx) but not client errors (4xx):
  return error?.status >= 500;
}

// Usage:
const report = await bulkUpdateRecords(records, { concurrency: 10 });
console.log(`Updated ${report.succeeded}/${report.total} records`);
if (report.failed.length > 0) {
  const retryable = report.failures.filter(f => f.retryable);
  console.warn(`${report.failed} failures (${retryable.length} retryable)`);
}
```

### Execution Trace

```

Chunk 1: [r1..r10] — 10 concurrent updateRecord() calls start.
await Promise.allSettled([p1..p10]).

  t=50ms:  r3 fails (404 validation error).
           p3 = { status: 'rejected', reason: Error{status:404} }. allSettled still pending.
  t=100ms: r1,r2,r4..r10 all succeed.
           allSettled: all 10 inputs settled → fulfills!

  outcomes[0] = { status: 'fulfilled', value: { record: r1, result: {...} } }
  outcomes[2] = { status: 'rejected', reason: Error{status:404} }
  ... etc.

Chunk 2: [r11..r20] starts. await Promise.allSettled([p11..p20]).
  ... (similar process)

[After all chunks processed]:
allOutcomes has 50 entries.
Classification:
  succeeded = 47 (status: 'fulfilled')
  failed    = 3  (status: 'rejected')
    - failures[0]: { record: r3, error: Error{status:404}, retryable: false }
    - failures[1]: { record: r28, error: Error{status:503}, retryable: true }
    - failures[2]: { record: r45, error: Error{status:400}, retryable: false }

```

### Complexity
- **Latency**: `ceil(N / concurrency)` chunks × max(latency per chunk). With N=50, concurrency=10: 5 chunks × max_latency.
- **Memory**: O(N) for all outcomes stored in `allOutcomes`.
- **vs `Promise.all`**: `Promise.all` would fail on the first rejection, aborting the batch. `Promise.allSettled` processes all 50 regardless.

### Edge Cases
- **All fail**: `Promise.allSettled` still fulfills — all entries have `status: 'rejected'`. `succeeded.length === 0`.
- **Empty batch**: `chunkArray([], 10) = []`. Loop doesn't execute. Returns `{total:0, succeeded:0, failed:0}`.
- **Concurrency = 1**: sequential processing, one at a time. Slower but minimizes server load.

### Extensions
- **Automatic retry of retryable failures**: after the first pass, retry `failures.filter(f => f.retryable)` with `Promise.allSettled` again.
- **Progress callbacks**: call `onProgress({ processed, total })` after each chunk.

## Implementation 5 — First Available Resource with `Promise.any`

### Challenge
Fetch a static asset from multiple CDN endpoints. Use whichever CDN responds successfully first. If all CDNs fail, throw a comprehensive error listing all failures.

### Pattern
`Promise.any` for "first success" semantics — start all requests simultaneously; use the first successful response; fail only if all fail with `AggregateError`.

### Key Insight
`Promise.any` ignores rejections until all promises reject. This is perfect for redundant resource fetching: a single CDN being down or slow doesn't affect the user if another responds first. A fast CDN with a failed response should not win over a slower CDN with a successful response — validate responses and re-reject non-OK responses.

### Implementation

```js
const CDN_ENDPOINTS = [
  'https://cdn1.example.com',
  'https://cdn2.example.com',
  'https://cdn3.example.com',
];

async function fetchFromAnyCDN(path, endpoints = CDN_ENDPOINTS) {
  if (endpoints.length === 0) throw new Error('No CDN endpoints configured');

  const requests = endpoints.map(async cdn => {
    const url = `${cdn}/${path}`;
    const res = await fetch(url);

    if (!res.ok) {
      // Non-2xx response: reject so Promise.any tries the next CDN
      throw Object.assign(new Error(`${cdn}: HTTP ${res.status} ${res.statusText}`), {
        status: res.status,
        cdn,
      });
    }

    return { response: res, cdn }; // tag with which CDN won, for logging
  });

  try {
    const { response, cdn } = await Promise.any(requests);
    console.log(`Asset served from: ${cdn}`);
    return response;
  } catch (err) {
    // err is AggregateError — all CDNs failed
    const details = err.errors.map(e => `  ${e.cdn}: ${e.message}`).join('\n');
    throw new Error(`All CDNs failed for "${path}":\n${details}`);
  }
}

// Usage with race-awareness: also report slow CDNs:
async function fetchWithCDNMetrics(path) {
  const startTimes = Object.fromEntries(CDN_ENDPOINTS.map(cdn => [cdn, Date.now()]));
  const requests = CDN_ENDPOINTS.map(async cdn => {
    const res = await fetch(`${cdn}/${path}`);
    if (!res.ok) throw new Error(`${cdn}: ${res.status}`);
    console.log(`${cdn} responded in ${Date.now() - startTimes[cdn]}ms`);
    return res;
  });

  return Promise.any(requests);
}
```

### Complexity
- **Latency**: O(min(successful CDN response times)) — best-case.
- **If k CDNs fail before the first success**: latency = max(k failing CDNs) or first success, whichever comes later.
- **vs `Promise.race`**: race would adopt cdn2's 503 rejection at t=120ms, failing the whole operation before cdn3 could succeed. `Promise.any` correctly ignores cdn2's failure.

### Edge Cases
- **All CDNs respond with non-OK HTTP status**: all promises reject with formatted errors; `AggregateError` is thrown.
- **Network error (DNS failure, timeout) vs HTTP error**: both are rejections — `Promise.any` treats them identically.
- **Single CDN endpoint**: `Promise.any([singleRequest])` behaves identically to awaiting `singleRequest` directly, except failures are wrapped in `AggregateError`.

### Extensions
- **Prioritized endpoints**: try the primary CDN first; only use fallbacks after a short delay. Use a `Promise.any` where fallback promises start after `delay` ms.
- **Caching winners**: track which CDN responded fastest, prefer it for subsequent requests.

## Implementation 6 — Retry with Exponential Backoff

### Challenge
Implement a general-purpose `withRetry` wrapper that retries any async operation on failure, using exponential backoff between attempts (1s, 2s, 4s, ...), respecting cancellation via `AbortSignal`, and distinguishing retryable from non-retryable errors.

### Pattern
Async loop with `Promise`-based delay and structured error classification — each attempt awaits the operation; on failure, awaits a backoff delay before the next attempt; respects external cancellation signals.

### Key Insight
Exponential backoff (`delay = baseDelay × 2^(attempt-1)`) reduces server load during outages by spreading retries over increasing intervals. Respecting `AbortSignal` makes the wrapper composable with other cancellation patterns. Distinguishing error types (transient vs permanent) avoids wasting retries on errors that will never succeed (e.g., 404 Not Found).

### Implementation

```js
class RetryExhaustedError extends Error {
  constructor(attempts, lastError) {
    super(`Operation failed after ${attempts} attempt(s): ${lastError.message}`);
    this.name = 'RetryExhaustedError';
    this.attempts = attempts;
    this.cause = lastError;
  }
}

const DEFAULT_RETRYABLE = err =>
  // Retry on network errors and 5xx server errors, not 4xx client errors:
  !err?.status || err.status >= 500;

async function withRetry(fn, {
  maxAttempts   = 3,
  baseDelayMs   = 1000,
  maxDelayMs    = 30_000,
  jitter        = true,   // add randomness to avoid thundering herd
  signal        = null,   // AbortSignal for external cancellation
  isRetryable   = DEFAULT_RETRYABLE,
  onRetry       = null,   // optional callback: ({ attempt, error, delayMs }) => void
} = {}) {
  let lastError;

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    // Check for external cancellation before each attempt:
    if (signal?.aborted) {
      throw Object.assign(new Error('Operation cancelled'), { name: 'AbortError' });
    }

    try {
      return await fn({ attempt, signal }); // pass context to fn for its own AbortSignal use

    } catch (err) {
      lastError = err;

      // Don't retry if: this was the last attempt, or error is not retryable, or cancelled:
      const isLastAttempt  = attempt === maxAttempts;
      const shouldRetry    = !isLastAttempt && isRetryable(err) && !signal?.aborted;

      if (!shouldRetry) {
        if (isLastAttempt) throw new RetryExhaustedError(attempt, err);
        throw err; // non-retryable or cancelled — rethrow immediately
      }

      // Calculate delay with exponential backoff + optional jitter:
      const exponentialDelay = Math.min(baseDelayMs * 2 ** (attempt - 1), maxDelayMs);
      const delayMs = jitter
        ? exponentialDelay * (0.5 + Math.random() * 0.5) // ±50% jitter
        : exponentialDelay;

      onRetry?.({ attempt, error: err, delayMs, nextAttempt: attempt + 1 });

      // Wait for backoff period (cancellable via AbortSignal):
      await new Promise((resolve, reject) => {
        const id = setTimeout(resolve, delayMs);
        signal?.addEventListener('abort', () => { clearTimeout(id); reject(new Error('Cancelled')); }, { once: true });
      });
    }
  }

  throw new RetryExhaustedError(maxAttempts, lastError);
}

// Usage example:
async function fetchWithRetry(url) {
  return withRetry(
    async ({ signal }) => {
      const res = await fetch(url, { signal });
      if (!res.ok) {
        const err = new Error(`HTTP ${res.status}`);
        err.status = res.status;
        throw err;
      }
      return res.json();
    },
    {
      maxAttempts: 4,
      baseDelayMs: 500,
      isRetryable: err => !err.status || err.status >= 500,
      onRetry: ({ attempt, error, delayMs }) =>
        console.warn(`Attempt ${attempt} failed (${error.message}). Retrying in ${Math.round(delayMs)}ms...`),
    }
  );
}
```

### Complexity
- **Total delays**: baseDelay × (2^0 + 2^1 + ... + 2^(n-2)) = baseDelay × (2^(n-1) - 1). For n=3, baseDelay=1000: ~3s total wait.
- **Jitter**: reduces "thundering herd" — multiple clients retrying simultaneously spread out their retries randomly.
- **AbortSignal**: cancelled during a delay → delay Promise rejects immediately, function exits cleanly.

### Edge Cases
- **First attempt succeeds**: returns immediately with no delays. O(1 fetch time).
- **All attempts fail with retryable error**: `RetryExhaustedError` wraps the last error. The `.cause` field preserves the original error for diagnosis.
- **`maxAttempts = 1`**: a single attempt, no retries. Any failure throws immediately (`isLastAttempt` is true on attempt 1).
- **Infinite backoff prevention**: `maxDelayMs` caps the delay. Without it, attempt 20 would wait 1000 × 2^19 ≈ 146 hours.

### Extensions
- **Circuit breaker**: track failure rate over a time window; stop attempting if failure rate exceeds threshold; automatically reset after a cool-down period.
- **Retry budgets**: global retry counter shared across all calls; stop retrying if budget exhausted (prevents cascading retry storms).

## Quick Reference — Promise Method Decision Tree

```
What do you need to do?
│
├── SEQUENCE async operations (each step depends on the previous)?
│   └── Promise chaining: return a Promise from each .then() handler.
│       fetch(url).then(r => r.json()).then(data => process(data)).catch(handleError)
│       Or: async/await with sequential awaits.
│
├── RUN independent async operations and need ALL to succeed?
│   └── Promise.all([op1, op2, op3]).
│       Fulfills with [v1, v2, v3] in INPUT order.
│       Rejects on FIRST rejection — other operations continue but results ignored.
│       Anti-pattern: const a = await op1; const b = await op2; (sequential, slow!)
│
├── RUN independent operations, need ALL results even if some fail?
│   └── Promise.allSettled([op1, op2, op3]).
│       Always fulfills with [{status, value/reason}, ...].
│       Never rejects. Good for: batch processing, independent side effects.
│
├── RACE async operations — need whichever SETTLES first (fulfilled OR rejected)?
│   └── Promise.race([op, timeoutPromise]).
│       Adopts state of first settlement, fulfilled or rejected.
│       Use for: timeouts, first-to-respond patterns.
│       Warning: empty array → never settles (pending forever).
│
├── RACE for FIRST SUCCESS — need first fulfilled, ignore failures unless ALL fail?
│   └── Promise.any([op1, op2, op3]).
│       Fulfills with first fulfillment. Rejects with AggregateError if ALL reject.
│       Use for: redundant resources (multiple CDNs), fallback chains.
│
├── CLEANUP regardless of success or failure?
│   └── .finally(fn) — fn receives no args; original value/reason passes through.
│       NOT .then(f, f) — that replaces the value with undefined.
│
├── RECOVER from an error mid-chain?
│   └── .catch(e => fallbackValue) — returns fallback; chain continues as fulfilled.
│       To keep chain rejected: .catch(e => { throw e; }) or .catch(Promise.reject).
│
├── TIMEOUT any async operation?
│   └── Promise.race([operation, new Promise((_, r) => setTimeout(() => r(new Error('Timeout')), ms))]).
│       Always use AbortController to cancel the operation on timeout.
│
└── RETRY on failure with backoff?
    └── for...of loop with await + setTimeout delay.
        Classify errors (retryable vs not). Respect AbortSignal for cancellation.
        Cap maximum delay. Add jitter to prevent thundering herd.
```

## Common Bugs Checklist

Before shipping any Promise-based code, verify:

1. **Missing `return` inside a `.then()` handler?** — `fetch(url).then(r => { r.json(); })` returns `undefined`, not the parsed JSON. The Promise chain sees `undefined` and the actual data is lost. Always `return` from `.then()` handlers: `r => r.json()` or `r => { return r.json(); }`.

2. **Using `.then(f, f)` instead of `.then(f).catch(f)` for combined error handling?** — `.then(onFulfilled, onRejected)` does NOT protect against errors thrown by `onFulfilled`. The `onRejected` only catches the incoming rejection. Use `.then(onFulfilled).catch(onRejected)` when you want to catch both the upstream rejection AND errors from the handler.

3. **Forgetting to re-throw in a `.catch()` that should propagate the error?** — `.catch(e => console.log(e))` returns `undefined`, recovering the chain. All subsequent `.then()` handlers run as if nothing went wrong. If the error should propagate: `throw e` or `return Promise.reject(e)` inside `.catch()`.

4. **Sequential `await` for independent operations?** — `const a = await op1(); const b = await op2();` takes `time(op1) + time(op2)`. Use `const [a, b] = await Promise.all([op1(), op2()])` for `max(time(op1), time(op2))`. This is the most common async performance bug in production Node.js code.

5. **`await` inside `.forEach()`?** — `items.forEach(async item => { await process(item); })` does not wait for the async callbacks. `forEach` returns `undefined` synchronously; the returned Promise from each callback is discarded. Use `for...of` with `await` for sequential, or `await Promise.all(items.map(async item => process(item)))` for parallel.

6. **Unhandled rejections?** — Any Promise chain without a terminal `.catch()` will trigger `UnhandledPromiseRejection`. Always add `.catch()` at the end of chains that start with `new Promise()`, `fetch()`, or any async operation. For async functions, always wrap in `try/catch` at the call site or add `.catch()` on the returned Promise.

7. **`Promise.race([])` never settles?** — An empty iterable to `Promise.race` produces a Promise that stays pending forever. Always validate that the iterable is non-empty before calling `Promise.race`. `Promise.any([])` rejects immediately, which is safer.

8. **Not validating HTTP responses before treating them as success?** — `fetch()` only rejects on network failures (DNS, connection refused). A `404` or `500` response fulfills the fetch Promise with a Response object where `r.ok === false`. Always check `if (!r.ok) throw new Error(...)` before calling `r.json()`.

9. **Creating Promises unnecessarily (`new Promise` anti-pattern)?** — `new Promise((res, rej) => fetch(url).then(res).catch(rej))` is redundant — just `return fetch(url)`. The constructor anti-pattern hides errors: if `fetch(url)` throws synchronously (it won't, but many functions can), the outer Promise never rejects. Use `new Promise()` only when wrapping callback-based APIs.

10. **Swallowing errors from `async` functions called without `await`?** — `riskyOp()` (without `await`) ignores the returned Promise. If `riskyOp` rejects, no one handles it — unhandled rejection. Either `await riskyOp()` inside an async function, or `.catch(e => ...)` on the returned Promise.

11. **`Promise.all` result order vs arrival order?** — `Promise.all` always returns values in **input index order**, not the order in which the promises fulfilled. The fastest promise does not appear first in the result array. If `promises[2]` resolves first, `result[2]` still corresponds to `promises[2]`. This is by spec — rely on it.

12. **Not clearing timers in timeout patterns?** — `withTimeout(promise, 5000)` creates a `setTimeout`. If the Promise resolves before the timeout, the timer still exists and holds a reference, delaying garbage collection and potentially firing unexpectedly. Always `clearTimeout` in `.finally()` to clean up.

---

**Final Tip:** At the 5 YOE level, the decisive signal for Promise work is articulating **three things** before choosing a combinator: (1) **What is the dependency structure?** — "these operations are independent" → `Promise.all` / `allSettled` / `race` / `any`; "each depends on the previous" → sequential chain or sequential `await`. (2) **What failure behavior do I want?** — "any failure aborts all" → `Promise.all`; "collect all results regardless" → `Promise.allSettled`; "first success wins" → `Promise.any`; "first settlement wins" → `Promise.race`. (3) **Does every rejection have a handler?** — trace every code path; every Promise that can reject must have a `.catch()` somewhere, either on itself, on the chain it belongs to, or via `try/catch` at the `await` site. For `.finally()`, always state the pass-through invariant explicitly: *"`.finally()` passes the original value through unchanged — I use it for cleanup (spinner, metrics, timer), never to transform the value."* That framing before any combinator choice is the mark of a senior who designs async flows correctly the first time.
