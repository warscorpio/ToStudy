## Part 1 — Theory & Interview Q&A

---

## Topic A: The Call Stack

### Section A1: Fundamentals

**Q1. What is the JavaScript call stack, and what does it track?**
A: The call stack is a LIFO (last-in, first-out) data structure that tracks the currently executing function calls. Each time a function is invoked, a new **stack frame** (also called an execution context) is pushed onto the stack. That frame holds the function's local variables, arguments, and a return address — where execution should resume after the function returns. When a function finishes, its frame is popped and execution resumes from the frame below it.

JavaScript is **single-threaded**: there is exactly one call stack. Only one piece of JavaScript code runs at any moment. This is the foundational constraint that the entire event loop architecture exists to work around — enabling asynchronous behavior on a single thread.

```
Code:
function greet(name) { return `Hello, ${name}`; }
function run() { console.log(greet('Alice')); }
run();

Call stack evolution:
[empty]
→ push run()         [run]
→ push greet('Alice') [run, greet]
→ greet returns      [run]
→ console.log        [run, console.log]
→ console.log returns [run]
→ run returns        [empty]
```

**Q2. What is a stack frame, and what information does it contain?**
A: A stack frame (execution context) is the record pushed onto the call stack when a function is called. It contains:

- **Variable environment**: all `var`, `let`, `const` declarations within the function scope, and function declarations.
- **Arguments object** (for non-arrow functions): the `arguments` object binding.
- **`this` binding**: the value of `this` for the current call.
- **Outer environment reference**: a pointer to the enclosing scope (for closure resolution — the scope chain).
- **Return address**: where in the calling code execution resumes after this function returns.

The global execution context (for top-level code) is the base frame — it is pushed when the script starts and remains until the script finishes. Module-level code has a module execution context at the base instead of the global one.

**Q3. What is a stack overflow, and what causes it in JavaScript?**
A: A stack overflow occurs when the call stack exceeds its maximum depth — typically caused by unbounded recursion (a function that calls itself without a base case, or a base case that is never reached). Each recursive call pushes a new frame; the stack grows until the engine throws a `RangeError: Maximum call stack size exceeded`.

```js
// Infinite recursion → stack overflow:
function infiniteRecurse() { return infiniteRecurse(); }
infiniteRecurse(); // RangeError: Maximum call stack size exceeded

// Deep but bounded — works in most engines up to ~10,000–15,000 frames:
function countDown(n) { return n === 0 ? 'done' : countDown(n - 1); }
countDown(10000); // works (probably)
countDown(100000); // likely stack overflow
```

The maximum stack depth is engine-dependent: V8 (Node.js, Chrome) allows roughly 10,000–15,000 frames. Tail call optimization (TCO) in strict mode — where the last action of a function is a recursive call — theoretically allows infinite recursion without stack growth, but V8 has not implemented TCO in practice (as of 2025).

**Q4. Why does synchronous code block the event loop, and what are the practical consequences?**
A: While synchronous code is running on the call stack, the event loop cannot process any pending events — the stack must be empty before the loop can pick up the next task. Any UI interaction, network response, timer callback, or other event that arrives during a long synchronous operation is queued but not handled until the synchronous work finishes.

Practical consequences:
- **UI freezes**: browsers cannot repaint or respond to user input while the main thread's stack is busy. A `while(true)` loop or a 500ms synchronous computation makes the tab unresponsive.
- **Timer inaccuracy**: `setTimeout(fn, 0)` does not guarantee `fn` runs in 0ms — it runs after the current stack clears AND after any preceding queued tasks.
- **Network starvation**: a `fetch` response callback cannot execute while synchronous computation is running, regardless of how long ago the response arrived.

```js
console.log('start');
// Simulate heavy synchronous work:
const start = Date.now();
while (Date.now() - start < 2000) {} // blocks for 2 seconds
console.log('end'); // only after 2 full seconds
// During these 2 seconds: no clicks handled, no timers fired, no network callbacks
```

### Section A2: Advanced Patterns

**Q5. What is the difference between the execution context and the scope chain?**
A: The **execution context** is the runtime record for one function call — it holds the current variable bindings, `this`, and the return address. It is created fresh each time the function is called.

The **scope chain** (or environment record chain) is a static property determined at function *definition* time — it is the chain of lexical environments from the function's definition site up to the global scope. It enables closures: a function "closes over" its defining scope, so inner functions can access outer variables even after the outer function has returned and its execution context has been popped.

```js
function outer() {
  const x = 10; // lives in outer's variable environment
  function inner() {
    console.log(x); // inner's scope chain includes outer's environment
  }
  return inner;
}
const fn = outer(); // outer's execution context is popped
fn(); // 10 — inner still has access via scope chain (closure)
```

The execution context is on the stack; the scope chain (lexical environment) is on the heap (as long as any closure references it). This is why closures can keep outer variables alive after the function returns.

## Topic B: Web APIs and Asynchronous Handoff

### Section B1: Fundamentals

**Q6. What are Web APIs, and how do they interact with the JavaScript engine?**
A: Web APIs are capabilities provided by the browser (or by Node.js's runtime) that exist *outside* the JavaScript engine itself — in C++ code, OS threads, or dedicated processes. They include:

- **Timers**: `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval` — managed by the browser's timer thread.
- **Network**: `fetch`, `XMLHttpRequest`, `WebSocket` — handled by the browser's networking stack.
- **DOM events**: `addEventListener` — event dispatch handled by the browser's event dispatch system.
- **Geolocation, Storage, IndexedDB**: I/O managed outside the JS thread.
- **Node.js equivalents**: `fs.readFile`, `http.request`, `crypto`, `child_process` — managed by libuv's thread pool and OS I/O.

The interaction pattern:
1. JavaScript calls a Web API function (e.g., `setTimeout(fn, 1000)`).
2. The Web API begins its work in its own thread/process — JavaScript execution continues immediately (non-blocking).
3. When the Web API's work completes (timer fires, response arrives, file read done), it places the registered callback into the appropriate **task queue** — either the macrotask queue or the microtask queue.
4. The event loop picks up the callback when the call stack is empty.

```
JS Engine (single thread)       Web API Layer (multi-thread)
──────────────────────────      ───────────────────────────
setTimeout(fn, 1000)     ──→    Timer thread: countdown 1000ms
↓ (continues immediately)       ↓ (1000ms later)
...more synchronous code        places fn in macrotask queue
```

**Q7. Why does `setTimeout(fn, 0)` not guarantee immediate execution?**
A: `setTimeout(fn, 0)` registers `fn` with the timer Web API with a delay of 0ms (or 1ms — the HTML spec mandates a minimum delay of 1ms for nested timers and 0ms for non-nested). Once the delay expires, `fn` is placed into the **macrotask queue** — not executed immediately. Three things must happen before `fn` runs:

1. The **current call stack must be empty** — all synchronous code in the current task must finish.
2. All **microtasks** currently in the microtask queue must drain (including any microtasks that enqueue further microtasks).
3. The event loop picks `fn` from the macrotask queue as the *next* task — but if other macrotasks were enqueued before `fn`'s timer expired, they run first.

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// Output: A, C, B
// 'B' runs AFTER 'A' and 'C' because the current synchronous task (logging A, C)
// must finish before the event loop can pick up the setTimeout callback.
```

Practical use of `setTimeout(fn, 0)`: defer work to after the current synchronous task — useful for avoiding blocking UI renders, breaking up heavy computations, or ensuring DOM updates are applied before running code that reads layout.

**Q8. How does `setInterval` differ from `setTimeout`, and what is interval drift?**
A: `setTimeout` schedules a callback to run *once* after a delay. `setInterval` repeatedly schedules the callback every `interval` ms — after each execution, another execution is scheduled.

**Interval drift** occurs because `setInterval` schedules the *next* timer the moment the interval fires — not when the callback finishes. If the callback takes longer than the interval to execute, the next interval fires immediately (it was already in the queue). Over time, the actual execution times drift away from the intended regular cadence.

```
setInterval(fn, 1000), where fn takes 200ms:
Intended: fn at t=1000, t=2000, t=3000 ...
Actual:   fn starts at t=1000, ends at t=1200 → next fires at t=2000 (200ms gap, not 800ms)
          fn starts at t=2000, ends at t=2200 → next fires at t=3000

But if fn takes 1500ms:
          fn starts at t=1000, ends at t=2500 → interval at t=2000 was missed
          → next fires immediately after t=2500 → fn runs at t=2500 instead of t=3000
```

For precise cadences, use recursive `setTimeout` — schedule the next call *after* the previous one finishes:

```js
function runWithDelay(fn, delay) {
  setTimeout(function tick() {
    fn();
    setTimeout(tick, delay); // schedule next only after current finishes
  }, delay);
}
```

### Section B2: Advanced Patterns

**Q9. How does Node.js's libuv differ from browser Web APIs in managing async operations?**
A: Both serve the same role — offloading I/O from the JavaScript thread — but differ in implementation:

**Browser Web APIs**: provided by the browser runtime (Blink, WebKit, Gecko). Timers, network, DOM events each have dedicated subsystems. The browser has a single event loop per tab/worker.

**Node.js libuv**: a cross-platform C library that provides the event loop, async I/O, thread pool, and timers. Key differences:

- **Thread pool**: libuv maintains a pool of 4 threads (configurable via `UV_THREADPOOL_SIZE`) for CPU-bound or blocking OS operations (file I/O, DNS lookup, crypto). Network I/O uses non-blocking OS APIs (epoll, kqueue, IOCP) directly — no thread pool needed.
- **Multiple phases**: the Node.js event loop has distinct phases (timers → pending callbacks → idle/prepare → poll → check → close callbacks), not just macrotask/microtask. `setImmediate` callbacks run in the "check" phase; timer callbacks in the "timers" phase.
- **`process.nextTick`**: a Node.js-specific micro-like queue that runs *before* the microtask queue (before Promises), between every event loop phase transition.

```
Node.js event loop phases (simplified):
  ┌──────────────────────────────┐
  │           timers             │  ← setTimeout, setInterval callbacks
  │     pending callbacks        │  ← I/O errors from previous iteration
  │       idle, prepare          │  ← internal use
  │           poll               │  ← retrieve new I/O events; execute callbacks
  │           check              │  ← setImmediate callbacks
  │       close callbacks        │  ← socket.on('close', ...) etc.
  └──────────────────────────────┘
Between each phase: process.nextTick queue, then Promise microtask queue
```

**Q10. What is the difference between `setImmediate` (Node.js) and `setTimeout(fn, 0)`?**
A: Both schedule a callback to run "soon," but they fall in different event loop phases:

- `setTimeout(fn, 0)` fires in the **timers phase** — the next iteration of the event loop after the minimum delay (typically 1ms).
- `setImmediate(fn)` fires in the **check phase** — always after the **poll phase** of the *current* event loop iteration.

When called from the main module (outside any I/O callback), their relative order is non-deterministic — depends on OS timer precision. When called *inside* an I/O callback, `setImmediate` always fires before `setTimeout(fn, 0)`:

```js
// In an I/O callback:
fs.readFile('file.txt', () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
  // Always: "immediate" before "timeout"
  // Because after poll phase (where I/O callback ran), check phase comes next
  // before the next timers phase iteration.
});
```

## Topic C: The Microtask Queue

### Section C1: Fundamentals

**Q11. What is the microtask queue, and what kinds of tasks go into it?**
A: The microtask queue (also called the "microtask checkpoint" or "job queue" in the ECMAScript spec) holds callbacks that should run *before the event loop returns to the macrotask queue* — after the current task finishes but before the next macrotask begins, and also between tasks if new microtasks are enqueued.

Sources of microtasks:
- **Promise callbacks** (`.then()`, `.catch()`, `.finally()` handlers) — the most common source.
- **`queueMicrotask(fn)`** — explicitly enqueues a function as a microtask (available in browsers and Node.js).
- **`MutationObserver` callbacks** (browser) — fires microtasks when observed DOM mutations occur.
- **`process.nextTick`** (Node.js) — technically a separate "nextTick queue" processed before the Promise microtask queue, but shares the "before next macrotask" timing.
- **`async/await`** — `await` creates microtasks under the hood (each `await` resumes in a microtask).

```js
Promise.resolve().then(() => console.log('microtask 1'));
queueMicrotask(() => console.log('microtask 2'));
console.log('synchronous');
// Output: synchronous, microtask 1, microtask 2
// Microtasks run after synchronous code but before any macrotask
```

**Q12. What is the critical rule about microtask queue draining?**
A: The microtask queue is **drained completely** before the event loop moves on — this includes microtasks that enqueue further microtasks. The event loop does not pick up the next macrotask until the microtask queue is empty.

This has a dangerous consequence: a microtask that endlessly enqueues new microtasks will **starve the event loop** — macrotasks (including rendering, timer callbacks, and I/O) are permanently blocked:

```js
// DANGER: infinite microtask starvation
function infiniteMicrotask() {
  Promise.resolve().then(infiniteMicrotask); // always enqueues a new microtask
}
infiniteMicrotask(); // The page freezes — the event loop never reaches a macrotask
```

This is the microtask-equivalent of an infinite synchronous loop. Unlike an infinite `setTimeout` loop (which processes one callback per event loop iteration, allowing other tasks to interleave), infinite microtask chains completely starve the macrotask queue.

```
Microtask draining algorithm (after each task and at other checkpoints):
1. while (microtaskQueue is not empty):
     task = microtaskQueue.dequeue()
     task()   // may enqueue more microtasks
     // loop continues with the newly enqueued microtasks
2. // only after queue is empty: proceed to next macrotask or rendering
```

**Q13. How do Promise `.then()` callbacks become microtasks?**
A: When a Promise is resolved (or rejected), its `.then(onFulfilled)` handler is not called synchronously — it is scheduled as a microtask. Even if the Promise is *already resolved* when `.then()` is called, the handler is still asynchronous (runs as a microtask):

```js
const p = Promise.resolve(42); // already resolved
p.then(v => console.log('handler:', v)); // scheduled as microtask, NOT called now
console.log('after .then()');
// Output: "after .then()", "handler: 42"
// Even though p is already resolved, the handler runs asynchronously (microtask)
```

Under the hood: each `.then()` call creates a new Promise and registers a reaction. When the upstream Promise resolves, the reaction is enqueued as a microtask (a "PromiseReactionJob" in the spec). The microtask, when executed, calls the `onFulfilled` handler and resolves the new Promise with the returned value.

Chained `.then()` calls each schedule a new microtask — each handler runs in a separate microtask turn:

```js
Promise.resolve()
  .then(() => console.log('1'))   // microtask 1
  .then(() => console.log('2'))   // microtask 2 (enqueued when microtask 1 completes)
  .then(() => console.log('3'));  // microtask 3 (enqueued when microtask 2 completes)
// Output: 1, 2, 3 — each in a separate microtask "turn"
```

**Q14. How does `async/await` relate to the microtask queue?**
A: `async/await` is syntactic sugar over Promises. An `async` function returns a Promise. An `await` expression suspends the `async` function and schedules its *resumption* as a microtask when the awaited value resolves.

```js
async function example() {
  console.log('A');
  await Promise.resolve();  // suspends here; resumes as a microtask
  console.log('B');         // runs as a microtask
}

console.log('1');
example();                  // starts running synchronously up to the first await
console.log('2');
// Output: 1, A, 2, B
// Explanation:
// '1' — synchronous
// example() starts → 'A' — synchronous (before first await)
// await suspends example(), schedules resumption as microtask
// '2' — synchronous (continues after example() suspends)
// [microtask queue drains]: B runs
```

Each `await` in a function creates (at minimum) one microtask "hop" — the function resumes in the microtask queue after the awaited Promise resolves. Multiple `await`s create multiple sequential microtask turns:

```js
async function multiAwait() {
  await null; // hop 1
  await null; // hop 2
  console.log('done'); // runs after 2 microtask turns
}
```

In V8, the number of microtask hops per `await` has been optimized over time — native Promises were optimized from 3 hops to 2 hops to 1 hop in recent versions. This matters for understanding precise output ordering in tricky interview puzzles.

### Section C2: Advanced Patterns

**Q15. What is `queueMicrotask`, and when should you use it instead of `Promise.resolve().then()`?**
A: `queueMicrotask(fn)` directly enqueues `fn` as a microtask without creating a Promise object. It is:

- **Cheaper**: no Promise allocation, no `.then()` call overhead.
- **Cleaner semantics**: makes the intent "run this as a microtask" explicit — not "resolve a dummy Promise and run a handler."
- **Error isolation**: `Promise.resolve().then(fn)` wraps `fn` in a Promise rejection handler — if `fn` throws, it becomes an unhandled Promise rejection (silently swallowed unless caught). `queueMicrotask(fn)` throws synchronously into the event loop's uncaught-exception handler — the error is reported like a regular unhandled error.

```js
// These have the same timing:
queueMicrotask(() => console.log('microtask'));
Promise.resolve().then(() => console.log('microtask'));

// But queueMicrotask has better error behavior:
queueMicrotask(() => { throw new Error('oops'); });
// → uncaught error, visible in console

Promise.resolve().then(() => { throw new Error('oops'); });
// → UnhandledPromiseRejection — may be silently ignored depending on environment
```

Use `queueMicrotask` when you want to defer code to the microtask queue without the semantics of Promise chaining — e.g., batching DOM reads/writes, deferring validation, scheduling reactive updates.

## Topic D: The Macrotask Queue

### Section D1: Fundamentals

**Q16. What is the macrotask queue (task queue), and what kinds of tasks go into it?**
A: The macrotask queue (the HTML spec calls it the "task queue"; it is sometimes called the "callback queue" or "message queue") holds tasks scheduled by Web APIs. The event loop picks **one** macrotask per iteration — processes it completely (running all synchronous code in that task), drains the microtask queue, optionally renders, then picks the next macrotask.

Sources of macrotasks:
- `setTimeout` and `setInterval` callbacks.
- `MessageChannel` port messages.
- `postMessage` from workers/iframes.
- DOM event handlers (`click`, `keydown`, `load`, `scroll`, etc.).
- `XMLHttpRequest` `onload`, `onerror` callbacks.
- `fetch`'s underlying network response (though the microtask queue handles `.then()` resolution).
- `setImmediate` (Node.js check phase — equivalent to a macrotask).
- Script loading (`<script>` tag evaluations).

```
One event loop iteration:
1. Dequeue ONE macrotask from the task queue → execute it (may push/pop call stack)
2. Drain ALL microtasks (including newly enqueued microtasks)
3. If rendering is needed: perform layout, paint, run requestAnimationFrame callbacks
4. Return to step 1
```

**Q17. Are there multiple macrotask queues, and how does the browser prioritize between them?**
A: Yes — the HTML spec defines that a browsing context can have **multiple task sources** (task queues), each feeding into the event loop. Different sources have different queues:

- **Timer task source**: `setTimeout`/`setInterval` callbacks.
- **DOM manipulation task source**: DOM mutations.
- **User interaction task source**: mouse clicks, keyboard events.
- **Networking task source**: network callbacks.
- **History traversal task source**: `history.back()` etc.

The event loop chooses which queue to process next based on priority — **user interaction** tasks typically get higher priority than timer tasks in browsers, ensuring responsiveness. This is why a rapid series of `setTimeout(fn, 0)` calls may be interleaved with user click handlers even if the timers were queued first.

In practice, most developers treat the task queue as a single FIFO queue for simplicity — the multi-queue model matters mainly for browser engine implementors and for understanding why some tasks feel more responsive than others.

**Q18. What is the full event loop tick sequence with microtasks, macrotasks, and rendering?**
A: The complete sequence for one event loop "tick":

```
┌─────────────────────────────────────────────────────────────┐
│  EVENT LOOP ITERATION                                        │
│                                                             │
│  1. MACROTASK: dequeue ONE task from the task queue(s)      │
│     → run its JavaScript (fills/empties call stack)         │
│                                                             │
│  2. MICROTASK CHECKPOINT: drain the microtask queue         │
│     while (microtaskQueue not empty):                       │
│       → run next microtask (may enqueue more microtasks)    │
│     (also check process.nextTick queue first in Node.js)    │
│                                                             │
│  3. RENDERING (browsers only, if needed):                   │
│     → run requestAnimationFrame callbacks                   │
│     → perform layout and paint                              │
│     → (only happens at ~60fps cadence, not every iteration) │
│                                                             │
│  4. Return to step 1                                        │
└─────────────────────────────────────────────────────────────┘
```

Microtask checkpoints also occur: after each individual task, after `DOMContentLoaded` parsing, after `import()` module evaluation, and in several other spec-defined places — not only at the end of a macrotask.

**Q19. What is `requestAnimationFrame`, and where does it fit in the event loop?**
A: `requestAnimationFrame(callback)` schedules a callback to run just before the browser's next repaint, after microtasks are processed and before layout/paint. It targets the display refresh rate (typically 60fps → every ~16.67ms). `rAF` callbacks are processed as a batch before each rendering opportunity — not as macrotasks (they have their own rendering-phase queue).

```
Timeline at 60fps:
t=0ms:    macrotask → microtasks → rAF callbacks → layout → paint
t=16.7ms: macrotask → microtasks → rAF callbacks → layout → paint
t=33.3ms: macrotask → microtasks → rAF callbacks → layout → paint
```

Use `requestAnimationFrame` for animations and any code that reads/writes the DOM in coordination with rendering — it avoids layout thrashing and ensures changes are visible in the next frame. Using `setTimeout(fn, 16)` for animation is inferior: it may fire slightly off the refresh cadence, causing dropped frames.

```js
function animate(timestamp) {
  // Update animation based on timestamp
  element.style.transform = `translateX(${timestamp * 0.1}px)`;
  requestAnimationFrame(animate); // schedule next frame
}
requestAnimationFrame(animate); // start
```

### Section D2: Advanced Patterns

**Q20. What is the priority ordering of all async mechanisms, from highest to lowest?**
A: From highest priority (runs first) to lowest (runs last) in a single event loop tick:

```
1. Synchronous code (call stack)                [runs NOW]
2. process.nextTick callbacks (Node.js only)    [before microtasks]
3. Promise microtasks (.then, await, queueMicrotask)  [after sync, before macrotask]
4. MutationObserver callbacks (browsers)        [microtask level]
5. requestAnimationFrame callbacks (browsers)   [rendering phase, after microtasks]
6. setTimeout / setInterval / setImmediate      [macrotask — next event loop iteration]
7. I/O callbacks (fs, network, etc.)            [macrotask — when I/O completes]
```

Precise rules:
- Synchronous code always runs to completion first.
- After any synchronous code finishes: microtask queue drains completely (process.nextTick first in Node.js, then Promises).
- Only after microtask queue is empty: the event loop may perform rendering (rAF).
- Only after rendering: the event loop picks the next macrotask.

**Q21. How does the event loop interact with Web Workers?**
A: Web Workers run in completely separate threads, each with their own JavaScript engine, call stack, event loop, and memory (no shared state except via `SharedArrayBuffer`). Communication happens via `postMessage` — messages are serialized (structured clone algorithm) and delivered as macrotasks on the receiving worker's event loop.

The main thread's event loop is unaffected by a Worker's computations — Workers are the browser's solution to truly parallel execution. Microtasks and macrotasks within a Worker operate independently from the main thread's queues.

```js
// Main thread:
const worker = new Worker('worker.js');
worker.postMessage({ data: [1,2,3] }); // serialized and queued as macrotask in worker

worker.onmessage = (e) => console.log('result:', e.data); // runs as macrotask on main thread

// worker.js:
self.onmessage = (e) => {
  const result = heavyComputation(e.data.data); // runs without blocking main thread
  self.postMessage(result); // serialized and queued as macrotask on main thread
};
```

## Topic E: Cross-Topic & Interview-Style Questions

**Q22. "Explain the event loop in one paragraph to a junior developer."**
A: JavaScript runs on a single thread — only one thing can happen at a time. The call stack tracks what's currently running. When you call a Web API like `setTimeout` or `fetch`, the browser handles it in the background while JavaScript keeps going. When the background work is done (timer fires, data arrives), the callback is placed in a queue. The event loop constantly checks: "Is the call stack empty?" — if yes, it takes the next callback from the queue and runs it. There are two queues with different priorities: the microtask queue (Promise `.then()` callbacks) is always fully processed before the next macrotask (setTimeout, click events) is taken from the macrotask queue. This is what makes JavaScript non-blocking despite being single-threaded.

**Q23. "What is the output of this code, and why?"**

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve()
  .then(() => console.log('3'))
  .then(() => console.log('4'));

console.log('5');
```

A: Output: `1, 5, 3, 4, 2`

Step-by-step:
1. `console.log('1')` — synchronous → prints `1`.
2. `setTimeout(fn, 0)` — registers callback with timer Web API; callback placed in macrotask queue after ~0ms. Execution continues.
3. `Promise.resolve().then(→'3').then(→'4')` — `Promise.resolve()` creates an already-resolved Promise. `.then(→'3')` schedules the '3' callback as a microtask. Returns a new pending Promise. `.then(→'4')` registers on that new pending Promise — not yet schedulable (upstream hasn't resolved).
4. `console.log('5')` — synchronous → prints `5`.
5. **Synchronous code done. Microtask queue drains:**
   - Run microtask: `console.log('3')` → prints `3`. The `.then(→'3')` call's returned Promise resolves → schedules `→'4'` as a new microtask.
   - Run microtask: `console.log('4')` → prints `4`. Microtask queue now empty.
6. **Event loop picks next macrotask**: `console.log('2')` → prints `2`.

**Q24. "What is the output of this more complex example?"**

```js
async function foo() {
  console.log('foo start');
  await bar();
  console.log('foo end');
}

async function bar() {
  console.log('bar');
}

console.log('script start');
setTimeout(() => console.log('timeout'), 0);
foo();
Promise.resolve().then(() => console.log('promise'));
console.log('script end');
```

A: Output: `script start, foo start, bar, script end, foo end, promise, timeout`

Step-by-step:
1. `console.log('script start')` → `script start`.
2. `setTimeout(...)` → timeout callback queued as macrotask (fires after ~0ms).
3. `foo()` called:
   - `console.log('foo start')` → `foo start`.
   - `await bar()` — calls `bar()` synchronously:
     - `console.log('bar')` → `bar`.
     - `bar()` returns a resolved Promise (async function always returns Promise).
   - `await` suspends `foo()`. Schedules `foo`'s resumption as a microtask (after `bar()`'s Promise resolves).
4. `Promise.resolve().then(() => console.log('promise'))` → schedules `promise` callback as microtask.
5. `console.log('script end')` → `script end`.
6. **Microtask queue drains** (two microtasks):
   - Microtask 1: `foo` resumes → `console.log('foo end')` → `foo end`.
   - Microtask 2: `console.log('promise')` → `promise`.
7. **Macrotask**: `console.log('timeout')` → `timeout`.

The key: `await bar()` schedules `foo`'s resumption as a microtask. `Promise.resolve().then(...)` also schedules a microtask. Both are in the microtask queue before `timeout`. The order of microtasks: `foo`'s resumption was scheduled first (by `await`), so it runs before `promise`.

**Q25. "How would you implement a simple event loop in pseudocode?"**
A:

```
// Simplified event loop pseudocode:

macrotaskQueue = Queue()
microtaskQueue = Queue()
callStack = Stack()

function runTask(task):
  callStack.push(task)
  task.execute()        // runs synchronous JS; may enqueue microtasks/macrotasks
  callStack.pop()
  drainMicrotasks()     // always drain microtasks after each task

function drainMicrotasks():
  while microtaskQueue is not empty:
    microtask = microtaskQueue.dequeue()
    callStack.push(microtask)
    microtask.execute() // may enqueue more microtasks
    callStack.pop()
    // loop continues — newly enqueued microtasks are processed in the same drain

// Main event loop:
while true:
  if macrotaskQueue is not empty:
    task = macrotaskQueue.dequeue()   // ONE task per iteration
    runTask(task)
    // drainMicrotasks already called inside runTask
    maybeRender()                     // browsers: update UI if needed
  else:
    sleep_until_new_task_arrives()    // block thread (I/O wait)
```

**Q26. "What is the output, and what does it reveal about microtask vs. macrotask timing?"**

```js
console.log('A');

setTimeout(() => {
  console.log('B');
  Promise.resolve().then(() => console.log('C'));
}, 0);

setTimeout(() => {
  console.log('D');
}, 0);

Promise.resolve().then(() => {
  console.log('E');
  setTimeout(() => console.log('F'), 0);
});

console.log('G');
```

A: Output: `A, G, E, B, C, D, F`

Step-by-step:
1. `A` — synchronous.
2. `setTimeout(→B→C, 0)` → macrotask queue: `[B-task]`.
3. `setTimeout(→D, 0)` → macrotask queue: `[B-task, D-task]`.
4. `Promise.resolve().then(→E→F)` → microtask queue: `[E-task]`.
5. `G` — synchronous.
6. **Microtask drain**:
   - Run E-task: prints `E`. `setTimeout(→F)` → macrotask queue: `[B-task, D-task, F-task]`. Queue empty.
7. **Macrotask**: B-task runs: prints `B`. `Promise.resolve().then(→C)` → microtask queue: `[C-task]`.
8. **Microtask drain**: prints `C`. Queue empty.
9. **Macrotask**: D-task runs: prints `D`. No microtasks enqueued.
10. **Macrotask**: F-task runs: prints `F`.

Key insights: (a) The microtask `E` runs before any macrotask (B or D). (b) `F` (scheduled from within a microtask) goes to the *end* of the macrotask queue, after B and D. (c) Each macrotask (B, D, F) is followed by a full microtask drain — `C` runs right after `B`, not after `D`.

**Q27. "In one sentence each, state the key property of the call stack, microtask queue, and macrotask queue."**
A:
- **Call stack**: executes synchronous code in LIFO order — only one frame runs at any instant, and the event loop cannot process any queued work while it is non-empty.
- **Microtask queue**: drains completely (including any microtasks enqueued during draining) after every task and before any rendering or next macrotask — making microtasks ideal for work that must happen "immediately after" the current operation, before anything else can intervene.
- **Macrotask queue**: contributes exactly one task per event loop iteration — ensuring that long-running callbacks cannot starve other macrotasks indefinitely, and that each task gets a full microtask drain and rendering opportunity afterward.

Predict the exact console output of the following code and explain the event loop reasoning behind each line.

Multi-queue ordering problem — distinguish synchronous execution, Promise microtasks, `queueMicrotask` microtasks, and setTimeout macrotasks. Trace the call stack, microtask queue, and macrotask queue state at each step.

## Problem 2 — Implement `asyncMap` with Concurrency Control

### Problem
Implement `asyncMap(items, asyncFn, concurrency)` that processes `items` array by applying `asyncFn` to each item asynchronously, running at most `concurrency` async operations simultaneously. Preserves output order (result[i] corresponds to items[i]). Returns a Promise resolving to the results array.

```js
const results = await asyncMap(
  [1, 2, 3, 4, 5],
  async (n) => {
    await delay(Math.random() * 100); // simulate variable-time async work
    return n * 2;
  },
  2 // at most 2 concurrent operations
);
// results = [2, 4, 6, 8, 10] (order preserved)
```

### Pattern Recognition
Promise-based concurrency control — use a "worker pool" of `concurrency` parallel Promise chains. Each worker pulls items from a shared index and processes them sequentially. All workers run concurrently. `Promise.all` waits for all workers to finish.

### Key Insight
The naive approach (`items.map(asyncFn)`) runs all async operations simultaneously — no concurrency control. The controlled approach: create `concurrency` independent "worker" Promises. Each worker shares a mutable index pointer and processes items one at a time, advancing the pointer atomically (safely in single-threaded JS). Workers naturally stop when the index exceeds the array length.

### Solution

```js
async function asyncMap(items, asyncFn, concurrency) {
  const results = new Array(items.length);
  let index = 0; // shared index — safe because JS is single-threaded

  // Each worker is a Promise that repeatedly picks the next item and processes it
  async function worker() {
    while (index < items.length) {
      const i = index++; // capture current index, advance atomically (single-threaded: safe)
      results[i] = await asyncFn(items[i], i); // await preserves result at correct index
    }
  }

  // Start 'concurrency' workers, all running concurrently
  const workers = Array.from(
    { length: Math.min(concurrency, items.length) },
    worker
  );

  await Promise.all(workers); // wait for all workers to exhaust the item list
  return results;
}

// Helper for testing:
const delay = (ms) => new Promise(resolve => setTimeout(resolve, ms));
```

### Dry Run

```
items = [A, B, C, D, E], asyncFn = slow(item), concurrency = 2

index = 0, results = [_, _, _, _, _]

Two workers start simultaneously:

Worker 1:                        Worker 2:
i=0 (index→1), await slow(A)    i=1 (index→2), await slow(B)
  ↓ (A finishes first)
results[0] = slowResult(A)
i=2 (index→3), await slow(C)      ↓ (B finishes)
                                 results[1] = slowResult(B)
  ↓ (C finishes)                 i=3 (index→4), await slow(D)
results[2] = slowResult(C)
i=4 (index→5), await slow(E)      ↓ (D finishes)
                                 results[3] = slowResult(D)
                                 index(5) >= length(5) → Worker 2 exits
  ↓ (E finishes)
results[4] = slowResult(E)
index(5) >= length(5) → Worker 1 exits

Promise.all([Worker1, Worker2]) resolves → return results
```

### Why `index++` is safe without a mutex
JavaScript is single-threaded. `await` is the only point where another piece of code can run. Between `const i = index++` and the next `await`, no other worker can execute. So `index` is always incremented and captured atomically from each worker's perspective — no race condition.

### Complexity
- Time: O(n/concurrency × avgTime) — items are distributed across `concurrency` workers; total wall-clock time is roughly `⌈n/concurrency⌉ × avg(asyncFn)`.
- Space: O(n) — results array + at most `concurrency` in-flight Promises.

### Edge Cases
- `concurrency >= items.length`: all items start simultaneously — equivalent to `Promise.all(items.map(asyncFn))`.
- `concurrency = 1`: fully sequential — each item processed after the previous completes.
- `items = []`: `Math.min(0, 0) = 0` workers; `Promise.all([])` resolves immediately; returns `[]`.
- `asyncFn` throws: the worker's `while` loop's `await` rejects; the worker Promise rejects; `Promise.all` rejects. The remaining workers continue until they complete (but `Promise.all` already rejected — their results are discarded). Use `Promise.allSettled` if you want all results even when some fail.

### Follow-up Questions
- "Handle errors gracefully (don't stop other items)?" → Wrap `asyncFn` in a try/catch inside the worker; store `{ status: 'fulfilled', value }` or `{ status: 'rejected', reason }` — matches `Promise.allSettled` semantics.
- "Add progress callbacks?" → Call `onProgress(i, result)` after each `results[i] = await asyncFn(...)`.
- "Make `concurrency` dynamically adjustable?" → Replace the static `concurrency` count with a semaphore: a counter + queue of waiting Promises that release on decrement — allows live adjustment.

## Problem 3 — Implement a Microtask-Safe Event Emitter

### Problem
Implement an `EventEmitter` class where emitted events deliver callbacks as **microtasks** (not synchronously). This prevents emitter callers from being affected by slow or throwing listeners, and ensures listeners run after the current synchronous code completes.

```js
const emitter = new EventEmitter();

emitter.on('data', (val) => console.log('listener 1:', val));
emitter.on('data', (val) => console.log('listener 2:', val));

emitter.emit('data', 42);
console.log('after emit');

// Output:
// "after emit"           ← synchronous, before any listeners
// "listener 1: 42"       ← microtask
// "listener 2: 42"       ← microtask
```

### Pattern Recognition
Event emitter with deferred delivery — use `queueMicrotask` to schedule each listener call as a microtask rather than calling listeners synchronously inside `emit`. Listeners are isolated from each other (one throwing doesn't prevent others).

### Key Insight
Standard EventEmitter implementations (Node.js `EventEmitter`, DOM `EventTarget`) call listeners synchronously inside `emit` — if a listener throws, subsequent listeners may not run, and the `emit` caller is exposed to listener exceptions. Microtask delivery fixes both: each listener is scheduled independently, and exceptions in one listener don't affect others (each is an independent microtask).

### Solution

```js
class EventEmitter {
  constructor() {
    this._listeners = new Map(); // event name → array of listeners
  }

  on(event, listener) {
    if (!this._listeners.has(event)) {
      this._listeners.set(event, []);
    }
    this._listeners.get(event).push(listener);
    return this; // enable chaining: emitter.on('a', fn).on('b', fn)
  }

  off(event, listener) {
    if (!this._listeners.has(event)) return this;
    const listeners = this._listeners.get(event);
    const idx = listeners.indexOf(listener);
    if (idx !== -1) listeners.splice(idx, 1);
    return this;
  }

  once(event, listener) {
    // Wrap: call listener once then auto-remove
    const wrapper = (...args) => {
      this.off(event, wrapper);
      listener(...args);
    };
    return this.on(event, wrapper);
  }

  emit(event, ...args) {
    if (!this._listeners.has(event)) return false;

    // Snapshot listeners at emit time — prevents mutation mid-iteration
    const listeners = [...this._listeners.get(event)];

    for (const listener of listeners) {
      // Schedule each listener as an INDEPENDENT microtask
      // → async delivery: 'after emit' logs before listeners
      // → isolated: one listener throwing doesn't stop others
      queueMicrotask(() => {
        try {
          listener(...args);
        } catch (err) {
          // Emit as a separate microtask to avoid swallowing errors
          queueMicrotask(() => { throw err; });
        }
      });
    }

    return listeners.length > 0;
  }

  // Utility: wait for next occurrence of an event as a Promise
  waitFor(event) {
    return new Promise((resolve) => {
      this.once(event, resolve);
    });
  }
}
```

### Dry Run

```js
const emitter = new EventEmitter();

emitter.on('data', (v) => console.log('L1:', v));
emitter.on('data', (v) => console.log('L2:', v));

// State: _listeners = { 'data': [L1, L2] }

emitter.emit('data', 42);
// listeners snapshot = [L1, L2]
// queueMicrotask(→ L1(42))  → MICROTASK QUEUE: [M1]
// queueMicrotask(→ L2(42))  → MICROTASK QUEUE: [M1, M2]
// emit returns true

console.log('after emit');
// CALL STACK: prints "after emit"
// Synchronous code complete.

// MICROTASK DRAIN:
// M1: L1(42) → prints "L1: 42"
// M2: L2(42) → prints "L2: 42"

// Output: "after emit", "L1: 42", "L2: 42" ✓
```

### Complexity
- `on`/`off`: O(1) amortized (array push/indexOf).
- `emit`: O(L) where L = number of listeners for the event — one `queueMicrotask` call per listener.
- Memory: O(total listeners across all events).

### Edge Cases
- Listener added during `emit`: the snapshot `[...this._listeners.get(event)]` prevents newly-added listeners from receiving the current emission — consistent with Node.js semantics.
- Listener removed during `emit`: same — snapshot prevents the removal from affecting the current emission.
- Listener throws: the try/catch inside the microtask catches it; re-throwing in another `queueMicrotask` ensures it's reported as an unhandled error without affecting the next listener's microtask.
- `waitFor` with `once`: after the event fires, `wrapper` removes itself before calling `listener` (which here is `resolve`) — preventing memory leaks.

### Follow-up Questions
- "Make delivery synchronous instead?" → Replace `queueMicrotask(() => { try { listener(...args) } ... })` with direct `try { listener(...args) } catch (e) { ... }` — Node.js `EventEmitter` behavior.
- "Support async listeners and await all completions?" → `emit` returns `Promise.all(listeners.map(l => Promise.resolve().then(() => l(...args))))` — waits for all async listeners to resolve.
- "Add listener count limit (max listeners warning)?" → Track `this._maxListeners` (default 10); warn when adding more than the limit — same as Node.js's `setMaxListeners`.

## Problem 4 — Build a Promise-Based Scheduler

### Problem
Implement a `Scheduler` class that limits the number of concurrently running async tasks to a fixed maximum. Tasks are submitted via `add(asyncFn)` which returns a Promise resolving to the task's result. Tasks exceeding the concurrency limit are queued and run when a slot opens.

```js
const scheduler = new Scheduler(2); // max 2 concurrent

const delay = (ms, val) => new Promise(r => setTimeout(() => r(val), ms));

scheduler.add(() => delay(300, 'A')).then(v => console.log(v, Date.now() - start));
scheduler.add(() => delay(200, 'B')).then(v => console.log(v, Date.now() - start));
scheduler.add(() => delay(100, 'C')).then(v => console.log(v, Date.now() - start));
scheduler.add(() => delay(100, 'D')).then(v => console.log(v, Date.now() - start));

// Output (approximate):
// B ~200ms  (started immediately at t=0, finishes at t=200)
// C ~300ms  (started at t=200 when B slot freed, finishes at t=300)
// A ~300ms  (started immediately at t=0, finishes at t=300)
// D ~400ms  (started at t=300 when A or C slot freed, finishes at t=400)
```

### Pattern Recognition
Concurrency semaphore with a Promise queue — maintain a count of running tasks and a queue of pending tasks with their resolve/reject handlers. When a task finishes, check the queue and start the next task if a slot is available.

### Key Insight
Each call to `add()` returns a Promise to the caller. That Promise resolves when the task *finishes* — not when it starts. The scheduler internally manages when tasks actually execute. The queue stores `{ fn, resolve, reject }` entries — the resolve/reject from `add()`'s returned Promise. When a slot opens, the scheduler calls `fn()`, awaits it, and calls `resolve(result)` or `reject(error)`.

### Solution

```js
class Scheduler {
  constructor(maxConcurrent) {
    this.maxConcurrent = maxConcurrent;
    this.running = 0;          // currently executing task count
    this.queue = [];           // pending tasks: { fn, resolve, reject }
  }

  add(asyncFn) {
    // Return a Promise that resolves when asyncFn completes
    return new Promise((resolve, reject) => {
      // Enqueue the task with its Promise handlers
      this.queue.push({ fn: asyncFn, resolve, reject });
      this._tryRunNext(); // attempt to start immediately if slots are available
    });
  }

  _tryRunNext() {
    // Start tasks while slots are available and tasks are waiting
    while (this.running < this.maxConcurrent && this.queue.length > 0) {
      const { fn, resolve, reject } = this.queue.shift();
      this._execute(fn, resolve, reject);
    }
  }

  async _execute(fn, resolve, reject) {
    this.running++;
    try {
      const result = await fn();   // run the actual async task
      resolve(result);             // fulfill the caller's Promise
    } catch (err) {
      reject(err);                 // reject the caller's Promise
    } finally {
      this.running--;
      this._tryRunNext();          // a slot freed up — start the next queued task
    }
  }
}
```

### Dry Run

```
Scheduler(maxConcurrent=2), start = Date.now()

t=0: add(→delay(300,'A'))
  → queue: [{A,resolveA,rejectA}]
  → _tryRunNext: running(0) < 2, queue not empty → _execute(A)
    running=1, queue: []
  → Promise returned to caller: promiseA (pending)

t=0: add(→delay(200,'B'))
  → queue: [{B,resolveB,rejectB}]
  → _tryRunNext: running(1) < 2 → _execute(B)
    running=2, queue: []
  → promiseB (pending)

t=0: add(→delay(100,'C'))
  → queue: [{C,resolveC,rejectC}]
  → _tryRunNext: running(2) >= 2 → WAIT (queue: [C])
  → promiseC (pending)

t=0: add(→delay(100,'D'))
  → queue: [C, D]
  → _tryRunNext: running(2) >= 2 → WAIT (queue: [C, D])
  → promiseD (pending)

State at t=0: running=2 (A, B), queue=[C, D]

t=200ms: B's delay resolves
  → _execute for B: result='B', resolveB('B') → promiseB resolves → logs "B ~200ms"
  → finally: running=1, _tryRunNext()
    running(1) < 2, queue=[C,D] → _execute(C), running=2, queue=[D]

t=300ms: A's delay resolves (simultaneously with C finishing)
  Actually: A fires at t=300 (started t=0, 300ms delay)
            C fires at t=300 (started t=200, 100ms delay)
  Both _execute finallys run (order by microtask scheduling — interleaved):
  A resolves: resolveA('A') → logs "A ~300ms"; running--, _tryRunNext
  C resolves: resolveC('C') → logs "C ~300ms"; running--, _tryRunNext
  After both: running=0, _tryRunNext × 2 → starts D (and... no more tasks)

t=400ms: D resolves → logs "D ~400ms"
```

### Complexity
- `add()`: O(1) — enqueue + possibly start a task.
- `_execute()`: O(1) overhead per task beyond the task's own async time.
- Space: O(Q) where Q = number of queued (not yet started) tasks.

### Edge Cases
- `maxConcurrent = 1`: fully sequential — each task waits for the previous to finish before starting.
- `maxConcurrent = Infinity` (or very large): all tasks start immediately — equivalent to `Promise.all(tasks.map(fn => fn()))`.
- Task throws: `reject(err)` is called — the caller's `add()` Promise rejects. The scheduler continues to the next task (`_tryRunNext()` in `finally`).
- `add()` called after some tasks complete: `_tryRunNext()` checks `running < maxConcurrent` — if slots are available, the task starts immediately.
- `queue.shift()` ordering: FIFO — tasks execute in the order they were added when concurrent slots are available.

### Follow-up Questions
- "Support task cancellation?" → `add()` returns `{ promise, cancel }`. Cancelling removes the task from the queue (if not yet started) or signals running tasks via an `AbortSignal`.
- "Support priority queues (high-priority tasks run first)?" → Replace `this.queue = []` (FIFO) with a priority queue ordered by a `priority` field passed to `add(asyncFn, priority)`.
- "Pause and resume the scheduler?" → Add a `paused` flag: `_tryRunNext` returns early if `this.paused`. `resume()` sets `paused = false` and calls `_tryRunNext()`.

## Quick Reference — Event Loop Cheat Sheet

```
EXECUTION ORDER (one event loop iteration):

  [1] SYNCHRONOUS CODE               runs immediately on call stack
      ↓ (call stack empties)
  [2] process.nextTick (Node.js)     before Promise microtasks
      ↓
  [3] MICROTASKS                     drain completely (including newly added ones)
      • Promise .then/.catch/.finally
      • await resumptions
      • queueMicrotask()
      • MutationObserver (browsers)
      ↓ (microtask queue empty)
  [4] RENDERING (browsers only)      requestAnimationFrame → layout → paint
      ↓
  [5] ONE MACROTASK                  then back to [2]
      • setTimeout / setInterval
      • DOM events (click, keydown...)
      • postMessage / MessageChannel
      • setImmediate (Node.js check phase)
      • I/O callbacks (fs, network)

KEY RULES:
  ✓ Call stack must be EMPTY before ANY queued work runs
  ✓ Microtask queue FULLY drains after EACH task (including newly enqueued)
  ✓ Exactly ONE macrotask is processed per iteration (then check microtasks again)
  ✓ setTimeout(fn,0) fires AFTER all microtasks, even microtasks enqueued later
  ✓ Promise executor runs SYNCHRONOUSLY (only .then callbacks are async)
  ✓ async function runs synchronously until first await; resumes as microtask
  ✓ Infinite microtask loop STARVES the event loop (worse than infinite setTimeout)

TIMER ACCURACY:
  setTimeout(fn, N) → fires AT LEAST N ms later (not exactly N)
  Actual delay = N + (time for current stack to clear) + (preceding microtasks)
                   + (preceding macrotasks if any) + (rendering time if any)

NODE.JS SPECIFICS:
  process.nextTick → before Promise microtasks (its own "nextTick queue")
  setImmediate     → check phase (after poll), before next timers phase
  setImmediate vs setTimeout(fn,0): order non-deterministic at top level;
                                     setImmediate always first INSIDE I/O callbacks

BROWSER SPECIFICS:
  requestAnimationFrame → rendering phase (after microtasks, before next macrotask)
  MutationObserver      → microtask level (runs before macrotasks)
  User events (click)   → macrotask (but high-priority task queue)
```

## Common Bugs Checklist

Before submitting any async JavaScript code, verify:

1. **Assuming `setTimeout(fn, 0)` runs immediately after the current line?** — It doesn't. It runs after all synchronous code, all microtasks, and any preceding macrotasks. `setTimeout(fn, 0)` is a lower bound of "after the current stack clears," not "next line."

2. **Forgetting that Promise executors run synchronously?** — `new Promise((resolve) => { console.log('here'); resolve(); })` — "here" prints synchronously, before `.then()` callbacks. Only `.then()`/`.catch()`/`.finally()` callbacks are microtasks.

3. **Assuming `.then()` runs before `setTimeout` just because it was written first?** — Correct that `.then()` runs first, but make sure you know *why*: Promise `.then` callbacks are microtasks; `setTimeout` is a macrotask. Microtasks always drain before the next macrotask, regardless of code order.

4. **Infinite microtask recursion freezing the event loop?** — A Promise `.then()` that enqueues itself (`then(() => { p.then(same) })`) or a `queueMicrotask` loop starves the event loop. The page/process freezes. Use `setTimeout` for work that should yield to other tasks.

5. **Not awaiting async functions in async contexts?** — `async function foo() { await bar(); }; foo();` — the `await` inside `foo` is correctly awaited within `foo`. But the *caller* calling `foo()` without `await` does not wait for `foo` to complete — the caller continues synchronously. Always `await` or `.then()` a returned Promise if you need its result or side effects.

6. **Calling async functions in array methods without awaiting?** — `arr.forEach(async (item) => { await asyncWork(item); })` — `forEach` does not await the returned Promises. Use `for...of` with `await`, or `Promise.all(arr.map(async fn))`, or the `asyncMap` from Problem 2 for concurrency control.

7. **Assuming `Promise.all` short-circuits as soon as one resolves?** — `Promise.all` resolves when ALL Promises resolve. `Promise.race` resolves/rejects when the FIRST settles. `Promise.any` resolves when the FIRST fulfills. `Promise.allSettled` waits for ALL, regardless of success/failure.

8. **Forgetting that `await` inside a `try/catch` catches rejections?** — `try { const r = await riskyFn(); } catch (e) { /* handles rejection */ }` — `await` converts a rejected Promise into a thrown exception, which `try/catch` handles. Without `await`, the rejection is unhandled: `try { riskyFn(); } catch (e) { /* NEVER fires for Promise rejections */ }`.

9. **`process.nextTick` vs `Promise.resolve().then()` ordering in Node.js?** — `process.nextTick` runs before Promise microtasks. If you need something to run before Promise callbacks (but after the current operation), use `process.nextTick`. If you need standard microtask semantics consistent across browser and Node.js, use `queueMicrotask` or `Promise.resolve().then()`.

10. **Creating Promises inside loops without concurrency control?** — `const results = await Promise.all(items.map(item => fetchData(item)))` — all `items.length` fetch calls fire simultaneously. For large arrays or rate-limited APIs, use the concurrency-controlled `asyncMap` (Problem 2) or the `Scheduler` (Problem 4) to limit simultaneous operations.

---

**Final Tip:** The event loop question that trips up the most engineers — even senior ones — is the precise ordering of microtasks vs. macrotasks when both are enqueued from inside each other. The reliable mental model: after *every piece of synchronous code finishes* (whether it's an initial script, a macrotask callback, or a microtask callback), the engine immediately checks the microtask queue and drains it completely before doing anything else. The macrotask queue is only ever consulted when the microtask queue is empty. Internalizing that single rule — microtask queue drains completely between every macrotask — makes the output of even the trickiest event loop puzzle predictable. Pair it with "Promise executors are synchronous" and "each `.then()` hop is one microtask turn," and no ordering question should be surprising.
