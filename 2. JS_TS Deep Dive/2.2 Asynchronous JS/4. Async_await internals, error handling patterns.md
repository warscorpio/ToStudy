## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals

**Q1. What is `async/await`, and what does it compile down to under the hood?**
A: `async/await` is syntactic sugar over **Promises and generator functions**. An `async` function, when called, always returns a Promise. The `await` keyword inside it suspends execution of that function (without blocking the thread) until the awaited Promise settles, then resumes with the resolved value or re-throws the rejection as a synchronous error. Under the hood, the JavaScript engine (or Babel/TypeScript transpilation) transforms an `async` function into a state machine — conceptually similar to a generator-based coroutine where each `await` point is a `yield` point, and the Promise machinery drives the resumption.

```js
// This async function:
async function fetchUser(id) {
  const res = await fetch(`/users/${id}`);
  const data = await res.json();
  return data;
}

// Is roughly equivalent to this Promise chain:
function fetchUser(id) {
  return fetch(`/users/${id}`)
    .then(res => res.json())
    .then(data => data);
}

// And more precisely to this generator-based state machine:
function fetchUser(id) {
  return new Promise((resolve, reject) => {
    const gen = (function* () {
      try {
        const res = yield fetch(`/users/${id}`);
        const data = yield res.json();
        resolve(data);
      } catch (e) {
        reject(e);
      }
    })();

    function step(nextFn, arg) {
      let result;
      try { result = nextFn.call(gen, arg); }
      catch (e) { reject(e); return; }
      if (result.done) return;
      Promise.resolve(result.value).then(
        val => step(gen.next.bind(gen), val),
        err => step(gen.throw.bind(gen), err)
      );
    }
    step(gen.next.bind(gen), undefined);
  });
}
```

**Q2. What does `async` do to a function's return value, and what happens when an `async` function throws?**
A: An `async` function **always returns a Promise**, regardless of what the function body returns:
- If the function returns a non-Promise value `x`, the returned Promise resolves with `x`.
- If the function returns a Promise `p`, the returned Promise adopts `p`'s state (follows/flattens it — doesn't wrap it in another Promise layer).
- If the function throws (explicitly or via an unawaited rejection), the returned Promise **rejects** with the thrown value.

```js
async function returnsValue()   { return 42; }      // resolves with 42
async function returnsPromise() { return Promise.resolve(42); } // resolves with 42 (not wrapped)
async function throws()         { throw new Error('oops'); }    // rejects with Error
async function rejectsAwaited() { await Promise.reject(new Error('fail')); } // rejects

await returnsValue();   // 42
await returnsPromise(); // 42 (not Promise<Promise<42>>)
await throws();         // throws Error('oops') — must be caught
```

**Q3. What is the JavaScript event loop, and where do async/await operations fit into it?**
A: The JavaScript runtime is single-threaded with an **event loop** that continuously processes two types of queues:
- **Macrotask queue** (task queue): setTimeout callbacks, setInterval callbacks, I/O event callbacks, MessageChannel messages.
- **Microtask queue**: Promise `.then`/`.catch`/`.finally` callbacks, `queueMicrotask()` callbacks, `MutationObserver` callbacks.

After each macrotask completes, the engine **drains the entire microtask queue** before starting the next macrotask. `await` suspends the current async function and schedules its resumption as a **microtask** (via the Promise resolution mechanism). This means `await`-resumed code runs before any pending `setTimeout` callbacks, even `setTimeout(fn, 0)`.

```js
console.log('1 - sync');

setTimeout(() => console.log('2 - macrotask'), 0);

Promise.resolve().then(() => console.log('3 - microtask'));

async function run() {
  console.log('4 - async start (sync)');
  await Promise.resolve();
  console.log('5 - after await (microtask)');
}

run();
console.log('6 - sync after run()');

// Output order:
// 1 - sync
// 4 - async start (sync)
// 6 - sync after run()
// 3 - microtask
// 5 - after await (microtask)
// 2 - macrotask
```

**Q4. What is the difference between `await`ing a Promise versus a non-Promise value?**
A: `await` always wraps its operand in `Promise.resolve()` before awaiting. This means:
- `await 42` → suspends briefly (one microtask tick), resolves with `42`. Functionally equivalent to `await Promise.resolve(42)`.
- `await somePromise` → suspends until `somePromise` settles.
- `await undefined` → suspends briefly, resolves with `undefined`.

The key nuance: even `await nonPromise` introduces at least one **microtask delay** — the function is suspended and scheduled for resumption, even though there's nothing asynchronous to wait for. This can occasionally matter for ordering guarantees in complex async orchestration.

### Section 2: Error Handling

**Q5. What are the three standard patterns for handling errors in async/await code, and what are the trade-offs of each?**
A:

**Pattern 1: `try/catch` block** — The most readable, mirrors synchronous error handling. Catches both synchronous errors (thrown inside the `try` block) and asynchronous rejections (via `await`).

```js
async function fetchData(url) {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    console.error('Fetch failed:', err.message);
    return null; // or re-throw, or return a default value
  }
}
```

**Pattern 2: `.catch()` on the returned Promise** — Useful when you want to handle errors at the call site rather than inside the function, or when you can't modify the async function.

```js
const data = await fetchData(url).catch(err => {
  console.error(err);
  return null;
});
```

**Pattern 3: Await with `.catch()` inline (Go-style)** — Inspired by Go's `(result, error)` pattern. Avoids nesting, explicit about which specific `await` might fail, keeps the function body flat.

```js
async function fetchData(url) {
  const [res, fetchErr] = await fetch(url).then(r => [r, null]).catch(e => [null, e]);
  if (fetchErr) return handleError(fetchErr);

  const [data, parseErr] = await res.json().then(d => [d, null]).catch(e => [null, e]);
  if (parseErr) return handleError(parseErr);

  return data;
}

// Or with a small helper:
const to = p => p.then(v => [null, v]).catch(e => [e, null]);

async function fetchData(url) {
  const [fetchErr, res] = await to(fetch(url));
  if (fetchErr) { /* handle */ return; }

  const [parseErr, data] = await to(res.json());
  if (parseErr) { /* handle */ return; }

  return data;
}
```

**Q6. What is an "unhandled Promise rejection," how does it arise, and why is it dangerous?**
A: An unhandled Promise rejection occurs when a Promise rejects and **no rejection handler** (`.catch()`, second argument to `.then()`, or `try/catch` around `await`) is attached before the current microtask queue drains. It's dangerous because in Node.js (since v15) and modern browsers, it terminates the process or logs a critical error — and in older environments, it silently swallows the error, making bugs invisible.

Common ways unhandled rejections arise:
```js
// 1. Forgetting to await (rejection never observed):
async function example() {
  fetchData(url); // returns a Promise that might reject — but we're not awaiting it
}

// 2. Awaiting without try/catch (rejection propagates up uncaught):
async function example() {
  const data = await fetchData(url); // if this rejects, the rejection propagates...
  // but only if the CALLER also handles it:
  // example().catch(...)  — if the caller doesn't catch, it's unhandled
}

// 3. Creating a Promise in a setTimeout (rejection detached from any await chain):
setTimeout(() => {
  Promise.reject(new Error('detached')); // always unhandled — no chain attached
}, 100);
```

**Q7. What is the `unhandledRejection` event in Node.js, and how should it be used?**
A: Node.js emits `'unhandledRejection'` on the `process` object whenever a Promise rejects without a handler. This is your **last line of defense** — a global safety net for unexpected errors that slipped through local error handling. It should log the error and optionally exit the process cleanly (to avoid running in a corrupted/unknown state after an unhandled rejection).

```js
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Rejection at:', promise, 'reason:', reason);
  // In production: log to error monitoring service (Sentry, Datadog, etc.)
  // Then optionally: process.exit(1)
});

process.on('uncaughtException', (err) => {
  console.error('Uncaught Exception:', err);
  process.exit(1); // always exit after uncaught exception — state is unreliable
});
```

**Q8. What is the difference between re-throwing an error and wrapping it in a new Error — when should each be used?**
A:
- **Re-throwing** (`throw err`) preserves the original error's stack trace and message, passing it up the call chain unchanged. Appropriate when the current level has no additional context to add and just wants errors to propagate to a higher-level handler.
- **Wrapping** (`throw new Error('context: ' + err.message)`) or using `Error.cause` (ES2022) adds context about what operation failed, which is invaluable when errors are logged far from where they originated. The `cause` option preserves the original error as the `cause` property, maintaining the full chain.

```js
// Re-throw: appropriate when the error is self-explanatory
async function readConfig(path) {
  try {
    return await fs.readFile(path, 'utf8');
  } catch (err) {
    if (err.code === 'ENOENT') throw err; // re-throw: clear enough on its own
    throw err; // re-throw unknown errors
  }
}

// Wrapping with context: appropriate when the source is non-obvious at the point of failure
async function loadUserProfile(userId) {
  try {
    return await db.query('SELECT * FROM users WHERE id = ?', [userId]);
  } catch (err) {
    // Without context, a "connection refused" error tells you nothing about
    // which operation was being performed or for which user
    throw new Error(`Failed to load profile for user ${userId}`, { cause: err });
  }
}

// Accessing the chain:
try {
  await loadUserProfile(42);
} catch (err) {
  console.log(err.message);       // "Failed to load profile for user 42"
  console.log(err.cause.message); // "Connection refused" (original)
  console.log(err.cause.stack);   // original stack trace preserved
}
```

### Section 3: Common Pitfalls

**Q9. What goes wrong when you use `async` callbacks inside `Array.forEach`, and what's the fix?**
A: `Array.forEach` ignores the return value of its callback — it doesn't await the Promises returned by `async` callbacks. This means all iterations fire simultaneously (each starts an async operation), but `forEach` itself returns `undefined` synchronously, not a Promise that resolves when all callbacks complete. Any errors thrown inside the async callback become unhandled rejections.

```js
// BROKEN: forEach doesn't await — runs all in parallel, errors are unhandled
async function processAll(items) {
  items.forEach(async (item) => {
    await doWork(item); // these run in parallel, uncaught rejections
  });
  // reaches here BEFORE any async work completes
}

// FIX 1: sequential processing — for...of loop
async function processAllSequential(items) {
  for (const item of items) {
    await doWork(item); // each waits for the previous to finish
  }
}

// FIX 2: parallel processing — Promise.all with map
async function processAllParallel(items) {
  await Promise.all(items.map(item => doWork(item)));
  // all run in parallel, errors are properly propagated
}
```

**Q10. What is the "sequential vs. parallel" anti-pattern with multiple `await`s, and how do you write each intentionally?**
A: Multiple sequential `await`s introduce unnecessary latency when the operations are independent — each waits for the previous to complete before starting, even when they could run simultaneously.

```js
// SLOW: sequential — total time = T(fetchUser) + T(fetchPosts)
async function loadDashboard(userId) {
  const user  = await fetchUser(userId);   // waits for this...
  const posts = await fetchPosts(userId);  // ...then starts this
  return { user, posts };
}

// FAST: parallel — total time = max(T(fetchUser), T(fetchPosts))
async function loadDashboard(userId) {
  const [user, posts] = await Promise.all([
    fetchUser(userId),
    fetchPosts(userId)
  ]);
  return { user, posts };
}

// INTENTIONAL SEQUENTIAL: when each result depends on the previous
async function loginAndFetch(credentials) {
  const session = await login(credentials);      // must finish first...
  const profile = await fetchProfile(session.id); // ...needs the session
  return profile;
}
```

**Q11. What is the "await in a loop vs. Promise.all" trade-off, and when is sequential actually correct?**
A: The choice between sequential (`for...of` with `await`) and parallel (`Promise.all`) must be intentional:
- **Parallel** (`Promise.all`) is correct when operations are independent and can safely run concurrently — minimizes total time.
- **Sequential** (`for...of`) is correct when: (a) each operation depends on the result of the previous (data dependency), (b) the operations have side effects that must happen in order (database writes, file system operations that conflict), or (c) resource/rate-limit constraints require serialization.

```js
// Rate-limited API: must serialize to avoid hitting rate limits
async function fetchAllWithRateLimit(ids) {
  const results = [];
  for (const id of ids) {
    results.push(await fetchWithDelay(id)); // sequential — intentional
    await sleep(100); // rate limiting delay
  }
  return results;
}

// Bounded parallelism: run at most N concurrent operations
async function processWithConcurrencyLimit(items, limit) {
  const results = [];
  for (let i = 0; i < items.length; i += limit) {
    const batch = items.slice(i, i + limit);
    const batchResults = await Promise.all(batch.map(processItem));
    results.push(...batchResults);
  }
  return results;
}
```

**Q12. What is `Promise.allSettled` and when should it be used instead of `Promise.all`?**
A: `Promise.all` **short-circuits on the first rejection** — if any input Promise rejects, the whole `Promise.all` rejects immediately, and results from the other promises are discarded. `Promise.allSettled` **waits for all promises to settle** (resolve or reject), and returns an array of result objects each with a `status` field (`'fulfilled'` or `'rejected'`) and either a `value` or `reason` field.

Use `Promise.allSettled` when:
- You want **all operations to complete** even if some fail.
- You want to process **partial successes** — use what succeeded, log/handle what failed.
- Failures are expected and non-fatal for the overall operation.

```js
// Promise.all: first failure stops everything
const [user, posts] = await Promise.all([fetchUser(id), fetchPosts(id)]);
// If fetchPosts rejects, we lose the fetchUser result too

// Promise.allSettled: get all results regardless of failures
const results = await Promise.allSettled([fetchUser(id), fetchPosts(id)]);
// results[0] = { status: 'fulfilled', value: userData }
// results[1] = { status: 'rejected', reason: Error('404') }

const successes = results.filter(r => r.status === 'fulfilled').map(r => r.value);
const failures  = results.filter(r => r.status === 'rejected').map(r => r.reason);
```

**Q13. What is `Promise.race` vs `Promise.any`, and what is each useful for?**
A:
- **`Promise.race(promises)`**: resolves or rejects with the **first settled Promise** — whichever finishes first, regardless of whether it fulfilled or rejected. Use for timeouts (race against a delay Promise) or "first responder" patterns where the fastest response wins, even if it's an error.
- **`Promise.any(promises)`**: resolves with the **first fulfilled Promise** (ignoring rejections until all reject, at which point it rejects with `AggregateError`). Use when you have multiple fallback strategies and want the first successful one, regardless of order.

```js
// Promise.race: timeout pattern — rejects if the operation takes too long
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error(`Timeout after ${ms}ms`)), ms)
  );
  return Promise.race([promise, timeout]);
}

const data = await withTimeout(fetchHeavyData(), 5000);

// Promise.any: try multiple CDN servers, use the fastest successful one
const asset = await Promise.any([
  fetch('https://cdn1.example.com/asset.js'),
  fetch('https://cdn2.example.com/asset.js'),
  fetch('https://cdn3.example.com/asset.js')
]);
// If cdn1 and cdn2 are down, cdn3's response is returned
// If ALL fail, AggregateError is thrown
```

### Section 4: Advanced Patterns

**Q14. How do you correctly cancel an in-flight async operation using `AbortController`?**
A: `AbortController` provides a standard cancellation mechanism for async operations that support it (native `fetch`, some Node.js APIs, and custom code). An `AbortController` owns an `AbortSignal`; when `controller.abort()` is called, the signal fires an `abort` event and its `aborted` property becomes `true`. APIs that accept a `signal` option throw or reject with an `AbortError` when aborted.

```js
async function fetchWithCancellation(url) {
  const controller = new AbortController();
  const { signal } = controller;

  // Cancel if the operation takes more than 3 seconds
  const timeoutId = setTimeout(() => controller.abort(), 3000);

  try {
    const res = await fetch(url, { signal }); // fetch respects the signal
    const data = await res.json();
    clearTimeout(timeoutId);
    return data;
  } catch (err) {
    if (err.name === 'AbortError') {
      console.log('Fetch was cancelled');
      return null;
    }
    throw err; // re-throw non-cancellation errors
  }
}

// In a UI context: cancel in-flight request when user navigates away
class DataLoader {
  #controller = null;

  async load(url) {
    this.cancel(); // cancel any previous in-flight request
    this.#controller = new AbortController();
    try {
      return await fetch(url, { signal: this.#controller.signal }).then(r => r.json());
    } catch (err) {
      if (err.name !== 'AbortError') throw err;
    }
  }

  cancel() {
    this.#controller?.abort();
  }
}
```

**Q15. How do you implement a retry pattern with exponential backoff for flaky async operations?**
A: Retry with exponential backoff is the standard approach for transient failures (network timeouts, temporary service unavailability). Each attempt waits progressively longer before retrying, with optional jitter (random variation) to prevent "thundering herd" problems where many clients retry at exactly the same moment.

```js
async function withRetry(fn, {
  maxAttempts = 3,
  initialDelay = 200,   // ms
  maxDelay = 10_000,    // ms cap
  factor = 2,           // exponential multiplier
  jitter = true,        // add randomness to avoid stampede
  shouldRetry = (err) => true // predicate: which errors are retryable?
} = {}) {
  let attempt = 0;
  let delay = initialDelay;

  while (attempt < maxAttempts) {
    try {
      return await fn();
    } catch (err) {
      attempt++;
      if (attempt >= maxAttempts || !shouldRetry(err)) throw err;

      const jitterMultiplier = jitter ? (0.5 + Math.random() * 0.5) : 1;
      const waitTime = Math.min(delay * jitterMultiplier, maxDelay);

      console.log(`Attempt ${attempt} failed. Retrying in ${Math.round(waitTime)}ms...`);
      await new Promise(resolve => setTimeout(resolve, waitTime));
      delay *= factor; // exponential growth for next delay
    }
  }
}

// Usage: retry only on network errors, not 4xx responses
const data = await withRetry(
  () => fetch('/api/data').then(r => {
    if (!r.ok) throw Object.assign(new Error(`HTTP ${r.status}`), { status: r.status });
    return r.json();
  }),
  {
    maxAttempts: 5,
    shouldRetry: (err) => !err.status || err.status >= 500 // retry server errors, not client errors
  }
);
```

**Q16. What is the async generator pattern, and when would you use it over returning an array of Promises?**
A: An **async generator** (`async function*`) is a function that `yield`s values asynchronously — callers consume them one at a time with `for await...of`, without needing to materialize all results upfront. This is the correct pattern for **streaming data** (paginated API responses, file reading line by line, real-time event streams) where buffering all results in memory would be wasteful or impossible.

```js
// Async generator: paginated API traversal
async function* fetchAllPages(baseUrl) {
  let page = 1;
  let hasMore = true;

  while (hasMore) {
    const res = await fetch(`${baseUrl}?page=${page}&limit=100`);
    const { items, total, perPage } = await res.json();

    for (const item of items) {
      yield item; // yields one item at a time to the consumer
    }

    hasMore = page * perPage < total;
    page++;
  }
}

// Consumer: processes items as they arrive, without loading all pages first
for await (const user of fetchAllPages('/api/users')) {
  await processUser(user); // handles each one individually
}

// With early termination (stops fetching after first match):
for await (const user of fetchAllPages('/api/users')) {
  if (user.email === 'target@example.com') {
    console.log('Found:', user);
    break; // generator is automatically cleaned up via .return()
  }
}
```

### Section 5: Scenario / Interview-Style Questions

**Q17. "You have three API calls where B depends on A's result and C is independent. How do you optimize?"**
A: Fetch A first (because B needs it), then start B and C in parallel (C doesn't depend on A, so it should start as early as possible — the moment execution starts, not after A resolves):

```js
async function optimizedFetch() {
  // Start C immediately — it's independent of A and B
  const cPromise = fetchC(); // started but NOT awaited yet

  // Start A and wait for it (B needs A's result)
  const aResult = await fetchA();

  // Now start B (depends on A) and await both B and C in parallel
  const [bResult, cResult] = await Promise.all([
    fetchB(aResult),
    cPromise // already in-flight since the start of this function
  ]);

  return { aResult, bResult, cResult };
}
// Total time ≈ max(T(A) + T(B), T(C)) — optimal given the dependency constraints
```

**Q18. "An async function throws but the error is never caught. What happens in Node.js, and how do you prevent it?"**
A: If an `async` function rejects and no `.catch()`, `try/catch`, or error handler at the call site handles the rejection, Node.js emits an `unhandledRejection` event. Since Node.js v15, this also terminates the process with exit code 1 by default (earlier versions only emitted the event without exiting). Prevention strategies: (1) always `await` async functions inside `try/catch` or chain `.catch()`; (2) add a global `process.on('unhandledRejection', ...)` handler as a safety net; (3) use linting rules (e.g., `no-floating-promises` in TypeScript with `@typescript-eslint`) to catch unawaited promises at compile time.

**Q19. "How would you implement a Promise-based queue that processes at most N tasks concurrently?"**
A: Maintain a counter of currently-running tasks; when a task completes, decrement the counter and start the next queued task if capacity is available:

```js
class AsyncQueue {
  #concurrency;
  #running = 0;
  #queue = [];

  constructor(concurrency) {
    this.#concurrency = concurrency;
  }

  add(fn) {
    return new Promise((resolve, reject) => {
      this.#queue.push({ fn, resolve, reject });
      this.#tick();
    });
  }

  #tick() {
    while (this.#running < this.#concurrency && this.#queue.length > 0) {
      const { fn, resolve, reject } = this.#queue.shift();
      this.#running++;
      Promise.resolve(fn())
        .then(resolve, reject)
        .finally(() => {
          this.#running--;
          this.#tick(); // try to start the next queued task
        });
    }
  }
}

// Usage: process up to 3 API calls simultaneously
const queue = new AsyncQueue(3);
const results = await Promise.all(
  items.map(item => queue.add(() => fetchItem(item)))
);
```

**Q20. "What is the 'async tax' and when should you consider synchronous alternatives?"**
A: The "async tax" refers to the overhead introduced by `async/await` — even `async` functions that perform no actual asynchronous work create a Promise object and schedule their resolution as a microtask, adding a small but nonzero overhead versus a direct synchronous return. This is measurable in hot paths called millions of times per second (e.g., tight loops, high-frequency event handlers, WebAssembly interop). In most application code, this overhead is negligible and the readability/maintainability benefits of `async/await` far outweigh it. However, in performance-critical library code, avoiding unnecessary `async` functions (using synchronous returns where possible) can be worthwhile — V8 has optimized many async patterns over time, but the fundamental microtask overhead remains.

## Problem 1 — Parallel Fetch with `Promise.all` and Proper Error Handling

### Problem
Fetch user data from three different endpoints simultaneously. If any fetch fails, throw a descriptive error that preserves the original cause. If all succeed, return a merged result object.

```js
// Must be faster than sequential fetching
// Must handle partial failures with clear error messages
// Must preserve the original error for debugging
```

### Pattern Recognition
`Promise.all` for parallel execution, `Error.cause` for error wrapping with context, `try/catch` inside the `async` function.

### Key Insight
`Promise.all` fails fast on the first rejection — appropriate here because all three pieces of data are required for a meaningful result. Wrapping errors with context is critical in parallel scenarios because the error's source (which of the three endpoints failed) is otherwise invisible in the stack trace.

### Solution

```js
async function fetchUserDashboard(userId) {
  try {
    const [profile, settings, activity] = await Promise.all([
      fetchProfile(userId),
      fetchSettings(userId),
      fetchActivity(userId)
    ]);

    return { profile, settings, activity };
  } catch (err) {
    // Without wrapping, the error gives no context about which call failed
    // or for which user — both critical for debugging in production
    throw new Error(
      `Failed to load dashboard for user ${userId}`,
      { cause: err }
    );
  }
}

// Helper: simulate async fetch with error possibility
async function fetchProfile(userId) {
  const res = await fetch(`/api/users/${userId}/profile`);
  if (!res.ok) throw new Error(`Profile fetch failed: HTTP ${res.status}`);
  return res.json();
}

// Caller
try {
  const dashboard = await fetchUserDashboard(42);
  renderDashboard(dashboard);
} catch (err) {
  console.error(err.message);       // "Failed to load dashboard for user 42"
  console.error(err.cause.message); // "Profile fetch failed: HTTP 404"
  // err.cause.stack has the original stack trace ✓
}
```

### Verification

```js
// Test: all succeed
const result = await fetchUserDashboard(1);
// → { profile: {...}, settings: {...}, activity: {...} }

// Test: one fails
// → throws Error: "Failed to load dashboard for user 1"
//   with cause: Error: "Settings fetch failed: HTTP 403"

// Test: parallel vs sequential timing
console.time('parallel');
await fetchUserDashboard(1); // ≈ max(T_profile, T_settings, T_activity)
console.timeEnd('parallel');

console.time('sequential');
await fetchProfile(1);
await fetchSettings(1);
await fetchActivity(1); // ≈ T_profile + T_settings + T_activity (much slower)
console.timeEnd('sequential');
```

### Edge Cases
- If `userId` doesn't exist: all three fetches may return 404, `Promise.all` fails on the first rejection and the error is wrapped. The specific failing endpoint is preserved in `err.cause`.
- If network is offline: `fetch` throws a `TypeError` (not an HTTP error response) — the `try/catch` catches it, wraps it, and the `cause` preserves the network error.
- If only partial data is acceptable (e.g., activity is optional): split into two `Promise.all` calls or use `Promise.allSettled` for the optional parts.

### Follow-up Questions
- "What if some fields are optional and their failure shouldn't fail the whole dashboard?" → Use `Promise.allSettled` for the optional fields and `Promise.all` only for required ones, then merge results.
- "What if you need to show whatever loaded even on partial failure?" → `Promise.allSettled` with processing of individual settled results — see Problem 2.

## Problem 2 — Resilient Parallel Fetch with `Promise.allSettled`

### Problem
Fetch user profile (required), user posts (optional), and user recommendations (optional). Return whatever succeeded. Log each failure individually without blocking the overall response.

```js
// Profile failure → reject the whole thing (it's required)
// Posts/recommendations failure → return partial result, log the error
```

### Pattern Recognition
Mixed strategy: `Promise.all` for the required element plus `Promise.allSettled` for optional elements, combining their results.

### Key Insight
`Promise.allSettled` lets you distinguish "the operation failed but we still have other useful data" from the `Promise.all` all-or-nothing model. The caller code is responsible for deciding what to do with partial results.

### Solution

```js
async function loadUserPage(userId) {
  // Profile is required — if it fails, the whole page fails
  const profile = await fetchProfile(userId); // let rejection propagate if it fails

  // Posts and recommendations are optional — collect what we can
  const [postsResult, recommendationsResult] = await Promise.allSettled([
    fetchPosts(userId),
    fetchRecommendations(userId)
  ]);

  // Process settled results
  const posts = postsResult.status === 'fulfilled'
    ? postsResult.value
    : (() => {
        console.error('Posts unavailable:', postsResult.reason.message);
        return []; // graceful default
      })();

  const recommendations = recommendationsResult.status === 'fulfilled'
    ? recommendationsResult.value
    : (() => {
        console.error('Recommendations unavailable:', recommendationsResult.reason.message);
        return []; // graceful default
      })();

  return { profile, posts, recommendations };
}
```

### Verification

```js
// All succeed:
// → { profile: {...}, posts: [...], recommendations: [...] }

// Profile fails:
// → throws (caller must handle)

// Posts fail, recommendations succeed:
// → console.error: "Posts unavailable: HTTP 503"
// → { profile: {...}, posts: [], recommendations: [...] }

// Both optional fail:
// → console.error x2
// → { profile: {...}, posts: [], recommendations: [] }
```

### Edge Cases
- Logging inside the IIFE `(() => { ... })()` is one approach; alternatively, process the results in a loop for more uniform handling of many optional fields.
- If you need to report to the caller WHICH fields failed (not just log them), include a `warnings` array in the returned object: `{ profile, posts, recommendations, warnings: [...failures] }`.

### Follow-up Questions
- "What if all fields are optional and you want to return an empty object rather than throw?" → Wrap the entire `Promise.allSettled` in a try/catch free function, always resolving to an object (potentially empty) with a `warnings` key for failures.

## Problem 3 — Sequential Async Processing with `for await...of`

### Problem
Process a list of file paths sequentially — read each file, transform its content, and write the result. Each operation must complete before the next begins. Collect all errors but don't stop processing.

```js
const paths = ['a.json', 'b.json', 'c.json'];
const results = await processFiles(paths);
// → { succeeded: ['a.json', 'c.json'], failed: [{ path: 'b.json', error: Error }] }
```

### Pattern Recognition
`for...of` with `await` for intentional sequential processing; per-iteration `try/catch` for independent error handling per item; accumulating successes and failures separately.

### Key Insight
Sequential processing here is intentional — file system operations can conflict when parallelized (file locking, resource contention). Per-iteration `try/catch` means one failure doesn't abort the others — we want to process everything and report what failed.

### Solution

```js
async function processFiles(paths) {
  const succeeded = [];
  const failed = [];

  for (const path of paths) {
    try {
      const content = await fs.readFile(path, 'utf8');
      const transformed = transform(JSON.parse(content));
      await fs.writeFile(path.replace('.json', '.out.json'), JSON.stringify(transformed));
      succeeded.push(path);
    } catch (err) {
      // Per-file error: don't abort the loop, just record the failure
      failed.push({ path, error: err });
    }
  }

  return { succeeded, failed };
}

function transform(data) {
  // ... business logic ...
  return { ...data, processedAt: new Date().toISOString() };
}
```

### Verification

```js
const { succeeded, failed } = await processFiles(['a.json', 'missing.json', 'b.json']);

console.log(succeeded); // ['a.json', 'b.json']
console.log(failed);    // [{ path: 'missing.json', error: Error: ENOENT... }]
// Processing continued after missing.json failed ✓
// a.json and b.json were still processed ✓
```

### Edge Cases
- `JSON.parse` errors: caught by the same `try/catch`, treated as processing failures (not read failures) — the error message distinguishes them.
- Write permission errors: also caught; the file was read and transformed but couldn't be written — the error preserves the file path and reason.
- Empty `paths` array: loop never executes, returns `{ succeeded: [], failed: [] }` immediately.

### Follow-up Questions
- "What if processing order doesn't matter but you want bounded parallelism (e.g., 3 at a time)?" → Use the `AsyncQueue` from Q19 or the batch-with-`Promise.all` pattern from Q11, replacing the sequential `for...of` loop.

## Problem 4 — Async Error Boundary with Retry and Timeout

### Problem
Implement a robust `safeCall` wrapper that: (1) retries the operation up to 3 times on failure, (2) enforces a maximum total timeout across all attempts, (3) distinguishes non-retryable errors (4xx status) from retryable ones (network errors, 5xx), and (4) returns a typed result object instead of throwing.

```js
const result = await safeCall(() => fetchData(url), { timeout: 5000, maxRetries: 3 });
if (!result.ok) {
  console.error('Failed:', result.error.message);
} else {
  use(result.value);
}
```

### Pattern Recognition
Combines timeout (`AbortController` or `Promise.race`), retry with backoff, error classification, and a result-object pattern (eliminating the need to wrap call sites in try/catch).

### Key Insight
Returning `{ ok: boolean, value, error }` instead of throwing moves error handling from the exception path (which requires `try/catch` everywhere) to the happy path (a simple `if (!result.ok)` check) — familiar from languages like Rust (`Result<T, E>`) and Go (`(value, err)`). This is particularly useful when `safeCall` is used in many places.

### Solution

```js
async function safeCall(fn, {
  timeout = 10_000,
  maxRetries = 3,
  backoff = 300,
  isRetryable = (err) => !err.status || err.status >= 500
} = {}) {
  const deadline = Date.now() + timeout;
  let lastError;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const remaining = deadline - Date.now();
    if (remaining <= 0) {
      return { ok: false, error: new Error('Total timeout exceeded'), value: undefined };
    }

    try {
      // Race the operation against the remaining timeout
      const value = await Promise.race([
        fn(),
        new Promise((_, reject) =>
          setTimeout(() => reject(Object.assign(new Error('Operation timed out'), { isTimeout: true })), remaining)
        )
      ]);
      return { ok: true, value, error: undefined };

    } catch (err) {
      lastError = err;

      if (err.isTimeout) {
        return { ok: false, error: err, value: undefined };
      }

      if (!isRetryable(err) || attempt >= maxRetries) {
        return { ok: false, error: err, value: undefined };
      }

      // Exponential backoff before next attempt
      const delay = Math.min(backoff * 2 ** attempt, 5000);
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }

  return { ok: false, error: lastError, value: undefined };
}

// Usage
async function fetchData(url) {
  const res = await fetch(url);
  if (!res.ok) {
    throw Object.assign(new Error(`HTTP ${res.status}`), { status: res.status });
  }
  return res.json();
}

const result = await safeCall(() => fetchData('/api/data'), {
  timeout: 5000,
  maxRetries: 3
});

if (!result.ok) {
  logError(result.error);
} else {
  render(result.value);
}
```

### Verification

```js
// Scenario 1: first attempt succeeds
// → { ok: true, value: {...} }

// Scenario 2: fails twice then succeeds on third attempt
// → console logs two "retrying" messages, then { ok: true, value: {...} }

// Scenario 3: 404 (non-retryable) — no retry, immediate failure
// → { ok: false, error: Error('HTTP 404') }

// Scenario 4: timeout exceeded before any success
// → { ok: false, error: Error('Total timeout exceeded') }
```

### Edge Cases
- `fn` itself might throw synchronously (not return a Promise) — `Promise.race` handles this because `fn()` is called inside it, and synchronous throws become rejected Promises.
- `deadline` drift: each attempt reduces `remaining` by the time taken so far, preventing total timeout from being exceeded even with multiple retries.
- `maxRetries: 0`: the loop runs exactly once (attempt 0), and on failure immediately returns without retrying.

### Follow-up Questions
- "How would you make this cancellable (so the caller can cancel mid-retry)?" → Accept an `AbortSignal` and check `signal.aborted` at the start of each loop iteration; also pass the signal to `fn` if it accepts one.
- "TypeScript version with proper generics?" → `async function safeCall<T>(fn: () => Promise<T>, ...): Promise<{ ok: true; value: T } | { ok: false; error: Error }>` — the discriminated union makes TypeScript narrow the type correctly at the `if (!result.ok)` check.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve coordinating multiple async operations or handling async errors?
│
├── SINGLE ASYNC OPERATION, need error handling?
│   └── try/catch around await — or .catch() at the call site
│
├── MULTIPLE INDEPENDENT OPERATIONS, ALL must succeed?
│   └── Promise.all([op1, op2, op3]) — fails fast on first rejection
│
├── MULTIPLE OPERATIONS, want ALL results (successes AND failures)?
│   └── Promise.allSettled([op1, op2, op3])
│       → each result has { status: 'fulfilled'|'rejected', value|reason }
│
├── MULTIPLE FALLBACK STRATEGIES, want FIRST SUCCESS?
│   └── Promise.any([op1, op2, op3]) — rejects with AggregateError only if ALL fail
│
├── RACE AGAINST TIMEOUT or want FIRST SETTLED (success OR failure)?
│   └── Promise.race([operation, timeoutPromise])
│
├── SEQUENTIAL PROCESSING (each step depends on previous, or must be ordered)?
│   └── for...of with await — intentional, explicit sequential execution
│       (NOT forEach — it doesn't await async callbacks)
│
├── PARALLEL WITH BOUNDED CONCURRENCY (don't overwhelm server/rate limits)?
│   └── Batch with Promise.all in chunks, or AsyncQueue class
│
├── STREAMING / PAGINATED DATA (too much to load all at once)?
│   └── async generator (async function*) + for await...of
│
├── CANCELLABLE OPERATION?
│   └── AbortController + AbortSignal — pass signal to fetch/custom async code
│       → catch AbortError specifically to handle cancellation gracefully
│
├── TRANSIENT FAILURES (network blips, rate limits)?
│   └── withRetry() with exponential backoff + jitter + isRetryable predicate
│
└── AVOID THROWING AT EVERY CALL SITE?
    └── Result-object pattern: return { ok, value, error } instead of throwing
        → caller uses if (!result.ok) check instead of try/catch
```

## Common Bugs Checklist

Before shipping any async/await code, verify:

1. **`async` callbacks in `forEach`, `map`, `filter`, `reduce` are properly awaited?** — `forEach` ignores returned Promises entirely; `map` returns `Promise[]` not `Promise<T[]>` — must wrap with `await Promise.all(arr.map(async fn))`. `filter`/`reduce` with async callbacks are even trickier and usually need explicit `for...of` loops instead.

2. **Unintentional sequential `await`s on independent operations?** — Two `await`s in a row when the second doesn't need the first's result means unnecessary serialization. Start both Promises before awaiting either, then use `Promise.all`.

3. **`try/catch` scope is wide enough — but not too wide?** — A single `try/catch` wrapping many `await`s catches all of them, but you lose information about WHICH one failed. For different error-handling strategies per operation, use separate `try/catch` blocks or per-operation `.catch()`.

4. **Error swallowing: `catch` block returns silently without logging or re-throwing?** — A `catch (err) { return null; }` with no logging is almost always a bug — at minimum, log the error. Returning `null` silently can propagate unexpected nulls through the codebase.

5. **Unhandled rejections from unawaited Promises?** — `fetchData(url);` (no `await`, no `.catch()`) creates a floating Promise that silently fails. Always `await` or chain `.catch()` on every Promise you create.

6. **`Promise.all` with non-parallel-safe operations?** — Not all operations are safe to run concurrently: operations that share a transaction, write to the same file, or depend on each other's side effects must remain sequential. `Promise.all` is for genuinely independent operations.

7. **`AbortError` not checked specifically when handling fetch cancellation?** — Checking `err.name === 'AbortError'` (not `err instanceof AbortError`) is the portable way since `AbortError` is not a standard global in all environments. Treating `AbortError` as a failure (logging, retrying) is usually wrong — it was intentional cancellation.

8. **`Error.cause` compatibility: using `{ cause: err }` option of `new Error()`?** — Available in Node.js 16.9+, Chrome 93+, Firefox 91+. In older environments, manually attach the cause: `const wrapped = new Error('msg'); wrapped.cause = originalErr;` — the effect is the same, just not standardized.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to reason about async code in terms of the **event loop** (microtasks drain completely before macrotasks, which is why `await` resumptions run before `setTimeout` callbacks), to make **intentional choices** between sequential and parallel execution with explicit justification (not "sequential by default"), and to design **robust error handling** that distinguishes retryable from non-retryable errors, wraps errors with context, and never silently swallows failures. The strongest signal is proactively noting the `forEach` async anti-pattern before being asked, naming `Promise.allSettled` vs `Promise.all` as a deliberate architectural choice based on whether partial results are acceptable, and demonstrating that `async/await` is transparent syntax over Promises — not a fundamentally different execution model.
