# What to Cache, What Not to Cache — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does caching solve, and what is its core mechanism?**
A: Caching solves the mismatch between the cost of computing or fetching data and the frequency with which that data is needed. The mechanism: store the result of an expensive operation in a faster, closer store; serve subsequent requests from there instead of repeating the work. "Expensive" can mean slow (DB query across a network), CPU-intensive (rendering, aggregation), or financially costly (third-party API with per-call pricing). Caching trades memory for latency, throughput, and cost.

**Q2. What are the three things that make data a good cache candidate?**
A: A useful heuristic — data is cacheable when it is:
- **Expensive to produce** — the cost of generating or fetching it is meaningfully higher than reading from cache. If the source is already fast, caching adds complexity with little gain.
- **Read more than it's written** — a high read/write ratio means cached data is served many times between invalidations. Data that changes as often as it's read benefits little from caching.
- **Tolerant of some staleness** — the application can function correctly if the cached value is slightly behind the authoritative source. The tolerance window defines how aggressive invalidation needs to be.

All three should hold. A single missing property is usually a signal to not cache.

**Q3. What is cache hit rate, and why is it the primary health metric for a cache?**
A: Cache hit rate is the fraction of requests served from cache rather than the backing store: `hits / (hits + misses)`. It directly determines how much benefit the cache provides. A 50% hit rate means half the requests still go to the DB — marginal gain. A 99% hit rate means only 1 in 100 requests reaches the DB — the cache is load-bearing. Most production caches are only valuable above ~80–90% hit rate; below that, the operational complexity rarely justifies the benefit.

**Q4. What is the difference between cache-aside, write-through, write-behind, and read-through caching?**
A:
- **Cache-aside (lazy loading)** — the application checks the cache first; on a miss, it fetches from the DB, writes to the cache, and returns the result. The application owns the cache interaction. Cache only contains what was actually requested.
- **Read-through** — the cache sits in front of the DB and handles misses itself. The application always reads from cache; the cache fetches from DB on a miss transparently. Simpler for the application but the cache layer is more complex.
- **Write-through** — every write goes to both the cache and the DB synchronously. Keeps the cache consistent but doubles write latency and caches data that may never be read again.
- **Write-behind (write-back)** — writes go to the cache immediately; persistence to the DB is asynchronous. Faster writes, but risks data loss if the cache node fails before flushing, and the DB is temporarily stale.

**Q5. What is a cold cache, and why does it matter for system design?**
A: A cold cache is one that starts empty — no data has been loaded yet, so every request is a miss until the cache warms up. Cold caches happen on service restarts, cache cluster failures, or first deployment. During warmup, all traffic falls through to the DB, which may receive more load than it was sized to handle if the system was designed assuming high hit rates. Cold start is a critical operational scenario: systems should have a plan (pre-warming, gradual traffic ramp, circuit breakers on the DB) rather than discovering it in production under a rollout.

**Q6. What is the difference between caching at different layers (CDN, application, database)?**
A:
- **CDN / edge cache** — caches HTTP responses close to users geographically. Best for static assets, public API responses, rendered HTML. Not suitable for user-specific or rapidly changing data.
- **Application-layer cache (Redis, Memcached)** — caches computed results, DB query results, session data. Lives between the application servers and the DB. Handles dynamic data the CDN can't.
- **Database-level cache (buffer pool, query cache)** — the DB itself caches data pages and (in some DBs) query results in memory. This is automatic and always present; it means a "DB hit" that goes to the buffer pool is far cheaper than a disk read. Tuning DB memory allocation is a form of caching.
- **In-process / local cache** — a hashmap or LRU cache inside the application process. Zero network overhead, but not shared across instances; can serve stale data across deployments, and consumes process heap memory.

## Section 2: What to Cache

**Q7. What types of data are the strongest candidates for caching?**
A: The best candidates share the property that computing or fetching them is expensive relative to how often the data changes:
- **Reference / lookup data** — country codes, currency exchange rates, product categories, configuration tables. Changes rarely, read constantly; a near-perfect cache candidate.
- **Expensive aggregations** — leaderboard rankings, dashboard metrics, analytics roll-ups. Computing them requires scanning many rows; results can be pre-computed and cached on a schedule.
- **External API responses** — results from third-party APIs (geocoding, weather, enrichment services) that are rate-limited or per-call priced. Caching reduces both cost and latency, and the data rarely changes within seconds.
- **Session data** — user authentication tokens, preferences, shopping cart state. Frequently accessed on every request; relatively small, user-scoped, and naturally expires.
- **Rendered output** — HTML fragments, serialized JSON payloads, email templates. If the same response is served to many users (or the same user repeatedly), caching the rendered output avoids re-serialization and templating overhead.
- **Hot database rows** — records that appear in many queries (e.g., a viral post, a top-selling product). A small fraction of rows account for most reads; caching the hot fraction dramatically reduces DB load.

**Q8. What makes static assets an obvious caching target?**
A: Static assets (images, JS bundles, CSS, fonts) never change for a given URL (once deployed they are immutable if content-addressed). Hit rate approaches 100% for returning users. They can be cached at every layer: browser, CDN, reverse proxy. The correctness risk is zero — a stale static asset just means an old version, which is usually acceptable for the duration of a CDN TTL. Content-addressed URLs (`/app.a3f8bc.js`) make cache invalidation trivial: changing the content changes the URL, so the old version naturally expires and the new version is a cache miss.

**Q9. What is "read-heavy workload amplification" and why does it make something cache-worthy?**
A: When a single write event causes many subsequent reads of the result. A social media post written once may be read by millions of followers — the read amplification is massive. Caching the post's rendered content means one DB write but zero DB reads for all subsequent views until the cache expires. The higher the read/write ratio for a piece of data, the more each cached entry earns its keep.

**Q10. When is caching computed/derived data more valuable than caching raw data?**
A: When the computation is expensive relative to reading raw rows. Example: computing a user's recommendation feed involves joining purchase history, similarity scores, and inventory — possibly hundreds of DB operations. Caching the final recommendation list (the derived result) saves all of that work per request. Caching the raw input rows individually would still require re-running the expensive join on every request. Cache at the level where the most computation is saved, not necessarily the lowest level.

**Q11. What is a "thundering herd" and how does caching address it?**
A: A thundering herd occurs when a cache entry expires (or the cache goes cold) and many concurrent requests simultaneously experience a miss, all racing to fetch the same data from the backing store — amplifying load at the worst moment. Caching directly reduces the steady-state herd (most requests hit cache), but the expiry event itself can still trigger a mini-herd. Mitigations: probabilistic early expiration (refresh slightly before expiry), mutex/single-flight (only one request fetches from DB while others wait for the cached result), and staggered TTLs (add random jitter to expiry times to prevent synchronized expiry across many keys).

## Section 3: What Not to Cache

**Q12. What types of data should never be cached?**
A:
- **Highly personalized data with low reuse** — data unique to a single user that no other request will benefit from. If cache hit rate on a key is ~1 (one request, then expiry), caching adds overhead with no benefit.
- **Data where correctness is non-negotiable** — financial balances, inventory counts, medical records. Serving a stale cached balance during a payment or a stale stock count during checkout can cause real financial harm. The cost of incorrectness exceeds the benefit of reduced latency.
- **Write-heavy data** — data that changes so frequently that cached entries are invalidated before being reused. The cache becomes a write-amplification layer with no read benefit.
- **Large, rarely reused blobs** — caching a 50MB video file for a single view wastes cache memory that could serve thousands of small hot records. Caches have finite memory; use it for high-reuse, high-value entries.
- **Data with complex invalidation dependencies** — if invalidating one piece of data requires invalidating many other dependent cached entries in non-obvious ways, the cache becomes a consistency liability that's hard to reason about correctly.

**Q13. Why is caching financial balances or inventory counts dangerous?**
A: These values are the source of truth for transactions with real consequences. Serving a cached balance of $1,000 while the actual balance is $0 (after a recent debit) allows an overdraft. Serving a cached stock count of 5 while actual stock is 0 allows overselling. The correct approach is to always read these values from the authoritative source at transaction time, using pessimistic or optimistic locking to ensure consistency. Post-transaction, you might cache derived display values (e.g., the last-known balance for a dashboard widget), but the transaction itself must read fresh.

**Q14. Why is caching the results of authentication and authorization checks risky?**
A: Permissions and session validity change in ways that must take effect immediately: a user's role is revoked, their session is terminated after a security incident, or their account is suspended. Caching these checks means a revoked user continues to be authorized until the cache entry expires — a security window that could be minutes or hours depending on TTL. Short TTLs reduce the window but don't eliminate it; for high-security contexts, auth checks should always hit the authoritative source, or the cache must be invalidated explicitly on permission change events.

**Q15. What is "cache poisoning" and which data types are most vulnerable?**
A: Cache poisoning is when incorrect, malicious, or corrupted data enters the cache and is then served to many users. Particularly dangerous for shared/public caches (CDN, reverse proxy) where a poisoned entry affects all users, not just one. Most vulnerable: public API responses where the cache key doesn't include all relevant request parameters (e.g., caching a user-specific response under a public key), responses built from untrusted user input, and any cache without TTL (a poisoned entry lives forever). Data that is user-specific or security-sensitive should not be placed in shared caches.

**Q16. Why is caching data with high cardinality but low reuse a waste?**
A: High cardinality means many distinct keys (e.g., individual user activity feeds, one-time search queries, per-session ephemeral state). Low reuse means each cached entry is read rarely before expiry. The cache fills with many entries each used once, evicting more valuable hot entries. Cache memory is a finite resource; filling it with low-reuse data reduces the hit rate for everything else — a net negative. The rule: cache entries should be accessed many times before they expire, not just once.

**Q17. What is the "write-invalidate amplification" problem and which data patterns trigger it?**
A: When a single write must invalidate many cached entries — e.g., updating a user's display name might need to invalidate cached versions of every post, comment, and profile reference for that user across many cache keys. Each invalidation is a cache write; at high write rates or with complex dependency graphs, the invalidation work itself becomes expensive. Data with many derived cached representations (fan-out on write) is a poor cache candidate unless you design an explicit invalidation strategy upfront.

**Q18. Should you cache database query results that include joins across many tables?**
A: Sometimes — but carefully. Caching the final result of a complex join is valuable (saves re-running expensive query). The danger: any change to any of the joined tables should invalidate the cache, but tracking those dependencies across multiple tables is complex and error-prone. A change to `orders` invalidates the cache, a change to `users` invalidates the cache, a change to `products` invalidates the cache — you need to instrument every write path to all source tables. Prefer caching derived aggregates at a higher level (e.g., a pre-computed report) with a simple scheduled refresh, rather than trying to maintain exact consistency for a complex multi-table query result.

## Section 4: Cache Invalidation

**Q19. Why is cache invalidation considered one of the hardest problems in computer science?**
A: Phil Karlton's maxim: "There are only two hard things in computer science: cache invalidation and naming things." The difficulty is that the cache and its backing store are two separate systems that must be kept consistent, without a transaction that spans both. Every strategy for keeping them in sync involves a trade-off: TTL-based expiry tolerates staleness; event-driven invalidation requires every write path to reliably notify the cache; write-through doubles write latency. No strategy is both consistent and available when the cache and source diverge. Getting it wrong is silent — stale data often looks correct.

**Q20. What are the main cache invalidation strategies and their trade-offs?**
A:
- **TTL (Time-To-Live)** — entries expire automatically after a fixed duration. Simple, no write-path instrumentation needed. Trade-off: serves stale data for up to TTL duration; setting TTL requires knowing acceptable staleness upfront.
- **Event-driven / active invalidation** — on write, explicitly delete or update the affected cache key(s). Keeps cache fresh but requires every write path to know which cache keys to invalidate — brittle as the system grows.
- **Write-through** — write to cache and DB synchronously on every update. Cache always reflects the latest write. Trade-off: doubles write latency; caches data that may never be read; cache node failure blocks writes.
- **Cache-aside with short TTL** — lazy loading with a TTL short enough that staleness is acceptable. The simplest practical strategy for most use cases.
- **Versioned keys** — embed a version or hash in the cache key. To "invalidate," increment the version; old keys are naturally orphaned and eventually evicted. No active deletion needed. Trade-off: orphaned keys consume memory until eviction; requires version tracking infrastructure.

**Q21. What is "stale-while-revalidate" and when is it the right strategy?**
A: Stale-while-revalidate serves the cached (possibly stale) entry immediately while asynchronously refreshing it in the background. The user never waits for a cache miss — they get a fast (slightly stale) response, and the cache is updated for the next request. Ideal for data where freshness is preferred but not required: news feeds, recommendation lists, analytics dashboards. Not appropriate where correctness is critical (financial data, inventory counts). It's natively supported in HTTP cache headers (`Cache-Control: stale-while-revalidate=60`) and can be implemented manually in application caches.

**Q22. What is a "cache stampede" and how does mutex/single-flight prevent it?**
A: A cache stampede (variant of thundering herd) is when a popular cache entry expires and many concurrent requests simultaneously miss, each independently fetching from the DB and writing back. The DB receives N parallel identical queries. Mutex/single-flight: when a miss is detected, a flag (distributed lock or in-process mutex) is set. Only the first request actually fetches from the DB; all other concurrent requests for the same key wait for the first to complete and then read the freshly populated cache entry. This reduces N DB queries to 1 at the cost of slightly higher latency for the waiting requests.

**Q23. How do you invalidate a cache entry when the data model spans multiple services?**
A: This is a distributed invalidation problem — Service A writes data, but Service B owns the cache of derived data that depends on it. Options: (1) **Event-driven invalidation via message bus** — Service A publishes a change event; Service B subscribes and invalidates its cache. Decoupled but introduces eventual consistency delay and requires reliable messaging. (2) **Short TTL as a fallback** — if event delivery is delayed or fails, the cache self-corrects within TTL. (3) **Cache ownership alignment** — reorganize so the service that owns the data also owns its cache; avoid cross-service cache invalidation dependencies. (4) **Accept staleness** — if the data relationship is loose enough, tolerate the lag between write and cache update.

## Section 5: Eviction Policies & Cache Sizing

**Q24. What are the common cache eviction policies and when does each apply?**
A:
- **LRU (Least Recently Used)** — evicts the entry that was accessed least recently. Works well when recent access is a good predictor of future access (temporal locality). The most common default for general-purpose caches.
- **LFU (Least Frequently Used)** — evicts the entry accessed the fewest total times. Better than LRU when access patterns are stable over time (a frequently accessed entry that wasn't recently accessed should be kept). Harder to implement; susceptible to cache pollution from historical high-frequency entries that are no longer popular.
- **FIFO (First In First Out)** — evicts the oldest-inserted entry regardless of access pattern. Simple but ignores actual usage; rarely optimal.
- **Random** — evicts a random entry. Surprisingly competitive with LRU in some access patterns, zero bookkeeping overhead. Used in some CPU cache implementations.
- **TTL-based** — entries are evicted after a time window, not based on access. Ensures freshness; doesn't optimize memory usage for hot vs. cold entries.

**Q25. How do you size a cache, and what is the "working set" concept?**
A: The **working set** is the set of distinct data items actively requested within a time window. A cache should be large enough to hold the working set — if it's smaller, evictions constantly push out items that are about to be requested again, causing a high miss rate regardless of policy. Practical sizing: start by measuring your hit rate at current cache size; if it's low, increase size incrementally and observe hit rate improvement. There's usually a "knee of the curve" beyond which adding more memory produces diminishing hit rate returns — cache at that point. A cache that holds 20% of your data can often serve 80–90% of requests if access follows a power-law (Zipf) distribution.

**Q26. What is cache memory pressure and how does it affect system stability?**
A: When the cache uses memory aggressively, it competes with the application process, OS page cache, and DB buffer pool for the same physical RAM. On Redis, an `maxmemory` limit with an eviction policy prevents OOM crashes but starts evicting entries when the limit is hit — watch `evicted_keys` in Redis metrics as a signal of memory pressure. On in-process caches, uncontrolled growth causes JVM GC pressure or native OOM. Cache sizing must account for the full memory budget of the host, not just the cache in isolation.

## Section 6: Failure Modes & Anti-patterns

**Q27. What is "cache-as-database" anti-pattern and why is it dangerous?**
A: Using the cache as the primary store for data that has no durable backing store, relying on it for persistence rather than performance. Redis (with AOF/RDB) can be durable, but it's designed for fast access, not transactional guarantees. If the cache is the only store and it fails, data is gone. The pattern is tempting — it's fast and simple — but it collapses the distinction between cache (expendable, reconstructable) and database (authoritative, durable). The rule: a cache should always be reconstructable from the backing store. If losing the cache would cause data loss, it's a database, not a cache.

**Q28. What is "cache bypass under load" and when is it a problem?**
A: An application that reads from cache on normal requests but bypasses the cache for "accurate" reads under certain conditions (e.g., admin views, post-write reads, certain feature flags) can send unexpectedly high traffic to the DB during load peaks. If these bypass conditions correlate with high traffic (e.g., every new user registration triggers a bypass read), the DB sees load that the cache was supposed to absorb. Audit all cache bypass paths; they are often unintentional DB load vectors.

**Q29. What is "cache key collision" and how does it cause bugs?**
A: When two logically different data items are stored under the same cache key, one overwrites the other and incorrect data is served. Common causes: forgetting to include all relevant dimensions in the key (e.g., caching user data by `user_id` but forgetting `tenant_id` in a multi-tenant system — all tenants see the same user), using the same key prefix for different data types, or auto-generated keys that don't account for all input parameters. Cache key design should be treated as carefully as DB schema design: include every dimension that makes the data unique.

**Q30. What is the "n+1 caching" anti-pattern?**
A: Calling the cache once per item in a loop rather than fetching all needed items in a single batch call. Example: rendering a list of 100 posts by calling `cache.get(post_id)` 100 times in a loop instead of `cache.mget([id1, id2, ..., id100])`. Each individual get is a network round trip to Redis; 100 round trips add up (100 × ~0.5ms = 50ms) even when every key is a hit. Use bulk/pipeline operations (`MGET`, `MSET`, pipelining) when working with multiple cache keys in one request.

**Q31. What is "negative caching" and when should you use it?**
A: Caching the fact that data does *not* exist — e.g., storing a sentinel value (or explicit null) for a key when a DB lookup returned no results. Without negative caching, every request for a non-existent key is a cache miss that goes to the DB — easily exploited by an attacker querying random IDs, or just wasteful if your application legitimately has many "not found" lookups. With negative caching, the first miss hits the DB; subsequent misses are served "not found" from cache. Use a shorter TTL for negative entries than positive ones, since "not found" is more likely to change (the item may be created soon).

**Q32. What is "cache incoherence" in a multi-instance deployment?**
A: When different application instances maintain separate local (in-process) caches, they can diverge. Instance A updates a record and clears its local cache; Instance B still serves the old cached version. External users hitting different instances see inconsistent data. Solutions: (1) use a shared remote cache (Redis) as the only cache — all instances see the same data; (2) broadcast invalidation events to all instances via pub/sub; (3) use extremely short TTLs on local caches and accept brief inconsistency; (4) avoid local caches for anything that changes. Local caches are safe only for truly immutable or process-scoped data.

## Section 7: Trade-offs & Decision-Making

**Q33. How do you decide between a short TTL and event-driven invalidation?**
A: TTL is simpler and requires no write-path instrumentation — the right choice when the cost of brief staleness is low and the write paths are numerous or hard to modify. Event-driven invalidation keeps the cache fresher and is worth the complexity when: staleness causes visible user-facing bugs, data changes frequently within the TTL window, or correctness matters more than implementation simplicity. In practice, use TTL as the baseline safety net even with event-driven invalidation — if an invalidation event is missed or delayed, TTL ensures the entry eventually corrects itself.

**Q34. When is it better to not cache and just make the DB faster?**
A: When the DB query is already fast (sub-millisecond on a good index), the data changes frequently (high invalidation rate), or adding a cache introduces more complexity than the latency saving justifies. DB read replicas, connection pooling, and query optimization often get you further with less operational risk. Cache when you've exhausted DB-level optimization, not as the first resort. A slow query that runs in 200ms and is called 1,000 times/second is a caching candidate. The same query running in 2ms is a better-index candidate.

**Q35. How does caching interact with personalization and A/B testing?**
A: Personalized content (user-specific recommendations, targeted pricing, experiment variants) cannot be cached at a shared layer without the cache key including the personalization dimensions. Adding user ID, experiment group, locale, and device type to the cache key dramatically increases key cardinality and reduces hit rate — for highly personalized content, effective hit rate approaches zero. Caching is most powerful when many users share the same response; personalization is the opposite force. The architecture often splits: cache the non-personalized skeleton of a page at the CDN; inject personalized fragments at the application layer without caching them.

**Q36. What are the hidden operational costs of adding a cache?**
A: Caching is not free even when it works:
- **Operational complexity** — one more system to monitor, alert on, scale, and handle failures for.
- **Debugging difficulty** — bugs that only reproduce when the cache is warm are notoriously hard to find.
- **Consistency reasoning** — every read in the system must be analyzed for whether it can tolerate staleness.
- **Cache warming on restart** — every deployment, failover, or cache flush sends a traffic spike to the DB.
- **Memory cost** — RAM is expensive; over-provisioning the cache wastes money, under-provisioning hurts hit rate.
- **Two-phase writes** — writing to both the DB and cache must be handled carefully (what order? what if one fails?).
Start by questioning whether caching is actually needed before accepting these costs.

## Section 8: Scenario / System Design Style Questions

**Q37. "Design the caching strategy for a social media feed. Each user's feed is an aggregated, ranked list of posts from accounts they follow."**
A: This is a high-read, fan-out-on-write workload. Several layers:
- **Pre-computed feed cache (push model)**: When a user with many followers posts, their post is pushed into each follower's cached feed (fan-out on write). Feed reads are pure cache reads. Trade-off: expensive for high-follower accounts (celebrities posting to millions of feeds). Mitigate with a hybrid: push to active followers, pull for inactive ones.
- **Post content cache**: Cache individual post objects (text, media URLs, metadata) in Redis by post ID. High reuse — the same post appears in many feeds. Short TTL or event-invalidated on post edit/delete.
- **Do not cache**: The real-time feed for the poster (they should see their own post immediately), follower counts used for transaction decisions, or anything requiring strong consistency.
- **CDN**: Cache rendered feed pages for anonymous/logged-out users. Personalized feeds stay behind the application cache.

**Q38. "Your e-commerce product catalog has 10 million SKUs, but 90% of revenue comes from 50,000 products. How do you cache it?"**
A: Classic Zipf/power-law distribution — cache the hot 50,000, not all 10 million. Strategy:
- **Application cache (Redis)**: Cache product detail pages for the top N products by traffic, with TTL of 5–10 minutes. Use LFU eviction so naturally hot items stay in cache and cold items are evicted.
- **Cache key**: `product:{id}:v{version}` — version bump on any product update; no active invalidation needed for the catalog.
- **Do not cache**: real-time inventory count (risk of overselling), personalized pricing per user, or flash-sale pricing that changes by the second.
- **Pre-warm on deployment**: Before traffic shifts to a new deploy, warm the top-N product cache using historical access logs. Prevents cold-start spikes.
- **DB**: Ensure product table has proper indexes; the 9.95 million cold SKUs hit the DB on rare access — acceptable since they're <10% of traffic.

**Q39. "A reporting dashboard shows aggregate metrics (total orders, revenue by region) that take 8 seconds to compute. Users refresh it frequently. What do you do?"**
A: Don't compute on request — pre-compute on a schedule:
- **Scheduled refresh (cron/worker)**: Run the expensive aggregation every N minutes (match to acceptable staleness: 5 minutes is usually fine for dashboards), store the result in Redis or a materialized view. Dashboard reads are always from cache — sub-millisecond.
- **Stale-while-revalidate**: Serve the last cached result immediately while the background job computes the update. Users always see a fast response.
- **TTL as safety net**: Set TTL to 2× the refresh interval so if the refresh job fails, the dashboard degrades gracefully (showing slightly stale data) rather than running the 8-second query on every user request.
- **Do not cache**: the individual transaction records that feed the aggregate — only cache the aggregate output.
- **Avoid**: computing on request even with caching; the 8s query is a time bomb under concurrent dashboard refreshes where multiple users trigger a cache miss simultaneously.

**Q40. "You're seeing frequent cache misses even though you have a large Redis cluster. How do you diagnose the problem?"**
A: Systematic investigation:
1. **Measure hit rate per key prefix**: `redis-cli INFO stats` gives global `keyspace_hits`/`keyspace_misses`. Drill into per-prefix hit rates using `MONITOR` (carefully, in low-traffic window) or application-level metrics to find which data types are missing.
2. **Check TTL values**: `TTL <key>` on sample keys — are TTLs too short for access patterns? High cardinality keys expiring before reuse?
3. **Check eviction**: `evicted_keys` counter climbing → cache is undersized, evicting entries before they can be reused. Fix: increase memory or reduce what's cached.
4. **Check key design**: are cache keys accidentally unique per-request? A key like `user:{id}:request:{request_id}` will always miss. Audit key generation code.
5. **Check cold start**: is this after a recent deployment or Redis restart? If so, it's expected — wait for warmup or pre-warm explicitly.
6. **Check access pattern shift**: a product going viral or a traffic pattern change can shift the working set outside what the cache was sized for.

**Q41. "A teammate proposes caching the result of an authorization check (`can_user_X_access_resource_Y`) for 10 minutes to reduce DB load. How do you respond?"**
A: Push back carefully on the TTL, not the concept. Authorization results can be cached — the concern is the window during which a revoked permission is still honored. 10 minutes is too long for most security contexts: a fired employee or compromised account can access resources for 10 minutes after revocation. Counter-proposal: (1) reduce TTL to 30–60 seconds — enough to reduce DB load significantly, short enough to be operationally acceptable; (2) add explicit cache invalidation when permissions change (user role update, account suspension events); (3) never cache negative authorization for elevated-privilege actions (admin operations, payment actions) even with short TTL — always check fresh. The DB load concern is valid; solve it with short TTL + event invalidation, not a long TTL that becomes a security liability.

| Complex multi-table join results | With care    | High compute value but complex invalidation dependency graph           | Pre-computed materialized view or scheduled refresh|

## Key Concepts Cheat Sheet

| Term                      | One-line definition                                                                                   |
|---                        |---                                                                                                    |
| Cache hit rate            | Fraction of requests served from cache; the primary health metric for any cache                       |
| Working set               | The set of data actively requested within a time window; cache should be sized to hold it             |
| Cold cache                | Empty cache after restart or flush; all traffic falls through to backing store during warmup          |
| Cache-aside               | App checks cache, misses fetch from DB and populate cache; app owns the cache interaction             |
| Write-through             | Writes go to cache and DB synchronously; always consistent, doubles write latency                     |
| Write-behind              | Writes go to cache, async to DB; fast writes, risk of data loss on cache failure                      |
| TTL (Time-To-Live)        | Maximum age of a cache entry; simple staleness bound requiring no write-path instrumentation          |
| Cache stampede            | Popular entry expires; many concurrent misses hit the backing store simultaneously                    |
| Single-flight / mutex     | Only one request fetches on a miss; others wait for the result — eliminates stampede amplification    |
| Stale-while-revalidate    | Serve cached (possibly stale) entry immediately; refresh asynchronously in background                 |
| Negative caching          | Cache "not found" results to prevent repeated DB lookups for non-existent keys                        |
| Cache poisoning           | Incorrect or malicious data enters the cache and is served to many users                              |
| Cache incoherence         | Local caches across instances diverge; different users see different data from different nodes         |
| LRU eviction              | Evict least recently accessed entry; best for workloads with temporal locality                        |
| LFU eviction              | Evict least frequently accessed entry; best for stable long-term popularity distributions             |
| Write-invalidate amplification | A single write triggers invalidation of many dependent cache keys — a sign of poor cache design  |
| Versioned keys            | Embed version in cache key; invalidate by version bump, old keys expire naturally                     |
| n+1 caching               | Fetching cache keys one-by-one in a loop instead of batching — eliminates the latency benefit        |

**Tip for the interview:** Interviewers at 5 YOE level expect you to go beyond "cache the things that are slow." The strongest answers frame caching decisions around three questions: *what is the read/write ratio?*, *what is the cost of serving stale data?*, and *what does invalidation look like?* If any of those three is unfavorable, say so and explain why. Being able to argue *against* caching in specific scenarios — financial data, auth checks, write-heavy rows — shows you understand correctness tradeoffs, not just performance optimization. Bonus points for mentioning the operational costs: cold starts, cache incoherence in multi-instance deployments, and the debugging complexity that comes with adding a cache layer.
