# Cache Coherence in Distributed Systems — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is cache coherence in distributed systems?**
A: Cache coherence is the guarantee that all caches in a distributed system reflect a consistent view of the underlying data at any point in time. When the same data is cached in multiple places (multiple service instances, multiple CDN nodes, multiple layers of a cache hierarchy), a write to the origin must eventually — or immediately, depending on the consistency model — be reflected in every cache that holds a copy. Without coherence mechanisms, different readers can see different versions of the same data simultaneously.

**Q2. Why is cache coherence harder in distributed systems than in a single machine?**
A: In a single machine, the CPU cache coherence protocol (MESI, MOESI) is handled in hardware — it's invisible, instantaneous, and guaranteed. In distributed systems:
- Caches are on separate machines with no shared bus or hardware protocol.
- Network communication introduces latency and the possibility of reordering or loss.
- There is no atomic "update all caches at once" primitive — you must coordinate via messaging, which takes time.
- Partial failures are possible — an update reaches some cache nodes but not others.
- The CAP theorem applies: under a network partition, you must choose between consistency (all caches agree) and availability (all caches respond). CPU caches face no such trade-off.

**Q3. What is the difference between cache coherence and cache consistency?**
A: Often used interchangeably, but have a precise distinction:
- **Cache coherence** — the property that all copies of a specific data item across all caches converge to the same value. It's a per-key guarantee: if you write key K, all caches will eventually (or immediately) reflect the new value of K.
- **Cache consistency** — a broader property describing the ordering guarantees across multiple keys and operations. Strong consistency means reads always reflect the latest write globally. Eventual consistency means all copies converge eventually with no ordering guarantee.

Coherence is a necessary precondition for consistency: you can't have a consistent system if individual keys are incoherent across caches. But coherence alone doesn't guarantee consistency — you also need ordering guarantees across multiple keys.

**Q4. What are the main sources of cache incoherence in distributed systems?**
A:
- **Write-behind lag** — a write to the origin DB is not immediately propagated to all cache nodes.
- **Concurrent writes** — two writers update the same key simultaneously; different caches receive the updates in different orders.
- **Replication lag** — in a primary-replica Redis setup, replicas may serve stale reads before the primary's writes reach them.
- **Network partitions** — a cache node isolated from the rest of the cluster continues serving its last known value.
- **Cache-aside miss with stale DB read** — a cache miss triggers a DB read, but the DB replica read returns stale data (write not yet replicated), which is then cached — incoherence introduced by the DB layer below the cache.
- **TTL misalignment** — different cache layers have different TTLs; a mid-tier cache TTL expires and re-fetches stale data from a downstream cache that hasn't yet expired its old copy.

**Q5. What consistency models apply to distributed caches?**
A:
- **Strong consistency** — every read reflects the most recent write. All caches are updated synchronously before the write is acknowledged. High latency, low availability under partition.
- **Sequential consistency** — all operations appear to execute in some global order, and each client's operations appear in order. Weaker than strong consistency but stronger than eventual.
- **Eventual consistency** — given no new writes, all caches will converge to the same value eventually. No guarantee on when. Highest availability, lowest latency. Most distributed caches operate here by default.
- **Read-your-own-writes consistency** — a specific client is guaranteed to see its own writes immediately, even if others may see stale data. Often implemented via sticky routing or cache write-through for the writing client.
- **Monotonic read consistency** — once a client reads a value, subsequent reads never return an older value. Prevents the confusing case of reading "new" then "old" data on successive reads.

## Section 2: Invalidation Strategies

**Q6. What is cache invalidation and why is it called one of the hardest problems in computer science?**
A: Cache invalidation is the process of removing or updating stale entries in a cache when the underlying data changes. Phil Karlton's quip — "There are only two hard things in Computer Science: cache invalidation and naming things" — reflects that invalidation in distributed systems is genuinely difficult because:
- You must know *which* caches hold a copy of the changed data — non-trivial when data flows through multiple cache layers.
- Invalidation messages can arrive out of order or be lost, leaving caches stale.
- Invalidation itself can create thundering herds — all invalidated keys miss simultaneously.
- A cache may be invalidated while a reader is mid-computation using the old value — atomicity is impossible across the cache + reader.
- You must handle the gap between "write committed to origin" and "all caches invalidated" during which incoherence exists.

**Q7. What is TTL-based invalidation and what are its trade-offs?**
A: TTL (Time-To-Live) is the simplest invalidation strategy: each cache entry has a fixed lifetime after which it expires and is discarded. The next read misses the cache and fetches fresh data.

**Pros:** Zero coordination needed. No invalidation messages. Predictable memory reclamation. Works in any cache topology.

**Cons:**
- Stale data is served for up to the full TTL after a write — bounded staleness, not freshness.
- TTL too short → high miss rate, high origin load.
- TTL too long → stale data visible for too long.
- Synchronized expiry of keys written at the same time → thundering herd (mitigated with TTL jitter).
- No way to instantly reflect a critical update (security patch, price correction) — must wait for TTL.

**Q8. What is active invalidation (event-driven invalidation) and how does it work?**
A: When the origin data changes, a signal is sent to all cache nodes holding that key, instructing them to delete or update the key immediately — without waiting for TTL expiry.

**Implementation patterns:**
- **Pub/Sub:** The writer publishes an invalidation message to a channel (Redis Pub/Sub, Kafka topic). All cache nodes subscribe and delete the key on receipt.
- **Write-through with broadcast:** The application layer updates both the DB and the cache atomically (or near-atomically), ensuring the cache is never stale.
- **Change Data Capture (CDC):** A CDC tool (Debezium, Maxwell) tails the DB write-ahead log and emits invalidation events for every DB row change. Cache nodes consume these events and invalidate matching keys.

**Pros:** Near-instant coherence after writes. No bounded-staleness window.
**Cons:** Requires messaging infrastructure. Invalidation messages can be lost or delayed (requires at-least-once delivery + idempotent handling). Adds operational complexity.

**Q9. What is the "write-through" cache pattern and how does it enforce coherence?**
A: In write-through, every write goes to the cache and the origin simultaneously (or in sequence before acknowledging success). The cache is always updated at write time — reads never see a stale value for a key that has been written through.

```
Client → write(K, V) → Cache.set(K, V) + DB.write(K, V) → ack
Client → read(K)     → Cache.get(K) → returns V (always fresh)
```

**Coherence guarantee:** Strong for the writing client. Other clients reading from the same cache node also see fresh data immediately. Other cache nodes (in a multi-node setup) are not automatically updated — write-through is only coherent within a single cache node unless combined with broadcast invalidation across nodes.

**Q10. What is the "write-behind" (write-back) pattern and what coherence risks does it carry?**
A: In write-behind, writes go to the cache first and are asynchronously flushed to the origin later. Reads are served from cache immediately.

**Coherence risk:** Between the write to cache and the flush to origin, the cache has data that the DB doesn't. Other cache nodes that miss and read from the DB see stale data. If the cache node crashes before flushing, writes are lost. This pattern optimizes write throughput at the cost of coherence and durability.

**Q11. What is the "cache-aside" (lazy loading) pattern and where does coherence break down?**
A: In cache-aside, the application manages the cache explicitly: check cache → on miss, read from DB → write to cache → return. Writes go directly to the DB; the cache is invalidated or updated separately.

**Where coherence breaks:**
- **Write race:** Client A reads a key (cache miss), fetches from DB, is preempted. Client B writes a new value to the DB and deletes the cache key. Client A resumes and writes the now-stale DB value into the cache — the cache now holds stale data that won't expire until TTL.
- **Replication lag:** Client A's cache miss reads from a DB replica that hasn't received the latest write from the primary — stale data gets cached.
- **No invalidation on write:** If the application simply updates the DB without invalidating the cache key, the cache serves stale data until TTL expiry.

## Section 3: Coherence Patterns

**Q12. What is the "delete on write" pattern and why is it preferred over "update on write"?**
A: When the origin data changes, delete the cache key rather than updating it with the new value.

**Why delete is safer than update:**
- **Avoids write races:** If you update the cache with the new value, a concurrent reader may have already fetched the old value and is about to overwrite your update. Deletion forces the next read to re-fetch from the authoritative origin — the DB — which has the correct value.
- **Simpler atomicity:** Deleting a key is a single atomic operation. Updating a key with a new value requires the new value to be computed and the update to be applied atomically — harder to coordinate across distributed writers.
- **Handles complex invalidation:** When a write changes multiple denormalized cache keys (e.g., a product price change invalidates both `product:42` and `category:electronics:products`), deleting all affected keys is simpler than recomputing and updating each.

**Trade-off:** One additional cache miss (the read after delete fetches from origin). Acceptable for most workloads; use write-through if the key is hot enough to warrant pre-population.

**Q13. What is the "look-aside + invalidation" pattern and how does it maintain coherence?**
A: A hybrid approach combining cache-aside reads with active invalidation on writes:

**Read path (cache-aside):**
```
cache.get(K) → hit: return value
             → miss: value = db.read(K); cache.set(K, value, ttl); return value
```

**Write path (invalidate-on-write):**
```
db.write(K, new_value)
cache.delete(K)  ← invalidation, not update
```

**Coherence guarantee:** After a write, the next read for K will miss the cache and fetch fresh data from the DB. Bounded window of incoherence = time between DB write and cache delete (near-zero if done in sequence, longer if the delete is async).

**Residual race:** DB write succeeds, cache delete fails (Redis down). Cache now holds stale data until TTL expiry. Mitigation: use a short TTL as a backstop even when relying on active invalidation.

**Q14. What is the "version key" (cache busting) pattern?**
A: Instead of invalidating a key in place, embed a version identifier in the key name. When data changes, increment the version — old keys become orphaned and expire via TTL; new reads use the new versioned key (and miss, fetching fresh data).

```python
version = db.get_version("product:42")          # e.g., 7
cache_key = f"product:42:v{version}"            # "product:42:v7"
value = cache.get(cache_key) or db.read(...)
```

**On write:**
```python
db.write("product:42", new_value)
db.increment_version("product:42")              # version becomes 8
# No cache delete needed — "product:42:v7" is now orphaned
```

**Pros:** No explicit invalidation message needed. Write races are impossible — the new version key is distinct. Works naturally with CDNs (URL versioning).
**Cons:** Orphaned old-version keys accumulate and must expire via TTL. Requires a version store (additional DB read on cache miss). Key proliferation for high-write-rate data.

**Q15. What is the "two-phase invalidation" pattern for multi-layer cache hierarchies?**
A: In a cache hierarchy (L1 local → L2 Redis → L3 origin), a naive single-phase invalidation deletes the Redis key but leaves stale copies in local in-process caches on other instances. Two-phase invalidation addresses this:

**Phase 1 (broadcast):** When a write occurs, publish an invalidation event to all service instances (via Redis Pub/Sub, a message bus, or a gossip protocol). Each instance deletes the key from its local cache.

**Phase 2 (TTL backstop):** Set a short TTL on the Redis key as well (even with active invalidation). If the Pub/Sub message was missed (instance was down, network hiccup), the TTL ensures eventual coherence.

This two-layer approach provides near-immediate coherence for connected instances and eventual coherence for transiently disconnected ones.

## Section 4: Multi-Layer and Distributed Cache Coherence

**Q16. How does coherence work in a multi-layer cache (L1 local → L2 Redis → L3 DB)?**
A: Each layer introduces a coherence surface:
- **L1 (local in-process):** Per-instance, no sharing. A write on Instance A invalidates A's L1 but leaves B's and C's L1 stale. Requires broadcast invalidation (Pub/Sub) or very short TTLs on L1 entries.
- **L2 (Redis):** Shared across instances. Write-through or delete-on-write to Redis ensures all instances that miss L1 see fresh data. Redis replication lag between primary and replicas introduces a brief incoherence window.
- **L3 (DB primary → replicas):** Replication lag on DB replicas means cache misses that read from a replica may cache stale data. Fix: route cache-miss reads to the DB primary (higher load) or accept bounded staleness from replicas.

The coherence SLA for the whole system is the *maximum* of the coherence windows across all layers.

**Q17. What is "stale-while-revalidate" and how does it trade coherence for availability?**
A: A cache policy that serves a stale (expired) entry immediately to the requesting client while asynchronously fetching a fresh value in the background. The client gets a fast response; the cache gets updated for the next reader.

**Coherence trade-off:** The requesting client knowingly receives stale data. The window of incoherence = time for the background revalidation to complete (typically milliseconds to seconds). For many use cases (product descriptions, news feeds, exchange rates with defined update intervals), this is acceptable and provides better availability and latency than blocking on a synchronous refresh.

**Not acceptable when:** The stale value could cause financial harm, security bypass, or incorrect decisions (account balance, authorization data, inventory counts at checkout).

**Q18. How does CDC (Change Data Capture) achieve cache coherence, and what are its failure modes?**
A: CDC tools (Debezium, Maxwell, AWS DMS) tail the database write-ahead log (WAL) and emit an event for every row-level change. A cache invalidation service consumes these events and deletes or updates cache keys corresponding to the changed rows.

**Advantages:** Coherence is driven by the DB itself — no application code changes needed. Works across multiple writers. Catches writes made directly to the DB (bypassing the application).

**Failure modes:**
- **Consumer lag:** If the CDC consumer falls behind (event processing slow, consumer restarts), the cache is stale for the lag duration — potentially minutes.
- **Event loss:** If the Kafka topic or CDC pipeline drops events, cache entries are never invalidated. Mitigation: use a TTL backstop.
- **Schema changes:** If a DB column rename or table restructure happens, the CDC event format changes and the consumer may silently fail to parse invalidation events.
- **WAL retention:** If the DB WAL is rotated before the CDC consumer catches up (after a consumer outage), events are permanently lost.

**Q19. How do CDN caches handle coherence, and what mechanisms exist for forced invalidation?**
A: CDN edge nodes are independent caches with no coherence protocol between them. Coherence mechanisms:
- **Cache-Control headers:** `max-age`, `s-maxage` define how long an edge node caches a response. After expiry, the edge revalidates with origin.
- **Surrogate keys / cache tags:** Tag cached responses with logical identifiers (e.g., `product:42`). A single API call to the CDN purges all responses tagged with `product:42` across all PoPs simultaneously. Supported by Fastly, Cloudflare, Akamai.
- **Purge API:** CDNs expose a purge endpoint that invalidates specific URLs or patterns across all edge nodes. Propagation is fast (seconds) but not instantaneous.
- **Instant Purge (Fastly):** Sub-second purge propagation using a purpose-built messaging system — effectively active invalidation at CDN scale.
- **Soft purge / stale-while-revalidate:** Mark content as stale without evicting it. Edge nodes serve stale content immediately while revalidating asynchronously.

## Section 5: Trade-offs & Decision-Making

**Q20. How do you choose between TTL-based and event-driven invalidation?**
A: Key decision factors:

| Factor | Lean TTL-based | Lean Event-driven |
|---|---|---|
| Data change frequency | Infrequent (data is mostly static) | Frequent (data changes constantly) |
| Acceptable staleness | Minutes to hours | Seconds to near-zero |
| Write pattern | Many writers, complex topology | Single writer or well-defined write path |
| Infrastructure | Simple, no messaging infra | Kafka/Pub/Sub already in stack |
| Data criticality | Non-critical (content, descriptions) | Financial, inventory, auth data |
| Operational maturity | Small team, simple system | Platform team with observability |

In practice: use TTL as a safety backstop always, even when using event-driven invalidation. TTL catches the cases where invalidation messages are lost.

**Q21. What is the "cache coherence vs cache performance" tension and how do you resolve it?**
A: Stronger coherence requires more coordination — more messages, more synchronous waits, more round trips. This directly costs throughput and latency. The tension:
- **Strong coherence** — synchronous write-through to all caches before ack. High write latency. High coordination overhead. Tight consistency SLA.
- **Eventual coherence** — async invalidation or TTL-based expiry. Low write latency. No coordination on write path. Loose consistency SLA.

Resolution: the right choice is determined by the data's business semantics:
- Account balance, payment status, auth tokens → strong coherence, accept the latency cost.
- Product descriptions, blog content, leaderboards → eventual coherence, TTL-based, accept bounded staleness.
- Inventory counts → middle ground: eventual coherence for display, strong coherence at checkout (re-read from DB at the moment of purchase, bypass cache).

**Q22. What is the "cache poisoning" risk in incoherent caches, and how do you prevent it?**
A: Cache poisoning occurs when incorrect or malicious data is written into the cache and then served to many users before expiry. Sources:
- **Application bug** — a computation error produces a wrong value that gets cached widely.
- **Race condition** — stale data wins a write race and is cached (see Q11).
- **Malicious input** — in HTTP caches, a crafted request causes a shared cache to store an attacker's response and serve it to other users (cache deception attack).

**Prevention:**
- Short TTLs limit the blast radius and duration of poisoned entries.
- Input validation before caching — never cache values that fail schema validation.
- Cache key namespacing — ensure user-specific data is never cached under a shared key.
- Monitoring for unexpected cache values — alert on anomalous cache values (e.g., product prices more than 2 standard deviations from the mean).
- Immediate purge capability — ability to delete specific keys or flush namespaces in production with an operator-facing tool.

**Q23. How does cache coherence interact with database transactions?**
A: The fundamental problem: DB transactions are atomic, but cache operations are not part of the transaction. The sequence:

```
BEGIN TRANSACTION
  UPDATE products SET price = 99 WHERE id = 42
COMMIT                            ← DB atomically updates
cache.delete("product:42")        ← separate operation, outside transaction
```

If the process crashes between COMMIT and the cache delete, the cache is stale indefinitely (until TTL). Solutions:
- **Transactional outbox:** Write the cache invalidation event to an `outbox` table inside the DB transaction. A relay process delivers the invalidation after the transaction commits. The outbox is durable — no invalidations are lost on crash.
- **Two-phase approach:** Mark the cache key as "invalidating" (a flag or short TTL) before the DB write. Complete the DB write. Delete the cache key. If the process crashes mid-sequence, the short TTL ensures eventual coherence.
- **Accept the gap:** For non-critical data, accept that the window between DB commit and cache delete is a brief incoherence period (usually milliseconds). Mitigate with a short TTL backstop.

## Section 6: Scenario / System Design Style Questions

**Q24. "You have a product catalog cached in Redis with a 1-hour TTL. A pricing error is discovered and corrected in the DB. How do you immediately propagate the correct price to all users?"**
A: TTL-based expiry is unacceptable here — users would see wrong prices for up to 1 hour. Immediate coherence required:

1. **Fix the DB record** — correct the price in the DB first.
2. **Active invalidation** — call `redis.delete("product:{id}")` for the affected product immediately after the DB write. If multiple cache key formats exist (`product:42`, `category:electronics:products`, search result caches), delete all of them.
3. **Broadcast to local caches** — if service instances have local in-process caches, publish an invalidation event to a Redis Pub/Sub channel. All instances subscribe and evict the key from their local cache.
4. **CDN purge** — if product pages are cached at the CDN layer, trigger a surrogate key purge via the CDN's API for all URLs containing the product.
5. **Verify** — query the cache directly after invalidation to confirm the key is absent. Monitor cache hit rate for the key to confirm the next reads fetch fresh data.
6. **Prevent recurrence** — implement CDC-driven invalidation so future price changes automatically trigger cache invalidation without manual intervention.

**Q25. "You're designing a multi-region active-active system where each region has its own Redis cache. A user updates their profile in Region A. How do you maintain cache coherence across regions?"**
A: Cross-region coherence is expensive — network latency between regions is 50–200ms. You must decide your consistency model first:

**Option 1 — Eventual coherence via replication:**
- Publish a `UserProfileUpdated` event to a cross-region message bus (Kafka MirrorMaker, AWS EventBridge).
- Each region's cache invalidation service consumes the event and deletes `user:{id}:profile` from its local Redis.
- Propagation lag = event replication latency (seconds). Users in other regions may briefly see the old profile.

**Option 2 — Session affinity (strong coherence for the user):**
- Route the updating user's subsequent requests to Region A (sticky session) for a short window (e.g., 60 seconds). They always read from their own region's fresh cache.
- Other users in other regions may see stale data (acceptable for profile data).

**Option 3 — Global cache (latency trade-off):**
- Use a globally consistent cache (DynamoDB Global Tables, Redis Enterprise Active-Active) as the shared cache layer. Writes propagate globally in seconds with conflict resolution.
- Adds cross-region write latency (higher write p99), but all reads are coherent within propagation time.

**Practical choice:** For profile data, eventual coherence (Option 1) with a short TTL backstop (5 minutes) is usually acceptable. Reserve global consistency for financial or security-critical data where multi-region incoherence has real consequences.

**Q26. "Your e-commerce site uses cache-aside. During a flash sale, you notice some users see an old price and some see the new price for the same product, even on the same page load. What's happening and how do you fix it?"**
A: Classic multi-layer incoherence with a write race:

**Root cause diagnosis:**
- The page load makes multiple requests — product detail, price widget, cart preview — potentially hitting different service instances, each with their own local L1 cache at different states of warming/invalidation.
- A price update was written to the DB but only some cache nodes were invalidated (invalidation message missed by some instances).
- DB replica lag: some requests hitting a replica haven't yet received the price update, caching the old price; others hit the primary and cache the new price.

**Fixes:**
- **Consistent cache key** — ensure all components on a page use the same cache key format and the same cache node (L2 Redis) for the price, not different L1 instances.
- **Invalidation broadcast** — on price write, publish to Redis Pub/Sub so all L1 caches evict the key simultaneously.
- **DB read routing** — route cache-miss reads to the DB primary (not replicas) during a flash sale window to eliminate replica lag as a source of stale data.
- **Short L1 TTL** — set L1 TTL to 5 seconds during sale windows; L2 Redis with active invalidation handles coherence; L1 is just a micro-cache to absorb burst reads.
- **Version in response** — include a `price_version` field in the API response; the frontend detects version mismatch across concurrent requests and re-fetches, or collapses all price reads into a single API call per page load.

## Quick Reference: Coherence Strategy Comparison

| Strategy | Coherence Strength | Write Latency Impact | Complexity | Best For |
|---|---|---|---|---|
| TTL only | Eventual (bounded by TTL) | None | Minimal | Non-critical, infrequent writes |
| Delete on write | Near-immediate | Minimal (one extra delete) | Low | General purpose — most common |
| Write-through | Strong (single node) | Moderate (cache + DB write) | Low–Medium | Hot keys, low write rate |
| Active invalidation (Pub/Sub) | Near-immediate (all nodes) | Low (async) | Medium | Multi-instance local caches |
| CDC-driven invalidation | Near-immediate | None (decoupled) | High | Complex write topologies, multiple writers |
| Version key (cache busting) | Immediate (no race) | None | Medium | High-write-rate data, CDN assets |
| Two-phase invalidation | Near-immediate + eventual backstop | Low | Medium | Multi-layer cache hierarchies |
| Transactional outbox | Guaranteed (crash-safe) | None | High | Financial data, critical consistency |

---

**Tip for the interview:** Cache coherence questions almost always reveal themselves as "why are users seeing stale data" investigations. Senior engineers are expected to know that the answer is always multi-layered — L1 local cache, L2 Redis, DB replica lag, and CDN can all independently introduce incoherence, and you need to diagnose which layer is the culprit. The two conceptual anchors that matter: (1) TTL is a backstop, not a coherence strategy — always combine it with active invalidation for anything time-sensitive; (2) the coherence guarantee of your system is only as strong as its weakest layer — fixing Redis invalidation doesn't help if DB replica lag is still poisoning cache-miss reads.
