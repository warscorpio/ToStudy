# Multi-Level Caching: In-Process → Distributed (Redis) → CDN — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is multi-level caching and why does it exist?**
A: Multi-level caching stacks several cache tiers between the application and the authoritative data source, each with a different speed, capacity, and scope trade-off. No single cache technology optimally satisfies all requirements simultaneously: a CDN is fast for global users but can't serve authenticated data; Redis is shared across instances but adds a network hop; an in-process cache is zero-latency but not shared. Stacking layers lets each tier handle what it does best, with misses falling through to the next level. The goal is to absorb as many requests as possible at the cheapest, fastest layer before falling through to a more expensive one.

**Q2. What are the three main tiers in the canonical stack and what does each optimize for?**
A:
- **L1 — In-process (in-memory)**: Lives inside the application process as a hashmap or LRU structure. Zero network overhead — a cache hit is a local memory read in microseconds. Scope is single-instance only; not shared across app servers. Capacity is limited by process heap.
- **L2 — Distributed cache (Redis/Memcached)**: Lives on dedicated cache nodes, shared across all application instances. A hit is a network round trip — typically 0.5–2ms on a local network. Scope is cluster-wide; all instances see the same data. Capacity is limited by cache cluster RAM, but can be scaled horizontally.
- **L3 — CDN (Content Delivery Network)**: Lives at geographically distributed edge nodes close to users. A hit is served without touching your origin at all — typically 5–50ms from the user's perspective vs. 50–300ms+ to origin. Scope is public/anonymous responses. Capacity is effectively unlimited (CDN provider's infrastructure). Not suitable for private, user-specific, or dynamic data.

**Q3. What is the fundamental principle governing when a request moves from one tier to the next?**
A: A request is served by the fastest tier that has a valid (non-expired, non-stale) copy of the data. If L1 has it → serve from L1. L1 miss, L2 has it → serve from L2, optionally populate L1. L2 miss, CDN has it → serve from CDN, optionally populate L2. All miss → fetch from origin (DB or upstream service), populate the appropriate tiers on the way back. This is called **read-through promotion**: data travels up through the tiers as it's requested, naturally concentrating hot data at the fastest layers.

**Q4. What is the cost model that justifies adding each tier?**
A: Each tier has a cost (latency, operational complexity, memory) and a benefit (requests absorbed). A tier is worth adding when:
- The hit rate at that tier is high enough that the latency reduction it provides is material to overall system performance.
- The operational cost of the tier is less than the cost of the load it absorbs from the tier below.

In practice: L1 is essentially free (heap memory, no infra); L2 (Redis) has meaningful infra cost and operational overhead; CDN has per-GB transfer and request pricing. You add each tier when the traffic volume and latency requirements justify it — a startup with 100 RPS probably doesn't need all three.

**Q5. How does a multi-level cache interact with read vs. write traffic differently?**
A: Reads flow outward (L1 → L2 → CDN → origin), serving from the nearest warm tier. Writes flow inward (origin → invalidate/update caches) and are where multi-level caching gets complex. A write to the DB must propagate invalidation to all relevant tiers, in the right order, without race conditions. The more tiers you add, the more write paths you must instrument. This asymmetry — reads are simple, writes are hard — is why multi-level caching is most effective for read-heavy workloads where writes are infrequent relative to reads.

## Section 2: L1 — In-Process (In-Memory) Cache

**Q6. How is an in-process cache typically implemented?**
A: As a bounded, eviction-managed data structure inside the application process. Common implementations:
- **Java/JVM**: Guava Cache, Caffeine (the modern standard — uses a Window TinyLFU algorithm outperforming LRU in most workloads).
- **Python**: `cachetools` library (LRU, LFU, TTL variants), `functools.lru_cache` for function-level memoization.
- **Go**: `sync.Map` with manual TTL management, or libraries like `ristretto` (designed for high concurrency, admission control via TinyLFU).
- **Node.js**: Plain `Map` with a size bound and TTL, or `node-cache`.

All share the same properties: zero network round trip, lives in the process heap, not shared across instances, evicts based on a policy (LRU, LFU, TTL) when capacity is exceeded.

**Q7. What are the ideal characteristics of data stored in L1?**
A:
- **Extremely hot**: accessed many times per second by a single instance. Data accessed once every few minutes is better left to L2 — it'll be evicted from L1 before reuse.
- **Small in size**: L1 is bounded by process heap. A cache of thousands of small objects (user profile structs, config values) is fine; caching large blobs (rendered HTML pages) wastes heap and triggers GC.
- **Tolerant of brief per-instance staleness**: since L1 is not shared, different instances may have different versions of the same data for up to the TTL duration.
- **Infrequently changing**: high churn data wastes the L1 slot — it's evicted or invalidated before being reused enough to justify its presence.

**Q8. What is the "instance isolation" problem with L1 caches and why does it matter?**
A: Each application instance has its own L1 cache, independent of all others. A write to the DB (or an invalidation event) clears the L1 on the instance that handled the write but leaves stale copies on all other instances. For a fleet of 50 app servers, a data change affects one L1 immediately — the other 49 serve stale data for up to the TTL. This is acceptable for data where brief per-instance inconsistency is tolerable (config values, reference data), but dangerous for data where all instances must immediately agree (user permissions after a revocation, pricing during a flash sale).

**Q9. How do you handle L1 invalidation across a fleet of instances?**
A: Several approaches depending on acceptable consistency:
- **TTL-only**: set a short TTL (e.g., 10–30s). No cross-instance communication — staleness resolves itself within the TTL window. Simple, at the cost of brief inconsistency.
- **Pub/sub broadcast**: on write, publish an invalidation event to a channel (Redis pub/sub, an internal message bus). All instances subscribe and clear the relevant L1 key on receipt. Near-real-time consistency, but adds complexity and a dependency on the messaging system.
- **Version-tagged keys**: embed a global version number in the L1 key. On write, increment the version in L2. Each instance checks the current version on L1 access; a version mismatch is treated as a miss and falls through to L2. More complex key management but avoids a pub/sub system.
- **Avoid L1 for invalidation-sensitive data**: if the data requires immediate consistency across all instances, put it in L2 only. L1 is for data where per-instance staleness is acceptable.

**Q10. What is "GC pressure" from an in-process cache and how do you manage it?**
A: An unbounded or poorly tuned in-process cache fills the JVM (or other GC'd runtime) heap with cache objects. When the heap nears capacity, GC runs more frequently and for longer, causing latency spikes (stop-the-world pauses in older JVM collectors). On managed runtimes, treat L1 cache size as a first-class configuration parameter: set a hard entry count or byte limit, choose a cache library that tracks memory accurately (Caffeine uses entry weights), and monitor heap usage alongside cache hit rates. Cache-induced GC pauses are a common source of mysterious latency spikes in Java services.

**Q11. What is the "local cache warm-up" problem during rolling deployments?**
A: When a new instance starts, its L1 cache is cold — every request misses L1 and falls through to L2 or origin until the cache warms up. During a rolling deployment with many instances restarting sequentially, the fraction of traffic hitting cold L1s is continuously elevated, increasing L2 and origin load. Mitigation: slow rolling deployments (replace a small fraction of instances at a time), pre-warming by replaying recent L2 keys on startup, or accepting the brief warmup period and ensuring L2 can absorb the extra load.

## Section 3: L2 — Distributed Cache (Redis)

**Q12. Why is Redis the dominant choice for L2 in most stacks?**
A: Redis combines a rich data structure library (strings, hashes, sorted sets, lists, streams), single-threaded atomic operations (no lock contention for most operations), sub-millisecond latency at high throughput, cluster mode for horizontal scaling, built-in TTL per key, pub/sub for invalidation broadcasting, and a large operational ecosystem (Redis Sentinel, Redis Cluster, managed offerings like ElastiCache, Upstash). Memcached is simpler and may outperform Redis on pure string get/set throughput, but Redis's richer feature set and operational tooling make it the default choice for most teams.

**Q13. How does L2 cache a DB query result that previously required joining three tables?**
A: The application runs the query once, receives the result set, serializes it (JSON, MessagePack, Protobuf), and stores it in Redis under a key that encodes all query parameters: `product:category:electronics:page:2:sort:price_asc`. On the next request with identical parameters, the application checks this key first; a hit means no DB round trip. The serialized result is deserialized and returned directly. The key design is critical — it must capture every dimension of the query that affects the result, including locale, user segment, or feature flags if those affect the output.

**Q14. What is the "dog-pile" or "thundering herd" problem at L2 and how do you prevent it?**
A: When a popular L2 key expires, many concurrent application instances simultaneously experience a miss and each independently fires the same expensive DB query to repopulate it. The DB receives N parallel identical queries. Prevention strategies:
- **Mutex/single-flight**: the first instance to detect the miss acquires a short-lived Redis lock (`SET nx px`); it fetches from DB and populates the cache. Other instances detect the lock and either wait briefly or serve a slightly stale value.
- **Probabilistic early expiry (PER)**: slightly before actual expiry, each cache read randomly decides to refresh early based on how close to expiry the entry is. Refreshes happen gradually before expiry rather than simultaneously at the moment of expiry.
- **Background refresh**: a separate process monitors TTLs and refreshes entries before they expire, so they never actually go cold.

**Q15. What Redis data structures beyond plain strings are useful for multi-level caching scenarios?**
A:
- **Hashes**: store multiple fields of an object under one key (`HSET user:123 name "Alice" email "alice@example.com"`). Fetch individual fields without deserializing the full object.
- **Sorted sets**: leaderboards, rate limiting windows, time-ordered feeds. The score enables range queries without touching the DB.
- **Lists**: job queues, paginated feed slices. Efficient head/tail operations.
- **Bitmaps and HyperLogLog**: space-efficient approximate counts (daily active users, unique visitors) — store aggregates that would require expensive `COUNT DISTINCT` queries in the DB.
- **Streams**: event log with consumer groups — useful for cache invalidation fan-out to multiple subscribers.

Choosing the right data structure reduces both memory usage and the number of round trips needed to assemble a response.

**Q16. How does Redis Cluster affect cache key design?**
A: Redis Cluster distributes keys across shards using a hash slot (CRC16 of the key, mod 16384). By default, the entire key is hashed. This means `user:123:profile` and `user:123:posts` may land on different shards, requiring two round trips or MGET across shards (which requires client-side scatter-gather). Use **hash tags** — `{user:123}:profile` and `{user:123}:posts` — to force related keys to the same shard by hashing only the content inside `{}`. This enables single-shard MGET and atomic operations across related keys, at the cost of potentially uneven key distribution if the tag space is narrow.

**Q17. What is the difference between Redis persistence modes and why does it matter for L2 cache?**
A: Redis offers RDB (periodic snapshots), AOF (append-only log of every write), and no persistence. For a cache, persistence is usually unnecessary — the cache is a performance layer, not the authoritative store. Disabling persistence (`save ""`, `appendonly no`) maximizes Redis throughput and simplifies operations. Enabling persistence adds write overhead and recovery time on restart but means the warm cache survives a planned restart. The trade-off: for a pure L2 cache, accept cold start after restart (L1 warms quickly anyway) and disable persistence for simplicity. For data that is expensive to re-warm (large computed aggregates), AOF can be worth the overhead.

## Section 4: L3 — CDN Cache

**Q18. What is a CDN and how does it function as the outermost cache tier?**
A: A CDN is a globally distributed network of edge nodes (PoPs — Points of Presence) that cache responses close to end users. When a user requests a resource, the request goes to the nearest edge node. If the edge has a cached copy (hit), it responds directly without touching the origin server — typical latency is 5–50ms vs. 50–300ms+ to origin. On a miss, the edge fetches from origin, caches the response, and serves it. Subsequent requests from users near that edge node are served from the cache. The CDN functions as a geographically distributed L3 cache with massive scale and capacity, operated and maintained by the CDN provider (Cloudflare, Fastly, AWS CloudFront, Akamai).

**Q19. What HTTP headers control CDN caching behavior?**
A: The CDN reads standard HTTP response headers from origin:
- `Cache-Control: public, max-age=3600` — cache publicly for 3600 seconds (1 hour). `public` means the CDN may cache it; `private` means only the browser may cache it (CDN will not store it).
- `Cache-Control: no-store` — neither CDN nor browser caches the response.
- `Cache-Control: s-maxage=600` — specifically for shared caches (CDNs); overrides `max-age` for CDN TTL while `max-age` controls browser TTL.
- `Cache-Control: stale-while-revalidate=60` — serve stale content for up to 60s while revalidating in background.
- `Vary: Accept-Encoding, Accept-Language` — cache separately per combination of these headers (a CDN stores one entry per Vary dimension). Overusing `Vary` fragments the cache and reduces hit rates.
- `ETag` / `Last-Modified` — enable conditional requests; CDN can revalidate with origin cheaply (304 Not Modified) rather than re-fetching the full response.

**Q20. What is cache key composition at the CDN layer and why does it need careful design?**
A: The CDN's default cache key is usually the URL (scheme + host + path + query string). Two requests with the same URL are served the same cached response. Problems arise when:
- **User-specific headers affect content**: the response varies by `Authorization`, `Cookie`, or `Accept-Language` but the cache key doesn't include them — users see each other's data (a serious security bug). Never cache authenticated responses at the CDN without explicit cache key customization.
- **Irrelevant query params fragment the cache**: `?utm_campaign=email` creates a separate cache entry from `?utm_campaign=social` even if the content is identical. Strip tracking parameters from the cache key (most CDNs support this via configuration) to unify cache entries.
- **Custom headers are invisible to default key**: if your origin returns different content based on a custom request header (`X-AB-Group: control`), configure the CDN to include that header in the cache key via `Vary` or explicit key rules.

**Q21. What types of content should never be served from a CDN cache?**
A:
- **Authenticated/user-specific responses**: profile pages, account settings, private dashboards. A CDN hit would serve one user's data to another. Always set `Cache-Control: private` or `no-store` for these.
- **Real-time data**: live sports scores, stock prices, anything where serving a 60-second-old value is user-visible and harmful.
- **Form submission responses and POST endpoints**: CDNs cache GET by default; caching POST responses can cause repeated form submissions to appear to succeed when the cached response is served.
- **Responses with `Set-Cookie` for session cookies**: caching a response that sets a session cookie means all users who hit the cached version share the first user's session cookie in the response headers — a critical session hijacking vulnerability. Strip or avoid `Set-Cookie` on cacheable responses, or configure the CDN not to cache responses containing it.

**Q22. What is "cache purging" at the CDN layer and what are its limitations?**
A: Cache purging is an API call to the CDN instructing it to immediately invalidate a specific URL or set of URLs before their TTL expires. It's the CDN equivalent of active invalidation. Limitations:
- **Propagation delay**: purge requests must reach all edge nodes globally; this can take seconds to minutes depending on the CDN provider and region count.
- **Wildcard purging is expensive or unavailable**: purging `example.com/products/*` requires the CDN to invalidate potentially millions of keys; some providers limit or charge extra for wildcard purges.
- **Purge API rate limits**: frequent purge calls are throttled by most CDN providers; it's not a substitute for correct TTL design.
- **Surrogate keys / cache tags** (Fastly, Cloudflare): a better pattern — tag responses with logical group identifiers (`product:123`, `category:electronics`) and purge all responses sharing a tag in one API call. More scalable than URL-by-URL purging.

## Section 5: Cache Coherence Across Levels

**Q23. What is the read path through all three tiers and what happens at each miss?**
A: A fully specified read path:
1. Check L1 (in-process): hit → return immediately (microseconds). Miss → continue.
2. Check L2 (Redis): hit → return, populate L1 with the result and a short TTL. Miss → continue.
3. Check L3 (CDN): only applicable for HTTP responses at the edge; if the request reached the application server, the CDN already missed. Miss → continue.
4. Fetch from origin (DB/upstream): execute query, return result. Populate L2 (with appropriate TTL), optionally populate L1.

On the way back up, each tier is populated with the freshly fetched data, so subsequent requests hit the fastest available layer. This is **read-through promotion**.

**Q24. What is the write path and why is it harder than the read path?**
A: A write to the DB must propagate invalidation (or an updated value) outward through all cache tiers, in the right order. A common pattern:
1. Write to DB (commit the change).
2. Delete or update L2 (Redis) for affected keys.
3. Publish invalidation events to all app instances via Redis pub/sub or a message bus; each instance deletes the relevant L1 keys.
4. Purge the CDN for affected URLs (if the response is cached at the CDN).

Order matters: delete L2 *after* committing to DB, not before — if you delete L2 before committing, a concurrent reader might miss L2, go to DB, read the old value, and repopulate L2 with stale data before the commit lands. The write path must be instrumented at every layer, which multiplies as you add tiers.

**Q25. What is the "stale L1 after L2 invalidation" race condition?**
A: A write invalidates L2 correctly and broadcasts an L1 invalidation event. But between the L2 delete and the L1 invalidation event being received, another thread on the same instance re-reads the key: it misses L1 (just evicted or never populated), goes to L2 (just invalidated — miss), goes to DB (reads the new value), and re-populates *both* L2 and L1 with the fresh value. This is fine. But a subtler race: the key is in L1 on instance B; the invalidation event is delayed (pub/sub delivery is not instantaneous); instance B serves the stale L1 value for the duration of the delay. Mitigations: short L1 TTLs (upper-bound the staleness), accept the brief window as a design trade-off, or don't use L1 for data requiring near-real-time consistency.

**Q26. What is "multi-tier TTL laddering" and how should TTLs be set across tiers?**
A: TTL should decrease as you move outward (closer to the user) and increase as you move inward. The pattern:
- **CDN TTL**: longest — minutes to hours for stable content. The CDN absorbs the most traffic but is hardest to invalidate quickly.
- **L2 (Redis) TTL**: medium — seconds to minutes. Easier to invalidate programmatically; shorter TTL means faster self-correction.
- **L1 TTL**: shortest — seconds. Because L1 is not shared and hardest to invalidate across all instances, it should self-correct fastest.

Example: L1 TTL = 5s, L2 TTL = 60s, CDN TTL = 300s. A staleness event resolves in at most 5s for L1, 60s for L2, 300s for CDN — or faster if you actively invalidate. Never set L1 TTL longer than L2 TTL; an L1 hit past the L2 TTL could serve stale data that L2 has already refreshed.

**Q27. What is "cache version stampeding" in a multi-tier system and how do versioned keys prevent it?**
A: When a data version changes, every tier must be invalidated. If invalidation is event-driven and the event is delivered to thousands of CDN edge nodes, all simultaneously making origin requests to validate, the origin sees a traffic spike that mirrors the CDN request volume — exactly what the CDN was supposed to prevent. Versioned URL keys (`/api/products?v=42`) sidestep active invalidation entirely: the new version is a different URL, which is a guaranteed CDN miss but for a well-defined, single-event traffic spike. Old versioned URLs expire naturally. Versioned keys trade instantaneous correctness (the old URL still serves old data until TTL) for predictable, controllable origin load on updates.

## Section 6: Failure Modes & Anti-patterns

**Q28. What is "cache tier bypass amplification" and when does it cascade?**
A: If L2 (Redis) goes down or becomes unreachable, all requests that would have hit L2 fall through to the DB simultaneously. If the system's hit rate at L2 was 90%, the DB was handling 10% of traffic. With L2 down, it suddenly handles 100% — a 10× spike the DB was never sized for. This is the central operational risk of multi-level caching: the system becomes dependent on the cache for survival, not just performance. Mitigations: circuit breakers that serve stale L1 data when L2 is unreachable, DB connection pool limits with graceful shedding, pre-provisioning DB capacity to handle cache-miss load, and Redis Cluster / Sentinel for high availability.

**Q29. What is "cache stampede amplification" in a multi-tier system vs. a single-tier system?**
A: In a single-tier cache, a stampede hits the DB with N requests. In a multi-tier system, the amplification is worse: an L2 miss causes all app instances to fall through to the DB; if that L2 miss was caused by L2 being cold (restart), the warm L1s on surviving instances don't help because L1 was populated *from* L2, which is now empty. The cold L2 effectively cold-caches all L1s above it simultaneously. A Redis restart without pre-warming is a system-wide cold start event, not just a Redis outage.

**Q30. What is the "L1 cache incoherence during blue-green deployment" problem?**
A: In a blue-green deployment, two fleets (blue = old, green = new) run simultaneously while traffic shifts. The blue fleet has warm L1 caches built on the old code's cache key schema. The green fleet starts cold. If a write happens during the transition: blue invalidates its L1 using old key patterns; green may use new key patterns (if schema changed). Some instances invalidate the right key, others don't. The window between fleets seeing consistent invalidation events is a consistency gap. Mitigation: never change cache key schemas in a single deployment — use a two-phase deploy (add new keys without removing old ones, then remove old ones), or flush L2 during the transition with careful timing.

**Q31. What is "CDN origin shield" and how does it protect L2 from CDN miss amplification?**
A: When a CDN edge node has a miss, it fetches from origin. With hundreds of globally distributed edge nodes, a popular piece of content expiring simultaneously could trigger hundreds of parallel origin requests. An **origin shield** (also called a "shield PoP") is a single designated CDN node that all other edge nodes treat as their "origin" — edge misses go to the shield, not directly to the application server. Only shield misses hit the real origin. This collapses N edge nodes' miss traffic into at most 1 request to origin, effectively turning the shield into an L4 cache between CDN and application. Most CDN providers offer this as a configuration option (Cloudflare's Tiered Cache, CloudFront's Origin Shield, Fastly's shielding).

**Q32. What is "thundering herd on TTL alignment" and how do staggered TTLs fix it?**
A: If many cache keys share the same TTL value and were all populated at the same time (e.g., during a cold start or a bulk write), they all expire simultaneously. Every expiry triggers a miss that falls through to L2 or the DB, creating a periodic traffic spike every TTL interval. Fix: add random jitter to TTL values at population time: `ttl = base_ttl + random(0, base_ttl * 0.2)`. This spreads expiry events over a window instead of aligning them, smoothing the load on downstream tiers. A subtle but important production detail.

## Section 7: Trade-offs & Decision-Making

**Q33. How do you decide which tiers to add and in what order?**
A: Start with the problem, not the technology:
- **L2 (Redis) first**: almost always the right first cache layer for server-side applications. It's shared, durable enough for a cache, easy to operate, and solves the multi-instance consistency problem that L1 cannot.
- **L1 second**: add only when L2 round-trip latency is a measurable bottleneck for your hottest data (sub-millisecond matters for your SLA), or when L2 is becoming a throughput bottleneck. Measure before adding — L2 at 0.5ms is fast enough for most use cases.
- **CDN last**: add when you have public, cacheable HTTP responses and your origin's bandwidth or latency is a constraint for geographically distributed users. Not relevant for private APIs or non-HTTP workloads.

Adding a tier before you need it is premature optimization; it adds complexity and failure modes without proportional benefit.

**Q34. What is the "cache tax" and how do you quantify whether a tier is worth adding?**
A: The cache tax is the operational overhead of a tier: monitoring, alerting, cold start handling, invalidation instrumentation, consistency reasoning, and failure mode design. Each tier you add doubles the number of places where a write must be propagated and a bug can hide. Quantify the benefit before paying the tax: measure the p99 latency reduction from adding the tier against a realistic hit rate estimate. If adding L1 reduces L2 latency from 1ms to 0.01ms for 70% of requests, the end-to-end p99 improvement may be negligible for a service with 50ms of business logic. Cache the bottleneck, not everything.

**Q35. How does each cache tier interact with horizontal scaling of the application layer?**
A:
- **L1**: scales *with* the application — every new instance adds its own L1. But each instance's L1 is isolated; adding instances doesn't increase total L1 capacity, it just adds more independent L1s. More instances → more L1s → more total traffic falling through to L2 (since each instance's L1 is cold initially).
- **L2 (Redis)**: shared across all instances, so adding app instances doesn't reduce L2 hit rate. L2 may need to scale independently (via Redis Cluster) if app instance count grows enough to saturate Redis throughput.
- **CDN**: completely independent of app scaling — it absorbs traffic before it reaches the application tier at all. Adding app instances behind a CDN doesn't affect CDN behavior; it just increases origin capacity for CDN misses.

**Q36. When does adding L1 hurt more than it helps?**
A:
- **Infrequently accessed keys**: an L1 cache for data accessed once per minute per instance is never warm — it wastes heap and adds a lookup overhead with zero benefit.
- **Data requiring immediate cross-instance consistency**: L1 is always slightly stale from the perspective of other instances. If a permission change must be visible immediately everywhere, L1 will silently serve the old value.
- **Large-value objects**: caching a 1MB serialized response in L1 consumes heap aggressively and causes GC pressure that increases latency more than the cache saves.
- **High instance churn**: in an auto-scaling environment where instances start and stop frequently, L1 is perpetually cold for a fraction of the fleet, offering little aggregate benefit.

## Section 8: Scenario / System Design Style Questions

**Q37. "Design the caching architecture for a news website's article pages. Articles are updated occasionally, but read millions of times."**
A: A textbook multi-tier caching problem:
- **CDN (L3)**: cache fully rendered article HTML at the edge. `Cache-Control: public, s-maxage=300, stale-while-revalidate=60`. On article publish/update, purge the CDN by URL or surrogate key (`article:{id}`). Hit rate: >99% — most article reads are repeat visitors reading recently published content.
- **L2 (Redis)**: cache the article's structured content (title, body, author, metadata) serialized as JSON. Key: `article:{id}:v{version}`. TTL: 10 minutes. Used by the application when the CDN misses (e.g., first reader after publish, or authenticated users bypassing CDN).
- **L1 (in-process)**: cache the rendered HTML fragment or article struct for the top N most-read articles currently in memory. TTL: 30 seconds. Prevents even the L2 round trip for viral or trending articles hitting one instance heavily.
- **Do not cache at CDN**: the edit interface, draft preview, authenticated personalization (comments, subscription status).
- **Invalidation**: on article update, write to DB → delete L2 key → purge CDN URL. L1 self-corrects within its TTL.

**Q38. "Your Redis cluster is getting hammered — 95% CPU, 40ms p99 latency. You want to add L1 to reduce Redis load. Walk through the design."**
A:
- **Identify what's hot**: run `redis-cli --hotkeys` or enable keyspace notifications to find the top accessed keys. The goal is to cache in L1 only the keys that account for the majority of Redis hits — likely a small set (Zipf distribution).
- **Choose a library**: Caffeine (Java) or Ristretto (Go) — both support maximum size, per-entry weight, TTL, and async loading. Set a maximum entry count or byte budget (e.g., 500MB of the 4GB heap, avoiding GC pressure).
- **Set TTL carefully**: L1 TTL should be significantly shorter than L2 TTL (e.g., L1: 5s, L2: 60s). Stale L1 data is invisible to other instances; keep the window short.
- **Populate on L2 hit**: when a request hits L2, store the result in L1 before returning. Do not pre-populate L1 speculatively — let it warm naturally from real traffic.
- **Invalidation**: subscribe to Redis pub/sub for invalidation events (if you already broadcast them). On event receipt, delete the L1 key. Add a fallback: even without invalidation events, the L1 TTL bounds staleness.
- **Measure after**: re-check Redis CPU and p99. If the hot keys were concentrated (common), Redis load should drop significantly. If not, the problem is a data model issue — shard or redesign the hot keys.

**Q39. "Walk through exactly what happens when a user requests a product page, from CDN to DB, in a system with all three cache tiers."**
A: Full request trace for a product page (`GET /products/123`):
1. User's browser sends request to `cdn.example.com/products/123`.
2. **CDN edge node** checks its cache: HIT (page cached from a previous request) → serves HTML response in ~20ms. Request ends here for ~95% of traffic. OR MISS → CDN forwards request to origin shield.
3. **Origin shield** checks its cache: HIT → serves to edge, edge caches and serves to user. MISS → forwards to origin application server.
4. **Application server** receives request. Checks **L1 (Caffeine/Ristretto)** for key `product:123`: HIT → deserializes struct, renders HTML, returns to CDN in ~1ms. MISS → continues.
5. Application checks **L2 (Redis)** for key `product:123`: HIT (returns serialized JSON in ~1ms) → deserializes, renders HTML, **populates L1** with a 5s TTL, returns to CDN. CDN caches response with `s-maxage=300`. MISS → continues.
6. Application queries **DB**: `SELECT * FROM products WHERE id = 123` (~5ms on indexed PK). Receives result. **Populates L2** (serialized JSON, TTL=60s). **Populates L1** (struct, TTL=5s). Renders HTML, returns to origin shield → CDN edge → user.
7. Next request for same product: served from CDN in step 2. Next request after CDN expiry but within L2 TTL: served from L2 in step 5. Next request after L2 expiry: goes to DB.

**Q40. "A deployment bug populated L2 with corrupted data for 10,000 product keys. What's your remediation plan?"**
A:
1. **Immediate**: identify the key pattern (e.g., `product:*`) and the time window of the bad write. Use `SCAN` with pattern matching (never `KEYS *` in production — it blocks Redis) to enumerate affected keys. If the key set is bounded and identifiable, mass-delete with a scripted pipeline (`redis-cli --scan --pattern "product:*" | xargs redis-cli DEL` in batches).
2. **L1 impact**: all L1 entries populated from corrupted L2 data during the bug window must also be cleared. Since L1 is per-instance and not enumerable centrally, publish an L1 invalidation broadcast via Redis pub/sub for the affected key pattern. Alternatively, if L1 TTL is short (5–30s), let it self-correct — the corrupted L2 entries will be gone before L1 entries expire and re-fetch from L2.
3. **CDN impact**: if any corrupted data was served as HTTP responses that the CDN cached, issue targeted CDN purges for affected URLs. Use surrogate keys if available to purge by product ID tag rather than URL-by-URL.
4. **Re-population**: after deletion, L2 will cold-miss and repopulate from DB with correct data. If product data is expensive to re-warm, trigger a pre-warm job that reads the top-N product IDs and primes L2.
5. **Prevention**: add cache write validation (check data shape before writing to L2), deploy with a canary before full rollout, and add monitoring for cache hit rate drops that would signal mass invalidation events.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                    | L1 — In-Process                             | L2 — Distributed (Redis)                         | L3 — CDN                                              |
|---                        |---                                          |---                                                |---                                                    |
| Latency                   | Microseconds (local memory read)            | 0.5–2ms (network round trip, LAN)                 | 5–50ms from user (no origin request)                  |
| Scope                     | Single instance only                        | Shared across all app instances                   | Globally distributed; public responses only           |
| Capacity                  | Process heap (GBs, constrained)             | Cache cluster RAM (GBs–TBs, scalable)             | Effectively unlimited (CDN provider infra)            |
| Consistency across nodes  | No — each instance is independent           | Yes — all instances share the same L2             | No — each edge PoP is independent                     |
| Invalidation difficulty   | Hard (must broadcast or use short TTL)      | Easy (direct key delete via any instance)         | Hard (purge API, propagation delay, rate limits)      |
| Suitable for              | Extremely hot, small, staleness-tolerant    | Shared state, session data, hot query results     | Public, static or semi-static HTTP responses          |
| Not suitable for          | Data requiring cross-instance consistency   | Sub-millisecond requirement, process-local data   | Authenticated, private, real-time, or POST responses  |
| Failure impact            | Instance loses its cache; L2 absorbs        | All instances fall through to DB (major impact)   | All requests hit origin (potentially overwhelming)    |
| TTL guidance              | Seconds (5–30s)                             | Seconds to minutes (30s–10m)                      | Minutes to hours (5m–24h for stable content)          |
| Operational cost          | Low (library config, GC tuning)             | Medium (cluster ops, monitoring, HA config)        | Low (CDN provider manages infra) to medium (key design)|

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Read-through promotion        | On a miss, fetch from the next tier and populate all tiers above it on the way back                          |
| TTL laddering                 | L1 TTL < L2 TTL < CDN TTL; staleness resolves fastest at the closest layer                                  |
| Dog-pile / thundering herd    | Many concurrent misses on the same key simultaneously hammer the next tier                                   |
| Single-flight / mutex         | Only one request fetches on a miss; concurrent requests for the same key wait for the first result           |
| Stale-while-revalidate        | Serve the cached (possibly stale) response immediately; refresh asynchronously in background                 |
| Origin shield                 | A single designated CDN PoP that all other edge nodes treat as origin, collapsing miss traffic               |
| Surrogate keys / cache tags   | Tag CDN responses with logical identifiers; purge all tagged responses in one API call                       |
| `Cache-Control: s-maxage`     | CDN-specific TTL override; separate from browser `max-age`                                                   |
| `Vary` header                 | Instructs CDN to cache separate entries per combination of specified request headers                          |
| Hash tags (Redis Cluster)     | `{key}` syntax forces related keys onto the same shard; enables atomic multi-key operations                  |
| Instance isolation            | L1 caches are independent per instance; invalidation must be broadcast; stale data is invisible to others    |
| Cache tax                     | Operational overhead (monitoring, invalidation, failure modes) each tier adds; must be justified by benefit  |
| GC pressure                   | Large or unbounded L1 caches on JVM runtimes cause frequent garbage collection, increasing latency           |
| Cold start                    | A tier with empty cache; all traffic falls through to the next tier until warm                               |
| Probabilistic early expiry    | Randomly refresh a cache entry slightly before TTL to avoid synchronized expiry stampedes                    |
| Write-invalidate amplification| A single write must invalidate keys across L1, L2, and CDN — complexity multiplies with tier count          |

**Tip for the interview:** At 5 YOE level, the examiner isn't looking for you to recite what L1/L2/CDN are — they expect you to reason about the *interactions*: what happens to L1 when L2 restarts (cold stampede), why L1 TTL must always be shorter than L2 TTL, why CDN caching of authenticated responses is a security bug, and how a write propagates invalidations outward through all three tiers without race conditions. The candidates who stand out can also argue *against* a tier — "we don't need L1 because our L2 latency is 0.8ms and our business logic takes 40ms; L1 would save 0.8ms and cost us significant consistency complexity." That kind of judgment is what separates a senior engineer from someone who just knows the names of the layers.
