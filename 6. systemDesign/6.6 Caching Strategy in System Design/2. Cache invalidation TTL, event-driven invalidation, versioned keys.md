# Cache Invalidation: TTL, Event-Driven Invalidation, Versioned Keys — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is cache invalidation considered one of the hardest problems in computer science?**
A: Phil Karlton's quote — "There are only two hard things in Computer Science: cache invalidation and naming things" — captures a real truth. A cache is correct only at the moment it's filled; the moment the underlying data changes, the cache becomes a liability. The hard part isn't storing or retrieving cached values — it's knowing *when* a cached value is no longer valid and acting on that knowledge reliably, at scale, across distributed nodes, without introducing race conditions or over-invalidating (which defeats the purpose of caching). Every invalidation strategy involves a trade-off between consistency, availability, complexity, and performance.

**Q2. What are the three fundamental cache invalidation strategies?**
A:
- **TTL (Time-To-Live)**: Every cached entry expires after a fixed duration. Simple, no coordination required, but data is stale for up to the TTL window regardless of whether the underlying data changed.
- **Event-driven invalidation**: The cache is explicitly invalidated or updated when the underlying data changes — triggered by a DB write, a Kafka event, or a CDC signal. Stale window is minimised but requires coordination between the write path and the cache layer.
- **Versioned keys**: Instead of invalidating a cache entry, you change its key when the data changes (e.g., `user:42:v3` instead of `user:42`). Reads always get a fresh value by reading the new key; old keys expire naturally via TTL. No deletion required, but requires a mechanism to propagate the current version.

**Q3. What is a cache hit, cache miss, and cache stampede?**
A:
- **Cache hit**: The requested key exists and is valid — the fast path; no DB query needed.
- **Cache miss**: The key doesn't exist or has expired — the system falls through to the DB, fetches the value, populates the cache, and returns the result. Miss adds latency equal to the DB query time.
- **Cache stampede** (thundering herd): When a popular cached key expires, many concurrent requests all miss simultaneously, all query the DB at the same time, all attempt to populate the cache — hammering the DB with N identical queries instead of 1. A cold cache after a deployment or a TTL expiry on a hot key triggers this.

**Q4. What are the main cache write policies, and how do they affect consistency?**
A:
- **Cache-aside (lazy loading)**: Application reads from cache; on miss, reads from DB and writes to cache. Cache is only populated for keys that are actually read — no wasted space. Stale data possible between a DB write and the next cache miss + repopulation.
- **Write-through**: On every DB write, also write the new value to cache. Cache is always fresh for written keys. Adds write latency; populates cache with data that may never be read.
- **Write-behind (write-back)**: Write to cache immediately, flush to DB asynchronously. Fastest writes, but risks data loss if the cache node crashes before flushing. Rarely used for primary data stores in fintech.
- **Read-through**: Cache sits in front of the DB and handles its own population on miss — the application only talks to the cache. Simpler application code but tightly couples the cache to the DB query logic.

**Q5. What is the difference between cache eviction and cache invalidation?**
A: Eviction is the cache removing entries to free space when it's full — driven by memory pressure, using policies like LRU (Least Recently Used), LFU (Least Frequently Used), or FIFO. It's about capacity management. Invalidation is explicitly marking or removing a cache entry because the underlying data has changed — driven by correctness concerns. An evicted entry might still be valid (just removed due to space); an invalidated entry is definitionally stale. In Redis: eviction is controlled by `maxmemory-policy`; invalidation is controlled by your application logic (`DEL`, `EXPIRE`, key versioning).

## Section 2: TTL-Based Invalidation

**Q6. How does TTL-based invalidation work, and what are its core trade-offs?**
A: Every cache entry is stored with an expiration time. Reads after expiry trigger a cache miss and a fresh DB fetch. The cache self-heals automatically — no write path coordination needed. Trade-offs:

| Aspect | TTL Behaviour |
|---|---|
| Stale window | Up to the full TTL duration |
| Complexity | Minimal — set TTL on write, nothing else |
| Coordination | None — write path doesn't touch the cache |
| Thundering herd risk | High when many keys share the same TTL |
| Over-invalidation | None — entries expire naturally |

TTL is the right default for data where some staleness is acceptable (product descriptions, config values, public profile data) and the wrong choice for data that must be fresh immediately after a write (balances, inventory counts, session state).

**Q7. How do you choose an appropriate TTL?**
A: Balance staleness tolerance against cache effectiveness:
- **How often does the data change?** A product price that changes weekly tolerates a 1-hour TTL. A user's cart that changes per interaction doesn't.
- **What's the cost of serving stale data?** Stale product description: low cost. Stale account balance: high cost (financial and trust).
- **What's the read:write ratio?** High read, low write (product catalogue): long TTL is fine. High write (real-time feed): TTL must be short or TTL isn't the right strategy.
- **What's the DB load?** A very short TTL approaches no caching at all; if every request misses, you've added cache overhead with no benefit.

Common starting points: user session state (15–30 min), product/catalogue data (1–24 hours), reference/config data (1–24 hours), aggregated counts (30–60 seconds), financial data (avoid TTL — use event-driven).

**Q8. What is TTL jitter, and why is it important?**
A: Jitter adds a small random offset to each entry's TTL — instead of all entries expiring at exactly T+3600s, they expire at T+(3600 ± random(0, 300)s). Without jitter, a batch of entries populated together (e.g., during a deployment or a bulk load) all expire simultaneously, triggering a mass stampede. With jitter, expirations are spread over a window, smoothing the miss rate and DB load. A rule of thumb: jitter of ±10–20% of the base TTL. In Redis, instead of `EXPIRE key 3600`, use `EXPIRE key (3300 + random(0, 600))`.

**Q9. What is the "dog-pile effect," and how do you prevent it beyond jitter?**
A: The dog-pile effect is the cache stampede in disguise — a popular key expires and N concurrent requests all miss and all query the DB. Beyond jitter (which prevents coordinated expiry of multiple keys), targeted solutions for a single hot key:

- **Probabilistic early expiration (PER)**: Before TTL expires, probabilistically start refreshing the key early. As TTL approaches zero, each read has an increasing probability of triggering a background refresh. Implemented as: `if remaining_TTL < threshold AND random() < probability: refresh_in_background()`.
- **Mutex/lock on miss**: First request to miss acquires a Redis lock (`SET lock:key 1 NX EX 5`), queries the DB, and populates the cache. Subsequent misses wait for the lock to release and then hit the cache. Prevents N simultaneous DB queries but adds lock contention.
- **Stale-while-revalidate**: Serve the stale (expired) entry immediately while triggering a background refresh. The user gets fast (slightly stale) data; the cache is refreshed asynchronously. Not always possible with TTL-based expiry in Redis without storing a separate "soft TTL" alongside the entry.
- **Background refresh before expiry**: A separate cron/worker proactively refreshes hot keys before they expire, so they never actually miss in production.

**Q10. What are the operational risks of very long TTLs?**
A: A long TTL means stale data persists for a long time after the source changes — and with no event-driven invalidation, there's no way to push an update to the cache. If a product price is wrong for 24 hours because of a long TTL and no invalidation logic, customers see incorrect prices the whole time. Long TTLs are also a silent failure mode: everything appears to work during testing (the cache is fresh), but production data correctness erodes over time as source data changes. Mitigate with event-driven invalidation layered on top of TTL — TTL as a safety net, events for correctness.

## Section 3: Event-Driven Invalidation

**Q11. What is event-driven cache invalidation, and how does it work?**
A: Instead of waiting for a TTL to expire, the cache is invalidated (or updated) as soon as the underlying data changes — triggered by an explicit signal from the write path. The signal can be:
- **Direct invalidation on write**: The service that writes to the DB also calls `DEL cache_key` (or `SET cache_key new_value`) immediately after committing.
- **Message-driven invalidation**: The write publishes an event to Kafka or a pub/sub channel; a cache invalidation consumer subscribes and invalidates the affected keys.
- **CDC-driven invalidation**: A CDC tool (Debezium) tails the DB write log and invalidates cache keys when it detects relevant row changes — no application code change needed.

**Q12. What are the risks of direct invalidation (invalidating the cache in the same code path as the DB write)?**
A: Three main risks:
- **Partial failure**: The DB write succeeds but the cache invalidation call fails (Redis is down, network blip) — the cache now holds stale data with no automatic recovery until TTL expires. Always keep a TTL as a safety net even when doing event-driven invalidation.
- **Race condition on repopulation**: Delete the cache key, then another request immediately reads and re-populates it from the DB before the DB write has fully replicated to replicas — the cache is repopulated with the old value. Use a short post-invalidation lock or route the repopulation read to the primary.
- **Tight coupling**: The write service must know which cache keys are affected by its write. In a microservices system, a User service write shouldn't need to know that the Order service caches user data.

**Q13. How does message-driven cache invalidation decouple the write path from cache management?**
A: The write service publishes a domain event (`UserUpdated`, `PriceChanged`) to Kafka or Redis Pub/Sub. A dedicated cache invalidation service (or a sidecar) subscribes to these events and performs the cache operations. The write service has no knowledge of cache keys or cache topology — it just publishes what happened. This is the correct pattern in microservices: each service manages its own cache, and it listens for upstream change events to invalidate entries. The trade-off is additional async lag (Kafka consumer lag between write and invalidation) — a short window where the cache is still warm with stale data.

**Q14. How does CDC-driven cache invalidation work with Debezium?**
A: Debezium tails the Postgres WAL and emits a change event for every row insert, update, or delete. A Kafka consumer reads these change events, maps them to cache keys, and invalidates them:
```
DB row update on `products` (id=42)
  → Debezium emits: { op: "u", after: { id: 42, price: 99.99, ... } }
  → Consumer maps: cache key = "product:42"
  → Consumer executes: Redis DEL product:42
                    OR: Redis SET product:42 <serialised new value> EX 3600
```
The advantage over application-level invalidation: no code change required in the write service, the invalidation is guaranteed to fire for every DB commit (CDC reads from the WAL, not application code), and you can invalidate or update the cache with the new value directly (avoiding a re-read round trip).

**Q15. What is the "cache invalidation fan-out" problem?**
A: A single data change may invalidate many cache keys. Example: updating a user's name might require invalidating their profile cache, their author byline on every post they've written, their cached order history, and their session. At large scale, a single write can trigger invalidation of hundreds of keys across multiple cache nodes. Strategies:
- **Tag-based invalidation**: Associate cache keys with tags (`user:42`, `post:author:42`). On a user update, invalidate all keys tagged `user:42`. Redis doesn't support tags natively — implement with a Redis Set per tag storing all associated keys, then `SMEMBERS` + `DEL` in a pipeline.
- **Namespace versioning**: Increment a namespace version for `user:42`; all keys under that namespace include the version and naturally "expire" logically without individual deletion (covered in Section 4).
- **Selective invalidation**: Only invalidate the specific keys you know will be read next — accept that other derived caches will self-heal via TTL.

**Q16. How do you handle cache invalidation in a multi-region deployment?**
A: Each region has its own cache cluster; a write in Region A must invalidate caches in Region B and C. Options:
- **Geo-replicated cache** (Redis Enterprise, Elasticache Global Datastore): Writes replicate across regions automatically — but with replication lag, so invalidation isn't instant everywhere.
- **Publish to a global event bus**: The write publishes to a global Kafka topic; each region's cache invalidation consumer subscribes and clears local caches.
- **Accept regional staleness**: Design caches so that cross-region staleness is tolerable — use short TTLs in remote regions, treat the write-origin region as authoritative, and let other regions self-heal via TTL.
- **Route reads to write-origin region for fresh data**: After a write, short-circuit the next read to the origin region where the cache is warm with fresh data.

## Section 4: Versioned Keys

**Q17. What are versioned cache keys, and how do they work?**
A: Instead of storing a value under a stable key (`user:42`) and invalidating it on change, you embed a version into the key itself (`user:42:v7`). When data changes, the version increments to `v8`; reads now request `user:42:v8` — which is a cache miss, so it's fetched fresh from the DB and stored under the new key. The old key (`user:42:v7`) is never explicitly deleted — it simply expires via TTL or eviction. No invalidation logic is needed; the key change *is* the invalidation.

**Q18. Where is the current version stored, and how is it retrieved?**
A: The current version must be stored somewhere that's fast to read and consistent — typically Redis itself, or a DB column:
- **Redis version key**: `GET user:42:version` → `7`. Construct the cache key as `user:42:v{version}`. On data change, atomically `INCR user:42:version`.
- **DB column**: Store a `cache_version` integer column on the entity. On every update, `UPDATE users SET ..., cache_version = cache_version + 1`. The cache key is `user:42:v{cache_version}`, read from the DB or embedded in the API response.
- **Content hash**: Use a hash of the entity's content as the version — `user:42:{md5(content)}`. Version changes automatically when content changes, no explicit version management. Used heavily in CDN cache-busting for static assets.

**Q19. What are the advantages of versioned keys over explicit invalidation?**
A:
- **No deletion race conditions**: You never delete a key that another request might be in the middle of reading. Old keys coexist harmlessly until eviction.
- **No coordination on write**: The write path just increments the version; no DEL or SET on the cache required.
- **Instant "invalidation" without touching Redis**: If the version is stored in the DB, a DB update automatically makes all old cache entries unreachable — without any Redis operation at write time.
- **Cache warming is natural**: The next read after a version bump just populates the new key; no separate warming step.
- **Rollback-friendly**: If a deployment is rolled back, the old version key may still be warm in the cache — instant cache hit with no warming period.

**Q20. What are the disadvantages of versioned keys?**
A:
- **Version lookup overhead**: Every cache read requires first fetching the current version (an extra Redis GET or DB read), then constructing and fetching the actual key — two round trips instead of one. Mitigate by embedding the version in the request context (API response includes the version, client passes it back) or caching the version itself with a very short TTL.
- **Key proliferation**: Old versioned keys accumulate until TTL expires or eviction. A key that's updated frequently generates many short-lived keys, increasing Redis memory pressure. Set aggressive TTLs on versioned keys.
- **Version storage consistency**: The version itself must be consistent — if it's stored in Redis and Redis loses the version key (eviction, flush), you lose the ability to construct the correct cache key until the version is re-established.
- **Not suitable for list/collection caches**: If a cache key represents a list of items (search results, a user's orders), versioning the whole list invalidates the entire list on any single item change. Item-level versioning + list reassembly is complex.

**Q21. How do versioned keys apply to CDN cache-busting for static assets?**
A: The exact same principle, applied at the HTTP layer. Static assets are deployed with a content hash in the filename or query string: `app.a3f8c2.js` or `styles.css?v=a3f8c2`. The CDN caches the asset forever (TTL = infinite / `Cache-Control: immutable`). When the asset changes, the build pipeline generates a new hash; the HTML references the new filename. The old cached version is never invalidated — it simply becomes unreferenced. This is the most reliable cache invalidation strategy in existence: content-addressed storage means the key *is* the content hash, so a key change always means a content change and vice versa.

## Section 5: Advanced Patterns & Edge Cases

**Q22. What is a write-around cache pattern, and when is it useful?**
A: Write-around bypasses the cache entirely on writes — data goes directly to the DB without updating or invalidating the cache. The cache is only populated on reads (cache-aside). Useful when writes are frequent but reads of the same data are rare — writing to the cache would waste memory on data that's never re-read before its TTL expires. Example: write-heavy logging or event streams where the written data is almost never read back through the same path. Trade-off: the first read after a write is always a cache miss.

**Q23. What is a cache warming strategy, and when is it needed?**
A: Cache warming is proactively populating the cache before traffic hits, to avoid a cold-start stampede. Needed after: deployments that flush the cache, scaling events that add new cache nodes, planned cache cluster failovers. Approaches:
- **Lazy warming (natural)**: Accept the cold-start miss spike; the cache warms itself under traffic. Works for non-critical services or low-traffic endpoints.
- **Read-ahead warming**: After deployment, replay recent read patterns against the cache programmatically — fetch the top N most-requested keys from logs and pre-populate them before opening traffic.
- **Shadow traffic**: Route a copy of live traffic to the new cache nodes before switching them to production, warming them under real traffic patterns.
- **Persistent cache snapshots**: Redis `BGSAVE` / RDB snapshots — restore from a recent snapshot on restart so the cache starts warm rather than empty.

**Q24. What is cache poisoning, and how do you prevent it?**
A: Cache poisoning is storing invalid, malicious, or corrupted data in the cache such that subsequent reads serve the bad data to all users. Sources: a bug that writes incorrect data to the cache, an attacker manipulating cache keys (e.g., HTTP response splitting in web caches), or a race condition that stores a partial/corrupt value. Prevention:
- **Validate before caching**: Never cache a value without validating it against your schema — if the DB returns unexpected data, don't populate the cache.
- **Short TTL as a safety net**: Even if bad data gets in, it expires quickly.
- **Atomic cache writes**: Use Redis transactions (`MULTI/EXEC`) or Lua scripts to ensure the cache is never written in a half-populated state.
- **Key namespacing and input sanitisation**: Never construct cache keys from user input without strict sanitisation and length limits.

**Q25. How do you handle cache invalidation for paginated or list-based caches?**
A: List caches are the hardest invalidation problem — a single item change can affect many pages. Strategies:
- **Short TTL, no event-driven invalidation**: Accept that list caches are eventually consistent; use a short TTL (30–60 seconds). Works for non-critical feeds and search results.
- **Invalidate the entire list namespace on any change**: On item add/update/delete, delete all pages of the list. Simple but aggressive — next requests re-query all pages.
- **Cursor-based caching instead of offset**: Cache by cursor token rather than offset page number — cursors are stable between writes, so fewer pages are invalidated by a new item.
- **Separate item cache + list of IDs**: Cache individual items by ID (long TTL) and cache the list of IDs separately (short TTL or event-invalidated). Reads fetch the ID list, then hydrate from the item cache. Only the ID list needs invalidation on structural changes; item caches invalidate individually.

**Q26. What is the "thundering herd on deployment" problem and how do you solve it?**
A: When a new version of a service deploys, it often connects to a fresh Redis cluster (or flushes the cache as part of the deploy), making all cache entries cold simultaneously. All requests miss at once, hammering the DB until the cache warms. Solutions:
- **Blue-green cache namespacing**: The new deployment uses a different cache namespace prefix from the old — it warms gradually as traffic shifts, while the old deployment's cache remains warm for in-flight requests.
- **Zero-downtime cache migration**: Warm the new cache cluster from the old one before switching traffic (Redis `MIGRATE` or a read-from-both-write-to-new strategy).
- **Rate-limited DB fallback**: If cache miss rate spikes above a threshold, rate-limit DB queries and queue the excess — prevent the DB from being overwhelmed even if the cache is cold.
- **Persistent snapshots**: Restore the Redis cache from a recent RDB snapshot on deploy, so it starts warm.

## Section 6: Trade-offs & Decision-Making

**Q27. How do you choose between TTL, event-driven, and versioned key invalidation?**
A: Choose based on staleness tolerance and write pattern:

| Scenario | Recommended Strategy |
|---|---|
| Config / reference data, changes rarely | Long TTL (hours) — simplicity wins |
| Product catalogue, infrequent updates | TTL (minutes–hours) + event-driven on write |
| User profile, moderate update frequency | Event-driven invalidation on write + TTL fallback |
| Financial data (balance, limits) | Bypass cache entirely OR write-through with immediate invalidation |
| Multi-service read fan-out | Versioned keys — decouple invalidation from write path |
| Static assets / CDN | Content-addressed versioned keys (immutable TTL) |
| Paginated / list results | Short TTL + accept eventual consistency |
| High-write, high-read aggregates | CQRS read model — cache the read model, not the raw data |

**Q28. What are the signs that your cache invalidation strategy is failing in production?**
A: Watch for:
- **Stale data complaints from users** — profile changes not reflected, prices showing old values.
- **Cache hit rate dropping over time** — aggressive invalidation is evicting too many keys; the cache isn't staying warm.
- **DB CPU spikes correlated with deploys or scheduled TTL expirations** — thundering herd / stampede.
- **Memory pressure and eviction rate climbing** — key proliferation from versioned keys or unbounded list caches; missing TTLs on some key patterns.
- **Inconsistent data across regions or services** — multi-region invalidation lag, or a service caching data it doesn't know to invalidate when upstream changes.
- **Redis `keyspace_hits` / `keyspace_misses` ratio degrading** — monitor with `INFO stats`; a worsening hit ratio signals either over-invalidation or wrong TTL choices.

**Q29. Should you ever skip caching for a data type entirely?**
A: Yes — some data should never be cached, or cached only with extreme care:
- **Real-time financial balances**: A stale balance cached for even 1 second can lead to overdrafts or double-spend. Route balance reads to the DB primary always, or use a write-through cache with synchronous invalidation.
- **Security / auth tokens**: Revoked tokens must not be served from cache. Either don't cache them, or use an event-driven revocation list that's checked on every read.
- **Idempotency keys**: If you cache "this payment ID has been processed" and the cache is stale, you may process a payment twice. Store idempotency state in the DB with strong consistency, not the cache.
- **ACL / permission data**: A user whose permissions were revoked must not continue to get cached "allowed" responses. Short TTL + event-driven invalidation on permission changes, or skip caching entirely for high-security permission checks.

## Section 7: Scenario / System Design Questions

**Q30. "Your product page is showing an old price after a price update. Users are completing purchases at the wrong price. How do you fix this?"**
A: Two failures: the cache wasn't invalidated on price update, and the TTL was too long. Immediate fix: `DEL product:{id}` from the write path in the price update API. Durable fix: implement event-driven invalidation — when `PriceUpdated` event fires (either from the write path or via Debezium), the cache invalidation consumer deletes `product:{id}`. Add a write-through on the invalidation: instead of just deleting, `SET product:{id} <new serialised product> EX 3600` so the next read is a hit, not a miss. Keep a 1-hour TTL as a safety net. Also add a cache version to the checkout flow — the checkout page reads the price at checkout time from the DB (not cache) to confirm the price hasn't changed since the product page was rendered.

**Q31. "Design the cache invalidation strategy for a NACH payment status system where the BRE updates payment state and multiple downstream services read that state."**
A: Multiple services reading the same BRE-produced state is a fan-out invalidation problem. Strategy:
1. **Versioned keys per payment**: Cache key is `payment:{id}:v{version}`. The `payments` table has a `cache_version` column incremented on every BRE state update.
2. **CDC via Debezium**: On every `payments` row update, Debezium emits a change event with the new `cache_version`.
3. **Each downstream service's cache invalidation consumer** reads the event, constructs `payment:{id}:v{old_version}`, deletes it, and pre-populates `payment:{id}:v{new_version}` with the new payload from the event body (no re-read needed — the new state is in the event).
4. **TTL on all keys**: 5-minute TTL on all versioned keys as a safety net.
5. **Critical reads bypass cache**: Fraud checks and deduplication reads go to the DB primary — never cached.
This gives each service an independently managed, near-instantly invalidated cache with no direct coupling to the BRE write path.

**Q32. "A Redis cache key for a user's permission set is being read 50,000 times per second. How do you handle invalidation when permissions change without causing a stampede?"**
A: A hot key like this needs both careful invalidation and stampede prevention:
1. **In-process L1 cache**: Each application node caches the permission set in memory for 5 seconds. Permission checks are served from memory — zero Redis calls. Invalidation of the in-process cache is triggered by the Redis Pub/Sub `SUBSCRIBE permissions:invalidate:{user_id}` channel.
2. **Redis invalidation on permission change**: The write path publishes to `permissions:invalidate:{user_id}` — each app node's subscriber clears its in-process cache for that user.
3. **Stale-while-revalidate in Redis**: The Redis key has a "soft TTL" stored alongside the value. On read, if soft TTL has passed, one request triggers a background refresh while others continue serving the stale value — preventing stampede.
4. **Probabilistic early expiration**: As the Redis key's TTL approaches zero, reads increasingly trigger early background refresh, so the key is never actually cold when it expires.
At 50k reads/second, the L1 in-process cache is the most important layer — it absorbs the load before it ever reaches Redis.

**Q33. "After a deployment, your API response times spike for 2 minutes before recovering. You suspect cache stampede. How do you confirm and fix it?"**
A: Confirm via metrics: check Redis `keyspace_misses` spike at deploy time, DB connection pool saturation or query rate spike, and API latency percentiles correlating with the deploy timestamp. If misses spike and DB load spikes simultaneously at deploy, it's a cold-cache stampede.

Fixes:
1. **Immediate**: Add TTL jitter to all cache writes — spread expirations so they don't all land at once.
2. **Short-term**: Implement a mutex lock on cache population (`SET lock:{key} 1 NX EX 5`) — only one request rebuilds each key; others wait and hit cache.
3. **Structural**: Warm the cache before switching traffic — run a cache-warming script as part of the deploy pipeline that pre-populates the top 1,000 most-read keys before the new instances receive traffic.
4. **Long-term**: Persist the cache across deployments using Redis RDB snapshots — restore from the last snapshot on startup so the new deployment starts warm, not cold.

## Quick Comparison Table

| Strategy              | Staleness Window        | Complexity | Write Coupling | Best For                                        |
|-----------------------|-------------------------|------------|----------------|-------------------------------------------------|
| TTL only              | Up to full TTL          | Low        | None           | Config data, reference data, tolerant reads     |
| TTL + jitter          | Up to full TTL (spread) | Low        | None           | Any TTL use case with hot key stampede risk     |
| Direct invalidation   | Seconds (write lag)     | Medium     | Tight          | Single-service writes, simple topologies        |
| Message-driven        | Kafka consumer lag      | Medium     | Loose          | Microservices, cross-service invalidation       |
| CDC-driven            | WAL replication lag     | High       | None           | Any DB write, no app code change required       |
| Versioned keys        | Zero (key miss = fresh) | Medium     | None           | Multi-reader fan-out, rollback-safe caching     |
| Content-addressed     | Zero (immutable)        | Low        | None           | Static assets, CDN, build artefacts             |
| Write-through         | Zero                    | Medium     | Tight          | Low-write, high-read, freshness-critical data   |

---

**Tip for the interview:** At the 5 YOE level, interviewers want to see that you treat cache invalidation as a correctness problem, not just a performance one. The strongest answers name the *failure mode* of each strategy — TTL causes stale data, direct invalidation has partial failure and race condition risks, versioned keys cause key proliferation and version-lookup overhead — and explain how you layer strategies (TTL as a safety net under event-driven invalidation, L1 in-process cache under Redis, versioned keys for fan-out scenarios). In a fintech context, be ready to state explicitly which data you will *not* cache (balances, idempotency keys, revocation lists) and why — that boundary-drawing is what separates a thoughtful engineer from one who over-caches everything.
