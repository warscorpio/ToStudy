# Circuit Breaker Pattern: Closed → Open → Half-Open States — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does the circuit breaker pattern solve, and what failure mode makes it necessary?**
A: The circuit breaker pattern prevents cascading failures in distributed systems. Without it, a single failing downstream service can exhaust the thread pool, connection pool, or memory of every upstream service calling it — a phenomenon called cascading failure or cascade collapse. The pattern is named after the electrical circuit breaker that trips to protect wiring from overload:

```
The cascading failure without a circuit breaker:

  Normal flow:
    Client → API Gateway → Order Service → Payment Service (200ms, healthy)

  Payment Service starts failing (DB overloaded, latency → 30s):

    Client → API Gateway → Order Service → Payment Service
                                  │              │
                                  │         waits 30s
                                  │              │
                                  │         returns 500
                                  │
                        Thread held for 30s per request
                        At 100 req/s: 100 threads × 30s = 3000 threads blocked
                        Thread pool exhausted: 1001st request hangs immediately
                        Order Service stops responding
                        API Gateway threads now block on Order Service

  Cascade:
    Payment Service fails → Order Service starves → API Gateway starves → Users see 504

  The failure from one service propagates upstream and destroys healthy services.
  The payment service being slow is bad; the payment service taking down order
  service and the gateway is catastrophic.
```

```
What a circuit breaker provides:

  With a circuit breaker around the Payment Service call:

  Payment Service starts failing (latency → 30s):

    Requests 1-5:   Payment Service times out
    Circuit breaker: "5 failures in 10 seconds — OPEN the circuit"

    Request 6+:     Circuit breaker short-circuits immediately
                    Returns fallback response in < 1ms
                    Does NOT call Payment Service at all
                    Thread returns immediately — no exhaustion

  Result:
    Payment Service fails → Order Service stays healthy (fast fallback)
    Order Service stays healthy → API Gateway stays healthy
    Users see "payment unavailable" instead of total outage

  Additional benefits:
    Failing service gets relief: fewer requests → more time to recover
    Faster feedback to callers: immediate error vs 30s timeout
    Automatic recovery: half-open state probes for recovery without manual intervention
    Visibility: circuit state is an observable metric (open = something is wrong)
```

**Q2. What are the three states of a circuit breaker and what transitions them?**
A: The circuit breaker is a finite state machine with three states. Each state determines how calls are handled, and specific conditions trigger transitions between states:

```
State machine diagram:

                    failure threshold                   timeout expires
                    exceeded                            (probe time)
    ┌─────────┐ ──────────────────► ┌─────────┐ ──────────────────► ┌────────────┐
    │         │                     │         │                      │            │
    │  CLOSED │                     │  OPEN   │                      │ HALF-OPEN  │
    │         │ ◄────────────────── │         │                      │            │
    └─────────┘    reset (manually  └─────────┘                      └─────┬──────┘
         ▲           or on success)      ▲                                 │
         │                               │                                 │
         │                               │ probe fails                     │ probe succeeds
         │                               └─────────────────────────────────┘
         │                                                                 │
         └─────────────────────────────────────────────────────────────────┘
                              success threshold met

  ┌──────────────────────────────────────────────────────────────────────────────┐
  │ CLOSED (normal operation)                                                    │
  │   Calls pass through to the downstream service                               │
  │   Failures are counted within a time window                                  │
  │   Transition to OPEN: when failure rate or count exceeds threshold            │
  │   Example threshold: >50% failure rate in the last 10 requests               │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │ OPEN (tripped — service presumed down)                                       │
  │   All calls fail immediately without attempting the downstream service        │
  │   Returns error or fallback response in < 1ms                                │
  │   Transition to HALF-OPEN: after a configured reset timeout                  │
  │   Example timeout: 30 seconds after tripping                                 │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │ HALF-OPEN (probing — is the service recovered?)                              │
  │   Allows a limited number of probe requests through                          │
  │   Remaining requests still fail fast (not all traffic let through)            │
  │   Probe succeeds → transition to CLOSED (service recovered)                  │
  │   Probe fails → transition back to OPEN (still down, reset timeout restarts) │
  └──────────────────────────────────────────────────────────────────────────────┘
```

```typescript
// State machine in code — the core logic:
enum CircuitState {
    CLOSED,
    OPEN,
    HALF_OPEN
}

class CircuitBreaker {
    private state: CircuitState = CircuitState.CLOSED;
    private failureCount = 0;
    private successCount = 0;
    private lastFailureTime: number | null = null;

    // Configuration:
    private readonly failureThreshold: number;    // e.g. 5 failures
    private readonly resetTimeout: number;        // e.g. 30,000ms
    private readonly halfOpenProbeCount: number;  // e.g. 3 probe requests

    canAttempt(): boolean {
        switch (this.state) {
            case CircuitState.CLOSED:
                return true;  // Always attempt

            case CircuitState.OPEN:
                // Check if reset timeout has elapsed:
                const elapsed = Date.now() - (this.lastFailureTime ?? 0);
                if (elapsed >= this.resetTimeout) {
                    this.transitionTo(CircuitState.HALF_OPEN);
                    return true;  // Allow first probe
                }
                return false;  // Still open — fail fast

            case CircuitState.HALF_OPEN:
                // Only allow limited probe requests:
                return this.successCount + this.failureCount < this.halfOpenProbeCount;
        }
    }

    recordSuccess(): void {
        this.failureCount = 0;

        if (this.state === CircuitState.HALF_OPEN) {
            this.successCount++;
            // If enough successful probes: close the circuit:
            if (this.successCount >= this.halfOpenProbeCount) {
                this.transitionTo(CircuitState.CLOSED);
            }
        }
    }

    recordFailure(): void {
        this.lastFailureTime = Date.now();
        this.failureCount++;

        if (this.state === CircuitState.HALF_OPEN) {
            // Even one failure in half-open → back to open:
            this.transitionTo(CircuitState.OPEN);
        } else if (this.state === CircuitState.CLOSED) {
            if (this.failureCount >= this.failureThreshold) {
                this.transitionTo(CircuitState.OPEN);
            }
        }
    }

    private transitionTo(newState: CircuitState): void {
        console.log(`Circuit breaker: ${this.state} → ${newState}`);
        this.state = newState;
        this.failureCount = 0;
        this.successCount = 0;
    }
}
```

## Section 2: The CLOSED State

**Q3. How does the CLOSED state work — what failure detection strategies exist?**
A: In the CLOSED state, all calls pass through to the downstream service. The circuit breaker monitors outcomes (successes and failures) and compares them against thresholds to decide when to open. There are two main failure detection strategies: count-based and rate-based:

```
Count-based detection:
  Track the last N requests
  Open when: failure count in window >= threshold
  Example: 5 failures in the last 10 requests

  Window: [ S S F S F F F F S S ]  (S=success, F=failure)
                    ↑
                    5th failure → OPEN

  Problem: susceptible to bursty traffic
  At 1 req/sec: 5 failures in 10 seconds → opens
  At 100 req/sec: 5 failures in 0.05 seconds → opens on very brief blip

Rate-based detection:
  Track failure PERCENTAGE over a sliding time window
  Open when: failure rate >= threshold percentage
  Example: >50% failure rate over 10-second window with minimum 10 requests

  This is more robust for variable traffic:
  At 1 req/sec: 5 failures out of 10 = 50% → opens (matches threshold)
  At 100 req/sec: 5 failures out of 1000 = 0.5% → does NOT open (below 50%)
  The minimum request count prevents opening on first few requests

  Sliding window implementation:
  ├── Time-based: evaluate last N seconds regardless of request count
  └── Count-based: evaluate last N requests regardless of time elapsed
```

```typescript
// Rate-based sliding window circuit breaker (closer to Resilience4j's model):
class RateBasedCircuitBreaker {
    private readonly windowSize: number;         // e.g. 10 (last 10 requests)
    private readonly failureRateThreshold: number; // e.g. 0.5 (50%)
    private readonly minimumRequests: number;    // e.g. 5 (need at least 5 requests)
    private readonly resetTimeoutMs: number;     // e.g. 30000

    private outcomes: boolean[] = [];  // true = success, false = failure
    private state = CircuitState.CLOSED;
    private openedAt: number | null = null;

    async execute<T>(fn: () => Promise<T>, fallback?: () => T): Promise<T> {
        if (!this.canAttempt()) {
            if (fallback) return fallback();
            throw new CircuitOpenError('Circuit breaker is OPEN');
        }

        try {
            const result = await fn();
            this.recordOutcome(true);
            return result;
        } catch (err) {
            this.recordOutcome(false);
            if (fallback && this.state === CircuitState.OPEN) {
                return fallback();
            }
            throw err;
        }
    }

    private recordOutcome(success: boolean): void {
        // Maintain sliding window of last N outcomes:
        this.outcomes.push(success);
        if (this.outcomes.length > this.windowSize) {
            this.outcomes.shift();  // Remove oldest
        }

        // Only evaluate if we have enough data:
        if (this.outcomes.length < this.minimumRequests) return;

        const failures = this.outcomes.filter(o => !o).length;
        const failureRate = failures / this.outcomes.length;

        if (this.state === CircuitState.CLOSED && failureRate >= this.failureRateThreshold) {
            this.trip();
        } else if (this.state === CircuitState.HALF_OPEN) {
            if (success) {
                this.close();  // Probe succeeded
            } else {
                this.trip();   // Probe failed → back to open
            }
        }
    }

    private trip(): void {
        this.state = CircuitState.OPEN;
        this.openedAt = Date.now();
        this.outcomes = [];
        console.warn(`Circuit OPENED at ${new Date().toISOString()}`);
    }

    private close(): void {
        this.state = CircuitState.CLOSED;
        this.openedAt = null;
        this.outcomes = [];
        console.info(`Circuit CLOSED at ${new Date().toISOString()}`);
    }

    private canAttempt(): boolean {
        if (this.state === CircuitState.CLOSED) return true;

        if (this.state === CircuitState.OPEN) {
            const elapsed = Date.now() - (this.openedAt ?? 0);
            if (elapsed >= this.resetTimeoutMs) {
                this.state = CircuitState.HALF_OPEN;
                return true;  // Allow probe
            }
            return false;
        }

        if (this.state === CircuitState.HALF_OPEN) {
            return true;  // Single probe allowed
        }

        return false;
    }
}
```

## Section 3: The OPEN State

**Q4. What happens in the OPEN state — how do you implement fallback behaviour and what are the fallback strategies?**
A: In the OPEN state, the circuit breaker short-circuits all calls — it does not contact the downstream service at all. The caller either receives an immediate error or a fallback response. The fallback strategy is what separates a good circuit breaker implementation from a great one:

```
OPEN state behaviour:

  Incoming request
       │
       ▼
  ┌─────────────────────────────┐
  │  Circuit Breaker (OPEN)     │
  │                             │
  │  canAttempt() → false       │
  │                             │
  │  Has fallback configured?   │
  │    YES → return fallback    │  (sub-millisecond response)
  │    NO  → throw error        │
  └─────────────────────────────┘
       │
       ▼
  Downstream service NOT called (protected from load)

  Key: the downstream service receives ZERO calls while circuit is open
  This gives it breathing room to recover
```

```typescript
// Fallback strategies — from most to least graceful:

// Strategy 1: Return cached data (best user experience):
class CachedFallbackBreaker {
    private cache = new Map<string, { value: unknown; expiresAt: number }>();

    async getUser(userId: string): Promise<User> {
        return this.breaker.execute(
            () => this.userService.getUser(userId),
            // Fallback: return last known good value from cache:
            () => {
                const cached = this.cache.get(userId);
                if (cached && cached.expiresAt > Date.now()) {
                    return cached.value as User;
                }
                throw new ServiceUnavailableError('User service unavailable, no cached data');
            }
        );
    }

    // After each successful call: update cache:
    private async executeWithCacheUpdate(userId: string): Promise<User> {
        const user = await this.userService.getUser(userId);
        this.cache.set(userId, {
            value: user,
            expiresAt: Date.now() + 5 * 60 * 1000  // Cache for 5 minutes
        });
        return user;
    }
}

// Strategy 2: Return a default/degraded response:
async getProductRecommendations(userId: string): Promise<Product[]> {
    return this.breaker.execute(
        () => this.recommendationService.getFor(userId),
        // Fallback: return bestsellers instead of personalised recommendations:
        () => this.cache.getBestSellers()  // Preloaded, always available
    );
}

// Strategy 3: Return empty/neutral response:
async getUserPreferences(userId: string): Promise<Preferences> {
    return this.breaker.execute(
        () => this.preferencesService.get(userId),
        // Fallback: return empty preferences (app works without them):
        () => ({ theme: 'default', language: 'en', notifications: true })
    );
}

// Strategy 4: Fail fast with a specific error (for critical paths):
async processPayment(payment: Payment): Promise<PaymentResult> {
    return this.breaker.execute(
        () => this.paymentService.process(payment),
        // No fallback — payment MUST succeed or fail explicitly:
        () => { throw new PaymentServiceUnavailableError('Payment service unavailable'); }
    );
    // The caller shows: "Payment service temporarily unavailable, please try again"
    // User waits and retries — better than charging a card with no confirmation
}

// Strategy 5: Queue for later processing (async paths):
async sendNotification(notification: Notification): Promise<void> {
    return this.breaker.execute(
        () => this.notificationService.send(notification),
        // Fallback: queue it for later delivery:
        async () => {
            await this.queue.push('notifications', notification);
            console.warn('Notification queued for later delivery');
        }
    );
}
```

```typescript
// OPEN state timer — how long to stay open:

// Fixed timeout:
const RESET_TIMEOUT = 30_000;  // Always wait 30 seconds

// Exponential backoff — increase wait time on repeated failures:
class BackoffCircuitBreaker {
    private openCount = 0;   // How many times has this circuit been opened?

    private getResetTimeout(): number {
        const baseTimeout = 5_000;   // 5 seconds
        const maxTimeout = 300_000;  // 5 minutes
        // 1st open: 5s, 2nd: 10s, 3rd: 20s, 4th: 40s... capped at 5m
        return Math.min(baseTimeout * Math.pow(2, this.openCount), maxTimeout);
    }

    private trip(): void {
        this.openCount++;
        this.openedAt = Date.now();
        this.state = CircuitState.OPEN;
        // Next probe will happen in getResetTimeout() ms
    }

    private close(): void {
        this.openCount = 0;  // Reset backoff on successful recovery
        this.state = CircuitState.CLOSED;
    }
}

// Rationale for exponential backoff:
// A service recovering from a major incident may need more than 30 seconds
// Rapid probe cycles put additional load on a recovering service
// If the circuit has tripped 5 times, something is seriously wrong → wait longer
```

## Section 4: The HALF-OPEN State

**Q5. How does the HALF-OPEN state work — what are the probe strategies and why does it matter?**
A: The HALF-OPEN state is the circuit breaker's recovery detection mechanism. After the reset timeout expires, the circuit allows a limited number of test requests through to determine if the downstream service has recovered. Getting this state right prevents premature recovery (re-opening immediately) and unnecessary latency (staying open too long):

```
HALF-OPEN state mechanics:

  OPEN circuit → reset timeout expires → HALF-OPEN

  In HALF-OPEN:
  ├── Allow 1 probe request (minimal) or N probe requests (faster assessment)
  ├── Non-probe requests: still fail fast (circuit still functionally open)
  └── Decision:
       Probe succeeds → CLOSED (service recovered)
       Probe fails    → OPEN again (reset timeout restarts)

  Why limit to a small number of probes?
    The service might be in a fragile state — just barely recovering
    Sending all traffic immediately could overwhelm it again
    1-3 probes gives signal without risking re-collapse

  The probe sample size matters:
    Too few (1): single fluke success re-closes the circuit → unstable cycling
    Too many (10): slow to recover, probe requests accumulate
    Typical: 3-5 probe requests with all succeeding to re-close
```

```typescript
// Half-open probe implementation with concurrent request limiting:
class HalfOpenCircuitBreaker {
    private state = CircuitState.CLOSED;
    private probeCount = 0;
    private probeSuccessCount = 0;
    private readonly requiredSuccessfulProbes = 3;

    async execute<T>(fn: () => Promise<T>, fallback?: () => T): Promise<T> {
        if (this.state === CircuitState.OPEN) {
            if (!this.shouldTransitionToHalfOpen()) {
                return this.callFallback(fallback);
            }
            this.state = CircuitState.HALF_OPEN;
            this.probeCount = 0;
            this.probeSuccessCount = 0;
        }

        if (this.state === CircuitState.HALF_OPEN) {
            // Only allow limited probes; reject others immediately:
            if (this.probeCount >= this.requiredSuccessfulProbes) {
                // Probe slots full — non-probe request: fail fast
                return this.callFallback(fallback);
            }
            this.probeCount++;
        }

        try {
            const result = await fn();
            this.onSuccess();
            return result;
        } catch (err) {
            this.onFailure(err);
            throw err;
        }
    }

    private onSuccess(): void {
        if (this.state === CircuitState.HALF_OPEN) {
            this.probeSuccessCount++;
            if (this.probeSuccessCount >= this.requiredSuccessfulProbes) {
                // All probes succeeded: close the circuit
                this.state = CircuitState.CLOSED;
                this.resetCounts();
                this.emit('stateChange', { from: 'HALF_OPEN', to: 'CLOSED' });
            }
            // Not all probes done yet — keep in HALF_OPEN
        } else {
            this.failureCount = 0;  // Reset failure count on success in CLOSED
        }
    }

    private onFailure(err: unknown): void {
        if (this.state === CircuitState.HALF_OPEN) {
            // Even one failure in half-open → immediately reopen:
            this.state = CircuitState.OPEN;
            this.openedAt = Date.now();
            this.probeCount = 0;
            this.probeSuccessCount = 0;
            this.emit('stateChange', { from: 'HALF_OPEN', to: 'OPEN' });
        } else if (this.state === CircuitState.CLOSED) {
            this.failureCount++;
            if (this.failureCount >= this.failureThreshold) {
                this.state = CircuitState.OPEN;
                this.openedAt = Date.now();
                this.emit('stateChange', { from: 'CLOSED', to: 'OPEN' });
            }
        }
    }

    private shouldTransitionToHalfOpen(): boolean {
        return Date.now() - (this.openedAt ?? 0) >= this.resetTimeoutMs;
    }
}
```

```typescript
// Advanced: concurrent request limiting in HALF-OPEN
// Problem: multiple threads simultaneously hit the expired timer and all probe
// → All N threads become probes simultaneously (N requests hit fragile service)

class ConcurrentSafeHalfOpenBreaker {
    private probeInProgress = false;

    private canAttemptProbe(): boolean {
        if (this.state !== CircuitState.HALF_OPEN) return false;

        // Atomic check-and-set to prevent multiple simultaneous probes:
        if (this.probeInProgress) {
            return false;  // Another probe is in flight — fail fast
        }
        this.probeInProgress = true;
        return true;
    }

    private onProbeComplete(success: boolean): void {
        this.probeInProgress = false;
        if (success) {
            this.state = CircuitState.CLOSED;
        } else {
            this.state = CircuitState.OPEN;
            this.openedAt = Date.now();  // Reset timer
        }
    }
}

// In single-threaded Node.js: the probeInProgress flag works without locks
// In multi-threaded environments: use atomic compare-and-swap or mutex
```

## Section 5: Implementation with Production Libraries

**Q6. How do you implement circuit breakers in Node.js/NestJS with a production-grade library?**
A: Rolling your own circuit breaker is instructive but risky for production. Libraries like `opossum` (Node.js) and `@nestjs/circuit-breaker` provide battle-tested implementations with metrics, events, and timeout handling built in:

```typescript
// npm install opossum
// npm install --save-dev @types/opossum

import CircuitBreaker from 'opossum';

// Wrap any async function:
const breaker = new CircuitBreaker(
    async (userId: string) => {
        const response = await fetch(`http://user-service/users/${userId}`);
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        return response.json();
    },
    {
        // CLOSED → OPEN threshold:
        errorThresholdPercentage: 50,   // Open when >50% of requests fail
        volumeThreshold: 5,             // Minimum requests before evaluating
        timeout: 3000,                  // Treat calls > 3s as failures

        // OPEN → HALF-OPEN transition:
        resetTimeout: 30000,            // Wait 30s before probing

        // Metrics rolling window:
        rollingCountTimeout: 10000,     // Evaluate failures over last 10s
        rollingCountBuckets: 10,        // Split window into 10 × 1s buckets
    }
);

// Fallback for OPEN state:
breaker.fallback((userId: string) => ({
    id: userId,
    name: 'Unknown User',
    _fromFallback: true
}));

// Event monitoring:
breaker.on('open',     () => metrics.increment('circuit.user_service.open'));
breaker.on('close',    () => metrics.increment('circuit.user_service.close'));
breaker.on('halfOpen', () => metrics.increment('circuit.user_service.half_open'));
breaker.on('fallback', (result) =>
    logger.warn('User service circuit fallback triggered', { result })
);
breaker.on('reject',   () =>
    metrics.increment('circuit.user_service.rejected')
    // 'reject': fired when OPEN and a request is short-circuited
);
breaker.on('timeout',  () =>
    metrics.increment('circuit.user_service.timeout')
);
breaker.on('success',  (result, latencyMs) =>
    metrics.timing('circuit.user_service.latency', latencyMs)
);
breaker.on('failure',  (error, latencyMs) =>
    logger.error('User service call failed', { error: error.message, latencyMs })
);

// Usage:
async function getUser(userId: string): Promise<User> {
    return breaker.fire(userId);
}

// Check state:
console.log(breaker.status.stats);
// {
//   failures: 3, successes: 47, rejects: 12,
//   fallbacks: 12, timeouts: 2, latencyMean: 245
// }
console.log(breaker.opened);    // true if OPEN
console.log(breaker.halfOpen);  // true if HALF_OPEN
console.log(breaker.closed);    // true if CLOSED
```

```typescript
// NestJS service with circuit breaker:
// npm install opossum
// (or use the community @nestjs/circuit-breaker package)

import { Injectable, Logger } from '@nestjs/common';
import CircuitBreaker from 'opossum';
import { HttpService } from '@nestjs/axios';
import { firstValueFrom } from 'rxjs';

@Injectable()
export class PaymentService {
    private readonly logger = new Logger(PaymentService.name);
    private readonly breaker: CircuitBreaker;

    constructor(private readonly http: HttpService) {
        this.breaker = new CircuitBreaker(
            this.callPaymentApi.bind(this),
            {
                errorThresholdPercentage: 50,
                timeout: 5000,
                resetTimeout: 30000,
                volumeThreshold: 10,
                rollingCountTimeout: 30000,
            }
        );

        this.setupEvents();
    }

    async processPayment(payment: PaymentRequest): Promise<PaymentResult> {
        try {
            return await this.breaker.fire(payment);
        } catch (err) {
            if (err.code === 'EOPENBREAKER') {
                // Circuit is open — payment service presumed down
                throw new ServiceUnavailableException(
                    'Payment service is temporarily unavailable. Please try again in a moment.'
                );
            }
            throw err;
        }
    }

    private async callPaymentApi(payment: PaymentRequest): Promise<PaymentResult> {
        const response = await firstValueFrom(
            this.http.post<PaymentResult>(
                `${process.env.PAYMENT_SERVICE_URL}/payments`,
                payment,
                { timeout: 4500 }  // Slightly less than circuit breaker timeout
            )
        );
        return response.data;
    }

    private setupEvents(): void {
        this.breaker.on('open', () => {
            this.logger.warn('Payment service circuit OPENED — fast-failing requests');
        });
        this.breaker.on('halfOpen', () => {
            this.logger.log('Payment service circuit HALF-OPEN — probing...');
        });
        this.breaker.on('close', () => {
            this.logger.log('Payment service circuit CLOSED — resuming normal operation');
        });
        this.breaker.on('fallback', () => {
            this.logger.warn('Payment service fallback triggered');
        });
    }

    getHealthStatus(): object {
        return {
            state: this.breaker.opened ? 'OPEN'
                : this.breaker.halfOpen ? 'HALF_OPEN'
                : 'CLOSED',
            stats: this.breaker.stats,
        };
    }
}
```

```typescript
    name: string;
    threshold: number;
    timeout: number;
    resetTimeout: number;
    fallback?: (...args: unknown[]) => unknown;
}) {
    return (target: unknown, propertyKey: string, descriptor: PropertyDescriptor) => {
        const original = descriptor.value;
        const breaker = new CircuitBreaker(original, {
            errorThresholdPercentage: options.threshold,
            timeout: options.timeout,
            resetTimeout: options.resetTimeout,
        });

        if (options.fallback) {
            breaker.fallback(options.fallback);
        }

        descriptor.value = function (...args: unknown[]) {
            return breaker.fire(...args);
        };

        return descriptor;
    };
}

    async checkAvailability(productId: string): Promise<InventoryStatus> {
        return this.http.get(`/inventory/${productId}`);
    }
}
```

## Section 6: Bulkhead Pattern Integration

**Q7. How does the circuit breaker relate to the bulkhead pattern — and why should they be used together?**
A: The circuit breaker stops sending requests when a service is failing. The bulkhead limits the number of concurrent requests even when the service is healthy. Together they form the core of resilience: bulkhead prevents overloading a struggling service, circuit breaker stops calling a failed one:

```
Without bulkhead — thread exhaustion even before circuit opens:

  Payment service becomes slow (2s responses instead of 100ms):
  Requests arrive at 50 req/s × 2s per request = 100 concurrent threads needed
  Thread pool size: 20 → 20 threads busy → 30 queued → queue overflows
  Order service now has NO threads for other work
  Circuit breaker hasn't opened yet (< threshold failures, just slow)
  Order service is effectively down even though payment service is "working"

With bulkhead:

  Payment service calls: max 10 concurrent (bulkhead limit)
  Other 40 requests per second: immediately rejected from the bulkhead
  Order service retains threads for other work (user service, inventory, etc.)
  Circuit breaker counts the bulkhead rejections as failures
  Circuit opens faster (rejections count as failures)
  Result: isolated — payment slowness only affects payment calls
```

```typescript
// Bulkhead + circuit breaker together (thread pool / semaphore bulkhead):
import { Semaphore } from 'async-mutex';

class BulkheadCircuitBreaker<T> {
    private readonly semaphore: Semaphore;
    private readonly breaker: CircuitBreaker;

    constructor(
        fn: (...args: unknown[]) => Promise<T>,
        options: {
            maxConcurrent: number;      // Bulkhead: max concurrent calls
            queueSize: number;          // How many can wait in queue
            errorThreshold: number;     // Circuit: failure percentage
            timeout: number;            // Per-call timeout
            resetTimeout: number;       // Circuit: time before half-open
        }
    ) {
        // Semaphore limits concurrency (bulkhead):
        this.semaphore = new Semaphore(options.maxConcurrent);

        // Circuit breaker wraps the semaphore-guarded function:
        this.breaker = new CircuitBreaker(
            async (...args: unknown[]) => {
                const [value, release] = await this.semaphore.acquire();

                // If semaphore not available (all slots busy):
                if (value !== 1) {
                    // Queue is full — reject immediately:
                    throw new BulkheadFullError('Too many concurrent requests');
                }

                try {
                    return await fn(...args);
                } finally {
                    release();
                }
            },
            {
                errorThresholdPercentage: options.errorThreshold,
                timeout: options.timeout,
                resetTimeout: options.resetTimeout,
            }
        );
    }

    async execute(...args: unknown[]): Promise<T> {
        return this.breaker.fire(...args) as Promise<T>;
    }
}

// Usage:
const paymentBreaker = new BulkheadCircuitBreaker(
    (payment: Payment) => paymentService.process(payment),
    {
        maxConcurrent: 10,    // At most 10 simultaneous payment calls
        queueSize: 5,         // Allow 5 to queue (15 total at any moment)
        errorThreshold: 50,
        timeout: 5000,
        resetTimeout: 30000,
    }
);
```

## Section 7: Metrics and Observability

**Q8. What metrics should a circuit breaker expose, and how do you build observability around circuit state changes?**
A: A circuit breaker that trips silently is worse than having no circuit breaker — you need to know it opened, why it opened, and when it recovered. The circuit breaker should be a first-class observable component in your monitoring stack:

```typescript
// Comprehensive circuit breaker metrics:
import { Counter, Histogram, Gauge } from 'prom-client';

class ObservableCircuitBreaker {
    // Prometheus metrics:
    private readonly stateGauge: Gauge;           // Current state as number
    private readonly requestCounter: Counter;      // Total requests by outcome
    private readonly fallbackCounter: Counter;     // Fallback invocations
    private readonly latencyHistogram: Histogram;  // Call duration
    private readonly stateChangeCounter: Counter;  // State transitions

    constructor(private readonly serviceName: string) {
        this.stateGauge = new Gauge({
            name: 'circuit_breaker_state',
            help: 'Circuit breaker state: 0=CLOSED, 1=OPEN, 2=HALF_OPEN',
            labelNames: ['service']
        });

        this.requestCounter = new Counter({
            name: 'circuit_breaker_requests_total',
            help: 'Total circuit breaker requests by outcome',
            labelNames: ['service', 'outcome']
            // outcome: success, failure, timeout, rejected, fallback
        });

        this.latencyHistogram = new Histogram({
            name: 'circuit_breaker_call_duration_seconds',
            help: 'Circuit breaker call latency',
            labelNames: ['service', 'outcome'],
            buckets: [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2, 5]
        });

        this.stateChangeCounter = new Counter({
            name: 'circuit_breaker_state_changes_total',
            help: 'Circuit breaker state transitions',
            labelNames: ['service', 'from', 'to']
        });
    }

    wrapBreaker(breaker: CircuitBreaker): void {
        // Initial state:
        this.stateGauge.set({ service: this.serviceName }, 0); // CLOSED

        breaker.on('open', () => {
            this.stateGauge.set({ service: this.serviceName }, 1);
            this.stateChangeCounter.inc({ service: this.serviceName, from: 'CLOSED', to: 'OPEN' });
            // Alert: page on-call if this is a critical service
            this.sendAlert(`Circuit OPENED for ${this.serviceName}`);
        });

        breaker.on('halfOpen', () => {
            this.stateGauge.set({ service: this.serviceName }, 2);
            this.stateChangeCounter.inc({ service: this.serviceName, from: 'OPEN', to: 'HALF_OPEN' });
        });

        breaker.on('close', () => {
            this.stateGauge.set({ service: this.serviceName }, 0);
            this.stateChangeCounter.inc({ service: this.serviceName, from: 'HALF_OPEN', to: 'CLOSED' });
            this.sendAlert(`Circuit CLOSED (recovered) for ${this.serviceName}`);
        });

        breaker.on('success', (_result, latencyMs) => {
            this.requestCounter.inc({ service: this.serviceName, outcome: 'success' });
            this.latencyHistogram.observe(
                { service: this.serviceName, outcome: 'success' },
                latencyMs / 1000
            );
        });

        breaker.on('failure', (_error, latencyMs) => {
            this.requestCounter.inc({ service: this.serviceName, outcome: 'failure' });
            this.latencyHistogram.observe(
                { service: this.serviceName, outcome: 'failure' },
                latencyMs / 1000
            );
        });

        breaker.on('timeout', () => {
            this.requestCounter.inc({ service: this.serviceName, outcome: 'timeout' });
        });

        breaker.on('reject', () => {
            this.requestCounter.inc({ service: this.serviceName, outcome: 'rejected' });
        });

        breaker.on('fallback', () => {
            this.requestCounter.inc({ service: this.serviceName, outcome: 'fallback' });
        });
    }

    private sendAlert(message: string): void {
        // Send to PagerDuty, Slack, OpsGenie, etc.
        console.warn(`[CIRCUIT BREAKER ALERT] ${message}`);
    }
}
```

## Section 8: Advanced Patterns

**Q9. How do you handle circuit breakers in a multi-instance deployment — is state shared or per-instance?**
A: In a typical Node.js deployment, each application instance has its own circuit breaker with its own state — they don't share state by default. This is usually correct, but leads to inconsistent failure detection across instances. There are tradeoffs between local and distributed state:

```
Per-instance circuit breakers (default, most common):

  Instance 1: CLOSED   ← saw 3 failures
  Instance 2: OPEN     ← saw 12 failures (unlucky routing)
  Instance 3: CLOSED   ← saw 1 failure

  Some users (hitting Instance 2) get fast fallbacks
  Other users (hitting Instance 1/3) get slow failures
  Inconsistent experience, but:
  ✓ No distributed coordination overhead
  ✓ No single point of failure in circuit state
  ✓ Each instance independently decides based on what IT sees
  ✓ Works correctly for most use cases (load balancer distributes traffic)

  When per-instance is fine:
  - Traffic is distributed across instances via load balancer
  - All instances will see similar failure patterns
  - Slight inconsistency in when they open is acceptable

Distributed circuit breaker (share state across instances):

  All instances read/write circuit state to Redis:
  { "payment-service": { "state": "OPEN", "openedAt": 1710000000000 } }

  Instance 1 fails → writes OPEN to Redis
  Instance 2 reads state → sees OPEN → stops calling payment service immediately
  All instances in sync: consistent experience for all users

  ✓ One instance's failures protect all instances
  ✓ Consistent user experience
  ✗ Redis becomes a dependency (Redis failure = cannot read circuit state)
  ✗ Additional latency on every request (must check Redis)
  ✗ More complex implementation
  ✗ Race conditions in state updates need careful handling

  When distributed state is worth it:
  - Very low traffic: one instance may not see enough failures to trip individually
  - Critical downstream services where even one failure per instance matters
  - Regulatory requirement for consistent behaviour
```

```typescript
// Distributed circuit breaker using Redis:
import Redis from 'ioredis';

class DistributedCircuitBreaker {
    private readonly stateKey: string;
    private readonly statsKey: string;

    constructor(
        private readonly name: string,
        private readonly redis: Redis,
        private readonly config: CircuitBreakerConfig
    ) {
        this.stateKey = `circuit:${name}:state`;
        this.statsKey = `circuit:${name}:stats`;
    }

    async canAttempt(): Promise<boolean> {
        const state = await this.redis.get(this.stateKey);

        if (!state || state === 'CLOSED') return true;

        if (state === 'OPEN') {
            const openedAt = parseInt(await this.redis.hget(this.statsKey, 'openedAt') ?? '0');
            if (Date.now() - openedAt >= this.config.resetTimeoutMs) {
                // Transition to HALF_OPEN using SET NX (atomic):
                const transitioned = await this.redis.set(
                    this.stateKey,
                    'HALF_OPEN',
                    'XX',   // Only set if exists
                    'GET'   // Return old value
                );
                return transitioned === 'OPEN';  // Only the one that transitioned gets the probe
            }
            return false;
        }

        if (state === 'HALF_OPEN') {
            // Use Redis atomic increment to limit probe count:
            const probeCount = await this.redis.incr(`circuit:${name}:probes`);
            await this.redis.expire(`circuit:${name}:probes`, 60);
            return probeCount <= this.config.halfOpenProbes;
        }

        return true;
    }

    async recordFailure(): Promise<void> {
        const pipeline = this.redis.pipeline();
        pipeline.hincrby(this.statsKey, 'failures', 1);
        pipeline.expire(this.statsKey, 300);

        const failures = parseInt(await this.redis.hget(this.statsKey, 'failures') ?? '0');

        if (failures >= this.config.failureThreshold) {
            await this.redis.set(this.stateKey, 'OPEN');
            await this.redis.hset(this.statsKey, 'openedAt', Date.now().toString());
        }
        await pipeline.exec();
    }

    async recordSuccess(): Promise<void> {
        const state = await this.redis.get(this.stateKey);
        if (state === 'HALF_OPEN') {
            await this.redis.set(this.stateKey, 'CLOSED');
            await this.redis.del(`circuit:${name}:probes`);
            await this.redis.hdel(this.statsKey, 'failures', 'openedAt');
        } else {
            await this.redis.hdel(this.statsKey, 'failures');
        }
    }
}
```

**Q10. How do you test circuit breaker behaviour — what scenarios must your tests cover?**
A: Circuit breaker logic has subtle edge cases. Tests must verify the state transitions, the fallback behaviour, and the timing-sensitive half-open recovery:

```typescript
// Comprehensive circuit breaker test suite:
import { jest } from '@jest/globals';

describe('CircuitBreaker', () => {
    let breaker: CircuitBreaker;
    let mockFn: jest.Mock;

    beforeEach(() => {
        mockFn = jest.fn();
        breaker = new CircuitBreaker(mockFn, {
            errorThresholdPercentage: 50,
            volumeThreshold: 4,
            timeout: 1000,
            resetTimeout: 100  // Short timeout for testing
        });
    });

    // Test 1: CLOSED state — happy path
    it('passes calls through in CLOSED state', async () => {
        mockFn.mockResolvedValue({ data: 'ok' });
        const result = await breaker.fire('arg1');
        expect(result).toEqual({ data: 'ok' });
        expect(mockFn).toHaveBeenCalledWith('arg1');
        expect(breaker.closed).toBe(true);
    });

    // Test 2: CLOSED → OPEN transition
    it('opens after threshold failures', async () => {
        mockFn.mockRejectedValue(new Error('Service unavailable'));

        // Fire enough requests to exceed threshold:
        for (let i = 0; i < 4; i++) {
            await expect(breaker.fire()).rejects.toThrow();
        }
        // 4 failures, 0 successes = 100% failure rate → should open:
        expect(breaker.opened).toBe(true);
    });

    // Test 3: OPEN state — fast fail
    it('rejects requests immediately when OPEN', async () => {
        // Open the circuit:
        mockFn.mockRejectedValue(new Error('fail'));
        for (let i = 0; i < 4; i++) {
            await expect(breaker.fire()).rejects.toThrow();
        }
        expect(breaker.opened).toBe(true);
        mockFn.mockClear();

        // Fire when OPEN — should NOT call mockFn:
        await expect(breaker.fire()).rejects.toThrow('EOPENBREAKER');
        expect(mockFn).not.toHaveBeenCalled();  // ← The key assertion
    });

    // Test 4: Fallback is called when OPEN
    it('calls fallback instead of throwing when OPEN', async () => {
        const fallback = jest.fn().mockReturnValue({ fallback: true });
        breaker.fallback(fallback);

        mockFn.mockRejectedValue(new Error('fail'));
        for (let i = 0; i < 4; i++) {
            await breaker.fire();  // Fallback handles it
        }

        const result = await breaker.fire();
        expect(result).toEqual({ fallback: true });
        expect(fallback).toHaveBeenCalled();
        expect(mockFn).not.toHaveBeenCalled();
    });

    // Test 5: OPEN → HALF-OPEN transition (time-based)
    it('transitions to HALF-OPEN after reset timeout', async () => {
        mockFn.mockRejectedValue(new Error('fail'));
        for (let i = 0; i < 4; i++) {
            await expect(breaker.fire()).rejects.toThrow();
        }
        expect(breaker.opened).toBe(true);

        // Wait for reset timeout:
        await new Promise(resolve => setTimeout(resolve, 150));  // > 100ms resetTimeout

        expect(breaker.halfOpen).toBe(true);
    });

    // Test 6: HALF-OPEN → CLOSED (successful probe)
    it('closes after successful probe in HALF-OPEN', async () => {
        // Open the circuit:
        mockFn.mockRejectedValue(new Error('fail'));
        for (let i = 0; i < 4; i++) {
            await expect(breaker.fire()).rejects.toThrow();
        }

        // Wait for half-open:
        await new Promise(resolve => setTimeout(resolve, 150));
        expect(breaker.halfOpen).toBe(true);

        // Successful probe:
        mockFn.mockResolvedValue({ data: 'recovered' });
        const result = await breaker.fire();

        expect(result).toEqual({ data: 'recovered' });
        expect(breaker.closed).toBe(true);  // ← Circuit recovered
    });

    // Test 7: HALF-OPEN → OPEN (failed probe)
    it('reopens on failed probe in HALF-OPEN', async () => {
        mockFn.mockRejectedValue(new Error('fail'));
        for (let i = 0; i < 4; i++) {
            await expect(breaker.fire()).rejects.toThrow();
        }

        await new Promise(resolve => setTimeout(resolve, 150));
        expect(breaker.halfOpen).toBe(true);

        // Probe fails:
        await expect(breaker.fire()).rejects.toThrow();
        expect(breaker.opened).toBe(true);  // ← Back to OPEN
    });

    // Test 8: Does not open on below-threshold failures
    it('stays CLOSED if failures are below threshold', async () => {
        mockFn
            .mockResolvedValueOnce('ok')
            .mockRejectedValueOnce(new Error('fail'))
            .mockResolvedValueOnce('ok')
            .mockRejectedValueOnce(new Error('fail'));

        await breaker.fire();  // success
        await expect(breaker.fire()).rejects.toThrow();  // fail
        await breaker.fire();  // success
        await expect(breaker.fire()).rejects.toThrow();  // fail

        // 2/4 = 50% failure rate — exactly at threshold (not above):
        expect(breaker.closed).toBe(true);  // Should NOT have opened
    });

    // Test 9: Timeout counts as failure
    it('counts timeouts as failures', async () => {
        // Mock a slow function (longer than circuit breaker timeout):
        mockFn.mockImplementation(
            () => new Promise(resolve => setTimeout(resolve, 2000))
        );

        const results = await Promise.allSettled([
            breaker.fire(), breaker.fire(), breaker.fire(), breaker.fire()
        ]);

        // All 4 should timeout and count as failures:
        expect(results.every(r => r.status === 'rejected')).toBe(true);
        expect(breaker.opened).toBe(true);
    });
});
```

## Section 9: Scenario-Based Questions

**Q11. "Your order service is making 500 calls/second to the payment service. The payment service starts timing out at 10s. How does this play out with and without a circuit breaker?"**
A:

```
WITHOUT a circuit breaker:

  T=0s: Payment service starts timing out (10s per call)
  T=0s: 500 calls/sec × 10s timeout = 5000 concurrent threads needed
  T=1s: Thread pool (200 threads) exhausted
  T=1s: New requests queue → queue overflows → requests rejected
  T=2s: Order service responding with 503 to all clients
  T=3s: API gateway loses all order service connections
  T=3s: Full cascade: payment outage → order outage → frontend outage

  Recovery without circuit breaker:
  Payment service recovers at T=60s
  But: order service threads are still blocked on in-flight 10s calls
  Must wait for all those calls to time out before threads free
  Order service recovery: T=70s (60s payment recovery + 10s timeout drain)

WITH a circuit breaker:
  Circuit config: threshold=50%, volumeThreshold=10, timeout=3s, resetTimeout=30s

  T=0s:  Payment service starts timing out
  T=3s:  Each call times out (3s circuit breaker timeout)
  T=6s:  10 calls recorded: 10 failures / 10 total = 100% failure rate
  T=6s:  Circuit OPENS
  T=6s:  All new payment calls return fallback immediately (< 1ms)
  T=6s:  Order service threads free immediately — no longer blocked on payment
  T=6s:  Order service continues processing orders (with "payment unavailable" response)
  T=6s:  Payment service load: drops from 500 req/s to ~0 (circuit open)

  Payment recovery:
  T=36s: Circuit enters HALF-OPEN (30s reset timeout after T=6s)
  T=36s: 1 probe request sent to payment service
  T=36s: Payment service responds successfully (it recovered at T=60s... wait)
         Actually: payment not recovered yet → probe fails → circuit stays OPEN
  T=66s: Another HALF-OPEN probe
  T=66s: Payment service recovered → probe succeeds → circuit CLOSES
  T=66s: Full normal operation resumes

  Impact comparison:
  Without CB: 70s total outage, all services affected, manual intervention needed
  With CB:    6s of degraded service (payment unavailable), order service healthy
              66s for payment to recover, no manual intervention needed
```

**Q12. "Design the circuit breaker configuration for a checkout flow that calls: inventory check (fast, non-critical), payment processing (slow, critical), and email notification (unreliable, optional)."**
A:

```typescript
// Three different circuit breakers with very different configurations:

// 1. INVENTORY CHECK — fast, non-critical
// Nature: pure read, fast (< 100ms), stale data acceptable briefly
// Fallback: assume "in stock" and let inventory service handle contention
const inventoryBreaker = new CircuitBreaker(
    (productId: string) => inventoryService.checkStock(productId),
    {
        errorThresholdPercentage: 60,  // Tolerant: allow more failures before opening
        volumeThreshold: 20,           // Need more data points (fast calls = more data)
        timeout: 500,                  // Fail fast on slow responses
        resetTimeout: 10_000,          // Try to recover quickly (10s)
        rollingCountTimeout: 10_000,   // Evaluate over 10s window
    }
);

// Fallback: optimistic — assume in stock (oversell risk is acceptable, handled elsewhere)
inventoryBreaker.fallback(
    (productId: string) => ({ productId, available: true, _fromFallback: true })
);

// 2. PAYMENT PROCESSING — slow, critical
// Nature: write operation, 1-5s, NO data loss acceptable, NO optimistic fallback
const paymentBreaker = new CircuitBreaker(
    (payment: Payment) => paymentService.charge(payment),
    {
        errorThresholdPercentage: 30,  // Strict: open quickly on payment failures
        volumeThreshold: 5,            // Open on just 5 requests (payments are critical)
        timeout: 10_000,               // Payments can take up to 10s (3D Secure)
        resetTimeout: 60_000,          // Wait 60s before probing (payment issues take time)
        rollingCountTimeout: 30_000,   // Evaluate over 30s window
    }
);

// Fallback: FAIL explicitly — never silently drop a payment
paymentBreaker.fallback(
    (payment: Payment) => {
        throw new PaymentServiceUnavailableError(
            'Payment processing is temporarily unavailable. Your card has NOT been charged.'
        );
    }
);

// Additional safety: payment must be idempotent
// Use an idempotency key so retried payments are deduplicated on the payment side:
async function chargeWithIdempotency(payment: Payment): Promise<PaymentResult> {
    const idempotencyKey = `payment-${payment.orderId}-${payment.attempt}`;
    return paymentBreaker.fire({ ...payment, idempotencyKey });
}

// 3. EMAIL NOTIFICATION — unreliable, optional
// Nature: fire-and-forget, async, failure is acceptable (can retry later)
const emailBreaker = new CircuitBreaker(
    (notification: EmailNotification) => emailService.send(notification),
    {
        errorThresholdPercentage: 70,  // Very tolerant: email services are flaky
        volumeThreshold: 10,
        timeout: 5_000,
        resetTimeout: 120_000,         // Wait 2 minutes (email services often have brief outages)
        rollingCountTimeout: 60_000,   // Evaluate over 1 minute
    }
);

// Fallback: queue for later delivery — never block checkout for an email
emailBreaker.fallback(
    async (notification: EmailNotification) => {
        await emailQueue.push(notification);  // Will be retried by queue worker
        logger.warn('Email notification queued due to circuit open', { notification });
    }
);

// The checkout orchestration:
async function checkout(cart: Cart, payment: Payment): Promise<Order> {
    // 1. Inventory: non-blocking, optimistic fallback
    const inventory = await inventoryBreaker.fire(cart.productId);
    if (!inventory.available && !inventory._fromFallback) {
        throw new OutOfStockError();
    }

    // 2. Payment: critical path, explicit failure
    let paymentResult: PaymentResult;
    try {
        paymentResult = await paymentBreaker.fire(payment);
    } catch (err) {
        if (err instanceof PaymentServiceUnavailableError) {
            // Tell the user clearly — do NOT complete the order:
            throw err;
        }
        throw err;
    }

    // 3. Create order (local operation — no circuit breaker needed):
    const order = await orderRepository.create({
        cart,
        paymentResult,
        status: 'CONFIRMED'
    });

    // 4. Email: fire-and-forget, queued fallback
    emailBreaker.fire({
        to: cart.userEmail,
        template: 'order-confirmation',
        orderId: order.id
    }).catch(err => logger.error('Email notification failed', err));
    // NOT awaited — email failure never blocks order completion

    return order;
}
```

|---|---|---|---|
| CLOSED state | Normal operation — calls pass through | Failures counted within a rolling window; transitions to OPEN on threshold | Setting `volumeThreshold` too low — circuit opens on first few requests before there's enough signal |
| OPEN state | Circuit tripped — all calls fail fast | No calls made to downstream service; returns fallback or error in < 1ms | Not implementing a fallback — callers get a cryptic error instead of a graceful degraded response |
| HALF-OPEN state | Recovery probe — limited calls let through | Only probe requests allowed; others still fail fast; one failure → back to OPEN | Letting all traffic through in HALF-OPEN — overwhelms a fragile recovering service |
| Reset timeout | How long to stay OPEN before probing | Start with 30s; use exponential backoff for repeated failures | Too short: circuit flaps open/closed; too long: slow recovery detection |
| Failure threshold | What percentage/count triggers OPEN | Rate-based (%) is more robust than count-based for variable traffic volumes | Using 100% threshold — circuit never opens until every single request fails |
| `volumeThreshold` | Minimum requests before evaluating failure rate | Prevents opening circuit on first 1-2 failures at startup | Setting too high — circuit won't open during genuine low-traffic failure scenarios |
| Fallback | What to return when circuit is OPEN | Cached data, default values, or explicit error — never silently swallow critical writes | Returning stale data for a payment or critical write — users think it succeeded |
| Timeout = failure | Slow calls should count as failures | Set `timeout` less than the downstream service's SLA | Not counting timeouts — a service returning in 30s is just as harmful as returning 500 |
| Per-instance state | Each app instance has its own circuit | Default and usually correct; one instance seeing failures doesn't affect others | Assuming shared state — in a 10-instance deployment, each needs to independently detect failures |
| Idempotency with CB | Retries after HALF-OPEN must be safe | Payment, order creation etc. need idempotency keys to prevent double charges on circuit recovery | Retrying non-idempotent operations after circuit recovery — can charge a card twice |
| What counts as failure | Only server errors (5xx), not client errors (4xx) | 404 Not Found is not a server failure; 503 Service Unavailable is | Counting 400 Bad Request as a circuit failure — circuit trips because callers send bad data |
| Cascading failure | One failing service takes down all dependents | Thread/connection pool exhaustion propagates upstream | Confusing circuit breaker (stops sending) with retry (tries again) — retries make cascades worse |

---

**Tip for interviews:** Five things separate strong candidates on the circuit breaker pattern: (1) explaining **why the pattern exists in terms of thread pool exhaustion** — that without a circuit breaker, a downstream service timing out at 30 seconds causes each caller to hold a thread for 30 seconds, and at 100 req/s that means 3000 threads blocked simultaneously against a pool of maybe 200, so the caller dies even though it's healthy, and that the circuit breaker's fast-fail (< 1ms) prevents this exhaustion from propagating; (2) articulating **the HALF-OPEN state precisely** — that it allows only a limited number of probe requests (not all traffic), that a single probe failure immediately reopens the circuit (not just increments a counter), and that this is intentional because a recovering service may be fragile and sending all traffic during HALF-OPEN could cause it to fail again; (3) knowing **what should and should not count as a failure** — that HTTP 4xx errors (400, 401, 403, 404) are client errors that indicate the caller is doing something wrong, not that the server is down, and should NOT trip the circuit, while 5xx errors, connection timeouts, and slow calls above a threshold SHOULD count, and that misconfiguring this causes circuits to open on client bugs; (4) being able to articulate **three different fallback strategies appropriate for three different service types** — cached/stale data for read services where eventual consistency is acceptable, explicit error surfacing for payment/write operations where silent failures cause data loss, and async queuing for notification services where delay is acceptable but loss is not; and (5) understanding **the `volumeThreshold` parameter** — that without it, a circuit operating at 1 req/min would open after a single failure (100% failure rate on 1 request), and that setting it to 10 means "don't even evaluate the failure rate until at least 10 requests have been made," preventing false trips during low-traffic startup periods or after a circuit has just recovered.
