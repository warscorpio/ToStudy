# Rate Limiting Algorithms — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is rate limiting, and why does it exist?**
A: Rate limiting controls how many requests a client (user, IP, API key, service) can make to a system within a given time window. It exists to protect services from abuse (DoS/DDoS), prevent resource exhaustion, enforce fair usage in multi-tenant systems, and implement business rules (e.g., free-tier API quotas).

**Q2. Where in a system is rate limiting typically enforced?**
A: At multiple layers — most commonly at the API gateway or reverse proxy (Nginx, AWS API Gateway, Kong) before requests reach application servers, and sometimes again at the application layer for finer-grained per-endpoint or per-user logic. Redis is the standard backing store for distributed rate limiters since it supports atomic operations with low latency.

**Q3. What are the four main rate limiting algorithms?**
A: Token Bucket, Leaky Bucket, Fixed Window Counter, and Sliding Window (Log or Rolling Counter). Each has different accuracy, burst handling, and implementation complexity trade-offs.

**Q4. What's the key distinction between "rate limiting" and "throttling"?**
A: Often used interchangeably, but technically rate limiting is about enforcing a maximum request rate (hard reject over the limit), while throttling may slow requests down rather than reject them outright (e.g., queuing excess requests, adding artificial delay). In interviews, clarify which behaviour is required.

**Q5. What data do you need to implement any rate limiter?**
A: At minimum: a key (who is being limited — IP, user ID, API key), a counter or state representing usage, and a time component (window start, token refill timestamp). The storage must support atomic reads and writes — hence Redis `INCR`/`SET`/`EXPIRE` or Lua scripts for distributed systems.

---

## Section 2: Token Bucket

**Q6. How does the Token Bucket algorithm work?**
A: A bucket holds up to `capacity` tokens. Tokens are added at a fixed refill rate (e.g., 10 tokens/second). Each request consumes one token. If the bucket has tokens, the request is allowed and a token is removed. If the bucket is empty, the request is rejected (or queued). The bucket never exceeds its capacity — excess tokens are discarded.

**Q7. What are the key parameters of a Token Bucket?**
A: Two: the **bucket capacity** (maximum burst size) and the **refill rate** (sustained throughput). A capacity of 100 with a refill rate of 10/sec means you can burst 100 requests instantly but sustain only 10/sec over time.

**Q8. What's the biggest advantage of Token Bucket?**
A: It naturally handles burst traffic. A client that was idle can accumulate tokens up to the bucket capacity and spend them in a short burst — which matches real user behaviour (e.g., a user rapidly loading a dashboard). The sustained rate is still bounded by the refill rate.

**Q9. What's the implementation challenge with Token Bucket in a distributed system?**
A: Maintaining accurate token count across multiple nodes. A naive per-node bucket gives each node its own tokens, allowing N× the intended rate with N nodes. The correct approach is a centralised store (Redis) with atomic operations — store the `{last_refill_timestamp, current_tokens}` pair and compute the refill on each request using elapsed time. A Redis Lua script makes the read-compute-write atomic.

**Q10. Which real-world systems use Token Bucket?**
A: AWS API Gateway, Stripe's API rate limiting, and most network QoS (traffic shaping) implementations use token bucket semantics. It's the de facto standard for API rate limiting that needs burst tolerance.

## Section 3: Leaky Bucket

**Q11. How does the Leaky Bucket algorithm work?**
A: Requests enter a queue (the "bucket") and are processed (leak out) at a fixed rate regardless of incoming rate. If the bucket (queue) is full, new requests are dropped. The output is a perfectly smooth, constant stream — it absorbs bursts by queuing them, but drops excess if the queue overflows.

**Q12. How is Leaky Bucket different from Token Bucket?**
A: Token Bucket limits the *average* rate but allows short bursts up to capacity. Leaky Bucket enforces a strictly *constant output rate* — even if requests arrive in bursts, they're processed one-by-one at the fixed leak rate. Token Bucket is more permissive; Leaky Bucket is more rigid.

**Q13. When is Leaky Bucket the right choice?**
A: When you need to smooth out traffic to protect a downstream system that can't handle bursts — for example, calling a third-party API with a strict per-second rate limit (like payment gateways). You queue your outbound requests and drain them at the allowed rate, ensuring you never exceed the vendor's hard limit. It's less about user-facing rate limiting and more about outbound traffic shaping.

**Q14. What's the practical downside of Leaky Bucket for user-facing APIs?**
A: Latency. A burst of legitimate requests gets queued rather than immediately served or rejected — users see slow responses instead of a clean 429. Also, if the queue is bounded, it's hard to distinguish "legitimate burst" from "abuse flooding the queue," so you may slow down real users under load.

**Q15. Can Token Bucket and Leaky Bucket be combined?**
A: Yes — some systems use a two-rate token bucket (like IETF RFC 2698) or a combination where requests must pass both a burst check (token bucket) and a sustained-rate queue (leaky bucket). In practice, most API rate limiters choose one or the other based on whether burst tolerance is desired.

## Section 4: Fixed Window Counter

**Q16. How does Fixed Window Counter work?**
A: Divide time into fixed-size windows (e.g., each minute from :00 to :59). For each window, maintain a counter per key. Each request increments the counter; if it exceeds the limit, the request is rejected. The counter resets at the start of each new window.

**Q17. What's the key flaw in Fixed Window Counter?**
A: The "boundary burst" problem. A client can send the full limit at the end of one window (say, 100 requests from :55 to :59) and the full limit again at the start of the next (:00 to :05) — effectively doubling the allowed rate in a 10-second span. The algorithm only sees each window in isolation, not the actual request density around the boundary.

**Q18. Why do teams still use Fixed Window Counter despite this flaw?**
A: Simplicity and performance. It's trivially implemented with a Redis `INCR` + `EXPIRE`: one atomic increment, one expiry set. It uses O(1) memory per key and is extremely fast. For many use cases (especially where the limit is generous relative to the burst concern), the boundary effect is an acceptable trade-off. It's a good "start here" approach.

**Q19. How do you implement Fixed Window Counter in Redis?**
A:
```
key = "rate:{user_id}:{current_minute}"
count = INCR key
if count == 1:
    EXPIRE key 60   # set TTL only on first request to avoid overwriting
if count > limit:
    reject request
```
The key encodes the window (current minute/hour/day), so it naturally resets when the window rolls over and the key expires.

**Q20. What is the memory footprint of Fixed Window Counter?**
A: O(1) per key per window — just one integer counter with a TTL. Compare this to Sliding Window Log, which stores every request timestamp.

## Section 5: Sliding Window

**Q21. What problem does Sliding Window solve that Fixed Window doesn't?**
A: It eliminates the boundary burst problem. Instead of resetting at hard window boundaries, it looks at actual request counts in the rolling window ending *right now* — so the limit is enforced continuously, not per discrete epoch.

**Q22. What are the two main implementations of Sliding Window?**
A:
- **Sliding Window Log**: Store a timestamp for every request in a sorted set. On each new request, remove timestamps older than `now - window_size` and count what remains. Accurate, but memory-intensive — stores every request's timestamp.
- **Sliding Window Counter (hybrid)**: A weighted combination of the previous fixed window's count and the current fixed window's count, prorated by how much of the current window has elapsed. Memory-efficient (still O(1)), approximates a true sliding window with slight inaccuracy.

**Q23. Walk through the Sliding Window Counter approximation.**
A: If the window is 60s and we're 25% into the current window:
```
estimated_count = (previous_window_count × 0.75) + current_window_count
```
The assumption is that requests in the previous window were uniformly distributed, so 75% of them fall within our 60s look-back. It's an approximation — real distributions are rarely uniform — but in practice the error is small and acceptable for most rate limiting purposes.

**Q24. How do you implement Sliding Window Log in Redis?**
A: Use a Redis sorted set, with the score being the Unix timestamp of each request:
```
key = "rate_log:{user_id}"
now = current_timestamp_ms
window_start = now - window_ms

ZREMRANGEBYSCORE key 0 window_start   # remove old entries
count = ZCARD key
if count >= limit:
    reject request
else:
    ZADD key now now                   # add current request
    EXPIRE key window_ms
```
Wrap in a Lua script for atomicity. Memory cost: O(requests in window) per key.

**Q25. What's the memory cost of Sliding Window Log at scale?**
A: It stores every request timestamp in the window — if a user is allowed 10,000 requests/hour, you're storing up to 10,000 entries per user. With millions of users, this becomes significant. Sliding Window Counter avoids this by keeping only two counters per key, making it far more practical at scale.

## Section 6: Trade-offs & Decision-Making

**Q26. How do you choose between these algorithms in practice?**
A:
- **Token Bucket** — default choice for user-facing API rate limiting where burst tolerance is acceptable. Good balance of accuracy and performance.
- **Leaky Bucket** — when you need smooth, constant outbound throughput to protect a downstream system (e.g., calling a vendor API). Not ideal for user-facing rejection behaviour.
- **Fixed Window** — when simplicity and speed matter more than boundary precision. Good for internal services, coarse quotas, or as a first iteration.
- **Sliding Window Counter** — when you need more accurate enforcement than Fixed Window with comparable memory cost. The production sweet spot for most high-scale API gateways.
- **Sliding Window Log** — when you need exact accuracy and can afford the memory (low request volume with strict precision requirements, e.g., financial transaction limits).

**Q27. Can you layer multiple rate limiters?**
A: Yes — commonly done in real systems. Example: a per-second token bucket to handle burst control + a per-day fixed window counter for quota enforcement. AWS API Gateway and most enterprise API platforms expose both a burst limit and a steady-state rate limit, which is exactly a token bucket layered with a sustained quota.

**Q28. What happens in a distributed setup where multiple nodes share a rate limiter?**
A: Each node must read/write from the same centralised state (Redis). Local in-memory rate limiters per node will allow N× the intended rate with N nodes. The trade-off is Redis latency added to every request path — typically 0.5–2ms, which is acceptable for most APIs but may be too expensive for ultra-low-latency paths.

**Q29. How would you handle rate limit state if Redis goes down?**
A: Strategy depends on the use case:
- **Fail open** — allow requests if the limiter is unavailable (prioritises availability over protection).
- **Fail closed** — reject requests if the limiter is unavailable (prioritises protection over availability, risky for user experience).
- **Local fallback** — each node falls back to an in-memory limiter with conservative limits when Redis is unavailable.
Most production systems fail open with alerting, since taking the site down because the rate limiter is unavailable is usually a worse outcome than temporarily allowing extra traffic.

**Q30. What HTTP status code and headers should a rate-limited response return?**
A: Status `429 Too Many Requests`. Standard headers:
- `Retry-After: <seconds>` — when the client can retry
- `X-RateLimit-Limit: <max>` — the configured limit
- `X-RateLimit-Remaining: <n>` — requests remaining in current window
- `X-RateLimit-Reset: <epoch>` — when the window resets (for fixed/token bucket)

These allow well-behaved clients to back off and retry correctly instead of hammering the server harder.

## Section 7: Scenario / System Design Questions

**Q31. "Design a rate limiter for a public REST API that allows 1,000 req/min per API key with burst tolerance."**
A: Use a Token Bucket backed by Redis. Each API key maps to a Redis hash storing `{tokens, last_refill_ts}`. On each request, compute tokens earned since last refill (`elapsed_seconds × refill_rate`), cap at bucket capacity (1,000), subtract 1 for the current request, store back, and reject if tokens < 0. Wrap the read-compute-write in a Lua script for atomicity. Add `X-RateLimit-*` headers from the result. Deploy the check at the API gateway layer (Kong/Nginx module) to avoid hitting app servers.

**Q32. "Your payment gateway vendor allows 100 calls/min. Your service sends 500 calls/min during peak. How do you handle this?"**
A: A Leaky Bucket (queue-based) on the outbound call path. Enqueue all outbound payment requests; a worker drains the queue at ≤100/min using a token bucket against the vendor's limit. Requests that wait too long are failed fast with a meaningful error. Add a circuit breaker so if the vendor starts returning 429s, you back off immediately rather than exhausting retries. This is a classic use case for Leaky Bucket on egress rather than ingress.

**Q33. "Fixed Window is giving users a bad experience around minute boundaries — they hit the limit in 2 seconds at the start of each minute. What do you do?"**
A: This is the classic boundary burst problem in reverse — users are legitimately bursting at window resets. Move to Sliding Window Counter: same Redis memory footprint, but the weighted approximation prevents the hard reset spike. Alternatively, switch to Token Bucket — users who were idle accumulate tokens, but the sustained rate is still enforced, eliminating the "reset race."

**Q34. "How would you rate-limit at multiple granularities — per second AND per day?"**
A: Run two independent rate limiters in series on each request, each with its own Redis key and TTL:
- Key 1: `rate:{user}:{epoch_second}` — per-second limit (Fixed Window is fine at 1s granularity)
- Key 2: `rate:{user}:{epoch_day}` — per-day quota (Fixed Window or Sliding Window Counter)

Reject if either check fails, and return headers reflecting the binding limit. This is how most production APIs implement "10 req/sec, 100,000 req/day" semantics.

## Quick Comparison Table

| Algorithm              | Burst Handling      | Memory Cost         | Accuracy            | Complexity          | Best For                              |
|------------------------|---------------------|---------------------|---------------------|---------------------|---------------------------------------|
| Token Bucket           | ✅ Yes, controlled   | O(1) per key        | High                | Medium              | User-facing APIs, burst-tolerant      |
| Leaky Bucket           | 🟡 Queued, not burst  | O(queue size)       | High (output rate)  | Medium              | Outbound traffic shaping              |
| Fixed Window Counter   | ❌ Boundary bursts   | O(1) per key        | Low (at boundaries) | Low                 | Coarse quotas, internal services      |
| Sliding Window Log     | ✅ Accurate          | O(requests/window)  | Exact               | High                | Low-volume, strict precision required |
| Sliding Window Counter | 🟡 Approximate       | O(1) per key        | High (approximate)  | Medium              | High-scale APIs, production default   |

---

**Tip for the interview:** At the 5 YOE level, interviewers want to see that you've actually *built* or *debugged* a rate limiter, not just recited the algorithms. Be ready to talk about Redis atomicity (why Lua scripts or `MULTI/EXEC`), what happens when the store is unavailable, how you surfaced 429s with proper headers, and a time where you tuned limits based on real traffic patterns. Knowing when *not* to implement a custom rate limiter (and use an off-the-shelf API gateway feature instead) is also a strong signal.
