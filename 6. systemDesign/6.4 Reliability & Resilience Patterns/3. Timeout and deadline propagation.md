# Timeout & Deadline Propagation — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a timeout in the context of distributed systems?**
A: A timeout is a maximum duration a caller is willing to wait for a response before giving up and treating the operation as failed. It prevents a caller from blocking indefinitely when a downstream service is slow or unreachable — without timeouts, a single slow dependency can exhaust all threads/connections and cascade into a full outage.

**Q2. What is a deadline, and how does it differ from a timeout?**
A: A deadline is an absolute point in time by which an operation must complete (e.g., "this entire request must finish by T+500ms from when it started"). A timeout is relative and per-hop (e.g., "wait up to 200ms for *this* call"). The critical difference: a deadline is propagated across the entire call chain and shrinks as the request passes through services — a timeout restarts fresh at each hop, so downstream services have no idea how much budget the top-level caller has left.

**Q3. Why does propagating timeouts naively (per-hop) cause problems?**
A: Consider a chain: Client → Service A (timeout: 5s) → Service B (timeout: 5s) → DB (timeout: 5s). If the DB is slow, Service B waits 5s, then A waits another 5s for B — the total wait to the client is up to 15s, far beyond any reasonable user-facing SLA. Each hop resets the clock, so total latency is the *sum* of all individual timeouts in the worst case, not the max.

**Q4. What is "deadline propagation" and why is it a better pattern?**
A: Deadline propagation passes the original absolute deadline (or remaining budget) from the top-level caller down through every service in the chain. Each downstream service computes its remaining time (`deadline - now`) before doing any work. If the budget is already exhausted before a call starts, the service can reject the work immediately rather than doing expensive processing that will be discarded anyway.

**Q5. What is a "budget" in the context of deadline propagation?**
A: The remaining time available for an operation at any point in the call chain. Budget = `deadline - current_time`. Each service should check the budget before making further downstream calls and subtract its own expected processing time before passing the budget on. If the budget is near zero, it's better to fail fast than to proceed.

**Q6. What happens when a deadline expires mid-flight?**
A: The initiating caller stops waiting and returns an error (typically `DEADLINE_EXCEEDED`). Meanwhile, downstream services may still be doing work — computing, writing to databases, holding locks — without anyone waiting for their result. This is called "orphaned work" or "abandoned work" and is one of the most important failure modes to design around.

## Section 2: Timeout Configuration & Tuning

**Q7. How do you pick a timeout value for a service call?**
A: Base it on empirical data, not guesses. Look at your p99 or p999 latency histogram for that dependency. A common heuristic: set the timeout somewhere between p99 and p999 so you tolerate normal tail latency but cut off truly stuck requests. Setting it too low creates false failures on legitimate slow-but-correct requests; too high and you hold resources for too long under degradation.

**Q8. What is the difference between a connection timeout and a read/request timeout?**
A:
- **Connection timeout** — how long to wait to *establish* a TCP connection to a server. Typically shorter (e.g., 1–5s), since a missing or overloaded host usually fails fast.
- **Read/request timeout** — how long to wait for a response *after* the connection is established. This should reflect expected processing time (can range from milliseconds to tens of seconds depending on the operation).
- Some clients also expose a **write timeout** — time to send the request body — useful for large payloads over slow networks.

**Q9. Should every service call in your code have an explicit timeout set?**
A: Yes, always. Never rely on a library or framework's default — defaults are often extremely high (or even infinite in some HTTP clients) and will silently allow calls to block forever. Every external call (HTTP, DB query, cache, queue, gRPC) should have an explicitly reasoned timeout.

**Q10. What is "timeout budget slicing" and when is it used?**
A: When a service fans out to multiple parallel downstream calls, it divides its remaining budget among them (or gives all of them the same remaining budget since they run in parallel). For sequential calls, it subtracts elapsed time before each hop. The goal is to ensure no single downstream call can consume more than is available in the top-level budget.

**Q11. How should you handle timeout values in configuration vs. code?**
A: Externalize them — store timeout values in configuration (environment variables, config maps, feature flags) rather than hardcoding them. This lets you tune timeouts without a code deploy, which is critical during incidents when you need to quickly tighten or relax a timeout to stabilize the system.

**Q12. What is a "retry budget" and how does it interact with timeouts?**
A: A retry budget is a limit on how many retries a service will attempt within a time window, to prevent retry storms. It interacts with timeouts because if a timeout is too low, you'll get many false failures that trigger retries, amplifying load on an already struggling dependency. Good practice: treat timeouts and retry policies as a unified system — tighten one, loosen the other accordingly.

## Section 3: Deadline Propagation in Distributed Systems

**Q13. How is a deadline typically transmitted across service boundaries?**
A: Via request metadata / headers. Common patterns:
- **gRPC** — propagates deadlines natively in the protocol header; each service reads the deadline and the framework enforces it.
- **HTTP** — commonly a custom header like `X-Request-Deadline` (absolute timestamp) or `X-Request-Timeout` (remaining ms); you must propagate it manually or via middleware.
- **Message queues** — embed a `ttl` or `expiry` field in the message envelope; consumers check it before processing.
- **Distributed tracing context (W3C TraceContext, Baggage)** — some teams piggyback deadline info in baggage headers alongside trace IDs.

**Q14. How does gRPC handle deadlines natively?**
A: gRPC treats deadlines as a first-class concept. When a client sets a deadline on a call, the framework encodes it in the wire protocol. On the server side, the context object has `ctx.Err()` / `ctx.Done()` that signal expiry automatically. If the server tries to initiate a downstream gRPC call, it can pass the same context and the framework will automatically compute the remaining deadline and encode it into the outgoing header.

**Q15. How do you propagate deadlines in a system using plain HTTP?**
A: Manually, usually via middleware/interceptors:
1. At the entry point (API gateway or top-level service), record the start time and compute the absolute deadline from the incoming timeout header or your SLA.
2. Attach the deadline to a request-scoped context object.
3. On every outgoing HTTP call, compute remaining time (`deadline - now`) and set it as a header (e.g., `X-Request-Timeout: 340`) or as the HTTP client's request timeout.
4. Downstream services read this header, re-attach it to their context, and repeat.

**Q16. What should a service do when it receives a request with an already-expired deadline?**
A: Reject it immediately and return a "deadline exceeded" error without doing any work. This is a critical optimization — there's no point doing expensive computation, acquiring locks, or writing to a database if the caller has already timed out and will discard the result. It also protects downstream services from the ripple of orphaned calls.

**Q17. How do deadlines interact with asynchronous workflows (e.g., jobs kicked off via a queue)?**
A: Async workflows break the synchronous request chain, so the original HTTP deadline doesn't apply directly. Instead, embed a `message_expiry` or `process_by` timestamp in the message payload. Workers check this before processing: if the job has expired (e.g., the user's session is gone, the window for action has passed), they discard it rather than doing the work. This prevents stale work from clogging queues during backlogs.

**Q18. What is "context cancellation" and how does it relate to deadlines?**
A: Context cancellation (common in Go, but also in async/task-based frameworks) is the mechanism by which a deadline expiry propagates through the call tree *within* a service. When a deadline fires, the context is cancelled, which signals goroutines/tasks doing work on behalf of that request to stop. Properly written code checks `ctx.Done()` at yield points (before DB calls, between loop iterations) and exits early rather than continuing pointless work.

## Section 4: Failure Modes & Anti-patterns

**Q19. What is a "cascading timeout failure" and how does it happen?**
A: When a slow downstream service causes callers to hold threads/connections open until their timeout fires, exhausting the caller's connection pool or thread pool, which then causes *that* service to be slow for its callers — and so on up the chain. The slowness cascades upward even though the root cause is one dependency. Proper timeouts, combined with circuit breakers, limit how long each tier holds resources.

**Q20. What is the "thundering herd" problem in the context of timeouts?**
A: When many callers hit a timeout simultaneously (e.g., because a dependency went slow and all requests started at roughly the same time), they all fail at once, potentially all retrying at the same time, creating a spike of traffic that overwhelms the recovering dependency. Mitigations: jittered retries, circuit breakers that open before the timeout fires, and exponential backoff.

**Q21. What is "timeout thrashing" and what causes it?**
A: When a timeout is set just below the normal p99 latency, so a significant fraction of legitimate requests always time out, causing constant retries and elevated error rates. This is usually caused by tuning timeouts too aggressively (too short) without looking at the actual latency distribution. Fix: measure before cutting.

**Q22. Why is "do nothing on timeout" an anti-pattern for downstream calls?**
A: If a service initiates a downstream call and doesn't cancel it when the deadline fires, the downstream service continues doing work, holding connections, DB transactions, locks, and CPU — all of which are wasted because the caller has already moved on. Over time this leads to resource exhaustion on downstream services. Always propagate cancellation so downstream work stops when the caller gives up.

**Q23. What is a "missing timeout" bug and why is it insidious?**
A: A call made without any timeout will block forever if the downstream is hung. Under normal conditions this bug is invisible — calls return quickly. But during a partial failure (a service is slow but not dead), all threads/connections pile up on the blocking calls, eventually exhausting the pool and causing the calling service to appear fully down even though only one dependency is degraded. These bugs often only surface in production under failure conditions and are hard to reproduce in tests.

**Q24. What's wrong with using the same timeout value everywhere in your system?**
A: Different operations have different latency profiles. A Redis cache hit should resolve in <5ms; a complex analytical DB query might legitimately take 10s. Using a single global timeout means you're either too permissive for fast operations (holding resources too long under failures) or too strict for slow ones (falsely failing legitimate operations). Each call site needs a timeout appropriate to its expected latency.

## Section 5: Trade-offs & Decision-Making

**Q25. When should you use deadlines vs. per-hop timeouts?**
A:
- **Deadlines** are strongly preferred in any multi-tier system where you have an end-to-end latency SLA (user-facing APIs, real-time pipelines). They're the only way to guarantee total request duration across a chain.
- **Per-hop timeouts alone** are acceptable for simple two-tier systems (client → single service → DB) where the chain is short and the total latency is easy to reason about.
- In practice, use both: propagate an end-to-end deadline, but also set per-hop timeouts as a safety net so no single call consumes the entire remaining budget.

**Q26. How do you decide between failing fast vs. waiting longer during a dependency slowdown?**
A: It depends on whether the work is idempotent/retriable and what the user impact is. For user-facing requests, fail fast (tight timeouts + clear error messages) — a quick error is better than a 30s hang. For background/batch jobs where losing the work is costly, you might use longer timeouts with retries. The key question: what's worse — a visible error now, or wasted resources and a slower error later?

**Q27. How do circuit breakers complement deadline propagation?**
A: Circuit breakers "open" after a threshold of failures, short-circuiting calls to a failing dependency without even waiting for a timeout. This means:
- **Timeouts/deadlines** handle slow-but-alive dependencies (they eventually fire).
- **Circuit breakers** handle known-dead dependencies (they fail immediately, saving timeout wait time and protecting the dependency from being hammered while it recovers).
Together they form a defensive layer: the circuit breaker is the fast path, the timeout is the last-resort backstop.

**Q28. What's the trade-off between a tight and a loose timeout for a non-idempotent operation (e.g., a payment)?**
A: Tight timeout: you get a quick error response but don't know if the operation completed on the downstream side before the timeout. If you retry, you risk double-charging. Loose timeout: you hold resources longer and the UX suffers, but you get a cleaner success/failure signal. The right answer: design the operation to be idempotent (use an idempotency key), so retrying is safe regardless — and then you can afford a tighter timeout.

## Section 6: Scenario / System Design Style Questions

**Q29. "Your checkout service has a p99 latency of 800ms, but users complain about 30-second hangs during peak load. What do you investigate first?"**
A: Classic missing-timeout signature. Start by checking whether all downstream calls (payment gateway, inventory service, DB queries, external fraud checks) have explicit timeouts set. One call without a timeout blocking on a slow service under load will manifest exactly as described — most requests finish fast, but a fraction hang indefinitely. Audit every outbound call, add timeouts, emit latency metrics per call site, and check for thread/connection pool exhaustion as the secondary effect.

**Q30. "Design deadline propagation for a system: Client → API Gateway → Service A → Service B → DB. Walk through the full flow."**
A:
1. **Client** sets a `Request-Timeout: 1000ms` header on its HTTP request (or the API gateway enforces a max).
2. **API Gateway** records `deadline = now + 1000ms`, attaches it to the internal request context, and passes `X-Request-Deadline: <epoch_ms>` to Service A.
3. **Service A** reads the header, attaches to context, checks `budget = deadline - now`. If budget ≤ 0, return `504` immediately. Otherwise, does its work and before calling Service B, sets its HTTP client timeout to `min(remaining_budget - own_overhead, max_allowed)`, and forwards `X-Request-Deadline`.
4. **Service B** repeats: checks budget, issues DB query with `SET statement_timeout = <remaining_ms>`, returns result or fails fast.
5. If any hop fires a timeout, it returns `503/504` and propagates the cancellation upward. Every tier logs the remaining budget at entry so you can trace where budget was consumed.

**Q31. "A service is occasionally returning errors with cause `DEADLINE_EXCEEDED` even when your own code has a 5-second timeout. How do you debug it?"**
A: The deadline exceeded isn't coming from your code — it's coming from *above* you. A caller higher in the chain has a shorter deadline that's expiring before your 5s timeout fires. Steps: (1) check incoming request headers for a deadline/timeout value, (2) log the incoming deadline vs. your own timeout at service entry, (3) check if the `DEADLINE_EXCEEDED` error comes from the gRPC framework (it will) before your own timeout fires. Fix: either negotiate a longer SLA with the upstream caller or reduce your own processing time to fit within the tighter budget.

**Q32. "How would you add deadline propagation to an existing microservices system that currently uses no propagation?"**
A: Incrementally:
1. **Add tracing infrastructure first** (if not present) — you'll need request IDs and context passing already working.
2. **Add a timeout header** to your API gateway layer with a system-wide max (e.g., 2s for user-facing APIs).
3. **Add middleware** to each service that reads the header, attaches to context, and logs remaining budget at entry.
4. **Enforce outbound timeouts** on every downstream call using the remaining budget.
5. **Add metrics** — track `remaining_budget_at_entry` as a histogram to see which services are receiving near-zero budgets (they're deep in slow call chains).
6. **Add fast-fail** logic: reject requests where budget ≤ some floor (e.g., 50ms) at each service entry.
Do this service by service; partial propagation is still better than none.

**Q33. "A background job processor is slow to drain its queue during peak hours. How do timeouts and deadlines apply here?"**
A: Messages in the queue should carry a `process_by` timestamp (set by the producer based on business requirements). Workers check this before processing: if `now > process_by`, discard the message (or dead-letter it) rather than doing the work — the result would be stale anyway. Additionally, set timeouts on each downstream call the worker makes (DB writes, API calls) so a single slow call doesn't block the worker thread for an arbitrarily long time. This prevents queue backlog from compounding: stale messages get discarded cheaply, and workers don't pile up on stuck calls.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                    | Per-hop Timeout                                        | End-to-end Deadline                                      |
|---                        |---                                                     |---                                                       |
| Clock model               | Relative, resets at each service                       | Absolute, shared across the entire call chain            |
| Total latency bound       | Sum of all hop timeouts (worst case)                   | Fixed at the original deadline, regardless of chain depth|
| Coordination needed       | None — each service acts independently                 | Must propagate context across every service boundary     |
| Orphaned work prevention  | Partial — downstream may still run after caller times out | Strong — remaining budget tells each tier when to bail out early |
| Adoption complexity       | Low — just set a timeout per client call               | Higher — requires context propagation infrastructure     |
| Works natively in gRPC    | Partially                                              | Yes — first-class protocol support                       |
| Best for                  | Simple 2-tier systems, easy wins                       | Multi-tier, user-facing systems with strict SLAs         |
| Risk if misconfigured     | Latency additive blow-up in long chains                | Premature rejection if deadline is set too tight at entry|

## Key Concepts Cheat Sheet

| Term                    | One-line definition                                                                 |
|---                      |---                                                                                  |
| Timeout                 | Max wait time per hop, relative, resets at each service                             |
| Deadline                | Absolute expiry time propagated across the entire call chain                        |
| Budget                  | `deadline - now` — remaining time at a given point in the chain                    |
| Context cancellation    | Mechanism by which deadline expiry stops in-progress work within a service          |
| Orphaned work           | Processing that continues after the caller has already given up                     |
| Cascading failure       | Slowness propagating upward as held threads/connections exhaust upstream pools      |
| Circuit breaker         | Fails calls immediately to a known-bad dependency, bypassing timeout wait entirely  |
| Thundering herd         | Mass simultaneous retries after a synchronized timeout burst                        |
| Idempotency key         | Token that makes retrying a non-idempotent operation safe                           |

**Tip for the interview:** At 5 YOE level, interviewers expect you to connect timeouts and deadlines to real system behaviors — thread pool exhaustion, retry storms, cascading failures. Go beyond "set a timeout on every call" and show you understand *why*: what happens to threads, connections, and downstream services when you don't. Bonus points for mentioning gRPC's native deadline support, context propagation patterns, and how circuit breakers and deadlines complement each other.
