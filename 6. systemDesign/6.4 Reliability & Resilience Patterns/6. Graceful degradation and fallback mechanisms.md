# Graceful Degradation & Fallback Mechanisms — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is graceful degradation?**
A: A design philosophy where a system continues to function — at reduced capability — when part of it fails, rather than failing entirely. The goal is to preserve the most critical user-facing functionality and shed non-essential features under stress or partial outage. The system "degrades gracefully" rather than collapsing catastrophically.

**Q2. What is a fallback mechanism?**
A: A predefined alternative behavior that kicks in when the primary path fails. It's the concrete implementation of graceful degradation — e.g., returning cached data when a live API call fails, showing a default UI when a personalization service is down, or queuing a write when the database is temporarily unreachable.

**Q3. What's the difference between graceful degradation and high availability?**
A: They're complementary but distinct:
- **High availability** — keeps the system fully functional through redundancy (failover, replication, multi-AZ). The goal is *no degradation at all* — users shouldn't notice a failure.
- **Graceful degradation** — accepts that some failures can't be masked entirely and designs explicit reduced-functionality modes. It's your plan for when HA isn't enough — when an entire dependency is down and you need to still serve something useful.

**Q4. What's the difference between fail-fast and graceful degradation? Are they opposites?**
A: Not opposites — they operate at different layers:
- **Fail-fast** — reject a request immediately when a precondition can't be met (e.g., bulkhead full, circuit open), rather than waiting and timing out. Fail-fast protects *system resources*.
- **Graceful degradation** — determines what to *return to the user* after a fail-fast. Instead of propagating an error to the user, you return a fallback. Fail-fast triggers the degradation; graceful degradation is what you do *after* triggering it.

**Q5. What are the core categories of fallback strategies?**
A:
- **Cached response** — return the last known-good value from cache (Redis, local in-memory).
- **Default/static response** — return a hardcoded safe default (empty list, zero, a placeholder).
- **Stub/degraded response** — return a partial result from what succeeded, omitting the failed part.
- **Async retry / queue** — accept the request, enqueue it for later processing, return an optimistic acknowledgement.
- **Redirect to alternate** — route to a secondary system, read replica, or backup service.
- **Feature flag off** — disable the failing feature entirely for all users until it recovers.

## Section 2: Design Patterns

**Q6. How does the Cache-Aside pattern support graceful degradation?**
A: In the normal path, the app checks cache first and falls back to the DB on a miss. Under graceful degradation, this inverts: if the *DB is down*, the app checks cache first and serves stale data if available, rather than erroring. The same cache layer that was an optimization becomes a resilience layer. The key design requirement: cache entries must have a TTL long enough to ride out typical outage durations for the dependencies they back.

**Q7. What is a stale-while-revalidate strategy and when does it help?**
A: A caching policy where the cache serves a stale (expired) entry immediately while asynchronously fetching a fresh value in the background. Under normal conditions, users always get fast responses with data that's at most one refresh cycle old. Under degradation (origin is down), the cache continues serving the last good value indefinitely, rather than returning an error. Useful for read-heavy data that's tolerable to be slightly stale (product catalog, exchange rates, feature flags).

**Q8. What is the "feature shedding" approach to graceful degradation?**
A: Classifying your features by criticality and shedding non-critical ones first when the system is under stress. Example tiers:
- **Tier 0 (must work):** authentication, core transaction processing, checkout.
- **Tier 1 (important):** order history, account details.
- **Tier 2 (enhancing):** personalized recommendations, social proof widgets.
- **Tier 3 (nice-to-have):** A/B test variants, real-time analytics overlays.

When load spikes or a dependency fails, you programmatically disable Tier 2/3 features first (via feature flags or circuit breakers with empty fallbacks) to protect Tier 0/1 capacity.

**Q9. How do feature flags enable graceful degradation at runtime?**
A: Feature flags decouple deployment from activation. When a service backing a feature becomes unhealthy, an operator (or automated system) flips a flag to disable that feature — all users get the fallback path immediately, without a code deploy or restart. This is faster and safer than a hotfix. LaunchDarkly, Unleash, and similar tools support targeting (disable only for users who would hit the failing backend), staged rollouts, and circuit-breaker-triggered automatic flag flips.

**Q10. What is a "static fallback" and when is it appropriate?**
A: Returning a hardcoded, pre-built response when the real data source is unavailable. Examples:
- A CDN-hosted static HTML page served when the app servers are completely down ("We're experiencing an issue, try again shortly").
- An empty product recommendations list instead of an error when the recommendations service is down.
- A default credit limit when the credit-scoring service is unreachable.

Appropriate when: the feature is non-critical, any data is better than an error, and you have no cache to fall back on. Not appropriate when: stale or default data could cause financial harm or incorrect user decisions (e.g., a default "approved" for a loan when the scoring service is down).

## Section 3: Implementation

**Q11. How do you implement a fallback with Resilience4j?**
A: Resilience4j's `CircuitBreaker`, `Bulkhead`, and `TimeLimiter` all support `decorateSupplier` / `executeSupplier` patterns where you chain a fallback function:

```java
CircuitBreaker cb = CircuitBreaker.ofDefaults("recommendations");

String result = Decorators.ofSupplier(() -> recommendationService.get(userId))
    .withCircuitBreaker(cb)
    .withFallback(
        List.of(CallNotPermittedException.class, TimeoutException.class),
        ex -> Collections.emptyList() // fallback: empty list
    )
    .get();
```

The fallback lambda receives the exception so you can differentiate — e.g., return cached data for a timeout but an empty list for a circuit-open.

**Q12. What's the pattern for async fallback with a message queue?**
A: "Accept and queue" — you accept the write request, persist it to a durable queue (Kafka, SQS, RabbitMQ), and return a 202 Accepted to the caller. A background consumer processes the queue when the downstream recovers. This decouples the caller from the dependency's availability. Key requirements: the queue must be durable (not in-memory), the consumer must be idempotent (handle duplicate processing on retry), and the caller must be informed they're getting eventual, not immediate, consistency.

**Q13. How do you implement graceful degradation for a search feature backed by Elasticsearch?**
A: Layered fallbacks in order of preference:
1. Try Elasticsearch — return results if it responds within timeout.
2. On timeout/error, try a Redis cache of recent popular search results for the same query.
3. On cache miss, fall back to a basic SQL LIKE query on the primary DB (slower, less relevant, but functional).
4. If all fail, return an empty result set with a UI message ("Search is temporarily limited").

Each layer is tried only if the previous one fails. The SQL fallback deliberately has lower throughput limits to prevent it from overwhelming the DB under Elasticsearch outage.

**Q14. How do you handle a fallback that itself can fail?**
A: Fallbacks must be simpler and more reliable than the primary path — otherwise you've just added complexity with no resilience gain. Design principles:
- Fallbacks should have no or minimal external dependencies (prefer in-memory cache over a secondary API call).
- If the fallback is itself a remote call, it needs its own timeout and circuit breaker.
- Avoid cascading fallbacks more than 2 levels deep — the complexity becomes untestable.
- Prefer static or cached fallbacks over "try another service" fallbacks when possible.

**Q15. How do you propagate degradation state to the frontend?**
A: Via response metadata, not just content:
- Add a `X-Degraded: true` response header so the client knows the response is a fallback.
- Include a `degraded` field in the JSON payload body (e.g., `{ "recommendations": [], "meta": { "degraded": true, "reason": "recommendations_service_unavailable" }`).
- The frontend can then conditionally hide the recommendations section entirely rather than rendering an empty list — better UX than a mysteriously empty widget.

## Section 4: Data Consistency & Correctness

**Q16. What are the risks of serving stale cached data as a fallback?**
A: Depends heavily on the domain:
- **Low risk:** product descriptions, blog content, exchange rates (bounded staleness is acceptable).
- **Medium risk:** inventory counts (user might add an out-of-stock item to cart).
- **High risk:** account balances, credit limits, fraud signals (stale data can cause financial harm or security bypass).

The design principle: before choosing a stale-cache fallback, explicitly model the worst-case consequence of serving data that's N minutes/hours old. If it can cause financial loss, regulatory violation, or a security issue — that fallback is not acceptable; you need to fail visibly instead.

**Q17. How do you prevent a fallback from masking data corruption?**
A: Two techniques:
- **Versioning/checksums in cache** — store a hash or schema version alongside cached data. On read, validate it. If it fails validation, treat it as a cache miss (don't serve corrupt data silently).
- **Fallback observability** — emit a metric every time the fallback is invoked, tagged by reason. If the fallback fires continuously for hours without operators noticing, that's a silent data outage. Alerting on fallback rate ensures the root cause gets fixed, not just tolerated.

**Q18. What is "read-your-own-writes" consistency and how does it interact with fallbacks?**
A: Read-your-own-writes (RYOW) guarantees that after a user writes data, their next read reflects that write — even in an eventually consistent system. This breaks under stale cache fallbacks: a user updates their profile, the write goes to the primary DB, but their next read hits a replica or stale cache that doesn't have the update yet. Solutions:
- After a write, invalidate or update the user's cache entry immediately.
- For critical post-write reads, route to the primary DB bypassing cache (identified by a session flag or sticky routing).
- Scope RYOW to the session only (not all replicas) — smaller consistency surface.

## Section 5: Observability & Operations

**Q19. What operational signals tell you that graceful degradation is working correctly?**
A: A healthy degradation event looks like:
- Fallback invocation rate spikes and stays elevated.
- Error rate to end-users stays near zero (or rises only slightly).
- Dependency error rate / circuit-breaker open events are visible in tracing.
- Latency may *improve* (fallbacks are typically faster than the primary path).

A *problem* looks like: fallback rate is high, but error rate to users is also high — meaning the fallback itself is failing, or the wrong fallback was implemented for this failure mode.

**Q20. What should you instrument when adding a fallback?**
A:
- **fallback.invoked** — counter, tagged with `service=`, `reason=` (timeout vs. circuit_open vs. error).
- **fallback.type** — which fallback was used (cache, static, queue).
- **fallback.cache_hit_rate** — if cache-based, how often the cache had a value (vs. returning empty/default).
- **fallback.staleness_seconds** — how old the cached data was when served.
- Alert when `fallback.invoked` rate exceeds a threshold for more than N minutes — the system is degraded and a human should investigate.

**Q21. How do you test that your fallbacks actually work?**
A: Chaos engineering / fault injection:
- **Unit tests** — mock the dependency to throw an exception/timeout; assert the fallback value is returned.
- **Integration tests** — use a test container or stub server that returns 500s or delays; verify the service returns the fallback response, not a 500.
- **Chaos testing in staging** — tools like Chaos Monkey, Gremlin, or Istio fault injection kill or delay a dependency and verify the fallback path activates end-to-end.
- **Game days** — deliberately fail a dependency in production (off-peak) to verify fallbacks behave as designed under real traffic patterns.

The biggest risk: a fallback that was written once, never exercised, and silently broken by a later refactor. Fallback paths must be in the regular test suite, not just documented.

## Section 6: Scenario / System Design Style Questions

**Q22. "Your homepage loads product recommendations from a third-party ML service. During a Black Friday sale, the ML service goes down. What's your degradation strategy?"**
A: Three-layer fallback designed in advance:
1. **L1 — Warm cache (Redis):** On each successful ML response, cache the result per user with a 1-hour TTL. On failure, serve the cached recommendations. Fast, personalized, slightly stale.
2. **L2 — Segment-level defaults:** If no user-specific cache exists (new user or expired), serve a pre-computed "trending products for this category" list stored in Redis, refreshed hourly by a batch job. Not personalized but relevant.
3. **L3 — Editorial static list:** A hardcoded or CMS-managed list of bestsellers. Always available. Deployed as a static asset or inline in the app config.
The circuit breaker trips on the ML service; the frontend receives `X-Degraded: recommendations` and hides the "Personalized for you" label — users see valid products without knowing the ML service is down.

**Q23. "Design graceful degradation for a payment gateway integration where the primary processor is down."**
A: Payment is Tier 0 — you can't silently degrade. Options, in order:
1. **Secondary processor failover** — maintain an integration with a backup payment processor (e.g., primary: Stripe, secondary: Razorpay). Circuit breaker on the primary automatically routes new transactions to the secondary. Requires keeping both integrations live and tested.
2. **Queue with user acknowledgement** — for asynchronous payment contexts (e.g., invoice billing), enqueue the payment attempt and notify the user "your payment is being processed" with a follow-up confirmation. Not usable for real-time checkout.
3. **Visible degradation** — disable checkout entirely if neither processor is available; display a clear status page. Better than silently failing transactions or double-charging. Never silently return "payment successful" without actually processing it.

**Q24. "Your search service is backed by Elasticsearch. During an ES outage, your SQL fallback is also getting overwhelmed. What went wrong and what's the fix?"**
A: The fallback lacked its own capacity guard. When ES failed, 100% of search traffic hit the SQL fallback, which was not designed for that throughput. Fix:
- **Rate-limit the SQL fallback** — semaphore or thread-pool bulkhead with a small capacity (e.g., 20 concurrent queries). Excess requests get an immediate empty result or a "search temporarily limited" message — they don't hit SQL.
- **Cache SQL fallback results** — the most common search terms have a high repeat rate. Cache results in Redis for 60 seconds; the same query only hits SQL once per minute regardless of traffic.
- **Load shed at the edge** — return an empty search result with a visible message for all but the top N most critical search paths during the outage rather than degrading the DB for all traffic.

**Q25. "How would you implement graceful degradation in a microservices checkout flow where 5 services are called sequentially?"**
A: Classify each service call by whether it's blocking or optional for checkout completion:
- **Blocking (must succeed):** Cart validation, payment processing, order creation — no fallback; fail the checkout if these fail.
- **Non-blocking with fallback:** Inventory reservation (fallback: mark as "pending confirmation", send async reservation later); coupon validation (fallback: skip coupon, flag for manual review); fraud scoring (fallback: approve with a low-risk flag, queue for async review); email receipt (fallback: queue for delayed delivery).

Run non-blocking calls concurrently with a timeout; collect results; if a non-blocking service fails, use its fallback and proceed. Only block on payment and order creation. This means a fraud service or email outage never kills a checkout.

**Q26. "A senior engineer says 'our system degrades gracefully because we have circuit breakers everywhere.' Is that correct?"**
A: Not quite — circuit breakers are a *trigger* mechanism, not a degradation strategy themselves. A circuit breaker that opens and returns an exception to the user is just fast failure, not graceful degradation. Graceful degradation requires: (1) circuit breakers or bulkheads to detect/gate the failure, AND (2) explicit fallback logic that determines what to return when the gate closes. If there's no fallback registered — just a catch block that re-throws — the user gets an error. True graceful degradation needs both the detection layer and a thoughtful fallback response designed for each specific failure scenario.

## Quick Reference: Fallback Strategy Selection

| Scenario                          | Recommended Fallback                          | Watch Out For                                  |
|---                                |---                                            |---                                             |
| Read from slow/unavailable API    | Stale cache (Redis/in-memory)                 | Cache staleness causing incorrect decisions    |
| Recommendation / personalization  | Pre-computed segment defaults or static list  | Empty UI looking broken without explanation    |
| Write to unavailable service      | Durable queue + 202 Accepted                  | Queue backup if service is down long-term      |
| Search (Elasticsearch down)       | Degraded SQL query with rate limit            | SQL overwhelmed by full search traffic         |
| Entire feature unreliable         | Feature flag off + hidden UI                  | Users confused by missing feature with no msg  |
| Auth service unreachable          | Short-lived cached token validation           | Serving expired or revoked tokens as valid     |
| Payment processor down            | Secondary processor failover                  | Divergent transaction states between processors|
| Configuration service down        | Last-known-good config snapshot               | Stale config enabling a disabled feature       |

---

**Tip for the interview:** The thing that separates senior answers here is understanding that graceful degradation is a *product decision* as much as a technical one — it requires deciding which features are allowed to degrade and what "degraded" looks like to the user. Be ready to talk about how you'd classify features by criticality, how you'd communicate degradation to end users (status pages, UI messaging, response headers), and how you'd *know* degradation is happening via metrics. The failure mode that kills teams is implementing fallbacks but never testing them — mention chaos testing or game days if you've done it.
