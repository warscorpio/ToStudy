# Health Checks: Liveness vs Readiness Probes — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a health check in a distributed system?**
A: A health check is a mechanism by which an orchestrator, load balancer, or monitoring system periodically queries a service to determine whether it is functioning correctly. Rather than assuming a process is healthy because it started successfully, health checks continuously verify that the service can actually do useful work — and act on the result (restart, remove from rotation, alert).

**Q2. What is a liveness probe?**
A: A liveness probe answers the question: *"Is this process alive and not stuck?"* If it fails, the orchestrator (e.g., Kubernetes) kills and restarts the container on the assumption that the process is in an unrecoverable bad state — deadlocked, out of memory, or corrupted — and a fresh start will fix it. A passing liveness probe means the process is running and not terminally broken; it says nothing about whether it can serve traffic.

**Q3. What is a readiness probe?**
A: A readiness probe answers the question: *"Is this instance ready to serve traffic right now?"* If it fails, the orchestrator removes the pod from the load balancer's endpoint pool — traffic stops being sent to it — but the container is *not* restarted. A failing readiness probe is a signal that the service is temporarily unable to handle requests (warming up, overwhelmed, waiting for a dependency) and should be given a chance to recover without being killed.

**Q4. What is the core operational difference between the two?**
A: Liveness failure → **restart the container**. Readiness failure → **remove from load balancer, do not restart**. This distinction is critical: misconfiguring them (e.g., using a liveness probe that checks dependencies) can cause mass restarts of healthy pods during a dependency outage, turning a partial degradation into a full one.

**Q5. Is there a third probe type worth knowing?**
A: Yes — **startup probes** (Kubernetes 1.16+). They answer: *"Has the application finished initializing?"* While the startup probe is active, liveness and readiness probes are disabled. This prevents Kubernetes from killing a slow-starting container (e.g., a JVM loading large caches) before it has had a chance to initialize. Once the startup probe succeeds, liveness and readiness probes take over. Think of it as a one-shot readiness check specifically for the boot phase.

**Q6. What happens if you define no health checks at all?**
A: The orchestrator uses process liveness as the only signal — if the process is running, traffic is sent to it. This means:
- A deadlocked or OOM-looping process keeps receiving traffic it can't handle.
- A newly started pod gets traffic before it finishes warming up, causing errors during deployments.
- A pod stuck waiting for a dependency silently serves errors with no automatic remediation.
Health checks are the difference between a system that self-heals and one that silently degrades.

## Section 2: Probe Mechanics & Configuration

**Q7. What are the common probe implementation types?**
A: Three main types:
- **HTTP GET** — the most common; the orchestrator makes an HTTP request to a specified path/port and checks the status code (2xx/3xx = healthy, anything else = unhealthy).
- **TCP socket** — attempts to open a TCP connection to a port; success means the process is accepting connections (coarser than HTTP — doesn't verify the application layer).
- **Exec command** — runs a command inside the container; exit code 0 = healthy, non-zero = unhealthy. Useful for non-HTTP services (e.g., checking a Redis `PING` response via the CLI).

**Q8. What are the key configuration parameters for a probe in Kubernetes?**
A:
- `initialDelaySeconds` — how long to wait after container start before the first probe fires. Set this long enough for your app to boot.
- `periodSeconds` — how often to probe. Lower = faster detection, more overhead.
- `timeoutSeconds` — how long to wait for a probe response before counting it as a failure.
- `failureThreshold` — how many consecutive failures before acting (restarting or removing from rotation).
- `successThreshold` — how many consecutive successes before marking as healthy again (readiness only; liveness is always 1).

**Q9. How do you tune `initialDelaySeconds` and what happens if it's too short?**
A: If `initialDelaySeconds` is shorter than your application's boot time, the liveness probe fires before the app is ready, immediately fails, and Kubernetes restarts the container — which hasn't finished starting yet — creating a restart loop. Tune it to at least your p99 cold-start time in production (not just on your laptop). For apps with variable startup times, a **startup probe** is a cleaner solution than a generous `initialDelaySeconds`.

**Q10. What is the effect of `failureThreshold` on system behavior?**
A: It prevents a single transient probe failure (a GC pause, a brief network hiccup) from triggering a restart or traffic removal. Setting it too low causes instability — pods bouncing unnecessarily on transient blips. Setting it too high delays detection of genuinely sick pods. A common default is 3 consecutive failures before acting, combined with a `periodSeconds` of 10s, giving a ~30s detection window.

**Q11. Should your probe endpoint itself be expensive to compute?**
A: No. Probe endpoints should be cheap and fast — they are called continuously by the orchestrator. An expensive liveness check (e.g., one that runs a DB query) adds load on every probe cycle and may itself time out under load, triggering false failures. Liveness should check internal state only (flag set by the app, basic I/O check). Readiness can be slightly heavier (dependency pings) but should still be optimized.

**Q12. How do you handle probe timeouts relative to probe period?**
A: `timeoutSeconds` must be less than `periodSeconds`. If a probe takes longer to time out than the period between probes, you get overlapping probe calls piling up, which amplifies load and produces misleading failure counts. A safe rule: `timeoutSeconds ≤ periodSeconds / 2`.

## Section 3: What to Check in Each Probe

**Q13. What should a liveness probe check?**
A: Only internal, self-owned state that would require a restart to fix:
- Is the event loop / main thread still responsive?
- Is the process deadlocked or OOM-looping?
- Is an internal health flag still set (e.g., the app sets a flag to `false` when it detects an unrecoverable error)?

A liveness probe should **not** check external dependencies (databases, downstream services). A DB going down should not restart your app — your app is fine, the DB is the problem.

**Q14. What should a readiness probe check?**
A: Anything that affects the ability to handle a request successfully *right now*:
- Has the app finished loading caches / warming up?
- Can it reach critical dependencies (DB connection pool has at least one connection, required config is loaded)?
- Is it under too much load to accept more traffic (optional, but useful for backpressure)?

Readiness failing removes the pod from the load balancer — the right response to a temporary inability to serve rather than an unrecoverable crash.

**Q15. Should the readiness probe check all dependencies or just critical ones?**
A: Only critical ones — those whose absence makes the service unable to fulfill *any* request. If your service has an optional feature backed by a secondary cache and that cache goes down, the service can still serve most traffic in a degraded mode. Marking it not-ready in that case would remove it from rotation unnecessarily. Reserve not-ready for situations where the service genuinely cannot serve traffic at all.

**Q16. What is a "deep" vs "shallow" health check?**
A: 
- **Shallow** — checks only whether the process is up and the HTTP server is responding (e.g., `/ping` returns 200). Fast and cheap; appropriate for liveness.
- **Deep** — checks connectivity to dependencies, validates configuration, runs a test query (e.g., `SELECT 1` against the DB). More informative; appropriate for readiness, but must be capped at reasonable cost and not used for liveness.

**Q17. Can you have separate `/healthz/live` and `/healthz/ready` endpoints?**
A: Yes — this is the recommended pattern. Expose distinct endpoints for each probe type so their logic stays separated. Common conventions:
- `/healthz` or `/healthz/live` — liveness (is the process alive?)
- `/readyz` or `/healthz/ready` — readiness (can it serve traffic?)
- `/healthz/startup` — startup (has it finished booting?)

Some teams also expose a `/healthz/details` endpoint (not used by probes) that returns a richer breakdown of dependency states for debugging — but keep this separate from the probe endpoints to avoid coupling probe latency to detailed checks.

## Section 4: Failure Modes & Anti-patterns

**Q18. What is the "dependency check in liveness" anti-pattern and why is it dangerous?**
A: Putting a check for an external dependency (e.g., `SELECT 1` against the DB) into the liveness probe. When the DB has an outage, every pod fails its liveness probe, Kubernetes restarts all of them simultaneously, and they all come back up still unable to reach the DB — now you have both a DB outage *and* a pod restart storm. The service was fine before; the restarts added nothing and may make recovery slower. External dependency checks belong in readiness probes.

**Q19. What is a "flapping" readiness probe and what causes it?**
A: A pod that rapidly alternates between ready and not-ready, being added and removed from the load balancer pool repeatedly. Causes include: a `failureThreshold` of 1 combined with a dependency that has intermittent latency, a probe timeout that's too short, or a dependency that is genuinely unstable. Flapping routes traffic erratically and produces confusing error patterns. Fix: tune `failureThreshold` and `successThreshold` to require sustained failure/recovery before acting.

**Q20. What happens during a rolling deployment if readiness probes are misconfigured or absent?**
A: Kubernetes replaces old pods with new ones and, if there's no readiness probe, marks the new pod ready immediately on container start — before the app has finished booting. Traffic is routed to the starting pod, which can't serve it yet, causing a burst of errors on every deployment. A proper readiness probe holds the pod out of rotation until it's genuinely ready, enabling zero-downtime rolling deployments.

**Q21. What is a "liveness probe restart loop" and how do you diagnose it?**
A: When a pod keeps restarting in a cycle driven by repeated liveness probe failures. Symptoms: `kubectl get pods` shows a high `RESTARTS` count and status `CrashLoopBackOff`. Diagnosis steps: (1) check `kubectl describe pod <name>` for the "Liveness probe failed" event, (2) check `kubectl logs <pod> --previous` to see what the container was doing before the restart, (3) verify `initialDelaySeconds` is long enough for your boot time, (4) confirm the liveness endpoint isn't checking external dependencies.

**Q22. Can a readiness probe cause a full outage even without restarting pods?**
A: Yes — if all pods simultaneously fail their readiness probe, they're all removed from the load balancer and the service becomes completely unavailable even though every pod is running. This can happen when a readiness probe checks a dependency that is down (e.g., the DB), or when a probe timeout is too short and all pods have a correlated slow response at the same time. This is a silent outage from the orchestrator's perspective — pods are "healthy" but receiving no traffic.

**Q23. What is "probe amplification" and when does it occur?**
A: When the probe endpoint itself triggers expensive work — e.g., it opens a new DB connection on every call rather than reusing the pool, or it runs an uncached query. At `periodSeconds: 5` across 50 pods, that's 10 probe calls per second hitting your DB. Under load, these probe calls compete with real traffic, potentially causing the very latency that makes probes fail. Keep probe endpoints stateless and cheap.

**Q24. What is the "thundering herd on startup" problem with readiness probes?**
A: During a large deployment or after a cluster restart, many pods start simultaneously. If their readiness probe periods are all synchronized (same `initialDelaySeconds`, same `periodSeconds`), their probe calls all fire together, creating synchronized spikes of load on whatever the probe checks (DB, config service, etc.). Mitigation: Kubernetes adds a small random jitter to probe timing automatically, but you should also avoid probes that are expensive enough to matter at scale.

## Section 5: Trade-offs & Decision-Making

**Q25. When should you make a readiness probe more aggressive (short period, low threshold)?**
A: When fast traffic removal is more important than stability — e.g., a payment processing service where routing traffic to a degraded pod causes incorrect charges is worse than briefly under-utilizing capacity. Tighter probes mean faster removal from rotation at the cost of more sensitivity to transient blips.

**Q26. When should you make probes more lenient (long period, high threshold)?**
A: For services with high startup cost (JVM, ML model loading) or dependencies with occasional latency spikes (not genuine failures). Lenient probes prevent unnecessary restarts and flapping at the cost of slower detection of genuinely bad pods. Use a startup probe to handle the initialization phase rather than inflating liveness/readiness parameters.

**Q27. Should you use the same endpoint for both liveness and readiness probes?**
A: Rarely, and only for the simplest services. In practice, the semantics differ: liveness wants the fastest possible check of internal health; readiness wants a broader check of serving capability. Using the same endpoint forces you to pick one — you'll either have a liveness probe that's too heavy (dependency checks) or a readiness probe that's too shallow (missing dependency state). Separate endpoints keep the concerns clean.

**Q28. How do health checks interact with horizontal pod autoscaling (HPA)?**
A: HPA scales pods based on metrics (CPU, custom metrics). Health checks don't feed directly into HPA decisions, but they interact: if pods are failing readiness probes and are out of rotation, they're still counted in the replica count — HPA may not scale up because it sees "enough" pods, while actually none of them are serving traffic. This is a subtle failure mode: monitor ready pod count separately from total pod count.

**Q29. How should health checks be designed for a service with a long graceful shutdown?**
A: When a pod receives `SIGTERM` (during a rolling deployment or scale-down), it should immediately start failing its readiness probe so Kubernetes removes it from the load balancer before shutdown completes. The process should then drain in-flight requests, finish them, and exit — the liveness probe can still pass during this window. Failing readiness on `SIGTERM` + finishing in-flight requests = zero-drop graceful shutdown.

## Section 6: Scenario / System Design Style Questions

**Q30. "Your service has a 3-minute cold start because it loads a 2GB model into memory. How do you configure health probes?"**
A: Use a **startup probe** with a long `failureThreshold * periodSeconds` window (e.g., `failureThreshold: 36`, `periodSeconds: 5` = 3 minutes) to gate liveness/readiness until the model is loaded. The startup probe can hit a lightweight endpoint that returns 200 only after the model is fully in memory. Once startup succeeds, switch to a fast liveness probe (internal flag check) and a readiness probe that verifies the inference engine is responsive. This avoids bloating `initialDelaySeconds` on liveness and prevents premature restarts during loading.

**Q31. "A downstream database goes down. Walk through what should happen in a correctly configured system vs. a badly configured one."**
A:
- **Correctly configured**: The DB outage causes readiness probes to fail (they check DB reachability). Pods are removed from the load balancer. Liveness probes continue passing (they check only internal state). Pods are not restarted. When the DB recovers, readiness probes pass again, pods are added back to rotation. Zero unnecessary restarts; recovery is automatic and fast.
- **Badly configured** (liveness checks DB): All pods fail liveness. Kubernetes restarts all pods simultaneously. They restart into the same DB outage, fail liveness again, restart again — restart loop. Logs are noisy and potentially lost. When the DB recovers, pods have to cold-start, adding latency to recovery. The outage is worse than the original DB failure warranted.

**Q32. "You're doing a rolling deployment and seeing a spike of 5xx errors on every deploy. What do you check?"**
A: Almost certainly a readiness probe issue. Check: (1) Is there a readiness probe defined at all? (2) Is `initialDelaySeconds` long enough for the app to boot? (3) Does the readiness probe correctly return non-200 until the app is ready to serve? (4) Is `minReadySeconds` set to give a buffer after the probe first passes before replacing the next pod? Also check: does the app handle `SIGTERM` gracefully (drain in-flight requests before exiting), or does it hard-exit, dropping connections?

**Q33. "Design health check endpoints for a service that has: a local cache (warm on startup), a primary DB (required), and a secondary analytics DB (optional)."**
A:
- **`/healthz/live`** (liveness): Returns 200 if the HTTP server is responding and no internal deadlock flag is set. Does not check any DB. Lightweight, always fast.
- **`/healthz/ready`** (readiness): Returns 200 only if (a) the local cache is fully warmed and (b) the primary DB connection pool has at least one live connection. Does *not* check the analytics DB — its absence should trigger degraded mode, not traffic removal. Returns 503 with a JSON body indicating which check failed.
- **`/healthz/startup`** (startup probe): Returns 200 only when the cache warm-up is complete. Disables liveness/readiness until then.
- **`/healthz/details`** (debugging only, not used by probes): Returns full JSON breakdown of all dependency states including analytics DB connectivity, cache stats, pool sizes — used by engineers during incidents, not by orchestrators.

**Q34. "A pod's readiness probe is passing, but users are seeing errors from that pod. How do you investigate?"**
A: The readiness probe is too shallow — it passes even when the pod can't serve real traffic correctly. Investigation: (1) Check what the readiness probe actually verifies (maybe just a TCP ping or a trivial `200 OK` with no real business logic check). (2) Add more meaningful checks — e.g., attempt a real operation against the dependency, verify config is loaded, check that thread/worker pools aren't exhausted. (3) Look at pod-level error metrics broken down by instance — if errors are concentrated on one pod, correlate with that pod's internal state (recent restarts, memory, GC logs). (4) Consider adding a circuit-breaker at the load balancer layer to remove pods exceeding an error-rate threshold, separate from the probe mechanism.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                    | Liveness Probe                                      | Readiness Probe                                            | Startup Probe                                   |
|---                        |---                                                  |---                                                         |---                                              |
| Question answered         | Is the process alive and not broken?                | Can this instance serve traffic right now?                 | Has the app finished initializing?              |
| Action on failure         | Restart the container                               | Remove from load balancer (no restart)                     | Keep liveness/readiness disabled (no action yet)|
| Action on recovery        | No special action (pod keeps running)               | Re-add to load balancer                                    | Hand off to liveness + readiness probes         |
| What to check             | Internal state only (deadlock flag, basic I/O)      | Internal state + critical dependencies                     | Initialization completion only                  |
| External dependencies     | Never                                               | Yes, for critical ones only                                | Depends on what "ready to start" means          |
| Cost target               | Extremely cheap (<5ms)                              | Cheap, but can do light dependency pings                   | Can be heavier (checks large init tasks)        |
| Risk if misconfigured     | Restart storms during dependency outages            | Silent full outage (all pods pulled from rotation)         | Premature liveness failures on slow-booting apps|
| Typical period            | 10–30s                                              | 5–15s                                                      | 5–10s with high failure threshold               |

## Key Concepts Cheat Sheet

| Term                      | One-line definition                                                                          |
|---                        |---                                                                                           |
| Liveness probe            | Is the container alive? Failure → restart                                                   |
| Readiness probe           | Can it serve traffic? Failure → remove from load balancer                                   |
| Startup probe             | Has it finished booting? Disables other probes until it passes                              |
| initialDelaySeconds       | Grace period before first probe fires; must be ≥ app boot time                              |
| failureThreshold          | Consecutive failures before action is taken; prevents acting on transient blips             |
| successThreshold          | Consecutive successes before marking healthy again (readiness); prevents flapping            |
| Probe amplification       | When the probe endpoint itself causes expensive work that compounds under load               |
| Flapping                  | Pod rapidly toggling between ready/not-ready due to probe misconfiguration or instability   |
| Graceful shutdown         | Failing readiness on SIGTERM + draining in-flight requests before exit = zero-drop deploys  |
| Deep vs shallow check     | Shallow = process alive; deep = dependencies reachable. Match depth to probe type.          |

---

**Tip for the interview:** At 5 YOE level, the classic trap is conflating liveness and readiness. Make it clear early that you understand the restart vs. traffic-removal distinction — it's the crux of the topic. The best candidates go further: they talk about what *not* to put in each probe, the startup probe as a third tool, graceful shutdown interaction, and the failure modes that come from getting it wrong (restart storms, silent outages). A war story about a production restart loop caused by a DB check in a liveness probe lands especially well.
