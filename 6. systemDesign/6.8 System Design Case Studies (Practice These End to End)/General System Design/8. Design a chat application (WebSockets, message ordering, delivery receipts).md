# Design a Chat Application — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a chat application?**
A: Core functional requirements:
- **1:1 messaging** — two users exchange messages in a conversation thread.
- **Group messaging** — N users share a conversation; a message sent by one is delivered to all others.
- **Message delivery receipts** — sent (server received), delivered (recipient device received), read (recipient opened).
- **Message ordering** — messages within a conversation are displayed in the order they were sent; no reordering on delivery.
- **Online presence** — show whether a user is online, offline, or last seen.
- **Push notifications** — deliver messages to offline users via APNs (iOS) / FCM (Android).
- **Message history** — users can scroll back through conversation history; pagination required.
- **Media messages** — images, video, files (treated separately from text; upload to object storage).
- **Typing indicators** — ephemeral signal that a user is currently composing a message.

**Q2. What are the non-functional requirements?**
A:
- **Low latency** — message delivery to an online recipient must feel instantaneous; P99 < 100ms server-to-server, < 500ms end-to-end (including client render).
- **High availability** — chat is a core product feature; downtime directly impacts user trust. Target 99.99% availability for the message delivery path.
- **Durability** — a sent message must never be lost. Once the server acknowledges receipt to the sender, the message must be persisted and delivered eventually, even if the recipient is temporarily offline.
- **At-least-once delivery with deduplication** — the delivery path may retry on failure; the recipient client must deduplicate to avoid showing a message twice.
- **Ordering guarantees** — within a conversation, all clients must agree on the order of messages. Across conversations, ordering is independent.
- **Scale** — at 500M DAU with average 10 messages/day, that's ~58,000 messages/second at average; peak can be 3–5x. WebSocket connections are long-lived; a server handling 100k connections must sustain them simultaneously.
- **Eventual consistency** — strict consistency across all devices is expensive; acceptable model is that all devices converge to the same message order within seconds.

**Q3. Why use WebSockets instead of HTTP polling or Server-Sent Events?**
A:
- **HTTP short polling** — client polls every N seconds. Simple but wasteful: most polls return nothing; latency is up to N seconds; server load scales with polling frequency × user count.
- **HTTP long polling** — client holds a connection open until the server has data, then immediately re-opens. Better latency but still half-duplex; connection overhead per message is high; hard to multiplex multiple event types.
- **Server-Sent Events (SSE)** — server pushes to client over HTTP/1.1; client-to-server is separate HTTP requests. Good for one-directional streams (notifications, live feeds) but chat requires bidirectional communication (typing indicators, receipts, messages all flow both ways).
- **WebSockets** — full-duplex, low-overhead (no HTTP headers per message after handshake), persistent connection ideal for bidirectional real-time communication. The right choice for chat. Overhead: each open connection consumes a file descriptor and memory on the server; connection management becomes the primary scaling concern.

## Section 2: WebSocket Architecture

**Q4. What does the WebSocket connection lifecycle look like?**
A:

```
Client                          WebSocket Gateway
  │                                    │
  │── HTTP GET /ws (Upgrade: websocket)──►│
  │◄── 101 Switching Protocols ──────────│
  │                                    │
  │  [Connection established]          │
  │                                    │
  │── {type:"auth", token:"JWT..."} ──►│  Validate JWT; associate
  │◄── {type:"auth_ok", userId:"..."} ──│  userId ↔ connection
  │                                    │
  │  [Heartbeat every 30s]             │
  │──────── {type:"ping"} ────────────►│
  │◄─────── {type:"pong"} ─────────────│
  │                                    │
  │── {type:"message", ...} ──────────►│  Route to recipient
  │◄── {type:"ack", msgId:"..."} ───────│  Durability confirmed
  │                                    │
  │  [Client disconnects / timeout]    │
  │── TCP FIN ─────────────────────────►│
                                       │  Clean up: remove
                                       │  userId ↔ connection mapping
```

Key details:
- **Authentication on connect** — the WebSocket handshake HTTP request carries a JWT in the `Authorization` header or query param; the gateway validates before upgrading. Don't allow unauthenticated WebSocket connections.
- **Heartbeat / keepalive** — NATs and load balancers silently drop idle TCP connections after 30–300 seconds. Client sends a `ping` every 25–30 seconds; server responds with `pong`. If the server misses N consecutive pings, it closes the connection. The client detects the closed connection and reconnects with exponential backoff.
- **Graceful reconnection** — on reconnect, the client sends its last received message sequence number; the server replays any messages missed during the disconnect window.

**Q5. How do you scale WebSocket connections across multiple gateway servers?**
A: WebSocket connections are stateful — a connection is pinned to a specific gateway server process. This breaks the standard stateless horizontal scaling model. The solution is a routing layer backed by a connection registry:

```
                    Load Balancer (L4 / sticky)
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    WS Gateway 1    WS Gateway 2    WS Gateway 3
    [user A, B]     [user C, D]     [user E, F]
          │                │                │
          └────────────────┼────────────────┘
                           │
                    ┌──────▼──────┐
                    │    Redis    │  Connection registry
                    │  user_id →  │  gateway_id + server_ip
                    │  gateway_id │
                    └─────────────┘
```

When User A (on Gateway 1) sends a message to User C (on Gateway 2):
1. Gateway 1 receives the message.
2. Looks up User C's location in Redis: `GET ws:connection:{userC_id}` → `gateway_2_id`.
3. Publishes the message to a Redis Pub/Sub channel or message queue that Gateway 2 subscribes to.
4. Gateway 2 delivers the message to User C's open connection.

Redis Pub/Sub is the standard inter-gateway fanout mechanism for chat; each gateway subscribes to its own channel. For very large deployments, replace Redis Pub/Sub with Kafka (per-gateway consumer groups) for durability and replay capability.

**Q6. What message format should WebSocket frames use?**
A: Use a structured envelope — every message type (chat message, receipt, typing indicator, presence update) uses the same outer shape so the client can dispatch by type without special-casing:

```typescript
// Outbound (client → server)
interface WsClientMessage {
  type:    'message' | 'receipt' | 'typing' | 'ping';
  payload: MessagePayload | ReceiptPayload | TypingPayload | null;
  clientMsgId: string;   // client-generated UUID for deduplication
}

// Inbound (server → client)
interface WsServerMessage {
  type:    'message' | 'receipt' | 'typing' | 'presence' | 'ack' | 'pong';
  payload: unknown;
  serverMsgId?: string;  // server-assigned ID; stable identifier for the message
}

// Chat message payload
interface MessagePayload {
  conversationId: string;
  text:           string;
  sentAt:         string;  // ISO 8601; client's local time (informational only)
  seqNum?:        number;  // server-assigned sequence number within conversation
}
```

Binary serialization (protobuf / MessagePack) reduces frame size 30–60% vs JSON — relevant at scale but adds complexity. Start with JSON; migrate to binary if bandwidth becomes a measured bottleneck.

## Section 3: Message Ordering

**Q7. Why is message ordering hard in a distributed chat system?**
A: Three sources of ordering ambiguity:

1. **Clock skew** — two clients' clocks differ by seconds. If ordering is by client-reported timestamp, a message sent "later" by one client may have an earlier timestamp than a message sent "earlier" by another. Using wall-clock time from clients for ordering is fundamentally broken.

2. **Network reordering** — two messages sent in rapid succession may arrive at the server out of order if they travel different network paths or hit different gateway servers.

3. **Concurrent sends** — in a group chat, two users send messages simultaneously. Both arrive at the server within milliseconds of each other. Which comes "first" in the conversation's history?

**Q8. How do you assign a canonical order to messages?**
A: The server assigns ordering — clients are never authoritative about order. Two complementary mechanisms:

**Per-conversation sequence numbers:**
The server assigns a monotonically increasing integer (`seq_num`) to each message within a conversation at the moment it's persisted. All clients see the same `seq_num` order. Implementation:

```sql
-- Atomic sequence assignment in Postgres
UPDATE conversations
SET last_seq_num = last_seq_num + 1
WHERE id = $1
RETURNING last_seq_num;

-- Assign the returned value to the message being inserted
INSERT INTO messages (id, conversation_id, seq_num, sender_id, body, created_at)
VALUES ($1, $2, $returned_seq_num, $3, $4, now());
```

The `UPDATE … RETURNING` is atomic — concurrent inserts for the same conversation serialize through this row-level lock, guaranteeing unique, gap-free sequence numbers per conversation.

**Hybrid Logical Clocks (HLC) for multi-region:**
In a multi-region deployment, a single Postgres sequence becomes a bottleneck (all writes must hit one region). HLC combines physical time with a logical counter: `hlc = (physical_time_ms, logical_counter)`. Two events at the same physical millisecond are distinguished by the counter. HLC preserves causality (a message always has a higher HLC than the message it's replying to) without requiring a centralized sequence generator. Implemented as a 64-bit integer: upper 48 bits = milliseconds since epoch, lower 16 bits = logical counter.

**Q9. How do clients handle receiving messages out of order?**
A: Despite server-side ordering, messages may arrive at the client out of order (network reordering, WebSocket reconnect with replay). The client must buffer and re-sequence:

```typescript
class ConversationBuffer {
  private buffer: Map<number, Message> = new Map();
  private nextExpected: number = 1;

  receive(msg: Message): Message[] {
    this.buffer.set(msg.seqNum, msg);
    const ready: Message[] = [];

    // Drain contiguous messages from nextExpected
    while (this.buffer.has(this.nextExpected)) {
      ready.push(this.buffer.get(this.nextExpected)!);
      this.buffer.delete(this.nextExpected);
      this.nextExpected++;
    }
    return ready;  // render these in order; hold the rest
  }
}
```

If a gap persists for > 2 seconds (the message may have been lost), the client requests the missing range via a REST API (`GET /conversations/{id}/messages?from_seq=N&to_seq=M`) rather than waiting indefinitely.

**Q10. How does message ordering work for group chats with many participants?**
A: The sequence number approach scales to group chats without modification — the `conversations` table row for the group chat is the single serialization point. Every message in the group gets a globally consistent `seq_num`; all members see the same ordering. The fan-out (delivering the message to all N members) is the scaling challenge, not the ordering:

- **Small groups (< 100 members)** — fan-out at delivery time: for each online member, publish to their gateway via Redis Pub/Sub; for offline members, enqueue a push notification.
- **Large groups (100–10k members)** — async fan-out via a message queue: write the message once to the DB; publish a single event to Kafka; a fan-out worker reads the event and delivers to each member's gateway. This decouples message persistence latency from fan-out latency.
- **Very large groups (10k+ members)** — treat like a broadcast channel; use a topic-based pub/sub model where members subscribe to the channel rather than receiving individual pushes.

## Section 4: Delivery Receipts

**Q11. What are the three delivery receipt states and how is each triggered?**
A:

| State | Meaning | Triggered by |
|--- |--- |--- |
| **Sent** (✓) | Server persisted the message | Server sends `ack` to sender after DB write |
| **Delivered** (✓✓) | Recipient's device received it | Recipient client sends `receipt{type:delivered}` on WebSocket receipt |
| **Read** (✓✓ blue) | Recipient opened the conversation | Recipient client sends `receipt{type:read}` when conversation is foregrounded |

Each state transition is a receipt event that flows from the recipient back to the sender via the server:

```
Sender                Server                Recipient
  │── send message ──►│── store message ───►│
  │◄── ack (SENT) ────│                     │
  │                   │◄── receipt:DELIVERED─│  (on WebSocket delivery)
  │◄── receipt:DELIVERED ─────────────────────│  (server forwards to sender)
  │                   │◄── receipt:READ ──────│  (when user opens chat)
  │◄── receipt:READ ──────────────────────────│
```

**Q12. What is the data model for receipts?**
A:

```sql
-- Message receipts (one row per recipient per message per state)
CREATE TABLE message_receipts (
  message_id      UUID NOT NULL REFERENCES messages(id),
  recipient_id    UUID NOT NULL REFERENCES users(id),
  status          TEXT NOT NULL,      -- DELIVERED | READ
  occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (message_id, recipient_id, status)
);
CREATE INDEX ON message_receipts(message_id);
CREATE INDEX ON message_receipts(recipient_id, occurred_at);

-- Denormalized on the message itself for fast sender lookup
ALTER TABLE messages ADD COLUMN delivered_count INT DEFAULT 0;
ALTER TABLE messages ADD COLUMN read_count      INT DEFAULT 0;
```

For group chats, the sender UI shows "Delivered to 12 / 15" — the `delivered_count` and `read_count` columns give O(1) access without counting the receipts table. They're incremented atomically when a receipt is recorded:

```sql
INSERT INTO message_receipts (message_id, recipient_id, status, occurred_at)
VALUES ($1, $2, 'DELIVERED', now())
ON CONFLICT DO NOTHING;  -- idempotent

UPDATE messages
SET delivered_count = delivered_count + 1
WHERE id = $1
AND NOT EXISTS (
  SELECT 1 FROM message_receipts
  WHERE message_id = $1 AND recipient_id = $2 AND status = 'DELIVERED'
);
```

**Q13. How do you handle receipts for messages delivered while the sender is offline?**
A: Receipt events are buffered server-side and delivered to the sender when they reconnect:

```sql
-- Pending receipt events for offline senders
CREATE TABLE pending_receipt_events (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sender_id       UUID NOT NULL,       -- the user who needs to receive this receipt
  message_id      UUID NOT NULL,
  recipient_id    UUID NOT NULL,
  status          TEXT NOT NULL,
  occurred_at     TIMESTAMPTZ NOT NULL,
  delivered_at    TIMESTAMPTZ          -- null until sent to sender's WS
);
CREATE INDEX ON pending_receipt_events(sender_id, delivered_at NULLS FIRST);
```

On WebSocket connect, the server immediately queries pending events for the connecting user and flushes them over the connection. This ensures the sender's UI reflects all receipts that accumulated during their offline period.

**Q14. How do you prevent duplicate receipts from causing incorrect counts?**
A: Three layers of deduplication:
- **`ON CONFLICT DO NOTHING`** on the `message_receipts` insert — the primary key `(message_id, recipient_id, status)` makes the insert idempotent at the DB layer.
- **Conditional increment** — the `UPDATE delivered_count` checks `NOT EXISTS` before incrementing, ensuring the count only goes up once per recipient per status.
- **Client deduplication** — the sender's client tracks which `(message_id, receipt_status)` pairs it has already applied to the UI; duplicate receipt events from the server are ignored.

## Section 5: Data Model

**Q15. What does the core data model look like?**
A:

```sql
-- Users
CREATE TABLE users (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username     TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,
  avatar_url   TEXT,
  created_at   TIMESTAMPTZ DEFAULT now()
);

-- Conversations (both 1:1 and group)
CREATE TABLE conversations (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type            TEXT NOT NULL,          -- DIRECT | GROUP
  name            TEXT,                   -- null for DIRECT
  last_seq_num    BIGINT NOT NULL DEFAULT 0,
  last_message_at TIMESTAMPTZ,
  created_at      TIMESTAMPTZ DEFAULT now()
);

-- Conversation membership
CREATE TABLE conversation_members (
  conversation_id UUID NOT NULL REFERENCES conversations(id),
  user_id         UUID NOT NULL REFERENCES users(id),
  role            TEXT NOT NULL DEFAULT 'MEMBER',   -- MEMBER | ADMIN
  joined_at       TIMESTAMPTZ DEFAULT now(),
  last_read_seq   BIGINT NOT NULL DEFAULT 0,        -- highest seq_num this user has read
  PRIMARY KEY (conversation_id, user_id)
);
CREATE INDEX ON conversation_members(user_id);      -- "inbox" query

-- Messages
CREATE TABLE messages (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id UUID NOT NULL REFERENCES conversations(id),
  sender_id       UUID NOT NULL REFERENCES users(id),
  seq_num         BIGINT NOT NULL,
  client_msg_id   TEXT NOT NULL,           -- sender's UUID for deduplication
  body            TEXT,
  media_url       TEXT,
  media_type      TEXT,
  delivered_count INT NOT NULL DEFAULT 0,
  read_count      INT NOT NULL DEFAULT 0,
  created_at      TIMESTAMPTZ DEFAULT now(),
  UNIQUE (conversation_id, seq_num),
  UNIQUE (sender_id, client_msg_id)        -- dedup sender retries
);
CREATE INDEX ON messages(conversation_id, seq_num DESC);

-- Online presence
CREATE TABLE user_presence (
  user_id       UUID PRIMARY KEY REFERENCES users(id),
  status        TEXT NOT NULL,             -- ONLINE | OFFLINE
  last_seen_at  TIMESTAMPTZ NOT NULL,
  gateway_id    TEXT                       -- which WS gateway this user is on
);
```

The `UNIQUE (conversation_id, seq_num)` constraint ensures sequence numbers are unique per conversation at the DB level — a second line of defense beyond the application-level atomic increment.

**Q16. How do you model the "unread count" for a user's inbox?**
A: The `last_read_seq` column on `conversation_members` records the highest `seq_num` the user has read in each conversation. Unread count for a conversation:

```sql
SELECT COUNT(*) AS unread_count
FROM messages
WHERE conversation_id = $1
  AND seq_num > (
    SELECT last_read_seq FROM conversation_members
    WHERE conversation_id = $1 AND user_id = $2
  );
```

For the inbox view (all conversations with unread counts), this query runs per conversation — expensive at scale. Optimization: maintain a `unread_count` denormalized column on `conversation_members`, incremented on message insert and reset to 0 when the user sends a `READ` receipt. Trades write complexity for O(1) inbox reads.

## Section 6: Presence & Typing Indicators

**Q17. How do you implement online presence efficiently?**
A: Presence is high-frequency and ephemeral — storing every presence event in Postgres is prohibitively expensive. Use Redis with TTL:

```
User connects to WS gateway:
  SET user:presence:{user_id} "ONLINE" EX 35   -- expires in 35s
  PUBLISH presence.updates "{userId, status: ONLINE}"

Heartbeat every 30s (client ping / server pong):
  SET user:presence:{user_id} "ONLINE" EX 35   -- refresh TTL

User disconnects / TTL expires:
  (Key expires automatically → treated as OFFLINE)
  PUBLISH presence.updates "{userId, status: OFFLINE}"
```

The 35-second TTL with a 30-second heartbeat means a user who silently disconnects (process kill, network failure) is automatically marked OFFLINE within 35 seconds — no explicit disconnect event needed.

**Fanning out presence updates:** Other users who care about User A's presence (friends, conversation partners) subscribe to presence updates via the WebSocket gateway, which subscribes to the Redis `presence.updates` Pub/Sub channel. At scale, presence fan-out is expensive — limit it to the user's active conversation partners and friends list, not all users globally.

**Q18. How do you implement typing indicators?**
A: Typing indicators are ephemeral — they must never be stored persistently, and staleness of a few seconds is acceptable:

```typescript
// Client sends while typing (debounced — max once per 3s)
{ type: "typing", payload: { conversationId: "...", isTyping: true } }

// Server receives, does NOT persist — directly publishes to conversation members
// via Redis Pub/Sub or WS gateway fan-out

// Auto-expire: if no typing event received in 5s, server sends
{ type: "typing", payload: { conversationId: "...", userId: "...", isTyping: false } }
// to all conversation members
```

Server-side per-user-per-conversation TTL in Redis:

```
On typing event:
  SET typing:{conversationId}:{userId} "1" EX 5
  PUBLISH typing.{conversationId} "{userId, isTyping: true}"

Background job or keyspace notification on expiry:
  PUBLISH typing.{conversationId} "{userId, isTyping: false}"
```

Using Redis keyspace notifications for expiry events is elegant but adds Redis configuration overhead (`notify-keyspace-events KEg`). Alternatively, use a short client-side timeout: if no typing event from a user in 5 seconds, the recipient client clears the indicator itself.

## Section 7: Offline Delivery & Push Notifications

**Q19. What happens when a recipient is offline?**
A: Three-layer offline delivery:

```
Message arrives for offline user
        │
        ▼
1. Persist to messages table (durable; user will fetch on reconnect)
        │
        ▼
2. Check: user has other devices online? (look up all WS connections for this user)
   └── Yes → deliver to those connections (multi-device support)
   └── No  → proceed to push notification
        │
        ▼
3. Enqueue push notification job (async; not on message delivery critical path)
   └── APNs for iOS
   └── FCM for Android / Web Push for PWA
        │
        ▼
4. On user reconnect:
   - Client sends last received seq_num per conversation
   - Server returns all messages with seq_num > last_received (catch-up)
```

**Q20. What are the pitfalls of push notifications for chat?**
A:
- **Notification content vs privacy** — showing message preview in the notification leaks content to the OS notification system (which may sync to cloud). Offer a "privacy mode" that sends "New message from Alice" without the body.
- **Notification collapsing** — if a user receives 50 messages while offline, send one collapsed notification ("50 new messages"), not 50 individual ones. APNs `apns-collapse-id` and FCM `collapse_key` support this.
- **Token expiry** — push tokens expire or become invalid when users reinstall the app. Handle `DeviceTokenNotForTopic` (APNs) and `NotRegistered` (FCM) errors by removing the stale token and not retrying.
- **Rate limits** — APNs and FCM have per-device rate limits. A user with many active conversations must not exceed limits; batch and deduplicate notifications per device.
- **Double delivery** — if the push notification arrives while the user is reconnecting, the app may receive the message both via push and via WebSocket catch-up. Use `client_msg_id` deduplication on the client.

## Section 8: Message History & Pagination

**Q21. How do you implement efficient message history pagination?**
A: Use cursor-based pagination on `seq_num` — not offset-based. Offset pagination (`LIMIT N OFFSET M`) requires the DB to scan M rows to skip them, which degrades at large offsets. Cursor pagination is O(log N) via the index:

```sql
-- Initial load: most recent N messages
SELECT * FROM messages
WHERE conversation_id = $1
ORDER BY seq_num DESC
LIMIT 50;

-- Load older messages (scroll-up / infinite scroll)
-- cursor = seq_num of the oldest message currently displayed
SELECT * FROM messages
WHERE conversation_id = $1
  AND seq_num < $cursor
ORDER BY seq_num DESC
LIMIT 50;

-- Load newer messages (catch-up after reconnect)
SELECT * FROM messages
WHERE conversation_id = $1
  AND seq_num > $last_received_seq
ORDER BY seq_num ASC
LIMIT 100;
```

The index `ON messages(conversation_id, seq_num DESC)` makes all three queries index-range scans — O(log N + K) regardless of conversation size.

**Q22. How do you handle very large conversation histories (millions of messages)?**
A: Hot/cold tiering:
- **Hot tier (Postgres)** — last 90 days of messages per conversation. Fast indexed access; in-memory buffer pool covers frequently accessed recent messages.
- **Cold tier (S3 / Cassandra)** — messages older than 90 days archived to S3 in Parquet format (batch export job runs nightly) or Cassandra for individual row access. Slower (100–500ms) but accessed rarely.
- **Transparent tiering** — the API checks if the requested cursor falls in the hot tier; if not, proxies to the cold tier. The client doesn't know which tier it's hitting.
- **Cassandra for extreme scale** — if the message volume is very high (billions of messages), replace Postgres with Cassandra as the primary message store. Cassandra's partition key `(conversation_id)` with clustering key `(seq_num DESC)` maps directly to the access pattern; wide rows per partition give efficient range scans within a conversation.

## Section 9: Scenario Questions

**Q23. "Two users send messages simultaneously in a 1:1 chat. User A sends 'Hello' and User B sends 'Hi' at the same millisecond. How does ordering work?"**
A: Both messages arrive at the server near-simultaneously. The `UPDATE conversations SET last_seq_num = last_seq_num + 1 WHERE id = $1 RETURNING last_seq_num` is an atomic row-level operation — one of the two concurrent updates wins the row lock first. That message gets `seq_num = N`; the other waits, then gets `seq_num = N+1`. The "winner" is determined by which DB transaction commits first — effectively random from the users' perspective, but consistent: both users will see the same ordering. Neither user's message is "wrong" for appearing first; the conversation is still coherent.

**Q24. "A user's phone loses network for 30 seconds mid-conversation. What happens to messages sent and received during the outage?"**
A: Full offline resilience:

**Messages the user sent during outage:**
- The client queues outgoing messages locally (IndexedDB / SQLite) with status `PENDING`.
- On reconnect, the client retries each queued message using its `client_msg_id` (idempotency key).
- The server's `UNIQUE (sender_id, client_msg_id)` constraint ensures retried messages are deduplicated — if the first attempt actually reached the server despite the apparent failure, the retry returns the existing message ID without creating a duplicate.

**Messages the user missed during outage:**
- On reconnect, the WebSocket connection sends `{type: "sync", lastSeqNums: {convId1: 42, convId2: 17, ...}}`.
- The server queries each conversation for messages with `seq_num > lastSeqNum` and delivers them in order.
- The client buffer re-sequences any out-of-order arrivals before rendering.

**Receipts during outage:**
- Messages delivered while the user was offline accumulate in `pending_receipt_events`.
- On reconnect, the server flushes all pending receipts for the reconnecting user.

**Q25. "Your WebSocket gateway has a memory leak and must be restarted. 50,000 users are connected. How do you minimize disruption?"**
A: Graceful rolling restart:

1. **Signal the instance to stop accepting new connections** — remove it from the load balancer's target group (or mark it unhealthy in health checks). New connections route to other gateways.
2. **Drain existing connections gracefully** — send a `{type: "reconnect", delay_ms: 5000}` frame to all connected clients. Well-implemented clients start reconnecting to a different gateway after the specified delay.
3. **Wait for drain window** — give clients 10–30 seconds to reconnect elsewhere. Clients that don't self-reconnect will be dropped when the process exits; they'll reconnect automatically on TCP close.
4. **Restart the process** — with connections drained, the restart is low-impact.
5. **Connection registry cleanup** — on gateway shutdown, publish a `gateway_shutdown:{gateway_id}` event; other gateways or a cleanup job removes stale `user → gateway_id` mappings from Redis to prevent routing messages to the dead gateway.

At 50,000 connections, the reconnect storm is the risk — if all 50k clients reconnect simultaneously to the remaining gateways, connection setup CPU spikes. The `delay_ms` in the reconnect frame should be randomized per client (jitter): `delay = 5000 + random(0, 5000)` to spread the reconnection load over 10 seconds.

## Quick Reference

| Concern | Mechanism |
|--- |--- |
| Real-time delivery | WebSocket; full-duplex; persistent connection per client |
| Multi-server routing | Redis connection registry (`user_id → gateway_id`); Redis Pub/Sub for cross-gateway delivery |
| Message ordering | Server-assigned `seq_num` via atomic `UPDATE … RETURNING`; client buffer re-sequences |
| Deduplication (sender) | `client_msg_id` UUID; `UNIQUE (sender_id, client_msg_id)` DB constraint |
| Deduplication (receipts) | `ON CONFLICT DO NOTHING`; conditional count increment |
| Delivery receipts | Three states (sent/delivered/read); receipt events flow recipient → server → sender; buffered for offline senders |
| Offline delivery | Persist to DB; push notification (APNs/FCM); catch-up on reconnect via `seq_num` sync |
| Typing indicators | Redis TTL key per user per conversation; Pub/Sub fan-out; never persisted |
| Presence | Redis `SET … EX 35`; heartbeat refreshes TTL; expiry = OFFLINE |
| Pagination | Cursor-based on `seq_num`; `(conversation_id, seq_num DESC)` index |
| Group fan-out | Sync for small groups; Kafka async fan-out worker for large groups |
| Reconnect storm | Jittered `delay_ms` in server-initiated reconnect frame |

**Tip for the interview:** Chat is one of the most common system design questions, and interviewers have heard the generic answers many times. Differentiate by going deep on the hard parts: the atomic `UPDATE … RETURNING` for sequence number assignment (not just "use a sequence"), exactly how cross-gateway delivery works with Redis Pub/Sub (not just "use pub/sub"), and the three-state receipt model with the buffering mechanism for offline senders. If asked about ordering, the answer "use timestamps" is a red flag — demonstrate that you know client timestamps are unreliable and that server-assigned sequence numbers are the correct primitive. For group chats, mention the fan-out scaling inflection point (sync vs async) with a concrete threshold. The candidate who explains the reconnect storm and jitter in Q25 has clearly operated a WebSocket service in production.
