# Design a Distributed Cache (Consistent Hashing, Eviction, Replication) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Estimation

**Q1. What are the functional requirements of a distributed cache?**
A: Core requirements:
- **Get:** Return the value for a given key, or a cache-miss signal if absent.
- **Set:** Store a key-value pair, optionally with a TTL.
- **Delete:** Explicitly evict a key.
- **TTL / expiry:** Automatically evict keys after a configured duration.
- **Eviction policy:** When memory is full, evict keys according to a configured policy (LRU, LFU, FIFO, random).

Extended requirements (production systems):
- **Replication:** Copies of data on multiple nodes for fault tolerance.
- **Partitioning:** Data distributed across nodes so no single node holds everything.
- **Consistency guarantees:** Define what a client sees immediately after a write (strong vs eventual).
- **Monitoring:** Hit rate, eviction rate, memory utilization, per-node health.

**Q2. What are the scale assumptions and how do they shape the design?**
A: Typical interview scale — 1 trillion requests/day, 1KB average value size, 10TB total data:
- **Read/write QPS:** 1T / 86,400 ≈ 11.5M ops/sec (peak ~3×: ~35M ops/sec).
- **Data size:** 10TB total. A single machine with 256GB RAM holds ~2.5% of the dataset — need at minimum 40 nodes, practically 60–80 with replication and headroom.
- **Latency target:** p99 < 1ms for cache hits (in-memory, same datacenter). p99 < 5ms including network.
- **Availability target:** 99.99% (< 1hr downtime/year). Requires replication — no single node failure should cause data loss or prolonged unavailability.
- **Read:write ratio:** Typically 80:20 to 95:5 for a cache. Design read path for maximum throughput.

**Q3. What are the key design decisions to call out upfront?**
A: Before diving into components, state your design axes:
- **Partitioning strategy:** How data is distributed across nodes (consistent hashing vs range partitioning vs hash-slot).
- **Replication model:** How many copies, where they live, and who can serve reads (leader-only vs any replica).
- **Consistency model:** What a client is guaranteed to see after a write (strong, eventual, read-your-own-writes).
- **Eviction policy:** What gets evicted when memory is full.
- **Client architecture:** Smart client (client knows topology, routes directly) vs proxy (client talks to a proxy that routes) vs cluster-aware (Redis Cluster model).

## Section 2: Consistent Hashing

**Q4. Why not use simple modular hashing for partitioning — what goes wrong?**
A: Simple modular hashing: `node = hash(key) % N`. Fast and easy, but catastrophic when N changes:
- Adding one node changes N from 10 to 11. Almost every key remaps to a different node (`hash(key) % 10 ≠ hash(key) % 11` for ~90% of keys).
- Every remapped key is a cache miss on the new assignment, and the old node still holds the data (now orphaned).
- Scaling up or down (node addition, node failure) causes a near-total cache invalidation, defeating the purpose of the cache and slamming the origin with misses.

**Q5. What is consistent hashing and how does it solve the remapping problem?**
A: Consistent hashing maps both keys and nodes onto a fixed ring of 2^32 positions (a "hash ring"). To find which node owns a key:
1. Hash the key to a position on the ring.
2. Walk clockwise until you hit a node.
3. That node owns the key.

When a node is added or removed, only the keys between the new/removed node and its predecessor on the ring need to remapped — typically 1/N of total keys, where N is the number of nodes. All other keys stay on the same node. This makes scaling operations cheap and cache-miss spikes proportionally small.

**Q6. What is the "virtual nodes" (vnodes) problem and solution in consistent hashing?**
A: With only one position per physical node, the ring is uneven — nodes end up owning arcs of very different sizes, causing uneven data distribution and load. Worse, when a node fails, all its keys pile onto a single successor, potentially overwhelming it.

**Virtual nodes:** Each physical node is assigned multiple positions on the ring (typically 100–200 virtual nodes per physical node, e.g., `hash("node-A-1")`, `hash("node-A-2")`, ..., `hash("node-A-150")`). Keys are spread across many more positions, and when a node fails, its virtual positions are distributed to many different successors — load is spread evenly rather than dumped on one neighbor.

```python
import hashlib
from sortedcontainers import SortedList

class ConsistentHashRing:
    def __init__(self, vnodes=150):
        self.vnodes = vnodes
        self.ring = SortedList()          # sorted list of (position, node_id)
        self.position_to_node = {}

    def add_node(self, node_id):
        for i in range(self.vnodes):
            key = f"{node_id}-{i}".encode()
            pos = int(hashlib.md5(key).hexdigest(), 16)
            self.ring.add((pos, node_id))
            self.position_to_node[pos] = node_id

    def remove_node(self, node_id):
        for i in range(self.vnodes):
            key = f"{node_id}-{i}".encode()
            pos = int(hashlib.md5(key).hexdigest(), 16)
            self.ring.remove((pos, node_id))
            del self.position_to_node[pos]

    def get_node(self, key: str) -> str:
        pos = int(hashlib.md5(key.encode()).hexdigest(), 16)
        idx = self.ring.bisect_left((pos,))
        if idx == len(self.ring):
            idx = 0                       # wrap around
        return self.ring[idx][1]
```

**Q7. How does consistent hashing handle node addition and data migration?**
A: When a new node X is added between nodes A and B on the ring:
- X's virtual positions are inserted into the ring.
- Keys that now map to X (previously mapped to B) must be migrated from B to X.
- Migration is done lazily (keys migrate on access — next write to the new owner, or miss-and-rewrite) or eagerly (a background job reads keys from B and writes them to X before traffic is shifted).
- Lazy migration is simpler but causes cache misses during the transition window. Eager migration requires coordination but achieves a cleaner cutover.
- For a 10-node cluster adding an 11th node, ~9% of keys (1/11) migrate. With 150 vnodes per physical node, this migration is spread evenly across all existing nodes, not concentrated on one.

**Q8. What is "rendezvous hashing" (highest random weight) and how does it compare to consistent hashing?**
A: Rendezvous hashing assigns each (key, node) pair a score using a hash function, and the key is assigned to the node with the highest score:

```python
def get_node(key, nodes):
    return max(nodes, key=lambda node: hash(f"{key}:{node}"))
```

**Vs consistent hashing:**
- **Consistency on change:** Both remap only a 1/N fraction of keys when a node is added/removed. Rendezvous is slightly simpler — no ring, no virtual nodes needed for even distribution.
- **Lookup cost:** Consistent hashing is O(log N) with a sorted structure. Rendezvous is O(N) — must compute hash for every node. Acceptable for small clusters (< 100 nodes), expensive for large ones.
- **Weighted nodes:** Rendezvous supports weighted nodes naturally (multiply score by weight). Consistent hashing requires proportionally more vnodes.
- **Used in:** Memcached clients, some load balancers. Less common than consistent hashing for large distributed caches.

## Section 3: Replication

**Q9. Why is replication necessary in a distributed cache?**
A: Without replication, each cache node is a single point of failure. A node crash means all keys mapped to that node are lost — every subsequent request for those keys misses the cache and hits the origin simultaneously (thundering herd). For a 10-node cluster, a single node failure exposes 10% of the keyspace to origin load instantly. With 10TB of data, that's 1TB of cache misses.

Replication also enables:
- **Read scaling:** Multiple replicas can serve reads, multiplying read throughput.
- **Hot standby for fast failover:** A replica can take over immediately on node failure, with zero or minimal data loss.
- **Geographic redundancy:** Replicas in different AZs/regions protect against datacenter-level failures.

**Q10. What are the replication models for a distributed cache?**
A: Three primary models:

**Leader-follower (primary-replica):**
- All writes go to the leader. Leader replicates to followers asynchronously (or synchronously for stronger consistency).
- Reads can go to the leader (strong consistency) or followers (eventual consistency, higher read throughput).
- Used by Redis Sentinel and Redis Cluster.

**Leaderless (multi-primary):**
- Any node can accept writes. Writes are replicated to N nodes; a write is acknowledged when W nodes confirm. A read is served when R nodes respond, and the client takes the latest version.
- Configurable consistency: W + R > N → strong consistency. W + R ≤ N → eventual.
- Used by Cassandra, DynamoDB. Less common for pure cache use cases.

**Quorum-based:**
- A specific variant of leaderless with explicit quorum parameters (N, W, R). The cache operator sets the consistency/availability trade-off numerically.

**Q11. How does Redis handle replication, and what are the trade-offs?**
A: Redis uses asynchronous leader-follower replication:
- The leader appends writes to a replication backlog and streams them to replicas.
- Replicas acknowledge once the write is applied locally.
- The leader acknowledges the write to the client *before* replicas confirm — async replication.

**Trade-offs:**
- **Performance:** Writes return fast (no waiting for replicas). High throughput.
- **Consistency:** On leader failure, replicas may not have received the last few writes. Failover (via Sentinel or Cluster) promotes a replica that may be slightly behind — potential data loss window = replication lag.
- **WAIT command:** Redis supports `WAIT numreplicas timeout` — blocks until N replicas acknowledge, giving synchronous-like behavior on demand for critical writes at the cost of latency.

**Q12. What is replication factor and how do you choose it?**
A: Replication factor (RF) = number of copies of each key stored in the cluster.
- **RF=1:** No replication. Single point of failure per partition. Acceptable only for non-critical caches where misses are cheap.
- **RF=2:** One leader + one replica. Tolerates single-node failure. Standard for non-critical production systems.
- **RF=3:** One leader + two replicas. Tolerates two simultaneous node failures (with quorum reads/writes). Standard for critical systems. Used by Cassandra's default, Kafka default.

Choose RF based on: tolerable failure scenarios, read throughput multiplication needed (each replica adds read capacity), and storage cost (RF=3 triples storage requirement).

**Q13. How does the cache handle a node failure during replication?**
A: Sequence for leader failure in a leader-follower setup:
1. **Detection:** Health check (heartbeat ping) from other nodes or a coordinator (Sentinel) detects the leader is unresponsive (typically after 3–5 seconds of missed heartbeats).
2. **Election:** The coordinator or cluster nodes elect a new leader from available replicas — typically the replica with the most up-to-date replication offset (least lag).
3. **Promotion:** The elected replica is promoted to leader. Its replication offset becomes the new baseline.
4. **Client redirect:** Clients (or the smart client library) are notified of the new leader address and redirect reads/writes.
5. **Data loss window:** Writes acknowledged by the old leader but not yet replicated to the new leader are permanently lost (async replication gap). Mitigated by synchronous replication or by accepting this bounded data loss as acceptable for cache use cases (a cache miss is not a data loss event in most systems).

## Section 4: Eviction Policies

**Q14. What eviction policies does a distributed cache typically support?**
A: When memory is full and a new key must be stored, the cache must evict an existing key. Common policies:

- **LRU (Least Recently Used):** Evict the key that has not been accessed for the longest time. Best approximation of "least likely to be accessed again" for most workloads. The default choice.
- **LFU (Least Frequently Used):** Evict the key with the lowest access count. Better than LRU for workloads where some keys are accessed very frequently over a long period but rarely recently (hot keys that go cold temporarily are not evicted by LFU).
- **FIFO (First In, First Out):** Evict the oldest-inserted key regardless of access pattern. Simple but ignores access frequency entirely. Rarely optimal.
- **Random:** Evict a random key. Surprisingly competitive with LRU in practice for uniform access patterns. Very low implementation overhead.
- **TTL-based (volatile):** Only evict keys with a TTL set, choosing the one nearest to expiry. Protects keys without TTLs from eviction. Useful when mixing persistent and ephemeral data in the same cache.
- **No eviction:** Reject new writes when memory is full. Appropriate for use cases where all data is critical (session store, not a true cache).

**Q15. How is LRU implemented at scale, and what is Redis's approximation approach?**
A: True LRU requires a doubly-linked list (for O(1) move-to-front on access) plus a hash map (for O(1) lookup). Every read must update the list — at millions of ops/sec, this linked list manipulation is a bottleneck and the list itself consumes significant memory per key (two pointers ≈ 16 bytes per entry).

**Redis's approximated LRU:** Instead of maintaining a full LRU list, Redis samples a small random set of keys (default: 5 candidates, configurable via `maxmemory-samples`) and evicts the one with the oldest `lru_clock` timestamp. This is an approximation — not perfectly LRU — but studies show 10 samples approximate true LRU within 1–2% accuracy at a fraction of the memory and CPU cost.

**Redis LFU:** Redis 4.0+ also supports LFU using a Morris counter (logarithmic counter) per key that approximates access frequency in a single byte. The counter decays over time so recently cold keys can be evicted even if historically hot.

**Q16. What is cache churn and how does eviction policy choice prevent it?**
A: Cache churn occurs when the eviction policy repeatedly evicts keys that are still needed, causing them to be re-fetched and re-evicted in a cycle. Common causes:
- **Scan-resistant workloads:** A large sequential scan (e.g., a batch job reading all products) floods the cache with single-use keys, evicting hot keys under LRU (the scan keys are the "most recent"). Fix: use LFU (scan keys have count=1) or "scan-resistant LRU" (segment the cache into probationary and protected regions — keys must be accessed twice to enter the protected region).
- **Working set larger than cache:** The hot working set exceeds cache capacity — any eviction policy churns. Fix: increase cache size or implement tiered caching (L1 in-process + L2 distributed).
- **TTL cliff:** Many keys expire simultaneously, causing a thundering herd that floods the cache with new keys, evicting each other. Fix: TTL jitter (covered in cache warming section).

**Q17. How do you handle eviction in a multi-node cluster — is eviction per-node or cluster-wide?**
A: Eviction is per-node in most distributed cache implementations (Redis Cluster, Memcached). Each node manages its own memory budget independently and evicts from its own keyspace when it hits its `maxmemory` limit. There is no cluster-wide eviction coordinator.

**Implication:** If one node's keyspace is disproportionately hot (data skew on the consistent hash ring), it may evict frequently while other nodes have abundant free memory. Mitigation:
- Virtual nodes (150+ per physical node) smooth data distribution.
- Monitor per-node eviction rate — a consistently high-eviction node signals a hot shard.
- Re-shard: add a node specifically in the ring region of the hot shard to split its keyspace.

## Section 5: Client Architecture

**Q18. What are the three client models for a distributed cache?**
A: How clients discover and route to the right cache node:

**Smart client:**
- The client library holds a copy of the cluster topology (which node owns which hash range).
- For each operation, the client computes `hash(key)` and connects directly to the owning node.
- No proxy hop — lowest latency. Client must handle topology changes (node addition, failure) by refreshing its view periodically or on redirect.
- Used by Redis Cluster clients, most Memcached clients.

**Proxy (sidecar or standalone):**
- Clients connect to a local proxy (e.g., Twemproxy/nutcracker, mcrouter). The proxy knows the cluster topology and routes requests.
- Client is simple — no topology awareness. Proxy handles sharding, failover, connection pooling.
- Extra network hop (localhost: ~0.1ms, but still adds latency). Proxy can become a bottleneck or SPOF if not replicated.
- Used by: Twitter's Twemproxy for Memcached, Facebook's mcrouter.

**Cluster-aware with server-side redirect:**
- Client connects to any node. If the node doesn't own the key, it returns a MOVED or ASK redirect telling the client which node to go to.
- Client learns the topology progressively and caches it. After a few redirects, the client goes directly to the right node.
- Used by Redis Cluster's native protocol.

**Q19. How does a smart client handle a node failure in real time?**
A: On a request failure (connection refused, timeout):
1. **Retry with replica:** If the failed node has a known replica (from the topology map), retry the read against the replica immediately.
2. **Refresh topology:** Trigger an async topology refresh from a well-known cluster endpoint (e.g., a Sentinel, a cluster coordinator, or any healthy node). Update the local routing table.
3. **Retry with new topology:** Re-attempt the failed operation against the newly mapped node.
4. **Circuit breaker on the failed node:** Mark the node as unhealthy in the client. Stop routing to it until health checks pass. Prevents repeated connection attempts to a dead node.
5. **Fallback to origin:** If the operation is a cache read and all replicas are unavailable, proceed with a cache miss (fetch from origin DB). Do not fail the application request over a cache failure.

## Section 6: Advanced Design Topics

**Q20. How do you handle hot keys (cache hotspots)?**
A: A viral key — one product, one user profile, one configuration — can receive millions of requests per second, overwhelming the single node that owns it even though the rest of the cluster is idle. Strategies:

**Local replication (read-local):**
- Cache the hot key in every service instance's local in-process L1 cache (Caffeine, Guava).
- Reads are served locally, never hitting the distributed cache for that key.
- Coherence: set a short L1 TTL (1–5 seconds) so updates propagate quickly via TTL expiry.

**Key replication with suffix:**
- Store the hot key on multiple nodes by appending a random suffix: `product:42:shard0`, `product:42:shard1`, ..., `product:42:shard9`.
- On read, the client randomly picks a suffix → distributes load across 10 nodes.
- On write, update all sharded copies (or use a short TTL so stale copies expire quickly).

**Request coalescing:**
- When many concurrent requests miss the hot key simultaneously, coalesce them: only one thread fetches from origin while others wait. On completion, all waiters receive the same result. Go's `singleflight` package is the canonical implementation.

**Q21. How do you handle large values efficiently in a distributed cache?**
A: Keys with very large values (> 1MB) cause problems: they consume disproportionate memory per key, slow down serialization/deserialization, and can saturate network bandwidth between client and cache node.

Strategies:
- **Chunking:** Split the large value into fixed-size chunks, each stored as a separate key (`obj:42:chunk:0`, `obj:42:chunk:1`, ...). A metadata key stores the chunk count. Client reads all chunks in parallel and assembles. Adds read complexity but distributes memory and network load.
- **Pointer pattern:** Store the large object in an object store (S3, GCS) and cache only the URL/pointer. The cache hit gives the client a URL; the client fetches the object directly from S3. Cache is used for URL lookups, not object storage.
- **Size limits with enforcement:** Set a hard max value size (e.g., Redis default: 512MB, but operational best practice is much lower, e.g., 10MB). Reject or compress values above the limit. Alert when large values are detected.

**Q22. How do you implement cache persistence — when does a cache need durability?**
A: Most caches are ephemeral by design — a miss is costly but not catastrophic. However, some use cases benefit from persistence:
- **Session stores:** Losing all sessions on cache restart forces all users to re-authenticate.
- **Rate limit counters:** Losing counters resets limits, allowing bursts.
- **Materialized computation results:** Expensive-to-recompute values that take minutes to regenerate after a cold start.

Redis supports two persistence mechanisms:
- **RDB (snapshotting):** Periodic fork + write of a full dataset snapshot to disk. Fast restart, but data since the last snapshot is lost on crash. Configurable interval (e.g., every 5 minutes).
- **AOF (Append-Only File):** Every write command is appended to a log. On restart, the log is replayed. Near-zero data loss (configurable fsync frequency: every write, every second, or OS-managed). Slower restart, larger file, but much stronger durability.

For a pure cache (origin exists as source of truth), RDB with a 5-minute interval is typically sufficient — the worst case is a 5-minute cold start. For a session store or rate limiter, AOF with `fsync everysec` is appropriate.

**Q23. How do you monitor a distributed cache in production?**
A: Key metrics to instrument and alert on:

- **Hit rate:** `hits / (hits + misses)`. The primary health signal. Alert if it drops more than 5% from baseline — indicates eviction, TTL misconfiguration, or origin data change invalidating keys.
- **Eviction rate:** `evicted_keys` counter. Non-zero means the cache is under memory pressure. Alert on sustained eviction rate > 0.
- **Memory utilization:** `used_memory / maxmemory` per node. Alert at 80% (approaching eviction threshold).
- **Replication lag:** For leader-follower setups, monitor `master_repl_offset - slave_repl_offset`. Alert if lag exceeds N bytes or N seconds.
- **Connection count:** Alert on connection saturation (near `maxclients` limit).
- **Command latency (p99):** Alert if GET/SET p99 exceeds threshold (e.g., > 2ms indicates overloaded node or network issue).
- **Key count per node:** Monitor for data skew — uneven key counts across nodes signal consistent hashing imbalance.

## Section 7: Scenario / System Design Style Questions

**Q24. "Walk me through the complete design of a distributed cache supporting 35M ops/sec, 10TB data, 99.99% availability."**
A: Full system architecture:

**Partitioning:** Consistent hashing with 150 virtual nodes per physical node. 60 physical nodes × 256GB RAM = ~15TB raw capacity, ~10TB usable with 30% headroom. Each node owns ~167GB of data.

**Replication:** RF=2 (leader + 1 replica per shard, replicas in a different AZ). Writes go to leader (async to replica). Reads from leader by default; replica available for read offload and failover.

**Client model:** Smart client with local topology cache. On cache miss or node failure, client refreshes topology from a Cluster Coordinator (ZooKeeper / etcd maintains the authoritative node map).

**Eviction:** `allkeys-lru` with approximated LRU (10 samples). `maxmemory-policy` set per node. TTL jitter on all writes to prevent synchronized eviction.

**Persistence:** RDB snapshots every 5 minutes to S3 (crash recovery, cold-start acceleration). No AOF (cache use case — origin is source of truth).

**Hot key handling:** L1 in-process cache (Caffeine, 10k keys, 5s TTL) on each service instance in front of the distributed cache. Hot keys are served locally.

**Write path:** `client.set(key, value, ttl)` → smart client computes hash → TCP connection to owning leader node → Redis SET with PX → async replication to replica → ACK to client. Target: < 1ms p99.

**Read path:** `client.get(key)` → L1 check (hit: return, ~0.01ms) → distributed cache leader (hit: return, ~0.5ms) → origin DB (miss, ~10ms) → populate L1 + distributed cache → return. Target: < 1ms p99 for L1+L2 hits.

**Q25. "Your distributed cache cluster is experiencing high eviction rates on two specific nodes while three others are nearly empty. What's wrong and how do you fix it?"**
A: This is a data skew problem — keys are not evenly distributed across nodes. Root causes:

**Diagnosis:**
- Check the consistent hash ring: the two hot nodes likely own disproportionately large arcs. This can happen with too few virtual nodes (e.g., 10 vnodes per node instead of 150) where statistical variance creates large arcs.
- Check for key pattern hotspots: certain key prefixes (e.g., all session keys start with `sess:`) may hash into a narrow ring region owned by the hot nodes.
- Check for skewed access patterns: even with even data distribution, some key ranges may receive far more traffic (hot shard problem, not data skew).

**Fixes:**
- **Increase virtual nodes:** If using < 100 vnodes/node, increase to 150–200. More vnodes = better statistical uniformity. Requires rehashing and data migration.
- **Add nodes in the hot arc:** Insert new nodes specifically in the ring region of the overloaded nodes. This splits their arc and redistributes their keys to the new nodes.
- **Key prefix hashing:** If keys have a common prefix causing clustering, hash the full key including a random component (`hash(key + random_salt)`), or add artificial prefix diversity to the key scheme.
- **Increase memory on hot nodes:** Vertical scale the hot nodes as a short-term mitigation while the rebalancing is planned.
- **Move to range-based partitioning with explicit shard map** if the key space has inherent structure that consistent hashing can't handle evenly.

**Q26. "A client library bug caused 10 million keys to be written without TTLs. The cache is now full and evicting hot keys. How do you remediate without taking the cache offline?"**
A: A live TTL remediation without downtime:

**Immediate mitigation:**
- Temporarily raise `maxmemory` on affected nodes (if host RAM allows) to stop eviction while remediation proceeds.
- Switch eviction policy to `volatile-lru` — only evict keys with TTLs set. The TTL-less keys won't be evicted, but at least hot keys with TTLs are protected from eviction (they won't be touched). Then set TTLs on the rogue keys (see below).

**Remediation — set TTLs without cache offline:**
- Use a background scan: `SCAN 0 COUNT 1000` iterates all keys without blocking (unlike `KEYS *`). For each key returned, check `TTL key` — if it returns -1 (no TTL), apply `EXPIRE key <appropriate_ttl>`.

```python
cursor = 0
while True:
    cursor, keys = redis.scan(cursor, count=1000)
    for key in keys:
        if redis.ttl(key) == -1:          # no TTL set
            redis.expire(key, 86400)      # set 24-hour TTL
    if cursor == 0:
        break                             # full scan complete
```

- Rate-limit the scan (sleep between batches) to avoid saturating Redis with scan commands.
- After scan completion, switch eviction policy back to `allkeys-lru`.

**Prevention:** Add a write interceptor / middleware in the cache client that enforces a maximum TTL on all writes — reject or override any SET without a TTL. Make TTL-less writes a build-time lint warning or unit test assertion.

## Quick Reference: Component Decisions Summary

| Component | Choice | Rationale |
|---|---|---|
| Partitioning | Consistent hashing + 150 vnodes | Minimal key remapping on topology change; even distribution |
| Alternative partitioning | Hash slots (Redis Cluster: 16,384 slots) | Fixed slot count, explicit slot-to-node map, simpler rebalancing |
| Replication | Leader-follower, RF=2 (async) | Tolerates single node failure; high write throughput |
| Strong consistency | RF=3 with sync replication / WAIT | For session stores, rate limiters where data loss is unacceptable |
| Eviction policy | allkeys-lru (approximated, 10 samples) | Best general-purpose approximation; low overhead |
| Eviction for mixed data | volatile-lru | Protect non-TTL keys; only evict ephemeral TTL-bearing keys |
| Client model | Smart client | Lowest latency; no proxy hop |
| Hot key mitigation | L1 in-process cache + key sharding | Absorb read spikes locally; distribute across nodes for writes |
| Persistence | RDB snapshots (cache) / AOF (session store) | Cache: fast restart, tolerate data loss. Session: near-zero loss |
| Failure detection | Heartbeat + Sentinel / Cluster bus | Fast detection (3–5s); automatic failover without operator |

**Tip for the interview:** Distributed cache questions reward structured thinking over exhaustive coverage. Open with estimation (10TB, 35M ops/sec, read-heavy → validates every subsequent component choice), then walk the three pillars in order: partitioning (consistent hashing + vnodes), replication (RF, leader-follower, async vs sync trade-off), and eviction (LRU vs LFU, per-node not cluster-wide). The questions that separate senior candidates: knowing that consistent hashing solves key remapping but not data skew (that's vnodes), knowing that async replication means accepting bounded data loss on failover (and being explicit about whether that's acceptable), and knowing that hot keys require a different solution than partitioning (L1 local cache or key sharding). End with monitoring — mentioning hit rate, eviction rate, and replication lag signals operational maturity.
