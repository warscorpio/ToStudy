# Design a Ride-Sharing Backend (Real-Time Matching, Geospatial Queries) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Estimation

**Q1. What are the functional requirements of a ride-sharing backend?**
A: Core requirements:
- **Rider:** Request a ride (pickup + destination), see nearby drivers, track driver in real time, receive fare estimate, cancel ride.
- **Driver:** Go online/offline, accept or reject ride requests, navigate to pickup, complete ride, receive earnings summary.
- **Matching:** Find the best available driver for a ride request (proximity, ETA, driver rating, vehicle type).
- **Pricing:** Calculate dynamic fare based on distance, time, surge multiplier, and vehicle type.
- **Trip lifecycle:** Manage states — `REQUESTED → MATCHED → DRIVER_EN_ROUTE → RIDER_PICKED_UP → IN_PROGRESS → COMPLETED / CANCELLED`.
- **Payments:** Charge rider, pay driver, handle refunds and disputes.
- **Ratings:** Mutual post-trip ratings (rider ↔ driver).

Non-functional: matching latency p99 < 3 seconds, location update ingestion at millions of events/sec, high availability (99.99%), geospatial query accuracy within 50 meters.

**Q2. What are the scale assumptions and how do they drive design?**
A: Uber-scale approximations:
- **Active drivers:** 1M online drivers globally, each sending location updates every 4 seconds → 250,000 location updates/sec.
- **Active riders:** 5M concurrent riders (subset actively requesting or in trips).
- **Ride requests:** 10M rides/day ≈ 115 RPS (peak ~3×: ~350 RPS) — ride creation is light.
- **Location reads (nearby drivers):** Every rider request + periodic map refreshes → ~50,000 geospatial reads/sec.
- **Trip state updates:** 10M trips/day × ~8 state transitions = 80M DB writes/day ≈ 925 writes/sec.
- **Storage:** Driver location is ephemeral (overwritten on each update). Trip history: 10M trips/day × 1KB ≈ 10GB/day → ~3.6TB/year.

**Q3. What are the key design axes to state upfront?**
A: Before component design, declare:
- **Location storage:** Where and how driver locations are stored for fast geospatial queries (Redis GEO vs PostGIS vs H3/S2 cell index).
- **Matching algorithm:** How drivers are ranked and selected for a request (nearest-first, ETA-based, fairness-weighted).
- **Communication model:** How drivers receive dispatch and riders track drivers (WebSocket, long poll, SSE, push notification).
- **Trip state machine:** Whether state is owned by a stateless service + DB or a stateful orchestrator (SAGA orchestrator, workflow engine like Temporal).
- **Surge pricing:** Real-time supply/demand ratio computation scope (cell-level, city-level).

## Section 2: Location Tracking

**Q4. How do you ingest 250,000 driver location updates per second?**
A: A dedicated Location Service with a write-optimized ingestion pipeline:

```
Driver App → WebSocket / gRPC → Location Gateway
                                      ↓
                                 Kafka (topic: driver-locations)
                                      ↓
                        Location Consumer (updates Redis GEO)
                                      ↓
                          Redis GEO (current positions)
                                + ↓
                          Location History Store (optional, for replay / auditing)
```

- **WebSocket / gRPC** — persistent connections from driver app. Avoids HTTP handshake overhead per update. Location Gateway maintains connections (stateful) but is horizontally scalable.
- **Kafka** — decouples ingestion from processing. Absorbs bursts. Partitioned by `driver_id` so updates for the same driver are ordered. At 250k updates/sec with a 200-byte payload, Kafka throughput is ~50MB/sec — well within capacity.
- **Location Consumer** — reads from Kafka, batches updates, and writes to Redis GEO using pipelining. Batch writes reduce per-update Redis round trips.
- **Redis GEO** — stores current position. Each update overwrites the previous. The effective storage is O(active drivers) ≈ 1M entries × ~50 bytes = ~50MB — trivially fits in memory.

**Q5. How does Redis GEO work and why is it suited for this use case?**
A: Redis GEO stores geographic coordinates using a Geohash-based encoding inside a sorted set. Each member (e.g., `driver_id`) is stored with a score derived from its latitude/longitude encoded as a 52-bit integer, giving ~0.6m precision.

Key commands:
```
GEOADD drivers:active <lng> <lat> <driver_id>   # insert/update position
GEOPOS drivers:active <driver_id>               # get position
GEODIST drivers:active <id1> <id2> km           # distance between two members
GEOSEARCH drivers:active FROMLONLAT <lng> <lat> BYRADIUS 5 km ASC COUNT 20
# → returns up to 20 driver IDs within 5km, sorted nearest-first
```

**Why suited:** GEOSEARCH is O(N+log M) where N is results and M is total members — fast even with 1M drivers. Returns sorted by distance in one round trip. Redis processes all GEO operations in-memory, achieving sub-millisecond latency. Atomic updates via single-command GEOADD prevent race conditions.

**Q6. What are the alternatives to Redis GEO for geospatial indexing?**
A:
- **PostGIS (PostgreSQL extension):** Full geospatial SQL — `ST_DWithin`, `ST_Distance`, spatial indexes (GIST). Excellent for complex queries (polygon containment, route intersection), but higher latency than in-memory Redis for simple radius searches. Best for analytics, surge zone computation, and historical trip data — not for real-time driver lookup under 250k updates/sec.
- **H3 (Uber's hexagonal grid):** Divides the world into hierarchical hexagonal cells. Encode driver position as an H3 cell ID at a chosen resolution (~1km² at resolution 8). Store `cell_id → [driver_ids]` in Redis. To find nearby drivers: compute the target cell + its ring-1/ring-2 neighbors, union the driver lists. Extremely fast for fixed-radius queries; naturally supports multi-resolution (coarsen cell for sparse areas, fine for dense). Used in Uber's production H3 geospatial system.
- **S2 (Google's spherical geometry):** Similar to H3 but uses square cells on a sphere. Used by Google Maps, Lyft, and others. S2 cell covering allows flexible region queries.
- **Quadtree / R-tree:** Spatial tree structures. Used in PostGIS's GIST index. Good for complex shapes; more overhead than H3/S2 for simple radius queries.

**Q7. How do you handle location updates for drivers who are offline or in a completed trip?**
A: Driver location is only relevant when the driver is available for matching. Two approaches:
- **Namespace by status:** Maintain separate Redis GEO sets: `drivers:available`, `drivers:en_route`, `drivers:in_trip`. On status change, move the driver between sets using a Lua script (atomic). The matching service only queries `drivers:available`. Drivers who go offline are removed from all sets.
- **Status flag in GEO data:** Keep all active drivers in one GEO set but store status in a separate Redis hash (`HSET driver:{id} status available`). The matching service queries GEO for nearby drivers then bulk-fetches their status to filter. Simpler to maintain but requires a second round trip.

**Preferred:** Separate GEO sets per availability status. The matching service's most critical query (`GEOSEARCH drivers:available`) is always performed on the smallest relevant set.

## Section 3: Matching Service

**Q8. Walk through the end-to-end flow of a ride request.**
A:
```
1. Rider submits request (pickup lat/lng, destination, vehicle type)
2. Matching Service receives request
3. Query Redis GEO: GEOSEARCH drivers:available FROMLONLAT <pickup> BYRADIUS 5km ASC COUNT 50
4. Filter candidates: vehicle type match, minimum rating, no active dispatch
5. Rank candidates: ETA to pickup (use routing engine), driver score, wait time fairness
6. Select top candidate → create a Dispatch record (trip_id, driver_id, status=PENDING)
7. Notify driver via push + WebSocket: "Ride available, accept within 10s"
8a. Driver accepts → update trip status to MATCHED, notify rider with driver ETA
8b. Driver rejects / timeout → remove from candidate pool, try next candidate
9. If no driver accepts after N candidates → expand search radius and retry
```

**Q9. How do you rank driver candidates beyond simple proximity?**
A: Nearest-first is a starting point, but production matching uses a multi-factor score:
- **ETA to pickup** — actual driving time via the routing engine, not straight-line distance. A driver 2km away on a direct road may have lower ETA than one 1km away across traffic.
- **Driver rating** — weight higher-rated drivers slightly higher to maintain quality.
- **Acceptance rate** — drivers who frequently decline waste matching latency. Deprioritize low-acceptance-rate drivers.
- **Idle time / wait time fairness** — drivers who have been waiting longer get a slight boost. Prevents starvation (one driver never receiving requests because they're always 50 meters behind a competitor).
- **Vehicle type match** — hard filter: a rider requesting an SUV only matches SUV-capable drivers.
- **Supply-demand balance** — in high-demand areas, slightly expand the match radius to pull in drivers from adjacent zones.

```python
def score_driver(driver, pickup, routing_engine):
    eta = routing_engine.get_eta(driver.location, pickup)       # seconds
    eta_score      = max(0, 1 - eta / 600)                      # normalize 0–1 (0 if >10min)
    rating_score   = (driver.rating - 4.0) / 1.0                # normalize 4.0–5.0 → 0–1
    fairness_score = min(1, driver.idle_seconds / 300)           # boost after 5min idle
    return 0.6 * eta_score + 0.3 * rating_score + 0.1 * fairness_score
```

**Q10. How do you prevent the same driver from being dispatched to multiple riders simultaneously?**
A: Race condition: two riders request rides simultaneously, both get driver D in their candidate list, and both dispatch to D concurrently. D can only accept one.

Prevention layers:
- **Optimistic lock on dispatch:** When creating a Dispatch record, use a unique constraint `(driver_id, status=PENDING)` — only one pending dispatch per driver at a time. The second insert fails, triggering the matching service to try the next candidate.
- **Redis lock per driver:** Before dispatching to a driver, acquire a short-lived Redis lock: `SET dispatch:lock:{driver_id} {trip_id} NX PX 15000` (15-second TTL). Only the lock winner dispatches to that driver. On driver accept/reject, the lock is released.
- **Driver state machine in Redis:** Driver status transitions atomically: `AVAILABLE → DISPATCHING → EN_ROUTE`. Use a Lua script for atomic check-and-set. If `GEOADD` + status update is not atomic, a small window exists where two matchers see the driver as available simultaneously.

**Q11. What happens when no drivers are available within the initial search radius?**
A: Progressive expansion with backoff:
1. Initial search: 3km radius, wait up to 10 seconds for acceptance.
2. On timeout/full rejection: expand to 5km, retry.
3. On second timeout: expand to 8km, retry.
4. On third timeout: notify rider of estimated wait time, optionally queue the request and notify matching service to retry when a driver becomes available in the area.
5. Hard timeout (e.g., 2 minutes): cancel the request and notify the rider to try again.

Additionally, during expansion: relax soft filters (lower minimum rating threshold slightly, include drivers finishing nearby trips within 2 minutes). Never relax hard filters (vehicle type, license status).

## Section 4: Real-Time Communication

**Q12. How do drivers and riders receive real-time updates?**
A: Three mechanisms, each suited to different scenarios:

**WebSocket (bidirectional, persistent):**
- Best for: driver app (receives dispatch, sends location, receives navigation updates), rider app during active trip (driver location stream, ETA updates).
- Each connected client holds a persistent TCP connection to a WebSocket Gateway server.
- WebSocket Gateway is stateful (connection affinity) but horizontally scalable — client reconnects on gateway restart.
- Messages are pushed server-to-client without polling.

**Server-Sent Events (SSE, unidirectional push):**
- Best for: rider waiting for driver (receive ETA updates, driver location updates).
- Simpler than WebSocket for one-way push. Automatically reconnects. Works over HTTP/2.

**Push Notifications (FCM / APNs):**
- Best for: driver app when backgrounded (dispatch notification wakes the app).
- Not suitable as the sole real-time mechanism — delivery delay varies (1–30 seconds), not guaranteed.
- Used as a fallback when the app loses WebSocket connection.

**Q13. How do you route a server-side event to the right client's WebSocket connection?**
A: The WebSocket Gateway is stateless in routing but stateful in connections. The problem: when driver D is at location (lat, lng), the Matching Service needs to notify D's driver app — which is connected to WebSocket Gateway instance 3 out of 10.

Solution — publish/subscribe via Redis Pub/Sub or Kafka:
```
Matching Service → publishes to Kafka topic: notifications
                   key: driver_id (ensures ordering per driver)
                        ↓
WebSocket Gateway instances (all subscribe to notification stream)
                        ↓
Each Gateway checks its in-memory connection map:
  if driver_id is connected to this Gateway → push message
  else → discard (the right Gateway will handle it)
```

Alternatively: use a Redis Pub/Sub channel per driver (`channel: driver:{driver_id}`). The Gateway instance holding D's connection subscribes to that channel on connection establishment, and unsubscribes on disconnect.

**Q14. How does the rider track the driver in real time during the trip?**
A: Driver location updates flow:
```
Driver App → WebSocket → Location Gateway → Kafka (driver-locations)
                                                    ↓
                                         Location Fan-out Service
                                           reads from Kafka,
                                           identifies active trips,
                                           publishes to rider's WebSocket channel
                                                    ↓
                                         WebSocket Gateway → Rider App
```

The fan-out service maintains a `trip_id → rider_id` mapping (in Redis). For each driver location update, if the driver is in an active trip, it publishes the update to the rider's channel. This adds ~100–200ms additional latency to location updates (Kafka hop) — acceptable for a map UI refreshing every 4 seconds.

**Optimization:** During active trips, the Location Gateway can also directly push to the fan-out service via a shared Kafka topic rather than going through Redis, reducing hops.

## Section 5: Data Model & Storage

**Q15. What is the core data model for trips and how is it stored?**
A: Primary entities:

**`trips` table (PostgreSQL):**
```sql
CREATE TABLE trips (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rider_id        UUID NOT NULL REFERENCES users(id),
    driver_id       UUID REFERENCES drivers(id),   -- nullable until matched
    status          trip_status NOT NULL,           -- enum
    pickup_lat      DOUBLE PRECISION NOT NULL,
    pickup_lng      DOUBLE PRECISION NOT NULL,
    dropoff_lat     DOUBLE PRECISION,
    dropoff_lng     DOUBLE PRECISION,
    vehicle_type    VARCHAR(20) NOT NULL,
    fare_estimate   NUMERIC(10,2),
    fare_actual     NUMERIC(10,2),
    surge_multiplier NUMERIC(4,2) DEFAULT 1.0,
    requested_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    matched_at      TIMESTAMPTZ,
    pickup_at       TIMESTAMPTZ,
    dropoff_at      TIMESTAMPTZ,
    cancelled_at    TIMESTAMPTZ,
    cancel_reason   TEXT
);

CREATE TYPE trip_status AS ENUM (
    'REQUESTED', 'MATCHING', 'MATCHED', 'DRIVER_EN_ROUTE',
    'RIDER_PICKED_UP', 'IN_PROGRESS', 'COMPLETED', 'CANCELLED'
);

CREATE INDEX idx_trips_rider    ON trips(rider_id, requested_at DESC);
CREATE INDEX idx_trips_driver   ON trips(driver_id, requested_at DESC);
CREATE INDEX idx_trips_status   ON trips(status) WHERE status NOT IN ('COMPLETED', 'CANCELLED');
```

**`drivers` table:**
```sql
CREATE TABLE drivers (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id),
    license_number  TEXT UNIQUE NOT NULL,
    vehicle_type    VARCHAR(20) NOT NULL,
    rating          NUMERIC(3,2) DEFAULT 5.0,
    rating_count    INT DEFAULT 0,
    is_active       BOOLEAN DEFAULT false,          -- currently online
    current_trip_id UUID REFERENCES trips(id)
);
```

**Redis (ephemeral, real-time):**
- `drivers:available` — GEO set of available driver positions.
- `drivers:en_route` — GEO set of en-route driver positions.
- `driver:{id}:status` — current driver state (AVAILABLE, DISPATCHING, EN_ROUTE, IN_TRIP).
- `dispatch:lock:{driver_id}` — distributed lock for dispatch race prevention.
- `trip:{id}:state` — current trip state (hot path, avoids DB read on every state check).
- `surge:{cell_id}` — current surge multiplier per geospatial cell.

**Q16. How do you manage the trip state machine reliably?**
A: Trip state must be durable and transitions must be atomic. Two approaches:

**DB-owned state machine:**
- Each state transition is an UPDATE with an optimistic lock: `UPDATE trips SET status='MATCHED', driver_id=$1, matched_at=now() WHERE id=$2 AND status='MATCHING'`.
- Rows-affected=0 means another process already transitioned this trip — the caller retries or aborts.
- Simple, durable, auditable. Every state is in PostgreSQL.

**SAGA orchestrator (Temporal / AWS Step Functions):**
- The Matching Service is a workflow. Each step (find drivers, dispatch, wait for acceptance, notify rider) is a Temporal activity with built-in retry, timeout, and compensation.
- Handles complex scenarios: dispatch timeout → retry with next driver, payment failure → cancel trip, driver cancels mid-route → find replacement driver.
- Adds operational complexity (Temporal cluster) but makes the business logic explicit, testable, and resilient.

**Recommendation:** DB-owned state machine for the trip table (always, for durability), optionally wrapped with a Temporal workflow for complex orchestration logic. The DB is the source of truth; Temporal is the coordinator.

## Section 6: Surge Pricing & Supply-Demand

**Q17. How do you compute surge pricing in real time?**
A: Surge pricing increases fares when demand exceeds supply in a geographic area. Implementation:

**Cell-based computation:**
1. Divide the city into geographic cells (H3 resolution 7 ≈ 5km² per cell, ~1,000 cells per major city).
2. Every 30 seconds, a Surge Service computes per-cell:
   - `supply` = count of available drivers in the cell + adjacent cells.
   - `demand` = count of active ride requests in the cell in the last 5 minutes.
   - `ratio` = demand / max(supply, 1).
3. Apply surge function: `multiplier = max(1.0, min(5.0, 1 + (ratio - 1) * surge_sensitivity))`.
4. Write `surge:{cell_id} → multiplier` to Redis with a 60-second TTL.

**On fare estimate:**
- Compute pickup cell → fetch `surge:{cell_id}` from Redis → multiply base fare.
- If the cell key is absent (expired or never computed), default to multiplier=1.0.

**Smooth transitions:** To avoid jarring price jumps, cap the surge change per interval (e.g., multiplier can move at most 0.2 per 30-second window). Gradual ramp-up and ramp-down.

**Q18. How do you handle the surge pricing notification to riders?**
A: Transparency is a product requirement (and in some regions, a legal one):
- Always show the surge multiplier explicitly before the rider confirms the request.
- For surge > 1.5×, require the rider to type the multiplier (e.g., "2.0×") to confirm — reduces accidental high-fare bookings and support complaints.
- Notify riders in the app if surge increases significantly while they are waiting for a driver (before pickup — they may want to cancel and wait).
- Driver earnings are also shown with surge component clearly — incentivizes drivers to move toward high-demand areas.

## Section 7: Advanced Design Topics

**Q19. How do you handle driver ETA computation at scale?**
A: Straight-line distance (Haversine formula) is a poor ETA proxy in urban environments (buildings, one-way streets, traffic). Production ETA computation:

**Routing Engine Integration:**
- Maintain an internal routing engine (OSRM, Valhalla) or use a third-party API (Google Maps Routes API, HERE).
- For matching candidate ranking (Q9), ETA is computed for the top 10–20 candidates in parallel — fan-out requests to the routing engine.
- Cache ETA results in Redis: `eta:{driver_id}:{pickup_cell}` with a 30-second TTL. Nearby drivers often have similar ETAs to the same cell — cache reuse reduces routing engine load.
- For lower-accuracy but faster matching, use straight-line distance with a traffic-adjusted factor (urban: multiply by 2.5; highway: multiply by 1.2).

**Traffic-aware routing:**
- Ingest real-time traffic data (from driver GPS traces — Uber uses its own fleet's speed data as a traffic signal).
- Build a traffic-weighted road graph. Update edge weights every few minutes.
- Use Dijkstra or A* on the weighted graph for ETA computation.

**Q20. How do you handle driver cancellation after matching?**
A: Driver cancellation mid-trip is a poor experience and must be managed:

**After acceptance, before pickup:**
- Allow driver cancellation with a reason (rider not at location, safety concern).
- Penalize repeated pre-pickup cancellations (affects driver acceptance rate score, eventually leading to deactivation).
- On driver cancel: immediately re-enter the rider's request into the matching queue with the same search parameters. Notify rider "Your driver cancelled, finding a new one."
- Re-matching is treated as high priority — use a smaller radius initially (the replacement driver should be nearby) with a shorter timeout.

**After pickup (in-trip cancellation):**
- Safety feature — rider or driver can end the trip early.
- Driver ending trip early: flag for review, no fare charged, rider issued a credit.
- Rider ending trip early: partial fare based on distance/time traveled.

**Q21. How do you design for multiple cities and regions?**
A: Multi-region architecture:

**Geographic sharding:**
- Partition the system by city or region. Each city cluster has its own: Location Service + Redis GEO, Matching Service, Surge Pricing Service. Trips are local — a ride in Mumbai is never dispatched to a Mumbai driver by a Lagos server.
- A global layer handles: user accounts, driver profiles, payments, cross-region analytics.

**Data residency:**
- Many regions (EU, India) have data residency requirements — rider and driver PII must stay within the region's DB cluster.
- Trip data stored in the regional PostgreSQL cluster. Analytics replicated to a global warehouse for cross-regional insights.

**Driver migration between cities:**
- A driver can be active in multiple cities (if they travel). Their position update must route to the correct city's Redis GEO. Client sends city_id with each update; the Location Gateway routes to the appropriate city cluster.

**Q22. How do you prevent fraud and abuse in the matching system?**
A: Key fraud vectors and mitigations:

**GPS spoofing (driver faking location to appear closer):**
- Cross-validate GPS with cell tower triangulation and accelerometer data.
- Flag drivers whose reported speed between consecutive updates implies physically impossible movement.
- ML model on location patterns — known fraudulent patterns (stationary driver reporting movement, sudden teleportation).

**Trip fraud (driver taking longer routes to inflate fare):**
- Compare actual route taken (from GPS trace) to optimal route from routing engine.
- Flag trips where actual distance exceeds optimal by > 20% for review.
- Rider-facing route display during trip — riders can see if the driver is detouring.

**Fake accounts (demand spoofing — rider bots inflating demand to trigger surge, then cancelling):**
- Rate-limit ride requests per account.
- Penalize accounts with high request-without-ride-completion rates.
- ML fraud model on request patterns (time of day, location, historical behavior).

## Section 8: Scenario / System Design Style Questions

**Q23. "Walk me through the complete system design for a ride-sharing backend."**
A: Component map and responsibilities:

**Rider/Driver Apps** → mobile clients sending location (driver), ride requests (rider), real-time updates via WebSocket.

**API Gateway** → auth (JWT validation), rate limiting, routes to appropriate backend service.

**Location Service:**
- Ingests 250k driver location updates/sec via WebSocket → Kafka → Redis GEO.
- Namespaced GEO sets per driver status: `drivers:available`, `drivers:en_route`, `drivers:in_trip`.

**Matching Service:**
- GEOSEARCH on `drivers:available` for candidates within radius.
- Scores candidates (ETA, rating, fairness).
- Dispatches to top candidate with Redis distributed lock.
- Manages dispatch timeout and retry loop.
- Publishes match events to Kafka for downstream services.

**Trip Service:**
- Owns trip state machine in PostgreSQL.
- Processes state transitions (REQUESTED → MATCHED → EN_ROUTE → ...).
- Exposes REST APIs for trip lifecycle (rider: cancel, driver: accept/reject/complete).

**Notification Service:**
- Subscribes to Kafka events (match, state change, driver location).
- Fans out to WebSocket Gateway (real-time) and Push Notification Service (background).

**WebSocket Gateway:**
- Maintains persistent connections for active riders and drivers.
- Routes inbound messages to appropriate services.
- Delivers outbound notifications from Kafka.

**Surge Pricing Service:**
- Periodic H3 cell supply/demand computation.
- Writes surge multipliers to Redis with TTL.
- Exposes surge multiplier for fare estimates.

**Routing Engine:**
- Internal OSRM or external routing API.
- Computes ETA and optimal route.
- Traffic-weighted graph updated from fleet GPS traces.

**Trip History / Analytics:**
- PostgreSQL (primary, regional) for trip records.
- Kafka → ClickHouse for analytics (trips per hour, driver earnings, demand heatmaps).

**Payments Service:**
- Triggered on trip completion.
- Charges rider, distributes driver earnings.
- Separate service with its own DB and retry logic (SAGA pattern for payment + payout atomicity).

**Q24. "250,000 driver location updates per second is overwhelming your Redis GEO writes. How do you scale the write path?"**
A: Multiple levels of optimization:

**Batch writes via pipelining:**
The Location Consumer doesn't write one-by-one. It buffers 100ms of updates and issues them as a Redis pipeline — all `GEOADD` commands sent in one round trip. Reduces round trips from 250k/sec to ~2,500 pipeline batches/sec.

**Deduplicate stationary drivers:**
If a driver hasn't moved more than 10 meters since the last update, skip the Redis write. Roughly 30–40% of "updates" are effectively no-ops (driver waiting at a light, parked). Filter in the Location Consumer before writing.

**Shard Redis GEO by city/region:**
Split `drivers:available` into `drivers:available:city:{city_id}`. Each city cluster has its own Redis instance. No single Redis node handles all 250k updates — each handles its city's subset. Matching Service queries the correct city's Redis.

**Increase update interval for non-critical states:**
Drivers in an active trip (in `drivers:in_trip`) don't need 4-second updates for matching purposes (they're not candidates). Reduce their update frequency to 10 seconds. Only `drivers:available` and `drivers:en_route` need high-frequency updates. Reduces write volume by 40–60% depending on the trip-to-available ratio.

**Q25. "A driver accepts a ride but the rider cancels 2 minutes later, while the driver is already en route. How does the system handle this, and what does the driver receive?"**
A: Full lifecycle with compensation:

**Cancellation detection:**
- Rider calls `POST /trips/{trip_id}/cancel` with reason.
- Trip Service validates: is the trip in a cancellable state for the rider? Trip is `DRIVER_EN_ROUTE` — rider can cancel but may incur a cancellation fee.

**Fee computation:**
- Calculate if the driver has been en route beyond the free cancellation window (e.g., 2 minutes after acceptance). If yes, charge the rider a cancellation fee (e.g., flat $5 or time-based).

**Driver notification:**
- Trip Service transitions trip to `CANCELLED`.
- Publishes `TripCancelledEvent` to Kafka.
- Notification Service delivers cancellation push + WebSocket message to driver immediately.
- Driver app stops navigation, shows cancellation reason and any cancellation fee earned.

**Driver compensation:**
- If driver was en route past the free window, they receive the cancellation fee (after platform cut).
- Driver status transitions back to `AVAILABLE` — they are immediately re-eligible for new requests.
- Their current location is re-added to `drivers:available` GEO set.

**Fairness adjustment:**
- The cancelled trip does not count against the driver's acceptance rate (they accepted and were cancelled on).
- Rider's cancellation rate is tracked — high cancellation rates affect their access to the service.

**Q26. "How would you design the system to handle 10× traffic during a major event (New Year's Eve, stadium event end)?"**
A: Planned surge handling vs organic growth:

**Pre-event preparation:**
- Pre-scale the Location Service, Matching Service, and WebSocket Gateway to 10× capacity 30 minutes before the expected surge. Kubernetes HPA pre-scaling based on event schedule (not reactive — proactive).
- Warm Redis with current driver locations. No cold cache concern since location updates are continuous, but ensure Redis cluster has enough memory headroom.
- Pre-compute surge multipliers for the event area at higher frequency (every 10 seconds instead of 30 seconds).

**During the surge:**
- **Geofenced matching:** For riders near the event venue, restrict initial matching to a smaller radius (1km) with higher driver density — prevents distant drivers from being dispatched and then caught in the outgoing traffic.
- **Queue-based matching:** Instead of immediate matching, queue requests and process in priority order (time of request, rider rating, distance from driver). Prevents system overload from simultaneous dispatch storms.
- **Degraded features:** Disable non-critical features (scheduled rides, in-app chat) to reduce load on shared services. Kill switch via feature flags.
- **Rider wait time transparency:** Surface accurate wait times based on current matching queue depth. "Currently 8-minute wait" is better UX than a spinner that eventually times out.

**Load shedding:**
- If matching service queue depth exceeds threshold, return a 503 with `Retry-After: 30s` to new ride requests rather than accepting them into an overloaded system. Clear to the rider ("We're experiencing high demand, please try again in 30 seconds") rather than silently failing.

## Quick Reference: Component Decisions Summary

| Component | Choice | Rationale |
|---|---|---|
| Location storage | Redis GEO (current) + Kafka (stream) | Sub-ms reads, overwrites on update, 50MB for 1M drivers |
| Geospatial indexing | Redis GEOSEARCH + H3 cells for surge | Fast radius query; H3 for cell-level supply/demand aggregation |
| Location write path | WebSocket → Kafka → batch Redis writes | Decouples ingestion from storage; batch reduces round trips |
| Matching algorithm | ETA-weighted score (ETA + rating + fairness) | Proximity alone is suboptimal; ETA accounts for real road network |
| Dispatch race prevention | Redis NX lock + DB unique constraint | Dual-layer: lock prevents concurrent dispatch, DB prevents duplicate |
| Trip state machine | PostgreSQL with optimistic lock | Durable, auditable, atomic transitions via conditional UPDATE |
| Complex orchestration | Temporal for retry/compensation flows | Explicit workflow, built-in timeout + retry, testable |
| Real-time communication | WebSocket (driver + active rider) + push (background) | Persistent connection for low-latency; push as fallback |
| WebSocket routing | Kafka pub/sub per driver/rider channel | Decouples notification producers from WebSocket gateway instances |
| Surge pricing | H3 cell supply/demand ratio, 30s interval | Cell granularity balances accuracy vs computation cost |
| Routing / ETA | Internal OSRM + Redis ETA cache (30s TTL) | Avoid per-request external API cost; cache for nearby drivers |
| Analytics | PostgreSQL → Kafka → ClickHouse | OLTP for trip records; OLAP for demand heatmaps, earnings reports |

**Tip for the interview:** Ride-sharing backends test your ability to connect three hard problems simultaneously — geospatial data at write scale (250k location updates/sec), low-latency matching under contention (dispatch race prevention), and real-time bidirectional communication (routing events to the right WebSocket connection). Cover all three explicitly and early. The most common gaps: treating driver location as a simple DB write (it's a high-frequency stream that needs Kafka buffering), not addressing the dispatch race condition (two matchers dispatching the same driver), and forgetting about the WebSocket routing problem (how a server-side event reaches a specific client connection on a specific gateway instance). End with the surge handling scenario — it ties together geospatial cells, supply/demand computation, and graceful degradation under load, which is exactly what a senior interviewer wants to see connected.
