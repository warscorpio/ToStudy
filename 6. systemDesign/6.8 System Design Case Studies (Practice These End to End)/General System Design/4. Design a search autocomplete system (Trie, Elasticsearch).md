# Design a Search Autocomplete System — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a search autocomplete system?**
A: Core functional requirements:
- **Prefix completion** — given a partial query string typed by the user, return the top-N (typically 5–10) suggested completions ranked by relevance/popularity.
- **Low latency** — suggestions must appear as the user types; P99 < 100ms end-to-end including network. Ideally < 50ms from the server's perspective.
- **Personalization (optional)** — surface suggestions relevant to the user's history, location, or context ahead of globally popular ones.
- **Typo tolerance (optional)** — handle minor misspellings ("samsng" → "samsung"); fuzzy matching.
- **Trending / recency** — blend globally popular queries with recently trending ones; a query that spiked in the last hour should surface before a stale popular one.
- **Safe search / content filtering** — filter inappropriate suggestions based on user context or regional policy.
- **Multi-language / Unicode support** — handle non-ASCII characters; CJK prefix matching behaves differently from Latin scripts.

**Q2. What are the non-functional requirements?**
A:
- **Throughput** — autocomplete is one of the highest-traffic endpoints in any search product; every keystroke is a request. At 10M DAU with users averaging 5 searches/day and 4 keystrokes per search, that's ~2,300 RPS at average; peak can be 5–10x. The system must handle this without degradation.
- **Freshness** — suggestion rankings should reflect query popularity updated at least hourly; trending topics ideally within minutes.
- **Availability** — a slow or unavailable autocomplete degrades user experience but is not catastrophic (users can still search without suggestions). Design for graceful degradation: if the autocomplete service is down, the search box still works.
- **Storage efficiency** — a Trie over millions of query strings with popularity scores must fit in memory for the lowest latency tier. Memory is the primary constraint, not disk.
- **Read-heavy workload** — writes (index updates) are infrequent relative to reads (every keystroke). Optimize aggressively for read performance.

**Q3. What are the two primary architectural approaches, and when do you choose each?**
A:
- **Trie-based (in-memory)** — build a prefix tree over the query corpus; each node stores top-N completions for that prefix. Sub-millisecond lookup, purely in-memory, horizontally scalable. Best for: simple prefix completion, very high throughput requirements, controlled vocabulary (product catalog, airport codes). Limitations: no typo tolerance, no full-text ranking, complex to update in real-time, memory-bound.
- **Elasticsearch-based** — use ES's `completion` suggester or `search_as_you_type` field type. Handles fuzzy matching, rich ranking (BM25 + boosting), personalization via re-ranking, and full-text features. Best for: general search with typo tolerance, complex ranking, multi-field suggestions (title + category + brand). Limitations: higher latency (5–30ms per query vs < 1ms for Trie), more operational overhead, overkill for simple prefix use cases.

In practice: many large systems use a Trie for the fast popular-queries path and Elasticsearch for the long-tail / fuzzy path, with the Trie result taking priority when it returns a full result set.

## Section 2: Trie Design

**Q4. What is a Trie and how does it work for autocomplete?**
A: A Trie (prefix tree) is a tree data structure where each node represents a character and the path from the root to a node spells out a prefix. For autocomplete, each node additionally stores a list of the top-N most popular completions for that prefix — so a lookup for prefix "sea" directly returns ["search", "seattle", "seaworld", ...] in one traversal to the node, without iterating all descendants.

```
root
 ├── s
 │    └── e
 │         └── a         top-5: ["search","seattle","sea","seafood","seal"]
 │              ├── r
 │              │    └── c
 │              │         └── h   top-5: ["search engine","search bar",...]
 │              └── t
 │                   └── t
 │                        └── l
 │                             └── e  top-5: ["seattle weather","seattle times",...]
 └── ...
```

**Q5. What does the Trie node structure look like in code?**
A:

```typescript
interface TrieNode {
  children:    Map<string, TrieNode>;
  isEndOfWord: boolean;
  topK:        Array<{ query: string; score: number }>; // pre-computed at build time
}

class Trie {
  root: TrieNode = { children: new Map(), isEndOfWord: false, topK: [] };

  insert(query: string, score: number): void {
    let node = this.root;
    for (const char of query.toLowerCase()) {
      if (!node.children.has(char)) {
        node.children.set(char, { children: new Map(), isEndOfWord: false, topK: [] });
      }
      node = node.children.get(char)!;
      // Merge into topK at each node along the path
      this.mergeTopK(node.topK, { query, score }, K);
    }
    node.isEndOfWord = true;
  }

  search(prefix: string): Array<{ query: string; score: number }> {
    let node = this.root;
    for (const char of prefix.toLowerCase()) {
      if (!node.children.has(char)) return [];
      node = node.children.get(char)!;
    }
    return node.topK; // O(prefix_length) lookup; top-K already computed
  }

  private mergeTopK(
    topK: Array<{ query: string; score: number }>,
    entry: { query: string; score: number },
    k: number
  ): void {
    topK.push(entry);
    topK.sort((a, b) => b.score - a.score);
    if (topK.length > k) topK.pop();
  }
}
```

**Q6. Why store top-K completions at every node instead of traversing descendants at query time?**
A: Traversing descendants to find the top-K completions at query time is O(number of completions under that prefix) — for a common prefix like "a", that's potentially millions of descendants. Storing the pre-computed top-K at each node reduces lookup to O(prefix_length), which is at most O(~20) for any realistic query. The trade-off is increased memory (each node stores K entries instead of just its children) and increased build/update complexity, but for a read-heavy system serving thousands of RPS, the lookup time reduction is worth it.

**Q7. How do you build the Trie from query log data?**
A: The build pipeline runs periodically (hourly or daily):

```
Raw query logs (Kafka / S3)
        │
        ▼
[Aggregation job — Spark / Flink]
  - Filter: remove PII queries (email addresses, phone numbers via regex)
  - Filter: remove single-char and nonsense queries
  - Count: query frequency in the last 7 days (or weighted: recent days weighted higher)
  - Output: (query, score) pairs sorted by score descending
        │
        ▼
[Trie builder — single-threaded or partitioned]
  - Insert all (query, score) pairs
  - Serialize to binary format (protobuf / custom)
  - Upload to S3/GCS: trie-YYYY-MM-DD-HH.bin
        │
        ▼
[Autocomplete servers — rolling reload]
  - Each server polls S3 for new Trie version
  - Load new Trie into memory alongside the current one
  - Atomic pointer swap: new requests use the new Trie
  - Release old Trie (GC)
```

The atomic pointer swap is critical — during the reload, the server serves from the old Trie, with zero downtime or partial-state serving.

**Q8. How do you handle real-time trending queries that shouldn't wait for the hourly batch rebuild?**
A: Two-layer approach:
- **Batch Trie** (rebuilt hourly/daily) — covers all historical popular queries with stable rankings.
- **Trending overlay** (updated every few minutes) — a small in-memory map of queries that have spiked in the last 15–60 minutes. At query time, merge the Trie results with the trending map; trending entries get a boost or are injected at the top of the list.

The trending map is computed by a stream processor (Flink / Kafka Streams) counting query frequency in a sliding window and publishing the top-100 trending queries to Redis. The autocomplete server reads the trending map from Redis on each request (or caches it locally for 30 seconds).

**Q9. What is the memory footprint of a Trie and how do you manage it?**
A: A naïve Trie is memory-inefficient — each node is a separate heap object with a `Map` of children. For 10 million unique queries:
- Each character in a query = one node.
- Average query length = 20 chars → ~200M nodes.
- Each node with K=10 top entries ≈ 500 bytes → ~100GB. Infeasible.

Optimizations:
- **DAWG (Directed Acyclic Word Graph)** — merge shared suffixes as well as prefixes; reduces node count by 60–80%.
- **Compressed Trie / Patricia Trie** — merge single-child nodes into edge labels; reduces node count proportional to branching factor.
- **Limit depth** — only index prefixes up to length N (e.g., 20 chars); queries longer than N are served by a fallback (Elasticsearch).
- **Shard by first character** — distribute the Trie across multiple servers, each responsible for a subset of the alphabet. Reduces per-server memory to 1/26th (roughly).
- **Serialized flat array** — instead of heap-allocated objects, serialize the Trie to a flat byte array using DFS traversal with offsets. Cache-friendly; much lower memory overhead than pointer-per-child node maps.

In practice, a compressed Trie covering 5M queries with K=5 completions fits in ~2–4GB of RAM per shard — reasonable for a modern server.

## Section 3: Elasticsearch Approach

**Q10. What Elasticsearch features are used for autocomplete?**
A: Two purpose-built features:

**`search_as_you_type` field type** (ES 7.2+):
- Creates sub-fields that index the original value plus all prefix and shingle (n-gram) variations.
- Supports efficient prefix matching via the `bool_prefix` query type.
- Example mapping:
```json
{
  "mappings": {
    "properties": {
      "suggest": {
        "type": "search_as_you_type",
        "max_shingle_size": 3
      }
    }
  }
}
```
Query:
```json
{
  "query": {
    "multi_match": {
      "query": "sea",
      "type": "bool_prefix",
      "fields": ["suggest", "suggest._2gram", "suggest._3gram"]
    }
  }
}
```

**`completion` suggester**:
- A dedicated FST (Finite State Transducer) data structure optimized for prefix lookups; stored in memory in the JVM heap.
- Faster than `search_as_you_type` for pure prefix completion but less flexible (no BM25 ranking, no filter queries on other fields).
- Best for: autocomplete on a single field (product name, airport name) where ranking is purely by weight.

**Q11. When do you use `completion` suggester vs `search_as_you_type`?**
A:
- **`completion` suggester** — when you need the absolute fastest prefix matching within ES, and ranking is determined entirely by a pre-assigned weight (popularity score). No support for filtering by other fields at query time (filters must be applied via `context` mappings defined at index time). Use for: city names, product catalog where all ranking is pre-computed.
- **`search_as_you_type`** — when you need to combine prefix matching with BM25 relevance scoring, filter by other fields (category, in-stock status, user's country), or support phrase matching across multiple words. More flexible, slightly higher latency. Use for: general search where ranking involves multiple signals.

**Q12. How do you handle typo tolerance in Elasticsearch autocomplete?**
A: Use `fuzziness` in the query:

```json
{
  "query": {
    "multi_match": {
      "query": "samsng",
      "type": "bool_prefix",
      "fields": ["suggest", "suggest._2gram"],
      "fuzziness": "AUTO"
    }
  }
}
```

`fuzziness: "AUTO"` sets edit distance 0 for strings < 3 chars, 1 for 3–5 chars, 2 for > 5 chars. This handles single-character transpositions and omissions. Caveat: fuzzy prefix matching is expensive (ES evaluates all terms within edit distance of the prefix) — apply `prefix_length: 2` to fix the first 2 characters and only apply fuzziness to the remainder, dramatically reducing the candidate space.

**Q13. How do you rank autocomplete results in Elasticsearch beyond simple prefix match?**
A: Multi-signal ranking using function score:

```json
{
  "query": {
    "function_score": {
      "query": {
        "multi_match": {
          "query": "sea",
          "type": "bool_prefix",
          "fields": ["suggest"]
        }
      },
      "functions": [
        {
          "field_value_factor": {
            "field": "popularity_score",
            "modifier": "log1p",
            "factor": 1.5
          }
        },
        {
          "gauss": {
            "updated_at": {
              "origin": "now",
              "scale": "7d",
              "decay": 0.5
            }
          }
        }
      ],
      "score_mode": "multiply"
    }
  }
}
```

Ranking signals to combine:
- **Query frequency** (last 7/30 days) — primary signal for popularity.
- **Recency decay** — down-rank stale queries; up-rank recently trending ones.
- **Click-through rate** — queries that led to clicks are better suggestions than ones users abandoned.
- **Personalization boost** — at re-ranking stage (post-ES), boost queries matching the user's history.
- **Exact prefix match boost** — a result that starts with the exact prefix ranks above one that matches mid-string.

## Section 4: System Architecture

**Q14. What does the end-to-end architecture look like?**
A:

```
User types "sea..."
        │
        │  GET /autocomplete?q=sea&uid=<user_id>
        ▼
┌─────────────────────────────────────────┐
│         API Gateway / CDN               │

│    prefixes (TTL: 60s)                  │

                   │
                   ▼
┌─────────────────────────────────────────┐

│                                         │

│  2b. (fallback / fuzzy) ES query        │
```

**Q15. How do you implement caching at multiple levels?**
A: Autocomplete is extremely cache-friendly — the same prefix ("se", "sea", "sear") is typed by thousands of users simultaneously. Cache at three layers:

**CDN cache** (for non-personalized responses):
- Cache key: `prefix` (normalized: lowercased, trimmed).
- TTL: 60 seconds. Stale suggestions for 60 seconds is acceptable; the ranking won't change meaningfully faster.
- Covers ~80% of traffic (most queries hit popular prefixes).
- Don't cache personalized responses (include `uid` in the cache key → cache miss always; defeats the purpose).

**Application in-process cache** (LRU):
- Language-level LRU cache (Node.js: `lru-cache`; Java: Caffeine) keyed by normalized prefix.
- Capacity: ~50,000 entries (popular prefixes are short strings; 50k entries ≈ a few MB).
- TTL: 30 seconds.
- Eliminates Trie/Redis/ES round-trips for the hottest prefixes.

**Redis cache** (for personalized responses):
- Key: `autocomplete:{user_id}:{prefix}`.
- TTL: 5 minutes.
- Only populated for users who have fetched this prefix; don't pre-warm.

**Q16. How do you handle request debouncing on the client side?**
A: Without debouncing, a user typing "search" generates 6 requests (s, se, sea, sear, searc, search) within ~500ms. Most of these are wasted — the user doesn't see the intermediate results. Client-side strategies:
- **Debounce** — wait N ms after the last keystroke before sending a request (typical: 100–150ms). A fast typist generates 1–2 requests instead of 6 per word. Trade-off: suggestions appear later for slow typists.
- **Request cancellation** — send every request but cancel the previous one if a new keystroke arrives before the response returns. Works well with `AbortController` in browsers. Ensures freshness without waiting for debounce timeout.
- **Minimum prefix length** — don't request completions until the user has typed at least 2–3 characters. Single-character prefixes generate enormous result sets and are rarely useful.

Combining debounce (100ms) with minimum length (2 chars) reduces server load by 70–80% compared to a naïve implementation.

**Q17. How do you scale the autocomplete service horizontally?**
A: The autocomplete service is stateless (the Trie is read-only after loading) — horizontal scaling is straightforward:
- Run N identical instances behind a load balancer; any instance can serve any request.
- Each instance holds its own copy of the Trie in memory (shared-nothing; no distributed Trie needed — the Trie is read-only so there's no consistency problem).
- Instances reload the Trie from S3 independently on a schedule; a 5-minute window where different instances have different Trie versions is acceptable (the Tries are successive snapshots, not conflicting states).
- Scale based on CPU (Trie lookups are CPU-bound) and memory (each instance needs RAM for the full Trie). A single large Trie (2GB) on an 8GB instance leaves headroom for 3x traffic spikes before memory becomes the bottleneck.

## Section 5: Scoring & Ranking

**Q18. How do you compute the popularity score for a query?**
A: Raw frequency is a poor score — a query popular 6 months ago but abandoned recently ranks higher than a currently trending one. Better approach:

**Time-decayed frequency:**
```
score(query) = Σ (count_in_window_i × decay_factor^i)

where:
  window_i = day i (0 = today, 1 = yesterday, ...)
  decay_factor = 0.9 (10% decay per day)
```

This gives recent queries a natural advantage without explicitly filtering by date. Implemented in the Spark/Flink aggregation job that processes query logs.

**Additional signals to blend into the score:**
- **Click-through rate** — if a query leads to a result click, it's a quality suggestion. Up-weight by CTR: `final_score = frequency_score × (1 + ctr_boost)`.
- **Session completion rate** — queries where the user found what they needed (didn't reformulate immediately) are better suggestions.
- **Spam/bot filtering** — queries from non-human sources (crawlers, load tests) must be filtered before scoring; they artificially inflate frequency.

**Q19. How do you personalize autocomplete suggestions?**
A: Personalization adds user-specific signals on top of global popularity:

**Sources of personalization signals:**
- **User's search history** — queries the user has typed before; surface them first if they match the prefix.
- **User's click history** — products, articles, or entities the user has clicked; boost related queries.
- **User's location** — geo-relevant completions ("coffee" → "coffee near downtown Seattle" for a Seattle user).
- **User's language / locale** — prefer completions in the user's language.

**Implementation — re-ranking (not re-indexing):**
Don't personalize at the Trie/ES layer — the index is shared across all users. Instead:
1. Fetch top-20 global suggestions from the Trie/ES.
2. Fetch user's personal signals from a user profile service (Redis-cached, < 5ms).
3. Re-rank the 20 candidates using a simple scoring function: `personalized_score = global_score × (1 + personal_boost)`.
4. Return the top-5 re-ranked results.

Re-ranking 20 candidates in-memory takes < 1ms and keeps the personalization complexity out of the index.

## Section 6: Data Pipeline

**Q20. How does the query log pipeline work end-to-end?**
A:

```
User searches → query logged to Kafka topic: "search.queries"
  Fields: {query, user_id, timestamp, session_id, result_clicked: bool}

Flink streaming job (15-min sliding window, 5-min slide):
  - Parse and normalize queries (lowercase, trim, remove PII)
  - Filter: drop queries < 2 chars, drop queries matching PII patterns
  - Aggregate: count per query in window
  - Output to Kafka topic: "autocomplete.scores" {query, window_count}

Spark batch job (hourly, full 7-day window):
  - Read all query events from S3 (partitioned by hour)
  - Apply time-decay weighting (recent days weighted higher)
  - Join with CTR data from clickstream logs
  - Output: (query, final_score) sorted descending — top 5M queries
  - Feed into Trie builder

Trie builder (triggered after Spark job):
  - Consume top-5M (query, score) pairs
  - Build compressed Trie; serialize to binary
  - Upload to S3: s3://autocomplete-trie/trie-{timestamp}.bin
  - Write pointer to latest version: s3://autocomplete-trie/LATEST

Autocomplete service instances:
  - Poll S3/LATEST every 10 minutes
  - If new version: download, load into memory, atomic swap
```

**Q21. How do you detect and filter PII from query logs?**
A: Users accidentally type PII into search boxes (email addresses, phone numbers, partial SSNs, credit card numbers). Including these in the Trie would surface another user's PII as a suggestion — a serious privacy violation.

Filtering approach in the Flink pipeline:
```typescript
const PII_PATTERNS = [
  /\b[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}\b/i,  // email
  /\b\d{3}[-.]?\d{3}[-.]?\d{4}\b/,                 // US phone
  /\b\d{3}-\d{2}-\d{4}\b/,                         // SSN pattern
  /\b(?:\d[ -]*?){13,16}\b/,                        // credit card
];

function isPII(query: string): boolean {
  return PII_PATTERNS.some(p => p.test(query));
}
```

Additionally: apply a frequency threshold — only include queries seen at least K times (e.g., K=5) across different users. A PII query typed by one person is filtered out; a genuine popular query typed by thousands passes through.

## Section 7: Scenario Questions

**Q22. "Autocomplete is returning suggestions that are offensive or brand-damaging. How do you handle it?"**
A: Multi-layer content filtering:

1. **Blocklist at build time** — maintain a curated blocklist of terms (slurs, competitor brand attacks, legally problematic phrases). The Trie builder filters out any query matching blocklist terms before insertion. Updated by a content policy team; hot-reloaded without a full Trie rebuild.
2. **Blocklist at serve time** — a second blocklist check at the autocomplete service before returning results, for terms added after the last Trie build. Redis SET; `SISMEMBER` check in < 1ms per suggestion.
3. **Safe search mode** — per-user or per-surface flag that enables a stricter filter (adult content removed regardless of popularity).
4. **Frequency floor** — very low-frequency queries (< 50 occurrences) don't make it into the Trie regardless of content; this naturally filters most long-tail offensive content.
5. **Reactive removal** — when a problematic suggestion is reported, add it to the serve-time blocklist immediately (Redis, takes effect in seconds) and schedule removal from the next Trie build.

**Q23. "Users in Japan type in Hiragana/Katakana. How do you adapt the Trie-based system?"**
A: CJK and kana scripts require different treatment than Latin:
- **Character-level Trie still works** — Japanese kana are individual Unicode code points; the Trie operates on Unicode characters, not bytes. A Trie node per kana character is correct.
- **Tokenization** — Japanese text often lacks spaces between words. For multi-word completions in Japanese, the prefix is a kana sequence, not a space-delimited token. The Trie must store kana sequences directly.
- **Romanization / IME input** — users may be mid-IME-composition when the request fires (typing "sa" to produce "さ"). The autocomplete service should accept both the romaji input and the composed kana and query both Tries (or a combined one that indexes both forms).
- **Normalization** — normalize full-width ASCII to half-width; normalize Katakana to Hiragana (or index both); handle dakuten (voiced marks) in both composed (が) and decomposed (か + ゛) Unicode forms.
- **Segmentation for Chinese** — Chinese has no character boundaries between words; use a segmentation library (jieba for Simplified Chinese) to split query logs into meaningful prefix units before Trie insertion.

**Q24. "Your autocomplete Trie takes 3 minutes to rebuild. A PR is pushed that causes a bug in the Trie builder — all instances reload a corrupt Trie. How do you recover?"**
A: This is a classic "bad deploy to shared infrastructure" failure. Recovery:
1. **Immediate mitigation** — the autocomplete service should validate the loaded Trie before the atomic pointer swap: check that the node count, memory size, and a sample of known popular queries return expected results. A Trie with 0 nodes or corrupted results fails validation and the service keeps the previous version. This should have caught the corruption.
2. **S3 versioned rollback** — S3 object versioning is enabled on the Trie bucket. Roll back by pointing `LATEST` to the previous version's S3 key; all instances pick up the rollback on next poll (within 10 minutes).
3. **Manual trigger** — don't wait for the poll interval; push a manual reload signal (a message to a Redis pub/sub channel that all instances subscribe to) that triggers an immediate re-fetch.
4. **Fallback to ES** — if the Trie is unavailable or corrupted and rollback takes time, route all autocomplete traffic to the Elasticsearch fallback. Latency degrades (5–30ms vs < 1ms) but suggestions remain correct.
5. **Post-mortem** — add the Trie validation step if it was missing; add a canary deployment for Trie updates (one instance gets the new Trie first; wait 5 minutes for error rate signal before rolling out to all instances).

**Q25. "How would you support autocomplete for a product search where suggestions should respect inventory availability (don't suggest out-of-stock products)?"**
A: Inventory state changes too frequently (seconds to minutes) to be baked into the Trie at build time. Layered approach:

1. **Index-time filtering (coarse)** — only include products with `availability: IN_STOCK` in the Trie/ES index at build time. Eliminates products that have been out-of-stock for days/weeks. Works for the majority of cases.
2. **Serve-time filtering (fine)** — fetch top-20 suggestions from the Trie/ES; batch-check their inventory status against a low-latency inventory cache (Redis; updated in near-real-time from inventory events). Filter out out-of-stock results before returning top-5. The inventory cache lookup for 20 product IDs via `MGET` takes < 2ms.
3. **Graceful degradation** — if the inventory cache is unavailable, don't block autocomplete; return unfiltered results with a backend flag. Showing an out-of-stock product in autocomplete is a minor UX issue; blocking the entire autocomplete on inventory service unavailability is worse.
4. **Popularity-adjusted ranking** — products with low inventory should be down-ranked (they'll go out of stock soon and generate bad UX if suggested). Add `inventory_level` as a ranking signal in the score function.

## Quick Comparison: Trie vs Elasticsearch

| Aspect | Trie (in-memory) | Elasticsearch |
|--- |--- |--- |
| Lookup latency | < 1ms | 5–30ms |
| Typo tolerance | None (exact prefix) | Native (`fuzziness`) |
| Ranking flexibility | Pre-computed at build time | Rich (BM25 + function score) |
| Real-time updates | Batch rebuild (hourly) | Near-real-time (seconds) |
| Memory requirements | High (full Trie in RAM) | Moderate (FST in JVM heap) |
| Operational complexity | Low (stateless binary) | High (cluster management) |
| Multi-field search | No | Yes |
| Best for | High-throughput exact prefix | General search with fuzzy + rich ranking |

The systems layer differentiators: multi-level caching strategy (CDN → in-process LRU → Redis), client-side debouncing as a first-class concern, and the atomic pointer swap for zero-downtime Trie reloads. If the interviewer asks about scale, ground it in numbers: "at 10M DAU with 4 keystrokes per search, that's ~2,300 RPS average, so the in-process cache eliminates 80% of Trie lookups for common prefixes."
