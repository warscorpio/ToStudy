# Design a Logging and Monitoring System — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scoping

**Q1. What are the functional requirements of a logging and monitoring system?**
A: Before designing, establish scope clearly:
- **Log ingestion**: Collect structured logs from every service, host, and infrastructure component — at high throughput, with minimal impact on the emitting service.
- **Log storage and querying**: Store logs durably, index them for fast full-text and field-level queries, and support time-range filtering, aggregation, and correlation by `trace_id` or `request_id`.
- **Metrics collection**: Scrape or receive numeric time-series data from every service and infrastructure component — counters, gauges, histograms.
- **Alerting**: Evaluate metric and log-based rules continuously; notify the right people through the right channel (PagerDuty, Slack, email) with context-rich alerts.
- **Dashboards**: Visualise system health, SLO burn rates, business metrics, and per-service RED metrics in real time.
- **Distributed tracing integration**: Correlate logs and metrics to traces — jump from a log line to its trace, from a metric spike to an exemplar trace.
- **Retention management**: Enforce per-tier retention policies — hot storage for recent logs, warm/cold for older logs, with configurable TTLs per log level and service.
- **Access control**: Restrict log access by team, service, and data sensitivity — PII-containing logs must not be accessible to all engineers.

**Q2. What are the non-functional requirements?**
A:
- **Durability**: No log line or metric data point should be silently dropped under normal operating conditions. Loss is acceptable only under extreme backpressure, and only for low-priority log levels (DEBUG/INFO), never for ERROR/FATAL.
- **Latency**: Log lines should be queryable within 5–10 seconds of emission. Metric data points should be scrapeable within 15–60 seconds. Alerts should fire within 1–2 minutes of a threshold breach.
- **Throughput**: A mid-size platform emits 50,000–500,000 log lines per minute. Large-scale: tens of millions per minute. The ingestion pipeline must handle peak bursts without head-of-line blocking.
- **Query performance**: A log search over the last 1 hour of data across all services should return in under 5 seconds for most queries. Metric queries over 30-day windows should return in under 2 seconds.
- **Scalability**: Ingest and storage layers must scale horizontally. Indexing must not become a bottleneck as log volume grows.
- **Cost efficiency**: Log storage is the dominant cost driver. Tiered storage (hot → warm → cold → archive) with compression and sampling is essential at scale.
- **High availability**: The monitoring system must be more available than the systems it monitors. Alerts must fire even if some components of the monitoring system itself are degraded.

**Q3. What are the core entities in a logging and monitoring system?**
A: The domain model:
- **Log entry**: `{timestamp, level, service, host, trace_id, span_id, correlation_id, event, message, fields:{}, stack_trace?}` — the atomic unit of log data.
- **Log stream**: A named, labelled source of log entries — e.g., `{service="payment-service", env="prod", region="ap-south-1"}`. The unit of ingestion and retention policy.
- **Metric series**: A named time series with labels — `{__name__="http_request_duration_seconds", service="payment-service", method="POST", status="200"}`.
- **Alert rule**: A query + threshold + duration + severity + notification target — the definition of a condition worth waking someone up for.
- **Alert instance**: A firing alert — `{rule_id, labels, state: firing|resolved, fired_at, resolved_at, annotations}`.
- **Dashboard**: A collection of panels — each panel is a metric query, a log query, or a trace view rendered as a graph, table, or stat.
- **Retention policy**: `{log_stream_selector, hot_retention_days, warm_retention_days, cold_retention_days}`.

## Section 2: High-Level Architecture

**Q4. What are the major components of a logging and monitoring system?**
A: Six logical layers:

```
Services / Infrastructure
(emit logs to stdout, expose /metrics endpoints)
          |
          ▼
  [1] Collection Layer
      Log collectors: Fluent Bit / Vector (per node)
      Metric scrapers: Prometheus / OTel Collector
          |
          ▼
  [2] Ingestion / Transport Layer
      Log pipeline: Kafka (high-volume buffer)
      Metric pipeline: Remote Write / OTLP push
          |
          ▼
  [3] Storage Layer
      Logs: Loki / Elasticsearch / OpenSearch
      Metrics: Prometheus TSDB / Thanos / Cortex
      Traces: Tempo / Jaeger
          |
          ▼
  [4] Query & Processing Layer
      LogQL / PromQL / TraceQL
      Log parsing, enrichment, aggregation
          |
          ▼
  [5] Alerting Layer
      Prometheus Alertmanager / Grafana Alerting
      PagerDuty / Slack / Email routing
          |
          ▼
  [6] Visualisation Layer
      Grafana (unified: logs + metrics + traces)
      SLO dashboards, RED dashboards, business dashboards
```

Each layer is independently scalable and replaceable. The Kafka buffer in the ingestion layer is the key architectural decision — it decouples log emission rate from storage write capacity and prevents backpressure from reaching the emitting services.

**Q5. Why use Kafka as a buffer in the log ingestion pipeline?**
A: Without a buffer between collectors and storage:
- **Storage slowdowns cascade to services**: If Elasticsearch is slow to index, Fluent Bit's buffer fills, and log emission from the service blocks — adding latency to the service's request path.
- **No replay on storage failure**: If the log storage cluster goes down, in-flight logs are lost. Kafka retains logs for a configurable window (e.g., 24 hours) — if storage recovers, the consumer replays from the last committed offset.
- **No fan-out**: The same log stream can be consumed by multiple downstream systems simultaneously — Elasticsearch for full-text search, Loki for label-based querying, an alerting stream processor, and a SIEM (security information and event management) system — all from the same Kafka topic.
- **Throughput decoupling**: Kafka absorbs bursts. A deploy that causes a spike in ERROR logs doesn't overwhelm Elasticsearch; the consumer drains at storage's sustainable rate.

The trade-off: Kafka adds operational complexity and ~5–10 seconds of additional latency between log emission and queryability. For most operational use cases this is acceptable. For real-time security alerting, a parallel stream processor (Flink, Spark Streaming) reads from the same Kafka topic without waiting for storage indexing.

**Q6. What is the collection layer, and how does it work in a Kubernetes environment?**
A: In Kubernetes, log collection is handled by a DaemonSet — one collector pod per node that tails the stdout/stderr of all containers on that node:

```
Node
├── app-pod-1 → stdout → /var/log/containers/app-pod-1.log
├── app-pod-2 → stdout → /var/log/containers/app-pod-2.log
└── Fluent Bit DaemonSet
    ├── INPUT: tail /var/log/containers/*.log
    ├── FILTER: parse JSON, add k8s metadata (pod, namespace, node)
    ├── FILTER: drop DEBUG logs in prod (log level filter)
    └── OUTPUT: Kafka topic `logs.prod`
```

Fluent Bit is preferred over Fluentd for resource efficiency — it uses ~10MB RAM vs Fluentd's ~40MB, critical when running on every node. Key Fluent Bit configuration concerns:
- **Tail from the beginning on restart**: Use `DB` path persistence so Fluent Bit resumes from where it left off after a crash — no log lines skipped.
- **Buffer size**: Configure `Mem_Buf_Limit` to prevent Fluent Bit from consuming unbounded memory under a storage backpressure event. Set to a few hundred MB per node.
- **Kubernetes metadata enrichment**: The `kubernetes` filter automatically adds `pod_name`, `namespace`, `container_name`, `node_name` to every log line — critical for filtering in storage.
- **Multi-line log handling**: Stack traces span multiple lines; configure the `multiline` parser to reassemble them into a single log entry before shipping.

## Section 3: Log Storage & Querying

**Q7. How do you choose between Elasticsearch/OpenSearch and Grafana Loki for log storage?**
A: The fundamental difference is the indexing strategy:

| Aspect | Elasticsearch / OpenSearch | Grafana Loki |
|---|---|---|
| Indexing | Full inverted index on every field | Index only on labels (low-cardinality); log lines stored as compressed chunks |
| Query power | Full-text search, complex aggregations, any-field queries | Label-filtered queries first, then grep within chunks |
| Storage cost | High — indexing is expensive in CPU and disk | Low — 10–20× cheaper than Elasticsearch for the same volume |
| Query speed | Fast on any indexed field | Fast on labels; slower for unindexed full-text search |
| Cardinality limit | High — can index high-cardinality fields | Low — high-cardinality labels cause chunk explosion |
| Operational complexity | High — cluster management, shard sizing, index lifecycle | Lower — stateless querier + object storage backend |
| Best for | Security/audit logs, full-text search, complex analytics | Application logs, high volume, cost-sensitive, Grafana-native |

For a fintech platform with mixed needs: use **Loki for application/service logs** (high volume, label-filtered, Grafana-native correlation with metrics and traces) and **Elasticsearch for audit/compliance logs** (require full-text search, complex field queries, and long retention with rich querying).

**Q8. How does Loki store and query logs?**
A: Loki stores logs in two parts:
- **Index**: A mapping from label sets (e.g., `{service="payment-service", level="error", env="prod"}`) to chunk IDs. Small and fast to query. Stored in an object store (S3) or a key-value store (Cassandra, BoltDB).
- **Chunks**: Compressed blocks of log lines for a given label set and time range, stored in object storage (S3/GCS). Loki reads chunks only for the matching label sets, then applies grep/regex within the chunk.

A LogQL query: `{service="payment-service", level="error"} |= "card_declined" | json | duration > 200ms`:
1. The label selector `{service="payment-service", level="error"}` queries the index → list of chunk IDs.
2. Loki fetches those chunks from S3.
3. The filter `|= "card_declined"` applies a grep within each chunk.
4. The parser `| json` extracts fields from each matching line.
5. The expression `| duration > 200ms` filters on the parsed field.

Query performance implication: **always start with the most selective label selector** to minimise chunks fetched from S3. A query without a label selector scans every chunk — catastrophically slow and expensive.

**Q9. What is an index lifecycle policy, and how do you manage log retention?**
A: Logs have drastically different value over time — a log from 5 minutes ago is precious for debugging an active incident; a log from 6 months ago is rarely read. Tiered storage manages this cost/access trade-off:

```
Hot tier (0–7 days):   SSD-backed, fast random access, full indexing
                        Cost: ~$0.25/GB/month
                        Use: active incident debugging, alerting

Warm tier (7–30 days): HDD-backed, slower, compressed
                        Cost: ~$0.06/GB/month
                        Use: post-incident review, trend analysis

Cold tier (30–90 days): Object storage (S3 Glacier)
                         Cost: ~$0.004/GB/month
                         Use: compliance audits, rare retrospective queries

Archive (90+ days):     S3 Glacier Deep Archive
                         Cost: ~$0.00099/GB/month
                         Use: regulatory retention (RBI mandates 5–7 years for financial records)
```

In Elasticsearch: Index Lifecycle Management (ILM) policies automate tier transitions. In Loki: retention is configured per stream selector with a TTL. Key fintech consideration: ERROR and FATAL logs, audit logs, and payment transaction logs have longer mandatory retention than DEBUG/INFO application logs. Configure per-log-level and per-service retention policies, not a single global TTL.

**Q10. How do you handle high-cardinality fields in log queries efficiently?**
A: High-cardinality fields — `user_id`, `order_id`, `trace_id` — cannot be primary label selectors in Loki (too many unique label sets = too many tiny chunks). They must be stored in the log line body, not as labels, and queried after a label-filtered chunk fetch:

```logql
-- Wrong: high-cardinality label → chunk explosion
{user_id="usr_42", service="payment-service"}

-- Correct: low-cardinality labels first, then field filter
{service="payment-service", level="error"} | json | user_id="usr_42"
```

In Elasticsearch, `user_id` can be a document field and queried directly — but with high cardinality it increases index size significantly. Use `keyword` type (not `text`) for ID fields to avoid unnecessary full-text analysis. For very high cardinality, use doc_values and avoid aggregating on these fields unless absolutely necessary.

## Section 4: Metrics Collection & Storage

**Q11. How does Prometheus scrape and store metrics, and what are its scaling limits?**
A: Prometheus uses a pull model — it scrapes HTTP `/metrics` endpoints at a configured interval (default: 15s). Each scrape fetches all time series the target currently exposes in Prometheus exposition format:
```
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="POST",status="200",endpoint="/payments"} 4523
http_requests_total{method="POST",status="500",endpoint="/payments"} 12
```
Prometheus stores scraped data in its local TSDB — a write-optimised columnar storage with chunk-based compression (typically 1–2 bytes per sample). Scaling limits:
- **Cardinality ceiling**: A single Prometheus instance becomes unstable beyond ~10M active time series. High-cardinality labels (`user_id`, `session_id`) are the primary cause of cardinality explosion.
- **Single-node storage**: Prometheus doesn't replicate or shard natively — local TSDB is bounded by a single node's disk. Long-term retention (>15 days) is impractical on local storage.
- **No global query view**: Two Prometheus instances scraping different service clusters can't be queried together without federation.

Solutions: **Thanos** (sidecar uploads blocks to S3, global querier across instances) or **Cortex/Mimir** (horizontally scalable, multi-tenant Prometheus backend). For managed simplicity: Grafana Cloud or AWS Managed Service for Prometheus.

**Q12. What is remote write, and how does it extend Prometheus for long-term storage?**
A: Remote write is a Prometheus feature that forwards metric samples to an external storage backend in near-real-time as they are scraped. Configured in `prometheus.yml`:
```yaml
remote_write:
  - url: "https://thanos-receive.internal:10908/api/v1/receive"
    queue_config:
      max_samples_per_send: 10000
      batch_send_deadline: 5s
```
Prometheus continues using its local TSDB for recent data (fast queries); remote write simultaneously streams samples to long-term storage (Thanos, Cortex, Grafana Cloud). This gives you: fast local query for recent data, long-term queryable history, and cross-instance global view — without changing how services expose metrics.

**Q13. How do you prevent metric cardinality explosion?**
A: Cardinality = the product of the number of unique values of each label. `{service, endpoint, status_code}` with 10 services × 50 endpoints × 10 status codes = 5,000 series — manageable. Adding `user_id` with 1M unique users → 5,000 × 1,000,000 = 5 billion series — catastrophic. Prevention:
- **Never use high-cardinality values as metric labels**: No `user_id`, `order_id`, `session_id`, `trace_id`, `IP address` as Prometheus labels. These belong in logs and traces, not metrics.
- **Enumerate label values in code review**: Require a metric cardinality estimate as part of any new metric addition — the number of unique label combinations must be bounded and small.
- **Monitor cardinality in production**: `prometheus_tsdb_head_series` gauge tracks active series count. Alert if it grows unexpectedly. Use the Prometheus TSDB analysis tool (`tsdb analyze`) to identify top cardinality contributors.
- **Use recording rules to pre-aggregate**: Instead of a metric per user, record `payment_success_rate` per `{service, endpoint}` — a recording rule computes it and stores the aggregated result as a new series.

**Q14. What are recording rules, and when do you use them?**
A: Recording rules pre-compute frequently-used or expensive PromQL expressions and store the result as a new time series, updated on each evaluation cycle. Defined in Prometheus rule files:
```yaml
groups:
  - name: payment_aggregations
    interval: 60s
    rules:
      - record: job:payment_success_rate:rate5m
        expr: |
          rate(payment_requests_total{status="success"}[5m])
          /
          rate(payment_requests_total[5m])
```
Use recording rules when:
- A PromQL expression is used in multiple dashboards and alerts — compute once, query many times.
- A query scans many time series and is slow to evaluate at query time — pre-aggregate to a smaller result set.
- A dashboard must load fast — dashboard panels backed by recording rules return in milliseconds vs seconds for complex live queries.
- Alert rules use complex expressions — complex alerting PromQL evaluated every 15 seconds adds CPU load to Prometheus; recording rules reduce this to a simple series lookup.

## Section 5: Alerting

**Q15. What makes a good alert rule?**
A: An alert should fire when a human needs to act, and only then. The common failures:
- **Too sensitive**: Fires on every transient blip — engineers ignore it ("alert fatigue"). The alert loses its meaning.
- **Too insensitive**: Fires after the incident has already been noticed by users — the alert is decorative.
- **No context**: "High error rate" with no link to a runbook, no recent deployment info, no affected service scope — the on-call engineer must reconstruct all context from scratch at 3am.

A good alert rule has:
- **A `for` duration**: The condition must hold for N minutes before firing — eliminates transient spikes. `for: 2m` is a common starting point.
- **Severity labels**: `severity: critical` (page immediately), `severity: warning` (Slack notification, investigate during business hours).
- **Runbook annotation**: A link to a step-by-step runbook — `runbook_url: "https://wiki.internal/runbooks/payment-error-rate"`.
- **Summary and description templates**: Human-readable alert title and body using label interpolation — `"Payment error rate {{ $value | humanizePercentage }} on {{ $labels.service }}"`.
- **Alert on symptoms, not causes**: Alert on "user-visible error rate > 1%" not "CPU > 80%". CPU at 80% may be fine; a 1% error rate definitely isn't.

**Q16. What is alert fatigue, and how do you combat it?**
A: Alert fatigue is the state where engineers stop treating alerts as meaningful signals because too many fire, too often, for things that don't require action. It's one of the most damaging failure modes of a monitoring system — the alert that matters gets ignored because it arrives alongside 20 that don't. Remediation:
- **Audit every alert**: Monthly review — for every alert that fired in the last 30 days, ask "did a human take action because of this alert?" If no, delete or demote it.
- **Require actionability**: An alert with no runbook action is a noise source. Every alert must have a defined response.
- **Use `for` durations**: Never alert on a single data point. Require sustained breach.
- **Alert on error budget burn rate, not raw metrics**: "Your 30-day error budget will be exhausted in 2 hours at the current burn rate" is more actionable than "error rate is 2.1% right now."
- **Group and deduplicate in Alertmanager**: `group_by: [service, alertname]` — don't fire 50 individual alerts for 50 pods all experiencing the same issue; fire one grouped alert.
- **Time-based inhibition**: Suppress low-severity alerts during a known maintenance window or after a deployment (a short grace period before alert evaluation begins).

**Q17. What is SLO-based alerting (error budget burn rate), and how does it improve on threshold alerting?**
A: Traditional threshold alerting ("error rate > 1% for 2 minutes") has two failure modes: it fires too many false positives for brief spikes (too sensitive) and misses slow-burning degradations that never breach the threshold at any instant but steadily consume the error budget (too insensitive).

Error budget burn rate alerting triggers based on how fast the error budget is being consumed, not on instantaneous metric values:
```
# Error budget burn rate alert
# SLO: 99.9% availability → error budget = 0.1% = 43.2 min/month
# Alert: if burn rate > 14.4×, budget exhausted in 2 hours

alert: PaymentSLOBurnRateHigh
expr: |
  (
    rate(payment_requests_total{status=~"5.."}[1h])
    /
    rate(payment_requests_total[1h])
  ) / 0.001 > 14.4
for: 2m
labels:
  severity: critical
annotations:
  summary: "Payment SLO error budget burning at {{ $value }}× rate — exhaustion in < 2h"
```
This alert fires when the actual error rate is high enough to exhaust the monthly budget in 2 hours — regardless of whether the instantaneous rate crosses any fixed threshold. It also naturally ignores brief blips: a 5-minute spike at 2× burn rate (which would fire a threshold alert) consumes only 5/43,200 = 0.01% of the monthly budget — not worth waking someone up.

**Q18. How does Alertmanager route, group, and deduplicate alerts?**
A: Alertmanager is a separate process that receives alerts from Prometheus and handles notification routing, grouping, silencing, and inhibition:

```yaml
route:
  group_by: [alertname, service]       # Group related alerts together
  group_wait: 30s                       # Wait to collect grouped alerts before sending
  group_interval: 5m                    # Wait before sending updates to a group
  repeat_interval: 4h                   # Re-notify if still firing after 4h
  receiver: slack-warnings

  routes:
    - match:
        severity: critical
      receiver: pagerduty-oncall
      continue: false

    - match:
        team: payments
      receiver: payments-slack-channel

receivers:
  - name: pagerduty-oncall
    pagerduty_configs:
      - routing_key: <key>
  - name: slack-warnings
    slack_configs:
      - channel: "#alerts-warnings"
```

Key concepts:
- **Grouping**: Multiple pods of the same service all firing the same alert → one grouped notification, not 20 individual pages.
- **Inhibition**: If a `cluster_down` critical alert is firing, inhibit all lower-severity alerts from that cluster — they're symptoms, not causes.
- **Silencing**: Temporarily suppress known alerts during maintenance. Never permanently silence — set an expiry.
- **Routing tree**: Alerts traverse the routing tree from top to bottom; the first matching route wins (unless `continue: true`).

## Section 6: Dashboards & Visualisation

**Q19. What dashboards should a fintech platform have as a baseline?**
A: Five tiers of dashboards, each answering a different audience's questions:

**Tier 1 — Service RED dashboard** (one per service, for on-call):
- Request rate, error rate, p50/p95/p99 latency per endpoint.
- Downstream dependency latency and error rates (DB, Redis, external APIs).
- Active alerts for this service.

**Tier 2 — Infrastructure USE dashboard** (for SRE/platform):
- CPU utilisation and saturation (run queue length) per node and pod.
- Memory utilisation and OOM events.
- Disk I/O throughput and latency.
- Network packet loss and bandwidth saturation.

**Tier 3 — SLO / error budget dashboard** (for team leads and management):
- SLI over the last 30 days vs SLO target.
- Error budget remaining (absolute minutes and percentage).
- Error budget burn rate (current rate vs safe burn rate).
- SLO breach history.

**Tier 4 — Business metrics dashboard** (for product and finance):
- Payment success rate, transaction volume, and total value processed.
- NACH debit success/failure rates by bank.
- KYC verification pass rates and processing time.
- PAN deduplication hit rates.

**Tier 5 — Log analytics dashboard** (for debugging):
- Log volume by service and level (ERROR/WARN trends).
- Top error messages in the last 1 hour.
- Log-to-trace correlation panel (click a log line → open trace).

**Q20. What is a Grafana variable, and how does it make dashboards reusable?**
A: Grafana variables are template parameters that make a dashboard work for any value of a given label — `$service`, `$env`, `$region`. Defined once per dashboard, they populate dropdowns at the top of the dashboard UI. Every panel query references `$service` instead of a hardcoded service name:
```promql
rate(http_requests_total{service=~"$service", env="$env"}[5m])
```
Variables are populated from a metric label query (`label_values(http_requests_total, service)`) — as new services appear, they automatically appear in the dropdown without dashboard changes. One dashboard template serves all services, all environments, and all regions — instead of maintaining 50 nearly-identical per-service dashboards.

## Section 7: Log-Metric-Trace Correlation

**Q21. How do you implement end-to-end correlation across logs, metrics, and traces?**
A: Correlation is achieved by sharing identifiers across all three pillars and building navigation between them in the query UI:

**Logs → Traces**:
Every log line includes `trace_id` and `span_id` as structured fields. In Grafana, configure a derived field on the Loki data source:
```
Field name: trace_id
Regex: trace_id=(\w+)
URL: http://tempo:3200/trace/$${__value.raw}
```
Clicking a `trace_id` in a log line opens the corresponding trace in Tempo — directly from the log view, no copy-paste.

**Metrics → Traces (exemplars)**:
Prometheus histogram metrics support exemplars — individual sample observations attached to a metric data point, carrying a `trace_id`:
```go
histogram.Observe(duration, prometheus.Labels{
  "trace_id": traceID,
})
```
In Grafana, enable exemplar display on histogram panels. When p99 spikes, click the spike → see exemplar points → click an exemplar → open the corresponding trace. You go from "the p99 was 3 seconds at 14:32" to "here is the actual slow request that caused it."

**Traces → Logs**:
From a Tempo trace view in Grafana, configure a "Logs for this span" button that runs a Loki query pre-filtered by `trace_id` and time range of the span. One click opens all log lines emitted during that specific span's execution.

**Q22. What is a unified alerting workflow that spans all three pillars?**
A: A production alert should carry enough context to begin investigation without switching tools:

**Alert fires** (metrics trigger):
```
🔴 PaymentErrorRateHigh — payment-service
Error rate: 3.2% (SLO: 0.1%)
Burn rate: 32× — budget exhausted in 37 minutes
Runbook: wiki.internal/runbooks/payment-error-rate
Dashboard: grafana.internal/d/payments-red
Logs (last 15 min errors): grafana.internal/explore?...
Recent traces (errors only): grafana.internal/explore?...
```

The alert notification includes pre-built deep-links to:
- The relevant Grafana dashboard scoped to the affected service and time window.
- A Loki query for ERROR logs from that service in the last 15 minutes.
- A Tempo query for traces with errors from that service in the last 15 minutes.

The on-call engineer clicks the alert, opens three browser tabs simultaneously, and starts the investigation with full context — no manual query construction at 3am.

## Section 8: Security, Compliance & Access Control

**Q23. How do you handle PII and sensitive data in logs?**
A: PII in logs is a regulatory and security risk — card numbers, Aadhaar numbers, PAN numbers, phone numbers, and bank account numbers must never appear in raw log storage. A defence-in-depth approach:

**At emission (application layer)**:
- Mask or redact sensitive fields in the logger middleware before the log line is written to stdout:
```javascript
// NestJS logger interceptor
const REDACTED_FIELDS = ['pan', 'card_number', 'account_number', 'otp', 'cvv'];
function sanitisePayload(obj) {
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) =>
      REDACTED_FIELDS.includes(k) ? [k, '***REDACTED***'] : [k, v]
    )
  );
}
```

**At collection (Fluent Bit)**:
- Apply a `lua` filter to redact patterns matching credit card numbers (`\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}`), Aadhaar (`\d{4}\s\d{4}\s\d{4}`), and PAN (`[A-Z]{5}\d{4}[A-Z]`) before shipping to Kafka.

**At storage**:
- Separate log streams for audit logs containing financial identifiers — store in an encrypted, access-controlled Elasticsearch index with stricter retention and access policies than general application logs.
- Enable field-level encryption for sensitive log fields in Elasticsearch (using Elasticsearch's field-level security or an encryption plugin).

**Q24. How do you implement log access control in a multi-team environment?**
A: Not all engineers should see all logs — a frontend engineer debugging a UI bug doesn't need access to raw payment transaction logs. Access control layers:

**Grafana team-based access**:
- Create Grafana organisations or teams per business unit (payments team, identity team, platform team).
- Each team's Grafana data source is pre-filtered to their services' log streams via a label selector — `{team="payments"}` — enforced at the data source level, not the dashboard level.
- Team members can only query their own service logs; platform SREs have cross-team access.

**Elasticsearch field-level security**:
- Define Elasticsearch roles that grant read access to specific indices (e.g., `logs-payment-*`) but exclude sensitive fields (`account_number`, `pan`) from the response — engineers see the log but the sensitive fields are blank.

**Kafka topic ACLs**:
- Log streams containing audit/compliance data flow through a separate Kafka topic (`logs.audit`) with ACLs restricting consumer access to the compliance team and the audit log storage consumer only.

**Q25. What are the regulatory log retention requirements for a fintech platform in India?**
A: Indian fintech platforms are subject to multiple regulators with overlapping retention requirements:
- **RBI (Reserve Bank of India)**: Payment transaction records must be retained for a minimum of 5 years. This includes NACH mandate records, UPI transaction logs, and payment gateway interaction logs.
- **SEBI**: Capital markets data and trade logs — 5–7 years depending on instrument type.
- **IRDAI**: Insurance transaction records — 3–5 years minimum.
- **PCI-DSS**: Cardholder data environment audit logs — 12 months online (queryable), 12 months archived.
- **IT Act / CERT-In (2022 directive)**: All ICT system logs must be retained for 180 days and must be available to CERT-In within 6 hours of a request. This applies to all systems, not just financial records.

Implementation: tag log streams with a `compliance_tier` label at emission. The retention policy is driven by the tag — `compliance_tier=rbi_payment` gets a 5-year retention on cold storage (S3 Glacier), while `compliance_tier=application` gets 90 days. The tagging must be enforced at the collection layer, not left to application teams — a misconfigured tag on an audit log that gets deleted after 90 days is a compliance breach.

## Section 9: Scenario / System Design Questions

**Q26. "Design the logging and monitoring stack for a NestJS-based payment platform on AWS with Kafka and Postgres."**
A: End-to-end stack design:

**Log collection**: Fluent Bit DaemonSet on every EKS node. Tails `/var/log/containers/*.log`, enriches with Kubernetes metadata, applies PII redaction Lua filters, batches and ships to Kafka topic `logs.prod`.

**Log transport**: Kafka with 3 partitions per topic (allows 3 parallel consumers), 24-hour retention on the log topic as replay buffer.

**Log storage**: Two consumers from Kafka:
- **Loki consumer** (Promtail or Kafka-to-Loki bridge) → Grafana Loki backed by S3. Application logs, 30-day hot retention. LogQL queries in Grafana.
- **OpenSearch consumer** → AWS OpenSearch Service. Audit/compliance logs, 5-year retention via index lifecycle policy with S3 offload.

**Metrics**: OTel Collector DaemonSet scrapes `/metrics` from all pods (Prometheus format), receives OTLP push from NestJS services (via `@opentelemetry/sdk-node`), remote-writes to Amazon Managed Service for Prometheus (AMP). Grafana queries AMP via PromQL.

**Traces**: NestJS services auto-instrumented with OTel SDK → OTLP export to OTel Collector → Grafana Tempo backed by S3. 7-day retention, 1% head sampling + 100% error trace retention.

**Alerting**: Grafana Alerting (unified alerting) evaluates rules against AMP. Routes via:
- `severity=critical` → PagerDuty (wake on-call engineer).
- `severity=warning` → `#payments-alerts` Slack channel.
- `severity=info` (business metric anomaly) → `#payments-metrics` Slack channel.

**Dashboards**: Grafana with five dashboard tiers (as per Q19). All dashboards use `$service` and `$env` variables. Exemplars enabled on all histogram panels for metrics→trace correlation.

**Q27. "Your payment service starts logging 10× its normal volume at 2am. Walk through how you detect this, investigate, and prevent it recurring."**
A: Full observability-driven investigation:

**Detection**:
- Alert fires: `LogIngestionRateHigh` — `rate(loki_ingester_chunks_created_total{service="payment-service"}[5m]) > 10 * baseline`. Or a simpler Prometheus alert on Fluent Bit's output rate metric per service label.
- Alternatively, the Kafka consumer lag alert fires — the Loki consumer is falling behind because the payment service's log volume spiked.

**Investigation**:
1. Open the Grafana log analytics dashboard, filter `{service="payment-service"}`, time range 01:55–02:05. Volume chart shows the spike onset at exactly 02:00.
2. Break down by `level` label — 95% of the spike is `DEBUG` logs. Something enabled DEBUG logging in production.
3. Filter `{service="payment-service", level="debug"}` — the log lines all contain `"BRE rule evaluation debug"` — a new BRE feature flag was deployed at 01:58 with debug logging accidentally left enabled.
4. Confirm via deployment events — a Kubernetes deployment annotation shows a new pod rollout at 01:58.

**Immediate fix**: Toggle the feature flag to disable debug logging without redeployment. Log volume returns to baseline within 30 seconds.

**Prevention**:
- Add a pre-deployment check in CI: scan log statements in changed files — fail the pipeline if any `logger.debug()` call is added without a `if (featureFlag.debugEnabled)` guard.
- Add a Grafana alert for sustained log volume > 3× baseline per service — fires within 2 minutes of the spike.
- Add a log-level override API endpoint (protected, internal only) — change log level at runtime without a code deploy or restart.
- Enforce a linting rule: no bare `logger.debug()` in production code paths — all debug logging must be behind a configurable level check.

**Q28. "Your Prometheus instance is running out of disk space. Cardinality has grown from 500K to 8M series over 6 months. How do you diagnose and fix it?"**
A: Cardinality explosion diagnosis and remediation:

**Diagnosis**:
1. `prometheus_tsdb_head_series` gauge: 8M series, growing 100K per day.
2. Run `tsdb analyze` on the Prometheus data directory — output shows top 20 metric names by series count.
3. Top offender: `http_request_duration_seconds` with 6.5M series — investigate its labels.
4. PromQL: `count by (__name__, job) ({__name__=~"http_request_duration_seconds"})` grouped by all label names — reveals a `user_id` label with 1M unique values on this metric.
5. Git blame: a 4-month-old commit added `user_id` as a label to the HTTP middleware instrumentation.

**Fix**:
1. **Immediate**: Remove `user_id` from the HTTP duration histogram labels in the NestJS OTel instrumentation. Deploy — series count drops as old series expire (TSDB retention window).
2. **Recover disk**: Once series count drops, run `promtool tsdb delete-series` to immediately remove the high-cardinality series without waiting for retention expiry. Or snapshot the TSDB, drop the bloated blocks, and restore.
3. **Migrate to Thanos**: The incident reveals Prometheus is a single point of failure and a single-node bottleneck. Add Thanos sidecar for S3 offload and increase scrape capacity.

**Prevention**:
- Add `prometheus_tsdb_head_series > 2_000_000` as a warning alert — catch growth early.
- Require a cardinality review as part of every PR that adds or modifies metric instrumentation — include a comment with estimated series count.
- Add a CI check using `prom-label-proxy` or a custom script that validates no high-cardinality labels (matching a blocklist: `user_id`, `order_id`, `session_id`, `ip_address`) appear in metric definitions.

**Q29. "A CERT-In audit requests all payment service logs from a 3-day window 8 months ago. How does your system handle this?"**
A: This tests your retention architecture under a real regulatory scenario:

**If the retention architecture is correct**:
- Payment service logs are tagged `compliance_tier=rbi_payment` at emission by Fluent Bit.
- This stream flows to OpenSearch via a dedicated Kafka topic `logs.audit`.
- OpenSearch ILM policy: hot (0–30 days) → warm (30–90 days) → cold S3 offload (90 days–5 years).
- At 8 months, the logs are in S3 cold storage, but the OpenSearch index still exists (metadata) — restoring the S3-backed segment makes them queryable.

**Retrieval process**:
1. Open OpenSearch Dashboards, query index `logs-payment-prod-*` for the 3-day window.
2. If cold-tier segments need restoration from S3: trigger an OpenSearch searchable snapshot restore for the relevant date indices — typically takes 5–30 minutes depending on data volume.
3. Export results to a signed, encrypted S3 bucket — provide the CERT-In team with a pre-signed URL with a 24-hour expiry.
4. Log the audit access event itself — who queried what, when, and what was exported — in a separate immutable audit log of the audit system.

**If the retention architecture was not designed for compliance**:
The logs were stored only in Loki with a 30-day TTL — they no longer exist. This is a compliance breach. The response is: escalate to legal and compliance immediately, produce whatever partial records exist (application DB records, Kafka offsets if retention was set long enough), and begin a post-mortem to implement correct retention before the next audit.

This scenario is why retention architecture must be a day-zero design decision for fintech platforms, not an afterthought.
