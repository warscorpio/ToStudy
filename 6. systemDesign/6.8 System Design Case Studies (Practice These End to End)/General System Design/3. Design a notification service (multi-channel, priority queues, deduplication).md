# Design a Notification Service (Multi-Channel, Priority Queues, Deduplication) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scoping

**Q1. What are the functional requirements of a notification service?**
A: Before designing, nail the requirements:
- **Multi-channel delivery**: Support at least email, SMS, push notification (FCM/APNS), and in-app. Possibly WhatsApp, Slack, or webhooks.
- **Priority queues**: Critical notifications (OTP, payment failure, fraud alert) must be delivered within seconds; marketing notifications can wait minutes or hours.
- **Deduplication**: The same notification must not be delivered more than once to a user — even if the upstream service publishes the event multiple times.
- **Template management**: Notification content should be driven by templates, not hardcoded strings, so product teams can update copy without code changes.
- **User preferences**: Users opt in/out of specific notification types per channel. The service must respect these preferences.
- **Delivery tracking**: Track sent, delivered, failed, and opened states per notification per channel.
- **Retry with backoff**: Failed deliveries must retry with exponential backoff, with a dead-letter queue for permanently failing notifications.
- **Rate limiting**: Don't spam a user — enforce per-user per-channel per-type rate limits (e.g., max 3 OTPs per 10 minutes).

**Q2. What are the non-functional requirements?**
A:
- **Latency**: OTP/critical notifications delivered within 2–3 seconds of the triggering event. Marketing batch notifications within 5–10 minutes of schedule time.
- **Throughput**: For a mid-size fintech — 10,000–50,000 notifications/minute at peak. For scale: 1M+/minute for large platforms.
- **Reliability**: At-least-once delivery. No notification should be silently dropped. Every failure should be retryable or dead-lettered.
- **Idempotency**: Duplicate event publishes must not produce duplicate notifications.
- **Extensibility**: Adding a new channel (WhatsApp, Slack) should not require changes to the core routing or queuing logic.
- **Observability**: Per-channel delivery rates, failure rates, queue depths, and p99 latency tracked as metrics. Every notification traceable end-to-end.

**Q3. What are the core entities in a notification service?**
A: The domain model before any architecture decisions:
- **Notification**: The intent to notify a user — `{id, user_id, type, channel, template_id, payload, priority, idempotency_key, status, created_at}`.
- **Template**: Parameterised content per channel and locale — `{id, type, channel, locale, subject, body, variables[]}`.
- **User preference**: Per-user per-type per-channel opt-in/out — `{user_id, notification_type, channel, enabled}`.
- **User contact**: The actual delivery address per channel — `{user_id, channel, address, verified, primary}`. (e.g., channel=`email`, address=`user@example.com`).
- **Delivery log**: Immutable record of every delivery attempt — `{id, notification_id, channel, provider, status, provider_response, attempted_at}`.
- **Dead letter**: Permanently failed notifications for human review — `{notification_id, reason, last_attempted_at}`.

## Section 2: High-Level Architecture

**Q4. What are the major components of a notification service?**
A: Five logical layers:

```
Upstream Services (Payment, Auth, BRE, NACH)
          |
          | (event / API call)
          ▼
  [1] Notification API / Event Consumer
          |
          | (enqueue with priority + idempotency key)
          ▼
  [2] Priority Queue Layer (Kafka / SQS)
     [CRITICAL] [HIGH] [NORMAL] [LOW]
          |
          ▼
  [3] Dispatcher (reads queue, resolves template,
      checks preferences, deduplicates, rate-limits)
          |
          ▼
  [4] Channel Workers (Email / SMS / Push / In-App)
          |
          ▼
  [5] Provider Adapters (SendGrid, Twilio, FCM, APNS)
```

Each layer is independently scalable. The Dispatcher is the brain — it makes all routing, deduplication, and preference decisions. Channel Workers are stateless executors. Provider Adapters are thin wrappers that normalise provider-specific APIs and errors.

**Q5. How does an upstream service trigger a notification?**
A: Two patterns, used together:

- **Event-driven (preferred)**: The upstream service publishes a domain event to Kafka (`payment.confirmed`, `otp.requested`, `nach.debit.failed`). The Notification service's Event Consumer subscribes to these topics and converts events into notification intents. The upstream service has zero knowledge of notification logic — it just publishes what happened.

- **Direct API (for interactive flows)**: A REST/gRPC endpoint — `POST /notifications` — for cases where the caller needs synchronous confirmation that the notification was accepted (e.g., an OTP request where the caller needs to know the OTP was queued before proceeding). The API immediately enqueues and returns a `notification_id`.

Both paths converge at the same queue. The API path is the fast lane; the event path is the standard lane.

**Q6. Why use a queue between the Dispatcher and the Channel Workers instead of calling providers directly?**
A: Direct provider calls from the Dispatcher create tight coupling and fragility:
- **Provider rate limits**: Twilio, SendGrid, FCM all have rate limits. A queue absorbs bursts and drains at the provider's allowed rate.
- **Backpressure**: If a provider is slow or down, the queue buffers without dropping notifications or blocking upstream services.
- **Retries without re-entering the pipeline**: A failed delivery re-enqueues the channel-specific message for retry, without re-running deduplication or preference checks (those were already passed).
- **Throughput scaling**: Scale Channel Workers independently per channel — SMS workers can scale separately from push workers based on their respective queue depths.
- **Observability**: Queue depth per channel and per priority is a first-class metric. You can immediately see if the SMS worker is falling behind without instrumenting individual provider calls.

## Section 3: Priority Queues

**Q7. How do you implement priority queues for notifications?**
A: Define 4 priority tiers based on business urgency:

| Priority | Tier | Examples | SLA |
|---|---|---|---|
| P0 | CRITICAL | OTP, fraud alert, password reset, payment failure | < 3 seconds |
| P1 | HIGH | Transaction confirmation, NACH debit result, KYC status | < 30 seconds |
| P2 | NORMAL | Account updates, policy renewal reminders | < 5 minutes |
| P3 | LOW | Marketing, newsletters, feature announcements | < 1 hour |

Implementation approaches:

- **Separate Kafka topics per priority**: `notifications.critical`, `notifications.high`, `notifications.normal`, `notifications.low`. Dispatcher consumers are configured with more partitions and more consumer instances on higher-priority topics. Simple, predictable, operationally transparent.
- **SQS FIFO with message group IDs**: Use one queue per priority tier in SQS. MessageGroupId = `{user_id}:{channel}` ensures per-user per-channel ordering within a priority level.
- **Single queue with priority scoring + sorted consumer**: Use Redis sorted sets (`ZADD`) with a score combining priority and timestamp — `score = (priority_weight * 1e13) + epoch_ms`. Consumer always `ZPOPMIN` from the head — highest priority, then oldest within priority. Flexible but adds Redis as a critical dependency.

For most fintech systems: **separate Kafka topics per priority** is the right call — simple, auditable, and allows independent consumer lag monitoring per priority.

**Q8. How do you prevent low-priority notifications from starving under high load?**
A: Starvation occurs when CRITICAL and HIGH queues are always full, and LOW consumers never get scheduled. Mitigations:
- **Dedicated consumer groups per priority**: LOW-priority consumers are always running and draining their own topic — they don't compete with CRITICAL consumers for the same partitions. As long as each topic has dedicated consumers, starvation within a topic doesn't happen.
- **Capacity planning per tier**: Size consumer fleets per tier based on expected throughput, not shared capacity. CRITICAL tier needs enough consumers to drain within the SLA even at peak; LOW tier can run with minimal consumers and tolerate queue growth.
- **Age-based priority escalation**: If a LOW-priority notification has been in the queue for more than 30 minutes, escalate it to NORMAL. Prevents indefinite delay without disrupting normal priority ordering. Implement via a periodic job that scans old queue entries.
- **Backpressure signalling**: If total queue depth across all tiers exceeds a threshold, reject new LOW-priority enqueues at the API layer with a 429 — force the caller to retry later rather than growing the queue unboundedly.

**Q9. How do you handle priority inversion — where a P2 notification becomes urgent after a delay?**
A: Priority inversion happens when a notification that was queued as NORMAL becomes time-sensitive because of a business event (e.g., a reminder notification queued 24 hours ahead that's now 5 minutes before the deadline). Approaches:
- **Scheduled re-prioritisation job**: A cron runs every minute scanning the notification table for entries where `deliver_at <= now + 5min AND priority = NORMAL` and re-enqueues them to the HIGH topic.
- **Scheduled delivery with priority baked in at queue time**: The upstream service sets `deliver_at` and `priority` at publish time — the Dispatcher holds the notification in a scheduled store (Redis sorted set by `deliver_at`) and enqueues to the correct priority queue at the right time.
- **Avoid storing priority in the queue**: Store priority in the notification record, not the queue message. When the Dispatcher picks up any message, it re-reads the current priority from the DB — if priority has changed, it processes accordingly.

## Section 4: Deduplication

**Q10. Why is deduplication necessary in a notification service?**
A: Three sources of duplicates in an event-driven notification system:
1. **At-least-once message delivery**: Kafka and SQS guarantee at-least-once delivery. If the Dispatcher processes a message and crashes before committing the offset, the same message is redelivered on restart. Without deduplication, the user receives two identical notifications.
2. **Upstream retries**: A payment service that publishes `payment.confirmed` may publish it twice if its own retry logic fires after a network timeout where the first publish actually succeeded.
3. **Multiple triggers for the same logical event**: Two code paths both detect the same fraud event and both publish a `fraud.alert` event — the user should receive exactly one fraud alert.

**Q11. What is an idempotency key, and how do you use it for deduplication?**
A: An idempotency key is a unique, stable identifier for a specific notification intent — identical events must produce the same key. The key is generated by the upstream caller or the Event Consumer and stored with the notification. Before creating a new notification, the Dispatcher checks if a notification with this key already exists:
```sql
INSERT INTO notifications (id, idempotency_key, user_id, type, ...)
VALUES ($1, $2, $3, $4, ...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING id;
-- If no row returned → duplicate, skip processing
```

Key construction strategies:
- **Event-based**: `{event_type}:{aggregate_id}:{event_id}` — e.g., `payment.confirmed:pay_789:evt_abc`. Stable across retries because event IDs are stable.
- **Content-based**: `SHA256({user_id}:{notification_type}:{relevant_payload_fields})` — e.g., `SHA256(usr_42:otp_requested:session_xyz)`. Good when the upstream doesn't provide a stable event ID.
- **Business-rule-based**: `{user_id}:{notification_type}:{date}` for notifications that should fire at most once per day (e.g., daily digest) — the key itself encodes the deduplication window.

**Q12. Where in the pipeline do you enforce deduplication?**
A: At two points — defence in depth:

- **At ingestion (Event Consumer / API layer)**: Before enqueuing, check the `notifications` table for an existing row with the same `idempotency_key`. If found, return the existing `notification_id` and do not enqueue. This prevents duplicate queue messages from ever being created.
- **At dispatch (Dispatcher, before sending)**: Before calling the provider, check the `delivery_log` for a successful delivery of this `notification_id` to this `channel`. If a successful delivery exists, skip. This catches the case where the Dispatcher processed a message and sent the notification, but crashed before committing the Kafka offset — on redelivery, the second attempt finds the delivery log and skips.

The ingestion check eliminates most duplicates cheaply. The dispatch check is the safety net for the race window between consume and commit.

**Q13. How do you handle the deduplication window — how long should an idempotency key be valid?**
A: The deduplication window is how long after the first delivery you'll suppress a duplicate with the same key. Rules by notification type:

| Notification Type | Deduplication Window | Rationale |
|---|---|---|
| OTP | 10 minutes | OTPs expire; a new OTP request after expiry is legitimate |
| Payment confirmation | 24 hours | Same payment should never notify twice, ever |
| Fraud alert | 1 hour | A new fraud event on the same account after 1 hour is a distinct event |
| Daily digest | 24 hours | Exactly once per calendar day |
| Marketing campaign | 7 days | Same campaign message shouldn't repeat within a week |

Implement with a TTL on the idempotency key in Redis: `SET dedup:{idempotency_key} 1 EX {window_seconds} NX`. If `NX` fails (key exists), it's a duplicate — skip.

**Q14. What is the deduplication race condition, and how do you prevent it?**
A: If two identical events arrive simultaneously, both may pass the "does this idempotency key exist?" check before either has written the record — both proceed, both create notifications, both send to the user. The fix: make the idempotency key check atomic using either:
- **DB unique constraint + `ON CONFLICT DO NOTHING`**: The unique constraint on `idempotency_key` in the `notifications` table means only one INSERT succeeds; the loser gets 0 rows back and skips.
- **Redis `SET NX` (set if not exists)**: `SET dedup:{key} 1 NX EX 300` — only one caller gets `OK`; the rest get `nil` and skip. Works even across multiple Dispatcher instances.
Both approaches rely on atomic operations — no read-then-write pattern, which is inherently racy.

## Section 5: Channel Routing & Template Rendering

**Q15. How do you route a notification to the correct channel?**
A: Channel selection follows a priority order:

1. **User preference**: If the user has explicitly opted out of a channel for this notification type, skip it.
2. **Notification type policy**: Some types are always a specific channel (OTP = SMS only; push only if app is installed). Policy is defined per notification type, not per user.
3. **Channel availability**: Does the user have a verified contact for this channel? (Email address verified? Push token registered and not expired?)
4. **Fallback chain**: If the primary channel fails or is unavailable, try the next in the fallback chain. Example: Push → SMS → Email for a transaction alert.

Routing logic lives entirely in the Dispatcher — channel workers receive a `channel`-specific message and just execute delivery. The Dispatcher resolves all routing decisions before enqueuing to the channel queue.

**Q16. How do you manage notification templates across channels and locales?**
A: A template service (can be a table in the DB, or a dedicated microservice for large scale) stores templates keyed by `{notification_type, channel, locale}`:
```sql
CREATE TABLE templates (
  id           UUID PRIMARY KEY,
  type         VARCHAR(100) NOT NULL,   -- 'payment_confirmed'
  channel      VARCHAR(20)  NOT NULL,   -- 'email', 'sms', 'push'
  locale       VARCHAR(10)  NOT NULL DEFAULT 'en-IN',
  subject      TEXT,                    -- email subject, push title
  body         TEXT NOT NULL,           -- Handlebars / Mustache template
  variables    JSONB NOT NULL,          -- schema of expected variables
  version      INT NOT NULL DEFAULT 1,
  active       BOOLEAN NOT NULL DEFAULT TRUE
);
UNIQUE (type, channel, locale, active);
```

Template rendering happens in the Dispatcher after preference checks and before enqueuing to the channel queue. The Dispatcher fetches the template, merges the notification payload into the template variables, and produces a `rendered_notification` with the final subject and body. Channel workers receive the rendered content — they never touch templates.

Cache templates aggressively in Redis (TTL: 5 minutes) — templates change rarely, and DB round trips per notification at high throughput are expensive.

**Q17. How do you handle user contact resolution at scale?**
A: User contacts (email addresses, phone numbers, push tokens) are owned by the User service, not the Notification service. The Notification service resolves contacts at dispatch time:
- **Cache user contacts in Redis**: After the first resolution, cache `{user_id}:{channel}` → contact address with a TTL of 5–15 minutes. Invalidate via event when a user updates their contact (`user.email_changed` event).
- **Bulk pre-fetch for batch notifications**: For marketing sends to 1M users, pre-fetch contacts in batches of 1,000 before enqueueing — avoid 1M individual Redis lookups during dispatch.
- **Handle missing contacts gracefully**: If a user has no push token (never installed the app), skip the push channel silently and fall through to the next in the fallback chain — log it but don't treat it as an error.

## Section 6: Retry, Failure Handling & Dead Letter

**Q18. How do you implement retries for failed notification deliveries?**
A: Retry with exponential backoff and jitter, capped at a maximum retry count:

```
Attempt 1: immediate
Attempt 2: 30 seconds later
Attempt 3: 2 minutes later
Attempt 4: 10 minutes later
Attempt 5: 30 minutes later
→ Dead letter after 5 failures
```

Implementation: on a failed delivery, the Channel Worker re-enqueues the message to a retry topic/queue with a `next_attempt_at` timestamp and incremented `retry_count`. A retry scheduler (Redis sorted set or SQS delay queue) holds the message until `next_attempt_at`, then re-delivers to the channel queue. The retry loop is isolated from the main queue — retry traffic doesn't consume capacity from new notifications.

**Q19. Which failures should you retry, and which should you dead-letter immediately?**
A: Classify by whether retrying could succeed:

| Error Type | Action | Rationale |
|---|---|---|
| Provider 5xx / timeout | Retry with backoff | Transient — provider will recover |
| Rate limit (429) | Retry after `Retry-After` header | Transient — honour the backoff signal |
| Invalid phone number / email | Dead-letter immediately | Retrying won't fix bad contact data |
| User unsubscribed (provider bounce) | Dead-letter + update preference | Retrying would violate opt-out |
| Provider auth failure | Alert + dead-letter | Config issue — retrying won't help |
| OTP expired before delivery | Dead-letter | Stale notification — delivery would confuse the user |
| Template render error | Dead-letter | Code bug — retrying same template won't help |

The rule: retry transient infrastructure failures; dead-letter permanent data or logic failures.

**Q20. What is a dead letter queue (DLQ), and how do you operationalise it?**
A: A DLQ is a storage destination for notifications that have exhausted all retries or failed in a non-retriable way. It is not a discard bin — every entry in the DLQ represents a notification that a user *should have received* but didn't. Operational requirements:
- **Alert on DLQ depth**: PagerDuty if DLQ grows faster than a threshold (signals a systemic failure — provider down, bad deploy).
- **DLQ dashboard**: Show DLQ entries by channel, failure reason, and notification type — to quickly identify patterns (e.g., all Twilio SMS failing = Twilio outage).
- **Replay capability**: After fixing the root cause (invalid contacts corrected, provider restored), replay DLQ entries back into the main queue with a single operator action. The replay must re-run deduplication — a notification that made it to DLQ and was also eventually delivered through another path must not be re-sent.
- **Manual review for critical notifications**: OTP and fraud alert DLQ entries should trigger immediate human review — these represent security-sensitive failures.

## Section 7: Rate Limiting & User Preferences

**Q21. How do you enforce per-user notification rate limits?**
A: Rate limiting at the Dispatcher level, before enqueuing to the channel queue. Use Redis sliding window counters per `{user_id}:{channel}:{notification_type}`:

```
Key: rate:{user_id}:{channel}:{type}:{window}
Example: rate:usr_42:sms:otp:1min

INCR rate:usr_42:sms:otp:1min
EXPIRE rate:usr_42:sms:otp:1min 60  (set only on first increment)
if count > limit: reject / queue for later
```

Rate limit policies per notification type:

| Type | Limit |
|---|---|
| OTP (SMS) | 3 per 10 minutes per user |
| Fraud alert | 1 per 30 minutes per user |
| Transaction confirmation | 10 per minute per user |
| Marketing (email) | 1 per day per campaign per user |
| Push (any) | 20 per hour per user |

Rate-limited notifications are either dropped (for low-priority types) or queued with a `send_after` delay (for important types like OTP — queue it, but don't send until the window resets).

**Q22. How do you manage user notification preferences at scale?**
A: User preferences are the source of truth for whether a notification should be sent. Architecture:
- **Preference store**: A table `{user_id, notification_type, channel, enabled}` in Postgres. The authoritative record.
- **Preference cache**: Cache per-user preferences in Redis as a hash — `HGET prefs:{user_id} {type}:{channel}`. TTL: 5 minutes. Invalidate via a `user.preferences_updated` event.
- **Default preferences**: Every notification type has a default policy (opt-in or opt-out). Users who haven't set a preference inherit the default.
- **Mandatory notifications**: Some types (OTP, fraud alert, regulatory notices) are non-overridable — the Dispatcher sends them regardless of user preference. This must be encoded in the notification type policy, not just the preference check.
- **Global unsubscribe**: A single "unsubscribe all marketing" flag overrides all individual marketing preferences. Check the global flag first; skip the per-type check if set.

## Section 8: Observability & Operations

**Q23. What metrics should a notification service expose?**
A: By layer:

**Ingestion layer**:
- `notifications_received_total{type, source}` — volume by type and upstream service.
- `notifications_deduplicated_total{type}` — deduplication hit rate.
- `notifications_enqueued_total{type, priority}` — what's entering the queue.

**Queue layer**:
- `queue_depth{priority, channel}` — the most important operational metric. Alert if CRITICAL depth > 100 for more than 30 seconds.
- `queue_consumer_lag{priority, channel}` — how far behind consumers are.

**Dispatcher layer**:
- `dispatcher_processing_duration_ms{p50, p95, p99}` — time from queue dequeue to channel enqueue.
- `preference_check_skipped_total{reason}` — user opted out, mandatory override, etc.
- `rate_limited_total{type, channel}` — how often rate limits are firing.

**Delivery layer**:
- `delivery_attempts_total{channel, status}` — sent, failed, retried per channel.
- `delivery_duration_ms{channel, provider, p99}` — provider call latency.
- `dlq_depth{channel}` — dead letter queue size. Alert aggressively on this.

**Business metrics**:
- `notification_delivery_rate{type, channel}` — what fraction of sent notifications were confirmed delivered.
- `otp_delivery_p99_ms` — the most latency-sensitive metric; should be < 3 seconds.

**Q24. How do you trace a notification end-to-end through the system?**
A: Thread a `notification_id` and `trace_id` through every stage:
- The upstream event carries a `correlation_id` → the Notification service creates a `notification_id` and links it to the `correlation_id`.
- Every queue message carries both `notification_id` and `trace_id`.
- Every log line at every stage includes `notification_id` and `trace_id`.
- Every `delivery_log` row stores `notification_id`, `provider_message_id` (the ID the provider gives back), and `trace_id`.

This makes it possible to answer "what happened to OTP notification for user X at 3:42pm?" in under 30 seconds — query `delivery_log` by `notification_id`, follow `trace_id` into the distributed trace, and read the log lines. For fintech audit requirements, the `delivery_log` table is an immutable append-only record — no deletes.

## Section 9: Scenario / System Design Questions

**Q25. "Design the notification flow for a NACH debit failure. The user must be notified via SMS and push within 5 seconds."**
A: End-to-end design:

1. **Event publish**: The NACH processing service publishes `nach.debit.failed` to Kafka with `{payment_id, user_id, amount, reason, idempotency_key: "nach.debit.failed:{payment_id}"}`.
2. **Event Consumer**: Subscribes to `nach.debit.failed`. Checks idempotency key — if new, creates a `notification` record with `priority=CRITICAL` and enqueues to `notifications.critical` Kafka topic.
3. **Dispatcher** (dedicated consumers on the CRITICAL topic — low consumer group lag, over-provisioned): Reads the message, checks user preferences (NACH failure alert is mandatory — skips preference check), resolves user's phone and push token from cache, renders SMS template ("Your NACH debit of ₹{amount} failed. Reason: {reason}. Contact support.") and push template, enqueues one message each to `channel.sms.critical` and `channel.push.critical`.
4. **SMS Worker**: Calls Twilio API. On success, writes to `delivery_log`. On failure (timeout), re-enqueues with 5-second backoff — max 3 retries before DLQ.
5. **Push Worker**: Calls FCM. On success, writes to `delivery_log`. If push token is invalid (app uninstalled), dead-letters the push attempt and does NOT fall back to SMS — SMS was already sent independently.
6. **SLA tracking**: Alert if `otp_delivery_p99_ms` (same infrastructure) exceeds 3 seconds for more than 1 minute — the same metric covers NACH critical notifications.

**Q26. "How would you design the notification service to send a promotional campaign to 10 million users at 9am?"**
A: Batch marketing at scale is a different problem from real-time transactional notifications:

1. **Campaign scheduling**: A Campaign service stores `{campaign_id, template_id, target_segment, scheduled_at}`. At `scheduled_at`, a campaign job starts.
2. **User segment fan-out**: The campaign job queries the segment (e.g., "all users with active savings accounts") in batches of 10,000. For each batch, it publishes messages to `notifications.low` Kafka topic — NOT to the real-time pipeline. The fan-out job itself is idempotent: it writes `{campaign_id, user_id, enqueued: true}` to a `campaign_users` table — restarts resume from the last unqueued user.
3. **Dispatcher throttling**: LOW-priority consumers are configured with a maximum processing rate — e.g., 50,000/minute — to avoid saturating email/SMS providers. This naturally spreads a 10M send over ~3.3 hours at this rate, which is acceptable for marketing.
4. **Per-user deduplication**: Idempotency key: `campaign:{campaign_id}:{user_id}` — each user gets exactly one message per campaign.
5. **Global unsubscribe check**: Before enqueuing each user's notification, check the marketing opt-out flag. This is the first check — if opted out, skip entirely.
6. **Delivery rate tracking**: A campaign dashboard shows delivered/failed/opened per campaign, updated in near-real-time as `delivery_log` entries arrive.

Key insight: never route batch campaigns through the real-time CRITICAL or HIGH queues. They are entirely separate consumer groups and topics — a 10M campaign must not affect OTP delivery latency.

**Q27. "A bug caused 50,000 duplicate payment confirmation events to be published to Kafka. How does your notification service handle this?"**
A: This is the deduplication system under stress — a real test of the design:

1. **Idempotency key check at ingestion**: The Event Consumer checks `SELECT id FROM notifications WHERE idempotency_key = 'payment.confirmed:{payment_id}'` before creating each notification. For 50,000 duplicates of the same payment, 49,999 will hit the unique constraint and be discarded immediately — only 1 notification is created.
2. **Redis NX as first gate**: If Redis `SET dedup:{key} 1 NX EX 86400` is the first check, it's faster than a DB query. 49,999 duplicates never even reach the DB.
3. **Delivery log as final gate**: Even if a few duplicates slip through to the Dispatcher (e.g., due to a Redis eviction), the `delivery_log` unique constraint on `{notification_id, channel}` prevents the same notification from being delivered twice.
4. **Observability signal**: `notifications_deduplicated_total{type=payment_confirmed}` spikes from near-zero to 49,999 in minutes. This is an alert-worthy signal — high deduplication rate indicates an upstream bug, not just normal at-least-once redelivery. Page the upstream team.

Result: the user receives exactly one payment confirmation notification. The upstream bug is caught via metrics before anyone notices.

**Q28. "How would you handle notification delivery when a user's push token has expired and their phone number has changed?"**
A: This is the contact staleness problem — the most common silent failure in notification services:

**Stale push token detection**:
- FCM and APNS return specific error codes for invalid/expired tokens (`NotRegistered` from FCM, `BadDeviceToken` from APNS).
- The Push Worker, on receiving these errors, publishes a `push.token.invalid` event — the User service (or a dedicated device registry) listens and marks the token as inactive, and the Notification service removes it from the contact cache.
- On the next notification, the push channel has no valid token → falls back to SMS per the fallback chain.

**Stale phone number detection**:
- Twilio returns `30003` (unreachable) or `21614` (not a valid mobile number) for invalid numbers.
- The SMS Worker publishes `sms.contact.invalid` → User service is notified to prompt the user to update their number on next login.
- In the meantime, the Notification service falls back to email.

**Proactive staleness management**:
- Push tokens: FCM/APNS send token refresh callbacks when tokens rotate. Subscribe to these callbacks and update the device registry immediately.
- Phone numbers: Run a periodic validation job (using a number lookup API) against all stored numbers — flag numbers that have been deactivated or ported without a corresponding update.

## Quick Comparison Table

| Concern | Approach | Trade-off |
|---|---|---|
| Priority | Separate Kafka topics per tier | Simple, auditable; fixed number of tiers |
| Deduplication | Idempotency key → Redis NX + DB unique constraint | Defence in depth; slight write overhead |
| Retry | Exponential backoff via delay queue | Adds retry infrastructure complexity |
| Template rendering | Dispatcher-side, before channel enqueue | Centralised; Dispatcher becomes a fat layer |
| Contact resolution | Redis cache + event-driven invalidation | Stale contacts possible within TTL window |
| Rate limiting | Redis sliding window per user per channel per type | Redis is a critical dependency |
| Batch campaigns | Separate LOW-priority topic + throttled consumers | Isolated from real-time traffic completely |
| Dead letter | DLQ table + alerting + replay tooling | Requires operational discipline to drain |

**Tip for the interview:** At the 5 YOE level, interviewers expect you to go beyond "use Kafka and Redis" and reason through the failure modes. Be ready to whiteboard the deduplication race condition and explain why `SET NX` is atomic. Know why batch campaigns must never share a queue with OTP notifications. Distinguish between transient failures (retry) and permanent failures (dead-letter immediately). In a fintech context, name the specific notifications in your domain (NACH debit failure, PAN verification result, OTP for payment authorisation) and show how the priority and deduplication strategy maps to each — that specificity signals you've thought through the actual business requirements, not just the generic pattern.
