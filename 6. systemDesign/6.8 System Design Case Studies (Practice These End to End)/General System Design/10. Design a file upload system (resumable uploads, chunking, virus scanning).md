# Design a File Upload System (Resumable Uploads, Chunking, Virus Scanning) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Estimation

**Q1. What are the functional requirements of a file upload system?**
A: Core requirements:
- **Upload:** Accept files from clients, support small (< 5MB) and large (up to several GB) files.
- **Resumable upload:** If an upload is interrupted (network drop, browser close), allow the client to resume from where it left off — not restart from byte 0.
- **Chunked upload:** Split large files into smaller chunks on the client, upload each chunk independently, reassemble on the server.
- **Virus / malware scanning:** Scan uploaded files before making them accessible to other users.
- **Download:** Serve uploaded files to authorized clients efficiently.
- **Metadata:** Store filename, size, MIME type, uploader identity, upload timestamp, scan status.
- **Access control:** Files are accessible only to authorized users (owner, shared users, or public depending on product).
- **Deduplication (optional):** Avoid storing identical files twice (content-addressed storage).

Non-functional: upload throughput matching client bandwidth, resumability across hours-long interruptions, scan latency < 30 seconds for files up to 100MB, 99.99% durability (files never lost after upload completes).

**Q2. What are the scale assumptions and how do they drive design?**
A: Dropbox / Google Drive scale:
- **Daily uploads:** 500M files/day ≈ 5,800 uploads/sec (peak ~3×: ~17,500 uploads/sec).
- **Average file size:** 2MB (median across all file types — mix of docs, images, videos).
- **Upload throughput:** 17,500 uploads/sec × 2MB = 35GB/sec peak ingestion. This cannot go through application servers — must go direct-to-object-store.
- **Large file uploads:** 5% of files > 100MB → ~875 large file uploads/sec at peak, each needing chunking.
- **Storage:** 500M files/day × 2MB × 365 days × 5 years ≈ 1.8EB over 5 years. Object storage (S3, GCS) is the only viable option at this scale.
- **Virus scan queue:** 17,500 files/sec entering scan queue. Average scan time 2 seconds → need 35,000 concurrent scan workers at peak. In practice, scan is async and files are held in a quarantine state until cleared.

**Q3. What are the key design axes to state upfront?**
A: Before diving into components:
- **Upload path:** Do files go through your application servers (easy auth, high egress cost) or direct to object storage via pre-signed URLs (low cost, requires client-side logic)?
- **Chunking responsibility:** Client-side chunking (client splits, uploads each chunk) vs server-side chunking (server receives full stream, splits internally)?
- **Resumability protocol:** Custom protocol vs standard (TUS protocol)?
- **Scan placement:** Scan before making file accessible (blocks access until scanned) vs scan after (file accessible immediately, revoked if malicious)?
- **Storage tiers:** Hot storage for recent files, cold/archive for old files (S3 Intelligent-Tiering, Glacier)?

## Section 2: Upload Architecture

**Q4. Why should large file uploads bypass application servers and go directly to object storage?**
A: Routing uploads through application servers creates multiple problems at scale:
- **Memory pressure:** A 1GB file upload held in server memory while being proxied to S3 consumes 1GB of RAM per concurrent upload. With 1,000 concurrent large uploads, that's 1TB of RAM — impossible to provision.
- **Bandwidth cost:** Application servers pay egress to S3 *and* ingress from clients — you pay for data transfer twice. Direct-to-S3 uploads pay only client → S3 ingress (often free or cheaper).
- **Throughput ceiling:** Application server network is a bottleneck. S3 can absorb essentially unlimited parallel uploads.
- **Timeout risk:** A 10GB upload over a slow connection takes hours. HTTP connections through application servers have timeouts (load balancer: 60s, proxy: 300s) that kill long uploads.

**Solution: Pre-signed URLs.** The application server authenticates the user, generates a time-limited pre-signed URL (S3 `put_object` or GCS signed URL), and returns it to the client. The client uploads directly to object storage using that URL. The application server is not in the upload path.

**Q5. Walk through the complete upload flow for a large file using pre-signed URLs and chunking.**
A:
```
1. Client initiates upload:
   POST /uploads/initiate
   { filename, size, mime_type, chunk_size }
   → Server creates an upload_session record, returns { upload_id, chunk_urls[] }

2. Server generates pre-signed URLs:
   For each chunk (e.g., 5MB each for a 100MB file → 20 chunks):
   S3.generate_presigned_url("put_object",
       Bucket="uploads-quarantine",
       Key=f"{upload_id}/chunk_{i}",
       ExpiresIn=3600)
   → Returns array of 20 signed URLs, one per chunk

3. Client uploads chunks in parallel:
   HTTP PUT chunk_0_data → presigned_url_0
   HTTP PUT chunk_1_data → presigned_url_1
   ... (parallelism: 3–5 concurrent chunk uploads)
   Each S3 PUT returns an ETag (MD5 of the chunk content)

4. Client reports progress:
   PATCH /uploads/{upload_id}
   { completed_chunks: [{ index: 0, etag: "abc..." }, ...] }
   → Server records which chunks are done (in Redis or DB)

5. Client signals completion:
   POST /uploads/{upload_id}/complete
   { all_chunk_etags: [...] }
   → Server calls S3 CompleteMultipartUpload with all ETags
   → S3 assembles the file atomically

6. Server triggers post-processing:
   → Enqueue virus scan job
   → Update file status to SCANNING
   → Return { file_id, status: "scanning" }
```

**Q6. What is S3 Multipart Upload and how does it enable resumability?**
A: S3 Multipart Upload is AWS's native chunked upload protocol:
- **Initiation:** `CreateMultipartUpload` returns an `upload_id`.
- **Part upload:** Each part is uploaded via `UploadPart` with the `upload_id` and a part number (1–10,000). Each part must be ≥ 5MB (except the last). S3 returns an ETag per part.
- **Completion:** `CompleteMultipartUpload` with all ETags. S3 assembles the object atomically.
- **Abort:** `AbortMultipartUpload` cleans up partial uploads (must be done or you pay for partial part storage).

**Resumability:** The `upload_id` is durable on S3's side. If the client disconnects mid-upload, it can call `ListParts` to see which parts were already uploaded (and their ETags), then resume uploading only the remaining parts. No data already uploaded is re-sent.

**Q7. What is the TUS protocol and when would you use it instead of S3 Multipart?**
A: TUS (tus.io) is an open, resumable upload protocol implemented at the HTTP layer — independent of the underlying storage:

**Core TUS operations:**
- `POST /files` — create an upload resource, returns a URL and `Upload-Offset: 0`.
- `PATCH /files/{id}` with `Content-Type: application/offset+octet-stream` and `Upload-Offset` header — upload a chunk starting at the given byte offset. Server returns new `Upload-Offset`.
- `HEAD /files/{id}` — query current offset. Client uses this to determine where to resume.

**When to use TUS:**
- When you need resumability at the *protocol* level, not just the storage level — TUS works with any backend (local disk, S3, GCS, SFTP).
- When clients are diverse (browsers, mobile, CLI tools) and a standard protocol is preferable to a custom API.
- When uploads go through your application servers (not direct-to-S3) — TUS is well-suited to server-mediated uploads.
- TUS server implementations exist for Node.js, Go, Python, Ruby.

**When to use S3 Multipart instead:**
- When uploads go direct-to-S3 via pre-signed URLs — TUS requires a server intermediary.
- When you're fully committed to AWS and want native resumability without additional server logic.

**Q8. How do you handle chunk size selection?**
A: Chunk size is a trade-off between parallelism overhead and resume granularity:
- **Too small (< 1MB):** High overhead — many HTTP requests, many S3 PUT operations (S3 charges per request), many ETag round trips.
- **Too large (> 100MB):** Low parallelism — fewer concurrent uploads, coarser resume granularity (a failed chunk means re-uploading 100MB).
- **Sweet spot:** 5–20MB per chunk. AWS recommends 5–25MB for multipart uploads. 8MB is a common default (balances parallelism, S3 request cost, and resume granularity).

Adaptive chunk size: start with 5MB, measure upload speed of the first chunk, and adjust subsequent chunk sizes to target a chunk upload duration of ~10 seconds. Fast connection → larger chunks (fewer requests). Slow connection → smaller chunks (finer resume granularity).

## Section 3: Resumability

**Q9. How does the server track upload state for resumability?**
A: An `upload_sessions` table (PostgreSQL) plus a Redis state for hot access:

```sql
CREATE TABLE upload_sessions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(id),
    filename        TEXT NOT NULL,
    mime_type       TEXT NOT NULL,
    total_size      BIGINT NOT NULL,
    chunk_size      INT NOT NULL,
    total_chunks    INT NOT NULL,
    s3_upload_id    TEXT NOT NULL,           -- S3 Multipart Upload ID
    s3_bucket       TEXT NOT NULL,
    s3_key          TEXT NOT NULL,
    status          upload_status NOT NULL,  -- INITIATED, IN_PROGRESS, ASSEMBLING, COMPLETED, FAILED
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at      TIMESTAMPTZ NOT NULL,    -- abandoned upload cleanup
    completed_at    TIMESTAMPTZ
);

CREATE TABLE upload_chunks (
    upload_id       UUID NOT NULL REFERENCES upload_sessions(id),
    chunk_index     INT NOT NULL,
    etag            TEXT,                    -- null until uploaded
    size            BIGINT NOT NULL,
    uploaded_at     TIMESTAMPTZ,
    PRIMARY KEY (upload_id, chunk_index)
);
```

**Redis (hot path):**
- `upload:{upload_id}:chunks` — a Redis SET or bitmap of completed chunk indices. Fast O(1) membership checks without querying PostgreSQL on every chunk completion.
- `upload:{upload_id}:status` — current status string. Checked by the client's progress polling.

**Q10. How does a client resume an interrupted upload?**
A:
```
1. Client has a locally stored upload_id (persisted in localStorage or mobile storage).

2. Client calls:
   GET /uploads/{upload_id}/status
   → Server returns:
   {
     upload_id: "...",
     status: "IN_PROGRESS",
     completed_chunks: [0, 1, 2, 5],   // chunks 3 and 4 are missing
     total_chunks: 10,
     chunk_presigned_urls: {           // fresh URLs for missing chunks
       3: "https://s3.../...",
       4: "https://s3.../..."
     }
   }

3. Client uploads only the missing chunks (3 and 4).

4. Client calls POST /uploads/{upload_id}/complete once all chunks are done.
```

Key implementation details:
- Pre-signed URLs expire (typically 1 hour). The resume endpoint always issues fresh URLs for the remaining chunks — never assume the original URLs are still valid.
- Client must persist the `upload_id` durably (local storage, file, mobile keychain). If the ID is lost, the upload cannot be resumed — it must restart.
- Server-side expiry: upload sessions expire after 7 days of inactivity. A background job calls `AbortMultipartUpload` on S3 and deletes the session record to avoid paying for partial part storage.

**Q11. How do you handle the scenario where a client resumes but the server has no record of the upload session?**
A: This can happen if the server's DB was cleared, the session expired, or the client has a stale upload_id. The server returns a 404 or 410 Gone on `GET /uploads/{upload_id}/status`. The client must detect this and restart the upload from scratch:
- Generate a new `upload_id` (new session).
- Re-upload all chunks.
- Inform the user: "Upload expired, restarting." for transparency.

Mitigation — reduce occurrence:
- Store sessions with long expiry (7–30 days) and refresh expiry on each chunk completion.
- Use a stable, content-derived `upload_id` (e.g., hash of filename + file size + user_id). This allows re-associating a lost `upload_id` with the existing session if the user uploads the same file again.

## Section 4: Virus Scanning

**Q12. Where in the upload pipeline do you place virus scanning?**
A: Three possible placements, each with different trade-offs:

**Pre-availability scan (quarantine model):**
- File is uploaded to a quarantine bucket/prefix (not accessible to other users).
- Scan job runs. On clean → move to production bucket, update status to AVAILABLE. On malicious → delete, notify uploader, update status to REJECTED.
- **Pros:** Malicious files are never served. Strong safety guarantee.
- **Cons:** Latency before file is available (scan time: 2–30 seconds for most files, minutes for large files). Poor UX for time-sensitive uploads ("I just uploaded, why can't I share it yet?").

**Post-availability scan (optimistic model):**
- File is immediately accessible after upload completes.
- Scan job runs async. On malicious → revoke access, delete file, notify affected users who may have downloaded it.
- **Pros:** Zero scan latency for the user. Files shareable immediately.
- **Cons:** Window of exposure where malicious files are accessible. Harder to notify users who already downloaded. May be unacceptable for regulated industries (healthcare, finance).

**Hybrid (tiered by file type and user trust):**
- Executable files, archives (.zip, .tar), Office documents (macro-enabled) → quarantine model (high risk, must scan first).
- Images, plain text, PDFs from verified users → optimistic model with background scan.
- Anonymous / unverified users → always quarantine model.

**Recommendation:** Quarantine model for a general file upload system. Make the scan fast (< 10 seconds for files < 10MB) and transparent to the user with a progress indicator.

**Q13. What does the virus scanning pipeline look like architecturally?**
A:
```
Upload Complete
      ↓
File lands in S3 (quarantine-bucket/{upload_id}/{filename})
      ↓
S3 Event Notification → SQS Queue (scan-jobs)
      ↓
Scan Worker Fleet (auto-scaling EC2 / ECS tasks)
  ├── Pull job from SQS
  ├── Download file from S3 quarantine bucket (stream, don't load fully into memory)
  ├── Pipe to ClamAV / commercial AV engine (ICAP protocol or CLI)
  ├── Record result: CLEAN / INFECTED / SCAN_ERROR
  └── On CLEAN:
        S3 CopyObject: quarantine-bucket → production-bucket
        Update files table: status = AVAILABLE
        Publish FileAvailableEvent to Kafka
      On INFECTED:
        S3 DeleteObject from quarantine
        Update files table: status = REJECTED, rejection_reason = 'malware'
        Notify user (email / in-app notification)
        Log threat details for security team
      On SCAN_ERROR:
        Retry up to 3 times with backoff
        After max retries: quarantine, alert security team for manual review
```

**Q14. How do you scan files without loading them entirely into memory?**
A: Large files (several GB) cannot be fully buffered in a scan worker's RAM. Stream-based scanning:
- **Streaming download from S3:** Use S3's `get_object` with a streaming response. Process the byte stream in chunks.
- **Streaming to ClamAV:** ClamAV supports streaming via its INSTREAM command over a TCP connection:

```python
import socket
import boto3

def scan_s3_file_streaming(bucket, key):
    s3 = boto3.client('s3')
    response = s3.get_object(Bucket=bucket, Key=key)
    body = response['Body']

    sock = socket.create_connection(('clamd', 3310))
    sock.send(b'nINSTREAM\n')
    while True:
        chunk = body.read(65536)  # 64KB chunks
        if not chunk:
            break
        size = len(chunk).to_bytes(4, 'big')
        sock.send(size + chunk)
    sock.send(b'\x00\x00\x00\x00')  # end of stream
    result = sock.recv(1024).decode()
    sock.close()
    return 'FOUND' not in result  # True = clean
```

This approach scans a 10GB file using only 64KB of RAM in the scan worker.

**Q15. What are the limitations of ClamAV and when do you use commercial scanning?**
A: ClamAV is open-source, free, and widely deployed, but has real limitations:
- **Detection rate:** ClamAV's detection rate for zero-day and novel malware is significantly lower than commercial engines (AV-TEST scores ClamAV at 70–80% vs commercial engines at 99%+).
- **Signature update lag:** ClamAV signatures update daily. New malware may have a 24-hour window before detection.
- **Performance:** Scanning large files is CPU-intensive. ClamAV single-threaded scanning of a 1GB file takes 10–30 seconds.

**Commercial AV via ICAP:**
- Symantec, Sophos, Trend Micro, and others expose AV scanning via the ICAP protocol.
- Your scan service sends the file to the ICAP server, receives a verdict.
- Much higher detection rates, faster signature updates, better performance.
- Cost: typically per-scan or per-GB pricing.

**Multi-engine scanning:**
- Services like VirusTotal (via API) scan with 70+ engines simultaneously.
- Returns per-engine verdicts. Use a threshold: if > 2 engines flag a file, reject it.
- Best for high-value file uploads where false negatives are unacceptable.
- Cost and latency are higher — appropriate for security-critical use cases, not for consumer file storage at billions of daily uploads.

**Q16. How do you handle false positives (legitimate files flagged as malicious)?**
A: False positives (clean files incorrectly flagged) are a real operational concern — ClamAV and even commercial engines occasionally flag legitimate files (PDFs with certain embedded fonts, compressed archives with specific signatures):
- **Appeal process:** Provide the user a "Report false positive" option. Trigger a manual review by the security team.
- **Whitelist by hash:** Maintain a whitelist of known-good file hashes (SHA-256). Files matching a whitelist hash skip scanning or override a INFECTED verdict. Useful for common enterprise files (Office templates, standard installers).
- **Second-opinion scan:** On INFECTED verdict, automatically scan with a second engine before final rejection. Only reject if both engines agree.
- **Graceful notification:** Don't say "your file contains malware" if it might be a false positive. Say "your file couldn't be verified — please contact support" to avoid alarming users unnecessarily.

## Section 5: Post-Upload Processing

**Q17. What post-upload processing happens beyond virus scanning?**
A: A file upload triggers a pipeline of async processing jobs via an event-driven architecture:

```
FileUploadCompleteEvent (Kafka)
    ├── Virus Scanner         → marks file CLEAN / INFECTED
    ├── Metadata Extractor    → EXIF from images, document properties, duration for video
    ├── Thumbnail Generator   → create 128×128, 512×512 thumbnails for images/video
    ├── Content Indexer       → extract text from PDFs/docs for full-text search
    ├── Deduplication Check   → compare SHA-256 hash against existing files
    └── Storage Tier Assigner → tag file for hot/warm/cold storage based on type/age policy
```

Each processor is an independent Kafka consumer, scaling independently. A file is not "available" until the virus scan completes (quarantine model). Other processors run concurrently after the file is available.

**Q18. How do you implement content deduplication to avoid storing the same file twice?**
A: Content-addressable storage using SHA-256:
- On upload completion (before or during chunk assembly), compute SHA-256 of the full file content.
- Check a `content_hashes` table: `SELECT file_id FROM files WHERE sha256 = $hash AND owner_id = $user` (or globally if cross-user deduplication is desired).
- If found: don't store a new S3 object. Create a new `files` record pointing to the existing S3 key. Increment a reference count.
- If not found: proceed with storage, record the hash.

**Client-side deduplication:** Compute the hash on the client before initiating the upload. Send the hash with `POST /uploads/initiate`. If the server already has this hash, skip the upload entirely and return the existing file metadata. Saves the entire upload bandwidth cost.

**Chunk-level deduplication (rsync delta):** For updated files (new version of a document), compare chunk hashes against previous version — only upload chunks that have changed. Complex to implement but powerful for large files with small edits.

**Q19. How do you handle file versioning?**
A: When a user uploads a new version of an existing file:
- Create a new `file_versions` record linking to the new S3 object.
- The `files` record's `current_version_id` is updated atomically.
- Old versions are retained (accessible via version history) until explicitly deleted or until a retention policy expires them.
- S3 has native versioning — enable it on the bucket to automatically preserve previous object versions on overwrite.

```sql
CREATE TABLE file_versions (
    id              UUID PRIMARY KEY,
    file_id         UUID NOT NULL REFERENCES files(id),
    version_number  INT NOT NULL,
    s3_key          TEXT NOT NULL,
    size            BIGINT NOT NULL,
    sha256          TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL,
    created_by      UUID NOT NULL REFERENCES users(id),
    UNIQUE (file_id, version_number)
);
```

## Section 6: Download & Access Control

**Q20. How do you serve large files to clients efficiently?**
A: Never proxy large file downloads through application servers — same reasons as uploads. Use pre-signed download URLs or a CDN:

**Pre-signed S3 download URL:**
```python
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'production-bucket', 'Key': s3_key},
    ExpiresIn=300   # 5-minute window
)
return redirect(url)  # 302 redirect to S3
```

The client downloads directly from S3. Application server only handles the auth check and URL generation.

**CDN for frequently accessed files:**
- Place CloudFront (or Cloudflare) in front of the S3 bucket.
- Popular files are cached at edge PoPs globally — faster download, lower S3 egress cost.
- Signed CDN URLs for private files: `CloudFront.sign_url(url, key_pair_id, private_key, expires)`.

**Byte-range requests (partial downloads / resume):**
- S3 and CDN both support `Range: bytes=0-1048575` headers.
- Clients can download specific byte ranges — enables download resume (if download interrupted, client sends `Range: bytes={downloaded_so_far}-`) and video seeking (media players request specific timestamp ranges without downloading the whole file).

**Q21. How do you implement access control for files?**
A: Multi-layer access control:

**Ownership:**
- Every file has an `owner_id`. Owner has full access (read, update, delete, share).

**Sharing model:**
```sql
CREATE TABLE file_permissions (
    file_id     UUID NOT NULL REFERENCES files(id),
    grantee_id  UUID REFERENCES users(id),   -- null = public
    permission  TEXT NOT NULL,               -- READ, WRITE, ADMIN
    granted_by  UUID NOT NULL REFERENCES users(id),
    expires_at  TIMESTAMPTZ,
    PRIMARY KEY (file_id, COALESCE(grantee_id, '00000000-0000-0000-0000-000000000000'))
);
```

**Link sharing:**
- Generate a shareable token: `share:{random_32_bytes_base64}`.
- Store in Redis: `share:{token} → { file_id, permission, expires_at }`.
- Anyone with the link can access the file (optionally with password protection).

**Pre-signed URL scoping:**
- Pre-signed S3 URLs are time-limited (5 minutes for download links). Even if leaked, they expire quickly.
- For sensitive files: generate URLs with a 60-second expiry; client uses them immediately.
- Never embed long-lived S3 URLs in responses — always generate fresh URLs on each access request after an auth check.

## Section 7: Scenario / System Design Style Questions

**Q22. "Walk me through the complete design of a file upload system."**
A: Full system components:

**Upload Service:**
- `POST /uploads/initiate` — auth check, create S3 Multipart Upload, create upload_session record, return upload_id + chunk pre-signed URLs.
- `PATCH /uploads/{id}/chunks/{n}` — mark chunk complete, store ETag (or client calls this implicitly via S3 event).
- `GET /uploads/{id}/status` — return completed chunks + fresh URLs for remaining (resume support).
- `POST /uploads/{id}/complete` — call S3 CompleteMultipartUpload, create file record, enqueue scan job.

**Storage Layer:**
- S3 quarantine bucket (`uploads-quarantine`) — destination for all new uploads. No public access. Lifecycle policy: delete objects older than 7 days (cleanup for abandoned uploads).
- S3 production bucket (`files-production`) — files promoted here after clean scan. Versioning enabled. Lifecycle policy: transition to S3 Intelligent-Tiering after 30 days (auto hot/cold).

**Scan Pipeline:**
- S3 Event → SQS → Scan Worker Fleet (ECS Fargate, auto-scale on queue depth).
- ClamAV + commercial ICAP for critical file types.
- On clean: S3 CopyObject quarantine → production. Update file status. Publish FileAvailable event.
- On infected: delete from quarantine, update status, notify user, log to SIEM.

**File Metadata DB (PostgreSQL):**
- `files` table: file_id, owner_id, s3_key, sha256, size, mime_type, status, version.
- `upload_sessions` table: upload tracking state.
- `file_permissions` table: sharing ACL.
- `file_versions` table: version history.

**Post-Processing (Kafka consumers):**
- Thumbnail Service, Metadata Extractor, Content Indexer, Deduplication Service.

**Download Service:**
- Auth check → generate pre-signed S3 URL or signed CDN URL → 302 redirect.
- CDN (CloudFront) in front of production bucket for popular files.

**Q23. "A user reports their 8GB video upload fails every time at around 70% completion. How do you diagnose and fix it?"**
A: Systematic diagnosis:

**Step 1 — Check upload session state:**
Query `upload_sessions` and `upload_chunks` for the user's upload_id. Confirm which chunks completed and which failed. If chunks 0–13 completed (out of 20) and chunk 14 consistently fails, the issue is chunk-14-specific.

**Step 2 — Check S3 Multipart Upload state:**
Call `ListParts` on the S3 upload_id. Verify that parts S3 acknowledges match what the DB records as complete. Mismatch → the DB was not updated despite S3 accepting the part (app server crash after S3 PUT but before DB update). Fix: reconcile DB from S3's ListParts response.

**Step 3 — Investigate the failure mode:**
- **Client-side timeout:** The pre-signed URL for chunk 14 expired (URLs issued at session start expire after 1 hour; if the user uploaded slowly, hours-old URLs are stale). Fix: resume endpoint always issues fresh URLs.
- **Network interruption:** Client's connection drops at ~70% consistently (pattern suggests a specific time duration, not a specific chunk). Fix: reduce chunk size so each upload completes in < 60 seconds, well within any intermediate proxy timeout.
- **S3 rate limiting:** If the user is uploading too many chunks in parallel, S3 may throttle with 503 SlowDown. Fix: cap parallel chunk uploads to 3.
- **Chunk size mismatch:** If chunk 14 is the last chunk and it's smaller than 5MB, S3 Multipart requires the final part to be ≥ 5MB unless it's the only part. Fix: ensure final chunk is handled correctly (S3 allows the final part to be any size ≥ 1 byte — verify the client's chunk logic isn't accidentally combining the last two chunks).

**Step 4 — Fix and verify:**
After fixing the root cause, the user resumes from chunk 14 using the resume flow. No re-upload of the already-completed 70%.

**Q24. "Your virus scan queue is backing up — files are sitting in quarantine for 45 minutes before being scanned. What's your response?"**
A: Queue backup indicates scan worker capacity is insufficient for the current upload volume:

**Immediate (minutes):**
- Scale out scan worker fleet. If running on ECS/Fargate with SQS-based auto-scaling, reduce the scale-out cooldown period. Manually trigger scale-out to maximum capacity.
- Check if the backup is caused by a few very large files monopolizing workers (a 100GB file held by one worker for 30 minutes blocks that worker from processing thousands of small files). Fix: implement file-size-based priority queues — separate SQS queues for small (< 10MB), medium (10–500MB), and large (> 500MB) files. Small files get scanned first.

**Short-term (hours):**
- Switch large file scans to streaming mode (Q14) if not already — reduces per-scan memory and wall-clock time.
- Enable parallel scanning: split large files into segments, scan each segment in parallel across multiple workers, aggregate results. If any segment is infected, the file is infected.
- Increase ClamAV thread count per worker if CPU is underutilized.

**Medium-term (days):**
- Implement tiered scanning: quick hash-based check first (SHA-256 against known-bad hash database — milliseconds). Only do full AV scan if hash is not in known-bad or known-good list. Known-good (whitelisted) files skip scan entirely.
- Add CDN-level caching for scan results: if the same SHA-256 was scanned and cleared in the last 24 hours, skip re-scanning. Store `sha256 → CLEAN` in Redis with 24h TTL.

**Q25. "Design the chunking and reassembly flow for a file upload system where uploads go through your servers (not direct to S3)."**
A: Server-mediated uploads — necessary when you need to process the stream (encrypt, compress, transform) before writing to storage, or when S3 pre-signed URLs are not an option.

**Chunk upload endpoint:**
```python
@app.put("/uploads/{upload_id}/chunks/{chunk_index}")
def upload_chunk(upload_id: str, chunk_index: int, body: bytes):
    # Validate auth and upload session
    session = db.get_upload_session(upload_id)
    assert session.status == 'IN_PROGRESS'
    assert 0 <= chunk_index < session.total_chunks
    assert len(body) <= session.chunk_size + 1024  # allow slight oversize

    # Write chunk to temp storage (local disk or S3 temp prefix)
    chunk_key = f"temp/{upload_id}/chunk_{chunk_index:04d}"
    s3.put_object(Bucket='upload-temp', Key=chunk_key, Body=body)

    # Record chunk completion
    redis.sadd(f"upload:{upload_id}:chunks", chunk_index)
    db.mark_chunk_complete(upload_id, chunk_index, len(body))

    return {"chunk_index": chunk_index, "received": len(body)}
```

**Reassembly (triggered on complete):**
```python
def reassemble_file(upload_id: str):
    session = db.get_upload_session(upload_id)
    chunk_keys = [f"temp/{upload_id}/chunk_{i:04d}"
                  for i in range(session.total_chunks)]

    # Stream-concatenate chunks into a single S3 multipart upload
    mpu = s3.create_multipart_upload(Bucket='quarantine', Key=session.s3_key)
    parts = []
    for i, chunk_key in enumerate(chunk_keys, start=1):
        chunk_obj = s3.get_object(Bucket='upload-temp', Key=chunk_key)
        response = s3.upload_part(
            Bucket='quarantine', Key=session.s3_key,
            UploadId=mpu['UploadId'], PartNumber=i,
            Body=chunk_obj['Body'].read()
        )
        parts.append({'PartNumber': i, 'ETag': response['ETag']})

    s3.complete_multipart_upload(
        Bucket='quarantine', Key=session.s3_key,
        UploadId=mpu['UploadId'],
        MultipartUpload={'Parts': parts}
    )
    # Cleanup temp chunks
    for key in chunk_keys:
        s3.delete_object(Bucket='upload-temp', Key=key)
```

This approach keeps application server memory bounded — each chunk is streamed to S3 temp storage immediately, then re-streamed into the final assembly without full buffering.

## Quick Reference: Component Decisions Summary

| Component | Choice | Rationale |
|---|---|---|
| Upload path | Pre-signed S3 URLs (direct-to-S3) | Avoids server memory/bandwidth bottleneck; scales to GB/sec |
| Chunking protocol | S3 Multipart Upload | Native S3 resumability; ListParts for resume reconciliation |
| Alternative protocol | TUS | Server-mediated uploads; storage-agnostic; cross-platform |
| Chunk size | 8MB default, adaptive | Balances S3 request cost, parallelism, resume granularity |
| Upload state tracking | PostgreSQL (durable) + Redis (hot path) | DB for resume source-of-truth; Redis for fast chunk status checks |
| Session expiry | 7 days, extended on activity | Covers multi-day slow uploads; AbortMultipartUpload on expiry |
| Scan placement | Quarantine model (pre-availability) | Malicious files never served; scan before production access |
| Scan engine | ClamAV + commercial ICAP for high-risk | Open-source baseline + commercial for better detection |
| Scan performance | Streaming (64KB chunks), parallel workers | Scans GB files without memory exhaustion |
| Scan scaling | SQS + size-tiered queues + ECS auto-scale | Prevents large files from blocking small file scan queue |
| Deduplication | SHA-256 content hash, client-side check first | Avoids redundant storage; client-side skips upload bandwidth |
| Download path | Pre-signed URL / signed CDN URL (302 redirect) | Client downloads direct from S3/CDN; server handles only auth |
| Large file download | Byte-range requests (S3 Range header) | Enables resume, video seeking, partial content |
| Access control | DB ACL + Redis link-share tokens + short-lived pre-signed URLs | Layered: structural permissions + ephemeral URL expiry |

**Tip for the interview:** File upload system questions reward completeness across three distinct problem spaces: the upload pipeline (pre-signed URLs, chunking, resumability), the safety pipeline (virus scanning placement, streaming scan, false positives), and the access pipeline (CDN, pre-signed downloads, access control). The most common gaps: not explaining *why* uploads bypass application servers (memory, bandwidth, timeout — all three), not addressing how resumability actually works end-to-end (the client persists the upload_id, queries for missing chunks, gets fresh pre-signed URLs, uploads only remaining chunks), and treating virus scanning as a black box ("we scan it") without discussing placement (quarantine vs optimistic), streaming (memory-bounded scanning), and scaling (size-tiered queues). The scan queue backup scenario (Q24) is a favourite because it tests both operational instinct and architectural foresight — pre-partition by file size from day one.
