# Design a URL Shortener (Hashing, Redirect, Analytics) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Estimation

**Q1. What are the functional requirements of a URL shortener?**
A: Core requirements:
- **Shorten:** Given a long URL, return a short alias (e.g., `https://short.ly/aB3xKp`).
- **Redirect:** Given a short code, redirect the user to the original long URL (HTTP 301 or 302).
- **Custom alias:** Optionally allow users to specify their own short code (e.g., `short.ly/launch2026`).
- **Expiry:** Optionally allow links to expire after a date or number of uses.
- **Analytics:** Track click counts, timestamps, referrers, user agents, and geo-location per short link.

Non-functional requirements: low redirect latency (p99 < 20ms), high availability (99.99%), globally consistent short code uniqueness, horizontally scalable read path.

**Q2. What are the scale assumptions and how do they drive design?**
A: Typical interview scale — 100M new URLs per day (creation), 10B redirects per day (reads):
- **Write QPS:** 100M / 86,400 ≈ 1,200 writes/sec (peak ~3×: ~3,600 writes/sec).
- **Read QPS:** 10B / 86,400 ≈ 115,000 reads/sec (peak ~3×: ~350,000 reads/sec).
- **Read:write ratio:** ~100:1 — heavily read-dominant. Cache is critical.
- **Storage:** Each mapping ~500 bytes (short code + long URL + metadata). 100M/day × 365 × 5 years × 500B ≈ ~90TB over 5 years.
- **Short code length:** 7 alphanumeric characters [a-zA-Z0-9] = 62^7 ≈ 3.5 trillion combinations — sufficient for years of growth at this scale.

**Q3. Should redirects use HTTP 301 or 302, and why does it matter for analytics?**
A: A critical design decision with real trade-offs:
- **301 Permanent Redirect** — browsers cache the redirect permanently. Subsequent requests for the same short URL go directly to the destination, bypassing your servers entirely. Lower server load, faster for repeat users. **Fatal for analytics** — you never see repeat clicks from the same browser.
- **302 Temporary Redirect** — browsers do not cache. Every click hits your redirect service. Accurate click tracking, but higher server load and slightly higher latency (one extra network hop each time).
- **Recommendation:** Use 302 for analytics-enabled links. Optionally use 301 for "fire and forget" links where click tracking is explicitly disabled, since it reduces infrastructure cost for those links.

## Section 2: Short Code Generation

**Q4. What are the main approaches to generating short codes?**
A: Three primary approaches, each with distinct trade-offs:

**Approach 1 — Hash-based:** Hash the long URL (MD5, SHA-256, MurmurHash), take the first 7 characters of the base62-encoded hash. Fast, deterministic (same URL always produces the same code — natural deduplication). Risk: hash collisions in the truncated 7-char space; requires collision detection and retry.

**Approach 2 — Random ID generation:** Generate a cryptographically random 7-character base62 string. Check uniqueness against the DB before storing. Simple, no collision by hash truncation, but requires a uniqueness check on every write and doesn't naturally deduplicate same-URL inputs.

**Approach 3 — Auto-increment + base62 encoding:** Use a globally unique auto-increment ID (from a DB sequence or a dedicated ID generator service), then base62-encode it. ID 1 → `0000001`, ID 3.5T → `zzzzzzz`. Guaranteed uniqueness (no collision check needed), naturally ordered, easy to shard. Most production systems use this approach or a variant.

**Q5. How does base62 encoding work for short codes?**
A: Base62 uses the character set `[0-9a-zA-Z]` — 62 characters. To encode an integer N:

```python
CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode(n: int) -> str:
    if n == 0:
        return CHARS[0]
    result = []
    while n > 0:
        result.append(CHARS[n % 62])
        n //= 62
    return ''.join(reversed(result))

def decode(s: str) -> int:
    n = 0
    for c in s:
        n = n * 62 + CHARS.index(c)
    return n
```

A 7-character base62 string encodes integers up to 62^7 − 1 ≈ 3.5 trillion. At 1,200 new URLs/sec, you exhaust the 7-char space in ~90 years.

**Q6. How do you handle hash collisions in hash-based short code generation?**
A: Since you truncate a large hash to 7 characters, two different long URLs can produce the same short code. Mitigation:
- On write, attempt to INSERT the (short_code, long_url) pair with a unique constraint on short_code.
- On conflict, check if the existing entry has the same long URL (return existing code — natural deduplication) or a different long URL (true collision — append a salt to the input and rehash, retry up to N times).
- In practice, with 62^7 ≈ 3.5 trillion slots and a few billion stored URLs, collision probability per insert is negligible (~10^-6). But you must handle it defensively.

**Q7. What is a distributed ID generator and why is it preferred at scale?**
A: At high write QPS across multiple service instances, a single DB auto-increment sequence becomes a bottleneck (every write serializes through the sequence). Distributed ID generators solve this:

**Twitter Snowflake:** 64-bit IDs composed of timestamp + datacenter ID + machine ID + sequence. Globally unique without coordination between machines. IDs are roughly time-ordered. No single point of contention. Base62-encode the lower 42 bits (or the full 64 bits with an 11-char code) for the short code.

**Range pre-allocation:** A central ID service (or Zookeeper) allocates ranges of IDs to each application server (e.g., "server A owns IDs 1,000,001–2,000,000"). Each server uses its range locally without network calls. When the range is exhausted, it requests a new one. Low coordination overhead, simple implementation.

**Q8. How do you deduplicate — avoid creating a new short code for a long URL that already has one?**
A: Two approaches:
- **Hash-based lookup:** Maintain a secondary index (or separate table) keyed by `hash(long_url)`. On a new shorten request, check this index first. If found, return the existing short code. If not, create a new one. Works well with hash-based generation (the hash is already computed).
- **Accept duplicates:** Don't deduplicate at all — different users shortening the same URL get different short codes. Simpler system, costs slightly more storage. Analytics are naturally segmented per short code (useful when you want per-campaign tracking of the same destination URL). Many production URL shorteners (Bitly) take this approach by default, with optional "find existing" API for deduplication.

## Section 3: Data Model & Storage

**Q9. What is the core data model for a URL shortener?**
A: Two primary tables:

**`url_mappings` (the core table):**
```sql
CREATE TABLE url_mappings (
    id            BIGINT PRIMARY KEY,           -- auto-increment or Snowflake ID
    short_code    VARCHAR(10) UNIQUE NOT NULL,  -- base62-encoded ID or custom alias
    long_url      TEXT NOT NULL,
    user_id       BIGINT,                       -- nullable (anonymous shortening allowed)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at    TIMESTAMPTZ,                  -- nullable = never expires
    is_active     BOOLEAN NOT NULL DEFAULT true,
    click_count   BIGINT NOT NULL DEFAULT 0     -- denormalized counter (optional)
);
CREATE INDEX idx_short_code ON url_mappings(short_code);  -- primary read path
CREATE INDEX idx_user_id    ON url_mappings(user_id);     -- for user dashboard
```

**`click_events` (analytics raw log):**
```sql
CREATE TABLE click_events (
    id            BIGSERIAL PRIMARY KEY,
    short_code    VARCHAR(10) NOT NULL,
    clicked_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    ip_address    INET,
    user_agent    TEXT,
    referrer      TEXT,
    country_code  CHAR(2),
    city          VARCHAR(100)
);
CREATE INDEX idx_click_short_code ON click_events(short_code, clicked_at DESC);
```

**Q10. How do you choose the right database for each component?**
A:
- **URL mappings (core redirect data):** PostgreSQL or MySQL — strong consistency, ACID, simple indexed lookups by short_code. Low write QPS (3,600/sec is manageable). Alternatively, DynamoDB with short_code as partition key for serverless simplicity and automatic scaling.
- **Cache layer (redirect hot path):** Redis — short_code → long_url mappings. 350,000 reads/sec is trivially handled by Redis. A full dataset of 100M mappings × ~200 bytes ≈ 20GB — fits in a single large Redis instance. TTL = 24–48 hours (most links peak in first 24 hours).
- **Click events (analytics writes):** Kafka → data warehouse (ClickHouse, BigQuery, Redshift). Write at 115,000 events/sec — OLTP databases can't handle this analytically. Write to Kafka immediately; a consumer aggregates and writes to the warehouse in batches. Counter increments to `click_count` are batched and flushed periodically.

**Q11. How do you store and serve custom aliases?**
A: Custom aliases share the same `url_mappings` table — short_code is just a user-provided string instead of a base62-encoded ID. Constraints:
- Unique constraint on `short_code` prevents conflicts between auto-generated and custom codes.
- Validate custom aliases: allow only `[a-zA-Z0-9_-]`, length 3–50, reject reserved words (`api`, `admin`, `health`, `robots.txt`, etc.).
- Custom aliases are never auto-generated — use a flag or nullable `custom_alias_requested` column for analytics.
- Charge for custom aliases (business model) or rate-limit them to prevent squatting.

## Section 4: Redirect Service

**Q12. Walk through the end-to-end redirect request flow.**
A: A user clicks `https://short.ly/aB3xKp`:

```
1. DNS resolves short.ly → Load Balancer IP
2. Load Balancer routes GET /aB3xKp to a Redirect Service instance
3. Redirect Service extracts short_code = "aB3xKp"
4. Check local in-process cache (L1, ~1ms, tiny LRU for hottest codes)
   → Hit: return 302 with Location header, done
   → Miss: go to step 5
5. Check Redis (L2, ~1ms over network)
   → Hit: populate L1 cache, return 302
   → Miss: go to step 6
6. Query PostgreSQL: SELECT long_url, is_active, expires_at FROM url_mappings WHERE short_code = 'aB3xKp'
   → Not found: return 404
   → Found but expired/inactive: return 410 Gone
   → Found: populate Redis (TTL 24h), populate L1, return 302
7. Asynchronously (fire-and-forget): publish click event to Kafka
   → Kafka consumer writes to ClickHouse + increments Redis counter
```

Total latency target: < 10ms p99 for cache hits (steps 1-5), < 50ms for DB fallback (step 6).

**Q13. How do you make the redirect service handle 350,000 RPS with low latency?**
A: Layered approach:
- **Stateless redirect instances** — horizontally scalable behind a load balancer. No shared state in-process (state lives in Redis). Add instances freely.
- **Redis as the primary data store for hot path** — at 350k RPS, with 99% cache hit rate, only 3,500 RPS reach the DB. Redis handles 350k+ reads trivially.
- **Local L1 cache per instance** — a small in-process LRU cache (e.g., 10,000 most recently accessed codes, TTL 60 seconds) absorbs the hottest links without any network call. On a 10-instance fleet, this gives 100,000 L1-cached codes collectively.
- **Connection pooling** — Redis and PostgreSQL connections are pooled per instance. Avoid re-establishing connections per request.
- **Async analytics** — click event recording is fire-and-forget via Kafka. Never block the redirect response on analytics writes.
- **HTTP keep-alive** — redirect responses are tiny (< 1KB). Keep-alive on the load balancer connection eliminates TCP handshake overhead for repeat clicks from the same client.

**Q14. How do you handle link expiry efficiently?**
A: Two components:
- **At redirect time:** Check `expires_at` (stored in Redis alongside `long_url`). If expired, return 410 Gone. Zero additional DB query since expiry is cached with the URL.
- **Cleanup of expired rows:** A background job runs nightly, deleting rows where `expires_at < now()`. Batch deletes in small chunks (1,000 rows at a time) to avoid lock contention. Alternatively, rely on TTL-based eviction if using DynamoDB or a document store.
- **Use count limits:** For "expires after N clicks" links, atomically decrement a Redis counter on each click; when it hits zero, mark the link inactive and return 410 on subsequent requests.

## Section 5: Analytics

**Q15. What analytics data do you collect per click, and how?**
A: Per click event:
- `short_code` — which link was clicked.
- `clicked_at` — timestamp (millisecond precision).
- `ip_address` — for geo-lookup (country, city, ASN).
- `user_agent` — for device/browser/OS parsing.
- `referrer` — HTTP Referer header (where the click came from).
- `accept_language` — locale/language of the user's browser.

**Collection:** After the redirect response is sent (non-blocking), the redirect service publishes a `ClickEvent` protobuf message to Kafka (topic: `click-events`). This is fully async — the user's redirect is not delayed by analytics. A consumer service reads from Kafka, enriches (geo-lookup from IP, UA parsing), and writes to ClickHouse (or BigQuery) in micro-batches.

**Q16. How do you implement real-time click counters efficiently?**
A: Don't write to the DB on every click — at 115,000 clicks/sec, that's 115,000 UPDATE statements/sec, which would overwhelm PostgreSQL. Instead:

**Redis counter with periodic flush:**
```python
# On each click (in redirect service, async):
redis.incr(f"clicks:{short_code}")

# Background job every 30 seconds:
for short_code in redis.scan_match("clicks:*"):
    count = redis.getdel(f"clicks:{short_code}")  # atomic get + delete
    db.execute(
        "UPDATE url_mappings SET click_count = click_count + $1 WHERE short_code = $2",
        count, short_code
    )
```

**HyperLogLog for unique visitors:** Redis HyperLogLog (`PFADD clicks:unique:{short_code} {ip}`) gives an approximate count of unique IPs with < 1% error and O(1) memory (~12KB per counter regardless of cardinality). Exact unique counts require storing all IPs, which is expensive at scale.

**Q17. How do you serve analytics queries efficiently?**
A: OLTP databases (PostgreSQL) are not suited for analytical queries over billions of click events. Architecture:

```
Kafka (raw click stream)
    ↓
ClickHouse / BigQuery / Redshift (OLAP warehouse)
    ↓ (pre-aggregated materialized views / scheduled jobs)
Analytics API → Dashboard
```

Pre-aggregate common queries as materialized views or scheduled rollups:
- `clicks_by_hour` — for time-series charts.
- `clicks_by_country` — for geo maps.
- `clicks_by_referrer` — for traffic source breakdown.
- `clicks_by_device` — for device breakdown.

These rollups are updated every 5–60 minutes. Real-time counts come from Redis. Historical analysis comes from ClickHouse. This tiered approach avoids scanning billions of raw rows for every dashboard load.

**Q18. How do you handle analytics for extremely high-traffic links (viral links)?**
A: A single link going viral (e.g., 10M clicks in an hour) creates hot spots:
- **Redis counter:** `INCR` on a single key is serialized in Redis — at extreme rates this becomes a bottleneck. Use local counters in the redirect service instances, flushed to Redis in batches (every 100ms or every 1,000 increments).
- **Kafka partitioning:** Partition the `click-events` topic by `short_code`. A viral link may saturate a single partition — use a random suffix on the partition key to spread load, then de-duplicate in the consumer.
- **Analytics approximate counts:** For viral links, exact counts are less important than order-of-magnitude. Use approximate counters (Bloom filters, HyperLogLog, Count-Min Sketch) for real-time display; exact counts from the warehouse for post-hoc analysis.

## Section 6: Advanced Design Topics

**Q19. How do you handle custom domains (e.g., `go.mycompany.com/campaign`)?**
A: Multi-tenant vanity domain support:
- Add a `domain` column to `url_mappings`. Primary key becomes `(domain, short_code)`.
- On redirect request, the HTTP `Host` header identifies the tenant domain. Look up `(host, short_code)` in Redis/DB.
- DNS: tenant configures a CNAME pointing their domain to your redirect service's load balancer.
- TLS: Use Let's Encrypt wildcard certs or a cert-per-domain via ACME. Cloudflare for SaaS handles this at scale.
- Namespace short codes per domain — `go.mycompany.com/abc` and `short.ly/abc` are different entries.

**Q20. How do you prevent abuse (spam links, malicious URLs)?**
A: Defense in depth:
- **URL validation on creation:** Check that the long URL is a valid, reachable URL (HTTP HEAD request with timeout). Reject obviously malformed URLs.
- **Malicious URL scanning:** Integrate with Google Safe Browsing API or VirusTotal on creation. Reject known phishing/malware URLs immediately. Re-scan periodically for links that become malicious after creation.
- **Rate limiting on creation:** Cap new short link creation per IP, per user account, and per API key. Prevent bulk spam generation.
- **Link deactivation:** Maintain a blocklist of short codes whose long URLs have been flagged. On redirect, check blocklist (Redis SET, O(1) lookup). Return 410 Gone for flagged links.
- **Click anomaly detection:** Alert on links with abnormally high click velocity (e.g., >10,000 clicks/minute from the same IP range) — possible click fraud or DDoS amplification via redirect.

**Q21. How do you scale the creation service to handle write spikes?**
A: Creation (1,200 writes/sec, peak 3,600) is much lighter than redirects, but spikes during marketing campaigns or API client bursts can be significant:
- **Stateless creation instances** — scale horizontally. Each instance generates its own Snowflake IDs without coordination.
- **Async creation with queue:** Accept the long URL, enqueue to Kafka, return a "pending" response with a job ID. A consumer processes the queue and stores the mapping. The client polls or receives a webhook with the final short code. Useful for bulk creation APIs (create 1M links for a campaign), less so for interactive web UIs.
- **Write buffering:** Batch DB inserts — accumulate 100ms of write requests and INSERT in bulk. Reduces DB round trips from N to 1 per batch. Must handle partial batch failures.

**Q22. How do you design for global low-latency redirects across multiple geographic regions?**
A: Multi-region architecture:
- **GeoDNS routing:** DNS resolves `short.ly` to the nearest regional PoP (e.g., US-East, EU-West, APAC). Users hit the closest redirect service, minimizing network RTT.
- **Regional Redis clusters:** Each region has its own Redis cluster preloaded with hot mappings. On L2 miss, the regional instance reads from its regional DB read replica.
- **Global DB with regional replicas:** A global PostgreSQL primary (or CockroachDB/PlanetScale for globally distributed primary writes) with read replicas in each region. Redirect reads hit the local replica. Creation writes go to the global primary.
- **Consistency trade-off:** A link created in EU-West may not be immediately resolvable in APAC until replication propagates (~100ms–1s). For most use cases this is acceptable. For customer-facing link creation, return the short code immediately and tolerate a brief propagation window before the link is globally resolvable.

## Section 7: Scenario / System Design Style Questions

**Q23. "Walk me through the complete system design for a URL shortener at Bitly scale."**
A: High-level components and their responsibilities:

**Creation Service:**
- REST API: `POST /shorten { url, custom_alias?, expires_at? }`
- Validates URL, checks Safe Browsing, generates Snowflake ID → base62 short code.
- Writes to PostgreSQL (primary) and populates Redis.
- Returns `{ short_url: "https://short.ly/aB3xKp" }`.

**Redirect Service:**
- Handles `GET /{short_code}` at massive scale.
- L1 (local LRU) → L2 (Redis) → L3 (PostgreSQL read replica).
- Returns `302 Location: {long_url}`.
- Publishes `ClickEvent` to Kafka asynchronously.

**Analytics Pipeline:**
- Kafka consumers enrich events (geo-lookup, UA parsing).
- Write to ClickHouse in micro-batches.
- Redis counters for real-time click counts, flushed periodically to PostgreSQL.
- Analytics API serves pre-aggregated rollups + real-time Redis counts.

**Supporting Services:**
- ID Generator Service (Snowflake) — centralized or embedded per-instance.
- Link Health Service — periodically scans long URLs for malicious content.
- Admin Service — deactivate links, manage users, view system metrics.

**Infrastructure:**
- CDN (Cloudflare) in front of redirect service — caches 301 responses for non-tracked links.
- GeoDNS + regional PoPs for global low-latency.
- Kafka cluster for analytics event streaming.
- ClickHouse cluster for OLAP analytics queries.

**Q24. "Your URL shortener's Redis cache is evicting URL mappings under memory pressure. Redirects are hitting PostgreSQL at 50,000 RPS, which is approaching its limit. What do you do?"**
A: Immediate and medium-term actions:

**Immediate (minutes):**
- Increase Redis `maxmemory` — if the Redis instance has headroom on the host, raise the limit. Or add a Redis replica and read-distribute across replicas.
- Switch eviction policy from `allkeys-lru` to `volatile-lru` — only evict keys with TTLs (set TTLs on all URL mapping keys if not already set), protecting hot keys without TTL from eviction.
- Add a PostgreSQL read replica to distribute the 50k RPS across multiple DB nodes while the cache issue is resolved.

**Medium-term (hours/days):**
- Shard Redis by short_code prefix — distribute the key space across multiple Redis instances. Each handles a fraction of total keys and traffic.
- Analyze eviction patterns — identify which keys are being evicted (monitor `redis_evicted_keys` by key pattern). If long-tail cold keys are consuming memory, reduce their TTL to free space for hot keys.
- Add a regional CDN cache in front of the redirect service for the highest-traffic links — Cloudflare can cache 302 responses for specific short codes, removing load from Redis entirely.

**Q25. "A customer reports that their short link `short.ly/xKp9Ab` sometimes redirects to the wrong URL. What could cause this, and how do you investigate?"**
A: Short code collision or cache poisoning — investigate in layers:

**Step 1 — Verify the DB:** Query `SELECT * FROM url_mappings WHERE short_code = 'xKp9Ab'`. If multiple rows exist (shouldn't — there's a unique constraint), the constraint was violated during a data migration or bulk import.

**Step 2 — Check the cache:** `redis.get('url:xKp9Ab')`. Does the cached value match the DB? If not, the cache has a stale or incorrect value — possibly written during a race condition or by a bug in the creation service. Fix: `redis.delete('url:xKp9Ab')` and let it re-warm from DB.

**Step 3 — Audit click logs:** Query `click_events WHERE short_code = 'xKp9Ab'` for the timestamps the customer reported the wrong redirect. Does the `referrer` or `user_agent` suggest a different type of client? Is there a pattern (certain times, certain regions)?

**Step 4 — Check creation service logs:** Were there multiple creation requests for this short code? A custom alias conflict? A retry that created a duplicate during a transient DB failure window?

**Step 5 — Check for hash collision (if hash-based generation):** Compute `hash(reported_long_url)` — does it collide with the stored short code? If yes, the collision handling logic has a bug.

**Resolution:** Fix the root cause (cache or DB), add a unique constraint if missing, and implement a "verify redirect" endpoint that the customer can use to inspect what `short.ly/xKp9Ab` resolves to without following the redirect.

## Quick Reference: Component Decisions Summary

| Component | Choice | Rationale |
|---|---|---|
| Short code generation | Snowflake ID → base62 | Unique, no collision check, distributed, ordered |
| Redirect code | HTTP 302 | Enables click analytics (browser doesn't cache) |
| Core DB | PostgreSQL | ACID, indexed short_code lookup, familiar ops |
| Cache | Redis (L1 + L2) | 350k RPS, ~20GB working set fits in memory |
| Analytics ingestion | Kafka | Decouple redirect latency from analytics write |
| Analytics storage | ClickHouse | OLAP, columnar, fast aggregations over billions of rows |
| Real-time counters | Redis INCR + periodic flush | High write rate, avoid OLTP counter update bottleneck |
| Unique visitor count | HyperLogLog | Approximate, O(1) memory, < 1% error |
| Abuse prevention | Safe Browsing API + rate limiting | Creation-time scan + rate cap per IP/user |
| Global latency | GeoDNS + regional PoPs | Route users to nearest redirect service |

---

**Tip for the interview:** URL shortener questions test breadth more than depth — interviewers want to see that you cover all three pillars (generation, redirect, analytics) and make deliberate trade-off decisions rather than jumping to implementation. The most common gaps: not explaining why 302 over 301, not quantifying cache hit rate expectations, and treating analytics as an afterthought. Lead with estimation (read:write ratio, storage), use it to justify every component decision, and explicitly call out what you'd compromise first under cost or complexity constraints ("analytics can be approximate; redirects must be exact and fast").
