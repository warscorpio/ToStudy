# Design a Rate Limiter (Distributed, Multi-Tier) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a rate limiter and what does it protect?**
A: A rate limiter enforces an upper bound on how many requests a client (user, IP, API key, service) can make within a time window. It protects against: **abuse and DoS** (a single actor overwhelming the system), **resource exhaustion** (preventing one tenant from starving others in a multi-tenant system), **cost control** (capping usage of expensive operations like ML inference or third-party API calls), and **SLA enforcement** (guaranteeing fair share of capacity across clients). A rate limiter answers one question on every request: "Has this client exceeded their allowed rate? If so, reject now."

**Q2. What are the axes along which a rate limiter can be defined?**
A: Four key dimensions to clarify before designing:
- **Limit key**: what identifies the "client" being limited — IP address, user ID, API key, tenant ID, endpoint, or a combination. The key determines the granularity of enforcement.
- **Limit value**: how many requests are allowed — e.g., 100 requests per minute, 1000 per hour, 10 concurrent.
- **Window type**: fixed time window (resets every minute on the clock), sliding window (rolling 60-second window from each request), or token-based (continuous replenishment rate).
- **Action on breach**: hard reject (429 Too Many Requests), soft throttle (add delay, downgrade response), or queue (defer and process later when capacity opens).

**Q3. What is the difference between a rate limiter and a circuit breaker?**
A: A **rate limiter** is caller-side or gateway-side logic that limits how much traffic a specific client can send — it's about protecting the system from individual actors. A **circuit breaker** is service-side logic that stops a service from calling a failing dependency when error rates are high — it's about protecting the system from cascading failures caused by a downstream being unhealthy. Both reject requests, but for opposite reasons: rate limiting because the caller is too active, circuit breaking because the downstream is too fragile. In a full system, you typically have both.

**Q4. What are the two broad categories of rate limiters by enforcement point?**
A:
- **Ingress rate limiting** (at the gateway/load balancer/CDN): enforces limits before requests reach application servers. Protects the entire backend from excessive traffic. Operates on coarse-grained keys (IP, API key). Examples: Nginx `limit_req`, AWS API Gateway throttling, Cloudflare rate limiting rules.
- **Application-level rate limiting** (inside the service): enforces limits on specific operations, endpoints, or business actions (e.g., "maximum 3 password reset emails per hour per user"). Can use richer context (authenticated user ID, business tier, plan limits) that is unavailable at the gateway layer. More granular, higher implementation cost.

Multi-tier means having both — gateway for bulk/coarse protection, application-level for fine-grained business logic.

**Q5. What HTTP response does a rate limiter return, and what headers should it include?**
A: Return **HTTP 429 Too Many Requests**. Standard response headers for client transparency:
- `X-RateLimit-Limit`: the total allowed requests in the window.
- `X-RateLimit-Remaining`: how many requests are left in the current window.
- `X-RateLimit-Reset`: Unix timestamp (or seconds) until the window resets and the limit is restored.
- `Retry-After`: seconds (or HTTP date) after which the client may retry — required by RFC 6585 for 429 responses.

These headers allow well-behaved clients to implement adaptive backoff rather than blindly retrying, reducing repeated rejected requests.

## Section 2: Rate Limiting Algorithms

**Q6. What is the Fixed Window Counter algorithm?**
A: Divide time into fixed-size windows (e.g., every minute from :00 to :59). Maintain a counter per client per window. On each request, increment the counter; if it exceeds the limit, reject. On window rollover, reset the counter to zero.

Implementation: Redis `INCR` + `EXPIRE`. On first increment, set TTL to the window duration. Subsequent increments reuse the existing key until it expires.

Trade-off: **boundary burst** — a client can send up to 2× the limit by sending the max in the last second of one window and the max again in the first second of the next. Simple and cheap, but this double-burst vulnerability makes it unsuitable for strict rate limiting.

**Q7. What is the Sliding Window Log algorithm?**
A: Store a sorted set of timestamps for each client's requests. On each request: remove all timestamps older than the window (e.g., older than 60 seconds ago), count remaining entries, reject if count ≥ limit, otherwise add current timestamp.

Implementation: Redis sorted set — `ZREMRANGEBYSCORE` (remove old entries) + `ZCARD` (count) + `ZADD` (record new request), wrapped in a `MULTI`/`EXEC` or Lua script for atomicity.

Trade-off: **perfectly accurate** — no boundary burst, true sliding window behavior. But **memory-expensive**: stores one entry per request per client. At 1000 req/min per user × 1M users, the sorted set count is enormous. Only practical for low-volume, high-precision cases (e.g., 10 requests/hour).

**Q8. What is the Sliding Window Counter algorithm and why is it the practical default?**
A: A hybrid that approximates a sliding window using two fixed-window counters — the current window and the previous window — plus a linear interpolation of the overlap:

```
weight_of_previous = (window_size - elapsed_time_in_current_window) / window_size
estimated_count = previous_window_count * weight_of_previous + current_window_count
```

If `estimated_count` ≥ limit → reject.

Example: window = 60s, limit = 100. You are 15s into the current minute. Previous window had 80 requests. Current window has 30. Estimated = 80 × (45/60) + 30 = 60 + 30 = 90. Allow the request.

Trade-off: **memory efficient** (two integers per client per window), **good accuracy** (smooths the boundary burst to at most ~1.1× the limit in the worst case), and **cheap to compute** (two Redis GETs + arithmetic + one INCR). This is the algorithm used by Cloudflare, Stripe, and most production rate limiters. The slight inaccuracy at window boundaries is acceptable for most use cases.

**Q9. What is the Token Bucket algorithm?**
A: Imagine a bucket with capacity `C` tokens. Tokens are added at a fixed rate `r` tokens/second (up to capacity). Each request consumes 1 token (or N tokens for a weighted request). If the bucket has tokens → allow and consume. If empty → reject.

The bucket naturally handles **burst tolerance**: a client that hasn't used the API for a while accumulates tokens (up to `C`) and can burst up to `C` requests before being throttled. The steady-state rate is `r` requests/second.

Implementation: store `(token_count, last_refill_timestamp)` per client. On each request: compute tokens to add since last refill = `min(C, stored_tokens + r × elapsed_seconds)`, subtract 1 if tokens available, update stored state — all atomically via Lua script or a single-key Redis transaction.

Trade-off: **burst-tolerant and smooth** — models real-world usage patterns well. Slightly more complex to implement correctly than counter-based approaches. Hard to distribute accurately across nodes without a shared token store.

**Q10. What is the Leaky Bucket algorithm and how does it differ from Token Bucket?**
A: Leaky bucket processes requests at a fixed output rate regardless of how fast they arrive — excess requests queue or are dropped. Think of a bucket with a hole at the bottom: water (requests) pours in at variable rate, drips out at constant rate. If the bucket overflows (queue is full), requests are dropped.

The key difference from token bucket: token bucket allows bursts up to capacity; leaky bucket enforces a strict constant output rate — no burst tolerance. Leaky bucket is appropriate when you need a **smooth, metered output** (e.g., sending notifications at exactly 10/sec regardless of demand). Token bucket is appropriate when **occasional bursts** are acceptable up to a cap.

In practice, leaky bucket is less commonly used for API rate limiting (users expect some burst tolerance) and more common for traffic shaping at the network layer.

**Q11. Which algorithm should you choose for a public API rate limiter?**
A: **Sliding window counter** for most cases — it's memory-efficient, accurate enough (error ≤ limit/window_size at boundaries), easy to implement in Redis, and widely understood. **Token bucket** when burst tolerance is an explicit product requirement (e.g., "clients can burst up to 200 requests but average no more than 100/min"). **Fixed window** only as a starting point or for very coarse limits where the boundary burst is acceptable — never for strict enforcement. **Sliding window log** only for very low-volume, high-precision limits (e.g., fraud detection triggers, login attempts).

## Section 3: Distributed Rate Limiting

**Q12. Why is distributed rate limiting hard?**
A: In a single-process rate limiter, a shared in-memory counter is trivially consistent. Across multiple application servers handling the same user's requests, each server only sees its fraction of the traffic. Server A sees 60 requests and allows them; Server B sees 60 requests and allows them — the user sent 120, 20% over the limit. Every distributed rate limiter must solve the fundamental problem of **coordinating state across nodes** without making that coordination so expensive it becomes the bottleneck.

**Q13. What is "local counting with global sync" and what are its accuracy trade-offs?**
A: Each node maintains a local counter in memory. Periodically (e.g., every 100ms), nodes sync their local counts to a central store (Redis) and fetch the aggregate. Between syncs, each node makes local decisions based on a potentially stale view of the global count.

Trade-off: **accuracy vs. overhead**. With a 100ms sync interval and 10 nodes, a client can exceed the limit by up to `(limit / sync_interval) × node_count × sync_latency` in the worst case before the excess is globally visible. For a 100 req/min limit with 100ms sync and 10 nodes, the overshoot window is small but non-zero. This is acceptable for most rate limiting use cases where soft limits (approximate enforcement) are fine, and it keeps Redis call frequency bounded regardless of request rate.

**Q14. What is the centralized Redis approach and what does a correct atomic implementation look like?**
A: All nodes perform every rate limit check directly against a central Redis instance — no local counters. For the sliding window counter:

```lua
-- Lua script executed atomically on Redis
local key_current = KEYS[1]       -- e.g. "rl:user:123:1720000060"
local key_previous = KEYS[2]      -- e.g. "rl:user:123:1720000000"
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])  -- seconds
local now = tonumber(ARGV[3])
local elapsed = now % window

local prev_count = tonumber(redis.call('GET', key_previous) or 0)
local curr_count = tonumber(redis.call('GET', key_current) or 0)

local weight = (window - elapsed) / window
local estimated = prev_count * weight + curr_count

if estimated >= limit then
  return {0, estimated}  -- rejected
end

redis.call('INCR', key_current)
redis.call('EXPIRE', key_current, window * 2)
return {1, estimated + 1}  -- allowed
```

Wrapping in a Lua script is critical — it executes atomically on Redis, preventing race conditions between the read and the increment.

**Q15. What is the "Redis INCR + EXPIRE" pattern for fixed window rate limiting and what race condition does it have?**
A: Common pattern:
```
count = INCR rl:user:123:minute:1720000060
IF count == 1: EXPIRE rl:user:123:minute:1720000060 60
IF count > limit: reject
```

The race condition: two concurrent requests both execute `INCR` and get count = 1 and 2 respectively. The first request sets `EXPIRE`. If the Redis process crashes between the `INCR` and `EXPIRE` commands, the key has no TTL and lives forever — every future request for this user is rejected until manual cleanup.

Fix: replace `INCR` + conditional `EXPIRE` with a Lua script that does both atomically, or use `SET key 0 EX 60 NX` to initialize with TTL only if the key doesn't exist, then `INCR`. Better still: use `INCR` followed immediately by `EXPIRE` always (idempotent TTL reset is fine for a fixed window key).

**Q16. What is the GCRA (Generic Cell Rate Algorithm) and why is it considered the mathematically cleanest rate limiting algorithm?**
A: GCRA (also called "virtual scheduling") is a token-bucket-equivalent algorithm that avoids storing token counts by instead storing the **theoretical arrival time (TAT)** of the next cell (request). On each request:
- Compute `TAT = max(now, stored_TAT) + emission_interval` where `emission_interval = 1/rate`.
- If `TAT - now > burst_tolerance` → reject (client is too far ahead of schedule).
- Otherwise → allow and update stored TAT to the new value.

It reduces per-client state to a single timestamp, supports burst tolerance cleanly via the `burst_tolerance` parameter, and is trivially atomic (one read + one conditional write). It's the algorithm behind many network rate limiters and is used in production by Stripe. The downside: less intuitive to explain or tune than token bucket.

**Q17. How do you handle rate limiting across multiple Redis nodes (Redis Cluster)?**
A: Rate limit keys should be hashed to the same Redis slot to enable atomic Lua scripts. Use hash tags: `{user:123}:rl:current` and `{user:123}:rl:previous` both hash on `user:123`, landing on the same slot. This ensures the Lua script that reads both current and previous window counters executes on a single Redis node without cross-slot coordination. If you don't use hash tags, the two keys may land on different nodes, making atomic multi-key operations impossible.

## Section 4: Multi-Tier Architecture

**Q18. What does a multi-tier rate limiter look like end-to-end?**
A: Three enforcement tiers, each catching a different class of abuse:

**Tier 1 — CDN / Edge (coarsest, cheapest)**:
Configured rules at the CDN (Cloudflare, Fastly, AWS WAF). Limits by IP address or geographic region. Blocks volumetric attacks (DDoS, crawler floods) before traffic reaches your infrastructure. TTL: per-second or per-minute. No awareness of user identity or business logic.

**Tier 2 — API Gateway / Load Balancer**:
Limits by API key, client ID, or authenticated user identity at the ingress point. Enforces plan-level quotas (free tier: 100 req/min, paid tier: 1000 req/min). Uses a shared Redis cluster for coordination. Returns 429 with `Retry-After`. Sits in front of all services — one central enforcement point.

**Tier 3 — Application / Service Layer (finest, most context-aware)**:
Limits on specific high-cost operations: "max 3 SMS messages per user per hour," "max 10 concurrent ML inference jobs per tenant," "max 5 failed login attempts per user per 15 minutes." Uses application-level context (authenticated user, business plan, feature flags) unavailable at the gateway. Enforced inside the service code or as a shared library/sidecar.

**Q19. What is "defense in depth" in the context of multi-tier rate limiting?**
A: Each tier handles a different attack surface:
- **CDN**: absorbs volumetric attacks (millions of requests from botnets) with zero application cost — the CDN handles it entirely.
- **Gateway**: enforces identity-based quotas — a single API key can't monopolize all capacity even if the CDN lets it through.
- **Application**: enforces business-logic limits — a legitimate user can't trigger expensive operations at unlimited rate even if they're within their API quota.

No single tier can handle all cases. The CDN can't see authenticated user identity; the gateway doesn't know which operations are expensive; the application can't absorb volumetric DDoS. Defense in depth means a request must satisfy all tiers to be processed — bypassing one tier still gets caught by the next.

**Q20. How do you avoid double-counting or double-throttling in a multi-tier system?**
A: Each tier enforces a different limit along a different dimension — they're not redundant, they're additive:
- CDN enforces IP-level limits (e.g., 1000 req/min per IP).
- Gateway enforces API-key-level limits (e.g., 100 req/min per key, regardless of how many IPs the key is used from).
- Application enforces operation-level limits (e.g., 10 password resets per user per hour).

A single request passes through all three checks, but since the limits are on different keys and different operations, there's no double-counting. A request rejected at the CDN never reaches the gateway (no double-check). A request rejected at the gateway never reaches the application (no double-check). Each tier independently enforces its own dimension.

**Q21. How should rate limit state be partitioned — global vs. per-region?**
A: Depends on where your users are and what your limit means:
- **Global limits** (enforce across all regions): required when the limit has business meaning across geography — e.g., a paid API quota of 1000 req/min that should be 1000 globally, not 1000 per region. Requires cross-region Redis synchronization or a globally consistent data store (e.g., DynamoDB global tables, Cloudflare Durable Objects). Cross-region latency (50–200ms) makes synchronous global enforcement expensive.
- **Per-region limits**: each region enforces independently. Simpler and lower latency. A client can use up to `limit × region_count` globally — acceptable if the limit is for local fairness (per-region DoS protection) rather than global quota enforcement.
- **Hybrid**: coarse global limits enforced asynchronously (sync every N seconds), fine local limits enforced synchronously per-region. Global sync catches sustained overuse; local sync catches bursts.

**Q22. What is a "rate limit sidecar" pattern in a microservices architecture?**
A: Instead of each service implementing rate limiting independently (duplicated logic, inconsistent behavior), deploy a shared rate limiting sidecar (or a centralized rate limit service) that all services call before processing a request. The sidecar handles the Redis communication, algorithm, and key computation. Services make a single gRPC/HTTP call to the sidecar: `AllowRequest(key, limit, window)` → `{allowed: true/false, remaining: N}`. Envoy Proxy's `global rate limit` feature implements this pattern — it calls a configurable rate limit service (e.g., Lyft's `ratelimit` open-source service) on every request.

Trade-off: the sidecar becomes a critical dependency — its latency adds to every request, and its failure blocks all requests. It must be highly available and low-latency (sub-millisecond on p99).

## Section 5: Implementation Details

**Q23. How do you implement rate limiting at the CDN tier without writing custom code?**
A: Most CDN providers offer built-in rate limiting rule engines:
- **Cloudflare**: Rate Limiting rules in the firewall — configure matching criteria (URL pattern, HTTP method, IP), threshold (N requests per period), and action (block, challenge, log). State is maintained at each edge PoP; Cloudflare's Durable Objects can synchronize state across PoPs for global limits.
- **AWS CloudFront + WAF**: AWS WAF rate-based rules count requests matching a condition per 5-minute window per IP. Automatically blocks IPs exceeding the threshold.
- **Fastly**: Custom VCL (Varnish Configuration Language) with rate limiting primitives (`ratecounter`). More flexible but requires VCL knowledge.

These require no application code changes and operate at CDN scale with no origin cost for rejected requests.

**Q24. How do you implement rate limiting at the API gateway tier?**
A: For a self-managed gateway (Kong, Nginx, Envoy):
- **Kong**: `Rate Limiting` plugin — configure `limit_by` (IP, consumer, credential), algorithm (fixed window or sliding window), and backend (local, cluster via Redis, or Redis Sentinel). Configurable per-route and per-consumer.
- **Nginx**: `ngx_http_limit_req_module` — `limit_req_zone` defines a shared memory zone + rate; `limit_req` applies it per location. Leaky bucket algorithm with burst tolerance via `burst` parameter.
- **Envoy**: `global rate limit` filter calling an external rate limit service, or `local rate limit` filter for per-instance limits without a shared backend.

For managed gateways (AWS API Gateway, Azure APIM), rate limiting is configuration only — no infrastructure to manage.

**Q25. How do you implement a Redis-backed sliding window counter rate limiter in application code?**
A: The full implementation with proper atomicity, TTL handling, and response headers:

```python
import time, redis

r = redis.Redis()

def check_rate_limit(user_id: str, limit: int, window_seconds: int) -> dict:
    now = int(time.time())
    current_window = now - (now % window_seconds)
    previous_window = current_window - window_seconds

    key_curr = f"rl:{user_id}:{current_window}"
    key_prev = f"rl:{user_id}:{previous_window}"

    lua_script = """
    local prev = tonumber(redis.call('GET', KEYS[1]) or 0)
    local curr = tonumber(redis.call('GET', KEYS[2]) or 0)
    local elapsed = tonumber(ARGV[1]) % tonumber(ARGV[2])
    local weight = (tonumber(ARGV[2]) - elapsed) / tonumber(ARGV[2])
    local estimated = prev * weight + curr
    if estimated >= tonumber(ARGV[3]) then
      return {0, math.floor(estimated)}
    end
    redis.call('INCR', KEYS[2])
    redis.call('EXPIRE', KEYS[2], tonumber(ARGV[2]) * 2)
    return {1, math.floor(estimated + 1)}
    """

    allowed, count = r.eval(lua_script, 2,
        key_prev, key_curr,
        now % window_seconds, window_seconds, limit)

    reset_at = current_window + window_seconds
    return {
        "allowed": bool(allowed),
        "remaining": max(0, limit - count),
        "reset": reset_at,
        "retry_after": reset_at - now if not allowed else 0
    }
```

Key design decisions: Lua script for atomicity, two-key sliding window, TTL of `2 × window` on the current key (it must survive into the next window to serve as the "previous" key), and returning enough data to populate standard response headers.

**Q26. How do you implement an in-process L1 rate limiter efficiently?**
A: An in-process rate limiter is useful as the first tier — zero network overhead for clear over-limit cases. Use a thread-safe bounded data structure: a `ConcurrentHashMap<String, AtomicLong>` (Java) or equivalent, with a background sweep thread that resets counters at window rollover. For a more accurate implementation, use a sliding window with a `ConcurrentHashMap<String, Deque<Long>>` of timestamps — but bound the deque size and access it behind a lock.

Critically: the in-process limiter should be a **pre-filter for obvious abusers**, not the authoritative limit. It rejects requests from a client that has clearly exceeded the limit (already hit 200 req/s) before touching Redis. Borderline cases — where the true count requires the distributed view — fall through to Redis. This prevents Redis from being hammered by bots while still maintaining accurate limits for normal clients.

**Q27. How do you make rate limit configuration dynamic (without code deploys)?**
A: Store rate limit configuration in a system that can be updated at runtime:
- **Feature flags** (LaunchDarkly, Flipt): store limit values as flag variants, evaluated per client at request time. Allows instant limit changes per user segment, plan tier, or A/B group without restarts.
- **Centralized config store** (etcd, Consul, AWS AppConfig): rate limit service polls for config changes, applies new limits immediately. Config changes propagate in seconds.
- **Database-backed with local cache**: store limits per API key/plan in the DB; cache in Redis (short TTL) so changes propagate in seconds without DB load on every request.
- **Control plane API**: a rate limit service exposes an admin API to update limits for specific keys instantly (useful for emergency throttling of a misbehaving client).

Dynamic configuration is essential for incident response — the ability to reduce a limit from 1000 to 10 for a specific API key without a deploy can stop an incident in seconds.

## Section 6: Failure Modes & Anti-patterns

**Q28. What should your rate limiter do when Redis is unavailable?**
A: This is a critical design decision with two opposing philosophies:
- **Fail open (allow all requests)**: when Redis is down, bypass rate limiting and allow traffic through. Rationale: availability over security — it's better to temporarily allow too much traffic than to lock out all users. Risk: an outage window becomes a free DDoS opportunity.
- **Fail closed (deny all requests)**: when Redis is down, reject all traffic. Rationale: safety over availability — the system can't safely enforce limits, so it should not serve. Risk: a Redis blip causes a service-wide outage.
- **Fail to L1**: when Redis is down, fall back to in-process rate limiting. Each node enforces limits independently (allowing up to `limit × node_count` globally), but at least some protection exists. Usually the right balance.

Document the failure mode explicitly — teams discover it during an incident, and a surprise fail-closed behavior is often worse than a deliberate fail-open.

**Q29. What is "limit key injection" and how do you prevent it?**
A: An attacker manipulates the rate limit key by forging headers like `X-Forwarded-For` or `X-Real-IP` to impersonate a different IP address, either to avoid their own limit or to push the limit counter for a victim IP to trigger a false block (a DoS via rate limit exhaustion). Prevention:
- Never trust `X-Forwarded-For` from untrusted sources directly as the rate limit key. Use the rightmost non-private IP in the chain (set by your trusted gateway, not the client) or the TCP connection IP.
- For user-level limits, key on authenticated user ID from a validated JWT/session, not a client-supplied header.
- Validate and sanitize any client-supplied value that participates in the key.

**Q30. What is "rate limit bypass via endpoint enumeration"?**
A: A client that is rate limited on `/api/v1/search` simply calls `/api/v1/search?` or `/api/v1/search#` or other URL variations — if the rate limit key is the raw URL and not normalized, each variation is treated as a different key with a fresh limit. Prevention: normalize the URL (lowercase, strip query params irrelevant to rate limiting, canonicalize path) before computing the limit key. Apply rate limits on semantic identity (user ID, operation type), not raw URL strings.

**Q31. What is "the thundering herd on limit reset" and how does it manifest?**
A: When a fixed window resets (e.g., on the minute boundary), all clients that were blocked simultaneously become unblocked and fire their backlogged requests. The system receives a traffic spike precisely at the window rollover. At scale (millions of clients all throttled, all retrying at :00), this is a serious problem. Mitigations: sliding window algorithms spread reset times naturally; stagger client retry times via `Retry-After` headers that vary slightly between clients (add jitter); use token bucket so limits are not binary (blocked/unblocked) but continuous (each second replenishes some tokens, smoothing the retry distribution).

**Q32. What is "rate limit amplification" via webhooks or callbacks?**
A: A client sends 10 API calls, each of which triggers your system to make 100 callback/webhook calls to the client's endpoint. The client effectively receives 1000 messages from 10 API calls — a 100× amplification. From the client's rate limit perspective they were under the limit; from your outbound call perspective, you're hammering them. Apply separate rate limits to outbound callbacks and webhook deliveries, independent of the inbound API rate limits. This also protects your own systems from a client's endpoint being slow (which causes a buildup of pending outbound calls).

**Q33. What is a "rate limit oracle" attack?**
A: When rate limit responses reveal information about the system. Returning a 429 at exactly the limit count tells an attacker they've confirmed a valid user ID or API key exists (invalid keys might not be rate limited, or might hit a different limit). For login attempt limiting especially, return the same 429 response regardless of whether the user ID exists — don't distinguish "too many attempts for user X" from "user X doesn't exist." The error response itself should leak no information beyond "rate limited."

## Section 7: Trade-offs & Decision-Making

**Q34. How do you set rate limits — what's the process?**
A: Not by intuition. Data-driven process:
1. **Measure normal traffic**: collect p50, p95, p99 request rates per client over several weeks. Set the limit at 2–5× the p99 of legitimate usage — high enough to never throttle normal clients, low enough to catch abuse.
2. **Model the cost of a single request**: what does one API call cost in CPU, DB queries, downstream API calls? Expensive operations deserve tighter limits.
3. **Segment by client tier**: free tier gets a fraction of paid tier limits. Enterprise clients may get custom limits per contract.
4. **Monitor and adjust**: instrument how often limits are hit, by whom, and at what rate. Initial limits are guesses; tune based on real-world hit rate data. A limit that is never hit protects nothing; one that frequently hits legitimate users is a product defect.

**Q35. When is per-IP limiting insufficient and what should you use instead?**
A: Per-IP limiting fails when:
- **Shared IPs**: many legitimate users behind a corporate NAT or university proxy share one IP. One bad actor gets all users throttled.
- **Distributed botnets**: thousands of IPs each send one request — per-IP limits are useless against distributed attacks.
- **Mobile users with rotating IPs**: a single user's IP changes as they move between networks; per-IP limits don't correctly attribute usage.

Better alternatives: **authenticated user ID** (most accurate, requires login), **API key** (for API consumers), **device fingerprint** (for pre-auth flows), **behavioral analysis** (flag accounts with unusual patterns regardless of IP). Per-IP limiting is a coarse first layer — cheap to enforce at the CDN — but should never be the only layer for anything that matters.

**Q36. What is "rate limit by resource cost" (weighted rate limiting) and when is it needed?**
A: Standard rate limiting counts requests equally — each request costs 1 unit. Weighted rate limiting assigns a cost to each request based on its resource consumption: a search query costs 1 token; a bulk export costs 100 tokens; an ML inference costs 10 tokens. A client's limit is expressed in tokens/minute rather than requests/minute. This prevents a client from consuming disproportionate resources by using expensive operations within their "request" quota.

Implementation: token bucket is a natural fit — set the bucket capacity and refill rate in "cost units," and each operation deducts its cost. The cost can be determined statically (per-endpoint config) or dynamically (based on result size, computation time, or downstream API calls triggered).

**Q37. How do you handle rate limiting for long-running streaming or WebSocket connections?**
A: Stateless per-request rate limiting doesn't apply cleanly to long-lived connections. Strategies:
- **Connection establishment limiting**: rate limit the handshake/upgrade request. A client can only open N WebSocket connections per minute. Once established, the connection itself is not rate limited.
- **Message rate limiting**: for WebSockets, rate limit individual messages on the connection. Maintain a per-connection counter; if message rate exceeds limit, close the connection or stop reading (apply backpressure).
- **Byte/bandwidth limiting**: for streaming responses, limit the total bytes served per client per time window rather than request count. More meaningful for bandwidth-heavy operations.
- **Concurrent connection limiting**: use Redis `INCR`/`DECR` to track open connections per client; reject new connections if over the limit. Decrement on close (requires a reliable close event, which complicates implementation on ungraceful disconnects — use TTL as a fallback).

## Section 8: Scenario / System Design Style Questions

**Q38. "Design a rate limiter for a public API with three tiers: free (100 req/min), pro (1000 req/min), enterprise (custom). Walk through the full architecture."**
A:
- **Storage**: Redis Cluster with hash-tagged keys `{api_key}:rl:current` and `{api_key}:rl:previous`. One cluster per region; global quota synchronization via async counter sync every 5 seconds.
- **Algorithm**: sliding window counter — balances accuracy and memory efficiency. Atomic Lua script.
- **Limit lookup**: at request time, look up the client's plan from a local in-process cache (Caffeine, TTL=60s) populated from the DB. Avoids a DB query on every request.
- **Enforcement point**: API gateway (Kong or Envoy sidecar) applies the check before routing to any backend service. One enforcement point for all services.
- **Response**: 429 with `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After` headers.
- **Enterprise**: store per-key custom limits in the DB; cache in Redis (key `limit:{api_key}`, TTL=5min). On limit change, invalidate the cache. The rate limiter reads the custom limit from Redis on each check.
- **Monitoring**: track `rate_limit_hits` counter by plan tier and API key. Alert when a pro key is hitting limits consistently (signal to upgrade or investigate abuse).

**Q39. "A single API key is generating 50,000 requests per second — way above their 1000 req/min limit. Your rate limiter is keeping up, but it's causing Redis to spike. How do you fix it?"**
A: The problem is that every request — even obviously over-limit ones — is hitting Redis. Fix: add an **in-process circuit breaker per API key**. Once a key has been rate limited N consecutive times (e.g., 5 times in a row), mark it as "known bad" in a local hashmap with a short TTL (e.g., 1 second). For the duration of that TTL, reject all requests for that key locally without touching Redis. At 50K req/sec, this drops Redis calls from 50K/sec to ~1/sec for that key during the burst.

Separately: alert and trigger automatic IP blocking or API key suspension via a background process when a key sustains this rate for more than 30 seconds — this is not normal usage.

**Q40. "You need to implement 'max 5 failed login attempts per user per 15 minutes.' How does this differ from API rate limiting and what are the implementation gotchas?"**
A: Key differences from standard API rate limiting:
- **Event-conditioned**: only failed attempts count, not all login requests. The rate limiter must inspect the result of the authentication check, not just the request. This means the rate limit check happens *after* the auth logic (or the failed-attempt counter is incremented after failure), not before.
- **Key is the username/email**: the rate limit must apply even if the attacker uses different IPs. Key on the target user identity, not the source IP. Also rate limit per IP as a secondary measure.
- **Asymmetric unlock**: standard API limits reset on a timer. Login attempt limits should also reset on a *successful* login — once the user proves they know the password, the failed-attempt counter should clear. Requires explicit counter deletion on success.
- **Account enumeration**: returning "too many attempts for user X" confirms user X exists. Return a generic error ("too many attempts from this device") regardless of whether the user exists.
- **Lockout notification**: consider notifying the real user (email/SMS) when their account is rate limited — they may not know an attack is happening.
- **Admin override**: provide a support tool to manually clear the lockout for legitimate users locked out of their own accounts.

**Q41. "How would you design a rate limiter that handles 1 million unique clients with sub-millisecond enforcement latency per request?"**
A: At this scale, the centralized Redis approach is the bottleneck. Architecture:

**L1 (In-process, per-node)**: Each app server maintains a local token bucket or sliding window counter per client. Handles the first line of defense for extreme over-limit cases. Uses ~100MB RAM for 1M entries (each entry: ~100 bytes for key + counter + timestamp). No network overhead — enforcement in microseconds. Accepts inaccuracy (allows up to `limit × node_count` globally in edge cases).

**L2 (Redis, async sync)**: Each node periodically (every 100–500ms) batches its local increments and syncs to Redis via `INCRBY`. Reads the global aggregate back and updates its local view. The enforcement decision uses the local count adjusted by the last-known global offset. This bounds the sync overhead to `node_count × 1 Redis call per sync_interval` regardless of request rate.

**L3 (Background enforcement)**: A separate process watches for global overages (clients whose sum across all nodes exceeds the limit) and pushes a "hard block" flag to all nodes via Redis pub/sub. Nodes check for hard block flags on every request — a fast local hashmap lookup. Hard blocks are applied within one pub/sub latency (typically <5ms) of detection.

This architecture handles 1M clients at microsecond-level enforcement without Redis being on the hot path for every request.

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                        |
|---                            |---                                                                                                         |
| Rate limiter                  | Enforces an upper bound on requests a client can make in a time window                                     |
| Fixed window                  | Counter resets at wall-clock boundary; simple but double-burst vulnerable at window edges                  |
| Sliding window log            | Stores individual request timestamps; exact but memory-expensive at high volume                            |
| Sliding window counter        | Two fixed-window counters with linear interpolation; efficient and accurate enough for production           |
| Token bucket                  | Tokens replenish at rate R; burst up to capacity C; natural burst tolerance model                          |
| Leaky bucket                  | Requests queue and drain at constant rate; enforces smooth output, no burst                                |
| GCRA                          | Tracks theoretical arrival time; mathematically equivalent to token bucket; O(1) state per client          |
| Limit key                     | The identity dimension being rate limited (IP, user ID, API key, operation type)                           |
| Fail open                     | When rate limit backend (Redis) is unavailable, allow all traffic through                                  |
| Fail closed                   | When backend is unavailable, deny all traffic — safer but risks full outage                                |
| Local + global sync           | Each node counts locally; periodically syncs to shared store; trades accuracy for reduced Redis load       |
| Single-flight on miss         | Only one inflight request fetches from DB on cache miss; others wait — prevents stampede                   |
| Rate limit sidecar            | Shared rate limiting service called by all microservices; centralizes logic, adds a network hop            |
| Weighted rate limiting        | Each request has a cost in tokens; expensive operations deduct more — enforces resource fairness           |
| Origin shield                 | CDN PoP that aggregates misses before hitting origin; applies equally to rate limit bypass traffic          |
| Hard block flag               | A per-key global override pushed via pub/sub to all nodes; bypasses all local approximation                |
| `Retry-After`                 | HTTP header on 429 response; tells client when to retry — enables adaptive backoff, reduces stampede       |
| Surrogate keys / cache tags   | Tag CDN cached responses; purge all matching by tag — same concept applies to rate limit key namespacing   |

**Tip for the interview:** Most candidates describe one algorithm and one Redis key pattern and stop there. What separates a senior answer: (1) naming the exact failure mode of fixed windows (boundary burst) and why you'd use sliding window counter instead; (2) the atomicity argument — why `INCR` + `EXPIRE` without Lua is racy; (3) the multi-tier framing — CDN for volumetric, gateway for identity-level, application for business logic; (4) the Redis failure mode — what your system does when Redis is unreachable; and (5) a concrete example of a limit you'd *not* put in the gateway (login attempt limiting keyed on username, which requires auth context). Bonus: knowing that a 429 without `Retry-After` is spec non-compliant and causes retry storms.
