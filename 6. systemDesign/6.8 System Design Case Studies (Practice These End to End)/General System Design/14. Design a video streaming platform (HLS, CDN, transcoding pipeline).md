# Design a Video Streaming Platform — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a video streaming platform?**
A: Core functional requirements:
- **Video upload** — creators upload raw video files (MP4, MOV, AVI, MKV) of arbitrary size and resolution; upload must be resumable and fault-tolerant.
- **Transcoding pipeline** — convert uploaded raw video into multiple quality variants (240p, 360p, 480p, 720p, 1080p, 4K) and package into an adaptive streaming format (HLS or DASH).
- **Adaptive bitrate streaming (ABR)** — clients dynamically switch between quality levels based on available bandwidth; no manual quality selection required.
- **Video playback** — low time-to-first-frame (< 3 seconds); smooth playback without buffering under normal network conditions.
- **Content delivery** — serve video segments from edge locations close to the viewer to minimize latency and bandwidth cost.
- **Video metadata** — title, description, tags, thumbnail, duration, view count, creator info.
- **Search & discovery** — search by title/tag; recommendations; trending videos.
- **Access control** — public, unlisted, private, and subscriber-only videos; DRM for premium content.
- **Analytics** — view counts, watch time, completion rate, buffering events per video.

**Q2. What are the non-functional requirements?**
A:
- **Scalability** — at YouTube scale, 500 hours of video are uploaded per minute; at a mid-tier platform, hundreds of uploads per hour. Transcoding is CPU-intensive and must scale independently of serving.
- **Low playback latency** — time-to-first-frame < 3 seconds globally; rebuffering ratio < 0.5%.
- **High availability** — video serving must be 99.99% available; transcoding pipeline can tolerate higher failure rates with retry.
- **Storage efficiency** — a 1-hour 1080p video at 8 Mbps produces ~3.6GB; with 5 quality variants, ~12GB per video. Storage cost is the dominant operational cost at scale.
- **Durability** — uploaded source files and transcoded segments must survive any single storage failure; minimum 3-copy replication.
- **Eventual consistency** — a newly uploaded video does not need to be globally available within milliseconds; 1–5 minutes of processing latency is acceptable.
- **Cost** — CDN egress is expensive (typically $0.01–$0.08/GB); optimizing encoding efficiency (better codecs, lower bitrates at same quality) directly reduces cost.

**Q3. What is the difference between HLS and DASH, and which do you choose?**
A:
- **HLS (HTTP Live Streaming)** — developed by Apple. Segments video into `.ts` (MPEG-TS) or `.fmp4` chunks; uses an `.m3u8` playlist manifest. Native support in all Apple devices (Safari, iOS) and most modern players. The de facto standard for broad device compatibility.
- **DASH (Dynamic Adaptive Streaming over HTTP)** — MPEG standard; uses `.mpd` XML manifest and `.m4s` segments. No native Safari/iOS support (requires JavaScript player like Shaka Player). More flexible codec support (VP9, AV1 alongside H.264/H.265); used by YouTube, Netflix.
- **Choice**: HLS for broad compatibility and simpler implementation; DASH for advanced codec support and adaptive streaming features. Most production platforms serve both, or serve HLS with fMP4 segments (compatible with both protocols) to maximize compatibility.

For a general interview: choose HLS, acknowledge DASH exists for advanced use cases, and note that fMP4 segments allow a single transcode to serve both formats.

## Section 2: Upload Pipeline

**Q4. How do you handle large video file uploads reliably?**
A: Raw video files are large (1–50GB). A single HTTP POST times out on mobile networks and loses all progress on failure. The solution is multipart / chunked upload directly to object storage:

```
Client                          Upload API              S3 / GCS
  │                                 │                      │
  │── POST /uploads/initiate ──────►│                      │
  │                                 │── CreateMultipartUpload ──►│
  │                                 │◄── uploadId ─────────────│
  │◄── {uploadId, videoId} ─────────│                      │
  │                                 │                      │
  │  [For each 5MB chunk:]          │                      │
  │── PUT /uploads/{uploadId}/parts │                      │
  │    ?partNumber=N ──────────────►│                      │
  │                                 │── UploadPart (pre-signed) ──►│
  │◄── {eTag: "abc..."} ────────────│◄── ETag ─────────────────│
  │                                 │                      │
  │  [After all parts:]             │                      │
  │── POST /uploads/{uploadId}/complete ──────────────────►│
  │                                 │── CompleteMultipartUpload ──►│
  │◄── {videoId, status:"PROCESSING"}│                    │
```

Key design points:
- **5–10MB chunk size** — small enough to retry on failure without losing too much progress; large enough to avoid excessive HTTP overhead.
- **Client-side resumability** — the client stores which parts have been successfully uploaded (by part number + eTag) in local storage. On resume, skip already-uploaded parts.
- **Pre-signed URLs** — the upload API issues pre-signed S3 PUT URLs per chunk; raw video bytes never flow through your application servers, reducing bandwidth cost and single-point-of-failure risk.
- **Server-side deduplication** — hash the file client-side (SHA-256) before upload; check if a video with that hash already exists. Skip re-upload and re-transcode for duplicate content.

**Q5. What happens immediately after the raw upload completes?**
A: Upload completion triggers the transcoding pipeline asynchronously:

```
S3 upload complete
        │
        │  S3 Event Notification / EventBridge
        ▼
┌─────────────────────────┐
│   Upload Complete Handler│
│   (Lambda / worker)      │
│                          │
│  1. Validate file:        │
│     - MIME type (magic bytes, not extension)
│     - Duration < max limit
│     - File not corrupt (probe with ffprobe)
│  2. Extract metadata:     │
│     - Duration, resolution, codec, bitrate
│     - Store in videos table
│  3. Generate thumbnail:   │
│     - Extract frame at 10% of duration
│     - Upload to S3/CDN    │
│  4. Enqueue transcoding jobs (one per output variant)
│  5. Update video status → PROCESSING
└─────────────────────────┘
        │
        ▼
   Job Queue (SQS / Kafka)
   [transcode:720p, transcode:1080p, transcode:480p, ...]
```

`ffprobe` validation before enqueuing prevents malformed files from entering the transcoding pipeline and wasting expensive compute.

## Section 3: Transcoding Pipeline

**Q6. What does the transcoding pipeline architecture look like?**
A:

```
Job Queue (SQS)
   [transcode jobs per variant]
        │
        ▼
┌─────────────────────────────────────────────┐
│         Transcoding Worker Pool              │
│         (EC2 GPU / CPU fleet,                │
│          auto-scaled by queue depth)         │
│                                              │
│  Worker picks up job:                        │
│  1. Download source file from S3             │
│     (stream to local NVMe, not full download)│
│  2. Run FFmpeg transcode:                    │
│     ffmpeg -i input.mp4                      │
│       -c:v libx264 -crf 23 -preset fast      │
│       -c:a aac -b:a 128k                     │
│       -vf scale=-2:720                       │
│       -f hls -hls_time 6                     │
│       -hls_segment_filename 'seg_%03d.ts'    │
│       -hls_playlist_type vod                 │
│       output_720p.m3u8                       │
│  3. Upload segments + manifest to S3         │
│  4. Report completion to orchestrator        │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│      Transcoding Orchestrator               │
│      (tracks job status per variant)        │
│                                             │
│  When all variants complete:                │
│  1. Generate master playlist (HLS master    │

```

**Q7. What are the target bitrates and resolutions for each quality tier?**
A: Standard H.264 ladder (the "encoding ladder" — a set of bitrate/resolution combinations that balance quality vs. bandwidth):

| Quality | Resolution | Video Bitrate | Audio Bitrate | Segment Size (6s) |
|--- |--- |--- |--- |--- |
| 240p | 426×240 | 400 kbps | 64 kbps | ~350 KB |
| 360p | 640×360 | 800 kbps | 96 kbps | ~660 KB |
| 480p | 854×480 | 1,400 kbps | 128 kbps | ~1.1 MB |
| 720p | 1280×720 | 2,800 kbps | 128 kbps | ~2.2 MB |
| 1080p | 1920×1080 | 5,000 kbps | 192 kbps | ~3.9 MB |
| 4K | 3840×2160 | 16,000 kbps | 192 kbps | ~12.2 MB |

Modern platforms replace H.264 with H.265 (HEVC) or AV1 for 30–50% better compression at the same visual quality — same resolution at half the bitrate. AV1 encoding is 10–50x slower than H.264, making it more expensive; used for popular videos where the encoding cost amortizes over millions of views.

**Q8. What is HLS packaging and what files does it produce?**
A: HLS packaging converts the transcoded video into a set of files that a player can request over HTTP:

**Per quality variant** (`/videos/{videoId}/720p/`):
- `playlist.m3u8` — variant-level manifest listing every segment file and its duration.
- `seg_000.ts`, `seg_001.ts`, ... — video segments, typically 6–10 seconds each.

**Master manifest** (`/videos/{videoId}/master.m3u8`):
```m3u8
#EXTM3U
#EXT-X-VERSION:3

#EXT-X-STREAM-INF:BANDWIDTH=400000,RESOLUTION=426x240
240p/playlist.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p/playlist.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=2800000,RESOLUTION=1280x720
720p/playlist.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p/playlist.m3u8
```

The player fetches the master manifest first, selects the initial quality based on available bandwidth, fetches the corresponding variant playlist, then fetches segments sequentially. When bandwidth changes, the player switches to a different variant playlist for subsequent segments.

**Q9. How do you optimize transcoding throughput for cost and speed?**
A: Several techniques compound:

- **Parallel per-variant jobs** — all quality variants transcode simultaneously (not serially). A 5-variant transcode on 5 workers takes as long as the slowest variant (1080p ≈ the source duration at 1x speed on a mid-tier CPU). Serial would be 5x slower.
- **Segment-level parallelism** — split the source video into chunks (e.g., 2-minute chunks), transcode each chunk independently in parallel across multiple workers, then concatenate the segments. For a 2-hour video, this reduces wall-clock time from 120 minutes to ~2 minutes on 60 workers.
- **Hardware acceleration** — use GPU encoding (`h264_nvenc` for NVIDIA, `h264_videotoolbox` for Apple) instead of CPU (`libx264`). GPU encoding is 5–20x faster, though quality/bitrate efficiency is slightly lower than CPU at equivalent settings.
- **Two-pass encoding vs. CRF** — CRF (Constant Rate Factor) encoding in one pass is fast; two-pass encoding optimizes bitrate distribution but takes 2x the time. Use CRF for low-to-mid quality tiers; two-pass for 1080p/4K where quality matters most.
- **Per-title encoding** — instead of a fixed bitrate ladder, analyze each video's complexity and generate a custom ladder. A simple talking-head video compresses much better than an action scene; applying the action-scene bitrate to the talking-head video wastes bandwidth. Netflix pioneered this; saves 20–40% bandwidth.

**Q10. How do you handle transcoding failures and retries?**
A: Transcoding is long-running and fail-prone (OOM, FFmpeg crash, source file corruption). Resilience design:

```
Job picked from SQS queue
        │
        ▼ (SQS visibility timeout: 2 hours for long jobs)
Worker transcodes
        │
   ┌────┴────┐
   │         │
Success   Failure
   │         │
   ▼         ▼
Mark      Increment retry count
DONE      If retry < 3: return to queue (SQS nack)
          If retry == 3: move to Dead Letter Queue (DLQ)
                         Alert on-call; manual inspection
```

Critical details:
- **SQS visibility timeout** must exceed the maximum expected transcode duration to prevent the job from being re-picked by another worker while still running. Set to 2–3x the expected duration.
- **Idempotent workers** — each worker writes segments to a path keyed by `{videoId}/{variant}/{attempt_id}/`. On retry, a new attempt ID creates fresh output without colliding with a partial previous attempt's files.
- **Checkpointing for segment-level parallelism** — in the chunk-and-concatenate pattern, record which chunks have been transcoded. On retry, skip completed chunks. A 2-hour video that fails at chunk 50 of 60 doesn't re-transcode the first 50 chunks.

## Section 4: HLS and Adaptive Bitrate Streaming

**Q11. How does a video player implement adaptive bitrate (ABR) switching?**
A: The player maintains a buffer of pre-fetched segments (typically 30 seconds ahead). An ABR algorithm continuously estimates available bandwidth and selects the appropriate quality for the next segment fetch:

```
ABR Algorithm (simplified BOLA / throughput-based):

Every segment fetch:
  1. Measure download throughput: bytes / time = estimated_bandwidth
  2. Apply smoothing: smoothed_bw = 0.8 × prev_bw + 0.2 × estimated_bandwidth
  3. Select highest quality tier whose bitrate ≤ smoothed_bw × 0.8
     (0.8 safety margin to avoid selecting exactly at the limit)
  4. Check buffer level:
     - buffer < 10s: drop to lower quality (buffer protection)
     - buffer > 30s: allow quality upgrade
  5. Hysteresis: don't switch quality more than once per 3 segments
     (prevents thrashing between two tiers on a fluctuating connection)
```

ABR algorithms in production (HLS.js, Shaka Player, Video.js) are more sophisticated — they factor in throughput history, segment fetch latency, buffer level, and sometimes network type (WiFi vs cellular) to minimize rebuffering while maximizing quality.

**Q12. What is the optimal HLS segment duration and why?**
A: Segment duration is a critical trade-off:

| Segment duration | Pros | Cons |
|--- |--- |--- |
| **2 seconds** | Fast ABR switching (reacts to bandwidth changes quickly); lower seek latency | More HTTP requests; higher manifest overhead; more S3 objects |
| **6 seconds** | Industry standard; balances switching speed with request overhead | Default choice for VOD |
| **10 seconds** | Fewer HTTP requests; better CDN caching efficiency | Slow ABR reaction; 10 seconds of wrong-quality video before a switch |

**6-second segments** are the VOD standard. For live streaming, 2-second segments are common to minimize end-to-end latency. The segment duration is set in the FFmpeg `-hls_time` parameter; actual segments may be slightly longer if they don't align with keyframe boundaries (the encoder always cuts at a keyframe to ensure clean switching).

**Q13. What is a keyframe and why does it matter for HLS?**
A: A keyframe (I-frame) is a complete video frame that can be decoded independently without reference to other frames. Inter-frames (P-frames, B-frames) encode only the difference from a reference frame and cannot be decoded alone. HLS segment boundaries must align with keyframes — a player switching quality mid-stream needs to start decoding from a complete frame:

```
FFmpeg keyframe interval (GOP size):
  -g 48          # keyframe every 48 frames
  -keyint_min 48 # minimum interval between keyframes
  -sc_threshold 0 # disable scene-change keyframes (irregular GOP)

For 24fps video: 48 frames / 24 fps = keyframe every 2 seconds
For 6-second segments: 3 keyframes per segment (consistent)
```

Forcing keyframes at regular intervals (`-sc_threshold 0`) increases file size slightly (keyframes are larger than inter-frames) but ensures predictable segment boundaries for HLS packaging. Without this, scene-change detection inserts extra keyframes at unpredictable points, causing variable segment durations.

## Section 5: CDN and Content Delivery

**Q14. How does a CDN fit into video delivery, and what is the request flow?**
A:

```
Viewer (London)                CDN Edge (London)          Origin (S3, us-east-1)
     │                               │                            │
     │── GET master.m3u8 ───────────►│                            │
     │                               │── Cache MISS ─────────────►│
     │                               │◄── master.m3u8 ────────────│
     │◄── master.m3u8 ───────────────│  [Cache: 5 min TTL]        │
     │                               │                            │
     │── GET 720p/playlist.m3u8 ────►│                            │
     │                               │── Cache MISS ─────────────►│
     │◄── 720p/playlist.m3u8 ────────│  [Cache: 5 min TTL]        │
     │                               │                            │
     │── GET 720p/seg_000.ts ────────►│                            │
     │                               │── Cache MISS ─────────────►│
     │◄── seg_000.ts (3.9 MB) ───────│  [Cache: 1 year TTL]       │
     │                               │                            │
     │── GET 720p/seg_001.ts ────────►│  Cache HIT                 │
     │◄── seg_001.ts (3.9 MB) ───────│  (from London edge)        │
```

Once the first viewer in a region fetches a segment, subsequent viewers get it from the CDN edge — the origin (S3) is only hit once per segment per PoP (Point of Presence). CDN cache hit rates for popular videos are 95–99%; for long-tail content, closer to 40–60%.

**Q15. What are the CDN caching strategies for different HLS file types?**
A: Different files have different update frequencies and require different TTLs:

| File type | Cache-Control | Reasoning |
|--- |--- |--- |
| `master.m3u8` | `max-age=300` (5 min) | Rarely changes after video is published; short TTL for quality ladder updates |
| `{quality}/playlist.m3u8` (VOD) | `max-age=300` | Segment list is fixed after transcode; can be longer |
| `{quality}/playlist.m3u8` (Live) | `max-age=2`, `no-cache` | Updated every segment duration; must be fresh |
| `seg_XXX.ts` (VOD) | `max-age=31536000` (1 year) | Immutable; content-addressed by filename — never changes |
| `seg_XXX.ts` (Live) | `max-age=10` | Short-lived; new segments constantly added |
| Thumbnail | `max-age=86400` (1 day) | Changes infrequently; allow CDN caching |

Segments get 1-year TTLs because they are immutable — if a re-transcode is needed, new segment filenames are generated (content-addressed: `seg_{videoId}_{variant}_{hash}.ts`). Old segments are never modified.

**Q16. How do you handle CDN cache invalidation when a video is re-transcoded?**
A: Segment files are immutable by design — a re-transcode generates new segment files at new paths. The only files that need invalidation are the manifests (`.m3u8` files) that reference the new segment paths:

```
Re-transcode event:
  1. New segments uploaded to new paths:
     /videos/{videoId}/{variant}/{new_version}/seg_000.ts

  2. New variant playlists reference new segment paths

  3. New master.m3u8 references new variant playlist URLs

  4. Invalidate CDN cache for:
     /videos/{videoId}/master.m3u8
     /videos/{videoId}/*/playlist.m3u8
     (CDN API: CloudFront CreateInvalidation, Fastly Purge)

  Old segments at old paths remain in CDN cache (benign — no manifest references them)
  Old segments in S3 are lifecycle-deleted after 7 days
```

CDN invalidation propagates globally in 30–60 seconds (varies by CDN). During this window, some viewers may receive the old manifest — acceptable since they'll pick up the new one at the next manifest refresh (within the TTL).

**Q17. How do you protect premium content from unauthorized access?**
A: Two primary mechanisms:

**Signed URLs / Signed Cookies:**
- The CDN generates time-limited, user-specific URLs for each video session. The URL includes a signature that the CDN verifies before serving content.
- `master.m3u8` is signed with a 4-hour expiry; segment URLs within the manifest are also signed (or the CDN verifies a session cookie for all requests).
- Prevents URL sharing: a signed URL only works for the intended user and expires after the session.

**DRM (Digital Rights Management):**
- For premium content requiring strong protection (movies, sports rights), DRM encrypts the video stream with a key that is only released to authorized, licensed players.
- Standard systems: Widevine (Chrome, Android), FairPlay (Safari, iOS), PlayReady (Edge, Windows).
- Implementation: encrypt segments with AES-128 during transcode; embed key URI in the HLS manifest pointing to a license server. The player requests the decryption key from the license server after authenticating; the license server validates entitlement before issuing the key.
- The CDN serves encrypted segments; even if someone downloads the raw bytes, they cannot decrypt without the key.

## Section 6: Storage Architecture

**Q18. How do you organize video storage in S3?**
A: A hierarchical key structure that maps to CDN URL patterns and supports lifecycle management:

```
s3://video-platform/
├── raw/
│   └── {videoId}/
│       └── source.mp4               # original upload; lifecycle: delete after 30 days
│                                    # (or keep indefinitely for re-transcode capability)
├── transcoded/
│   └── {videoId}/
│       ├── master.m3u8
│       ├── 240p/
│       │   ├── playlist.m3u8
│       │   ├── seg_000.ts
│       │   ├── seg_001.ts
│       │   └── ...
│       ├── 720p/
│       │   ├── playlist.m3u8
│       │   └── ...
│       └── 1080p/
│           └── ...
├── thumbnails/
│   └── {videoId}/
│       ├── default.jpg
│       └── {timestamp}.jpg
└── captions/
    └── {videoId}/
        ├── en.vtt
        └── es.vtt
```

**S3 storage class tiering** reduces cost for older content:
- **S3 Standard** — videos uploaded within the last 30 days; high access frequency.
- **S3 Standard-IA (Infrequent Access)** — videos 30–180 days old; 40% cheaper than Standard with a per-retrieval fee.
- **S3 Glacier Instant Retrieval** — videos > 180 days old with low view counts; 68% cheaper; millisecond retrieval acceptable since CDN caches popular content.
- **S3 Glacier Deep Archive** — raw source files kept for re-transcode capability; 95% cheaper; 12-hour retrieval acceptable.

S3 Intelligent-Tiering automates this lifecycle based on access patterns without per-file monitoring overhead.

**Q19. How do you estimate storage cost for a mid-scale platform?**
A: Concrete estimation is expected in interviews:

```
Assumptions:
  - 10,000 videos uploaded/day
  - Average source file: 2GB (30-min video at 8Mbps)
  - 5 quality variants; average across variants: 2GB per video
  - Retention: keep transcoded forever; source for 90 days

Daily storage growth:
  Source (raw):       10,000 × 2GB   = 20 TB/day
  Transcoded:         10,000 × 2GB   = 20 TB/day
  Total new:          ~40 TB/day

After 1 year (source deleted after 90 days):
  Source (90 days):   90 × 20TB      = 1.8 PB (rolling)
  Transcoded (1 year): 365 × 20TB   = 7.3 PB

S3 cost (US-East at ~$0.023/GB/month):
  Source (IA tier):   1.8PB × $0.0125/GB ≈ $22,500/month
  Transcoded (mixed): 7.3PB × $0.015/GB  ≈ $109,500/month
  Total: ~$132,000/month storage only

CDN egress (separate, often larger cost):
  Assume 1M daily viewers × 500MB avg watch ≈ 500TB/day
  CDN at $0.01/GB: 500TB × $10/TB = $5,000/day → $150,000/month
```

This order-of-magnitude estimation demonstrates you understand that CDN egress often exceeds storage cost at scale, and that codec efficiency (AV1 saving 50% bandwidth) has direct dollar impact.

## Section 7: Live Streaming

**Q20. How does live streaming differ from VOD in architecture?**
A: VOD and live streaming share the HLS format but differ fundamentally in the pipeline:

| Aspect | VOD | Live |
|--- |--- |--- |
| Source | Pre-uploaded file | Real-time RTMP/SRT stream from encoder |
| Transcoding timing | Async, after full upload | Real-time, must keep up with incoming stream |
| Manifest | Static, complete from start | Dynamic, appended every segment duration |
| Segment TTL (CDN) | Immutable (1 year) | Short-lived (seconds to minutes) |
| End-to-end latency | N/A | 5–30s (HLS); 2–5s (LL-HLS / DASH CMAF) |
| Packaging | FFmpeg offline | Media server (Wowza, nginx-rtmp, MediaLive) |

**Live streaming pipeline:**

```
Broadcaster (OBS / hardware encoder)
        │  RTMP / SRT stream
        ▼
┌─────────────────────┐
│  Ingest Server      │  (MediaLive / custom nginx-rtmp)
│  - Receives RTMP    │
│  - Validates stream │
│  - Splits to        │
│    transcoding workers
└────────┬────────────┘
         │  Raw frames
         ▼
┌─────────────────────┐
│  Live Transcoder    │  (Real-time; GPU accelerated)
│  - Multiple bitrates│
│  - Must finish in   │
│    < segment_duration│
└────────┬────────────┘
         │  HLS segments + manifest updates
         ▼
┌─────────────────────┐
│  Packaging / Origin │  Appends segments to manifest
│  Server             │  Writes segments to S3 / CDN origin
└────────┬────────────┘
         │
         ▼
    CDN Edge nodes
    (very short TTL; manifest polled every 2s by players)
```

**Q21. What is Low-Latency HLS (LL-HLS) and when do you need it?**
A: Standard HLS delivers live content with 10–30 seconds of end-to-end latency (3–5 segments of buffer + network). LL-HLS (Apple's extension, RFC 8216bis) reduces this to 2–5 seconds using two mechanisms:
- **Partial segments** — instead of waiting for a full 6-second segment before serving, the server delivers 200ms "partial" segments as they're encoded. Players can start playing before the full segment is available.
- **HTTP/2 Push / blocking playlist requests** — the player requests the next playlist update with `_HLS_msn` and `_HLS_part` parameters; the server holds the response until the requested segment/part is available (server-sent blocking) rather than the player polling at fixed intervals.

Use LL-HLS for: live sports (score spoilers are a real user complaint at 30s delay), live auctions, interactive live events. Standard HLS is fine for: news, concerts, webinars where 15-second latency is acceptable.

## Section 8: Data Model

**Q22. What does the core data model look like?**
A:

```sql
CREATE TABLE videos (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  creator_id        UUID NOT NULL REFERENCES users(id),
  title             TEXT NOT NULL,
  description       TEXT,
  status            TEXT NOT NULL DEFAULT 'UPLOADING',
    -- UPLOADING | PROCESSING | AVAILABLE | FAILED | DELETED
  visibility        TEXT NOT NULL DEFAULT 'PUBLIC',
    -- PUBLIC | UNLISTED | PRIVATE | SUBSCRIBERS_ONLY
  duration_seconds  INT,
  source_s3_key     TEXT,                        -- raw upload path
  master_manifest_url TEXT,                      -- CDN URL of master.m3u8
  thumbnail_url     TEXT,
  view_count        BIGINT NOT NULL DEFAULT 0,
  like_count        BIGINT NOT NULL DEFAULT 0,
  published_at      TIMESTAMPTZ,
```

**Q23. How do you handle view count at scale without write contention?**
A: A popular video can receive thousands of view events per second. A simple `UPDATE videos SET view_count = view_count + 1 WHERE id = $1` serializes all increments through a single row lock — this is a hot spot that degrades at scale. Solutions:

**Buffered counting (standard approach):**
1. Write view events to Kafka (`view.events` topic) — async, no DB write on the hot path.
2. A streaming job (Flink / Kafka Streams) aggregates view counts in 1-minute tumbling windows.
3. The aggregated count is periodically flushed to Redis: `INCRBY video:views:{videoId} {count}`.
4. A background job reads from Redis and updates the `videos.view_count` column every 5 minutes (batching many updates into one `UPDATE`).
5. The API serves view counts from Redis (near-real-time) rather than Postgres (periodic batch update).

**Redis approximate counting for hyper-scale:**
For exact counts beyond billions (YouTube-scale), use Redis HyperLogLog for unique viewer counts — `PFADD video:unique_viewers:{videoId} {viewerId}` — 12KB per video regardless of viewer count, with < 1% error rate. Total views (not unique) remain a simple INCRBY counter.

## Section 9: Scenario Questions

**Q24. "A viral video gets 1 million concurrent viewers within 5 minutes of publishing. How does your system handle it?"**
A: A viral spike stresses three components: transcoding speed (can the video be processed fast enough?), origin (CDN miss storm on first access), and CDN capacity.

**Transcoding speed:**
- Segment-level parallelism across many workers: a 10-minute video split into 300 2-second chunks, transcoded on 300 workers simultaneously, completes in minutes rather than the source duration.
- Auto-scaling the transcoding fleet responds to queue depth — SQS queue depth alarm triggers EC2 Auto Scaling within 2–3 minutes.
- Pre-warming: if the creator has significant followers, the platform can detect the upload and pre-scale the transcoding fleet before the video finishes uploading.

**CDN miss storm:**
- Before publishing the video, pre-warm the CDN: the platform's CDN API allows pushing content to edge nodes proactively. Send the master manifest and the first 60 seconds of each variant to the top-20 CDN PoPs before flipping the video to AVAILABLE status.
- Without pre-warming: the first N requests per PoP all miss the cache simultaneously and hit the S3 origin. S3 is durable but has per-prefix request rate limits — mitigate by using hash-prefixed paths (`/ab/cd/{videoId}/`) to spread requests across S3 partitions.

**CDN capacity:**
- A well-configured multi-CDN setup (CloudFront + Fastly + Akamai) naturally distributes the load. Traffic routing via DNS or Anycast sends viewers to the nearest available PoP with spare capacity.
- The CDN absorbs virtually unlimited concurrent viewers for cached content; the origin sees only cache-miss traffic (< 1% of total for popular content).

**Q25. "Your transcoding pipeline is backing up — 10,000 videos in the queue with a 3-hour processing delay. How do you diagnose and resolve it?"**
A: Systematic triage:

**Diagnose:**
1. Check auto-scaling metrics — is the worker fleet at maximum capacity? If the fleet didn't scale up, check the auto-scaling alarm configuration and IAM permissions.
2. Check worker health — are workers crashing mid-job? Check DLQ depth; high DLQ depth means jobs are failing repeatedly, consuming capacity without completing.
3. Check for a "poison pill" — one very large or malformed file consuming a worker indefinitely. Check worker CPU/memory utilization per instance; a stuck worker shows 100% CPU with no progress on queue depth.
4. Check the SQS visibility timeout — if the timeout is shorter than actual transcode time, jobs re-appear in the queue and multiple workers pick up the same job simultaneously, wasting capacity.

**Resolve:**
1. **Immediate**: increase auto-scaling max capacity; add spot instances to the fleet for burst capacity (transcoding is stateless and tolerates interruption with SQS job requeuing).
2. **Poison pill**: identify stuck jobs via CloudWatch metrics (longest running jobs); manually move them to DLQ for later investigation; unblock the fleet.
3. **Priority queue**: create a priority SQS queue for new uploads (shorter wait time); route the backlog of older uploads to a lower-priority queue. New creators get acceptable wait times even during a backlog.
4. **Partial availability**: while transcoding catches up, make videos available in a single low-quality variant (480p) immediately after that variant completes, rather than waiting for all variants. Update the master manifest as each variant finishes.
5. **Post-incident**: size the baseline fleet to handle N × normal upload rate; configure auto-scaling to pre-scale based on upload rate, not just queue depth (leading indicator vs lagging indicator).
