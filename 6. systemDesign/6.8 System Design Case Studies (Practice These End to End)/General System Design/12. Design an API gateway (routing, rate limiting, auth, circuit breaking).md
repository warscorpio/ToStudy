# Design an API Gateway — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of an API gateway?**
A: Core functional requirements:
- **Routing** — match incoming requests to upstream services by path, method, host, or header; support path rewriting, versioning (`/v1/`, `/v2/`), and weighted routing (canary splits).
- **Authentication & authorization** — validate API keys, JWT tokens, or OAuth2 access tokens before the request reaches upstream; reject invalid credentials at the edge.
- **Rate limiting** — enforce per-client, per-endpoint, or per-tenant request quotas; return `429 Too Many Requests` when exceeded.
- **Circuit breaking** — detect upstream failures and stop forwarding requests to an unhealthy upstream; fail fast rather than accumulating latency.
- **Load balancing** — distribute requests across multiple instances of an upstream service.
- **Request / response transformation** — rewrite headers, strip internal fields from responses, inject correlation IDs, translate between REST and gRPC.
- **Observability** — emit access logs, metrics (latency, error rate, upstream health), and distributed trace spans for every request passing through.
- **TLS termination** — handle HTTPS at the gateway; forward plain HTTP or mTLS internally.

**Q2. What are the non-functional requirements?**
A:
- **Latency overhead** — the gateway sits on every request's critical path. Its own processing overhead should add < 5ms P99. A gateway that adds 50ms to every request is worse than no gateway.
- **High availability** — the gateway is the single entry point; its failure takes down all APIs. Target 99.99% availability; deploy in multiple zones with no single point of failure.
- **Throughput** — must handle the aggregate traffic of all upstream services combined. At 100k RPS across all APIs, the gateway must sustain this without becoming the bottleneck.
- **Horizontal scalability** — the gateway itself must scale out; all state (rate limit counters, circuit breaker state) must be external (Redis), not in-process.
- **Hot configuration updates** — routing rules, rate limits, and circuit breaker thresholds must update without gateway restarts or dropped connections.
- **Security** — the gateway is the outermost trust boundary; it must validate every request, strip internal headers clients shouldn't see (`X-Internal-User-Id` injected by the gateway should not be spoofable by clients), and enforce TLS.

**Q3. What is the difference between an API gateway, a reverse proxy, and a service mesh?**
A:
- **Reverse proxy** (Nginx, HAProxy) — sits in front of one or more services; forwards requests, handles TLS termination, and does basic load balancing. No API-aware logic (no JWT validation, no rate limiting per API key, no circuit breaking per route).
- **API gateway** — a reverse proxy with API-aware middleware: authentication, rate limiting, routing by API version, circuit breaking, request transformation. The business logic of "who can call what at what rate" lives here.
- **Service mesh** (Istio, Linkerd) — handles service-to-service (east-west) traffic inside the cluster. Provides mTLS between services, per-service circuit breaking, and observability without application code changes (sidecar proxy pattern). Complements the API gateway (north-south traffic) rather than replacing it.

In a mature architecture: the API gateway handles external traffic (internet → cluster); the service mesh handles internal traffic (service A → service B). They coexist.

**Q5. How do you separate the control plane from the data plane?**
A:
- **Data plane** — the gateway instances that process live requests. Must be highly available, low-latency, and stateless (no local config state that can become stale). This is the hot path.
- **Control plane** — the system that manages configuration (routes, policies, upstream definitions). Operators or CI/CD pipelines push config changes here; the control plane pushes updates to all data plane instances.

Separation matters because: a control plane outage (e.g., you can't push a new route) should not take down the data plane (existing routes continue to serve traffic). The data plane caches the last-known-good config locally and continues serving it even if the control plane is unreachable.

Implementation: the control plane writes config to etcd or Consul; gateway instances watch for changes (long-poll or gRPC watch) and reload config atomically in memory — no restart required.

## Section 3: Routing

**Q6. How does request routing work in an API gateway?**
A: Routing matches an incoming request to an upstream service using a rule evaluated against request attributes:

```typescript
interface Route {
  id:          string;
  match: {
    methods:   string[];           // ['GET', 'POST']
    pathPattern: string;           // '/api/v1/users/:id' or regex
    headers?:  Record<string, string>;  // host-based routing: {Host: 'api.example.com'}
  };
  upstream: {
    serviceId: string;             // 'user-service'
    pathRewrite?: string;          // rewrite '/api/v1/users' → '/users'
    stripPrefix?: string;          // strip '/api/v1' before forwarding
    timeout: number;               // ms; per-route timeout budget
  };
  rateLimit?:  RateLimitPolicy;
  auth?:       AuthPolicy;
  weight?:     number;             // for canary: 90 = 90% of traffic
}
```

Routes are evaluated in priority order (most specific first). The matching algorithm:
1. Exact path match — highest priority.
2. Prefix match — `/api/v1/` matches `/api/v1/users`, `/api/v1/orders`, etc.
3. Regex match — lowest priority; most flexible but slowest.

**Q7. How do you implement canary deployments and A/B routing?**
A: Weighted routing splits traffic across multiple upstreams for the same route:

```typescript
interface WeightedUpstream {
  serviceId: string;
  weight:    number;   // percentage; must sum to 100
}

// Route config for canary:
{
  match: { pathPattern: '/api/v1/orders' },
  upstreams: [
    { serviceId: 'order-service-v1', weight: 90 },
    { serviceId: 'order-service-v2', weight: 10 }
  ]
}
```

Implementation — weighted random selection:

```typescript
function selectUpstream(upstreams: WeightedUpstream[]): string {
  const rand = Math.random() * 100;
  let cumulative = 0;
  for (const u of upstreams) {
    cumulative += u.weight;
    if (rand < cumulative) return u.serviceId;
  }
  return upstreams[upstreams.length - 1].serviceId;
}
```

For sticky canary (same user always hits the same version): hash `userId` or a cookie value to determine the bucket rather than random selection. This ensures consistent user experience across a session and makes it possible to compare metrics between cohorts accurately.

**Q8. How do you handle API versioning at the gateway?**
A: Three common strategies, each with trade-offs:

- **Path versioning** (`/v1/users`, `/v2/users`) — explicit in the URL; easy to route by prefix; becomes cluttered over time. Most common; easiest for clients to understand.
- **Header versioning** (`Accept: application/vnd.api+json;version=2`) — keeps URLs clean; harder to test in a browser; caching is tricky (Vary header required). Favored by REST purists.
- **Query param versioning** (`/users?version=2`) — flexible but pollutes query strings; rarely used for public APIs.

Gateway routing handles path versioning trivially — separate route entries per version prefix pointing to different upstreams (or the same upstream with a version header injected). The gateway can also support version sunset: when `v1` is deprecated, the gateway adds a `Deprecation` response header and logs a warning metric before forwarding.

## Section 4: Rate Limiting

**Q9. What are the main rate limiting algorithms and when do you use each?**
A:

**Fixed window counter:**
- Count requests in a fixed time window (e.g., 0:00–0:59, 1:00–1:59).
- Simple: one Redis `INCR` + `EXPIRE` per request.
- Flaw: "boundary burst" — a client sends 100 requests at 0:59 and 100 at 1:00, effectively getting 200 requests in 2 seconds while staying within the 100/minute limit.
- Use when: the boundary burst problem is acceptable; simplicity is paramount.

**Sliding window log:**
- Store a timestamp for each request in a sorted set; count entries within the rolling window.
- Precise: no boundary burst.
- Memory-expensive: O(requests) storage per client.
- Use when: precision matters and traffic is low enough that per-request storage is acceptable.

**Sliding window counter (approximation):**
- Blend the current and previous window counts proportionally:
  `estimated_count = prev_window_count × (1 - elapsed_fraction) + current_window_count`
- Memory-efficient (two counters per client), ~1% error rate for uniform traffic.
- Best balance of accuracy and cost; the production standard for most systems.

**Token bucket:**
- A bucket holds up to `capacity` tokens; tokens refill at `rate` per second. Each request consumes one token. Allows bursting up to `capacity` requests instantaneously.
- Good for: APIs where short bursts are acceptable but sustained throughput must be capped.

**Leaky bucket:**
- Requests queue and are processed at a fixed rate; excess requests are dropped. Smooths out bursts entirely.
- Good for: downstream services that can't handle any bursting and need uniform input rate.

**Q10. How do you implement a sliding window counter in Redis?**
A:

```lua
-- Redis Lua script (atomic execution)
local key = KEYS[1]           -- "rl:{client_id}:{window_start_minute}"
local prev_key = KEYS[2]      -- "rl:{client_id}:{prev_window_start_minute}"
local limit = tonumber(ARGV[1])
local window_seconds = tonumber(ARGV[2])
local elapsed_fraction = tonumber(ARGV[3])  -- seconds elapsed in current window / window_seconds

local prev_count = tonumber(redis.call('GET', prev_key) or 0)
local curr_count = tonumber(redis.call('GET', key) or 0)

-- Weighted estimate of requests in the sliding window
local estimated = math.floor(prev_count * (1 - elapsed_fraction) + curr_count)

if estimated >= limit then
  return { 0, estimated, limit }  -- rejected; return count and limit for headers
end

-- Increment current window counter
local new_count = redis.call('INCR', key)
if new_count == 1 then
  redis.call('EXPIRE', key, window_seconds * 2)  -- keep for 2 windows
end

return { 1, estimated + 1, limit }  -- allowed; updated count
```

The Lua script executes atomically — no race condition between reading the counter and incrementing it. Return the counter and limit so the gateway can set `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` response headers.

**Q11. How do you structure rate limit policies — by API key, user, tenant, or endpoint?**
A: Rate limiting is multidimensional; production systems apply multiple policies simultaneously:

```typescript
interface RateLimitPolicy {
  dimension: 'api_key' | 'user_id' | 'tenant_id' | 'ip' | 'global';
  scope:     'global' | 'per_route' | 'per_method';
  limit:     number;
  window:    number;   // seconds
  burstLimit?: number; // for token bucket
}

// Example: tiered limits
const policies: RateLimitPolicy[] = [
  // IP-level (DDoS / bot protection): 100 req/min regardless of auth
  { dimension: 'ip',        scope: 'global',    limit: 100,   window: 60 },
  // Tenant-level (fair sharing): 10,000 req/min per tenant
  { dimension: 'tenant_id', scope: 'global',    limit: 10000, window: 60 },
  // API key level (billing tier enforcement): varies by plan
  { dimension: 'api_key',   scope: 'global',    limit: 1000,  window: 60 },
  // Endpoint-level (protect expensive endpoints): 10 req/min per user
  { dimension: 'user_id',   scope: 'per_route', limit: 10,    window: 60 },
];
```

All applicable policies are checked per request; the request is rejected if **any** policy is exceeded. Redis key structure: `rl:{dimension}:{value}:{route_id}:{window}` gives one counter per dimension per window per route.

**Q12. How do you handle rate limiting in a distributed gateway cluster without a centralized bottleneck?**
A: Three approaches, in order of accuracy vs. overhead:

- **Centralized Redis counter** — all gateway instances share Redis counters. Accurate; adds ~1ms per request for the Redis round-trip. Works well for most scales. Redis Cluster handles throughput at millions of counter increments per second.
- **Local counter with periodic sync** — each gateway instance maintains a local in-process counter and syncs to Redis every 100ms. Allows local serving between syncs; slightly inaccurate (over-serving by up to `local_excess × gateway_count`). Good for very high-throughput scenarios where 1ms Redis latency is too expensive.
- **Token allocation** — the Redis store holds the total remaining tokens; each gateway instance requests a batch (e.g., 100 tokens) and serves from its local allocation. When the batch is exhausted, fetch more from Redis. Reduces Redis calls by 100x; accuracy depends on batch size.

For a 5 YOE interview, the standard answer is centralized Redis — it's accurate and the Redis latency is acceptable. Mention the local counter approach as an optimization if the interviewer probes for scale beyond 100k RPS.

## Section 5: Authentication & Authorization

**Q13. How does JWT validation work at the gateway?**
A: The gateway validates JWTs before forwarding to upstreams — upstreams trust the gateway's verdict and don't re-validate:

```
Client request with Authorization: Bearer <jwt>
        │
        ▼
Gateway:
1. Extract token from Authorization header
2. Decode header → get `kid` (key ID)
3. Fetch public key for `kid` from JWKS endpoint
   (cached locally; refreshed every hour or on `kid` miss)
4. Verify signature using public key
5. Check claims: `exp` (not expired), `iss` (trusted issuer), `aud` (this API)
6. On valid: inject X-User-Id, X-Tenant-Id, X-Roles headers; strip Authorization header
7. On invalid: return 401 Unauthorized; do not forward request
        │
        ▼
Upstream receives request with injected identity headers
(clients cannot set these headers — gateway strips client-supplied X-User-Id)
```

**JWKS caching** is critical for latency — a live JWKS fetch on every request adds 10–50ms. Cache the full JWKS response in memory with a TTL (1 hour); on a `kid` not found in cache, fetch fresh (handles key rotation). The JWT signature validation itself is CPU-bound (asymmetric crypto) but < 1ms for RS256 on modern hardware.

**Q14. How do you handle API key authentication alongside JWT?**
A: Different clients use different auth mechanisms (mobile apps use JWT from OAuth2 flow; server-to-server integrations use API keys). The gateway supports multiple auth schemes, applied based on route config:

```typescript
type AuthScheme = 'jwt' | 'api_key' | 'none';

interface AuthPolicy {
  scheme:    AuthScheme;
  scopes?:   string[];    // required OAuth2 scopes for JWT
  keyHeader?: string;     // header name for API key: 'X-Api-Key' or 'Authorization'
}
```

API key validation flow:
1. Extract key from `X-Api-Key` header (or `Authorization: ApiKey <key>`).
2. Hash the key (SHA-256) — never store raw keys.
3. Look up `hash → {tenantId, rateLimitTier, allowedRoutes, isActive}` in Redis (cache TTL: 5 minutes) or DB on cache miss.
4. Check `isActive`; check that the requested route is in `allowedRoutes`.
5. Inject `X-Tenant-Id` and `X-Rate-Limit-Tier` headers for upstream consumption.

Always hash API keys before storage and comparison — a DB breach should not expose usable keys. On key presentation, hash and compare; the raw key is only ever in transit.

**Q15. How do you prevent clients from spoofing gateway-injected headers?**
A: The gateway must strip any client-supplied headers that it will inject from its own auth validation. If a client sends `X-User-Id: admin` and the gateway doesn't strip it, the upstream service receives a fake user ID even though the request was unauthenticated:

```typescript
const INTERNAL_HEADERS = [
  'X-User-Id',
  'X-Tenant-Id',
  'X-Roles',
  'X-Rate-Limit-Tier',
  'X-Forwarded-User',
  'X-Internal-Auth',
];

function stripInternalHeaders(req: IncomingRequest): void {
  for (const header of INTERNAL_HEADERS) {
    delete req.headers[header.toLowerCase()];
  }
}

// Called BEFORE auth processing, so client-supplied values are removed
// THEN gateway injects its own validated values after successful auth
```

Upstreams must also be configured to only trust these headers from the gateway's IP range (internal network) — a belt-and-suspenders approach in case a client somehow bypasses the gateway.

## Section 6: Circuit Breaking

**Q16. What is a circuit breaker and why does an API gateway need one?**
A: A circuit breaker monitors calls to an upstream service and, when it detects a failure threshold has been crossed, stops forwarding requests to that upstream for a recovery period — returning an immediate error response instead. Without a circuit breaker:
- A slow or failing upstream causes requests to accumulate (thread/connection pool exhaustion).
- Latency cascades: the gateway's connection pool to the failing upstream fills up; new requests queue; P99 latency spikes across the gateway even for healthy upstreams.
- Retry storms: clients retry on failure, multiplying load on an already struggling upstream.

The circuit breaker breaks this feedback loop by failing fast (returning 503 immediately) rather than accumulating connections.

**Q17. What are the three states of a circuit breaker and what triggers each transition?**
A:

```
           failure_rate > threshold              success in HALF_OPEN
CLOSED ──────────────────────────────► OPEN ──────────────────────────► CLOSED
  ▲                                     │                                  ▲
  │         timeout (recovery_period)   │                                  │
  └─────────────────────────────────────►─── HALF_OPEN ────────────────────┘
                                                │
                                                │ failure in HALF_OPEN
                                                └────────────────────► OPEN
```

- **CLOSED** (normal) — requests flow through. The breaker tracks a rolling window of success/failure counts. If `failure_rate > threshold` (e.g., > 50% of requests in the last 10 seconds fail), transition to OPEN.
- **OPEN** (tripped) — all requests immediately return 503 without hitting the upstream. After `recovery_period` (e.g., 30 seconds), transition to HALF_OPEN.
- **HALF_OPEN** (probing) — allow a small number of probe requests through. If they succeed, the upstream has recovered → transition to CLOSED. If they fail, the upstream is still broken → back to OPEN.

**Q18. How do you implement circuit breaker state in a distributed gateway cluster?**
A: Per-gateway in-process circuit breakers are easy but inconsistent — Gateway 1 might have an OPEN breaker for `payment-service` while Gateway 2 still routes to it. For cluster-wide consistency:

**Redis-backed circuit breaker:**

```typescript
interface CircuitBreakerState {
  state:           'CLOSED' | 'OPEN' | 'HALF_OPEN';
  failureCount:    number;
  successCount:    number;
  lastStateChange: number;   // unix ms
  nextAttemptAt?:  number;   // for OPEN: when to move to HALF_OPEN
}

const CB_KEY = (serviceId: string) => `cb:${serviceId}`;

async function checkCircuitBreaker(serviceId: string): Promise<boolean> {
  const raw = await redis.get(CB_KEY(serviceId));
  const state: CircuitBreakerState = raw ? JSON.parse(raw) : defaultClosed();

  if (state.state === 'OPEN') {
    if (Date.now() < state.nextAttemptAt!) return false;  // still open; reject
    // Transition to HALF_OPEN
    await transitionState(serviceId, 'HALF_OPEN');
    return true;  // allow probe request through
  }
  return true;   // CLOSED or HALF_OPEN: allow
}

async function recordResult(serviceId: string, success: boolean): Promise<void> {
  // Use Redis Lua script for atomic read-modify-write of the state
  await redis.eval(updateCircuitBreakerScript, [CB_KEY(serviceId)], [success ? '1' : '0']);
}
```

Trade-off: Redis-backed state adds a Redis round-trip per request (read) and per response (write). At high throughput, use in-process state with periodic cluster synchronization (leader publishes state changes; followers subscribe) to avoid the Redis overhead on every request.

**Q19. How do you configure circuit breaker thresholds per upstream?**
A: Different upstreams have different reliability profiles and tolerance for false trips:

```typescript
interface CircuitBreakerConfig {
  serviceId:          string;
  windowSeconds:      number;    // rolling window for failure rate
  failureThreshold:   number;    // fraction: 0.5 = 50% failures trip the breaker
  minRequests:        number;    // minimum requests in window before tripping
                                 // (prevents tripping on 1 failure in a quiet period)
  recoveryPeriod:     number;    // seconds in OPEN before moving to HALF_OPEN
  halfOpenMaxRequests: number;   // probe requests allowed in HALF_OPEN
  slowCallThreshold:  number;    // ms; calls slower than this count as failures
}

// Example configs:
const configs: CircuitBreakerConfig[] = [
  {
    serviceId: 'payment-service',
    windowSeconds: 10, failureThreshold: 0.3,   // trip at 30% failures
    minRequests: 10, recoveryPeriod: 60,          // 60s recovery (critical service)
    halfOpenMaxRequests: 3, slowCallThreshold: 2000
  },
  {
    serviceId: 'recommendation-service',
    windowSeconds: 30, failureThreshold: 0.6,   // tolerate 60% failures (non-critical)
    minRequests: 20, recoveryPeriod: 15,
    halfOpenMaxRequests: 5, slowCallThreshold: 5000
  },
];
```

`minRequests` is the most commonly forgotten parameter — without it, the first request failure in a quiet period (1 failure out of 1 request = 100% failure rate) immediately trips the breaker.

## Section 7: Load Balancing & Health Checks

**Q20. What load balancing strategies does an API gateway support?**
A:

| Strategy | How it works | Best for |
|--- |--- |--- |
| **Round robin** | Cycle through instances sequentially | Homogeneous instances; stateless services |
| **Weighted round robin** | Cycle with per-instance weights | Mixed instance sizes; canary traffic splitting |
| **Least connections** | Route to instance with fewest active connections | Long-lived requests; variable request duration |
| **IP hash** | Hash client IP → always route to same instance | Session stickiness without a session store |
| **Random** | Pick a random instance | Equivalent to round robin under high load; simpler |
| **Least response time** | Route to instance with lowest recent P99 | Latency-sensitive; requires response time tracking |

For most stateless microservices, round robin is sufficient. Least connections is better when request duration varies significantly (some requests take 1ms, others 500ms — least connections naturally balances load better than round robin in this case).

**Q21. How do you implement health checks for upstream instances?**
A: Two complementary health check types:

**Active health checks** — the gateway probes each upstream instance on a schedule:

```typescript
interface HealthCheckConfig {
  path:            string;          // '/health' or '/ping'
  intervalMs:      number;          // probe every 5000ms
  timeoutMs:       number;          // 2000ms timeout per probe
  healthyThreshold: number;         // 2 consecutive successes → healthy
  unhealthyThreshold: number;       // 3 consecutive failures → unhealthy
  expectedStatus: number;           // 200
}
```

If an instance fails `unhealthyThreshold` consecutive probes, it's removed from the load balancer pool. Restored after `healthyThreshold` consecutive successes. The probe runs from the gateway itself — it catches network-level failures between gateway and upstream.

**Passive health checks (circuit breaker integration)** — the gateway monitors actual request results. A 5xx response or timeout from an upstream instance increments its failure counter. The instance is temporarily removed from the pool when it exceeds the threshold. Passive checks react instantly to failures on live traffic; active checks catch failures between requests.

Both are necessary: active checks catch a failed instance even during quiet periods; passive checks react faster during high traffic.

## Section 8: Observability

**Q22. What observability does an API gateway emit and how is it structured?**
A: The gateway is the best single vantage point for system-wide observability — it sees every request and response across all services.

**Access log (structured JSON per request):**
```json
{
  "timestamp":      "2024-07-23T14:03:00.123Z",
  "method":         "POST",
  "path":           "/api/v1/orders",
  "status":         201,
  "upstream":       "order-service",
  "upstreamInstance": "10.0.1.42:8080",
  "durationMs":     87,
  "upstreamDurationMs": 82,
  "gatewayOverheadMs": 5,
  "clientIp":       "203.0.113.45",
  "userId":         "usr_abc123",
  "tenantId":       "tenant_xyz",
  "correlationId":  "a1b2c3d4-...",
  "rateLimitRemaining": 847,
  "circuitBreakerState": "CLOSED",
  "cacheHit":       false
}
```

**Metrics (emitted to Prometheus / Datadog):**
- `gateway_requests_total{method, route, status, upstream}` — request count by dimension.
- `gateway_request_duration_ms{route, upstream, quantile}` — latency histogram.
- `gateway_upstream_errors_total{upstream, error_type}` — upstream failure count.
- `gateway_rate_limit_hits_total{dimension, route}` — rate limit rejections.
- `gateway_circuit_breaker_state{upstream}` — current state (0=CLOSED, 1=HALF_OPEN, 2=OPEN).
- `gateway_active_connections` — current WebSocket / HTTP2 connection count.

**Distributed trace span:** The gateway creates the root span (or continues an incoming trace) for every request:
```
gateway.request [87ms]
  ├── gateway.auth_validation [2ms]
  ├── gateway.rate_limit_check [1ms]
  └── order-service.upstream_call [82ms]
       └── (order-service creates child spans internally)
```

The `correlationId` is injected as both a trace ID and a response header (`X-Correlation-Id`) so client teams can reference it in support tickets.

## Section 9: Scenario Questions

**Q23. "The payment-service is responding slowly (P99 = 8s instead of 200ms). How does the circuit breaker prevent this from degrading the entire gateway?"**
A: Without a circuit breaker, slow payment-service responses hold gateway connection pool slots open for 8 seconds each. At 1,000 RPS to payment-service with a pool of 100 connections, the pool fills in 0.1 seconds — all subsequent requests queue, P99 spikes to 8s+ for payment requests, and connection pool pressure eventually spills over to other upstreams sharing the gateway's resources.

With the circuit breaker:
1. The `slowCallThreshold` (e.g., 2,000ms) counts calls taking > 2s as failures.
2. After `minRequests` (e.g., 10) requests in the `windowSeconds` (e.g., 10s) window, the failure rate calculation begins.
3. At 30% failure threshold, after ~4 slow calls out of 10 requests, the breaker trips to OPEN.
4. All subsequent payment-service requests immediately return 503 — no connection held, no pool exhaustion, response time drops to < 1ms for the failure path.
5. After `recoveryPeriod` (60s), the breaker moves to HALF_OPEN and allows 3 probe requests. If payment-service has recovered, probes succeed → CLOSED. If not → back to OPEN.

The gateway's other upstreams are completely unaffected because the payment-service connection pool pressure is eliminated by the circuit breaker.

**Q24. "A client is sending 10,000 requests per second, exceeding their 1,000 req/min rate limit. How does your rate limiter handle this, and what does the client receive?"**
A: With the sliding window counter in Redis:

1. The first 1,000 requests within the minute window are allowed through. Redis counter increments to 1,000.
2. Request 1,001 arrives: the Lua script computes `estimated ≥ limit` → returns rejection signal.
3. The gateway returns:
   ```
   HTTP/1.1 429 Too Many Requests
   Retry-After: 34
   X-RateLimit-Limit: 1000
   X-RateLimit-Remaining: 0
   X-RateLimit-Reset: 1721740980
   Content-Type: application/json

   {"error": "rate_limit_exceeded", "retryAfter": 34}
   ```
4. Requests 1,002–10,000 in that second all return 429 immediately — they hit the Redis check (< 1ms) and return without touching the upstream at all.

The upstream (user-service, etc.) sees zero load from the abusive client. The Redis incr for allowed requests and the short-circuit read for rejected requests are both O(1) — the gateway handles 10,000 RPS of rejected traffic cheaply. `Retry-After` tells the client when the window resets so they can implement proper backoff rather than a retry storm.

**Q25. "Your gateway config store (etcd) has an outage. What happens to live traffic?"**
A: The gateway's behavior depends entirely on how the data plane is designed relative to the control plane:

**With proper data plane independence:**
1. Each gateway instance caches its full configuration in memory (routes, rate limit policies, circuit breaker configs, JWKS public keys) on startup and on each config update.
2. On etcd outage, the watch connection fails. The gateway logs a warning but continues serving from its cached config.
3. Configuration changes pushed during the outage are not applied until etcd recovers and the watch resumes.
4. JWKS key rotation: the gateway has the last-fetched public keys in memory (TTL: 1 hour). JWTs signed with those keys continue to validate. If a key rotation happens during the outage and a JWT with a new `kid` arrives, validation fails and returns 401 — acceptable degradation.

**Operational response:**
- Alert on the etcd outage immediately (monitored separately from gateway metrics).
- Config changes that are urgently needed (e.g., a new route for an incident response service) cannot be applied until etcd recovers — this is the correct trade-off (config consistency > live-serving interruption).
- If the outage is prolonged, fall back to a static config file baked into the gateway container as a last resort.

The core principle: the data plane never makes a synchronous call to the control plane on the hot request path. Config is pulled asynchronously and cached; the hot path is never blocked on config store availability.
