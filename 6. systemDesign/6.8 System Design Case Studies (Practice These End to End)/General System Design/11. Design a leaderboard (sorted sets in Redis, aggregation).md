# Design a Leaderboard (Sorted Sets in Redis, Aggregation) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the core engineering problem a leaderboard must solve?**
A: A leaderboard must efficiently answer three queries against a frequently-updated, potentially huge dataset: **"What is player X's rank?"**, **"Who are the top K players?"**, and **"Who are the players around rank R?"** (the neighborhood query). The difficulty is that these queries must be answered in near-real-time against a dataset that is being updated continuously — scores change with every game, purchase, or action. A naive solution (sort the entire user table on every read) doesn't scale. The right data structure must support O(log N) insertions and rank queries simultaneously, where N is the number of ranked entities.

**Q2. What are the five operations a production leaderboard must support?**
A:
- **Score update**: increment or set a player's score. Must be fast (high write volume), atomic (concurrent updates must not race), and idempotent-safe (retry of the same event must not double-count).
- **Rank query**: given a player ID, return their rank among all players. Required for showing "You are #4,821."
- **Top-K query**: return the top K players with their scores and ranks. Required for the global leaderboard page.
- **Neighborhood query**: return the K players immediately above and below a given player. Required for the "players near you" view — more engaging than the raw top-K for most users.
- **Score read**: return a specific player's current score. Required alongside the rank for display.

**Q3. What makes leaderboard design hard at scale?**
A: Three compounding problems:
- **Write amplification**: in a high-engagement game or app, scores update millions of times per second. Every update must touch the sorted ranking structure — high write throughput with low latency.
- **Read hotness**: the top of the leaderboard is read constantly. The top-K query is disproportionately popular — everyone wants to see rank #1, very few care about rank #500,000. This creates hot-key pressure on the leaderboard store.
- **Dimensionality**: real leaderboards are rarely one flat sorted list. They are segmented by time window (today, this week, all-time), geography (country, region), user group (friends, platform), and sometimes multiple score dimensions (score + secondary tiebreaker). Each dimension multiplies the number of distinct leaderboard structures to maintain.

**Q4. What are the two broad categories of leaderboard by scoring model?**
A:
- **Cumulative leaderboards**: score is the running total of all events (e.g., total points earned all-time, total kills, total purchases). Score only increases; once a player earns points they are never removed. Simpler consistency model.
- **Windowed / decaying leaderboards**: score is based on events within a time window (today's score, this week's score, points earned in the last 30 days). Scores expire or decay over time. Significantly harder — requires either periodic recalculation, event expiry, or window-aware aggregation. Most competitive game leaderboards are windowed.

**Q5. What are the consistency requirements for a leaderboard, and how do they differ from a financial system?**
A: Leaderboards are almost universally **eventual consistency** systems. Showing a player's rank as #4,821 when it's actually #4,819 due to two concurrent updates is entirely acceptable — the next read will be correct. This is fundamentally different from a financial balance, where a $2 discrepancy causes real harm. Embracing eventual consistency unlocks: async score updates (don't block the game action on the leaderboard write), approximate rank computation, background aggregation, and batch recalculation. The consistency requirement a leaderboard does have: **monotonic score integrity** — a player's score should never go backward due to a race condition (a concurrent increment producing a lower result than expected).

## Section 2: Redis Sorted Sets

**Q6. What is a Redis sorted set and why is it the canonical data structure for leaderboards?**
A: A Redis sorted set (`ZSET`) is a collection of unique members (strings — e.g., player IDs) each associated with a floating-point score, automatically maintained in sorted order by score. It is implemented as a dual data structure: a **skip list** for O(log N) rank queries and range scans, and a **hash table** for O(1) member-to-score lookups. This combination makes it uniquely suited for leaderboards: inserting/updating a score is O(log N), finding a member's rank is O(log N), and returning a range of members by rank or score is O(log N + K) where K is the number of elements returned. No other common data structure achieves all three efficiently.

**Q7. What are the core Redis commands used in a leaderboard and what are their complexities?**
A:
- `ZADD leaderboard {score} {player_id}` — insert or update a player's score. O(log N). With `NX` flag: only add if member doesn't exist. With `XX` flag: only update if member exists. With `GT`/`LT` flag (Redis 6.2+): only update if new score is greater/less than current — critical for preventing score rollback on out-of-order events.
- `ZINCRBY leaderboard {delta} {player_id}` — atomically increment a player's score by delta. O(log N). Safer than read-then-write for cumulative scores.
- `ZREVRANK leaderboard {player_id}` — return 0-based rank from highest score (rank 0 = #1). O(log N).
- `ZRANK leaderboard {player_id}` — rank from lowest score. O(log N).
- `ZSCORE leaderboard {player_id}` — return the player's score. O(1).
- `ZREVRANGE leaderboard 0 9 WITHSCORES` — top 10 players with scores (highest first). O(log N + K).
- `ZREVRANGEBYSCORE leaderboard +inf -inf LIMIT 0 10 WITHSCORES` — top 10 by score range. O(log N + K).
- `ZRANGEBYSCORE` / `ZREVRANGEBYSCORE` with `LIMIT` — pagination by score. O(log N + K).
- `ZCARD leaderboard` — total number of players on the leaderboard. O(1).
- `ZCOUNT leaderboard {min} {max}` — count players within a score range. O(log N).

**Q8. How do you implement a "players around me" neighborhood query efficiently?**
A: Use `ZREVRANK` to find the player's 0-based rank (highest score = rank 0), then fetch a window around that rank:

```
rank = ZREVRANK leaderboard {player_id}
start = max(0, rank - neighborhood_size)
end = rank + neighborhood_size
neighbors = ZREVRANGE leaderboard {start} {end} WITHSCORES
```

This returns the player and `neighborhood_size` players above and below them in a single O(log N + K) range call. The result includes all players in the window — the client filters to present them as "above you / below you." This is two Redis calls (`ZREVRANK` + `ZREVRANGE`) — combine them in a pipeline or Lua script for a single round trip.

**Q9. How do you handle ties in a sorted set — when multiple players have the same score?**
A: Redis sorted sets break ties lexicographically by member string (ascending). This is often undesirable — you typically want ties broken by time of achievement (earlier achievement = better rank) or some secondary metric. Strategies:
- **Composite score encoding**: encode the tiebreaker into the score itself so that the sort key is unique. For a score with a time tiebreaker: `composite_score = score * 1e10 + (MAX_TIMESTAMP - achievement_timestamp)`. Players with the same base score are ordered by earliest achievement time. Requires careful range selection to not overflow float64 precision (~15 significant digits).
- **Lexicographic member encoding**: use `ZADD` with members encoded as `{score_padded}:{player_id}` and score = 0. Lexicographic sort on the member string acts as the full sort key. Use `ZRANGEBYLEX`/`ZRANGEBYSCORE` for queries. Flexible but more complex key design.
- **Accept Redis default**: for casual leaderboards, lexicographic tie-breaking by player ID is acceptable and requires no extra design. Document it so product understands what it means.

**Q10. What is the precision limitation of Redis sorted set scores and when does it matter?**
A: Redis sorted set scores are IEEE 754 double-precision floats (float64), which provides approximately **15–17 significant decimal digits** of precision. For scores that fit within this range (integers up to 2^53 ≈ 9 quadrillion), exact integer arithmetic is preserved. Problems arise when: (1) composite scores multiply large values together and exceed the precision range — the lower bits of the encoded tiebreaker are silently rounded; (2) floating-point scores accumulate rounding errors across many increments. Fix: keep scores as integers where possible (store points as whole numbers, not fractions). If composite encoding is needed, carefully calculate the required bit width and verify that the two components don't interfere within float64's 52-bit mantissa.

**Q11. How do you implement a paginated leaderboard endpoint backed by Redis?**
A: Use score-based cursor pagination (not rank-based offset) to avoid inconsistency when scores change between page fetches:

```
# Page 1: top K
entries = ZREVRANGEBYSCORE leaderboard +inf -inf WITHSCORES LIMIT 0 {page_size}
cursor = lowest_score_in_page  # returned to client

# Page N+1 (client sends cursor from previous page)
entries = ZREVRANGEBYSCORE leaderboard ({cursor}) -inf WITHSCORES LIMIT 0 {page_size}
# Note: ( prefix means "exclusive lower bound" — excludes the cursor score itself
```

This is stable under concurrent updates: new higher scores don't shift lower-ranked entries' positions relative to the cursor. One caveat: if multiple players share the same score as the cursor, they may be skipped. Handle by using `ZREVRANGEBYSCORE ... LIMIT 0 {page_size+buffer}` and client-side deduplication, or by including player ID in the cursor to handle the tie boundary precisely.

## Section 3: Time-Windowed Leaderboards

**Q12. What are the main types of time-windowed leaderboards and what does each require?**
A:
- **Fixed window** (today, this week, this month): resets on a calendar boundary. All-time score is separate from weekly score. Simple: maintain one sorted set per window (e.g., `leaderboard:weekly:2024-W30`), populated only by events in that window. On window rollover, create a new key; the old key expires naturally via TTL.
- **Rolling window** (last 24 hours, last 7 days): the window slides continuously — a score earned 25 hours ago is no longer counted. Harder: requires tracking when each individual score event occurred so old events can be subtracted as they age out.
- **Seasonal / campaign**: a leaderboard active only for a specific time period (a game season, a promotional event). Functionally identical to a fixed window with a known start and end time.

**Q13. How do you implement a rolling window leaderboard?**
A: Two main approaches:

**Approach 1 — Event log with periodic recalculation**: store every score event with a timestamp in a time-series store (Redis sorted set keyed by timestamp, or Cassandra). Periodically (e.g., every minute), recompute each player's total by summing events within the window: `ZRANGEBYSCORE events:{player_id} {window_start} +inf`. Rebuild the leaderboard sorted set from scratch. Exact, but expensive at scale (recompute all active players every minute).

**Approach 2 — Bucketed aggregation**: divide time into small fixed buckets (e.g., 1-hour buckets). Maintain a sorted set per bucket: `leaderboard:bucket:{hour}`. On each score event, `ZINCRBY` the current bucket. To read the rolling window leaderboard, `ZUNIONSTORE` (union with score summation) across the last N buckets into a temporary sorted set, then read from that. Clean up expired bucket keys via TTL. Trade-off: score granularity is limited to the bucket size (updates within the same bucket look simultaneous), but reads are fast and writes are O(log N) per event.

**Q14. How does `ZUNIONSTORE` work and what is its complexity?**
A: `ZUNIONSTORE destination numkeys key1 key2 ... [WEIGHTS w1 w2 ...]` creates a new sorted set at `destination` that is the union of the input sorted sets. For members appearing in multiple inputs, scores are summed (or combined via AGGREGATE MIN/MAX). Complexity: O(N × K + M × log M) where N is the number of input keys, K is the largest sorted set size, and M is the total number of members in the result. For a 7-bucket rolling window with 1M players per bucket, this is expensive — run it as a background job, cache the result, and serve reads from the cached union rather than computing it on every request.

**Q15. What is the "bucket boundary" problem in bucketed rolling window leaderboards?**
A: When the rolling window is assembled from discrete time buckets, the effective window snaps to bucket boundaries. A "last 7 days" leaderboard using 1-day buckets gives a result accurate only to the day — a score earned 6 days and 23 hours ago may or may not be included depending on where the current bucket boundary falls. For most leaderboards, 1-hour bucket granularity is a good balance: the window is accurate to within 1 hour, buckets are small enough to manage, and only 24–168 buckets need to be unioned for daily/weekly windows. For sub-minute accuracy, use 1-minute buckets but cap the union size.

**Q16. How do you handle leaderboard resets (e.g., weekly reset at midnight Sunday)?**
A: Never delete the old leaderboard in-place — that causes a gap where the leaderboard appears empty mid-reset. Instead:
1. At reset time, rename the current week's key to an archive key: `RENAME leaderboard:weekly leaderboard:weekly:archive:2024-W30`.
2. The new week's key (`leaderboard:weekly`) starts empty. Scores accumulate from the first event of the new window.
3. Set a TTL on the archive key to retain it for historical queries (e.g., 90 days) before automatic expiry.
4. For a clean atomicity boundary, do the rename inside a Lua script or Redis transaction (`MULTI`/`EXEC`) to prevent the brief gap between key deletion and creation.

## Section 4: Aggregation & Score Updates

**Q17. What is the right pattern for updating a player's score on a game event, and what race condition must you avoid?**
A: Use **`ZINCRBY`**, not read-then-write. The read-then-write pattern (`score = ZSCORE lb player; ZADD lb (score + delta) player`) has a race condition: two concurrent events both read the same score, both compute `score + delta`, and both write back — one delta is silently lost. `ZINCRBY lb {delta} {player_id}` is atomic — Redis guarantees the increment happens without interleaving, even under concurrent writes to the same member. For setting an absolute score (not incrementing), `ZADD lb {score} {player_id}` atomically sets the score regardless of the current value.

**Q18. What is "score idempotency" and why does it matter in event-driven systems?**
A: In an event-driven score update pipeline, events may be delivered more than once (at-least-once delivery from Kafka, SQS). If processing the same score event twice increments the player's score twice, the leaderboard is wrong. Idempotency strategies:
- **Deduplication via event ID**: store processed event IDs in a Redis set with TTL. Before processing: `SISMEMBER processed_events {event_id}`. If already seen, skip. After processing: `SADD processed_events {event_id}` (with TTL to bound memory). Adds a Redis read per event.
- **Idempotent score model**: use absolute score updates instead of increments. Each event carries the player's new total score (not a delta). `ZADD lb {new_total} {player_id}` is naturally idempotent — processing it twice produces the same result. Requires maintaining the authoritative score elsewhere (DB) and computing the new total before writing to Redis.
- **`ZADD GT` flag**: (Redis 6.2+) `ZADD lb GT {score} {player_id}` only updates if the new score is greater than the current. For monotonically increasing scores, this makes duplicate and out-of-order events safe — a lower score value is silently ignored.

**Q19. How do you aggregate scores across multiple dimensions (e.g., score = kills × 10 + assists × 3 + wins × 50)?**
A: Two approaches:
- **Pre-aggregate at write time**: compute the composite score in the application layer before writing to Redis. Each game event computes the weighted sum and writes the final score via `ZADD`. The leaderboard stores only the final score — simple and fast at read time. Trade-off: changing the weights requires recalculating all scores from scratch.
- **Store components separately, aggregate at read time**: maintain separate Redis sorted sets for each metric (`kills_lb`, `assists_lb`, `wins_lb`). To read the leaderboard, `ZUNIONSTORE result 3 kills_lb assists_lb wins_lb WEIGHTS 10 3 50`. The union with weights computes the weighted sum. More flexible (weight changes don't require historical data), but `ZUNIONSTORE` across large sorted sets is expensive — run as a background job and cache the result.

**Q20. How do you handle score updates from multiple upstream services (e.g., a score combining in-game events from service A and purchase events from service B)?**
A: Use a **centralized score aggregation service** or a shared event bus:
- All score-contributing services publish events to a Kafka topic (`score-events`) with a common schema: `{player_id, source, delta, event_id, timestamp}`.
- A dedicated score aggregation consumer reads all events, deduplicates, computes the final delta (or new total), and writes to Redis.
- The aggregation consumer owns the Redis sorted set — no other service writes directly to it. This prevents split-brain score state where two services independently increment the same player's score with partial information.

Alternatively, use a **per-source sorted set** (`leaderboard:game`, `leaderboard:purchases`) and combine at read time via `ZUNIONSTORE`. This avoids the aggregation service bottleneck but adds read-time complexity.

**Q21. What is the "hot key" problem for a leaderboard and when does it occur?**
A: A single Redis sorted set is a single key — all reads and writes go to one Redis node (the node owning that key's hash slot). In Redis, a single node can handle ~100,000–500,000 operations/second. For a highly active leaderboard in a popular game with millions of concurrent players updating scores and reading the leaderboard simultaneously, all operations target a single key on a single node. This single-key throughput ceiling is the hot key problem.

Signals: Redis node CPU spike, latency on leaderboard operations increasing, while other nodes in the cluster remain idle. The leaderboard key is not distributed — sharding the cluster doesn't help if all load is on one key.

## Section 5: Scaling & Sharding

**Q22. What strategies exist for scaling a leaderboard beyond a single Redis node's throughput?**
A: Several complementary approaches:

- **Read replicas**: route all read queries (`ZREVRANK`, `ZREVRANGE`) to Redis read replicas. Writes go to the primary. Reduces primary load proportional to the read/write ratio. Simple to implement; adds slight staleness on replicas (typically < 1ms replication lag).
- **Local aggregation + async flush**: instead of writing to Redis on every score event, batch updates in an in-process buffer (or a separate fast local store). Every N seconds or N events, flush the aggregated delta to Redis (`ZINCRBY`). Reduces Redis write frequency by the batch factor. Trade-off: score freshness degrades to the flush interval.
- **Approximate leaderboard via sharding**: partition players across M sorted sets (`leaderboard:shard:0` through `leaderboard:shard:M-1`, assigned by `player_id mod M`). Each shard holds 1/M of players. For top-K queries: query all M shards for their top K, merge, return global top K. Rank queries require knowing the count of players above the player's shard rank — maintained as a per-shard count. Distributes load across M nodes but complicates rank computation.
- **Accept eventual consistency with caching**: cache the top-K result (e.g., top 100 players) in a separate key with a short TTL (5–30 seconds). Reads serve from the cache; only misses (or TTL expiry) hit the sorted set. The top-K list is the most read data — caching it collapses read load dramatically.

**Q23. How does sharding a leaderboard across multiple sorted sets work for rank computation?**
A: With M shards, player rank within their own shard is: `shard_rank = ZREVRANK leaderboard:shard:{s} {player_id}`. Global rank = number of players in higher-ranked shards + shard_rank. "Higher-ranked shards" means shards containing players with higher scores.

This requires knowing the count of players in other shards who have a higher score than this player — which requires either: (1) querying all shards for `ZCOUNT leaderboard:shard:{i} {player_score} +inf` (N additional queries), or (2) maintaining a separate global sorted set of (shard_id, highest_score_in_shard) for approximate rank. Sharding complicates rank queries significantly — it's the main reason sharding is avoided unless throughput absolutely demands it.

**Q24. What is "approximate rank" and when is it an acceptable product trade-off?**
A: Exact rank requires knowing the precise count of all players with a higher score — hard to compute cheaply in a sharded system. Approximate rank uses a probabilistic or sampled approach:
- **Percentile approximation**: maintain a histogram of score distribution (score buckets with player counts). A player's approximate percentile = `players_below_score / total_players`. From percentile, compute approximate rank. Histograms are compact (a few hundred buckets) and can be maintained cheaply.
- **Skip-list sampling**: sample the leaderboard sorted set at regular rank intervals (every 1000th rank) to build an index. Interpolate the player's rank from the two nearest index points. O(1) rank queries with bounded error.
- **Accept ±N rank error**: for a leaderboard of 10M players, showing "approximately rank #48,200" instead of exactly #48,217 is fine. Most users can't perceive a difference. Approximate rank simplifies the distributed implementation enormously.

**Q25. What is the "segment leaderboard" architecture and how does it scale?**
A: Most production leaderboards are segmented — separate leaderboards per country, per platform, per friend group, per user tier. This is actually helpful for scaling: each segment is a separate sorted set, distributed across Redis nodes by key hash. Country segmentation (`leaderboard:country:US`, `leaderboard:country:IN`) naturally distributes load without explicit sharding — each country's leaderboard is a separate key on a different node.

The operational challenge: writes must update all relevant segment leaderboards simultaneously. A score update for a US iOS player touches: `leaderboard:global`, `leaderboard:country:US`, `leaderboard:platform:ios`, `leaderboard:friends:{player_id}`, `leaderboard:weekly:global`. Each is a separate Redis write. Batch these in a pipeline — a single network round trip for N `ZINCRBY` commands — to keep the write path efficient.

**Q26. How do you build a "friends leaderboard" efficiently?**
A: A global sorted set doesn't answer "rank among my friends" — that requires knowing which subset of players are friends with the requesting user. Two approaches:

- **Materialized per-user friend leaderboard**: maintain a separate sorted set per user containing only their friends' scores: `leaderboard:friends:{user_id}`. On score update, write to all friends' leaderboard keys (fan-out on write). On friend add, copy the new friend's current score into the user's friends leaderboard. Expensive fan-out for high-friend-count users; read is O(1).
- **Query-time intersection**: when a user requests their friends leaderboard, fetch the user's friend list, then `ZMSCORE leaderboard:global friend_id_1 friend_id_2 ...` to get all friends' scores in one round trip. Sort in the application layer and compute ranks within the friend set. No fan-out writes; reads scale with friend list size (bounded, typically < 1000 friends). The practical choice for most products.

## Section 6: Persistence & Durability

**Q27. Is Redis the source of truth for the leaderboard, or is there a durable backing store?**
A: Redis should **not** be the only source of truth for leaderboard scores. Redis is a cache-class store: even with AOF persistence, recovery from a crash takes time and may lose the last few seconds of writes. The authoritative score should be stored in a durable DB (Postgres, MySQL, Cassandra) and Redis should be a derived view — a pre-computed sorted index for fast rank queries. The flow:
1. Score event → durable DB (source of truth).
2. Score event also → Redis (derived index for leaderboard queries).
3. On Redis failure or data loss → rebuild the sorted set from the DB.

This means writes must go to both the DB and Redis — either synchronously (slower write path but always consistent) or asynchronously (faster writes, brief Redis/DB divergence).

**Q28. How do you rebuild a Redis leaderboard sorted set from the database after a Redis failure?**
A: Rebuilding strategy:
1. Query the DB for all players' current scores: `SELECT player_id, score FROM leaderboard_scores ORDER BY score DESC`.
2. Batch-insert into Redis using a pipeline of `ZADD` commands. For 1M players, use batches of 10,000 with `ZADD leaderboard {score} {player_id}` per entry. Pipelines reduce round trips — 100 pipeline calls for 1M entries vs. 1M individual calls.
3. During rebuild, the leaderboard may be cold or stale. Options: (1) serve stale results from a snapshot, (2) return an "updating" state to clients, (3) rebuild asynchronously starting from the top (most read) entries first so the top-K is available quickly while the rest rebuilds.

Pre-computation: maintain a periodic Redis `BGSAVE` (RDB snapshot) or enable AOF so that rebuild from DB is a rare fallback rather than the normal recovery path.

**Q29. How do you ensure atomicity when writing to both the DB and Redis?**
A: Two common patterns:
- **Write to DB first, then Redis**: the DB is the authority. If Redis write fails, the DB has the correct score and Redis will be rebuilt or the next event will correct it (via `ZADD GT` semantics). If the DB write fails, neither side is updated — correct behavior. The Redis write can be done asynchronously after the DB commit, via a Kafka event or outbox pattern. Brief inconsistency (DB updated, Redis not yet) is acceptable for a leaderboard.
- **Transactional outbox**: write the score update to the DB inside a transaction with an outbox event. A relay process reads the outbox and updates Redis. Guarantees eventual Redis consistency without a distributed transaction. Adds latency (the relay introduces a small delay) but is more resilient than a direct dual-write.
- **Redis-first with async DB sync**: write to Redis immediately (lower latency), enqueue a DB write. Risks: if Redis fails before the DB is updated, the score is lost. Only acceptable if the DB is truly a secondary store and Redis data can be reconstructed from event logs.

## Section 7: Failure Modes & Anti-patterns

**Q30. What is the "score rollback" bug and what causes it?**
A: A score rollback occurs when a player's score decreases due to a race condition or out-of-order event processing. Example: two workers concurrently process events for the same player. Worker A reads score = 100, computes 100 + 20 = 120, writes 120. Worker B reads score = 100 (before A's write), computes 100 + 15 = 115, writes 115. The final score is 115 — 20 points were silently lost. Fix: use `ZINCRBY` (atomic increment) for delta-based updates, or `ZADD GT` (only update if higher) for absolute score updates. Never use read-then-write for score updates.

**Q31. What is "leaderboard poisoning" and how does it manifest?**
A: Leaderboard poisoning is when invalid or fraudulent scores corrupt the leaderboard — a player has a score of 2^53 (max float64) placing them at rank #1 permanently, or a negative delta incorrectly reduces a player's score below zero. Sources: bugs in score calculation logic, malicious score manipulation by compromised clients, misconfigured weights in a weighted aggregation, or processing the same event multiple times (if idempotency is broken). Defenses: server-side score validation (sanity bounds per event type), score change rate limiting (a player can't gain more than X points per minute), audit logging of all score changes, and anomaly detection alerting on statistically impossible score deltas.

**Q32. What is the "top-K hotspot" and how does caching help?**
A: The global top-K query (`ZREVRANGE leaderboard 0 99`) is called by every user who views the leaderboard — potentially millions of times per minute. Even at O(log N + K) per call, at 100,000 req/sec the Redis node handling the leaderboard key is saturated. The top-K result is also highly stable — in most leaderboards, the top 100 players don't change frequently (rank changes at the top are slow). Cache the top-K response in a separate Redis key (`leaderboard:top100:cache`) with a short TTL (5–30 seconds). `ZREVRANGE` populates this cache; all reads serve from it. This collapses millions of sorted set reads into one read every 5–30 seconds.

**Q33. What is the "ghost player" problem in time-windowed leaderboards?**
A: In a windowed leaderboard, a player who was active in a previous window still appears in the leaderboard even after their window score has expired — because their sorted set entry was never removed. In a rolling window system, their contribution should be zero once all their events fall outside the window, but if the leaderboard is not rebuilt, their old score persists. Fix: when the window aggregation runs (either periodic rebuild or bucket union), players with zero current-window score should be either excluded from the result or explicitly removed from the sorted set: `ZREMRANGEBYSCORE leaderboard -inf 0`. In bucketed systems, a player with no activity in recent buckets naturally contributes zero to the `ZUNIONSTORE` — but only if all old buckets have expired.

**Q34. What is the "rank instability" problem for players near the cutoff in tiered leaderboards?**
A: Many games have tier thresholds (e.g., top 10% of players get a "Gold" tier reward). A player just above or below the cutoff may flip between tiers as scores update — seeing their reward status flicker. This is a UX problem caused by the leaderboard being served in real time. Mitigations: (1) "lock" tier assignments at the end of the season rather than displaying them in real time, (2) add a hysteresis band — a player must be N ranks clear of the cutoff to change tier status, (3) display tier assignment only on the final leaderboard snapshot, not the live one.

## Section 8: Trade-offs & Decision-Making

**Q35. When is Redis sorted set the wrong choice for a leaderboard?**
A: Redis sorted set is the wrong choice when:
- **The leaderboard is enormous and rarely read**: if you have 100M players but the leaderboard is only viewed once per day, the memory cost of keeping 100M entries in Redis is not justified. Use a DB with a sorted index; query it for the top-K and cache the result.
- **Score computation requires complex joins**: if the score depends on data that requires SQL joins (e.g., score adjusted by account age, verified status, subscription tier), precomputing it into a Redis score is brittle. Run the complex query in the DB and cache the result set.
- **Ultra-high write throughput exceeds Redis capacity**: if you have 10M score updates per second (rare, but possible in large-scale real-time games), even Redis can't handle a single sorted set key. Consider stream aggregation (Kafka + Flink) to pre-aggregate scores before writing to Redis, or use a purpose-built leaderboard service.
- **Analytical queries are the primary use case**: if you primarily need queries like "average score by country" or "score percentile distribution," a column-store database (ClickHouse, BigQuery) is far more appropriate than Redis.

**Q36. What is the trade-off between real-time and batch leaderboard computation?**
A:
- **Real-time (Redis sorted set, live updates)**: always current, but requires high write throughput infrastructure, hot key management, and careful consistency handling. Every score event touches the leaderboard immediately.
- **Batch (periodic recalculation from DB)**: leaderboard is recomputed every N minutes from authoritative data. Simpler — no hot key problem, no dual-write complexity, no idempotency concerns. Trade-off: the leaderboard is stale by up to N minutes. Acceptable for many products (weekly leaderboards where minute-level staleness is invisible), unacceptable for real-time competitive games where players need to see rank changes immediately after a game.
- **Hybrid**: real-time for the player's own rank and score display (they care about their own position), batch for the global top-K display (a 60-second-stale top 100 is indistinguishable from a live top 100 for most users). Use Redis for own-rank queries, a cached batch snapshot for the leaderboard page.

**Q37. How do you design a leaderboard for a system where score calculation involves multiple aggregated metrics with changing weights?**
A: Avoid baking weights into the Redis score — it makes weight changes expensive (full recalculation required). Instead:
- **Store raw metrics separately**: maintain sorted sets for each metric (`kills_lb`, `wins_lb`, `assists_lb`). Scores are the raw metric values.
- **Compute composite on demand**: use `ZUNIONSTORE result 3 kills_lb wins_lb assists_lb WEIGHTS {w1} {w2} {w3}` to produce a composite leaderboard at query time. Cache the result.
- **Make weight changes cheap**: updating weights only requires re-running the `ZUNIONSTORE` with new weights — no historical data is lost, no per-player recalculation.
- **Cost**: `ZUNIONSTORE` across large sorted sets is expensive (O(N log N) for N total members). Run it as a scheduled job (e.g., every minute), not on every read.

## Section 9: Scenario / System Design Style Questions

**Q38. "Design a real-time global leaderboard for a mobile game with 10 million daily active players. Walk through the full architecture."**
A:
- **Score update path**: game server emits a `ScoreEvent` to Kafka on game completion. A score consumer reads events, deduplicates via event ID (Redis set), validates the score delta (server-side bound check), and writes to: (1) Postgres `player_scores` table (source of truth: `UPSERT player_id, total_score, updated_at`), (2) Redis `ZINCRBY leaderboard:global {delta} {player_id}` for the global leaderboard, (3) Redis `ZINCRBY leaderboard:weekly:{week_key} {delta} {player_id}` for the weekly leaderboard.
- **Top-K reads**: a background job (runs every 10 seconds) executes `ZREVRANGE leaderboard:global 0 99 WITHSCORES` and caches the result as serialized JSON in `leaderboard:top100:cache` with TTL=10s. The leaderboard page reads from `leaderboard:top100:cache` — a single O(1) GET, not a sorted set scan. 99.9% of leaderboard page reads are served from this cache.
- **Own rank reads**: `ZREVRANK leaderboard:global {player_id}` + `ZSCORE leaderboard:global {player_id}` — two pipelined commands per player request. No cache (personalized per player). Served in ~1ms.
- **Neighborhood query**: `ZREVRANK` to get rank, then `ZREVRANGE rank-5 rank+5` — two pipelined commands.
- **Weekly reset**: cron job at Monday 00:00 UTC renames `leaderboard:weekly:{current_week}` → `leaderboard:weekly:{current_week}:archive` and sets TTL=90 days on the archive. New week key starts fresh.
- **Durability**: on Redis failure, score consumer falls back to DB-only writes. Rebuild job reads `SELECT player_id, total_score FROM player_scores ORDER BY total_score DESC` in batches of 10,000 and pipelines `ZADD` commands to Redis.

**Q39. "A player completes an action in your system that should add 50 points. The request is processed twice (at-least-once delivery). How do you prevent a 100-point credit?"**
A: Idempotency via event ID deduplication:
1. Each score event carries a globally unique `event_id` (UUID generated client-side or server-side at the action point).
2. Before processing: `SET processed:{event_id} 1 NX EX 86400` — set with NX (only if not exists) and 24-hour TTL. If the SET returns 0, the event was already processed; skip.
3. If the SET returns 1: apply `ZINCRBY leaderboard {delta} {player_id}` and `UPDATE player_scores SET score = score + 50 WHERE player_id = ?`.
4. The `NX` + TTL pattern guarantees: each event_id is processed exactly once within the 24-hour deduplication window; after 24 hours the key expires, but duplicate events older than 24 hours are presumed handled.

If using `ZADD GT` with absolute scores (total score, not delta): duplicate processing is inherently idempotent — writing the same total score twice produces the same result. This requires computing the new total before writing, which requires reading the current score from the DB.

**Q40. "The weekly leaderboard reset is causing a 30-second spike in DB and Redis load every Monday. How do you fix it?"**
A: The spike has two components: the reset operation itself and the cold cache afterward.
- **Reset operation**: if the reset involves querying all player scores from the DB and re-inserting into Redis, that is O(N) DB reads and Redis writes. Fix: the weekly leaderboard is already a separate Redis sorted set (`leaderboard:weekly`). The reset is just a `RENAME` + TTL — O(1), zero DB reads. The new weekly sorted set starts empty and fills organically as the week progresses. No bulk re-seeding needed.
- **Cold cache after reset**: Monday morning, all players' weekly scores are 0, so the leaderboard is empty or minimal. Top-K queries return few results. Players writing their first event of the week each trigger a `ZINCRBY` that inserts them into the fresh sorted set — this is the normal warm-up. Pre-seed with: after the rename, immediately run a background job that copies top-N global leaderboard players into the new weekly sorted set with a score of 0, so the leaderboard isn't visually empty. No DB reads needed — copy from the existing global sorted set.
- **DB spike root cause**: investigate whether the reset is triggering unnecessary DB reads at all. If the weekly sorted set is maintained independently in Redis and the DB is only the fallback, the reset should not touch the DB.

**Q41. "How would you design a leaderboard for 1 billion registered players where only 1% are active on any given day?"**
A: 1 billion players in a Redis sorted set = ~100GB RAM just for member storage — impractical. But only 10M are active daily.

**Architecture**:
- **Redis sorted set for active players only**: only insert players into the Redis leaderboard when they post their first score in the current period. Inactive players are not in the sorted set. 10M active players → ~1GB Redis memory.
- **DB (Postgres or Cassandra) as the full leaderboard**: store all-time scores in `player_scores` with a `score` index. For deep pagination (ranks beyond the active set), fall through to the DB.
- **Hybrid rank computation**: for ranks within the active set (top ~10M), use `ZREVRANK` in Redis — fast, exact. For a player ranked #50M among all-time players, query: `SELECT COUNT(*) FROM player_scores WHERE score > {player_score}` — their approximate global rank from the DB (slow, but rarely needed; cache the result).
- **Inactive player on return**: when an inactive player posts a score, insert them into the Redis sorted set via `ZADD`. If their score ranks them into the top K of the Redis set, they appear on the leaderboard immediately.
- **Score threshold for leaderboard eligibility**: for display purposes, only show players who have posted at least one score in the current period. A player with an all-time score from 3 years ago shouldn't appear on the "this week" leaderboard.

**Q42. "You need to support 'rank among my country' and 'rank globally' simultaneously. Walk through how you maintain both without doubling your write amplification problem."**
A: Two sorted sets per player update: `leaderboard:global` and `leaderboard:country:{country_code}`. Write both in a Redis pipeline — a single network round trip for 2 `ZINCRBY` commands. Pipeline overhead is negligible; the two writes arrive at the Redis node in one batch.

Key concerns:
- **Country assignment**: country is determined server-side at registration and stored in the player profile. Never trust a client-supplied country parameter for leaderboard placement.
- **Country change**: if a player's country changes (rare), remove them from the old country sorted set (`ZREM leaderboard:country:{old_country} {player_id}`) and add them to the new one with their current score. Retroactive history (past weeks' country leaderboards) is not updated — accepted as a product limitation.
- **Cardinality**: with ~200 countries, the write amplification is 2× (global + one country), not 200×. Each country sorted set is smaller and independently scalable.
- **Top-K by country**: `ZREVRANGE leaderboard:country:US 0 99` — same O(log N + K) operation as the global leaderboard. Cache per-country top-K results separately.
- **Memory**: 200 country sorted sets containing non-overlapping subsets of the global player population consume the same total memory as the global sorted set — no amplification, just distribution across more keys.

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Redis sorted set (ZSET)       | Skip list + hash table: O(log N) insert/rank, O(log N + K) range scan — the canonical leaderboard structure |
| `ZINCRBY`                     | Atomic score increment; prevents the read-then-write race condition for delta-based score updates            |
| `ZADD GT`                     | Only update if new score is greater; makes absolute score updates idempotent for monotonic scores            |
| `ZREVRANK`                    | 0-based rank from highest score; rank 0 = #1 on the leaderboard                                             |
| `ZREVRANGEBYSCORE` with LIMIT | Score-based cursor pagination; stable under concurrent score updates unlike offset pagination                |
| `ZUNIONSTORE`                 | Union multiple sorted sets with optional per-set weights; used for composite scores and rolling windows      |
| Composite score encoding      | Pack multiple sort dimensions into a single float64 score for tie-breaking without auxiliary data structures |
| Hot key problem               | All leaderboard operations target a single Redis key on one node; throughput capped by that node's capacity |
| Active user filter            | Only insert players with recent activity into Redis; avoids storing inactive players in the sorted set       |
| Bucket aggregation            | Divide time into fixed buckets (1-hour ZSET each); union recent buckets for rolling window leaderboard      |
| Ghost player                  | Expired-window player still appearing due to un-evicted sorted set entry                                     |
| Rank instability              | Player near a tier boundary flickering between tiers as scores update in real time                           |
| Neighborhood query            | ZREVRANK + ZREVRANGE to return players immediately above and below a given player's rank                     |
| Score idempotency             | Processing the same score event twice produces the same result; achieved via event ID deduplication or ZADD GT|
| Leaderboard poisoning         | Invalid or fraudulent scores corrupting rank order; prevented by server-side validation and rate limits      |
| Segment leaderboard           | Separate sorted set per dimension (country, platform, friends); naturally distributes across Redis nodes     |

---

**Tip for the interview:** Leaderboard questions are often deceptively simple — "use a Redis sorted set" is the expected first answer, but the real conversation starts with follow-ups. Be ready to address the hot key problem (single sorted set → single node ceiling → read replicas + caching top-K), time-windowed leaderboards (bucketed ZUNIONSTORE vs. periodic rebuild), the celebrity/friends leaderboard (query-time ZMSCORE merge vs. materialized per-user sets), and durability (Redis is not the source of truth — DB is). The candidates who stand out can also explain *why* `ZINCRBY` is used instead of read-then-write, that `ZADD GT` exists and what problem it solves, and how composite float64 scores encode tie-breaking — these signal hands-on Redis experience, not just textbook knowledge.
