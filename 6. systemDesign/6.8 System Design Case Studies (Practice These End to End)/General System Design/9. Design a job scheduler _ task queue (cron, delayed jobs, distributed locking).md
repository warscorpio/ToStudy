# Design a Job Scheduler / Task Queue (Cron, Delayed Jobs, Distributed Locking) — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scoping

**Q1. What are the functional requirements of a job scheduler / task queue system?**
A: Before designing, define the scope clearly:
- **One-time delayed jobs**: Enqueue a task to run once at a specific future time — e.g., send a payment reminder 24 hours after invoice creation, expire a session token at T+30min.
- **Recurring cron jobs**: Run a task on a fixed schedule — e.g., generate daily settlement reports at 2am, retry failed NACH debits every 6 hours.
- **Immediate async jobs**: Decouple slow operations from the request path — e.g., send a welcome email after user signup, trigger KYC verification asynchronously.
- **Distributed execution**: Multiple worker nodes pick up and execute jobs, with no two workers running the same job concurrently (exactly-once execution semantics, or at-least-once with idempotency).
- **Job lifecycle management**: Jobs have states — `pending`, `running`, `completed`, `failed`, `retrying`, `dead`. Transitions are tracked.
- **Retry with backoff**: Failed jobs retry with exponential backoff up to a configurable max attempt count.
- **Dead letter**: Jobs that exhaust retries move to a dead letter state for human inspection and optional replay.
- **Priority**: High-priority jobs (fraud checks, OTP generation triggers) execute before low-priority batch jobs.
- **Job cancellation**: Cancel a scheduled or pending job before it runs.
- **Observability**: Queue depth, job execution duration, failure rates, and cron schedule adherence tracked as metrics.

**Q2. What are the non-functional requirements?**
A:
- **Reliability**: No job should be silently dropped. Every enqueued job either completes, fails with a tracked error, or is dead-lettered.
- **Exactly-once execution (or at-least-once with idempotency)**: The same job must not execute concurrently on two workers. True exactly-once is hard; at-least-once with idempotent job handlers is the practical standard.
- **Durability**: Jobs survive process restarts and node failures. Volatile in-memory queues (like Bull's in-memory mode) are insufficient for production.
- **Low scheduling jitter**: A cron job scheduled for 02:00:00 should fire within seconds of that time, not minutes. Jitter > 30 seconds is usually unacceptable for financial batch jobs.
- **Horizontal scalability**: Adding worker nodes should linearly increase throughput without coordination overhead.
- **Backpressure**: Workers should not be overwhelmed — rate-limit job dispatch based on worker capacity.
- **Throughput**: A mid-scale system handles 10,000–100,000 jobs/hour. Large-scale: millions/hour.

**Q3. What are the core entities in a job scheduler?**
A: The domain model:
- **Job definition**: The template — `{id, name, handler, default_retry_limit, default_timeout_ms, default_priority}`.
- **Job instance**: A specific execution — `{id, definition_id, payload, status, priority, run_at, started_at, completed_at, attempt_count, max_attempts, idempotency_key, worker_id, error}`.
- **Cron schedule**: A recurring trigger — `{id, name, cron_expression, job_definition_id, payload_template, timezone, enabled, last_fired_at, next_fire_at}`.
- **Job lock**: Distributed mutex for a running job — `{job_id, worker_id, acquired_at, expires_at}`.
- **Dead letter record**: Exhausted job preserved for review — `{job_id, last_error, dead_lettered_at, replayed: false}`.

## Section 2: High-Level Architecture

**Q4. What are the major components of a job scheduler system?**
A: Five core components:

```
Producers (API services, event consumers, cron trigger)
          |
          | enqueue(job, run_at, priority)
          ▼
  [1] Job Store (Postgres / Redis)
      - Durable job records with status
      - Scheduled jobs indexed by run_at
      ▼
  [2] Scheduler / Dispatcher
      - Polls for due jobs (run_at <= now)
      - Claims jobs via distributed lock
      - Pushes claimed jobs to work queue
      ▼
  [3] Work Queue (Redis / Kafka / SQS)
      - In-flight jobs ready for execution
      - Priority lanes per tier
      ▼
  [4] Worker Pool
      - Pulls jobs from work queue
      - Executes handler, updates status
      - Heartbeats lock during execution
      - Retries or dead-letters on failure
      ▼
  [5] Cron Trigger
      - Evaluates cron schedules
      - Enqueues job instances at fire time
      - Ensures exactly-one trigger per fire
```

The **Job Store** is the source of truth — the work queue is a delivery mechanism, not the record of what needs to run. If the work queue loses a message, the Scheduler re-discovers it from the Job Store on the next poll cycle.

**Q5. What is the role of the Job Store vs the Work Queue?**
A: A critical architectural distinction:

- **Job Store** (Postgres): Durable, queryable, the authoritative record of every job and its current status. Survives process crashes. Supports complex queries (jobs due in the next 5 minutes, jobs belonging to a tenant, jobs in `failed` state). Slow to poll at high frequency.
- **Work Queue** (Redis Sorted Set / SQS / Kafka): Fast, ephemeral delivery channel for jobs that are ready to run right now. Workers pull from the queue for low-latency dispatch. Not the source of truth — if a message is lost (Redis flush, SQS message expiry), the Scheduler re-publishes from the Job Store.

The two-tier design decouples durability from throughput: Postgres gives you durability and queryability; Redis/SQS gives you fast, low-latency job dispatch to workers.

**Q6. What does the Scheduler / Dispatcher do, and why is it a separate component?**
A: The Scheduler is the bridge between the Job Store and the Work Queue. Its responsibilities:
- **Polling for due jobs**: Every N seconds (typically 1–5s), query `SELECT * FROM jobs WHERE status = 'pending' AND run_at <= NOW() ORDER BY priority DESC, run_at ASC LIMIT 500`.
- **Claiming jobs**: Acquire a distributed lock on each due job before pushing it to the Work Queue — prevents two Scheduler instances from dispatching the same job to two workers.
- **Heartbeat management**: Track which running jobs have stale locks (worker crashed) and re-queue them.
- **Cron expansion**: Evaluate cron schedules and enqueue new job instances at fire time.

It's a separate component (not merged into workers) because its bottleneck is DB polling latency and lock acquisition, not CPU — it scales differently from workers, and separating concerns makes each independently tunable.

## Section 3: Cron Jobs

**Q7. How do you implement recurring cron jobs in a distributed system?**
A: The challenge: multiple Scheduler instances may all evaluate the same cron schedule simultaneously and each trigger a job — resulting in duplicate runs. The solution is a single-leader election for cron evaluation combined with idempotent job creation:

**Approach 1 — Leader election (simplest)**:
One Scheduler instance holds a `cron_leader` lock in Redis (`SET cron_leader {instance_id} NX EX 30`). Only the leader evaluates cron schedules and fires jobs. Other instances compete for leadership if the leader's heartbeat stops. Simple, but the leader is a single point of failure for scheduling (not for execution — workers are still distributed).

**Approach 2 — Idempotent fire-per-window (more robust)**:
Each cron schedule has a `next_fire_at` timestamp stored in the DB. On each poll cycle, every Scheduler instance executes:
```sql
UPDATE cron_schedules
SET last_fired_at = NOW(),
    next_fire_at  = calculate_next(cron_expression, NOW())
WHERE id = $1
  AND next_fire_at <= NOW()
  AND next_fire_at > NOW() - INTERVAL '60 seconds'  -- idempotency window
RETURNING id;
```
The `UPDATE ... WHERE next_fire_at <= NOW()` with an optimistic lock — only one instance gets a row back (the others update 0 rows and skip). The winner enqueues the job. No leader election required; the DB atomicity handles the race.

**Q8. How do you parse and evaluate cron expressions?**
A: Use an established cron parsing library — do not hand-roll this. Common cron expression formats:
- **Standard 5-field**: `minute hour day-of-month month day-of-week` — `0 2 * * *` = daily at 2am.
- **6-field with seconds**: `second minute hour day-of-month month day-of-week` — used by Quartz, Spring.
- **7-field with year**: Rarely needed but supported by some libraries.
- **Named shortcuts**: `@daily`, `@hourly`, `@weekly`.

In Node.js/NestJS: `node-cron`, `croner`, or `cron-parser` for parsing and computing `next_fire_at`. Key concern: **timezone handling**. Always store and compute cron schedules in a specified timezone (`Asia/Kolkata` for Indian fintech), not UTC — a cron scheduled for "2am" must fire at 2am IST, not 2am UTC. Store the timezone alongside the cron expression, not baked into it.

**Q9. What happens if a cron job misses its scheduled fire time (e.g., the system was down)?**
A: Three strategies depending on the job's semantics:

- **Fire immediately on recovery (catch-up)**: As soon as the system restarts, fire the missed job. Suitable for jobs where the work is still valid even if late — e.g., a retry sweep that missed its 6am run can run at 6:15am when the system recovers.
- **Skip missed fires**: If the system was down for 2 hours and a job was scheduled every 15 minutes, skip the 8 missed runs and wait for the next scheduled time. Suitable for jobs where running old instances has no value or would cause confusion — e.g., a "daily summary email" that missed yesterday's window should not fire 8 times on recovery.
- **Fire exactly N missed instances**: For audit or financial reconciliation jobs, every missed run must execute — fire all missed instances in sequence. Requires computing all missed fire times between `last_fired_at` and `now`.

The strategy is a per-schedule configuration. Default for fintech batch jobs: **skip missed, fire at next scheduled time** — running a settlement report 2 hours late is usually less harmful than running it 8 times.

**Q10. How do you prevent a long-running cron job from overlapping with its next scheduled run?**
A: Use a job lock with a `running` status check before firing:
```sql
-- Only fire if no instance is currently running
INSERT INTO jobs (id, definition_id, payload, status, run_at)
SELECT gen_random_uuid(), $1, $2, 'pending', NOW()
WHERE NOT EXISTS (
  SELECT 1 FROM jobs
  WHERE definition_id = $1
    AND status IN ('pending', 'running')
);
```
If a prior instance is still running, the new instance is not created — the schedule skips this fire. Alert if a job consistently overlaps with itself (it's taking longer than its schedule interval — the interval needs increasing or the job needs optimisation).

## Section 4: Delayed Jobs

**Q11. How do you implement delayed job scheduling efficiently?**
A: A delayed job has a `run_at` in the future — the system must hold it until then and execute it as close to `run_at` as possible. Two storage strategies:

**Redis Sorted Set (for sub-minute precision)**:
```
ZADD delayed_jobs {run_at_epoch_ms} {job_id}
```
The Scheduler runs a tight loop:
```
ZRANGEBYSCORE delayed_jobs 0 {now_epoch_ms} LIMIT 100
→ claim each job, push to work queue, ZREM from delayed_jobs
```
Pros: millisecond-precision, fast range scan, O(log N) insert and remove. Cons: Redis is not durable by default — enable AOF persistence (`appendfsync everysec`) or accept that a Redis crash may lose recently-enqueued delayed jobs (mitigated by Postgres as the authoritative store).

**Postgres with polling (for minute-level precision)**:
```sql
SELECT id FROM jobs
WHERE status = 'pending'
  AND run_at <= NOW()
ORDER BY priority DESC, run_at ASC
LIMIT 500
FOR UPDATE SKIP LOCKED;
```
Poll every 5–10 seconds. Pros: durable, consistent, no additional infrastructure. Cons: polling adds latency (up to poll interval) and DB load. Sufficient for most fintech delayed jobs where ±10 seconds is acceptable.

**Hybrid (recommended)**: Postgres is the authoritative store for all jobs. A background sync process pushes jobs due in the next 5 minutes from Postgres into a Redis Sorted Set. The Scheduler polls Redis for due jobs (fast, low-latency) and falls back to Postgres polling for jobs Redis missed (e.g., after a Redis restart).

**Q12. How do you handle a delayed job whose payload references data that changes between enqueue time and execution time?**
A: This is the "stale payload" problem — a job enqueued with `{amount: 5000}` may run after the amount was updated to `6000`. Two approaches:

- **Store a reference, not a snapshot**: The payload stores only the entity ID (`{payment_id: "pay_789"}`), not the full entity. The job handler re-fetches from the DB at execution time — always gets current state. Preferred for most cases; the job acts on the current truth, not a stale snapshot.
- **Store a snapshot with a version**: The payload includes the entity and its version (`{payment: {...}, version: 7}`). The handler checks if the entity's current version matches; if not, it either re-processes with current state or aborts (the triggering condition may no longer be valid). Required when the job must act on the state *at enqueue time*, not execution time — e.g., a price-locked order that must be processed at the price the user saw.

**Q13. How do you implement job cancellation for a delayed job?**
A: Cancellation depends on the job's current state:
- **`pending` (not yet dispatched)**: Update status to `cancelled` in the Job Store. The Scheduler will skip it on next poll (status check in the query). If it's also in the Redis Sorted Set, `ZREM delayed_jobs {job_id}`.
- **`running` (worker is executing it)**: Send a cancellation signal to the worker — either via a Redis pub/sub channel the worker subscribes to (`PUBLISH cancel:{job_id} 1`) or a DB flag the worker checks at checkpoints within the handler. Long-running jobs must periodically check for cancellation — a handler that ignores cancellation can't be interrupted without killing the process.
- **`completed`**: Cancellation is a no-op — the job already ran. Return an error to the caller.

Cancellation is soft by default — the job record transitions to `cancelled` status and is retained for audit. Hard deletion is available for compliance-driven data removal but requires explicit confirmation.

## Section 5: Distributed Locking

**Q14. Why do you need distributed locking in a job scheduler?**
A: In a horizontally scaled worker pool, multiple workers compete to execute jobs. Without coordination:
- **Double execution**: Two workers both dequeue the same job message and execute it concurrently — a payment job runs twice, charges the user twice.
- **Concurrent cron fires**: Two Scheduler instances both fire the same cron job at 2am — the settlement report runs twice.
- **Stale lock takeover**: A worker crashes mid-job; another worker must eventually take over, but only after confirming the first worker is genuinely dead (not just slow).

Distributed locking is the mechanism that ensures at most one worker executes a given job at any time.

**Q15. How do you implement a distributed lock with Redis for job execution?**
A: Use the `SET NX PX` command — atomic set-if-not-exists with a TTL:
```
SET lock:job:{job_id} {worker_id} NX PX {timeout_ms}
```
- `NX`: Only set if the key doesn't already exist — the lock.
- `PX {timeout_ms}`: The lock expires after `timeout_ms` even if the worker doesn't release it — prevents permanent lock if the worker crashes.
- Value `{worker_id}`: Stored so only the lock owner can release it (prevents a different worker from accidentally releasing a lock it doesn't hold).

Release — only if still the owner:
```lua
-- Lua script for atomic check-and-delete
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

The Lua script is critical — a non-atomic `GET` then `DEL` has a race window where another worker acquires the lock between the GET and the DEL, and the original worker then deletes the new owner's lock.

**Q16. What is lock expiry, and why is choosing the right TTL difficult?**
A: The lock TTL must be long enough that the job completes before the lock expires, but short enough that a crashed worker's lock is reclaimed quickly. The tension:
- **TTL too short**: A legitimate job running slightly long loses its lock → another worker picks up the same job → double execution.
- **TTL too long**: A crashed worker's lock keeps the job blocked for the full TTL before another worker can reclaim it → job delay proportional to TTL.

No single TTL fits all jobs. Solutions:
- **Per-job-type timeout**: Configure a `timeout_ms` per job definition based on expected execution time. A 5-second DB query job has a 30-second lock TTL; a file export job has a 5-minute lock TTL.
- **Lock heartbeat / renewal**: The worker extends the lock TTL while the job is actively running:
```
every 10 seconds while job is running:
  SET lock:job:{job_id} {worker_id} XX PX {timeout_ms}
  -- XX: only set if key already exists (don't re-acquire, only renew)
```
If the worker crashes, the heartbeat stops, and the lock expires after one TTL window — regardless of how long the job was expected to run.

**Q17. What is Redlock, and when should you use it?**
A: Redlock is Redis's algorithm for distributed locking across multiple independent Redis nodes, designed to provide safety guarantees even if a single Redis node fails. It acquires locks on N Redis masters (typically 5), considers the lock valid only if acquired on a majority (⌊N/2⌋+1), and uses the minimum remaining TTL across successful acquisitions. Use Redlock when: a single Redis node is a single point of failure for your locking infrastructure and the job you're protecting has serious consequences for double execution (financial transactions, irreversible side effects). Don't use Redlock for most job scheduling use cases — a single Redis node with AOF persistence is sufficient, and Redlock adds significant complexity. The `redlock` npm package implements this algorithm.

**Q18. What is the "fencing token" problem with distributed locks, and how do you handle it?**
A: A fencing token addresses the scenario where a worker holds a lock, experiences a long GC pause or network partition, the lock expires, another worker acquires the lock and starts the job, and then the first worker resumes and also tries to complete the job — both think they hold the lock. Fencing tokens solve this: when a lock is acquired, the lock service returns a monotonically increasing token. Every write operation to the downstream resource (DB update, file write) includes the fencing token. The resource rejects writes with a token lower than the highest it has seen:
```sql
UPDATE jobs SET status = 'completed'
WHERE id = $1
  AND lock_token = $2   -- only the current lock holder's token matches
  AND status = 'running';
-- If 0 rows updated → lock was stolen; this worker must abort
```
In practice, most job schedulers use the `worker_id` + DB status check as an implicit fencing mechanism — if the job's `worker_id` in the DB doesn't match the current worker, the write is rejected. True fencing tokens are needed only when the external resource doesn't support conditional writes.

**Q19. How do you detect and recover from a worker that crashed mid-job?**
A: A crashed worker leaves a job in `running` state with an expired lock. Recovery:
1. **Heartbeat tracking**: Workers write a heartbeat to the Job Store every N seconds (`UPDATE jobs SET heartbeat_at = NOW() WHERE id = $1 AND worker_id = $2`).
2. **Stale job detector**: A Scheduler process runs a periodic sweep (every 30–60 seconds):
```sql
SELECT id FROM jobs
WHERE status = 'running'
  AND heartbeat_at < NOW() - INTERVAL '60 seconds';
-- These jobs' workers are presumed dead
```
3. **Re-queue or fail**: For each stale job, increment `attempt_count`. If `attempt_count < max_attempts`, reset status to `pending` and set `run_at = NOW() + backoff(attempt_count)`. If exhausted, transition to `dead`.
4. **Lock cleanup**: The Redis lock TTL handles itself — it expired when the worker crashed. The stale detector only needs to update the Job Store status.

The sweep interval + lock TTL together determine the maximum delay before a crashed job is recovered: `max_recovery_delay = lock_TTL + sweep_interval`.

## Section 6: Worker Pool Design

**Q20. How do you design a worker pool for concurrent job execution?**
A: Workers pull jobs from the work queue and execute handlers concurrently:

```
Worker Node
├── Concurrency: 10 (10 simultaneous job slots)
├── Pull loop: BLPOP work_queue TIMEOUT 5
├── Per-slot:
│   ├── Acquire lock (Redis SET NX)
│   ├── Update job status → 'running'
│   ├── Execute handler (with timeout)
│   ├── Heartbeat loop (every 15s)
│   ├── On success: status → 'completed', release lock
│   └── On failure: status → 'failed', schedule retry or dead-letter
```

Key design decisions:
- **Concurrency per worker**: Set based on job type. CPU-bound jobs: concurrency ≈ number of CPU cores. I/O-bound jobs (DB queries, HTTP calls): concurrency can be 10–50× cores, since most time is spent waiting. Use separate worker pools for CPU-bound vs I/O-bound jobs.
- **Job timeout enforcement**: Each job slot has a max execution time. If the handler exceeds `timeout_ms`, the slot cancels the job (Promise.race with a timeout), marks it as failed, and makes the slot available. Without timeout enforcement, a hung handler occupies a slot indefinitely.
- **Graceful shutdown**: On SIGTERM, stop accepting new jobs, let in-flight jobs finish (up to a grace period), then release locks and exit. Never kill a worker mid-job without giving it a chance to release its lock and update job status.

**Q21. How do you implement job priority within the worker pool?**
A: Priority determines which job a worker picks next when multiple jobs are available:

- **Multiple queues, weighted polling**: Workers poll from CRITICAL, HIGH, NORMAL, and LOW queues in weighted order. A simple implementation: for every 1 job from LOW, poll 2 from NORMAL, 4 from HIGH, 8 from CRITICAL — using a round-robin with weights.
- **Redis Sorted Set with priority score**: `ZADD work_queue {score} {job_id}` where `score = (MAX_PRIORITY - priority_tier) * 1e13 + epoch_ms`. Workers always `ZPOPMIN` — they get the highest-priority, oldest job. Single queue, simple, naturally fair.
- **Dedicated worker pools per priority tier**: CRITICAL jobs go to a dedicated pool of workers that process nothing else. LOW-priority batch workers share a separate pool. Isolation ensures CRITICAL jobs are never delayed by a backlog of LOW-priority work.

For fintech: dedicated pools per tier is the safest choice — a batch reconciliation job backlog can never block a fraud check execution.

**Q22. How do you handle job handler timeouts without resource leaks?**
A: A job handler that exceeds its timeout must be interrupted cleanly:
```javascript
async function executeWithTimeout(handler, payload, timeoutMs) {
  const timeoutPromise = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Job timeout')), timeoutMs)
  );
  try {
    await Promise.race([handler(payload), timeoutPromise]);
  } catch (err) {
    // Cancel any ongoing work (close DB connections, abort HTTP calls)
    // Update job status to 'failed' with error = 'timeout'
    throw err;
  }
}
```
Beyond the Promise race: ensure the handler holds AbortController references for any ongoing HTTP calls (`fetch(url, { signal: controller.signal })`), and that DB connections are returned to the pool (not leaked) even when the handler is aborted. A timed-out job should not leave dangling connections or uncommitted transactions.

## Section 7: Retry & Dead Letter

**Q23. How do you implement exponential backoff for retries?**
A: On failure, compute the next run time using exponential backoff with jitter:
```javascript
function nextRetryAt(attemptCount, baseDelayMs = 30_000, maxDelayMs = 3_600_000) {
  const exponential = baseDelayMs * Math.pow(2, attemptCount - 1);
  const capped = Math.min(exponential, maxDelayMs);
  const jitter = Math.random() * capped * 0.2;  // ±20% jitter
  return new Date(Date.now() + capped + jitter);
}

// Attempt 1 → 30s, Attempt 2 → 60s, Attempt 3 → 120s,
// Attempt 4 → 240s, Attempt 5 → 480s ... capped at 1 hour
```
Jitter is essential — without it, all retrying jobs hit the DB or downstream API simultaneously after a mass failure event (e.g., a provider outage at T+0 causes 10,000 jobs to fail, all retry at T+30s, all fail again, all retry at T+60s — a retry storm). Jitter spreads the retries across the window, smoothing the load.

**Q24. Which errors should trigger a retry, and which should dead-letter immediately?**
A:

| Error Type | Action | Rationale |
|---|---|---|
| DB connection timeout | Retry | Transient infrastructure issue |
| HTTP 503 / 504 from provider | Retry with backoff | Provider temporarily unavailable |
| HTTP 429 (rate limited) | Retry after `Retry-After` | Honour provider's backoff signal |
| HTTP 400 (bad request) | Dead-letter | Payload is invalid — retrying won't help |
| HTTP 401 / 403 | Dead-letter + alert | Auth failure — config issue |
| Unhandled exception / assertion error | Dead-letter | Code bug — retrying reproduces the bug |
| Job timeout | Retry (if idempotent) | May have been a transient slowdown |
| Duplicate key DB error | Dead-letter | Job already produced its output; idempotency key violation |
| Stale payload (entity deleted) | Dead-letter | Entity no longer exists — job is moot |

The key question: "would running this job again with the same payload on the same system state produce a different outcome?" If yes → retry. If no → dead-letter.

**Q25. How do you operationalise the dead letter queue?**
A: A dead letter entry represents a job that needed to run but couldn't. Treat it seriously:
- **Alert on DLQ growth**: PagerDuty if DLQ grows by more than 10 entries per minute — signals a systemic failure.
- **Dashboard by failure reason**: Group dead letters by `error.code` and `job_definition_id` — a spike in one job type with one error code points directly to the root cause (e.g., all `generate_settlement_report` jobs failing with `DB_TIMEOUT` → DB overloaded).
- **Replay tooling**: An operator-triggered replay re-enqueues dead letter jobs back to `pending`. Replay must re-run idempotency checks — a job that dead-lettered but partially completed must not duplicate its side effects.
- **Expiry policy**: Dead letter records are retained for 30–90 days for audit, then archived. Financial job dead letters may require indefinite retention for regulatory compliance.
- **Manual intervention hooks**: For jobs that require human data correction before replay (e.g., an invalid account number in the payload), expose an API to update the payload before re-enqueuing.

## Section 8: Observability & Operations

**Q26. What metrics does a job scheduler expose?**
A: By component:

**Job Store**:
- `jobs_enqueued_total{definition, priority}` — volume by job type.
- `jobs_completed_total{definition}` and `jobs_failed_total{definition, error_code}`.
- `jobs_pending_count{definition, priority}` — current backlog per job type.
- `job_execution_duration_ms{definition, p50/p95/p99}` — how long jobs are taking.

**Scheduler/Dispatcher**:
- `scheduler_poll_duration_ms` — how long each DB poll takes; alert if > 1 second.
- `scheduler_claim_failures_total` — lock acquisition failures (contention signal).
- `cron_fire_delay_ms{schedule}` — how late each cron job fired vs its scheduled time.

**Worker Pool**:
- `worker_concurrency_utilisation{worker_id}` — what fraction of concurrency slots are in use; alert if sustained at 100% (need more workers).
- `worker_job_timeout_total{definition}` — jobs timing out; signals handler performance issues.
- `lock_acquisition_duration_ms` — how long distributed lock acquisition takes.

**Dead Letter**:
- `dlq_depth{definition}` — dead letter count per job type. Alert aggressively.
- `dlq_growth_rate` — entries per minute; the most important operational health signal.

**Q27. How do you trace a job execution end-to-end?**
A: Thread a `job_id` and `trace_id` through every stage:
- **Enqueue**: The producer includes a `correlation_id` (e.g., `payment_id`). The Job Store creates a `job_id` linked to `correlation_id`. Both are logged at enqueue.
- **Dispatch**: The Scheduler logs `dispatching job_id={} trace_id={}` when pushing to the work queue.
- **Execution**: The worker sets the `trace_id` as the active trace context before calling the handler — all DB queries, HTTP calls, and log lines emitted by the handler carry the same `trace_id`. This links the job execution spans into the distributed trace.
- **Completion/failure**: Final status update logged with `job_id`, `duration_ms`, `attempt_count`, and `error` (if failed).

With this in place, answering "what happened to the settlement report job that ran at 2am?" takes 30 seconds: query the Job Store by `definition_id + run_at`, get the `job_id`, follow `trace_id` into Grafana/Tempo for the full distributed trace.

## Section 9: Scenario / System Design Questions

**Q28. "Design the job scheduler for a NACH debit retry system. Failed debits must be retried at 6am, 12pm, and 6pm for 3 days."**
A: A finite retry schedule with specific fire times — not generic exponential backoff:

1. **Job definition**: `nach_debit_retry` with a custom retry schedule: `[6am, 12pm, 6pm]` for up to 3 days (9 total retry attempts), encoded as a `retry_schedule` array in the job definition.
2. **On initial debit failure**: The NACH processor publishes `nach.debit.failed`. An event consumer creates a `nach_debit_retry` job with `run_at = next_fire_time(now, retry_schedule)` and payload `{payment_id, attempt: 1}`.
3. **On retry execution**: The handler re-attempts the NACH debit. On success: mark job `completed`, publish `nach.debit.succeeded`. On failure: if `attempt < 9`, create a new job with `run_at = next_fire_time(now, retry_schedule)` and `attempt + 1`. If `attempt == 9`: dead-letter, publish `nach.debit.exhausted`, trigger manual follow-up.
4. **Idempotency key**: `nach_debit_retry:{payment_id}:{attempt}` — ensures the same retry attempt never runs twice even if the job is dispatched more than once.
5. **Locking**: Acquire a Redis lock `lock:nach_debit:{payment_id}` before executing — prevents concurrent retry execution for the same payment if the Scheduler dispatches a duplicate.
6. **Timezone**: Compute `6am / 12pm / 6pm` in `Asia/Kolkata`, not UTC — NACH processing follows IST business hours.

**Q29. "Your cron job that generates daily settlement reports at 2am is running for 45 minutes and overlapping with the next day's run. How do you fix it?"**
A: Two independent problems — the overlap symptom and the root performance problem:

**Immediate fix — prevent overlap**:
Add an `overlap guard` (Q10 pattern): the cron trigger checks for an already-running instance before firing. If `status IN ('pending', 'running')` for this job definition, skip the fire. Add a metric: `cron_overlap_skipped_total{schedule=settlement_report}` — alert if this fires more than once per week (chronic overlap signals a deeper problem).

**Short-term fix — increase schedule interval**:
If the report takes 45 minutes, schedule it at 1am (giving a 25-minute buffer before the next day's business activity). Buys time while the root cause is fixed.

**Root cause investigation using observability**:
Pull the distributed trace for the last several report runs (`job_definition=settlement_report, run_at~2am`). The trace waterfall shows exactly which DB query or processing step consumes the most time. Common causes:
- **Full table scan on large table**: Add an index on `created_at` or `status` to the transactions table used by the report query.
- **N+1 queries**: The report loops over 10,000 accounts and makes one DB query per account — replace with a single bulk query.
- **No pagination / chunking**: The report loads all rows into memory at once — process in batches of 1,000.

**Long-term fix — make the report incremental**:
Instead of recomputing the full settlement from scratch each night, maintain a running aggregate updated throughout the day (via event-driven updates as transactions close). The 2am job reads the pre-computed aggregate and formats the report — execution time drops from 45 minutes to under 1 minute.

**Q30. "Design a job scheduler that runs 1 million nightly batch jobs — one per user account — starting at midnight. The jobs must all complete by 6am."**
A: A 6-hour window for 1M jobs = max 1M / 21,600 seconds ≈ 46 jobs/second minimum throughput. In practice, target 200–500 jobs/second with headroom for retries.

**Enqueue strategy**:
Don't enqueue 1M jobs at midnight simultaneously — the Job Store insert would spike the DB. Instead, use a **sweeper job** that runs at 11:45pm and enqueues in batches:
```
for each batch of 10,000 user_ids:
  INSERT INTO jobs (user_id, definition_id, run_at, idempotency_key)
  SELECT user_id, 'nightly_account_job', NOW(), 'nightly:{user_id}:{date}'
  FROM accounts WHERE active = true
  ORDER BY user_id
  LIMIT 10000 OFFSET $cursor
  ON CONFLICT (idempotency_key) DO NOTHING;
  sleep 100ms;  -- rate-limit the inserts
```
The idempotency key prevents duplicate jobs if the sweeper runs twice (e.g., after a crash and restart).

**Worker capacity planning**:
At 500 jobs/second with each job taking 2 seconds average → need 500 × 2 = 1,000 concurrent worker slots. At 10 concurrency per node → 100 worker nodes. Scale worker nodes via auto-scaling group targeting queue depth.

**Priority segregation**:
All 1M nightly jobs run at `LOW` priority. Any real-time job (OTP, fraud check) that arrives during the batch window runs at `CRITICAL` priority on a dedicated worker pool — the nightly batch never affects real-time job latency.

**Progress tracking**:
A dashboard shows `jobs_completed / jobs_total` per night. Alert if completion rate at 4am is below 60% (projected to miss the 6am deadline) — trigger an investigation or add worker capacity before the deadline.

**Q31. "A Redis node storing distributed locks crashes at 3am during a batch job run. What happens and how do you recover?"**
A: Redis lock crash means all currently-held locks are gone. Two failure modes:

**Mode 1 — Jobs complete without releasing lock (lock was in-memory, job status is in Postgres)**:
Jobs may complete successfully but can't release their lock (already gone). On next Scheduler sweep, these jobs are `completed` in Postgres — no problem, the stale job detector only targets `running` jobs with expired heartbeats.

**Mode 2 — Jobs in-flight lose their lock mid-execution**:
The job is still running on the worker, but the lock is gone. Another worker may acquire the same job from the Work Queue and start executing it concurrently. This is the double-execution risk. Mitigations:
- **Fencing via DB status**: The second worker does `UPDATE jobs SET status='running', worker_id=$1 WHERE id=$2 AND status='pending'` — since the first worker already set it to `running`, the second worker gets 0 rows and aborts cleanly.
- **Job handler idempotency**: All batch job handlers must be idempotent — running the same job twice produces the same result, not duplicate DB rows or double charges.
- **Redis HA**: Avoid single-node Redis for lock storage. Use Redis Sentinel (automatic failover) or Redis Cluster. AOF persistence (`appendfsync always`) ensures lock state survives restarts in most cases.

Recovery procedure: monitor `lock_acquisition_failures_total` spike (jobs that couldn't re-acquire locks on the new Redis node) and `stale_jobs_requeued_total` (the stale detector re-queuing abandoned jobs). Both should self-correct within 60–120 seconds as the stale detector runs its sweep.

## Quick Comparison Table

| Concern | Approach | Trade-off |
|---|---|---|
| Cron deduplication | `UPDATE WHERE next_fire_at <= NOW()` atomic claim | No leader election; DB contention at high cron volume |
| Delayed job store | Postgres (durable) + Redis Sorted Set (fast) | Redis sync adds complexity; Redis crash = re-sync from Postgres |
| Distributed lock | Redis `SET NX PX` + lock heartbeat | Redis is a critical dependency; use Sentinel/Cluster for HA |
| Priority | Dedicated worker pool per priority tier | More infrastructure; isolates real-time from batch completely |
| Retry policy | Exponential backoff + jitter + per-error classification | Dead-letter logic requires careful error taxonomy |
| Worker crash recovery | Heartbeat + stale job detector sweep | Recovery delay = lock TTL + sweep interval |
| 1M nightly jobs | Batched sweeper enqueue + auto-scaled worker pool | Sweeper itself is a job that must be monitored |
| Job cancellation | Status flag + Redis pub/sub for in-flight cancel | In-flight cancellation is best-effort, not guaranteed |
