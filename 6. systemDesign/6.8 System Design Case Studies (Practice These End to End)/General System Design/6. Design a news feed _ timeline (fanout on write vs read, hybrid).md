# Design a News Feed / Timeline (Fanout on Write vs Read, Hybrid) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the core engineering problem a news feed system must solve?**
A: A news feed aggregates content from N sources (accounts a user follows) and presents it as a ranked, paginated stream to each user. The fundamental tension: **writes are cheap, reads are expensive** in the naive model, or vice versa depending on the approach. When User A posts, their content must eventually appear in the feeds of potentially millions of followers. When a user opens their feed, they expect a fast, relevant, pre-assembled response — not a 5-second query across thousands of accounts. Every feed design decision is a trade-off between write-time cost (fanout on write), read-time cost (fanout on read), and storage cost (maintaining per-user feed materialized views).

**Q2. What are the three core operations a feed system must support and what are their latency requirements?**
A:
- **Post (write)**: a user creates content. Latency requirement: the write itself must be fast (< 200ms for the user-facing ack), but propagation to all followers' feeds can be asynchronous — eventual consistency is acceptable. Most users tolerate a 1–5 second delay before a post appears in followers' feeds.
- **Feed read**: a user opens their feed and expects a response in < 300ms. This is the latency-critical operation — a slow feed loads destroys engagement. This operation must read pre-assembled or cheaply-assembable data.
- **Follow/unfollow**: a user follows or unfollows an account. The effect on the feed (adding or removing that account's past and future posts) can be eventually consistent. Immediate consistency is a nice-to-have, not a hard requirement for most products.

**Q3. What data does a single feed entry typically contain, and what is the implication for storage?**
A: A feed entry is not the post itself — it is a reference to a post plus metadata needed for ranking and display:
- `post_id` — reference to the actual post content stored elsewhere.
- `author_id` — who created the post.
- `score` or `timestamp` — for ordering within the feed.
- `feed_owner_id` — whose feed this entry belongs to (in a push model where entries are stored per-user).

The post content (text, media URLs, like count, comment count) is stored once in a separate posts service/table. The feed stores only the reference. This separation means: (1) post edits are reflected everywhere without touching feed storage, (2) feed storage is small (just IDs + scores), (3) the feed read must join with the post content service to hydrate entries — typically done via a bulk fetch from a post cache.

**Q4. What is the "follow graph" and why is its shape the central variable in feed system design?**
A: The follow graph is the directed graph where an edge `A → B` means "A follows B." The two critical properties of this graph that determine your design:
- **Fan-in** (followers per account): a celebrity with 50M followers means a single post must be delivered to 50M feed entries. This is the write amplification problem.
- **Fan-out** (accounts followed per user): a power user following 5000 accounts means a feed read must aggregate content from 5000 sources. This is the read amplification problem.

Real social networks exhibit a highly skewed (power-law) follower distribution — a tiny fraction of accounts have enormous fan-in, and a small fraction of users have enormous fan-out. This skew is why simple approaches fail at scale and why hybrid strategies exist.

**Q5. What is eventual consistency in the feed context, and what are the user-visible symptoms?**
A: In a feed system, eventual consistency means a post may not appear in all followers' feeds at exactly the same time — there is a propagation delay. User-visible symptoms:
- User A posts; their follower User B sees the post 3 seconds later (acceptable).
- User A and User B are both looking at User C's post simultaneously; A sees 1,000 likes, B sees 998 likes (acceptable).
- User A deletes a post; it briefly still appears in follower feeds before propagation catches up (less acceptable — needs bounded window).
- User A's feed shows a post from User B, but User A unfollowed User B 2 minutes ago (poor experience — needs proactive cleanup).

Most feed products accept 1–30 seconds of propagation delay on writes, but work hard to minimize "ghost" content from unfollowed/blocked accounts.

## Section 2: Fanout on Write (Push Model)

**Q6. What is fanout on write and how does it work mechanically?**
A: When a user creates a post, the system immediately identifies all of their followers and inserts a reference to the post into each follower's pre-materialized feed. By the time any follower opens their feed, the entry is already there — the read is a simple sequential scan of a pre-sorted list, not a query across the graph.

Mechanism:
1. User writes post → Post Service stores post, returns `post_id`.
2. Post Service enqueues a fanout job to a message queue (Kafka, SQS).
3. Fanout workers consume the job, look up the author's follower list, and for each follower write a feed entry: `ZADD feed:{follower_id} {timestamp_score} {post_id}` in Redis.
4. Feed reads: `ZREVRANGE feed:{user_id} 0 49` — returns the 50 most recent post IDs, then bulk-fetch post content.

**Q7. What are the advantages of fanout on write?**
A:
- **Fast reads**: feed reads are O(1) sorted set lookups — no graph traversal, no per-read aggregation. Latency is predictable and low regardless of how many accounts the user follows.
- **Pre-sorted**: the feed is sorted at write time (by timestamp or pre-computed rank score). The read just returns a slice.
- **Isolation**: each user's feed is independent — a slow follower list doesn't slow down the read for another user.
- **Cache-friendly**: per-user feed sorted sets fit naturally in Redis; the entire feed is a single key lookup.

**Q8. What are the disadvantages of fanout on write?**
A:
- **Write amplification**: posting once fans out to N writes, where N is follower count. A user with 10M followers causes 10M Redis writes per post — potentially millions of operations per second across the cluster.
- **Storage amplification**: each post is stored N times (once per follower's feed sorted set). A popular account's posts consume enormous Redis memory.
- **Celebrity problem**: accounts with very high follower counts make fanout on write impractical — a single post by a celebrity generates a fanout storm that can overwhelm the write pipeline.
- **Wasted writes**: if a follower hasn't opened the app in 6 months, writing to their feed consumes resources with zero benefit. Fanout on write does work for inactive users.
- **Stale state on unfollow**: when a user unfollows an account, their feed may contain that account's posts that were already fanned out. Cleanup requires either a retroactive feed scan or accepting brief staleness.

**Q9. What is the "celebrity problem" (also called the "hot user" or "thundering herd" problem) in fanout on write?**
A: A celebrity account (e.g., 50M followers) posts once. The fanout job must write to 50M feed sorted sets. Even at 50,000 Redis writes/second, this takes 1000 seconds (~17 minutes) to complete — meaning followers at the back of the queue see the post nearly 20 minutes late. During that 17 minutes, the fanout workers are saturated processing this single post, delaying fanout for all other users' posts.

The celebrity problem is the single most important design constraint for large-scale feed systems. Every viable solution (hybrid model, pull for high-follower accounts, async batching, priority queues) exists primarily to address this failure mode.

**Q10. How do fanout workers handle partial failures mid-fanout?**
A: A fanout job for a post with 1M followers might be processed across multiple worker instances over several minutes. If a worker crashes mid-way:
- **Idempotent writes**: Redis `ZADD` is idempotent — adding the same `(score, member)` to a sorted set twice has no effect. Workers can safely retry any batch of writes without duplication.
- **Checkpointing**: track the cursor (last processed follower ID) in the job payload. On retry, resume from the checkpoint rather than restarting from follower 0.
- **At-least-once delivery**: accept that some followers may receive the fanout slightly out of order (a follower at position 500,000 gets the entry before a follower at position 499,999 if batches are processed in parallel). For chronological feeds this is fine; for ranked feeds, the score is computed at write time so the order within the sorted set is correct regardless of insertion order.

## Section 3: Fanout on Read (Pull Model)

**Q11. What is fanout on read and how does it work mechanically?**
A: When a user requests their feed, the system dynamically computes it by fetching recent posts from all accounts the user follows, merging them, sorting by recency or rank, and returning a page. No per-user feed is pre-materialized — posts are stored once, and the feed is assembled at read time.

Mechanism:
1. User requests feed → Feed Service fetches the user's following list (e.g., 500 accounts they follow).
2. For each followed account, fetch their recent posts: `ZREVRANGE posts:{author_id} 0 99` from a per-author post list in Redis or a DB index.
3. Merge all fetched posts into a unified sorted list (merge N sorted lists — O(N log N) where N is the total post count fetched).
4. Apply ranking, filter deleted/blocked content, return top K entries.

**Q12. What are the advantages of fanout on read?**
A:
- **Write simplicity**: posting requires one write — store the post and append to the author's own post list. No follower enumeration, no fanout queue, no fanout workers.
- **No storage amplification**: posts are stored once regardless of follower count. A celebrity's posts occupy no more space than a regular user's.
- **No wasted work for inactive users**: if nobody reads a feed, no computation is done.
- **Immediate consistency on follow/unfollow**: following a new account immediately includes their posts in your next feed read; unfollowing immediately excludes them. No cleanup of materialized feeds required.
- **Always fresh**: the feed reflects the current state of posts, follow relationships, and ranking signals at read time.

**Q13. What are the disadvantages of fanout on read?**
A:
- **Read amplification**: reading a feed for a user following 2000 accounts requires fetching data from 2000 sources — 2000 cache lookups or DB queries — and merging the results. At high traffic, this is expensive.
- **Slow reads at scale**: the merge of N sorted lists for large N is compute-intensive. A user following 5000 active accounts each with 100 posts fetched = 500,000 entries to merge per feed load. Even with caching, this is slow.
- **Hot author caches**: popular authors' post lists are accessed on every feed read for every one of their followers. The author's post cache becomes a hotspot proportional to their follower count — the opposite scaling problem from fanout on write.
- **Hard to rank**: real-time ranking at read time (ML scores, engagement signals) requires fetching more data than just post IDs — making the read even more expensive.
- **Difficult to cache**: the merged feed is unique per user and changes constantly (new posts from any followed account invalidate it). Cache hit rates for assembled feeds are low.

**Q14. What is "merge of N sorted lists" and why is it the computational bottleneck of fanout on read?**
A: Given N sorted lists (one per followed account, each containing their recent posts sorted by time), producing a single merged sorted list requires: fetch all lists (N network calls, parallelizable), then merge. A k-way merge using a min-heap runs in O(total_posts × log N) time. For a user following 1000 accounts, each with 20 recent posts fetched: 20,000 entries, merged in O(20,000 × log 1000) ≈ 200,000 operations per feed load, per user, per request. At 100,000 concurrent feed reads per second, this is 20 billion operations/second — clearly not scalable without significant optimization.

**Q15. What caching strategies reduce the cost of fanout on read?**
A:
- **Per-author post cache**: cache each author's recent post list in Redis (sorted set). Most feed reads hit Redis rather than the DB. Hot authors benefit disproportionately — their cache entry is extremely warm.
- **Assembled feed cache**: after computing a user's feed, cache the result (list of post IDs) in Redis for a short TTL (e.g., 30–60 seconds). Subsequent reads within the TTL are O(1). Trade-off: the feed may miss posts that arrived during the TTL window.
- **Partial merge caching**: cache the merged feed for a user, but invalidate and recompute when a new post arrives from any followed account. Requires tracking which users are affected by each new post — effectively a partial fanout on write, pulling the models closer together.

## Section 4: The Hybrid Model

**Q16. What is the hybrid fanout model and what problem does it solve?**
A: The hybrid model applies fanout on write for most users (those with modest follower counts) and fanout on read for a specific subset of accounts (celebrities with very high follower counts), then merges the two at read time. This addresses the celebrity problem directly: celebrity posts are not pre-distributed to millions of feeds, avoiding the fanout storm. Regular users' posts are pre-distributed as normal, keeping reads fast for the vast majority of content.

**Q17. How is the "celebrity threshold" determined and applied?**
A: A configurable follower count threshold (e.g., 1 million followers) designates an account as a "celebrity" for fanout purposes. The threshold is a product and infrastructure decision — not a social judgment. Implementation:
- Account metadata includes a `fanout_strategy` flag: `PUSH` (≤ threshold) or `PULL` (> threshold), updated whenever follower count crosses the boundary.
- On post creation: if `PUSH`, enqueue a normal fanout job. If `PULL`, store the post only in the celebrity's own post list (no follower fanout).
- On feed read: fetch the pre-built feed from Redis (populated by PUSH fanout for followed regular users) + for each followed celebrity, fetch their recent posts from their own post list and merge them in.

**Q18. Walk through the complete hybrid read path for a feed load.**
A:
1. User requests their feed.
2. Feed Service fetches the user's following list, partitioned into `push_followees` (regular users, pre-fanned-out) and `pull_followees` (celebrities, not pre-fanned-out).
3. **Push portion**: read the user's pre-materialized feed from Redis: `ZREVRANGE feed:{user_id} 0 199` — fast, pre-sorted.
4. **Pull portion**: for each celebrity in `pull_followees`, fetch their recent posts: `ZREVRANGE posts:{celebrity_id} 0 49` — N parallel Redis lookups.
5. **Merge**: merge the push feed entries with the pulled celebrity posts into a single ranked list (k-way merge, but N is small since most users follow few celebrities).
6. **Hydrate**: bulk-fetch post content for the top K post IDs from the post cache.
7. Return ranked, hydrated feed.

The merge in step 5 is cheap because `|pull_followees|` is small (most users follow 0–5 celebrities, not thousands) — the expensive merge from pure fanout on read is avoided.

**Q19. How do you handle a user who follows many celebrities (e.g., 100 celebrity accounts)?**
A: The pull portion of step 5 requires fetching from 100 celebrity post lists and merging them. This is expensive but bounded — 100 is far less than the 2000+ followed accounts a "power user" might have in a pure pull model, most of which would be regular accounts. In practice: cache the merged celebrity portion per user (short TTL, e.g., 5 minutes), update it in the background when a new celebrity post arrives. The pre-built push feed changes more frequently; the celebrity portion changes less often (celebrities post less frequently than the aggregate of 2000 regular followees).

**Q20. How does the hybrid model handle the transition when an account crosses the celebrity threshold?**
A: This transition must be handled carefully:
- **Regular → Celebrity (gaining followers)**: when the account crosses the threshold, set `fanout_strategy = PULL`. Future posts use pull. Past posts already distributed to millions of feeds stay there (no cleanup needed — they expire naturally via feed TTL). From this point, new followers don't receive pre-fanned-out posts.
- **Celebrity → Regular (losing followers, rare)**: when account drops below threshold, set `fanout_strategy = PUSH`. Future posts fan out to all current followers. No retroactive fanout for past posts.
- **Edge case**: a viral post causes a regular account to gain 2M followers in an hour. Their posts were pushed to 2M feeds early in the viral event. After crossing the threshold, subsequent posts switch to pull. The in-progress fanout jobs for pre-threshold posts should complete (they're already partially distributed).

**Q21. What is "active user filtering" in fanout on write and how does it reduce wasted work?**
A: A significant fraction of followers are inactive (haven't opened the app in days, weeks, or months). Writing to their feed sorted sets consumes Redis memory and write throughput with no benefit — the entry will expire before they return. Active user filtering: before fanning out, check each follower's `last_active_at` timestamp. Skip fanout for followers inactive for more than a threshold (e.g., 30 days). Store this threshold in a separate Redis set or Bloom filter for fast membership check.

When an inactive user returns: their feed is stale (missing content from their fanout skip window). On login, trigger a retroactive pull: fetch recent posts from all their followees to fill in the gap, then resume normal fanout. This is the "wake-up feed" problem — handled as a one-time catch-up read that populates their feed before the first load.

## Section 5: Storage Layer Design

**Q22. What data stores are used in a feed system and what does each hold?**
A:
- **Post store (Cassandra or MySQL)**: the source of truth for post content — text, media references, author, timestamp, engagement counts. Append-heavy, high-volume. Cassandra's wide-row model fits naturally: partition by `author_id`, cluster by `post_id` descending for efficient "recent posts by author" queries.
- **Feed store (Redis — sorted sets)**: per-user materialized feed. Key: `feed:{user_id}`, sorted set where member = `post_id` and score = timestamp (or rank score). Supports O(log N) insert and O(log N + K) range read. Bounded per user (trim to last 1000 entries via `ZREMRANGEBYRANK`).
- **Author post list (Redis — sorted sets)**: per-author recent post index. Key: `posts:{author_id}`, sorted set of recent post IDs. Used by fanout on read and hybrid pull path. TTL-based or bounded size.
- **Social graph store (specialized graph DB or Cassandra)**: the follow/follower relationship. Cassandra is common: `following:{user_id}` → list of followed IDs; `followers:{user_id}` → list of follower IDs. Partitioned by user.
- **Post content cache (Redis)**: cached post objects (serialized JSON) keyed by `post:{post_id}`. Feed reads hydrate post IDs here before hitting the post DB.

**Q23. Why is Redis sorted set the canonical data structure for the feed?**
A: A feed has three required operations: insert a new entry (at write time or on fanout), read the top K entries by score (feed load), and range-delete old entries (to bound feed size). Redis sorted set supports all three efficiently:
- `ZADD feed:{uid} {score} {post_id}` — O(log N) insert.
- `ZREVRANGEBYSCORE` / `ZREVRANGE` — O(log N + K) range read.
- `ZREMRANGEBYRANK feed:{uid} 0 -(MAX_SIZE+1)` — O(log N + M) trim to bounded size.
- `ZCARD` — O(1) count.

The score encodes the sort key — a Unix timestamp for chronological feeds, or a pre-computed ML rank score for algorithmic feeds. The sorted set maintains order automatically; no re-sorting on read.

**Q24. How do you bound Redis memory usage for feed storage?**
A: Several complementary strategies:
- **Feed size cap**: after each fanout write, trim the sorted set to the last N entries: `ZREMRANGEBYRANK feed:{uid} 0 -(N+1)` where N = 1000. Users only see the most recent 1000 feed items; older content is fetched via a "load more" path that falls through to the post store directly.
- **Feed TTL**: set an expiry on feed keys for inactive users. If a user hasn't read their feed in 30 days, allow the key to expire; rebuild on next login.
- **Score-based eviction**: remove entries with scores (timestamps) older than a fixed window (e.g., 7 days): `ZREMRANGEBYSCORE feed:{uid} 0 {7_days_ago_timestamp}`. Older content is archived to cheaper storage (Cassandra) and fetched on scroll.
- **Tiered storage**: hot feed (last 24 hours) in Redis; warm feed (last 7 days) in Redis with lower memory priority; cold feed (beyond 7 days) in Cassandra, fetched on deep scroll.

**Q25. How do you paginate a feed and why is cursor-based pagination preferred over offset?**
A: Offset pagination (`ZREVRANGE feed:{uid} 0 49` for page 1, `50 99` for page 2) fails for feeds: new posts inserted at the top shift all existing entries down by one position. A user scrolling through offset pages 1, 2, 3 may see duplicates (an entry that was at offset 49 when page 1 was fetched is now at offset 50 on the next fetch) or skip entries.

Cursor-based pagination uses the score (timestamp) of the last seen entry as a cursor: `ZREVRANGEBYSCORE feed:{uid} ({last_score}) -inf LIMIT 0 50`. This fetches up to 50 entries with score strictly less than the cursor — immune to new insertions at the top, since those have higher scores and don't affect the cursor's position. Always design feed pagination with score-based cursors, not offsets.

## Section 6: Feed Ranking & Content Filtering

**Q26. What is the difference between chronological and algorithmic feed ranking?**
A:
- **Chronological**: entries are sorted by post timestamp only. Simple to implement (score = timestamp), perfectly consistent across clients, and predictable for users. Used by: early Twitter/Instagram, current Twitter's "latest tweets" mode. Disadvantage: a user following 1000 active accounts sees mostly recent noise from the most active posters, potentially missing content from accounts that post less frequently.
- **Algorithmic**: entries are scored by a model that considers engagement signals (likes, comments, shares, watch time), poster relationship strength (how often the user interacts with this author), content type affinity, recency, and diversity penalties. Requires ML infrastructure, feature stores, and offline training. The score must be computed at fanout time (embed in the sorted set score) or at read time (fetch candidate posts, score them, re-sort). Used by: Facebook News Feed, Instagram, TikTok For You Page.

**Q27. How do you embed an ML rank score in a fanout-on-write system?**
A: Two approaches:
- **Score at fanout time**: when inserting `ZADD feed:{uid} {score} {post_id}`, compute the rank score using features available at write time (author relationship strength, post content type, historical engagement rate). This means every follower gets a personalized score computed at insertion. At 10M followers, this is 10M score computations per post — expensive, must be fast (pre-computed feature lookup, lightweight model).
- **Score at read time**: store entries with timestamp score at fanout time. At feed load, fetch the top N candidates (e.g., 500), score them with the full ML model, re-sort, and return top K (e.g., 50). This allows using a richer model (more features, heavier compute) at the cost of fetching more candidates than needed and adding inference latency to the read path. Pre-warming a ranking cache (candidate set → ranked result) for active users bridges the gap.

**Q28. How do you handle deleted posts in a pre-materialized feed?**
A: Post deletion must propagate to all feed entries that reference the deleted post:
- **Hard delete from feed**: enumerate all followers who received the post in their feed (or all feed keys that might contain the post ID) and remove it. At scale, this is expensive — a post with 1M fanout requires removing 1M feed entries.
- **Soft delete with filter-on-read**: mark the post as deleted in the post store. Feed reads bulk-fetch post content and filter out any entries where the post is marked deleted. The feed entry remains in the sorted set but is omitted from the response. Simpler, eventually consistent — deleted posts stop appearing within one feed TTL.
- **Hybrid**: immediately hard-delete from active users' feeds via a fast path (Redis pipeline); rely on soft-delete filter for inactive users whose feeds aren't immediately refreshed.

**Q29. How do you handle follow/block/unfollow consistency in the feed?**
A: Each event requires different treatment:
- **New follow**: the user's pre-materialized feed doesn't automatically include the new followee's past posts (they weren't fanned out to this user). Options: (1) do nothing — new posts from the followee will appear going forward; (2) back-fill the feed with the followee's recent N posts (pull their post list and insert into the user's feed). Back-fill is a better UX but adds a one-time write burst on each follow action.
- **Unfollow**: future posts from the unfollowed account are no longer fanned out. Past posts already in the feed remain until they expire or the feed is rebuilt. For immediate cleanup: remove the unfollowed account's post IDs from the user's feed sorted set — requires knowing which post IDs belong to that author (store `{author_id}:{post_id}` as the member instead of just `{post_id}`, enabling `ZSCAN` + filter).
- **Block**: stricter than unfollow — must also remove the blocked user's posts from the blocker's feed (and vice versa), and filter them from all future reads. Filter-on-read is the practical choice; hard removal from sorted set is expensive.

## Section 7: Failure Modes & Anti-patterns

**Q30. What is "fanout storm" and how do you prevent it?**
A: A fanout storm occurs when a high-follower account posts and the resulting fanout job overwhelms the queue consumers, Redis write throughput, or network bandwidth — delaying fanout for all other users and potentially causing latency spikes across the entire feed system. Prevention:
- **Rate-limit fanout writes**: fanout workers write to Redis at a capped rate (e.g., 50,000 writes/second per worker). The celebrity post takes longer but doesn't starve other work.
- **Priority queues**: separate queues for regular-user posts (high priority, fast) and celebrity posts (low priority, rate-limited). Regular users' feeds are never delayed by celebrity fanout.
- **Pre-detect and route**: celebrity accounts are pre-classified (`fanout_strategy = PULL`); their posts never enter the fanout queue at all.
- **Backpressure on post creation**: if the fanout queue depth exceeds a threshold, apply backpressure at the write layer — accept the post but queue it for delayed fanout.

**Q31. What is "feed pollution" and how does it manifest?**
A: Feed pollution is when incorrect, irrelevant, or stale content appears in a user's feed:
- **Unfollowed account posts**: posts fanned out before an unfollow still appear until they age out or are cleaned up.
- **Deleted posts still appearing**: soft-delete propagation lag leaves deleted posts in feeds until they're filtered on the next read.
- **Blocked user content**: a blocked user's posts still in the sorted set appear if the block filter is not applied at read time.
- **Duplicate entries**: a fanout worker retries a batch and `ZADD`'s the same post twice — benign in Redis (sorted set deduplicates), but if using an append-only store like Cassandra, the entry appears twice.

The defense is a read-time filter layer that checks post validity, author block/unfollow status, and content availability before returning entries. This filter catches what write-time propagation misses.

**Q32. What is the "cold start problem" for new users and how is it handled?**
A: A new user with zero follows has an empty feed. Two approaches:
- **Onboarding follows**: prompt the user to follow seed accounts (popular creators, friends via contact import) during signup. Immediately back-fill their feed with those accounts' recent posts via a pull fanout.
- **Recommended feed**: for users with < N follows, substitute a curated or interest-based feed (algorithmically selected content from popular accounts in the user's declared interests) until their follow graph is rich enough for a personalized feed. Transition to the social feed as the follow count grows.

Both approaches require the feed system to support a "fallback feed source" that activates when the social feed is empty.

**Q33. What is "feed lag" and what are its acceptable bounds?**
A: Feed lag is the time between a post being created and it appearing in a specific follower's feed. Sources of lag:
- **Queue depth**: if the fanout queue is deep (high write volume), a new post waits behind existing jobs before being processed.
- **Worker throughput**: each fanout worker can process N follower writes per second; a 10M-follower celebrity post takes longer than a 100-follower regular user's post.
- **Redis write latency**: under heavy write load, Redis pipelining helps, but there's still a physical throughput ceiling.

Acceptable bounds vary by product: Twitter-class (< 5 seconds for most followers), Facebook-class (< 30 seconds), notification systems (< 1 second for push notification trigger, feed lag is secondary). Design the fanout pipeline capacity to meet your p95 lag SLA for the median post (not the celebrity case).

**Q34. What is "thundering herd on feed open" after a server restart?**
A: After a cache restart or deployment, all Redis feed keys are cold. When users open the app, every feed read is a miss — the system falls through to computing feeds from scratch via fanout on read, potentially hitting the social graph DB and post store simultaneously for millions of users. This is a feed-specific cold start amplification: the systems that a warm cache was protecting receive a sudden spike.

Mitigations: pre-warm the feed cache for top-N active users before directing traffic to a restarted instance; use a rolling restart strategy so only a fraction of the fleet is cold simultaneously; implement a graceful degradation path (serve the last N posts from the author's individual post lists directly, skipping the merged feed, until the feed cache warms).

## Section 8: Trade-offs & Decision-Making

**Q35. How do you decide whether to start with fanout on write or fanout on read?**
A: Key questions:
- **What is your follow graph shape?** If you expect a highly skewed follower distribution (celebrity accounts) from launch — media, creator, news platform — plan for the hybrid model from the start. If follower counts are bounded (enterprise social, internal tools) — fanout on write is simple and correct.
- **What is your read/write ratio?** If reads vastly outnumber writes (typical social network), favor fanout on write to shift cost to the write path. If writes are roughly equal to reads (collaborative tools), fanout on read or on-demand assembly may be more balanced.
- **What is your user activity pattern?** Many inactive users → fanout on write wastes resources. Mostly active daily users → fanout on write is efficient.
- **What is your early scale?** Most teams start with fanout on read (simpler) and add fanout on write as read latency becomes a bottleneck. Premature fanout on write at small scale adds operational complexity with no benefit.

**Q36. What is the cost of switching from one fanout model to another mid-product lifecycle?**
A: High — it requires migrating the storage schema, the write pipeline, and the read path simultaneously. Teams typically:
1. Run both models in parallel (shadow mode) to validate the new model produces equivalent feeds.
2. Gradually shift read traffic to the new model behind a feature flag, starting with a small user cohort.
3. Drain the old model's data structures (let feed sorted sets expire) while the new model warms up.

The transition can take months for a large-scale system. Planning the architecture to support the eventual model (even if starting simpler) reduces migration cost.

**Q37. How does a ranked (algorithmic) feed change the architecture compared to a chronological feed?**
A: Chronological feeds use timestamp as the score — a single integer, trivially computed at write time. Ranked feeds require:
- **Feature computation**: engagement rate, relationship strength, content affinity — features computed offline and stored in a feature store, looked up at fanout or read time.
- **Larger candidate sets**: ranking requires seeing more candidates than the final page size to rank and filter down. A page of 50 items may require fetching 500 candidates.
- **Re-ranking on read**: even with pre-computed scores, a full re-rank pass at read time is often needed to incorporate real-time signals (breaking trending topics, very recent viral engagement). This adds latency and compute to the read path.
- **Score freshness**: a pre-computed score from 10 minutes ago may be stale for a post that went viral since then. Ranked feeds need a mechanism to surface sudden high-engagement posts that weren't highly ranked at fanout time.

**Q38. How does the feed system interact with notifications (push notifications, email digests)?**
A: Notifications and feed are separate systems with overlapping triggers but different delivery requirements:
- **Feed**: eventually consistent, pull-based, tolerant of seconds of lag, content is browsed.
- **Push notification**: latency-sensitive (< 1 second for a reply or mention), delivered via APNs/FCM, must not be duplicated, and must be suppressed if the user is currently active.

The fanout pipeline that populates feeds also triggers notification events, but they flow through a separate notification service. The notification service checks notification preferences, applies suppression rules (do not disturb, mute settings, active session detection), deduplicates, and delivers via the push channel. Feed fanout and notification dispatch share the same triggering event (new post) but diverge immediately after — the notification path is fire-and-forget to the push provider; the feed path writes to the sorted set.

## Section 9: Scenario / System Design Style Questions

**Q39. "Design the write path for a post that fans out to 50,000 followers. Walk through every component."**
A:
1. **Client** submits post → **Post API** validates, stores post in Cassandra (`posts` table, partition key = `author_id`, clustering key = `post_id DESC`). Returns `post_id` to client within 200ms (async fanout, don't block the API response).
2. **Post API** publishes a `PostCreated` event to **Kafka** topic `post-events` with payload `{post_id, author_id, timestamp, content_type}`.
3. **Fanout Consumer** (Kafka consumer group) picks up the event. Checks `fanout_strategy` for `author_id` → `PUSH` (50,000 followers, below celebrity threshold).
4. **Fanout Consumer** fetches follower list from **social graph store** (Cassandra: `followers:{author_id}`) → 50,000 follower IDs. Partitions them into batches of 500.
5. **Fanout Consumer** filters inactive followers (Bloom filter lookup against `last_active_at`) — reduces to ~30,000 active followers.
6. For each batch of 500: pipeline 500 Redis `ZADD feed:{follower_id} {timestamp} {post_id}` commands → single pipeline call to Redis. Also pipeline `ZREMRANGEBYRANK feed:{follower_id} 0 -1001` to cap each feed at 1000 entries.
7. After all batches complete, publish a `FanoutComplete` event for observability and downstream triggers (notification service picks this up to dispatch push notifications).
8. Total time: with 30,000 active followers, 60 batches × ~5ms per Redis pipeline = ~300ms of Redis write time across parallel workers. End-to-end post-to-feed propagation: < 5 seconds for p95.

**Q40. "A post from a celebrity with 80 million followers needs to appear in followers' feeds within 30 seconds. Is that achievable with fanout on write? What would you do instead?"**
A: Not achievable with simple fanout on write. At 100,000 Redis writes/second (a well-provisioned Redis cluster), 80M writes takes 800 seconds. The hybrid model is the answer:
- The celebrity's account is flagged `fanout_strategy = PULL`. Their post is stored in their own post list only: `ZADD posts:{celebrity_id} {timestamp} {post_id}`.
- Followers' pre-built feeds contain entries from their regular followees only.
- At feed read time, the follower's app fetches their pre-built feed (push portion) + the celebrity's recent posts (pull portion) and merges them. The celebrity's post appears within the first feed open after the post — effectively immediate for active users.
- For followers who are currently active (have the app open): send a push notification or use a WebSocket/SSE channel to notify of a new post from the celebrity. The client pulls the celebrity's latest posts in real time.
- The 30-second requirement is met for all active users without any feed-level fanout.

**Q41. "A user follows 5,000 accounts. Their feed takes 8 seconds to load. How do you debug and fix it?"**
A: Systematic diagnosis:
1. **Identify the bottleneck**: add per-stage latency tracing. Is the delay in fetching the following list? Fetching the pre-built feed from Redis? The pull merge for celebrities? Content hydration?
2. **Most likely cause**: if using fanout on read, 5,000 parallel Redis fetches (one per followee) are probably the culprit — even at 0.5ms each, 5,000 serial calls = 2,500ms; parallel but Redis throughput-constrained.
3. **Fix 1 — Switch to fanout on write**: for this user, pre-materialize their feed. Their 5,000 followees' posts are fanned out to their sorted set. Feed read becomes a single `ZREVRANGE` — < 5ms.
4. **Fix 2 — Assembled feed caching**: after computing the feed once, cache the assembled result (list of post IDs) with a 60-second TTL. Most feed opens within a minute are served from cache.
5. **Fix 3 — Reduce candidate set**: instead of fetching from all 5,000 followees, maintain a "top followees" list (most interacted with, most recently followed) and fetch from the top 200. Supplement with a periodic background job that fetches from the remaining 4,800.
6. **Fix 4 — Cap per-followee fetch depth**: instead of fetching the last 100 posts from each of 5,000 accounts, fetch only the last 5 posts from each. Reduces total entries to merge from 500,000 to 25,000.

**Q42. "How do you design the feed for a platform where all content is public and anonymous (no accounts), like a trending news aggregator?"**
A: The follow-graph-based feed model doesn't apply — there are no user relationships to drive personalization. Replace with:
- **Global trending feed**: a single sorted set (`feed:global`) ranking all posts by a trending score (recency + engagement velocity). All users see the same feed — trivially cached, no per-user materialization.
- **Topic/interest feeds**: sorted sets per topic tag (`feed:topic:technology`, `feed:topic:sports`). Users subscribe to topics; their feed is the merge of their subscribed topic feeds at read time. Topic fanout (push a post to all subscribed topic feeds) is simpler than social fanout because topics have bounded, known members.
- **Personalized without identity**: use implicit signals (reading history stored in a cookie/device ID, geolocation, time of day) to rank a candidate set from the global feed. No per-user pre-materialization needed — ranking is applied at read time to a shared candidate pool.
- **CDN-cacheable**: since feeds are not user-specific (or minimally personalized), global and topic feeds can be cached at the CDN layer. Cache `GET /feed/topic/technology?page=1` for 30 seconds — serves millions of concurrent reads from edge without touching origin.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                    | Fanout on Write (Push)                                     | Fanout on Read (Pull)                                          | Hybrid                                                         |
|---                        |---                                                         |---                                                             |---                                                             |
| When feed is built        | At post creation (async)                                   | At feed load (sync)                                            | Both — push for regular users, pull for celebrities            |
| Write cost                | High — N writes per post (N = follower count)              | Low — 1 write per post                                         | Medium — N writes for regular, 1 for celebrities               |
| Read cost                 | Low — single sorted set range read                         | High — N reads + merge (N = following count)                   | Low for push content, small N merge for celebrity pull content |
| Storage cost              | High — N copies per post in Redis                          | Low — 1 copy per post                                          | Medium — copies for regular users only                         |
| Celebrity problem         | Severe — 50M writes per celebrity post                     | None at write time, but hot cache at read time                 | Solved — celebrities use pull, no write amplification          |
| Consistency on unfollow   | Poor — stale entries until TTL/cleanup                     | Perfect — unfollow takes effect on next read                   | Partial — push content stale, pull content immediate           |
| Inactive user cost        | Wasteful — fanning out to users who never read             | Free — no work done for inactive users                         | Mitigated — active-user filter skips inactive in push fanout   |
| Read latency              | < 5ms — single Redis lookup                                | High — proportional to following count                         | Low — single lookup + small merge                              |
| Ranking support           | Natural — pre-compute rank score at fanout time            | Flexible — rank at read time with fresh signals                | Mixed — pre-rank push content; re-rank at merge                |
| Best for                  | Moderate follower counts, active users, latency-sensitive  | Low follower counts, write-heavy, creator-side tools           | Large-scale social networks with skewed follower distribution  |

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Fanout on write               | Distribute post to all followers' pre-materialized feeds at write time; reads are fast, writes expensive    |
| Fanout on read                | Assemble feed dynamically at read time by pulling from all followees; writes are cheap, reads expensive      |
| Hybrid model                  | Push for regular users, pull for celebrities; merge both at read time                                        |
| Celebrity problem             | High-follower accounts make fanout on write impractical; single post → millions of write operations          |
| Follow graph                  | Directed graph of follow relationships; its fan-in/fan-out shape drives the entire architecture choice       |
| Feed materialization          | Pre-computing and storing a per-user feed so reads don't require graph traversal                             |
| Feed sorted set               | Redis sorted set keyed by user ID; members are post IDs, scores are timestamp or rank score                  |
| Active user filter            | Skip fanout for followers inactive beyond a threshold; rebuild their feed on next login                      |
| Wake-up feed                  | One-time pull fanout triggered on inactive user's first login to fill in the missed fanout window            |
| Cursor-based pagination       | Use last-seen score as the cursor for the next page; immune to new insertions shifting offset positions       |
| Feed size cap                 | Trim feed sorted set to last N entries after each insert; keeps Redis memory bounded                         |
| Soft delete filter            | Mark posts deleted in post store; filter them out at feed read time without touching feed sorted sets        |
| Feed lag                      | Delay between post creation and appearance in followers' feeds; driven by queue depth and worker throughput  |
| Fanout storm                  | Celebrity post overwhelms fanout workers and Redis write throughput, delaying all other users' feeds         |
| Back-fill on follow           | Insert a new followee's recent posts into the user's feed immediately on follow action                       |
| Candidate set                 | Larger set of post IDs fetched from the feed store; scored and trimmed to final page size for ranked feeds   |
| Engagement velocity           | Rate at which a post is gaining likes/comments; used to surface suddenly viral content in ranked feeds       |

**Tip for the interview:** Interviewers expect you to immediately name the celebrity/hot-user problem when discussing fanout on write — it's the canonical failure mode and the reason every large social network uses a hybrid. Don't just describe what each model does; explain *when each breaks* and *why the hybrid is not just a compromise but the correct answer at scale*. The strongest candidates also walk through the full write path end-to-end (post API → Kafka → fanout worker → Redis → notification), discuss active-user filtering as a memory optimization, and know that cursor-based pagination is non-negotiable for feeds. Bonus: explaining that the feed storage key uses `{author_id}:{post_id}` as the member (not just `post_id`) to enable efficient cleanup on unfollow.
