# Design a Payment Processing System — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a payment processing system?**
A: Core functional requirements:
- **Initiate a payment** — accept payment request from a client (amount, currency, source, destination, metadata).
- **Charge a payment method** — interact with a PSP (Payment Service Provider: Stripe, Braintree, Adyen) to debit the customer.
- **Track payment state** — model the lifecycle: `PENDING → PROCESSING → SUCCEEDED | FAILED | REFUNDED`.
- **Idempotent submission** — the same payment request submitted multiple times must only charge the customer once.
- **Refunds** — full or partial reversal of a completed charge.
- **Webhooks / event notification** — notify downstream services (order management, fulfillment, ledger) when payment state changes.
- **Reconciliation** — detect and resolve discrepancies between internal records and PSP statements.

**Q2. What are the non-functional requirements that make payments uniquely hard?**
A:
- **Exactly-once semantics** — a customer must never be double-charged; money movement must be idempotent end-to-end.
- **Consistency over availability** — in a conflict between CAP properties, payments must favor consistency. A payment that appears successful but wasn't is worse than a temporary unavailability.
- **Auditability** — every state transition, retry, and external call must be logged immutably with timestamps. Required for dispute resolution and regulatory compliance.
- **Durability** — committed payment records must survive any single node failure. No `fsync=off`, no eventual consistency on payment state.
- **Latency** — most PSP calls complete in 200–800ms; the system should add minimal overhead. P99 end-to-end < 3s.
- **Security** — PCI-DSS compliance; no raw card data stored; all communication TLS 1.2+; secrets vaulted.

**Q3. What is the scale assumption and how does it affect design?**
A: At moderate scale (e.g., 1,000 TPS peak), a single Postgres instance with good indexing handles state; at 10,000+ TPS you need horizontal write scaling, but payments are almost never the write bottleneck — PSP latency (200–800ms per call) is the natural rate limiter. The interesting scaling problems are in the read/reporting layer and reconciliation pipelines, not the transactional core. Design the transactional core for correctness first; optimize for throughput only when measured.

## Section 2: Idempotency

**Q4. What is idempotency in the context of payments, and why is it critical?**
A: An operation is idempotent if performing it N times produces the same result as performing it once. In payments: if a client submits the same "charge $50" request twice — due to a network timeout, retry logic, or a double-click — the customer should be charged exactly once. Without idempotency, network unreliability and client retries become a source of double charges, which are catastrophic for user trust and extremely expensive to reverse.

**Q5. How do you implement idempotency at the API layer?**
A: The canonical pattern is the **idempotency key**:
1. The client generates a unique key per logical payment operation (UUID v4, or a hash of the business intent).
2. The client sends it as a header: `Idempotency-Key: <uuid>`.
3. The server, before executing any work, checks a durable store for this key.
   - **Key not seen**: execute the operation, atomically persist the result and the key together.
   - **Key seen, operation in progress**: return `409 Conflict` or wait (depending on policy).
   - **Key seen, operation complete**: return the original response from the stored result.
4. The key expires after a defined TTL (e.g., 24–72 hours) — reuse after expiry is treated as a new request.

```sql
CREATE TABLE idempotency_keys (
  key           UUID PRIMARY KEY,
  payment_id    UUID,
  request_hash  TEXT,          -- hash of request body; detects same key, different payload
  response_body JSONB,
  status        TEXT,          -- PROCESSING | COMPLETE
  created_at    TIMESTAMPTZ DEFAULT now(),
  expires_at    TIMESTAMPTZ
);
```

**Q6. What is the "request hash" on the idempotency key record, and why include it?**
A: A hash of the request body (amount, currency, source, destination). If a client sends the same idempotency key with a *different* payload (amount changed, different card), that's a client bug — reusing a key for a semantically different operation. The server detects this by comparing the stored `request_hash` with the new request's hash and returns `422 Unprocessable Entity` rather than silently applying the wrong idempotency. Without this check, a client bug could corrupt payment intent without any error signal.

**Q7. How do you make the idempotency key check and operation execution atomic?**
A: With a database transaction. The pattern:

```sql
BEGIN;

-- Attempt to insert the key; fails (no-op) if already exists
INSERT INTO idempotency_keys (key, status, request_hash)
VALUES ($1, 'PROCESSING', $2)
ON CONFLICT (key) DO NOTHING;

-- Check what happened
SELECT status, response_body, request_hash
FROM idempotency_keys WHERE key = $1 FOR UPDATE;

-- If status = COMPLETE: return stored response, ROLLBACK
-- If status = PROCESSING and this thread didn't insert: 409 (another request in flight)
-- If status = PROCESSING and this thread inserted: proceed with payment, then UPDATE to COMPLETE

COMMIT;
```

The `FOR UPDATE` lock ensures two concurrent requests with the same key don't both proceed past the check simultaneously — the second request blocks until the first commits, then sees `COMPLETE`.

**Q8. Who should generate the idempotency key — the client or the server?**
A: The **client** must generate it, because the key must be stable across retries of the *same logical operation*. If the server generated the key on first receipt, a retried request (due to a network timeout where the client never saw the server's response) would arrive as a new request with no key — the server can't know it's a retry of a previous call. The client's key is what links "the request I sent before I got a timeout" to "the request I'm sending now" as the same logical operation.

## Section 3: Exactly-Once Processing

**Q9. What does "exactly-once processing" mean in a payment system, and is it truly achievable?**
A: Exactly-once means the real-world effect (money moved) happens exactly one time, regardless of retries, failures, or crashes. True exactly-once is theoretically impossible across two independent systems (the payment DB and the PSP are two separate systems with no shared transaction). What's achievable in practice is **effectively-once** via idempotency: the customer is charged once, even if the charge was *attempted* multiple times. PSPs provide their own idempotency keys for exactly this reason — the same PSP idempotency key submitted twice results in one charge.

**Q10. Walk through the failure modes in a payment flow and how each is handled.**
A: The critical sequence is:

```
Client → Payment API → [DB write] → PSP charge → [DB update] → Response to client
```

Failure modes:

| Failure point | What happened | Correct handling |
|--- |--- |--- |
| Client timeout before API receives request | Nothing executed | Client retries with same idempotency key → treated as first request |
| API crashes after DB write but before PSP call | Payment in DB as `PENDING`, PSP not called | Recovery job detects stale `PENDING` payments and retries PSP call using stored PSP idempotency key |
| PSP call succeeds but API crashes before updating DB | DB says `PENDING`, PSP says charged | Recovery job calls PSP's "retrieve charge" API using the PSP idempotency key → sees success → marks DB as `SUCCEEDED` |
| PSP returns ambiguous error (timeout, 5xx) | PSP state unknown | Retry with **same PSP idempotency key** — if PSP charged, it returns the existing charge; if it didn't, it charges now. Never retry with a new key. |
| DB update succeeds but response never reaches client | DB and PSP are consistent; client doesn't know | Client retries with same idempotency key → server looks up complete state → returns stored response |

**Q11. What is the PSP idempotency key, and how is it different from the API idempotency key?**
A: Two distinct keys serving different layers:
- **API idempotency key** — sent by your client to your payment API. Prevents your service from processing the same request twice.
- **PSP idempotency key** — sent by your payment API to the PSP (Stripe's `Idempotency-Key` header, Adyen's `reference` field). Prevents the PSP from executing the same charge twice when your service retries a failed or timed-out PSP call.

You must generate and persist the PSP idempotency key *before* calling the PSP — not derived from the response. It's typically a deterministic derivation of your internal payment ID: `psp_idem_key = "pmt_" + payment_id`. Stored in the payment record so that any retry — including from a recovery job running on a different server — uses the same key.

**Q12. What is the outbox pattern, and when do you use it in a payment system?**
A: The outbox pattern solves the dual-write problem: "update the payments table AND publish a PaymentSucceeded event to Kafka" cannot be done atomically in a single operation across two systems. If you publish to Kafka first and the DB write fails, or write to DB first and Kafka publish fails, you get inconsistency.

Solution: write the event to an `outbox` table in the *same* DB transaction as the payment state update. A separate process (outbox publisher/relay) polls the outbox table and publishes events to Kafka, then marks them as published.

```sql
-- Both in one transaction:
UPDATE payments SET status = 'SUCCEEDED' WHERE id = $1;
INSERT INTO outbox (aggregate_id, event_type, payload, published)
VALUES ($1, 'PaymentSucceeded', $2, false);
```

The outbox relay delivers at-least-once (it may re-publish on crash/retry), so consumers must be idempotent on the event's `paymentId`.

**Q13. What is the saga pattern, and when does a payment system need it?**
A: A saga is a sequence of local transactions across multiple services, each publishing an event that triggers the next step, with compensating transactions to undo completed steps on failure. In payments, the classic example is a checkout flow:

```
Reserve inventory → Charge payment → Confirm order → Release reservation
```

If "Charge payment" fails after "Reserve inventory" succeeded, the saga must execute a compensating transaction to release the inventory reservation. Each step is a local transaction (no distributed lock); compensating transactions restore consistency. Sagas are complex — use them only when operations genuinely span multiple services that can't share a DB. Many payment systems avoid them by making the payment the first step (don't reserve inventory until payment is confirmed).

## Section 4: Data Model

**Q14. What does the core data model for a payment system look like?**
A:

```sql
-- Core payment record
CREATE TABLE payments (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  idempotency_key   UUID UNIQUE NOT NULL,
  amount            BIGINT NOT NULL,         -- always store in minor units (cents)
  currency          CHAR(3) NOT NULL,        -- ISO 4217
  status            TEXT NOT NULL,           -- PENDING | PROCESSING | SUCCEEDED | FAILED | REFUNDED
  psp               TEXT NOT NULL,           -- 'stripe' | 'adyen'
  psp_idempotency_key TEXT NOT NULL,         -- key sent to PSP; deterministic, stored before PSP call
  psp_charge_id     TEXT,                    -- returned by PSP after success
  psp_raw_response  JSONB,                   -- full PSP response; invaluable for disputes
  customer_id       UUID NOT NULL,
  order_id          UUID,
  metadata          JSONB,
  failure_reason    TEXT,
  created_at        TIMESTAMPTZ DEFAULT now(),
  updated_at        TIMESTAMPTZ DEFAULT now(),
  version           INT DEFAULT 0            -- optimistic locking
);

-- Immutable audit trail of every state transition
CREATE TABLE payment_events (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id  UUID NOT NULL REFERENCES payments(id),
  from_status TEXT,
  to_status   TEXT NOT NULL,
  actor       TEXT,               -- 'api' | 'recovery-job' | 'webhook'
  metadata    JSONB,
  occurred_at TIMESTAMPTZ DEFAULT now()
);

-- Refunds (child of a payment)
CREATE TABLE refunds (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id   UUID NOT NULL REFERENCES payments(id),
  amount       BIGINT NOT NULL,
  status       TEXT NOT NULL,
  psp_refund_id TEXT,
  created_at   TIMESTAMPTZ DEFAULT now()
);
```

**Q15. Why store amounts in minor currency units (cents) rather than decimal?**
A: Floating-point arithmetic on decimal types introduces rounding errors. `0.1 + 0.2 = 0.30000000000000004` in IEEE 754. For money, rounding errors are unacceptable — they accumulate, cause reconciliation mismatches, and in aggregate represent real money lost or overcharged. Always store as integers in the smallest currency unit (cents for USD, pence for GBP, yen for JPY — which has no minor unit). Perform all arithmetic as integer arithmetic; only format for display at the presentation layer.

**Q16. What is optimistic locking and why is it on the payments table?**
A: The `version` column implements optimistic concurrency control. When updating a payment's status, include the version in the WHERE clause:

```sql
UPDATE payments
SET status = 'SUCCEEDED', version = version + 1, updated_at = now()
WHERE id = $1 AND version = $2;
-- If 0 rows updated: another process already updated this record; handle conflict
```

This prevents two concurrent processes (e.g., a webhook handler and a recovery job) from both reading `PENDING`, both calling the PSP, and both writing `SUCCEEDED` — the second write would fail the version check, signaling a conflict. Without it, you rely on DB-level row locks (`SELECT ... FOR UPDATE`), which hold locks longer and reduce throughput.

## Section 5: Reconciliation

**Q17. What is reconciliation in a payment system?**
A: Reconciliation is the process of comparing your internal payment records against the PSP's records to detect and resolve discrepancies. PSPs provide daily settlement files or reports (CSV/API) listing every transaction they processed. Reconciliation detects:
- **Missing payments**: PSP shows a charge that doesn't exist in your DB (possible data loss in your system).
- **Ghost payments**: your DB shows a succeeded payment that the PSP has no record of (your DB was updated incorrectly).
- **Amount mismatches**: PSP charged a different amount than your record shows.
- **Status mismatches**: your DB says `PENDING`, PSP says `SUCCEEDED` (recovery job missed it or failed).
- **Unmatched refunds**: a refund in your DB that the PSP didn't process (or vice versa).

**Q18. How do you implement a reconciliation pipeline?**
A: A standard reconciliation pipeline:

```
PSP Settlement File (daily/hourly)
        │
        ▼
[Ingest & Normalize] → reconciliation_psp_records table
        │
        ▼
[Match against payments table]
  JOIN ON psp_charge_id
        │
        ├── Matched, amounts agree → mark RECONCILED
        ├── Matched, amount mismatch → flag AMOUNT_MISMATCH
        ├── In PSP, not in DB → flag MISSING_IN_DB
        └── In DB (SUCCEEDED), not in PSP → flag MISSING_IN_PSP
        │
        ▼
[Exceptions queue] → manual review / automated remediation
```

```sql
CREATE TABLE reconciliation_psp_records (
  id              UUID PRIMARY KEY,
  psp             TEXT NOT NULL,
  psp_charge_id   TEXT NOT NULL,
  amount          BIGINT NOT NULL,
  currency        CHAR(3) NOT NULL,
  psp_status      TEXT NOT NULL,
  settled_at      TIMESTAMPTZ,
  raw             JSONB
);

CREATE TABLE reconciliation_exceptions (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id      UUID REFERENCES payments(id),
  psp_record_id   UUID REFERENCES reconciliation_psp_records(id),
  exception_type  TEXT NOT NULL,   -- MISSING_IN_DB | MISSING_IN_PSP | AMOUNT_MISMATCH | STATUS_MISMATCH
  status          TEXT DEFAULT 'OPEN',
  resolved_at     TIMESTAMPTZ,
  resolution_note TEXT,
  created_at      TIMESTAMPTZ DEFAULT now()
);
```

**Q19. How do you handle the "PSP says succeeded, our DB says pending" case found in reconciliation?**
A: This is the most common discrepancy — caused by a crash or timeout between the PSP responding and your DB being updated. Resolution:
1. Verify the PSP charge ID exists in the PSP's system (call PSP retrieve API or confirm from settlement file).
2. Update the internal payment record to `SUCCEEDED`, setting `psp_charge_id` from the PSP data.
3. Write a `payment_events` row with `actor = 'reconciliation'` documenting what happened.
4. Trigger the `PaymentSucceeded` event via the outbox so downstream systems (order management, fulfillment) get notified — even if belatedly.

This must be idempotent: running the reconciliation job twice for the same exception should be safe.

**Q20. How frequently should reconciliation run, and what are the trade-offs?**
A:
- **Real-time / near-real-time** (webhooks from PSP): PSPs send webhooks on charge completion. Process them immediately to close the PENDING→SUCCEEDED gap. Fastest, but webhooks can fail or be delayed — don't rely on them exclusively.
- **Hourly reconciliation**: catches missed webhooks quickly; good for high-volume systems where even 1-hour gaps cause customer support tickets.
- **Daily reconciliation** (settlement file): PSPs provide official daily settlement files; these are the authoritative record for financial reporting and accounting. Always run this regardless of real-time reconciliation.

Layered approach: webhooks for speed, hourly job for reliability, daily settlement reconciliation for financial accuracy. Each layer catches what the previous missed.

## Section 6: Architecture & Component Design

**Q21. What does the high-level architecture of a payment processing system look like?**
A:

```
Client (web/mobile/backend)
         │
         │  POST /payments  (Idempotency-Key header)
         ▼
┌─────────────────────┐
│   Payment API        │  NestJS / Express
│  - Idempotency check │
│  - Validate request  │
│  - Write DB + outbox │
│  - Call PSP          │
│  - Update DB         │
└────────┬────────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
┌───────┐  ┌──────────────┐
│  DB   │  │   PSP API    │  Stripe / Adyen / Braintree
│Postgres│ │(with our PSP │
│       │  │ idem key)    │
└───────┘  └──────────────┘
    │
    │ Outbox polling
    ▼
┌──────────────────┐
│  Outbox Publisher │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│    Kafka / SQS   │  PaymentSucceeded | PaymentFailed events
└────────┬─────────┘
         │
    ┌────┴──────────────────┐
    ▼                       ▼
Order Service          Ledger Service


┌─────────────────────────┐
│   Recovery Job           │  Cron / Temporal workflow
│  - Find stale PENDING    │
│  - Re-query PSP          │
│  - Update DB             │
└─────────────────────────┘

┌─────────────────────────┐
│  Reconciliation Pipeline │  Daily + hourly
│  - Ingest PSP files      │
│  - Match records         │
│  - Flag exceptions       │
└─────────────────────────┘
```

**Q22. What is the recovery job, and how does it work?**
A: The recovery job handles payments stuck in `PROCESSING` or `PENDING` state longer than a threshold (e.g., 5 minutes). Algorithm:

```
1. SELECT * FROM payments WHERE status IN ('PENDING', 'PROCESSING')
   AND updated_at < now() - interval '5 minutes'
   FOR UPDATE SKIP LOCKED;  -- skip rows locked by another recovery worker

2. For each stale payment:
   a. Call PSP retrieve API using psp_idempotency_key
   b. PSP says SUCCEEDED → update DB to SUCCEEDED, publish event
   c. PSP says FAILED    → update DB to FAILED, record failure_reason
   d. PSP says NOT_FOUND → payment was never submitted; retry PSP charge using same psp_idempotency_key
   e. PSP is unreachable → leave in PENDING, retry at next job run

3. Write payment_events row for every transition.
```

`SKIP LOCKED` prevents multiple recovery job instances from processing the same payment simultaneously — a critical detail for correctness.

**Q23. How do you handle PSP webhooks reliably?**
A: Webhooks are PSP-initiated HTTP POST calls to your endpoint when a charge completes. Reliability challenges:
- **At-least-once delivery**: PSPs retry webhooks if your endpoint returns non-2xx. Your webhook handler must be idempotent.
- **Out-of-order delivery**: a `charge.failed` webhook may arrive before `charge.succeeded` due to network quirks — always check the webhook's own timestamp/event version, not just the current DB state.
- **Signature verification**: PSPs sign webhook payloads (Stripe: `Stripe-Signature` header with HMAC-SHA256). Verify before processing — reject unsigned or incorrectly signed webhooks to prevent spoofing.
- **Fast acknowledgment**: return 200 immediately, enqueue the webhook payload for async processing. Don't do DB work synchronously in the webhook handler — if your DB is slow and you take >30s, the PSP retries.

**Q24. How do you handle currency conversion and multi-currency payments?**
A: Key rules:
- Always store the original charged currency and amount separately from the settlement currency and amount.
- Never do currency conversion yourself at charge time — let the PSP handle it; store their conversion rate and the settled amount in the PSP's settlement currency.
- Reconciliation must compare amounts in the *same* currency — match PSP settlement records in settlement currency, not converted amounts.
- For internal accounting, maintain a separate ledger in your functional currency; use a defined FX rate source (e.g., ECB rates) applied at settlement date, not charge date.

## Section 7: Scenario Questions

**Q25. "A customer is charged twice for the same order. How do you debug and prevent this?"**
A: Debugging:
1. Pull `payment_events` for both payment records — what triggered each? Different idempotency keys means the client made two distinct requests (client-side bug: double-submit without idempotency key, or retried with a new key).
2. Same idempotency key but two PSP charges? The PSP idempotency key was different on retry — a bug in your PSP key generation (e.g., generated from a timestamp instead of a stable payment ID).
3. PSP shows one charge but your DB shows two `SUCCEEDED` records? A race condition in your status update — missing `FOR UPDATE` lock or missing optimistic locking.

Prevention: enforce idempotency key at API layer, derive PSP idempotency key deterministically from payment ID (not timestamps), use `FOR UPDATE SKIP LOCKED` in recovery job, and add a unique constraint on `psp_charge_id` in the payments table.

**Q26. "Your reconciliation job finds 50 payments where your DB says SUCCEEDED but the PSP has no record. What does this mean and what do you do?"**
A: This is a serious data integrity issue — money may not have moved despite your system showing success. Possible causes:
- A bug where your code updated DB to `SUCCEEDED` without actually calling the PSP (e.g., test code merged to prod, or a short-circuit in error handling).
- The PSP records were cleared (PSP data retention issue — rare but possible in sandbox environments leaking to prod).
- Wrong PSP environment (sandbox vs production keys mixed up).

Immediate actions:
1. **Stop triggering downstream fulfillment** for these payments until investigated.
2. Pull application logs and `payment_events` for the affected payments — was a PSP call made? What was the response?
3. If PSP was never called: these are phantom successes; revenue was never collected. Depending on business policy, re-charge or cancel the orders.
4. If PSP was called but returned an error that was incorrectly interpreted as success: fix the bug, then re-process the payments.
5. Post-mortem to understand why the PSP idempotency key wasn't used to re-query before marking success.

**Q27. "How would you design the payment system to support multiple PSPs with automatic failover?"**
A: Multi-PSP routing adds significant complexity but is valuable for high-availability and cost optimization. Design:
- **PSP abstraction layer** — a `PaymentGateway` interface implemented by each PSP adapter (`StripeAdapter`, `AdyenAdapter`). The API calls the interface, not the PSP directly.
- **Routing rules** — configurable rules (in DB or config service) that select the PSP: round-robin, by currency, by card type, by cost per transaction, or by current health.
- **Health tracking** — track PSP error rate and latency in a sliding window. If Stripe's error rate exceeds 5% in the last 5 minutes, route new payments to Adyen.
- **PSP-specific idempotency keys** — PSP idempotency keys are PSP-specific; if you failover mid-attempt from Stripe to Adyen, you need a fresh Adyen idempotency key. Your `payments` table needs `psp` and `psp_idempotency_key` columns, and possibly a `payment_attempts` child table if a single payment can be attempted across multiple PSPs.
- **Reconciliation per PSP** — each PSP has its own settlement file format; your reconciliation pipeline must handle each independently and match against the `psp` field on the payment record.

## Quick Reference

| Concern                    | Mechanism                                                               |
|---                         |---                                                                      |
| API idempotency            | Client-supplied `Idempotency-Key`; stored with response in DB           |
| PSP idempotency            | Deterministic PSP key from payment ID; stored before PSP call           |
| Atomic idempotency check   | DB transaction + `INSERT ... ON CONFLICT DO NOTHING` + `FOR UPDATE`     |
| Crash recovery             | Recovery job polls stale PENDING; re-queries PSP with same idem key     |
| Dual-write safety          | Outbox pattern — event written in same transaction as payment update     |
| Multi-service consistency  | Saga with compensating transactions                                      |
| Concurrent update safety   | Optimistic locking (`version` column) or `SELECT FOR UPDATE SKIP LOCKED`|
| Amounts                    | Always minor units (cents); integer arithmetic only                     |
| Discrepancy detection      | Daily settlement file + hourly reconciliation + PSP webhooks            |
| Audit trail                | Immutable `payment_events` table; every state transition recorded       |

**Tip for the interview:** Payment system design is one of the few where interviewers expect you to lead with correctness concerns before scalability. Open by stating the two axioms — "a customer must never be double-charged" and "a payment's state must survive any single failure" — and show how every design decision flows from those. The specific things that separate 5 YOE answers: knowing that PSP idempotency keys must be generated *before* the PSP call and persisted, explaining the crash-between-PSP-call-and-DB-update failure mode and how the recovery job handles it, and knowing why amounts must be integers. If you can draw the outbox pattern and explain `SKIP LOCKED`, you've covered the hard parts.
