# Design a KYC / Onboarding System — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a KYC onboarding system?**
A: Core functional requirements:
- **Identity document collection** — accept government-issued documents (passport, national ID, driver's license) as image uploads; support front/back where applicable.
- **Document verification** — validate authenticity (not expired, not tampered, security features present), extract structured data (name, DOB, document number, expiry), and match to the user's self-declared identity.
- **Liveness / selfie check** — confirm the person submitting the document is physically present and matches the document photo (prevents using a stolen document).
- **Data extraction (OCR)** — extract machine-readable fields from document images; validate against MRZ (Machine Readable Zone) on passports and ID cards.
- **Watchlist screening** — check extracted name and DOB against sanctions lists (OFAC SDN, EU consolidated list), PEP (Politically Exposed Person) databases, and adverse media.
- **Risk classification** — assign a KYC risk tier (low / medium / high) based on document quality, watchlist hits, and jurisdiction rules.
- **Manual review queue** — route borderline or failed automated checks to human analysts with full document context.
- **Status notifications** — push real-time status updates to the user (PENDING → UNDER_REVIEW → APPROVED / REJECTED) via email, SMS, or webhook.
- **Audit trail** — immutable record of every decision, document version, and analyst action for regulatory inspection.
- **Re-KYC / refresh** — trigger re-verification when documents expire or risk tier changes (e.g., user starts high-value transactions).

**Q2. What are the non-functional requirements that make KYC uniquely hard?**
A:
- **Regulatory compliance** — requirements differ by jurisdiction (FATF recommendations, EU AMLD5/6, US BSA/AML, UK FCA). The system must be configurable to apply different rule sets per user's country of residence and product type.
- **Data residency** — document images often cannot leave the user's jurisdiction (GDPR for EU, India's PDPB, China's PIPL). Document storage and processing may need to be physically isolated per region.
- **Immutability and auditability** — regulators can demand a full audit trail years after onboarding. Records, including the original document images, must be tamper-evident and retained for the legally required period (5–10 years in most jurisdictions).
- **PII sensitivity** — document images are the highest-sensitivity PII. Encryption at rest and in transit is mandatory; access must be logged; raw images must never appear in application logs.
- **Latency vs. accuracy trade-off** — automated checks aim for < 60 seconds for straightforward cases; complex cases may take minutes. SLA for manual review is typically 24–48 hours. The user experience degrades sharply if the automated path is slow.
- **Fraud and spoofing resistance** — attackers submit deepfake selfies, printed photos, screen replays, and digitally altered documents. Detection must keep pace with attack sophistication.

**Q3. What are the main vendor integration patterns for document verification?**
A: Most production systems use a third-party KYC vendor (Onfido, Jumio, Persona, Stripe Identity, Sumsub) rather than building document OCR and liveness detection from scratch. The integration patterns:
- **SDK-based** — vendor's mobile/web SDK handles capture and uploads directly to the vendor's servers; your backend receives webhook callbacks with results. Minimizes raw document image handling in your infrastructure (PCI-DSS / data minimisation benefit).
- **API-based** — your backend receives document uploads, forwards to vendor API, receives structured results. Gives more control over UX and retry logic; increases your data handling obligation.
- **Hybrid** — SDK handles capture (reducing PII exposure on your infra), your backend orchestrates the workflow and stores metadata and decisions (not raw images).

Building in-house is justified only at very large scale (tens of millions of verifications/year) or for jurisdictions where no vendor operates. The state machine, manual review queue, and audit layer are almost always built in-house regardless of vendor choice.

## Section 2: State Machine

**Q4. Why model KYC onboarding as a state machine?**
A: KYC is a multi-step, multi-day process involving async external calls (vendor APIs, watchlist lookups, manual review), retries, timeouts, and multiple terminal states. A state machine makes this tractable because:
- **Explicit valid transitions** — only permitted state transitions can occur; invalid transitions are rejected at the data layer. You can't accidentally mark a `REJECTED` application as `APPROVED` without going through a defined path.
- **Auditability** — every state transition is an event that can be recorded immutably with a timestamp, actor, and reason.
- **Idempotency** — processing a webhook or event twice is safe; if the application is already in the target state, the transition is a no-op.
- **Recovery** — on crash or timeout, the current state tells the recovery job exactly where to resume.
- **Operational clarity** — support and compliance teams can see exactly where an application is and what unblocks it.

**Q5. What does the complete KYC state machine look like?**
A:

```
                        ┌─────────────────────────────────────────────────────┐
                        │                                                     │
   User submits     ┌───▼────┐   Documents    ┌───────────────┐              │
   application ───► │CREATED │ ──uploaded──►  │DOCS_SUBMITTED │              │
                    └────────┘                └───────┬───────┘              │
                                                      │                      │
                                              Automated checks start         │
                                                      │                      │
                                              ┌───────▼────────┐             │
                                              │ AUTO_VERIFYING  │             │
                                              └───────┬────────┘             │
                              ┌───────────────────────┼─────────────────┐    │
                              │                       │                 │    │
                    Auto-pass │             Auto-fail │    Ambiguous /  │    │
                              │                       │    low confidence    │
                    ┌─────────▼──────┐    ┌──────────▼──┐  ┌──────────▼──┐  │
                    │WATCHLIST_CHECK │    │  AUTO_FAILED │  │PENDING_REVIEW│  │
                    └─────────┬──────┘    └──────────┬──┘  └──────────┬──┘  │
                              │                      │                │      │
                   No hits    │         Inform user  │   Analyst      │      │
                              │         → REJECTED   │   reviews      │      │
                    ┌─────────▼──────┐               │   ┌────────────┼────┐ │
                    │ RISK_ASSESSED  │     ┌──────────▼─┐ │ Approve   │Rej │ │
                    └─────────┬──────┘     │  REJECTED  │ └────────────┼────┘│

                    ┌─────────▼──────┐                        ┌────────▼──┐  │
                    │   APPROVED     │◄───────────────────────│  APPROVED │  │
```

Full state list: `CREATED` → `DOCS_SUBMITTED` → `AUTO_VERIFYING` → `WATCHLIST_CHECK` → `RISK_ASSESSED` → `APPROVED` | `REJECTED` | `PENDING_REVIEW` | `AUTO_FAILED` | `RE_KYC_REQUIRED` | `EXPIRED`

**Q6. What are the permitted state transitions and what triggers each?**
A:

| From | To | Trigger |
|--- |--- |--- |
| `CREATED` | `DOCS_SUBMITTED` | User uploads all required documents |
| `DOCS_SUBMITTED` | `AUTO_VERIFYING` | Verification job picks up the application |
| `AUTO_VERIFYING` | `WATCHLIST_CHECK` | Automated doc/liveness checks pass |
| `AUTO_VERIFYING` | `AUTO_FAILED` | Hard failure: expired doc, liveness fail, tampered image |
| `AUTO_VERIFYING` | `PENDING_REVIEW` | Low confidence score; ambiguous liveness; OCR mismatch |
| `WATCHLIST_CHECK` | `RISK_ASSESSED` | No watchlist hits |
| `WATCHLIST_CHECK` | `PENDING_REVIEW` | Potential watchlist match (fuzzy name match requiring human judgment) |
| `RISK_ASSESSED` | `APPROVED` | Risk tier acceptable per product rules |
| `RISK_ASSESSED` | `PENDING_REVIEW` | High-risk tier requires manual sign-off |
| `PENDING_REVIEW` | `APPROVED` | Analyst approves |
| `PENDING_REVIEW` | `REJECTED` | Analyst rejects |
| `AUTO_FAILED` | `DOCS_SUBMITTED` | User re-uploads corrected documents (within retry limit) |
| `APPROVED` | `RE_KYC_REQUIRED` | Document expiry approaching; transaction risk trigger |
| `RE_KYC_REQUIRED` | `DOCS_SUBMITTED` | User begins re-verification |
| Any | `EXPIRED` | Application not completed within N days (configurable) |

**Q7. How do you enforce state transition validity at the data layer?**
A: Use a transition guard in the service layer and a database constraint to make illegal transitions impossible:

```sql
CREATE TABLE kyc_applications (
  id          UUID PRIMARY KEY,
  user_id     UUID NOT NULL UNIQUE,
  status      TEXT NOT NULL DEFAULT 'CREATED',
  risk_tier   TEXT,                   -- LOW | MEDIUM | HIGH
  version     INT NOT NULL DEFAULT 0, -- optimistic locking
  created_at  TIMESTAMPTZ DEFAULT now(),
  updated_at  TIMESTAMPTZ DEFAULT now()
);

-- Permitted transitions table; the service queries this before any UPDATE
CREATE TABLE kyc_permitted_transitions (
  from_status TEXT NOT NULL,
  to_status   TEXT NOT NULL,
  PRIMARY KEY (from_status, to_status)
);
```

In the service:
```typescript
async function transition(
  appId: string,
  toStatus: KycStatus,
  actor: string,
  reason: string,
  tx: DbTransaction
) {
  const app = await tx.query(
    `SELECT status, version FROM kyc_applications WHERE id = $1 FOR UPDATE`,
    [appId]
  );

  const allowed = await tx.query(
    `SELECT 1 FROM kyc_permitted_transitions
     WHERE from_status = $1 AND to_status = $2`,
    [app.status, toStatus]
  );
  if (!allowed.rows.length) {
    throw new InvalidTransitionError(app.status, toStatus);
  }

  // Optimistic lock: version must match
  const updated = await tx.query(
    `UPDATE kyc_applications
     SET status = $1, version = version + 1, updated_at = now()
     WHERE id = $2 AND version = $3`,
    [toStatus, appId, app.version]
  );
  if (updated.rowCount === 0) throw new ConcurrentUpdateError();

  await tx.query(
    `INSERT INTO kyc_events (application_id, from_status, to_status, actor, reason)
     VALUES ($1, $2, $3, $4, $5)`,
    [appId, app.status, toStatus, actor, reason]
  );
}
```

## Section 3: Document Handling

**Q8. What is the document upload flow and how do you handle PII safely?**
A: The upload flow must minimize PII exposure across the system:

```
User (browser/mobile)
        │
        │  1. Client requests a pre-signed upload URL
        ▼
Onboarding API ──► S3/GCS: generate pre-signed PUT URL (15-min TTL)
        │
        │  2. Return pre-signed URL to client (no document touches your API server)
        ▼
User uploads document DIRECTLY to S3/GCS using pre-signed URL
        │
        │  3. S3 triggers an event (S3 Event Notification / EventBridge)
        ▼
Document Processor (async worker)
  - Validate file type (magic bytes, not just extension)
  - Validate file size (< 10MB)
  - Virus scan (ClamAV or cloud-native)
  - Encrypt with customer-managed KMS key
  - Generate a document_id; write metadata to DB (never log the S3 path in plain text)
  - Transition application → DOCS_SUBMITTED
```

Benefits: the raw document image never passes through your application server's memory, reducing your PCI/GDPR surface area significantly. The pre-signed URL is scoped to a specific S3 key (user-specific path), so users can only write to their own location.

**Q9. How do you store document metadata vs document images?**
A:

```sql
-- Metadata in Postgres — queryable, no PII in plain fields
CREATE TABLE kyc_documents (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  application_id    UUID NOT NULL REFERENCES kyc_applications(id),
  document_type     TEXT NOT NULL,       -- PASSPORT | NATIONAL_ID | DRIVERS_LICENSE
  side              TEXT,                -- FRONT | BACK | SELFIE
  storage_key       TEXT NOT NULL,       -- encrypted reference to S3 object key
  content_hash      TEXT NOT NULL,       -- SHA-256 of original file (tamper detection)
  mime_type         TEXT NOT NULL,
  file_size_bytes   INT,
  ocr_data          JSONB,               -- extracted fields (name, dob, doc_number)
  verification_result JSONB,             -- vendor response (score, checks passed/failed)
  uploaded_at       TIMESTAMPTZ DEFAULT now(),
  expires_at        TIMESTAMPTZ          -- document expiry date from OCR
);
```

`storage_key` in the DB is itself encrypted (application-level encryption or Postgres `pgcrypto`) — even if someone dumps the DB table, they can't access the document without the decryption key. The S3 bucket has SSE-KMS encryption; the bucket is not public; access is only via pre-signed URLs generated by the backend with a short TTL (5 minutes for reads).

**Q10. How do you handle document expiry and re-KYC?**
A: At document upload, the OCR pipeline extracts the expiry date and stores it in `kyc_documents.expires_at`. A scheduled job (runs nightly) queries:

```sql
SELECT a.id, a.user_id, d.expires_at
FROM kyc_applications a
JOIN kyc_documents d ON d.application_id = a.id
WHERE a.status = 'APPROVED'
  AND d.expires_at BETWEEN now() AND now() + interval '60 days'
  AND d.document_type IN ('PASSPORT', 'NATIONAL_ID', 'DRIVERS_LICENSE');
```

For each match: transition the application to `RE_KYC_REQUIRED`, send a notification to the user (email/push), and optionally restrict product access (configurable per risk tier — high-risk users may be restricted immediately; low-risk users may get a 30-day grace period).

## Section 4: Automated Verification Pipeline

**Q11. What checks does the automated verification pipeline run?**
A: In sequence (fail fast — stop on hard failure):

1. **Document authenticity** — security feature detection (holograms, microprint patterns, UV features via vendor model), tamper detection (pixel-level manipulation analysis), format validation (document layout matches expected template for that country/type).

2. **OCR and data extraction** — extract: full name, date of birth, document number, nationality, expiry date, issuing country, MRZ. Validate MRZ checksum (the MRZ encodes check digits using a defined algorithm — a mismatch indicates tampering or OCR error).

3. **Cross-field consistency** — DOB extracted from visual zone matches DOB in MRZ; document number format matches issuing country's format; expiry date is in the future.

4. **Identity match** — compare OCR-extracted name and DOB against user's self-declared name and DOB at registration. Fuzzy match (Levenshtein distance / Jaro-Winkler) to handle OCR errors and transliteration variants; flag if similarity is below threshold.

5. **Liveness check** — the selfie is not a printed photo, screen replay, or deepfake. Vendor ML models detect texture (paper grain), reflection patterns, 3D depth cues (active liveness requires the user to blink or turn head), and GAN artifacts.

6. **Face match** — compare the selfie to the document photo using facial recognition. Similarity score above threshold (e.g., 0.85) required to pass.

7. **Watchlist screening** — see Section 5.

**Q12. How do you handle OCR errors and low-confidence extractions?**
A: Every extracted field from the OCR model has a confidence score. Strategy:
- **High confidence (> 0.9)**: use extracted value directly.
- **Medium confidence (0.7–0.9)**: use extracted value but flag the field for potential analyst review if the application is routed to `PENDING_REVIEW` for any reason.
- **Low confidence (< 0.7)**: do not use the value; either route to `PENDING_REVIEW` with a note for analyst to manually transcribe, or ask the user to re-upload a clearer image (for self-service, first attempt).
- **MRZ as ground truth**: on documents with an MRZ (passports, many national IDs), prefer MRZ-extracted values over visual zone OCR — the MRZ is machine-printed and checksummed, making it far more reliable than handwriting or worn visual zones.

**Q13. How do you design the verification pipeline for resilience?**
A: The vendor API call is the most fragile component:

```
Document Processor (worker)
        │
        │  1. Check idempotency: has this document_id already been sent to vendor?
        │     (stored: vendor_submission_id in kyc_documents)
        │
        │  2. Submit to vendor API with idempotency key = document_id
        │
        │  3a. Vendor responds synchronously (< 10s): process result immediately
        │  3b. Vendor is async (result via webhook): store submission_id, exit worker
        │      Webhook handler receives result, resumes pipeline
        │
        │  4. On vendor timeout / 5xx: exponential backoff retry (3 attempts)
        │     After 3 failures: transition to PENDING_REVIEW with reason
        │     "vendor_unavailable"; analyst reviews raw documents manually
        │
        │  5. On vendor permanent failure (invalid document): mark AUTO_FAILED
        │     with vendor's reason codes; notify user with specific guidance
```

The vendor submission ID (stored before the call) ensures that if your worker crashes after submitting but before receiving the response, a recovery job can poll the vendor for the result using the stored ID rather than re-submitting (avoiding double billing and vendor rate limits).

## Section 5: Watchlist Screening

**Q14. What is watchlist screening and what lists are typically checked?**
A: Watchlist screening checks the user's extracted identity against databases of sanctioned individuals, high-risk persons, and known fraudsters. Standard lists:
- **OFAC SDN** (US Office of Foreign Assets Control Specially Designated Nationals) — mandatory for US-regulated businesses; transactions with SDN-listed persons are illegal.
- **EU Consolidated Sanctions List** — equivalent for EU-regulated businesses.
- **UN Security Council Consolidated List** — global sanctions.
- **PEP (Politically Exposed Persons)** — senior government officials, their family members, and close associates. Not prohibited, but require enhanced due diligence (EDD) and higher risk tier.
- **Adverse media** — news screening for criminal allegations, fraud, corruption.
- **Internal fraud lists** — your own database of previously rejected or flagged users.

**Q15. How do you handle fuzzy name matching in watchlist screening?**
A: Name matching is not exact — names are transliterated differently from Arabic/Chinese/Cyrillic scripts, nicknames and name order variations exist, and OCR may introduce errors. Approach:
- **Normalize** — remove diacritics, standardize to uppercase, normalize whitespace, expand common abbreviations (e.g., "St." → "Saint").
- **Tokenize and permute** — split name into tokens; try all orderings (first/last name reversal is extremely common).
- **Fuzzy match algorithms** — Jaro-Winkler (good for name transpositions), double Metaphone (phonetic similarity — "Smith" and "Smyth" match), edit distance thresholds.
- **Date of birth gating** — a name match without DOB match is downgraded; a name match with DOB match within ±1 year is escalated. DOB dramatically reduces false positives from common names.
- **Match scoring** — combine name similarity score + DOB match + nationality into a composite match score. Below 0.7: no match. 0.7–0.9: potential match → `PENDING_REVIEW`. Above 0.9 on a sanctions list: hard `REJECTED`.

**Q16. How frequently must watchlist screening be re-run after initial approval?**
A: Initial screening at onboarding is not sufficient — watchlists are updated continuously (OFAC updates the SDN list multiple times per week). Regulatory requirements vary but typical practice:
- **Real-time screening on transactions** — each high-value transaction screens the sender/receiver (often at the payment processing layer, not just onboarding).
- **Periodic re-screen of customer base** — run all `APPROVED` users against updated watchlists daily or weekly. A batch job that processes the full customer database nightly is standard.
- **Event-driven re-screen** — when a watchlist provider publishes a major update (new SDN additions), trigger an immediate re-screen sweep rather than waiting for the nightly batch.

If a re-screen hits a match on a previously approved user, transition them to `PENDING_REVIEW` immediately and restrict account access pending analyst review.

## Section 6: Manual Review Queue

**Q17. How do you design the manual review queue for analyst efficiency?**
A: The review queue is a case management interface where analysts resolve applications that automated checks couldn't decide. Design priorities:

**Queue structure:**
```sql
CREATE TABLE review_queue (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  application_id  UUID NOT NULL REFERENCES kyc_applications(id),
  priority        INT NOT NULL DEFAULT 5,    -- 1 = urgent (sanctions hit), 10 = routine
  reason          TEXT NOT NULL,             -- AUTO_FAILED | LOW_CONFIDENCE | WATCHLIST_HIT
  assigned_to     UUID REFERENCES analysts(id),
  assigned_at     TIMESTAMPTZ,
  sla_deadline    TIMESTAMPTZ NOT NULL,      -- 24h from creation for standard; 4h for high priority
  completed_at    TIMESTAMPTZ,
  decision        TEXT,                      -- APPROVE | REJECT | REQUEST_MORE_INFO
  decision_reason TEXT,
  created_at      TIMESTAMPTZ DEFAULT now()
);
```

**Analyst tooling:**
- Display document images (front, back, selfie, side-by-side comparison) with the vendor's automated check results and reason codes.
- Show pre-computed identity match score, OCR extracted data, and which specific checks failed.
- Render watchlist hits with the matched entity's details and similarity score.
- Provide structured decision options (approve / reject / request more info) with mandatory reason code selection — free-text notes allowed but a coded reason is required for audit.
- Show the SLA deadline and queue depth; prioritize by deadline, then by risk tier.

**Q18. How do you prevent analysts from making arbitrary decisions (bias and consistency)?**
A: Structured decision workflow:
- **Mandatory checklists** — before approving or rejecting, the analyst must confirm specific items (document not expired, face match visually confirmed, no unresolved watchlist hit). Checkboxes are stored in the audit trail.
- **Two-analyst rule for high-risk** — applications in the HIGH risk tier or with watchlist hits require a second analyst to confirm the decision. Implemented as a second `PENDING_REVIEW` queue step.
- **Decision reason codes** — rejection must select from a predefined list (DOCUMENT_EXPIRED, FACE_MISMATCH, SUSPECTED_FORGERY, WATCHLIST_MATCH, POOR_IMAGE_QUALITY). Enables quality monitoring and bias detection.
- **Auditor role** — a separate auditor role can review completed decisions, flag inconsistencies, and trigger re-review without being able to change the record.
- **Quality sampling** — randomly sample 5% of APPROVED decisions for retrospective review by a senior analyst; track analyst-level approval rates and flag statistical outliers.

## Section 7: Data Model

**Q19. What does the complete data model look like?**
A:

```sql

CREATE TABLE kyc_applications (
```

## Section 8: Compliance & Audit

**Q20. How do you make the audit trail tamper-evident?**
A: `kyc_events` is append-only by design — no application code has UPDATE or DELETE privileges on this table. Enforced at the DB level:

```sql
-- Revoke all non-INSERT DML on kyc_events from the application role
REVOKE UPDATE, DELETE, TRUNCATE ON kyc_events FROM kyc_app_role;

-- For stronger tamper evidence: hash chaining
-- Each event stores a hash of (its own data || previous event's hash)
-- An auditor can recompute the chain; any modification breaks the chain
ALTER TABLE kyc_events ADD COLUMN chain_hash TEXT;
```

For regulatory-grade immutability: export the event log to WORM (Write Once Read Many) storage — AWS S3 Object Lock or Azure Immutable Blob Storage — on a daily basis. Even if your DB is compromised, the WORM export is independently verifiable.

**Q21. What data retention requirements apply and how do you implement them?**
A: Most AML regulations require KYC records to be retained for 5 years after the business relationship ends (10 years in some jurisdictions). Implementation:
- Tag records with a `retention_until` date at creation.
- A scheduled deletion job runs monthly, hard-deleting records (including S3 documents) whose `retention_until` has passed.
- Before deletion, export a final audit summary to WORM storage (event log, final status, watchlist results) — regulators need the decision trail even after document deletion.
- GDPR right to erasure is in tension with AML retention requirements — AML wins; inform users that legal obligations prevent deletion during the retention period, but personal data not required for the AML record (e.g., unrelated account data) can still be erased.

**Q22. How do you handle a regulatory examination / data subject access request?**
A: Both require producing a complete record of a specific user's KYC history:

```sql
-- Everything a regulator or data subject needs:
SELECT
  a.*,
  json_agg(DISTINCT e.*) AS events,
  json_agg(DISTINCT d.document_type || ':' || d.verification_result::text) AS documents,
  json_agg(DISTINCT w.*) AS watchlist_screenings,
  json_agg(DISTINCT r.*) AS review_decisions
FROM kyc_applications a
LEFT JOIN kyc_events e ON e.application_id = a.id
LEFT JOIN kyc_documents d ON d.application_id = a.id
LEFT JOIN watchlist_screenings w ON w.application_id = a.id
LEFT JOIN review_queue r ON r.application_id = a.id
WHERE a.user_id = $1
GROUP BY a.id;
```

The output — every document submitted, every automated check result, every state transition with timestamp and actor, every analyst decision with reason — is the complete audit package. For regulatory examinations, export as a signed PDF. For data subject access requests, redact analyst-internal notes per your privacy policy.

## Section 9: Scenario Questions

**Q23. "A user's document passes automated checks but a watchlist screening returns a potential match with 0.75 similarity on an OFAC SDN entry. What does the system do?"**
A: A 0.75 similarity score is below the hard-block threshold (0.9) but above the no-match threshold (0.7) — it's a potential match requiring human judgment. The system:
1. Transitions the application to `PENDING_REVIEW` with reason `WATCHLIST_POTENTIAL_MATCH`.
2. Creates a high-priority review queue entry (priority 1 — sanctions hits are always urgent) with a 4-hour SLA.
3. Restricts the user's account access immediately — the user cannot transact until the match is resolved (regulatory requirement for sanctions screening).
4. The analyst sees: the matched SDN entity's name, aliases, DOB, nationality; the user's OCR-extracted data; the similarity scores per field. The analyst must either confirm no match (with documented reasoning) or escalate to the compliance team.
5. If the analyst confirms no match: transition to `RISK_ASSESSED` → `APPROVED`; restore account access; log the decision with full rationale.
6. If confirmed match: transition to `REJECTED`; freeze account; escalate to compliance who may be required to file a Suspicious Activity Report (SAR).

**Q24. "Design the system to support multiple countries, each with different required documents and verification rules."**
A: A configuration-driven approach:

```typescript
interface KycRuleSet {
  countryCode:         string;
  productType:         string;          // 'RETAIL' | 'BUSINESS' | 'CRYPTO'
  requiredDocuments:   DocumentSpec[];  // which documents are required
  acceptedDocuments:   string[];        // which document types are accepted
  watchlistsRequired:  string[];        // which watchlists to screen
  riskTierThresholds:  RiskThresholds;
  manualReviewTriggers: string[];       // which auto-check failures trigger review vs rejection
  retentionYears:      number;
  edRequired:          boolean;         // enhanced due diligence required for all users
}
```

Rules are stored in a database (not hardcoded), loaded at startup, and hot-reloaded when updated. The onboarding flow selects the applicable rule set based on `(countryCode, productType)` at the start of the application and stores the rule set version on the application record — so the rules are evaluated consistently even if they change mid-flow. Compliance teams can update rule sets (add a required document, change watchlists) via an admin UI without an engineering deployment.

**Q25. "A vendor (Onfido) has a 2-hour outage. How does your system handle in-flight KYC applications?"**
A: The vendor outage must not block all onboarding indefinitely. Layered response:
1. **Immediate**: the automated verification pipeline detects vendor 5xx responses after 3 retries with exponential backoff (total ~2 minutes of retrying). Applications in `AUTO_VERIFYING` are transitioned to `PENDING_REVIEW` with reason `VENDOR_UNAVAILABLE`.
2. **Manual review fallback**: analysts manually review the document images already uploaded to S3. They have access to the same documents and OCR data (some OCR may have succeeded before the outage). High-volume operations may pre-train analysts for this fallback — it happens more than you'd like.
3. **Queue draining on recovery**: when the vendor comes back, a recovery job queries all applications with `VENDOR_UNAVAILABLE` reason in the review queue and re-submits them to the vendor, using the stored vendor submission ID to avoid re-billing if the vendor received the original request. Successfully auto-verified applications are moved back out of the manual queue.
4. **Vendor SLA tracking**: vendor outage duration and impact (applications delayed, analyst hours spent) are logged against the vendor's SLA. Most enterprise KYC vendor contracts include SLA credits for downtime.
5. **Multi-vendor fallback** (for high-volume operations): maintain a secondary vendor integration. Route new applications to the backup vendor when the primary is unhealthy. The vendor abstraction layer (`KycVendorAdapter` interface) makes swapping transparent to the pipeline.

## Quick Reference

| Concern | Mechanism |
|--- |--- |
| State enforcement | Permitted transitions table + `FOR UPDATE` + optimistic locking |
| Audit trail | Append-only `kyc_events`; WORM export for tamper evidence |
| Document storage | Pre-signed S3 upload (PII never touches app server); encrypted at rest with KMS |
| Document PII | `storage_key` encrypted in DB; images never in logs; short-TTL pre-signed read URLs |
| Idempotent vendor calls | Store vendor submission ID before call; re-use on retry |
| Vendor outage | Retry with backoff → PENDING_REVIEW with `VENDOR_UNAVAILABLE` reason |
| Watchlist matching | Fuzzy name match (Jaro-Winkler + phonetic) + DOB gate + composite score |
| Re-KYC | Nightly job on document expiry dates; event-driven on risk tier change |
| Multi-country rules | Config-driven rule sets per `(country, product_type)`; version pinned on application |
| Analyst consistency | Mandatory checklists + reason codes + two-analyst rule for high-risk |
| Data retention | `retention_until` date; scheduled deletion; WORM export before deletion |

**Tip for the interview:** KYC questions test regulatory awareness as much as systems design — interviewers notice immediately if you treat it as a generic document upload + status tracking problem. Lead by naming the real regulatory constraints (sanctions screening is legally mandatory, not optional; AML retention overrides GDPR erasure requests) and show that every design decision flows from them. The specific things that separate 5 YOE answers: the pre-signed S3 upload pattern for PII minimisation, the watchlist fuzzy match with DOB gating (not just exact name match), and understanding that the state machine's event log is the product the regulator cares about, not the application UI. If you can articulate the tension between GDPR right-to-erasure and AML retention requirements and how you resolve it, you've demonstrated the compliance depth that senior roles require.
