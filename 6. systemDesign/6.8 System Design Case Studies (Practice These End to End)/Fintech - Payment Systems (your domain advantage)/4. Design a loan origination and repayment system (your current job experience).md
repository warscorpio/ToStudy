# Design a Loan Origination and Repayment System — Interview Q&A (5 YOE Level)

---

## Section 1: Domain Fundamentals

**Q1. What are the two major phases of a loan system, and what does each involve?**
A: Every loan system has two distinct lifecycles that are often built as separate bounded contexts:

- **Loan Origination** — everything from a borrower's application to the moment funds are disbursed. Covers: application intake, KYC/identity verification, credit underwriting (risk assessment, credit bureau pulls), product selection (loan amount, tenure, interest rate), approval workflow, agreement signing, and disbursement. The output is a sanctioned, active loan.
- **Loan Servicing / Repayment** — everything after disbursement until the loan is fully repaid or written off. Covers: repayment schedule generation, EMI collection, payment processing, delinquency tracking, foreclosure/prepayment handling, NOC (No Objection Certificate) issuance, and collections for defaulted loans.

Keeping these separated architecturally matters — origination is event-driven and workflow-heavy (a loan application moves through states over days); servicing is schedule-driven and ledger-heavy (recurring debits on fixed dates for months or years).

**Q2. What is an EMI and how is it calculated?**
A: EMI (Equated Monthly Installment) is the fixed monthly payment a borrower makes, covering both principal repayment and interest. The standard formula for a reducing-balance loan:

```
EMI = P × r × (1 + r)^n / ((1 + r)^n − 1)

Where:
  P = Principal (loan amount)
  r = Monthly interest rate (annual rate / 12)
  n = Number of monthly installments (tenure in months)
```

Example: ₹100,000 loan at 12% annual interest for 12 months:
- r = 12% / 12 = 1% = 0.01
- n = 12
- EMI = 100000 × 0.01 × (1.01)^12 / ((1.01)^12 − 1) ≈ ₹8,885

Key property: EMI is constant across all installments, but the split between principal and interest changes each month — early installments are interest-heavy; later ones are principal-heavy. This is called an **amortization schedule**.

**Q3. What is an amortization schedule, and why is it a first-class entity in the data model?**
A: An amortization schedule is the pre-computed, installment-by-installment breakdown of a loan for its entire tenure — showing for each due date: the opening balance, interest component, principal component, total EMI, and closing balance. It's a first-class entity because:
- It is the contractual repayment plan — legally binding once the loan agreement is signed.
- It drives every downstream process: when to collect, how much to collect, how to split a payment between interest and principal.
- It enables delinquency tracking — comparing what *was due* per schedule against what *was actually paid*.
- It is the source of truth for outstanding principal at any point in time, which drives prepayment and foreclosure calculations.

It must be generated at disbursement time and stored immutably. Recalculation only happens on specific lifecycle events (restructuring, prepayment, rate change on floating-rate loans).

**Q4. What is the difference between flat-rate and reducing-balance interest, and why does it matter for the data model?**
A: 
- **Flat-rate interest** — interest is computed on the original principal for the entire tenure, regardless of how much has been repaid. A ₹100,000 loan at 10% flat for 2 years = ₹20,000 total interest, spread equally across 24 EMIs. Simple to compute but effectively a higher cost to the borrower (since they're paying interest on principal they've already repaid). Common in consumer goods/BNPL lending.
- **Reducing-balance interest** — interest is computed each period on the outstanding principal only. As principal reduces, so does the interest component each month. True cost to the borrower is lower. Standard in home loans, personal loans, and most regulated lending.

The data model must store the interest type as an immutable field on the loan at origination — the amortization schedule generation algorithm branches on this. Mixing them up is a regulatory and financial error that can't be fixed without reissuing the loan.

## Section 2: Origination — Data Model & Workflow

**Q5. What are the core entities in a loan origination system?**
A:

```sql
-- Loan Application: the customer's request for credit
CREATE TABLE loan_applications (
    application_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    applicant_id        UUID NOT NULL,           -- FK to users/customers table
    product_id          UUID NOT NULL,           -- FK to loan_products (personal, home, BNPL, etc.)
    requested_amount    BIGINT NOT NULL,          -- in smallest currency unit (paise/cents)
    requested_tenure    INT NOT NULL,             -- in months
    purpose             TEXT,                    -- 'HOME_RENOVATION', 'EDUCATION', 'MEDICAL', etc.
    status              TEXT NOT NULL DEFAULT 'DRAFT',
    idempotency_key     TEXT UNIQUE NOT NULL,
    submitted_at        TIMESTAMPTZ,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT valid_status CHECK (status IN (
        'DRAFT', 'SUBMITTED', 'UNDER_REVIEW', 'APPROVED', 'REJECTED',
        'OFFER_ACCEPTED', 'AGREEMENT_SIGNED', 'DISBURSED', 'CANCELLED', 'EXPIRED'
    ))
);

-- Credit Decision: underwriting output
CREATE TABLE credit_decisions (
    decision_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    application_id      UUID NOT NULL REFERENCES loan_applications(application_id),
    decision_type       TEXT NOT NULL,           -- 'APPROVED', 'REJECTED', 'CONDITIONAL'
    approved_amount     BIGINT,                  -- may differ from requested amount
    approved_tenure     INT,
    interest_rate       NUMERIC(6,4) NOT NULL,   -- annual rate, e.g. 18.5000
    interest_type       TEXT NOT NULL,           -- 'REDUCING_BALANCE', 'FLAT_RATE'
    processing_fee      BIGINT,                  -- upfront fee in smallest unit
    rejection_reasons   TEXT[],                  -- array of reason codes if rejected
    credit_score        INT,                     -- bureau score at time of decision
    decided_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    decided_by          TEXT NOT NULL,           -- 'SYSTEM', 'UNDERWRITER_USER_ID', 'RULE_ENGINE'
    valid_until         TIMESTAMPTZ NOT NULL     -- offer expiry
);

-- Loan: the active financial contract after disbursement
CREATE TABLE loans (
    loan_id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    application_id      UUID NOT NULL REFERENCES loan_applications(application_id),
    borrower_id         UUID NOT NULL,
    loan_account_number TEXT UNIQUE NOT NULL,    -- human-readable reference (e.g. LN-2026-00012345)
    principal_amount    BIGINT NOT NULL,
    disbursed_amount    BIGINT NOT NULL,         -- may be less if processing fee deducted upfront
    interest_rate       NUMERIC(6,4) NOT NULL,
    interest_type       TEXT NOT NULL,
    tenure_months       INT NOT NULL,
    emi_amount          BIGINT NOT NULL,
    disbursement_date   DATE NOT NULL,
    first_due_date      DATE NOT NULL,
    status              TEXT NOT NULL DEFAULT 'ACTIVE',
    currency            CHAR(3) NOT NULL DEFAULT 'INR',
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT valid_loan_status CHECK (status IN (
        'ACTIVE', 'CLOSED', 'WRITTEN_OFF', 'NPA', 'RESTRUCTURED'
    ))
);

-- Amortization Schedule: the installment-by-installment repayment plan
CREATE TABLE amortization_schedules (
    schedule_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    loan_id             UUID NOT NULL REFERENCES loans(loan_id),
    installment_number  INT NOT NULL,            -- 1, 2, 3 ... n
    due_date            DATE NOT NULL,
    opening_principal   BIGINT NOT NULL,
    emi_amount          BIGINT NOT NULL,
    principal_component BIGINT NOT NULL,
    interest_component  BIGINT NOT NULL,
    closing_principal   BIGINT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'PENDING',  -- 'PENDING', 'PAID', 'PARTIAL', 'OVERDUE'
    UNIQUE (loan_id, installment_number)
);
```

**Q6. What does the loan application state machine look like, and why model it explicitly?**
A: A loan application moves through well-defined states, and illegal transitions (e.g., going from REJECTED back to UNDER_REVIEW) must be prevented at the application layer:

```
DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED ──→ OFFER_ACCEPTED → AGREEMENT_SIGNED → DISBURSED
                                 ↘ REJECTED                                        ↘ CANCELLED
                                 ↘ EXPIRED (offer not accepted in time)
```

Modelling it explicitly matters because:
- Each state change triggers downstream actions: SUBMITTED → trigger KYC check; APPROVED → generate offer letter; AGREEMENT_SIGNED → trigger disbursement.
- Invalid transitions are bugs that could result in financial loss (disbursing a rejected application, accepting an expired offer).
- The state machine is auditable — the state history (with timestamps and actor IDs) is your compliance trail.

Implement transitions in code as a state machine with an explicit allowed-transitions map. Reject any transition not in the map with a 409 Conflict. Log every transition to an `application_state_history` table with `(application_id, from_state, to_state, transitioned_at, transitioned_by, reason)`.

**Q7. What is a loan product, and how does it parameterize the origination system?**
A: A loan product is a template that defines the rules and constraints for a category of loans — personal loans, home loans, BNPL, gold loans. It prevents business logic from being hardcoded in the origination flow:

```sql
CREATE TABLE loan_products (
    product_id          UUID PRIMARY KEY,
    name                TEXT NOT NULL,           -- 'Personal Loan', 'Salary Advance', 'BNPL'
    min_amount          BIGINT NOT NULL,
    max_amount          BIGINT NOT NULL,
    min_tenure_months   INT NOT NULL,
    max_tenure_months   INT NOT NULL,
    interest_rate_min   NUMERIC(6,4) NOT NULL,   -- risk-based pricing range
    interest_rate_max   NUMERIC(6,4) NOT NULL,
    interest_type       TEXT NOT NULL,
    processing_fee_pct  NUMERIC(5,4),            -- e.g. 0.0200 = 2%
    prepayment_penalty_pct NUMERIC(5,4),
    grace_period_days   INT NOT NULL DEFAULT 0,
    late_fee_per_day    BIGINT,
    is_active           BOOLEAN NOT NULL DEFAULT TRUE,
    requires_collateral BOOLEAN NOT NULL DEFAULT FALSE
);
```

The underwriting engine uses product parameters to validate the requested amount and tenure, calculate the interest rate within the product's range (risk-based pricing), and compute fees. Adding a new loan product is a data change, not a code change.

## Section 3: Credit Underwriting

**Q8. What is credit underwriting, and what systems does it interact with?**
A: Underwriting is the process of evaluating a borrower's creditworthiness and deciding whether to lend, how much, and at what interest rate. It interacts with:
- **Credit bureaus** (CIBIL, Experian, Equifax in India; Equifax, TransUnion, Experian in the US) — pull the applicant's credit report: score, existing loans, repayment history, enquiries, defaults.
- **Bank statement analysis** — assess income, cash flow, and existing EMI obligations from the applicant's bank statements (via account aggregators in India, Plaid in the US).
- **Internal data** — repayment history with your own platform, product usage patterns, fraud signals.
- **Rule engine** — codified policy rules: minimum credit score, maximum debt-to-income ratio, employment type eligibility, blacklisted pincodes.
- **ML model** (at scale) — probability of default (PD) model that scores the applicant and determines risk-based pricing.

**Q9. What is a rule engine in the underwriting context, and how would you design one that's configurable at runtime?**
A: A rule engine evaluates a set of business rules against an applicant's profile and produces a decision (APPROVE / REJECT / FLAG_FOR_REVIEW). The key design requirement is that credit policy changes (e.g., "raise minimum CIBIL score from 700 to 720") should not require a code deployment — they should be configurable by the credit risk team without engineering involvement.

A configurable rule engine approach:

```sql
CREATE TABLE underwriting_rules (
    rule_id         UUID PRIMARY KEY,
    product_id      UUID REFERENCES loan_products(product_id),
    rule_name       TEXT NOT NULL,
    attribute       TEXT NOT NULL,       -- 'credit_score', 'dti_ratio', 'age', 'monthly_income'
    operator        TEXT NOT NULL,       -- 'GTE', 'LTE', 'EQ', 'IN', 'NOT_IN'
    threshold_value TEXT NOT NULL,       -- stored as text, cast at runtime
    action          TEXT NOT NULL,       -- 'REJECT', 'FLAG', 'APPROVE_IF_ONLY_FAILURE'
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    effective_from  TIMESTAMPTZ NOT NULL,
    effective_until TIMESTAMPTZ
);
```

At underwriting time: load all active rules for the product, evaluate each against the applicant's bureau data and financials, collect failures, and produce a decision. Rejections with specific rule failures are logged to `credit_decisions.rejection_reasons` for regulatory disclosure (in India, lenders must communicate rejection reasons to applicants under RBI guidelines).

**Q10. What is debt-to-income (DTI) ratio, and why is it a critical underwriting signal?**
A: DTI ratio is the percentage of a borrower's monthly income that is already committed to debt repayment:

`DTI = (Total existing monthly EMI obligations + Proposed new EMI) / Monthly net income × 100`

A DTI of 40% means 40% of the borrower's income is already spoken for by loan repayments. High DTI (e.g., >50–60%) signals the borrower may not have sufficient cash flow to service a new loan — it's one of the strongest predictors of default alongside credit score. Most lenders set a hard DTI cap per product (e.g., max 50% for personal loans). The data challenge: computing DTI requires knowing the applicant's existing EMIs from the bureau report *and* their verified income from bank statements — both need to be fetched, parsed, and normalized before the rule can fire.

## Section 4: Repayment & Servicing

**Q11. How does the repayment flow work end-to-end for an EMI collection?**
A: On each EMI due date, the following sequence runs:

1. **Scheduler** — a cron job (or event-driven trigger) identifies all `amortization_schedules` rows where `due_date = today` and `status = 'PENDING'`.
2. **Debit instruction** — for each due installment, generate a debit instruction to the borrower's registered repayment method: NACH mandate (auto-debit from bank account in India), card-on-file, UPI AutoPay.
3. **Payment attempt** — submit the debit to the payment processor (NPCI for NACH, Razorpay/Stripe for cards). This is asynchronous; the result comes back via webhook.
4. **Webhook processing** — on success: post journal entries (DEBIT borrower's bank → CREDIT loan repayment account), update `amortization_schedules` row to PAID, update `loans` outstanding principal. On failure: mark attempt as failed, trigger retry logic or delinquency flow.
5. **Interest vs principal split** — the payment amount is split per the amortization schedule for that installment. If a partial payment arrives, apply to interest first (standard accounting convention), then principal.
6. **Prepayment handling** — if the borrower pays more than the EMI, the excess reduces the outstanding principal. Depending on product terms: recalculate future EMIs (same tenure, lower EMI) or reduce the tenure (same EMI, fewer installments).

**Q12. How do you handle a partial payment on an EMI?**
A: Partial payments are operationally complex. The standard approach:
- Apply the partial amount to **interest first**, then principal — this protects the lender's revenue and is the legally standard waterfall in most jurisdictions.
- Mark the installment as PARTIAL in `amortization_schedules`, recording `amount_paid` and `paid_at`.
- Track the **shortfall** (EMI − amount_paid) as an outstanding balance on that installment.
- At the next collection attempt, the total due = current EMI + prior installment shortfall + any accrued late fees.
- Late fees begin accruing on the unpaid portion from the due date, per the product's `late_fee_per_day` parameter.

Never silently roll a shortfall into future EMIs without explicit restructuring — that changes the contract, requires borrower consent, and is a regulated activity.

**Q13. What is a NACH mandate, and how does it work in the Indian lending context?**
A: NACH (National Automated Clearing House) is NPCI's system for recurring debit mandates — it allows a lender to auto-debit a borrower's bank account on scheduled dates without requiring the borrower to initiate each payment. During loan origination, the borrower signs a NACH mandate form (physical or e-NACH via Aadhaar/NetBanking). The lender registers the mandate with NPCI through their sponsor bank. On EMI due dates, the lender presents a debit instruction through NPCI; the borrower's bank debits the account and settles funds to the lender. NACH returns (failed debits) arrive with standardized reason codes: `INSUFFICIENT_FUNDS`, `ACCOUNT_CLOSED`, `MANDATE_REVOKED`, etc. — each code drives different downstream logic (retry for insufficient funds; flag for manual review for revoked mandate).

**Q14. What is the payment waterfall, and how should you apply a payment when a borrower has multiple overdue installments?**
A: When a borrower pays after missing multiple EMIs, the order in which the payment is applied matters financially and legally. The standard waterfall (lender-favorable, and often mandated by regulation):

```
1. Overdue fees and charges (late fees, bounce charges, legal fees)
2. Overdue interest (from oldest to newest installment)
3. Overdue principal (from oldest to newest installment)
4. Current installment interest
5. Current installment principal
6. Prepayment toward future principal (if any excess remains)
```

This order must be hardcoded as a configuration on the loan product and disclosed to the borrower in the loan agreement — changing it post-origination is a contract violation. Implement it as an explicit allocation function that takes `payment_amount` and returns a breakdown across each category, creating a separate ledger entry per bucket.

## Section 5: Delinquency & Collections

**Q15. What is DPD (Days Past Due), and how is it used for delinquency classification?**
A: DPD is the number of calendar days since an installment's due date that it remains unpaid. It's the primary axis for delinquency classification and provisioning:

| DPD Range     | Classification | Action |
|---            |---             |---     |
| 0             | Current        | None |
| 1–30          | SMA-0 (Special Mention Account) | Soft reminder, SMS/email nudge |
| 31–60         | SMA-1          | Outbound calls, payment link |
| 61–90         | SMA-2          | Escalated collections, legal notice |
| 91–180        | NPA Sub-standard | Provisioning, legal recovery |
| 180+          | NPA Doubtful / Loss | Write-off consideration |

This classification follows RBI's IRAC (Income Recognition and Asset Classification) norms in India. A loan is classified as NPA (Non-Performing Asset) when principal or interest remains overdue for more than 90 days — at which point the lender must stop recognizing income from that loan and begin provisioning. Your data model must be able to compute DPD for every loan in real time, which means a daily job that scans for unpaid installments past their due date and updates a `delinquency_records` table.

**Q16. How would you design the delinquency tracking data model?**
A:

```sql
CREATE TABLE delinquency_records (
    record_id           UUID PRIMARY KEY,
    loan_id             UUID NOT NULL REFERENCES loans(loan_id),
    as_of_date          DATE NOT NULL,
    dpd                 INT NOT NULL,               -- days past due as of this date
    overdue_principal   BIGINT NOT NULL,
    overdue_interest    BIGINT NOT NULL,
    overdue_charges     BIGINT NOT NULL,
    total_overdue       BIGINT NOT NULL,
    classification      TEXT NOT NULL,              -- 'CURRENT', 'SMA0', 'SMA1', 'SMA2', 'NPA'
    UNIQUE (loan_id, as_of_date)
);

CREATE TABLE collection_actions (
    action_id           UUID PRIMARY KEY,
    loan_id             UUID NOT NULL REFERENCES loans(loan_id),
    action_type         TEXT NOT NULL,              -- 'SMS', 'EMAIL', 'CALL', 'LEGAL_NOTICE', 'FIELD_VISIT'
    triggered_at        TIMESTAMPTZ NOT NULL,
    triggered_by        TEXT NOT NULL,              -- 'SYSTEM' or agent_id
    outcome             TEXT,                       -- 'PROMISE_TO_PAY', 'DISPUTE', 'NO_RESPONSE', 'PAID'
    promise_date        DATE,                       -- if borrower committed to pay by a date
    notes               TEXT
);
```

A daily batch job (`delinquency_refresh`) runs after midnight, computes DPD for every active loan by comparing today's date against each unpaid installment's `due_date`, sums the overdue amounts, writes a new `delinquency_records` row, and updates `loans.status` to `NPA` if DPD ≥ 90.

**Q17. What is provisioning, and why does it matter to the engineering team?**
A: Provisioning is the accounting practice of setting aside a reserve against potential loan losses — recognizing that some loans won't be fully repaid. Regulators (RBI, FDIC) mandate minimum provisioning percentages per NPA classification:

| Classification | Min. Provision % of Outstanding |
|---             |---                               |
| SMA-0          | 0%                               |
| SMA-1          | 5–10% (lender discretion)       |
| Sub-standard NPA | 15%                            |
| Doubtful NPA   | 25–100% depending on age        |
| Loss            | 100%                            |

Engineering's job: produce accurate daily/monthly reports of every loan's classification and outstanding amounts so the finance team can compute provision requirements. Errors in DPD calculation or outstanding balance computation directly cause under-provisioning — which is a regulatory violation. This is why the ledger's correctness invariants (from the wallet/ledger system design) directly feed into compliance outcomes.

## Section 6: Prepayment & Foreclosure

**Q18. What is the difference between prepayment and foreclosure?**
A:
- **Prepayment (Part-prepayment)** — the borrower pays an extra lump sum on top of the EMI, reducing the outstanding principal. The loan continues; future installments are recalculated. The borrower may choose between: (a) keeping the EMI the same and reducing tenure, or (b) keeping tenure the same and reducing the EMI. The lender may charge a prepayment penalty (e.g., 2% of the prepaid amount) — which is product-configured and must be disclosed upfront.
- **Foreclosure (Full prepayment)** — the borrower pays off the entire outstanding principal plus any accrued interest and charges in one shot, closing the loan before tenure ends. Triggers: closing the loan account, issuing an NOC, releasing any collateral (for secured loans), updating credit bureau records.

**Q19. How do you compute the foreclosure amount at a given date?**
A: The foreclosure amount is not simply the remaining installments summed — that would over-charge the borrower by including future interest they won't owe. The correct computation:

```
Foreclosure Amount =
    Outstanding Principal (from amortization schedule as of today)
  + Interest accrued since last EMI date to today (per diem interest)
  + All overdue EMIs and charges (if any)
  + Foreclosure penalty (if applicable per product)
  − Any excess payments already received

Per diem interest = Outstanding Principal × (Annual Rate / 365)
```

This must be computed dynamically — the answer is different on every calendar day. Expose it as an API endpoint (`GET /loans/{loan_id}/foreclosure-quote`) that returns the amount valid for a specific date with an expiry (typically valid for 24 hours, since per diem interest accrues each day). Once the borrower pays the quoted amount on the quoted date, the loan closes. If they pay on a different date, a new quote is required.

**Q20. Walk through the amortization schedule recalculation after a prepayment.**
A: When a part-prepayment is received:

1. Record the prepayment as a ledger transaction — DEBIT borrower, CREDIT loan principal account, with `type = PREPAYMENT`.
2. Reduce the outstanding principal by the prepayment amount.
3. Ask the borrower (or apply the product default): reduce tenure or reduce EMI?
4. **Reduce tenure path:** recompute the number of remaining installments using the existing EMI and the new outstanding principal. Regenerate the amortization schedule for the remaining installments with the original EMI amount.
5. **Reduce EMI path:** keep the original remaining tenure, recompute the new EMI using the reduced principal. Regenerate the schedule with the new EMI.
6. Mark old future schedule rows as `SUPERSEDED` (never delete — audit trail). Insert new schedule rows with `version = 2`.
7. Cancel any pending NACH debit instructions for the old EMI amount and create new ones for the revised amounts/dates.

The `SUPERSEDED` status is important — during reconciliation or an audit, you need to know what the schedule was at each point in the loan's history, not just the current version.

## Section 7: Architecture & Cross-Cutting Concerns

**Q21. How would you structure the services in a loan origination and repayment system?**
A: At 5 YOE level, the expected answer is a bounded-context decomposition that separates concerns without over-engineering into dozens of microservices:

- **Application Service** — handles application CRUD, state transitions, document uploads, and the application state machine. Produces `ApplicationSubmitted`, `ApplicationApproved`, `ApplicationDisbursed` events.
- **Underwriting Service** — consumes `ApplicationSubmitted`. Calls bureau APIs, runs the rule engine, calls the ML scoring model, and produces a credit decision. Publishes `CreditDecisionMade`.
- **Loan Management Service** — the ledger owner. Creates the loan record, generates the amortization schedule at disbursement, owns all loan lifecycle state. Consumes `ApplicationDisbursed`.
- **Collection Service** — consumes the amortization schedule. Runs the daily scheduler for EMI presentation, handles NACH submissions and return processing, manages retry logic, and owns the delinquency state machine.
- **Repayment Ledger** — a double-entry ledger (as described in the wallet/ledger design) specifically for loan repayments. Every payment posts journal entries. Provides the authoritative record of what was collected and how it was allocated.
- **Notification Service** — consumes events from all of the above and sends borrower-facing communications (EMI reminders, approval letters, payment receipts).
- **Reporting Service** — read model that materializes views for NPA reports, collection efficiency, portfolio health metrics, and regulatory filings.

**Q22. How do you handle the disbursement of a loan atomically — the loan is created and funds are transferred?**
A: Disbursement is a two-system write: the Loan Management Service creates the loan record (and amortization schedule), and the payment system transfers funds to the borrower's bank account. These are in different systems and can't be wrapped in a single DB transaction. Use the Outbox pattern:

1. In a single DB transaction: INSERT `loans` row, INSERT `amortization_schedules`, INSERT an `outbox_events` row of type `LOAN_DISBURSEMENT_REQUESTED`.
2. An outbox worker polls the outbox table and publishes the event to a queue (Kafka topic: `loan-disbursements`).
3. A disbursement worker consumes the event, calls the payment gateway to initiate the bank transfer (IMPS/NEFT in India).
4. The payment gateway returns success via webhook; the worker updates `loans.status` from `PENDING_DISBURSEMENT` to `ACTIVE` and records the disbursement transaction in the ledger.
5. If the gateway call fails, the outbox event stays in the queue and retries — idempotency on the payment gateway call (using `loan_id` as the idempotency key) ensures the transfer isn't duplicated.

This guarantees: if the loan record was created, the disbursement will eventually be attempted. If disbursement ultimately fails after retries, a human review queue is triggered and the loan is set to `DISBURSEMENT_FAILED`.

**Q23. How do you ensure the amortization schedule and the ledger stay consistent over the loan's lifetime?**
A: This is the core correctness invariant: at any point in time, `sum of outstanding principal per amortization schedule = outstanding principal in the ledger`. Enforce it through:

- **Single writer** — only the Loan Management Service modifies the amortization schedule and posts the corresponding ledger entries. No other service writes to either. This eliminates the class of bugs where two services independently update related records.
- **Atomic updates** — when a repayment is posted, the amortization schedule row update and the ledger journal entry INSERT happen in the same DB transaction.
- **Daily reconciliation job** — compare `SUM(closing_principal of last PAID installment per loan)` from the amortization schedule against `outstanding_principal` derived from the ledger for every active loan. Any discrepancy is a P1 data integrity alert.
- **Event sourcing for schedule changes** — every recalculation (prepayment, restructuring) publishes an event with the before and after state. The audit log is derived from these events, not mutable in the tables.

**Q24. What are the key regulatory and compliance requirements that directly affect system design in India?**
A: Several RBI regulations have direct engineering implications:

- **KYC (Know Your Customer)** — mandatory identity verification before disbursement. Must store KYC documents with access logs (who accessed, when). V-KYC (video KYC) requires storing video recordings with a defined retention period.
- **Fair Practices Code** — lenders must disclose all fees, charges, and the effective interest rate (APR) to the borrower before agreement signing. The system must generate and preserve a Key Fact Statement (KFS) document as a PDF with a digital timestamp.
- **IRAC norms** — the DPD and NPA classification logic must exactly match RBI's IRAC guidelines. Regulatory examiners will audit your classification methodology.
- **Credit Bureau Reporting** — all lenders must report loan performance to credit bureaus (CIBIL, Experian) monthly in a defined format (Metro 2 / CIBIL format). The reporting pipeline must be reliable and auditable — missed or erroneous reporting is a regulatory violation.
- **Data Localization** — borrower financial data must be stored within India (per RBI PA/PG guidelines). Cloud architecture choices (regions, replication) must comply.
- **Grievance Redressal** — RBI mandates a 30-day resolution window for borrower complaints. The system must log every complaint, track resolution status, and escalate if SLA is breached — this is a product requirement, not just a business nicety.

**Q25. How do you design the interest accrual engine for a loan portfolio of 1 million active loans?**
A: Interest accrual is the daily process of computing and recognizing the interest earned on each loan's outstanding principal. At scale, a naive row-by-row approach is too slow. Design:

- **Daily batch, not real-time** — accrual runs once per night after business hours. The accrual date is deterministic: `outstanding_principal × (annual_rate / 365)` per loan per day.
- **Set-based SQL, not row-by-row** — compute accruals for all active loans in a single SQL query using a join between `loans` and today's outstanding principal, and bulk-INSERT the results into an `interest_accrual_ledger` table. Avoid cursors or application-level loops.
- **Partition by accrual date** — the accrual table is partitioned by `accrual_date`. Each night's run inserts into today's partition. Queries for a date range hit only the relevant partitions.
- **Idempotent runs** — the accrual job checks for existing rows for today's date before inserting. Running it twice on the same day is a no-op, not a double-accrual.
- **Skip NPA loans** — RBI's IRAC norms require that interest on NPA loans is not recognized as income ("income de-recognition"). The accrual job must exclude `loans` where `status = 'NPA'` — this is both a regulatory requirement and a significant correctness concern.

## Section 8: Scenario Questions

**Q26. "A borrower says they paid their EMI but our system still shows it as overdue. Walk through how you'd debug this."**
A: This is a payment reconciliation problem. Investigation path:
1. Check the borrower's claim — what payment reference did they get? (UTR number for bank transfers, transaction ID for UPI/NACH).
2. Check the `collection_attempts` table for that loan and due date — was a debit attempt made? What was the status?
3. If the attempt shows SUCCESS but the schedule row is still PENDING, there's a webhook processing failure — the payment gateway delivered the success webhook but our handler failed to update the schedule. Check the webhook processing logs and the `outbox_events` or dead-letter queue for that transaction ID.
4. If no attempt was made, check if the NACH mandate was active and registered correctly at the time.
5. Cross-reference with the payment gateway's transaction report — pull the settlement report for that date and search for the borrower's account/transaction.
6. If the payment is confirmed on the gateway side but missing in the ledger, it's a missed webhook — manually trigger the webhook handler with the idempotency key to replay the credit without duplication.
7. If the payment never reached the gateway, the borrower's bank may have the record — ask for a bank statement to confirm.

Document every step. In a regulated lending environment, the resolution must be logged with timestamps and actor IDs for the grievance audit trail.

**Q27. "Design the EMI collection scheduler for 2 million active loans, where each loan has a different due date."**
A: Naive approach (scan all 2M loans every day) is too slow and fragile. Better design:

- **Partition due dates into daily queues** — at loan origination, publish a recurring job configuration into a scheduler (e.g., a `scheduled_tasks` table or a cron-based workflow engine like Temporal). Each loan's EMI due dates are pre-registered as future tasks.
- **Temporal / Conductor for workflow orchestration** — use a durable workflow engine. Each loan has a workflow instance that sleeps until the next due date, wakes up, attempts collection, handles retries with backoff, and sleeps again. Temporal handles the state persistence and retry mechanics, eliminating the need for a custom scheduler.
- **Batch grouping by due date** — if using a simpler architecture: one DB query per morning fetches `WHERE due_date = today AND status = 'PENDING'`. Paginate results into batches of 1,000 and publish each batch to a Kafka topic. A consumer group of N workers processes batches in parallel, presenting NACH debits for each.
- **Rate limiting against the payment gateway** — NPCI has throughput limits on NACH presentations. The producer must respect these limits (e.g., max 10,000 debit instructions per minute) using a token bucket or a controlled Kafka consumer lag.
- **Idempotency on debit presentation** — each NACH presentation attempt must carry a unique presentation ID derived from `(loan_id, installment_number, attempt_number)`. If the scheduler crashes and restarts, re-processing the same Kafka message presents the same debit instruction, and NPCI's deduplication rejects the duplicate rather than double-debiting.

## Core Domain Formulas

| Calculation | Formula |
|--- |--- |
| EMI (reducing balance) | `P × r × (1+r)^n / ((1+r)^n − 1)` where r = monthly rate, n = months |
| EMI (flat rate) | `(P + P × annual_rate × years) / total_months` |
| Per diem interest | `Outstanding Principal × Annual Rate / 365` |
| Foreclosure amount | `Outstanding Principal + Accrued interest to date + Overdue + Penalty` |
| DTI ratio | `(Existing EMIs + Proposed EMI) / Monthly income × 100` |
| Outstanding principal | `Initial Principal − SUM(principal_component of all PAID installments)` |
| Interest for installment n | `Opening Principal of installment n × monthly rate` |
