# Design a Fraud Detection System — Interview Q&A (5 YOE Level)

---

## Section 1: Requirements & Scope

**Q1. What are the functional requirements of a fraud detection system?**
A: Core functional requirements:
- **Real-time transaction scoring** — evaluate every payment/login/account-creation event and return a fraud score or decision (ALLOW / REVIEW / BLOCK) within a latency budget (typically < 100ms for payments, < 300ms for account actions).
- **Rule engine** — a configurable layer of deterministic rules (velocity checks, blocklists, geo-anomalies) that can be updated without redeployment.
- **ML scoring** — a model that produces a continuous risk score (0–1) from behavioral and contextual features.
- **Feature store** — pre-computed and real-time features that both the rule engine and ML model consume.
- **Case management** — a queue of REVIEW-flagged transactions for human analysts to investigate and label (feeds back into model training).
- **Feedback loop** — confirmed fraud/legitimate labels from analysts and chargebacks flow back into feature computation and model retraining.
- **Blocklist / allowlist management** — manage lists of known bad actors (IPs, device fingerprints, card BINs, user IDs) and trusted entities.

**Q2. What are the non-functional requirements that make fraud detection uniquely hard?**
A:
- **Latency** — real-time scoring must complete within the payment processing window (< 100ms P99). The feature store and model inference are on the critical path; any slow feature retrieval kills the SLO.
- **Throughput** — must handle peak transaction volume (e.g., 10,000 TPS for a large merchant) without degradation.
- **Precision vs. recall trade-off** — false positives (blocking legitimate transactions) lose revenue and anger customers. False negatives (missing fraud) cause financial loss and chargebacks. The acceptable trade-off is a business decision, not a technical one, and changes over time.
- **Concept drift** — fraud patterns evolve continuously. A model trained three months ago becomes stale as fraudsters adapt. The system must support rapid retraining and deployment.
- **Explainability** — disputed decisions must be explainable to analysts, customers, and regulators ("why was my transaction blocked?"). Black-box model scores alone are insufficient.
- **Adversarial robustness** — fraudsters actively probe and adapt to detection systems. Rules and models must be kept confidential; the system must detect probing behavior itself.

**Q3. What is the core precision-recall trade-off and how does the business set the threshold?**
A: At a given decision threshold:
- **Precision** — of all transactions flagged as fraud, what fraction was actually fraud? Low precision = too many legitimate transactions blocked (customer friction, revenue loss).
- **Recall** — of all actual fraud, what fraction was caught? Low recall = fraud slips through (financial loss, chargebacks).

The threshold is a business decision driven by unit economics: compare the cost of a false positive (blocked legitimate transaction — average order value lost, customer churn risk) against the cost of a false negative (fraud loss + chargeback fee, typically $20–$100 per dispute). Most businesses accept a lower threshold (higher recall) during fraud spikes and raise it (higher precision) during normal periods. The ML model's score is fixed; the **threshold applied to that score** is the lever the business turns.

The critical path (everything above the Kafka line) must complete in < 100ms. Everything below is async and does not block the transaction.

**Q5. How do you keep the critical scoring path under 100ms?**
A: Every component on the critical path must be optimized:
- **Feature store reads** — Redis for sub-millisecond feature retrieval. Pre-compute everything that can be pre-computed (user historical features) so the real-time path only needs a single multi-key `MGET`.
- **Rule engine** — pure in-memory evaluation; rules loaded into application memory on startup and refreshed periodically. No DB round-trip per rule evaluation.
- **ML inference** — model served locally in the same process (ONNX Runtime embedded) or via a co-located gRPC sidecar. Remote HTTP calls to a model server add 20–50ms; avoid on the hot path.
- **Parallelism** — feature fetch, rule evaluation, and model inference can partially overlap. Fetch features and start rule evaluation simultaneously; pass features to model as they arrive.
- **Timeouts with fallback** — if any component exceeds its timeout budget (e.g., feature store takes > 30ms), proceed with available features and a conservative fallback score rather than blocking indefinitely.

## Section 3: Feature Store

**Q6. What is a feature store, and why does fraud detection need one?**
A: A feature store is a centralized system that manages the definition, computation, storage, and serving of ML features. Fraud detection specifically needs one because:
- **Training-serving skew** — the features used to train a model must be identical to the features served at inference time. Without a feature store, teams independently compute features for training (batch, on historical data) and serving (real-time), introducing subtle differences that degrade model performance in production.
- **Feature reuse** — a feature like "number of transactions by this user in the last 1 hour" is useful to the rule engine, the ML model, and the analyst dashboard. The feature store computes it once and serves it everywhere.
- **Point-in-time correctness** — when generating training data, features must reflect what was known *at the time of the transaction*, not current values. A feature store with temporal query support prevents future data leakage into training.

**Q7. What are the two storage layers in a feature store and what does each hold?**
A:
- **Online store (Redis / DynamoDB)** — serves real-time feature values for inference. Holds the *latest* value of each feature per entity (user, card, device, merchant). Optimized for single-entity point reads with < 5ms P99. Only the current value matters; no history needed here.
- **Offline store (Cassandra / S3 + Parquet)** — serves historical feature values for model training. Holds time-series of feature values per entity with timestamps, enabling point-in-time queries. Optimized for batch scans, not point reads.

The feature compute pipeline writes to both simultaneously: new feature values are pushed to Redis (online) and appended to the offline store (historical record).

**Q8. What are the most important feature categories for fraud detection?**
A:

| Category | Examples | Freshness needed |
|--- |--- |--- |
| **Velocity** | txn count / user in last 1h, 24h, 7d; spend / card in last 1h | Seconds |
| **Behavioral** | avg txn amount for user, typical merchant categories, usual txn hour | Minutes to hours |
| **Device** | device fingerprint seen before, device age, VPN/proxy/Tor flag | Seconds (lookup) |
| **Geo** | distance from last txn ("impossible travel"), country risk score, IP geolocation mismatch vs billing address | Seconds |
| **Network / graph** | shared device across multiple accounts, card used on multiple accounts, account age | Minutes |
| **Merchant** | merchant fraud rate, merchant category risk, new merchant flag | Hours |
| **Card / payment method** | BIN country vs IP country, prepaid card flag, card age, prior chargebacks on card | Seconds (lookup) |

Velocity features are the most powerful and most time-sensitive — they must be computed and updated in near-real-time.

**Q9. How do you compute velocity features in real-time?**
A: Three approaches, from simplest to most scalable:

1. **Redis counters with TTL** — for each entity (user_id, card_id), maintain a sorted set of transaction timestamps. At scoring time, count entries within the window. Atomic and fast, but expensive for long windows on high-volume entities.

```
ZADD user:{user_id}:txns <unix_timestamp> <txn_id>
ZCOUNT user:{user_id}:txns <now - 3600> <now>   -- count in last hour
EXPIRE user:{user_id}:txns 86400                 -- keep 24h of data
```

2. **Approximate sliding window with Redis** — use a fixed-window counter that approximates a sliding window: weighted average of current and previous window count. 50x less memory than storing every event, with < 1% error for uniform traffic.

3. **Stream processing (Flink / Kafka Streams)** — for complex multi-dimensional velocity (e.g., "distinct merchants visited by this card in the last hour across all users"), use a stateful stream processor that maintains rolling aggregations and pushes results to the feature store.

**Q10. What is training-serving skew, and how does the feature store prevent it?**
A: Training-serving skew occurs when a feature is computed differently during model training than during live inference, causing the model to behave unexpectedly in production. Common causes:
- Training uses `AVG(amount)` over all historical data; serving computes `AVG(amount)` over a 30-day rolling window.
- Training uses filled-in null values (mean imputation); serving returns raw nulls.
- Training pipeline uses future data (leakage): computing "user's fraud rate" includes transactions that happened *after* the training example.

Prevention via feature store: define features in a single canonical definition (a feature spec). The same code path computes the feature for both training (applied to historical timestamps) and serving (applied to the current moment). Point-in-time joins in the offline store ensure training queries only use data available at each historical transaction's timestamp.

## Section 4: Rule Engine

**Q11. What is a rule engine in a fraud detection system?**
A: A configurable layer of deterministic, human-readable rules evaluated against transaction context before (or alongside) ML scoring. Rules produce hard outcomes (BLOCK) or signals that feed into the final decision. Examples:
- `IF card_country != ip_country AND amount > 500 → BLOCK`
- `IF user_txn_count_1h > 10 → REVIEW`
- `IF device_fingerprint IN blocklist → BLOCK`
- `IF merchant_id IN high_risk_merchants AND amount > 1000 → REVIEW`
- `IF card_bin IN known_test_bins → ALLOW` (bypass scoring for test transactions)

**Q12. Why do you need a rule engine alongside an ML model? Can't the model do everything?**
A: Rules and models serve different purposes and complement each other:
- **Explainability** — rules produce human-readable reason codes ("blocked: card country mismatch"). Model scores alone are opaque to customers and regulators who demand explanations.
- **Reaction speed** — when a new fraud pattern is discovered (e.g., a specific BIN range is compromised), a rule can be deployed in minutes. Retraining and deploying a model takes hours to days.
- **Hard constraints** — some decisions must always hold regardless of model score. A card on a regulatory sanctions list must always be blocked, not scored at 0.9 and reviewed.
- **Rare event handling** — ML models struggle with extremely rare fraud patterns seen only a few times in training data. Rules handle these explicitly.
- **Trust and auditability** — risk and compliance teams can audit rules directly; they cannot audit a gradient boosted tree with 500 features.

**Q13. How do you design the rule engine for operational flexibility?**
A: Key design decisions:
- **Rules as data, not code** — store rules in a DB or config system (not hardcoded). An analyst or risk operator can update a threshold without an engineer and a deployment.
- **Rule DSL** — define a simple expression language for rules: `field op value AND/OR ...`. Avoid Turing-complete scripting (no arbitrary code execution) to prevent injection attacks and ensure auditability.
- **Rule priority / ordering** — rules are evaluated in priority order; a `BLOCK` from a high-priority rule short-circuits remaining evaluation. Define clear precedence between rule types.
- **Hot reload** — the scoring service polls for rule changes (or subscribes to a config stream) and reloads without restart. Rule updates take effect within seconds, not the next deployment.
- **Shadow mode** — new rules can run in shadow mode: they evaluate and log their decisions but don't affect the actual outcome. This lets you validate a rule's impact before enabling it.

```typescript
interface FraudRule {
  id:         string;
  name:       string;
  expression: string;    // "user_txn_count_1h > 10 AND amount > 500"
  action:     'BLOCK' | 'REVIEW' | 'ALLOW' | 'SCORE_BOOST';
  scoreAdjust?: number;  // for SCORE_BOOST: add N to ML score
  priority:   number;
  enabled:    boolean;
  shadowMode: boolean;
}
```

**Q14. What is a blocklist and how do you serve it efficiently on the hot path?**
A: A blocklist is a set of known bad entity identifiers (IP addresses, device fingerprints, card BINs, user IDs, email domains) that should always trigger BLOCK or REVIEW. At scoring throughput (10k TPS), you can't do a DB lookup per transaction per blocklist.

Efficient serving options:
- **Bloom filter in memory** — for large blocklists (millions of IPs), a Bloom filter gives probabilistic membership check in O(1) with no false negatives and a tunable false positive rate (~0.1%). Store in application memory; refresh from DB every few minutes.
- **Redis SET** — for smaller, frequently updated blocklists (thousands of entries), `SISMEMBER` in Redis is fast enough and gives exact results.
- **Hash set in application memory** — for stable, small lists (a few thousand entries), load into a `Set<string>` at startup and refresh periodically. Zero network round-trip.

## Section 5: ML Model

**Q15. What ML approaches work well for fraud detection?**
A: In rough order of prevalence in production:
- **Gradient Boosted Trees (XGBoost, LightGBM)** — the industry workhorse. Excellent tabular data performance, handles missing values natively, fast inference (< 5ms for a 500-tree model), relatively interpretable (feature importances, SHAP values). Most production fraud systems run a GBM at their core.
- **Logistic Regression** — used as a baseline, for interpretability requirements, or as a component in ensemble. Fully explainable; fast inference; poor on non-linear feature interactions.
- **Neural networks (wide & deep, tabular transformers)** — better at capturing complex interactions and learning from raw behavioral sequences. Higher accuracy ceiling but slower inference, harder to explain, more expensive to train and serve.
- **Graph neural networks** — for network/relationship features (shared devices, money mule rings). Emerging; complex to operationalize.
- **Anomaly detection (Isolation Forest, Autoencoders)** — useful for detecting novel patterns unseen in training. High false positive rate as a standalone; most effective as a signal in an ensemble.

In practice: GBM as the primary model, logistic regression for explainability and regulatory reporting, anomaly detection as a secondary signal.

**Q16. How do you handle the extreme class imbalance in fraud detection?**
A: Fraud is typically 0.01%–0.5% of transactions. A naive model that predicts "legitimate" for every transaction achieves 99.9% accuracy but 0% recall — useless. Techniques:
- **Resampling** — oversample the minority (fraud) class (SMOTE) or undersample the majority class to balance the training set. Use carefully — oversampling synthetic fraud can teach the model to classify synthetic patterns rather than real ones.
- **Class weights** — assign higher misclassification cost to fraud samples in the loss function (`scale_pos_weight` in XGBoost). Most practical approach.
- **Threshold tuning** — train on imbalanced data but tune the decision threshold on a held-out set to hit the target precision/recall trade-off. The model outputs a calibrated probability; the threshold is a separate business decision.
- **Evaluation metrics** — never use accuracy. Use precision-recall AUC (PR-AUC), F1 at the operating threshold, and KS statistic. PR-AUC is more informative than ROC-AUC under severe imbalance.

**Q17. How do you serve the ML model within the 100ms latency budget?**
A: Options, from lowest to highest latency:
- **Embedded inference (ONNX Runtime in-process)** — export the model to ONNX format; run inference in the same Node.js/Python/Java process using ONNX Runtime bindings. Latency: 1–10ms for a GBM. Zero network overhead. Best choice for GBMs and logistic regression.
- **Co-located gRPC sidecar** — run a TensorFlow Serving or Triton Inference Server container alongside the scoring service on the same host. Latency: 5–20ms. Good for larger models (neural nets) that need GPU or require Python runtime.
- **Remote model server** — call a centralized model serving cluster via gRPC. Latency: 20–80ms depending on network. Only viable if other parts of the pipeline leave enough budget. Not recommended for the primary fraud model on the critical path.

For a GBM with 100–500 trees and 50–100 features, ONNX embedded inference is the clear choice: 2–5ms, no network dependency, no additional infrastructure.

**Q18. How does model retraining work, and how often should it happen?**
A: The feedback loop:

```
New transactions (scored in real-time)
        │
        ▼
Labels arrive (days to weeks later):
  - Chargeback confirmed → fraud label
  - Analyst review → fraud / legitimate label
  - No chargeback after N days → legitimate (proxy label)
        │
        ▼
Training pipeline:
  1. Join transactions with labels (point-in-time feature values from offline store)
  2. Retrain model on sliding window (e.g., last 90 days of labeled data)
  3. Evaluate on holdout set (last 7 days, not seen in training)
  4. Shadow deploy: run new model alongside current; compare score distributions and KPIs
  5. Promote if metrics improve; rollback if degradation
        │
        ▼
Model registry (MLflow) → versioned model artifact
        │
        ▼
Deploy to scoring service (hot-swap ONNX model file without restart)
```

Retraining cadence depends on concept drift rate: weekly for high-drift environments (consumer payments), monthly for slower-changing patterns (B2B). Monitor score distribution shift daily — a significant shift in the fraction of high-score transactions is an early drift signal without waiting for chargeback labels (which lag 30–90 days).

## Section 6: Decision Logic & Explainability

**Q19. How do you combine rule engine output and ML score into a final decision?**
A: A layered decision model:

```
1. Hard BLOCK rules (sanctions, known stolen cards) → immediate BLOCK; skip ML
2. Hard ALLOW rules (internal test cards, trusted enterprise accounts) → immediate ALLOW; skip ML
3. Rule-based SCORE_BOOST → adjust ML score up/down based on rule signals
4. ML model score (0.0–1.0)
5. Apply thresholds:
     score >= 0.85 → BLOCK
     score >= 0.50 → REVIEW
     score <  0.50 → ALLOW
6. Velocity circuit breaker: regardless of score, REVIEW if user has > N blocked
   transactions in the last 24h (prevents persistent probing)
```

Thresholds (0.85, 0.50) are configurable per merchant, transaction type, and channel — a card-present transaction at a physical terminal has a different risk profile than a card-not-present e-commerce transaction.

**Q20. How do you generate human-readable explanations for decisions?**
A: Multi-layer explanation strategy:
- **Rule engine**: rules that fired are natural language reason codes: `CARD_COUNTRY_MISMATCH`, `VELOCITY_LIMIT_EXCEEDED`, `DEVICE_ON_BLOCKLIST`. These are always explainable.
- **ML model**: use SHAP (SHapley Additive exPlanations) values computed alongside inference. SHAP assigns each feature a contribution to the score: "amount contributed +0.15, user_age_days contributed −0.08, txn_count_1h contributed +0.22." The top 3–5 features by absolute SHAP value become the explanation.
- **Caveats on SHAP in production**: SHAP computation for a GBM adds 5–20ms. Precompute SHAP for REVIEW and BLOCK decisions (where explanation is needed); skip for ALLOW (no explanation required, and the latency saving matters). Store the SHAP values alongside the transaction record for analyst use.
- **Regulatory compliance**: some jurisdictions (EU's GDPR Article 22, US FCRA) require that automated decision explanations be provided to consumers on request. The stored SHAP values + fired rules satisfy this requirement.

## Section 7: Feedback Loop & Model Health

**Q21. What is concept drift in fraud detection and how do you detect it?**
A: Concept drift is the change over time in the statistical relationship between features and the fraud label — fraudsters adapt their behavior to evade detection, new payment channels introduce new patterns, and seasonal variation shifts transaction distributions. Types:
- **Gradual drift** — the fraud population slowly shifts over weeks/months. Detected by tracking model score distribution and chargeback rate weekly.
- **Sudden drift** — a new fraud campaign starts overnight (e.g., a large card database leak). Detected by anomaly detection on the score distribution or a sudden spike in REVIEW/BLOCK rates.

Detection metrics to monitor:
- **Population Stability Index (PSI)** on the score distribution: PSI > 0.2 indicates significant drift; trigger retraining.
- **Chargeback rate on ALLOW decisions**: rising chargeback rate means fraud is slipping through — model recall is degrading.
- **REVIEW rate**: if suddenly 30% of transactions are going to REVIEW (up from 5%), either a new fraud pattern triggered rules or score distribution shifted.

**Q22. How do you deal with delayed labels in fraud detection?**
A: Fraud labels (chargebacks) arrive 30–90 days after the transaction. This creates a labeling lag that complicates training:
- **Proxy labels** — transactions older than N days with no chargeback are labeled legitimate. This introduces false negatives (some fraud slips through without a chargeback), but provides a usable training signal quickly.
- **Analyst labels** — analysts reviewing REVIEW-queue transactions provide labels within hours/days. These are high-quality but cover only a sample (the transactions that scored high enough to be reviewed, creating selection bias).
- **Label calibration** — models trained on proxy labels will underestimate fraud base rate. Calibrate predicted probabilities using Platt scaling or isotonic regression on a labeled holdout set.
- **Embargo period** — when evaluating model performance, use an embargo between the training cutoff and the evaluation window to account for labeling lag: train on transactions up to day T-90, evaluate on day T-90 to T-30 (where labels are mostly complete), test on T-30 to T (recent, partial labels, with caveats).

## Section 8: Scenario Questions

**Q23. "A new fraud pattern emerges: fraudsters are creating accounts with stolen SSNs and making one large purchase before detection. Design the detection response."**
A: Multi-layer response:
1. **Immediate rule**: add a rule targeting the pattern's observable signals — account age < 7 days AND amount > $500 AND first transaction for this user → REVIEW. Deploy in minutes via rule hot-reload.
2. **Feature engineering**: create a feature `account_age_days` if not already present; add `is_first_transaction` boolean. Push to feature store.
3. **Graph signal**: if multiple fraudulent accounts share device fingerprints or IPs, add a graph feature: `device_shared_account_count`. Accounts sharing a device with a fraud-labeled account get elevated scores.
4. **Model retrain**: once 50–100 labeled fraud examples of this pattern are collected (from analyst review), retrain the model with the new features included. The model generalizes the pattern; the rule handles it until then.
5. **Retrospective sweep**: run the new rule retrospectively on accounts created in the last 30 days that made a large first purchase. Flag for analyst review — there may be undetected fraud already in the system.

**Q24. "Your fraud model is blocking 8% of legitimate transactions (false positive rate too high). How do you diagnose and fix it?"**
A: Systematic diagnosis:
1. **Segment the false positives** — which features are driving high scores on legitimate transactions? Pull SHAP values for false positives; cluster them. Are they concentrated in specific merchant categories, geographies, or device types?
2. **Check for data quality issues** — is a feature returning stale or null values that the model interprets as high-risk? A null `device_age_days` being imputed as 0 (new device) when the feature store lookup failed would inflate scores for all affected transactions.
3. **Check threshold** — is the 8% FPR at a threshold that's too low? Raise the BLOCK threshold; move ambiguous cases to REVIEW rather than BLOCK (wrong transactions block a sale; REVIEW only delays it).
4. **Feature distribution shift** — has a recent product change altered how existing features are computed (e.g., a new mobile app version changed device fingerprinting format)? Training data features no longer match serving features → training-serving skew.
5. **Remediation options** (in order of speed):
   - Raise the BLOCK threshold (minutes, no retraining).
   - Add an ALLOW rule for the most-impacted legitimate segment (hours).
   - Retrain with corrected feature pipeline (days).
   - Re-engineer features causing the skew (days to weeks).

**Q25. "How would you design the fraud system to handle a flash fraud event — 10,000 fraudulent transactions in 5 minutes using a newly compromised card database?"**
A: A flash event challenges both detection and response:

**Detection:**
- Velocity at the card BIN level — if 500 cards from the same BIN are transacting simultaneously, that's an anomalous signal even if each individual card looks normal. Add BIN-level velocity as a feature: `bin_txn_count_5min`.
- Network signal — many transactions sharing IP ranges or device fingerprints across different user accounts.
- Anomaly detection layer — an isolation forest or autoencoder trained on normal transaction volumes per BIN will fire an anomaly alert even before the ML model's fraud labels confirm it.

**Response (automated):**
- Automated circuit breaker: if `bin_txn_count_5min` exceeds 3 standard deviations above baseline, auto-escalate the threshold for all transactions on that BIN to REVIEW.
- Alert on-call fraud team with the BIN range and transaction count; human decides whether to add a hard BLOCK rule on the BIN.

**Response (operational):**
- Bulk rule deployment: add `card_bin IN (compromised_bins)` → BLOCK within minutes.
- Retrospective review: transactions from the last 10 minutes on affected BINs that were already ALLOWED get flagged for manual review and potential proactive refund.
- Coordinate with PSP: request that the PSP flag these BINs on their end as well; dual-layer protection.

**Tip for the interview:** Fraud detection is one of the few system design questions that tests ML systems design, real-time systems, and operational thinking simultaneously. Lead by acknowledging the precision-recall trade-off as a business decision, not a technical one — interviewers notice. The specific things that separate 5 YOE answers: knowing why training-serving skew is the #1 silent killer of fraud model performance and how the feature store prevents it; explaining the layered decision model (hard rules first, ML second, thresholds third); and articulating why rules and ML are complementary rather than competing. If you can explain concept drift and delayed labels in the same breath, you've covered the production ML angle that most candidates miss.
