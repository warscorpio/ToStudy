# Design a Wallet / Ledger System (Double-Entry Bookkeeping, Balance Consistency) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is double-entry bookkeeping, and why does financial software use it?**
A: Double-entry bookkeeping is an accounting principle where every financial transaction records *two* entries: a debit to one account and a credit to another, always of equal value. The fundamental invariant is:

`Sum of all debits = Sum of all credits` (across the entire ledger, always)

Financial software uses it because it provides two things single-entry systems ("just update a balance column") can't:
- **Built-in error detection** — if debits don't equal credits after any operation, something is wrong. The books don't balance, and that's an immediate signal.
- **Full auditability** — every state change is an immutable record. You can reconstruct *any* account's balance at *any* point in history by replaying the ledger. With a mutable balance column, history is lost the moment you update it.

**Q2. What is the difference between a ledger and a wallet in system design terms?**
A: A **ledger** is the core append-only record of all financial transactions — it's the source of truth. It never mutates; entries are only ever added. A **wallet** is an abstraction on top: a user-facing entity that has a *derived* balance, computed from the ledger entries belonging to that account. In practice:
- The ledger stores rows like: `(txn_id, debit_account, credit_account, amount, timestamp, description)`.
- The wallet balance is `SELECT SUM(credits) - SUM(debits) FROM ledger WHERE account_id = ?` — or a materialized/cached version of that query.

Separating the two means balance is always derivable from the ledger. If a balance cache gets corrupted, you can always recompute it. If you only stored a balance column, corruption is unrecoverable without an audit trail.

**Q3. What are the core entities in a wallet/ledger system?**
A: At minimum:
- **Account** — represents a wallet, a liability account, a revenue account, or an asset account. Has an `account_id`, `type`, `currency`, `owner_id`, and `created_at`. Does *not* store a balance column (derived from ledger).
- **Transaction** — a financial event: a transfer, a deposit, a fee, a refund. Has a `transaction_id`, `status`, `type`, `created_at`, and metadata. A transaction groups one or more journal entries that must atomically succeed together.
- **Journal Entry** — the individual debit or credit line. Has `entry_id`, `transaction_id`, `account_id`, `direction` (DEBIT or CREDIT), `amount`, and `currency`. A transaction always has at least two journal entries that sum to zero.
- **Currency** — amounts should always be stored in the smallest denomination (cents for USD, paise for INR) as integers, never as floating-point numbers.

**Q4. Why must amounts never be stored as floating-point numbers?**
A: Floating-point arithmetic (IEEE 754) introduces rounding errors that accumulate across operations. `0.1 + 0.2 = 0.30000000000000004` in most languages. In a financial system, even a fraction-of-a-cent error compounded across millions of transactions leads to material discrepancies during reconciliation — and regulatory problems. Always store monetary amounts as integers in the smallest indivisible unit (cents, paise, satoshis). Perform all arithmetic in integers. Only convert to a decimal representation at display time, using fixed-point formatting, never floating-point math.

## Section 2: Schema Design

**Q5. Walk me through a production-grade schema for a double-entry ledger.**
A:

```sql
-- Accounts: wallets, liability pools, revenue buckets, etc.
CREATE TABLE accounts (
    account_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id        UUID NOT NULL,           -- user, merchant, or system entity
    type            TEXT NOT NULL,           -- 'USER_WALLET', 'REVENUE', 'LIABILITY', 'FEE_POOL'
    currency        CHAR(3) NOT NULL,        -- ISO 4217: 'USD', 'INR', 'EUR'
    status          TEXT NOT NULL DEFAULT 'ACTIVE',   -- 'ACTIVE', 'FROZEN', 'CLOSED'
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT valid_type CHECK (type IN ('USER_WALLET','REVENUE','LIABILITY','FEE_POOL'))
);

-- Transactions: the business event that caused entries
CREATE TABLE transactions (
    transaction_id  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    type            TEXT NOT NULL,           -- 'DEPOSIT', 'WITHDRAWAL', 'TRANSFER', 'FEE', 'REFUND'
    status          TEXT NOT NULL DEFAULT 'PENDING',  -- 'PENDING', 'POSTED', 'REVERSED', 'FAILED'
    idempotency_key TEXT UNIQUE NOT NULL,    -- caller-supplied deduplication key
    currency        CHAR(3) NOT NULL,
    amount          BIGINT NOT NULL,         -- in smallest unit (cents); always positive
    initiated_by    UUID,                    -- user or system that triggered this
    metadata        JSONB,                   -- reference IDs, notes, external IDs
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    posted_at       TIMESTAMPTZ,
    CONSTRAINT positive_amount CHECK (amount > 0)
);

-- Journal entries: immutable debit/credit lines
CREATE TABLE journal_entries (
    entry_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    transaction_id  UUID NOT NULL REFERENCES transactions(transaction_id),
    account_id      UUID NOT NULL REFERENCES accounts(account_id),
    direction       TEXT NOT NULL,           -- 'DEBIT' or 'CREDIT'
    amount          BIGINT NOT NULL,         -- always positive; direction field carries the sign
    currency        CHAR(3) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT positive_entry_amount CHECK (amount > 0),
    CONSTRAINT valid_direction CHECK (direction IN ('DEBIT','CREDIT'))
);

-- Indexes for common query patterns
CREATE INDEX idx_journal_entries_account_id ON journal_entries(account_id, created_at DESC);
CREATE INDEX idx_journal_entries_transaction_id ON journal_entries(transaction_id);
CREATE INDEX idx_transactions_idempotency ON transactions(idempotency_key);
```

**Q6. Why is `idempotency_key` a critical column on the transactions table?**
A: In distributed systems, network failures, retries, and timeouts mean the same request may arrive multiple times. Without an idempotency key, a retry of a $100 transfer could result in two $100 transfers. The `idempotency_key` is a unique identifier the caller generates and sends with every request — a UUID or hash of the request parameters. The server uses a `UNIQUE` constraint on this column: the first request INSERTs a new transaction; a retry hits the unique constraint, and the server returns the original transaction's result without creating a new one. This is table-stakes for any financial API: without it, you have a double-spend vulnerability.

**Q7. How do you compute an account balance from the journal entries?**
A: Balance is derived by summing credits and subtracting debits for a given account:

```sql
SELECT
    account_id,
    SUM(CASE WHEN direction = 'CREDIT' THEN amount ELSE -amount END) AS balance
FROM journal_entries
WHERE account_id = $1
  AND currency = $2;
```

For a wallet, a CREDIT increases the balance (money coming in) and a DEBIT decreases it (money going out). The convention is account-type-dependent — in standard accounting, the credit/debit rules flip for assets vs liabilities — but for a simplified wallet system, the above convention is consistent and sufficient.

**Q8. What is a balance snapshot (materialized balance) and when do you need one?**
A: Computing balance from a full table scan of `journal_entries` is fine for accounts with thousands of entries, but becomes slow for accounts with millions of entries (high-frequency trading accounts, payment processors). A balance snapshot is a periodically written summary row:

```sql
CREATE TABLE account_balance_snapshots (
    account_id      UUID NOT NULL REFERENCES accounts(account_id),
    currency        CHAR(3) NOT NULL,
    balance         BIGINT NOT NULL,
    as_of_entry_id  UUID NOT NULL,    -- last journal entry included in this snapshot
    as_of_time      TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (account_id, currency, as_of_time)
);
```

To get the current balance: take the latest snapshot balance, then sum only the journal entries with `entry_id > as_of_entry_id`. This reduces the scan from millions of rows to only the delta since the last snapshot. The snapshot is derived data — if it's ever wrong, you can recompute it by replaying the full journal. It must never be a mutable "live" balance that's updated in place.

## Section 3: Consistency & Atomicity

**Q9. How do you ensure a transfer between two accounts is atomic?**
A: Wrap the entire operation in a database transaction. A transfer from Account A to Account B for $50 requires:
1. INSERT into `transactions` table (status = PENDING).
2. INSERT debit journal entry: Account A, DEBIT, $50.
3. INSERT credit journal entry: Account B, CREDIT, $50.
4. UPDATE `transactions` status to POSTED.

All four operations must succeed or all must roll back. If step 3 fails, step 2 must be undone — you can't have a debit without a matching credit. Using a single database transaction with `BEGIN` / `COMMIT` guarantees this. The invariant to verify before committing: sum of all entry amounts where direction=DEBIT equals sum where direction=CREDIT for this transaction.

```sql
BEGIN;

INSERT INTO transactions (transaction_id, type, status, idempotency_key, currency, amount)
VALUES ($txn_id, 'TRANSFER', 'PENDING', $idem_key, 'USD', 5000);

INSERT INTO journal_entries (transaction_id, account_id, direction, amount, currency)
VALUES ($txn_id, $account_a, 'DEBIT', 5000, 'USD');

INSERT INTO journal_entries (transaction_id, account_id, direction, amount, currency)
VALUES ($txn_id, $account_b, 'CREDIT', 5000, 'USD');

UPDATE transactions SET status = 'POSTED', posted_at = now()
WHERE transaction_id = $txn_id;

COMMIT;
```

**Q10. How do you prevent an account from going negative (overdraft prevention)?**
A: Check the balance before posting the debit — but naively, this check-then-act pattern has a race condition. If two concurrent withdrawals both read the balance, both see sufficient funds, and both proceed, you get a double-spend. Two safe approaches:

- **Pessimistic locking (`SELECT FOR UPDATE`)** — lock the account row (or a balance row) before reading the balance. Concurrent transactions queue behind the lock. Safe, simple, and correct; expensive under high contention.

```sql
BEGIN;
SELECT balance FROM account_balances WHERE account_id = $1 FOR UPDATE;
-- If balance >= amount, proceed; else ROLLBACK
INSERT INTO journal_entries ...
COMMIT;
```

- **Optimistic concurrency control (OCC)** — read the current balance and a version number without locking. At commit time, verify the version hasn't changed. If it has (another transaction committed in between), retry. Good for low-contention accounts; suffers under high contention (many retries).

- **Database constraint** — the most robust approach: maintain a `balance` column (alongside the ledger, updated atomically within the same transaction) and add a `CHECK (balance >= 0)` constraint. The DB enforces the invariant and rejects the transaction if it would go negative, eliminating the race entirely.

**Q11. What is the "check-then-act" race condition, and how does it apply to wallet systems?**
A: The check-then-act (TOCTOU — Time Of Check To Time Of Use) race condition occurs when you read a value, make a decision based on it, and then act — but the value may have changed between the read and the act. In a wallet: two concurrent withdrawal requests for $80 both read a balance of $100, both conclude "$80 ≤ $100, proceed," both debit $80, leaving the balance at -$60. The fix is to ensure the check and the act are atomic — either via database-level locking (`SELECT FOR UPDATE`), a compare-and-swap on a versioned row, or a database constraint that rejects the violating write regardless of what the application believed.

**Q12. How would you handle a transfer that spans two different databases or services (distributed transaction)?**
A: Single-DB ACID transactions don't work across service boundaries. Options ranked by complexity:

- **Avoid it where possible** — keep both accounts in the same database. Most wallet systems can achieve this by co-locating user accounts in one DB, even at large scale.
- **Saga pattern (compensating transactions)** — break the transfer into a sequence of local transactions, each with a compensating action that undoes it on failure. Transfer $50 from A to B: (1) debit A locally (local txn); (2) credit B remotely (local txn on service B); if step 2 fails, run the compensating action: credit A back. Eventual consistency; no distributed lock; requires careful handling of partial failures and idempotency.
- **Two-Phase Commit (2PC)** — a coordinator asks all participants to prepare (lock resources), then commits if all agreed. Strongly consistent but slow, operationally fragile (coordinator failure leaves participants locked), and rarely used in modern high-throughput systems.
- **Outbox pattern** — write the debit and an outbox event atomically in one local DB transaction. A separate process reads the outbox and delivers the event to the downstream service, which credits the target account. Guarantees at-least-once delivery with idempotency on the consumer side.

For most wallet systems, the Saga + Outbox combination is the industry-standard answer.

## Section 4: Idempotency & Failure Handling

**Q13. A transfer request succeeds on the server but the client gets a network timeout and retries. How do you handle this without double-crediting?**
A: The idempotency key is the answer. The client generates a unique key before making the request and sends it in every retry attempt. Server behavior:
1. First request: check `transactions` table for this idempotency key. Not found → execute the transfer, insert the transaction row with the key, return success.
2. Retry: check for the key → found → return the same transaction result without executing anything again.

The `UNIQUE` constraint on `idempotency_key` is the enforcement mechanism — even under concurrent retries, only one INSERT can succeed; the second hits a constraint violation and the server returns the existing result. The idempotency key typically has a TTL (e.g., 24 hours) after which it can be reclaimed, since retrying a days-old request is a different operation.

**Q14. What is a "pending" transaction status, and when does a transaction stay pending?**
A: A transaction starts as PENDING when the intent is recorded but the funds haven't fully moved. This happens in multi-step flows:
- **Pre-authorization** — an e-commerce charge holds $100 (PENDING) at checkout, then either captures (POSTED) when the order ships or releases (REVERSED/EXPIRED) if cancelled.
- **External payment processing** — a bank transfer is PENDING until the ACH network settles (1–2 business days).
- **Two-leg transfers in flight** — in a saga, the debit leg is PENDING until the credit leg confirms.

Pending transactions should typically not be counted in the available balance as spendable funds but should be shown to the user. The available balance = posted balance − pending debits. This prevents spending funds that are earmarked for an in-flight transaction.

**Q15. How do you handle reversals and refunds in a ledger system?**
A: In a double-entry system you never update or delete journal entries — they are immutable. A reversal creates a *new* transaction that mirrors the original with debits and credits swapped:

Original transfer: DEBIT User A $50, CREDIT User B $50.
Reversal: CREDIT User A $50, DEBIT User B $50.

The reversal transaction references the original via metadata (e.g., `reversal_of: original_txn_id`). The original entries remain in the ledger; the net effect after both transactions is zero movement. This preserves the full audit trail — you can see exactly when the original transfer happened and when it was reversed. The same pattern applies to refunds (reversing a payment) and chargebacks (forced reversal by the card network).

## Section 5: Concurrency & Performance

**Q16. What is a "hot account" problem, and when does it appear?**
A: A hot account is one that receives an extremely high rate of concurrent transactions — a platform's central fee pool, a marketplace's escrow account, or a viral merchant's account. All concurrent transactions that touch it contend for the same row lock (`SELECT FOR UPDATE` on the account), serializing throughput. At high volume (thousands of TPS), this becomes a severe bottleneck: lock wait times dominate, timeouts increase, and the account becomes a throughput ceiling for the entire system.

**Q17. What are the patterns for solving the hot account problem?**
A: Several approaches, often combined:

- **Account sharding (sub-accounts)** — split the hot account into N "shard" accounts (e.g., 100 sub-accounts for the fee pool). Each transaction picks a shard randomly and debits/credits that shard. Balance queries sum across all shards. This distributes lock contention across N rows instead of one, multiplying throughput by ~N.
- **Async credit posting** — instead of crediting the hot account synchronously in the transaction, write a credit event to a queue (Kafka). A background worker batches the queue events and posts aggregated credits to the hot account periodically. Individual transactions are faster; hot account updates are batched.
- **CRDT-style counters** — in some architectures, credits are purely additive to sharded partitions that are periodically compacted. Each partition is lock-free for writes and totals are computed at read time.
- **Deferred settlement** — accept that the hot account's balance is eventually consistent, and only reconcile precisely at settlement time. Appropriate for internal accounts (fee pools, revenue accounts) where real-time precision isn't required.

**Q18. How do you scale read throughput for balance queries without hitting the primary database?**
A: Several techniques:
- **Read replicas** — route balance queries to a read replica. Acceptable when slight replication lag is tolerable (user sees their balance as of a few seconds ago). Not acceptable for pre-debit balance checks where stale data could allow overdrafts.
- **Materialized balance cache (Redis)** — maintain a pre-computed balance in Redis, updated within the same transaction that posts journal entries (via Lua script or transaction pipeline). Reads are O(1) from cache; writes update both the DB and cache atomically. Must handle cache invalidation on failure (the DB is always the source of truth; cache is a warm copy).
- **Balance snapshots** — as described in Q8; reduces the DB scan from all time to just recent entries.
- **CQRS (Command Query Responsibility Segregation)** — separate write model (ledger, journal entries) from read model (materialized balance view, transaction history). The read model is updated asynchronously via events from the write path. Gives you independent scaling of reads and writes.

## Section 6: Reconciliation & Auditing

**Q19. What is reconciliation in a financial system, and how does double-entry make it tractable?**
A: Reconciliation is the process of verifying that two independent records of the same financial activity agree. In a wallet system, you reconcile:
- **Internal ledger vs external payment processor** — every card charge Stripe records should have a matching journal entry. Discrepancies indicate a failed webhook, a missed credit, or a processing error.
- **Per-account balance check** — for every account: `SUM(credits) - SUM(debits) = displayed balance`. Any mismatch is a data integrity bug.
- **Global zero-sum check** — in a closed double-entry system, `SUM of all journal entry amounts where direction=DEBIT = SUM where direction=CREDIT` across the *entire* ledger. If these don't match, money has been created or destroyed — a critical bug.

Double-entry makes this tractable because every dollar is traceable: you can always ask "where did this money come from and where did it go?" and follow the chain of entries.

**Q20. How would you build a reconciliation job for a wallet system?**
A: A daily (or continuous) reconciliation job should:

1. **Global balance check** — `SELECT SUM(CASE WHEN direction='DEBIT' THEN amount ELSE -amount END) FROM journal_entries` should equal zero for a fully closed system (all money that left one account entered another).
2. **Per-account balance consistency** — compare `SUM(credits - debits)` from journal entries against any cached/materialized balance. Flag any discrepancy above a threshold (e.g., non-zero difference means a bug, not just rounding).
3. **External reconciliation** — fetch the previous day's transactions from Stripe/Adyen/bank via their reporting APIs. For each external transaction, verify a matching journal entry exists in the ledger. Produce a discrepancy report: unmatched external records (missed credits) and unmatched internal records (phantom transactions).
4. **Pending transaction cleanup** — flag transactions stuck in PENDING status beyond their expected settlement window for manual review.
5. **Emit metrics** — reconciliation discrepancy count as a counter, reconciliation job duration as a gauge, unmatched records as a gauge. Alert on any non-zero discrepancy.

**Q21. How do you handle timezone and timestamp consistency in a financial ledger?**
A: All timestamps must be stored in UTC, never in local time. Mixing timezones in financial records causes reconciliation nightmares — a transaction that appears to happen on "Dec 31" in one timezone and "Jan 1" in another creates cross-year discrepancy in monthly/annual reports. Use `TIMESTAMPTZ` in Postgres (which always stores in UTC internally). Application code should always work in UTC and only convert to local time for display purposes. For financial reporting periods ("give me all January transactions"), always define the period in UTC boundaries and document the convention explicitly.

## Section 7: Scenario / System Design Style Questions

**Q22. "Design the data model for a P2P money transfer feature. User A sends $50 to User B, the platform takes a $1 fee."**
A: This requires three journal entries in one atomic transaction:

Accounts involved: `user_a_wallet`, `user_b_wallet`, `platform_fee_pool` (a system account).

```
Transaction: P2P_TRANSFER, amount=$50, status=POSTED

Journal Entries:
1. DEBIT  user_a_wallet    $51   (total debited from sender: transfer + fee)
2. CREDIT user_b_wallet    $50   (recipient receives $50)
3. CREDIT platform_fee_pool $1   (platform earns $1 fee)

Invariant check: total DEBIT ($51) = total CREDIT ($50 + $1) ✓
```

The $51 debit from User A equals the $50 credit to User B plus the $1 credit to the fee pool. The books balance. All three entries are inserted in one DB transaction — if any fails, none are committed. Note: User A's wallet is checked for a balance of ≥ $51 before proceeding (not $50 — the fee comes out of the sender's funds too).

**Q23. "A webhook from Stripe fails halfway through processing — we credited the user but never marked the transaction as POSTED. What's your recovery strategy?"**
A: This is why the `status` field exists. Recovery strategy:

1. **Idempotent webhook processing** — the webhook handler first checks if this Stripe event ID has already been processed (using the idempotency key = Stripe event ID). If yes, return 200 immediately without re-processing.
2. **Transactional status update** — credit the journal entry and update the transaction status to POSTED in the *same* DB transaction. If the DB transaction succeeds, both happen; if it fails, neither does. There's no state where credits exist without a POSTED status.
3. **Stuck PENDING detection** — a reconciliation job finds transactions in PENDING status longer than the expected settlement window (e.g., > 5 minutes for a Stripe webhook that should arrive in seconds). These are flagged for automated retry or manual review.
4. **Stripe reconciliation** — the daily Stripe reconciliation job catches any Stripe-side success not reflected in the internal ledger — these surface as unmatched external records and are resolved by replaying the credit.

The idempotency key on the webhook event ID is the critical guard — it ensures even if the webhook fires 5 times (Stripe retries on non-200 responses), only one credit is issued.

**Q24. "How would you design the system to support multiple currencies in the same wallet?"**
A: Currency is a first-class dimension, not an afterthought. Design choices:
- **Per-currency balance** — an account doesn't have one balance; it has one balance per currency it holds. The `journal_entries` table has a `currency` column; balance queries always filter by currency. Never mix currencies in a single sum.
- **No implicit conversion** — cross-currency transfers require an explicit FX transaction that records the exchange rate at the moment of conversion: DEBIT source_account in USD, CREDIT target_account in EUR, with the exchange rate stored in transaction metadata. The FX rate is immutable on the transaction record — you need to know exactly what rate was applied for audit purposes.
- **Currency-safe constraint** — the double-entry invariant must hold *per currency*: total DEBIT in USD = total CREDIT in USD. Don't mix currencies in a single transaction's entries.
- **Display** — amounts displayed to users are always rendered with the correct decimal places and symbol for their currency, using ISO 4217 metadata (USD has 2 decimal places; JPY has 0; KWD has 3).

**Q25. "Your senior engineer says 'we should just use a balance column and update it in place — it's simpler.' How do you push back?"**
A: I'd acknowledge the simplicity argument is real — a single `UPDATE accounts SET balance = balance - 50` is much simpler to write than a full double-entry system. Then I'd explain what you give up:

- **No audit trail** — once the balance is updated, the history is gone. You can't answer "what was this user's balance on March 15th?" or "where did this $200 come from?" without a separate audit log (which is just a ledger by another name).
- **Reconciliation is impossible** — if the balance column gets corrupted (bug, failed partial transaction, direct DB edit), you have no way to recompute the correct value. With a ledger, you replay entries.
- **Double-spend race conditions are harder to prevent** — with a balance column you need careful locking on every update. With a ledger + constraint, the database enforces it structurally.
- **Regulatory requirements** — most financial regulators (PCI DSS, SOC 2, banking regulators) require immutable audit trails. A mutable balance column doesn't satisfy this.

The counter-offer: a ledger-first design doesn't have to be complex to start. A minimal `transactions` and `journal_entries` table with a simple balance query is only slightly more work than a balance column — and it's the foundation you don't have to rip out later when auditors ask for history.

**Q26. "Walk me through handling a high-volume flash sale where 50,000 users try to purchase a limited item simultaneously — each deducting from a single merchant's account."**
A: This is the hot account problem at its most extreme. 50,000 concurrent transactions all trying to lock the same merchant wallet row will serialize completely, leading to massive lock wait times and timeouts. Strategy:

1. **Inventory as a separate concern** — decouple inventory (how many items remain) from the financial transfer. Use a Redis atomic decrement (`DECR`) for inventory reservation — it's lock-free and handles 50,000 concurrent decrements cleanly. Only proceed to the financial debit after a successful inventory reservation.
2. **Async financial posting** — for the financial leg, accept the purchase synchronously (reserve inventory via Redis), post a PENDING transaction immediately, and push the actual journal entry creation to a queue (Kafka). A worker pool drains the queue and posts journal entries asynchronously. The merchant sees the funds in their balance within seconds, not milliseconds.
3. **Sharded merchant account** — if the merchant's account is the hot account for debits (e.g., a refund scenario), shard it as described in Q17.
4. **Batch settlement** — if strict per-transaction real-time settlement isn't required (often it isn't for marketplace transactions), aggregate all flash sale debits and post a single batched journal entry per settlement cycle.

The key insight: not every business operation needs to be a synchronous, strongly-consistent financial posting. Real-time reservation + async posting + eventual reconciliation handles the throughput ceiling while maintaining correctness.

## Quick Reference: Core Invariants to Enforce

| Invariant | Where to Enforce | How |
|--- |--- |--- |
| Debits = Credits per transaction | Application layer + DB check | Sum entries before commit; `ASSERT sum == 0` |
| No negative balances | DB constraint + app layer | `CHECK (balance >= 0)` on balance table; `SELECT FOR UPDATE` before debit |
| Amounts are positive integers | DB constraint | `CHECK (amount > 0)` on journal_entries; `BIGINT` column type |
| No currency mixing in a transaction | Application layer | Validate all entries share the same currency before inserting |
| Idempotency on every write | DB unique constraint | `UNIQUE (idempotency_key)` on transactions |
| Immutable journal entries | DB permissions + app design | No UPDATE/DELETE on journal_entries; append-only; DB role without UPDATE privilege |
| All timestamps in UTC | Application convention + DB type | `TIMESTAMPTZ`; never store `TIMESTAMP WITHOUT TIME ZONE` |

## Common Failure Modes to Know

| Failure | Root Cause | Prevention |
|--- |--- |--- |
| Double-spend | Concurrent balance reads without locking | `SELECT FOR UPDATE`; DB constraint; OCC |
| Phantom credit on retry | Missing idempotency key | `UNIQUE (idempotency_key)` on transactions |
| Floating-point rounding discrepancy | Storing amounts as `FLOAT` / `DECIMAL` | Always use `BIGINT` in smallest currency unit |
| Inconsistent balance after partial failure | Non-atomic multi-step write | Wrap all writes in a single DB transaction |
| Undetected reconciliation drift | No global zero-sum check | Daily `SUM(all entries)` job; alert on non-zero |
| Hot account deadlock | All TPS contending on one row | Account sharding; async posting; Redis reservation |
| Lost history after refund | Mutating original entries | Always create new reversal transaction; never update entries |
| Timezone discrepancy in reporting | Mixing UTC and local time | Store and compute everything in UTC; convert only for display |

---

**Tip for the interview:** Wallet/ledger design questions are deceptively broad — they can go deep on schema, on distributed systems (saga, outbox, 2PC), on concurrency (hot accounts, SELECT FOR UPDATE), or on correctness (reconciliation, idempotency). The best signal you can give is that you've thought about the *failure modes*, not just the happy path. Every senior interviewer has a war story about a double-spend bug, a float rounding discrepancy, or a balance corruption from a non-atomic update. Showing you've reasoned through those failure modes — before being asked — is what separates a 5 YOE answer from a junior one.
