# DNS-Based Load Balancing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is DNS-based load balancing, at a conceptual level?**
A: It's the practice of using the DNS resolution step itself — what IP (or IPs) a given domain name resolves to — as a mechanism for distributing client traffic across multiple servers, regions, or data centers. Instead of all clients always resolving a name to the same single address, the authoritative DNS layer can return different answers (different IPs, different orderings, different subsets) to different queries, so that by the time any individual client reaches the actual connection step, it's already been pointed toward one of several possible destinations — distributing the *initial connection target* before any traffic has actually moved.

**Q2. How does DNS-based load balancing fundamentally differ from L4/L7 load balancing?**
A: An L4/L7 load balancer sits in the actual data path — every request passes through it, so it has real-time visibility into connection state, in-flight request counts, and backend health, and can make a fresh, informed routing decision *per request* (or per connection). DNS-based load balancing sits entirely outside the data path: it only ever influences which IP a client resolves to at the moment of resolution, has no visibility into what happens after that (no awareness of in-flight requests, no per-request granularity), and that resolution result gets cached and reused by the client for the TTL duration (and often longer, due to caching/pinning behavior), meaning DNS's "decision" can remain in effect long after the underlying conditions that motivated it have changed. DNS-based load balancing is best understood as a coarse, first-pass routing mechanism, not a substitute for a real load balancer.

**Q3. Why would anyone use DNS-based load balancing at all, given these limitations relative to a proper load balancer?**
A: Because the problems it's good at solving are problems an in-path load balancer fundamentally can't solve by itself: getting a client's traffic to the *nearest region or data center in the first place*, before any single load balancer instance could possibly be in the path (a load balancer in one region has no way to redirect a client to a different region before the client's first packet even arrives). DNS-based mechanisms operate one layer earlier than any in-path device can — they influence which data center/region a client targets at all, which is exactly the "coarse, first pass" role described in Q2. It's typically combined with, not substituted for, real load balancing once traffic actually arrives within a chosen region.

**Q4. What are the main techniques that fall under "DNS-based load balancing"?**
A: DNS round robin (multiple A/AAAA records for the same name, returned and consumed in rotating fashion); GeoDNS (returning different records based on the querying resolver's apparent geographic location); latency-based routing (returning records based on measured network performance to different regions, rather than pure geography); weighted DNS routing (returning records in proportions controlled by configured weights, for gradual traffic shifting); and DNS-based health-check failover (automatically removing unhealthy endpoints from the response set or switching to a designated failover record). These are often combined — e.g., latency-based routing with health-check failover layered on top.

## Section 2: DNS Round Robin

**Q5. How does DNS round robin work mechanically?**
A: A single domain name has multiple A (or AAAA) records configured, each pointing at a different server's IP. The authoritative nameserver returns all of them in its response, often rotating the order on successive queries; resolvers and clients then pick one (commonly the first in the list, or via their own internal logic) to actually connect to. Across many independent clients and queries over time, this produces a statistical tendency toward roughly even distribution across the set of IPs — though, as covered in Q6, it's a loose tendency, not a controlled guarantee.

**Q6. What are the core limitations of DNS round robin as a load balancing mechanism?**
A: Three main ones: (1) **no health awareness** — if one of the backend IPs goes down, plain round robin has no built-in way to detect that and will keep handing that dead IP to some fraction of clients until someone manually intervenes (unless paired with a separate health-check feature, Q14); (2) **client/resolver stickiness** — once a client resolves and caches one IP, it stays pinned to it for the TTL duration (and, for long-lived connections, often well beyond that), so it doesn't benefit from "round robin" again until it re-resolves; (3) **uneven real-world distribution** — large upstream resolvers (e.g., a major ISP serving thousands of users from one shared cache entry) can skew the effective distribution, since many downstream clients behind that one resolver all get routed to whichever IP that resolver happened to cache, rather than each client getting its own independent rotation.

**Q7. Is the order in which multiple records are returned something you can rely on or control precisely?**
A: Not reliably. Some authoritative nameservers rotate the order on each query; some don't. Some resolvers respect and preserve that order; others re-shuffle it themselves; some clients always just pick the first entry regardless of order. There's no protocol-level guarantee of even distribution baked into DNS round robin — it's a best-effort, statistical pattern across many independent clients and queries rather than a deterministic, controllable load-balancing decision the way an L7 load balancer's algorithm is.

## Section 3: GeoDNS and Latency-Based Routing

**Q8. How does GeoDNS work, and what is it trying to approximate?**
A: GeoDNS configures the authoritative nameserver to return different records depending on the apparent geographic location of the querying resolver (inferred from the resolver's IP via geolocation data) — a user querying from Europe gets records pointing at a European data center; a user querying from Asia gets records for an Asia-Pacific data center. It's trying to approximate "route the user to whichever deployment will give them the best network experience," using geographic proximity as a reasonably good, but imperfect, proxy for actual network latency/path quality.

**Q9. Why is geographic proximity an imperfect proxy for actual network performance?**
A: Physical distance doesn't always correlate cleanly with network path quality — undersea cable routing, peering arrangements between specific ISPs and providers, and regional internet infrastructure quality can all mean a user geographically close to a data center experiences worse latency to it than a user who's geographically farther away but better-peered. This is the same caveat that applies to Anycast/BGP routing decisions more generally — geographic and network-topological distance aren't the same thing, even though they're often correlated.

**Q10. How does latency-based routing differ from GeoDNS, and what does it require to work?**
A: Instead of inferring location from IP geolocation and assuming proximity implies good performance, latency-based routing (offered by some managed DNS providers, e.g., Route 53's latency-based routing policy) uses *actual measured network latency data* between different regions/data centers and the querying resolver's network, routing to whichever region the provider's measurements show as genuinely fastest for that resolver's network — a more accurate, but more provider-specific and infrastructure-dependent, mechanism, since it depends on the DNS provider having accumulated and maintaining real performance measurement data across many network paths.

**Q11. What's a key caveat with both GeoDNS and latency-based routing, related to who's actually being measured?**
A: The routing decision is made based on the *resolver's* apparent location/network performance, not the *client's* directly — DNS doesn't have visibility into the actual end client at all, only the resolver that's relaying the query on the client's behalf (per the recursive/iterative distinction). For most consumer setups (a user's ISP resolver, geographically close to the user) this approximation is reasonably accurate. It breaks down more visibly when a client uses a resolver that's geographically distant from them (e.g., a privacy-focused public resolver, or a corporate VPN routing DNS queries through a centralized resolver far from where the actual user sits) — in that case, the DNS-layer routing decision reflects the resolver's location/performance, which may have little to do with the actual client's.

## Section 4: Weighted DNS Routing

**Q12. What is weighted DNS routing and what problem does it specifically solve?**
A: Multiple records for the same name are configured with different relative weights, and the DNS provider distributes the proportion of responses (and, roughly, the resulting proportion of traffic) according to those weights — e.g., 95% of responses point at the current production environment, 5% point at a new environment being gradually validated. The core use case is **gradual traffic migration**: shifting load incrementally between two environments (a new region, a new cloud provider, a new infrastructure version) at the DNS layer, with the ability to dial the percentage up or down as confidence in the new target grows, before the migration is fully committed.

**Q13. What limitations does weighted DNS routing have that a weighted routing policy at the L7 load balancer layer doesn't?**
A: The same caching/stickiness limitation that applies to DNS round robin generally (Q6) applies here: each client effectively "locks in" to whichever weighted record they happened to resolve, for the duration of their cache (and any connection pinning beyond that), so the actual observed traffic split converges toward the configured weight only gradually, smoothed out across many independent clients re-resolving over time — it's not a live, continuously-adjustable per-request split the way an L7 load balancer's weighted algorithm can be, where every single request can independently respect the current weight in real time. DNS-layer weighting is coarser and slower to converge, particularly right after a weight change, since already-cached clients don't immediately reflect the new ratio.

## Section 5: Health Checking and Failover

**Q14. Does DNS itself have any native concept of backend health?**
A: No — this is a frequent point of confusion worth being precise about. The DNS protocol itself has no concept of "is this server currently healthy," no built-in heartbeat, no connection-level awareness of anything happening after a resolution is handed out. "DNS-based health checking" is a separate, provider-specific feature bolted on top of DNS, not a capability inherent to the protocol.

**Q15. How does DNS-based health-check failover actually work, given that DNS itself has no health awareness?**
A: Managed DNS providers that offer this feature (Route 53, Cloudflare, NS1, among others) run their own independent infrastructure that periodically probes the actual backend endpoints (HTTP health checks, similar in spirit to what an L7 load balancer does) entirely *outside* the DNS protocol itself, and use the results to decide what to include in DNS responses — automatically excluding an unhealthy endpoint's record from the rotation, or switching to a designated failover/backup record, without requiring any DNS-protocol-level health concept at all. It's effectively active monitoring infrastructure run alongside DNS, whose output happens to be expressed as DNS record changes.

**Q16. What determines how fast a DNS-based health-check failover actually takes effect for end users?**
A: Two independent factors stacked together: how quickly the health-check infrastructure itself detects the unhealthy state (governed by the provider's check interval and failure threshold configuration — e.g., "3 consecutive failed checks at 10-second intervals" implies at least ~30 seconds of detection lag), and then how quickly the resulting DNS record change propagates to already-caching clients (governed by TTL, per the TTL guide's discussion of pre-change procedures and the general principle that TTL is a maximum, not a guarantee). Both factors need to be tuned together for a meaningful failover SLA — a fast health check paired with a long TTL still produces slow effective failover, and vice versa.

**Q17. What's a scenario where DNS-based failover alone would be insufficient, even with aggressive health-check and TTL tuning?**
A: Clients holding long-lived connections established before the failover event — those connections are pinned to whatever IP they originally resolved and won't re-resolve mid-connection regardless of how fast the DNS-layer failover technically completed; they only pick up the new value on their next fresh resolution (reconnect, restart, or explicit re-resolution logic). This is why DNS-based failover is typically described as a coarse, first layer of resilience, best combined with application/client-level resilience (retry logic, connection-level health awareness, periodic re-resolution) and, within each region, a real L4/L7 load balancer's own health-check-driven failover for fine-grained, near-instant backend rerouting that doesn't depend on any DNS caching behavior at all.

## Section 6: Limitations and When DNS-Based Load Balancing Isn't Enough

**Q18. Summarize the core structural limitations of DNS-based load balancing as a category, independent of which specific technique is used.**
A: It operates entirely outside the actual data path — no visibility into in-flight requests, connection state, or real-time backend load; its decisions are cached by clients and resolvers, meaning a "current" routing decision can keep being honored well after the conditions that motivated it have changed; it has no native health concept (anything resembling health awareness is a separate, bolted-on provider feature); it can't make per-request decisions, only per-resolution decisions, which get reused for potentially many subsequent requests/connections; and large intermediate resolvers can distort the effective distribution relative to what was configured. All of these point toward the same conclusion: it's a coarse, slow-reacting, first-pass mechanism, not a substitute for in-path, real-time load balancing.

**Q19. Given these limitations, what's the typical, recommended architecture pattern combining DNS-based and in-path load balancing?**
A: Use DNS-based routing (GeoDNS, latency-based, weighted, health-check-aware) as the coarse first layer — getting a client's traffic to the right *region or data center* in the first place. Once traffic arrives at that region's entry point, hand off to a proper L4/L7 load balancer for the actual fine-grained, real-time, health-check-aware distribution across that region's backend fleet. This layered approach plays to each mechanism's strength: DNS for the decision that genuinely can't be made any other way (which region, before the client has even connected anywhere), and an in-path load balancer for everything that benefits from real-time, per-request visibility and control, which DNS structurally cannot provide.

**Q20. In what situations is DNS round robin alone (no health checking, no weighting) still a reasonable, sufficient choice?**
A: When the backends behind it are roughly interchangeable, failure is rare or quickly self-correcting (e.g., the backends are themselves resilient enough that a brief period of some clients hitting a momentarily degraded one isn't a serious problem), traffic volume and client count are large enough that the statistical tendency toward even distribution (Q5) is good enough in practice, and there isn't a hard requirement for fast, automatic failover. It's a reasonable, low-complexity choice for relatively low-stakes or already-resilient setups; it becomes a poor choice the moment failover speed, even distribution accuracy, or backend health awareness genuinely matter.

## Section 7: Security and Reliability Considerations

**Q21. How does DNS-based load balancing's reliance on caching create a specific operational risk during an active incident?**
A: If you're trying to route traffic away from a failing region or backend during an active incident, the speed of that mitigation is bounded by the TTL of the records involved — if those records happen to have a long TTL (perhaps because no one anticipated needing fast failover for them), you can correctly update the DNS configuration to redirect traffic, and a meaningful fraction of clients will continue hitting the failing infrastructure anyway, for up to the old TTL's duration, regardless of how quickly you reacted operationally. This is why infrastructure with any realistic failover scenario should have its TTL pre-configured short *in advance*, rather than discovering during an incident that the TTL is too long to allow fast DNS-driven mitigation.

**Q22. What risk does relying entirely on DNS-based health checking (without independent monitoring) introduce?**
A: You're trusting the DNS provider's health-check infrastructure as your sole signal of backend health for routing purposes — if that health-check system itself has an outage, a misconfiguration, or simply checks an endpoint/path that doesn't accurately represent true application health (e.g., checking a lightweight `/health` endpoint that stays up even when the actual application logic behind it is broken), you can end up with DNS continuing to route traffic to backends that are, by any meaningful measure, not actually serving requests correctly — a false-healthy state that DNS-layer routing alone has no way to catch. Independent, application-aware monitoring and alerting (not solely relying on the DNS provider's health-check signal) remains important even when DNS-based failover is in place.

**Q23. How does DNS-based traffic management interact with DNS cache poisoning risk?**
A: The mechanism is the same as any DNS spoofing concern — DNS-based load balancing's entire value proposition rests on resolvers genuinely receiving and honoring the authoritative answers you intend, so a successfully poisoned cache (forged records injected into a resolver) can redirect traffic to an attacker-controlled destination just as effectively as it could for a simple A record, with the added wrinkle that DNS-based load balancing setups often involve multiple records/policies that an attacker forging just one entry point into could potentially exploit. DNSSEC (covered in the general DNS security material) remains the relevant mitigation for ensuring the authenticity of whichever record a given routing policy ultimately returns.

## Section 8: Scenario-Based Questions

**Q24. "You're designing the DNS strategy for a global SaaS product with regional deployments in North America, Europe, and Asia. How would you approach it?"**
A: Use GeoDNS or latency-based routing as the coarse first layer, directing users to their nearest/best-performing regional deployment's entry point, ideally backed by DNS-level health checking so that if an entire region becomes unhealthy, DNS automatically stops directing users there — with TTL tuned to balance failover propagation speed against query volume on the authoritative infrastructure. Within each region, once traffic arrives at that region's entry point, hand off to a proper L4/L7 load balancer for the actual fine-grained, real-time distribution across that region's backend fleet, since DNS's caching/TTL limitations make it a poor fit for the kind of per-request, health-aware decisions an in-path load balancer handles well. This is the standard "DNS for coarse regional routing, in-path LB for fine-grained in-region distribution" layered pattern.

**Q25. "Your team wants to gradually shift 5% of production traffic to a new infrastructure version using DNS, increasing the percentage over the next two weeks if things look healthy. Walk through the approach and its limitations."**
A: Configure weighted DNS routing with the new environment initially at a low weight (e.g., 5%) relative to the existing environment, then incrementally increase that weight over the migration window as confidence builds, monitoring error rates/performance on the new environment at each step before increasing further. The key limitation to flag explicitly: because of DNS caching, the *observed* traffic split won't track the configured weight in real time — clients that resolved before a weight change stay on whatever they resolved until their cache (and any connection pinning) expires, so especially right after each weight adjustment, the actual traffic split lags behind the configured one and only converges gradually. For genuinely fine-grained, real-time-responsive traffic shifting (e.g., wanting to instantly halt the rollout the moment an error spike is detected), an L7 load balancer's weighted/canary routing, layered within the region traffic actually reaches, would respond far faster than adjusting DNS weights and waiting for caches to catch up.

**Q26. "During an incident, your team needs to redirect all traffic away from a failing region as fast as possible. The relevant DNS record currently has a 1-hour TTL. What do you do, and what should change going forward?"**
A: In the moment: update the DNS configuration to remove or fail the unhealthy region's record immediately, but be transparent that this won't be instantaneous for already-caching clients — some meaningful fraction of traffic will continue reaching the failing region for up to the remainder of that 1-hour TTL window, regardless of how fast you react. If the architecture allows it, lean more heavily on whatever in-path/L7 mechanisms can react faster within the still-reachable failing region (e.g., having that region's own load balancer or application layer reject/redirect requests, if that's architecturally feasible) as a faster-acting complement to the DNS-layer fix. Going forward: this incident is a clear signal that any record involved in a realistic failover scenario should have a short TTL configured *proactively*, well before any incident, specifically so that DNS-driven mitigation during a future incident isn't bottlenecked by a TTL that was never tuned with failover speed in mind.

**Q27. "Monitoring shows traffic isn't evenly distributed across the three backend IPs returned via DNS round robin for a service — one IP is receiving a disproportionate share. What would you investigate, and would you recommend changing approach entirely?"**
A: First check whether the imbalance is explained by resolver-level aggregation — a small number of large upstream resolvers serving many downstream clients from one shared, infrequently-refreshed cache entry can skew the effective distribution well beyond what individual per-client randomness would predict (Q6). Also verify the authoritative nameserver is actually rotating record order on each query, since some configurations don't rotate by default, biasing toward whichever IP consistently appears first. If the application genuinely needs more precise, controllable distribution (rather than the loose statistical tendency DNS round robin provides), the broader recommendation would be to move the actual load-balancing responsibility to a real L4/L7 load balancer sitting behind a single stable DNS name — letting DNS round robin's structural imprecision stop being a load-distribution mechanism at all, and instead just be a name that points at infrastructure designed to load balance precisely.

**Q28. "A new engineer proposes relying solely on DNS round robin across application server IPs as the entire load balancing solution for a customer-facing production service, to avoid the cost/complexity of a managed load balancer. How would you respond?"**
A: Walk through the structural gaps this would leave open: no health awareness (a dead server's IP keeps being handed out to some fraction of clients until someone manually notices and removes it — there's no automatic detection or rerouting); the distribution itself is only a loose statistical tendency, not a controlled, even split, and can be visibly skewed by large intermediate resolvers; and clients/connections that have already resolved are pinned to their chosen IP regardless of that server's subsequent health, meaning even after manually fixing the DNS records, already-connected clients won't benefit until they reconnect. For a customer-facing production service, these gaps generally translate into real, visible reliability problems (slow-to-notice outages, uneven load causing some servers to be overloaded while others sit idle) that a managed load balancer (even a relatively low-complexity one) would directly solve via real-time health checking and even, controllable distribution — making the cost/complexity trade-off worth revisiting rather than accepting DNS round robin as the complete solution.

**Q29. "You suspect a competitor or bad actor might be exploiting your DNS-based GeoDNS configuration to redirect a specific region's users to a degraded backend. How would you investigate and what would confirm or rule this out?"**
A: Independently query your authoritative nameservers directly (bypassing any intermediate resolver) from vantage points simulating the affected region, to confirm exactly what your own DNS infrastructure is genuinely configured to return for that region — ruling out a configuration mistake on your own side first. If the authoritative answer is correct but affected users are still seeing a different, wrong destination, that points toward resolver-level cache poisoning or interception somewhere between your authoritative servers and those specific users (rather than your GeoDNS policy itself being compromised), since a correctly-answering authoritative server combined with a wrong client-observed result implicates a layer in between. DNSSEC validation status would be a relevant data point here too — if DNSSEC is enabled and validating resolvers are rejecting forged responses while non-validating resolvers in the affected region are accepting them, that pattern would further support a cache-poisoning explanation specific to certain resolver populations rather than a flaw in your own GeoDNS configuration.

## Quick Reference Table

| Technique | Key Idea |
|---|---|
| DNS round robin | Multiple A/AAAA records, rotated order; loose statistical distribution, no health awareness |
| GeoDNS | Routes based on resolver's apparent geographic location |
| Latency-based routing | Routes based on measured network performance, not just geography |
| Weighted DNS routing | Configured-proportion traffic split across records; coarse, slow-converging |
| DNS health-check failover | Provider-specific feature bolted on top of DNS; not native to the protocol |
| Structural limitation | No in-path visibility, no per-request decisions, caching delays propagation |
| Layered pattern | DNS for coarse regional routing; L4/L7 LB for fine-grained in-region distribution |
| TTL's role | Sets the floor on how fast any DNS-driven routing/failover change takes effect |
| Connection pinning | Long-lived connections don't re-resolve regardless of DNS-layer changes |

---

**Tip for interviews:** What separates strong candidates on DNS-based load balancing specifically: (1) being able to clearly articulate **why it's structurally coarse** — no in-path visibility, no per-request decisions, caching-bound propagation — rather than just listing the techniques without explaining the underlying limitation they all share (Q2, Q18); (2) knowing that **DNS itself has no native health concept**, and that "DNS health checking" is always a separate, provider-specific feature layered on top, not a protocol capability (Q14–15); (3) understanding that **TTL is the binding constraint** on how fast any DNS-driven routing decision — round robin, weighted, failover — can actually take effect, and that this needs to be proactively tuned before an incident, not discovered during one (Q16, Q21, Q26); (4) recognizing **connection pinning** as a failure mode entirely orthogonal to DNS-layer correctness — a perfectly executed DNS failover still won't move already-pinned long-lived connections (Q17, Q28); and (5) being able to confidently recommend the **standard layered architecture** — DNS for coarse regional/geographic routing, real L4/L7 load balancing for fine-grained in-region distribution — as the synthesis answer that ties the whole topic together, which is exactly the systems-level reasoning interviewers look for at the 5 YOE level (Q3, Q19, Q24).
