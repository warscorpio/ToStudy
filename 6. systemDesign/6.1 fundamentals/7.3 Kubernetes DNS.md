# Kubernetes DNS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Kubernetes DNS and why does every cluster need it?**
A: Kubernetes DNS is a cluster-internal DNS service that automatically assigns stable, resolvable hostnames to every Service and (in certain cases) Pod in the cluster. Without it, services would have to discover each other via hard-coded IP addresses — but Pod and Service IPs are ephemeral in Kubernetes (Pods are killed and replaced, cluster IP allocations change across environments), making hard-coded IPs unmaintainable. Kubernetes DNS provides the stable naming layer: a service named `payments` in the `billing` namespace is always reachable as `payments.billing.svc.cluster.local`, regardless of what IP it's currently assigned, what environment the cluster is running in, or how many times the underlying pods have been replaced since the service was created.

**Q2. What is CoreDNS and what role does it play?**
A: CoreDNS is the default DNS server used by Kubernetes clusters since version 1.13 (replacing the older kube-dns). It runs as a Deployment (typically 2 replicas for HA) in the `kube-system` namespace, serves as the cluster's internal recursive DNS resolver, and is backed by a plugin-based architecture that allows highly flexible configuration. Its primary job in a Kubernetes cluster: respond to intra-cluster DNS queries (service discovery), forward queries for external domains (outside the cluster) to upstream resolvers, and apply cluster-specific DNS policies. Every Pod's `/etc/resolv.conf` is automatically configured by the kubelet to point to CoreDNS's cluster IP as the first nameserver.

**Q3. What is the cluster domain, and what does `svc.cluster.local` mean structurally?**
A: `cluster.local` is the default cluster domain — the root of the cluster's internal DNS namespace. The full DNS name structure for a Service is:

```
<service-name>.<namespace>.svc.cluster.local
```

Breaking it down right-to-left (per the DNS hierarchy from the DNS fundamentals guide):
- `cluster.local` — the cluster-internal TLD (configurable at cluster setup; some teams change this to avoid conflicts with real `.local` mDNS usage).
- `svc` — indicates this is a Service resource (as opposed to `pod`, which is the subdomain for Pod DNS records).
- `<namespace>` — the Kubernetes namespace.
- `<service-name>` — the Service's `metadata.name`.

CoreDNS is authoritative for the `cluster.local` zone entirely — queries for this suffix never leave the cluster.

**Q4. What DNS name does a Pod automatically get, and what controls it?**
A: Pods do not automatically get DNS records like Services do — by default, a Pod is only addressable by its IP, which isn't stable. However, a Pod can get a DNS record in two ways:
- **If it belongs to a headless Service** (Q10): it gets a DNS A record of the form `<pod-ip-with-dashes>.<service-name>.<namespace>.svc.cluster.local` — e.g., `10-0-1-5.my-headless-svc.default.svc.cluster.local`.
- **If `hostname` and `subdomain` fields are set** on the Pod spec, and a headless Service with that `subdomain` name exists in the same namespace: the Pod gets a DNS record of the form `<hostname>.<subdomain>.<namespace>.svc.cluster.local` — a human-readable, stable name even across pod replacements (as long as the hostname field is set consistently, e.g., by a StatefulSet).

StatefulSets use this mechanism to give each replica a stable, ordinal-based DNS name — one of their key differentiating features from Deployments.

**Q5. How is a Pod's `/etc/resolv.conf` configured in Kubernetes, and what does it contain?**
A: The kubelet writes `/etc/resolv.conf` inside every Pod when it starts, according to the Pod's `dnsPolicy` setting (Q6). For the default `ClusterFirst` policy, the generated file typically looks like:

```
nameserver 10.96.0.10       # CoreDNS's cluster IP (kube-dns Service IP)
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

Key elements: the `nameserver` line points to CoreDNS; the `search` list defines the DNS search domain suffixes the OS resolver automatically appends to short/unqualified names before trying them as absolute FQDNs; `ndots:5` means any name with fewer than 5 dots is first tried with search suffixes appended before trying as a fully-qualified name — a behavior with meaningful performance implications discussed in Q7.

## Section 2: DNS Resolution Behavior

**Q6. What are the four `dnsPolicy` options in Kubernetes and when would you use each?**
A:
- **`ClusterFirst`** (default): queries for cluster-internal names (matching `cluster.local`) go to CoreDNS; all other queries are forwarded by CoreDNS to the upstream resolver. The `/etc/resolv.conf` points to CoreDNS for everything. Used by the vast majority of application pods — they need to resolve both internal services and external hostnames.
- **`ClusterFirstWithHostNet`**: same as ClusterFirst, but required for Pods that use `hostNetwork: true` (share the node's network namespace). Without this explicit setting, such pods would inherit the node's `/etc/resolv.conf` directly, bypassing CoreDNS entirely.
- **`Default`**: the Pod inherits its DNS configuration directly from the node it runs on (the node's `/etc/resolv.conf`), entirely bypassing CoreDNS. Internal Kubernetes service names are unresolvable. Used for node-level system/infrastructure pods that need to behave like any other workload on the node's network, not a cluster service consumer.
- **`None`**: the Pod has no DNS configuration at all unless explicitly provided via `dnsConfig` in the Pod spec — a starting-from-scratch override, giving maximum control for very specific or unusual DNS requirements.

**Q7. What is the `ndots:5` setting in Kubernetes and why does it cause a performance concern?**
A: `ndots:5` means: if the queried hostname contains fewer than 5 dots, the resolver treats it as a relative/short name first and tries appending each suffix from the `search` list before trying it as an absolute FQDN. With the default Kubernetes search list (`default.svc.cluster.local`, `svc.cluster.local`, `cluster.local`), resolving a completely external hostname like `api.stripe.com` (3 dots — fewer than 5) triggers the following lookup sequence before the resolver ever tries the intended absolute name:

1. `api.stripe.com.default.svc.cluster.local` → NXDOMAIN
2. `api.stripe.com.svc.cluster.local` → NXDOMAIN
3. `api.stripe.com.cluster.local` → NXDOMAIN
4. `api.stripe.com` → resolves correctly

That's 3 unnecessary CoreDNS queries (each returning NXDOMAIN) before the correct answer is found — adding latency to every external DNS lookup, especially under high request volume where each application instance may trigger this sequence repeatedly. Mitigations: (1) use fully-qualified domain names (FQDNs) with a trailing dot in application configuration (`api.stripe.com.`) — a name with a trailing dot is always treated as already absolute, bypassing search suffix expansion entirely; (2) tune `ndots` downward via Pod `dnsConfig.options` (e.g., `ndots:2` is often sufficient for most real workloads); (3) ensure CoreDNS is caching NXDOMAIN responses (negative caching, covered in the DNS guide) so repeated identical external lookups don't all traverse the full NXDOMAIN chain individually.

**Q8. How does CoreDNS handle forwarding for non-cluster-local queries?**
A: CoreDNS's Corefile (the configuration file) typically defines two zones: the `cluster.local` zone (authoritative, handled entirely by the `kubernetes` plugin that queries the Kubernetes API server for Service/Pod/Endpoint data) and a catch-all `.` zone (everything else) handled by the `forward` plugin, which forwards to upstream resolvers (typically the node's configured DNS server, inferred from the node's `/etc/resolv.conf`):

```
.:53 {
    errors
    health
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
    }
    forward . /etc/resolv.conf    # Forward external queries to node's upstream resolver
    cache 30                      # Cache upstream responses for 30s
    loop
    reload
    loadbalance
}
```

This means CoreDNS acts as both an authoritative server (for `cluster.local`) and a recursive forwarder (for everything else) in one — a single DNS endpoint inside the cluster handles all DNS regardless of whether the name is cluster-internal or external.

**Q9. What is the Kubernetes plugin in CoreDNS and what does it do internally?**
A: The `kubernetes` plugin is CoreDNS's integration point with the Kubernetes API. It watches the API server (via list/watch informers on Services, Endpoints/EndpointSlices, and Pods) and maintains an in-memory representation of all DNS records implied by cluster resources — resolving `my-service.default.svc.cluster.local` to the Service's ClusterIP by looking it up from this in-memory state rather than querying any external DNS infrastructure. Because it uses the Kubernetes watch API (an event-driven streaming protocol), CoreDNS's view of Services and Endpoints is near-real-time — a new Service is typically resolvable within seconds of creation, driven by the API server notifying CoreDNS of the change, rather than polling on a TTL schedule. This is fundamentally different from standard external DNS, where TTL-based caching is the primary consistency mechanism.

## Section 3: Services and Headless Services

**Q10. What DNS records does a regular (ClusterIP) Service get?**
A: A regular ClusterIP Service gets:
- An **A record** (or AAAA for IPv6): `<service-name>.<namespace>.svc.cluster.local` → ClusterIP (the single virtual IP assigned to the Service). This is the most commonly used form — application code simply uses the short service name or FQDN and gets back one IP, with kube-proxy handling the actual load balancing behind that IP.
- A **SRV record** for each named port: `_<portname>._<protocol>.<service-name>.<namespace>.svc.cluster.local` — the SRV record includes the port number, enabling clients that understand SRV records (some gRPC clients, service discovery-aware libraries) to discover both the address and the port from a single DNS query rather than needing the port hard-coded.

**Q11. What DNS records does a headless Service get, and why is it important?**
A: A headless Service (defined by setting `clusterIP: None`) gets **multiple A records** — one per healthy Pod backing the service (from its Endpoints/EndpointSlices), all returned under the same service DNS name:

```
<service-name>.<namespace>.svc.cluster.local → 10.0.1.1 (Pod A)
                                             → 10.0.1.2 (Pod B)
                                             → 10.0.1.3 (Pod C)
```

Each Pod also gets an individual A record at `<pod-ip-dashes>.<service-name>.<namespace>.svc.cluster.local`, allowing direct pod-level addressability. This is important because:
- Clients resolving the service name get the full list of backing Pod IPs, making their own client-side load balancing decisions (or connecting to all of them, e.g., a Cassandra driver connecting to all cluster nodes).
- StatefulSets rely on headless services to give each ordinal replica a stable, individual DNS name (Q4), enabling stateful workloads where replicas are not interchangeable.
- It's the DNS foundation that gRPC and other multiplexed-protocol services need to do proper per-RPC load balancing (covered in the L4/L7 and Round Robin guides — gRPC needs individual Pod IPs, not a single virtual IP).

**Q12. What happens to DNS records when pods behind a headless service become unhealthy?**
A: The `kubernetes` plugin in CoreDNS pulls its endpoint data from Endpoints/EndpointSlice objects maintained by the Endpoints controller. When a Pod's readiness probe fails, the Endpoints controller removes that Pod's IP from the Endpoints object almost immediately (it's watching Pod readiness state) — and CoreDNS, watching the Endpoints object via its informer, updates its in-memory record set to stop returning that IP. The DNS record update is therefore driven by the readiness probe mechanism, not by any DNS-level health checking — connecting readiness probes directly to DNS-based service discovery. However, due to client-side DNS caching (any client that already resolved and cached the address list) and the inherent asynchrony of event propagation, there's always a brief window (typically a few seconds) during which clients may still have the failing Pod's IP in their local DNS cache. This is another instance of the caching-vs-consistency trade-off from the DNS and cache invalidation guides.

**Q13. What DNS records do ExternalName Services produce?**
A: An ExternalName Service is a special type that maps a Kubernetes service name to an external DNS name rather than to a ClusterIP or Pod set. The DNS record it produces is a CNAME rather than an A record:

```
my-external-db.default.svc.cluster.local → CNAME → prod-db.us-east-1.rds.amazonaws.com
```

This lets application code inside the cluster use a stable internal service name (`my-external-db`) to refer to an external resource (an RDS database, a third-party API endpoint, etc.) — with the actual target DNS name defined once in the ExternalName Service manifest rather than scattered across all application configuration. It's also useful for migrating between environments: during a migration, swap the ExternalName target from the old to the new host without changing any application config. The main caveat (from the DNS guide): CNAME chasing is fully external to the cluster from that point — the eventual A record resolution of the target hostname happens via the normal external DNS resolution path, not CoreDNS's internal authoritative data.

## Section 4: StatefulSets and DNS

**Q14. How do StatefulSets use DNS to provide stable identities for stateful workloads?**
A: A StatefulSet creates Pods with stable, ordinal-based names (`<statefulset-name>-0`, `<statefulset-name>-1`, etc.) and uses a headless Service (Q11) to give each Pod a stable, individually-addressable DNS name. Given a StatefulSet named `postgres` in the `database` namespace with a headless Service also named `postgres`:

- Pod 0: `postgres-0.postgres.database.svc.cluster.local`
- Pod 1: `postgres-1.postgres.database.svc.cluster.local`
- Pod 2: `postgres-2.postgres.database.svc.cluster.local`

These names persist across pod rescheduling — if `postgres-0` crashes and is replaced with a new pod, the new pod gets the same name `postgres-0` and the same DNS name, allowing clients (and peer pods in the stateful cluster) to reliably find it by name even after a restart. This is fundamentally different from a Deployment's pods, which get random names and are not individually addressable by a stable DNS name.

**Q15. How does a distributed database like Cassandra or Kafka use StatefulSet DNS for intra-cluster communication?**
A: Each node in the distributed database cluster needs to know the addresses of its peers to form the cluster (gossip protocol for Cassandra, broker lists for Kafka). StatefulSet DNS makes this bootstrappable from a static configuration: each Cassandra node can be configured with seed addresses using the stable DNS names of the first few StatefulSet pods (`cassandra-0.cassandra.namespace.svc.cluster.local`, `cassandra-1.cassandra.namespace.svc.cluster.local`) — these names remain valid regardless of when the cluster starts, what IPs are assigned, or how many times nodes restart. Without stable DNS (e.g., using bare pod IPs), bootstrap configuration would need to be dynamically generated after pod scheduling, adding significant operational complexity.

**Q16. What is the "pod hostname" pattern in StatefulSets, and how is it configured in the Pod spec?**
A: When Kubernetes creates a StatefulSet pod, it automatically sets the pod's `hostname` field to the pod's ordinal name (e.g., `redis-2`) and its `subdomain` field to the headless Service's name. CoreDNS picks up these fields (via the `kubernetes` plugin watching Pods with non-empty `subdomain` fields) and creates an A record at `<hostname>.<subdomain>.<namespace>.svc.cluster.local` → Pod IP. This is entirely automatic for StatefulSet pods — the StatefulSet controller handles setting these fields when creating pods. For non-StatefulSet pods, you can achieve the same effect by manually setting `spec.hostname` and `spec.subdomain` in the Pod spec and ensuring the matching headless Service exists, though this is rarely done outside of StatefulSet context.

## Section 5: CoreDNS Configuration and Tuning

**Q17. Where is CoreDNS's configuration stored in a Kubernetes cluster, and how do you modify it?**
A: In a ConfigMap named `coredns` in the `kube-system` namespace — the Corefile is stored as a data key in this ConfigMap and mounted into the CoreDNS pods:

```bash
kubectl edit configmap coredns -n kube-system
```

The CoreDNS pods watch the ConfigMap for changes (via the `reload` plugin) and automatically pick up configuration changes without needing a full restart, typically within 30-60 seconds. Changes are applied live — though misconfigured Corefiles can break cluster DNS entirely, so changes should be tested carefully (ideally in a staging cluster) before applying to production.

**Q18. How do you configure CoreDNS to handle a specific domain differently — for example, forwarding queries for `internal.corp.com` to a specific private DNS server that's not the default upstream?**
A: By adding an additional server block in the Corefile for that specific domain, before the catch-all `.` block:

```
.:53 {
    # Default catch-all block
    kubernetes cluster.local in-addr.arpa ip6.arpa { ... }
    forward . /etc/resolv.conf
    cache 30
}

internal.corp.com:53 {
    forward . 10.0.0.53   # Route queries for this domain to a specific private resolver
    cache 30
}
```

This is called "conditional forwarding" — CoreDNS routes queries for `internal.corp.com` to a dedicated private DNS server (which knows those records) while handling everything else normally. Common use case: a company with an on-premises active directory/corporate DNS infrastructure wants internal corporate DNS names to be resolvable from within the Kubernetes cluster (perhaps connected via VPN or VPC peering).

**Q19. How do you add custom DNS entries (like a hosts file) inside a Kubernetes cluster without modifying every Pod?**
A: Via the CoreDNS `hosts` plugin in the Corefile:

```
.:53 {
    hosts {
        192.168.1.100  legacy-server.internal
        10.0.0.50     old-cache.internal
        fallthrough
    }
    kubernetes cluster.local ...
    forward . /etc/resolv.conf
    cache 30
}
```

The `fallthrough` directive tells the `hosts` plugin to pass the query to the next plugin if it doesn't match any entry — without it, unmatched queries would return NXDOMAIN rather than being forwarded. This is useful for hardcoding a few entries (e.g., pointing a hostname at a specific external IP during a migration, or providing a DNS alias for a legacy service) without needing to set up a full separate DNS infrastructure.

**Q20. How do you tune CoreDNS caching behavior, and what's the performance implication?**
A: Via the `cache` plugin in the Corefile, which caches both successful (positive) and failed (negative/NXDOMAIN) upstream DNS responses:

```
cache 30 {
    success 9984 3600    # Cache up to 9984 positive responses for up to 3600s
    denial 9984 30       # Cache up to 9984 NXDOMAIN responses for up to 30s
}
```

The default `cache 30` without extra options caches responses for up to 30 seconds. The performance implication: the `ndots:5` NXDOMAIN storm described in Q7 generates a high volume of negative queries for non-existent cluster-local versions of external names; caching those NXDOMAIN responses for even 30 seconds dramatically reduces repeated upstream resolver hits for the same predictable negative result. For internal cluster queries (authoritative answers from the `kubernetes` plugin), the response isn't cached by CoreDNS at all in most default configurations — it's served fresh from the in-memory API state on every query, since that state is already kept current by the watch mechanism (there's no stale-data risk requiring cache TTLs for authoritative cluster data the way there is for forwarded external queries).

**Q21. How do you scale CoreDNS horizontally in a large cluster, and what configuration knobs matter?**
A: CoreDNS scales by increasing its Deployment replica count (the default of 2 is appropriate for small/medium clusters) — each replica independently handles queries, load-balanced via the `kube-dns` Service that CoreDNS sits behind. For large clusters (hundreds of nodes, thousands of pods), additional considerations: (1) increase replicas to 3-5+ and use PodAntiAffinity rules to spread them across nodes, avoiding a scenario where all CoreDNS replicas land on the same node and fail together; (2) configure resource requests/limits appropriately — a common production issue is CoreDNS being OOM-killed (the `kubernetes` plugin's in-memory state grows with cluster size) or CPU-throttled during query bursts; (3) consider NodeLocal DNSCache (Q22) to reduce the load CoreDNS itself must handle as the cluster grows; (4) the `lameduck` plugin and graceful shutdown configuration ensure in-flight queries complete cleanly when a CoreDNS pod is being terminated during updates.

**Q22. What is NodeLocal DNSCache and what problem does it solve?**
A: An add-on component (DaemonSet) that runs a local DNS cache agent directly on every node, intercepting DNS queries before they reach CoreDNS by binding to a link-local IP address (169.254.20.10 by default) and caching responses locally on the node. Benefits: (1) reduces latency for the majority of cached DNS responses (a localhost loopback query to the node-local cache is faster than a Pod → CoreDNS network hop, even on a fast cluster network); (2) drastically reduces query load on CoreDNS pods, since each node now absorbs its own caching load rather than forwarding everything to a small fleet of CoreDNS pods; (3) eliminates the conntrack overhead of many short-lived UDP connections to CoreDNS (each DNS query creates a connection-tracking table entry, which becomes significant at high query rates across a large cluster); (4) improves resilience — if CoreDNS is momentarily unreachable, the node-local cache can continue serving recently-cached answers. The trade-off: additional DaemonSet to operate on every node, and slightly more complex DNS path to reason about and debug.

## Section 6: Common Problems and Failure Modes

**Q23. What is "DNS thrashing" in Kubernetes and what typically causes it?**
A: A situation where pods experience intermittent DNS resolution failures, high latency, or NXDOMAIN responses for names that should be resolvable — often manifesting as transient connection failures, retried requests, or "service temporarily unavailable" errors in application logs, with no obvious infrastructure failure. Common causes: (1) CoreDNS pods being CPU-throttled (set too-low CPU limits, causing query queue buildup) or memory-constrained; (2) the `ndots:5` search suffix expansion generating excessive NXDOMAIN storm volume against a small CoreDNS fleet that can't keep up; (3) conntrack table exhaustion (the node's kernel connection tracking table fills up, causing dropped packets — DNS queries, being UDP, are silently dropped rather than getting a TCP RST to trigger a retry, leading to silent resolution timeouts); (4) CoreDNS pods crashing or being evicted and the small default replica count leaving the cluster with zero DNS for the recovery window.

**Q24. What is the conntrack exhaustion problem specific to DNS in Kubernetes, and how is it mitigated?**
A: Linux's conntrack (connection tracking) table tracks every network connection for NAT/iptables purposes. In Kubernetes with iptables-based kube-proxy, every Pod-to-CoreDNS DNS query (UDP) generates conntrack entries. At large scale (many pods, high DNS query rate), the conntrack table fills up — new entries can't be created, and some DNS queries are silently dropped (no ICMP error for UDP), manifesting as DNS timeouts. NodeLocal DNSCache (Q22) is a primary mitigation — it changes the DNS query path to use TCP (more efficiently tracked) for upstream CoreDNS communication, and reduces the number of remote CoreDNS connections by absorbing most queries locally. Additional mitigations: increase `nf_conntrack_max` kernel parameter; switch kube-proxy to IPVS mode (which has less conntrack overhead); or switch to a CNI that avoids iptables entirely (e.g., Cilium with eBPF).

**Q25. How do you debug DNS failures inside a Kubernetes cluster, step by step?**
A:
1. **Verify CoreDNS is running and healthy**: `kubectl get pods -n kube-system -l k8s-app=kube-dns` — check all pods are Running, not OOMKilled or CrashLooping; `kubectl logs -n kube-system <coredns-pod>` for error output.
2. **Test DNS from inside a Pod**: use a debug container or a temporary pod with `dnsutils` image: `kubectl run debug --image=infoblox/dnstools -it --rm` then run `nslookup my-service.my-namespace`, `nslookup my-service.my-namespace.svc.cluster.local`, `nslookup kubernetes.default`.
3. **Check resolv.conf inside the affected Pod**: `kubectl exec <pod> -- cat /etc/resolv.conf` — verify it points to CoreDNS's IP (the `kube-dns` Service's ClusterIP, typically `10.96.0.10` in default kubeadm clusters) and has the expected search domains.
4. **Verify the Service and Endpoints actually exist**: `kubectl get svc my-service -n my-namespace` and `kubectl get endpoints my-service -n my-namespace` — a common cause of NXDOMAIN is that the Service or its Endpoints object doesn't exist at all (e.g., no pods match the selector, or the Service is in the wrong namespace).
5. **Check CoreDNS metrics**: via Prometheus/Grafana if available — `coredns_dns_request_count_total`, `coredns_dns_response_rcode_count_total` (high NXDOMAIN rate), and `coredns_forward_request_count_total` (excessive forwarding, indicating the ndots issue).
6. **Test against CoreDNS directly**: `kubectl exec <pod> -- nslookup my-service <coreDNS-ClusterIP>` to bypass any client-side caching and confirm CoreDNS itself returns the expected answer.

**Q26. What happens to in-flight DNS queries when a CoreDNS pod is terminated (e.g., during a rolling update)?**
A: In-flight UDP DNS queries to the terminating pod are dropped, resulting in timeouts for those specific queries — the querying client must wait for the query to time out (typically 5 seconds per attempt) before retrying against another CoreDNS pod. The `kube-dns` Service that fronts CoreDNS uses iptables/IPVS rules to load-balance across all healthy CoreDNS pods — but during the brief window between when a pod begins terminating and when kube-proxy removes it from the iptables/IPVS rules, some queries continue being sent to the terminating pod and are lost. Mitigations: the `lameduck` plugin in CoreDNS's Corefile delays the pod from fully terminating until in-flight queries have had time to complete and kube-proxy has had a chance to update routing rules — effectively a graceful shutdown grace period specific to DNS; `PodDisruptionBudgets` ensuring at least one replica remains available during rolling updates; and the `preStop` lifecycle hook for an additional short sleep (a common Kubernetes pattern to bridge the kube-proxy update lag).

**Q27. What causes "SERVFAIL" responses from CoreDNS, as distinct from NXDOMAIN, and what should you check?**
A: NXDOMAIN ("no such domain") means the name genuinely doesn't exist in the authoritative data — the queried name was not found. SERVFAIL ("server failure") means CoreDNS encountered an error while trying to resolve the query — a fundamentally different failure mode. Common causes of SERVFAIL from CoreDNS: (1) the `kubernetes` plugin can't reach the Kubernetes API server (network issue, API server overload, authentication problem) — queries for cluster-internal names fail since CoreDNS can't consult its authoritative source; (2) the upstream resolver used for external forwarding is unreachable or returning errors — queries for external domains fail; (3) DNSSEC validation failures if DNSSEC is configured; (4) CoreDNS itself is resource-starved and timing out internally. In debugging: a SERVFAIL while NXDOMAIN for the same name would be unexpected and suggests a transient resolution infrastructure issue rather than "this service doesn't exist."

## Section 7: Advanced Topics

**Q28. What is DNS policy `None` with custom `dnsConfig`, and when is it useful in practice?**
A: `dnsPolicy: None` removes all automatically-generated DNS configuration from the Pod, and the `dnsConfig` field is then used to specify exactly what should appear in the Pod's `/etc/resolv.conf`:

```yaml
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
      - 1.1.1.1
      - 8.8.8.8
    searches:
      - my-custom-domain.internal
    options:
      - name: ndots
        value: "2"
```

Practical use cases: (1) workloads that must resolve only external names (never internal cluster names) and should bypass CoreDNS entirely to reduce latency; (2) performance-sensitive workloads where the default `ndots:5` NXDOMAIN expansion overhead (Q7) is unacceptable and careful tuning is needed — using `dnsPolicy: None` with a tuned `ndots:2` and explicit external resolvers; (3) pods that need to use a specific corporate DNS infrastructure that's not the default node resolver; (4) debugging scenarios where you want to test with completely controlled DNS behavior.

**Q29. How does the Kubernetes DNS specification handle wildcard records, and are they supported?**
A: The Kubernetes DNS specification (the spec that defines what cluster DNS implementations must provide, not any specific implementation) does not define wildcard DNS support for Services or Pods — the DNS records it specifies are all specific, named entries corresponding to specific cluster resources. CoreDNS itself, being a general-purpose DNS server, supports wildcard records via plugins like the `template` plugin, which can generate dynamic DNS responses matching regex patterns. This is occasionally used for things like wildcard Ingress/Istio gateway routing where you want `*.myapp.example.com` to resolve to a specific IP — but this requires explicit CoreDNS configuration beyond the default kubernetes plugin, and the use cases are narrow enough that most Kubernetes engineers never need it.

**Q30. What is DNS-based service discovery vs API-based service discovery, and when does each make sense in Kubernetes?**
A: **DNS-based discovery** (the default in Kubernetes): services are discovered by name resolution — the application looks up `payment-service` and gets an IP; no special client libraries are needed; works with any language/framework. Simple, universal, and appropriate for the vast majority of Kubernetes workloads where pods are stateless and interchangeable. **API-based discovery** (Kubernetes API, Consul, etcd): the application or a proxy (Envoy via xDS) directly queries a registry for the current endpoint list, getting richer metadata (health status, labels, weights) than a plain DNS A record can carry, and receiving near-real-time push updates rather than waiting for DNS TTLs and caches. More complex to implement but required when: you need real-time endpoint awareness (DNS caching lag is too slow), you need the full set of individual Pod IPs for client-side load balancing (the service mesh alternative to headless DNS, but richer), or you need metadata beyond IP/port (like health status or version labels) for sophisticated routing decisions. The service mesh pattern (Istio/Envoy) effectively uses API-based discovery (via xDS from the control plane) for all traffic routing decisions, while still exposing DNS names for initial name resolution — combining both approaches at different layers.

## Section 8: Scenario-Based Questions

**Q31. "A developer says their pod can reach `http://payment-svc` but not `http://payment-svc.billing`. What's happening?"**
A: Both should resolve to the same service (`payment-svc` in the `billing` namespace), but the difference is how short names are expanded by the search domain list. `payment-svc` with the default search list for a pod in the `billing` namespace would have `billing.svc.cluster.local` as a search suffix — so `payment-svc` expands to `payment-svc.billing.svc.cluster.local`, which resolves correctly. `payment-svc.billing` has 2 dots — with `ndots:5`, it's also treated as a relative name and the search suffixes are appended, but the expansion `payment-svc.billing.default.svc.cluster.local` (appending the pod's own namespace's suffix first) is tried before `payment-svc.billing.svc.cluster.local`. The resolution order depends on the pod's own namespace — a pod in `default` namespace trying `payment-svc.billing` first tries `payment-svc.billing.default.svc.cluster.local` (NXDOMAIN), then `payment-svc.billing.svc.cluster.local` (hits!). So it *should* work, just with extra lookups. If it doesn't resolve at all, check: does the Service `payment-svc` actually exist in the `billing` namespace (`kubectl get svc payment-svc -n billing`)? Does the calling pod have permission (NetworkPolicy) to reach it? Is it timing out or returning NXDOMAIN? Distinguishing those cases determines the fix.

**Q32. "Your gRPC microservice connects to a downstream service using its cluster DNS name. You notice all traffic goes to a single pod, even though the downstream service has 10 replicas. Why, and how do you fix it?"**
A: This is the gRPC-over-a-regular-ClusterIP-Service problem — the same issue described in the L4/L7 load balancer guide. A regular ClusterIP Service returns one single virtual IP from DNS resolution. gRPC clients establish long-lived HTTP/2 connections to that IP, and kube-proxy's iptables/IPVS rules do connection-level load balancing — but since gRPC multiplexes all RPCs over that one connection, all RPCs flow to whatever single pod kube-proxy mapped the connection to at establishment time. The 10 replicas aren't being reached because the client only ever has one TCP connection to one backend pod, despite 10 existing. Fixes: (1) **Headless Service**: change the downstream service to `clusterIP: None` — DNS then returns all 10 pod IPs, allowing the gRPC client to do per-RPC load balancing across all of them (gRPC client libraries support this with appropriate resolver configuration); (2) **Service mesh**: use Istio/Linkerd, whose sidecar proxy handles gRPC-aware per-RPC load balancing transparently without changing the service to headless; (3) **gRPC client-side LB with ServiceConfig**: configure the gRPC client's resolver to use `round_robin` policy and point at the service name, relying on the headless DNS to return the full pod list for client-side LB.

**Q33. "A batch job running in the `jobs` namespace needs to connect to a Redis instance in the `infrastructure` namespace. What DNS name should it use, and what might go wrong?"**
A: The fully-qualified internal name `redis.infrastructure.svc.cluster.local` — or the shortened cross-namespace form `redis.infrastructure` (which works but triggers the search suffix expansion overhead from Q7; the FQDN is cleaner and unambiguous). What might go wrong: (1) NetworkPolicy — if the `infrastructure` namespace has NetworkPolicies restricting ingress, the `jobs` namespace pods may not be permitted to connect to Redis; simply resolving the DNS name doesn't mean the connection will succeed; (2) the Redis Service's port may not be named, making SRV discovery unavailable — the application must hard-code the port (6379); (3) using just `redis` without a namespace qualifier — the batch job in `jobs` namespace will try to find a Redis service in its *own* `jobs` namespace first (via the search domain expansion), fail, then try `redis.jobs.svc.cluster.local` (NXDOMAIN), then correctly find `redis.infrastructure.svc.cluster.local` — working but with unnecessary NXDOMAIN round-trips. Best practice: always use the fully-qualified cross-namespace name in configuration, not the short form.

**Q34. "During a large deployment rollout, engineers notice a spike in application errors that correlates with DNS failures in the monitoring dashboard. CoreDNS pods are Running but high-CPU. What do you do?"**
A: This is likely a DNS query rate burst during the rollout overwhelming CoreDNS's compute capacity. Immediate steps: (1) check CoreDNS pod resource metrics — if CPU is at or near the configured limit, CPU throttling is causing query queue buildup and timeouts; temporarily increase CoreDNS CPU limits as an emergency measure; (2) scale up CoreDNS replicas (`kubectl scale deployment coredns -n kube-system --replicas=5`) to spread query load; (3) identify the source of the query spike — is it the new pods (many starting simultaneously, each doing initial DNS lookups) or existing pods re-resolving frequently? Check the `ndots:5` expansion pattern — a rollout that starts many new pods, each making external API calls, will each generate multiple NXDOMAIN queries per external request (Q7 pattern). Longer-term: deploy NodeLocal DNSCache (Q22) to absorb node-level query load before it hits CoreDNS; tune `ndots` downward in the application pods' `dnsConfig`; and adjust CoreDNS resource limits/replicas ahead of large rollouts as part of the deployment runbook.
