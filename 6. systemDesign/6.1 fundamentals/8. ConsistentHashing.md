# Consistent Hashing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does consistent hashing solve?**
A: The modulo remapping problem. With naive modulo hashing (`hash(key) % N`), adding or removing one node causes nearly all keys to remap to different nodes — approaching `(N-1)/N` disruption as N grows. For a 10-node cache cluster, removing one node remaps ~90% of keys, causing a thundering herd of cache misses that floods the database. Consistent hashing limits remapping to approximately `1/N` of keys on any pool change — only the keys that "belonged" to the changed node are affected, and they move to exactly one other node.

**Q2. How does the basic consistent hash ring work?**
A: Both nodes and keys are mapped onto a circular hash space (0 to 2³² − 1, treated as a ring). Each node is placed at `hash(node_id)` on the ring. A key is placed at `hash(key)` and then routed to the first node encountered when walking clockwise from that position. This "next clockwise node" is called the key's home node or coordinator.

When a node is added: it takes over a contiguous arc of the ring from its clockwise predecessor — only keys in that arc remap, roughly `1/N` of total keys.
When a node is removed: its arc is absorbed by its clockwise successor — again only `~1/N` of keys move.

**Q3. What is the "successor node" rule and why clockwise specifically?**
A: The convention of taking the first clockwise node is arbitrary — counterclockwise or "nearest" work equally — but clockwise is the standard implemented in virtually all libraries. What matters is consistency: all nodes and clients must apply the same rule so they independently agree on which node owns which key. The ring metaphor makes this rule visually intuitive and easy to implement as a sorted list traversal.

**Q4. How is the ring implemented in code?**
A: As a sorted data structure mapping ring positions to node identifiers. In practice:

```python
# Build ring
ring = SortedDict()  # or sorted list of (position, node) tuples
for node in nodes:
    position = hash(node.id)
    ring[position] = node

# Route key
def get_node(key):
    position = hash(key)
    # Find first position >= hash(key) (clockwise successor)
    idx = ring.bisect_left(position)
    if idx == len(ring):
        idx = 0  # Wrap around
    return ring.values()[idx]
```

Lookup is O(log N) via binary search on the sorted ring. For small N (typical in LB pools), this is nanoseconds. For very large N or very high QPS, Maglev's O(1) lookup table is preferred.

**Q5. What is the key insight that makes consistent hashing "consistent"?**
A: The assignment of a key to a node is a function only of the key's hash position and the set of nodes currently in the ring. If the node set doesn't change, the mapping never changes. If one node is added or removed, only the keys adjacent to that change point remap — no global shuffle. This is the "consistency" property: the mapping is stable under local changes to the node set, unlike modulo hashing which is a global function of N and changes completely when N changes.

## Section 2: Virtual Nodes

**Q6. What is the problem with placing each physical node at a single ring position?**
A: With N physical nodes at N random ring positions, the arc lengths between consecutive nodes vary significantly by chance — especially at small N. Some nodes end up owning large arcs (receiving more than their fair share of keys/traffic), others own small arcs. With 3 nodes, one might own 60% of the ring and another 15% purely by hash luck. This causes uneven load distribution — the hot node becomes a bottleneck. Virtual nodes solve this.

**Q7. What are virtual nodes (vnodes) and how do they fix uneven distribution?**
A: Each physical node is mapped to K positions on the ring (K = 100–200 typically) instead of one. Each position acts as an independent "virtual node" that owns a small arc. The K arcs belonging to one physical node are scattered around the ring, and by the law of large numbers, their total arc length averages out to approximately `K / (N × K) = 1/N` of the ring — equal share regardless of hash luck.

```
# Node A at 150 virtual positions → owns ~150 arcs scattered around ring
# Node B at 150 virtual positions → owns ~150 arcs scattered around ring
# Node C at 150 virtual positions → owns ~150 arcs scattered around ring
# Each gets roughly 1/3 of all keys
```

A side benefit: when a node fails, its K arcs are each absorbed by their respective clockwise successors — the failed node's load is spread across all other nodes, not dumped on one successor.

**Q8. How do you choose the vnode count K?**
A: Trade-off between distribution quality and memory/metadata overhead:
- **K = 1**: no vnodes, maximum imbalance.
- **K = 10**: moderate improvement, still visible imbalance at small N.
- **K = 100–150**: standard for most systems (Ketama uses 160, Cassandra defaults to 256). Distribution error is < 5% with N ≥ 3.
- **K = 1000+**: near-perfect distribution but O(N × K) ring entries — memory and startup overhead.

For a 10-node cluster with K=150, the ring has 1,500 entries — trivial. For a 1,000-node cluster with K=150, it has 150,000 entries — still fine. Only extremely large clusters (10,000+ nodes) need to consider K carefully.

**Q9. Do vnodes affect consistent hashing's `1/N` remapping guarantee?**
A: No — the `1/N` property still holds. When a node with K virtual positions is added, it takes over K arcs — each arc is approximately `1/(N×K)` of the ring. Total keys remapped is K × `1/(N×K)` = `1/N`. The math works out the same. Vnodes improve distribution without changing the remapping guarantee.

**Q10. What is "token assignment" in Cassandra's consistent hashing, and how does it differ from random vnode placement?**
A: Early Cassandra (pre-1.2) used manually assigned tokens — each node was given a specific position (token) on the ring by the operator, requiring careful calculation to achieve even distribution. Cassandra 1.2+ introduced random vnode assignment (`num_tokens` per node, default 256) — each node generates 256 random positions on the ring at startup. This eliminated manual token calculation and improved rebalancing (when a node joins, it takes small amounts from many existing nodes instead of a large chunk from one). Modern Cassandra uses 16 vnodes by default (Cassandra 4.0+) with a more sophisticated token allocation strategy that achieves better balance with fewer vnodes.

## Section 3: Hash Functions

**Q11. What makes a good hash function for consistent hashing?**
A: Four properties matter:
- **Uniform distribution**: output values should be evenly spread across the hash space, so ring positions are well-scattered and arcs are naturally balanced. A clustered hash function defeats vnodes.
- **Speed**: called on every request — must be fast (nanoseconds). Cryptographic hashes (SHA-256) are overkill and 10–100x slower than necessary.
- **Avalanche effect**: small changes in input (e.g., "node1" vs "node2") should produce dramatically different outputs — preventing nearby ring placements for similarly-named nodes.
- **Determinism**: same input must always produce the same output across all nodes and restarts.

**Q12. Which hash functions are commonly used in production consistent hashing systems?**
A:
- **MD5**: used by Ketama (historical — chosen for good distribution, cryptographic strength unnecessary but not harmful). 128-bit output, typically truncated to 32-bit ring positions.
- **MurmurHash3**: fast, excellent distribution, widely used in modern systems (Cassandra, Redis Cluster, Guava's consistent hash). 32- or 128-bit variants.
- **xxHash**: fastest non-cryptographic hash available, comparable distribution to MurmurHash3. Used in systems where hashing is on the critical path.
- **FNV (Fowler–Noll–Vo)**: simple, fast, decent distribution. Used in some LB implementations.
- **CRC32**: hardware-accelerated on x86 (SSE4.2 `crc32` instruction), extremely fast. Used in some cache systems.

Avoid: SHA-256 (too slow), identity/simple modulo (terrible distribution), Java's `Object.hashCode()` (not stable across JVM restarts or versions).

**Q13. What is Google's Guava `consistentHash` function and how does it work differently?**
A: Guava's `Hashing.consistentHash(hash, buckets)` implements the "Jump Consistent Hash" algorithm (Lamping & Veach, 2014). Instead of a ring, it uses a mathematical recurrence to jump directly to the assigned bucket:

```python
def consistent_hash(key, num_buckets):
    b, j = -1, 0
    while j < num_buckets:
        b = j
        key = (key * 2862933555777941757 + 1) & 0xFFFFFFFFFFFFFFFF
        j = int((b + 1) * (1 << 31) / ((key >> 33) + 1))
    return b
```

Properties: O(1) computation, no ring data structure, perfect uniform distribution, minimal remapping on node add. Limitation: only supports adding nodes at the end of the range (bucket count must be monotonically increased) — can't remove arbitrary nodes without remapping. Used in Google's internal infrastructure where nodes are added but rarely removed mid-operation.

## Section 4: Where Consistent Hashing Is Used

**Q14. How does Memcached use consistent hashing?**
A: Memcached itself has no built-in clustering — it's the client library that implements consistent hashing to decide which server receives each key. The Ketama algorithm (libketama) is the standard: the client builds a ring with 160 virtual nodes per server (40 MD5 hashes × 4 positions each), routes `get(key)` and `set(key)` to the same server, and on server failure minimally remaps the affected keys. All clients independently compute the same ring — no coordination server is needed. This is "client-side consistent hashing."

**Q15. How does Redis Cluster implement key distribution, and is it consistent hashing?**
A: Redis Cluster uses a variant called "hash slots" — the key space is divided into exactly 16,384 fixed slots. Each key maps to a slot via `CRC16(key) % 16384`, and each Redis node owns a range of slots. This is consistent in the sense that moving a slot from one node to another only affects keys in that slot — but it's not a hash ring. It's a fixed partition table (slot → node mapping) stored in the cluster's gossip state. Migration is explicit: an operator or Redis Sentinel assigns slots to nodes. The minimal remapping property holds (move slots, not all keys), but via explicit assignment rather than a ring algorithm.

**Q16. How does Apache Cassandra use consistent hashing?**
A: Cassandra uses a ring (called the "token ring") where each node owns token ranges. Keys are routed to their coordinator node via `hash(partition_key)` mapped to the ring. Replication factor (RF) controls how many nodes store each key — the coordinator plus the next `RF-1` clockwise nodes (the "replica set"). On a 6-node ring with RF=3: a key's coordinator and its 2 clockwise neighbours all store the data. This enables reads and writes to succeed even if 1 of the 3 replicas is down (with QUORUM consistency: any 2 of 3 must agree).

**Q17. How does DynamoDB (Amazon) use consistent hashing?**
A: DynamoDB's internal architecture (described in the Dynamo paper, 2007) uses consistent hashing with virtual nodes. Each item's partition key is hashed to a ring position; each node owns multiple token ranges (virtual nodes). The replication strategy is "preference list" — for each key, the top N nodes clockwise on the ring form the preference list, and the item is stored on all of them. Unlike Cassandra's strict "coordinator + next clockwise" rule, Dynamo's preference list skips nodes that are down and continues clockwise until it finds N healthy nodes. This is the origin of many modern distributed database designs.

**Q18. How do CDNs use consistent hashing?**
A: CDNs use consistent hashing to route requests for the same URL to the same edge cache node — maximising cache hit rate. When a client requests `https://cdn.example.com/video/abc.mp4`, the CDN's request router hashes the URL (or a portion of it) and maps it to a cache node. All edge servers independently compute the same mapping, so the same content is always found on the same node without a central lookup. When a cache node fails, Ketama/ring hash minimally remaps affected URLs to adjacent nodes — causing a cold cache miss burst only for the affected content, not a full cache invalidation.

**Q19. How do load balancers use consistent hashing?**
A: For source IP or session-key-based affinity (the use case from the IP Hash guide), load balancers use consistent hashing to map client identifiers to backends with minimal disruption on pool changes. Envoy's `RING_HASH` and `MAGLEV` policies implement this. The hash input can be configured as source IP, a specific header value, cookie value, or query parameter — enabling flexible affinity without the modulo remapping problem of basic IP Hash.

## Section 5: Replication and Consistency

**Q20. How does consistent hashing support replication?**
A: By extending the "next clockwise node" rule to select multiple replicas. For replication factor RF=3: a key's primary is the first clockwise node; its replicas are the next 2 clockwise nodes. All three nodes independently know they should hold the key (they each compute the same ring position). No central coordinator is needed to assign replicas — it falls naturally from the ring structure. This is the foundation of the "sloppy quorum" model used in Dynamo-style databases.

**Q21. What is a "preference list" and how does it handle failures during replication?**
A: A preference list is the ordered set of nodes that should hold a key, derived from walking clockwise from the key's ring position. In Dynamo-style systems, the preference list has more entries than the replication factor — e.g., top 6 nodes for RF=3 — so that if the first 3 are unavailable, replicas can be placed on the next 3 ("hinted handoff"). When the target node recovers, the hinted replica transfers the data back. This ensures writes always succeed even during partial failures, at the cost of temporary inconsistency (eventual consistency model).

**Q22. What is a "hinted handoff" and when is it used?**
A: When a write arrives and one of the RF target nodes is temporarily unavailable, another node ("handoff node") accepts the write with a "hint" — metadata indicating which node was the real target and when it should be forwarded. When the target recovers, the handoff node pushes the stored write to it. Hinted handoff enables "always-writable" semantics at the cost of temporary inconsistency. Cassandra and DynamoDB both implement this. The hints are stored durably on the handoff node — if the handoff node also fails before delivering, Cassandra uses "read repair" and anti-entropy (Merkle tree reconciliation) to detect and repair the inconsistency.

**Q23. What is a Merkle tree in the context of consistent hashing systems?**
A: A Merkle tree (hash tree) is used for efficient anti-entropy — detecting which keys differ between two replicas without comparing every key individually. Each leaf is the hash of a key-value pair; each internal node is the hash of its children. Two replicas exchange root hashes — if they match, all data is identical. If they differ, the tree is traversed to identify which subtrees (and ultimately which keys) are out of sync. Cassandra runs periodic Merkle tree exchanges between replica pairs to repair divergence caused by hinted handoff delivery failures, network partitions, or node restarts. This is O(log N) communication to identify divergent keys in a dataset of N items.

## Section 6: Advanced Algorithms

**Q24. What is Rendezvous Hashing (Highest Random Weight, HRW)?**
A: An alternative to ring-based consistent hashing. For each key, every candidate node is scored:

```
score(node, key) = hash(node_id + key)
```

The key is assigned to the node with the highest score. Since `hash(node_id + key)` is pseudo-random and deterministic, all clients independently agree on the same assignment. When a node is removed, only keys where that node had the highest score are remapped — to whatever node now has the highest score — approximately `1/N` of keys. No ring data structure is needed; just score all N nodes and pick the max.

Advantages over ring hash: no vnodes needed (distribution is inherently uniform), simpler implementation, no ring metadata. Disadvantage: O(N) per lookup (score all nodes) — fine for small N, bad for large N. Used in DNS load balancing, some CDN routing systems, and distributed file systems.

**Q25. What is Google's Maglev hashing algorithm and what problem does it solve over ring hash?**
A: Maglev (2016 Google paper) is a consistent hashing scheme that builds a lookup table of size M (a large prime, e.g., 65537) where each entry maps to a backend. Construction:
1. Each backend generates a random permutation of table positions (using two hash functions: `offset = hash1(backend) % M`, `skip = hash2(backend) % M + 1`).
2. Backends fill the table in round-robin order using their permutations — each claims the next unclaimed slot from their permutation.
3. The result: each backend owns approximately `M/N` table entries, and the table is filled.

Lookup: `table[hash(key) % M]` — O(1), no binary search.

Advantages over ring hash:
- **Better uniformity at small N** — ring hash with few vnodes has high variance; Maglev's table construction guarantees near-perfect `1/N` distribution.
- **O(1) lookup** — no sorted ring traversal.
- **Minimal disruption on change** — approximately `1/N` remapping, same as ring hash.

Disadvantages: table consumes M × (pointer size) memory — 65537 × 8 bytes ≈ 512KB per LB instance. For pools of < 100 backends, trivial. Maglev is used by Google's front-end load balancers and supported in Envoy.

**Q26. How does Envoy choose between `RING_HASH` and `MAGLEV`?**
A: Envoy supports both as cluster LB policies:

```yaml
lb_policy: RING_HASH   # or MAGLEV
ring_hash_lb_config:
  minimum_ring_size: 1024
  maximum_ring_size: 8388608
```

Guidelines:
- **`MAGLEV`**: preferred when N is small (< 20 backends) and uniform distribution is critical — Maglev's table construction gives near-perfect balance even at N=3. O(1) lookup.
- **`RING_HASH`**: preferred when memory is constrained (no fixed-size table) or when N is large and ring construction cost matters. The ring size is configurable.
- Both support the same `HashPolicy` configuration (what to hash: source IP, header, cookie, query param).

## Section 7: Hotspots and Skew

**Q27. What is a "hot key" and how does consistent hashing make it worse?**
A: A hot key is a single key (or a small set of keys) that receives disproportionately high traffic — celebrity users, viral content, popular products. Consistent hashing maps each key to exactly one node — so a hot key concentrates all its traffic on one node, which becomes a bottleneck regardless of how well the ring is balanced. Other nodes sit idle for that key's traffic. Consistent hashing solves distribution across keys, but not load concentration from a small number of very popular keys.

Mitigations:
- **Key splitting / scatter-gather**: split the hot key into K sub-keys (`key#0`, `key#1`, ..., `key#K-1`), each mapping to a different node. Reads are scattered across all K nodes and results merged; writes go to all K. Used in BigTable, Bigtable-style systems.
- **Local caching**: add an in-process cache on each application server for hot keys — serves from memory before the request reaches the distributed cache.
- **Probabilistic early expiration**: each cache node probabilistically refreshes a key before it expires, preventing a thundering herd of cache misses when the hot key's TTL expires simultaneously across all clients.
- **Read replicas for hot keys**: detect hot keys (via access frequency monitoring) and dynamically replicate them to more nodes, giving multiple nodes that can serve the key.

**Q28. What is "partition skew" and how does it differ from hot key skew?**
A: Partition skew is uneven distribution of keys across nodes — some nodes own more keys (and thus more data/load) than others. It's a property of the ring structure and hash function, not of key popularity. Causes:
- Too few vnodes → large variance in arc lengths.
- Poorly distributed hash function → key hashes cluster on part of the ring.
- Non-uniform key distribution — keys themselves cluster in the hash space.

Hot key skew is about traffic volume on popular keys; partition skew is about data volume distribution. A system can have perfect partition balance (equal keys per node) but severe hot key skew (most traffic hitting keys on one node), and vice versa.

**Q29. How do you detect and mitigate partition skew in production?**
A: Detection: monitor per-node metrics — keys stored, memory used, read/write QPS, CPU utilisation. Significant divergence (> 20% above mean) signals skew.

Mitigations:
- **Increase vnode count**: more virtual nodes → better arc length averaging → less skew. Moving from K=10 to K=150 typically eliminates most structural skew.
- **Re-seed vnodes**: generate new random vnode positions (carefully, with migration) if the current positions are unlucky.
- **Manual token adjustment** (Cassandra): move a token boundary to redistribute a specific range.
- **Better hash function**: if the key space has inherent structure (e.g., sequential IDs), a hash function with good avalanche effect (MurmurHash3) distributes them well; a weak function clusters them.

## Section 8: Operational Concerns

**Q30. What happens operationally when a node is added to a consistent hash ring?**
A: Step by step:
1. New node generates its vnode positions (K hashes of its ID) and announces them to the cluster (via gossip, configuration, or control plane).
2. All other nodes update their ring view.
3. The new node's positions on the ring each "claim" the arc between themselves and their clockwise predecessor — keys in those arcs should now route to the new node.
4. Data migration: for stateful systems (caches, databases), existing data in those arc ranges must be transferred from the predecessor node to the new node. This is a "streaming" or "bootstrapping" phase.
5. During migration, requests to those keys may be served from the predecessor (for reads) and written to both (for writes), ensuring no data loss.
6. Once migration completes, the new node fully handles its ranges.

For stateless systems (LBs routing traffic, not storing data), steps 4–6 are omitted — clients simply start routing to the new node immediately.

**Q31. What is the "bootstrap storm" and how is it mitigated?**
A: When many nodes are added simultaneously (e.g., a large-scale expansion), each new node triggers data migrations from existing nodes. If the migrations are all concurrent and unthrottled, they saturate network bandwidth and disk I/O on existing nodes — causing degraded performance or timeouts for live traffic. Mitigations:
- **Throttle streaming**: Cassandra's `stream_throughput_outbound_megabits_per_sec` setting caps migration bandwidth.
- **Sequential bootstrap**: add nodes one at a time, waiting for each to complete before adding the next.
- **Off-peak scheduling**: schedule large cluster expansions during low-traffic windows.
- **Decommission-before-bootstrap**: for planned expansions (not emergency capacity), pre-stage new nodes during low traffic.

**Q32. What is "repair" in Cassandra and why is it needed even with consistent hashing?**
A: Consistent hashing tells each node which keys it should own. But during failures (node down during a write, hinted handoff delivery failure, network partition), a node may miss some writes it was supposed to receive. "Repair" is the process of reconciling all replicas to ensure they hold the same data. Cassandra's repair runs Merkle tree comparison between replica pairs (Q23), identifies divergent keys, and transfers the canonical (most recent) value. Without periodic repair, replicas gradually diverge — "entropy" accumulates. Repair is CPU and network intensive; it's typically scheduled during off-peak hours. This is an operational cost that doesn't exist for simpler single-node or non-replicated systems.

**Q33. How does consistent hashing interact with rolling deployments in a load balancer context?**
A: When backends are deployed one at a time (rolling update), the pool size changes repeatedly — first by -1 (old node removed), then by +1 (new node added). Each change remaps ~1/N of clients. For a 10-backend pool:
- Remove old node: ~10% of clients remap to different backends (sessions disrupted for those clients).
- Add new node: ~10% of clients remap again.

With Maglev or ring hash (consistent), this is far better than modulo hash (which would remap ~90% on each pool change). But for strictly zero-session-disruption deployments, consistent hashing still isn't perfect — only externalised session storage (Redis) eliminates disruption entirely.

## Section 9: Failure Modes and Edge Cases

**Q34. What happens when a ring node goes down without graceful removal?**
A: The node's arc is absorbed by its clockwise successor(s). For a cache:
- All keys that were homed on the failed node now route to the successor.
- The successor has a cold cache for those keys — cache miss burst. At RF=1, the data is lost until re-populated.
- At RF≥2, replicas on other nodes serve the data while the failed node is replaced.

For a load balancer using consistent hashing for backend affinity:
- Sessions from the ~1/N of clients assigned to the failed backend are disrupted.
- New routing maps those clients to the successor backend — sessions start fresh.
- Much better than modulo hash, which would disrupt all clients.

**Q35. What is "split brain" in a consistent hashing cluster and how is it handled?**
A: Split brain occurs when a network partition divides the cluster into two or more groups that can't communicate. Each partition may have an incomplete view of the ring — especially if a node is in only one partition. The two partitions may serve different data for the same key (divergent writes). Resolution approaches:
- **Fencing and quorum**: require a quorum of nodes (RF/2 + 1) to agree before accepting a write — prevents both partitions from accepting conflicting writes (CP model: consistency over availability).
- **Eventual consistency + vector clocks**: accept writes in both partitions, reconcile when the partition heals using vector clocks or CRDTs to merge conflicting versions (AP model: availability over consistency).
- **Leader election per partition range**: each range has a designated primary; during partition, only the partition containing the primary accepts writes.

Cassandra uses the AP model (tunable consistency — QUORUM writes require RF/2+1 nodes, which prevents split-brain for writes at the cost of availability if too many nodes are down).

**Q36. What is "data skew after failure" and how does the successor absorb it?**
A: When a node fails and its traffic is absorbed by the clockwise successor, that successor suddenly handles its own traffic plus the failed node's traffic — approximately doubling its load. With K=150 vnodes, the failed node's 150 arcs each go to different successors (scattered around the ring) — spreading the load across roughly K different nodes (ideally all N-1 remaining nodes), so each absorbs only 1/(N-1) more traffic rather than one node absorbing everything. This is the "load spreading on failure" benefit of vnodes, distinct from their "distribution uniformity" benefit.

## Section 10: Comparison and Scenario Questions

**Q37. Consistent hashing vs modulo hashing — when would you ever use modulo?**
A: Modulo hashing (`hash(key) % N`) is appropriate only when:
- The node set is completely static and never changes (rare in practice).
- The remapping cost is acceptable — e.g., it's acceptable to invalidate/warm all caches during a deployment.
- Simplicity trumps everything — e.g., a quick prototype or a system where sessions are stateless anyway.
- Sharding in a database where rebalancing is a scheduled offline operation (shard count fixed at schema design time, changing it requires a full migration).

In virtually all production distributed caching, load balancing, and database scenarios where nodes come and go, consistent hashing is the right choice.

**Q38. Consistent hashing vs range-based partitioning — how do distributed databases choose?**
A: Range-based partitioning divides the key space into contiguous ranges (e.g., A–M on node 1, N–Z on node 2). Benefits: range scans are efficient (query all keys from "apple" to "banana" hits one shard). Downsides: hotspots for sequential keys (e.g., time-series data where all new writes go to the last shard), and adding a node requires splitting an existing range.

Consistent (hash-based) partitioning randomises key distribution — eliminates hotspots for sequential keys but makes range scans across the full key space require a scatter-gather to all shards. Choice:
- **Hash-based (consistent hash)**: DynamoDB, Cassandra, Redis Cluster — optimise for uniform write distribution.
- **Range-based**: HBase, BigTable, CockroachDB — optimise for range scans. CockroachDB adds load-based range splitting to avoid hotspots.

**Q39. "Design a distributed cache for a social media platform's user profile data (100M users, 50 cache nodes). Walk me through the consistent hashing design."**
A: Key design decisions:

1. **Hash function**: MurmurHash3 on `user_id` (integer) — fast, excellent distribution across the ring.
2. **Vnode count**: K=150 per node → 7,500 ring entries for 50 nodes. Distribution variance < 2%.
3. **Replication factor**: RF=2 for cache (if primary misses, fall back to replica; DB is the source of truth). Replica is the next clockwise node.
4. **Hot user handling**: detect top-1000 most-accessed user IDs via access frequency counter (LFU eviction + access logging). Replicate these profiles to all 50 nodes (broadcast write, scatter-gather read at app layer). Eliminates celebrity-user hotspots.
5. **Node failure**: with RF=2, one node failure means ~1/50 of users miss primary cache, hit replica — no DB hit. Ring remapping affects ~1/50 of users.
6. **Scale-out**: adding 10 nodes (50→60) remaps 1/50 of keys per new node = ~10/50 = ~20% of total keys remap — accepted as a scheduled event with DB fallback during migration.
7. **Client-side vs proxy-side**: prefer client-side consistent hashing (each app server computes the ring independently) to avoid a proxy bottleneck — same model as libketama for Memcached.

**Q40. "A candidate says 'I'd just use Redis Cluster for consistent hashing.' What's missing from that answer?"**
A: Redis Cluster uses hash slots (fixed 16,384 partitions), not a traditional consistent hash ring — it's a related but distinct mechanism. A strong answer distinguishes:
- Redis Cluster's hash slots are a fixed-size partition table with explicit slot assignment, not a ring with emergent routing.
- Moving slots requires explicit `CLUSTER SETSLOT` / `MIGRATE` commands — it's an administrative operation, not automatic.
- Redis Cluster doesn't support arbitrary vnode counts or Ketama/Maglev-style routing — its model is slot ranges per node.
- For true consistent hashing with Ketama semantics (auto-routing, minimal remapping, no central coordination), a client-side library (e.g., twemproxy, Envoy RING_HASH, or a Memcached client with libketama) is more accurate.

Redis Cluster is an excellent choice for many workloads — but knowing the difference between "Redis Cluster's slot-based partitioning" and "consistent hashing ring" demonstrates depth that separates 5 YOE candidates.

**Tip for interviews:** Five things separate strong 5 YOE candidates on consistent hashing: (1) explaining precisely *why* modulo hash causes `(N-1)/N` remapping while consistent hashing achieves `1/N` — with the ring mechanics, not just the claim; (2) knowing that **vnodes fix distribution variance** but don't change the `1/N` remapping guarantee — these are separate properties; (3) explaining the **hot key problem** (consistent hashing distributes keys uniformly but can't prevent traffic concentration on one key) and the key-splitting mitigation; (4) distinguishing **Redis Cluster hash slots from true consistent hashing** (Q40) — a common conflation; and (5) knowing **Maglev vs ring hash trade-offs** (O(1) lookup, better uniformity at small N, fixed memory table) — demonstrates awareness of production-scale LB design beyond textbook ring hash. If you can draw the ring, explain vnodes, and then immediately pivot to "but consistent hashing doesn't help with hot keys — here's how I'd fix that," you'll stand out clearly at the 5 YOE level.
