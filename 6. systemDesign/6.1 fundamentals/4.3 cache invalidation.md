# Cache Invalidation — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is cache invalidation famously considered one of the hardest problems in computer science?**
A: The quote, attributed to Phil Karlton ("There are only two hard things in Computer Science: cache invalidation and naming things"), points at a structural problem: caching inherently creates a second copy of truth that can silently diverge from the source of truth, and there's no universal, automatic way to know the instant the source changes — especially across distributed systems where the cache and the data source aren't co-located, the update path may bypass the cache entirely, and multiple caches at different layers may each hold different stale snapshots simultaneously. The difficulty isn't implementing any single invalidation technique — it's that every approach involves a genuine trade-off between consistency, complexity, and performance, with no universally "correct" answer independent of the specific application's tolerance for staleness.

**Q2. What is the fundamental trade-off all cache invalidation strategies navigate?**
A: Freshness (how quickly does the cache reflect the true current state) versus cost/complexity (how much overhead — latency, infrastructure, engineering effort — does achieving that freshness require) versus availability (can the system keep serving reads even when the invalidation mechanism itself is degraded or partitioned). Pushing harder on freshness generally means either accepting higher latency (synchronous invalidation before any write is considered complete) or higher complexity (event-driven invalidation pipelines, distributed coordination). Every invalidation strategy is a specific point chosen along these axes, not a free win.

**Q3. What are the three broad categories of cache invalidation strategy?**
A:
- **Time-based (TTL expiration)**: the cache entry has a fixed lifespan; after it elapses, the entry is considered stale regardless of whether the underlying data actually changed. Simple, requires no coordination with the write path, but creates a fixed staleness window even when data hasn't changed (wasted cache hit rate) or doesn't react fast enough when data has changed before TTL expiry.
- **Explicit/active invalidation**: the write path (application code, database trigger, deployment pipeline) explicitly notifies the cache that a specific entry is now invalid, the moment the underlying data changes. More precise and timely than TTL, but requires the write path and cache to be coupled — every code path that mutates data must remember to invalidate the right cache keys.
- **Event-driven/reactive invalidation**: changes to the source of truth emit events (via a message queue, change data capture stream, or pub/sub mechanism) that downstream caches subscribe to and react to independently — decoupling the writer from needing to know which caches exist or what their keys are.

**Q4. What is the difference between "invalidation" and "eviction"?**
A: Invalidation means marking a cache entry as no longer valid because the underlying data has changed — a correctness-driven removal. Eviction means removing a cache entry to free up space for other entries (LRU, LFU, or TTL-based capacity management, covered in the edge caching guide) — a capacity-driven removal, independent of whether the data is still accurate. An entry can be evicted while still perfectly valid (simply because the cache ran out of room), and an entry can become invalid while remaining physically present in the cache until something actively invalidates or it naturally expires. Conflating the two is a common source of confusion in interview answers.

## Section 2: Application-Level Caching Patterns

**Q5. What is the cache-aside (lazy loading) pattern, and what does invalidation look like in it?**
A: The application code is responsible for checking the cache first; on a miss, it reads from the database, then explicitly populates the cache. On a write, the application updates the database, then explicitly invalidates (or updates) the corresponding cache entry:

```
def get_user(user_id):
    cached = cache.get(f"user:{user_id}")
    if cached: return cached
    user = db.query(user_id)
    cache.set(f"user:{user_id}", user, ttl=300)
    return user

def update_user(user_id, data):
    db.update(user_id, data)
    cache.delete(f"user:{user_id}")  # invalidation
```

This is the most common application-level caching pattern (used heavily with Redis/Memcached). Invalidation here is explicit and application-driven — the cache itself has no awareness of the database; it's purely the application's responsibility to keep them in sync.

**Q6. What is write-through caching, and how does its invalidation behavior differ from cache-aside?**
A: In write-through, every write goes through the cache first (or simultaneously to both cache and database as a single logical operation) — the cache is always updated synchronously as part of the write path, rather than being invalidated and left to repopulate lazily on the next read. This means there's no "miss after every write" the way cache-aside's delete-then-repopulate approach causes, but it requires every write code path to go through the caching layer rather than writing to the database directly — a stricter architectural constraint than cache-aside's looser coupling.

**Q7. What is write-behind (write-back) caching, and what invalidation/consistency risk does it introduce?**
A: Writes go to the cache immediately (fast, low-latency write acknowledgment to the caller) and are asynchronously flushed to the underlying database afterward, often batched. This is great for write-heavy workloads needing low write latency, but introduces a durability/consistency risk: if the cache fails before the asynchronous flush completes, the write is lost entirely — the database never saw it. It also means any other system reading directly from the database (bypassing the cache) sees stale data until the flush completes. Write-behind is appropriate only when the cache layer itself has strong durability guarantees (e.g., persisted, replicated) and the application can tolerate eventual (not immediate) database consistency.

**Q8. Why is "update the cache" generally riskier than "invalidate (delete) the cache" on a write?**
A: Updating the cache on write means computing or copying the new value into the cache as part of the write path — if that computation/copy logic has any bug, race condition, or doesn't perfectly match what a fresh read from the database would produce, the cache silently diverges from the database with no automatic correction mechanism (no future cache miss will trigger a fix, since the entry technically still exists and appears valid). Deleting (invalidating) the cache on write is simpler and self-correcting: the next read is guaranteed to be a cache miss, fetching the canonical fresh value directly from the database and repopulating the cache from that authoritative source — there's no way for the cache to drift from a stale, manually-maintained "update" path. This is why "delete on write, repopulate on next read" (cache-aside with delete-based invalidation) is generally the safer default recommendation over "update cache value directly on write."

## Section 3: The Classic Race Condition

**Q9. What is the race condition between database writes and cache invalidation, and why does ordering matter?**
A: Consider the cache-aside write path: should you invalidate the cache *before* or *after* writing to the database? Both orderings have a race condition window:

**Invalidate-then-write** (delete cache, then update DB):
1. Thread A: deletes cache entry.
2. Thread B (concurrent read): cache miss, reads *old* value from DB (Thread A's write hasn't committed yet), repopulates cache with the *old* value.
3. Thread A: writes new value to DB.
4. Result: cache now holds the old value indefinitely (until TTL expiry), even though the DB has the new value — a stale cache with no further trigger to correct it until TTL.

**Write-then-invalidate** (update DB, then delete cache):
1. Thread A: writes new value to DB.
2. Thread B (concurrent read, started just before Thread A's write committed): reads *old* value from DB (depending on isolation level/replication lag), repopulates cache with the *old* value.
3. Thread A: deletes cache entry — but Thread B's repopulation with the old value happened *after* this delete.
4. Result: same outcome — stale cache with old value, no further trigger to correct it until TTL.

**Q10. Which ordering is generally recommended despite both having race windows, and why?**
A: Write-then-invalidate (update DB first, then delete cache) is generally recommended, because the race window is typically much narrower and harder to trigger in practice. For the race to manifest, a concurrent read has to (a) start, (b) read stale data from the DB, and (c) complete its cache repopulation — all happening to land *after* the invalidating delete completes, which is a tighter timing window than the invalidate-then-write ordering, where the window is open for the entire duration of the database write itself (which can be much longer than a cache repopulation, especially for writes involving multiple statements, business logic, or replication). Neither ordering eliminates the race entirely — only TTL-based expiration (acting as an eventual self-correcting safety net) and more sophisticated patterns (Q11-13) fully close the gap.

**Q11. What is the "double-delete" pattern and what problem does it address?**
A: A defensive pattern: delete the cache entry, write to the database, then delete the cache entry *again* after a short delay (e.g., a few hundred milliseconds, or after the write is confirmed to have propagated to any read replicas). The second delayed delete catches the specific race window where a concurrent read repopulated the cache with stale data between the first delete and the database write completing. This doesn't eliminate the race in a strictly theoretical sense (a sufficiently adversarial timing could still slip through) but closes the realistic window significantly for most production traffic patterns, at the cost of an extra cache operation and added complexity (managing the delay, ensuring the second delete actually executes even if the first request's process crashes — often requiring a reliable delayed-job/queue mechanism rather than an in-process `sleep`).

**Q12. Why does TTL still matter even with explicit invalidation logic in place?**
A: TTL acts as a self-healing safety net / eventual-consistency backstop for exactly the race conditions described in Q9-11 — even if an invalidation race causes the cache to hold a stale value indefinitely from the application's invalidation logic's perspective, a TTL guarantees that staleness has a hard upper bound (the cache entry will expire and be repopulated fresh, correctly, no later than the TTL duration after it was last set). This is why production caching systems almost always combine explicit invalidation (for fast, common-case freshness) with a TTL (for guaranteed worst-case staleness bounds) rather than relying on either mechanism alone — explicit invalidation alone has no recovery path for races/bugs; TTL alone has unnecessary staleness in the common case where nothing went wrong.

**Q13. How does read-through caching with a short lock/lease reduce this race condition risk?**
A: Some caching architectures (notably patterns popularized by Facebook's "Memcache at Scale" paper) use a "lease" mechanism: when a cache miss occurs, the cache returns a special "lease token" to the requesting client (rather than nothing), and any subsequent attempt to populate that key requires presenting a valid lease token — preventing a stale concurrent write (from a read that started before an invalidating delete) from repopulating the cache with outdated data, since its lease would have been invalidated by the delete. This adds meaningful complexity (lease issuance, validation, expiry) but directly closes the race window at the caching-layer level rather than relying on timing-dependent patterns like double-delete.

## Section 4: Distributed Caching and Multi-Instance Invalidation

**Q14. What additional invalidation complexity arises when an application has multiple instances, each with its own local in-process cache?**
A: A purely local (in-process, e.g., a simple in-memory dictionary or Caffeine/Guava cache) cache is the fastest possible cache (no network round-trip at all), but a write on one application instance has no automatic way to inform the local caches on every *other* instance that their copy is now stale — each instance's local cache can independently drift, serving stale data to whichever users happen to be routed to that instance, for as long as its local TTL allows. This is a fundamentally different problem from single-shared-cache invalidation (like a centralized Redis instance, where one delete is visible to all readers immediately) — distributed local caches require an explicit fan-out mechanism to propagate invalidation across instances.

**Q15. What is pub/sub-based cache invalidation, and how does it solve the multi-instance local cache problem?**
A: When any application instance writes data and needs to invalidate a key, it publishes an invalidation message (e.g., via Redis Pub/Sub, Kafka, or a similar message bus) containing the affected cache key(s); every application instance subscribes to this invalidation channel and, upon receiving a message, deletes the corresponding entry from its own local in-process cache. This combines the speed of local in-process caching (no network round-trip on cache *hits*) with the correctness of centralized invalidation (every instance learns about writes promptly), at the cost of running and maintaining a pub/sub messaging layer and accepting that invalidation propagation isn't instantaneous (some small window between publish and every subscriber processing the message).

**Q16. What is Change Data Capture (CDC) and how is it used for cache invalidation?**
A: CDC is a technique for capturing row-level changes (inserts, updates, deletes) directly from a database's transaction/replication log (e.g., MySQL binlog, Postgres logical replication, via tools like Debezium) and streaming them as structured events to downstream consumers — without requiring the application's write path to explicitly emit invalidation events itself. A cache invalidation service subscribes to this CDC stream and invalidates the relevant cache keys whenever a corresponding row changes. This decouples invalidation logic entirely from application code (no risk of a developer forgetting to add a `cache.delete()` call somewhere in a complex write path) and catches *any* write to the data, including ones made by background jobs, direct database scripts, or other services that bypass the main application's write path entirely — at the cost of needing CDC infrastructure and accepting the (typically small, sub-second) propagation latency inherent in streaming from a transaction log.

**Q17. What is the trade-off between application-driven explicit invalidation and CDC-driven invalidation?**
A: Application-driven invalidation (Q5, explicit `cache.delete()` calls in write code paths) is simpler to set up initially (no extra infrastructure) and can be very precise/immediate (invalidation happens in the same code path as the write, no propagation delay), but is fragile — every single write path, including ones added later by other engineers who may not know about the caching layer's invalidation requirements, must remember to include the correct invalidation call, or the cache silently goes stale with no automatic detection. CDC-driven invalidation is more robust (catches all writes regardless of code path, including ones outside the application) and decouples invalidation logic from the application's write code entirely, but requires meaningfully more infrastructure (CDC pipeline, schema/event mapping, monitoring for pipeline lag) and introduces a small but nonzero propagation delay that pure application-driven invalidation (executed synchronously in the same request) doesn't have.

## Section 5: Tag-Based and Dependency-Based Invalidation

**Q18. What is the limitation of single-key invalidation when one underlying data change affects many cached entries?**
A: If a single piece of data is referenced by many different cached responses (e.g., an author's name change should invalidate every cached page that displays content by that author — which could be hundreds of cached article pages), simple key-based invalidation requires knowing and explicitly invalidating every single affected cache key — which is often impractical, since the write path for "update author name" has no inherent knowledge of which article pages happen to display that author. This is the many-to-many invalidation problem: one data change, many dependent cache entries, no direct key mapping between them.

**Q19. What is tag-based (or surrogate-key-based) invalidation and how does it solve the many-to-many problem?**
A: Rather than invalidating by the cache's primary key (the URL or request identifier), each cached entry is additionally tagged with one or more dependency identifiers at the time it's cached — e.g., a cached article page tagged with `author:42` and `category:tech`. When the author's data changes, the invalidation system issues a single "invalidate everything tagged `author:42`" command, and the caching layer (which maintains an internal index from tags to the cache entries carrying them) purges every matching entry in one operation — without the write path needing to know the specific URLs/cache keys of every affected page. Fastly calls this mechanism "surrogate keys"; Varnish supports a similar pattern via custom VCL and the `xkey` module; many CDN providers expose tag-based purging as a first-class API feature.

**Q20. What's a concrete example of how surrogate-key invalidation would be implemented?**
A: When generating a response, the origin includes a header listing all the tags relevant to that response's dependencies:

```
Surrogate-Key: article-123 author-42 category-tech
```

The CDN/cache layer indexes the cached response under all three tags. Later, when the author's profile is updated, the application issues a purge request scoped to the tag, not a specific URL:

```
PURGE-TAG: author-42
```

This invalidates every cached response that included `author-42` in its `Surrogate-Key` header — potentially hundreds of article pages — in a single operation, without the invalidation logic needing to enumerate or even know about each individual affected URL.

**Q21. What is the operational cost of tag-based invalidation compared to simple key-based invalidation?**
A: The caching layer must maintain an additional index (tag → set of cache keys) alongside the primary cache key index, which consumes extra memory/storage and adds bookkeeping overhead on every cache write (updating the tag index) and every invalidation (looking up and purging potentially many entries per tag, rather than a single O(1) key deletion). For data with many cross-cutting dependencies (content management systems, e-commerce catalogs with shared attributes like brand/category), this overhead is well justified by the alternative (either over-broad invalidation — purging everything on any change — or under-invalidation — missing dependent pages and serving stale data). For simpler, narrowly-scoped caching needs, plain key-based invalidation remains simpler and sufficient.

## Section 6: Consistency Models and Staleness Tolerance

**Q22. How does the choice of invalidation strategy relate to the CAP theorem / consistency-availability trade-off?**
A: Strongly consistent invalidation (e.g., synchronous, blocking invalidation that must complete and be acknowledged across all cache replicas before a write is considered done) prioritizes consistency at the cost of write latency and availability during partition (if a cache replica is unreachable, the write can't complete or the system must choose to proceed anyway and risk inconsistency). Eventually consistent invalidation (asynchronous, fire-and-forget invalidation messages, TTL-based self-correction) prioritizes availability and lower write latency at the cost of a window during which different readers may see different (stale vs. fresh) data. Most production caching systems lean eventually consistent — the asynchronous, TTL-backed patterns described throughout this guide — because the cost of strict synchronous invalidation (write latency proportional to the slowest cache replica, reduced availability during network issues) is rarely justified relative to most applications' actual staleness tolerance.

**Q23. What determines an acceptable staleness window for a given piece of cached data, and how should an engineer decide?**
A: The business/product requirement for that specific data, not a generic technical default. Key questions: what's the real-world cost of a user seeing stale data for N seconds (a stale product price shown for 5 seconds before checkout might be a genuine financial/legal problem; a stale "like count" shown for 5 seconds is inconsequential)? How frequently does the underlying data actually change (a config value that changes once a year can tolerate a long TTL trivially; a stock ticker price cannot)? Is the staleness self-correcting and bounded (TTL-based) or potentially unbounded (a forgotten invalidation call with no TTL safety net)? A senior engineer's answer to "what should the cache TTL/invalidation strategy be" should always start from these questions rather than picking an arbitrary number.

**Q24. What is "read-your-own-writes" consistency and why does it matter specifically for cache invalidation UX?**
A: A guarantee that a user who just performed a write (e.g., updated their profile, posted a comment) will, on their very next read, see their own change reflected — even if other users might still briefly see stale cached data. This matters because even a technically "acceptable" eventual consistency window (a few hundred milliseconds, fine for the broader user base) can feel like a visible bug to the specific user who just made the change, if they immediately refresh and see their old data still displayed. Common implementations: route the writer's subsequent reads to bypass the cache entirely for a short window (e.g., via a sticky session or a short-lived "force fresh read" flag tied to that user's session), or ensure the write-path invalidation is synchronous enough that, combined with realistic UI refresh timing, the user practically never observes their own stale write.

## Section 7: Database and Query-Level Invalidation

**Q25. What is materialized view invalidation and how does it differ from key-value cache invalidation?**
A: A materialized view is a precomputed, stored result of a (often expensive) query, refreshed periodically or on a trigger, rather than recomputed on every read — conceptually a form of caching implemented at the database layer itself. Invalidation/refresh strategies include: scheduled full refresh (recompute the entire view on a fixed interval, simple but can be expensive and stale between refreshes), incremental/eager refresh (the database automatically updates only the affected rows of the view when underlying table data changes, supported natively by some databases like PostgreSQL's eager materialized view extensions or specialized systems), and on-demand refresh triggered by application logic. This differs from typical key-value cache invalidation in that the "cache" is itself a queryable database object with its own consistency guarantees from the database engine, rather than an external system the application must explicitly keep in sync.

**Q26. What is query result caching and what specific invalidation challenge does it pose?**
A: Caching the result of a specific SQL query (keyed by the query text + parameters) rather than caching domain objects by ID — common in ORMs and some database proxy layers. The invalidation challenge: a query result cache entry for `SELECT * FROM articles WHERE author_id = 42` has no simple, direct correspondence to "invalidate when article 99 changes" the way an ID-keyed cache (`article:99`) does — the database would need to track which cached queries' result sets *could* be affected by a write to any given row, which is a much harder dependency-tracking problem than simple key-based invalidation (related to the tag-based invalidation problem from Q18-21, but at the SQL query level). This is why query result caching is generally invalidated more conservatively (often by invalidating broad categories of queries, or using fairly short TTLs) rather than attempting precise per-row dependency tracking, unless using a specialized system built specifically for this (e.g., some GraphQL caching layers implement field-level dependency tracking for exactly this reason).

**Q27. How do ORMs typically handle cache invalidation for object-level caching, and what's a common pitfall?**
A: Many ORMs offer built-in or pluggable caching that automatically invalidates an object's cache entry when that object is saved/updated through the ORM's own write methods. The common pitfall: any write path that bypasses the ORM (a raw SQL query, a bulk update statement, a database migration script, a different service writing directly to the same table) silently doesn't trigger the ORM's automatic invalidation — leaving the ORM-managed cache stale with no warning, since from the ORM's perspective, nothing happened. This is a specific, very common instance of the broader application-driven-invalidation fragility problem (Q17) — and is one of the strongest practical arguments for CDC-based invalidation in systems where data is written from multiple paths/services, not just through a single application's ORM layer.

## Section 8: Scenario-Based Questions

**Q28. "Your e-commerce site caches product prices in Redis with a 5-minute TTL. A price change needs to be reflected within 10 seconds for legal/compliance reasons. What do you change?"**
A: A 5-minute TTL alone is far too loose for a 10-second freshness requirement — TTL-only invalidation is the wrong primary mechanism here. Add explicit invalidation on the write path: when a price update occurs (through whatever admin tool/pipeline updates prices), immediately call `cache.delete(f"product:{id}:price")` (or update the cache value directly, accepting the slightly higher risk discussed in Q8, given the strict latency requirement makes "wait for the next natural read to repopulate" potentially too slow if reads are infrequent for a given product). Keep a TTL as a safety net (perhaps reduced to something like 30-60 seconds) in case an invalidation call is ever missed due to a bug or a write path that bypasses the explicit invalidation logic — this bounds worst-case staleness even if the primary explicit-invalidation mechanism fails, while the explicit invalidation handles the common case well within the 10-second requirement.

**Q29. "You have 50 application server instances, each with a local in-memory cache for frequently-accessed config values. How do you ensure a config change propagates to all instances promptly?"**
A: Pub/sub-based invalidation (Q15) is the standard solution: when config changes (e.g., via an admin panel or config service), publish an invalidation event to a shared channel (Redis Pub/Sub, Kafka topic) containing the changed config key; every one of the 50 instances subscribes to this channel and evicts the corresponding entry from its local cache upon receiving the message, forcing the next read on that instance to repopulate from the authoritative config source. Combine with a moderate TTL as a safety net in case any instance misses a pub/sub message (e.g., due to a transient subscription disconnect) — bounding staleness even for that edge case. This preserves the latency benefit of local in-process caching for the common case (cache hits require zero network calls) while solving the multi-instance propagation problem.

**Q30. "A junior engineer proposes: 'Let's just set every cache TTL to 1 second so we never have to worry about explicit invalidation.' How do you respond?"**
A: This trades away nearly all of caching's benefit to avoid solving invalidation properly — at 1-second TTL, any data that's read more than roughly once per second per cache key essentially becomes a cache-miss-every-time system in practice, since most of those reads will land just after expiry, defeating the purpose of caching (reducing origin/database load) almost entirely for moderate-traffic keys, while still incurring all the operational complexity of running a caching layer. The right framing: TTL should be set based on the actual acceptable staleness window for that specific data (Q23) — and for data that genuinely needs sub-second freshness with high read volume, the correct solution isn't an artificially short TTL but proper explicit/event-driven invalidation (Q5, Q15-17) combined with a *much* longer TTL purely as a worst-case safety net, not as the primary freshness mechanism.

**Q31. "Your CDC-based invalidation pipeline (Debezium → Kafka → invalidation service) goes down for 10 minutes due to a Kafka cluster issue. What's the blast radius, and how would you have designed for this failure mode?"**
A: Blast radius: during the outage, any data written to the database during those 10 minutes never triggers invalidation — affected cache entries remain stale indefinitely *unless* a TTL safety net is also in place (reinforcing Q12's point: TTL matters precisely for failure scenarios like this, not just race conditions). Design considerations to flag: (1) always pair CDC-driven invalidation with a TTL backstop, sized to the maximum acceptable staleness if the pipeline is ever down — this turns "cache is stale forever" into "cache is stale for at most TTL duration, even during a full pipeline outage"; (2) monitor CDC pipeline lag/health explicitly (alerting if the consumer offset falls behind, or if no invalidation events have been processed in an unexpectedly long window) so the outage is detected and resolved quickly rather than silently degrading correctness; (3) consider whether the invalidation service should have a "catch-up" mechanism that, upon recovery, reprocesses the backlog of missed CDC events rather than just resuming from the current offset and permanently missing the gap.

**Q32. "How would you explain, to an interviewer, the single most important principle for designing a cache invalidation strategy?"**
A: Always pair whatever explicit/event-driven invalidation mechanism you build (for fast, common-case freshness) with a TTL-based safety net (for guaranteed worst-case staleness bounds) — because every explicit invalidation mechanism, no matter how well designed, has failure modes (missed code paths, race conditions, pipeline outages, bugs) where it silently fails to fire, and without a TTL backstop, those failures result in unboundedly stale data with no automatic recovery. The TTL doesn't need to be tight (it's a safety net, not the primary mechanism) — but its absence turns "an invalidation bug causes brief staleness" into "an invalidation bug causes permanent staleness," which is a qualitatively much worse failure mode. This single principle — defense in depth between explicit invalidation and TTL — is the throughline connecting nearly every pattern in this guide.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Invalidation vs eviction | Correctness-driven removal vs capacity-driven removal |
| Cache-aside | App checks cache, falls back to DB, explicitly invalidates on write |
| Write-through | Writes go through cache synchronously — no post-write miss |
| Write-behind | Writes hit cache first, async flush to DB — fast but riskier |
| Delete vs update on write | Delete is self-correcting; update can silently drift |
| Write-then-invalidate | Generally safer ordering than invalidate-then-write |
| Double-delete | Defensive delayed second delete to close the race window |
| Lease-based caching | Token-gated repopulation to prevent stale writes after invalidation |
| Pub/sub invalidation | Fan-out invalidation across distributed local in-process caches |
| CDC-based invalidation | Invalidate from the DB transaction log, decoupled from app code |
| Tag/surrogate-key invalidation | Invalidate many dependent entries via shared tags, not individual keys |
| TTL as safety net | Bounds worst-case staleness even when explicit invalidation fails |
| Read-your-own-writes | The writer must see their own change immediately, even if others briefly don't |

---

**Tip for interviews:** Five things separate strong candidates on cache invalidation: (1) being able to **draw out the race condition** between cache delete and DB write (Q9) on a whiteboard, with both orderings, and explain why write-then-invalidate is the safer default despite still having a window; (2) knowing **why delete is preferred over update** on the write path (Q8) — the self-correcting property is a subtle but important insight; (3) being able to articulate the **defense-in-depth principle**: explicit invalidation for the common case, TTL as the safety net for failure modes (Q12, Q31-32) — this is the single most reliable signal of real production experience; (4) knowing **tag-based/surrogate-key invalidation** (Q19-20) by name for the many-to-many invalidation problem, rather than only knowing single-key invalidation; and (5) recognizing that **invalidation strategy should be derived from the specific data's staleness tolerance**, not a one-size-fits-all default (Q23) — the junior engineer's "just set TTL to 1 second" question (Q30) is a great test of this judgment.
