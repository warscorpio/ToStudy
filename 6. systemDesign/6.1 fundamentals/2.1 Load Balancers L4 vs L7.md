# Load Balancers: L4 vs L7 — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a load balancer and what problem does it solve?**
A: A load balancer sits between clients and a pool of backend servers, distributing incoming traffic so no single server bears all the load. It solves three core problems: capacity (spread traffic across more nodes), availability (route around unhealthy nodes), and operability (enable rolling deployments without downtime). Without one, horizontal scaling is pointless — you'd need clients to know about all backend nodes.

**Q2. What does "L4" and "L7" actually refer to?**
A: They refer to layers in the OSI model:
- **L4 (Transport Layer)** — operates at the level of TCP/UDP. It sees IP addresses and ports, but not the content of the packets.
- **L7 (Application Layer)** — operates at the level of HTTP, gRPC, WebSocket, etc. It can read and route based on request content — headers, URL paths, cookies, query params, body.

The "layer" describes what the load balancer looks at when making routing decisions.

**Q3. What does an L4 load balancer actually do with a connection?**
A: When a TCP connection arrives, the L4 LB picks a backend based on the source IP/port and destination port — typically using NAT (Network Address Translation) or DSR (Direct Server Return) — and forwards raw TCP segments to that backend. The client and backend establish what looks like a direct TCP connection. The LB doesn't read the HTTP payload at all — it's just moving bytes.

**Q4. What does an L7 load balancer actually do differently?**
A: It terminates the TCP (and usually TLS) connection from the client, fully reads the incoming HTTP request (headers, URL, body), makes a routing decision based on that content, and then opens a new (or reuses a pooled) TCP connection to the selected backend. It's a full HTTP proxy. This means it can inspect, mutate, or reject requests before they reach the backend.

**Q5. What is TLS termination, and which layer handles it?**
A: TLS termination means decrypting the client's HTTPS traffic so the backend receives plain HTTP. L7 LBs terminate TLS by design (they must, to read the HTTP content). L4 LBs can also terminate TLS if configured, but many L4 deployments use "TLS passthrough" — forwarding the encrypted bytes to the backend, which handles decryption itself. TLS passthrough preserves end-to-end encryption but removes the LB's ability to inspect content.

## Section 2: How Routing Works

**Q6. How does an L4 load balancer decide which backend to send traffic to?**
A: Based only on L3/L4 metadata — primarily the source IP, source port, and destination port. Common algorithms:
- **Round-robin** — each new connection goes to the next server in rotation.
- **IP hash** — hash of source IP determines the backend (provides stickiness by IP).
- **Least connections** — send new connections to the server with the fewest active ones.

It cannot differentiate two HTTP requests on the same TCP connection.

**Q7. How does an L7 load balancer decide which backend to send traffic to?**
A: It routes based on request content. Common strategies:
- **Path-based routing** — `/api/users` → users service, `/api/payments` → payments service.
- **Host-based routing** — `api.example.com` → API servers, `static.example.com` → CDN/static servers.
- **Header-based routing** — e.g., `X-Tenant-ID: acme` → Acme's dedicated cluster.
- **Cookie-based stickiness** — insert/read a cookie to pin a user to a specific backend.
- **HTTP method** — e.g., `GET` vs `POST` to different backends.
- **Canary/weighted routing** — send 5% of traffic to a new version, 95% to stable.

**Q8. What is connection multiplexing, and which load balancer type supports it?**
A: Connection multiplexing is where the LB maintains a pool of long-lived connections to backends and reuses them for multiple client requests, rather than opening a new backend connection per client connection. Only an L7 LB can do this (it has to parse individual HTTP requests to know where one request ends and another begins). This significantly reduces backend connection overhead and is especially valuable for HTTP/2 and gRPC.

**Q9. What is "sticky sessions" and how do L4 vs L7 handle it differently?**
A: Sticky sessions ensure a user's requests always land on the same backend (important for stateful apps). L4 LBs achieve stickiness via IP hash — same source IP always goes to the same backend, but this breaks behind NAT (many users share one IP) and can cause imbalance. L7 LBs can do proper cookie-based stickiness — insert a cookie on first response, read it on subsequent requests — which is far more precise and works behind NAT.

## Section 3: Performance & Scale

**Q10. Which is faster — L4 or L7? Why?**
A: L4 is generally faster and lower-latency per connection because it does less work — no TLS termination, no HTTP parsing, no header inspection. It's essentially packet forwarding. L7 adds overhead: TLS handshake (though session resumption helps), HTTP parsing, routing logic evaluation, and the overhead of being a full HTTP proxy (two TCP connections instead of one forwarded one).

For latency-sensitive, high-throughput workloads (e.g., real-time gaming, raw TCP services), L4 wins. For most web workloads, the overhead of L7 is negligible and its features are well worth it.

**Q11. How does an L4 LB handle millions of connections efficiently?**
A: Many L4 LBs operate in kernel space or use kernel bypass techniques (e.g., DPDK, XDP/eBPF) to forward packets without expensive user-space context switches. Some implementations (like Google's Maglev) use ECMP (Equal-Cost Multi-Path routing) at the network layer to distribute traffic across a fleet of LB instances, each maintaining a consistent hash table to ensure the same flow always goes to the same backend — avoiding per-flow state on any single machine.

**Q12. Does an L7 LB become a bottleneck at high scale?**
A: It can be if not designed carefully, since it handles full HTTP processing. Mitigations include: running a fleet of L7 LB instances (horizontally scaled, usually fronted by an L4 LB or DNS-based load balancing), connection pooling to reduce backend connection overhead, efficient HTTP/2 multiplexing, and offloading TLS to hardware or specialized instances. Products like Envoy and NGINX are purpose-built for high-throughput L7 proxy workloads.

## Section 4: Features & Capabilities Comparison

**Q13. What health checking capabilities differ between L4 and L7?**
A: L4 health checks are basic — TCP connect to the backend port. If the TCP handshake succeeds, the backend is considered healthy, even if the app itself is returning 500s or is deadlocked. L7 health checks are semantic — send an HTTP GET to `/health`, verify a 200 OK response and optionally validate the response body. This means L7 LBs catch application-level failures that L4 LBs miss entirely.

**Q14. Can an L7 load balancer do rate limiting? Can an L4?**
A: L7 LBs can implement per-route, per-user, or per-IP rate limiting based on HTTP attributes (e.g., headers, tokens). This is a common use case — API gateways built on L7 proxies (Envoy, NGINX, Kong) do this natively. L4 LBs can only do connection-level rate limiting (limit connections per IP), which is crude and doesn't map well to HTTP request semantics.

**Q15. What other L7-only features should I know for interviews?**
A: Key ones:
- **Request/response header manipulation** — add, remove, or rewrite headers (e.g., inject `X-Request-ID`, strip internal headers before sending to client).
- **Authentication/AuthZ offloading** — verify JWTs, API keys, or OAuth tokens at the LB layer, so backends don't have to.
- **Circuit breaking** — track error rates per backend and temporarily stop sending traffic to unhealthy ones, avoiding cascading failures.
- **Retry logic** — automatically retry on `503` or network errors, with configurable back-off.
- **Request mirroring/shadowing** — duplicate live traffic to a shadow environment for testing without impacting production.
- **Observability** — emit per-request metrics, access logs, and distributed tracing spans, since it sees every request.
- **WebSocket/gRPC support** — protocol-aware handling of long-lived streams.

**Q16. Can an L4 LB handle WebSockets?**
A: Yes — WebSockets start as an HTTP Upgrade request but then become a persistent TCP connection. An L4 LB handles them naturally (it just forwards TCP streams), but it can't understand or route based on the WebSocket handshake. An L7 LB can parse the Upgrade request, route it intelligently (e.g., to a specific service), and terminate the TLS. Once the WebSocket is established and the L7 LB's job is to forward the stream, behavior is similar. Envoy, for example, has explicit protocol-aware WebSocket support.

## Section 5: Real-World Architecture

**Q17. In a real production system, do you use L4 or L7 — or both?**    
A: Typically both, layered. A common pattern:
1. **DNS/anycast** routes traffic geographically to a data center or PoP.
2. **L4 LB fleet** (e.g., AWS NLB, Google Maglev) distributes raw TCP connections across a pool of L7 LBs — providing DDoS absorption and horizontal scale for the L7 tier itself.
3. **L7 LB fleet** (e.g., Envoy, NGINX, AWS ALB) terminates TLS, parses HTTP, and routes to microservices.
4. **Service mesh sidecars** (e.g., Envoy as a sidecar in Istio) provide L7 load balancing within the cluster, service-to-service.

**Q18. How do cloud providers map to L4/L7?**
A: 
- **AWS**: NLB (Network Load Balancer) = L4; ALB (Application Load Balancer) = L7.
- **GCP**: Network Load Balancer = L4; HTTP(S) Load Balancer = L7.
- **Azure**: Azure Load Balancer = L4; Azure Application Gateway = L7.
- **Self-hosted**: HAProxy operates in both modes; NGINX and Envoy are primarily L7.

**Q19. What is a service mesh, and how does it relate to L7 load balancing?**
A: A service mesh (e.g., Istio, Linkerd) deploys a lightweight L7 proxy (typically Envoy) as a sidecar alongside every service instance. This moves L7 load balancing, retries, circuit breaking, mTLS, and observability inside the cluster, handling east-west traffic (service-to-service). Traditional L7 LBs handle north-south traffic (client-to-cluster). They complement each other.

**Q20. What is an API Gateway, and how does it differ from an L7 LB?**
A: An API Gateway is essentially an L7 LB with a product layer on top — authentication, rate limiting, API key management, developer portal, versioning, and monetization. Under the hood, products like Kong, Apigee, or AWS API Gateway are L7 proxies with those extra management features. For internal microservice routing, a plain L7 LB/service mesh is more appropriate; for public-facing APIs, an API Gateway adds the policy enforcement and developer-experience layer.

## Section 6: Algorithms Deep-Dive

**Q21. Walk me through the most common load balancing algorithms and when to use each.**
A:
- **Round Robin** — requests distributed cyclically. Simple; best when backends are homogeneous and requests have similar cost.
- **Weighted Round Robin** — like round robin but some backends receive proportionally more traffic (useful for canary deployments or mixed-capacity nodes).
- **Least Connections** — new request goes to the backend with fewest active connections. Better than round robin when requests have variable processing time (avoids piling on a slow backend).
- **Least Response Time** — routes to the backend with the lowest combination of active connections and response latency. Good for latency-sensitive APIs.
- **IP Hash** — hash of client IP determines backend. Provides sticky routing without cookies; breaks if backend count changes.
- **Random with 2 choices (Power of 2)** — pick 2 backends at random, route to the less loaded one. Achieves near-optimal balance with very low coordination overhead; commonly used in distributed L7 proxies.
- **Consistent hashing** — used in distributed caches/databases; ensures minimal redistribution when nodes are added/removed.

**Q22. What is the "Power of Two Choices" algorithm, and why is it popular in distributed systems?**
A: Instead of checking all N backends (expensive) or picking one at random (poor balance), you pick 2 at random and route to the less loaded one. It eliminates the "thundering herd" problem of purely random selection while avoiding the synchronization cost of global least-connections tracking. Netflix's Ribbon and many Envoy deployments use this. It gives O(log log N) max load vs O(log N/log log N) for random, provably approaching optimal.

## Section 7: Failure Modes & Edge Cases

**Q23. What happens if a backend fails mid-connection in an L4 vs L7 LB setup?**
A: In L4 (especially passthrough mode), the client directly feels the TCP RST or timeout from the backend failing — the error is visible to the client with no ability for the LB to intervene. In L7, the LB can detect the backend failure (RST, timeout, HTTP 5xx) and potentially retry on a different backend transparently, absorbing the failure before the client sees it — assuming the request is idempotent.

**Q24. What is a "thundering herd" in the context of load balancers, and how is it mitigated?**
A: When many backends simultaneously recover from a failure or a new LB node comes online with a fresh empty connection pool, a burst of connections all arrive at backends at once — overwhelming them. Mitigations: slow-start in NGINX/Envoy (gradually ramp up traffic to a recovering backend), connection pool warming, and jitter in retry backoff to stagger reconnections.

**Q25. Can an L7 load balancer itself become a SPOF?**
A: Yes, if you only have one. Production setups always run multiple L7 LB instances, fronted by an L4 LB or DNS round-robin or Anycast to ensure the LB tier itself is highly available. The L4 LB tier is easier to make robust (stateless, kernel-level, can use BGP/ECMP) — so the typical defense-in-depth is: redundant L4 → redundant L7 → backends.

## Section 8: Scenario-Based Questions

**Q26. "Your microservices team wants to route /v1/orders to the orders service and /v1/payments to the payments service. What do you use and why?"**
A: An L7 load balancer with path-based routing. An L4 LB can't inspect HTTP paths — it would only know the destination port (e.g., 443) and can't split traffic to different backends by URL. This is a textbook L7 use case. In AWS, that's an ALB with listener rules; in Kubernetes with Envoy/Istio, you'd configure a VirtualService with match conditions on path prefix.

**Q27. "A client complains that after login they're immediately logged out — the next request hits a different backend that doesn't have their session. How do you solve this?"**
A: Session state is stored in memory on individual backends — the classic stickiness problem. Solutions in order of preference:
1. **Best — externalize session storage**: Move session state to Redis/Memcached so any backend can serve it — no stickiness needed.
2. **Intermediate — cookie-based sticky sessions at L7 LB**: Insert a sticky cookie to pin the user to one backend, but this creates uneven load and breaks on backend restart.
3. **Avoid — IP-based stickiness (L4)**: Unreliable behind NAT and can create severe imbalance.

The real fix is making the app stateless; stickiness is a crutch.

**Q28. "You need to do a canary release — send 5% of traffic to v2 and 95% to v1. Can your L4 LB do this?"**
A: Not precisely. An L4 LB can do weighted round-robin by connection, which approximates a percentage, but it has no visibility into which "type" of user or request it's sending — and percentages are approximate since it's connection-level. A true canary deployment with fine-grained control (e.g., "only users with header `X-Beta: true`" or "5% of requests to the /checkout path") requires an L7 LB, which can apply weighted routing rules per HTTP attribute.

**Q29. "Your service is getting hammered by a DDoS at the HTTP layer — tons of requests with a specific malicious User-Agent. Where do you mitigate it?"**
A: At the L7 LB / WAF layer — because only an L7 system can inspect HTTP headers like `User-Agent`. Block the pattern there, before requests even reach your backends. An L4 LB can't help here since it can't read HTTP headers. For volumetric DDoS (bandwidth/connection flood), you'd also want upstream L4/network-layer mitigations (e.g., BGP blackholing, scrubbing centers) since the L7 tier can be overwhelmed before it even gets to inspect requests.

**Q30. "You have a gRPC service. Should you use an L4 or L7 LB? What's the trap with L4 here?"**
A: Use an L7 LB with gRPC support (e.g., Envoy). The trap with L4 is that gRPC runs over HTTP/2, which multiplexes many RPC streams over a single long-lived TCP connection. An L4 LB that routes per TCP connection will send all RPC calls on that connection to the same backend — effectively no load balancing at the RPC level. An L7 LB that understands HTTP/2 can balance at the stream (individual RPC call) level, spreading load correctly across backends.

## Quick Comparison Table

| Feature            | L4 (Transport)                  | L7 (Application)               |
|---                 |---                              |    ---                         |
| OSI Layer          | 4 (TCP/UDP)                     | 7 (HTTP, gRPC, etc.)           |
| Routing based on   | IP, port                        | URL, headers, cookies, method  |
| TLS handling       | Passthrough or terminate        | Always terminates              |
| Health checks      | TCP connect                     | HTTP response (semantic)       |
| Sticky sessions    | IP hash (crude)                 | Cookie-based (precise)         |
| Performance        | Lower latency, less overhead    | Slightly higher overhead       |
| HTTP/2 + gRPC      | Per-connection only             | Per-stream (correct)           |
| Connection pooling | No                              | Yes                            |
| Rate limiting      | Connection-level only           | Per-request/per-user           |
| Retries            | No                              | Yes (idempotent requests)      |
| Observability      | Limited (byte counts)           | Per-request metrics/logs       |
| Circuit breaking   | No                              | Yes                            |
| Use cases          | Raw TCP, gaming, streaming, DNS | APIs, HTTP microservices, gRPC |
| AWS equivalent     | NLB                             | ALB                            |

---

**Tip for interviews:** The gRPC/HTTP2 question (Q30) is a genuine gotcha that many 5 YOE engineers miss. If you know L4 doesn't load-balance at the stream level for HTTP/2, and *why*, you'll stand out. Also be ready to sketch the two-layer architecture (L4 → L7 fleet → services) on a whiteboard.
