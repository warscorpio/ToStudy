# Least Response Time — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Least Response Time (LRT) algorithm?**
A: A dynamic load balancing algorithm that routes each new request to the backend with the best combination of active connections and observed response latency. It is the most signal-rich of the common algorithms — unlike Round Robin (which ignores state) or Least Connections (which tracks only connection count), LRT additionally measures how fast backends are actually responding and uses that as a routing signal. The backend with the lowest "load score" — a function of both busyness and speed — receives the next request.

**Q2. What is the scoring formula LRT uses?**
A: Implementations vary, but the two most common formulas are:

**Multiplicative (NGINX Plus, common default):**
```
score(backend) = active_connections * mean_response_time
```
A backend with 2 connections and 100ms avg latency scores 200. One with 3 connections and 10ms avg scores 30 — it's preferred despite more connections because it's much faster.

**Additive (some implementations):**
```
score(backend) = active_connections + (mean_response_time / latency_unit)
```

The backend with the lowest score is selected. Ties are broken by round-robin or random selection.

**Q3. Why does multiplying connections by response time give a better signal than just connection count?**
A: Connection count approximates queue depth; response time approximates service rate. Multiplying them approximates the expected wait time for a request sent to that backend right now — analogous to Little's Law from queueing theory: `L = λW` (average number in system = arrival rate × average time in system). A backend with many fast connections may have a lower wait time than one with few slow connections. Pure LC misses this — LRT captures it.

**Q4. What is Little's Law and how does it apply to LRT?**
A: Little's Law states that in a stable queueing system: `L = λW`, where L is the average number of requests in the system, λ is the throughput (requests/sec), and W is the average time a request spends in the system. Rearranging: `W = L / λ`. LRT approximates W (expected wait time) per backend by using active connections (≈ L) and response time (≈ 1/λ in a single-server model). The scoring formula `connections * response_time` is a heuristic for this expected wait. Mentioning Little's Law in an interview when discussing LRT is a strong differentiator.

**Q5. How is response time measured and stored at the LB?**
A: The LB timestamps each request when it's forwarded to a backend and records the elapsed time when the response returns. This per-request measurement is aggregated into a moving average or exponentially weighted moving average (EWMA) per backend. EWMA gives more weight to recent measurements:

```
new_avg = (1 - α) * old_avg + α * latest_sample
```

Where α (smoothing factor, e.g., 0.1–0.3) controls how quickly the average responds to changes. A higher α reacts faster to sudden slowdowns but is noisier; a lower α is smoother but slower to adapt.

**Q6. What is EWMA and why is it preferred over a simple moving average for LRT?**
A: Exponentially Weighted Moving Average weights recent observations more heavily than older ones without needing to store a full window of samples. For LRT:
- A simple moving average over the last N samples has equal weight for all — a latency spike from 2 minutes ago counts the same as one from 2 seconds ago.
- EWMA decays old observations geometrically — a spike 10 samples ago has negligible weight. This means EWMA adapts quickly to a backend suddenly becoming slow (responds in a few requests) and also recovers quickly when it speeds back up.
- EWMA requires only two values per backend (current average and smoothing factor) — O(1) storage regardless of traffic volume.

## Section 2: Variants and Implementations

**Q7. How does NGINX Plus implement Least Response Time?**
A: Via the `least_time` directive in the upstream block:

```nginx
upstream backend_pool {
    least_time header;       # or: least_time last_byte;
    server backend1;
    server backend2;
    server backend3;
}
```

Two measurement modes:
- **`header`**: measures time from request send to receiving the first byte of the response header. Captures backend processing time but not response body transmission — good for APIs with small payloads.
- **`last_byte`**: measures time until the full response body is received — includes both backend processing and network transfer time. Better for file downloads or large payloads.
- **`inflight`** (optional modifier): also factors in the number of incomplete requests, similar to combining LC with LRT.

NGINX Plus tracks the EWMA of response time per upstream server and combines it with active connection count using the multiplicative formula.

**Q8. How does Envoy implement Least Response Time?**
A: Envoy doesn't have a dedicated "least_time" policy — instead its `LEAST_REQUEST` policy with the `active_request_bias` parameter approximates LRT:

```yaml
lb_policy: LEAST_REQUEST
least_request_lb_config:
  active_request_bias:
    default_value: 1.0   # Higher = more weight on active requests vs latency
    runtime_key: "lb.active_request_bias"
  choice_count: 2        # P2C: pick 2 random backends, compare scores
```

Envoy's approach uses P2C under the hood (pick 2, compare) rather than scanning all backends — making it O(1) per selection. True per-backend latency tracking in Envoy is handled via outlier detection and health check latency — which feeds into locality weighted routing but not per-endpoint LRT directly. For full LRT, Envoy users typically combine `LEAST_REQUEST` with outlier detection.

**Q9. How does HAProxy implement response-time-based routing?**
A: HAProxy's native algorithms don't include true LRT. The closest approaches:
- **`leastconn`** — LC, not LRT.
- **Agent health checks** — HAProxy can query a sidecar agent on each backend that reports a dynamic weight based on observed latency/CPU. The LB then uses Weighted Least Connections with those agent-provided weights.
- **`be_sess_rate`** and ACLs — session rate-based dynamic routing using HAProxy's stick tables.

For true LRT in HAProxy environments, the common pattern is to run an external health-check agent that periodically measures backend response time and adjusts server weights via HAProxy's runtime API (`set server`), effectively implementing dynamic WRR driven by latency.

**Q10. What is the difference between LRT and Least Request (in the Envoy/gRPC sense)?**
A: These terms are sometimes conflated but are distinct:
- **Least Response Time**: routing signal is measured latency (historical response times), optionally combined with connection count.
- **Least Request (Least Connections at request level)**: routing signal is the number of active in-flight requests/streams — no latency measurement. This is Envoy's `LEAST_REQUEST` default without latency weighting.

Envoy's `LEAST_REQUEST` is fundamentally LC at the request level (more accurate than TCP connection LC for HTTP/2) with an optional bias toward latency via `active_request_bias`. True LRT requires latency history tracking, which Envoy handles indirectly via outlier detection rather than per-request EWMA.

## Section 3: When LRT Wins and When It Fails

**Q11. What workloads benefit most from LRT?**
A: LRT is most valuable when:
- **Latency SLAs are tight** (p99 < 50ms) — even small differences in backend response times matter; LRT steers requests toward faster backends.
- **Grey failures are common** — backends that are slow but not down (GC pauses, CPU steal, noisy neighbours in VMs, hot threads) aren't caught by health checks but show elevated response time. LRT deprioritizes them automatically.
- **Backend performance is heterogeneous and variable** — mixed hardware generations, backends with unpredictable latency spikes.
- **Mixed payload sizes** — responses vary widely in size, causing variable backend processing time not reflected in connection count alone.
- **Stateless services where latency variance is the primary load signal** — LRT is most useful when you can't predict which request will be expensive.

**Q12. When is LRT overkill and simpler algorithms are preferable?**
A: LRT adds measurement overhead and algorithmic complexity. It's overkill when:
- **Backends are fast and uniform** (p99 < 5ms, low variance) — the latency signal is noise, not signal. Round Robin is equally effective and simpler.
- **Request cost is the dominant variable** (not backend speed) — some requests are inherently expensive regardless of backend. LRT can't distinguish a slow backend from an expensive request; LC or LRT both route away from backends holding expensive requests.
- **Traffic volume is very low** (< 10 req/sec) — EWMA at low QPS is statistically noisy; a single slow request skews the average dramatically. WRR with manually tuned weights is more predictable.
- **Short-lived connections dominate** — if connections close before the LB can act on the latency signal, LRT has no advantage over LC.

**Q13. What is the "latency measurement lag" problem with LRT?**
A: LRT measures response time of completed requests and updates the EWMA. But the routing decision for the next request is made before the in-flight requests complete. If backend A suddenly becomes slow (GC pause), the requests currently in-flight to A are slow, but the EWMA hasn't been updated yet — those requests haven't completed. LRT will keep sending new requests to A during this lag window (until enough completed requests return slow measurements and pull the EWMA up). The lag is proportional to α (EWMA smoothing factor) and QPS. At high QPS, the lag is short (many samples, fast update); at low QPS, the lag can be many seconds.

**Q14. What is the "noisy measurement" problem and how does LRT handle it?**
A: Individual response times are noisy — a single GC pause or lock contention spike produces an outlier that inflates the EWMA. If α is too high (fast adaptation), this outlier disproportionately steers traffic away from the backend immediately, potentially causing thundering herd on other backends. If α is too low (slow adaptation), real slowdowns aren't detected quickly. Mitigations:
- Use a windowed percentile (p95 or p99) rather than mean for the EWMA — more robust to outliers.
- Clip measurements at a configurable maximum (e.g., cap at 2x the moving average) to prevent outliers from dominating.
- Apply minimum floor on response time (e.g., 1ms minimum) to prevent backends with zero connections from having an inflated "advantage" based on stale measurements.

**Q15. What is the "cold start" or "stale measurement" problem in LRT?**
A: When a backend first joins the pool or has been idle (no recent requests), it has no measured response time — its EWMA is either zero or stale. If zero, the score formula (`connections * response_time`) gives 0 regardless of connections, making it appear infinitely fast — causing thundering herd on the new backend. If stale (pre-set to an optimistic value), it may attract too much traffic before real measurements arrive.

Mitigations:
- Initialize new backends with a pessimistic (high) response time estimate and let it decay to reality as measurements come in.
- Use slow start (ramp up weight over time, restricting the share of traffic sent to unmeasured backends).
- Fall back to Round Robin for new backends until sufficient measurements exist (e.g., N completed requests).

**Q16. Can LRT cause "oscillation" between backends?**
A: Yes, in a specific scenario: two backends A (slightly slower, lower connections) and B (slightly faster, higher connections). LRT scores them similarly — oscillating which one is preferred as connections open and close and EWMA shifts. At high QPS, this oscillation is harmless (requests spread almost evenly). At low-to-medium QPS, the oscillation can cause bursty, uneven distribution. Mitigation: apply hysteresis — only switch preferred backend when the score difference exceeds a threshold, preventing micro-oscillations on near-tied backends.

## Section 4: LRT vs Other Algorithms

**Q17. LRT vs Least Connections — complete comparison.**
A:

| Dimension | Least Connections | Least Response Time |
|---|---|---|
| Routing signal | Active connection count | Connections × latency |
| Detects slow backends | Indirectly (more connections accumulate) | Directly (EWMA latency measured) |
| Handles GC pauses | Partially (slow backend accumulates connections) | Yes (latency spike detected quickly) |
| Idle keep-alive distortion | ⚠️ Yes — idle connections counted | Less affected (idle connections have no latency measurement) |
| Measurement overhead | Atomic counter only | Counter + EWMA per backend |
| Stale measurement problem | ❌ No (connections are live) | ⚠️ Yes (EWMA decays but lags) |
| Best for | General variable-cost APIs | Latency-SLA-critical, heterogeneous backends |

Rule: if you care about tail latency (p99), use LRT. If you just care about not overloading backends, LC is sufficient.

**Q18. LRT vs Power of Two Choices (P2C) — which is better for large systems?**
A: P2C (in Envoy's `LEAST_REQUEST` with `choice_count=2`) picks 2 backends at random and routes to the less loaded. LRT scans all backends and picks the globally optimal one. Trade-offs:

- **Accuracy**: LRT with global minimum is theoretically more optimal than P2C.
- **Scalability**: P2C is O(1) per decision with no global state — scales to large distributed LB fleets without coordination. LRT is O(N) and requires latency state per backend.
- **Noise sensitivity**: P2C's random sampling makes it less sensitive to latency measurement noise — it doesn't always route to the single globally-best backend, which actually helps avoid herding.
- **Practical outcome**: at large scale, P2C with connection count tracking approaches LRT's quality without LRT's measurement complexity. This is why Envoy, Netflix Ribbon, and Finagle all default to P2C rather than global LRT.

For pools of < 20–30 backends with a single LB instance and a tight latency SLA, LRT wins. For large distributed systems, P2C wins.

**Q19. LRT vs Weighted Round Robin — when would you choose WRR over LRT?**
A:
- **WRR** is appropriate when backend speed differences are known, stable, and attributable to hardware capacity — you manually encode this knowledge as weights. It's predictable, easy to reason about, and doesn't require measurement infrastructure.
- **LRT** is appropriate when backend speed differences are dynamic and unpredictable — transient slowdowns, GC pauses, noisy neighbours, variable request cost. LRT discovers and adapts to these differences automatically without operator intervention.

Choose WRR when the performance topology is static and known; choose LRT when it's dynamic and unknown.

**Q20. Can you combine LRT with WRR (Weighted Least Response Time)?**
A: Yes — Weighted LRT adjusts the score by the backend's configured weight:

```
score(backend) = (active_connections * mean_response_time) / weight
```

A backend with higher weight (more capacity) needs proportionally higher connections × latency before it's deprioritized. This is the most capable single-node routing algorithm — adapting to both capacity differences (weight) and dynamic performance (latency). NGINX Plus supports this when both `least_time` and `weight` are configured together. The downside is the most complex tuning surface — weights, EWMA alpha, and measurement mode all interact.

## Section 5: Production Considerations

**Q21. How do you tune the EWMA smoothing factor (α) for LRT in production?**
A: There's no universal right value — it's a trade-off:

- **High α (0.3–0.5)**: fast adaptation to latency changes. Useful when GC pauses or traffic spikes are short (< 1 second) and you want LRT to react quickly. Risk: noisy, overreacts to individual slow requests.
- **Low α (0.05–0.1)**: slow, stable adaptation. Useful when backends have gradual drift (e.g., memory leak causing progressive slowdown) and you want a smooth signal. Risk: slow to react to sudden failures or GC pauses.

Practical approach: start with α = 0.1, observe EWMA latency per backend in metrics, check if it tracks real latency trends (look at per-backend p99 alongside EWMA), and adjust. If the EWMA is too jumpy, lower α. If it lags real slowdowns by more than 10–15 seconds, raise α.

**Q22. What observability do you need to operate LRT in production?**
A: More than for LC or RR, because LRT's behavior depends on internal state that isn't visible at the request level:
- **Per-backend EWMA latency** — expose as a gauge metric so you can see what the LB "thinks" each backend's latency is.
- **Per-backend active connection/request count** — for verifying the routing signal.
- **Per-backend request rate** — to verify LRT is actually de-emphasizing slow backends.
- **Per-backend error rate** — slow backends may also be erroring; correlate with latency.
- **Score distribution** — if two backends are always nearly tied (scores within 5%), LRT is oscillating and you should check for EWMA tuning issues.
- **EWMA staleness** — how long since the EWMA was last updated (matters for low-traffic backends where measurements are rare).

**Q23. How does LRT interact with health checks?**
A: Health checks and LRT are complementary, not substitutes:
- **Health checks** handle binary failures — a backend that's down, returning 5xx, or not responding to TCP gets removed from the pool.
- **LRT** handles grey failures — a backend that's slow (300ms instead of 20ms) but still returning 200 OK. Health checks won't remove it; LRT will reduce its traffic share.

In Envoy, outlier detection (passive health checking based on error rate and latency thresholds) + `LEAST_REQUEST` is the standard production combination — outlier detection removes truly degraded backends; `LEAST_REQUEST` continuously steers traffic toward faster ones among the healthy set.

**Q24. How does LRT behave differently under low QPS vs high QPS?**
A:
- **Low QPS (< 10 req/sec per backend)**: EWMA updates are infrequent — measurements are rare and each one has outsized impact on the average. A single slow request (e.g., from a large payload) can make a backend appear slow for minutes. LRT is unreliable at low QPS; WRR or LC is more predictable.
- **Moderate QPS (10–1000 req/sec per backend)**: EWMA stabilizes — measurements arrive frequently enough to give a meaningful average. LRT's advantage over LC is clearest here — latency differences between backends manifest reliably.
- **High QPS (> 1000 req/sec per backend)**: EWMA is very stable and reacts quickly to changes. LRT works well but the benefit over LC diminishes because fast request turnaround means connection count tracks load almost as well as latency.

**Q25. How do you handle LRT in a multi-region or multi-AZ setup?**
A: Cross-region latency differences swamp intra-region backend latency differences — a backend in us-east-1 will always "win" against one in us-west-2 on response time, regardless of backend health. LRT must be applied within a locality, not across regions. The standard pattern:
- Use Geo-DNS, Anycast, or a global LB to route to the nearest region/AZ first.
- Apply LRT within the local backend pool (same AZ preferred).
- Use locality-weighted routing in Envoy (prefer same-AZ backends, only spill cross-AZ when local capacity is insufficient) — and apply LRT only within each locality tier.

**Q26. How does LRT interact with retries?**
A: LRT reduces the need for retries on slow backends by proactively steering away from them. However, when retries do occur (e.g., on 503 or timeout), the retry should go to a different backend — and LRT is a natural retry policy complement because the backend that just timed out now has an elevated EWMA, making it less likely to be selected for the retry. This is better than pure random retry selection, which has a 1/N chance of hitting the same slow backend again.

## Section 6: Failure Modes & Edge Cases

**Q27. What is the "winner takes all" failure mode in LRT?**
A: If one backend consistently responds faster than all others (e.g., it's been recently restarted with a warm JVM, empty connection pool, and empty caches — wait, that's backwards — or it has faster hardware), LRT continuously routes to it until its connection count or latency rises to match the others. During this period, the "winner" backend receives disproportionate traffic — potentially overwhelming it. This is especially pronounced when traffic is low, EWMA hasn't stabilized, or one backend is genuinely faster for structural reasons. Mitigation: use LRT within weighted routing (W-LRT) so the structurally faster backend has a higher weight ceiling it can absorb to.

**Q28. How does LRT handle backends with high throughput but high latency (batch-style)?**
A: Poorly by default. Consider a backend that processes requests in 500ms each but handles them without queuing (all in parallel, high concurrency). LRT's EWMA registers 500ms and scores it low — deprioritizing it relative to a backend doing 20ms lightweight requests. But the 500ms backend may have plenty of capacity to handle more. LRT doesn't distinguish between "latency because it's busy" and "latency because the work is inherently slow." Mitigation: separate batch-style and interactive workloads into distinct backend pools with separate routing policies, rather than mixing them under one LRT LB.

**Q29. What happens to LRT when a backend recovers from a slowdown?**
A: As the backend speeds up, completed requests start returning faster measurements, pulling the EWMA down. With a reasonable α (0.1–0.2), the EWMA recovers within 10–30 completed requests. During recovery, LRT gradually increases traffic to the backend as its score improves. This is a natural, smooth ramp-up — unlike LC, which would immediately route many connections to the backend the moment it drops to minimum connections. LRT's EWMA provides a built-in "soft slow start" on recovery without explicit configuration.

**Q30. What is measurement poisoning in LRT?**
A: If a backend receives a burst of artificially fast requests (e.g., all from cache, or all empty responses), its EWMA is pulled down — making it appear very fast — causing LRT to route more traffic to it, some of which are slower requests that inflate the EWMA back up. In the worst case, this creates an unstable cycle: fast burst → looks great → gets more traffic → slower requests arrive → looks bad → loses traffic → fewer slower requests → looks fast again. Mitigation: separate cache-hit and cache-miss path latencies if possible, or use response-type-aware LRT that buckets measurements by request category.

## Section 7: Scenario-Based Questions

**Q31. "You have 4 backend pods behind an NGINX Plus LB. One pod has a JVM GC pause every ~60 seconds causing 800ms latency spikes for ~2 seconds. With `least_conn`, users see latency spikes. Would `least_time` help, and how?"**
A: Yes, significantly. With `least_conn`, the GC-pausing pod accumulates connections during the pause — but it takes a few seconds for connections to pile up enough that LC routes away from it. Requests keep arriving at the pod during the pause, experiencing 800ms latency. With `least_time header`, NGINX Plus measures response times via EWMA. The first few requests to the pausing pod return at 800ms — immediately pulling its EWMA from ~20ms to ~100ms+ after just a handful of samples (depending on α). The score (`connections * mean_response_time`) spikes, causing LRT to route new requests to the other 3 pods within a few seconds. Tail latency during GC pauses drops materially. The trade-off: users who hit the pod in the first 1–2 seconds of the pause still see the spike — LRT has a detection lag proportional to α and QPS.

**Q32. "An interviewer asks: 'You're designing the load balancing strategy for a financial trading API where p99 latency must be under 10ms. Which algorithm would you use?'"**
A: This is a layered answer:

1. **Primary algorithm: LRT (Least Response Time)** — with `last_byte` measurement (full response time, not just header) and a moderately high α (0.2) to react quickly to any backend that starts degrading. This ensures requests are continuously steered toward the fastest available backend.

2. **Complement with P2C** — if running a large fleet (> 20 pods), switch to P2C-based LRT (Envoy's `LEAST_REQUEST` with `choice_count=2` and latency tracking) to avoid the O(N) scan overhead at every request at < 1ms routing budgets.

3. **Outlier detection** — any backend whose p99 exceeds 8ms (80% of the 10ms SLA) is ejected from the pool immediately via passive health checking.

4. **Locality-aware routing** — ensure all backends are in the same AZ; cross-AZ latency (0.5–2ms) alone would blow the budget.

5. **Connection pool pre-warming** — keep backend connection pools pre-warmed (no cold TCP handshake on first request).

The key interview point: LRT alone is not enough for a 10ms SLA — it's one layer in a stack that includes pool locality, connection warming, outlier ejection, and capacity headroom.

**Q33. "You've implemented LRT but you notice one backend consistently handles 70% of traffic even though all backends have identical hardware. What's wrong?"**
A: Several possible causes:
- **EWMA initialization**: if the preferred backend happened to serve fast requests early on, its EWMA is lower than others — and LRT keeps routing to it, which keeps it fast (cached responses, warmed JIT), reinforcing the preference. This is a self-fulfilling prophecy — the "winner" stays warm and fast because it keeps getting traffic.
- **Uneven request distribution**: requests arriving in bursts may always hit the same backend due to timing artifacts. Add jitter to routing decisions.
- **Cold EWMA on other backends**: if other backends have fewer total requests, their EWMA is based on fewer samples and may be stale or initialized high.
- **Fix**: periodically rebalance by resetting EWMA values, use slow-start probing (send occasional traffic to non-preferred backends to keep measurements current), or switch to P2C which naturally prevents "winner takes all" by randomizing which two backends are compared.

**Q34. "You're running Envoy with `LEAST_REQUEST` for a gRPC service. A backend pod starts experiencing 50% increase in CPU due to a memory leak, causing 40ms p99 instead of 10ms. How does `LEAST_REQUEST` handle this, and is it sufficient?"**
A: Envoy's `LEAST_REQUEST` tracks active request count, not latency. The leaky pod processes requests slower — so it accumulates more in-flight requests — causing `LEAST_REQUEST` to route fewer new RPCs to it. This partial mitigation works well for steady-state slowdowns: the pod reaches a lower equilibrium share of traffic. However:
- It doesn't remove the pod — users hitting it still see 40ms instead of 10ms.
- If the memory leak progresses to OOM kill or GC thrashing, the pod's active request count may appear artificially low (requests are being dropped or timed out, quickly decrementing the counter) — causing `LEAST_REQUEST` to over-route to it.

Sufficient? No — combine with: (1) Envoy outlier detection with a p99 latency threshold to eject the pod when it crosses a threshold; (2) Kubernetes liveness probe to restart the leaking pod when memory exceeds a limit; (3) HPA to bring replacement pods online. `LEAST_REQUEST` buys you time but isn't a substitute for fixing the root cause.

**Tip for interviews:** Four things separate strong candidates on LRT: (1) connecting the scoring formula to **Little's Law** (L = λW) — almost no candidate makes this connection and it shows deep systems intuition; (2) explaining the **EWMA α tuning trade-off** (fast adaptation vs noise sensitivity) with concrete numbers; (3) knowing that LRT has a **"winner takes all"** failure mode due to self-reinforcing warm cache effects on the preferred backend; and (4) explaining why **Envoy's `LEAST_REQUEST` is not true LRT** — it tracks request counts (LC at the stream level), not measured latency — and what you need to add (outlier detection) to approximate LRT behaviour. Any two of these in an answer will stand out at the 5 YOE level.
