# A Record (DNS) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an A record, specifically?**
A: An A ("Address") record is the DNS resource record type that maps a domain name directly to an IPv4 address — `example.com A 93.184.216.34`. It is the most fundamental record type in DNS: when a client asks "where do I connect to reach this name," the A record (or its IPv6 counterpart, the AAAA record) is what ultimately ends the resolution chain with a concrete, routable address rather than another name to keep chasing.

**Q2. What does the structure of an A record actually look like in a zone file?**
A: A zone file entry for an A record has four core fields: the **name** (the hostname or subdomain the record applies to, e.g., `www`), the **TTL** (in seconds, how long the record may be cached), the **class** (almost always `IN` for Internet, a historical artifact rarely touched), the **type** (`A`), and the **value/rdata** (the IPv4 address itself, e.g., `93.184.216.34`). A typical line looks like: `www.example.com.  300  IN  A  93.184.216.34`.

**Q3. Where does the A record fit into the overall DNS resolution chain?**
A: It's the terminal step. Root and TLD nameservers only ever return referrals (NS records pointing to the next server to ask); the authoritative nameserver for the domain is the one that actually holds and returns the A record. Once a resolver receives the A record, resolution is complete — there's nothing further to chase. Everything downstream of that (the TCP handshake, TLS negotiation, HTTP request) happens entirely outside DNS, using the IP the A record provided.

**Q4. Can an A record's value be a hostname instead of an IP address?**
A: No — this is a frequent point of confusion with CNAME. An A record's value field must be a literal IPv4 address; the DNS protocol does not allow it to contain another name that itself needs to be resolved. If you want a name-to-name alias (so that updating one record automatically updates what a dependent name resolves to), that's precisely what a CNAME record is for, not an A record. A records are intentionally the "no further indirection" terminal record.

**Q5. Can a single domain name have multiple A records?**
A: Yes, and this is both common and important. A name can have any number of A records, each pointing to a different IPv4 address. When queried, the authoritative server returns all of them in a single response, and the resolver (or ultimately the client) chooses which one to use — this is the basis of DNS round robin (covered in Section 3).

## Section 2: A Records vs Other Record Types

**Q6. How does an A record differ from an AAAA record?**
A: They serve the identical purpose — mapping a name to an address — but for different IP versions: A records hold IPv4 addresses (32-bit, dotted-decimal, e.g., `93.184.216.34`), AAAA records hold IPv6 addresses (128-bit, colon-hex, e.g., `2606:2800:220:1:248:1893:25c8:1946`). A domain commonly has both simultaneously for dual-stack support, with the client's OS/browser typically preferring AAAA (IPv6) when available via the Happy Eyeballs algorithm, falling back to the A record's IPv4 address otherwise.

**Q7. Can an A record coexist with a CNAME record at the same name?**
A: No — this is a hard DNS protocol-level rule, not a vendor-specific limitation. If a name has a CNAME record, it cannot have any other record type at that exact same name, including an A record. This is precisely why you cannot, for example, have `www.example.com` be a CNAME to a CDN's hostname *and* also manually attach an A record to `www.example.com` for some secondary purpose — the zone would be invalid. The two are mutually exclusive at a given name.

**Q8. Why can't you put a CNAME at the zone apex, and how does this push people back toward A records?**
A: The apex (the bare root domain, `example.com` with no subdomain) almost always requires NS and SOA records to function as a zone at all — and since a CNAME can't coexist with any other record at the same name (Q7), you can't have a CNAME at the apex. This forces apex domains to use a plain A record (pointing to a fixed IP) when possible. The friction arises when the service you want the apex to point to (a CDN, a PaaS like Heroku, an ALB) only hands out a CNAME-style hostname rather than a stable IP — which is why provider-specific workarounds like AWS Route 53 "Alias" records or Cloudflare's "CNAME flattening" exist: they behave like a CNAME for zone-management purposes but are resolved server-side into an actual A record before being returned to the client, sidestepping the protocol restriction.

**Q9. What is a wildcard A record and how does it behave?**
A: A wildcard record uses `*` as the name (e.g., `*.example.com A 93.184.216.34`) and matches any subdomain that doesn't have its own more specific record — so `foo.example.com`, `anything.example.com`, etc., would all resolve to that same IP unless a specific record for that exact subdomain exists and takes precedence. Common uses include multi-tenant SaaS platforms (`tenant1.example.com`, `tenant2.example.com` all routing to the same application tier) or catch-all staging environments. A caveat worth knowing: a wildcard does not match multiple levels of subdomain (`*.example.com` does not match `a.b.example.com`) and does not override an existing exact-match record at a more specific name.

## Section 3: Multiple A Records and DNS Round Robin

**Q10. What happens when a domain has multiple A records — how is one chosen?**
A: The authoritative nameserver typically returns all configured A records in its response. Most resolvers and operating system stub resolvers will then either pick the first one in the list or (more commonly with well-behaved resolvers) rotate/shuffle the order on each query — this rotation is the mechanism behind "DNS round robin," a crude form of load distribution where, over many independent clients and queries, traffic is roughly spread across the set of IPs.

**Q11. Is the order in which multiple A records are returned guaranteed or controllable?**
A: Not reliably. Some authoritative nameservers rotate the order of records in their response on each query (so the "first" record isn't always the same one); some resolvers respect that order, others re-shuffle it themselves, and some clients simply always pick the first record returned regardless of order. There's no protocol-level guarantee of even distribution — it's a statistical tendency across many clients/queries, not a controlled, deterministic load-balancing decision. This is the core reason DNS round robin is considered a weak, best-effort mechanism rather than a real load balancing solution.

**Q12. What are the practical limitations of using multiple A records as a load balancing mechanism?**
A: Three main ones, all stemming from DNS's lack of connection-level awareness: (1) **no health checking** — if one of the IPs in the rotation goes down, plain DNS round robin has no native way to know that and will keep handing that dead IP out to some fraction of clients until someone manually removes the record (some managed DNS providers bolt on health-check-driven failover as a separate feature, but it's not inherent to the record type itself); (2) **client/resolver stickiness** — once a client resolves and caches one of the IPs, it stays pinned to that IP for the TTL duration (and often longer, for long-lived connections), so it doesn't get the benefit of "round robin" again until it re-resolves; (3) **uneven distribution in practice** — because resolvers themselves cache and serve the same answer to many downstream clients behind them (e.g., a large ISP's resolver serving thousands of users), the actual observed distribution across the backend IPs can be lumpy rather than smooth, especially with a small number of distinct upstream resolvers.

**Q13. How does having multiple A records interact with the Happy Eyeballs algorithm when AAAA records are also present?**
A: Happy Eyeballs operates at the level of "try IPv6 first, race IPv4 as a fallback (or in parallel with a short head start)" — it doesn't care how many A or AAAA records exist, only that both record types may be present. If multiple A records exist, the client's IPv4 fallback attempt will use whichever A record address it selected (per Q10–11) as its IPv4 candidate in that race; multiple A records don't change Happy Eyeballs' core IPv4-vs-IPv6 racing logic, they just affect which specific IPv4 address ends up being raced.

## Section 4: TTL and Caching Behavior for A Records

**Q14. Does TTL behave any differently for A records compared to other record types?**
A: No — TTL is a generic mechanism that applies uniformly to any record type, A records included. What makes TTL discussions particularly practically important for A records specifically is that A records are the record type most frequently changed during real operational events (failovers, migrations, autoscaling-driven IP churn), so the TTL trade-offs (fast propagation vs. query load, covered generally in DNS fundamentals) are felt most acutely here.

**Q15. Why is the "lower TTL before a planned change" practice especially relevant to A records?**
A: Because an A record change is almost always the mechanism by which you redirect live traffic during a migration, failover, or incident — for example, cutting over from one load balancer's IP to another's. If the A record's TTL is still long (e.g., 24 hours) at the moment you change the IP, clients holding cached copies of the old IP will keep sending traffic to infrastructure you may be in the process of decommissioning, for up to the full TTL duration. The standard practice: lower the TTL well in advance, wait out the *old* TTL duration so stale long-TTL caches have a chance to expire naturally, then perform the actual IP change against the now-short TTL, and raise the TTL back up once the change has stabilized.

**Q16. What happens with negative caching if a hostname is queried before its A record exists?**
A: If a resolver queries for an A record on a name that doesn't exist yet (or exists but has no A record), it receives an NXDOMAIN or NODATA response and caches that *negative* result for a duration governed by the zone's SOA minimum-TTL field, not by any TTL on the (nonexistent) A record itself. Practically: if you create a brand-new subdomain's A record, but that subdomain was queried (and got a negative response) before you published it, some resolvers may continue returning "doesn't exist" for a while even after the record is correctly live — a common source of "I just added the record but it's not resolving yet" confusion.

## Section 5: A Records in Cloud Infrastructure and Operations

**Q17. Why do many managed load balancers (e.g., AWS ALB/ELB, Heroku, many PaaS platforms) not give you a fixed IP for a plain A record?**
A: These services are typically backed by a fleet of machines whose underlying IPs can change at any time (scaling events, AZ failover, infrastructure upgrades on the provider's side) — so instead of exposing a single static IP suitable for a hardcoded A record, they expose a stable *hostname* (e.g., `my-app-1234567890.us-east-1.elb.amazonaws.com`) that the provider's own DNS resolves to whichever current IP(s) are correct at query time. You're expected to CNAME to that hostname rather than hardcode an A record to one of its current IPs, precisely because hardcoding would silently break the moment the provider rotates the underlying IP.

**Q18. Given Q17, how do you point an apex/root domain (which can't use a CNAME, per Q8) at such a service?**
A: This is exactly the use case for ALIAS/ANAME-style records: AWS Route 53's "Alias" record type, when used at the zone apex pointing at an ALB or CloudFront distribution, is resolved server-side by Route 53 itself — it looks up the target's current IP(s) on the fly and returns them to the client as if they were ordinary A records, all while letting you manage it like a name-based alias rather than a hardcoded IP. Functionally, the client still receives a normal-looking A record in the DNS response; the "alias" behavior is purely a zone-management convenience on the provider's side that avoids the CNAME-at-apex restriction and avoids the staleness risk of a manually hardcoded IP.

**Q19. What's the operational risk of manually hardcoding a static A record to "whatever IP the load balancer currently has"?**
A: It silently breaks the moment that underlying infrastructure's IP changes for any reason outside your control — a provider-side maintenance event, an autoscaling/failover event, or a regional incident causing the provider to shift traffic to different infrastructure. Unlike a CNAME or ALIAS pointing at the provider's stable hostname (which the provider keeps correctly updated on their end), a hardcoded A record requires *you* to notice the IP changed and update DNS yourself — often after an outage has already started, since there's typically no automated trigger telling you the IP underneath has moved. This is why, outside of genuinely static, self-managed infrastructure (e.g., a single fixed-IP VM or an Anycast IP that's intentionally permanent), pointing A records at someone else's dynamic infrastructure by IP is generally an anti-pattern.

**Q20. How do CDNs and Anycast-based services typically use A records, given they're globally distributed across many physical edge locations?**
A: Many large-scale CDNs and Anycast-based services advertise the *same* IP address (or small set of IPs) from many physically distributed points of presence simultaneously, using BGP-level Anycast routing rather than DNS-level geo-logic to get a given client's traffic to the nearest edge — so the A record itself can be a single, simple, unchanging entry, while the actual "which physical server answers" decision happens at the network layer, invisibly to DNS. This is distinct from GeoDNS, where the *DNS layer itself* would return different A record values depending on the querying resolver's apparent location — Anycast keeps the DNS answer constant and pushes the routing decision down a layer.

## Section 6: Security Considerations Specific to A Records

**Q21. How does A record manipulation factor into DNS cache poisoning attacks?**
A: Cache poisoning's entire goal is typically to inject a forged A (or AAAA) record into a resolver's cache — since the A record is what ultimately tells a client which IP to connect to, controlling it is functionally equivalent to controlling where the victim's traffic actually goes. An attacker who successfully forges a response (exploiting weak transaction ID/source port entropy, per the Kaminsky-class attacks) for, say, a bank's domain, causes every client relying on that poisoned resolver to receive the attacker's IP instead of the legitimate one — the A record is the payload of the attack, even though the vulnerability being exploited is in the resolver's response-matching logic, not the A record format itself.

**Q22. Why does validating a user-supplied hostname's resolved A record matter for SSRF prevention, and what's the common mistake?**
A: When an application accepts a user-supplied URL/hostname and needs to ensure it doesn't point at internal infrastructure (cloud metadata endpoints, internal services, `localhost`), it typically resolves the hostname to an A record and checks whether that IP falls in a private/reserved range before proceeding. The common mistake is validating the A record once, then making the actual outbound request via a *separate* DNS resolution later — if an attacker controls the domain's DNS and changes the A record between those two steps (DNS rebinding, Q23), the validated check and the actual request can resolve to two different IPs, defeating the check entirely. The fix is to resolve once, validate that result, and pin/reuse that exact IP for the actual connection rather than re-resolving.

**Q23. How does DNS rebinding specifically abuse the mutability of A records?**
A: An attacker who controls a domain's authoritative DNS can configure a very short TTL and then change the A record's value between two points in time — for example, first returning a legitimate public IP (so an initial validation check passes), then, shortly after, switching the A record to an internal/private IP (`127.0.0.1`, `169.254.169.254`, or an internal service address) before the application's actual request executes. Because the domain name itself never changes, only the A record's value, naive validation logic that trusts "the hostname looked fine when I checked" rather than re-validating or pinning the IP at request time is vulnerable.

## Section 7: Performance and Operational Considerations

**Q24. What should you actively monitor with respect to A records you manage?**
A: Query volume and latency at the authoritative level for the records (spikes can indicate legitimate growth, a TTL set too low causing excessive re-querying, or abuse); the actual *value* of critical A records over time via independent verification (periodically querying authoritative servers directly to confirm the record matches what you believe is configured — catching drift from manual changes, automation bugs, or unauthorized modification); and propagation status after any change (querying from multiple geographically distributed resolvers/vantage points to confirm the new value has actually rolled out, rather than assuming TTL math alone guarantees it everywhere).

**Q25. What's a practical way to verify an A record's current value and TTL from the command line?**
A: `dig example.com A` (or `dig example.com A +short` for just the IP) queries against your configured resolver; adding `@8.8.8.8` or `@1.1.1.1` lets you check what a specific public resolver currently has cached or returns. To bypass caching entirely and see the live authoritative answer, query the authoritative nameserver directly: `dig example.com A @ns1.example-dns-provider.com`. The TTL value shown in the response indicates how long that particular answer may still be cached from that point forward — useful for confirming both the current value and the freshness of what you're seeing.

**Q26. What's the trade-off in TTL specifically for A records that see frequent legitimate IP churn (e.g., behind autoscaling)?**
A: A short TTL minimizes the window during which clients hold a stale IP after a legitimate scaling/failover event, but increases query volume against the authoritative nameservers proportionally — and if the churn is frequent enough, this can become a meaningful, sustained load rather than an occasional cost. In practice, most such architectures avoid exposing raw, frequently-changing instance IPs as a manually managed A record at all — instead fronting them with a load balancer (whose own DNS name is comparatively far more stable) and letting the load balancer absorb the actual backend IP churn, keeping the user-facing A/CNAME record itself relatively static.

## Section 8: Scenario-Based Questions

**Q27. "A domain returns three A records, but your monitoring shows almost all traffic landing on just one of the three IPs. What would you investigate?"**
A: First check whether the imbalance is a measurement artifact of resolver-level aggregation — a small number of large upstream resolvers (e.g., a major ISP's resolver) can dominate the traffic mix and, depending on how that resolver orders/caches the response, can disproportionately steer many downstream clients toward whichever record it happened to return or cache first, especially if its own TTL handling doesn't perfectly reshuffle on each client query. Next, verify the authoritative nameserver is actually rotating the order of the three records on each query (some DNS providers don't rotate by default, which would mean the "first" record is consistently favored by resolvers/clients that simply pick the first entry). Also rule out an application-level cause entirely unrelated to DNS — e.g., connection pooling or keep-alive behavior in the client/load testing tool that's pinning to one resolved IP for the duration of a test, rather than re-resolving per request.

**Q28. "Your team is migrating a service from a single static-IP VM to an autoscaling group behind a load balancer. What changes about how you manage the A record?"**
A: You stop pointing the public-facing DNS name at the workload's IP directly (which was viable when it was a single, genuinely static VM) and instead point it at the load balancer's stable endpoint — for a non-apex name, this typically becomes a CNAME to the LB's provided hostname; for the apex, an ALIAS/ANAME-style record resolving to the LB (Q18). The underlying autoscaling group's individual instance IPs become entirely internal implementation detail that DNS users never see or need to track — the load balancer absorbs that churn, and your "A record" management responsibility shifts from "keep this IP current" to "ensure this points at the right load balancer," which is a much lower-maintenance, less error-prone steady state.

**Q29. "Your application opens long-lived TCP/gRPC connections to a downstream host identified by an A record, and that downstream host's IP changes periodically (e.g., due to failover). What problem will you hit, and how do you mitigate it?"**
A: Once your client resolves the A record and opens a long-lived connection, it has implicitly pinned to that specific IP for the connection's lifetime — a subsequent A record change on the DNS side won't affect an already-open connection, regardless of TTL, because the client isn't re-resolving mid-connection. If the original IP becomes invalid (old instance terminated post-failover), the connection eventually breaks, and the application only gets a fresh, correct IP on its *next* DNS resolution (e.g., on reconnect). Mitigations: use a client library that supports periodic re-resolution and connection rebalancing even for currently-healthy long-lived connections (common in gRPC client implementations); keep TTLs reasonably short on records expected to change due to failover; and where uptime is critical, prefer routing through a load balancer (whose own address is comparatively stable) rather than connecting directly to an A record that's expected to change underneath a long-lived connection.

**Q30. "Should the root domain of a CDN-backed marketing site use a static A record pointing at a fixed IP, or an ALIAS/CNAME-flattening record pointing at the CDN's hostname? Justify the choice."**
A: ALIAS/CNAME-flattening is almost always the better choice here, because the CDN's actual edge IPs are not something you control and are not guaranteed to stay fixed — they may rotate for the CDN's own operational reasons (capacity changes, infrastructure migrations, Anycast announcement changes) entirely outside your visibility. A static A record pointing at "whatever IP the CDN currently shows" risks silently breaking the moment the CDN changes that IP on their end, since nothing on your side would automatically detect or correct it (Q19). An ALIAS/flattened record instead continuously re-resolves the CDN's stable hostname server-side, so it always reflects the CDN's current, correct IP(s) without requiring any manual intervention from you — the only reason to actually go with a hardcoded static A record at the apex is the rare case where the upstream service genuinely guarantees a fixed, permanent IP (e.g., your own self-managed, single fixed-IP server, or a deliberately permanent Anycast IP).

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| A record | Maps a name directly to an IPv4 address; terminal record in resolution |
| AAAA | IPv6 counterpart of A; both can coexist for dual-stack |
| CNAME restriction | A record cannot coexist with a CNAME at the same exact name |
| Apex restriction | No CNAME at zone apex → static A or ALIAS/ANAME used instead |
| Multiple A records | Enables DNS round robin; no health checking, weak distribution guarantee |
| Negative caching | NXDOMAIN/NODATA for a missing A record cached per SOA minimum TTL |
| ALIAS/ANAME | Provider-side resolution of a CNAME-like target into A records at the apex |
| Hardcoded static A | Risky against dynamic/managed infra whose IP can change without notice |
| Anycast | Same A record value announced from many locations; routing handled at network layer |
| DNS rebinding | Attacker changes A record value between validation and use (TOCTOU) |
| Connection pinning | Long-lived connections don't re-resolve A records mid-connection |

---

**Tip for interviews:** What separates strong candidates on A records specifically: (1) knowing **why an A record's value must be a literal IP**, not a name, and how that cleanly explains the CNAME-coexistence rule (Q4, Q7); (2) understanding that **multiple A records are a weak, best-effort load-balancing mechanism** — no health awareness, no even-distribution guarantee, client/resolver stickiness — rather than a real substitute for a load balancer (Q10–12); (3) recognizing **why dynamic cloud infrastructure pushes you toward CNAME/ALIAS over hardcoded A records**, and why that becomes a real problem specifically at the zone apex (Q17–19); (4) connecting **A record mutability to real security issues** like DNS rebinding and SSRF validation gaps, not just treating it as a benign data field (Q22–23); and (5) being able to reason clearly about **connection pinning** — why a long-lived connection doesn't "follow" an A record change — since this is one of the most common production incidents tied to A records in practice (Q29).
