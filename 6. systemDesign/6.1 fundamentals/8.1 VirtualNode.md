# Consistent Hashing: Virtual Nodes — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem Virtual Nodes Solve

**Q1. What specifically goes wrong with consistent hashing when each physical node occupies only one position on the ring?**
A: With N physical nodes each placed at one randomly-determined ring position, the arc lengths between consecutive positions are highly unequal by chance — especially at small N. This is a consequence of the coupon collector problem and the statistics of uniform random placement: the expected maximum arc length is `O(log N / N)` of the ring, but individual arcs vary wildly around that mean. A concrete example with 3 nodes:

```
Ring (0 to 1.0):
Node A at position 0.05
Node B at position 0.10
Node C at position 0.60

Arc A→B: 0.05  (5% of ring  → 5% of keys)
Arc B→C: 0.50  (50% of ring → 50% of keys)
Arc C→A: 0.45  (45% of ring → 45% of keys)
```

Node C handles 50% of all requests, Node A handles 5%. With just one ring position each, N=3 nodes have a 10:1 traffic imbalance purely by chance — not because of anything wrong with the nodes themselves. This imbalance compounds: the overloaded node becomes a bottleneck, while underloaded nodes sit largely idle.

**Q2. Why doesn't this problem go away with more nodes?**
A: The variance in arc length scales with `1/N` in expectation, but the *maximum* arc (and therefore the worst-case imbalance) scales as `O(log N / N)` — it shrinks as N grows, but never disappears. With 10 nodes you might see a 3:1 imbalance; with 100 nodes it's more like 1.5:1; with 1000 it approaches 1.15:1. At small N (typical for most real-world distributed caches — 3 to 20 nodes), the imbalance is severe and practically significant. At large N it's smaller but still nonzero. Virtual nodes are the solution that works regardless of N, by adding statistical regularity through repetition rather than relying on increasing N to eventually even things out.

**Q3. What is the second distinct problem that single-position consistent hashing has, beyond uneven distribution?**
A: Uneven load redistribution on failure. When a node with a single ring position fails, its one arc — which by chance might be very large (owning a disproportionate share of keys) — is entirely absorbed by its single clockwise successor. That successor suddenly receives the failed node's full share of traffic on top of its own — potentially 2-10x its normal load if the failed node was unlucky enough to own a large arc. With virtual nodes (K positions per physical node), the failed node's K arcs are each individually small and each absorbed by K different successor nodes — spreading the recovery load across (ideally) all N-1 remaining nodes rather than concentrating it on one unlucky neighbor.

**Q4. How do virtual nodes directly fix both problems?**
A: By placing each physical node at K positions on the ring instead of one, each chosen independently at random:

- **Uneven distribution fix**: each node's K arcs are independently distributed around the ring. Their combined length averages to exactly `K / (N×K) = 1/N` of the ring — the law of large numbers brings the average into line. Variance around that average decreases as K increases (with K=150, each node's actual share of the ring is within ~2-5% of the target `1/N`).
- **Failure recovery fix**: when a node fails, its K arcs each go to K different successors (one per arc, each arc's successor being the next clockwise position from that arc). With K=150 virtual nodes and N=10 physical nodes, the expected number of distinct physical nodes absorbing the failed node's load is `min(N-1, K) = 9` — all remaining nodes share the recovery load equally. No single node doubles its traffic.

## Section 2: Mechanics and Implementation

**Q5. How are virtual node positions on the ring generated?**
A: Each physical node generates K distinct hash inputs and hashes them to produce K ring positions. The standard approach is to derive a unique string per virtual node by combining the node identifier with an ordinal:

```python
positions = []
for i in range(K):
    key = f"{node_id}#{i}"          # e.g., "node-A#0", "node-A#1", ...
    position = hash(key) % RING_SIZE
    positions.append(position)
```

Alternatively, some implementations use a seeded PRNG initialized with `hash(node_id)` to generate K positions deterministically without explicitly constructing K strings. Either way: positions are deterministic given the node ID and K — any node in the cluster can independently reconstruct the full ring without coordination, which is essential for the "stateless routing decision" property of consistent hashing.

**Q6. How is the ring data structure maintained in memory, and what are the lookup operations?**
A: The ring is typically stored as a sorted list of `(position, node_id)` tuples — all K×N virtual node entries from all physical nodes, sorted by position:

```python
ring = sorted(
    [(pos, node_id)
     for node_id in nodes
     for pos in virtual_positions(node_id, K)],
    key=lambda x: x[0]
)
```

Key operations:
- **Route a key**: compute `hash(key)`, binary-search the sorted ring for the first position ≥ that hash (the clockwise successor), return the corresponding `node_id`. O(log(N×K)) per lookup.
- **Add a node**: generate K new positions for the new node, insert them into the sorted structure (maintaining sort order), update the arc-ownership bookkeeping. O(K log(N×K)).
- **Remove a node**: delete the K positions for the departing node. O(K log(N×K)).

In practice the sorted structure is implemented as a sorted array (for cache-friendliness) or a sorted set (e.g., Python's `sortedcontainers.SortedList`, Java's `TreeMap`), since the binary search for routing is on the hot path.

**Q7. Walk through a concrete routing example with virtual nodes.**
A:

```
Physical nodes: A, B, C  (K=3 for illustration; production uses K=100-200)

Virtual positions (hash results, ring size = 100):
A#0 → 5     A#1 → 45    A#2 → 78
B#0 → 20    B#1 → 60    B#2 → 90
C#0 → 35    C#1 → 70    C#2 → 10

Sorted ring:
[5→A, 10→C, 20→B, 35→C, 45→A, 60→B, 70→C, 78→A, 90→B]

Route key "user:42":
  hash("user:42") = 37
  First position ≥ 37: position 45 → Node A
  Result: "user:42" is served by Node A

Route key "session:99":
  hash("session:99") = 75
  First position ≥ 75: position 78 → Node A
  Result: "session:99" is served by Node A

Route key "order:17":
  hash("order:17") = 95
  No position ≥ 95 exists → wrap around to position 5 → Node A
  Result: "order:17" is served by Node A (wrap-around)
```

**Q8. How does adding a new node with virtual nodes affect key ownership?**
A: When node D is added with K virtual positions, each of D's K positions lands somewhere on the ring and "claims" keys from the arc between it and its clockwise predecessor. Only keys in that arc move — to D — while all other keys remain where they are. The total fraction of keys that move is approximately `K / (N×K) × N_new = 1/(N+1)` where N is the current count — approximately 1/(N+1) of all keys remapped, distributed from K different existing nodes (one per new virtual position's arc, each giving up a small slice).

Concretely with 3 nodes and K=3 from Q7, adding node D with positions [15, 50, 85]:

```
New sorted ring:
[5→A, 10→C, 15→D, 20→B, 35→C, 45→A, 50→D, 60→B, 70→C, 78→A, 85→D, 90→B]

Moved keys:
  Arc 10→15: previously owned by B (first B position clockwise from 10 was 20)
              now owned by D (position 15 is before B's 20)
  Arc 45→50: previously owned by B (position 60), now owned by D (position 50)
  Arc 78→85: previously owned by B (position 90), now owned by D (position 85)
```

D takes small slices from three different nodes (all from B in this example — coincidence of the toy example) rather than one big slice from one node. In production with large K, D's incoming slices come from many different existing nodes.

**Q9. Why must all nodes in a distributed system agree on the same K value and the same virtual node generation function?**
A: Consistent hashing's correctness depends on every client/node being able to independently compute the same ring and arrive at the same routing decision for the same key — with no coordination required at request time. If different nodes used different K values or different virtual node generation functions, they would produce different rings and route the same key to different destinations — breaking the consistency property entirely. K and the hash function are therefore cluster-wide configuration constants, typically fixed at cluster initialization and not changed without a full re-partitioning operation (which requires migrating data to the new distribution).

**Q10. What is the memory footprint of the virtual node ring in practice?**
A: Each ring entry is a `(position, node_id)` pair. For a 32-bit ring (2^32 positions, standard for many implementations), the position is a 4-byte integer; node_id is typically a string like `"node-03"` (a few bytes, or an index into a node table). For N=10 nodes and K=150 virtual nodes:
- Ring entries: 10 × 150 = 1,500 entries
- Memory per entry: ~16-32 bytes (position + node reference + pointer overhead in sorted structure)
- Total: ~25-50 KB — trivially small, fits entirely in L2 cache of any modern CPU

For N=1,000 nodes and K=150:
- Ring entries: 150,000
- Memory: ~2.5-5 MB — still trivially manageable

This is why Maglev's fixed-size lookup table (from the consistent hashing guide) is the only scheme that has meaningfully different memory characteristics, not virtual node ring size itself.

## Section 3: Choosing K — The Right Number of Virtual Nodes

**Q11. What is the mathematical relationship between K, N, and load distribution variance?**
A: For N nodes each with K virtual nodes on a ring of size R, each physical node's expected share of the ring is exactly `1/N` (by symmetry), but the actual share varies. The variance of each node's fraction of the ring is approximately:

```
Var(fraction) ≈ 1 / (N × K)
```

So the standard deviation of any node's actual load fraction is approximately:

```
σ ≈ 1 / sqrt(N × K)
```

With N=10, K=150: σ ≈ 1/√1500 ≈ 2.6%. So any given node's actual share of keys is within roughly ±5% (2σ) of the target 10% with high probability — acceptable for almost all production use cases. With N=10, K=10: σ ≈ 1/√100 = 10% — meaning a node could be handling 20% or 0% of traffic, which is too variable for most real systems.

**Q12. How do common production systems choose K, and why do their choices differ?**
A:
- **Ketama (Memcached clients)**: K=160 (40 hash points × 4 derivations from each MD5 output, using different byte offsets). Chosen empirically as giving good distribution with the MD5 hash function for typical Memcached cluster sizes (3-20 nodes).
- **Cassandra (original)**: K=256 per node (the `num_tokens` setting). Modern Cassandra (4.0+) defaults to K=16 with smarter token placement algorithms that achieve better distribution with fewer tokens than pure random placement (discussed in Q18).
- **Redis Cluster**: doesn't use virtual nodes at all (uses fixed 16,384 slots — a different partitioning approach, as noted in the consistent hashing guide).
- **Envoy RING_HASH**: configurable `minimum_ring_size` and `maximum_ring_size`, defaulting to a ring with 1024 minimum entries. Envoy's implementation effectively auto-tunes K to hit the minimum ring size given the actual number of backends — with 10 backends and minimum_ring_size=1024, K≈102 per backend.

The choices differ because K is a trade-off: higher K = better distribution + smaller arcs (less disruption per event) but more memory (negligible at typical scales) and more computation during ring construction (usually a one-time or rare operation). There's no universally "right" K — it's calibrated to the cluster size (N), acceptable variance, and the hash function's distribution quality.

**Q13. At what value of K does adding more virtual nodes yield diminishing returns, and why?**
A: The marginal improvement in variance from increasing K follows the `1/sqrt(N×K)` relationship — improving proportionally to `1/sqrt(K)`, which means the benefit of doubling K is only a `1/sqrt(2) ≈ 29%` reduction in standard deviation. From K=50 to K=150: σ drops from ~4.5% to ~2.6% (meaningful). From K=150 to K=1500: σ drops from ~2.6% to ~0.8% (less meaningful, and K=1500 is 10× the memory/construction cost). The practical inflection point for most systems is around K=100-200: beyond that, the improvement in distribution is often smaller than the natural variance in request rates across keys, making further investment in vnode count statistically unhelpful. This is why Ketama's K=160 and Cassandra's K=256 have stood the test of time — they're in the range where returns are good but not yet diminishing.

## Section 4: Non-Uniform and Weighted Virtual Nodes

**Q14. How do you handle heterogeneous nodes (different capacities) with virtual nodes?**
A: Assign K proportional to each node's relative capacity. If node A has twice the capacity of node B, assign A twice as many virtual nodes — it will own approximately twice the ring arc and receive twice the traffic:

```
Total capacity = 24 units
Node A: 16 units capacity → K_A = 150 × (16/24) = 100 vnodes
Node B: 8 units capacity  → K_B = 150 × (8/24) = 50 vnodes

Expected traffic shares:
Node A: 100/(100+50) = 66.7% ✓ (proportional to 16/24)
Node B: 50/(100+50) = 33.3% ✓ (proportional to 8/24)
```

This is the virtual-node equivalent of Weighted Consistent Hashing — capacity differences are expressed as vnode count differences, and the ring's statistical properties handle the rest without requiring any special-case routing logic. This was described in the consistent hashing guide as "Weighted backends via vnode count."

**Q15. What happens when a node's capacity changes mid-operation (e.g., a node is given more memory or CPU), and how do you adjust vnode count?**
A: Increasing a node's capacity requires adding more virtual nodes to reflect its new share. Adding vnodes is disruptive (some keys move to the newly-expanded node from other nodes, same as adding a new node would be) but localized — only keys in the arcs claimed by the new positions move. Decreasing capacity (fewer vnodes) means some of that node's arcs are now claimed by other nodes — equivalent to partially removing a node. In systems like Cassandra, this is called "rebalancing token ownership" and is an administrative operation. The key engineering consideration: changing a node's vnode count isn't instantaneous and requires data migration (for stateful caches/databases). Most systems therefore treat the vnode count as stable configuration rather than dynamically adjusting it — capacity scaling is typically done by adding or removing physical nodes entirely, rather than re-weighting existing ones.

**Q16. Can virtual nodes be used to implement "zone-aware" placement — ensuring replicas land in different availability zones?**
A: Yes, and this is an important production pattern in cloud deployments. The constraint "no two replicas of the same key may land on nodes in the same AZ" can be enforced by modifying the replica selection algorithm: when walking the ring clockwise to find the RF replicas, skip any candidate node that's in the same AZ as an already-selected replica. This "zone-aware ring walk" guarantees AZ diversity for every key's replica set, without changing the fundamental consistent hashing or virtual node mechanics. Cassandra's `NetworkTopologyStrategy` implements this (specifying how many replicas go to each datacenter/rack), and some Dynamo-style systems implement similar "rack-aware" placement via modified successor selection on the ring.

## Section 5: Consistent Hashing Algorithms Compared Through the Virtual Node Lens

**Q17. How does Ketama's virtual node implementation work in detail?**
A: Ketama (the Memcached-standard consistent hash) generates virtual node positions using MD5:

```python
def ketama_positions(node, K=40):
    positions = []
    for i in range(K):
        digest = md5(f"{node}-{i}".encode()).digest()
        # Each MD5 produces 16 bytes = 4 × 4-byte integers
        # Use all 4 to get 4 positions per hash computation
        for j in range(4):
            pos = (digest[3+j*4] << 24 |
                   digest[2+j*4] << 16 |
                   digest[1+j*4] << 8  |
                   digest[0+j*4])
            positions.append(pos)
    return positions  # 40 × 4 = 160 positions total
```

By extracting 4 positions from each MD5 (using different byte offsets), Ketama amortizes the MD5 computation cost across 4 virtual nodes — more efficient than computing a separate hash per virtual node, at no distribution quality cost (different byte slices of the same MD5 output are approximately independent, given MD5's avalanche property). This yields K_effective=160 at the cost of only 40 MD5 computations per node — a practical optimization that's baked into every Ketama-compatible client library.

**Q18. What is Cassandra's "token allocation" strategy for virtual nodes and how does it improve on pure random placement?**
A: Pure random placement of K virtual node positions per physical node produces good-but-not-perfect distribution (the `1/sqrt(N×K)` variance from Q11). Cassandra 4.0+ introduced a smarter token allocation strategy that places virtual nodes *deterministically* rather than randomly, to achieve near-perfect distribution with fewer tokens. The algorithm: given N existing nodes and their current token positions, compute where a new node's tokens should go to minimize the maximum deviation from the ideal `1/N` load share — essentially solving a placement optimization problem rather than accepting random placement. This allows Cassandra 4.0 to achieve Cassandra 3.x's distribution quality with K=16 instead of K=256 — a 16× reduction in ring metadata, cluster gossip overhead, and data migration complexity when adding nodes, at the cost of more complex initial token calculation logic.

**Q19. How does Rendezvous hashing (HRW) relate to virtual nodes — is it equivalent?**
A: Rendezvous hashing achieves the same `1/N` distribution and `1/N` remapping properties as consistent hashing with virtual nodes, but without a ring data structure at all — and without needing virtual nodes specifically. For each key, every candidate node computes a score (`hash(node_id + key)`), and the node with the highest score "wins." The scores are random and uniform, so on average each node wins for `1/N` of keys, and removing a node only affects the keys where that node had the highest score (approximately `1/N` of keys). From the virtual node perspective: Rendezvous hashing achieves perfectly uniform distribution (zero variance in expectation, bounded variance in practice) without any K parameter to tune, at the cost of O(N) per routing decision (must evaluate all N nodes). It's as if virtual nodes with K=∞ are implicit in the algorithm's per-key randomness, though that framing breaks down if you push it too far — the mechanisms are fundamentally different.

## Section 6: Data Migration and Rebalancing

**Q20. When a new node joins and claims K arc slices, what exactly must be migrated and from where?**
A: For each of the K new virtual positions the new node inserts into the ring, the new node's arc extends from its position back to the previous position on the ring (i.e., its clockwise predecessor). All keys whose hash falls within that arc were previously owned by the node that used to be the first clockwise node from those positions — that predecessor node must transfer those keys to the new node. The migration is per-arc: K separate small migrations, each from a (potentially different) predecessor node. In total, approximately `1/(N+1)` of all keys migrate, sourced from up to K different nodes (one source per arc). The fact that the source is distributed (many small transfers from many nodes, rather than one massive transfer from one node) is a significant operational advantage: network bandwidth for migration is distributed across the cluster, not concentrated on one node.

**Q21. What is the "stream" operation in Cassandra, and how does it implement the virtual node data migration described in Q20?**
A: In Cassandra, when a new node joins and its token ranges are determined, existing nodes that own data in those ranges initiate "streaming" sessions to transfer the relevant SSTables (data files) to the new node. With virtual nodes, many small streaming sessions run concurrently — each existing node streams a small subset of its data proportional to how many of its token ranges it's ceding to the new node. This concurrent, distributed streaming is one of the key operational benefits of virtual nodes vs. single-token assignment: with single tokens, one node must stream the entire new node's dataset (a massive sequential transfer); with virtual nodes, that dataset is streamed from many nodes in parallel, potentially saturating the new node's incoming bandwidth more efficiently and completing migration faster overall.

**Q22. How do virtual nodes affect "gossip" overhead in a peer-to-peer distributed system like Cassandra?**
A: In Cassandra's gossip protocol, each node periodically exchanges state information about all nodes' token positions with a random subset of peers. Token position information is O(K) per node — with K=256, every gossip exchange includes significantly more ring-position data per node than if K=1. With N nodes, the total gossip state for ring positions is O(N×K). Cassandra 4.0's move to K=16 (per Q18's smarter placement) was motivated partly by reducing this gossip overhead: at K=256 with large clusters (N=100+), gossip messages carry 25,600 token entries, creating non-trivial serialization and network overhead per gossip round. K=16 reduces that to 1,600 entries — a 16× reduction with equivalent distribution quality, making gossip overhead negligible again even at large cluster sizes.

**Q23. What is "virtual node rebalancing" when the cluster grows by many nodes simultaneously, and how does it differ from adding one node at a time?**
A: Adding nodes one at a time is operationally simpler: each addition triggers a small, bounded data migration (1/(N+1) of keys from up to K sources) and the ring is re-sorted after each addition. Adding many nodes simultaneously is more disruptive: if N_new nodes join at once, each with K virtual positions, they collectively claim approximately `N_new / (N + N_new)` of all keys — potentially a large fraction if expanding the cluster significantly. The migration is still distributed (many nodes are sources, many nodes are destinations), but the concurrent streaming load across the cluster is proportionally higher. Best practice for large expansions: add nodes in batches, waiting for each batch's migration to complete before adding the next — trading a longer total expansion timeline for more controlled resource usage during migration.

## Section 7: Failure Modes Specific to Virtual Nodes

**Q24. What is "vnode collision" and how is it handled?**
A: A collision occurs when two different virtual nodes (from different physical nodes, or even from the same physical node) hash to the same ring position. With a 32-bit ring (4 billion positions) and typical cluster sizes (N=10, K=150 → 1,500 total positions), the probability of any collision is extremely low (birthday problem: `~1500² / (2 × 4×10⁹) ≈ 0.03%`). With a 64-bit ring, collisions are astronomically unlikely. Most implementations handle collisions by either: skipping to the next position on a collision (adding 1 or re-hashing with a different seed), inserting both entries but using a deterministic tie-break (e.g., lexicographic ordering of node IDs) to assign the key to exactly one of them consistently, or simply accepting the infinitesimally-small probability with a 64-bit ring and not special-casing it at all. The collision handling strategy must be identical across all nodes to maintain consistency.

**Q25. What happens to virtual node ring consistency when a node fails transiently (network partition vs actual crash) and then returns?**
A: This is a nuanced issue. If a node is merely temporarily unreachable (transient partition) and other nodes reroute its keys to successor nodes, then the transiently-partitioned node may have accepted local writes (if it's still processing requests on its side of the partition) that the rest of the cluster doesn't know about — creating divergent copies of data. When the partition heals, those copies must be reconciled. Virtual nodes don't add complexity here specifically — this is a general distributed systems consistency problem handled by the system's conflict resolution policy (vector clocks, last-write-wins, CRDTs, etc.). However, because virtual nodes spread each node's key responsibility across many arcs, the set of nodes that "notice" a failure (the successors for each of K arcs) is larger than with single-token placement, meaning failure detection and rerouting involves more nodes — slightly more gossip communication, but also faster aggregate detection since more nodes are monitoring different subsets of keys.

**Q26. Can a misconfigured K value cause correctness issues, or only performance/distribution issues?**
A: Only performance/distribution issues — never correctness issues. The fundamental correctness guarantees of consistent hashing (same key always routes to the same node, given the same ring) hold regardless of K, even K=1. A misconfigured K (too low) produces poor distribution (some nodes handle far more than their fair share) and poor failure recovery load spreading, but doesn't cause routing disagreements or data loss in a correctly-implemented system. The exception: if different nodes in the cluster use *different* K values for the same physical node (a misconfiguration, not a valid "wrong K" scenario), they would produce different ring states and route the same key to different destinations — a genuine correctness failure. This is why K must be cluster-wide configuration (Q9) — not a per-node tunable, but a system constant.

## Section 8: Virtual Nodes in Different Systems

**Q27. How does Riak's approach to virtual nodes differ from Cassandra's, and what concept did Riak introduce?**
A: Riak (a Dynamo-inspired key-value store from Basho) introduced the term "virtual node" and pioneered many of the concepts covered here. Its key innovation beyond basic ring placement: in Riak, the ring is pre-divided into a fixed number of partitions (`ring_size`, always a power of 2, typically 64-512), and each partition is a "vnode" — a unit of data responsibility. Physical nodes are assigned partitions (vnodes) from this fixed partition set rather than generating random ring positions. This is important: Riak's vnodes are fixed-slot, not random-position. The ring never changes structurally; only the assignment of vnodes to physical nodes changes. This makes data migration more predictable (move whole partitions, not arbitrary key ranges) at the cost of less flexibility in tuning distribution granularity — the partition count is fixed at cluster creation and can't be changed later without a full rebuild.

**Q28. How does DynamoDB (Amazon's internal and external) handle virtual nodes in its architecture?**
A: The original Dynamo paper (2007) described consistent hashing with virtual nodes where each node is assigned multiple (non-contiguous) token ranges from a ring. Amazon's internal Dynamo implementation used this to ensure load balancing and minimize disruption during membership changes. Amazon DynamoDB (the public service) doesn't expose its internal partitioning to customers, but it internally uses a similar approach to distribute partition responsibility across its internal storage nodes. What customers interact with: a partition key determines which logical partition handles their data, and DynamoDB's internal partitioning layer (consistent hashing with vnodes) maps logical partitions to physical storage nodes transparently. The key customer-visible implication: designing partition keys with high cardinality (many distinct values) is critical precisely because consistent hashing distributes distinct partition key hashes across nodes — a low-cardinality partition key means few distinct ring positions regardless of virtual node count, creating hot partitions.

**Q29. How does Envoy's RING_HASH LB policy use virtual nodes, and how is K tuned in that context?**
A: In Envoy's `RING_HASH` policy for load balancing (not data storage), virtual nodes serve a different purpose than in a database: they ensure that requests for the same hash key (often a user ID or session ID extracted from a request header) are consistently routed to the same backend, enabling cache affinity or session affinity at the load balancing layer. Envoy's configuration:

```yaml
lb_policy: RING_HASH
ring_hash_lb_config:
  minimum_ring_size: 1024     # Minimum total ring entries
  maximum_ring_size: 8388608  # Maximum total ring entries
  hash_function: XX_HASH
```

Envoy automatically adjusts the effective K per backend to maintain the minimum_ring_size constraint: with 10 backends and minimum_ring_size=1024, K≈102. If backends have configured weights, their effective K is proportional to their weight (more weight = more ring entries = more requests routed to them). This is the weighted virtual node pattern (Q14) applied to LB rather than data storage — same mechanics, different application context.

## Section 9: Scenario-Based Questions

**Q30. "Design a consistent hash ring for a Memcached cluster of 5 nodes with different memory sizes (32GB, 32GB, 64GB, 64GB, 128GB). Walk through the virtual node configuration."**
A: Total memory: 32+32+64+64+128 = 320GB. Virtual node count should be proportional to memory (capacity), so each node's K is proportional to its share of total capacity:

```
Node A: 32GB  → K_A = base × (32/320)  = base × 0.10
Node B: 32GB  → K_B = base × (32/320)  = base × 0.10
Node C: 64GB  → K_C = base × (64/320)  = base × 0.20
Node D: 64GB  → K_D = base × (64/320)  = base × 0.20
Node E: 128GB → K_E = base × (128/320) = base × 0.40
```

Choose base=500 (giving ~50-200 vnodes per node with reasonable distribution): K_A=K_B=50, K_C=K_D=100, K_E=200. Total ring entries: 50+50+100+100+200=500. Expected traffic shares: A=10%, B=10%, C=20%, D=20%, E=40% — matching memory proportions. Verify: with K_min=50, `σ ≈ 1/sqrt(5 × 50) ≈ 9.5%` — somewhat high variance. Increase base to 2000 for K_A=K_B=200, K_C=K_D=400, K_E=800: `σ ≈ 1/sqrt(5 × 200) ≈ 4.5%` — better. The interview expects you to state the proportional K formula, calculate and verify distribution, and recognize that K must be increased when the smallest node's K is too low for acceptable variance.

**Q31. "Your Cassandra cluster has 6 nodes, each with K=256 virtual tokens. After monitoring, you notice Node 3 consistently handles 25% of read traffic while each other node handles ~15%. What would cause this and how do you fix it?"**
A: With K=256, purely random placement should give roughly equal distribution (σ ≈ 1/sqrt(6×256) ≈ 2.6%), so 25% vs 15% (a ~10% deviation) is far outside the expected statistical range and suggests something structural, not random:
- **Non-uniform hash distribution**: if the hash function has bias for the key range that lands on Node 3's arcs, its arcs attract more keys than a random model predicts. Check the actual key distribution, not just arc lengths.
- **Hot keys**: a small number of very frequently-accessed keys all happen to map to Node 3's token ranges — consistent hashing distributes keys uniformly but not necessarily request volume (a hot key is still just one key, going to one node, regardless of how many virtual nodes exist). Check per-key access rates.
- **Unequal arc lengths despite high K**: unlikely but possible — check Node 3's actual token positions and arc lengths (Cassandra's `nodetool ring` output). If arcs are genuinely unequal, removing and re-adding Node 3 regenerates its token positions.
- **Fix for structural imbalance**: run `nodetool rebalance` (Cassandra 4.0+ with the smarter token allocator) or manually adjust tokens. Fix for hot keys: key-splitting (Q27 of the consistent hashing guide) or application-level caching of the hot data.

**Q32. "A junior engineer asks: 'Why don't we just set K=10,000 to get perfect distribution? Storage is cheap.' How do you respond?"**
A: The storage cost itself is indeed negligible (K=10,000 with N=10 nodes = 100,000 ring entries ≈ a few MB). But the real costs are elsewhere:
- **Construction/modification cost**: each node addition/removal requires computing 10,000 new positions, inserting them into a sorted structure, and potentially triggering data migration across 10,000 arc boundaries. At K=150, this is milliseconds; at K=10,000, it's slower but still manageable for rare operations.
- **Gossip overhead (in P2P systems)**: 100,000 token entries gossiped across N nodes with every state exchange (Q22) — becomes non-trivial at large N.
- **Diminishing returns** (the critical point): moving from K=150 to K=10,000 reduces σ from ~2.6% to ~0.3% — an improvement smaller than the natural statistical variation in actual request rates across different keys. You've paid 67× the operational overhead for a distribution improvement you can't even measure in practice, since real workloads don't have uniform request rates across keys regardless of how perfect the ring distribution is. The right answer: K=150-256 already provides excellent distribution; invest engineering effort elsewhere rather than over-engineering a solved problem.

**Q33. "You're designing a distributed rate limiter where each request for user `U` must be tracked by the same node (for accurate per-user rate counting). The backend node fleet autoscales between 5 and 50 nodes. How do virtual nodes help, and what's the key operational concern?"**
A: Virtual nodes (via Envoy's RING_HASH or a custom consistent hash in the rate limiter application) route all requests for user `U`'s hash to the same backend node, giving the rate limiter consistent state for that user. The key operational concern with autoscaling: every scale-out/scale-in event causes `1/N` of users to remap to different nodes — and their in-flight rate limit counters are on the old node, not the new one. For the brief migration window, those users could exceed their rate limit (they appear to have zero requests to the new node) or be incorrectly throttled (the new node sees no state and starts fresh). Mitigations: (1) stateful handoff — on scale events, the cluster migrates rate-limit state for remapped users to the new node before the routing switch (expensive, complex); (2) short-TTL counters — rate limit windows are short (e.g., 1 minute); a remap mid-window causes at most one window of inaccuracy, after which the new node has correct state; (3) accept bounded inaccuracy around scale events as a product decision, since a brief rate limit undercount at low volume (scale-out) or overcounting (scale-in) is often acceptable for non-billing-critical rate limits; (4) use centralized storage (Redis) for rate limit state instead of node-local state — eliminating affinity requirements entirely, at the cost of a network hop per check.

|---|---|
| Single-position problem | Random arc lengths → high load variance; one node absorbs all of failed node's load |

| K selection | K=100-200 typical; Ketama=160, Cassandra=256 (old), 16 (new with smarter placement) |
| Weighted vnodes | Capacity ∝ K; higher-capacity nodes get proportionally more ring positions |

| Ring size (N×K entries) | O(N×K); trivially small even at K=1000 |
| Routing: O(log N×K) | Binary search on sorted ring entries |

| Cassandra 4.0 tokens | Deterministic optimal placement; K=16 matches K=256 random distribution quality |
| Riak vnodes | Fixed-slot partitions assigned to nodes; not random ring positions |
| Data migration | Distributed: K small transfers from K different source nodes per join |
| Gossip overhead | O(N×K); Cassandra 4.0's K=16 reduces this 16× vs K=256 |
