# Service Discovery — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is service discovery, and what problem does it solve?**
A: Service discovery is the mechanism by which services in a distributed system locate each other's current network addresses at runtime, without those addresses being hardcoded anywhere. It solves the problem of **dynamic infrastructure**: in any non-trivial system, the actual set of running service instances (their IPs, ports, and health) changes continuously — new instances spin up via autoscaling, old ones terminate via deployments or failures, addresses shift across restarts — making it impossible to statically configure "where is service X" in any durable way. Service discovery replaces the static assumption with a live, continuously-updated source of truth about which instances are currently healthy and reachable.

**Q2. Why is static configuration (hardcoded IPs or hostnames per service) insufficient in modern distributed systems?**
A: Static configuration treats infrastructure as fixed, but modern infrastructure is designed to be ephemeral — instances are created and destroyed by orchestrators, not manually managed. A hardcoded IP breaks the moment that instance is replaced; a hardcoded hostname helps only if something else is already doing the discovery work behind it (a load balancer or DNS record that itself must be kept current). More practically: in a system with dozens of services each running multiple instances that scale and deploy continuously, manually maintaining correct static address configuration across all callers of all services becomes an operational burden that doesn't scale, creates frequent stale-configuration incidents, and produces tight coupling between callers and the specific infrastructure topology of their dependencies — exactly the coupling dynamic service discovery is designed to eliminate.

**Q3. What are the two fundamental components of any service discovery system?**
A: A **service registry** — the authoritative, live data store that tracks which service instances currently exist, their addresses, and their health status; and a **discovery mechanism** — the means by which a service (or its proxy) queries that registry to find current, healthy instances of a dependency it wants to call. Different architectures separate or combine these responsibilities differently (DNS can act as both; a system like Consul explicitly separates them), but the two logical functions — "maintain a live registry" and "allow clients to query it" — are always present in some form.

**Q4. What's the difference between service discovery and load balancing, and how do they relate?**
A: Service discovery answers "which instances of this service currently exist and are healthy" — it returns a set of candidates. Load balancing answers "of those candidates, which specific one should this particular request go to" — it selects from the set and distributes across it. Discovery is logically prior to load balancing: you can't load balance across a set of instances without first knowing what that set is. In practice the two are deeply intertwined — many service discovery systems expose their results directly as input to a load balancer (the load balancer's backend pool is populated dynamically from the registry), and some client-side discovery implementations fold a load-balancing algorithm directly into the discovery client.

## Section 2: Client-Side vs Server-Side Discovery

**Q5. What is client-side service discovery, and what does it require of the calling service?**
A: In client-side discovery, the calling service is responsible for querying the registry itself, receiving the list of currently available instances, applying a load-balancing algorithm to select one, and making the request directly to the chosen instance — the intelligence for both discovery and load balancing lives in the client. This requires each calling service to embed a discovery-aware client library (e.g., Netflix Ribbon, or a gRPC resolver implementation) that knows how to talk to the registry and how to select instances from it. The calling service is therefore tightly coupled to the registry's interface/protocol — changing the registry system requires updating every service that embeds the client library.

**Q6. What is server-side service discovery, and how does it shift responsibility compared to client-side?**
A: In server-side discovery, the calling service makes a request to a well-known, stable address (a load balancer, a gateway, or a sidecar proxy), and *that intermediary* performs the registry query, selects a backend instance, and forwards the request — the calling service itself never directly interacts with the registry or makes load-balancing decisions. The discovery and selection logic lives in the intermediary, not the caller, making the caller genuinely simple (it just calls a stable address and the routing is handled elsewhere). This is the model used by service meshes (the sidecar proxy handles discovery transparently), Kubernetes Services (kube-proxy handles endpoint selection behind a stable ClusterIP), and API Gateways doing dynamic backend routing (the gateway queries the registry, per the dynamic routing discussion in the API Gateway: request routing guide).

**Q7. What are the concrete trade-offs between client-side and server-side discovery?**
A: Client-side gives the caller more direct control and visibility into which specific instance it connected to (useful for stateful protocols where the caller genuinely needs to target a specific instance), and avoids adding a network hop — the call goes directly from caller to chosen instance. Server-side keeps calling services simple and decoupled from the registry system (no embedded library, no registry protocol dependency), centralizes the discovery/routing logic so it can be updated without changing every calling service, and handles discovery-related failures in one place — at the cost of adding an intermediary hop and a component that itself must be reliable, since it becomes a dependency of every service-to-service call. In practice, service mesh architectures (Q20–21) have largely shifted the balance toward server-side (via sidecar proxies) because they achieve simplicity-for-callers while keeping the hop within the same node rather than adding a remote round trip.

## Section 3: Service Registration

**Q8. What is service registration, and when/how does it happen?**
A: Service registration is the act of an instance recording itself in the service registry — "I exist, I'm at this address, I serve this service name" — typically on startup, and deregistering on shutdown. The registry then includes that instance as a candidate for discovery queries until it's removed (either by explicit deregistration or by the registry's health-check mechanism detecting it's no longer healthy/present, Q12).

**Q9. What is the difference between self-registration and third-party registration?**
A: In **self-registration**, each service instance registers itself with the registry directly on startup, using an embedded registration client — the service itself is responsible for the register/deregister lifecycle (e.g., a Spring Boot app with a Consul client library that calls the Consul API at startup). Simple to implement but couples each service to the specific registry's client API, and relies on the service correctly deregistering itself on clean shutdown — something it may fail to do if it crashes suddenly rather than shutting down gracefully. In **third-party registration**, an external agent or orchestrator (Kubernetes, a sidecar, a deployment platform) is responsible for registering and deregistering service instances on their behalf — the service itself is unaware of the registry at all, keeping it decoupled. This is the more common model in modern containerized environments, where the orchestrator (Kubernetes, Nomad, ECS) already knows exactly which instances are running and can maintain registry state authoritatively without relying on each service instance to correctly manage its own registration lifecycle.

**Q10. What is the risk of a service instance failing to deregister itself when it goes down, and how is it mitigated?**
A: If a crashed or abruptly terminated instance remains registered as "available" in the registry, it will continue to receive traffic from clients resolving it as a valid target — causing connection failures, errors, or timeouts for those callers until the stale registration is removed. This is mitigated via the registry's health-checking mechanism: a well-designed registry doesn't rely solely on explicit deregistration but actively probes registered instances on a schedule, and automatically marks (or removes) instances that fail health checks as unavailable — so a crashed instance that never had a chance to deregister itself is automatically culled from the available set by the registry's own health-check poller within some bounded time window (governed by the health-check interval and failure threshold).

## Section 4: Health Checking in Service Discovery

**Q11. How does health checking integrate with service discovery, and why is it not optional?**
A: Health checking is the mechanism by which the service registry distinguishes "this instance is registered" from "this instance is actually currently healthy and able to serve traffic" — without it, the registry is just a list of everything that was ever registered, including instances that have since crashed, hung, or degraded. Discovery queries that return unhealthy instances cause real failures for callers, making health-check-integrated discovery a correctness requirement, not an optional enhancement. Callers should be able to trust that the instances returned by the registry are currently healthy — that trust is what the health-check mechanism maintains.

**Q12. What are the main types of health checks used in service discovery contexts?**
A: **Heartbeat/TTL-based**: the registered service itself is responsible for periodically sending a "I'm still alive" ping to the registry; if the registry doesn't receive a heartbeat within a configured TTL window, it marks the instance as failing — simple but requires the service to implement heartbeat logic, and can mark healthy-but-network-disrupted instances as failed. **Active probing (agent-based)**: the registry (or an agent running alongside the registry, as in Consul's agent model) actively makes outbound probes to each registered instance on a schedule — typically an HTTP health endpoint, a TCP connection attempt, or a gRPC health check — and marks instances failing based on probe outcomes; the probe results reflect actual reachability and liveness from the registry's network perspective, independent of whether the service is correctly implementing a heartbeat. **Kubernetes readiness probes**: a specific variant of active probing where the kubelet probes each container's configured readiness endpoint, and Kubernetes' endpoint controller automatically adds/removes pod IPs from Service Endpoints based on readiness probe results — directly driving which instances the Kubernetes service abstraction routes traffic to.

**Q13. What's the distinction between a liveness check and a readiness check, and why does it matter for service discovery?**
A: A **liveness check** answers "is this process alive and not deadlocked/crashed — should the orchestrator restart it" — it's about whether the process itself is running healthily. A **readiness check** answers "is this instance currently prepared to serve traffic — should it receive requests" — it's about whether the instance is in a state appropriate for inclusion in active service discovery results. An instance can be *live* but not *ready* (a newly started instance still warming up a cache, or a healthy process temporarily unable to reach a required dependency) — and for service discovery specifically, the readiness check is the relevant one: a live-but-not-ready instance should not be in the discovered set of instances returned to callers, even though it shouldn't necessarily be restarted. Conflating the two causes either premature traffic routing to unready instances or unnecessary restarts of temporarily-unready-but-healthy processes.

## Section 5: Service Registries — Technologies and Patterns

**Q14. What are the main dedicated service registry technologies, and what characterizes each?**
A: **Consul** (HashiCorp): purpose-built for service discovery and health checking, with a rich agent-based health-check model, DNS and HTTP API interfaces for querying, built-in key-value store, and support for multiple data centers — widely used both in VM-based and container-based environments, and frequently paired with API Gateways or service meshes as the underlying registry backend. **etcd**: a distributed key-value store focused on consistency (used as Kubernetes' own internal state store), sometimes used directly as a service registry in custom implementations or as a backend for other systems; not primarily purpose-built for service discovery but reliable for the consistency guarantees required. **Apache ZooKeeper**: an older distributed coordination service used for service discovery in older Java-centric architectures (originally prominent in Kafka, Hadoop, early Netflix stack); largely replaced by Consul and Kubernetes-native mechanisms in newer systems. **Kubernetes Endpoints / EndpointSlices**: the Kubernetes API objects that track, per Service, the current set of healthy pod IPs — not a standalone registry product but effectively *the* service registry within a Kubernetes cluster, automatically maintained by the endpoint controller, queried by kube-proxy and CoreDNS and other Kubernetes-aware consumers.

**Q15. What consistency model do service registries generally need to prioritize, and what's the CAP theorem implication?**
A: Service registries are a case where **availability** is generally prioritized over strict consistency, for a pragmatic reason: a briefly stale view of the registry (an instance that recently became unhealthy still appearing as available for a short window, or a newly-registered instance not yet visible everywhere) is less harmful in practice than the registry itself becoming unavailable (causing callers to be unable to discover *any* instances of their dependencies). Most production service registries (Consul in its default mode, for example) are designed for AP behavior under partition — they'll serve possibly slightly stale data rather than refuse to serve data at all when a cluster partition occurs. The implication for operators: briefly inconsistent registry state is expected and should be tolerated in calling service logic (health-check retries at the call layer, not blind trust in every returned instance being perfectly healthy), not treated as an indication of system failure.

**Q16. Why does the service registry itself need to be highly available, and how is that typically achieved?**
A: Because it's a dependency of all service-to-service communication in the system — if the registry becomes unavailable, services that re-query for fresh instance lists on each request (or at short intervals) may fail to find healthy backends, effectively taking down service communication broadly even when all the actual backend services are perfectly healthy. Achieved by running the registry itself as a distributed, replicated cluster (Consul runs as a Raft-consensus cluster of 3 or 5 nodes; etcd similarly; Kubernetes' own API server is deployed with etcd replication for exactly this reason), and by having service discovery clients cache recently-resolved instance lists locally so they can continue using a slightly stale but functional list during a brief registry outage rather than failing immediately when the registry is momentarily unreachable.

## Section 6: DNS as Service Discovery

**Q17. How does DNS function as a service discovery mechanism, and what's its fundamental appeal?**
A: DNS is the simplest possible service discovery interface — every language, runtime, and standard networking library already knows how to make a DNS query, so a service just resolves a hostname (e.g., `orders-service.internal`) and gets back the current IP(s) of available instances, without any additional client library or discovery SDK required. In Kubernetes specifically, CoreDNS provides exactly this interface for internal service discovery — every Service gets a DNS name automatically, and querying it returns the ClusterIP (or, for headless services, individual pod IPs directly), making DNS the universal, zero-additional-dependency discovery mechanism for workloads running in the cluster.

**Q18. What are the limitations of DNS-based service discovery compared to a dedicated registry like Consul?**
A: The same fundamental limitations discussed in the DNS and DNS-based load balancing guides: TTL-bound propagation means the view of available instances is not instantaneous — a newly registered instance won't be visible until a DNS TTL expires and is re-queried, and a recently-failed instance may still appear in cached DNS results until its TTL expires, even if health-checking infrastructure has already detected it as unhealthy. DNS also has limited expressiveness in what it can return — basic A/AAAA records (IP only) or SRV records (IP + port + priority/weight), but no richer metadata (instance version, availability zone, custom labels) that a dedicated registry can expose and that a sophisticated service-discovery client can filter or prefer on. For simple, stable-topology use cases, DNS is perfectly sufficient; for high-churn environments or cases requiring rich, metadata-driven routing, a dedicated registry provides meaningfully more capability.

**Q19. What is a "headless" Kubernetes Service, and when is it the right service discovery tool?**
A: A headless Service (configured with `clusterIP: None`) has no stable virtual ClusterIP — DNS resolution of its name returns the individual IP addresses of all currently healthy and ready backing pods directly (as multiple A records), rather than one virtual IP that kube-proxy load balances behind. This is the right tool when the calling application needs direct, individual addressability of specific backend instances rather than opaque, transparent load balancing — most commonly for stateful workloads (database clusters like Cassandra or MongoDB replication sets, Kafka brokers, Elasticsearch nodes) where the client needs to target specific nodes directly (e.g., sending a write to the primary replica, or using a client-side sharding algorithm that maps keys to specific cluster members) rather than treating all instances as interchangeable behind a single IP.

## Section 7: Service Discovery and Service Meshes

**Q20. How does a service mesh handle service discovery differently from the approaches described so far?**
A: A service mesh (Istio, Linkerd, Consul Connect) intercepts all network calls from each service instance via a sidecar proxy (typically Envoy or a lightweight equivalent) running alongside every instance in the same pod/node — the application code makes what appears to be a direct call to the target service hostname, but the mesh's iptables rules transparently redirect that call through the local sidecar, which handles discovery (querying the control plane for current healthy endpoints, per Q21), load balancing, retries, circuit breaking, and mTLS, entirely transparently to the application. This is server-side discovery (Q6) implemented at the sidecar level — the application itself is genuinely decoupled from the discovery mechanism, more thoroughly than even a cluster-level load balancer, since even the awareness that a load balancer exists is hidden from the application's perspective.

**Q21. What is the "control plane vs data plane" distinction in a service mesh, and how does it relate to service discovery specifically?**
A: The **control plane** is the centralized management component of the mesh (Istiod in Istio, the Linkerd control plane) responsible for maintaining the authoritative view of service topology — which instances exist, their health, and any routing policies — and distributing that information to all the sidecar proxies. The **data plane** is the set of sidecar proxies themselves, which actually handle the live request traffic based on the configuration they receive from the control plane. From a service discovery perspective: the control plane is the registry and configuration source; the data plane's sidecars are the discovery clients, continuously receiving updated endpoint information from the control plane (often via the xDS API in Envoy-based meshes) rather than polling a central registry themselves. This "push from control plane to sidecar" model means discovery information propagates quickly and continuously without each proxy needing to poll on its own schedule, avoiding the TTL-bound staleness of DNS-based discovery.

## Section 8: Operational and Security Considerations

**Q22. What is a service discovery "split-brain" scenario, and how does it manifest in practice?**
A: Split-brain in a service registry cluster occurs when a network partition causes the registry nodes to divide into two groups that can no longer communicate with each other, each of which may independently continue operating as if it has authoritative state — potentially diverging on which instances are registered/healthy, depending on the registry's consistency model. In practice, this can mean one subset of discovery clients (those talking to one partition's nodes) and another subset (talking to the other partition's nodes) receive different views of available instances, causing asymmetric routing and confusing behavior that's hard to diagnose since both groups believe they have the correct registry state. Most production registries handle this via their consensus protocol (Raft) explicitly refusing to serve queries from the minority partition (the partition that doesn't hold a quorum), accepting temporary unavailability of discovery on the minority partition over potentially incorrect/diverged answers.

**Q23. What security concerns are specific to service discovery infrastructure?**
A: The registry is a high-value target because it knows the address of every internal service — unauthorized read access to the registry effectively leaks the internal network topology of the entire system, giving an attacker a directory of targets. Unauthorized write access is worse: a compromised registry could register malicious instances as valid backends, redirecting traffic from legitimate services to attacker-controlled endpoints without any application code change. This is why service registries in production should require authentication for both reads and writes (Consul's ACL system, for example), and why service mesh control planes typically use mTLS for communication between the control plane and each sidecar, ensuring only authorized proxies can receive endpoint information or influence the routing data plane.

**Q24. How does service discovery need to handle multi-region or multi-cluster deployments?**
A: Single-registry discovery that spans multiple regions introduces latency (discovery queries crossing regions) and tight coupling (a registry outage in one region can affect discovery in others). The more common pattern is **per-region/per-cluster discovery**, where each region or cluster has its own local registry instance that's authoritative for instances within that region — with a separate, higher-level mechanism (DNS-based or geo-routing-aware) handling the question of which region a given caller should target in the first place (precisely the DNS-based load balancing / GeoDNS layer discussed in earlier guides). Cross-region service-to-service calls are typically handled as a distinct concern from within-region discovery, often with explicit configuration of "what is the stable address for this service in the other region" rather than expecting the local discovery registry to transparently serve cross-region results.

## Section 9: Scenario-Based Questions

**Q25. "A new service is deployed to Kubernetes and starts calling a dependency by its Kubernetes Service DNS name. Occasionally, especially right after deployments of the dependency, calls fail with connection refused errors for a short window. How would you explain and fix this?"**
A: This is the readiness-probe lag at the intersection of service discovery and health checking (Q13): when a new pod of the dependency starts up, it may take a moment to fully initialize before it can serve traffic — but if the readiness probe isn't configured, or is configured with too aggressive a success threshold (marking the pod ready before it's truly ready), Kubernetes may add the pod's IP to the Service's Endpoints before it can actually accept connections, and callers that resolve to that IP immediately get connection-refused errors. The fix is correctly configuring the dependency's readiness probe — ensuring it accurately represents "I am fully initialized and able to serve traffic" (checking application-layer readiness, not just "the process started") and tuning the initial delay and success threshold to match the actual startup behavior — so that Kubernetes only adds a pod to the Endpoints (and thus to service discovery results) after it's genuinely ready, not merely alive.

**Q26. "A microservice uses client-side service discovery with a locally-cached instance list refreshed every 30 seconds. During an incident, a backend instance becomes unhealthy and starts returning errors. Callers continue hitting it for up to 30 seconds before the cache refreshes. How would you reduce this window without just setting the refresh interval to zero?"**
A: Several complementary approaches that don't require polling the registry on every single call: implement **error-rate-triggered cache invalidation** — when a configured threshold of errors against a specific discovered instance is reached (e.g., 3 consecutive failures), proactively mark that instance as unavailable in the local cache and re-query the registry immediately for a fresh list, without waiting for the scheduled 30-second refresh; combine this with **call-layer retry logic** that avoids retrying against the same instance that just failed (retrying on a different discovered instance from the same cached list), so even within the 30-second window, individual failed calls recover against healthy instances rather than repeatedly hitting the same bad one; and ensure the health-check mechanism in the registry itself is configured with a short probe interval (Q12) so that by the time a local cache invalidation triggers a re-query, the registry already reflects the unhealthy state rather than still showing the instance as healthy.

**Q27. "Your organization runs services across both a Kubernetes cluster and some legacy VM-based services. The VM services need to discover and call the Kubernetes-based services, and vice versa. How would you approach this?"**
A: This is a hybrid discovery problem — the Kubernetes-internal DNS (e.g., `orders-service.default.svc.cluster.local`) is not resolvable from outside the cluster, and VM services have no native awareness of Kubernetes service topology. Common approaches: expose Kubernetes services that need to be reachable from VMs via a stable external endpoint (a LoadBalancer-type Service, an Ingress, or a NodePort) with a hostname that's registered in an external, cluster-agnostic registry (e.g., Consul) or a DNS zone that VM services can resolve — making those Kubernetes services discoverable from outside via the same mechanism VM services use for everything else. For Kubernetes services that need to discover VM services, register the VM services in Consul (or another registry Kubernetes is also aware of), and configure CoreDNS within the cluster to forward queries for the relevant hostname suffix to Consul's DNS interface — making VM services discoverable from within the cluster via standard DNS queries. This bidirectional registration in a shared, cluster-agnostic registry (Consul is commonly used for exactly this hybrid role) is the most generalized solution, treating both Kubernetes and VM environments as equal citizens in one unified service registry rather than having either side be invisible to the other.

**Q28. "A team proposes that your organization's services should each implement self-registration directly, calling the Consul API on startup and shutdown. Another team argues all registration should go through the Kubernetes deployment pipeline (third-party registration). Evaluate both approaches."**
A: Self-registration (Q9) gives each service team direct, explicit control over their own registration lifecycle and the metadata they publish (version, capabilities, custom labels), but couples every service to the Consul client API specifically — changing the registry system later requires updating every service. It also relies on clean shutdown for deregistration, which crash scenarios don't guarantee (though TTL-based health checks mitigate this, Q12). Third-party registration via the Kubernetes pipeline keeps services entirely decoupled from the registry protocol (a service that registers itself via the orchestrator is portable to a different registry without code changes), centralizes registration correctness in one place (the platform team owns it, reducing the chance of individual teams implementing registration incorrectly), and handles deregistration correctly even for crash scenarios since the orchestrator knows definitively when a pod has terminated. The stronger default for a Kubernetes-native architecture is third-party/orchestrator-driven registration — it's consistent with how Kubernetes already manages pod lifecycle, eliminates a class of potential implementation bugs across many teams, and keeps service code free of infrastructure-specific dependencies — reserving self-registration for cases where a service genuinely needs to publish custom, dynamic metadata that only it knows at runtime and that can't be inferred from the orchestrator's view.

**Q29. "Your team is building a new internal RPC framework and needs to decide whether to use client-side or server-side service discovery. What questions would you ask to make this decision, and which would you lean toward for most modern microservices setups?"**
A: Questions to ask: Does the calling service need direct, instance-specific addressability (targeting a specific stateful backend node), or is transparent, any-healthy-instance routing sufficient? Is the organization already running a service mesh — if so, server-side discovery is already provided transparently and adding a client-side library duplicates that layer unnecessarily. How many different languages/runtimes are calling services written in — client-side discovery requires a correct, maintained library per language, while server-side discovery is language-agnostic at the call site. How important is it to keep application code free of infrastructure dependencies? For most modern microservices setups running on Kubernetes, the lean is clearly toward **server-side discovery** — either via Kubernetes Services (kube-proxy handling backend selection behind a stable ClusterIP) or via a service mesh sidecar, both of which provide transparent, zero-library-embedding, language-agnostic discovery that's automatically synchronized with the cluster's actual live topology. Client-side discovery makes more sense specifically for stateful protocols requiring direct instance addressing (headless services, Q19) or for performance-critical cases where even a local-proxy hop is too costly and the team is willing to maintain per-language client libraries to eliminate it.

**Q30. "After migrating to a service mesh, a team notices that requests to a downstream service still occasionally fail immediately after that service's deployment rolles out new pods, despite the mesh supposedly handling discovery automatically. How would you investigate?"**
A: The likely cause is a propagation lag between when Kubernetes adds a new pod to the Service Endpoints (which can happen before the pod is fully ready if readiness probes aren't configured correctly, Q25) and when the service mesh control plane has distributed that updated endpoint information to all the relevant sidecar proxies (Q21). If new pod IPs appear in the Endpoints before they're truly ready, and the control plane pushes those IPs to sidecars that immediately start routing to them before they can accept connections, callers get transient failures during the propagation window. Investigate by checking: (1) whether readiness probes on the newly-deployed pods are correctly configured to gate endpoint addition (Q25); (2) the control-plane-to-sidecar propagation latency for endpoint updates in the mesh setup — is there meaningful lag between when the control plane receives the new endpoint and when all sidecars reflect it; (3) whether the sidecar's load balancing is configured with outlier detection (automatic removal of endpoints generating errors from active rotation), which would limit blast radius even during a brief propagation window where a not-yet-ready endpoint briefly receives traffic. The fix typically combines better readiness probe configuration (addressing the root cause) with outlier detection configured in the mesh (providing defense in depth even if a not-ready instance briefly makes it into active rotation).

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Service discovery | Runtime resolution of which instances of a service are currently healthy and reachable |
| Service registry | The authoritative, live store of registered instances and their health status |
| Client-side discovery | Caller queries registry, selects instance, connects directly — requires embedded client library |
| Server-side discovery | Caller uses a stable address; intermediary (proxy/LB/sidecar) handles registry query and selection |
| Self-registration | Service instance registers itself on startup; relies on clean shutdown or health-check culling |
| Third-party registration | Orchestrator/platform registers instances; services are registry-agnostic |
| Readiness vs liveness | Readiness = ready to serve traffic (discovery); liveness = alive/not deadlocked (restart) |
| Health-check integration | Registry actively probes instances; stale/unhealthy removed from discovery results |
| Headless Service (K8s) | Returns individual pod IPs directly; for clients needing per-instance addressability |
| DNS-based discovery | Zero-library; TTL-bound staleness; limited metadata expressiveness |
| Consul / etcd / ZooKeeper | Dedicated registries; richer health-checking, metadata, and query capabilities |
| Service mesh discovery | Control plane maintains registry; sidecars receive live endpoint updates via push (xDS) |
| Multi-region | Per-region registries; higher-level geo-routing (DNS/GeoDNS) for cross-region targeting |
| Registry security | Authentication required; unauthorized write access = ability to redirect arbitrary traffic |

**Tip for interviews:** What separates strong candidates on service discovery specifically: (1) being precise about **client-side vs server-side discovery** as a real architectural decision with concrete trade-offs, not just two names for the same thing — and knowing which modern environments (Kubernetes, service meshes) effectively mandate server-side (Q5–7, Q29); (2) understanding that **health checking is not optional** — the registry is only useful if it accurately reflects live health, and the readiness-vs-liveness distinction is a concrete, practical thing that causes real production incidents when confused (Q11–13, Q25); (3) being able to explain **why the registry itself must be highly available and cached locally** — it's a dependency of all service-to-service communication, so its own failure mode must be designed for (Q16, Q26); (4) clearly articulating **DNS-based discovery's limitations** compared to a dedicated registry — specifically TTL-bound propagation and limited metadata expressiveness — and knowing *when* DNS is sufficient vs when a dedicated registry is worth the added operational complexity (Q17–19); and (5) understanding the **service mesh control-plane/data-plane split** clearly enough to explain how endpoint information flows from registry to sidecar and why that propagation is fast but not instantaneous — a source of real, subtle production incidents that strong candidates can reason through concretely (Q20–21, Q30).
