# IP Hash — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is IP Hash load balancing?**
A: A stateless affinity algorithm that deterministically maps a client's source IP address to a backend server using a hash function. Every request from the same IP always lands on the same backend — as long as the pool size doesn't change. Unlike Round Robin or Least Connections, which optimize for even distribution, IP Hash optimizes for consistency: the same client always reaches the same server. It is the simplest form of client-to-server affinity at the network layer.

**Q2. How does the hash mapping work mechanically?**
A: The LB extracts the client's source IP from the IP header, runs it through a hash function, and maps the result to a backend index using modulo:

```
backend_index = hash(client_ip) % num_backends
selected_backend = backend_list[backend_index]
```

The hash function is typically a fast non-cryptographic hash (CRC32, MurmurHash, or FNV) chosen for speed and reasonable distribution rather than security. The result is deterministic — the same IP always produces the same hash, the same modulo, the same backend — with no per-request state stored at the LB.

**Q3. What does "stateless affinity" mean, and why does it matter?**
A: Stateless affinity means the LB doesn't need to store a lookup table of "IP → backend" mappings. The mapping is computed on the fly from the IP itself. This is a key advantage over cookie-based sticky sessions, which require the LB to insert, read, and track session cookies — adding storage and lookup overhead. IP Hash scales to millions of clients without any per-client storage, because the backend selection is a pure function of the input IP.

**Q4. What information does the LB actually hash — just the IP, or more?**
A: Implementations vary:
- **IP only** (most common): `hash(source_ip)` — simplest, but all traffic from one IP goes to one backend.
- **IP + Port**: `hash(source_ip, source_port)` — different TCP connections from the same IP (different ports) may go to different backends. Better distribution but breaks per-client affinity.
- **IP + Destination port**: `hash(source_ip, dest_port)` — useful for multi-protocol LBs where the same client accesses different services.
- **URI hash**: `hash(request_uri)` — an L7 variant that routes based on URL rather than IP, useful for caching proxies (same URL always hits the same cache node).

In NGINX, the default `ip_hash` directive hashes the first three octets of the IPv4 address (the /24 subnet, not the full IP) — a design choice discussed in Q8.

**Q5. Is IP Hash L4 or L7?**
A: It can operate at both layers but is most commonly implemented at L4 (the hash is computed from the IP header, visible at L4) or as an L7 feature when the LB needs to extract IP from an `X-Forwarded-For` header (because the direct connection IP is the upstream proxy, not the real client). The routing decision itself requires no HTTP parsing for basic IP Hash — making it lighter than L7 algorithms — but real-world deployments behind proxies/CDNs require L7 header inspection to get the true client IP.

## Section 2: Use Cases

**Q6. What is the primary use case for IP Hash?**
A: Session affinity for stateful applications — where backend servers store user session state in local memory (HTTP sessions, WebSocket state, in-memory game state) and cannot share it across nodes. IP Hash ensures a user's requests consistently reach the backend holding their session, without requiring external session storage. It is a pragmatic "lift and shift" technique for legacy stateful apps that weren't designed for distributed environments.

**Q7. What are the other use cases beyond session stickiness?**
A: Several important ones:
- **Caching proxies / CDN origin selection**: route all requests for the same content to the same origin cache node, maximising cache hit rate. Similar to consistent hashing but simpler.
- **Rate limiting per client**: if rate limiting state is stored per-backend, IP Hash ensures a client's requests always hit the same backend's rate limiter — avoiding under-counting across nodes.
- **Stateful protocol handling**: some protocols (FTP active mode, SIP, certain VPN protocols) establish control and data connections separately. IP Hash ensures both connections land on the same backend, which holds the protocol state.
- **Debugging / troubleshooting**: pin a specific IP to a specific backend for reproducible testing or incident investigation.
- **License-server / auth-server affinity**: systems where authentication tokens or licence checks are cached per-backend benefit from requests returning to the same node.

**Q8. Why does NGINX hash only the first three octets of an IPv4 address (the /24 subnet)?**
A: This is a deliberate design choice to improve load distribution when clients sit behind a NAT or CGNAT that assigns IPs from the same /24 subnet. If hashing the full IP, all clients from `192.168.1.x` (same NAT, different last octet) would spread across backends. But hashing only the first three octets means all clients from `192.168.1.x` go to the same backend — preserving locality for cases where all clients in a /24 are related (e.g., a corporate network behind NAT). The trade-off: it reduces effective hash entropy (at most 256 distinct values per /24 instead of 65536), which can cause uneven distribution when most clients share a /24. This behaviour is specific to NGINX and differs from most other LB implementations.

**Q9. What is URI hash and how does it relate to IP Hash?**
A: URI hash is an L7 variant that hashes the request URI (path + query string) instead of the client IP. It's used in caching proxy layers where the goal is to ensure the same URL always goes to the same cache node — maximising cache hit ratio by preventing the same object from being cached on multiple nodes. NGINX supports this via the `hash $request_uri` directive. The algorithm is identical to IP Hash; only the hash input changes from IP address to URI string. Both are examples of the broader "hash-based sticky routing" pattern.

## Section 3: The Core Problem — NAT and CGNAT

**Q10. What is NAT and why does it break IP Hash?**
A: Network Address Translation (NAT) allows many devices behind a router to share a single public IP address. From the LB's perspective, all requests from those devices appear to originate from one IP — the NAT gateway's public address. IP Hash maps that single IP to one backend, so all users behind the NAT gateway hit the same backend, regardless of how many there are. A corporate office of 500 people behind a single NAT gateway sends all 500 users' traffic to one backend — creating a hot spot and defeating load distribution entirely.

**Q11. What is CGNAT and why is it a worse version of the same problem?**
A: Carrier-Grade NAT (CGNAT, RFC 6598) is NAT applied at the ISP level — an entire ISP or mobile carrier places thousands or millions of subscribers behind a single public IP (or a small pool of IPs). This is increasingly common as IPv4 addresses are exhausted. From the LB's perspective, an IP Hash that maps one IP to one backend could route millions of end users to a single backend. CGNAT is especially prevalent on mobile networks (4G/5G), making IP Hash particularly unreliable for mobile-facing applications.

**Q12. How common is the NAT problem in real deployments?**
A: Very common — far more common than most engineers expect:
- Enterprise SaaS: most B2B customers access from corporate networks behind NAT. A company with 1,000 employees may appear as 1–5 IPs.
- Mobile apps: 4G/5G CGNAT is near-universal. A single cell tower's traffic may share a handful of IPs.
- Cloud functions / serverless backends: AWS Lambda, GCP Cloud Functions share IPs from a small pool — all invocations from the same provider region may hash to the same backend.
- Bot traffic and scrapers: often operate from a small IP pool, concentrating on one backend.

The practical implication: **IP Hash should never be your primary load balancing strategy for public internet traffic.** It works reasonably well for internal services (where client IPs are predictable and diverse) or in specific affinity scenarios where the alternative (external session storage) is too costly.

**Q13. How does IPv6 affect IP Hash distribution?**
A: IPv6 introduces new challenges:
- Clients with IPv6 can use privacy extensions (RFC 4941) that randomize the last 64 bits of the address periodically (typically every 24 hours or per network connection). This means the same physical client may appear as a different IP on each connection — breaking affinity even without NAT.
- On the positive side, IPv6 eliminates NAT for most residential/enterprise clients — each device gets a unique routable IP, improving hash distribution dramatically.
- NGINX's /24 subnet hashing doesn't apply cleanly to IPv6 (no comparable /24 equivalent) — different implementations handle IPv6 IP Hash differently.

## Section 4: Redistribution on Pool Changes

**Q14. What happens to IP Hash routing when a backend is added or removed?**
A: With simple modulo hashing, adding or removing any backend remaps a large fraction of client IPs to different backends:

```
# 3 backends: hash(ip) % 3
Client A (hash=10): 10 % 3 = 1 → backend[1]

# After adding backend 4: hash(ip) % 4
Client A (hash=10): 10 % 4 = 2 → backend[2]  ← CHANGED
```

With N backends, adding or removing one server causes approximately `(N-1)/N` of all clients to be remapped — approaching 100% disruption as N grows. For stateful applications relying on IP Hash for session affinity, this means a deployment or failover event invalidates nearly all sessions — causing mass logouts or state loss.

**Q15. What is Consistent Hashing and how does it solve the redistribution problem?**
A: Consistent Hashing places both backends and client IPs on a virtual ring (hash space of 0 to 2^32). Each backend occupies one or more positions on the ring (called "virtual nodes" or "vnodes"). A client IP is hashed to a position on the ring, then routed to the nearest backend in the clockwise direction.

When a backend is added or removed, only clients whose hash position falls between the old and new backend positions are remapped — approximately `1/N` of clients instead of `(N-1)/N`. This minimises disruption:

- Adding 1 backend to a 10-backend pool: ~10% of clients remap (instead of ~90% with modulo hash).
- Removing 1 failed backend: only its share of clients remap to the next node.

**Q16. What are virtual nodes (vnodes) in consistent hashing and why are they needed?**
A: Without vnodes, consistent hashing with N backends places N points on the ring. With random placement, the arc lengths (and thus traffic shares) between backends are uneven — some backends get much more traffic than others by chance. Virtual nodes solve this: each backend is placed at K positions on the ring (K = 100–200 is typical). The arc lengths average out across K positions, giving each backend approximately 1/N of the ring — even distribution despite random placement. Vnodes also improve resilience: when a backend fails, its K positions are redistributed across all other backends, spreading the load evenly rather than dumping all traffic on one successor.

**Q17. Does NGINX's `ip_hash` use consistent hashing?**
A: No — NGINX's `ip_hash` uses simple modulo hashing. This means pool changes cause widespread remapping. NGINX does offer consistent hashing via the `hash` directive with the `consistent` keyword (which uses the Ketama consistent hash algorithm):

```nginx
upstream backend_pool {
    hash $remote_addr consistent;
    server backend1;
    server backend2;
    server backend3;
}
```

The `consistent` keyword activates Ketama — the same algorithm used by Memcached and many distributed caches — providing minimal remapping on pool changes. For production stateful applications, `hash $remote_addr consistent` is almost always preferable to `ip_hash`.

**Q18. What is the Ketama algorithm and why is it the standard for consistent hashing in caches?**
A: Ketama (developed at Last.fm in 2007) is a consistent hashing implementation that became the de facto standard for Memcached client libraries. Key properties:
- Places backends at 160 virtual nodes each (40 hash points × 4 replicas per point using MD5).
- Uses MD5 as the hash function — well-distributed across the ring though cryptographically overkill for LB use.
- Minimises key remapping on node addition/removal.
- Widely implemented: libketama, NGINX `consistent`, Python/Java/Ruby Memcached clients all implement it.

For load balancer use cases (rather than cache key routing), faster non-cryptographic hashes (MurmurHash3, xxHash) with 100–200 vnodes are common replacements.

## Section 5: IP Hash vs Cookie-Based Stickiness

**Q19. What are the trade-offs between IP Hash and cookie-based sticky sessions?**
A:

| Dimension | IP Hash | Cookie-Based Stickiness |
|---|---|---|
| State at LB | None (stateless) | Cookie storage/lookup per client |
| Accuracy | Poor (NAT, CGNAT, IPv6 privacy) | Exact (one cookie per browser session) |
| Works behind NAT | ❌ All NAT clients → same backend | ✅ Each browser gets its own cookie |
| Works with mobile / CGNAT | ❌ Poor distribution | ✅ Each app instance gets its own cookie |
| Requires L7 | ❌ L4 is sufficient | ✅ Must read/write HTTP headers |
| TLS termination required | ❌ No (can passthrough) | ✅ Yes (must read HTTP) |
| Session survives backend restart | ❌ Session in-memory, lost on restart | ❌ Same (session still in-memory on backend) |
| Client control | ❌ Client can't opt out | ✅ Client can clear cookies |
| Scale | O(1) per request | O(1) with hash lookup, but stores cookie map |

Rule of thumb: **IP Hash for internal services with predictable, diverse client IPs; cookie-based for public internet applications where NAT is common.** Neither is as good as externalising session state to Redis/Memcached, which eliminates affinity requirements entirely.

**Q20. Can you combine IP Hash with cookie-based stickiness?**
A: They're generally alternatives, not complements, since they solve the same problem (affinity). However, a layered approach is sometimes used: IP Hash as the first pass (fast, stateless, handles most clients correctly), with cookie-based stickiness as a fallback for clients whose IP changes between requests (mobile users, VPN switchers). In practice, this complexity is rarely justified — cookie-based stickiness alone is more reliable.

## Section 6: Implementation Details

**Q21. How does NGINX implement `ip_hash`?**
A: NGINX's `ip_hash` directive:
- Extracts `$remote_addr` (the direct connection's source IP).
- For IPv4: hashes the first 3 octets (the /24 subnet) using an internal hash function.
- For IPv6: hashes the full address.
- Maps the hash to a backend using modulo against the number of active (non-`down`, non-`backup`) servers.
- On a tie or unavailable server, tries adjacent backends in the list.
- Does not use consistent hashing — pool changes cause widespread remapping.

```nginx
upstream backend_pool {
    ip_hash;
    server backend1;
    server backend2;
    server backend3 down;   # excluded from rotation, hash still counts it
}
```

Note: marking a server `down` keeps it in the hash count (to preserve existing mappings) but stops routing to it — requests that would have gone to it are forwarded to the next available server in the list.

**Q22. What is the `$remote_addr` vs `$http_x_forwarded_for` problem in NGINX `ip_hash`?**
A: `$remote_addr` is the IP of the direct TCP connection to NGINX. If NGINX is behind a CDN, upstream proxy, or AWS ALB, `$remote_addr` is the proxy's IP — not the real client IP. Every client then appears to come from the same IP (the proxy), mapping all traffic to one backend. Fix: use the `hash` directive with `$http_x_forwarded_for` or `$realip_module` to extract the true client IP from the forwarded header:

```nginx
upstream backend_pool {
    hash $http_x_forwarded_for consistent;
    server backend1;
    server backend2;
}
```

But `X-Forwarded-For` can be spoofed by clients — a malicious client can set any IP in this header, potentially targeting a specific backend. In trusted proxy setups (e.g., behind your own ALB), this is fine; in untrusted contexts, validate or use `$realip_module` with trusted proxy IP ranges.

**Q23. How does Envoy implement IP Hash?**
A: Envoy's `RING_HASH` and `MAGLEV` policies implement consistent hashing (not simple IP modulo):

```yaml
lb_policy: RING_HASH
ring_hash_lb_config:
  minimum_ring_size: 1024
  maximum_ring_size: 8388608
  hash_function: XX_HASH  # or MURMUR_HASH_2
```

The hash key defaults to source IP but can be customised (header value, cookie, query param) via `HashPolicy` in the route configuration. `MAGLEV` is an alternative consistent hash implementation (from Google's Maglev paper) with better uniformity than ring hash at small pool sizes.

**Q24. What is Google's Maglev hashing algorithm, and when is it preferred over ring hash?**
A: Maglev (described in Google's 2016 paper) is a consistent hashing scheme that builds a lookup table of size M (a large prime, e.g., 65537) where each slot maps to a backend. The table is constructed so each backend occupies approximately M/N slots. Properties:
- **More uniform distribution** than ring hash, especially at small N (3–10 backends) — ring hash with few vnodes has high variance in arc lengths.
- **Faster lookup** — O(1) table lookup vs O(log N) ring traversal.
- **Larger memory footprint** — stores a full lookup table of M entries.
- **Minimal disruption on change** — like ring hash, remaps ~1/N entries on backend add/remove.

Preferred over ring hash when: backend pool is small (< 20 nodes) and distribution uniformity is critical, or when lookup speed is paramount. Ring hash is preferred when memory is constrained (no large table) or when the pool is very large (Maglev table grows).

## Section 7: Failure Modes & Edge Cases

**Q25. What is a "hot shard" in the context of IP Hash, and what causes it?**
A: A hot shard (or hot backend) is one backend receiving disproportionate traffic due to poor hash distribution. Causes:
- **NAT/CGNAT**: many clients sharing one IP all map to one backend.
- **Poor hash function**: clustering of hash values for certain IP ranges.
- **Small backend pool with unlucky distribution**: with 3 backends and a non-uniform hash, one may receive 50% of traffic.
- **Subnet-level hashing**: NGINX's /24 hashing maps an entire /24 subnet to one backend — if your biggest client is a large enterprise on one /24, that backend is overloaded.

Detection: monitor per-backend request rate and connection count. A hot shard will show significantly higher metrics than peers. Mitigation: switch to consistent hashing with vnodes (better distribution), or abandon IP Hash in favour of cookie-based stickiness.

**Q26. What happens to IP Hash when a backend fails mid-session?**
A: The client's IP was mapped to the failed backend. Options depending on implementation:
- **Simple modulo hash with failover**: the LB detects the backend is down (via health check) and falls back to the next backend in the list — disrupting the session once, then providing a stable new mapping.
- **Consistent hash with failover**: the client's position on the ring is served by the next clockwise backend — session is disrupted once, but only ~1/N of clients are affected (those whose home backend failed), not all clients.
- **No failover**: some simple implementations simply fail the request if the target backend is down.

In all cases, session affinity is broken on backend failure — the session state on the dead backend is inaccessible regardless of where the next request goes. This underscores the fundamental limitation of memory-resident session state, irrespective of which affinity algorithm is used.

**Q27. How does IP Hash interact with auto-scaling?**
A: Poorly. Auto-scaling adds or removes backends dynamically — exactly the pool change that causes widespread remapping in modulo-based IP Hash (Q14). With consistent hashing, remapping is minimal (~1/N). But even with consistent hashing, auto-scaling causes some session disruption:
- **Scale-out** (new backend added): ~1/N of clients are remapped to the new backend — those sessions are lost/reset.
- **Scale-in** (backend removed): the removed backend's clients (~1/N) are remapped to the next backend — sessions lost.

For applications that auto-scale frequently (e.g., based on CPU, time-of-day), IP Hash (even consistent) is a poor fit. External session storage is the only clean solution for auto-scaling + session affinity.

**Q28. What is the "changing client IP" problem and when does it occur?**
A: IP Hash assumes the same client always presents the same source IP. This breaks when:
- **Mobile network handoff**: switching between WiFi and 4G/5G changes the client's IP — session is lost.
- **VPN connection/disconnection**: changes egress IP.
- **Multi-path TCP (MPTO)**: can use multiple IPs simultaneously.
- **CDN / proxy IP rotation**: some CDNs rotate the IP they use for backend connections.
- **Round-robin DNS on client**: if the client resolves a hostname that round-robins across IPs for the forward proxy.

For mobile applications, the IP change problem is near-universal — sessions must survive IP changes, which IP Hash cannot provide. Cookie-based stickiness (which follows the session cookie regardless of IP) is robust to IP changes.

**Q29. Can IP Hash be used for DDoS mitigation?**
A: Somewhat — if the DDoS source IPs are diverse (which is common for a botnet), IP Hash distributes attack traffic across all backends, preventing a single backend from being overwhelmed. But if the attack uses few source IPs (amplification attacks, or attacks via a small botnet), IP Hash concentrates the attack on one or a few backends. IP Hash is not a DDoS mitigation tool — rate limiting, connection limiting, and upstream scrubbing centres are the right tools. IP Hash's effect on DDoS is incidental and unreliable.

## Section 8: Comparison With Other Algorithms

**Q30. IP Hash vs Consistent Hashing — complete comparison.**
A:

| Dimension | IP Hash (modulo) | Consistent Hashing |
|---|---|---|
| Algorithm | hash(ip) % N | Ring or lookup table |
| Remapping on pool change | (N-1)/N ≈ nearly all | ~1/N (minimal) |
| Distribution uniformity | Moderate | High (with vnodes) |
| Memory overhead | O(1) | O(N × vnodes) |
| Lookup speed | O(1) | O(log N) ring / O(1) Maglev |
| Supports weighted backends | ❌ Hard | ✅ Via vnode count |
| NGINX support | ✅ `ip_hash` | ✅ `hash ... consistent` |
| Envoy support | ❌ | ✅ `RING_HASH`, `MAGLEV` |
| Best for | Small stable pools, simple affinity | Caches, large/dynamic pools, minimal remapping |

For any production use case with auto-scaling or rolling deployments, consistent hashing strictly dominates modulo IP Hash.

**Q31. IP Hash vs cookie-based stickiness — when is IP Hash still the right choice?**
A: IP Hash is still appropriate when:
- **L7 is unavailable** — pure L4 TCP load balancing where HTTP headers aren't accessible.
- **Non-HTTP protocols** — SIP, custom TCP protocols where cookies don't apply.
- **Internal services** — client IPs are controlled, diverse, and stable (e.g., a fixed fleet of internal service instances calling a backend).
- **Simplicity is paramount** — no external session store, no cookie management, minimal operational overhead.
- **Debugging/testing** — pin specific IPs to specific backends deterministically.

For public internet HTTP traffic, cookie-based stickiness is almost always more reliable.

**Q32. IP Hash vs Random — is there ever a reason to use random selection?**
A: Pure random selection has no affinity — different requests from the same client go to different backends. It's never a replacement for IP Hash in affinity use cases. As a load balancing algorithm without affinity requirements, random is inferior to Round Robin (more variance at low request counts) and worse than P2C (less load-adaptive). The only scenario where random wins: extremely high QPS with large backend pools where even the O(1) Round Robin counter becomes a contention point — random requires no shared state at all. This is a niche edge case; P2C is almost always preferred over pure random.

## Section 9: Scenario-Based Questions

**Q33. "Your e-commerce app stores shopping carts in server memory. You're using Round Robin and users complain their cart empties on every other request. How do you fix it, and what are your options?"**
A: The root problem is that requests are hitting different backends, each with their own in-memory session store. Three options in order of quality:

1. **Best — externalise session storage**: move cart/session state to Redis or a database. All backends read from the same store — no affinity needed, works perfectly with any LB algorithm. Eliminates the problem at its root.
2. **Acceptable — cookie-based sticky sessions**: configure the LB to insert a session cookie and always route that cookie's requests to the same backend. Precise, works behind NAT, but creates uneven load and breaks on backend restart/scale-out.
3. **Quick but fragile — IP Hash**: configure `ip_hash` in NGINX. Zero-config, works immediately, but breaks for NAT users and disrupts sessions on any pool change. Appropriate only as a stopgap.

The interviewer expects you to advocate for option 1 while explaining why 2 and 3 are short-term workarounds.

**Q34. "You're designing a Memcached cluster. Should you use Round Robin, IP Hash, or Consistent Hashing for routing cache reads/writes from application servers?"**
A: Consistent Hashing — unambiguously. Here's why each other option fails:
- **Round Robin**: the same cache key is written to whichever backend is next in rotation, and reads for that key also go to whichever is next — almost always a different backend. Cache hit rate approaches 0%.
- **IP Hash**: routes all requests from one application server to one Memcached node. Doesn't help — the goal is to route each *key* to the *same* node, not each *caller* to the *same* node. Two app servers asking for the same key would hit different Memcached nodes (different source IPs → different backends).
- **Consistent Hashing**: routes `hash(cache_key)` to the same Memcached node, regardless of which app server asks. All app servers asking for the same key hit the same node — maximising hit rate. When a Memcached node fails or is added, only ~1/N keys remap — minimising thundering herd on cache miss.

This question tests understanding of *what* is being hashed (client IP vs. request key) and why the choice of hash input matters as much as the algorithm.

**Q35. "You're behind a CDN (Cloudflare). Your NGINX LB is using `ip_hash`. Engineers report all traffic goes to one backend. What's happening and how do you fix it?"**
A: `$remote_addr` in NGINX shows the CDN's edge node IP — not the real client IP. Cloudflare uses a small pool of edge IPs, so `hash(cloudflare_edge_ip) % N` maps most traffic to one or two backends. Fix:
1. Extract the real client IP from `CF-Connecting-IP` (Cloudflare's header) or `X-Forwarded-For`.
2. Use NGINX's `ngx_http_realip_module` to set `$remote_addr` to the value from the trusted header, after validating the request came from Cloudflare's known IP ranges.
3. Switch to `hash $realip_remote_addr consistent;` instead of `ip_hash;`.

Security note: only trust `CF-Connecting-IP` or `X-Forwarded-For` from Cloudflare's published IP ranges — validate these at the firewall level, not just NGINX config.

**Q36. "You have a gRPC service. Can you use IP Hash for load balancing? What are the limitations?"**
A: Technically yes at L4 (IP Hash routes the TCP connection), but with critical limitations:
- gRPC uses HTTP/2 — clients hold long-lived connections and multiplex many RPCs over one TCP connection. IP Hash at L4 pins all RPCs from one client IP to one backend for the lifetime of the connection (which may be hours). This works for per-client affinity but provides zero load balancing within that client's RPC stream.
- For gRPC, the better approaches are: (1) L7 load balancing at the stream level (Envoy `LEAST_REQUEST`) with no affinity (stateless gRPC services are preferred), or (2) if gRPC client affinity is needed, client-side load balancing (where the gRPC client library itself load-balances across a discovered set of backends), which bypasses the LB entirely for per-stream distribution.
- IP Hash + gRPC is appropriate only for legacy gRPC services that store per-client state server-side — the same niche as any other stateful affinity scenario.

**Tip for interviews:** Four things separate strong candidates on IP Hash: (1) immediately knowing the **NAT/CGNAT problem** (Q10–Q12) and why IP Hash is unreliable for public internet traffic — most candidates miss how pervasive CGNAT is on mobile; (2) knowing that **NGINX `ip_hash` hashes only the /24 subnet** (not full IP) and why (Q8) — a genuinely surprising implementation detail that shows real NGINX knowledge; (3) explaining the **modulo remapping problem** (Q14) and how consistent hashing (Ketama, Maglev) solves it with ~1/N remapping vs ~(N-1)/N; and (4) the **Memcached question (Q34)** — knowing that IP Hash routes per *client*, not per *key*, and why that distinction makes it wrong for cache routing. These four together demonstrate you understand not just what IP Hash does, but why it fails in the specific ways it does.
