# Consistent Hashing: Virtual Nodes in Distributed Caches and Databases — Interview Q&A (5 YOE Level)

---

## Section 1: Why Distributed Caches and Databases Need Consistent Hashing

**Q1. What specific failure does modulo-based sharding cause in a distributed cache, and how does it motivate consistent hashing with virtual nodes?**
A: In a Memcached cluster using modulo sharding (`hash(key) % N`), adding or removing one node causes `(N-1)/N` of all cached keys to remap to different nodes. For a 10-node cluster, a single node failure causes ~90% of all cached keys to suddenly be cache misses simultaneously — every client resolves them against a different backend than where the data was placed. The result is a thundering herd against the origin/database: all those cache misses hit the origin at once, potentially orders of magnitude more load than the origin can sustain. This "cache stampede on topology change" is the exact problem consistent hashing with virtual nodes is designed to solve, limiting remapping to ~1/N of keys (10% in the same example) regardless of how many virtual nodes are configured.

**Q2. What is the specific difference between how a cache and a database use consistent hashing, at the operational level?**
A: For a **cache**, data locality is advisory — if a key remaps to a new node after a topology change, it's a cache miss (the origin is consulted), not data loss or inconsistency. The cache re-populates naturally. Consistent hashing's main cache benefit is limiting the blast radius of topology changes: fewer remapped keys = fewer simultaneous origin hits = avoidance of thundering herd. For a **database**, data is the system of record — remapping doesn't just mean a miss, it means moving the actual data itself to the new owner node. Consistent hashing determines which node physically stores which rows/documents, and topology changes require actual data migration. The `1/N` remapping guarantee is critical because it bounds how much data must physically move and how many nodes are involved in that migration.

**Q3. Why is client-side consistent hashing common for distributed caches (Memcached) but server-side for distributed databases (Cassandra, DynamoDB)?**
A: Memcached itself is a simple, intentionally-dumb cache server — it has no built-in clustering, replication, or topology awareness. The consistent hash ring must therefore live in the client library (libketama, Twemproxy/Nutcracker, or application-embedded client code), with every client independently maintaining the same ring state. This works because cache consistency is eventually self-correcting (a wrong-node access is just a miss, fixed by re-populating that node), and all clients can agree on the ring from shared configuration without coordination. Cassandra and DynamoDB operate the ring server-side — each node knows the full ring topology through gossip (Cassandra) or a coordination service, and the client can send requests to any node (which will route correctly via the server-side ring knowledge), or use a smart driver that's ring-aware. Server-side ring management is necessary when the cluster needs to enforce replication, coordinate consistency across replicas, and manage data migration — responsibilities that belong to the storage system, not scattered across every client instance.

## Section 2: Distributed Caches

**Q4. How does a Memcached client library implement consistent hashing with virtual nodes in practice?**
A: A conformant Memcached client (using the Ketama algorithm) builds the ring at startup or on topology change:

```python
class MemcachedClient:
    def __init__(self, servers):
        self.ring = SortedDict()
        for server in servers:
            for vnode_pos in ketama_positions(server, K=40):  # 40 × 4 = 160 positions
                self.ring[vnode_pos] = server

    def get_server(self, key):
        h = ketama_hash(key)
        # Clockwise successor
        idx = self.ring.bisect_left(h)
        if idx == len(self.ring):
            idx = 0  # wrap-around
        return self.ring.values()[idx]

    def get(self, key):
        server = self.get_server(key)
        return server.get(key)

    def set(self, key, value, ttl):
        server = self.get_server(key)
        server.set(key, value, ttl)
```

All client instances have the same server list and the same Ketama parameters, so they independently compute the identical ring and therefore agree on which server owns each key — no coordination required between clients at request time. Server additions/removals require rebuilding the ring in all client instances (typically via a shared configuration store, push notification, or a periodic poll of the server list).

**Q5. What is Twemproxy (Nutcracker) and how does it centralize consistent hashing for Memcached?**
A: Twemproxy (open-sourced by Twitter) is a lightweight proxy that sits between application servers and a Memcached/Redis cluster, centralizing the consistent hashing logic. Application servers treat Twemproxy as a single Memcached endpoint — they issue standard Memcached commands without any ring awareness. Twemproxy internally maintains the consistent hash ring and routes each command to the correct backend node. This simplifies client code (no need to embed Ketama in every application service) and centralizes topology management (update Twemproxy's config to add/remove a node, without coordinating config changes across every application instance). The trade-off: Twemproxy is a new component on the critical path (single point of failure unless run redundantly), adds a network hop, and can become a throughput bottleneck at very high request rates. Modern architectures often skip Twemproxy and use client-side libraries or move to Redis Cluster instead.

**Q6. How does Redis Cluster differ from Ketama-based Memcached sharding, and how does this affect virtual node mechanics?**
A: Redis Cluster uses 16,384 fixed hash slots rather than a continuous ring with virtual node positions. The mapping is: `slot = CRC16(key) % 16384`, and each node owns a configurable contiguous range of slots. This is not virtual-node-based consistent hashing — it's a fixed-partition scheme. Key differences:

| Dimension | Ketama (Memcached) | Redis Cluster |
|---|---|---|
| Partitioning | Continuous ring + virtual nodes | 16,384 fixed discrete slots |
| Node ownership | Non-contiguous arcs (random vnode positions) | Contiguous slot ranges |
| Remapping on change | Automatic via ring (client-computed) | Explicit slot migration (CLUSTER SETSLOT) |
| Redistribution on node add | Automatic, ~1/N keys | Manual or via redis-cli --cluster rebalance |
| Who decides routing | Client library (ring-aware) or proxy | Cluster gossip (MOVED redirect to client) |
| Hot slot isolation | Difficult | Easy (move a specific slot to another node) |

Redis Cluster's slot approach sacrifices the automatic minimal-remapping property of true consistent hashing for more explicit, operational control over data placement — a trade-off that makes sense for a system where operators often want to precisely control which data goes where.

**Q7. What is hash slot "rebalancing" in Redis Cluster and how does it differ from consistent hash ring migration?**
A: In Redis Cluster, rebalancing is explicit: an operator (or redis-cli tooling) runs `CLUSTER REBALANCE` or manually issues `CLUSTER SETSLOT` + `MIGRATE` commands to move specific slot ranges from one node to another. During migration, a slot is in transitional state (`MIGRATING` on the source, `IMPORTING` on the destination); the cluster uses `MOVED` and `ASK` redirects to route requests correctly during the transition. This is fundamentally different from consistent hash ring migration: the ring automatically computes the new owner of every key and triggers background migration as a side effect of the ring update. Redis Cluster's explicit model gives more control (you can move exactly one slot at a time, observe it in flight, pause it) but requires more operational involvement — the redistribution doesn't "just happen" when you add a node the way it does with a consistent hash ring.

**Q8. What is hash tags in Redis Cluster, and why do they matter?**
A: Redis Cluster routes each key to a slot based on `CRC16(key) % 16384`. A hash tag forces a subset of characters — the content between the first `{` and `}` in the key name — to be used as the hash input instead of the full key name. This means keys like `{user:42}:profile` and `{user:42}:settings` both hash based on `user:42` and are therefore guaranteed to land on the same slot/node. This is critical for multi-key operations (`MGET`, `MSET`, transactions/pipelines, Lua scripts) — Redis Cluster only supports atomic multi-key operations when all keys are in the same slot. Without hash tags, it's statistically unlikely that two related keys land on the same slot, making server-side transactions impractical. This is a Redis Cluster-specific pattern with no equivalent in Ketama-based Memcached (which doesn't support multi-key atomic operations across nodes at all).

**Q9. What is a "cache avalanche" vs a "cache miss storm" in the context of distributed cache topology changes, and how does consistent hashing help?**
A: These terms are sometimes used interchangeably but are subtly different contexts:
- **Cache avalanche**: many cached entries expire simultaneously (same TTL, set at the same time) causing a burst of origin requests at one moment. This is unrelated to topology changes — it's a TTL-synchronization problem, mitigated by TTL jitter (covered in the cache invalidation guide).
- **Cache miss storm** (also "thundering herd on topology change"): a topology change (node failure, addition, or rebalancing) causes a large fraction of keys to remap to new nodes, all becoming simultaneous misses that hit the origin at once. This *is* a consistent hashing problem — and its mitigation is limiting remapping to `1/N` via virtual nodes, so that at most ~10% (for a 10-node cluster) of cached data needs to be re-fetched from origin at any one time. Without consistent hashing, a single node failure causes ~90% of keys to miss simultaneously — trivially enough to overwhelm most origin databases.

## Section 3: Distributed Databases — Cassandra

**Q10. How does Cassandra's token ring implement consistent hashing with virtual nodes, end to end?**
A: Each Cassandra node, at startup, generates or is assigned `num_tokens` (K) token positions on a 64-bit ring (range 0 to 2^63 - 1). These tokens are stored in system tables and gossiped to every other node. When a row is written, the partition key is hashed (using Murmur3 by default) to a 64-bit value, and that value's position on the ring determines which node is the coordinator (the first clockwise token position ≥ the hash). Replication factor (RF) determines how many nodes store each row: the coordinator plus the next RF-1 clockwise distinct physical nodes (skipping nodes already chosen, per the replication strategy). A read or write at QUORUM consistency requires RF/2+1 nodes to respond — ensuring that any quorum for a read overlaps with at least one node that received any prior quorum write, guaranteeing the latest write is always seen.

**Q11. What is Cassandra's `nodetool ring` output and what does it tell you about virtual node distribution?**
A: `nodetool ring` prints the full token ring — every token position, the node that owns it, and the arc (key range) each token is responsible for, with load percentage. A well-balanced ring shows each node appearing many times (equal to `num_tokens`) with small, roughly-equal arc lengths:

```
Address      Rack         Status State   Load    Owns      Token
10.0.0.1    rack1        Up     Normal  45.2GB  16.8%     -9223372036854775808
10.0.0.2    rack1        Up     Normal  46.1GB  17.1%     -9007199254740992
10.0.0.1    rack1        Up     Normal  45.2GB  16.8%     -8791026511324184
... (256 tokens per node = 1536 lines for 6 nodes)
```

Signs of poor distribution (worth flagging in an interview): one node consistently showing >25% load while others show <15% (high arc length variance — suggesting the random token placement was unlucky for that node, fixed by `nodetool rebalance`); all tokens for one node appearing in one region of the ring (clustering — suggests a poorly-distributed hash of that node ID, unlikely with Murmur3 but possible with weaker hash functions).

**Q12. What is Cassandra's replication strategy, and how does virtual node placement interact with it?**
A: Two main strategies:
- **SimpleStrategy**: replicas are placed on the next RF-1 clockwise physical nodes after the coordinator, regardless of rack or datacenter. Simple but rack-unaware — if RF=3 and three consecutive tokens belong to nodes all in the same rack, a rack failure takes down all replicas for those keys. Acceptable only for single-datacenter clusters without rack-awareness requirements.
- **NetworkTopologyStrategy**: replicas are placed by walking the ring clockwise and selecting nodes from different racks (and optionally different datacenters), skipping nodes already chosen or in an already-represented rack. Rack-aware by design. In multi-datacenter deployments, you specify a replica count per datacenter independently (e.g., RF=3 in us-east, RF=2 in eu-west).

Virtual nodes interact with replication strategies: with many virtual nodes, the RF nodes clockwise from any given token are very likely to be from different physical nodes (and with NetworkTopologyStrategy, from different racks) — the statistical independence of vnode positions across physical nodes makes replica diversity a natural outcome of high K, rather than requiring careful manual token assignment to ensure diversity.

**Q13. What is "token allocation" in Cassandra 4.0, and how does it change the operational meaning of `num_tokens`?**
A: Pre-Cassandra 4.0: `num_tokens` (default 256) are placed randomly, and high K is needed to achieve acceptable distribution (σ ≈ 1/sqrt(N×K)). Cassandra 4.0+ introduced an allocation algorithm that places tokens *optimally* — given the current ring state, it computes token positions for a new node that minimize variance, rather than sampling random positions and hoping for good luck. This allows K=16 (`num_tokens=16`) to achieve the same distribution quality as K=256 random placement — a 16× reduction in ring metadata. Operationally, this means: (1) the ring is 16× smaller and gossip is 16× cheaper for the same distribution quality; (2) data migration when adding/removing nodes involves 16 token ranges instead of 256, making it easier to track and faster to complete per-node; (3) `nodetool ring` output is much shorter and readable. The trade-off: the smarter placement algorithm only works when adding nodes sequentially (one at a time), not in parallel — and if nodes use different Cassandra versions with different allocation algorithms, ring state can be inconsistent.

**Q14. What is "vnodes and rack awareness" in Cassandra, and what is the common misconfiguration?**
A: With NetworkTopologyStrategy and vnodes, Cassandra walks the ring clockwise from a key's hash position, selecting one node per rack for the first RF replica placements. A common misconfiguration: fewer racks than RF replicas. If RF=3 and only 2 racks exist (`rack1`, `rack2`), Cassandra must place at least two replicas in the same rack to achieve RF=3 — violating rack-awareness semantics and making a single rack failure a potential data-unavailability event for some keys. The correct configuration: number of racks ≥ RF per datacenter, so Cassandra can always find RF distinct racks. In AWS: map each AZ to a rack in Cassandra config (`endpoint_snitch`), use at least 3 AZs when RF=3. Misconfiguring this is deceptively easy because Cassandra doesn't prevent under-racked configurations — it silently falls back to placing multiple replicas in the same rack, and you only discover the problem during an AZ failure.

**Q15. What is "repair" in Cassandra and why does it exist despite consistent hashing guarantees?**
A: Consistent hashing tells each node which keys it should own — but ownership ≠ guaranteed receipt of every write. During network partitions, node downtime, or hinted handoff delivery failures (covered in the consistent hashing guide), a node may miss writes it was supposed to receive. Repair is Cassandra's active anti-entropy process: it uses Merkle trees (one per token range) to efficiently compare data between replicas, identifies divergent keys, and transfers the canonical (most recent, per timestamp/vector clock) value to out-of-sync replicas. Without repair, missed writes accumulate silently — data that was supposed to be on a node simply isn't there, without any error being surfaced. This is why Cassandra operators must run `nodetool repair` on a regular schedule (typically once per `gc_grace_seconds`, the tombstone expiry window — usually 10 days). It's a maintenance requirement inherent to the eventual consistency model, not a sign of a bug — and it's an important operational detail that distinguishes managing Cassandra from managing a strongly-consistent database.

## Section 4: Distributed Databases — DynamoDB and Dynamo-Style Systems

**Q16. How does the original Dynamo paper's use of consistent hashing with virtual nodes differ from Cassandra's implementation?**
A: Both are directly derived from the Dynamo paper (2007), which first described the combination of consistent hashing with virtual nodes for distributed databases. Key implementation differences:

| Dimension | Dynamo (paper) | Cassandra (implementation) |
|---|---|---|
| Ring hash space | MD5 (128-bit) | Murmur3 (64-bit) |
| Virtual node placement | Random | Random (pre-4.0) / Optimal (4.0+) |
| Replication | "Preference list" (skip unhealthy nodes) | RF clockwise distinct physical nodes |
| Write consistency | Sloppy quorum (any N' available nodes) | Tunable (ONE/QUORUM/ALL per query) |
| Conflict resolution | Vector clocks + client-side merge | Last-write-wins (timestamp) |
| Coordinator role | Any node can be coordinator | Any node can be coordinator |

The sloppy quorum in Dynamo is notably different: writes go to any W available nodes from the preference list (even nodes not "naturally" responsible for that key range), with hinted handoff to return data to the natural owner when it recovers. Cassandra's model is stricter about which nodes are replicas but more flexible about per-query consistency levels.

**Q17. How does Amazon DynamoDB (the managed service) use consistent hashing internally, and what does this mean for customers?**
A: DynamoDB is a fully managed service — customers never see the internal ring topology. Internally, DynamoDB distributes data across many storage servers using consistent hashing on the partition key attribute of each item. From the customer's perspective, the relevant implications are: (1) **partition key cardinality determines distribution quality** — a low-cardinality partition key (e.g., a boolean field, a small set of statuses) causes most data to hash to a small number of positions, creating hot partitions regardless of how many storage nodes exist internally; (2) **hot partition throttling** — when a partition key's hash position receives more than its provisioned share of throughput, DynamoDB throttles requests to that partition (returning `ProvisionedThroughputExceededException`), even if other partitions have idle capacity. This is directly caused by consistent hashing assigning all traffic for one partition key to one (or a few replicated) server — no different from the hot-key problem in Cassandra or Memcached; (3) **adaptive capacity** (introduced in 2019) partially mitigates hot partitions by dynamically redistributing provisioned throughput to where actual traffic is concentrated, but doesn't eliminate the problem for extreme hot keys.

**Q18. What is the "write sharding" pattern for DynamoDB hot partitions, and how does it relate to virtual nodes?**
A: When a DynamoDB partition key is inherently hot (e.g., a status field with value `"active"` that most items have), write sharding artificially increases cardinality by appending a random suffix to the partition key: instead of `PK="active"`, write to `PK="active_1"`, `PK="active_2"`, ..., `PK="active_N"` — distributing writes across N virtual partition keys, each hashing to a different position on the internal ring. Reads must scatter-gather across all N shards. This is the same key-splitting technique described in the consistent hashing guide (Q27 of that guide) — but applied at the DynamoDB item level rather than at the ring level. The connection to virtual nodes: this is the application layer manually creating what virtual nodes achieve at the infrastructure layer — more hash positions per logical entity → more even distribution. When the infrastructure doesn't expose virtual node controls to you (as with DynamoDB), you simulate the effect at the data model layer.

**Q19. What is Apache HBase's approach to consistent hashing, and why does it differ from Cassandra?**
A: HBase uses **range-based partitioning** (regions) rather than hash-based consistent hashing. Each region owns a contiguous key range, and the region assignment to RegionServers is tracked by a centralized HMaster (and stored in a dedicated `-ROOT-` / `hbase:meta` table). This means: (1) range scans are efficient (all keys in a range are co-located on one region), unlike hash-based systems where a range scan requires scatter-gather across all nodes; (2) sequential key writes create "hotspotting" — all new writes go to the last region until it splits, causing write hotspots that consistent hashing avoids by design; (3) region splits (HBase's equivalent of adding virtual nodes) are automatic but can cause performance spikes during the split operation itself. The design choice reflects the same hash-vs-range partitioning trade-off described in the consistent hashing guide: HBase prioritizes range scan efficiency (good for analytics/OLAP workloads) at the cost of write hotspot risk; Cassandra prioritizes write distribution (good for OLTP/time-series) at the cost of inefficient range scans.

## Section 5: Replication and Consistency With Virtual Nodes

**Q20. How does replication factor interact with virtual node count in determining data durability?**
A: RF (replication factor) determines how many physical copies of each piece of data exist across the cluster. Virtual node count K determines how evenly the ring is divided. These are independent dimensions — you can have high K with RF=1 (well-distributed, zero redundancy) or low K with RF=3 (redundant, potentially uneven distribution). The correct production design sets them independently based on distinct requirements: K is chosen to achieve acceptable load distribution (using the σ ≈ 1/sqrt(N×K) formula from the virtual nodes guide); RF is chosen to achieve the desired durability and availability (RF=3 can survive 1 node failure while maintaining QUORUM reads/writes; RF=5 can survive 2 failures, etc.). A common interview mistake is confusing K and RF — they are orthogonal parameters with different purposes.

**Q21. What is a "partial failure during replica placement" with virtual nodes, and how does Cassandra handle it?**
A: When a write arrives, Cassandra attempts to write to all RF replicas. If one replica node is temporarily unreachable, Cassandra uses **hinted handoff**: the coordinator stores the write locally with a "hint" (the write's intended target node). When the target node recovers (detected via gossip), the coordinator delivers the queued hints to it. With virtual nodes, the set of nodes holding hints for a given partition is the same set of RF nodes that should own that key's replica — the virtual node ring determines which nodes those are, and hinted handoff is just the delivery mechanism for when those nodes are temporarily absent. The consistency implication: a write acknowledged at QUORUM despite one replica being down is only immediately consistent at RF/2+1 nodes; the hint-receiving node is eventually consistent (will receive the write when it comes back). If the coordinator fails before delivering the hint, the write may be permanently lost on the target node — why repair (Q15) is necessary as an independent consistency mechanism.

**Q22. How does "quorum" consistency interact with virtual nodes and ring topology?**
A: Quorum (RF/2+1 nodes must acknowledge a write and must respond on a read) works at the physical node level, not the virtual node level — each physical node is counted once regardless of how many virtual positions it holds. Virtual nodes affect which physical nodes are in a key's replica set (by determining the RF clockwise physical nodes from the key's ring position), but the quorum arithmetic is purely over physical nodes. The key quorum property: any read quorum and any write quorum for the same key will always share at least one common physical node, guaranteeing that a read-after-write at QUORUM always finds the latest write — this property holds regardless of K, as long as the same RF physical nodes are consistently chosen as replicas for a given key (which the ring guarantees deterministically).

**Q23. What is "replica placement skew" in a virtual-node-based database, and how does it differ from "load skew"?**
A: Load skew (uneven traffic) was the primary problem virtual nodes solve (covered in the virtual nodes guide). Replica placement skew is a subtler, distinct issue: even with perfectly even traffic distribution, the actual physical nodes that serve as replicas for any given key range depend on which physical nodes are adjacent on the ring. If two nodes happen to have many virtual positions adjacent to each other (near-neighbors on many arcs), those two nodes will frequently be co-replicas — meaning their failure combination is disproportionately dangerous (losing both removes more keys from RF than losing two randomly-chosen nodes would). With high K, this is statistically unlikely but not impossible. Zone-aware placement (Q16 of the virtual nodes guide) mitigates the worst version: by ensuring physically-proximate nodes are in the same AZ, and using NetworkTopologyStrategy to enforce AZ diversity in replica selection, you prevent any single AZ failure from losing all replicas for any key range — regardless of how the virtual node positions happen to be distributed.

## Section 6: Operational Concerns

**Q24. What is the operational process for adding a node to a Cassandra cluster with virtual nodes, step by step?**
A:
1. **Provision the new node** with the same Cassandra version, the same `cluster_name`, and `num_tokens` set to the cluster-standard K value. Set `auto_bootstrap: true` (default).
2. **Start Cassandra** on the new node. It contacts a seed node (configured in `cassandra.yaml`) to discover the ring.
3. **Token generation**: with Cassandra 4.0+'s optimal allocator, the cluster computes K token positions for the new node that minimize distribution variance given the current ring; with older versions, K random positions are generated.
4. **Streaming**: for each of the K token ranges the new node will own, the previous clockwise owner streams the relevant SSTables to the new node. These K streaming sessions run concurrently, distributing source load across (up to) K different existing nodes.
5. **Gossip propagation**: the new node's token positions and "UP" status propagate to all cluster members via gossip. Clients and cluster nodes begin routing appropriate keys to the new node.
6. **Cleanup**: once bootstrapping is complete, run `nodetool cleanup` on each node that donated ranges — this removes data those nodes no longer own (previously they held it until the new node confirmed successful bootstrap; cleanup discards the now-redundant copies).
7. **Verify**: `nodetool status` shows the new node as `UN` (Up, Normal); `nodetool ring` shows its K token positions; per-node load metrics should reflect re-balanced traffic.

**Q25. What is the "bootstrap storm" in Cassandra and how does it affect database operations during the process?**
A: A bootstrap storm occurs when multiple new nodes join simultaneously, each triggering streaming sessions, causing aggregate streaming I/O and network bandwidth to exceed what the cluster can sustain alongside serving normal client traffic. With K=256 per node and N_new nodes joining simultaneously, the cluster may initiate thousands of concurrent streaming sessions, saturating disk I/O on nodes donating data and network bandwidth on both donors and recipients. Mitigations: add nodes sequentially (wait for each node to fully bootstrap and for `nodetool cleanup` to run before adding the next); throttle streaming bandwidth via `stream_throughput_outbound_megabits_per_sec` and `inter_dc_stream_throughput_outbound_megabits_per_sec` in `cassandra.yaml`; schedule bootstraps during low-traffic periods; use Cassandra 4.0+'s smaller K=16 (fewer streaming sessions per node add — 16 instead of 256, a 16× reduction in concurrency). Some teams pre-provision cluster capacity in advance (adding nodes before they're needed) to avoid emergency bootstraps during traffic spikes.

**Q26. How do you safely decommission a Cassandra node without data loss?**
A: Run `nodetool decommission` on the node to be removed. This:
1. Marks the node as `LEAVING` in gossip, stopping new client routing to it.
2. Streams this node's token ranges to the next clockwise RF owners that don't already hold replicas (since the leaving node's data will no longer be covered by the leaving node's own RF contribution).
3. Once all streaming is confirmed complete, removes the node's tokens from the ring and marks the node as `LEFT`.
4. Other nodes can then `nodetool cleanup` to remove any data they were temporarily holding as a streaming destination.

Safe decommission requires that the remaining cluster can still maintain RF replicas for all token ranges after the node leaves — if removing the node would bring a rack below RF replicas (the under-racked misconfiguration from Q14), decommission will fail or produce warnings. Never `nodetool removenode` (which removes a node without data streaming) unless the node is already dead and data loss is acceptable or covered by remaining replicas.

**Q27. What is "incremental repair" in Cassandra and why is it preferred over full repair?**
A: Full repair re-Merkle-trees the entire dataset on all RF replicas for every token range — accurate but expensive, especially as data volumes grow. Incremental repair (introduced in Cassandra 3.0, improved in 4.0) tracks which SSTables have been repaired before (via `REPAIRED_AT` metadata timestamp) and only processes SSTables written since the last repair — dramatically reducing the data volume each repair run must process. With virtual nodes and K=256, each node owns many small token ranges, each of which must be repaired — full repair on a 256-vnode cluster means 256 Merkle tree computations per node per repair cycle, which is expensive. Incremental repair reduces this cost proportionally to the fraction of data that's changed since the last repair, making regular repair cycles practical even on large clusters. Most production Cassandra operations use scheduled incremental repairs (often daily) rather than full repairs (reserved for bootstrapping new nodes or after major incidents).

## Section 7: Cross-Cutting Performance Concerns

**Q28. What is a "hot partition" in the context of virtual nodes, and why can't you solve it purely by adding more virtual nodes?**
A: A hot partition occurs when a small number of keys (or even a single key) receives far more requests than average — many orders of magnitude more, in extreme cases (celebrity users, viral content, a trending product). Consistent hashing with virtual nodes distributes keys uniformly across nodes, but "uniform distribution of keys" ≠ "uniform distribution of traffic" when some keys are many times more popular than others. The hot key still maps to exactly one set of RF nodes (or one node in a cache) regardless of K — adding more virtual nodes distributes the *other* keys more evenly, but does nothing for a key that's already on its own node receiving 100× average traffic. The fixes for hot keys are not ring-level but data-model-level:
- **Read replicas/caching at the application layer**: cache the hot key in a local in-process cache on every application server, absorbing reads before they hit the distributed cache/database.
- **Key splitting**: shard the hot key into N sub-keys (for a cache) or add a shard suffix to the partition key (for DynamoDB, as in Q18) — distributing its traffic across N nodes at the cost of scatter-gather on reads.
- **Dedicated hot-key detection and promotion**: some cache systems (e.g., Facebook's Memcache at scale) dynamically detect keys above a traffic threshold and replicate them to more nodes, serving reads from whichever replica is nearest.

**Q29. How does consistent hashing with virtual nodes affect read/write latency in a distributed database?**
A: Virtual nodes directly affect latency in two ways:
- **Positive effect**: with RF>1 and NetworkTopologyStrategy, the RF replica nodes for any given key are chosen by the ring — with high K and good physical diversity, those replicas are likely to be in different AZs. A read at QUORUM can be served from the nearest (lowest-latency) of the RF/2+1 AZ-distributed replicas. This is "speculative execution" (Cassandra's `read_repair_chance` and speculative retry settings) — the coordinator can speculatively send the read to additional replicas if the first response is slow, taking the first response that arrives.
- **Negative effect (small)**: the O(log(N×K)) binary search on the ring at routing time adds nanoseconds per request — negligible for database operations that take milliseconds, but worth being aware of as a theoretical overhead.

The dominant latency factor in a virtual-node-based database is not the ring lookup but the network hop to the coordinator + the coordinator-to-replica hops for RF-1 additional copies. Virtual nodes affect which physical machines are chosen for those hops (via the ring structure) but don't add meaningful latency to the hops themselves.

**Q30. What is "speculative retry" in Cassandra and how does it interact with virtual node replica selection?**
A: Speculative retry is a Cassandra feature where, if a replica doesn't respond within a configured percentile threshold (e.g., 99th percentile of observed response times), the coordinator speculatively sends the read to an additional replica — taking whichever response arrives first and using it, ignoring the later response. This hedges against slow replicas (due to GC pauses, disk I/O, CPU contention) without waiting for a full timeout. Its interaction with virtual nodes: the effectiveness of speculative retry depends on having alternative replicas that are fast — if all RF replicas for a given key happen to be in the same AZ (poor zone diversity due to poor virtual node distribution or misconfigured NetworkTopologyStrategy), a speculative retry to "another replica" hits a server in the same fault domain, with potentially correlated slowness. With well-configured virtual nodes and zone-aware replica placement, the alternative replicas are in different AZs, making speculative retry genuinely effective at reducing tail latency.

## Section 8: Scenario-Based Questions

**Q31. "Your 6-node Cassandra cluster (RF=3, NetworkTopologyStrategy, 2 AZs with 3 nodes each) starts showing uneven load — one node handles 28% of reads while others handle ~14%. Describe how you'd investigate and remediate."**
A: Step 1 — identify the type of imbalance:
- Run `nodetool tablestats` and `nodetool tpstats` to distinguish whether it's data-skew (one node owns more data) or traffic-skew (one node handles more requests despite similar data volume, suggesting a hot key problem).
- Run `nodetool ring` to check this node's actual token ownership percentage — if it genuinely owns 28% of token ranges (not 16.7%), the ring is unbalanced.

Step 2 — if ring imbalance (structural):
- Cassandra 4.0+: run `nodetool rebalance` — the smarter token allocator re-assigns tokens to equalize load.
- Older Cassandra: manually identify and move tokens using `nodetool move` to shift specific token boundaries from the overloaded node to adjacent underloaded nodes.

Step 3 — if hot key (access pattern):
- Enable key access logging or use a monitoring tool to identify which specific partition keys are receiving the most traffic.
- For read-heavy hot keys: enable row cache for that table in Cassandra, add an application-layer in-process cache, or use the key-splitting strategy described in Q28.
- For write-heavy hot keys: evaluate schema redesign to spread writes across more partition keys.

Step 4 — check AZ distribution:
- With only 2 AZs and RF=3, at least one AZ must host 2 replicas per key. Ensure this is intentional and that the high-load node isn't in the AZ that holds 2 replicas for most keys (a coincidence of ring topology that could be fixed by adding a 3rd AZ or accepting the current topology as a known tradeoff).

**Q32. "You're designing a distributed cache for a video streaming platform. The catalog has 50 million video IDs, but 0.1% of videos (50,000 'trending' videos) receive 80% of all playback requests. How would you architect the caching layer?"**
A: A two-tier caching strategy to handle both the hot-key problem and the long-tail:

Tier 1 — Local in-process cache on each application server (e.g., Caffeine/Guava cache, 1-5GB per server): cache metadata for the top trending videos. With consistent hashing in the distributed cache, a trending video maps to 1-3 cache nodes; adding local caching replicates it to every application server, absorbing reads before they hit the distributed cache. TTL: short (30-60 seconds) to ensure fresh trending data without stale-serving risk. Detection: a real-time trending-video tracker (sliding window access counter per video) promotes videos into the local tier automatically when they cross a request-rate threshold.

Tier 2 — Distributed Memcached cluster (e.g., 20 nodes with Ketama K=160): standard consistent hash routing for all 50 million video IDs. Handles the long tail (99.9% of videos — not trending, but still need cache). With 20 nodes and K=160, distribution is excellent (σ ≈ 1/sqrt(20×160) ≈ 1.8%).

Hot-key detection boundary: any video exceeding ~1000 requests/minute (configurable) gets promoted to Tier 1. At 50,000 trending videos × all application servers (e.g., 100 servers), the local cache per server holds 50,000 × ~2KB metadata ≈ 100MB — trivially within the 1-5GB budget.

On topology change (Memcached node failure): Tier 2 remaps ~1/20 = 5% of all 50M videos, causing brief cache misses for 2.5M videos — a 5% miss increase, manageable. Trending videos (Tier 1) are unaffected — they're in local cache everywhere.

**Q33. "A startup is choosing between Cassandra and a Redis Cluster for a session storage system (100M sessions, ~50k reads/sec, ~10k writes/sec, 10-node cluster). Walk through the consistent-hashing/partitioning implications of each choice."**
A: **Cassandra (consistent hashing with virtual nodes):**
- With K=256 and RF=3, each of 10 nodes handles ~10% of session keys but stores 30% of data (RF=3 means 3 copies). Writes go to all 3 RF replicas; reads at ONE consistency hit the fastest replica.
- Session expiry: TTLs are natively supported per-row. Expired sessions are cleaned up by Cassandra's compaction process.
- Topology changes: adding nodes is smooth — K=256 means 256 small streaming sessions from existing nodes, distributing migration load across the cluster.
- Concern: sessions are typically written once and read many times — Cassandra's write path (coordinator + 3 replicas) has higher write latency (~3-5ms) than Redis, and its eventual consistency model means `ONE` reads may see slightly stale session data in edge cases.

**Redis Cluster (hash-slot partitioning):**
- 16,384 slots distributed across 10 masters (each owning ~1,638 slots). With replicas (1 per master = 20 nodes total), each slot has 2 copies.
- Session expiry: Redis TTLs are lightweight and deterministic (key-level TTL, evicted precisely when expired). Much simpler than Cassandra's compaction-based cleanup.
- Topology changes: adding a node requires explicit slot migration (redis-cli `--cluster rebalance`), more operational than Cassandra's automatic vnode bootstrap.
- Hash tags (Q8): if session data is split across multiple keys per session (e.g., session metadata + session values), hash tags are required to co-locate them on the same slot, complicating key naming.

**Recommendation**: Redis Cluster for session storage — lower read/write latency, native TTL precision, simpler session-expiry semantics. Cassandra shines for session workloads only if you need multi-datacenter geo-distribution of sessions with NetworkTopologyStrategy replication, or session data volumes that exceed Redis's memory cost (Cassandra stores to disk). The consistent hashing vs hash-slot distinction matters less than the operational and latency characteristics for this use case.
