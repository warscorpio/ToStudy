# Client-Side vs Server-Side Service Discovery — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the core distinction between client-side and server-side service discovery?**
A: The distinction is about *where* the work of querying the service registry, receiving the current instance list, and selecting a specific backend instance to call actually happens. In **client-side discovery**, that work is done by the calling service itself — the caller embeds a discovery-aware client library, queries the registry directly, receives the list of available instances, applies a load-balancing algorithm to select one, and connects to the chosen instance directly. In **server-side discovery**, the calling service makes a request to a well-known stable intermediary (a load balancer, a gateway, or a sidecar proxy), and *that intermediary* performs the registry query and instance selection on the caller's behalf — the calling service never interacts with the registry at all, and may not even know that multiple backend instances exist.

**Q2. What does each model require of the calling service, concretely?**
A: Client-side discovery requires the calling service to: embed a language/runtime-specific discovery client library that knows how to talk to the specific registry in use; implement or configure a load-balancing algorithm within that library to select among the returned instances; handle the case where the registry returns an empty or stale list; and manage the registry client's own configuration (registry address, auth, refresh intervals). The calling service is actively and explicitly participating in the discovery process. Server-side discovery requires almost none of this from the calling service — it just makes a network call to a stable, pre-known address (a ClusterIP, a proxy port, a gateway hostname) using completely ordinary networking primitives, with no registry awareness, no embedded library, and no selection logic of its own. The stable address is, from the caller's perspective, indistinguishable from calling a single fixed endpoint.

**Q3. Why does the choice between these two models matter more than it might initially seem?**
A: The choice has cascading implications for coupling, operational complexity, polyglot support, failure modes, and organizational ownership of cross-cutting concerns — it's not just a technical routing detail but an architectural decision about where intelligence lives in the system. Client-side discovery embeds routing intelligence into every calling service; server-side discovery centralizes it in shared infrastructure. That centralization vs. embedding trade-off shapes how difficult it is to update routing logic, how many languages the system can realistically support with consistent behavior, and which team is responsible when something goes wrong with how a service is being reached.

## Section 2: Client-Side Discovery — In Depth

**Q4. How does client-side discovery work mechanically, step by step?**
A: On startup (or periodically, or per-request depending on the implementation), the calling service's embedded discovery client queries the registry (e.g., Consul's HTTP API, a Eureka server, an etcd cluster) for the list of currently healthy instances of the target service. The client typically caches this list locally with some refresh interval (per the TTL/caching trade-offs discussed in the service discovery guide) rather than querying the registry on every single outbound call. When the application code makes a call to a downstream service, the discovery client intercepts, selects a specific instance from its cached list using a configured load-balancing algorithm (round robin, least connections, random, etc.), and the actual network connection goes directly from the calling process to the chosen instance's IP and port — no intermediary, no proxy, no extra network hop.

**Q5. What are the most well-known implementations of client-side service discovery, and what context did they emerge from?**
A: Netflix Ribbon (paired with Netflix Eureka as the registry) was the canonical client-side discovery implementation in the Java/Spring microservices ecosystem — the Netflix OSS stack brought this pattern into wide use around 2012–2015 when the industry was first decomposing into microservices at scale, and Spring Cloud integrated these components into a cohesive framework that many teams adopted. gRPC's name resolution and load-balancing architecture also follows a client-side model, with the gRPC client library responsible for resolving a service name to a set of endpoints and applying load balancing across them (the gRPC-specific headless-Service-based discovery in Kubernetes is exactly this). Consul's client SDK and client-side SDKs for most dedicated registry systems also generally follow the client-side model.

**Q6. What does the client-side model's load-balancing capability look like compared to a server-side intermediary?**
A: A sophisticated client-side load-balancing implementation (like gRPC's or a well-configured Ribbon setup) can be quite capable — supporting multiple algorithms, instance-specific health signals, and even zone/latency-awareness within the client's local decision logic. However, the client's view is inherently limited to what the registry last reported: it has no real-time, connection-level visibility into how loaded each backend instance currently is (how many in-flight requests it's handling right now) the way a co-located proxy or a purpose-built load balancer can observe — a client-side load balancer making a round-robin decision today can't know that one of the registered instances has been slow for the last 10 seconds because it has a full request queue, unless that state is explicitly exposed through the registry or through an explicit health signal the instance publishes.

**Q7. What are the strengths of client-side discovery?**
A: **Direct connections**: requests go directly from caller to chosen instance, with no additional network hop through a proxy or intermediary — minimizing added latency and eliminating the intermediary as a component that can fail or become a bottleneck. **Caller control**: the calling service has full visibility into which specific instance it's connecting to and can implement sophisticated, application-aware selection logic (preferring instances in the same availability zone, weighting by observed response time, explicitly routing to a specific instance for a stateful protocol). **No shared-intermediary bottleneck**: load and routing are distributed across every calling instance rather than concentrated through a shared proxy that becomes a scaling constraint.

**Q8. What are the weaknesses of client-side discovery?**
A: **Library coupling**: every service must embed a registry-specific client library, coupling all services to the registry's protocol and API — changing the registry system (e.g., migrating from Eureka to Consul) requires updating every service that calls any other service, which in a large polyglot system is a massive, coordinated migration. **Polyglot complexity**: the client library must exist, be maintained, and be correctly implemented for every language/runtime used in the system; a team adopting a new language must implement or find a compatible discovery client before they can call any other service. **Duplicated cross-cutting logic**: discovery, load balancing, retry, timeout, and circuit-breaking logic is each independently implemented (and potentially inconsistently) across every service's embedded library — a bug in the library is a bug in every service using it. **Discovery logic in application process**: a misconfigured or buggy embedded discovery client can affect the calling service's own stability, mixing infrastructure concerns into the application process.

## Section 3: Server-Side Discovery — In Depth

**Q9. How does server-side discovery work mechanically?**
A: The calling service addresses its dependency via a stable, fixed address — a hostname or IP that never changes from the caller's perspective regardless of how many backend instances exist or how frequently they change. That stable address is owned by an intermediary (a load balancer, an API Gateway, a Kubernetes kube-proxy ClusterIP, or a sidecar proxy) which handles all the discovery work: maintaining awareness of currently healthy backend instances (by querying the registry or watching the orchestrator's API), selecting a specific instance for each forwarded request using its own load-balancing algorithm, and forwarding the request there. The calling service's code contains no registry logic, no instance list, no selection algorithm — it just calls the stable address as if it were a single server.

**Q10. What are the main forms an intermediary takes in server-side discovery, and how does each differ?**
A: **Kubernetes Service / kube-proxy**: the ClusterIP of a Kubernetes Service is the stable address; kube-proxy implements round-robin or IPVS-based load balancing across the Endpoints (the set of healthy ready pods), updated dynamically by the endpoint controller. Simple, zero-configuration for the calling service, but with limited load-balancing algorithm options natively. **API Gateway**: an externally-facing or internal gateway handles discovery and routing as described in the API Gateway: request routing guide — querying a registry or the Kubernetes API to dynamically populate backend pools per route. **Service mesh sidecar proxy** (Envoy/Linkerd proxy): a per-instance sidecar running alongside every service instance, intercepting outbound calls transparently via iptables rules, receiving continuously-updated endpoint information from the mesh control plane (via xDS), and applying sophisticated load balancing (including L7-aware algorithms, outlier detection, retries) without the calling application's knowledge. The sidecar is the most sophisticated form — transparent to the application while providing richer capability than a simpler L4 load balancer, and without the remote-hop cost of a centralized load balancer since the proxy is co-located on the same node.

**Q11. What are the strengths of server-side discovery?**
A: **Zero library dependency for callers**: calling services use completely ordinary networking, with no registry SDK or discovery logic embedded — a completely new service in any language can call any other service without any special setup beyond knowing the stable address. **Centralized, updatable routing logic**: load balancing, retries, circuit breaking, and routing policy all live in the intermediary, which can be updated, reconfigured, or replaced independently of any calling service — updating routing behavior across the entire system requires changing the intermediary, not redeploying every caller. **Consistent behavior regardless of language**: all traffic flows through the same intermediary implementation, so every service — whether written in Go, Python, Java, or Rust — gets identical discovery and load-balancing behavior without requiring per-language library parity. **Application isolation**: the calling service's application code and process are genuinely free of infrastructure concerns — a discovery failure is an infrastructure-layer failure, not a failure of the application code.

**Q12. What are the weaknesses of server-side discovery?**
A: **Additional network hop** (for non-sidecar intermediaries): traffic routed through a centralized load balancer or API Gateway crosses an additional network segment, adding latency; though typically small (sub-millisecond for local proxies), it's non-zero and can accumulate in deeply nested service call chains. **Intermediary as bottleneck and failure point**: a centralized load balancer or gateway concentrates all service-to-service traffic through one component — if it becomes overloaded or fails, it can impact all traffic, even between services that are otherwise completely healthy (the same single-point-of-failure concern discussed in the API Gateway guide, mitigated by running the intermediary redundantly). **Reduced caller visibility**: the calling service typically doesn't know which specific backend instance handled a given request (the routing decision is opaque to it), which can complicate debugging in cases where behavior is instance-specific.

## Section 4: Trade-Off Analysis Across Specific Dimensions

**Q13. How do the two models compare on polyglot system support?**
A: This is one of the starkest practical differentiators: server-side discovery is inherently language-agnostic — the calling service just makes a TCP/HTTP/gRPC call to a stable address, which is something every language does identically. Client-side discovery requires a correct, maintained, registry-protocol-compatible client library for every language in use. In a genuinely polyglot organization (Go services calling Python services calling Node.js services, with Rust and JVM services also in the mix), maintaining per-language client libraries with consistent behavior and equivalent feature sets is a real, ongoing engineering burden — and the moment a team starts a service in a language without a supported library, they're either blocked or must implement their own, risking inconsistency. Server-side discovery eliminates this problem entirely by moving the per-language concern down into the network layer, which every language already handles uniformly.

**Q14. How do the two models compare on load-balancing algorithm richness and flexibility?**
A: Client-side implementations of sophisticated algorithms (latency-aware, consistent hashing for cache affinity, zone-aware) are fully possible and do exist in some ecosystems — gRPC's client-side load balancing is notably capable. However, keeping algorithm logic consistent *across* all client library implementations in a polyglot system is difficult; different versions of libraries in different languages or at different update levels may implement algorithms differently. Server-side intermediaries (especially sidecar proxies like Envoy) offer very rich, actively-maintained algorithm libraries (round robin, least-request, ring hash, Maglev, random, etc.) available to all traffic uniformly regardless of what language or version the caller is written in — updating the proxy's algorithm configuration takes effect for all callers simultaneously, without any code change or redeployment of calling services.

**Q15. How do the two models compare on failure isolation?**
A: In client-side discovery, a bug in the embedded client library can crash or corrupt the calling service's own process — the library's failure is the application's failure, since they run in the same process. In server-side discovery via a sidecar, the proxy's failure is isolated to the sidecar process, which is separate from the application container — a crashing sidecar can be restarted without restarting the application, and a bug in the proxy doesn't corrupt application-level state. For centralized server-side intermediaries (a shared load balancer or gateway), a failure affects all traffic through that intermediary simultaneously — a wider blast radius than a per-instance client library failure, but one that's operated and monitored by an infrastructure team rather than buried inside each individual application.

**Q16. How do the two models compare on observability?**
A: Client-side discovery, because the calling service is the one doing the selection and connecting, gives the calling service direct visibility into which specific instance it chose and what happened — it can log or instrument at the exact point of selection and connection. However, this observability lives inside each calling service independently, making it hard to get a unified, cross-service view of routing behavior. Server-side discovery, because the intermediary sees all traffic, can provide centralized, consistent observability across all service-to-service calls in one place — a service mesh's control plane, for example, can produce uniform metrics and traces for every RPC in the system, regardless of what the applications themselves instrument, which is a major operational advantage in systems where not every team maintains disciplined application-level observability.

## Section 5: The Role of Load Balancing in Each Model

**Q17. In client-side discovery, how is load balancing typically implemented and where does it live?**
A: Load balancing logic is embedded within the discovery client library itself — the same component that queries the registry and caches the instance list also implements the algorithm for selecting among instances. This means load balancing is distributed: each instance of each calling service runs its own independent load balancer, making selection decisions independently based on its own locally-cached instance list. The behavior across many callers is statistically coherent (if they all use round robin on the same instance set, aggregate traffic is distributed roughly evenly) but not coordinated — no single component has a global, coordinated view of load distribution.

**Q18. In server-side discovery, how is load balancing typically implemented, and what additional capabilities does co-location in a proxy enable?**
A: Load balancing is implemented in the intermediary — whether a centralized L4/L7 load balancer, an API Gateway, or a sidecar proxy. A sidecar proxy specifically can do something a client-side library or remote load balancer cannot as easily: observe the *actual* number of in-flight requests to each upstream instance from this specific caller, in real time, enabling **least-outstanding-requests** (also called least-connections at L7) load balancing — routing each new request to whichever backend instance currently has the fewest requests actively in flight from this proxy's perspective. This is particularly valuable for services with variable response times, where round-robin or random selection can cause some backends to accumulate a backlog while others are idle, because the algorithm adapts to observed load rather than assuming each request takes an identical amount of time.

## Section 6: Service Mesh as the Modern Server-Side Evolution

**Q19. Why has the service mesh sidecar model become the dominant modern approach to server-side discovery, over centralized load balancers?**
A: The sidecar model resolves the main historical weakness of server-side discovery — the additional network hop — by making the intermediary *co-located* with each service instance, on the same node, intercepting traffic before it even leaves the local host. The extra "hop" is now just a loopback call within the same machine, adding microseconds rather than the network round-trip a centralized remote load balancer would add. This gives server-side discovery the latency characteristics of client-side (essentially direct connections, or very close to it) while retaining all the operational benefits of server-side (centralized, updateable routing logic; language-agnostic; no embedded library). Combined with the control plane's push-based distribution of endpoint updates (rather than TTL-based polling), sidecar-based discovery also has better propagation speed than DNS-based or polling-based client-side implementations.

**Q20. In a service mesh, what specifically does the sidecar handle on behalf of the calling application?**
A: All of the following, entirely transparently to the application code: resolving the target service name to a set of current, healthy endpoints (via endpoint information pushed from the control plane); selecting a specific endpoint using a configured load-balancing algorithm (often least-outstanding-requests); establishing the outbound connection with mTLS for service identity authentication; applying retry and timeout policies; recording per-request metrics and trace spans; and implementing circuit breaking and outlier detection (automatically removing endpoints generating errors from active rotation). From the application's perspective, it made a call to `orders-service:8080` and received a response — the entire complexity above is handled between the app's kernel socket and the remote endpoint, without the app being aware of or responsible for any of it.

**Q21. Does using a service mesh mean client-side discovery is never appropriate?**
A: No — even in mesh environments, there are cases where client-side selection logic is appropriate. The most notable: stateful protocols requiring per-instance addressability (connecting to a specific Cassandra node for a token-range-aware request, or to a specific Kafka broker for a specific partition) require the client to know *which* specific instance to target, not just *any* healthy instance — something a transparent sidecar's opaque load balancing can't determine without explicit application-layer routing hints. In these cases, the application (or a framework-level client) must be involved in the selection decision, and client-side-style selection logic is inherent to the use case. The mesh may still handle the mTLS, metrics, and retry layers; the instance-selection decision itself flows from application logic.

## Section 7: Failure Modes and Edge Cases

**Q22. How does each model behave when the service registry itself becomes unavailable?**
A: Client-side discovery's local instance-list cache provides a natural short-term buffer against registry outages — the calling service continues using its locally-cached list (albeit potentially stale) for as long as that cache remains valid, without any impact to live traffic. Once the cache expires and the registry is still unavailable, the client has no fresh list and must either fail calls (if configured strictly) or keep serving from the expired cache (if configured permissively). Server-side discovery's intermediary faces the same trade-off but at the proxy level — Envoy-based sidecars, for instance, continue using their last-known endpoint set when the control plane is unreachable, rather than immediately failing all traffic, specifically because serving slightly stale routing state is far better than failing all requests during a control-plane outage.

**Q23. How does each model handle an instance that has become unhealthy but hasn't yet been removed from the registry?**
A: In client-side discovery, the embedded client receives the still-present (stale) instance from the registry, includes it in its locally-cached list, and selects it by the load-balancing algorithm — the caller discovers the unhealthy instance through actual connection failures or error responses, which the client library should (if properly implemented) use to temporarily penalize or remove that instance from future selections until the registry catches up. In server-side discovery via a sophisticated proxy, **outlier detection** (a form of passive health checking) continuously monitors the error rates and response latency of each endpoint and automatically ejects endpoints exceeding configured error thresholds from the active rotation — even before the registry itself has been updated to reflect the failure — providing faster adaptation to unhealthy backends than waiting for the registry's own health-check cycle to detect and remove them.

**Q24. What is the "thundering herd" risk specific to client-side discovery's registry polling model, and how is it mitigated?**
A: If many service instances all cache their instance lists with the same TTL and all start up at approximately the same time (e.g., during a large deployment), they will all attempt to refresh their registry cache at approximately the same moment — a synchronized wave of registry queries that can overwhelm the registry precisely when it's most likely to be under load from the deployment event itself. Mitigated by **jittered TTL refresh**: each client adds a random jitter to its refresh interval (rather than all refreshing at exactly TTL seconds after their synchronized start time), spreading the refresh wave over time rather than concentrating it into a synchronized burst — the same jitter principle discussed for client retry behavior in the rate-limiting guide, applied here to the polling cadence.

## Section 8: Choosing Between the Models

**Q25. What factors most strongly favor client-side discovery in a given system?**
A: The use case requires direct instance addressability (stateful protocols, per-instance routing — Q21); the system has low language diversity (one or two primary languages with well-maintained, widely-used client libraries); latency is highly constrained and even a same-host proxy hop is unacceptable; the team has the expertise to correctly implement and maintain the embedded library logic (health-penalization, retry, circuit breaking) consistently; or the team is specifically working within an ecosystem where client-side discovery is the established, well-supported convention (gRPC's model, Spring Cloud's ecosystem).

**Q26. What factors most strongly favor server-side discovery?**
A: The system is polyglot or expected to add new languages over time; the organization wants to centralize cross-cutting concerns (load balancing, retries, observability) as policy rather than per-service implementation; the team is running Kubernetes and already has service-mesh or Ingress infrastructure available (the server-side intermediary is essentially free at that point — it's already there); the organization wants to update routing behavior without redeploying calling services; or there's a strong preference to keep application code free of infrastructure dependencies. These factors describe most modern cloud-native systems, which is why server-side discovery — particularly via service meshes — has become the default recommendation in new greenfield microservices architectures.

**Q27. How do you evaluate the two models for a system that's currently using neither and is experiencing intermittent "service not found" failures?**
A: Before choosing a model, determine the root cause of the failures — are they caused by an absence of discovery entirely (services using hardcoded IPs that go stale), or by an existing discovery mechanism that's propagating stale data too slowly? If the root cause is hardcoded configuration, *either* model improves the situation significantly, and the choice can be based on the longer-term architectural factors (Q25–26). If the root cause is stale data in an existing registry, understand whether the staleness is from slow registry health-check detection or from slow propagation to callers — client-side local cache staling vs. server-side intermediary staling have different remediation paths (health-check interval tuning vs. reducing polling TTL or moving to push-based propagation). The common mistake is choosing a model based on what's easiest to implement immediately rather than what fits the system's long-term trajectory — especially since migrating from client-side to server-side (or vice versa) after building significant investment in one model is a significant undertaking.

## Section 9: Scenario-Based Questions

**Q28. "Your team runs a gRPC-based microservices system where each service embeds the gRPC client library for client-side load balancing and discovery. A new team wants to write a service in Python. They ask why the Python gRPC library's load balancing behavior seems to differ from the Java library's. How do you explain this, and what's the architectural implication?"**
A: This is the per-language client library divergence problem (Q8, Q13) made concrete — the Java and Python gRPC client libraries are independent implementations that may implement the same *intended* behavior differently, have different bugs, support different subsets of load-balancing algorithms, or be at different maintenance stages with different update cadences. The architectural implication: the system's routing behavior is now inconsistent across languages, and fixing it in one language's library doesn't automatically fix it in others. This is a canonical signal that client-side discovery may be reaching its polyglot scaling limit for this organization — if routing correctness and consistency across all languages matters, moving toward a server-side model (a sidecar proxy that applies consistent routing regardless of what language the calling service is written in) eliminates this class of inconsistency by removing per-language library parity from the equation entirely.

**Q29. "A team proposes adopting a service mesh to handle discovery and load balancing. A skeptical engineer argues that 'adding a sidecar to every pod just for routing is wasteful overhead.' How do you evaluate this concern?"**
A: Acknowledge that the sidecar does add real resource overhead — each sidecar proxy consumes memory and CPU, and at a large number of pods, this overhead aggregates to something non-trivial. However, evaluate what the sidecar is providing in return: transparent discovery, L7 load balancing (including least-outstanding-requests, which is materially better for variable-latency services), mTLS for service identity, automatic retry and circuit breaking, and uniform per-RPC observability — all without any application code change, in any language, and updateable independently of the application. Then compare that to the alternative: achieving the same capabilities via client-side libraries requires per-language library maintenance, duplicated implementation of each of these concerns in every service, and the risk of inconsistency and bugs spread across every service's codebase. The sidecar's overhead is real but finite; the alternative's overhead is also real but distributed, harder to measure, and scales with the number of services and languages rather than remaining fixed. The argument isn't that sidecar overhead is zero — it isn't — but that the capabilities it replaces would otherwise require distributed, per-service engineering effort that, in aggregate, likely costs more than the sidecar's resource budget.

**Q30. "You're designing the service-to-service communication architecture for a new greenfield microservices system. The team is currently two services written in Go, but expects to grow to fifteen services in multiple languages over the next year. Which discovery model would you recommend, and what would your initial setup look like?"**
A: Recommend server-side discovery from the start, specifically via a Kubernetes-native approach: use Kubernetes Services (ClusterIP) as the stable addressing mechanism initially (zero additional infrastructure, fully adequate for simple load balancing across healthy pods), and plan for a service mesh (Istio or Linkerd) introduction when the system reaches the scale where richer traffic management (retries, circuit breaking, per-RPC observability, mTLS) becomes operationally necessary. The reason to start here rather than with client-side: embedding a discovery library now, while only two Go services exist, establishes a precedent and a debt that grows with every new service and every new language added — by the time fifteen services in multiple languages exist, migrating away from client-side is a large, coordinated undertaking. Starting server-side keeps calling services clean from day one, makes adding any language trivial (just deploy a new service, call its ClusterIP, discovery just works), and the transition from basic Kubernetes Services to a full mesh is an infrastructure upgrade that doesn't require touching any application code.

**Q31. "During a traffic spike, your server-side load balancer is itself becoming a bottleneck — its CPU is saturating and it's adding measurable latency to all service-to-service calls. How would you address this without abandoning server-side discovery?"**
A: Several options, depending on the specific bottleneck: if it's a centralized remote load balancer, scale it horizontally (multiple instances with their own load balancer in front) and verify that the calling services are distributing connections across all instances rather than routing to just one; if the bottleneck is that the centralized intermediary is doing expensive L7 inspection on every call, consider whether a lighter-weight L4 path would suffice for the high-volume traffic, reserving L7 processing for traffic that genuinely requires it; if the architecture allows, migrate from a centralized remote intermediary toward a sidecar/co-located proxy model (Q19), which distributes the proxy workload across all nodes rather than concentrating it — a sidecar proxy saturating on one node can be addressed by scaling that node, and doesn't affect proxies on other nodes. The principle: a bottlenecked intermediary is an infrastructure scaling problem with standard infrastructure scaling remedies, not an argument for abandoning the server-side model — client-side discovery's "no intermediary" characteristic avoids this specific bottleneck type but replaces it with the others discussed in Q8.

## Quick Reference Table

| Dimension | Client-Side Discovery | Server-Side Discovery |
|---|---|---|
| Who queries the registry | The calling service itself | An intermediary (LB, sidecar, gateway) |
| Registry coupling | Per-service, per-language client library required | Calling service is registry-agnostic |
| Polyglot support | Per-language library required; behavior may diverge | Inherently language-agnostic |
| Load balancing location | Inside calling service (library) | Inside intermediary |
| Extra network hop | None — direct to chosen instance | Minimal (co-located sidecar) or measurable (remote LB) |
| Failure isolation | Library failure = app failure | Proxy failure isolated from app process |
| Registry outage handling | Serves stale local cache | Serves last-known endpoint set from proxy |
| Instance addressability | Direct — caller knows which instance it chose | Opaque — caller doesn't know which instance was selected |
| Observability | Per-service, each team instruments independently | Uniform, centralized across all traffic in intermediary |
| Update routing behavior | Requires updating and redeploying each calling service | Update intermediary config; no calling service change |
| Modern canonical example | gRPC client-side resolver, Netflix Ribbon | Kubernetes Service + kube-proxy, Envoy sidecar (service mesh) |
| Best fit for | Stateful/per-instance routing; constrained latency; single-language systems | Polyglot systems; centralized policy; Kubernetes-native; service mesh |

---

**Tip for interviews:** What separates strong candidates on client-side vs server-side service discovery specifically: (1) being able to articulate **exactly what each model requires of the calling service** — not just naming the models but being concrete about what the caller must implement vs what it can ignore entirely (Q2, Q4, Q9); (2) identifying **polyglot support as the most practically decisive differentiator** in most real-world systems — the per-language library burden of client-side is the failure mode most organizations eventually hit, and recognizing it early is a sign of architectural maturity (Q13, Q28); (3) explaining **why sidecar-based server-side discovery specifically resolves the historical objection to server-side** (the extra network hop) — understanding that a co-located proxy's hop is fundamentally different in cost from a remote load balancer's hop (Q19, Q29); (4) knowing that **client-side discovery retains genuine advantages for stateful, per-instance-addressing protocols** — it's not universally wrong, just wrong for the common case, and being able to name the concrete exception (Q21, Q25); and (5) framing the **greenfield choice clearly** — starting with server-side from day one avoids the large, coordinated migration cost of moving away from embedded client libraries later, which is the kind of long-term architectural thinking interviewers at the 5 YOE level specifically probe for (Q30).
