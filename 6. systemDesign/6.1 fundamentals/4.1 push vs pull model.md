# Push vs Pull Model (CDN Content Delivery) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Push model in CDN content delivery?**
A: The origin proactively uploads (pushes) content to CDN edge servers ahead of time, before any client requests it. The content owner controls exactly what gets distributed and when — typically as part of a deployment or publishing pipeline. By the time a user requests the content, it's already present at the edge (or at least at the regional tier), so the first request is a cache hit, not a miss.

**Q2. What is the Pull model in CDN content delivery?**
A: The CDN edge fetches (pulls) content from the origin lazily, on-demand, the first time a client requests it — this is the "origin fetch on cache miss" behavior described in the standard CDN caching guide. The edge doesn't know what content exists in advance; it discovers and caches content reactively, based on real traffic patterns. This is also called "origin pull" caching and is the default behavior of virtually all modern general-purpose CDNs (CloudFront, Cloudflare, Akamai, Fastly) for typical web traffic.

**Q3. What is the one-sentence distinction between the two?**
A: Push = the origin decides what goes to the edge and sends it proactively, regardless of whether anyone has asked for it yet. Pull = the edge decides what to fetch, reactively, based on actual incoming requests, and only after a real user asks for it.

**Q4. Why is Pull the default/dominant model for general web CDN usage today?**
A: Because it requires zero extra deployment work from the origin operator — you set `Cache-Control` headers correctly, and the CDN handles population automatically based on real traffic. It naturally adapts to whatever content actually gets requested (no need to predict in advance), it scales effortlessly to massive content catalogs without pre-uploading everything, and it's self-managing — content that's never requested never consumes edge storage. This operational simplicity is why nearly all modern CDN providers default to pull, and most engineers' day-to-day CDN experience (CloudFront, Cloudflare) is pull-based even if they don't think of it by that name.

## Section 2: Mechanics

**Q5. Walk through the pull model request flow in detail.**
A:
1. Client requests `https://cdn.example.com/image.jpg`.
2. Request routes (via GeoDNS/Anycast) to the nearest edge PoP.
3. Edge checks its local cache — not present (cold cache, first request anywhere for this object) → cache miss.
4. Edge issues a request to the configured origin (e.g., an S3 bucket, the application's web server) for `image.jpg`.
5. Origin returns the content with `Cache-Control` headers.
6. Edge stores it locally according to those headers, and serves it to the requesting client.
7. All subsequent requests for `image.jpg` from clients near that PoP are served from cache (cache hit) until TTL expiry.

**Q6. Walk through the push model request flow in detail.**
A:
1. As part of a publish/deploy event (e.g., uploading a new video, releasing a software build, deploying a new app version), the origin/content owner explicitly uploads the content to the CDN's storage/distribution system — via an API call, a management console, or an integrated deployment pipeline.
2. The CDN distributes the content to its edge locations (or a defined subset — not necessarily every PoP immediately; some push CDNs propagate progressively or only pre-populate based on configured tiers).
3. When the first real client request arrives, the content is already present at the edge — served immediately as a "hit," with no origin round-trip needed for that first request.
4. The origin is responsible for explicitly pushing updates and, in many push setups, explicitly managing removal/expiration — the CDN isn't independently deciding what to fetch or evict based on traffic patterns the way a pull cache does.

**Q7. What does "cold cache" mean and how does it relate to push vs pull?**
A: A cold cache is one with no (or stale/evicted) entries for the requested content — the first relevant request is always a cache miss requiring an origin round-trip. In the pull model, every piece of content starts cold at every PoP until the first request "warms" it — meaning the very first user to request any given object at any given PoP always experiences the slower, full origin-fetch latency. In the push model, content is pre-warmed before any user ever requests it — there is no "first unlucky user" who eats the cache-miss penalty, because population happened proactively during deployment, not reactively on first request.

## Section 3: When Each Model Is the Right Choice

**Q8. What workloads/content types favor the Push model?**
A:
- **Large media files with known release schedules**: software downloads, game patches, OS updates, movie/video releases — content where you know in advance exactly what will be requested and when (often a sudden, massive spike right at release time).
- **Low-traffic or unpredictable-access content where guaranteed availability matters more than storage efficiency**: niche content that might get one request a month, but that single request must be fast — pull would mean that lone request pays the full cache-miss penalty every time (since infrequent access means it likely gets evicted between requests).
- **Content where the first-request latency is unacceptable**: e.g., a major product launch where the very first wave of users (often the most engaged, most likely to tweet about a bad experience) must get a fast, cache-hit-quality experience immediately — pull's "first request is always a miss" property is a deal-breaker here.
- **Bandwidth-constrained or unreliable origin**: if the origin itself has limited capacity or unreliable uptime, push lets you control exactly when the origin is hit (during a scheduled push window) rather than being at the mercy of unpredictable real-time pull traffic patterns.

**Q9. What workloads/content types favor the Pull model?**
A:
- **Large catalogs of unpredictable popularity**: a content/media platform with millions of assets where only a small "hot" subset is actually requested at any time (the classic long-tail distribution) — pre-pushing everything would waste enormous edge storage on content nobody requests.
- **Frequently-updated or dynamic-adjacent content**: pull naturally re-fetches on TTL expiry, fitting content that changes regularly without requiring an explicit push for every update.
- **General web traffic (HTML, API responses, typical website assets)**: the standard case — content set is large, request patterns are organic and hard to predict in advance, and operational simplicity (zero extra deployment steps) is valuable.
- **New/growing platforms**: where future popular content can't be known in advance — pull adapts automatically to whatever turns out to be popular, with no operator prediction required.

**Q10. Give a concrete example where push is clearly the right choice and explain why.**
A: A AAA video game release with a 60GB day-one patch, expected to be downloaded by millions of players within the first hour of release. If using pull: the very first wave of millions of concurrent download requests would all hit cold edge caches simultaneously, causing a massive synchronized cache-miss storm hitting the origin all at once — exactly the "thundering herd" scenario that overwhelms infrastructure. With push: the publisher uploads the patch to the CDN hours or days before release, the CDN pre-distributes it to all relevant edge locations during the lead time (off-peak, controlled bandwidth), and at release time, every download request is already a cache hit from the first millisecond — no origin involvement needed at all during the traffic spike.

**Q11. Give a concrete example where pull is clearly the right choice and explain why.**
A: A photo-sharing social media platform with billions of user-uploaded images, the vast majority of which receive only a handful of views ever. Pushing every uploaded image to every CDN edge location would be absurd — petabytes of storage duplicated across hundreds of PoPs for content that, statistically, almost nobody will request from most of those locations. Pull naturally handles this: each PoP only caches the images its actual nearby users request, automatically adapting to real demand, with old/rarely-accessed images naturally evicted (LRU or similar) to make room for active content — no operator intervention required.

## Section 4: Hybrid and Tiered Approaches

**Q12. Do real-world CDN deployments use pure push or pure pull, or do they combine both?**
A: Almost always a hybrid, applied at different layers of the same architecture:
- **Pull for general web/API traffic** — the default behavior for most page assets, dynamic content acceleration, and the bulk of day-to-day traffic.
- **Push (pre-warming) for specific high-stakes events** — major releases, marketing campaigns with predictable traffic spikes, or content the business knows in advance will be hot. Most major CDN providers offer an explicit "cache pre-warming" or "pre-fetch" API for exactly this purpose, layered on top of an otherwise pull-based architecture.

**Q13. What is "cache pre-warming" and how does it relate to push vs pull?**
A: Pre-warming is the practice of proactively triggering cache population (effectively simulating real requests, or explicitly pushing content) for specific content before real traffic arrives — a push-like technique layered on top of an otherwise pull-based CDN. Common implementations: issuing synthetic GET requests to each PoP/region right after a deployment so the first real users get cache hits; or using the CDN provider's explicit pre-fetch/pre-load API where supported. This combines the operational simplicity of pull-based CDNs for everyday traffic with the "no cold cache penalty" benefit of push for predictable, high-stakes traffic events.

**Q14. What is "origin shielding" and how does it relate to mitigating pull's cold-cache weakness?**
A: As covered in the core CDN guide, origin shielding designates one tier/PoP as the only one allowed to fetch directly from origin — other edges fetch from the shield rather than from origin directly on a miss. This doesn't eliminate the pull model's inherent "first request is a miss" property, but it dramatically reduces its blast radius: instead of every one of (say) 200 PoPs independently experiencing a cold-cache miss and hitting origin directly (200 concurrent origin requests for the same new content), they all funnel through the shield tier, which itself only misses once globally — reducing origin load from O(PoP count) to O(1) for any given piece of newly-popular content. This is a pull-model optimization, distinct from switching to push.

**Q15. How does multi-tier caching (regional/mid-tier caches between edge and origin) interact with push vs pull?**
A: Most large CDN architectures have more than two tiers: edge PoPs → regional/mid-tier caches → origin. In a pull architecture, a cache miss at the edge first checks the regional tier (which may already have the content cached from a different edge's earlier request in that region) before going all the way to origin — reducing origin load and latency for the "miss" path without requiring any push. This tiered pull architecture captures much of push's benefit (avoiding origin round-trips for popular content) while retaining pull's core advantage (no manual content prediction needed) — which is part of why pure push architectures have become less necessary as tiered pull caching has matured.

## Section 5: Operational and Cost Trade-offs

**Q16. What are the storage cost implications of push vs pull?**
A: Push pre-populates content at every targeted edge location regardless of actual local demand — if you push a file to 300 PoPs but it's only ever requested from 10 of them, you've paid storage/distribution cost for 290 PoPs' worth of wasted capacity. Pull only stores content where it's actually been requested, naturally minimizing storage to what's truly needed at each location — more storage-efficient for unpredictable or long-tail content, at the cost of less control over exactly where content lives at any given moment.

**Q17. What are the operational/engineering overhead implications of push vs pull?**
A: Push requires the content owner to build and maintain an explicit publishing pipeline — deciding what to push, when, and to where, integrating this into deployment/release processes, and handling updates/invalidation explicitly. This is real engineering investment. Pull requires comparatively little explicit work — correct `Cache-Control` headers and the CDN's default reactive behavior handle population and eviction automatically, with no custom publishing logic needed. This operational asymmetry is a major reason pull dominates for general-purpose use, reserving push (or pre-warming) for situations where the predictability and control benefit clearly outweighs the added engineering cost.

**Q18. How does the "predictability of demand" factor into the push vs pull decision?**
A: This is the central decision variable. If you can predict with high confidence what will be requested and when (a scheduled release, a known marketing campaign, a fixed catalog of training videos for a course), push lets you front-load the cost/latency of distribution during a controlled window, paying it once rather than under live traffic pressure. If demand is unpredictable (organic user-generated content, long-tail catalogs, traffic patterns that depend on viral/unplannable factors), push requires guessing — and guessing wrong means either wasted distribution (pushed content nobody wanted) or missed distribution (popular content that wasn't pushed, falling back to an uncontrolled pull miss anyway). Pull's reactive nature handles unpredictable demand gracefully without requiring prediction at all.

**Q19. What is the failure mode of push when predictions are wrong?**
A: Two distinct failure directions:
- **Over-push** (pushed content that turns out unpopular): wasted storage and distribution bandwidth cost across potentially hundreds of PoPs, with little or no offsetting benefit since few/no users ever request it from most locations.
- **Under-push** (content that turns out popular but wasn't pushed, or wasn't pushed widely enough): those requests fall through to an uncontrolled pull-style cache miss anyway — except now it's happening under unplanned, possibly high-pressure traffic conditions, potentially worse than if you'd just used pull-with-pre-warming in the first place, since the push infrastructure wasn't built to handle dynamic re-routing of unplanned hot content.

This asymmetric risk is why most modern architectures favor pull as the default and use push/pre-warming surgically for specific known events, rather than committing fully to a push architecture.

## Section 6: Content Update and Consistency Behavior

**Q20. How does content updating differ between push and pull when the origin content changes?**
A: In pull, an update at origin doesn't automatically propagate anywhere — the CDN keeps serving the old cached version until the TTL expires (or an explicit purge/invalidation is triggered, as covered in the cache invalidation guide). In push, the content owner explicitly triggers a new push when content changes — there's no implicit TTL-based staleness window the same way, since the model assumes the origin is authoritatively in control of exactly what version exists at the edge at any time. However, "explicit push on every update" requires the same operational discipline as explicit purge in a pull model — if you forget to push an update, the edge silently serves the old version indefinitely, with no automatic re-fetch mechanism to eventually correct it (unlike pull's TTL-based self-healing).

**Q21. Which model handles unplanned origin content changes more gracefully — push or pull?**
A: Pull, generally — because TTL expiry provides an automatic, self-healing consistency mechanism: even if nobody remembers to explicitly invalidate, the cache eventually refreshes on its own once the TTL lapses. Push has no equivalent automatic mechanism by default — if an operator updates origin content but forgets to trigger a corresponding push, the edge can serve stale content indefinitely with no built-in correction. This is a meaningful operational risk that favors pull (or push systems that are explicitly paired with a TTL/expiration mechanism as a safety net) for content that may change outside of a tightly controlled release process.

**Q22. How does the consistency/staleness trade-off differ in terms of "guaranteed freshness at first request"?**
A: Push offers a stronger guarantee for the very first request after a release: since content is pre-distributed before traffic arrives, the first user to request it gets the fully fresh, correct version immediately — there's no propagation lag for that initial population. Pull, by contrast, can briefly serve different versions to different users immediately after an origin update, depending on which PoPs happen to have cached the old version with time remaining on the TTL versus which PoPs experience a fresh miss and pull the new version — a transient inconsistency window that doesn't exist in a correctly-executed push, but exists by design in pull's reactive model.

## Section 7: Implementation and Provider-Specific Notes

**Q23. What is an example of an explicit "push CDN" feature offered by major providers?**
A: Most general-purpose CDNs are pull-by-default but offer explicit pre-fetch/pre-warm APIs that function as push capability layered on top:
- **AWS CloudFront**: doesn't have a dedicated "push" mode in the traditional sense, but content stored in S3 with appropriate origin configuration is effectively pre-positioned at origin (not edge); true edge pre-warming requires synthetic request triggering or third-party tooling.
- **Akamai**: has historically offered both pull (NetStorage-backed pull-based delivery) and explicit "Push" products for large media files where content is uploaded directly into Akamai's storage and proactively distributed.
- **Fastly**: pull-based by default with strong instant-purge capability (sub-second invalidation), reducing the practical need for push since stale content can be corrected almost immediately rather than requiring pre-population to avoid staleness windows.
- **Cloudflare**: pull-based; offers cache pre-warming patterns via Workers or external scripts issuing synthetic requests across PoPs, rather than a dedicated push product.

**Q24. Why have dedicated "push CDN" products become less common over time, even though the use case (large media releases) still exists?**
A: Several converging factors: (1) instant/fast purge capabilities in modern pull CDNs have largely closed the staleness gap that push originally solved; (2) pre-warming/pre-fetch APIs let operators get push-like behavior on top of pull infrastructure without committing to a fully separate push architecture; (3) origin shielding and tiered caching (Q14-15) reduce the "thundering herd on release" problem that push was originally designed to prevent, by absorbing the herd at a shield tier rather than requiring pre-population at every edge; (4) operational simplicity strongly favors a single unified pull-based architecture with selective pre-warming over maintaining two entirely separate content delivery pipelines (push for some content, pull for everything else).

**Q25. How would you implement a pre-warming step in a deployment pipeline for a pull-based CDN, in practice?**
A: After deploying new content to origin (e.g., publishing a new build artifact or media file), the deployment pipeline issues synthetic GET requests for the new URLs, targeted (directly or indirectly) at each major edge region/PoP — either by hitting region-specific CDN endpoints if the provider exposes them, or by relying on the provider's pre-fetch API if available. This forces the cache-miss-and-populate cycle to happen during the controlled deployment window rather than during the first wave of real user traffic. Combined with cache-busting (versioned URLs from the CDN guide), this ensures the new version is both correctly identified (no stale version served) and pre-populated (no cold-cache penalty) by the time real users arrive.

## Section 8: Comparison Table and Scenario Questions

**Q26. Full comparison: Push vs Pull.**
A:

| Dimension | Push | Pull |
|---|---|---|
| Who initiates distribution | Origin/content owner | CDN edge, on first client request |
| Timing | Proactive (before traffic) | Reactive (on demand) |
| First-request latency | Fast (pre-warmed) | Slow (cold cache miss) |
| Storage efficiency | Lower (content pushed everywhere, used or not) | Higher (only stores what's actually requested) |
| Operational overhead | Higher (explicit publish pipeline) | Lower (automatic via headers) |
| Update/consistency handling | Manual (must re-push on change) | Automatic (TTL expiry self-heals) |
| Best for | Large media, scheduled releases, predictable spikes | General web traffic, long-tail/unpredictable content |
| Risk if demand is mispredicted | Wasted storage (over-push) or uncontrolled miss (under-push) | None — adapts automatically |
| Default in modern CDNs | No (niche/explicit feature) | Yes (standard behavior) |
| Common mitigations layered on top | N/A (is itself the mitigation) | Pre-warming, origin shielding, tiered caching |

**Q27. "A streaming service is launching a highly anticipated new show, expected to get 5 million viewers in the first hour. How would you design the content delivery strategy?"**
A: Push (pre-distribute) the video segments to CDN edge locations ahead of the launch — ideally during off-peak hours over the preceding day, using the lead time to populate edges in regions with the highest expected viewership without competing with live traffic. Combine with origin shielding for any content that does experience a miss (e.g., less-popular regions that weren't pre-targeted), and use adaptive bitrate streaming (HLS/DASH, from the CDN guide) so the pre-pushed content includes all the bitrate variants needed for different network conditions. The key reasoning to state explicitly: with a known release time and predictable massive concurrent demand, pull's "first request is a cache miss" property would create a synchronized thundering herd against origin at the exact moment of peak demand — exactly the scenario push is designed to prevent.

**Q28. "Your e-commerce platform's product catalog has 50 million SKUs, but any given day only about 200,000 of them receive significant traffic. How would you approach CDN caching?"**
A: Pull, with no push component needed — this is the textbook long-tail scenario. Pushing all 50 million product pages/images to every edge location would be enormously wasteful, since the vast majority will receive few or no requests from most regions. Pull naturally adapts: the ~200,000 actively-traffic SKUs become cached at the relevant edges based on real demand, while the long tail simply isn't cached anywhere it isn't requested — no operator decision-making required. If specific high-traffic flash-sale items are known in advance (a predictable subset within the broader unpredictable catalog), pre-warming just those specific SKUs ahead of the sale would be the targeted hybrid approach, rather than pushing the entire catalog.

**Q29. "An interviewer asks: 'Isn't push always better since it avoids the cache-miss penalty entirely?' How do you respond?"**
A: Push avoids the cache-miss penalty only for content you correctly predicted would be requested, at the locations you correctly predicted it would be requested from — it doesn't eliminate the cache-miss problem in general, it just shifts the risk to "did you predict correctly?" For unpredictable or very large content catalogs, that prediction is either impossible or so costly (in storage/distribution overhead) that it isn't worth it relative to pull's automatic adaptation. Push is the better choice specifically when prediction is both possible and economically justified (known release schedules, manageable content volume) — not universally superior. The honest framing: push trades operational complexity and prediction risk for guaranteed first-request latency; pull trades a bounded first-request penalty (mitigated via pre-warming/shielding) for zero prediction risk and minimal operational overhead.

**Q30. "How does push vs pull relate to the broader 'eager vs lazy' pattern seen elsewhere in distributed systems?"**
A: It's a direct instance of a very general distributed-systems trade-off: eager (push) computation/distribution does the work upfront, paying cost predictably but possibly wastefully if the work turns out unneeded; lazy (pull) computation/distribution defers work until it's actually needed, avoiding waste on unneeded work but incurring a first-use penalty and less predictable load timing. The same pattern shows up in cache warming strategies generally, lazy initialization in software design, eager vs lazy evaluation in programming languages, and read-through vs write-through caching strategies in application-level caching. Recognizing CDN push/pull as an instance of this broader pattern — rather than a CDN-specific quirk — is a strong signal of systems thinking that generalizes across the rest of an interview.
