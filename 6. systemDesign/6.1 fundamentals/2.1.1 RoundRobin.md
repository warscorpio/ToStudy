# Round Robin — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Round Robin load balancing?**
A: Round Robin is a scheduling algorithm where each new request (or connection) is routed to the next server in a fixed cyclic sequence. If you have backends A, B, C, the first request goes to A, the second to B, the third to C, the fourth back to A, and so on indefinitely. It assumes all backends are equally capable and all requests have roughly equal cost.

**Q2. What problem does Round Robin solve?**
A: It distributes traffic evenly across backends in a simple, predictable, and stateless way — ensuring no single server receives all requests while others sit idle. It's the baseline algorithm against which more sophisticated strategies are compared.

**Q3. What does "stateless" mean in the context of Round Robin?**
A: The load balancer only needs to track one piece of state: a pointer (counter/index) indicating which backend was used last. It doesn't need to know active connection counts, response latencies, or health states of backends — making it computationally trivial and easy to implement. Compare this to Least Connections, which must maintain a counter per backend.

**Q4. How is Round Robin implemented at a low level?**
A: Typically with an atomic counter and a modulo operation:

```
backend_index = (counter++) % num_backends
selected_backend = backend_list[backend_index]
```

The counter is incremented on every request. In multi-threaded or distributed LB environments, the counter is usually atomic (e.g., `std::atomic` in C++, `sync/atomic` in Go) to avoid race conditions.

**Q5. Is Round Robin the same at L4 and L7?**
A: The concept is the same, but what gets rotated differs. At L4, it rotates per TCP connection (all HTTP requests on one connection go to the same backend). At L7, it can rotate per HTTP request (each individual request, even on the same connection, can go to a different backend via connection pooling). L7 Round Robin is therefore more granular and more "fair" at the request level.

## Section 2: Variants

**Q6. What is Weighted Round Robin?**
A: A variant where each backend is assigned a weight proportional to its capacity. A backend with weight 3 receives 3x the traffic of a backend with weight 1. The scheduler cycles through backends but visits higher-weight backends more frequently.

Example: backends A (weight 3), B (weight 1), C (weight 2) → sequence: A, A, A, B, C, C, A, A, A, B, C, C...

Used for:
- Canary deployments (e.g., v2 gets weight 5 out of 100, v1 gets 95).
- Mixed-capacity fleets (e.g., some nodes have more CPU/RAM).
- Gradual traffic shifts during blue/green deployments.

**Q7. How is Weighted Round Robin implemented efficiently?**
A: The naive approach expands the backend list by repeating each backend weight times — simple but memory-inefficient for large weights. The production-grade approach is the **Smooth Weighted Round Robin** algorithm (used in NGINX):

Each backend tracks:
- `weight` (static, configured)
- `current_weight` (dynamic, starts at 0)

Each cycle:
1. Add each backend's `weight` to its `current_weight`.
2. Select the backend with the highest `current_weight`.
3. Subtract the sum of all weights from the selected backend's `current_weight`.

This produces an evenly interleaved sequence (e.g., A, C, A, B, A, C for weights 3, 1, 2) instead of bursting all of A's requests together — reducing backend hotspots and improving latency distribution.

**Q8. What is IP Hash Round Robin?**
A: Not strictly Round Robin — IP Hash deterministically maps a client's source IP to a backend via hashing. The effect is sticky routing: the same IP always hits the same backend. It's often described alongside Round Robin as a variant because many LBs offer it in the same configuration menu, but the algorithm is fundamentally different (no rotation occurs).

**Q9. What is DNS Round Robin?**
A: A primitive form of load balancing where a single domain name has multiple A/AAAA records, each pointing to a different IP. DNS resolvers return them in rotating order. It requires no dedicated LB hardware/software — just DNS configuration.

Limitations:
- DNS caching at clients, OS, and intermediate resolvers means the "round" takes far longer than a request cycle — traffic isn't distributed in real time.
- No health checking — a failed backend stays in DNS rotation until TTL expires and records are updated.
- No session awareness, no TLS termination, no path-based routing.
- Clients cache DNS and may stick to one IP for minutes despite TTL.

DNS Round Robin is best treated as a coarse-grained fallback or a first layer in a multi-tier architecture (geo-DNS → L4 LB → L7 LB), not as a production load balancing solution on its own.

**Q10. What is Round Robin scheduling in the context of CPU scheduling vs load balancing?**
A: The concept originates in CPU process scheduling — each process gets a fixed time quantum in cyclic order. In load balancing, the idea is the same (cyclic distribution) but the "unit" being scheduled is a network request/connection instead of CPU time. Interviewers occasionally ask about the connection to test breadth of systems knowledge.

## Section 3: When Round Robin Works and When It Fails

**Q11. Under what conditions does Round Robin work well?**
A: Round Robin is optimal when:
- All backends are homogeneous (same hardware, same capacity).
- Requests have roughly uniform cost (e.g., serving static files, simple reads from cache).
- Connection durations are short and roughly equal.
- Traffic is steady (no sharp spikes that expose its unawareness of load).

Typical good fit: serving static assets (images, JS bundles), simple REST endpoints with cached reads, or any workload where request processing time is tight and predictable.

**Q12. When does Round Robin break down?**
A: It breaks down when the "equal distribution = equal load" assumption fails:

- **Non-uniform request cost** — If 1 in 100 requests triggers a heavy DB query or CPU-intensive computation, Round Robin may pile several expensive requests on the same backend purely by chance, while it's already busy. Least Connections or Least Response Time handles this better.
- **Long-lived connections** — If connections are persistent (keep-alive, WebSockets, gRPC streams), Round Robin at the connection level means the backend serving an early heavy connection gets no relief while new connections are distributed elsewhere. The LB distributes connections evenly, not load.
- **Heterogeneous backends** — If one backend is underpowered or degraded, Round Robin still sends it the same share of traffic. It will fall behind, queuing up requests. Weighted Round Robin or health-check-based dynamic weighting is needed.
- **Slow backends** — A backend experiencing GC pauses, disk I/O saturation, or a slow downstream dependency will continue receiving new requests at the same rate. Round Robin is oblivious to backend latency.

**Q13. What is the "slow backend" or "thundering herd" problem with Round Robin?**
A: If one backend becomes slow (e.g., GC pause, DB lock), its in-flight requests pile up. Round Robin keeps sending it new requests at the same rate as healthy backends — making the slow backend fall further behind. Meanwhile, the LB's health check may not flag it as "unhealthy" since it's still accepting connections. Algorithms like Least Connections or Least Response Time detect this automatically (the slow backend accumulates connections/latency and gets deprioritized). Round Robin needs explicit circuit breaking or timeout-based outlier detection (available in Envoy) as a compensating mechanism.

**Q14. How do long-lived connections defeat L4 Round Robin?**
A: Consider a fleet of servers behind an L4 LB using Round Robin per connection. If each client opens one long-lived TCP connection and sends thousands of requests over it, all those requests go to whichever backend was assigned at connection establishment. New clients get distributed evenly, but old clients pin a backend to their workload. The distribution is only fair at the moment of connection — not over time. This is specifically why gRPC and HTTP/2 services need an L7 LB that can load-balance at the request/stream level.

## Section 4: Round Robin in Production Systems

**Q15. Where in the stack would you use Round Robin in a real production architecture?**
A: Multiple layers, each with different granularity:
- **DNS level**: Coarse routing across data centers or regions (DNS Round Robin, though limited).
- **L4 LB tier**: Distribute TCP connections across a fleet of L7 LB instances (Round Robin works well here since L7 LBs are homogeneous and stateless from L4's perspective).
- **L7 LB tier**: Distribute HTTP requests to backend service replicas (Round Robin works if backends are homogeneous and requests are uniform cost — otherwise use Least Connections).
- **Client-side LB (service mesh / gRPC)**: Each client proxy (e.g., Envoy sidecar) uses Round Robin or Power of Two Choices across discovered instances from the service registry.

**Q16. How does NGINX implement Round Robin?**
A: NGINX's default upstream selection is Round Robin. It cycles through backends sequentially per worker process. Each NGINX worker maintains its own state, so the global distribution isn't perfectly even across workers (each worker does its own round-robin), but in aggregate it approximates even distribution. NGINX's smooth weighted round-robin (described in Q7) is built in when weights are configured.

**Q17. How does Envoy implement Round Robin?**
A: Envoy supports multiple LB policies including `ROUND_ROBIN` (configured per cluster). It runs Round Robin at the request level (L7), not connection level, using connection pooling to backends. Envoy also supports priority groups and locality-weighted load balancing on top of Round Robin — e.g., prefer backends in the same availability zone, and only spill over to other zones when local capacity is exceeded.

**Q18. What is locality-aware Round Robin and why does it matter?**
A: In a multi-AZ or multi-region deployment, purely Round Robin across all backends ignores network topology — a backend in us-east-2c gets requests from an LB in us-east-2a, adding cross-AZ latency and egress cost. Locality-aware Round Robin (supported in Envoy/Istio) weights backends by proximity — prefer same-AZ backends, then same-region, then cross-region — only distributing outside the preferred zone when local capacity is insufficient. This reduces latency and cloud networking costs significantly.

**Q19. How does Round Robin interact with auto-scaling?**
A: When a new backend instance joins the pool (scale-out event), it enters the Round Robin rotation and starts receiving its share of traffic. Since Round Robin doesn't track load, the new instance immediately receives the same rate as established instances regardless of warm-up state. This can cause problems if the new instance has a cold JVM, empty in-memory cache, or needs to establish DB connection pools. Mitigation: slow-start mode (available in NGINX and Envoy) — gradually increase the new backend's effective weight from 0 to its full weight over a configurable ramp period, giving it time to warm up before receiving full traffic.

**Q20. What is "slow start" mode and when do you use it with Round Robin?**
A: Slow start is an optional ramp-up phase where a newly added backend is assigned a low initial weight that linearly increases to full weight over a configured duration (e.g., 30-120 seconds). It prevents a cold backend from being hit with full traffic the moment it's healthy. Configured in NGINX via `slow_start` directive on upstream servers, and in Envoy via `slow_start_config` on the cluster. Important for services with JVM warmup, cache warming, or connection pool initialization.

## Section 5: Comparison With Other Algorithms

**Q21. Round Robin vs Least Connections — when does each win?**
A:
- **Round Robin wins** when request processing time is roughly uniform. It's simpler, has zero per-backend state to maintain, and distributes connections perfectly evenly in the homogeneous case.
- **Least Connections wins** when request cost is variable. If some requests take 5ms and others take 500ms, Least Connections naturally sends new requests to the less-loaded backend, avoiding pileups. The cost is maintaining a counter per backend, which is cheap but adds synchronization in distributed LB setups.

Rule of thumb: if p99 request latency is within 2-3x of p50, Round Robin is fine. If you have a fat tail (some requests 10-100x slower), use Least Connections or Least Response Time.

**Q22. Round Robin vs Power of Two Choices — what's the trade-off?**
A: Power of Two Choices (P2C) picks 2 backends at random and routes to the less loaded one (by connection count or response time). Compared to Round Robin:
- P2C adapts to heterogeneous load without global coordination — each LB node makes an independent decision with just 2 comparisons.
- Round Robin gives perfectly even distribution in the homogeneous case; P2C gives near-optimal distribution in the heterogeneous case.
- P2C works better in distributed LB fleets where maintaining a globally consistent round-robin counter would require coordination. Round Robin requires either a shared atomic counter or per-instance independent counters (which lose global fairness).

P2C is generally preferred for large-scale distributed systems; Round Robin is preferred when simplicity and perfect sequential fairness matter.

**Q23. Round Robin vs Consistent Hashing — when do you use each?**
A: Entirely different use cases:
- **Round Robin** — distributes load evenly, doesn't care which backend handles which request. No affinity. Best for stateless services.
- **Consistent Hashing** — maps a key (e.g., user_id, cache key) to a specific backend deterministically. Minimizes remapping when backends are added/removed. Used for caching layers (Memcached, Redis clusters), sharded databases, or any system where the same key must always go to the same node for cache efficiency or data locality.

You'd use Round Robin for your stateless API servers and Consistent Hashing for your cache or storage layer.

**Q24. Round Robin vs Random — is random ever better?**
A: Pure random has worse expected distribution than Round Robin for a finite number of backends with low request count (more variance — you might get 4 requests to A and 0 to B by chance). At very high request counts, random converges to even distribution by the law of large numbers. Power of Two Choices is strictly better than pure random for load distribution. In practice, random is rarely used as a standalone policy; it's the sampling mechanism inside P2C.

## Section 6: Failure Modes & Edge Cases

**Q25. What happens to Round Robin when a backend is removed from the pool (due to failure or scale-in)?**
A: The backend is removed from the list and the Round Robin index adjusts. Connections/requests already in-flight to the removed backend are dropped (connection reset or timeout from the client's perspective). The LB redistributes future requests among remaining backends. This is why health checks are critical — you want the backend removed before it starts failing requests, not after. A graceful shutdown flow (drain connections before deregistering) avoids in-flight drops.

**Q26. What is "connection draining" and how does it interact with Round Robin?**
A: Connection draining (also called "deregistration delay" in AWS ALB) is a period during which an LB stops sending new requests to a backend being taken out of rotation, but allows in-flight requests to complete. During draining, the backend is excluded from the Round Robin sequence for new requests but continues serving existing ones until they finish or the drain timeout expires. This enables zero-downtime deployments.

**Q27. Can Round Robin cause a cascade failure when a backend goes down?**
A: Indirectly, yes. If backend C goes down and Round Robin keeps routing to it (before health checks detect the failure), those requests fail or time out. During that detection window, the load from C's failed requests is effectively lost. Once C is removed, A and B absorb C's share of traffic — if they were already near capacity, this increased load can cause them to degrade or fail too. The cascade is mitigated by fast health check intervals, circuit breaking, and maintaining headroom in the healthy backends.

**Q28. What is the "thundering herd" on recovery with Round Robin?**
A: When a failed backend recovers and re-enters the pool, Round Robin immediately starts sending it its full share of traffic. If the backend's in-memory caches are cold, connection pools are empty, or the JVM hasn't warmed up, this sudden full load can overwhelm it and cause it to fail again. Slow start (Q20) is the direct mitigation.

## Section 7: Scenario-Based Questions

**Q29. "You have 3 backends behind a Round Robin LB. One backend is running on a VM with half the CPU of the others. What problem do you anticipate and how do you fix it?"**
A: The underpowered backend will receive the same volume of requests as the others but take longer to process them. Its request queue will grow, latency will increase, and it may start timing out or rejecting connections — while the LB happily keeps routing a third of traffic to it. Fix: configure Weighted Round Robin with the underpowered backend at half the weight (e.g., A=2, B=2, C=1), so it receives proportionally less traffic matching its capacity. Long-term, normalize the fleet to homogeneous instances.

**Q30. "Your service uses gRPC and you're seeing one backend consistently handling 10x more RPC calls than the others despite Round Robin being configured at the L4 LB. Why?"**
A: Classic L4 + HTTP/2 mismatch. gRPC multiplexes many RPCs over a single HTTP/2 connection. The L4 LB does Round Robin at the TCP connection level — distributing connections evenly. But if clients hold long-lived connections (which gRPC clients do by default), all RPCs from a client go to whichever backend was assigned at connection time. The fix is to move load balancing to L7 (use Envoy, Istio, or a gRPC-aware proxy) so the LB can balance at the individual RPC call level rather than the TCP connection level.

**Q31. "You're rolling out a new version of a service. How do you use Weighted Round Robin to do a safe canary release, and what metrics do you watch?"**
A: Start with a small weight on v2 — e.g., v1=95, v2=5 — so 5% of traffic hits the new version. Monitor:
- **Error rate** — any spike in 5xx on v2 vs v1 baseline.
- **P99 latency** — regressions in tail latency on v2.
- **Business metrics** — conversion rate, checkout success rate (if traffic includes transactions).
- **Resource utilization** — CPU/memory on v2 pods.

If clean, gradually shift weight: 5 → 10 → 25 → 50 → 100. On any signal, instantly shift weight back to 0 (roll back) — far faster than redeploying. This is the same principle as feature flags but at the traffic routing layer.

**Q32. "You have a stateless API service where 95% of requests are fast (p50: 5ms) but 5% trigger a report generation that takes 2-3 seconds. Round Robin is configured. What problem emerges and what do you do?"**
A: The slow 5% of requests are distributed evenly by Round Robin, but while they're in-flight, each backend is "busy" with one slow request while also receiving its normal share of fast requests. If the slow requests accumulate (e.g., traffic spike), backends queue up and latency degrades. Round Robin doesn't know which backends are holding slow requests.

Better options:
1. **Least Connections** — backends holding long-running report requests accumulate more connections and get deprioritized for new ones.
2. **Separate queue/service** — route report generation to a dedicated worker pool (background jobs, async queue) so it never competes with fast API traffic.
3. **Least Response Time** — backends with elevated latency get fewer new requests automatically.

The pattern of mixing fast and slow workloads on the same fleet with Round Robin is a common source of latency degradation.
