# API Gateway: Request Routing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is request routing at the API Gateway level, specifically?**
A: It's the logic that determines, for each incoming request, which backend service (and which specific instance/endpoint of that service) should actually handle it — based on attributes of the request itself (the path, the host header, an HTTP method, custom headers, sometimes the request body) matched against a configured set of routing rules. It's the gateway's core dispatching function: every other gateway responsibility (auth, rate limiting, transformation) operates around this central job of getting each request to the correct destination.

**Q2. Why does request routing need to be a deliberate, configured concern rather than something trivially handled by a simple reverse proxy mapping?**
A: In any system beyond a handful of backend services, the mapping from "what the client asked for" to "which specific backend handles it" is rarely a flat, one-to-one, static mapping — it often involves matching on multiple request attributes simultaneously, applying precedence rules when multiple route patterns could match the same request, supporting path rewriting so the client-facing URL structure doesn't have to mirror internal service boundaries exactly, and frequently needs to change dynamically as services are added, split, or migrated, without requiring every routing decision to be hardcoded and redeployed manually each time the backend topology shifts.

**Q3. What are the main attributes of an incoming request that routing rules commonly match on?**
A: **Path** (most common — matching on the URL path, e.g., `/orders/*` routes to the orders service); **host/subdomain** (e.g., `api.example.com` vs `admin.example.com` routing to entirely different backend systems sharing the same gateway); **HTTP method** (e.g., routing `GET /orders` differently from `POST /orders` if they're handled by different services, though this is less common than path-based splitting); **headers** (e.g., routing based on a custom header like `X-API-Version`, or an `Accept` header indicating a desired response format); and sometimes **query parameters or request body content**, though matching on body content is less common and more operationally fragile, since it requires the gateway to parse and inspect the body before routing, adding overhead and complexity to what's ideally a fast, lightweight dispatching step.

**Q4. What does "path-based routing" look like concretely, and what's a common convention for it?**
A: Configuring routes where a path prefix maps to a backend service — e.g., `/api/orders/*` routes to the order-service, `/api/users/*` routes to the user-service, `/api/payments/*` routes to the payment-service — all reachable through one shared gateway hostname, with the path prefix itself acting as the dispatching key. This is the most common and intuitive routing pattern for REST-style APIs, since it naturally maps to how API consumers already think about resource hierarchies, and it keeps the entire system's API surface reachable under one consistent domain rather than requiring clients to know separate hostnames per service.

## Section 2: Path Manipulation and Versioning

**Q5. What is path rewriting, and why is it commonly needed at the gateway?**
A: Path rewriting is the gateway modifying the request path before forwarding it to the backend — commonly stripping a routing prefix that was only meaningful for the gateway's own dispatching logic but isn't part of the backend service's actual internal route structure. For example, a client-facing request to `/api/orders/123` might be routed by matching the `/api/orders` prefix, then rewritten to simply `/123` (or `/orders/123`, depending on the backend's own internal structure) before being forwarded — letting the backend service's internal routing stay clean and decoupled from whatever prefix scheme the gateway uses to organize its client-facing API surface.

**Q6. How is API versioning commonly handled at the routing layer, and what are the main approaches?**
A: A few common conventions: **URL path versioning** (`/v1/orders`, `/v2/orders` — explicit, highly visible, and trivially routable since the version is right there in the path the gateway already matches on); **header-based versioning** (a custom header like `X-API-Version: 2`, or content negotiation via the `Accept` header specifying a versioned media type — keeps the URL itself version-agnostic, at the cost of being less immediately visible/discoverable and requiring header-aware routing logic rather than simple path matching); and **host-based versioning** (`v1.api.example.com` vs `v2.api.example.com` — uncommon, but sometimes used when versions need to be treated as genuinely fully separate deployments). Path-based versioning is the most common in practice, largely because it's the simplest to route on and the most self-evident to API consumers browsing or debugging requests directly.

**Q7. What's a trade-off consideration in choosing whether multiple API versions route to the same backend service instance or to entirely separate deployments?**
A: Routing multiple versions to the *same* backend deployment (with the service itself handling version differences internally) keeps deployment topology simpler but pushes versioning complexity into the backend service's own code (conditional logic, multiple supported response shapes maintained simultaneously). Routing each version to genuinely *separate* backend deployments (the gateway directing `/v1/*` and `/v2/*` to entirely different running services, possibly different codebases or branches) keeps each version's backend implementation simpler and more independently evolvable, at the cost of running and maintaining multiple parallel deployments, including the operational overhead of eventually deprecating and decommissioning old versions cleanly. Larger, longer-lived public APIs more often lean toward separate deployments per major version; internal or rapidly-iterating APIs more often handle versioning within a single deployment.

## Section 3: Dynamic and Service-Discovery-Based Routing

**Q8. What's the difference between static routing configuration and dynamic, service-discovery-based routing?**
A: Static routing configuration hardcodes the mapping from route patterns to specific backend addresses (a fixed IP or hostname) directly in the gateway's configuration, requiring a configuration change and redeploy/reload of the gateway whenever the backend topology changes. Dynamic, service-discovery-based routing instead has the gateway consult a live service registry (Consul, etcd, a Kubernetes service registry/API) at request time or on a refresh interval, automatically picking up new service instances as they're registered and removing ones that have deregistered or failed health checks — without requiring manual gateway configuration changes every time the underlying backend topology shifts.

**Q9. Why does dynamic routing matter particularly in containerized/microservices environments with frequent deployments and autoscaling?**
A: In such environments, the actual set of healthy backend instances behind any given service can change frequently and automatically — autoscaling adding/removing instances based on load, rolling deployments replacing instances continuously, instances failing and being replaced by orchestration. A gateway relying on static, manually-maintained configuration would either become stale almost immediately (routing to instances that no longer exist, or missing newly-scaled-up instances) or require an unsustainable amount of manual upkeep to stay current — dynamic, service-discovery-integrated routing is effectively a requirement, not a nice-to-have, once the backend topology is this fluid.

**Q10. How does API Gateway routing in a Kubernetes context typically integrate with the cluster's own service discovery?**
A: Many API Gateway products either implement the Kubernetes Ingress or Gateway API specification directly, or run as a controller that watches the Kubernetes API for Service/Endpoint changes and automatically reconfigures its own routing rules in response — meaning routing configuration is often expressed declaratively as Kubernetes resources (Ingress objects, or newer Gateway API resources like HTTPRoute) rather than gateway-vendor-specific configuration files, and the gateway stays continuously synchronized with the cluster's actual current service topology without manual intervention, leveraging Kubernetes' own service discovery (backed by its internal DNS and endpoint tracking) as the source of truth.

**Q11. What's an operational risk specifically introduced by dynamic, auto-updating routing configuration, compared to static configuration?**
A: A misconfigured or buggy service registration (a service incorrectly registering itself under the wrong name, or a faulty health check incorrectly marking healthy instances as unhealthy and deregistering them) can immediately and automatically propagate into live routing changes, with no human review step in between — unlike static configuration, where a routing change requires someone to deliberately edit and deploy a configuration change, providing a natural (if imperfect) review checkpoint. This is generally an accepted trade-off given the operational necessity in dynamic environments (Q9), but it does mean the service registry and health-check logic itself becomes a more security/correctness-critical piece of infrastructure than it might first appear, since errors there translate directly and automatically into routing behavior.

## Section 4: Advanced Routing Patterns

**Q12. What is canary routing, and how is it typically implemented at the gateway?**
A: Canary routing directs a small percentage of traffic to a new version of a service (the "canary") while the majority continues to the existing, stable version — allowing the new version to be validated against real production traffic at low risk before a full rollout. Implemented at the gateway typically via weighted routing rules, similar in concept to weighted DNS routing but applied per-request at the gateway layer rather than at the DNS resolution layer — e.g., 95% of requests matching a given route continue to the stable deployment, 5% are routed to the canary deployment, with that percentage gradually increased as confidence in the canary builds.

**Q13. How does gateway-level canary/weighted routing differ in practical behavior from DNS-based weighted routing?**
A: Because the gateway makes a fresh routing decision on every single request that passes through it (it's in the actual data path, unlike DNS), the configured weight is reflected accurately and immediately on a per-request basis — there's no client-side caching or stickiness delaying convergence to the configured split, unlike DNS-based weighted routing, where each client effectively locks into whichever record they resolved until their cache expires. This makes gateway-level weighted/canary routing meaningfully more precise and immediately responsive to weight changes than the DNS-layer equivalent.

**Q14. What is blue-green deployment, and how does its routing pattern differ from canary?**
A: Blue-green deployment maintains two complete, parallel production environments ("blue" — currently live, and "green" — the new version, fully deployed and validated but not yet receiving production traffic), with the cutover happening as a single, instantaneous routing switch from blue to green once the green environment is confirmed ready — rather than canary's gradual, percentage-based traffic shift. The routing change itself is simple (a single all-or-nothing switch rather than a gradually adjusted weight), but blue-green requires running two complete, full-capacity environments simultaneously during the transition, whereas canary only needs the new version sized for the small fraction of traffic it initially receives — a real infrastructure-cost trade-off between the two patterns.

**Q15. What is traffic mirroring (also called shadowing), and what's it used for?**
A: The gateway duplicates incoming requests, sending the original to the actual production backend as normal while sending a copy of the same request to a separate, typically new or experimental backend — without that mirrored backend's response ever being returned to the real client (the mirrored response is usually just logged/compared, not actually used). This is used to validate how a new service version or backend implementation behaves against genuine, real production traffic patterns with zero risk to actual users, since the mirrored backend's behavior, even if completely broken, never affects what the real client receives.

**Q16. What's an important caveat to be aware of when using traffic mirroring with requests that have side effects (e.g., writes, payments, sending emails)?**
A: Mirroring a request that triggers a real side effect (a database write, an email send, a payment charge) on the mirrored backend means that side effect genuinely happens a second time, in addition to the real one — which can cause real, harmful duplication (double-charging a customer, sending a duplicate notification email) if the mirrored backend isn't carefully isolated or configured to safely no-op/sandbox such side effects. Traffic mirroring is safest and most commonly used for read-heavy or idempotent operations, or specifically configured so the mirrored backend operates against an isolated environment/sandboxed dependencies (a test payment provider, a non-production email service) rather than genuinely live, side-effect-producing infrastructure.

## Section 5: Routing and Resilience Interplay

**Q17. How do per-route timeout configurations interact with routing decisions?**
A: Different routes commonly warrant different timeout values, since different backend operations have genuinely different expected latency profiles — a simple lookup endpoint might reasonably warrant a tight timeout (a few hundred milliseconds), while a report-generation or bulk-export endpoint might legitimately need a much longer allowance. Configuring a single, uniform timeout across all routes regardless of their actual expected behavior tends to either be too aggressive for genuinely slow-but-legitimate operations (causing spurious failures) or too lenient for fast operations (allowing a slow/stuck backend to hold gateway resources open far longer than that route should ever realistically need), which is why timeout configuration is typically scoped per-route rather than globally uniform.

**Q18. What is fallback routing, and when is it used?**
A: Fallback routing configures an alternate destination (a backup service, a cached/static response, or a degraded-but-functional alternative) to route to when the primary destination for a given route is unavailable or has tripped a circuit breaker — rather than simply returning an error to the client outright. This is used where a degraded-but-present response is meaningfully better for the client experience than an outright failure — e.g., falling back to a slightly stale cached version of a recommendations list if the live recommendations service is down, rather than showing the client nothing at all.

**Q19. How does retry behavior interact with routing when multiple backend instances exist behind a single logical route?**
A: A well-designed gateway's retry logic, on a failed attempt to one specific backend instance, should generally retry against a *different* instance of the same service (if multiple healthy instances are available) rather than blindly retrying the exact same instance that just failed — since retrying the identical instance that already failed is far less likely to succeed than trying a different, potentially healthy instance, especially if the failure was instance-specific (a single bad node) rather than a problem affecting the entire service uniformly. This requires the routing layer and retry logic to be integrated closely enough that a retry attempt can be informed by "which instance was already tried and failed," not just "retry the same logical route again."

## Section 6: Operational Considerations

**Q20. What is route precedence/specificity, and why does it matter when multiple configured route patterns could match the same incoming request?**
A: When a gateway has multiple route rules configured, more than one can sometimes structurally match a given incoming request (e.g., a general `/api/*` catch-all route and a more specific `/api/orders/*` route both technically match a request to `/api/orders/123`) — route precedence is the deterministic rule the gateway uses to decide which single match actually wins. Most gateways apply a "most specific match wins" principle (the longer/more specific path prefix takes priority over a broader catch-all), but the exact precedence rules vary by product, and misunderstanding them is a common source of "why is my request going to the wrong service" debugging sessions — explicitly understanding and testing precedence behavior, rather than assuming intuitive behavior, matters for any non-trivial route configuration.

**Q21. What's a common operational pitfall with route configuration as a system grows to have many routes managed by many different teams?**
A: Configuration sprawl and conflict risk — as the number of routes grows and ownership becomes distributed across teams, the chance of two teams unintentionally configuring overlapping or conflicting route patterns (a new team's route accidentally shadowing or being shadowed by an existing one due to precedence rules they weren't fully aware of, per Q20) increases, and without some form of validation, review process, or namespacing convention (e.g., requiring routes to be scoped under a team-specific path prefix), this can silently break existing functionality when a new, broader-matching route is introduced. Larger organizations commonly address this with declarative, version-controlled route configuration (reviewed via normal code-review processes), automated conflict/overlap detection in CI before a route change is deployed, and clear path-prefix ownership conventions.

**Q22. How does route-matching performance scale as the number of configured routes grows, and what should you be aware of?**
A: Naive linear scanning through every configured route pattern on every single incoming request would scale poorly as the route count grows into the hundreds or thousands, adding latency to the hot path of every request. Production-grade gateways typically use more efficient matching structures internally (trie-based path matching, compiled/indexed rule sets) specifically to keep route resolution fast and roughly constant-time-ish even with large route tables — but this is implementation-dependent across different gateway products, and it's worth being aware that not all routing-rule configurations are equally cheap to evaluate (e.g., complex regex-based path matching is generally more expensive than simple prefix matching), which can matter at very high request volumes or very large route counts.

**Q23. What should be monitored specifically with respect to routing behavior in production?**
A: Per-route latency and error rate (distinguishing which specific routes/backends are experiencing problems, rather than only system-wide aggregate metrics that could mask a problem isolated to one route among many healthy ones); routing-rule match rates and any requests falling through to an unexpected default/catch-all route (which can indicate a misconfigured or missing route pattern that legitimate traffic is unintentionally hitting); and, for dynamic/service-discovery-based routing specifically, the health and freshness of the underlying service registry data the gateway is routing against, since stale or incorrect registry data translates directly into incorrect routing decisions.

## Section 7: Scenario-Based Questions

**Q24. "After adding a new, broadly-matching route (`/api/*` forwarding to a new general-purpose service), an existing, more specific route (`/api/orders/*`) stopped receiving traffic — all requests to it are now going to the new general-purpose service instead. What happened, and how do you fix it?"**
A: This is a route precedence/specificity issue (Q20) — depending on how the gateway resolves overlapping matches, the newly added broad `/api/*` route may be evaluated (or simply registered) in a way that's now matching and intercepting requests before the more specific `/api/orders/*` route gets a chance to match, even though the more specific route is the intuitively "correct" one for those requests. The fix is ensuring the gateway's configuration explicitly reflects the intended precedence — either by relying on (and verifying) the gateway's most-specific-match-wins behavior if it supports that natively, or by explicitly ordering/prioritizing routes in configuration if the gateway resolves conflicts by configuration order rather than automatic specificity — and adding this scenario to whatever validation/testing process exists for route changes going forward (Q21), so a similarly broad route added later doesn't silently repeat the same problem.

**Q25. "You're rolling out a new version of a critical backend service and want to validate it against real production traffic with minimal risk before fully committing to it. Compare your options and recommend an approach."**
A: Three reasonable options, with different risk/cost profiles: traffic mirroring (Q15–16) gives the lowest direct risk to real users, since the mirrored backend's responses are never actually returned to clients, but it requires the new version to safely handle real production request volume without affecting any real side effects (a real concern if the service involves writes, per Q16), and it doesn't validate the *response* the new version would actually produce in a way real users experience. Canary routing (Q12–13) actually exposes a small, controlled fraction of real users to genuine responses from the new version, providing more complete end-to-end validation (including response correctness, not just "did it crash") at the cost of some real users genuinely being affected if the new version has a bug. Blue-green (Q14) provides the cleanest all-or-nothing cutover with easy instant rollback, but requires running full parallel capacity and doesn't get the gradual, real-traffic validation canary provides. For a critical service, a reasonable recommendation: start with mirroring to validate basic stability/non-crashing behavior against real traffic shape with zero user risk, then proceed to a gradually-increasing canary rollout for genuine end-to-end validation with bounded blast radius, reserving blue-green-style instant full cutover for the final, already-validated promotion step.

**Q26. "Your gateway routes requests to backend services using a static, hardcoded list of service IPs in its configuration. As the team adopts Kubernetes with autoscaling, routing starts intermittently failing — some requests succeed, others get connection errors, seemingly at random." How would you diagnose and fix this?**
A: This is the static-vs-dynamic routing mismatch described in Q8–9 — the hardcoded IP list in the gateway's configuration goes stale the moment Kubernetes' autoscaling or rolling deployments change the actual set of running pod IPs behind a service, since nothing is keeping the gateway's static configuration in sync with the cluster's actual live topology. Some configured IPs end up pointing at pods that have since been terminated (causing connection errors), while newly-scaled-up pods never receive any traffic at all because they were never added to the static list. The fix is moving to dynamic, service-discovery-integrated routing — having the gateway either implement/consume the Kubernetes Ingress or Gateway API directly, or otherwise continuously watch the cluster's actual service/endpoint state (Q10) — so routing automatically and correctly reflects the live, current set of healthy backend instances rather than a manually-maintained, inevitably-stale static list.

**Q27. "A new API version (`/v2/orders`) needs to be introduced alongside the existing `/v1/orders`, with the eventual goal of deprecating v1. How would you structure the routing, and what would you keep in mind for the deprecation phase?"**
A: Structure routing with explicit path-based version prefixes (Q6), each routed independently — `/v1/orders/*` continuing to route exactly as it does today, `/v2/orders/*` routed to whatever new backend deployment or updated internal logic implements the new version (per the separate-deployment-vs-same-deployment trade-off in Q7, decided based on how substantially the v2 implementation actually differs). For the deprecation phase: keep per-route observability (Q23) specifically on the `/v1/orders/*` route to track real, ongoing usage over time (rather than assuming it's safe to remove once announced), consider adding deprecation-signaling response headers (e.g., a `Sunset` header) on v1 responses to proactively warn remaining clients, and only fully remove v1 routing once usage has genuinely dropped to an acceptable level or a committed deprecation deadline has passed — treating route removal as a deliberate, monitored, gradual process rather than an abrupt cutoff that could break clients who haven't yet migrated.

**Q28. "Your team wants to gradually shift a fraction of traffic for a specific route to a new region's backend deployment, increasing the percentage over time, while keeping the ability to immediately and precisely halt the shift the moment an error spike is detected. Would you implement this via DNS-based weighted routing or gateway-level weighted routing, and why?"**
A: Gateway-level weighted routing is the better fit here specifically because of the "immediately and precisely halt" requirement — since the gateway makes a fresh routing decision on every request (Q13), a weight change takes effect on the very next request evaluated, with no client-side caching delay to wait out, unlike DNS-based weighted routing, where already-resolved clients remain pinned to their previous answer until their cache naturally expires, meaning a sudden weight change (including dropping it back to zero in response to an error spike) wouldn't actually stop traffic to the problematic destination as quickly as the requirement demands. DNS-based weighted routing remains a reasonable choice for coarser, slower-moving traffic shifts where immediate precision isn't the priority, but for this specific requirement, gateway-level (in-path) weighted routing is the right tool.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Routing match attributes | Path, host, method, headers — path is most common |
| Path rewriting | Strips/transforms the matched prefix before forwarding to the backend |
| API versioning | Path-based most common; header-based and host-based also used |
| Static routing | Hardcoded backend addresses; goes stale in dynamic environments |
| Dynamic/service-discovery routing | Gateway syncs with a live registry (Consul, Kubernetes); required at scale |
| Canary routing | Gradual, weighted traffic shift to a new version; precise, per-request |
| Blue-green | Instant full cutover between two complete parallel environments |
| Traffic mirroring | Duplicates requests to a new backend with no client-facing effect; risky with side effects |
| Per-route timeouts | Scoped per route to match each operation's real expected latency |
| Fallback routing | Routes to a backup/degraded response when the primary destination fails |
| Route precedence | Most-specific-match-wins (or config-order); a common source of routing bugs |
| Route matching performance | Trie/indexed structures keep matching fast at scale; not all match types are equally cheap |

**Tip for interviews:** What separates strong candidates on API Gateway request routing specifically: (1) being able to clearly explain **why dynamic, service-discovery-based routing becomes a near-requirement** (not just a nice-to-have) in containerized/autoscaling environments, and what concretely breaks with static configuration there (Q8–9, Q26); (2) comparing **canary, blue-green, and traffic mirroring** with a clear sense of their actual risk/cost trade-offs rather than treating them as interchangeable rollout buzzwords — especially the side-effect caveat with mirroring (Q12–16, Q25); (3) understanding precisely **why gateway-level weighted routing converges faster and more precisely than DNS-based weighted routing**, tying back to the in-path-vs-out-of-path distinction (Q13, Q28); (4) being able to reason through a **route precedence/specificity bug** concretely — this is one of the most common real-world gateway debugging scenarios (Q20, Q24); and (5) knowing that **per-route timeout and retry configuration**, not a single global setting, is the correct default posture, since different routes have genuinely different latency and failure characteristics (Q17, Q19).
