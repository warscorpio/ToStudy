# Consul: Service Discovery — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Consul, and what problems is it designed to solve?**
A: Consul is a distributed system tool built by HashiCorp that provides several closely-related capabilities: service discovery (a registry of which service instances currently exist and are healthy), health checking (actively probing registered services and removing unhealthy ones from the registry), a distributed key-value store (for dynamic configuration and coordination), and service mesh capabilities (mTLS-based service-to-service communication via Consul Connect). It was designed to solve the operational problems of large, dynamic infrastructure: services need to find each other without hardcoded addresses, health state needs to be maintained in real time, and configuration needs to be distributed consistently across many nodes without manual propagation. Consul's particular architectural emphasis is on being operationally simple to run while being robust in the face of partial network failures — its gossip-based membership protocol means it handles node failures gracefully without requiring a fully-connected topology.

**Q2. What makes Consul distinct from simpler service discovery tools like DNS or etcd used directly?**
A: Several things distinguish Consul as a purpose-built service discovery system: its agent-based health-checking model (health checks run *on the same node as the service*, giving them direct local access to the service rather than requiring network probes from a central location, which means a health check can test things a remote probe can't — like reading a local file, running a script, or checking a local socket); its dual interface for discovery (both DNS and HTTP API, so existing applications using DNS can discover services without code changes, while more sophisticated clients use the rich HTTP API); its built-in awareness of datacenter topology (services can be registered as belonging to a specific datacenter, and queries can be scoped to a datacenter or crossed across datacenters); and its combination of service discovery with a KV store and service mesh capabilities in one coherent system, rather than requiring separate tools for each concern.

**Q3. What are the two primary roles a Consul agent can run as, and what does each do?**
A: Every node running Consul runs a **Consul agent**, which operates in one of two modes: **server mode** or **client mode**. Server agents form the cluster's control plane — they participate in the Raft consensus protocol, maintain the authoritative state of all registered services, health check results, and KV data, and are responsible for ensuring that state is consistently replicated and persisted across the server cluster. Client agents run on every non-server node (every application host or pod) and serve as the local interface for services on that node — forwarding registration and discovery queries to the server cluster on behalf of local services, running health checks locally for locally-registered services, and caching some state to reduce load on the server cluster. The client agent is the component that service code and SDKs on that node communicate with (via localhost), rather than calling the server agents directly.

## Section 2: Consul Architecture

**Q4. How does Consul use Raft consensus, and why is it important to service discovery correctness?**
A: The Consul server agents form a Raft consensus cluster — one server is elected leader, and all writes (service registrations, deregistrations, health-check state changes, KV updates) flow through the leader, which replicates them to a quorum of followers before acknowledging success. This guarantees that the service registry's state is consistent and durable — a write acknowledged by Consul is persisted on a majority of servers, so it survives the failure of any minority of servers without data loss. For service discovery specifically, this means the registry reflects a consistent, agreed-upon view of which services are registered and healthy, not potentially diverged views across different servers — a correctness guarantee that's important because clients routing traffic based on discovery results need to trust that those results are accurate, not artifacts of inconsistent state.

**Q5. What is the gossip protocol in Consul, what does it handle, and how is it different from Raft?**
A: Consul uses two distinct protocols for two distinct concerns. Raft handles **data consensus** — ensuring server agents agree on the authoritative state of the registry, KV store, and ACLs. The gossip protocol (based on HashiCorp's Serf library) handles **membership and failure detection** — propagating information about which nodes are alive or dead across the entire cluster (including both server and client agents) via epidemic-style random peer communication. When a node goes down, the gossip protocol detects it quickly (via heartbeat failure propagation through the gossip network) and notifies the Raft servers, which can then trigger deregistration of services that were registered on that failed node. Gossip is designed to work well in large, partially-connected topologies where maintaining direct connections between every pair of nodes would be impractical — each node only needs to communicate with a small, random subset of peers, and information propagates exponentially to all nodes within a small number of rounds.

**Q6. How many server agents should a production Consul cluster run, and why?**
A: Three or five server agents, depending on the desired fault tolerance. Raft requires a quorum (majority) of servers to be alive to accept writes and serve reads — a cluster of 3 can tolerate 1 server failure (since 2 of 3 is still a quorum); a cluster of 5 can tolerate 2 failures. More than 5 servers is generally counterproductive — each additional server increases the write latency (more nodes must acknowledge each write to form a quorum) without increasing fault tolerance meaningfully beyond what 5 servers already provide. The common production choice between 3 and 5 depends on whether the organization can tolerate one simultaneous server failure (three-node cluster is adequate) or needs to tolerate two (five-node cluster is necessary — relevant during maintenance windows where one server is intentionally taken down for upgrades, protecting against an unplanned failure during that window).

**Q7. What is the difference between a Consul datacenter and a Consul cluster?**
A: In Consul's terminology, a **datacenter** is the fundamental unit of independent Raft consensus — one datacenter has one Raft server cluster with its own elected leader, maintaining its own authoritative state. All agents (servers and clients) within a datacenter participate in the same gossip pool and share the same consistent state. A **cluster** and a **datacenter** are essentially synonymous in Consul's model — there is one Raft cluster per datacenter. Multiple datacenters can be joined via WAN federation (Q23), allowing cross-datacenter service discovery queries, but each datacenter remains independently governed by its own Raft cluster rather than forming one global Raft cluster across all datacenters (which would be impractical given the latency involved in WAN Raft consensus).

## Section 3: Service Registration

**Q8. What are the two ways to register a service with Consul, and what are the trade-offs?**
A: **Configuration-file-based registration**: a service definition file (JSON or HCL) placed in the Consul agent's configuration directory specifies the service's name, ID, address, port, tags, and health-check configuration — the agent reads this file on startup and registers the service automatically. Simple, declarative, and version-controllable, but requires the file to be present on the host before the agent starts, and registering a new service requires placing the file and either restarting or signaling the agent. **API-based registration**: a `PUT` to the local Consul client agent's HTTP API (`/v1/agent/service/register`) registers the service dynamically at runtime — used by service processes that register themselves on startup (self-registration) or by deployment orchestrators that register services on behalf of newly started instances (third-party registration). More dynamic (no file placement needed, no agent restart) but requires explicit deregistration on shutdown or reliance on health-check-based culling for cleanup.

**Q9. What information does a Consul service definition contain, and what parts are most operationally important?**
A: A service definition includes: **name** (the logical service name, used as the primary lookup key for discovery — `orders-service`); **ID** (a per-instance unique identifier, defaulting to the name but should be unique when multiple instances of the same service run on the same node); **address and port** (the actual network endpoint clients should connect to — if address is omitted, Consul uses the agent's own node address); **tags** (arbitrary strings for filtering and metadata — `v2`, `primary`, `us-east-1` — used in queries to select a subset of instances); **meta** (key-value metadata, richer than tags, for structured service metadata); and **health checks** (one or more health check definitions, Q11). The name and health checks are the most operationally critical: an incorrect name means the service is undiscoverable under the expected lookup key, and missing or incorrectly configured health checks mean unhealthy instances remain in the registry indefinitely.

**Q10. What is the Consul service catalog, and what is the difference between it and the agent's local registry?**
A: The **service catalog** is the global, consistent, Raft-replicated view of all registered services across the entire datacenter — maintained by the server agents and queryable via the catalog API (`/v1/catalog/*`). The **agent's local registry** is each client agent's record of services registered on its own node — when a service registers with a local client agent, the client agent forwards that registration to the server cluster for inclusion in the catalog, but also maintains its own local record for the purpose of running that service's health checks locally. The distinction matters operationally: a service appearing in the agent's local state but not yet in the catalog indicates a propagation lag or a server communication failure; querying the catalog API gives the authoritative, globally-consistent view, while querying the agent API gives the local view, which is fresher for locally-registered services but not global.

## Section 4: Health Checking

**Q11. What types of health checks does Consul support, and what are the appropriate use cases for each?**
A: **Script/command checks**: the Consul agent runs a configured shell command or script at a defined interval; the exit code determines the health status (0 = passing, 1 = warning, non-zero = failing) — extremely flexible, can test anything a script can test (filesystem state, internal process queues, external dependency reachability from the local node), but requires the script to exist on the agent's host and appropriate permissions for the agent to execute it. **HTTP checks**: the agent makes an HTTP GET to a configured URL at an interval; any 2xx response is passing, 429 Too Many Requests is warning, anything else is failing — the most common check type for HTTP/REST services, with the check endpoint typically being a dedicated `/health` or `/ready` endpoint the service exposes. **TCP checks**: the agent attempts a TCP connection to a configured address and port; a successful connection is passing — useful for services that don't speak HTTP but can be validated by their ability to accept a TCP connection. **TTL checks**: instead of the agent probing the service, the *service itself* is responsible for periodically sending a heartbeat to the agent's API (`PUT /v1/agent/check/pass/<check_id>`) to declare itself healthy; if no heartbeat is received within the configured TTL window, the check fails — useful for background jobs or services where external probeability is architecturally impractical. **gRPC checks**: the agent uses the gRPC health checking protocol to check a gRPC service's health status — purpose-built for gRPC services, cleaner than a generic TCP check for this protocol.

**Q12. What is the health-check state machine in Consul, and what statuses can a check be in?**
A: A Consul health check has three possible states: **passing** (the last check succeeded), **warning** (an intermediate degraded state, supported by some check types like HTTP returning 429 or a script exiting 1 — the service is still returned in discovery queries by default but is flagged), and **critical** (the check is failing — a service with any check in critical state is excluded from discovery results for healthy-service queries, though still visible in the catalog). This three-state model (rather than a binary pass/fail) allows for graceful degradation: a service in warning state can still receive traffic while an operator investigates, without requiring the binary choice of "fully in rotation" or "fully removed."

**Q13. How do health checks interact with discovery results — specifically, what does querying for "healthy" instances actually filter on?**
A: When a client queries Consul for service instances (either via DNS or the HTTP API), the default behavior returns only instances whose **all registered checks are currently passing** — both service-level checks (specific to that service) and node-level checks (monitoring the health of the entire Consul node itself, like the `Serf Health Status` check that reflects gossip-based liveness). A service can pass its own HTTP health check but still be excluded from discovery results if the node-level health check is failing (e.g., the Consul agent itself has lost connectivity to the rest of the cluster, which gossip detects). This design is intentional: a service running on a node that's having infrastructure-level problems (network partition, disk failure) should be excluded from traffic even if the service's own `/health` endpoint is still responding, because the node's broader health is a real signal about the reliability of traffic routed there.

## Section 5: Service Discovery — DNS Interface

**Q14. How does Consul's DNS interface work for service discovery, and what query formats does it support?**
A: Consul runs a DNS server (by default on port 8600 on each agent node) that resolves Consul-specific DNS names to service instance addresses, allowing any DNS-capable application to discover services without SDK integration. The primary query format is `<service-name>.service.consul` — for example, `orders-service.service.consul` — which returns A records (one per healthy instance's IP) for all healthy instances of that service. Additional query formats allow filtering: `<tag>.<service-name>.service.consul` filters to only instances tagged with the specified tag (e.g., `primary.orders-service.service.consul` for instances tagged `primary`). SRV record queries return both the address *and* the port (plus priority and weight), which is important for services not on a standard port — A records return IPs only, so if different instances of the same service run on different ports, SRV queries are the appropriate interface. Datacenter-specific queries are possible via `<service-name>.service.<datacenter>.consul`.

**Q15. How do applications typically reach Consul's DNS server, given that it runs on port 8600 rather than the standard DNS port 53?**
A: Several integration patterns: configure the operating system's DNS resolver to forward queries for the `.consul` domain specifically to `127.0.0.1:8600` (via `dnsmasq`, `systemd-resolved` split-horizon configuration, or `/etc/resolv.conf` `nameserver` entry with a stub zone) — this is the most transparent approach, as applications resolve `.consul` names via completely ordinary DNS calls without knowing Consul is involved. Alternatively, configure the system DNS to have Consul's agent as a forwarder for `.consul` queries while routing all other DNS normally. In Kubernetes specifically, CoreDNS can be configured to forward queries for `.consul` to a Consul agent, bridging Kubernetes DNS-based service discovery with Consul's registry for hybrid VM/Kubernetes environments.

**Q16. What are the limitations of Consul's DNS interface compared to its HTTP API for service discovery?**
A: DNS returns only addresses and (via SRV) ports — it cannot return richer metadata (service tags beyond the single-tag filter, meta key-values, health check details, geographic information). DNS is also subject to client-side TTL-based caching (the same limitations discussed in the DNS guides), meaning recently-unhealthy instances may still be returned for queries that hit a cached result before the TTL expires. The HTTP API, by contrast, returns full service metadata, supports complex filtering expressions (queries filtering on multiple tags, node metadata, or service metadata simultaneously), supports blocking queries (long-poll that waits until the state changes before returning), and bypasses client-side TTL caching concerns entirely. For applications that need more than "give me a healthy address," the HTTP API (or a client library that wraps it) is the appropriate interface.

## Section 6: Service Discovery — HTTP API

**Q17. What are the key Consul HTTP API endpoints for service discovery, and what does each return?**
A: The primary discovery-oriented endpoints: **`/v1/health/service/<service-name>`** returns instances of the named service with full health status detail — the most commonly used discovery endpoint, accepting query parameters like `passing=true` (filter to only healthy instances), `tag=<tag>` (filter by tag), and `dc=<datacenter>` (query a specific datacenter). **`/v1/catalog/service/<service-name>`** returns all registered instances of a service from the catalog, regardless of health status — useful for administrative inspection but typically not appropriate for traffic routing, since it includes unhealthy instances. **`/v1/agent/services`** returns only the services registered on the local agent node — the local view, not the global catalog view. The distinction between the health and catalog endpoints (Q10) matters: routing clients should use the health endpoint with `passing=true`; the catalog endpoint is for inspection and operational tooling.

**Q18. What is a Consul blocking query, and why is it particularly valuable for service discovery clients?**
A: A blocking query is Consul's implementation of long-polling: when making an HTTP API request, a client passes the `index` parameter (the Consul cluster's current modification index for the queried resource) and an optional `wait` timeout — Consul holds the connection open until either the resource's state changes (its index advances past the provided value) or the wait timeout elapses, then returns immediately with the updated result. For a service discovery client, this means instead of polling the Consul API on a fixed interval (e.g., every 30 seconds, potentially missing rapid changes or generating unnecessary load during stable periods), the client can maintain one blocking query connection that returns immediately whenever the service's healthy instance set changes — getting near-real-time updates with far fewer unnecessary requests during stable periods. This is fundamentally more efficient and more responsive than TTL-based polling, and is how well-implemented Consul-native service discovery clients (including Consul Template, envconsul, and the Consul SDK) operate.

## Section 7: Key-Value Store

**Q19. What is the Consul KV store, and how is it commonly used alongside service discovery?**
A: Consul's KV store is a simple, hierarchically-organized distributed key-value database backed by the same Raft consensus infrastructure as the service catalog — keys are arbitrary strings (with `/`-separated path conventions for organization), values are arbitrary byte blobs up to 512KB. Common uses alongside service discovery: dynamic configuration that needs to be distributed to running services without restart (feature flags, rate limit values, connection pool sizes — a service watches a KV path via blocking query and picks up changes in near-real-time); leader election coordination (multiple instances of a service use Consul KV sessions and locks to elect a primary without an external coordination service); and service routing configuration (the routing policies or weights for traffic management expressed as KV values that the gateway or load balancer reads dynamically). The key distinction from the service catalog: the KV store is general-purpose and schema-free; the service catalog is structured specifically around the service/node/check data model.

**Q20. What are the size and use-case limitations of the Consul KV store?**
A: The 512KB per-value limit makes it unsuitable for storing large blobs (application binaries, large config files, binary data) — it's designed for small configuration values, not bulk data storage. Because all KV data is replicated via Raft across all server nodes, storing very large amounts of data in the KV store increases memory pressure on server agents and write latency (each write must be replicated through consensus, so high write throughput to the KV store can affect Raft performance and latency for service registration/deregistration operations that share the same Raft log). For anything beyond small, frequently-changing configuration values, a purpose-built configuration store (Vault for secrets, a dedicated config service) is more appropriate, with Consul KV reserved for the lightweight coordination and configuration use cases it's actually designed for.

## Section 8: Consul Connect and Service Mesh

**Q21. What is Consul Connect, and how does it extend Consul beyond basic service discovery?**
A: Consul Connect is Consul's built-in service mesh capability — it enables authorized, mTLS-encrypted service-to-service communication where Consul acts as the certificate authority (issuing and rotating certificates for each service's identity) and enforces access control via **intentions** (a policy layer specifying which services are allowed to communicate with which other services, independently of network-level firewall rules). Each service participates via a sidecar proxy (typically Envoy) registered alongside it, which handles the mTLS termination and intention enforcement transparently to the application — following the same sidecar/server-side discovery model discussed in the service mesh section of the client-side vs server-side discovery guide. Consul Connect directly addresses the "how do I ensure service A is actually talking to the real service B and not an impersonator" and "how do I control which services are allowed to call which other services" problems that plain service discovery leaves entirely to network-level controls.

**Q22. What is a Consul intention, and how does it differ from a network-level firewall rule?**
A: An intention is a Consul-level policy rule specifying whether service A is allowed to communicate with service B — expressed in terms of Consul service names and identities (backed by mTLS certificates), not IP addresses or network topology. Unlike a firewall rule, intentions work regardless of how the network is structured, travel with the services as they move across infrastructure, and are enforced at the sidecar proxy level on every connection — meaning a misconfigured firewall that accidentally allows network connectivity between services doesn't also allow them to successfully complete an mTLS handshake if no intention permits it (since the certificates establish the identities and the sidecar enforces the intention against those identities). Intentions are also far more human-readable and service-topology-aware than firewall rules: `deny orders-service → payment-service` is immediately meaningful; the equivalent IP-range firewall rules require knowing the exact current IP ranges of each service, which change constantly in dynamic environments.

## Section 9: Multi-Datacenter Consul

**Q23. How does Consul support multi-datacenter service discovery, and what are its limitations?**
A: Multiple Consul datacenters can be joined via **WAN federation** — server agents in different datacenters establish WAN gossip connections with each other, allowing cross-datacenter service discovery queries. When a client queries for a service specifying a remote datacenter (`orders-service.service.us-west-2.consul` or `?dc=us-west-2` on the HTTP API), the local datacenter's server agents forward that query to the specified datacenter's server agents and return the result. Limitations: cross-datacenter queries are not highly available (they depend on WAN connectivity between datacenters), introduce WAN latency into the query path, and are effectively read-forwarding rather than true replication — there's no automatic failover "if the primary datacenter is down, return instances from the secondary datacenter" built into basic WAN federation, which requires additional tooling or Consul Enterprise's prepared queries with failover capabilities.

**Q24. What is Consul's "prepared query" feature, and when is it valuable?**
A: A prepared query is a named, reusable query stored in Consul that encodes not just what to find but *how to find it*, including fallback behavior — for example, "find healthy instances of the orders-service in this datacenter; if none are healthy, failover to the us-west-2 datacenter and return healthy instances there instead." This cross-datacenter failover behavior is not available from a simple DNS or API query targeting one datacenter explicitly — it requires the fallback logic to be encoded somewhere, and prepared queries are Consul's built-in mechanism for this. They're particularly valuable for multi-datacenter active-passive setups where the primary datacenter serves traffic normally and a secondary datacenter should automatically absorb traffic when the primary's service becomes unavailable, expressed as a single stable query name that clients use regardless of which datacenter is currently serving.

## Section 10: Security — ACLs

**Q25. What is Consul's ACL system, and why is it critical in production?**
A: Consul's Access Control List (ACL) system controls which agents and clients are allowed to read from or write to the service catalog, KV store, intentions, and other Consul resources — using tokens that are issued to agents, services, and human operators, each with a policy defining exactly what operations they're permitted. In production, the ACL system is critical because without it, any node in the network that can reach the Consul agent's API can read the full service registry (learning the addresses of every internal service — a significant information leakage) or, more damagingly, write to it (registering fake services, deregistering real ones, or modifying KV configuration) — the same unauthorized-write-access concern highlighted in the service discovery guide's security section. ACLs should be enabled by default in any production deployment; running a production Consul cluster without ACLs enabled is a significant security posture failure.

**Q26. What is the ACL bootstrap process, and what is the "initial management token"?**
A: When ACLs are first enabled on a Consul cluster (or a new cluster is initialized with ACLs), the cluster generates a single all-powerful **initial management token** (the bootstrap token) via the `consul acl bootstrap` command — this token has unrestricted access to all Consul APIs and is intended solely for initial setup (creating more narrowly-scoped tokens for individual agents, services, and operators). The initial management token should be stored securely (in a secrets manager like Vault, not in plaintext configuration files), and its use should be limited to administrative bootstrapping operations — the operational equivalent of a root password for the Consul cluster. Individual services and agents should use their own narrowly-scoped tokens rather than the management token, applying the principle of least privilege (Q29 in the API Gateway auth guide) to Consul access just as anywhere else.

## Section 11: Operational Considerations

**Q27. What are the most common operational failure modes in a Consul cluster, and how are they diagnosed?**
A: **Loss of quorum**: if more than half the server agents become unavailable simultaneously, the Raft cluster loses quorum and can no longer process writes — the cluster enters a read-only-ish degraded state where existing registrations are preserved but new registrations, deregistrations, and health-check state changes can't be committed. Diagnosed via `consul operator raft list-peers` and the absence of a current leader in `consul info`. **Flapping health checks**: a health check that oscillates rapidly between passing and failing (a service under temporary load, a network hiccup causing intermittent check failures) can cause a service to be rapidly added and removed from discovery results, causing erratic traffic routing — mitigated with check `DeregisterCriticalServiceAfter` settings and appropriate check intervals/timeouts. **Gossip ring partition**: client agents losing gossip connectivity to server agents won't get timely health-check state updates and may cache stale registration state — diagnosed by monitoring the gossip member count and watching for agents going `failed` in `consul members`.

**Q28. What should be monitored in a production Consul deployment?**
A: Leadership stability and Raft consensus health (leader election events should be rare — frequent re-elections indicate instability, often from network issues between server agents or resource contention on server nodes); Raft commit latency (how long writes take to be committed through consensus — elevated commit latency signals server node overload or degraded network between servers); gossip member health (the count of `alive`, `failed`, and `left` members — growing `failed` count indicates nodes not cleanly deregistering or losing connectivity); health check failure rates per service (an unexpected spike in a service's critical check rate can indicate an application issue, a misconfigured check, or an infrastructure problem on those nodes); and ACL token expiry if tokens with TTLs are in use (expired tokens cause suddenly-rejected Consul API calls that can be difficult to trace without monitoring token expiry proactively).

**Q29. What is Consul Template, and where does it fit in a Consul-based service discovery architecture?**
A: Consul Template is a daemon that watches Consul's service catalog and KV store (via blocking queries, Q18) and renders templates to disk whenever the watched state changes — typically used to dynamically regenerate configuration files (like HAProxy or nginx upstream configurations) based on the current set of healthy service instances, then signal the configured application to reload its configuration. It bridges Consul's discovery system with applications that don't natively understand Consul's API but do support reloading from configuration files — a load balancer's upstream list, for example, can be kept automatically current without the load balancer itself being Consul-aware, by having Consul Template regenerate and hot-reload the upstream config whenever Consul's healthy instance set changes. In Kubernetes-native or service-mesh environments, Consul Template is less necessary since the mesh or Kubernetes itself handles dynamic routing, but it remains widely used in VM-based or hybrid architectures.

## Section 12: Scenario-Based Questions

**Q30. "Services are being registered with Consul on startup but aren't appearing in DNS discovery results, even though they show up in the Consul UI. How would you investigate?"**
A: Work through a structured diagnostic: first, check the service's health status in the Consul UI or via `consul health service <name>` — if the service shows as registered in the catalog but its health checks are in `critical` state, it will be excluded from DNS results that filter to passing-only instances (Q13), which is the most common explanation for "appears in UI, not in DNS." Check whether the health check is correctly configured — a misconfigured HTTP check URL (wrong port, wrong path, expecting a response format the service doesn't return) or a TTL check where the service hasn't sent its first heartbeat yet will both cause the check to be critical. If the service's checks are passing, verify the DNS query format is correct (the `.service.consul` suffix, Q14) and that the client is querying the right DNS server (port 8600 on the local agent or a forwarding setup, Q15) rather than a public DNS resolver that wouldn't know about Consul records. Finally, check whether ACLs are enabled and the client making the DNS query has a token with read permissions for that service (Q25) — denied queries often return NXDOMAIN rather than an explicit access-denied error, making ACL issues look superficially like discovery failures.

**Q31. "A Consul server cluster of three nodes loses two nodes simultaneously due to a hardware incident. What is the state of the cluster, and what are the recovery options?"**
A: With two of three servers gone, the remaining server has no quorum (1 of 3, majority requires 2) — the cluster cannot elect a leader and cannot process any writes, including new service registrations, deregistrations, or health-check state updates. Existing cached state on the surviving server and on client agents may still be readable (clients can still resolve previously-discovered services from their local cache), but the catalog is effectively frozen. Recovery options: if the two failed servers can be brought back (same nodes, same data), restoring them to connectivity allows the Raft cluster to reform naturally once a quorum is present again. If the servers are permanently lost, Consul supports **peer removal** (removing the failed servers from the Raft peer configuration on the surviving server to allow it to become a single-node leader, resuming writes), followed by adding new server agents to rebuild to the desired cluster size — a `consul operator raft remove-peer` operation performed on the surviving server. This is why five-node clusters provide meaningfully better fault tolerance: a five-node cluster can survive two simultaneous failures and maintain quorum, eliminating the split-second where a two-simultaneous-failure event takes down all writes.

**Q32. "Your organization runs services on both bare-metal VMs and in Kubernetes. VM-based services need to discover Kubernetes services, and Kubernetes services need to discover VM-based services. How would you use Consul to bridge these environments?"**
A: Run Consul agents on the VM hosts (client agents registering VM services directly) and deploy Consul client agents inside the Kubernetes cluster — either as a DaemonSet (one client agent per node) or as a pod sidecar — with a Consul server cluster accessible from both environments as the shared authoritative registry. VM services register with their local Consul client agents as they do today; Kubernetes services can be registered with Consul either via the Consul Helm chart's auto-registration feature (which watches the Kubernetes API and registers Kubernetes services with Consul automatically — the third-party registration pattern from the service discovery guide) or via explicit service definition files. Both environments then have a unified Consul catalog: VM services query `vm-service.service.consul` (served by the Consul DNS interface on their local agent, Q14–15), and Kubernetes services resolve Consul names via CoreDNS configured to forward `.consul` queries to the Consul agent running on each Kubernetes node. This makes both environments full citizens in the same unified registry, rather than requiring either side to be statically configured with the other's addresses.

**Q33. "A developer reports that their service is returning stale endpoint lists — they updated a service registration (changed the port), but clients are still connecting to the old port for several minutes afterward. How would you investigate the source of the staleness?"**
A: Work through the layers where staleness can accumulate: first, verify the registration change actually reached the Consul catalog (query `/v1/catalog/service/<name>` on a server agent directly, bypassing any client-agent caching — Q10) — if the catalog shows the old port, the registration update itself didn't propagate to the servers yet, possibly due to a client agent connectivity issue or an ACL permissions problem. If the catalog is already updated but clients still see the old port, the staleness is in the client's discovery mechanism: if they're using DNS, the DNS TTL (Consul's default DNS TTL is quite short, but client-side OS/resolver caching applies, Q14–16 from the DNS guides) may be holding the old SRV record; if they're using the HTTP API with polling, the polling interval determines how stale the local cache can be; if they're using blocking queries (Q18), the update should have arrived near-instantly after the catalog change — a significant lag on a blocking-query-based client suggests a network or client-implementation issue. The structured diagnostic principle from the TTL guide (Q37 in the original DNS guide) applies directly: isolate *which layer* (authoritative catalog, client agent cache, DNS TTL cache, application-level cache) is actually holding the stale value before concluding.

**Q34. "Your team is evaluating whether to use Consul's built-in health checking or to rely on Kubernetes liveness/readiness probes for service health, given that your infrastructure runs entirely on Kubernetes. What are the trade-offs of each approach?"**
A: Kubernetes readiness probes integrate natively with the Kubernetes endpoint controller — when a pod fails its readiness probe, Kubernetes automatically removes it from the Service's Endpoint slice, which CoreDNS and kube-proxy immediately reflect in routing, without any Consul involvement. This is tight, automatic integration with no additional configuration or tooling. Consul's health checking provides richer check types (script checks, TTL checks, multi-condition checks) and makes health state visible in the Consul catalog for any non-Kubernetes consumer — if the same Consul catalog is bridging Kubernetes and VM environments (Q32), having health checks expressed in Consul gives a unified health-state view regardless of where the service runs. The practical recommendation for Kubernetes-only environments: rely primarily on Kubernetes readiness probes (they're the native integration point and require no additional tooling), but if Consul is already in use for other reasons (KV store, cross-environment discovery, Consul Connect), register Kubernetes services in Consul with Consul health checks specifically so that the Consul catalog remains an accurate, health-aware reflection of the Kubernetes service state for any consumers querying Consul rather than Kubernetes directly.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Consul agent (server mode) | Participates in Raft consensus; maintains authoritative catalog state |
| Consul agent (client mode) | Local interface for services; forwards to servers; runs local health checks |
| Raft consensus | Ensures consistent, durable service catalog state across server cluster |
| Gossip (Serf) | Membership and failure detection across all agents; separate from Raft |
| Quorum | Majority of servers must be alive; 3-node cluster tolerates 1 failure; 5-node tolerates 2 |
| Service catalog | Global, Raft-replicated view of all registered services and their health |
| Health check types | Script, HTTP, TCP, TTL, gRPC — each with different probing models |
| Check states | Passing / Warning / Critical; Critical excludes from discovery results |
| DNS interface | `<service>.service.consul` A records; `<tag>.<service>.service.consul`; SRV for port |
| HTTP API `/v1/health/service` | Discovery with health filter; use `passing=true` for routing |
| Blocking queries | Long-poll until state changes; near-real-time updates without polling overhead |
| KV store | Distributed config and coordination; 512KB per value; Raft-backed |
| Consul Connect | mTLS service mesh; intentions for service-level access control |
| Intentions | Service-identity-based (not IP-based) allow/deny communication policy |
| WAN federation | Cross-datacenter discovery; each datacenter retains its own Raft cluster |
| Prepared queries | Named queries with built-in cross-datacenter failover logic |
| ACLs | Token-based access control; critical for production; disabled = full read/write exposure |
| Consul Template | Watches Consul, renders config files; bridges to non-Consul-native apps |
