# DNS (Domain Name System) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is DNS and what problem does it solve?**
A: DNS is a globally distributed, hierarchical naming system that translates human-readable domain names (`example.com`) into machine-usable identifiers — most commonly IP addresses, but also other resource records (mail servers, service locations, text metadata). It solves the problem of indirection at internet scale: humans and applications reference stable, memorable names, while the underlying infrastructure (IP addresses, server locations) can change freely without requiring every reference to that name to be updated — DNS is the layer that maps the stable name to the current reality.

**Q2. What does it mean that DNS is "hierarchical" and "distributed"?**
A: Hierarchical: the namespace is structured as a tree, read right-to-left in a domain name — the root (implicit, represented by a trailing dot), then top-level domains (TLDs like `.com`, `.org`), then the registered domain (`example`), then subdomains (`www.example.com`, `api.example.com`). Distributed: no single server holds the entire DNS database; authority for each level of the hierarchy is delegated to different organizations and servers — the root is operated by a small set of root server operators, each TLD is operated by its registry, and each individual domain's records are operated by whoever runs that domain's authoritative nameservers. This distribution is what lets DNS scale globally without a central bottleneck or single point of failure.

**Q3. What are the four main types of DNS servers involved in a typical resolution, and what does each do?**
A:
- **DNS resolver (recursive resolver)**: the client-facing server (often run by your ISP, a public service like Google's 8.8.8.8 or Cloudflare's 1.1.1.1, or configured locally) that takes a client's query and does the work of walking the hierarchy to find the answer, caching results along the way.
- **Root nameserver**: the starting point of the hierarchy — doesn't know the answer to `example.com` directly, but knows which TLD nameserver (e.g., for `.com`) to ask next.
- **TLD nameserver**: knows which authoritative nameserver is responsible for a specific domain within that TLD (e.g., knows that `example.com`'s authoritative servers are X and Y).
- **Authoritative nameserver**: holds the actual, source-of-truth DNS records for a specific domain — the final answer in the chain, returned by whoever operates DNS for that domain (often a registrar, a cloud DNS service like Route 53/Cloudflare DNS, or self-hosted infrastructure).

**Q4. What is the difference between a recursive query and an iterative query?**
A: A recursive query is what a client sends to its configured resolver: "give me the final answer, I don't want to deal with the hierarchy myself." The resolver is then responsible for doing all the work to produce that final answer. An iterative query is what the resolver itself sends, repeatedly, to each server in the hierarchy: "I'm looking for X — if you don't know, tell me who to ask next" (rather than expecting that server to fully resolve it). The resolver does iterative queries against root → TLD → authoritative servers, then returns the final, fully-resolved answer to the client recursively. This distinction — client does recursive, resolver does iterative — is a frequent point of confusion worth being precise about in an interview.

**Q5. Walk through a full DNS resolution for `www.example.com`, assuming nothing is cached anywhere.**
A:
1. Client asks its configured recursive resolver: "What's the IP for `www.example.com`?"
2. Resolver asks a root nameserver. Root doesn't know the answer but knows the `.com` TLD nameservers, and returns a referral to them.
3. Resolver asks a `.com` TLD nameserver. It doesn't know the final answer either, but knows which nameservers are authoritative for `example.com` (delegated when the domain was registered), and returns a referral to them.
4. Resolver asks `example.com`'s authoritative nameserver directly for the `www` record.
5. Authoritative nameserver returns the actual answer (e.g., an A record with an IP address).
6. Resolver caches the result (per its TTL) and returns it to the client.
7. Client now has the IP and can establish a connection directly to that server — DNS's job is done; the actual HTTP/TCP connection happens entirely outside the DNS system.

## Section 2: Record Types

**Q6. What is an A record vs an AAAA record?**
A: An A record maps a domain name to an IPv4 address (`93.184.216.34`). An AAAA record ("quad-A") maps a domain name to an IPv6 address (`2606:2800:220:1:248:1893:25c8:1946`). A domain can have both simultaneously — a client capable of IPv6 will typically prefer the AAAA record (via the "Happy Eyeballs" algorithm, which races both connection attempts and uses whichever succeeds/responds first), falling back to the A record's IPv4 address if IPv6 connectivity isn't available or is slower.

**Q7. What is a CNAME record and what's its key restriction?**
A: A CNAME (Canonical Name) record aliases one domain name to another — `www.example.com CNAME example.com` means any query for `www.example.com` is redirected to resolve `example.com` instead, ultimately returning whatever `example.com`'s own records resolve to. The key restriction: a CNAME record cannot coexist with any other record type at the same name (you can't have both a CNAME and an A record, or a CNAME and an MX record, for the same exact subdomain) — this is a DNS protocol-level rule, not a vendor limitation, and it specifically causes the common "can't CNAME the zone apex" problem (Q9).

**Q8. What is an MX record?**
A: A Mail Exchange record specifies which mail server(s) are responsible for accepting email on behalf of a domain, including a priority value for failover/load distribution among multiple mail servers (lower priority number = higher preference). Relevant in interviews mainly to demonstrate breadth — most application engineers don't directly manage MX records, but understanding that DNS carries far more than just "what's the IP" is a useful framing.

**Q9. What is the "zone apex CNAME problem" and how is it typically solved?**
A: Because of the CNAME coexistence restriction (Q7), you technically cannot set a CNAME record at a domain's bare root/apex (`example.com`, as opposed to `www.example.com`) if that apex also needs other records — most critically, the apex almost always needs at least an SOA record and NS records (required for the domain to function as a zone at all), which would conflict with a CNAME at the same name. This becomes a practical problem when you want the root domain to point to a CDN or load balancer that only provides a CNAME-style hostname target (common with services like CloudFront, Heroku, or many SaaS platforms) rather than a fixed IP suitable for a plain A record. Solutions: **ALIAS/ANAME records** (a non-standard, vendor-specific record type — supported by Route 53 as "Alias", Cloudflare as "CNAME flattening", and several other DNS providers — that behaves like a CNAME from the zone management perspective but is resolved server-side by the DNS provider into an actual A/AAAA record before being returned to clients, avoiding the protocol-level conflict); or simply using a static A record pointing to a fixed IP if the target service provides one (often not flexible enough for services that load-balance/change IPs dynamically, which is why ALIAS records exist).

**Q10. What is a TXT record and what are its common modern uses?**
A: A TXT record holds arbitrary free-text data associated with a domain — originally a general-purpose catch-all, now used heavily for domain verification and email security:
- **Domain ownership verification**: many services (Google Workspace, SSL certificate authorities) require adding a specific TXT record to prove you control a domain before granting access/certificates.
- **SPF (Sender Policy Framework)**: lists which mail servers are authorized to send email on behalf of the domain, helping receiving servers detect spoofed sender addresses.
- **DKIM (DomainKeys Identified Mail)**: publishes a public key used to verify cryptographic signatures on outgoing email, proving the email wasn't tampered with in transit.
- **DMARC**: a policy record telling receiving mail servers what to do (reject, quarantine, or just report) when SPF/DKIM checks fail for mail claiming to be from this domain.

**Q11. What is an NS record and an SOA record?**
A: An NS (Nameserver) record specifies which servers are authoritative for a given zone/domain — this is literally the mechanism by which delegation happens in the hierarchy (the TLD nameserver's NS records for `example.com` are what tell resolvers where to go next, per Q5 step 3). An SOA (Start of Authority) record contains administrative metadata about a zone: the primary nameserver, an administrator contact, a serial number (incremented on changes, used by secondary nameservers to detect updates needing replication), and several timing values (refresh, retry, expire, minimum/negative-cache TTL) governing zone transfer and caching behavior between nameservers.

**Q12. What is a PTR record and what is "reverse DNS"?**
A: A PTR record does the inverse of an A record — given an IP address, it returns the associated domain name, used for reverse DNS lookups. Implemented via a special reverse-mapping zone (`in-addr.arpa` for IPv4, `ip6.arpa` for IPv6). Common uses: mail servers often check reverse DNS on the sending IP as a spam-fighting heuristic (legitimate mail servers usually have proper reverse DNS configured; many spam sources don't), and reverse DNS is sometimes used for logging/diagnostic readability (showing a hostname instead of a raw IP in logs).

**Q13. What is an SRV record and where is it commonly used?**
A: A Service record specifies the hostname, port, priority, and weight for a specific service running on a domain — unlike most record types, it encodes both *where* (hostname) and *which port* a service runs on, which plain A/CNAME records can't express. Commonly used by protocols like SIP (VoIP), XMPP (messaging), and notably by service discovery in some infrastructure contexts (e.g., Kubernetes headless services can expose SRV records for service discovery, and HashiCorp Consul uses DNS SRV records as one of its service discovery interfaces). The priority/weight fields function similarly to MX record priority and to weighted load balancing concepts covered in the load balancing guides — allowing DNS-level traffic distribution across multiple service instances.

## Section 3: TTL and Caching Behavior

**Q14. What is TTL in the context of DNS and where is it set?**
A: Time To Live — a value (in seconds) attached to every DNS record by the authoritative nameserver, telling any resolver or client that caches the record how long it may continue using that cached answer before it must re-query for a fresh one. Set by whoever manages the domain's DNS records (e.g., in Route 53, Cloudflare DNS, or any DNS hosting provider's record configuration), as part of each individual record — different records for the same domain can have different TTLs.

**Q15. What is the trade-off in choosing a short vs long TTL?**
A: Short TTL (e.g., 30-60 seconds): enables fast propagation of changes (failover, IP changes, load balancer reconfiguration take effect quickly across the internet), at the cost of significantly higher query volume against your authoritative nameservers (since caches expire and re-query far more often) and slightly higher latency for end users on cache misses (more frequent full resolution chains, though this is usually a minor factor compared to the volume cost). Long TTL (e.g., 24 hours, 86400 seconds): reduces load on authoritative nameservers and improves average resolution speed (more cache hits, fewer full chain walks), at the cost of slow propagation — if you need to change an IP (e.g., during an incident, a migration, or a failover), clients caching the old value will continue using it, potentially for the full TTL duration, regardless of how quickly you update the authoritative record.

**Q16. What is the standard operational practice for TTL around planned infrastructure changes (e.g., a migration or major deployment)?**
A: Lower the TTL on the relevant record well in advance of the planned change (e.g., reduce from 24 hours to 60 seconds, and *wait at least the old TTL's duration* before proceeding, since any cached copies with the old long TTL will still be honored by resolvers until they naturally expire) — this ensures that by the time the actual change happens, any resolver querying for the record gets the new short TTL, meaning the eventual real change (updating the IP/record value) propagates quickly. After the change has fully rolled out and stabilized, the TTL can be raised back to its normal longer value to reduce ongoing query load. Forgetting this step — changing a record's value while it still has a long TTL from before — is a common operational mistake that causes a slow, inconsistent rollout where some users see the new infrastructure and others remain stuck on the old one for hours.

**Q17. Why can't you fully guarantee fast DNS propagation even with a very short TTL?**
A: TTL is a *maximum* caching duration that well-behaved resolvers should respect — but it's not universally enforced. Some resolvers (particularly certain ISP-level or corporate resolvers, and some client-side OS/browser DNS caches) have historically ignored or overridden very short TTLs with their own minimum caching floor (e.g., refusing to cache for less than some minimum interval, or conversely sometimes caching longer than instructed for efficiency), and DNS is also cached at multiple independent layers (OS-level resolver cache, browser-level DNS cache, intermediate recursive resolver, sometimes application-level connection pooling that implicitly "pins" a resolved IP for the lifetime of a long-lived connection) — each layer can introduce its own caching behavior somewhat independent of the authoritative TTL. This is part of why DNS-based traffic management (DNS Round Robin, GeoDNS, the IP Hash guide's discussion of DNS limitations) is considered a relatively blunt, slow-reacting mechanism compared to Anycast or an actual load balancer's health-check-driven failover.

**Q18. What is negative caching in DNS, and what controls its duration?**
A: When a query returns "this name doesn't exist" (NXDOMAIN) or "this record type doesn't exist for this name," resolvers cache that *negative* result too — to avoid repeatedly re-querying for something that's confirmed not to exist. The duration of negative caching is governed by the minimum TTL field in the zone's SOA record (Q11), not by a per-record TTL (since there's no record to attach a TTL to for something that doesn't exist). This matters operationally: if you're about to create a new DNS record that was previously queried and got an NXDOMAIN response, resolvers that cached that negative result won't re-query until the SOA's negative-cache TTL expires — meaning a newly created record can appear to "not exist yet" for some users even after you've correctly published it.

## Section 4: DNS-Based Traffic Management

**Q19. How does DNS function as a (limited) load balancing and traffic management mechanism, and how does this connect to concepts already covered?**
A: This curriculum has touched on several DNS-based traffic management patterns already: DNS Round Robin (returning multiple A records in rotating order — covered in the Round Robin guide, with its caching/health-check limitations), GeoDNS (resolving differently based on the querying resolver's apparent location — covered in the CDN guide), and Anycast (a network-layer alternative that sidesteps DNS-level geo-logic entirely by having BGP route to the nearest of several servers sharing one IP — also covered in the CDN guide). The unifying theme: DNS can influence *which* IP a client ultimately connects to, but it has no visibility into or control over what happens *after* that IP is handed out — no health checking of the actual connection, no awareness of in-flight requests, and caching means decisions can be "sticky" for longer than ideal. This is why DNS-based traffic management is typically layered as a coarse, first-pass routing mechanism (route to the right region/data center) rather than the sole or fine-grained load balancing mechanism (which is the job of an actual L4/L7 load balancer once traffic reaches that region).

**Q20. What is "DNS-based health checking" / "DNS failover" and how does it work, given DNS's lack of native connection-level visibility?**
A: Many managed DNS providers (Route 53, Cloudflare, NS1) offer an integrated health-checking feature: the DNS provider's infrastructure periodically probes the actual backend endpoints (HTTP health checks, similar in spirit to a load balancer's health checks) *outside* of the DNS protocol itself, and uses the results to decide which records to include in DNS responses — automatically removing an unhealthy endpoint's record from the response rotation, or switching to a designated failover record, without requiring any DNS protocol-level health awareness (since DNS itself has no such concept). This is effectively bolting active monitoring onto the DNS layer as a separate, provider-specific feature, not a capability inherent to the DNS protocol — worth being precise about in an interview, since it's a common point of confusion ("does DNS know if a server is down?" — no, the DNS *provider's* additional tooling does).

**Q21. What is latency-based routing in DNS, and how does it differ from simple GeoDNS (location-based)?**
A: GeoDNS routes based on the *apparent geographic location* of the querying resolver (inferred from IP geolocation) — a reasonable but imperfect proxy for actual network latency, since geographic proximity doesn't always correlate with network path quality (the same caveat discussed for Anycast/BGP in the CDN guide). Latency-based routing (offered by some managed DNS providers, e.g., Route 53's latency-based routing policy) instead uses measured network latency data between AWS regions and the resolver's network, to route to whichever region actually offers the best measured performance — a more accurate but more provider-specific and infrastructure-dependent mechanism than pure geographic inference.

**Q22. What is weighted DNS routing, and what use case does it serve?**
A: Similar in concept to weighted round robin (covered in the dedicated WRR guide) but implemented at the DNS layer — multiple records for the same name are returned with different configured weights, and the DNS provider distributes the proportion of responses (and thus, roughly, the proportion of resulting traffic) according to those weights. Common use case: gradual traffic migration between two infrastructure environments (e.g., shifting 5% of traffic to a new region or a new cloud provider, then increasing gradually) at the DNS layer, when you want this control even before traffic reaches any application-level load balancer. The same caching/TTL caveats apply — DNS-layer weighting is coarser and slower to converge than an L7 load balancer's weighted routing, since each client effectively "locks in" to whichever record they resolved until their local cache expires.

## Section 5: DNS in Microservices and Service Discovery

**Q23. How is DNS used for service discovery in containerized/microservices environments?**
A: Many container orchestration platforms expose internal DNS as the primary service discovery mechanism — in Kubernetes, every Service gets a DNS name (`my-service.my-namespace.svc.cluster.local`) automatically resolvable from within the cluster, backed by an internal DNS server (CoreDNS, the current default) that's aware of the cluster's actual service registry and updates records dynamically as pods/services are created or removed. This means application code can simply use ordinary DNS resolution (`my-service`) to discover and connect to other services, without needing a separate service-discovery client library or protocol — DNS itself becomes the discovery mechanism, abstracting away the underlying dynamic set of pod IPs behind a stable service name.

**Q24. What is a "headless service" in Kubernetes and how does its DNS behavior differ from a normal Service?**
A: A normal Kubernetes Service gets a single stable cluster-internal IP (a "ClusterIP"), and DNS resolution for it returns that one virtual IP, with kube-proxy handling the actual load balancing to backing pods behind that IP (as covered in the load balancing guides — kube-proxy implements something like Round Robin via iptables/IPVS). A headless service (created by explicitly setting `clusterIP: None`) has no such virtual IP — instead, DNS resolution for it directly returns the individual IPs of all the backing pods (as multiple A records, similar in spirit to DNS Round Robin), letting the client application itself choose among them or connect to all of them, rather than going through a single virtual-IP load-balancing layer. This is useful for stateful workloads (e.g., a database cluster like Cassandra or a Kafka cluster) where the client needs direct, individual addressability of each backing instance rather than an opaque load-balanced pool.

**Q25. Why might DNS-based service discovery be insufficient for very dynamic, high-churn microservices environments, and what alternatives exist?**
A: DNS's caching model (TTL-based) is fundamentally in tension with rapid change — if pod IPs are churning frequently (frequent deployments, aggressive autoscaling, frequent pod restarts), DNS caching at any layer (client-side resolver cache, connection pooling that implicitly pins a resolved IP) can mean an application continues trying to connect to an IP that's no longer valid, until the cache expires or the connection fails outright. This is why many service mesh architectures (Istio, Linkerd) and dedicated service discovery systems (Consul, etcd-backed discovery, Netflix Eureka) layer additional mechanisms on top of or instead of plain DNS — actively pushing updated endpoint lists to clients/proxies in near-real-time (via the xDS protocol in Envoy's case, covered conceptually in the L4/L7 guide) rather than relying on clients to periodically re-resolve DNS and respect TTLs. DNS-based discovery remains simpler and sufficient for many use cases, but high-churn, latency-sensitive service-to-service communication often outgrows it.

## Section 6: Security

**Q26. What is DNS cache poisoning / spoofing?**
A: An attack where a malicious actor injects a forged DNS response into a resolver's cache, causing it to return an attacker-controlled IP address for a legitimate domain name to all subsequent queriers — effectively redirecting traffic intended for the real site to an attacker's server (commonly used for phishing, credential theft, or man-in-the-middle interception). Classic attacks (e.g., the 2008 Kaminsky DNS vulnerability) exploited the fact that DNS over UDP has limited entropy in matching queries to responses (a 16-bit transaction ID and a source port that was historically often predictable), allowing an attacker to race and guess a forged response that the resolver would accept as legitimate before the real authoritative server's response arrived.

**Q27. What is DNSSEC and how does it defend against cache poisoning?**
A: DNS Security Extensions add cryptographic signatures to DNS records, allowing a resolver to verify that a response genuinely came from the claimed authoritative source and hasn't been tampered with in transit — using a chain of trust rooted at the DNS root zone (each level cryptographically signs the delegation to the level below it, similar in spirit to a certificate chain in TLS). A resolver performing DNSSEC validation will reject a forged/tampered response even if an attacker successfully guesses the matching transaction ID and source port, because the forged response won't carry a valid cryptographic signature matching the legitimate chain of trust. Adoption has historically been slower than TLS/HTTPS adoption, partly due to deployment complexity (key management, ensuring the entire chain from root to leaf domain is properly signed) and partly because DNSSEC addresses authenticity/integrity of DNS responses specifically, not confidentiality (a DNSSEC-validated query is still sent and answered in plaintext, visible to network observers — that's a separate problem, addressed by Q28).

**Q28. What is DNS over HTTPS (DoH) and DNS over TLS (DoT), and what problem do they solve that DNSSEC doesn't?**
A: Standard DNS queries are sent in plaintext over UDP/TCP port 53 — anyone observing network traffic between the client and resolver (an ISP, a network operator, an attacker on the same network) can see exactly which domains a user is looking up, even if DNSSEC ensures the *answers* aren't tampered with. DoH wraps DNS queries inside HTTPS (making DNS traffic indistinguishable from regular web traffic on port 443, and encrypting the query contents); DoT wraps DNS queries inside a dedicated TLS connection (typically port 853) — both achieve the same core goal: confidentiality of the query/response between client and resolver, preventing network-level eavesdropping or tampering of the DNS exchange itself. DNSSEC and DoH/DoT solve different, complementary problems: DNSSEC ensures the resolver gets an authentic, untampered answer from the authoritative source; DoH/DoT ensures that the conversation between the client and its resolver is private and tamper-resistant in transit. A fully secured DNS posture uses both.

**Q29. What is a "DNS amplification attack" and why is DNS a common vector for it?**
A: A type of DDoS attack where an attacker sends a small DNS query to an open/misconfigured DNS resolver with a spoofed source IP address (the victim's IP), causing the resolver to send its (often much larger) response to the victim instead of back to the attacker — exploiting the significant size asymmetry between a small DNS query and a larger DNS response (especially with DNSSEC-signed responses, which are notably larger, or queries crafted to request large record types) to amplify the attacker's effective bandwidth many times over against the victim. Mitigation primarily involves DNS resolver operators properly configuring their servers to not respond to queries from outside their intended client base ("open resolvers" — publicly accessible recursive resolvers that will answer queries from anyone — are the root enabler of this attack class) and implementing source IP validation (BCP 38 / ingress filtering) at the network level to prevent the spoofed-source-IP packets that make the attack possible in the first place.

**Q30. What is "DNS rebinding" and why is it a relevant security concern for applications that fetch user-supplied URLs?**
A: An attack where a domain's DNS record is changed (rebound) to a different IP — often an internal/private IP — *after* an initial security check has already validated the original IP as safe, exploiting the gap between validation time and actual use time (a TOCTOU — time-of-check to time-of-use — vulnerability, the same pattern flagged for SSRF in the reverse proxy guide). Example: an application validates that a user-supplied hostname resolves to a public IP, then later makes the actual request — but if the attacker controls the DNS record and changes it to point to an internal IP (e.g., `169.254.169.254` or `localhost`) between the validation step and the actual request, the application ends up making a request to an internal resource it never meant to be reachable. Mitigation: re-validate the resolved IP immediately before use (not just once, earlier in the flow), pin the validated IP for the actual connection rather than re-resolving DNS at request time, and apply the same private-IP-range blocking discussed in the SSRF mitigation from the reverse proxy guide.

## Section 7: Performance and Operational Considerations

**Q31. What is DNS prefetching and how does it improve perceived web performance?**
A: A browser optimization where the browser proactively resolves DNS for domains it anticipates the page will need (e.g., domains referenced in `<link rel="dns-prefetch">` hints, or domains found in links on the current page) *before* the user actually navigates to or requests resources from them — so that by the time an actual request is made, the DNS resolution step (which would otherwise add a full resolution round-trip to the critical path) is already complete and cached. This is a pure latency-hiding optimization that doesn't change DNS's fundamental behavior, just shifts when the resolution cost is paid relative to when it's perceptible to the user.

**Q32. How much does DNS resolution typically contribute to overall page load / request latency, and when does it matter most?**
A: For a single uncached resolution involving the full hierarchy walk (root → TLD → authoritative), DNS resolution can add tens to low hundreds of milliseconds — but in practice, most resolutions hit a cache at some layer (resolver cache, OS cache) and resolve in single-digit milliseconds or less. It matters most on: first-time visits to a new domain (no cache anywhere yet), pages with many distinct third-party domains (ads, analytics, fonts, each potentially requiring its own DNS resolution if not already cached), and any scenario involving DNS-based traffic management (GeoDNS, weighted routing) where the resolution itself, not just the connection, may be on a slower or more distant path. It matters comparatively less for established, frequently-visited domains where caching has already absorbed most of the cost.

**Q33. What is "split-horizon DNS" (also called split-brain DNS) and why is it used?**
A: A configuration where the same domain name resolves differently depending on who's asking — typically, internal/corporate network clients get one set of records (e.g., pointing to internal-only IPs, bypassing external load balancers/firewalls entirely for internal traffic), while external/public clients get a different set of records (the actual public-facing IPs). Implemented by running separate authoritative DNS zones/views for internal vs external resolvers. Common use case: an internal microservice or admin tool that should be reachable by name from within the corporate network or VPN, but where you don't want to expose that same name's "real" internal routing details to the public internet — split-horizon DNS lets the same memorable hostname work correctly in both contexts without conflict.

**Q34. What operational monitoring/observability matters specifically for DNS infrastructure you control (e.g., your domain's authoritative DNS)?**
A: Query volume and latency at the authoritative nameserver level (sudden spikes can indicate either legitimate traffic growth, a TTL misconfiguration causing excessive re-querying, or an attack like DNS amplification being reflected through your infrastructure); NXDOMAIN rate (an unusually high rate of "not found" responses can indicate misconfigured clients, a recently-changed/removed record that's still being queried by stale references, or reconnaissance/scanning activity); propagation verification after any record change (actively querying from multiple geographic vantage points/resolvers to confirm a change has actually rolled out as expected, rather than assuming TTL math alone guarantees it); and DNSSEC validation failures if DNSSEC is enabled (signature expiration is a real, surprisingly common operational failure mode — DNSSEC signatures have their own expiry separate from record TTLs, and a forgotten re-signing schedule can cause an entire domain to become unreachable for DNSSEC-validating resolvers, despite the underlying records themselves being completely correct).

## Section 8: Scenario-Based Questions

**Q35. "You're migrating your production API from one cloud provider's load balancer to another, with a completely different IP. Walk through how you'd execute this via DNS with minimal disruption."**
A: Following the planned-change TTL practice (Q16): days before the migration, lower the TTL on the relevant DNS record (e.g., from 3600s to 60s) and wait at least the *old* TTL duration (in this case, up to an hour) to ensure any previously-cached long-TTL copies have naturally expired across the internet before proceeding. Once the short TTL window has fully taken effect, update the record to point to the new load balancer's IP (or, better, set up the new infrastructure first and verify it's fully healthy before the cutover, potentially using a weighted routing policy (Q22) to gradually shift traffic rather than an instant flip). Monitor both the old and new infrastructure's traffic/error rates during the transition window to catch any clients still resolving to the old IP (which may persist briefly due to caching layers that don't perfectly respect TTL, per Q17) before fully decommissioning the old load balancer. After the migration is confirmed stable, raise the TTL back to a normal longer duration to reduce ongoing query load on the new authoritative DNS infrastructure.

**Q36. "Your application makes a long-lived gRPC connection to a downstream service identified by DNS name. The downstream service scales horizontally and its pod IPs change frequently. What problem will you encounter, and how do you address it?"**
A: This is the DNS-caching-vs-connection-pinning problem (related to Q25 and to the gRPC/L4 mismatch discussed in the L4 vs L7 guide): once the gRPC client resolves the hostname and establishes a long-lived connection to a specific IP, it has implicitly "pinned" to that IP for the connection's lifetime — even if DNS records change (new pods, old pods terminated) and even if the client's local DNS cache would technically allow a fresher answer, the existing connection doesn't automatically re-resolve or migrate. If the original pod is terminated, the connection breaks; if many pods exist behind the DNS name (e.g., via a Kubernetes headless service, Q24) but the client only resolved and connected to one, the client never benefits from the others except by chance on reconnect. Fixes: use a gRPC client library with built-in DNS-aware load balancing/re-resolution (many gRPC client implementations support periodically re-resolving DNS and rebalancing connections across the current set of returned IPs, particularly when paired with a headless service returning multiple A records); or move to a proper service mesh/xDS-based service discovery mechanism (Envoy/Istio, as discussed in Q25) that actively pushes endpoint updates rather than relying on the client's DNS resolution and caching behavior to stay current.

**Q37. "A user reports that after your team updated a DNS record to fix a bug, they're still seeing the old (broken) behavior 20 minutes later, well past the configured 60-second TTL. How do you investigate?"**
A: Several non-mutually-exclusive possibilities to check, reflecting Q17's point that TTL is a maximum, not a guarantee: (1) verify the change actually propagated correctly to the authoritative nameservers in the first place (query the authoritative server directly, bypassing any resolver, to confirm the new record is genuinely live there) — sometimes the apparent "DNS isn't updating" issue is actually a deployment/configuration issue, not a caching issue at all; (2) check whether the user's specific resolver (ISP-level, corporate, or a public resolver) might be ignoring or overriding the short TTL with its own minimum caching floor; (3) check whether the staleness is actually happening at a layer other than DNS resolution entirely — e.g., the user's browser or OS might have its own connection-level or DNS-level cache independent of the resolver, or (very commonly) the *application* itself might be the one caching a resolved IP at the connection-pool level (Q36's pinning problem) rather than the DNS layer being at fault at all; (4) if DNSSEC is enabled, confirm there isn't a validation issue causing fallback to a cached/stale state. The key diagnostic principle: isolate which layer (authoritative record itself, intermediate resolver cache, client OS/browser cache, or application-level connection caching) is actually serving the stale answer, rather than assuming "DNS" as an undifferentiated single cause.

**Q38. "How would you design the DNS strategy for a global SaaS product with users in North America, Europe, and Asia, each ideally served by a regional deployment?"**
A: Layer DNS-based routing as the coarse, first-pass mechanism, combined with finer-grained mechanisms underneath, rather than relying on DNS alone for everything. At the DNS layer: use either GeoDNS or latency-based routing (Q21) to direct users to the nearest regional deployment's entry point — ideally backed by DNS-level health checking (Q20) so that if an entire region becomes unhealthy, DNS automatically stops directing users there (with appropriate TTL tuned to balance propagation speed for failover against query volume, as discussed in Q15-16). Within each region, once traffic arrives at that region's entry point, hand off to a proper L7 load balancer (from the earlier load balancing guides) for the actual fine-grained, health-check-aware, low-latency traffic distribution across that region's backend fleet — since DNS's caching/TTL limitations make it a poor fit for the kind of real-time, per-request load balancing decisions an L7 LB handles well. This combination — DNS for coarse geographic/regional routing, L4/L7 LB for fine-grained in-region distribution — mirrors the layered architecture pattern discussed in the L4 vs L7 guide's "real-world architecture" section.

**Tip for interviews:** Five things separate strong candidates on DNS: (1) being precise about the **recursive vs iterative** distinction (Q4) instead of using the terms interchangeably; (2) understanding that **TTL is a maximum, not a guarantee** (Q17) — several caching layers exist beyond the authoritative TTL, which explains a lot of real-world "DNS isn't updating" confusion; (3) knowing the **proper TTL-lowering procedure before planned changes** (Q16) — wait out the *old* TTL before changing the value, a frequently-missed operational detail; (4) being able to clearly separate what **DNSSEC solves (authenticity) vs what DoH/DoT solves (confidentiality)** (Q27-28) — a very common conflation; and (5) connecting DNS-based traffic management back to the load balancing curriculum by correctly framing it as a **coarse, slow-reacting first-pass mechanism** that's layered with, not a replacement for, proper L4/L7 load balancing (Q19, Q38) — this ties the whole curriculum together and is exactly the kind of systems-level synthesis interviewers look for at the 5 YOE level.
