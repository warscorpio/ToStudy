# Least Connections — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Least Connections (LC) algorithm?**
A: A dynamic load balancing algorithm where each new request or connection is routed to the backend currently holding the fewest active connections. Unlike Round Robin (which is oblivious to backend state), Least Connections continuously monitors how many in-flight connections each backend has and routes toward the least-loaded one. It is the simplest adaptive algorithm — the only signal it uses is connection count.

**Q2. How does "active connections" get defined and tracked?**
A: An active connection is one that has been established and not yet closed. The LB increments a counter on the selected backend when a connection opens and decrements it when the connection closes (TCP FIN/RST, HTTP response complete, or timeout). The counter is typically a per-backend atomic integer maintained in the LB's memory. The LB does not look inside the connection — just whether it exists.

**Q3. Why is Least Connections better than Round Robin for variable-cost workloads?**
A: Round Robin distributes connections evenly but is blind to how long each takes. If backend A gets a 5ms request and backend B gets a 500ms request simultaneously, Round Robin's next request still goes to A even though B is occupied and A is free. Least Connections routes the next request to A automatically — because A's counter is 0 and B's is 1 — without needing to know anything about request durations. It adapts implicitly: slow or expensive requests accumulate connections on a backend, naturally reducing the traffic it receives.

**Q4. What is the core assumption Least Connections makes?**
A: That connection count is a reasonable proxy for backend load. This holds when: each connection consumes roughly similar resources on the backend, connection duration correlates with server busyness, and backends are homogeneous. When these assumptions break — e.g., some connections are idle keep-alives, backends have different capacities, or CPU load doesn't correlate with connection count — LC's accuracy degrades.

**Q5. What is the algorithm's time complexity per routing decision?**
A: Naively O(N) — scan all backends, find the minimum connection count, route there. In practice this is fine for small N (typical backend pools are 5–100 nodes). For large N, the minimum can be maintained in a min-heap (O(log N) per update), or an approximation like Power of Two Choices (O(1)) can replace the exact global minimum.

## Section 2: Variants

**Q6. What is Weighted Least Connections (WLC)?**
A: An extension combining capacity weights with live connection counts. Instead of routing to the backend with the absolute fewest connections, it routes to the one with the lowest ratio of active connections to weight:

```
score(backend) = active_connections / weight
```

The backend with the lowest score is selected. This means a backend with weight=4 can hold 4x as many connections as a backend with weight=1 before it stops being preferred. WLC handles heterogeneous fleets where backends have different capacities — it's the default algorithm in Linux Virtual Server (LVS/IPVS) and a common choice in HAProxy.

**Q7. What is Least Response Time (LRT) and how does it differ from Least Connections?**
A: LRT routes to the backend with the lowest combination of active connections and observed response latency. A common formula:

```
score(backend) = active_connections * mean_response_time
```

Or in some implementations:
```
score(backend) = active_connections + (response_time / threshold)
```

Difference from LC: LC assumes all connections are equally expensive. LRT additionally tracks how fast backends are actually responding. A backend with 3 connections but very fast responses may score better than one with 1 connection but a slow response. NGINX Plus supports this as `least_time`; Envoy approximates it with `LEAST_REQUEST` combined with active health check latency tracking.

**Q8. What is Random Least Connections (or "jittered" LC)?**
A: Instead of always routing to the backend with the absolute minimum connections (which can cause ties to be broken deterministically, creating patterns), Random LC picks randomly among the N backends that are tied for minimum connections. This avoids the "thundering herd on one backend" problem when many backends are at the same connection count — instead of always picking the first one in the list, traffic is spread randomly among the tied group.

**Q9. What is NGINX's `least_conn` directive and what does it actually do?**
A: `least_conn` in NGINX activates Weighted Least Connections for the upstream block. NGINX tracks active connections per backend and routes each new request to the backend with the fewest, adjusted for weight if weights are set. In case of a tie, NGINX uses a round-robin-like fallback among tied backends. The implementation uses per-worker counters (NGINX is multi-process/single-threaded per worker), so the global minimum isn't perfectly accurate across all workers — but in practice this approximation is fine.

**Q10. What is NGINX Plus's `least_time` directive?**
A: An extension available only in NGINX Plus (commercial) that implements Least Response Time. It can be configured to use either the time to receive the response header (`header`) or the time to receive the full response (`last_byte`):

```nginx
upstream backend_pool {
    least_time header;
    server backend1;
    server backend2;
    server backend3;
}
```

This gives a more accurate picture of backend load than connection count alone — a backend that's fast but temporarily busy can be preferred over one that's slow but free.

## Section 3: When Least Connections Wins and When It Fails

**Q11. What workloads benefit most from Least Connections?**
A: LC excels when request cost is highly variable:
- **Long-polling / streaming endpoints** — a request may hold a connection open for 30+ seconds while another closes in 50ms. LC naturally deweights the backend holding long-poll connections.
- **Mixed workloads** — APIs where some endpoints return cached results in 5ms and others do heavy DB joins or report generation taking seconds.
- **File upload/download services** — upload duration depends on file size and client bandwidth, wildly variable.
- **WebSocket services** — connections are long-lived by definition; LC prevents one backend from accumulating all the persistent connections while others sit idle.
- **Database connection pools** — LC is used internally by connection poolers (e.g., PgBouncer in round-robin mode vs. least-conn mode) to distribute DB clients across DB nodes.

**Q12. When does Least Connections perform worse than Round Robin?**
A: When all requests have uniform, short duration. At high QPS with fast requests (e.g., 1–5ms p99), connections open and close so rapidly that the connection counter is almost always 0 or 1 across all backends. LC degenerates to approximately round-robin behavior — but with the overhead of maintaining and reading atomic counters. Round Robin is simpler and slightly more cache-friendly in this case. LC's advantage only materializes when variance in connection duration is meaningful.

**Q13. What is the "idle keep-alive connection" problem with Least Connections?**
A: HTTP keep-alive maintains open connections between client and backend even when no request is in-flight. Many LBs count these idle keep-alive connections as "active." A backend that recently served many fast requests may show a high connection count from idle keep-alives — even though it's actually doing no work. LC would then under-select it, sending traffic to a busier backend. Solutions: distinguish between idle and active connections (harder to track), use HTTP/1.1 `Connection: close`, shorten keep-alive timeouts, or switch to Least Response Time which is insensitive to idle connections.

**Q14. Can Least Connections cause "the best backend gets all the traffic" (thundering herd)?**
A: Yes — this is a known failure mode called the **herding problem**. If one backend momentarily finishes all its requests and drops to 0 connections while others have 1+, the LC algorithm routes the next N requests all to it until its count rises enough to no longer be the minimum. This creates a burst on the "empty" backend. In practice mitigations are: using LC with small jitter, using P2C (which samples 2 random backends rather than scanning all), or using Least Response Time which is less prone to this since latency smooths out the signal.

**Q15. What happens with Least Connections when a backend is slower than others but not slow enough to fail health checks?**
A: It accumulates connections — which is exactly the intended behavior. If backend C is 2x slower than A and B, it'll hold 2x more in-flight connections on average, so LC will route fewer new connections to it automatically, without any manual weight tuning. This is LC's key adaptive property: degraded backends self-regulate without operator intervention. This contrasts with WRR, where you'd have to manually detect the slowdown and reduce the weight.

**Q16. How does LC behave when a new backend joins the pool?**
A: A new backend starts with 0 connections — the minimum possible — so LC immediately routes all new connections to it until its count rises to match the pool average. This is exactly the thundering herd / cold start problem (Q14). Without slow start, the new instance gets hammered before its caches, JIT compiler, and connection pools are ready. The same slow start mechanism used with WRR applies here: gradually increase the backend's effective weight from 0 to full, or use a "new backend" grace period before adding it to full rotation.

## Section 4: Implementation Details

**Q17. How does a multi-threaded LB safely maintain per-backend connection counters?**
A: Each backend's connection count is an atomic integer (e.g., `std::atomic<int>` in C++, `sync/atomic.Int64` in Go). Increment is atomic on connection open, decrement on close. The selection step (find minimum, route there) is a read-then-act operation — there's a TOCTOU (time-of-check to time-of-use) window where two threads may both read the same backend as minimum and both route to it. This is acceptable — the slight over-assignment corrects itself in the next cycle. Locking the entire selection is too expensive at high QPS.

**Q18. How does a distributed fleet of LB instances handle Least Connections — do they share state?**
A: Generally, no — sharing per-backend connection counts across a fleet of LB instances would require a distributed coordination layer (e.g., a shared in-memory store or consensus protocol), adding latency and complexity. Instead, each LB instance maintains its own local counters and makes locally-optimal decisions. The aggregate result approximates global LC, because if one LB instance happens to send more connections to backend A, A becomes slower, and other LB instances using LC (or LRT) will deprioritize it. In large-scale deployments (e.g., Google), algorithms like P2C with local counters work around this — P2C's theoretical guarantees hold even without global coordination.

**Q19. What is the difference between per-connection and per-request LC tracking at L7?**
A: At L7 with connection pooling, the LB reuses backend connections across multiple client requests. "Active connections" can mean:
- **Per-TCP-connection**: counts open TCP connections to the backend — doesn't reflect in-flight requests on multiplexed connections (HTTP/2, gRPC).
- **Per-request / per-stream**: counts in-flight HTTP requests or gRPC streams. More accurate for HTTP/2 workloads where many streams share one TCP connection.

Envoy's `LEAST_REQUEST` policy tracks active requests (not just connections), making it correct for gRPC and HTTP/2 where TCP connection count is a misleading signal.

**Q20. What is Envoy's `LEAST_REQUEST` policy, and how does it differ from standard LC?**
A: Envoy calls its LC variant `LEAST_REQUEST`. Key distinctions:
- Tracks **active requests** (HTTP requests / gRPC streams), not TCP connections — correct for HTTP/2.
- Uses **Power of Two Choices** by default (configurable `choice_count`) rather than scanning all backends — O(1) per selection, scales to large pools.
- Supports **active request bias** — applies a configurable multiplier that makes backends with more active requests less preferred, tuning the sensitivity of the algorithm.
- Integrates with Envoy's outlier detection — if a backend starts returning 5xx or timing out, it's ejected from the pool regardless of connection count.

This makes `LEAST_REQUEST` in Envoy strictly more capable than a plain LC implementation.

## Section 5: Least Connections in the Stack

**Q21. How does LC interact with connection pooling at the LB?**
A: When the LB maintains a pool of reused connections to backends (common in L7 proxies), the "active connections" metric tracked by LC is the number of in-use connections from the pool — not the total pool size. Idle pooled connections don't count as active load. This makes LC more accurate in a connection-pooling L7 LB (like Envoy) than in an L4 LB doing passthrough, where every TCP connection from a client is a new backend connection.

**Q22. How does HAProxy implement Least Connections?**
A: HAProxy's `leastconn` algorithm selects the server with the lowest number of connections. In case of a tie, it uses a round-robin-like rotation. HAProxy's `leastconn` is most appropriate for long-lived connections (it explicitly recommends this in the docs for protocols like LDAP, SQL, RDP). For short HTTP requests, HAProxy recommends `roundrobin` or `static-rr` because the overhead of LC isn't justified. HAProxy also supports `leastconn` combined with server weights — which is effectively Weighted Least Connections.

**Q23. Where in a typical microservices architecture would you use Least Connections vs Round Robin?**
A: Rule of thumb:
- **API Gateway / Ingress (north-south)**: LC for user-facing endpoints with variable request cost (upload, search, report). Round Robin for uniform, fast endpoints (health checks, simple reads).
- **Service-to-service (east-west, via service mesh)**: LC (or Envoy's `LEAST_REQUEST`) for services with variable latency. Round Robin for uniform, cache-backed services.
- **Database connection pooling**: LC (or WLC) is standard for distributing client connections across DB replicas — PgBouncer, ProxySQL, and similar tools use it.
- **L4 LB → L7 LB fleet**: Round Robin is fine here — L7 LB instances are homogeneous and stateless from the L4 perspective.

**Q24. What does the Linux Virtual Server (LVS/IPVS) implementation of Least Connections look like?**
A: IPVS (IP Virtual Server, built into the Linux kernel) supports both `lc` (Least Connection) and `wlc` (Weighted Least Connection) as scheduling algorithms. It maintains an in-kernel connection table with per-real-server active and inactive connection counts. The scoring formula for `wlc` is:

```
score = (active_conns * 256 + inactive_conns) / weight
```

Active connections are weighted 256x more than inactive (TIME_WAIT / FIN_WAIT state) connections. This means recently-finished connections still count a little, preventing a backend from immediately being flooded the moment it closes a connection. IPVS is used by kube-proxy in IPVS mode and by many high-performance L4 LB implementations.

## Section 6: Failure Modes & Edge Cases

**Q25. What is the "oscillation" problem in Least Connections?**
A: In a two-backend system at high QPS, LC can oscillate: A reaches minimum, gets traffic, B becomes minimum, gets traffic, repeat. With perfectly synchronized fast requests, this degenerates to alternating round-robin. With slightly asynchronous connections, it can cause both backends to be selected simultaneously by concurrent threads (TOCTOU), momentarily over-assigning one backend. At moderate QPS, this self-corrects instantly. At very low QPS (1–2 req/sec), oscillation can cause most requests to pile on one backend before the other connection closes. At very low QPS with variable duration, prefer WRR with manually tuned weights.

**Q26. What happens when a backend's connection count is stuck high due to leaked connections?**
A: If a backend has connection leaks (connections that were opened but never properly closed — common in buggy keep-alive handling or misconfigured timeouts), its LC counter stays artificially high. LC then avoids routing to it, sending more traffic to other backends than intended — effectively removing the leaky backend from rotation without it being marked unhealthy. This is a silent failure: the backend is alive and responding but under-utilized because of a counter artifact. Fix: set connection timeouts aggressively, ensure proper FIN/RST handling, and monitor per-backend connection counts over time for unexpected drift.

**Q27. How do you handle a backend that becomes slow without failing health checks (the "grey failure" problem)?**
A: This is one of the hardest operational problems in load balancing:
- **LC** partially helps — the slow backend accumulates connections, reducing new traffic to it. But it doesn't remove it from rotation entirely.
- **LRT (Least Response Time)** — more sensitive: even if connection count is moderate, high latency reduces the score, further deprioritizing the slow backend.
- **Outlier detection / circuit breaking** (Envoy) — track per-backend error rate and response time; eject backends that exceed configurable thresholds (e.g., consecutive 5xx, p99 latency > threshold).
- **Active health checks with latency thresholds** — probe backends and consider latency-based health (not just binary up/down).

LC alone is necessary but not sufficient for grey failures. It must be combined with circuit breaking for robust handling.

**Q28. What is "connection count inflation" in proxied environments and how does it affect LC?**
A: In a service mesh with Envoy sidecars, each pod's sidecar proxy maintains connections to other pods' sidecars. From the LC perspective of an upstream proxy, the connection count it sees is sidecar-to-sidecar connections — which includes connections from many different downstream callers pooled through each sidecar. The upstream LB's LC counter reflects the aggregate load aggregated at the sidecar level, not individual request counts. This is why Envoy's `LEAST_REQUEST` tracks active requests at the HTTP layer rather than TCP connections — it pierces the connection pool abstraction to get accurate load signal.

## Section 7: Comparison With Other Algorithms

**Q29. Least Connections vs Round Robin — decision matrix.**
A:

| Signal | Use Round Robin | Use Least Connections |
|---|---|---|
| Request duration variance | Low (p99 ≈ p50) | High (fat tail, p99 >> p50) |
| Connection type | Short-lived HTTP | Long-lived (WS, gRPC, streaming) |
| Backend homogeneity | Homogeneous | Homogeneous or mixed |
| QPS | Very high (LC overhead not worth it) | Moderate to high |
| Operational simplicity | ✅ Simpler | Slightly more complex |

**Q30. Least Connections vs Least Response Time — when is the extra complexity worth it?**
A: LRT is strictly more informative than LC — it uses both connection count and measured response latency. Use LRT when:
- Backends experience intermittent slowdowns not reflected in connection count (e.g., GC pauses, disk flush, CPU steal in shared VMs).
- You have mixed-speed backends where a slower one might appear "available" (low connection count) but would respond slowly.
- Latency SLAs are tight (p99 < 50ms) — LRT actively steers away from slow backends, tightening the distribution.

LRT cost: it requires the LB to measure and store moving-average response times per backend — slightly more state and computation. Worth it for latency-sensitive services. Not needed if backend response times are consistently uniform.

**Q31. Least Connections vs Power of Two Choices (P2C) — which scales better?**
A: 
- **LC (global minimum)**: O(N) to find the minimum, requires scanning all backends. In a distributed LB fleet, coordinating the global minimum requires cross-instance communication.
- **P2C**: O(1) — pick 2 random backends, route to the less loaded one. No global scan, no coordination across LB instances. Provably achieves load distribution within O(log log N) of optimal vs O(log N) for pure random. Scales to large backend pools and large LB fleets without degradation.

For pools of < ~50 backends with a single LB instance, the O(N) overhead of global LC is negligible. For large distributed systems with many backends or many LB instances (the Google/Netflix/Uber scale), P2C is strictly superior.

**Q32. Least Connections vs Consistent Hashing — are they mutually exclusive?**
A: They serve different goals and can be combined:
- **LC** optimizes for even load distribution — use it for stateless services.
- **Consistent Hashing** optimizes for key affinity — use it for stateful/caching layers where the same key must hit the same backend for cache hit ratio.

You might use LC at the application server layer (stateless, even load desired) and Consistent Hashing at the cache layer (Memcached/Redis, same key = same node). They're not competing algorithms — they solve different problems.

## Section 8: Scenario-Based Questions

**Q33. "Your API has a /search endpoint (avg 200ms) and a /ping endpoint (avg 2ms) behind the same LB pool. You're using Round Robin. What's the problem and what do you change?"**
A: /search requests hold connections ~100x longer than /ping. With Round Robin, every third request (or whatever the rotation is) goes to each backend regardless — a backend serving 3 simultaneous /search requests gets the same new traffic rate as one serving 3 /ping requests. The backend with multiple in-flight /search requests queues up and shows elevated latency. Switch to Least Connections: backends holding active /search requests accumulate connections and receive fewer new requests, while backends that finished fast /ping requests drop to low counts and absorb more. Better long-term fix: route /search and /ping to separate backend pools entirely (since their resource profiles differ significantly).

**Q34. "You have a database with 1 primary and 3 replicas behind a read-replica LB using Round Robin. One replica is running on older hardware and is 30% slower. What algorithm do you change to, and how does it help?"**
A: Switch to Weighted Least Connections. With Round Robin, each replica gets 33% of reads — the slow one is constantly falling behind, showing higher query latency. Options:
1. **WLC with manually tuned weights**: reduce the slow replica's weight (e.g., 2,2,2,1), reducing its share of connections proportionally.
2. **Plain LC**: the slow replica accumulates more in-flight connections naturally, self-regulating its load downward without manual weight tuning. However, LC doesn't prevent it from being assigned new connections during its brief idle moments — WLC is cleaner for a known permanently slower backend.

Best answer: WLC with reduced weight on the slow replica, plus a plan to replace the hardware.

**Q35. "You're running 5 instances of a gRPC service behind an Envoy proxy using `ROUND_ROBIN`. Engineers report that one instance consistently handles 80% of RPCs. What's happening and how do you fix it?"**
A: Classic L7 gRPC load balancing problem — but with a twist. If the L7 proxy is using `ROUND_ROBIN` at the TCP connection level rather than the request/stream level, and gRPC clients hold long-lived connections, all RPCs from a given client may go to one backend. Fix: ensure Envoy's LB policy is applied at the request level (which it does by default with HTTP/2 stream balancing), and verify that client-side connection management isn't creating persistent connections that bypass the LB. Switch policy to `LEAST_REQUEST` — Envoy's `LEAST_REQUEST` tracks active RPC streams, not just connections, giving a more accurate view of per-backend load for gRPC.

**Q36. "After a deployment, one backend takes 2 minutes to warm up (JVM JIT + cache) and starts returning 500ms p99 vs 20ms for others. How does Least Connections handle this, and is it enough?"**
A: LC partially helps — the slow backend will accumulate connections faster than others, causing LC to deprioritize it. But "partially" is key: LC doesn't remove the backend; it just reduces (not eliminates) traffic to it. During those 2 minutes, some users still hit the slow backend. Better strategy:
1. **Slow start** — don't add the backend to full rotation immediately; ramp its weight over 2 minutes.
2. **LC + outlier detection** — Envoy's outlier detection can eject the backend if its p99 exceeds a threshold, completely removing it until it recovers.
3. **Readiness probe** — Kubernetes readiness probe should ensure the pod isn't added to the Service until it's actually warm. This is the cleanest solution: LC never even sees the cold backend because it's not in the pool yet.
