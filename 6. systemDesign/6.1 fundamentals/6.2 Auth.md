# API Gateway: Auth — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "auth at the gateway" actually mean, and what is it trying to centralize?**
A: It means the API Gateway is responsible for validating who (or what) is making a request — and, to varying degrees, what they're allowed to do — before that request is forwarded to any backend service. The goal is centralizing credential validation logic (parsing and verifying API keys, JWTs, OAuth tokens, mTLS certificates) in exactly one place, applied consistently to all traffic entering the system, rather than every individual backend service independently reimplementing the same validation logic — with all the inconsistency and duplicated security-critical code that would imply.

**Q2. What's the precise distinction between authentication and authorization, and why does conflating them cause real problems?**
A: Authentication (AuthN) answers "who is making this request" — verifying identity via a credential. Authorization (AuthZ) answers "is this identified party allowed to do this specific thing." Conflating them causes real problems because a system can correctly authenticate a request (genuinely confirm who's asking) while still needing a separate, distinct decision about whether that identity has permission for the specific action being attempted — treating "the token is valid" as equivalent to "this request is allowed" skips an entire necessary decision step, and is a common source of authorization bugs (e.g., a validly authenticated user successfully accessing or modifying another user's resource, because only authentication, not authorization, was actually checked).

**Q3. Why is the gateway a natural place for authentication specifically, but a less complete place for authorization?**
A: Authentication is relatively uniform — validating a token's signature, checking expiry, extracting claims — regardless of what the request is actually trying to do, so it generalizes cleanly to a single shared implementation at the edge. Authorization, especially fine-grained authorization, often depends on business-logic context the gateway doesn't have (does this specific user own this specific resource, is this specific record in a state that permits this specific operation) — context that typically lives inside the backend service that actually understands the domain. The gateway is well-suited for *coarse-grained* authorization (does this identity have access to this API/route at all) but fine-grained, resource-specific authorization is usually left to the backend service itself.

**Q4. What's the risk of a backend service blindly trusting that "if the request reached me, it must be properly authenticated"?**
A: This trust is only valid if the network path between the gateway and that backend service is itself genuinely private and unreachable by anything other than the gateway — if a backend service can be reached directly (bypassing the gateway), an attacker with access to that internal network path can send unauthenticated or forged requests straight to the backend, which would blindly trust them as already-validated. This is why gateway-centralized auth needs to be paired with actual network-level enforcement (private networking, firewall rules, service mesh mTLS) ensuring backend services genuinely can't be reached except through the gateway — otherwise the "auth is centralized at the gateway" model has a real, exploitable gap.

## Section 2: Authentication Mechanisms

**Q5. What is API key authentication, and what are its limitations?**
A: A simple, typically static, opaque string issued to a client/application, sent with each request (commonly as a header, e.g., `X-API-Key`) and validated by the gateway against a known list of issued keys. It's simple to implement and reason about, making it common for service-to-service integrations and third-party API consumers. Limitations: it's a long-lived, static credential — if leaked (committed to a public repo, logged accidentally, intercepted), it remains valid until manually revoked, with no built-in expiry; it typically identifies an *application/client*, not an individual end user, so it's poorly suited for representing per-user identity or permissions on its own; and it carries no structured claims (roles, scopes) unless the gateway separately looks those up from the key via a backing store.

**Q6. What is JWT (JSON Web Token) authentication, and why is it commonly used at the gateway?**
A: A JWT is a compact, self-contained, cryptographically signed token containing a set of claims (identity, expiry, scopes/roles, and other metadata) encoded in its payload. It's commonly used at the gateway because the gateway can validate it **statelessly** — verifying the cryptographic signature and checking the expiry/claims locally, without needing to call out to a separate identity service or database on every single request — which keeps the validation step fast and avoids adding an external dependency to the hot path of every request, in contrast to mechanisms that require a lookup against a backing store.

**Q7. What is OAuth 2.0's role at the gateway, and how does it typically combine with JWT?**
A: OAuth 2.0 is fundamentally an authorization *framework* — a set of standardized flows for how a client obtains an access token (often after a user grants consent), rather than a token format itself. In modern practice, the access token OAuth issues is very commonly implemented as a JWT (sometimes called "JWT-based OAuth" or, more formally, often layered with OpenID Connect for identity specifically), meaning the gateway's job becomes validating that JWT access token (per Q6) according to standard JWT validation, while the *issuance* of that token (the actual OAuth flow — authorization code grant, client credentials grant, etc.) happens earlier, against a separate authorization server, before the token ever reaches the gateway.

**Q8. What is mutual TLS (mTLS) authentication, and when is it typically used at the gateway level?**
A: In mTLS, both the client and the server present X.509 certificates to authenticate each other (standard TLS only authenticates the server to the client; mTLS adds client authentication too) — the gateway, acting as the TLS-terminating server, validates the client's presented certificate against a trusted certificate authority before allowing the connection/request through. It's typically used for especially sensitive integrations — partner/B2B API access, service-to-service communication between organizations, or internal infrastructure requiring very strong, hard-to-forge identity guarantees — since certificate-based identity is generally harder to leak/replay accidentally than a bearer token that can be copy-pasted or logged inadvertently.

**Q9. What's the difference between a "bearer" credential (like a typical API key or JWT) and the certificate-based identity mTLS provides, from a security standpoint?**
A: A bearer credential's security model is exactly what the name implies: whoever *bears* (possesses) the token is treated as authenticated, regardless of how they obtained it — if it leaks, anyone holding the leaked value can impersonate the legitimate client until the token is revoked or expires. mTLS's certificate-based model ties authentication to possession of a private key that, properly managed, never needs to be transmitted or exposed in the request itself (only the certificate, the public part, is presented, and the private key is used locally to prove possession during the TLS handshake) — making it meaningfully harder to leak via the same common channels that compromise bearer tokens (logs, browser history, accidental commits, network interception of the actual credential value itself).

## Section 3: JWT Validation in Depth

**Q10. What are the core components of a JWT, and what does the gateway need to check in each?**
A: A JWT has three base64url-encoded parts separated by dots: a **header** (specifying the signing algorithm and key identifier), a **payload** (the actual claims — issuer, subject, expiry, audience, custom claims like roles/scopes), and a **signature** (cryptographically binding the header and payload together, generated using the issuer's private/signing key). The gateway needs to: verify the signature is valid using the correct corresponding public key (confirming the token genuinely came from the expected issuer and hasn't been tampered with); check the `exp` (expiry) claim hasn't passed; typically check the `iss` (issuer) and `aud` (audience) claims match what's expected for this gateway/API; and then extract whatever claims (roles, scopes, user ID) are needed for subsequent authorization decisions.

**Q11. Why is it critical that the gateway validates the JWT's signature using a key it independently trusts, rather than trusting an algorithm specified inside the token itself?**
A: This points to a well-known, real-world JWT vulnerability class: if the gateway's validation logic blindly trusts the `alg` field inside the token's own header to decide *how* to verify it, an attacker can craft a token claiming `"alg": "none"` (no signature required at all) or attempt an algorithm-confusion attack (e.g., a token signed with a symmetric algorithm using the issuer's known-public RSA public key as the symmetric secret, exploiting a validator that doesn't strictly enforce which algorithm family is expected). Correct, secure validation hardcodes the *expected* algorithm(s) on the verifying side (the gateway decides what algorithm it will accept, independent of what the token claims) rather than deferring that decision to attacker-controlled content within the token itself.

**Q12. What is a JWKS (JSON Web Key Set) endpoint, and what role does it play in gateway-side JWT validation?**
A: A JWKS endpoint is a URL (typically published by the token issuer/identity provider) that exposes the current public key(s) used to verify tokens it has signed, in a standardized JSON format, often including a key ID (`kid`) so a verifier can match a specific token's header-specified key ID to the correct public key in the set (supporting key rotation, where multiple valid keys may be active simultaneously during a rollover period). The gateway typically fetches and caches this JWKS data periodically (rather than fetching it fresh on every single request, which would add a real-time external dependency to the hot path), refreshing it on a schedule or when it encounters a `kid` it doesn't yet have cached.

**Q13. JWTs are commonly described as "stateless" — what does that mean precisely, and what's the trade-off it implies for revocation?**
A: Stateless means the token itself carries everything needed to validate it (signature, claims, expiry) without the verifier needing to consult any external state/database on each validation — that's exactly what makes gateway-side validation fast and dependency-free per request (Q6). The direct trade-off: since validation doesn't consult any live, mutable state, there's no natural way to immediately invalidate a specific already-issued token before its embedded expiry — if a token is compromised, or a user's access needs to be revoked immediately (account suspended, permissions changed), a purely stateless JWT scheme has no built-in mechanism to reject that specific token early; it remains valid, from the gateway's stateless-verification perspective, until it naturally expires.

**Q14. Given the revocation limitation in Q13, what are common mitigations?**
A: Keep JWT expiry times relatively short (minutes, not days), limiting the maximum window an attacker or revoked user could exploit a still-valid-but-supposedly-revoked token, paired with a separate refresh-token mechanism (typically a longer-lived, more carefully-protected token used to obtain new short-lived access tokens) that *can* be revoked server-side, since refresh-token issuance does go through a stateful check against the authorization server. Some systems also introduce an explicit, checked **revocation/denylist** (a smaller, focused piece of mutable state the gateway or authorization server consults specifically for "has this token been explicitly revoked," reintroducing a limited amount of statefulness deliberately, scoped just to that purpose, rather than abandoning JWT's stateless-validation benefits entirely for everything).

## Section 4: OAuth 2.0 / OIDC Flows at the Gateway

**Q15. What is the difference between self-contained token validation and token introspection, and when is each used at the gateway?**
A: Self-contained validation (Q6) means the gateway can verify the token entirely on its own (signature + claims), with no external call needed — appropriate when the access token is a JWT the gateway has the means to validate independently. Token introspection (an OAuth 2.0 standard, RFC 7662) instead means the gateway sends the token to a dedicated endpoint on the authorization server and asks "is this token currently valid, and if so, what are its associated claims/scopes" — used when the token is opaque (not a JWT, or a JWT-format token where the issuer deliberately wants live state-checking) and genuinely requires checking live, current state (catching revoked tokens in real time, addressing exactly the limitation in Q13). The trade-off is the same general one as Q18 in the rate-limiting guide's discussion of external dependencies in the request path: introspection adds a real-time network call and a dependency on the authorization server's availability to every single gateway-validated request, in exchange for accurate, live revocation awareness that pure self-contained validation can't provide.

**Q16. What is the client credentials grant, and why is it particularly relevant to gateway-fronted service-to-service traffic?**
A: A client credentials grant is an OAuth 2.0 flow where an application (not acting on behalf of an end user) authenticates directly to the authorization server using its own client ID and secret, and receives an access token representing the application itself — no user, no consent screen, no redirect-based flow involved. This is the natural fit for machine-to-machine traffic through the gateway (one backend service calling another, or a trusted partner system calling an API), since there's no human user in the loop to authenticate or grant consent — the calling application's own identity is what's being authenticated and represented in the resulting token.

**Q17. What is the authorization code grant, and why does the gateway typically not participate directly in this flow's early steps?**
A: The authorization code grant is OAuth's flow for representing an actual end user's consent — the user is redirected to the authorization server, authenticates and grants permission, and the client application receives a short-lived authorization code which it then exchanges (server-side, with its client secret) for an access token. The gateway typically isn't directly involved in the redirect/consent dance itself (that happens between the client application, the user's browser, and the authorization server) — the gateway's role begins downstream of that flow, simply receiving and validating the resulting access token on subsequent API calls, the same way it would validate a token obtained via any other grant type, since by the time a request reaches the gateway, the distinction in *how* the token was originally obtained is no longer relevant to validation.

**Q18. What is OpenID Connect (OIDC), and how does it relate to OAuth 2.0 in the context of gateway authentication?**
A: OIDC is an identity layer built on top of OAuth 2.0 — OAuth 2.0 alone is fundamentally about authorization (granting access to resources), not standardized identity assertion; OIDC adds a standardized **ID token** (a specific JWT format with standardized identity claims) and standardized endpoints/flows specifically for authenticating *who the user is*, not just what they're allowed to access. At the gateway, this distinction matters because an OAuth access token (used to authorize API calls) and an OIDC ID token (used to assert identity, typically consumed by the client application itself rather than sent on every API call) serve different purposes — a gateway validating API requests is generally validating access tokens, not ID tokens, even in a system that also uses OIDC for the initial user login/identity-establishment step.

## Section 5: Propagating Identity Downstream

**Q19. Once the gateway validates a credential, how does it typically communicate the resulting identity to backend services?**
A: Commonly via internal headers added to the proxied request before forwarding it downstream — e.g., `X-User-Id`, `X-User-Roles`, `X-Client-Id` — populated from the claims the gateway extracted during validation. Backend services then read and trust those headers directly, rather than each one independently re-parsing and re-validating the original raw credential (the JWT, the API key) themselves. This only works correctly under the trust-boundary assumption from Q4: the path from gateway to backend must be genuinely private, since anything able to inject its own version of those headers directly to a backend (bypassing the gateway) could trivially impersonate any identity.

**Q20. What's the risk if a backend service doesn't strip or overwrite identity headers on requests that somehow arrive *not* via the gateway, or if the network boundary isn't airtight?**
A: If those internal trust headers (`X-User-Id`, etc.) can also be set directly by an external client in a raw request that reaches the backend without passing through the gateway's validation/stripping logic, an attacker could simply set `X-User-Id: admin` themselves and have the backend trust it completely, fully bypassing the gateway's auth entirely. The correct mitigation is defense in depth: the gateway should explicitly **strip any client-supplied versions of these trust headers** before adding its own validated versions (so a client can't pre-set a header hoping it survives through to the backend unexamined), and the network path itself should make it actually infeasible for any request to reach a backend service without first passing through the gateway.

**Q21. What is "token exchange," and when might a gateway use it rather than simply forwarding the original validated token unchanged?**
A: Token exchange (a distinct OAuth extension, RFC 8693) is a mechanism where the gateway (or an intermediate service) trades an inbound token for a *different* token — often with a narrower scope, different audience, or shorter lifetime — specifically for use in calls to a particular downstream service, rather than forwarding the original, potentially broadly-scoped client-facing token unchanged into internal service-to-service calls. This is used to apply the principle of least privilege internally: a token that legitimately grants a client broad access to the public API doesn't need to carry that same broad scope into every internal downstream call it triggers — exchanging it for a more narrowly-scoped internal token limits the blast radius if that downstream token were somehow intercepted or misused.

## Section 6: Authorization at the Gateway

**Q22. What does "coarse-grained authorization at the gateway" typically look like in practice?**
A: Route-level or scope-level checks: does this token/identity have the required scope or role claim to access this specific API route at all (e.g., requiring a `read:orders` scope on the JWT before allowing a request through to the orders API's GET endpoints), independent of any deeper business-logic question about the specific resource being accessed. This is a relatively simple, declarative check the gateway can perform directly against claims already present in the validated token, without needing any additional business context.

**Q23. Why does fine-grained, resource-specific authorization usually have to live in the backend service rather than the gateway?**
A: Questions like "does this specific user own this specific order record" or "is this specific document currently in a state that permits this specific edit" require business-domain context — the actual current state of a specific resource — that the gateway, by design, doesn't have and shouldn't need to fetch and understand for every route across every service it fronts (doing so would effectively require the gateway to replicate significant business logic and data access for every backend it serves, defeating the purpose of keeping the gateway as a relatively thin, generic, cross-cutting layer). The backend service that actually owns and understands that resource is the natural, and usually only practical, place to make that specific determination.

**Q24. What is RBAC (Role-Based Access Control), and how is it commonly implemented at the gateway layer?**
A: RBAC grants permissions based on a user's assigned role(s) (admin, editor, viewer, etc.) rather than evaluating permissions individually per user. At the gateway, this commonly looks like: the validated token carries a `roles` claim, and gateway-level route configuration specifies which role(s) are required to access a given route — a relatively simple, declarative mapping the gateway can enforce directly from claims already present in the token, without needing to consult any external system at request time.

**Q25. What is ABAC (Attribute-Based Access Control), and how does it differ from RBAC in terms of what the gateway can practically enforce?**
A: ABAC makes authorization decisions based on a broader, more flexible set of attributes — not just a static role, but potentially attributes of the user, the resource being accessed, the environment (time of day, request origin), and the specific action being attempted, combined via policy rules. ABAC decisions are often genuinely more complex than something the gateway can practically evaluate using only claims already present in a token — they frequently require consulting attributes about the *specific resource* being accessed, which (per Q23) the gateway typically doesn't have. This is why genuinely rich ABAC policies are more commonly enforced via a dedicated policy engine (Q26) or pushed into the backend service, with the gateway at most enforcing a simpler subset of attribute checks it can evaluate from the token/request alone.

**Q26. What is a dedicated policy engine (e.g., Open Policy Agent / OPA), and what role can it play alongside an API Gateway?**
A: A policy engine externalizes authorization decision logic into a separate, declarative policy language and evaluation service, which the gateway (or backend services) can query at request time — "given this identity, this resource, this action, and these attributes, is this allowed?" — rather than hardcoding authorization rules directly into gateway configuration or scattering them across backend service code. This allows authorization policy to be defined, versioned, tested, and updated centrally and consistently, independent of gateway or service deployment cycles, and supports more sophisticated ABAC-style decisions than simple role-claim checks alone — at the cost of introducing another network call/dependency into the request path, similar in nature to the token-introspection trade-off discussed in Q15.

## Section 7: Security Considerations

**Q27. What is token replay, and what mitigations exist at the gateway level?**
A: Token replay is an attacker capturing a legitimate, valid token (via interception, log exposure, or a compromised client) and reusing it to make their own requests, impersonating the original client for as long as the token remains valid. Mitigations include keeping token lifetimes short (limiting the exploitable window, per Q14), enforcing TLS everywhere so tokens aren't transmitted in a form interceptable over the network, and in higher-security contexts, binding tokens to additional context (e.g., proof-of-possession mechanisms, or mTLS-bound tokens where the token is only valid when presented alongside the specific client certificate it was issued for) so a bare, copied token value alone isn't sufficient to impersonate the legitimate client even if intercepted.

**Q28. Why does key rotation matter for JWT signing keys, and what's the operational risk of rotating carelessly?**
A: Signing keys, like any long-lived cryptographic secret, should be periodically rotated to limit the impact of an undetected compromise — if a signing key is ever leaked, an attacker could forge arbitrarily valid tokens until that key is rotated out. The operational risk of rotating carelessly: if old, already-issued, still-unexpired tokens were signed with a key that gets immediately and fully removed from the gateway's trusted key set the moment rotation happens, those still-valid tokens suddenly fail validation, potentially causing a wave of legitimate authentication failures. The standard mitigation is publishing both the old and new keys in the JWKS (Q12) for an overlap period (long enough for all tokens signed with the old key to naturally expire) before fully retiring the old key, rather than an abrupt cutover.

**Q29. What's the risk of overly permissive token scopes, and how does the principle of least privilege apply at the gateway?**
A: A token with broad, unnecessary scope grants more access than the legitimate use case actually requires — if that token is ever compromised (leaked, replayed, stolen from a compromised client), the resulting blast radius is as large as the token's full granted scope, even if the specific compromised context only ever needed a small fraction of it. Applying least privilege at the gateway means enforcing scope checks precisely per route (not just "is this token valid" but "does this token have *exactly* the scope this specific route requires"), encouraging upstream token issuance to grant narrowly-scoped tokens for narrowly-scoped use cases rather than broad, all-purpose tokens issued for convenience, and using mechanisms like token exchange (Q21) to further narrow scope specifically for internal downstream calls.

## Section 8: Scenario-Based Questions

**Q30. "Your gateway validates JWTs by decoding the `alg` field from the token header and using whatever algorithm it specifies to verify the signature. A security review flags this as a vulnerability. Explain why, and how you'd fix it."**
A: This is the algorithm-confusion / `alg: none` vulnerability class (Q11) — trusting the token's own self-declared algorithm hands the attacker control over how their forged token gets verified, including the possibility of declaring no signature is required at all, or exploiting a mismatch between symmetric and asymmetric algorithm handling in the verifying library. The fix: the gateway should hardcode the specific algorithm(s) it expects to see and trust for a given issuer/key, independent of what the token itself claims, rejecting any token whose header specifies an unexpected algorithm outright, rather than deferring that decision to content inside the token being verified.

**Q31. "A customer reports that revoking a compromised API token through your admin dashboard doesn't seem to take effect — requests using that token keep succeeding for several more minutes. How do you explain this, and is it actually a bug?"**
A: If the system uses purely stateless JWT validation at the gateway (Q6, Q13), this is expected, not a bug per se — the gateway validates tokens based solely on signature and embedded expiry, with no live check against a "has this been revoked" state, so a token revoked in the admin dashboard remains cryptographically valid and gateway-acceptable until its embedded expiry, regardless of the revocation action. Whether this is acceptable depends on the token's configured lifetime (a token expiring in 5 minutes naturally bounds this exposure tightly) and the system's actual revocation requirements — if customers genuinely need *immediate* revocation, the fix is introducing a real revocation mechanism (a denylist check, Q14, or moving to introspection-based validation for at least this category of token, Q15), explicitly trading away pure stateless-validation simplicity for the immediacy this use case requires.

**Q32. "Two different teams' backend services, both behind the same gateway, are independently re-implementing JWT signature validation logic in their own service code, in addition to whatever validation the gateway already performs. Is this a problem, and how would you address it?"**
A: It's not inherently wrong from a pure security standpoint (defense in depth isn't bad), but it does undermine a core reason for centralizing auth at the gateway in the first place (Q1) — duplicated validation logic across multiple teams' codebases means multiple places that need to be kept correctly updated (algorithm handling, key rotation awareness, JWKS endpoint configuration) and multiple opportunities for one implementation to drift, have a subtle bug, or simply fall out of sync with the others over time. The better pattern: have the gateway perform the full, authoritative validation once, then have backend services trust the gateway-forwarded, already-validated identity (via the internal headers pattern, Q19) rather than re-parsing and re-validating the raw token themselves — reserving any backend-side checks for things genuinely outside the gateway's scope, like fine-grained, resource-specific authorization (Q23), rather than redundant signature/expiry validation that the gateway has already correctly handled.

**Q33. "Your API serves both end-user-facing mobile/web clients and trusted internal service-to-service traffic, all through the same gateway. Should both use the same auth mechanism, and how would you design the gateway's auth configuration?"**
A: Not necessarily the same mechanism, though the gateway can absolutely handle both within one unified configuration. End-user-facing traffic typically flows through an OAuth 2.0/OIDC-based authorization code grant (Q17), resulting in a user-context JWT the gateway validates per request; internal service-to-service traffic is more naturally suited to client credentials grant tokens (Q16) or mTLS (Q8–9), representing the calling service's own identity rather than an end user's. The gateway's auth configuration would typically distinguish these by route or by expected audience/issuer claim on the token, applying the appropriate validation logic and likely different scope/role requirements for each category — internal service traffic might reasonably get broader access on certain internal-only routes than any end-user token would ever be granted, reflecting their genuinely different trust levels and use cases, while still funneling through the same shared gateway infrastructure for consistent observability and centralized policy enforcement.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| AuthN vs AuthZ | Who you are vs what you're allowed to do — distinct decisions |
| API key | Simple, static, opaque; no built-in expiry or structured claims |
| JWT | Self-contained, signed; statelessly validated; no native revocation |
| OAuth 2.0 | Authorization framework defining how tokens are obtained, not a token format |
| OIDC | Identity layer on top of OAuth 2.0; adds standardized ID tokens |
| mTLS | Certificate-based mutual authentication; harder to leak than bearer tokens |
| JWKS | Published public keys for JWT signature verification; supports key rotation |
| Token introspection | Live, stateful validation call to the authorization server |
| Client credentials grant | OAuth flow for service-to-service (no end user) |
| Authorization code grant | OAuth flow for end-user consent-based access |
| Header propagation | Gateway forwards validated identity via internal headers; requires a trusted network path |
| Token exchange | Swaps a broad token for a narrower-scoped internal one |
| RBAC / ABAC | Role-based vs attribute-based authorization; ABAC often needs a policy engine |
| Policy engine (e.g., OPA) | Externalized, queryable authorization decision logic |

**Tip for interviews:** What separates strong candidates on API Gateway auth specifically: (1) being precise about **authentication vs authorization as genuinely separate decisions**, and correctly identifying that fine-grained authorization usually can't live at the gateway because it needs business context the gateway doesn't have (Q2–3, Q23); (2) understanding **JWT's core trade-off** — stateless, fast, dependency-free validation in exchange for no native revocation — and being able to discuss the standard mitigations (short expiry, refresh tokens, denylists, introspection) rather than treating JWT as a simple drop-in solution with no downsides (Q13–15); (3) knowing the **classic `alg`-confusion JWT vulnerability** and why the verifier, not the token, must dictate the trusted algorithm (Q11, Q30); (4) recognizing that **identity propagation via internal headers is only as secure as the network trust boundary behind it**, and being able to explain the header-injection bypass risk if that boundary isn't airtight (Q4, Q19–20); and (5) being able to map **OAuth grant types to the right use case** — client credentials for service-to-service, authorization code for end-user flows — and explaining why the gateway's validation responsibility looks the same regardless of which grant originally produced the token (Q16–17, Q33).
