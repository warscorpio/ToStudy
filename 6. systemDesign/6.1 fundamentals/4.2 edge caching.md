# Edge Caching — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is edge caching, and how is it broader than "CDN caching"?**
A: Edge caching is the general practice of storing data as close as possible to the point of use — at any layer between the original data source and the consumer — to reduce latency and offload upstream systems. CDN caching (covered in the CDN guide) is one specific, well-known instance of edge caching: caching HTTP responses at geographically distributed PoPs. But "edge" more broadly includes the browser cache, service workers, mobile app local storage, edge compute KV stores (Cloudflare Workers KV, Durable Objects), and even on-device ML model caching. The unifying idea is the same in every case: move data physically or logically closer to where it's consumed, trading storage duplication for latency reduction.

**Q2. What is the full caching hierarchy in a typical modern web request, from client to database?**
A: A request can pass through several caching layers, each with different scope and lifetime:
1. **Browser cache** — local to one user's device, governed by `Cache-Control`/`Expires` headers, persists across page loads.
2. **Service worker cache** — programmable, JavaScript-controlled cache running in the browser, giving the application explicit control over caching logic (including offline support).
3. **CDN / edge cache** — shared across all users near a given PoP, the layer covered in the dedicated CDN guide.
4. **Regional / mid-tier cache** — an intermediate tier some CDN architectures use between edge and origin (covered as multi-tier caching in the CDN guide).
5. **Reverse proxy / application-layer cache** — e.g., Varnish or NGINX in front of the application server, often within the same data center as origin.
6. **Application-level cache (Redis/Memcached)** — explicit, application-managed caching of computed results, session data, or query results.
7. **Database query cache / buffer pool** — the database engine's own internal caching of frequently accessed pages/rows.

A request only travels as far down this chain as necessary — each layer that has a valid cached entry short-circuits the rest.

**Q3. Why does it matter which layer you cache at?**
A: Different layers have different trade-offs in scope, freshness control, and blast radius:
- Caching closer to the client (browser, edge) gives the best latency but the least control — invalidating a browser cache entry across millions of users is effectively impossible (you can only change the URL/cache key going forward).
- Caching closer to origin (application cache, DB cache) gives the most control (you can invalidate instantly, it's all in infrastructure you own) but the least latency benefit (still incurs full network round-trip from the client).
- Choosing the wrong layer for a given piece of data is a common production mistake — e.g., caching user-specific data at the CDN edge (wrong layer — should be application cache or not cached at shared layers at all) or re-computing a global, rarely-changing config value on every request at the application layer when it could be cached at the edge for massive request volume reduction.

## Section 2: Edge Caching for Dynamic and API Content

**Q4. What is "micro-caching" and what problem does it solve?**
A: Caching a normally "dynamic" or frequently-changing response for a very short TTL (often 1-10 seconds) at the edge, rather than treating it as fully uncacheable. The insight: even content that updates frequently is usually static *within* a short window — a news homepage that updates every 30 seconds doesn't need to be regenerated for every one of 10,000 requests/second; it only needs to be regenerated roughly once every few seconds, with all requests in between served from the brief cache. This was covered as a CDN caching pattern in the CDN guide (the `s-maxage` + `stale-while-revalidate` pattern for the news homepage example) — edge caching is the general principle that pattern is an instance of.

**Q5. How do you decide whether a piece of API/dynamic content is a good micro-caching candidate?**
A: Key questions: (1) Is the content roughly the same for many different users (not deeply personalized)? Micro-caching a per-user dashboard doesn't help much since each user's cache key is effectively unique anyway. (2) Can you tolerate a few seconds of staleness? If the business requirement is "real-time, to the millisecond," micro-caching isn't appropriate. (3) Is request volume high enough that even a few seconds of caching meaningfully reduces origin load? At low request volume, the operational complexity of micro-caching may not be worth it. Good candidates: public leaderboards, trending/popular content lists, aggregated statistics/dashboards, search result pages for common queries, homepage feeds with shared (non-personalized) components.

**Q6. What is "fragment caching" or "partial page caching" and how does it relate to edge caching of dynamic content?**
A: Rather than caching an entire HTTP response as one atomic unit, fragment caching breaks a page into cacheable and non-cacheable pieces — caching the shared/static fragments aggressively while leaving the personalized fragments uncached or cached separately at a much shorter TTL. This lets you apply edge caching benefits even to mostly-personalized pages, by isolating the genuinely cacheable parts (navigation, footer, trending sidebar, product details shared across all viewers) from the genuinely personalized parts (logged-in user's name, cart contents, personalized recommendations).

**Q7. What is Edge Side Includes (ESI) and how does it implement fragment caching at the CDN/edge layer?**
A: ESI is a markup language (an XML-based standard) that lets an origin server return a page with embedded include directives, which the edge/CDN resolves by fetching and substituting in separate sub-fragments — each with its own independent cache policy:

```html
<html>
  <body>
    <esi:include src="/fragments/header" />
    <esi:include src="/fragments/personalized-greeting" />
    <esi:include src="/fragments/footer" />
  </body>
</html>
```

The edge (e.g., Varnish, Akamai, Fastly support ESI) fetches each fragment, applying that fragment's own `Cache-Control` headers — `header` and `footer` might be cached for hours, while `personalized-greeting` is fetched fresh (or cached for seconds, per-user) on every request. The composed page is assembled entirely at the edge, without the origin server needing to assemble it — meaning even pages with some personalization can have the bulk of their content served from cache, with only the small personalized fragment requiring real compute per request.

**Q8. What is the practical alternative to ESI in modern architectures, and why has ESI adoption declined?**
A: Client-side composition: the initial page load returns a cached, mostly-static HTML shell from the edge, and personalized content is fetched separately via a client-side JavaScript API call after page load (often to an uncacheable or very-short-TTL API endpoint). This shifts the "assembly" step from the edge (ESI) to the browser (JavaScript), avoiding ESI's operational complexity (limited support across providers, debugging difficulty, the awkwardness of server-side templating across cache boundaries) at the cost of an extra round-trip and a brief flash of unpersonalized content before the client-side fetch completes. Most modern single-page applications and JAMstack architectures use this pattern rather than ESI, though ESI remains relevant in some enterprise/Akamai-heavy environments.

## Section 3: Cache Stampede / Dogpile Prevention

**Q9. What is a cache stampede (also called dogpile effect or cache miss storm)?**
A: When a popular cached item expires (or is evicted/purged) and a large number of concurrent requests arrive for it simultaneously — all of them simultaneously experience a cache miss and independently fetch/recompute the value, hitting the origin or backend with a sudden burst of redundant, identical work instead of the single fetch that was actually needed. The amplification factor scales with concurrent request volume — a cache stampede on a moderately popular item can be a minor inefficiency; on a viral/hot item, it can take down the origin entirely.

**Q10. What is "request coalescing" and how does it prevent cache stampedes?**
A: When the edge/cache layer detects multiple concurrent requests for the same now-missing key, it sends only one request upstream (to origin or to the computation that produces the value), holds the other concurrent requests waiting, and serves all of them from the single response once it returns — rather than letting every concurrent request independently trigger its own upstream fetch. This is sometimes called "request collapsing" (Varnish terminology) or "single-flight" (a common name in Go/application-layer implementations, from the `golang.org/x/sync/singleflight` package). Most production-grade caching layers (Varnish, NGINX with `proxy_cache_lock`, many CDN providers) implement this by default for cache-miss scenarios.

**Q11. What is `stale-while-revalidate` and how does it prevent stampedes differently from request coalescing?**
A: Rather than making concurrent requesters wait for a fresh fetch (as coalescing does), `stale-while-revalidate` immediately serves the existing (now-stale) cached value to all requesters, while triggering exactly one background revalidation request to refresh the cache for future requests. The key difference: coalescing still makes everyone wait for the first response (just only one of them triggers the actual fetch); stale-while-revalidate makes nobody wait — everyone gets an immediate (if slightly stale) response, with freshness happening asynchronously. The two techniques are complementary and often used together: stale-while-revalidate handles the common case (cache exists but is stale), and request coalescing handles the harder case (cache entry doesn't exist at all, e.g., first request ever, or after a hard eviction).

**Q12. What is "probabilistic early expiration" (XFetch / early recomputation) and what problem does it solve that stale-while-revalidate doesn't?**
A: A technique where, as a cached item's TTL approaches expiry, each request has a small, increasing probability of proactively triggering a recomputation/refetch *before* the TTL actually expires — spreading out the refresh load across the approach to expiry rather than concentrating it at the exact expiry moment. A common formula (from Vattani, Chierichetti, and Lowenstein's XFetch algorithm, used at Facebook): trigger early recomputation when `current_time - (delta * beta * log(random()))  >= expiry_time`, where delta is the time taken to recompute the value and beta is a tuning parameter. This solves a subtler problem than basic stale-while-revalidate: it avoids having many independent cache entries (e.g., across many edge nodes, each with its own copy and its own TTL countdown) all expire at exactly the same wall-clock moment and all trigger their background revalidation simultaneously — instead spreading the revalidation requests out over a window leading up to expiry.

**Q13. What is "lock-based" cache stampede prevention and what's its downside compared to coalescing?**
A: An explicit application-level pattern where, on a cache miss, the first request acquires a distributed lock (e.g., via Redis `SETNX`) before computing/fetching the value, and subsequent concurrent requests either wait for the lock to release (then read the now-populated cache) or, in some implementations, fall back to serving a stale/default value rather than waiting. This achieves the same goal as built-in request coalescing but requires explicit application code rather than relying on the caching infrastructure's built-in behavior. Downside: it's more error-prone to implement correctly (lock timeout handling, deadlock avoidance, lock contention overhead) and is generally only necessary when you're managing your own application-level cache (Redis/Memcached) rather than relying on a CDN/reverse-proxy layer that already implements coalescing natively.

## Section 4: Edge Compute and Key-Value Storage at the Edge

**Q14. How does "edge caching" extend beyond HTTP response caching into stateful edge storage?**
A: Modern edge compute platforms (Cloudflare Workers, Fastly Compute) offer purpose-built key-value stores designed to be read (and sometimes written) directly from edge compute functions — distinct from HTTP response caching. Examples: Cloudflare Workers KV (eventually consistent, globally replicated, read-optimized key-value store), Cloudflare Durable Objects (strongly consistent, single-instance coordination primitives useful for things like rate limiting counters or websocket session state at the edge), Fastly's Compute KV Store. These let edge functions make caching/business-logic decisions (feature flags, A/B test assignment, geofencing rules, rate limit counters) without a round-trip to a centralized origin database for every request.

**Q15. What is the consistency model typically used for edge KV stores, and why?**
A: Eventually consistent, in most cases — writes to an edge KV store propagate asynchronously to all edge locations, meaning a write made via one PoP may not be immediately visible to reads at a different PoP (propagation can take seconds). This trade-off is deliberate: requiring strong consistency across hundreds of geographically distributed PoPs would require expensive coordination (consensus protocols) on every write, defeating the latency purpose of having edge storage in the first place. Edge KV stores are therefore best suited for data that's read far more often than written, and where brief inconsistency windows are tolerable — configuration values, feature flags, geofencing rules, cached computed results — not for data requiring transactional guarantees (e.g., financial balances), which should stay in a centralized, strongly consistent datastore.

**Q16. When would you use an edge KV store instead of (or in addition to) standard CDN response caching?**
A: Standard CDN caching caches the *output* of a request (an HTTP response) keyed by URL. An edge KV store lets edge compute logic make *decisions* using stored data before generating a response — e.g., looking up a user's A/B test bucket assignment, checking a feature flag, applying per-tenant configuration, or making a routing decision — logic that needs to run for every request (even ones with different cache keys, or that are otherwise uncacheable) but benefits from not requiring an origin round-trip just to fetch a small piece of reference data. The two techniques are often combined: an edge function reads from KV to make a decision, and the resulting response may itself then be cached normally via standard HTTP caching.

**Q17. What is a practical example combining edge compute and KV storage for caching purposes?**
A: A geofencing/licensing check: instead of every request hitting origin to verify "is this content licensed for this country," an edge function reads a small, infrequently-changing KV-stored mapping of content-ID → allowed-countries directly at the edge (sub-millisecond KV read, no origin round-trip), makes the allow/deny decision locally, and only forwards genuinely allowed requests onward (where they may then hit a normal CDN cache for the actual content). This removes a per-request origin dependency for a decision that doesn't need centralized real-time data — exactly the kind of "frequently read, rarely written, tolerant of brief staleness" workload edge KV stores are designed for.

## Section 5: Edge Caching Technologies

**Q18. What is Varnish and what role does it play in edge/reverse-proxy caching?**
A: Varnish Cache is a specialized open-source HTTP accelerator/reverse proxy purpose-built for caching — historically one of the most widely deployed caching layers sitting directly in front of origin web servers (distinct from a full geographically-distributed CDN, though some CDN providers, like Fastly, are built on Varnish internally). Its defining feature is VCL (Varnish Configuration Language), a domain-specific language that gives fine-grained, programmatic control over caching decisions — cache key construction, TTL logic, request coalescing behavior, ESI processing — beyond what simple `Cache-Control` header configuration alone allows.

**Q19. What is VCL and why would you write custom caching logic instead of relying on HTTP cache headers alone?**
A: VCL (Varnish Configuration Language) lets you write explicit, imperative caching logic that runs at defined points in the request lifecycle (`vcl_recv`, `vcl_backend_response`, `vcl_deliver`, etc.) — for example, deciding to strip a specific cookie before checking cache (so that an unrelated tracking cookie doesn't fragment the cache key), normalizing query parameter order so `?a=1&b=2` and `?b=2&a=1` hit the same cache entry, or implementing custom logic for handling specific edge cases that simple header-based configuration can't express. This is necessary when the application's existing `Cache-Control` headers aren't sufficiently expressive for the caching behavior you need, or when you don't control the origin application code directly (e.g., caching in front of a third-party or legacy system) and need to impose caching logic externally.

**Q20. What is NGINX's `proxy_cache` and how does it compare to a dedicated caching layer like Varnish?**
A: NGINX, in addition to its common reverse-proxy/load-balancer roles, supports response caching via `proxy_cache` directives — storing responses from upstream servers and serving subsequent matching requests from local disk/memory cache. It's less specialized than Varnish (no equivalent to VCL's expressiveness) but is frequently sufficient for straightforward caching needs, and has the operational advantage of being the same tool already deployed for reverse-proxying/load-balancing — avoiding the need to run and maintain a separate caching layer. The relevant directive for stampede prevention is `proxy_cache_lock`, NGINX's equivalent of Varnish's request coalescing.

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m max_size=1g;

server {
    location / {
        proxy_cache my_cache;
        proxy_cache_valid 200 10s;
        proxy_cache_lock on;
        proxy_cache_use_stale error timeout updating;
        proxy_pass http://backend;
    }
}
```

**Q21. What is "microcaching" specifically in NGINX, and how is it configured?**
A: A common pattern (popularized by NGINX itself and adopted widely) of setting an extremely short `proxy_cache_valid` duration (often 1 second) on otherwise-dynamic backend responses, combined with `proxy_cache_lock` to prevent stampedes — letting NGINX absorb very high request rates against a backend that would otherwise need to handle every request individually, with a barely-perceptible (1 second) staleness trade-off. This is the same micro-caching pattern discussed in Q4-5, but specifically refers to the NGINX implementation pattern by name, since it's commonly referenced by this specific term in production NGINX/PHP-FPM/dynamic-backend contexts.

## Section 6: Cache Eviction and Sizing

**Q22. What eviction policies are commonly used at the edge, and how do they differ?**
A: Edge cache storage is finite — when full, something must be evicted to make room for new entries:
- **LRU (Least Recently Used)**: evict the entry that hasn't been accessed in the longest time. The most common default — works well when recent access is a good predictor of future access (true for most web traffic's "recency bias").
- **LFU (Least Frequently Used)**: evict the entry with the fewest total accesses. Better than LRU for content with stable long-term popularity that might have brief gaps in access (LRU would prematurely evict it during the gap); worse for adapting to rapidly shifting popularity.
- **TTL-based expiration**: independent of access patterns — entries are evicted purely based on elapsed time since caching, regardless of how popular they are. This is the primary mechanism at most CDN edges (combined with LRU as a secondary mechanism when storage is full before TTL expiry).
- **Size-aware eviction**: some implementations weight eviction decisions by entry size as well as recency/frequency — preferring to evict one large rarely-accessed entry over many small frequently-accessed ones, since it frees more space per eviction.

**Q23. How does edge cache storage capacity planning differ from origin storage planning?**
A: Edge storage at any single PoP is typically much smaller than the full origin dataset — a CDN edge node might have terabytes of cache storage while the origin's full content catalog is petabytes. This is fine precisely because of the pull model's demand-driven population (from the Push vs Pull guide) — each edge only needs enough capacity to hold its local "working set" (the subset of content actually popular in that region), not the entire catalog. Capacity planning at the edge is therefore about understanding working-set size and access patterns (how concentrated is demand — a small hot set, or broadly spread?) rather than simply provisioning storage proportional to total catalog size.

**Q24. What happens when an edge cache is undersized relative to its working set, and how do you detect it?**
A: If the actively-requested content (working set) exceeds available cache storage, popular items get evicted prematurely (before their TTL would naturally expire) to make room for other popular items — causing cache hit ratio to drop even though the content is genuinely popular and "should" be cacheable. This shows up as a lower-than-expected hit ratio metric (covered in the CDN guide) combined with eviction-rate metrics indicating capacity-pressure evictions rather than TTL-expiry evictions. Detection requires monitoring both metrics together — a low hit ratio alone doesn't distinguish "content isn't cacheable" from "content is cacheable but cache is too small," which require very different fixes (better cache headers/key design vs. more storage capacity).

## Section 7: Security and Correctness at the Edge

**Q25. What is the risk of caching responses that contain user-specific or sensitive data at a shared edge layer?**
A: If a response containing one user's private data (account details, auth tokens, personalized content) is mistakenly cached at a shared cache layer (CDN edge, Varnish, NGINX) without proper `private`/`no-store` headers or without including the necessary distinguishing identifier in the cache key, that cached response can be served to a *different* user who happens to make a request that maps to the same cache key — a serious data leak. This is a well-documented class of real-world vulnerability (often triggered by misconfigured `Vary` headers, missing `Cache-Control: private` on authenticated endpoints, or a cache key that doesn't include the session/auth identifier when it should).

**Q26. How do you defend against accidentally caching sensitive/personalized responses at a shared layer?**
A: Explicit, conservative `Cache-Control` headers on every authenticated/personalized endpoint (`private, no-store` or `no-cache` as appropriate) rather than relying on the cache layer's default behavior; architectural separation between cacheable (public, shared) and uncacheable (personalized, authenticated) endpoints, so cache policy can be applied consistently at a routing level rather than per-response; automated testing/auditing that checks responses from authenticated endpoints for the absence of caching headers that would make them shareable; and at the infrastructure level, configuring the cache layer itself to default to *not* caching responses with an `Authorization` header or session cookie present, unless explicitly overridden — a safer default than caching everything unless told not to.

**Q27. What is "cache deception" and how does it differ from standard cache poisoning?**
A: Cache deception is an attack where a malicious actor crafts a URL that appears to point to a cacheable static resource (e.g., by appending a fake static-looking path segment, like `/account/profile/nonexistent.css`) but which a misconfigured server actually routes to a dynamic, authenticated endpoint, returning the user's private data — and crucially, because the URL *looks* like a static asset, an intermediate cache layer caches the response as if it were a generic static file. A subsequent attacker request to the exact same crafted URL then retrieves the victim's cached private data. This differs from classic cache poisoning (where an attacker causes a *malicious* response to be cached and served to *others*) — in cache deception, the attacker causes a *victim's legitimate* response to be cached and then retrieves it themselves. Mitigation: ensure URL routing/caching logic is based on genuine content-type and explicit cache policy, not naive path-suffix pattern matching, and that authenticated routes can never be matched by a path pattern intended for static assets.

## Section 8: Scenario-Based Questions

**Q28. "Your API endpoint `/api/trending` returns the same data for all users, updates every 60 seconds, and receives 50,000 requests/second at peak. Currently it's marked `no-store`. What would you change, and what specific mechanisms would you configure?"**
A: This is a textbook micro-caching candidate (Q4-5) — non-personalized, tolerant of brief staleness, very high request volume. Change `Cache-Control` to something like `public, s-maxage=10, stale-while-revalidate=30` — caching for 10 seconds at the edge/CDN layer, with up to 30 additional seconds of serving stale content while a background revalidation occurs. This means the origin only needs to actually generate this response roughly once every 10 seconds (per PoP), rather than 50,000 times per second — a five-orders-of-magnitude reduction in backend load. Also explicitly verify request coalescing/cache locking is enabled at whatever layer sits in front of origin (CDN default behavior, or `proxy_cache_lock` if NGINX, or Varnish's built-in coalescing) to prevent a stampede the moment the 10-second TTL expires under that request volume.

**Q29. "A page shows a product listing (same for everyone) plus a 'Recently Viewed by You' personalized sidebar. The whole page is currently rendered server-side and marked uncacheable because of the personalized section. How would you redesign this for better caching?"**
A: Apply fragment caching (Q6-8) — separate the product listing (cacheable, shared, can have a normal CDN TTL) from the personalized sidebar (must remain per-user, uncacheable or very-short-TTL). Two implementation paths: (1) ESI, if the CDN/edge layer supports it — the origin returns the page with an `<esi:include>` for the sidebar, and the edge assembles the cached listing with a freshly-fetched sidebar fragment per request; (2) client-side composition — return a cached page with an empty/placeholder sidebar, then have client-side JavaScript fetch the personalized sidebar content via a separate (uncacheable) API call after page load. Either approach lets the bulk of the page (and its associated backend rendering cost) be served from cache, with only the small personalized fragment requiring real per-request work.

**Q30. "You notice that after a CDN content update, some users briefly see a broken page that references a new CSS class which the old, still-cached stylesheet doesn't define. What's happening, and how do you prevent it?"**
A: This is the cache consistency/propagation gap discussed in the CDN and Push/Pull guides — during purge propagation (or simply because HTML and CSS have independent cache lifetimes/keys), different PoPs or different resources can be in inconsistent states relative to each other for a brief window. The standard prevention is cache-busting via versioned/content-hashed filenames (e.g., `style.a1b2c3.css` instead of `style.css`) — since the new HTML references the new hashed CSS filename, there's no ambiguity: a user either gets the fully old version (old HTML + old CSS, both cached, internally consistent) or the fully new version (new HTML + new CSS, the new CSS filename being a guaranteed fresh fetch) — never an inconsistent mix of old CSS with new HTML, because the URLs themselves are different and don't share a cache entry.

**Q31. "Your Redis-backed application cache (not a CDN) experiences a stampede every time a popular cached computation expires, spiking database load for a few seconds every few minutes. How would you fix this at the application layer?"**
A: Since this is application-level caching (not a CDN/reverse-proxy with built-in coalescing), implement explicit stampede prevention in application code: either (1) a distributed lock pattern (Q13) — first request to miss acquires a Redis lock (`SET key value NX PX timeout`), computes the value, populates the cache, and releases the lock; concurrent requests either wait briefly or fall back to a slightly-stale previous value while waiting; or (2) probabilistic early recomputation (Q12) — store the computation's typical duration alongside the cached value, and have requests probabilistically trigger early recomputation as the TTL approaches, smoothing out the refresh load instead of concentrating it at exact expiry. Given this is recurring and predictable ("every few minutes" suggests a known, fixed TTL), probabilistic early expiration is usually the cleaner fix — it requires no locking complexity and naturally smooths load without any request ever fully blocking on a cold cache.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Caching hierarchy | Browser → service worker → CDN/edge → mid-tier → reverse proxy → app cache → DB |
| Micro-caching | Very short TTL (1-10s) on "dynamic" content to absorb high QPS |
| Fragment caching | Cache parts of a page independently (shared vs personalized) |
| ESI | Server/edge-side markup for assembling cached fragments |
| Cache stampede | Many concurrent misses on one expired/evicted key flood origin |
| Request coalescing | Collapse concurrent misses into one upstream fetch |
| stale-while-revalidate | Serve stale immediately, refresh in background |
| Probabilistic early expiration | Spread refresh load before exact TTL expiry (XFetch) |
| Edge KV store | Eventually-consistent key-value store readable from edge compute |
| LRU / LFU / TTL eviction | How edge cache storage decides what to evict when full |
| Cache deception | Tricking a cache into storing/serving another user's private response |

---

**Tip for interviews:** Four things separate strong candidates on edge caching: (1) treating it as the general principle that CDN caching, browser caching, and application caching are all instances of — not a CDN-specific topic; (2) knowing the **difference between request coalescing and stale-while-revalidate** (Q10-11) — they solve overlapping but distinct problems and are often used together; (3) being able to name **probabilistic early expiration / XFetch** (Q12) by name with the rough mechanism — very few candidates know this beyond "use stale-while-revalidate," and it shows genuine production-scale experience; and (4) recognizing **cache deception** (Q27) as a distinct vulnerability class from cache poisoning — a frequently confused pair that's worth being able to articulate precisely.
