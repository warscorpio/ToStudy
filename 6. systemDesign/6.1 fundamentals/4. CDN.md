# CDN (Content Delivery Network) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a CDN and what problem does it solve?**
A: A Content Delivery Network is a geographically distributed network of edge servers (PoPs — Points of Presence) that cache and serve content closer to end users, reducing latency, offloading the origin server, and improving availability. The core problem it solves is physics: the speed of light imposes a hard floor on latency over distance. A user in Tokyo requesting content from a single origin server in Virginia incurs ~150-200ms of round-trip network latency just from geography, regardless of how fast the origin server is. A CDN places a copy of the content in Tokyo, cutting that latency to single-digit milliseconds.

**Q2. How does a CDN relate to the reverse proxy concept?**
A: A CDN is architecturally a distributed reverse proxy — from the origin's perspective, the CDN represents and protects the origin server, exactly like the reverse proxy definition. The key addition is geographic distribution: instead of one reverse proxy location, there are hundreds or thousands of PoPs worldwide, and the CDN's routing layer (DNS or Anycast) directs each client to the nearest/best PoP.

**Q3. What is a PoP (Point of Presence) / edge location?**
A: A physical or virtual location where the CDN operates servers that cache content and serve client requests. Major CDN providers operate hundreds of PoPs globally (Cloudflare: 300+, Akamai: thousands, AWS CloudFront: 600+ edge locations as of recent years). Each PoP typically includes caching servers, and increasingly, compute capability (edge functions) and security features (WAF, DDoS scrubbing).

**Q4. What types of content are CDNs best suited for?**
A: Historically, **static content**: images, CSS, JavaScript bundles, videos, downloadable files, fonts — content that doesn't change per-request and can be cached and reused across many users. Modern CDNs have expanded into: **dynamic content acceleration** (route optimization and connection reuse even for uncacheable content), **API acceleration**, **video streaming** (live and VOD, with specialized protocols), and **edge compute** (running logic at the edge, not just caching).

**Q5. What is the difference between "origin" and "edge" in CDN terminology?**
A: The **origin** is the authoritative source server — where content is first created or where requests ultimately go when not servable from cache (your application server, S3 bucket, etc.). The **edge** is the CDN's distributed PoP layer that sits between clients and the origin, caching responses and serving them directly when possible. "Origin pull" / "origin fetch" / "cache miss" all refer to the edge going back to the origin to retrieve content it doesn't have cached.

## Section 2: How Requests Are Routed to the Nearest Edge

**Q6. How does a CDN determine which PoP should serve a given client?**
A: Two primary mechanisms, often combined:
- **DNS-based routing (GeoDNS)**: the CDN's authoritative DNS server resolves the CDN hostname to a different IP address depending on the resolving client's apparent location (inferred from the DNS resolver's IP, which is often close to the actual client). The client then connects directly to that IP.
- **Anycast routing**: the same IP address is announced via BGP from multiple PoPs simultaneously. Internet routing protocols (BGP) naturally route the client's packets to the topologically nearest PoP announcing that IP — no DNS-level geo-logic needed; standard internet routing handles it.

**Q7. What are the trade-offs between GeoDNS and Anycast routing?**
A:
- **GeoDNS**: routing decision is based on the DNS resolver's location, not the actual client's location — this can be inaccurate if the client uses a DNS resolver in a different region (e.g., a public DNS resolver like 8.8.8.8 that may not reflect the client's true location, or corporate DNS routing all queries through a central office). DNS responses are also cached (TTL-based), so routing can't react instantly to PoP failures — a client's cached DNS answer may keep pointing to a failed/congested PoP until TTL expires.
- **Anycast**: routing follows actual network topology (BGP shortest path), which often correlates well with latency but isn't guaranteed to be optimal — BGP path selection is about AS-hop count and routing policy, not real-time latency measurement. Anycast can react to PoP failures faster (BGP withdrawal of the failed PoP's route), but is more complex to operate (requires BGP peering infrastructure) and can suffer from "flapping" or asymmetric routing issues.

Many large CDNs (Cloudflare, Google) use Anycast as the primary mechanism; some (historically Akamai) lean more on sophisticated GeoDNS with real-time network performance data.

**Q8. What is the role of BGP in Anycast CDN routing?**
A: Border Gateway Protocol is the internet's inter-AS (Autonomous System) routing protocol. In Anycast, the same IP prefix is announced from multiple physical locations via BGP. Internet routers, using BGP's path-selection algorithm (shortest AS path, among other factors), naturally route traffic to whichever announcing location is "closest" in terms of network topology. If a PoP goes down, it stops announcing the prefix via BGP, and traffic automatically reroutes to the next-closest PoP within seconds — without any client-side action or DNS propagation delay.

**Q9. Why might Anycast routing sometimes send a user to a "wrong" (non-nearest) PoP?**
A: BGP optimizes for AS-path length and routing policy (business agreements between networks), not physical distance or real-time latency. Two networks can have a short AS-path between them that traverses a longer physical/congested route than an alternative with more hops. This is a known limitation — "BGP doesn't know about geography or congestion." Real-world example: a user in a country with limited international connectivity might get routed to a distant PoP because the AS-path through their available transit providers happens to be shorter than the AS-path to a geographically closer PoP that isn't well-peered with their ISP.

## Section 3: Caching Mechanics

**Q10. How does a CDN edge node decide whether it can serve a cached response?**
A: It checks the incoming request against its cache using a cache key (often the URL plus optionally headers like `Accept-Encoding` or `Vary`-listed headers) and validates the cached entry's freshness using `Cache-Control`/`Expires` headers set by the origin. If a fresh, matching entry exists: cache hit, served immediately. If no entry exists or it's stale: cache miss, the edge fetches from origin (or a parent/regional cache tier first, in multi-tier CDN architectures).

**Q11. What are the key `Cache-Control` directives a CDN respects, and what do they mean?**
A:
- **`max-age=N`**: cache the response for N seconds before considering it stale.
- **`s-maxage=N`**: like max-age but specifically for shared caches (CDNs, proxies) — overrides max-age for CDN purposes, letting origins set a different cache duration for CDNs vs browsers.
- **`no-cache`**: the response *can* be cached, but must be revalidated with the origin before each use (via conditional requests) — misleadingly named, since it doesn't mean "don't cache."
- **`no-store`**: the response must never be cached anywhere — used for sensitive/private data.
- **`private`**: cacheable only by the end client's browser, not by shared/intermediate caches like a CDN.
- **`public`**: explicitly cacheable by any cache, including shared ones, even for responses that might otherwise be treated as private (e.g., with authorization headers).
- **`stale-while-revalidate=N`**: serve the stale cached response immediately while asynchronously revalidating with origin in the background — improves perceived performance.
- **`stale-if-error=N`**: serve the stale cached response if the origin is unreachable/erroring — improves availability during origin outages.

**Q12. What is the difference between `max-age` and `s-maxage`?**
A: `max-age` applies to all caches, including the end user's browser. `s-maxage` applies only to shared caches (CDN, reverse proxy) and takes precedence over `max-age` for those caches when both are present. This lets an origin set, for example, `Cache-Control: max-age=60, s-maxage=3600` — the browser caches for 1 minute, but the CDN caches for 1 hour, serving many users from the CDN tier while still letting individual browsers refresh more frequently for personalization or content updates.

**Q13. What is a "cache key" and why does its design matter?**
A: The cache key is the identifier the CDN uses to determine if two requests should be served the same cached response — typically derived from the URL, but can include selected headers, cookies, or query parameters depending on configuration. Cache key design directly impacts hit ratio and correctness:
- **Too broad** (e.g., ignoring a query parameter that actually changes content) → cache poisoning risk, serving wrong content to users.
- **Too narrow** (e.g., including irrelevant headers like `User-Agent` with high cardinality, or a session-specific cookie) → cache fragmentation, near-zero hit ratio, since almost every request looks "unique."

A common production bug: including a tracking/analytics query parameter (`?utm_source=...`) in the cache key, causing what should be one cacheable resource to fragment into thousands of cache entries — destroying hit ratio.

**Q14. What is the `Vary` header and how does it affect CDN caching?**
A: `Vary` tells caches which request headers must match (in addition to the URL) for a cached response to be considered valid for reuse. For example, `Vary: Accept-Encoding` means the CDN must cache separate versions for gzip-compressed vs uncompressed responses, since the response body differs by encoding. `Vary: User-Agent` is a common anti-pattern — User-Agent has extremely high cardinality (thousands of distinct values), so varying on it effectively disables caching almost entirely. A well-designed API should minimize what it varies on, or use more targeted mechanisms (like serving different cache-friendly endpoints) instead of broad Vary headers.

**Q15. What is "negative caching" and why is it useful?**
A: Caching error responses (404s, sometimes 5xxs) for a short TTL, so that repeated requests for non-existent resources don't all hit the origin. Useful for absorbing scraper/bot traffic hitting invalid URLs, or preventing a "miss storm" when a popular but mistyped URL gets hit repeatedly. Typically configured with a much shorter TTL than positive (200 OK) caching, since you want legitimate fixes (e.g., the resource being created) to propagate reasonably fast.

## Section 4: Cache Invalidation and Purging

**Q16. What is cache invalidation/purging and why is it one of the hardest problems in CDN operations?**
A: Invalidation is the act of telling the CDN "this cached content is no longer valid, don't serve it anymore" — needed when origin content changes before the natural TTL expires. It's hard because: (1) invalidation requests must propagate to potentially hundreds of geographically distributed PoPs, which takes time (seconds to minutes depending on provider and method); (2) during propagation, different users in different regions may see different (stale vs fresh) versions of the same content — an inherent consistency gap; (3) at scale, purging individual URLs one-by-one doesn't work for large content changes (e.g., a full site redeploy), requiring batch/wildcard purges which are more expensive operations for the CDN provider to execute quickly.

**Q17. What are the common cache invalidation strategies?**
A:
- **TTL-based (passive) expiration**: simplest — just wait for `max-age` to expire. No action needed but introduces staleness up to the TTL duration.
- **Explicit purge (active invalidation)**: API call to the CDN telling it to evict a specific URL or set of URLs immediately. Fast (seconds) but must be triggered by your deployment process.
- **Cache-busting via versioned URLs**: instead of invalidating `style.css`, deploy `style.a1b2c3.css` (filename includes a content hash or version) and update references to it. The old URL remains cached (harmless, nobody requests it anymore) and the new URL is a guaranteed cache miss on first request, then cached fresh. This is the standard practice for static assets in modern build pipelines (Webpack, Vite content hashing) — it avoids the purge propagation delay problem entirely.
- **Soft purge / stale marking**: mark content as stale (forcing revalidation) rather than fully evicting it — combined with `stale-while-revalidate`, users still get fast (if slightly stale) responses while the cache refreshes in the background.

**Q18. Why is cache-busting via versioned filenames generally preferred over explicit purging for static assets?**
A: Because it sidesteps the propagation consistency problem entirely. With explicit purge, there's a window during global propagation where some PoPs serve old content and others serve new — users can get inconsistent experiences (e.g., new HTML referencing a CSS class that the still-cached old stylesheet doesn't define). With versioned URLs, there's no "in-between" state: the old URL keeps serving old content (cached, that's fine — nothing references it anymore), and the new URL is unambiguously new content from the first request. It also avoids purge API rate limits/costs, which matter at scale.

**Q19. What is a "purge storm" or "thundering herd on purge" and how do you mitigate it?**
A: When a popular cached resource is purged and immediately receives a high volume of concurrent requests, all of them become simultaneous cache misses hitting the origin at once — potentially overwhelming it, especially if the resource was cached precisely because it's expensive to generate. Mitigations: **request coalescing** at the edge (the CDN recognizes multiple concurrent requests for the same now-missing resource and only sends one request to origin, holding the others until the response arrives, then serving all from that single origin response); `stale-while-revalidate` (serve the stale version to most users while one background request refreshes); and staggered/soft purging (mark stale rather than hard-evict, letting natural request flow trigger gradual revalidation rather than an instant flood).

## Section 5: Performance Optimizations Beyond Caching

**Q20. What is TCP/TLS connection reuse and how does a CDN leverage it for dynamic (uncacheable) content?**
A: Establishing a new TCP connection (and TLS handshake on top) involves multiple round trips before any data flows — costly over high-latency links. A CDN PoP maintains persistent, already-warmed connections to the origin (connection pooling) and to upstream "parent" CDN nodes. When a client's request can't be served from cache, the CDN forwards it over this pre-established connection rather than the client establishing a fresh long-distance connection to origin itself. The client's connection to the nearby edge is fast to establish (short physical distance); the edge-to-origin hop reuses a warm connection — net latency is much lower than a client connecting directly to a distant origin.

**Q21. What is "TCP optimization" / "route optimization" at the CDN layer?**
A: CDN providers often operate private backbone networks between their PoPs, bypassing the congested/unpredictable public internet for the "middle mile" (edge-to-edge or edge-to-origin hop). They also apply TCP tuning (larger initial congestion windows, BBR congestion control, TCP Fast Open) on these well-characterized private links, which wouldn't be safe to assume on the unpredictable public internet. This is a major value-add for dynamic/API content where caching doesn't apply but the CDN can still measurably reduce latency through smarter routing and transport tuning.

**Q22. What is TLS session resumption and why does it matter at CDN scale?**
A: Full TLS handshakes involve asymmetric cryptography (expensive) and multiple round trips. Session resumption (via session IDs or session tickets, and in TLS 1.3, 0-RTT) lets a returning client skip the full handshake, resuming a previous session with much less overhead. Since a CDN edge serves enormous numbery of repeat visitors, efficient session resumption substantially reduces both latency (fewer round trips) and CPU load (avoiding expensive public-key crypto operations) at the edge — a meaningful operational cost factor at CDN scale.

**Q23. What is HTTP/2 and HTTP/3 (QUIC) support, and why do CDNs push for early adoption?**
A: HTTP/2 introduced multiplexing (many requests over one connection, eliminating head-of-line blocking at the application layer) and header compression. HTTP/3 (built on QUIC, over UDP instead of TCP) eliminates TCP-level head-of-line blocking entirely and reduces connection establishment to fewer round trips (combining transport and TLS handshake). CDNs are typically the first adopters of new protocol versions because: (1) they control both ends of the most latency-sensitive hop (client-to-edge); (2) the benefits compound at their scale; (3) they can deploy protocol upgrades to the edge fleet faster than every individual origin server operator could. A client can speak HTTP/3 to the CDN edge even if the origin only supports HTTP/1.1 — the CDN translates between protocol versions across the edge-to-origin hop.

**Q24. What is image/asset optimization at the CDN edge, and how does it work?**
A: Many CDNs offer on-the-fly image transformation: resizing, format conversion (e.g., converting JPEG/PNG to WebP or AVIF for browsers that support them, often via `Accept` header content negotiation), and quality compression — all performed at the edge, cached per-variant, without the origin needing to pre-generate every size/format combination. This significantly reduces payload size and improves Core Web Vitals (especially Largest Contentful Paint) for image-heavy sites. The trade-off: more cache key permutations (one per format × size combination requested), increasing storage and reducing hit ratio per-variant compared to a single canonical image.

## Section 6: CDN for Dynamic Content, APIs, and Edge Compute

**Q25. Can a CDN help with content that can never be cached (e.g., a personalized API response)?**
A: Yes, through several mechanisms even without caching the response body itself: (1) connection/route optimization (Q20-21) reduces the network latency portion of the request regardless of cacheability; (2) TLS termination at the edge means the expensive handshake happens close to the client even if the request still goes to origin; (3) the CDN can still cache and serve *shared, non-personalized fragments* of a response if the architecture separates cacheable and personalized parts (e.g., edge-side includes, or client-side composition of a cached shell + a small personalized API call); (4) DDoS/bot mitigation and WAF protection still apply, even to uncacheable traffic.

**Q26. What is "edge compute" and how does it differ from traditional CDN caching?**
A: Edge compute lets you run actual application logic at CDN PoPs, not just cache/serve static content. Examples: Cloudflare Workers, AWS CloudFront Functions / Lambda@Edge, Fastly Compute. Use cases: A/B testing and feature flag evaluation at the edge (no origin round trip needed to decide which variant to serve), authentication/authorization checks before forwarding to origin, request/response header manipulation, geofencing/redirect logic, and even full API endpoints for latency-sensitive, stateless logic. This blurs the line between "CDN" and "distributed compute platform" — modern CDN providers increasingly market themselves as edge platforms, not just caching networks.

**Q27. What are the constraints typically imposed on edge compute functions, and why?**
A: Edge functions usually run in lightweight, sandboxed runtimes (e.g., V8 isolates for Cloudflare Workers, rather than full containers or VMs) to keep cold-start times near-zero and resource footprint minimal — since they run on shared infrastructure across thousands of PoPs serving extremely high request volumes. Common constraints: strict CPU time limits (often single-digit milliseconds of CPU time, though longer wall-clock time is allowed for I/O), memory limits (tens of MB), limited or no access to a traditional filesystem, and constrained or no support for long-running connections/background processing. These constraints exist because edge functions must not degrade the performance or reliability of the shared multi-tenant edge fleet.

**Q28. How does video streaming via CDN differ from regular static asset delivery?**
A: Video streaming (live or VOD) uses adaptive bitrate streaming protocols (HLS, DASH) where content is pre-segmented into small chunks (typically 2-10 seconds) at multiple quality/bitrate levels. The CDN caches these segments like any static file, but the player dynamically requests different bitrate segments based on measured network conditions — switching quality mid-stream without interrupting playback. For live streaming, segments are generated continuously and have very short TTLs (since they're new content arriving constantly) — this creates much higher cache churn and requires lower-latency origin-to-edge propagation than typical static content. Specialized "live origin" infrastructure and protocols (e.g., Low-Latency HLS) address the additional latency sensitivity of live streaming specifically.

## Section 7: Security and Resilience

**Q29. How does a CDN provide DDoS protection?**
A: Primarily through sheer absorption capacity — a CDN's distributed edge network has aggregate bandwidth and compute capacity vastly larger than any single origin server, so volumetric attacks (traffic floods) get spread across hundreds of PoPs rather than concentrated on one target. Additional mechanisms: Anycast routing naturally distributes attack traffic across the PoPs nearest each attack source (rather than concentrating at origin); rate limiting and traffic pattern anomaly detection at the edge; and dedicated "scrubbing centers" that some providers operate specifically to absorb and filter large-scale attacks before clean traffic is forwarded onward. Because the CDN sits in front of the origin, the origin's actual IP can also be kept hidden from attackers (origin shielding) — preventing direct-to-origin attacks that bypass the CDN entirely.

**Q30. What is "origin shielding" and what specific problem does it solve?**
A: A configuration where one specific PoP (or a designated "shield" tier) is the only one allowed to fetch directly from origin — all other edge PoPs that experience a cache miss go to the shield PoP first (which may have the content cached from a previous edge's request) rather than hitting origin directly. This reduces the number of concurrent connections origin must handle (since many edges fetching the same newly-popular content funnel through one shield layer instead of all hitting origin simultaneously) and improves cache hit ratio for the origin-facing tier, since the shield PoP aggregates demand across all edges globally rather than each edge maintaining an independent, smaller cache.

**Q31. What is a WAF and how is it typically deployed at the CDN layer?**
A: A Web Application Firewall inspects incoming requests against rule sets designed to detect and block common attack patterns: SQL injection, XSS, known bad bot signatures, OWASP Top 10 patterns. Deploying WAF at the CDN edge means malicious requests are blocked before they ever reach origin infrastructure — reducing load and risk on the application itself, and benefiting from the CDN's global visibility (attack patterns observed against one customer can inform rules protecting others, a form of crowdsourced threat intelligence common among large CDN/security providers).

**Q32. How does a CDN improve availability beyond just performance?**
A: Several mechanisms:
- **Stale-if-error serving**: if origin is down, the CDN can continue serving cached (even if technically stale) content rather than returning errors to users — graceful degradation during an origin outage.
- **Multi-origin failover**: configure multiple origin servers/regions; the CDN automatically routes to a healthy origin if the primary fails health checks.
- **Geographic isolation of failures**: a problem affecting one PoP/region (hardware failure, local network issue) doesn't affect users served by other PoPs, unlike a single-origin architecture where any origin issue affects all users globally.
- **Absorbing traffic spikes**: viral content or flash-sale traffic spikes are absorbed by the elastic edge capacity rather than overwhelming a fixed-capacity origin.

**Q33. What happens to a CDN-fronted site if the origin goes completely down, with no stale-if-error or multi-origin failover configured?**
A: Cached content with valid (non-expired) TTLs continues to be served normally — users requesting already-cached resources see no disruption. However, any cache miss (new content, expired TTL, or uncached dynamic requests) will fail, since the edge has nowhere to fetch fresh content from. The site appears "partially up" — some pages/assets work, others return errors — which can be confusing without monitoring that distinguishes cache-hit traffic from origin-dependent traffic. This is precisely why `stale-if-error` and multi-origin failover are recommended for production systems, not just performance optimizations but availability ones.

## Section 8: Cost and Operational Considerations

**Q34. What are the primary cost drivers for CDN usage?**
A: **Bandwidth/data transfer out** (the dominant cost factor — billed per GB served from edge to client, often with regional pricing variation), **request count** (especially relevant for high-volume, small-payload APIs), **invalidation/purge operations** (some providers charge per-purge or rate-limit free purges), and **edge compute execution** (billed similarly to serverless functions — per invocation and/or compute time). Cache hit ratio directly impacts cost in two ways: higher hit ratio reduces origin bandwidth/compute costs (the origin serves fewer requests), though CDN-to-client bandwidth cost is incurred regardless of whether it was a hit or miss.

**Q35. How do you measure and improve cache hit ratio in production?**
A: Measure via the CDN provider's analytics (hit/miss ratio metrics, often broken down by path/content-type) or by inspecting cache status headers the CDN adds to responses (e.g., `X-Cache: HIT`/`MISS`, `CF-Cache-Status`, `X-Cache-Status` — naming varies by provider). Improvement levers: ensure appropriate `Cache-Control`/`s-maxage` headers are set (many low-hit-ratio issues are simply missing or overly conservative cache headers from the origin); audit and minimize `Vary` header usage and cache key cardinality (Q13-14); separate cacheable static assets from dynamic/personalized content architecturally so caching policy can be applied surgically; and use origin shielding (Q30) to improve effective cache population especially for long-tail content.

**Q36. What is "cache hit ratio" and what's considered a "good" value?**
A: The percentage of requests served directly from cache versus requiring an origin fetch. "Good" is highly context-dependent: a static-asset-heavy site (images, JS/CSS bundles with long TTLs and versioned URLs) can reasonably target 95%+ hit ratio. A dynamic, highly personalized application might only achieve 20-40% hit ratio even with good caching architecture, because most requests are inherently uncacheable. The metric is only meaningful relative to the theoretical maximum for that specific traffic mix — interviewers asking this question are testing whether you understand it's not a universal target number.

## Section 9: Comparison and Architecture Questions

**Q37. CDN vs a traditional reverse proxy/load balancer — when do you need a CDN specifically?**
A:

| Dimension | Reverse Proxy / LB (single location) | CDN (distributed) |
|---|---|---|
| Geographic distribution | Single data center/region | Hundreds of PoPs globally |
| Primary goal | Routing, TLS termination, backend protection | + latency reduction via proximity, massive scale absorption |
| Best for | Backend fronting regardless of client location | Content/traffic with a geographically dispersed audience |
| Caching scope | Local to that LB instance/cluster | Globally distributed cache tiers |

You need a CDN specifically when your users are geographically dispersed and latency/proximity matters, when you need to absorb internet-scale traffic spikes or attacks, or when you're serving substantial static content volume. A single-region application serving a regionally concentrated user base may not need a full CDN — a reverse proxy/LB with local caching may suffice.

**Q38. "Your company runs a SaaS dashboard application — mostly authenticated, personalized, dynamic content, with some static JS/CSS bundles. Is a CDN worth it, and what would you cache?"**
A: Yes, but selectively. Even though most page content is personalized and uncacheable, the static assets (JS bundles, CSS, fonts, images, favicon) are textbook CDN candidates — apply versioned/hashed filenames and long `max-age` for these. For the dynamic dashboard itself, the CDN still provides value via connection/route optimization (Q20-21) and TLS termination at the edge, reducing latency for the API calls even though responses aren't cached. If any dashboard data is shared across users (e.g., public statistics, non-personalized reference data), that subset could be cached with a short TTL. The architecture decision to flag: separate static asset hosting (aggressively cached) from the API/application tier (CDN-fronted for security/performance but not cached), rather than treating the whole app as one uniform caching policy.

**Q39. "A news website's homepage updates every 30 seconds with new headlines, but gets 10,000 requests per second. How would you design the caching strategy?"**
A: Set a short `s-maxage` (e.g., 5-10 seconds) on the homepage response combined with `stale-while-revalidate` — this means the CDN serves the cached version to the vast majority of the 10,000 req/s, while only a small number of background revalidation requests actually reach origin (one per PoP per revalidation interval, not one per user request) — origin load becomes a small constant rather than scaling with traffic. This is the classic "cache nearly-everything for a very short time" pattern that handles high QPS for frequently-changing content far better than either (a) no caching (origin gets crushed) or (b) long TTLs (content goes stale for too long). Mention request coalescing (Q19) as the underlying mechanism that prevents a "miss storm" every time the short TTL expires.

**Q40. "How would you explain the value of a CDN to a non-technical stakeholder in one or two sentences?"**
A: A CDN puts copies of your website's content on servers physically closer to your users around the world, so pages load faster no matter where someone is — and as a side benefit, it acts as a shield that absorbs huge traffic spikes and attacks before they ever reach your actual servers, keeping the site both fast and reliable.

---

**Tip for interviews:** Five things separate strong candidates on CDN questions: (1) immediately framing a CDN as a *distributed reverse proxy* rather than treating it as an unrelated concept — ties this guide back to the load balancing fundamentals; (2) knowing the **`max-age` vs `s-maxage`** distinction and why origins set them differently — a frequent gotcha; (3) understanding **cache key design** (Q13-14) as the actual lever that determines real-world hit ratio, not just "turning caching on"; (4) knowing **request coalescing** (Q19) as the mechanism that prevents thundering herd on short-TTL high-traffic content (Q39 is a very common system design prompt); and (5) being able to articulate that a CDN still adds value for **uncacheable dynamic content** via connection/route optimization (Q20-21, Q25) — many candidates incorrectly think CDNs are only useful for static assets.
