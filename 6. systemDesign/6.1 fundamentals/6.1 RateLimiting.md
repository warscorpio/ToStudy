# API Gateway: Rate Limiting — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is rate limiting, specifically, at the API Gateway level?**
A: Rate limiting is the practice of restricting how many requests a given client (identified by API key, IP address, user ID, or some other key) is allowed to make within a defined time window, with requests beyond that threshold being rejected (commonly with an HTTP 429) rather than forwarded to backend services. At the gateway specifically, it's implemented as a cross-cutting policy applied at the edge — before a request ever reaches a backend service — so it protects the entire system uniformly rather than relying on each backend independently enforcing its own limits.

**Q2. Why is rate limiting needed at all — what specific problems does it solve?**
A: Several distinct problems, often conflated but worth separating: protecting backend capacity from being overwhelmed by either organic traffic spikes or a misbehaving client (a buggy retry loop, a runaway script); ensuring fair resource sharing across multiple clients so one heavy consumer can't starve capacity that other clients/tenants depend on; enforcing business/product constraints (a free-tier API plan capped at a certain request volume, distinct from a paid tier's higher allowance); and providing a first line of defense against abuse and certain classes of attack (credential stuffing attempts, scraping, application-layer DDoS) by capping how fast any single source can hammer the system.

**Q3. Why is the gateway specifically the right place to implement rate limiting, rather than each backend service handling it independently?**
A: Centralizing it at the gateway means excess requests are rejected at the very edge of the system, before consuming any backend compute, database, or downstream-service capacity at all — the cheapest possible point to reject a request. It also means the limiting logic and its client-facing behavior (status codes, headers, error format) are implemented and maintained consistently in one place, rather than potentially duplicated with subtle inconsistencies across many independently-developed backend services, each of which would otherwise need to reimplement the same logic correctly.

**Q4. What's the difference between rate limiting and a concurrency limit?**
A: Rate limiting bounds *how many requests over a time window* (e.g., 100 requests per minute), regardless of how long each individual request takes. A concurrency limit instead bounds *how many requests are simultaneously in flight* at any given moment (e.g., no more than 10 concurrent requests from this client), regardless of their rate of arrival over time. They address different failure modes: rate limiting protects against high request *volume* over time; concurrency limiting protects against a backend being saturated by many slow, long-running requests piling up simultaneously, even if the overall request rate looks modest. Gateways commonly support both, and they're often used together rather than as alternatives.

## Section 2: Rate Limiting Algorithms

**Q5. What is the fixed window algorithm, and what's its key weakness?**
A: The fixed window algorithm divides time into discrete, non-overlapping intervals (e.g., each calendar minute) and counts requests within the current interval against a fixed cap, resetting the counter to zero at the start of each new interval. Simple to implement and reason about, but its key weakness is a **boundary burst problem**: a client can send its full quota right at the very end of one window, and immediately send another full quota's worth right at the start of the next window — resulting in up to double the intended rate within a short span straddling the window boundary, even though each individual window's count never technically exceeded its limit.

**Q6. What is the sliding window log algorithm, and how does it address the fixed window's weakness?**
A: Instead of resetting at fixed boundaries, the sliding window log tracks the precise timestamp of every individual request within the lookback window (e.g., the last 60 seconds, continuously, not anchored to a fixed clock boundary), and counts how many requests fall within that continuously-moving window at the moment of each new request. This eliminates the boundary-burst problem entirely, since there's no fixed reset point for a client to exploit — the window always represents "however many requests happened in the *actual* last 60 seconds," accurately, at any point in time. The trade-off: it requires storing a timestamp per request (at least within the window), which is more memory/storage-intensive than a single counter, especially at high request volumes or with many distinct clients to track.

**Q7. What is the sliding window counter algorithm, and how does it balance the trade-offs of the previous two?**
A: A hybrid approach: it keeps simple counters per fixed window (like the fixed window algorithm, cheap to store) but estimates the *effective* count within a true sliding window by weighting the previous window's count proportionally to how much of it still overlaps with the current sliding window — e.g., if you're 25% of the way into the current window, the algorithm counts the current window's requests in full plus 75% of the previous window's count. This approximates the accuracy of a true sliding log without needing to store individual timestamps, at the cost of being an approximation rather than exact (it assumes requests were evenly distributed within the previous window, which isn't always precisely true, but is generally close enough in practice).

**Q8. What is the token bucket algorithm, and why is it a particularly common choice for rate limiting?**
A: A bucket holds a maximum number of tokens (the burst capacity), refilled at a steady, configured rate over time (e.g., one token added every X milliseconds, up to the bucket's cap). Each incoming request consumes one token if available; if the bucket is empty, the request is rejected (or queued, depending on configuration). It's a particularly common choice because it elegantly supports both a sustained average rate (governed by the refill rate) *and* a tolerance for legitimate short bursts (governed by the bucket's capacity) — a client that's been idle and has accumulated a full bucket can legitimately burst up to that capacity, while a client sending steadily at exactly the refill rate can sustain indefinitely without ever being rejected.

**Q9. What is the leaky bucket algorithm, and how does it differ in behavior from token bucket?**
A: Conceptually the inverse emphasis: incoming requests fill a bucket (queue) of fixed capacity, and requests are processed/forwarded out of the bucket at a fixed, steady rate, regardless of how bursty their arrival was — like water leaking out of a bucket at a constant rate regardless of how it was poured in. If the bucket (queue) is full when a new request arrives, that request is rejected. The key behavioral difference from token bucket: leaky bucket actively **smooths out bursts into a steady outflow rate** (closer to throttling, Q4 from the broader gateway guide's distinction between rejecting and smoothing), whereas token bucket *permits* bursts up to the bucket capacity to pass through immediately, only constraining the *sustained average* rate over time, not the instantaneous burst rate within that allowance.

**Q10. Given these options, how would you decide which algorithm to use for a given API?**
A: If legitimate clients are expected to have bursty-but-bounded usage patterns (e.g., a mobile app that does several rapid calls when a screen loads, then goes quiet) and you want to accommodate that without being overly strict, token bucket is generally the most natural fit, since it explicitly tolerates burst behavior. If you specifically want to smooth traffic into a steady, predictable outflow rate toward a backend that handles bursts poorly (regardless of how clients actually send requests), leaky bucket's smoothing behavior is more appropriate. If implementation simplicity and low overhead matter more than precise accuracy, and a modest boundary-burst tolerance is acceptable, fixed window (or sliding window counter as a cheap-but-more-accurate middle ground) is reasonable. True sliding window log is reserved for cases needing maximum precision and where the storage/memory cost of tracking individual timestamps is acceptable.

## Section 3: Dimensions and Keys for Rate Limiting

**Q11. What are the common dimensions along which a rate limit key is constructed?**
A: Per-API-key or per-authenticated-client (the most precise and common approach once a client is identified, allowing per-customer/per-tier limits); per-IP-address (useful before/without authentication, or as a coarser fallback, but imprecise — many genuine clients can share one IP behind NAT or a corporate proxy, and a single client can rotate IPs to evade IP-based limits); per-user (distinct from per-API-key when a single API key/application serves many end users, and you want to prevent one abusive end user from exhausting the application's shared quota); per-route/per-endpoint (applying tighter limits to specifically expensive operations like search, export, or report generation, distinct from cheaper read endpoints); and global/system-wide (an overall ceiling independent of any individual client, protecting absolute backend capacity regardless of how traffic happens to be distributed across clients).

**Q12. Why might per-IP rate limiting alone be insufficient or even counterproductive in some scenarios?**
A: Many legitimate, distinct clients can share a single observed IP address — behind a corporate NAT gateway, a public Wi-Fi network, or a CDN/proxy that doesn't forward the true originating client IP — meaning a per-IP limit can inadvertently throttle many innocent users collectively because of one heavy or abusive client sharing their IP. Conversely, it's also relatively easy for a genuinely abusive client to evade IP-based limiting by rotating across many IP addresses (common in distributed scraping or credential-stuffing setups), making IP alone a weak signal for actually identifying and constraining the responsible party. It's commonly used as one layer among several, not the sole rate-limiting dimension.

**Q13. What is tiered rate limiting, and what's a common real-world example?**
A: Different rate limit thresholds applied based on a client's plan, subscription tier, or contractual agreement — a free-tier API consumer might be capped at, say, 100 requests/hour, while a paid enterprise tier gets 10,000 requests/hour or higher, all enforced via the same underlying rate-limiting mechanism at the gateway, just parameterized differently per client based on their identified tier (commonly looked up from the client's API key or account metadata at request time). This is a very common monetization/product-tiering pattern for public-facing APIs, implemented as a configuration concern at the gateway rather than separate enforcement logic per tier.

**Q14. How should rate limits typically be communicated and configured for genuinely high-value or trusted internal clients (e.g., one internal service calling another through the gateway)?**
A: Internal, trusted service-to-service traffic is often exempted from the same restrictive limits applied to external/public clients, or given a much higher dedicated allowance — since the original motivations for limiting (protecting against unknown/untrusted/potentially abusive external actors) apply much less to traffic already authenticated as coming from another known, trusted internal service. That said, *some* ceiling is still often worth retaining even for internal traffic, as a safety net against bugs (a misbehaving internal service in a retry loop can still overwhelm a downstream dependency, even though it's "trusted" in the security sense) — distinguishing "protect against malicious abuse" from "protect against accidental self-inflicted overload" as two separate justifications for limits that may warrant different threshold philosophies even for trusted internal callers.

## Section 4: Distributed Rate Limiting

**Q15. Why does rate limiting become significantly harder once there are multiple gateway instances behind a load balancer, rather than a single gateway instance?**
A: If each gateway instance tracks rate-limit counters purely in its own local memory, a client's requests landing across multiple different instances (which is exactly what a load balancer is designed to do) means no single instance has a complete, accurate picture of that client's total request count — the client could effectively get N times their intended quota, where N is the number of gateway instances, by having their requests spread across all of them. Accurate rate limiting across multiple instances requires shared, centralized state that all instances can consult and update consistently.

**Q16. What's the typical solution to the distributed-state problem in Q15?**
A: A shared, external, low-latency data store — most commonly Redis — that all gateway instances read from and write to for rate-limit counters, rather than each instance maintaining its own independent local count. Redis specifically is a very common choice because it offers atomic increment-and-check operations (often via Lua scripting or built-in commands) with the speed needed to not noticeably add latency to every request, since the rate-limit check sits directly in the critical path of every single request passing through the gateway.

**Q17. What's the race condition risk in distributed rate limiting, and how is it typically mitigated?**
A: If checking "is this client under their limit" and incrementing their counter are done as two separate, non-atomic operations against the shared store, two near-simultaneous requests from the same client (arriving at different gateway instances at nearly the same moment) could both read the same "current count," both see it's under the limit, and both proceed — allowing the client to briefly exceed their intended limit despite the system technically performing a check on every request. The mitigation is ensuring the check-and-increment happens as a single atomic operation against the shared store (e.g., an atomic `INCR` followed by comparing the *returned* new value against the limit, or a Lua script in Redis that performs the whole check-and-increment as one atomic unit), rather than as two separate read-then-write steps that can interleave with another concurrent request.

**Q18. What's the trade-off of relying on a shared external store like Redis for every rate-limit check, given it sits in the critical path of every request?**
A: It introduces an additional network hop and a dependency on the external store's own availability and latency into every single request's path through the gateway — if Redis becomes slow or unavailable, it can directly degrade or break the gateway's ability to process *any* request, not just rate-limiting specifically, unless the gateway has a deliberate fallback behavior for that failure case (Q19). This is a real operational cost that needs to be weighed against the alternative (less accurate, instance-local limiting) — many production systems accept this trade-off because Redis (or similar) is fast and reliable enough in practice, but it's a dependency that needs its own monitoring, capacity planning, and failure-mode consideration, not an assumption-free addition.

**Q19. If the shared rate-limiting store becomes unavailable, what should the gateway's fallback behavior be, and what's the trade-off?**
A: Two broad options, each with a real trade-off: **fail open** (allow requests through without rate limiting when the store is unreachable) prioritizes availability — the system keeps serving traffic even during a store outage — at the cost of temporarily losing the protection rate limiting was meant to provide, right at a moment when something is already going wrong infrastructure-wise (arguably exactly when protection matters most). **Fail closed** (reject requests when the store is unreachable, since the limit can't be verified) prioritizes safety/protection at the cost of potentially taking down legitimate traffic entirely during what might otherwise be a survivable, partial infrastructure issue. Most production systems lean toward fail-open for rate limiting specifically (since an availability outage caused by losing rate-limiting protection is usually considered worse than briefly under-protecting the backend), but this is a deliberate trade-off decision, not a universally "correct" default — it depends on how much backend protection the rate limiter is actually relied upon for.

## Section 5: Client-Facing Behavior

**Q20. What HTTP status code is conventionally returned for a rate-limited request, and why does using the correct code matter?**
A: HTTP 429 (Too Many Requests) is the standard, purpose-built status code for this case. Using it correctly (rather than, say, a generic 503 or 403) matters because well-built clients and HTTP libraries often have specific, automatic handling for 429 — recognizing it as a transient, retry-appropriate condition distinct from a permanent failure (like 403 Forbidden, which implies retrying won't help) or a generic server error (503, which might imply a different kind of backoff/retry logic) — so using the wrong status code can cause client libraries to handle the rejection incorrectly (e.g., not retrying when they should, or retrying immediately when they should back off).

**Q21. What headers are conventionally included on rate-limited (and even non-rate-limited) responses, and what's each for?**
A: `Retry-After` tells the client how long to wait before retrying (in seconds, or as a specific timestamp), giving a concrete, actionable signal rather than leaving the client to guess. `X-RateLimit-Limit` communicates the client's total allowed quota for the current window; `X-RateLimit-Remaining` communicates how much of that quota is left; `X-RateLimit-Reset` indicates when the current window resets. Including these informational headers on *every* response (not just rejected ones) lets well-behaved clients proactively self-regulate their request rate before ever hitting the limit, rather than only discovering the limit through trial-and-error rejection.

**Q22. What client-side strategy should a well-behaved API consumer implement in response to rate limiting, and why does naive retry behavior make things worse?**
A: Exponential backoff (waiting progressively longer between retry attempts after each successive rejection) combined with jitter (adding randomness to the backoff delay) is the standard recommended client-side pattern. Naive immediate retry — retrying the instant a request is rejected, with no delay — is actively counterproductive: if many clients are simultaneously rate-limited (e.g., during a broader traffic spike that triggered the limiting in the first place) and all retry immediately and simultaneously, they collectively create a synchronized retry storm that can keep hitting the same limit repeatedly, or even worsen backend load right as it's trying to recover — exponential backoff with jitter specifically exists to desynchronize many clients' retry timing and avoid this thundering-herd effect.

**Q23. Should rate limit error responses include a descriptive error body, and what should/shouldn't be included?**
A: Yes — beyond just the status code and headers, a clear, machine-parseable error body (commonly JSON) explaining that the request was rate-limited, ideally including which specific limit was hit (useful when multiple dimensions/tiers of limiting are in play, per Q11) and reinforcing the retry timing, helps both automated client logic and human developers debugging the integration understand what happened without needing to separately consult documentation. What generally shouldn't be included: internal implementation details of the rate-limiting mechanism itself (which algorithm, which internal store, internal thresholds beyond what's already exposed via the standard headers) that aren't useful to the client and could expose unnecessary internal detail.

## Section 6: Related Concepts and Distinctions

**Q24. What's the difference between rate limiting and a usage quota?**
A: Rate limiting governs the *rate* of requests over a relatively short, often rolling time window (e.g., requests per second or minute), primarily for protection and traffic-shaping purposes. A usage quota typically governs total consumption over a much longer billing/contractual period (e.g., a monthly cap of 1 million API calls under a given pricing plan), primarily for product/monetization purposes rather than moment-to-moment protection. They're often implemented as two genuinely separate mechanisms at the gateway — a client might be well within their monthly quota overall but still get rate-limited for sending too many requests too quickly within a short window, and vice versa.

**Q25. How does rate limiting relate to, and differ from, the circuit breaker pattern at the gateway?**
A: Rate limiting protects backend capacity proactively, based on a configured threshold of how much traffic *should* be allowed, regardless of whether the backend is currently healthy or struggling — it's a static, policy-driven cap. A circuit breaker is reactive — it monitors the actual *observed failure rate* of calls to a backend and dynamically stops sending traffic once that backend appears to genuinely be failing, independent of whether the request volume itself was within any configured rate limit. They're complementary, not overlapping mechanisms: rate limiting controls volume regardless of backend health; circuit breaking reacts to backend health regardless of request volume, and a well-architected gateway typically implements both as separate, independently-configured layers of protection.

## Section 7: Security Considerations

**Q26. How does rate limiting function as a defense (though not a complete one) against application-layer DDoS or scraping attacks?**
A: By capping how many requests any single identified source can send within a given window, rate limiting bounds the effective impact a single source can have, regardless of how aggressively that source attempts to send traffic — turning what would otherwise be an unbounded flood from one source into a bounded, predictable, much more manageable load. It's not a complete defense against large-scale distributed attacks (an attacker spreading requests across thousands of distinct sources/IPs, each individually staying under the per-source limit, can still collectively generate enormous aggregate load — addressed by global/system-wide limits and other DDoS-specific infrastructure, not per-client rate limiting alone), but it meaningfully raises the bar and is a standard, necessary first layer.

**Q27. What's a common bypass technique attackers use against naive rate limiting, and how does it inform better limiting design?**
A: Rotating across many distinct API keys, accounts, or IP addresses (e.g., via a botnet, proxy network, or freely-creatable free-tier accounts) to keep each individual identified source under its per-source limit, while the aggregate request volume across all of them remains very high. This is precisely why relying solely on a single, easily-rotatable dimension (just IP, or just a freely self-registerable API key) is weak — better-designed rate-limiting strategies layer multiple dimensions together (per-key *and* a global ceiling; behavioral/anomaly-detection signals beyond pure rate counting; sometimes proof-of-work or CAPTCHA challenges for suspicious patterns) rather than relying on any single easily-evadable identifier as the sole gate.

**Q28. Why is it important that rate-limit state (counters, keys) itself isn't trivially manipulable by the client?**
A: If a client could influence what key their requests are counted under (e.g., a poorly designed system that derives the rate-limit key from a client-supplied, unauthenticated header rather than a verified, server-validated identity), an attacker could simply vary that client-controlled value on each request to effectively get a fresh counter every time, bypassing the limit entirely. This is why rate-limit keys should be derived from server-validated identity (an authenticated API key, a validated JWT claim, the actual observed connection IP) rather than anything the client can freely choose or spoof in a request it controls.

## Section 8: Scenario-Based Questions

**Q29. "A specific API key is making far more requests than its configured limit should allow — investigation shows requests are landing on multiple gateway instances, and each instance's local rate limiting is independently within bounds. What's going wrong, and how do you fix it?"**
A: This is the distributed-state problem (Q15) — each gateway instance is correctly enforcing the limit *against its own local view*, but because no instance has a complete picture of the client's total request count across all instances, the client is effectively getting up to N times their intended quota (N = number of gateway instances) by having their traffic spread across the fleet. The fix is moving to centralized, shared rate-limit state (commonly Redis) that every gateway instance reads from and atomically updates on each request (Q16–17), rather than each instance maintaining independent local counters — ensuring the limit reflects the client's true aggregate request volume regardless of which specific instance handled any given request.

**Q30. "Your team wants to add rate limiting to a previously unprotected public API that's seen a recent traffic spike, some of which looks like legitimate growth and some of which looks like abusive scraping. How would you roll this out?"**
A: Start by distinguishing the two traffic patterns concretely (via logging/analysis of request patterns, source diversity, request timing) rather than applying a single blunt limit to everyone immediately — a limit set too aggressively risks rejecting genuine, valuable growing usage right alongside the abuse. A practical rollout: deploy rate limiting initially in a "log only, don't reject" / shadow mode to observe what limits would actually trigger against real current traffic without yet impacting any client, calibrate thresholds based on that real data (distinguishing what looks like reasonable peak legitimate usage from clear outliers), then enable actual enforcement, likely with generous limits for authenticated/identified legitimate clients (per-API-key, tiered per plan, Q13) and tighter limits for anonymous/unauthenticated traffic where abuse is more likely to originate from. Communicate the new limits and the standard headers (Q21) to existing API consumers ahead of enforcement, so legitimate integrators aren't caught off guard.

**Q31. "Rate limiting is implemented at the gateway via a shared Redis store, and during a recent Redis outage, the entire API went down — not just rate-limiting protection, but all traffic. How would you explain this, and what would you change?"**
A: This points to a fail-closed configuration (Q19), or possibly a synchronous, blocking dependency on Redis with no timeout/fallback at all — if the gateway treats "I can't reach Redis to check the rate limit" as equivalent to "reject this request," then a Redis outage takes down all traffic, not just rate-limiting specifically, which is a disproportionate blast radius for what should arguably be a best-effort protection layer, not a hard dependency for serving traffic at all. The recommended change: configure explicit fail-open behavior for the rate-limiting check specifically (allow requests through, without rate-limiting enforcement, if the shared store is unreachable within a tight timeout), accepting the trade-off of temporarily reduced protection during a Redis outage in exchange for not taking the entire API down over what's meant to be a supplementary, not foundational, protective layer — paired with proper alerting on the Redis dependency itself, so the temporary reduced-protection window is visible and short-lived rather than silent.

**Q32. "A client integration team reports their well-behaved, properly-backed-off retry logic is still getting rate-limited far more than expected, even though they're confident they're under the documented limit. How would you investigate?"**
A: First verify what rate-limit key the client is actually being evaluated under — confirm it matches what the client believes (their specific API key) rather than an unintended broader key (e.g., accidentally being grouped under a shared IP with other unrelated clients, per Q12, if IP-based limiting is layered in alongside or instead of key-based limiting). Check whether multiple distinct rate-limit dimensions are in play (Q11/Q23) — the client may be comfortably within their per-key limit but unknowingly tripping a separate per-route or global limit they weren't aware applied to them, which the documented "per-key" limit alone wouldn't explain. Also verify the actual algorithm and window behavior in use (Q5–9) — if the system uses fixed windows, a client whose traffic happens to legitimately cluster near window boundaries could be getting caught by the boundary-burst effect (Q5) despite their overall sustained rate genuinely being under the limit, which would point toward switching to a sliding window approach rather than the client's integration logic being at fault.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| Rate limiting | Caps request *rate* over time; rejects (commonly 429) excess requests |
| Concurrency limiting | Caps simultaneous *in-flight* requests, independent of arrival rate |
| Fixed window | Simple counter per interval; vulnerable to boundary-burst doubling |
| Sliding window log | Exact, timestamp-based; accurate but storage-heavier |
| Sliding window counter | Weighted hybrid; cheap and reasonably accurate approximation |
| Token bucket | Refilling token pool; tolerates bursts up to bucket capacity |
| Leaky bucket | Fixed-rate outflow; smooths bursts into steady throughput |
| Common keys | Per-API-key, per-IP, per-user, per-route, global |
| Distributed limiting | Requires shared state (e.g., Redis) with atomic check-and-increment |
| Fail open vs closed | Trade-off between availability and protection when the shared store is down |
| 429 + headers | Retry-After, X-RateLimit-Limit/Remaining/Reset for client self-regulation |
| Backoff + jitter | Standard client retry pattern to avoid synchronized retry storms |
| Quota vs rate limit | Quota = long-term usage cap; rate limit = short-window pace control |
| Circuit breaker | Reactive, health-based; complementary to proactive, volume-based rate limiting |

---

**Tip for interviews:** What separates strong candidates on API Gateway rate limiting specifically: (1) being able to **compare the algorithms concretely** — explaining the fixed-window boundary-burst problem and why token bucket vs leaky bucket produce genuinely different traffic shapes, not just naming them (Q5–10); (2) understanding that **distributed rate limiting across multiple gateway instances requires shared, atomically-updated state**, and being able to explain the race condition that arises without atomicity (Q15–17); (3) having a clear, deliberate answer for the **fail-open vs fail-closed trade-off** when the shared rate-limit store itself becomes unavailable, rather than treating it as an unconsidered edge case (Q19, Q31); (4) knowing the **standard client-facing contract** — 429, Retry-After, the X-RateLimit-* headers, and why exponential backoff with jitter matters for avoiding retry storms (Q20–22); and (5) recognizing that **a single easily-rotatable rate-limit dimension is a weak defense**, and being able to reason about layered, multi-dimensional limiting and server-validated (not client-supplied) keys as the more robust real-world design (Q27–28).
