# Weighted Round Robin (WRR) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Weighted Round Robin (WRR)?**
A: An extension of Round Robin where each backend is assigned a numeric weight reflecting its relative capacity. The scheduler distributes requests proportionally to those weights — a backend with weight 4 receives 4x the traffic of a backend with weight 1. It solves the core weakness of plain Round Robin: the assumption that all backends are equal.

**Q2. Why do we need weights at all — why not just run homogeneous fleets?**
A: In theory, homogeneous fleets are ideal. In practice:
- Cloud instance types differ in CPU, memory, and network throughput — you may not always have the exact instance class available.
- Mixed generations of hardware exist in on-prem and hybrid deployments.
- Canary and blue/green deployments intentionally run two versions at different traffic proportions.
- Some backends may be intentionally under-provisioned for cost reasons (e.g., spot/preemptible instances at lower weight).
- Backends coming online after a restart or cold start should receive less traffic initially (slow start).

**Q3. How do you calculate weight values in practice?**
A: Weights are usually relative integers, not percentages. Common approaches:
- **Capacity-based**: proportional to CPU cores or memory — a 4-core node gets weight 4, a 2-core node gets weight 2.
- **Benchmark-based**: run load tests, assign weights proportional to measured RPS throughput at target latency.
- **Percentage-based translation**: for a canary at 5%, set v2 weight = 1 and v1 weight = 19 (1/20 = 5%).
- **Empirical tuning**: start with capacity-based weights, observe latency/error distributions per backend, adjust.

The absolute values don't matter — only the ratios. Weight 3,1,2 is identical to 30,10,20.

**Q4. What is the difference between WRR and plain Round Robin at the implementation level?**
A: Plain Round Robin maintains a single counter modulo N. WRR must track:
- A static `weight` per backend (configured).
- A dynamic `current_weight` per backend (changes each cycle).
- Selection logic that picks the highest current_weight and adjusts after each pick.

This makes WRR O(N) per request selection (scan all backends to find max) vs O(1) for plain Round Robin, though N is typically small enough that this is negligible.

**Q5. What is the difference between Weighted Round Robin and Weighted Random?**
A: WRR guarantees a deterministic, interleaved sequence — over any W requests (where W = sum of weights), each backend receives exactly its weight's share. Weighted Random samples probabilistically — each request independently picks a backend with probability proportional to its weight. Weighted Random has more variance at short time scales (especially at low QPS, one backend may receive more than its share by chance) but requires no state. WRR is fairer at low QPS; the two converge at high QPS.

## Section 2: Algorithms — Naive vs Smooth

**Q6. How does the naive WRR algorithm work, and what is its problem?**
A: The naive approach repeats each backend in the rotation by its weight value:

Weights: A=3, B=1, C=2 → sequence: A, A, A, B, C, C, A, A, A, B, C, C, ...

Problem: **burstiness**. All 3 of A's requests arrive back-to-back before B or C gets any. If A is a backend that has a shared resource (e.g., a DB connection pool or a rate-limited downstream API), those 3 consecutive requests hit it in rapid succession. This causes latency spikes, queue buildup, and poor interleaving — defeating one of the main goals of load balancing: spreading traffic smoothly over time.

**Q7. What is Smooth Weighted Round Robin (SWRR), and how does it work?**
A: Smooth WRR (used by NGINX) produces an interleaved sequence — requests are distributed evenly in time, not in bursts. Algorithm per request:

1. Add each backend's `weight` to its `current_weight`.
2. Select the backend with the highest `current_weight`.
3. Subtract the total sum of all weights from the selected backend's `current_weight`.

Example — weights A=3, B=1, C=2, total=6:

| Step | current_weight before    | Selected                 | current_weight after |
|---   |---                       |---                       |---                   |
| 1    | A=3, B=1, C=2            | A (highest=3)            | A=-3, B=1, C=2       |
| 2    | A=0, B=2, C=4            | C (highest=4)            | A=0, B=2, C=-2       |
| 3    | A=3, B=3, C=0            | A (highest=3, tie→first) | A=-3, B=3, C=0       |
| 4    | A=0, B=4, C=2            | B (highest=4)            | A=0, B=-2, C=2       |
| 5    | A=3, B=-1, C=4           | C (highest=4)            | A=3, B=-1, C=-2      |
| 6    | A=6, B=0, C=0            | A (highest=6)            | A=0, B=0, C=0        |

Resulting sequence: A, C, A, B, C, A — perfectly interleaved, not A, A, A, B, C, C. After 6 steps (= total weight), the state resets to zero and repeats.

**Q8. Why does SWRR reduce latency compared to naive WRR?**
A: Because it avoids request bursts to any single backend. Burst requests to one backend mean they queue up there simultaneously, increasing latency. Smooth interleaving means each backend's requests are spaced out in time — backends process one request, return to idle briefly, then get another — keeping queues short and response times consistent.

**Q9. What is the time complexity of SWRR and does it scale with large backend pools?**
A: O(N) per request — you must scan all backends to find the maximum current_weight. For large N (hundreds of backends), this becomes expensive. Alternatives for large pools:
- Use a **max-heap** (priority queue) to reduce selection to O(log N).
- Or switch to P2C (Power of Two Choices) which is O(1) and handles heterogeneous load better at large scale.

In practice, LB backend pools are rarely more than a few dozen nodes, making O(N) SWRR fast enough (nanoseconds per decision).

**Q10. Is SWRR the algorithm NGINX uses by default?**
A: Yes — NGINX's upstream module uses SWRR when weights are specified. The algorithm was introduced in NGINX in 2013 and is now the de facto standard implementation. Envoy also uses SWRR for its `ROUND_ROBIN` policy when locality weights are configured.

## Section 3: Use Cases

**Q11. How is WRR used for canary deployments?**
A: WRR is a clean mechanism for traffic splitting between versions:
- Set v1 weight = 95, v2 weight = 5 → 5% of traffic hits v2.
- Observe error rate, p99 latency, and business metrics on v2.
- Gradually increase v2 weight: 5 → 10 → 25 → 50 → 100.
- If v2 looks bad, drop its weight to 0 instantly — no redeployment needed.

This is the approach used by Kubernetes Ingress controllers (NGINX Ingress, Traefik), Envoy with two weighted clusters, Istio VirtualService with `weight` fields on destination routes, and AWS ALB with weighted target groups.

**Q12. How is WRR used for blue/green deployments?**
A: Blue/green maintains two full parallel environments. WRR enables a controlled cutover rather than an instantaneous switch:
- Start: blue=100, green=0.
- Begin cutover: blue=90, green=10.
- Validate green, ramp: blue=50, green=50 → blue=0, green=100.
- Blue stays live (weight=0 but deployed) as an instant rollback target.

Unlike pure blue/green (instant cut), WRR-based gradual cutover limits blast radius and allows real-traffic validation before full commitment.

**Q13. How do you use WRR for A/B testing?**
A: WRR can split traffic between variants, but it's not ideal for A/B testing on its own because it doesn't provide user stickiness — the same user may hit both variants across requests, contaminating results. Proper A/B testing needs consistent assignment per user (via cookie, user ID hash, or feature flag service). WRR is better for infrastructure-level canaries (catching crashes, regressions) than product-level A/B experiments (measuring conversion rates).

**Q14. How is WRR used for heterogeneous fleets?**
A: In a fleet where nodes have different specs:
- 8-core nodes → weight 8.
- 4-core nodes → weight 4.
- 2-core nodes → weight 2.

The 8-core node gets 4x the traffic of the 2-core node, proportional to capacity. This is common in on-prem environments where hardware generations mix, or in cloud environments using different instance families (e.g., c5.2xlarge alongside c5.xlarge).

**Q15. How is WRR used with spot/preemptible instances?**
A: Spot instances are cheaper but can be interrupted. A safe pattern:
- On-demand instances: weight = full capacity.
- Spot instances: weight = reduced (e.g., 50% of on-demand weight).

Lower weight means fewer requests in flight on spot instances at any moment, reducing the number of requests that need to be re-routed on interruption. Combined with connection draining, this minimizes disruption when spot instances are reclaimed.

**Q16. What is "slow start" in the context of WRR, and when is it critical?**
A: Slow start gradually increases a new backend's effective weight from 0 to its configured weight over a ramp period (e.g., 30–120 seconds). Without it, a freshly started backend with an empty JVM JIT cache, cold DB connection pool, and no in-memory caches receives full traffic immediately — and may fail or respond slowly, causing errors that WRR won't automatically compensate for.

In NGINX: `server backend3 weight=5 slow_start=60s;`
In Envoy: `slow_start_config` with `min_weight_percent` and ramp duration.

Critical for: JVM services (JIT warmup), services with expensive cache warming, or backends initializing large in-memory data structures.

## Section 4: Integration with Health Checks and Dynamic Weighting

**Q17. What happens to WRR when a backend fails its health check?**
A: The backend is removed from the WRR pool entirely (weight effectively becomes 0). The scheduler redistributes requests among surviving backends proportional to their weights. When the backend recovers and passes health checks, it re-enters the pool — ideally through slow start to avoid thundering herd on recovery.

**Q18. Can weights be changed dynamically without restarting the LB?**
A: Yes, and this is a key operational feature:
- **NGINX**: reload config with `nginx -s reload` — graceful reload with no dropped connections.
- **Envoy/xDS**: weights are part of the cluster's EDS (Endpoint Discovery Service) payload — updated in real time via the control plane (e.g., Istio, custom xDS server) with no restart.
- **AWS ALB**: modify weighted target group via API/console in real time — takes effect within seconds.
- **Kubernetes Ingress (NGINX/Traefik)**: update annotation or CRD field, the controller reconciles immediately.

Dynamic weight adjustment is the basis for automated canary promotion tools (e.g., Flagger, Argo Rollouts) that adjust weights programmatically based on metrics.

**Q19. What is dynamic/adaptive WRR?**
A: Standard WRR uses static, manually configured weights. Dynamic WRR adjusts weights automatically based on observed backend metrics — response time, error rate, CPU utilization — reducing weight on degraded backends and increasing it on healthy ones. This blurs the line between WRR and Least Response Time. Systems like Envoy's `LEAST_REQUEST` with active health checking approximate this behavior. True dynamic WRR is rare in off-the-shelf LBs but common in custom traffic management systems and service meshes.

**Q20. How do tools like Flagger or Argo Rollouts use WRR under the hood?**
A: They implement automated canary promotion by:
1. Starting with v2 weight = 0 (or 5%). 
2. Querying a metrics backend (Prometheus, Datadog, New Relic) for error rate and latency on v2.
3. If metrics are within acceptable thresholds, incrementing v2's weight by a configured step (e.g., +10% every 5 minutes).
4. If metrics breach a threshold, rolling back weight to 0 and alerting.

They interact with the LB via its API (Istio VirtualService, NGINX Ingress annotation, Argo Rollouts TrafficRouting) to update weights programmatically. The LB mechanism is WRR; the intelligence is in the progressive delivery controller.

## Section 5: WRR in Specific Technologies

**Q21. How do you configure WRR in NGINX?**
A:
```nginx
upstream backend_pool {
    server backend1 weight=5;
    server backend2 weight=3;
    server backend3 weight=2 slow_start=30s;
}
```
NGINX uses SWRR automatically when weights differ. The total weight is 10, so backend1 gets 50% of requests, backend2 gets 30%, backend3 gets 20%. `slow_start=30s` ramps backend3's effective weight from 0 to 2 over 30 seconds after it joins the pool.

**Q22. How do you configure WRR in Envoy?**
A: At the endpoint level via EDS or static config:
```yaml
load_assignment:
  cluster_name: my_service
  endpoints:
    - locality:
        region: us-east-1
        zone: us-east-1a
      load_balancing_weight: 70    # 70% of traffic to this locality
      lb_endpoints:
        - endpoint:
            address: {socket_address: {address: backend1, port_value: 8080}}
          load_balancing_weight: 3
        - endpoint:
            address: {socket_address: {address: backend2, port_value: 8080}}
          load_balancing_weight: 1
```
Envoy also supports locality-weighted load balancing on top of per-endpoint weights, enabling AZ-aware WRR.

**Q23. How does Istio VirtualService implement WRR for canary deployments?**
A:
```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: my-service
spec:
  http:
    - route:
        - destination:
            host: my-service
            subset: v1
          weight: 90
        - destination:
            host: my-service
            subset: v2
          weight: 10
```
The `weight` fields in the route sum to 100 (treated as percentages). Istio's Envoy sidecars enforce this split at every pod-to-pod connection, not just at the ingress — meaning internal service-to-service traffic also respects the canary split.

**Q24. How does AWS ALB implement WRR for canary/blue-green?**
A: AWS ALB uses **Weighted Target Groups** — each target group (a set of backend instances) gets a weight. Traffic is split proportionally:
```
Target Group v1: weight 90
Target Group v2: weight 10
```
Managed via the AWS Console, CLI (`aws elbv2 modify-rule`), or Terraform (`aws_lb_listener_rule` with `weighted_forward`). Combined with ALB's slow-start duration setting per target group and connection draining, this provides a full WRR-based progressive delivery mechanism in AWS without a service mesh.

**Q25. How does Kubernetes handle WRR natively (without a service mesh)?**
A: Standard Kubernetes Services use `kube-proxy` (iptables/ipvs) for load balancing, which is plain Round Robin with no weight support. IPVS mode technically supports weighted scheduling, but Kubernetes doesn't expose weight configuration through the Service API. For WRR you need either:
- An Ingress controller (NGINX Ingress: `nginx.ingress.kubernetes.io/canary-weight` annotation) for north-south traffic.
- A service mesh (Istio, Linkerd, Cilium) for east-west weighted routing.
- A Gateway API implementation (`HTTPRoute` with `weight` field on `BackendRef`) — the newer, standard approach.

## Section 6: Failure Modes & Edge Cases

**Q26. What happens if two backends have the same weight and one is 2x slower?**
A: WRR distributes requests evenly (same weight = same share), but the slower backend accumulates a backlog. Its in-flight request count grows while the fast backend finishes requests and sits idle between rounds. WRR doesn't adapt — it doesn't see backend latency. The slow backend degrades silently until health checks remove it (if error rates spike) or it falls over entirely. This is WRR's fundamental blind spot — use Least Connections or Least Response Time when backends can exhibit variable latency.

**Q27. Can WRR cause uneven load during a rapid traffic spike?**
A: Yes — WRR is a statically-weighted algorithm. During a sudden spike (e.g., flash sale), it continues distributing at configured ratios regardless of whether backends are keeping up. A backend at 40% utilization in steady state may be overwhelmed at 90%+ during a spike, but WRR doesn't shift traffic away from it. Mitigation: combine WRR with circuit breaking (stop sending to backends above error threshold) and auto-scaling (add more backends, which enter the pool and get their weight immediately).

**Q28. What is weight starvation, and when does it occur?**
A: In naive WRR, if one backend has a very high weight relative to others, lower-weight backends go long stretches without receiving requests. Example: weights A=100, B=1, C=1. Backend B and C each receive only 1 request every 102 requests. During that gap, if B or C become unhealthy, they may not receive a health-check probe for a long time (if health checking is request-based). SWRR mitigates this through interleaving, and most LBs use separate active health checks (periodic pings) independent of request routing to avoid this issue.

**Q29. How do floating-point weight ratios (e.g., 33.3%) cause problems and how do you handle them?**
A: WRR implementations typically use integers. Expressing 33.3% with integers requires rounding: weights 1,1,1 give 33.3% each — fine for three-way splits. But 10%/90% splits: weight 1 vs 9, or 10 vs 90 — both work. Problems arise with prime-number splits (e.g., 7%/93%) or multi-service splits that don't reduce to small integers cleanly (e.g., 5 services at 20% each = trivial; 3 services at different % = needs care). Most tools (Istio, ALB) accept percentages directly and handle rounding internally. When doing it yourself, scale up: use weights in the hundreds to preserve precision (e.g., 7 vs 93 instead of 1 vs 13).

**Q30. What happens when a new backend is added mid-rotation with a high weight?**
A: It immediately receives its full proportional share of new requests — which can overwhelm a warming-up backend. Without slow start, a new backend with weight=5 in a pool of 5 other backends each at weight=5 suddenly absorbs 1/6th of traffic, cold. Slow start mitigates this. Additionally, connection draining on the rest of the pool isn't needed (they're still healthy), but the new backend may need time to fill its connection pools and caches before handling its full share gracefully.

## Section 7: Scenario-Based Questions

**Q31. "You have three backends: two c5.2xlarge (8 vCPU) and one c5.xlarge (4 vCPU). You're using plain Round Robin. What's the problem and how do you fix it?"**
A: Plain Round Robin sends equal traffic to all three — each gets 33% of requests. But the c5.xlarge has half the capacity of a c5.2xlarge, so it's handling the same load with fewer resources. It will show higher CPU utilization, longer queues, and higher latency than the other two. Fix: Weighted Round Robin with weights c5.2xlarge=2, c5.2xlarge=2, c5.xlarge=1. The xlarge gets 20% of requests, each 2xlarge gets 40%, matching their capacity ratio.

**Q32. "Your canary deployment (WRR: v1=95, v2=5) is showing higher p99 latency on v2. Do you roll back? What's your process?"**
A: Don't immediately roll back — investigate first:
1. **Is the latency difference statistically significant?** At 5% traffic, sample size is small — a few slow requests can skew p99 heavily. Compare absolute request counts, not just percentages.
2. **Is it consistent or spiky?** A transient spike (cold start, JIT compilation) vs consistent elevation tells a different story.
3. **Check for obvious causes**: new DB queries, missing indexes, synchronous calls that were previously async, larger payload sizes.
4. **Decision**: If p99 is >20% higher and consistent after 10+ minutes, drop v2 weight to 0 immediately (zero-downtime rollback). Investigate in staging. If it's a transient spike that recovered, hold at 5% longer before promoting.

The ability to set weight=0 instantly is the key operational advantage of WRR-based canaries over big-bang deployments.

**Q33. "You need to migrate traffic from an on-prem data center to AWS without downtime. How does WRR help?"**
A: Use WRR at the DNS/L4 layer (e.g., Route 53 weighted routing policies or a global LB):
- Start: on-prem=100, AWS=0.
- Once AWS environment is validated: on-prem=95, AWS=5.
- Gradually shift: 80/20 → 50/50 → 20/80 → 0/100.
- Keep on-prem at weight=0 (not decommissioned) for a week as rollback insurance.

Key considerations: session state must be externalized (so users don't lose sessions when shifted from on-prem to AWS), DB replication must keep both environments in sync during the transition, and monitoring must cover both environments to detect divergence early.

**Q34. "A product manager wants to A/B test two checkout flows — 50% of users see flow A, 50% see flow B, and a user must always see the same flow. Can WRR do this?"**
A: WRR alone can't — it distributes requests, not users. The same user will hit both A and B across different requests, corrupting experiment results. The solution is:
- **WRR + sticky sessions**: set WRR weights to 50/50 AND use cookie-based stickiness so once a user is assigned to A or B, they stay there. But this requires the LB to store/enforce the stickiness.
- **Better: feature flags**: use a proper experimentation platform (LaunchDarkly, Optimizely, or a custom user-ID hash-based system) that assigns users deterministically. WRR at the LB layer is the wrong tool for user-level A/B testing — it's an infrastructure distribution mechanism, not a user segmentation mechanism.
