# Reverse Proxy vs Forward Proxy — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a proxy server, fundamentally?**
A: An intermediary that sits between a client and a server, forwarding requests and responses on behalf of one side. The defining question that distinguishes proxy types is: **whose interests does the proxy represent — the client's or the server's?** A forward proxy represents and is configured by the client. A reverse proxy represents and is configured by the server/origin infrastructure. The mechanics (intercept request, forward, relay response) are nearly identical; the ownership and intent are what differ.

**Q2. What is a forward proxy?**
A: A proxy that sits in front of a group of clients, forwarding their outbound requests to the internet on their behalf. The destination server sees the proxy's IP, not the client's. The client is explicitly configured to use the proxy (browser settings, system proxy config, or corporate network enforcement). Classic use: a corporate network where all employee traffic exits through a forward proxy for content filtering and monitoring.

**Q3. What is a reverse proxy?**
A: A proxy that sits in front of a group of backend servers, receiving inbound requests from clients on the internet and forwarding them to the appropriate backend. The client only ever sees the reverse proxy's address — it has no idea how many backend servers exist or where they are. The backend servers are configured to receive traffic only from the reverse proxy, not the public internet directly. Classic use: NGINX or an ALB sitting in front of a fleet of application servers.

**Q4. What's the simplest mental model to distinguish them?**
A: Forward proxy = "I am hiding/representing the client from the server." Reverse proxy = "I am hiding/representing the server from the client." If you ask "who configured this proxy and whose traffic does it protect?" — client-side config and client protection = forward; server-side config and server protection = reverse.

**Q5. Does the client know it's talking to a reverse proxy?**
A: Typically no — from the client's perspective, the reverse proxy *is* the server. The client makes a request to `api.example.com`, gets a response, and has no visibility into whether that request was served directly or routed through a reverse proxy to one of 50 backend instances. This transparency is by design — it lets the backend infrastructure change completely (scale, migrate, restructure) without clients noticing.

**Q6. Does the server know it's talking to a forward proxy?**
A: Generally yes, partially — the destination server sees the forward proxy's IP address as the connection source, not the original client's IP. Depending on the forward proxy type (Q9), the server may or may not know a proxy is involved at all, and may or may not be able to recover the original client's identity.

## Section 2: Architecture and Traffic Flow

**Q7. Walk through the request flow for a forward proxy.**
A: 
1. Client (e.g., an employee's laptop) is configured to route all HTTP/HTTPS traffic through the forward proxy (via browser proxy settings, PAC file, or transparent network interception).
2. Client sends request to the forward proxy: "Get me `https://example.com`."
3. Forward proxy evaluates policy (allowed? blocked category? cached?), then makes the request to `example.com` on the client's behalf.
4. `example.com` sees the request coming from the forward proxy's IP — it has no direct knowledge of the original client.
5. Forward proxy receives the response and relays it back to the client.

**Q8. Walk through the request flow for a reverse proxy.**
A:
1. Client sends a request to `api.example.com` — DNS resolves to the reverse proxy's IP (the client thinks this IS the server).
2. Reverse proxy receives the request, applies routing/load balancing logic, and selects an appropriate backend server.
3. Reverse proxy forwards the request to the selected backend (often over an internal/private network).
4. Backend processes the request and returns a response to the reverse proxy.
5. Reverse proxy relays the response back to the client, who never sees which backend actually served it.

**Q9. What is the difference between a transparent, anonymous, and explicit forward proxy?**
A:
- **Explicit (configured) proxy**: the client is explicitly configured with the proxy's address (browser settings, `HTTP_PROXY` env var, PAC file). The client knows it's using a proxy.
- **Transparent proxy**: the network intercepts traffic (e.g., via firewall rules redirecting port 80/443) without any client-side configuration. The client is unaware a proxy is involved — common in ISP-level or corporate gateway proxies.
- **Anonymous proxy**: strips identifying headers (like `X-Forwarded-For`) so the destination server cannot determine the original client IP at all — used for privacy/anonymity tools.

**Q10. Is a reverse proxy always "transparent" to the backend server?**
A: No — the backend typically knows it's behind a reverse proxy and is configured accordingly (e.g., trusting `X-Forwarded-For` headers only from the reverse proxy's IP, binding to internal interfaces only). What's transparent is the relationship to the *client*, not to the *backend*.

## Section 3: Use Cases

**Q11. What are the primary use cases for a forward proxy?**
A:
- **Content filtering / access control**: corporate networks blocking specific categories of websites (social media, gambling, malware domains).
- **Anonymity / privacy**: hiding the client's real IP from destination servers (VPN-adjacent use case).
- **Bypassing geographic restrictions**: routing through a proxy in a different region to access geo-restricted content.
- **Caching for outbound traffic**: caching frequently-accessed external resources to reduce bandwidth (e.g., caching OS update packages for an entire office).
- **Centralized logging / monitoring / DLP**: auditing what employees access, preventing data exfiltration.
- **Centralized authentication for outbound access**: requiring proxy auth before allowing internet access.

**Q12. What are the primary use cases for a reverse proxy?**
A:
- **Load balancing**: distributing incoming requests across multiple backend servers (the use case covered throughout this curriculum).
- **TLS termination**: decrypting HTTPS at the edge so backend servers handle plain HTTP, centralizing certificate management.
- **Caching**: caching responses from backend servers to reduce backend load (e.g., Varnish, NGINX caching static content).
- **Security / WAF**: filtering malicious requests (SQL injection, XSS patterns) before they reach application servers; hiding backend topology and software versions from attackers.
- **Compression**: gzip/brotli compressing responses at the proxy layer, offloading CPU work from backends.
- **Request routing**: path-based or host-based routing to different microservices (the L7 LB use case).
- **Rate limiting / DDoS mitigation**: absorbing and throttling traffic before it reaches application infrastructure.

**Q13. Is a CDN a forward proxy or a reverse proxy?**
A: A reverse proxy — from the perspective of the origin server. A CDN edge node sits in front of the origin, caching and serving content on the origin's behalf. Clients connect to the CDN edge thinking they're talking to the origin (or at least to a service the origin operates). The CDN protects and represents the origin's infrastructure — the defining characteristic of a reverse proxy, deployed geographically distributed for latency reasons.

**Q14. Is a VPN a forward proxy?**
A: Conceptually similar but technically broader. A VPN operates at the network layer (L3) and tunnels *all* traffic (not just HTTP/HTTPS) from the client through a remote endpoint, which then forwards it to the destination. A forward proxy typically operates at L4/L7 and is protocol-specific (HTTP proxies handle HTTP/HTTPS only). Both hide the client's origin IP from the destination, which is why they're often discussed together — but a VPN is a more general-purpose network tunnel, while a forward proxy is usually an application-layer intermediary for specific protocols.

**Q15. How does API Gateway relate to reverse proxy?**
A: An API Gateway is a specialized, feature-rich reverse proxy — it adds product-layer capabilities (authentication, rate limiting per API key, request/response transformation, API versioning, developer portal, billing/metering) on top of the core reverse proxy mechanics (routing, TLS termination). Every API Gateway is architecturally a reverse proxy; not every reverse proxy is a full API Gateway. The distinction matters for interview answers about Kong, Apigee, AWS API Gateway — they're reverse proxies with extra policy enforcement.

## Section 4: Security Implications

**Q16. How does a reverse proxy improve security?**
A:
- **Hides backend topology**: attackers see only the reverse proxy's IP/hostname — they don't know how many backend servers exist, their IPs, OS, or software stack.
- **Centralizes TLS**: certificates are managed in one place rather than on every backend, reducing the surface for misconfiguration.
- **Single point for WAF rules**: SQL injection, XSS, and other attack patterns can be filtered before reaching application code.
- **Backend isolation**: backend servers can be placed on a private network with no direct internet route — only reachable via the reverse proxy. This means even an exploited application bug can't be reached directly from the internet.
- **DDoS absorption**: a reverse proxy fleet (or upstream CDN) absorbs volumetric attacks before they reach origin infrastructure.

**Q17. How does a forward proxy improve security?**
A:
- **Outbound content filtering**: blocks employees from accessing malicious or policy-violating sites, reducing malware/phishing exposure.
- **Centralized monitoring**: security teams can audit all outbound traffic from one chokepoint rather than monitoring every individual device.
- **Data loss prevention (DLP)**: inspect outbound traffic for sensitive data patterns (credit card numbers, SSNs) before they leave the network.
- **Malware scanning**: scan downloaded files for malware before they reach the client device.

**Q18. What new security risks does each type of proxy introduce?**
A:
- **Reverse proxy**: becomes a high-value single point of attack — if compromised, an attacker gains a foothold with access to route to any backend, can intercept TLS-terminated traffic in plaintext, and can serve as a pivot point into the internal network. Misconfigured reverse proxies are a common source of SSRF (server-side request forgery) and request smuggling vulnerabilities.
- **Forward proxy**: if compromised or misconfigured (e.g., an "open proxy" accessible to anyone on the internet), it can be abused by attackers to anonymize malicious traffic, exfiltrate data, or pivot into the internal network from a compromised client.

**Q19. What is "HTTP request smuggling" and why is it relevant to proxies?**
A: A vulnerability that exploits inconsistencies in how a front-end proxy (reverse proxy/LB) and back-end server parse the boundaries between HTTP requests — typically arising from differing interpretations of `Content-Length` vs `Transfer-Encoding: chunked` headers. An attacker crafts a request that the proxy parses as one request but the backend parses as two, allowing them to "smuggle" a hidden second request that gets processed in the context of the next legitimate user's connection (potentially stealing session data or bypassing security controls). This is specifically a reverse proxy / L7 load balancer concern because it depends on having two layers (proxy + backend) parsing the same HTTP stream differently. Mitigation: use HTTP/2 end-to-end (less ambiguity), ensure proxy and backend use the same parsing library/behavior, and reject ambiguous requests outright (most modern proxies like Envoy and NGINX have hardened against known smuggling patterns).

**Q20. What is SSRF and how does it relate to reverse proxies?**
A: Server-Side Request Forgery is when an attacker tricks a server into making requests to unintended destinations — often internal services not meant to be reachable from outside (e.g., cloud metadata endpoints like `169.254.169.254`). Reverse proxies that forward user-supplied URLs (e.g., a webhook configuration feature, an image-fetching proxy) are common SSRF vectors if they don't validate/restrict destination addresses. Mitigation: maintain an allowlist of permitted destination hosts, block requests to private IP ranges (RFC 1918) and link-local addresses, and use a dedicated egress proxy with strict policy for any "fetch a URL on behalf of a user" feature.

## Section 5: Header Handling and Client IP Preservation

**Q21. What is the `X-Forwarded-For` header and why does it exist?**
A: When a proxy (forward or reverse) forwards a request, the backend/destination sees the proxy's IP as the connection source — the original client's IP is lost unless explicitly preserved. `X-Forwarded-For` (XFF) is a de facto standard header that proxies add to carry the original client IP forward:

```
X-Forwarded-For: client_ip, proxy1_ip, proxy2_ip
```

Each proxy in the chain appends its own seen source IP, creating an audit trail. The backend reads the first entry (or the entry from a trusted hop count back) to recover the true client IP, important for rate limiting, geolocation, logging, and IP-based security rules.

**Q22. Why can't you trust `X-Forwarded-For` blindly?**
A: Because it's just a regular HTTP header — any client can set it to an arbitrary value before the request reaches your first trusted proxy:

```
X-Forwarded-For: 1.2.3.4   <- attacker-supplied, fake IP
```

If your application reads the first value in XFF without validation, an attacker can spoof their apparent IP — bypassing IP-based rate limiting, geofencing, or allowlists. The correct approach: only trust XFF entries appended by proxies you control. Strip/ignore any client-supplied XFF value at your edge (the first trusted hop), and only append from there. Most reverse proxies (NGINX, Envoy, ALB) have a "trusted proxy" configuration that handles this correctly by default.

**Q23. What is `Forwarded` (RFC 7239) and how does it differ from `X-Forwarded-For`?**
A: `Forwarded` is the standardized header (RFC 7239, 2014) intended to replace the ad-hoc `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host` family with a single structured header:

```
Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43
```

It includes `for` (client), `by` (the proxy itself), `proto` (original protocol), and `host`. Despite being the official standard, adoption is mixed — `X-Forwarded-For` remains far more widely used in practice due to legacy inertia, broader library/tooling support, and simplicity. Most modern systems support both for compatibility.

**Q24. What is the `X-Real-IP` header and how does it differ from `X-Forwarded-For`?**
A: `X-Real-IP` carries only a single IP — the original client's IP as seen by the immediate proxy — without the full chain history that XFF accumulates. It's simpler to parse (no comma-separated list, no need to figure out which hop to trust) but loses the audit trail of intermediate proxies. NGINX's `ngx_http_realip_module` uses this pattern; many applications prefer `X-Real-IP` for simplicity when there's only one trusted reverse proxy hop.

**Q25. How does TLS termination at a reverse proxy affect end-to-end encryption, and how do you communicate the original protocol to the backend?**
A: When a reverse proxy terminates TLS, the connection from proxy to backend is often plain HTTP (unless re-encrypted). The backend needs to know the original request was HTTPS — for generating correct redirect URLs, setting `Secure` cookies, and security logic that depends on scheme. The `X-Forwarded-Proto` header communicates this:

```
X-Forwarded-Proto: https
```

The backend application framework reads this header to behave as if it received an HTTPS request directly, even though the actual proxy-to-backend hop was plain HTTP. Misconfiguring this is a common bug source — infinite redirect loops occur when an app keeps redirecting HTTP→HTTPS because it doesn't trust `X-Forwarded-Proto` from the reverse proxy.

## Section 6: Technology and Implementation

**Q26. What technologies are commonly used to build forward proxies?**
A:
- **Squid**: the most widely deployed open-source forward proxy, especially for corporate content filtering and caching.
- **NGINX**: can act as a forward proxy with `proxy_pass` and appropriate configuration, though it's more commonly deployed as a reverse proxy.
- **Privoxy**: privacy-focused forward proxy with ad/tracker filtering.
- **Cloud NAT Gateway / egress proxies**: AWS NAT Gateway, GCP Cloud NAT — function as forward proxies for outbound traffic from private subnets (more L3/L4 than L7, but conceptually a forward proxy for internet egress).
- **Corporate secure web gateways**: Zscaler, Netskope — modern SaaS-delivered forward proxy/CASB platforms.

**Q27. What technologies are commonly used to build reverse proxies?**
A:
- **NGINX**: the most widely used open-source reverse proxy/web server, excellent for static content, TLS termination, and L7 routing.
- **Envoy**: cloud-native L7 proxy, the data plane standard for service meshes (Istio), strong observability and dynamic configuration via xDS.
- **HAProxy**: high-performance, both L4 and L7 capable, historically strong in performance-critical environments.
- **Traefik**: cloud-native reverse proxy with automatic service discovery, popular in Kubernetes/Docker environments.
- **Cloud-managed**: AWS ALB/CloudFront, GCP Load Balancer, Azure Application Gateway — managed reverse proxy services.
- **Apache HTTP Server (mod_proxy)**: older but still widely deployed, especially in legacy environments.

**Q28. How do you configure NGINX as a forward proxy vs a reverse proxy?**

Reverse proxy (most common NGINX use case):
```nginx
server {
    listen 443 ssl;
    server_name api.example.com;
    location / {
        proxy_pass http://backend_pool;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
Here, NGINX is the destination from the client's perspective, fronting an upstream pool.

Forward proxy (less common, requires explicit proxy directives):
```nginx
server {
    listen 8888;
    resolver 8.8.8.8;
    location / {
        proxy_pass http://$http_host$request_uri;
        proxy_set_header Host $http_host;
    }
}
```
Here, clients explicitly configure their browser/system to send requests to this NGINX instance on port 8888 as their proxy, and NGINX forwards to whatever destination the client requested.

**Q29. How does an explicit HTTPS forward proxy handle encrypted traffic if it can't read inside TLS?**
A: Via the `CONNECT` method. When a client wants to reach `https://example.com` through a forward proxy, it doesn't ask the proxy to fetch the page directly (that would require the proxy to terminate TLS and re-encrypt, which most setups avoid for end-to-end encryption reasons). Instead:
1. Client sends `CONNECT example.com:443 HTTP/1.1` to the proxy.
2. Proxy establishes a raw TCP tunnel to `example.com:443`.
3. Proxy responds `200 Connection Established`.
4. From this point, the proxy just relays encrypted bytes — it's now acting as a pure TCP tunnel (essentially L4), blind to the TLS contents inside.

This means a standard forward proxy can route HTTPS traffic without decrypting it, preserving end-to-end encryption between client and destination — at the cost of the proxy being unable to apply content-based filtering (URL path, content inspection) to the encrypted payload, only the destination host:port from the CONNECT request.

**Q30. How do corporate forward proxies inspect HTTPS traffic despite the CONNECT tunnel limitation?**
A: Via "TLS interception" (also called "SSL inspection" or, less charitably, a man-in-the-middle): the proxy terminates the client's TLS connection using a corporate-issued root CA certificate pre-installed on managed devices, inspects the decrypted traffic, then re-encrypts and forwards to the real destination using its own TLS connection. The client's browser trusts the corporate CA, so it doesn't flag the swapped certificate as suspicious. This is controversial — it breaks end-to-end encryption and requires careful CA key management, but is common in enterprise security tooling (Zscaler, Netskope, Palo Alto) for content inspection and DLP on encrypted traffic.

## Section 7: Caching Behavior

**Q31. How does caching differ between a forward proxy and a reverse proxy?**
A:
- **Forward proxy caching**: caches responses from *many different destination servers* on behalf of *many clients behind it*. Useful when many users in an organization request the same external resource (e.g., a popular CDN-hosted library, an OS update). The cache key is essentially the requested URL; cache hit rate depends on how often different clients request the same external content.
- **Reverse proxy caching**: caches responses from a *small set of known backend servers* on behalf of *many external clients*. Useful for reducing backend load — e.g., caching a product page that thousands of users view. The reverse proxy operator controls cache invalidation precisely because they control the origin.

**Q32. Why is reverse proxy caching generally more effective and predictable than forward proxy caching?**
A: Because the reverse proxy operator controls both sides — they know exactly what content changes, when, and can set precise cache-control headers, purge caches on deployment, and use cache keys that match their application's data model. A forward proxy caches arbitrary third-party content it has no control over — it must obey whatever `Cache-Control` headers those origins provide, can't proactively invalidate when origin content changes (no visibility), and faces more cache-poisoning risk from untrusted destinations.

**Q33. What is "cache poisoning" and how does it threaten reverse proxy caches specifically?**
A: An attack where a malicious or malformed response gets cached and served to subsequent legitimate users. For reverse proxies, a common vector is header-based cache key manipulation — e.g., if the cache key includes a header that's attacker-controllable (like `X-Forwarded-Host`), an attacker can craft a request that causes a malicious response (e.g., a redirect to a phishing site) to be cached and served to all subsequent users requesting that same cache key. Mitigation: carefully control which request attributes contribute to the cache key, validate/sanitize headers used in cache key generation, and use a well-audited caching layer (Varnish, NGINX, CDN) rather than rolling your own.

## Section 8: Comparison Table and Scenario Questions

**Q34. Full comparison: Forward Proxy vs Reverse Proxy.**
A:

| Dimension | Forward Proxy | Reverse Proxy |
|---|---|---|
| Represents | The client | The server/origin |
| Configured by | Client (or client's network admin) | Server operator |
| Client awareness | Often explicit (browser config) or transparent | Always transparent — client thinks it IS the server |
| Server awareness | Server may not know a proxy is involved | Server (backend) is configured for it |
| Hides identity of | Client (from server) | Server/backend topology (from client) |
| Primary goals | Filtering, privacy, monitoring, outbound caching | Load balancing, TLS termination, security, inbound caching |
| Typical deployment | Corporate network edge, egress gateway | Data center / cloud ingress, in front of app servers |
| Example tech | Squid, Zscaler, NAT Gateway | NGINX, Envoy, ALB, CloudFront |
| Number of destinations | Many (any internet destination) | Few (known, fixed backend pool) |
| Number of sources | Few (known client population, e.g., one company) | Many (any internet client) |

**Q35. "Your company wants to block employees from accessing social media during work hours. Forward or reverse proxy?"**
A: Forward proxy. The goal is controlling outbound traffic from a known set of internal clients (employees) to arbitrary external destinations. Deploy a forward proxy (or a secure web gateway like Zscaler) at the network egress, configure devices to route all traffic through it, and apply category-based URL filtering rules.

**Q36. "Your application has 20 backend instances and you want clients to access it via a single domain with load balancing and TLS termination. Forward or reverse proxy?"**
A: Reverse proxy. The goal is fronting a known set of backend servers, presenting a single entry point to external clients, distributing load, and centralizing TLS. This is the textbook reverse proxy / load balancer use case — NGINX, Envoy, or a cloud ALB would be the implementation choice.

**Q37. "A security team wants to inspect all outbound HTTPS traffic from developer laptops for data exfiltration, without breaking legitimate sites. What approach would you suggest, and what's the trade-off?"**
A: A forward proxy with TLS interception (Q30) — issue a corporate root CA to managed devices, route all outbound traffic through the forward proxy, and have it terminate/inspect/re-encrypt HTTPS traffic. Trade-offs to flag: this breaks true end-to-end encryption (the proxy can read everything), creates a single high-value target (compromise of the proxy's CA private key would let an attacker impersonate any site to any employee), can break certificate pinning in some applications (mobile apps, some desktop clients that pin specific certs will fail), and raises legitimate employee privacy concerns that should be addressed via policy, not just technology.

**Q38. "You're building a webhook delivery system that fetches a user-supplied URL to verify it's reachable. What proxy-related security concern should you flag, and how do you mitigate it?"**
A: SSRF (Q20) — a malicious user could supply a URL pointing to an internal service (e.g., `http://169.254.169.254/latest/meta-data/` for cloud instance metadata, or `http://localhost:6379` for an internal Redis instance) and trick your server into making a request to it, potentially exposing secrets or enabling further attacks. Mitigation: route the outbound fetch through a dedicated egress proxy with strict allowlisting (block RFC 1918 private ranges, link-local addresses, and cloud metadata IPs), validate the resolved IP (not just the hostname, since DNS can be manipulated after validation — "TOCTOU" via DNS rebinding), and consider using a separate network namespace/VPC for this outbound fetch capability with no route to internal services.

**Q39. "Your reverse proxy fleet terminates TLS and forwards plain HTTP to backends on a private network. A new compliance requirement mandates encryption in transit everywhere, including internal hops. What do you change?"**
A: Move from TLS termination to TLS re-encryption (sometimes called "TLS bridging"): the reverse proxy still terminates the client's TLS connection (to apply L7 routing logic, inspect headers, etc.), but instead of forwarding plain HTTP to the backend, it opens a new TLS connection to the backend using internal certificates (often from an internal/private CA, or mutual TLS via a service mesh like Istio's automatic mTLS between sidecars). This satisfies "encrypted everywhere" while still allowing the proxy to do L7 work that requires decrypted visibility. The alternative — full TLS passthrough (Q5 from the L4/L7 guide) — would prevent the reverse proxy from doing L7 routing at all, so it's not compatible with most reverse proxy use cases that need to inspect HTTP.

**Q40. "How would you explain to a junior engineer, in one sentence each, the difference between a forward and reverse proxy, using a real-world analogy?"**
A: Forward proxy is like a personal assistant who makes phone calls on your behalf and the person on the other end only sees the assistant's number — useful for screening and control over your outbound calls. Reverse proxy is like a company's front receptionist who answers all incoming calls and routes them to the right department internally — callers never get a direct line to any specific employee, only to reception. The "I'm hiding the caller" vs "I'm hiding the destination/internal-structure" framing usually clicks immediately for junior engineers.

## Quick Reference Table

| Feature | Forward Proxy | Reverse Proxy |
|---|---|---|
| Sits in front of | Clients | Servers |
| Hides | Client from server | Server topology from client |
| Configured by | Client / client network | Server operator |
| TLS handling | CONNECT tunnel (passthrough) or TLS interception | TLS termination (or re-encryption) |
| Common headers | Adds `X-Forwarded-For` outbound | Adds `X-Forwarded-For`/`Proto` inbound |
| Caching benefit | Many clients, many destinations | Few backends, many clients |
| Security focus | Outbound filtering, DLP, privacy | Inbound WAF, DDoS, backend isolation |
| Example | Corporate web gateway, Squid | NGINX/Envoy/ALB in front of microservices |
| Key vulnerability | Open proxy abuse, TLS interception risk | SSRF, request smuggling, cache poisoning |

---

**Tip for interviews:** Three things separate strong candidates here: (1) immediately framing the distinction as "whose traffic/identity is being protected" rather than reciting definitions — interviewers want the mental model, not memorized text; (2) knowing the `CONNECT` method mechanics (Q29) for how forward proxies handle HTTPS without decrypting it, and the TLS interception trade-off (Q30) for when they do; and (3) being able to flag SSRF (Q20/Q38) unprompted whenever a system fetches user-supplied URLs — this is one of the most common real-world security gaps interviewers probe for at the senior level.
