# API Gateway — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an API Gateway, and what problem does it solve?**
A: An API Gateway is a single, centralized entry point that sits between clients (web apps, mobile apps, third-party integrators) and a system's backend services, routing incoming requests to the appropriate service while handling a set of cross-cutting concerns — authentication, rate limiting, request/response transformation, logging, and more — in one consistent place rather than duplicated inside every individual backend service. It solves the problem of **clients needing to know about and individually call many backend services directly**: without a gateway, every client has to know each service's address, handle auth against each one separately, and absorb the complexity of a system that may be internally composed of dozens of independently deployed services — the gateway collapses all of that into one coherent, stable surface.

**Q2. Why is a gateway particularly important in a microservices architecture specifically?**
A: As a system decomposes into many independently deployable services, the number of things a client would otherwise need to know about (addresses, auth schemes, versioning, internal service boundaries) grows with the number of services — and worse, internal restructuring (splitting a service, merging two services, moving a capability from one service to another) would otherwise directly break clients who'd hardcoded knowledge of the old internal topology. A gateway decouples the client-facing API surface from the internal service topology entirely: clients only ever interact with the gateway's stable, versioned API, while the actual backend composition behind it can change freely without clients needing to know or care.

**Q3. What are the core responsibilities typically handled by an API Gateway?**
A: Request routing (directing each incoming request to the correct backend service, often based on path, host, or header matching); authentication and authorization (validating credentials/tokens before a request is allowed through, so backend services don't each need to reimplement this); rate limiting and throttling (protecting backend services from being overwhelmed, and enforcing per-client usage limits); request/response transformation (adapting between what the client sends/expects and what the backend service actually provides — format conversion, header manipulation, sometimes protocol translation); aggregation/composition (combining responses from multiple backend services into a single client-facing response); caching (serving repeated identical requests from a cache rather than hitting backend services every time); and observability (centralized logging, metrics, and tracing for all traffic passing through, since it's a natural chokepoint for visibility).

**Q4. What is the difference between an API Gateway and a simple reverse proxy?**
A: A reverse proxy's core job is narrower: receive a request, forward it to the appropriate backend, and return the response — essentially routing and basic request relaying, sometimes with TLS termination and simple load balancing layered in. An API Gateway is a superset of that, purpose-built specifically for *API* traffic, adding API-specific concerns a generic reverse proxy typically doesn't handle out of the box: structured authentication/authorization schemes (OAuth, JWT validation, API keys), fine-grained per-client/per-route rate limiting, request/response transformation logic, API versioning support, and often a developer-facing layer (API key management, usage analytics, sometimes a developer portal). In practice, many API Gateway products are literally built as a reverse proxy with these additional API-specific layers added on top — the line is more about scope of responsibility than a fundamentally different underlying mechanism.

**Q5. How does an API Gateway differ from a load balancer?**
A: A load balancer's core job is distributing traffic across multiple instances of typically the *same* backend service, optimizing for even distribution and backend health — it generally doesn't care about the content or semantics of the request. An API Gateway typically routes *different* requests to *different* backend services entirely, based on the request's actual content (path, method, headers) — its core job is correctly directing heterogeneous traffic to the right destination, layered with API-specific cross-cutting concerns. In practice, a gateway commonly sits in front of multiple backend services, each of which may itself be fronted by its own load balancer — the two are complementary layers, not competing alternatives, with the gateway handling "which service" and the load balancer handling "which instance of that service."

## Section 2: API Gateway vs Related Architectural Patterns

**Q6. How does an API Gateway relate to, and differ from, a service mesh?**
A: An API Gateway sits at the **edge** of the system, handling **north-south traffic** — requests coming in from external clients to the system as a whole. A service mesh (Istio, Linkerd) handles **east-west traffic** — communication *between* internal services, typically via a sidecar proxy deployed alongside each service instance, handling concerns like service-to-service authentication (mTLS), retries, circuit breaking, and traffic shaping for internal calls. They're complementary, not competing: a request might enter through the gateway (north-south), get routed to a service, and that service's subsequent calls to other internal services would then be handled by the mesh (east-west) — both layers can implement similar-sounding concerns (auth, rate limiting, retries) but at different points in the request's overall journey through the system.

**Q7. What is a "Backend for Frontend" (BFF) pattern, and how does it relate to API Gateways?**
A: A BFF is a thin, purpose-built API layer tailored specifically to one particular client type's needs (a mobile app's BFF, a web app's BFF), each shaping and aggregating backend service responses exactly the way that specific client wants them, rather than exposing one generic API that every client type has to adapt to on their own. It's often implemented either as a distinct service sitting behind a shared API Gateway, or as gateway-level routing/transformation logic split per client type within the gateway itself — some API Gateway products support enough request transformation and composition capability to implement BFF-style logic directly in the gateway configuration, while more complex BFF logic is often pulled out into dedicated BFF services that the gateway simply routes to.

**Q8. Can an API Gateway and an Ingress controller (in a Kubernetes context) be the same thing?**
A: They overlap significantly but aren't strictly identical in scope. A Kubernetes Ingress controller's core, baseline job is routing external HTTP(S) traffic into the cluster based on host/path rules to the correct internal Service — a relatively narrow, infrastructure-level routing concern. Many API Gateway products can *also* function as an Ingress controller (several are explicitly designed to, implementing the Kubernetes Ingress or Gateway API spec) while additionally providing the richer API-specific feature set (auth, rate limiting, transformation) beyond what a minimal/default Ingress controller offers. So in practice: every API-Gateway-as-Ingress-controller is also functioning as an Ingress controller, but not every Ingress controller has full API Gateway capabilities — it depends on which specific product/controller is deployed.

## Section 3: Authentication and Authorization at the Gateway

**Q9. Why is the gateway a natural place to centralize authentication, rather than each backend service implementing it independently?**
A: Centralizing auth at the gateway means the logic for validating credentials (checking a JWT's signature and expiry, verifying an API key, handling an OAuth token introspection call) exists and is maintained in exactly one place, rather than being reimplemented — and potentially implemented inconsistently or with bugs — across every individual backend service. It also means unauthenticated/invalid requests are rejected at the very edge of the system, before consuming any backend compute resources at all, and backend services can be simplified to trust that anything reaching them has already passed authentication, rather than each one independently re-validating raw credentials.

**Q10. What's a common pattern for how the gateway communicates "this request is authenticated, here's who it is" to downstream backend services?**
A: After validating the original credential (a JWT, an API key, etc.), the gateway commonly extracts the relevant identity/claims information and forwards it to backend services via internal headers (e.g., `X-User-Id`, `X-User-Roles`) on the proxied request, rather than forwarding the original raw credential further downstream unchanged. Backend services then trust those headers as already-validated, rather than re-validating the original token themselves — which only works correctly if the network path between the gateway and backend services is itself trusted/private (otherwise a malicious actor with access to that internal network could forge those headers directly, bypassing the gateway's auth entirely — a real risk worth being precise about).

**Q11. What's the distinction between authentication and authorization, and which is more commonly handled at the gateway versus deeper in the system?**
A: Authentication answers "who is making this request" (validating identity via a credential); authorization answers "is this identity allowed to do this specific thing." Authentication is very commonly centralized at the gateway, since it's a relatively uniform check (validate the token, extract identity) that applies the same way regardless of what's being requested. Authorization is more often split: coarse-grained authorization (does this client have access to this API/route at all) is frequently handled at the gateway, while fine-grained, resource-specific authorization (can this specific user modify this specific record they don't own) typically requires business-logic context the gateway doesn't have, and is more commonly left to the backend service itself, which actually understands the resource being accessed.

**Q12. What are common authentication mechanisms an API Gateway is expected to support?**
A: API keys (a simple, static credential identifying a client/application, often used for service-to-service or third-party integrator access); JWT (JSON Web Token) validation (verifying a token's cryptographic signature and standard claims like expiry, often issued by a separate identity provider/auth service, with the gateway validating rather than issuing them); OAuth 2.0 flows (the gateway may handle token introspection against an authorization server, or validate self-contained tokens depending on the OAuth flow in use); and mutual TLS (mTLS) for especially sensitive service-to-service or partner integrations, where both client and server present certificates to authenticate each other.

## Section 4: Rate Limiting and Traffic Control

**Q13. Why is rate limiting commonly implemented at the gateway rather than within individual backend services?**
A: It protects the entire system, not just one service, from being overwhelmed — by rejecting excess requests at the very edge, before they consume any backend compute, network, or database capacity at all. It's also far simpler to implement and reason about once, centrally, with a consistent policy and consistent client-facing behavior (consistent error responses, consistent headers communicating remaining quota), rather than each backend service independently tracking and enforcing its own rate limits with potentially inconsistent logic and inconsistent client-facing semantics.

**Q14. What are common dimensions along which rate limiting is applied at a gateway?**
A: Per-API-key/per-client (each registered client or API consumer gets their own quota, common for third-party integrator APIs); per-IP-address (a coarser fallback, useful when client identity isn't yet established, or as DDoS-style protection against any single source); per-route/per-endpoint (some endpoints — especially expensive ones, like search or report generation — may warrant tighter limits than simple read endpoints); and globally (an overall ceiling on total throughput the backend system can absorb, regardless of how it's distributed across individual clients).

**Q15. What's the difference between rate limiting and throttling, as the terms are sometimes distinguished?**
A: The terms are often used interchangeably in casual conversation, but a useful distinction: rate limiting typically refers to outright **rejecting** requests once a quota is exceeded (returning an error, commonly HTTP 429 Too Many Requests); throttling more specifically refers to **slowing down** or queuing/delaying requests to bring the effective rate within an acceptable bound, rather than rejecting them outright. Some gateways support both behaviors as distinct configurable policies — reject immediately past a hard limit, versus smooth out bursts via queuing/delay up to a softer limit.

**Q16. What HTTP status code and headers are conventionally used to communicate rate limiting to clients, and why does this matter?**
A: HTTP 429 (Too Many Requests) is the conventional status code for a rejected, over-limit request. Commonly paired with headers like `Retry-After` (telling the client how long to wait before retrying) and informational headers like `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (communicating the client's current quota state proactively, so well-behaved clients can self-regulate before even hitting the limit). This matters because well-designed rate limiting isn't just about protection — it's also about giving API consumers enough information to build correctly-behaved, considerate clients, rather than leaving them to discover limits purely through trial-and-error rejection.

## Section 5: Request/Response Transformation and Aggregation

**Q17. What is request/response transformation at the gateway, and why might it be needed?**
A: The gateway modifying the shape, format, or content of a request before forwarding it to a backend service, or modifying a backend's response before returning it to the client — examples include translating between a client-facing REST API and a backend that internally speaks gRPC or SOAP, renaming/reshaping fields to maintain a stable public API contract even as an internal service's actual schema evolves, stripping internal-only fields from a response before it reaches external clients, or adding/removing headers as requests cross the public/internal boundary. It lets the gateway maintain a stable, well-designed public contract independent of how a given backend service happens to be implemented internally.

**Q18. What is response aggregation/composition at the gateway, and what's a concrete example?**
A: The gateway making calls to multiple backend services to fulfill what the client experiences as a single request, then combining those multiple backend responses into one unified response before returning it. A concrete example: a mobile app's "product details" screen might need data from a product-catalog service, a pricing service, and a reviews service — rather than requiring the mobile client to make three separate calls and assemble the result itself (more round trips, more client-side complexity), the gateway (or a BFF layer behind it, per Q7) makes all three backend calls and returns one composed response tailored to exactly what that screen needs.

**Q19. What's a risk or trade-off with putting significant aggregation/composition logic into the gateway layer?**
A: The gateway can start accumulating real business logic — decisions about how to combine, prioritize, or reconcile data from multiple services — which blurs the line between "infrastructure cross-cutting concern" (appropriate for a gateway) and "application logic" (which arguably belongs in a dedicated service, not a shared piece of edge infrastructure that every team's traffic passes through). Heavy aggregation logic in the gateway can also become a deployment bottleneck (changes to that logic require touching the shared gateway, potentially needing coordination across teams) and a reliability risk (a bug in gateway-level composition logic has blast radius across everything routed through that gateway, rather than being contained to one service). This is part of why heavier composition needs are often pulled into dedicated BFF services instead, leaving the shared gateway focused on more genuinely cross-cutting concerns.

## Section 6: Resilience Patterns at the Gateway

**Q20. What is a circuit breaker pattern, and why is it often implemented at the gateway level?**
A: A circuit breaker tracks the failure rate of calls to a given backend service and, once failures exceed a threshold, "opens" — stops sending further requests to that backend for a cooldown period (returning a fast failure or fallback response instead) rather than continuing to send requests that are very likely to fail or time out. Implementing it at the gateway means this protection is applied consistently across all traffic to a struggling backend, and crucially, **protects the struggling backend from being further overwhelmed** by continued traffic while it's already failing — sending more requests at a backend that's already failing can make recovery harder, not easier, so cutting off that traffic quickly is itself a form of help to the failing service, not just protection for the caller.

**Q21. What is the relationship between timeouts, retries, and circuit breaking at the gateway, and why do they need to be configured together thoughtfully?**
A: Timeouts bound how long the gateway waits for a backend response before giving up; retries determine whether and how many times a failed/timed-out request is attempted again; circuit breaking determines whether to stop sending requests to a backend altogether after sustained failures. These need to be tuned together because naive configuration can compound problems: aggressive retries without circuit breaking can actually amplify load on an already-struggling backend (each failed request gets multiplied by the retry count, right when the backend is least able to handle more load); timeouts set too long mean the gateway (and the client waiting on it) holds resources/connections open longer than necessary during a backend slowdown; and circuit breaking without sensible retry/timeout settings underneath it can trip prematurely or too late depending on how those other settings shape the failure signal it's reacting to.

**Q22. What is gateway-level response caching, and what are its trade-offs?**
A: The gateway storing and serving responses for repeated, identical requests (matched by URL, method, and sometimes specific headers) without forwarding them to the backend service again, typically for read-heavy, relatively static or slow-changing data. The upside: reduced backend load and faster response times for cached requests. The trade-offs mirror general caching trade-offs (similar in spirit to DNS TTL trade-offs): how long to cache (a longer cache duration reduces backend load further but risks serving stale data after the underlying data changes), what's safe to cache at all (responses containing user-specific or sensitive data generally shouldn't be cached at a shared gateway layer without careful per-user cache key scoping), and cache invalidation complexity when underlying data changes before the cache would naturally expire.

## Section 7: Operational and Observability Considerations

**Q23. Why is the gateway a particularly natural place to centralize observability (logging, metrics, tracing)?**
A: Because it's a genuine chokepoint — essentially all external traffic to the system passes through it, making it a single, consistent place to capture request/response logs, latency metrics, error rates, and the starting point of distributed traces, without needing every individual backend service to independently implement the same instrumentation for traffic entering the system. It's especially valuable for system-wide visibility (overall request volume, overall error rate, which routes/clients are generating the most traffic) that would otherwise require aggregating data from many independently-instrumented services.

**Q24. What's a risk of relying solely on gateway-level observability, without per-service observability behind it?**
A: The gateway can tell you a request came in and (eventually) what response went out, and roughly how long the whole round trip took — but it generally can't tell you *where inside the backend system* time was spent, or which specific internal service or downstream call was the actual root cause of a slow or failed request, if the gateway's request fanned out to multiple internal services (Q18) or if the directly-called service itself called further downstream services. Genuinely useful root-cause diagnosis requires distributed tracing that follows a request through every internal hop, not just the gateway's edge-level view — gateway-level observability is necessary but not sufficient for deep operational visibility into a multi-service backend.

**Q25. Why is the gateway often described as a single point of failure, and how is that risk typically mitigated?**
A: Since essentially all client traffic passes through it, an outage or severe degradation at the gateway layer can take down access to the entire system, even if every individual backend service behind it is perfectly healthy. This is mitigated the same way any critical infrastructure component's single-point-of-failure risk is mitigated generally: running multiple gateway instances behind a load balancer (rather than a single instance), deploying across multiple availability zones/regions for resilience against a localized infrastructure failure, ensuring the gateway layer itself is stateless (or has externalized state) so instances are interchangeable and can be scaled horizontally, and load/capacity testing the gateway layer specifically, since it needs to handle the *sum* of all traffic to every backend service behind it, not just the load any individual service experiences.

**Q26. What's a common operational pitfall when introducing a new API Gateway into an existing system that didn't previously have one?**
A: Underestimating how much additional latency, complexity, and operational surface area the gateway itself introduces — every request now has an extra hop (and, if the gateway does meaningful auth/transformation/aggregation work, extra processing time) before reaching the actual backend, and the gateway becomes a new piece of critical infrastructure that needs its own monitoring, capacity planning, and on-call ownership. A related pitfall: migrating all traffic through the new gateway in one cutover rather than incrementally (route-by-route or client-by-client), which makes it harder to isolate gateway-introduced issues from pre-existing backend issues during the transition, and concentrates migration risk into a single high-stakes event rather than spreading it across smaller, individually-verifiable steps.

## Section 8: Scenario-Based Questions

**Q27. "Your team is introducing an API Gateway in front of an existing set of microservices that currently each handle their own authentication independently. How would you approach the migration?"**
A: Migrate incrementally rather than as a single cutover: start by deploying the gateway in front of a small, low-risk subset of services (or even just a subset of routes), with the gateway initially passing auth straight through unchanged (or running auth in both places temporarily) rather than immediately becoming the sole point of auth enforcement — validating that routing, latency, and observability through the gateway behave as expected before relying on it for anything security-critical. Once confidence is established, progressively centralize auth validation at the gateway (per Q9–10) and correspondingly simplify backend services to trust the gateway-forwarded identity headers, service by service, rather than flipping the entire system's auth model in one coordinated, high-risk event. Throughout, ensure the network path between gateway and backend services is genuinely trusted/private, since backend services trusting forwarded identity headers (Q10) is only safe if that internal path can't be reached directly, bypassing the gateway.

**Q28. "A specific backend service behind your gateway has started timing out intermittently under load, and you're seeing cascading slowness across unrelated routes that don't even call that service. How would you investigate and what gateway-level mitigation would you apply?"**
A: The cross-route cascading symptom strongly suggests a shared-resource exhaustion problem at the gateway itself — most commonly, a shared connection pool or shared worker/thread pool being consumed by the slow backend's requests, starving capacity for unrelated requests that have nothing to do with that backend. Investigate whether the gateway's connection/concurrency limits are properly isolated per-backend (so one struggling backend can't starve capacity meant for others) rather than pooled globally. The direct mitigation: apply a circuit breaker (Q20) and a sensible timeout specifically scoped to that backend, so requests to it fail fast once it's clearly struggling rather than holding gateway-level resources open and starving everything else; if available, also configure per-backend connection/concurrency isolation (sometimes called bulkheading) so that even before the circuit trips, that one backend's slowness is contained rather than able to bleed into unrelated traffic.

**Q29. "Product wants the mobile app's home screen to load faster by reducing the number of round trips it currently makes to five separate backend services. How might the gateway help, and what would you watch out for?"**
A: This is a textbook case for response aggregation (Q18) — the gateway (or a dedicated BFF layer behind it, per Q7) can make the five backend calls itself and return one composed response tailored to exactly what the home screen needs, eliminating the round-trip overhead the mobile client currently pays for sequential or even parallel-but-separate calls. What to watch out for: this aggregation logic starts to look like genuine application/presentation logic (deciding how to shape and combine data specifically for one screen), which risks gateway bloat and team-coordination friction if implemented directly in the shared gateway config (Q19) — for anything beyond fairly simple composition, pulling this into a dedicated, mobile-specific BFF service that the gateway simply routes to (rather than building deep aggregation logic into the gateway itself) tends to scale better organizationally and keeps the shared gateway layer focused on genuinely cross-cutting concerns.

**Q30. "Your API Gateway is a single deployed instance, and a recent incident report flagged it as a single point of failure for the entire system, even though all individual backend services are independently highly available. How do you respond to this, and what would you change?"**
A: Agree with the underlying concern — concentrating all traffic through a single instance means its availability becomes a hard ceiling on the entire system's effective availability, regardless of how resilient anything behind it is. The fix follows the standard pattern for any critical, stateless-or-externalized-state infrastructure component: run multiple gateway instances behind a load balancer, distribute them across multiple availability zones (and regions, if the system's overall architecture already spans regions), ensure the gateway's own state (rate-limit counters, cache, session data if any) is externalized to shared infrastructure rather than held in-process so that instances are genuinely interchangeable, and specifically load/capacity test the gateway tier under realistic peak load, since it needs to absorb the combined traffic of every backend service behind it rather than any one service's individual load — a capacity profile that's easy to underestimate if the gateway was originally sized informally rather than deliberately tested.

## Quick Reference Table

| Concept | Key Idea |
|---|---|
| API Gateway | Centralized entry point handling routing + cross-cutting API concerns |
| Gateway vs reverse proxy | Gateway is a superset, adding API-specific auth/rate limiting/transformation |
| Gateway vs load balancer | Gateway routes different requests to different services; LB distributes across instances of one |
| Gateway vs service mesh | Gateway = north-south (edge); mesh = east-west (internal service-to-service) |
| BFF | Client-type-specific API layer, often behind or implemented within the gateway |
| Auth at the gateway | Centralized validation; identity forwarded via internal headers on a trusted network path |
| Rate limiting | Per-key/IP/route/global; 429 + Retry-After / X-RateLimit-* headers |
| Aggregation | Gateway/BFF combines multiple backend calls into one client response |
| Circuit breaker | Stops sending requests to a failing backend; protects both caller and backend |
| Caching | Reduces backend load; trade-off against staleness and per-user data safety |
| Single point of failure | Mitigated via multiple instances, multi-AZ, externalized state, capacity testing |

---

**Tip for interviews:** What separates strong candidates on API Gateway specifically: (1) being able to cleanly **distinguish it from a reverse proxy, a load balancer, and a service mesh** — same general "sits in the request path" shape, but genuinely different scope and responsibility for each (Q4–6); (2) understanding that **auth centralization at the gateway depends on a trusted internal network path** — forwarding identity via headers is only safe if backend services can't be reached directly, bypassing the gateway (Q10); (3) knowing that **retries, timeouts, and circuit breaking must be tuned together**, since naive retry logic without circuit breaking can amplify load on an already-struggling backend rather than protect it (Q21); (4) recognizing the **organizational/architectural trade-off of putting aggregation/business logic into the gateway** — useful for reducing round trips, but risks gateway bloat and cross-team coordination friction at scale (Q19, Q29); and (5) treating the gateway as a **genuine single point of failure requiring the same resilience discipline as any critical infrastructure** — multiple instances, multi-AZ, externalized state, and capacity testing sized to the *sum* of all backend traffic, not informally assumed (Q25, Q30).
