# Request-Response vs Fire-and-Forget vs Streaming — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals and Mental Model

**Q1. What are the three fundamental interaction models and what single question distinguishes them?**
A: The three fundamental models are request-response, fire-and-forget, and streaming. The single distinguishing question is: **how many messages flow in each direction, and does the sender wait?**

- **Request-response**: exactly one message sent, exactly one message returned. The sender waits for the reply before proceeding. The interaction has a defined start and end — the round-trip is atomic from the caller's perspective.
- **Fire-and-forget**: exactly one message sent, zero replies. The sender does not wait — it dispatches and moves on immediately. There is no response channel; the sender has no mechanism to learn whether the receiver processed the message.
- **Streaming**: one or more messages flow in one or both directions, continuously, over a persistent connection. Neither side "waits" in the blocking sense — data flows as it becomes available. The interaction has a defined start but a potentially unbounded or long-running duration.

The pattern you choose encodes assumptions about your system: request-response assumes the caller needs confirmation and the operation completes quickly; fire-and-forget assumes the caller doesn't need confirmation or can tolerate uncertainty; streaming assumes data arrives or must be sent continuously and buffering per-message round trips is unacceptable.

**Q2. What is the relationship between these three patterns and the synchronous/asynchronous distinction from the communication patterns guide?**
A: The three patterns don't map cleanly onto sync/async — it's a common misconception:
- **Request-response** is most often synchronous (caller blocks waiting for the reply) but can be asynchronous (caller dispatches, gets a correlation ID, polls or gets called back later with the result — the "async request-response" or "callback" pattern).
- **Fire-and-forget** is always asynchronous by definition — there is no reply to wait for.
- **Streaming** is fundamentally asynchronous in spirit (data arrives or is sent as it becomes available) but the stream itself is a persistent synchronous channel (both sides are connected and active).

The more useful dimension for distinguishing the three is **message cardinality**: how many messages flow per interaction? 1→1 = request-response; 1→0 = fire-and-forget; N→M (where N or M > 1) = streaming. This cardinality directly determines what the sender can know about the outcome and when it can proceed.

**Q3. What is the "caller coupling spectrum" from tightest to loosest across these three patterns?**
A: From tightest to loosest coupling between sender and receiver:

**Request-response (tightest)**: the sender is blocked, actively waiting. If the receiver is slow, the sender is slow. If the receiver fails, the sender fails. The receiver must be available at the exact moment of the call. The sender knows the exact outcome immediately. Total temporal coupling.

**Streaming (middle)**: the sender and receiver must both be connected for the stream to flow, but neither blocks waiting for the other to complete a unit of work — data flows as produced/consumed. If the connection drops, both sides detect it and can reconnect. The persistence of the connection creates a form of coupling (both must be up simultaneously) but within that constraint, neither side is blocked.

**Fire-and-forget (loosest)**: the sender needs the receiver (or a durable intermediary) to be available only for the fraction of a second required to accept the message — then it's done. If the receiver processes the message 10 minutes later, the sender doesn't know or care. Temporal coupling is minimized to message handoff only.

## Section 2: Request-Response — Deep Dive

**Q4. What are the two forms of request-response — synchronous blocking and asynchronous callback — and when does each apply?**
A: Both are request-response (one request, one response with correlation), but they differ in whether the caller blocks:

**Synchronous blocking** (most common): the caller sends a request and suspends its execution thread until the response arrives. Simple to code (linear flow), easy to reason about (success/failure is immediate), but ties up a thread per in-flight request. Under high concurrency (thousands of simultaneous callers each blocking on a response), threads become the scalability bottleneck. Used in: typical HTTP API calls from web servers, database queries, RPC calls in traditional thread-per-request architectures.

**Asynchronous callback / future-based**: the caller sends a request and receives a `Future`, `Promise`, or `CompletableFuture` immediately — the thread is not blocked. The runtime notifies the caller (via callback, event loop continuation, or async/await machinery) when the response arrives. This is the model used in: Node.js async HTTP calls, Java's `CompletableFuture` chains, Python's `async/await` HTTP clients, gRPC async stubs, and reactive frameworks (Project Reactor, RxJava). Under high concurrency, a small thread pool handles thousands of in-flight requests — far more scalable than blocking.

The distinction matters for system design: a service handling 10k concurrent users each waiting on a response needs async non-blocking I/O internally (event loops, reactive streams) to avoid spawning 10k threads. The external API is still "request-response" from the caller's perspective — the implementation of that call from within the server is what's async.

**Q5. What is the async request-response pattern (also called "async query" or "request/acknowledge/poll"), and when is it the right design?**
A: When a request-response interaction takes too long for a synchronous HTTP call (more than a few seconds) but the caller still needs the result eventually, the async request-response pattern breaks it into three steps:

```
Step 1 — Submit:
  Client → POST /reports/generate { params }
  Server → 202 Accepted { "job_id": "abc123", "status_url": "/jobs/abc123" }
  (Server begins processing asynchronously; client thread is immediately free)

Step 2 — Poll (or server-push):
  Client → GET /jobs/abc123
  Server → 200 OK { "status": "processing", "progress": 45 }
  [... some time later ...]
  Client → GET /jobs/abc123
  Server → 200 OK { "status": "complete", "result_url": "/reports/abc123" }

Step 3 — Retrieve:
  Client → GET /reports/abc123
  Server → 200 OK { ...report data... }
```

The server returns HTTP `202 Accepted` immediately (acknowledging receipt, not completion), and the client polls for completion. The semantic is still "one request, one response" — the asynchrony is in the execution, not the interaction model. Used for: report generation, video transcoding, ML inference on large inputs, bulk data export, any operation where synchronous completion would take > 10 seconds.

**Q6. How do timeouts interact with request-response, and what are the specific timeout parameters that should be configured for every HTTP/gRPC client?**
A: A synchronous request-response call without a timeout will wait forever if the server is unresponsive — blocking a thread indefinitely and, at scale, exhausting all threads in a server's pool (cascading failure). Every request-response call in production must have explicit timeouts at multiple levels:

**Connection timeout**: maximum time to establish the TCP connection. If the server is unreachable (network partition, wrong IP), fail fast here rather than waiting. Typical: 1-5 seconds. Configured separately from read timeout.

**Read timeout** (also called socket timeout or response timeout): maximum time to wait for data from the server after the connection is established. If the server accepted the connection but stopped responding mid-processing, fail here. Typical: depends on the endpoint's SLA — set to the 99.9th percentile of expected processing time × 2.

**Request timeout** (overall): maximum end-to-end time for the entire request, from sending to receiving the full response. Guards against slow servers that send partial responses and then stall. Set as the outer bound when the connection + read timeout sum isn't sufficient.

**gRPC deadline**: gRPC uses "deadlines" (absolute timestamps) rather than "timeouts" (durations). The deadline propagates through the call chain — if Service A gives Service B a deadline of T=10, and B calls C with the same deadline, C automatically respects the remaining time budget without B needing to recalculate. This deadline propagation is a key gRPC operational advantage over REST, where callers must manually calculate remaining time budget when making nested calls.

**Q7. What is the difference between a timeout, a circuit breaker, and a retry, and how do they compose for request-response reliability?**
A: These three mechanisms address different failure scenarios in request-response:

**Timeout**: "if this call takes longer than N seconds, assume it failed." Protects the caller from blocking indefinitely on a slow/unresponsive downstream. Timeout alone doesn't prevent the failed call from retrying; it just bounds wait time.

**Retry**: "if this call failed, try again." Recovers from transient failures (a momentary network hiccup, a briefly-overloaded server that recovers within seconds). Retries are safe only for idempotent operations. Non-idempotent retries (creating an order, processing a payment) can cause duplicate side effects — must use idempotency keys or conditional logic to prevent this. Exponential backoff + jitter prevents retry storms from multiple callers all retrying simultaneously after a shared failure.

**Circuit breaker**: "if too many recent calls have failed, stop trying and fail fast immediately." Protects a struggling downstream service from being overwhelmed with retried calls during recovery. When the error rate exceeds a threshold (e.g., 50% of calls in the last 10 seconds failed), the circuit opens — subsequent calls fail immediately without even attempting to contact the downstream. The circuit probes after a recovery window and closes if probes succeed. Circuit breakers are system-level (shared across all threads calling a downstream), unlike per-call timeouts and retries.

**Composition**: the correct order of application from outermost to innermost is: circuit breaker (don't even try if circuit is open) → timeout (bound the attempt) → retry (retry on timeout/transient error, with backoff). Most resilience libraries (Resilience4j, Polly, Envoy's outlier detection) implement all three composably.

## Section 3: Fire-and-Forget — Deep Dive

**Q8. What guarantees does fire-and-forget make, and what guarantees does it not make that developers often incorrectly assume?**
A: **What fire-and-forget guarantees**: the sender will not wait for processing completion. It dispatches the message and returns immediately. This is the only guarantee — rapid return to the caller.

**What fire-and-forget does NOT guarantee** (common misconceptions):
- **It does NOT guarantee message delivery**: "fire-and-forget" over a raw UDP socket or an in-process queue that crashes loses the message entirely. Fire-and-forget describes the sender's behavior (no waiting), not the delivery mechanism's reliability. To get at-least-once delivery, you need a durable intermediary (Kafka, SQS) — which itself can be used in a fire-and-forget style from the sender's perspective.
- **It does NOT guarantee processing**: the message could be received but processing could fail silently. Without a response channel, the sender has no visibility.
- **It does NOT guarantee ordering**: especially with concurrent sends, messages may arrive at the receiver out of send order.
- **It does NOT eliminate side effects on failure**: if the sender fires and forgets an "update inventory" message, and that message is lost, inventory is not updated — the sender's business operation has a silent inconsistency. Fire-and-forget's simplicity is appropriate when these silent inconsistencies are acceptable, not when they're not noticed.

**Q9. What is the "best-effort delivery" pattern and what systems use it intentionally?**
A: Best-effort delivery is fire-and-forget with acknowledgment at the transport layer (TCP SYN/ACK ensures the packet arrived at the network layer) but no application-layer confirmation of receipt or processing. The sender sends and moves on; the system makes a reasonable effort to deliver but does not guarantee it. Intentional use cases:

- **Metrics and telemetry**: Prometheus scraping, StatsD UDP metrics, application logging. Dropping 0.01% of metric data points is acceptable — the aggregated trend is still meaningful. The overhead of guaranteed delivery (acknowledgments, retries) is not justified for monitoring data.
- **DNS queries** (UDP): a DNS query is sent; if no response arrives, the client retries — but the original query was fire-and-forget from the client's perspective. This is covered in the DNS guide.
- **Analytics event tracking**: sending a "user clicked button X" event to an analytics service. Dropping 0.1% of click events doesn't meaningfully distort analytics. The cost of guaranteed delivery is not justified by the value of each individual event.
- **Cache invalidation broadcast** (Redis Pub/Sub): broadcasting "invalidate cache key K" to all cache nodes. If one node misses the message, its cached value will eventually expire via TTL anyway. The missed invalidation causes brief staleness, not correctness failure.

The distinguishing question: "what happens to the business if this specific message is lost?" If the answer is "a negligible statistical blip," best-effort is appropriate. If the answer is "a user loses money or sees incorrect data," you need at-least-once delivery with a durable intermediary.

**Q10. How do you implement fire-and-forget correctly in code without the common pitfalls?**
A: Common pitfall: spawning a background thread/task for fire-and-forget work without bounded error handling, observability, or lifecycle management:

```python
# Bad: untracked, unmonitored, can silently fail
def place_order(order):
    db.save(order)
    threading.Thread(target=send_confirmation_email, args=(order,)).start()  # fire and forget
    return order.id

# Better: use a durable intermediary (message queue)
def place_order(order):
    db.save(order)
    sqs.send_message(QueueUrl=EMAIL_QUEUE, MessageBody=json.dumps(order))
    return order.id  # email is now guaranteed (at-least-once) via SQS retry
```

If a true in-process fire-and-forget is needed (for non-critical work): use a bounded thread pool executor with overflow handling, structured logging on failure, and metrics on queue depth:

```java
// Better in-process fire-and-forget: bounded, monitored, with error handling
ExecutorService executor = Executors.newFixedThreadPool(10);

void placeOrder(Order order) {
    db.save(order);
    executor.submit(() -> {
        try {
            analyticsService.trackOrder(order);  // non-critical analytics
        } catch (Exception e) {
            log.warn("Analytics tracking failed for order {}", order.id, e);
            metrics.increment("analytics.fire_and_forget.failed");
        }
    });
}
```

The worst version: `CompletableFuture.runAsync(() -> sendEmail(order))` with no exception handler — exceptions are swallowed by the default `ForkJoinPool` with no logging, no metrics, and no retry. This is one of the most common "silent failure" patterns in production Java code.

**Q11. What is the "async request-acknowledge" pattern — where fire-and-forget meets request-response — and how is it distinguished from pure fire-and-forget?**
A: The async request-acknowledge pattern (sometimes called "accepted-processing" or "async acknowledgment") is a hybrid: the sender fires a request and receives only a delivery acknowledgment (not a processing result):

```
Sender → Receiver: "process this job"
Receiver → Sender: "received and queued" (HTTP 202 Accepted)
[Receiver processes asynchronously]
[No further communication back to sender unless polling is implemented]
```

Distinguished from pure fire-and-forget: the sender receives confirmation that the message was accepted by the receiver (or queued durably). It still doesn't know whether processing succeeded, but it knows the request wasn't lost in transit. Distinguished from full async request-response (Q5): no poll/callback — the sender never learns the processing outcome unless it implements polling or subscribes to result events. Used for: webhook acknowledgment patterns ("we received your event" → HTTP 200, then process), job submission APIs where callers don't need results, notification pipelines where delivery confirmation is sufficient. The HTTP 202 Accepted response code exists specifically for this semantic.

## Section 4: Streaming — Deep Dive

**Q12. What are the four streaming patterns, and what is the correct use case for each?**
A: Streaming breaks into four patterns based on which direction data flows and how much:

**Server-side streaming** (one request, N responses): the client sends one request and the server responds with a stream of messages over time. The client reads from the stream as messages arrive. gRPC server-side streaming, Server-Sent Events (SSE), and chunked HTTP responses all implement this. Use cases: live data feeds (stock ticker subscriptions, live sports scores), streaming large query results (don't wait for all 10M rows — send them as they're read), real-time log tailing, progress updates for long-running server operations.

**Client-side streaming** (N requests, one response): the client sends a stream of messages; the server accumulates and sends one final response. Use cases: uploading a large file in chunks (the server returns a single upload result after all chunks arrive), sending a batch of events for server-side aggregation (the server returns aggregated statistics after all events are received), IoT sensor data ingestion where the device sends a stream of readings and the server returns a summary.

**Bidirectional streaming** (N requests, M responses): both client and server send streams independently and simultaneously. Use cases: real-time collaborative editing (both sides send changes as they happen), multiplayer game state synchronization, chat applications, live audio/video codecs (send encoded audio frames, receive decoded output), interactive command-and-response shells.

**Infinite/continuous streaming** (special case of bidirectional or server-side): the stream has no defined end — it runs for the lifetime of the connection. Kafka consumers, NATS subscribers, and WebSocket connections for live dashboards all model this. The stream terminates only on disconnection or explicit close, not because a logical operation is complete.

**Q13. What is HTTP chunked transfer encoding, and how does it enable streaming over standard HTTP?**
A: HTTP chunked transfer encoding (HTTP/1.1, RFC 7230) allows a server to send a response body in pieces (chunks) without knowing the total content length in advance. Each chunk is prefixed with its size in hexadecimal; a zero-length chunk signals the end of the body:

```
HTTP/1.1 200 OK
Transfer-Encoding: chunked
Content-Type: application/json

5\r\n
Hello\r\n
6\r\n
 World\r\n
0\r\n
\r\n
```

This enables streaming in scenarios where the server is generating data progressively — a database cursor reading rows and sending them as they arrive, or an LLM generating tokens and sending them word-by-word (streaming generation). The client reads the response incrementally without waiting for the complete body. HTTP/2 replaces chunked encoding with its own data framing mechanism (DATA frames), providing the same streaming semantics natively. Used in: streaming large API responses (export endpoints, search result streaming), server-sent events are built on chunked HTTP, LLM API streaming responses (OpenAI's API uses chunked JSON lines for token-by-token generation).

**Q14. What is gRPC bidirectional streaming in detail and what are the failure modes specific to long-lived streams?**
A: gRPC bidirectional streaming opens one HTTP/2 connection and exchanges HTTP/2 DATA frames in both directions simultaneously. The stream is identified by a stream ID within the HTTP/2 connection. The programming model:

```go
// Server-side: receive requests, send responses simultaneously
func (s *ChatServer) Chat(stream pb.Chat_ChatServer) error {
    for {
        msg, err := stream.Recv()  // receive from client
        if err == io.EOF { return nil }
        if err != nil { return err }

        // Process and reply (can also send without waiting for a message)
        stream.Send(&pb.ChatMessage{Content: "Echo: " + msg.Content})
    }
}
```

Failure modes specific to long-lived streams:

**Half-closed streams**: one side sends a FIN (closes its write direction) while the other is still sending. The stream is "half-closed." Applications must handle this gracefully — if the server closes its write direction, the client can still send (and vice versa). A common bug: treating "server sent EOF" as "stream is fully closed" and shutting down the client's send side prematurely.

**Head-of-line blocking in HTTP/2 multiplexing**: multiple gRPC streams share one TCP connection. If the TCP layer is congested (TCP HOL blocking), all streams slow down together. A slow stream processing large messages can starve other streams on the same connection. HTTP/3 (QUIC) eliminates this by providing stream-level independence at the transport layer.

**Keepalive and idle stream detection**: a TCP connection can survive long periods of inactivity (idle) without either side knowing the other has crashed (half-open TCP problem — the connection appears alive but data is no longer flowing to the remote peer). gRPC uses HTTP/2 PING frames (`keepalive_time` and `keepalive_timeout`) to detect dead connections and close them so applications can reconnect. Without keepalives, a crashed server may not be detected for minutes (until a TCP timeout triggers), during which the client's stream appears open but receives nothing.

**Backpressure in bidirectional streams**: HTTP/2 has a flow control mechanism (WINDOW_UPDATE frames) that limits how much data can be in-flight before the receiver must acknowledge. If the server sends faster than the client can read (or vice versa), the flow control window fills up and the sender must pause. Applications must ensure receivers process and acknowledge data fast enough to prevent flow control stalls — which manifest as send-side blocking or throughput drops.

**Q15. What is WebSocket and how does its streaming model differ from gRPC bidirectional streaming?**
A: WebSocket provides a full-duplex, frame-based, message-oriented persistent connection over a single TCP connection (upgraded from HTTP). Compared to gRPC bidirectional streaming:

| Dimension | WebSocket | gRPC Bidirectional Streaming |
|---|---|---|
| Protocol | WebSocket protocol (RFC 6455) | HTTP/2 DATA frames |
| Transport | HTTP → WebSocket upgrade, then TCP | HTTP/2 (always) |
| Message framing | WebSocket frames (text/binary) | Protobuf length-prefixed frames |
| Browser support | Native (all browsers) | Requires grpc-web proxy |
| Schema/contract | None (application defines format) | Mandatory .proto schema |
| Multiplexing | Single logical channel per connection | Multiple streams per HTTP/2 connection |
| Binary support | Yes (binary frames) | Yes (Protobuf is binary) |
| Backpressure | TCP-level only (no application-level) | HTTP/2 flow control (WINDOW_UPDATE) |

WebSocket's key advantage: native browser support without any proxy layer. gRPC streaming's key advantages: schema-enforced message types, multiplexing multiple streams per connection, and HTTP/2 flow control. The practical choice: WebSocket for browser clients needing bidirectional real-time communication; gRPC bidirectional streaming for service-to-service communication where the type safety and multiplexing benefits outweigh the infrastructure complexity.

**Q16. What is "backpressure" in streaming specifically, and how does each streaming technology handle it?**
A: Backpressure in streaming is the mechanism by which a slow receiver signals a fast sender to slow down, preventing the receiver from being overwhelmed (covered more broadly in the async guide). In streaming contexts, the stakes are higher than in queued systems: a queue can buffer unlimited messages on disk; a streaming connection has finite in-memory buffers, and exceeding them causes either message drops or the sender blocking.

**HTTP/2 flow control (gRPC streaming)**: the HTTP/2 protocol has built-in flow control at both the stream level and connection level. The receiver advertises a "receive window" (how many bytes it can accept); the sender must stop sending when the window is exhausted, waiting for `WINDOW_UPDATE` frames from the receiver. This is protocol-enforced — the sender physically cannot overflow the receiver's buffer. Implication: a slow gRPC stream receiver will cause the sender to stall at the HTTP/2 layer, which is visible as increased `stream.Send()` latency on the sending side.

**WebSocket**: TCP-level flow control only (TCP receive buffer). If the client-side WebSocket receive buffer fills (because the JavaScript event loop isn't processing messages fast enough), TCP's receive window fills, and the sender stalls at the TCP layer. No application-level backpressure signaling. The WebSocket spec has no explicit backpressure mechanism — applications must implement it manually (e.g., client sends a "ready for next message" message).

**Reactive Streams** (Java/Kotlin — RxJava, Project Reactor): explicit demand signaling (`Subscription.request(N)`) as a first-class protocol. The subscriber requests N items; the publisher sends at most N. This is the cleanest application-level backpressure model. Used in Spring WebFlux, Akka Streams, and Vert.x for internal reactive pipelines.

**Kafka consumer (streaming consumer)**: the consumer polls at its own rate — natural pull-based backpressure. The consumer controls how many records it reads per poll call (`max.poll.records`), and the Kafka broker accumulates unread records in the partition. The consumer's processing rate directly determines throughput.

## Section 5: Hybrid Patterns

**Q17. What is the "request-streaming response" pattern and where does it appear in production systems?**
A: Request-streaming response is a hybrid where the client sends one request and the server streams back many responses progressively (server-side streaming). This is distinct from full bidirectional streaming — the client sends once, then only receives. It appears most prominently in:

**LLM APIs** (OpenAI, Anthropic, Gemini): a client sends a prompt (one request) and the server streams tokens back as they're generated. The client renders each token to the user immediately rather than waiting for the full response. Without streaming, a 500-word response might take 10-15 seconds of blank waiting; with streaming, the user sees the first word within 200ms. The implementation is `Transfer-Encoding: chunked` HTTP with newline-delimited JSON ("NDJSON") or `text/event-stream` (SSE):

```
POST /v1/chat/completions
{"stream": true, ...}

Response:
data: {"choices":[{"delta":{"content":"The"}}]}
data: {"choices":[{"delta":{"content":" quick"}}]}
data: {"choices":[{"delta":{"content":" brown"}}]}
...
data: [DONE]
```

**Database result streaming**: executing a large query (`SELECT * FROM events WHERE year = 2023`) with a cursor-based result streaming interface — the database sends rows as it reads them rather than buffering all rows in memory before returning. JDBC `Statement.setFetchSize()`, PostgreSQL `ResultSet` streaming, and MongoDB cursor iteration all implement this.

**File upload APIs with progress**: the client uploads a large file in chunks (client-side streaming) and the server streams progress updates back. This is technically bidirectional but practically one large stream in each direction at different times.

**Q18. What is the "request-reply over message queue" pattern, and when is it used instead of direct request-response?**
A: Request-reply over a message queue uses asynchronous messaging to implement a logical request-response, providing durability and decoupling at the cost of complexity:

```
Client → [Request Queue] → Server
Server → [Reply Queue (per-request or per-client)] → Client

Message: {
    "correlation_id": "xyz-789",   # links request to reply
    "reply_to": "reply-queue-client-42",  # where to send the response
    "payload": {...}
}
```

The client generates a `correlation_id`, puts the request on the request queue with a `reply_to` address, then waits (or polls) on the reply queue for a message with the matching `correlation_id`. The server reads from the request queue, processes, and sends the reply to the `reply_to` address.

Use cases: when the server that processes requests may not be the same instance as the one that receives them (a processing cluster behind a queue); when the client needs durability (if it disconnects, its reply waits in the queue); when you need load balancing across processing instances without a synchronous load balancer. Implemented natively in: RabbitMQ (temporary reply queues, correlation IDs), gRPC over Kafka (less common), NATS request-reply (built-in `Inbox` mechanism). Disadvantages: complexity (correlation ID management, reply queue lifecycle, timeout handling for lost replies), latency (two queue hops instead of one direct call), and overkill when direct synchronous RPC is available.

**Q19. What is the "polling vs streaming" trade-off for real-time data delivery, and how do you choose?**
A: For delivering data updates from server to client, the choice between polling and streaming is a fundamental design decision:

**Polling** (client requests at regular intervals):
- Simple to implement (just a GET endpoint with a timestamp filter)
- Stateless server (no persistent connection)
- Client controls the refresh rate
- Inefficient: most polls return no new data ("nothing changed since last check")
- Minimum latency = poll interval (if event happens just after a poll, client waits the full interval)
- Appropriate when: data changes infrequently (hourly or daily), the client can tolerate latency equal to the poll interval, or infrastructure can't support persistent connections (very limited environments)

**Streaming / push** (server sends updates as they occur):
- Real-time: client sees updates within milliseconds of occurrence
- Efficient: no wasted requests when nothing changes
- Stateful server: must maintain a persistent connection per client (connection count scales with concurrent users — significant at large scale)
- More complex: connection management, reconnect logic, error handling for dropped connections
- Appropriate when: data changes frequently or unpredictably, minimum latency matters to users (live dashboards, chat, notifications), client count is manageable relative to server capacity

**Hybrid (long-polling)**: covered in the communication patterns guide — an intermediate option that provides push-like latency without a persistent bidirectional connection. Appropriate when streaming infrastructure isn't available.

**Scale consideration**: 100k concurrent streaming clients each maintaining an open WebSocket connection requires 100k open file descriptors and associated kernel state. At 1M concurrent connections, specialized event-loop architectures (Nginx, Node.js, netty, Vert.x) are necessary — one thread-per-connection (traditional Java servlet model) won't scale past ~10k simultaneous connections.

## Section 6: Error Handling Across Patterns

**Q20. How does error visibility and handling fundamentally differ across the three patterns?**
A: Error handling is where the three patterns diverge most sharply:

**Request-response**: errors are immediately visible to the caller — the response carries an error code, an exception is thrown, or a timeout fires. The caller can react immediately: retry, fallback, or propagate the error to the end user. Error handling is straightforward: every call site has explicit success/failure handling. Risk: callers that don't handle errors properly propagate them upward (unhandled exceptions, 500 errors surfaced to users).

**Fire-and-forget**: errors are invisible to the original sender. If a fire-and-forget message fails processing, the sender doesn't know. Error handling must be implemented entirely on the receiver's side (retries, DLQ, alerting) or via a monitoring/observability layer (error rate on the receiving service, DLQ depth alerts). The sender has no recovery path. Risk: silent failure — the system appears to work but effects are never applied, with no visible symptom on the sender side.

**Streaming**: errors may occur at different points — connection establishment failure (immediate, visible), mid-stream errors (the stream errors out; both sides receive an error event), or partial failures (some messages delivered, then the stream breaks; which messages were successfully processed?). Recovery requires tracking last-successfully-processed position to resume from the right point. The complication: in a bidirectional stream, an error on one direction doesn't automatically close the other — applications must handle half-errors explicitly.

**Q21. What is the "at-most-once vs at-least-once" tension specific to request-response with retries?**
A: Retrying a failed request-response call is safe only if the operation is idempotent. For non-idempotent operations (creating a resource, processing a payment), a retry after a timeout creates a genuine correctness problem:

```
Client → Server: POST /payments { amount: 100 }
Server: [processes payment, charges $100, prepares response]
Network: [drops the response before client receives it]
Client: [timeout fires] → retries → POST /payments { amount: 100 }
Server: [processes AGAIN, charges $100 again] → client receives response
Result: $200 charged instead of $100
```

Solutions:
1. **Idempotency keys**: the client generates a unique `Idempotency-Key: uuid-123` header on the first request. On retry, the same key is sent. The server stores `(idempotency_key → result)` and returns the cached result for a duplicate key without re-executing the operation. This is how Stripe, Twilio, and most payment APIs handle retries safely.

2. **Conditional requests (HTTP ETags/If-Match)**: for updates, include the current resource version in the request. The server only processes if the version matches — preventing a retry from overwriting changes made between the original request and the retry.

3. **Distinguish timeout from definitive failure**: a timeout means "I don't know if the server processed it" — not "the server definitely didn't process it." A retry after a timeout on a non-idempotent operation risks duplication. A retry after a definitive 5xx ("server crashed before processing") is safer for non-idempotent operations (though still not 100% certain). Applications should use `DEADLINE_EXCEEDED` (gRPC) vs `UNAVAILABLE` (gRPC) differently for retry decisions (covered in the REST/gRPC guide).

## Section 7: Performance Characteristics

**Q22. What are the latency and throughput characteristics of each pattern under load?**
A: The three patterns have fundamentally different latency profiles:

**Request-response latency components**:
```
Total latency = network round-trip time (RTT)
              + server processing time
              + serialization + deserialization (both directions)
              + queue time if server is busy (waiting for a thread)
              + connection establishment time (if not pooled)
```
P50 latency for a well-optimized internal gRPC call: 1-5ms. P99 latency is dominated by server-side queue time under load — when server threads are all busy, incoming requests queue up. The P99 degrades non-linearly as utilization approaches capacity (Little's Law: queue depth → ∞ as utilization → 1.0).

**Fire-and-forget latency from the sender's perspective**: the time to hand off the message to the intermediary (queue, network socket). For a Kafka produce: ~1-5ms from producer.send() to broker acknowledgment (with acks=1) or ~5-20ms (with acks=all for durability). The sender's observed latency is decoupled from the processing latency — the sender measures only the handoff time.

**Streaming throughput advantage over repeated request-response**: for high-frequency data transfer, streaming eliminates the per-message round-trip overhead. Compare:

```
1000 small messages, request-response (1ms RTT each):
  Total time = 1000 × 1ms = 1 second (sequential)
  Or with pipelining: 1000 ÷ (connection_pool_size × parallelism)

1000 small messages, streaming (one connection, amortized RTT):
  Connection setup: 1ms
  Message transfer: 1000 × (message size / bandwidth)
  Total: ~10-50ms for typical message sizes
```

Streaming amortizes connection setup and RTT across all messages, achieving 20-100× throughput improvement over sequential request-response for high-frequency small messages. This is the performance argument for gRPC server/client streaming over repeated REST calls.

**Q23. What is head-of-line blocking and how does it affect each pattern?**
A: Head-of-line (HOL) blocking occurs when a slow or large message prevents subsequent messages from being processed:

**Request-response over HTTP/1.1**: each connection handles one request at a time. If request 1 takes 500ms and requests 2-10 are waiting, they all wait behind it. Mitigated by connection pooling (multiple connections), but at the cost of more connections.

**Streaming over HTTP/2**: HTTP/2 multiplexes multiple streams over one TCP connection. But TCP itself is ordered — a lost TCP packet pauses all streams on that connection until the packet is retransmitted (TCP-level HOL blocking). A large frame on one gRPC stream can delay frames from other streams on the same TCP connection.

**HTTP/3 over QUIC**: QUIC provides stream-level independence — a lost packet on stream 3 doesn't delay stream 7, because QUIC is not a strictly ordered byte stream at the connection level. HTTP/3 eliminates TCP-level HOL blocking, at the cost of being a newer protocol with less infrastructure support.

**Fire-and-forget**: minimal HOL blocking risk — messages are queued and processed independently. A slow message in a queue (taking longer to process than others) doesn't block other messages from being picked up by other consumers (unless it's a single-consumer FIFO queue where order must be preserved).

## Section 8: Scenario-Based Questions

**Q24. "Design the communication pattern between a client and a server for a large language model (LLM) chat application. Users expect to see words appear progressively (like ChatGPT). What pattern do you use and what are the implementation details?"**
A: The interaction is: one user message (request), many response tokens (streaming response) — server-side streaming. The user should see the first token within 200-500ms; the full response may take 10-30 seconds. Batch (non-streaming) response would mean 10-30 seconds of blank waiting — unacceptable UX.

**Pattern**: server-side streaming over HTTP with SSE (Server-Sent Events) or chunked JSON.

**Implementation**:
```
Client → POST /v1/chat { "message": "Explain quantum computing", "stream": true }
         HTTP/1.1 200 OK
         Content-Type: text/event-stream
         Cache-Control: no-cache

Server → data: {"token": "Quantum", "index": 0}\n\n
Server → data: {"token": " computing", "index": 1}\n\n
Server → data: {"token": " is", "index": 2}\n\n
[... hundreds of tokens ...]
Server → data: {"done": true, "total_tokens": 342}\n\n
```

**Key design decisions**:
- **Why SSE over WebSocket**: the user only sends one message and receives a stream of tokens — no bidirectional streaming needed. SSE is simpler (standard HTTP, auto-reconnect built-in, CDN-compatible) for unidirectional server-push. WebSocket would add complexity without benefit here.
- **Token buffering for client rendering**: don't render each token individually (causes visual jitter). Buffer 3-5 tokens, then append to the DOM as a batch — smooth animation at ~20-30 renders per second.
- **Cancellation**: if the user sends a new message mid-generation or closes the tab, the client should close the SSE connection. The server must detect the closed connection (read error on the HTTP response body) and cancel the LLM inference to save compute.
- **Proxy considerations**: SSE requires that proxies and CDNs pass through chunked responses without buffering. Some CDN configurations buffer until the full response is received — defeating streaming. This must be explicitly configured (`X-Accel-Buffering: no` for nginx, `DisableContentCompression` for some ALB configs).

**Q25. "You're designing an IoT system where 100,000 sensors each send temperature readings every second. The backend must detect anomalies in real-time. What communication pattern do you use for sensor → backend?"**
A: 100k sensors × 1 reading/second = 100k messages/second from sensors to backend. The decision is: request-response (each sensor makes an HTTP POST per reading), fire-and-forget, or streaming.

**Request-response per reading**: 100k HTTP requests/second. Each HTTP/1.1 request has headers (~500 bytes overhead), TCP connection management, and requires a response (acknowledgment). At this rate, the response overhead is wasted — sensors don't need to know the backend received the reading to continue operating. Request-response overhead per sensor: connection pool management, 2× the bandwidth (for the response), threads blocked waiting for acknowledgment.

**Fire-and-forget via UDP**: maximum simplicity — sensors send UDP datagrams with no acknowledgment, no connection. Extremely low overhead. Risk: UDP packet loss (typically 0.01-1% on a local network, higher on WAN). For temperature readings, losing 0.01% of readings is acceptable (trends are still correct). For anomaly detection, briefly missing a reading is tolerable. Used by many IoT protocols (CoAP over UDP, MQTT-SN over UDP).

**Streaming via MQTT or persistent TCP connection**: each sensor maintains one persistent TCP/TLS connection to an MQTT broker. Within that connection, it sends small readings (MQTT messages can be < 100 bytes). The persistent connection amortizes TLS handshake cost across millions of messages; MQTT's QoS 1 (at-least-once) provides delivery guarantees without HTTP overhead. At 100k concurrent connections, the broker must handle 100k file descriptors — requiring a high-performance async broker (EMQX, Mosquitto, AWS IoT Core). MQTT is the industry-standard protocol for this exact pattern.

**Recommendation**: MQTT over TLS with QoS 0 (fire-and-forget within the broker) for non-critical readings and QoS 1 (at-least-once) for anomaly-triggering readings. Backend: MQTT broker (AWS IoT Core or EMQX) → Kafka (for stream processing) → Flink (real-time anomaly detection per sensor). The sensor-to-backend pattern is streaming (persistent MQTT connection); the backend-to-processing pattern is event streaming (Kafka).

**Q26. "A client needs to upload a 5GB file and wants to see upload progress in real-time. The server must process the file after upload and show processing progress too. Design the complete interaction."**
A: Three distinct phases with different optimal patterns:

**Phase 1 — Upload (client → server, streaming)**:
Chunked upload via HTTP multipart or streaming POST. The client sends the file in chunks (e.g., 5MB each), and the server acknowledges each chunk. Why not one giant POST? Resumability — if the connection drops after chunk 400 of 1000, the client can resume from chunk 401 rather than starting over. Implementation: use the `Content-Range` header (HTTP range requests) to track position; the server stores a partial upload state keyed by an `Upload-ID`.

**Phase 2 — Upload progress (server → client, streaming)**:
SSE endpoint `/uploads/{id}/progress` — the client subscribes and receives byte-count updates as chunks arrive:
```
data: {"phase": "upload", "bytes_received": 52428800, "total": 5368709120, "pct": 1}\n\n
data: {"phase": "upload", "bytes_received": 104857600, "pct": 2}\n\n
```
The client renders a progress bar from these events.

**Phase 3 — Processing progress (server → client, streaming)**:
After upload completes, the same SSE connection or a new one streams processing progress. If processing is async (triggered by a background job), use the async request-response (Q5) pattern with polling, or switch the SSE stream to processing events:
```
data: {"phase": "processing", "step": "virus_scan", "pct": 0}\n\n
data: {"phase": "processing", "step": "virus_scan", "pct": 100}\n\n
data: {"phase": "processing", "step": "indexing", "pct": 23}\n\n
data: {"phase": "processing", "step": "complete", "result_url": "/files/abc123"}\n\n
```

**Complete pattern**:
- Upload: client-side streaming (HTTP chunked POST with `Content-Range`)
- Upload progress: server-side streaming (SSE)
- Processing: fire-and-forget to a background job queue (SQS/Kafka)
- Processing progress: server-side streaming (SSE from job status emitter)
- Final result: request-response (GET `/files/abc123`)

This is a representative example of how real systems combine all three interaction models — no single pattern serves all phases of a complex workflow.

**Q27. "Two microservices need to exchange data. Service A produces 50,000 small status updates per second. Service B must consume them in real-time and update a dashboard. The updates must be delivered in order per entity. What's your design?"**
A: Three constraints: high throughput (50k/sec), real-time delivery, and per-entity ordering. Analysis of options:

**Direct request-response (Service A → Service B via HTTP/gRPC)**: at 50k calls/second with ~1ms per call, Service A needs 50 threads/connections constantly making calls to B. Service B must handle 50k concurrent or sequential requests per second. If B is slow or down, A is blocked. Tight coupling. Not the right pattern.

**Fire-and-forget (UDP/Kafka)**: at 50k messages/second, a single Kafka topic with sufficient partitions handles this comfortably (Kafka's throughput ceiling is millions/sec). Per-entity ordering: use `entity_id` as the Kafka partition key — all updates for entity X go to one partition in order. Service B maintains a consumer group reading from Kafka. If B falls behind (consumer lag), messages queue in Kafka durably without affecting A.

**Streaming (gRPC server streaming or WebSocket)**: A streams to B via a persistent connection. A single gRPC bidirectional stream can deliver 50k small messages/second with very low per-message overhead (no HTTP header overhead per message, just Protobuf framing). If B disconnects, A must buffer or drop — no durable intermediary. If per-entity ordering must be preserved across reconnections, streaming needs application-level sequencing.

**Recommended design**: Kafka as the primary transport. Service A produces to Kafka with `entity_id` partition key (per-entity ordering guaranteed within partition). Service B consumes from Kafka with a consumer group sized to partition count. Kafka provides durability (B can fall behind and catch up), per-entity ordering (partition key), and throughput (50k/sec is well within a 10-partition topic's capacity). For the dashboard update, Service B processes Kafka events and pushes to the dashboard via WebSocket or SSE — combining event streaming (A → Kafka → B) with server-side streaming (B → Dashboard).

## Quick Reference Table

| Dimension | Request-Response | Fire-and-Forget | Streaming |
|---|---|---|---|
| Message cardinality | 1 → 1 | 1 → 0 | N → M (N or M > 1) |
| Sender blocks? | Yes (sync) or awaits future (async) | No | No (reads/writes as available) |
| Delivery confirmation | Immediate | None (unless ack pattern) | Per-message or per-batch |
| Error visibility | Immediate | Invisible to sender | Immediate on connection break |
| Coupling | High temporal | Low (with durable intermediary) | Medium (connection must persist) |
| Latency profile | RTT + processing | Handoff time only (fast) | First message after setup + stream |
| Throughput ceiling | Per-connection parallelism | Queue/broker throughput | Connection bandwidth |
| Retries | Safe for idempotent, careful for non-idempotent | Handled by intermediary | Application-level, from last offset |
| Use cases | API calls, queries, transactions | Notifications, metrics, events | Live feeds, file transfer, real-time data |
| Technologies | REST, gRPC (unary), GraphQL | Kafka, SQS, UDP | gRPC streaming, WebSocket, SSE, MQTT |

---

**Tip for interviews:** Five things separate strong candidates on these three patterns: (1) being able to state the **message cardinality** for each pattern (1→1, 1→0, N→M) as the primary distinguishing characteristic — not sync/async, which is a secondary property; (2) knowing that **fire-and-forget does not inherently guarantee delivery** — confusing "fire-and-forget" with "guaranteed async delivery" is a common misconception, and knowing a durable intermediary is required for the latter; (3) articulating **idempotency keys** (Q21) as the correct solution to request-response retry safety for non-idempotent operations — not "just don't retry" (incorrect) or "use exactly-once delivery" (too expensive); (4) knowing **SSE vs WebSocket vs gRPC streaming** selection criteria (Q15, Q24) — SSE for unidirectional browser push, WebSocket for bidirectional browser, gRPC streaming for service-to-service — and being precise about why each wins in its domain; and (5) proposing a **hybrid design** when the scenario has multiple phases (Q26) — real production systems always combine patterns, and demonstrating this rather than picking one for the entire system shows architectural maturity.
