# Webhook Design: Delivery Guarantees, Retry with Exponential Backoff, Idempotency — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals and Mental Model

**Q1. What is a webhook and how does it differ architecturally from polling and server-sent events?**
A: A webhook is an HTTP callback — the provider (sender) pushes an HTTP request to a consumer-defined URL when an event occurs, rather than waiting for the consumer to ask. It inverts the request-response model: the consumer registers a URL, and the provider becomes the HTTP client.

Architectural comparison:

```
Polling (consumer-driven):
Consumer ─── GET /events?since=T ───► Provider
Consumer ◄─── {events: [...]} ───────
(repeated on schedule, even when nothing happened)

Webhook (provider-driven):
Provider ─── POST /webhook {event: "payment.succeeded"} ──► Consumer
Consumer ◄─── 200 OK ────────────────────────────────────
(only when something happens, zero consumer polling overhead)

SSE / WebSocket (persistent connection):
Consumer ◄──── persistent connection ──── Provider
(real-time push, but requires persistent infrastructure on both sides)
```

The fundamental trade-off: webhooks are simpler for the consumer (just an HTTP endpoint) and cheaper at low event frequency, but the provider now bears the operational burden of reliable delivery — retry logic, dead letter queues, backpressure handling, and secret rotation. Polling is simpler for the provider; webhooks shift complexity to the provider.

**Q2. What are the three delivery guarantee semantics, and which one do webhooks typically provide?**
A: The three delivery guarantee levels apply to any distributed messaging system, including webhooks:

**At-most-once**: the provider attempts delivery once. If the consumer is down or returns a non-2xx, the event is dropped. Zero duplicate risk, but events are permanently lost on transient failures. Appropriate only for metrics, analytics, or fire-and-forget telemetry where data loss is acceptable.

**At-least-once**: the provider retries until the consumer acknowledges (2xx response) or a maximum retry limit/TTL is exceeded. Events are guaranteed to arrive *eventually* if the consumer comes back online within the retry window — but on timeout/retry, the consumer may receive the same event multiple times (network partition: provider sent, consumer processed, ACK lost — provider retries, consumer processes again). This is the standard webhook delivery model used by Stripe, GitHub, Twilio, and virtually every production webhook provider.

**Exactly-once**: each event is delivered and processed exactly once, with no duplicates and no losses. Impossible to guarantee at the network layer alone — requires cooperation between provider (idempotent delivery IDs) and consumer (idempotent processing with deduplication store). Not a property providers can offer unilaterally; it's a contract the consumer must uphold by implementing idempotent handlers.

**Production reality**: all serious webhook providers offer at-least-once delivery and document this explicitly. Stripe's documentation states: *"Stripe attempts to deliver your webhooks for up to three days with an exponential back off."* The consumer's responsibility is always to handle duplicates gracefully — making exactly-once semantics achievable end-to-end.

**Q3. Why is "fire and forget" (at-most-once) insufficient for financial or state-mutation webhooks?**
A: Consider a `payment.succeeded` webhook: the provider's payment service charges the customer's card and fires a webhook to the merchant's fulfillment service. With at-most-once:

- The fulfillment service is doing a rolling deploy — the pod handling the webhook request is killed mid-processing, returning a 502.
- The provider drops the event — no retry.
- The customer's card was charged, but the merchant's system never fulfilled the order. The customer pays and receives nothing.

At-most-once is only safe when: (1) the event is purely informational and the consumer can reconstruct state by polling, (2) the loss of individual events has no business consequence, or (3) the event is immutable and will naturally be superseded (e.g., a sensor reading where the next reading makes the previous one irrelevant).

For any state-mutating webhook — account creation, payment confirmation, permission grant, subscription change — at-least-once with idempotent consumers is the minimum acceptable guarantee. The risk of processing twice is always lower than the risk of not processing at all when the event represents a real-world financial or state change.

## Section 2: Delivery Guarantees — Deep Dive

**Q4. What does it mean for a webhook provider to "guarantee" delivery, and what are the practical limits of that guarantee?**
A: A provider's delivery guarantee is bounded by two parameters: **maximum retry attempts** (or maximum retry duration) and **consumer acknowledgment semantics**. Neither is infinite.

**Stripe's model**: retries over 3 days with exponential backoff. If the consumer endpoint is unreachable for >3 days, the event is permanently dropped (moved to a failed events log, visible in the Stripe Dashboard for manual replay). The guarantee is: *deliver at least once within 72 hours, given any transient consumer unavailability shorter than the retry window.*

**GitHub's model**: 3 immediate retries, then the webhook is disabled if too many consecutive failures occur (GitHub deactivates the hook). The guarantee is much weaker — persistent consumer downtime of even a few hours can cause permanent webhook disablement.

**What "2xx acknowledgment" means**: the provider considers the event delivered when it receives any 2xx HTTP status from the consumer endpoint within a response timeout (typically 5-30 seconds). The provider does not know or care whether the consumer *processed* the event — only that the consumer's HTTP server responded. This is why the correct consumer pattern is:

```
1. Receive webhook → immediately persist to queue/DB → return 200 OK
2. Process asynchronously from the queue

NOT:
1. Receive webhook → process synchronously → return 200 OK after processing
```

If processing takes 10 seconds and the provider's timeout is 5 seconds, the provider receives a timeout, marks the delivery as failed, and retries — even though the consumer processed it successfully. The consumer then processes it again from the retry. Returning 200 immediately and processing asynchronously is the only way to decouple provider timeout constraints from consumer processing time.

**Q5. How should a consumer endpoint be implemented to correctly separate acknowledgment from processing?**
A: The correct pattern is a two-phase approach: acknowledge-then-process, not process-then-acknowledge.

```typescript
// NestJS controller — correct pattern
@Post('/webhook/stripe')
async handleStripeWebhook(
  @Headers('stripe-signature') signature: string,
  @RawBody() rawBody: Buffer,
  @Res() res: Response,
): Promise<void> {
  // Phase 1: Validate signature (fast, synchronous — must happen before 200)
  let event: Stripe.Event;
  try {
    event = this.stripeService.constructEvent(rawBody, signature);
  } catch (err) {
    res.status(400).send('Invalid signature');
    return;
  }

  // Phase 2: Persist to queue (fast, durable — job queue, Redis, or DB)
  await this.webhookQueue.add('stripe-event', {
    eventId: event.id,
    type: event.type,
    data: event.data,
    receivedAt: Date.now(),
  });

  // Phase 3: Acknowledge immediately — DO NOT wait for processing
  res.status(200).send('OK');
}

// Separate worker processes the queue asynchronously
@Process('stripe-event')
async processStripeEvent(job: Job): Promise<void> {
  const { eventId, type, data } = job.data;

  // Idempotency check happens here, not in the HTTP handler
  const alreadyProcessed = await this.webhookProcessingRepo.exists(eventId);
  if (alreadyProcessed) return; // Duplicate — safe to skip

  // Actual business logic
  switch (type) {
    case 'payment_intent.succeeded':
      await this.fulfillmentService.fulfill(data.object);
      break;
    // ...
  }

  // Mark as processed
  await this.webhookProcessingRepo.markProcessed(eventId);
}
```

**Why this matters at scale**: a consumer processing 500 webhooks/second with 50ms average processing time needs 25 worker threads to keep up if processing is synchronous with the HTTP handler. With the queue pattern, the HTTP handler returns in <1ms (just a queue write), the web server handles thousands of concurrent inbound webhooks with minimal threads, and workers process at their own pace — decoupled from inbound throughput.

**Q6. What HTTP status codes should a consumer return, and what does the provider do with each?**
A: The provider interprets the consumer's HTTP response status to determine whether to retry:

| Status | Provider interpretation | Provider action |
|---|---|---|
| `200 OK`, `201 Created`, `204 No Content` | Success — event delivered | Mark delivered, no retry |
| `400 Bad Request` | Consumer rejected event (bad payload) | **Do not retry** — retrying won't fix a malformed payload. Log as permanently failed. |
| `401 Unauthorized`, `403 Forbidden` | Authentication failure | **Do not retry** (some providers retry once with fresh credentials, but generally treat as permanent failure). Log as failed. |
| `404 Not Found` | Endpoint doesn't exist | **Do not retry** — endpoint is gone. Disable webhook (GitHub behavior). |
| `408 Request Timeout` | Consumer too slow | Retry with backoff |
| `429 Too Many Requests` | Consumer rate-limited | Retry with backoff, respect `Retry-After` header if present |
| `500 Internal Server Error` | Consumer crashed | Retry with backoff |
| `502 Bad Gateway`, `503 Service Unavailable` | Consumer infrastructure issue | Retry with backoff |
| `504 Gateway Timeout` | Upstream processing timeout | Retry with backoff |
| Connection refused / TCP timeout | Consumer unreachable | Retry with backoff |

**The consumer's contract**: return `400` for events that are malformed or not understood (not for business logic failures — a duplicate payment you can't fulfill is not a `400`; it's a `200` after your idempotency check). Return `2xx` once the event is safely persisted. Never return `200` if you haven't at least durably saved the event somewhere — that's lying to the provider about delivery.

## Section 3: Retry with Exponential Backoff — Deep Dive

**Q7. What is exponential backoff and why is it the standard retry strategy for webhooks?**
A: Exponential backoff increases the wait interval between retry attempts exponentially rather than using a fixed interval. If the consumer is down (server crash, deploy, database outage), hammering it at a fixed 1-second interval wastes provider resources, floods the consumer's error logs, and can prevent recovery (a consumer restarting under load gets hammered before it's fully initialized, triggering another crash).

Exponential backoff gives the consumer time to recover while still achieving eventual delivery:

```
Attempt 1: immediate (t = 0)
Attempt 2: t + 1s       (2^0 × base)
Attempt 3: t + 2s       (2^1 × base)
Attempt 4: t + 4s       (2^2 × base)
Attempt 5: t + 8s       (2^3 × base)
Attempt 6: t + 16s
Attempt 7: t + 32s
...
Attempt N: t + min(2^(N-1) × base, max_delay)
```

With a 1-second base and 1-hour cap:
- After 10 attempts: ~17 minutes total elapsed time
- After 15 attempts: ~9 hours total elapsed time (already capped at 1-hour intervals)

**Real provider schedules**:
- **Stripe**: 1h, 1h, 1h, 3h, 6h, 12h, 24h (manual intervals, ~72 hours total)
- **GitHub**: 0s, 5s, 60s, 2min (4 attempts, no long-term retry)
- **Shopify**: 5s, 10s, 60s, 5min, 10min, 30min, 1h, 2h, 4h, 8h, 24h (11 attempts over ~48h)

**Q8. What is jitter in exponential backoff, and why is it critical for webhook providers at scale?**
A: Jitter adds randomness to the retry interval. Without jitter, all consumers that experienced a failure at time T will retry at exactly T + 2^N seconds — a synchronized thundering herd. If 10,000 webhook deliveries failed because of a 30-second provider outage at T=0, without jitter all 10,000 retry at T=1s, fail again, retry at T=2s simultaneously, fail again. The synchronized retries can sustain the overload that caused the original failure.

**Full jitter** (AWS recommended): `sleep = random_between(0, min(cap, base * 2^attempt))`

```typescript
function computeRetryDelay(
  attempt: number,
  baseDelayMs: number = 1000,
  maxDelayMs: number = 3_600_000, // 1 hour cap
): number {
  const exponentialDelay = Math.min(maxDelayMs, baseDelayMs * Math.pow(2, attempt));
  // Full jitter: random value between 0 and the exponential delay
  return Math.floor(Math.random() * exponentialDelay);
}

// attempt 0 → 0–1000ms
// attempt 1 → 0–2000ms
// attempt 2 → 0–4000ms
// attempt 5 → 0–32000ms
// attempt 10 → 0–1hour (capped)
```

**Equal jitter** (preserves minimum delay guarantee): `sleep = cap/2 + random_between(0, cap/2)` — ensures at least half the cap delay, with jitter in the second half. Preferable when you need a minimum delay between retries (e.g., to avoid overwhelming a consumer that needs at least N seconds to recover).

The practical effect of jitter: 10,000 retries that would all hit at T+1s are spread across a 1-second window, reducing peak retry throughput by ~1000×. At webhook provider scale (millions of deliveries), jitter is the difference between orderly recovery and cascading retry storms.

**Q9. How does a webhook provider implement the retry queue at scale? What does the infrastructure look like?**
A: A production webhook delivery system has multiple layers:

```
Event Source (payment service, user service, etc.)
    │
    ▼
Event Bus (Kafka / SQS)          ← durable, ordered, replay-capable
    │
    ▼
Webhook Dispatcher Service       ← consumes events, manages delivery
    │
    ├── Immediate Delivery Pool (attempt 1)
    │       │ success → mark delivered
    │       │ failure → enqueue to retry queue
    │
    ▼
Retry Queue (SQS with DelaySeconds / Redis sorted set with score=next_attempt_time)
    │
    ├── Retry Worker (polls for due retries)
    │       │ success → mark delivered
    │       │ failure → re-enqueue with incremented attempt count
    │       │ max attempts exceeded → move to Dead Letter Queue
    │
    ▼
Dead Letter Queue (DLQ)          ← failed events for manual inspection / replay
    │
    ▼
Provider Dashboard / Alert       ← notify webhook owner of persistent failures
```

**Redis sorted set implementation** (common for smaller scale):
```typescript
// Enqueue a retry: score = Unix timestamp of next attempt
const nextAttemptAt = Date.now() + computeRetryDelay(attempt);
await redis.zadd('webhook:retry_queue', nextAttemptAt, JSON.stringify({
  webhookId,
  eventId,
  attempt,
  payload,
  endpoint,
}));

// Worker: poll for due retries every second
const now = Date.now();
const dueRetries = await redis.zrangebyscore(
  'webhook:retry_queue', '-inf', now, 'LIMIT', 0, 100
);
// Atomically remove and process
await redis.zrem('webhook:retry_queue', ...dueRetries);
```

**SQS implementation** (AWS-native, preferred for production):
- SQS `DelaySeconds` on individual messages: set delay to `computeRetryDelay(attempt)` seconds when re-enqueuing.
- SQS `MessageDeduplicationId`: prevents the queue from double-delivering due to producer retries (SQS FIFO).
- SQS DLQ: configure `maxReceiveCount` — after N failed dequeue-process-delete cycles, SQS automatically moves to the DLQ. Zero custom DLQ routing code.

**Q10. What is the difference between the provider retrying the webhook and the consumer's internal retry logic?**
A: These are two completely separate retry mechanisms operating at different layers, and conflating them is a common design error:

**Provider retry**: the provider's webhook dispatcher retrying delivery to the consumer's HTTP endpoint after a non-2xx response or timeout. This is the *network delivery* retry — it handles consumer downtime, network partitions, and infrastructure failures. The provider's retry is driven by HTTP response codes. The consumer has no direct control over this except by returning the correct status codes.

**Consumer internal retry**: after the consumer's HTTP handler persists the event to a queue and returns 200, the consumer's async worker may fail to process the event (database unavailable, downstream API down, bug in processing logic). The consumer must implement its own retry logic for the *business logic processing* retry — the provider has already delivered successfully and won't retry.

```
Provider retry scope:
[Provider] ──HTTP POST──► [Consumer HTTP endpoint]
               ↑
         Provider retries here on timeout/5xx

Consumer internal retry scope:
[Consumer HTTP endpoint] ──enqueue──► [Job Queue] ──dequeue──► [Worker]
                                                                    ↑
                                                     Consumer retries here on processing failure
```

A webhook that produces a 200 response but fails to persist to the queue is the worst outcome: the provider marks it delivered (no retry coming), but the consumer never processed it. The queue write in the HTTP handler must be synchronous and confirmed before returning 200.

## Section 4: Idempotency — Deep Dive

**Q11. What is idempotency in the context of webhooks, and what makes a handler idempotent?**
A: A function is idempotent if applying it multiple times produces the same result as applying it once. An idempotent webhook handler produces the same system state whether the event is processed once or N times:

**Non-idempotent handler** (dangerous):
```typescript
// BAD: processes payment.succeeded by crediting the user's balance
async function handlePaymentSucceeded(event: PaymentEvent) {
  await db.query(
    'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
    [event.amount, event.userId]
  );
}
// Called twice → balance credited twice
```

**Idempotent handler** (correct):
```typescript
// GOOD: uses event ID as idempotency key
async function handlePaymentSucceeded(event: PaymentEvent) {
  // Attempt to insert a processing record with a unique constraint on event_id
  const inserted = await db.query(`
    INSERT INTO webhook_events (event_id, type, processed_at)
    VALUES ($1, $2, NOW())
    ON CONFLICT (event_id) DO NOTHING
    RETURNING event_id
  `, [event.id, event.type]);

  // If nothing was inserted, this event was already processed
  if (inserted.rowCount === 0) {
    logger.info({ eventId: event.id }, 'Duplicate webhook — skipping');
    return;
  }

  // Safe to process — guaranteed to run exactly once per event_id
  await db.query(
    'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
    [event.amount, event.userId]
  );
}
```

**The ON CONFLICT trick**: using the database's uniqueness constraint as an atomic idempotency check eliminates the TOCTOU (time-of-check-time-of-use) race condition present in a check-then-insert pattern. Two concurrent requests for the same event ID will race to insert — exactly one will succeed; the other gets `rowCount === 0` and skips. No application-level locking required.

**Q12. What are the different strategies for idempotency key design in webhooks?**
A: The idempotency key is the unique identifier used to detect duplicate events. Several strategies exist with different trade-offs:

**Provider-assigned event ID** (best — use when available):
Every serious webhook provider assigns a globally unique event ID (`evt_1Nabcd...` in Stripe, `X-GitHub-Delivery` header UUID in GitHub). Use this as the idempotency key. It's stable across all retries of the same event, globally unique across all events, and the canonical way to identify a specific occurrence.

```typescript
// Stripe: event.id = "evt_1NiCGdLkdIwHu7ixjIFM5GSo"
// GitHub: request header X-GitHub-Delivery = "72d3162e-cc78-11e3-81ab-4c9367dc0958"
// Twilio: event.MessageSid = "SM123..."
```

**Content-based hashing** (fallback when provider doesn't assign IDs):
Hash the deterministic, immutable parts of the event payload. Be careful: any field that changes between retries (timestamp of delivery, attempt number) must be excluded from the hash.

```typescript
import { createHash } from 'crypto';

function computeEventKey(event: WebhookPayload): string {
  // Include only stable, content-identifying fields
  const stable = {
    type: event.type,
    resourceId: event.resource.id,
    // Include a timestamp only if it represents when the event OCCURRED, not when it was DELIVERED
    occurredAt: event.occurred_at,
  };
  return createHash('sha256').update(JSON.stringify(stable)).digest('hex');
}
```

**Sequence-number-based** (for ordered event streams):
If the provider guarantees sequential event IDs per resource (e.g., event sequence numbers per account), use `(resourceId, sequenceNumber)` as a composite key. This enables gap detection (sequence 5 arrived but sequence 4 hasn't — hold 5 until 4 arrives) in addition to deduplication.

**Q13. How do you handle idempotency when a webhook triggers a downstream API call that is not idempotent?**
A: This is the hardest idempotency problem — your handler is idempotent at the DB level, but the side effect it needs to trigger (charge a card, send an email, call a third-party API) is not inherently idempotent.

**Strategy 1: Idempotency keys on downstream calls**
Most payment APIs (Stripe, Razorpay, JusPay) accept an idempotency key parameter. Pass the webhook's event ID as the downstream idempotency key — the downstream API deduplicates on its end.

```typescript
// Passing webhook event ID as Stripe idempotency key for downstream charge
await stripe.charges.create(
  { amount: 1000, currency: 'usd', source: cardToken },
  { idempotencyKey: `webhook-${webhookEventId}` }  // ← derived from webhook event ID
);
// If called twice with the same idempotencyKey, Stripe returns the first charge — no duplicate charge
```

**Strategy 2: State machine with transition guards**
Model the entity as a state machine. Only transition if the current state is valid for the transition. Duplicate events attempting the same transition are no-ops:

```typescript
async function handleOrderShipped(event: OrderShippedEvent) {
  const order = await orderRepo.findById(event.orderId);

  // Transition guard — idempotent: transitioning from 'shipped' to 'shipped' is a no-op
  if (order.status !== 'payment_confirmed') {
    logger.info({ orderId: event.orderId, status: order.status }, 'Order not in expected state — skipping');
    return;
  }

  await orderRepo.updateStatus(event.orderId, 'shipped');
  await notificationService.notifyCustomer(event.orderId, 'Your order has shipped!');
}
```

**Strategy 3: Exactly-once side effects via outbox pattern**
For non-idempotent side effects (sending one SMS per event), use the transactional outbox pattern: write the side effect intent to a DB table in the same transaction as the idempotency record. A separate poller reads the outbox and executes side effects with a unique constraint preventing duplicate sends:

```
Transaction:
  INSERT INTO webhook_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING → rowCount check
  INSERT INTO outbox (event_id, action, payload) VALUES ($1, 'send_sms', $2)
    ON CONFLICT (event_id, action) DO NOTHING
→ COMMIT

Outbox worker: SELECT unpublished outbox rows → send SMS → mark sent
```

**Q14. What is the idempotency window problem, and how do you handle it?**
A: Even with idempotency keys, time matters. Consider:

1. Worker A picks up event `evt_123`, begins processing, writes the idempotency record, starts a 10-second downstream API call.
2. Worker B is also processing `evt_123` (e.g., two queue consumers racing). Worker B checks idempotency → record exists → skips. Correct.
3. Worker A crashes after writing the idempotency record but before completing the downstream call. The idempotency record exists, so no future worker will re-process. **The event is permanently stuck — neither processed nor retried.**

Solutions:

**Status field on idempotency record** (recommended):
```sql
CREATE TABLE webhook_events (
  event_id    VARCHAR PRIMARY KEY,
  status      VARCHAR NOT NULL DEFAULT 'processing',  -- 'processing' | 'completed' | 'failed'
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  completed_at TIMESTAMPTZ
);
```

Workers mark status='processing' on insert, 'completed' when done. On crash recovery, a cleanup job finds 'processing' records older than a heartbeat window and resets them (or marks 'failed' for manual replay). This allows exactly-once semantics even with worker crashes.

**Distributed locking with TTL** (for high-concurrency scenarios):
```typescript
const lockKey = `webhook:lock:${eventId}`;
const lockTTL = 30_000; // 30 seconds — max expected processing time

const acquired = await redis.set(lockKey, workerId, 'NX', 'PX', lockTTL);
if (!acquired) return; // Another worker has it

try {
  await processEvent(event);
  await markEventProcessed(eventId);
} finally {
  await redis.del(lockKey); // Release lock on completion or crash (TTL handles crash case)
}
```

## Section 5: Security

**Q15. How do you verify that a webhook actually came from the claimed provider, and not a malicious actor?**
A: A webhook endpoint is a public HTTP URL — anyone who discovers it can POST arbitrary payloads to it. Without verification, an attacker who knows your webhook URL can forge events ("payment.succeeded" for a payment they never made) and manipulate your application state.

**HMAC signature verification** (industry standard):
The provider signs each webhook payload using a shared secret key and includes the signature in a request header. The consumer recomputes the signature using the same secret and compares:

```typescript
import { createHmac, timingSafeEqual } from 'crypto';

function verifyStripeWebhook(
  rawBody: Buffer,
  signatureHeader: string,  // "t=1714000000,v1=abc123..."
  webhookSecret: string,
): boolean {
  const parts = signatureHeader.split(',');
  const timestamp = parts.find(p => p.startsWith('t='))?.slice(2);
  const signature = parts.find(p => p.startsWith('v1='))?.slice(3);

  if (!timestamp || !signature) return false;

  // Replay attack prevention: reject signatures older than 5 minutes
  const ageSeconds = Math.floor(Date.now() / 1000) - parseInt(timestamp, 10);
  if (ageSeconds > 300) throw new Error('Webhook timestamp too old — potential replay attack');

  // Recompute: signed_payload = timestamp + '.' + raw_body
  const signedPayload = `${timestamp}.${rawBody.toString('utf8')}`;
  const expectedSignature = createHmac('sha256', webhookSecret)
    .update(signedPayload)
    .digest('hex');

  // Timing-safe comparison to prevent timing oracle attacks
  const expectedBuf = Buffer.from(expectedSignature, 'hex');
  const receivedBuf = Buffer.from(signature, 'hex');

  if (expectedBuf.length !== receivedBuf.length) return false;
  return timingSafeEqual(expectedBuf, receivedBuf);
}
```

**Critical implementation details**:
1. **Raw body**: compute the HMAC over the raw request body bytes, not the parsed JSON. JSON serialization is not deterministic across languages/libraries — `{"a":1}` and `{ "a": 1 }` are different byte sequences. Always capture raw body before parsing.
2. **Timing-safe comparison**: use `timingSafeEqual` instead of `===`. String comparison short-circuits on first mismatch — an attacker can measure response time to deduce how many bytes of the signature they guessed correctly. Timing-safe comparison takes constant time regardless of where the mismatch occurs.
3. **Timestamp + replay window**: include the delivery timestamp in the signed payload and reject signatures older than N minutes. Without this, an attacker who intercepts a valid webhook can replay it hours later. Stripe uses a 5-minute window.

**Q16. What happens if the webhook secret is compromised, and how do you rotate it safely?**
A: If the shared secret leaks, an attacker can forge arbitrary webhook payloads that pass signature verification. Secret rotation must happen without dropping legitimate webhooks during the transition:

**Zero-downtime rotation strategy**:
```
Step 1: Provider generates new secret (new_secret). Old secret still valid.
Step 2: Provider sends new webhooks signed with BOTH old_secret and new_secret
        (two v1= values in the signature header: v1=old_sig,v1=new_sig)
Step 3: Consumer deploys code accepting EITHER old_secret OR new_secret
Step 4: Consumer rotates to new_secret only (decommissions old_secret)
Step 5: Provider stops signing with old_secret
```

Stripe implements this exactly — their `Stripe-Signature` header can contain multiple `v1=` values for the transition window. Consumers that validate any one of the v1 signatures pass validation during rotation.

**In your own webhook system** (if you're the provider): store secrets in a versioned secrets table. Sign with the current active secret, include a `key_version` identifier in the header. The consumer tries verification with the key version specified — if it fails (concurrent rotation edge case), fall back to trying all recent active key versions.

## Section 6: Advanced Patterns

**Q17. What is the fan-out problem in webhook delivery, and how do you solve it for providers with many subscribers?**
A: Fan-out occurs when one event triggers deliveries to many consumers. In a platform like GitHub where a popular repository might have 10,000 webhook subscribers, a single `push` event requires 10,000 outbound HTTP requests.

**Naive implementation** (breaks at scale):
```typescript
// BAD: synchronous fan-out blocks the event ingestion pipeline
const subscribers = await db.query('SELECT * FROM webhook_subscriptions WHERE event=$1', [eventType]);
for (const sub of subscribers) {
  await httpClient.post(sub.endpoint, payload);  // Blocks — 10,000 sequential HTTP calls
}
```

**Queue-based fan-out** (production pattern):
```
Event occurs → Write single event to Kafka topic
                    │
                    ▼
Fan-out Worker (consumer group): reads event → queries subscribers → 
  enqueues one delivery task per subscriber into delivery queue
                    │
                    ▼
Delivery Workers (pool): each worker dequeues one delivery task → makes one HTTP POST
  success → ack task
  failure → re-enqueue with backoff (increment attempt count)
```

This decouples event ingestion throughput from fan-out throughput. The fan-out worker writes 10,000 tasks to the delivery queue in parallel; the delivery worker pool drains the queue at sustainable throughput with backpressure control (don't overwhelm slow consumers).

**Per-subscriber rate limiting**: if a subscriber's endpoint is slow (consistently returning after 5s), don't let their slowness block deliveries to fast subscribers. Assign each subscriber their own queue partition or use a separate rate limiter per `endpoint_domain` to prevent one slow consumer from consuming all delivery workers.

**Q18. What is the Dead Letter Queue (DLQ) pattern for webhooks, and how should it be operationalized?**
A: A DLQ receives events that exhausted all retry attempts without a successful delivery. Without a DLQ, permanently failed events are silently lost — the provider and consumer have no record of what wasn't delivered.

**DLQ operational requirements**:

```
Webhook Retry Queue
    │
    │ (maxAttempts exceeded OR event TTL expired)
    ▼
Dead Letter Queue
    │
    ├── Alert: "Webhook delivery permanently failed for endpoint X"
    ├── Dashboard: list of failed events with payload, error, attempt history
    └── Manual replay: operator reviews DLQ, fixes consumer, replays specific events
```

**Manual replay endpoint** (what providers expose to consumers):
```typescript
// Provider API: replay a specific failed event
POST /webhook/events/{event_id}/replay

// Consumer receives this as a fresh delivery attempt
// — same payload, same idempotency key, but a new HTTP delivery
```

**Automated DLQ processing** (for consumer-side internal retries):
```typescript
// BullMQ dead letter queue pattern
const queue = new Queue('webhook-processing', { connection: redis });
const worker = new Worker('webhook-processing', processWebhook, {
  connection: redis,
  settings: {
    maxStalledCount: 3,   // move to failed after 3 stalls
  },
});

// Failed job listener
worker.on('failed', async (job, err) => {
  if (job.attemptsMade >= job.opts.attempts) {
    // All retries exhausted → send to DLQ
    await dlqQueue.add('failed-webhook', {
      originalJobId: job.id,
      payload: job.data,
      error: err.message,
      failedAt: new Date().toISOString(),
    });
    await alertingService.notify(`Webhook permanently failed: ${job.data.eventId}`);
  }
});
```

**Q19. How do you handle webhook ordering guarantees — and do you need them?**
A: Webhooks from the same provider are not guaranteed to arrive in the order they were generated. Network conditions, retry scheduling, and parallel delivery workers all cause reordering. Common example: `subscription.updated` (status: 'active') arrives *after* `subscription.updated` (status: 'cancelled') — processing in arrival order would incorrectly mark the subscription active.

**Do you actually need ordering?**
Most webhook handlers are idempotent on event ID, not ordering-sensitive. If your handler's logic is "apply this specific event's state change," order doesn't matter as long as you apply each event at most once. The danger is handlers that do incremental updates ("add these permissions") rather than absolute state updates ("set permissions to exactly these values").

**Prefer absolute state in payloads**: design webhook payloads to carry the full current state of the resource, not a delta. `{"status": "cancelled"}` is safe to apply regardless of order. `{"delta": {"credits": -10}}` is order-sensitive and dangerous.

**Sequence-number ordering** (when strict ordering is required):
```typescript
// Each event carries a sequence number per resource
interface WebhookEvent {
  id: string;
  resourceId: string;
  sequence: number;   // monotonically increasing per resourceId
  payload: object;
}

async function handleOrdered(event: WebhookEvent) {
  const lastProcessed = await redis.get(`seq:${event.resourceId}`);
  const expected = (parseInt(lastProcessed ?? '0', 10)) + 1;

  if (event.sequence < expected) {
    return; // Already processed (duplicate or old)
  }

  if (event.sequence > expected) {
    // Out-of-order — store in holding buffer, wait for missing sequence
    await redis.zadd(`buffer:${event.resourceId}`, event.sequence, JSON.stringify(event));
    return;
  }

  // event.sequence === expected — process and drain buffer
  await processEvent(event);
  await redis.set(`seq:${event.resourceId}`, event.sequence);
  await drainBuffer(event.resourceId, event.sequence + 1);
}
```

**Q20. "Design a webhook delivery system for a payment platform (similar to Razorpay/Stripe). Merchants register endpoint URLs; events include payment.captured, refund.processed, dispute.opened. SLA: at-least-once delivery within 24 hours."**
A: System components and design decisions:

**Event ingestion**:
```
Payment Service → publishes to Kafka topic `payment.events`
Refund Service  → publishes to Kafka topic `refund.events`
Dispute Service → publishes to Kafka topic `dispute.events`
```

**Webhook Dispatcher** (Kafka consumer):
- Reads events from Kafka.
- Queries `webhook_subscriptions` table: `SELECT * FROM webhook_subscriptions WHERE merchant_id = $1 AND event_types @> ARRAY[$2]`.
- For each matching subscription, writes one delivery record to `webhook_deliveries` table and enqueues a delivery job to the SQS delivery queue.

**Delivery table schema**:
```sql
CREATE TABLE webhook_deliveries (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id        VARCHAR NOT NULL,
  subscription_id UUID NOT NULL REFERENCES webhook_subscriptions(id),
  endpoint_url    VARCHAR NOT NULL,
  payload         JSONB NOT NULL,
  status          VARCHAR NOT NULL DEFAULT 'pending',  -- pending/delivered/failed
  attempt_count   INT NOT NULL DEFAULT 0,
  next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_error      TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  delivered_at    TIMESTAMPTZ
);
CREATE INDEX ON webhook_deliveries (next_attempt_at) WHERE status = 'pending';
```

**Delivery worker**:
```typescript
async function attemptDelivery(deliveryId: string): Promise<void> {
  const delivery = await db.findDeliveryById(deliveryId);
  const startTime = Date.now();

  try {
    const response = await httpClient.post(delivery.endpointUrl, delivery.payload, {
      timeout: 10_000,
      headers: {
        'Content-Type': 'application/json',
        'X-Webhook-ID': delivery.eventId,
        'X-Webhook-Signature': computeHmac(delivery.payload, delivery.subscriptionSecret),
        'X-Webhook-Attempt': String(delivery.attemptCount + 1),
      },
    });

    if (response.status >= 200 && response.status < 300) {
      await db.markDelivered(deliveryId);
    } else if (response.status >= 400 && response.status < 500 && response.status !== 429) {
      // 4xx (except 429) → permanent failure, do not retry
      await db.markFailed(deliveryId, `HTTP ${response.status}`);
    } else {
      await scheduleRetry(delivery);
    }
  } catch (err) {
    await scheduleRetry(delivery);
  }
}

async function scheduleRetry(delivery: WebhookDelivery): Promise<void> {
  const attempt = delivery.attemptCount + 1;
  const maxAttempts = 20; // ~24 hours with exponential backoff

  if (attempt >= maxAttempts) {
    await db.markFailed(delivery.id, 'Max attempts exceeded');
    await dlqService.enqueue(delivery);
    return;
  }

  const delayMs = computeRetryDelay(attempt, 1000, 3_600_000); // base=1s, cap=1h
  await db.scheduleRetry(delivery.id, attempt, new Date(Date.now() + delayMs));
}
```

**Q21. "A merchant reports they're receiving the same `payment.captured` webhook 3 times and it's causing triple-charges to customers. How do you debug and fix this?"**
A: This is a classic at-least-once + non-idempotent consumer incident. Systematic debugging:

**Step 1: Determine whether it's a provider bug or consumer bug**

Check the provider's delivery logs:
- Did the provider send 3 distinct attempts (different timestamps, same event ID)?
- Or did it send one attempt that the consumer somehow processed 3 times?

If 3 attempts: check the HTTP response codes the provider received. If all 3 attempts got `200 OK` → the consumer is returning 200 even after failures, preventing the provider from seeing the error. If attempts 1-2 got `500` or timeout → the consumer is failing mid-processing, returning a non-2xx, provoking retries.

If 1 attempt: the consumer's internal architecture is processing the same job multiple times (multiple queue consumers picking up the same job, queue visibility timeout shorter than processing time causing re-delivery).

**Step 2: Fix the consumer (regardless of root cause)**

```typescript
// Add idempotency check BEFORE the charge call
async function handlePaymentCaptured(event: PaymentCapturedEvent) {
  // Atomic insert — returns 0 rows if event already processed
  const result = await db.query(`
    INSERT INTO processed_webhook_events (event_id, processed_at)
    VALUES ($1, NOW())
    ON CONFLICT (event_id) DO NOTHING
    RETURNING event_id
  `, [event.id]);

  if (result.rowCount === 0) {
    logger.warn({ eventId: event.id }, 'Duplicate webhook skipped');
    return; // ← return 200, but do nothing
  }

  // Only reaches here if first-time processing
  await billingService.charge(event.orderId, event.amount);
}
```

**Step 3: Remediate already-affected customers**

Query `processed_webhook_events` for events processed more than once (if the idempotency record was written but the uniqueness constraint wasn't enforced). Identify over-charged orders. Issue refunds via the payment provider's API for the duplicate charges. Notify affected customers.

**Step 4: Prevent recurrence**

- Unique constraint on `processed_webhook_events.event_id`.
- Add a reconciliation job: daily, compare provider's delivery log (via provider API) against consumer's processed events table. Alert on any event delivered but not processed, or processed without a delivery record.

## Quick Reference Table

| Dimension | At-most-once | At-least-once | Exactly-once |
|---|---|---|---|
| Provider responsibility | Send once | Retry until 2xx or TTL | Send with stable event ID |
| Consumer responsibility | None | Handle duplicates | Idempotency store + dedup |
| Data loss risk | High | None (within retry window) | None |
| Duplicate risk | None | Present | None (if implemented correctly) |
| Implementation cost | Trivial | Moderate (retry queue) | High (dedup store, outbox) |
| Appropriate for | Metrics, analytics, fire-and-forget | Notifications, payment events | Financial state mutations |

| Backoff Strategy | Formula | Use case |
|---|---|---|
| Fixed interval | `delay = base` | Simple, low-scale, same-origin retries |
| Linear backoff | `delay = base × attempt` | When recovery time grows predictably |
| Exponential backoff | `delay = min(cap, base × 2^attempt)` | General-purpose — balances speed and relief |
| Exponential + full jitter | `delay = random(0, min(cap, base × 2^attempt))` | High-scale providers — prevents thundering herd |
| Exponential + equal jitter | `delay = cap/2 + random(0, cap/2)` | When minimum delay is required |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) immediately recognizing that **at-least-once is the default webhook guarantee** and the consumer always bears responsibility for idempotency — not the provider; (2) knowing the **acknowledge-then-process pattern** (return 200 immediately, process from queue asynchronously) and why synchronous processing causes provider-induced duplicates; (3) being precise about **jitter in exponential backoff** (Q8) — knowing *why* jitter exists (thundering herd prevention) and the formula difference between full jitter and equal jitter; (4) implementing **HMAC signature verification correctly** — raw body (not parsed JSON), timing-safe comparison (`timingSafeEqual`), and timestamp replay window; (5) knowing the **ON CONFLICT DO NOTHING** idempotency pattern (Q11) as a concurrency-safe alternative to check-then-insert, and understanding why the check-then-insert pattern has a race condition. Candidates who've deployed webhooks in production (Stripe, Razorpay, JusPay) will immediately recognize these as real operational lessons, not textbook theory.
