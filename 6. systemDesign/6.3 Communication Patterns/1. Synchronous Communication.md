# Synchronous Communication: REST, gRPC, GraphQL — Tradeoffs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals and Mental Model

**Q1. What is the single most important question to ask before choosing between REST, gRPC, and GraphQL?**
A: "Who is the client and how well do you control both sides of the API?" REST is designed for the open web where the server can't control its clients — any HTTP client in any language can call it with no setup. gRPC is designed for controlled, trusted service-to-service calls where both sides share a `.proto` contract and go through a build pipeline. GraphQL is designed for client-driven APIs where the client's data requirements are heterogeneous, not fully predictable, and differ significantly across clients (mobile vs desktop vs third-party). The answer to this question — open web / heterogeneous uncontrolled clients vs controlled internal services vs client-driven flexible queries — eliminates two of the three options almost immediately in most real design scenarios.

**Q2. What is the underlying transport each protocol uses and why does it matter?**
A: All three ride on TCP, but at different HTTP layers, and this affects performance, infrastructure compatibility, and feature sets:
- **REST** (typically): HTTP/1.1 by convention, though nothing prevents HTTP/2. HTTP/1.1 means one request per TCP connection at a time (unless pipelining, which is poorly supported), or connection pooling (one connection reused for sequential requests, or a pool of connections for concurrency). The 6-connection-per-host browser limit is an HTTP/1.1 constraint that affects REST APIs serving browsers directly.
- **gRPC**: HTTP/2 exclusively and mandatorily. HTTP/2 provides multiplexing (many concurrent request/response pairs over one TCP connection), header compression (HPACK), server push, and binary framing. This is a hard requirement — gRPC cannot run over HTTP/1.1, which means any infrastructure that doesn't support HTTP/2 (older AWS ALBs, nginx without explicit HTTP/2 configuration, some corporate proxies) will block gRPC.
- **GraphQL**: typically HTTP/1.1 or HTTP/2 — it's agnostic about transport. GraphQL is an application-layer protocol, not a transport-layer one. Subscriptions (real-time) typically use WebSocket. GraphQL over HTTP is just a POST request to a single endpoint — it can run over any HTTP version.

**Q3. What is the fundamental contract model each protocol uses, and what does "contract" mean for each?**
A:
- **REST**: no mandatory contract. A REST API is described by its URL structure, HTTP methods, request/response JSON shapes, and status codes — but none of these are enforced by the protocol itself. OpenAPI/Swagger is an optional documentation standard that can generate client code, but there's no compile-time enforcement that a client and server are using compatible schemas. The contract is informal ("this endpoint returns this JSON shape") and validated only at runtime.
- **gRPC**: mandatory formal contract in a `.proto` file (Protocol Buffers IDL). The proto file is the source of truth — both client and server generate their code from it (using `protoc`). If client and server have incompatible proto files, mismatches are caught at code generation time (if the same file) or at the wire level via field number mismatch. The contract is formal, versioned, and machine-enforced.
- **GraphQL**: mandatory formal schema defined in SDL (Schema Definition Language) on the server. The schema specifies every type, field, query, mutation, and subscription. Clients write queries against this schema; the server validates every incoming query against it at runtime (queries that reference nonexistent fields fail at parse time, before execution). Client code can be generated from the schema, but GraphQL queries are strings sent at runtime — the contract is formal and runtime-enforced, but unlike gRPC, it doesn't require build-time code generation to use.

## Section 2: REST — Deep Dive

**Q4. What are the practical implications of REST's stateless constraint, and when does it become a problem?**
A: Statelessness means every request must carry complete context — the server stores no per-client session between requests. Practical implications: horizontal scaling is trivial (any server can handle any request, no session affinity needed); load balancers can freely route requests to any instance; server restarts don't affect in-progress sessions (there are none). Problems emerge when: (1) **authentication overhead**: every request must carry credentials (JWT, session cookie, API key) and validate them — no "the server knows who you are from context." JWTs are self-contained (no server lookup needed) but have size overhead; session IDs require a Redis or DB lookup per request; (2) **conversational workflows**: a multi-step wizard (step 1 → step 2 → step 3) can't rely on server-side state to remember step 1's context — either the client sends all context on each step, or the server must persist intermediate state explicitly (in a database), negating the statelessness benefit for complex workflows; (3) **server-side caching of computation**: since the server doesn't track the client's state, it can't remember a previous expensive computation for that client unless the response itself is HTTP-cached.

**Q5. What is "Richardson Maturity Model" and what does it mean for REST API quality?**
A: The Richardson Maturity Model (Leonard Richardson, 2008) describes four levels of REST implementation quality:
- **Level 0 (The Swamp of POX)**: one endpoint, everything is a POST, XML or JSON body determines the action. HTTP is just a transport tunnel. Example: `POST /api` with body `{"action": "getUser", "id": 42}`. Not REST at all — just HTTP-tunneled RPC.
- **Level 1 (Resources)**: multiple endpoints representing resources, but still mostly POSTing everything. Example: `POST /users` to get a user, `POST /orders` to create or list orders. Better, but HTTP verbs are ignored.
- **Level 2 (HTTP Verbs)**: proper use of HTTP methods (`GET` to read, `POST` to create, `PUT`/`PATCH` to update, `DELETE` to delete), proper status codes (201 Created, 404 Not Found, 409 Conflict). Most "REST APIs" in production are Level 2. Enables HTTP-layer caching (GET responses are cacheable), proper idempotency (DELETE is idempotent; POST is not), and standard error semantics.
- **Level 3 (Hypermedia Controls / HATEOAS)**: responses include links to related actions, enabling clients to discover the API dynamically without out-of-band documentation. Example: a `GET /orders/42` response includes `{"status":"shipped", "links":{"cancel":"/orders/42/cancel","track":"/orders/42/tracking"}}`. Almost never implemented in practice — adds complexity without commensurate benefit for most APIs. Worth knowing for interviews to demonstrate awareness that "pure REST" (Fielding's original vision) isn't what most people build.

**Q6. What are the most common REST API design mistakes that experienced engineers avoid?**
A:
- **Using GET for state-changing operations**: `GET /users/42/delete` — violates HTTP semantics, breaks caches (CDNs and browsers cache GET responses), and prevents clients from knowing the operation has side effects.
- **Returning 200 OK for errors**: `200 OK {"error": "user not found"}` — clients must inspect the body for every response to determine success. HTTP status codes exist precisely to communicate this: 404 Not Found.
- **Ignoring idempotency**: PUT and DELETE should be idempotent (calling them twice produces the same result as calling once). A DELETE that returns 404 on the second call is correct; a DELETE that returns an error saying "already deleted" and requires special handling is not.
- **Inconsistent naming**: `GET /getUsers` (verb in URL), `POST /create_order` (snake_case mixing), `GET /User/{id}` (PascalCase) — inconsistency increases cognitive load for API consumers.
- **Unbounded list responses**: `GET /events` returning all events with no pagination — at scale, this times out or returns enormous payloads. Always design pagination from the start (cursor-based for large/frequently-updated datasets, offset-based for simple cases).
- **Versioning in the wrong place**: putting version in the URL path (`/v1/users`) vs in headers (`Accept: application/vnd.myapi.v1+json`) — path versioning is simpler and more cache-friendly (different URL = different cache key); header versioning is "more RESTful" but invisible in URLs and harder to test.

**Q7. What are cursor-based vs offset-based pagination in REST APIs, and when does each fail?**
A: **Offset-based** (skip N, take M): `GET /orders?offset=100&limit=20`. Simple to implement, lets clients jump to any page. Fails at scale because: (1) large offsets require the database to scan and discard N rows before returning the next page — `OFFSET 1000000` on a 1M-row table is expensive; (2) if new items are inserted while a client is paginating, pages shift — a row inserted on page 1 while the client is on page 3 causes the client to see some rows twice and miss others.

**Cursor-based** (opaque token pointing to a position): `GET /orders?cursor=eyJpZCI6MTIzfQ&limit=20`. The cursor encodes a stable position (often a timestamp + ID tuple, base64-encoded). Next page: `cursor=eyJpZCI6MTQ1fQ`. Advantages: consistent results regardless of concurrent inserts (the cursor anchors to a specific row, not an offset); efficient at any depth (database uses a WHERE condition, not OFFSET); no page-drift from concurrent writes. Disadvantages: clients can't jump to page 50 directly (must paginate sequentially from the start); less intuitive for simple admin UIs. Cursor-based is the correct choice for any API serving clients that paginate through large, frequently-updated datasets (social feeds, event logs, audit records).

## Section 3: gRPC — Deep Dive

**Q8. What is Protocol Buffers (Protobuf) and why is binary serialization a significant advantage over JSON?**
A: Protocol Buffers is Google's language-neutral data serialization format, used as gRPC's wire format. A `.proto` file defines message types with typed, numbered fields:

```protobuf
syntax = "proto3";

message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
  repeated string roles = 4;
  google.protobuf.Timestamp created_at = 5;
}
```

The serialized binary format encodes each field as `(field_number << 3 | wire_type) + value` — no field names in the wire format, just numbers. Advantages vs JSON:
- **Size**: Protobuf is typically 3-10× smaller than equivalent JSON (no field name repetition per record, efficient varint encoding for integers, binary blobs for strings). For an API returning millions of small objects, 5× smaller payload = 5× less bandwidth = 5× less serialization CPU.
- **Speed**: Protobuf serialization/deserialization is typically 3-6× faster than JSON parsing. JSON parsing is character-by-character text processing; Protobuf decoding is fixed-width field extraction with type coercion.
- **Type safety**: the proto schema defines exact types (int64, float, bool, bytes, repeated, oneof) — no JSON type ambiguity (a JSON "number" could be int, float, or scientific notation; a proto `int64` is always a 64-bit signed integer).
- **Schema evolution**: fields are identified by number, not name. Adding a new field (field number 6) is backward compatible — old code ignores unknown field numbers; new code sees the value. Removing a field: old binary still works (the new code sees the field as absent/default). Changing a field name: non-breaking (only numbers matter on the wire).

**Q9. What are the four gRPC communication patterns and when is each used?**
A: gRPC's HTTP/2 foundation enables four call types, defined in the `.proto` file:

```protobuf
service OrderService {
  // 1. Unary: one request, one response
  rpc GetOrder(GetOrderRequest) returns (Order);

  // 2. Server streaming: one request, many responses
  rpc ListOrderUpdates(GetOrderRequest) returns (stream OrderUpdate);

  // 3. Client streaming: many requests, one response
  rpc UploadOrderBatch(stream Order) returns (BatchResult);

  // 4. Bidirectional streaming: many requests, many responses
  rpc OrderChat(stream ChatMessage) returns (stream ChatMessage);
}
```

- **Unary** (most common): standard request-response. Same semantics as a REST endpoint call.
- **Server streaming**: client sends one request; server sends a stream of responses. Use cases: live stock price feed for a specific symbol, streaming results of a large query (instead of waiting for all results), sending real-time notifications to a subscribed client.
- **Client streaming**: client sends a stream of requests; server accumulates and returns one response. Use cases: uploading a large file in chunks, streaming a batch of events for server-side aggregation, sending a sequence of commands that should be processed together.
- **Bidirectional streaming**: both client and server send streams independently and simultaneously. Use cases: chat messaging, real-time collaborative sessions, game state synchronization. The most powerful but also most complex to implement correctly (flow control, error handling, partial failure recovery).

**Q10. What are the practical deployment challenges of gRPC and how are they addressed?**
A: gRPC's HTTP/2 requirement creates specific infrastructure friction:
- **Browser clients**: browsers don't support raw HTTP/2 gRPC (the Fetch API doesn't expose the HTTP/2 framing needed for gRPC trailers). Solution: `grpc-web` — a proxy (typically Envoy) translates between gRPC-Web (a modified protocol browsers can speak) and backend gRPC. Adds a hop and some overhead; bidirectional streaming isn't fully supported in grpc-web.
- **L4 vs L7 load balancing**: gRPC multiplexes many RPCs over one long-lived HTTP/2 connection. An L4 load balancer routes per-connection — if a client maintains one persistent connection to the LB, all its RPCs go through one backend, defeating load balancing. Solution: L7 load balancing (Envoy, nginx with gRPC support) that understands HTTP/2 streams and can balance per-RPC across backends. This is the same issue covered in the L4/L7 load balancer guide.
- **Older AWS infrastructure**: AWS ALBs added gRPC support in 2020; NLBs pass TCP through and don't terminate HTTP/2 (so gRPC works but L7 balancing is not available). If using older ALBs or custom infrastructure, explicit HTTP/2 support must be verified.
- **Service mesh requirement for observability**: gRPC calls don't produce HTTP access logs the way REST does — the binary protocol requires a gRPC-aware proxy (Envoy/Istio) to observe and trace calls. This is often presented as a benefit (mesh provides observability) but is a hard dependency if the team doesn't already run a service mesh.
- **Firewall/proxy compatibility**: some corporate HTTP proxies strip or misinterpret HTTP/2 headers, causing gRPC connections to fail silently. gRPC falls back to long-polling in some environments, losing the performance benefits.

**Q11. What is gRPC's error model and how does it compare to HTTP status codes?**
A: gRPC uses a fixed set of 16 canonical status codes (defined in `google.rpc.Code`) that are more semantically precise than HTTP status codes for RPC scenarios:

| gRPC Status | Meaning | HTTP rough equiv |
|---|---|---|
| OK | Success | 200 |
| CANCELLED | Call was cancelled by the caller | 499 (client closed) |
| INVALID_ARGUMENT | Bad request parameters | 400 |
| DEADLINE_EXCEEDED | Timeout | 504 |
| NOT_FOUND | Resource doesn't exist | 404 |
| ALREADY_EXISTS | Resource already exists | 409 |
| PERMISSION_DENIED | Authorization failure | 403 |
| RESOURCE_EXHAUSTED | Rate limited / quota exceeded | 429 |
| FAILED_PRECONDITION | Operation not valid for current state | 400 / 422 |
| UNAVAILABLE | Service temporarily down (retry) | 503 |
| UNIMPLEMENTED | Method not implemented | 501 |
| INTERNAL | Internal server error | 500 |

The key advantage: `DEADLINE_EXCEEDED` vs `UNAVAILABLE` communicates very different retry semantics — `UNAVAILABLE` is safe to retry immediately (transient failure); `DEADLINE_EXCEEDED` means the server may have completed the operation (dangerous to retry a non-idempotent call). HTTP's `503` doesn't make this distinction. gRPC also supports an `ErrorDetails` extension via Protobuf `Any` to attach structured error metadata (field-level validation errors, retry hints, help links) to any status code — far richer than HTTP's body-based error conventions.

## Section 4: GraphQL — Deep Dive

**Q12. What is the N+1 query problem in GraphQL and how is it solved?**
A: The N+1 problem is GraphQL's most important performance issue. Consider a query fetching a list of posts and each post's author:

```graphql
query {
  posts {          # fetches N posts → 1 query
    title
    author {       # for each post, fetches 1 author → N queries
      name
    }
  }
}
```

A naive GraphQL resolver for `author` fetches one author per post, triggering 1 + N database queries (1 to fetch posts, N to fetch each author). With 100 posts, that's 101 queries vs the 2 that a well-written JOIN would produce. This is the N+1 problem.

**Solution — DataLoader (batching + caching)**:
DataLoader (open-sourced by Facebook) is the standard solution. It collects all the IDs that a resolver needs within one event loop tick, then issues a single batched query for all of them:

```javascript
const authorLoader = new DataLoader(async (authorIds) => {
  // Receives [1, 2, 3, ...N] author IDs accumulated from all resolver calls
  const authors = await db.query('SELECT * FROM users WHERE id IN (?)', [authorIds]);
  return authorIds.map(id => authors.find(a => a.id === id));
});

// Resolver — looks like it fetches one author, but DataLoader batches them
const resolvers = {
  Post: {
    author: (post) => authorLoader.load(post.authorId)
  }
};
```

The result: regardless of how many posts are returned, exactly 2 queries execute (1 for posts, 1 batched author query). DataLoader also caches within a request — if the same author_id appears for multiple posts, it's only fetched once. N+1 → 2 queries with DataLoader. Important to flag in interviews: N+1 is not unique to GraphQL (it's a common ORM problem too), but GraphQL's deeply-nested resolver model makes it especially easy to create inadvertently.

**Q13. How does GraphQL handle mutations, and what are the tradeoffs vs REST writes?**
A: GraphQL mutations are the write equivalent of queries — they modify server state and return the result:

```graphql
mutation {
  createOrder(input: {
    items: [{productId: "123", quantity: 2}]
    shippingAddress: {street: "123 Main St", city: "NYC"}
  }) {
    id
    status
    estimatedDelivery
    items { productId quantity price }
  }
}
```

The mutation's return type can include any fields from the affected resource — the client specifies exactly what it wants back, same as a query. This is a key advantage over REST: REST's POST to create an order typically returns the full order object (over-fetch) or just the ID (under-fetch, requiring a follow-up GET); GraphQL lets the client request exactly the fields it needs from the mutation result in one round-trip.

Trade-offs vs REST mutations: (1) **Ordering semantics**: multiple mutations in one GraphQL request execute sequentially in order — unlike queries, which may execute in parallel. This provides some consistency guarantees but prevents parallelization. (2) **Atomicity**: GraphQL has no built-in multi-mutation transaction semantics — if three mutations are sent and the second fails, the first has already committed. REST also lacks multi-endpoint atomicity, but the contrast is sharper in GraphQL where clients may bundle multiple writes in one document. (3) **Caching**: mutations, like queries, go to `POST /graphql` — HTTP-layer cache invalidation doesn't apply.

**Q14. What is GraphQL schema design and what are the most common schema design mistakes?**
A: The GraphQL schema is the complete contract between server and client — poor schema design has long-lasting consequences because clients build against it and changing it is a breaking change.

**Input/Output type separation**: use `input` types for mutation arguments, `type` for query outputs — don't reuse output types as mutation inputs (they often carry server-generated fields like `id`, `createdAt` that shouldn't be mutation inputs):

```graphql
# Wrong: using output type as input
mutation {
  createUser(user: User!) { ... }  # User has id, createdAt fields the client shouldn't set
}

# Correct: separate input type
input CreateUserInput {
  name: String!
  email: String!
}
type User {
  id: ID!
  name: String!
  email: String!
  createdAt: DateTime!
}
mutation {
  createUser(input: CreateUserInput!): User!
}
```

**Nullability**: every field in GraphQL is nullable by default. Excessive nullability forces clients to null-check every field defensively. Over-use of `!` (non-null) can cause the entire query to fail if one field resolver throws — even unrelated fields. The convention: mark fields non-null when the server guarantees they'll always be present (IDs, required attributes); leave nullable for optional or potentially-missing data.

**Nested mutations anti-pattern**: `mutation { user { updateProfile(...) } }` — mutations must be top-level. Nesting business logic arbitrarily deep in the schema makes it hard to reason about ordering and side effects.

**Q15. What is GraphQL query complexity and depth limiting, and why is it necessary for production APIs?**
A: Because GraphQL lets clients specify arbitrary queries, a malicious or naive client can craft a query that triggers enormous server work:

```graphql
# Depth bomb: each level fans out
query {
  users {
    friends {
      friends {
        friends {
          friends { name }  # O(N^4) database queries
        }
      }
    }
  }
}
```

Or a width bomb requesting thousands of fields in one query. Unlike REST where each endpoint has fixed work, GraphQL's flexibility means unbounded query complexity is a genuine DoS vector.

Production mitigations: (1) **Query depth limiting**: reject queries deeper than N levels (typically 5-10). Simple to implement (count nesting depth before execution); (2) **Query complexity limiting**: assign a cost to each field (e.g., 1 for a scalar, N for a list, custom cost for expensive resolvers) and reject queries above a complexity budget; (3) **Field count limiting**: reject queries requesting more than N total fields; (4) **Persisted queries** (most effective for internal/mobile APIs): only pre-approved, server-registered queries are accepted — arbitrary query strings are rejected. This transforms the API from "any query at runtime" to "a known set of queries" — eliminating the DoS vector but losing the flexibility advantage that motivated using GraphQL in the first place (appropriate trade-off for internal or mobile apps where the client is controlled).

**Q16. What is the Apollo Federation / schema stitching pattern and what problem does it solve?**
A: In a microservices architecture, each service owns its domain's data. Naive GraphQL deployment gives each service its own GraphQL API — but clients would need to know which service owns which data and make separate calls. Schema stitching (older approach) and Apollo Federation (current standard) solve this by creating a unified GraphQL API that spans multiple services:

```
Client → GraphQL Gateway (unified schema)
             ↓              ↓               ↓
         User Service   Order Service  Product Service
         (Users type)  (Orders type)  (Products type)
```

Apollo Federation uses `@key` directives in each service's schema to declare ownership of types and the ability to extend types from other services:

```graphql
# In Order Service schema
type Order @key(fields: "id") {
  id: ID!
  userId: ID!
  user: User  # References User type owned by User Service
}

extend type User @key(fields: "id") {
  id: ID! @external
  orders: [Order]  # Extends User type with orders field
}
```

The Gateway receives a client query, builds a query plan (which sub-queries to send to which services, in what order), and stitches the results. This allows a single GraphQL API for the entire platform while services remain independently deployable. The trade-offs: the Gateway becomes a new point of failure and performance bottleneck; cross-service queries add latency (multiple sub-service round-trips); schema coordination across teams is required (who owns which type, how do extension fields get approved and deployed).

## Section 5: Direct Comparison

**Q17. How do REST, gRPC, and GraphQL compare on performance under different traffic patterns?**
A: Performance comparison depends heavily on context:

**Payload size (small objects, high frequency)**:
gRPC + Protobuf wins clearly. A user object serialized as:
- JSON (REST/GraphQL): ~200 bytes text
- Protobuf (gRPC): ~40-60 bytes binary

At 100k requests/second, that's 140-160MB/sec less bandwidth for gRPC, reducing network cost, serialization CPU, and memory allocation. For very small payloads the difference narrows; for large, field-rich objects the difference widens.

**Latency (single request, internal services)**:
gRPC: ~1-5ms (HTTP/2 multiplexing amortizes connection overhead; Protobuf parsing is fast)
REST: ~5-20ms (HTTP/1.1 requires connection establishment per pool slot; JSON parsing overhead)
GraphQL: ~5-20ms baseline + N+1 risk (if DataLoader not implemented correctly)

**Throughput under concurrency**:
gRPC HTTP/2 multiplexing allows thousands of concurrent RPCs over one connection — ideal for high-concurrency microservice mesh. REST HTTP/1.1 is limited by connection pool size (often 50-200 connections per backend pair). REST over HTTP/2 narrows this gap significantly.

**Mobile/weak network (large round-trips expensive)**:
GraphQL wins — one request to get exactly the data needed for one screen, vs multiple REST round-trips. The reduced round-trip count matters more than payload size on high-latency mobile connections.

**Q18. How does caching work differently across REST, gRPC, and GraphQL?**
A: Caching is where REST has a clear, structural advantage:

**REST**: cache keys are URLs + HTTP method + `Vary` headers. `GET /products/42` is unambiguously cacheable at the HTTP level. CDNs, reverse proxies (Varnish, NGINX), and browsers cache GET responses automatically based on `Cache-Control` headers. A REST product catalog API fronted by CloudFront serves repeat reads from the CDN edge with zero backend load. This is the HTTP caching model described extensively in the CDN and cache invalidation guides — REST was designed to exploit it.

**gRPC**: no built-in HTTP-level caching (Protobuf binary over HTTP/2 can't be trivially key-cached by standard CDN infrastructure). Caching must be implemented at the application layer (response caching in the service or in a Redis sidecar). Some gRPC frameworks support response caching with custom headers, but it's non-standard and not supported by CDN infrastructure. Safe unary gRPC calls can theoretically be cached, but the tooling is immature.

**GraphQL**: all operations go to `POST /graphql` (or occasionally `GET /graphql` with the query as a URL parameter). POST requests are not cacheable by HTTP infrastructure — CDNs and proxies won't cache them. Application-level caching options: (1) Apollo Client's normalized client-side cache (caches by type + ID, shares data across queries that overlap on the same entity); (2) persisted queries on CDN (a specific query hash → response is cacheable as a GET, if the server supports GET-based persisted query execution); (3) DataLoader (per-request, not cross-request); (4) Redis response cache per query hash at the server (coarse-grained, not entity-aware). The caching story for GraphQL is significantly weaker than REST at the infrastructure layer, which is a genuine cost for high-traffic public APIs.

**Q19. How does each protocol handle breaking vs non-breaking schema changes?**
A:

**REST**:
Non-breaking: add new optional fields to response (clients ignore unknown fields); add new optional query parameters; add new endpoints. Breaking: remove fields, change field types, change URL structure, change HTTP method semantics. Standard practice: URL versioning (`/v2/users`) for breaking changes; multiple API versions maintained simultaneously until clients migrate. The informal contract means no automated detection of breaking changes — manual API changelog discipline required (or OpenAPI diff tooling).

**gRPC/Protobuf**:
Non-breaking: add new fields with new field numbers; add new RPC methods; change a singular field to a `repeated` (in most cases); change between compatible numeric types (`int32` → `int64`). Breaking: change a field's type incompatibly; reuse a field number for a different type; rename a field (names don't matter on the wire, but generated code changes); remove a required field (proto2 only — proto3 has no required). Protobuf's field-number-based evolution means adding fields is always backward compatible — old binaries ignore unknown field numbers; new binaries treat missing fields as defaults. This is a structural advantage: non-breaking evolution happens without API versioning machinery.

**GraphQL**:
Non-breaking: add new types, add nullable fields to existing types, add new arguments with defaults, deprecate fields (`@deprecated`). Breaking: remove types or fields, change field types, add non-null fields without defaults, remove enum values. The `@deprecated` directive enables a soft deprecation signal without breaking existing clients. The challenge: GraphQL has no standard versioning mechanism — the community convention is "never version, evolve the schema additively" (Shopify's practice). When a breaking change is unavoidable, the options are: (1) run two schemas simultaneously on different endpoints (complex); (2) use the `@deprecated` pattern to retire fields after a monitoring period showing no client usage. Facebook's production practice: monitor field usage via telemetry, deprecate, wait 90 days, then remove.

**Q20. How does each protocol handle authentication and authorization?**
A:
**REST**: authentication via standard HTTP mechanisms — `Authorization: Bearer <JWT>`, `Authorization: Basic <base64>`, API key via header or query param. Authorization enforced per-endpoint (route-level middleware checks permissions before handler runs). Clean and well-understood; HTTP middleware ecosystems (Express middleware, Spring Security interceptors) handle auth declaratively. Field-level authorization is the application developer's responsibility in the handler.

**gRPC**: metadata (analogous to HTTP headers) carries credentials: `authorization: Bearer <JWT>` in gRPC metadata. Interceptors (server-side middleware) validate metadata before the RPC handler runs. Authorization can be enforced per-RPC method or per-field within the handler. gRPC's channel-level TLS + metadata-level JWT is the standard pattern. The typed contract also enables role-based method-level authorization in the interceptor (`GetUserProfile` requires `user` role; `AdminDeleteUser` requires `admin` role).

**GraphQL**: authentication at the transport level (JWT in `Authorization` header, same as REST). Authorization is more complex — the flexible query model means clients can request any combination of fields, and some fields may require different permissions. Authorization patterns: (1) **resolver-level**: each resolver checks permissions — granular but scattered across the codebase; (2) **directive-based**: `@auth(role: ADMIN)` directives in the schema, centralized but requires framework support (e.g., `graphql-shield`); (3) **middleware / schema transform**: a layer that wraps resolvers and injects authorization logic. The GraphQL authorization story is more complex than REST precisely because the per-field query flexibility doesn't map cleanly to per-endpoint authorization. Field-level data security (user X can see their own email but not other users' emails, even though both appear in the `User` type) requires explicit resolver-level enforcement that's easy to forget in a large schema.

## Section 6: Versioning Strategies

**Q21. What are the REST API versioning strategies, and what are the operational trade-offs of each?**
A:
- **URI versioning** (`/v1/users`, `/v2/users`): most widely adopted. Explicit in URLs, CDN-cacheable (different URL = different cache key), easy to test (just change the URL). Downside: clients must change URLs when upgrading; multiple versions must be maintained simultaneously ("version deprecation" requires coordinating with all clients). The V in the URL is also technically non-RESTful (a resource should have one canonical URL).
- **Header versioning** (`Accept: application/vnd.myapp.v2+json`): "more RESTful" — the URL represents the resource; the header represents the representation format. Same cache invalidation burden as URI versioning, but invisible in URLs (harder to test with curl, Postman, etc.). Not supported by most CDN-level caching (CDNs don't vary cache by arbitrary `Accept` values unless explicitly configured with `Vary` headers).
- **Query parameter** (`/users?version=2`): simple but mixes version routing with business parameters. CDN-cacheable if the CDN includes query parameters in the cache key (often the default, but not universal).
- **Request body field** (a version field in the POST body): rare, breaks cacheable GET semantics, generally considered poor practice.

Operational recommendation for most teams: URI versioning for breaking changes (clear, cacheable, tooling-friendly); additive evolution (new optional fields, new endpoints) without version bumps; sunset period with `Deprecation` and `Sunset` headers for removed endpoints.

**Q22. How does gRPC handle service evolution across client and server versions?**
A: gRPC's evolution model relies entirely on Protobuf's backward/forward compatibility guarantees:

**Backward compatibility** (old client → new server): the new server can add new fields and new RPC methods. An old client's stub code ignores unknown fields in responses (Protobuf skips unknown field numbers). Old clients that don't call new RPC methods are completely unaffected.

**Forward compatibility** (new client → old server): the new client might send requests with new optional fields. The old server ignores unknown field numbers in the request — the new fields are simply absent from the server's processing. Old servers that don't implement new RPC methods return `UNIMPLEMENTED` — the new client must handle this gracefully.

**Breaking changes that require migration**:
- Removing an existing RPC method: old clients calling it get `UNIMPLEMENTED`. Requires coordinating deprecation.
- Changing a field's wire type (type 0 varint → type 2 length-delimited): the receiver misparses the field. This is the one truly dangerous evolution — Protobuf won't detect it as an error; it will silently produce garbled data. Field number retirement (marking a number as reserved: `reserved 3;`) prevents accidental field number reuse.

The practical workflow: proto files are stored in a shared repository; a CI check (`buf breaking`) compares any proto change against the last committed version and flags breaking changes before they merge.

## Section 7: Choosing in Practice

**Q23. Walk through a concrete system — an e-commerce platform — and derive which protocol to use for each communication pair.**
A: An e-commerce platform with multiple components illustrates how the choice differs by use case:

**Mobile app → API Gateway (public-facing)**:
**GraphQL**. Mobile apps have heterogeneous screens (product listing: needs thumbnail, name, price; product detail: needs full description, reviews, inventory, images). GraphQL's per-query field selection eliminates over-fetching for bandwidth-constrained mobile. One request per screen instead of multiple REST calls. Client drives the data shape.

**Browser → CDN → Static Asset Service**:
**REST** (or just HTTP). Static assets (JS, CSS, images) are served over plain HTTP with aggressive caching. No gRPC, no GraphQL needed for static content.

**Order Service → Payment Service** (internal):
**gRPC**. Both are internal services under the company's control, both have build pipelines, both need reliable, typed, low-latency communication. `ProcessPaymentRequest` → `PaymentResult` is a clearly defined unary RPC. The proto contract prevents mismatches; Protobuf binary is 5× smaller than JSON for high-frequency payment calls. Bidirectional streaming isn't needed; a streaming pattern could be used for `SubscribeToPaymentUpdates` if needed.

**Recommendation Service → Product Service** (internal, read-heavy, cacheable):
**REST or gRPC**. If product data changes slowly and responses can be cached (Redis or in-process TTL cache), REST is simpler and the cache makes the JSON overhead negligible. If product data is high-churn or queries are complex typed requests, gRPC is better.

**Backend Services → Notification Service** (fan-out, async):
**Neither** (async message queue — Kafka or SQS). A synchronous call from Order Service to Notification Service creates temporal coupling. If Notification Service is slow or down, Order Service suffers. This is the event-driven async pattern from the communication patterns guide — not REST, gRPC, or GraphQL.

**Q24. "A startup with 3 backend engineers is building a new product. They ask which API protocol to start with. What's your recommendation and reasoning?"**
A: Start with REST, structured for future evolution. Reasoning:

**Developer productivity today matters more than protocol perfection**: REST requires no build pipeline changes (no proto compilation step), no schema definition before writing a single endpoint (start with an endpoint, document it in OpenAPI later), and every engineer and consumer already knows how to use it (curl, Postman, browser fetch API). gRPC's build pipeline overhead (proto files, code generation, HTTP/2 infrastructure, grpc-web proxy for browser clients) adds days of setup with no user-visible benefit at 3-engineer/early-startup scale.

**REST evolves well to a point**: at startup scale (< 1M requests/day), REST's serialization overhead and connection management costs are negligible. The performance argument for gRPC only materializes at meaningful scale (10M+ requests/day, hundreds of microservices) — by which time the team will have more engineers, cleaner service boundaries, and the time to invest in gRPC for specific high-frequency internal paths.

**When to add GraphQL**: when the front-end team starts complaining about multiple round-trips per screen and the mobile team starts complaining about downloading fields they don't use. Not at 3 engineers — not enough clients with divergent data needs to justify it.

**When to add gRPC**: when a specific internal service pair has profiling evidence that JSON serialization and HTTP/1.1 connection overhead is measurable and impactful. Not at startup scale.

**Q25. What is the "BFF" (Backend for Frontend) pattern and how does it inform the protocol choice?**
A: The Backend for Frontend pattern (Sam Newman, 2015) creates a separate backend service (BFF) tailored to each client type (mobile BFF, web BFF, third-party API BFF), rather than a single generic API serving all clients:

```
Mobile App → Mobile BFF → [internal gRPC services]
Web App    → Web BFF    → [internal gRPC services]
Partners   → Public API → [internal gRPC services]
```

Protocol implications: the BFF-to-client interface uses the client's preferred protocol (REST or GraphQL for external clients; gRPC for internal services); the BFF-to-internal interface uses gRPC universally for typed, efficient internal communication. This pattern resolves the "which protocol to use?" question into "which protocol is right for each interface?": always gRPC internally; REST for public/partner APIs (simpler, better ecosystem support, cacheable); GraphQL at the BFF layer if clients have heterogeneous data needs. Many large companies (Netflix, Spotify, SoundCloud) have independently arrived at this layered approach, making it a well-validated architecture to propose in interviews.

## Section 8: Scenario-Based Questions

**Q26. "Your REST API is used by 500+ external partners. Response payloads average 15KB. You're receiving complaints about slow mobile performance. What are the first three changes you'd investigate, without changing the API protocol?"**
A: In order of investigation priority and impact:

**1. Field filtering / sparse fieldsets**: add `?fields=id,name,price` support (JSON:API style) so partners/mobile clients can request only the fields they need. If the 15KB response is a product object with 80 fields and mobile only displays 10, this alone could reduce payload to 2KB — a 7.5× reduction with one query parameter. No breaking change to existing clients; they continue getting full responses by default.

**2. Compression**: verify `Accept-Encoding: gzip` or `br` (Brotli) is supported and enabled. JSON is highly compressible (60-80% reduction typical on text/JSON). A 15KB JSON response compresses to ~3-5KB. If the API is running without Content-Encoding (some internal setups skip compression to reduce server CPU), enabling gzip/Brotli at the nginx/CDN layer with no application code change reduces bandwidth immediately.

**3. Pagination / response splitting**: if 15KB is driven by large arrays (e.g., all related items embedded), enforce pagination (`?limit=20`) and return IDs or references for related resources instead of full nested objects. Combine with HTTP `Link` headers for cursor-based navigation.

If after these three the payload is still too large and mobile performance is still poor, that's the moment to seriously evaluate adding a mobile BFF (with REST or GraphQL) that pre-shapes responses for mobile clients — not changing the existing partner API.

**Q27. "An interviewer asks: your team is migrating from REST to gRPC for internal microservices. What are the three hardest parts of the migration?"**
A:
**1. Proto schema design and governance**: every existing REST endpoint must be modeled as a proto message and RPC method. This reveals implicit assumptions in existing REST APIs — REST's "return whatever fields are convenient" must become explicit typed proto messages. Fields that were stringly-typed (`"status": "active"` as a string) become enum values (requiring a shared proto enum). Getting 10 teams to agree on shared proto types, naming conventions, and how to handle backward compatibility without a versioning mechanism is a significant coordination cost that REST's looser coupling avoided. Set up a shared proto repository and a `buf lint` CI check before writing any service-specific protos.

**2. Load balancer and infrastructure changes**: existing REST infrastructure (nginx, HAProxy, AWS ALB) may not support HTTP/2 in gRPC mode — requires verifying HTTP/2 support everywhere in the request path, upgrading LB configuration, and potentially deploying Envoy as a per-service sidecar to handle gRPC-aware L7 load balancing. Each service pair that migrates to gRPC needs to re-validate its entire network path supports HTTP/2 end-to-end.

**3. Debugging and observability regression**: REST traffic is trivially observable — `curl`, browser DevTools, `tcpdump` with text parsing all work. Protobuf binary is opaque to standard HTTP debugging tools. The migration requires establishing gRPC-aware observability before it can be trusted in production: distributed tracing (Jaeger/Zipkin with gRPC interceptors), gRPC status code metrics in Prometheus (not just HTTP status codes), and a Protobuf-aware reflection endpoint or Envoy tap to inspect actual request/response payloads during incidents. Until this is in place, on-call engineers will be flying blind when gRPC calls fail.

**Q28. "Design the API layer for a social media feed. 200M daily active users, each loading their feed up to 20 times per day. The feed changes frequently. Both a mobile app and a web app consume it."**
A: The feed loading pattern — heterogeneous clients, per-user data, high-frequency read — is a multi-constraint optimization problem:

**Client-facing API**: **GraphQL at a BFF (Backend for Frontend)** layer. Mobile and web have different display requirements (mobile: 3 fields per post; web: 10 fields + sidebar widgets). GraphQL's per-query field selection serves both without over-fetching. Mobile saves bandwidth; web gets richer data — one endpoint, two queries. Feed queries are specific and predictable enough to use persisted queries (pre-registered query strings), enabling CDN-level GET-based caching of recent feed data per cursor position (if feed data isn't per-user but follows a pattern).

**BFF → Internal services**: **gRPC**. Feed ranking service, user profile service, media service, and interaction counts service are all internal. gRPC's typed contracts and low-latency binary protocol handle the high-frequency internal fan-out that assembling a feed requires. Streaming gRPC for the feed ranking service (server streams ranked post IDs as they're computed) reduces time-to-first-post.

**Caching strategy**: feeds are per-user (not shareable across users at the edge). Application-level per-user feed caching in Redis (cache the pre-assembled feed for 30-60 seconds — longer TTL is stale; shorter is wasteful). At 200M DAU × 20 loads/day = 4B feed loads/day ≈ 46k/second. Even a 30-second Redis TTL absorbs the vast majority of loads per user into cache hits, reducing fan-out to internal services to ~1 per user per 30 seconds = ~6.6M/day to the ranking service — 600× reduction in internal load.

**Real-time updates (new posts appearing in feed)**: not covered by GraphQL query/mutation — use GraphQL subscriptions (WebSocket-based) or SSE from the BFF to notify clients when significant feed updates are available, triggering a re-query. This is the notification that "your feed has new content" — the client then makes a GraphQL query to fetch the new posts.

## Quick Reference Table

| Dimension | REST | gRPC | GraphQL |
|---|---|---|---|
| Transport | HTTP/1.1 or 2 | HTTP/2 (mandatory) | HTTP (any version), WS for subscriptions |
| Payload format | JSON (text) | Protobuf (binary) | JSON (text) |
| Schema/contract | Optional (OpenAPI) | Mandatory (.proto) | Mandatory (SDL schema) |
| Code generation | Optional | Mandatory (stubs) | Optional (can generate) |
| Type safety | Runtime (JSON) | Compile-time (proto) | Runtime (schema validation) |
| Browser support | Native | Via grpc-web proxy | Native |
| HTTP caching | Excellent (GET-based) | Poor (non-standard) | Poor (all POST) |
| Streaming | Limited (chunked) | First-class (4 modes) | Subscriptions (WebSocket) |
| Versioning | URL/header/query | Field numbers (additive) | Additive + @deprecated |
| Error model | HTTP status codes | 16 gRPC status codes | HTTP codes + errors array |
| Best for | Public/partner APIs | Internal microservices | Heterogeneous client APIs |
| Avoid when | High-freq internal calls | Browser clients | Simple fixed-shape APIs |

**Tip for interviews:** Five things separate strong candidates on REST/gRPC/GraphQL tradeoffs: (1) being able to explain **why gRPC can't be cached at CDN** and why REST's GET-based caching is a structural advantage — not just saying "REST is easier to cache" but understanding that HTTP caching is keyed on URL + method, which gRPC/GraphQL violate; (2) knowing the **N+1 problem and DataLoader** by name and mechanism (Q12) — this is the most common GraphQL production issue and almost every interviewer with GraphQL experience will ask about it; (3) explaining **gRPC's four streaming patterns** (Q9) and when each is appropriate — this distinguishes candidates who've used gRPC seriously from those who've only read about it; (4) knowing that **gRPC requires HTTP/2 everywhere** and articulating the infrastructure implications (L7 load balancing, no CDN caching, browser client proxies) — these are the real migration costs that matter; and (5) being able to propose **the BFF pattern** (Q25) to resolve the "which API to use" question into "which API for which interface" — this demonstrates systems thinking that generalizes the question rather than picking one protocol as universally correct.
