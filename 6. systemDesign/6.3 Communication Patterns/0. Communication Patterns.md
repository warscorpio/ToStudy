# Communication Patterns in System Design — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a communication pattern and why does choosing the right one matter for system design?**
A: A communication pattern defines how two or more components in a distributed system exchange data — the protocol, the timing model (synchronous vs asynchronous), the delivery semantics (at-most-once, at-least-once, exactly-once), the coupling between components, and how failures in one component affect the other. Choosing the wrong pattern produces systems that are: too tightly coupled (a slow consumer cascades failures to a fast producer), too loosely coupled (you lose the ability to know if an operation succeeded), over-engineered (a message queue between two services that never need decoupling), or under-engineered (REST calls between microservices that create temporal coupling and retry storms). The right pattern depends on latency requirements, reliability needs, coupling tolerance, throughput, ordering guarantees, and the nature of the data being exchanged — not on familiarity or what the team already knows.

**Q2. What is the fundamental distinction between synchronous and asynchronous communication?**
A: In synchronous communication, the sender blocks and waits for the receiver to process the request and return a response before proceeding — the sender's execution is paused for the duration of the operation. The sender and receiver must both be available at the same time. In asynchronous communication, the sender dispatches a message and immediately continues — it does not wait for the receiver to process the message or return a result. The sender and receiver do not need to be available simultaneously; the message may be queued and processed later. The trade-off: synchronous communication provides immediate feedback (success or failure) and is simple to reason about, but creates temporal coupling (both parties must be up) and propagates latency (the caller waits for the slowest chain link). Asynchronous communication decouples availability and speeds up the sender, but complicates result handling (how does the sender learn the outcome?) and error recovery.

**Q3. What are the three fundamental coupling dimensions that communication pattern choice affects?**
A: 
- **Temporal coupling**: must both parties be available at the same time? Synchronous (REST, gRPC) = high temporal coupling (both must be up for the call to succeed). Asynchronous (message queue, event stream) = low temporal coupling (producer publishes, consumer processes later even if producer is down).
- **Behavioral coupling**: does the sender need to know what the receiver does with the data? Request-response = high behavioral coupling (the sender expects a specific response). Pub/sub = low behavioral coupling (the publisher has no knowledge of subscribers or what they do with the event).
- **Data format coupling**: must both parties agree on the same schema? RPC (gRPC/Thrift) with generated stubs = high format coupling (shared schema definition). REST with informal documentation = moderate. Schemaless messaging (raw JSON) = low coupling but runtime errors replace compile-time errors.

Reducing coupling along all three dimensions improves independent deployability and fault tolerance — but increases operational complexity, observability difficulty, and eventual-consistency reasoning burden.

## Section 2: Request-Response

**Q4. What is the request-response pattern and when is it the right choice?**
A: Request-response is the synchronous call-and-reply pattern: a client sends a request, waits for the server to process it, and receives a response. The call is atomic from the client's perspective — either the server processed it and returned a result (success or domain error), or the call failed (timeout, network error, server error). Right choice when: the client needs the result immediately to proceed; the operation is short-lived (< a few seconds in duration); the operation is naturally transactional and the caller needs confirmation before continuing; the use case is read-heavy (the caller needs data back from the server, not just to trigger side effects). Examples: fetching a user profile, querying search results, submitting a payment with immediate confirmation, an HTTP API for a mobile app.

**Q5. How does REST implement the request-response pattern and what are its core constraints?**
A: REST (Representational State Transfer) is an architectural style for HTTP-based request-response APIs, defined by Roy Fielding in 2000. Six constraints:
- **Stateless**: every request must contain all information needed to process it — the server holds no session state between requests. Enables horizontal scaling (any server can handle any request).
- **Client-server separation**: client and server evolve independently.
- **Cacheable**: responses must declare whether they're cacheable, enabling intermediate caching layers (CDN, browser cache, reverse proxy).
- **Uniform interface**: resources are identified by URIs, manipulated via standard HTTP methods (GET, POST, PUT, PATCH, DELETE), representations (JSON/XML) are self-describing, and (ideally) hypermedia links guide further navigation (HATEOAS — rarely fully implemented in practice).
- **Layered system**: clients don't know (or need to know) if they're talking to the real server or an intermediary.
- **Code on demand (optional)**: server can send executable code to clients (JavaScript).

REST's strengths: widely understood, excellent tooling, leverages HTTP caching and CDN infrastructure, human-readable for debugging, flexible schema evolution. Weaknesses: over-fetching (getting more fields than needed), under-fetching (multiple round-trips to get related data), no strong schema contract enforcement, no built-in streaming.

**Q6. What is GraphQL and what problem does it solve that REST doesn't?**
A: GraphQL is a query language for APIs and a runtime for executing those queries, developed by Facebook in 2012 (open-sourced 2015). It solves two core REST problems:
- **Over-fetching**: a REST endpoint for `/users/:id` returns all fields; a client needing only `name` and `email` gets the full object. GraphQL clients specify exactly which fields they need in the query — only those fields are returned.
- **Under-fetching**: a REST client needing a user's profile + their recent orders + their addresses makes 3 separate API calls. A GraphQL query can fetch all of this in one request:

```graphql
query {
  user(id: "42") {
    name
    email
    orders(last: 5) { id total status }
    addresses { street city country }
  }
}
```

GraphQL's additional features: strongly typed schema (enables IDE autocomplete, compile-time query validation), subscriptions (real-time updates via WebSocket, built into the protocol), introspection (clients can query the schema itself). Weaknesses: complex caching (a single `/graphql` endpoint receives all requests; traditional URL-based CDN caching doesn't apply — requires query-aware caching or persisted queries); N+1 query problem (naively resolving each nested field triggers redundant database queries — mitigated by DataLoader/batching); higher server complexity than REST; not easily cacheable at the HTTP layer; overkill for simple APIs with fixed data shapes.

**Q7. What is gRPC and how does it differ from REST for service-to-service communication?**
A: gRPC (Google Remote Procedure Call) is a high-performance, contract-first RPC framework using Protocol Buffers (Protobuf) for serialization and HTTP/2 as the transport. Compared to REST:

| Dimension | REST | gRPC |
|---|---|---|
| Protocol | HTTP/1.1 (typically) | HTTP/2 (always) |
| Payload format | JSON (text, human-readable) | Protobuf (binary, compact) |
| Contract | Informal (OpenAPI/Swagger optional) | Mandatory `.proto` schema |
| Code generation | Optional (OpenAPI generators) | Mandatory (gRPC stubs from `.proto`) |
| Streaming | HTTP chunked (limited) | Bidirectional streaming (native) |
| Browser support | Native | Limited (requires grpc-web proxy) |
| Performance | Moderate (JSON parsing overhead) | High (binary serialization, HTTP/2 multiplexing) |
| Error model | HTTP status codes (imprecise) | Rich status codes + details |

gRPC excels for internal microservice communication: the contract-first `.proto` schema generates client/server stubs in any language, eliminating manual HTTP client code; Protobuf is 3-10× smaller than equivalent JSON; HTTP/2 multiplexing allows many concurrent calls over one connection; bidirectional streaming enables real-time data flows. Weaknesses: not human-readable (Protobuf is binary), requires code generation in build pipeline, browser clients need a proxy layer, `proto` schema changes require careful versioning to maintain backward compatibility.

## Section 3: Asynchronous Communication

**Q8. What is a message queue and how does it implement asynchronous communication?**
A: A message queue is a durable, ordered buffer between a producer and a consumer. The producer writes messages to the queue and immediately returns — it doesn't wait for the consumer to process them. The consumer reads from the queue at its own pace. Key properties: (1) **decoupling** — producer and consumer don't know about each other, don't need to be up simultaneously, and can be independently scaled; (2) **buffering** — the queue absorbs bursts (if producer runs at 10k msg/sec for a minute but the consumer only handles 8k msg/sec, the queue absorbs the 2k/sec difference temporarily); (3) **durability** — messages are persisted until acknowledged by the consumer, so a consumer crash doesn't lose the work; (4) **one consumer per message** — in a standard point-to-point queue, each message is consumed by exactly one consumer instance (work queue pattern). Classic implementations: AWS SQS, RabbitMQ (AMQP), ActiveMQ, Azure Service Bus.

**Q9. What is the difference between a message queue (point-to-point) and a publish-subscribe pattern?**
A: These are two distinct models for routing messages:

**Point-to-point (message queue)**: one producer, one consumer (or a competing consumer group where each message goes to exactly one consumer). The queue holds messages until exactly one consumer processes and acknowledges each message. Used for: distributing work items across a pool of workers, where each unit of work should be done once (task queues, job dispatch, order processing).

**Publish-Subscribe (pub/sub)**: one producer (publisher), multiple consumers (subscribers). Every subscriber receives every message — the same message is delivered to all subscribers independently. Used for: broadcasting events to multiple independent consumers (an order created event delivered to inventory, billing, notifications, and analytics services simultaneously, each consuming their own copy).

The key distinction: point-to-point = competing consumers, one wins per message; pub/sub = all subscribers receive all messages. Most real message brokers (Kafka, RabbitMQ, SNS/SQS) support both patterns or a combination.

**Q10. What is Apache Kafka and how does its model differ from a traditional message queue?**
A: Kafka is a distributed log / event streaming platform that differs from traditional message queues in fundamental ways:
- **Log-based storage**: Kafka retains all messages as an immutable, ordered log for a configurable retention period (days to forever). This is unlike SQS/RabbitMQ, which delete messages after acknowledgment. Any consumer can re-read historical messages by replaying from an earlier offset.
- **Consumer groups**: instead of competing consumers (one message → one consumer), Kafka uses consumer groups where each partition is assigned to exactly one consumer in the group, and multiple groups can independently consume the same topic from their own offset positions. One topic can be consumed simultaneously by a billing service (consumer group A), a notifications service (consumer group B), and an analytics service (consumer group C) — each maintaining their own cursor, never interfering with each other.
- **Topic partitions**: a topic is split into N partitions, each an independent ordered log. Parallelism = partition count. A consumer group can have at most as many active consumers as there are partitions (extra consumers sit idle).
- **Ordering guarantee**: strict ordering within a partition; no cross-partition ordering guarantee. Messages with the same partition key always go to the same partition, maintaining relative order for that key.
- **High throughput**: sequential disk I/O (append-only log), zero-copy kernel optimization, and batching give Kafka millions of messages/second throughput that traditional queues can't match.

**Q11. What are "at-most-once", "at-least-once", and "exactly-once" delivery semantics, and what does each cost?**
A:
- **At-most-once**: messages may be lost but are never processed twice. Implemented by acknowledging before processing — if the consumer crashes between ack and processing, the message is lost. Lowest overhead. Appropriate for: metrics/telemetry where dropping occasional data points is acceptable, fire-and-forget notifications.
- **At-least-once**: messages are never lost but may be processed more than once (if a consumer processes a message but crashes before acknowledging, the broker redelivers it). Requires idempotent consumers (processing the same message twice must produce the same result as processing it once). Most common in production — the default for Kafka consumers and SQS with visibility timeouts. Appropriate for: most business workflows, assuming the consumer is made idempotent (e.g., using the message ID as a deduplication key).
- **Exactly-once**: each message is processed exactly once — no loss, no duplication. The hardest guarantee to provide. Requires end-to-end coordination between producer, broker, and consumer (Kafka provides this via transactional producers + exactly-once semantics (EOS) using `enable.idempotence=true` and transactional APIs; SQS provides it partially via deduplication IDs in FIFO queues). High overhead — 2-10× latency overhead vs at-least-once. Appropriate for: financial transactions, inventory adjustments, any operation that is genuinely non-idempotent and where duplication causes real harm.

## Section 4: Event-Driven Architecture

**Q12. What is event-driven architecture (EDA) and how does it differ from request-driven architecture?**
A: In request-driven architecture, a service directly calls another service when it needs it to do something — the caller knows the callee, waits for the response, and couples the two services' availability. In event-driven architecture, services emit events describing what just happened (past tense — "OrderCreated", "UserSignedUp", "PaymentProcessed"), and other services subscribe to the events they care about and react independently. The event producer has no knowledge of, or dependency on, any consumer — it simply records that something happened. This creates a fundamentally different dependency graph: instead of Service A → Service B → Service C (a chain where each link must be up), you have: Service A emits "OrderCreated" → [Inventory Service, Billing Service, Notifications Service, Analytics Service] each independently consume and react. No service is tightly coupled to any other; each can be deployed, scaled, and failed independently.

**Q13. What is the difference between an "event" and a "command" and why does it matter?**
A: A **command** is a message that says "please do X" — it's imperative, directed at a specific recipient, and the sender expects the recipient to fulfill it: `CreateOrder`, `SendEmail`, `RefundPayment`. Commands imply the sender has authority over the receiver and knows what should happen. A **event** is a message that says "X happened" — it's a fact, in past tense, addressed to nobody in particular: `OrderCreated`, `EmailSent`, `PaymentRefunded`. Events describe history; they don't prescribe future action. This distinction matters for system design because: commands create tight coupling (the sender must know the exact service to call and what it should do); events enable loose coupling (any number of services can independently decide how to react to the fact that an order was created). Martin Fowler summarizes this as the difference between "the sender telling the receiver what to do" vs "the sender telling the world what happened."

**Q14. What is the "outbox pattern" and what problem does it solve in event-driven systems?**
A: A common problem: a service must atomically update its database AND publish an event — if the database commit succeeds but the event publish fails (or vice versa), the system is inconsistent. The outbox pattern solves this by making the event publishing part of the database transaction:
1. The service writes both the business entity change AND the event to an "outbox" table in the same database transaction (atomically).
2. A separate "relay" process (or a CDC tool like Debezium) reads from the outbox table and publishes events to the message broker, then marks them as published.
3. Since the outbox write and the business write are in one transaction, they succeed or fail together — consistency is guaranteed.

```sql
BEGIN TRANSACTION;
  UPDATE orders SET status = 'CONFIRMED' WHERE id = 42;
  INSERT INTO outbox (event_type, payload) VALUES ('OrderConfirmed', '{"order_id": 42}');
COMMIT;
-- Relay process reads outbox and publishes to Kafka
```

This is the standard pattern for microservices that need reliable event emission without distributed transactions. It trades the complexity of a distributed transaction for the simpler guarantee: "if the database commit succeeded, the event will eventually be published."

## Section 5: Real-Time Communication Patterns

**Q15. What is long-polling and how does it simulate real-time updates over HTTP?**
A: Long-polling is a technique for receiving server-push events over standard HTTP without WebSockets. The client sends a request; the server holds the connection open (without responding) until an event occurs or a timeout expires, then responds. The client immediately issues a new request, creating a perpetual cycle:

```
Client: GET /updates (request 1)
Server: [holds connection open...]
        [event occurs 45 seconds later]
Server: 200 OK { "event": "new_message" }
Client: immediately issues GET /updates (request 2)
Server: [holds connection open...]
```

Advantages: works through any HTTP infrastructure (proxies, firewalls, CDNs) without special support; simpler than WebSockets. Disadvantages: a new TCP connection per cycle (HTTP/1.1 overhead; HTTP/2 mitigates this); server must hold thousands of open connections (one per active client); additional latency for events that arrive just after a request was sent (client must complete the cycle before seeing the event); not truly bidirectional (client must send a new request to send data). Appropriate for: systems where real-time latency can tolerate 100ms-1s (not financial trading or multiplayer gaming), where WebSocket infrastructure isn't available, or where client support for WebSockets isn't guaranteed (certain corporate firewalls block WebSocket upgrades).

**Q16. What are Server-Sent Events (SSE) and how do they compare to WebSockets?**
A: SSE is a unidirectional HTTP streaming protocol — the server sends a stream of events to the client over a persistent HTTP connection, using the standard HTTP response body with `Content-Type: text/event-stream`. Unlike long-polling, the server doesn't close and reopen the connection — one connection streams many events over time. Unlike WebSockets, SSE is unidirectional (server → client only) and uses plain HTTP (works through any HTTP/2-capable infrastructure):

```
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"type": "price_update", "symbol": "AAPL", "price": 189.50}\n\n
data: {"type": "price_update", "symbol": "GOOGL", "price": 140.20}\n\n
```

Advantages over WebSockets: simpler protocol (plain HTTP), automatic reconnection built into the browser SSE API, works through all HTTP proxies without special configuration, HTTP/2 multiplexing allows many SSE streams on one connection. Disadvantages: server-to-client only (client must use separate HTTP requests for server-bound data); limited browser support for sending data alongside an SSE subscription. Best use cases: live feeds (news, stock prices, sports scores), real-time dashboards, notification streams — any scenario where the server pushes updates to clients but clients don't need to simultaneously send data at high frequency.

**Q17. What are WebSockets and when do they justify the added complexity vs SSE or long-polling?**
A: WebSockets provide a full-duplex, persistent, bidirectional communication channel between client and server over a single TCP connection. The connection begins as an HTTP request (the "upgrade" handshake) and then switches to the WebSocket protocol — bypassing HTTP's request-response framing entirely. Both sides can send messages at any time, in either direction, with very low overhead (2-10 bytes of framing per message, vs HTTP's 100s of bytes of headers per request).

When WebSockets justify the complexity:
- **Bidirectional, high-frequency communication**: multiplayer games (client sends player position 30 times/second; server sends other players' positions 30 times/second); collaborative editing (user keystrokes in real-time, cursor positions from other editors).
- **Latency-sensitive real-time features**: financial trading platforms where order book updates must arrive in < 50ms and the client also submits orders over the same connection.
- **Chat applications**: both parties send messages at any time without a request-response cycle.

When WebSockets are overkill: SSE suffices for unidirectional server-push at moderate frequency (news feeds, notification badges, dashboard metric updates). Long-polling suffices when events are infrequent (once every few seconds or minutes) and connection overhead isn't critical. The WebSocket protocol requires stateful connection management (each client has a persistent connection to a specific server instance, complicating horizontal scaling unless you use a pub/sub broker or sticky sessions), infrastructure support (some corporate firewalls and older proxies block WebSocket upgrades), and more complex server infrastructure (one open file descriptor per connected client, requiring async I/O or lightweight threads).

**Q18. What is a webhook and how does it implement asynchronous callback communication?**
A: A webhook is a user-defined HTTP callback — when a specific event occurs in system A, system A sends an HTTP POST request to a URL that system B pre-configured ("the webhook endpoint"). It's the inverse of polling: instead of system B repeatedly asking "did anything happen yet?", system A proactively notifies system B the moment something happens. Example: Stripe sends a POST to `https://yourapp.com/webhooks/stripe` when a payment succeeds; GitHub sends a POST to your CI system's endpoint when a commit is pushed. 

Webhooks are asynchronous (system A doesn't wait for system B to process the notification before continuing), loosely coupled (system A only knows B's URL, not what B does with it), and simple to implement (standard HTTP POST). Key reliability challenges: (1) system B may be down when the webhook arrives — system A must implement retry logic with exponential backoff; (2) system B must be idempotent — retries mean the same webhook can arrive multiple times; (3) system B must validate that the webhook actually came from system A (HMAC signature verification on the payload, using a shared secret — without this, anyone can POST to your endpoint and trigger actions). Appropriate for: third-party integrations where system A (the SaaS vendor) controls the event emission and system B is the customer's system; low-to-moderate event volume (not millions of events per second); when both systems are HTTP-accessible.

## Section 6: Streaming Communication

**Q19. What is stream processing vs batch processing as a communication paradigm?**
A: Batch processing: collect data over a time window, then process the entire batch at once (e.g., nightly ETL jobs). Simple, high-throughput, can reprocess in bulk. Latency equals the batch interval — hours for nightly, minutes for micro-batch. Stream processing: process each event as it arrives, continuously, with very low latency (milliseconds to seconds). Data is treated as a continuous, unbounded sequence of events rather than a bounded dataset. The fundamental shift: instead of "process these N records," stream processing means "for every record that arrives, apply this transformation/aggregation." Frameworks: Apache Flink (stateful stream processing, exactly-once semantics, event-time windowing), Apache Spark Structured Streaming (micro-batch, simpler fault tolerance, integrates with Spark ecosystem), Apache Kafka Streams (library, runs inside the application, Kafka-only), AWS Kinesis Data Analytics. Stream processing is appropriate when: latency requirements are under a few minutes, events must trigger real-time reactions (fraud detection on transactions, real-time recommendation updates, live dashboards), or the data is inherently unbounded (you can never "wait for all the data" because new events always arrive).

**Q20. What is event sourcing and how does it use communication patterns?**
A: Event sourcing is an architectural pattern where the state of a system is derived by replaying an ordered log of immutable events, rather than being stored as a current-state snapshot. Instead of `UPDATE orders SET status='shipped' WHERE id=42`, you append `OrderShipped {order_id:42, timestamp:..., carrier:...}` to the event log. The current state is computed by replaying all events from the beginning (or from a cached snapshot + events since the snapshot). Event sourcing is inherently tied to event-driven communication: events are both the storage format AND the communication mechanism — other services subscribe to the event log and derive their own read models (projections) from the events. Advantages: complete audit history, time travel (replay to any point in time), easy event-driven integration with other services, debugging by replaying events. Challenges: eventual consistency between the event log and read models (projections may lag), query complexity (must build and maintain read-side projections for every query pattern), event schema evolution (old events must remain interpretable as the schema evolves). Often implemented with Kafka as the event log and separate read-model databases per service (CQRS pattern).

**Q21. What is CQRS (Command Query Responsibility Segregation) and how does it relate to communication patterns?**
A: CQRS separates the read model (queries) from the write model (commands) in a system, typically using different data stores optimized for each. The write side accepts commands, validates them, and emits events. The read side subscribes to events and maintains denormalized, query-optimized read models (projections). Communication pattern: the write side and read side communicate exclusively through events on a message bus/event log (never direct calls) — this is event-driven communication at the service-internal level, not just inter-service. Example: an e-commerce order service accepts `PlaceOrderCommand` (write side — normalizes into domain events, stores in a write DB optimized for transactional integrity), emits `OrderPlaced` event, which the read side consumes to update a denormalized `orders_by_customer` read model (optimized for dashboard queries). The practical benefit: the write store (normalized, transactional) and the read store (denormalized, query-optimized — possibly Elasticsearch or Redis) are each optimized for their specific access pattern. The cost: eventual consistency between write and read (a command is processed, but the read model takes milliseconds to seconds to update), added architectural complexity, more services to operate and monitor.

## Section 7: Service Mesh Communication

**Q22. What is a service mesh and how does it change inter-service communication?**
A: A service mesh is an infrastructure layer that handles service-to-service communication transparently — typically implemented as a sidecar proxy (Envoy, Linkerd's proxy) deployed alongside every service instance, intercepting all inbound and outbound network calls without requiring application code changes. The mesh provides: (1) **mutual TLS (mTLS)** — all service-to-service calls are automatically encrypted and mutually authenticated, without any application TLS code; (2) **observability** — distributed tracing, metrics, and access logs for every service call automatically, without instrumentation; (3) **traffic management** — circuit breaking, retries with configurable backoff, load balancing (Envoy's LEAST_REQUEST), timeout enforcement, canary deployments by traffic percentage — all configured centrally via the control plane (Istio, Linkerd); (4) **service discovery** — the mesh handles discovering healthy endpoints via the control plane, removing the need for client-side service registry queries. The service mesh is a communication pattern in itself: it makes the "how do services communicate reliably" question an infrastructure concern rather than an application code concern.

**Q23. What is circuit breaking and why is it a critical communication pattern for distributed systems?**
A: Circuit breaking is a pattern that prevents a slow or failing downstream service from taking down callers by limiting the number of in-flight requests to that service. It mimics an electrical circuit breaker: when too many failures are detected, the circuit "opens," and subsequent calls immediately fail fast (return an error instantly, without actually calling the downstream service) until the downstream recovers. Three states:
- **Closed** (normal): calls flow through; failures are counted.
- **Open** (failing): calls immediately return an error without contacting downstream; a timer runs.
- **Half-open** (probing): after the timer expires, a small number of test calls are allowed through. If they succeed, the circuit closes; if they fail, the circuit re-opens.

Without circuit breaking: a slow downstream service causes every upstream caller to queue up connections waiting for responses, exhausting thread pools, connection pools, and memory — cascading the failure to the upstream service and beyond. With circuit breaking: after N% of calls fail in a window, the upstream immediately returns errors (or falls back to a default response) rather than waiting, protecting its own resources and giving the downstream time to recover. Implemented in: Hystrix (Netflix, now deprecated), Resilience4j, Envoy (outlier detection), Istio (circuit breaking via DestinationRule), application-level via libraries per service.

## Section 8: Communication Pattern Selection

**Q24. How do you choose between synchronous and asynchronous communication for a given interaction?**
A: A decision framework based on the requirements:

**Use synchronous (REST/gRPC) when:**
- The result is needed immediately to continue processing (a checkout page must know if the payment succeeded before confirming the order to the user).
- Latency requirements are tight and the dependency is reliably fast (< 100ms p99).
- The operation is a query (read) — you need data back.
- Failure must be immediately visible to the caller (payment processing, authentication).
- The interaction is simple enough that coupling is acceptable (a frontend calling a backend API).

**Use asynchronous (message queue/event stream) when:**
- The caller doesn't need the result immediately (an order confirmation email can be sent seconds later).
- The receiver may be slow or temporarily unavailable (backpressure absorption).
- The same event needs to trigger multiple independent consumers (an order placed event consumed by inventory, billing, and shipping independently).
- The operation is a write that may take longer than a user-acceptable wait time (video transcoding, report generation, ML inference).
- You need to decouple producer and consumer scaling (a payment service can accept 10k orders/sec from the queue at its own rate, regardless of whether the order service is producing 1k or 50k/sec).

**Q25. What is the "two generals problem" and why does it mean you can never have perfect guarantees in distributed communication?**
A: The Two Generals Problem (from computer science theory) illustrates the impossibility of guaranteed coordination over an unreliable channel: two generals need to coordinate an attack but can only communicate via messengers who may be captured. General A sends "attack at dawn" — but how does A know the message arrived? A waits for an acknowledgment. But how does B know A received the acknowledgment? B sends an ack of the ack. This regress has no end — no finite number of message exchanges can provide certainty over an unreliable channel. The distributed systems implication: you can never fully guarantee that both sides of a distributed communication have arrived at the same state. Every practical system accepts a trade-off: at-least-once delivery (accept occasional duplication), at-most-once delivery (accept occasional loss), or exactly-once semantics (accept the overhead and complexity of the approximation). The right response in a system design interview to "how do you guarantee X never happens?" is to quantify the probability ("the probability of both A and B failing within the acknowledgment window is 0.0001%") rather than claim absolute guarantees.

**Q26. What is backpressure and why is it critical in high-throughput communication?**
A: Backpressure is a flow-control mechanism where a slower consumer signals a faster producer to slow down, preventing the consumer from being overwhelmed. Without backpressure: a producer that generates 100k events/sec writing to a consumer that processes 20k events/sec will fill any intermediate buffer and eventually crash the consumer or cause memory exhaustion. With backpressure: the consumer signals to the producer (or the message broker signals to the producer) to reduce send rate or pause until capacity is available. Implementation approaches:
- **Pull-based systems (Kafka)**: the consumer controls its own consumption rate by controlling when it reads from the partition — natural backpressure, the broker just buffers up to its retention limit.
- **Reactive Streams (RxJava, Project Reactor, Akka Streams)**: standardized protocol (`Publisher`, `Subscriber`, `Subscription` interfaces) where the subscriber requests N elements at a time (demand signaling), preventing the publisher from overwhelming it.
- **TCP flow control**: the underlying TCP protocol implements backpressure via receive window size — if the receiver's buffer is full, it signals the sender to pause. This provides implicit backpressure for any TCP-based system, but at a lower level than is useful for application-level rate control.
- **Queue depth monitoring**: when a message queue's depth exceeds a threshold, alert and add consumer capacity (auto-scaling) or throttle producers at the application level.

## Section 9: Scenario-Based Questions

**Q27. "Design the communication pattern between a payment service and the downstream services that need to react to a successful payment (inventory update, send email receipt, update user loyalty points, trigger fulfillment)."**
A: This is a one-to-many, write-triggered, non-time-critical fan-out — a textbook event-driven async pattern. The payment service should not synchronously call four downstream services, because: any one of them failing would fail the payment API call to the user; their latency stacks (total wait = sum of all four); they're independent concerns with no ordering requirement.

**Architecture**: the payment service uses the outbox pattern (Q14) — atomically updates the payment record in its database AND writes a `PaymentSucceeded` event to an outbox table in one transaction. A relay process (Debezium CDC or a polling relay) reads the outbox and publishes to a Kafka topic `payments.succeeded`. Four independent consumer groups subscribe:
- `inventory-service` group: decrements stock.
- `email-service` group: generates and sends receipt email.
- `loyalty-service` group: credits loyalty points.
- `fulfillment-service` group: creates fulfillment order.

Each service consumes independently at its own pace, retries on failure independently, and scales independently. The payment service's API responds to the user as soon as the database transaction commits — not after all four downstream services complete. The user sees "payment successful" in < 200ms; the email arrives 2 seconds later; loyalty points update 5 seconds later; fulfillment is triggered 10 seconds later. All of this is the correct production behavior — there's no reason the user should wait for a receipt email before seeing "payment successful."

**Q28. "A junior engineer proposes using REST calls between all microservices for simplicity. You're building a system with 15 microservices handling 50k requests/sec at peak. What's your response?"**
A: REST between all microservices is a valid starting point for simple systems — but at 15 services and 50k req/sec, several failure modes emerge that warrant a different approach for specific interactions:

**Appropriate for REST**: user-facing read APIs (fetch product catalog, user profile, search results) where the response is needed synchronously and the downstream dependency is predictable and fast.

**Problematic with pure REST at this scale**: (1) **Synchronous chain latency**: a user request triggering A → B → C → D where each hop is 20ms means 80ms of chain latency minimum — plus any retry overhead; (2) **Cascading failures**: if D is slow (200ms instead of 20ms), A's threads are blocked waiting, exhausting A's thread pool, causing A to appear slow to its callers, and so on — a distributed deadlock; (3) **Tight temporal coupling**: all 15 services must be up for the user request to succeed; any one outage causes visible errors.

**Recommended evolution**: (1) Add circuit breakers (Resilience4j or Envoy) to all service-to-service REST calls immediately — limits cascade failure damage; (2) Move write-side fan-outs (events after an order is placed, payment processed) to async Kafka events — decouples the services that don't need to be synchronous; (3) Keep REST/gRPC for queries that genuinely need synchronous responses; (4) Add request timeouts and fallback responses for all downstream calls — "if the recommendation service times out, show default recommendations" is better than propagating the timeout to the user.

**Q29. "You need to implement real-time collaborative document editing (think Google Docs). What communication pattern do you use and why?"**
A: Collaborative editing requires: (1) very low latency (user keystrokes must appear to other users in < 100ms to feel real-time); (2) bidirectional (both client → server and server → client); (3) high-frequency (potentially hundreds of messages/second per active document); (4) ordered delivery (operations must be applied in a consistent order across all clients). This is the canonical WebSocket use case — the only communication pattern that satisfies all four requirements:

**Protocol**: WebSocket for client-server bidirectional streaming.
**Server-side**: a stateful server (or cluster of servers) maintains the current document state per open document. When a client connects, it subscribes to a "document room." Every operation (insert character, delete, format) is sent as a small WebSocket message from the client to the server.
**Conflict resolution**: Operational Transformation (OT, used by Google Docs) or CRDTs (Conflict-free Replicated Data Types, used by Figma, Notion) to handle concurrent edits from multiple clients — the server (for OT) or each client (for CRDTs) merges concurrent operations without requiring a global lock.
**Broadcast**: the server broadcasts each transformed operation to all other clients subscribed to that document room. For a cluster of servers, a pub/sub layer (Redis Pub/Sub, Kafka) broadcasts across server instances so clients on different servers all receive the update.
**Fallback**: for environments blocking WebSocket (rare), SSE for server→client plus HTTP POST for client→server — higher latency but functionally correct.

**Q30. "You're designing a system where a third-party SaaS vendor (payment processor) needs to notify your system when payment status changes. What are the trade-offs between webhooks and polling?"**
A: Both approaches have legitimate uses; the choice depends on volume, latency requirements, and operational control:

**Webhooks (vendor pushes to your endpoint)**:
- Pros: near-real-time notification (seconds after the event); your infrastructure isn't making repeated API calls; efficient (no traffic when nothing happens).
- Cons: your endpoint must be publicly reachable; you must handle vendor retry logic (if your service is down, does the vendor retry? How many times? Exponential backoff?); you must implement HMAC signature verification (reject forged webhooks); your endpoint must be idempotent (retries will arrive); if the vendor is down or misbehaving, you don't know — you're dependent on them calling you.

**Polling (you query vendor API on a schedule)**:
- Pros: you control the polling rate and retry logic; works even if your service was temporarily down (you catch up on the next poll); simpler infrastructure (no public endpoint needed).
- Cons: latency equals polling interval (polling every 60 seconds = up to 60 seconds to learn about a status change); inefficient at low event rates (most polls return nothing); burns vendor API rate limits.

**Recommended**: webhooks as the primary path for near-real-time updates, with a polling fallback (every 5-15 minutes) to catch events that webhooks may have missed during a downtime window. This is the standard pattern used by Stripe, GitHub, and most payment processors — they document that you should "reconcile using the API" in addition to relying on webhooks, precisely because webhook delivery cannot be 100% guaranteed.

**Tip for interviews:** Five things separate strong candidates on communication patterns: (1) framing every pattern choice around the **three coupling dimensions** (temporal, behavioral, data format) rather than just "sync vs async" — it's a more complete analysis; (2) knowing the **outbox pattern** (Q14) by name and being able to explain why a raw Kafka publish inside a database transaction isn't reliable — this is one of the most common real-world microservice reliability problems; (3) being precise about **delivery semantics** (at-most-once / at-least-once / exactly-once) and knowing that exactly-once requires end-to-end coordination with real overhead — the "just use exactly-once" answer isn't free; (4) knowing **when WebSockets are overkill** vs when they're necessary (Q17) — many candidates reach for WebSockets for any "real-time" feature, but SSE solves most unidirectional use cases with far less operational complexity; and (5) being able to design the **webhook + polling fallback** pattern for third-party integrations (Q30) — treating webhooks as "reliable delivery" without a reconciliation loop is a common production mistake that interviewers probe for.
