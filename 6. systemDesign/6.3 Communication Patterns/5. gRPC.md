# gRPC: Protocol Buffers, Unary, Server Streaming, Client Streaming, Bidirectional Streaming — Interview Q&A (5 YOE Level)

---

## Section 1: gRPC Fundamentals

**Q1. What is gRPC and what set of problems does it solve that plain REST doesn't?**
A: gRPC is Google's open-source RPC (Remote Procedure Call) framework that combines three technologies: Protocol Buffers (a binary serialization format for defining messages and services), HTTP/2 (for transport — multiplexing, header compression, bidirectional streaming), and a code generation toolchain (producing type-safe client/server stubs from `.proto` files in any supported language). The problems it solves that REST doesn't:

- **Formal, machine-enforced contract**: a `.proto` file is the single source of truth for the API. Client and server stubs are generated from it — no manual HTTP client code, no informal JSON schema documentation that drifts from the implementation. The contract is enforced at compile time (if the generated code compiles, the client and server agree on the schema).
- **Efficient binary serialization**: Protobuf is 3-10× smaller and 3-6× faster to serialize/deserialize than JSON. At high request volume, this is meaningful CPU and bandwidth savings.
- **Native streaming**: REST requires workarounds (chunked HTTP, SSE, WebSocket) for streaming. gRPC has four first-class call types (unary, server streaming, client streaming, bidirectional) defined in the proto file and implemented symmetrically in generated code.
- **Deadline propagation**: a gRPC deadline (absolute timestamp) is propagated through the entire call chain automatically — if Service A gives Service B a 100ms deadline, and B calls C, the remaining deadline automatically constrains C. REST has no equivalent mechanism.
- **HTTP/2 multiplexing**: many concurrent RPCs over one TCP connection — no connection-per-request overhead, no connection pool management complexity.

**Q2. What is the relationship between gRPC and Protocol Buffers — are they inseparable?**
A: They're designed together but technically separable. gRPC uses Protobuf by default for message serialization and for defining the service interface (the `.proto` IDL). However, gRPC is transport-agnostic at the serialization layer — you can use gRPC with JSON (grpc-gateway), MessagePack, or custom serialization via gRPC's `Codec` interface. In practice, nearly all production gRPC usage uses Protobuf, because:
1. Protobuf's type system (with `oneof`, `repeated`, `map`, `Any`) is richer than JSON's primitive types.
2. Generated stubs from `.proto` files assume Protobuf serialization by default.
3. The binary efficiency of Protobuf is one of gRPC's primary value propositions — using JSON would sacrifice this.

The correct framing for interviews: gRPC defines the *transport and call semantics* (HTTP/2, streaming modes, metadata, deadlines, error codes); Protobuf defines the *message schema* and *service interface*. Both are usually used together but serve distinct purposes.

## Section 2: Protocol Buffers — Deep Dive

**Q3. What is the Protocol Buffers wire format and why is it more efficient than JSON?**
A: Protobuf encodes each message field as a tag-value pair on the wire, where the tag encodes both the field number and the wire type in a single varint:

```
tag = (field_number << 3) | wire_type

Wire types:
0 = varint (int32, int64, uint32, uint64, sint32, sint64, bool, enum)
1 = 64-bit (fixed64, sfixed64, double)
2 = length-delimited (string, bytes, embedded messages, repeated fields)
5 = 32-bit (fixed32, sfixed32, float)
```

For a message `{id: 1, name: "Alice"}` defined as:
```protobuf
message User {
  int64 id = 1;
  string name = 2;
}
```

The binary encoding:
```
Field 1 (id=1):   tag=0x08 (field_number=1, wire_type=0), value=0x01
Field 2 (name):   tag=0x12 (field_number=2, wire_type=2), length=0x05, bytes="Alice"

Total: 9 bytes

JSON equivalent: {"id":1,"name":"Alice"} = 22 bytes
```

Efficiency sources:
- **No field names on the wire**: field names in Protobuf are only in the `.proto` file; the wire format uses 1-3 byte field number tags. JSON repeats field name strings in every encoded record.
- **Varint encoding**: small integers encode to 1-2 bytes; a JSON number `"1"` is always at least 1 character but numbers like `"1234567"` take 7 bytes; varint would encode this as 3 bytes.
- **No structural punctuation**: no `{`, `}`, `[`, `]`, `:`, `,` characters consuming bytes.
- **Binary, not text**: no UTF-8 character boundaries to respect, no escape sequences for special characters.

**Q4. What is the complete `proto3` syntax and what are the key differences from `proto2`?**
A: A complete `.proto` file showing common `proto3` patterns:

```protobuf
syntax = "proto3";

package ecommerce.v1;

option go_package = "github.com/company/proto/ecommerce/v1;ecommerce";
option java_package = "com.company.ecommerce.v1";

import "google/protobuf/timestamp.proto";
import "google/protobuf/any.proto";

// Enum: always start with the zero value
enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;  // zero value convention
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_CONFIRMED = 2;
  ORDER_STATUS_SHIPPED = 3;
  ORDER_STATUS_DELIVERED = 4;
  ORDER_STATUS_CANCELLED = 5;
}

// Basic message
message Address {
  string street = 1;
  string city = 2;
  string country_code = 3;  // snake_case field names
  string postal_code = 4;
}

// Message with common field types
message Order {
  string order_id = 1;          // string
  int64 user_id = 2;            // 64-bit integer
  OrderStatus status = 3;       // enum
  repeated OrderItem items = 4; // repeated = array
  Address shipping_address = 5; // nested message
  google.protobuf.Timestamp created_at = 6;  // well-known type
  map<string, string> metadata = 7;  // map<key_type, value_type>
  double total_amount = 8;      // float (double or float)
  bytes payment_token = 9;      // binary blob

  // oneof: exactly one of these fields may be set
  oneof delivery_method {
    string courier_code = 10;
    bool is_pickup = 11;
  }
}

message OrderItem {
  string product_id = 1;
  int32 quantity = 2;
  int64 unit_price_cents = 3;
}

// Service definition
service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc ListOrders(ListOrdersRequest) returns (stream Order);
  rpc CreateOrders(stream CreateOrderRequest) returns (CreateOrdersResponse);
  rpc OrderUpdates(stream OrderUpdateRequest) returns (stream OrderUpdate);
}

message GetOrderRequest {
  string order_id = 1;
}

message ListOrdersRequest {
  int64 user_id = 1;
  int32 page_size = 2;
  string page_token = 3;
}
```

Key `proto3` vs `proto2` differences:
- **All fields optional by default**: in `proto2`, fields are `required` or `optional` (explicit). In `proto3`, all fields are implicitly optional — missing fields get default values (0 for numbers, empty string, empty list). There is no `required` keyword in `proto3`.
- **Default values are always zero-values**: unset numeric fields are 0, strings are `""`, booleans are `false`, enums are 0. You cannot distinguish between "field not set" and "field set to zero" in `proto3` without using `google.protobuf.Int64Value` wrappers.
- **No `required` fields**: eliminates the forward-compatibility issue where `proto2`'s required fields would break old code if a required field was added.
- **Enum zero value must be defined**: convention is `FIELD_NAME_UNSPECIFIED = 0` to make the "not set" state explicit and safe.

**Q5. What are "field numbers" and why are they the cornerstone of Protobuf's backward/forward compatibility?**
A: Every field in a Protobuf message has a unique integer field number (1-536,870,911, with some ranges reserved). The field number — not the field name — is what appears on the wire. This is Protobuf's fundamental compatibility mechanism:

**Adding a new field**: give it a new field number never used before. Old decoders see an unknown field number, apply the "unknown field" rule (skip the field based on its wire type), and continue parsing. Old code doesn't know about the new field but doesn't fail. New code sees the field normally.

**Removing a field**: old encoders send the field; new decoders see an unknown field number and skip it. New encoders don't send the field; old decoders see it as absent (use the default value). No failures.

**The `reserved` keyword**: after removing a field, its field number should be marked as reserved to prevent future developers from accidentally reusing it (which would cause silent data corruption — old data with field number 3 meaning "user_age" would be misinterpreted as the new field 3 meaning "account_balance"):

```protobuf
message User {
  // user_age was removed, its number is reserved
  reserved 3;
  reserved "user_age";  // also reserve the name to prevent code using it

  string user_id = 1;
  string username = 2;
  // field 3 (user_age) removed — DO NOT reuse field number 3
  int64 created_at = 4;
}
```

**What is NOT backward compatible**: changing a field's type in a wire-incompatible way (e.g., changing from `int32` to `string` — the wire type changes, causing parse errors); changing an enum's zero value to a non-zero default; reusing a field number for a different type; removing an entry from an enum if old code uses that entry.

**Q6. What are Protobuf's well-known types and when should you use them?**
A: Protobuf ships with a standard library of commonly-needed types in the `google.protobuf` package. Using them ensures interoperability and avoids reinventing common patterns:

- **`google.protobuf.Timestamp`**: a point in time as `{seconds: int64, nanos: int32}` since Unix epoch. Use instead of a raw `int64` Unix timestamp (which loses type clarity) or a formatted string (which loses precision and parsing efficiency). JSON serialization renders as RFC 3339 (`"2024-01-15T09:30:00Z"`).
- **`google.protobuf.Duration`**: a span of time as `{seconds, nanos}`. Use for timeouts, intervals.
- **`google.protobuf.Any`**: a container for any Protobuf message type, identified by a type URL. Use for polymorphic fields where the type isn't known at compile time (error details, plugin payloads).
- **`google.protobuf.Struct`**: represents a JSON-like structure (`map<string, Value>` where Value can be bool, string, number, Struct, or ListValue). Use for truly schemaless data where you need JSON-equivalent flexibility within a Protobuf message.
- **Wrapper types** (`google.protobuf.Int64Value`, `google.protobuf.StringValue`, etc.): nullable wrappers for primitive types. In `proto3`, an unset `int64` is indistinguishable from a zero `int64`. Wrapping in `Int64Value` makes null representable. Use when "not set" vs "set to 0" is semantically meaningful.
- **`google.protobuf.Empty`**: an empty message for RPCs with no request or response payload. Use instead of creating a custom empty message.
- **`google.protobuf.FieldMask`**: a list of field paths representing a subset of fields. Used for partial updates (only update the fields in the mask) — the standard pattern for PATCH-like operations in gRPC.

## Section 3: Service Definition and gRPC Internals

**Q7. How does gRPC map onto HTTP/2, and what does a gRPC frame look like on the wire?**
A: A gRPC call is an HTTP/2 stream. The mapping:

- **gRPC method** (`/package.ServiceName/MethodName`) → HTTP/2 `:method: POST` + `:path: /ecommerce.v1.OrderService/GetOrder`
- **gRPC request headers** → HTTP/2 HEADERS frame (first frame of the stream)
- **gRPC request body** → HTTP/2 DATA frame with a 5-byte gRPC data frame prefix + serialized Protobuf
- **gRPC response headers** → HTTP/2 HEADERS frame
- **gRPC response body** → HTTP/2 DATA frames
- **gRPC trailers** (status code, metadata) → HTTP/2 HEADERS frame with `END_STREAM` flag

The 5-byte gRPC data frame prefix that wraps each Protobuf message:
```
Byte 0:    Compressed-Flag (0 = not compressed, 1 = compressed)
Bytes 1-4: Message-Length (big-endian uint32, length of the serialized Protobuf)
Bytes 5+:  Protobuf-encoded message bytes
```

This 5-byte prefix is what allows gRPC to frame individual messages within an HTTP/2 DATA frame stream — HTTP/2 DATA frames can be split across multiple TCP packets, and multiple Protobuf messages can span multiple DATA frames. The length prefix lets the gRPC runtime know exactly where one message ends and the next begins.

**Q8. What is gRPC metadata and how is it used in practice?**
A: gRPC metadata is key-value pairs attached to a gRPC call, analogous to HTTP headers. Metadata can be sent as:
- **Request metadata** (from client): sent with the initial HEADERS frame before the request body.
- **Response headers** (from server): sent before any response messages.
- **Response trailers** (from server): sent after all response messages, in the final HEADERS frame.

Common uses in production:
```go
// Client sending metadata (Go example)
md := metadata.Pairs(
    "authorization", "Bearer <jwt>",
    "x-request-id", "abc-123",
    "x-client-version", "2.1.0",
)
ctx := metadata.NewOutgoingContext(context.Background(), md)
response, err := client.GetOrder(ctx, &pb.GetOrderRequest{OrderId: "ord-42"})

// Server reading metadata
func (s *server) GetOrder(ctx context.Context, req *pb.GetOrderRequest) (*pb.Order, error) {
    md, ok := metadata.FromIncomingContext(ctx)
    if !ok {
        return nil, status.Error(codes.Unauthenticated, "no metadata")
    }
    authHeader := md.Get("authorization")
    requestId := md.Get("x-request-id")
    // ...
}
```

Binary metadata (for non-UTF-8 values): use keys ending in `-bin` (e.g., `trace-data-bin`). gRPC base64-encodes binary metadata values automatically.

**Q9. What is a gRPC interceptor (middleware) and what are its use cases?**
A: gRPC interceptors are middleware functions that wrap gRPC handlers — executed before and after each RPC call, on both client and server side. Analogous to HTTP middleware (Express.js middleware, Spring filters), but gRPC-specific and supporting streaming call types.

Unary server interceptor (Go):
```go
func authInterceptor(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
) (interface{}, error) {
    // Before: extract and validate auth token
    md, _ := metadata.FromIncomingContext(ctx)
    token := md.Get("authorization")
    if err := validateToken(token); err != nil {
        return nil, status.Error(codes.Unauthenticated, "invalid token")
    }

    // Execute the actual handler
    resp, err := handler(ctx, req)

    // After: log result
    log.Printf("RPC: %s, error: %v", info.FullMethod, err)
    return resp, err
}

// Register interceptor
server := grpc.NewServer(
    grpc.UnaryInterceptor(authInterceptor),
)
```

Production interceptor use cases:
- **Authentication/authorization**: validate JWTs, API keys, or mTLS certificates before any handler runs.
- **Distributed tracing**: inject trace IDs into context, create spans per RPC, propagate trace context via metadata (OpenTelemetry gRPC plugin).
- **Logging**: log every RPC's method name, request size, response size, duration, and status code.
- **Rate limiting**: count requests per client/method, reject with `RESOURCE_EXHAUSTED` when exceeded.
- **Request validation**: validate required fields, format constraints before handler runs.
- **Panic recovery**: catch panics in handlers, convert to `INTERNAL` status errors, log stack traces.
- **Deadline enforcement**: add a maximum server-side deadline regardless of what the client requests.

## Section 4: Unary RPC

**Q10. What is a unary RPC and what is its exact execution lifecycle?**
A: A unary RPC is the simplest gRPC call type: one request message, one response message — semantically identical to a function call. The complete lifecycle:

```
Client                         Server
  |                              |
  |─── HTTP/2 HEADERS ──────────►|  (method path, metadata, END_HEADERS)
  |─── HTTP/2 DATA ─────────────►|  (5-byte prefix + serialized request)
  |─── HTTP/2 DATA (END_STREAM) ►|  (signals client is done sending)
  |                              |
  |                              | [handler executes]
  |                              |
  |◄── HTTP/2 HEADERS ──────────|  (response metadata)
  |◄── HTTP/2 DATA ─────────────|  (5-byte prefix + serialized response)
  |◄── HTTP/2 HEADERS (trailers)|  (grpc-status, grpc-message, END_STREAM)
```

The `grpc-status` trailer is the canonical success/error indicator — `grpc-status: 0` means OK; any non-zero value is an error. The response body DATA frame may come before or after the response HEADERS frame (response metadata) but always before trailers.

**Q11. How does deadline propagation work in unary gRPC calls, and what makes it superior to HTTP timeouts?**
A: gRPC deadlines are absolute timestamps (not relative durations) propagated as the `grpc-timeout` header in the request metadata:

```go
// Client sets a 2-second deadline
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

resp, err := orderClient.GetOrder(ctx, req)
// If 2 seconds elapse, the context is cancelled, gRPC sends RST_STREAM
// and the handler on the server side receives context.DeadlineExceeded
```

Why this is superior to HTTP-level timeouts: when Service A calls Service B with a 100ms deadline, and B must call C to fulfill the request, B can compute the remaining budget (`deadline - now`) and pass it to C — ensuring C doesn't spend 90ms on work that Service A will never wait for anyway. In HTTP, each service would need to manually extract and recalculate timeout values, pass them via custom headers, and manually check them. In gRPC, the `context.Context` carries the deadline, and any gRPC call made with that context automatically propagates the remaining deadline to the downstream service — no manual calculation.

Server-side deadline checking:
```go
func (s *server) GetOrder(ctx context.Context, req *pb.GetOrderRequest) (*pb.Order, error) {
    // Check if context is already cancelled before expensive work
    if ctx.Err() != nil {
        return nil, status.FromContextError(ctx.Err()).Err()
    }

    // Perform DB lookup
    order, err := s.db.GetOrder(ctx, req.OrderId)  // ctx propagates deadline to DB query
    if err != nil {
        if ctx.Err() != nil {
            // Context cancelled during DB query
            return nil, status.Error(codes.DeadlineExceeded, "timed out fetching order")
        }
        return nil, status.Errorf(codes.Internal, "db error: %v", err)
    }
    return order, nil
}
```

**Q12. How does gRPC error handling work in unary calls, and what are the best practices for rich error details?**
A: gRPC errors are communicated via the `grpc-status` and `grpc-message` trailers. The status code is a numeric value from the 16-code canonical set; the message is a human-readable string for debugging (not for programmatic handling).

For rich, structured error information (field validation errors, retry hints, resource info), use `google.rpc.Status` with `details` containing typed `Any` extensions:

```go
import (
    "google.golang.org/grpc/status"
    "google.golang.org/grpc/codes"
    epb "google.golang.org/genproto/googleapis/rpc/errdetails"
)

func (s *server) CreateOrder(ctx context.Context, req *pb.CreateOrderRequest) (*pb.Order, error) {
    // Validation error with field-level details
    if req.Items == nil || len(req.Items) == 0 {
        st, _ := status.New(codes.InvalidArgument, "order validation failed").
            WithDetails(
                &epb.BadRequest{
                    FieldViolations: []*epb.BadRequest_FieldViolation{
                        {Field: "items", Description: "order must contain at least one item"},
                    },
                },
                &epb.Help{
                    Links: []*epb.Help_Link{
                        {Url: "https://docs.example.com/orders", Description: "Order API docs"},
                    },
                },
            )
        return nil, st.Err()
    }

    // Rate limit error with retry information
    if s.rateLimiter.Exceeded(ctx) {
        st, _ := status.New(codes.ResourceExhausted, "rate limit exceeded").
            WithDetails(
                &epb.QuotaFailure{
                    Violations: []*epb.QuotaFailure_Violation{
                        {Subject: "orders/user_id", Description: "100 orders per minute exceeded"},
                    },
                },
                &epb.RetryInfo{
                    RetryDelay: durationpb.New(30 * time.Second),
                },
            )
        return nil, st.Err()
    }
    // ...
}

// Client extracting error details
resp, err := client.CreateOrder(ctx, req)
if err != nil {
    st := status.Convert(err)
    for _, detail := range st.Details() {
        switch t := detail.(type) {
        case *epb.BadRequest:
            for _, v := range t.FieldViolations {
                log.Printf("Field: %s, Error: %s", v.Field, v.Description)
            }
        case *epb.RetryInfo:
            log.Printf("Retry after: %v", t.RetryDelay.AsDuration())
        }
    }
}
```

## Section 5: Server Streaming RPC

**Q13. What is a server streaming RPC, when should it be used, and what is its exact wire behavior?**
A: A server streaming RPC sends one request and receives a sequence of response messages from the server. The client's request is a single Protobuf message; the server sends any number of response messages before closing the stream.

Wire behavior:
```
Client                         Server
  |─── HEADERS ────────────────►|  (method + metadata)
  |─── DATA (END_STREAM) ───────►|  (single request, END_STREAM = client done)
  |                              |
  |◄── HEADERS ─────────────────|  (optional response metadata)
  |◄── DATA ────────────────────|  (response message 1)
  |◄── DATA ────────────────────|  (response message 2)
  |◄── DATA ────────────────────|  (response message N)
  |◄── HEADERS (END_STREAM) ────|  (trailers: grpc-status + grpc-message)
```

The server sends multiple DATA frames, each containing one complete gRPC message (5-byte prefix + Protobuf bytes). The stream ends when the server sends a HEADERS frame with `END_STREAM` (the trailers). The client reads messages until it receives the end-of-stream signal.

**Server streaming implementation (Go)**:
```go
// Proto definition:
// rpc ListOrderUpdates(ListOrderUpdatesRequest) returns (stream OrderUpdate);

func (s *server) ListOrderUpdates(
    req *pb.ListOrderUpdatesRequest,
    stream pb.OrderService_ListOrderUpdatesServer,
) error {
    // The stream argument replaces the return value
    ctx := stream.Context()

    for {
        // Check if client cancelled or deadline exceeded
        if ctx.Err() != nil {
            return status.FromContextError(ctx.Err()).Err()
        }

        update, err := s.orderRepo.NextUpdate(ctx, req.OrderId)
        if err == io.EOF {
            return nil  // no more updates, close stream normally
        }
        if err != nil {
            return status.Errorf(codes.Internal, "failed to get update: %v", err)
        }

        // Send a message to the client
        if err := stream.Send(update); err != nil {
            // Client disconnected or flow control blocked
            return err
        }
    }
}

// Client receiving the stream:
stream, err := client.ListOrderUpdates(ctx, &pb.ListOrderUpdatesRequest{OrderId: "ord-42"})
for {
    update, err := stream.Recv()
    if err == io.EOF {
        break  // stream closed normally
    }
    if err != nil {
        log.Fatalf("stream error: %v", err)
    }
    processUpdate(update)
}
```

**Appropriate use cases**: streaming large query results (avoid loading all rows into memory before responding), live data feeds (stock prices, real-time sensor data), progressive computation results (send partial results as they become available — like streaming ML inference outputs), log tailing.

**Q14. How does flow control affect server streaming, and what happens when the server sends faster than the client reads?**
A: HTTP/2's flow control mechanism (WINDOW_UPDATE frames) applies within gRPC server streaming. The receiver (client) advertises a receive window (initially 65,535 bytes); the sender (server) must stop sending when this window is exhausted and wait for the client to issue WINDOW_UPDATE frames (which it does as it processes and frees buffer space):

```
Server: sends 65,535 bytes → window exhausted
Server: stream.Send(message) BLOCKS — flow control prevents sending more
Client: processes messages, frees buffer → sends WINDOW_UPDATE (more window available)
Server: stream.Send() unblocks — can send again
```

From the server's perspective: `stream.Send()` is a blocking call that returns only when the message has been placed in the HTTP/2 send buffer. If the client is slow, `stream.Send()` blocks the goroutine/thread sending messages. The server application must handle this case: check the context for cancellation inside the loop (so a cancelled context unblocks a stuck `Send`), and monitor server-side goroutine count or streaming send latency.

Common production issue: server generates data faster than it sends (CPU-bound data generation), and the client reads slower than the server sends — causing the server's send goroutine to block, accumulating backlog in server memory. Monitor `stream.Send()` duration as a metric; if p99 send latency is high, the client is too slow or the client is constrained (slow network, slow processing).

## Section 6: Client Streaming RPC

**Q15. What is a client streaming RPC, when should it be used, and how does the server accumulate the stream?**
A: A client streaming RPC sends a sequence of request messages and receives a single response. The client sends messages until it calls `CloseAndRecv()` (or the equivalent in the target language); the server accumulates these messages and sends one final response.

Wire behavior:
```
Client                         Server
  |─── HEADERS ────────────────►|  (method + metadata)
  |─── DATA ────────────────────►|  (request message 1)
  |─── DATA ────────────────────►|  (request message 2)
  |─── DATA ────────────────────►|  (request message N)
  |─── DATA (END_STREAM) ───────►|  (last message + signals client done)
  |                              |
  |                              | [server processes accumulated stream]
  |                              |
  |◄── HEADERS ─────────────────|  (response metadata)
  |◄── DATA ────────────────────|  (single response)
  |◄── HEADERS (END_STREAM) ────|  (trailers)
```

**Client streaming implementation (Go)**:
```go
// Proto definition:
// rpc UploadOrderBatch(stream CreateOrderRequest) returns (BatchResult);

// Client: streaming multiple requests
func uploadOrders(client pb.OrderServiceClient, orders []*pb.CreateOrderRequest) error {
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    stream, err := client.UploadOrderBatch(ctx)
    if err != nil {
        return err
    }

    for _, order := range orders {
        if err := stream.Send(order); err != nil {
            return fmt.Errorf("send failed: %w", err)
        }
    }

    // Close the send direction and receive the single response
    result, err := stream.CloseAndRecv()
    if err != nil {
        return fmt.Errorf("CloseAndRecv: %w", err)
    }
    log.Printf("Batch result: %d created, %d failed", result.Created, result.Failed)
    return nil
}

// Server: receiving the stream
func (s *server) UploadOrderBatch(stream pb.OrderService_UploadOrderBatchServer) error {
    var created, failed int32
    ctx := stream.Context()

    for {
        req, err := stream.Recv()
        if err == io.EOF {
            // Client finished sending — send the single response
            return stream.SendAndClose(&pb.BatchResult{
                Created: created,
                Failed:  failed,
            })
        }
        if err != nil {
            return status.Errorf(codes.Internal, "recv error: %v", err)
        }
        if ctx.Err() != nil {
            return status.FromContextError(ctx.Err()).Err()
        }

        // Process each order as it arrives (streaming processing)
        if err := s.processOrder(ctx, req); err != nil {
            failed++
        } else {
            created++
        }
    }
}
```

**Appropriate use cases**: uploading large files in chunks (send each chunk as a separate message), submitting a batch of records where the client knows the count but the server returns only a summary, continuous data ingestion from a device that streams readings to a server for aggregation.

**Q16. What is the difference between batch-then-respond vs streaming-accumulate approaches on the server for client streaming?**
A: Two server-side patterns for handling client streaming:

**Batch-then-respond** (accumulate-then-process): the server receives all messages into a slice, then processes the complete batch at once:
```go
var allRequests []*pb.CreateOrderRequest
for {
    req, err := stream.Recv()
    if err == io.EOF { break }
    allRequests = append(allRequests, req)
}
// Process all at once — enables operations that need the full dataset
result := s.processBatch(ctx, allRequests)
return stream.SendAndClose(result)
```
Appropriate when: the operation requires the complete dataset (bulk database inserts with a transaction spanning all records, machine learning inference on a complete feature vector, data validation that cross-references records within the batch).

**Streaming-accumulate** (process-as-received): the server processes each message as it arrives, accumulating only summary state:
```go
var created, failed int32
for {
    req, err := stream.Recv()
    if err == io.EOF { break }
    if err := s.processOrder(ctx, req); err != nil {
        failed++
    } else {
        created++
    }
}
return stream.SendAndClose(&pb.BatchResult{Created: created, Failed: failed})
```
Appropriate when: each message can be processed independently (inserting records one at a time, each into its own transaction), or the server needs to handle very large streams without accumulating all records in memory.

The streaming-accumulate approach is almost always preferable: lower memory usage, consistent latency per message regardless of batch size, and enables the server to begin processing while the client is still sending (pipeline overlap).

## Section 7: Bidirectional Streaming RPC

**Q17. What is a bidirectional streaming RPC and what is unique about its concurrency model?**
A: A bidirectional streaming RPC allows both client and server to send streams of messages independently and simultaneously. Neither side waits for the other to finish — both can send at any time, and the stream closes when both sides signal completion. The critical point: **the two directions are independent** — the server can send 5 messages before reading any client message; the client can send 10 messages before the server sends its first reply.

Wire behavior:
```
Client                         Server
  |─── HEADERS ────────────────►|  (initial metadata)
  |─── DATA ────────────────────►|  (client message 1)
  |◄── HEADERS ─────────────────|  (server metadata, optional)
  |─── DATA ────────────────────►|  (client message 2)
  |◄── DATA ─────────────────────|  (server message 1)
  |─── DATA ────────────────────►|  (client message 3)
  |◄── DATA ─────────────────────|  (server message 2)
  |─── DATA (END_STREAM) ───────►|  (client done sending)
  |◄── DATA ─────────────────────|  (server message 3)
  |◄── HEADERS (END_STREAM) ─────|  (server done, trailers)
```

The concurrency model: both the client and server run two independent goroutines (or equivalent) — one for reading, one for writing. They share access to the stream object via the gRPC runtime's internal synchronization:

```go
// Server: bidirectional streaming
func (s *server) OrderChat(stream pb.OrderService_OrderChatServer) error {
    ctx := stream.Context()

    // Reading goroutine: receive client messages
    incomingMsgs := make(chan *pb.ChatMessage, 100)
    go func() {
        defer close(incomingMsgs)
        for {
            msg, err := stream.Recv()
            if err != nil {
                return  // EOF or error closes the channel
            }
            incomingMsgs <- msg
        }
    }()

    // Processing + writing: respond to each client message
    for {
        select {
        case msg, ok := <-incomingMsgs:
            if !ok {
                return nil  // client closed its send side
            }
            response := s.processMessage(msg)
            if err := stream.Send(response); err != nil {
                return err
            }
        case <-ctx.Done():
            return status.FromContextError(ctx.Err()).Err()
        }
    }
}
```

**Q18. What are the half-close semantics of bidirectional streaming and why do they matter?**
A: In bidirectional streaming, each direction can be closed independently — "half-close" means one side has finished sending but the other can still send:

**Client half-close**: when the client sends its last message with `END_STREAM` set (or calls `CloseSend()`), the server's `stream.Recv()` returns `io.EOF`. The server knows the client is done sending, but the server can still continue sending responses. The server's send side remains open.

**Server half-close**: when the server returns from its handler (returning `nil` or an error), the gRPC runtime sends a HEADERS frame with `END_STREAM` and the `grpc-status` trailer. The client's `stream.Recv()` returns the status (either `io.EOF` for OK or an error). The client knows the server is done.

Why this matters: a common pattern is "client sends a stream of requests, server processes each and sends a corresponding response, then client closes its send side, then server sends a final summary response":

```go
// Proto: rpc Process(stream Input) returns (stream Output);

// Client pattern:
stream, _ := client.Process(ctx)
for _, input := range inputs {
    stream.Send(input)           // send all inputs
}
stream.CloseSend()               // half-close: tell server we're done sending

for {
    output, err := stream.Recv()  // still receiving server responses
    if err == io.EOF { break }    // server closed its side
    processOutput(output)
}

// Server pattern:
func (s *server) Process(stream pb.Service_ProcessServer) error {
    for {
        input, err := stream.Recv()
        if err == io.EOF { break }  // client half-closed
        output := s.process(input)
        stream.Send(output)         // can still send after client half-closes
    }
    // Server closes when the handler returns
    return nil
}
```

Applications must explicitly handle half-close: a server that stops calling `stream.Recv()` after client sends `END_STREAM` but the server hasn't sent `END_STREAM` yet leaves the stream in a limbo state — the client is still waiting for server responses that will never come, until a deadline fires.

**Q19. What is the "chat pattern" vs the "request-response in stream" pattern for bidirectional streaming, and when does each make sense?**
A: Two distinct interaction models within bidirectional streaming:

**Chat pattern** (full duplex, no pairing between client and server messages): either side sends at any time, messages are independent. The client doesn't wait for a server response before sending another message. Used for: chat applications (users send messages; other users' messages arrive from the server; neither direction waits for the other), multiplayer game state synchronization (client sends player inputs; server sends game state updates; both happen at their own rate).

```
Client: input1, input2, input3
Server:           state1,      state2, state3
       (interleaved, no 1:1 correspondence)
```

**Request-response in stream** (paired, synchronous-like but over a stream): the client sends a request and waits for the server's response before sending the next request. This is logically equivalent to many sequential unary calls, but uses one persistent stream instead of many HTTP/2 connections — reducing connection setup overhead for high-frequency short interactions:

```
Client: req1      req2      req3
Server:     resp1     resp2     resp3
```

Used for: interactive query sessions (database query protocol), command-and-control protocols (send a command, receive the result, send the next command). More efficient than unary for high-frequency interactions because the HTTP/2 stream setup cost (HEADERS frame) is amortized once rather than paid per call.

## Section 8: Production Concerns

**Q20. What are the key gRPC load balancing considerations and why does gRPC break standard L4 load balancing?**
A: Covered at a high level in earlier guides — here is the deep technical explanation. gRPC uses HTTP/2 multiplexing: multiple RPCs are sent as HTTP/2 streams over one long-lived TCP connection. A standard L4 load balancer routes at the TCP connection level — once a gRPC client establishes a connection to backend A, all its RPCs (streams on that connection) go to backend A. Other backends receive RPCs only from clients whose connections were load-balanced to them at connection time.

The result: in a 10-backend cluster with 3 persistent client connections established, those 3 clients drive all load — and only 3 backends handle RPCs. The other 7 are idle. Round-robin at the connection level means even traffic only if connections are evenly distributed at connection time, which they usually aren't (clients connect at different times, some send more RPCs per connection than others).

The correct approach for gRPC load balancing:
1. **L7 gRPC-aware load balancing** (Envoy, grpc-web proxy, Istio): the proxy terminates the gRPC connection from the client and maintains a separate pool of backend connections, load-balancing at the HTTP/2 stream level (individual RPC level). Each RPC can go to any backend regardless of which client connection brought it to the proxy.

2. **Client-side load balancing**: the gRPC client library itself distributes RPCs across backend endpoints, using a discovery mechanism (DNS with multiple A records, xDS from Envoy control plane, or Kubernetes headless service DNS). The client opens connections to multiple backends and distributes RPCs via round-robin or `LEAST_REQUEST`. Used in: internal microservice meshes where all clients are under your control and can be configured with a resolver.

3. **gRPC with a service mesh (Istio/Linkerd)**: sidecar proxies handle gRPC-aware L7 load balancing transparently, without requiring client-side LB configuration changes.

**Q21. What is gRPC connection management — how are connections established, kept alive, and managed?**
A: gRPC manages connections through channels — an abstraction over one or more HTTP/2 connections to a backend:

**Channel states**: gRPC channels follow a state machine — IDLE (no recent activity), CONNECTING (attempting to establish), READY (connection established), TRANSIENT_FAILURE (connection attempt failed, will retry), SHUTDOWN (permanently closed).

**Connection keepalive** (`grpc.WithKeepaliveParams`): prevents connections from going half-open (the server crashes but the client's TCP stack doesn't notice):
```go
conn, err := grpc.NewClient(
    "server:50051",
    grpc.WithKeepaliveParams(keepalive.ClientParameters{
        Time:                10 * time.Second, // ping interval when idle
        Timeout:             5 * time.Second,  // wait for pong before declaring dead
        PermitWithoutStream: true,             // keepalive even with no active RPCs
    }),
)
```

The server must be configured to accept keepalives (otherwise it sends `ENHANCE_YOUR_CALM` / `GOAWAY` frames and closes the connection):
```go
server := grpc.NewServer(
    grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{
        MinTime:             5 * time.Second,  // min interval between client pings
        PermitWithoutStream: true,
    }),
    grpc.KeepaliveParams(keepalive.ServerParameters{
        MaxConnectionAge:      30 * time.Minute, // max connection lifetime
        MaxConnectionAgeGrace: 5 * time.Second,  // grace period for in-flight RPCs
        Time:                  10 * time.Second,
        Timeout:               5 * time.Second,
    }),
)
```

**`MaxConnectionAge`**: after a connection has been alive for this duration, the server sends a `GOAWAY` frame (politely closing the connection after in-flight RPCs complete). The client reconnects immediately, potentially to a different backend if multiple are available — effectively implementing connection-level load balancing without requiring a per-RPC L7 proxy. This is a common technique for improving L4 load balance over time in gRPC clusters.

**Q22. What is gRPC's cancellation model and how does it propagate?**
A: gRPC uses Go's `context.Context` (or language-equivalent) for cancellation propagation. When a client cancels a call (deadline exceeded, client disconnects, explicit cancel), the gRPC runtime sends an HTTP/2 `RST_STREAM` frame to the server with error code `CANCEL` (8). The server's `stream.Context().Done()` channel closes, and `stream.Recv()` returns an error containing the cancellation reason.

Critical for servers handling client streaming and bidirectional streaming: the server must check the context in its processing loop, otherwise it continues consuming CPU/IO long after the client has gone:

```go
func (s *server) ProcessStream(stream pb.Service_ProcessStreamServer) error {
    ctx := stream.Context()
    for {
        msg, err := stream.Recv()
        if err == io.EOF { return nil }
        if err != nil { return err }

        // CHECK CONTEXT BEFORE EXPENSIVE WORK
        if ctx.Err() != nil {
            return status.FromContextError(ctx.Err()).Err()
        }

        result, err := s.expensiveComputation(ctx, msg)  // ctx propagates to computation
        if err != nil { return err }

        if err := stream.Send(result); err != nil { return err }
    }
}
```

Cancellation propagation in nested calls: if Service A receives a request with a context that is later cancelled (deadline expired), and A is in the middle of a gRPC call to Service B, the `ctx.Done()` channel signals, A's call to B returns with `DeadlineExceeded`, and A's own handler can return the error. The cancellation cascades down the call chain automatically — this is the "context propagation" pattern that Go's `context.Context` and gRPC's deadline propagation enable together.

## Section 9: Schema Design and Evolution

**Q23. What is `google.protobuf.FieldMask` and how does it enable partial updates (PATCH semantics) in gRPC?**
A: REST's PATCH semantics ("update only specified fields") don't map directly to Protobuf because in `proto3`, you can't distinguish between "field not set" and "field set to its zero value." `FieldMask` solves this by explicitly listing which fields should be updated:

```protobuf
message UpdateUserRequest {
  string user_id = 1;
  User user = 2;  // the new values for fields being updated
  google.protobuf.FieldMask update_mask = 3;  // which fields to update
}

// Client specifying only name and email should be updated:
req := &pb.UpdateUserRequest{
    UserId: "user-42",
    User: &pb.User{
        Name:  "Alice Smith",  // update this
        Email: "alice@example.com",  // update this
        // Role, CreatedAt, etc. not set — and FieldMask tells server to ignore them
    },
    UpdateMask: &fieldmaskpb.FieldMask{
        Paths: []string{"name", "email"},  // only these paths should be updated
    },
}

// Server applying the update:
func (s *server) UpdateUser(ctx context.Context, req *pb.UpdateUserRequest) (*pb.User, error) {
    // Validate the mask (protoimpl can do this)
    req.UpdateMask.Normalize()
    if !req.UpdateMask.IsValid(req.User) {
        return nil, status.Error(codes.InvalidArgument, "invalid field mask")
    }
    // Apply only masked fields to the existing user
    return s.userRepo.PartialUpdate(ctx, req.UserId, req.User, req.UpdateMask.Paths)
}
```

Without `FieldMask`, a client updating a user's name would need to send all other fields too — or the server would zero out any unset fields (the proto3 default value problem). `FieldMask` is the canonical gRPC solution for partial updates.

**Q24. How do you design a gRPC API for pagination, and what does the standard pattern look like?**
A: gRPC pagination follows the same cursor-based pattern as REST, encoded in Protobuf:

```protobuf
message ListOrdersRequest {
  string user_id = 1;
  int32 page_size = 2;   // max results per page, bounded server-side (e.g., max 100)
  string page_token = 3; // opaque cursor from previous response (empty = first page)
}

message ListOrdersResponse {
  repeated Order orders = 1;
  string next_page_token = 2;  // empty if no more pages
  int32 total_size = 3;        // optional total count (expensive for large tables)
}
```

The `page_token` is an opaque string that encodes the cursor state — typically a base64-encoded Protobuf containing `{last_order_id, sort_key}` or a database cursor value. The client never parses or constructs page tokens — they're treated as opaque blobs received from the server and echoed back on subsequent requests.

For very large result sets, streaming is an alternative to cursor-based pagination:
```protobuf
// Alternative: stream all results for a user (no pagination needed)
rpc StreamOrders(StreamOrdersRequest) returns (stream Order);
```
Streaming is appropriate when: the client needs all results (export, bulk processing); result count is large enough that managing many paginated requests is cumbersome; results don't need random access (sequential processing is fine).

## Section 10: Scenario-Based Questions

**Q25. "Design a real-time order tracking system where customers can subscribe to updates on their order's status. What gRPC call type and what are the implementation details?"**
A: Customers connect to track an order → server pushes status updates until delivery → **server streaming RPC**.

```protobuf
service TrackingService {
  rpc TrackOrder(TrackOrderRequest) returns (stream OrderStatusUpdate);
}

message TrackOrderRequest {
  string order_id = 1;
  string customer_id = 2;  // for authorization
}

message OrderStatusUpdate {
  string order_id = 1;
  OrderStatus status = 2;
  string location = 3;
  google.protobuf.Timestamp estimated_delivery = 4;
  string message = 5;  // human-readable update ("Your package is in Chicago")
}
```

Server implementation:
```go
func (s *server) TrackOrder(
    req *pb.TrackOrderRequest,
    stream pb.TrackingService_TrackOrderServer,
) error {
    ctx := stream.Context()

    // Authorization: verify customer owns this order
    if err := s.authz.CanTrack(ctx, req.CustomerId, req.OrderId); err != nil {
        return status.Error(codes.PermissionDenied, "access denied")
    }

    // Subscribe to status updates for this order via Kafka/Redis Pub/Sub
    subscription, err := s.eventBus.Subscribe(ctx, "order."+req.OrderId)
    if err != nil {
        return status.Errorf(codes.Internal, "subscription failed: %v", err)
    }
    defer subscription.Close()

    // Send current status immediately (don't make customer wait for next event)
    current, err := s.orderRepo.GetStatus(ctx, req.OrderId)
    if err != nil {
        return status.Errorf(codes.Internal, "failed to get current status: %v", err)
    }
    if err := stream.Send(current); err != nil {
        return err
    }

    // Stream future updates until delivery or cancellation
    for {
        select {
        case update, ok := <-subscription.Updates():
            if !ok {
                return nil  // order tracking complete (delivered/cancelled)
            }
            if err := stream.Send(update); err != nil {
                return err  // client disconnected
            }
            if update.Status == pb.OrderStatus_ORDER_STATUS_DELIVERED {
                return nil  // close stream on delivery
            }
        case <-ctx.Done():
            return status.FromContextError(ctx.Err()).Err()
        }
    }
}
```

**Scaling**: each active tracking session holds a goroutine + event subscription. At 1M active orders with 1 customer each, 1M goroutines (each ~8KB stack = 8GB memory). With N tracking server instances and a subscription fan-out bus (Kafka or Redis Pub/Sub), each instance handles ~1M/N subscriptions. The subscription bus must efficiently deliver events only to the instance where the subscriber is connected — matched by order ID via consistent hashing or a routing table in Redis.

**Q26. "A data pipeline needs to ingest 100,000 log entries per second from distributed applications. Design the gRPC interface."**
A: High-throughput write from many clients to a central ingestion service → **client streaming RPC**.

```protobuf
service LogIngestionService {
  // Client streams log entries; server returns batch summary
  rpc IngestLogs(stream LogEntry) returns (IngestResult);

  // Alternative: bidirectional for backpressure signaling
  rpc IngestLogsWithAck(stream LogEntry) returns (stream IngestAck);
}

message LogEntry {
  string service_name = 1;
  string level = 2;  // ERROR, WARN, INFO, DEBUG
  string message = 3;
  map<string, string> labels = 4;
  google.protobuf.Timestamp timestamp = 5;
  bytes trace_id = 6;  // 16-byte UUID as bytes (more efficient than string)
}

message IngestResult {
  int64 accepted = 1;
  int64 rejected = 2;
  repeated string errors = 3;
}
```

At 100k entries/second from, say, 1,000 services (100 entries/second each):
- **Client-side batching**: each log agent buffers entries and sends in micro-batches via client streaming. One `IngestLogs` RPC might stream 1,000 entries before closing. This amortizes the RPC overhead (one stream setup per 1,000 entries vs one unary RPC per entry = 100× fewer RPCs).
- **Compression**: gRPC supports per-message compression via the Compressed-Flag byte in the data frame prefix. Log entries (mostly text) compress to 20-30% of original size with gzip. Enable compression via `grpc.UseCompressor(gzip.Name)` on the client — saves significant bandwidth at 100k/s.
- **Why not unary**: one unary RPC per log entry = 100k RPCs/second to the ingestion service. Each unary RPC has at minimum 3 HTTP/2 frames (HEADERS + DATA + HEADERS trailers). Client streaming reduces this by batching N entries into one stream with N DATA frames and 2 HEADERS frames — 3+N frames vs 3N frames. For N=1000: 3 HEADERS + 1000 DATA vs 3000 HEADERS + 1000 DATA — orders of magnitude less header overhead.

**Q27. "Design the real-time collaborative document editing backend (like Google Docs) using gRPC. What call types would you use for different operations?"**
A: A collaborative document service requires multiple interaction patterns — different operations map to different gRPC call types:

```protobuf
service DocumentService {
  // Load initial document state: unary
  rpc GetDocument(GetDocumentRequest) returns (Document);

  // Stream of all operations from all editors in real-time: bidirectional
  // Client sends operations they apply; server broadcasts all editors' operations
  rpc EditDocument(stream EditOperation) returns (stream EditOperation);

  // Save a snapshot/version: unary
  rpc SaveVersion(SaveVersionRequest) returns (DocumentVersion);

  // Stream version history for sidebar: server streaming
  rpc ListVersions(ListVersionsRequest) returns (stream DocumentVersion);

  // Cursor positions of all collaborators: bidirectional
  rpc SyncCursors(stream CursorUpdate) returns (stream CursorUpdate);
}

message EditOperation {
  string document_id = 1;
  string session_id = 2;
  string user_id = 3;
  int64 sequence_number = 4;  // for OT ordering
  oneof operation {
    InsertOp insert = 5;
    DeleteOp delete = 6;
    FormatOp format = 7;
  }
  google.protobuf.Timestamp client_timestamp = 8;
}

message CursorUpdate {
  string session_id = 1;
  string user_id = 2;
  int64 position = 3;  // character offset
  string selection_anchor = 4;
}
```

**EditDocument (bidirectional streaming)**: each editor maintains one bidirectional stream. The server receives operations from all editors, applies Operational Transformation (OT) to resolve conflicts, assigns a canonical sequence number, and broadcasts the transformed operation back to all editors' streams. The server holds a fan-out room per document: operations from editor A's stream are transformed and sent to editors B, C, and D's streams.

**SyncCursors (bidirectional streaming)**: cursor position updates don't need OT — they're last-write-wins per user. A separate bidirectional stream keeps cursor synchronization off the main edit stream, allowing different rate control (cursors update at mouse-move frequency; operations update only on keystroke).

**Why not WebSocket for this design**: the gRPC schema provides compile-time guarantees about operation types (`InsertOp`, `DeleteOp`, `FormatOp` as `oneof`) — preventing invalid operations from being sent/received at the type level. The schema also enables server-side validation interceptors that reject malformed operations before they reach the OT engine. WebSocket would require application-level schema validation; gRPC's proto-generated code provides it for free.
