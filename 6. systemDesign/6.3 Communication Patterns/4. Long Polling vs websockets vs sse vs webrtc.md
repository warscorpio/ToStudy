# Long Polling vs WebSockets vs SSE vs WebRTC — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals and Selection Framework

**Q1. What problem do all four technologies solve, and what is the core question for choosing between them?**
A: All four solve the same underlying problem: HTTP's request-response model requires the client to initiate every interaction — the server cannot spontaneously push data to the client. For real-time applications (live scores, notifications, chat, video calls), waiting for the client to poll is either too slow or too wasteful. Each technology addresses this limitation differently. The core selection question is: **how many directions does data flow, and what is the latency and frequency requirement?**

- **Long polling**: unidirectional (server → client) with high latency tolerance, stateless server preferred, no infrastructure changes possible.
- **SSE (Server-Sent Events)**: unidirectional (server → client), low latency, clean HTTP, browser-native auto-reconnect.
- **WebSocket**: bidirectional, low latency, high frequency, browser or server clients.
- **WebRTC**: peer-to-peer (direct client ↔ client), ultra-low latency, media streams (audio/video), bypass server for data path.

The direction of data flow eliminates two or three options immediately in most scenarios. If data only flows server → client, SSE is almost always better than WebSocket. If data flows client ↔ client without needing server in the media path, WebRTC is the only option. Defaulting to WebSocket for every real-time feature is the most common over-engineering mistake.

**Q2. What is the evolution of these technologies and why were they each created?**
A: Each technology was created to fill a gap left by its predecessor:

**Long polling** (early 2000s): the first workaround for HTTP's request-response limitation. Uses only standard HTTP — no protocol changes, works through any proxy. Created because browsers had no other option for server-push.

**SSE** (HTML5, 2004 spec, widespread by 2012): formalizes the streaming-over-HTTP pattern into a browser API (`EventSource`). Eliminates the repeated connection overhead of long polling, adds structured events with named types and IDs, and builds in automatic reconnection. Created because long polling was wasteful and ad-hoc.

**WebSocket** (RFC 6455, 2011): created when SSE's unidirectional limitation became a bottleneck for chat, gaming, and collaborative applications. The HTTP upgrade mechanism was standardized to avoid the proprietary server-push hacks (Comet, Flash sockets, Java applets) that preceded it.

**WebRTC** (W3C/IETF, 2011-2017 standardization): created for browser-to-browser audio/video calls and data transfer without server involvement in the media path. The previous approach — routing all media through a server — was bandwidth-intensive and added latency. WebRTC enables direct peer connections from the browser for the first time.

## Section 2: Long Polling — Deep Dive

**Q3. How does long polling work mechanically, and what is the lifecycle of a single long-poll cycle?**
A: Long polling exploits HTTP's ability to hold connections open. The client sends a standard HTTP request, and the server deliberately delays its response until either an event occurs or a timeout expires. The client immediately re-issues a new request upon receiving any response — creating the illusion of a persistent connection from a series of standard HTTP calls:

```
Time →

Client:  ─── GET /events?since=T1 ────────────────────────────────────────► (waiting)
Server:                                                   event occurs
Server:  ◄──────────────────────────── 200 OK {event data} ───────────────
Client:  ─── GET /events?since=T2 ───────────────────────────────────────► (waiting)
Server:                                    timeout (30s, no event)
Server:  ◄──── 204 No Content ───────────────────────────────────────────
Client:  ─── GET /events?since=T2 ──────────────────────────────────────► (waiting)
```

The server responds with `204 No Content` (or a heartbeat response) on timeout, prompting the client to reconnect immediately. The `since=T2` cursor ensures the client doesn't miss events between connections by tracking the last seen event's timestamp or ID.

**Q4. What are the server-side resource implications of long polling, and how does it affect server architecture?**
A: Each long-polling client holds one server connection open for the duration of the timeout window (typically 15-60 seconds). For a server handling 10,000 concurrent long-polling clients with a 30-second timeout:
- 10,000 open HTTP connections simultaneously
- 10,000 threads (if thread-per-connection — traditional Java servlet model) → ~10GB of thread stack memory
- 10,000/30 ≈ 333 new connections per second just from timeout cycling — baseline overhead even when no events occur

This is why long polling effectively forces servers toward async I/O architectures (Node.js event loop, async Java with Netty/Vert.x, asyncio in Python) — thread-per-connection models collapse under long polling load that would be trivial for non-long-polling request-response workloads.

The hidden cost: even with async I/O (one thread per CPU core), each open connection holds a file descriptor and kernel socket buffer. At 100k concurrent connections, file descriptor limits (`ulimit -n`) and kernel socket buffer memory become the binding constraints — requiring OS-level tuning (`sysctl -w net.core.somaxconn=65535`, `fs.file-max`).

**Q5. What are the delivery semantics of long polling, and what happens when the connection drops between events?**
A: Long polling can achieve at-least-once delivery if implemented correctly, but requires careful design:

**The gap problem**: when the client receives a response and before the next request reaches the server, the server may generate an event that no pending client request is waiting for. This event is buffered server-side and delivered when the next request arrives — no event is lost. The server must buffer events for a reconnect window (typically seconds).

**The duplicate problem**: if the connection drops after the server sends a response but before the client receives it, the client re-connects without advancing its cursor. The server sends the same event again. If the cursor is a timestamp, events generated in the same millisecond may be re-delivered. Use monotonically increasing event sequence IDs as cursors — not timestamps — to avoid this.

**The ordering problem**: events are delivered in the order they're sent in each response. If a long-poll response contains multiple events (batched for efficiency), they arrive in one atomic HTTP response — no partial delivery mid-response.

Correct cursor protocol:
```
Client: GET /events?cursor=42  (requesting events after sequence ID 42)
Server: 200 OK {events: [{id:43, ...}, {id:44, ...}]}
Client: GET /events?cursor=44  (advances cursor to last received ID)
```

## Section 3: Server-Sent Events (SSE) — Deep Dive

**Q6. What is the SSE protocol, and how does it structure events on the wire?**
A: SSE (Server-Sent Events) uses a standard HTTP response with `Content-Type: text/event-stream`. The server sends events as structured text over the persistent HTTP connection — each event is a set of field:value lines followed by a blank line:

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

id: 1
event: user_joined
data: {"user_id": 42, "username": "alice"}

id: 2
event: message
data: {"room_id": 7, "content": "Hello!"}
data: {"this_continues": "on_next_line"}

: this is a comment (ignored by client)

retry: 3000

id: 3
event: message
data: {"room_id": 7, "content": "Anyone there?"}

```

Fields:
- **`id`**: the event ID — the client's `Last-Event-ID` header on reconnect contains the last seen ID, enabling the server to replay missed events.
- **`event`**: named event type — `EventSource.addEventListener('message', ...)` registers listeners per event type.
- **`data`**: the payload (one or more `data:` lines are concatenated with `\n`).
- **`retry`**: suggested reconnect delay in milliseconds — overrides the browser's default (3 seconds).
- **`:` (comment)**: server-to-client heartbeat — sent periodically to keep the connection alive through proxies that would otherwise time out idle connections.

**Q7. How does SSE's built-in reconnection work and what does `Last-Event-ID` achieve?**
A: The browser's `EventSource` API implements automatic reconnection — if the connection drops (network error, server restart, proxy timeout), the browser waits `retry` milliseconds and reconnects. Crucially, it sends `Last-Event-ID: <last-seen-id>` as a request header on reconnect:

```
Client (on reconnect): GET /events
                       Last-Event-ID: 47
                       Accept: text/event-stream
```

The server reads `Last-Event-ID` and replays any events with ID > 47 that were emitted since the client disconnected. This provides at-least-once delivery across reconnects as long as: (1) the server retains a recent event buffer (not just a single "latest" value), and (2) event IDs are monotonically increasing (so the server knows which events to replay).

Without `Last-Event-ID` support: the server just starts from the current position — the client misses events that occurred during the disconnection window. For notifications (where missing one notification is acceptable), this is fine. For ordered event streams (chat history), event ID replay is essential.

**Q8. Why can SSE work through HTTP/2 without the "6 connection limit" issue that affects HTTP/1.1?**
A: HTTP/1.1 browsers limit concurrent connections to any one origin to 6 (Chrome) or 8 (Firefox). An SSE connection over HTTP/1.1 occupies one of those slots permanently — leaving only 5 for regular page resource loading. This can noticeably slow page loading for pages with many concurrent SSE connections or resource requests. HTTP/2 uses one TCP connection per origin and multiplexes all requests/streams over it — an SSE stream is one multiplexed stream that doesn't consume a dedicated connection. 100 SSE connections to the same origin still use one TCP connection under HTTP/2.

Additionally, HTTP/2 header compression (HPACK) makes SSE handshakes cheaper. The `Content-Type: text/event-stream` and other headers are compressed and cached between requests. This is a genuine HTTP/2 advantage for SSE-heavy applications and one of the reasons SSE has seen a resurgence (after being temporarily overshadowed by WebSocket) as HTTP/2 became ubiquitous.

**Q9. What are SSE's limitations and when does it force you toward WebSocket?**
A: SSE's fundamental limitation is unidirectionality — the server pushes; the client cannot push over the same SSE connection. Client-to-server communication still requires separate HTTP requests. This creates a problem when:

1. **High-frequency bidirectional data**: in a collaborative editing app, every keystroke is client → server AND server → all clients. Using SSE for server push + HTTP POST for client sends means two separate connections (HTTP/2 reduces this to one TCP connection but still two logical channels). The round-trip per user action (keystroke → POST → SSE event) adds latency vs a single WebSocket message.

2. **Request-response within the real-time channel**: if the application needs to send a message and receive a correlated reply in real-time (e.g., "I sent message X, is it delivered?"), SSE can't carry the reply — you'd need a correlation mechanism over separate HTTP requests.

3. **Binary data efficiency**: SSE is text-only (the protocol is text-based). Binary data (audio frames, encoded video) must be base64-encoded (+33% size overhead) before sending via SSE. WebSocket supports native binary frames.

4. **Browser support edge cases**: SSE lacks support in older browsers (IE11 has no `EventSource` — requires a polyfill). WebSocket has better legacy browser support (though in 2024+, this distinction is largely academic).

## Section 4: WebSocket — Deep Dive

**Q10. What is the WebSocket upgrade handshake, and what happens to the connection afterward?**
A: WebSocket begins as a standard HTTP request that negotiates an upgrade:

```
Client → Server:
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

Server → Client:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

After the `101 Switching Protocols` response, the TCP connection is no longer HTTP. Both sides communicate using the WebSocket framing protocol: each message is preceded by a 2-14 byte frame header containing: FIN bit (whether this is the last frame of a message), opcode (text, binary, ping, pong, close), mask bit (client→server messages must be masked), and payload length. The overhead per message is 2-14 bytes — orders of magnitude less than an HTTP request's 200-800 bytes of headers.

The connection remains open indefinitely until either side sends a close frame (opcode 0x8) with an optional status code and reason. Unlike HTTP, there's no built-in timeout — the connection lives as long as the TCP connection lives, which means applications must implement their own keepalive (ping/pong frames) and idle detection.

**Q11. What is the WebSocket ping/pong mechanism and why is it necessary?**
A: WebSocket has two control frames — ping (opcode 0x9) and pong (opcode 0xA) — for connection keepalive. The server (or client) sends a ping frame; the recipient must send a pong within a timeout. If no pong arrives, the sender closes the connection.

Why necessary: TCP connections can enter a "half-open" state where one side's OS believes the connection is alive but the remote peer has crashed or the network path has silently failed. Without any data exchange, this can persist indefinitely. WebSocket ping/pong drives data through the connection, forcing TCP to detect and surface the underlying failure.

Additionally: intermediate proxies and load balancers often close idle TCP connections after 30-300 seconds (ALB default: 60 seconds of inactivity). A WebSocket connection with no user activity (e.g., a chat app where users are reading but not typing) will be silently closed by intermediate infrastructure. Ping/pong frames sent every 20-30 seconds keep the connection active through these infrastructure timeouts.

Typical configuration:
```python
# Server sends ping every 20 seconds, expects pong within 5 seconds
PING_INTERVAL = 20  # seconds
PING_TIMEOUT = 5    # seconds

async def connection_handler(websocket):
    try:
        await websocket.wait_closed()
    except websockets.exceptions.ConnectionClosedError:
        handle_disconnect()
```

**Q12. How does WebSocket handle message framing, and what is the difference between text and binary frames?**
A: WebSocket differentiates between text frames (opcode 0x1, UTF-8 encoded) and binary frames (opcode 0x2, raw bytes). The distinction is contractual: the receiver must not interpret a binary frame as text or vice versa.

For large messages, WebSocket supports message fragmentation across multiple frames — the FIN bit is 0 on all but the last frame of a fragmented message. The receiver reconstructs the complete message by concatenating frames in order. Application code typically works with complete messages (the WebSocket library handles frame reassembly transparently).

**Text frames**: used for JSON, plain text, XML. Slightly heavier due to UTF-8 encoding requirement and validation overhead. Universally supported and easiest to debug (human-readable in browser DevTools).

**Binary frames**: used for Protobuf, MessagePack, raw audio/video data, compressed payloads. No encoding overhead — bytes are passed through as-is. Required for efficient real-time media applications or when payload size is critical. Binary WebSocket messages with Protobuf payloads are a common alternative to gRPC for browser clients that can't use gRPC directly.

**Q13. What are the scaling challenges of WebSocket compared to HTTP, and how are they addressed?**
A: WebSocket scaling differs fundamentally from HTTP scaling:

**HTTP (request-response)**: stateless — any server can handle any request. A load balancer routes each request independently. Servers scale horizontally with no coordination. Horizontal scaling is trivial.

**WebSocket (persistent connection)**: stateful per connection. A WebSocket connection is established with one specific server instance. All subsequent messages on that connection go to that same instance. This creates:

**Stickiness requirement**: a WebSocket load balancer must use sticky sessions — once a client connects to server S1, all its messages must route to S1 for the connection's lifetime. This is "IP hash" or "cookie-based sticky routing" at the load balancer. Without stickiness, messages from the same client arrive at different server instances, none of which have the connection state. AWS ALB supports sticky sessions natively.

**Cross-instance message broadcasting**: if client A (connected to server S1) sends a message to all clients in room R, and some of those clients are on S2 and S3, S1 must broadcast to S2 and S3 to relay the message to their clients. This requires a pub/sub backplane: Redis Pub/Sub, Kafka, or a message bus between server instances. Each server instance subscribes to all channels relevant to its connected clients and relays messages from the backplane to its local WebSocket connections.

**Connection capacity**: a single server instance can maintain ~10k-100k WebSocket connections (limited by file descriptors, memory for connection state, and CPU for message processing). At 1M concurrent users, 10-100 server instances are needed — each maintaining their slice of connections. Dedicated WebSocket server libraries (socket.io, ws for Node.js, netty for Java) are designed for this scale, not traditional thread-per-request frameworks.

## Section 5: WebRTC — Deep Dive

**Q14. What is WebRTC's fundamental architectural difference from the other three technologies?**
A: WebRTC is the only technology in this group designed for **peer-to-peer** communication — data and media flow directly between browsers (or browser and native client) without passing through a server for the media path. The other three technologies all route all data through the server:

```
Long Polling / SSE / WebSocket:
Browser A → Server → Browser B  (all data through server)

WebRTC:
Browser A ──────────────────────── Browser B  (direct peer connection)
     ↑↓                               ↑↓
  (signaling only, via server)    (signaling only)
```

Why this matters: for audio/video calls, routing media through a server doubles the latency (your voice travels A → server → B instead of A → B) and requires the server to receive and forward all media bandwidth (for 100 concurrent video calls at 2Mbps each, the server needs 400Mbps uplink + 400Mbps downlink = 800Mbps just to relay media). Peer-to-peer eliminates this server-side bandwidth cost and reduces latency to physical network propagation (typically 10-50ms for nearby peers vs 50-150ms through a server).

**Q15. What is ICE, STUN, and TURN in WebRTC, and what problem do they solve?**
A: The fundamental challenge for peer-to-peer browser communication: browsers are almost always behind NAT (Network Address Translation — your router's private IP is different from your public internet IP) and firewalls. Browser A doesn't know Browser B's real IP; Browser B doesn't know Browser A's real IP; and even if they did, NAT gateways would block direct connections.

**ICE (Interactive Connectivity Establishment)**: the framework that coordinates the process of finding a viable network path between peers. ICE tries candidate addresses in order of preference (direct → STUN-assisted → TURN relay) until a connection is established.

**STUN (Session Traversal Utilities for NAT)**: a server that tells a browser its public-facing IP and port as seen from outside its NAT. When Browser A asks the STUN server "what is my public IP?", the STUN server responds with the IP/port that A's NAT presents to the outside world. A can now include this as an ICE candidate — telling B "try connecting to me at <public_IP>:<port>." Works for most NAT types (full cone, restricted cone) but fails for symmetric NAT (where the public port changes per destination). Cost: trivially cheap — one UDP query/response, no media routing. Google operates free STUN servers (`stun.l.google.com:19302`).

**TURN (Traversal Using Relays around NAT)**: a relay server that forwards media when direct peer-to-peer connection fails (symmetric NAT, strict firewalls). Both peers connect to the TURN server and media flows: Peer A → TURN → Peer B. This is functionally similar to routing through a regular server — but TURN is the fallback for when direct peer-to-peer is impossible, used for ~15-20% of real-world WebRTC calls. TURN is bandwidth-intensive and costly to operate: the server must receive and forward all media. Self-hosting TURN (coturn) or using managed TURN services (Twilio TURN, metered.ca) is necessary for production WebRTC.

**The process**: ICE gathers all possible candidate addresses (local IP, STUN-discovered public IP, TURN relay address), both peers exchange their candidates via signaling (the server), and ICE tries each combination to find a working path.

**Q16. What is WebRTC signaling and why doesn't WebRTC specify a signaling protocol?**
A: Signaling is the process of exchanging session description and ICE candidate information between peers — before the peer-to-peer connection is established — through a server. WebRTC doesn't specify a signaling protocol because the data being exchanged (SDP — Session Description Protocol, and ICE candidates) is just structured text that can travel over any messaging channel. The application chooses its signaling mechanism:

```
Standard WebRTC signaling flow:

Browser A                  Signaling Server              Browser B
    |------- "offer" SDP ─────────────────────────────────────► |
    |         (ICE candidates A)                                 |
    |                                                            |
    |◄────────── "answer" SDP ──────────────────────────────── |
    |         (ICE candidates B)                                 |
    |                                                            |
    |◄──────────────────── ICE connectivity checks ───────────► |
    |                                                            |
    |◄════════════ Direct peer-to-peer connection ══════════════|
    |                 (audio/video/data)                         |
```

Common signaling implementations: WebSocket (most common), SSE (for the offer, then WebSocket for the answer), or even HTTP long polling in simple cases. The signaling channel carries only small text messages (SDP ~200-400 bytes, ICE candidates ~50 bytes each) — bandwidth is irrelevant. Once the peer-to-peer connection is established, the signaling server is no longer involved in the media path.

**Q17. What are the three WebRTC connection modes — mesh, SFU, and MCU — and when does each apply?**
A: For calls with more than two participants, three architectures exist:

**Mesh (peer-to-peer full mesh)**: each participant establishes a direct connection to every other participant. For N participants: `N×(N-1)/2` peer connections. Participant 1 sends their video stream to every other N-1 participant, receives N-1 incoming streams. At N=6: 15 peer connections, each participant sending 5 streams (5× uplink bandwidth) and receiving 5 streams (5× downlink). The uplink bandwidth requirement grows linearly with N and quickly becomes prohibitive for typical home internet connections (10-20 Mbps uplink). Maximum practical scale: 3-5 participants. Used by: simple P2P video calls (Google Meet for small calls, some WebRTC demos).

**SFU (Selective Forwarding Unit)**: a server that receives each participant's media stream and selectively forwards it to others — without decoding or re-encoding the media. Each participant sends one upstream stream to the SFU (fixed uplink bandwidth), and receives N-1 streams from the SFU (scales downlink with participant count). The SFU can selectively forward at different quality levels (simulcast, SVC) based on each receiver's network conditions. Scalable to 50-100 participants per room. Used by: Zoom, Google Meet (large calls), Discord video, most production video conferencing. Requires significant server bandwidth but no encoding CPU.

**MCU (Multipoint Control Unit)**: a server that decodes all incoming streams and mixes them into a single composite output stream sent to each participant. Each participant sends one upstream stream and receives one composite stream — fixed bandwidth for both uplink and downlink regardless of participant count. Scales downlink perfectly. But: compositing N video streams requires N decode + 1 composite encode operations per frame — extremely CPU-intensive and expensive. Introduces encoding latency. Used when: clients have severely limited bandwidth (mobile on 2G, where receiving one composite stream is the only viable option). Rarely the right choice in 2024 — SFU is almost always better.

## Section 6: Infrastructure and Scaling

**Q18. How do you scale each technology to 100,000 concurrent connections?**
A:

**Long polling at 100k connections**: 100k persistent HTTP connections, each held for 15-60 seconds. Requires async I/O server (Node.js, async Python, Vert.x). File descriptor limit must be raised to > 100k. A single async Node.js server can handle ~10k-50k concurrent long-poll connections depending on memory per connection and event processing throughput. 3-10 servers behind a stateless load balancer (long polling is effectively stateless — no connection affinity required, since each reconnect can go to any server). Event bus or Redis Pub/Sub needed if events need to cross server boundaries.

**SSE at 100k connections**: nearly identical constraints to long polling, but with even lower per-reconnect overhead (connections stay open longer, no reconnect cycling). Async I/O server required. HTTP/2 multiplexing means the kernel-level connection count is lower than the logical SSE connection count. Redis Pub/Sub backplane for cross-instance event delivery. 3-10 server instances. No sticky sessions required (each SSE connection is independent and stateless in terms of business logic — the server just needs to know which events to send for this client's subscriptions, fetched from Redis/DB).

**WebSocket at 100k connections**: requires sticky sessions at the load balancer (connection affinity). Each server instance handles a portion of the 100k connections. Redis Pub/Sub or Kafka for cross-instance broadcasting. WebSocket-optimized libraries (ws, uWebSockets.js for Node.js — uWebSockets.js benchmarks at ~1M concurrent connections per server on high-memory machines). Per-connection memory: ~2-10KB for connection state depending on framework.

**WebRTC at 100k concurrent calls**: the SFU architecture scales differently — each SFU node handles X participants (typically 200-1000, depending on video resolution and bandwidth). A 100k user system with average 5 users/call = 20k calls → 20-100 SFU nodes behind a call routing layer. Media servers (mediasoup, Janus, Jitsi Videobridge) are designed for this — they're highly CPU-optimized for media forwarding. The signaling layer (WebSocket/HTTP) handles significantly less load than the media layer and scales independently.

**Q19. How does the reverse proxy / load balancer configuration differ for each technology?**
A:

**Long polling**: no special configuration beyond standard HTTP load balancing. Increase the proxy's keepalive and upstream timeout settings to accommodate 30-60 second connections without timing out:
```nginx
upstream backend {
    server app1:8080;
    keepalive 100;
}
location /events {
    proxy_read_timeout 70s;  # slightly longer than the 60s long-poll timeout
    proxy_pass http://backend;
}
```

**SSE**: same as long polling, plus disable proxy buffering (critical — nginx buffers proxy responses by default, meaning SSE events are held in the nginx buffer and delivered in a burst, not streamed):
```nginx
location /events {
    proxy_buffering off;     # CRITICAL: don't buffer SSE events
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_pass http://backend;
    add_header X-Accel-Buffering no;  # for nested proxy configs
}
```

**WebSocket**: requires explicit WebSocket upgrade handling and sticky sessions:
```nginx
upstream backend {
    ip_hash;  # sticky sessions for WebSocket
    server app1:8080;
    server app2:8080;
}
location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "Upgrade";
    proxy_read_timeout 3600s;  # long timeout for persistent connections
}
```

**WebRTC**: the signaling server uses standard HTTP/WebSocket config. Media traffic (SRTP over UDP) bypasses HTTP infrastructure entirely — STUN/TURN servers receive direct UDP traffic. If using TURN, the TURN server needs dedicated UDP ports (3478 for STUN/TURN, 5349 for TLS TURN) exposed directly to the internet, not proxied through nginx. Media servers (SFU nodes) also bypass HTTP load balancers for media — typically with their own UDP port range and a separate media routing layer.

## Section 7: Security

**Q20. What security considerations are unique to each technology?**
A:

**Long polling**: same security surface as standard HTTP. CSRF (Cross-Site Request Forgery) is a risk — the browser automatically sends cookies with cross-origin HTTP requests, potentially allowing a malicious page to initiate long-poll requests to your API. Mitigation: use `SameSite=Strict` or `SameSite=Lax` cookie attributes, or use JWT in `Authorization` header (not sent automatically by browsers cross-origin). Rate limit the long-poll endpoint to prevent a single client from holding too many simultaneous connections.

**SSE**: same CSRF risk as long polling (the browser's `EventSource` does not send custom headers or bodies — authentication must be via cookies or URL query parameters). CORS applies: the server must include `Access-Control-Allow-Origin` for cross-origin SSE. A critical SSE-specific risk: if the SSE endpoint emits data containing user-specific information without proper authentication, a page from any origin can instantiate an `EventSource` and receive that data (CORS origin check only blocks JavaScript from reading responses, but SSE events are delivered to `EventSource.onmessage` handler, not a raw response). Always authenticate SSE connections on the first request.

**WebSocket**: the WebSocket handshake includes an `Origin` header — the server should validate it to prevent cross-origin WebSocket connections from unauthorized origins. The browser's WebSocket API does not enforce the same CORS policy as XHR/fetch — a cross-origin WebSocket connection is allowed by default unless the server explicitly rejects non-approved origins. WebSocket connections are not automatically authenticated by browser cookie sending to cross-origin endpoints (unlike HTTP, WebSocket cookie behavior varies by browser). Use JWT in the URL query string on the initial handshake (`wss://example.com/ws?token=...`) or validate a session cookie during the handshake. Implement rate limiting on message frequency — a malicious WebSocket client can send millions of messages per second.

**WebRTC**: the media path is always encrypted — WebRTC mandates SRTP (Secure Real-time Transport Protocol) for all media and DTLS-SCTP for the data channel. There is no option to use unencrypted WebRTC media (unlike HTTP which can be plain text). However: the signaling channel is application-defined and must be secured separately (use WSS, not WS). The TURN server has access to all media that passes through it — use a TURN server you control (not public TURN) and authenticate TURN credentials per-session (short-lived, one-time TURN credentials via HMAC, not static shared credentials). Malicious ICE candidates (ICE "probing" attacks) can allow peers to probe internal network addresses — validate ICE candidates server-side if sensitive.

## Section 8: Choosing the Right Technology

**Q21. Build the decision tree for choosing between the four technologies.**
A:

```
Step 1: Does data flow browser ↔ browser directly (audio, video, P2P file transfer)?
  YES → WebRTC (only technology enabling P2P browser communication)
  NO  → Continue

Step 2: Does data flow primarily or exclusively server → client?
  YES → Is binary data needed at high frequency? (audio snippets, compressed frames)
    YES → WebSocket (SSE is text-only; binary base64 overhead is significant)
    NO  → Does the environment restrict persistent connections?
      YES → Long polling (works through any proxy, no special config)
      NO  → SSE (simpler than WebSocket, built-in reconnect, HTTP/2 compatible)
  NO  → Continue (data flows client → server too, at some meaningful rate)

Step 3: Does client → server data flow at high frequency (> 1 message/second)?
  NO  → SSE for server push + standard HTTP POST for client sends (hybrid approach)
         (Low-frequency client sends don't justify WebSocket complexity)
  YES → Continue

Step 4: Are there strict constraints on WebSocket infrastructure?
  YES (corporate firewalls blocking WS, no HTTP/2 upgrade support) → Long polling
  NO  → WebSocket
```

**Q22. What is the "SSE + HTTP hybrid" pattern and when is it the pragmatic choice over WebSocket?**
A: Many applications have asymmetric communication patterns — the server sends many updates to the client, but the client sends relatively infrequent commands. A chat app where users read 50 messages for every 1 they send. A live trading dashboard where prices update 10 times/second but the user places a trade once a minute. A collaborative document where the server pushes edits from others frequently, but the user types intermittently.

For these asymmetric workloads, the SSE + HTTP hybrid eliminates WebSocket's complexity while delivering the same user experience:
- **SSE connection**: persistent server → client channel for all server-initiated updates (messages received, price ticks, edits from other users, notifications).
- **Standard HTTP POST/PUT**: client → server for user-initiated actions (send a message, place an order, submit an edit).

Benefits over full WebSocket: no sticky session requirement (SSE connections are stateless from a load balancer perspective — events come from Redis/Kafka backplane), simpler reconnection (SSE built-in vs WebSocket manual), HTTP/2 multiplexing (SSE and HTTP API calls share one connection), better CDN and proxy compatibility. Drawbacks: two logical channels instead of one; HTTP POST latency slightly higher than WebSocket message (HTTP headers vs WebSocket frame headers, though HTTP/2 header compression mitigates this).

Used by: GitHub notifications, many notification-heavy SaaS dashboards, real-time leaderboards, and any system where the engineering team correctly identified that their client-to-server traffic doesn't justify WebSocket's operational overhead.

## Section 9: Scenario-Based Questions

**Q23. "Design real-time notifications for a social media platform (100M users, <5% online at any given time). Users receive likes, comments, and follows in real-time. What technology?"**
A: Constraints: 5M concurrent users, notification rate is sparse (most users receive a notification every few minutes at best, not continuously), server → client unidirectional for notifications, client → server only for explicit actions (not within the notification stream).

**Technology**: SSE. Reasoning:
- Unidirectional (server → client) — SSE is the right fit; WebSocket's bidirectionality is unnecessary overhead.
- Sparse event rate — the SSE connection is "quiet" most of the time. This is fine — the connection is cheap to maintain (one file descriptor, small kernel socket buffer, no active CPU use). Long polling would generate wasteful reconnect cycles; SSE holds quietly.
- HTTP/2 compatibility — 5M concurrent SSE connections on HTTP/2 means 5M logical streams, not 5M TCP connections (many share HTTP/2 connections to the same CDN/load balancer).

**Architecture**:
```
User connects → SSE endpoint → subscribes to per-user channel in Redis Pub/Sub
Event occurs (like on user 42's post):
  Event Service → Redis PUBLISH user:42:notifications {type: "like", ...}
  SSE server for user 42 → receives Redis message → writes SSE event to user's stream
```

**Scaling**: each SSE server instance subscribes to Redis channels for its connected users. With 5M users and 100 server instances, each instance handles 50k SSE connections. Redis Pub/Sub fan-out delivers notifications only to the instance where the recipient is connected. If using Redis Cluster, user channel sharding across Redis nodes. Per-instance connection limit is the binding constraint — tune with `ulimit`, async I/O, and per-connection memory optimization.

**Missed events during disconnect**: SSE `Last-Event-ID` replay. The notification service writes to both Redis Pub/Sub (real-time) and a MongoDB/Cassandra notification store (persistent). On reconnect with `Last-Event-ID`, replay undelivered notifications from the store.

**Q24. "Design the communication layer for a multiplayer real-time game (100 players per room, game state updates 30 times/second, player inputs sent at the same rate)."**
A: Constraints: bidirectional, 30 Hz in each direction, 100 concurrent players per room, latency-critical (> 100ms is noticeable lag), binary data (compact game state representations).

**Technology**: WebSocket. Reasoning:
- High-frequency bidirectional (30 Hz send + 30 Hz receive) — SSE can't handle client → server at 30 Hz without HTTP overhead; long polling at 30 Hz would be 3,000 requests/sec per client; WebSocket's 2-14 byte framing overhead handles 30 Hz trivially.
- Binary data — game state (player positions, velocities, health) is most efficiently encoded as binary (Protobuf or a custom binary format). WebSocket binary frames have no encoding overhead.
- Low latency — WebSocket's persistent connection eliminates per-message TCP+HTTP handshake overhead.

**Why not WebRTC data channels**: WebRTC is P2P — all 100 players connecting to each other is a mesh with 4,950 connections. Uplink requirement: 100 players × 30 msgs/sec × 200 bytes = 600KB/s uplink per player × 99 destinations is obviously impractical. WebRTC works for P2P games (2 players) but not 100-player rooms. Use WebSocket to a game server that manages state authoritatively.

**Architecture**:
```
100 WebSocket clients → Game Server (authoritative state)
Player sends: {action: "move", dx: 1, dy: 0}
Server: validates, updates game state, computes delta
Server sends to all 100: {frame: 1234, players: [{id:1, x:100, y:200}, ...]}
```

**Optimization**: delta compression (send only changed state, not full state each frame); client-side interpolation (smooth display between server frames); dead reckoning (predict player movement locally, correct with server updates). At 30 Hz × 100 players × ~500 bytes per frame = 1.5MB/s server uplink per room — manageable on a single server instance handling dozens of rooms.

**Q25. "Design the video calling feature for a collaboration platform (meetings up to 25 participants, screen sharing, chat alongside video). What technology for each communication type?"**
A: Multiple communication types requiring different technologies:

**Audio/Video streams**: WebRTC with SFU architecture.
- Each participant sends one video + audio stream to the SFU (fixed uplink ~1-2Mbps).
- SFU selectively forwards to each participant (receives up to 24 streams, but uses bandwidth estimation to adapt quality per receiver).
- 25 participants: SFU receives 25 streams and forwards appropriate streams to 25 participants — manageable for a single SFU node.
- Screen sharing: a separate video track from the sharer → SFU → all participants. Higher resolution, lower frame rate (5-10 fps).

**Chat alongside the call**: WebSocket or SSE.
- Chat is low-frequency, text-only, unidirectional for delivery.
- WebSocket already established for call signaling — reuse it for chat. Zero additional connection cost.
- Or: separate SSE channel for chat delivery + HTTP POST for sending. Cleaner separation of concerns.

**Signaling (offer/answer/ICE candidates)**: WebSocket.
- Bidirectional (client sends offer/candidates, server sends answer/candidates to other peers).
- Low volume but latency-sensitive (slow ICE exchange delays call setup).

**Meeting control** (mute/unmute, raise hand, admit from lobby): WebSocket (reuse signaling channel) or SSE + HTTP.
- Low frequency, mix of bidirectional (request mute) and unidirectional (see that another user raised hand).

**Complete architecture**:
```
Browser A ←── WebSocket ──────────────────── Signaling Server
         ←── WebRTC (media, via SFU) ──────── SFU Media Server
         ←── WebSocket (chat, meeting ctrl) ── Meeting Server
                                                     ↕ (pub/sub)
Browser B ←── same pattern ──────────────────────────────────
```

**Q26. "A developer argues: 'Just use WebSocket for everything — it supports all patterns.' How do you respond?"**
A: WebSocket *can* implement all patterns — it's bidirectional, low-latency, and handles binary. But "can" ≠ "should." Three concrete costs of using WebSocket everywhere:

**Infrastructure cost**: WebSocket requires sticky session load balancing (connection affinity) — preventing free rotation of requests across server instances. An SSE-only or long-polling deployment can use stateless L7 load balancing (round robin, least connections) with no affinity, simplifying the load balancer configuration and enabling more even load distribution. For notification systems at scale, eliminating sticky sessions is a significant operational simplification.

**Reconnection reliability**: SSE's built-in `Last-Event-ID` reconnection with automatic event replay handles connection drops gracefully — the browser handles reconnection transparently, and the protocol carries the resume point. WebSocket reconnection requires entirely application-implemented logic: maintain a reconnect state machine, store the last-seen message ID, reconnect to the server, re-authenticate, re-subscribe to relevant channels. This is ~100 lines of careful application code that SSE gives you for free.

**Proxy and firewall compatibility**: WebSocket requires an HTTP Upgrade from HTTP/1.1 to the WebSocket protocol — some corporate proxies and older load balancers don't support this and silently drop the upgrade, causing invisible failures. SSE and long polling are plain HTTP — they work through any HTTP-capable proxy with no special configuration. In enterprise environments where WebSocket is blocked (surprisingly common), falling back to SSE or long polling is necessary.

The correct answer: use the simplest technology that meets the requirements. Server-push only → SSE. P2P media → WebRTC. High-frequency bidirectional binary → WebSocket. Using WebSocket for a notification bell is using a hammer when a feather would do — the extra power costs extra maintenance, extra complexity, and extra infrastructure without delivering any user-visible benefit.

**Tip for interviews:** Five things separate strong candidates on this topic: (1) immediately recognizing that **data direction eliminates options** — unidirectional → SSE before considering WebSocket; P2P media → WebRTC; only high-frequency bidirectional → WebSocket. Not reaching for WebSocket by default shows architectural judgment; (2) knowing **SSE's built-in `Last-Event-ID` reconnection** (Q7) by name and mechanism — this is SSE's most important production-relevant feature and distinguishes candidates who've deployed SSE vs those who've only read about it; (3) being precise about **WebRTC's three-part model**: STUN (NAT discovery), TURN (relay fallback), ICE (path selection) — and knowing TURN is needed for ~15-20% of calls even though WebRTC is "peer-to-peer" (Q15); (4) knowing **WebSocket requires sticky sessions** (Q13) and what that means for load balancers — and that SSE+long polling don't — which is a real operational differentiator at scale; and (5) articulating the **SFU vs MCU vs mesh** tradeoffs (Q17) for multi-party WebRTC — most candidates know "WebRTC is for video calls" but don't know why mesh fails at 6+ participants or that SFU is the industry standard, which is what shows real understanding.
