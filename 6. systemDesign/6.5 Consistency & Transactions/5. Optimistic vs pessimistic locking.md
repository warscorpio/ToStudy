# Optimistic vs Pessimistic Locking — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do both locking strategies solve?**
A: Both address the **lost update problem** — a concurrency anomaly where two transactions read the same data, independently compute an update, and then both write back, with the second write silently overwriting the first. Without some form of conflict management, the first writer's changes disappear. Locking strategies enforce a serializable ordering of conflicting operations so that concurrent writers don't clobber each other's work.

**Q2. What is pessimistic locking?**
A: Pessimistic locking assumes that conflicts are likely and prevents them by acquiring an exclusive lock on data *before* reading it for modification. Other transactions that need the same data are blocked until the lock is released at commit or rollback. It's called pessimistic because it assumes the worst — that a conflict will happen — and pays the coordination cost upfront to prevent it.

**Q3. What is optimistic locking?**
A: Optimistic locking assumes that conflicts are rare and allows transactions to proceed without acquiring locks. Instead, before committing, each transaction checks whether the data it read has been modified by someone else since it was read. If a conflict is detected, the transaction is rejected and the caller must retry. It's called optimistic because it assumes conflicts are the exception, not the rule, and pays the coordination cost only when that assumption turns out to be wrong.

**Q4. What is the core trade-off between the two?**
A: Pessimistic locking pays a coordination cost on every operation regardless of whether a conflict would have occurred — it serializes access preemptively. Optimistic locking pays nothing upfront but pays a retry cost when conflicts do occur. Pessimistic wins when conflicts are frequent (retries become expensive); optimistic wins when conflicts are rare (upfront locking overhead is wasted). The inflection point depends on read/write ratio, contention level, and transaction duration.

**Q5. How is a "conflict" defined in each model?**
A: In **pessimistic locking**, a conflict surfaces immediately as a blocked transaction — the second writer can't proceed until the first releases the lock. In **optimistic locking**, a conflict is detected at commit time by comparing the current state of the data against what the transaction originally read. If the data changed between read and commit, the commit is rejected as a conflict.

**Q6. What is the lost update problem concretely, and how does each strategy handle it?**
A: Classic example — two users simultaneously editing a wiki page:
- Read: User A reads page (version 5). User B reads page (version 5).
- Write: User A saves edits → page becomes version 6. User B saves edits → page becomes version 6 (overwrites A's changes).

**Pessimistic**: User A acquires a write lock on read. User B's read-for-update blocks until A commits. B then reads version 6 and edits from the correct base.

**Optimistic**: No locks on read. At commit, User A's write succeeds (still version 5 in DB). User B's write checks version — DB now shows version 6, not 5 — conflict detected, B's write is rejected, B must re-read and retry.

## Section 2: Pessimistic Locking — Mechanics & Behavior

**Q7. How is pessimistic locking implemented at the database level?**
A: Via `SELECT ... FOR UPDATE` (or `SELECT ... FOR SHARE` for shared/read locks). This instructs the database to acquire a row-level exclusive lock on every row returned by the query. Other transactions issuing `SELECT ... FOR UPDATE` or any `UPDATE`/`DELETE` on those rows will block until the locking transaction commits or rolls back. The lock is held for the duration of the transaction, not just the statement.

**Q8. What is the difference between `SELECT FOR UPDATE` and `SELECT FOR SHARE`?**
A:
- `SELECT FOR UPDATE` — acquires an exclusive lock. No other transaction can read-for-update, update, or delete the locked rows. Used when you intend to modify the data.
- `SELECT FOR SHARE` — acquires a shared lock. Other transactions can also read-for-share (read-only intention), but none can acquire an exclusive lock (i.e., no concurrent updates). Used when you need to read data and prevent it from being modified by others while you work, without blocking other readers.

**Q9. What is `SKIP LOCKED` and `NOWAIT`, and when are they used?**
A:
- `NOWAIT` — instead of blocking when a lock is unavailable, the statement immediately fails with an error. Used when blocking is unacceptable and the caller should be told to retry rather than wait.
- `SKIP LOCKED` — instead of blocking or failing, the query simply skips rows that are currently locked and returns only unlocked rows. Classically used for **job queue implementations** — multiple workers can concurrently pick up jobs without blocking each other, each worker claiming a different unlocked row.

**Q10. What is a deadlock, and why is pessimistic locking susceptible to it?**
A: A deadlock occurs when two or more transactions each hold a lock the other needs, creating a circular wait that neither can resolve. Example: Transaction A locks row 1 then tries to lock row 2; Transaction B locks row 2 then tries to lock row 1 — both block indefinitely. Pessimistic locking is susceptible because it holds locks for the full transaction duration. Databases detect deadlocks automatically (cycle detection in the lock wait graph) and resolve them by killing one transaction (the "victim"), which must then retry. Applications must handle deadlock errors and retry.

**Q11. What is lock escalation, and how does it cause unexpected contention?**
A: Some databases, notably SQL Server, escalate many fine-grained row locks into a coarser page lock or table lock when the number of held locks exceeds a threshold. This is done to reduce lock manager memory overhead, but it dramatically increases contention — a transaction expecting to lock 10 rows may end up locking thousands, blocking unrelated transactions. PostgreSQL and MySQL (InnoDB) do not escalate locks, which is one reason they're often preferred for high-concurrency workloads.

**Q12. What is a "lock wait timeout" and why is it important to configure?**
A: If a transaction waits for a lock indefinitely, it holds any locks it already acquired and blocks other transactions behind it — a chain of blocked transactions that grows over time. A lock wait timeout (e.g., `innodb_lock_wait_timeout` in MySQL, `lock_timeout` in PostgreSQL) causes a waiting transaction to fail after a specified duration, releasing its own locks and allowing the chain to clear. Without a timeout, a single slow or hung transaction can cascade into a system-wide stall.

## Section 3: Optimistic Locking — Mechanics & Behavior

**Q13. How is optimistic locking typically implemented in a relational database?**
A: By adding a **version column** (integer counter or timestamp) to the table. The protocol:
1. Read the row and capture the current version: `SELECT id, data, version FROM table WHERE id = ?`.
2. Perform business logic using the read data.
3. Write back with a version check: `UPDATE table SET data = ?, version = version + 1 WHERE id = ? AND version = <version_read>`.
4. Check affected rows: if 1 row updated → success. If 0 rows updated → conflict (someone else modified it); retry from step 1.

**Q14. Why is checking affected row count essential in optimistic locking?**
A: The `WHERE id = ? AND version = ?` clause silently produces zero affected rows if the version has changed — the database doesn't raise an error; it just updates nothing. If you don't check the affected row count and assume success, you have silently dropped your own write. ORMs like Hibernate throw an `OptimisticLockException` by checking this automatically, but in raw SQL you must check it yourself.

**Q15. Can you use a timestamp instead of an integer version counter?**
A: Yes, but with caveats. Timestamps work if their precision is fine enough that two concurrent writes can't happen within the same tick. Millisecond precision is often too coarse for high-throughput systems — two transactions completing in the same millisecond both succeed and one silently loses. Integer version counters are strictly monotonic and don't have this problem. If using timestamps, prefer database-generated timestamps (`NOW()` called inside the transaction) rather than application-side clock values, which may drift.

**Q16. What is Compare-And-Swap (CAS) and how does it relate to optimistic locking?**
A: CAS is the hardware/CPU-level primitive underlying most lock-free data structures: atomically check that a memory location still holds an expected value, and if so, replace it with a new value — otherwise fail. Optimistic locking in databases is the storage-layer equivalent: the `UPDATE ... WHERE version = ?` is a CAS operation at the row level. Redis's `WATCH`/`MULTI`/`EXEC` transaction mechanism is another CAS-style optimistic locking pattern — `WATCH` marks a key, and `EXEC` aborts the transaction if the key changed since `WATCH` was called.

**Q17. How does optimistic locking interact with long-running transactions or user think time?**
A: Optimistic locking's strength is that it holds no locks during the "think time" between read and write — ideal for user-facing workflows where a user reads data, spends 30 seconds editing a form, then submits. Pessimistic locking would hold a DB lock for those 30 seconds, blocking everyone else. With optimistic locking, no lock is held; if two users edit simultaneously, the second to submit gets a conflict and must re-read. The conflict rate is usually low (most data isn't being edited by two people simultaneously), making optimistic locking a natural fit for long-read-modify-write cycles.

**Q18. How do ORMs typically implement optimistic locking?**
A: Most major ORMs have first-class support via annotations or configuration:
- **Hibernate/JPA** — `@Version` annotation on an integer or timestamp field. Hibernate automatically appends `AND version = ?` to update queries and increments the version. Throws `OptimisticLockException` on conflict.
- **ActiveRecord (Rails)** — `lock_version` column (by convention). Automatically handled if the column exists.
- **SQLAlchemy** — `version_id_col` parameter on `Mapper`. Raises `StaleDataError` on conflict.

The ORM handles the check-and-increment, but the application must still catch the exception and implement retry logic.

## Section 4: Failure Modes & Anti-patterns

**Q19. What is the "ABA problem" in optimistic locking, and when does it matter?**
A: The ABA problem: a row is at version A, another transaction changes it to B, then back to A. Your transaction read version A initially and at commit time sees version A again — the version check passes, but the data was changed and changed back in between. With integer monotonic version counters this can't happen (version only increments), but with timestamps or checksum-based detection it can. The fix: always use a strictly monotonic version counter, never a content hash or timestamp for conflict detection.

**Q20. What is "retry storm" in optimistic locking and what causes it?**
A: Under high contention, many transactions conflict simultaneously, all retry at the same time, conflict again, retry again — amplifying load on the database rather than reducing it. This is the mirror image of the thundering herd problem. Causes: high write contention on a hot row (e.g., a global counter), unbounded retry loops with no backoff. Mitigations: exponential backoff with jitter on retry, limiting retry attempts with a circuit breaker, or recognizing that high contention is a signal to switch to pessimistic locking or redesign the data model (e.g., shard the counter).

**Q21. What is the "phantom retry" anti-pattern?**
A: Retrying an optimistic conflict without re-reading the data — reusing the stale read from the original attempt and just re-submitting the update with a new version guess. This defeats the entire purpose of optimistic locking: the retry must re-read the current state from the DB and recompute the update based on the fresh data, not blindly re-apply the same delta. Failing to re-read means you're still working from a stale base and the business logic result may be wrong even if the version check passes.

**Q22. What is "write skew" and does optimistic locking prevent it?**
A: Write skew is a concurrency anomaly where two transactions each read overlapping data and make decisions based on it that are individually valid but collectively violate a constraint. Example: two doctors each check that at least one doctor is on call, both see one other doctor on call, and both go off-call — now no one is on call. Standard row-level optimistic locking doesn't prevent write skew because neither transaction modified the rows the other read — their version checks both pass. Preventing write skew requires either `SELECT FOR UPDATE` on all rows involved in the constraint check (pessimistic), `SERIALIZABLE` isolation level (which uses predicate locking or SSI), or explicit application-level constraint checking.

**Q23. What is "silent data loss" and how does it happen with optimistic locking?**
A: If a conflict is detected (0 rows affected) but the application code doesn't check the affected row count and treats the write as successful, the update is simply dropped — no error, no exception, no log. The user thinks their change was saved; it wasn't. This is the most dangerous optimistic locking bug, and it's easy to introduce when writing raw SQL. Always assert `affected_rows == 1` or use an ORM that raises an exception automatically.

**Q24. What are the risks of very long optimistic locking retry loops?**
A: Without a retry limit: an application under high contention may loop indefinitely, wasting CPU, holding application-level resources (memory, threads, connection pool slots), and never making progress — effectively a livelock. Always bound retry attempts (e.g., max 3–5 retries), and escalate to an error after exhausting them. Some systems escalate to pessimistic locking after N failed optimistic attempts as a fallback.

**Q25. What happens if you forget to include the version column in your SELECT but include it in the WHERE clause of the UPDATE?**
A: You can't perform the conflict check correctly because you don't have the version value from the original read. You'd be forced to hard-code a version or fetch it separately, breaking atomicity of the check-and-update. This is usually a code bug; ORMs prevent it by managing the version field automatically. In raw SQL, always `SELECT` the version column explicitly alongside the data columns.

## Section 5: Isolation Levels & Locking Interaction

**Q26. How do database isolation levels relate to locking strategy choice?**
A: Isolation levels define what anomalies a transaction may observe; locking strategies are one mechanism to implement them:
- **READ COMMITTED** (most common default) — sees only committed data. Provides no protection against lost updates by itself; you need explicit pessimistic (`FOR UPDATE`) or application-level optimistic locking.
- **REPEATABLE READ** — guarantees that rows read in a transaction don't change if re-read. In MySQL InnoDB this prevents lost updates via gap locks. In PostgreSQL it uses snapshot isolation — you still need explicit locking or versioning to prevent lost updates in some patterns.
- **SERIALIZABLE** — the strongest level; prevents all anomalies including write skew. Implemented via predicate locking or Serializable Snapshot Isolation (SSI in PostgreSQL). Essentially the DB implements optimistic concurrency control automatically; you don't need application-level versioning, but throughput is lower.

**Q27. What is Serializable Snapshot Isolation (SSI) and how does it relate to optimistic locking?**
A: SSI (used by PostgreSQL's `SERIALIZABLE` isolation level) is a database-level optimistic concurrency control mechanism. It tracks read and write dependencies between concurrent transactions and detects serialization conflicts at commit time — exactly like application-level optimistic locking but transparently, without requiring version columns. Transactions that would cause a non-serializable outcome are aborted and must retry. The trade-off: it adds overhead to every transaction and can produce more aborts than you'd expect, but it's simpler to use correctly than manual optimistic locking and prevents all anomalies including write skew.

**Q28. Why does `READ COMMITTED` not prevent lost updates by itself?**
A: Under `READ COMMITTED`, each statement sees a fresh snapshot of committed data, but two concurrent transactions can still both read the same value, both compute an update independently, and both write back — the second overwriting the first without knowing it. The isolation level prevents dirty reads but doesn't prevent the interleaving of independent read-modify-write cycles. You still need either `SELECT FOR UPDATE` (pessimistic) or application-level version checking (optimistic) to close this gap.

## Section 6: Trade-offs & Decision-Making

**Q29. When should you choose pessimistic locking?**
A:
- **High contention on specific rows** — if multiple writers frequently target the same row (e.g., a bank account balance), optimistic locking's retry storm becomes expensive; pessimistic is more predictable.
- **Short, fast transactions** — lock hold time is brief, so blocking other transactions is low-cost.
- **Non-idempotent side effects** — if the work inside the transaction has external effects (sending an email, charging a card) that can't be safely retried, it's better to block than to conflict and retry.
- **Complex constraint validation across multiple rows** — where optimistic locking can't easily prevent write skew without `SERIALIZABLE` isolation.

**Q30. When should you choose optimistic locking?**
A:
- **Low to medium write contention** — conflicts are rare; avoiding upfront lock overhead is a net win.
- **Long read-modify-write cycles** (user think time, multi-step workflows) — holding a DB lock for seconds or minutes is untenable.
- **High read/write ratio** — most operations are reads; locking on reads adds unnecessary overhead.
- **Distributed systems without a shared lock manager** — optimistic locking via version columns works across horizontally scaled app servers without any shared state; pessimistic locking requires all writers to go through the same lock manager.
- **Idempotent or safe-to-retry operations** — retrying a failed optimistic write is straightforward; retrying a non-idempotent operation is not.

**Q31. How does the choice change in a microservices / distributed architecture?**
A: Pessimistic database-level locks (`SELECT FOR UPDATE`) only work when all writers share the same database connection and the same DB instance. Across services or DB shards, there's no shared lock manager — you'd need a distributed lock (Redis `REDLOCK`, ZooKeeper) which introduces its own failure modes (lock expiry, coordinator failure). Optimistic locking with version columns works naturally across multiple app service instances hitting the same DB — no shared infrastructure needed. For cross-service transactions, neither approach applies cleanly; Sagas or event-driven patterns are more appropriate.

**Q32. What is "optimistic locking in caches" and how is it implemented?**
A: Redis supports optimistic locking via `WATCH`/`MULTI`/`EXEC`: `WATCH key` registers the key for observation; if it's modified before `EXEC` runs, the transaction aborts (returns `nil`). This is the Redis equivalent of checking a version column — the client detects a conflict and retries. It's used for atomic read-modify-write on cache values (e.g., incrementing a counter without a native atomic command, updating a complex JSON blob). Like database optimistic locking, it relies on the caller implementing retry logic.

**Q33. What is "optimistic offline lock" and how does it differ from database-level optimistic locking?**
A: Optimistic offline lock (Martin Fowler's pattern) extends optimistic locking to span multiple HTTP requests in a user session. The version is surfaced to the client (e.g., as an HTTP `ETag` header or a hidden form field), held in the browser, and sent back with the write request. The server validates the version before committing. This handles long user-facing edit sessions where a DB transaction can't stay open. Database-level optimistic locking is scoped to a single DB transaction; offline lock is scoped to a user session that may span many requests over many minutes.

## Section 7: Scenario / System Design Style Questions

**Q34. "Two users open the same inventory record (stock: 10 units), both sell 8 units simultaneously. Walk through what happens under each strategy."**
A:
- **Pessimistic**: User A's transaction issues `SELECT stock FROM inventory WHERE id = 1 FOR UPDATE`. Gets lock. Reads stock = 10. Checks 8 ≤ 10, proceeds. User B's `SELECT ... FOR UPDATE` blocks. User A writes stock = 2, commits, releases lock. User B unblocks, reads stock = 2, checks 8 ≤ 2 — fails, returns "insufficient stock." Correct outcome, no oversell.
- **Optimistic**: Both read stock = 10 (version = 7). Both check 8 ≤ 10 — ok. User A's `UPDATE inventory SET stock = 2, version = 8 WHERE id = 1 AND version = 7` → 1 row affected, succeeds. User B's `UPDATE inventory SET stock = 2, version = 8 WHERE id = 1 AND version = 7` → 0 rows affected (version is now 8). Conflict detected. User B re-reads stock = 2, re-checks 8 ≤ 2 — fails. Correct outcome, no oversell — but required a retry cycle.

**Q35. "You have a job queue table where workers pull tasks using `SELECT ... FOR UPDATE SKIP LOCKED`. Why is this better than a simple `SELECT` without locking?"**
A: Without `FOR UPDATE SKIP LOCKED`, multiple workers can read the same row simultaneously (since reads don't block each other), each believing they've claimed the job, and execute it concurrently — the job runs multiple times. `FOR UPDATE SKIP LOCKED` ensures each row is exclusively claimed by exactly one worker: the lock prevents concurrent claims, and `SKIP LOCKED` means other workers don't block waiting — they just move on to the next available row. This gives you a high-throughput, exactly-once-dispatch queue using only the database, with no external coordinator.

**Q36. "A user edits a long form that takes 5 minutes to fill out. When they submit, another user has already updated the same record. What strategy fits best and how do you surface the conflict to the user?"**
A: Optimistic offline locking. Include the current version (or `ETag`) in the form as a hidden field (or in the HTTP request). On submit, the server runs `UPDATE ... WHERE id = ? AND version = ?`. If 0 rows affected, return a `409 Conflict` response with the current server-side data. The client presents a merge UI — show the user what changed while they were editing and let them resolve the conflict (accept theirs, accept the server's, or merge). Never silently discard the user's work, and never hold a DB lock for 5 minutes. Pessimistic locking is completely wrong here — it would block all other users of that record for the duration of the form session.

**Q37. "Your global leaderboard has a single row storing the top score. Under high load, optimistic lock retries are causing 60% failure rates. What do you do?"**
A: The root cause is a hot row with high write contention — optimistic locking's worst case. Options in order of invasiveness:
1. **Switch to pessimistic locking** for this specific row: `SELECT ... FOR UPDATE` serializes writes, eliminates retries, accepts throughput serialization.
2. **Batch writes** — buffer score updates in memory or a fast store (Redis) and persist the leaderboard row in periodic batches, drastically reducing write frequency.
3. **Shard the counter** — split the leaderboard into N partial rows and merge on read. Each writer targets a random shard, reducing per-shard contention by 1/N.
4. **Use a database-native atomic operation** — `UPDATE leaderboard SET top_score = GREATEST(top_score, ?) WHERE id = 1` is a single atomic statement; no read-modify-write cycle, no versioning needed.
The core lesson: high contention on a single row is a data model problem, not a locking strategy problem. Fix the model first.

**Q38. "How would you implement optimistic locking for a document store (e.g., MongoDB) that doesn't have native version column support?"**
A: Add a `version` field manually to each document. Use MongoDB's **atomic `findAndModify`** (or `findOneAndUpdate`) with a filter that includes the version:
```
db.collection.findOneAndUpdate(
  { _id: id, version: versionRead },
  { $set: { ...data, version: versionRead + 1 } },
  { returnDocument: "after" }
)
```
If the document was modified (version changed), the filter matches nothing and the operation returns `null` — conflict detected. The caller must re-read and retry. This is exactly the same pattern as SQL `UPDATE ... WHERE version = ?`, just using MongoDB's atomic document-level operations. DynamoDB has a native equivalent via `ConditionExpression: "version = :expected"` in `PutItem`/`UpdateItem` calls.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                    | Pessimistic Locking                                       | Optimistic Locking                                         |
|---                        |---                                                        |---                                                         |
| Core assumption           | Conflicts are likely — prevent them upfront               | Conflicts are rare — detect and retry after the fact       |
| Lock held when            | From first read to commit/rollback                        | Never — no lock held; version checked at commit only       |
| Blocking behavior         | Competing writers block and wait                          | Competing writers proceed; loser retries                   |
| Deadlock risk             | Yes — circular lock waits possible                        | No — no locks to deadlock on                               |
| Retry logic required      | No (waits automatically)                                  | Yes — application must catch conflicts and retry           |
| Write skew prevention     | Yes, with `FOR UPDATE` on all relevant rows               | No — needs `SERIALIZABLE` isolation or explicit design     |
| Long think time suitability | No — holds DB lock for session duration               | Yes — no lock held between read and write                  |
| Hot row / high contention | Predictable (serialized queue)                            | Retry storm — degrades badly                               |
| Distributed systems       | Requires shared lock manager (hard across services)       | Works naturally with version columns across service nodes  |
| Best for                  | Short transactions, high contention, non-idempotent ops   | Long sessions, low contention, read-heavy, distributed     |
| DB mechanism              | `SELECT FOR UPDATE`, `SELECT FOR SHARE`                   | Version column + `UPDATE ... WHERE version = ?`            |

## Key Concepts Cheat Sheet

| Term                      | One-line definition                                                                              |
|---                        |---                                                                                               |
| Lost update               | Two concurrent read-modify-write cycles where the second write silently overwrites the first     |
| Pessimistic locking       | Acquire exclusive lock before reading; block all other writers for the transaction's duration    |
| Optimistic locking        | No lock on read; version-check at commit time; retry on conflict                                 |
| `SELECT FOR UPDATE`       | SQL clause that acquires a row-level exclusive lock on all returned rows                         |
| `SKIP LOCKED`             | Skips rows already locked instead of blocking — used for concurrent job queue workers            |
| `NOWAIT`                  | Fails immediately if the lock is unavailable instead of blocking                                 |
| Version column            | Integer counter incremented on every write; the conflict-detection token in optimistic locking   |
| ABA problem               | Version check passes despite intervening change because the value returned to its original state |
| Write skew                | Concurrent transactions each see valid state and write validly, but the combined result violates a constraint |
| Retry storm               | High contention causes many optimistic conflicts simultaneously, all retrying and re-conflicting |
| Optimistic offline lock   | Extends optimistic locking across multiple HTTP requests using ETags or hidden form version fields|
| CAS (Compare-And-Swap)    | Atomic hardware/storage primitive: update only if current value matches expected value           |
| SSI                       | Serializable Snapshot Isolation — DB-level optimistic CC that prevents all anomalies transparently|
| Lock escalation           | DB converts many row locks into a page/table lock to save memory, increasing contention          |
| Deadlock                  | Circular lock dependency; DB resolves by aborting a victim transaction                           |

**Tip for the interview:** The strongest candidates frame the choice as a **contention probability problem**, not a preference. Start there: "How likely are conflicts? How long is the lock held? Are operations idempotent?" Then move to the edge cases — write skew (optimistic locking doesn't cover it without `SERIALIZABLE`), the hot-row retry storm (optimistic's worst case), and long user sessions (pessimistic's worst case). Finishing with the distributed systems angle — that pessimistic locking requires a shared lock manager that doesn't exist across services — shows you've connected it to real architecture.
