# Idempotency: Keys, Natural vs Artificial — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does idempotency mean in distributed systems?**
A: An operation is idempotent if executing it multiple times produces the same result as executing it once. The system state after N identical calls is identical to the state after 1 call. This is critical in distributed systems because networks are unreliable — requests time out, connections drop, and clients retry. If retried operations are not idempotent, you get double charges, duplicate records, or inconsistent state.

**Q2. Why is idempotency a distributed systems problem specifically?**
A: In a single-process in-memory system, you control exactly when operations execute. In a distributed system, a client can't distinguish between "the server received my request and failed before responding" and "the server never received my request." In both cases, the client times out and retries — but the first case may have already committed the operation. Without idempotency, that retry causes a duplicate. The client has no safe way to retry without it.

**Q3. What is the difference between idempotency and exactly-once semantics?**
A: Related but different:
- **Idempotency** — a property of the *operation itself*: applying it multiple times is safe. The burden is on the server to detect and deduplicate.
- **Exactly-once semantics** — a delivery guarantee: a message or request is processed *exactly once*, not zero or more than once. Achieved by combining at-least-once delivery with server-side idempotency checks.

True exactly-once is extremely hard to guarantee end-to-end across network boundaries. The practical approximation is: at-least-once delivery + idempotent consumer. The consumer deduplicates; the producer retries freely.

**Q4. What is natural idempotency?**
A: When the operation's semantics are inherently safe to repeat without extra deduplication logic. The operation produces the same outcome regardless of how many times it's called. Examples:
- `SET user.email = 'a@b.com'` — running it 10 times leaves the same email.
- `DELETE FROM orders WHERE id = 42` — the row is gone after the first call; subsequent calls are no-ops.
- `PUT /users/42 { "name": "Alice" }` — HTTP PUT with a full resource representation is idempotent by definition.
- `GET /users/42` — reads never mutate state.

**Q5. What is artificial idempotency?**
A: When the operation is not naturally idempotent (e.g., "charge $100", "insert a record", "send an email"), and you engineer idempotency on top by:
1. Assigning a unique key to each logical operation.
2. Storing whether that key was already processed.
3. On duplicate arrival, returning the stored result instead of re-executing.

This is the idempotency key pattern. It's "artificial" because the safety comes from external bookkeeping, not from the operation's own semantics.

**Q6. Give examples of operations that are NOT naturally idempotent.**
A:
- `INSERT INTO orders ...` — inserts a new row each time.
- `UPDATE accounts SET balance = balance - 100` — decrements on every call.
- Charging a payment card — each API call initiates a new charge.
- Sending an email or SMS — each invocation delivers another message.
- `POST /orders` — HTTP POST is not idempotent by definition.
- Incrementing a counter, appending to a log, enqueuing a message.

All of these require artificial idempotency if they must be retryable.

## Section 2: Idempotency Keys

**Q7. What is an idempotency key?**
A: A unique identifier, generated by the *client*, that represents a specific logical operation. The client attaches it to every request (typically as a header: `Idempotency-Key: <uuid>`). The server uses it to detect duplicate requests and return the cached result of the original execution instead of re-executing.

**Q8. Who generates the idempotency key — client or server?**
A: The **client** generates it, before the first attempt. This is essential: the key must be the same across all retries of the same logical operation. If the server generated the key, the client wouldn't know it before the first request succeeded — making it useless for retries. The client generates a UUID (or similar unique token) when it decides to perform an operation (e.g., "place this order") and reuses that same key on every retry until it gets a definitive success or failure response.

**Q9. How does a server implement idempotency key handling?**
A: The typical implementation:

```
1. Extract idempotency key from request header.
2. Look up the key in an idempotency store (Redis, DB table).
3. If found AND completed:
   → Return the stored response (status code + body). Do not re-execute.
4. If found AND in-progress (another request is currently executing):
   → Return 409 Conflict (or wait briefly and retry lookup).
5. If not found:
   → Mark key as in-progress (with TTL).
   → Execute the operation.
   → Store the result against the key.
   → Return the result to the client.
```

The key insight: the stored response must include the HTTP status code, not just a success flag — so that even a "payment declined" result is returned as-is on retry, not re-attempted.

**Q10. What should the idempotency store contain?**
A: Per key:
- The idempotency key itself (primary key).
- The request fingerprint (optional but useful — hash of request body to detect same-key-different-body misuse).
- The response status code.
- The response body (serialized).
- Execution status: `IN_PROGRESS`, `COMPLETED`.
- Created-at timestamp (for TTL / expiry).
- Expiry timestamp — keys should not be stored forever; 24–48 hours is typical for payment APIs.

**Q11. What happens if two concurrent requests arrive with the same idempotency key?**
A: Race condition — both find the key absent and attempt to execute. Without locking, you get a duplicate execution. Fix:
- **Atomic insert / optimistic lock:** Use `INSERT ... ON CONFLICT DO NOTHING` or a Redis `SET NX` (set if not exists). Only one writer wins; the other gets a conflict and waits for the first to complete.
- **Distributed lock (Redis SETNX + TTL):** Lock on the key before executing. On lock failure, wait and poll for the result.
- **Transactional outbox with DB unique constraint:** Insert the idempotency record in the same DB transaction as the operation itself. The unique constraint rejects the duplicate at the DB level.

**Q12. What is the "same key, different body" problem?**
A: A client sends request A with idempotency key K, gets a response, then — due to a bug — sends a completely different request B using the same key K. Options for server behavior:
- **Reject with 422** — hash the request body on first receipt; on subsequent requests with the same key, compare the hash. If it differs, return a 422 Unprocessable Entity with a clear error ("idempotency key reuse with different parameters").
- **Ignore body, return cached** — safer but can mask client bugs.

Stripe's API uses body fingerprinting and returns a 422 on mismatch — good practice for financial APIs.

**Q13. How long should idempotency keys be retained?**
A: Long enough to cover the maximum retry window your clients use, plus a safety margin. Practical guidelines:
- Payment APIs (Stripe-style): 24–48 hours is standard.
- Internal microservice calls: 1–24 hours depending on retry policy.
- Message queue consumers: retain until the consumer's deduplication window (Kafka's `enable.idempotence` uses a producer epoch + sequence number within a session; for longer windows, use an external store).
Keys should not be retained indefinitely — this grows the store unboundedly. Use TTL-based expiry. After expiry, a client retrying with the same key is treated as a new request.

## Section 3: Designing for Idempotency

**Q14. How do you make a database INSERT idempotent?**
A: Several approaches:
- **Natural unique key:** If the record has a natural unique identifier (e.g., `order_id` generated by the client), use a DB unique constraint. A duplicate insert hits the constraint and fails; the application catches the conflict and treats it as success.
- **INSERT ... ON CONFLICT DO NOTHING / DO UPDATE:** Postgres `ON CONFLICT` clause makes upsert behavior explicit and atomic.
- **Idempotency key foreign key:** Store the idempotency key as a column with a unique constraint. The insert either succeeds (new) or hits the constraint (duplicate), and you return the existing record.

```sql
INSERT INTO payments (idempotency_key, amount, user_id, status)
VALUES ($1, $2, $3, 'pending')
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;
```

**Q15. How do you make a payment charge idempotent?**
A: At each layer:
- **Client → Your API:** Client generates UUID, sends `Idempotency-Key` header. Your API deduplicates as described in Q9.
- **Your API → Payment Processor:** Pass the idempotency key (or a derivative) to the processor's API. Stripe, Razorpay, and most payment processors accept an `Idempotency-Key` header and deduplicate on their end.
- **Your DB:** Record the charge with a unique constraint on `(idempotency_key, processor_charge_id)`. If your API retried the processor and got a duplicate response, store the original charge ID.

The key principle: pass the idempotency key through the entire call chain. Don't generate a new key at each layer — that defeats deduplication at downstream services.

**Q16. How do you make a message queue consumer idempotent?**
A: Kafka (and most queues) guarantee at-least-once delivery — a message may be delivered more than once due to consumer rebalance or offset commit failure. To make the consumer idempotent:
- **Deduplication table:** Before processing, check a `processed_message_ids` table (or Redis set) for the message's unique ID. If present, skip. If absent, process and insert.
- **Upsert instead of insert:** Design the consumer's DB write as an upsert on a natural key — duplicate processing produces the same final state.
- **Kafka's transactional API:** For produce-consume-produce patterns, use Kafka transactions + `enable.idempotence=true` on the producer. This gives exactly-once within the Kafka ecosystem, but not for external side effects (DB writes, API calls).

**Q17. How do you handle idempotency for operations with external side effects that can't be undone?**
A: Side effects like sending an email, triggering a webhook, or initiating a wire transfer can't be "un-done" if a duplicate slips through. Strategies:
- **Gate on status:** Before executing the side effect, check an idempotency/status table. Only execute if status is `PENDING` — update to `COMPLETED` atomically with the side effect (or in a two-step: mark `IN_PROGRESS`, execute, mark `COMPLETED`).
- **Outbox pattern:** Write the intent to an outbox table in the same DB transaction as the business logic. A separate publisher reads the outbox and delivers the side effect exactly once (deduplicating on the outbox record ID).
- **Accept bounded duplicates:** For low-stakes side effects (e.g., analytics events), accept that rare duplicates may occur and design the consumer to tolerate them (count-distinct rather than count, etc.).

**Q18. What is the transactional outbox pattern and how does it enforce idempotency?**
A: Instead of calling an external service (queue, email provider, webhook) directly inside a DB transaction — which can't be atomic with the DB commit — you write a record to an `outbox` table in the same transaction. A separate "relay" process reads undelivered outbox records and publishes them.

```sql
BEGIN;
  UPDATE orders SET status = 'confirmed' WHERE id = $1;
  INSERT INTO outbox (id, event_type, payload, published)
    VALUES (gen_random_uuid(), 'ORDER_CONFIRMED', $payload, false);
COMMIT;
```

Idempotency: the outbox record has a unique ID. The relay marks it `published = true` after successful delivery. On relay restart, it retries only unpublished records. Downstream consumers deduplicate on the outbox record ID. This gives you at-least-once with a clear deduplication handle.

## Section 4: HTTP & API Design

**Q19. Which HTTP methods are idempotent by spec, and which aren't?**
A:
- **Idempotent by spec:** GET, HEAD, PUT, DELETE, OPTIONS. Calling them N times should have the same server state effect as calling once.
- **Not idempotent:** POST, PATCH (by default — PATCH is idempotent only if the patch is a replacement, not an increment).

This is why REST convention uses POST for "create new resource" (not idempotent) and PUT for "replace entire resource at known URL" (idempotent). The URL being the resource identifier is what makes PUT idempotent — `PUT /orders/42` always refers to the same resource.

**Q20. If PUT is idempotent, why do we need idempotency keys for APIs that use POST?**
A: HTTP method idempotency is a *specification contract*, not an implementation guarantee. A server can violate it. More importantly, POST is the common verb for financial operations ("create a charge", "place an order") because the resource ID is server-generated. For these, the idempotency key is the mechanism that makes a POST behave idempotently: the client provides the uniqueness token since the URL can't carry it (the resource doesn't exist yet before the first successful request).

**Q21. How does Stripe's idempotency key implementation work, and what can you learn from it?**
A: Stripe sets the gold standard:
- Clients send `Idempotency-Key: <client-generated-uuid>` on any POST.
- Stripe stores the key, request fingerprint (hash of URL + body), and response for 24 hours.
- Replays return the exact same HTTP status and body as the original.
- Reuse of a key with a different body returns 400 with an explanatory error.
- Keys are scoped per API key (so two different merchants can use the same UUID without collision).

Lessons: store the full response (not just "success/fail"), fingerprint the request body, scope keys per caller identity, and set an explicit TTL.

## Section 5: Trade-offs & Failure Modes

**Q22. What are the failure modes of idempotency key implementations?**
A:
- **Key store unavailable:** If Redis/DB is down, you can't check for duplicates. You must choose: fail the request (safe, but adds downtime) or proceed without deduplication (risky, may duplicate). For financial operations, always fail safe.
- **IN_PROGRESS lock never released:** If the server crashes mid-execution, the key is stuck as `IN_PROGRESS` and all retries get 409. Fix: set a TTL on the `IN_PROGRESS` state (e.g., 30 seconds). After TTL expiry, treat it as a fresh attempt.
- **Race condition on concurrent retries:** Two retries arrive simultaneously, both find the key absent (before either inserts). Fix: atomic insert with unique constraint (see Q11).
- **TTL too short:** Key expires before the client's retry window. The client retries after expiry, gets treated as a new request, and a duplicate executes. Fix: align TTL with the maximum realistic retry window.
- **Response too large to store:** Storing a full response body can be expensive for large payloads. Fix: store a reference (e.g., the created resource ID) and reconstruct the response rather than serializing the full body.

**Q23. What's the difference between idempotency and deduplication?**
A: Often used interchangeably but have a subtle distinction:
- **Idempotency** — a property of an operation. Focuses on the server returning the same *outcome* regardless of how many times the operation is invoked.
- **Deduplication** — a mechanism/process of detecting and discarding duplicate inputs before processing. Focused on the detection layer.

Deduplication is one *implementation* of idempotency. You can also achieve idempotency without explicit deduplication — through natural idempotency (e.g., upsert semantics), where duplicate processing still produces the correct outcome. Deduplication is necessary when the operation has side effects that can't be made naturally idempotent (payment charges, emails).

**Q24. How does idempotency interact with distributed caching?**
A: When using Redis as the idempotency store, watch for:
- **Cache eviction under memory pressure:** If Redis evicts idempotency keys before TTL expiry (due to `maxmemory-policy allkeys-lru`), duplicates slip through. Fix: use a dedicated Redis instance (or namespace) for idempotency with `noeviction` policy, or use a DB as the source of truth.
- **Redis cluster split-brain:** Under a network partition, two Redis nodes may both accept the same key as new. Fix: use Redis with `WAIT` for synchronous replication before returning success on the first write, or use a DB with stronger consistency.
- **Cold start after Redis flush:** If Redis is flushed (deploy, disaster recovery), all idempotency history is lost. Clients retrying within the TTL window now get duplicate execution. Fix: persist idempotency keys to a DB (Redis as cache, DB as source of truth), or accept this as a rare acceptable risk.

## Section 6: Scenario / System Design Style Questions

**Q25. "Design the idempotency layer for a payment API that receives POST /charges from mobile clients on unreliable networks."**
A:
- **Client:** Generate `idempotency_key = UUID v4` when the user taps "Pay." Store it locally. Attach as `Idempotency-Key` header on every retry. Retry with exponential backoff (1s, 2s, 4s, max 30s) for up to 5 minutes.
- **API gateway:** Extract and validate key format. Reject requests missing the key with 400.
- **Application layer:**
  1. Atomic `INSERT INTO idempotency_keys (key, status, fingerprint) VALUES (...) ON CONFLICT DO NOTHING`.
  2. If conflict: fetch existing record → if COMPLETED, return stored response; if IN_PROGRESS, return 202 or poll.
  3. If inserted: mark IN_PROGRESS, call payment processor with the same key as their idempotency key, store result, mark COMPLETED.
- **Payment processor:** Pass client's key (or a `sha256(api_key + client_key)` namespaced version) to Stripe/Razorpay.
- **TTL:** 48 hours. `IN_PROGRESS` auto-expires after 60 seconds (handles server crash mid-execution).
- **Monitoring:** Alert on `IN_PROGRESS` keys older than 2 minutes — indicates a stuck execution.

**Q26. "A Kafka consumer processes 'send welcome email' events. Kafka delivers the same event twice due to a rebalance. How do you prevent the user from receiving two welcome emails?"**
A: The message itself is not naturally idempotent — sending an email is a side effect. Two-layer defence:
1. **Deduplication table check:** Before calling the email provider, check `SELECT 1 FROM sent_emails WHERE event_id = $1`. If found, skip. The `event_id` comes from the Kafka message's unique identifier (topic + partition + offset, or a business-level `user_id + event_type` composite).
2. **Upsert on insert:** `INSERT INTO sent_emails (event_id, user_id, sent_at) VALUES (...) ON CONFLICT DO NOTHING`. Only call the email provider if the insert succeeds (rows affected = 1).
3. **Outbox cross-check (stronger):** The welcome email row is written to an outbox in the same transaction that marks the user as "welcome email pending." The outbox relay calls the email provider and marks it delivered. Kafka duplicate → outbox record already marked delivered → skip.

This gives you idempotency even if the consumer crashes between the email send and the offset commit.

**Q27. "Your team proposes generating idempotency keys server-side to 'simplify the client.' What's wrong with this?"**
A: It fundamentally breaks the retry safety guarantee. Idempotency keys exist for this scenario: the client sends a request, the server processes it, but the response is lost in transit (network failure). The client needs to retry — but it needs to send the *same key* it sent before, so the server recognizes it as a duplicate. If the server generates the key on receipt, the client doesn't know it before the first request, so:
- First request: server generates key K, processes operation, response lost.
- Client retry (can't send K — doesn't know it): server generates new key K', processes operation again → duplicate.

The only safe model: client generates the key *before any network call*, persists it locally if necessary, and reuses it on every retry. Server-side key generation can only work for non-retried flows (which defeats the purpose).

## Quick Reference: Natural vs Artificial Idempotency

| Operation                         | Natural?  | Why / How                                                           |
|---                                |---        |---                                                                  |
| GET /resource                     | Yes       | Read-only, no state change                                          |
| PUT /resource (full replacement)  | Yes       | Same payload → same resulting state                                 |
| DELETE /resource                  | Yes       | Resource absent after first call; subsequent calls are no-ops       |
| SET email = 'x@y.com'             | Yes       | Absolute assignment, not relative                                   |
| INSERT with unique constraint     | Yes       | Duplicate insert fails gracefully, state unchanged                  |
| POST /charges                     | No        | New charge on every call without idempotency key                    |
| balance = balance - 100           | No        | Relative update; each call changes state further                    |
| Send email                        | No        | Each call delivers another email                                    |
| Append to log / queue             | No        | Each call adds a new entry                                          |
| Increment counter                 | No        | Each call changes the value                                         |

---

**Tip for the interview:** Idempotency questions almost always escalate to failure scenarios — "what if the key store goes down," "what if two retries race," "what if the server crashes between execution and storing the result." Have a clear mental model of the happy path (Q9) and then be ready to walk through each failure mode with a mitigation. The other differentiator at senior level: knowing *which* layer to add idempotency at (client key generation, API layer dedup, DB upsert, queue consumer dedup, third-party API key passthrough) — and that all layers are often needed in a complete implementation.
