# SAGA Pattern: Choreography vs Orchestration — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does the SAGA pattern solve?**
A: In a microservices architecture, a business operation often spans multiple services — each with its own database. Traditional ACID transactions can't span service boundaries (you can't hold a two-phase lock across network calls to independent services). The SAGA pattern provides a way to maintain *eventual consistency* across services by breaking a distributed transaction into a sequence of local transactions, each of which publishes an event or message that triggers the next step.

**Q2. What is a SAGA?**
A: A sequence of local transactions across multiple services where each step has a corresponding *compensating transaction* that can undo its effect. If step N fails, the SAGA runs compensating transactions for steps N-1 through 1 in reverse order, rolling back the distributed operation to a consistent state — without ever holding distributed locks.

**Q3. What is a compensating transaction?**
A: A business-level undo operation for a completed local transaction. It doesn't literally reverse the DB operation (which may have been committed and visible to other processes); instead, it applies a semantic reversal. Examples:
- Step: "Reserve inventory" → Compensating: "Release inventory reservation"
- Step: "Charge payment" → Compensating: "Issue refund"
- Step: "Create shipment" → Compensating: "Cancel shipment"

Compensating transactions must be idempotent — they may be retried multiple times due to network failures.

**Q4. What consistency model does SAGA provide — and what does it NOT provide?**
A: SAGA provides *eventual consistency* — all services will reach a consistent state eventually, but there are transient windows where partial state is visible (e.g., payment charged but inventory not yet reserved). It does NOT provide:
- **Isolation** — other transactions can see intermediate states mid-SAGA.
- **Atomicity in the traditional sense** — success is not guaranteed in one shot; the system may go through failed + compensated states.
- **Immediate consistency** — the distributed state converges only after all steps (or all compensations) complete.

**Q5. What are the two implementation styles of SAGA?**
A:
- **Choreography** — no central coordinator. Each service listens for events from the previous step, performs its local transaction, and publishes its own event for the next step. Decentralized, event-driven.
- **Orchestration** — a central coordinator service (the "orchestrator") explicitly tells each participant what to do and in what order, tracking the overall SAGA state. Centralized, command-driven.

## Section 2: Choreography

**Q6. How does choreography-based SAGA work?**
A: Each service is both a consumer and a producer. When a service completes its local transaction, it publishes a domain event to a message broker (Kafka, RabbitMQ). The next service in the flow subscribes to that event, does its work, and publishes the next event. No service knows about the overall workflow — each only knows what event triggers it and what event it emits.

Example — Order flow:
1. **Order Service** creates order → publishes `OrderCreated`
2. **Payment Service** listens for `OrderCreated` → charges payment → publishes `PaymentCompleted`
3. **Inventory Service** listens for `PaymentCompleted` → reserves stock → publishes `InventoryReserved`
4. **Shipping Service** listens for `InventoryReserved` → creates shipment → publishes `ShipmentCreated`

On failure at step 3, Inventory publishes `InventoryReservationFailed` → Payment Service listens and issues refund → publishes `PaymentRefunded` → Order Service listens and marks order as `Cancelled`.

**Q7. What are the advantages of choreography?**
A:
- **Loose coupling** — services don't know about each other; they only know about events. Adding a new step means adding a new subscriber, not modifying existing services.
- **No single point of failure** — there's no orchestrator to go down.
- **Natural fit for event-driven architectures** — if you already have a message broker and event-driven services, choreography falls out naturally.
- **Simpler per-service logic** — each service handles only its own state machine.

**Q8. What are the disadvantages of choreography?**
A:
- **Distributed workflow visibility** — the overall SAGA state is implicit and spread across event logs. Answering "what is the current state of order #1234?" requires piecing together events from multiple topics.
- **Cyclic event dependencies** — as workflows grow, the event graph can become difficult to reason about. Service A listens to Service B which listens to Service C which listens to Service A.
- **Harder to debug** — a bug in a compensation flow may be discovered only when the events are traced end-to-end across multiple services and topics.
- **No centralized timeout/retry handling** — if a service crashes mid-SAGA and never publishes its completion event, the SAGA hangs silently unless each step has its own timeout+retry logic.

**Q9. How do you track overall SAGA progress in a choreography model?**
A: You typically build a dedicated *SAGA state store* — a read model that subscribes to all SAGA-related events and builds a current-state projection per SAGA instance. This isn't a coordinator; it doesn't issue commands. It's purely observability. Alternatively, you query an event log (Kafka topic replay, event sourcing store) to reconstruct the state of any given SAGA. Without this, you're flying blind in production.

**Q10. When should you prefer choreography?**
A:
- Simple, linear workflows with few steps (2–4 services).
- Teams already operating an event-driven architecture where event publishing is a standard pattern.
- When loose coupling between services is the top priority and teams own individual services independently.
- When the workflow rarely changes shape — new participants subscribe without modifying existing services.

## Section 3: Orchestration

**Q11. How does orchestration-based SAGA work?**
A: A dedicated **Orchestrator** service (or a stateful workflow engine) holds the SAGA definition and drives execution by sending commands to participant services and listening for their responses.

Example — same Order flow orchestrated:
1. Orchestrator sends `ReservePayment` command to Payment Service.
2. Payment Service replies with `PaymentReserved` or `PaymentFailed`.
3. On success, Orchestrator sends `ReserveInventory` to Inventory Service.
4. On success, Orchestrator sends `CreateShipment` to Shipping Service.
5. On any failure, Orchestrator sends compensating commands in reverse (`CancelShipment`, `RefundPayment`, `CancelOrder`).

The orchestrator tracks the current step and state of every in-flight SAGA instance in a persistent store.

**Q12. What are the advantages of orchestration?**
A:
- **Centralized visibility** — the orchestrator owns the SAGA state; you can query it directly to see exactly where any SAGA instance is stuck.
- **Explicit workflow definition** — the business process is codified in one place, making it easy to understand, audit, and modify.
- **Easier error handling and compensation** — the orchestrator decides when and how to compensate, with full context of what succeeded and what failed.
- **Timeouts and retries centralized** — one place to define retry policies, timeouts per step, and dead-letter handling.
- **Easier testing** — mock participant services and test the orchestrator's state machine directly.

**Q13. What are the disadvantages of orchestration?**
A:
- **Orchestrator as a God Service** — the orchestrator ends up knowing about all participants and their contracts. It can become a coupling hub that negates the independence of microservices.
- **Single point of failure risk** — if the orchestrator goes down mid-SAGA, in-flight SAGAs are stuck (mitigated with HA orchestrator and persistent state store, but adds operational complexity).
- **More boilerplate** — each SAGA needs command/reply message types, and the orchestrator needs explicit handling for each participant's success and failure responses.
- **Orchestrator proliferation** — complex systems end up with many orchestrators, each needing its own state store and HA deployment.

**Q14. What is a SAGA execution coordinator (SEC) and how does it relate to orchestration?**
A: The SEC is the component in an orchestrated SAGA that persists the SAGA state and drives execution. It typically:
- Stores the current step and status of every SAGA instance in a DB (e.g., a `saga_instances` table).
- Sends commands to participants via a message broker or HTTP.
- Listens for replies and updates state before triggering the next step.
- Resumes in-flight SAGAs on restart by replaying from the last persisted state.

Frameworks like Axon Framework, Eventuate Tram, Temporal, and AWS Step Functions all implement SEC-like behavior.

**Q15. When should you prefer orchestration?**
A:
- Complex, multi-step workflows with branching logic, conditional steps, or parallel branches.
- When you need strong observability into SAGA state out of the box.
- Teams that need to frequently change the workflow (adding or reordering steps) without touching participant services.
- When the business process has compliance/audit requirements (need a record of every step's decision).
- When you're adopting a workflow engine (Temporal, Step Functions) that provides SEC behavior for free.

## Section 4: Implementation Details

**Q16. How do you make SAGA steps idempotent and why is it critical?**
A: In a distributed system, message delivery is at-least-once — a participant may receive the same command/event more than once (network retry, consumer restart). If a step is not idempotent, re-processing it causes double charges, double reservations, etc. Implementation:
- **Idempotency key** — include a unique SAGA step ID in every command. Before processing, check if this key has already been processed (in a `processed_messages` table or Redis set). If yes, skip execution and re-publish the success reply.
- **Natural idempotency** — design operations to be inherently safe to repeat (e.g., "set inventory_reserved = true where order_id = X" is idempotent; "decrement stock by 1" is not).

**Q17. What is the "saga instance ID" and how is it used?**
A: A unique identifier assigned to each SAGA execution at creation time (e.g., a UUID). It's included in every command and event message throughout the SAGA. Each participant stores it alongside their local transaction record. The orchestrator (or choreography state store) uses it to correlate all steps belonging to the same distributed transaction. Without it, you can't associate a `PaymentFailed` event with the right order out of thousands of in-flight SAGAs.

**Q18. How do you handle a compensating transaction that itself fails?**
A: This is one of the hardest problems in SAGA. Options:
- **Retry with backoff** — compensating transactions should be retried aggressively (they're idempotent by design), with exponential backoff. Most transient failures (network blip, service restart) resolve within seconds.
- **Dead-letter queue (DLQ)** — after N retries, move the failed compensation to a DLQ. A human operator or automated alerting reviews and manually triggers or force-completes the compensation.
- **Pivot transaction model** — design SAGAs with a "point of no return" pivot step. Steps before the pivot can be compensated; steps after the pivot are retriable (not compensatable). This avoids needing to compensate truly irreversible operations (e.g., a wire transfer that has already settled).

**Q19. What is the "pivot transaction" concept in SAGA design?**
A: A pivot transaction is the step past which the SAGA is committed and cannot be rolled back — compensation is no longer possible, only forward retries. Everything before the pivot can be compensated if a later step fails. Everything after the pivot is designed to be retried until it succeeds (it must eventually succeed or require manual intervention). Choosing the pivot wisely is a business decision: typically it's the payment charge or the order confirmation — the point at which the customer has "paid" and the system is obligated to fulfill.

**Q20. How do you handle timeouts in a SAGA — what if a participant never replies?**
A:
- **Orchestration** — the orchestrator sets a per-step deadline. On timeout, it treats the step as failed and initiates compensation (or retries, depending on the step's retry policy). The orchestrator polls or uses a scheduled job to detect timed-out steps.
- **Choreography** — each service must implement its own timeout logic. A common pattern: each service sets a scheduled job to check for incomplete SAGA steps older than T minutes and publishes a timeout failure event. Without this, a missing event leaves the SAGA permanently stuck.

## Section 5: Trade-offs & Decision-Making

**Q21. Choreography vs Orchestration — how do you choose in a real system?**
A: Key decision factors:

| Factor | Lean Choreography | Lean Orchestration |
|---|---|---|
| Workflow complexity | Simple, linear (≤4 steps) | Complex, branching, conditional |
| Observability needs | Can build event-sourced read model | Need out-of-box state visibility |
| Team structure | Each team owns their service end-to-end | Central platform team owns workflow |
| Change frequency | Stable workflows | Frequently evolving business process |
| Existing infra | Event-driven / Kafka-first | Workflow engine available (Temporal, SFN) |

In practice: many systems start with choreography for simplicity and migrate to orchestration when workflow complexity or debugging pain exceeds a threshold.

**Q22. Can you mix choreography and orchestration in the same system?**
A: Yes, and it's common. A payment SAGA might be orchestrated (complex, multi-step, requires audit trail) while a notification SAGA (send email on order shipped) is choreographed (simple, fire-and-forget, naturally event-driven). The key is making the boundary explicit: don't let a choreography-based SAGA accidentally depend on the implicit ordering assumptions of an orchestrated one.

**Q23. How does SAGA interact with event sourcing?**
A: They complement each other well. In an event-sourced system:
- Each local transaction appends domain events to an event store — these are the same events choreography listens to.
- The complete SAGA history is reconstructable by replaying the event store — giving you the observability that pure choreography lacks.
- The event store provides the idempotency primitive (event IDs) and the durability guarantee needed for SAGA reliability.
Orchestration can also use event sourcing: the orchestrator stores its state as a sequence of SAGA state-change events, making recovery and auditing straightforward.

**Q24. What's the difference between SAGA and Two-Phase Commit (2PC)?**
A:
- **2PC** — a distributed protocol that coordinates all participants to either all-commit or all-abort atomically, using a prepare + commit round trip. Provides full ACID isolation. Requires all participants to hold locks during the protocol — doesn't work across services with independent DBs, has high latency, and fails if the coordinator goes down mid-protocol.
- **SAGA** — no locks, no coordinator blocking participants. Each step commits locally and immediately. Provides eventual consistency, not isolation. Compensations are business-level, not DB-level rollbacks. Scales better, tolerates partial failures better, but exposes intermediate states.

2PC is appropriate within a single DB or tightly coupled systems that support it. SAGA is the practical alternative for microservices where 2PC is not feasible.

## Section 6: Scenario / System Design Style Questions

**Q25. "Design the SAGA for an e-commerce order placement that spans Order, Payment, Inventory, and Shipping services."**
A: Using orchestration (preferred here due to 4 services + compensation complexity):

**Forward steps:**
1. Order Service: Create order (status: `PENDING`) → SAGA starts
2. Payment Service: Charge customer card → `PaymentReserved`
3. Inventory Service: Reserve items → `InventoryReserved`
4. Shipping Service: Schedule shipment → `ShipmentCreated`
5. Order Service: Mark order `CONFIRMED`

**Compensations (on failure at step N, compensate N-1 to 1):**
- Shipping fails → cancel inventory reservation → refund payment → cancel order
- Inventory fails → refund payment → cancel order
- Payment fails → cancel order (no compensation needed before payment)

**Pivot:** Payment charge (step 2). After payment succeeds, all subsequent steps are retried until success rather than compensated. A failed shipment scheduling is retried, not refunded.

**Q26. "Your choreography-based SAGA is causing 'ghost orders' — orders that are stuck in PENDING forever with no visible reason. How do you diagnose and fix it?"**
A: Ghost orders mean a SAGA started but never completed — a service in the chain never published its completion event. Diagnosis:
1. Correlate the ghost order's SAGA ID across all event topics — find which service published its event last and which one never responded.
2. Check DLQ for that service's consumer group — messages may have failed deserialization or been rejected.
3. Check the service's logs around the SAGA ID for exceptions that caused it to skip event publication.

Fix:
- Add a SAGA-level timeout monitor: a scheduled job queries for SAGA instances older than T minutes in `PENDING` state and publishes a `SAGATimeout` event that triggers compensation.
- Add structured logging per SAGA step — every service logs `saga_id`, `step`, `status` at the start and end of its local transaction.
- Build a SAGA state projection (event-driven read model) so the ops team can see exactly where every SAGA is stuck without parsing raw Kafka logs.

**Q27. "You're building a travel booking SAGA: flight + hotel + car rental. The flight is booked first, then hotel, then car. If car rental fails, what are your compensation options, and what's your pivot?"**
A: This is the classic "saga of irreversible steps" problem — flight booking fees are often non-refundable.

**Compensation options:**
- **Cancel hotel** — typically refundable if cancelled within window; send `CancelHotelBooking` command.
- **Cancel / refund car** — depends on vendor; usually fully refundable before pickup.
- **Flight** — if non-refundable, true compensation isn't possible. Options: issue a travel credit, leave flight as-is and notify user, or proactively book a refundable fare during SAGA design.

**Pivot design:** The flight booking is the natural pivot — it's the hardest to reverse. Before confirming the flight (i.e., before committing the payment for a non-refundable fare), hold a reservation. Only fully commit the flight booking after hotel succeeds (i.e., re-order steps so the non-refundable commit happens as late as possible, when confidence in overall SAGA success is highest). This is the "postpone the point of no return" principle.

**Fallback:** If car rental consistently fails, implement a try-three-vendors pattern — try Vendor A, then B, then C before triggering compensation. The SAGA definition branches on car rental failure before deciding to compensate.

## Quick Comparison Table

| Aspect                   | Choreography                                       | Orchestration                                        |
|---                       |---                                                 |---                                                   |
| Coordination             | Decentralized — events between services            | Centralized — orchestrator drives participants        |
| Coupling                 | Services coupled to event schema only              | Orchestrator coupled to all participants              |
| Workflow visibility      | Implicit — requires event log reconstruction       | Explicit — orchestrator state store                  |
| Failure handling         | Each service handles its own failures              | Orchestrator handles all failures centrally           |
| Debugging complexity     | High — must trace events across services           | Lower — single orchestrator log/state                |
| Adding a step            | New service subscribes to event                    | Modify orchestrator workflow definition               |
| Best for                 | Simple, stable, event-driven workflows             | Complex, branching, frequently changing workflows     |
| Tooling                  | Kafka, RabbitMQ, SNS/SQS                           | Temporal, AWS Step Functions, Axon, Eventuate         |
| Single point of failure  | No                                                 | Yes (mitigated with HA + persistent state)            |

---

**Tip for the interview:** SAGA questions at the senior level almost always go beyond "explain choreography vs orchestration" into failure handling — what happens when a compensation fails, how you handle idempotency, and how you avoid ghost SAGAs. Be ready to talk through a concrete example (order placement or travel booking) end-to-end, identify the pivot transaction, and explain what you'd monitor in production. Knowing a real tool (Temporal, Step Functions, Eventuate) and its trade-offs lands significantly better than describing the pattern abstractly.
