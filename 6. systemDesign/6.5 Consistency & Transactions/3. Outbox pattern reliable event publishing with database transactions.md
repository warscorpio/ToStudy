# Outbox Pattern: Reliable Event Publishing with Database Transactions — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Outbox pattern?**
A: The Outbox pattern is a technique for reliably publishing events or messages to a message broker (Kafka, RabbitMQ, SQS) in the same logical operation as a database write — without a distributed transaction. Instead of publishing directly to the broker, you write the event to an `outbox` table in the same local database transaction as your business data. A separate process then reads unpublished events from the outbox and publishes them to the broker, deleting or marking them as published once confirmed.

**Q2. What problem does the Outbox pattern solve?**
A: The dual-write problem. In event-driven systems, a common pattern is: (1) update the database, (2) publish an event to a message broker. If step 1 succeeds and step 2 fails — or the process crashes between the two — the database reflects a state change but no event was published. Downstream consumers are never notified. The Outbox pattern makes these two operations atomic by keeping both writes inside a single local database transaction, eliminating the window of inconsistency.

**Q3. Why can't you just wrap the DB write and broker publish in a try-catch and retry the publish?**
A: Because the failure can happen in ways a retry doesn't fix. The process might crash after the DB commit but before the publish — there's no retry because there's no process left running. Even if you add a retry, you risk publishing the event multiple times if the first publish actually succeeded but the acknowledgement was lost. A naive retry gives you at-most-once or unpredictable delivery; the Outbox pattern gives you at-least-once with a clear idempotency strategy.

**Q4. What is the "dual-write problem"?**
A: Dual-write is when a service must write to two separate systems atomically — typically a database and a message broker. Since these are two separate systems with no shared transaction coordinator, you can't atomically commit to both. One will succeed and the other can fail, leaving the two systems in an inconsistent state. The Outbox pattern, Change Data Capture, and the Saga pattern are all approaches to working around dual-write in different contexts.

**Q5. What guarantees does the Outbox pattern provide?**
A: At-least-once delivery — every event that was committed to the database will eventually be published to the broker. It does NOT provide exactly-once delivery; the relay process might publish a message that was already published if it crashes after publishing but before marking the event as sent. Consumers must be idempotent to handle duplicate messages correctly.

## Section 2: How It Works

**Q6. Walk through the Outbox pattern step by step.**
A:
1. A service receives a request (e.g., "create order").
2. In a single local database transaction:
   - Insert the business record (`orders` table).
   - Insert an event record into the `outbox` table (`{id, aggregate_type, aggregate_id, event_type, payload, created_at, published: false}`).
3. The transaction commits atomically — both rows land or neither does.
4. A separate **relay process** (sometimes called the "message relay" or "outbox poller") periodically queries the outbox for unpublished events.
5. The relay publishes each event to the broker.
6. Once the broker acknowledges the message, the relay marks the outbox row as published (or deletes it).
7. If the relay crashes between step 5 and 6, it republishes on restart — consumers see a duplicate and handle it via idempotency.

**Q7. What does an outbox table schema typically look like?**
A:
```sql
CREATE TABLE outbox (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type  VARCHAR(255) NOT NULL,   -- e.g., 'Order', 'Payment'
    aggregate_id    VARCHAR(255) NOT NULL,   -- e.g., the order_id
    event_type      VARCHAR(255) NOT NULL,   -- e.g., 'OrderCreated'
    payload         JSONB        NOT NULL,   -- serialised event body
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    published_at    TIMESTAMPTZ,             -- NULL = unpublished
    retry_count     INT          NOT NULL DEFAULT 0
);
```
The relay queries `WHERE published_at IS NULL ORDER BY created_at ASC` to process events in order.

**Q8. What are the two main approaches to reading the outbox and publishing events?**
A:
- **Polling**: A scheduled job (cron, worker loop) queries the outbox table at a fixed interval for unpublished events, publishes them, and marks them as done. Simple to implement, adds DB query load, and has latency equal to the polling interval.
- **Change Data Capture (CDC)**: A CDC tool (Debezium) tails the database's binary log (Postgres WAL, MySQL binlog) and streams new outbox rows to the broker as they're inserted — without polling the table. Near-real-time, no extra DB query load, but adds infrastructure complexity.

**Q9. What is Debezium, and how does it work with the Outbox pattern?**
A: Debezium is an open-source CDC platform that reads database transaction logs and streams changes as events. For the Outbox pattern, Debezium monitors the `outbox` table; when a new row is inserted (committed), Debezium reads it from the WAL and publishes it to Kafka — typically without the application needing to know. Debezium has a dedicated Outbox Event Router SMT (Single Message Transform) that extracts the payload and routes to the correct Kafka topic based on `aggregate_type`. This is the production-grade approach for Kafka-based systems.

**Q10. How do you handle ordering guarantees with the Outbox pattern?**
A: Use a monotonically increasing `created_at` timestamp or a sequence-based `id`. The relay processes events in insertion order. For Kafka, use the `aggregate_id` (e.g., `order_id`) as the message key — Kafka guarantees ordering within a partition for the same key, so all events for a given order land on the same partition in insertion order. If strict global ordering is needed across aggregates, a single-partition topic works but sacrifices throughput.

## Section 3: Polling vs CDC

**Q11. What are the trade-offs of polling the outbox table?**
A:

| Aspect | Polling |
|---|---|
| Latency | Bounded by poll interval (typically 1–10s) |
| DB load | Additional read queries on every poll cycle |
| Complexity | Low — a simple cron job or worker |
| Reliability | Risk of DB becoming a bottleneck at high event volume |
| Infrastructure | No extra components needed |

Best for lower-volume systems or teams without Kafka/CDC infrastructure already in place.

**Q12. What are the trade-offs of CDC (Debezium)?**
A:

| Aspect | CDC (Debezium) |
|---|---|
| Latency | Near real-time (milliseconds) |
| DB load | Reads WAL, not the table — minimal extra query load |
| Complexity | High — Kafka Connect cluster, connector config, SMT setup |
| Reliability | Debezium handles its own offset tracking — very reliable at scale |
| Infrastructure | Requires Kafka Connect, Zookeeper/KRaft, WAL access |

Best for high-volume, low-latency event publishing where Kafka is already part of the stack.

**Q13. What is WAL (Write-Ahead Log), and why can CDC tools read from it?**
A: The WAL is a sequential log that databases write to before applying changes to data files — it's the durability mechanism (crash recovery replays the WAL). It contains a record of every committed change. CDC tools like Debezium use logical replication slots in Postgres (or binlog in MySQL) to read this stream of changes without impacting normal query traffic. It's a read of the log, not the table, which is why CDC doesn't add query load to the DB.

**Q14. What happens if the relay (polling or CDC) falls behind due to high event volume?**
A: Unpublished events accumulate in the outbox table (or in Debezium's internal buffer). This introduces latency between the DB write and the downstream consumer seeing the event. Monitor the outbox table size and relay lag as key operational metrics. Mitigations: scale the relay (multiple workers with row-level locking to avoid duplicate publishing), increase poll frequency, optimise the outbox table with an index on `(published_at, created_at)`, or switch from polling to CDC for near-real-time throughput.

## Section 4: Idempotency & Exactly-Once Semantics

**Q15. Why must consumers of outbox-published events be idempotent?**
A: Because the Outbox pattern guarantees at-least-once delivery — the relay may publish a message and then crash before marking it as published, causing it to republish on restart. Consumers will receive the same event twice. Without idempotency, the second processing of "OrderCreated" might create a duplicate order, charge the customer twice, or send duplicate emails. Idempotency at the consumer level is the standard solution — the producer side of the Outbox pattern cannot eliminate duplicates.

**Q16. How do you implement idempotency in a consumer?**
A: Store the event's unique ID after processing it — in a dedicated `processed_events` table or using the event ID as a deduplication key in the business logic:
```sql
INSERT INTO processed_events (event_id, processed_at)
VALUES ($1, NOW())
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;
-- If no row returned, this event was already processed — skip
```
Alternatively, design operations to be naturally idempotent — `INSERT ... ON CONFLICT DO NOTHING`, `UPDATE ... WHERE status = 'pending'`, using the event's `aggregate_id` as a natural deduplication key in upserts.

**Q17. Is exactly-once delivery possible with the Outbox pattern?**
A: Not natively — the Outbox pattern provides at-least-once. Exactly-once is achievable in specific combinations: Kafka transactions + idempotent producers provide exactly-once between producer and Kafka broker. For end-to-end exactly-once (including consumer processing), you need transactional consumers that commit their Kafka offset and their DB write atomically — possible with Kafka's transactional API but complex. In practice, most systems accept at-least-once delivery with idempotent consumers rather than paying the complexity and latency cost of exactly-once.

**Q18. What is the "poison pill" problem in the Outbox relay, and how do you handle it?**
A: A poison pill is an event that consistently fails to publish — the broker rejects it (malformed payload, schema mismatch, topic doesn't exist) and the relay retries it endlessly, blocking all subsequent events behind it in the queue. Handle it with: exponential backoff on retries, a `retry_count` column with a max threshold, and moving permanently-failing events to a dead-letter table or dead-letter topic for human inspection. Never let a single bad event block the relay indefinitely.

## Section 5: Schema Design & Operational Concerns

**Q19. Should you delete published outbox rows or mark them as published?**
A: Both are valid with different trade-offs:
- **Mark as published** (`published_at = NOW()`): Preserves an audit log of all events ever published; useful for debugging and replay. Requires periodic cleanup (archive or hard-delete rows older than N days) to prevent table bloat.
- **Delete on publish**: Table stays small and queries stay fast; no cleanup needed. Loses the built-in audit trail — you'd need to rely on the broker's retention policy for replay.
For fintech/audit-sensitive systems, marking + archival is common. For high-volume, low-retention systems, deletion is simpler.

**Q20. How do you prevent multiple relay instances from publishing the same outbox row twice?**
A: Use `SELECT ... FOR UPDATE SKIP LOCKED` (Postgres) to claim a batch of unpublished rows atomically:
```sql
SELECT * FROM outbox
WHERE published_at IS NULL
ORDER BY created_at ASC
LIMIT 100
FOR UPDATE SKIP LOCKED;
```
`SKIP LOCKED` skips rows already locked by another relay instance, so multiple relay workers can process disjoint batches in parallel without overlap. This is the standard pattern for concurrent outbox processing.

**Q21. What indexes does the outbox table need?**
A: At minimum:
```sql
CREATE INDEX idx_outbox_unpublished
    ON outbox (created_at ASC)
    WHERE published_at IS NULL;
```
A partial index on `published_at IS NULL` dramatically reduces the index size and query cost since the vast majority of rows will be published (and thus excluded from the index). Without this, the relay's polling query degrades as the table grows.

**Q22. How do you handle outbox table bloat in a high-throughput system?**
A: A background archival job (daily or hourly) moves rows older than a retention window (e.g., 7 days) from the `outbox` table to an `outbox_archive` table or deletes them. Use a batched delete to avoid long-running transactions:
```sql
DELETE FROM outbox
WHERE published_at IS NOT NULL
  AND published_at < NOW() - INTERVAL '7 days'
LIMIT 1000;
```
Run this in a loop until no rows are affected. Avoid one giant `DELETE` that locks the table and spikes replication lag.

**Q23. What happens to outbox events if the database itself goes down?**
A: If the DB is down, the application can't commit the transaction — no business record is written and no outbox row is created. This is correct behaviour: the Outbox pattern ensures the two writes are always in sync. The risk is that unpublished events already in the outbox don't get relayed until the DB recovers. This is an acceptable trade-off — the events are safe in the DB and will be published once the relay resumes. The system is consistent; it's just delayed.

## Section 6: Outbox Pattern vs Alternatives

**Q24. How does the Outbox pattern compare to Saga pattern?**
A: They solve related but distinct problems. The Outbox pattern solves reliable event publishing — ensuring a committed DB change always results in a published event. The Saga pattern solves distributed transaction coordination — orchestrating a multi-step business process across multiple services with compensating transactions on failure. The Outbox pattern is typically used *within* a Saga step to ensure that each Saga step reliably publishes its event or command to trigger the next step.

**Q25. Why not use a distributed transaction (2PC) instead of the Outbox pattern?**
A: Two-Phase Commit (2PC) coordinates atomic commits across multiple systems (DB + broker) but has severe drawbacks: it requires all participants to support the XA protocol (most modern brokers don't), it blocks both systems during the prepare phase (a slow or crashed participant blocks everyone), it's a single point of failure, and it adds significant latency. In cloud/microservices environments, 2PC is essentially never used. The Outbox pattern achieves the same outcome (no lost events) without distributed coordination.

**Q26. When would you choose transactional messaging (Kafka transactions) over the Outbox pattern?**
A: Kafka's transactional API lets a producer atomically publish a batch of messages and commit offsets — useful for consumer-to-producer pipelines entirely within Kafka. It does NOT help when the atomicity requirement spans a DB write and a Kafka publish (the most common case). Use Kafka transactions when you're transforming or routing messages between Kafka topics; use the Outbox pattern when you need to atomically tie a DB state change to a Kafka event.

**Q27. How does the Outbox pattern relate to Event Sourcing?**
A: In Event Sourcing, the event log IS the database — state is derived by replaying events, not stored directly. The outbox problem largely disappears because your event store and your event broker are the same thing (or the event store itself is the source of truth that consumers read). The Outbox pattern is the pragmatic alternative when you're using a traditional relational database for state but want reliable event publishing — you don't need to adopt full Event Sourcing to get reliable events.

## Section 7: Scenario / System Design Questions

**Q28. "You need to send a 'payment confirmed' event to Kafka after updating payment status in Postgres. How do you make this reliable?"**
A: Classic Outbox pattern use case. In a single Postgres transaction: update `payments` table to `status = 'confirmed'`, insert into `outbox` (`event_type = 'PaymentConfirmed'`, `payload = {payment_id, amount, ...}`). A relay (polling worker or Debezium) reads the outbox and publishes to the `payments.confirmed` Kafka topic, keyed on `payment_id` for partition ordering. Mark the row as published after Kafka ack. Consumers (notification service, ledger service) are idempotent via `payment_id` deduplication. This ensures no payment status change is silently lost.

**Q29. "Your outbox relay has fallen 10,000 events behind due to a Kafka outage. Kafka is back — how do you recover?"**
A: The relay should resume automatically from where it left off — it reads unpublished rows ordered by `created_at`, so it will process the backlog in order. Monitor relay throughput and lag during catchup. Key concerns: ensure downstream consumers can handle the burst of delayed events without side effects (e.g., time-sensitive notifications that are now stale — add event `created_at` to the payload so consumers can decide whether to act on old events). If the backlog is enormous, consider temporarily increasing relay concurrency (`SKIP LOCKED` with multiple workers) to drain it faster, then scale back down.

**Q30. "A service team says they just publish to Kafka directly after the DB write and it works fine. How do you explain the risk?"**
A: Acknowledge it works fine until it doesn't. The failure window is small but real: a process crash, network blip, or broker unavailability between the DB commit and the Kafka publish means the DB reflects a state change (e.g., order created) but no event is published — downstream services are never notified. In a payment context this could mean: the inventory service never decrements stock, the notification service never sends a confirmation email, the ledger never records the transaction. These failures are silent — no error is thrown, no alert fires — and they accumulate as data inconsistency until a user complains. The Outbox pattern adds one table and a small relay; the trade-off is worth it for any write that has downstream consequences.

**Q31. "How would you implement the Outbox pattern in a NestJS + Postgres + Kafka stack?"**
A:
1. **Transaction wrapper**: Use TypeORM's `QueryRunner` or Prisma's `$transaction` to batch the business insert + outbox insert atomically.
2. **Outbox table**: Standard schema with `id, aggregate_type, aggregate_id, event_type, payload, created_at, published_at, retry_count`.
3. **Relay worker**: A NestJS scheduled task (`@Cron`) that runs every 2 seconds, uses `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100` to claim a batch, publishes to Kafka via `kafkajs`, and marks rows as published on ack.
4. **Dead-letter handling**: After `retry_count > 5`, move to a `outbox_dlq` table and alert.
5. **Observability**: Track `outbox_unpublished_count` as a Prometheus gauge; alert if it grows beyond a threshold (relay is stuck).
For high throughput, swap the cron poller for Debezium tailing the Postgres WAL — zero polling overhead and sub-second latency.

**Q32. "How would you test the Outbox pattern in an integration test?"**
A: Write a test that:
1. Calls the service method (e.g., `createOrder()`).
2. Asserts the business record exists in the DB.
3. Asserts the outbox row exists with the correct `event_type` and `payload` — without triggering the relay.
4. Manually invoke the relay (or trigger its logic directly) in the test.
5. Assert the message was published to the broker (use a test Kafka consumer or a mock).
6. Assert the outbox row is marked as published.
7. Run the relay again — assert the message is NOT published a second time (idempotency).
Step 7 is the most important test most teams skip — it validates that the relay doesn't double-publish on retry.

## Quick Comparison Table

| Aspect                  | Polling Relay                        | CDC (Debezium)                          |
|-------------------------|--------------------------------------|-----------------------------------------|
| Latency                 | Poll interval (1–10s typical)        | Near real-time (milliseconds)           |
| DB load                 | Extra read queries per poll cycle    | WAL read — no table query overhead      |
| Infrastructure          | Just a worker process                | Kafka Connect + connector + config      |
| Ordering guarantee      | Process in `created_at` order        | WAL order = commit order                |
| At-least-once guarantee | Yes (retry unpublished rows)         | Yes (Debezium tracks WAL offsets)       |
| Operational complexity  | Low                                  | High                                    |
| Best for                | Low-to-medium volume, simpler stacks | High volume, Kafka-native environments  |

---

**Tip for the interview:** At the 5 YOE level, interviewers expect you to know *why* direct Kafka publish after a DB write is subtly broken, not just that the Outbox pattern exists. Be ready to draw the failure scenario on a whiteboard: "process dies here, between commit and publish — what's the state?" Walk through the at-least-once guarantee, explain why consumers must be idempotent, and mention `SELECT FOR UPDATE SKIP LOCKED` if concurrent relay workers come up. In a fintech context, connect it to payment integrity — a missed `PaymentConfirmed` event that silently skips the ledger is exactly the kind of silent data corruption that causes audit failures.
