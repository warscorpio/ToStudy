# Distributed Locks and Their Pitfalls — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a distributed lock and why do you need one?**
A: A distributed lock is a mutual exclusion mechanism that works across multiple processes or machines. In a single-process system, language-level primitives (`synchronized`, `Mutex`, `Lock`) prevent concurrent access to a shared resource within that process. In a distributed system, multiple service instances run on separate machines with no shared memory — so you need an external coordination service to enforce that only one actor at a time performs a critical section (e.g., modifying a shared resource, running a scheduled job, processing a unique event).

**Q2. What are the classic use cases for distributed locks?**
A:
- **Leader election** — only one instance acts as the active leader at a time (e.g., running a cron job, processing a queue partition).
- **Preventing double-processing** — ensure only one consumer processes a specific item when multiple workers compete.
- **Inventory / seat reservation** — prevent overselling by serializing concurrent "reserve last unit" operations.
- **Rate limiting with shared state** — enforce a global rate cap across all instances.
- **Schema migrations / one-time startup tasks** — ensure only one instance runs a migration in a multi-instance deploy.

**Q3. What properties must a correct distributed lock provide?**
A: Three safety and liveness properties:
- **Mutual exclusion (safety)** — at any given time, only one client holds the lock. This is the core invariant.
- **Deadlock freedom (liveness)** — the lock is eventually acquirable even if a lock holder crashes before releasing it (achieved via TTL/lease expiry).
- **Fault tolerance** — the lock service itself should not be a single point of failure; it must survive partial node failures.

**Q4. How do distributed locks differ from database row locks?**
A: Database row locks (SELECT FOR UPDATE, advisory locks) are transactional — they're held for the duration of a DB transaction and automatically released on commit or rollback. Distributed locks are held by a process across arbitrary code (including non-DB operations) and released explicitly or via TTL. DB locks are tied to a DB connection's lifecycle; distributed locks are tied to a TTL. Also, DB locks only protect resources within that database — a distributed lock can protect any shared resource, including external APIs or filesystem operations.

## Section 2: Implementation Approaches

**Q5. How do you implement a distributed lock with Redis?**
A: The standard single-node approach uses `SET NX PX`:

```
SET lock:<resource> <unique-token> NX PX <ttl-ms>
```

- `NX` — only set if the key does not exist (atomic acquire).
- `PX <ttl-ms>` — set a TTL so the lock auto-expires if the holder crashes.
- `<unique-token>` — a UUID generated by the acquirer. Critical for safe release (see Q10).

Release using a Lua script (atomic check-and-delete):
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

The Lua script is atomic — it prevents a race where you check the token, the TTL expires, another client acquires the lock, and then you delete the new owner's lock.

**Q6. What is the Redlock algorithm?**
A: An algorithm proposed by Redis's author for distributed locks across multiple independent Redis nodes (not replicated — independent). To acquire a lock:
1. Record the current time.
2. Attempt to acquire the lock on N Redis nodes (N = 5 is typical) sequentially, each with a small per-node timeout.
3. If a majority (⌊N/2⌋ + 1) of nodes succeed, and the total elapsed time is less than the lock TTL, the lock is considered acquired.
4. The effective lock TTL = configured TTL − elapsed acquisition time.
5. Release by deleting the key on all nodes (even ones that failed acquisition).

The majority quorum ensures that no two clients can both believe they hold the lock, as long as fewer than N/2 nodes fail simultaneously.

**Q7. How do you implement a distributed lock with a relational database?**
A: Two common approaches:

**Advisory locks (PostgreSQL):**
```sql
SELECT pg_try_advisory_lock(hashtext('my-lock-name'));
-- Returns true if acquired, false if already held
-- Released on session end or explicit pg_advisory_unlock()
```

**Explicit lock table:**
```sql
CREATE TABLE distributed_locks (
  lock_name TEXT PRIMARY KEY,
  holder_id TEXT NOT NULL,
  acquired_at TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL
);

-- Acquire:
INSERT INTO distributed_locks (lock_name, holder_id, acquired_at, expires_at)
VALUES ('my-lock', $holder_id, now(), now() + interval '30 seconds')
ON CONFLICT (lock_name) DO NOTHING;

-- Release:
DELETE FROM distributed_locks WHERE lock_name = 'my-lock' AND holder_id = $holder_id;
```

A background job or the acquirer on next attempt cleans up expired rows. DB locks trade raw speed for the DB's strong consistency guarantees.

**Q8. How does ZooKeeper implement distributed locking?**
A: ZooKeeper's ephemeral sequential znodes provide a natural locking primitive:
1. Each client creates an ephemeral sequential znode under `/locks/my-lock/lock-` (e.g., creates `lock-0000000001`).
2. The client lists all children and checks if its znode has the lowest sequence number. If yes, it holds the lock.
3. If not, it watches the znode with the next-lowest sequence number (not all children — avoids herd effect) and waits for a notification.
4. When the watched znode is deleted (its holder released or crashed — ephemeral nodes auto-delete on session loss), the next client checks again.

The ephemeral node mechanism means ZooKeeper automatically releases locks when a holder's session times out — no manual TTL management needed.

## Section 3: Pitfalls

**Q9. What is the "lock expiry during execution" pitfall?**
A: The most dangerous pitfall. A process acquires a lock with TTL T, then takes longer than T to complete its critical section (due to GC pause, slow DB query, network stall, or just underestimating execution time). The lock expires and another process acquires it. Now two processes believe they hold the lock simultaneously — mutual exclusion is violated.

This is not a theoretical edge case. JVM GC pauses can last seconds. Network timeouts are often 30+ seconds. Any TTL you set is a bet that your critical section completes in time — and distributed systems constantly find ways to make that bet wrong.

**Q10. Why must you use a unique token to release a lock, and what goes wrong without it?**
A: Without a unique token, any client can delete the lock key — including one that no longer holds it. The failure scenario:
1. Client A acquires lock, starts work.
2. Client A's TTL expires (GC pause). Lock auto-releases. Client B acquires the lock.
3. Client A resumes, finishes work, calls `DEL lock:resource`.
4. Client A just deleted Client B's lock. Client C now acquires the lock. Both B and C are now in the critical section.

With a unique token (UUID), the release script checks that the token stored in Redis matches the one the caller holds. If it doesn't match (because the TTL expired and B acquired it), the DEL is skipped — A can't accidentally release B's lock.

**Q11. What is the "clock drift" pitfall in Redlock?**
A: Redlock's safety relies on TTL-based expiry being consistent across nodes. If the clocks on different Redis nodes drift significantly, a lock's effective TTL varies across nodes — a node with a fast clock expires the lock before the holder has finished. Martin Kleppmann's critique of Redlock specifically highlights that NTP clock jumps (forward or backward) can cause a Redis node to expire a lock early or late, breaking the quorum-based safety guarantee.

**Q12. What is the "herd effect" (thundering herd) in distributed locking?**
A: When a lock is released and all waiting clients are notified simultaneously, they all race to re-acquire. With N waiters, you get N−1 unnecessary wake-ups and N−1 failed acquisition attempts. Under high contention, this creates CPU and network spikes every time the lock turns over. ZooKeeper avoids it by having each waiter watch only the *previous* znode in sequence (not the lock znode itself) — only one waiter is notified per release. Redis-based implementations typically address it with a randomized retry jitter: instead of polling immediately on failure, wait `base_delay + random(0, jitter_ms)` before retrying.

**Q13. What is a "fencing token" and why does it matter?**
A: A fencing token is a monotonically increasing number issued with each lock grant. The lock holder passes this token to any resource it writes to. The resource rejects any request with a token lower than the highest it has seen. This prevents the following scenario:
1. Client A acquires lock, gets token 33.
2. A's lock expires (GC pause). Client B acquires lock, gets token 34.
3. A resumes and sends a write with token 33.
4. Resource rejects A's write (33 < 34). B's writes (token 34) succeed.

Without fencing tokens, A and B's writes can interleave arbitrarily after a lock expiry, corrupting shared state even though both believe they're operating "under the lock." Redis-based locks don't provide fencing tokens natively — you need to implement them yourself (e.g., increment a Redis counter on each lock grant).

**Q14. What is the "split-brain" pitfall in Redis replication-based locks?**
A: If you use a single Redis primary with replicas (not Redlock), and the primary fails, a replica is promoted. But Redis replication is asynchronous — the lock key may not have been replicated to the new primary before failover. Client A holds the lock on the old primary. The old primary crashes. The new primary (former replica) doesn't have the key. Client B acquires the lock on the new primary. Both A and B now believe they hold the lock. This is exactly why Redlock uses independent nodes with no replication between them.

**Q15. What happens if the lock service itself goes down?**
A: Depends on your implementation:
- **Redis single node** — all lock acquisitions fail. Services that require the lock to proceed halt (or bypass locking, which is dangerous).
- **Redis Sentinel / Cluster** — failover occurs; there's a brief window during which split-brain (Q14) is possible.
- **Redlock (5 independent nodes)** — can tolerate ⌊N/2⌋ = 2 node failures. With 3 nodes down, no quorum is achievable and all acquisitions fail.
- **ZooKeeper** — with its Raft-based quorum, tolerates minority node failures gracefully and never returns incorrect results (it returns errors instead).

The general principle: in distributed systems, choose CP (consistency + partition tolerance) for lock services. A lock service that returns incorrect results under partition is worse than one that becomes temporarily unavailable.

## Section 4: Advanced Concepts

**Q16. What is lock renewal (lease extension) and when do you need it?**
A: If a critical section may legitimately take longer than the initial TTL, the lock holder can periodically renew the lease before it expires — essentially extending the TTL. The holder runs a background thread that calls `EXPIRE lock:<resource> <ttl>` (or a SET with the same token and new TTL) every TTL/3 seconds. Key requirements:
- The renewal must verify the token is still the holder's before extending (same Lua script pattern as release).
- If the renewal fails (Redis down, key already gone), the holder must abort its critical section immediately — it can no longer safely assume it holds the lock.
- Renewal adds complexity; it's preferable to design critical sections short enough to fit within a fixed TTL.

**Q17. What is the difference between optimistic locking and distributed locking?**
A: Fundamentally different strategies for concurrency control:
- **Distributed lock (pessimistic)** — acquire exclusive access before doing work. Others are blocked (or rejected) until the lock is released. Guarantees no conflict during execution. High contention cost if the critical section is long.
- **Optimistic locking** — do work without acquiring a lock, then verify at commit time that no one else modified the resource (via a version number or ETag). If a conflict is detected, retry. Low overhead when conflicts are rare; high retry cost when conflicts are frequent.

Use distributed locks when the critical section has side effects that are hard to roll back (payment charges, external API calls). Use optimistic locking when the operation is a DB write and conflicts are infrequent.

**Q18. What is "lock-free" design and when can you avoid distributed locks entirely?**
A: Many use cases that seem to require locks can be redesigned to avoid them:
- **Single-writer architecture** — route all writes for a resource to a single service instance (consistent hashing, Kafka partition ownership). No lock needed because only one writer exists by design.
- **Atomic DB operations** — replace lock + read + modify + write with a single atomic DB operation (`UPDATE inventory SET count = count - 1 WHERE id = $1 AND count > 0`). The DB's row lock handles concurrency; no distributed lock needed.
- **CAS (Compare-and-Swap)** — use conditional writes (`UPDATE ... WHERE version = $expected_version`) combined with retry on conflict. Eliminates the need for explicit locking.
- **Idempotent queue processing** — instead of locking to prevent double-processing, make the processing idempotent (see idempotency key pattern). Any processor can process any message safely.

Distributed locks are a last resort — they add operational complexity, latency, and failure modes. Exhaust lock-free alternatives first.

**Q19. How does Kubernetes leader election work, and what distributed lock primitive does it use?**
A: Kubernetes leader election uses a `Lease` object (or a `ConfigMap`/`Endpoints` resource in older versions) as a distributed lock. Each candidate periodically tries to update the Lease object with its identity and a `renewTime`. The update uses a `resourceVersion` optimistic lock — only one candidate's update wins per version. The winner is the leader; it keeps renewing the Lease. If the leader fails to renew within the `leaseDuration`, others can acquire it. Used by kube-controller-manager, kube-scheduler, and custom operators to ensure a single active instance among replicas.

## Section 5: Trade-offs & Decision-Making

**Q20. Redis vs ZooKeeper vs DB for distributed locks — how do you choose?**
A:

| Factor | Redis (SET NX) | ZooKeeper / etcd | Database |
|---|---|---|---|
| Performance | Very high (sub-ms) | Moderate (ms-range) | Moderate to low |
| Consistency guarantee | Weak (async replication) | Strong (Raft/ZAB) | Strong (ACID) |
| Lock expiry model | TTL-based (client-managed) | Session-based (auto-release) | TTL-based or session-based |
| Operational overhead | Low (Redis already in stack) | High (separate cluster) | Low (DB already in stack) |
| Fencing token support | Manual | Built-in (zxid) | Manual |
| Best for | High-throughput, latency-sensitive, tolerable brief inconsistency | Correctness-critical, low-write-rate (config, leader election) | Simple use cases, teams without Redis |

**Q21. How do you decide what TTL to set on a distributed lock?**
A: TTL must be longer than the worst-case execution time of your critical section, but short enough that a crashed holder doesn't block others for too long. In practice:
- Profile the P99 execution time of the critical section under load.
- Add a generous safety margin (2–3×) to account for GC pauses, slow DB queries, and network jitter.
- If the worst-case is unbounded or highly variable, use lock renewal rather than a fixed TTL.
- Set an alert if critical-section execution time approaches 50% of the TTL — that's a warning sign.
- Never set TTL to "forever" — a crashed holder would block indefinitely.

**Q22. When should you NOT use a distributed lock?**
A:
- When the operation can be made naturally idempotent — locks add latency and failure modes for no benefit.
- When contention is high and the critical section is long — lock contention becomes a throughput bottleneck. Consider partitioning the resource so each partition has its own lock (reducing contention per lock).
- When you're protecting read-only operations — reads don't need mutual exclusion unless you're implementing a read-write lock pattern.
- When a DB transaction's native row lock is sufficient — reach for the DB's built-in concurrency control before adding an external lock service.
- When eventual consistency is acceptable — distributed locks enforce strict serialization; if the use case tolerates occasional conflicts (rare inventory oversell, for example), use optimistic locking or accept and reconcile conflicts.

## Section 6: Scenario / System Design Style Questions

**Q23. "You're building a flash sale: 1,000 users simultaneously try to buy the last item in stock. How do you prevent overselling without a distributed lock?"**
A: Avoid a distributed lock here — under 1,000 concurrent acquirers, lock contention would serialize all requests through one chokepoint, destroying throughput. Better approaches:
- **Atomic DB decrement with guard:** `UPDATE inventory SET quantity = quantity - 1 WHERE item_id = $1 AND quantity > 0`. Returns rows-affected = 1 on success, 0 on failure (already zero). DB row lock handles concurrency. No external lock service needed.
- **Redis DECR with floor check:** `DECR inventory:<item_id>` is atomic. If result < 0, call `INCR` to compensate and reject the request. Fast and contention-free — Redis serializes DECRs internally per key.
- **Pre-allocation tokens:** Before the sale, insert N tickets into a queue. Each buyer dequeues one atomically. If the queue is empty, sale is over. Naturally handles concurrency without locks.

**Q24. "A distributed cron job runs on 10 instances. You only want one instance to execute the job at a time. How do you implement this with a distributed lock, and what pitfalls do you guard against?"**
A: Standard leader-election pattern with Redis:

```python
def try_acquire_job_lock(redis, job_name, instance_id, ttl_ms):
    return redis.set(f"cron:{job_name}", instance_id, nx=True, px=ttl_ms)

def release_job_lock(redis, job_name, instance_id):
    lua = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else return 0 end
    """
    redis.eval(lua, 1, f"cron:{job_name}", instance_id)
```

**Pitfalls guarded against:**
- Unique token (`instance_id` = UUID per instance) prevents one instance from releasing another's lock.
- TTL set to `job_timeout × 2` prevents permanent blockage if the winner crashes.
- Lock renewal if the job is long-running — background thread extends TTL every TTL/3 seconds.
- On renewal failure, the job aborts — it no longer safely holds the lock.
- Alert on "job didn't run in expected window" — detects silent lock starvation.

**Q25. "Martin Kleppmann argued that Redlock is unsafe. What's his argument, and do you agree?"**
A: Kleppmann's argument centers on two points:
1. **Clock jumps break TTL assumptions.** Redlock assumes that TTLs expire at predictable times across nodes. If a Redis node's system clock is stepped forward by NTP (or the OS scheduler pauses the Redis process), a lock can expire on that node before the holder expects — breaking the quorum guarantee.
2. **No fencing tokens.** Even if Redlock correctly grants the lock to one client, it provides no mechanism to prevent a stale lock holder (whose lock expired mid-execution) from writing to the resource. Without fencing tokens, two clients can both write, believing they're protected.

His conclusion: use ZooKeeper (which provides monotonic zxid as a fencing token) for correctness-critical locks. Use Redis locks only where "best effort" mutual exclusion is acceptable and brief duplicates are tolerable.

Counter-argument (Redis's author Antirez): clock jumps are an operational problem, not an algorithmic one — properly configured NTP with bounded drift makes Redlock safe in practice. The debate is unresolved and context-dependent. At interview: acknowledge both sides, state your preference (ZooKeeper/etcd for correctness-critical, Redis for performance-critical with acceptable risk), and mention fencing tokens as the mitigation.

**Q26. "Your service holds a distributed lock to process an order, but a GC pause causes the lock to expire mid-execution. The next instance picks up the lock and also processes the order. How do you prevent double-processing?"**
A: Defense in depth — don't rely on the lock alone:
- **Fencing token on the DB write:** The lock grants a token (monotonic counter); the order update includes it. DB checks `WHERE processing_token < $new_token` before applying the write — the stale holder's write with the lower token is rejected.
- **Idempotency key on the order:** The order has a unique `order_id`. Processing logic uses `INSERT ... ON CONFLICT DO NOTHING` or checks `IF status = 'pending' THEN process`. A second processing attempt sees status = 'processing' or 'completed' and exits early.
- **Optimistic version lock on the order row:** `UPDATE orders SET status='processing', version=version+1 WHERE id=$1 AND version=$expected`. The stale holder's update fails (wrong version); the new holder's succeeds.

Layering idempotency with the distributed lock means that even when the lock fails (and it will, eventually), the underlying operation is still safe.

## Quick Reference: Distributed Lock Pitfalls Summary

| Pitfall | Root Cause | Mitigation |
|---|---|---|
| Lock expires mid-execution | TTL too short vs. execution time | Set TTL generously; use lock renewal for long tasks |
| Releasing another holder's lock | No unique token on release | Store UUID on acquire; use check-and-delete Lua script |
| Split-brain on Redis failover | Async replication loses lock key | Use Redlock (independent nodes) or ZooKeeper/etcd |
| Thundering herd on release | All waiters notified simultaneously | Watch previous-sequence znode (ZK); randomized retry jitter (Redis) |
| No fencing after lock expiry | Lock provides no write-ordering guarantee | Implement fencing tokens; layer idempotency on the resource |
| Clock drift (Redlock) | NTP jumps affect TTL accuracy across nodes | Use ZooKeeper for correctness-critical locks; bound NTP drift |
| Lock service becomes SPOF | Single Redis node failure blocks all lock holders | HA Redis with Sentinel; Redlock; ZooKeeper quorum |
| Deadlock (lock never released) | Holder crashes without release and no TTL set | Always set a TTL; ephemeral nodes in ZooKeeper auto-release |

---

**Tip for the interview:** Distributed lock questions are a reliability and correctness trap — interviewers want to see that you know the failure modes, not just the happy path. The two things that separate senior answers: (1) knowing that a distributed lock alone is not sufficient and must be paired with idempotency or fencing tokens at the resource level, and (2) knowing when to *avoid* the lock entirely (atomic DB ops, single-writer design, idempotent processing). If you mention the Kleppmann vs. Antirez debate on Redlock, be ready to take a position and defend it.
