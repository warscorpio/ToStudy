# Metrics: Counters, Gauges, Histograms, Percentiles — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a metric in the context of observability?**
A: A metric is a numeric measurement of a system property captured over time — CPU usage, request count, error rate, latency. Unlike logs (which are event records) or traces (which follow a single request's path), metrics are aggregated numerical data suited to alerting, dashboards, and capacity planning. They're cheap to store and query at scale, which is why they form the backbone of most monitoring systems.

**Q2. What are the four main metric types you'll encounter in practice?**
A: Counter, Gauge, Histogram, and Summary. Different systems (Prometheus, StatsD, Datadog) name and implement them slightly differently, but these four primitives cover nearly every use case — counting events, measuring current state, capturing distributions, and computing percentiles.

**Q3. What is a counter?**
A: A counter is a monotonically increasing integer that only goes up (or resets to zero on process restart). It's used to count events — HTTP requests, errors, bytes sent. You never read the raw counter value in isolation; you compute the rate of change over time (e.g., `rate(http_requests_total[5m])` in PromQL gives you requests per second over the last 5 minutes).

**Q4. What is a gauge?**
A: A gauge is a metric that can go up or down freely — it represents a current snapshot of a value. Examples: current memory usage, active connections, queue depth, temperature. Unlike a counter, you read the current value directly. It requires no rate computation, but you do need to be careful about what "current" means — gauges can be misleading if the sampling interval misses spikes.

**Q5. What is a histogram?**
A: A histogram samples observations (typically latencies or response sizes) and places them into pre-configured buckets. For example, a request latency histogram might have buckets at ≤10ms, ≤50ms, ≤100ms, ≤500ms, ≤1s, +Inf. It also tracks the total count of observations and their sum. From a histogram you can compute approximate percentiles and averages — across multiple instances and over time windows, which makes it more powerful than a simple gauge.

**Q6. What is a summary, and how is it different from a histogram?**
A: A summary also samples observations and computes quantiles (e.g., p50, p95, p99), but it calculates them on the client side within a sliding time window. The key difference: a histogram sends raw bucket data to the metrics server and lets you aggregate across instances; a summary pre-computes quantiles locally, making it impossible to accurately aggregate across multiple instances. In practice, histograms are preferred for distributed systems.

## Section 2: Counters in Depth

**Q7. Why should you never alert directly on a counter value?**
A: Because counters only go up (until a reset), a raw counter value has no contextual meaning — "1,000,000 requests" tells you nothing about whether the system is healthy right now. You alert on the *rate* of change (e.g., "error rate > 5%") or the *delta* over a window. Also, counter resets (on deployment or crash) can cause spurious dips — good metrics systems handle this with `increase()` or `irate()` functions that account for resets.

**Q8. What's the difference between `rate()` and `irate()` in Prometheus?**
A: `rate()` computes the per-second average rate over a range (e.g., last 5 minutes), smoothing out spikes — good for slow-moving dashboards and alerting rules. `irate()` computes the instantaneous rate using only the last two data points — more responsive to sudden spikes but also noisier. Use `rate()` for alerts and trend dashboards; `irate()` when you specifically want to see rapid transient spikes.

**Q9. Give examples of good counter metrics to instrument in a web service.**
A: 
- `http_requests_total` (labeled by method, path, status_code)
- `http_errors_total` (labeled by error type)
- `db_queries_total` (labeled by query type and outcome)
- `cache_hits_total` / `cache_misses_total`
- `queue_messages_published_total` / `queue_messages_consumed_total`
- `retries_total`

The key insight: counters tell you *how much* of something has happened; labels (dimensions) slice the data so you can isolate failures by service, endpoint, or status.

## Section 3: Gauges in Depth

**Q10. What are common mistakes when using gauges?**
A: 
- **Sampling blind spots** — a gauge is a point-in-time sample. A queue that spikes to 10,000 and drains in 5 seconds may show 0 if your scrape interval is 15 seconds. Use counters + rate for event flow; reserve gauges for state that holds across scrapes.
- **Aggregating gauges incorrectly** — averaging gauge values across instances is usually wrong (e.g., averaging memory usage across 10 pods gives a misleading middle value; you often want the max or sum).
- **Alerting on averages of gauges** — the average can look healthy while individual nodes are saturated.

**Q11. When should you use `sum` vs `avg` vs `max` when aggregating a gauge across instances?**
A: It depends on what you care about:
- `sum` — for additive quantities: total active connections across all pods, total memory used by the fleet.
- `max` — for saturation signals: if *any* instance is at 90% CPU, you want to know, even if the average is 40%. Max reveals the hot spot.
- `avg` — rarely the right choice for alerting; useful for "typical" baselines but hides outliers.

## Section 4: Histograms in Depth

**Q12. Walk me through how a Prometheus histogram works internally.**
A: When you observe a value (e.g., a 75ms request), the histogram increments the counter for every bucket whose upper bound is ≥ 75ms. So if buckets are [10, 50, 100, 500, +Inf], the 100ms, 500ms, and +Inf buckets all get incremented. The histogram also maintains `_sum` (total of all observed values) and `_count` (total observations). This cumulative bucket structure allows Prometheus to compute `histogram_quantile()` across multiple time series — which is the key advantage over client-side summaries.

**Q13. How does `histogram_quantile()` work, and why is it approximate?**
A: `histogram_quantile(0.95, ...)` interpolates within the bucket that contains the target percentile, assuming values are uniformly distributed within that bucket. If your p95 latency falls in the 100ms–500ms bucket, Prometheus linearly interpolates within that range. This is approximate — the accuracy depends on bucket granularity. Too few/wide buckets → imprecise quantiles. Too many buckets → more cardinality overhead. Bucket selection is a design choice that trades precision against cost.

**Q14. How do you choose histogram bucket boundaries?**
A: Know your expected latency range first, then place buckets densely where you care about precision. A common pattern for HTTP latencies: `.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10` (in seconds). Practical rules:
- Include a bucket near your SLO threshold (e.g., if your SLO is p99 < 500ms, have a 500ms bucket).
- Don't spread buckets uniformly on a linear scale — latency distributions are usually right-skewed, so use a logarithmic spread.
- Avoid too many buckets per metric: each bucket is a separate time series; with high-cardinality labels this multiplies fast.

**Q15. Why are histograms better than averages for measuring latency?**
A: Averages hide the distribution. A service with 90% of requests completing in 10ms and 10% timing out at 10 seconds shows an "average" of ~1 second — which looks bad, but doesn't tell you 90% of users are actually fine. Conversely, a service where 50% of requests take 200ms and 50% take 800ms has the same average as one where all requests take 500ms — but very different user experience. Histograms reveal the shape of the distribution, including tail behavior, which is where user pain actually lives.

## Section 5: Percentiles in Depth

**Q16. What does p50 (median), p95, and p99 mean, and why do we care about each?**
A: 
- **p50 (median)** — 50% of requests completed in this time or less. Represents the "typical" user experience.
- **p95** — 95% of requests are at or below this latency. Catches slowness affecting 1 in 20 requests — noticeable to active users.
- **p99** — 99% of requests are at or below this latency. 1 in 100 requests is affected — matters for high-volume services or SLA-sensitive workflows.

At 1,000 RPS, a p99 issue affects ~10 users/second. At 100,000 RPS, it affects ~1,000 users/second — the same percentage but very different business impact.

**Q17. Why not just monitor p99 and ignore p50 and p95?**
A: Because they tell you different things. p50 reflects the majority user experience; a degraded p50 means *most* users are suffering. p95 is a leading indicator — it often spikes before p99 does, giving you earlier warning. Monitoring only p99 can mask a broad slowdown that hasn't yet reached the tail: you might have a p50 of 800ms and p99 of 950ms, which looks "fine" at p99 but means half your users are waiting nearly a second. You need the full picture.

**Q18. What is p100 (max), and why is it usually not useful as an alert target?**
A: p100 is the single slowest request observed in the window. It's extremely noisy — one garbage collection pause, one slow DNS resolution, or one cold-start can skew it wildly. It's useful for debugging after an incident ("what was the worst-case request?") but not for alerting, because it fires constantly on harmless one-off outliers, producing alert fatigue.

**Q19. Can you aggregate percentiles from multiple instances? Why is this tricky?**
A: You cannot simply average percentiles. If instance A has a p99 of 200ms and instance B has a p99 of 800ms, the combined p99 is *not* 500ms — it depends on the actual distribution of all requests across both instances. This is why histograms (which send raw bucket counts that can be summed across instances) are preferred over pre-computed summaries. With histograms, you sum the bucket counts first, then compute the quantile on the aggregate — giving a mathematically correct result.

**Q20. What are SLIs, SLOs, and how do percentile metrics connect to them?**
A: 
- **SLI (Service Level Indicator)** — the actual measured metric, e.g., "p99 latency of checkout endpoint."
- **SLO (Service Level Objective)** — the target, e.g., "p99 latency < 500ms, measured over a 30-day rolling window."
- **SLA (Service Level Agreement)** — the contractual commitment, often slightly looser than the SLO.

Percentile-based SLOs are the industry standard because they reflect real user experience. Alerting on "p99 latency > 500ms for 5 consecutive minutes" is a meaningful, user-centric signal — far better than "CPU > 80%" which doesn't map directly to user pain.

## Section 6: Cardinality & Labeling

**Q21. What is cardinality in the context of metrics, and why does it matter?**
A: Cardinality is the number of unique time series a metric generates — determined by the combination of its label values. A metric `http_requests_total` with labels `{method, status_code}` and 5 methods × 10 status codes = 50 time series. Add a high-cardinality label like `user_id` (millions of users) and you suddenly have millions of time series — this blows up storage, query performance, and ingestion cost in systems like Prometheus or Datadog.

**Q22. What are good vs bad labels to add to a metric?**
A: 
- **Good labels (low cardinality, high analytical value):** `method` (GET/POST/DELETE), `status_code` (200/404/500), `region` (us-east-1/eu-west-1), `service`, `endpoint` (if bounded).
- **Bad labels (high cardinality):** `user_id`, `session_id`, `request_id`, `email`, `IP address`, free-form error messages. These explode cardinality and should be in logs/traces, not metrics.

The rule: if a label value is unbounded or user-generated, it doesn't belong in a metric.

**Q23. What happens if you accidentally add a high-cardinality label to a frequently observed histogram?**
A: You get a cardinality explosion. A histogram with 10 buckets and a `user_id` label with 1 million unique values generates 10 million time series — just for that one metric. Most Prometheus setups will OOM or become too slow to query. This is one of the most common production incidents with Prometheus: a developer adds `user_id` to a histogram "for debugging," deploys, and the metrics server falls over within minutes.

## Section 7: Alerting & Practical Patterns

**Q24. What's the difference between a threshold alert and a burn rate alert?**
A: 
- **Threshold alert** — fires when a metric crosses a fixed value (e.g., error rate > 5% for 5 minutes). Simple but can be noisy and doesn't account for SLO budget consumption.
- **Burn rate alert** — based on how fast you're consuming your SLO error budget. If your SLO allows 0.1% errors over 30 days, a 1% error rate means you're burning through the budget 10× faster than sustainable. Burn rate alerts fire early on severe outages and stay quiet on minor blips — better signal-to-noise for on-call teams.

**Q25. Why do p99 latency alerts sometimes fire during deployments even when there's no real problem?**
A: Several reasons:
- **Reduced pool size** — during a rolling deploy, fewer instances handle traffic, so the distribution shifts and tail latency rises temporarily.
- **Cold start / JIT warmup** — new instances have cold caches and JIT-unoptimized code paths, causing transient slow requests.
- **Short window + noisy tail** — p99 computed over a 1-minute window is very sensitive to a handful of slow requests. Extending the window (e.g., 5 or 10 minutes) reduces false positives.

Good practice: account for deploy windows in alert policies, or suppress alerts for a warmup period after deployment.

**Q26. "Your p99 latency is 800ms but your p50 is 20ms. What does this tell you, and where would you look first?"**
A: A huge gap between median and tail latency is a classic sign of a bimodal distribution — most requests are fast, but a subset is very slow. Common culprits:
- A slow code path or query triggered only by specific inputs (e.g., a user with 10,000 items in their cart).
- GC pauses (Java/Go) or event loop stalls causing occasional request queuing.
- A downstream dependency with high tail latency (e.g., a cache miss path hitting the DB).
- Thread pool or connection pool exhaustion causing some requests to queue.

I'd start by breaking the latency histogram down by endpoint and checking for correlations — is it one endpoint? A specific downstream call? Then look at traces (if available) for the slow requests to find where time is spent.

**Q27. How do you use the `_sum` and `_count` from a histogram to compute average latency, and when is that useful?**
A: Average latency = `rate(http_request_duration_sum[5m]) / rate(http_request_duration_count[5m])`. It's useful as a cheap, low-overhead signal for dashboards when you don't need the full distribution — a rising average over time is a useful macro-trend indicator. But never use average latency as an SLO metric or alert basis; it hides tail behavior. Use it for trending and sanity checks, not for user-experience SLOs.

## Section 8: Scenario / System Design Style Questions

**Q28. "You're instrumenting a new payment service from scratch. What metrics would you add, and what types would you use?"**
A: I'd follow the RED method (Rate, Errors, Duration) plus a few domain-specific gauges:
- `payments_requests_total` (counter, labeled by method and status) → rate gives you throughput.
- `payments_errors_total` (counter, labeled by error_type) → rate gives error rate for SLO.
- `payments_request_duration_seconds` (histogram, labeled by method) → percentiles for latency SLO.
- `payments_in_flight` (gauge) → current concurrent requests; useful for detecting overload.
- `payments_queue_depth` (gauge, per payment provider) → signals upstream backpressure.
- `payments_amount_total` (counter, in cents to avoid float issues) → business metric for revenue tracking.

**Q29. "Your on-call alert fires: p99 DB query latency is 2 seconds. Walk me through your investigation using metrics."**
A: 
1. Check the query-level histogram: is it all queries or a specific query type (labeled by `query_type` or `table`)? Narrow the blast radius.
2. Check `db_connections_in_use` gauge vs pool size — if the pool is saturated, queries are queuing, not slow.
3. Check `db_query_errors_total` rate — are there lock timeouts or deadlocks?
4. Check infra-level gauges: DB CPU, disk I/O, and memory. A cache eviction spike (buffer pool pressure) often causes sudden latency spikes.
5. Cross-reference with deployment counters or feature flag changes around the time the spike started.
6. If available, pull a slow query log or trace — metrics narrow *what* is slow, traces tell you *why*.

**Q30. "A teammate suggests adding `user_id` as a label to the request duration histogram for easier per-user debugging. How do you respond?"**
A: That's a well-intentioned but dangerous idea. Adding `user_id` to a histogram with even 10 buckets and 1 million users creates 10 million time series — which will likely OOM the Prometheus server and make queries unusably slow. For per-user debugging, the right tool is distributed tracing (traces carry user context without blowing up cardinality) or structured logs (filter by user_id at query time). If you need user-level latency metrics at all, you'd aggregate into cohorts (e.g., by subscription tier or region), not individual user IDs.

## Key Formulas to Know

| What You Want | How to Get It |
|---            |---            |
| Request rate  | `rate(http_requests_total[5m])` |
| Error rate %  | `rate(http_errors_total[5m]) / rate(http_requests_total[5m]) * 100` |
| p99 latency   | `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` |
| Avg latency   | `rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])` |
| Apdex score   | `(satisfied + 0.5 * tolerating) / total` (counts from histogram buckets) |

**Tip for the interview:** At 5 YOE level, interviewers expect you to go beyond "counter counts, gauge measures current state." They want to hear *why* you'd use a histogram over a gauge for latency, *why* percentiles beat averages for SLOs, and *how* cardinality decisions have real operational consequences. Have a story ready about a time a metric led you to or away from a wrong conclusion — that's the kind of judgment that separates mid-level from senior engineers.
