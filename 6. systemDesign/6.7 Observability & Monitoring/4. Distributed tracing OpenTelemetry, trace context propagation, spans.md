# Distributed Tracing: OpenTelemetry, Trace Context Propagation, Spans — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is distributed tracing, and what problem does it solve?**
A: Distributed tracing records the end-to-end journey of a single request as it flows through multiple services, capturing timing, order, and causal relationships between operations. The problem it solves: in a microservices system, a user-visible latency spike or failure may involve 5–10 services. Logs tell you what happened per service; tracing tells you *where time was spent across the entire call graph* — which service, which operation, which DB query was the bottleneck.

**Q2. What is a trace?**
A: A trace represents the complete lifecycle of one request through the system — from the moment it enters the outermost service to the moment the response is returned (or the async operation completes). A trace is composed of one or more spans arranged in a tree. It's identified by a globally unique `traceId`.

**Q3. What is a span?**
A: A span represents a single unit of work within a trace — e.g., "handle HTTP request", "query users table", "call payment-service". Every span records:
- `traceId` — which trace it belongs to.
- `spanId` — its own unique ID.
- `parentSpanId` — the span that created it (absent only on the root span).
- `name` — what operation this span represents.
- `startTime` and `endTime` (or `duration`).
- `status` — OK, ERROR, UNSET.
- `attributes` (key-value metadata) and `events` (timestamped log-like records within the span).

**Q4. What is the root span?**
A: The first span created when a request enters the system — it has no `parentSpanId`. Everything downstream is a child or descendant of the root span. The total duration of the root span represents the end-to-end latency of the request from the system's perspective.

**Q5. How is distributed tracing different from logging and metrics?**
A: The three are complementary observability pillars:
- **Metrics** — aggregated numerical data over time (request rate, p99 latency, error rate). Tells you *something is wrong*.
- **Logs** — discrete events with context. Tells you *what happened* at a specific moment.
- **Traces** — causal, timing-aware request flow across services. Tells you *where in the call graph time was spent* and *which service caused the problem*.

Traces are uniquely suited to latency attribution and understanding cross-service dependencies; logs and metrics can't reconstruct a call graph.

## Section 2: OpenTelemetry

**Q6. What is OpenTelemetry (OTel)?**
A: OpenTelemetry is a CNCF project that provides a vendor-neutral, standardized API, SDK, and protocol (OTLP — OpenTelemetry Protocol) for generating and exporting telemetry data (traces, metrics, and logs). It replaces the need to instrument against a specific vendor (Datadog, Jaeger, Zipkin) — you instrument once against OTel, then export to any backend by swapping the exporter.

**Q7. What are the core OTel components you interact with in code?**
A:
- **TracerProvider** — the factory for creating `Tracer` instances. Configured once at startup with exporters, samplers, and resource attributes.
- **Tracer** — obtained from the provider; used to create spans (`tracer.startSpan(...)`).
- **Span** — the unit of work you record. You start it, add attributes/events, and end it.
- **Context** — the in-process store for the currently active span. OTel's context propagation ensures the active span is accessible anywhere in the call stack without passing it explicitly.
- **Propagator** — extracts/injects trace context across process boundaries (HTTP headers, message headers).
- **Exporter** — ships completed spans to a backend (Jaeger, Zipkin, Datadog, OTLP Collector).

**Q8. What is the OTel Collector, and why use it instead of exporting directly from the app?**
A: The OTel Collector is a standalone agent/gateway that receives telemetry from your apps, processes/transforms it, and forwards it to one or more backends. Benefits of using it:
- **Backend decoupling** — swap or add backends (Jaeger → Datadog) without redeploying app code.
- **Batching and retry** — the app gets fast non-blocking exports; the Collector handles buffering, retries, and backpressure.
- **Sampling decisions** — tail-based sampling (see Q18) can be implemented in the Collector, not the app.
- **Enrichment** — add resource attributes (cluster name, datacenter) centrally rather than per-service.

**Q9. What is auto-instrumentation in OTel?**
A: OTel SDKs provide instrumentation libraries for common frameworks (Express, NestJS, Fastify, pg, Redis, gRPC, etc.) that automatically create spans for HTTP requests, DB queries, and outbound calls without writing any span code manually. In Node.js, `@opentelemetry/auto-instrumentations-node` registers all available instrumentations at process startup (before app code loads). This gives you baseline traces across the stack with zero per-library instrumentation code.

**Q10. When do you write manual (custom) spans on top of auto-instrumentation?**
A: Auto-instrumentation covers I/O boundaries (HTTP, DB, queues) but doesn't know about your business logic. You add custom spans for:
- Business-level operations: `"process-order"`, `"calculate-discount"`, `"validate-kyc"`.
- Non-standard I/O: a third-party SDK that auto-instrumentation doesn't cover.
- CPU-intensive operations where you want to isolate timing: `"parse-csv"`, `"render-template"`.
- Any operation you'd want to see in a flame graph independently of its parent.

```typescript
const span = tracer.startSpan('calculate-discount', {
  attributes: { 'order.id': orderId, 'user.tier': userTier }
});
try {
  const result = calculateDiscount(order);
  span.setStatus({ code: SpanStatusCode.OK });
  return result;
} catch (err) {
  span.recordException(err);
  span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
  throw err;
} finally {
  span.end();
}
```

**Q11. What are span attributes vs span events?**
A:
- **Attributes** — key-value metadata describing the span's context: `http.method`, `db.statement`, `user.id`, `order.id`. Indexed by backends for filtering/search. Set at span start or during the span's lifetime (before `end()`).
- **Events** — timestamped log-like records attached to a span: something that *happened* during the span's execution (`"cache miss"`, `"retry attempt 2"`, `"validation passed"`). Think of them as structured log entries scoped to a span — queryable alongside the trace without being a separate log line.

## Section 3: Trace Context Propagation

**Q12. What is trace context propagation?**
A: Propagation is the mechanism for passing trace identity (`traceId`, `spanId`, sampling decision) across process boundaries — so that the downstream service can create spans that are children of the upstream span, forming a connected tree rather than isolated per-service fragments.

**Q13. What is the W3C Trace Context standard?**
A: A W3C specification (now an official web standard) defining two HTTP headers for trace propagation:
- `traceparent` — encodes `version`, `traceId`, `parentSpanId`, and `traceFlags` (sampling bit) in a single header: `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`.
- `tracestate` — vendor-specific key-value pairs (optional), allowing backends like Datadog or Jaeger to carry proprietary metadata alongside the standard fields.

W3C Trace Context is the OTel default propagator and should be the standard choice in new systems. Older alternatives (B3 from Zipkin, X-Amzn-Trace-Id from AWS) still exist in legacy or mixed environments.

**Q14. How does propagation actually work in an HTTP call between two services?**
A:
1. **Injecting (outgoing)**: when Service A makes an HTTP call to Service B, the OTel SDK's propagator reads the active span from context and writes `traceparent` (and `tracestate`) headers onto the outgoing HTTP request.
2. **Extracting (incoming)**: when Service B receives the request, its OTel middleware reads those headers, creates a `SpanContext` from them, and sets it as the remote parent for the new span it creates. The new span gets the same `traceId` and sets `parentSpanId` to Service A's `spanId`.
3. Result: both spans share a `traceId` and the backend can render them as a connected parent-child pair.

In Node.js with OTel auto-instrumentation, this injection/extraction happens automatically for HTTP via `@opentelemetry/instrumentation-http`.

**Q15. How do you propagate trace context across a message queue (Kafka, RabbitMQ)?**
A: Inject the trace context into message headers at produce time; extract it at consume time. OTel instrumentation libraries for Kafka (`@opentelemetry/instrumentation-kafkajs`) and AMQP handle this automatically. The consuming span links to the producing span — but note the relationship is typically a *link* (not parent-child), because the consumer runs in a different async context, potentially much later, and the producer span may already be closed. Span links model this "caused by" relationship without implying synchronous nesting.

**Q16. What is a span link, and when do you use it instead of parent-child?**
A: A span link references another span by `traceId`/`spanId` without making it a structural parent. Use links when:
- **Async/decoupled flows**: the consuming process runs independently of the producer (queue, batch job). Parent-child would create a span that outlives the producer span, which is semantically wrong.
- **Fan-in**: a span that aggregates results from multiple upstream spans (e.g., a batch processor that handles 100 messages) — it can link to all 100 producer spans rather than having 100 parents.
- **Cross-tenant or cross-trace references**: you want to reference a related trace without merging them.

**Q17. What happens to propagation if one service in the chain doesn't instrument?**
A: The chain breaks. The uninstrumented service doesn't extract the `traceparent` from the incoming request, so any downstream spans it creates (if it does create any) start a new trace with a fresh `traceId`. The original trace appears to end at the hop before the uninstrumented service — you lose visibility into everything downstream of it. In mixed environments, this is a common "missing spans" debugging experience.

## Section 4: Sampling

**Q18. What is trace sampling, and why is it necessary?**
A: Tracing every single request at 100% volume is often impractical — at high RPS the storage and processing cost is prohibitive, and most traces of successful requests look identical. Sampling selects which traces to record in full and which to drop. The key constraint: the sampling decision must be consistent within a trace — all spans belonging to a trace must either all be kept or all be dropped.

**Q19. What is head-based sampling?**
A: The sampling decision is made at the start of a trace (at the root span) before any downstream work happens. The decision is encoded in the `traceFlags` bit of `traceparent` and propagated to all downstream services — they honor the upstream decision rather than making their own. Simple and cheap (no need to buffer spans), but the decision is made without knowing what the trace will look like (can't preferentially keep errors or slow traces that weren't yet slow at the start).

**Q20. What is tail-based sampling?**
A: The sampling decision is deferred until the entire trace is complete. All spans are collected (typically in the OTel Collector), the complete trace is evaluated, and then a decision is made — e.g., keep 100% of traces with errors, keep 100% of traces with latency > 2s, keep 1% of healthy fast traces. More intelligent than head-based but requires buffering all spans until the trace is complete, which adds memory/latency overhead in the Collector. Implemented in the OTel Collector's `tailsampling` processor.

**Q21. What is the `ParentBased` sampler in OTel?**
A: A composite sampler that defers to the upstream sampling decision if a remote parent exists (i.e., if `traceparent` arrives with the sampled flag set, keep it; if not, drop it). If there's no remote parent (root span), it falls back to a configured sampler (e.g., `TraceIdRatioBased` at 10%). This ensures sampling consistency: a downstream service won't create spans for a trace the upstream already decided to drop.

## Section 5: Production Concerns

**Q22. How do you connect traces to logs?**
A: Inject `traceId` and `spanId` into every log entry. OTel SDKs provide a log bridge that does this automatically — the current span's IDs are added to the log record. In practice with `pino` or `winston`, you read from OTel's active context:
```typescript
import { trace } from '@opentelemetry/api';

function getTraceContext() {
  const span = trace.getActiveSpan();
  if (!span) return {};
  const { traceId, spanId } = span.spanContext();
  return { traceId, spanId };
}

logger.info({ ...getTraceContext(), message: 'Order processed', orderId });
```
With this, you can jump from a log line in Kibana/Datadog directly to the corresponding trace in Jaeger/Tempo.

**Q23. What are OTel resource attributes, and why do they matter?**
A: Resource attributes describe the entity producing telemetry — the service, not the individual request. Set once at SDK initialization:
- `service.name` — mandatory; identifies which service's spans these are.
- `service.version` — correlate performance changes to deploys.
- `deployment.environment` — `production`, `staging`.
- `k8s.pod.name`, `k8s.namespace.name` — for Kubernetes; enables filtering by pod.

Without `service.name`, all spans from different services appear unlabeled in the backend — the most basic production mistake.

**Q24. What is the OTel semantic conventions spec, and why should you follow it?**
A: OTel defines standardized attribute names for common operations — `http.request.method`, `db.system`, `db.statement`, `rpc.method`, `messaging.system`, etc. Following these conventions means your traces are interpreted correctly by backends (Datadog, Grafana Tempo, Honeycomb can auto-build service maps, DB query analysis, and HTTP breakdowns from standard attributes). Inventing your own attribute names works but loses backend intelligence and makes cross-team observability harder.

**Q25. How do you avoid logging sensitive data in span attributes?**
A: Same discipline as structured logging — never set attributes like `user.password`, `credit_card.number`, or raw auth tokens. Span attributes are stored and indexed by the backend; they're queryable by anyone with access to the tracing UI. Follow OTel's guidance: log entity IDs (`user.id: 42`, `order.id: "ORD-999"`) not entity content. The OTel Collector's `transform` processor can scrub or redact attributes centrally before they reach the backend.

## Section 6: Scenario / System Design Questions

**Q26. "You have 5 microservices. A user reports checkout is slow intermittently. How do distributed traces help you diagnose this?"**
A: Pull traces for the checkout flow filtered by high latency (p95+). In the trace waterfall, you can see each service's span and its contribution to total latency. If `payment-service` consistently shows a 2s span while all other services are <100ms, the bottleneck is isolated. Drill into that span's attributes — `db.statement`, `http.url` of the downstream call it's making. Cross-reference with logs using `traceId` to find specific error events. Without tracing, you'd be guessing which of 5 services to investigate.

**Q27. "Design the tracing setup for a new NestJS-based microservice that communicates via HTTP and Kafka."**
A: 
1. **SDK init**: `@opentelemetry/sdk-node` initialized before app bootstrap, with `@opentelemetry/auto-instrumentations-node` for Express/NestJS HTTP, pg, Redis, kafkajs.
2. **Resource**: `service.name`, `service.version`, `deployment.environment` set from env vars.
3. **Exporter**: OTLP exporter pointing to the OTel Collector (not directly to Jaeger/Datadog — keeps the app decoupled).
4. **Sampler**: `ParentBasedSampler` wrapping `TraceIdRatioBased(0.1)` for prod (10% of new root traces, 100% of already-sampled upstream traces).
5. **Propagator**: W3C `TraceContextPropagator` + `B3Propagator` registered if any legacy services use B3.
6. **Kafka**: `@opentelemetry/instrumentation-kafkajs` handles inject/extract; spans use links (not parent-child) for async consume.
7. **Custom spans**: business operations (`process-payment`, `reserve-inventory`) wrapped manually with try/catch/finally + `recordException`.
8. **Log correlation**: `traceId`/`spanId` injected into pino logger via active span context.
9. **Collector**: tail-based sampling in Collector configured to keep 100% of error traces and 100% of latency > 1s, 5% otherwise.

**Q28. "A trace shows all spans except the ones from your DB query. What do you check?"**
A: 
1. Confirm `@opentelemetry/instrumentation-pg` (or relevant DB instrumentation) is registered *before* the DB client is initialized — OTel patches the client at require-time; if the client loads first, patching is missed.
2. Check sampling — if the DB spans are being created but dropped, increase sampling rate or check `traceFlags` propagation.
3. Verify the DB client version is in the supported range for the instrumentation package — version mismatches silently break patching.
4. Check if the DB calls are made inside an async context that lost OTel's context — `AsyncLocalStorage` context loss is a common cause of orphaned or missing child spans (e.g., DB calls made inside `Promise.all` without active context propagation).

## Quick Reference

| Concept               | What it is                                              | Key detail                                                    |
|---                    |---                                                      |---                                                            |
| Trace                 | End-to-end request journey                              | Identified by `traceId`; composed of spans                    |
| Span                  | Single unit of work                                     | Has `spanId`, `parentSpanId`, start/end, attributes, events   |
| Root span             | First span; no parent                                   | Duration = total request latency                              |
| `traceparent`         | W3C propagation header                                  | Carries `traceId`, `parentSpanId`, sampling bit               |
| `tracestate`          | W3C vendor extension header                             | Optional; carries backend-specific metadata                   |
| Span link             | Non-parent reference to another span                    | Use for async/queue flows, fan-in                             |
| Head-based sampling   | Decision at trace start                                 | Fast, cheap; can't prefer errors/slow traces                  |
| Tail-based sampling   | Decision after trace complete                           | Intelligent; requires buffering in Collector                  |
| OTel Collector        | Agent between app and backend                           | Batching, retry, sampling, backend decoupling                 |
| Resource attributes   | Static entity metadata (service name, version)          | Set once at init; mandatory for backend usability             |
| Auto-instrumentation  | Zero-code spans for HTTP, DB, queues                    | Register before app code loads                                |

---

**Tip for the interview:** At 5 YOE level, interviewers want to know you've actually set up OTel — not just that you know what a span is. Be ready to explain the Node.js SDK init order (OTel must load before the framework), why `ParentBased` sampling matters for consistency, and the difference between head and tail sampling. Have a war story about finding a latency bottleneck using traces that logs alone wouldn't have exposed. Know what breaks propagation (uninstrumented service in the chain, async context loss) — those are the real interview differentiators.
