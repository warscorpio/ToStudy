# Structured Logging, Log Levels, Correlation IDs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is structured logging, and how does it differ from plain-text logging?**
A: Plain-text logging emits human-readable strings (`"User 42 logged in at 14:03"`). Structured logging emits log entries as machine-parseable key-value documents — typically JSON — so every field is queryable, filterable, and aggregatable without regex. Example:
```json
{
  "timestamp": "2024-07-23T14:03:00.123Z",
  "level": "info",
  "message": "User logged in",
  "userId": 42,
  "service": "auth-service",
  "correlationId": "a1b2c3d4"
}
```

**Q2. Why does JSON become the de facto format for structured logs?**
A: JSON is natively supported by virtually every log aggregation platform (Datadog, Elasticsearch/ELK, Splunk, CloudWatch, Loki), easily parsed in any language, human-readable enough for local development, and self-describing — no schema file required to understand a field. Alternatives like logfmt (`key=value` pairs) exist but have weaker type support and less ecosystem momentum.

**Q3. What are the core fields every structured log entry should include?**
A:
- `timestamp` — ISO 8601 with milliseconds (UTC), critical for ordering and latency analysis.
- `level` — severity (see Section 2).
- `message` — short, static string describing the event (not a printf-style concatenation with dynamic data — those go in separate fields).
- `service` / `app` — which service emitted the log (essential in microservices).
- `correlationId` / `requestId` — trace the log back to a specific request (see Section 3).
- `environment` — `prod`, `staging`, `dev`.
- `version` / `commit` — the deployed artifact version (invaluable during incident triage).

**Q4. What's wrong with putting dynamic data inside the `message` string?**
A: `"User 42 failed login from 192.168.1.5"` is a unique string per event — you can't group all failed logins in Kibana/Datadog without a regex. If instead `message: "User login failed"` is static and `userId`, `ip` are separate fields, you can filter `message: "User login failed" AND userId: 42` or aggregate failure counts by IP directly. The message string should be a stable event type identifier, not a formatted sentence.

**Q5. What is log serialization overhead, and when does it matter?**
A: JSON serialization on the hot path (e.g., per-request on a 50k RPS service) can add CPU cost — especially with naïve implementations that allocate per log call. Libraries like `pino` (Node.js) are designed for this: they use fast JSON serializers, avoid V8 de-opt traps, and batch writes. In high-throughput systems you should benchmark logging overhead; sometimes async/non-blocking log flushing or log sampling is needed.

## Section 2: Log Levels

**Q6. What are the standard log levels, in order of severity?**
A: Commonly (from lowest to highest severity): `trace` → `debug` → `info` → `warn` → `error` → `fatal`. Different frameworks use slightly different names (`critical` instead of `fatal`, etc.), but the hierarchy is the same: levels below the configured threshold are suppressed at runtime.

**Q7. How do you choose which level to use? Walk through each.**
A:
- **trace** — extremely verbose, sub-operation details (entering/exiting functions, loop iterations). Almost never enabled in production; used in local debugging.
- **debug** — internal state useful for diagnosing a problem (DB query params, cache hit/miss). Disabled in prod by default; enabled temporarily during incident investigation.
- **info** — normal, expected system events worth recording (request received, job started, user authenticated). High volume but each event is meaningful.
- **warn** — something unexpected but non-fatal happened; the system handled it but it signals degradation or a recoverable error (e.g., retry succeeded, config fallback used, deprecated API called). Should be reviewed; too many warns = signal of underlying issue.
- **error** — an operation failed and the system could not recover from it internally (failed to save to DB, external API returned 500). Requires attention; typically alerts trigger on sustained error rates.
- **fatal** — the process/service cannot continue and will shut down (e.g., failed to connect to DB on startup). Rare; often followed immediately by a process exit.

**Q8. A junior dev logs every caught exception as `error`. What's the problem?**
A: Alert fatigue and noise. Not every caught exception is an error in the monitoring sense. A 404 "not found" that was caught and returned to the client is an expected application flow — log it at `info` or `warn`. An upstream timeout that triggered a retry and succeeded is a `warn`. Reserve `error` for unrecoverable failures that a human needs to act on. If everything is `error`, oncall gets paged for noise and true errors are buried.

**Q9. How do you configure log levels at runtime without redeployment?**
A: Several patterns:
- **Environment variable** — `LOG_LEVEL=debug node server.js`; app reads it on startup. Requires restart.
- **Hot-reload via config service** — app polls a feature-flag store or config endpoint and updates the logger's level atomically. No restart needed; useful for temporary debug logging in prod.
- **Per-module level overrides** — most logging frameworks support setting `debug` for `auth-module` while keeping everything else at `info`. Lets you target noisy investigation without drowning in unrelated logs.

**Q10. What is log sampling, and when do you use it?**
A: Log sampling means only recording a fraction of log events (e.g., 1% of `debug` logs, or 10% of `info` logs for high-frequency paths) to reduce volume and cost while preserving signal. Common in high-throughput services where logging every request at `info` would generate TBs/day. Errors are almost never sampled — you need 100% of them. Sampling decisions can be random, rate-based, or head-based (decision made at the start of a request and propagated to all services handling it).

## Section 3: Correlation IDs / Request IDs

**Q11. What is a correlation ID (also called a request ID or trace ID)?**
A: A unique identifier attached to a request at its entry point into the system, then propagated to every log entry, downstream service call, and queue message that originates from that request. It lets you pull all logs across all services that belong to a single user request, even across async boundaries.

**Q12. Where should a correlation ID be generated?**
A: At the outermost boundary — the API gateway, reverse proxy (Nginx/Traefik), or load balancer — so it's stamped before the request even reaches your application code. If an upstream service sends a correlation ID in a header (e.g., `X-Correlation-ID` or `X-Request-ID`), reuse theirs; don't generate a new one that breaks the chain. If none is provided, generate one at the first application layer that receives the request.

**Q13. What format should a correlation ID be?**
A: UUID v4 is the standard default — 128-bit, globally unique, easy to generate in any language. Some teams prefer shorter formats (base62-encoded 8-12 char strings) for readability in log lines. If you're using distributed tracing (OpenTelemetry, Jaeger, Zipkin), use that library's trace ID format directly so logs and traces can be correlated natively in the same tool.

**Q14. How do you propagate a correlation ID through a Node.js/NestJS service?**
A: The canonical pattern:
1. **Extract** the ID from the incoming request header (`X-Correlation-ID`) in middleware/interceptor.
2. **Store** it in async context — `AsyncLocalStorage` (Node.js ≥16) is the right primitive; it provides a request-scoped store without passing the ID down every function call manually.
3. **Inject** into the logger — a custom logger that reads from `AsyncLocalStorage` on every call, so `logger.info('...')` automatically includes the correlation ID.
4. **Forward** in all outgoing HTTP calls via an HTTP interceptor (Axios interceptor, NestJS `HttpService` interceptor) that reads from `AsyncLocalStorage` and sets the header on every outbound request.

```typescript
// Simplified NestJS interceptor pattern
@Injectable()
export class CorrelationIdInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const req = context.switchToHttp().getRequest();
    const correlationId = req.headers['x-correlation-id'] ?? uuid();
    req.headers['x-correlation-id'] = correlationId;
    return asyncLocalStorage.run({ correlationId }, () => next.handle());
  }
}
```

**Q15. How does a correlation ID propagate across message queues (RabbitMQ, Kafka)?**
A: The producer includes the correlation ID as a message header (AMQP supports headers natively; Kafka has record headers). The consumer reads the header at the start of processing and stores it in its own `AsyncLocalStorage` context, exactly like an HTTP middleware would. This ensures that async event-driven flows are traceable end-to-end.

**Q16. What's the difference between a correlation ID, a request ID, and a trace ID?**
A:
- **Request ID** — scoped to a single service's handling of one HTTP request. Unique within that service, not necessarily globally.
- **Correlation ID** — spans multiple services, passed across service boundaries. One correlation ID = one user-visible operation, regardless of how many microservices it touches.
- **Trace ID** — a distributed tracing concept (OpenTelemetry, Zipkin, Jaeger) that also carries span IDs to reconstruct the call graph (parent/child relationships). More powerful than a raw correlation ID — it tells you not just "which request" but "which service called which other service in what order with what latency." A trace ID is essentially a standardized, tooling-backed correlation ID.

**Q17. A user reports a bug. They give you their user ID and an approximate time. How do you use correlation IDs to investigate?**
A: Search the log aggregation platform (Kibana/Datadog) for that `userId` and time window to find any log entry from their session. Grab the `correlationId` from any one of those entries, then query all logs across all services for that correlation ID. You get the complete end-to-end log trail — every service the request touched, in order, with precise timestamps — regardless of which team's service produced the logs.

## Section 4: Production Concerns

**Q18. What are log aggregation platforms, and why do you need one?**
A: When you have multiple service instances writing logs to stdout, you need a centralized pipeline to collect, store, index, and query them. Common stacks: ELK (Elasticsearch + Logstash + Kibana), Datadog Logs, Grafana Loki (label-based, cheaper than full-text indexing), Splunk, AWS CloudWatch Logs Insights. Without aggregation, debugging a production issue means SSH-ing into individual containers — infeasible at any meaningful scale.

**Q19. What is log cardinality, and why is it a problem?**
A: Cardinality in logs refers to the number of unique values a field has. High-cardinality fields (like `userId`, `orderId`, or `correlationId`) are fine as log fields but dangerous as metric labels/tags in time-series databases (Prometheus, Datadog Metrics) — they explode the number of metric series and can crash the metrics backend. The rule: high-cardinality values go in logs, not in metric dimensions. For tracing, use trace ID correctly — it's what distributed tracing systems are built to handle.

**Q20. How do you handle sensitive data in logs (PII, tokens, passwords)?**
A: Never log raw sensitive fields — passwords, auth tokens, credit card numbers, SSNs. Strategies:
- **Scrubbing at the logger level** — many logging libraries support field redaction patterns applied before serialization (e.g., pino's `redact` option).
- **Structural discipline** — log entity IDs (`userId: 42`) not entity content (`email: "user@example.com"`).
- **Log level gating** — debug logs that dump full request/response bodies should be disabled in production by default.
- **Compliance requirements** — GDPR may require ability to delete a user's log entries; pseudonymizing identifiers (hashing user IDs) before logging is a common mitigation.

**Q21. What is the difference between logging and distributed tracing? Do you need both?**
A: Logs record discrete events with context; distributed traces record the call graph (timing, parent-child span relationships) across services. They're complementary: logs tell you *what happened* (and with correlation IDs, on *which request*), traces tell you *where time was spent* and *how services relate*. In a mature microservices setup you want both — and ideally linked: OpenTelemetry can inject trace IDs into log context automatically so you can jump from a trace waterfall directly to the relevant log entries.

**Q22. How do you prevent logging from becoming a performance bottleneck?**
A: Key practices:
- Use an async logger (writes are buffered and flushed off the request hot path) — `pino` does this by default.
- Avoid serializing expensive objects on every call. Use lazy evaluation where the framework supports it (`logger.debug(() => expensiveSerialize(obj))`).
- Set appropriate log levels per environment — debug/trace disabled in production.
- Apply log sampling for high-frequency info-level events.
- Write to stdout and let the container runtime/sidecar (Fluentd, Fluent Bit) handle forwarding — don't make the app responsible for network I/O to the logging backend.

## Section 5: Scenario / Design Questions

**Q23. "Design the logging strategy for a new NestJS microservice from scratch."**
A: Key decisions:
1. **Library**: `pino` for structured JSON with minimal overhead; `pino-http` for automatic HTTP request/response logging with response time.
2. **Fields**: every log gets `correlationId`, `service`, `environment`, `version` injected via a global logger wrapper backed by `AsyncLocalStorage`.
3. **Levels**: `info` for normal flow, `warn` for recoverable issues and business anomalies, `error` for unhandled failures (tied to alerting), `debug` off in prod by default, controllable via env var.
4. **Sensitive data**: configure `pino`'s `redact` for fields like `password`, `token`, `authorization`.
5. **Propagation**: NestJS interceptor for extraction + `AsyncLocalStorage` for propagation + Axios interceptor for forwarding in outbound calls.
6. **Aggregation**: emit to stdout; Fluent Bit sidecar ships to Elasticsearch/Datadog.

**Q24. "You're getting thousands of error logs per minute in production, but users aren't actually reporting issues. What's happening and how do you fix it?"**
A: Classic alert-fatigue antipattern — likely over-logging expected errors as `error`. Triage: sample 20-30 of the logs to understand the actual events. Common culprits: 4xx client errors (not found, unauthorized) logged at `error`, failed health-check retries that always succeed, third-party API rate-limit responses handled gracefully. Fix: reclassify by intent — client errors are `info` or `warn`, retried recoverable errors are `warn`, only true unhandled failures stay at `error`. Then rebuild alerting thresholds on the correct signal.

**Q25. "Your on-call engineer gets a pager alert that the checkout service has elevated errors. Walk me through how logs and correlation IDs help triage."**
A: 
1. Go to log aggregation, filter `service: checkout-service`, `level: error`, last 30 minutes. 
2. Look at the error messages — are they clustering around one message type (e.g., `"Payment gateway timeout"`)? 
3. Pick one error log, grab its `correlationId`. Query all services for that ID — this gives the full request trace: which upstream called checkout, what checkout called downstream, where it failed.
4. Check the `version` field — did this start after a recent deploy? Compare error rate before/after the deploy timestamp.
5. Look for common attributes across errors — same `userId` pattern? Same `paymentMethod`? Narrows root cause fast.

## Quick Comparison Table

| Aspect                  | Plain-text Logs                   | Structured (JSON) Logs                     |
|---                      |---                                |---                                         |
| Queryability            | Regex only                        | Field-level filtering, aggregations        |
| Parsing overhead        | None at write time                | JSON serialization cost (usually minimal)  |
| Human readability       | High (out of the box)             | Medium (needs pretty-print in dev)         |
| Aggregation platform    | Difficult to index                | First-class support (ELK, Datadog, Loki)   |
| Adding context fields   | String concatenation              | Add a key-value field — zero friction      |
| Correlation support     | Manual regex or convention        | Native field — just include `correlationId`|

---

**Tip for the interview:** At 5 YOE level, interviewers expect you to connect logging to operational realities — incident response, alert fatigue, compliance, cost. Know the `AsyncLocalStorage` pattern cold for Node.js/NestJS, be able to explain why `message` should be a static string, and have an opinion on when you'd reach for distributed tracing vs plain correlation IDs. "I've debugged a production issue using correlation IDs" is worth more than reciting log level definitions.
