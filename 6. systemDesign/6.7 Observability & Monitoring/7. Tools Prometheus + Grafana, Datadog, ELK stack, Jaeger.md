# Observability Tools: Prometheus + Grafana, Datadog, ELK Stack, Jaeger — Interview Q&A (5 YOE Level)

---

## Section 1: Observability Foundations

**Q1. What are the "three pillars of observability," and which tools cover which pillar?**
A: The three pillars are metrics, logs, and traces — each answers a different question about system behavior:
- **Metrics** — "Is something wrong?" Numerical aggregates over time. Tools: Prometheus, Datadog, Grafana (as a frontend), CloudWatch.
- **Logs** — "What happened?" Timestamped event records with full context. Tools: ELK stack (Elasticsearch, Logstash, Kibana), Datadog Logs, Loki.
- **Traces** — "Where did it go wrong?" End-to-end request flow across services. Tools: Jaeger, Zipkin, Datadog APM, Tempo.

In practice, you need all three: metrics tell you something is broken, logs tell you what happened, and traces tell you which service in the call chain caused it.

**Q2. Why do you need all three pillars? Can't you get by with just logs?**
A: Logs alone don't scale well as a primary alerting signal — searching through millions of log lines to answer "is my p99 latency degraded?" is slow and expensive. Metrics are purpose-built for that. Conversely, metrics alone can't tell you *why* a specific request failed — you need the log line with the stack trace. And without traces, in a microservices architecture, you have no way to know that the slow checkout request is actually caused by a downstream inventory service, not the checkout service itself. Each pillar has a different cost and use profile; together they cover the full diagnostic surface.

**Q3. What is OpenTelemetry, and why does it matter when choosing observability tools?**
A: OpenTelemetry (OTel) is a CNCF standard for instrumenting applications to produce metrics, logs, and traces in a vendor-neutral format. Instead of instrumenting your code with Datadog-specific SDKs or Jaeger-specific clients, you instrument once with the OTel SDK and route the telemetry to any compatible backend (Jaeger, Prometheus, Datadog, Grafana Cloud, etc.) via the OTel Collector. It matters because it decouples instrumentation from vendor lock-in — switching from Jaeger to Datadog APM doesn't require re-instrumenting every service. At 5 YOE level, you're expected to know this exists and understand why teams are adopting it.

## Section 2: Prometheus

**Q4. How does Prometheus collect metrics — push vs pull, and what are the trade-offs?**
A: Prometheus uses a **pull model** — it scrapes HTTP endpoints (`/metrics`) exposed by target services at a configured interval (default: 15s). This is the opposite of StatsD or Datadog Agent's push model where services send metrics to a central collector.

Pull trade-offs:
- **Advantages** — Prometheus controls the scrape schedule; it can detect when a target is down (scrape fails); targets don't need to know the address of the metrics server. Easier to reason about what's being collected and when.
- **Disadvantages** — doesn't work well for short-lived jobs (a batch job that runs for 30 seconds may disappear before being scraped). Prometheus provides **Pushgateway** as a workaround for this case — batch jobs push metrics there, and Prometheus scrapes the gateway.

**Q5. What is a Prometheus exporter, and when do you need one?**
A: An exporter is a sidecar or adapter that translates a third-party system's internal metrics into the Prometheus exposition format. You need one when you're monitoring infrastructure or middleware that doesn't natively expose a `/metrics` endpoint. Common exporters: `node_exporter` (Linux host metrics: CPU, memory, disk, network), `postgres_exporter` (DB stats), `redis_exporter`, `blackbox_exporter` (probing endpoints for uptime), `kafka_exporter`. For your own services, you use a Prometheus client library (Go, Java, Python, etc.) to directly expose a `/metrics` endpoint — no exporter needed.

**Q6. Explain Prometheus's data model and what a time series looks like.**
A: Every time series in Prometheus is uniquely identified by a metric name plus a set of key-value labels. For example:

`http_requests_total{method="GET", status_code="200", service="checkout"} 4821`

The metric name describes what's being measured; labels are the dimensions. The combination of name + all label values defines one unique time series. This model enables powerful filtering and aggregation in PromQL — you can sum across all methods, filter to a specific service, or compute per-label rates. The cardinality trap (Section 5 of the metrics Q&A) lives here: every unique label combination is a separate time series stored in Prometheus's TSDB.

**Q7. Walk me through how you'd write a PromQL query to compute the per-second error rate as a percentage of total traffic, broken down by service.**
A: 

```promql
100 * (
  sum by (service) (rate(http_requests_total{status_code=~"5.."}[5m]))
  /
  sum by (service) (rate(http_requests_total[5m]))
)
```

Breaking it down:
- `rate(http_requests_total{status_code=~"5.."}[5m])` — per-second rate of 5xx requests over the last 5 minutes, using a regex to match all 500-level codes.
- `sum by (service)` — aggregate across all instances of each service (so if checkout has 10 pods, you get one combined rate).
- Divide error rate by total rate to get proportion, multiply by 100 for percentage.

This is the kind of query that drives an error-rate SLO dashboard or burn-rate alert.

**Q8. What is Prometheus's retention model, and what are its limitations for long-term storage?**
A: By default, Prometheus stores data locally on disk with a configurable retention period (default: 15 days). This local TSDB is highly optimized for recent data and fast range queries, but it's not designed for long-term storage — it doesn't replicate data, has no HA built in (a single Prometheus server is a SPOF), and retention beyond 1–2 years is impractical on local disk. For long-term storage, teams use remote write backends: **Thanos** (object storage like S3, with a query layer that federates across Prometheus instances) or **Cortex / Grafana Mimir** (horizontally scalable, multi-tenant Prometheus-compatible backends). The remote write API lets Prometheus stream samples to these systems in real time.

**Q9. What is Prometheus Alertmanager, and what does it do that Prometheus itself doesn't?**
A: Prometheus evaluates alerting rules and fires alerts, but it doesn't manage *what happens to those alerts*. That's Alertmanager's job. Alertmanager handles:
- **Routing** — send alerts to different channels (PagerDuty, Slack, email) based on labels (e.g., severity=critical → PagerDuty; severity=warning → Slack).
- **Grouping** — batch related alerts into a single notification so a large outage doesn't flood on-call with 200 individual pages.
- **Inhibition** — suppress child alerts when a parent alert is firing (e.g., if the whole datacenter is down, suppress individual service alerts for that DC).
- **Silencing** — mute alerts during planned maintenance windows.

## Section 3: Grafana

**Q10. What exactly is Grafana's role — is it a metrics system?**
A: Grafana is a visualization and dashboarding layer — it stores no data itself. It connects to data sources (Prometheus, Elasticsearch, Datadog, Loki, Tempo, CloudWatch, SQL databases, and dozens of others) and renders their data as charts, tables, heatmaps, and stat panels. Its value is unifying metrics, logs, and traces in a single UI, regardless of the backend. In a typical stack: Prometheus stores metrics, Loki stores logs, Tempo stores traces — Grafana queries all three and lets you navigate between them (e.g., click a spike in a latency chart → open the correlated logs for that time window).

**Q11. What is Grafana Loki, and how is it different from Elasticsearch for log storage?**
A: Loki is Grafana's log aggregation system, designed to be "Prometheus for logs." The key difference from Elasticsearch:
- **Loki** — indexes only log *labels* (not the full log text). Log content is stored compressed in object storage (S3, GCS). This makes it significantly cheaper to operate at scale. Queries are done with LogQL (similar to PromQL), and full-text search works via grep-style pattern matching on the stored chunks — fast for targeted queries, slower for open-ended search.
- **Elasticsearch** — indexes the full text of every log line (inverted index), enabling very fast arbitrary full-text search. Much more powerful for exploratory search (e.g., "find all logs mentioning 'payment failed' in the last 7 days across all services"). But also significantly more expensive in CPU, memory, and storage — especially at high ingestion rates.

Choose Loki when you have high log volume and primarily query by known labels (service, pod, level). Choose Elasticsearch when your team relies heavily on full-text search and ad-hoc log exploration.

**Q12. What makes a Grafana dashboard good vs bad in a production environment?**
A: Bad dashboards are common and create noise rather than insight. Key principles for good dashboards:
- **Answer a specific question** — a dashboard titled "Service Health" that shows 40 unrelated panels answers nothing clearly. Design around a user question: "Is checkout healthy right now?" or "Why is latency elevated?"
- **Show SLI/SLO status prominently** — the most important panel is usually the one that tells you if you're in SLO breach, with burn rate and remaining budget visible.
- **Use the right panel type** — time series for trends, stat panels for current values, heatmaps for latency distributions, tables for ranked lists. Using a time-series panel for "current error count" misleads the viewer.
- **Template variables** — parameterize by environment, service, and region so one dashboard serves all contexts without duplication.
- **Avoid alert-in-dashboard anti-pattern** — dashboards are for investigation, not alerting. An alert should page you; the dashboard is what you open next.

## Section 4: Datadog

**Q13. What is Datadog, and how does it differ architecturally from the Prometheus + Grafana stack?**
A: Datadog is a fully managed, SaaS observability platform — it handles ingestion, storage, querying, dashboards, alerting, APM, log management, and more in a single product. You install the Datadog Agent on your hosts/containers, and it ships metrics, logs, and traces to Datadog's cloud.

Key architectural differences from Prometheus + Grafana:
- **Managed vs self-hosted** — no Prometheus server, TSDB, Alertmanager, or Grafana to operate; Datadog manages all infrastructure.
- **Push vs pull** — the Datadog Agent pushes data to Datadog's cloud; Prometheus pulls from targets.
- **Unified product** — metrics, logs, APM, RUM, synthetics, security all in one platform with native correlation. In Prometheus + Grafana, you assemble and integrate separate tools.
- **Cost model** — Datadog charges per host, per ingested log byte, per APM span; costs can escalate quickly at scale. Prometheus + Grafana is open source (infra costs only) but has operational overhead.

**Q14. What is a Datadog Agent, and what does it do?**
A: The Datadog Agent is a lightweight daemon that runs on every host or as a sidecar in containers. It:
- Collects system-level metrics (CPU, memory, disk, network) automatically.
- Runs integration checks for databases, middleware, and cloud services (150+ integrations).
- Tails log files and ships them to Datadog's log management backend.
- Receives APM traces from the application (via language-specific tracing libraries) and forwards them.
- Collects custom metrics sent via DogStatsD (a StatsD-compatible push interface embedded in the agent).

In Kubernetes, the Agent typically runs as a DaemonSet (one pod per node) with a Cluster Agent (one per cluster) for cluster-level metadata.

**Q15. What are Datadog tags, and how do they compare to Prometheus labels?**
A: Datadog tags are key-value pairs attached to metrics, logs, and traces — functionally equivalent to Prometheus labels but with a few differences:
- Tags in Datadog apply uniformly across all three pillars; the same `service:checkout` tag on a metric, a log line, and a trace allows cross-pillar correlation natively.
- Prometheus labels are typed per-metric; Datadog tags are more loosely typed and applied at the agent or SDK level.
- Cardinality is a shared concern — Datadog also charges more for high-cardinality custom metrics (metrics with many unique tag combinations), and their documentation explicitly warns against `user_id` or `session_id` as tags for the same reasons as Prometheus.

**Q16. What is Datadog APM, and what does it give you that metrics and logs alone don't?**
A: Datadog APM provides distributed tracing and service performance monitoring. It automatically instruments popular frameworks and libraries (Express, Django, Spring, etc.) via auto-instrumentation, capturing spans for every incoming request, outgoing DB call, HTTP call, and cache operation. What it gives you beyond metrics and logs:
- **Service Map** — automatically visualizes service dependencies and traffic flows; no manual diagram maintenance.
- **Flame graphs** — trace-level view of where time is spent within a single request: which DB query took 800ms, which external API call timed out.
- **Error attribution** — correlates a spike in your error rate metric directly to a specific code path and error message, without manual log searching.
- **Continuous profiling** — code-level CPU/memory profiling correlated with traces, showing which function is consuming resources.

**Q17. When would you choose Datadog over a self-hosted Prometheus + Grafana + Jaeger stack?**
A: This is a cost-vs-operational-overhead decision:

Choose **Datadog** when:
- The team is small and can't afford to operate observability infrastructure (Prometheus HA, Thanos, ELK cluster tuning, Jaeger backend).
- You need a unified product where metrics, logs, and traces correlate natively out of the box.
- Budget is available — Datadog costs are predictable at small scale and the ROI of not self-managing is real.
- You need features like RUM (Real User Monitoring), Synthetics, or Security Monitoring that would require additional tools to replicate.

Choose **self-hosted** when:
- Scale makes Datadog prohibitively expensive (high host count, high log volume, or high APM span volume).
- Data residency or compliance requirements prohibit sending telemetry to a third-party SaaS.
- The team has SRE/platform engineers who can own the observability stack.
- You're already in the Kubernetes/CNCF ecosystem and Prometheus is native.

In reality: many teams start with Datadog for speed, then migrate parts of the stack to self-hosted as scale makes the cost untenable.

## Section 5: ELK Stack

**Q18. What does ELK stand for, and what does each component do?**
A: ELK stands for **Elasticsearch**, **Logstash**, and **Kibana** — though the modern term is "Elastic Stack" because Beats (lightweight shippers) are now a core component:
- **Elasticsearch** — the distributed search and analytics engine; stores and indexes log data, and handles queries.
- **Logstash** — a data processing pipeline that ingests logs from many sources, parses/transforms them (grok patterns, field extraction, enrichment), and ships to Elasticsearch.
- **Kibana** — the visualization frontend; Discover (ad-hoc log search), Dashboards, and Lens (charts) all query Elasticsearch.
- **Beats** — lightweight agents (Filebeat for log files, Metricbeat for system metrics, Packetbeat for network) that ship data from hosts to Logstash or directly to Elasticsearch. Often preferred over Logstash for simple forwarding because they have a much smaller resource footprint.

**Q19. What is an Elasticsearch index, and what is index lifecycle management (ILM)?**
A: An Elasticsearch index is a logical namespace for a collection of documents (log entries). In practice, logs are organized into time-based indices (e.g., `logs-2026.07.23`) so you can query a day's worth of logs without scanning all data. Index Lifecycle Management (ILM) automates the transitions an index goes through:
- **Hot** — actively written to and queried; stored on fast SSD nodes.
- **Warm** — no longer written to but still queried; can be moved to lower-cost nodes with slower storage.
- **Cold** — rarely queried; compressed and moved to cheapest storage (e.g., frozen tier or object storage).
- **Delete** — indices older than the retention policy are automatically removed.

ILM is critical for controlling Elasticsearch storage costs and performance at scale; without it, clusters fill up and performance degrades as old indices compete with hot data for resources.

**Q20. What is a grok pattern in Logstash, and when would you use it?**
A: Grok is a pattern-matching syntax used in Logstash (and Elasticsearch's ingest pipelines) to parse unstructured log text into structured fields. For example, an NGINX access log line like:

`192.168.1.1 - - [23/Jul/2026:10:15:32 +0000] "GET /api/orders HTTP/1.1" 200 1234`

Can be parsed with a grok pattern to extract: `client_ip`, `timestamp`, `method`, `path`, `status_code`, `bytes`. Once structured, these fields are indexed and queryable (e.g., filter by `status_code:500`). You use grok when you're ingesting logs from systems that don't emit structured JSON — legacy apps, third-party services, syslog output. Modern practice is to emit logs as structured JSON directly from the application, which Logstash or Filebeat can pass through without grok parsing overhead.

**Q21. What are common operational pain points with Elasticsearch at scale?**
A: Elasticsearch is powerful but operationally demanding:
- **Heap pressure and GC pauses** — Elasticsearch runs on the JVM. A heap that's too small causes frequent GC; too large risks long stop-the-world GC pauses. The rule of thumb: set heap to 50% of available RAM, capped at 32GB (above 32GB, JVM compressed OOPs are disabled, hurting performance).
- **Split brain** — if a cluster loses quorum and two node groups both elect themselves as master, you get two clusters writing to the same indices. Modern Elasticsearch uses the Raft-based cluster coordination (removed Zen discovery) to mitigate this, but it's a classic war story.
- **Shard count explosion** — too many small shards (from over-indexing or long retention with daily indices) increases cluster state size and metadata overhead. Too few shards limits parallelism. Right-sizing shards is a recurring operational challenge.
- **Reindexing cost** — changing a field's mapping requires reindexing — copying all data into a new index with the new mapping. For large indices this is slow and resource-intensive.
- **Hot nodes bottlenecking** — without ILM or proper tiering, all indices compete for the same hot-tier node resources.

**Q22. What is Kibana's Discover view, and how is it used during an incident?**
A: Discover is Kibana's log exploration interface — you pick a time range, filter by fields (e.g., `service: checkout AND level: error`), and see matching log lines with their full fields. During an incident it's typically used to:
- Narrow down the first occurrence of an error after a spike shows on a metrics dashboard.
- Search for a specific error message or exception across all services in a time window.
- Correlate events — "the error started at 14:32; what deployed or changed around that time?"
- Drill into a specific request by trace ID (if logs carry trace context) to find all log lines for that request across services.

## Section 6: Jaeger

**Q23. What is distributed tracing, and what problem does Jaeger solve?**
A: In a microservices system, a single user request may fan out through 10 or 20 services. A traditional log gives you what happened in one service; it can't tell you that the total checkout latency of 3 seconds was caused by a 2.7-second delay in the inventory service, which was waiting on a slow database query. Distributed tracing instruments every service to emit spans — records of the work done for a request, with a shared trace ID linking them all. Jaeger collects, stores, and visualizes these spans as a trace: a tree of nested operations showing timing, dependencies, and errors for the full request lifecycle.

**Q24. Explain the data model: what is a trace, a span, and a parent-child relationship?**
A: 
- **Trace** — the full end-to-end record of a single request across all services. Identified by a globally unique `trace_id`.
- **Span** — a single unit of work within a trace: one RPC call, one DB query, one function call. Has a `span_id`, a start timestamp, a duration, a name, and tags (key-value metadata).
- **Parent-child** — when service A calls service B, A's span is the parent; B creates a child span. This tree structure reveals the call hierarchy and lets you see that B's 200ms latency is nested inside A's total 300ms.
- **Span context propagation** — the `trace_id` and parent `span_id` are propagated in request headers (e.g., `traceparent` in W3C Trace Context standard, or `X-B3-TraceId` in Zipkin B3 format) so that downstream services can attach their spans to the same trace.

**Q25. What is sampling in Jaeger, and why is it necessary?**
A: At high traffic volumes (thousands of RPS), storing a span for every operation of every request would be prohibitively expensive — a single request might generate 50+ spans across 10 services. Sampling decides which traces to actually record:
- **Head-based sampling (probabilistic)** — the decision is made at the entry point before the request is processed. Simple: sample 1% of all traffic. Cheap and easy to implement. Downside: you may miss 99% of the errors if they affect only 1 in 1,000 requests.
- **Tail-based sampling** — the decision is made *after* the request completes, based on the full trace. This lets you capture 100% of errors and slow requests (the interesting ones) while sampling away the healthy fast requests. More accurate but much harder to implement — requires buffering traces before making the sampling decision (Jaeger's Collector supports this via remote sampling strategies, and OpenTelemetry Collector has a tail-sampling processor).

**Q26. How do you use Jaeger to debug a latency spike in production?**
A: 
1. Start from a metrics alert: p99 latency on the checkout service is 3 seconds.
2. Open Jaeger, search for traces on the `checkout` service filtered to duration > 2 seconds in the affected time window.
3. Pick a representative slow trace and open the flame graph view — this shows the timeline of all spans for that request.
4. Identify the bottleneck: "the checkout span itself took 3s, but 2.7s was spent waiting on a child span to `inventory-service`."
5. Drill into the inventory span: it shows a child span `db.query` on the `inventory` table took 2.6s with a tag `db.statement: SELECT * FROM inventory WHERE product_id=...` — a missing index query.
6. You now have the full chain: latency alert → slow trace → slow service → slow query → root cause.

This is the canonical "metrics → traces → logs" workflow; without traces, step 4–5 would require correlating logs across services manually.

**Q27. What is Jaeger's storage backend, and what are the options?**
A: Jaeger's Collector receives spans and writes them to a storage backend. Supported backends:
- **Cassandra** — the original recommended backend; handles high write throughput well, but operationally complex to manage and tune.
- **Elasticsearch / OpenSearch** — popular choice because many teams already run Elasticsearch for logs; traces and logs co-exist in the same cluster, and Kibana/Jaeger UI can both query it. The downside: Elasticsearch is not optimized for trace data's access patterns (wide documents, short TTL).
- **Badger** (embedded) — in-memory/local disk store for development and very small deployments. Not suitable for production.
- **Kafka** (as a buffer) — for high-throughput deployments, Collectors can publish to Kafka and a separate Ingester reads from Kafka and writes to the backend, decoupling ingest spikes from storage writes.

At scale, many teams migrate to Tempo (Grafana's trace backend, uses object storage like S3) or Datadog APM to avoid operating Elasticsearch or Cassandra for traces.

## Section 7: Cross-Tool Integration & Scenarios

**Q28. How do you correlate a metric alert in Grafana to a log in ELK and then a trace in Jaeger?**
A: This is the "three pillars" workflow in practice, and it requires deliberate instrumentation:
1. **Metric alert fires** in Grafana: p99 latency spike on `payment-service` at 14:32.
2. **Jump to logs** in Kibana (or Grafana Explore if using Loki): filter `service: payment-service AND level: error` in the 14:30–14:35 window. You find log lines with `trace_id: abc-123` in the error entries.
3. **Jump to trace** in Jaeger: search for `trace_id: abc-123`. The flame graph shows the payment service called `fraud-service`, which timed out after 5 seconds on an external API.
4. **Root cause**: the fraud-detection API vendor had a partial outage. Fix: add a circuit breaker and fallback.

This workflow only works if your services emit `trace_id` in structured log output — a discipline that has to be enforced at the instrumentation layer. OTel's SDKs make this automatic when properly configured.

**Q29. "Your team is considering replacing ELK with Loki. What are the trade-offs you'd walk through?"**
A: I'd frame this as a cost vs capability trade-off:

**Reasons to move to Loki:**
- Significantly cheaper to operate — no expensive full-text indexing; uses object storage (S3) for log body storage.
- Tighter Grafana integration — metrics, logs, and traces all in Grafana with easy cross-navigation.
- Lower operational complexity — no JVM tuning, shard management, or cluster rebalancing.
- PromQL-like LogQL is familiar to anyone already writing Prometheus queries.

**Reasons to stay on ELK:**
- Full-text search is genuinely faster and more powerful in Elasticsearch — if your team does a lot of ad-hoc log exploration with arbitrary text searches, Loki's chunk-scan model is slower.
- Existing investment — if ELK is well-tuned and the team knows it, migration cost may outweigh the benefit.
- Elasticsearch has richer aggregation and analytics capabilities (e.g., rare term detection, anomaly detection in paid tier).

The honest summary: if your team queries logs primarily by known labels (service, pod, level, trace_id), Loki is cheaper and fits the Grafana ecosystem better. If you rely on exploratory full-text search across all fields, Elasticsearch is still better at that specific job.

**Q30. "You're designing the observability stack for a new platform from scratch — 20 microservices, 50 engineers, cloud-native on Kubernetes. Walk me through your decisions."**
A: I'd make decisions in layers:

**Metrics:** Prometheus with the kube-prometheus-stack (Prometheus Operator, node-exporter, kube-state-metrics, and pre-built Grafana dashboards). For long-term storage: Grafana Mimir or Thanos, writing to S3. This is the standard cloud-native choice — well-supported, cost-effective, and native to the Kubernetes ecosystem.

**Logs:** Depends on team maturity. If the team is small and log exploration patterns are predictable: Grafana Loki (cheaper, integrates natively). If there's a strong need for full-text search and the team will do a lot of ad-hoc analysis: a managed Elasticsearch (Elastic Cloud or OpenSearch on AWS) to avoid the operational burden of self-managing the cluster.

**Traces:** Jaeger with Elasticsearch backend initially (reusing the log cluster), or Grafana Tempo (if using Loki, keeps the stack unified). Instrument everything with OpenTelemetry SDKs from day one — so we can switch backends later without re-instrumentation. Use head-based sampling at 10% initially, with tail-based sampling for errors (capture 100% of failing traces).

**Frontend:** Grafana as the unified UI for all three pillars. Dashboards for each service's RED metrics (Rate, Error rate, Duration) using Grafonnet or Terraform for dashboard-as-code.

**Alerting:** Prometheus Alertmanager for metric-based alerts, with burn-rate alerting rules (not static thresholds) routed to PagerDuty for critical, Slack for warnings.

**Instrumentation standard:** OTel from the start — enforce it via shared libraries and CI checks.

**Tip for the interview:** At 5 YOE level, the interesting answer is never just "use Prometheus for metrics and ELK for logs." Interviewers want to hear *why* — why Loki instead of Elasticsearch, why Thanos instead of just longer retention on Prometheus, why OTel matters for avoiding lock-in, what goes wrong when you add a high-cardinality label to a Datadog metric. The best answers show you've actually operated these tools under pressure: you've debugged a flapping Elasticsearch cluster, you've hit Prometheus cardinality limits, you've chased a latency bug through a Jaeger flame graph. Those war stories are worth more than a feature comparison table.
