# Blob/Object Storage (S3): Presigned URLs, Multipart Uploads — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is object storage, and how does it differ from block and file storage?**
A: Object storage stores data as discrete, self-contained **objects** — each consisting of the data itself (arbitrary bytes), metadata (system metadata like content-type, size, ETag, and user-defined custom metadata), and a unique key within a flat namespace (no real directory hierarchy, though `/`-delimited key prefixes simulate one). It differs from the other two storage paradigms in important ways: **block storage** (EBS, SAN) exposes raw storage devices to an OS, which then manages a filesystem on top — appropriate for databases and operating systems that need low-latency, random read/write access at the block level. **File storage** (NFS, EFS) exposes a hierarchical directory tree accessible via file protocols — appropriate for workloads needing shared file access across multiple servers. Object storage sacrifices the random-byte-modification capability (you can't append to or partially modify a stored object without replacing it entirely) and the strong filesystem semantics in exchange for: unlimited horizontal scale, very high durability (S3 is designed for 99.999999999% — "eleven nines" — durability), global accessibility via HTTP, and a simple flat API that requires no mounted filesystem or attached block device — making it ideal for large-scale storage of blobs, images, videos, backups, data lake files, and any data where the unit of access is the whole object rather than individual bytes.

**Q2. What is S3's data model — what are buckets, objects, and keys?**
A: A **bucket** is the top-level namespace container — a globally-unique name within the S3 service, scoped to a specific AWS region, configured with access policies, versioning settings, lifecycle rules, and replication configuration. A **object** is a single stored item — up to 5TB in size, comprising the data payload, system metadata, and any user-defined metadata. An **object key** is the unique identifier for an object within its bucket — a string that can contain `/` characters, which S3 treats as an ordinary character in the key name but which the console and most tools interpret as a path delimiter, creating the appearance of a folder hierarchy. The "folder" abstraction is purely cosmetic — `images/profile/user123.jpg` is just a flat string key whose prefix `images/profile/` happens to look like a directory path; S3 doesn't actually maintain directory objects. This distinction matters operationally because listing "all objects in a folder" is implemented as listing all keys with a given prefix — a flat prefix scan, not a directory read — and very large numbers of objects with the same prefix can have listing performance implications.

**Q3. What consistency guarantees does S3 provide, and why did this change in 2020 matter?**
A: Before December 2020, S3 provided **eventual consistency** for overwrite PUTs and DELETEs — a PUT replacing an existing object might return the old version to a subsequent GET for some brief window; a DELETE might still return the deleted object briefly afterward. New object PUTs (first time a key is written) were strongly consistent. In December 2020, AWS updated S3 to provide **strong read-after-write consistency for all operations** — a successful PUT, DELETE, or COPY immediately reflected in all subsequent GETs and LIST operations for that object, from any client, anywhere, with no eventual-consistency window. This matters because it eliminates an entire class of application-level workarounds (using DynamoDB as a consistent index over S3, cache-busting strategies, retry loops after writes) that teams previously needed to tolerate S3's eventual consistency. For interview purposes: the modern answer is that S3 is strongly consistent, but being aware of the historical eventual-consistency behavior and the workarounds it necessitated demonstrates depth.

## Section 2: Presigned URLs

**Q4. What is a presigned URL, and what problem does it solve?**
A: A presigned URL is a time-limited, cryptographically signed URL that grants temporary access to a specific S3 object (for GET/download, PUT/upload, or other operations) to **anyone who possesses the URL**, without requiring them to have AWS credentials. It solves the problem of **controlled, temporary, direct client access to S3 objects without proxying through your application server**. Without presigned URLs, allowing a user to download a private S3 object requires either: making the object public (loses access control entirely), or having your application server fetch the object from S3 and stream it to the user (application server becomes a bandwidth bottleneck, pays for the egress twice — S3 to server, then server to client). A presigned URL gives the user a direct path from their browser to S3, bypassing your application server entirely for the actual data transfer, while the credential and access control logic remains on your server (which generates and issues the signed URL).

**Q5. How does a presigned URL work mechanically — what does the signature actually bind?**
A: A presigned URL is an ordinary S3 URL with authentication parameters appended as query string parameters (using AWS Signature Version 4): the **credential scope** (which AWS account and IAM identity generated the signature), the **expiry timestamp** (`X-Amz-Expires`, the number of seconds until the URL becomes invalid), the **signed headers**, and the **signature itself** (an HMAC-SHA256 of the canonical request — constructed from the HTTP method, the URL path, the expiry, the credential scope, and the specific headers being signed). The signature cryptographically binds all of these together — if any component is modified (the bucket, the key, the expiry, the allowed method), the signature verification by S3 fails and the URL is rejected. The key security property: the URL is tamper-evident. An attacker who has the URL cannot extend its expiry, access a different object, or use it for a different HTTP method — any such modification invalidates the signature.

**Q6. What information must be decided at URL generation time, and what are the constraints?**
A: The **bucket**, **object key**, **HTTP method** (GET for download, PUT for upload, DELETE, etc.), **expiry duration** (maximum 7 days for presigned URLs signed with IAM user credentials or IAM role credentials — with one important caveat: presigned URLs signed with temporary credentials from STS have a maximum expiry equal to the remaining lifetime of the underlying temporary credentials, which may be shorter than 7 days), and optionally **content-type** and **content-length-range constraints** (for PUT URLs, you can bind the URL to only accept objects with a specific Content-Type or within a size range, providing server-side validation that the client must satisfy). Constraints chosen at URL generation time cannot be changed without generating a new URL — this is a design implication: if a use case requires flexible expiry or variable access scope, the URL must be regenerated, which requires calling back to the application server.

**Q7. What are the common use cases for presigned GET URLs versus presigned PUT URLs, and how do the security models differ?**
A: **Presigned GET** (download): used to grant temporary, authenticated access to a private object — profile pictures, generated reports, invoice PDFs, any content stored privately in S3 that a specific user should be able to access for a limited time. The security model: the application server controls *who* gets the URL and *when*, verifying authorization before generating and returning the URL. Once issued, the URL is valid for its lifetime regardless of whether the user's session remains valid — a user whose access is revoked mid-session can still use a previously issued presigned GET URL until it expires, which is one reason short expiry durations are preferred. **Presigned PUT** (upload): used to allow a client to upload a file directly to S3 without the file bytes ever passing through the application server — the application server generates a presigned PUT URL for a specific key (typically including the user's ID and a UUID in the key to scope and namespace the upload), the client uploads directly to S3, and the application server is notified (via S3 event notification or polling) when the upload completes. The security model difference: a PUT URL grants write access to a specific key — if leaked, an attacker can overwrite that key until the URL expires, but cannot read existing content or write to other keys (the URL is key-specific). Content-type and size constraints on PUT URLs limit the damage from a leaked URL by preventing arbitrary data from being uploaded.

**Q8. What are the security risks of presigned URLs, and how do you mitigate them?**
A: **URL leakage** — a presigned URL is a bearer credential: anyone possessing it can exercise its permissions. It can leak via browser history, referrer headers (if the URL is used as an `href` and the page has external resources), server logs on the S3 side, shared via copy-paste, or intercepted if not transmitted over HTTPS. Mitigations: always use short expiry times proportional to the specific use case (a URL for a user's current session's document download: minutes; a link in an email for later retrieval: hours; never days unless genuinely necessary); ensure URLs are only transmitted over HTTPS; log URL generation (not the URL itself, but which identity generated a URL for which object at what time) for audit purposes. **Overly broad scope** — using a presigned URL that covers a broader key prefix than necessary, or signing a DELETE URL when only GET is needed. Mitigation: always sign for the minimum required method and the most specific possible key. **Revocation difficulty** — presigned URLs cannot be individually revoked before expiry (without rotating the underlying signing credentials, which is disruptive). Mitigation: short expiry is the primary tool; for especially sensitive content, use a separate CloudFront signed URL with a custom origin, which can be invalidated via a CloudFront key group rotation.

**Q9. What is the difference between a presigned URL and a CloudFront signed URL/cookie, and when would you choose one over the other?**
A: Both grant temporary, authenticated access to private content, but they operate at different layers with different trade-offs. A **presigned S3 URL** provides direct S3 access — the client's request goes to S3, the content is served from S3's regional endpoints, and each URL is independently generated and independently valid. A **CloudFront signed URL or signed cookie** provides access through a CloudFront distribution — the content is served from CloudFront's global edge cache, not directly from S3, giving caching, lower global latency, and the ability to use custom domains; signed cookies in particular can grant access to multiple objects matching a pattern (e.g., all objects under `/private/user123/*`) with one cookie, rather than generating a separate signed URL per object. Choose presigned S3 URLs for: simple, infrequent, single-object access where CDN caching isn't needed; developer-facing APIs or back-office tooling. Choose CloudFront signed URLs/cookies for: user-facing content where global low-latency matters; streaming media (video, audio); granting access to many objects in one auth decision; content that benefits from edge caching to reduce origin load.

## Section 3: Multipart Uploads

**Q10. What is a multipart upload, and what problems does it solve?**
A: A multipart upload is S3's mechanism for uploading large objects by splitting them into smaller parts, uploading each part independently (potentially in parallel), and then completing the upload by telling S3 to assemble all parts into one final object. It solves three distinct problems: **reliability** — uploading a 10GB file in one HTTP request means a network interruption at the 9.5GB mark requires restarting from zero; with multipart upload, only the affected part needs to be retried, not the entire file; **throughput** — parts can be uploaded concurrently (from multiple threads or even multiple machines), saturating available upload bandwidth rather than being limited to what one sequential HTTP connection achieves; and **large file support** — S3's single-PUT limit is 5GB; for objects larger than 5GB, multipart upload is the only option (for objects between 100MB and 5GB it's optional but strongly recommended; AWS recommends using it for anything above 100MB).

**Q11. What are the three phases of a multipart upload lifecycle?**
A: **Initiation**: the client calls `CreateMultipartUpload`, specifying the target bucket, key, and any object-level metadata (Content-Type, server-side encryption settings, object tags); S3 returns an `UploadId` — a unique identifier for this multipart upload session, required for all subsequent operations. **Part upload**: the client calls `UploadPart` repeatedly, each time providing the `UploadId`, a part number (1–10,000), and the part's data; S3 returns an `ETag` for each successfully uploaded part, which must be collected by the client for the final step. Parts can be uploaded in any order, in parallel, with any retry logic the client needs for failed parts — each part is independently durable once acknowledged. Part sizes must be at least 5MB for all parts except the last (which can be smaller); the maximum part size is 5GB. **Completion**: the client calls `CompleteMultipartUpload` with the `UploadId` and a manifest of all part numbers and their ETags in order; S3 assembles the final object from the parts, validates the manifest, and makes the assembled object available. Alternatively, `AbortMultipartUpload` cancels the upload and instructs S3 to delete all stored parts for the given `UploadId`.

**Q12. What happens to incomplete multipart uploads, and why is this an important operational concern?**
A: Uploaded parts that are never assembled via `CompleteMultipartUpload` (because the client crashed, the upload was abandoned, or the `AbortMultipartUpload` call was never made) **continue to occupy storage space and accrue storage costs indefinitely** — the parts exist in S3 in an invisible "in-progress" state that doesn't appear in normal bucket listings (only in `ListMultipartUploads` results). In high-churn scenarios (many large uploads started but not always cleanly completed), this "ghost storage" from incomplete multipart uploads can become a meaningful cost over time — it's a common source of unexpected S3 bill increases that teams don't immediately attribute to multipart uploads since the data doesn't appear in their bucket contents. The standard mitigation: create an S3 bucket lifecycle rule with `AbortIncompleteMultipartUpload` configured (e.g., after 7 days), which automatically aborts and cleans up any incomplete multipart upload that has been in progress beyond the specified duration — a simple, one-line lifecycle rule that eliminates ghost storage accumulation entirely.

**Q13. How does client-side multipart upload implementation typically work in practice?**
A: Most AWS SDKs (S3 clients for Python/boto3, Java, Go, JavaScript) provide a high-level transfer manager that handles the multipart upload logic automatically — splitting a file into appropriately-sized parts, managing concurrent part uploads (configurable parallelism), tracking ETags, retrying failed parts, and calling Complete or Abort as appropriate. In practice, explicitly calling the low-level multipart upload APIs directly is necessary mainly for two scenarios: server-side-initiated uploads from a browser (where a presigned URL must be generated per part — Q14), or when implementing custom logic (dynamic part sizing based on file size, custom retry strategies, progress reporting, or resumable uploads that survive process restarts). For backend-to-S3 transfers where the application server has the file, using the SDK's high-level `upload_file` (boto3) or `TransferManager` (Java) is almost always the correct approach, as they handle edge cases (empty files, single-part threshold, concurrency) correctly.

**Q14. How do presigned URLs and multipart uploads combine for browser-direct large file uploads?**
A: Browser-direct large file uploads require generating a presigned URL per part, since the browser must make authenticated requests to S3 but doesn't have AWS credentials. The flow: the client requests an upload initiation from the application server → the server calls `CreateMultipartUpload` and returns the `UploadId` and the total number of expected parts; the client requests presigned PUT URLs for each part from the server → the server generates one presigned `UploadPart` URL per part (each specifying the `UploadId`, the part number, and the bucket/key); the client uploads each part directly from the browser to S3 using the presigned URL, collecting the `ETag` from each response; the client sends the manifest of part numbers and ETags to the server → the server calls `CompleteMultipartUpload`. This pattern keeps all credential handling and key-path decisions on the server while moving all bulk data transfer directly between the browser and S3 — the application server handles only small metadata requests, never the file bytes. Parallelism is controlled by how many parts the client uploads simultaneously (limited by browser connection concurrency limits and upload bandwidth).

**Q15. How should part size be chosen for a multipart upload?**
A: Part size should be chosen based on the total file size, the desired level of parallelism, and the minimum 5MB part constraint: `part_size = max(5MB, ceil(total_size / desired_part_count))`, capped such that the total number of parts doesn't exceed 10,000. Practical guidance: for files under 100MB, a single PUT is usually simpler (no multipart overhead); for 100MB–1GB, 10–50 parts of 10–25MB is reasonable; for files 1GB–10GB, 50–100 parts of 25–100MB; for very large files (>10GB), aim for 100–1,000 parts, balancing the overhead of too many concurrent presigned URL requests (browser-direct case) against the advantage of fine-grained retry granularity. Larger parts mean fewer total network roundtrips (less overhead per byte transferred) but coarser retry granularity (a failure means re-uploading a larger chunk); smaller parts give finer retry granularity and better parallelism but more HTTP request overhead. In practice, most SDK transfer managers default to 8MB parts with dynamic adjustment based on file size, which is a sensible starting point.

## Section 4: Access Control

**Q16. What are the different layers of S3 access control, and how do they interact?**
A: S3 access control has several distinct layers that all apply simultaneously: **IAM policies** (attached to IAM users, roles, or groups) — control what S3 actions those identities are allowed to perform, evaluated by AWS's authorization engine; **bucket policies** (resource-based policies attached to the bucket itself) — control what any identity (including cross-account identities and public access) can do to that bucket and its objects, expressed in the same policy JSON as IAM policies but evaluated from the resource's perspective; **S3 Block Public Access settings** — four account-level or bucket-level settings that can override and override bucket policies or ACLs that would otherwise allow public access, providing a reliable public-access safeguard even if a misconfigured policy or ACL would otherwise permit it; and **Object ACLs** (largely deprecated in modern S3 usage) — per-object access control list entries, now generally disabled in favor of bucket policies (AWS recommends disabling ACLs for new workloads). A request succeeds only if it's explicitly allowed and not explicitly denied by any applicable layer — the evaluation logic is "if Block Public Access says no, the request is denied regardless of bucket policy or ACL."

**Q17. What is the principal of least privilege as applied to S3 access, and what are common mistakes that violate it?**
A: Least privilege applied to S3 means: IAM roles and policies grant exactly the S3 actions (`s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`) on exactly the resources (specific bucket ARNs, specific key prefixes via ARN wildcards) that a given service or function actually needs, and nothing more. Common violations: granting `s3:*` on `*` (all S3 actions on all buckets) to a service that only needs to read from one specific bucket; using a wildcard key prefix (`arn:aws:s3:::mybucket/*`) for a service that should only read from `arn:aws:s3:::mybucket/uploads/service-a/*`; granting `s3:DeleteObject` to a service that should only read and write, not delete; and generating presigned URLs using a long-lived IAM user's credentials rather than a short-lived IAM role's credentials, meaning the presigned URL's signing identity persists indefinitely (a leaked URL's underlying credential doesn't naturally expire on the IAM user's rotation schedule the way an IAM role's temporary credential does).

## Section 5: Performance Patterns

**Q18. What is the S3 request rate limit, and how does prefix distribution affect it?**
A: S3 automatically scales to handle very high request rates per prefix — S3 partitions storage based on key prefixes, and each partition supports up to 3,500 PUT/COPY/POST/DELETE requests per second and 5,500 GET/HEAD requests per second. In early S3 (pre-2018), achieving high throughput required randomizing key prefixes (adding a hash prefix to distribute objects across S3 partitions), because S3 partitioned based on lexicographic key ordering and sequential prefixes (like timestamp-prefixed keys) could concentrate traffic onto one partition. Since 2018, S3 automatically partitions at higher throughput thresholds and handles prefix distribution more intelligently — sequential/timestamp prefixes are no longer a severe throughput bottleneck for most workloads. However, for extremely high request rates (tens of thousands of requests per second to a single prefix), having multiple distinct prefixes still helps S3 distribute the load, since each prefix can independently scale its partition throughput.

**Q19. What is S3 Transfer Acceleration, and when is it worth the additional cost?**
A: S3 Transfer Acceleration routes upload/download traffic through AWS's globally distributed CloudFront edge network — a client uploading to an S3 bucket with Transfer Acceleration enabled uploads to the nearest CloudFront edge point of presence (PoP), which then transfers the data to S3 over AWS's optimized backbone network rather than the public internet for the remaining journey. This is beneficial when: clients are geographically distant from the S3 bucket's region (an S3 bucket in us-east-1 accessed by users in Asia-Pacific benefits from Transfer Acceleration routing through a nearby PoP); the primary bottleneck is public internet latency and packet loss over long-distance connections (which AWS's backbone avoids); and the data being transferred is large enough that the routing optimization outweighs the additional cost per GB. It's not worth the cost for: clients geographically close to the bucket's region (minimal routing benefit); small files (overhead amortization is minimal); or workloads that are already using CloudFront for distribution (CloudFront to S3 is already on the AWS backbone).

**Q20. How does S3 integrate with CDN for serving objects at scale, and what's the correct architecture?**
A: S3 is commonly used as a CDN origin — CloudFront (or another CDN) caches S3 objects at edge locations globally, serving the vast majority of requests from edge cache hits without reaching S3 at all. The correct architecture for public or semi-public content: CloudFront distribution with S3 as the origin, configured via **Origin Access Control** (OAC, the modern replacement for the older Origin Access Identity / OAI) — this allows the S3 bucket's bucket policy to restrict `s3:GetObject` to CloudFront's service principal only, so objects are not directly publicly accessible from S3's URLs, but only via CloudFront. This prevents cache bypass attacks (users directly hitting S3 URLs to bypass CloudFront, avoiding caching and potentially bypassing geo-restriction or security headers), controls egress costs (S3-to-CloudFront egress within the same region is free; S3 direct-to-client egress is charged), and provides CDN caching, edge compression, and global latency benefits. Cache invalidation after an object update is triggered by calling `CloudFront.CreateInvalidation` for specific paths.

## Section 6: Storage Classes and Lifecycle

**Q21. What are S3 storage classes, and how should they inform lifecycle design?**
A: S3 offers several storage classes with different durability, availability, retrieval time, and cost trade-offs: **S3 Standard** — default; high availability, low latency, highest per-GB storage cost; for frequently-accessed objects. **S3 Standard-IA** (Infrequent Access) — same durability and availability as Standard, lower per-GB storage cost, per-retrieval fee, 30-day minimum storage duration; for data accessed less than once a month. **S3 One Zone-IA** — same as Standard-IA but stored in only one AZ; lower cost but reduced durability if the AZ fails; appropriate for easily-reconstructable data. **S3 Glacier Instant Retrieval** — lowest cost for data accessed once a quarter, retrieval within milliseconds; **S3 Glacier Flexible Retrieval** — retrieval in minutes to hours, for archival data; **S3 Glacier Deep Archive** — cheapest per-GB; 12-hour retrieval; for long-term compliance archives accessed at most once a year. **S3 Intelligent-Tiering** — automatically moves objects between access tiers based on actual access patterns, for workloads with unknown or changing access patterns, at a per-object monitoring fee. Lifecycle policies automate transitions between classes based on age — a lifecycle rule might move objects to Standard-IA after 30 days, Glacier Instant Retrieval after 90 days, and Glacier Deep Archive after 365 days, dramatically reducing long-term storage costs for data that's initially active but progressively less accessed.

**Q22. What is S3 versioning, and when is it important?**
A: Versioning preserves every version of every object in a bucket — each PUT creates a new version rather than overwriting the previous one, and DELETE markers are added rather than permanent deletion. This enables: **accidental deletion recovery** (the most common use case — a deleted object is not truly gone; restoring it means deleting the delete marker); **overwrite recovery** (if application code overwrites an object with incorrect data, previous versions are retrievable); and **audit trail** (a complete history of all versions of every object, with timestamps). The cost: storage for every version of every object accumulates until lifecycle rules expire old versions. For a bucket where objects are frequently overwritten (a config file updated many times per day), versioning without lifecycle rules expiring old versions creates unbounded storage growth for old versions. Versioning interacts critically with lifecycle rules: lifecycle rules can be scoped to non-current versions specifically, allowing "keep the current version forever; expire non-current versions after 30 days" — the standard pattern for versioned buckets that don't want to pay for indefinite version storage.

## Section 7: Security Considerations

**Q23. What are the encryption options for S3, and what does each protect against?**
A: **In-transit encryption**: all S3 APIs are available over HTTPS, and bucket policies can enforce `aws:SecureTransport: true` to deny any unencrypted HTTP requests — protects data against network interception between client and S3. **Server-side encryption (SSE)**: S3 encrypts the data at rest, transparently on the server side: **SSE-S3** uses S3-managed AES-256 keys (enabled by default since January 2023 on all new objects); **SSE-KMS** uses AWS KMS customer-managed keys — provides key rotation control, per-key usage audit logging via CloudTrail, and the ability to revoke access to all objects encrypted with a key by disabling that KMS key; **SSE-C** uses customer-provided keys (the client sends the key with each request; S3 never stores the key) — maximum key control, but the client must manage and provide the key on every single request, adding operational complexity. **Client-side encryption**: the client encrypts data before sending to S3 — S3 stores and returns ciphertext, with no server-side knowledge of plaintext; appropriate for most stringent data-sovereignty requirements. SSE-KMS is the most common production choice for sensitive data — it provides meaningful key control and auditability with minimal operational overhead compared to client-side or SSE-C encryption.

**Q24. What is an S3 Access Log, and what should be monitored from it?**
A: S3 server access logging records one log entry per request to a bucket, written to a target logging bucket — each entry includes the bucket name, request timestamp, requester identity (IAM ARN or anonymous), operation type, object key, response status, bytes transferred, and error codes. What to monitor: **4xx error rates per key** — a spike in 403 (Access Denied) on a specific key prefix can indicate a misconfigured policy, an expired presigned URL, or potentially a probing attack; **unexpected requester identities** — any request from an identity or IP not expected to access the bucket could indicate a leaked credential or presigned URL; **large volume of GET requests on non-existent keys** (404 responses) — can indicate application misconfiguration, CDN misconfiguration, or enumeration attempts; and **data transfer volumes** — a sudden spike in egress (GET requests transferring large amounts of data) can indicate a data exfiltration event or a runaway process. Access logs have delivery delay (best-effort, typically minutes) and are not a substitute for CloudTrail for audit purposes — CloudTrail records S3 management API calls and, with data events enabled, object-level API calls with full request context and IAM identity details.

## Section 8: Operational Considerations

**Q25. What are the most common S3 cost drivers, and how are they managed?**
A: Storage costs (per-GB per month, varying by storage class) and request costs (per-PUT, per-GET, per-LIST) are the primary drivers, with egress costs (data transferred out of S3 to the internet or to different AWS regions) often being larger than storage costs for high-traffic applications. Management strategies: lifecycle policies transitioning to cheaper storage classes as data ages (Q21); S3 Intelligent-Tiering for variable-access data where manual lifecycle design is difficult; serving via CloudFront (S3-to-CloudFront egress within the same region is free, while direct S3-to-internet egress is charged, so CloudFront CDN reduces egress cost for frequently-accessed public content); `AbortIncompleteMultipartUpload` lifecycle rules eliminating ghost storage from abandoned multipart uploads (Q12); and S3 Storage Lens or S3 Cost Explorer analysis identifying unexpectedly expensive buckets or prefixes. A common mistake: LIST operations charged per 1,000 requests — a tight polling loop calling `ListObjects` on a large prefix thousands of times per minute generates meaningful API cost alongside the latency overhead, better replaced with S3 Event Notifications to Kafka/SQS or S3 Inventory for bulk listing.

**Q26. What are S3 Event Notifications, and how do they integrate with a processing pipeline?**
A: S3 Event Notifications publish messages to SNS, SQS, or Lambda (and, via EventBridge, to a wide range of targets) when specific events occur on a bucket — object creation (`s3:ObjectCreated:*`), deletion, replication events, restore completion. This enables **event-driven processing pipelines**: a user uploads a file via presigned PUT → S3 publishes an `ObjectCreated` event to SQS → a Lambda or consumer service reads from SQS and processes the uploaded file (resizing an image, extracting metadata, running a virus scan, triggering a database record creation) — without any polling loop. The event notification contains the bucket name, object key, size, and ETag of the newly created object. Important caveats: event notifications are delivered **at least once** (not exactly once), so processing logic should be idempotent (processing the same event twice should not produce duplicate side effects); there's a small delivery delay (typically seconds); and notifications are not delivered for objects created by S3 replication or lifecycle transitions — only for direct API operations.

**Q27. What is S3 Object Lock, and when is it required?**
A: S3 Object Lock implements WORM (Write Once Read Many) semantics — once an object is locked, it cannot be overwritten or deleted for the duration of the configured retention period, regardless of what IAM permissions the caller has (the lock is enforced at the S3 service level, not by access control policies). Two modes: **Governance mode** — objects are protected from modification/deletion unless the caller has the `s3:BypassGovernanceRetention` permission (allows privileged administrators to override); **Compliance mode** — objects cannot be modified or deleted by anyone, including the root account, for the retention period — no override is possible. Object Lock is required for: regulatory compliance mandating tamper-proof data retention (SEC Rule 17a-4, HIPAA, FINRA); healthcare record retention; financial record immutability; and audit log integrity guarantees. It must be enabled at bucket creation time (cannot be enabled on an existing bucket without creating a new one), and versioning is automatically enabled when Object Lock is enabled.

## Section 9: Scenario-Based Questions

**Q28. "Your application lets users upload profile pictures. Currently, users POST the file to your API server, which uploads it to S3. As user growth increases, your API servers are becoming a bandwidth bottleneck. How would you redesign this?"**
A: Redesign to browser-direct upload using presigned PUT URLs (Q4, Q7). The flow: (1) the client sends a small metadata request to the API server (`POST /api/upload/request` with filename, content-type, file size); (2) the API server validates the request (user is authenticated, file type is acceptable, size is within limits), generates a UUID-based key (`profiles/{user_id}/{uuid}.jpg`), calls AWS SDK to generate a presigned PUT URL for that key with a short expiry (5–15 minutes) and content-type constraint (`image/jpeg` or `image/png` only), returns the presigned URL and the key to the client; (3) the client uploads the file bytes directly to S3 using the presigned URL via a standard HTTP PUT (no AWS credentials needed by the client); (4) S3 sends an Event Notification (Q26) to SQS on `ObjectCreated`, triggering a Lambda that validates the image (virus scan, dimension check, content moderation), generates thumbnails, and updates the user's profile record in the database with the S3 key. The API server's role is reduced to tiny metadata requests and presigned URL generation — it never touches the file bytes.

**Q29. "A data pipeline uploads 50GB log files to S3 daily. Uploads occasionally fail midway and must restart from scratch, which is taking hours. How would you fix this?"**
A: This is a multipart upload problem (Q10–11): the pipeline is likely using a single-PUT upload for the entire 50GB file, which fails completely on any interruption. Fix: use the SDK's transfer manager or implement explicit multipart upload with resumability. For a pipeline that may be interrupted and restarted (process restart, network failure): on upload start, call `CreateMultipartUpload` and **persist the `UploadId` and already-completed part ETags to durable storage** (a database record, a local file) before beginning part uploads; on each successful `UploadPart`, persist that part number's ETag; if the process is interrupted and restarted, check for an existing persisted `UploadId` for this file, call `ListParts` to see which parts S3 already has, and resume uploading only the missing parts — then call `CompleteMultipartUpload` once all parts are present. With 50GB split into 100MB parts (500 parts), a failure at the 49GB mark only requires re-uploading the last 1GB (10 parts), not the entire file. Add an `AbortIncompleteMultipartUpload` lifecycle rule at 3 days to clean up any uploads that are definitively abandoned rather than just temporarily interrupted.

**Q30. "You're building a video streaming service. Users upload videos (1–20GB each), and these are served to potentially millions of viewers globally. Walk through the storage and delivery architecture."**
A: This requires the full combination of patterns. **Upload**: browser-direct multipart upload via presigned part URLs (Q14) — the client's video file is split into 50–100MB parts client-side, each uploaded to S3 in parallel using presigned `UploadPart` URLs, with progress tracking and retry on the client side. The application server manages the `UploadId`, persists part ETags, and calls `CompleteMultipartUpload` once the client signals completion. **Post-upload processing**: S3 Event Notification triggers a Lambda or processing job that hands the raw uploaded video key to a transcoding pipeline (AWS Elemental MediaConvert, or a self-hosted FFmpeg fleet) — producing multiple bitrate/resolution variants (adaptive bitrate streaming, HLS or DASH format) stored back in S3 under a structured key prefix. **Delivery**: CloudFront distribution with S3 as origin via OAC (Q20) — CloudFront serves the HLS/DASH manifests and video segments from edge caches globally, with only cache misses hitting S3. For private/paywalled videos: CloudFront signed URLs or cookies (Q9) rather than presigned S3 URLs, so delivery benefits from CDN caching while access is still controlled. **Storage tiers**: fresh uploads in Standard; after 90 days (past the main view window for most content), transition to Standard-IA; after 365 days, Glacier Instant Retrieval for the original raw upload (keep it for re-transcoding if needed), Glacier Deep Archive for very old originals.

**Q31. "A security audit flags that your S3 buckets containing customer data have no encryption enforcement, some objects are accessible via HTTP (not HTTPS), and several presigned URLs in your codebase have 7-day expiry. What would you address and how?"**
A: Address each systematically: **Encryption at rest**: enable default bucket encryption (SSE-KMS with a customer-managed KMS key for customer data — provides key usage audit logs via CloudTrail and the ability to revoke access by disabling the key); apply a bucket policy condition `{"StringNotEquals": {"s3:x-amz-server-side-encryption": "aws:kms"}}` to deny any PutObject that doesn't specify SSE-KMS, preventing any unencrypted writes even from callers that don't respect the default. **HTTPS enforcement**: add a bucket policy statement denying requests where `aws:SecureTransport` is `false` — any client using HTTP instead of HTTPS is denied entirely. **Presigned URL expiry**: audit the codebase for all URL generation sites and replace 7-day expiry with the shortest duration that fits the actual use case — download URLs generated for the current user session: 15–30 minutes; upload URLs: 5–15 minutes; email links for later retrieval: 1–4 hours maximum, not days. Review whether any cases actually need long expiry or whether the generating endpoint should be called again for a fresh URL when needed. Additionally: enable S3 Block Public Access at the account level (not just per-bucket), ensure all buckets have access logging enabled to a separate audit log bucket, and review IAM policies for any overly-broad S3 permissions.

**Q32. "Your application serves private user documents from S3. On every page load that shows a document, your server fetches the document from S3 and streams it to the client. Users report slow document loads. What's wrong and how do you fix it?"**
A: The server is acting as an unnecessary data proxy — fetching from S3 and then re-streaming the same bytes to the client, doubling the data transfer and adding server-side bandwidth consumption and latency (S3 → server → client, two sequential transfers, instead of S3 → client, one direct transfer). The fix is presigned GET URLs (Q4, Q7): instead of fetching the document itself, the server generates a short-lived presigned GET URL for the specific document key, verifies the user is authorized to access it, and returns the URL to the client; the client then fetches the document directly from S3 (or CloudFront, if CDN is appropriate for this content) without any server involvement in the data transfer. For private documents that shouldn't be served publicly but would benefit from CDN caching (the same document accessed by many users), CloudFront signed URLs with OAC provide the same direct-to-CDN serving pattern while maintaining access control. The server's role reduces from bandwidth proxy to authorization check and URL generator — a computation-only operation with no data transfer overhead.
