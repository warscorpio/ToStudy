# Data Warehouses (Redshift, BigQuery) vs OLTP Databases — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the core distinction between OLTP and OLAP workloads, and why does it matter for database choice?**
A: OLTP (Online Transaction Processing) describes the workload of running an application's day-to-day operations — short, frequent, highly concurrent transactions that read or modify a small number of rows (fetch a user's order, update an inventory count, insert a payment record). OLAP (Online Analytical Processing) describes the workload of analyzing accumulated historical data — infrequent but complex queries that scan large portions of a dataset to compute aggregations, trends, and cross-dimensional summaries (total revenue by product category per quarter, month-over-month user retention by acquisition channel). These two workload profiles have directly opposing optimization requirements: OLTP needs low per-transaction latency, high concurrency of small operations, and efficient single-row access; OLAP needs high throughput on massive sequential scans, efficient aggregation over billions of rows, and the ability to answer ad-hoc analytical questions that touch most of a dataset. Optimizing a single database system for both simultaneously produces a system that excels at neither — which is why OLTP databases and data warehouses exist as distinct, purpose-built system categories.

**Q2. What is a data warehouse, specifically?**
A: A data warehouse is a database system purpose-built for OLAP workloads — designed to ingest and store large volumes of historical data from multiple operational (OLTP) source systems, and to serve complex analytical queries over that accumulated data with high throughput and acceptable query latency at scale. Key distinguishing characteristics: columnar storage (data organized by column rather than by row, enabling efficient aggregation over a few columns of many rows without reading irrelevant columns); MPP (Massively Parallel Processing) architecture (queries are automatically distributed across many processing nodes, with each node handling a subset of the data in parallel, then results are combined); bulk-load-optimized writes (data arrives in large, periodic batches via ETL/ELT processes rather than via thousands of concurrent single-row inserts); and analytical query semantics optimized for reads (complex joins, window functions, multi-level aggregations) rather than transactional guarantees.

**Q3. Why does columnar storage specifically make data warehouses more efficient for analytical queries?**
A: In a row-oriented database (the typical OLTP layout), all columns for one row are stored contiguously on disk — fetching a row means one sequential read, ideal for the "fetch all data for user X" access pattern. In a columnar database, all values for one column are stored contiguously — fetching a column across all rows means one sequential scan of that column's data, skipping all other columns entirely. For an analytical query like `SELECT region, SUM(revenue) FROM orders GROUP BY region`, a columnar database reads only the `region` and `revenue` columns' data, skipping `customer_id`, `product_id`, `shipping_address`, and every other column. On a table with 100 columns and 10 billion rows, this might mean reading 2% of the stored data instead of 100%. Columnar storage also enables dramatically better compression per column (a column containing an integer status code with 5 possible values compresses far better than a mixed row containing all column types interleaved), which further reduces I/O. These two effects — column pruning and compression — together make columnar storage the single most important architectural decision in a data warehouse.

## Section 2: OLTP Databases In Depth

**Q4. What storage and indexing characteristics make OLTP databases well-suited to transactional workloads?**
A: OLTP databases use **row-oriented storage** (a natural fit for "fetch or update this specific row" access patterns), **B-tree indexes** (enabling O(log n) point lookups and range scans by specific column values — finding the one row with `user_id = 12345` in a billion-row table takes milliseconds), and **MVCC (Multiversion Concurrency Control)** (maintaining multiple versions of rows in flight to allow concurrent readers and writers to coexist without locking each other, enabling the high concurrency typical of application workloads). They enforce **ACID transactional semantics** (atomicity, consistency, isolation, durability — critical for operational data integrity, as discussed in the SQL vs NoSQL guide). The overall design is optimized for the worst case of OLAP (many concurrent short transactions on individual rows) — random access patterns where any row might be needed at any moment, and where data modifications happen continuously throughout the day.

**Q5. What happens when you run a heavy analytical query directly against an OLTP database, and why is this a problem?**
A: A heavy analytical query (full-table scans, large aggregations, complex multi-table joins over millions of rows) competes directly with OLTP transactions for the same resources — CPU, memory, disk I/O, and lock contention. The analytical query typically causes: **lock contention** (long-running reads can block or be blocked by concurrent writes, depending on the isolation level and lock model); **I/O saturation** (scanning millions of rows reads far more data from disk than any individual OLTP transaction, potentially filling the buffer pool and evicting cached data that OLTP transactions need, degrading their latency); **query planner and executor resource exhaustion** (a complex aggregation may consume all available sort/hash memory and spill to disk, dominating the system's resources for its duration). The combined effect is that analytical queries running against the production OLTP database degrade the application's transaction latency during the query's execution — which is exactly why separating analytical workloads onto a dedicated data warehouse is the standard architectural pattern.

## Section 3: Redshift In Depth

**Q6. What is Redshift's architecture, and how does MPP work in practice?**
A: Redshift is a cluster-based MPP columnar data warehouse built on PostgreSQL. A Redshift cluster consists of a **leader node** (receives client queries, parses them, develops query execution plans, and coordinates result assembly) and one or more **compute nodes** (each holding a slice of the data and executing the portion of each query plan that applies to their local data). When a query arrives, the leader compiles an optimized execution plan and distributes it to all compute nodes simultaneously; each node executes the plan against its local data slice in parallel, streams partial results back to the leader, and the leader combines them into the final result. The parallelism scales with the number of nodes — a query that scans 1TB of data takes roughly the same wall-clock time regardless of whether the 1TB is distributed across 4 nodes or 16 nodes (assuming the query is I/O-bound and communication overhead is minimal), because each node handles proportionally less data. This is why scaling a Redshift cluster adds both storage capacity and query throughput simultaneously.

**Q7. What is a distribution key in Redshift, and why does it critically affect query performance?**
A: Redshift distributes each table's rows across compute nodes based on a **distribution style**: `KEY` (rows with the same value of the chosen distribution key column are placed on the same node — e.g., distributing an orders table by `customer_id` puts all orders for the same customer on the same node); `EVEN` (round-robin distribution, equal rows per node regardless of column values); or `ALL` (every node receives a full copy of the table — appropriate only for small dimension tables joined frequently). The choice of distribution key critically affects whether **co-located joins** are possible: if two tables being joined have the same distribution key and that key is the join column, the join can happen entirely on each node locally (no data movement required); if the distribution keys don't align with the join condition, Redshift must **redistribute** one table's rows across nodes during query execution — a broadcast or hash redistribute operation that transfers data across the network between nodes, adding significant latency to the query. Choosing distribution keys to co-locate the most common and expensive joins is the single highest-impact performance decision in Redshift schema design.

**Q8. What are sort keys in Redshift, and how do they accelerate analytical queries?**
A: Sort keys define the physical on-disk sort order of a table's rows within each node's storage slice. When data is stored in sort-key order, Redshift can use **zone maps** — per-block metadata tracking the minimum and maximum value of the sort key column in each 1MB disk block — to skip entire blocks whose range can't contain the queried values. For a time-series table sorted by `event_timestamp`, a query filtering `WHERE event_timestamp > '2024-01-01'` skips all blocks whose max timestamp is before that date — potentially scanning only a small fraction of the table for recent-data queries. Sort keys are most effective when: the most common query filter is on the sort key column (typically timestamp or date for time-series); and data is loaded in sort-key order (out-of-order loads require periodic `VACUUM SORT` operations to re-sort). **Compound sort keys** (ordered list of columns — primary, secondary) extend this to multi-column filter combinations; **interleaved sort keys** (weight all columns equally for filtering) are better for tables queried with many different filter combinations but have higher maintenance overhead.

**Q9. What is Redshift Spectrum, and what architectural pattern does it enable?**
A: Redshift Spectrum extends Redshift's query engine to directly query data stored in S3 (in columnar formats like Parquet or ORC, or in CSV/JSON) without first loading it into Redshift — the query is partially executed on Redshift compute nodes, partially on Spectrum's own separate, serverless compute layer that scales independently. This enables a **hot/warm/cold data tiering pattern**: recent, frequently-queried data lives in Redshift tables (fast, optimized columnar storage on compute node local disk or managed storage); older, less frequently-queried historical data lives in S3 as Parquet (cheap, unlimited storage); Spectrum makes both tiers queryable together via standard SQL, with joins and aggregations spanning both. The cost benefit: S3 storage at ~$0.023/GB/month vs Redshift managed storage at $0.024/GB/month, with Spectrum billing per terabyte of data scanned from S3 rather than paying for dedicated compute to hold cold data. The architectural pattern mirrors the time-series database tiered storage pattern discussed in the TSDB guide — hot data in expensive, fast storage; cold data in cheap, slow storage; queries spanning both transparently.

## Section 4: BigQuery In Depth

**Q10. What is BigQuery's architecture, and how does it differ fundamentally from Redshift's cluster model?**
A: BigQuery is a **serverless**, fully-managed analytical database — there is no cluster to size, no nodes to configure, no capacity to reserve (in the default on-demand pricing model). Under the hood, BigQuery separates storage and compute entirely: data is stored in Google's Colossus distributed file system in Dremel's columnar format (Capacitor); compute is provided by Dremel, a massively parallel query engine whose workers are dynamically allocated from a shared, enormous pool of Google's infrastructure for each query, then released when the query completes. A query that needs to scan 10TB gets a proportionally large allocation of compute slots for its duration; a query that scans 100MB gets a small allocation — dynamically and automatically. This means BigQuery's cost model and operational model are fundamentally different from Redshift: there's no cluster to provision or right-size, no idle capacity being paid for, and query throughput scales essentially without bound (limited by available slot quota). The trade-off: less control over query latency for complex, concurrent workloads and more cost unpredictability with on-demand pricing (a runaway query or a data modeler scanning a multi-terabyte table accidentally can generate a large unexpected bill).

**Q11. What are BigQuery's partitioning and clustering features, and how do they function analogously to Redshift's sort keys?**
A: **Partitioning** divides a BigQuery table into segments based on a time column or an integer range column — each partition's data is physically stored separately, and queries with a filter on the partition column can skip partitions entirely (pruning), scanning only the relevant segment of the data. BigQuery requires the partition column to be included in the `WHERE` clause for partition pruning to activate; a query with no partition filter scans the entire table. **Clustering** physically sorts the data within each partition by up to four specified columns — rows with similar values for those columns are stored contiguously, and BigQuery uses block-level metadata to skip blocks that can't satisfy the clustering column filter. Together, partition pruning and cluster-based block skipping can reduce the bytes scanned by a query by orders of magnitude relative to a full table scan — and since BigQuery's on-demand pricing is based on bytes scanned, these are also direct cost-reduction tools, not just performance optimizations. Partition + cluster design is the most important query-cost-reduction decision in BigQuery schema design.

**Q12. What is the difference between BigQuery's on-demand and capacity pricing models, and when does each make sense?**
A: In **on-demand pricing**, you pay per terabyte of data scanned by each query, with no commitment and no idle cost — ideal for unpredictable, bursty analytical workloads (ad-hoc analysis by data scientists, monthly reports, infrequent heavy queries) where paying only for what's actually used is cost-optimal. In **capacity pricing** (reservations/commitments), you purchase a committed number of **slots** (BigQuery's unit of compute) — a fixed monthly cost regardless of query volume, with additional auto-scaling slots available on demand above the commitment. Capacity pricing is more cost-efficient for **sustained, high-throughput analytical workloads** (BI dashboards refreshed thousands of times per day, heavy ETL pipelines, real-time analytics with high query rates) where the per-query cost of on-demand scanning would exceed the equivalent reserved capacity cost. Many organizations run both: production BI workloads on a capacity reservation for predictable cost, and ad-hoc exploratory querying on on-demand to avoid paying for idle reserved capacity for unpredictable usage.

**Q13. How does BigQuery handle data freshness — what is the difference between streaming inserts and batch loads?**
A: **Batch loads** (via the BigQuery Storage Write API or the older load jobs) are the cost-free, recommended pattern for data that doesn't need real-time freshness — data is written in bulk (via files from GCS, or API batch writes) and becomes immediately available for querying once the load job completes. **Streaming inserts** (via the legacy streaming API) allow individual rows to be inserted in near-real-time (data is queryable within seconds of insertion) but at additional per-row cost and with different durability semantics (streamed rows aren't available in table exports and some table operations until they're moved from the streaming buffer into regular storage, typically within a few minutes to an hour). The modern BigQuery Storage Write API unifies both patterns — it supports both committed (immediately queryable) and pending (batched, more efficient) write modes with strong exactly-once delivery guarantees, at lower cost than the legacy streaming API. The architectural implication: for most ELT pipelines where data freshness of minutes to an hour is acceptable, batch loads via Storage Write API are preferred; real-time streaming into BigQuery is reserved for use cases with a genuine sub-minute freshness requirement.

## Section 5: Redshift vs BigQuery

**Q14. When should you choose Redshift over BigQuery?**
A: Redshift is the stronger choice when: the organization is deeply AWS-native (IAM integration, VPC networking, AWS Glue for ETL, S3 for data lake — a cohesive AWS data stack avoids cross-cloud data egress costs and complexity); the team needs **fine-grained control over query performance** (Redshift's distribution keys, sort keys, and WLM workload management allow expert tuning for specific query patterns that BigQuery handles more opaquely); the workload involves **many concurrent, short-to-medium analytical queries** with strict latency requirements (Redshift's cluster model provides consistent, predictable query latency for common queries when properly configured, while BigQuery's slot-based model can be less consistent at low slot counts); or **Redshift Spectrum's S3 data lake integration** is needed within the AWS ecosystem. Redshift's main operational burden is right-sizing the cluster (too small = slow queries; too large = overpaying for idle capacity) and maintaining distribution and sort keys as query patterns evolve.

**Q15. When should you choose BigQuery over Redshift?**
A: BigQuery is the stronger choice when: the organization is GCP-native or doesn't have a strong cloud-vendor preference; **operational simplicity is a priority** — no cluster to size, no vacuuming, no distribution key design, no WLM configuration; the workload is highly **bursty and unpredictable** (on-demand pricing means idle periods cost nothing, and ad-hoc queries from many data scientists don't require pre-provisioned capacity); **very large-scale queries** are common (BigQuery's serverless compute scales to essentially unlimited parallelism for single queries, making it faster than a fixed-size Redshift cluster for enormous one-off scans); or **geospatial, ML (BigQuery ML), or real-time analytics** capabilities are needed (BigQuery's native support for these is more mature). BigQuery's main operational challenge is cost governance — on-demand query costs can be surprising for teams unfamiliar with bytes-scanned pricing, requiring partitioning, clustering, and query cost controls as discipline.

## Section 6: ETL vs ELT

**Q16. What is the difference between ETL and ELT, and why has ELT become dominant with modern data warehouses?**
A: **ETL (Extract, Transform, Load)** was the traditional pattern: extract data from source systems, transform it (clean, join, reshape) in a separate transformation layer (often a purpose-built ETL server or cluster), and then load the cleaned, pre-structured data into the warehouse. **ELT (Extract, Load, Transform)** inverts the last two steps: extract raw data from source systems, load it into the warehouse in raw or lightly-structured form first, then use the warehouse's own massive computational power to perform transformations via SQL within the warehouse. ELT has become dominant with modern columnar warehouses because their compute is so powerful and cheap that it's more efficient to push transformation work into the warehouse (which has all the raw data co-located with massive parallel compute) than to maintain a separate transformation infrastructure; it also preserves raw data in the warehouse for reprocessing if transformation logic changes, rather than having only the pre-transformed output. Tools like dbt (data build tool) have popularized ELT by enabling SQL-based transformation logic to be version-controlled, tested, and deployed against the warehouse natively.

**Q17. How does Change Data Capture (CDC) work for populating a data warehouse from an OLTP source, and why is it preferable to full table dumps?**
A: CDC captures every row-level change (INSERT, UPDATE, DELETE) from the OLTP source database's transaction log in near-real-time, rather than periodically dumping the entire table. Full table dumps are problematic at scale: a 500GB production table dumped nightly takes significant time and I/O on the source, produces a large intermediate file, and gives the warehouse a full-day-old snapshot rather than fresh data. CDC instead streams only the delta of changes since the last checkpoint — tools like Debezium (reads Postgres WAL, MySQL binlog), Fivetran, Airbyte, or AWS DMS capture these change events and deliver them to the warehouse (or an intermediate Kafka topic that feeds the warehouse), enabling data freshness of minutes rather than hours. The trade-off: CDC is more complex to operate than a simple dump-and-load (requires log retention on the source, managing replication slots in Postgres, handling schema evolution), but the freshness and efficiency benefits justify the complexity for production data pipelines where stale data has real business cost.

## Section 7: Data Modeling for Warehouses

**Q18. What is a star schema, and why is it the standard modeling approach for data warehouses?**
A: A star schema organizes warehouse data into **fact tables** (large, narrow tables containing the measurable events or transactions — orders, pageviews, ad impressions — with a timestamp, numeric measures like revenue or quantity, and foreign keys to dimension tables) and **dimension tables** (smaller, descriptive tables containing the attributes of the entities involved — customers, products, marketing campaigns, geographic regions). The schema "looks like a star" with the fact table at the center and dimension tables radiating outward. It's the standard approach because: analytical queries almost always aggregate facts (sum of revenue, count of orders) while filtering or grouping by dimensions (by region, by product category, by customer segment) — the star schema maps directly to this access pattern; dimension tables are typically small enough to broadcast to all compute nodes (the `ALL` distribution style in Redshift, or simply joining small dimension tables against the large fact table efficiently in BigQuery); and the model is intuitive for analysts writing SQL (join orders to products to get category, join to customers to get segment, sum revenue — straightforward).

**Q19. What is a snowflake schema, and when is it preferred over a star schema?**
A: A snowflake schema further normalizes dimension tables — instead of one flat `products` dimension table with all product attributes (including category, subcategory, brand name, supplier name), these are decomposed into separate related dimension tables (`product`, `category`, `brand`, `supplier`) linked by foreign keys — the schema "snowflakes" out from the fact table rather than being one level deep. Snowflake schemas reduce data redundancy and storage (a brand name stored once in a `brand` table rather than repeated in every product row), and simplify maintaining slowly-changing dimensions. However, queries against a snowflake schema require more joins than a star schema, adding query complexity and sometimes join cost in the warehouse. Modern data warehousing practice generally leans toward **flattened/denormalized dimension tables** (closer to star schema) because storage is cheap in a warehouse context and analytical queries benefit from fewer joins — the normalization rationale that's critical for OLTP (preventing update anomalies in frequently-modified operational data) matters far less in a warehouse where dimension data changes slowly and is loaded via controlled ETL processes.

**Q20. What are slowly changing dimensions (SCDs), and why do they matter for historical accuracy?**
A: A slowly changing dimension is a dimension whose attributes change over time — a customer moves to a new city, a product gets re-categorized, a salesperson changes region. The question is: when analyzing historical sales, should a sale from a year ago when the customer lived in Chicago be attributed to Chicago (the city at time of transaction) or to New York (their current city)? The answer depends on the analysis — revenue by customer's current region vs. revenue by customer's region at time of purchase are both valid but different questions. SCD handling strategies: **Type 1** (overwrite — just update the dimension record to the new value, losing history — simplest, appropriate when history doesn't matter); **Type 2** (add a new dimension record with a validity date range for each change, preserving history — enables "as-of" analysis; each fact row's foreign key points to the specific version of the dimension that was current at that time; most analytically rich but adds rows to dimension tables); **Type 3** (add a `previous_value` column — stores one level of history, simple but only handles one prior state). Type 2 is the most common production choice for attributes where historical accuracy in analysis genuinely matters.

## Section 8: Query Performance Patterns

**Q21. What are materialized views in the warehouse context, and how do they differ from standard views?**
A: A standard view is a saved SQL query that executes against the underlying base tables every time it's queried — no pre-computation, no stored results; it's just a named query definition. A **materialized view** pre-executes the query and stores the result set physically, so queries against the materialized view read the pre-computed result rather than re-executing the underlying aggregation against base tables. In a warehouse context, materialized views are the primary tool for accelerating expensive, frequently-repeated aggregations — a dashboard that queries "daily active users by country for the last 30 days" runs against 30 billion rows and takes minutes without optimization; a materialized view pre-aggregating that query result to the daily-country grain runs in seconds. Both Redshift and BigQuery support materialized views with automatic or scheduled refresh. The trade-off is the same as any cache: the materialized result may lag the underlying data (depending on refresh frequency), and maintaining many materialized views adds storage and refresh compute cost.

**Q22. How does window function usage in warehouse queries differ from OLTP query patterns, and why do warehouses handle them efficiently?**
A: Window functions (RANK(), ROW_NUMBER(), LAG(), LEAD(), cumulative SUM OVER a partition) are analytical operations that compute a value for each row based on a related set of rows (a "window") defined by partition and ordering criteria — e.g., computing each customer's order as a rank within their own lifetime order history, or computing a running total of daily revenue. These are common and natural in analytical SQL but extremely expensive against OLTP databases (they require sorting entire partitions of data, which in a row-oriented database means reading and sorting many full rows). In a columnar warehouse, window functions work with column-projected data (only the relevant columns are materialized), and the MPP architecture distributes the partitioned computation across nodes — each node handles the window function over its local partition of data in parallel. This makes window functions that would be prohibitively expensive in Postgres or MySQL at analytical scale routine and fast in Redshift or BigQuery.

## Section 9: Operational Considerations

**Q23. What is Redshift's VACUUM operation, and why does it matter?**
A: Redshift uses an append-only write model — DELETEs mark rows as deleted without immediately reclaiming their space, and UPDATEs are internally implemented as a DELETE + INSERT. Over time, soft-deleted rows accumulate, consuming storage and polluting columnar blocks that queries must scan through. `VACUUM` reclaims space from deleted rows and, for tables with a sort key, re-sorts unsorted rows that arrived out of order (because data loaded in non-sort-key order sits in an unsorted region, bypassing zone map pruning). `VACUUM DELETE ONLY` is cheaper (just reclaims space); `VACUUM SORT ONLY` (or full VACUUM) also re-sorts, improving future query performance at the cost of significant I/O during the vacuum run. Failing to run VACUUM on heavily-modified tables causes progressive query slowdown (more rows to scan through, increasingly ineffective zone maps) and storage bloat. Modern Redshift (RA3 node types) handles VACUUM more automatically, but on older node types manual VACUUM scheduling was a significant operational concern. The conceptual equivalent of Postgres's AUTOVACUUM, but at warehouse scale.

**Q24. What is workload management (WLM) in Redshift, and why is it important for multi-user environments?**
A: WLM in Redshift controls how concurrent queries are queued and allocated compute resources — configuring which types of queries (large reporting queries, small BI tool queries, ETL loads) run in separate queues with separate memory allocations and concurrency limits. Without WLM configuration, a single long-running heavy query can consume all available cluster memory, causing all other concurrent queries to queue behind it; a burst of many small BI dashboard queries can saturate the cluster's concurrency limit and queue behind slow ETL jobs. WLM configuration defines: **queues** (separate execution lanes for different query types, typically identified by user group or query group label); **concurrency** (maximum parallel queries per queue); **memory allocation** (percentage of cluster memory per queue); and **timeout** (maximum query runtime before automatic cancellation). Concurrency Scaling (a Redshift feature) adds temporary additional cluster capacity automatically when queue wait times exceed a threshold — routing overflow queries to ephemeral additional compute, scaling out concurrency automatically during peak periods.

**Q25. What are the main cost drivers in a data warehouse, and how are they managed?**
A: **Redshift cost drivers**: compute (per-hour cluster cost, dependent on node type and count — the primary cost, running whether or not queries are executing); storage (managed storage billed per GB for RA3 nodes, separate from compute); concurrency scaling (additional compute-hours when scaling out); Spectrum (per TB scanned from S3). Management: right-size the cluster to the sustained query load (not peak load, which is better handled by concurrency scaling); use Redshift Pause/Resume for clusters that have extended idle periods (e.g., a development or reporting cluster not used overnight); audit slow queries and optimize schema (distribution keys, sort keys) to reduce scan volume. **BigQuery cost drivers**: storage (per GB per month, with cheaper long-term storage after 90 days of no modification); compute / bytes scanned (on-demand: per TB scanned; capacity: per slot-hour); streaming inserts (per GB). Management: partitioning and clustering to reduce bytes scanned per query; query cost controls (maximum bytes billed per query, project-level quotas); use the BigQuery cost estimator before running large ad-hoc queries; audit and optimize high-scan queries identified via INFORMATION_SCHEMA query logs.

## Section 10: The OLTP vs Warehouse Decision Framework

**Q26. What are the clearest signals that a query workload belongs in a data warehouse rather than the OLTP database?**
A: The query: scans a large fraction of a large table (more than a few percent of millions of rows); performs multi-level aggregations (GROUP BY with SUM, COUNT, or complex window functions across many rows); joins many large tables to produce a wide analytical result; takes more than a few seconds to execute; or is best expressed with analytical SQL features (window functions, rollup, grouping sets) that OLTP databases handle poorly at scale. The data: is historical (weeks, months, or years of accumulated records) rather than operational (the current state of entities); arrives in bulk from multiple source systems via ETL/ELT rather than via application transactions; and doesn't require the ACID guarantees or row-level locking semantics of a transactional system. The user: is a data analyst, data scientist, or BI tool (not an end-user application making real-time requests); can tolerate some query latency (seconds to minutes) that an application user cannot; and benefits from SQL expressiveness over performance guarantees.

**Q27. What are the signals that data should remain in or be served from the OLTP system rather than the warehouse?**
A: The query: fetches a specific small number of rows by primary key or a selective index (a single user's profile, a specific order by ID); is triggered by a real-time user action that requires a response in milliseconds; runs hundreds or thousands of times per second concurrently; or must see the absolutely latest committed data (zero staleness tolerance). The data: is operational state (current inventory levels, current account balances, active sessions) rather than historical events; is modified continuously by application transactions; requires transactional integrity (reading data that might be concurrently modified, needing isolation guarantees); or needs to be modified and the modification must immediately affect subsequent reads. The user: is an end user or a real-time application expecting sub-100ms response times.

## Section 11: Scenario-Based Questions

**Q28. "Your e-commerce company's data science team runs weekly retention and revenue reports directly against the production Postgres database. These queries take 10–20 minutes, and the engineering team reports degraded application performance during their execution. How would you address this?"**
A: This is the canonical OLTP-vs-warehouse problem (Q5). The immediate mitigation (before a warehouse is set up) is directing analytical queries to a Postgres **read replica** — the replica handles the long-running scans without blocking or competing with OLTP transactions on the primary. This doesn't fully solve the problem (the replica's row-oriented storage still makes these queries slower than necessary, and heavy replica queries can increase replication lag) but removes the direct production impact. The durable solution: implement a data warehouse (Redshift or BigQuery based on cloud provider and scale, per Q14–15). Set up a CDC or nightly ETL pipeline from Postgres to the warehouse, model the data in a star schema (fact tables for orders, events; dimension tables for customers, products), and route all analytical queries to the warehouse. The data science team's queries become faster (columnar storage, MPP) and completely decoupled from production application performance. Establish a data freshness SLA (nightly batch load is often sufficient for weekly reports) and document which queries should run where, preventing analysts from inadvertently connecting to the production database.

**Q29. "BigQuery is ingesting your product events (clicks, page views, purchases) and you notice that a common dashboard query scanning 90 days of event data is scanning 4TB per run, running many times per day, and generating significant cost. How would you reduce the scan cost?"**
A: Apply the two standard BigQuery cost-reduction tools in sequence. First, **partition** the events table on the event `timestamp` column (or `event_date` column) if not already done — the 90-day query can then use partition pruning, scanning only the 90 partitions (days) that are relevant rather than the full table history. If the table has years of history, this alone can reduce scanned bytes to just the 90-day window. Second, **cluster** the partitioned table by the most common filter dimensions in the dashboard query — if the dashboard always filters by `country` and `event_type`, clustering on `(event_type, country)` allows BigQuery to skip blocks within each partition that don't match those filter values. Third, if the dashboard query always computes the same aggregation (daily active users by country by event type), create a **materialized view** at that grain and redirect the dashboard to query the materialized view — dramatically reducing per-query scan to just the pre-aggregated result. Add a **maximum bytes billed** constraint on the dashboard query as a cost circuit breaker, preventing accidental full-table scans if a partition filter is accidentally removed.

**Q30. "You're designing the analytics infrastructure for a SaaS platform from scratch. You need to provide customers with dashboards showing their own usage data, and you need internal BI dashboards for your own product and revenue analytics. How would you structure the data layer?"**
A: Two distinct problems with different requirements — treat them separately. **Internal BI** (product analytics, revenue reporting, cohort analysis): a standard ELT pipeline from your OLTP sources (CDC from Postgres via Debezium → Kafka → BigQuery or Redshift; or Fivetran for managed connectors), with dbt models building a star schema (fact tables for events, subscriptions, payments; dimension tables for customers, plans, accounts), served by a BI tool (Looker, Metabase, Superset). Standard data warehouse architecture. **Customer-facing usage dashboards** (each customer sees only their own data): a data warehouse is generally the wrong tool for this because: customers expect sub-second dashboard response times; a per-customer query against a shared warehouse table scales poorly when thousands of customers simultaneously query their slice of a billion-row events table; and row-level security in a shared warehouse table adds complexity. Better architecture: **pre-aggregate customer usage metrics** (daily/hourly active users, feature usage counts, API call volumes) into summary tables in your OLTP database or a purpose-built fast query layer (ClickHouse for per-tenant aggregated analytics, TimescaleDB for time-series metrics), and serve those pre-aggregated metrics via your application API. The warehouse handles your internal analytics; a pre-aggregated, customer-scoped store handles customer-facing dashboards.

**Q31. "A team proposes building a single 'unified data store' using BigQuery for both operational application queries and analytical queries, arguing that BigQuery is 'fast enough' for both. How would you evaluate this?"**
A: Push back on this proposal with the structural argument (Q1): OLTP and OLAP workloads have opposite optimization requirements, and BigQuery is architecturally an OLAP system. Specific problems with using BigQuery for operational application queries: **latency** — BigQuery's query latency for simple lookups is typically seconds (slot allocation, query planning, distributed execution overhead), while OLTP applications need millisecond response times for user-facing queries; **concurrency model** — BigQuery's slot-based execution model is not designed for thousands of concurrent tiny queries (the overhead of slot allocation and query compilation per request would dominate at OLTP transaction rates); **cost** — bytes-scanned pricing means even a simple `SELECT * FROM users WHERE user_id = 123` scans significant data if users is a large table with many columns (BigQuery's columnar storage helps, but a point lookup is never as efficient as a B-tree index lookup on an OLTP row store); and **transactional semantics** — BigQuery supports DML (INSERT, UPDATE, DELETE) with ACID within single-table operations, but it's not designed as a multi-table transactional system the way Postgres is. The correct architecture is what the rest of this guide describes: Postgres (or equivalent OLTP) for operational application queries, BigQuery (or equivalent) for analytics — each doing what it's designed for.
