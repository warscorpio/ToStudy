# Data Storage in System Design: Column-Oriented vs Row-Oriented Storage — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is row-oriented storage and what is its defining physical characteristic?**
A: In row-oriented (row-store) storage, all columns of a single row are stored contiguously on disk. The physical layout mirrors the logical record: one row's worth of data occupies a contiguous block of bytes before the next row begins. This means reading a full row — retrieving all its columns — is a single sequential read of a compact region of disk or memory. Row stores are also called NSM (N-ary Storage Model) in academic literature. Classic examples: PostgreSQL, MySQL/InnoDB, Oracle, SQL Server — virtually every traditional OLTP relational database, and most document stores like MongoDB.

```
Row-oriented layout on disk (simplified):

[id=1, name="Alice", age=30, salary=90000, dept="Eng"]
[id=2, name="Bob",   age=25, salary=70000, dept="Mkt"]
[id=3, name="Carol", age=35, salary=85000, dept="Eng"]
```

**Q2. What is column-oriented storage and what is its defining physical characteristic?**
A: In column-oriented (column-store) storage, all values of a single column are stored contiguously — one column's worth of data for all rows occupies contiguous disk space, before the next column begins. Reading a single column across all rows is a single sequential scan; reading a different column requires seeking to a completely different region of the file. Column stores are also called DSM (Decomposition Storage Model). Classic examples: Apache Parquet, Apache ORC, Google BigQuery, Amazon Redshift, ClickHouse, Apache Cassandra (partially), DuckDB.

```
Column-oriented layout on disk (same data):

id column:     [1, 2, 3, ...]
name column:   ["Alice", "Bob", "Carol", ...]
age column:    [30, 25, 35, ...]
salary column: [90000, 70000, 85000, ...]
dept column:   ["Eng", "Mkt", "Eng", ...]
```

**Q3. What is the one-sentence mental model that explains when to use each?**
A: Row-oriented storage is optimized for reading and writing entire individual records (OLTP — "give me everything about user 42, and let me update it"); column-oriented storage is optimized for scanning a small number of columns across millions or billions of rows (OLAP — "give me the average salary for everyone in Engineering"). The question "how much of each row do you typically need?" is the primary decision variable.

**Q4. What is OLTP vs OLAP and how does it map to storage model choice?**
A:
- **OLTP (Online Transaction Processing)**: many small, fast, concurrent transactions — each touching few rows but potentially many columns of those rows (read a user's profile, insert an order, update inventory). Latency-sensitive; workload is write-heavy and read-by-key-lookup. Row stores excel here.
- **OLAP (Online Analytical Processing)**: few large, slow queries — each scanning huge numbers of rows but typically only a subset of columns (aggregate sales by region, compute monthly churn rate, find all orders above a threshold). Throughput-sensitive; workload is read-heavy with full-column scans. Column stores excel here.

The mapping is almost deterministic: OLTP → row-store; OLAP → column-store. Most system design interview storage questions reduce to correctly identifying which workload pattern the system has, then deriving the storage choice from that.

## Section 2: Physical I/O and Performance Mechanics

**Q5. Why is column-oriented storage dramatically faster for analytical queries that touch few columns?**
A: Because it only reads the bytes it needs. Consider a table with 100 columns and 1 billion rows where a query needs only 3 columns (`SELECT dept, AVG(salary) FROM employees GROUP BY dept`). In a row store, reading those 3 columns requires scanning all 1 billion complete rows — reading all 100 columns' worth of data per row, discarding 97% of what it reads from disk. In a column store, only the `dept` and `salary` column files are read — roughly 2% of total disk I/O. The saving is proportional to `(columns needed) / (total columns)`: at 3/100 columns, column-store I/O is ~50× less than row-store I/O for the same query. This directly translates to query time: at 100GB/s disk bandwidth, reading 2GB instead of 100GB saves ~1 second of disk I/O — the dominant cost in analytical queries.

**Q6. Why is row-oriented storage faster for point lookups and full-row fetches?**
A: A point lookup (fetching one row by primary key) in a row store is a single read to a contiguous memory region containing all columns — one I/O that returns everything. In a column store, the same query requires N separate reads — one per column — from N different file regions that may not be physically adjacent. The overhead of N seeks (especially on spinning disk) and N separate read operations is far higher than one read in the row-store case. Additionally, row stores pair naturally with B-tree indexes that resolve a primary key directly to the page containing the full row — the entire fetch is the index lookup + one page read. Column stores weren't designed for this access pattern and pay a structural penalty for it.

**Q7. What is I/O amplification and how does it affect each storage model?**
A: I/O amplification is the ratio of actual bytes read from storage to the bytes logically needed by the query. Row stores have very high I/O amplification for column-subset queries (reading all columns when only a few are needed). Column stores have very low I/O amplification for column-subset queries (reading only the needed columns) but high I/O amplification for full-row-assembly queries (reading N separate column segments for one row). The ideal storage model minimizes I/O amplification for the dominant query pattern of the system.

**Q8. How does hardware evolution — specifically SSDs vs HDDs — affect the row vs column tradeoff?**
A: The column-store advantage for analytical queries was particularly strong in the HDD era, where random seeks were expensive (~10ms per seek) and sequential reads were many times faster (seek time dominated). Column-store analytical queries are inherently sequential within each column, while row-store analytical queries mix sequential and random access patterns as they discard irrelevant column data. SSDs reduce (though don't eliminate) the random vs sequential access penalty — modern NVMe SSDs have random I/O performance within ~10× of sequential, versus ~100× for HDDs. This makes the column-store advantage somewhat smaller on SSDs but still significant at scale: reading 2% of total data vs 100% is still a massive difference regardless of storage medium. Additionally, CPU cache effects matter more as I/O speed increases — column-oriented data is denser and more cache-friendly for analytical scans, a CPU-level advantage that doesn't exist for HDDs.

**Q9. What is the role of CPU cache and SIMD in column-store performance?**
A: Column-oriented data enables two CPU-level performance advantages that row-oriented data cannot:
- **Cache locality**: scanning a column means reading a contiguous array of the same data type (e.g., `int64[]` for a salary column). Modern CPUs prefetch sequential memory very efficiently; an L3 cache line loaded during one read is useful for the next several iterations. Row-oriented data interleaves many types in each cache line (a row might contain a string, int, date, float) — the non-target fields consume cache space without contributing to the computation.
- **SIMD (Single Instruction Multiple Data)**: column data of a uniform type can be processed using vectorized CPU instructions (AVX-512 on x86, NEON on ARM) that operate on 256 or 512 bits at once — computing 8 or 16 comparisons or additions in one instruction. Row-oriented data's mixed-type layout prevents this automatic vectorization. ClickHouse, DuckDB, and most modern analytical databases explicitly exploit SIMD for column scan operations, achieving 4-16× throughput improvement over scalar code on the same hardware.

## Section 3: Compression

**Q10. Why do column stores compress dramatically better than row stores?**
A: Compression algorithms exploit redundancy — repeated patterns and similar values. In a column store, all values in a column are the same data type and often semantically similar (e.g., all salaries are in a similar numeric range, all department names repeat a handful of values). This homogeneity gives compression algorithms far more to work with than a row's mixed bag of types and values. Empirical compression ratios:
- Row-store typical compression: 2-4× (general-purpose compression like LZ4 or Snappy on mixed-type rows)
- Column-store typical compression: 5-20× (specialized column encodings on homogeneous data, described in Q11-13)

For a 10TB row-oriented analytical database, columnar storage with good compression might store the same logical data in 1-2TB — a 5-10× storage cost reduction with the added bonus that less data on disk also means less I/O to read it, multiplying the query performance advantage.

**Q11. What is Run Length Encoding (RLE) and why is it particularly effective for columnar data?**
A: RLE replaces consecutive repeated values with a (value, count) pair. For a column with low cardinality (few distinct values) that is physically sorted — e.g., a `status` column that's sorted so all `"active"` rows are grouped together — RLE is extremely effective:

```
Before RLE: ["active", "active", "active", ...(10M times)..., "inactive", "inactive", ...]
After RLE:  [("active", 10000000), ("inactive", 3000000), ("pending", 500000)]
```

Row-store pages intermix rows from different statuses (insertion order), so RLE achieves little. Columnar storage, especially when data is sorted by a key column, makes long runs of identical values very common. Some columnar systems (e.g., Redshift's `DISTKEY`/`SORTKEY`) are explicitly designed to maximize RLE opportunities by physically sorting the data.

**Q12. What is dictionary encoding and why is it ubiquitous in columnar formats?**
A: Dictionary encoding replaces actual values with compact integer codes, with a separate dictionary mapping codes back to values. Highly effective for low-to-medium cardinality string or categorical columns:

```
Department column (raw):   ["Engineering", "Marketing", "Engineering", "Sales", ...]
Dictionary:                {0: "Engineering", 1: "Marketing", 2: "Sales"}
Encoded column:            [0, 1, 0, 2, ...]   ← 1-2 bytes per value instead of 10-15 bytes
```

Benefits: storage reduction (often 5-20× for string columns), faster comparison (integer comparison vs string comparison), and SIMD-friendly encoded values (integers are uniform-width, enabling vectorized operations directly on the encoded data without decoding). Parquet, ORC, and virtually every production columnar format use dictionary encoding for string/categorical columns by default.

**Q13. What is bit-packing and delta encoding in columnar storage?**
A: 
- **Bit-packing**: if the values in a column fit within fewer bits than the standard type width (e.g., an `INT64` column where all values are between 0-255 fits in 8 bits, not 64), store each value in only the required bits — achieving 8× storage reduction over the declared type. Combined with dictionary encoding (where the codes are small integers), bit-packing often achieves very high compression ratios on encoded columns.
- **Delta encoding**: for monotonically-increasing or clustered numeric sequences (timestamps, auto-increment IDs, sorted prices), store the first value and then only the differences (deltas) between consecutive values: `[1001, 1002, 1003, 1005] → [1001, +1, +1, +2]`. Deltas are typically much smaller numbers than the original values, fitting into fewer bits when combined with bit-packing. Parquet uses a combination of delta encoding + bit-packing for integer/timestamp columns, achieving excellent compression on time-series or sorted ID data.

## Section 4: Write Path Mechanics

**Q14. Why do column stores traditionally have slower write performance than row stores?**
A: Writing a single new row to a column store requires updating N separate column files — one write per column, potentially to N different disk locations:

```
Insert row {id:4, name:"Dave", age=28, salary=92000, dept="Eng"}:
Row store:   1 write to a single contiguous page
Column store: 5 separate writes (one per column file/section)
```

Additionally, column stores that maintain data in sorted order (for better RLE compression) may need to re-sort or rebuild segments when new data doesn't arrive in sort order — an expensive operation that row stores typically don't need. The write amplification (ratio of actual bytes written to logical bytes inserted) is much higher in a column store. This is why column stores are generally considered poor fits for high-frequency transactional writes and are primarily used in read-heavy analytical workloads.

**Q15. What is an LSM-tree (Log-Structured Merge-tree) and how do some columnar databases use it to improve write performance?**
A: The LSM-tree is a write-optimized data structure that converts random writes into sequential ones — all writes go to an in-memory buffer (MemTable), which is periodically flushed sequentially to immutable disk segments (SSTables), and segments are periodically compacted and merged in the background. Apache Cassandra and LevelDB/RocksDB use LSM-trees as their primary storage engine. Some analytical databases (e.g., ClickHouse with its MergeTree engine) combine LSM-tree-style sequential write batching with columnar on-disk format: incoming writes accumulate in memory as mini-row-stores, then are flushed to disk as sorted columnar parts and merged in the background. This allows write throughput to approach row-store performance while the on-disk format remains columnar for efficient analytical reads — a write-buffering strategy that amortizes the per-column write overhead.

**Q16. What is the "write-then-read" lifecycle pattern that makes columnar databases viable despite slow writes?**
A: Most analytical data follows a write-once, read-many lifecycle: data is bulk-loaded (ingested in large batches from ETL pipelines, Kafka consumers, or database exports), persisted durably, and then queried many times over hours, days, or months. In this pattern, the higher write cost of a columnar format is acceptable because: (1) writes are batched (not transactional one-at-a-time), amortizing the per-column overhead; (2) reads vastly outnumber writes in volume; (3) the cumulative read latency saved by columnar format over the data's lifetime far exceeds the one-time write cost penalty. Data warehouses, analytics engines, and ML training data pipelines almost universally follow this pattern — which is why columnar formats (Parquet, ORC) have become the default for all of these use cases.

## Section 5: Columnar File Formats

**Q17. What is Apache Parquet and how is it physically structured?**
A: Parquet is the dominant open-source columnar file format, designed for HDFS and cloud object storage (S3, GCS, ADLS). Physical structure:

```
Parquet File:
├── Row Group 1 (e.g., 128MB of rows)
│   ├── Column Chunk: column A  [compressed column data + metadata]
│   ├── Column Chunk: column B
│   └── Column Chunk: column C
├── Row Group 2
│   ├── Column Chunk: column A
│   └── ...
└── File Footer (schema, row group metadata, column statistics)
```

A **row group** is a horizontal partition of the data (a subset of rows) — all column chunks within one row group store data for the same set of rows. This hybrid structure provides two benefits: within a row group, data is column-oriented (sequential column scans within a row group are efficient); row groups enable coarse-grained row filtering (the footer contains min/max statistics per column chunk per row group, allowing entire row groups to be skipped if a filter can't match any row in that group). Row group size (typically 128MB-1GB) is the primary tuning parameter — larger groups improve compression and columnar scan efficiency; smaller groups improve row-filtering granularity and parallelism.

**Q18. What is Apache ORC (Optimized Row Columnar) and how does it differ from Parquet?**
A: ORC is the other major columnar format, developed originally at Hortonworks for Apache Hive, with strong support from the Hadoop/Hive/Spark ecosystem. Key structural differences from Parquet:

| Dimension | Parquet | ORC |
|---|---|---|
| Primary ecosystem | Spark, Presto/Trino, Pandas/Arrow, Iceberg | Hive, HBase, older Hadoop ecosystem |
| Stripe vs Row Group | Row groups (horizontal) + column chunks | Stripes (horizontal) + streams (column data within stripe) |
| Compression | Column-level (Snappy, GZIP, Zstd per column) | Stripe-level |
| Nested data support | First-class (Dremel encoding for nested/repeated) | Supported but less rich |
| Predicate pushdown metadata | Row group/column chunk min/max | Stripe-level min/max + row index (fine-grained every 10k rows) |
| ACID transactions | Not natively (Hudi/Iceberg adds this) | Native (via Hive ORC ACID) |

In practice, Parquet is the dominant format for new system designs — especially with cloud-native services (BigQuery natively reads Parquet, Snowflake uses Parquet internally, dbt outputs Parquet). ORC remains relevant in legacy Hive-heavy environments.

**Q19. What are "row groups" in Parquet and why does row group size matter for query performance?**
A: Row groups are the unit of parallelism and the unit of predicate filtering in Parquet. Each row group is read independently — a query engine can distribute row groups across workers for parallel processing. Row group size affects: (1) **filtering granularity**: the footer contains min/max statistics per column per row group — a query `WHERE date > '2024-01-01'` can skip entire row groups whose max date < '2024-01-01' without reading them; smaller row groups mean finer-grained skipping but more metadata overhead; (2) **compression efficiency**: larger row groups give the compression algorithm more data to find patterns in (especially for RLE and dictionary encoding), achieving better ratios; (3) **parallelism**: with a 512MB file containing two 256MB row groups, max parallelism is 2 workers; with eight 64MB row groups, max parallelism is 8. The typical production choice: 128MB-512MB row groups for batch analytics, smaller (16-64MB) for interactive queries requiring low latency.

## Section 6: Columnar Databases in Production

**Q20. How does Google BigQuery implement columnar storage, and what makes it architecturally distinctive?**
A: BigQuery uses a proprietary columnar format called Capacitor (not Parquet, though it can read Parquet). Architectural distinctives: (1) **storage-compute separation**: data is stored in Colossus (Google's distributed file system) completely independently of the compute nodes that execute queries — allowing near-infinite scaling of each independently; (2) **serverless execution**: no cluster to provision or size; BigQuery auto-allocates workers per query based on data volume; (3) **Dremel execution model**: queries are decomposed into a tree of workers, each processing a column chunk from one or more row groups, results aggregated up the tree; (4) **automatic partitioning and clustering**: tables can be partitioned by date/timestamp column (queries on a date range skip irrelevant partitions entirely) and clustered by up to 4 columns (data within each partition is physically sorted by the clustering columns, maximizing RLE/min-max filtering effectiveness).

**Q21. How does Amazon Redshift implement columnar storage, and what is its "distribution key" concept?**
A: Redshift is a PostgreSQL-derived, fully managed columnar MPP (Massively Parallel Processing) data warehouse. Each table is stored column-by-column on each node, with each column compressed using the most effective encoding for its data distribution (LZO, Zstd, AZ64, RLE, Delta, or Dictionary — selected automatically by `ANALYZE COMPRESSION` or manually set per column). The **distribution key** (`DISTKEY`) determines how rows are distributed across cluster nodes: all rows with the same `DISTKEY` value go to the same node. Choosing the right `DISTKEY` is critical for join performance — if two frequently-joined tables share a `DISTKEY` on the join column, the joined rows co-reside on the same node and the join requires no cross-node data transfer ("co-located join"). A poor `DISTKEY` forces massive data redistribution during joins, dominating query time. The **sort key** (`SORTKEY`) physically sorts data within each node's column storage, enabling effective zone maps (min/max filtering per 1MB disk block) and maximizing RLE compression for sorted data.

**Q22. What is ClickHouse and why has it become popular for real-time analytics?**
A: ClickHouse is an open-source OLAP database from Yandex, now widely adopted for high-throughput real-time analytics (event tracking, log analytics, metrics, time series). Key differentiators: (1) **MergeTree engine**: LSM-tree-style write batching (writes go to small "parts" that are merged in the background) combined with columnar on-disk format — achieving both high write throughput and fast analytical reads; (2) **vectorized execution**: all query operators are implemented using SIMD instructions, operating on columns of data in batches; (3) **sparse primary index**: the primary index stores only one entry per 8192 rows (not every row), making the index fit entirely in memory and enabling efficient coarse-grained range scans; (4) **columnar in-memory and on-disk**: data remains in columnar format throughout the query pipeline, never row-oriented even in intermediate query steps. Benchmark comparisons typically show ClickHouse 10-100× faster than traditional row-store databases on analytical queries, at the cost of less mature ACID transaction support and complex join handling.

**Q23. What is DuckDB and where does it fit in the landscape?**
A: DuckDB is an in-process (embedded, no server required) columnar OLAP database — analogous to SQLite for OLAP workloads. Key properties: runs inside a Python/R/Java/C++ process with zero infrastructure overhead, reads Parquet/CSV/JSON files natively (so it can analyze data lake files without loading them into a separate database), uses vectorized execution and adaptive query processing, and achieves competitive performance with much larger distributed systems for single-node data volumes (up to ~hundreds of GB). It's become the go-to tool for data scientists and engineers who want columnar query performance directly on Parquet files without spinning up BigQuery/Snowflake for every ad-hoc analysis. In system design contexts, DuckDB is increasingly relevant as an analytical sidecar that reads from the same Parquet files the data lake uses, without requiring a separate data warehouse cluster.

## Section 7: Hybrid Approaches

**Q24. What is HTAP (Hybrid Transactional/Analytical Processing) and how do different systems approach it?**
A: HTAP databases aim to serve both OLTP (transactional, row-level) and OLAP (analytical, columnar) workloads from the same system, eliminating the need for separate OLTP and OLAP databases and the ETL pipelines between them. Approaches:
- **Dual-format storage** (TiDB/TiFlash, MySQL with HeatWave): maintain row-oriented storage for OLTP and a real-time-replicated columnar copy for OLAP, with the query optimizer routing to the appropriate format based on query type. Writes go to the row store and are asynchronously replicated to the column store.
- **In-memory columnar acceleration** (SAP HANA, Oracle In-Memory, SQL Server Columnstore Index): add a columnar in-memory store alongside the primary row store, keeping hot analytical data in both formats simultaneously.
- **Unified format with layout hints** (emerging systems): use a single storage format that can be read both row-wise and column-wise depending on access pattern (experimental; few production examples).

The dual-format approach (separate row + column stores with replication) is the most mature and widely deployed — at the cost of data duplication and replication lag (analytical queries may see slightly stale data, typically seconds to minutes).

**Q25. What is a "Columnstore Index" in SQL Server and PostgreSQL's `cstore_fdw`/columnar extension?**
A: SQL Server (2012+) introduced Columnstore Indexes — a secondary index structure that stores column data in columnar compressed format alongside the primary row-store table. Queries that scan large numbers of rows and touch few columns are automatically accelerated by the columnstore index (the optimizer chooses it when the cost model favors it), while point lookups and row-level transactions continue using the row-store primary structure. This is the in-memory columnar acceleration approach from Q24 — adding a columnar read path to an existing row store without migrating the system. PostgreSQL has a similar extension (`pg_columnar`/`hydra`) that adds columnar table access methods. These hybrid indexes are a pragmatic middle ground for systems that have an existing OLTP database but increasingly need analytical query performance — rather than standing up an entirely separate OLAP database, you add columnar indexes to the existing database.

**Q26. What is the "Lakehouse" architecture and how does it reconcile row-oriented OLTP systems with columnar data lakes?**
A: A Lakehouse (coined by Databricks) combines the raw storage economics and flexibility of a data lake (Parquet/ORC files on object storage like S3) with ACID transaction semantics and schema enforcement typically found only in databases. Implemented via table format layers: **Apache Iceberg**, **Apache Hudi**, and **Delta Lake** add a transaction log and metadata layer on top of Parquet/ORC files, enabling: ACID transactions (atomic file swaps, snapshot isolation via time travel), schema evolution, partition pruning at query time via file-level metadata, and real-time "upserts" (which would require overwriting Parquet files — the table format handles this by managing which files are "current" via the transaction log, physically organizing data using copy-on-write or merge-on-read strategies). The Lakehouse pattern decouples the OLTP system (which continues using a row store for transactional workloads) from the analytical layer (which gets near-real-time data via streaming ingestion to the columnar data lake), eliminating the traditional 24-hour ETL batch window.

## Section 8: Indexing Differences

**Q27. How does indexing differ between row and column stores, and why are B-trees less relevant in columnar systems?**
A: Row stores heavily rely on B-tree indexes — a B-tree on a primary key enables O(log N) point lookups by resolving directly to the row's disk page. This is valuable because fetching a row by primary key is a primary access pattern for row stores (OLTP). Column stores, however, are used for analytical scans where point lookups are rare — the dominant access pattern is "scan 1 billion rows, filter on column X, aggregate column Y." B-tree indexes provide little benefit for this workload (you'd still need to touch most rows, and B-tree traversal overhead at scale is significant). Instead, column stores use:
- **Zone maps / min-max indexes**: per-file or per-row-group min/max values for each column, stored in metadata. A filter `WHERE date > '2024-01-01'` skips entire files whose max date < '2024-01-01'. O(1) to check, zero storage overhead proportional to data, and dramatically effective for sorted/clustered columns.
- **Bitmap indexes**: for low-cardinality columns, a bitmap (one bit per row, per distinct value) enables set-intersection-based filtering in O(N/64) time using 64-bit bitwise operations.
- **Bloom filters**: per-column bloom filter in each row group (Parquet/Iceberg) enabling probabilistic filtering — "does this row group contain value X?" — with no false negatives and small, tunable false positive rate.

**Q28. What is a bloom filter in the context of columnar storage, and how does it improve query performance?**
A: A bloom filter is a compact, probabilistic data structure that can answer "is element X definitely not in this set?" with certainty (zero false negatives) or "is element X probably in this set?" with a tunable false positive rate. For columnar storage:

- At write time, a bloom filter is built for each column in each row group (or file), compactly encoding which values appear in that segment.
- At query time, a filter predicate (e.g., `WHERE user_id = 12345`) checks the bloom filter for each row group/file before reading any data. If the bloom filter says "12345 is definitely not in this row group," the entire row group is skipped — zero I/O. If it says "12345 might be in this row group," the row group is read and the filter is applied precisely.

Parquet 2.0 added native bloom filter support per column per row group. Iceberg's file-level metadata includes bloom filters. The combined effect: equality predicate queries on non-sorted columns (where min-max filtering is ineffective) can skip the majority of data files without reading them, approaching the performance of a B-tree index for certain access patterns — without the B-tree's write overhead.

## Section 9: Scenario-Based Questions

**Q29. "Design the data storage layer for a real-time dashboard showing sales metrics (total revenue, top products, conversion rate by region) computed over the last 30 days of event data. The event stream produces 100,000 events/second. What storage format and architecture would you use?"**
A: The workload characteristics: very high write throughput (100k events/sec), analytical read pattern (aggregations over large event sets, few columns selected), time-bounded queries (last 30 days), and dashboard latency requirements (sub-second for a real-time dashboard). Storage architecture:

**Ingestion layer**: events land in Kafka; a stream processor (Flink, Spark Streaming, or ClickHouse's built-in Kafka table engine) consumes them. At 100k events/sec with ~200 bytes/event, that's ~20MB/sec or ~1.7TB/day.

**Hot layer (0-24 hours)**: ClickHouse — optimized for high write throughput via MergeTree's LSM-style batching + columnar storage. Real-time dashboards query ClickHouse directly with sub-second latency. Retain 24-72 hours of data in ClickHouse.

**Cold layer (1-30 days)**: Parquet files on object storage (S3), partitioned by `date` and `region`. Larger row groups (256MB) for better compression and scan efficiency on historical data. Queried via Trino/Athena or DuckDB for longer-range reports.

**Serving layer**: pre-aggregate common dashboard metrics into a separate materialized table (daily rollups by product, region, conversion funnel) — so the dashboard queries the aggregate, not the raw event table, at <100ms latency.

Why not a row store? Aggregating 100k events/sec × 30 days = 260 billion rows — no row-oriented database scales to this analytical scan pattern without extraordinary infrastructure cost. Why not pure Parquet without ClickHouse? Parquet on S3 can't be written to continuously in a streaming fashion; Parquet is immutable once written, requiring batch-flush architecture with inherent latency.

**Q30. "Your team is building a multi-tenant SaaS analytics platform where customers run queries on their own event data. Each customer has 10M-50B events. How would you approach the storage and isolation model?"**
A: Several considerations intersect:

**Storage format**: Parquet on object storage — per-customer prefix/bucket in S3 (`s3://analytics-platform/tenants/{tenant_id}/events/year=.../month=.../`). Partitioned by date and optionally by event type. Using Parquet means any Presto/Trino/Athena/DuckDB-compatible query engine can read it, avoiding vendor lock-in.

**Small tenants (10M events)**: queries run directly on Parquet via Athena or a shared ClickHouse cluster. Storage is cheap (10M events × 200 bytes × 10× compression ≈ 200MB). Query latency is acceptable with Parquet column pruning + date partition pruning.

**Large tenants (1B-50B events)**: dedicated ClickHouse instance (or isolated schema on a shared cluster) for sub-second query performance on recent data (last 30 days); Parquet on S3 for cold historical data (>30 days). The hot/cold split is critical — querying 50B events on Parquet for "last 7 days" is slower than querying a purpose-built ClickHouse hot store.

**Isolation**: tenant data in separate S3 prefixes; IAM policies preventing cross-tenant access. For compute isolation on shared ClickHouse: per-tenant query user with resource quotas (`max_memory_usage`, `max_execution_time`). A runaway tenant query on a shared cluster can degrade all tenants — physical isolation (separate ClickHouse instances) eliminates this at higher operational cost.

**Q31. "A startup is building a product analytics tool (think Mixpanel or Amplitude). They expect 500M events/day, need funnel analysis, user-level event sequences, and real-time dashboards. Should they use PostgreSQL, Cassandra, or ClickHouse?"**
A: The workload is unambiguously OLAP: high write volume, time-series-like access, analytical aggregations, funnel computations over potentially billions of events, sub-second dashboard needs. Walk through each option:

**PostgreSQL**: row-oriented, not designed for this scale. Even with Citus sharding and table partitioning, 500M events/day (~5,800 events/sec peak) would stress write capacity, and analytical queries scanning billions of rows would time out or require expensive hardware. Not appropriate at this scale.

**Cassandra**: good write throughput (LSM-tree write path), but fundamentally a wide-column store designed for key-value and time-series lookups, not analytical aggregations. Funnel analysis requires scanning all events for a user and joining across event types — a pattern Cassandra's data model handles poorly (it's optimized for reads by partition key, not arbitrary group-by aggregations). Not appropriate for the analytical query pattern.

**ClickHouse**: purpose-built for this exact workload. MergeTree engine handles 500M events/day write volume comfortably (many production deployments exceed this significantly). Columnar storage + vectorized execution makes funnel queries on billions of events execute in seconds. Native support for approximate aggregations, time-series operations, and user session analysis functions. The correct answer — with the caveat that operations are more complex than managed PostgreSQL (ClickHouse requires more tuning and has historically had weaker ACID guarantees for complex transactions).

**Q32. "What is the right storage model for a system that needs both: (1) real-time order processing with ACID transactions, and (2) daily fraud detection analytics over 3 years of transaction history?"**
A: Two separate systems with a well-defined boundary — the textbook case for the OLTP + OLAP split:

**OLTP (order processing)**: PostgreSQL or MySQL with InnoDB (row-oriented, ACID-compliant, optimized for point lookups, updates, and concurrent transactions). Orders table with B-tree indexes on `order_id`, `customer_id`, `status`. Write path is the application's hot path — must be low-latency and transactionally safe.

**OLAP (fraud analytics)**: ClickHouse or BigQuery (columnar, optimized for analytical scans). 3 years of transactions × 365 days × estimated volume = potentially billions of rows. Fraud detection queries (`find all transactions from unusual locations for users who changed their password in the last 24 hours`) require scanning large volumes of data with complex filters across many columns.

**Bridge**: CDC-based replication (Debezium capturing PostgreSQL WAL changes → Kafka → ClickHouse or BigQuery). New transactions are available for analytics within seconds. The OLTP system is never touched by analytical queries — complete workload isolation. This is the exact architecture pattern covered in the cache invalidation guide's CDC section, applied to the OLTP→OLAP pipeline.

The single-system temptation: "can we just add a Columnstore Index to PostgreSQL?" Possibly viable at small scale (single-digit billions of rows), but the columnar extensions for PostgreSQL are not yet as mature as purpose-built OLAP databases for truly large-scale analytical workloads.

## Quick Reference Table

| Dimension | Row-Oriented (NSM) | Column-Oriented (DSM) |
|---|---|---|
| Physical layout | Entire row contiguous | Entire column contiguous |
| Best workload | OLTP (point lookups, transactions) | OLAP (aggregations, column scans) |
| Read I/O: full row | Excellent (1 read) | Poor (N column reads) |
| Read I/O: few columns | Poor (reads all columns) | Excellent (reads only needed columns) |
| Write performance | Excellent (1 write per row) | Poor (N writes, one per column) |
| Compression ratio | 2-4× | 5-20× |
| Compression techniques | General-purpose (LZ4, Snappy) | RLE, Dictionary, Delta, Bit-packing |
| Primary index type | B-tree | Zone maps, Bloom filters, Bitmap |
| SIMD/vectorization | Difficult (mixed types per row) | Excellent (uniform type per column) |
| Examples | PostgreSQL, MySQL, MongoDB | Parquet, BigQuery, ClickHouse, Redshift |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) immediately deriving the storage choice from the **I/O amplification argument** — "column store reads only needed-columns/total-columns fraction of data" — not just stating "column stores are better for analytics"; (2) knowing that **compression is multiplicative** with I/O savings — a 10× compression ratio means 10× less data to read, stacking on top of the columnar I/O reduction; (3) being able to articulate the **write path trade-off** concretely (N writes per row in a column store) and naming LSM-tree-style batching (ClickHouse MergeTree) as the mitigation; (4) knowing **Parquet's row group + column chunk structure** (Q17) — most candidates know Parquet is columnar but can't describe how it actually stores data, which is a distinguishing detail; and (5) being able to propose the **OLTP + OLAP split with CDC replication** (Q32) as the canonical architecture for systems needing both transactional and analytical workloads, rather than trying to find one system that does both acceptably.
