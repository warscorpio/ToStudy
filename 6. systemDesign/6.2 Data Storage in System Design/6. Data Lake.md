# Data Lake Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a data lake and what problem does it solve that a traditional data warehouse doesn't?**
A: A data lake is a centralized storage repository that holds raw data in its native format — structured, semi-structured (JSON, CSV, Parquet), and unstructured (logs, images, audio) — at arbitrary scale, typically on cheap object storage (S3, GCS, ADLS). The core problem it solves is the rigidity of traditional data warehouses: a warehouse requires a predefined schema before data can be loaded ("schema-on-write") — if your schema evolves or if you need to store data types the warehouse wasn't designed for, you face expensive migrations or simply can't store the data at all. A data lake uses "schema-on-read": raw data is stored as-is, and the schema is applied at query time by the consumer — meaning any data can be landed immediately, and different consumers can interpret the same data differently for different purposes (a data scientist reading raw clickstream events as a flat JSON array; a BI tool reading the same events as a structured events table; an ML pipeline reading them as a feature matrix). The flexibility trades off against the structure and governance that warehouses provide by default.

**Q2. What are the "5 Vs" that motivate data lake design, and how does the lake architecture address each?**
A: The 5 Vs of big data:
- **Volume**: data lakes store petabytes on object storage (S3 costs ~$0.023/GB/month — orders of magnitude cheaper than SSD-backed warehouse storage). Distributed processing (Spark, Flink) scales compute horizontally across the data.
- **Velocity**: real-time and batch ingestion pipelines land data continuously (Kafka → object storage, database CDC → Parquet files). The lake accepts data as fast as sources produce it.
- **Variety**: raw, unstructured, semi-structured, and structured data all co-exist. No schema negotiation required for ingestion.
- **Veracity**: a challenge for data lakes — without enforced schema, data quality varies. Addressed by table format layers (Iceberg, Delta Lake), data quality frameworks (Great Expectations, dbt tests), and catalog metadata.
- **Value**: raw data alone has limited value. Processing layers (transformation pipelines, feature stores, ML models, BI dashboards) extract value by transforming raw lake data into curated, queryable assets.

**Q3. What is "schema-on-read" vs "schema-on-write" and what are the practical trade-offs?**
A: Schema-on-write (data warehouse model): data must conform to a predefined schema before being stored. The schema is enforced at write time — if a new field is added, the schema must be altered and existing rows backfilled or NULLed. Reads are fast because the data is always in a known, consistent format. Schema-on-read (data lake model): data is stored as-is. When a query is executed, the reader applies a schema interpretation at that moment — infers types from JSON, or uses a supplied schema to interpret Parquet column names. New data fields are immediately available without migrations; incompatible or malformed data fails only at query time, not at ingest time. Trade-off summary: schema-on-write sacrifices ingestion flexibility for read reliability and performance; schema-on-read sacrifices query reliability for ingestion flexibility. The Lakehouse architecture (Q27-Q28) attempts to capture both — columnar format with schema enforcement at write time, but via a flexible metadata layer rather than a rigid relational schema.

**Q4. What is the canonical data lake storage hierarchy and what does each zone contain?**
A: Most mature data lake architectures use a multi-zone (Bronze/Silver/Gold or Raw/Refined/Curated) approach, separating raw from processed data:

```
Bronze (Raw / Landing Zone):
  - Exact copy of source data, never modified after landing
  - Preserved for reprocessing, auditing, debugging
  - Format: as-is (JSON logs, CSV exports, Avro from Kafka, DB snapshots)
  - Retention: long (months to years)
  - Example: s3://datalake/bronze/events/2024/01/15/*.json.gz

Silver (Refined / Cleaned Zone):
  - Cleaned, deduplicated, type-cast, schema-enforced version of Bronze
  - Joined and enriched (e.g., session events enriched with user attributes)
  - Format: Parquet or Delta/Iceberg tables, partitioned by date
  - Retention: medium-long (months)
  - Example: s3://datalake/silver/events/year=2024/month=01/day=15/*.parquet

Gold (Curated / Serving Zone):
  - Aggregated, business-logic-applied, serving-ready datasets
  - Structured for specific use cases: BI dashboards, ML features, product metrics
  - Format: Parquet/Delta, often further pre-aggregated (daily rollups)
  - Retention: varies (often indefinite for business metrics)
  - Example: s3://datalake/gold/product_metrics/daily_active_users/
```

The multi-zone pattern separates concerns: Bronze preserves the source of truth for reprocessing; Silver makes data queryable and reliable; Gold optimizes for specific consumers. Pipelines flow Bronze → Silver → Gold, with quality gates at each transition.

## Section 2: Storage Layer

**Q5. Why is object storage (S3, GCS, ADLS) the foundation of modern data lakes, and what are its key properties?**
A: Object storage is the foundation because of five properties uniquely suited to data lake scale:
- **Cost**: at $0.023/GB/month (S3 Standard), object storage is 10-100× cheaper than block storage (EBS) or SSD-backed database storage. At petabyte scale, this cost difference is mission-critical.
- **Infinite scale**: no provisioning required — you write an object, it's stored. Capacity is effectively unlimited, with no cluster to size or resize.
- **Durability**: S3 provides 11 nines (99.999999999%) durability via automatic redundancy across multiple AZs — no RAID, no backup management required from the user.
- **Decoupled from compute**: object storage has no "attached" compute. Any compute service (Spark on EMR, Presto on Athena, dbt on Redshift Spectrum, Flink on Kinesis Analytics) can read from and write to the same S3 bucket — enabling a single copy of data served to many compute engines simultaneously.
- **HTTP/REST API**: objects are accessed via standard REST — enabling direct access from any language, any machine, without a database driver or client library.

The critical limitation: object storage has no in-place modification. Objects are immutable — you can write a new object, or delete an existing one, but not update bytes within one. This fundamentally shapes data lake architecture (discussed in Q9-Q10).

**Q6. What is the object storage consistency model and how did its evolution affect data lake architecture?**
A: Historically (pre-2020), Amazon S3 offered only "eventual consistency" for overwrites and deletes — meaning a newly overwritten object might still serve the old version to some readers for a brief window. This forced complex workarounds in data lake architectures (never overwrite, only append new files; use external coordination to tell readers which files are "current"). In December 2020, AWS announced **strong read-after-write consistency** for S3 — all read/delete/list operations are now strongly consistent immediately after a write. This was a significant architectural simplification: data lake frameworks no longer need to work around eventual consistency. GCS was always strongly consistent; ADLS Gen2 is strongly consistent. The change removed a class of subtle data lake bugs (reading a stale file list after writing new data) and made atomic operations on sets of files more reliable.

**Q7. How does partitioning of data on object storage work, and what is Hive-style partitioning?**
A: Partitioning organizes files in a directory hierarchy where each directory level corresponds to a partition column's value — allowing query engines to skip entire directories when a query's filter doesn't match:

```
Hive-style partitioning (key=value directory naming):

s3://datalake/silver/events/
├── year=2024/
│   ├── month=01/
│   │   ├── day=14/
│   │   │   └── part-00000.parquet
│   │   └── day=15/
│   │       └── part-00000.parquet
│   └── month=02/
│       └── ...
```

A query `WHERE year=2024 AND month=01 AND day=15` only reads files under `s3://datalake/silver/events/year=2024/month=01/day=15/` — skipping all other directories without reading a single byte from them. This is "partition pruning" — the query engine discovers partitions by listing the directory structure and filters the list before reading any data. Partition column choice is critical: choose columns that are frequently used as query filters (date is almost universal), have manageable cardinality (high-cardinality columns like `user_id` would create millions of directories), and align with the data's natural access pattern (time-series data almost always partitioned by date).

**Q8. What are the common mistakes in partition design, and how do you avoid them?**
A:
- **Over-partitioning**: partitioning on a high-cardinality column (`user_id`, `session_id`, `event_id`) creates millions of tiny files — each query lists millions of S3 keys (expensive API calls), reads many tiny files (each with per-file overhead), and generates excessive metadata. Fix: partition on low-to-medium cardinality columns (date, region, event_type with bounded cardinality).
- **Under-partitioning**: a single partition covering months or years of data provides no pruning benefit — queries that need last week's data must scan everything. Fix: at minimum, partition by date for time-series data.
- **Wrong column order**: `day=15/month=01/year=2024` is harder for tools to prune efficiently than `year=2024/month=01/day=15` (coarser-to-finer order). Fix: order partition columns from lowest-cardinality (broadest filter) to highest.
- **Small files problem**: many parallel writers create many small files per partition (each Spark task writes its own output file) — causing excessive file listing and per-file overhead at query time. Fix: periodic compaction (coalescing small files into larger ones), or using table format write-path optimizations (Delta/Iceberg file size enforcement).

## Section 3: The Small Files Problem and Compaction

**Q9. What is the "small files problem" in data lakes and why is it so pervasive?**
A: The small files problem is one of the most common and impactful operational issues in data lake architectures. It occurs when a directory (partition) contains many files that are each much smaller than the optimal read size (typically 128MB-1GB for Parquet). Causes:
- **High-frequency streaming ingestion**: a pipeline that writes data every 5 minutes creates 288 files per partition per day — each tiny.
- **High parallelism with small data**: 200 Spark tasks writing to one date partition each produce their own output file, resulting in 200 small files.
- **Incremental updates**: each "upsert" or correction to a partition adds new small files on top of existing ones.

Impact: reading a partition with 10,000 × 1MB files is dramatically slower than reading one 10GB file of the same data — each file requires an S3 `GET` request with its own latency (~5-20ms), and Parquet footer reading is per-file. At 10,000 files, footer reading alone is 50-200 seconds of latency before any data is processed. Additionally, S3 `LIST` operations to discover files are paginated at 1,000 results per API call — 10,000 files requires 10 API calls just for file discovery.

**Q10. What is "compaction" in a data lake and how is it implemented?**
A: Compaction is the process of merging many small files in a partition into fewer larger files, reducing file count and increasing average file size toward the optimal range (128MB-1GB). Implementations:
- **Spark-based compaction job**: a scheduled job reads all small files in a partition, repartitions the data to a target number of output files, and overwrites the partition. Simple but requires careful coordination to avoid readers seeing a "missing" partition during the overwrite window.
- **Delta Lake `OPTIMIZE`**: a built-in command (`OPTIMIZE table WHERE date = '2024-01-15'`) that reads small files, combines them into 1GB target files, writes the new files, and atomically updates the transaction log to mark old files as deleted and new files as current — without any reader seeing inconsistent state.
- **Iceberg rewrite data files action**: `SparkActions.rewriteDataFiles(table).option("target-file-size-bytes", "512MB").execute()` — similarly atomic via Iceberg's metadata layer.
- **Auto-compaction**: Delta Lake and Iceberg both support background auto-compaction that triggers when a partition exceeds a file count threshold, without explicit operator scheduling.

**Q11. What is the "file listing" bottleneck and how do table formats address it?**
A: In a bare Parquet-on-S3 data lake without a table format layer, discovering which files constitute a table requires listing the S3 directory tree — which becomes slow at scale (millions of files require thousands of LIST API calls, each taking 10-100ms, adding minutes to query planning time). Table formats (Iceberg, Delta Lake, Hudi) solve this by maintaining a manifest/metadata layer that catalogs all files belonging to a table at any point in time:
- **Iceberg**: a tree of metadata files (table metadata → snapshot → manifest list → manifest files → data files) that can be traversed in a small, bounded number of reads regardless of total file count.
- **Delta Lake**: a transaction log (`_delta_log/`) containing JSON and Parquet checkpoint files listing all active files — a query engine reads the log to determine the current file set in O(log N) operations, not O(N) S3 LISTs.

This means query planning time is O(metadata size), not O(number of data files) — critical at petabyte scale where a single table may have millions of data files.

## Section 4: Table Formats — Iceberg, Delta Lake, Hudi

**Q12. What are the three major open table formats, and what problem do they collectively solve?**
A: Apache Iceberg, Delta Lake (Databricks), and Apache Hudi all solve the same set of problems that bare Parquet-on-S3 cannot handle: ACID transactions (atomic multi-file writes), time travel (query historical snapshots of table state), schema evolution (add/rename/drop columns without rewriting data), partition evolution (change partitioning strategy without rewriting), efficient upserts (update or delete individual rows in an immutable file system), and fast file discovery (Q11). They are "table format" or "open table format" layers — not storage systems themselves, but a metadata + protocol layer on top of standard Parquet/ORC files on object storage that adds database-like transactional semantics to a data lake.

**Q13. How does Delta Lake implement ACID transactions on object storage?**
A: Delta Lake maintains a transaction log as a directory of sequential JSON files (`_delta_log/00000000000000000000.json`, `00000000000000000001.json`, ...). Each transaction appends a new log entry describing what changed — which files were added, which were removed, and what metadata changed. Atomicity is achieved by the log entry being a single S3 `PUT` operation (which is atomic per S3's consistency guarantees): either the log entry exists (transaction committed) or it doesn't (transaction never happened). Reading the current table state means reading the log to reconstruct the latest set of active files. Concurrency is handled via optimistic concurrency control — a writer reads the current log version, validates its changes don't conflict with any concurrent writes (e.g., two writers modifying different partitions can both succeed; two writers updating the same rows conflict), writes data files, then appends the log entry. If another writer committed between reading and writing, the transaction retries.

```
_delta_log/:
  00000000000000000000.json  ← Initial commit: adds files A, B, C
  00000000000000000001.json  ← Append: adds file D
  00000000000000000002.json  ← Update: removes B, adds B' (updated B)
  00000000000000000010.parquet  ← Checkpoint (compacted log, every N commits)
```

**Q14. How does Apache Iceberg differ from Delta Lake architecturally?**
A: Both solve the same problems but with different metadata structures and design philosophies:

| Dimension | Delta Lake | Apache Iceberg |
|---|---|---|
| Metadata structure | Sequential JSON log files + Parquet checkpoints | Tree: table metadata → snapshot → manifest list → manifest files |
| Primary backer | Databricks | Apple (original), Apache Foundation (now) |
| Query engine support | Best on Spark; improving on others | Multi-engine first (Spark, Flink, Trino, Hive, Dremio) |
| Partition evolution | Limited | Full (change partition spec without rewriting data) |
| Hidden partitioning | No | Yes (partition by transform: `months(event_time)`, `bucket(N, user_id)`) |
| Row-level delete | Copy-on-write or merge-on-read | Copy-on-write or merge-on-read |
| File format | Parquet only | Parquet, ORC, or Avro |
| Merge-on-read performance | Good (Photon engine) | Good (native Iceberg read optimization) |

Iceberg's "hidden partitioning" is a notable design win: the physical partition strategy (how data is laid on disk) is decoupled from the query predicate. A query `WHERE event_time > '2024-01-15'` works correctly even if the table is partitioned by `months(event_time)` — the metadata translates the predicate to the appropriate partition filter automatically, without the query author needing to know the physical partition structure. Delta Lake requires the writer and reader to agree on partition column values explicitly.

**Q15. What is "merge-on-read" vs "copy-on-write" for handling row-level updates in table formats, and when does each excel?**
A: When a row must be updated or deleted in an immutable file system, two strategies exist:

**Copy-on-write (CoW)**: when an update/delete arrives, read the entire affected data file, apply the change to produce a new file, and mark the old file as deleted in the metadata. Every write rewrites entire files. Reads are fast (no reconciliation needed — files always contain the latest data). Writes are slow for small updates (rewriting a 500MB file to change one row). Best for: infrequent updates with large batches, read-heavy workloads.

**Merge-on-read (MoR)**: write updates/deletes as small "delta files" (containing only the changed rows) alongside the base data files. Reads must merge the base file with all applicable delta files to reconstruct the current row state. Writes are fast (append-only, small delta files). Reads are slower (must reconcile base + deltas, like reading an LSM-tree). Best for: frequent small updates, write-heavy workloads, near-real-time ingestion.

Production practice: both Delta Lake and Iceberg support both modes, often with a periodic "compaction/optimize" job converting MoR delta files into CoW merged files during off-peak hours — getting fast writes during the day and fast reads after compaction.

**Q16. What is "time travel" in a data lake table format and what are its operational uses?**
A: Time travel is the ability to query a table as it existed at a previous point in time (or at a previous snapshot/version), using the metadata log to reconstruct the historical file set:

```sql
-- Delta Lake time travel syntax
SELECT * FROM events TIMESTAMP AS OF '2024-01-10 09:00:00';
SELECT * FROM events VERSION AS OF 5;

-- Iceberg time travel
SELECT * FROM events FOR SYSTEM_TIME AS OF TIMESTAMP '2024-01-10 09:00:00';
SELECT * FROM events FOR SYSTEM_VERSION AS OF 5;
```

Operational uses: (1) **debugging bad pipelines**: a faulty transformation corrupted Gold data — time travel lets you query Silver data from before the bad run and reprocess from that snapshot; (2) **audit compliance**: regulators require showing exactly what data the model trained on at a specific date — time travel provides a reproducible snapshot; (3) **rollback**: `RESTORE TABLE events TO VERSION AS OF 5` atomically reverts a table to a previous state after an accidental deletion or corruption; (4) **slowly changing dimensions**: track how a user's attributes changed over time by querying different historical snapshots. Time travel data is retained as long as the old data files haven't been garbage-collected (`VACUUM` in Delta Lake, expiry policies in Iceberg).

## Section 5: Ingestion Patterns

**Q17. What are the main data lake ingestion patterns and when is each appropriate?**
A:
- **Batch ingestion**: large files written periodically (hourly, daily). Simple pipelines, high throughput, natural fit for bulk exports from OLTP databases or external API data. Limitation: data latency proportional to batch interval — daily batches mean analytics are 24h stale.
- **Micro-batch streaming** (Spark Structured Streaming, Flink in checkpoint mode): continuous mini-batches (every 1-5 minutes) written as Parquet files to the lake. Reduces latency to minutes while retaining the simplicity of batch-like file writing. Generates small files (requiring compaction).
- **Streaming ingestion** (Kafka → object storage via Kafka Connect S3 Sink or Kinesis Firehose): near-real-time landing of events as files, typically every few seconds to minutes. Higher complexity, lowest latency for landing. Still generates small files that require compaction for efficient querying.
- **CDC (Change Data Capture)** (Debezium → Kafka → lake): captures row-level changes from OLTP databases (inserts, updates, deletes) via the database transaction log. Essential for keeping analytical data in sync with production databases without impacting the production DB with read queries. Debezium emits change events in Avro or JSON; these are typically materialized into Delta/Iceberg tables via a merge operation.

**Q18. What is a Lambda Architecture and what problem does it solve?**
A: Lambda Architecture is a data processing pattern (introduced by Nathan Marz, 2012) that runs two parallel data paths to handle the trade-off between latency and accuracy:
- **Batch layer**: processes all historical data periodically (e.g., daily Spark jobs) producing accurate, complete views but with high latency (data is 12-24h stale).
- **Speed layer** (real-time layer): processes only recent data (last few hours) using a stream processor (Flink, Spark Streaming), producing low-latency but potentially incomplete or approximate views.
- **Serving layer**: merges results from batch and speed layers, using batch results for older data (more accurate) and speed layer results for recent data (less accurate but fast).

Problem: operational complexity — two separate codebases (batch logic and streaming logic) solving the same business problem, requiring them to produce identical semantics and be kept in sync. The Kappa Architecture (Q19) emerged as a simplification.

**Q19. What is the Kappa Architecture and how does it simplify Lambda?**
A: Kappa Architecture (proposed by Jay Kreps, 2014) eliminates Lambda's batch layer entirely — everything is processed as a stream. Historical reprocessing is handled by re-reading from the beginning of a durable, replayable stream (Kafka with long retention) rather than a separate batch layer. Simplification: one codebase (streaming), one set of infrastructure, one set of operational concerns. The insight: with sufficiently fast stream processing (Flink, Spark Streaming) and sufficiently long stream retention (Kafka retention of 30+ days), batch processing is just a special case of stream processing starting from offset 0. Modern data lakes often implement Kappa-style architectures using Kafka as the source-of-truth event log and Flink or Spark Structured Streaming for all processing, writing to the lake via Delta/Iceberg tables that handle the ACID semantics. The remaining practical limitation: full historical reprocessing of years of data through a streaming system is slower and more resource-intensive than a highly parallelized batch Spark job — so some architectures keep a batch layer for initial historical backfills only.

## Section 6: Query Engines and the Serving Layer

**Q20. What query engines are commonly used on top of data lakes, and how do they differ?**
A:
- **Apache Spark SQL**: dominant general-purpose distributed query engine for data lakes. Reads Parquet/Delta/Iceberg directly from S3. Scales to petabytes. Best for complex transformations, ML pipelines, and batch analytics. Latency: seconds to hours depending on data volume.
- **Trino / Presto**: SQL-first, fast interactive query engine designed for ad-hoc analytics on data lakes. Lower latency than Spark for interactive queries (seconds) due to a pipeline execution model (no write-to-disk between stages). Supports federated queries across different sources (S3, PostgreSQL, Kafka, Elasticsearch). Widely deployed at Facebook (Presto) and by Starburst/AWS Athena (Trino).
- **AWS Athena**: managed serverless Trino, query-priced ($5/TB scanned). Zero infrastructure to manage — submit SQL, pay for data scanned, get results. Strongly incentivizes Parquet + partitioning (reduces scanned bytes = reduces cost). Not suitable for complex multi-step transformations.
- **Databricks SQL / Spark**: tight integration with Delta Lake; Photon engine (C++-implemented vectorized executor) for fast columnar processing.
- **DuckDB**: embedded, in-process, can query Parquet/Iceberg directly. Excellent for single-node data (up to ~500GB) — a data scientist's tool rather than a production cluster.
- **BigQuery / Snowflake / Redshift Spectrum**: managed data warehouses that can query external data lake files (Parquet on S3) without importing them — the "query the lake from the warehouse" pattern.

**Q21. What is "predicate pushdown" in data lake queries and why does it matter so much?**
A: Predicate pushdown is the optimization where a filter condition (`WHERE date = '2024-01-15' AND user_id = 42`) is pushed as early as possible in the query pipeline — ideally before any data is even read from storage. In data lake query engines:
- **Partition pruning** (coarsest level): the filter matches a partition column, so entire directory subtrees are skipped by the file listing step. Zero I/O for skipped partitions.
- **File-level pruning** (table format level): Iceberg/Delta metadata contains per-file statistics (min/max values per column per file). A filter `WHERE salary > 100000` skips files whose max salary < 100000 without reading those files.
- **Row group pruning** (Parquet level): each Parquet file's footer contains min/max statistics per column per row group. Files that pass file-level pruning are still filtered at the row group level — row groups whose column statistics exclude the filter condition are skipped.
- **Page-level filtering** (Parquet column index): within a row group, column index statistics enable skipping individual Parquet pages.

The cumulative effect: a well-structured lake with good partitioning and table format statistics might read 0.1% of total stored data for a specific narrow query — 1000× less I/O than a naive full scan. Getting predicate pushdown to work correctly (which requires correct partition column specification, up-to-date statistics, and correct filter column types) is often the single most impactful performance optimization in a data lake.

**Q22. What is a data catalog and why is it essential for a data lake at scale?**
A: A data catalog is a metadata management system that inventories what data exists in the lake, describes its structure and meaning, tracks its lineage (where it came from and how it was transformed), and controls access. Without a catalog, a data lake becomes a "data swamp" — data exists but no one knows what's in it, where it came from, whether it's accurate, or how to use it. Key catalog capabilities:
- **Schema registry**: stores table schemas, column descriptions, data types — so consumers know what columns a table has without reading a file.
- **Data lineage**: tracks which source tables were used to produce a derived table, and which pipelines created or modified it — enabling impact analysis ("if I change this source table, what downstream tables break?").
- **Data discovery**: search interface for finding tables, columns, or datasets by name, description, or tag.
- **Data quality metadata**: stores quality scores, test results, freshness metrics — consumers know whether to trust a dataset.

Common catalog implementations: Apache Atlas (Hadoop/Hive ecosystem), AWS Glue Data Catalog (auto-discovers Parquet schemas from S3, integrates with Athena/Spark), DataHub (LinkedIn-originated, widely adopted open-source), Amundsen (Lyft-originated), Alation/Collibra (commercial).

## Section 7: Data Quality and Governance

**Q23. What is the "data swamp" anti-pattern and how do you prevent it?**
A: A data swamp is a data lake that has accumulated vast amounts of data that is impossible to find, trust, or use effectively — no catalog, no schema enforcement, no data quality checks, no lineage tracking, no access control. Common causes: treating the lake as a dump ("land everything, figure out how to use it later") without investing in the governance layer. Prevention strategies that must be implemented proactively, not retroactively:
- **Mandate schema documentation** for every new table before it lands in Silver — no undocumented tables allowed past Bronze.
- **Data quality gates**: pipelines must pass quality checks (row count non-zero, null rate below threshold, schema validation) before writing to Silver. Frameworks: Great Expectations, dbt tests, Soda.
- **Freshness monitoring**: alerting when a table hasn't been updated within its expected schedule (a pipeline failure often manifests first as stale data, not as an error).
- **Access review**: regular audits of who has read/write access to which tables — data sprawl + unconstrained access = undetectable data leaks.
- **Naming conventions and tagging**: enforced table naming (`domain.dataset_name.grain`), mandatory tags (PII-containing, retention class, owning team) applied at catalog registration time.

**Q24. What is data lineage and why does it matter for both reliability and compliance?**
A: Data lineage tracks the full provenance and transformation history of any data asset — where it originated (source database, API, event stream), how it was transformed (which pipeline, which code version, which parameters), and what downstream assets depend on it. It matters for:
- **Incident response**: "Our Gold metrics table shows incorrect revenue for yesterday — which Silver table does it depend on? Which pipeline ran? Can we trace the bad data back to a source record?" Lineage makes this trace in minutes instead of days.
- **Impact analysis**: "We're changing the schema of the `orders` source table — which of our 200 downstream derived tables will break?" Without lineage, you can't know without inspecting every pipeline's code.
- **GDPR/CCPA compliance (right to erasure)**: a user requests deletion of all their data. Without lineage, you can't systematically find every table that contains a derived representation of their data. With lineage, you traverse the graph to find all downstream tables, assess which contain PII derived from that user, and execute targeted deletion or masking.
- **Regulatory audit**: financial or healthcare regulators may require demonstrating exactly how a specific metric was calculated and from which source systems — lineage provides the documented audit trail.

**Q25. What are PII handling and data retention requirements in data lake design, and how are they implemented?**
A: PII (Personally Identifiable Information) requires specific handling at every lake layer:
- **Detection**: automated PII scanning at ingestion (AWS Macie, custom classifiers) identifies and tags columns containing PII (email, phone, SSN, IP address) before they're stored.
- **Encryption**: all PII data encrypted at rest (S3 server-side encryption with customer-managed KMS keys) and in transit (TLS). PII columns may use column-level encryption within Parquet for finer-grained access control.
- **Access control**: PII tables in a separate S3 prefix with restrictive IAM policies; only approved roles/teams can read PII columns. Dynamic data masking (supported in Databricks Unity Catalog, Iceberg with row-level security) allows some users to query a table with PII columns masked while others see real values.
- **Tokenization/pseudonymization**: replace real PII values with consistent tokens (e.g., `user_id` instead of email) at the Silver layer, keeping PII only in Bronze and a separate secure mapping table.
- **Retention policies**: data lake tables tagged with retention classes (`30d`, `7y`, `indefinite`). Automated S3 lifecycle rules delete objects after their retention period expires. For GDPR "right to erasure," streaming deletion must propagate through all layers including Gold aggregates that may contain PII-derived values.

## Section 8: Cost Optimization

**Q26. What are the primary data lake cost drivers and how do you control them?**
A: Three main cost buckets:
- **Storage costs** (often the largest at scale): `storage_cost = total_data_GB × $/GB/month`. Controls: aggressive compression (Parquet + Snappy/Zstd), S3 storage class tiering (S3 Standard → S3 Standard-IA after 30 days → S3 Glacier after 90 days, reducing cost by 40-80%), data retention policies (delete data past its useful life), and deduplication (landing the same event twice is common; detect and remove duplicates at Silver transformation).
- **Compute costs** (for processing): `compute_cost = cluster_hours × $/hour`. Controls: right-size Spark clusters for the workload (a 100-node cluster idle 90% of the time is expensive), use spot/preemptible instances for batch ETL (50-70% cheaper, tolerable for jobs that can be retried), autoscaling clusters that shrink during idle periods, and serverless compute (Athena: pay per TB scanned) for ad-hoc queries.
- **Query costs** (for interactive analytics): Athena charges $5/TB scanned. Controls: Parquet (compressed columnar format reduces bytes scanned by 5-10× vs CSV), partitioning (reduces scanned bytes by partition-match ratio), and result caching (Athena caches results for 24h by default — repeat queries are free).

The most impactful single optimization: converting CSV/JSON raw data to Parquet in the Silver layer. A 10GB CSV file might compress to 500MB-1GB as Parquet with Snappy — reducing future query scans (and Athena cost) by 5-10×.

## Section 9: Lakehouse Architecture (Synthesis)

**Q27. What is the Lakehouse architecture and how does it synthesize data lake and data warehouse patterns?**
A: The Lakehouse (coined by Databricks, 2021) is an architectural pattern that adds data warehouse-like capabilities (ACID transactions, schema enforcement, BI query performance) directly to the data lake storage layer — using open table formats (Delta Lake, Iceberg, Hudi) on top of cheap object storage (Parquet on S3), rather than requiring data to be loaded into a separate, proprietary warehouse system. The key claim: a single system can serve both data engineering workloads (Spark ETL), data science workloads (ML on raw data), and BI workloads (SQL dashboards) — all reading from the same Parquet files governed by the same table format layer. This eliminates the traditional "data lake → ETL → data warehouse" pipeline, reducing latency, cost (no warehouse storage duplication), and the engineering complexity of maintaining the bridge between systems.

**Q28. What are the key tensions in Lakehouse design that haven't been fully resolved?**
A: Despite the Lakehouse's promise, several genuine tensions remain:
- **Query performance vs openness**: purpose-built warehouses (Snowflake, BigQuery) typically outperform open Lakehouse stacks (Spark + Delta/Iceberg) for BI queries because they control the entire stack (custom storage format, caching, query engine). The Lakehouse trades some performance for openness (vendor independence, direct file access, multi-engine compatibility).
- **Transaction complexity vs simplicity**: ACID on an immutable file system requires metadata overhead (transaction logs, manifest files, compaction) that adds operational complexity absent from bare Parquet-on-S3.
- **Real-time vs batch**: Lakehouse table formats were designed around batch writes. True sub-second update latency (required for some operational use cases) still requires purpose-built systems (ClickHouse, DynamoDB) rather than a Lakehouse Delta table.
- **Catalog standardization**: multiple competing catalogs (Glue, Hive Metastore, Nessie, Unity Catalog) with incomplete interoperability means "open" Lakehouse architectures can still accumulate vendor dependencies at the catalog layer.

## Section 10: Scenario-Based Questions

**Q29. "Design a data lake for a ride-sharing company that needs to store trip events, compute driver earnings, power real-time fraud detection, and train ML surge pricing models."**
A: Four distinct workloads with different requirements — use the multi-zone lake with specialized serving layers per consumer:

**Ingestion**:
- Trip events from mobile apps → Kafka (100k events/sec) → Kinesis Firehose → Bronze S3 as JSON.gz, partitioned by `year/month/day/hour`. Firehose provides exactly-once delivery with automatic retry.
- Driver and rider profiles → CDC (Debezium) from production PostgreSQL → Kafka → Bronze as Avro.
- GPS pings → Kafka → Bronze as compressed JSON (very high volume, stored separately from trip events due to different retention needs).

**Bronze → Silver (Spark Structured Streaming)**:
- Deduplicate events (trip events can arrive twice from mobile retry logic).
- Type-cast JSON strings to proper types, flatten nested fields.
- Join trip events with driver/rider profiles (enrichment).
- Output: Delta Lake tables on S3, partitioned by `date`, with schema enforcement.

**Silver → Gold (Spark Batch, hourly)**:
- Driver earnings aggregated by day, week, month — Gold Delta table consumed by payroll system.
- Trip completion funnel by city/time — Gold table for BI dashboards (Tableau/Looker reading via Databricks SQL).
- Feature tables for ML: 30-day rolling trip stats per driver, per-zone demand features — consumed by Feature Store for surge pricing model training.

**Real-time fraud detection**: Silver events additionally stream to ClickHouse for sub-second analytical queries (is this driver/rider flagged? is this trip route anomalous?). ClickHouse serves the real-time API; the lake serves the historical training data.

**ML training**: Spark jobs read Gold feature tables directly from Delta Lake as Parquet into PyTorch DataLoaders or XGBoost. Feature Store (Feast or Tecton) provides point-in-time correct feature snapshots for training to prevent target leakage.

**Q30. "A data engineer reports that Silver table queries are taking 45 minutes for what should be a 2-minute job. The Silver table has 3 years of data with daily partitions. How do you diagnose and fix it?"**
A: Step-by-step diagnosis:

**Step 1 — Check if partition pruning is working**: is the query actually using the date partition, or scanning all 1,095 daily partitions? In Spark: `df.explain()` or check the `FilesRead` metric in the Spark UI. If all 1,095 partitions are being scanned for a query filtered on a specific date, partition pruning is broken — likely because the query is filtering on a derived column (`WHERE DATE(event_time) = '2024-01-15'`) rather than the partition column directly (`WHERE event_date = '2024-01-15'`).

**Step 2 — Check file count per partition**: `ls -l s3://lake/silver/events/year=2024/month=01/day=15/` — if there are thousands of small files (< 10MB each), the small files problem (Q9) is dominating. 3 years × 365 days × 200 files/day = 219,000 files total — at 50ms per S3 GET, file I/O overhead alone is 3 hours.

**Step 3 — Check Parquet statistics**: are min/max statistics being used for row group pruning? Check if the Parquet files have statistics with `parquet-tools meta` — no statistics means no row group skipping, even within files that were read.

**Fixes in order of impact**:
1. Fix the query predicate to use the partition column directly (zero cost, immediate fix).
2. Run Delta Lake `OPTIMIZE` on recent partitions to compact small files — target 1-10 files per partition.
3. If on bare Parquet (no table format): write a compaction Spark job, run and schedule it.
4. Convert Silver layer to Delta/Iceberg if not already — gain file statistics and transaction safety.
5. Tune Spark parallelism to match file count after compaction (too many tasks for few files wastes scheduler overhead).

**Q31. "Your company's data lake has grown to 5PB over 3 years. The data team reports that 80% of queries only touch the last 90 days of data. Storage costs are $500k/month. How would you reduce storage costs by 60%?"**
A: A 60% reduction on $500k/month = saving $300k/month. Approaches in priority order:

**Tiering old data to cheaper S3 storage classes (immediate, no query impact)**:
Data older than 90 days is rarely queried → move from S3 Standard ($0.023/GB) to S3 Standard-IA ($0.0125/GB, 45% cheaper) after 90 days, and to S3 Glacier Instant Retrieval ($0.004/GB, 83% cheaper) after 1 year. S3 Lifecycle policies automate this. Impact: if 80% of data is > 90 days old, tiering saves ~45-70% of storage cost on that portion. Estimated saving: ~$170-200k/month.

**Compression improvements**:
Audit current Bronze/Silver compression. Many older Bronze layers store gzip-compressed JSON or uncompressed CSV. Converting to Parquet + Zstd (5-10× compression on event data) during Silver transformation reduces ongoing storage growth. If Silver is already Parquet, verify Zstd is used (20-30% better compression than Snappy at similar speed). Estimated saving: significant on future data; limited on existing unless recompressed.

**Retention policy enforcement**:
Audit data with no business purpose older than 3 years. GPS ping data needed for real-time fraud but not for 3-year historical analysis? Delete after 6 months. Implement `Delta Lake VACUUM` to clean up old file versions (time travel data) after their 30-day retention window.

**Deduplicate Bronze data**:
Bronze is often the largest zone and may contain duplicates (retry logic, multiple Kafka consumers). A one-time deduplication Spark job on Bronze can reduce its size by 10-30%.

**Combined realistic saving**: storage tiering (45% of total cost) + retention policies (15%) + compression improvements (10%) = ~70% cost reduction, exceeding the 60% target.
