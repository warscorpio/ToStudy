# Time-Series Databases (InfluxDB, TimescaleDB) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is time-series data, and what makes it structurally distinct from general application data?**
A: Time-series data is a sequence of measurements or events where **time is the primary axis** — each data point is a value (or set of values) associated with a specific timestamp, and the temporal ordering and density of those measurements is what makes the data meaningful. It differs structurally from general application data in several ways: it is almost always **append-only** (new readings arrive continuously; past readings are rarely updated or deleted individually); it arrives at high, often regular frequency (thousands to millions of measurements per second across many sources simultaneously); individual data points are low-value but the **aggregate pattern over time is what matters** (a single CPU reading is meaningless; the trend over an hour reveals a leak); and queries are almost always **range-based** (what happened between time A and time B, for these sources) rather than point lookups by arbitrary non-time keys. These structural properties mean storage layouts, compression schemes, and query engines optimized for general application data handle time-series data poorly — and time-series databases are built specifically to exploit these structural regularities.

**Q2. Why do general-purpose relational databases struggle with time-series workloads specifically?**
A: Several compounding reasons: **Write throughput** — a high-cardinality time-series workload (thousands of devices writing every few seconds) produces insert rates that quickly saturate a single SQL primary's transaction throughput, and each insert must update multiple B-tree indexes, which becomes expensive under sustained high-write load. **Storage efficiency** — SQL databases store each row with full overhead (null column storage, transaction metadata, row headers), while time-series data's sequential, append-only nature allows far more aggressive compression (delta encoding on timestamps, run-length encoding on slowly-changing values) that general-purpose row-based storage doesn't exploit. **Query performance on time ranges** — a SQL table with billions of time-series rows requires either a full-table scan or an index range scan for time-range queries, but even with a good index, joining that with per-device filtering and per-window aggregation forces the query planner to handle what should be a simple sequential scan of one device's chronological data as a generic relational query — time-series databases partition and sort data by time specifically so that range scans are sequential disk reads, not random access. **Data lifecycle management** — retention policies (automatically expiring data older than N days/months) are a first-class operation in time-series databases; in SQL they require scheduled jobs, partition drops, or costly DELETE operations that generate table bloat and require subsequent vacuum cycles.

**Q3. What is the data model shared (in spirit) by most time-series databases?**
A: At the conceptual level, most time-series databases organize data around: a **metric or measurement name** (what is being measured — `cpu_usage`, `temperature`, `http_requests`); a **timestamp** (when the measurement was taken, typically at nanosecond or millisecond precision); **tags or labels** (indexed metadata identifying the source — `host=server-01`, `region=us-east`, `sensor_id=abc123` — used for filtering and grouping); and **fields or values** (the actual measured quantities — `value=87.3`, `user=45.1, system=12.7` — not indexed, just stored). The distinction between tags (indexed, used for filtering) and fields (not indexed, just values) is critical and is a common source of misdesign. Queries almost always filter on tags to select a subset of sources, then aggregate fields over a time range — the entire storage and indexing strategy is optimized for this specific access pattern.

## Section 2: Core Time-Series Concepts

**Q4. What is cardinality in a time-series context, and why is high cardinality a performance concern?**
A: Cardinality in time-series databases refers to the number of unique **time series** (unique combinations of metric name + tag values) — each distinct `{metric_name, tag_set}` combination is a separate time series, tracked independently. High cardinality means a very large number of unique tag combinations: if you tag each HTTP request with both `user_id` and `request_id`, and you have millions of users each making thousands of requests, the number of unique time series becomes enormous. This is a concern because most time-series databases maintain an **in-memory index** mapping tag combinations to their on-disk data locations, so the in-memory footprint of the tag index grows linearly with cardinality — a database with tens of millions of unique series can exhaust memory with index overhead alone, before considering the actual data. The practical rule: use tags only for attributes with **bounded, low cardinality** (host names, regions, service names — values that repeat across many data points); never use tags for attributes that are unique per data point (user IDs, request IDs, session IDs — use these as field values if needed, not tags).

**Q5. What is downsampling, and why is it a fundamental operation in time-series data management?**
A: Downsampling is reducing the resolution of historical data by aggregating fine-grained measurements into coarser summaries over time — for example, replacing 60 individual per-second CPU readings with one per-minute average, minimum, and maximum. It's fundamental because raw time-series data at high resolution accumulates very quickly (1,000 metrics × 1 write/second × 1 year = ~31.5 billion data points) and most analytical queries don't need the full per-second resolution for data that's weeks or months old — the trend over last month is well-represented by minute-level or hour-level summaries. Downsampling reduces storage by orders of magnitude while preserving the aggregate signal value of historical data, and queries over downsampled data are dramatically faster since they operate over far fewer points. Implementing downsampling as an automated, scheduled operation (rather than ad-hoc, one-time compaction) is a key feature of production-grade time-series database setups.

**Q6. What are retention policies, and how do they differ from simply deleting old rows in a SQL database?**
A: A retention policy is a first-class database-level configuration specifying how long data should be kept before being automatically expired and dropped — `RETAIN 30 DAYS` means any data older than 30 days is automatically removed, with no application-level code required. In most time-series databases, retention is enforced at the **storage partition level** — data is organized into time-bounded chunks (shards), and expiring old data is as simple as dropping an entire chunk file from disk, with no write amplification, no table bloat, no vacuum required. In a SQL database, deleting old time-series rows requires either expensive DELETE queries (updating B-tree indexes, generating dead rows, requiring subsequent VACUUM) or careful table partitioning by time (so old partitions can be dropped as units — this works well but requires deliberate design, it's not automatic). Retention as a first-class, automatic, cheap operation is one of the reasons time-series databases are genuinely better-suited to long-running data collection use cases than general-purpose SQL with manual cleanup jobs.

## Section 3: InfluxDB In Depth

**Q7. What is InfluxDB's data model, and what are its core concepts?**
A: InfluxDB organizes data around **measurements** (analogous to a table — a named collection of related time series, e.g., `cpu`, `memory`, `http_requests`); **tags** (indexed key-value string pairs identifying the source — `host`, `region`, `env` — stored as metadata and used for filtering/grouping); **fields** (the actual measured numeric or string values — `usage_user`, `usage_system` — not indexed, not available for efficient filtering); and **timestamps** (nanosecond-precision by default). A **series** is one unique combination of measurement + tag set — all data points with the same measurement and same tags form one time series. InfluxDB 2.x organizes data into **buckets** (named data stores with an associated retention policy), replacing the older concepts of databases and retention policies. Each bucket can have a default retention duration and multiple underlying time-structured storage shards that age out automatically.

**Q8. What is the InfluxDB line protocol, and why does its design matter for write throughput?**
A: The line protocol is InfluxDB's wire format for writing data — a compact, text-based format optimized for high-throughput writes: `<measurement>[,<tag_key>=<tag_value>...] <field_key>=<field_value>[,<field_key>=<field_value>...] [<timestamp>]`. For example: `cpu,host=server01,region=us-east usage_user=45.2,usage_system=12.1 1609459200000000000`. Its design matters because: it's human-readable and easily generated by scripts/agents without SDK overhead; it supports batch writes (multiple lines in one HTTP POST body) so clients can buffer and batch data points, dramatically reducing per-write HTTP overhead; and its explicit separation of tags (before the space) from fields (after the first space) lets InfluxDB parse and index only the tag portion without touching the field data during ingestion, keeping the write path fast. The Telegraf agent uses line protocol natively and handles batching, buffering, and retry automatically.

**Q9. What is Flux, InfluxDB's query language, and how does it differ from SQL-style querying?**
A: Flux is a functional, pipeline-based query language introduced in InfluxDB 2.x — queries are expressed as a chain of transformation functions rather than declarative SQL statements: `from(bucket:"metrics") |> range(start:-1h) |> filter(fn:(r) => r.host == "server01") |> mean()`. Each `|>` pipes the output of one transformation into the next, making the data flow explicit and composable. It differs from SQL in being purpose-built for time-series operations: it has first-class functions for time-windowing (`window(every:5m)`), downsampling (`aggregateWindow(every:1m, fn:mean)`), shape transformations (pivoting wide vs narrow), and cross-measurement joining. The trade-off: Flux's learning curve is steeper than SQL for analysts already fluent in SQL, and the functional style is more verbose for simple queries — which is part of why InfluxDB 3.x (InfluxDB's latest architecture based on Apache Arrow/DataFusion) is moving back toward SQL support alongside Flux.

**Q10. What are continuous queries (InfluxDB 1.x) and tasks (InfluxDB 2.x), and what role do they play?**
A: Continuous queries (1.x) and tasks (2.x) are scheduled, automated operations that run on a recurring schedule — the primary mechanism for implementing downsampling and data lifecycle management in InfluxDB. A task might run every hour, aggregating the last hour of per-second data into per-minute averages, and writing those summaries to a separate bucket with a longer retention policy — automatically maintaining a tiered storage strategy (raw high-resolution data retained for 7 days; per-minute aggregates retained for 90 days; per-hour aggregates retained indefinitely) without any application code or external cron jobs. This automation is one of the key operational advantages of a purpose-built time-series database over a general-purpose database where the same tiering logic requires scheduled ETL jobs.

## Section 4: TimescaleDB In Depth

**Q11. What is TimescaleDB and how does it extend Postgres?**
A: TimescaleDB is a Postgres extension that adds time-series-optimized storage and query capabilities on top of standard Postgres — a running TimescaleDB instance is a regular Postgres server with the `timescaledb` extension loaded, accessible via any standard Postgres client, driver, or tool. It introduces two main concepts: **hypertables** (a Postgres table declared as a hypertable is transparently partitioned by time into **chunks** — small, time-bounded sub-tables — behind an abstraction layer that makes it appear as one unified table to query writers) and **continuous aggregates** (materialized views that automatically update as new data arrives, pre-computing time-windowed aggregations for fast historical queries). The critical architectural choice: because TimescaleDB is a Postgres extension, it inherits the full Postgres SQL query language, all Postgres ecosystem tooling (pgAdmin, existing ORM integrations, Postgres backups, Postgres replication, pg_dump), and full ACID transactional semantics — making it the natural choice when a team is already deeply invested in Postgres and wants time-series optimization without abandoning their existing stack.

**Q12. What is a hypertable and how does chunking improve time-series performance?**
A: A hypertable is a TimescaleDB abstraction over a regular Postgres table — when you insert data into a hypertable, TimescaleDB transparently routes each row to the appropriate **chunk**: a smaller, internally-managed child table covering a specific time interval (e.g., one week). Each chunk is a separate Postgres table on disk, stored in time order, with its own indexes. This chunking improves performance in several specific ways: **insert performance** — all new data lands in the most recent chunk (the "hot" chunk), which is small, index-maintainable efficiently, and fits in memory, rather than inserting into one enormous table with a massive index; **query performance** — a time-range query that intersects only a few chunks touches only those chunks' data, skipping all others (chunk exclusion), rather than scanning the full table; **compression** — completed (older) chunks can be compressed independently without affecting the current hot chunk; **retention** — dropping old data is as cheap as dropping old chunk files, inheriting the same efficiency advantage as InfluxDB's shard-based retention.

**Q13. How do TimescaleDB continuous aggregates work, and how do they differ from standard Postgres materialized views?**
A: A continuous aggregate is a TimescaleDB-specific materialized view (created with `CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)`) that automatically and incrementally refreshes as new data arrives — unlike a standard Postgres materialized view, which requires a full recomputation on every manual `REFRESH MATERIALIZED VIEW` call. TimescaleDB tracks which chunks have changed and refreshes only the affected portions of the continuous aggregate incrementally, making the refresh cheap even for large datasets. This is the mechanism underlying automated downsampling: define a continuous aggregate computing per-minute averages from per-second raw data, set a refresh policy, and TimescaleDB maintains the downsampled view automatically — queries against the aggregate run against pre-computed data rather than re-aggregating raw rows on every query.

**Q14. What is TimescaleDB's native compression, and what compression ratios does it typically achieve?**
A: TimescaleDB implements columnar compression on older, "cold" chunks — data within a chunk is reorganized from row-oriented storage (one row per data point) to column-oriented storage (all values for one column stored contiguously), and then compressed with algorithms appropriate to each column's data type: delta encoding and delta-of-delta on timestamps (consecutive timestamps have small differences, which compress extremely well); simple-8b encoding on integer values; XOR compression on floating-point values (a technique derived from Gorilla, Facebook's time-series compression paper, where consecutive float values often differ only in a few bits). Typical compression ratios in real-world time-series workloads range from 20x to 100x — a dataset that occupies 100GB uncompressed commonly compresses to 1-5GB. This compression applies only to completed cold chunks (not the current hot chunk, which remains uncompressed for write performance), and the compression and decompression are transparent to queries — compressed chunks are readable via standard SQL without any application-side changes.

## Section 5: InfluxDB vs TimescaleDB — Choosing Between Them

**Q15. When should you choose InfluxDB over TimescaleDB?**
A: InfluxDB is the stronger choice when: the team has no existing Postgres investment and no need for relational joins or ACID cross-metric transactions; the primary use case is pure observability/metrics (infrastructure monitoring, IoT telemetry) where the tag/field/measurement model maps naturally to the data; write throughput is the primary concern (InfluxDB's custom TSM storage engine is optimized for high write throughput in a way a Postgres-based system doesn't quite match at extreme rates); the team wants a purpose-built, schema-light ingestion pipeline (the Telegraf agent ecosystem, line protocol, and native cloud integrations are very mature in the InfluxDB ecosystem); or the organization is using the InfluxDB cloud-native stack (InfluxDB Cloud, built on InfluxDB IOx/3.x with columnar storage) where cloud-managed operations eliminate the operational overhead of running Postgres at scale.

**Q16. When should you choose TimescaleDB over InfluxDB?**
A: TimescaleDB is the stronger choice when: the team is already deeply invested in Postgres (existing ORM integrations, DBAs who know Postgres, backup/monitoring infrastructure already in place — TimescaleDB adds time-series capability to the existing stack without a new system to operate); the time-series data needs to be **joined with relational data** (e.g., joining sensor readings with a device metadata table, or correlating metrics with deployment event records — pure InfluxDB is a specialized silo that doesn't join with external relational data easily); ad-hoc SQL queries from analysts or on-call engineers matter (the full Postgres SQL ecosystem, including window functions, complex GROUP BY, and JOINs, is available natively); or the data model doesn't fit cleanly into InfluxDB's tag/field/measurement model (TimescaleDB just uses regular SQL columns, making any tabular time-series data easy to model).

**Q17. Is there a meaningful write throughput difference between InfluxDB and TimescaleDB, and when does it matter?**
A: Yes, there's a real difference at extreme write rates: InfluxDB's TSM (Time-Structured Merge Tree) storage engine is purpose-built for high-frequency append writes, with a write-ahead log and in-memory cache that batch commits to disk, achieving millions of writes per second in clustered configurations. TimescaleDB, built on Postgres, inherits Postgres's write path — WAL, B-tree index updates per insert, and MVCC overhead — which is significantly more overhead per row than InfluxDB's purpose-built path. TimescaleDB compression and chunking reduce this gap substantially (inserts only update the small hot chunk's index, not the whole table's), and TimescaleDB handles tens to hundreds of thousands of inserts per second on well-tuned hardware, which is adequate for most workloads. The difference genuinely matters at very high IoT or infrastructure telemetry scale (hundreds of thousands to millions of distinct metrics writing sub-second intervals) — at that point, InfluxDB's write path is architecturally better suited. For most observability use cases with moderate write volumes, TimescaleDB's throughput is sufficient, and the SQL ecosystem benefits may outweigh the write-throughput gap.

## Section 6: When to Use a TSDB vs Alternatives

**Q18. The SQL vs NoSQL guide discussed Cassandra as suitable for time-series workloads. When should you choose Cassandra for time-series data versus a purpose-built TSDB?**
A: Cassandra's wide-column model (partition by device/metric ID, cluster by timestamp) does handle time-series patterns well and can achieve extremely high write throughput across a distributed cluster — it's a reasonable choice for time-series at very large scale when you're already operating Cassandra for other data needs (operational simplicity of one system), or when strong multi-datacenter replication with tunable consistency is a hard requirement. Purpose-built TSDBs (InfluxDB, TimescaleDB) are generally preferable when: the team isn't already running Cassandra (the operational complexity of a Cassandra cluster for a time-series-only use case is rarely worth it when a TSDB provides better ergonomics); downsampling, retention policies, and continuous aggregates are needed as first-class features (these require substantial application-level work in Cassandra); or efficient compression is a priority (Cassandra's compression is good but not as aggressive as TSDB-specific compression on time-series data). The practical summary: Cassandra is a viable time-series substrate at very large scale where its distributed replication model is already justified for other reasons; for pure time-series workloads, a purpose-built TSDB is almost always simpler to operate and more feature-complete.

**Q19. When might Elasticsearch be used for time-series data, and what are its trade-offs?**
A: Elasticsearch (and OpenSearch) is commonly used for log and event time-series data — particularly structured log records where **full-text search across arbitrary event fields** is as important as time-range aggregation. The ELK/EFK stack (Elasticsearch, Logstash/Fluentd, Kibana) is a widely deployed pattern for application log aggregation specifically because Elasticsearch's inverted-index model enables both time-range filtering and arbitrary field search in one system, with Kibana providing dashboards and visualizations. The trade-offs versus a purpose-built TSDB: Elasticsearch's storage is significantly less efficient for numeric metric data (it's optimized for full-text index structures, not the delta/XOR compression appropriate for monotonically increasing timestamps and slowly-changing numeric values); Elasticsearch is operationally complex (JVM heap tuning, shard sizing, index lifecycle management); and it lacks first-class downsampling and continuous aggregate features for metric-style data. Elasticsearch is the right tool when the data is log-structured (high variability, rich text fields, search is a primary operation) rather than metric-structured (numeric values per named measurement, aggregation is the primary operation).

**Q20. What is ClickHouse, and when is it a better choice than InfluxDB or TimescaleDB for time-series data?**
A: ClickHouse is a columnar OLAP database optimized for very fast analytical queries over large datasets — not specifically a time-series database, but its columnar storage and vectorized query execution make it extremely fast for time-range aggregation queries over billions of rows. It's a better choice than purpose-built TSDBs when: the workload is more analytical than operational (complex multi-dimensional aggregations, joins across many metrics, exploratory analysis by data engineers rather than real-time dashboards); query latency on large historical datasets is the primary concern rather than high-frequency write ingestion; the data is already flowing into a columnar format; or the team needs ad-hoc SQL with sub-second response over hundreds of billions of time-series events. ClickHouse is not as strong on the operational/ingestion side (no native retention policies, downsampling, or time-series-specific compression modes) and has a different operational profile than a purpose-built TSDB — it's a data warehouse for time-stamped events, not a purpose-built time-series collection and monitoring system. Cloudflare, Uber, and several large-scale observability platforms (Grafana's backend for some queries) use ClickHouse for the analytical tier of a multi-tier time-series architecture.

## Section 7: Common Time-Series Architecture Patterns

**Q21. What is the tiered storage pattern for time-series data, and how is it implemented?**
A: The tiered storage pattern maintains multiple representations of the same time-series data at different resolutions and different retention durations — raw high-resolution data for a short window (last 7 days), downsampled medium-resolution data for a medium window (last 90 days, per-minute aggregates), and coarse low-resolution summaries for long-term retention (per-hour or per-day aggregates, retained indefinitely or for several years). This matches the real usage pattern: recent data is queried at high resolution (debugging an incident from an hour ago requires per-second CPU readings); historical data is queried at lower resolution (trend analysis from 6 months ago needs only hourly averages, and the per-second data from then has no additional analytical value). Implementation: in InfluxDB, separate buckets with different retention policies and tasks (Q10) that continuously downsampled from the high-resolution bucket to lower-resolution buckets; in TimescaleDB, a hypertable with a short retention policy for raw data plus continuous aggregates (Q13) at multiple resolutions materialized into their own tables with longer retention.

**Q22. What is a write-ahead buffer and why is it important for time-series ingestion pipelines?**
A: A write-ahead buffer (or ingestion queue) is a durable intermediate layer — commonly Kafka, or simpler alternatives like a local agent buffer (Telegraf, Prometheus remote write) — that sits between data producers and the time-series database, absorbing spikes in write volume and providing durability against temporary database unavailability. Without a buffer, a spike in telemetry writes (a fleet of devices all sending data simultaneously after a network reconnect) can overwhelm the TSDB's write path directly; with a buffer, the TSDB ingests at a controlled, sustained rate while the buffer absorbs the spike. It also decouples the collection infrastructure from the storage infrastructure — a TSDB upgrade or restart doesn't cause data loss, since the buffer retains data until the database recovers and can catch up. Kafka is commonly used for this role in large-scale pipelines (multiple consumers can read the same stream for different purposes — storage, real-time alerting, stream processing); simpler local agent buffers suffice for smaller setups.

**Q23. How does alerting integrate with a time-series database, and what are the common patterns?**
A: Alerting on time-series data is typically implemented via one of: **threshold alerting** (if metric X for source Y exceeds threshold Z for more than N consecutive intervals, fire an alert); **anomaly detection** (if metric X deviates more than K standard deviations from its historical pattern for this time of day/week, fire an alert); or **rate-of-change alerting** (if metric X increases/decreases by more than P% over a time window, fire an alert). In InfluxDB 2.x, alerting is handled natively through checks (queries that evaluate alert conditions) and notification endpoints (where alerts are sent). In Prometheus-style setups (common with TimescaleDB via the Prometheus remote-write adapter), Alertmanager evaluates alert rules against queried data and routes alerts to notification channels. The key architectural consideration: alerting queries run continuously against the TSDB (often every minute or more frequently for high-urgency alerts), so the query load from alerting rules is non-trivial at scale — this is one motivation for pre-computing continuous aggregates, so alerting queries evaluate against materialized summaries rather than re-aggregating raw data on every evaluation cycle.

## Section 8: Operational Considerations

**Q24. What is the "cardinality explosion" problem, and what causes it in production?**
A: Cardinality explosion is when the number of unique time series in the database grows so large that the in-memory tag index exhausts available memory, causing severe performance degradation or outright failure. In production it's almost always caused by using **unbounded or high-cardinality values as tags** — the most common specific causes are: tagging with user IDs or customer IDs (millions of unique values); tagging with request IDs or trace IDs (unique per request — catastrophically high cardinality); dynamic tag values generated from application code (version strings that include commit hashes, pod names in Kubernetes with random suffixes); or tagging with IP addresses where a large rotating pool of IPs is used. Prevention requires team discipline in what gets tagged, enforced either by documentation/convention or by an ingestion validation layer that rejects tags exceeding a cardinality threshold. In InfluxDB specifically, cardinality is bounded at the bucket level and can be monitored via the cardinality endpoint; in Prometheus (which has the same issue) it's monitored via `prometheus_tsdb_symbol_table_size_bytes` and `prometheus_tsdb_head_series`.

**Q25. How should storage capacity be planned for a time-series workload?**
A: Estimate required storage as: `(metrics_count × write_frequency × bytes_per_point × retention_duration) / compression_ratio`. For example: 10,000 metrics × 1 write/second × 16 bytes/point × 7 days × 86,400 seconds/day ÷ 30 (compression ratio) ≈ 32GB. The key variables: **bytes per point** for uncompressed time-series data is typically 8–24 bytes depending on the precision and number of fields; **compression ratio** for time-series data is typically 10–100x depending on the data regularity (very regular sequences compress better than noisy data); and **write frequency** multiplied by the retention window dominates the calculation. Plan for the tiered storage pattern (Q21) to dramatically reduce long-term storage by downsampling — the 7-day raw data at 1s resolution might be 32GB, but the 90-day per-minute downsampled tier could be a fraction of that. Monitor actual compression ratios in production (they vary significantly from estimates) and plan for 30–50% headroom above the estimated raw storage to accommodate indexing overhead, write-ahead log buffering, and temporary double-capacity during compaction.

**Q26. What are the most important metrics to monitor for a production TSDB deployment?**
A: **Write throughput and write queue depth** — writes accumulating faster than the database can ingest signals impending backpressure; **cardinality** — the current number of active time series, with alerting when approaching the memory-constrained safe threshold; **compaction/merge lag** — both InfluxDB and TimescaleDB periodically compact/merge storage files; a growing backlog of uncompacted data indicates disk throughput pressure; **query latency by query type** — especially distinguishing fast queries (recent data, pre-aggregated continuous aggregates) from potentially slow queries (raw data scans over long historical ranges, which indicate queries that should be routed to the downsampled tier instead); **disk usage and growth rate** — relative to projected retention-policy-driven data expiry, to catch cases where retention policies are not expiring data as expected; and **replication lag** (for InfluxDB Enterprise cluster or TimescaleDB streaming replication) — replica reads returning stale data is a real operational concern for dashboards relying on replica reads.

## Section 9: Scenario-Based Questions

**Q27. "Your team is building a monitoring system for 100,000 IoT sensors, each sending temperature, humidity, and battery level every 5 seconds. Queries need current readings per sensor and historical trends over 30 days. How would you design the storage layer?"**
A: This is a clear TSDB use case — 100,000 sensors × 1 write/5 seconds × 3 fields = 60,000 inserts/second sustained. Choose a TSDB: InfluxDB for a pure metrics pipeline with no SQL requirements; TimescaleDB if the team is Postgres-centric or if sensor metadata (device type, owner, location) needs to be joined with readings. Design: a measurement/table with `sensor_id` as a tag (low enough cardinality at 100,000 for an index — this is at the upper boundary; above ~1 million unique series, cardinality becomes a concern), `location` and `device_type` as additional tags, and `temperature`, `humidity`, `battery_level` as fields. Retention policy: retain 7 days of raw 5-second data; use continuous aggregates (TimescaleDB) or tasks (InfluxDB) to materialize per-minute averages retained for 30 days, per-hour averages retained for 1 year. "Current reading per sensor" is a point lookup by sensor_id at the latest timestamp — in InfluxDB, a last-value query; in TimescaleDB, a `SELECT DISTINCT ON (sensor_id) ... ORDER BY sensor_id, time DESC` or a dedicated latest-values materialized view. "Historical trend over 30 days" routes to the per-minute aggregate tier, not the raw data.

**Q28. "A team is storing application performance metrics (request latency percentiles per endpoint, error rates, throughput) in Postgres with a simple table: `(endpoint, timestamp, p50, p95, p99, error_count, request_count)`. They report queries are increasingly slow as the table grows. Should they migrate to a TSDB, and if so which one?"**
A: This schema is already basically correct conceptually — it's modeling the data as time-series naturally — but Postgres without TimescaleDB doesn't exploit the time-series access patterns well: range queries on `timestamp` with a filter on `endpoint` are hitting a large B-tree index rather than sequentially scanning a chunk-partitioned table; there's no compression applied; and deleting old data requires DELETE + VACUUM cycles. Given they're already on Postgres, **TimescaleDB is the natural migration path** — it's an extension install, a `SELECT create_hypertable('metrics_table', 'timestamp')` conversion, and minimal application change. The result: existing queries run unchanged (same SQL, same Postgres connection), but now against a chunked hypertable that scans only the relevant time chunks rather than the full table, with compression applicable to cold chunks (likely 20–50x size reduction), and automatic retention policies replacing manual cleanup jobs. An InfluxDB migration would require re-modeling the data in the tag/field schema and rewriting all queries in Flux or InfluxQL — significantly more migration cost for no incremental benefit over TimescaleDB given the team is already running Postgres.

**Q29. "An engineer proposes adding `user_id`, `session_id`, and `request_id` as tags to a request-metrics time-series database to enable per-user, per-session, and per-request debugging via the TSDB. How would you respond?"**
A: Flag this as a cardinality explosion risk (Q24) — `user_id` with millions of users, `session_id` with tens of millions of sessions, and `request_id` being unique per request are all unbounded high-cardinality tag values. Adding these as tags would cause the in-memory series index to grow without bound as the application runs, eventually causing memory exhaustion and query/write degradation on the TSDB. The right architecture: **use the TSDB for aggregated metrics** (request rate, error rate, p95 latency per endpoint — low-cardinality tags like `endpoint`, `status_code`, `region`) where the TSDB's aggregation and downsampling features are genuinely valuable; route **per-request, per-user traces and logs to a distributed tracing system** (Jaeger, Tempo, Zipkin) and a log management system (Elasticsearch, Loki) respectively, which are specifically designed for high-cardinality event data rather than aggregated metrics. These two concerns — aggregate metrics and individual-event tracing — require different storage systems for good reason, and conflating them into one TSDB creates the worst of both worlds.

**Q30. "Your infrastructure monitoring stack uses Prometheus for metrics scraping and storage. The team reports that Prometheus is running out of disk space and queries over 30 days of data are too slow. How would you redesign the storage layer?"**
A: This is a common Prometheus scaling pain point — Prometheus's local storage is designed for short-term, high-resolution operational data (days to weeks), not long-term historical analytics. The solution is a **remote storage backend**: Prometheus's remote_write API allows it to forward all scraped metrics to a durable long-term store. TimescaleDB with the Prometheus remote storage adapter (or Promscale, TimescaleDB's purpose-built Prometheus adapter) is a natural fit — it stores all Prometheus metrics in a hypertable, applies chunk-based compression, supports Prometheus's native query language (PromQL) alongside SQL, and handles the retention/downsampling concerns. InfluxDB with the Prometheus remote write integration is an equally valid choice if the team prefers InfluxDB's ecosystem. Keep Prometheus's local storage short (7–14 days, for fast operational queries) and have Prometheus remote-write all data to the long-term backend in parallel, routing dashboard queries over long time ranges directly to the long-term backend. This Prometheus-as-collector + TSDB-as-long-term-store pattern is the standard scaling path for Prometheus-based monitoring at production scale.

**Q31. "Product wants a feature showing each user's 'activity graph' — the number of actions they've taken per day over the last year — displayed on their profile page. Should this be stored in a TSDB or the application's existing Postgres database?"**
A: This is a case where the TSDB impulse should be resisted — the cardinality concern (Q4) applies immediately: `user_id` is the metric identifier, and with millions of users, each with a daily time-series, the series count is user_count × metrics_per_user, which can be very high and grows with the user base. A TSDB would require `user_id` as a tag (high cardinality) and provide aggregation features (downsampling, continuous queries) that aren't actually needed here — the granularity is daily (not sub-second), the retention is one year (not massive), and the queries are simple per-user lookups, not aggregate analytics across many users simultaneously. A simple SQL table in Postgres (`user_id, date, action_count`) with a composite index on `(user_id, date)` handles this perfectly well — the data volume is small (365 rows/user/year), the queries are simple point lookups by user_id and date range, and the data naturally joins with the user table and other relational data. Not every time-stamped data access pattern needs a TSDB — the right signal for TSDB is high write frequency, high cardinality at the measurement level (not the series level), or aggregation-heavy queries at scale.

## Quick Reference Table

| Dimension | InfluxDB | TimescaleDB |
|---|---|---|
| Base architecture | Purpose-built TSDB (TSM storage engine) | Postgres extension (hypertables + chunks) |
| Query language | Flux (pipeline-based) / InfluxQL / SQL (v3) | Full SQL (Postgres) |
| Write throughput | Higher (purpose-built write path) | High (chunked hot table); lower at extreme rates |
| Compression | TSM columnar; ~10-100x on time-series data | Columnar on cold chunks; ~20-100x |
| Relational joins | Not native | Full Postgres SQL joins |
| Downsampling | Tasks + multi-bucket | Continuous aggregates |
| Retention policies | Bucket-level, automatic | Retention policies via extension |
| Ecosystem | Telegraf, Chronograf, Grafana, InfluxDB Cloud | Full Postgres ecosystem, Grafana, any PG tool |
| Cardinality limit | In-memory series index (millions of series feasible) | Postgres index (similar concern applies) |
| Best fit | Pure metrics/telemetry; Telegraf agent pipeline; extreme write rates | Postgres shops; need SQL joins; mixed relational + TS data |

| Signal | Right storage choice |
|---|---|
| High-frequency numeric metrics, fixed schema | InfluxDB or TimescaleDB |
| Need SQL joins with relational tables | TimescaleDB |
| Log/event data with full-text search | Elasticsearch / OpenSearch |
| Very large-scale analytical queries over TS data | ClickHouse |
| Already on Cassandra; multi-DC replication critical | Cassandra time-series schema |
| Small daily/weekly aggregates per user | Regular Postgres |
| Per-request or per-user traces | Distributed tracing (Jaeger, Tempo) |

**Tip for interviews:** What separates strong candidates on time-series databases specifically: (1) understanding **cardinality as the central operational concern** — being able to identify immediately when a proposed tag would cause cardinality explosion (user IDs, request IDs, session IDs as tags) and explaining concretely why the in-memory index makes this a memory problem, not just a "best practice" (Q4, Q24, Q29); (2) being able to **articulate the tiered storage pattern** — raw high-resolution data with short retention, downsampled aggregates with longer retention — as the standard production architecture rather than treating raw retention as a simple "how many days" decision (Q21, Q5–6); (3) knowing **when not to use a TSDB** — resisting the impulse to reach for InfluxDB or TimescaleDB for any time-stamped data (per-user activity counts in Postgres, individual request traces in a tracing system) and being able to justify a simpler choice (Q31, Q29); (4) being precise about **the InfluxDB vs TimescaleDB trade-off** — not just "TimescaleDB is Postgres-based" but what that concretely implies for joins, SQL ecosystem, write throughput, and migration cost (Q15–17, Q28); and (5) connecting TSDB decisions back to the broader storage decision framework — recognizing that the choice of TSDB vs Cassandra vs ClickHouse vs Elasticsearch depends on which specific properties of the workload (write throughput, query flexibility, full-text search, analytical aggregations) dominate (Q18–20).
