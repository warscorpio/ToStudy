# Hot/Warm/Cold Storage Tiering — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is storage tiering and what fundamental economic principle drives it?**
A: Storage tiering is the practice of placing data on different storage media based on how frequently it is accessed — using faster, more expensive storage for data accessed often (hot), and slower, cheaper storage for data accessed rarely (cold). The economic principle: access frequency and storage cost are inversely correlated in almost every real-world dataset. A small fraction of data ("the hot set") receives the vast majority of access; the large remainder receives little or none. If you stored everything on fast, expensive storage, you'd pay premium prices for data nobody reads. If you stored everything on cheap, slow storage, your active workloads would be intolerably slow. Tiering exploits this natural access distribution to optimize the cost-performance trade-off: pay premium prices only for the small fraction that justifies it, and pay commodity prices for the rest.

**Q2. What is the "access frequency distribution" and why does it make tiering so effective?**
A: Empirically, data access follows a power law (Pareto/Zipf-like distribution): roughly 20% of data receives 80% of access, and within that, 20% of 20% receives 80% of 80% of access — the distribution is heavily skewed toward a small "hot" subset. For a data system: recent orders are queried constantly; last month's orders occasionally; last year's orders rarely; four-year-old orders almost never. The access frequency drops off sharply as data ages, aligns with business cycles, or represents inactive users/objects. This sharp dropoff is what makes tiering so valuable: moving the 80% of data that receives 20% of access from hot ($X/GB) to cold ($X/10 /GB) reduces storage cost by ~64% (80% of data at 10% of the cost) while only slightly increasing latency for that rarely-needed 20% of requests.

**Q3. What are the three canonical tiers — hot, warm, and cold — and what characterizes each?**
A: The tiers represent points on the latency/cost spectrum:

**Hot storage**: sub-millisecond to low-millisecond access latency. Highest cost per GB. Maximum I/O throughput. Data accessed multiple times per second or per minute — the "working set" of active computations. Technologies: in-memory (DRAM/Redis), NVMe SSDs, high-performance SAN. Examples: current user sessions, live game state, financial order books, real-time dashboards powered by recent data.

**Warm storage**: low-millisecond to tens-of-milliseconds access latency. Moderate cost per GB. Moderate throughput. Data accessed daily or weekly — recent but not real-time. Technologies: SATA SSD, HDD RAID arrays, lower-tier cloud block storage, or frequently-accessed object storage classes (S3 Standard). Examples: last 30 days of orders, recent analytics, recent media uploads, recent application logs.

**Cold storage**: hundreds of milliseconds to seconds (or even hours for archive retrieval) access latency. Very low cost per GB. Low or pay-per-retrieval throughput. Data accessed rarely or never in normal operations — compliance archives, historical backups, rarely-queried analytical history. Technologies: HDD-based object storage with infrequent access pricing (S3 Standard-IA, S3 Glacier, Azure Archive). Examples: years-old transaction records, regulatory archives, raw data before it was processed into a warehouse, old software versions.

**Q4. What is the distinction between a "tier" as a storage technology and as a data classification?**
A: An important nuance: "hot/warm/cold" are data classification concepts (based on access frequency), not inherent properties of storage technologies. A piece of data can transition from hot to cold as it ages, while remaining on the same underlying storage system — the tier describes the data's access pattern, and ideally that classification drives which physical storage medium it lives on. In practice, tiering can be implemented at multiple layers simultaneously: the OS page cache is the hottest tier (in-memory), NVMe SSD is the next tier, HDD is the next, object storage is the next, archival (Glacier/tape) is the coldest — a real system often spans several of these simultaneously, with different data at different layers at any given time.

## Section 2: Storage Technologies Per Tier

**Q5. What are the storage technologies available for hot tier, and how do they compare?**
A:
- **DRAM (in-memory)**: fastest possible — ~100ns access latency, ~50-100 GB/s bandwidth, ~100k-1M IOPS. Extremely expensive (~$5-15/GB for server RAM vs ~$0.02-0.10/GB for SSD). Volatile — contents lost on power failure without persistence mechanisms (Redis AOF/RDB, Memcached has no persistence). Used for: session caches, hot database buffer pools, real-time computation state.
- **NVMe SSD (via PCIe)**: 100-500 μs access latency, 5-15 GB/s sequential bandwidth, 500k-1M+ IOPS. Currently ~$0.10-0.30/GB (enterprise) to $0.05-0.10/GB (consumer). Non-volatile — data persists across power cycles. Used for: primary database storage (PostgreSQL on NVMe, Cassandra hot tier), OS volumes, real-time analytics engines (ClickHouse on NVMe).
- **SATA SSD**: 50-200 μs access latency, 500 MB/s-1 GB/s bandwidth, 50k-100k IOPS. ~$0.04-0.08/GB. Lower throughput than NVMe but significantly cheaper. Good for warm-tier data that needs faster-than-HDD access but doesn't justify NVMe prices.

**Q6. What storage technologies serve the warm and cold tiers?**
A:
**Warm tier technologies**:
- **HDD (Hard Disk Drive)**: 5-15ms access latency (seek + rotation), 100-250 MB/s sequential, 100-200 random IOPS. ~$0.015-0.025/GB for enterprise. Sequential reads are reasonably fast; random reads are slow (mechanical seek). Suitable for data accessed in large sequential batches (log processing, nightly analytics, media serving) but poor for random-access workloads.
- **Cloud block storage (gp3 EBS, Azure Premium SSD)**: SSD-backed cloud volumes with configurable IOPS. AWS gp3 EBS: $0.08/GB/month, up to 16k IOPS, 1 GB/s. Managed, no hardware operations — at the cost of higher per-GB price than raw hardware.
- **S3 Standard (object storage)**: 5-100ms latency (first byte, over network), effectively unlimited throughput (parallelized across requests). ~$0.023/GB/month. The default "warm" object storage tier — suitable for data accessed several times a month.

**Cold tier technologies**:
- **S3 Standard-IA (Infrequent Access)**: same durability and performance as S3 Standard, but 45% cheaper storage cost ($0.0125/GB/month) with a per-GB retrieval fee ($0.01/GB retrieved). Makes economic sense when data is read rarely (< once a month).
- **S3 Glacier Instant Retrieval**: $0.004/GB/month storage, $0.03/GB retrieval, millisecond access latency (same as S3 Standard when retrieved). For data accessed once a quarter.
- **S3 Glacier Flexible Retrieval**: $0.0036/GB/month, but retrieval takes 1-12 hours (standard) or 3-5 minutes (expedited at $0.03/GB). For true archives accessed once a year or less.
- **S3 Glacier Deep Archive**: $0.00099/GB/month (~$1/TB/month), retrieval within 12 hours. Cheapest cloud storage option — regulatory compliance archives, disaster recovery cold copies.
- **Tape (LTO)**: $0.002-0.005/GB in large volumes, effectively zero per-GB retrieval cost (manual process to locate and mount tape). Retrieval latency: hours to days. Still used for hyperscale archival where cloud archive storage is too expensive at volume (some enterprises with multi-exabyte archives).

## Section 3: Cloud Storage Classes and Lifecycle Policies

**Q7. How do AWS S3 storage classes map to the tiering model, and what should guide class selection?**
A: AWS S3 offers a progression of storage classes that map directly to the hot/warm/cold spectrum:

| S3 Class | $/GB/month | Retrieval cost | Retrieval latency | Min storage | Use case |
|---|---|---|---|---|---|
| S3 Standard | $0.023 | $0.00 | Milliseconds | None | Hot/Warm: frequently accessed |
| S3 Intelligent-Tiering | $0.023 + $0.0025/1k objects | $0.00 | Milliseconds | None | Unknown or variable access patterns |
| S3 Express One Zone | ~$0.16 | Very low | Single-digit ms | None | Ultra-low latency, single AZ |
| S3 Standard-IA | $0.0125 | $0.01/GB | Milliseconds | 30 days | Infrequent: monthly access |
| S3 One Zone-IA | $0.01 | $0.01/GB | Milliseconds | 30 days | IA data in one AZ only |
| S3 Glacier Instant | $0.004 | $0.03/GB | Milliseconds | 90 days | Quarterly access |
| S3 Glacier Flexible | $0.0036 | $0.01-0.03/GB | 1min-12hrs | 90 days | Annual access |
| S3 Glacier Deep Archive | $0.00099 | $0.0025/GB | 12-48hrs | 180 days | Regulatory 7+ year retention |

Selection guide: if retrieval frequency is unknown → Intelligent-Tiering (it moves objects automatically). If access is predictably monthly → Standard-IA (predictable savings). If access is annual or compliance-only → Glacier Flexible or Deep Archive. The key economic calculation: `break-even retrieval frequency = (Standard cost - IA cost) / retrieval cost per GB`. For Standard vs Standard-IA: break-even = ($0.023 - $0.0125) / $0.01 = 1.05 retrievals/month — if you retrieve the data less than ~once a month, Standard-IA is cheaper.

**Q8. What are S3 Lifecycle Policies and how do they automate tiering?**
A: S3 Lifecycle Policies are rules attached to an S3 bucket or prefix that automatically transition objects to cheaper storage classes or delete them after a specified number of days since creation or last modification:

```json
{
  "Rules": [{
    "ID": "tiering-rule",
    "Status": "Enabled",
    "Filter": {"Prefix": "data/events/"},
    "Transitions": [
      {"Days": 30,  "StorageClass": "STANDARD_IA"},
      {"Days": 90,  "StorageClass": "GLACIER_IR"},
      {"Days": 365, "StorageClass": "GLACIER"},
      {"Days": 2555, "StorageClass": "DEEP_ARCHIVE"}
    ],
    "Expiration": {"Days": 3650}
  }]
}
```

This policy transitions event data from Standard → Standard-IA after 30 days → Glacier Instant Retrieval after 90 days → Glacier after 1 year → Deep Archive after 7 years → deletion after 10 years. The policy runs automatically — no application code or operational intervention needed once configured. This is the standard mechanism for data lake cost optimization described in the data lake guide's storage cost section.

**Q9. What is S3 Intelligent-Tiering and when should you use it instead of explicit lifecycle rules?**
A: S3 Intelligent-Tiering monitors each object's access frequency and automatically moves it between access tiers (Frequent, Infrequent, Archive Instant, Archive, Deep Archive) at no retrieval cost, charging a small per-object monitoring fee ($0.0025 per 1,000 objects/month). It's designed for data with unknown or unpredictable access patterns — where you can't reliably define lifecycle rules because access frequency varies by object rather than uniformly by age.

Best suited for: heterogeneous data lakes where some files are accessed frequently and others rarely, without a predictable time-based pattern (a catalog of 10 million videos where 1% are viral and 99% are rarely viewed — the 1% can't be predicted in advance by age alone). Less suited for: data with a predictable time-based access decay (most event log analytics) where explicit lifecycle rules are cheaper (no monitoring fee) and more predictable. A common anti-pattern: applying Intelligent-Tiering to very small objects (< 128KB) where the monitoring fee exceeds the potential storage savings — for small objects, explicit lifecycle rules are almost always cheaper.

**Q10. How do GCS (Google Cloud Storage) and Azure Blob Storage tiering compare to S3?**
A: All three major clouds offer equivalent tiering models with similar pricing tiers and comparable cost-performance profiles, though naming conventions differ:

| AWS S3 | Google Cloud Storage | Azure Blob Storage |
|---|---|---|
| S3 Standard | Standard | Hot |
| S3 Standard-IA | Nearline ($0.01/GB/month) | Cool ($0.015/GB/month) |
| S3 Glacier Instant | — | — (Cold, $0.0045/GB) |
| S3 Glacier Flexible | Coldline ($0.004/GB/month) | Archive ($0.00099/GB/month) |
| S3 Glacier Deep Archive | Archive ($0.0012/GB/month) | Archive |

GCS "Nearline" requires minimum 30 days storage; "Coldline" requires 90 days; "Archive" requires 365 days — similar to S3's minimum storage duration requirements. Both GCS and Azure offer lifecycle management equivalent to S3 Lifecycle Policies. The choice between clouds for archival storage is typically driven by existing cloud provider (minimize egress costs) rather than price differences between equivalent tiers.

## Section 4: Application-Level Tiering

**Q11. How does application-level tiering work in a typical web application, and what layers does it span?**
A: Application-level tiering stacks multiple caching and storage layers, each representing a hotter tier:

```
Request arrives
    ↓
L1: In-process cache (Guava/Caffeine, bounded per JVM)  → sub-ms, ~100MB per instance
    ↓ miss
L2: Distributed cache (Redis/Memcached)                 → ~1ms, GB-TB scale
    ↓ miss
L3: Database (PostgreSQL on NVMe)                       → ~5-50ms
    ↓ (for old/rarely-accessed data)
L4: Archive table / object storage (S3)                 → 100ms-seconds
    ↓
Origin / recompute
```

Each layer is hotter (faster, more expensive, smaller) than the next. Data flows down on write (writing to DB, optionally warming cache) and up on read (cache miss propagates down until a hit, then populates all warmer layers on the way back up). The application typically doesn't expose this complexity to the client — from the client's perspective, all requests hit "the API," and the tiering is internal.

**Q12. How do relational databases implement internal storage tiering, and what is a "buffer pool"?**
A: A database's buffer pool (also called buffer cache or shared buffers in PostgreSQL) is an in-memory cache of frequently-accessed data pages from the on-disk database files — the hottest tier of the database's own internal storage hierarchy. The database keeps the most recently and frequently accessed 8KB or 16KB pages in the buffer pool (often allocated as 10-50% of total server RAM), serving reads from memory (~100ns) without disk I/O when the page is present. On a buffer pool miss, the page is read from the on-disk storage tier (NVMe or HDD). The buffer pool's eviction policy (typically LRU or a variant) determines which pages are "hot" (kept in memory) vs "cold" (evicted to make room). This is the database engine's own implementation of the hot/warm tiering concept, entirely transparent to the application's SQL queries. PostgreSQL's `shared_buffers` parameter, MySQL's `innodb_buffer_pool_size` — these configure the size of this hottest tier.

**Q13. How does Elasticsearch implement hot-warm-cold architecture for time-series data?**
A: Elasticsearch's Index Lifecycle Management (ILM) is one of the most explicit implementations of the three-tier model for a distributed system. For a time-series use case (application logs, metrics):

**Hot nodes**: NVMe SSD-backed nodes handling current write traffic and frequent read queries. New indices land here. Highest cost per node, highest indexing throughput. Data age: 0-7 days (configurable).

**Warm nodes**: HDD or SATA SSD-backed nodes for read-only, less-frequently-queried data. ILM automatically moves indices from hot to warm nodes after the configured rollover age, marking them read-only (`index.blocks.write: true`) and optionally force-merging segments (reducing file count and memory usage). Data age: 7-30 days.

**Cold nodes**: Lower-spec HDD nodes (or partially mounted from object storage using Elasticsearch's Searchable Snapshots feature) for rarely-queried data. Further segment merging. Data age: 30-90+ days.

**Frozen tier** (Elasticsearch 7.12+): Indices fully stored as snapshots on object storage (S3/GCS), with only metadata in memory. Queries trigger on-demand partial retrieval from object storage — very slow (seconds to minutes) but near-zero cost per GB. Data age: 90+ days, compliance retention.

**Delete phase**: ILM deletes indices older than the configured retention period automatically.

The ILM policy configuration specifies age thresholds, rollover triggers (max index size or age), and actions for each phase — entirely automated once configured, a production-grade implementation of data-age-based tiering.

**Q14. How does Apache Cassandra implement tiering, and what is the "cold keyspace" pattern?**
A: Cassandra doesn't have a native built-in hot/warm/cold tiering mechanism equivalent to Elasticsearch's ILM, but several patterns are used:
- **Storage class per table/keyspace**: configure tables with different compaction strategies and bloom filter false positive rates (more memory for hot tables, less for cold) to optimize memory/storage trade-offs per access pattern.
- **Separate cluster topology**: physically separate nodes with NVMe SSDs serve as the "hot" Cassandra cluster (recent data), while HDD-backed nodes form the "warm" cluster (older data). Application code routes reads to the appropriate cluster based on the query's time range.
- **DSE (DataStax Enterprise) tiered storage**: the commercial Cassandra distribution supports tiered storage where hot data lives on SSDs and cold data on HDDs or object storage, managed by the DSE engine.
- **TTL-based expiry + separate archive**: Cassandra TTLs automatically tombstone and eventually delete old rows; application code concurrently writes data to the analytical lake (S3/Parquet) before the TTL-driven deletion, providing a cold tier without keeping old rows in Cassandra indefinitely.

## Section 5: Tiering Policies and Automation

**Q15. What are the primary signals used to make tiering decisions — time-based vs access-frequency-based?**
A: Two fundamental tiering approaches, each with different complexity and accuracy:

**Time-based (age-based) tiering**: data is moved to a colder tier after it reaches a certain age, regardless of actual access frequency. Simple to implement and reason about (S3 Lifecycle Policies, Elasticsearch ILM are both time-based). Works well for data that has a predictable access frequency decay — most time-series data (event logs, transaction records) is accessed frequently when recent and rarely as it ages. Risk: may move still-actively-accessed older data to cold storage, or keep rarely-accessed recent data on hot storage.

**Access-frequency-based tiering**: data is moved based on measured access patterns (how often it was read in the last N days). More accurate — data that's actually being accessed stays hot regardless of age; data that's never accessed moves cold even if it's recent. More complex to implement (requires tracking per-object or per-row access counts, which itself has storage/performance overhead). S3 Intelligent-Tiering and database LRU buffer pool eviction are access-frequency-based. Works well for heterogeneous catalogs where access patterns aren't age-correlated (viral video platforms, ML model registries).

Hybrid approaches (most production systems): primary tier movement is time-based (age thresholds are simple and predictable), with an access-frequency override that can promote data back to hot tier on a cache miss from cold storage (reactive warming).

**Q16. What is "data promotion" and "data demotion" in tiering systems?**
A: **Demotion**: moving data to a colder (cheaper, slower) tier — triggered by age threshold, eviction from a cache, or manual lifecycle rule execution. The common path as data ages. In S3 Lifecycle, demotion is automatic via transition rules. In a database buffer pool, demotion is LRU eviction when a new page must be loaded.

**Promotion**: moving data back to a hotter (faster, more expensive) tier upon access — triggered by a read that hits cold storage. The key question: should a cold-tier access warm/hot the data automatically (eager promotion) or leave it cold (no promotion)? 

- **Eager promotion**: first access to cold data copies it to hot tier immediately. Subsequent accesses are fast. Risk: a single anomalous access to archival data promotes it to expensive hot storage unnecessarily (if a compliance report accesses 1TB of 5-year-old data once a year, eagerly promoting all of it wastes hot-tier capacity).
- **Lazy/conditional promotion**: count accesses over a window; promote only after N accesses in M days. More accurate but requires access tracking infrastructure.
- **No promotion**: cold data stays cold regardless of access frequency — any access to cold data always pays the cold retrieval cost. Simplest operationally; correct choice when cold accesses are genuinely rare and non-repeating (e.g., regulatory audit access to archive data).

## Section 6: Tiering in Distributed Database Systems

**Q17. How does Google Bigtable implement tiered storage internally?**
A: Bigtable separates compute (tablet servers holding in-memory memtables and managing reads/writes) from storage (Colossus, Google's distributed filesystem). Internally:
- **Memtable (hottest)**: recent mutations held in tablet server RAM — sub-millisecond access, bounded by server memory.
- **Minor compaction to SSTables**: periodically flushed to Colossus as immutable SSTable files — millisecond access via Colossus cache + local SSD caching.
- **Major compaction**: multiple SSTables merged into one, reading and rewriting from Colossus — slower background operation.
- **Colossus**: distributed filesystem with its own internal caching (RAM + SSD) that transparently accelerates frequently-accessed SSTable blocks.

The tiering is transparent to the application — a read always hits the appropriate level of this internal hierarchy automatically. The key insight: Bigtable's architecture (and its descendant HBase) follows the LSM-tree pattern where writes go to the hottest tier (memtable) and are promoted/compacted to colder persistent tiers, while reads check each tier from hottest to coldest until they find the requested data.

**Q18. How does the LSM-tree (Log-Structured Merge-tree) implement a natural tiered storage hierarchy?**
A: The LSM-tree is a storage data structure that directly encodes hot/warm/cold tiering in its architecture. Data flows from hot to cold as it ages and compacts:

```
Write → MemTable (RAM, hot)
         ↓ flush when full
       L0 SSTables (SSD, warm, small files)
         ↓ compact when L0 file count threshold reached
       L1 SSTables (SSD, larger files, sorted)
         ↓ compact when L1 size exceeds threshold
       L2 SSTables (SSD or HDD, even larger)
         ↓
       L3+ SSTables (HDD or object storage, very large, cold)
```

Each level is progressively larger, slower, and cheaper. Recent data stays in L0/L1 (SSD, fast random read via bloom filters + sparse index). Old data compacts down to L3+ (HDD, slower but cheap). A read checks each level from L0 down until it finds the key — recent data found quickly in hot levels; old data requires checking more levels. Systems using LSM trees: RocksDB (and every database built on it: TiKV, MyRocks, CockroachDB's original storage engine), LevelDB, Cassandra (SSTables without explicit level compaction by default, uses Size-Tiered Compaction).

## Section 7: Cost Modeling

**Q19. How do you build a cost model to justify a tiering architecture to stakeholders?**
A: A tiering cost model compares current single-tier cost against tiered cost:

**Step 1 — Inventory data by access tier**:
Measure or estimate what fraction of data falls into each tier based on age or access frequency:
- Hot (last 7 days): 5% of total data, 70% of total access
- Warm (8-90 days): 15% of total data, 25% of total access
- Cold (91+ days): 80% of total data, 5% of total access

**Step 2 — Calculate current single-tier cost**:
If all 100TB is on S3 Standard: `100TB × 1024 GB/TB × $0.023/GB = $2,355/month`

**Step 3 — Calculate tiered cost**:
```
Hot  (5TB  on S3 Standard):     5,120 GB × $0.023      = $118/month
Warm (15TB on S3 Standard-IA):  15,360 GB × $0.0125    = $192/month
Cold (80TB on S3 Glacier):      81,920 GB × $0.0036    = $295/month

Retrieval costs (cold, 5% of 80TB accessed monthly):
  4,096 GB × $0.01/GB retrieval                         = $41/month

Total tiered cost: $118 + $192 + $295 + $41             = $646/month
```

**Step 4 — Savings and payback**:
Monthly saving: $2,355 - $646 = $1,709/month (72.6% cost reduction)
Engineering cost to implement: ~$20k one-time (lifecycle policy setup, application changes)
Payback period: $20k / $1,709/month ≈ 12 months

This kind of quantified model is what interviewers expect when you mention "use cold storage for old data" — the ability to put numbers on the trade-off.

**Q20. What are the hidden costs in tiering that the simple storage price comparison misses?**
A: Several costs are easy to miss:
- **Minimum storage duration charges**: S3 Standard-IA, Glacier classes all have minimum storage duration (30-180 days depending on class). If you transition an object to Glacier and then delete it after 30 days, you're still charged the 90-day minimum. Tiering rapidly-changing short-lived data to cold storage can cost more than keeping it on Standard due to these minimums.
- **API call costs**: S3 Glacier retrievals have per-request costs beyond the per-GB fee. Mass retrieval of many small objects can accumulate significant per-request charges.
- **Egress / retrieval latency impact on user experience**: cold retrieval latency (up to 12 hours for Glacier Flexible) can be business-impactful if a user needs old data unexpectedly — "restore from archive" workflows add operational overhead and user-facing latency that has a non-zero business cost.
- **Data re-hydration for reprocessing**: when a batch job needs to reprocess 1 year of archived data (e.g., to backfill a new metric), retrieving it all from Glacier at once can cost as much as several months of S3 Standard storage.
- **Monitoring and transition overhead**: Intelligent-Tiering monitoring fees add up for tables with many small objects. S3 Lifecycle PUT/DELETE requests for transitions have small per-request costs that become significant at billions of objects.

## Section 8: Tiering for Specific Workloads

**Q21. How is tiering applied in a time-series database, and what is the "retention policy" pattern?**
A: Time-series data (metrics, IoT sensor readings, application telemetry) has the most predictable access-frequency decay of any data type: recent data is queried constantly (real-time dashboards, alerting); data from last month is queried occasionally (trend analysis); data from last year is queried rarely (capacity planning, anomaly baseline). This clean decay makes time-based tiering highly effective. Retention policy pattern:
- **Hot tier (last 14 days)**: stored in the time-series database itself (InfluxDB, TimescaleDB, Prometheus) on SSD. Full resolution, sub-millisecond query latency.
- **Warm tier (15-90 days)**: downsampled (e.g., 1-second raw metrics downsampled to 1-minute averages, reducing data volume 60×) and stored in the same or a larger HDD-backed cluster. Millisecond query latency on aggregated data.
- **Cold tier (90+ days)**: further downsampled (1-minute to 1-hour) and exported to Parquet files on S3 or directly to a data warehouse. Queries take seconds but are rare enough that this is acceptable.
- **Archive (1+ years)**: S3 Glacier or deep archive. Only accessed for multi-year trend reports or regulatory audits.

Prometheus implements this via "recording rules" (pre-aggregation) and federation; InfluxDB and TimescaleDB have built-in downsampling policies; Thanos and Cortex (Prometheus extensions for long-term storage) explicitly implement this multi-tier pattern using object storage as the cold tier.

**Q22. How is tiering applied in a content delivery / media storage system?**
A: Media files (videos, images, audio) have access patterns dominated by content popularity — a small set of popular/recent content drives the vast majority of traffic, while the long tail of older or niche content sits mostly unused:

**Hot tier**: popular content served via CDN edge caches (covered in the CDN guide — CDN as a hot tier for static content). The CDN's edge nodes are effectively the hottest tier; the CDN's origin (S3 or a media server) is the warm tier from the CDN's perspective.

**Warm tier**: recently uploaded or moderately popular content on S3 Standard. CDN cache misses fetch from here.

**Cold tier**: content older than 6-12 months or with below-threshold play counts transitions to S3 Standard-IA via Intelligent-Tiering or explicit lifecycle rules. CDN misses on cold content incur higher retrieval latency (milliseconds from IA, still acceptable for a video start) and retrieval cost.

**Archive tier**: content that has never been accessed or that is a raw master file (pre-transcoded, very large, stored for re-encoding purposes) goes to S3 Glacier. A user requesting archived content triggers a restore workflow (hours to days) rather than immediate delivery.

Access-frequency-based tiering via S3 Intelligent-Tiering is especially valuable here — you can't know in advance which content will go viral vs which will be watched once and never again.

**Q23. How is tiering applied in a multi-tier database architecture for a SaaS product with many customers?**
A: A SaaS product serving customers with different subscription tiers or usage patterns may implement tiering at the customer level:

**Active enterprise customers** (pay highest rates, heavy usage): data on the fastest storage (NVMe SSD PostgreSQL, dedicated read replicas, aggressive read caching). Query latency SLA: < 100ms for 99th percentile.

**Active SMB customers** (moderate usage): shared PostgreSQL cluster on SSD. Query latency SLA: < 500ms.

**Inactive / churned customers** (no active subscription, data retained for compliance or reactivation): data archived from the live database to a cheaper store — either a separate PostgreSQL instance on HDD (warm), or fully exported to Parquet on S3 (cold). If the customer reactivates, data is restored from the archive tier. This "customer-level archival" pattern reduces the live database size significantly (often 30-50% of customer accounts are inactive at any time), improving active database performance by reducing table sizes and improving cache hit rates.

## Section 9: Failure Modes and Operational Concerns

**Q24. What happens when the wrong data gets moved to cold storage, and how do you recover?**
A: Cold-tier mistakes fall into two categories:

**Premature demotion** (data moved to cold too early, still actively needed): a query hits cold storage, waits for retrieval (hours for Glacier Flexible), and the user experience degrades severely. Fix: initiate a restore/promotion from cold to warm immediately (S3 Glacier restore to S3 Standard takes 1-12 hours; plan accordingly). Prevent: audit access patterns before setting lifecycle thresholds; use Intelligent-Tiering instead of hard-coded lifecycle rules for heterogeneous access patterns; add a read path that gracefully handles cold retrieval latency (queue the request, notify the user, fulfill asynchronously).

**Missing minimum retention** (data deleted from cold tier before required retention period): a regulatory audit requires 7 years of retention, but lifecycle rules deleted objects at year 5. Fix: immediate escalation — this is a compliance failure. Prevent: enforce retention policies via S3 Object Lock (WORM — Write Once Read Many) which prevents deletion or modification regardless of lifecycle rules or IAM permissions, for defined retention periods; test lifecycle rules in a non-production account before applying to compliance data.

**Q25. How do you monitor a tiered storage system and what metrics matter most?**
A: Effective monitoring of a tiered system requires visibility at each tier boundary:

**Cost metrics**: per-tier storage cost, retrieval cost, and transition cost — tracked monthly to verify savings match projections and catch unexpected access patterns (unusually high cold retrieval cost indicates premature demotion or unexpected access to archived data).

**Access distribution metrics**: what fraction of reads are served from each tier (hot/warm/cold hit ratio). A high cold-tier read rate means your hot/warm thresholds are misconfigured or your data access patterns changed.

**Retrieval latency per tier**: P50/P99 latency for reads from each tier. Cold-tier reads should be rare; if P99 spiked on cold retrievals, diagnose whether it's expected (a scheduled report) or unexpected (a code bug hitting old data).

**Promotion/demotion rate**: how much data is moving between tiers per day — unusually high rates suggest thrashing (data is being promoted and demoted repeatedly, adding cost without benefit).

**"Surprise cold retrieve" alerting**: alert on any unexpectedly large retrieval from Glacier or Deep Archive (e.g., > 100GB in one operation) — likely a code bug, a misconfigured report, or an unexpectedly wide query range.

## Section 10: Scenario-Based Questions

**Q26. "Your PostgreSQL database is 8TB on NVMe SSD. 6TB of that is orders data, 90% of which is older than 1 year and almost never queried. Database performance is degrading as tables grow. Design a tiering solution."**
A: Three-phase approach:

**Phase 1 — Partition the orders table by year** (prerequisite):
Implement PostgreSQL table partitioning by `order_date` (range partitioning by year). This doesn't move data yet but enables detaching old partitions cleanly. Schema change is backward-compatible — application SQL against the parent table still works.

**Phase 2 — Archive partitions older than 1 year to S3**:
Export partitions `orders_2021`, `orders_2022`, `orders_2023` to Parquet files on S3 (using `COPY TO` or a data export tool like `pg_dump` with Parquet conversion). Store in S3 Standard-IA (accessed maybe once a month for compliance queries). Then detach those partitions from the PostgreSQL parent table and drop them from the live database. PostgreSQL table size drops from 8TB to ~2TB (current year + some previous months).

**Phase 3 — Federated query path for historical data**:
Route queries with date ranges falling in archived years to Athena/DuckDB querying the S3 Parquet files. Implement in the application layer: an API endpoint that checks the date range and queries either PostgreSQL (recent) or Athena (historical). Or use PostgreSQL foreign data wrappers (FDW) with parquet_s3_fdw — recent queries remain PostgreSQL queries; historical queries transparently go to S3 Parquet via FDW.

**Result**: PostgreSQL at ~2TB instead of 8TB — better buffer pool hit rate, faster vacuum operations, smaller B-tree indexes, lower backup time. Historical query latency increases (Athena: seconds instead of milliseconds) but for rare historical queries this is acceptable. Storage cost for 6TB of archived orders on S3 Standard-IA vs NVMe SSD: ~$75/month vs ~$600/month (assuming $0.10/GB/month SSD) = $525/month saving.

**Q27. "You're designing storage for a video platform with 50M videos. 1% are viral and constantly viewed; 99% are rarely accessed after the first 30 days. Walk through the tiering architecture."**
A: Content access pattern is highly heterogeneous (access frequency not age-correlated) — some 5-year-old viral videos still get millions of views; some uploaded yesterday get zero. This is the Intelligent-Tiering use case, not explicit lifecycle rules.

**Storage tiers for video content**:
- **CDN edge cache (hottest)**: top ~0.1% of content (500 videos) cached at every CDN PoP globally. These are videos receiving millions of daily plays — CDN hit rate for these is ~99%.
- **CDN origin / S3 Standard (warm)**: transcoded video files for the viral 1% (500k videos) on S3 Standard — CDN misses fetch from here. Also newly uploaded content before its access pattern is known.
- **S3 Intelligent-Tiering (mid-tier)**: the bulk of content — 49.5M videos. Intelligent-Tiering monitors each video's access frequency and moves it between Frequent/Infrequent/Archive tiers automatically. A video that goes viral months after upload automatically returns to Frequent tier; a video that drops off moves to Infrequent.
- **S3 Glacier Instant Retrieval (cold)**: raw master files (pre-transcoded, typically 3-5× larger than the transcoded files). Retrieved only when re-encoding is needed for a new format (AV1, 8K). Queried perhaps once in the video's lifetime.

**Access path for a rarely-accessed video**:
CDN miss → S3 Standard-IA fetch → CDN caches the first few segments → video plays. User sees ~100-200ms added latency for the first segment (S3 IA retrieval) vs ~20ms (S3 Standard). This is imperceptible for a video that takes 1-2 seconds to start anyway.

**Cost estimate for 50M videos at ~500MB average transcoded file**:
- Total storage: 50M × 500MB = 25PB
- Without tiering (all S3 Standard): 25PB × 1024 × 1024 GB/PB × $0.023 = ~$589M/month (clearly unrealistic — this shows why tiering is non-optional at this scale)
- With Intelligent-Tiering + Glacier for masters: average blended cost ~$0.003-0.005/GB ≈ $75-125M/month. Still large, but within range of major platform economics at this scale.

**Q28. "Your team is building a compliance archive for financial transaction records. Regulations require 7-year retention with the ability to produce any specific transaction record within 24 hours of a regulator requesting it. How do you design this?"**
A: Compliance archival has three requirements that tension each other: long retention (7 years), cost efficiency (7 years of all transactions is large), and retrieval SLA (24 hours, which eliminates some options but opens others).

**Storage choice**: S3 Glacier Flexible Retrieval ($0.0036/GB/month) with "standard" retrieval tier (3-5 hours). For a 24-hour SLA, 3-5 hour retrieval is acceptable — there's time to initiate the restore job when a request comes in, verify the restored data, and deliver it with hours to spare. S3 Glacier Deep Archive (12-48 hours) is borderline — only acceptable if the restore is initiated immediately upon regulatory request.

**Data organization**: Parquet files partitioned by date (year/month/day) and account/entity ID, stored in a dedicated compliance bucket with S3 Object Lock in Compliance Mode (WORM — prevents deletion by anyone, including root account) for 7 years. This satisfies regulatory tamper-proof requirements that lifecycle rules alone don't.

**Catalog**: a lightweight catalog table in RDS PostgreSQL (not Glacier — must be fast) mapping `(transaction_id, date, account_id)` → `(s3_key, parquet_row_group)`. When a regulator requests transaction X, the catalog is queried in milliseconds to find the exact Glacier object, then the restore is initiated for that specific object only (not the entire partition) — minimizing restore time and retrieval cost.

**Restore workflow**: automated pipeline — receive request → lookup in catalog → initiate S3 Glacier restore (`POST /?restore`) → poll for restore completion (typically 3-5 hours) → generate signed S3 URL for the restored copy → deliver to requester. The restored temporary copy expires after 7 days (restore copies are temporary and free after the 7-day window, returning to Glacier).

**Cost estimate for $0.0036/GB for 7 years of transactions**: for a bank doing 1M transactions/day at 1KB each: 1M × 365 × 7 = 2.555B records = ~2.5TB. `2,560 GB × $0.0036 = $9.2/month` — virtually negligible. This explains why compliance archival is never a cost concern relative to the retrieval SLA and tamper-proof requirements.
