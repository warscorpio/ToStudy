# Rebalancing Partitions — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Rebalancing Is Necessary

**Q1. What is partition rebalancing and when does it become necessary?**
A: Rebalancing is the process of redistributing data and request load across nodes in a distributed system after a change in cluster topology. It becomes necessary whenever the assignment of partitions to nodes no longer reflects what you want — which happens in four situations:
- **Node addition**: A new node joins and should take on a share of the data and traffic currently handled by existing nodes.
- **Node removal (planned)**: A node is decommissioned and its partitions must be redistributed to remaining nodes before it shuts down.
- **Node failure (unplanned)**: A node crashes and its partitions must be taken over by surviving nodes to remain available.
- **Skew correction**: The initial partition distribution has become uneven over time — some nodes carry disproportionately more data or traffic than others.

The goal of rebalancing is always the same: even distribution of data and load across all available nodes, with minimal disruption to ongoing reads and writes.

**Q2. What are the three properties a good rebalancing strategy must satisfy?**
A: Any rebalancing strategy is evaluated on:
- **Minimal data movement**: Only the data that *must* move (to achieve even distribution) should move. Moving more than necessary wastes network bandwidth, I/O, and time — and increases the risk window during which the cluster is in a partially rebalanced, potentially degraded state. The theoretical minimum is 1/N of all data when adding the Nth node.
- **Even distribution after rebalancing**: Data and request load should be approximately equal across all nodes after rebalancing completes. A strategy that rebalances quickly but leaves one node with 3× the data of others has only partially solved the problem.
- **Continued availability during rebalancing**: Reads and writes must continue to be served while data is moving. Rebalancing is not a "take the system offline and reshuffle" operation — it must be incrementally online.

**Q3. What is the difference between rebalancing and resharding?**
A: They address different layers of the partitioning scheme:
- **Rebalancing**: Reassigning existing partitions to different nodes. The total number of partitions is unchanged; their ownership changes. This is the routine operation triggered by node additions, failures, and removals.
- **Resharding**: Changing the total number of partitions — splitting partitions into more pieces or merging them into fewer. This is a more invasive operation, required when the current partition count is too low (each partition has grown too large) or too high (too many tiny partitions create overhead). Resharding often requires a migration period and, in some systems, downtime or careful dual-write strategies.

In many production systems (Elasticsearch, Kafka, DynamoDB), the partition/shard count is fixed at creation time — making resharding a rare, painful, and sometimes impossible operation. This is a deliberate trade-off: the inflexibility of a fixed count enables much simpler rebalancing.

## Section 2: The Naive Approach — Hash Mod N and Why It Fails

**Q4. What is the "hash mod N" partitioning strategy and how does it work?**
A: The simplest partitioning scheme: assign a key to a node by computing `hash(key) mod N`, where N is the current number of nodes. Node 0 owns keys where the hash is divisible by N, Node 1 owns the remainder 1, and so on. It distributes keys uniformly (assuming a good hash function) and is trivial to implement.

Example with 3 nodes and a hash space:
```
hash("user:alice") = 42  →  42 mod 3 = 0  →  Node 0
hash("user:bob")   = 17  →  17 mod 3 = 2  →  Node 2
hash("user:carol") = 33  →  33 mod 3 = 0  →  Node 0
```

**Q5. Why does hash mod N fail catastrophically when nodes are added or removed?**
A: Because adding or removing even one node changes N, which changes the mapping for nearly every key. When N changes from 3 to 4:

```
hash("user:alice") = 42  →  42 mod 3 = 0  (was Node 0)
                         →  42 mod 4 = 2  (now Node 2)  ← MOVED

hash("user:bob")   = 17  →  17 mod 3 = 2  (was Node 2)
                         →  17 mod 4 = 1  (now Node 1)  ← MOVED

hash("user:carol") = 33  →  33 mod 3 = 0  (was Node 0)
                         →  33 mod 4 = 1  (now Node 1)  ← MOVED
```

Going from N to N+1 nodes causes approximately `(N−1)/N` of all keys to map to a different node. For a 3→4 transition: ~75% of all data must move. For a 10→11 transition: ~91% of all data must move. This is the antithesis of "minimal data movement" — the entire dataset must essentially be redistributed on every topology change, which makes hash mod N unusable for any system where nodes are added or removed dynamically.

**Q6. What is the "thundering herd" or cascade failure risk with hash mod N rebalancing?**
A: When N changes and 75–91% of data must move, the rebalancing traffic floods the network simultaneously — every node is both a source and destination for data migration. This competes directly with ongoing client traffic for the same network bandwidth and I/O capacity. In a system already under production load, this can:
- Saturate network links, causing timeouts for real client requests
- Overwhelm disk I/O on source and destination nodes
- Trigger false-positive failure detection (nodes appear unresponsive due to overload, not actual failure)
- Initiate further rebalancing in response to the false failures — a cascade

This cascade pattern — rebalancing overhead causes apparent failures, which triggers more rebalancing, which causes more overhead — is a real production failure mode that has taken down clusters. It's why the "minimal data movement" requirement is not just about efficiency; it's about operational safety.

## Section 3: Consistent Hashing

**Q7. What is consistent hashing and what problem does it fundamentally solve?**
A: Consistent hashing (Karger et al., 1997) is a partitioning scheme designed so that adding or removing a node requires moving only `1/N` of all keys — the theoretical minimum. It achieves this by decoupling key assignment from the specific value of N, so a change in N only affects the keys that were assigned to the changed node.

The key idea: instead of `hash(key) mod N` — which depends on N — consistent hashing maps both keys and nodes to positions on a fixed-size "ring" (typically `[0, 2^32)`). A key's owner is determined not by arithmetic modulo N, but by finding the nearest node on the ring — a relationship that changes for only a small fraction of keys when one node's position is added or removed.

**Q8. How does the consistent hash ring work mechanically?**
A: The ring is a circular hash space from 0 to 2^32 − 1. Each node is assigned a position on the ring by hashing its identifier (e.g., `hash("node_ip:port")`). Each key is also hashed to a position. A key's owner is the first node encountered when traveling clockwise around the ring from the key's position:

```
Ring positions (simplified to 0–100):

         0/100
          │
    A(10) ○
                    ○ B(40)
          
    D(90) ○
                    ○ C(65)

Key at position 25 → clockwise to B(40) → owned by B
Key at position 55 → clockwise to C(65) → owned by C
Key at position 75 → clockwise to D(90) → owned by D
Key at position 95 → clockwise to A(10) (wraps) → owned by A
```

Adding a new node E at position 50: only keys between B(40) and E(50) — those that were going clockwise to C(65) — now stop at E instead. All other keys are unaffected. Removing node C: only C's keys (between B(40) and C(65)) move to D(90). Everything else is unchanged.

**Q9. What is the data movement cost when adding or removing a node in consistent hashing?**
A: Adding a node: the new node takes over the keys between itself and its predecessor on the ring. On average, this is `1/N` of all data — exactly the theoretical minimum. No other node loses or gains data.

Removing a node: the removed node's keys move to its successor on the ring. Again, `1/N` of data moves, minimum. No other node is affected.

This is the exact property that hash mod N lacks — a single node change affects only the adjacent neighborhood of keys, not the entire keyspace. The `1/N` bound is achieved because the ring distributes keys uniformly and each node "owns" approximately `1/N` of the ring.

**Q10. What is the virtual node (vnode) problem with basic consistent hashing, and how does it fix itself?**
A: Basic consistent hashing assigns each physical node one position on the ring. This creates two problems:
- **Uneven distribution**: If node positions happen to cluster (or if the number of nodes is small), some nodes may own much larger arc segments than others, receiving disproportionate data and traffic.
- **Lopsided rebalancing**: Adding one physical node relieves exactly one existing node (its ring predecessor) of its keys. The new node's entire load comes from that one predecessor — an uneven transfer that doesn't spread the load relief across the cluster.

**Virtual nodes** (vnodes) fix this: each physical node is assigned *multiple* positions on the ring (e.g., 150–256 vnodes per physical node in Cassandra). Each vnode is a separate entry on the ring, but all vnodes for a physical node ultimately store data on that physical machine.

Effect of vnodes:
- **Even distribution**: 150 random positions per node produce a much more uniform distribution of arc lengths — the Law of Large Numbers smooths out clustering.
- **Even rebalancing**: When a new physical node joins, it acquires vnodes from many existing nodes rather than from just one predecessor. Every existing node gives up a proportional share.
- **Heterogeneous hardware**: A more powerful node can be assigned more vnodes, receiving a proportionally larger share of data — capacity weighting without changing the algorithm.

**Q11. Does consistent hashing solve hotspots caused by skewed access patterns?**
A: No — and this is a critical limitation worth stating clearly. Consistent hashing distributes keys uniformly across nodes based on the hash of the key. But if certain keys receive dramatically more requests than others (a "hot key"), hashing them to a node still concentrates that traffic on one node. No partitioning scheme based on key hashing can solve access-pattern skew — the problem is that the access frequency is bound to the key, and the key maps to one node.

Examples of hot key scenarios:
- A celebrity user's profile (100M reads/day vs. 100 reads/day for an average user)
- A trending topic in a social network
- A partition holding the current month's data in a time-series system

Solutions to hotspots are application-level, not partitioning-level: adding a random suffix to hot keys and spreading them across N partitions (requiring reads to query all N and merge), caching at a layer above the database, or sharding the hot key's value itself across nodes.

## Section 4: Fixed Number of Partitions

**Q12. What is the fixed-number-of-partitions strategy and how does it differ from consistent hashing?**
A: Rather than assigning keys directly to nodes, this strategy creates a fixed, large number of logical partitions upfront — far more than the current node count — and assigns multiple partitions to each node. The mapping is:

```
key  →  hash(key) mod P   (P = total number of partitions, fixed)
partition  →  node           (assignment, changes during rebalancing)
```

Rebalancing means moving whole partitions between nodes — the key-to-partition mapping never changes, only the partition-to-node assignment. This is fundamentally different from consistent hashing, which works by changing which node "owns" a range of the hash ring.

Example: 1,000 partitions across 10 nodes = 100 partitions per node. Adding 10 more nodes: move ~50 partitions from each existing node to new nodes → each node ends up with ~50 partitions. No key ever changes which partition it belongs to — only which node that partition lives on.

**Q13. What are the advantages of fixed-number-of-partitions over consistent hashing?**
A: Several operational advantages:
- **Whole-partition moves**: Data always moves as complete partitions, never as individual key ranges. This is simpler to implement, easier to track progress on, and simpler to abort and retry.
- **Stable key routing**: The key-to-partition mapping (`hash(key) mod P`) never changes — clients can cache it forever. Only the partition-to-node directory needs to update during rebalancing.
- **Proportional rebalancing**: By controlling exactly which partitions move, the system can balance load proportionally — new nodes take exactly the right number of partitions.
- **Used by**: Elasticsearch (shards per index, fixed at creation), Riak (number of "ring partitions" fixed at cluster creation), Couchbase, Voldemort.

**Q14. What is the key operational risk of fixed-number-of-partitions?**
A: Choosing the wrong P at creation time — and being unable to change it without a full data migration:
- **Too few partitions**: If data grows beyond what P partitions can represent (e.g., P=10 and you have 10 nodes — each node is one partition with no room to rebalance), the system can't expand without resharding. Partition sizes become very large, making rebalancing slow.
- **Too many partitions**: Each partition has metadata overhead — an Elasticsearch cluster tracking 10,000 shards has meaningful overhead in the cluster state, and routing tables grow. Very small partitions can make coordination overhead dominate.

The dilemma: at cluster creation time, you must predict the total data volume and node count years in advance. Elasticsearch's default of 5 shards per index (fixed) has bitten many teams — either hitting the ceiling and needing a reindex, or creating too many shards and hitting performance limits. The mitigations (rollover indices, shrink/split APIs) exist precisely because the fixed count is operationally painful.

## Section 5: Dynamic Partitioning

**Q15. What is dynamic partitioning and what problem does it solve over fixed-count approaches?**
A: Dynamic partitioning allows the number of partitions to grow and shrink automatically in response to data volume, rather than being fixed at creation time. The rules are simple:
- **Split**: When a partition exceeds a configured size threshold (e.g., 10 GB in HBase), it is split into two roughly equal partitions. One half stays on the current node; the other may be transferred to a different node to balance load.
- **Merge**: When adjacent partitions shrink below a minimum threshold (e.g., after bulk deletes), they can be merged into a single partition.

This solves the fixed-count dilemma: the partition count naturally adapts to the dataset. A cluster starting with 1 GB of data has few partitions; the same cluster at 1 TB has orders of magnitude more, with no manual reconfiguration. Used by HBase (HRegions), Google Bigtable, RethinkDB, and MongoDB's auto-sharding.

**Q16. What is the "initial bootstrapping" problem with dynamic partitioning and how is it mitigated?**
A: When a database starts from scratch with dynamic partitioning, it begins with a single partition on a single node. All writes go to that one node until the partition grows large enough to split. This means:
- Write throughput is bounded by one node until the first split
- The first node is a hot spot for the entire bootstrap phase
- For a large initial data load, the cluster is effectively single-node for a significant period

Mitigations:
- **Pre-splitting**: Most systems (HBase, MongoDB) allow operators to configure an initial number of empty partitions at creation time, distributed across nodes from the start — bypassing the single-partition bootstrap phase.
- **Guided splits**: Specifying an initial set of split points (if the key distribution is known in advance) seeds the partition map with a good starting distribution.

The bootstrapping problem is why dynamic partitioning is most natural for systems that start small and grow organically, but requires deliberate pre-splitting for large initial data loads.

**Q17. What is the difference between range-based and hash-based partitioning in the context of dynamic partitioning?**
A: Dynamic partitioning is most natural with **range-based partitioning** (keys divided into ordered ranges; each partition owns a contiguous key range). Split points are simply the midpoint of the range, and the new partition inherits the upper half. Adjacent ranges can be merged trivially.

With **hash-based partitioning**, dynamic splitting is harder: hash ranges aren't ordered by any meaningful key property, so identifying a split point requires knowing the distribution of actual hash values. Consistent hashing with vnodes is the hash-based equivalent of dynamic partitioning — adding a vnode is functionally a split of the ring arc.

Most systems that advertise "dynamic partitioning" (HBase, Bigtable, RethinkDB) use range-based partitioning precisely because splits and merges are natural on ordered ranges. The downside of range partitioning is that sequential key access patterns (e.g., time-series data where all writes share a timestamp prefix) can create hot partitions — a trade-off dynamic partitioning doesn't eliminate.

## Section 6: Automatic vs. Manual Rebalancing

**Q18. What is the core argument for and against automatic rebalancing?**
A:
- **For automatic**: In a large cluster, manually directing which partitions move to which nodes is operationally impractical. Automatic rebalancing responds immediately to node failures and additions without human intervention, reducing time-to-recovery and operator burden.
- **Against automatic**: Automatic rebalancing can make the wrong decision at the worst time. The classic failure: a node becomes slow due to a network hiccup or temporary I/O saturation. The system, detecting it as degraded, automatically starts moving its partitions to other nodes. The rebalancing traffic adds more load to the already-stressed node, making it actually fail. Other nodes absorb the transferred partitions and their load, becoming stressed themselves — triggering further rebalancing. This cascade can take down a healthy cluster.

Riak's documentation explicitly warns about this and recommends treating the cluster's suggested rebalancing plan as a proposal to be human-approved before execution, not an action to take automatically.

**Q19. What is the recommended operational pattern for rebalancing in production?**
A: A middle ground between fully automatic and fully manual: **auto-generate, human-approve**:
1. The system continuously monitors partition distribution and, when it detects imbalance beyond a threshold, generates a rebalancing plan — which partitions would move from which node to which node.
2. The plan is surfaced to operators as a proposed action (in a dashboard, CLI, or alerting system).
3. An operator reviews and approves the plan, triggering execution.

This approach gives operators visibility and veto power over rebalancing, while automating the calculation of *what* to move. It also enables scheduling rebalancing during off-peak hours rather than reacting immediately in the middle of a traffic spike.

Elasticsearch, Cassandra, and MongoDB all support both modes — automatic rebalancing is available but operators in high-stakes environments often disable it and run rebalancing explicitly.

**Q20. What is rebalancing throttling and why is it non-negotiable in production?**
A: Rebalancing involves copying potentially terabytes of data across the network. Without throttling, this rebalancing traffic can consume the majority of available network bandwidth, directly competing with production request traffic and causing latency spikes or timeouts for clients.

Throttling limits the rate at which rebalancing data is transferred — e.g., "use no more than 50 MB/s per node for rebalancing." This makes rebalancing take longer but keeps it from disrupting production traffic. Every production distributed storage system exposes a throttle setting:
- Cassandra: `stream_throughput_outbound_megabits_per_sec`
- Elasticsearch: `indices.recovery.max_bytes_per_sec`
- HBase: throttled via HDFS bandwidth management

The right throttle value is a function of your available bandwidth, production traffic baseline, and how urgently you need the rebalancing to complete. A node failure typically justifies a higher throttle (faster recovery); a routine node addition can afford a lower throttle.

## Section 7: Hotspots and Skew

**Q21. What is partition skew and what are its two forms?**
A: Partition skew is an uneven distribution across partitions — one partition (and the node hosting it) handles disproportionately more than its fair share. It appears in two forms:
- **Data skew (size skew)**: Some partitions hold far more data than others. This happens with range partitioning when writes are not uniformly distributed across the key range — e.g., time-series data where "today's" partition grows rapidly while historical partitions are static.
- **Access skew (load skew)**: Some partitions receive far more reads or writes than others, even if data sizes are similar. This happens with hash partitioning when certain keys are intrinsically more popular — a celebrity's user ID, a viral event's hashtag, or the current time bucket in a metrics system.

Both forms can overwhelm a single node regardless of how well the rebalancing algorithm works — the problem is in the write/read pattern, not the partition assignment.

**Q22. What is the "celebrity problem" and how is it typically handled?**
A: The celebrity problem (also called the "hot key" problem) occurs when one key — such as a famous person's ID in a social network — receives orders of magnitude more traffic than average keys. In a partitioned system, that key maps to one partition on one node, concentrating all that traffic on that single node regardless of how many other nodes exist.

Application-level mitigations:
- **Key salting**: Append a random suffix (e.g., 0–99) to the hot key, spreading it across 100 partitions: `celebrity_id:42`, `celebrity_id:73`, etc. Writes pick a random suffix; reads must query all 100 suffixed versions and merge. This distributes write load but adds read complexity.
- **Dedicated partition or caching tier**: Identify hot keys explicitly (through monitoring) and serve them from a separate cache (Redis, Memcached) rather than the underlying partitioned store.
- **Read replicas for hot partitions**: Detect hot partitions and spin up additional read replicas specifically for those partitions, independently of global rebalancing.

None of these are automatic — they all require application-level awareness of which keys are hot, which is why monitoring for hot partitions is a critical operational concern.

**Q23. Why does sequential key design cause partition hotspots in range-partitioned systems?**
A: Range-partitioned systems assign adjacent keys to the same partition. If writes are mostly sequential — all keys share a timestamp prefix, auto-incrementing IDs, alphabetically clustered usernames — then all writes concentrate on the partition holding the current end of the range. Other partitions are cold (historical, read-rarely). This creates both data skew (the current partition grows rapidly) and access skew (the current partition absorbs all writes).

Fixes:
- **Hash prefix**: Prepend a hash of the key to distribute writes across ranges: `hash(timestamp)[0:2] + timestamp` — destroys the ability to range-scan by time but distributes writes.
- **Compound key reversal**: For time-series data, reverse the timestamp or use a "salted time bucket" so writes distribute across many current-range partitions.
- **Explicit hot partition splitting**: Monitor partition sizes and split the active partition aggressively when it's growing rapidly, distributing new writes across two partitions immediately after the split.

This is the fundamental trade-off in range partitioning: natural ordering enables efficient range scans, but natural ordering also means sequential writes concentrate on the leading partition.

## Section 8: Trade-offs and Decision Making

**Q24. When should you choose range partitioning vs. hash partitioning?**
A:
- **Choose range partitioning** when: your queries frequently scan a contiguous range of keys (e.g., all records for a date range, all events for a user in a time window). Range partitions allow the scan to read from one or few partitions rather than all partitions. HBase, Bigtable, DynamoDB's sort key, and Cassandra clustering columns are all range-partitioned at the second level. Accept the cost: sequential write hotspots require explicit mitigation.
- **Choose hash partitioning** when: your queries are mostly point lookups (single key) or random reads, and scan across the full key range is not needed. Hash partitioning gives uniform distribution with no hotspot risk for writes — at the cost of making range scans impossible (the range is randomly distributed across all partitions). Consistent hashing variants are used here.
- **Compound approaches**: Many systems combine both — hash on the first key component (distributing across nodes) and range on the second (enabling range queries within a node). DynamoDB's partition key (hashed) + sort key (range) is the canonical example.

**Q25. When would you choose fixed-count partitions vs. dynamic partitioning?**
A:
- **Fixed-count** (Elasticsearch, Riak, Kafka) when: you can reasonably predict the data scale at creation time, you want the simplicity of a stable routing table, and you can tolerate a pre-sizing mistake through careful initial sizing or a later migration. Operationally simpler; rebalancing is just partition assignment changes.
- **Dynamic partitioning** (HBase, Bigtable, MongoDB auto-sharding) when: data volume is highly unpredictable, you need the system to adapt automatically without upfront sizing decisions, and range-based key access patterns are important. Operationally more complex (split and merge logic must be correct); bootstrapping requires pre-splitting for large initial loads.

**Q26. How do you reason about the right number of replicas vs. partitions?**
A: These are independent axes of the design:
- **Replication factor (RF)**: How many copies of each partition exist. RF=3 means each partition lives on 3 nodes. Replication provides fault tolerance and read throughput (if you allow replica reads). Adding replicas increases storage cost but improves availability; it does not increase write throughput.
- **Partition count (P)**: How many partitions the data is divided into. More partitions enable more parallel writes and reads, and finer-grained rebalancing. But each partition has metadata overhead, and too many partitions with too-small sizes can hurt performance.

They compound: `total data copies = data_size × RF`. `partitions per node = P / N`. For a system with 100GB of data, RF=3, and N=10 nodes: total storage consumed = 300GB; each node holds ~30GB. Increasing P (without increasing N) just means more, smaller partitions on the same nodes — more rebalancing granularity, same storage.

## Section 9: Scenario / System Design Style Questions

**Q27. "You're running an Elasticsearch cluster with 3 nodes and 5 shards per index. Traffic grows and you add 2 more nodes (5 total). Walk through what happens."**
A: Elasticsearch's rebalancing is automatic by default (controlled by `cluster.routing.rebalance.enable`). On node addition:
1. Elasticsearch detects the new nodes joining the cluster.
2. It calculates the current shard distribution: 5 shards across 3 nodes ≈ 1.67 shards/node (2 nodes have 2 shards, 1 node has 1).
3. The target distribution across 5 nodes: 1 shard/node (5 shards ÷ 5 nodes = 1 each).
4. It generates a rebalancing plan: move shards from the 2-shard nodes to the new empty nodes, one shard per new node.
5. Each moved shard is first replicated to the destination node, then the source shard is marked as relocated. During this transfer, the shard is still readable from the source.
6. After both moves complete, each node has exactly 1 primary shard.

Key operational concerns: the throttle setting (`indices.recovery.max_bytes_per_sec`, default 40MB/s) controls how fast shards transfer. On a large index, this could take hours at the default rate. Monitor `_cat/recovery` for progress. The cluster stays green during rebalancing because replicas cover any primary that's being relocated.

**Q28. "A Cassandra node fails at 2AM. On-call gets paged. What is the rebalancing decision they need to make, and what are the risks of acting immediately?"**
A: When a node fails, Cassandra detects it via gossip protocol and (if configured with `auto_bootstrap` and hinted handoff) begins streaming the failed node's data to its ring neighbors. The on-call engineer faces a decision:

**Act immediately (initiate repair/replace)**:
- Starts data movement from remaining nodes to restore RF
- Risk: if the failure was caused by a transient issue (network partition, brief overload), rebalancing adds extra I/O and network load to nodes that may already be stressed — potentially causing further failures. If the failed node comes back online after rebalancing starts, you now have two sources of truth being merged concurrently.

**Wait (observe first)**:
- If the node is likely to return (e.g., a known network hiccup), waiting avoids unnecessary data movement
- Cassandra's hinted handoff preserves missed writes for a configurable window (default 3 hours)
- Risk: if the node is actually permanently dead and you wait, the cluster runs at RF-1 for longer, reducing fault tolerance

**Best practice**: wait 10–15 minutes to see if the node recovers on its own. If it doesn't, initiate replacement with a throttled stream rate (`nodetool setstreamthroughput`) to avoid overwhelming the cluster. Monitor with `nodetool netstats` during streaming.

**Q29. "Your DynamoDB table has one partition getting 80% of all write traffic — the 'orders' partition key is `store_id`, and one store is 10× larger than all others. How do you fix this without changing the partition key?"**
A: The root cause is a hot partition key — `store_id` of the large store hashes to one DynamoDB partition that's receiving 80% of writes. DynamoDB's adaptive capacity helps somewhat (it can allocate more capacity to hot partitions), but it has limits and adds latency. Fixes without changing the primary partition key:

- **Write sharding via suffix**: Add a write-time suffix (0–9) to the partition key: `store_id#3`, `store_id#7`, etc. Writes distribute across 10 partitions. Reads must query all 10 suffixed keys and aggregate — use a DynamoDB BatchGetItem or Query per suffix, then merge in application code. The number of shards is your application's choice; more shards = more distribution, more read fan-out.
- **Caching for read hot keys**: If 80% of writes come from one store and it's also heavily read, put an application-level cache (ElastiCache) in front of that store's data. Reads are served from cache; only writes hit DynamoDB, and cache invalidation handles eventual consistency.
- **SQS write buffer**: Queue writes for the hot store through SQS; a consumer writes them to DynamoDB at a controlled rate, smoothing out bursts. Adds latency but protects the partition.

For a new table design, the partition key should be something with high cardinality and uniform distribution — `order_id` (UUID) rather than `store_id` — with a GSI on `store_id` for store-level queries.

**Q30. "You're designing the partitioning scheme for a time-series metrics system. Metrics are queried by `(service_name, metric_name, time_range)`. What partitioning strategy do you use and what hotspot risk do you mitigate for?"**
A: The query pattern is range-heavy on time but point-exact on service and metric — a compound partitioning scheme is needed:

**Partition key**: `hash(service_name + metric_name)` — this distributes writes uniformly across nodes by service+metric identity. Each unique (service, metric) pair maps to one node for all time, keeping the time-series data co-located for that series.

**Sort key within partition**: `timestamp` — range-ordered within each partition. This enables efficient time-range scans: "give me `cpu_usage` for `payments-service` in the last hour" queries one partition and range-scans by timestamp. No cross-partition scatter-gather is needed for the common query.

**Hotspot risk**: A very high-cardinality metric (e.g., a metric emitted 10,000 times/second by a critical service) concentrates writes on one partition. Mitigation: sub-shard by time bucket — partition key becomes `hash(service + metric + time_bucket_hour)` — so each hour of data lives in a separate partition. This limits the maximum data per partition while keeping scans within a bucket fast. Cross-hour queries require merging results from multiple partitions, but a time range of N hours fan-outs to exactly N partitions — bounded and predictable.

**Retention and rebalancing**: Old partitions (historical time buckets) are cold; current partitions are hot. Dynamic partitioning handles this naturally — the current bucket's partition splits as it grows, while old buckets remain static. After TTL expiry, old partitions are dropped entirely rather than merged — an efficient "rebalancing by deletion."

| Consistent hashing      | Key/node hashed to ring; nearest node owns | 1/N (minimum)               | None; vnodes help skew | No (ring is dynamic) | Cassandra, DynamoDB, Riak    |
| Fixed partitions        | P partitions, each assigned to a node      | Whole partitions moved       | None; application-side | Yes (P fixed)      | Elasticsearch, Kafka, Voldemort|
| Dynamic partitioning    | Partitions split/merge on size thresholds  | 1 split → 2 partitions       | Split hot partitions   | No (adapts)        | HBase, Bigtable, MongoDB       |

---

## The Core Mental Model

```
The fundamental constraint: to add the Nth node, at minimum 1/N of all data must move.
Any strategy that moves more than this is wasteful.
Any strategy that claims to move less is wrong.

Hash mod N:         Moves (N−1)/N   — catastrophically wrong
Consistent hashing: Moves 1/N      — theoretically optimal, practically achieved with vnodes
Fixed partitions:   Moves ~1/N     — optimal if whole partitions are moved
Dynamic:            Moves ~1/N     — optimal; splits limit movement to adjacent data only

The rebalancing problem has two sub-problems:
  1. How much data moves? (the algorithm's efficiency)
  2. When and how fast does it move? (the operational safety problem)

Algorithm correctness ≠ operational safety.
Optimal data movement + no throttle + no human gate = cascade failure waiting to happen.

Rebalancing checklist:
  ✓ Throttle rebalancing bandwidth explicitly
  ✓ Human-approve or schedule rebalancing in stable clusters
  ✓ Monitor for hot partitions independently of rebalancing
  ✓ Pre-split new tables/indices with known-large initial datasets
  ✓ Design partition keys for uniform distribution (not sequential / low-cardinality)
```

---

**Tip for the interview:** Rebalancing questions at 5 YOE almost always start with "why does hash mod N fail?" — know the `(N−1)/N` math cold. Then the conversation moves to consistent hashing and vnodes, where the key insight is *why* vnodes are necessary (uneven ring distribution + lopsided rebalancing without them). The most senior signal: knowing that consistent hashing solves *movement efficiency* but not *hotspots* — those require application-level key design. The best answers also flag the operational dimension: "rebalancing is correct in theory, but without throttling and human gating, it can cascade and take down the cluster" — that's the kind of war story framing that signals you've thought about this in production, not just in textbooks.
