# Hotspot Problem and Mitigation (Skewed Keys, Salting) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the hotspot problem in distributed systems?**
A: A hotspot occurs when a disproportionate fraction of traffic, storage, or computation is routed to a single node, partition, or shard — while other nodes sit underutilised. The hot node becomes the bottleneck for the entire system: its CPU saturates, its I/O queue backs up, its latency climbs, and eventually it begins rejecting requests or failing. The system's theoretical capacity is N nodes × per-node capacity, but the effective capacity is limited to the hot node's capacity alone. Hotspots violate the core premise of horizontal scaling — that adding nodes improves throughput linearly. They are the most common reason a horizontally scaled system fails to scale.

**Q2. What causes hotspots — what are the distinct root causes?**
A: Four distinct root causes, each requiring a different mitigation:

- **Skewed partition keys**: The key chosen for partitioning data or routing requests has a highly uneven value distribution. A partition key of `country_code` routes all Indian users to one shard if India has 80% of the user base. A partition key of `date` routes all today's writes to one shard.
- **High-frequency access to a single key**: A small number of keys (or a single key) are accessed far more often than others — a celebrity's social media post, a product on a flash sale, a shared configuration value. The key itself is fine as a partition key; the access pattern is the problem.
- **Sequential key generation**: Auto-increment integer IDs and monotonically increasing timestamps route all new writes to the partition responsible for the highest key range — the "last" partition receives 100% of writes while all other partitions are read-only.
- **Uneven data distribution in range partitioning**: A range-partitioned system assigns each partition a key range. If the data distribution is not uniform within those ranges, some partitions hold much more data or receive much more traffic than others — even with an apparently reasonable range split.

**Q3. Why is the hotspot problem particularly dangerous compared to other scaling failures?**
A: Most scaling failures are visible and symmetric — if a system is under-provisioned, all nodes are busy, latency rises uniformly, and the fix is obvious (add nodes). A hotspot is asymmetric and deceptive: aggregate metrics (average CPU across all nodes, total throughput) can look healthy while one node is on fire. A system averaging 40% CPU across 10 nodes may have one node at 100% and nine nodes at 33% — the aggregate hides the problem. The hot node fails under load while nine nodes have plenty of headroom. Adding more nodes doesn't help — all new writes still route to the same hot node. The fix requires changing the data model, partition strategy, or access pattern — not just adding capacity.

**Q4. What is key skew, and how do you detect it?**
A: Key skew is the statistical non-uniformity of values in a partition key — some values appear far more frequently than others. In a perfectly uniform distribution, each partition receives 1/N of the traffic. With key skew, the distribution follows a power law (Zipf distribution in many real-world datasets): the most popular key receives orders of magnitude more traffic than the average.

Detection methods:
- **Per-partition metrics**: Monitor request rate, CPU, and I/O per partition or shard separately — not just aggregated totals. A hotspot is visible as one partition's metrics diverging dramatically from the others.
- **Key frequency analysis**: Sample production traffic and count the frequency of each partition key value. Any key accounting for more than 5–10% of total traffic is a potential hotspot under load.
- **Database-level tools**: `pg_stat_user_tables` per partition in Postgres, Cassandra `nodetool tablestats` per node, DynamoDB CloudWatch metrics per partition key. These surface uneven distribution directly.
- **Kafka consumer lag per partition**: In a Kafka-based system, a hotspot producer key causes one partition to fill faster than others. Monitor `kafka_consumergroup_lag` per partition — a single partition with dramatically higher lag is a hotspot signal.

## Section 2: Sequential Key Hotspots

**Q5. Why do sequential keys (auto-increment IDs, timestamps) cause write hotspots?**
A: In a range-partitioned system, data is distributed by key range — partition 1 holds keys 1–1000, partition 2 holds 1001–2000, and so on. With sequential keys, new inserts always have the highest key value and therefore always go to the last partition (the one responsible for the highest range). All writes concentrate on that single partition; all other partitions only receive reads. This is the "hot tail" or "monotonic key" problem. It's endemic to any system using:
- Auto-increment integer primary keys in a distributed DB (CockroachDB, YugabyteDB, sharded Postgres).
- Timestamp-based keys (`2024-01-15T14:32:01.203Z` as a row key in HBase or Bigtable).
- Sequential order numbers, invoice numbers, or transaction IDs as shard keys.

The hot tail partition receives 100% of write load. It becomes the bottleneck for the entire write path regardless of how many total partitions exist.

**Q6. How does HBase or Bigtable suffer from sequential key hotspots, and what is the canonical mitigation?**
A: HBase and Bigtable are sorted key-value stores — rows are stored in lexicographic key order. Regions (partitions) hold contiguous key ranges. A common pattern is using a timestamp prefix as the row key: `2024-01-15:user:42:event:click`. This makes range scans by time easy (read "all events in January" with one range scan). But it means all writes go to the region responsible for the current timestamp range — one region receives 100% of writes, while all historical regions serve only reads.

**Canonical mitigation — key reversal**: Reverse the timestamp string: `5102-10-41:user:42:event:click`. Lexicographic order of reversed timestamps is reverse chronological — writes still go to one region, but that region is now the "first" region rather than the "last," and more importantly, the key space can be split differently. More effective: reverse the timestamp bytes so that the most recent timestamp sorts first, spreading recency across the key space.

**Better mitigation — salting with a hash prefix**: Prepend a short hash prefix (2–4 hex characters) to the row key: `a3:2024-01-15:user:42`. The prefix distributes writes across 256 (for 2-hex-char prefix) or 65536 (for 4-hex-char prefix) regions. Reads for a specific key must know the prefix (deterministic from the key content). Range scans by time require scanning all prefix-keyed regions in parallel. The write hotspot is eliminated at the cost of range scan complexity.

**Q7. How do you generate non-sequential distributed IDs to avoid the sequential key problem from the start?**
A: Use ID generation strategies that produce globally unique, non-sequential (or pseudo-random) identifiers:

- **UUID v4 (random)**: 128-bit random identifier. Globally unique, no coordination required, distributes inserts uniformly across partitions by hash. Downside: completely random — no ordering information, large index fragmentation in B-tree indexes (random inserts cause page splits), not human-readable.
- **UUID v7 (time-ordered)**: 128-bit identifier with a millisecond-precision timestamp prefix followed by random bits. Provides time ordering for range scans while distributing writes across partitions within the same millisecond (the random suffix ensures no two IDs at the same millisecond are sequential). Best of both worlds for most use cases. Supported natively in Postgres 17+.
- **ULID (Universally Unique Lexicographically Sortable Identifier)**: 26-character base32 string, millisecond timestamp prefix + 80 random bits. Time-ordered, URL-safe, and distributes writes uniformly within each millisecond window.
- **Snowflake IDs (Twitter/Discord)**: 64-bit integer composed of `{timestamp_ms: 41 bits, machine_id: 10 bits, sequence: 12 bits}`. Time-ordered, unique per machine, compact. The `machine_id` bits mean two machines generating IDs at the same millisecond produce non-adjacent IDs — no sequential hotspot. Used by Twitter, Discord, Instagram.

For a fintech payment platform: Snowflake IDs or ULID are preferred — they're compact (important for index size), time-ordered (important for range scans on recent transactions), and non-sequential at the partition level (no write hotspot).

## Section 3: Salting

**Q8. What is salting, and how does it mitigate hotspot keys?**
A: Salting is the technique of appending or prepending a random or computed value (the "salt") to a hot partition key, artificially spreading its traffic across multiple partitions. Instead of all traffic for key `K` going to one partition, it's spread across `S` partitions by routing key `K` to `K:0`, `K:1`, ..., `K:S-1` — where the suffix is chosen randomly on write (random salting) or deterministically (hash salting):

```
Original key: "product:iphone15"  → all traffic to partition P7

Salted keys (S=10):
Write 1: "product:iphone15:3"  → partition P3
Write 2: "product:iphone15:7"  → partition P7
Write 3: "product:iphone15:1"  → partition P1
Write 4: "product:iphone15:9"  → partition P9
...traffic distributed across 10 partitions
```

The salt value is either random (for writes where you don't need to read back the exact key) or derived deterministically from some request attribute (user ID, request ID) so that reads can reconstruct which salted partition to query.

**Q9. What are the trade-offs of salting, and what does it break?**
A: Salting redistributes write load but complicates reads and aggregations:

**Write side**: Simple — choose a salt (random or deterministic), append to the key, write to the resulting partition. No coordination required.

**Read side (exact key lookup)**: If the salt was random, the reader doesn't know which salted partition holds the value. Must query all S partitions in parallel and merge results:
```javascript
// Reading a salted counter
const SALT_COUNT = 10;
const results = await Promise.all(
  Array.from({length: SALT_COUNT}, (_, i) =>
    redis.get(`product:iphone15:${i}`)
  )
);
const total = results.reduce((sum, v) => sum + (parseInt(v) || 0), 0);
```
Reads become S× more expensive (S parallel queries instead of 1).

**Aggregations**: A simple `SUM` or `COUNT` on a salted key requires reading all S partitions and summing — what was a single-key lookup becomes a scatter-gather across S partitions.

**Range scans**: Range scans on salted keys are broken — the keys are no longer contiguous in the key space. Range-scanning `product:iphone15:0` through `product:iphone15:9` requires separate queries per salt value.

**Operational complexity**: The salting factor S is baked into the data. If you later decide S=10 was too small (the hot key grew hotter), you must re-shard the data — you can't simply change S without migrating existing data.

**Q10. What is the difference between random salting and hash salting?**
A: The distinction determines how reads reconstruct which partition to query:

**Random salting**: The salt is chosen randomly at write time (`Math.random() * S | 0`). Writes are uniformly distributed across S partitions. Reads cannot determine which partition to query — they must scatter-gather across all S partitions. Best for write-heavy workloads where aggregate reads (sum all S partitions) are acceptable and exact-key point reads are rare.

**Hash salting (deterministic salting)**: The salt is derived deterministically from a request attribute — typically the requesting user's ID or a request attribute:
```javascript
const salt = hash(userId) % S;  // always the same salt for the same userId
const key = `product:iphone15:${salt}`;
```
A given user always reads and writes the same salted partition. Reads are single-partition (no scatter-gather) — the reader computes the same salt and queries exactly one partition. Best for user-partitioned access where each user's reads and writes are self-contained. Does not help if the hot key is accessed uniformly by all users (a global counter) — all users end up on different partitions, but a single user's shard is still a hotspot if that user is the celebrity.

**Q11. How do you salt a hot key in Redis, and what does the read path look like?**
A: Redis is single-threaded per shard — a single hot key can saturate a Redis node's CPU regardless of how many Redis nodes exist in a cluster. Salting distributes a hot key across multiple Redis keys (and potentially multiple nodes in a Redis Cluster):

**Write (random salting, for a counter)**:
```javascript
const SALT_COUNT = 16;
async function incrementCounter(baseKey) {
  const salt = Math.floor(Math.random() * SALT_COUNT);
  const saltedKey = `${baseKey}:${salt}`;
  return redis.incr(saltedKey);
}
// "like_count:post_42" becomes:
// "like_count:post_42:0" through "like_count:post_42:15"
// distributed across up to 16 Redis nodes in a cluster
```

**Read (scatter-gather)**:
```javascript
async function getCounter(baseKey) {
  const keys = Array.from({length: SALT_COUNT},
    (_, i) => `${baseKey}:${i}`
  );
  const values = await redis.mget(...keys);
  return values.reduce((sum, v) => sum + (parseInt(v) || 0), 0);
}
```

**Trade-off in practice**: `MGET` fetches all 16 salted keys in one Redis round trip (if all keys are on the same node) or multiple round trips (in Redis Cluster, keys hash to different nodes). In Redis Cluster, use hash tags to control which node a key lands on: `{like_count:post_42}:0` through `{like_count:post_42}:15` — the hash tag `{like_count:post_42}` ensures all 16 keys land on the same cluster node, making `MGET` a single-node operation. But this partially defeats the distribution purpose — use hash tags only when the scatter-gather cost is the dominant concern, not the hot node CPU.

## Section 4: Hot Key Caching & Read Mitigation

**Q12. How does caching mitigate read hotspots without salting?**
A: For read hotspots (a single key read extremely frequently), caching is often more appropriate than salting — the data doesn't need to be split across partitions; it just needs to be served without repeatedly hitting the hot storage node:

**Local in-process cache (L1)**:
```javascript
const LRU = require('lru-cache');
const localCache = new LRU({ max: 1000, ttl: 5000 }); // 5s TTL

async function getProductPrice(productId) {
  const cached = localCache.get(productId);
  if (cached !== undefined) return cached;  // L1 hit — no Redis, no DB

  const price = await redis.get(`price:${productId}`);
  localCache.set(productId, price);
  return price;
}
```

At 10,000 req/sec on a hot product, an in-process cache with a 5-second TTL converts 10,000 Redis calls/sec into 1 Redis call per 5 seconds per application pod — a 99.99% reduction in Redis load. This is the most effective mitigation for read hotspots on stable data.

**CDN caching for public read hotspots**:
For publicly readable data (product listings, public profiles, exchange rates), a CDN serves cached responses from edge nodes globally — the origin (API server, Redis, DB) receives only cache misses, not the full read volume. A flash sale product page that gets 1 million reads/minute has nearly all reads served from CDN cache; the origin sees only the cache miss volume (inversely proportional to the cache hit rate).

**Replication of hot keys**:
In Redis Cluster, a hot key sits on one node. Redis Enterprise and KeyDB support key-level replication — a hot key is replicated to multiple nodes, and reads are load-balanced across all replicas. Not available in open-source Redis Cluster without application-level sharding.

**Q13. What is the "celebrity problem" in social systems, and how is it mitigated?**
A: The celebrity problem (sometimes called the "thundering herd" or "hot account" problem) is when a celebrity or viral account generates orders of magnitude more traffic than ordinary accounts — their posts, profile reads, and interactions flood a specific shard with read traffic that a uniform sharding strategy never anticipated. A user with 50 million followers generates 50 million fan-out write operations on a post; a user with 100 followers generates 100. The same data model, same shard key, but a difference in traffic of 5 orders of magnitude.

Mitigations:
- **Tiered fan-out (push for regular users, pull for celebrities)**: Regular users' posts are pushed to followers' feeds at write time (fast reads, expensive writes). Celebrity posts are NOT pushed — they're fetched at read time by querying the celebrity's post store and merging with the pre-computed feed (expensive reads, cheap writes). The read expense is shared across followers' timelines rather than concentrated on one write path. Twitter, Instagram, and LinkedIn all implement this hybrid push-pull fan-out.
- **Pre-computed hot shards**: Detect accounts above a follower threshold (e.g., > 1M followers) and assign them dedicated infrastructure — a dedicated DB partition, a dedicated Redis cluster, or a dedicated CDN cache entry — that is provisioned for their specific traffic volume.
- **Read replicas per celebrity**: For read hotspots on celebrity data, create additional read replicas specifically for celebrity accounts. The replication factor is higher for celebrity shards than for ordinary user shards.
- **Aggressive caching with short TTL**: Cache celebrity profile and post data with a 1-second TTL. Even 1-second caching reduces load by 100× for a service receiving 100 reads/second on the same celebrity key.

**Q14. What is local aggregation before writing, and when does it apply?**
A: Local aggregation accumulates writes in memory (per application node) for a short window before flushing to the DB or cache — converting N individual writes into 1 batched write. This reduces the write rate on a hot key by up to N×:

```javascript
// Without local aggregation: 10,000 INCR calls/second on "views:post_42"
app.post('/view', (req) => {
  redis.incr('views:post_42');  // 10,000 Redis ops/second
});

// With local aggregation: 1 write/second regardless of request rate
const localCounters = new Map();

app.post('/view', (req) => {
  localCounters.set('views:post_42',
    (localCounters.get('views:post_42') || 0) + 1
  );
});

// Flush every 1 second
setInterval(async () => {
  for (const [key, delta] of localCounters.entries()) {
    await redis.incrby(key, delta);
    localCounters.delete(key);
  }
}, 1000);
```

Appropriate when: the exact count doesn't need to be real-time (view counts, like counts, impression counts). Not appropriate when: the value must be immediately consistent (available balance, inventory count, OTP attempt count).

The trade-off: if the application pod crashes between local accumulation and flush, the buffered increments are lost. For view counts, losing 1 second of view data on a crash is acceptable. For payment counts, it is not.

## Section 5: Database-Specific Hotspot Patterns

**Q15. How does Cassandra handle hotspot keys, and what are the specific mitigations?**
A: Cassandra distributes data by hashing the partition key — each partition key maps to a token (a 64-bit hash value) and is assigned to the node(s) responsible for that token range. A hotspot in Cassandra manifests as one node's CPU and disk I/O far exceeding others. Cassandra-specific causes and mitigations:

**Cause 1 — Hot partition key with high access rate**:
One partition key (e.g., `payment_gateway:razorpay`) is read/written far more than others. All requests for that key go to the same node(s) (however many replicas exist).

Mitigation: **Bucket the hot key by a secondary dimension**:
```
Instead of: partition_key = "gateway:razorpay"
Use:        partition_key = "gateway:razorpay:{month}"
            → "gateway:razorpay:2024-01"
            → "gateway:razorpay:2024-02"
```
Distributes the hot key across time buckets — each bucket is a separate partition on potentially different nodes. Queries for a specific month are still single-partition. Queries across months require multi-partition reads (one per month in the range).

**Cause 2 — Wide partition (too many rows in one partition)**:
Cassandra stores all rows within a partition on the same node. A partition key of `date` with billions of daily events creates a partition that is gigabytes in size — one node holds all of today's data. This causes both storage imbalance and read/write hotspots.

Mitigation: **Composite partition key with a bucketing dimension**:
```sql
CREATE TABLE events (
  date        DATE,
  bucket      INT,    -- hash(event_id) % 64
  event_id    UUID,
  ...
  PRIMARY KEY ((date, bucket), event_id)
);
```
The composite partition key `(date, bucket)` spreads each day's events across 64 partitions — 64 different nodes receive writes for today's data. Queries for all of today's events must query all 64 buckets in parallel (scatter-gather), but no single node receives all of today's write traffic.

**Cause 3 — Sequential clustering key causing local hotspot**:
Within a Cassandra partition, rows are stored sorted by the clustering key. If all new rows have the latest timestamp as the clustering key, writes always append to the "end" of the partition on disk — causing write amplification and read-hotspot on the partition's newest data. Mitigation: add a random component to the clustering key or use time-bucket partitions with random row keys within each bucket.

**Q16. How do DynamoDB hot partitions work, and how does DynamoDB itself mitigate them?**
A: DynamoDB partitions data by hashing the partition key. Each partition has a throughput limit: ~1,000 WCU (Write Capacity Units) and ~3,000 RCU (Read Capacity Units) per second. A hot partition key that receives more than this limit gets throttled — requests return `ProvisionedThroughputExceededException` even if the table's total provisioned throughput has headroom.

**DynamoDB's internal mitigation — Adaptive Capacity**:
DynamoDB automatically redistributes throughput from underutilised partitions to hot partitions in real time — up to the table's total provisioned throughput. This helps for moderate imbalances but does not help when one partition genuinely needs more than the table's total provisioned capacity.

**DynamoDB's internal mitigation — Burst Capacity**:
DynamoDB reserves unused partition capacity for bursts — a partition can briefly exceed its allocated capacity by drawing from a 5-minute burst reserve. Helps for short-lived spikes, not sustained hotspots.

**Application-level mitigation — partition key design**:
The most important mitigation is designing the partition key to have high cardinality and uniform access distribution. Instead of `partition_key = "payment_status"` (only a few values: pending, confirmed, failed), use `partition_key = payment_id` (millions of unique values, uniformly distributed). For access-pattern hotspots on a legitimately unique key (a specific payment that's queried millions of times), add a caching layer (ElastiCache/Redis) in front of DynamoDB — the DynamoDB partition is hit only on cache misses.

**Write sharding for hot keys**:
```javascript
// Hot key: "inventory:iphone15" — receives 50,000 writes/second
// DynamoDB partition limit: 1,000 WCU/second → throttled

// Write sharding: spread across S virtual shards
const SHARD_COUNT = 64;
const shard = Math.floor(Math.random() * SHARD_COUNT);
await dynamodb.updateItem({
  TableName: 'inventory',
  Key: { pk: { S: `inventory:iphone15:${shard}` } },
  UpdateExpression: 'SET stock = stock - :delta',
  ExpressionAttributeValues: { ':delta': { N: '1' } }
});

// Read: scatter-gather across all 64 shards
const shards = Array.from({length: SHARD_COUNT}, (_, i) =>
  `inventory:iphone15:${i}`
);
```

**Q17. How does Kafka handle partition hotspots, and what are the mitigations?**
A: Kafka assigns messages to partitions based on the message key (hashed) or round-robin (no key). A hotspot occurs when a message key is highly skewed — all messages with key `payment_gateway=razorpay` go to the same partition, which has a single consumer. That consumer lags while other consumers sit idle.

**Mitigation 1 — Key redesign**:
Choose a higher-cardinality key that distributes messages more evenly. Instead of `payment_gateway` (3 values: razorpay, juspay, stripe), use `payment_id` (millions of unique values). If ordering by payment gateway is required, use a compound key: `{payment_gateway}:{payment_id}` — same gateway orders are co-partitioned but distributed across gateways.

**Mitigation 2 — Custom partitioner**:
Implement a custom Kafka partitioner that detects hot keys and distributes them across multiple partitions:
```javascript
class SaltingPartitioner {
  partition(topic, key, partitionCount) {
    const basePartition = murmur2(key) % partitionCount;
    if (isHotKey(key)) {
      // Spread hot key across S partitions
      const salt = Math.floor(Math.random() * HOT_KEY_SALT);
      return (basePartition + salt) % partitionCount;
    }
    return basePartition;
  }
}
```
Consumers of a salted hot key must consume from all S partitions and merge — ordering within the hot key is lost across salted partitions.

**Mitigation 3 — Increase partition count**:
More partitions allow more parallelism. But increasing partition count for an existing topic is operationally disruptive (existing key→partition mappings change; ordering guarantees for existing keys are broken). Partition count should be set generously at topic creation time (Kafka recommends starting with 3× the peak expected consumer throughput / per-partition throughput).

**Mitigation 4 — Consumer-side parallelism**:
If the hot partition's consumer is CPU-bound (processing is slow), use virtual threads or worker threads to parallelise processing within a single consumer. The consumer reads from the hot partition at full speed but dispatches work to a thread pool — limited by the fact that single-partition ordering must be preserved (process sequentially within the partition).

## Section 6: Trade-offs & Decision-Making

**Q18. How do you decide which hotspot mitigation to apply?**
A: Match the mitigation to the root cause and access pattern:

| Root Cause | Access Pattern | Recommended Mitigation |
|---|---|---|
| Sequential write keys | Write-heavy, range scan required | UUID v7 / ULID / Snowflake IDs at creation time |
| Sequential write keys | Write-heavy, no range scan | UUID v4 (fully random) |
| Skewed partition key (few values) | Write-heavy | Key redesign (higher cardinality key) |
| Hot key (frequent reads) | Read-heavy, data is stable | In-process L1 cache + Redis L2 cache |
| Hot key (frequent reads) | Read-heavy, data changes often | Short TTL cache + event-driven invalidation |
| Hot key (frequent writes, counter) | Write-heavy, approximate count ok | Random salting + scatter-gather reads |
| Hot key (frequent writes, counter) | Write-heavy, exact count ok with delay | Local aggregation + periodic flush |
| Celebrity / viral content | Read-heavy fan-out | Pull-on-read for large accounts, CDN cache |
| Wide partition (Cassandra/HBase) | Mixed | Composite partition key with bucket suffix |
| Kafka skewed key | Event-driven | Higher-cardinality key or custom salting partitioner |

**Q19. What are the operational signals that indicate a hotspot has developed in production?**
A: A hotspot is rarely announced — it develops gradually and appears as asymmetric degradation. Watch for:
- **Per-shard/per-partition CPU or I/O divergence**: One node at 90% CPU while all others are at 30%. In Cassandra: `nodetool tpstats` per node. In DynamoDB: CloudWatch `ConsumedWriteCapacityUnits` per partition key prefix. In Kafka: consumer group lag per partition.
- **Tail latency spikes without aggregate throughput changes**: p99 or p999 latency rises while p50 stays flat. The hotspot causes queuing on the hot node — a small percentage of requests queue behind the hot one, inflating the tail.
- **Throttling errors from a specific key pattern**: DynamoDB `ProvisionedThroughputExceededException` or Cassandra timeout exceptions — check which keys are triggering them.
- **Kafka partition lag imbalance**: One partition's consumer lag grows while other partitions drain normally.
- **Redis CPU spikes on a single node in a cluster**: Use `redis-cli --hotkeys` (requires `maxmemory-policy allkeys-lfu`) to identify the most frequently accessed keys. Or `OBJECT FREQ <key>` for LFU frequency estimates.
- **Database slow query log with repeated identical queries**: The same query (fetching a specific product, a specific user) appears in `pg_stat_statements` with very high `calls` — a read hotspot on that row.

**Q20. What is consistent hashing, and how does it help prevent hotspots during rebalancing?**
A: Consistent hashing is a partitioning technique that maps both data keys and nodes to the same circular "ring" of hash values (0 to 2^64). Each key is assigned to the first node clockwise from its position on the ring. When a node is added or removed, only the keys on the affected segment of the ring need to be relocated — not all keys (as would happen with modular hashing). This minimises rebalancing disruption.

How it prevents hotspots during rebalancing:
- **Modular hashing** (`key % N`): Adding one node changes `N` to `N+1`, which changes the assignment of almost every key — a full data migration. During migration, some nodes receive extra traffic (holding both old and new keys) while others are empty. This creates a temporary hotspot.
- **Consistent hashing**: Adding one node splits one existing node's range in half — only that node's keys move. All other nodes are unaffected. No temporary hotspot.

Virtual nodes (vnodes) further improve balance: instead of placing each physical node at one ring position, each node has 100–200 virtual positions spread evenly around the ring. Key distribution is more uniform, and when a physical node fails, its vnodes' keys redistribute to many other physical nodes — no single node receives all the failed node's traffic. Used by Cassandra (vnodes default: 256 per node), DynamoDB (internal), and Redis Cluster (hash slots: 16,384 total, distributed across nodes).

## Section 7: Scenario / System Design Questions

**Q21. "Your Cassandra cluster processing NACH debit records is showing one node at 95% CPU while others are at 25%. The partition key is `debit_date`. What's happening and how do you fix it?"**
A: Classic wide partition + date-based hotspot. `debit_date` as the partition key means all NACH debits for today land on one Cassandra node. With NACH batch windows (most debits processed in morning and evening windows), that node receives burst write traffic during batch runs while other nodes are idle.

**Immediate diagnosis**:
- `nodetool tablestats` on the hot node — confirm the `debit_date` table has a disproportionate partition size for today's date.
- `nodetool cfhistograms` — check read and write latency histograms on the hot node vs others.
- Query: `SELECT COUNT(*) FROM nach_debits WHERE debit_date = '2024-01-15'` — if this returns millions of rows, the partition is too wide.

**Fix — Composite partition key with bucket**:
```sql
-- Before (hotspot)
CREATE TABLE nach_debits (
  debit_date  DATE,
  debit_id    UUID,
  ...
  PRIMARY KEY (debit_date, debit_id)
);

-- After (bucketed, no hotspot)
CREATE TABLE nach_debits (
  debit_date  DATE,
  bucket      SMALLINT,   -- hash(debit_id) % 32
  debit_id    UUID,
  ...
  PRIMARY KEY ((debit_date, bucket), debit_id)
);
```

Writes are now distributed across 32 partitions per day — 32 different Cassandra nodes receive today's debit write traffic. The 95% CPU node drops to ~3% of today's traffic.

**Read path after bucketing**:
- Fetch a specific debit (by `debit_id`): compute `bucket = hash(debit_id) % 32`, query `WHERE debit_date = ? AND bucket = ?`.
- Fetch all debits for a date: query all 32 buckets in parallel, merge results. This is the scatter-gather cost of bucketing.

**Migration**: Data migration from the old schema to the new schema requires reading all existing rows and re-inserting with the new composite partition key. In Cassandra, this is done with Spark Cassandra Connector or a custom migration job running during a low-traffic window, with dual-write to both schemas during the migration period.

**Q22. "A Redis key 'global:transaction_count' is being incremented 100,000 times per second. Redis CPU on the shard holding this key is at 100%. How do you fix it?"**
A: A global counter with extremely high write throughput — the textbook case for salting + local aggregation.

**Step 1 — Local aggregation (immediate fix, zero infrastructure change)**:
Each application pod accumulates increments locally and flushes to Redis every 100ms:
```javascript
let localCount = 0;

// In the hot path — no Redis call
function recordTransaction() {
  localCount++;
}

// Background flush every 100ms
setInterval(async () => {
  if (localCount > 0) {
    const toFlush = localCount;
    localCount = 0;
    await redis.incrby('global:transaction_count', toFlush);
  }
}, 100);
```
With 20 application pods each flushing every 100ms, Redis receives 20 × 10 = 200 INCRBY calls/second instead of 100,000 INCR calls/second — a 500× reduction. CPU on the hot Redis shard drops immediately. Trade-off: count is up to 100ms stale. For a global transaction counter shown on an analytics dashboard, this is acceptable.

**Step 2 — Salting (if local aggregation is insufficient or pod count is very high)**:
```javascript
const SALT_COUNT = 16;
const salt = workerId % SALT_COUNT;  // each pod has a stable salt

async function flush(delta) {
  await redis.incrby(`global:transaction_count:${salt}`, delta);
}

async function getTotal() {
  const keys = Array.from({length: SALT_COUNT},
    (_, i) => `global:transaction_count:${i}`
  );
  const values = await redis.mget(...keys);
  return values.reduce((sum, v) => sum + (parseInt(v) || 0), 0);
}
```
Each pod owns its own salted counter shard — no lock contention. Reads scatter-gather across 16 keys. With Redis Cluster and hash tags disabled, the 16 keys can distribute across 16 different Redis nodes — truly parallel write throughput.

**Step 3 — Approximate counting with HyperLogLog (if exact count not required)**:
```javascript
// Write: O(1) time, O(1) space regardless of cardinality
redis.pfadd('global:transaction_hll', transactionId);

// Read: approximate count with ~0.81% standard error
redis.pfcount('global:transaction_hll');
```
HyperLogLog uses a fixed 12KB of Redis memory regardless of the number of distinct elements counted. Not suitable for counting total operations (all increments) — only for counting distinct elements (unique transaction IDs). If deduplication is the goal, HyperLogLog eliminates the hotspot entirely.

**Q23. "Your e-commerce platform uses `product_category` as the DynamoDB partition key. During a flash sale on electronics, the 'electronics' partition is throttled. How do you redesign?"**
A: `product_category` is a low-cardinality partition key — a few dozen values, with heavily skewed access (electronics dominates flash sales). This is a key design problem, not a transient hotspot.

**Root cause**: DynamoDB's partition throughput limit (1,000 WCU/3,000 RCU per partition) is being exceeded by the `electronics` partition during the flash sale. All electronics products share one partition.

**Redesign — use `product_id` as the partition key**:
```
Before: PK = "electronics", SK = "prod_iphone15"
        PK = "electronics", SK = "prod_macbook"  ← all on same partition

After:  PK = "prod_iphone15"  ← independent partition
        PK = "prod_macbook"   ← independent partition
```
With `product_id` as the partition key, each product is its own DynamoDB partition — traffic to iPhone 15 doesn't affect MacBook's partition. Category queries ("list all electronics") require a GSI (Global Secondary Index) with `category` as the GSI partition key and `product_id` as the sort key. The GSI distributes category writes across multiple GSI partitions using DynamoDB's internal sharding.

**For the flash sale hot product specifically**:
Even with `product_id` as PK, `prod_iphone15` alone may exceed partition limits during a flash sale (millions of reads/second). Layer a cache:
```
Flash sale read path:
Client → CloudFront (CDN cache, TTL 1s) → ElastiCache Redis (TTL 5s) → DynamoDB
```
With a 5-second Redis TTL, 1 million reads/second on `prod_iphone15` become 1 DynamoDB read per 5 seconds — the partition receives negligible direct traffic. Cache invalidation on price/stock change is event-driven (publish `product.updated` → clear `prod_iphone15` from Redis).

**Write sharding for inventory during flash sale**:
If inventory decrements on `prod_iphone15` exceed 1,000 WCU/second, apply write sharding:
```javascript
// Spread inventory across S=10 shards
const shard = Math.floor(Math.random() * 10);
await dynamodb.updateItem({
  Key: { pk: { S: `prod_iphone15:inv:${shard}` } },
  UpdateExpression: 'ADD stock :delta',
  ConditionExpression: 'stock >= :abs_delta',
  ExpressionAttributeValues: {
    ':delta': { N: '-1' },
    ':abs_delta': { N: '1' }
  }
});
// Read total inventory: sum all 10 shards
```
The floor constraint (`stock >= 0`) is enforced per-shard — each shard can decrement independently until its local shard stock is zero. Total inventory is the sum of all shards' stock values. This allows 10,000 WCU/second of inventory decrements (10 shards × 1,000 WCU each) without coordination.

| Technique | Eliminates Write Hotspot | Eliminates Read Hotspot | Read Complexity | Data Model Change | Best For |
|---|---|---|---|---|---|
| Key redesign (higher cardinality) | ✅ Yes | ✅ Yes | None | Schema change | Low-cardinality partition keys |
| Non-sequential IDs (UUID v7, ULID) | ✅ Yes | N/A | None | ID generation change | Sequential key write hotspots |

| Hash salting (deterministic) | ✅ Yes | ✅ Per-user single read | Low (1 read) | Application change | Per-user access patterns |
| Local aggregation | ✅ Yes (reduces rate) | ❌ No | None | Application change | High-rate counter writes |
| In-process L1 cache | ❌ No | ✅ Yes | None | Application change | Read-heavy stable data |
| Redis cache | ❌ No | ✅ Yes | None | Infrastructure | Read-heavy, TTL-tolerant |
| Composite partition key (Cassandra) | ✅ Yes | ❌ Scatter-gather | High (N buckets) | Schema change | Wide partitions, Cassandra |
| CDN cache | ❌ No | ✅ Yes (public reads) | None | Infrastructure | Public read-heavy endpoints |
| Pull-on-read fan-out | ✅ Yes (write fan-out) | ⚠️ Slower reads | Medium | Architecture change | Celebrity/viral content |

**Tip for the interview:** At the 5 YOE level, the key signal is diagnosing *which type* of hotspot you're dealing with before proposing a solution — a sequential write key hotspot is fixed by non-sequential IDs; a high-frequency read hotspot is fixed by caching; a high-frequency write hotspot on a specific key is fixed by salting or local aggregation. Proposing caching for a write hotspot or salting for a read hotspot shows you haven't diagnosed the root cause. In a fintech context, name the specific hotspot risks in your domain: `debit_date` as a Cassandra partition key for NACH batches, `payment_gateway` as a Kafka message key for JusPay/Razorpay traffic, and sequential auto-increment payment IDs as a write hotspot in a distributed SQL database. Connecting the pattern to a concrete example from your domain is what turns a textbook answer into a senior-level one.
