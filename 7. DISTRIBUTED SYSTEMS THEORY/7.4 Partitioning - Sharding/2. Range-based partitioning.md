# Range-Based Partitioning — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is range-based partitioning and what problem does it solve?**
A: Range-based partitioning (also called range sharding) divides the key space into contiguous, non-overlapping intervals — called ranges, partitions, tablets, or regions depending on the system — and assigns each interval to a specific node or storage unit. All records whose key falls within a range's boundaries are stored on the node responsible for that range.

It solves the scalability ceiling of a single node by distributing data across many nodes, while preserving the ordered structure of the key space. Unlike hash partitioning (which scatters keys pseudorandomly), range partitioning keeps neighboring keys physically adjacent — enabling efficient range scans: "give me all orders between January and March" can be answered by querying only the partitions whose range overlaps that interval, not by touching every node in the cluster.

**Q2. What does a range partition look like structurally, and what metadata is needed to operate it?**
A: Each partition is defined by a half-open interval `[start_key, end_key)` — it includes its start key and excludes its end key. The full key space is covered by a set of non-overlapping, contiguous partitions. For a string user ID space: `[A, D)`, `[D, K)`, `[K, R)`, `[R, Z]`.

Required metadata — the **partition map** or **routing table** — records for each partition: its key range boundaries, which node owns it, and any replication group membership. Every read and write request must first consult this map to route to the correct node. This map is typically small (hundreds to thousands of entries) and cached aggressively — in ZooKeeper (HBase), the Coordinator (CockroachDB), or a dedicated metadata service. The map is the system's single source of truth for "who owns what range."

**Q3. How does range partitioning differ from hash partitioning, and when does each apply?**
A: Hash partitioning applies a deterministic hash function to each key, maps the hash to a partition bucket (often via consistent hashing), and distributes records accordingly. Neighboring keys hash to different buckets — they are scattered across nodes with no locality.

The fundamental trade-off:
- **Range partitioning**: preserves key order. Efficient range scans (all data between two keys lives on a contiguous set of partitions). Prone to load imbalance if keys are unevenly distributed or monotonically increasing.
- **Hash partitioning**: destroys key order. Distributes load evenly (with a good hash function, records spread uniformly). Range scans require querying all partitions (scatter-gather) — O(partitions) instead of O(relevant_partitions).

Choose range partitioning when range queries are a primary access pattern. Choose hash partitioning when point lookups dominate and uniform load distribution is critical. Most large-scale systems use one or a combination: DynamoDB uses hash partitioning by partition key but range partitioning by sort key within each partition.

**Q4. What is a "tablet" and how does it differ from a "partition"?**
A: The terms are largely synonymous — both refer to a bounded key range owned by a single node. The naming convention varies by system: HBase calls them **regions**, Bigtable and CockroachDB call them **ranges** or **tablets**, Spanner uses **tablets**, Cassandra uses **virtual nodes (vnodes)** for its token ring. All refer to the same concept: a contiguous slice of the key space, stored as an ordered data structure (typically a B-tree or LSM-tree) on one node, independently readable, writable, and movable to other nodes during rebalancing.

The distinction worth knowing: in HBase, a **region** is the unit of distribution (one region per RegionServer at a time), while a **store** is the unit of storage within a region (one store per column family). The range partition concept sits at the region level.

**Q5. What is the role of a B-tree or LSM-tree within a range partition?**
A: The range partition defines the *boundaries* of which keys live on a node; the storage engine within that partition defines *how* those keys are organized on disk. Range partitions almost universally use an ordered storage engine:
- **B-tree** (PostgreSQL, MySQL, CockroachDB): keys within the partition are stored in sorted order in a balanced tree. Range scans within a partition are efficient (tree traversal from start key to end key).
- **LSM-tree** (HBase, Cassandra, RocksDB): keys are written to an in-memory memtable (also sorted), flushed to sorted immutable SST files, and periodically compacted. Range scans read sorted SST files sequentially.

Both engines maintain sorted order within the partition, which is what enables range queries to run efficiently. A range partition with an unsorted internal store (e.g., a hash table) would defeat the purpose — you'd lose the O(log N + K) range scan and degrade to a full scan.

## Section 2: Partition Key Design & Range Selection

**Q6. What makes a good partition key for range-based partitioning?**
A: A good range partition key has three properties:
- **High cardinality**: enough distinct values to allow fine-grained partition boundaries. A boolean column has cardinality 2 — useless as a range key.
- **Even distribution**: values are distributed roughly uniformly across the key space so partitions can be sized similarly. Skewed distributions (most records have the same key value) cause hot partitions.
- **Query alignment**: the key should match the dominant range query pattern. If most queries ask for data by `(customer_id, date)`, a compound key of `customer_id:date` as the range key means each customer's temporal data is co-located and scannable efficiently.

**Q7. What are "range boundaries" and how should they be chosen?**
A: Range boundaries are the keys that define where one partition ends and the next begins. Two strategies for selecting them:
- **Static boundaries (pre-defined splits)**: the operator chooses boundaries at schema design time based on expected data distribution. Example: partitioning a `user_id` space by first letter (A–D, D–K, ...). Simple but brittle — if most users have IDs starting with 'M', that partition is overloaded from day one.
- **Data-driven splits**: analyze the actual data distribution (or a sample) and choose boundaries that produce roughly equal partition sizes (equal-depth partitioning). Each partition contains approximately the same number of records. More accurate but requires knowing the data before partitioning, and must be re-evaluated as data evolves.
- **Dynamic splitting** (preferred at scale): start with coarse initial boundaries and let the system automatically split partitions that grow too large or receive too much traffic, moving the split boundary to the median key of the partition. HBase, CockroachDB, and Spanner all use dynamic splitting.

**Q8. What is a compound partition key and how does it extend range partitioning capabilities?**
A: A compound (composite) partition key combines multiple columns into a single ordered key, typically encoded as a byte-comparable concatenation: `key = column1_bytes + separator + column2_bytes + ...`. The range partition operates on this compound key. This enables multi-dimensional range queries: with a compound key `(region, timestamp)`, the range `[(US, 2024-01-01), (US, 2024-12-31)]` scans all US records in 2024, touching only partitions that overlap this range.

DynamoDB makes this explicit: every table has a **partition key** (hash-partitioned) and an optional **sort key** (range-partitioned within each partition). Within a DynamoDB partition, records are stored sorted by sort key — enabling efficient range queries like `query(partition_key=USER123, sort_key BETWEEN 2024-01-01 AND 2024-12-31)`. This two-level scheme (hash outer, range inner) is common in distributed databases.

**Q9. What is lexicographic ordering and why does it matter for string partition keys?**
A: Lexicographic (dictionary) ordering compares strings byte by byte from left to right — the same order a dictionary uses. In range partitioning, string keys are compared lexicographically to determine which partition they belong to. This has a critical implication: numeric strings are ordered lexicographically, not numerically. `"100" < "20" < "9"` lexicographically — so a partition `["1", "5")` contains `"100"`, `"2"`, `"3"`, and `"4"` but not `"5"` or `"50"`.

If keys are numeric, either: (1) zero-pad them to a fixed width (`"0001"`, `"0020"`, `"0100"`) so lexicographic order matches numeric order; (2) use the raw binary big-endian integer representation (used by HBase, BigTable); or (3) use a numeric sort codec (CockroachDB's key encoding preserves numeric order for integers). Failing to account for this produces partition boundaries that don't match expected key distribution.

**Q10. How do you partition a time-series dataset by range, and what is the "hot partition" problem?**
A: A natural partition key for time-series data is timestamp. With range partitioning on timestamp: all data for January goes to one partition, February to another, etc. Range scans for time ranges (e.g., "last 30 days") touch only the relevant partitions — efficient.

The hot partition problem: all new writes target the partition containing the current time — the "latest" partition. Older partitions receive only reads (historical queries). This creates a severe write skew: one node handles 100% of writes while others sit idle. This pattern is called a **monotonically increasing key hot spot** and is the most common failure mode of range partitioning in production. Solutions are covered in the hot spot section, but the core insight is: monotonically increasing keys and range partitioning are fundamentally in tension unless additional distribution is applied.

## Section 3: Range Scans & Query Patterns

**Q11. How does a range scan execute against a range-partitioned table?**
A: A range scan (e.g., `WHERE order_date BETWEEN '2024-01-01' AND '2024-03-31'`) proceeds in three phases:
1. **Partition pruning**: the query planner consults the partition map to identify which partitions overlap the scan range. Only partitions whose `[start_key, end_key)` intersects `['2024-01-01', '2024-03-31']` are candidates. Partitions entirely outside the range are pruned.
2. **Parallel or sequential scan across relevant partitions**: the query engine sends range scan sub-queries to each relevant partition's node. Within each node, the ordered storage engine (B-tree or LSM-tree) performs an efficient seek to the start key and scans forward until the end key.
3. **Merge**: results from multiple partitions are merged in key order (merge of sorted streams — O(K log P) where K is total result size and P is the number of partitions touched) and returned.

If the scan touches many partitions across many nodes (scatter-gather), the total latency is bounded by the slowest node (tail latency). For well-chosen partition keys and narrow range predicates, the scan may touch only 1–2 partitions — nearly as fast as a single-node query.

**Q12. What is "partition pruning" and when does it fail?**
A: Partition pruning is the optimizer's ability to exclude partitions that cannot contain any rows satisfying the query's predicate, based solely on the partition boundary metadata. A partition `[2024-01-01, 2024-02-01)` can be pruned from a query with `WHERE date >= '2024-03-01'` without reading any data from it.

Pruning fails when:
- **The predicate uses a non-partition-key column**: `WHERE amount > 1000` on a table partitioned by `date` — the optimizer cannot prune any partition because high-amount rows can appear in any date partition.
- **The predicate uses a function on the partition key**: `WHERE YEAR(date) = 2024` — the optimizer may not evaluate `YEAR(date)` against partition boundaries if it can't determine the equivalent range. Fix: rewrite as `WHERE date BETWEEN '2024-01-01' AND '2024-12-31'`.
- **The partition key is implicit or wrapped**: ORM-generated queries that transform the key before comparison may prevent the optimizer from matching the predicate to partition boundaries.
- **Type mismatch**: comparing a string predicate to an integer partition key without an implicit cast that the optimizer handles correctly.

**Q13. What is the difference between intra-partition and inter-partition range scans?**
A: An **intra-partition range scan** operates entirely within one partition — the scan start and end keys both fall within the same partition's range. It's a single-node operation: one seek + one forward scan, no network coordination. Latency is bounded by local I/O.

An **inter-partition range scan** spans multiple partitions — the key range crosses one or more partition boundaries. The coordinator must identify all relevant partitions, send sub-scans to each node in parallel, and merge the results. This introduces network latency (one round trip per partition, parallelizable), merge overhead, and tail latency sensitivity (the slowest partition determines total response time). The goal of partition key design is to make frequent range queries intra-partition or touch as few partitions as possible — which is why collocating related data within the same partition (e.g., all of one customer's records in the same partition) is the dominant design principle.

**Q14. How do secondary indexes interact with range partitioning?**
A: The primary partition key determines physical data placement. Secondary indexes (on non-partition-key columns) can be structured in two ways:

- **Local secondary index**: each partition maintains its own index covering only the data within that partition. A secondary index range scan must scatter-gather across all (or many) partitions, merging results. Partition pruning is impossible for secondary index queries if the partition key is not in the predicate. Local indexes are cheap to maintain (no cross-partition writes) but expensive to query.
- **Global secondary index**: a separate index table is itself range-partitioned by the secondary key. A range scan on the secondary key uses the index's own partition map — pruning works on the secondary key. However, a write to the primary table must also update the secondary index — potentially on a different node. This cross-partition write requires either a distributed transaction or an asynchronous update with eventual consistency. DynamoDB's Global Secondary Indexes (GSI) use eventual consistency; CockroachDB uses distributed transactions.

**Q15. What is a "covering index" in the context of range partitioning and why is it particularly valuable?**
A: A covering index is a secondary index that includes all columns needed to answer a query — so the index itself, without accessing the primary data store, can return the complete result. In a range-partitioned system where the primary data is distributed, a covering global secondary index transforms a scatter-gather operation (fan out to N partition nodes for primary data) into a targeted range scan on the index partition(s). The performance impact is dramatic: instead of touching potentially hundreds of primary partition nodes, the query touches only the index partitions whose range overlaps the predicate. The trade-off: larger index storage (includes extra columns) and higher write amplification (every write must update the index with additional columns).

## Section 4: Hot Spots & Load Imbalance

**Q16. What are the three main causes of hot spots in range-partitioned systems?**
A:
- **Monotonically increasing keys**: timestamps, auto-increment IDs, and sequence numbers mean all writes go to the partition containing the current maximum. The "right edge" partition absorbs all write traffic; all other partitions are cold for writes.
- **Key skew / popular keys**: some key values appear far more frequently than others (Zipf distribution). A partition containing a highly popular key prefix receives disproportionate read (and sometimes write) traffic regardless of how evenly the key count is distributed.
- **Poor initial boundary selection**: if partition boundaries are chosen without data distribution knowledge, some partitions end up with significantly more data or traffic than others from the start — a static hot spot that never self-corrects without a resplit.

**Q17. What are the techniques for handling write hot spots from monotonically increasing keys?**
A: Several strategies, ranging from simple to complex:

- **Key salting / prefix hashing**: prepend a random prefix (e.g., `random(0, N)`) to the key before writing: `salted_key = HASH(original_key) % N + ":" + original_key`. Writes distribute across N "salted" partitions. Range scans require querying all N salted variants and merging — trading read amplification for write distribution. Used when writes are dominant and range scans are less frequent.
- **Reverse key index**: reverse the bytes of the key before using it as the partition key. A monotonically increasing key like `20240115T143022` becomes `22030341T51402` — reversal destroys the monotonic property and distributes writes. Reads by exact key still work (just reverse the key again); range scans break (reversed keys are no longer in time order). Appropriate for point-lookup-dominant workloads.
- **Bucket-prefix sharding**: prepend a computed bucket to the key: `bucket = HASH(key) % NUM_BUCKETS`. Similar to salting but deterministic — the same key always gets the same prefix, so point lookups don't need scatter-gather. Range scans still require N-way merge.
- **Application-level key redesign**: choose a partition key that isn't monotonic. For event data, partition by `(user_id, timestamp)` rather than just `timestamp` — writes distribute across user IDs while still enabling efficient per-user time-range queries.
- **Pre-splitting**: for known write patterns, create many partitions at initialization so the write load is distributed from the start, even before any splitting occurs. HBase's `createTable` API accepts pre-split keys.

**Q18. What is a "hot region split" and how do systems like HBase handle it automatically?**
A: A hot region split is when a region (partition) that has grown too large in size or is receiving too much traffic is divided into two smaller regions at the median key. The two new regions replace the original, and one is typically moved to a different RegionServer to distribute load.

HBase triggers automatic splits when a region exceeds the configured size threshold (`hbase.hregion.max.filesize`, default 10GB). The split procedure: (1) identify the midpoint key (the key that equally divides the region's data size); (2) write a split marker to the WAL; (3) create two daughter regions with boundaries `[start, mid)` and `[mid, end)` — both initially pointing to the parent's data files (no data is moved immediately, only boundary metadata is updated); (4) update the META table with the new regions; (5) the RegionServer reads daughter data from the parent's files during compaction, producing separate files for each daughter region. The split is initially cheap (metadata update + reference files); the physical separation of data happens lazily during background compaction.

**Q19. What is "region hotspot after split" and why doesn't splitting always solve the problem?**
A: After a partition is split at its median key, the system has two partitions. If the write pattern is monotonically increasing, all new writes still go to the partition containing the latest key — which is one of the two daughter partitions, typically the "right" one (containing higher keys). The left daughter immediately goes cold (only historical reads). The right daughter accumulates more data and traffic and will need to be split again soon. This cycle repeats: split → right daughter gets all writes → split again → right daughter gets all writes. The result is a cascading series of splits that never resolves the fundamental write concentration.

The fix is not more splits but **key redesign** — changing the key so writes don't concentrate on a single frontier. Splits are a tool for handling organic growth and unforeseeable hotspots, not for fixing structural key design problems.

**Q20. What is "partition skew" distinct from a write hot spot, and what causes it?**
A: Partition skew is a storage imbalance — some partitions contain far more data than others — even without a write hot spot. Causes:
- **Non-uniform key distribution**: key values cluster in certain ranges. A user ID space partitioned alphabetically into equal-letter-count ranges may have 40% of users with last names starting A–C (if the dataset is English-speaker-heavy), overloading that partition.
- **Delete patterns**: if older data is frequently deleted but newer data is retained, partitions containing older ranges may shrink while newer partitions grow — disrupting the original balance.
- **Variable record sizes**: if records with keys in a certain range are systematically larger (e.g., enterprise customers with more data), their partition grows faster even with equal record counts.

Partition skew causes uneven disk utilization and memory pressure across nodes, and may require manual re-splitting or boundary adjustment even if no single partition is a traffic hot spot.

## Section 5: Splitting, Merging & Rebalancing

**Q21. What is partition rebalancing and why is it necessary?**
A: Rebalancing is the process of moving partitions between nodes to restore even load distribution. It becomes necessary when: (1) a new node is added to the cluster — it starts empty while others carry all the load; (2) a node is removed — its partitions must be distributed to surviving nodes; (3) partitions split or merge — the resulting partitions may be on nodes that are already overloaded; (4) traffic patterns shift — what was balanced when partitions were assigned may become skewed over time.

In range-partitioned systems, rebalancing means **moving a partition's data from one node to another** while keeping the partition's key range boundaries constant. The key range doesn't change — only the node responsible for it. This is simpler than rehashing in hash-partitioned systems (which requires re-mapping many keys). The cost: transferring potentially gigabytes of data across the network during the move, while the partition continues to serve traffic from the old node until the move completes.

**Q22. How does a live partition move work without downtime?**
A: A live partition move (used by HBase, CockroachDB, Spanner) proceeds in phases to minimize unavailability:
1. **Snapshot the partition**: take a snapshot or begin streaming the partition's data to the destination node. The source node continues serving reads and writes during transfer.
2. **Stream incremental changes**: while the bulk of the data is being transferred, the source node buffers new writes. These are also streamed to the destination so it stays up to date.
3. **Catch-up**: once the bulk transfer completes, stream the remaining buffered writes to the destination until it is nearly in sync (within milliseconds of the source).
4. **Cutover**: briefly pause writes to the source partition (a few milliseconds), apply the last few remaining writes to the destination, update the routing table to point to the destination, and resume writes on the destination. The brief write pause is the only downtime window — typically < 100ms.
5. **Source cleanup**: once the routing table is updated and in-flight requests have drained, the source's copy of the partition data is deleted.

This protocol ensures the partition is always available for reads (from source during transfer, from destination after cutover) and that no writes are lost.

**Q23. What is partition merging and when is it triggered?**
A: Partition merging is the inverse of splitting: two adjacent partitions are combined into a single partition. Triggered when: a partition has grown so small (due to deletions) that it's underutilizing the node and generating overhead (metadata, heartbeats, replication) disproportionate to its data size. A node with thousands of tiny partitions has significant per-partition overhead even if the total data is small.

Merge procedure: the two adjacent partitions (their ranges must be contiguous — `[A, M)` and `[M, Z)` can merge into `[A, Z)`) must be on the same node (or one is moved to the other's node first). Their data structures are merged (B-tree merge or SST file adoption), the routing table is updated with the combined range, and the old partition entries are removed. CockroachDB automatically merges ranges that fall below a minimum size threshold.

**Q24. What is the "thundering herd on split" problem and how is it mitigated?**
A: When a large, hot partition splits, the split event is visible to the routing tier — which must update its cached partition map. During the brief window when the map is stale, some requests may still route to the old (now non-existent) partition or route incorrectly to one of the daughter partitions for keys that belong to the other. Additionally, immediately after the split, both daughter partitions may still be on the same node (the move to a new node is asynchronous). The hot partition's traffic hasn't actually distributed yet — it's just been logically split.

The thundering herd variant: many clients all simultaneously invalidate their cached routing info and retry their requests, causing a burst of metadata lookups to the partition map service. Mitigation: clients cache partition maps with a version number; on a routing miss (request rejected by the node because the key is no longer in its range), they refresh only the affected portion of the map, not the entire map. Exponential backoff with jitter on routing errors prevents the retry burst.

## Section 6: Range Partitioning in Real Systems

**Q25. How does HBase implement range partitioning, and what are the key design considerations for HBase row keys?**
A: HBase stores data in **regions** — range partitions of the row key space. Each region is served by exactly one RegionServer. The region boundaries (row key ranges) are tracked in the `hbase:meta` table. A client first queries the META table (cached in ZooKeeper) to find which RegionServer holds a given row key, then communicates directly with that RegionServer.

HBase row key design is critical because the row key is the *only* dimension along which data is sorted and partitioned:
- **Avoid monotonically increasing keys** (timestamps, sequential IDs): causes all writes to one region (the "leading edge" region). Use salting, hashing, or reverse-byte encoding.
- **Collocate related data**: if queries frequently fetch multiple rows together, design the key so those rows are adjacent: `user_id:event_type:timestamp` collocates all events of a given type for a user.
- **Row key is the primary sort within a region**: columns within a row are unordered; ordering must be encoded in the row key.
- **Variable-length keys**: HBase keys are arbitrary byte arrays — use fixed-width components within compound keys to avoid ambiguous boundary parsing.

**Q26. How does CockroachDB implement range-based partitioning and rebalancing?**
A: CockroachDB partitions data into **ranges** of approximately 512MB each (configurable). Every row of every table has a key that is a CockroachDB-encoded representation of the primary key, and all data is stored in a single sorted key-value space (RocksDB). Ranges are automatically split when they exceed the size threshold and merged when they fall below a minimum.

Rebalancing is handled by the **leaseholder** (the range's primary) and the **rebalancer** (a background process on each node). The rebalancer periodically evaluates store statistics (disk usage, QPS per range, replica count) and moves range replicas to underutilized stores. A **lease transfer** is cheaper than a replica move: the leaseholder designation changes (just a metadata update) without moving data. A replica move requires shipping data.

Partitioning in CockroachDB also supports **locality-aware placement**: using `PARTITION BY RANGE` + `CONFIGURE ZONE` statements, specific ranges can be pinned to nodes in specific regions, implementing geo-partitioning without sacrificing the global SQL interface.

**Q27. How does DynamoDB use range partitioning (the sort key), and how does it differ from top-level partitioning?**
A: DynamoDB uses a two-level scheme:
- **Partition key (hash key)**: determines which physical partition stores the item. DynamoDB hashes the partition key and maps the hash to a partition. This is hash partitioning — no ordering, uniform distribution.
- **Sort key (range key)**: within a single partition, items are stored sorted by the sort key. Queries can use range predicates on the sort key: `query(pk=USER123, sk BETWEEN "order#2024-01" AND "order#2024-12")`. This is range partitioning within a partition.

The DynamoDB data model is `(partition_key, sort_key) → attributes`. Items sharing a partition key form an "item collection" — all stored on the same physical partition, sorted by sort key. Range queries are always scoped within one partition key — you cannot efficiently range-query across multiple partition keys (that requires a Global Secondary Index, which is separately partitioned). This design combines hash partitioning's write distribution with range partitioning's query efficiency, scoped to within-partition ranges.

**Q28. How does MySQL's `RANGE` partitioning work, and what are its practical limitations?**
A: MySQL `RANGE` partitioning divides rows based on column value ranges:

```sql
CREATE TABLE orders (
  order_date DATE,
  order_id INT,
  amount DECIMAL(10,2)
) PARTITION BY RANGE (YEAR(order_date)) (
  PARTITION p2022 VALUES LESS THAN (2023),
  PARTITION p2023 VALUES LESS THAN (2024),
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

Each partition is stored as a separate `.ibd` file on the same server. Partition pruning works: `WHERE order_date >= '2024-01-01'` only scans `p2024` and `p_future`.

Practical limitations: (1) MySQL range partitioning is **intra-server** — all partitions live on the same machine. It improves query pruning and maintenance (dropping a partition is O(1)) but does not distribute load across servers. For multi-server distribution, MySQL uses sharding at the application layer (e.g., Vitess) on top of MySQL partitioning. (2) The partition expression must be an integer or date function — arbitrary expressions are not supported. (3) Adding a new partition requires an `ALTER TABLE` — there is no automatic splitting based on size or load.

**Q29. How does PostgreSQL declarative table partitioning implement range partitioning?**
A: PostgreSQL supports declarative range partitioning (since version 10):

```sql
CREATE TABLE measurements (
  logdate DATE,
  peaktemp INT,
  unitsales INT
) PARTITION BY RANGE (logdate);

CREATE TABLE measurements_y2023 PARTITION OF measurements
  FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE measurements_y2024 PARTITION OF measurements
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

Partitions are full child tables — each has its own indexes, toast tables, and can be independently `DETACH`ed (converting a partition back into a standalone table in O(1)). Attaching a new partition is also O(1). Constraint exclusion enables partition pruning: `WHERE logdate >= '2024-06-01'` only scans `measurements_y2024`. PostgreSQL supports multi-column range partition keys and can sub-partition (partition partitions further). Limitation: unlike HBase or CockroachDB, PostgreSQL range partitioning is intra-server — it's a query optimization and maintenance tool, not a distribution mechanism.

## Section 7: Failure Modes & Anti-patterns

**Q30. What is the "write-all-to-one-partition" anti-pattern and what are its symptoms?**
A: This is the monotonically increasing key problem in production. Symptoms: one node in the cluster has 90–100% write throughput; all other nodes are idle for writes. The active node's disk fills faster than others. Latency for writes increases as the node approaches its throughput limit. Replication lag on the replicas of the hot partition grows. The hot partition is continuously splitting, but each split immediately produces a new hot "right edge" partition.

Diagnosis: check per-partition write QPS in the cluster's monitoring dashboard. If one partition (or a small rotating set of recently-split partitions) accounts for nearly all writes, this anti-pattern is present. Root cause: the partition key is a timestamp, auto-increment ID, or other monotonically increasing value. Fix requires key redesign, not operational tuning.

**Q31. What is "partition boundary leakage" and how does it cause query errors?**
A: Partition boundary leakage occurs when the application's routing logic has a stale partition map, and it sends a request to a node that no longer owns the targeted key range (because a split, merge, or rebalance has occurred). The receiving node detects that the key is outside its range and returns an error (e.g., HBase's `NotServingRegionException`, CockroachDB's `RangeKeyMismatch` error).

Well-designed clients handle this transparently: on receiving such an error, refresh the partition map from the metadata service and retry the request. The retry hits the correct node. The error is transient — it resolves in one retry. The anti-pattern is a client that does not implement this retry logic and surfaces the routing error directly to the application as a hard failure. Production SDK clients for distributed databases (HBase client, CockroachDB's SQL driver) handle this automatically; custom routing layers must implement it explicitly.

**Q32. What is "cross-partition transaction cost" and why is it a systemic concern for range-partitioned systems?**
A: A transaction that touches keys in multiple partitions (possibly on different nodes) requires cross-partition coordination — a distributed transaction. This involves: locking records on multiple nodes, coordinating the commit decision (often via 2PC), and ensuring all-or-nothing atomicity across the participating nodes. The costs:
- **Latency**: each participant adds a round trip (prepare + commit phases). A transaction spanning 3 nodes across 3 data centers adds 3 × WAN round trips.
- **Throughput reduction**: locks held across partitions block other transactions on the same rows for the duration of the 2PC.
- **Coordinator failure risk**: as covered in the 2PC section, coordinator failure during commit leaves participants in an in-doubt state.

Range partitioning mitigates this by design: if the partition key is chosen so that frequently co-modified records share the same key range, they co-locate on the same partition — transactions become single-partition and thus single-node, eliminating cross-partition coordination entirely. The primary goal of partition key design in transactional systems is colocation of records that change together.

**Q33. What is a "range scan storm" and when does it occur?**
A: A range scan storm is when many concurrent clients simultaneously execute broad range scans that touch many partitions, generating scatter-gather fan-out that overwhelms the partition nodes. Each scan fans out to P partitions; N concurrent scans generate N × P parallel sub-queries across the cluster. If P is large (the scan is broad) and N is high (many users running reports simultaneously), every partition node receives many simultaneous sub-queries from many scans — a read amplification crisis.

Common trigger: an analytics workload added to an OLTP range-partitioned database. OLTP queries typically touch 1–3 partitions (narrow key ranges); analytics queries scan entire tables (all partitions). When analytics and OLTP share the same cluster, analytics range scan storms starve OLTP reads.

Mitigations: separate OLAP from OLTP (read replicas for analytics), add rate limiting on scan fan-out degree (max concurrent sub-queries per scan), implement query queuing for broad scans, or use a dedicated columnar store for analytics where table-scan performance is optimized.

**Q34. What is "empty partition overhead" and how does it manifest after time-based range deletion?**
A: In a time-series or log table partitioned by date, old data is frequently deleted (purged after 90 days). If deletion is done by `DELETE WHERE date < '2023-12-01'` (row-by-row deletion), the old partitions become empty but still exist — they still appear in the partition map, still require heartbeats and metadata, and still must be checked during partition pruning. An empty partition is nearly free to serve but still has a fixed per-partition overhead that accumulates.

Fix: use **partition drop** instead of row deletion for time-series data. `DROP PARTITION p_2023_q4` (MySQL) or `DETACH PARTITION measurements_y2023 FROM measurements; DROP TABLE measurements_y2023` (PostgreSQL) removes the partition and all its data in O(1) — a metadata operation, not a row-by-row operation. This is the primary operational advantage of date-based range partitioning: "roll off" old data by dropping entire partitions rather than deleting rows, which is orders of magnitude faster and leaves no empty partition overhead.

## Section 8: Trade-offs & Decision-Making

**Q35. How do you decide between range partitioning and hash partitioning for a new system?**
A: Work from query patterns backward to partitioning strategy:
- **If range queries are dominant** (date ranges, prefix scans, customer-scoped queries): range partitioning enables efficient scan pruning. Hash partitioning turns every range query into an expensive scatter-gather.
- **If point lookups dominate** (fetch by exact key): hash partitioning distributes load evenly; range partitioning is acceptable but offers no advantage. If write load is high with monotonic keys, hash partitioning is safer.
- **If write distribution is paramount**: hash partitioning distributes writes evenly by definition. Range partitioning with monotonic keys concentrates writes.
- **If data locality matters** (transactions usually touch keys in the same range, or data has regional affinity): range partitioning enables colocation. Hash partitioning distributes related keys to different nodes, forcing cross-partition transactions.
- **If neither is dominant**: use a compound approach — hash partition by one dimension (for distribution) and range sort within each partition by another dimension (for within-partition queries). This is the DynamoDB model and is widely applicable.

**Q36. What is geo-partitioning and how does range partitioning enable it?**
A: Geo-partitioning pins specific ranges of data to specific geographic regions — typically to satisfy data residency requirements (EU user data must stay in EU) or to reduce read latency (serve users from nearby nodes). Range partitioning enables this because the partition is the unit of placement: a range `[EU_USER_MIN, EU_USER_MAX)` can be configured to only place replicas on nodes in European data centers.

CockroachDB implements this via `PARTITION BY RANGE` + `CONFIGURE ZONE USING constraints = '[+region=europe-west]'`. Writes and reads for EU-range keys are routed to EU nodes; non-EU keys go to other regions. The global index and SQL interface are unaffected — the geo-partitioning is transparent to the application. This is much simpler to implement with range partitioning than with hash partitioning, where EU users' keys would be scattered across all partitions by the hash function.

**Q37. How does range partitioning interact with data archival and the "tiered storage" pattern?**
A: Range partitioning on a time key makes tiered storage natural: recent partitions (hot data) live on fast NVMe nodes; older partitions (warm data) live on HDD nodes; ancient partitions (cold data) live on object storage (S3-compatible). The partition is the granularity at which data moves between tiers — an entire partition migrates atomically as a unit.

Implementation in practice: configure per-partition storage policies in the partition map metadata. As a partition ages (its key range falls outside the "hot" window), the storage manager moves it to the next tier. Queries that span tiers simply route some sub-scans to NVMe nodes and others to HDD or object storage nodes — slower for the cold portions but correct. This pattern is heavily used in time-series databases (ClickHouse's TTL moves, Apache Druid's deep storage) and is far simpler to implement with range partitioning (whole-partition moves) than with hash partitioning (where individual records from every partition age out, requiring per-record migration).

**Q38. When should you pre-split partitions, and how do you determine the number of initial partitions?**
A: Pre-splitting is creating multiple partitions before any data is loaded, rather than starting with one partition and letting it split organically. Pre-split when:
- **You know the key distribution**: if loading 1 billion rows with IDs 0–999,999,999, pre-split into 100 partitions at 10M-key intervals rather than letting a single initial partition absorb all writes until it splits repeatedly.
- **You have a time-based key with known future load**: for a time-series system, pre-create partitions for the next year of months, preventing the "split storm" that would occur as the current time crosses boundaries.
- **The system has high write throughput from the start**: if you expect millions of writes/second immediately after launch, pre-splitting avoids the cold-start period where all writes hit one partition.

Number of initial partitions: a common heuristic is `2 × number_of_nodes × replication_factor` — enough that each node handles several partitions (allowing fine-grained rebalancing) but not so many that per-partition overhead dominates. For HBase, 10–20 pre-splits per RegionServer is a reasonable starting point; CockroachDB's automatic splitting makes pre-splitting less critical.

## Section 9: Scenario / System Design Style Questions

**Q39. "Design the partitioning strategy for a multi-tenant SaaS analytics database where each tenant has a `tenant_id` and queries are always scoped to a single tenant."**
A: The query access pattern is always `WHERE tenant_id = ? AND ...` — all queries are tenant-scoped. This is a perfect case for range partitioning on `tenant_id` with data colocation:

- **Partition key**: `tenant_id` (range-partitioned). All data for one tenant lives in the same partition or a small set of contiguous partitions. Single-tenant queries are single-partition — no scatter-gather.
- **Compound key**: `(tenant_id, entity_type, entity_id)` or `(tenant_id, created_at)` as the full sort key. Within a tenant's partition, data is sorted by the secondary dimensions, enabling efficient sub-tenant range scans.
- **Partition sizing**: small tenants share a partition; large tenants get their own partition(s). Use range boundaries that produce roughly equal partition sizes (data-driven split points), or split large-tenant partitions as they grow.
- **Colocation benefit**: cross-table joins for a tenant's data are intra-partition (both the `orders` and `users` tables for tenant X share the same partition key range) — CockroachDB's interleaved tables or Spanner's table interleaving implement this explicitly.
- **Hot spot risk**: new tenants are all assigned to adjacent key ranges. If a viral SaaS product acquires 1000 new tenants simultaneously, they hash to the same partition (alphabetically adjacent names). Mitigate: salt tenant IDs or assign a hash of `tenant_id` as the partition key for distribution, then maintain a mapping table for routing. This trades query simplicity for write distribution.

**Q40. "Your time-series IoT database is partitioned by sensor timestamp. One node is receiving all writes. How do you fix it without losing the ability to query by time range?"**
A: The root cause is monotonically increasing timestamps concentrating writes on the latest partition. Fix with **compound partitioning** that preserves time-range queryability:

- **New partition key**: `(sensor_id % NUM_BUCKETS, truncated_timestamp)`. Pre-create `NUM_BUCKETS` × `NUM_TIME_WINDOWS` partitions. Each time bucket has `NUM_BUCKETS` partitions, one per hash bucket. Writes for the current time window distribute across `NUM_BUCKETS` partitions — `NUM_BUCKETS` nodes each receive 1/NUM_BUCKETS of write traffic.
- **Time range queries**: a query `WHERE timestamp BETWEEN T1 AND T2` scans all `NUM_BUCKETS` partitions for each time window in the range. This is `NUM_BUCKETS`-way scatter-gather per time window — acceptable if `NUM_BUCKETS` is small (8–16). The result is merged in timestamp order.
- **Per-sensor queries**: `WHERE sensor_id = X AND timestamp BETWEEN T1 AND T2` routes to the single bucket `X % NUM_BUCKETS` for each time window — still `O(time_windows)` partitions but only 1 bucket per window, not `NUM_BUCKETS`. Efficient.
- **Migration**: add the new compound key schema, backfill old data with the bucket prefix (a background job reads old records and inserts with the new key), then cut over writes. This is a dual-write migration pattern common in production resharding.

**Q41. "A CockroachDB cluster is rebalancing partitions continuously, causing high CPU and network load. How do you diagnose and tune it?"**
A: Continuous rebalancing means the rebalancer is never satisfied — it keeps finding imbalances to fix.

Diagnosis:
1. **Check range count per node**: `SHOW RANGES` or the CockroachDB Admin UI — are ranges evenly distributed? If one node has 5× more ranges, the rebalancer is trying to move them but failing to converge.
2. **Check replica count vs. replication factor**: if the replication factor changed recently or nodes were added/removed, the rebalancer is placing new replicas. This is expected but transient.
3. **Check QPS per range**: `SHOW RANGE STATISTICS` — are some ranges much hotter than others? The rebalancer moves lease-holders (not data) toward the nodes where the queries originate. If a hot range is co-located with its clients, leaseholder moves converge quickly. If not, the leaseholder churns.
4. **Check for range thrashing**: ranges splitting and merging repeatedly indicate unstable partition sizes — possibly near the split threshold. Increase `kv.range.max_bytes` (split threshold) to give ranges more room before splitting.

Tuning:
- Set `kv.rebalance.min_balance_fraction` higher — the rebalancer only acts when imbalance exceeds this fraction. Default is 5%; increasing to 10% reduces rebalancing frequency.
- Limit rebalance rate: `kv.snapshot_rebalance.max_rate` and `kv.snapshot_recovery.max_rate` cap bytes/second of replica transfer. Reducing them lowers CPU and network impact.
- Pin hot ranges to specific nodes using `CONFIGURE ZONE USING constraints` if certain ranges have known locality affinity.

**Q42. "How would you implement 'partition drop for data expiry' in a PostgreSQL time-series table, and why is it faster than DELETE?"**
A: Schema: the table is range-partitioned by month.

```sql
CREATE TABLE events (
  event_time TIMESTAMPTZ NOT NULL,
  user_id BIGINT,
  payload JSONB
) PARTITION BY RANGE (event_time);

-- Create monthly partitions
CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_2024_02 PARTITION OF events
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ... etc.
```

Data expiry — drop the partition for January 2023 (90-day retention):
```sql
ALTER TABLE events DETACH PARTITION events_2023_01;
DROP TABLE events_2023_01;
```

Why faster than `DELETE WHERE event_time < '2023-02-01'`:
- `DELETE` must find each row (full partition scan), acquire row-level locks, write delete markers (dead tuples) to the WAL, trigger VACUUM to reclaim space, and update indexes — all O(rows_deleted) work.
- `DROP TABLE` is a metadata operation: it removes the file system entry for the table's data files (`.ibd` in MySQL, data files in PostgreSQL) and its index files. The OS reclaims disk space without reading a single row. The operation completes in milliseconds regardless of partition size.
- Additionally, `DELETE` generates WAL entries for every deleted row — massive I/O and replication traffic. `DROP` generates a single WAL entry.

The partition drop approach is the primary operational reason to use range partitioning for time-series data even in single-server scenarios. It turns a multi-hour maintenance operation into a sub-second one.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                        | Range Partitioning                                         | Hash Partitioning                                          |
|---                            |---                                                         |---                                                         |
| Key ordering preserved        | Yes — neighboring keys co-located                          | No — hash scatters neighboring keys                        |
| Range scan efficiency         | High — partition pruning limits nodes scanned              | Low — scatter-gather across all partitions                 |
| Write distribution            | Uneven if keys are monotonic                               | Even (with good hash function)                             |
| Hot spot risk                 | High with timestamps / auto-increment IDs                  | Low — hash distributes uniformly                           |
| Data colocation               | Natural — related key ranges share a partition             | Poor — hash separates related keys                         |
| Rebalancing unit              | Range (contiguous key interval) moves between nodes        | Key remapping (consistent hashing minimizes movement)      |
| Metadata                      | Partition map (range → node)                               | Hash ring / slot map (hash → node)                         |
| Geo-partitioning              | Natural — pin key ranges to specific regions               | Difficult — hash scatters data globally                    |
| Data archival                 | Drop entire partitions in O(1)                             | Must delete row by row (no whole-partition drop)           |
| Cross-partition transactions  | Avoidable by colocation if key is well designed            | Frequent — related data often on different nodes           |
| Splitting trigger             | Size or load threshold on a range                          | Add node → rehash / rebalance ring                         |
| Best for                      | Time-series, tenant data, geographic ranges, audit logs    | High-throughput point lookups, uniform write distribution  |

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Range partition               | Contiguous interval `[start, end)` of the key space assigned to a single node                               |
| Partition map / routing table | Metadata mapping each key range to its owning node; consulted on every read/write                           |
| Partition pruning             | Query optimizer eliminating partitions that cannot contain rows matching the predicate                       |
| Hot spot                      | A partition receiving disproportionately high traffic, usually from monotonically increasing keys             |
| Monotonic key hot spot        | All writes target the "leading edge" partition because the key always increases (timestamps, auto-increment) |
| Key salting                   | Prepending a random or hashed prefix to distribute monotonic key writes across N partitions                  |
| Region / tablet               | System-specific name for a range partition (HBase: region, CockroachDB: range, Spanner: tablet)             |
| Auto-split                    | System-initiated partition split when size or load threshold is exceeded; splits at median key               |
| Intra-partition range scan    | Scan within a single partition — single-node, no coordination                                               |
| Inter-partition range scan    | Scan spanning multiple partitions — scatter-gather across nodes, merged at coordinator                       |
| Scatter-gather                | Fan-out to N partition nodes for sub-scans, then merge results at the coordinator                            |
| Local secondary index         | Index maintained per partition; range scans require scatter-gather across all partitions                     |
| Global secondary index        | Index table separately range-partitioned by secondary key; enables pruned secondary range scans              |
| DynamoDB sort key             | Range key within a DynamoDB partition; items within a partition sorted by sort key                           |
| Partition drop                | O(1) deletion of an entire partition's data by removing its files; used for time-series expiry              |
| Geo-partitioning              | Pinning specific key ranges to nodes in specific geographic regions for data residency or latency            |
| Rebalancing                   | Moving partitions between nodes to restore even load/storage distribution as cluster topology changes        |
| Compound partition key        | Multi-column key encoded as ordered bytes; enables range scans on multiple dimensions                        |
| Lexicographic ordering        | String comparison byte-by-byte; "100" < "20" — zero-pad numerics to match intended sort order               |

**Tip for the interview:** Range partitioning questions almost always lead to the monotonically increasing key trap — the interviewer wants to see whether you proactively identify it. Name it early: "with a timestamp partition key, all writes hit the latest partition — this is the classic hot spot." Then offer concrete solutions (salting, compound keys, bucket-prefix) and explain the read trade-off each introduces. The second level interviewers probe: partition pruning (why it fails with function-wrapped predicates), the O(1) partition drop vs. O(N) DELETE distinction, and why cross-partition transactions are expensive (motivating colocation by partition key design). The DynamoDB two-level model (hash outer, range inner) is a frequently asked follow-up — being able to explain why it exists and what problem each level solves shows architectural fluency beyond textbook definitions.
