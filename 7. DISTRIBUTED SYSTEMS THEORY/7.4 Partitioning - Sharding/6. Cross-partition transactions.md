# Cross-Partition Transactions — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem

**Q1. What is a cross-partition transaction, and why is it hard?**
A: A cross-partition transaction is a transaction that reads or writes data spanning multiple shards, nodes, or partitions in a distributed system — data that does not live on the same machine and cannot be updated with a single local ACID transaction. It is hard for a fundamental reason: the atomicity and isolation guarantees that a single-node database provides for free (via local locks and a single WAL) must now be coordinated across multiple independent nodes that can each fail, be slow, or be temporarily unreachable.

The specific hardness: on a single machine, the database engine ensures either all changes commit or all changes roll back — the storage engine enforces this. Across machines, there is no shared storage engine. Each node controls only its local data. To achieve atomicity across nodes, you need a protocol that gets all nodes to agree to either all commit or all abort — and that agreement must survive partial failures (some nodes crash mid-protocol), network partitions (nodes can't communicate), and the ambiguity that arises when you can't tell whether a remote node committed or crashed.

**Q2. What are the failure modes that make cross-partition transactions hard that don't exist locally?**
A: Local transactions fail cleanly — the database either commits or crashes, and on restart it recovers to a consistent state via the WAL. Cross-partition transactions introduce failure modes with no local equivalent:

- **Partial commit** — Node A commits its leg of the transaction; Node B crashes before committing. The transaction is half-committed — a state that is impossible in a local transaction (the entire WAL is committed or not) but trivially achievable in a distributed one.
- **Coordinator failure** — the node orchestrating the transaction crashes after instructing some participants to commit but before instructing others. Participants are left waiting indefinitely — they've locked resources and can't release them until they know the outcome.
- **Network partition mid-transaction** — a participant has prepared (locked resources, written to WAL) but loses connectivity to the coordinator. It cannot commit or abort unilaterally — it must wait. But the coordinator may have moved on (crashed or timed out the transaction).
- **Uncertainty window** — a participant that sent its prepare-OK response doesn't know if the coordinator received it before crashing. It can't safely commit (maybe others aborted) or safely abort (maybe the coordinator committed the rest). This uncertainty is the core of why distributed transactions are hard.
- **Cascading locks** — a transaction that holds locks across multiple nodes holds those locks for the entire duration of cross-node communication. Network latency multiplies lock hold times compared to local transactions, increasing contention and the risk of deadlock across nodes.

**Q3. What are the use cases that genuinely require cross-partition transactions?**
A: Not every multi-node write requires a full cross-partition transaction — sometimes relaxed consistency (sagas, eventual consistency) is sufficient. Genuine cross-partition transaction requirements arise when:

- **Financial transfers** — debiting Account A (on shard 1) and crediting Account B (on shard 2) must be atomic. A partial commit (debit without credit, or credit without debit) is a serious financial error.
- **Inventory + order creation** — an order must decrement inventory and create an order record atomically. Decrementing inventory without creating the order (or vice versa) leaves the system in an incorrect state that requires manual correction.
- **Multi-entity constraint enforcement** — uniqueness across a partitioned key space (e.g., a username must be globally unique across user shards), referential integrity across shard boundaries.
- **Batch event processing with atomicity** — a payment processor that must atomically mark a batch of transactions as settled across multiple customer accounts.
- **Distributed counter with exact semantics** — a limited-supply resource (seats, coupons, licenses) where the count is sharded for throughput but exact deduction without overselling requires atomicity.

The common thread: business logic where partial success is worse than total failure, and where the system cannot tolerate eventually recovering the partial failure (because by then, the external world may have already acted on the incorrect partial state — the customer has their goods, the seat is occupied, the money is spent).

## Section 2: Two-Phase Commit (2PC)

**Q4. What is two-phase commit (2PC), and what problem does it solve?**
A: Two-phase commit (2PC) is the foundational protocol for achieving atomicity across multiple distributed participants. It solves the atomic commit problem: given N participants that have each done some local work as part of a distributed transaction, ensure that either all of them commit (make their work permanent) or all of them abort (undo their work) — even in the presence of failures.

The protocol has two phases:

**Phase 1 — Prepare (Voting):**
1. The coordinator sends a `PREPARE` message to all participants.
2. Each participant checks whether it can commit its local portion: it flushes its changes to a WAL, acquires all necessary locks, and enters a "prepared" state — a state where it is ready to commit but has not yet committed.
3. Each participant responds with either `VOTE-COMMIT` (I can commit; I've persisted enough to guarantee I can commit even if I crash now) or `VOTE-ABORT` (something went wrong; I cannot commit).

**Phase 2 — Commit (Decision):**
4. The coordinator collects votes. If all participants voted COMMIT, the coordinator decides to commit and sends `COMMIT` to all participants. If any participant voted ABORT (or didn't respond within a timeout), the coordinator decides to abort and sends `ABORT` to all participants.
5. Each participant receives the decision, applies it (commits or rolls back its local changes), releases locks, and acknowledges the coordinator.
6. Once all acknowledgments are received, the transaction is complete.

**Q5. What is the "blocking problem" in 2PC, and why is it fundamental?**
A: The blocking problem is 2PC's most significant weakness: if the coordinator crashes after sending PREPARE but before sending the COMMIT/ABORT decision, participants that responded VOTE-COMMIT are stuck. They cannot:
- **Commit unilaterally** — maybe another participant voted ABORT. Committing unilaterally would violate atomicity.
- **Abort unilaterally** — maybe all other participants voted COMMIT and the coordinator decided to commit before crashing. Aborting unilaterally would also violate atomicity.

So they wait — holding their locks, blocking other transactions that need those resources — indefinitely, until the coordinator recovers. This is the "blocking" nature of 2PC: the protocol can be blocked by a single coordinator failure at precisely the worst moment. The duration of blocking is bounded only by the coordinator's recovery time — which can be minutes to hours if the coordinator disk has failed and must be replaced.

This is a fundamental property of 2PC, not an implementation flaw. The FLP impossibility result implies that no asynchronous consensus protocol can avoid blocking in the presence of failures — 2PC's blocking is the concrete manifestation of this theorem.

**Q6. How does 2PC handle the case where a participant crashes after voting COMMIT but before receiving the COMMIT decision?**
A: This is why the prepare phase requires durable writes — the participant must persist its prepared state to disk (WAL) before sending VOTE-COMMIT. The recovery sequence:

1. Participant crashes after writing "PREPARED for transaction T" to its WAL, then crashes.
2. Participant recovers. It reads its WAL and finds the prepared-but-not-committed record for transaction T.
3. Participant contacts the coordinator to ask: "What was the outcome of transaction T?"
4. If the coordinator committed: participant commits its prepared changes.
5. If the coordinator aborted: participant aborts and discards its prepared changes.
6. If the coordinator is also down (can't reach it): participant waits for the coordinator to recover (blocking).

The WAL record with "PREPARED" is the checkpoint that makes recovery possible. Without it, a restarted participant wouldn't know whether it voted COMMIT or ABORT and couldn't recover safely. This is why 2PC requires two fsyncs per participant per transaction: one for the prepared state (phase 1) and one for the committed/aborted state (phase 2) — making 2PC expensive in terms of disk I/O.

**Q7. What is "presumed abort" optimization in 2PC, and how does it reduce disk writes?**
A: Presumed abort is an optimization that eliminates the need for participants to persistently log the coordinator's ABORT decision. The key insight: if a coordinator crashes and its log doesn't mention a transaction, the default assumption on recovery is that it aborted (hence "presumed abort"). This is safe because:

- If the coordinator logged a COMMIT decision and sent it before crashing, participants will have received COMMIT and will eventually commit. The commit record is in the coordinator's log.
- If the coordinator crashed before deciding (or decided to abort), participants that are waiting can safely be told "abort" on coordinator recovery — the coordinator's log has no commit record for this transaction.

Under presumed abort, participants don't need to log the ABORT decision when they receive it from the coordinator — they just abort and release locks. Only the COMMIT decision needs to be persistently logged (on both coordinator and participants). This reduces the number of required fsyncs per transaction from four (coordinator prepare, participant prepare, coordinator commit, participant commit) to two in the abort case and three in the commit case, meaningfully improving average-case performance.

**Q8. What is 3PC (three-phase commit), and does it solve 2PC's blocking problem?**
A: Three-phase commit (3PC) adds a third phase between prepare and commit to eliminate the blocking problem in some failure scenarios. The three phases:

1. **Can-commit** — coordinator asks participants: "Can you commit?" Participants respond yes/no without acquiring locks or persisting anything. A lightweight pre-check.
2. **Pre-commit** — coordinator sends PRE-COMMIT if all said yes. Participants acknowledge. Now if the coordinator crashes, participants know the coordinator intended to commit — they can complete the commit among themselves without waiting for the coordinator.
3. **Do-commit** — coordinator sends DO-COMMIT. Participants commit and release locks.

The key addition: in the pre-commit phase, participants know enough to commit without the coordinator if the coordinator fails — eliminating the indefinite blocking of 2PC. However, 3PC only works in a **synchronous network** (where messages are guaranteed to arrive within a bounded time). In an asynchronous network (which is the realistic model), 3PC can still block or produce incorrect results during a network partition. A partition during phase 2 can leave some participants in pre-commit state and others still in can-commit state — if the pre-commit participants timeout and commit while the can-commit participants abort (because they never received pre-commit), atomicity is violated.

In practice, 3PC is rarely used in production systems. It's more complex than 2PC, has higher message overhead, and its non-blocking guarantee only holds under the unrealistic assumption of a synchronous network. Modern systems prefer Paxos/Raft-based commit protocols (which do work in asynchronous networks) over 3PC.

## Section 3: Saga Pattern

**Q9. What is the Saga pattern, and how does it differ from 2PC?**
A: A Saga is a sequence of local transactions, each on a single partition, where each step has a corresponding compensating transaction that can undo its effects if a later step fails. Rather than holding locks across all participants for the duration of the transaction, a Saga releases locks after each local step — trading strong atomicity for eventual atomicity with compensation.

The fundamental difference from 2PC:

| | 2PC | Saga |
|--- |--- |--- |
| Atomicity | Atomic by protocol (all-or-nothing simultaneously) | Eventual (all-or-nothing via compensation) |
| Lock duration | Holds locks across all participants for full duration | Releases locks after each local step |
| Failure handling | Coordinator drives abort of all participants | Compensating transactions undo completed steps |
| Intermediate states | Not visible (isolation maintained) | Visible to other transactions during execution |
| Suitable for | Short, low-contention cross-partition transactions | Long-running workflows, high-contention scenarios |
| Complexity | Protocol complexity | Business logic complexity (compensation design) |

A Saga is appropriate when: the business process is long-running (seconds to minutes, not milliseconds), intermediate states are acceptable (or can be hidden with status flags), and the compensation logic is well-defined and testable.

**Q10. What are the two execution styles for Sagas, and when do you use each?**
A: Sagas can be orchestrated or choreographed:

**Orchestration:**
A central coordinator (the "orchestrator") explicitly tells each participant what to do and in what order. It knows the full saga definition, tracks the current step, calls each service in sequence, and invokes compensation if a step fails. The orchestrator is stateful — it persists the saga's current state to a durable store so it survives crashes and can resume mid-saga.

When to use: complex multi-step workflows with many conditional branches (approve loan → if approved, disburse → notify); workflows where visibility into the current step matters (operations teams can see where a saga is stuck); workflows where the sequence may vary based on outcomes (the order of steps depends on data from prior steps).

**Choreography:**
No central coordinator. Each participant publishes an event when it completes its step. Other participants subscribe to events and react by performing their step and publishing their own event. The saga progresses via event propagation. No single node knows the full saga state.

When to use: simple linear workflows with few steps; systems already built on event-driven architecture; scenarios where decoupling services is more important than visibility; cases where adding an orchestrator service adds disproportionate overhead.

The trade-off: orchestration makes the saga's state explicit and inspectable but introduces the orchestrator as a potential bottleneck and SPOF (mitigated by making it stateless with durable state storage). Choreography is decentralized and scales naturally but is harder to debug (the saga's state is distributed across event logs) and harder to handle complex failure scenarios (detecting that a saga is stuck requires reading the event log, not querying a coordinator).

**Q11. How do you design compensation transactions, and what makes them hard?**
A: A compensating transaction is the semantic inverse of a forward transaction — it undoes the business effect of the forward step, not necessarily the technical operation. The distinction matters:

- **Forward**: debit $100 from Account A. Compensating: credit $100 back to Account A. This is a true reversal — the technical and business effect are both undone.
- **Forward**: send a confirmation email to the customer. Compensating: you can't un-send an email. The compensation must be a new action: send a cancellation email. This is a semantic compensation — a new forward action that creates the intended business outcome.

What makes compensation design hard:

- **Externalized side effects** — once a step has called an external API, charged a card, or sent a notification, it cannot be atomically undone. The compensation must create a new "undo" action in the external system (a refund, a cancellation) which itself may fail or be delayed.
- **State has moved on** — by the time compensation runs, the data that was modified by the forward step may have been further modified by other transactions. Crediting Account A with $100 is safe if the balance is still coherent. But if Account A was closed between the forward step and the compensation, the credit operation may fail — and you now need a compensation for the failed compensation.
- **Compensation is a write** — compensating transactions themselves can fail. If step 3 of a 5-step saga fails and compensation starts at step 2, the compensation for step 2 may also fail. You need a compensation-for-compensation strategy, or at minimum, a dead-letter queue for stuck compensations that require manual resolution.
- **Idempotency is mandatory** — the saga orchestrator may retry a compensation after a failure. The compensation must be idempotent — crediting $100 twice is a bug as much as not crediting at all.

**Q12. What is the "lost update" problem in sagas, and how do you mitigate it?**
A: Because sagas release locks after each local step, other transactions can read and modify the same data between saga steps. This creates the lost update problem: Saga S reads Account A's balance (step 1), another transaction T withdraws from Account A (between S's steps 1 and 2), and then S debits Account A (step 2) based on the balance it read in step 1 — without seeing T's withdrawal. The result: an incorrect debit that doesn't account for T's prior withdrawal.

Mitigations:

- **Semantic locks (status flags)** — a saga sets a flag on the affected entity at the start (e.g., `order.status = PROCESSING`) and clears it at the end. Other transactions that see the flag either block or abort. This re-introduces some lock-like behavior without the cross-partition coordination cost of 2PC.
- **Countermeasures for anomalies** — design the saga steps to be order-independent where possible. Rather than reading-then-writing a value, use delta operations (`balance -= $100` rather than `balance = current_balance - $100`) — deltas are commutative and survive interleaving without lost updates.
- **Idempotent re-reads** — in the compensation step, re-read the current state before applying the compensation rather than assuming the state is what it was when the forward step ran. If the state has changed, the compensation logic must account for the current state.
- **Version numbers (optimistic concurrency)** — each saga step reads the entity's version number and writes back with a conditional `WHERE version = N`. If another transaction has modified the entity (version is now N+1), the write fails and the saga retries or compensates. No locks held between steps.

## Section 4: Distributed Transaction Protocols in Real Systems

**Q13. How does Google Spanner implement cross-partition transactions?**
A: Spanner implements cross-partition transactions using a combination of Paxos-based replication per shard, a two-phase commit protocol, and TrueTime for external consistency.

The execution path for a read-write transaction spanning shards A and B:

1. **Begin transaction** — the client is assigned a transaction coordinator (typically the leader of one involved Paxos group).
2. **Buffered reads** — reads are executed at a specific timestamp (determined by TrueTime), reading from the latest committed state visible at that timestamp. Reads don't acquire locks — Spanner uses MVCC (multi-version concurrency control) for reads.
3. **Buffered writes** — writes are buffered client-side and not sent until commit time. This avoids holding locks during the read phase.
4. **Commit — 2PC with Paxos** — at commit, the client sends all buffered writes to the coordinator. The coordinator runs 2PC: sends PREPARE to all involved shard leaders (Paxos leaders for each shard). Each shard leader runs a Paxos consensus round to durably log the prepared state across its replicas. The coordinator collects votes; if all say COMMIT, it runs a Paxos consensus round to log the commit decision, then sends COMMIT to all participants.
5. **TrueTime commit timestamp** — the coordinator assigns a commit timestamp using TrueTime's `TT.now()` interval. It waits until `TT.after(commit_ts)` is true (the commit timestamp is guaranteed to be in the past from TrueTime's perspective) before releasing the commit to clients. This commit-wait ensures external consistency: any transaction that starts after this commit will have a start timestamp ≥ commit_ts and will see this commit.

The key insight: Spanner's 2PC doesn't have the classical blocking problem because each participant is a Paxos group, not a single machine. If the coordinator crashes, its Paxos group elects a new leader that has the coordinator's committed state (including the transaction outcome) in its replicated log. The new leader can answer "what was the outcome of transaction T?" without indefinite blocking.

**Q14. How does CockroachDB implement cross-range transactions?**
A: CockroachDB uses a variant of optimistic concurrency control (OCC) with a protocol it calls "parallel commits." Each range (shard) is managed by a Raft group. A cross-range transaction:

1. **Read phase** — reads are executed at a consistent timestamp (a hybrid logical clock timestamp chosen at transaction start). Reads use MVCC — they don't block writes; they read the latest committed version at the chosen timestamp. Read timestamps are tracked for conflict detection.
2. **Write phase** — writes are executed speculatively: each write is written to the relevant range as a "write intent" — a provisional record that marks the key as being modified by transaction T with a specific timestamp. Write intents are visible to other transactions (which can then check whether T has committed or aborted).
3. **Parallel commits** — at commit time, CockroachDB's optimization: the transaction coordinator atomically writes its commit record to its own range AND tells all participants to finalize their write intents — all in parallel, rather than the sequential prepare-then-commit of 2PC. The transaction is considered committed the moment the coordinator's commit record is durably written (via Raft), even before all participants have finalized. Other transactions that see write intents from T can discover T's commit by reading T's transaction record and finalizing the intents themselves ("intent resolution" — cooperatively completing the commit).
4. **Conflict resolution** — if two transactions write to the same key, one must wait or retry. CockroachDB uses a "transaction record" per transaction and a "push" mechanism: a waiting transaction can push a blocking transaction's timestamp forward (forcing it to restart at a later timestamp) if the blocker is old enough.

The innovation in parallel commits: traditional 2PC requires the coordinator to hear back from all participants before the transaction is "committed" from the client's perspective. CockroachDB's parallel commits make the transaction committed the moment the coordinator's record is durable — participants finalize asynchronously. This cuts the commit latency roughly in half for cross-range transactions.

**Q15. How does Amazon DynamoDB handle cross-partition transactions?**
A: DynamoDB Transactions (introduced 2018) use a coordinator-based 2PC protocol managed by DynamoDB's own transaction library, running on top of the eventually consistent DynamoDB storage layer:

**TransactWriteItems / TransactGetItems flow:**

1. A transaction token (transaction ID) is created for the operation.
2. For reads (`TransactGetItems`): DynamoDB performs a read phase, verifies that all items have consistent versions (using internal version tokens), and returns results. If any item changed between the read and the verification check, the read transaction fails and the client retries.
3. For writes (`TransactWriteItems`): DynamoDB runs a 2PC variant:
   - Phase 1: for each item, conditionally write a "transaction pending" marker alongside the item (using a conditional write — only succeeds if no other transaction has claimed this item). If any conditional write fails (item already claimed by another transaction), the whole transaction aborts.
   - Phase 2: if all phase 1 writes succeeded, commit all items by applying the intended values and removing the transaction markers. If phase 1 fails for any item, abort by removing all transaction markers.

The conditional write in phase 1 is the lock acquisition — it's non-blocking (fails immediately if the item is already locked) rather than a traditional wait-based lock. This makes DynamoDB transactions higher-throughput but also means transactions fail under contention rather than queue — the application must retry.

Cost: DynamoDB transactions consume 2× the read and write capacity units of a non-transactional operation — the extra cost reflects the two-phase protocol.

**Q16. What is the "transaction record" pattern used by CockroachDB and Spanner, and why is it important for recovery?**
A: The transaction record (or transaction table entry) is a single, durable record that represents the authoritative outcome of a distributed transaction. It is written once (by the coordinator) to a known, well-defined location (often determined by the transaction ID) and is the single source of truth for whether the transaction committed or aborted.

Why it's important for recovery: in a classical 2PC, the coordinator's log is the source of truth. If the coordinator crashes and its log is ambiguous, there's no recovery path. The transaction record pattern makes the outcome explicit and readable by any node:

- **Any participant that is uncertain** (it prepared but hasn't received a commit/abort from the coordinator) can look up the transaction record. If it says COMMITTED, the participant commits. If it says ABORTED, the participant aborts. If it doesn't exist yet, the participant waits (and can eventually force an abort if the transaction is too old).
- **Cooperative intent resolution** — in CockroachDB, when a reader encounters a write intent from transaction T, it reads T's transaction record. If committed, the reader resolves the intent (cleans it up by writing the committed value) and proceeds. If aborted, the reader resolves the intent by deleting it. If indeterminate (no record yet), the reader can push the transaction's timestamp or wait.

This pattern turns the "coordinator is a SPOF" problem of 2PC into "the coordinator's transaction record is the SPOF" — but the transaction record is replicated (via Raft or Paxos), so it's highly available. Any participant or any reader can determine the transaction's outcome by reading the record, eliminating indefinite blocking.

## Section 5: Optimistic vs Pessimistic Concurrency Control

**Q17. What is the difference between optimistic and pessimistic concurrency control in the context of cross-partition transactions?**
A: The distinction is about when conflicts are detected and how they are handled:

**Pessimistic concurrency control (PCC):**
Assumes conflicts are common. Acquires locks before reading or writing data and holds them for the transaction's duration. Conflicts are prevented by blocking: if transaction T1 holds a lock on key K, transaction T2 blocks until T1 releases the lock. Used in: traditional RDBMS (Postgres's `SELECT FOR UPDATE`), Spanner's read-write transactions (write locks), 2PC implementations that use locking in the prepare phase.

Trade-offs: safe and correct under high contention; expensive under low contention (lock acquisition and release overhead even when no conflict exists); cross-partition lock holding multiplies lock duration by network RTT, increasing the contention window.

**Optimistic concurrency control (OCC):**
Assumes conflicts are rare. Reads and writes proceed without acquiring locks. At commit time, a "validation phase" checks whether any data read or written during the transaction was modified by another concurrent transaction. If a conflict is detected, the transaction aborts and retries; if no conflict, it commits. Used in: CockroachDB (timestamp-based OCC), DynamoDB transactions (conditional writes), many MVCC systems.

Trade-offs: low overhead when conflicts are rare (no lock acquisition); high overhead under high contention (many aborts and retries, which waste work); retry storms can occur when many transactions contend on the same keys.

The rule of thumb: use pessimistic when contention is high and retries are expensive (financial transactions with small retry windows); use optimistic when contention is low and reads far outnumber writes (catalog updates, infrequent configuration changes).

**Q18. What is MVCC (Multi-Version Concurrency Control), and how does it enable cross-partition reads without locks?**
A: MVCC maintains multiple versions of each data item, each tagged with the timestamp (or transaction ID) of the write that created it. Instead of locking a row for reading, a transaction reads the version of the row that was current at its start timestamp — it never blocks a concurrent write and a concurrent write never blocks it.

In a cross-partition read transaction:
1. The transaction is assigned a read timestamp T_read (a consistent timestamp, e.g., from a HLC or from TrueTime).
2. Each shard is queried: "give me the latest version of key K with timestamp ≤ T_read."
3. Since each shard independently looks up the right version, no cross-shard locking is required. All shards can be queried in parallel.
4. The results represent a consistent snapshot of the database as of T_read — all reads see the same logical moment.

For cross-partition read-write transactions, MVCC handles the read phase but writes still require a conflict-detection mechanism (OCC validation or pessimistic locking) at commit time. Spanner uses MVCC for reads and 2PC for writes. CockroachDB uses MVCC for reads and OCC with write intents for commit-time conflict detection.

The key property MVCC provides for cross-partition transactions: reads don't block writes, and writes don't block reads. This dramatically increases concurrency compared to lock-based approaches, at the cost of storage overhead (maintaining multiple versions) and garbage collection complexity (old versions must be cleaned up).

## Section 6: Avoiding Cross-Partition Transactions

**Q19. What is the most effective strategy for handling cross-partition transactions?**
A: The most effective strategy is not to have them — design the data model so that transactions that must be atomic live on the same partition. This is not always possible, but it is underused because teams often partition first and then discover cross-partition atomicity requirements later.

Data co-location strategies:

- **Shard by transaction unit, not by entity** — if transfers between accounts must be atomic, shard by a key that keeps related accounts together. A family account, a business's accounts, or accounts within the same financial institution might all live on the same shard. Transfers within the shard are local; transfers between shards (cross-institution) can use a looser model (sagas with compensation).
- **Entity grouping (parent-child sharding)** — shard all child entities together with their parent. An order and its line items live on the same shard as the customer. Operations that touch a customer and their orders are always local. Used in Google Spanner's interleaved tables and in many NoSQL data models (DynamoDB's single-table design with partition key = customer_id).
- **Denormalization** — store the data that would span partitions on both partitions redundantly. An order record can store the customer's shipping address rather than joining to the customer table. The order is self-contained; no cross-shard read needed at serving time. Updates to the customer's address are propagated asynchronously.
- **Event sourcing with eventual consistency** — accept that the two affected entities will converge to the correct state eventually rather than atomically. Write the event ("TransferInitiated") and let each entity's event handler update local state. Appropriate when the business can tolerate a brief inconsistency window (a millisecond to a second) without user-visible harm.

**Q20. What is the "single-partition trick" using a surrogate key, and when is it applicable?**
A: The single-partition trick: design a transaction that appears to span multiple entities to only touch a single partition by creating a surrogate entity that represents the transaction itself.

Example — transferring funds between Account A (shard 1) and Account B (shard 2):

Instead of updating both accounts atomically (cross-partition), create a "Transfer" record:
1. Insert a Transfer record: `{transfer_id, from_account, to_account, amount, status: PENDING}`. This single-row insert is atomic and local to the Transfer record's shard.
2. A background worker reads PENDING transfers, applies the debit to Account A, applies the credit to Account B (each local operation), and marks the Transfer as COMPLETED.

The atomicity of the business operation is shifted: the Transfer record's existence and its final COMPLETED status are the source of truth. Individual account updates are idempotent and eventually consistent with the Transfer record. The "transaction" is defined by the Transfer record, not by a distributed atomic commit.

Applicable when: there is a natural transaction entity in the domain (Transfer, Order, Payment), the two parties can tolerate an eventually consistent update (the transfer will complete in milliseconds to seconds), and the transaction entity can be queried to resolve disputes ("your funds are in-flight, here is the transfer ID").

## Section 7: Failure Handling and Recovery

**Q21. What happens to in-flight cross-partition transactions during a node failure, and how should systems recover?**
A: Recovery behavior depends on which node failed and at what point in the protocol:

**Participant failure before PREPARE response:**
The coordinator receives no response (timeout). It aborts the transaction and sends ABORT to all participants that did respond. The failed participant recovers, finds no prepared state in its WAL for this transaction (it crashed before preparing), and discards any in-memory state. Clean recovery.

**Participant failure after PREPARE, before COMMIT:**
The participant recovers, finds a prepared state in its WAL. It contacts the coordinator: "What happened to transaction T?" The coordinator's answer drives recovery. This requires the coordinator to be available — the blocking problem. If the coordinator is also down, the participant waits (or the system has a recovery protocol using the transaction record approach described in Q16).

**Coordinator failure before sending COMMIT:**
All participants are stuck in prepared state, holding locks. On coordinator recovery, it reads its WAL: if it has a COMMIT decision logged, it re-sends COMMIT to all participants. If it has no decision logged, it aborts (using the presumed abort optimization). Recovery time = coordinator restart time + participant re-notification.

**Coordinator failure after sending COMMIT to some participants:**
Some participants committed; others haven't received COMMIT yet. On recovery, the coordinator re-sends COMMIT to non-acknowledging participants. Participants that already committed receive a duplicate COMMIT — their response should be idempotent (acknowledge without re-applying). The COMMIT must be logged before sending it (so it survives coordinator restart).

**Both coordinator and participant fail simultaneously:**
The most dangerous scenario. A human operator may need to manually inspect the WALs of both machines to determine the intended outcome. This is why 2PC implementations retain WAL entries for in-doubt transactions indefinitely — they may be needed for manual recovery.

**Q22. What is a "heuristic decision" in 2PC, and when should it be used?**
A: A heuristic decision is when a participant in the uncertain state (it has prepared but hasn't received a commit/abort from the coordinator) unilaterally decides to commit or abort after a timeout — without confirmation from the coordinator. It is called "heuristic" because it is a guess: the participant decides based on business logic or policy rather than protocol-guaranteed knowledge.

Heuristic decisions are explicitly a last resort for situations where the coordinator is unreachable for a prolonged period (hours to days) and the locked resources are causing serious operational impact — other transactions are blocked, users are waiting, and the business cannot wait for the coordinator to recover.

The risk: a heuristic commit may be wrong. If the coordinator had decided to abort, and the participant heuristically commits, the transaction is partially committed — a state that violates atomicity and requires manual reconciliation to repair. This is called a "heuristic damage" and is logged to a durable heuristic damage log that the operations team must manually inspect and resolve.

Heuristic decisions are supported by XA (the distributed transaction standard used in Java EE / Jakarta EE systems): `xa_commit(heuristic)` and `xa_rollback(heuristic)` allow a recovery manager to make heuristic decisions on stuck transactions. The standard requires that heuristic decisions be logged and reported to administrators. The guideline: never use heuristic decisions as a normal operational practice — only as a break-glass procedure for coordinator failures that cannot be resolved by normal recovery.

## Section 8: Scenario / System Design Questions

**Q23. "Design the transaction flow for a bank transfer where Account A is on shard 1 and Account B is on shard 2. What protocol do you use?"**
A: A bank transfer requires atomicity — the debit and credit must both happen or neither happens. I'd approach this in layers:

**Option 1: 2PC (if the database supports it)**
Use the database's native distributed transaction support (CockroachDB, Spanner, or a 2PC-capable sharded MySQL/Postgres setup). The application issues a single SQL transaction:
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';  -- on shard 1
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';  -- on shard 2
COMMIT;
```
The database handles the 2PC internally. The application sees a single atomic transaction. Appropriate when the database natively supports cross-shard transactions, the volume is moderate (2PC has latency overhead), and the transfer is time-sensitive (cannot tolerate eventual consistency).

**Option 2: Saga with choreography (if avoiding 2PC overhead)**
Define a Transfer entity (on its own shard, sharded by transfer_id):
1. `INSERT Transfer {id, from_A, to_B, amount, status: INITIATED}` — local atomic write.
2. Publish `TransferInitiated` event to Kafka.
3. Account A's service consumes event, atomically debits A and publishes `DebitCompleted` or `DebitFailed`.
4. Account B's service consumes `DebitCompleted`, credits B, publishes `CreditCompleted`.
5. Transfer service marks Transfer as `COMPLETED`.

Compensation path if credit fails:
- Account B's service publishes `CreditFailed`.
- Account A's service consumes `CreditFailed`, credits A back (compensation).
- Transfer is marked `FAILED`.

Each step is idempotent (protected by `transfer_id`). Intermediate states (`INITIATED`, `DEBIT_COMPLETED`, `CREDIT_PENDING`) are visible to the operations team. The transfer is eventually consistent — there is a window (milliseconds to seconds) where A is debited but B is not yet credited. For a bank transfer, this window may be acceptable (it is how ACH transfers work — the debit happens immediately, the credit follows within hours).

I'd use 2PC if the database supports it and the business requires strict atomicity with no visible intermediate states. I'd use a Saga if 2PC latency is unacceptable, the workflow is long-running, or the database doesn't natively support cross-shard transactions.

**Q24. "A saga's compensation step fails. How do you handle a failed compensation?"**
A: A failed compensation is the most operationally complex scenario in saga design — you now have a partially executed saga where a step has been applied but its compensation could not be applied. Options in order of preference:

**1. Retry the compensation (idempotent compensation is mandatory):**
The first response to a failed compensation should always be retry. If the compensation is idempotent (crediting Account A twice returns the same result as crediting once), retries are safe. Use exponential backoff with a maximum retry count. Most transient failures (network timeouts, temporary service unavailability) are resolved by retries.

**2. Dead-letter queue (DLQ) for stuck compensations:**
If retries are exhausted, push the failed compensation onto a dead-letter queue. A background process periodically retries DLQ items. This decouples the stuck compensation from the live transaction flow — other sagas proceed normally while the stuck compensation is handled asynchronously.

**3. Human-in-the-loop escalation:**
If the DLQ retry also fails repeatedly (the target service is permanently down, the account is closed, the entity no longer exists), escalate to an operations team. The saga's state is queryable — the operations team can see exactly which steps completed, which failed, and what compensation was attempted. They manually apply the compensation or make a business decision (write off the debt, issue a different form of restitution).

**4. Pivot transaction:**
A "pivot transaction" is a checkpoint in the saga where, if reached, the saga is considered committed and compensations beyond that point are not allowed. The pivot must be chosen carefully — it's the point of no return. For a funds transfer, the pivot is typically the credit to Account B — once B has been credited, you cannot unilaterally debit B back without B's consent (a separate refund flow is needed). The pivot transaction design avoids compensation for the most consequential steps by ensuring earlier steps are compensatable and later steps are final.

**Q25. "Your cross-partition transaction system is experiencing high latency. Where are the bottlenecks, and how do you address them?"**
A: Cross-partition transaction latency has several distinct components, each with different causes and mitigations:

**Network RTT amplification:**
Each phase of 2PC requires a round-trip: coordinator → participants (prepare), participants → coordinator (vote), coordinator → participants (commit), participants → coordinator (ack). In a 3-replica Raft-based system with 2 shards, the critical path is: 2 RTTs for 2PC × 1 Raft round per shard = significant latency stacking. Mitigations: co-locate coordinator and participants in the same AZ to minimize RTT; use parallel commits (CockroachDB's optimization) to reduce 2 RTT round trips to ~1.5; use batching (group multiple single-key writes into one cross-partition transaction where possible).

**Lock contention:**
If transactions contend on the same keys, pessimistic locks cause queuing. The bottleneck appears as high average transaction latency but low throughput — transactions are waiting, not working. Mitigations: reduce transaction scope (don't include reads that don't need locking in the locked section); use OCC instead of pessimistic locking if contention is actually rare; shard more finely to distribute the hot keys.

**Coordinator bottleneck:**
In a 2PC system where the same node is always the coordinator, it becomes a throughput ceiling. Mitigations: distribute coordination across all nodes (each transaction picks its coordinator randomly); use a stateless coordinator pattern where the coordinator is a routing layer, not a fixed node.

**fsync latency:**
Each phase requires a durable write (fsync) on the participant. On spinning disk, fsync is 5–10ms per operation. Two phases × 2 participants = up to 40ms of fsync overhead alone. Mitigations: NVMe SSDs (100–500µs fsync); group commit (batch multiple transactions' WAL entries into one fsync); write-coalescing.

**Replication lag for Raft-based participants:**
Each participant must replicate its prepared/committed state via Raft before acknowledging. Raft replication requires a quorum round-trip. Mitigations: pipeline Raft log entries; use leader-local commits with async replication where safety allows; keep participants in the same AZ as the coordinator.

**Q26. "You're designing a distributed e-commerce system. When do you use 2PC vs Saga for various transaction types?"**
A: The decision per transaction type:

**Order placement (reserve inventory + create order + charge payment):**
Use a **Saga**. This is a long-running operation (payment processing can take 2–5 seconds), involves an external system (payment gateway — cannot be part of a 2PC), and the intermediate state (inventory reserved, order pending) is acceptable with appropriate UI feedback ("your order is being processed"). Compensation: release inventory if payment fails.

**Inventory decrement during flash sale (atomic count across shards):**
Use **Redis atomic operations** (`DECR`) on a single counter, not a cross-partition transaction at all. If the inventory is sharded for throughput, use a Saga with a Redis reservation step first (atomic decrement via Redis) and database write second. The Redis decrement is the atomic coordination point; the database write is eventually consistent.

**Financial ledger entry (debit + credit across account shards):**
Use **2PC** if the database supports it natively (CockroachDB, Spanner) — the strict atomicity requirement and short duration make 2PC appropriate. Use a **Saga with a pivot transaction** if 2PC is not available — the credit to the recipient's account is the pivot (once complete, it's final). Ensure full idempotency on all steps and compensations.

**Refund (reverse charge, restore inventory, cancel order):**
Use a **Saga**. Refunds are inherently multi-step and long-running (payment reversal takes time). Each step has a well-defined compensation (re-charge if reversal fails midway). The customer-visible state ("Refund processing") is acceptable as an intermediate state.

**Reporting aggregate update (update sales totals across regions):**
Use **eventual consistency with no transaction at all**. Sales totals are derived data — they can be recomputed from the event log. Approximate totals are acceptable (a $1,000 rounding difference in a $10M daily sales report is not a critical correctness issue). Use CRDT-style increments that commute and converge without coordination.

## Quick Reference: Cross-Partition Transaction Protocols

| Protocol | Atomicity | Availability During Failure | Latency | Use When |
|--- |--- |--- |--- |--- |
| 2PC | Strong (simultaneous) | Blocks on coordinator failure | High (2 RTTs + 2 fsyncs per participant) | Short transactions, native DB support, strict atomicity |
| 3PC | Strong (non-blocking*) | Better than 2PC but still blocks in async networks | Higher than 2PC | Theoretical; rarely production-used |
| Saga (orchestrated) | Eventual (via compensation) | High (each step independent) | Low per step | Long workflows, external systems, high contention |
| Saga (choreographed) | Eventual (via events) | High | Low | Event-driven architectures, decoupled services |
| Parallel commits (CockroachDB) | Strong | High (Raft-backed coordinator) | ~1.5 RTTs | CockroachDB-native; balances 2PC correctness with lower latency |
| Transaction record (Spanner) | Strong | High (Paxos-backed) | ~2 RTTs + TrueTime wait | Spanner-native; external consistency |
| Single-partition redesign | Strong (local) | Highest (no cross-partition) | Lowest (local ACID) | Always preferred if data model allows it |

## Key Invariants to Enforce

| Invariant | Mechanism |
|--- |--- |
| All-or-nothing atomicity | 2PC with durable PREPARE before VOTE-COMMIT |
| No double-commit on retry | Idempotency key per transaction; transaction record checked before re-applying |
| Compensation is idempotent | Each compensating transaction is guarded by `IF NOT compensated` check |
| No lost compensation | Dead-letter queue for failed compensations; never silently discard |
| Pivot transaction is irreversible | No compensation defined after pivot; later steps use forward actions (refund flow, not reversal) |
| Coordinator is not a SPOF | Coordinator state stored in Raft/Paxos group; any survivor can answer "what was the outcome?" |
| Locks not held across user interactions | Sagas for workflows spanning user think time; 2PC only for sub-second automated flows |

The strongest answers connect the protocol choice to the failure mode it prevents and the failure mode it introduces: "2PC gives you atomicity but introduces blocking on coordinator failure — which is why systems like CockroachDB replace the single coordinator with a Raft group so the 'coordinator' is highly available and the blocking window is bounded by Raft election time, not crash recovery time." Have an opinion on when you'd use a Saga over 2PC and why — interviewers specifically probe this boundary, because it's where engineering judgment separates from textbook knowledge.
