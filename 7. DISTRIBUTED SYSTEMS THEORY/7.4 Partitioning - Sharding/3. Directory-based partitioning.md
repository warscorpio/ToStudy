# Directory-Based Partitioning — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is directory-based partitioning?**
A: Directory-based partitioning is a data distribution strategy where a central lookup service — the directory — maintains an explicit mapping from each data item (or range of items) to the node responsible for storing it. When a client wants to read or write a record, it first consults the directory to find out which node owns that record, then contacts that node directly.

```
Client
  │
  │  1. "Which node owns key='user:42'?"
  ▼
┌────────────────┐
│   Directory    │  {user:42 → Node 3, user:43 → Node 1, ...}
│   Service      │
└────────────────┘
  │
  │  2. "Node 3"
  ▼
Client contacts Node 3 directly
  │
  │  3. read/write user:42
  ▼
Node 3
```

The directory is the source of truth for partition ownership. It can store mappings at any granularity — per key, per key range, per shard ID, or per tenant — and can be updated independently of the data nodes themselves. This makes directory-based partitioning the most flexible of the three main partitioning strategies (range, hash, directory).

**Q2. How does directory-based partitioning differ from range and hash partitioning?**
A: The three strategies differ in how the partition-to-node mapping is determined:

**Range partitioning** — data is sorted by key; each node owns a contiguous key range (`A–M` on Node 1, `N–Z` on Node 2). The mapping is implicit in the range boundaries, which must be redistributed when nodes are added. Supports efficient range scans; vulnerable to hot spots on popular key ranges.

**Hash partitioning** (consistent hashing included) — a hash function maps each key to a node: `node = hash(key) % N`. The mapping is computed on the fly; no directory needed. Distributes load evenly; range scans are impossible; rebalancing still requires migrating data.

**Directory-based partitioning** — an explicit lookup table maps each key or key range to a node. The mapping is arbitrary and stored externally. No algorithmic constraint on which key goes where — the directory can assign any key to any node for any reason. Most flexible; introduces the directory as a component that must be kept consistent and available.

| Aspect | Range | Hash | Directory |
|--- |--- |--- |--- |
| Mapping mechanism | Implicit (range boundaries) | Computed (hash function) | Explicit (lookup table) |
| Range scan support | Yes | No | Depends on granularity |
| Load balance | Manual (range splits) | Automatic (hash) | Manual or automatic (directory update) |
| Rebalancing | Move ranges | Move hash-ring segments | Update directory entry |
| Flexibility | Low | Low | High |
| Extra component | No | No | Yes (directory service) |
| Hot spot control | Difficult | Good | Precise (arbitrary reassignment) |

**Q3. At what granularity can directory entries be defined?**
A: The granularity is a design choice that trades directory size against routing flexibility:

**Per-key mapping** — every individual key has its own directory entry (`user:42 → Node 3`). Maximum flexibility (any key can be on any node); directory can be enormous for large datasets. Practical only for small datasets or when keys cluster into a manageable number.

**Per-shard mapping** — data is pre-partitioned into a fixed number of logical shards (e.g., 1,024 shards), and the directory maps shard ID to node (`shard:0–63 → Node 1`, `shard:64–127 → Node 2`). The key-to-shard mapping uses a hash or range rule; only shard-to-node is in the directory. Directory is small (1,024 entries); rebalancing moves whole shards by updating a directory entry. This is the most common production pattern — used by MongoDB, Vitess, and Citus.

**Per-tenant mapping** — in multi-tenant SaaS systems, each tenant is a directory entry mapping to a shard or cluster (`tenant:acme → cluster-A`, `tenant:globex → cluster-B`). Natural isolation boundary; hot tenants can be moved individually.

**Per-range mapping** — key ranges are directory entries with explicit boundaries (`[0, 1000) → Node 1`, `[1000, 5000) → Node 2`). Supports range scans through the directory; boundaries can be adjusted without rehashing.

## Section 2: The Directory Service

**Q4. What does the directory service need to do, and what are its consistency requirements?**
A: The directory service has three core responsibilities:

**Reads (routing lookups):** Given a key or shard ID, return the responsible node. This is the hot path — called on every client request. Must be low-latency (< 1ms if cached, < 5ms if not); must never return a stale mapping that routes to a node that no longer owns the data (this would cause incorrect reads or writes that silently go to the wrong node).

**Writes (mapping updates):** Update the directory when a shard migrates from one node to another, when a node is added or removed, or when a new key range is assigned. Must be strongly consistent — a partial update (directory says shard X is on Node 2 but the data hasn't fully migrated yet) requires careful coordination to avoid serving stale or split data.

**Fault tolerance:** The directory is the single component that every client depends on for every operation. It must be highly available — a directory outage means clients cannot route any requests. Typically implemented as a replicated state machine (Raft or Paxos): reads from the leader or a quorum; writes go through the leader and are replicated before committing.

The directory's consistency requirement is **linearizable for writes** (all nodes must agree on the new mapping before it takes effect) and **at least read-your-own-writes for reads** (a client that updated the directory must see the update on its next read).

**Q5. How is the directory typically implemented in production systems?**
A: The directory is almost never a custom-built component — systems reuse existing strongly-consistent distributed key-value stores:

**etcd** — the most common choice in Kubernetes-native systems. Raft-based; linearizable reads and writes; watch API for real-time change notification. Used by Vitess (MySQL sharding) for its topology server. Appropriate for directories with thousands to hundreds of thousands of entries.

**ZooKeeper** — older; uses Zab (similar to Paxos). Watches are per-node; widely used in Hadoop/HBase/Kafka ecosystems for shard assignment. Directory entries are ZooKeeper znodes.

**Consul** — Raft-based; integrates service discovery with KV store. Used when the directory also serves as a service registry (node addresses change frequently).

**A dedicated metadata database** (e.g., a PostgreSQL instance with synchronous replication) — simpler for smaller systems; familiar tooling; requires care around caching and cache invalidation.

**Embedded in the database itself** — MongoDB's config servers (also a replicated set) store chunk-to-shard mappings. Citus stores shard placements in a metadata table on the coordinator node. The directory is co-located with the query router rather than a separate service.

**Q6. What is the "directory on the critical path" problem and how do you mitigate it?**
A: If every client request requires a live directory lookup, the directory becomes a latency bottleneck and a single point of failure amplification — every service depends on it synchronously. At 100k RPS, the directory must handle 100k lookups per second in addition to its consistency-critical write workload.

Mitigation strategies:

**Client-side caching (primary mitigation):**
Each client caches the directory mappings it has fetched. Routing lookups are served from the local cache (< 1ms, zero network) on the overwhelming majority of requests. The cache is invalidated when the directory notifies clients of mapping changes (push) or when a request to a cached node returns a "not my shard" error (pull — stale cache detected and refreshed).

```
Client cache: {shard:5 → Node 2, shard:6 → Node 1}
                        │
Request for shard:5 → cache hit → route to Node 2 directly
                        (no directory call)

Node 2 responds: "shard:5 moved to Node 3"
                        │
Client: invalidate cache entry for shard:5
        fetch updated mapping from directory
        retry request against Node 3
```

**Read replicas for the directory:**
Serve read-heavy lookup traffic from directory replicas (slightly stale, but staleness is bounded and detected via "not my shard" responses). Writes still go to the leader.

**Lazy propagation with error correction:**
Don't push invalidations proactively; let clients use stale cached mappings. When a stale mapping causes a misdirected request, the receiving node returns a redirect or error indicating the new owner. The client updates its cache and retries. Eventual convergence without push infrastructure. Used by MongoDB's `mongos` router.

## Section 3: Rebalancing and Migrations

**Q7. How does a shard migration work in a directory-based system?**
A: A shard migration moves data from Node A to Node B and then updates the directory to reflect the new owner. The challenge is doing this without downtime — reads and writes must continue during the migration. The standard protocol:

```
Phase 1: Copy (background, no interruption to traffic)
  - Node B starts pulling data for the shard from Node A
  - Node A continues serving all reads and writes for the shard
  - New writes to the shard on Node A are also tracked in a change log

Phase 2: Catch up (delta sync)
  - Node B has a snapshot of the shard's data as of time T
  - Node B applies the change log from Node A for all changes since T
  - Repeat until the lag is small (e.g., < 1 second of changes)

Phase 3: Cutover (brief pause)
  - Pause writes to the shard on Node A (typically milliseconds)
  - Node B applies the final delta (changes since last sync)
  - Node B acknowledges it is ready

Phase 4: Directory update (atomic)
  - Update the directory: shard → Node B
  - Resume writes; they now go to Node B
  - Node A can delete its copy of the shard after a grace period

Phase 5: Cache invalidation
  - Directory notifies clients (watch events / push) or
  - Clients detect stale cache via "not my shard" responses from Node A
  - Clients update cache and retry against Node B
```

The write pause in Phase 3 is the only user-visible interruption — typically 10–500ms depending on the remaining delta size. The migration is atomic from the directory's perspective: the mapping switches from A to B in a single linearizable write; there is never a moment where the directory says "both A and B" own the shard.

**Q8. How do you handle in-flight requests during a shard migration cutover?**
A: In-flight requests during the cutover must not be lost or corrupted:

**Requests in-flight to Node A during Phase 4 (cutover):**
- If the request arrived before the write pause: Node A processes it and the change is included in the final delta; Node B receives it via the change log.
- If the request arrived after the directory update but before the client's cache invalidated: Node A receives a write for a shard it no longer owns. Node A must reject it with a "shard moved" error. The client refreshes its cache and retries against Node B. Node A must continue to serve this role (acknowledge but reject, not drop) for the duration of the client cache TTL.

**Requests that straddle the cutover (read-modify-write):**
- A transaction that reads from Node A, modifies, and writes back must be treated as a unit. If the read was on the old owner (Node A) and the write goes to the new owner (Node B), the transaction is inconsistent.
- Solution: the shard migration protocol must drain all in-flight transactions before updating the directory. Node A tracks in-flight operation counts; the write pause begins only when the in-flight count reaches zero.

**Q9. What triggers a rebalancing decision in a directory-based system?**
A: Rebalancing decisions are made by a separate coordinator or the directory service itself, based on observed metrics:

**Imbalanced storage:** one node's disk usage is significantly higher than others. The coordinator identifies the largest shards on the overloaded node and migrates them to underloaded nodes. The directory is updated atomically for each migrated shard.

**Imbalanced query load (hot shards):** one shard receives disproportionate read or write traffic (a "hot spot"). Options: migrate the shard to a less-loaded node; or split the shard into two smaller shards (each half goes to a different node) and add two directory entries replacing the original one.

**Node addition:** a new node joins the cluster. The coordinator selects shards from overloaded nodes and migrates them to the new node, updating the directory for each moved shard. In a 1,024-shard / 4-node system, adding a 5th node should move ~205 shards (1,024/5) to the new node.

**Node failure:** the coordinator detects the failed node (via health checks), identifies its shards in the directory, and reassigns them to surviving nodes using spare replicas or by triggering migration from a replica. The directory update makes surviving nodes the new primaries immediately.

**Q10. How does directory-based rebalancing compare to consistent hashing rebalancing?**
A: The key difference is control and precision:

**Consistent hashing rebalancing:**
- Adding a node moves only the keys adjacent to it on the hash ring — O(K/N) keys where K is total keys and N is node count. Movement is minimal but not controlled: which keys move is determined by hash function output, not by actual load or storage metrics.
- Cannot selectively move a hot key to a different node without rehashing (the hash function determines placement).
- Automatic and decentralized; no directory needed.

**Directory-based rebalancing:**
- The coordinator can move exactly the shards that are causing imbalance, leaving all others untouched. A hot shard (shard 42) can be moved to a specific underloaded node without disturbing shards 0–41 and 43–1023.
- Can optimize placement based on actual measured metrics (disk usage, QPS, latency) rather than blind algorithmic distribution.
- Can co-locate shards that are frequently accessed together (e.g., a user's orders and the user's profile) on the same node to enable local joins.
- Requires the directory infrastructure; rebalancing decisions require a coordinator with visibility into cluster metrics.

In practice: systems that need intelligent, load-aware placement (MongoDB's balancer, Vitess's resharding, Citus's rebalancer) use directory-based approaches. Systems that need simple automatic distribution without operational overhead use consistent hashing (Cassandra, Redis Cluster).

## Section 4: Failure Modes

**Q11. What happens when the directory service becomes unavailable?**
A: The impact depends on how aggressively clients cache directory mappings:

**With aggressive client-side caching (standard):**
- Clients continue routing requests using cached mappings for the duration of the cache TTL or until a "not my shard" error is received.
- No new shard migrations can be committed (require a directory write).
- New clients that haven't cached any mappings cannot route at all — they must wait for the directory to recover.
- The data nodes themselves are unaffected and continue serving requests routed from clients with valid cache entries.

**Operational response:**
- The directory service is replicated (Raft / Paxos); a single node failure triggers leader election (seconds). Normal operations resume after election.
- If a majority of directory nodes fail simultaneously (cluster is split), the directory becomes unavailable. Client caches keep existing traffic alive; new operations that require directory updates (migrations, node additions) are blocked.
- Design: the directory cluster must be deployed across availability zones; losing one AZ should not lose directory quorum.

**Q12. What is a "stale cache" routing error and how is it handled end-to-end?**
A: A stale cache routing error occurs when a client routes a request to a node based on a cached directory mapping that is no longer accurate — the shard has since migrated to a different node.

```
Client cache: {shard:7 → Node 2}   ← stale; shard migrated to Node 3

Client sends write to Node 2 for shard:7
        │
Node 2 recognizes it no longer owns shard:7 (post-migration)
Node 2 responds: HTTP 301 / custom error code:
  {"error": "SHARD_MOVED", "new_owner": "Node 3", "shard": 7}
        │
Client:
  1. Invalidates cache entry for shard:7
  2. Updates cache: {shard:7 → Node 3}
  3. Retries the request against Node 3
  4. Node 3 serves the request successfully
```

This pattern — "try cached node, redirect if wrong, update cache, retry" — is how MongoDB's `mongos` router handles stale chunk mappings. It means the directory does not need to push invalidations to every client for every migration — the detection is lazy (on the next request to the stale node) and self-healing.

Node 2 must maintain its "shard moved" response capability for a grace period after migration (until all client caches are likely to have refreshed). During this window, Node 2 keeps a forwarding table: `{shard:7 → Node 3}`. After the grace period, Node 2 deletes the forwarding entry; a request to Node 2 for shard:7 after this point returns a hard error, forcing a full directory refresh.

**Q13. What is a split-brain scenario in a directory-based system and how do you prevent it?**
A: Split-brain occurs when two nodes both believe they are the owner of the same shard simultaneously, causing them to independently accept conflicting writes. This leads to data divergence that is difficult to reconcile.

Root causes:
- A directory update is partially applied (network partition during the cutover).
- Client caches are stale on different clients with long TTLs.
- Node A's "shard moved" notification is delayed; it continues accepting writes it shouldn't.

Prevention:

**Linearizable directory updates:** the directory write `shard:7 → Node 3` is atomic and linearizable — it commits on all directory replicas before either node is notified. There is no intermediate state where the directory is inconsistent.

**Lease-based ownership:** Node A holds a time-limited lease for each shard it owns. The lease must be renewed periodically (every 10 seconds) via the directory. When the lease expires, Node A stops serving the shard. The migration protocol: the coordinator waits for Node A's lease to expire (or explicitly revokes it) before granting a lease to Node B. Since leases are exclusive, only one node holds a valid lease at any time — split-brain is physically prevented.

```
Node A lease for shard:7 expires at T+10
At T+8: coordinator starts migration; Node B begins copying data
At T+10: Node A's lease expires; it stops accepting writes for shard:7
At T+10: Node B is granted a new lease for shard:7 (after confirming data sync)
Directory updated: shard:7 → Node B
```

**Fencing tokens:** each lease carries a monotonically increasing token. When Node B takes over with token=42, any write from Node A (with token=41) to the storage layer is rejected by a fencing check: "token 41 < current token 42 → reject." Protects against a "zombie" Node A that lost its lease but is still processing in-flight requests.

## Section 5: Real-World Systems

**Q14. How does MongoDB implement directory-based partitioning?**
A: MongoDB's sharding is a textbook directory-based system:

**Components:**
- **Config servers** — a 3-node replica set storing the cluster metadata (the directory). Contains the `config.chunks` collection: each document maps a chunk (a key range within a collection) to a shard. `{ns: "db.orders", min: {_id: 0}, max: {_id: 1000}, shard: "shard1"}`.
- **`mongos` (query router)** — a stateless proxy that caches the chunk mapping from config servers and routes client queries to the correct shard. Multiple `mongos` instances run in parallel for horizontal scaling of routing. Each `mongos` maintains a local cache with a version number (chunk version); stale cache is detected via "StaleConfig" errors from shards.
- **Shards** — the data nodes. Each shard is itself a replica set (primary + secondaries) for high availability.

**Balancer:**
- The balancer runs on the primary config server and monitors chunk distribution across shards.
- If a shard has significantly more chunks than others (default threshold: 8 chunks difference), the balancer selects chunks to migrate and coordinates the migration protocol, updating `config.chunks` atomically at cutover.
- Chunk splits are triggered when a chunk exceeds the max chunk size (default 128MB) — the chunk is split at the median key value, creating two directory entries.

**Q15. How does Vitess implement directory-based partitioning for MySQL?**
A: Vitess shards MySQL across multiple instances using a directory-based topology:

**Topology server (directory):** etcd or ZooKeeper stores the keyspace-to-shard mapping and shard-to-tablet mapping. A keyspace (logical database) is divided into shards by key range; each shard maps to a primary tablet (MySQL instance) and zero or more replica tablets.

**VTGate (query router):** the stateless query router (analogous to MongoDB's `mongos`) reads the topology from etcd, caches it locally, and routes SQL queries to the correct shard based on a vindex (virtual index — a column used as the sharding key). VTGate rewrites queries to target the correct shard and handles scatter-gather for queries that span shards.

**Resharding:** Vitess supports online resharding — splitting a shard (e.g., `-80` into `-40` and `40-80`) with zero downtime. The directory (topology server) is updated atomically at cutover; VTGate's cached topology is refreshed via watch events from etcd.

**Q16. How does Citus (distributed PostgreSQL) use directory-based partitioning?**
A: Citus distributes PostgreSQL tables across worker nodes using a directory stored in the coordinator's system catalog:

**Metadata tables on coordinator:**
```sql
-- Shard placement directory
SELECT * FROM pg_dist_shard;
-- shardid | logicalrelid | shardstorage | shardminvalue | shardmaxvalue
--    1001 |    orders    |      't'     |             0 |       999999

SELECT * FROM pg_dist_shard_placement;
-- placementid | shardid | shardstate | shardlength | nodename | nodeport
--           1 |    1001 |          1 |           0 | worker-1 |     5432
```

The coordinator intercepts every SQL query, consults these metadata tables to determine which worker node holds the relevant shards, rewrites the query, and routes it to the correct worker(s). The coordinator itself is the directory service and the query router in one component.

**Reference tables** (small lookup tables needed by many queries) are replicated to all workers — they have a directory entry pointing to all nodes, so any worker can join against them locally without cross-node communication.

## Section 6: Scenario Questions

**Q17. "You're designing a multi-tenant SaaS database. Each tenant's data should be isolated and you may need to move a tenant to a different database server without downtime. Why is directory-based partitioning a good fit?"**
A: Tenants are a natural directory key — the mapping is `tenant_id → database_server`. Directory-based partitioning is the right choice because:

**Arbitrary placement:** a new enterprise tenant that requires dedicated resources can be placed on a dedicated server from day one, independent of any hash or range rule. A small tenant and a large tenant can coexist on the same server; a growing tenant can be migrated without affecting others.

**Zero-downtime migration:** when a tenant needs to be moved (their usage is creating a hot spot, or they've purchased a dedicated instance), the migration protocol copies data to the new server, runs delta sync, pauses writes for milliseconds, updates the directory (`tenant:acme → server-B`), and resumes. The tenant's users experience at most a brief pause, not a planned maintenance window.

**Isolation:** directory entries can store more than just node assignments — they can carry tenant-specific configuration (connection pool size, max QPS, feature flags). The directory becomes the control plane for per-tenant customization.

**Operational flexibility:** tenants can be grouped or split at will. A tenant acquired by a larger company can be merged onto the acquirer's shard; two tenants on the same shard can be split without any algorithmic constraint.

The alternative — consistent hashing — would assign each tenant to a server based on `hash(tenant_id)`. Moving a tenant requires a rehash or a separate override table, which is effectively reimplementing a directory. For multi-tenant systems, just use a directory directly.

**Q18. "Your directory service has 50 million shard-to-node entries. etcd is struggling under the read load from 500 routing nodes each polling for mapping updates. What do you do?"**
A: 50 million entries in etcd is already at the edge of etcd's practical capacity (etcd is designed for tens of thousands of entries, not tens of millions). This is an architectural problem, not a tuning problem:

**Reduce directory granularity:** move from per-key to per-shard mappings. If 50 million keys are grouped into 10,000 shards, the directory shrinks to 10,000 entries — well within etcd's range. Clients compute `shard_id = hash(key) % 10000` locally and look up `shard_id → node` in the directory. The per-key-to-shard mapping is algorithmic (no directory needed); only the shard-to-node mapping is in the directory.

**Aggressive client-side caching with watch-based invalidation:** 500 routing nodes polling for updates is unnecessary. Replace polling with etcd watches — each routing node opens a watch on the directory prefix. etcd pushes changes only when they occur (typically rare: only during migrations or node failures). The directory read load drops to near zero between migrations.

**Hierarchical directory:** for truly large-scale systems, use a two-level directory: a top-level directory (in etcd) maps key ranges to sub-directories; sub-directories (local metadata tables on each data node) map individual keys within the range to specific rows. This is how HBase's region server works — the META table is itself partitioned.

**Separate directory reads from writes:** serve directory reads from a read-optimized replica cache (Redis or in-process LRU cache on each router) with a short TTL (30 seconds). Write migrations through etcd. Staleness is handled via "not my shard" errors as described. Directory read traffic effectively disappears from etcd.

**Q19. "Explain how a directory-based system handles a hot partition and why it handles it better than consistent hashing."**
A: A hot partition is a shard that receives disproportionately high traffic — a "celebrity" user, a viral product, a frequently-queried reference record. It saturates the CPU or network of its host node while other nodes are underloaded.

**Consistent hashing's limitation:** the shard's node assignment is determined by `hash(key) % N`. Moving the hot shard to a less-loaded node requires changing the hash function or adding a special-case override — the latter is effectively reimplementing a directory for that key. Additionally, splitting the hot shard (to spread load across two nodes) requires adjusting the hash ring, which may trigger broad data movement.

**Directory-based solution:**

Step 1 — detect the hot shard via monitoring (QPS / CPU per shard tracked by the coordinator).

Step 2 — migrate the hot shard to the least-loaded node. One directory entry update; only this shard's data moves. All other shards are undisturbed.

Step 3 — if migration isn't enough (the shard is too hot for any single node), split the shard:
```
Old directory: {shard:42 → Node 3}
                        │
Split at median key: lower half → Node 3, upper half → Node 7
                        │
New directory: {shard:42a → Node 3, shard:42b → Node 7}
```
The split is a directory operation — update one entry to two entries, copy the upper half of the data to Node 7, then commit. The key range is now distributed across two nodes; the hot-spot load is halved.

Step 4 — if the hot shard cannot be split (it's a single key, e.g., a celebrity user with millions of followers), the solution is application-level: use read replicas for the hot key, cache the value in Redis, or denormalize. The directory cannot solve a single-key hot spot because there is only one key to route — no split is possible.

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| Directory | Explicit mapping: key/shard → node | Source of truth; must be strongly consistent |
| Shard granularity | Per-key, per-shard, per-tenant, per-range | Per-shard (1k–10k entries) is the practical sweet spot |
| Directory implementation | etcd, ZooKeeper, Consul, metadata DB | Must be replicated (Raft/Paxos); linearizable writes |
| Client-side cache | Local mapping cache on each routing node | Primary latency mitigation; invalidated on "not my shard" |
| "Not my shard" error | Node rejects request for shard it no longer owns | Triggers client cache invalidation and retry; lazy propagation |
| Shard migration | Copy → delta sync → cutover → directory update | Write pause at cutover: typically 10–500ms |
| Lease-based ownership | Node holds a timed lease per shard | Prevents split-brain; fencing token rejects stale writes |
| Hot shard handling | Migrate to less-loaded node; split shard | Directory update per shard; other shards undisturbed |
| vs consistent hashing | Directory: flexible, explicit; Hash: automatic, algorithmic | Directory needed for load-aware placement and hot-shard splitting |
| MongoDB | Config servers (directory) + mongos (router) | Chunk map in `config.chunks`; balancer migrates chunks |
| Vitess | etcd topology + VTGate router | Keyspace/shard/tablet hierarchy; online resharding |
| Citus | `pg_dist_shard` + `pg_dist_shard_placement` on coordinator | Coordinator is both directory and query router |

---

**Tip for the interview:** Directory-based partitioning questions often come up in the context of "how does MongoDB sharding work" or "how do you handle hot partitions." The key insight to lead with is the fundamental trade-off: directory partitioning is the most flexible strategy (any key can go on any node, hot shards can be split and moved precisely) at the cost of a critical infrastructure component (the directory) that must be highly available and strongly consistent. The questions that separate 5 YOE answers: explaining why client-side caching with lazy "not my shard" invalidation is the right default rather than proactive push (it eliminates the directory from the hot path entirely), walking through the shard migration protocol with the write-pause phase and why lease-based ownership prevents split-brain, and being specific about why per-shard granularity (1k–10k shards) is the practical sweet spot rather than per-key (directory too large) or per-node (too coarse for rebalancing). If asked to compare with consistent hashing, the precise answer is: consistent hashing cannot selectively move a single hot key to a specific node without a directory override — which is exactly what directory partitioning does natively.
