# Key-Based (Hash) Partitioning — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is partitioning (sharding) and why is it necessary?**
A: Partitioning (also called sharding) is the practice of splitting a dataset across multiple nodes so that each node holds a subset of the data. It is necessary when:
- A single machine's storage capacity is insufficient for the full dataset (10TB of data won't fit on one node's disk).
- A single machine's throughput ceiling is too low for the required read/write QPS (a single PostgreSQL primary tops out at ~50,000–100,000 simple reads/sec; you need more).
- A single machine is a single point of failure — distributing data across nodes means no single failure takes down the entire dataset.

Partitioning is distinct from replication: replication copies the same data to multiple nodes (fault tolerance, read scaling); partitioning splits different data across nodes (capacity scaling, write scaling). Production systems use both.

**Q2. What is key-based (hash) partitioning?**
A: Key-based partitioning assigns each record to a partition based on a hash of a designated partition key. The hash function maps the key to a partition number:

```
partition = hash(key) % num_partitions
```

Every record with the same key always lands on the same partition. Records are distributed across partitions based on the hash output, not on the key's alphabetical range or any other semantic ordering. The goal is uniform distribution — each partition receives roughly the same number of records and the same request load.

**Q3. What properties make a good hash function for partitioning?**
A: A hash function for partitioning must satisfy:
- **Uniform distribution:** Outputs are spread evenly across the output space. Similar inputs (e.g., sequential IDs) produce very different outputs. This prevents hot spots where one partition receives disproportionate data.
- **Deterministic:** The same input always produces the same output. Essential for routing — every request for a key must land on the same partition.
- **Fast to compute:** Partitioning decisions are made on every read and write. The hash must be computed in microseconds.
- **Avalanche effect:** Small changes in input (one bit flip) cause large, unpredictable changes in output. Prevents correlated keys from clustering on the same partition.

Common choices: MurmurHash3 (fast, excellent distribution, non-cryptographic — used by Cassandra, Kafka), xxHash (fastest general-purpose hash, used by ClickHouse), FNV-1a (simple, fast, good distribution). MD5 and SHA-256 are cryptographic, overkill for partitioning, and slower than necessary.

**Q4. What is the partition key and how do you choose it?**
A: The partition key is the field (or combination of fields) whose hash determines which partition a record belongs to. Choosing it correctly is one of the most consequential design decisions in a partitioned system.

**Good partition key properties:**
- **High cardinality:** Enough distinct values to distribute data across all partitions without clustering. A boolean field (true/false) as a partition key limits you to 2 effective partitions regardless of how many you have.
- **Uniform access distribution:** The key should be queried roughly uniformly. If 80% of queries are for one key value (e.g., a single tenant), that partition becomes a hot spot.
- **Present in every query:** If your most frequent query doesn't include the partition key, every query is a scatter-gather (fan-out to all partitions) — defeating the purpose.
- **Immutable (or rarely changed):** Changing a record's partition key requires moving the record to a different partition — expensive and operationally dangerous.

**Common choices by system type:**
- User data: `user_id` — high cardinality, present in most queries, immutable.
- Orders: `order_id` or `customer_id` — depends on access pattern (lookup by order vs. lookup all orders for a customer).
- Messages: `conversation_id` — all messages in a conversation on one partition enables efficient range reads.
- Time-series metrics: `device_id` or `metric_name` — not timestamp alone (causes hot spots on the current time partition).

**Q5. What is a hot spot and what causes it in hash partitioning?**
A: A hot spot is a partition that receives disproportionately more traffic than others — becoming the bottleneck even as other partitions sit idle. Causes in hash partitioning:

**Low-cardinality partition key:** `hash("true") % 10 = 3` — all "true" values go to partition 3. With only two distinct values, at most two partitions are active.

**Skewed key distribution:** A small number of key values account for the majority of traffic. A celebrity's `user_id` might generate 1,000× more reads than an average user's. Even with uniform distribution by count, traffic concentration on a few keys makes those keys' partitions hot.

**Time-based partition key:** `hash(timestamp) % N` distributes evenly by count but all current writes go to the key corresponding to "now" — and since timestamps increment sequentially, even a non-time-based hash on a sequential ID can create sequential hot spots if the ID generator produces IDs that hash to the same partition.

**Q6. How does hash partitioning differ from range partitioning?**
A:

| Aspect | Hash Partitioning | Range Partitioning |
|---|---|---|
| Assignment rule | `hash(key) % N` | key falls within [min, max) for the partition |
| Distribution | Uniform by key count | Uneven if key distribution is skewed |
| Range queries | Scatter-gather (all partitions) | Single partition (if query is within a range) |
| Hot spots | Mitigated by hash uniformity | Possible if recent range receives most traffic |
| Key ordering | Destroyed (unordered within partition) | Preserved (data is sorted within partition) |
| Rebalancing | Hard (changing N remaps ~all keys) | Easier (split or merge a range, move data) |
| Typical use | High-write, point-lookup workloads | Time-series, range scan workloads |

The fundamental trade-off: hash partitioning sacrifices key ordering (and therefore efficient range queries) in exchange for uniform load distribution. Range partitioning preserves ordering but risks hot spots on the current range.

## Section 2: Routing and Lookup

**Q7. How does a client know which partition to route a request to?**
A: Three approaches, each with different trade-offs:

**Smart client (client-side routing):**
The client library computes `hash(key) % N` directly and connects to the owning node. No intermediary. Lowest latency — zero extra network hops. Client must know the cluster topology (which node owns which partition). Used by: Redis Cluster clients, most Cassandra client libraries (Datastax driver).

**Proxy / routing tier:**
Clients connect to a stateless routing proxy that computes the partition assignment and forwards the request to the owning node. Client is simple — no topology awareness. Extra network hop (proxy → node) adds ~0.1–1ms latency. Proxy can become a bottleneck if not scaled independently. Used by: MySQL Proxy, Vitess (for MySQL sharding), Twemproxy (for Memcached/Redis).

**Server-side redirect:**
Client connects to any node. If the node doesn't own the key, it returns a redirect (MOVED error in Redis Cluster, or forwards the request on the client's behalf). Client learns the correct partition progressively and caches the mapping. Used by: Redis Cluster's MOVED/ASK mechanism.

**Q8. How does Redis Cluster implement hash partitioning?**
A: Redis Cluster uses a fixed 16,384 hash slots instead of `hash(key) % N`:

```
slot = CRC16(key) % 16384
```

Each Redis node owns a range of slots (e.g., node 1 owns slots 0–5460, node 2 owns 5461–10922, node 3 owns 10923–16383). This slot-to-node mapping is stored in every node and gossiped among nodes.

**Why 16,384 slots instead of direct modular hashing?**
- Fixed slot count decouples the hash space from the number of nodes. Adding or removing a node moves slots (and their data) between nodes without changing the hash function. Only the slot → node assignment changes.
- 16,384 was chosen as the maximum cluster size Redis Cluster was designed to support. CRC16 has a 65,536 output range; 16,384 = 65,536 / 4 was chosen to keep the cluster state (slot assignment bitmap) compact.

**Hash tags:** `{user}.profile` and `{user}.sessions` both hash on `user` (the content inside `{}`), landing on the same slot. This allows multi-key operations (MGET, transactions) on related keys to work within a single node.

**Q9. What is the "scatter-gather" problem and when does it occur with hash partitioning?**
A: Scatter-gather occurs when a query cannot be routed to a single partition and must be sent to all partitions, with results aggregated:

```
Query: SELECT * FROM orders WHERE status = 'pending'
-- status is not the partition key (order_id is)
-- Every partition may have pending orders
-- Must query all N partitions in parallel, collect results, merge
```

This is a fan-out that multiplies query load by N (the number of partitions). A query that takes 10ms on one partition takes 10ms × 1 (best case, parallel) but uses N × the single-partition resources. The aggregation step also adds latency and memory overhead on the coordinator.

**When it's unavoidable:**
- Queries on non-partition-key fields.
- Aggregations (COUNT, SUM, AVG) across all records.
- Joins between two large tables partitioned differently.

**Mitigations:**
- Secondary indexes: maintain a separate index mapping the queried field to partition + record location. The query hits the index (which may be on a single node), gets the location, then fetches from the correct partition. Used by Cassandra's secondary index, Elasticsearch's inverted index.
- Denormalization: store the data in multiple partition schemes simultaneously — one partitioned by `order_id` (for order lookup), another partitioned by `customer_id` (for "all orders for this customer"). Doubles storage, eliminates scatter-gather.
- Pre-aggregation: compute aggregations at write time and store the result, rather than computing at read time across all partitions.

## Section 3: Rebalancing

**Q10. What is rebalancing and why does it happen?**
A: Rebalancing is the process of redistributing data across partitions when the cluster topology changes:
- **Adding nodes:** New nodes join the cluster and should take on some data from existing nodes.
- **Removing nodes:** A failed or decommissioned node's data must be redistributed to remaining nodes.
- **Data growth:** A partition that has grown larger than others needs to be split and its data spread.
- **Load imbalance:** A hot partition needs its load redistributed (often requires a different partition key, not just rebalancing).

**Q11. What is the fundamental rebalancing problem with naive modular hashing?**
A: With `hash(key) % N`, adding or removing a node changes N, which changes the assignment for almost every key:

```
Before: 3 nodes. partition = hash(key) % 3
After:  4 nodes. partition = hash(key) % 4

hash("user:1234") % 3 = 2   → was on node 2
hash("user:1234") % 4 = 1   → now on node 1

For most keys, (hash % 3) ≠ (hash % 4)
→ ~75% of keys move to a different node
→ Massive data migration, cache invalidation for every moved key
```

This is why consistent hashing exists — it reduces the fraction of keys that must move from ~(N-1)/N (almost all) to ~1/N (only the keys adjacent to the new node on the ring). See the consistent hashing guide for full treatment.

**Q12. How does the fixed hash-slot model (Redis Cluster, Kafka) solve the rebalancing problem?**
A: By separating the hash function from the node assignment:
- The hash function maps keys to a fixed set of slots (16,384 for Redis, configurable for Kafka partitions).
- Slot assignment to nodes is a separate, explicitly managed mapping.
- Rebalancing moves slots (and the data in them) between nodes — the hash function never changes.

```
Adding a node: move some slots from existing nodes to the new node.
Removing a node: move that node's slots to remaining nodes.
The hash function (CRC16 % 16384) is unchanged — clients compute the
correct slot for any key using the same formula forever.
Only the slot → node mapping updates.
```

**For Kafka:** The number of partitions is configured at topic creation. Producers hash the message key to a partition: `partition = hash(key) % num_partitions`. Partitions are reassigned to brokers as needed (partition leadership can move). Unlike key-value stores, Kafka rebalancing doesn't move message data — it just reassigns which broker is the leader for a partition.

**Q13. What is the cost of rebalancing data (not just partition leadership) and how do you minimize it?**
A: Data rebalancing requires reading data from old partitions and writing to new ones — I/O-intensive and potentially disruptive:
- A 500GB partition being split means 250GB of data read from disk and written to the new node over the network.
- During migration, both old and new assignments must be valid (split-brain avoided by routing to old partition until migration completes, then cutting over).
- Migrating data consumes disk I/O, network bandwidth, and CPU on both source and destination — competing with live traffic.

**Minimization strategies:**
- **Many small virtual partitions:** Instead of 10 large partitions, use 1,000 small virtual partitions (vnodes in Cassandra, 150 vnodes per physical node). When a node is added, it absorbs a few hundred virtual partitions from many existing nodes — each migration is small, spreading the load across the cluster. No single node is overwhelmed by a large data move.
- **Rate-limited migration:** Throttle migration bandwidth (e.g., 50MB/sec per node) to prevent it from saturating network or disk, at the cost of longer migration duration.
- **Off-peak scheduling:** Run large rebalancing operations during low-traffic windows.
- **Streaming with dual-read:** During migration, the system reads from both old and new locations and reconciles. Allows migration to proceed without a hard cutover moment.

## Section 4: Secondary Indexes and Cross-Partition Queries

**Q14. How do secondary indexes work in a hash-partitioned system?**
A: Hash partitioning routes data by primary partition key, but applications frequently need to query by other fields. Two approaches:

**Local secondary index (per-partition index):**
Each partition maintains its own secondary index covering only the records in that partition. A query on the secondary index requires scatter-gather: query all N partitions' secondary indexes in parallel, merge results.

```
Query: find all orders with status='pending'
→ Send to all N partitions: "give me pending orders in your partition"
→ Collect N result sets
→ Merge, sort, paginate
```
Used by: DynamoDB (local secondary index), Cassandra (secondary index). Simple to implement; scatter-gather is the cost.

**Global secondary index (cross-partition index):**
A separate data structure (itself partitioned, but by a different key) maps secondary key values to the primary key + partition location. A query on the secondary index hits the index partition (single node), retrieves the primary key, then fetches from the correct data partition.

```
Query: find all orders with status='pending'
→ Hit global index partition for status='pending': returns [order_id: 42 on partition 3, ...]
→ Fetch order 42 from partition 3
```
Used by: DynamoDB (global secondary index), Elasticsearch (inverted index). Better query performance; harder to keep consistent (index must be updated atomically with data — distributed transaction or eventual consistency).

**Q15. How do you handle joins across hash-partitioned tables?**
A: Joining two hash-partitioned tables is expensive if they're partitioned by different keys:

**Co-location (partition on the same key):**
If table A is partitioned by `user_id` and table B is also partitioned by `user_id`, rows with the same `user_id` from both tables are on the same partition. Joins are local — no network transfer needed. This is the most powerful optimization for join-heavy workloads. Designing your partition keys to enable co-location is a first-class design concern.

**Broadcast join (small table):**
If one table is small enough to fit in memory on every node, replicate it to all partitions. The large table stays partitioned; each partition does a local join against the full copy of the small table. Used by distributed query engines (Spark broadcast join, Presto/Trino broadcast join). Works for dimension tables (product catalog, user metadata) joined against large fact tables.

**Shuffle join (large tables, different partition keys):**
Repartition both tables by the join key and send matching rows to the same node. Network-intensive but necessary when neither co-location nor broadcast is possible. Used by: Spark shuffle join, MapReduce join phase. The shuffle is the most expensive operation in large-scale batch processing — minimized by co-location at the storage layer.

## Section 5: Hot Spots and Mitigation

**Q16. How do you handle a hot key — a single key receiving disproportionate traffic?**
A: No hash function can distribute traffic for a single key across multiple partitions — by definition, a key always maps to one partition. Strategies to handle hot keys:

**Key splitting with artificial suffix:**
Append a random suffix to the hot key, spreading it across multiple virtual keys:
```python
NUM_REPLICAS = 10

def write_hot_key(key, value):
    # Write to all replicas
    for i in range(NUM_REPLICAS):
        store.set(f"{key}:shard:{i}", value)

def read_hot_key(key):
    # Read from a random replica
    shard = random.randint(0, NUM_REPLICAS - 1)
    return store.get(f"{key}:shard:{shard}")
```
Each of the 10 sharded keys hashes to a different partition — distributing the load. Reads are cheap (random shard). Writes must update all shards — 10× write amplification. Acceptable when reads far outnumber writes (typical for hot content like celebrity profiles).

**L1 local cache in front of the partitioned store:**
Cache the hot key's value in every service instance's in-process memory (Caffeine, Guava Cache). With a short TTL (1–5 seconds), most reads never hit the partitioned store. The hot partition receives at most one request per service instance per TTL period. This is the most common mitigation in practice — a thin local cache absorbs hot-key read spikes without any partitioning scheme changes.

**Application-level rate limiting per key:**
For hot writes (e.g., a counter that everyone increments), aggregate increments locally in the application tier and flush to the partitioned store in batches. 10,000 increments/sec become 100 batches of 100, flushed every 100ms. Reduces hot partition write load by 100×.

**Q17. What is a compound partition key and when does it help with hot spots?**
A: A compound partition key combines two or more fields to form the partition key:

```
partition_key = hash(field_A + field_B) % N
```

**When it helps:** If `field_A` alone is low-cardinality (e.g., `country_code` with 200 values) but `field_B` is high-cardinality (e.g., `user_id` with millions of values), the compound key `(country_code, user_id)` has millions of distinct values — distributing well across partitions.

**When it hurts:** Queries that specify only `field_A` (without `field_B`) still require scatter-gather — the compound key is only useful when both fields are present in the query.

**Cassandra's partition key + clustering key model:** Cassandra separates the partition key (determines which node) from the clustering key (determines ordering within the partition). A compound partition key `(tenant_id, year)` puts all of tenant T's 2024 data on one partition — enabling efficient range scans within the partition while distributing across tenants and years.

**Q18. How does Cassandra handle hot spots via token-aware routing and vnodes?**
A: Cassandra uses consistent hashing with 128-bit Murmur3 hashes mapped to a token ring. Each physical node owns multiple virtual nodes (vnodes), each responsible for a range of the token ring:

- 256 vnodes per physical node by default (configurable).
- A physical node's token ranges are spread across the ring rather than contiguous — so a hot range hits many different nodes' vnodes, not one node.
- Token-aware routing: the Cassandra client library computes the token for the partition key and routes directly to the replica owning that token range. No hop through a proxy.

**Hot partition mitigation:** If one partition key is very hot (a celebrity user), its data sits on one primary vnode. The mitigation in Cassandra is to read from replicas (RF=3, read from any replica). Three replicas distribute read load 3× for that hot partition. Write load is still concentrated on one primary (with replication happening after). For extreme hot spots, the key-splitting technique (Q16) is still needed.

## Section 6: Real-World Systems

**Q19. How does Kafka use hash partitioning, and what are its unique considerations?**
A: Kafka partitioning differs from key-value store partitioning in a critical way: messages within a partition are ordered, and ordering is a feature (not a side effect).

**Default partitioning:**
```java
// Kafka's default partitioner
partition = murmur2(key) % numPartitions
// null key → round-robin across partitions
```

**Key insight — ordering guarantee:** All messages with the same key go to the same partition, and messages within a partition are delivered to consumers in order. This is how Kafka guarantees ordered processing of events for a given entity (user, order, device). Choosing the partition key = choosing the ordering unit.

**Considerations unique to Kafka:**
- **Partition count is fixed at topic creation.** Adding partitions later changes the hash mapping for existing keys — messages for the same key may land on different partitions before and after the change. This breaks ordering guarantees for existing consumers. Design partition count conservatively high upfront.
- **Consumer group parallelism is bounded by partition count.** A consumer group can have at most one consumer per partition. More partitions = more parallelism. Under-partitioning is a scaling ceiling; over-partitioning wastes resources and increases coordinator overhead.
- **Hot partitions = slow consumers.** If one partition receives 90% of messages (because one key value dominates), one consumer handles 90% of load while others idle. Detect via `kafka-consumer-groups.sh` — check per-partition lag. Fix: redesign the partition key, add a random suffix for the hot key's messages (accepts out-of-order delivery for those messages).

**Q20. How does DynamoDB implement hash partitioning?**
A: DynamoDB uses hash partitioning with a fixed internal partition space that scales automatically:

- **Partition key hash:** DynamoDB hashes the partition key (using an internal hash function) to determine which internal partition stores the item. Users never see partition numbers — the mapping is fully managed.
- **Composite key:** DynamoDB's primary key is either a partition key alone (hash key) or a partition key + sort key (range key). Items with the same partition key but different sort keys are co-located on the same partition, sorted by sort key — enabling efficient range queries within a partition.
- **Adaptive capacity:** DynamoDB automatically detects hot partitions and redistributes capacity to them without user intervention. Historically, DynamoDB enforced per-partition throughput limits (3,000 RCU/1,000 WCU per partition), causing hot partition throttling. Adaptive capacity (2019+) allows a hot partition to temporarily burst above its base allocation.
- **Partition splitting:** DynamoDB automatically splits hot or large partitions. Unlike user-managed systems, users don't configure partition count or trigger rebalancing.

**Q21. How does Elasticsearch use hash partitioning for its shards?**
A: Elasticsearch terms its partitions "shards." Each index is divided into a fixed number of primary shards (set at index creation time, cannot be changed without reindexing):

```
shard = hash(_routing) % num_primary_shards
# _routing defaults to the document's _id
```

**Unique characteristics:**
- **Inverted index per shard:** Each shard is a self-contained Lucene index with its own inverted index, segment files, and field data. Queries are parallelized across shards (scatter-gather) and results merged.
- **Routing customization:** The `_routing` parameter can be set per-document or per-request to override default ID-based routing. Setting `_routing = tenant_id` for all of a tenant's documents co-locates them on the same shard — enabling single-shard queries for per-tenant searches.
- **Replica shards:** Each primary shard has zero or more replica shards on different nodes. Reads are distributed across primary and replicas. Writes go to primary, replicated to replicas.
- **Shard count is immutable:** Like Kafka's partition count, Elasticsearch's shard count is fixed at index creation. Changing it requires creating a new index and reindexing all data (the `_reindex` API). This makes initial shard count a critical design decision — oversharding (too many shards for the data volume) wastes resources; undersharding hits scaling ceilings.

## Section 7: Scenario / System Design Style Questions

**Q22. "You're designing the data layer for a multi-tenant SaaS application with 10,000 tenants. How do you partition user data?"**
A: Multi-tenant partitioning has competing concerns — isolation, uniform distribution, and efficient per-tenant queries.

**Option 1 — Partition by tenant_id (pure tenant isolation):**
`partition = hash(tenant_id) % N`. All data for one tenant is on one partition. Efficient per-tenant queries (no scatter-gather for tenant-scoped reads). Risk: large tenants create hot partitions. With 10,000 tenants and a power-law distribution (a few tenants have 1,000× more data than the average), a few partitions hold most of the data.

**Option 2 — Partition by (tenant_id, entity_id):**
`partition = hash(tenant_id + entity_id) % N`. Distributes individual entities across partitions. Tenant-scoped queries require scatter-gather — you must query all partitions and filter by tenant. Good for write distribution; bad for per-tenant read locality.

**Option 3 — Tiered partitioning:**
- Large tenants (top 1% by data volume): dedicated partitions or dedicated shard groups. Each large tenant owns one or more partitions exclusively.
- Small tenants (bottom 99%): partitioned by `hash(tenant_id) % N`, packed into shared partitions. A single partition may hold data for hundreds of small tenants.
- A routing table maps tenant_id → partition assignment. Updated when a tenant grows large enough for promotion.

**Recommendation:** Start with Option 1 for simplicity. Monitor partition size distribution. When a tenant grows to > 10% of a partition's capacity, promote them to a dedicated partition. Build the routing table from day one — it's easier to add tiering later if the routing infrastructure exists.

**Q23. "Your partitioned database has one partition receiving 10× the write traffic of all others. Diagnose the cause and propose a fix."**
A: Systematic diagnosis:

**Step 1 — Identify the hot partition:**
Check per-partition metrics (write QPS, CPU utilization, disk I/O). Confirm which partition is hot and by how much.

**Step 2 — Identify the hot key(s):**
On the hot partition, analyze the write workload: are many different keys writing, or is one (or a few) keys driving the traffic?
- **Many keys, one partition:** The partition key has insufficient cardinality, or the hash function is distributing poorly. Examine the distribution of key values.
- **Few keys driving all traffic:** Classic hot key problem. A small number of high-traffic key values hash to this partition.

**Step 3 — Root cause:**
- **Low-cardinality key:** e.g., `status` field with values ('active', 'inactive') → only 2 effective partitions. Fix: choose a higher-cardinality partition key.
- **Sequential key:** e.g., auto-increment IDs with a hash function that doesn't have good avalanche effect. Consecutive IDs hash to similar partitions. Fix: switch to a UUID or a hash-based ID (e.g., Twitter Snowflake, ULID) that distributes better.
- **Hot entity:** A single entity (a celebrity user, a global configuration key) receives all the traffic. Fix: key splitting (Q16) or local caching (Q16).
- **Time-skewed key:** Data partitioned by date, and all current writes go to "today." Fix: include another high-cardinality field in the partition key.

**Step 4 — Fix:**
- If the partition key choice is fundamentally wrong: repartition. Pick a better key, migrate data (expensive, requires dual-read period), update all write/read paths.
- If it's a hot key with an otherwise-good partition key: apply key splitting or local write aggregation without changing the partition scheme.
- If it's a temporary event (product launch, viral moment): absorb with local caching and write batching. Monitor for recurrence and decide on structural fix based on frequency.

**Q24. "Design the partitioning scheme for a messaging system where users send messages in conversations. What's your partition key and why?"**
A: Access pattern analysis first:

**Most common queries:**
1. Fetch all messages in conversation C (most frequent — every time a user opens a chat).
2. Send a message to conversation C (high frequency writes).
3. Fetch all conversations for user U (less frequent — loading the conversation list).
4. Search messages by content (rare, offline batch is acceptable).

**Partition key choice: `conversation_id`**

All messages in a conversation hash to the same partition. Query 1 (fetch all messages in C) is a single-partition read — no scatter-gather, ordered read within the partition. Query 2 (send message to C) writes to the same partition as the conversation — no cross-partition coordination.

**Trade-offs accepted:**
- Query 3 (all conversations for user U) requires either: a separate table partitioned by `user_id` storing conversation IDs (a conversation membership index), or scatter-gather on the messages table (unacceptable for latency). Solution: maintain a `user_conversations` table partitioned by `user_id` as a secondary index — written to (denormalized) on every message send.
- Hot conversations: a group chat with 10,000 active members generates high write throughput on one partition. For very large conversations, apply key splitting: partition by `(conversation_id, time_bucket)` — e.g., messages from each hour go to a different partition. Reads scatter-gather across time buckets for the full conversation, but write load is distributed.

**Clustering key (within partition):** Sort messages by `sent_at` timestamp within the `conversation_id` partition. This gives efficient range reads ("get messages between time T1 and T2 in conversation C") without cross-partition queries.

**Q25. "You're adding a 4th node to a 3-node hash-partitioned cluster using naive modular hashing (hash % N). What are the operational risks and how do you mitigate them?"**
A: Adding the 4th node changes N from 3 to 4, remapping approximately `(N_new - N_old) / N_new` = 25% of keys immediately — but in practice, `hash % 3 ≠ hash % 4` for ~75% of keys, so nearly all keys need to move.

**Operational risks:**

**Cache invalidation storm:** If this is a cache layer, almost every key suddenly maps to a different node. Cache hit rate drops from ~90% to near 0% for the duration of the migration. Origin (database) receives full traffic — potential overload. Mitigation: pre-warm the new cache node with expected keys before switching traffic.

**Data migration duration:** For a storage layer, migrating 75% of data across the network takes hours or days for large datasets. During migration, you need a consistent routing strategy — either route to old assignment (and migrate writes to new assignment in the background), or use dual-read (check new location, fall back to old). Mitigation: use consistent hashing or fixed hash slots instead of naive modular hashing — only ~25% of keys (1/N_new) need to move.

**Consistency during migration:** A key being migrated has two locations. Writes during migration must go to the final location; reads must check both. Mitigation: two-phase cutover — freeze writes to migrating keys, migrate, unfreeze. Or: use a coordination service to mark keys as "in migration" and handle dual-location reads atomically.

**Mitigation summary — switch to a better partitioning scheme:**
The correct answer in production is to never use naive `hash % N` in the first place. Use consistent hashing (only 1/N keys move) or fixed hash slots (no data moves — only slot→node assignment changes). The migration from naive modular hashing to consistent hashing is a one-time pain worth paying to avoid all future rebalancing costs.

## Quick Reference: Hash Partitioning Decision Checklist

| Decision | Options | Recommendation |
|---|---|---|
| Partition key | Single field, compound, synthetic | Highest cardinality field present in most queries; immutable |
| Hash function | MurmurHash3, xxHash, FNV-1a, CRC16 | MurmurHash3 for general use; CRC16 if Redis Cluster compatibility needed |
| Partition scheme | `hash % N`, consistent hashing, fixed hash slots | Fixed hash slots (Kafka/Redis model) for flexibility; consistent hashing for key-value stores |
| Hot key mitigation | Key splitting, local cache, write batching | Local cache first (zero schema change); key splitting for persistent hot keys |
| Range query support | Secondary index, denormalization, co-location | Co-locate related data by choosing the join key as partition key |
| Rebalancing approach | Naive (move ~all keys), consistent (move 1/N), slot-based (move only slots) | Slot-based or consistent hashing; never naive in production |
| Multi-tenant | All in one scheme, tiered, dedicated large tenants | Tiered: dedicated partitions for large tenants, shared for small |
| Partition count | Fixed (Kafka, ES), dynamic (Cassandra vnodes, DynamoDB auto) | Start high enough for growth; DynamoDB auto-splits if managed |

---

**Tip for the interview:** Hash partitioning questions at senior level almost always pivot from "how does it work" to three follow-ups: (1) hot spots — what causes them, how do you detect them, what are the layered fixes (local cache → key splitting → repartition); (2) rebalancing — why `hash % N` is catastrophic on resize and why consistent hashing / fixed slots exist; (3) cross-partition queries — range queries require scatter-gather, how secondary indexes and co-location mitigate this. The messaging system design (Q24) is the canonical scenario because it forces you to reason about access patterns before choosing a partition key — and exposes the `conversation_id` vs `user_id` trade-off that appears in almost every chat system interview. Lead every answer with access patterns, not with the hash function — the hash function is a consequence of the access pattern decision, not a starting point.
