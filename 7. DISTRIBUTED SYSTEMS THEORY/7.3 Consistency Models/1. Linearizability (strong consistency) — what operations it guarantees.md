# Linearizability (Strong Consistency) — What Operations It Guarantees — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is linearizability?**
A: Linearizability is a correctness condition for concurrent systems: every operation appears to take effect atomically at some single point in time between its invocation and its completion, and the resulting order of operations is consistent with real time. Informally — the system behaves as if there is a single, always-up-to-date copy of the data, and every read reflects the most recent write that completed before it started.

It was formally defined by Maurice Herlihy and Jeannette Wing in their 1990 paper "Linearizability: A Correctness Condition for Concurrent Objects." It is the strongest consistency model for single-object operations and is the foundation on which distributed consensus systems (etcd, ZooKeeper, Google Spanner) build their correctness guarantees.

**Q2. What does "takes effect atomically at a single point in time" mean in practice?**
A: Every operation — no matter how long it takes over the network — can be thought of as having a linearization point: an instant within its execution window when it "happens." Before that instant, the operation hasn't taken effect. After it, all other operations see the result. This means:

- A write W that completes before a read R starts will always be seen by R.
- If two operations overlap in time (concurrent), the system can order them in either direction — but must pick one and stick to it consistently for all future operations.
- The real-time constraint: if W finishes before R starts, R must see W's value. The system cannot pretend W happened after R.

Concretely: if you write `x = 42` and then (after your write call returns) a colleague reads `x`, they must see 42 — not an older value. The write is "visible" globally from the moment it completes.

**Q3. What does linearizability NOT guarantee?**
A: It's important to be precise about scope:
- **Single-object guarantee only:** Linearizability is defined per object (per key, per register). It does not, by itself, guarantee consistency *across* multiple objects. If you read key A and key B in separate operations, you might see A's new value and B's old value — even in a linearizable system — unless the system also provides multi-object transactions or cross-key atomicity.
- **No transaction isolation:** Linearizability doesn't prevent interleaving of multi-step operations from different clients. A client that reads A then updates B based on A's value can still experience a lost update if another client modifies both A and B between those two steps.
- **No ordering across clients without coordination:** Two clients each performing independent writes see a linearizable history, but the relative ordering of their concurrent writes is not determined by the clients — it's chosen by the system and may not match either client's expectation.
- **No durability guarantee by definition:** Linearizability is about visibility ordering, not whether data survives crashes. A system can be linearizable and volatile (lost on reboot). Durability is a separate property (the D in ACID).

**Q4. How does linearizability differ from serializability?**
A: One of the most commonly confused distinctions in distributed systems:

- **Serializability** — a property of *transactions* (multi-step operations). A set of transactions is serializable if their interleaved execution produces a result equivalent to some serial (one-after-another) execution of those transactions. It does not constrain *which* serial order — only that *some* valid serial order exists. Crucially, that serial order need not match real time — a transaction that started later might appear to execute earlier in the serial order.
- **Linearizability** — a property of *single operations* (reads and writes to a single object). The constraint is real-time: the ordering must be consistent with the actual wall-clock timing of the operations.

**Strict serializability** (also called "strong serializability") = serializability + linearizability: transactions are serializable AND the serial order respects real time. This is what systems like Google Spanner and CockroachDB provide. It is the strongest practical consistency guarantee for multi-operation, multi-object systems.

In plain terms: serializability is about "looks like they ran one at a time" (transaction-level); linearizability is about "reads see the latest write" (operation-level, real-time-constrained).

**Q5. What is the relationship between linearizability and the CAP theorem?**
A: In CAP, the C stands for consistency — but Brewer's original CAP theorem uses a specific definition of consistency that is equivalent to linearizability (atomic, single-copy reads/writes). So when CAP says "you can't have both consistency and availability under partition," it specifically means you can't have linearizability and availability simultaneously during a network partition.

- A linearizable system under partition must refuse to respond (return errors) rather than risk returning stale or conflicting data — it chooses CP.
- An available system under partition must respond even if it can't guarantee the latest value — it accepts AP with weaker consistency (eventual, causal, etc.).

etcd and ZooKeeper choose CP — they are linearizable and become unavailable (reads/writes fail) on the minority side of a partition. DynamoDB (with default settings), Cassandra (with quorum < majority), and CouchDB are AP — they remain available under partition but return potentially stale data.

## Section 2: What Linearizability Guarantees

**Q6. What specific operations does linearizability guarantee?**
A: Linearizability makes precise guarantees for the following operation types on a single register (key/object):

**Read (GET):**
- A read always returns the value written by the most recent write that completed before the read started.
- A read that overlaps in time with a write may return either the old or new value — but whichever it returns, all subsequent reads see at least that value (no going backwards).

**Write (PUT/SET):**
- A write that completes has been durably applied. Any subsequent read (by any client anywhere in the system) sees the written value, not any older value.
- Concurrent writes: only one wins. The system picks a winner and all readers see that winner's value consistently — no reader sees one client's value and another reader simultaneously sees a different client's value.

**Compare-and-Swap (CAS / conditional write):**
- Atomically: read the current value, compare to expected, write new value only if match. This operation is linearizable — it appears to happen at a single instant. Between the compare and the swap, no other write can interpose. This is the foundation for distributed lock acquisition, optimistic concurrency control, and leader election.

**Read-Modify-Write (atomic increment, fetch-and-add):**
- Atomically: read the current value, apply a function, write the result. The entire read-modify-write appears atomic to all other clients.

**Q7. What is a linearization point and how do you identify it?**
A: The linearization point is the specific instant (within an operation's invocation-to-completion window) where the operation "takes effect." Before this point, the operation has no observable effect. After it, all observers see the result.

For reads and writes on a single-leader system:
- **Write linearization point:** When the leader applies the write to its state machine (after quorum acknowledgment in a consensus system). Any read that starts after this instant will see the written value.
- **Read linearization point:** When the leader serves the read from its current state (after confirming it is still the leader). For a read served by a follower, there is no single linearization point — this is why follower reads are not linearizable without additional mechanisms.

Identifying the linearization point in an execution history is how you formally prove (or disprove) that a history is linearizable. If you can find a linearization point for every operation such that the resulting total order is consistent with the sequential specification of the object, the history is linearizable.

**Q8. What is a linearizable history — can you show an example?**
A: A history is a sequence of operation invocations and completions by multiple clients. It is linearizable if there exists a legal sequential history (a reordering of operations that respects the object's semantics) consistent with real-time ordering.

**Linearizable history (valid):**
```
Client A: [----write(x=1)----]
Client B:                        [----read(x) → 1----]
Client C:                [----read(x) → 1----]
```
A's write completes before B's read starts → B must see x=1. C's read overlaps A's write — it sees 1, which is valid (it could have seen 0 if it linearized before the write, or 1 after). All consistent with a total order: write(x=1) → read(x=1) [C] → read(x=1) [B].

**Non-linearizable history (violation):**
```
Client A: [----write(x=1)----]
Client B:                        [----read(x) → 0----]
```
A's write completes before B's read starts. B returns 0 (the old value). This is a linearizability violation — there is no valid linearization point assignment that makes this legal. B's read started after A's write completed, so B must see x=1.

**Another violation — reads going backwards:**
```
Client B: [----read(x) → 1----]
Client C:                        [----read(x) → 0----]
```
B reads 1, then C reads 0. If x was 1 when B read it, C's later read cannot return 0 — that would mean time went backwards. No write changed x between B's and C's reads, so this is a violation.

**Q9. What is the "stale read" problem and how does linearizability prevent it?**
A: A stale read returns an older value than the most recently committed write, even though the read started after the write completed. This is the canonical linearizability violation in distributed systems.

Common cause: reading from a replica that hasn't yet received the latest write from the primary (replication lag).

```
Client A writes x=42 to primary.  Primary ACKs. Write is committed.
Client B reads x from replica.     Replica hasn't applied the write yet.
Client B sees x=0.                 Stale read — linearizability violated.
```

**How linearizability prevents it:**
- Route all reads through the leader/primary, which always has the latest committed value.
- For consensus systems (Raft, ZAB): the leader confirms it is still the leader before serving a read (sends a heartbeat round to confirm quorum). This prevents a deposed leader from serving stale reads.
- For systems like Spanner: use TrueTime — assign a timestamp to the write and only serve reads at timestamps the system can guarantee are fully committed (wait out the uncertainty window).

**Q10. How does linearizability interact with caching?**
A: Caching and linearizability are fundamentally in tension. A cache by definition serves data that may be older than the current state of the origin — introducing stale reads. A system with a cache between the client and the authoritative store is not linearizable unless:
- The cache is always updated synchronously before the write is acknowledged (write-through with cache invalidation before ACK) — effectively, the cache is always consistent with the origin.
- Or reads bypass the cache and always hit the authoritative store.

In practice, most caches (Redis with TTL, CDN edge caches, local in-process caches) explicitly trade linearizability for performance. Designers must decide which reads can tolerate staleness and which cannot — and route the latter directly to the authoritative source (the linearizable store, bypassing cache).

## Section 3: Consistency Models Below Linearizability

**Q11. What is sequential consistency and how does it differ from linearizability?**
A: Sequential consistency (Lamport, 1979) requires that all operations appear to execute in some sequential order consistent with each client's program order — but does not require that this order respects real time.

**What it guarantees:**
- Each client's operations appear in the order the client issued them.
- All clients see the same global order of operations.

**What it drops vs linearizability:**
- The real-time constraint. A write that completed before a read started may still appear to execute after the read in the sequential order. The system can "reorder" operations as long as each client's own operations remain in order.

```
Client A: write(x=1)      then      write(y=1)
Client B: read(y) → 0     then      read(x) → 1

Linearizable? No. y=0 but x=1 is only possible if B's read(y) executed
before A's write(y=1) AND B's read(x) executed after A's write(x=1).
But A's writes are sequential, so write(x=1) happened before write(y=1).
If read(x) is after write(x=1) and read(y) is before write(y=1), that
means read(x) and read(y) are interleaved with A's writes — possible
under sequential consistency (no real-time constraint), but the fact that
B's reads both started after both of A's writes completed makes it a
linearizability violation.

Sequentially consistent? Yes, if we order operations as:
read(y)→0, write(x=1), read(x)→1, write(y=1)
Each client's order is preserved, and a valid sequential history exists.
```

**Where it appears:** CPU memory models (x86 TSO is close to sequential consistency for certain access patterns), JavaScript's memory model within a single thread.

**Q12. What is causal consistency and when is it sufficient?**
A: Causal consistency preserves the order of causally related operations — if operation A causally precedes operation B (A "happened before" B in Lamport's sense), then all processes see A before B. Operations with no causal relationship (concurrent) can be seen in any order by different clients.

**What it guarantees:**
- If client A writes x=1 and then (having seen that write) client B writes y=2, all clients see x=1 before y=2.
- A client always sees its own writes before its subsequent reads (read-your-own-writes is implied by causality).
- Monotonic reads: once a client sees a value, it never sees an older value.

**What it drops vs linearizability:**
- No global total order for concurrent operations. Two clients writing independently can be seen in different orders by different readers.
- No real-time constraint — causally unrelated writes have no ordering guarantee.

**When sufficient:** Social networks (comments appear after the post that triggered them), collaborative document editing (your own edits are always visible to you), distributed counters where approximate order is fine. MongoDB's causal consistency sessions and DynamoDB's conditional writes provide causal guarantees in certain configurations.

**Q13. What is eventual consistency and what does it actually guarantee?**
A: Eventual consistency is the weakest useful consistency model: if no new writes occur, all replicas will eventually converge to the same value. It provides almost no timing or ordering guarantees:
- A read may return any value that was written at any point in the past.
- Different clients may see different values simultaneously (divergent replicas).
- The only guarantee: convergence will happen eventually (no specific time bound).

**Common misconception:** "Eventual consistency" is often used loosely to mean "some kind of weak consistency" — but even within eventual consistency, there are important sub-properties:
- **Monotonic reads:** Once you read a value, subsequent reads never return an older value. Not guaranteed by basic eventual consistency.
- **Read-your-own-writes:** After you write, you always see your own write on subsequent reads. Not guaranteed by basic eventual consistency (your write may not have reached your nearest replica yet).
- **Consistent prefix reads:** You never see a state that violates causal ordering. Not guaranteed by basic eventual consistency.

Systems like Cassandra and DynamoDB (with default settings) are eventually consistent with some sub-properties configurable per-operation via consistency levels (ONE, QUORUM, ALL).

**Q14. What is the consistency model hierarchy, from strongest to weakest?**
A: From strongest (most constraining on the system, most intuitive for developers) to weakest (most permissive for the system, most performance-friendly):

```
Strict Serializability
    (linearizable + serializable transactions — Spanner, CockroachDB)
        ↓
Linearizability
    (single-object real-time consistency — etcd, ZooKeeper, Redis single-instance)
        ↓
Sequential Consistency
    (global total order, no real-time constraint — some CPU memory models)
        ↓
Causal Consistency
    (causally related ops ordered, concurrent ops unordered — MongoDB causal sessions)
        ↓
Read-Your-Own-Writes
    (you see your own writes — sticky sessions to primary)
        ↓
Monotonic Reads
    (reads never go backwards — session-pinned replicas)
        ↓
Eventual Consistency
    (converges eventually, no other guarantees — Cassandra ONE, DNS)
```

Each level is a strict superset of the guarantees below it. A linearizable system also provides causal consistency, read-your-own-writes, and monotonic reads. An eventually consistent system provides none of the stronger guarantees.

## Section 4: Implementation in Real Systems

**Q15. How does a single-leader database achieve linearizable reads?**
A: A single-leader (primary-replica) database with synchronous replication can be linearizable for writes — all writes go through the leader, which commits them in order. But reads require care:

**Non-linearizable (default for most systems):**
Reading from a follower. The follower may lag behind the leader — a read returns an older value than the most recently committed write. This is the standard "read from replica" tradeoff.

**Linearizable read approaches:**
- **Read from leader only:** Route all reads to the leader. Simple, but the leader becomes the bottleneck and replicas provide no read throughput benefit.
- **Sync replication + read from any:** If every write is synchronously replicated to all replicas before acknowledging, any replica always has the latest value. Expensive — write latency = slowest replica's round trip.
- **Quorum reads:** Read from a quorum of replicas (⌊N/2⌋ + 1). At least one has the latest value. With a version reconciliation step (take the highest version), this provides linearizability. Used by DynamoDB with `ConsistentRead=true`.
- **Read-your-own-writes via version token:** Return a version/timestamp token with each write. On subsequent reads, send the token — the serving replica checks if it has applied at least that version before responding. If not, it routes to the leader or waits for replication.

**Q16. How does a consensus system (Raft) achieve linearizable reads without stale data?**
A: Raft's challenge: a leader could serve a read from its local state, but what if it was just deposed (a new leader elected) and doesn't know it? The deposed leader's local state is current up to when it was leader but may be missing writes committed by the new leader. Serving from stale local state = non-linearizable.

**Two approaches:**

**ReadIndex (default in etcd):**
1. The leader records its current commit index as the `readIndex`.
2. The leader sends a heartbeat to confirm it is still the leader (must hear back from a quorum).
3. The leader waits until its apply index ≥ `readIndex` (all entries up to readIndex are applied to the state machine).
4. Then serves the read from its state machine.
This ensures the read reflects all writes committed before the read was requested.

**Lease reads (optimization):**
The leader maintains a lease — a time-bounded guarantee that no other leader has been elected (no new leader can be elected without waiting for the election timeout). During the lease window, the leader can serve reads from local state without a quorum heartbeat round trip. Requires synchronized clocks with bounded drift. Used in etcd with `--experimental-enable-lease-checkpoints`.

**Q17. How does Google Spanner achieve linearizability globally across datacenters?**
A: Spanner uses TrueTime — a globally synchronized clock API with a bounded uncertainty interval [earliest, latest]. Every event is assigned a timestamp within its uncertainty interval.

**Commit wait for linearizable writes:**
When a transaction commits, Spanner assigns a commit timestamp T. It then waits until TrueTime's earliest possible time exceeds T (i.e., waits out the clock uncertainty, typically 1–7ms). This guarantees that any transaction starting after the commit wait sees the committed data — because the committing transaction's timestamp is definitely in the past from any observer's perspective.

**Read at a timestamp:**
Any read specifies a timestamp. The serving replica checks if it has applied all writes up to that timestamp. If yes, it serves the read. If not, it waits. This makes reads wait-free if the timestamp is old enough for replication to have caught up.

**Result:** Linearizability (and strict serializability for transactions) across geographically distributed datacenters, with external consistency: if transaction T1 commits before T2 starts (in real time), T2's timestamp is guaranteed to be higher than T1's.

**Q18. How does Redis achieve linearizability (and where does it fall short)?**
A: A single Redis instance is linearizable for its supported atomic commands: GET, SET, INCR, SETNX, GETSET, LPUSH, etc. Every command executes atomically in Redis's single-threaded event loop — there is no interleaving of commands. From a client's perspective, every command takes effect at exactly one point in time, in the order Redis processes them.

**Where Redis falls short:**

- **Redis Cluster (partitioned mode):** Each hash slot is linearizable independently, but cross-slot operations are not atomic. A MULTI/EXEC transaction spanning multiple slots is not atomic across the cluster.
- **Primary-replica with async replication:** If the primary ACKs a write and then crashes before replication, a promoted replica may be missing the write. A subsequent read returns the old value — linearizability violated. Mitigation: `WAIT` command (block until N replicas acknowledge) gives synchronous-like behavior.
- **Sentinel failover:** During the brief failover window, a new primary may serve reads that are missing the last few writes from the old primary — linearizability violation.

**Practical conclusion:** Single Redis instance = linearizable. Redis Cluster or Sentinel = "best effort" linearizability with small violation windows under failure scenarios.

## Section 5: Trade-offs & Decision-Making

**Q19. What is the performance cost of linearizability?**
A: Linearizability is not free — it trades performance for correctness:

**Write latency:** Every linearizable write must be acknowledged by a quorum before returning. In a Raft cluster, write latency = 2 × network RTT to a quorum member + disk fsync. In a single datacenter: 5–20ms. Cross-datacenter: 50–200ms per write.

**Read latency:** Linearizable reads require a leader round-trip (ReadIndex) or leader-only routing. Cannot be served from any nearby replica — eliminates read locality and replica read scaling.

**Throughput ceiling:** All writes are serialized through a single leader. Horizontal scaling of write throughput is impossible within a single linearizable object — you get one log, one sequence, one leader. To scale, you shard (partition into multiple independent linearizable objects), each with its own leader.

**Availability cost:** Under network partition, the minority side becomes unavailable. A linearizable system would rather return an error than return a potentially stale value.

**Q20. How do you decide whether your use case requires linearizability or a weaker model is sufficient?**
A: Ask what happens if a client reads stale data:

**Linearizability required:**
- Distributed locks / leader election: a stale read could grant the lock to two holders simultaneously.
- Account balances, inventory counts at checkout: stale reads enable overdraft or oversell.
- Configuration values that affect security decisions (feature flags enabling/disabling auth): stale could mean a disabled feature is briefly re-enabled.
- Fencing tokens, version checks: the entire correctness of the mechanism depends on reading the current value.

**Weaker consistency acceptable:**
- Social feed, activity streams: slight reordering of posts is imperceptible and harmless.
- Product catalog, content descriptions: a price that's 2 seconds stale rarely causes harm (and your T&Cs can cover it).
- Analytics counters, view counts: approximate is fine; "10,234 views" vs "10,232 views" doesn't matter.
- User preferences, display settings: stale by a few seconds is invisible to the user.
- DNS records: designed around eventual consistency; TTL defines acceptable staleness.

**The key question:** "If two clients simultaneously read this value and get different results, what is the worst-case outcome?" If the answer involves money, security, correctness of a protocol, or data loss — require linearizability. If the answer is "a slightly inconsistent UI for a second" — weaker consistency is fine.

**Q21. How do you achieve linearizability for a multi-key operation?**
A: Linearizability is a per-object property. To achieve linearizable semantics across multiple keys, you need one of:

**Single atomic transaction (within one system):**
Use the database's transaction support. In a Raft-based system, a transaction that touches multiple keys in a single log entry is atomic — the entire transaction appears to take effect at one linearization point. etcd's If/Then/Else transaction is atomic across all keys in the transaction.

**Two-phase locking (2PL):**
Acquire locks on all involved keys before reading/writing any of them. Hold all locks until the transaction commits. No other transaction can observe the intermediate state. This is how traditional RDBMS systems achieve serializable (and with a linearizable lock manager, strict serializable) multi-key transactions.

**Two-phase commit (2PC):**
For multi-key operations spanning multiple shards/nodes, 2PC coordinates an atomic commit across all participants. Phase 1 (prepare): all participants lock resources and vote commit/abort. Phase 2 (commit/abort): coordinator instructs all to commit or abort. The transaction appears atomic across all keys.

**Saga pattern (gives up linearizability):**
For long-running multi-step operations where 2PC is impractical, the Saga pattern uses compensating transactions instead of distributed locks. It does NOT provide linearizability — intermediate states are visible. The trade-off: availability and performance over consistency.

## Section 6: Scenario / System Design Style Questions

**Q22. "You're building a ticket booking system. Two users simultaneously try to book the last available seat. How do you ensure only one succeeds, and what consistency model does your solution rely on?"**
A: This is a classic lost-update scenario requiring linearizability:

**Wrong approach (non-linearizable):**
```
User A reads seats_available = 1
User B reads seats_available = 1
User A writes seats_available = 0, creates booking for A
User B writes seats_available = 0, creates booking for B
→ Two bookings for one seat. Oversell.
```

**Correct approach — database atomic CAS:**
```sql
-- Linearizable compare-and-swap at the DB level
UPDATE seats
SET seats_available = seats_available - 1,
    version = version + 1
WHERE event_id = $1
  AND seats_available > 0
  AND version = $expected_version;
-- Rows affected = 1 → success. = 0 → conflict, retry.
```

The DB's row lock makes this compare-and-swap linearizable — only one UPDATE wins, the other sees 0 rows affected and must retry.

**With distributed lock (if DB CAS is insufficient):**
Acquire a distributed lock on `event:{event_id}:booking` before reading and writing. Only the lock holder proceeds. Requires a linearizable lock service (etcd, ZooKeeper) with fencing tokens passed to the DB to prevent stale lock holders from writing.

**Consistency model required:** Linearizability on the `seats_available` counter. Without it, two reads both return 1, both proceed to book, both succeed, and you've oversold.

**Q23. "A distributed counter tracks the number of active sessions. Multiple services increment and decrement it. A dashboard reads it every second. Does the dashboard read need to be linearizable?"**
A: Almost certainly not — and requiring linearizability would be a costly over-engineering. Analyze the failure modes:

**If the counter is off by 1–2 for up to 1 second (eventual consistency):**
- Dashboard shows "10,432 active sessions" instead of "10,434."
- Impact: zero. This is a monitoring dashboard. Slight lag is expected and harmless.

**If the counter goes negative briefly (stronger inconsistency):**
- Shows "-3 active sessions" — clearly wrong, but only briefly.
- Impact: an alert might fire incorrectly. Fixable with a display floor of 0 and a brief alert debounce.

**Recommendation:** Use a Redis counter with `INCR`/`DECR`. Single-instance Redis is linearizable for individual commands — each `INCR` is atomic. If you're using Redis Cluster and the counter is sharded, the individual increments are still atomic per shard. For a dashboard reading the counter: a regular `GET` is fine — no need for a linearizable read, accept up to replication lag of staleness.

**The exception:** If the counter is used to gate access ("if active sessions > 10,000, reject new logins"), then you need a linearizable read — because a stale read of 9,999 when the true value is 10,001 would incorrectly allow new sessions. Gate-keeping reads require linearizability; display reads do not.

**Q24. "A colleague claims your system is linearizable because writes go through a single primary and replicas are read-only. Is this claim correct?"**
A: Partially correct, with a critical gap. Writes going through a single primary guarantees that writes are totally ordered and each write is committed before the next starts — the write path is linearizable. But linearizability also constrains reads, and reading from replicas breaks the guarantee:

**The violation scenario:**
```
Client A writes x=42 to primary. Primary ACKs.
Primary begins replicating to Replica 1 (async, 50ms lag).
Client B reads x from Replica 1 immediately → returns x=0.
Client A's write completed before B's read started → linearizability requires B to see x=42.
Replica 1 returned x=0 → violation.
```

**For the claim to be correct, one of the following must hold:**
- All reads are also routed to the primary (not replicas).
- Replication is synchronous: the primary does not ACK the write until all replicas confirm they've applied it. Then any replica is always up-to-date.
- Replicas check a version token with each read: if the requested version hasn't been applied yet, they forward to the primary or wait.

**Practical answer:** Single-primary async-replica systems are linearizable for writes but NOT for reads from replicas. This is the standard "read your own writes" problem. The system is linearizable only if reads are also forced through the primary or synchronous replication is used.

**Q25. "How would you explain linearizability to a product manager who is deciding whether to pay for a strongly consistent database or use an eventually consistent one?"**
A: Frame it in terms of user-visible consequences and business risk:

"Eventual consistency means that if two users look at the same data at the same time, they might briefly see different values. For a product listing showing 'in stock,' user A might see the last item as available while user B just bought it — leading to an oversold order and an unhappy customer.

Strong consistency (linearizability) means the database always shows one agreed-upon truth. As soon as user B buys the item, user A's next refresh shows 'out of stock' — no matter which server they're talking to.

The cost is that a strongly consistent database is harder to scale and slightly slower — every write has to be confirmed by multiple servers before you can proceed. An eventually consistent database can be faster and cheaper because servers don't have to agree before responding.

The decision comes down to: what's the cost of a briefly wrong answer? For your checkout inventory, it's an oversell and an unhappy customer — use strong consistency. For the number of views on a product page, showing 9,842 instead of 9,844 for a second is invisible — eventual consistency is fine and cheaper. We should use strong consistency where money or commitments are on the line and eventual consistency for everything display-only."

## Quick Reference: Consistency Model Guarantees

| Model | Reads reflect latest write | Global total order | Real-time order | Multi-key atomicity | Typical systems |
|---|---|---|---|---|---|
| Strict Serializability | Yes | Yes (tx level) | Yes | Yes (transactions) | Spanner, CockroachDB |
| Linearizability | Yes | Yes (op level) | Yes | No (single object) | etcd, ZooKeeper, Redis (single node) |
| Sequential Consistency | Maybe | Yes | No | No | Some CPU models |
| Causal Consistency | Causally related only | No | No | No | MongoDB causal sessions |
| Read-Your-Own-Writes | Own writes only | No | No | No | Sticky sessions, read-from-primary |
| Monotonic Reads | Never backwards | No | No | No | Session-pinned replicas |
| Eventual Consistency | Eventually | No | No | No | Cassandra (ONE), DNS, DynamoDB (default) |

---

**Tip for the interview:** Linearizability questions at senior level always expose two gaps: (1) confusing linearizability with serializability — be precise: linearizability is real-time single-object, serializability is transaction-level without real-time constraint, strict serializability is both; (2) not knowing where the model breaks down — specifically that single-primary async-replica systems are linearizable for writes but NOT for replica reads (Q24), and that caching violates linearizability by definition unless the cache is always synchronously updated. The fencing token question (Q10) connects linearizability to the practical world of distributed locks and is almost always in the follow-up. The product manager framing (Q25) shows you can translate a formal model into business terms — a signal interviewers look for in senior candidates.
