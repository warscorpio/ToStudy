# Causal Consistency — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is causal consistency?**
A: Causal consistency is a consistency model that guarantees: if operation B is causally dependent on operation A (B happened after A, and B's author could have observed A), then every node in the system must apply A before B. Operations with no causal relationship — concurrent operations — may be observed in different orders by different nodes, and that is acceptable.

Informally: causally related events are seen by everyone in the same order; unrelated events can be seen in any order. It sits in the consistency hierarchy between eventual consistency (no ordering guarantees) and linearizability (total ordering of all operations):

```
Weakest                                              Strongest
    │                                                     │
Eventual → Causal → Session → Sequential → Linearizable
```

Causal consistency is the strongest model that remains achievable under network partitions (it is partition-tolerant), which is why it is a practical target for geo-distributed systems where linearizability's latency cost is prohibitive.

**Q2. What does "causally dependent" mean precisely?**
A: Two operations have a causal dependency (written `A → B`, "A happened before B") if any of the following hold:

1. **Same process order** — A and B are performed by the same client/process, and A was executed before B. A client's own writes causally precede its own subsequent reads and writes.
2. **Read-then-write** — process P1 reads a value written by A, then performs B. P1 observed A, so B causally depends on A. "I saw your message, then I replied" — the reply depends on the message.
3. **Transitivity** — if A → B and B → C, then A → C. Causality is transitive.

Operations that are not related by any of these three rules are **concurrent** — neither happened before the other in any causal sense. Concurrent operations have no required ordering in a causally consistent system.

```
A: User posts "Question?"              ← causal ancestor
B: User reads the post                 ← B depends on A (read-after-write)
C: User replies "Answer!"              ← C depends on B → A (transitive)
D: Another user posts "Unrelated msg"  ← concurrent with A, B, C; may appear anywhere
```

**Q3. Why does causal consistency matter in practice? Give a concrete example.**
A: The canonical example is a social media comment thread:

```
Timeline (real order):          What a causally inconsistent replica might show:

Alice posts:                     Replica R2 (missing Alice's post):
  "Anyone up for lunch?"           Bob: "Sure, noon works!"
                                   Carol: "Count me in!"
Bob replies (sees Alice's post):   [Alice's post appears here — reordered]
  "Sure, noon works!"              Alice: "Anyone up for lunch?"

Carol replies (sees Bob's reply):
  "Count me in!"
```

On Replica R2, a viewer sees Bob and Carol responding before seeing what they are responding to — the conversation is incoherent. Causal consistency prevents this: R2 must deliver Alice's post before Bob's reply, and Bob's reply before Carol's response.

Real-world systems where this matters: comment threads, chat (message before reply), collaborative document editing (insert before referencing inserted text), shopping carts (add item before checking out), user profile updates (write new email before sending verification to it).

**Q4. How does causal consistency differ from sequential consistency and linearizability?**
A:

| Model | Ordering guarantee | Concurrent ops | Partition tolerant | Latency |
|--- |--- |--- |--- |--- |
| **Eventual** | None | Any order | Yes | Lowest |
| **Causal** | Causally related ops ordered | Any order | Yes | Low |
| **Sequential** | All ops ordered; same order on all nodes | One global order | No (in practice) | Medium |
| **Linearizable** | All ops ordered; consistent with real time | One global order respecting wall clock | No | Highest |

The practical distinction between causal and sequential: sequential consistency requires that all nodes agree on a single total order of all operations, including concurrent ones. A bulletin board where everyone sees posts in the same order — even unrelated posts — is sequentially consistent. Causal consistency only constrains causally related operations; different nodes can see unrelated posts in different orders. Sequential consistency is strictly stronger than causal; it requires global coordination for unrelated operations even though their ordering is semantically irrelevant.

Linearizability additionally requires the total order to respect real-world time: if operation A completes before operation B starts (in wall-clock time), then A must appear before B in the global order. It is the gold standard for correctness but requires synchronous coordination across all replicas for every operation.

## Section 2: Implementing Causal Consistency

**Q5. What data structure tracks causal dependencies?**
A: The standard mechanism is the **vector clock** (also called version vector). A vector clock is a map from process/node IDs to logical timestamps (monotonically increasing integers), representing the set of events a process has observed:

```
V = { node_A: 3, node_B: 1, node_C: 0 }

Meaning: this process has observed 3 events from node A,
         1 event from node B, 0 events from node C.
```

Rules:
- **On local event**: increment own component: `V[self]++`.
- **On send**: attach current vector clock to the message.
- **On receive**: merge by taking the element-wise maximum of local and received clocks, then increment own component:
  ```
  V[i] = max(V_local[i], V_received[i])  for all i
  V[self]++
  ```

Causal ordering check — event A causally precedes event B (`A → B`) if and only if `V_A[i] ≤ V_B[i]` for all i, and `V_A[j] < V_B[j]` for at least one j. If neither `V_A ≤ V_B` nor `V_B ≤ V_A`, the events are concurrent.

**Q6. Walk through a vector clock example for a causal chain.**
A:

```
Three nodes: A, B, C. Initial clocks: all {A:0, B:0, C:0}.

Step 1: Node A writes "post: Question?"
  A's clock: {A:1, B:0, C:0}
  A sends to B with clock {A:1, B:0, C:0}

Step 2: Node B receives A's write
  B merges: max({B:0,0,0}, {A:1,0,0}) → {A:1, B:0, C:0}
  B increments: {A:1, B:1, C:0}
  B writes "reply: Sure, noon!" with clock {A:1, B:1, C:0}
  B sends to C with clock {A:1, B:1, C:0}

Step 3: Node C receives B's write
  C merges: max({C:0,0,0}, {A:1, B:1, C:0}) → {A:1, B:1, C:0}
  C increments: {A:1, B:1, C:1}
  C writes "reply: Count me in!" with clock {A:1, B:1, C:1}

Now, does B's write causally precede C's write?
  V_B = {A:1, B:1, C:0}
  V_C = {A:1, B:1, C:1}
  V_B ≤ V_C for all components? A:1≤1 ✓, B:1≤1 ✓, C:0≤1 ✓ → YES
  So B → C: B's reply must be applied before C's reply. ✓

Is A's post concurrent with some unrelated post D from another user?
  V_A = {A:1, B:0, C:0}
  V_D = {A:0, B:0, D:1}  (from a fourth node D)
  V_A ≤ V_D? A:1>0 ✗ → not A→D
  V_D ≤ V_A? D:1>0 ✗ → not D→A
  → Concurrent: nodes can deliver A and D in any order.
```

**Q7. What is a causal cut and how do replicas use it to delay delivery?**
A: A causal cut is the boundary representing "everything a replica has causally observed so far." A replica enforces causal consistency by buffering incoming messages and only delivering them when all their causal dependencies have already been delivered — this is called **causal delivery**.

```
Replica R receives message M with vector clock V_M.
M is causally ready to deliver if, for all nodes i ≠ sender:
  V_local[i] ≥ V_M[i]
  (R has seen everything M's sender had seen from other nodes)
And for the sender s:
  V_local[s] = V_M[s] - 1
  (M is exactly the next message from sender s; no gap)

If M is not ready: buffer M until the missing dependencies arrive.
Then deliver from buffer in causal order.
```

Example: M says "reply to post #5" and carries `{A:5, B:2}`. If the replica has only seen `{A:3, B:2}`, it buffers M until it delivers A's events 4 and 5, then delivers M. The user never sees the reply before the post.

**Q8. What are the scalability problems with vector clocks and how are they addressed?**
A: Classic vector clocks have one entry per process/client — in a system with millions of clients, the vector clock grows to millions of entries per message. Three practical solutions:

**Dotted version vectors (per-replica, not per-client):**
Track versions per replica node (a small, fixed number) rather than per client. Clients write through a replica; the replica's version captures all writes it has processed. Vector size = number of replicas, typically 3–10. Used by Riak and modern Dynamo-style systems.

**Interval tree clocks (ITC):**
A generalization of vector clocks that supports dynamic addition and removal of participants without unbounded growth. Useful for systems with churn. More complex to implement than standard vector clocks.

**Hybrid Logical Clocks (HLC):**
Combine a physical timestamp (wall clock, ms precision) with a logical counter. Each node's HLC is `(physical_time, logical_counter)`. HLC advances to `max(local_physical, received_physical)` plus a logical counter for tie-breaking. More compact than vector clocks for many use cases; preserves causality without a vector-per-node entry. Used by CockroachDB, YugabyteDB. The trade-off: HLC cannot detect concurrent events as precisely as vector clocks (it needs clock synchronization to be bounded within a few milliseconds).

**Causal tokens (client-facing):**
Many production systems (MongoDB, CosmosDB) expose causality to clients as an opaque token — a serialized vector clock or HLC value. The client includes the token on its next request; the server uses it to ensure causal ordering without the client needing to understand vector clocks. This keeps the internal implementation flexible (the token format can change) while exposing a simple API.

## Section 3: Causal Consistency in Real Systems

**Q9. How does MongoDB implement causal consistency?**
A: MongoDB supports causal consistency via **causal sessions** (introduced in MongoDB 3.6). A session maintains a `clusterTime` (cluster-wide logical timestamp using a hybrid logical clock) and an `operationTime` (the logical time of the last operation in the session):

```
Client opens causally consistent session
  │
  │  write({name: "Aditya"}) → server returns operationTime=T5
  │
  │  Client's session records: operationTime=T5, clusterTime=T5
  │
  │  read() → client sends afterClusterTime=T5
  │            server waits until its oplog has reached T5
  │            then executes the read
  │            → guaranteed to see the write at T5
```

Implementation details:
- **`clusterTime`** is a `Timestamp` (BSON type: seconds + ordinal) that advances monotonically across the cluster. The primary increments it; secondaries receive it via the oplog.
- **`afterClusterTime`** on a read causes the secondary to wait (block) until its oplog has replicated up to that timestamp before executing the read. This ensures read-your-own-writes and causal ordering within the session.
- **Cross-session causality**: if Client A passes its `clusterTime` to Client B (out of band), Client B can include it in its session to establish a causal dependency between the two sessions — useful for "Client A wrote a post; Client B must see it before seeing replies."
- Sessions are per-driver connection; the causality token is automatically managed by the MongoDB driver. Application code opts into causal consistency at session creation: `client.startSession({causalConsistency: true})`.

**Q10. How does CosmosDB implement causal consistency?**
A: Azure CosmosDB offers causal consistency as one of five configurable consistency levels (Strong, Bounded Staleness, Session, Consistent Prefix, Eventual). CosmosDB's implementation:

- **Session consistency** (CosmosDB's name for what is effectively per-client causal consistency): within a session, reads are guaranteed to see the client's own writes, monotonic reads, and monotonic writes. The session is tracked by a session token — a vector of LSNs (Log Sequence Numbers) per partition, encoded as an opaque string returned with every response.
- The client includes the session token in subsequent requests; the server uses it to ensure the read replica has caught up to at least the LSN the client last wrote to.
- **Consistent prefix** (CosmosDB): a weaker model that guarantees writes are seen in order (no gaps), but doesn't guarantee you see your own writes immediately. Suitable for scenarios where you care about causal ordering of writes by all clients but not necessarily your own writes specifically.

CosmosDB's five levels map to the consistency spectrum: Strong ≈ Linearizability; Bounded Staleness ≈ Sequential within a lag bound; Session ≈ Causal (for the session); Consistent Prefix ≈ Causal ordering without session guarantee; Eventual ≈ No ordering.

**Q11. How does DynamoDB approach causal consistency?**
A: DynamoDB does not natively expose causal consistency as a consistency level — it offers eventually consistent reads and strongly consistent reads. However, applications can implement causal consistency on top of DynamoDB:

- **Strongly consistent reads** (`ConsistentRead: true`) read from the leader replica, which always has the latest committed write. Reading your own writes via strongly consistent reads after every write achieves per-client causal consistency, at the cost of leader read latency and higher RCU consumption.
- **Conditional writes** (`ConditionExpression`) implement optimistic locking — write only succeeds if a version attribute matches. This captures causality for dependent writes: B is only written if A's version is present, ensuring A causally precedes B at the data layer.
- **Streams + application-level ordering**: DynamoDB Streams delivers change events in shard order (ordered within a partition key). Applications consuming streams can enforce causal ordering for a single item's history, but cross-item causal ordering requires application-level vector clock tracking.

In practice, applications needing true causal consistency on DynamoDB use strongly consistent reads for reads-after-writes and version-conditioned writes for dependent writes — achieving causal guarantees without native support.

**Q12. How does Cassandra handle (or not handle) causal consistency?**
A: Cassandra does not provide causal consistency natively. Its quorum model (`R + W > N`) provides strong consistency for a single key across replicas — but does not enforce causal ordering across different keys or across different coordinator nodes. Two examples where Cassandra's model fails causal consistency:

**Cross-key causality:**
```
Client writes K1="post" (quorum achieved on nodes 1, 2)
Client writes K2="reply to K1" (quorum achieved on nodes 2, 3)
Another client reads K2 first (hits node 3) → sees the reply
Then reads K1 (hits node 3, which hasn't received the write yet) → doesn't see the post
```
Cassandra has no mechanism to ensure K1's write is visible before K2's write to a reader — they are independent quorum operations.

**Workarounds:**
- Use a single partition key for causally related data (keeps related data on the same replica set; quorum on one key covers both). Limits scalability.
- Include the causal dependency in the data itself (store the parent post's content within the reply row — denormalization). The reader always sees both when it reads the reply.
- Use Cassandra Lightweight Transactions (LWT) for causal writes — but LWT is per-partition and doesn't help for cross-partition causality.
- Accept eventual consistency and use application-level "wait for parent to load" logic in the client (lazy resolution).

## Section 4: Causal Consistency vs Other Models

**Q13. What is "read your own writes" and is it a form of causal consistency?**
A: Read your own writes (RYOW) is a session guarantee: after a client performs a write, all subsequent reads by that same client will reflect that write. It is a subset of causal consistency — specifically, it enforces the "same process order" rule (a client's write causally precedes its own subsequent reads) but does not enforce causality across clients.

```
Causal consistency ⊃ Read your own writes

RYOW alone:  Client A writes, Client A always reads its own write ✓
             Client B reads after Client A writes → may not see it ✗ (RYOW says nothing)

Causal:      Client A writes, Client B reads after seeing A's write → must see A's write ✓
             (because B's read causally depends on A's write via "read-then-write")
```

RYOW is easier to implement: route all of a client's requests to the same replica (sticky routing), or use a monotonically increasing session token that the replica uses to wait for the client's last write to replicate. Full causal consistency additionally requires tracking cross-client dependencies, which requires vector clocks or equivalent.

**Q14. What is "monotonic reads" and how does it relate to causal consistency?**
A: Monotonic reads is a guarantee that if a client reads a value at time T, all subsequent reads by the same client will return a value at least as recent — the client will never read an older value than one it has already seen. Formally: a client never "goes backward" in the version history.

Monotonic reads is also a subset of causal consistency. If a client reads value V2 (which causally succeeded V1), a causal system guarantees the client will never subsequently read V1 — because V2 → (client observes V2) → (client's next read) is a causal chain, and the next read must respect it.

Session consistency (as offered by CosmosDB and MongoDB) typically bundles four guarantees: read your own writes + monotonic reads + monotonic writes + consistent prefix. Together these form a practical causal consistency model for a single client session.

**Q15. When should you choose causal consistency over eventual consistency or linearizability?**
A:

**Choose causal over eventual consistency when:**
- Your application has user-visible causal chains (post-before-reply, write-before-read acknowledgment, profile-update-before-sending-email-to-new-address).
- Silent reordering would produce incoherent application state that users or other services would observe.
- You need more than "data will eventually converge" — you need "this specific read will see that specific write."

**Choose causal over linearizability when:**
- Your system is geo-distributed and cross-region linearizability latency (100–300ms round-trip for every operation) is unacceptable.
- Your operations don't need a total global ordering — only causally related operations need to be ordered.
- You need partition tolerance — linearizability is not achievable across a network partition; causal consistency is.

**Causal consistency is not sufficient when:**
- You need serializable transactions across multiple keys (bank transfers: debit one account, credit another — requires atomicity and isolation, not just causal ordering).
- You need real-time ordering of unrelated events (a global leaderboard where all score submissions must be totally ordered).
- Your conflict resolution cannot tolerate concurrent writes — you need compare-and-swap atomicity, which requires stronger coordination.

## Section 5: Scenario Questions

**Q16. "A user updates their email address in your distributed system, then immediately requests a verification email be sent to the new address. With eventual consistency, what can go wrong? How does causal consistency fix it?"**
A: With eventual consistency:

```
User writes new_email="new@example.com" → replica R1 (acked)
User triggers "send verification email" → hits replica R2
  R2 hasn't received the write from R1 yet (replication lag)
  R2 reads email="old@example.com"
  Verification email sent to old address ← wrong
```

The write and the read-then-action are causally dependent: the "send verification email" operation is explicitly triggered after observing the email update. Eventual consistency doesn't prevent the system from reading the stale value.

With causal consistency:
- The client's write returns a causal token (HLC or session timestamp) representing the write.
- When the client triggers "send verification email," it includes the token.
- The service handling the email send uses the token to ensure it reads from a replica that has applied the email update before computing the email address to send to.
- The verification always goes to the new address.

Implementation pattern: pass the causal token in a header (`X-Causal-Token`) in the API call chain. The email service waits (or routes to a replica that satisfies) the token before reading the user's current email.

**Q17. "In a distributed chat system, how do you ensure a user never sees a reply before the message being replied to?"**
A: The reply causally depends on the original message — the reply author must have read the original message before writing the reply. This is a textbook causal dependency:

```
M1: Alice posts "Hello" → vector clock {A:1, B:0, C:0}
M2: Bob replies "Hi!" (Bob read M1 first) → vector clock {A:1, B:1, C:0}
```

Causal delivery on the recipient's client:
1. Every message carries a vector clock.
2. The client buffers incoming messages and only renders a message when all its causal predecessors have been rendered.
3. M2 has `{A:1, B:1}` — the client will not render M2 until it has rendered the event at `A:1` (Alice's post M1). If M2 arrives before M1 (out of order over the network), it is held in the buffer until M1 arrives.

Server-side enforcement (stronger):
- The server validates causal ordering before accepting a message: a reply must reference a valid `parent_message_id`, and the parent must exist in the server's storage before the reply is accepted. If the parent is missing, reject the reply with `424 Failed Dependency`.
- This moves causal enforcement to the write path rather than the read path — no buffering needed on the client, and clients receive messages only in causal order.

**Q18. "Your team argues that using strong consistency (linearizability) everywhere solves the causal consistency problem automatically, so you don't need to think about it separately. Are they right? What's the counterargument?"**
A: They are technically correct — linearizability implies causal consistency (linearizability is strictly stronger). If all operations are linearized (total order respecting real time), causal dependencies are automatically preserved. The counterargument is practical, not theoretical:

**Linearizability is too expensive for many real workloads:**
- In a geo-distributed system with replicas in the US, Europe, and Asia, a linearizable write must synchronously coordinate all replicas — adding 100–300ms of cross-region round-trip latency to every operation. This is prohibitive for user-facing interactive features.
- Linearizability requires a single point of coordination (a leader, or a Paxos/Raft quorum). This leader is a throughput bottleneck and a failure domain. A leader failure requires election (seconds of unavailability).
- Linearizability is impossible during a network partition (CAP theorem). A geo-distributed system will experience inter-region connectivity issues; with linearizability, operations must fail or block during partitions. With causal consistency, the majority of operations can continue on each partition independently.

**Causal consistency gives you most of the practical safety at a fraction of the cost:**
- The vast majority of application-level bugs from "wrong ordering" are causal bugs — a reply before a post, a read before an acknowledged write. These are all fixed by causal consistency.
- True linearizability benefits (ordering of concurrent, causally unrelated operations) are rarely observable to users and rarely matter for application correctness.

The correct recommendation is: use causal consistency by default for user-facing distributed data; use linearizability only for operations that genuinely require a total order (distributed counters, leader elections, unique ID generation, financial transactions).

**Q19. "You're building a collaborative document editor (like Google Docs). Multiple users edit simultaneously. Is causal consistency sufficient? What additional guarantees do you need?"**
A: Causal consistency is necessary but not sufficient for a collaborative editor. It solves the ordering problem (a user inserting text at position 5 must see the preceding insert at position 3 first), but concurrent edits — two users inserting text at the same position simultaneously — require additional mechanisms beyond causal ordering:

**What causal consistency gives you:**
- User A's deletion of a character is seen before User B's formatting of that same character (if B's action causally depends on A's).
- A user who was offline and comes back online sees edits in causal order, not random order.

**What causal consistency doesn't solve:**
- **Convergence**: if User A and User B concurrently insert different characters at position 5, causal consistency doesn't define what the document should look like — both inserts are concurrent (neither causally precedes the other). Without a merge policy, different replicas end up with different documents.
- **Intention preservation**: if A deletes character at index 3 and B concurrently inserts at index 3, the naive merge may put B's insert in the wrong position (because A's deletion shifted the indices). The user's intent is to insert after position 2, not exactly at position 3.

**Additional requirement: CRDTs or OT (Operational Transformation):**
- **Operational Transformation (OT)** — used by Google Docs. Transforms concurrent operations against each other so that after transformation and application, all replicas converge to the same document. OT is complex to implement correctly for rich text.
- **CRDTs (specifically Sequence CRDTs: RGA, LSEQ, Logoot)** — data structures that define a commutative, associative merge operation for concurrent edits, guaranteeing convergence without explicit transformation. Causal ordering is often embedded in CRDT design (elements carry causal metadata). Used by Automerge, Yjs, and collaborative editors like Linear.

The full design: causal consistency for ordering + CRDT or OT for concurrent edit convergence + application-level undo/redo history for user-facing conflict visibility.

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| Causal dependency (`A → B`) | A happened before B; B's author observed A | Same-process order, read-then-write, or transitivity |
| Concurrent operations | Neither `A → B` nor `B → A` | May be delivered in any order; no consistency constraint |
| Vector clock | `{node_id: counter}` map tracking observed events | Compare element-wise; detects causal order and concurrency |
| Causal delivery | Buffer messages until dependencies are delivered | Core enforcement mechanism; prevents reply-before-post |
| Dotted version vectors | Per-replica (not per-client) version tracking | Fixes vector clock size problem; used by Riak |
| HLC | Physical time + logical counter per node | Compact; used by CockroachDB, MongoDB, CosmosDB |
| Causal token | Opaque client-facing serialized clock | Session token in MongoDB/CosmosDB; passed in API headers |
| Read your own writes | Client sees its own writes on subsequent reads | Subset of causal; easier to implement (sticky routing) |
| Monotonic reads | Client never reads older value than previously seen | Subset of causal; bundled with RYOW in session consistency |
| Causal vs linearizable | Causal: only related ops ordered; partition tolerant | Linearizable: all ops totally ordered; not partition tolerant |
| CRDT | Data structure with commutative merge for concurrent writes | Needed alongside causal for collaborative editing |
| Causal + partition tolerance | Strongest consistency model that survives partitions | Key reason to prefer it over linearizability in geo-distributed systems |

---

**Tip for the interview:** Causal consistency questions almost always start with a concrete anomaly ("user sees a reply before the post") and ask you to explain why it happens and how to fix it. Lead with the three rules that define causal dependency (same-process order, read-then-write, transitivity) and a concrete example before going into vector clocks. The vector clock mechanics (element-wise max on receive, increment on send) should be demonstrable on a whiteboard. The questions that separate 5 YOE answers: knowing that causal consistency is the strongest partition-tolerant model (which is why it's the practical choice over linearizability for geo-distributed systems), explaining the scalability problem with per-client vector clocks and how dotted version vectors or HLC address it, and being precise about what causal consistency does not solve — concurrent edits to shared state still need CRDTs or OT for convergence. If the interviewer asks about a real system (MongoDB, CosmosDB), know that they expose causality through session tokens / `afterClusterTime` rather than exposing raw vector clocks to the application.
