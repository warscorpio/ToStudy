# Session Consistency — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — The Gap Between Strong and Eventual

**Q1. What user-visible problem does session consistency solve?**
A: In an eventually consistent distributed system, a client writing to a replica and then reading from a different replica may observe their own write disappear — because the replica they're reading from hasn't received the update yet. This produces jarring user experiences:
- A user posts a comment and refreshes the page — the comment isn't there.
- A user updates their profile photo and immediately views their profile — the old photo appears.
- A user adds an item to a shopping cart and navigates to checkout — the cart looks empty.

The write happened. The data is there on some replica. But this client, right now, can't see it. Eventual consistency guarantees convergence eventually — it says nothing about *this user's* experience *right now*. Session consistency defines a set of guarantees scoped to a single client session that prevent this class of anomaly, without requiring the full coordination overhead of linearizability.

**Q2. Why is linearizability (strong consistency) often too expensive a fix for these problems?**
A: Linearizability requires every read to reflect the most recent completed write, globally — which means every read may need to contact a quorum of replicas or the single leader to confirm it's not stale. This adds:
- Latency on every read (not just writes)
- Reduced availability (reads fail if quorum can't be reached)
- Reduced throughput (reads and writes must be coordinated)

But most of the jarring user-experience bugs listed in Q1 only concern *one user* seeing *their own* changes. It's unnecessary to pay the global coordination cost to fix a per-user visibility problem. Session consistency is the right-sized fix: strong enough to eliminate the user-visible anomalies, cheap enough to implement without full coordination.

**Q3. Where does session consistency sit on the consistency spectrum?**
A: Between eventual consistency and causal consistency:

```
Linearizability  >  Sequential  >  Causal  >  Session  >  Eventual
(strongest)                                               (weakest)
```

Session consistency is weaker than causal consistency — it only guarantees ordered, coherent observations *within a single session* (one client's sequence of operations). It makes no cross-session guarantees: two different users may observe the system in inconsistent states relative to each other. Causal consistency extends session-like guarantees across all sessions — if any client observes a write and propagates it to another client, the second client will also see it in causal order.

## Section 2: The Four Session Guarantees

**Q4. Who defined the session consistency model and what are its four guarantees?**
A: Terry et al. defined the four session guarantees in the 1994 Bayou paper *"Managing Update Conflicts in Bayou, a Weakly Connected Replicated Storage System"*. The four guarantees, which can be applied independently or composed, are:
- **Read Your Writes (RYW)**: A client always sees the effects of its own prior writes.
- **Monotonic Reads (MR)**: A client never observes a value older than one it has already read — reads don't go backward in time.
- **Monotonic Writes (MW)**: A client's writes are applied in the order it issued them — write W1 is committed before W2 at every replica.
- **Writes Follow Reads (WFR)**: If a client reads a value V and then writes W, then W is committed after the write that produced V — the write reflects what the client observed.

Each guarantee addresses a different class of anomaly. "Session consistency" in practice usually means all four combined, though systems may offer subsets.

**Q5. What is a "session" in this context?**
A: A session is a logical context representing one client's sequence of interactions with the system. It is not necessarily a single connection or a single server process — it's an abstraction that groups a client's operations so guarantees can be scoped to that group. A session may be:
- A single HTTP request-response lifecycle (stateless apps)
- A user's login period across multiple requests (stateful web app)
- An explicitly opened client session object (e.g., MongoDB `ClientSession`, Cosmos DB session token)
- A device-level context (one session per device per user)

The key property of a session: operations within it are ordered and attributed to one logical client. The system uses this to track what the client has seen and written, enabling the four guarantees without affecting other clients.

**Q6. Can the four guarantees be used independently?**
A: Yes — they are orthogonal and composable. A system can offer any subset:
- RYW alone is enough to fix "I don't see my own writes."
- MR alone is enough to fix "the page showed new data, then refreshed to older data."
- MW alone ensures your own writes are replayed in the correct order.
- WFR alone ensures your reaction to observed data isn't committed before the data it reacts to.

In practice, systems typically offer all four together when they claim "session consistency." Azure Cosmos DB's "Session" consistency level is exactly this: all four guarantees scoped to a session token. A system offering only RYW (e.g., by sticky-routing reads to the write replica for a short window) is offering a weaker form of session consistency.

## Section 3: Read Your Writes (RYW)

**Q7. Formally define Read Your Writes and give the anomaly it prevents.**
A: **Definition**: If a client writes value V to key K in a session, any subsequent read of K in the same session returns V or a value written after V.

**Anomaly it prevents — Write Followed by Stale Read**:
```
Client writes:  PUT  /profile/avatar  →  "new_photo.jpg"   [goes to Replica A]
Client reads:   GET  /profile/avatar  →  "old_photo.jpg"   [served by Replica B, not yet synced]
```
Without RYW: the client sees the old photo immediately after uploading the new one. With RYW: the system ensures the read returns at least the value that was just written, regardless of which replica serves the read.

**Q8. Why does RYW break in multi-replica systems without explicit implementation?**
A: Because writes and reads may be served by different replicas, and asynchronous replication means there is a window — sometimes milliseconds, sometimes seconds — during which the write exists only on some replicas. A load balancer routing the read to an out-of-date replica serves the stale value. The system is correct by eventual-consistency standards (the value will propagate eventually), but it violates the user's reasonable expectation of seeing their own change.

The fundamental issue: the read and write are independent requests to independent servers with no shared state. Without a mechanism to bind the read to the write's replica, or to inform the read's replica of the write's version, the guarantee cannot be made.

**Q9. What are the three main implementation strategies for RYW?**
A:
- **Sticky sessions (server affinity)**: Route all requests from a given client to the same replica — the replica that accepted the write will always serve the subsequent reads. Simple to implement; breaks on server failure, poor for multi-region (nearest replica is forced even if geographically far). Works at the session layer (load balancer, service mesh) without changing the database.
- **Read-after-write tokens**: The write returns a version token (timestamp, LSN, or vector clock component). The client includes this token in subsequent read requests. The serving replica checks whether it has applied at least that version; if not, it either waits (if it's catching up) or forwards to a replica that has. This allows reads to go to any replica without sticky routing while preserving RYW.
- **Write-to-read replica fallback**: After a write, route reads to the write primary (or the exact replica that accepted the write) for a short bounded window (e.g., 1–2 replication lag cycles), then resume normal load-balanced reads. A pragmatic heuristic that avoids the full machinery of version tracking for the common case.

## Section 4: Monotonic Reads (MR)

**Q10. Formally define Monotonic Reads and give the anomaly it prevents.**
A: **Definition**: If a client reads value V from key K in a session, any subsequent read of K in the same session returns V or a value written after V. The client never observes a "newer" value followed by an "older" one.

**Anomaly it prevents — Time Running Backwards**:
```
Client reads:  GET /feed  →  sees posts up to timestamp T2   [served by Replica B, ahead]
Client reads:  GET /feed  →  sees posts up to timestamp T1   [served by Replica A, behind]
              where T1 < T2 — an older view of the data
```
Without MR: a client might see a newer state of the world and then, on the next request (routed to a different replica), see an older state — data appears to rewind. With MR: once a client has seen the state at version V, it will never be served anything older than V.

**Q11. How is Monotonic Reads implemented in practice?**
A: The client or middleware tracks the highest version (timestamp, LSN, or vector clock) it has observed in any read response. On every subsequent read, it passes this "read watermark" to the system. The serving replica must have applied at least this version before responding. Concretely:
- The client sends `X-Read-Version: 1042` in the request header.
- A replica at version 1038 cannot serve this request — it either blocks until it catches up, or forwards to a replica that is at ≥ 1042.
- Once the client observes version 1050 in a response, the watermark advances to 1050.

This requires the versioning scheme to be comparable across replicas — a global logical clock, a Lamport timestamp, or a replica-specific LSN paired with a replication topology understanding. It also requires the client (or a client-side proxy) to maintain and propagate the watermark across requests.

## Section 5: Monotonic Writes and Writes Follow Reads

**Q12. Formally define Monotonic Writes and give the anomaly it prevents.**
A: **Definition**: If a client performs write W1 followed by write W2 in a session, then W1 is committed at every replica before W2 is committed there. No replica ever applies W2 without having first applied W1.

**Anomaly it prevents — Out-of-Order Writes**:
```
Client writes:  APPEND  log  "step 1 complete"   [W1]
Client writes:  APPEND  log  "step 2 complete"   [W2]

Without MW: Replica C applies W2 before W1 → log reads "step 2 complete, step 1 complete"
With MW:    All replicas apply W1 then W2 → log always reads "step 1 complete, step 2 complete"
```
MW is particularly important for sequence-sensitive data: append-only logs, ordered event streams, wizard-style form progress, or any data where write N+1 logically builds on write N. Without MW, replication reordering can corrupt the logical structure of such data.

**Q13. Formally define Writes Follow Reads (WFR) and why it is the hardest guarantee to implement.**
A: **Definition**: If a client reads value V (produced by some write W_read) and then issues write W_new in the same session, then W_new is committed only after W_read at every replica. The client's write causally follows what it observed.

**Anomaly it prevents — Reaction Before Cause**:
```
Client reads:   GET /balance  →  $500    [reads from Replica A, which has applied W_read: "deposit $500"]
Client writes:  POST /transfer $200      [W_new: "transfer $200", goes to Replica B]

Without WFR: Replica B might apply W_new before applying W_read → transfer is processed against
            a $0 balance, producing -$200
With WFR:   W_new cannot commit until W_read is visible — the transfer is always against ≥ $500
```

WFR is hardest to implement because it requires tracking a causal dependency between a read (on one replica) and a subsequent write (possibly on a different replica). The system must record not just what the client wrote, but what the client *read* and which write produced that read — so the write can be held until that causal predecessor is applied at the target replica. This is essentially implementing causal consistency tracking within the scope of one session.

**Q14. How does WFR relate to causal consistency?**
A: WFR is the bridge between session consistency and causal consistency. Within a single session, WFR ensures that all of a client's actions reflect a causally consistent view — writes only go in after the observations they depend on. Across multiple sessions, causal consistency extends this: if Client A's write W is visible to Client B, and B reacts with write W', then W' causally follows W for all other clients too. Session consistency (including WFR) applies only within one session — it doesn't track inter-session causality. This is why two different users can see inconsistent states of the world even in a system with full session consistency.

## Section 6: Implementation Approaches

**Q15. What is a "session token" and how does it encode session state?**
A: A session token is a compact data structure — passed between client and server on every request — that encodes the client's "progress" through the consistency guarantees. Depending on the system, it may encode:
- The version or LSN (Log Sequence Number) of the client's last write (for RYW)
- The highest version the client has read (for MR)
- A vector clock or set of (replica_id, version) pairs (for MR + WFR across a multi-primary system)

Azure Cosmos DB's session token, for example, is a vector of per-partition version tokens. On every write, Cosmos DB returns an updated token. The client sends this token back with every subsequent request — the serving partition checks that its local version is at least the token's value before responding. This single mechanism satisfies RYW, MR, and MW simultaneously within a session.

**Q16. What does session state need to be persisted across, and what are the failure scenarios?**
A: Session state must survive:
- **Request routing changes**: If the load balancer routes request 2 to a different server than request 1, the session token must travel with the client (HTTP header, cookie, or SDK-managed state) so any server can honor it.
- **Client reconnects**: If the client's connection drops and reconnects, the token must be re-presented — most client SDKs handle this automatically.
- **Server failures**: If the replica the client was sticky-routed to crashes, the fallback replica needs the session token to know what version to serve from. Without the token, the guarantee breaks — the client may be served stale data by the fallback.

The failure scenario that breaks sticky-session implementations silently: a server fails, the load balancer routes the client to a lagging replica, and the client sees a stale view — violating both RYW and MR. Token-based implementations are more robust because the guarantee is enforced by the *content* of the request, not the *routing*.

**Q17. How does MongoDB implement causal consistency sessions?**
A: MongoDB 3.6+ introduced explicit `ClientSession` objects with causal consistency. Internally, it tracks two values per session:
- **`operationTime`**: A cluster-wide logical timestamp of the most recent operation the client performed (read or write). Passed as `afterClusterTime` in subsequent operations — the serving node waits until its oplog has reached this time before responding.
- **`clusterTime`**: The most recent cluster-wide time the client has observed (from any response, not just its own ops). Used for WFR — ensures any write commits after what the client has seen.

Every response from the server returns an updated `operationTime` and `clusterTime`. The client SDK automatically tracks these and includes them in future requests. This gives all four session guarantees with explicit, verifiable semantics — without requiring sticky session routing.

**Q18. How does Azure Cosmos DB's "Session" consistency level work?**
A: Cosmos DB offers five named consistency levels (Strong → Bounded Staleness → Session → Consistent Prefix → Eventual). The "Session" level is scoped to a session token the SDK manages per client:
- Reads and writes within the session are guaranteed RYW + MR + MW + WFR.
- Across different clients (different sessions), no guarantees beyond Consistent Prefix (reads never see out-of-order writes, but may see stale data).
- The session token is a per-partition vector of versions. The SDK tracks it automatically across retries, reconnects, and failovers.
- On multi-region reads, the client's session token is sent to the nearest read region — if that region is behind, it either waits or falls back to the write region.

Cosmos DB's Session level is the default and most popular consistency level because it eliminates the common user-facing anomalies while remaining significantly cheaper than Strong or Bounded Staleness.

## Section 7: Relationship to Other Consistency Models

**Q19. How does session consistency relate to PACELC?**
A: Session consistency is a point on the EL vs EC axis in PACELC — it's an EC (consistency costs latency) strategy, but one cheaper than linearizability. Specifically:
- **Sticky sessions**: No added latency for reads if the sticky replica is nearby; but availability suffers on sticky-node failure (PC tendency). In the EL/EC sense, it's approximately free in normal operation — a soft EC.
- **Token-based RYW**: Adds latency only when the serving replica is lagging behind the session token — which in a healthy cluster is rare and brief. Most reads cost nothing extra; only "hot off the write" reads pay a wait penalty. This is EL in normal operation trending toward EC when needed.
- **Full WFR with causal tracking**: Requires propagating causal metadata with every request and response, adding small but non-zero overhead. This is closer to EC in cost, though still cheaper than full linearizability because it only coordinates when causal dependencies actually exist.

Session consistency is why databases like Cosmos DB can offer a "feel consistent" experience at near-EL performance — they only pay the EC coordination cost when the client is actually at risk of a consistency anomaly.

**Q20. Does causal consistency imply session consistency?**
A: Yes — causal consistency is strictly stronger. If a system guarantees causal consistency globally, it guarantees that all causally related operations are ordered for all clients. A single client's session is a causal chain (each operation potentially depends on prior operations by the same client), so causal consistency trivially satisfies all four session guarantees within that session.

The converse is false: session consistency does not imply causal consistency. Two different users can interact with the system in ways that are causally related (User A's post is seen by User B, who replies), but session consistency only tracks each user's own causal chain — it makes no guarantee that B's reply is ordered after A's post from the perspective of a third viewer.

**Q21. What is PRAM consistency and how does it relate to session consistency?**
A: PRAM (Pipelined RAM) consistency, also called "causal+", requires that all processes see writes from each individual process in order — a process P's writes W1, W2, W3 are seen in that order by all other processes, though different processes' writes may be interleaved in different orders. PRAM = Monotonic Writes + Writes Follow Reads scoped to a single writer.

Session consistency adds the read-side guarantees (RYW + MR) on top. The relationship:
- PRAM ⊃ {MW, WFR} — PRAM guarantees the write ordering and causal write-after-read within a session
- Session consistency = PRAM + {RYW, MR}

PRAM is slightly weaker than session consistency because it doesn't constrain what the writing process *reads* — only what others see of its writes. Full session consistency is the practically useful model because the client also reads, and RYW is the most user-visible guarantee.

## Section 8: Limitations and Trade-offs

**Q22. What does session consistency NOT guarantee?**
A: Session consistency is deliberately scoped to one session and makes no promises beyond it:
- **Cross-session ordering**: Two users writing concurrently may see each other's updates in different orders, or not at all for some time. "Both users see a consistent view" is not a session consistency guarantee.
- **Bounded staleness**: Session consistency doesn't specify how old a value can be — only that it won't go backward within a session. A read might return a value that's minutes old if the replica is far behind, as long as it's at least as recent as what this client has seen before.
- **Global progress**: There's no commitment that writes by this session will ever be visible to other sessions within any timeframe — that's eventual consistency territory.
- **Convergence of concurrent writes**: If two sessions write concurrently to the same key, session consistency says nothing about which value wins or when the losing write is visible to the winning writer's session.

**Q23. What is the "multi-device" problem and why does session consistency fail to solve it?**
A: Session consistency scopes its guarantees to one logical session — usually tied to one client instance (browser tab, mobile app, SDK connection). When a user operates across multiple devices:
- User writes on their phone (Session A): `PUT /note "content A"` — Session A's RYW guarantee means the phone sees its own write.
- User reads on their laptop (Session B): `GET /note` — Session B has no knowledge of what Session A wrote. The laptop may serve a stale value.

From Session B's perspective, this isn't a violation of session consistency — Session B never wrote anything, so RYW doesn't apply, and if Session B has never seen "content A" before, MR isn't violated either. But the user experiences exactly the "I just saved and can't see it" anomaly that session consistency was supposed to prevent — just across devices.

Fix: extend the session across devices by sharing the session token (e.g., storing it in a per-user server-side store — Redis keyed by user ID — so any device retrieves and uses the same session state). This collapses multiple physical sessions into one logical user session. Alternatively, upgrade to causal consistency (which is cross-session by design).

**Q24. What is "session hijacking" from a consistency perspective (not a security perspective)?**
A: When a session fails mid-stream and a different client picks up the session token, the new client inherits the session guarantees — including the version watermarks. If the new client is a different user (e.g., a shared terminal), it will see data up to the previous user's version, which may expose more recent writes than the new user would otherwise see. More commonly in distributed systems, a "session hijack" is when a crashed client's session is resumed by a retry component that doesn't correctly restore the full session state — leading to replayed writes (violating MW) or reads that don't match the session's established watermark (violating MR). Session token propagation must be treated as carefully as auth tokens in the retry/failover path.

## Section 9: Scenario / System Design Questions

**Q25. "Users of your SaaS app report that after submitting a form, they're redirected to a list page that doesn't show their new record. Your backend uses Cassandra with `LOCAL_ONE` consistency. What's the problem and what are your options?"**
A: Classic RYW violation. The form POST writes to one Cassandra node at `LOCAL_ONE`. The redirect triggers a GET that hits a different node via the load balancer — that node hasn't yet received the asynchronous replication of the write. Options, in order of implementation cost:

- **Read-after-write at higher consistency**: Use `LOCAL_QUORUM` for the GET immediately following a POST — this contacts multiple nodes and returns the freshest value. Adds latency only on the post-write read. Viable if the form submit is infrequent and user-triggered.
- **Optimistic UI**: After successful form submit, inject the new record into the UI from the client's own POST response data — don't re-fetch from the server immediately. The server data catches up by the time the user navigates away and returns.
- **Sticky-route post-write reads**: For the 1-2 seconds after a write, route this user's reads to the coordinator node that handled their write. Can be implemented via a short-lived cookie or a routing header that the load balancer or API gateway respects.
- **Token-based RYW**: On write success, return a `X-Write-Version` header. The subsequent GET includes it, and the serving node waits until it's at that version before responding. Most correct; requires version-tracking infrastructure.

**Q26. "You're designing a collaborative document editor where multiple users edit simultaneously. A user edits paragraph 3, reads paragraph 5 (which another user just updated), then edits paragraph 5 themselves. What session guarantee is specifically relevant to that last edit?"**
A: Writes Follow Reads (WFR). The sequence:
1. User reads paragraph 5 — observes another user's write W_other.
2. User writes paragraph 5 — this is W_new, which logically reacts to W_other's content.

WFR requires that W_new is committed only after W_other at every replica — otherwise a replica might apply W_new on top of the old paragraph 5, losing W_other's changes and creating a causality inversion where the user's "response" to a change appears before the change itself.

Without WFR, a replica processing W_new without having W_other could produce a merge state that has already been superseded — the editor's CRDT or OT layer would then operate on a stale base, producing incorrect output. WFR is the session guarantee that makes "I edited what I saw" safe in a distributed setting.

**Q27. "Your team is evaluating Azure Cosmos DB for a user preferences service. A teammate suggests using Eventual consistency to minimize cost. What specific user-facing anomalies would this allow, and is Session consistency enough to fix them?"**
A: With Eventual consistency on Cosmos DB, all four session guarantees are dropped for cross-region reads. Specific anomalies:
- **RYW violation**: User saves dark mode preference, refreshes — the page loads light mode (different region, stale read).
- **MR violation**: User's notification count shows 7, then on the next page load shows 4 (the region serving the second read is behind).
- **MW violation**: User updates two preferences in sequence — a replica applies the second before the first, leaving the preferences in a partially updated, logically inconsistent state.

Session consistency (the Cosmos DB default) fixes all of these within a session by tracking a session token. Since user preferences are almost always single-user operations (one user reading/writing their own settings), Session consistency is exactly sufficient — you don't need Bounded Staleness or Strong, which would add latency and cost with no benefit for this use case. The teammate's instinct to minimize cost is right; the right answer is Session, not Eventual.

**Q28. "A distributed task queue allows workers to claim tasks. A worker reads a list of available tasks, picks one, and writes a claim. What happens without WFR, and how would you design around it?"**
A: Without WFR: the worker reads the task list from Replica A (which shows task T as available), then sends a claim write to Replica B. If Replica B hasn't yet received the task list state the worker read from, it might be operating on a state where T has already been claimed by another worker — but Replica B doesn't know that yet. Both workers successfully claim T, violating the at-most-once task execution guarantee.

Design options:
- **Optimistic locking with conditional writes**: The claim write includes the version of the task state the worker read (`PUT /task/T/claim IF version=42`). The database rejects the write if the current version doesn't match — the worker re-reads and re-evaluates. This doesn't need WFR; it achieves the safety guarantee through a compare-and-swap primitive instead.
- **Single-leader routing for claims**: Route all task claims to the primary/leader replica — eliminating cross-replica races for the write path. Reads can be distributed; writes are serialized at the leader.
- **Session consistency with WFR**: Worker's claim write carries a causal token encoding "I read version V of the task list." The database holds the write until V is visible at the target replica, then applies it. If another worker claimed T in the meantime, the write conflicts and the worker retries.

The conditional write (option 1) is the standard production approach — it's simpler and doesn't require session-level causal tracking infrastructure.

## Quick Reference: The Four Session Guarantees

| Guarantee              | Definition                                                        | Anomaly Prevented                          | Key Implementation Mechanism            |
|---                     |---                                                                |---                                         |---                                      |
| Read Your Writes (RYW) | Client sees its own writes in subsequent reads                    | "I saved it and it disappeared"            | Sticky routing, write tokens, read watermarks |
| Monotonic Reads (MR)   | Client never observes a value older than one it has already read  | Data appears to go backward in time        | Client-side read version watermark       |
| Monotonic Writes (MW)  | Client's writes are applied in issue order at every replica       | Writes appear in wrong order at replicas   | Write sequencing, LSN tracking           |
| Writes Follow Reads (WFR) | A write commits only after the write that produced the read it reacted to | Reaction appears before cause            | Causal tokens, operation timestamps      |

## The Core Mental Model

```
Session consistency = "A user's experience of the system is self-consistent."

The four guarantees prevent four ways a client's own history can be violated:
  RYW → My writes don't vanish when I look back
  MR  → The world doesn't rewind when I refresh
  MW  → My writes land in the order I sent them
  WFR → My reaction to what I saw commits after what I saw

What it does NOT do:
  × Guarantee consistency between two different users
  × Bound how stale reads are (only that they don't go backward)
  × Protect cross-device unless session state is explicitly shared
  × Replace coordination for mutual exclusion (still need conditional writes / compare-and-swap)

Where to reach for it:
  ✓ User-facing CRUD (profile, settings, cart, feed)
  ✓ Any system where "the user sees their own actions reflected immediately" is the UX contract
  ✓ As the default consistency level where full linearizability would be over-engineered
```

**Tip for the interview:** Session consistency rarely appears in interviews as the main topic — it usually surfaces as "how would you fix this user-facing bug?" Be ready to name the specific guarantee that's violated (nine times out of ten it's RYW), explain *why* it breaks in a multi-replica system, and give at least two implementation options with their trade-offs. The strongest 5 YOE answer connects it upward to the consistency spectrum ("weaker than causal, stronger than eventual") and downward to a concrete implementation ("in our stack, we'd use a write token returned in the POST response and pass it in the subsequent GET header"). Knowing that Cosmos DB calls this "Session consistency" and MongoDB calls it "causal consistency sessions" — and that they're the same idea — signals you've seen this in real systems, not just textbooks.
