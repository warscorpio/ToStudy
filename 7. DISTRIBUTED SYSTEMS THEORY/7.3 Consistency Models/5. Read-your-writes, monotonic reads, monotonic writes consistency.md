# Read-Your-Writes, Monotonic Reads, Monotonic Writes Consistency — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Weak Consistency Breaks Applications

**Q1. What is the gap between "eventual consistency" and what applications actually need?**
A: Eventual consistency guarantees that if no new writes occur, all replicas will eventually converge to the same value. It makes no guarantees about what any specific client sees in the meantime — a client might read stale data indefinitely, or see values jump backward in time, or have its own writes be invisible to it moments after writing. These anomalies are tolerable for some data (view counts, recommendation scores) but catastrophic for others.

The gap: application developers reason about their systems as if they have a single coherent view of data. A user who submits a form expects to see what they just submitted on the confirmation page. A service that writes a record and then reads it back expects to see the record. A client that reads version V of a document does not expect to read version V−1 on the next request. None of these expectations are guaranteed by pure eventual consistency — but they feel so fundamental that violating them produces bugs that look like data corruption to users and engineers alike.

Session consistency models — read-your-writes, monotonic reads, and monotonic writes — are the minimum set of guarantees that make eventually consistent systems behave like systems a developer can reason about, without paying the full coordination cost of linearizability.

**Q2. What is the "session" in session consistency models, and why does it matter?**
A: A session is a logical unit of interaction between a client and a distributed system — typically the duration of a user's login, a service's request lifecycle, or a connection to a database. Session consistency models make guarantees *within a session* rather than globally across all clients.

This scoping is deliberate and important:
- **Within a session:** the client sees a consistent, forward-progressing view of data it has read and written.
- **Across sessions:** no ordering guarantees. A different client in a different session may see the data in a different state.

The session scope is the right granularity for most application correctness requirements. A user cares that *they* see their own writes — they don't necessarily care that another user sees those writes in the same instant (that's a stronger global consistency property). Scoping guarantees to sessions lets systems provide meaningful correctness without global coordination, which is what makes session models practical on top of eventually consistent infrastructure.

**Q3. What are the four session consistency guarantees, and how do they compose?**
A: The four session consistency models (from Terry et al., 1994 — the Bayou paper) are:

- **Read-Your-Writes (RYW)** — a client always sees the effects of its own writes in subsequent reads, within the same session. If you write X=5, you won't read X=3 afterward.
- **Monotonic Reads (MR)** — once a client has seen a value at time T, it will never see an older value. Reads only move forward in time within a session. You won't "go back" to an older state.
- **Monotonic Writes (MW)** — writes from a single client are applied to all replicas in the order the client issued them. A client's second write is never applied before its first write on any replica.
- **Writes Follow Reads (WFR)** — also called "session causality." If a client reads a value X and then writes Y based on that read, the write Y is guaranteed to be applied after the version of X that was read. Prevents the anomaly where your write is applied to a replica that hasn't yet seen the data you based your write on.

Composing all four gives **PRAM consistency** (Pipelined RAM), which provides strong session-level guarantees without requiring global coordination. Composing RYW + MR + MW + WFR gives **causal consistency** when applied globally (all clients, not just within a session). The individual models are useful independently — many systems implement only one or two depending on the use case.

## Section 2: Read-Your-Writes

**Q4. Define read-your-writes precisely, and give a concrete example of what happens without it.**
A: Read-Your-Writes (RYW) guarantees: if a client writes a value W in session S, any subsequent read of that value within session S will return W or a later write, never a value that predates W.

Without RYW, the following sequence is possible in an eventually consistent system:
1. User updates their profile photo. Write goes to Replica A.
2. User is redirected to their profile page. Read goes to Replica B (load balancer picked a different server).
3. Replica B hasn't yet received the write from Replica A (replication lag).
4. User sees their old photo. They refresh. They see the old photo again. They think the update failed.
5. They submit the update again. Now they have a duplicate write.

This is not a theoretical edge case — it is the most common user-visible consistency bug in distributed systems. Facebook, Twitter, and Amazon have all documented this exact failure mode. It appears as a data loss bug to users even though no data was actually lost — the data is on Replica A, just not yet visible from Replica B.

**Q5. How do you implement read-your-writes in practice? What are the main strategies?**
A: Four main implementation strategies, each with different trade-offs:

- **Sticky sessions (session affinity)** — route all requests from a client session to the same replica. If every read goes to the same node that received the write, RYW is trivially guaranteed. Implementation: the load balancer uses a session cookie or IP hash to pin a client to a server. Downside: defeats load balancing flexibility; if the pinned server goes down, the client is disrupted; doesn't help if the same user connects from multiple devices (different sessions, different servers).

- **Read from primary** — always read from the primary (write) node. Since writes go to the primary and reads come from the primary, the primary always has the latest writes. Downside: eliminates the read scalability benefit of having replicas; the primary becomes a bottleneck; increases latency if the primary is geographically distant.

- **Replication timestamp / monotonic read token** — on each write, the server returns a token encoding the write's position in the replication log (e.g., a log sequence number or a timestamp). The client stores this token and sends it with subsequent reads. The receiving replica checks: "do I have all writes up to this token?" If yes, serve the read. If no, either wait until replication catches up, or forward the read to a replica that has caught up. Used in: MySQL Router's "transaction tracking," Google's Spanner's session-level timestamps, MongoDB's causal consistency sessions.

- **Write-through cache / local write buffer** — the client keeps a local write buffer. Reads first check the buffer before going to the server. If the read hits the buffer, the client sees its own write. If it misses the buffer, it goes to the server. After the write has been durably replicated (confirmed by the server), the buffer entry can be evicted. Downside: the buffer is per-session in memory; a crash or session restart loses the buffer. Works well for single-device sessions; complex for multi-device.

**Q6. What is the "multi-device" problem for read-your-writes, and how do you solve it?**
A: Sticky sessions and write buffers work for a single device — the same browser session, the same connection. But users increasingly access services from multiple devices simultaneously: a mobile phone, a laptop, a tablet. The same user writes on one device and reads on another, which is a different session. RYW guarantees per-session don't help here.

This is the multi-device (or cross-session) RYW problem. Solutions:

- **Replication token propagation** — when a write produces a replication token, the client syncs that token to the server (or a shared token store). Other sessions for the same user fetch the token and use it for reads. This requires a coordination layer (a small, fast store that maps user ID → latest write token) but keeps the actual data reads flexible. LinkedIn's Espresso and Apple's CloudKit use variants of this approach.
- **Route all reads for a user to the primary** — for a specific user's data, always read from the primary. Effectively per-user sticky routing rather than per-session. More targeted than routing all reads to primary; still limits replica read scalability for hot users.
- **Asynchronous replication with read-repair** — detect the stale read (compare the returned value's version against a recently written version) and trigger immediate read-repair from the primary. Optimistic but adds complexity and a visible inconsistency window.
- **Accept the gap with UI mitigation** — for cases where cross-device RYW is impractical, provide UI that sets expectations: "Your changes are being synced across devices" with a spinner. Not a technical solution, but honest and common for eventually consistent systems (iCloud, Google Drive, Dropbox all do this for conflict resolution).

**Q7. What is the relationship between read-your-writes and idempotency?**
A: They solve adjacent but different problems. RYW prevents a client from re-submitting a write because it couldn't see its original write (it appeared to be lost). Idempotency ensures that if the client does re-submit (because it genuinely can't tell if the original write succeeded), the duplicate submission doesn't cause double-processing.

The interaction: a system with RYW but without idempotency can still have double-processing if the client gets confused by a network failure between the write going through and the acknowledgment arriving back. A system with idempotency but without RYW can still have the user-visible anomaly of "my change disappeared." A robust system needs both:
- Idempotency: re-submitting the same write is safe.
- RYW: the client can see its write and know it doesn't need to re-submit.

Together they eliminate both the user confusion and the correctness risk of re-submission.

## Section 3: Monotonic Reads

**Q8. Define monotonic reads precisely, and give a concrete example of what happens without it.**
A: Monotonic Reads (MR) guarantees: if a client reads value V at time T, all subsequent reads in the same session will return V or a more recent value. The client's view of data only moves forward — it never "sees the past" after having seen the present.

Without monotonic reads, the following anomaly is possible:
1. A client reads a post with 150 comments. The read goes to Replica A which has caught up to time T.
2. The client refreshes. The load balancer routes to Replica B, which is lagging behind at time T−30s and only has 120 comments.
3. The client sees 30 comments disappear. They think comments were deleted. They're confused or alarmed.

This "time traveling backward" anomaly is deeply disorienting to users. It occurs whenever multiple reads in the same session can be routed to different replicas at different stages of replication. Users don't understand replication lag — they interpret decreasing values as data deletion and increasing values as data arrival. Monotonic reads prevents the former.

**Q9. How does monotonic reads differ from read-your-writes? When do you need one without the other?**
A: They address different anomaly classes:

- **RYW** — "I can't see *my own* writes." The stale data is caused by the client's own recent write not yet being visible. The write is the trigger.
- **MR** — "The data I'm reading is *going backward in time.*" The stale data is caused by being routed to a replica that is further behind than a previous read. No write by the client is necessary — pure reads can exhibit this anomaly.

You might need MR without RYW: a read-only analytics dashboard that reads from multiple replicas. The dashboard makes no writes, but if it's routed to different replicas on each refresh, values can jump backward. MR prevents this without requiring any write tracking.

You might need RYW without MR: a write-heavy service (a command processor) that writes data and immediately reads it back to verify, but doesn't care about the broader state of the replica it's reading from — it just needs to see its own writes. No "going back in time" concern because reads always follow writes from the same client.

In practice, MR and RYW are usually implemented together since the implementation mechanisms (replication tokens, session affinity) often provide both.

**Q10. How do you implement monotonic reads?**
A: The core idea: track the "read frontier" — the furthest-ahead replication position the client has seen — and never serve reads from a replica that's behind that frontier.

Implementation strategies:

- **Session token (read frontier)** — on each read response, the server includes a replication position token (an LSN, a timestamp, or a vector clock position). The client stores the *highest* token it has seen. On the next read, it sends this token; the serving replica checks whether it has applied all writes up to that token. If yes, serve the read. If no, either wait or redirect to a more up-to-date replica. This is how Cassandra's `SERIAL` reads and MongoDB's causal sessions work.
- **Sticky sessions** — same as RYW: pin the client to one replica. Since one replica's state only ever moves forward, monotonic reads are guaranteed by construction. But loses load balancing flexibility.
- **Replica version tracking at the router** — the load balancer or service mesh tracks the replication lag of each replica. When routing a read for a session, it only routes to replicas that are at or ahead of the session's last read position. The client is unaware; the routing layer enforces MR. More complex to implement but transparent to the client.
- **Quorum reads** — read from a quorum (majority) of replicas and return the most recent value among responses. Since a quorum always includes at least one replica that has the latest committed write, the response is always at least as recent as the latest committed value — trivially monotonic since the committed frontier only advances. Expensive but strong.

**Q11. What is the "read frontier" advancing problem, and how does it create overhead?**
A: The read frontier is a per-session state that must be maintained, propagated, and checked on every read. At scale this creates overhead:

- **Storage** — if you have 10 million active sessions and each session maintains a replication token (typically 8–16 bytes for an LSN or timestamp), that's 80–160MB of session state. Usually stored in a distributed session store (Redis) rather than in-memory on each server.
- **Token propagation latency** — the client must send the token with every read request. At high request rates this adds a small but non-zero amount of data to every request header. More importantly, the server must parse and validate the token before serving the read.
- **Replica readiness check** — for token-based approaches, the replica must check its own replication position against the client's token before serving. If the replica is behind, it either blocks (adding latency) or redirects (adding a network hop). Under heavy replication lag, many reads get blocked or redirected, creating a load amplification effect: the replicas that are ahead receive disproportionate read traffic.
- **Token expiry** — tokens must eventually expire (sessions end, users log out). A token that's valid indefinitely accumulates metadata that never gets cleaned up. Most systems expire tokens with the session TTL.

For read-heavy systems with strict monotonic read requirements, this overhead is non-trivial. Teams sometimes accept the occasional backward read for low-value data rather than pay the operational cost of full monotonic read enforcement.

## Section 4: Monotonic Writes

**Q12. Define monotonic writes precisely, and give a concrete example of what happens without it.**
A: Monotonic Writes (MW) guarantees: writes from a single client (within a session) are applied to all replicas in the order the client issued them. If a client writes W1 followed by W2, no replica will ever see W2 applied before W1.

Without monotonic writes, the following anomaly is possible:
1. A client issues Write 1: "Set user role to EDITOR."
2. The client immediately issues Write 2: "Set user role to ADMIN."
3. Write 2 reaches Replica A first (faster network path). Replica A applies W2, role = ADMIN.
4. Write 1 arrives at Replica A second. Replica A applies W1, role = EDITOR. The second write overwrites the first — the client's intended final state (ADMIN) is lost.
5. During replication, Replica B receives the writes in the correct order (W1 then W2) and ends up with role = ADMIN. Replica A has EDITOR. The two replicas have diverged.

This is not just a user-visible bug — it's a correctness violation where the same client's writes produce different final states on different replicas. Monotonic writes prevents this by ensuring W1 is applied everywhere before W2.

**Q13. Is monotonic writes the same as write ordering? How does it relate to "happens-before"?**
A: Monotonic writes is a specific form of write ordering — it enforces that *a single client's* writes are ordered consistently across all replicas. It does not say anything about write ordering across clients (concurrent writes from two different clients may arrive in different orders on different replicas — that's a conflict resolution problem, not an MW violation).

The relationship to happens-before: monotonic writes is the session-level expression of the "same process" rule in Lamport's happens-before relation. In Lamport's model, if event A precedes event B in the same process's execution, then A happens-before B. Monotonic writes operationalizes this for writes specifically: the client is the "process," and the client's writes form a sequence where each causally precedes the next.

Monotonic writes is weaker than causal consistency, which requires ordering across clients for causally related writes (if Client 1 reads a value and Client 2 writes based on seeing that value, Client 2's write must come after Client 1's write everywhere). MW only enforces within-client ordering.

**Q14. How do you implement monotonic writes?**
A: The primary mechanism: sequence numbers.

- **Client-side sequence numbers** — the client attaches a monotonically increasing sequence number to each write (e.g., `seq=1, seq=2, seq=3`). The server applies writes from the same client in sequence number order. If seq=3 arrives before seq=2, the server either buffers seq=3 until seq=2 arrives, or rejects seq=3 and waits for the client to retransmit in order.
- **Single write path** — route all writes from a session through a single primary that serializes them before replication. Since the primary applies them in arrival order, and arrival order matches the client's issue order (TCP guarantees in-order delivery within a connection), monotonic writes are implicit. This is how single-leader databases (Postgres, MySQL) provide MW for free — writes go to one primary which applies them in order.
- **Write pipeline / queue per client** — for multi-primary systems, maintain a per-client write queue at the coordination layer. Each new write from a client is only forwarded to a replica after the previous write has been acknowledged. This serializes the client's writes at the cost of queuing latency (each write waits for the previous one to complete before the next is issued).
- **Causally consistent replication** — systems that implement causal consistency (e.g., COPS, Eiger, some Cassandra configurations) track causal dependencies and ensure that replicas apply writes in dependency order. This subsumes monotonic writes as a special case (the "dependency" for W2 is just W1 from the same client).

**Q15. What is the relationship between monotonic writes and last-write-wins (LWW) conflict resolution?**
A: They interact in a subtle and important way. Last-write-wins resolves concurrent writes by keeping the write with the later timestamp (or sequence number). This assumes that write ordering is correct — the "last" write in LWW is defined by ordering.

If monotonic writes is violated (writes from the same client are applied in different orders on different replicas), LWW produces different outcomes on different replicas: on Replica A, W2 comes after W1, so W2 wins. On Replica B, W1 comes after W2, so W1 wins. The replicas diverge even after LWW is applied. Monotonic writes is a *precondition* for LWW to produce a consistent final state across replicas. Without MW, LWW doesn't just pick the "wrong" winner — it picks different winners on different replicas, which is worse than either outcome.

This is one reason why systems relying on LWW also rely on vector clocks or per-client sequence numbers to enforce write ordering — the "last" in last-write-wins must be well-defined, and that requires write ordering (MW) to be enforced first.

## Section 5: Writes Follow Reads

**Q16. What is "writes follow reads" consistency, and what anomaly does it prevent?**
A: Writes Follow Reads (WFR) — also called "session causality" — guarantees: if a client reads value V in a session and then performs a write W, W will be applied to any replica only after that replica has also seen the version of V that the client read.

The anomaly without WFR:
1. Client reads a post P from Replica A (which has P at version 3).
2. Client writes a reply R to P. The write goes to Replica B.
3. Replica B hasn't yet received P at version 3 from Replica A (replication lag). Replica B has P at version 1.
4. Replica B applies reply R to P version 1 — the reply is now associated with a stale version of P.
5. When Replica A receives reply R, it applies it to P version 3. The two replicas are consistent for R but R was written against different context on each replica.
6. A reader on Replica B sees reply R referencing content that hasn't been fully replicated yet — or worse, the reply references data that its context on Replica B no longer makes sense.

This is the "commenting on something you haven't fully seen" anomaly. More critically in financial systems: a write that adjusts a balance based on a read of that balance must be applied to replicas that have already applied the read's version of the balance. Otherwise, the adjustment is applied to a stale value.

**Q17. How does WFR relate to the other three session models, and how does composing all four give causal consistency?**
A: The four models and their scope:
- **RYW** — "I see my own writes." Prevents writes from being invisible to their own author.
- **MR** — "I don't go back in time." Prevents reads from returning older values than previously seen.
- **MW** — "My writes are ordered." Prevents client's writes from being applied in wrong order.
- **WFR** — "My writes respect what I've read." Prevents writes from being applied to replicas that haven't seen the values the write was based on.

Composing all four gives causal consistency (for a single session). The key: WFR is what connects reads to subsequent writes, establishing causal dependency chains. Without WFR, the other three models prevent intra-session anomalies but don't prevent the write-on-stale-read anomaly. WFR is what makes the session semantics causally coherent — each write is visibly "after" the reads that informed it.

Causal consistency (global, across sessions) additionally requires: if Client 1 writes W1 and Client 2 reads W1 and then writes W2, then W2 is visible everywhere only after W1 is visible. This extends WFR across session boundaries — the "read" in WFR can be by a different client, not just the one doing the write.

## Section 6: Implementation in Real Systems

**Q18. How does MongoDB implement causal consistency sessions, and which of the four models does it provide?**
A: MongoDB's causal consistency sessions (introduced in MongoDB 3.6) implement all four session models — RYW, MR, MW, and WFR — through a mechanism called **operation time** and **cluster time**:

- **Operation time** — every read and write returns an `operationTime` timestamp (a logical timestamp from the cluster's oplog). The client tracks the highest `operationTime` it has seen in the session.
- **After cluster time** — every subsequent read carries the client's current `operationTime` as an `afterClusterTime` parameter. The replica serving the read checks: "has my oplog advanced past `afterClusterTime`?" If not, it waits until it has (or returns an error if the wait exceeds a timeout).

This provides:
- **RYW** — the client sends the `operationTime` of its own write; reads wait until that time is reached on the serving replica.
- **MR** — the client always tracks the *highest* `operationTime` seen; reads always advance this frontier.
- **MW** — writes are serialized through the primary, which applies them in order. The oplog captures this order; replicas apply in oplog order.
- **WFR** — the `afterClusterTime` on a write ensures the write is applied to replicas that are at least as up-to-date as the data the client read before writing.

The cost: every read may stall briefly waiting for the replica to advance past the client's `afterClusterTime`. Teams that don't need causal consistency can opt out per-session and get eventually consistent reads with no stalling.

**Q19. How does Cassandra's tunable consistency relate to session consistency models?**
A: Cassandra's consistency levels are quorum-based — they determine how many replicas must respond to a read or write. They are not inherently session consistency models, but they can be combined to achieve session guarantees:

- **Monotonic reads**: using `QUORUM` reads ensures that a majority of replicas respond, and the highest value among responses is returned. Since quorum always overlaps with any quorum write, a quorum read can never return a value older than the last quorum-committed write — giving a form of monotonic reads (you won't see an older commit).
- **RYW with `LOCAL_QUORUM`**: write with `LOCAL_QUORUM` (majority of local DC) and read with `LOCAL_QUORUM`. The overlap guarantees that at least one replica that acknowledged the write is also in the read quorum. That replica returns the written value. RYW is satisfied.
- **MW**: Cassandra does not natively enforce monotonic writes — if two writes from the same client race to different coordinators, they may be applied in different order. To enforce MW, clients must serialize their own writes (wait for W1 to be acknowledged before sending W2) rather than pipelining them.
- **Lightweight transactions (LWT)**: Cassandra's LWT (using `IF` conditions and Paxos under the hood) provides compare-and-set semantics — a write is applied only if the current value matches a condition. This gives a limited form of WFR for update operations (the write is conditioned on reading the current value) but is expensive (multiple Paxos rounds).

The practical Cassandra session consistency recipe: `LOCAL_QUORUM` reads and writes + client-side write serialization + application-layer sequence numbers for MW. This is operationally achievable but requires discipline.

**Q20. How does DynamoDB's `ConsistentRead` option relate to session consistency models?**
A: DynamoDB offers two read modes:

- **Eventually consistent reads (default)** — reads may return stale data; routed to any replica. Provides no session consistency guarantees — not RYW, not MR, not MW.
- **Strongly consistent reads (`ConsistentRead: true`)** — reads always return the most recent committed write; routed to the leader replica. Provides RYW (you always see the latest write, including your own) and MR (the leader's state only advances forward). Costs 2× the read capacity units of eventually consistent reads.

DynamoDB Transactions (`TransactWriteItems`, `TransactGetItems`) use a two-phase commit protocol across items and provide atomicity and isolation — not directly session consistency, but they enforce that related reads and writes are consistent with each other, approximating WFR for transactional operations.

For full session consistency with DynamoDB, teams combine:
- `ConsistentRead: true` for reads where RYW and MR are required.
- DAX (DynamoDB Accelerator) for read-through caching — a DAX write-through cache can provide RYW by serving reads from the cache (where the latest write is present) before it has propagated to all DynamoDB replicas.
- Application-level sequencing for MW.

**Q21. How do relational databases (PostgreSQL, MySQL) provide session consistency, and is it "for free"?**
A: Single-primary relational databases provide session consistency models largely for free as a consequence of their architecture:

- **RYW**: writes go to the single primary; reads from the primary always see the latest writes (same node). If you read from async replicas, RYW is not guaranteed — the replica may be seconds behind the primary.
- **MR**: the primary's state only advances forward. Reads from the primary are always monotonically forward-moving. Reads from async replicas can violate MR if the replica's lag varies between requests.
- **MW**: the primary serializes all writes in a single write-ahead log (WAL). Writes from the same client are applied in the order they arrive at the primary (TCP in-order delivery within a connection ensures arrival order = issue order). MW is implicit.
- **WFR**: within a transaction, reads and writes see a consistent snapshot (MVCC). A write within a transaction sees all reads from that transaction's snapshot, ensuring WFR within a transaction. Across transactions, WFR holds because the WAL serializes everything.

The catch: this "for free" property evaporates the moment you add read replicas. Async read replicas can be seconds behind the primary. A client that writes to the primary and then reads from a replica will not see RYW. This is why many applications use a "read-after-write" pattern: reads immediately after a write always go to the primary; later reads (after a sufficient delay or a replication-caught-up signal) go to replicas. PostgreSQL's `synchronous_commit` and `synchronous_standby_names` settings control how much replication lag is allowed before the write is acknowledged, which in turn controls the RYW guarantee strength.

## Section 7: Choosing the Right Model

**Q22. For a given feature, how do you decide which session consistency model you need?**
A: The decision tree follows the failure modes that are unacceptable for the feature:

**Need RYW if:**
- The user makes a write and immediately views the result (profile updates, settings changes, post submissions, order placements).
- A service writes a record and immediately reads it back to make a business decision.
- The UI shows the user their own submitted data on a confirmation or results page.

**Need MR if:**
- The user browses paginated content (pages 1, 2, 3 of search results — items shouldn't disappear between pages).
- A dashboard shows metrics that should never decrease unexpectedly.
- Any context where "going backward in time" would appear to the user as data deletion.

**Need MW if:**
- A client issues multiple writes that have ordering dependencies (set role to EDITOR, then to ADMIN — order matters).
- A client updates a sequence of records where later updates are semantically "after" earlier ones.
- An event log or audit trail where client events must appear in issue order.

**Need WFR if:**
- A client reads data and makes a write that is semantically contingent on what was read (a reply, a balance adjustment, a conditional update).
- You want the system to be causally consistent — writes should never be applied to replicas that haven't seen the data they were based on.

Most user-facing web applications need at minimum RYW and MR. Adding MW is important for multi-step workflows. WFR becomes important in financial systems, collaborative applications, and anywhere write correctness depends on the value that was read.

**Q23. What is the performance cost of each session model, and how do you reason about the trade-off?**
A: From cheapest to most expensive:

- **MW** — cheapest. Client-side write sequencing (don't send W2 until W1 is acknowledged) or single-leader routing. No additional read overhead. The cost is write latency (sequential rather than pipelined writes from a client) and slightly reduced write throughput per client.
- **MR** — moderate. Requires maintaining a read frontier token (small per-session storage) and checking it on every read (small per-request overhead). The cost spikes when replicas are consistently behind the frontier — reads either stall (adding latency equal to the replication lag) or redirect to the more up-to-date replica (adding a network hop).
- **RYW** — moderate to expensive depending on strategy. Sticky sessions are free at the session level but expensive for load balancing. Read frontier tokens (same mechanism as MR) add the same costs. Primary reads are expensive because they don't distribute read load across replicas.
- **WFR** — most expensive. Requires tracking causal dependencies across reads and writes. Each write must carry the causal context (a vector clock or equivalent) of all reads that preceded it. Replicas must check and potentially wait on causal dependencies before applying writes. This is why full causal consistency systems (COPS, Eiger) are rare in production — the overhead is significant at high throughput.

The practical recipe: implement RYW and MR together (they share the read frontier mechanism and the cost is roughly the same as implementing either alone). Add MW via client-side write sequencing (free). Add WFR selectively for specific high-correctness paths (financial transactions, conditional updates) using transactions or CAS operations rather than implementing global causal consistency.

## Section 8: Scenario / System Design Questions

**Q24. "A user updates their username. They're immediately redirected to their profile page which shows the old username. What went wrong and how do you fix it?"**
A: This is a classic RYW violation. The write went to the primary replica; the redirect triggered a read that was routed to an async replica which hadn't yet received the write.

Diagnosis: check the replication lag between primary and replicas at the time of the incident. Even a 100ms lag is enough to cause this if the redirect happens in under 100ms. Confirm by checking if the issue is consistent with read replica latency.

Fixes (in order of increasing cost):
1. **Read-after-write routing**: for profile reads immediately following a profile write, route the read to the primary. Implement this as a short-term "primary read" flag set in the session for 1–5 seconds after a write, after which the flag expires and reads return to replicas. Most load balancers and ORMs support this pattern.
2. **Replication token**: the write response includes the LSN of the write. The client sends this LSN with the redirect read request. The replica serving the read checks its own LSN and either serves the read (if it's caught up) or waits/redirects (if not).
3. **Optimistic UI (client-side caching)**: immediately after the write, the client-side application updates its local state (React state, Redux store) with the new username. The profile page reads from local state first. The actual server read confirms or corrects. This is the simplest fix with the best user experience — the user sees the updated value instantly without a server round-trip.
4. **Synchronous replication for user profile data**: make the write synchronously replicate to at least one replica before acknowledging. Any subsequent read from that replica (or any replica with `W + R > N`) will see the write. Higher write latency, guaranteed RYW.

**Q25. "A financial dashboard shows account balance dropping from $5,000 to $3,000 to $4,500 — but it should only go up or stay flat (no withdrawals were made). What consistency violation is this?"**
A: This is a **monotonic reads violation**. The balance is bouncing around because different reads are hitting replicas at different replication positions — some replicas are ahead of others, and the client is reading from progressively different replicas with different amounts of lag.

The sequence: replica A has balance $4,500 (latest); replica B has $3,000 (lagging 30s); replica C has $5,000 (most current).
- Read 1 → Replica C: $5,000
- Read 2 → Replica B: $3,000 (went back in time — MR violation)
- Read 3 → Replica A: $4,500 (moved forward again, but still behind C)

This looks like balance manipulation to the user. In a financial context it could also trigger incorrect alerts ("balance below threshold") that fire and resolve within the same monitoring window.

Fix: enforce monotonic reads for balance queries. Implementation: use a read frontier token. The first read returns `{balance: $5,000, token: LSN_100}`. The client stores token=LSN_100. The second read sends `afterToken: LSN_100`. Only replicas with LSN ≥ 100 are eligible to serve the read. Replica B (at LSN_80) waits until it catches up to LSN_100 before serving — the client waits an extra 30 seconds, or the request is redirected to a replica that's already at LSN_100.

Alternative for financial dashboards: always read from the primary for balance data. Stale balance reads in a financial context are almost always worse than slightly higher primary read latency.

**Q26. "Your event sourcing system processes commands in parallel from the same client. Occasionally, event 3 from a client is applied before event 2, corrupting the aggregate state. What consistency model is violated and how do you fix it?"**
A: This is a **monotonic writes violation**. The client is issuing events in a sequence (event 1, event 2, event 3), but the parallel processing pipeline doesn't preserve client-issue order. Event 3 arrives at the aggregate faster than event 2 (perhaps event 2 was retried due to a transient failure), and the aggregate applies [1, 3, 2] instead of [1, 2, 3].

Root cause: the events were issued in order but processed in parallel without enforcing ordering. Common in Kafka consumer-group setups where events from the same client end up in different partitions (different consumers process them independently with no ordering guarantee across partitions).

Fixes:
- **Partition by client/aggregate ID**: in Kafka, use the client ID or aggregate ID as the partition key. All events from the same client land in the same partition, which Kafka processes in strict FIFO order. Consumer group parallelism is across aggregates (different partition keys), not within a single aggregate's events.
- **Client-side sequence numbers + server-side ordering enforcement**: each event carries `clientId + seqNum`. The aggregate (or a command handler in front of it) buffers out-of-order events and applies them only in sequence. Event 3 with `seq=3` is buffered until `seq=2` arrives and is applied first.
- **Serialized write path per aggregate**: route all commands for a given aggregate through a single writer (actor model, or a distributed lock per aggregate). The writer serializes commands in arrival order. Since TCP preserves in-connection order, a single writer sees commands in client-issue order. Used in event sourcing frameworks like Axon, Eventuate.
- **Optimistic concurrency control**: each command carries the expected version of the aggregate (`expectedVersion: 2` means "apply this command only if the aggregate is currently at version 2"). If version 3 arrives and finds the aggregate at version 2 (event 2 not yet applied), it's rejected and the client retries after event 2 succeeds. Enforces ordering at the cost of retries.

**Q27. "A team argues that they don't need any session consistency guarantees because they use a single-leader database. Are they right?"**
A: Partially right, and dangerously incomplete. For reads from the primary, they are correct — a single-leader database provides RYW, MR, MW, and WFR for free when every read goes to the primary (same node that received all writes, in WAL order).

Where they're wrong:
- **Read replicas**: if any reads go to async replicas, all four guarantees can be violated. Async replica lag (even 100–500ms) is enough to cause RYW violations on page loads, MR violations on paginated results, and WFR violations on read-then-write patterns.
- **Connection pooling**: if the client uses a connection pool that distributes connections across multiple primary instances (for a setup with horizontal write scaling or during primary failover), MW can be violated — writes may arrive at the primary through different TCP connections, which the server sees as different clients and may interleave.
- **Failover**: during a leader failover (primary crashes, replica is promoted), the new primary may not have all writes from the old primary (async replication). RYW and MR can be violated for the window between the last replicated write and the failover — clients see data go backward during this window.
- **Multi-region**: if the "single leader" is in one region and a regional failover promotes a local replica, the new primary's state reflects the replication lag at the time of failover. All four session guarantees can be violated for writes that hadn't replicated yet.

The correct statement: a single-leader database provides session consistency for reads from the primary. It is the responsibility of the team to ensure reads for session-consistency-sensitive paths actually go to the primary and not to replicas or stale promoted replicas.

## Quick Reference: Session Consistency Models

| Model | Guarantee | Anomaly Prevented | Implementation Mechanism |
|--- |--- |--- |--- |
| Read-Your-Writes (RYW) | A client sees its own writes in subsequent reads | "My update disappeared" | Sticky sessions; read-after-write routing; replication token |
| Monotonic Reads (MR) | A client never reads older data than it previously read | "Values going backward in time" | Read frontier token; quorum reads; sticky sessions |
| Monotonic Writes (MW) | A client's writes are applied in issue order everywhere | "Write 2 applied before Write 1" | Client-side sequencing; partition-by-key; single writer per aggregate |
| Writes Follow Reads (WFR) | A write is applied only after replicas have seen the data it was based on | "Reply on stale post; update on stale balance" | Causal context propagation; transactions; CAS operations |

---

## Composition and Coverage

```
RYW alone       → safe for: profile updates, settings, order confirmations
MR alone        → safe for: read-only dashboards, paginated browsing
MW alone        → safe for: event logs, sequential state machines
RYW + MR        → safe for: most interactive user-facing applications
RYW + MR + MW   → safe for: multi-step workflows, command processors
All four (PRAM) → safe for: financial adjustments, collaborative tools, causal event chains
Causal (global) → extends all four across sessions: messaging, social graphs, distributed counters
Linearizable    → all of the above + global ordering: distributed locks, financial ledgers
```

---

**Tip for the interview:** At 5 YOE level, these models are not asked as definitions — interviewers use them to probe whether you can diagnose a consistency bug and prescribe the right fix. The most effective format is: name the anomaly ("this is a monotonic reads violation"), explain the mechanism that caused it ("the load balancer routed two reads from the same session to replicas at different replication positions"), and prescribe the fix with its trade-off ("enforce a read frontier token — reads stall for up to the replication lag, which is typically 50–200ms at our scale"). Having a war story helps: "we saw this exact MR violation in our analytics dashboard — users thought balance data was being corrupted but it was just replica routing — here's how we fixed it." That combination of name + mechanism + fix + trade-off is what separates a 5 YOE answer from a junior-level definition recitation.
