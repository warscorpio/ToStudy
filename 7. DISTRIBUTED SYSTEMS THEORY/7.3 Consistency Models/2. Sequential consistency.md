# Sequential Consistency — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is sequential consistency, and who defined it?**
A: Sequential consistency was defined by Leslie Lamport in 1979 in his paper "How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs." His definition: *"the result of any execution is the same as if the operations of all the processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program."*

Two conditions must hold simultaneously:
1. **Total order**: there exists a single global sequential ordering of all operations across all processes that is consistent with every observed result.
2. **Program order preservation**: within that global order, each process's operations appear in the same order that process issued them.

Sequential consistency says nothing about *which* total order is chosen — only that *some* valid total order must exist that explains all observations.

**Q2. What does sequential consistency guarantee in plain terms?**
A: It guarantees that all processes in the system agree on the same history of operations — they all see the same interleaving of reads and writes, in an order that respects each process's local program order. If Process A writes `x = 1` then `y = 2`, no other process can observe `y = 2` before `x = 1` in the global order. However, the global order does not need to match wall-clock time — a write that happened "earlier" in real time may appear "later" in the global order, as long as program order within each process is preserved.

**Q3. What is the intuition behind the "some sequential order" phrasing — why does "some" matter?**
A: "Some" means there does not have to be a unique, predetermined global order — only that at least one valid sequential ordering exists that is consistent with all observations. In a system with two processes running concurrently, many interleavings of their operations are possible. Sequential consistency requires that the actual execution's observable results match *at least one* of those valid interleavings. This is weaker than demanding a specific execution order — it allows the implementation significant freedom in scheduling, as long as the results are explainable by *some* valid sequential execution.

**Q4. What are the two properties that must hold simultaneously for sequential consistency, and what breaks if either is violated?**
A:
- **Property 1 — Total order agreement**: all processes must observe operations in the same global order. If Process B sees `x = 1` before `y = 1`, then Process C must also see `x = 1` before `y = 1`. A violation: B sees `x=1` then `y=1`; C sees `y=1` then `x=1`. No single sequential order explains both observations — sequential consistency is violated.
- **Property 2 — Program order preservation**: the global order must respect each process's own program order. If Process A's code writes `x = 1` then reads `y`, those two operations must appear in that order in the global sequence. A violation: the global order shows A's read of `y` before A's write of `x=1` — impossible to reconcile with A's program, so sequential consistency is violated.

Breaking Property 1 means different processes have inconsistent views of history. Breaking Property 2 means a process sees its own operations reordered — which breaks standard programming assumptions.

**Q5. What is the register model and why is it the standard formal framing for sequential consistency?**
A: Sequential consistency is most precisely defined in terms of a **register** — an abstract memory location supporting two operations: `write(value)` and `read() → value`. A register is the atomic unit of shared state. The formal question is: given a history of reads and writes to registers across multiple processes, does there exist a valid sequential ordering that explains all read return values?

The register model is useful because it strips away everything domain-specific (transactions, network protocols, application logic) and focuses on the fundamental question: when a process reads a value, which write does it see, and is that choice consistent with a global sequential history? Most formal proofs about consistency models — and their separations — are stated in terms of registers.

## Section 2: What Sequential Consistency Does and Doesn't Guarantee

**Q6. Does sequential consistency guarantee that reads return the most recently written value?**
A: No — and this is one of the most important distinctions. Sequential consistency does not require operations to respect real-time order. A read can return a value from a write that occurred much earlier in wall-clock time, as long as the global sequential order is consistent and respects program order. Example: Process A writes `x = 1` at time T=1. Process B reads `x` at time T=100. Sequentially consistent behavior allows B to read `x = 0` (the initial value) if the sequential ordering places B's read before A's write — even though in real time B's read happened 99 units after A's write.

This is what separates sequential consistency from linearizability: linearizability additionally requires that the sequential order respects real-time — if A's write completed before B's read began, B must see A's write.

**Q7. Does sequential consistency guarantee that all processes agree on the order of operations across different processes?**
A: Yes — this is the core of the total order requirement. If Process B observes operation X before operation Y (where X and Y are from different processes), then every other process in the system must also observe X before Y. This is what distinguishes sequential consistency from causal consistency: under causal consistency, different processes can observe concurrent operations in different orders — only causally related operations must be ordered consistently. Sequential consistency is strictly stronger: *all* operations have a global agreed-upon order, not just causally related ones.

**Q8. What is the "global clock" intuition for sequential consistency?**
A: A helpful (though imprecise) intuition: imagine all operations across all processes are printed on index cards, then someone shuffles them into a single deck subject to two constraints — (1) within each process's subset of cards, the original program order is preserved; (2) the shuffled deck explains every read's return value (each read sees the value from the most recent write to that variable in the deck above it). If such a shuffle exists, the execution is sequentially consistent. The deck represents the "some sequential order" — it need not match wall-clock time, only program order and read-write coherence.

**Q9. Is sequential consistency compositional — does combining two sequentially consistent systems yield a sequentially consistent system?**
A: No — sequential consistency is famously **not compositional**. Two systems that are each individually sequentially consistent can, when composed, produce a combined behavior that is not sequentially consistent. This is a significant practical limitation: you cannot build a large SC system by assembling SC components without additional coordination between them. The global sequential order that each subsystem satisfies independently may not be reconcilable into a single global order when the subsystems interact.

Linearizability, by contrast, *is* compositional — independently linearizable objects compose into a linearizable system. This composability is one of the primary reasons linearizability is often preferred over sequential consistency in formal distributed systems work, despite being a stronger (harder to implement) property.

**Q10. What is "coherence" (or "cache coherence"), and how does it relate to sequential consistency?**
A: Coherence (or per-location sequential consistency) is a weaker property than sequential consistency: it requires that all writes to a *single* memory location appear in the same order to all processors — but makes no cross-location ordering guarantee. In a sequentially consistent system, *all* operations across *all* memory locations have a global total order. In a coherent-but-not-SC system, each memory location has its own independent total order of writes, but these per-location orders need not be consistent with each other.

Example: cache coherence is satisfied if all CPUs agree on the order in which `x` was written. But if CPU A's writes to `x` and `y` can be observed in different orders by CPU B and CPU C, coherence is satisfied while sequential consistency is violated. Modern CPU cache protocols (MESI, MOESI) guarantee coherence, not sequential consistency — a subtle but critical distinction for concurrent programming.

## Section 3: Sequential Consistency vs. Other Consistency Models

**Q11. What is linearizability, and how does it differ from sequential consistency?**
A: Linearizability (also called "atomic consistency" or "strong consistency") adds one requirement on top of sequential consistency: the global sequential order must be **consistent with real-time order**. Specifically: if operation A completes before operation B begins (no overlap in wall-clock time), then A must appear before B in the global sequential order.

Sequential consistency allows a completed operation to appear *after* a later-starting operation in the sequential order, as long as program order within each process is preserved. Linearizability does not — once an operation is complete, any operation that starts after it must see its effect.

The practical difference: linearizability is an "external consistency" guarantee that gives the system a behavior indistinguishable from a single centralized server. Sequential consistency is more permissive — it allows time-traveling writes that no external observer would expect from a centralized system, but that still form a consistent internal history.

**Q12. What is serializability, and how does it differ from sequential consistency?**
A: Serializability is a property of **transactions** (groups of operations), not individual operations. A history of transactions is serializable if the result is equivalent to some serial execution of those transactions (where each transaction runs to completion before the next begins). Sequential consistency applies to individual reads and writes.

The conceptual relationship:
- **Serializability**: the multi-operation analog of sequential consistency — transactions are the unit, not individual reads/writes. Two transactions can each be internally correct while their interleaving is correct only if some serial ordering exists.
- **Sequential consistency**: individual operations are the unit. Each read/write appears atomically in the global order.

**Strict serializability** = serializability + linearizability. It is the strongest common guarantee: transactions execute as if in a serial order that respects real-time. This is what most people informally mean when they say a system is "strongly consistent" — it's the guarantee provided by systems like Google Spanner.

**Q13. What is causal consistency, and how does it compare to sequential consistency?**
A: Causal consistency requires that causally related operations be seen by all processes in causal order — if write A happened before write B (A causally precedes B), then every process that sees B must also have seen A. Operations that are causally independent (concurrent, with no causal relationship) may be seen in different orders by different processes.

Sequential consistency is **strictly stronger**: it requires all operations (whether causally related or not) to appear in the same global total order for all processes. Causal consistency allows different processes to observe concurrent operations in different orders — sequential consistency does not.

The trade-off: causal consistency is achievable under network partitions and with low latency (vector clocks track causality without coordination). Sequential consistency requires coordination to agree on a total order even for causally independent operations — more expensive, not achievable under partition with full availability.

**Q14. What is the consistency model hierarchy from weakest to strongest?**
A: From weakest (most available, least consistent) to strongest (most consistent, least available):

1. **Eventual consistency**: all replicas converge to the same value eventually; no ordering guarantees on how or when.
2. **Causal consistency**: causally related operations are ordered; concurrent operations may be observed in different orders.
3. **PRAM (Pipelined RAM) consistency**: each process's writes are observed in program order by all other processes; different processes' writes may be observed in different orders.
4. **Sequential consistency**: all operations have a global agreed-upon total order consistent with each process's program order; real-time ordering not required.
5. **Linearizability**: sequential consistency + real-time ordering (completed operations appear before later-starting operations in the global order).
6. **Strict serializability**: linearizability for transactions (groups of operations).

Each level adds a constraint, making the model easier to reason about but harder and more expensive to implement.

**Q15. What does "external consistency" mean and why is it sometimes used instead of "linearizability"?**
A: External consistency (a term used by Google Spanner's team) is functionally equivalent to strict serializability: transactions appear to execute in a serial order consistent with real-time. It means the system's behavior is indistinguishable from a single server executing transactions one at a time, with the execution order matching wall-clock time. Sequential consistency, by contrast, is an "internal consistency" — the history is self-consistent according to program order, but may not match what an external observer (looking at wall-clock time) would expect. Spanner uses TrueTime to bound clock uncertainty and enforce external consistency across globally distributed data centers — a remarkable engineering achievement that explicitly requires going beyond sequential consistency.

## Section 4: Sequential Consistency in Hardware (CPUs)

**Q16. Are modern CPUs sequentially consistent by default?**
A: No — modern CPUs from all major architectures (x86, ARM, RISC-V, POWER) use **relaxed memory models** that are weaker than sequential consistency. Sequential consistency requires that the global order of all memory operations match the program order of each CPU. Modern CPUs break this in several ways for performance:
- **Store buffers**: writes are placed in a local store buffer and may not be immediately visible to other CPUs. A CPU may read a value it wrote from its own store buffer before other CPUs see it — violating the "all CPUs see the same order" requirement.
- **Load/store reordering**: CPUs speculatively reorder loads and stores when the reordering is invisible to the local program (within a single thread) but may be visible to other CPUs via shared memory.
- **Write combining**: multiple writes to adjacent addresses may be combined and issued to the cache in a different order than programmed.

**Q17. How does x86 deviate from sequential consistency specifically?**
A: x86 uses the **Total Store Order (TSO)** memory model — a relaxation of SC in one specific way: stores (writes) from one CPU may be delayed in a store buffer before becoming visible to other CPUs. Loads (reads) by the same CPU can be satisfied from this store buffer without waiting for the store to propagate. The result:
- Stores are not immediately visible to other CPUs — effectively, each CPU has a FIFO store buffer that buffers its writes.
- A CPU always sees its own stores immediately (reads bypass the store buffer to the value just written).
- Loads are not reordered with other loads; stores are not reordered with other stores.

The specific SC violation x86 allows: a **store followed by a load** to a *different* address can appear reordered. Process A writes `x = 1`, then reads `y`; Process B writes `y = 1`, then reads `x`. Under SC, it's impossible for both to read 0 (one write must come first). Under TSO, both can read 0 because each CPU's write is in its store buffer and hasn't propagated when the other CPU reads.

**Q18. What are memory barriers (fences) and how do they restore sequential consistency locally?**
A: A memory barrier (or fence) is an instruction that prevents the CPU from reordering memory operations across it. It forces the store buffer to flush before proceeding and ensures subsequent loads see all preceding stores. Types:
- **Store fence (SFENCE on x86)**: all preceding stores are made visible to other CPUs before any subsequent store is issued.
- **Load fence (LFENCE on x86)**: all preceding loads complete before any subsequent load begins.
- **Full fence (MFENCE on x86, `dmb sy` on ARM)**: both stores and loads cannot be reordered across the fence. Restores SC-level ordering at that point.
- **Atomic read-modify-write instructions** (e.g., `LOCK XCHG`, `CAS`): implicitly include a full fence, which is why using atomics in concurrent code provides SC-level guarantees around those operations.

High-level languages emit barriers implicitly: Java's `volatile` variables insert barriers; C++'s `std::atomic` with `memory_order_seq_cst` uses full fences. The programmer rarely writes barrier instructions directly — they use language-level primitives that compile to the appropriate barriers.

**Q19. Why do classic mutual exclusion algorithms like Peterson's fail on modern hardware without barriers?**
A: Peterson's algorithm for mutual exclusion between two threads assumes sequential consistency — specifically, that when Thread 1 writes its "interested" flag and then reads Thread 2's flag, the read reflects the value *after* the write has become visible to Thread 2. Under TSO (x86's actual memory model), Thread 1's write may still be in its store buffer when it reads Thread 2's flag. Both threads can simultaneously see the other thread as "not interested" and both enter the critical section — mutual exclusion is violated.

This is a celebrated example of sequential consistency assumptions breaking real programs. Fix: insert a full memory barrier (`MFENCE`) between the write and the read in each thread. The barrier flushes the store buffer before the read, restoring the SC assumption that Peterson's algorithm depends on.

## Section 5: Sequential Consistency in Distributed Systems

**Q20. Is sequential consistency achievable in a distributed system under network partitions?**
A: No — the CAP theorem (Brewer, formalized by Gilbert and Lynch) proves that no distributed system can simultaneously guarantee Consistency, Availability, and Partition tolerance. Sequential consistency is a consistency property that, like linearizability, requires all nodes to agree on a global operation order. During a network partition, nodes that can't communicate can't agree on a global order without one side blocking (sacrificing availability). Sequential consistency is therefore partition-intolerant in its full form: you can have SC + partition tolerance only if you sacrifice availability (nodes on the minority side of a partition stop accepting operations).

**Q21. What distributed systems provide sequential consistency, and how do they implement it?**
A: Sequential consistency is implemented by forcing all operations through a **total order broadcast** — a mechanism that delivers messages to all nodes in the same order. Two common implementations:

- **Single leader / sequencer**: all writes go through a single leader node that assigns a sequence number to each operation and broadcasts them in order. All replicas apply operations in the numbered sequence. Reads from any replica are sequentially consistent if they use the applied sequence position. Apache ZooKeeper uses this model: all writes go through the leader, and ZooKeeper guarantees sequential consistency for clients (all updates from a client appear in the order issued, and all clients see the same order of updates). ZooKeeper does *not* guarantee linearizability — reads from a follower may be stale.

- **Consensus-based total order (Raft/Paxos)**: a Raft leader serializes all writes into the log. All committed log entries are applied in index order by all replicas. This achieves sequential consistency (same total order, program order preserved per client) and, with linearizable reads (reading from the current leader with a lease or quorum read), also achieves linearizability.

**Q22. What does ZooKeeper's consistency guarantee precisely mean, and where does it fall on the consistency spectrum?**
A: ZooKeeper provides **sequential consistency** for all write operations: writes are totally ordered by the ZAB (ZooKeeper Atomic Broadcast) protocol, and all clients observe writes in this total order. Every client also sees its own writes before any subsequent reads — a read-your-own-writes guarantee.

However, ZooKeeper does **not** provide linearizability for reads: a read from a follower node may return stale data (an older state of the data before the latest committed write has been applied to that follower). To get linearizable reads, clients must call `sync()` before a read — this ensures the follower has applied all writes up to the current leader's state before serving the read. Without `sync()`, reads are "sequentially consistent within a session" but not linearizable against external real-time ordering.

This is a precise and important distinction: ZooKeeper is the canonical example of a system that is sequentially consistent but not linearizable.

**Q23. How does Kafka achieve sequential consistency within a partition?**
A: Kafka partitions provide sequential consistency through the log abstraction: all producers writing to the same partition go through the partition leader, which appends records in the order received and assigns monotonically increasing offsets. All consumers reading from the partition see records in exactly the same offset order — the total order is the offset sequence. Program order is preserved because a producer's records are appended in the order produced.

This is sequential consistency within a partition: there is a global total order (the offset sequence), and each producer's records appear in that order in the same sequence they were produced. Across partitions, there is no ordering guarantee — Kafka provides sequential consistency only within a partition.

**Q24. What is "total order broadcast" and why is it equivalent to sequential consistency for a replicated state machine?**
A: Total order broadcast (also called atomic broadcast) is a communication primitive that delivers a set of messages to all nodes such that: (1) every non-faulty node delivers every message, and (2) all nodes deliver messages in the same order. If you implement a replicated state machine where all nodes apply the same sequence of operations (delivered via total order broadcast) to the same initial state, all nodes end up in the same state after applying the same prefix of operations — they have the same view of history, satisfying sequential consistency's total order requirement.

The equivalence: consensus (Paxos/Raft) → total order broadcast → sequentially consistent replicated state machine. Consensus protocols solve the coordination problem of agreeing on a total order; total order broadcast is the communication layer that enforces it; sequential consistency is the observable property that results.

## Section 6: Failure Modes & Violations

**Q25. What does a sequential consistency violation look like concretely? Give an example.**
A: Classic example — two processes, two variables initially zero:

```
Process A:        Process B:
write(x, 1)       write(y, 1)
r1 = read(y)      r2 = read(x)
```

Under sequential consistency, there are three possible outcomes:
- A's write then B's write: `r1 = 1`, `r2 = 1`.
- B's write then A's write: `r1 = 1`, `r2 = 1` (same result here).
- A's write, A's read, B's write, B's read: `r1 = 0`, `r2 = 1`.
- B's write, B's read, A's write, A's read: `r1 = 1`, `r2 = 0`.

The outcome `r1 = 0` AND `r2 = 0` is **not** possible under sequential consistency. If A reads `y = 0`, then B's write of `y = 1` must come after A's read in the global order. Since B's read of `x` comes after B's write of `y` in B's program order, and A's write of `x = 1` comes before A's read of `y` in A's program order — A's write of `x` must have occurred before B's read of `x` in the global order. B must read `x = 1`. Contradiction. Under async replication without coordination, `r1 = 0, r2 = 0` is possible — this is the SC violation.

**Q26. What is the "message reordering" SC violation in distributed systems?**
A: In an eventually consistent distributed system, two writes to different keys can be observed in different orders by different nodes. Example: node A writes `user_status = "online"` at T=1, then `last_seen = now()` at T=2. Due to async replication, node B may apply `last_seen` before `user_status`. A reader on node B sees `last_seen` updated but `user_status` still "offline" — a causally inconsistent, sequentially inconsistent state. Both writes are from the same process (program order must be preserved), but the replica applied them out of order. This is an SC violation: no valid sequential order exists where `last_seen` is updated before `user_status` and `user_status` was written before `last_seen` in program order.

**Q27. How does the "stale read after write" failure mode relate to sequential consistency?**
A: A stale read after write is a read-your-own-writes violation — a process writes a value and then reads it back, receiving the old value. Under sequential consistency, this cannot happen: the write must appear before the subsequent read in the global sequential order (program order preservation), so the read must see the write's value. A system that allows stale read after write is definitionally not sequentially consistent from that process's perspective. Common cause in distributed systems: write goes to primary, read is routed to a lagging replica before the write has propagated. This violates sequential consistency because no valid sequential ordering can place the read (which returned old value) after the write (which wrote the new value) while respecting program order.

**Q28. What is the "anomalous read" under sequential consistency vs. linearizability?**
A: Suppose at wall-clock time T=1, Process A writes `x = 1` and the write completes. At T=2, Process B issues a read of `x` — it started after A's write completed. Under **linearizability**, B must read `x = 1` — the completed write must appear before B's read in the real-time order. Under **sequential consistency**, B can legally read `x = 0` — the global sequential order could place B's read before A's write (even though in real time, the read started after the write completed), as long as B's program order is preserved. From B's perspective, this looks like a "time-traveling" write — B read `x` before the write existed in the logical history, even though it happened after in the physical world.

This anomaly is invisible within a single process (a process always sees its own writes) but observable by external clients comparing timestamps or expecting real-time ordering. It's why linearizability is required for "single-copy semantics" (the system behaves as if there's one server), while sequential consistency allows this subtle deviation.

## Section 7: Trade-offs & Decision-Making

**Q29. Why would you choose sequential consistency over linearizability?**
A: Sequential consistency is cheaper to implement than linearizability because it does not require synchronized real-time clocks or coordination to establish real-time ordering — it only requires total order agreement and program order preservation. In practice:
- **Performance**: SC can be achieved with a simple sequencer or leader-based total order broadcast. Linearizable reads additionally require a leader-read or quorum-read on every operation (to confirm no newer write exists). This adds latency to reads that SC doesn't require.
- **Cross-region**: SC can be provided by routing all writes through a primary region and applying them in order on replicas. Linearizable reads from replicas require round-trips to the primary. SC reads from replicas only need to reflect a consistent order — not necessarily the most current value.
- **Sufficient for many use cases**: distributed coordination services (ZooKeeper), distributed queues (Kafka partitions), and ordered event logs only need a consistent global order — they don't need the real-time guarantee. SC is the right fit.

**Q30. Why would you choose linearizability over sequential consistency?**
A: Linearizability is required when external clients (outside the system) must observe behavior consistent with wall-clock time — when "what happened when" is an observable and correct-by-specification property:
- **Distributed locks**: a lock must be held by exactly one holder at any real-time moment. If the lock grant is sequentially consistent but not linearizable, a client that was granted a lock after another client released it (in real time) might observe the grant appearing before the release in the SC order — breaking the mutual exclusion guarantee.
- **Unique ID generation**: IDs assigned to events must reflect a real-time ordering if IDs are expected to be monotonically increasing with respect to actual event time.
- **Leader election**: only one node should be leader at any real-time instant. SC doesn't guarantee this — linearizability does.
- **External system integration**: when a distributed system integrates with external systems (humans, physical sensors, other organizations), real-time ordering matters. External observers can compare their wall clocks to system timestamps; SC allows invisible time-travel that linearizability prohibits.

**Q31. What is the performance cost of sequential consistency in a distributed system, and what optimization techniques exist?**
A: The core cost: all operations must be serialized through a total order mechanism (leader, sequencer, or consensus). This creates a throughput ceiling (the sequencer is the bottleneck) and adds latency (every operation waits for sequencing before completing).

Optimization techniques:
- **Pipelining**: the sequencer assigns sequence numbers and broadcasts in a pipeline — operations can be in flight simultaneously without waiting for each to fully complete before assigning the next number.
- **Batching**: group multiple operations into a single sequencing round (one consensus round for a batch of writes). Amortizes the per-operation consensus overhead.
- **Read optimization (not linearizable)**: reads don't need to go through the sequencer if you only need SC (not linearizability). A replica that applies writes in sequence-order can serve reads at any time — the read returns a sequentially consistent (possibly stale) value. This avoids adding reads to the sequencer's bottleneck.
- **Partitioning**: maintain independent sequencers per partition or shard. Within a partition, operations are sequentially consistent. Across partitions, no global order exists — acceptable if the application doesn't need cross-partition ordering.

**Q32. When is sequential consistency the wrong consistency model to claim?**
A: Sequential consistency is overclaimed and underclaimed:
- **Overclaimed**: a system says it provides SC but actually only provides causal consistency or per-key ordering (coherence). This matters when applications assume that writing to key X and then key Y means all observers see both changes in that order — causal consistency only guarantees this if the writes are causally related through a single client.
- **Underclaimed**: a system says it provides "eventual consistency" but actually provides SC. Teams build complex application-level ordering workarounds for a problem the storage layer has already solved.
- **Wrong model**: sequential consistency is the wrong choice when you need real-time external consistency (use linearizability), when you need transaction atomicity across multiple operations (use serializability or strict serializability), or when you need to operate under network partitions with full availability (use causal consistency or eventual consistency).

## Section 8: Scenario / System Design Style Questions

**Q33. "Explain why `r1 = 0, r2 = 0` is impossible under sequential consistency in the two-process example, but possible in a real database with async replication."**
A: Under sequential consistency, a valid sequential order must exist. If `r1 = 0` (A reads `y` before B writes `y`), then in the global order A's read of `y` precedes B's write of `y`. Since A's write of `x` precedes A's read of `y` (program order), A's write of `x = 1` also precedes B's write of `y`. Now B's read of `x` comes after B's write of `y` (B's program order), which comes after A's write of `x = 1` in the global order. So B's read of `x` must see `x = 1`. Contradiction with `r2 = 0`. No valid sequential order exists — hence SC prohibits this outcome.

In a database with async replication: writes to `x` and `y` go to different shards or replicas. A writes `x = 1` to shard X. B writes `y = 1` to shard Y. A reads `y` from shard Y before B's write has propagated — reads 0. B reads `x` from shard X before A's write has propagated — reads 0. Each shard independently processes its write, with no coordination ensuring A's write to shard X is visible before B reads from it, and vice versa. The two shards have no shared sequencing — each is an independent async replica. The result `r1 = 0, r2 = 0` is easily produced. To prevent it, you'd need a total order coordinator across both shards — exactly what SC requires and what async replication does not provide.

**Q34. "A distributed key-value store routes all writes through a single leader and replicates asynchronously to followers. Followers serve reads. Is this sequentially consistent?"**
A: Not in general. The leader assigns a total order to all writes (commits them to the log in order) — this satisfies the total order requirement. The leader also respects each client's program order (processes client writes in the order received per session). So far, SC conditions are met for writes.

The problem is reads from followers. If different followers are at different positions in the replication log, two clients reading from two different followers may observe different states — one client reads a more recent write that the other client's follower hasn't applied yet. If Client A writes `x = 1` (replicated to Follower 1 but not Follower 2) and Client B reads from Follower 1 (sees `x = 1`) then reads from Follower 2 (sees `x = 0`), Client B has observed values in an order inconsistent with any single sequential history — a violation.

For sequential consistency: all clients must read from replicas at the same applied log position (or the primary). One correct approach: route all reads from the same client session to the same follower (session pinning) — this ensures a single client's reads are monotonically non-decreasing in the log position. But different clients may still have different views. True system-wide SC requires either all reads go to the leader or all replicas apply writes synchronously before serving reads.

**Q35. "A candidate says ZooKeeper is linearizable. How do you respond?"**
A: Correct them precisely. ZooKeeper provides **sequential consistency**, not linearizability, for its default behavior. The distinction:
- **Writes**: ZooKeeper writes are linearizable — all writes go through the Zab leader, are totally ordered, and once a write is committed, all subsequent reads (system-wide) will see it. ZooKeeper guarantees write linearizability.
- **Reads**: ZooKeeper reads are *not* linearizable by default. A read from any ZooKeeper server (leader or follower) returns the server's local state, which may be behind the latest committed write if that server hasn't applied the latest log entries yet. Two clients reading from two different followers may see different states — not linearizable.
- **The `sync()` call**: invoking `sync()` before a read flushes the server's pending log and ensures the subsequent read reflects all prior committed writes — providing linearizable read semantics. Without `sync()`, reads are sequentially consistent within a session (you always see your own writes and see writes in order) but not linearizable against the global real-time ordering.

The ZooKeeper documentation explicitly says it provides "sequential consistency" and notes that to get linearizable reads, clients must use `sync()`. This is a well-known nuance that many engineers get wrong.

**Q36. "Your team is building a distributed counter used to assign unique sequential IDs (e.g., order numbers). What consistency model do you need and why?"**
A: You need **linearizability**, not merely sequential consistency. Here's why the distinction matters:

The requirement: every call to `generate_id()` must return a value strictly greater than all previously returned values, and the returned value must reflect the real-time order of calls — if one call completes before another begins, the first must get a lower ID.

Sequential consistency is insufficient: it allows the global order to deviate from real-time. Two callers could observe their ID assignments in a "globally consistent" order that doesn't match wall-clock time — Caller A finishes and receives ID #42 at T=1, Caller B starts at T=2 and receives ID #41. SC permits this (the SC order could be B then A), but it violates the requirement that IDs increase with real-time.

Implementation under linearizability: route all `generate_id()` calls through a single leader (or use a consensus-based counter that is linearizable by construction). The leader atomically increments and returns the counter; each call is serialized in real-time order. A sequencer service backed by a linearizable store (etcd, ZooKeeper with `sync()`, Redis with WAIT) is the standard implementation.

**Q37. "Why can two separately sequentially consistent databases, when used together by the same application, produce non-sequentially-consistent behavior?"**
A: Because sequential consistency is not compositional. Each database independently maintains a total order of operations consistent with each client's program order — the SC invariant holds within each system. But there is no shared total order *across* the two systems. The application's operation history spans both databases, and no single sequential order may exist that is consistent with all observations across both systems simultaneously.

Concrete example: the application writes `x = 1` to Database 1, then writes `y = 1` to Database 2. Both databases are individually SC. Another thread reads `y` from Database 2 (reads 1), then reads `x` from Database 1 (reads 0 — the write hasn't propagated yet in Database 1's internal SC order). In the combined system, the reader sees `y = 1` but `x = 0` even though `x` was written before `y` in program order. No global sequential order consistent with this observation and the write order exists. The composed system is not sequentially consistent.

Fix: introduce a shared coordinator (a single sequencer both databases go through) that establishes a total order across both — but this collapses two independent SC systems into one coordinated one, eliminating the separation that made them independent.

**Q38. "How does Raft achieve sequential consistency, and under what conditions does it also achieve linearizability?"**
A: Raft achieves sequential consistency through the log: all writes are committed to the Raft log in a leader-assigned total order, and all replicas apply log entries in the same order. A client's writes within a session are ordered by the log index, preserving program order. Any follower serving reads from its applied log state provides sequentially consistent reads — the same total order, the same program order per client.

Raft achieves **linearizability for reads** only with additional mechanisms:
- **Leader reads with lease**: the leader holds a lease guaranteeing no other leader exists. It serves reads from its in-memory state without a quorum round-trip. The lease must be refreshed before expiry; if it expires, the leader must check with a quorum before serving reads.
- **Quorum reads**: the leader sends a no-op round-trip to a quorum to confirm it is still the current leader before serving the read. This confirms no newer writes exist on another leader and that the leader's applied state is current.
- **Read index**: the leader records the current commit index at the time of the read request, waits until the follower has applied up to that index, then serves the read. Provides linearizable reads from followers.

Without these mechanisms, reads from Raft followers may be stale (sequentially consistent but not linearizable) — they see a consistent history but potentially not the most recently committed values.

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                              |
|---                            |---                                                                                                               |
| Sequential consistency        | All operations appear in a global total order consistent with each process's program order; real-time not required|
| Program order                 | The order in which a single process issues operations; must be preserved in the global SC order                  |
| Total order                   | A single agreed-upon sequence of all operations across all processes; every pair of ops is ordered               |
| Linearizability               | SC + real-time: if op A completes before op B starts, A precedes B in the global order                          |
| Serializability               | Transactions execute as if in some serial order; individual ops within transactions may interleave               |
| Strict serializability        | Serializability + real-time ordering; the strongest common guarantee; "external consistency"                     |
| Causal consistency            | Causally related ops ordered consistently; concurrent ops may appear in different orders on different nodes      |
| Coherence (cache coherence)   | Per-location total order: all nodes agree on write order for each individual variable; weaker than SC            |
| Total store order (TSO)       | x86's memory model; stores buffered locally; weaker than SC; allows store-then-load reordering                  |
| Memory barrier / fence        | CPU instruction forcing store buffer flush; restores SC-level ordering at that point in the instruction stream  |
| Total order broadcast         | Communication primitive delivering messages to all nodes in the same order; equivalent to SC for replicated SM  |
| Non-compositionality          | Two SC systems composed may not be SC; no shared total order exists across independent SC systems               |
| ZAB (ZooKeeper Atomic Broadcast)| Total order broadcast protocol underlying ZooKeeper; provides SC for writes, not linearizable reads by default|
| Read-your-own-writes          | A process always sees its own writes in subsequent reads; guaranteed by SC, not by eventual/causal consistency  |
| Monotonic reads               | A process never reads an older value after reading a newer one; guaranteed by SC                                 |
| `sync()` in ZooKeeper         | Forces the follower to apply all pending log entries before serving a read; upgrades SC reads to linearizable    |
| Sequencer / leader            | A single node assigning total order to all ops; the implementation mechanism for SC in distributed systems      |
| Relaxed memory model          | CPU or system model weaker than SC; allows reordering for performance; requires explicit barriers for SC ops    |

**Tip for the interview:** Sequential consistency is one of the most frequently confused concepts in distributed systems — candidates often conflate it with linearizability. The two distinctions that matter most: (1) SC does not require real-time ordering (linearizability does), and (2) SC is not compositional (linearizability is). Ground your answer in Lamport's two-part definition — total order + program order preservation — and give the canonical example: ZooKeeper is SC but not linearizable (reads may be stale; use `sync()` for linearizable reads). If asked to compare consistency models, position SC clearly on the spectrum between causal consistency (weaker — no global total order) and linearizability (stronger — adds real-time). The `r1=0, r2=0` impossibility proof is a strong demonstration that you understand what SC actually rules out. Bonus: knowing that x86 TSO is not SC and that Peterson's algorithm requires memory barriers is a hardware-awareness signal that separates strong candidates.
