# Network Partitions: What They Are, How They Affect System Behavior — Interview Q&A (5 YOE Level)

---

## Section 1: What Is a Network Partition

**Q1. What is a network partition in a distributed system?**
A: A network partition is a failure in the communication layer between nodes in a distributed system such that the nodes split into two or more groups that cannot reach each other — even though the nodes themselves are still running and healthy. Messages sent between groups are lost, delayed indefinitely, or never delivered. The nodes on each side of the partition have no way to distinguish "the other node is down" from "I can't reach the other node" — from their perspective, the outcome is the same: silence.

Partitions are not exotic edge cases. They occur regularly in production systems due to: misconfigured network switches, NIC failures, BGP misroutes, cloud provider availability zone failures, data center cross-connect failures, and even aggressive firewall rules that silently drop packets without sending a TCP RST. Any system that runs on a network must assume partitions will happen and design for them explicitly.

**Q2. How is a network partition different from a node crash?**
A: A node crash is unambiguous — the node is gone, it stops sending heartbeats, and other nodes can detect its absence after a timeout. A network partition is ambiguous — the remote node is still running and processing requests from nodes on its side of the partition, but it appears dead to nodes on the other side. This ambiguity is the root of most distributed systems complexity:

- After a crash, the crashed node makes no decisions. After a partition, both sides may continue making decisions — independently and potentially conflictingly — because neither side knows the other is still alive.
- A crashed node's state is frozen. A partitioned node's state continues to evolve, diverging from the other side.
- When a crashed node recovers, it rejoins with stale state. When a partition heals, both sides rejoin with *conflicting* states that must be reconciled.

The partition scenario is harder than the crash scenario in almost every meaningful way.

**Q3. Can you always detect that a partition has occurred?**
A: No — this is one of the fundamental constraints of distributed systems. The FLP impossibility result (Fischer, Lynch, Paterson, 1985) proves that in an asynchronous network where even one node can fail, no deterministic consensus algorithm can guarantee both safety (all nodes agree on the same value) and liveness (the algorithm always terminates). The core reason: an asynchronous system cannot distinguish between a slow node and a dead/partitioned node. A message that never arrives might be delayed or lost. You only know a partition has occurred after a timeout — and timeouts are always an approximation.

**Q4. What causes network partitions in real systems? Give concrete examples.**
A: Partitions arise from many layers of the network stack:

- **Switch/router failure** — a core switch in a data center fails; servers on either side of it can't reach each other. Common in large data centers where the spine-leaf topology has finite redundancy.
- **BGP misroute** — Border Gateway Protocol route advertisements are misconfigured or hijacked, causing traffic between two data centers to be blackholed or routed to the wrong destination. Major cloud providers have had incidents caused by BGP issues.
- **NIC or cable failure** — a single server's network interface card fails or a cable becomes intermittently faulty. The server is "up" but unreachable. These are particularly insidious because they may be intermittent — packets get through sometimes, not others.
- **Cross-AZ / cross-region latency spikes** — a network link between availability zones or regions becomes so congested that timeouts fire on the application side, effectively creating a "soft partition" even though the link is technically up.
- **Firewall rule misconfiguration** — a firewall change silently drops packets (no RST sent), causing the application to wait until TCP timeout fires — which can be minutes.
- **GC pause causing a "self-partition"** — a JVM node pauses for a 30-second garbage collection. During this pause, it cannot send heartbeats. Other nodes declare it dead and elect a new leader. When it resumes, it believes it's still the leader — a "split-brain" scenario caused by a software pause rather than a network fault.

## Section 2: The CAP Theorem

**Q5. What does the CAP theorem state?**
A: The CAP theorem (Brewer, 2000; formally proved by Gilbert and Lynch, 2002) states that a distributed data system can provide at most two of the following three guarantees simultaneously:

- **Consistency (C)** — every read receives the most recent write or an error. All nodes see the same data at the same time. (Note: this is linearizability, a strong consistency model — not the "C" in ACID which means something different.)
- **Availability (A)** — every request receives a response (not an error), though the response may not reflect the most recent write.
- **Partition tolerance (P)** — the system continues to operate even when network messages between nodes are lost or delayed arbitrarily.

The key insight that the theorem forces: **partition tolerance is not optional**. Networks fail. A system that cannot tolerate partitions is a system that fails completely whenever a network fault occurs — unacceptable for any production distributed system. Therefore, the real trade-off is not CA vs CP vs AP: it is **C vs A during a partition**. When a partition occurs, you must choose: do you stay consistent (refuse requests that might produce stale reads) or stay available (answer requests that may return stale data)?

**Q6. Why is the "CA" system from the CAP theorem not a realistic choice?**
A: A CA system (consistent and available, but not partition-tolerant) would be a system that provides linearizable reads/writes and never returns errors, but stops working correctly the moment a network partition occurs. In practice, this means the system must either crash or return inconsistent data during a partition — neither of which is "available" in any meaningful sense. The only way to truly avoid the trade-off is to run on a single machine (no partition possible), which is vertical scaling and sacrifices every benefit of distribution. Any system that runs on more than one machine over a network must be partition-tolerant, so the CA choice is effectively saying "we'll have one machine," which isn't distributed systems design.

**Q7. What is the difference between CP and AP systems? Give examples of each.**
A:
- **CP systems (Consistent + Partition-tolerant)** — when a partition occurs, the system refuses to serve requests that could return stale or inconsistent data. It sacrifices availability to preserve correctness. Example: during a partition, a CP database's minority partition stops accepting writes and returns errors (or blocks) until the partition heals and the node can confirm it has the latest state. HBase, Zookeeper, etcd, and traditional relational databases with a single primary are CP-leaning. The trade-off: the system may be unavailable during a partition even if it's technically running.
- **AP systems (Available + Partition-tolerant)** — when a partition occurs, every node continues to accept reads and writes. Correctness is sacrificed: nodes on either side of the partition may serve different data or accept conflicting writes, diverging until the partition heals and conflicts are reconciled. Cassandra, DynamoDB, CouchDB are AP-leaning. The trade-off: the system is always responsive but clients may read stale or conflicting data.

Real systems are rarely purely one or the other. Cassandra, for example, lets you configure per-operation consistency levels — `QUORUM` reads/writes are CP; `ONE` reads are AP. The choice is made at the query level, not the system level.

**Q8. What is a common misconception about the CAP theorem?**
A: The most common misconception is treating CAP as a static property of a database — "Postgres is CP, Cassandra is AP" — when in reality it describes a system's *behavior during a partition*, and many databases let you tune where they sit on the spectrum. A second misconception is that CAP is the only lens for thinking about distributed correctness. CAP is a blunt instrument: it deals only in binary (consistent vs not, available vs not) and doesn't capture nuance like *how* inconsistent, *how* unavailable, or for *how long*. The PACELC model (which extends CAP by also considering the latency vs consistency trade-off in the normal, non-partitioned case) is more useful for practical system design.

## Section 3: Consistency Models

**Q9. What is linearizability, and why is it the gold standard for consistency?**
A: Linearizability (also called "strong consistency" or "atomic consistency") is a correctness condition that says: even though operations on a distributed system are physically concurrent and run across multiple nodes, the system appears to external clients as if all operations execute atomically on a single machine, in some sequential order that is consistent with the real-time ordering of requests. Informally: once a write completes, every subsequent read by any client — anywhere in the world — must see that write or a newer one.

It's the gold standard because it's the easiest consistency model for application developers to reason about: the distributed system behaves just like a local variable. You don't need to think about stale reads, read-your-own-writes issues, or ordering anomalies. The cost: achieving linearizability requires coordination (quorum reads/writes, consensus protocols like Paxos or Raft), which adds latency and reduces availability during partitions.

**Q10. What is eventual consistency, and what guarantees does it actually provide?**
A: Eventual consistency guarantees that if no new writes are made to a piece of data, eventually all replicas will converge to the same value. It makes no guarantee about *when* convergence happens or what a read returns in the meantime. The practical meaning: reads may return stale data for an arbitrarily long time after a write; different clients may see different versions of the same data simultaneously; write conflicts are possible and must be resolved by some mechanism (last-write-wins, vector clocks, application-level merge).

"Eventual consistency" is often misunderstood as a single model, but it's actually a family — the weakest end of a spectrum. Systems that call themselves "eventually consistent" vary widely in their actual guarantees: some provide read-your-own-writes consistency, some provide monotonic reads, some provide causal consistency. When a system claims eventual consistency, the key follow-up questions are: what anomalies are possible? how are write conflicts resolved? and what is the realistic convergence time?

**Q11. What is causal consistency, and why is it a useful middle ground?**
A: Causal consistency guarantees that operations that are causally related are seen by all nodes in the same order. If Alice posts a message and Bob replies to it, all nodes that see Bob's reply must also have seen Alice's message — the cause must precede the effect. Operations that have no causal relationship (are concurrent) may be seen in different orders by different nodes.

Causal consistency is a useful middle ground because most application-level bugs from weak consistency are actually causality violations — a comment appearing before the post it responds to, a bank balance showing the debit before the credit. These are ordering anomalies, and causal consistency prevents them without requiring the full coordination overhead of linearizability. Systems like MongoDB's causal sessions, and research systems like COPS and Bolt-on Causal Consistency, implement this model.

**Q12. List the main consistency models from strongest to weakest.**
A: From most restrictive (most guarantees, most coordination cost) to least:

- **Linearizability (Strong Consistency)** — single-machine illusion; every operation appears instantaneous and global.
- **Sequential Consistency** — all operations appear in some global sequential order consistent with each node's local order, but not necessarily real-time order. (Weaker than linearizability: a read may not reflect the latest write if the write happened after the read started.)
- **Causal Consistency** — causally related operations are ordered; concurrent operations may differ per observer.
- **Read-Your-Own-Writes (RYOW)** — a client always sees its own writes, but may not see other clients' recent writes.
- **Monotonic Reads** — once a client reads a value, subsequent reads never return an older value. (No going backwards in time for a single client.)
- **Eventual Consistency** — the weakest guarantee: given no new writes, all replicas eventually converge. No ordering guarantees during the interim.

In practice these are often combined — a system might offer monotonic reads + read-your-own-writes, which together give a useful session-level guarantee without the full cost of linearizability.

## Section 4: Split-Brain

**Q13. What is split-brain, and why is it particularly dangerous in databases?**
A: Split-brain occurs when a network partition causes a distributed system to have two (or more) nodes that each believe they are the authoritative leader/primary, and both continue accepting writes. The name comes from the metaphor of a brain severed in two — each half acts independently, believing itself to be the whole. In databases:

- Both primaries accept writes for the same data.
- Each side's writes are invisible to the other.
- When the partition heals, both sides have conflicting state — the same key has two different values with no clear winner.
- The resolution may be irreversible: if both sides deleted and re-created records, or if financial transactions occurred on both sides, merging is not merely a technical problem but a business correctness problem.

This is why databases with leader election (Postgres with streaming replication, MongoDB, Elasticsearch) go to great lengths to prevent split-brain — using quorums, fencing tokens, or STONITH (Shoot The Other Node In The Head) to ensure the old leader is definitively dead before a new one is elected.

**Q14. What is a fencing token, and how does it prevent split-brain?**
A: A fencing token is a monotonically increasing number issued to a node when it becomes the leader. Every write the leader makes to a shared resource (a database, a distributed lock, a storage system) must include the fencing token. The storage system rejects any write with a token lower than the highest token it has seen.

The sequence that prevents split-brain:
1. Node A is elected leader and receives token 42.
2. Node A pauses (GC, long I/O) for 45 seconds. The lease expires.
3. Node B is elected new leader and receives token 43.
4. Node A resumes, still believing it's the leader. It tries to write with token 42.
5. The storage system sees token 42 < 43 (its current max), and rejects the write.
6. Node A's write fails, preventing it from acting as leader with a stale token.

The fencing token makes leadership revocation enforceable at the resource level, not just at the coordination layer. The critical insight from Martin Kleppmann's work: a lease/lock held by a process that pauses (GC, paging) doesn't protect you at the application level — you need the storage system to enforce exclusivity via fencing tokens.

**Q15. What is the difference between a network partition and a split-brain? Are they the same thing?**
A: A network partition is the *cause*; split-brain is a possible *consequence*. A network partition is a communication failure — two groups of nodes can't talk to each other. Split-brain is the outcome when both groups elect (or believe themselves to be) the leader simultaneously and proceed to accept writes. A partition does not always lead to split-brain — a well-designed CP system detects the partition and has the minority partition stop accepting writes rather than elect a new leader. Split-brain is what happens when the system fails to handle the partition correctly. The terms are often used interchangeably in casual conversation, which is imprecise — understanding the distinction matters in an interview context.

## Section 5: Quorums

**Q16. What is a quorum, and how does it help maintain consistency during partitions?**
A: A quorum is the minimum number of nodes that must participate in an operation for it to be considered valid. In a cluster of N nodes, a common quorum size is ⌊N/2⌋ + 1 (a simple majority). The key property: any two quorums must overlap in at least one node. This overlap node has seen all writes that achieved quorum — ensuring that a quorum read always intersects with the quorum that performed the latest write and therefore sees the latest data.

During a partition: one side of the partition has a majority of nodes (the quorum side) and continues operating. The minority side cannot form a quorum and must stop accepting writes (or reads that require quorum). This prevents split-brain: only one partition can form a quorum, so only one side can be "authoritative." The minority side becomes unavailable — the system chooses consistency over availability for that partition segment.

**Q17. What is the relationship between W + R > N and consistency in quorum systems?**
A: In a quorum-based system with N replicas, W write replicas (writes are acknowledged when W nodes confirm), and R read replicas (reads check R nodes):

- If `W + R > N` — read and write quorums overlap on at least one node. That overlapping node has seen the latest write, so reads always return the latest written value. This gives strong consistency.
- If `W + R ≤ N` — it's possible for a read quorum to not include any node that participated in the latest write. Reads may return stale data. Eventual consistency.

Common configurations:
- `N=3, W=2, R=2` — strong consistency; tolerates 1 node failure.
- `N=3, W=1, R=1` — maximum availability, minimum consistency; all three nodes may have different values.
- `N=3, W=3, R=1` — always consistent reads (fast), but writes require all nodes (slow, unavailable if any node is down).

The W + R > N condition doesn't guarantee linearizability on its own (clock skew and concurrent writes complicate things), but it's the baseline for quorum-based consistency reasoning in systems like Dynamo-style databases.

**Q18. What is "sloppy quorum," and what trade-off does it represent?**
A: A sloppy quorum is used in systems (notably Amazon's DynamoDB / Dynamo paper) where, during a partition, if the required W nodes from the "home" replicas for a key are unavailable, the write is accepted by W nodes from *other* available nodes — "hinted handoff." The write is temporarily stored on these non-home nodes with a hint about which home node it belongs to. When the home node recovers, the hinted handoff is replayed to deliver the write.

The trade-off: sloppy quorum improves write availability during a partition (writes don't fail just because some home replicas are unreachable), but it breaks the W + R > N consistency guarantee — a read quorum of R home nodes may not include the sloppy nodes holding the latest write. The system becomes AP during the partition. Sloppy quorums are appropriate when availability is more critical than strong consistency — a shopping cart being temporarily inconsistent is better than a write failing.

## Section 6: Partition Handling Patterns

**Q19. What are the two fundamental strategies for handling a partition, and when do you use each?**
A: When a partition occurs, a system must choose:

- **Refuse (CP strategy)** — nodes in the minority partition stop accepting writes (and possibly reads) and return errors until the partition heals. The system is unavailable for that segment of nodes but remains consistent. Use when correctness is non-negotiable: financial ledgers, inventory counts, distributed locks, configuration systems. The on-call burden is higher (availability incidents during partitions), but data integrity is preserved.
- **Proceed (AP strategy)** — all nodes continue accepting reads and writes. Reads may return stale data; writes may conflict. Use when availability is more valuable than strict consistency: product catalogs, user sessions, social media feeds, shopping carts. The system is resilient to partitions, but conflict resolution logic must exist and the application must tolerate seeing inconsistent data.

Many systems let you choose per-operation — Cassandra's consistency levels, DynamoDB's eventually vs strongly consistent reads. The right answer is usually: use CP for operations that require correctness (checkout, payment, balance reads) and AP for operations where stale data is tolerable (recommendation feeds, view counts, search indexes).

**Q20. What is the "write-ahead log" and how does it help with partition recovery?**
A: A write-ahead log (WAL) is an append-only log on each node that records every intended change before applying it to the actual data structures. During normal operation: write to WAL → apply to data. During a partition: the WAL continues recording writes on each side. When the partition heals: nodes compare their WALs to identify divergence — where their logs agree and where they differ.

WALs enable several partition recovery mechanisms:
- **Log shipping / streaming replication** — once connectivity is restored, the primary sends WAL entries to replicas to bring them up to date (used in Postgres, MySQL).
- **Point-in-time recovery** — replay the WAL from a known consistent checkpoint to reconstruct state.
- **Conflict detection** — by comparing WAL positions (LSN in Postgres, log index in Raft), the system can identify exactly which operations happened on each side during the partition.

The WAL doesn't resolve conflicts automatically — it makes conflicts visible and recoverable. The resolution policy is a separate concern.

**Q21. What is vector clock / version vector, and how does it help reason about concurrent writes during a partition?**
A: A vector clock is a data structure that tracks causality in a distributed system — each node maintains a counter, and every message carries the sender's vector (a list of all nodes' counters). By comparing two vector clocks, the system can determine:

- **A happened-before B** — if A's vector is strictly dominated by B's vector in all dimensions, A causally preceded B.
- **Concurrent** — if neither vector dominates the other, the two events happened concurrently (no causal relationship). These are the events that may conflict after a partition.

When a partition heals and nodes merge their writes, vector clocks identify which writes are concurrent (potential conflicts requiring resolution) vs which are simply later in the causal chain (no conflict — just apply in order). DynamoDB uses version vectors for this purpose; Riak used vector clocks prominently. Without causal tracking, systems fall back to last-write-wins (LWW) based on physical timestamps — which is incorrect because clocks on different machines are never perfectly synchronized.

**Q22. What is the "PACELC" model, and how does it improve on CAP?**
A: PACELC (Daniel Abadi, 2012) extends CAP by observing that the C vs A trade-off only describes behavior *during a partition (P)*. But partitions are rare — what trade-off does a system make in the *else (E)* case (normal operation, no partition)? The answer: **latency (L) vs consistency (C)**. Even without a partition, achieving strong consistency requires coordination between replicas (waiting for quorum, running consensus), which adds latency. A system that chooses low latency will return local reads without waiting for global agreement — trading consistency for speed.

PACELC framing: a system is described as `PA/EL` (partition → available, else → low latency) or `PC/EC` (partition → consistent, else → consistent) etc. Examples:
- **Cassandra** — PA/EL: during partition, prefer availability; in normal operation, prefer low latency (reads from one replica by default).
- **Zookeeper** — PC/EC: during partition, prefer consistency (minority partition stops serving); in normal operation, prefer consistency (quorum reads).
- **DynamoDB** — PA/EL by default (eventual reads); can be tuned to PC/EC with strongly consistent reads (higher cost/latency).

PACELC forces the conversation about the latency trade-off that CAP ignores, making it more useful for practical system selection.

## Section 7: Real Systems Behavior

**Q23. How does Zookeeper handle a network partition?**
A: Zookeeper uses the Zab (Zookeeper Atomic Broadcast) consensus protocol, a variant of Paxos. It requires a quorum (majority) of nodes to be available to serve requests. During a partition:

- The majority partition continues operating normally — it can elect a leader and process reads and writes.
- The minority partition stops serving reads and writes entirely. Clients connected to minority nodes receive errors (connection loss or session expiry).
- Specifically: if a cluster has 5 nodes and splits 3/2, the 3-node partition operates; the 2-node partition goes fully unavailable.

This is a CP choice: Zookeeper prioritizes consistency (every client sees the same view of the znodes tree) over availability. It's why Zookeeper is appropriate for distributed locks, leader election, and service discovery — where serving a stale value would be worse than returning an error. Zookeeper is explicitly not suitable for data that needs to be available during partition events.

**Q24. How does Cassandra handle a network partition?**
A: Cassandra is AP by default. During a partition:

- All nodes on both sides continue accepting reads and writes for any keys they hold replicas of.
- Writes that reach a node are logged and applied locally. The nodes on the other side of the partition don't see these writes until the partition heals.
- When the partition heals, **read repair** and **anti-entropy** (Merkle tree-based sync via `nodetool repair`) reconcile divergent replicas. Conflict resolution uses **last-write-wins** based on the write timestamp.

The danger in Cassandra's LWW conflict resolution: if two clients wrote different values to the same key during a partition, the one with the later timestamp wins — regardless of which write the application intended to "win." Clock skew between nodes means the "winning" write might not be the most recent in wall-clock time either. This is why Cassandra is appropriate for use cases that tolerate eventual consistency and where LWW semantics are acceptable (e.g., a user's last-seen timestamp) but not for use cases requiring strict correctness (financial balances, inventory).

**Q25. How does a distributed database using Raft handle a network partition?**
A: Raft (Ongaro and Ousterhout, 2014) is a consensus algorithm designed to be more understandable than Paxos while providing the same guarantees. In a Raft cluster during a partition:

1. The leader is on one side of the partition. It tries to replicate log entries to followers.
2. If the leader can still reach a quorum of followers, it continues operating — log entries are committed when a quorum acknowledges them. The minority-side followers get no new entries.
3. If the leader loses its quorum (it's now on the minority side), it stops committing new entries — it can still receive writes from clients but won't be able to commit them (no quorum). After an election timeout, the majority side elects a new leader.
4. The old leader, if it's still receiving client requests, will either timeout and step down, or its writes will pile up uncommitted.
5. When the partition heals, the old leader discovers a higher term number from the new leader, reverts to follower status, and its uncommitted entries are overwritten by the new leader's log.

Key Raft safety property: **only the leader with the most up-to-date log can be elected** (a candidate must have a log at least as up-to-date as the majority). This ensures the new leader after partition healing has all committed entries, preventing data loss.

**Q26. What is the "split-brain" scenario in Elasticsearch, and how does it mitigate it?**
A: Early versions of Elasticsearch (pre-7.0) had a notorious split-brain risk because the `minimum_master_nodes` setting was easy to misconfigure. If a 5-node cluster lost network connectivity in a 2/3 split and `minimum_master_nodes` was set to 1 (the default in early versions), both groups could elect a master — leading to two clusters both accepting writes to the same indices, creating a divergent state that was extremely difficult to reconcile.

Elasticsearch 7.0+ replaced the manual setting with a **self-configured bootstrapping** mechanism: the cluster automatically computes the correct quorum (`⌊N/2⌋ + 1`) at cluster formation time and refuses to change it without explicit operator intervention. The new cluster coordination layer (based on Raft-like consensus) also prevents the minority partition from electing a master, making split-brain structurally impossible under correct configuration. The lesson: making safety a default rather than a configurable parameter prevents the most common class of operator error.

## Section 8: Scenario / System Design Questions

**Q27. "Your service has two data centers. A network partition isolates them from each other. Users are connected to both. What do you do?"**
A: The answer depends on what the service does — that determines the C vs A trade-off:

**For a financial service (e.g., payment processing):**
Prefer CP. Designate one DC as primary. During a partition, the secondary DC stops accepting writes and returns errors (or serves reads from its local replica with a staleness warning). The primary continues operating. When the partition heals, the secondary re-syncs from the primary's WAL. Accepting concurrent writes in both DCs risks double-spend and balance inconsistencies that may be impossible to reconcile cleanly.

**For a social media service (e.g., newsfeed reads):**
Prefer AP. Both DCs continue serving reads from their local replica. Writes may be queued or served locally and synced after the partition heals. A user in DC-B may see their own post but not a post from a user whose write landed in DC-A. This is acceptable — the eventual convergence lag is measured in seconds to minutes, and the user experience degradation is minor compared to returning errors.

**For a shopping cart:**
AP, with a merge strategy. Both DCs accept adds/removes to the cart. On partition heal, merge the carts using a union strategy (keep all items from both sides). This is the "Amazon Dynamo" approach — it's better to show a user an item they removed than to fail their shopping session entirely.

**Q28. "How would you test that your system handles network partitions correctly?"**
A: Partition handling is notoriously undertested because partitions are hard to simulate in a dev environment. Approaches:

- **Chaos engineering (tc/iptables rules)** — use Linux `tc` (traffic control) or `iptables` rules to simulate packet loss, latency, and full partition between specific hosts. Tools like Pumba (for Docker), tc-netem, or Chaos Monkey inject these at the infrastructure level. Can be scripted as part of a CI/CD pipeline.
- **Jepsen testing** — Jepsen (Kyle Kingsbury) is a framework for testing distributed systems by running operations against a cluster while injecting network partitions and node crashes, then verifying consistency properties (linearizability, serializability) against the operation history using the Knossos checker. It has found bugs in Cassandra, MongoDB, Redis Sentinel, and many others.
- **Integration tests with partition simulation** — in-process or containerized integration tests where the "network" is a mock that can be configured to drop messages between specific node pairs. This is faster than real infrastructure tests and can run in CI.
- **Property-based testing** — define invariants (e.g., "no two leaders can be elected simultaneously," "a write acknowledged by quorum is always visible to a subsequent quorum read") and verify them across randomized sequences of operations and failure injections.
- **Game days** — deliberately inject a partition in a staging or even production environment (with careful safeguards) to verify that alerting fires, the system degrades as designed, and recovery procedures work.

**Q29. "A distributed cache returns stale data after a network partition heals. What are the failure modes and how do you mitigate them?"**
A: When a partition heals and a cache cluster re-converges, several failure modes are possible:

- **Stale reads for TTL window** — cache entries written to one side of the partition are not propagated to the other side until either TTL expires or an explicit invalidation occurs. After healing, nodes on the previously-isolated side serve their locally-cached (stale) version. Mitigation: short TTLs on critical data; explicit cache invalidation on write rather than TTL-only expiry.
- **Cache stampede on healing** — when many stale entries expire simultaneously after a partition heals, all misses hit the database at once. Mitigation: jitter on TTLs to spread expiry; probabilistic early expiration (PER) which randomly refreshes a cache entry before it expires to prevent thundering herd.
- **Inconsistent in-flight reads** — during the partition, some clients were reading from a replica with data version V1; others from a replica with V2. After healing, the cache reconciles to V2 — but some clients have already made decisions based on V1 and V2 data from the same "logical" moment. Mitigation: cache versioning with monotonic version numbers; clients include the version in their read; serve an error rather than a version mismatch.
- **Write conflicts** — if the cache allows writes (Redis with multi-primary replication), two conflicting writes may have happened during the partition. Redis's conflict resolution is LWW by timestamp. Mitigation: don't use cache as the source of truth for write-critical data; the DB is the authoritative source; cache is for read acceleration only.

**Q30. "You're designing a distributed lock service. What partition behavior do you choose, and why?"**
A: For a distributed lock, the answer is unambiguously CP. Here's why:

A distributed lock's entire purpose is mutual exclusion — at most one holder at a time. If, during a partition, both sides can independently "acquire" the lock (AP behavior), you have two lock holders simultaneously, which is worse than no lock at all — it's exactly the split-brain scenario that causes data corruption, double-spending, or race conditions.

Therefore: the lock service must require a quorum to acquire a lock. If a client can't reach a quorum, the lock acquisition fails (error returned) — the client must retry or fail gracefully. The minority side of a partition returns errors for all lock acquisitions. This is the correct behavior: it's better for a job to fail (retryable) than for two jobs to both believe they hold the exclusive lock.

Additional requirements for a correct distributed lock:
- **Leases with TTL** — locks must expire automatically in case the holder crashes or gets partitioned. The lock is released after TTL even if the holder hasn't explicitly released it.
- **Fencing tokens** — as described in Q14, the lock service issues a monotonically increasing token with each grant. The protected resource enforces the token, preventing a holder whose lease expired from continuing to act as if it holds the lock.
- **Avoid relying on lock for critical financial operations** — even a correct distributed lock can't prevent a GC-paused process from acting after its lease expires but before it checks. The resource itself must enforce exclusivity via fencing tokens. This is the lesson from the Redlock controversy: a lock reduces the probability of concurrent access but only fencing tokens eliminate it.
