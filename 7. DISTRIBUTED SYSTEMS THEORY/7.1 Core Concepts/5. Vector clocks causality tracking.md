# Vector Clocks: Causality Tracking — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Physical Clocks Fail

**Q1. Why can't distributed systems just use physical (wall-clock) timestamps to order events?**
A: Physical clocks on separate machines are never perfectly synchronized. Even with NTP (Network Time Protocol), clocks can drift by tens to hundreds of milliseconds relative to each other. This creates three concrete problems:

- **Clock skew** — two events that happen concurrently may have timestamps that suggest a sequential order. Event A at machine 1 at `10:00:00.100` and event B at machine 2 at `10:00:00.050` look like B happened first — but machine 2's clock simply ran slow.
- **Clock drift** — clocks continuously diverge between NTP sync intervals. A write that arrives "later" by wall clock may actually have been issued earlier in real time.
- **Clock jumps** — NTP can step a clock forward or backward abruptly (leap seconds, manual correction). A backward step can make an event appear to happen in the past, before events that genuinely preceded it.

The result: ordering events by physical timestamp in a distributed system is incorrect. You cannot distinguish "B happened after A in real time" from "B's machine has a faster clock than A's." For causal ordering — where the question is "did A *cause* or *influence* B?" — physical timestamps are fundamentally the wrong tool.

**Q2. What is Lamport's "happens-before" relation, and what problem does it solve?**
A: Leslie Lamport introduced the happens-before relation (→) in his 1978 paper "Time, Clocks, and the Ordering of Events in a Distributed System." It defines a partial order over events without relying on physical clocks:

Three rules define A → B (A happens-before B):
1. **Same process rule** — if A and B are events in the same process, and A occurs before B in that process's execution, then A → B.
2. **Message rule** — if A is the sending of a message and B is the receipt of that same message, then A → B. A send always happens-before its corresponding receive.
3. **Transitivity** — if A → B and B → C, then A → C.

If neither A → B nor B → A holds, then A and B are **concurrent** — they have no causal relationship. Neither caused or influenced the other.

The problem it solves: in distributed systems where correctness depends on causal ordering (a reply should not be visible before the message it replies to; a balance read should not precede the write that updated it), we need a way to identify *which events causally precede which others* without trusting physical clocks. Happens-before gives us that — purely from the communication structure of the system.

**Q3. What is a Lamport clock, and what does it fail to capture?**
A: A Lamport clock is a logical counter maintained per process that implements the happens-before relation as a scalar timestamp:

- Each process starts at counter 0.
- On any local event: increment counter by 1.
- On sending a message: increment counter by 1; attach the counter value to the message.
- On receiving a message with timestamp T: set local counter = `max(local, T) + 1`.

The property Lamport clocks give: if A → B, then `LC(A) < LC(B)`. A lower Lamport timestamp reliably indicates "happened-before."

What they fail to capture: the converse is not true. If `LC(A) < LC(B)`, you cannot conclude A → B. A and B might be concurrent (no causal relationship), and yet B has a higher Lamport timestamp purely because of the max/increment arithmetic. Lamport clocks give a *consistent* ordering but not a *characterization* of concurrency — you cannot use a Lamport clock alone to detect whether two events are concurrent or causally related. That is the gap vector clocks fill.

## Section 2: Vector Clocks — The Mechanism

**Q4. What is a vector clock?**
A: A vector clock is an array of logical counters — one per process in the system — maintained by every process. If the system has N processes, every process maintains a vector of N integers, initialized to all zeros: `[0, 0, 0, ..., 0]`.

Update rules:
- **Local event** — the process increments only its own position in the vector. Process i: `V[i] += 1`.
- **Send message** — increment own position, then attach the full vector to the outgoing message.
- **Receive message** with vector `V_msg` — for each position k: `V_local[k] = max(V_local[k], V_msg[k])`. Then increment own position: `V_local[i] += 1`.

Example with 3 processes (A, B, C), initial state `[0,0,0]`:
- A does a local event: A's vector → `[1,0,0]`
- A sends to B: B receives, merges: `max([0,0,0], [1,0,0])` → `[1,0,0]`, then increments own: B → `[1,1,0]`
- B sends to C: C receives, merges `[1,1,0]`, increments: C → `[1,1,1]`
- Meanwhile A does another event: A → `[2,0,0]`

A's vector `[2,0,0]` and C's vector `[1,1,1]` are now concurrent — neither dominates the other.

**Q5. How do you compare two vector clocks to determine causality?**
A: Given two vector clocks V1 and V2 from N processes, comparison rules:

- **V1 = V2** (equal) — all positions are identical. Same event, or logically equivalent state.
- **V1 < V2** (V1 happens-before V2) — every position in V1 is ≤ the corresponding position in V2, AND at least one position in V1 is strictly less. V1 causally precedes V2.
- **V1 > V2** (V2 happens-before V1) — symmetric of the above.
- **V1 ∥ V2** (concurrent) — neither V1 ≤ V2 nor V2 ≤ V1. There exists at least one position where V1[k] > V2[k] and at least one position where V1[j] < V2[j]. The two events have no causal relationship.

```
V1 = [2, 1, 0]
V2 = [2, 2, 1]
→ V1 < V2 (V1 happens-before V2): every position of V1 ≤ V2, and some are strictly less.

V1 = [3, 1, 0]
V2 = [2, 2, 1]
→ V1 ∥ V2 (concurrent): V1[0]=3 > V2[0]=2, but V1[1]=1 < V2[1]=2. Neither dominates.
```

This is the key advantage over Lamport clocks: vector clocks characterize concurrency precisely. If two events are concurrent, their vector clocks are incomparable (∥). If one happened-before the other, its vector clock is strictly dominated.

**Q6. Prove (informally) that vector clocks correctly capture the happens-before relation.**
A: We need to show two things:

**A → B implies V(A) < V(B):**
- Same process: A and B are on the same process; each event increments the local counter. So V(A)[i] < V(B)[i], and all other positions are identical or B has seen at least as much. V(A) < V(B).
- Message send/receive: when B receives A's message, it merges A's vector using max, then increments. So every position of V(A) is ≤ V(B) (from the max), and V(B)[B_process] > V(A)[B_process] (from the increment after receiving). V(A) < V(B).
- Transitivity: if V(A) < V(B) and V(B) < V(C), then for all k: V(A)[k] ≤ V(B)[k] ≤ V(C)[k], with some strict inequalities. V(A) < V(C).

**V(A) < V(B) implies A → B:**
The contrapositive: if A and B are concurrent (no causal path from A to B), then no message chain connects them, so B's vector can't accumulate A's counter contribution through any path. There must be some position where A's counter is ahead of B's (from A's own events unseen by B), causing incomparability. If V(A) < V(B), some process's counter propagated from A to B — which only happens through message passing — proving a causal path exists.

## Section 3: Conflict Detection and Resolution

**Q7. How are vector clocks used to detect write conflicts in a distributed database?**
A: When a distributed database (like Riak or the original Amazon Dynamo) stores a value, it attaches the vector clock of the write. On a subsequent write, the new vector clock is compared to the existing one:

- **New write's VC dominates stored VC** (`new > stored`) — the new write causally follows the stored version. No conflict: overwrite safely.
- **Stored VC dominates new write's VC** (`stored > new`) — the new write is based on stale data (the client somehow missed a more recent version). The system can reject or flag it.
- **Concurrent** (`new ∥ stored`) — both writes happened without knowledge of the other. This is a genuine conflict — two independent clients updated the same key. The database cannot safely discard either. It stores both values as **siblings** (Riak's term) and returns both to the next reader, who must resolve the conflict.

This is the mechanism by which Dynamo-style databases avoid silent data loss. Last-write-wins (by timestamp) would silently discard one of the concurrent writes. Vector clocks expose the conflict explicitly, deferring resolution to the application or a merge function.

**Q8. What is a "sibling" in Riak, and how does the application resolve it?**
A: In Riak (a Dynamo-inspired key-value store), when two concurrent writes to the same key are detected via vector clock comparison, both versions are stored as siblings — the key now has two values simultaneously. The next read of that key returns all siblings to the client. Resolution strategies:

- **Application-level merge** — the client reads both siblings and merges them according to domain logic. For a shopping cart: union the items from both versions (keep all items from both siblings). For a counter: sum the values. For a document: show a "conflict" UI and ask the user to resolve.
- **Last-write-wins (LWW) as fallback** — if the application doesn't implement merge, Riak can be configured to discard all but the sibling with the latest physical timestamp. This is lossy (one write is silently dropped) but simpler.
- **CRDTs (Conflict-free Replicated Data Types)** — Riak's preferred solution for common data types: special data structures (G-Counters, PN-Counters, OR-Sets) whose merge function is mathematically guaranteed to be commutative, associative, and idempotent — so any order of merging siblings produces the same result. No application-level conflict handling needed.

The practical lesson: vector clocks surface conflicts; they don't resolve them. The resolution policy is a separate domain decision that must be made per data type.

**Q9. What is "last-write-wins" (LWW), and what are its dangers compared to vector clocks?**
A: Last-write-wins is a conflict resolution strategy where, when two concurrent writes exist, the one with the later physical timestamp is kept and the other is silently discarded. It's simple to implement and has no storage overhead (no vector clock to maintain), which is why it's common as a default in systems like Cassandra and Redis.

The dangers:
- **Silent data loss** — the losing write is dropped without any notification to the client that wrote it. The client believes its write succeeded (it got a 200 OK), but the data is gone. In a shopping cart: a user adds an item, gets a success response, refreshes, and the item is missing — because a concurrent write from another session "won" on timestamp.
- **Clock skew makes LWW incorrect** — if two machines' clocks are skewed and the "earlier" event has a later wall-clock timestamp (because the machine clock ran fast), LWW discards the causally-later write and keeps the older one.
- **No conflict visibility** — LWW never exposes the conflict to the application. With vector clocks, the application knows a conflict occurred and can apply domain logic. With LWW, data loss is silent.

When is LWW acceptable? For data where losing a write doesn't matter semantically — a user's last-seen timestamp (the latest value is always "correct"), a cache entry (stale is acceptable, loss is recoverable on the next miss), or metrics (one dropped sample is insignificant). For anything where every write is meaningful (orders, financial transactions, user-generated content), LWW is dangerous.

## Section 4: Version Vectors

**Q10. What is a version vector, and how is it different from a vector clock?**
A: A version vector is conceptually related to a vector clock but used specifically to track the version of a *data item* across replicas, rather than the causality of *events* in a process. The distinction:

- **Vector clock** — attached to an *event* (a send, receive, or local operation). Tracks the causal history of process executions. Every event in the system has a vector clock.
- **Version vector** — attached to a *data value* stored in a replica. Tracks which writes each replica has incorporated. The vector has one entry per replica, recording how many writes from that replica have been incorporated into this version of the value.

Example: a key-value store with 3 replicas (R1, R2, R3). After two writes, both going through R1:
- Version vector of the value: `{R1: 2, R2: 0, R3: 0}` — this version incorporates 2 writes from R1, 0 from R2, 0 from R3.

After R2 receives and acknowledges this version, and a new write goes through R2:
- Version vector: `{R1: 2, R2: 1, R3: 0}`

Comparison rules for version vectors are identical to vector clocks — dominance implies causal ordering; incomparability implies concurrent writes (conflict). The semantic difference is that version vectors are coarser-grained (per replica, per value) rather than per-event.

**Q11. Where are version vectors used in real systems?**
A: 
- **Riak** — stores a version vector with every object. On write, Riak requires the client to present the current version vector (read-before-write). The new write's vector is derived from the presented one, establishing causal lineage. Concurrent writes without causal lineage produce siblings.
- **DynamoDB (original Dynamo)** — the Dynamo paper (2007) describes vector clocks per object per replica, used to detect and expose conflicts. Modern DynamoDB has moved away from this in its public API, using LWW in most configurations, but the original design used version vectors extensively.
- **Git** — Git's commit DAG (directed acyclic graph) is a form of version history that captures causality. A merge commit has two parents — this is structurally equivalent to a concurrent-write conflict being explicitly recorded and resolved. The "version vectors" are the commit SHAs.
- **CouchDB / PouchDB** — CouchDB maintains a `_rev` field and a revision tree per document. Conflicting revisions (concurrent writes) are stored as branches of the tree, analogous to siblings in Riak.
- **Distributed caches (invalidation)** — version vectors can track which version of a cache entry each replica holds, enabling precise invalidation: a replica with version `{W1: 3, W2: 1}` knows it must invalidate if it sees a write from W1 with sequence > 3.

## Section 5: Dotted Version Vectors and Practical Issues

**Q12. What is the "false conflict" problem with naive version vectors, and what causes it?**
A: A false conflict is when the system reports a write conflict between two values that are actually causally related — one genuinely preceded the other — because the version vector comparison incorrectly shows them as concurrent. This happens in Riak's original design due to a subtle issue with how deletes and re-creates are tracked.

The scenario: 
1. Client reads key K, gets version vector `{R1: 2}`, value "hello".
2. Client deletes K. Delete is recorded with vector `{R1: 3}`. Key is removed.
3. A different client creates K again (unaware of the deletion). New value "world" starts at `{R1: 1}` (fresh start — the replica didn't propagate the delete to this client).
4. Now the system has `{R1: 3}` (delete) and `{R1: 1}` (new write). `{R1: 3}` dominates `{R1: 1}` — the system concludes the delete happened after the new write and applies the delete, silently losing "world."

The reverse problem also occurs: the new write's vector can be seen as conflicting with the delete's vector if the replica ordering is inconsistent, producing a false sibling. These pathological cases led to the development of **Dotted Version Vectors (DVV)** — an extension that distinguishes between "this event I know about" and "this event I caused," eliminating false conflicts in delete/re-create scenarios.

**Q13. What are the scalability limits of vector clocks, and how do real systems address them?**
A: Vector clocks have two main scalability problems:

- **Vector size grows with participant count** — the vector has one entry per process. In a system with 1,000 microservice instances, every message carries a 1,000-element vector. Storage and network overhead grow linearly with the number of participants. This is manageable for small, fixed-membership clusters (5-node databases) but impractical for large dynamic systems (thousands of ephemeral containers).
- **Participant churn** — in dynamic systems where processes join and leave (Kubernetes pods scaling up/down), the vector can accumulate entries for processes that no longer exist. The vector grows unboundedly without garbage collection.

How real systems address this:
- **Clock pruning / truncation** — periodically remove entries for processes that haven't communicated recently, accepting some loss of causal precision. Used in some Riak configurations.
- **Server-side version vectors only** — rather than tracking every client, only track the N replicas of the storage system. Clients don't get entries in the vector — they present an opaque token (the vector they last read) and the server compares it. This caps vector size at the number of replicas (typically 3–7), not the number of clients.
- **Hybrid Logical Clocks (HLCs)** — an alternative to pure vector clocks that combines physical timestamps with logical counters. HLCs are compact (a single 64-bit value), preserve happens-before for events within the physical clock's uncertainty bound, and work well in dynamic systems. Used in CockroachDB and Yugabyte.
- **Causal tokens / context** — some systems pass a causal context as an opaque blob (serialized but not interpreted by the client). The server extracts the relevant vector from it, hiding the scalability problem from the client interface.

## Section 6: CRDTs and Causality

**Q14. What is a CRDT, and how does it relate to causality tracking?**
A: A CRDT (Conflict-free Replicated Data Type) is a data structure designed so that concurrent updates can always be merged without conflict, as long as the merge function is: commutative (order of merging doesn't matter), associative (grouping of merges doesn't matter), and idempotent (merging the same update twice has the same effect as merging it once). CRDTs avoid the need for conflict resolution because by mathematical design, there are no conflicts.

The relationship to causality: CRDTs still use causal context (version vectors or dotted version vectors) — not to detect conflicts but to determine which updates a replica has already seen, so that re-delivered messages are correctly treated as idempotent (applied once) rather than applied multiple times. Without causal context, a re-delivery of an "add item to cart" operation could add the item twice. The causal context tracks exactly which add operations have been incorporated, making the merge idempotent.

**Q15. Walk through a G-Counter (Grow-only Counter) CRDT and explain its causal structure.**
A: A G-Counter is the simplest CRDT — a counter that can only be incremented (never decremented), replicated across N nodes. Each node maintains a vector of per-node increment counts:

```
State: [n1_count, n2_count, n3_count, ...]
Node i can only increment its own slot: state[i] += 1
Value (total count) = SUM of all slots
Merge of two states: element-wise max of each slot
```

Example with 3 nodes:
- Node 1 increments twice: `[2, 0, 0]`
- Node 2 increments once: `[0, 1, 0]`
- On merge: `max([2,0,0], [0,1,0]) = [2,1,0]`; total = 3

Causal structure: each slot records how many increments *from that node* have been seen. If Node 1's slot reads 2, I've seen both of Node 1's increments. Merging with max ensures that once an increment is seen, it's never "unseen." Idempotency: merging the same state twice gives the same result (`max(V, V) = V`). This structure is a version vector where each "entry" represents observed increments from each replica.

## Section 7: Hybrid Logical Clocks

**Q16. What is a Hybrid Logical Clock (HLC), and why was it developed?**
A: A Hybrid Logical Clock (Kulkarni et al., 2014) combines physical timestamps and logical counters into a single compact timestamp `(physical, logical)`. It was developed to address two limitations:

- **Pure logical clocks (Lamport, vector clocks)** — correctly order causally related events but have no relationship to physical time. You can't answer "did this event happen in the last 5 minutes?" with a Lamport clock.
- **Pure physical clocks** — relate to real time but can't correctly order concurrent events due to clock skew.

HLC gives the best of both: it tracks causality like a logical clock *and* stays close to physical time (within the system's maximum clock uncertainty, typically a few milliseconds to tens of milliseconds with NTP, or sub-millisecond with PTP/GPS).

Update rules:
- `l` = max physical timestamp seen so far (the "physical" component)
- `c` = logical counter (tiebreaker when physical timestamps are equal)
- On local event or send: if `pt.now() > l`: set `l = pt.now()`, `c = 0`. Else: `c += 1`.
- On receive with `(l_msg, c_msg)`: `l = max(l, l_msg, pt.now())`. If `l == l_msg == pt.now()`: `c = max(c, c_msg) + 1`. Else if `l == l_msg`: `c = max(c, c_msg) + 1`. Else if `l == pt.now()`: `c += 1`. Else: `c = 0`.

Properties: HLC timestamps are compact (64 bits: 48 bits physical + 16 bits logical), maintain causality like a Lamport clock (A → B implies `HLC(A) < HLC(B)`), and stay within bounded skew of physical time, enabling time-range queries.

**Q17. Where are Hybrid Logical Clocks used in production systems?**
A: HLCs are particularly well-suited to distributed databases that need both causal ordering and time-range queries — something vector clocks can't offer:

- **CockroachDB** — uses HLCs as the primary timestamp for MVCC (Multi-Version Concurrency Control). Every row write gets an HLC timestamp. Read transactions specify a read timestamp; they see all writes committed before that timestamp. The HLC's physical component allows CockroachDB to enforce serializable isolation across distributed nodes without a global lock.
- **Yugabyte DB** — similarly uses HLCs for MVCC and distributed transaction ordering, following a similar architecture to CockroachDB.
- **MongoDB** — uses a form of hybrid time (cluster time + logical time) for causal consistency in replica set reads and for change stream ordering.
- **Google Spanner** — uses TrueTime (hardware-assisted GPS/atomic clock synchronization) rather than HLCs, but the motivation is identical: commit timestamps must respect real-time ordering. TrueTime's uncertainty interval (`[earliest, latest]`) allows Spanner to commit transactions that are guaranteed not to overlap with past commits by waiting out the uncertainty window.

## Section 8: Scenario / System Design Questions

**Q18. "Two users edit the same document simultaneously in a collaborative editor. How do you use causality tracking to handle this?"**
A: Collaborative editing is one of the canonical use cases for causality tracking. The key challenge: User A inserts "hello" at position 5 while, concurrently, User B deletes characters 3–7. Without causality tracking, applying both operations in arbitrary order produces different (and incorrect) results.

Approaches using causality:

- **Operational Transformation (OT)** — each operation carries the vector clock of the document state it was applied to. When the server receives two concurrent operations (with incomparable vector clocks), it transforms one operation relative to the other so that both can be applied in sequence and produce the same result. Google Docs uses a variant of OT. The causality context (what state was the document in when the operation was generated?) determines how to transform.
- **CRDT-based editors (e.g., YATA, used in Yjs; LSEQ)** — represent the document as a sequence CRDT where each character has a unique, stable identity (typically a tuple of `(site_id, logical_counter)` — effectively a vector clock position). Insertions and deletions reference character identities, not positions. Concurrent inserts have a deterministic merge order based on their causal context. Used in Figma, linear.app, and many modern collaborative tools.

In both approaches, the vector clock (or per-character causal identifier) is what makes concurrent edits unambiguous — you know exactly which version of the document each edit was made against, enabling correct merge.

**Q19. "In a distributed shopping cart, a user adds item X on their mobile and removes item X on the web simultaneously (partition scenario). How does causality tracking help, and what's the correct outcome?"**
A: This is the concurrent write scenario where vector clocks detect the conflict and CRDTs provide a principled resolution:

With **LWW (no causal tracking)**: one operation wins based on timestamp. If "add" has a later timestamp (perhaps the mobile clock runs fast), the cart shows item X. If "remove" wins, it doesn't. The outcome is unpredictable and neither choice is necessarily what the user intended.

With **vector clocks + sibling resolution**: the system detects that add and remove are concurrent (neither causally precedes the other — they happened during a partition). Both are stored as siblings. On merge: the application must decide. Two common policies:
- **"Add wins" (OR-Set semantics)** — prefer the add over a concurrent remove. Rationale: the user's intent to buy is given priority over a possibly accidental remove. This is the OR-Set CRDT (Observed-Remove Set): an item is in the set if it has been added AND not yet removed *with causal knowledge of the add*. A concurrent remove (without seeing the add) does not remove the item.
- **"Remove wins"** — prefer the remove. Safer for preventing double-purchases, but risks items reappearing that users deliberately removed.

The right policy is a business decision — but vector clocks make it a *visible, explicit* decision rather than a silent coin flip based on clock skew.

**Q20. "Design a distributed key-value store that handles concurrent writes without data loss. What role do version vectors play?"**
A: The design follows the Dynamo paper model:

**Write path:**
1. Client reads key K, receives value V and its version vector `VV_current`.
2. Client modifies V to produce V', then sends a write request with: new value V', and the `VV_current` it read (the causal context).
3. The coordinator replica receives the write. It compares `VV_current` (what the client saw) with the currently stored version vector `VV_stored`:
   - If `VV_current >= VV_stored` (client has seen everything the store has): safe to overwrite. New version vector = `VV_current` with the writing replica's entry incremented.
   - If `VV_current < VV_stored` (write is based on stale data): reject or flag.
   - If `VV_current ∥ VV_stored` (concurrent write): store both values as siblings with their respective version vectors.
4. Replicate to W replicas.

**Read path:**
1. Read from R replicas. Collect all (value, version_vector) pairs.
2. Discard any value whose version vector is dominated by another's (it's a stale replica — the other value causally supersedes it).
3. If multiple non-dominated values remain: they are concurrent writes (siblings). Return all of them to the client for merge.
4. Client merges siblings, writes back the merged value with a new version vector that dominates all sibling VVs (confirming they've been merged).

Version vectors enable this design to achieve: no silent data loss (conflicts are surfaced as siblings), correct staleness detection (dominated VVs are pruned), and monotonic reads (a read that returns VV X guarantees the next read returns a VV ≥ X).

**Q21. "A new engineer says 'we can just use Kafka message offsets as our causal ordering mechanism.' What's your response?"**
A: Good instinct — Kafka offsets do provide a total order within a single partition, which is a form of causal ordering. But this only works under specific conditions, and breaks in common scenarios:

- **Single partition, single topic** — Kafka offsets work as causal timestamps. Every consumer reads in the same order. This is essentially a Lamport clock implemented by the broker.
- **Multiple partitions** — offsets are only meaningful within a partition. Two events in different partitions have no guaranteed ordering from offsets alone. Message at offset 42 in partition 0 and offset 15 in partition 1 have no defined causal relationship from the offset numbers.
- **Multiple topics** — no cross-topic ordering from offsets. A write to topic A at offset 100 and a subsequent write to topic B at offset 1 look like B preceded A if you compare offsets naively.
- **Consumer groups with lag** — a consumer processing offset 50 may be causally behind another consumer at offset 100. Their "view" of the world is at different points, and if they write to a shared store, the later offset consumer's writes may overwrite the earlier one's without the earlier consumer having seen those writes.

The right answer: Kafka offsets are excellent for *ordering within a partition* but not a general causality tracking mechanism. For cross-partition or cross-topic causal ordering, you still need vector clocks or HLCs carried in the message payload. Some Kafka-based event sourcing systems carry explicit vector clocks in event metadata precisely for this reason.

**Q22. "How does Git's commit graph relate to vector clocks conceptually?"**
A: Git's commit history is a DAG (Directed Acyclic Graph) where each commit points to its parent(s). This DAG encodes causality: a commit causally follows all commits reachable from it via parent pointers.

The correspondence to vector clocks:
- A commit's SHA is effectively a globally unique event identifier.
- A commit's set of parent SHAs is its causal context — equivalent to a vector clock that says "I know about these specific prior states."
- `git merge-base A B` finds the most recent common ancestor — equivalent to finding the "greatest lower bound" in a vector clock partial order.
- A merge commit with two parents is exactly a concurrent write detection and resolution: Git detected that `HEAD` and `origin/main` were concurrent (neither is an ancestor of the other — they're like incomparable vector clocks), stored both histories as parents, and the merge commit resolves them (like sibling resolution).
- `git rebase` linearizes a divergent history — equivalent to forcing a total order on events that were concurrent, by replaying one branch on top of another.

Understanding Git deeply through the lens of causality and vector clocks is a useful mental model — the `merge`, `rebase`, and `cherry-pick` operations all have direct analogues in distributed systems conflict resolution.

## Core Definitions Cheat Sheet

| Term | Definition |
|--- |--- |
| Happens-before (→) | A causally precedes B: same-process order, or A's message was received by B, or transitively |
| Concurrent (∥) | Neither A → B nor B → A: no causal relationship |
| Vector clock V(A) < V(B) | Every position of V(A) ≤ V(B), at least one strictly less: A happened-before B |
| Vector clock V(A) ∥ V(B) | Some position where V(A) > V(B) AND some where V(A) < V(B): concurrent |
| Version vector | Vector clock attached to a data value, tracking per-replica write counts |
| Sibling | Two concurrent versions of the same key, both stored pending merge |
| LWW | Last-write-wins: resolve conflict by physical timestamp; fast but lossy |
| CRDT merge | Commutative, associative, idempotent merge; no conflict possible by design |
| HLC | Hybrid Logical Clock: `(physical_time, logical_counter)`; causally ordered + time-anchored |
| Dotted VV | Version vector extension that eliminates false conflicts in delete/re-create scenarios |
| Causal context | The version vector a client presents with a write, establishing the causal baseline |

**Tip for the interview:** At 5 YOE level, vector clock questions are rarely about reciting the algorithm — interviewers want to see you reason about *why* the mechanism exists and *what breaks* without it. The most impressive answers connect the theory to system design decisions: why Riak uses version vectors instead of LWW, why Git's merge is fundamentally the same problem as Dynamo's sibling resolution, why HLCs exist in CockroachDB but not in simpler databases, and what goes wrong when a team naively uses Kafka offsets or physical timestamps as their causal ordering mechanism. The war story format works well here: "we had a bug where two concurrent writes silently lost data because we used LWW — here's the version vector design we put in place."
