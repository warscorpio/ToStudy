# Fallacies of Distributed Computing — Interview Q&A (5 YOE Level)

---

## Section 1: Overview & Origins

**Q1. What are the eight fallacies of distributed computing, and where do they come from?**
A: The eight fallacies are a set of incorrect assumptions that developers new to distributed systems typically make when designing networked software. They were originally articulated by L. Peter Deutsch at Sun Microsystems in the early 1990s and later expanded to eight by James Gosling (the creator of Java). In order:

1. The network is reliable.
2. Latency is zero.
3. Bandwidth is infinite.
4. The network is secure.
5. Topology doesn't change.
6. There is one administrator.
7. Transport cost is zero.
8. The network is homogeneous.

Each fallacy describes a comfort assumption that works perfectly in local development, on a single machine, or in a controlled demo — and breaks in production distributed systems. Interviewers at the 5 YOE level expect you to name all eight and to connect each one to a concrete engineering consequence and mitigation.

**Q2. Why do these fallacies matter for a practising backend engineer?**
A: Because every one of them surfaces as a real class of production bugs and architectural decisions. Treating the network as reliable leads to missing retry logic and silent data loss. Treating latency as zero leads to chatty service communication that tanks p99. Treating the network as secure leads to unencrypted inter-service communication inside the VPC — a single compromised node reads everything. The fallacies are not trivia; they are a taxonomy of the most common distributed systems design mistakes. Understanding all eight means you can audit any microservices design and name exactly which fallacies it's violating before it ships.

## Section 2: Fallacy 1 — The Network Is Reliable

**Q3. What does "the network is reliable" mean as a fallacy, and why is it false?**
A: Developers writing distributed code often write it as if a network call either succeeds or throws an immediate, obvious error — like a local function call. In reality, networks drop packets, switches fail, NICs fail, cables are accidentally unplugged, cloud provider network fabrics have transient faults, and Kubernetes pods are evicted mid-request. A call can fail silently — the request is sent, no response ever arrives, no exception is thrown immediately (only after a timeout). Or the response is sent but the caller never receives it, meaning the operation may have completed on the server side. The network is an unreliable, asynchronous medium, not a synchronous, reliable pipe.

**Q4. What engineering consequences follow from ignoring this fallacy?**
A: The most dangerous consequence is **silent partial failures** — the caller doesn't know whether the operation succeeded. If a payment service calls an external gateway, sends the charge request, and the response is lost in transit, the caller doesn't know if the user was charged. A naive retry will charge them again. The full set of consequences:
- Missing timeout configuration — calls hang indefinitely, exhausting thread pools.
- Missing retry logic — transient failures become permanent user-visible errors.
- Missing idempotency — retries cause duplicate operations (double charges, duplicate records).
- Missing circuit breakers — a failing downstream cascades into the caller's thread pool exhaustion.
- Missing dead-letter handling — messages lost silently with no recovery path.

**Q5. How do you design around network unreliability?**
A: A layered defence:
- **Timeouts on every network call** — no call should block indefinitely. Set connect timeout and read timeout independently; a fast connect but slow response is a different failure mode.
- **Retries with exponential backoff and jitter** — retry transient failures, but spread retries to avoid a retry storm. Never retry without idempotency guarantees.
- **Idempotency keys** — every mutating operation accepts an idempotency key so retrying a request that already succeeded is safe.
- **Circuit breakers** — detect when a downstream is consistently failing and stop sending requests for a cool-down period. Prevents cascade failures from a single degraded dependency.
- **Bulkheads** — isolate thread pools per downstream dependency so one slow dependency can't exhaust the shared pool.
- **At-least-once delivery with idempotent consumers** — accept that messages may be delivered more than once; design consumers to handle duplicates safely.

## Section 3: Fallacy 2 — Latency Is Zero

**Q6. What does "latency is zero" mean as a fallacy, and why is it false?**
A: On a single machine, a function call takes nanoseconds. A local loopback call takes microseconds. A call between services on the same data centre network takes hundreds of microseconds to low milliseconds. A call to another region takes tens to hundreds of milliseconds. Developers who treat remote calls like local function calls design systems with synchronous call chains 10–15 services deep — each hop adding latency. At 10ms per hop × 12 hops = 120ms before any business logic runs. Under load, where each service has queuing delay, the same chain can take seconds. Latency is never zero, and in a microservices architecture, it compounds with every synchronous dependency.

**Q7. What engineering consequences follow from ignoring latency?**
A: The primary consequence is **chatty interfaces** — APIs designed for local use that make many small calls instead of one coarser call. A service that calls the User service to get `name`, then calls it again for `email`, then again for `address` — three round trips for data that could have been fetched in one. Further consequences:
- Synchronous call chains become the p99 bottleneck — one slow service in the chain degrades all callers.
- No latency budgets — engineers don't know how much of their SLO's latency budget each downstream call is allowed to consume.
- N+1 query patterns emerge across service boundaries — loading a list of orders then fetching user data per order in a loop.
- No caching of remote data — repeated identical calls to the same service with no local cache.
- Distributed tracing is absent — latency is unobservable, so its source is unknown until a user complains.

**Q8. How do you design around non-zero latency?**
A: Treat latency as a first-class resource with a budget:
- **Coarse-grained APIs** — design service interfaces to return everything the caller needs in one call. Avoid chatty fine-grained calls between services; keep those inside a service boundary.
- **Latency budgets** — assign each downstream call a maximum allowed latency (e.g., 50ms). If the call exceeds this, fail fast or return a degraded response.
- **Async over sync** — decouple services with a message queue. The caller publishes an event and continues; the downstream processes it without blocking the caller.
- **Caching** — cache remote data locally (Redis, in-process cache) to eliminate repeat round trips. Balance cache TTL against staleness tolerance.
- **Parallel calls** — when multiple independent downstream calls are needed, fire them in parallel (`Promise.all`) rather than sequentially. Latency = max(individual latencies), not sum.
- **Distributed tracing** — instrument every service boundary with OTel spans so latency sources are visible, not guessed at.

## Section 4: Fallacy 3 — Bandwidth Is Infinite

**Q9. What does "bandwidth is infinite" mean as a fallacy, and why is it false?**
A: Bandwidth is the rate at which data can be transferred across a network link. It is always finite — constrained by NIC speed, switch port capacity, cloud provider egress limits, and contention with other traffic on shared network infrastructure. Developers who ignore bandwidth design systems that transfer unnecessarily large payloads: fetching entire database rows when only a few fields are needed, sending full object graphs when only a delta is required, returning 10MB API responses when 10KB would suffice. At low load this works; under scale, large payloads saturate network links, increase serialisation/deserialisation CPU cost, inflate memory allocations, and drive up cloud egress bills.

**Q10. What engineering consequences follow from ignoring bandwidth?**
A:
- **Over-fetching** — querying SELECT * when only 3 columns are needed. The extra columns traverse the network, consume memory, and are discarded.
- **Unbounded API responses** — returning an entire collection without pagination. At scale, `GET /orders` returns 500,000 rows and times out or OOMs the caller.
- **No compression** — large JSON payloads transferred uncompressed. gzip or Brotli compression typically reduces payload size by 60–80%.
- **Chatty event payloads** — Kafka events carrying full object graphs when downstream consumers need only an ID and a status.
- **Cross-region data replication bandwidth costs** — AWS charges for data transferred between regions and out to the internet. A system that replicates 1TB of log data cross-region per day has a non-trivial and avoidable egress cost.
- **Serialisation format mismatch** — JSON is human-readable but verbose. Binary formats (Protocol Buffers, Avro, MessagePack) are 3–10× more compact for the same data.

**Q11. How do you design around finite bandwidth?**
A:
- **Fetch only what you need** — SELECT only required columns; project fields in API responses; use GraphQL or field masks (gRPC FieldMask) to let callers specify exactly which fields they need.
- **Paginate all collection endpoints** — never return unbounded collections. Enforce a maximum page size and require cursor-based pagination.
- **Compress payloads** — enable HTTP response compression (gzip, Brotli) at the API gateway level. Use binary serialisation (Protocol Buffers, Avro) for internal service-to-service and event payloads.
- **Send deltas, not full state** — Kafka events should carry only what changed (the delta) plus an identifier for the entity. Consumers who need the full entity fetch it from the source of truth.
- **CDN for static and semi-static content** — offload repeated delivery of large static assets to a CDN rather than serving from origin on every request.
- **Monitor network I/O** — track bandwidth utilisation per service as a USE metric. Alert before saturation, not after.

## Section 5: Fallacy 4 — The Network Is Secure

**Q12. What does "the network is secure" mean as a fallacy, and why is it false?**
A: Developers often assume that traffic inside the network perimeter — within a VPC, within a Kubernetes cluster, between services on the same subnet — is implicitly trusted and does not need encryption or authentication. This is the "castle and moat" model: secure the perimeter, trust everything inside. It's false for two reasons. First, perimeters are routinely breached — a single compromised host inside the network can intercept all unencrypted inter-service traffic. Second, modern distributed systems span multiple clouds, data centres, and third-party services; there is no single perimeter. In a microservices deployment, a compromised payment-service pod with no mTLS between services can read all plaintext traffic between any two services on the same cluster network.

**Q13. What engineering consequences follow from ignoring network security?**
A:
- **Unencrypted inter-service traffic** — a network tap or compromised node reads all plaintext traffic including tokens, API keys, PII, and payment data.
- **No service-to-service authentication** — any process that can reach the network can call any internal service. A compromised pod can call the payment API directly without credentials.
- **Secrets in environment variables or logs** — database passwords and API keys emitted in plaintext logs, readable by anyone with log access.
- **No egress filtering** — a compromised service can make outbound connections to attacker-controlled infrastructure (data exfiltration, command-and-control).
- **Over-permissive IAM roles** — a service that only needs to read from S3 has a role that can also write to S3 and call Lambda — blast radius of compromise is unnecessarily large.
- **Missing input validation** — trusting that internal callers send well-formed inputs because they're "internal" — an attacker with internal access can craft malicious payloads.

**Q14. How do you design around an insecure network?**
A: Adopt a zero-trust architecture — treat every network call as potentially hostile, regardless of source:
- **mTLS (mutual TLS) between all services** — both sides of every connection present certificates; identity is verified before any data is exchanged. Implemented via a service mesh (Istio, Linkerd) with no application code changes.
- **Short-lived credentials** — use IAM roles (not long-lived access keys), SPIFFE/SPIRE for workload identity, and rotate secrets automatically (AWS Secrets Manager, Vault).
- **Principle of least privilege** — each service has exactly the permissions it needs and nothing more. IAM policies, Kubernetes RBAC, and DB user permissions are scoped per service, per action.
- **Network policies** — Kubernetes NetworkPolicy (or AWS security groups) restrict which pods can communicate with which, blocking lateral movement after a compromise.
- **Encrypt at rest and in transit** — all data at rest (S3, RDS, EBS) encrypted. All data in transit encrypted with TLS 1.2+. No exceptions for "internal" traffic.
- **Secrets management** — never store secrets in environment variables, source code, or Dockerfiles. Use a secrets manager (AWS Secrets Manager, HashiCorp Vault) with audit logging on every secret access.

## Section 6: Fallacy 5 — Topology Doesn't Change

**Q15. What does "topology doesn't change" mean as a fallacy, and why is it false?**
A: Network topology — the map of which hosts exist, which IPs they hold, which routes connect them — is constantly changing in modern infrastructure. In a Kubernetes cluster, pods start, restart, and die continuously; their IP addresses change on every restart. Auto-scaling groups add and remove EC2 instances in response to load. Deployments roll new versions with new pod IPs. DNS TTLs cause stale IP caches. A load balancer's backend pool changes as instances are registered and deregistered. Cloud provider maintenance events cause live migration of VMs to different physical hosts. A system that hardcodes IPs, assumes a fixed set of nodes, or holds connections open indefinitely without reconnection logic will break as the topology changes around it.

**Q16. What engineering consequences follow from ignoring topology changes?**
A:
- **Hardcoded IP addresses** — a service configured with a peer's IP breaks as soon as that peer is rescheduled to a new IP (Kubernetes pod restart, EC2 replacement).
- **Stale DNS caches** — JVM and Node.js DNS caches may hold IPs beyond their TTL. After a pod replacement, the caller still routes to the old IP — which may now belong to a different pod or be unassigned.
- **Long-lived TCP connections with no keepalive** — a connection held across a load balancer failover or a NAT gateway replacement becomes a dead connection the application doesn't know is dead until it tries to write and times out.
- **Service discovery not used** — services call each other by hardcoded hostnames or IPs instead of using a service registry (Kubernetes DNS, Consul, AWS Cloud Map). Adding a new instance of a service doesn't automatically become reachable by callers.
- **No graceful connection draining** — during a rolling deploy, existing connections to dying pods are abruptly terminated, causing in-flight requests to fail.

**Q17. How do you design around topology changes?**
A:
- **Use DNS-based service discovery, not hardcoded IPs** — Kubernetes services provide a stable DNS name (`payment-service.default.svc.cluster.local`) regardless of underlying pod IP changes. Never hardcode pod IPs.
- **Respect DNS TTLs** — configure HTTP clients and connection pools to re-resolve DNS periodically. In Node.js: `keepAliveMsecs` in `http.Agent` and configure `dns.lookup` TTL. Avoid infinite DNS caching.
- **TCP keepalive on long-lived connections** — configure keepalive probes so the OS detects dead connections rather than discovering them at the next write attempt.
- **Connection pool health checks** — database and Redis connection pools should validate connections before use (`testOnBorrow: true` in most pool implementations). A connection that was valid at pool creation may be dead after a DB failover.
- **Graceful shutdown handling** — on SIGTERM, stop accepting new connections, finish in-flight requests, and only then close connections. Kubernetes `terminationGracePeriodSeconds` and `preStop` hooks implement this.
- **Service mesh** — Istio/Linkerd handle topology changes transparently: they update Envoy proxy configurations as endpoints change, so application code never needs to know about pod IPs or topology.

## Section 7: Fallacy 6 — There Is One Administrator

**Q18. What does "there is one administrator" mean as a fallacy, and why is it false?**
A: In a local development environment, the developer controls everything — the database, the application, the network, the OS. In production distributed systems — especially those spanning organisational boundaries — there are many administrators with different responsibilities, different change processes, different maintenance windows, and different priorities. The AWS network team, the database team, the platform engineering team, the application team, and the third-party payment gateway team all independently make changes to their slice of the infrastructure. No single person or team can control or even see the full system. A change made by the AWS team (EC2 host maintenance migration) can break an application team's service without any coordination — because the application team assumed someone else's infrastructure was stable.

**Q19. What engineering consequences follow from ignoring the multi-administrator reality?**
A:
- **Uncoordinated changes** — the DB team upgrades Postgres during the application team's peak traffic window; the application team wasn't informed and has no fallback.
- **Dependency on third-party SLAs** — a fintech depending on a payment gateway assumes it's always available. The gateway's own maintenance window isn't communicated; the payment service has no circuit breaker and cascades into total failure.
- **Configuration drift** — different teams manage different parts of the infrastructure with different tooling; the production environment gradually diverges from what any individual team believes it is.
- **Blame-shifting during incidents** — "the network team changed a firewall rule" / "the DB team ran a migration that held locks" / "the cloud provider had a partial outage". Without a unified observability platform, root cause attribution is slow and contentious.
- **Missing contract testing** — teams own different services and independently evolve their APIs. A provider team changes a response schema; the consumer team's service breaks in production because no contract test caught the incompatibility.

**Q20. How do you design around a multi-administrator environment?**
A:
- **Infrastructure as code** — all infrastructure configuration (Terraform, Pulumi, Helm charts) is version-controlled. Every change is a PR with a review. Unilateral manual changes are not possible in the critical path.
- **Consumer-driven contract testing** — each consuming service publishes a contract (Pact) defining what it expects from a provider. Provider CI runs consumer contracts on every deploy — a breaking API change fails the provider's build before it reaches production.
- **Circuit breakers on all third-party dependencies** — external dependencies (payment gateways, KYC providers, Account Aggregators) are treated as unreliable by default. Circuit breakers, fallbacks, and dead-letter queues absorb their failures.
- **Runbook for every external dependency** — documented procedure for "what do we do if X is down?" for every third-party service. Not "we wait for them to fix it" — an actionable fallback.
- **Centralised observability** — a unified monitoring platform (Grafana, Datadog) that spans all teams' services so that during an incident, a single pane of glass shows the full dependency graph, not just one team's slice.
- **Change freeze coordination** — shared calendar of planned maintenance windows across all teams and dependencies. Block deployments to critical services during payment processing peak hours.

## Section 8: Fallacy 7 — Transport Cost Is Zero

**Q21. What does "transport cost is zero" mean as a fallacy, and why is it false?**
A: Sending data across a network is not free. There are two types of cost — financial and computational. Financial: cloud providers charge for data transfer — AWS charges for inter-AZ traffic ($0.01/GB), cross-region traffic ($0.02–0.09/GB), and internet egress ($0.09/GB). A system that replicates 10TB of data cross-region per month pays $900–$900 in egress alone. Computational: serialising and deserialising data (JSON.stringify, JSON.parse, Protobuf encode/decode) consumes CPU proportional to payload size and frequency. A service making 50,000 req/sec each with a 50KB JSON payload spends measurable CPU on serialisation alone. Developers who treat transport as free design systems with large payloads, frequent cross-region calls, and verbose serialisation formats — and are surprised by their cloud bill and CPU overhead.

**Q22. What engineering consequences follow from ignoring transport cost?**
A:
- **Unexpected cloud egress bills** — cross-AZ or cross-region data transfer that wasn't budgeted for becomes a significant monthly cost at scale.
- **Serialisation CPU overhead** — high-throughput services spending 10–20% of CPU on JSON serialisation for payloads that could be 5× smaller in Protobuf.
- **Unnecessary data copying** — service A fetches a large dataset, passes it to service B, which passes it to service C — each hop pays the serialisation and network cost. Pushing the processing closer to the data (closer to the source of truth) eliminates these hops.
- **CDN absence** — static and semi-static assets served from origin on every request, paying full egress cost, when a CDN would serve cached copies from an edge location at near-zero cost.
- **Log shipping costs** — shipping verbose DEBUG-level logs from all services to a centralised store at full volume. At 1GB/min of log data, storage and ingestion costs dominate the observability budget.

**Q23. How do you design around non-zero transport cost?**
A:
- **Co-locate services that communicate heavily** — services that exchange high data volumes should run in the same AZ to minimise inter-AZ traffic costs. Use Kubernetes topology-aware routing (`topologySpreadConstraints`) to prefer same-AZ traffic.
- **Choose efficient serialisation formats** — Protocol Buffers for internal service-to-service communication (3–10× smaller than JSON, 2–5× faster to serialise). Use JSON only where human-readability is required (external-facing APIs, debugging).
- **Log sampling and level filtering** — ship only WARN/ERROR logs from high-volume services; sample INFO logs at 1–10%. A Fluent Bit filter that drops DEBUG logs before they leave the node costs nothing to store.
- **Egress-aware architecture** — place read replicas and caching layers in the same region as the consumers to avoid cross-region read traffic. Use S3 Transfer Acceleration or CloudFront for cross-region access to S3 data.
- **Batch over stream where latency allows** — instead of making 1,000 individual API calls per second, batch them into 10 calls of 100 items each. Reduces both network overhead and per-call serialisation cost.

## Section 9: Fallacy 8 — The Network Is Homogeneous

**Q24. What does "the network is homogeneous" mean as a fallacy, and why is it false?**
A: Homogeneous means "uniform" — the same hardware, the same OS, the same network stack, the same encoding, the same protocol, everywhere. In reality, distributed systems span heterogeneous environments: different OS versions (Ubuntu 20, Amazon Linux 2, Alpine), different hardware architectures (x86_64 on EC2, ARM64 on Graviton, Apple Silicon in dev), different network equipment from different vendors with different behaviours for edge cases (MTU sizes, TCP window scaling, ECN support), different byte orders (little-endian vs big-endian, though x86 dominance has made this rare), different character encodings, and different interpretations of protocol standards. Two systems that both claim to "support TLS 1.2" may negotiate different cipher suites, have different certificate validation behaviours, and handle protocol edge cases differently.

**Q25. What engineering consequences follow from ignoring heterogeneity?**
A:
- **Encoding and endianness bugs** — a system that works between two x86 services fails when one endpoint is an ARM device with different struct padding or alignment.
- **Protocol version mismatches** — a service that requires TLS 1.3 can't communicate with a legacy system that only supports TLS 1.2. A gRPC server that requires HTTP/2 can't communicate with a client that only speaks HTTP/1.1.
- **Serialisation format incompatibility** — JSON is safe but verbose; Protobuf requires schema coordination; Avro requires schema registry coordination. A consumer compiled against schema v1 fails to deserialise messages produced under schema v2 if backward compatibility wasn't maintained.
- **MTU and packet fragmentation** — a path through the network that goes from a 9000-byte jumbo-frame Ethernet segment to a 1500-byte MTU segment causes packet fragmentation; misconfigured `DF` (Don't Fragment) bit causes black-hole routing where packets are silently dropped without ICMP responses.
- **Timezone and date format inconsistency** — one service emits timestamps in IST, another in UTC, another as Unix epoch in seconds, another in milliseconds. Without a canonical format, joins and comparisons produce incorrect results silently.
- **"Works on my machine" bugs** — local development on macOS or Windows behaves differently from production Linux due to filesystem case sensitivity, line endings (CRLF vs LF), signal handling, and file descriptor limits.

**Q26. How do you design around network heterogeneity?**
A:
- **Standardise on explicit, unambiguous serialisation formats** — JSON with an explicit schema (JSON Schema, OpenAPI) for external APIs. Protobuf or Avro with a schema registry for internal event-driven systems. Never rely on implicit type coercions.
- **Use schema registries with compatibility enforcement** — Confluent Schema Registry for Avro/Protobuf Kafka messages enforces backward/forward compatibility on schema evolution. A producer can't push a schema change that breaks existing consumers.
- **Canonical timestamp format** — always store and transmit timestamps as UTC ISO8601 (`2024-01-15T08:30:00.000Z`) or Unix epoch milliseconds. Convert to local time only at display. Never store timestamps in local time.
- **Abstract over protocol versions** — use an API gateway or service mesh to handle TLS termination, protocol negotiation, and version translation. Application code never speaks raw TLS.
- **Containerisation** — Docker containers encapsulate the OS, runtime, and dependencies so the "it works on my machine" environment is the same environment that runs in production. Multi-arch builds (`buildx --platform linux/amd64,linux/arm64`) handle architecture heterogeneity.
- **Contract-first API design** — define the wire format (OpenAPI spec, Protobuf schema) before writing code. Both client and server implement to the spec, not to each other's implementation. This surfaces heterogeneity assumptions at design time, not integration time.

## Section 10: Synthesis & Interview Application

**Q27. If you had to pick the three most dangerous fallacies for a fintech payment platform, which would you choose and why?**
A: The most dangerous three for a payment platform specifically:

**1. The network is reliable** — the most operationally dangerous in fintech. A payment request that was sent but whose response was lost means the caller doesn't know if the user was charged. Without idempotency keys and at-least-once-with-dedup patterns, the retry either double-charges the user or silently drops the payment. Both outcomes are unacceptable in financial systems. Every payment operation must be designed assuming the call will sometimes succeed without the caller knowing.

**2. The network is secure** — the most compliance-critical. A fintech handles PAN data, bank account numbers, UPI IDs, and transaction histories. Unencrypted inter-service traffic inside a VPC means a single compromised node can read every payment flowing through the system. RBI and PCI-DSS requirements are specific about encryption in transit. mTLS between all internal services and zero-trust network policies are non-negotiable, not optional optimisations.

**3. There is one administrator** — the most organisationally dangerous in fintech. A payment platform depends on NPCI, sponsor banks, payment gateways (Razorpay, JusPay), KYC providers, and Account Aggregators — all with independent maintenance schedules, SLAs, and change processes. Designing without circuit breakers, fallbacks, and runbooks for every external dependency means any one of a dozen external administrators can take down your payment flow. The NACH pipeline specifically depends on multiple third parties in sequence; each hop must be treated as independently fallible.

**Q28. How would you explain all eight fallacies to a junior engineer joining a distributed systems team?**
A: A memorable way to ground all eight in one scenario — a payment confirmation flow:

*Your service calls a payment gateway to confirm a transaction. What can go wrong?*

1. **Network unreliable**: The call is sent but no response arrives — did the charge happen or not?
2. **Latency not zero**: The gateway is in a different region — add 150ms of base latency before any business logic.
3. **Bandwidth not infinite**: The gateway returns a 2MB response with every transaction detail — but you only needed the status field.
4. **Network not secure**: The gateway call goes over HTTP inside the VPC — anyone who can sniff that segment reads the card data.
5. **Topology changes**: The gateway endpoint IP changed — your hardcoded IP in config.yaml now points nowhere.
6. **Multiple administrators**: The gateway has a maintenance window at 2am that their team didn't tell yours — your NACH batch runs at 2am.
7. **Transport costs money**: Your service calls the gateway 1M times/day cross-region — the egress bill is $2,700/month.
8. **Network heterogeneous**: The gateway sends timestamps in IST; your service parses them as UTC — every transaction appears to have happened 5.5 hours in the past.

Every fallacy is a real bug in that one flow. That's why all eight matter.

**Q29. How do the eight fallacies map to specific distributed systems patterns as their mitigations?**
A: Each fallacy has a canonical engineering response:

| Fallacy | Mitigation Pattern |
|---|---|
| Network is reliable | Timeouts, retries with idempotency, circuit breakers, dead-letter queues |
| Latency is zero | Async messaging, coarse-grained APIs, caching, parallel fan-out, latency budgets |
| Bandwidth is infinite | Pagination, compression, binary serialisation, field projection, delta events |
| Network is secure | mTLS, zero-trust architecture, least privilege IAM, secrets management, network policies |
| Topology doesn't change | DNS-based service discovery, connection pool health checks, graceful shutdown, service mesh |
| One administrator | Contract testing, circuit breakers on third parties, IaC, centralised observability |
| Transport cost is zero | Co-location, efficient serialisation, log sampling, CDN, batching |
| Network is homogeneous | Schema registries, canonical timestamps (UTC), containerisation, contract-first API design |

**Q30. What is the relationship between the eight fallacies and the CAP theorem?**
A: The fallacies and CAP theorem address the same underlying truth — networks are unreliable, and distributed systems must be designed around that reality — but from different angles. The CAP theorem is a formal proof that, during a network partition (fallacy 1: the network is reliable, violated), a distributed system must choose between consistency and availability. The fallacies are a practitioner's catalogue of the false assumptions that lead engineers to build systems that neither handle partitions gracefully nor make an explicit consistency/availability choice. Specifically: fallacy 1 (network is reliable) is the precondition whose violation activates the CAP partition scenario. Fallacy 2 (latency is zero) is what the PACELC theorem extends CAP with — even without a partition, you still choose between latency and consistency on every operation. The fallacies explain *why* engineers build systems that CAP theorem then proves will fail — they didn't believe the theorem applied to them because they assumed the network was reliable.

**Tip for the interview:** Interviewers rarely ask you to list all eight as a quiz — they embed individual fallacies inside scenario questions. "Your service is making synchronous calls to 8 downstream services" → latency fallacy. "Your team hardcodes the payment gateway IP in the config" → topology fallacy. "You send full JSON objects on every Kafka event" → bandwidth and transport cost fallacies. "Your inter-service traffic is unencrypted inside the VPC" → security fallacy. Train yourself to recognise which fallacy a design decision is violating when you see it in a system design interview, not just to recite the list. At the 5 YOE level, the signal interviewers look for is whether you use the fallacies as a mental checklist when auditing a design — naming the fallacy, stating the failure mode it produces, and proposing the mitigation pattern, without being asked.
