# Clock Synchronization: Physical Clocks & NTP Limitations — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals of Physical Clocks

**Q1. What is a physical clock in a computer system?**
A: A physical clock is a hardware oscillator (typically a quartz crystal) that generates ticks at a nominal frequency (e.g., 32,768 Hz). The OS counts those ticks and maintains a wall-clock time — the "real" time as reported by `System.currentTimeMillis()` or `clock_gettime()`. Each machine has its own independent oscillator; no two clocks tick at exactly the same rate.

**Q2. What is clock drift?**
A: Clock drift is the gradual divergence of a machine's clock from true time, caused by imperfections in the oscillator. A crystal running slightly fast or slow accumulates error over time — typically in the range of 10–100 ppm (parts per million), meaning a clock can drift by ~1–8 seconds per day without any correction. Temperature, voltage fluctuations, and aging all affect drift rate.

**Q3. What is clock skew?**
A: Clock skew is the instantaneous difference between two clocks at a given moment (e.g., Node A says 10:00:05.000, Node B says 10:00:05.120 — skew is 120ms). Drift is the *rate* of divergence; skew is the *accumulated offset* at any point. In a distributed system, clock skew between nodes is the root cause of most time-related bugs.

**Q4. Why does clock skew matter in distributed systems?**
A: Because correctness in many distributed protocols depends on time ordering. If Node A timestamps an event at T1 and Node B timestamps a causally-later event at T2 < T1 due to skew, any system relying on wall-clock timestamps (e.g., for ordering writes, expiring leases, or sorting events) will produce incorrect results. Causality can appear to run backwards.

**Q5. Can you assume clocks on different machines in the same data center are closely synchronized?**
A: Not safely. Even with NTP, clocks across machines in the same data center can diverge by 1–200ms in practice, depending on network jitter, NTP polling intervals, and drift between corrections. Google's internal studies found that on their fleet, worst-case skew between nodes is on the order of milliseconds — and they built TrueTime specifically because even that isn't tight enough for Spanner's needs. Assuming synchronized clocks is one of the [classic fallacies of distributed computing](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing).

## Section 2: NTP — How It Works

**Q6. What is NTP and what problem does it solve?**
A: NTP (Network Time Protocol) is a protocol that allows machines to synchronize their clocks to a reference time source (usually UTC) over a network. It solves the drift problem by periodically querying time servers and adjusting the local clock to converge on the correct time, rather than letting each machine drift freely.

**Q7. What is the NTP hierarchy (stratum model)?**
A: NTP organizes time sources in a tree called the *stratum hierarchy*:
- **Stratum 0**: The reference clock itself — atomic clocks, GPS receivers, radio clocks. Not on the network directly.
- **Stratum 1**: Servers directly connected to Stratum 0 hardware.
- **Stratum 2**: Servers that sync from Stratum 1 — what most organizations use internally.
- **Stratum 3+**: Servers syncing from the level above, adding one hop of latency/error per level.
Most production servers sync from Stratum 2 or 3 public NTP pools (e.g., `pool.ntp.org`). The stratum number tells you how far removed from the reference source you are.

**Q8. How does NTP actually compute the time offset?**
A: NTP uses a four-timestamp exchange (similar to Cristian's Algorithm):
1. Client sends a request at time **T1** (client clock).
2. Server receives request at **T2** (server clock).
3. Server sends response at **T3** (server clock).
4. Client receives response at **T4** (client clock).

From these, NTP estimates:
- **Round-trip delay**: `RTT = (T4 - T1) - (T3 - T2)`
- **Clock offset**: `θ = ((T2 - T1) + (T3 - T4)) / 2`

The offset assumes symmetric network delay (half RTT each way). NTP then gradually adjusts ("slews") the local clock toward the true time using this offset.

**Q9. What is clock slewing vs. stepping, and why does slewing matter?**
A: **Stepping** is a sudden jump of the clock to the correct time. **Slewing** is a gradual adjustment — NTP speeds up or slows down the local oscillator rate (by up to ~500 ppm) until the clock converges on the correct time. Slewing is preferred because a sudden step backward can break applications that assume time is monotonic — timestamps could appear to go backwards, causing ordering bugs, negative durations, or cache expiry logic to behave incorrectly. Most NTP implementations only step the clock on startup or when the offset is very large (>125ms by default in ntpd); otherwise they slew.

## Section 3: NTP Limitations

**Q10. What is the fundamental accuracy limitation of NTP?**
A: NTP's accuracy is bounded by the **assumption of symmetric network delay**. If packets take longer one way than the other (asymmetric routing, different network paths, or congestion), the offset estimate is wrong. In practice, WAN-synchronized clocks achieve ~10–100ms accuracy; LAN-synchronized clocks can get to ~1ms. GPS-disciplined NTP or PTP (see Q16) can reach microsecond-level accuracy on local networks.

**Q11. Why is NTP over the public internet unreliable for tight synchronization?**
A: Several compounding reasons:
- **Variable latency**: Internet RTTs vary due to congestion, routing changes, and queuing. Each sample has different asymmetry.
- **Polling intervals**: NTP polls time servers every 64–1024 seconds by default — between polls, drift accumulates unchecked.
- **Stratum overhead**: Each stratum hop adds measurement error.
- **Packet loss / jitter**: NTP discards outliers, but high jitter degrades its statistical accuracy.
The net result is that internet-synchronized NTP clocks may have skew in the tens to hundreds of milliseconds.

**Q12. Does NTP guarantee monotonic time?**
A: No. NTP's wall clock (what you get from `gettimeofday()`) can go backward if a step correction is applied or if a slew overshoots. Most operating systems expose a separate **monotonic clock** (`CLOCK_MONOTONIC` on Linux, `mach_absolute_time()` on macOS) that *never* goes backward — it measures elapsed time from an arbitrary reference, but it doesn't represent wall-clock time and can't be compared across machines. Applications that need both ordering *and* monotonicity within a process should use the monotonic clock; those needing cross-node comparison have no safe option with NTP alone.

**Q13. What is the "leap second" problem with NTP?**
A: UTC occasionally inserts a leap second (61 seconds in a minute) to account for irregularities in Earth's rotation. NTP distributes this — but many applications and OS kernels handle it poorly. The Unix epoch doesn't have leap seconds, so implementations either smear the leap second (Google and Amazon spread it across a window) or apply it abruptly, causing clocks to jump or repeat a second. Services that relied on strictly monotonic timestamps have experienced outages during leap seconds (e.g., Cloudflare's 2017 BGP outage, Reddit's 2012 outage).

**Q14. What is the "Byzantine NTP" problem?**
A: A malicious or misconfigured NTP server can send false time to clients that blindly trust it — causing entire clusters of machines to shift to a wrong time. NTP has authentication mechanisms (NTPsec, symmetric keys) but they're often not configured. A mis-synced server can also cause the "false ticker" problem — NTP's intersection algorithm tries to detect and exclude outlier servers, but if a majority of your configured servers agree on a wrong time, the algorithm will select that wrong time. Best practice is to use at least 4–5 diverse NTP sources so outliers can be detected and rejected.

**Q15. What is clock monotonicity violation and why is it a bug class of its own?**
A: If an application uses `System.currentTimeMillis()` to measure elapsed time or order events across restarts/NTP corrections, it can observe:
- Negative durations (end time < start time after a backward step)
- Identical timestamps for events that happened at different times (precision too low or clock frozen)
- Ordering inversions (event B timestamped before event A despite occurring after)

This is a distinct class from drift — it's the direct consequence of NTP applying a backward correction. The correct fix is to use monotonic clocks for durations and intervals, and to *never* use wall-clock timestamps for within-process ordering.

## Section 4: Better Synchronization Approaches

**Q16. What is PTP (IEEE 1588) and how does it improve on NTP?**
A: PTP (Precision Time Protocol) achieves sub-microsecond synchronization by offloading timestamp measurement to NIC hardware — so the "software timestamp" jitter that plagues NTP (kernel scheduling delay, interrupt latency) is eliminated. PTP requires hardware support in the NIC and network switches (hardware timestamping, transparent clock bridges). It's used in financial exchanges, telecom, and high-frequency trading where microsecond accuracy is required. NTP is a software-only protocol and can't match PTP's precision.

**Q17. What is Google's TrueTime, and how does it solve NTP's limitations for Spanner?**
A: TrueTime is Google's globally synchronized time API, used in Spanner (their globally distributed database). Instead of returning a single timestamp, it returns an **interval** `[earliest, latest]` representing the bounds within which the true time falls, with an uncertainty of typically 1–7ms (backed by GPS receivers and atomic clocks in each data center). Spanner uses this uncertainty bound to implement **commit wait** — before committing a transaction, it waits until the TrueTime uncertainty window has elapsed, guaranteeing that no future transaction can be assigned a timestamp that appears to be in the past. This gives Spanner external consistency (linearizability) across globally distributed nodes without relying on a single clock.

**Q18. What are Cristian's Algorithm and the Berkeley Algorithm?**
A: 
- **Cristian's Algorithm** (1989): A client requests the time from a time server, measures RTT, and estimates the true time as `server_time + RTT/2`. Accuracy is bounded by RTT/2 and assumes symmetric delay. Simple but has a single point of failure (the time server) and degrades in high-latency networks.
- **Berkeley Algorithm** (1989): Designed for environments without an authoritative time source. A master polls all machines, collects their times, computes a fault-tolerant average (excluding outliers using Cristian's method), and broadcasts the *delta* each machine should apply. No machine needs UTC access — the goal is agreement among peers, not absolute accuracy. Used in early LAN environments.

## Section 5: Logical Clocks — The Practical Alternative

**Q19. Why were logical clocks invented? What problem do they solve that NTP cannot?**
A: Logical clocks were invented by Leslie Lamport (1978) in response to the fundamental problem: **physical clocks can never be perfectly synchronized**, so you can't reliably use them to determine causality across distributed nodes. Logical clocks sidestep the physics — instead of asking "what wall-clock time did this event happen at?", they ask "did event A happen before event B?" (the *happened-before* relationship). They provide a consistent ordering without requiring synchronized hardware.

**Q20. How do Lamport timestamps work?**
A: Each process maintains a counter, initially 0. Rules:
1. Before each event, increment the counter: `L = L + 1`.
2. When sending a message, include the current counter value.
3. On receiving a message with timestamp `T`, set `L = max(L, T) + 1`.

This guarantees: if A → B (A happened before B), then `L(A) < L(B)`. However, `L(A) < L(B)` does **not** imply A → B — concurrent events can have any ordering of Lamport timestamps. Lamport clocks capture causality in one direction only.

**Q21. What is the limitation of Lamport timestamps, and how do vector clocks fix it?**
A: Lamport timestamps can't determine if two events are **concurrent** (neither happened before the other) — a smaller Lamport timestamp just means "not causally after," not "causally before." Vector clocks fix this by giving each process N a counter for every process in the system. On each event, process i increments `V[i]`. On message receipt, each slot is set to `max(received[j], local[j])`. Now: `A → B` iff `V(A)[i] <= V(B)[i]` for all i, with at least one strict inequality. Events where neither vector dominates the other are provably concurrent. The cost is O(N) space and bandwidth per message — which becomes impractical at large node counts.

**Q22. What are Hybrid Logical Clocks (HLC) and why are they used in databases like CockroachDB?**
A: HLC (Kulkarni et al., 2014) combines physical and logical clocks: the timestamp is `(wall_clock_time, logical_counter)`. On each event, HLC tries to use the current physical time, falling back to incrementing the logical counter when the physical clock hasn't advanced (to handle ties or backward steps). This gives you timestamps that are:
- Close to actual wall-clock time (within NTP uncertainty bounds), so they're human-readable and correlatable with logs
- Strictly monotonic and causality-preserving even when NTP steps the clock
- Compact (one 64-bit integer can encode both components)

CockroachDB uses HLC to assign globally consistent transaction timestamps across nodes, tolerating NTP skew while staying close to real time.

## Section 6: Trade-offs & Decision-Making

**Q23. In what scenarios is relying on NTP timestamps acceptable?**
A: 
- Logging and observability — humans reading logs can tolerate a few ms of skew; cross-service log correlation works well enough.
- Cache TTLs and expiry — tolerating a few seconds of error is usually fine.
- Rate limiting and throttling — approximate wall-clock time is sufficient.
- Metrics and monitoring — timestamps are for display; minor skew doesn't affect correctness.
- Any use case where your required precision (seconds/minutes) vastly exceeds worst-case NTP skew.

**Q24. In what scenarios must you avoid relying on NTP wall-clock time?**
A: 
- Determining causal ordering of events across distributed nodes — use logical or vector clocks.
- Distributed transactions requiring linearizability — use HLC (CockroachDB), TrueTime (Spanner), or a central coordinator.
- Leader election with time-based leases — a clock that runs fast can cause two nodes to think they hold a lease simultaneously; use heartbeats + monotonic clocks or consensus (Raft/Paxos).
- Measuring latency within a process — always use a monotonic clock, never wall clock.
- Financial transaction ordering in high-frequency systems — use PTP or a sequencer service.

**Q25. What's the difference between "wall-clock time" and "monotonic time" for a backend engineer?**
A: Wall-clock time (`System.currentTimeMillis()`, `Date.now()`, `time.time()`) represents real-world time but can go backwards or jump due to NTP corrections. Monotonic time (`System.nanoTime()` in Java, `CLOCK_MONOTONIC` in Linux, `time.monotonic()` in Python) always moves forward — it measures elapsed time since some arbitrary reference. Rule of thumb: **use monotonic time for durations, timeouts, and intervals; use wall-clock time for timestamps you store, log, or send to other services.** Never compute durations by subtracting two wall-clock readings.

**Q26. Your system needs distributed locks with time-based expiry. What clock do you use?**
A: Don't rely solely on wall-clock time. The recommended pattern (e.g., Redis's Redlock) is to use monotonic clock time to measure *elapsed* time within a single process (to detect lease expiry locally), but to treat the distributed lock as expired based on a timeout period agreed upon at acquisition. The fundamental problem is that if the lock holder's clock runs slow relative to others, it may not know its lease has expired. Proper solutions (e.g., Chubby, ZooKeeper) use consensus protocols rather than time-based expiry, or combine time-based expiry with fencing tokens to detect stale lock holders even when they think they still hold the lock (see Martin Kleppmann's analysis of Redlock).

## Section 7: Scenario / System Design Style Questions

**Q27. "Your distributed job scheduler is sometimes running the same job twice at 3AM. What time-related issue might cause this, and how do you fix it?"**
A: Classic NTP skew bug. If two scheduler nodes have clocks skewed by even a few hundred milliseconds, both may independently decide "it's 3:00:00 AM, time to fire the job" — especially if they each check on a slightly different tick. The fix isn't better clock sync; it's removing the reliance on synchronized clocks: use a distributed lock (Redis, ZooKeeper) with a short TTL so only one node can hold the "fire job" token per scheduled interval. Alternatively, use a dedicated single-leader scheduler service — one node owns all scheduling decisions, eliminating the distributed clock problem entirely.

**Q28. "You're building an event sourcing system that needs to replay events in exact causal order. Should you use NTP timestamps as the sort key? Why or why not?"**
A: No. NTP timestamps will produce ordering inversions when two events on different nodes happen close together in wall-clock time — their skew may exceed the inter-event gap. Additionally, two events on the same node can have the same millisecond timestamp. Use a combination: a **vector clock or Lamport timestamp** to determine causal ordering, with wall-clock time as a secondary hint for human readability. Alternatively, route all events through a single sequencer service that assigns strictly monotonic sequence numbers — trading availability for ordering guarantees.

**Q29. "An audit log in your fintech backend must show the exact time a transaction was initiated by the user and when it was processed by the backend. Are there any clock pitfalls to call out?"**
A: Several:
- **Client-side timestamps are untrusted** — the user's device clock could be wildly off or manipulated; always use server-side timestamps for the "received" time.
- **Across microservices**: If the initiation timestamp is recorded by Service A and the processing timestamp by Service B with different NTP sync states, they may appear out of order even if processing truly happened after initiation.
- **Store timestamps in UTC with timezone info** (ISO 8601 / RFC 3339); avoid storing local time without offset.
- **Best practice**: Record both the user-claimed time and the server-received time explicitly, and use a single authoritative time source (or at minimum, ensure all services sync to the same NTP stratum 1/2 pool). For regulatory compliance, the server-side timestamp backed by a reliable time source is what matters.

**Q30. "You need to implement a TTL-based cache invalidation across 50 microservices. A senior engineer warns you about 'clock skew bugs'. What specifically could go wrong?"**
A: If each service uses its own wall clock to check TTL expiry, you can get:
- **Premature expiry**: Service A's clock runs fast — it evicts a cache entry before its intended TTL is up from the perspective of other services still reading the stale value.
- **Extended staleness**: Service B's clock runs slow — it serves a cached entry past its intended expiry window.
- **Race at boundaries**: Near the TTL boundary, some services see the entry as expired and fetch fresh data while others still serve cached data — giving different responses to clients in the same second, which may violate consistency requirements.

Fix: Store the **absolute expiry timestamp** (UTC) with the cached value, computed once at write time from a single reliable source. All readers compare current time against that stored timestamp. This reduces the per-service clock dependency to a single write-time clock reading rather than N independent readings at expiry check time.
