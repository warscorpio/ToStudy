# CRDTs — G-Counter, PN-Counter, OR-Set — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why CRDTs Exist

**Q1. What distributed systems problem do CRDTs solve?**
A: In a distributed system, multiple nodes may accept writes to the same data concurrently — especially under network partitions, where nodes can't coordinate in real time. When the partition heals, the nodes must merge their diverged states. The naive approaches fail badly:
- **Last-Write-Wins (LWW)**: silently discards one of the concurrent writes. Data is lost without any error.
- **Locking / consensus before every write**: solves the problem but requires coordination, sacrificing availability during partitions.

CRDTs (Conflict-Free Replicated Data Types) offer a third path: data structures designed so that **any two replicas can always be merged into a single consistent result, automatically, with no coordination and no conflicts.** Concurrent updates are never lost — they're all incorporated by the merge function.

**Q2. What does "conflict-free" actually mean mathematically?**
A: A CRDT's merge operation forms a **join-semilattice**: a partial order where any two states have a unique least upper bound (the "join" or merge). Three properties must hold:
- **Commutativity**: `merge(A, B) = merge(B, A)` — order of merging doesn't matter.
- **Associativity**: `merge(A, merge(B, C)) = merge(merge(A, B), C)` — grouping doesn't matter.
- **Idempotency**: `merge(A, A) = A` — merging a state with itself (receiving a duplicate message) is harmless.

These three properties together guarantee that no matter what order replicas exchange their states, and no matter how many times the same state is re-sent, all replicas converge to the same final value. That's the "conflict-free" guarantee: the math rules out the possibility of a conflict, rather than detecting and resolving one.

**Q3. What are the two families of CRDTs?**
A: 
- **State-based CRDTs (CvRDTs — Convergent)**: Nodes periodically ship their entire local state to peers. The receiver merges the received state into its own using the join function. Simple to reason about; the full state is self-contained. Downside: state can become large.
- **Operation-based CRDTs (CmRDTs — Commutative)**: Nodes broadcast individual *operations* (e.g., "increment", "add element") to peers, rather than full state. Requires the messaging layer to guarantee **at-least-once, exactly-once, or causal delivery** depending on the CRDT. Operations must commute — applying them in any order yields the same result. More bandwidth-efficient; harder to implement correctly.

In practice, most interview discussions (and most production systems like Riak, Redis, Cassandra) use state-based CRDTs because the delivery guarantees are simpler to reason about. All three data structures below are described in their state-based form.

**Q4. What's the conceptual difference between a CRDT and "eventual consistency with last-write-wins"?**
A: Both are eventual consistency strategies, but with a critical difference:
- **LWW** resolves conflicts by *discarding* one value — it achieves convergence by losing information. A concurrent write is silently overwritten; the client that made the losing write never knows.
- **CRDTs** resolve conflicts by *merging* all values — convergence comes from incorporating every update into the result. No information is lost; both concurrent increments to a counter end up counted, both concurrent additions to a set end up in the set.

LWW is appropriate when the semantics are "only the latest value matters" (e.g., a user's current location). CRDTs are appropriate when the semantics require accumulation (counters, sets, sequences) — where every update has independent meaning.

## Section 2: G-Counter (Grow-Only Counter)

**Q5. What is a G-Counter and what is its invariant?**
A: A G-Counter is a distributed counter that supports only **increment** — it can never be decremented. It is the simplest non-trivial CRDT and forms the building block for more complex types.

Its invariant: the value of the counter only ever increases. Each increment is tracked per-node, so no update is ever lost during a merge. It cannot represent a count that goes down.

**Q6. What is the internal state of a G-Counter?**
A: A vector of N integers — one slot per node in the cluster:

```
State: [v0, v1, v2, ..., v(N-1)]
```

Each node i only ever writes to slot i. Node 0 increments `state[0]`; Node 1 increments `state[1]`; and so on. No node ever writes to another node's slot. This ownership rule is what makes conflict-free merging possible.

**Q7. Define the three operations on a G-Counter.**
A:
- **Increment (at node i)**: `state[i] = state[i] + 1`
- **Query (value)**: `sum(state[0], state[1], ..., state[N-1])` — the total count is the sum of all slots.
- **Merge (two states A and B)**: `result[i] = max(A[i], B[i])` for each i — take the element-wise maximum.

**Q8. Walk through a G-Counter merge example with two nodes.**
A: Two nodes, Node 0 and Node 1. Initial state on both: `[0, 0]`.

```
Node 0 increments 3 times:  state_A = [3, 0]
Node 1 increments 2 times:  state_B = [0, 2]
(No communication yet — both operated independently)

Merge: result[0] = max(3, 0) = 3
       result[1] = max(0, 2) = 2
       merged = [3, 2]

Query: 3 + 2 = 5  ✅ (all 5 increments captured)
```

Now suppose Node 0 had already received an older state from Node 1 (`[0, 1]`) before Node 1's second increment, so Node 0's state is `[3, 1]` and Node 1's final state is `[0, 2]`:

```
Merge: result[0] = max(3, 0) = 3
       result[1] = max(1, 2) = 2   ← takes the larger (more recent) value
       merged = [3, 2]   ✅ same result — merge is idempotent and associative
```

**Q9. Why does element-wise max work as the merge function? Why not sum?**
A: Because the same increment might be counted multiple times if you sum. If Node 0 received Node 1's state `[0, 1]` and updated to `[3, 1]`, then later received `[0, 2]` and *added* slot 1 together — it would count Node 1's first increment twice, giving `[3, 3]` → total 6 instead of 5.

The `max` works because each slot only ever increases, and each node only writes its own slot. The maximum of two versions of a slot is always the most up-to-date value for that node's contribution. There's no scenario where taking the max loses an update — because if Node 1's slot went from 1 → 2, `max(1, 2) = 2` captures the later state. It's idempotent: receiving the same state twice doesn't change the result.

**Q10. What is the space complexity of a G-Counter, and what's the practical implication?**
A: O(N) where N is the number of nodes. For a small, fixed cluster (e.g., 5 Riak nodes), this is trivial. For a system where every user's device is a "node" (e.g., mobile offline-first apps), the vector grows proportionally to the number of devices — which can become impractical. This is a real production concern: some systems use a delta-CRDT approach or compress old entries to bound the vector size.

## Section 3: PN-Counter (Positive-Negative Counter)

**Q11. What problem does a PN-Counter solve that a G-Counter cannot?**
A: A G-Counter only supports increment. Many real counters need decrement too — shopping cart item counts, available inventory, vote tallies that allow un-voting. A PN-Counter supports both increment and decrement while remaining a CRDT.

**Q12. What is the internal structure of a PN-Counter?**
A: Two G-Counters: one tracking all increments (P — positive), one tracking all decrements (N — negative):

```
State: { P: [p0, p1, ..., p(N-1)],
         N: [n0, n1, ..., n(N-1)] }
```

Each node i writes to `P[i]` on increment and to `N[i]` on decrement — and only to its own slot in each vector, preserving the ownership invariant.

**Q13. Define the three operations on a PN-Counter.**
A:
- **Increment (at node i)**: `P[i] = P[i] + 1`
- **Decrement (at node i)**: `N[i] = N[i] + 1`
- **Query (value)**: `sum(P) - sum(N)`
- **Merge (states A and B)**: `P_result[i] = max(A.P[i], B.P[i])` and `N_result[i] = max(A.N[i], B.N[i])` — element-wise max on both vectors independently.

**Q14. Walk through a PN-Counter merge example.**
A: Two nodes, a "likes" counter. Initial state: `P=[0,0]`, `N=[0,0]`.

```
Node 0: 3 increments  →  P=[3,0], N=[0,0]
Node 1: 1 increment, 1 decrement  →  P=[0,1], N=[0,1]
(Partition — no communication)

Merge P: [max(3,0), max(0,1)] = [3, 1]
Merge N: [max(0,0), max(0,1)] = [0, 1]

Query: sum([3,1]) - sum([0,1]) = 4 - 1 = 3  ✅
```

All 4 increments and 1 decrement are captured regardless of the order the two nodes exchange their state.

**Q15. Can a PN-Counter go negative? Is that a problem?**
A: The mathematical value can go negative (if decrements exceed increments). Whether that's a *problem* depends on the use case. For a "likes" counter, going negative is semantically wrong. For an inventory counter, going negative means oversell. CRDTs give you convergence, not domain invariants — if you need to enforce "count ≥ 0", you need application-level logic, a separate protocol (e.g., reservations), or a different CRDT. This is a key interview point: CRDTs solve the *merge* problem, not all application correctness problems.

**Q16. Why can't you just use one vector and allow both positive and negative increments to the same slot?**
A: Because the merge function (element-wise max) would break. If Node 0's slot is `+3` and Node 1's slot is `-1` (decrement), `max(3, -1) = 3` — the decrement is silently discarded. The two-vector approach works because each vector only ever increases: `N[i]` only ever goes up (each decrement is encoded as +1 to the N vector), so `max` safely takes the higher decrement count just as it takes the higher increment count.

## Section 4: OR-Set (Observed-Remove Set)

**Q17. What is an OR-Set and what problem does it solve?**
A: An OR-Set (Observed-Remove Set) is a CRDT that supports both **add** and **remove** operations on a set of elements, with a specific semantic: **add always wins over a concurrent remove**. It solves the fundamental distributed set problem — two nodes can concurrently add and remove the same element, and when they merge, the result must be deterministic and conflict-free.

The "observed-remove" name describes the semantics: a remove only removes additions that the removing node had *observed* (knew about). If a concurrent add was not yet observed by the removing node, that add survives.

**Q18. Why is a set so much harder to make conflict-free than a counter?**
A: A counter has commutative operations — increment and decrement in any order give the same total. But set add and remove are not naturally commutative:
- Add then remove → element absent
- Remove then add → element present

For concurrent (causally unrelated) add and remove of the same element, you must pick one semantic — you can't satisfy both. Different CRDTs make different choices. The OR-Set explicitly chooses: concurrent add wins over concurrent remove. This is usually the right user-facing semantic ("I added it, so it should be there"), but it's a design decision, not a mathematical necessity.

**Q19. What is the internal structure of an OR-Set?**
A: Each element in the set is stored with a set of unique tags (usually UUIDs or (node_id, timestamp) pairs). The full state is a set of `(element, tag)` pairs:

```
State: { (element, tag), (element, tag), ... }
```

A tombstone set (T) tracks removed tags in some formulations, but the modern "add-wins" OR-Set avoids tombstones entirely (see Q21).

**Q20. Define add, remove, lookup, and merge for an OR-Set.**
A: Let the state be a set of `(element, unique_tag)` pairs:
- **Add(e)**: Generate a globally unique tag `t` (e.g., UUID). Add `(e, t)` to the local state. The tag represents "this specific addition of e".
- **Remove(e)**: Remove *all* pairs `(e, *)` currently in the local state. Only removes tags the node has observed — does not affect tags added concurrently on other nodes.
- **Lookup(e)**: Return true if any pair `(e, *)` exists in the state.
- **Merge(A, B)**: `A ∪ B` — set union of all `(element, tag)` pairs. Because tags are globally unique, a pair from one replica doesn't conflict with a pair from another.

**Q21. Walk through an OR-Set merge showing "add wins" over a concurrent remove.**
A: Two nodes share an initial state: `{ (apple, t1) }`.

```
Node A: remove(apple)  → state_A = {}           (removes the (apple, t1) pair it observed)
Node B: add(apple)     → state_B = { (apple, t1), (apple, t2) }  (adds a new tag t2)

(These happen concurrently — no communication)

Merge: state_A ∪ state_B = {} ∪ { (apple, t1), (apple, t2) }
     = { (apple, t1), (apple, t2) }

Lookup(apple) = true  ✅
```

Node A removed `(apple, t1)` — the addition it had seen. But Node B's new `(apple, t2)` was not observed by Node A, so Node A could not remove it. After merge, the newer add wins. This is the "observed-remove" semantic: you can only remove what you've seen.

**Q22. What is the tombstone approach (2P-Set) and why is OR-Set better?**
A: A **2P-Set** (Two-Phase Set) uses two G-Sets: one for additions (A) and one for tombstones/removals (R). An element is in the set if it's in A but not in R. Once an element is added to R (removed), it can never be re-added. The merge is set-union on both A and R.

Problems with 2P-Set:
- **No re-add**: removing an element is permanent. Once tombstoned, it's gone forever — which is unacceptable for most applications ("I removed an item from my cart and can never add it back").
- **Tombstone growth**: R accumulates forever; you can't garbage-collect tombstones safely without coordination.

OR-Set's unique-tag approach avoids both issues: re-adding an element just creates a new tag, and tombstones aren't needed at all (removed pairs just aren't in the state anymore). The cost is that each element in the set carries a set of tags — in the worst case, one tag per addition — but elements can be compacted to a single tag once it's known all nodes have synced.

**Q23. How does OR-Set handle the case where the same element is added on two different nodes concurrently?**
A: Each node generates a distinct tag on add, so both additions are represented as separate `(element, tag)` pairs. After merge, both pairs exist in the set. `Lookup(element)` returns true (correctly — the element was added), and the set contains both tags for that element. The duplicated tags are transparent to the user; `Lookup` just checks for existence of any pair. This is unlike a plain set where "same element twice" is idempotent — the tag separation makes the two additions distinguishable and both preservable.

## Section 5: Limitations and Trade-offs

**Q24. CRDTs guarantee convergence. What do they NOT guarantee?**
A: Several important things:
- **They don't guarantee strong consistency.** Two nodes may return different values for the same query at the same moment — they converge *eventually*, not immediately. CRDTs are an AP (availability + partition tolerance) solution in CAP terms.
- **They don't enforce domain invariants.** A PN-Counter won't prevent a stock count from going negative. An OR-Set won't prevent adding a duplicate username. Invariants that require cross-node coordination can't be expressed as CRDTs.
- **They don't give you the "right" semantic automatically.** The OR-Set's "add wins" is a design choice that may be wrong for your use case (e.g., a ban list where remove should win over add). There's a "remove-wins" variant, but you must choose deliberately.
- **They don't solve the "what did the user intend?" problem.** If two users concurrently edit a document's title, a CRDT can merge both edits — but the result might be nonsensical ("Hello WorldGoodbye"). Convergence ≠ correctness from a user perspective.

**Q25. What is the metadata growth problem in practice?**
A: Every unique tag in an OR-Set and every slot in a G-Counter/PN-Counter vector adds metadata. For:
- **G/PN-Counter**: the vector grows with the number of nodes. Fine for a 5-node cluster; problematic if "nodes" are user devices (millions of slots).
- **OR-Set**: each element carries tags for every addition. An element added and removed repeatedly accumulates tags. Without garbage collection (which requires coordination), the set state grows indefinitely.

Production systems (Riak's `riak_dt`, Redis's `CRDT` module) implement delta-CRDTs and compaction strategies, but these add implementation complexity. Pure CRDTs as described here are conceptually clean but operationally expensive at scale.

**Q26. When should you NOT use a CRDT?**
A:
- When you need **strong consistency** — e.g., "exactly one user gets the last seat on this flight." No CRDT can enforce a mutual exclusion invariant without coordination.
- When **conflicts are semantically meaningful and require human resolution** — e.g., two people editing the same legal contract. A CRDT will auto-merge; sometimes you want to surface the conflict and ask a human to resolve it.
- When **the data type doesn't fit the CRDT model** — arbitrary mutable objects, relational data with foreign key constraints, or any invariant that spans multiple fields atomically.
- When **simplicity beats availability** — if your system can tolerate brief unavailability during partitions, a strongly consistent system (Postgres, etcd) is simpler to reason about and debug than CRDT-based eventual consistency.

## Section 6: Practical Applications & Scenario Questions

**Q27. Where are CRDTs used in production systems today?**
A: Several real systems either use or expose CRDTs:
- **Riak** (Basho): Pioneer of production CRDTs — exposes G-Counter, PN-Counter, OR-Set, OR-Map, and LWW-Register as first-class data types at the database level.
- **Redis Enterprise**: CRDT-based multi-master replication for geo-distributed clusters — counters and sets replicate conflict-free across regions.
- **Cassandra**: Counters use a PN-Counter-like structure internally, though their implementation has historically had edge case bugs around counter resets.
- **Figma**: Uses CRDT-like structures for collaborative editing of vector graphics — concurrent edits to object properties are merged.
- **Automerge / Yjs**: CRDT libraries for collaborative text editing (used in apps like Actual Budget, Logseq, and various VS Code extensions).
- **Apple Notes / iCloud**: Uses operational-transform-adjacent structures (related to operation-based CRDTs) for offline-first sync.

**Q28. "You're building a distributed shopping cart in a microservices architecture. Users can add and remove items while offline. Design the data structure."**
A: An OR-Set is the natural fit — items can be added and removed, and "add wins" on concurrent conflict is the right user-facing semantic (if I added an item and a network glitch also processed an old remove, the item should still be in my cart). Design:
- Each cart is an OR-Set of `(item_id, quantity, tag)`.
- To handle quantity: either model each unit as a separate OR-Set element with a unique tag (simple but verbose), or pair the OR-Set with a PN-Counter per item for quantity (each item's presence is tracked by OR-Set, its quantity by PN-Counter).
- Cart state is replicated to multiple nodes; merges happen on partition healing.
- At checkout, serialize the merged state and validate business constraints (stock availability, pricing) with a strongly consistent system — CRDTs handle the cart's structure, not the checkout invariant.

**Q29. "Your analytics dashboard shows a 'total clicks' counter that's served from 3 geographically distributed nodes. Users report the count sometimes goes down. What's the bug and how do you fix it?"**
A: Classic sign of LWW on a counter — the "total clicks" is stored as a plain integer, and when two nodes with different values sync, the lower-timestamped value overwrites the higher one, losing increments. The counter appears to decrease because the "winning" node's value is stale.

Fix: replace the plain integer with a G-Counter (or PN-Counter if decrements are needed). Each node maintains its own slot in the vector, never touching other nodes' slots. On sync, the merge is element-wise max — no increment is ever lost, and the value can only increase (for G-Counter) or monotonically converge (for PN-Counter). The query (sum of all slots) will always be ≥ any previous query result seen by any node.

**Q30. "A teammate suggests using an OR-Set to implement a distributed ban list (banned users are removed from the allowed-users set). What's the subtle problem?"**
A: The OR-Set's "add wins" semantic is backwards for a ban list. If a user is added to the allowed-users set and an admin concurrently bans them (removes them from the set), the OR-Set's merge will *keep* the user (add wins over concurrent remove) — exactly the wrong outcome for a security-sensitive ban list.

For a ban list, you want **remove wins** (also called "delete wins") semantics. Options:
- Invert the model: maintain a *ban set* (OR-Set of banned users) and add to it when banning. "Add to the ban set" wins over concurrent attempts to un-ban — which is now the safe default.
- Use a 2P-Set variant where removes are permanent — over-restricted but safe for security contexts.
- Use an LWW-Register per user with a careful timestamp strategy (e.g., "banned" state with a later timestamp always wins).

The lesson: CRDT semantics must match your application semantics. OR-Set's "add wins" isn't universal — always ask "when there's a conflict, which operation should win, and is that right for my domain?"

## Quick Reference: The Three CRDTs

| Property              | G-Counter                       | PN-Counter                        | OR-Set                                    |
|---                    |---                              |---                                |---                                        |
| Supports              | Increment only                  | Increment + Decrement             | Add + Remove (add wins on conflict)       |
| Internal state        | Vector of N ints (one per node) | Two vectors of N ints (P and N)   | Set of (element, unique-tag) pairs        |
| Merge function        | Element-wise max                | Element-wise max on P and N       | Set union                                 |
| Query                 | sum(vector)                     | sum(P) - sum(N)                   | Exists any (e, *) pair                    |
| Can go "backward"?    | No — only grows                 | Yes — value can decrease or go <0 | No — elements only disappear on remove    |
| Metadata overhead     | O(N nodes)                      | O(N nodes) × 2                    | O(additions) — tags per element           |
| Classic use case      | View/click counters             | Inventory, likes, vote tallies    | Shopping carts, presence, shared playlists|

## The Core Mental Model

```
G-Counter:   Each node owns one slot. Increment your slot. Merge = max per slot. Query = sum.
PN-Counter:  Two G-Counters. Increment P-slot. Decrement N-slot. Query = sum(P) - sum(N).
OR-Set:      Tag every add with a UUID. Remove = delete observed tags. Merge = union. Add wins.
```

Every CRDT is built on the same idea: **design your state so that the merge function is commutative, associative, and idempotent — then concurrent updates can never conflict.**

---

**Tip for the interview:** Senior interviewers want to see two things beyond the mechanics: (1) you understand *why* the merge function works (why max and not sum for counters; why unique tags and not plain sets); and (2) you know the limits — CRDTs don't enforce domain invariants, "add wins" isn't always right, and metadata growth is a real operational problem. The strongest answers connect to something real: "In a past project we stored a counter as an integer in Redis and lost counts during failover — a G-Counter structure would have prevented that because merges are always safe." Mechanics + limits + real-world grounding is the 5 YOE answer.
