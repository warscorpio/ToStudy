# Raft Consensus Algorithm: Leader Election, Log Replication, Safety Properties — Interview Q&A (5 YOE Level)

---

## Section 1: Why Consensus Is Hard

**Q1. What problem does a consensus algorithm solve, and why is it necessary?**
A: A consensus algorithm solves the problem of getting a group of distributed nodes to agree on a single value — and to agree on a sequence of values over time — even when some nodes crash, messages are lost, and the network is unreliable. Without consensus, distributed systems face the fundamental problem that every node independently decides what is "true," leading to divergent states, split-brain, and data loss.

The canonical use case: a replicated state machine. You want N nodes to all execute the same sequence of operations in the same order, so they all end up in the same state. If Node 1 applies operations [A, B, C] and Node 2 applies [A, C, B], they diverge even if they apply identical operations. Consensus is the mechanism that forces agreement on the *order* of operations before any node applies them. Every strongly-consistent distributed system — replicated databases, distributed locks, leader election — relies on a consensus algorithm at its core, whether explicitly (Raft, Paxos) or implicitly (two-phase commit, quorum writes).

**Q2. What is the FLP impossibility result, and what does it mean for Raft?**
A: The FLP impossibility result (Fischer, Lynch, Paterson, 1985) proves that in a fully asynchronous network where even one node may fail by crashing, no deterministic consensus algorithm can guarantee both safety (all nodes agree on the same value) and liveness (the algorithm always terminates in finite time). The proof is that you can never distinguish a crashed node from a very slow one — so any algorithm that waits for all nodes risks waiting forever, and any algorithm that proceeds without all nodes risks proceeding with inconsistent information.

What this means for Raft: Raft does not violate FLP because it is not a purely asynchronous algorithm. Raft relies on timing — specifically, on timeouts. It assumes that eventually, the network will be well-behaved enough for a leader to be elected and for messages to get through in a reasonable time. Raft sacrifices liveness under adversarial network conditions (it may not make progress if the network continuously drops messages or partitions keep forming) in exchange for always preserving safety (it never allows two nodes to commit different values to the same log position). FLP says you can't have both; Raft chooses safety and accepts that liveness is conditional on reasonable network behavior.

**Q3. What is Paxos, and why did Raft need to be invented?**
A: Paxos (Lamport, 1989) is the original practical consensus algorithm — the first to prove that consensus can be achieved in an asynchronous system tolerating crash failures. It remains the theoretical foundation for distributed consensus. Google Chubby, Apache Zookeeper (Zab, a Paxos variant), and many Google internal systems are built on Paxos.

The problem with Paxos: it is famously difficult to understand and even more difficult to implement correctly. The original paper describes single-value Paxos (one round of consensus for one value). Extending it to Multi-Paxos (consensus over a sequence of values — which is what replicated state machines need) requires filling in many gaps the original paper doesn't address: leader election, log management, membership changes, and reconfiguration — all of which are left to the implementer. The result is that every Paxos implementation is slightly different, there's no "reference implementation," and the algorithm's subtleties have caused correctness bugs in production systems.

Raft (Ongaro and Ousterhout, 2014) was explicitly designed as an alternative to Paxos with understandability as the primary design goal. The authors ran controlled experiments showing that students who learned Raft scored significantly better on comprehension tests than those who learned Paxos. Raft achieves the same safety properties as Multi-Paxos but decomposes the problem into three clearly defined sub-problems — leader election, log replication, and safety — each with a clear mechanism. This understandability made Raft far more widely adopted for new systems: etcd, CockroachDB, TiKV, Consul, and many others use Raft rather than Paxos.

## Section 2: Raft's Core Decomposition

**Q4. What are the three sub-problems Raft decomposes consensus into?**
A: Raft's key design insight is that consensus over a log can be decomposed into three largely independent sub-problems:

- **Leader Election** — at any given time, exactly one node is the leader. The leader has full authority over the log: it receives all client writes, decides the order of log entries, and replicates entries to followers. If the leader fails, a new one is elected. The mechanism for election and the guarantee that only one leader exists at a time is one sub-problem.
- **Log Replication** — once a leader exists, it accepts log entries from clients and replicates them to followers. The leader must ensure that followers' logs become identical to its own. The mechanism for replication, for handling follower failures, and for committing entries (making them permanent) is the second sub-problem.
- **Safety** — the set of properties that guarantee correctness regardless of timing, failures, or message loss. The most critical: if a log entry has been committed at a given index, no future leader will ever commit a different entry at that index. The mechanisms that guarantee safety are the third sub-problem.

This decomposition is deliberate: each sub-problem has a clear specification, a clear mechanism, and a clear invariant. Compare this to Paxos, where the three concerns are interleaved in ways that make it hard to reason about any one of them in isolation.

**Q5. What are the three roles a node can have in Raft, and how do they transition?**
A: Every Raft node is in exactly one of three states at any time:

- **Leader** — exactly one per term (usually; during an election there may be zero temporarily). Receives all client requests, appends entries to its log, and sends AppendEntries RPCs to all followers. Also sends heartbeats (empty AppendEntries) to prevent followers from timing out and starting an election.
- **Follower** — the default state. Passively receives AppendEntries from the leader (log replication and heartbeats) and RequestVote from candidates (voting in elections). If a follower doesn't hear from the leader within the election timeout, it becomes a candidate.
- **Candidate** — a node that believes the leader has failed and is trying to get itself elected as the new leader. Increments its term, votes for itself, and sends RequestVote RPCs to all other nodes.

Transitions:
```
Follower ──(election timeout)──→ Candidate ──(wins majority)──→ Leader
                                      │                              │
                                      └──(discovers higher term)─────┘
                                      └──(split vote / timeout)──→ Follower (retry)
Leader ──(discovers higher term)──→ Follower
```

The critical constraint: a node immediately reverts to follower when it discovers a message with a higher term number than its own. This is how stale leaders are deposed when they rejoin after a partition.

**Q6. What is a "term" in Raft, and what role does it play?**
A: A term is a logical clock — a monotonically increasing integer that acts as Raft's version of time. Terms are the mechanism by which Raft detects stale leaders and outdated information.

Key properties:
- Terms begin with an election. If a candidate wins, it leads for the rest of the term. If no candidate wins (split vote), the term ends and a new election (new term) begins.
- Every RPC in Raft carries the sender's current term. If a receiver sees a term higher than its own, it immediately updates its term and reverts to follower. If a receiver sees a term lower than its own, it rejects the RPC.
- Terms that have no leader (failed elections) simply don't produce any committed log entries — they're gaps in the leadership timeline.
- Terms provide a simple answer to "is this leader's authority current?" — if the leader's term matches the receiver's term, the leader is legitimate. If not, something has changed.

Terms are the foundation of Raft's stale-leader detection. When a leader is partitioned away, the rest of the cluster elects a new leader in a higher term. When the old leader reconnects, it sees RPCs with a higher term, reverts to follower, and the split-brain is resolved automatically.

## Section 3: Leader Election

**Q7. Walk through the leader election process step by step.**
A: The election process is triggered by a follower's election timeout:

1. **Timeout fires** — a follower has not received an AppendEntries (heartbeat or actual entries) from the leader within the election timeout window (typically 150–300ms, randomized per node). It concludes the leader has failed.
2. **Become candidate** — the follower increments its current term (e.g., term 4 → 5), transitions to candidate state, and votes for itself.
3. **Send RequestVote RPCs** — the candidate sends RequestVote to all other nodes in parallel, including: its current term, its node ID, and the index and term of the last entry in its log (the "log completeness" information — used by voters to reject candidates with incomplete logs).
4. **Votes are cast** — each node that receives RequestVote grants its vote if: (a) it hasn't already voted in this term, and (b) the candidate's log is at least as up-to-date as the voter's log. Each node votes for at most one candidate per term.
5. **Candidate wins** — if the candidate receives votes from a majority of nodes (including itself), it becomes the leader for this term. It immediately sends AppendEntries heartbeats to all nodes to assert its authority and reset their election timers.
6. **Split vote** — if no candidate wins a majority (two candidates split the votes), the term ends with no leader. Each candidate's election timer fires again (randomized), and a new election begins in the next term.
7. **Stale candidate** — if a candidate receives an AppendEntries from a node with a term ≥ its own while waiting for votes, it recognizes a legitimate leader has been elected and reverts to follower.

**Q8. Why are election timeouts randomized, and what happens if they aren't?**
A: If all nodes had the same election timeout, they would all time out at the same moment when the leader fails — all becoming candidates simultaneously, all voting for themselves, and all splitting the vote indefinitely. The system would never elect a leader (a liveness failure, though not a safety failure).

Randomized timeouts break this symmetry: each node picks a random timeout in a range (e.g., 150–300ms). The first node to time out becomes a candidate and sends RequestVote RPCs. If it can reach a majority before any other node times out, it wins before a competing candidacy begins. The other nodes receive its AppendEntries heartbeat, reset their timers, and remain followers.

The range must be chosen carefully:
- **Lower bound** — must be significantly larger than the typical network round-trip time. If the timeout fires before a heartbeat can arrive, the follower incorrectly concludes the leader is dead. Typically 10–20× the expected one-way network latency.
- **Upper bound** — determines the worst-case election time. If the lower bound is 150ms and the upper bound is 300ms, the worst-case gap between two candidates timing out simultaneously is 150ms — enough for the first to gather votes before the second starts. The range should be large enough to make simultaneous timeouts unlikely.
- **Gap relative to heartbeat interval** — the election timeout must be meaningfully larger than the heartbeat interval (the leader's rate of sending AppendEntries). If heartbeats are every 50ms, timeouts at 150–300ms give 3–6 heartbeat intervals of grace before a follower suspects failure.

**Q9. What is the "vote grant" condition, and why does it include log completeness?**
A: A node grants a vote to a candidate only if two conditions are both satisfied:

1. **The node hasn't voted for anyone else in this term** — one vote per node per term. This prevents a node from helping two candidates win the same term.
2. **The candidate's log is at least as up-to-date as the voter's log** — "at least as up-to-date" has a specific definition in Raft: compare the term of the last log entry first; higher term wins. If equal, longer log wins.

The log completeness condition is critical for safety. Without it, a node with a stale log (missing committed entries) could become leader and overwrite those committed entries with new ones — violating the fundamental safety guarantee. By requiring that a leader's log be at least as complete as a majority of nodes' logs, Raft ensures:

- A candidate can only win if a majority votes for it.
- A majority of nodes have seen all committed entries (by definition of commit — entries committed only after a majority acknowledges them).
- Therefore, the elected leader must have seen all committed entries — it can't be missing anything that was committed.

This is the "Election Restriction" — the safety property that prevents a candidate with an incomplete log from becoming leader and corrupting the committed log.

**Q10. How does Raft guarantee that at most one leader is elected per term?**
A: Two constraints together enforce this:

1. **Each node votes for at most one candidate per term** — enforced by each node persisting its vote to stable storage before responding. If a node crashes and restarts mid-election, it recovers its vote from disk and doesn't vote again. This prevents a node from accidentally voting for two candidates if it crashes and restarts.
2. **A candidate needs a majority to win** — any two majorities in a cluster of N nodes share at least one common member (by the pigeonhole principle: two groups of size ≥ ⌊N/2⌋+1 from N total must overlap). That common member voted for one candidate — it cannot have voted for the other. Therefore, only one candidate can assemble a majority in any given term.

This is a clean mathematical guarantee: two majorities must overlap; each node votes once per term; therefore only one candidate can win a majority.

## Section 4: Log Replication

**Q11. Walk through the log replication process from client request to committed entry.**
A: Once a leader is elected, the log replication sequence is:

1. **Client sends a request** — the client sends a command (e.g., "set x = 5") to the leader. If the client contacts a follower, the follower redirects to the leader.
2. **Leader appends to its local log** — the leader appends the command as a new log entry at the next index. The entry is not yet committed — it's just in the leader's log. The entry carries the current term number.
3. **Leader sends AppendEntries RPCs** — the leader sends AppendEntries in parallel to all followers. The RPC carries: the new entry, the term of the entry, the index and term of the entry immediately preceding it (the "consistency check" fields), and the leader's current commit index.
4. **Followers append and respond** — each follower performs a consistency check (described in Q12). If it passes, the follower appends the entry to its local log and responds with success. If it fails, it responds with failure.
5. **Leader counts acknowledgments** — once the leader receives success from a majority of nodes (including itself), the entry is committed. The leader updates its commit index.
6. **Leader responds to client** — the leader applies the committed entry to its state machine and returns the result to the client.
7. **Followers learn of commit** — on the next AppendEntries (heartbeat or new entry), the leader includes its updated commit index. Followers advance their own commit index to match and apply committed entries to their state machines.

**Q12. What is the "consistency check" in AppendEntries, and why is it necessary?**
A: Each AppendEntries RPC carries two "previous entry" fields: `prevLogIndex` (the index of the log entry immediately before the new entries) and `prevLogTerm` (the term of that entry). The follower checks: "does my log contain an entry at `prevLogIndex` with term `prevLogTerm`?" If yes, the follower appends the new entries. If no, the follower rejects the RPC.

Why this is necessary: it is the inductive step that ensures log consistency. If a follower's log matches the leader's up to index K (the consistency check), and the leader sends entries for index K+1 onward (with a matching prevLogIndex/prevLogTerm), then after appending, the follower's log matches the leader's through K+1. By induction, if the check ever passes, the follower's log is identical to the leader's for all entries up to and including the new ones. This invariant is called the **Log Matching Property**: if two log entries in any two nodes' logs have the same index and term, then the logs are identical for all entries up to that index.

**Q13. What happens when a follower's log is inconsistent with the new leader's log?**
A: After a leader election, some followers may have logs that are behind or even contain entries that conflict with the new leader's log (entries that were replicated by an old leader but never committed). The new leader must bring all followers into alignment with its own log.

The mechanism — **log repair via nextIndex:**

1. The leader maintains a `nextIndex` for each follower — the index of the next log entry it will try to send to that follower. Initially set to `leader's last log index + 1` (optimistically assuming the follower is up to date).
2. The leader sends AppendEntries with the entry at `nextIndex`. If the consistency check fails (the follower rejects it), the leader decrements `nextIndex` and retries.
3. This continues, walking backward, until the leader finds the point where the follower's log agrees with its own.
4. From that point forward, the leader sends all entries from that agreement point to the end of its log. The follower overwrites any conflicting entries with the leader's entries.
5. The follower's log now matches the leader's from the agreement point onward.

The critical safety point: the entries that get overwritten on the follower were *never committed* — no majority ever acknowledged them. Only uncommitted entries can be overwritten. Committed entries, by definition, were acknowledged by a majority and the new leader has all of them (guaranteed by the Election Restriction). This is why safety is preserved: committed data is never lost; only speculative, uncommitted entries are replaced.

**Q14. Why does Raft require log entries to be stored on stable storage before responding to AppendEntries?**
A: Before a follower sends a success response to AppendEntries, it must write the log entry to durable storage (disk) — not just memory. The reason: if the follower crashes immediately after writing the entry to memory but before persisting it, it reboots with no knowledge of the entry. If the leader counted that follower's in-memory acknowledgment toward a quorum and committed the entry, the committed entry is now lost on that node. With enough such crashes, the committed entry could be lost from a majority of nodes — a safety violation.

The three pieces of state Raft requires to persist before sending any response:
- **Current term** — so a restarted node doesn't vote for a candidate in a term it's already voted in.
- **Voted for (in current term)** — so a restarted node doesn't vote twice in the same election.
- **Log entries** — so committed entries survive crashes.

Everything else (commit index, leader identity, role) can be derived on restart. This persistence requirement is why the disk I/O path is on the critical latency path for Raft: every AppendEntries requires a `fsync` to disk before the follower can acknowledge. Systems using Raft (etcd, CockroachDB) use strategies like write-ahead logs with group commit, NVMe SSDs, and battery-backed DRAM to minimize this latency.

## Section 5: Safety Properties

**Q15. What are Raft's core safety properties, and what guarantees do they provide?**
A: Raft guarantees five safety properties. The most important are:

- **Election Safety** — at most one leader can be elected in any given term. Guaranteed by: one vote per node per term + majority requirement (proof in Q10).
- **Leader Append-Only** — a leader never overwrites or deletes entries in its log; it only appends. Guaranteed by: the leader only writes new client entries and never reverses its own log.
- **Log Matching** — if two logs contain an entry with the same index and term, then the logs are identical in all entries up through that index. Guaranteed by: the AppendEntries consistency check (Q12).
- **Leader Completeness** — if a log entry is committed in a given term, that entry will be present in the logs of all leaders for all higher-numbered terms. Guaranteed by: the Election Restriction (vote grant condition requires log completeness).
- **State Machine Safety** — if a node has applied a log entry at a given index to its state machine, no other node will ever apply a different log entry at that index. Guaranteed by: derived from Leader Completeness + Log Matching.

The most critical property for application designers is **State Machine Safety** — it is the end-to-end guarantee that all nodes execute the same operations in the same order and therefore end up in identical states. Every other property exists to support this one.

**Q16. What is the "committed entry" definition in Raft, and why is a majority required?**
A: A log entry is committed when the leader has replicated it to a majority of nodes in the current term. Formally: the leader increments its commit index when it has received success responses from a majority (including itself).

Why majority? Two reasons:

- **Durability across failures** — a cluster of N nodes can tolerate ⌊N/2⌋ simultaneous failures and still have a majority available. A committed entry is on a majority of nodes — even if ⌊N/2⌋ nodes crash, the majority that survives still has the entry.
- **Leader election guarantee** — any new leader must receive votes from a majority. Any two majorities share at least one common member. That common member has the committed entry in its log. Because the vote grant condition requires the candidate's log to be at least as up-to-date as the voter's, the new leader must have the committed entry. The entry cannot be lost across a leadership change.

This interplay between commit quorum and election quorum is Raft's core safety mechanism. Both use "majority" for exactly this reason — to guarantee the overlap.

**Q17. What is the "leader completeness" property, and why can't a leader commit entries from previous terms directly?**
A: Leader Completeness guarantees that an elected leader has all committed entries in its log. But there's a subtle hazard: what about entries from previous terms that are in the leader's log but may not be committed?

Scenario: 
- Term 3, Leader L1 replicates entry E to 2 of 5 nodes (not yet a majority), then crashes.
- Term 4, Leader L2 is elected (it had E in its log). L2 replicates a new entry F. Can L2 declare E committed just because a majority now has it?

The answer — and this is one of Raft's subtlest points — is **no**. Raft prohibits a leader from committing log entries from previous terms by counting replicas alone. The reason: in a later scenario, a different node without E could become leader in term 5 (if term 4 ended without E being widely replicated), overwrite E on some followers, and then E is gone — even though a majority of nodes had it at some point.

Raft's fix: **a leader only directly commits entries from its own current term**. Once the leader commits a current-term entry (by getting a majority to acknowledge it), all prior entries that precede it in the log are implicitly committed too — by the Log Matching Property. The current-term entry acts as a "seal" that retroactively commits all preceding entries. This is why a new Raft leader typically appends a no-op entry to its log immediately after election — to seal and commit all inherited prior-term entries as quickly as possible.

**Q18. What is the "no-op entry" a new leader appends, and why?**
A: Immediately after winning an election, a Raft leader appends a no-op (empty) log entry with its current term and replicates it to followers. Reasons:

- **Commit inherited entries** — as described in Q17, entries from prior terms cannot be directly committed. By appending a no-op in the current term and replicating it to a majority, the leader implicitly commits all prior entries that precede the no-op in the log.
- **Establish commit index** — until the leader commits something in its current term, its commit index may be stale. The no-op entry, once committed, brings the commit index up to date.
- **Unblock read linearizability** — in some implementations, a leader won't serve reads until it has committed at least one entry in its term (confirming it's still the leader). The no-op ensures this happens immediately after election rather than waiting for the first client request.
- **Notify followers of leadership** — the no-op AppendEntries is the first message that tells followers who the new leader is and what term it's in. It resets their election timers and informs them of the commit index.

The no-op is a small but essential piece of Raft's correctness — without it, inherited prior-term entries might remain uncommitted indefinitely, and the commit index wouldn't advance until the first real client request.

## Section 6: Cluster Membership Changes

**Q19. Why is changing cluster membership (adding or removing nodes) dangerous in Raft?**
A: Changing the cluster size changes the definition of "majority" — and if nodes switch to the new membership definition at different times, you can briefly have two different majorities that don't overlap, enabling split-brain.

Example: a 3-node cluster (majority = 2) grows to 5 nodes (majority = 3). If some nodes switch to 5-node majority rules while others still use 3-node majority rules:
- The 3-node majority side can elect a leader with 2 votes (under old rules).
- The 5-node majority side can elect a different leader with 3 votes (under new rules).
- Both are "legitimate" under their respective views of membership — two simultaneous leaders.

This is why membership changes can't be applied as a simple configuration update pushed to all nodes simultaneously. Nodes will apply the update at slightly different times due to network delays, and the window where some have switched and others haven't creates the overlap gap.

**Q20. What is "joint consensus" (the two-phase membership change approach), and how does it prevent the overlap problem?**
A: Joint consensus is Raft's original approach to safe membership changes. It introduces an intermediate configuration called `C_old,new` — a joint state where the cluster operates under *both* old and new membership rules simultaneously:

- **Phase 1** — the leader appends a special log entry for `C_old,new` (the joint configuration). During this phase, any decision (leader election, log commit) requires a majority of *both* the old cluster AND the new cluster to agree. This prevents either old-rules-only or new-rules-only majorities from acting unilaterally.
- **Phase 2** — once `C_old,new` is committed, the leader appends a `C_new` entry. Once committed, the cluster operates under new rules only. Old nodes not in the new cluster can be shut down.

The key safety property: at no point during the transition can two incompatible majorities form. Any election or commit during Phase 1 requires agreement from a majority of both old and new — the intersection of both guarantees no split.

The simpler alternative used in practice (etcd, many real Raft implementations): **single-server changes**. Change membership one node at a time. Adding one node to a 3-node cluster (3→4) and then to a 4→5 cluster, one at a time, is safe because adding or removing a single node never creates a window where two incompatible majorities can exist. This approach is operationally simpler and sufficient for most real-world scenarios.

## Section 7: Performance and Practical Characteristics

**Q21. What is the write latency profile of a Raft-based system, and what determines it?**
A: A write in a Raft cluster takes at minimum one round trip from leader to a quorum of followers, plus disk write time:

```
Total write latency ≈ disk_write_time + max(RTT to quorum nodes)
```

In a 3-node cluster, the leader writes to disk and sends AppendEntries to 2 followers in parallel. The commit happens when the *faster* of the two followers acknowledges (since either one, combined with the leader, forms a majority of 3). The `max` is the round-trip to the faster follower plus that follower's disk write time.

Factors that determine this latency:
- **Network RTT between leader and followers** — intra-datacenter: 0.1–1ms; cross-AZ: 1–5ms; cross-region: 50–200ms. Cross-region Raft clusters have correspondingly high write latency and are rare for latency-sensitive workloads.
- **Disk fsync latency** — a spinning disk fsync is 5–10ms. An NVMe SSD is 100–500µs. This is often the dominant term for local clusters, which is why Raft-based databases aggressively use NVMe SSDs and group commit (batching multiple writes into one fsync).
- **Batch size** — if the leader batches multiple client requests into one AppendEntries RPC, throughput increases dramatically with only a small increase in per-request latency. Systems like etcd and CockroachDB batch aggressively.

**Q22. What is "leader stickiness," and how does it affect Raft cluster behavior?**
A: Leader stickiness refers to the operational tendency for the same node to remain leader for long periods — Raft strongly favors the incumbent leader as long as it remains healthy and reachable. This is by design: unnecessary leader changes are expensive (election latency, log repair, no-op commit) and destabilizing.

Stickiness has practical consequences:
- **Hot leader** — in a write-heavy workload, the leader is the bottleneck. All writes go through the leader; followers only replicate. Unlike some AP systems (Cassandra, DynamoDB) that can spread writes across nodes, a Raft cluster's write throughput is bounded by what one node can sustain.
- **Read scalability** — naive reads can also go through the leader (for linearizability). Followers can serve stale reads ("follower reads") but require additional mechanisms (lease reads or follower reads with linearizable guarantees) to serve linearizable reads without asking the leader.
- **Geographic implications** — if the leader is in us-east and most clients are in eu-west, all writes incur cross-region latency. Raft doesn't inherently route the leader to where clients are — operational intervention (manual leader transfer) may be needed.

**Q23. What is a "read index" optimization, and why is it needed for linearizable reads from followers?**
A: By default, a Raft cluster routes all reads through the leader to guarantee linearizability — the read is treated as a no-op write, committed through the log, ensuring the read reflects the latest committed state. This is safe but expensive: reads consume log bandwidth and add latency.

The ReadIndex optimization (described in the Raft thesis) allows the leader to serve reads without writing to the log:

1. The leader records its current commit index as the "read index."
2. The leader sends heartbeats to a quorum of followers to confirm it is still the legitimate leader (not a stale leader from a previous term serving stale reads).
3. Once the quorum confirms (proving the leader hasn't been deposed), the leader waits until its state machine has applied all entries up to the read index, then serves the read from local state.

This halves the number of disk writes per read (no log entry needed) and enables **follower reads**: a follower can request the read index from the leader, apply log entries up to that index locally, and serve the read from its own state machine. This distributes read load across all nodes while maintaining linearizability — eliminating the hot-leader read problem without sacrificing correctness.

## Section 8: Where Raft Is Used and How It Maps to Real Systems

**Q24. Where is Raft used in practice, and what system-level property does it provide in each?**
A: Raft's correctness guarantee — that all nodes agree on the same log of operations in the same order — maps to different high-level properties depending on the system:

- **etcd** — the consensus backbone of Kubernetes. Stores all cluster state (pod definitions, service configs, secrets). Raft ensures that all etcd nodes agree on the cluster state, so any API server querying etcd sees a consistent view. A split-brain in etcd would mean different API servers see different "truths" about what pods are running — catastrophic for a production cluster.
- **CockroachDB** — each range (a ~64MB chunk of the key space) is replicated across 3 or 5 nodes via a Raft group. Writes to a range go through that range's Raft leader. Raft provides the per-range write ordering and durability. The distributed SQL layer coordinates across ranges for transactions. This is Raft at fine granularity — thousands of Raft groups running concurrently in a large cluster.
- **TiKV (TiDB's storage engine)** — same architecture as CockroachDB: key-space sharded into regions, each region is a Raft group. TiDB uses TiKV as its distributed storage layer, with Raft providing per-region consistency.
- **Consul** — uses Raft for service discovery and KV store consistency. The Raft log records service registration/deregistration events. All Consul servers agree on which services are registered and healthy.
- **Apache Kafka (KRaft mode)** — Kafka's metadata (topic configs, partition assignments, broker states) is now managed by a Raft-based metadata quorum (KRaft), replacing the previous Zookeeper dependency. The Raft log records metadata changes; all controllers agree on cluster topology.

**Q25. What is the difference between Raft and Zookeeper's Zab protocol?**
A: Zab (Zookeeper Atomic Broadcast) and Raft are both crash-tolerant consensus protocols designed for replicated state machines. They are architecturally similar — both use a single leader, majority quorums, and a write-ahead log — but differ in several ways:

- **Design goals** — Raft was designed for understandability (as a reaction to Paxos's complexity). Zab was designed specifically for Zookeeper's use case — high read throughput for a hierarchical namespace — and is less general.
- **Recovery semantics** — in Zab, the new leader's recovery protocol (synchronization phase) involves broadcasting its entire log to all followers, ensuring complete alignment before any new writes are accepted. Raft's recovery is more incremental (per-follower nextIndex regression), which is faster when only some followers are behind.
- **Epoch vs term** — Zab uses "epochs" as its logical clock concept; Raft uses "terms." Functionally equivalent, different nomenclature.
- **Read handling** — Zookeeper (Zab) by default serves reads from any node without quorum, providing "stale reads" for throughput. Raft-based systems typically route reads through the leader or use ReadIndex for linearizable reads. Zookeeper's `sync()` API call can force a read to be linearizable.
- **Practical adoption** — Raft is now more widely adopted for new systems due to its cleaner specification and better reference implementations. Zab remains Zookeeper-specific.

**Q26. How does Raft interact with the CAP theorem in practice?**
A: Raft-based systems are CP by design — they choose consistency over availability during a partition. This is not a coincidence; it's inherent to how Raft works:

- **Minority partition becomes unavailable** — if a network partition leaves fewer than a majority of nodes on one side, that side's Raft leader (if it's there) cannot commit entries (can't reach quorum). If that side has no leader, it can't elect one (can't win a majority vote). The minority partition stops accepting writes — it is unavailable.
- **Majority partition continues** — the majority side elects a leader (can win a majority vote) and continues committing entries. It is available and consistent.
- **No split-brain** — the minority can't commit anything (no quorum). The majority commits with a new leader if the old one is on the minority side. Safety is never violated.

This CP behavior is appropriate for Raft's use cases: configuration stores, coordination services, and databases where inconsistency is worse than unavailability. It is the wrong choice for systems where availability must be preserved during partitions (social feeds, recommendation systems, shopping carts) — those systems should not use Raft.

The throughput limitation also follows from CP: all writes go through the quorum, which adds coordination latency and caps write throughput at what a single leader can sustain. AP systems (Cassandra, DynamoDB) achieve higher write throughput by removing this coordination requirement — at the cost of the consistency guarantees Raft provides.

## Section 9: Scenario Questions

**Q27. "A 5-node Raft cluster has a network partition that splits it 3/2. What happens on each side?"**
A: With 5 nodes, majority = 3:

**Majority side (3 nodes):**
- If the current leader is on this side: it can still reach a quorum (2 followers + itself = 3). It continues committing entries and serving clients normally.
- If the current leader is on the minority side: these 3 nodes don't receive heartbeats and time out. They elect a new leader (one of the 3 times out first, wins votes from the other 2, and has the majority of 3). The new leader appends a no-op and begins serving clients. Term number increments.
- This side remains fully operational throughout — consistent and available for clients connected to it.

**Minority side (2 nodes):**
- If the current leader is here: it sends AppendEntries but can only reach 1 follower (1 + itself = 2, not a majority of 5). It cannot commit new entries. It continues to receive and buffer client requests but cannot respond to them (or returns errors depending on implementation). It keeps sending heartbeats and AppendEntries — they just can't achieve quorum.
- When the partition heals: the minority-side leader receives a message with the higher term from the majority side's new leader, immediately reverts to follower, and its uncommitted entries (buffered but not committed during the partition) are overwritten with the majority side's log.
- Clients connected to the minority side during the partition receive either errors or no response — they should be routed to the majority side.

**Q28. "How does a Raft cluster handle a leader that becomes very slow (not crashed, just slow) due to a GC pause?"**
A: A slow leader is one of the most insidious failure modes for Raft — the scenario Kleppmann's "fencing token" work highlights. The sequence:

1. Leader L enters a 20-second GC pause. It stops sending heartbeats.
2. Followers time out after ~300ms (election timeout). They elect a new leader (L2) in term N+1.
3. L2 begins committing entries. Clients connected to L2 receive responses.
4. L wakes from its GC pause. It still believes it is the leader in term N. It may try to commit entries (it was buffering client requests).
5. L sends AppendEntries. The followers reject them because their current term is N+1 > N.
6. L receives a response with term N+1, immediately reverts to follower. Its uncommitted entries are replaced by L2's log.

**The critical safety point:** any entries L buffered but never committed (because it couldn't reach quorum during the GC pause — it was sending heartbeats too slowly) are simply discarded. They were never committed (no quorum ever acknowledged them). Safety is preserved.

**The client-facing concern:** if a client received a success response from L for an entry L thought it committed (but hadn't actually committed because L paused before getting quorum), that client is wrong — the entry was never committed. This is why Raft leaders must not respond to clients until the entry is durably committed (quorum acknowledged). A leader that responds before getting quorum is violating the protocol and creating the appearance of success for entries that may be lost.

**Q29. "You're choosing between Raft-based CockroachDB and Cassandra for a financial transaction store. Walk through the decision."**
A: This is a CAP and consistency model decision, with Raft at its center:

**What Raft gives you (CockroachDB):**
- **Serializable isolation** — all transactions appear to execute one at a time, in some serial order. No dirty reads, no phantom reads, no write skew. The strongest ANSI isolation level.
- **Linearizable reads** — reads always reflect the latest committed write, globally. No stale reads.
- **Atomic cross-row transactions** — a transfer from account A to account B is atomic. Either both legs commit or neither does. Raft coordinates the per-range consensus; CockroachDB's transaction layer coordinates across ranges.
- **CP during partition** — minority partitions become unavailable. Clients on the minority side see errors, not wrong balances.

**What you give up:**
- **Write throughput ceiling** — all writes go through the Raft leader per range. Horizontal write scaling requires sharding (CockroachDB does this automatically, but there's a coordination cost per transaction that touches multiple ranges).
- **Write latency** — each write requires a quorum round-trip plus fsync. For a local 3-node cluster, this is ~1–5ms. For a geo-distributed cluster, it's 50–200ms per transaction.
- **Availability during partition** — minority nodes return errors during a partition.

**What Cassandra gives you:**
- High write throughput (writes go to any node, no leader bottleneck)
- Low write latency (with `ONE`, writes acknowledge after one node)
- AP during partition (all nodes respond, possibly with stale data)
- Tunable consistency per-query

**What you give up with Cassandra:**
- No multi-row atomic transactions (no "transfer $50 from A to B" atomicity)
- With `ONE`/`QUORUM`, stale reads are possible — a balance read may not reflect recent writes
- LWW conflict resolution — concurrent writes silently discard one value

**Decision for a financial transaction store:** CockroachDB (Raft). The core requirement of financial systems — atomicity, no double-spend, consistent balance reads — requires the guarantees Raft provides. Cassandra's AP model exposes you to exactly the stale-balance-read vulnerability that enables double-spend. The write latency and throughput costs are acceptable trade-offs for a financial use case.

**Q30. "A candidate loses an election, immediately increments its term again, and calls another election. What goes wrong?"**
A: This describes an "aggressive candidate" that repeatedly increments its term and re-runs for election without waiting for the proper timeout. The problem: term inflation disrupts the cluster even when a healthy leader exists.

The sequence:
1. A healthy leader L is serving in term 5.
2. Node C fails to win an election (split vote) in term 6. Instead of waiting, it immediately increments to term 7 and sends RequestVote.
3. The followers receive RequestVote for term 7. Per Raft rules, they update their term to 7 and revert to follower — even though L is healthy.
4. L receives a heartbeat response with term 7. L reverts to follower too.
5. The cluster has no leader. C tries to win term 7, may fail again, immediately moves to term 8, and the cycle repeats.

The cluster is stuck: the aggressive candidate continuously deposes the legitimate leader without winning an election. Throughput drops to zero. This is a liveness failure — not a safety failure (no incorrect data is committed), but the cluster stops making progress.

The Raft thesis addresses this with **Pre-Vote**: before incrementing its term and becoming a candidate, a node first runs a "pre-election" — it asks other nodes "would you vote for me in an election?" without actually changing any terms. If it can't win a pre-election (because a healthy leader's heartbeats are keeping everyone's timers reset), it doesn't start a real election. Only if it can win the pre-election (indicating the leader is genuinely unreachable) does it increment its term and run for real. Pre-Vote prevents term inflation from aggressive or isolated nodes disrupting a healthy cluster.

## Quick Reference: Raft in One Page

**Three sub-problems:**
```
Leader Election    →  at most one leader per term, guaranteed by majority vote + one vote per node
Log Replication    →  leader replicates entries to followers; committed when majority acknowledges
Safety             →  committed entries are never lost across leadership changes
```

**Five safety properties:**
```
Election Safety      →  at most one leader per term
Leader Append-Only   →  leaders only append, never overwrite
Log Matching         →  same index + same term → identical logs up to that point
Leader Completeness  →  leaders have all committed entries
State Machine Safety →  no two nodes apply different entries at the same log index
```

**Fault tolerance:**

| Cluster Size | Majority | Tolerated Failures |
|--- |--- |--- |
| 3 nodes | 2 | 1 failure |
| 5 nodes | 3 | 2 failures |
| 7 nodes | 4 | 3 failures |

Adding nodes beyond 5–7 increases fault tolerance marginally but increases quorum latency (more nodes to wait for). Most production Raft clusters use 3 or 5 nodes.

**Key RPCs:**
```
AppendEntries  →  leader → followers: replicate entries, send heartbeats, advance commit index
RequestVote    →  candidate → all nodes: request votes, carry log completeness info
```

**Persistence requirements (must survive crashes):**
```
current_term   →  prevents voting for two candidates in the same term after restart
voted_for      →  prevents double-voting in the same election after restart
log[]          →  prevents losing committed entries after restart
```

**Systems using Raft:**
```
etcd            →  Kubernetes cluster state
CockroachDB     →  per-range consensus for distributed SQL
TiKV            →  per-region consensus for TiDB
Consul          →  service discovery and KV store
Kafka (KRaft)   →  cluster metadata management
```

**Tip for the interview:** At 5 YOE level, Raft questions are not asking you to implement the algorithm — they're testing whether you understand *why* each mechanism exists and what breaks without it. The best answers explain the failure mode the mechanism prevents: "election timeouts are randomized to avoid split votes — without randomization all nodes time out simultaneously and vote for themselves indefinitely." Connect each mechanism to the safety property it enforces and the failure mode it prevents. The war story version is especially powerful: "we ran a 5-node etcd cluster and had a node with a JVM GC pause that kept triggering re-elections — we fixed it by tuning the election timeout to be 10× our 99th-percentile GC pause time." That level of operational grounding is what separates a 5 YOE answer from a textbook summary.
