# Replication Types: Synchronous vs Asynchronous vs Semi-Synchronous — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is database replication and what are its four primary purposes?**
A: Replication is the process of maintaining copies of the same data on multiple nodes, kept in sync as data changes. Its four primary purposes:
- **High availability (HA)**: if the primary node fails, a replica can take over, minimizing downtime. Replication is the technical foundation of any failover strategy.
- **Read scaling**: route read queries to replicas to offload the primary. The primary handles writes; replicas handle reads. Effective when reads dominate the workload.
- **Disaster recovery (DR)**: replicas in different data centers or regions survive a site-level failure. The replica is an up-to-date (or near-up-to-date) copy that can be promoted.
- **Geographic distribution**: serve reads from a replica closer to the user's region, reducing latency. Writes still go to a single primary; reads are localized.

**Q2. What is the replication log and why is it the mechanism behind all replication types?**
A: The replication log is the ordered, durable record of every change made to the primary's data. Replicas consume this log and apply changes in order, converging to the same state as the primary. The format varies by database: **MySQL** uses the binary log (binlog) — a record of SQL statements or row-level changes; **PostgreSQL** uses the Write-Ahead Log (WAL) — a record of physical page changes; **MongoDB** uses the oplog — a record of operations. All three replication types (synchronous, asynchronous, semi-synchronous) use the same replication log mechanism — they differ only in **when the primary acknowledges the write to the client** relative to when the log entry is durably on the replica.

**Q3. What is the fundamental trade-off that defines all three replication modes?**
A: The trade-off is between **durability guarantee** and **write latency**:
- Waiting for replicas to acknowledge before responding to the client → stronger durability (no data loss on primary failure), higher write latency (adds at least one network round trip per write).
- Not waiting → lower write latency, but a window of potential data loss if the primary fails before the replica catches up.

Every replication mode is a point on this spectrum. The question is: how much data loss risk is acceptable, and how much write latency can the application tolerate?

**Q4. What is RPO and RTO, and how does the choice of replication mode affect each?**
A:
- **RPO (Recovery Point Objective)**: the maximum acceptable amount of data loss measured in time. "We can tolerate losing at most 30 seconds of writes." With asynchronous replication, RPO equals the current replication lag at the moment of failure — could be seconds or minutes. With synchronous replication, RPO is zero — no committed write can be lost.
- **RTO (Recovery Time Objective)**: the maximum acceptable downtime before the system is restored. Replication mode affects RTO indirectly — a replica that is fully in sync with the primary promotes faster (no catch-up needed), reducing RTO. A lagging async replica must catch up before promotion, extending RTO.

Both RPO and RTO must be defined as explicit product and business requirements before choosing a replication mode. A financial ledger might require RPO = 0; a social media comment feed might tolerate RPO = 60 seconds.

**Q5. What is the difference between single-leader, multi-leader, and leaderless replication, and where do the three replication modes fit?**
A:
- **Single-leader (primary-replica)**: one node accepts all writes; replicas receive changes from the primary. Synchronous, asynchronous, and semi-synchronous are all variants of single-leader replication, differing in acknowledgment timing.
- **Multi-leader**: multiple nodes accept writes, each replicating to the others. Used for multi-region active-active setups. Introduces write conflict resolution complexity. Synchronous multi-leader is possible but latency across regions makes it impractical; async is the norm, with conflict resolution.
- **Leaderless (Dynamo-style)**: any node accepts writes; the write is considered successful when a quorum of nodes acknowledges it. Cassandra, DynamoDB, and Riak use this model. The quorum requirement (`W + R > N`) is a form of tunable durability that sits between async and sync — it is covered in the quorum section.

## Section 2: Asynchronous Replication

**Q6. How does asynchronous replication work mechanically?**
A: The primary writes to its local storage and its replication log, then **immediately acknowledges the write to the client** without waiting for any replica to confirm receipt. The replication log is sent to replicas in the background. Replicas apply changes as fast as they can, but there is no guarantee about when. At any moment, a replica may be seconds, minutes, or (under sustained write pressure) hours behind the primary.

The primary's acknowledgment carries an implicit promise: "I have durably stored this write on my local disk." It makes no promise about replicas. If the primary crashes before the replica receives the log entry, that write is permanently lost.

**Q7. What are the advantages of asynchronous replication?**
A:
- **Lowest write latency**: the primary does not block on network communication with replicas. The write path is as fast as writing to local disk.
- **Primary availability is independent of replica health**: if a replica is slow, overloaded, or offline, writes to the primary are completely unaffected. The primary never blocks waiting for a lagging replica.
- **Handles high-latency replica links**: when replicas are geographically distant (cross-region, cross-continent), the round-trip latency to a replica could be 100–300ms. Synchronous replication would add this latency to every write; async does not.
- **Simplicity**: no coordination protocol between primary and replica on the write path. The primary streams the log; replicas consume at their own pace.

**Q8. What are the disadvantages of asynchronous replication?**
A:
- **Data loss on failover**: if the primary crashes, writes that were acknowledged to clients but not yet received by the replica are permanently lost. The promoted replica's view of the world is behind the primary's last state.
- **Replication lag**: replicas serve stale data. A read from a replica may return data that is seconds, minutes, or hours old. Applications must tolerate this staleness or route reads carefully.
- **Failover complexity**: when a primary fails, the replica with the least lag is promoted. But "least lag" isn't zero — you must decide how much data loss to accept and whether to wait for the replica to catch up before promoting (extending RTO) or promote immediately (accepting data loss up to the lag).
- **Inconsistent reads**: different replicas may be at different points in the replication stream. A client reading from replica A then replica B may see the world go "backward" — reading newer data first, then older data.

**Q9. What is replication lag, how is it measured, and what causes it to grow?**
A: Replication lag is the delay between a change being committed on the primary and that change being applied on a replica. Measured as: `lag = primary_log_position - replica_applied_log_position`, often converted to seconds via `Seconds_Behind_Master` (MySQL) or `pg_stat_replication.write_lag / flush_lag / replay_lag` (PostgreSQL).

Causes of lag growth:
- **Write burst on primary**: the replica's I/O capacity can't keep up with the volume of changes being streamed, causing the applied position to fall behind.
- **Long-running queries on replica**: in MySQL (without parallel replication), a long `ALTER TABLE` or heavy read query on the replica blocks the replication SQL thread. Log entries accumulate in the relay log while the replica is occupied.
- **Network degradation**: packet loss, throttling, or bandwidth saturation between primary and replica slows log delivery.
- **Replica under-provisioned**: the replica has fewer CPU cores, slower disks, or less RAM than the primary, making it unable to apply changes at write speed.
- **Single-threaded replication**: older MySQL versions apply replication events single-threaded. High-concurrency write workloads on the primary (parallelized) are serialized on the replica, creating lag even with identical hardware.

**Q10. What are "read-your-own-writes," "monotonic reads," and "consistent prefix reads," and why do they matter for async replication?**
A: These are read consistency guarantees that async replication violates by default:
- **Read-your-own-writes**: after a user writes data, their subsequent reads should reflect that write. With async replication, a user who writes to the primary then reads from a lagging replica sees their own write disappear — they just posted a comment and it's not there. Fix: route reads for the writing user to the primary for a window after their write (sticky primary reads), or to a replica that is guaranteed to have applied the write.
- **Monotonic reads**: a user making multiple reads should not see time go backward — newer data on one read, then older data on the next. This happens if the same user's reads are routed to different replicas at different lag levels. Fix: pin each user's read requests to the same replica for the duration of a session.
- **Consistent prefix reads**: a user should see writes in the order they occurred. If write B depended on write A, a reader should never see B without also seeing A. In async replication, a replica may have applied B before A if they were on different tables or shards. Fix: application-level ordering guarantees or causal consistency.

## Section 3: Synchronous Replication

**Q11. How does synchronous replication work mechanically?**
A: The primary writes to its local storage and replication log, **sends the log entry to replicas**, and then **waits for all designated synchronous replicas to confirm they have durably written the log entry** before acknowledging the write to the client. Only after receiving acknowledgments from all synchronous replicas does the primary return a success response.

The acknowledgment confirms the replica has written the data durably to disk (fsync'd) — not just received it in memory. This means even if both the primary and the replica crash immediately after the ack, the write is not lost — it exists on at least two durable disks.

**Q12. What does "synchronous" mean precisely — is it about receiving the data or applying it?**
A: In most implementations, "synchronous" means the replica has **durably written the log entry to disk** (WAL flush confirmed), not necessarily that it has applied the change to its in-memory data structures or made it visible to queries on the replica. PostgreSQL's `synchronous_commit = on` waits for the WAL to be flushed to disk on the standby. The standby may still apply the change (make it queryable) a few milliseconds after the ack, but the data is safe — it will be applied. This distinction matters: a replica can be synchronous for durability purposes while still having a brief query-visibility lag.

**Q13. What are the advantages of synchronous replication?**
A:
- **Zero data loss (RPO = 0)**: every acknowledged write exists on at least two nodes' durable storage. A primary crash immediately after a write cannot lose that write — the replica has it.
- **Immediate failover**: on primary failure, the synchronous replica can be promoted instantly. It has every committed write — no lag to catch up, no data loss to reconcile.
- **Simplified application logic**: applications do not need to reason about replication lag or staleness. A read from the synchronous replica immediately after a write will reflect that write (if the replica has applied it, which it will have shortly after the ack).
- **Strong durability guarantee for regulated workloads**: financial systems, medical records, and legal documents often have explicit regulatory requirements for data durability that synchronous replication satisfies.

**Q14. What are the disadvantages of synchronous replication?**
A:
- **Write latency**: every write incurs at minimum one extra network round trip (primary → replica → primary) before the client receives a response. For replicas on the same LAN this adds ~1ms; across availability zones, 2–10ms; across regions, 50–300ms.
- **Primary availability is coupled to replica availability**: if a synchronous replica is offline, slow, or unreachable, **writes to the primary block indefinitely** waiting for an acknowledgment that never comes. The primary becomes unavailable due to a replica problem — a dramatic availability impact for a durability guarantee.
- **Throughput ceiling**: write throughput is limited by the slowest synchronous replica's acknowledgment rate, not just the primary's disk speed. A slow replica becomes a global write bottleneck.
- **Impractical across large distances**: adding 200ms of round-trip latency to every write is untenable for most user-facing applications. Synchronous replication is typically limited to nodes within the same data center or availability zone.

**Q15. How does PostgreSQL implement synchronous replication and what configuration options exist?**
A: PostgreSQL uses `synchronous_commit` and `synchronous_standby_names` parameters:
- `synchronous_commit = on` (default): wait for WAL flush on primary and WAL flush on synchronous standby(s).
- `synchronous_commit = remote_write`: wait for WAL flush on primary, and for standby to receive and write (but not fsync) — slightly weaker durability than `on`, but lower latency (no fsync RTT on standby).
- `synchronous_commit = remote_apply`: wait for WAL flush on primary and for standby to apply (make queryable) the changes — strongest guarantee, highest latency.
- `synchronous_commit = local`: wait for WAL flush on primary only — effectively async replication of durability.
- `synchronous_commit = off`: don't wait for primary WAL fsync either — maximum throughput, small data loss window even without replica failure.
- `synchronous_standby_names = 'FIRST 1 (replica1, replica2)'`: wait for the first 1 of the listed standbys to ack. `ANY 1` means any one of them. `FIRST 2` means the first 2 in order.

**Q16. What is "synchronous replica as a single point of failure" and how do you mitigate it?**
A: If there is one synchronous replica and it becomes unavailable, the primary blocks all writes — the primary is effectively down even though it is running. This makes the synchronous replica a SPOF for write availability. Mitigations:
- **Multiple synchronous replicas with quorum**: require acknowledgment from `ANY 1 OF (replica1, replica2, replica3)`. As long as one replica is available, writes proceed. One replica failing doesn't block the primary.
- **Automatic degradation to async**: some systems (MySQL semi-sync) automatically fall back to async if no synchronous replica acknowledges within a timeout. This preserves availability at the cost of temporarily weakening the durability guarantee.
- **Synchronous standby with async fallback chain**: PostgreSQL allows `FIRST 1 (replica1, replica2)` where if `replica1` fails, `replica2` automatically becomes the synchronous standby without operator intervention.

## Section 4: Semi-Synchronous Replication

**Q17. What is semi-synchronous replication and what problem does it solve?**
A: Semi-synchronous replication is a middle ground: the primary waits for **at least one replica** (not necessarily all replicas) to confirm receipt of the log entry before acknowledging the write to the client. Other replicas that are not designated as the synchronous target continue to replicate asynchronously.

It solves the primary availability problem of full synchronous replication: a single slow replica cannot block writes indefinitely, because the primary only waits for the fastest replica to respond. It also solves the data loss problem of pure async: at least one replica always has the write before the client is told it succeeded. If the primary crashes, the replica that acknowledged the write (the "semi-sync" replica) can be promoted with zero data loss for that write.

**Q18. How does MySQL implement semi-synchronous replication?**
A: MySQL's `rpl_semi_sync_master` plugin adds a hook after the primary writes to the binlog: it waits for acknowledgment from at least one semi-sync replica before returning to the client. Configuration:
- `rpl_semi_sync_master_enabled = ON`: enable semi-sync on the primary.
- `rpl_semi_sync_slave_enabled = ON`: enable semi-sync on the replica.
- `rpl_semi_sync_master_wait_for_slave_count = 1`: how many replicas must ack (default 1). Set to 2 for stronger guarantees.
- `rpl_semi_sync_master_timeout = 10000` (ms): if no replica acks within this timeout, fall back to async. Preserves write availability at the cost of temporarily weakening durability.
- `rpl_semi_sync_master_wait_point = AFTER_SYNC` (MySQL 5.7+): ack after the primary writes to binlog but before storage engine commit — stronger guarantee than `AFTER_COMMIT`.

**Q19. What is the difference between `AFTER_SYNC` and `AFTER_COMMIT` wait points in MySQL semi-sync?**
A: This subtle distinction matters for failure recovery:
- **`AFTER_COMMIT`** (older default): primary writes to binlog → commits to storage engine → waits for replica ack → responds to client. If the primary crashes after commit but before replica ack, the transaction is committed on the primary and visible to other clients, but the replica doesn't have it. After promotion, the replica is missing a transaction that clients have already seen — a consistency violation ("phantom commit").
- **`AFTER_SYNC`** (MySQL 5.7+ default, also called "lossless semi-sync"): primary writes to binlog → waits for replica ack → commits to storage engine → responds to client. If the primary crashes before storage engine commit, the transaction was never committed — no client saw it, and the replica doesn't have it. Clean rollback. If the primary crashes after replica ack but before commit, the replica has the binlog entry and can apply it on promotion. Zero data loss, no phantom commits. Always use `AFTER_SYNC`.

**Q20. What happens when the semi-sync timeout fires and replication falls back to async?**
A: When `rpl_semi_sync_master_timeout` expires (no replica acked within the window), MySQL automatically falls back to asynchronous mode for subsequent writes. The primary no longer waits for any replica. This fallback is logged (`Semi-sync replication switched OFF`) and should trigger an alert. While in async fallback mode, the system is in a degraded durability state — the original semi-sync guarantee is gone, and data loss on primary failure is possible.

When a replica reconnects and sends an ack, MySQL switches back to semi-sync mode. This automatic fallback/restore is a key feature that makes semi-sync viable in production: a transient replica issue doesn't cause a sustained primary outage, just a temporary weakening of the guarantee.

**Q21. How does semi-synchronous replication behave differently from synchronous when multiple replicas are present?**
A: With semi-synchronous (`wait_for_slave_count = 1`) and three replicas:
- The primary waits for the **first** replica to ack, then responds to the client. The other two replicas continue to replicate asynchronously.
- If the primary fails and the acking replica is promoted, it has all committed writes. The other two replicas may be behind.
- If the primary fails and neither of the two async replicas is the one that acked, they may be behind the promoted replica. The promoted replica has data they don't — they are now lagging behind the new primary, which they catch up from the new primary's log.

With `wait_for_slave_count = 2` and three replicas, two must ack before each write — stronger durability (can survive simultaneous failure of primary + one replica without data loss), but higher latency (must wait for the slower of the two to ack).

## Section 5: Replication Lag — Deep Dive

**Q22. What is "replication lag amplification" and when does it become a crisis?**
A: Replication lag amplification occurs when lag on one replica causes a cascading effect: the replica's lag causes queries to route to the primary (to avoid stale reads), which increases primary load, which slows the primary's binlog write, which increases the lag on the replica further — a positive feedback loop. It becomes a crisis when: (1) lag exceeds the application's staleness tolerance and all reads are forced to the primary, eliminating the read-scaling benefit; (2) lag grows to hours, making the replica useless as a failover target; (3) lag persists through business hours and the system never catches up.

Break the loop: identify the root cause (slow replica disk, blocking DDL, single-threaded apply) and fix it directly. Throttle primary write rate as a last resort if the replica cannot keep up.

**Q23. How do you monitor replication lag in production?**
A: Database-native metrics:
- **MySQL**: `SHOW SLAVE STATUS` → `Seconds_Behind_Master` (coarse, measures time difference between a replicated event's timestamp and now; can be misleading if the replica clock skews or there are long-running transactions). More precise: monitor `Read_Master_Log_Pos` vs `Exec_Master_Log_Pos` directly — the byte gap in the binlog.
- **PostgreSQL**: `SELECT * FROM pg_stat_replication` on the primary — `write_lag`, `flush_lag`, `replay_lag` columns give precise lag at each stage of the pipeline. On the replica: `SELECT now() - pg_last_xact_replay_timestamp()`.
- **Heartbeat tables**: write a timestamp to a dedicated table on the primary every second (`pt-heartbeat` from Percona Toolkit). Measure how stale this timestamp is on the replica. Immune to clock skew and blocking transaction issues.

Alerting thresholds: alert at lag > 30s for most OLTP systems; lag > 5 minutes is a crisis requiring immediate intervention; lag > RPO is a data loss risk situation.

**Q24. What is "phantom read from replica lag" and how does it affect application correctness?**
A: A phantom read from replica lag occurs when an application performs a write on the primary and then reads from a lagging replica, seeing pre-write state. Example: a user transfers money from account A to account B. The primary debits A and credits B. The application then reads account balances from a replica — the debit is visible (was applied earlier) but the credit is not yet applied (lag). The user sees their money has left account A but not arrived at account B — a transient phantom balance discrepancy that is alarming in a financial context.

Fix: route balance reads (and any post-write reads) to the primary, or use a "read-after-write" consistency strategy (wait for the replica to apply the write before reading from it — e.g., using `pg_last_wal_replay_lsn()` to confirm the replica has caught up to the write's LSN).

**Q25. What is "replication position" and how is it used to implement read-after-write consistency?**
A: The replication position (log sequence number, LSN, or GTID) identifies exactly where in the replication log the primary is after a write. After writing, the primary returns the LSN of the committed transaction. The application stores this LSN and, when routing a subsequent read to a replica, waits until the replica has applied at least this LSN: `WAIT_FOR_EXECUTED_GTID_SET({lsn}, timeout)` (MySQL) or checks `pg_last_wal_replay_lsn() >= {lsn}` (PostgreSQL). Only then does it execute the read. This guarantees read-after-write consistency without always routing to the primary.

## Section 6: Failure Modes & Anti-patterns

**Q26. What is "split-brain" in replication and when does it occur?**
A: Split-brain occurs when two nodes both believe they are the primary and accept writes simultaneously, causing the dataset to diverge. It happens during network partitions: the primary is isolated from replicas (and the monitoring system), replicas detect the primary as "down" and elect one as the new primary. Meanwhile, the original primary continues accepting writes from clients that can still reach it. Two primaries write different data; neither knows about the other. When the partition heals, the two diverged datasets must be reconciled — some writes must be discarded.

Prevention: **fencing** — ensure the old primary is prevented from accepting writes before a new one is promoted. Mechanisms: STONITH (Shoot The Other Node In The Head — physically power off or fence the old primary), distributed lock requiring a quorum before promotion, or a lease-based system (primary must renew a lease with a quorum; if the lease expires, it stops accepting writes).

**Q27. What is "async replica promotion data loss" and what does it look like concretely?**
A: When an async replica is promoted to primary after the original primary crashes, the replica may be missing some committed writes — those that were acknowledged to clients but not yet replicated. Concretely:

1. Client writes orders #1001 through #1010 to the primary. The primary acks all of them.
2. The primary crashes. At the time of crash, the replica had only received orders #1001 through #1007.
3. The replica is promoted to primary. It now has orders #1001 through #1007 only.
4. Orders #1008, #1009, #1010 are permanently lost. Clients who submitted them received success responses, but those orders don't exist in the new primary.

This is not a bug — it is the defined behavior of async replication. The team chose async replication and accepted this as the trade-off. The severity depends on the application: for an order management system, losing 3 orders is catastrophic; for a social media like counter, losing 3 likes is imperceptible.

**Q28. What is "replication loop" in multi-leader replication and how is it prevented?**
A: In a multi-leader setup, Leader A replicates a change to Leader B. Leader B applies it and, without a loop-prevention mechanism, attempts to replicate it back to Leader A — and to any other leaders. Each leader replicates the change to all others, which replicate back, infinitely. Prevention: tag each replication event with the originating node's ID. Before applying a replication event, check if the current node's ID is already in the event's "seen by" list. If so, drop it — the event has already passed through this node. MySQL binary log uses `server_id` for this purpose; events with a matching `server_id` are not applied.

**Q29. What is the "lagging replica promoted to primary" problem and how do orchestration tools handle it?**
A: When a primary fails and an orchestration tool (MHA, Orchestrator, Patroni) selects a replica for promotion, it should select the replica with the least lag (most up-to-date). But if all replicas are significantly behind, promoting any of them causes data loss proportional to their lag. Orchestration tool strategies:
- **Wait for the best replica to catch up** (if the primary's binlog/WAL is still accessible): copy missing log entries from the crashed primary's disk (if it's accessible) to the chosen replica before promoting. Minimizes or eliminates data loss.
- **Promote immediately, fix later**: accept the data loss, promote the least-lagging replica, alert the team to investigate what was lost. Used when RTO is prioritized over RPO.
- **GTID-based selection** (MySQL): Global Transaction Identifiers let the orchestrator precisely identify which transactions each replica has applied and choose the most advanced one. Other replicas can catch up to the new primary using GTID-based replication.

**Q30. What is "replication divergence" after a failed primary rejoin?**
A: After a primary crash and replica promotion, if the old primary comes back online, it may have data that the new primary doesn't (the writes that weren't replicated before the crash). If the old primary is naively re-joined as a replica, it will try to replicate those "extra" transactions to the new primary — but the new primary has moved on with new transactions from other clients. The logs diverge. Fix: the old primary must be **reset** before rejoining as a replica: its extra transactions must be rolled back (via `mysqlbinlog` replay reversal, or simply restoring from a snapshot of the new primary). Orchestration tools handle this automatically; doing it manually is error-prone and risky.

**Q31. What is "async replication as a false safety net" anti-pattern?**
A: Teams sometimes deploy async replication and assume it provides strong data protection — "we have a replica, so we're safe." In reality, async replication provides read scaling and fast failover (with some data loss), not zero-data-loss durability. If the primary fails during a write burst (high insert/update rate), the lag at time of failure could be minutes — thousands of writes lost. The false safety net: the team believes data is safe because the replica exists, but has never measured or set an acceptable RPO, and has never tested failover to understand the actual data loss. Fix: define explicit RPO, measure lag continuously, test failover regularly, and be honest about whether async replication meets the RPO requirement.

## Section 7: Trade-offs & Decision-Making

**Q32. How do you choose between synchronous, semi-synchronous, and asynchronous replication?**
A: Work backward from requirements:
- **If RPO must be zero (no data loss tolerated)**: synchronous replication is required. Accept the write latency penalty. Ensure the synchronous replica is within the same data center (LAN latency, not WAN) to keep added latency manageable. Use quorum-based sync to avoid making a single replica a write SPOF.
- **If RPO can be seconds to minutes, and write availability is critical**: semi-synchronous with a timeout fallback. Guarantees at-least-one-replica has every write, but falls back to async if replicas are temporarily unreachable. Balances durability and availability.
- **If RPO can be measured in minutes and write latency is paramount**: asynchronous replication. Accept the data loss risk; mitigate with frequent snapshots, short backup intervals, and replicas that are kept as current as possible.
- **If replicas are geographically distant**: asynchronous is almost always required. Adding 200ms per write for cross-region sync is untenable for user-facing writes.

**Q33. How does the CAP theorem relate to synchronous vs. asynchronous replication?**
A: The CAP theorem states that a distributed system can guarantee only two of three properties: Consistency, Availability, and Partition tolerance.
- **Synchronous replication** prioritizes CP: a write is not acknowledged until all synchronous replicas confirm, ensuring all nodes agree on the committed state (Consistency). If a replica is unreachable (Partition), the primary blocks writes (sacrificing Availability).
- **Asynchronous replication** prioritizes AP: the primary acknowledges writes immediately regardless of replica state (Availability). If a replica falls behind during a Partition, reads from it may be stale (sacrificing Consistency).
- **Semi-synchronous** is tunable: with `wait_for_slave_count = 1` and timeout fallback, it leans AP — availability is preserved via the fallback. With no timeout and all replicas required to ack, it leans CP.

In practice, database replication systems operate in the "PC" or "PA" corner depending on configuration, not a binary CA choice.

**Q34. When does the latency penalty of synchronous replication become acceptable?**
A: When all of these conditions hold:
- **The synchronous replica is on the same LAN or same data center**: added latency is 1–5ms, which is acceptable for most applications.
- **Write throughput is not latency-sensitive**: batch jobs, administrative operations, or business transactions where 5ms is imperceptible.
- **The data value justifies the cost**: financial ledgers, medical records, legal audit trails — workloads where losing a write causes real business harm.
- **The SLA explicitly requires RPO = 0**: regulated industries where data loss is a compliance violation.

Conversely, synchronous replication is a poor fit for: high-throughput OLTP (write latency accumulates), user-facing APIs (user perceives the added latency), or cross-region deployments (WAN RTT makes sync impractical).

**Q35. What is "tunable consistency" (as in Cassandra) and how does it relate to the three replication modes?**
A: Cassandra's write consistency level (`ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`, etc.) is a per-operation choice that maps roughly onto the synchronous/semi-sync/async spectrum:
- `ALL`: all replica nodes must ack the write → effectively synchronous replication, strongest durability, least tolerant of replica failure.
- `QUORUM`: majority of replica nodes must ack → like semi-sync with N/2+1 acks required, balances durability and availability.
- `ONE`: any one replica must ack → like semi-sync with one ack, fast with minimal durability guarantee.
- `ANY`: even a coordinator-side hint write counts → like async, weakest durability but highest availability.

Cassandra makes this tunable at the call level, allowing different operations in the same system to use different consistency levels. This is the leaderless analog of choosing replication modes — the concepts are equivalent, the implementation differs.

**Q36. How does semi-synchronous replication interact with replica chaining (relay replicas)?**
A: Relay replicas (also called "intermediate replicas" or "binlog servers") sit between the primary and downstream replicas, receiving the primary's log and re-streaming it. In a semi-sync setup, the semi-sync ack is typically from the **first-hop replica** (the relay), not from the downstream replicas that the relay feeds. This means semi-sync guarantees the relay has the write — but not the downstream replicas the relay feeds. If the relay fails after acking but before distributing to downstream replicas, the downstream replicas are behind. Factor this into your durability analysis: semi-sync's guarantee is as strong as the acking node's own durability, not the entire replica tree's.

## Section 8: Scenario / System Design Style Questions

**Q37. "You are designing the replication strategy for a payment processing database. What do you choose and why?"**
A: Synchronous replication is the only acceptable choice for a payment system where data loss is a compliance and financial risk. Concretely:
- **PostgreSQL with `synchronous_commit = on`** and `synchronous_standby_names = 'ANY 1 (replica1, replica2)'`. Any one of two designated standbys must ack before the client receives a success response. Two standbys ensures single standby failure doesn't block writes.
- **Same data center**: keep synchronous standbys in the same DC to hold added latency to 1–3ms. The trade-off is acceptable for financial transactions.
- **Async replica in a second region**: for disaster recovery, maintain an async replica in a second region. This replica is not in the synchronous path (would add 50ms per write) but is available for DR promotion if the primary DC is lost. RPO for a full DC failure = replication lag of the async replica, which should be monitored and kept under 60 seconds.
- **Explicit RPO = 0 for primary-level failures** (covered by sync standby). **RPO = < 60s for DC-level failures** (covered by async DR replica). Both must be defined, tested, and monitored.

**Q38. "Your MySQL replica is consistently 45 minutes behind the primary during business hours. Walk through your diagnosis and remediation."**
A: Systematic investigation:
1. **Identify the bottleneck stage**: `SHOW SLAVE STATUS` — is the replica receiving the binlog promptly (`Read_Master_Log_Pos` ≈ primary position)? If not, the bottleneck is network or primary binlog read speed. If yes, the bottleneck is in applying events (`Exec_Master_Log_Pos` far behind `Read_Master_Log_Pos`).
2. **Check for blocking events**: `SHOW PROCESSLIST` on the replica — is there a long-running DDL (`ALTER TABLE`), a slow query, or a locked table blocking the replication SQL thread?
3. **Check parallel replication**: is `slave_parallel_workers` = 0? MySQL 5.6+ supports parallel replication (`slave_parallel_type = LOGICAL_CLOCK` in 5.7+) that can apply independent transactions concurrently, dramatically improving apply throughput. Enable it.
4. **Check replica hardware**: is the replica under-provisioned? Compare I/O wait, CPU, and RAM utilization on replica vs. primary. IOPS may be the ceiling — consider faster storage (NVMe).
5. **Check write patterns**: is the primary running many `ALTER TABLE` or bulk inserts that serialize poorly on the replica? Consider scheduling heavy writes during off-hours or using online schema change tools (`pt-online-schema-change`) that are more replica-friendly.
6. **Check semi-sync vs. async**: is the primary in semi-sync mode waiting for this replica? A slow replica causes primary write latency to spike. Consider designating a faster replica as the semi-sync target and moving this one to async.
7. **Remediation**: after fixing the root cause, let the replica catch up naturally (don't restart it — restart loses position). Monitor `Seconds_Behind_Master` decreasing. If it's decreasing too slowly, temporarily reduce primary write load (rate limit writes) to give the replica room to catch up.

**Q39. "A candidate proposes using synchronous replication to a cross-region standby for a high-traffic e-commerce site to ensure zero data loss. How do you respond?"**
A: Push back on the cross-region part, not the zero-data-loss goal:
- **The latency cost is prohibitive**: a cross-region round trip (e.g., US East to US West) adds 60–80ms to every write. On a checkout page processing 1000 transactions/second, every one of those transactions is 60ms slower. At peak traffic (e.g., Black Friday), this latency directly impacts conversion rates — measurable revenue impact.
- **Better architecture**: keep synchronous standbys within the same region (1–3ms added latency, imperceptible). Add an **async replica in the second region** for DR purposes. Accept that a full-region failure has a non-zero RPO (lag of the async replica, typically < 60s with proper monitoring) — this is an acceptable business risk compared to 60ms write latency on every transaction.
- **If zero data loss for cross-region is truly required** (genuine regulatory requirement): consider a distributed database that handles cross-region consensus more efficiently than single-leader sync replication (CockroachDB, Google Spanner, YugabyteDB). These use Raft/Paxos to achieve strong consistency across regions at lower effective latency by using quorums of nearby replicas.

**Q40. "You're building a read-heavy analytics dashboard that queries replica data. Users are seeing stale data and complaining. How do you address it without routing everything to the primary?"**
A: The problem is replication lag making replica data too stale for the dashboard's freshness requirement. Several fixes without giving up replicas:
1. **Measure the actual lag and set a staleness SLA**: if users complain about 5-minute-old data but your lag is 5 minutes, the fix is reducing lag — not abandoning replicas. Reduce lag by enabling parallel replication, upgrading replica hardware, and ensuring no blocking queries.
2. **Read-after-write consistency for recent writes**: after a user updates dashboard settings or submits data, track the LSN of that write. Route subsequent reads to a replica only after it has applied up to that LSN. For reads not related to the user's own recent writes, replicas are fine.
3. **Route only stale-sensitive queries to primary**: identify which specific queries are generating complaints (balance displays, recent-transaction lists) and route those to the primary. Route aggregate and historical queries (charts, trends) to replicas — these are naturally tolerant of seconds of staleness.
4. **Tiered replica pool**: use `synchronous_commit = remote_apply` for one designated "low-lag" replica. Route freshness-sensitive reads to that replica only. Route bulk analytical queries to standard async replicas.
5. **Accept and communicate staleness**: for dashboard data that genuinely doesn't need sub-second freshness, display a "last updated X seconds ago" indicator. Many analytics dashboards are designed around explicit refresh intervals — align the replica lag with the declared refresh interval rather than fighting the fundamental async latency.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                        | Asynchronous                                          | Semi-Synchronous                                          | Synchronous                                               |
|---                            |---                                                    |---                                                        |---                                                        |
| Write ack timing              | Immediately after local disk write                    | After ≥ 1 replica confirms receipt                        | After all designated replicas confirm durable write       |
| Data loss on primary failure  | Yes — up to current replication lag                   | No — acking replica has every write                       | No — all sync replicas have every write                   |
| RPO                           | = replication lag (seconds to minutes)                | = 0 if acking replica is promoted                         | = 0 always                                                |
| Write latency impact          | None — no added latency                               | +1 round trip to fastest replica                          | +1 round trip to slowest sync replica                     |
| Primary availability          | Fully independent of replica state                    | Independent unless all replicas offline (fallback to async)| Blocked if any sync replica is unavailable                |
| Replica availability impact   | Zero — primary ignores replica state                  | Minimal — timeout fallback prevents blocking              | High — unavailable replica blocks all writes              |
| Read scaling                  | Yes (with staleness)                                  | Yes (acking replica is fresh; others may lag)             | Yes (sync replica is always current)                      |
| Suitable for cross-region     | Yes — designed for high-latency replica links         | Yes, with generous timeout                                | No — WAN latency makes every write unacceptably slow      |
| Typical use cases             | Read replicas, geo-DR replicas, analytics offload     | Default production DB replication in most web systems     | Financial systems, regulated data, same-DC HA             |
| MySQL implementation          | Default replication mode                              | `rpl_semi_sync` plugin, `AFTER_SYNC` wait point           | N/A natively; approximate via `wait_for_slave_count = N` with no timeout |
| PostgreSQL implementation     | `synchronous_commit = off / local`                    | `synchronous_commit = remote_write`                       | `synchronous_commit = on / remote_apply`                  |

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| Replication log               | Ordered record of every change on the primary (binlog, WAL, oplog); replicas consume it to converge        |
| RPO                           | Max acceptable data loss in time; async RPO = lag at failure; sync RPO = 0                                  |
| RTO                           | Max acceptable downtime; sync replica promotes instantly (low RTO); lagging async replica extends RTO        |
| Replication lag               | Delay between primary commit and replica apply; the central async replication variable                       |
| `Seconds_Behind_Master`       | MySQL's coarse lag metric; measure byte gap or use heartbeat tables for precision                            |
| `pg_stat_replication`         | PostgreSQL view showing write_lag, flush_lag, replay_lag per standby                                         |
| Read-your-own-writes          | Guarantee that a user's reads reflect their own writes; violated by async replication without sticky routing |
| Monotonic reads               | Guarantee that successive reads don't go backward in time; violated if reads route to different-lag replicas |
| GTID                          | Global Transaction Identifier in MySQL; uniquely identifies each transaction for precise lag tracking and promotion |
| LSN                           | Log Sequence Number in PostgreSQL WAL; used for read-after-write consistency checks on replicas              |
| `AFTER_SYNC`                  | MySQL semi-sync wait point: ack replica before storage engine commit; prevents phantom commits               |
| `synchronous_standby_names`   | PostgreSQL config specifying which standbys are synchronous and how many must ack (`FIRST N`, `ANY N`)       |
| Split-brain                   | Two nodes both acting as primary simultaneously; prevented by fencing and quorum-based promotion             |
| Fencing / STONITH             | Mechanism to prevent old primary from accepting writes after a new primary is elected                        |
| Phantom commit                | Async/semi-sync (`AFTER_COMMIT`) failure mode where a committed transaction is visible to clients but missing from promoted replica |
| Parallel replication          | Applying binlog events on multiple threads simultaneously on the replica; reduces lag under high write load  |
| Tunable consistency           | Per-operation consistency level (Cassandra `ONE`/`QUORUM`/`ALL`); the leaderless analog of sync/async choice |
| Replication divergence        | Old primary rejoins with extra transactions not in the new primary; must be fenced and reset before rejoining |

---

**Tip for the interview:** Most candidates answer "async is faster, sync is safer" and stop there. The depth interviewers look for: the concrete mechanism (primary doesn't wait / waits for ack), the exact failure scenario for each mode (data loss on async failover, write blocking on sync replica failure), and the real-world configurations (`AFTER_SYNC` vs `AFTER_COMMIT`, `synchronous_standby_names = ANY 1 OF`). The best answers connect replication mode to RPO/RTO explicitly — "we chose semi-sync because our RPO is zero but we can't tolerate write blocking, so the timeout fallback to async gives us the escape valve." Also know that synchronous cross-region replication is almost always the wrong answer — WAN latency makes it impractical, and the right answer is same-DC sync + async cross-region DR.
