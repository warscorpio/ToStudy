# Quorum Reads and Writes (`R + W > N`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a quorum in a distributed system?**
A: A quorum is the minimum number of nodes in a distributed system that must agree on an operation for it to be considered successful. It is the mechanism by which distributed databases achieve consistency without requiring all nodes to be available or agree — a majority (or configured subset) is sufficient. The term comes from parliamentary procedure: a quorum is the minimum attendance required for a vote to be valid.

In distributed databases (Cassandra, DynamoDB, Riak), replication factor N means each piece of data is stored on N nodes. W is the number of nodes that must confirm a write before the coordinator declares it successful; R is the number of nodes that must respond to a read. The quorum condition `R + W > N` guarantees that the read and write sets overlap — at least one node that participated in the last write also participates in every read.

**Q2. What does `R + W > N` guarantee, intuitively?**
A: If W nodes acknowledged the last write and R nodes respond to a read, and `R + W > N`, then by the pigeonhole principle the two sets must share at least one node. That shared node has the most recent write, so the read is guaranteed to return a value at least as recent as the last acknowledged write.

Visually, with N=3, W=2, R=2:

```
Nodes:   [Node 1]   [Node 2]   [Node 3]

Write:      ✓          ✓          ✗       (W=2 confirmed)
Read:       ✗          ✓          ✓       (R=2 responded)

Overlap:            [Node 2]              ← always at least one overlap
```

Node 2 is in both the write set and the read set — it has the latest value, so the read returns it. No matter which 2 nodes the write hits and which 2 the read hits, with `R + W = 4 > N = 3`, there is always an overlap of at least 1.

**Q3. What does `R + W > N` NOT guarantee?**
A: It guarantees overlap between the last write set and the current read set — but only if all writes go through the same replication path and there are no concurrent conflicting writes. It does not guarantee:
- **Linearizability** — in the presence of concurrent writes or network partitions, two clients may observe different orderings. `R + W > N` is a sufficient condition for **strong consistency in the quorum model**, but the quorum model itself is weaker than linearizability unless additional mechanisms (like leader-based writes or version vectors) are in place.
- **Protection against concurrent writes** — if two clients write simultaneously, both may achieve quorum but on overlapping sets; the system must have a conflict resolution policy (last-write-wins, vector clocks, CRDTs).
- **Consistency during network partitions** — if a partition prevents the coordinator from reaching W nodes, the write fails. If the system accepts writes anyway (sloppy quorum), the guarantee breaks.

**Q4. What are the common N, W, R configurations and what do they optimize for?**
A:

| Configuration | Guarantee | Trade-off |
|--- |--- |--- |
| N=3, W=2, R=2 | Strong consistency (`R+W=4>3`) | Balanced; 1 node can fail for both reads and writes |
| N=3, W=3, R=1 | Strong consistency (`R+W=4>3`) | Writes require all 3 nodes (low write availability); reads are fast (any 1 node) |
| N=3, W=1, R=3 | Strong consistency (`R+W=4>3`) | Writes are fast (any 1 node); reads require all 3 (low read availability) |
| N=3, W=1, R=1 | Eventual consistency (`R+W=2≤3`) | Maximum availability and throughput; no consistency guarantee |
| N=3, W=2, R=1 | Eventual consistency (`R+W=3≤3`) | Write-heavy optimized; reads may be stale |
| N=5, W=3, R=3 | Strong consistency (`R+W=6>5`) | Tolerates 2 node failures for both reads and writes |

The most operationally practical configuration is N=3, W=2, R=2 — it tolerates a single node failure for both reads and writes while maintaining strong consistency.

**Q5. What is the relationship between fault tolerance and quorum size?**
A: A system with replication factor N and write quorum W can tolerate `N - W` node failures for writes before writes start failing. Similarly, it tolerates `N - R` node failures for reads. For the common N=3, W=2, R=2 configuration:
- Write fault tolerance: `3 - 2 = 1` node can be unavailable.
- Read fault tolerance: `3 - 2 = 1` node can be unavailable.

For N=5, W=3, R=3:
- Write fault tolerance: `5 - 3 = 2` nodes.
- Read fault tolerance: `5 - 3 = 2` nodes.

Higher N gives better fault tolerance but increases the replication overhead (storage, cross-node write latency). The choice of N is a cluster-level decision driven by durability and availability requirements, not changed per operation.

## Section 2: Reads and Writes in Practice

**Q6. How does a quorum write actually work step-by-step?**
A: Using Cassandra's model as a concrete example:

```
Client
  │
  │  write(key="user:42", value={name:"Aditya"}, timestamp=T1)
  ▼
Coordinator Node (any node in the cluster)
  │
  │── replicate to Node A ──► Node A writes, responds ACK
  │── replicate to Node B ──► Node B writes, responds ACK
  │── replicate to Node C ──► Node C is slow / unavailable
  │
  │  W=2 ACKs received → declare write SUCCESS to client
  │  (Node C's write is pending; handled by hinted handoff)
  ▼
Client receives SUCCESS

[Later, async]
Node C comes back online → coordinator delivers the hinted write
All 3 nodes now consistent
```

The coordinator waits for W acknowledgments before responding to the client. The remaining `N - W` replicas are written asynchronously. If W ACKs are not received within the timeout, the write returns an error and the client must retry.

**Q7. How does a quorum read work, and what happens when nodes return different values?**
A: The coordinator sends read requests to R nodes simultaneously and waits for R responses:

```
Client
  │
  │  read(key="user:42")
  ▼
Coordinator
  │── read from Node A ──► returns {name:"Aditya", ts=T2}
  │── read from Node B ──► returns {name:"Aditya", ts=T2}
  │── read from Node C ──► returns {name:"Old Name",  ts=T1}
  │
  │  R=2 responses received (A and B) → return highest-timestamp value
  │  (Node C's stale value detected but not needed for R=2)
  ▼
Client receives {name:"Aditya", ts=T2}

[Read repair — async]
Coordinator detects Node C is stale (if it was in the R set)
→ sends Node C the latest value {name:"Aditya", ts=T2}
Node C updates its copy
```

When nodes return different values (divergent replicas), the coordinator uses a conflict resolution rule — in Cassandra and DynamoDB's last-write-wins (LWW) model, the highest timestamp wins. With vector clocks (Riak), the coordinator detects concurrent writes and may return multiple conflicting values for the client to resolve.

**Q8. What is read repair and why is it important?**
A: Read repair is the mechanism by which a quorum read detects and corrects stale replicas. When the coordinator reads from R nodes and discovers that some nodes have an older value than others, it proactively sends the latest value back to the stale nodes — repairing them in the background without the client waiting for this repair.

Two modes:
- **Synchronous read repair** — the coordinator waits for the repair write to complete before returning to the client. Stronger consistency guarantee but higher latency. Used when `read_repair_chance = 1.0`.
- **Asynchronous read repair** — the coordinator returns the result to the client immediately and repairs stale replicas in the background. Lower latency; the window of staleness for the repaired node is reduced on the next read.

Read repair is a convergence mechanism — it ensures that stale replicas eventually catch up, even without writes occurring. In Cassandra, `read_repair_chance` is a per-table configuration (0.0–1.0) that probabilistically triggers read repair on QUORUM reads. Without read repair, replicas only converge through new writes to those keys — stale replicas for rarely-written keys can persist indefinitely.

**Q9. What is the coordinator's role in a quorum operation?**
A: Any node in a leaderless distributed database (Cassandra, DynamoDB, Riak) can act as the coordinator for any operation. When a client sends a read or write to any node, that node becomes the coordinator for that operation:

1. **Identify replica nodes** — use the partitioning scheme (consistent hashing) to determine which N nodes are responsible for the key.
2. **Fan out the operation** — send the read/write to all N replicas (or at least W/R of them) concurrently.
3. **Wait for quorum** — collect responses; return to the client as soon as W (for writes) or R (for reads) responses are received.
4. **Handle stragglers** — responses from the remaining `N - W` or `N - R` nodes are ignored for the client response but may trigger read repair or be used for diagnostics.
5. **Timeout and error** — if quorum is not achieved within the timeout window, return an error to the client.

The coordinator pattern enables horizontal scalability — no special leader node is required for reads or writes; any node can serve any client.

## Section 3: Consistency Trade-offs

**Q10. What is the difference between quorum consistency and strong consistency (linearizability)?**
A: Quorum consistency (`R + W > N`) guarantees that a read returns a value written by the most recent successful write — but only in the absence of concurrent operations. It is **not** linearizable by default because:

- **Non-linearizable scenario**: Client A writes key=1 (achieves quorum on nodes 1,2). Client B reads key (hits nodes 2,3) — gets the new value (correct). Client C reads key (hits nodes 1,3 where Node 3 hasn't received the write yet due to network delay) — gets the old value. Client B and C observe different values for the same key at the same "real time."

True linearizability requires that once a write completes, all subsequent reads from any node reflect it. Achieving this with a quorum system requires additional mechanisms:
- **Leader-based writes** (Raft, Paxos) — only the leader accepts writes; all reads go through the leader. This is linearizable but sacrifices availability (leader is a SPOF without failover).
- **Conditional writes with fencing tokens** — write only succeeds if no other write has occurred since the read (optimistic locking via `version` checks).

For practical purposes: quorum reads and writes give "session consistency" (a client always reads its own writes if it uses the same coordinator) and "monotonic read consistency" (a client never sees an older value after seeing a newer one, within a session). Full linearizability requires a different architecture.

**Q11. What happens to quorum guarantees during a network partition?**
A: A network partition splits nodes into two groups that cannot communicate. With N=3, W=2, R=2:

```
Partition: [Node 1, Node 2] | [Node 3]

Side A (2 nodes):
  - Can still achieve W=2 writes ✓
  - Can still achieve R=2 reads ✓
  - Operates normally

Side B (1 node):
  - Cannot achieve W=2 writes ✗ (only 1 node available)
  - Cannot achieve R=2 reads ✗
  - Returns errors for all operations
```

This is the CP behavior from CAP theorem — during a partition, the minority partition becomes unavailable (returns errors) to maintain consistency. The majority partition continues operating and maintains the quorum guarantee. When the partition heals, the stale node (Node 3) catches up via read repair and anti-entropy (background sync).

If the system allows writes to Node 3 alone during the partition (sloppy quorum / hinted handoff), it becomes AP — available but potentially inconsistent when the partition heals, requiring conflict resolution.

**Q12. What is a sloppy quorum and when is it used?**
A: A sloppy quorum relaxes the quorum requirement during node failures by temporarily writing to nodes outside the "home" replica set. If the normal W replicas for a key are unavailable, the coordinator writes to any W available nodes in the cluster, including nodes not normally responsible for that key. These are "hints" — the node holds the value temporarily and forwards it to the correct replica when it comes back online (hinted handoff).

```
Normal replicas for key: Node 1, Node 2, Node 3
Node 3 is down.

Strict quorum (W=2): write to Node 1, Node 2 ✓ (quorum achieved)
Sloppy quorum (W=2): write to Node 1, Node 2 ✓ (same in this case)

If Node 1 AND Node 3 are both down:
Strict quorum: write FAILS (can't reach 2 of 3 home replicas)
Sloppy quorum: write to Node 2 + Node 4 (non-home node) ✓
  Node 4 holds a hint: "deliver {key, value} to Node 1 when it recovers"
```

Sloppy quorum trades consistency for availability — `R + W > N` no longer guarantees overlap because the write went to non-home nodes that don't participate in standard reads. DynamoDB uses sloppy quorum by default. Cassandra supports it via `LOCAL_ONE` and hinted handoff. Use sloppy quorum when availability matters more than strict consistency (shopping carts, session data) and not for financial transactions or inventory counts.

**Q13. What is the difference between `QUORUM`, `LOCAL_QUORUM`, and `ALL` in Cassandra?**
A:

- **`ONE`** — read/write succeeds when 1 replica responds. Fastest; no consistency guarantee; used for non-critical, high-throughput operations.
- **`QUORUM`** — read/write succeeds when `⌊N/2⌋ + 1` replicas respond, counted across all datacenters. For N=3, that's 2. Strong consistency across datacenters; higher cross-DC latency (must wait for a replica in a remote datacenter).
- **`LOCAL_QUORUM`** — read/write succeeds when a quorum of replicas in the local datacenter respond. Avoids cross-DC latency; strong consistency within a datacenter but weaker guarantees across DCs. The standard production choice for multi-DC deployments.
- **`ALL`** — all N replicas must respond. Maximum consistency (no stale reads possible); zero fault tolerance (any node failure causes the operation to fail). Rarely used in production; appropriate for schema migrations or critical one-off operations.
- **`EACH_QUORUM`** — quorum must be achieved in each datacenter independently. Strongest multi-DC consistency; highest latency; used for globally consistent writes.

In a multi-DC deployment the typical pattern is: `LOCAL_QUORUM` for both reads and writes — strong consistency within each DC, asynchronous replication between DCs, with the application designed to tolerate cross-DC staleness.

## Section 4: Versioning and Conflict Resolution

**Q14. How do distributed systems track which write is "newer" for conflict resolution in quorum reads?**
A: Two primary mechanisms:

**Last-Write-Wins (LWW) with wall-clock timestamps:**
- Each write carries a client-supplied or server-assigned timestamp.
- On a divergent quorum read, the coordinator picks the value with the highest timestamp.
- Simple; widely used (Cassandra default).
- Flaw: wall clocks can drift or go backward (NTP sync); a write with a slightly earlier wall-clock time may be incorrectly discarded even if it was causally later. Clock skew of even 1ms can cause data loss.

**Vector clocks / version vectors:**
- Each replica maintains a vector of `{node_id: sequence_number}` pairs recording how many writes it has seen from each node.
- On a read, the coordinator compares vector clocks to determine causal ordering:
  - If one version's vector clock is strictly greater than another's, it is causally later → return the later version.
  - If neither is strictly greater (concurrent writes), both values are returned to the client for application-level conflict resolution ("siblings" in Riak).
- Captures causality correctly; no clock dependency. Used by Riak, Amazon Dynamo (original paper), and DynamoDB's conditional writes.
- Flaw: vector clocks grow with the number of clients; must be garbage-collected.

**Q15. What is the "last write wins" problem and when is it dangerous?**
A: LWW silently discards concurrent writes that lose the timestamp race — no error is returned to the client whose write was dropped. This is dangerous when:

- **Counters**: two clients increment a counter simultaneously. Both read 10, both write 11 with different timestamps. The higher-timestamp write wins; the counter ends up at 11 instead of 12 — one increment is silently lost.
- **Set operations**: two clients add different items to a set. LWW picks one write; the other item disappears. The client that "won" has no idea its write discarded another client's data.
- **Financial operations**: two debit operations processed concurrently; LWW keeps one, silently drops the other. Money appears without being debited.

Mitigations:
- Use CRDTs (Conflict-free Replicated Data Types) for counters and sets — data structures designed so that any merge of concurrent updates converges to a correct result without discarding information.
- Use conditional writes (optimistic locking) — `write only if current version = V` — so concurrent writes are detected and one explicitly fails rather than being silently discarded.
- Use a single-leader system (Postgres, MySQL) for data where concurrent writes must be serialized.

## Section 5: Real-World Systems

**Q16. How does Cassandra implement quorum reads and writes?**
A: Cassandra is a leaderless, peer-to-peer database using consistent hashing to assign replicas. Every node can be a coordinator. Key implementation details:

- **Replication factor** is set per keyspace: `CREATE KEYSPACE ks WITH REPLICATION = {'class': 'NetworkTopologyStrategy', 'dc1': 3}`.
- **Consistency level** is set per operation (not per table), allowing fine-grained control: a write to a payments table can use `LOCAL_QUORUM` while a write to a logging table uses `ONE`.
- **Hinted handoff** — if a replica is unavailable during a write, the coordinator stores a "hint" (the data + target replica) and delivers it when the replica recovers. Hints expire after 3 hours by default; if the replica is down longer, it must catch up via repair.
- **Anti-entropy repair** — Merkle tree comparison between replicas detects and repairs divergence that hinted handoff missed. Run `nodetool repair` periodically (weekly for most clusters) to ensure full convergence.
- **Lightweight transactions (LWT)** — Cassandra's `INSERT ... IF NOT EXISTS` and `UPDATE ... IF condition` use Paxos to provide linearizable compare-and-swap operations on top of the eventually consistent quorum model. ~4x slower than a regular write; used sparingly.

**Q17. How does DynamoDB implement quorum internally?**
A: DynamoDB uses quorum internally but abstracts it from the user. Key details from the AWS Dynamo paper and subsequent disclosures:

- **Replication**: each item is replicated to 3 storage nodes (effectively N=3 internally).
- **Default reads (Eventually Consistent)**: read from 1 of 3 replicas — fast but may return stale data up to ~1 second old.
- **Strongly Consistent reads** (`ConsistentRead: true`): read from the leader replica, which has the latest committed write. This is effectively W=1 (leader-based write), R=1 (leader read) — linearizable but not a traditional quorum read.
- **Sloppy quorum**: DynamoDB uses sloppy quorum for high availability; writes may go to non-primary replicas during failures (hinted handoff), relaxing strict quorum guarantees.
- **Conditional writes** (`ConditionExpression`): implement optimistic locking on top of the replication model for cases where LWW is insufficient.

The abstraction means DynamoDB users don't configure R, W, and N directly — they choose between eventual and strong consistency, and DynamoDB manages the quorum mechanics internally.

**Q18. Why does MongoDB use a different approach (Raft-based) instead of a quorum read/write model like Cassandra?**
A: MongoDB uses a single-primary (leader-based) replication model with Raft for leader election, rather than a leaderless quorum model:

- **MongoDB**: all writes go to the primary; secondaries replicate asynchronously. Reads can go to secondaries (eventual consistency) or the primary (strong consistency). Leader election via Raft when the primary fails; a new primary is elected with majority vote from replica set members.
- **Cassandra**: any node can be a coordinator; no primary. Any node can accept writes and replicate to N replicas. No leader election; quorum determines consistency.

Trade-offs:
- **MongoDB's model** is simpler to reason about (one truth source = the primary), achieves linearizability naturally for primary reads, but the primary is a bottleneck for writes and a SPOF before failover completes (~10–30s).
- **Cassandra's model** has no write bottleneck (all nodes accept writes) and no leader election latency, but conflict resolution and achieving true linearizability are harder.

MongoDB added quorum-style semantics via `writeConcern: {w: "majority"}` — the primary waits for a majority of secondaries to acknowledge the write before confirming to the client, which is conceptually W = majority, using the Raft log as the coordination mechanism.

## Section 6: Scenario Questions

**Q19. "You're designing a distributed key-value store. A customer requires that reads always return the most recently written value. What quorum configuration do you recommend?"**
A: "Most recently written value" = strong consistency = `R + W > N`. For a 3-replica setup, recommend N=3, W=2, R=2 (`LOCAL_QUORUM` in Cassandra terminology):

- Guarantees that every read overlaps with the last write by at least one node.
- Tolerates 1 node failure for both reads and writes.
- Latency: write and read complete as soon as 2 of 3 nodes respond — the slow third node doesn't block the client.

Caveats to raise with the customer:
- This is not full linearizability — concurrent writes are resolved by LWW, which may surprise the customer if they have concurrent writers.
- For true linearizability (never any stale reads even under concurrent writes), use a leader-based system (Postgres, MongoDB primary read, DynamoDB strongly consistent read) or Cassandra Lightweight Transactions for specific keys.
- `W=2, R=2` still allows a brief window of staleness if a write is in-flight when a read occurs on a non-yet-written replica — quorum overlap ensures this resolves, but a concurrent read and write may observe intermediate states.

**Q20. "With N=5, what W and R values achieve strong consistency while maximizing write availability?"**
A: Strong consistency requires `R + W > 5`, i.e., `R + W ≥ 6`. To maximize write availability, minimize W (more nodes can be down before writes fail):

- **W=2, R=4**: write availability = tolerate 3 node failures (`5-2=3`); read requires 4 nodes, tolerate only 1 failure. Maximizes write availability; reads are fragile.
- **W=3, R=3**: symmetric; tolerate 2 failures for both reads and writes. The balanced choice.
- **W=4, R=2**: write requires 4 nodes (tolerate only 1 failure); reads tolerate 3 failures. Maximizes read availability; writes are fragile.

For "maximizing write availability" specifically: W=2, R=4 — writes can proceed with only 2 of 5 nodes available. But practically, R=4 means a single node failure blocks reads, which is typically unacceptable. The real answer is that maximizing write availability while maintaining strong consistency has an inherent cost to read availability: `W + R > N` means a smaller W forces a larger R.

In a write-heavy workload the pragmatic recommendation is W=3, R=3 — symmetric fault tolerance of 2 nodes for both reads and writes. Or use an async-write / sync-read model (W=1, R=5 with read repair) if write latency is paramount and brief read staleness is acceptable.

**Q21. "A read returns a value that is 10 minutes old despite using R=2, W=2, N=3. How is this possible?"**
A: Several root causes can break the quorum guarantee in practice:

1. **Hinted handoff not delivered** — the original write was directed to Node 1 and Node 2, but Node 2 was down. The coordinator wrote to Node 1 and stored a hint for Node 2. Node 2 came back online but the hint expired (Cassandra's default 3-hour hint window is fine, but if the node was down for hours, hints can accumulate and fail to deliver). The read hit Node 2 and Node 3 — neither of which has the latest write (Node 3 never received it; Node 2 missed it).

2. **Sloppy quorum with non-home replicas** — if sloppy quorum was used, the write went to Node 1 and Node 4 (a non-home node for this key). A subsequent standard read queries Nodes 1, 2, 3 — the home replicas. Node 4 holds the latest value but is outside the read set. The read returns a stale value from Node 2 or Node 3.

3. **Clock skew in LWW** — the write at T=10min ago had a higher wall-clock timestamp than a newer write (due to clock skew on the writing client). The newer write has a lower timestamp and "loses" in LWW conflict resolution — the read returns the older write because it has the higher timestamp.

4. **Read at consistency level ONE** — the application code uses a per-operation consistency level of `ONE` instead of `QUORUM`. A single replica responds; if it's stale, the stale value is returned regardless of W.

5. **Missed anti-entropy repair** — `nodetool repair` has not been run for months. A node that crashed and was replaced with a new node was not fully synced; it serves stale data for keys that haven't been touched since it joined.

Diagnosis: check the Cassandra trace for the read (`TRACING ON`); it shows which replicas responded, what values they returned, and whether read repair was triggered. Cross-reference with the write trace for the key.

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| N | Replication factor | Number of copies of each data item |
| W | Write quorum | Nodes that must ACK a write for it to succeed |
| R | Read quorum | Nodes that must respond to a read |
| `R + W > N` | Strong consistency condition | Guarantees read/write set overlap of ≥ 1 node |
| `R + W ≤ N` | Eventual consistency | No overlap guaranteed; reads may be stale |
| Read repair | Stale replica correction triggered by quorum read | Async (default) or sync; convergence mechanism |
| Hinted handoff | Temporary write to coordinator for unavailable replica | Expires after N hours; not a substitute for repair |
| Sloppy quorum | Write to non-home replicas when home replicas unavailable | Breaks `R+W>N` guarantee; trades consistency for availability |
| LWW | Last-Write-Wins conflict resolution | Fast; loses silent concurrent writes; dangerous for counters |
| Vector clocks | Causal ordering without wall-clock dependency | Detects concurrent writes; returns siblings for client resolution |
| LOCAL_QUORUM | Quorum within local datacenter only | Avoids cross-DC latency; standard multi-DC choice |
| Anti-entropy repair | Merkle tree comparison to detect/repair divergence | Run periodically; catches what hinted handoff missed |

---

**Tip for the interview:** Quorum questions almost always start with "explain `R + W > N`" and then probe into failure modes. The pigeonhole argument (write set and read set must overlap) should roll off naturally — draw the 3-node diagram. The questions that separate 5 YOE answers: knowing that `R + W > N` is necessary but not sufficient for linearizability (concurrent writes break it), being able to explain what sloppy quorum is and precisely why it breaks the guarantee, and naming at least two practical causes of stale reads despite `R + W > N` (clock skew in LWW, hinted handoff failures, missed repair). If the interviewer asks about Cassandra specifically, know the difference between `QUORUM` and `LOCAL_QUORUM` and why `LOCAL_QUORUM` is the production default for multi-DC deployments. The LWW counter-increment problem (two increments, only one takes effect) is a classic follow-up that tests whether you understand the difference between a consistency model and an application-level correctness guarantee.
