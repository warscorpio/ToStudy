# Single-Leader, Multi-Leader, Leaderless Replication — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is replication, and why does a distributed database need it?**
A: Replication is the practice of keeping copies of the same data on multiple nodes. Databases replicate for three reasons: **availability** (if one node dies, others continue serving), **fault tolerance** (data survives hardware failures because it exists on multiple disks in multiple locations), and **read scalability** (read traffic can be distributed across replicas, reducing load on any single node). Every replication strategy involves a fundamental tension: how do you ensure all copies stay in sync when writes can arrive at any node at any time, and the network between nodes is unreliable? The three architectures — single-leader, multi-leader, and leaderless — represent different points in the trade-off space between consistency, availability, write throughput, and operational complexity.

**Q2. What are the three replication architectures, and what is the core distinction between them?**
A: The core distinction is where writes are accepted:
- **Single-leader**: Only one designated node (the leader/primary) accepts writes. All other nodes (followers/replicas) receive write events from the leader and apply them. Reads can go to any node. One authoritative source of truth for the write order.
- **Multi-leader**: Multiple nodes accept writes simultaneously. Each leader replicates its writes to other leaders and to its own followers. Write conflicts are possible — two leaders may accept concurrent conflicting writes that must be reconciled.
- **Leaderless**: Any node accepts writes. The client sends writes to multiple nodes in parallel (or a coordinator does). Reads similarly go to multiple nodes in parallel; the client reconciles any differences. No single authoritative write order.

**Q3. What is replication lag, and why is it the source of most eventual consistency issues?**
A: Replication lag is the delay between a write being committed on the leader/primary and that same write becoming visible on a replica. During the lag window, a read from the replica returns stale data. Lag can range from milliseconds (same data centre, synchronous streaming replication) to seconds or minutes (cross-region, asynchronous replication under heavy write load). Replication lag is the root cause of: stale reads after writes, read-your-own-writes failures, monotonic read violations, and causality violations. Every replication architecture produces lag under some conditions — the architectures differ in how they manage it, not in whether they produce it.

**Q4. What is synchronous vs asynchronous replication, and what does the choice affect?**
A: The distinction is whether the leader waits for the replica to confirm before acknowledging the write to the client:
- **Synchronous replication**: The leader does not acknowledge the write until at least one replica confirms receipt. Guarantees no data loss if the leader fails immediately after the write — the replica has the data. Cost: write latency includes the round-trip to the replica. If the replica is slow or unreachable, writes stall.
- **Asynchronous replication**: The leader acknowledges the write immediately after committing locally, then replicates in the background. Write latency is low and independent of replica health. Cost: if the leader fails before the replica receives the write, that write is lost — the replica may become leader and acknowledge a state that doesn't include the latest committed writes.
- **Semi-synchronous**: One replica is synchronous (guarantees at least one durable copy), the rest are asynchronous. PostgreSQL streaming replication's default: one synchronous standby, others async. Balances durability with write latency.

## Section 2: Single-Leader Replication

**Q5. How does single-leader replication work?**
A: One node is designated the leader (also called primary, master). All writes go to the leader. The leader writes to its local storage and simultaneously (or asynchronously) replicates the change to follower nodes via a **replication log** (Postgres: WAL — Write-Ahead Log; MySQL: binlog; Kafka: internal log). Each follower applies log entries in the same order they were written on the leader, maintaining an identical copy of the data. Reads can be served by any node — the leader for strong consistency, followers for eventual consistency with potential replication lag.

```
                    ┌──────────┐
Client Write ──────►│  Leader  │──────────────────────────────┐
                    └──────────┘                              │
                         │ replication log (WAL / binlog)     │
                    ┌────┴────┐                          ┌────┴────┐
                    │Follower1│                          │Follower2│
                    └─────────┘                          └─────────┘
Client Read ──────► any node (leader for fresh, follower for stale-ok)
```

**Q6. What is log-based replication, and how does it differ from statement-based replication?**
A: Two approaches to how the leader communicates changes to followers:
- **Statement-based replication** (MySQL's historical default): The leader ships the raw SQL statements to followers, which re-execute them. Simple, but breaks on non-deterministic statements (`NOW()`, `UUID()`, `RAND()`, auto-increment) — each follower computes a different value, diverging from the leader.
- **Row-based replication / log-based replication** (Postgres WAL, MySQL row-based binlog): The leader ships the actual data changes — "row with PK=42 changed from {old} to {new}" — rather than the SQL that caused the change. Deterministic regardless of the statement. More verbose (full row before and after every update) but correct. Change Data Capture (CDC) tools like Debezium read this log — the WAL or binlog — and stream changes to Kafka.

**Q7. What are the operational advantages of single-leader replication?**
A:
- **Simple write ordering**: There is one authoritative sequence of writes. No conflict resolution is needed — the leader is always the truth, and followers apply changes in the same order.
- **Read scalability**: Reads can be distributed across followers. A read-heavy workload (10:1 read:write ratio) benefits greatly from multiple read replicas.
- **Simple failover concept**: If the leader fails, one follower is promoted to leader. The new leader has the most recent copy of the data (modulo async replication lag).
- **Transactional consistency**: The leader runs full ACID transactions locally. Followers receive the committed result, not the transaction in progress — followers never see partial writes.
- **Operational maturity**: Single-leader is the default replication model for Postgres, MySQL, MongoDB (replica sets), and Redis Sentinel. Tooling, documentation, and operational knowledge are well-established.

**Q8. What are the failure modes and limitations of single-leader replication?**
A:
- **Leader is a write bottleneck**: All writes go to one node. Write throughput is bounded by a single machine's CPU, I/O, and network capacity. Horizontal write scaling is not possible without sharding.
- **Write availability during leader failover**: When the leader fails, there is a gap between failure detection and promotion of a new leader (typically 30 seconds to several minutes in Postgres with Patroni or RDS Multi-AZ). No writes are accepted during this window.
- **Replication lag and stale reads**: Asynchronous followers may be seconds behind the leader. A read immediately after a write may return the pre-write state if routed to a follower.
- **Split-brain risk**: If the leader is partitioned from the network but still running, it may continue accepting writes. If a follower is simultaneously promoted to leader, two nodes believe they are the leader and both accept writes — resulting in diverged data that must be manually reconciled. Preventing split-brain requires proper quorum-based leader election (Patroni + etcd, Raft).
- **Cross-geography write latency**: If the leader is in Mumbai and a client is in New York, all writes from New York go to Mumbai. The write latency includes the trans-oceanic round trip.

**Q9. How does leader failover work, and what can go wrong?**
A: Automatic failover involves three steps: detecting the leader failure, electing a new leader, and reconfiguring clients and followers to use the new leader. Each step has failure modes:

**Detection**: Heartbeat-based — followers detect the leader is unreachable if no heartbeat arrives within a timeout. Too short a timeout → false positives (a slow network causes unnecessary failover, disrupting a healthy but lagged leader). Too long → long outage duration.

**Election**: Followers elect the most up-to-date follower as the new leader. In an asynchronous replication setup, the elected follower may be missing the last N committed writes from the old leader (those writes were not yet replicated when the leader died). These writes are effectively lost — or must be discarded if the old leader recovers and tries to rejoin.

**Reconfiguration**: Clients must be redirected to the new leader. Stale connections to the old leader must be terminated. If the old leader recovers, it must demote itself to follower and apply the changes it missed from the new leader's log — or be discarded entirely if its data has diverged.

What can go wrong: **split-brain** (two nodes believe they are leader); **data loss** (async replication lag at failover time); **incorrect failover** (a follower significantly behind is promoted, missing many committed writes); **client confusion** (clients routing to the old leader after failover).

**Q10. What is read-your-own-writes consistency and how do you implement it with single-leader replication?**
A: Read-your-own-writes (RYOW) guarantees that after a user performs a write, their subsequent reads reflect that write — even if reads are routed to followers that may lag behind. Without RYOW, a user saves their profile and immediately sees the old profile because the read hit a lagged replica. Implementation strategies:
- **Route user's reads to the leader for a window after a write**: Track the last write timestamp per user session. If `now - last_write < lag_estimate`, route reads to the leader; otherwise use a follower.
- **Read from the leader always for user-owned data**: Data a user modifies (their own profile, their own settings) always reads from the leader. Data they only view (other users' profiles, public feeds) can go to followers.
- **Include the write's replication position in the response**: After a write, the leader returns the WAL position (LSN in Postgres). The client passes this LSN on subsequent reads; the follower only serves the read after its replication has caught up to that LSN (`SELECT pg_last_wal_replay_lsn() >= $client_lsn`).

## Section 3: Multi-Leader Replication

**Q11. How does multi-leader replication work?**
A: Multiple nodes are designated leaders — each accepts writes independently and replicates to all other leaders (and to their own followers). Each leader processes its writes locally, then asynchronously forwards them to other leaders, which apply them to their local state. From each leader's perspective, changes from other leaders look like replicated writes arriving from a peer:

```
         ┌──────────────────────────────────────┐
         │  replication between leaders          │
         │  (async, bidirectional)               │
    ┌────▼─────┐                        ┌────────▼───┐
    │ Leader A │                        │  Leader B  │
    │(DC Mumbai)│◄──────────────────────►│(DC Singapore)│
    └─────┬────┘                        └──────┬─────┘
          │ WAL                                │ WAL
    ┌─────▼──────┐                    ┌────────▼──────┐
    │ Follower A1│                    │  Follower B1  │
    └────────────┘                    └───────────────┘
```

Writes made to Leader A are replicated to Leader B and vice versa. A user in Mumbai writes to Leader A; a user in Singapore writes to Leader B. Both changes eventually appear on both leaders — but if both users modify the same row concurrently, a **write conflict** occurs that must be detected and resolved.

**Q12. When is multi-leader replication the right choice?**
A: Multi-leader is appropriate in a narrow set of scenarios where its complexity is justified:
- **Multi-datacenter active-active deployments**: Each data centre needs to accept writes with low latency. Single-leader with a leader in Mumbai forces Singapore users to pay the trans-oceanic write round trip (~100ms). Multi-leader lets each DC accept writes locally and replicate asynchronously — writes are fast for users near any leader.
- **Offline-capable clients**: Mobile apps or desktop apps that must work offline and sync when reconnected. Each device is effectively a leader for its local changes; conflict resolution handles the sync. Google Docs, Notion, and calendar apps use this model.
- **Collaborative editing**: Multiple users editing the same document simultaneously — CRDTs or operational transformation handle the conflict resolution that multi-leader replication requires.
- **NOT for most transactional systems**: Multi-leader is almost never the right choice for financial data (payments, balances, inventory). The conflict resolution requirements and the risk of data anomalies outweigh the write latency benefits for ACID-sensitive workloads.

**Q13. What is a write conflict in multi-leader replication, and why does it occur?**
A: A write conflict occurs when two leaders concurrently receive writes to the same data and those writes are incompatible. Example: Leader A and Leader B both receive an update to `user:42.name` — Leader A sets it to "Alice" and Leader B sets it to "Alicia" at the same millisecond. Both commits succeed locally. When the leaders exchange their replication logs, they both see a conflict: the same row was modified by two leaders with no causal relationship between the writes. The database must decide which value to keep — there is no deterministic "correct" answer based on the data alone.

**Q14. What are the strategies for conflict detection and resolution?**
A: Conflict detection is straightforward (compare write versions or timestamps); conflict resolution is the hard part. Strategies in order of sophistication:

- **Last Write Wins (LWW)**: Keep the write with the most recent timestamp; discard the other. Simple, widely used (Cassandra's default). Dangerous: wall-clock timestamps are unreliable across nodes (clock skew means "most recent" is ambiguous), and LWW silently discards legitimate writes without any error.
- **Conflict avoidance**: Route all writes for a given record through the same leader — the user who owns record X always writes to Leader A. Eliminates conflicts for that record entirely. Works well when records have a natural affinity (user's own data → always their local DC leader).
- **Merge / CRDT-based resolution**: Design the data structure so concurrent writes can always be merged deterministically without conflict. A CRDT (Conflict-free Replicated Data Type) guarantees that any two nodes applying the same set of operations in any order converge to the same result. A grow-only counter, or an OR-Set (observed-remove set). Applicable to specific data types, not arbitrary relational updates.
- **Custom conflict resolution logic**: On conflict, call application-level logic — "for account balances, sum both increments; for profile updates, keep the one from the user's home region." Requires the application to understand the semantics of every conflictable field. Complex but correct.
- **Expose conflict to the user**: Show both conflicting versions and ask the user to choose. Used in collaborative tools (Google Docs "version history"), not acceptable for automated financial data.

**Q15. What is a replication topology in multi-leader replication?**
A: The topology defines how leaders replicate to each other. Three options:

- **All-to-all**: Every leader sends its writes directly to every other leader. Most resilient — if one replication path fails, changes still arrive via other paths. Risk: write ordering is not guaranteed — Leader C may receive a write that causally depends on another write that hasn't arrived yet (causality violation). Requires version vectors or logical timestamps to detect and buffer out-of-order writes.
- **Star topology**: One central leader forwards writes from all other leaders. Simple, but the central node is a single point of failure and a bottleneck.
- **Circular topology**: Each leader forwards writes to the next in a ring. A failure of one node breaks the ring — writes from nodes on either side can't reach each other. Fragile, rarely used.

All-to-all is most common for multi-DC deployments. Version vectors (one counter per leader per row, tracking which leader's write is the latest seen) are the standard mechanism for causality tracking.

**Q16. What are the operational pitfalls unique to multi-leader replication?**
A:
- **Conflict resolution bugs are silent data corruption**: A LWW conflict that discards a legitimate payment write doesn't throw an error — the data is simply wrong. In single-leader replication, the "wrong" outcome is a serialisation failure that the client retries; in multi-leader, the "wrong" outcome is silently committed data.
- **Schema changes are operationally complex**: A schema migration (adding a column, changing a type) must be coordinated across all leaders simultaneously. Applying it to Leader A before Leader B means Leader A's replication log includes column values that Leader B's schema doesn't know about — replication breaks.
- **Debugging replication conflicts requires understanding causality**: "Why did this row end up with value X?" may require tracing back through multiple leaders' replication logs across multiple data centres. Much harder to debug than single-leader.
- **Testing is harder**: Local development with a single-node DB doesn't reproduce multi-leader conflict scenarios. Integration testing requires a multi-node setup with conflict injection.

## Section 4: Leaderless Replication

**Q17. How does leaderless replication work?**
A: There is no designated leader — any node can accept writes, and any node can serve reads. The client (or a coordinator node acting on behalf of the client) sends writes and reads to multiple nodes in parallel, using a quorum to determine success:

```
Client Write ──► Node 1  ✓
             ──► Node 2  ✓   (W=2 out of N=3 nodes ACKed → write success)
             ──► Node 3  ✗   (one node missed the write)

Client Read  ──► Node 1  {v=5, value="A"}
             ──► Node 2  {v=5, value="A"}   (R=2, take newest version)
             ──► Node 3  {v=4, value="B"}   ← stale, missed the write
             Result: return "A" (highest version)
             Repair: send {v=5, value="A"} to Node 3 (read repair)
```

Write quorum: W nodes must acknowledge. Read quorum: R nodes must respond. For strong consistency: W + R > N (the read set and write set must overlap — at least one node in every read has the latest write). Example with N=3: W=2, R=2 → W+R=4 > 3 → guaranteed overlap.

**Q18. What are W, R, and N, and how do you tune them?**
A: These are the quorum parameters:
- **N**: The replication factor — how many nodes store a copy of each piece of data. Typical: 3 or 5.
- **W**: Write quorum — how many nodes must acknowledge a write before it's considered successful.
- **R**: Read quorum — how many nodes must respond to a read before a result is returned.

Tuning trade-offs:
- **W=1, R=N (read-heavy, write-fast)**: Writes succeed as soon as one node acknowledges. Reads query all nodes to find the latest. Fast writes, slow reads, low write durability (if the one acknowledging node dies before replication, the write is lost).
- **W=N, R=1 (write-durable, read-fast)**: Writes only succeed when all nodes acknowledge — very durable but slow writes (blocked by the slowest node). Reads only need one response. Any node failure blocks writes entirely.
- **W=⌈N/2⌉+1, R=⌈N/2⌉+1 (balanced, strong consistency)**: With N=3: W=2, R=2. Balanced write and read latency. Guarantees every read overlaps with the write quorum — no stale reads if the system is healthy.
- **W=1, R=1 (maximum availability, eventual consistency)**: Any node handles any operation. Fastest but no consistency guarantees — stale reads are common.

For fintech read-after-write on critical data: W=2, R=2, N=3. For analytics or approximate counts: W=1, R=1.

**Q19. What is read repair, and what is anti-entropy?**
A: Two mechanisms that bring diverged nodes back into sync in a leaderless system:

**Read repair**: When a read is served by multiple nodes and the coordinator detects that some nodes returned stale data (lower version number), it immediately writes the latest value back to the stale nodes. Happens synchronously during the read path — no background process needed. Effective for frequently-read data. Ineffective for data that is rarely read — stale data on infrequently-read keys may persist indefinitely.

**Anti-entropy (background sync)**: A background process that runs continuously, comparing data between nodes and copying any values that differ. Does not guarantee any particular order of repair — it just ensures eventual convergence. Implemented as a Merkle tree comparison: each node computes a hash of its data in tree form; nodes exchange Merkle tree roots first, then recursively compare subtrees to find diverged leaves efficiently, without exchanging all data. Used by Cassandra (`nodetool repair`), DynamoDB, and Riak.

**Q20. What is a sloppy quorum, and what is hinted handoff?**
A: Both mechanisms allow leaderless systems to remain available when some of the designated replica nodes for a key are temporarily unreachable:

**Sloppy quorum**: Normally, a write to a key goes to its designated N replica nodes. If some of those nodes are unreachable, a sloppy quorum allows the write to be accepted by other nodes outside the designated set — as long as W nodes acknowledge. The write is stored on nodes that are not the "home" nodes for this key.

**Hinted handoff**: The node that accepted the write on behalf of the unavailable home node stores a "hint" — "this data belongs to Node 3, deliver it when Node 3 comes back." When Node 3 recovers, the hint-holding node forwards the write. Together, sloppy quorum + hinted handoff allow writes to succeed during partial failures without blocking — at the cost of temporarily violating strict quorum guarantees. DynamoDB uses both by default for its "always available" writes.

**Q21. What are the consistency anomalies that leaderless replication cannot prevent even with W + R > N?**
A: The W + R > N guarantee holds only if: the N nodes are stable and the write set and read set actually overlap. Several anomalies break this assumption:

**Concurrent writes (write-write conflict)**: Two clients concurrently write different values to the same key. Both satisfy W=2 quorum. Both are "successful." But the two values are inconsistent across nodes — different nodes saw the writes in different orders. Last-write-wins with wall-clock timestamps resolves this but may silently discard one write.

**Read skew (non-repeatable read)**: A client reads two related records as part of a single logical operation — one from a node with the latest value, one from a node with a stale value. The two reads are inconsistent with each other. Single-leader transactions prevent this; leaderless has no transaction scope spanning multiple reads.

**Write skew**: Two clients read a shared condition (e.g., "is there at least one doctor on call?"), both see true, both decide to go off call — now zero doctors are on call. Leaderless has no mechanism to prevent this without application-level locking or a linearisable compare-and-swap.

**Stale reads after concurrent writes**: A node that didn't receive a write (was part of neither the W write set nor the R read set) may serve a stale read to a client. Even with W + R > N, if the read happens on a partitioned node that hasn't received the write, the stale value is returned.

## Section 5: Comparison & Decision-Making

**Q22. How do you choose between single-leader, multi-leader, and leaderless replication?**
A: Decision framework based on primary requirements:

| Requirement | Single-Leader | Multi-Leader | Leaderless |
|---|---|---|---|
| Strong consistency (ACID) | ✅ Best — total write order | ❌ Conflict resolution breaks ACID | ⚠️ Possible with W+R>N, but anomalies exist |
| Write throughput scalability | ❌ One leader is the ceiling | ✅ N leaders, N× write throughput | ✅ Any node accepts writes |
| Write availability during leader failure | ❌ Gap during failover | ✅ Other leaders continue | ✅ Quorum of remaining nodes continues |
| Multi-DC active-active writes | ❌ High cross-DC write latency | ✅ Local DC leader for low latency | ✅ Any DC node can write |
| Operational simplicity | ✅ Simple, mature tooling | ❌ Conflict resolution, schema migrations | ⚠️ Simpler than multi-leader, but quorum tuning is subtle |
| Financial / payment data | ✅ Only safe choice | ❌ Conflict risk is unacceptable | ❌ Too many anomalies |
| Social feeds, counters | ✅ Fine | ⚠️ Overkill | ✅ Ideal — eventual consistency is acceptable |
| Collaborative editing | ❌ Not designed for it | ✅ With CRDT conflict resolution | ✅ With CRDT |

**Q23. What replication model does each major database use?**
A:
- **PostgreSQL**: Single-leader (streaming replication, WAL-based). Patroni or Stolon for automatic failover. Logical replication (pglogical) for multi-leader, though rarely used.
- **MySQL**: Single-leader (binlog-based). Group Replication (Paxos-based) for multi-primary. NDB Cluster for multi-leader at the storage engine level.
- **MongoDB**: Single-leader per replica set (Raft-based election). Sharded clusters: one replica set (single-leader) per shard.
- **Cassandra**: Leaderless (inspired by Amazon Dynamo). W, R, N tunable per operation. Anti-entropy via Merkle tree. Quorum levels: `ONE`, `QUORUM`, `LOCAL_QUORUM`, `ALL`.
- **DynamoDB**: Leaderless with sloppy quorum and hinted handoff. Eventually consistent reads by default; strongly consistent reads available (costs 2× read capacity units).
- **Redis**: Single-leader per shard (Redis Sentinel or Redis Cluster). Redis Cluster: multiple shards, each with a single-leader replica set.
- **CockroachDB / YugabyteDB**: Raft-based per-range single-leader replication, distributed across nodes. Presents a SQL interface with distributed ACID semantics.
- **Elasticsearch**: Single-leader per shard (primary shard + replica shards). Sequence numbers for in-sync replica set tracking.

**Q24. What is the relationship between replication and the CAP theorem?**
A: CAP states that during a network partition, a distributed system must choose between Consistency (every read returns the latest write) and Availability (every request returns a response, even if stale). The three replication architectures make this choice differently:

**Single-leader (CP during partition)**: If the leader is partitioned from followers and quorum is required for promotion, the system rejects writes (not available) rather than risk split-brain or data loss. Prioritises consistency over availability during partition. Postgres with Patroni + etcd: if etcd loses quorum, no new leader is elected — writes halt.

**Multi-leader (AP during partition)**: Each leader continues accepting writes locally during a partition — high availability. When the partition heals, conflicts must be resolved. Prioritises availability over consistency.

**Leaderless with W+R>N (tunable CP/AP)**: If W is high (e.g., W=N), a single node failure causes write unavailability — CP. If W is low (e.g., W=1) with sloppy quorum, writes always succeed — AP. Leaderless replication lets you tune the CP/AP dial per operation by adjusting W and R. DynamoDB's eventual consistent reads are AP; its strongly consistent reads are CP.

**Q25. What is the PACELC theorem, and why does it extend CAP?**
A: CAP only describes the consistency/availability trade-off during a network partition. PACELC (Pat Helland, 2012) extends this: **even in the absence of a partition (E — else)**, a distributed system must choose between **L (Latency)** and **C (Consistency)**. Serving a strongly consistent read means waiting for quorum acknowledgement — adding latency. Serving a fast read means reading from a single local replica — potentially stale. The PACELC framing better describes the everyday trade-offs in distributed databases:

- **Single-leader with synchronous replication**: PA/LC — available during partition (followers serve reads), low latency/consistency during normal operation (writes wait for replica ack — consistent but higher latency).
- **Leaderless with W+R>N, no sloppy quorum**: PC/LC — consistent during partition (reject if quorum unavailable), low latency/consistency trade-off in normal operation (wait for quorum = higher latency for consistency).
- **DynamoDB eventual consistent reads**: PA/EL — available during partition, else optimise for latency (don't wait for quorum — serve from any replica, accept staleness).

For interview purposes: CAP explains what breaks during partitions; PACELC explains the everyday latency/consistency trade-off that matters even when the network is healthy.

## Section 6: Replication in Practice

**Q26. How does Postgres streaming replication work in detail?**
A: Postgres replication is WAL-based:
1. Every write on the primary produces WAL records — the exact byte-level changes to data pages.
2. The WAL sender process on the primary streams WAL records to the WAL receiver on each standby over a replication connection.
3. The standby's WAL receiver writes the records to its WAL and the recovery process replays them, applying changes to the standby's data files.
4. The standby acknowledges the LSN (Log Sequence Number) of the last WAL record it has replayed back to the primary.
5. If `synchronous_standby_names` is configured, the primary waits for at least one standby to acknowledge up to the current LSN before returning success to the client.

Key operational metrics: `pg_stat_replication` shows each standby's `write_lag`, `flush_lag`, `replay_lag` — the delay at each stage of WAL propagation. A high `replay_lag` means the standby is behind on applying changes — reads from this standby return stale data proportional to the replay lag.

**Q27. How do you handle replication lag operationally in a Postgres setup?**
A: Monitoring and routing:
- **Monitor `pg_last_wal_replay_lsn()` on standbys** — compare to the primary's `pg_current_wal_lsn()` to get the byte offset gap. Alert if lag exceeds a threshold (e.g., > 10MB or > 5 seconds of WAL).
- **Route reads intelligently**: Tag application queries as `stale_ok` or `fresh_required`. Only `fresh_required` queries go to the primary; `stale_ok` queries go to standbys. Implement as a middleware layer or PgBouncer routing rule.
- **Synchronous replication for critical paths**: Configure `synchronous_commit = on` for transactions that require zero replication lag at commit time (e.g., payment confirmation). This adds one network round-trip to the write but guarantees the standby has the data before the client is informed of success.
- **`pg_sleep` anti-pattern**: Never use `pg_sleep` delays to "wait for replication" — use LSN-based read-after-write as described in Q10 instead.
- **Logical replication slots**: Postgres logical replication slots hold the WAL on the primary until all downstream consumers have received it. If a consumer stops consuming (Debezium paused, replica disconnected), the WAL slot causes the primary's WAL directory to grow unboundedly — disk exhaustion. Monitor `pg_replication_slots` and alert on high `lag_bytes`.

**Q28. How does Cassandra's leaderless replication work with consistency levels?**
A: Cassandra partitions data across a ring of nodes using consistent hashing. For a given partition key, a set of N replica nodes (determined by the replication factor and placement strategy) are responsible for storing that key. When a client writes:
1. The coordinator node (any node the client connects to) routes the write to all N replica nodes for that partition key.
2. The write succeeds when W of those N nodes acknowledge.
3. Nodes that didn't acknowledge receive the write asynchronously (hinted handoff if they're down).

Consistency levels translate to W and R:
- `ONE`: W=1 or R=1 — any single replica suffices. Fastest, most available, eventually consistent.
- `QUORUM`: W=⌊N/2⌋+1 or R=⌊N/2⌋+1 — majority quorum. With N=3: W=R=2. Guarantees overlap → no stale reads if all nodes are healthy.
- `LOCAL_QUORUM`: Quorum within the local data centre only — avoids cross-DC latency while still providing DC-level consistency. Most common for multi-DC Cassandra deployments.
- `ALL`: W=N or R=N — all replicas must respond. Maximum consistency, minimum availability (any replica failure blocks the operation).
- `SERIAL` / `LOCAL_SERIAL`: Linearisable read via Paxos for lightweight transactions (`IF NOT EXISTS`, `IF version = x`). Used for idempotency checks and compare-and-swap operations.

## Section 7: Scenario / System Design Questions

**Q29. "Your payment platform uses Postgres with one primary and two read replicas. A user completes a payment but sees 'pending' on the order status page for 3 seconds. What's happening, and how do you fix it?"**
A: Classic RYOW (read-your-own-writes) failure caused by replication lag. The payment write was committed on the primary. The order status page read was routed to a replica that hadn't applied the write yet — it returned the pre-payment state.

**Root cause investigation**: Query `pg_stat_replication` on the primary — check `replay_lag` for the replica that served the read. Even a 3-second lag at the time of the write explains the symptom.

**Fixes in order of implementation cost**:
1. **Return updated state in the write response**: The payment API response includes the full updated order object. The UI updates directly from the response — no re-read needed. Eliminates the RYOW problem without any infrastructure change.
2. **LSN-based read-after-write**: After the payment write, the primary returns the commit LSN. The client passes this LSN on the status page read; the application layer routes to the primary OR waits for a replica to reach that LSN before serving the read from the replica.
3. **Route post-payment reads to primary for a window**: After any write tagged as a payment commit, route that user's reads to the primary for 5 seconds (tracked in Redis). Simpler than LSN tracking but adds primary read load.
4. **Synchronous replication for payment transactions**: Set `synchronous_commit = on` for the payment transaction — the primary waits for at least one replica to confirm before acknowledging the commit. Adds ~1–5ms to write latency but eliminates replication lag at commit time. The replica is always consistent with the primary by the time the client sees the write acknowledgement.

**Q30. "Your team is proposing a multi-leader Postgres setup across Mumbai and Singapore for low write latency. What questions do you ask and what risks do you raise?"**
A: This is a red flag proposal for a fintech system. Questions and risks to raise:

**Questions**:
- What data will be written by both leaders concurrently? Payment records? User balances? If yes, what is your conflict resolution strategy for a row that's updated by both leaders simultaneously?
- What are the semantics of a conflict on a balance field — do you sum the two increments, take the later timestamp, or reject one? Who decides?
- How will you handle schema migrations across two leaders in different time zones? What happens if Leader A applies the migration and Leader B hasn't received it yet when a write arrives?
- Have you measured the current Mumbai-to-Singapore write latency? (Typically 60–80ms.) Is 60–80ms write latency actually a user-visible problem for your use case?

**Risks**:
- **Silent data corruption from LWW conflicts**: If two concurrent payment status updates conflict and LWW discards one, a payment that should be "confirmed" is silently left as "pending" — or vice versa. No error is thrown; the data is simply wrong.
- **Regulatory compliance**: RBI regulations require accurate, auditable payment records. A multi-leader setup with conflict resolution that can discard writes is fundamentally incompatible with financial record integrity requirements.
- **Operational complexity cost**: Multi-leader Postgres requires pglogical or custom logical replication. Schema migrations, index creation, and sequence management all become coordination problems. The operational burden is significant.

**Alternative recommendation**: Single-leader Postgres in Mumbai (primary region). For Singapore users, use **read replicas** in Singapore for read traffic — this solves the majority of the latency problem (reads are typically 90% of traffic). For writes, 60–80ms cross-region latency is typically not user-visible when the write response itself carries the updated state (no re-read required). If Singapore write latency is genuinely unacceptable after measurement, explore **application-level sharding** (Singapore users' data lives on a Singapore cluster, Mumbai users' data on a Mumbai cluster) — no cross-leader conflicts because the data sets don't overlap.

**Q31. "Design the replication strategy for a NACH payment processing system that needs zero data loss on leader failure."**
A: Zero data loss on leader failure requires synchronous replication — at least one replica must have confirmed receipt of every write before the leader acknowledges success. Design:

**Replication setup**:
- Postgres primary in the primary AZ (e.g., ap-south-1a).
- One synchronous standby in a second AZ (ap-south-1b) — `synchronous_standby_names = 'standby1'`. Every committed transaction is confirmed by this standby before the client sees success.
- One asynchronous standby in a third AZ (ap-south-1c) for additional read capacity and disaster recovery — accepts some replication lag.

**Failover**:
- Patroni with etcd for automatic leader election. If the primary fails, Patroni promotes the synchronous standby (which has all committed data) to primary within 30–60 seconds.
- The async standby may be slightly behind the new primary after failover — it catches up via WAL streaming from the new primary before being marked as a valid read replica.

**Why synchronous replication for NACH specifically**:
- A NACH debit write that succeeds on the primary but is lost before reaching any replica means: the DB shows no record of the debit, but the bank was instructed to execute it. The bank executes the debit; the system has no record. Account reconciliation finds a discrepancy. This is a regulatory and financial integrity failure. The 1–5ms latency cost of synchronous replication is completely justified.

**Monitoring**:
- Alert if the synchronous standby's `replay_lag > 1 second` — this means the synchronous standby is falling behind and writes may begin blocking.
- Alert if `pg_replication_slots` shows high `lag_bytes` for logical replication slots (Debezium CDC).
- Alert if the number of synchronous standbys drops to zero — all writes are now async-only, zero data loss guarantee is gone.

## Quick Comparison Table

| Aspect | Single-Leader | Multi-Leader | Leaderless |
|---|---|---|---|
| Write target | One leader | Any leader | Any node |
| Write conflicts | Impossible (total order) | Possible, must resolve | Possible, version-based merge |
| Consistency | Strong (on leader) | Eventual (conflict resolution) | Tunable (W + R > N) |
| Write availability | Gap during failover | Always (other leaders) | Always (quorum of nodes) |
| Write latency (multi-DC) | High (all to one DC) | Low (local DC leader) | Low (local node) |
| Conflict resolution | Not needed | Required, complex | LWW or CRDT |
| Schema migration | Straightforward | Operationally complex | Straightforward |
| Used by | Postgres, MySQL, MongoDB, Redis | MySQL Group Replication, CouchDB | Cassandra, DynamoDB, Riak |
| Right for fintech | ✅ Yes | ❌ Avoid | ⚠️ With careful quorum tuning |

**Tip for the interview:** At the 5 YOE level, the key signal is understanding *why* single-leader is almost always the right choice for financial data, stated as a consequence of conflict resolution semantics — not just "it's simpler." Be ready to explain what a write conflict in multi-leader replication means for a payment record specifically (silent data corruption, regulatory non-compliance), and to propose the correct alternative (application-level sharding, read replicas) when someone suggests multi-leader for latency reasons. For leaderless, know the quorum arithmetic cold: with N=3, W=2, R=2, walk through why W+R>N guarantees read-write overlap, then explain the anomalies that break this guarantee (sloppy quorum, concurrent writes, read skew). Connecting every replication concept to a concrete failure mode with a concrete mitigation is what separates a senior answer from a textbook recitation.
