# ZooKeeper / etcd: Leader Election, Distributed Coordination — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do ZooKeeper and etcd solve?**
A: Distributed systems need a small set of primitives that are extremely difficult to implement correctly on commodity services — things like "only one process should be the leader," "all nodes should agree on a configuration value," or "this lock should be held by exactly one client." These primitives require consensus: the ability for a cluster of nodes to agree on a value even when some nodes fail or messages are delayed.

ZooKeeper and etcd are purpose-built consensus services — they sacrifice some throughput and flexibility to give you strong consistency guarantees that general-purpose databases don't provide. They are the coordination layer that other distributed systems (Kafka, Kubernetes, HBase, Hadoop) rely on for their own correctness.

**Q2. What is the difference between ZooKeeper and etcd?**
A: Both provide strongly consistent key-value storage with watch/notification primitives, but differ in design philosophy:

| Aspect | ZooKeeper | etcd |
|---|---|---|
| Consensus protocol | ZAB (ZooKeeper Atomic Broadcast) | Raft |
| Data model | Hierarchical tree of znodes | Flat key-value with range queries |
| API | Custom ZK protocol (TCP) | gRPC / HTTP/2 |
| Watch semantics | One-time watch (must re-register after fire) | Continuous watch streams (persistent) |
| Transactions | Multi-op (conditional multi-step) | Transactions with If/Then/Else |
| Primary ecosystem | Hadoop, Kafka, HBase, older JVM systems | Kubernetes, CoreDNS, newer Go-based systems |
| Client complexity | Higher (session management, ephemeral nodes) | Lower (simpler API, lease-based TTL) |
| Operational maturity | Older (2007), very battle-tested | Newer (2013), cloud-native standard |

**Q3. What consistency guarantee do ZooKeeper and etcd provide?**
A: Both provide **linearizability** for writes and reads routed through the leader — the strongest consistency model for distributed systems. A linearizable system behaves as if all operations execute atomically on a single machine, in some order consistent with their real-time order. Specifically:
- Every write is acknowledged only after a quorum of nodes has durably recorded it.
- Every read reflects the latest acknowledged write.
- No client ever reads a value that was written "in the future" relative to any other client's view.

ZooKeeper additionally provides a weaker read option — reads can be served from any follower for higher throughput (potentially stale). etcd defaults to linearizable reads (routed through leader) with an option for serializable (potentially stale) reads for performance.

**Q4. What is quorum and why does it matter?**
A: A quorum is the minimum number of nodes that must agree before an operation is considered committed. For a cluster of N nodes, quorum = ⌊N/2⌋ + 1 (a strict majority):
- 3-node cluster: quorum = 2. Tolerates 1 failure.
- 5-node cluster: quorum = 3. Tolerates 2 failures.
- 7-node cluster: quorum = 4. Tolerates 3 failures.

Quorum ensures that any two successful operations share at least one common node — guaranteeing that the latest committed write is visible to any subsequent operation. Without majority quorum, two separate groups could independently commit conflicting values (split-brain). The minimum viable production cluster is 3 nodes (tolerates 1 failure). 5 nodes is standard for systems requiring higher fault tolerance.

**Q5. What is the ZAB protocol (ZooKeeper Atomic Broadcast)?**
A: ZAB is ZooKeeper's consensus protocol, designed specifically for primary-backup coordination:
- **Leader election phase:** On startup or leader failure, nodes run an election to choose a new leader — the node with the highest `zxid` (transaction ID) wins, ensuring the most up-to-date node becomes leader.
- **Recovery phase:** The new leader synchronizes followers by replaying any committed transactions they may have missed.
- **Broadcast phase (steady state):** All writes go to the leader. The leader assigns a `zxid`, broadcasts the write to all followers as a proposal, waits for ACKs from a quorum, then commits and broadcasts the commit. Followers apply the commit in `zxid` order — total order guaranteed.

ZAB guarantees that all delivered messages are delivered in the same total order on all nodes, and that any message delivered by a new leader was delivered by the previous leader.

**Q6. What is the Raft protocol and how does etcd use it?**
A: Raft is a consensus protocol designed for understandability — it breaks the consensus problem into three relatively independent sub-problems:

**Leader election:** Each node starts as a follower. If a follower receives no heartbeat from a leader within an election timeout (150–300ms), it becomes a candidate, increments its term, and requests votes from peers. A node wins if it receives votes from a majority. Terms ensure stale leaders can't cause harm — any node receiving a message from a higher term immediately steps down.

**Log replication:** The leader receives client writes, appends them to its log, and replicates log entries to followers. An entry is committed when a majority of nodes have written it to their log. The leader then applies committed entries to its state machine and responds to the client.

**Safety:** Raft's election constraint guarantees that a leader always has all committed entries — a node can only win an election if its log is at least as up-to-date as a majority of nodes. This prevents a stale node from becoming leader and losing committed data.

etcd uses Raft with persistent storage (WAL) — every log entry is fsynced to disk before being acknowledged, ensuring no committed data is lost even on power failure.

## Section 2: Leader Election

**Q7. How does ZooKeeper implement leader election?**
A: The canonical ZooKeeper leader election pattern uses ephemeral sequential znodes:

```
1. All candidates create an ephemeral sequential znode under /election/
   e.g., /election/candidate-0000000001
         /election/candidate-0000000002
         /election/candidate-0000000003

2. Each candidate lists all children of /election/ and finds the node
   with the lowest sequence number.

3. The candidate with the lowest sequence number is the leader.
   Others watch the znode with the next-lower sequence number
   (NOT all children — avoids herd effect).

4. When the watched znode is deleted (its owner crashed — ephemeral nodes
   auto-delete on session loss), the watcher checks again:
   - If it now has the lowest sequence number → it becomes the new leader.
   - Otherwise → watch the new predecessor.

5. The elected leader performs its leader duties and keeps its ZK session
   alive with heartbeats. Session loss = automatic leadership relinquishment.
```

**Why ephemeral nodes?** ZooKeeper sessions have a timeout. If the leader process crashes, hangs, or loses network connectivity for longer than the session timeout, its session expires and all its ephemeral znodes are automatically deleted — triggering election of a new leader without any explicit "I died" signal.

**Q8. How does etcd implement leader election?**
A: etcd's leader election uses leases and the `campaign` API (implemented in the official etcd `concurrency` package):

```go
import (
    clientv3 "go.etcd.io/etcd/client/v3"
    "go.etcd.io/etcd/client/v3/concurrency"
)

func runLeaderElection(client *clientv3.Client, instanceID string) {
    // Create a session with a TTL — the lease.
    // If this process dies, the lease expires and leadership is released.
    session, err := concurrency.NewSession(client, concurrency.WithTTL(10))
    if err != nil { panic(err) }
    defer session.Close()

    election := concurrency.NewElection(session, "/my-service/leader")

    // Campaign blocks until this instance wins the election.
    ctx := context.Background()
    if err := election.Campaign(ctx, instanceID); err != nil {
        panic(err)
    }

    fmt.Printf("I am the leader: %s\n", instanceID)

    // Do leader work here.
    // Resign when done (or process dies → lease expires → automatic resign).
    defer election.Resign(ctx)
}
```

Under the hood, `Campaign` creates a key under the election prefix with a lease attached. The instance with the lexicographically smallest key (oldest campaign) is the leader. Others watch for deletion of the current leader key and re-check their position.

**Q9. What is the "split-brain" problem in leader election and how do ZooKeeper and etcd prevent it?**
A: Split-brain occurs when two nodes both believe they are the leader simultaneously — both accept writes, creating diverging state. It can happen when:
- Network partitions isolate the leader from the cluster — the leader thinks it's alive; the cluster elects a new one; now both are "leader."
- A slow GC pause causes the leader to miss heartbeats — it's deposed, a new leader is elected, the old leader resumes and doesn't know it lost.

**ZooKeeper prevention:**
- The leader must maintain an active ZK session via heartbeats. On network partition, the leader can't heartbeat ZK, so its session expires, its ephemeral leader znode is deleted, and a new leader is elected. The old leader, on reconnect, discovers its session expired — it must stop acting as leader.
- **Fencing:** The elected leader gets a monotonically increasing `zxid`. Resources (DBs, services) should reject requests from a leader with a lower `zxid` than they've seen — preventing a deposed leader from causing harm.

**etcd prevention:**
- Leases with TTL. If the leader doesn't renew its lease (network partition, crash), the lease expires, the leader key is deleted, and a new election fires.
- The Raft protocol itself prevents split-brain at the consensus layer: a leader can only commit writes if it can reach a quorum. A partitioned leader can't reach quorum → can't commit → effectively read-only even if it doesn't know it's deposed.

**Q10. What is the "fencing token" and why is it essential even with ZooKeeper / etcd leader election?**
A: Leader election gives you a distributed agreement on who the leader is — but it cannot prevent a deposed leader from taking harmful actions if it doesn't know it's been deposed. Scenario:
1. Leader A holds the ZK/etcd lease.
2. A experiences a long GC pause (30 seconds).
3. After 15 seconds (lease TTL), the lease expires. Leader B is elected.
4. B starts writing to the database.
5. A's GC pause ends. A doesn't know it lost leadership. A also writes to the database.
6. Now A and B are both writing — split-brain at the application layer.

**Fencing token:** Each time leadership is granted, a monotonically increasing token (ZooKeeper's `zxid`, etcd's revision number) is issued. Every write to an external resource includes this token. The resource maintains the highest token it has seen and rejects writes with a lower token:

```
Leader A (token 42) → write request with token 42 → DB accepts (highest seen: 42)
Leader B (token 43) → write request with token 43 → DB accepts (highest seen: 43)
Leader A (stale, token 42) → write request with token 42 → DB REJECTS (42 < 43)
```

The external resource enforces the fencing — ZooKeeper/etcd can't do this alone, because they can't intercept arbitrary application-level writes.

## Section 3: Distributed Coordination Primitives

**Q11. What is a ZooKeeper znode and what types exist?**
A: A znode is a node in ZooKeeper's hierarchical data tree (similar to a filesystem). Each znode has: a path, data (up to 1MB), ACLs, and metadata (version, timestamps, child count). Four types:

- **Persistent:** Survives client disconnection and session expiry. Explicitly deleted.
- **Ephemeral:** Deleted automatically when the creating client's session expires or disconnects. Cannot have children. Used for presence detection and locks.
- **Persistent Sequential:** Same as persistent, but ZooKeeper appends a monotonically increasing 10-digit suffix to the znode name. Guaranteed globally unique within the parent.
- **Ephemeral Sequential:** Ephemeral + sequential suffix. The foundation of leader election and distributed lock patterns.
- **Container znodes (3.6+):** Deleted automatically when their last child is deleted. Useful for recipe containers.

**Q12. What is a ZooKeeper watch and what are its semantics?**
A: A watch is a one-time trigger: a client registers interest in a znode, and ZooKeeper sends a notification when that znode changes (data change, creation, deletion, or child list change). Critical semantics:
- **One-time:** The watch fires once and is then removed. The client must re-register the watch if it wants continued notifications.
- **Ordered:** Watches are delivered in the order events occurred.
- **Guaranteed delivery:** A watch event is delivered before any subsequent state change is visible to the client — the client sees the notification before it sees the new state.

**Implication of one-time watches:** Between the watch firing and the client re-registering, additional changes may have occurred. The client must always re-read the current state after receiving a watch notification (not assume the notification describes the full extent of changes). This is a common source of bugs in ZooKeeper client code.

etcd's watches are fundamentally different — they are **persistent streams**: a single `Watch` call streams all future events for a key or prefix until the client cancels. No re-registration needed. Much simpler to work with.

**Q13. How do you implement a distributed lock with ZooKeeper?**
A: The standard ZooKeeper distributed lock using ephemeral sequential znodes:

```python
import kazoo.client as zk

def acquire_lock(client, lock_path, my_id):
    # Create an ephemeral sequential znode
    my_node = client.create(
        f"{lock_path}/lock-",
        ephemeral=True,
        sequence=True
    )
    my_seq = int(my_node.split("-")[-1])

    while True:
        # List all lock candidates
        children = sorted(client.get_children(lock_path))
        sequences = [int(c.split("-")[-1]) for c in children]
        min_seq = min(sequences)

        if my_seq == min_seq:
            return my_node   # I have the lock

        # Watch the node with the immediately lower sequence number
        # (not the minimum — avoids herd effect)
        predecessor_seq = max(s for s in sequences if s < my_seq)
        predecessor = f"lock-{predecessor_seq:010d}"
        event = threading.Event()

        @client.DataWatch(f"{lock_path}/{predecessor}")
        def watch_predecessor(data, stat, event_type):
            if event_type == EventType.DELETED:
                event.set()
                return False  # stop watching

        event.wait()  # block until predecessor is deleted
```

**Why sequential?** The sequence number provides a total order. The lowest-sequence-number holder is the lock owner. Others wait on their predecessor — not on the lock root — avoiding the thundering herd (all waiters racing on single-lock deletion).

**Why ephemeral?** If the lock holder crashes, its session expires, its ephemeral znode is deleted, and the next in sequence automatically gets the lock — no manual cleanup or timeout needed.

**Q14. How do you implement a distributed barrier with ZooKeeper?**
A: A barrier blocks a set of workers until all have reached a checkpoint:

```
Setup: Create /barrier/ready (persistent znode)

Each worker:
1. Creates /barrier/workers/{worker_id} (ephemeral znode) to signal "I'm here"
2. Calls getChildren(/barrier/workers) — if count == expected_workers:
   → Delete /barrier/ready (signals all arrived)
   → Proceed
3. Otherwise: watch /barrier/ready for deletion, wait

Teardown: When /barrier/ready is deleted, all watchers are notified and proceed.
```

Used for: map-reduce job coordination (all mappers must finish before reducers start), distributed test synchronization, phased rolling deployments (all instances in phase N before any start phase N+1).

**Q15. How does etcd's transaction API work and what makes it more powerful than ZooKeeper's multi-op?**
A: etcd's transactions have an If/Then/Else structure — they're conditional atomic batches:

```go
// Atomic compare-and-swap: only set "new-value" if key has version 5
txn := client.Txn(ctx)
resp, err := txn.If(
    clientv3.Compare(clientv3.Version("/my/key"), "=", 5),
).Then(
    clientv3.OpPut("/my/key", "new-value"),
    clientv3.OpPut("/audit/log", "updated at "+time.Now().String()),
).Else(
    clientv3.OpGet("/my/key"),  // return current value on conflict
).Commit()

if resp.Succeeded {
    fmt.Println("CAS succeeded")
} else {
    currentVal := resp.Responses[0].GetResponseRange().Kvs[0]
    fmt.Printf("Conflict — current value: %s\n", currentVal.Value)
}
```

**Compared to ZooKeeper's multi-op:** ZooKeeper's `multi()` batches operations atomically but doesn't support conditional branches — it either succeeds or fails as a unit without an Else path. etcd's If/Then/Else lets you express optimistic concurrency control patterns directly in a single round trip: "if version matches, update; else return current state." This eliminates a separate read-then-write round trip for CAS patterns.

## Section 4: Operational Characteristics

**Q16. What is an etcd lease and how does it differ from ZooKeeper's session?**
A: Both are TTL-based mechanisms for automatic cleanup, but scoped differently:

**ZooKeeper session:**
- A session is established per client connection. All ephemeral znodes created by a client are tied to its session. Session expiry (missed heartbeats beyond `sessionTimeout`) deletes all ephemeral znodes at once.
- One session = one logical client. Session is global to that client process.

**etcd lease:**
- A lease is an explicit resource with a TTL. Any number of keys can be attached to a lease (`LeaseGrant` returns a lease ID; `Put` includes `WithLease(leaseID)`). On lease expiry, all attached keys are deleted.
- Multiple leases can exist per client. A client can create leases with different TTLs for different purposes.
- Leases are explicitly renewed via `KeepAlive`. If `KeepAlive` stops (client crash), the TTL countdown resumes.

```go
// Grant a 10-second lease
leaseResp, _ := client.Grant(ctx, 10)
leaseID := leaseResp.ID

// Attach a key to the lease
client.Put(ctx, "/services/web-1", "192.168.1.10:8080",
    clientv3.WithLease(leaseID))

// Keep the lease alive (sends keepalive every TTL/3 seconds)
ch, _ := client.KeepAlive(ctx, leaseID)
go func() {
    for range ch {}  // drain keepalive responses
}()

// When process dies: KeepAlive stops, lease expires after 10s,
// /services/web-1 is automatically deleted → service deregistration
```

**Q17. How does etcd handle watch event history — what is the revision number?**
A: Every write to etcd increments a global revision counter (a monotonically increasing integer). Each key-value pair also has a `create_revision` (revision when first created) and `mod_revision` (revision of last modification). This is etcd's version of a logical clock.

**Why it matters for watches:** When a client disconnects and reconnects, it can resume watching from the revision it last processed:

```go
// Start watching from revision 42 — receive all events since then
watchChan := client.Watch(ctx, "/my/prefix",
    clientv3.WithPrefix(),
    clientv3.WithRev(42))
```

etcd stores a compacted event history (configurable retention window). As long as the client reconnects within the retention window, it gets all missed events in order. After compaction, it gets a `ErrCompacted` error and must re-read current state.

This is fundamentally more powerful than ZooKeeper's one-time watches — a client that misses events during a disconnect doesn't have to re-read the full state; it replays exactly the events it missed.

**Q18. How do ZooKeeper and etcd handle network partitions — what is their availability model?**
A: Both systems choose **CP** (Consistency + Partition Tolerance) in the CAP theorem — they sacrifice availability under network partitions to maintain consistency.

**During a partition:**
- The majority partition continues operating normally (can elect a leader, commit writes).
- The minority partition becomes unavailable for writes. Reads may be served from followers (stale) in ZooKeeper; etcd returns errors for linearizable reads (no quorum).
- Clients on the minority side experience timeouts or connection errors — not stale data on linearizable reads.

**Why CP is correct for coordination:** If a lock service returned stale data during a partition ("yes, you hold the lock" — when actually a new leader already granted it to someone else), distributed locks, leader election, and config coordination would all be silently incorrect. The correct behavior is to refuse to answer rather than answer incorrectly. Downstream systems must handle unavailability (retry, circuit break) — they cannot handle silent incorrectness.

**Q19. What is etcd's watch compaction and why does it matter operationally?**
A: etcd stores all historical revisions of every key in its Raft log and snapshot. Retaining infinite history would consume unbounded disk space. Compaction prunes history before a given revision:

```bash
# Compact everything before revision 100000
etcdctl compact 100000
# Defragment to reclaim disk space
etcdctl defrag
```

**Operational impact:**
- Compaction is a routine maintenance task. etcd can be configured to auto-compact after a retention period (e.g., `--auto-compaction-retention=1h`).
- A client that tries to watch from a revision before the compaction point gets `ErrCompacted` — it must re-read the full current state and start a new watch from the current revision.
- Aggressive compaction (short retention) reduces disk space but increases the chance of `ErrCompacted` on slow/reconnecting clients.
- etcd's database (`etcd.db`) grows with write volume. Compaction + defrag is required periodically to reclaim space — failure to do this is a common cause of etcd disk saturation in Kubernetes clusters.

## Section 5: Trade-offs & Decision-Making

**Q20. When do you use ZooKeeper vs etcd vs Redis for distributed coordination?**
A: Key decision factors:

**Use etcd when:**
- Building cloud-native or Kubernetes-native systems — etcd is the Kubernetes standard.
- You need persistent watch streams (no re-registration boilerplate).
- Your team works primarily in Go — the etcd client library is idiomatic Go.
- You want lease-based TTL (more flexible than session-scoped ZK ephemeral nodes).
- You need the If/Then/Else transaction model.

**Use ZooKeeper when:**
- Integrating with ZooKeeper-native systems (Kafka, HBase, older Hadoop ecosystem).
- Your team has deep ZooKeeper operational experience.
- You need the hierarchical data model (tree of znodes) for natural representation of your coordination data.

**Use Redis (Redlock, Lua scripts) when:**
- You already have Redis in your stack and need "good enough" coordination for non-critical use cases.
- You need very high throughput (ZooKeeper and etcd are optimized for correctness, not raw throughput — typically 10,000–50,000 ops/sec vs Redis's 500,000+).
- You accept the theoretical split-brain risk of Redlock under clock skew and network partition (Martin Kleppmann's critique — see distributed locks guide).
- **Never** use Redis for leader election or distributed locks where split-brain has financial, data-loss, or safety consequences.

**Q21. What are the performance characteristics of ZooKeeper and etcd, and what workloads are they NOT suited for?**
A: Both are optimized for correctness and coordination workloads — not for high-throughput data storage:

- **Throughput:** etcd handles ~10,000–50,000 simple reads/sec and ~5,000–15,000 writes/sec. ZooKeeper is similar. These numbers are orders of magnitude lower than Redis or a well-tuned PostgreSQL.
- **Latency:** Write latency = quorum round trip = 2× network RTT within the cluster + fsync. In a single-datacenter deployment: 5–20ms per write. Cross-datacenter: 50–200ms per write.
- **Data size:** etcd has a hard 8GB database size limit by default (configurable but not designed for large datasets). Each key-value pair should be small metadata (< 1KB), not application data.
- **Request rate:** Kubernetes clusters start seeing etcd performance issues with > 1,000 pods or > 500 nodes — not because etcd can't handle it, but because the watch event fan-out to many kube-apiserver instances saturates etcd's gRPC connections.

**Not suited for:**
- High-throughput application data storage (use Redis, Cassandra, or a database).
- Large value storage (use object storage, a key-value store designed for large values).
- High-frequency writes from many clients (use a message queue or CRDT-based data structure).
- Service meshes handling per-request coordination (the coordination overhead exceeds request latency).

**Q22. What is "watch amplification" in etcd and Kubernetes, and how do you mitigate it?**
A: Watch amplification occurs when a large number of clients watch the same key or prefix, and a single write event must be delivered to all watchers simultaneously — creating a fan-out that saturates etcd's outbound bandwidth and CPU:

- In Kubernetes: every node's kubelet watches `/registry/pods/{node}`. 5,000 nodes × 1 pod update event = 5,000 concurrent watch event deliveries from etcd.
- If etcd is also handling kube-apiserver watches on top of kubelet watches, total fan-out can reach millions of events per write.

**Mitigations:**
- **Aggregation proxy:** An intermediary (like kube-apiserver) aggregates watches from many clients into a single watch to etcd. etcd has one watcher per resource type (from kube-apiserver), and kube-apiserver fans out to kubelet clients. This is exactly how Kubernetes is architected — kubelets never watch etcd directly.
- **Watch caching:** kube-apiserver maintains an in-memory watch cache populated from etcd events. Kubelets watch the cache, not etcd directly. Writes to etcd update the cache once; the cache fans out to kubelets.
- **Avoid broad prefix watches:** Watching `/registry/` (entire registry) in etcd is catastrophic for event volume. Scope watches to the narrowest useful prefix.

## Section 6: Scenario / System Design Style Questions

**Q23. "Design a leader election system for a distributed cron job scheduler where exactly one instance should run each job at any given time."**
A: etcd-based implementation with per-job election:

**Design:**
- Each job has its own election path: `/cron/jobs/{job_name}/leader`.
- Each scheduler instance participates in the election for every job it is configured to run.
- The elected leader acquires the election, runs the job, then either resigns (one-shot job) or holds the election until the next scheduled run.

```go
func runJobWithLeaderElection(client *clientv3.Client, jobName, instanceID string, jobFn func()) {
    for {
        session, _ := concurrency.NewSession(client, concurrency.WithTTL(15))
        election := concurrency.NewElection(session, "/cron/jobs/"+jobName+"/leader")

        // Block until elected
        election.Campaign(context.Background(), instanceID)

        // Run the job — only the elected leader reaches here
        jobFn()

        // Resign after completion so another instance can take over
        // (or hold and sleep until next scheduled time)
        election.Resign(context.Background())
        session.Close()
    }
}
```

**Guarantees:**
- Lease TTL (15s): if the elected instance crashes mid-job, the lease expires, a new instance is elected and re-runs the job. Job must be idempotent (re-runnable on retry).
- Fencing: include the etcd revision (lease's create revision) in any external writes the job makes. External systems reject writes from stale leaders.
- Monitoring: watch `/cron/jobs/{job_name}/leader` — alert if the key is absent for > 30 seconds (no leader for a job that should have one).

**Q24. "Your Kafka cluster uses ZooKeeper for broker coordination. A ZooKeeper node fails. Walk through what happens and what the impact is on Kafka."**
A: Assuming a 3-node ZooKeeper ensemble and 1 node fails:

**ZooKeeper impact:**
- Remaining 2 nodes form a quorum (⌊3/2⌋ + 1 = 2). The ensemble continues operating normally — reads and writes proceed.
- The failed node's sessions expire after `sessionTimeout` (default: 30 seconds). Any ephemeral znodes owned by clients whose ZK connection was routed through the failed node (via a ZK client that connects to that specific node) will have their sessions terminated after the timeout.

**Kafka impact:**
- Kafka brokers maintain persistent ZK sessions — they reconnect to another ZK node immediately on the failed node becoming unavailable.
- The Controller (Kafka's elected leader broker) maintains its leadership via a ZK ephemeral node. If the Controller's connection was to the failed ZK node, it reconnects and re-establishes its session — retaining the controller ephemeral node.
- Partition leader elections (triggered by broker failures, not ZK failures) are unaffected if ZK has quorum.
- Producer and consumer clients are not directly affected — they don't connect to ZooKeeper (in modern Kafka, metadata is fetched from brokers).

**If 2 ZooKeeper nodes fail (loss of quorum):**
- ZooKeeper becomes unavailable for writes. Kafka brokers can continue serving existing metadata (cached in memory) for a period, but:
  - No new partition leader elections can occur.
  - No topic creation or partition reassignment.
  - If the Kafka Controller fails during this window, no new Controller can be elected — Kafka enters a degraded state.
- This is why ZooKeeper clusters should be 5 nodes in production environments where Kafka is critical — tolerating 2 simultaneous failures.

**Note:** Modern Kafka (2.8+) supports KRaft mode — eliminating ZooKeeper dependency entirely. The Kafka cluster itself runs Raft consensus for metadata. This removes ZooKeeper as a dependency and operational concern.

**Q25. "etcd in your Kubernetes cluster is showing high disk usage and increasing write latency. How do you diagnose and remediate?"**
A: Classic etcd operational problem with a well-defined remediation path:

**Diagnosis:**
```bash
# Check etcd database size
etcdctl endpoint status --write-out=table
# Look at DB SIZE column — if approaching 8GB, critical

# Check compaction status — when was last compaction?
etcdctl endpoint status --write-out=json | jq '.[].Status.raftAppliedIndex'

# Check write latency
etcdctl check perf  # runs a performance benchmark

# Check for large keys consuming disproportionate space
etcdctl get "" --from-key --keys-only | head -50  # list key space
```

**Common causes:**
- **No auto-compaction configured:** etcd retains infinite history by default. Every update to every Kubernetes resource (pod status, endpoint, configmap) is retained forever. A busy cluster generates millions of revisions per day.
- **High event volume:** Kubernetes operators or controllers writing frequently to etcd (every reconciliation loop updating resource status).
- **Large values:** ConfigMaps or Secrets with large payloads (> 1MB each) stored in etcd — which is not designed for large values.

**Remediation:**
```bash
# Step 1: Get current revision
REV=$(etcdctl endpoint status --write-out=json | jq '.[].Status.header.revision')

# Step 2: Compact to current revision (remove all old revisions)
etcdctl compact $REV

# Step 3: Defragment to reclaim disk space
etcdctl defrag --cluster

# Step 4: Verify
```

**Prevention:**
- Enable auto-compaction: `--auto-compaction-mode=periodic --auto-compaction-retention=1h`.
- Increase etcd disk quota: `--quota-backend-bytes=8589934592` (8GB, the recommended max).
- Move large data out of etcd: ConfigMaps > 100KB should reference external storage.
- Throttle aggressive controllers: add rate limits to operators writing high-frequency status updates.

**Q26. "How would you design a service discovery system using etcd?"**
A: Service discovery requires: registration, health-based deregistration, and efficient lookup.

**Registration (on service startup):**
```go
func registerService(client *clientv3.Client, serviceName, instanceID, addr string) {
    // Lease with TTL — auto-deregisters if instance dies
    lease, _ := client.Grant(ctx, 30)   // 30-second TTL

    // Register under a structured key
    key := fmt.Sprintf("/services/%s/instances/%s", serviceName, instanceID)
    client.Put(ctx, key, addr, clientv3.WithLease(lease.ID))

    // Keep-alive — renews every 10 seconds
    client.KeepAlive(ctx, lease.ID)
}
```

**Lookup (client-side):**
```go
func discoverService(client *clientv3.Client, serviceName string) []string {
    prefix := fmt.Sprintf("/services/%s/instances/", serviceName)
    resp, _ := client.Get(ctx, prefix, clientv3.WithPrefix())

    var addrs []string
    for _, kv := range resp.Kvs {
        addrs = append(addrs, string(kv.Value))
    }
    return addrs
}
```

**Watch for changes (client caches the list, updates on change):**
```go
func watchService(client *clientv3.Client, serviceName string, onChange func([]string)) {
    prefix := fmt.Sprintf("/services/%s/instances/", serviceName)
    watchChan := client.Watch(ctx, prefix, clientv3.WithPrefix())

    for watchResp := range watchChan {
        for _, event := range watchResp.Events {
            // Re-fetch current list on any change
            addrs := discoverService(client, serviceName)
            onChange(addrs)
        }
    }
}
```

**Deregistration:**
- Graceful shutdown: `client.Delete(ctx, key)` or `client.Revoke(ctx, leaseID)`.
- Crash / network loss: lease TTL expires (30 seconds) → key auto-deleted → watchers notified → clients update their endpoint lists.

**Health checking beyond TTL:** Add a health-check sidecar that monitors the service's health endpoint. On health failure, it revokes the lease immediately (rather than waiting for TTL expiry) — faster failover. On recovery, it re-registers.

## Quick Reference: ZooKeeper vs etcd Primitive Mapping

| Primitive | ZooKeeper | etcd |
|---|---|---|
| Key-value store | Znode data | Key-value with Put/Get |
| Hierarchical namespace | Native tree structure | Emulated via key prefixes |
| Ephemeral key (auto-delete on disconnect) | Ephemeral znode (session-scoped) | Key with Lease (lease TTL-scoped) |
| Sequential key (monotonic suffix) | Sequential znode | Not native — use revision or atomic counter |
| Watch (change notification) | One-time watch, must re-register | Persistent watch stream |
| Watch history replay | Not supported | Supported via revision + WithRev() |
| Distributed lock | Ephemeral sequential znodes | Concurrency package (Mutex) |
| Leader election | Ephemeral sequential znodes | Concurrency package (Election) |
| Barrier | Ephemeral znode + children count watch | Key existence watch + count |
| Atomic conditional write | multi() (batch, no else) | Txn If/Then/Else |
| Service discovery | Ephemeral znodes under service path | Keys with leases under service prefix |
| Configuration store | Persistent znodes | Regular keys |
| TTL-based expiry | Session timeout (all ephemerals) | Per-lease TTL (per-key granularity) |

**Tip for the interview:** ZooKeeper / etcd questions at senior level almost always pivot from "how does leader election work" to "what can go wrong" — the GC pause scenario, split-brain, and fencing tokens. Be ready to walk through the failure scenario in detail: leader pauses → lease expires → new leader elected → old leader resumes unaware → without fencing tokens, both leaders write → data corruption. The fencing token is the answer, and knowing that ZooKeeper's `zxid` and etcd's revision serve this purpose distinguishes senior answers from junior ones. Also be ready to discuss the operational side — etcd disk compaction (Q25) is a real Kubernetes operational concern that comes up frequently in SRE-adjacent interviews.
