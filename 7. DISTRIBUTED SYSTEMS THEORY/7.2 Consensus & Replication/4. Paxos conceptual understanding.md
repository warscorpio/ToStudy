# Paxos: Conceptual Understanding — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Consensus is Hard

**Q1. What is the distributed consensus problem?**
A: Consensus is the problem of getting a set of nodes in a distributed system to agree on a single value — even when some nodes crash, messages are delayed, or the network drops packets. More precisely, a consensus protocol must satisfy three properties:
- **Agreement**: All non-faulty nodes that decide, decide the same value. No two correct nodes decide different things.
- **Validity**: The decided value must have been proposed by some node. The system cannot invent a value out of thin air.
- **Termination** (liveness): Every non-faulty node eventually decides some value. The system doesn't stall forever.

Consensus underlies nearly every hard problem in distributed systems: leader election, atomic commit in distributed transactions, replicated state machines, and distributed locks all reduce to consensus.

**Q2. Why can't you just have every node vote and pick the majority?**
A: Because of the timing and failure model. If you send a "vote request" to all nodes and wait for a majority to respond:
- A slow node might respond so late that you've already made a decision — now its response arrives and it disagrees with the outcome it never heard about.
- A node might crash mid-vote and never respond — if you wait for it, you block forever; if you ignore it, you might have two concurrent proposers both collecting different majorities.
- Two proposers can simultaneously collect majority votes for different values and both declare victory.

Simple voting with no coordination protocol fails to guarantee Agreement. The hard part isn't collecting opinions — it's ensuring that once a value is chosen, no concurrent or future decision can contradict it. Paxos solves exactly this.

**Q3. What is the FLP impossibility result, and why does it matter for Paxos?**
A: The Fischer-Lynch-Paterson theorem (1985) proves that in a **purely asynchronous** system — where messages can be arbitrarily delayed and you cannot distinguish a crashed node from a slow one — no deterministic consensus protocol can guarantee all three properties simultaneously. Specifically: if even one node can crash, termination cannot be guaranteed.

This sounds devastating, but Paxos works around it practically:
- **Safety (Agreement + Validity) is always guaranteed**, regardless of timing. Paxos will never decide two different values.
- **Liveness (Termination) is only guaranteed under "eventual synchrony"** — periods where the network eventually delivers messages and some node is stable long enough to drive consensus to completion. In practice, real networks are synchronous enough, often enough, for Paxos to make progress.

The practical implication: if you see Paxos stall (livelock), it's a liveness failure — temporary and recoverable. If you see Paxos decide two different values, something is deeply wrong (a safety violation, likely a bug).

**Q4. Who invented Paxos and when was it published?**
A: Leslie Lamport invented Paxos and described it in "The Part-Time Parliament" (submitted 1989, published 1998 after Lamport rewrote it in a fictional narrative style). Because the original paper was famously difficult to follow, Lamport published "Paxos Made Simple" in 2001 — a stripped-down, accessible description that most practitioners use as the primary reference. Despite the name, Paxos remains notoriously hard to implement correctly, which is partly why Raft was designed as a more understandable alternative in 2014.

## Section 2: Roles and Structure

**Q5. What are the three roles in Paxos?**
A: Paxos defines three logical roles — in practice, a single physical node often plays multiple roles simultaneously:

- **Proposer**: Initiates the consensus process. Picks a proposal number, runs the two-phase protocol, and tries to get a value chosen. In a stable system, one designated Proposer (the leader) drives all proposals.
- **Acceptor**: The voter. Receives proposals from proposers, makes promises, and accepts or rejects proposals. A quorum (majority) of acceptors must agree for a value to be chosen. Acceptors are the "memory" of the system — they persist their state to survive crashes.
- **Learner**: Observes the outcome. Once a value is chosen (accepted by a quorum of acceptors), learners are notified and act on the decision. Learners don't participate in the protocol; they just learn the result.

**Q6. What is a "quorum" in Paxos and why must it be a majority?**
A: A quorum is any set of acceptors constituting a majority — more than half. For N acceptors: quorum size = ⌊N/2⌋ + 1. Common configurations: 3 acceptors → quorum of 2; 5 acceptors → quorum of 3.

The majority requirement is load-bearing: **any two majorities must overlap in at least one node**. This overlap is the core safety guarantee. If value V was accepted by a majority in Phase 2, then any future Phase 1 that contacts a majority will reach at least one acceptor that accepted V — and learn about it. Without a majority quorum, two disjoint groups could each independently accept different values, violating Agreement.

**Q7. What is a "proposal number" and what properties must it have?**
A: A proposal number (also called a ballot number or round number) is a monotonically increasing integer used to order competing proposals. Properties it must satisfy:
- **Globally unique**: No two proposers ever use the same proposal number. Typically achieved by embedding the proposer's node ID in the number (e.g., `round * num_nodes + node_id`), or by using a dedicated "proposal number allocator."
- **Strictly increasing**: Each new proposal from a proposer uses a number strictly higher than any it has used before, and higher than any it has seen in responses from acceptors.
- **No meaning beyond ordering**: The proposal number doesn't represent time or priority — it's purely a tie-breaker that establishes which proposer is "latest."

The proposal number is how Paxos handles competing proposers: an acceptor commits to the proposer with the highest number it has seen, and ignores lower-numbered requests. This is what prevents two proposers from simultaneously choosing different values.

## Section 3: Phase 1 — Prepare and Promise

**Q8. What happens in Phase 1a — the Prepare step?**
A: The proposer picks a proposal number `n` — higher than any it has previously used or seen. It then sends a `Prepare(n)` message to at least a quorum of acceptors. This message does not contain a value yet; it is a bid for leadership for proposal round `n`. The proposer is asking: "Will you promise to work with me on round n and tell me what you already know?"

**Q9. What happens in Phase 1b — the Promise step?**
A: Each acceptor that receives `Prepare(n)` decides whether to respond based on one rule: **it only promises if `n` is greater than any proposal number it has previously promised**. If it agrees:
- It sends back a `Promise(n, accepted_n, accepted_v)` where `(accepted_n, accepted_v)` is the highest-numbered proposal it has already accepted in Phase 2 (if any). If it has accepted nothing, it returns `(null, null)`.
- It records `n` as its highest-seen prepare, committing not to accept any proposal numbered less than `n` in the future.

If `n` is not higher than what the acceptor has already promised, it ignores the prepare or sends a `Nack`. The proposer must then try again with a higher proposal number.

**Q10. What is the semantic meaning of a "Promise"?**
A: A Promise is a two-part commitment from the acceptor:
1. **I will not accept any proposal numbered lower than n.** (Forward-looking constraint — protects the new proposer's Phase 2 from being undermined by stale proposals.)
2. **Here is what I have already accepted, if anything.** (Backward-looking report — lets the new proposer discover whether a value was already chosen in a previous round.)

Together, these two pieces let a new proposer safely take over. It knows that nothing it accepted in Phase 2 can be overturned by older proposals (because of part 1), and it knows the full history of what might have already been decided (because of part 2).

**Q11. Why does the proposer need responses from a quorum before proceeding to Phase 2?**
A: Because only a quorum of promises guarantees the proposer has seen the complete history of what may have been accepted. If a value V was accepted by some majority in a previous round, at least one of those acceptors is in any majority — including the one responding to this proposer's Prepare. By collecting a majority of Promises, the proposer is guaranteed to hear about any previously accepted value. It can then safely choose a value for Phase 2 without risking a contradiction with prior decisions.

## Section 4: Phase 2 — Accept and Accepted

**Q12. What happens in Phase 2a — the Accept step, and how does the proposer choose its value?**
A: Once the proposer collects Promises from a quorum, it selects a value and sends `Accept(n, v)` to a quorum of acceptors. The critical rule for choosing `v`:

- **If any acceptor returned a previously accepted value** in its Promise response: the proposer MUST use the value with the highest associated proposal number among all returned values. It cannot use its own value.
- **If no acceptor returned a previously accepted value**: the proposer is free to use any value — including its own original proposal.

This rule is the heart of Paxos safety. It ensures that if some value was already accepted (possibly chosen) in a previous round, any new proposer will re-propose the same value rather than overwriting it.

**Q13. Why must the proposer use the highest-numbered previously accepted value, not its own?**
A: Because that previously accepted value might already be "chosen" — accepted by a majority in some prior round — even if the current proposer doesn't know it. Consider:

```
Round 1: Proposer 1 sends Accept(1, "X") → Acceptors A, B accept "X" (majority of 3). Value "X" is chosen.
Proposer 1 crashes before notifying learners.

Round 2: Proposer 2 runs Phase 1, hears about "X" from A or B (at least one is in any majority).
```

If Proposer 2 were allowed to ignore "X" and propose "Y", it could get "Y" chosen — two values decided. The rule "use the highest previously accepted value" prevents this: Proposer 2 sees "X" in the Promise responses and must re-propose "X". The already-chosen value is preserved.

**Q14. What happens in Phase 2b — the Accepted step?**
A: Each acceptor receives `Accept(n, v)`. It accepts if and only if `n >= highest_promised` — meaning it hasn't promised to ignore proposal `n` by making a later Promise to a higher-numbered proposer. If it accepts:
- It records `(n, v)` as its accepted value, overwriting any previously accepted value with a lower proposal number.
- It sends `Accepted(n, v)` to all Learners (and optionally to the Proposer).

If `n < highest_promised`, it ignores the Accept (it has already committed to a newer proposer). The proposer whose Accept is rejected must restart Phase 1 with a higher proposal number.

**Q15. What does it mean for a value to be "chosen"?**
A: A value `v` is chosen when a quorum of acceptors has each sent `Accepted(n, v)` for the same proposal number `n`. At that point, Agreement is guaranteed — no other value can be chosen because any future Phase 1 quorum will overlap with this quorum in at least one acceptor, which will report `v` as its accepted value, and any subsequent proposer will be forced to re-propose `v`.

Importantly: a value being "chosen" does not require anyone to *know* it has been chosen at the moment it becomes so. A Learner learns the decision by collecting Accepted messages — either by hearing from a quorum directly, or by hearing from a Proposer or designated Learner that relays the result. The value is chosen in the mathematical sense regardless of whether anyone has yet observed that fact.

**Q16. Walk through a complete single-round Paxos execution with 3 acceptors.**
A:

```
Actors: Proposer P, Acceptors A1, A2, A3. Quorum = 2.

─── Phase 1 ───────────────────────────────────────────────
P  → A1, A2, A3 :  Prepare(n=5)

A1 → P :  Promise(n=5, accepted_n=null, accepted_v=null)   [has accepted nothing]
A2 → P :  Promise(n=5, accepted_n=null, accepted_v=null)   [has accepted nothing]
A3     :  (slow — no response yet, but P has a quorum of 2)

─── Phase 2 ───────────────────────────────────────────────
No acceptor returned a prior value → P is free to propose its own value.

P  → A1, A2, A3 :  Accept(n=5, v="leader=node7")

A1 → Learners :  Accepted(n=5, v="leader=node7")
A2 → Learners :  Accepted(n=5, v="leader=node7")
A3     :  (still slow)

─── Decision ──────────────────────────────────────────────
Learner receives Accepted(5, "leader=node7") from A1 and A2 — a quorum.
Value "leader=node7" is chosen. ✅
```

A3's response (or lack of it) doesn't matter — the decision is final once a quorum accepted.

## Section 5: Safety, Liveness, and the Dueling Proposers Problem

**Q17. How does Paxos guarantee Safety (Agreement) even with multiple competing proposers?**
A: Through the combination of two invariants:
1. **An acceptor only accepts a proposal if it hasn't promised a higher one** — so an acceptor is always "loyal" to the highest proposer it has seen.
2. **A proposer must re-propose any previously accepted value it discovers** — so a chosen value is never overwritten.

These two rules together mean: once a quorum accepts value V in round n, any future proposer running Phase 1 contacts a quorum, overlaps with at least one acceptor that accepted V, receives V in the Promise response, and is forced to propose V again. The chosen value propagates forward through all subsequent rounds, forever. No new value can be chosen in a future round — only the same V.

**Q18. What is the "dueling proposers" liveness problem?**
A: If two proposers concurrently run Paxos with escalating proposal numbers, they can indefinitely prevent each other from completing Phase 2:

```
P1 sends Prepare(n=1) → gets quorum of Promises
P2 sends Prepare(n=2) → gets quorum of Promises (overrides n=1 commitments)
P1 sends Accept(n=1, v) → rejected by acceptors (they promised n=2)
P1 retries with Prepare(n=3) → overrides P2's Promises
P2 sends Accept(n=2, v) → rejected
P2 retries with Prepare(n=4) → overrides P3's Promises
... (repeats indefinitely)
```

Neither proposer ever completes Phase 2. The system makes no progress — this is a liveness failure (not a safety failure; no incorrect value is ever chosen). The system can spin in this state indefinitely in an adversarial network model.

**Q19. How is the dueling proposers problem solved in practice?**
A: By electing a **single distinguished proposer** — a leader — who is the only node allowed to propose values. With one proposer, there is no competition and no escalating proposal numbers. All other nodes route their proposed values through the leader.

The catch: electing a leader is itself a consensus problem, creating an apparent circularity. In practice, this is handled pragmatically:
- Use a simple timeout-based mechanism: nodes vote for whoever contacts them first; ties are broken by node ID. This isn't perfectly safe under all network conditions, but is sufficient in practice.
- Use a randomized backoff: if a proposer's Phase 1 is rejected, it waits a random interval before retrying, reducing the probability of continued collision.
- In Multi-Paxos and Raft, the leader election is a first-class concept with explicit term/epoch management.

The key insight: leader election doesn't have to be perfectly safe itself — it just has to make livelock rare enough in practice. Paxos's Safety guarantee means that even if two nodes briefly think they're leader, they cannot choose different values. The worst case of a bad leader election is unnecessary latency, not incorrectness.

**Q20. Can Paxos tolerate Byzantine (malicious) faults?**
A: No. Paxos is designed for **crash-fault tolerance** only — nodes either work correctly or stop (crash). It cannot tolerate a Byzantine fault, where a node continues operating but sends arbitrary or malicious messages (e.g., lying about what value it accepted, or sending different promises to different proposers). A single Byzantine acceptor could violate Agreement by claiming to have accepted V to one proposer and V' to another.

For Byzantine fault tolerance you need different algorithms (PBFT, HotStuff, Tendermint), which require at least 3f+1 nodes to tolerate f Byzantine faults (vs. 2f+1 for crash faults). This is why blockchain consensus protocols look very different from classical Paxos — they operate in trustless, adversarial environments.

## Section 6: Multi-Paxos and the Path to Raft

**Q21. What is "Single-Decree Paxos" vs. "Multi-Paxos"?**
A: The Paxos described so far is **Single-Decree Paxos** — it decides exactly one value, once, forever. This is useful for one-shot decisions (e.g., "who is the leader?") but not for a continuous stream of decisions (e.g., a replicated command log where each slot in the log must be decided independently).

**Multi-Paxos** runs Paxos repeatedly — one instance per log slot — to build a **replicated log**: an ordered sequence of decided values that all nodes agree on. Each entry in the log is a separate Paxos consensus instance with its own proposal numbers and phases. The replicated log is the foundation for replicated state machines — the model underlying most production distributed databases and coordination services.

**Q22. What is the key optimization Multi-Paxos uses once a stable leader exists?**
A: In basic Paxos, Phase 1 (Prepare/Promise) is required before every single value is proposed. In Multi-Paxos, once a stable leader is elected, it runs Phase 1 **once** for a given proposal number n and receives promises from a quorum covering all future log slots. Subsequent log entries can skip Phase 1 entirely — the leader goes straight to Phase 2 (Accept/Accepted) for each new entry, using the same proposal number n.

This optimization transforms Multi-Paxos into a highly efficient protocol: normal-case operation is just **one round trip per log entry** (leader sends Accept; acceptors respond with Accepted). Phase 1 only re-runs when a new leader is elected. This is precisely how Raft works — Raft is essentially Multi-Paxos with Phase 1 made explicit as "leader election" and Phase 2 as "log replication."

**Q23. How does Raft relate to Paxos?**
A: Raft (Ongaro & Ousterhout, 2014) is a consensus algorithm explicitly designed to be more understandable than Paxos. It is functionally equivalent to Multi-Paxos but decomposes the problem into three clearly separated sub-problems:
- **Leader election**: A node becomes leader by winning an election in a new term (analogous to Phase 1 — the winning term number is the proposal number).
- **Log replication**: The leader appends entries to its log and replicates them to followers via AppendEntries RPCs (analogous to Phase 2 Accept).
- **Safety**: Log matching property, commitment only from current term — ensures no two leaders in the same term, and a committed entry is never overwritten.

Key differences from Paxos: Raft requires the leader to have the most up-to-date log (strong leader property), whereas Paxos allows a new proposer to discover and "fix up" the log. Raft's restriction simplifies log reconciliation but makes leader election slightly more constrained.

**Q24. What are ZAB and Viewstamped Replication?**
A: Two other consensus protocols that are equivalent in power to Multi-Paxos:
- **ZAB (ZooKeeper Atomic Broadcast)**: Used by ZooKeeper. Primary-based protocol where a leader proposes transactions to followers; a transaction is committed when a quorum acknowledges it. The epoch number plays the role of the proposal number; a new epoch is established when a new leader is elected. Functionally Multi-Paxos with ZooKeeper-specific terminology and recovery procedures.
- **Viewstamped Replication (Liskov & Cowling, 1988 / 2012)**: Described before Paxos's public release; independently discovered the same solution. "Views" correspond to leader terms; "view changes" are Phase 1 leader election. Mathematically equivalent to Paxos.

All three — Paxos, ZAB, Viewstamped Replication — solve the same problem with the same underlying quorum-based insight. The differences are in terminology, failure-recovery procedures, and how explicitly they define leader election.

## Section 7: Practical Limitations and Real-World Context

**Q25. Why is Paxos considered hard to implement correctly?**
A: Lamport's "Paxos Made Simple" describes the algorithm but deliberately leaves out many details needed for a production implementation:
- **Leader election**: How do you pick the first leader? What happens during a contested election?
- **Log gaps**: In Multi-Paxos, what if a leader crashes after proposing slot 5 but before slot 4 has been decided? Other nodes have a gap in their log. How do they fill it?
- **State persistence**: Acceptors must persist their highest-promised proposal number and accepted value to durable storage before responding — otherwise a crash and restart breaks the safety invariant. What exactly gets written, when, and how?
- **Read linearizability**: How does a client read the latest value without going stale? (A naive read from any replica might be stale if that replica hasn't learned the latest decisions.)
- **Membership changes**: Adding or removing acceptors changes the quorum size — this transition must itself be done safely via consensus.
- **Log compaction**: Logs grow unboundedly. Snapshots must be taken and old log entries truncated safely.

Each of these is a non-trivial distributed systems problem. This is why Chubby (Google's internal Paxos service) required significant engineering effort, and why production teams increasingly use Raft (which specifies all of the above) over rolling their own Paxos.

**Q26. How many failures can Paxos tolerate, and why?**
A: Paxos with N acceptors can tolerate `f < N/2` crash failures — i.e., fewer than half the acceptors can fail. This comes from the quorum requirement: you need a majority (⌊N/2⌋ + 1) of acceptors to make progress. If f nodes fail, you need N - f ≥ ⌊N/2⌋ + 1, which gives f < N/2.

Standard configurations:
- 3 acceptors → tolerates 1 failure (quorum = 2)
- 5 acceptors → tolerates 2 failures (quorum = 3)
- 7 acceptors → tolerates 3 failures (quorum = 4)

Adding more acceptors beyond 5 or 7 rarely makes sense for performance: each additional acceptor adds more network traffic (the leader must contact a larger quorum) for diminishing returns in fault tolerance. Most production deployments use 3 or 5 replicas.

## Section 8: Scenario / System Design Style Questions

**Q27. "Why can't you use Paxos directly as a database transaction protocol?"**
A: Paxos decides one value across replicas of a single resource. A database transaction typically involves multiple resources (multiple rows, tables, or even shards). To commit a multi-resource transaction atomically, you need to coordinate across multiple Paxos groups — which is the **distributed commit** problem, typically solved with Two-Phase Commit (2PC) layered on top of Paxos.

The architecture in systems like Spanner: each shard/partition has its own Paxos group for replication (ensuring each shard is replicated consistently). A cross-shard transaction uses 2PC across the shard leaders to atomically commit or abort. Paxos handles "which replica is authoritative" and "are writes replicated" — 2PC handles "did all shards agree to commit." Conflating the two is a common interview confusion.

**Q28. "Your distributed system needs a single configuration value (e.g., which node is the current primary) that all nodes must agree on. How would Paxos apply?"**
A: This is exactly Single-Decree Paxos's use case. The design:
1. Assign 3 or 5 nodes as Acceptors (can overlap with other roles).
2. Any node that wants to propose a primary runs Phase 1 with a proposal number higher than any it has seen.
3. It collects Promises from a majority. If a previously accepted value exists, it re-proposes that; otherwise it proposes itself (or whatever primary it wants to suggest).
4. It runs Phase 2 and gets Accepted from a majority.
5. All Learners (all nodes) update their view of who the primary is.

In practice, you wouldn't implement this from scratch — you'd use ZooKeeper or etcd (which run ZAB or Raft, equivalent protocols) and store the "current primary" as a key in their replicated key-value store, using ephemeral nodes or leases for failure detection. Paxos/Raft is the engine; ZooKeeper/etcd is the off-the-shelf packaging.

**Q29. "A colleague says Paxos guarantees the system will always make progress. Is that correct?"**
A: No — and this is a common misconception. Paxos guarantees **Safety always** and **Liveness only under favorable conditions**. The FLP result proves termination cannot be guaranteed in a purely asynchronous model. Paxos can livelock (dueling proposers), stall if the leader crashes and election takes time, or fail to make progress if the network is sufficiently adversarial.

What Paxos guarantees absolutely: the system will never decide two different values. It will never return an incorrect result. Safety is unconditional.

What Paxos guarantees conditionally: if a stable leader exists, the network eventually delivers messages, and a majority of acceptors are alive, then Paxos will make progress and decide a value. These conditions are met the vast majority of the time in real systems — which is why Paxos works in practice despite the FLP impossibility.

**Q30. "How does Paxos relate to the PACELC trade-offs you'd discuss for a system like Spanner?"**
A: Paxos is the mechanism that makes Spanner **PC/EC** in PACELC terms. Specifically:
- **PC (Consistent during Partition)**: Because Spanner uses Paxos for each shard, a write cannot be committed unless a quorum of replicas agrees. If a partition prevents quorum, Spanner blocks rather than allowing divergent writes — it chooses consistency over availability during partitions.
- **EC (Consistent costs Latency in normal operation)**: Each Paxos round requires at least one network round trip to a quorum of replicas. Spanner's cross-region deployment means this round trip can be 10–100ms. Spanner additionally adds a `commit wait` delay (TrueTime uncertainty, ~1–7ms) on top of the Paxos latency. Every write pays this cost — that's the EL vs EC trade-off made concrete: using Paxos (EC) costs real milliseconds on every operation.

A system that achieves Spanner's consistency guarantees without Paxos-like coordination does not exist — the latency cost of EC is the network round-trip cost of the quorum protocol, and no protocol can eliminate that without sacrificing the consistency guarantee.

## The Two-Phase Mental Model (Whiteboard Summary)

```
PHASE 1 — "Can I lead? What happened before me?"
  Proposer → Acceptors :  Prepare(n)
  Acceptors → Proposer :  Promise(n, highest_accepted_n, highest_accepted_v)
                           [only if n > my highest seen; else ignore]

PHASE 2 — "Here is the value. Please accept it."
  Proposer picks value:
    → If any Promise returned a (accepted_n, accepted_v):
          use the v with the highest accepted_n  [must re-propose prior work]
    → Else:
          use own value  [free to choose]
  Proposer → Acceptors :  Accept(n, v)
  Acceptors → Learners :  Accepted(n, v)  [only if n >= my highest promised; else ignore]

VALUE IS CHOSEN when a quorum sends Accepted(n, v) for the same (n, v).

KEY INVARIANT: Any two quorums overlap in ≥ 1 node.
               → A chosen value is always rediscovered by the next Phase 1.
               → Agreement is guaranteed forever once a value is chosen.
```

## Quick Reference

| Concept                  | Detail                                                                        |
|---                       |---                                                                            |
| Roles                    | Proposer, Acceptor, Learner (one node often plays all three)                  |
| Quorum size              | Majority: ⌊N/2⌋ + 1 of N acceptors                                           |
| Fault tolerance          | Tolerates f < N/2 crash failures                                              |
| Phase 1 (Prepare)        | Proposer bids with proposal number n; acceptors promise and report history    |
| Phase 2 (Accept)         | Proposer sends value (re-using prior if found); acceptors accept and notify   |
| Value selection rule     | Must use highest previously accepted value if any; else free to choose        |
| Safety guarantee         | Unconditional — never decides two different values                            |
| Liveness guarantee       | Conditional — requires stable leader, eventual message delivery               |
| Dueling proposers        | Liveness failure; fixed by single distinguished proposer (leader)             |
| Fault model              | Crash faults only; Byzantine faults require different algorithms (PBFT, etc.) |
| Multi-Paxos optimization | Phase 1 once per leader term; Phase 2 per log entry                          |
| Raft relationship        | Multi-Paxos with explicit leader election + more specified recovery           |

**Tip for the interview:** Paxos questions at 5 YOE almost never ask you to recite the algorithm verbatim — they probe your intuition for *why* each rule exists. Be ready to explain: why is the value constraint in Phase 2 the way it is (to preserve chosen values); why must quorums be majorities (to guarantee overlap); and why is Safety unconditional but Liveness conditional (FLP + stable leader assumption). The strongest answers connect Paxos to something concrete: "This is what ZooKeeper and etcd implement under the hood — when you use a ZooKeeper lock or an etcd key, a Paxos-equivalent quorum is what makes the guarantee real." Mechanics + why they work + where you've seen them is the 5 YOE answer.
