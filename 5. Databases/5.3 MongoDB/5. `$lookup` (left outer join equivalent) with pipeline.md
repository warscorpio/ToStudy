# MongoDB `$lookup` (Left Outer Join Equivalent) with Pipeline — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is `$lookup` and why does it exist in a document database — doesn't MongoDB's document model avoid joins?**

A: MongoDB's document model encourages embedding related data inside a single document to avoid joins. But embedding has limits: when the related data changes independently, is shared across many documents, or is too large to embed, you normalise into separate collections. `$lookup` is the aggregation pipeline stage that performs a left outer join between two collections in the same database when that normalised data needs to be recombined at query time.

```
Why you end up needing $lookup despite the document model:

Embedding works well for:
  - One-to-few relationships (user → addresses, order → order items)
  - Data that doesn't change independently
  - Data that is always accessed together

Separate collections (and $lookup) are needed for:
  - Many-to-many (users ↔ roles, products ↔ tags)
  - One-to-many where the "many" is unbounded (user → events, account → transactions)
  - Shared reference data (products referenced in millions of order lines)
  - Data with independent update lifecycles (user profile vs. user settings)

MongoDB's answer: $lookup in the aggregation pipeline
→ Equivalent to SQL: LEFT OUTER JOIN (not INNER JOIN — non-matching left docs are kept)
```

Left outer join semantics — what `$lookup` always does:

```javascript
// SQL equivalent:
// SELECT orders.*, users.*
// FROM orders
// LEFT OUTER JOIN users ON users._id = orders.userId

// MongoDB $lookup equivalent:
db.orders.aggregate([
    {
        $lookup: {
            from:         'users',        // right-hand collection
            localField:   'userId',       // field in 'orders' (left)
            foreignField: '_id',          // field in 'users' (right)
            as:           'user',         // output array field name
        }
    }
]);

// LEFT OUTER semantics:
// - Every order document is kept in the output, even if no matching user exists
// - If a matching user exists: user array contains the user document(s)
// - If NO matching user: user array is [] (empty array, not null, not missing)
// - Unlike SQL INNER JOIN: orders with no matching user are NOT dropped

// Example documents:
// orders collection:
{ _id: ObjectId('1'), userId: ObjectId('u1'), total: 99.99 }
{ _id: ObjectId('2'), userId: ObjectId('u2'), total: 49.99 }
{ _id: ObjectId('3'), userId: ObjectId('MISSING'), total: 19.99 }  // no matching user

// users collection:
{ _id: ObjectId('u1'), email: 'alice@example.com' }
{ _id: ObjectId('u2'), email: 'bob@example.com' }

// Output after $lookup:
{ _id: ObjectId('1'), userId: ..., total: 99.99,
  user: [{ _id: ObjectId('u1'), email: 'alice@example.com' }] }
{ _id: ObjectId('2'), userId: ..., total: 49.99,
  user: [{ _id: ObjectId('u2'), email: 'bob@example.com' }] }
{ _id: ObjectId('3'), userId: ..., total: 19.99,
  user: []  }   ← empty array, document is kept (left outer join)
```

**Q2. What are the two forms of `$lookup` — simple equality and pipeline — and when do you use each?**

A: MongoDB supports two syntaxes. The simple form covers equality joins between a local and foreign field. The pipeline form (added in MongoDB 3.6) handles everything the simple form cannot — multiple conditions, range joins, subqueries, and joining on non-_id fields with transformations:

```javascript
// ── Form 1: Simple equality join ─────────────────────────────────────────────
// Use when: joining on a single equality condition between two fields
{
    $lookup: {
        from:         'users',      // foreign collection
        localField:   'userId',     // field in the pipeline document (left)
        foreignField: '_id',        // field in 'users' (right)
        as:           'user',       // output array field name
    }
}
// Effectively: WHERE users._id = orders.userId
// Simple, readable, and optimised by MongoDB's query planner

// ── Form 2: Pipeline join (the modern, more powerful form) ───────────────────
// Use when: multiple conditions, non-equality, filtering/transforming joined docs,
//           subqueries within the joined collection, correlated lookups
{
    $lookup: {
        from:     'users',
        let:      { ordUserId: '$userId' },  // Variables from the LEFT document
        pipeline: [                           // Arbitrary pipeline on 'users'
            {
                $match: {
                    $expr: { $eq: ['$_id', '$$ordUserId'] }
                    // $$ accesses the let-declared variable
                    // $ accesses the current 'users' document's field
                }
            },
            { $project: { email: 1, name: 1, _id: 0 } }  // Limit returned fields
        ],
        as: 'user',
    }
}
// The pipeline runs once per left document, with access to that document's
// fields via the 'let' variables

// Feature comparison:
// ┌──────────────────────────────────┬──────────┬──────────┐
// │ Capability                       │ Simple   │ Pipeline │
// ├──────────────────────────────────┼──────────┼──────────┤
// │ Single equality condition        │    ✓     │    ✓     │
// │ Multiple join conditions         │    ✗     │    ✓     │
// │ Non-equality (range, $gt, $in)   │    ✗     │    ✓     │
// │ Filter joined documents          │    ✗     │    ✓     │
// │ Project/reshape joined docs      │    ✗     │    ✓     │
// │ Nested $lookup inside pipeline   │    ✗     │    ✓     │
// │ Use indexes on foreign collection│    ✓     │    ✓ *   │
// │ $lookup across shards (4.2+)     │    ✓     │    ✓     │
// └──────────────────────────────────┴──────────┴──────────┘
// * Pipeline form uses index on the first $match condition's field
```

## Section 2: Pipeline Form in Depth

**Q3. How does the `let` + `pipeline` syntax work — what is `$$` vs `$` and how do variables flow?**

A: The `let` clause declares variables from the left (pipeline) document, making them available inside the `pipeline` as `$$variableName`. Inside the sub-pipeline, `$fieldName` refers to fields in the RIGHT (joined) collection's documents. This two-dollar-sign vs one-dollar-sign distinction is the most common source of `$lookup` bugs:

```javascript
// Variable naming rules:
// $fieldName   → refers to the CURRENT DOCUMENT's field
//                inside the lookup pipeline: refers to the RIGHT collection's field
// $$varName    → refers to a VARIABLE declared in 'let' (from the LEFT document)
// $$NOW        → system variable: current date
// $$ROOT       → system variable: the entire current document
// $$CURRENT    → system variable: the current field being evaluated

db.orders.aggregate([
    {
        $lookup: {
            from: 'products',
            let: {
                //  Variable name   ← Expression evaluated against the LEFT (orders) document
                ordProductIds:       '$productIds',   // an array field on orders
                ordStatus:           '$status',        // a string field on orders
                ordCreatedAt:        '$createdAt',     // a date field on orders
            },
            pipeline: [
                // Inside here: '$fieldName' = products document field
                //              '$$varName'  = let-declared variable from orders document
                {
                    $match: {
                        $expr: {
                            $and: [
                                // Product._id must be in the order's productIds array:
                                { $in: ['$_id', '$$ordProductIds'] },

                                // Product must be active:
                                { $eq: ['$isActive', true] },

                                // Product price must be ≤ order total (contrived example
                                // of using a variable in a comparison):
                                { $lte: ['$price', '$$ordTotal'] },
                            ]
                        }
                    }
                },
                { $project: { name: 1, sku: 1, price: 1 } },
                { $sort: { price: 1 } },
            ],
            as: 'products',
        }
    }
]);

// The let block is evaluated ONCE per left document:
// For order { _id: 1, productIds: [ObjectId('p1'), ObjectId('p2')], status: 'pending' }:
//   $$ordProductIds = [ObjectId('p1'), ObjectId('p2')]
//   $$ordStatus     = 'pending'
//   $$ordCreatedAt  = ISODate('2024-01-15')

// The pipeline runs against 'products' collection, with access to those values:
// Step 1: $match filters products collection using both products fields ($) and order variables ($$)
// Step 2: $project limits fields on matched products
// Step 3: $sort sorts the matched products

// ── Common mistake: using $ instead of $$ for let variables ──────────────────
// WRONG:
{ $match: { $expr: { $in: ['$_id', '$ordProductIds'] } } }
// '$ordProductIds' tries to read a field named 'ordProductIds' from the products collection
// (which doesn't exist) → always matches nothing

// CORRECT:
{ $match: { $expr: { $in: ['$_id', '$$ordProductIds'] } } }
// '$$ordProductIds' reads the variable declared in 'let' from the orders document

// ── Using $expr for index hints ────────────────────────────────────────────────
// The $match stage inside a pipeline lookup CAN use indexes on the right collection
// BUT: the $expr operator bypasses the standard query planner in some versions
// For index use in pipeline lookups, structure the match to use the indexed field
// as the LEFT side of an $eq comparison when possible:
{ $match: { $expr: { $eq: ['$_id', '$$localId'] } } }
// MongoDB 5.0+ is smarter about index use inside $lookup pipelines
// Always verify with explain() on the full aggregation pipeline
```

**Q4. How do you join on multiple conditions — the key advantage of the pipeline form?**

A: The simple form only handles `localField = foreignField`. Real queries often need compound join conditions: equality on one field, a range condition on another, or matching against an array. The pipeline form handles all of these:

```javascript
// Scenario: find orders with their applicable promotions
// A promotion applies if:
//   1. promotion.userId matches order.userId (specific to this user)
//   2. promotion.validFrom <= order.createdAt (promotion started before the order)
//   3. promotion.validTo >= order.createdAt   (promotion hasn't expired)
//   4. promotion.minOrderValue <= order.total (order meets minimum value)
//   5. promotion.isActive = true

db.orders.aggregate([
    {
        $lookup: {
            from: 'promotions',
            let: {
                ordUserId:    '$userId',
                ordCreatedAt: '$createdAt',
                ordTotal:     '$total',
            },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                // Condition 1: user match
                                { $eq: ['$userId', '$$ordUserId'] },

                                // Condition 2: promotion has started
                                { $lte: ['$validFrom', '$$ordCreatedAt'] },

                                // Condition 3: promotion hasn't expired
                                { $gte: ['$validTo', '$$ordCreatedAt'] },

                                // Condition 4: minimum order value met
                                { $lte: ['$minOrderValue', '$$ordTotal'] },

                                // Condition 5: promotion is active
                                { $eq: ['$isActive', true] },
                            ]
                        }
                    }
                },
                // Only return relevant promotion fields:
                {
                    $project: {
                        code: 1,
                        discountPct: 1,
                        description: 1,
                    }
                }
            ],
            as: 'applicablePromotions',
        }
    },
    // Only orders that have at least one applicable promotion:
    { $match: { 'applicablePromotions.0': { $exists: true } } }
    // 'applicablePromotions.0' checks if the array has at least one element
    // Equivalent to: { applicablePromotions: { $ne: [] } }
]);

// ── Joining on array membership ────────────────────────────────────────────────
// Find products that belong to any of the user's followed categories
db.users.aggregate([
    {
        $lookup: {
            from: 'products',
            let: { userCategoryIds: '$followedCategoryIds' },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            // Product's categoryId is in the user's followed categories
                            $in: ['$categoryId', '$$userCategoryIds']
                        }
                    }
                },
                { $limit: 20 },  // Limit results per user (important for performance)
                { $project: { name: 1, price: 1, thumbnail: 1 } },
            ],
            as: 'recommendedProducts',
        }
    }
]);

// ── Correlated subquery pattern: $lookup + $filter ────────────────────────────
// Find each user with only their RECENT orders (last 30 days):
db.users.aggregate([
    {
        $lookup: {
            from: 'orders',
            let: { userId: '$_id' },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                { $eq: ['$userId', '$$userId'] },
                                {
                                    $gte: [
                                        '$createdAt',
                                        {
                                            $dateSubtract: {
                                                startDate: '$$NOW',
                                                unit: 'day',
                                                amount: 30
                                            }
                                        }
                                    ]
                                }
                            ]
                        }
                    }
                },
                { $sort: { createdAt: -1 } },
                { $limit: 10 },
                { $project: { total: 1, status: 1, createdAt: 1 } }
            ],
            as: 'recentOrders',
        }
    }
]);
```

## Section 3: Transforming the Output

**Q5. How do you reshape the `$lookup` result — `$unwind`, `$replaceRoot`, and flattening the array?**

A: `$lookup` always produces an array in the output field, even when only one document matches or when doing a one-to-one join. Subsequent stages reshape this into the final form:

```javascript
// After $lookup, output looks like:
// { _id: 1, total: 99.99, userId: ..., user: [{ email: '...', name: '...' }] }
// The 'user' field is an ARRAY — always, even for one-to-one joins

// ── $unwind: convert array to individual documents ─────────────────────────────
// For one-to-one joins: turn the array of one into a plain object
db.orders.aggregate([
    {
        $lookup: {
            from:         'users',
            localField:   'userId',
            foreignField: '_id',
            as:           'user',
        }
    },
    {
        $unwind: {
            path: '$user',
            preserveNullAndEmptyArrays: true,
            // preserveNullAndEmptyArrays: true  → keep orders with no matching user
            //   (user becomes null instead of dropping the document)
            // preserveNullAndEmptyArrays: false → acts like INNER JOIN (drops non-matches)
        }
    }
]);
// Output:
// { _id: 1, total: 99.99, user: { email: 'alice@...', name: 'Alice' } }
// { _id: 3, total: 19.99, user: null }  ← preserveNullAndEmptyArrays: true

// ── Shorthand $unwind without options (drops empty arrays — INNER JOIN behaviour):
{ $unwind: '$user' }
// Equivalent to SQL INNER JOIN — orders with user: [] are dropped

// ── Inline $unwind inside $lookup (MongoDB 3.2+ optimisation) ─────────────────
// When you immediately $unwind after $lookup, MongoDB can optimise this into a
// single pass instead of materialising the full array first:
db.orders.aggregate([
    {
        $lookup: {
            from:         'users',
            localField:   'userId',
            foreignField: '_id',
            as:           'user',
        }
    },
    { $unwind: '$user' }  // MongoDB fuses this with the $lookup above
]);
// The query planner detects $lookup immediately followed by $unwind
// and executes them as one efficient operation

// ── $addFields / $set to merge the joined document's fields ───────────────────
// Flatten the user object fields into the order document:
db.orders.aggregate([
    {
        $lookup: {
            from: 'users',
            localField: 'userId',
            foreignField: '_id',
            as: 'user',
        }
    },
    { $unwind: { path: '$user', preserveNullAndEmptyArrays: true } },
    {
        $addFields: {
            userName:  '$user.name',
            userEmail: '$user.email',
        }
    },
    { $unset: 'user' }   // Remove the full user object, keep the extracted fields
]);
// Output: { _id: 1, total: 99.99, userId: ..., userName: 'Alice', userEmail: '...' }

// ── $replaceRoot with $mergeObjects: merge joined doc fields at the root ────────
// Merge the entire user document into the order document (user fields become top-level):
db.orders.aggregate([
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    },
    { $unwind: { path: '$user', preserveNullAndEmptyArrays: true } },
    {
        $replaceRoot: {
            newRoot: {
                $mergeObjects: ['$user', '$$ROOT']  // Order fields override user fields on conflict
                // $$ROOT = the entire current pipeline document (order + user)
                // $user  = just the user subdocument
                // $mergeObjects: left keys are overridden by right keys
            }
        }
    },
    { $unset: 'user' }
]);
// Output: { _id: 1, email: 'alice@...', name: 'Alice', total: 99.99, ... }
// Order _id wins over user _id because $$ROOT comes second

// ── $first on array when you know exactly one match ───────────────────────────
// Without $unwind — extract the first element directly:
db.orders.aggregate([
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    },
    {
        $addFields: {
            user: { $first: '$user' }   // $first: extracts element 0, returns null if empty
            // $arrayElemAt: ['$user', 0]  ← equivalent alternative
        }
    }
]);
// Output: { _id: 1, ..., user: { email: '...', name: '...' } }
// No $unwind needed — user is a single object (or null)
```

**Q6. How do you chain multiple `$lookup` stages — and what are the performance implications?**

A: Multiple `$lookup` stages run sequentially in the pipeline. Each stage operates on the output of the previous one. Chaining is powerful but must be done carefully — each join multiplies the data flowing through the pipeline:

```javascript
// Scenario: get orders with their user, their product details, and their discount info
db.orders.aggregate([
    // Stage 1: filter to relevant orders first (do this BEFORE lookups)
    {
        $match: {
            status:    'pending',
            createdAt: { $gte: new Date('2024-01-01') }
        }
    },

    // Stage 2: join users (one-to-one: each order has one user)
    {
        $lookup: {
            from:         'users',
            localField:   'userId',
            foreignField: '_id',
            as:           'user',
        }
    },
    { $unwind: { path: '$user', preserveNullAndEmptyArrays: true } },

    // Stage 3: join products (one-to-many: each order has multiple products)
    {
        $lookup: {
            from: 'products',
            let:  { productIds: '$productIds' },
            pipeline: [
                { $match: { $expr: { $in: ['$_id', '$$productIds'] } } },
                { $project: { name: 1, sku: 1, price: 1 } },
            ],
            as: 'products',
        }
    },

    // Stage 4: join discounts (conditional: only for orders with a discountCode)
    {
        $lookup: {
            from: 'discounts',
            let:  { code: '$discountCode' },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                { $eq: ['$code', '$$code'] },
                                { $eq: ['$isActive', true] },
                            ]
                        }
                    }
                },
                { $project: { pct: 1, code: 1 } },
            ],
            as: 'discount',
        }
    },
    {
        $addFields: {
            discount: { $first: '$discount' }  // null if no discount
        }
    },

    // Stage 5: shape the final output
    {
        $project: {
            _id:       1,
            total:     1,
            status:    1,
            createdAt: 1,
            'user.email': 1,
            'user.name':  1,
            products:  1,
            'discount.pct':  1,
            'discount.code': 1,
        }
    }
]);

// ── Nested $lookup: joining INSIDE a pipeline lookup ──────────────────────────
// Fetch orders, then for each order fetch its items AND each item's product:
db.orders.aggregate([
    {
        $lookup: {
            from: 'orderItems',
            let:  { orderId: '$_id' },
            pipeline: [
                { $match: { $expr: { $eq: ['$orderId', '$$orderId'] } } },
                // Nested $lookup inside the pipeline:
                {
                    $lookup: {
                        from:         'products',
                        localField:   'productId',
                        foreignField: '_id',
                        as:           'product',
                    }
                },
                { $unwind: { path: '$product', preserveNullAndEmptyArrays: true } },
                {
                    $project: {
                        quantity: 1,
                        unitPrice: 1,
                        'product.name': 1,
                        'product.sku':  1,
                    }
                }
            ],
            as: 'items',
        }
    }
]);
// Warning: nested $lookup is expensive — O(orders × items × products)
// Ensure indexes exist on: orderItems.orderId, products._id
```

## Section 4: Performance

**Q7. How does `$lookup` use indexes — what is required for acceptable performance?**

A: `$lookup` performance is almost entirely determined by whether the right collection has an index on the foreign field. Without an index, each left document triggers a collection scan of the right collection:

```javascript
// Without index on the joined field:
// For each order document: full scan of users collection
// 10,000 orders × 100,000 users = 1 billion comparisons → catastrophically slow

// With index on users._id (or whatever foreignField is):
// For each order document: B-tree lookup in users
// 10,000 orders × O(log 100,000) = ~170,000 operations → fast

// ── Index requirements for each $lookup form ──────────────────────────────────

// Simple form:
db.orders.aggregate([{
    $lookup: {
        from:         'users',
        localField:   'userId',      // orders.userId
        foreignField: '_id',         // users._id ← MongoDB always has this index
        as:           'user',
    }
}]);
// users._id has an automatic index → efficient
// If foreignField were 'email': ensure db.users.createIndex({ email: 1 }) exists

// Pipeline form:
db.orders.aggregate([{
    $lookup: {
        from: 'users',
        let:  { uid: '$userId' },
        pipeline: [
            { $match: { $expr: { $eq: ['$_id', '$$uid'] } } },
            // MongoDB 5.0+ can use index on users._id here
            // Earlier versions: $expr sometimes bypasses indexes
        ],
        as: 'user',
    }
}]);
// To ensure index use in pipeline form (more reliable across versions):
// Structure the $match to help the query planner:
pipeline: [
    {
        $match: {
            // Add a non-expr condition first (index-friendly):
            // _id: { $in: someArrayOfIds }  -- but this is dynamic per doc
            // For pipeline lookups, MongoDB 5.0+ handles $expr with indexes well
            // For earlier versions, use the simple form when equality is the only condition
            $expr: { $eq: ['$_id', '$$uid'] }
        }
    }
]

// ── Checking if $lookup uses an index ────────────────────────────────────────
db.orders.explain('executionStats').aggregate([
    {
        $lookup: {
            from:         'users',
            localField:   'userId',
            foreignField: '_id',
            as:           'user',
        }
    }
]);
// In the explain output, look for the $lookup stage:
// "strategy": "IndexedLoopJoin" → using an index (fast)
// "strategy": "NestedLoopJoin"  → no index (potentially slow)
// "strategy": "HashJoin"        → MongoDB's hash join (4.4+, good for larger datasets)

// Creating the required index:
db.users.createIndex({ _id: 1 });    // Already exists (auto-created)
db.products.createIndex({ sku: 1 }); // If joining on SKU
db.orderItems.createIndex({ orderId: 1 }); // If joining on orderId

// ── $lookup join strategies (MongoDB 4.4+) ────────────────────────────────────
// MongoDB chooses between three join strategies automatically:
// 1. IndexedLoopJoin: for each left doc, index lookup on right → O(N log M)
// 2. NestedLoopJoin:  for each left doc, collection scan on right → O(N × M)
// 3. HashJoin:        hash the smaller collection, probe with larger → O(N + M)
//    → HashJoin is chosen when: no index on right, both collections fit in allowDiskUse memory
//    → Enable: { allowDiskUse: true } on the aggregate command

db.orders.aggregate(
    [{ $lookup: { from: 'users', localField: 'userId', foreignField: '_id', as: 'user' } }],
    { allowDiskUse: true }  // Allow hash join to spill to disk if needed
);
```

**Q8. What are the most common performance pitfalls with `$lookup` and how do you avoid them?**

A: `$lookup` is one of the most misused aggregation stages. The pitfalls are consistent and predictable:

```javascript
// ── Pitfall 1: No $match before $lookup (full collection join) ────────────────
// WRONG: lookup runs on the ENTIRE orders collection first:
db.orders.aggregate([
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    },
    { $match: { status: 'pending' } }  // Filter applied AFTER joining millions of docs
]);

// CORRECT: filter BEFORE lookup to reduce the number of left documents:
db.orders.aggregate([
    { $match: { status: 'pending' } },  // Reduces from 1M to 50k documents
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    }
]);
// Orders of magnitude improvement for filtered queries

// ── Pitfall 2: No $limit inside the pipeline lookup ────────────────────────────
// One-to-many join without limiting the "many" side:
db.users.aggregate([
    {
        $lookup: {
            from: 'events',
            let:  { uid: '$_id' },
            pipeline: [
                { $match: { $expr: { $eq: ['$userId', '$$uid'] } } },
                // No $limit! A power user with 500k events causes 500k docs in the array
            ],
            as: 'events',
        }
    }
]);
// One user with 500k events → 500k documents in 'events' array → likely OOM
// The 16MB BSON document size limit will error if the array is too large

// CORRECT: always limit one-to-many results:
pipeline: [
    { $match: { $expr: { $eq: ['$userId', '$$uid'] } } },
    { $sort: { createdAt: -1 } },
    { $limit: 100 },                    // Take only the 100 most recent
    { $project: { type: 1, createdAt: 1 } }  // Project early to reduce size
]

// ── Pitfall 3: Joining on unindexed fields ─────────────────────────────────────
db.orders.aggregate([{
    $lookup: {
        from:         'products',
        localField:   'productSku',   // orders.productSku
        foreignField: 'sku',          // products.sku  ← is this indexed?
        as:           'product',
    }
}]);
// Verify: db.products.getIndexes()
// If no index on 'sku': every order triggers a full products scan
// Fix: db.products.createIndex({ sku: 1 })

// ── Pitfall 4: Projecting too late (large intermediate documents) ──────────────
// WRONG: carry full documents through the pipeline then project at the end:
db.orders.aggregate([
    { $lookup: { from: 'users', localField: 'userId', foreignField: '_id', as: 'user' } },
    // users documents may have 50+ fields, user history arrays, etc.
    { $lookup: { from: 'products', localField: 'productIds', foreignField: '_id', as: 'products' } },
    { $project: { total: 1, 'user.email': 1, 'products.name': 1 } }  // Too late
]);
// Large intermediate documents consume memory throughout the pipeline

// CORRECT: project inside the lookup pipeline AND project early after each lookup:
{
    $lookup: {
        from: 'users',
        let:  { uid: '$userId' },
        pipeline: [
            { $match: { $expr: { $eq: ['$_id', '$$uid'] } } },
            { $project: { email: 1, name: 1, _id: 0 } }  // Project INSIDE lookup
        ],
        as: 'user',
    }
}
// user array now contains only {email, name} instead of the full user document

// ── Pitfall 5: $lookup across sharded collections (pre-5.0) ───────────────────
// In MongoDB < 5.0:
// - The 'from' collection must be unsharded OR on the same shard as the lookup
// - Sharded $lookup required the joined collection to be on the primary shard
// In MongoDB 5.0+:
// - $lookup can join across sharded collections freely (distributed joins)
// Still: cross-shard joins are expensive due to network round-trips
// Design to minimise cross-shard joins where possible

// ── Pitfall 6: $lookup as a substitute for embedding (wrong data model) ────────
// If you run $lookup on EVERY query for a particular pair of collections,
// the data model is wrong — embed the data instead
// $lookup is for OCCASIONAL denormalisation at query time, not routine joins
// If you always need user.name when displaying an order → embed it in the order
// { orderId: 1, userId: ..., userName: 'Alice', total: 99.99 }
// Accept write duplication for read performance
```

## Section 5: Common Patterns

**Q9. How do you implement an `INNER JOIN` equivalent with `$lookup` — filtering out non-matches?**

A: `$lookup` is always a LEFT OUTER join. To simulate an INNER join (drop documents with no matching right-side document), add a `$match` after the lookup:

```javascript
// LEFT OUTER (default $lookup behaviour):
// All orders kept, even those with no matching user → user: []

// INNER JOIN equivalent — drop orders with no matching user:
db.orders.aggregate([
    {
        $lookup: {
            from:         'users',
            localField:   'userId',
            foreignField: '_id',
            as:           'user',
        }
    },
    // Drop documents where the lookup produced an empty array:
    { $match: { user: { $ne: [] } } },
    // OR equivalently:
    { $match: { 'user.0': { $exists: true } } },
    // OR: $unwind without preserveNullAndEmptyArrays (drops empty arrays):
    // { $unwind: '$user' }  // This also achieves INNER JOIN semantics
]);

// Most readable INNER JOIN pattern:
db.orders.aggregate([
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    },
    { $unwind: '$user' }   // Drops orders where user: [] → INNER JOIN
]);

// ── Anti-join: find orders that have NO matching user ─────────────────────────
// Equivalent to SQL: WHERE NOT EXISTS (SELECT 1 FROM users WHERE users._id = orders.userId)
db.orders.aggregate([
    {
        $lookup: {
            from: 'users', localField: 'userId', foreignField: '_id', as: 'user'
        }
    },
    { $match: { user: { $eq: [] } } }   // Keep only orders with no matching user
]);
// Useful for: finding orphaned records, data integrity checks

// ── EXISTS check (not joining the data, just checking existence) ───────────────
// More efficient than a full join when you only need to know IF a match exists:
db.orders.aggregate([
    {
        $lookup: {
            from: 'reviews',
            let:  { ordId: '$_id' },
            pipeline: [
                { $match: { $expr: { $eq: ['$orderId', '$$ordId'] } } },
                { $limit: 1 },         // Stop after finding one match (existence check)
                { $project: { _id: 1 } },  // Minimal projection
            ],
            as: 'hasReview',
        }
    },
    {
        $addFields: {
            hasReview: { $gt: [{ $size: '$hasReview' }, 0] }  // Convert to boolean
        }
    }
]);
// { _id: 1, total: 99.99, hasReview: true }
// { _id: 2, total: 49.99, hasReview: false }
// More efficient than $lookup without $limit: only fetches one review document per order
```

**Q10. How do you implement a self-join or hierarchical query with `$lookup`?**

A: `$lookup` can join a collection to itself — useful for hierarchical data (categories with parent/child), graph traversals, and recursive relationships. MongoDB also provides `$graphLookup` for true recursive traversals:

```javascript
// ── Self-join: categories with their parent category ─────────────────────────
// Categories collection:
// { _id: 1, name: 'Electronics', parentId: null }
// { _id: 2, name: 'Laptops', parentId: 1 }
// { _id: 3, name: 'Gaming Laptops', parentId: 2 }

db.categories.aggregate([
    {
        $lookup: {
            from:         'categories',   // Same collection as the source
            localField:   'parentId',
            foreignField: '_id',
            as:           'parent',
        }
    },
    {
        $addFields: {
            parent: { $first: '$parent' }  // null if no parent (root category)
        }
    }
]);
// Output:
// { _id: 1, name: 'Electronics', parentId: null, parent: null }
// { _id: 2, name: 'Laptops', parentId: 1, parent: { _id: 1, name: 'Electronics' } }
// { _id: 3, name: 'Gaming Laptops', parentId: 2, parent: { _id: 2, name: 'Laptops' } }

// ── $graphLookup: recursive traversal up/down the hierarchy ───────────────────
// Find all ancestors of 'Gaming Laptops' (depth-first traversal):
db.categories.aggregate([
    { $match: { name: 'Gaming Laptops' } },
    {
        $graphLookup: {
            from:             'categories',     // Collection to traverse
            startWith:        '$parentId',      // Starting value (current doc's parentId)
            connectFromField: 'parentId',       // Field to follow (each doc's parentId)
            connectToField:   '_id',            // Field to match against
            as:               'ancestors',      // Output array of all ancestors
            maxDepth:         10,               // Maximum traversal depth
            depthField:       'depth',          // Add a 'depth' field to each result
        }
    }
]);
// Output:
// {
//   _id: 3, name: 'Gaming Laptops',
//   ancestors: [
//     { _id: 2, name: 'Laptops',     depth: 0 },  // immediate parent
//     { _id: 1, name: 'Electronics', depth: 1 },  // grandparent
//   ]
// }

// Find all descendants of 'Electronics' (top-down):
db.categories.aggregate([
    { $match: { name: 'Electronics' } },
    {
        $graphLookup: {
            from:             'categories',
            startWith:        '$_id',          // Start from current doc's _id
            connectFromField: '_id',           // Follow _id of each found document
            connectToField:   'parentId',      // Match against children's parentId
            as:               'descendants',
            maxDepth:         5,
        }
    }
]);
// Output includes all categories under Electronics at any depth
```

## Section 6: Real-World Patterns

**Q11. How do you build a complete product listing page query with `$lookup` — a realistic production example?**

A: A product listing page typically requires joining categories, reviews summary, stock levels, and promotions — all in a single aggregation:

```javascript
// Product listing: electronics category, in stock, sorted by rating, page 2
db.products.aggregate([
    // ── Stage 1: filter products (do this first!) ─────────────────────────────
    {
        $match: {
            categoryId: ObjectId('cat-electronics'),
            isActive:   true,
        }
    },

    // ── Stage 2: join category details ────────────────────────────────────────
    {
        $lookup: {
            from:         'categories',
            localField:   'categoryId',
            foreignField: '_id',
            as:           'category',
            pipeline: [
                { $project: { name: 1, slug: 1, _id: 0 } }
            ],
        }
    },
    // Note: pipeline form supported with 'from' in MongoDB 5.1+ for this syntax
    // For earlier versions: use let + pipeline syntax
    { $addFields: { category: { $first: '$category' } } },

    // ── Stage 3: join review summary (pre-aggregated for performance) ──────────
    // Assuming reviews are pre-aggregated into a reviewSummaries collection:
    // { productId, avgRating, totalReviews, ratingDistribution }
    {
        $lookup: {
            from:         'reviewSummaries',
            localField:   '_id',
            foreignField: 'productId',
            as:           'reviewSummary',
        }
    },
    { $addFields: { reviewSummary: { $first: '$reviewSummary' } } },

    // ── Stage 4: join current inventory (from separate inventory service/collection)
    {
        $lookup: {
            from: 'inventory',
            let:  { prodId: '$_id' },
            pipeline: [
                { $match: { $expr: { $eq: ['$productId', '$$prodId'] } } },
                { $project: { quantityAvailable: 1, warehouseId: 1 } },
                { $limit: 1 }
            ],
            as: 'inventory',
        }
    },
    { $addFields: { inventory: { $first: '$inventory' } } },

    // ── Stage 5: join active promotions ───────────────────────────────────────
    {
        $lookup: {
            from: 'promotions',
            let:  { prodId: '$_id' },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                { $in: ['$$prodId', '$applicableProductIds'] },
                                { $lte: ['$validFrom', '$$NOW'] },
                                { $gte: ['$validTo',   '$$NOW'] },
                                { $eq:  ['$isActive',  true]   },
                            ]
                        }
                    }
                },
                { $project: { discountPct: 1, label: 1, badgeColor: 1 } },
                { $limit: 1 }  // Only apply one promotion per product for display
            ],
            as: 'activePromotion',
        }
    },
    { $addFields: { activePromotion: { $first: '$activePromotion' } } },

    // ── Stage 6: add computed fields ──────────────────────────────────────────
    {
        $addFields: {
            inStock:        { $gt: ['$inventory.quantityAvailable', 0] },
            displayPrice:   {
                $cond: {
                    if:   { $ne: ['$activePromotion', null] },
                    then: {
                        $multiply: [
                            '$price',
                            { $subtract: [1, { $divide: ['$activePromotion.discountPct', 100] }] }
                        ]
                    },
                    else: '$price'
                }
            },
            avgRating:      { $ifNull: ['$reviewSummary.avgRating', 0] },
            totalReviews:   { $ifNull: ['$reviewSummary.totalReviews', 0] },
        }
    },

    // ── Stage 7: filter by stock (after computing inStock) ─────────────────────
    { $match: { inStock: true } },

    // ── Stage 8: sort ──────────────────────────────────────────────────────────
    { $sort: { avgRating: -1, totalReviews: -1 } },

    // ── Stage 9: pagination ────────────────────────────────────────────────────
    { $skip: 20 },   // Page 2, 20 per page
    { $limit: 20 },

    // ── Stage 10: final projection ─────────────────────────────────────────────
    {
        $project: {
            name:           1,
            slug:           1,
            price:          1,
            displayPrice:   1,
            images:         { $slice: ['$images', 1] },  // Only first image for listing
            'category.name': 1,
            'category.slug': 1,
            avgRating:      1,
            totalReviews:   1,
            inStock:        1,
            'activePromotion.label':      1,
            'activePromotion.badgeColor': 1,
        }
    }
]);
```

## Section 7: Testing and Scenario Questions

**Q12. "What's wrong with this `$lookup`? It's returning no results even though matching documents exist."**

```javascript
db.orders.aggregate([
    {
        $lookup: {
            from: 'users',
            let:  { userId: '$userId' },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $eq: ['$userId', '$userId']  // BUG HERE
                        }
                    }
                }
            ],
            as: 'user',
        }
    }
]);
```

A: The bug is using `$userId` instead of `$$userId` for the let variable — the most common `$lookup` pipeline mistake:

```javascript
// BUG ANALYSIS:
{ $eq: ['$userId', '$userId'] }
// '$userId' on the LEFT  → the 'userId' field of the current users document
// '$userId' on the RIGHT → ALSO the 'userId' field of the current users document
// This comparison is: users.userId == users.userId
// → Always TRUE for any user document that has a userId field
// → But since we want users._id == orders.userId, we're matching the WRONG condition
// → Every user matches every order (or none, depending on users having a userId field)

// ACTUAL RESULT: either all users are returned for every order,
// or no users if the 'userId' field doesn't exist on users collection

// CORRECT version:
{
    $match: {
        $expr: {
            $eq: ['$_id', '$$userId']
            //    ^          ^^
            //    $    = users._id (from the RIGHT collection)
            //    $$   = userId variable declared in 'let' (from the LEFT / orders document)
        }
    }
}

// OR in most cases, for a simple _id equality, use the simple form instead:
{
    $lookup: {
        from:         'users',
        localField:   'userId',  // orders.userId
        foreignField: '_id',     // users._id
        as:           'user',
    }
}
// Simpler, more readable, and often better optimised

// Additional debugging techniques for $lookup:
// 1. Test the inner pipeline independently:
db.users.aggregate([
    {
        $match: {
            $expr: {
                $eq: ['$_id', ObjectId('specific-user-id')]
                // Hard-code a value to test the pipeline alone
            }
        }
    }
]);

// 2. Check that let variables have the right value:
db.orders.aggregate([
    { $limit: 1 },
    {
        $addFields: {
            debug_userId: '$userId'  // Verify the field exists and has the right type
        }
    }
]);
// If userId is stored as a string but users._id is an ObjectId → type mismatch → no match

// 3. Type mismatch — one of the most common real bugs:
// orders.userId stored as: "507f1f77bcf86cd799439011" (String)
// users._id stored as:     ObjectId("507f1f77bcf86cd799439011")
// $eq comparison fails because String ≠ ObjectId even with same content
// Fix: normalise the type, or use $toObjectId / $toString in the $expr
```

**Q13. "Design an aggregation to find the top 10 users by total order value in the last 30 days, including their profile details and most recent order."**

A:

```javascript
db.orders.aggregate([
    // ── Stage 1: filter to last 30 days ──────────────────────────────────────
    {
        $match: {
            createdAt: {
                $gte: new Date(Date.now() - 30 * 24 * 60 * 60 * 1000)
            },
            status: { $in: ['completed', 'shipped', 'delivered'] }
        }
    },

    // ── Stage 2: sort by date before grouping (for $first to get most recent) ─
    { $sort: { createdAt: -1 } },

    // ── Stage 3: group by userId, aggregate order stats ───────────────────────
    {
        $group: {
            _id:              '$userId',
            totalOrderValue:  { $sum: '$total' },
            orderCount:       { $sum: 1 },
            mostRecentOrder: {
                $first: {       // $sort before $group → $first = most recent
                    orderId:   '$_id',
                    total:     '$total',
                    status:    '$status',
                    createdAt: '$createdAt',
                }
            },
            avgOrderValue:    { $avg: '$total' },
        }
    },

    // ── Stage 4: rank by total order value ───────────────────────────────────
    { $sort: { totalOrderValue: -1 } },
    { $limit: 10 },

    // ── Stage 5: join user profile details ───────────────────────────────────
    {
        $lookup: {
            from: 'users',
            let:  { uid: '$_id' },
            pipeline: [
                { $match: { $expr: { $eq: ['$_id', '$$uid'] } } },
                {
                    $project: {
                        email:     1,
                        name:      1,
                        plan:      1,
                        avatarUrl: 1,
                        joinedAt:  '$createdAt',
                        _id:       0,
                    }
                }
            ],
            as: 'userProfile',
        }
    },
    { $addFields: { userProfile: { $first: '$userProfile' } } },

    // ── Stage 6: join user's lifetime stats (from a pre-aggregated summary) ───
    {
        $lookup: {
            from:         'userOrderSummaries',
            localField:   '_id',
            foreignField: 'userId',
            as:           'lifetimeSummary',
        }
    },
    { $addFields: { lifetimeSummary: { $first: '$lifetimeSummary' } } },

    // ── Stage 7: final shape ──────────────────────────────────────────────────
    {
        $project: {
            _id:             0,
            userId:          '$_id',
            'userProfile.email':     1,
            'userProfile.name':      1,
            'userProfile.plan':      1,
            'userProfile.avatarUrl': 1,
            'userProfile.joinedAt':  1,

            // 30-day stats:
            totalOrderValue:  { $round: ['$totalOrderValue', 2] },
            orderCount:       1,
            avgOrderValue:    { $round: ['$avgOrderValue', 2] },
            mostRecentOrder:  1,

            // Lifetime stats (from summary collection):
            lifetimeTotalValue: '$lifetimeSummary.totalValue',
            lifetimeOrderCount: '$lifetimeSummary.orderCount',
        }
    }
]);

// Expected output:
// [
//   {
//     userId: ObjectId('...'),
//     userProfile: { email: 'alice@...', name: 'Alice', plan: 'enterprise', ... },
//     totalOrderValue: 15432.50,
//     orderCount: 23,
//     avgOrderValue: 670.98,
//     mostRecentOrder: { orderId: ..., total: 299.99, status: 'delivered', createdAt: ... },
//     lifetimeTotalValue: 89432.00,
//     lifetimeOrderCount: 145,
//   },
//   ...
// ]

// Performance notes:
// - $match at the start reduces documents from millions to ~30-day window
// - $group reduces further to one doc per user before $lookup
// - Only 10 documents go into the $lookup (after $limit 10)
// - This is critical: $lookup on 10 docs is fast; on 1M docs would be catastrophic
// - Index needed: orders.createdAt for the initial $match
// - Index needed: users._id (auto-indexed) for the $lookup
```

## Quick Reference Table

| Feature | Simple form | Pipeline form |
|---|---|---|
| **Syntax** | `localField` + `foreignField` | `let` + `pipeline` |
| **Single equality join** | ✓ | ✓ |
| **Multiple conditions** | ✗ | ✓ |
| **Range / non-equality** | ✗ | ✓ |
| **Filter joined docs** | ✗ | ✓ |
| **Project inside join** | ✗ | ✓ |
| **Nested `$lookup`** | ✗ | ✓ |
| **Index usage** | ✓ Reliable | ✓ MongoDB 5.0+ |
| **When to use** | Simple `_id` lookups | Everything else |

| Variable syntax | Meaning |
|---|---|
| `$fieldName` | Field in the current (right-side) document |
| `$$varName` | Variable declared in `let` (from the left-side document) |
| `$$NOW` | Current timestamp (system variable) |
| `$$ROOT` | Entire current pipeline document |

| After `$lookup` the output field is... | What to do |
|---|---|
| Always an array | Use `$unwind`, `$first`, or `$arrayElemAt` to extract single results |
| Empty array `[]` | Document had no match (left outer join kept it) |
| Array with one element | One-to-one join — use `{ $first: '$field' }` |
| Array with many elements | One-to-many join — use as-is or `$unwind` to flatten |

| Common mistake | Fix |
|---|---|
| `$varName` instead of `$$varName` in `let` pipeline | Always `$$` for let variables |
| `$lookup` before `$match` | Move `$match` before `$lookup` |
| No `$limit` in one-to-many pipeline | Add `$limit` inside the pipeline |
| No index on `foreignField` | `db.collection.createIndex({ field: 1 })` |
| Joining on mismatched types (String vs ObjectId) | Normalise types or use `$toObjectId`/`$toString` |
| Using `$lookup` instead of embedding | Embed if always accessed together |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **`$lookup` is always a LEFT OUTER join** — non-matching left documents are kept with an empty array, not dropped; dropping non-matches (INNER JOIN behaviour) requires a subsequent `$match: { field: { $ne: [] } }` or `$unwind` without `preserveNullAndEmptyArrays`; (2) understanding the **`$` vs `$$` distinction** — `$field` refers to the right-side (joined) collection's field, while `$$var` refers to a variable declared in `let` from the left document; confusing them produces a comparison of a field against itself (always true or always false) which is the most common `$lookup` bug; (3) knowing that **`$match` must come before `$lookup`** for performance — the most expensive mistake is putting `$lookup` first and `$match` after, causing the join to run on the entire collection before filtering; (4) always adding **`$limit` inside a one-to-many pipeline lookup** — joining users to their events without a `$limit` can produce arrays with millions of elements per document, hitting the 16MB BSON document size limit or causing OOM; (5) knowing the **three join strategies** MongoDB chooses from — `IndexedLoopJoin` (has index, fast), `NestedLoopJoin` (no index, very slow), `HashJoin` (MongoDB 4.4+, good for large datasets without indexes) — and that running `explain()` on an aggregation reveals which strategy was chosen; and (6) articulating **when `$lookup` is the wrong tool** — if you're doing a `$lookup` on every single query for the same pair of collections, the data model is wrong and embedding (denormalisation) is the correct solution; `$lookup` is for occasional recombination of naturally separate data, not a substitute for proper schema design.
