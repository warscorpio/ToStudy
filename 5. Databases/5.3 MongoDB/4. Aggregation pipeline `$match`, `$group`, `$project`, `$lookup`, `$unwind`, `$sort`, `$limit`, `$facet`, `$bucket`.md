# MongoDB Aggregation Pipeline — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the aggregation pipeline, how does it work, and what makes it different from `find()`?**
A: The aggregation pipeline is MongoDB's data transformation and analysis framework. It processes documents through a sequence of stages — each stage transforms the stream of documents from the previous stage and passes results to the next. Unlike `find()`, which only filters and projects existing documents, the pipeline can reshape documents, join collections, compute new fields, group data, and produce entirely new document structures:

```
Pipeline mental model — documents flow through stages:

  Collection: orders (1,000,000 documents)
  │
  ▼
  ┌─────────────────────────────────────────┐
  │ Stage 1: $match                         │  1,000,000 → 45,000 docs
  │ { status: "COMPLETED", year: 2024 }     │  Filter first — always
  └──────────────────┬──────────────────────┘
                     │ 45,000 documents
                     ▼
  ┌─────────────────────────────────────────┐
  │ Stage 2: $group                         │  45,000 → 250 docs
  │ { _id: "$region", total: { $sum: "$amount" } }  │  Aggregate
  └──────────────────┬──────────────────────┘
                     │ 250 documents
                     ▼
  ┌─────────────────────────────────────────┐
  │ Stage 3: $sort                          │  250 → 250 docs
  │ { total: -1 }                           │  Sort
  └──────────────────┬──────────────────────┘
                     │ 250 documents
                     ▼
  ┌─────────────────────────────────────────┐
  │ Stage 4: $limit                         │  250 → 10 docs
  │ 10                                      │  Limit
  └──────────────────┬──────────────────────┘
                     │ 10 documents
                     ▼
  Result: top 10 regions by completed order revenue in 2024
```

```javascript
// find() vs aggregation — what each can and cannot do:

// find(): filter + project only, documents always map 1:1
db.orders.find(
    { status: "COMPLETED" },             // filter
    { _id: 0, userId: 1, amount: 1 }     // project
)
// Cannot: group, compute totals, join other collections, reshape arrays

// aggregation: unlimited transformation power
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    {
        $group: {
            _id: "$userId",
            totalSpent: { $sum: "$amount" },
            orderCount: { $sum: 1 },
            avgOrder:   { $avg: "$amount" },
            lastOrder:  { $max: "$createdAt" }
        }
    },
    { $sort: { totalSpent: -1 } },
    { $limit: 100 }
])
// Returns computed summary documents — not original documents
// Documents produced by $group have no relation to individual orders
```

```javascript
// Pipeline execution basics:
db.collection.aggregate(
    pipeline,        // Array of stage objects
    options          // Optional configuration
)

// Options:
db.orders.aggregate(
    [ /* stages */ ],
    {
        allowDiskUse: true,    // Allow writing temp files for large sorts/groups
                               // Default: false — pipeline limited to 100MB RAM
        cursor: { batchSize: 1000 },  // How many docs per cursor batch
        comment: "revenue report Q1 2024",  // Appears in query logs for profiling
        hint: { status: 1, createdAt: 1 },  // Force index use (like .hint() on find)
        maxTimeMS: 30000,      // Kill if takes > 30 seconds
        explain: "executionStats"  // Get execution plan (or use .explain() method)
    }
)

// Explain a pipeline:
db.orders.explain("executionStats").aggregate([
    { $match: { status: "COMPLETED" } },
    { $group: { _id: "$region", count: { $sum: 1 } } }
])
// Shows: index usage, documents examined, time per stage
// Look for: "COLLSCAN" (no index) vs "IXSCAN" (index used)
```

**Q2. What is the performance golden rule of aggregation pipelines — why must `$match` and `$sort` come first?**
A: The pipeline processes documents sequentially. Every document entering a stage costs CPU and memory. Placing `$match` first reduces the document count flowing into all subsequent stages. Placing `$sort` before `$group` allows the sort to use an index. Violating these rules forces the pipeline to process more data than necessary:

```javascript
// BAD: $group before $match — processes ALL documents before filtering
db.orders.aggregate([
    { $group: { _id: "$region", total: { $sum: "$amount" } } },
    { $match: { total: { $gt: 10000 } } }  // Too late — already grouped everything
])
// MongoDB must: read all 1M orders → group all 1M → then filter
// Cannot use index for $match (applied to grouped output, not original docs)

// GOOD: $match before $group — processes only matching documents
db.orders.aggregate([
    { $match: { status: "COMPLETED", createdAt: { $gte: ISODate("2024-01-01") } } },
    { $group: { _id: "$region", total: { $sum: "$amount" } } }
])
// MongoDB: index scan on (status, createdAt) → 45K docs → group 45K docs
// 95% reduction in work before the expensive $group stage

// The index utilization rule:
// $match at the PIPELINE START can use collection indexes
// $match AFTER any other stage: applied to in-memory documents (no index)

// $sort with index (must be at the start, before $group):
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $sort: { createdAt: -1 } },    // Can use index on createdAt
    { $limit: 100 },                 // "Top K" optimization: sort + limit together
    { $group: { _id: "$region", count: { $sum: 1 } } }
])
// MongoDB optimizer: recognizes sort+limit → uses index to serve top 100 without
// sorting all matching documents in memory

// Verify index use in aggregation:
db.orders.explain("executionStats").aggregate([
    { $match: { status: "COMPLETED" } },
    { $group: { _id: "$region", total: { $sum: "$amount" } } }
])
// Look for in executionStats:
// "stage": "IXSCAN" (index used by $match) ← good
// "stage": "COLLSCAN" (no index) ← needs index
// "totalDocsExamined": N — should match docsReturned if index is selective
```

## Section 2: `$match`

**Q3. How does `$match` work in the pipeline, and how does it interact with indexes?**
A: `$match` filters documents using the same query syntax as `find()`. When placed first in the pipeline, it delegates filtering to the query planner, which can use collection indexes. When placed after a transformation stage, it operates on in-memory documents with no index benefit:

```javascript
// $match syntax — identical to find() query predicates:
db.orders.aggregate([
    {
        $match: {
            // Equality:
            status: "COMPLETED",

            // Range:
            amount: { $gte: 100, $lte: 1000 },

            // Date range:
            createdAt: {
                $gte: ISODate("2024-01-01T00:00:00Z"),
                $lt:  ISODate("2024-04-01T00:00:00Z")
            },

            // Array contains element:
            tags: "express-shipping",

            // Nested field (dot notation):
            "shipping.address.country": "US",

            // Multiple conditions:
            $and: [
                { amount: { $gt: 0 } },
                { "items.0": { $exists: true } }   // Has at least one item
            ],

            // Regular expression:
            "customer.name": { $regex: /^Alice/, $options: "i" },

            // In list:
            region: { $in: ["EU", "US", "APAC"] },

            // Not in list:
            status: { $nin: ["CANCELLED", "REFUNDED"] }
        }
    }
])
```

```javascript
// $match after $group — filtering on computed fields:
// Cannot use index (operating on pipeline output, not collection docs)
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },     // Stage 1: index used
    {
        $group: {
            _id: "$userId",
            totalSpent: { $sum: "$amount" },
            orderCount: { $sum: 1 }
        }
    },
    {
        $match: {                             // Stage 3: no index (on computed fields)
            totalSpent: { $gt: 500 },
            orderCount: { $gte: 3 }
        }
    }
])
// The second $match is fine here — it filters GROUP output
// Just don't expect index use for it
// This pattern is common: filter raw docs first, aggregate, then filter aggregates

// $match with text search (requires text index):
db.articles.aggregate([
    { $match: { $text: { $search: "mongodb aggregation" } } },
    { $sort: { score: { $meta: "textScore" } } },
    { $project: { title: 1, score: { $meta: "textScore" } } },
    { $limit: 10 }
])
// Text search in $match: can use text index
// $meta: "textScore" in $sort: sort by relevance
// Must be in first $match stage for text index to work
```

## Section 3: `$group`

**Q4. How does `$group` work — what are the accumulator operators and what does `_id: null` do?**
A: `$group` collapses multiple documents into one document per unique value of the `_id` expression. Accumulator operators (`$sum`, `$avg`, `$min`, `$max`, `$first`, `$last`, `$push`, `$addToSet`, `$count`) compute values across all documents in each group. Setting `_id: null` groups all documents into a single group — a global aggregate:

```javascript
// $group structure:
{
    $group: {
        _id: <expression>,         // The grouping key — what to group BY
        <field>: { <accumulator>: <expression> }  // What to compute for each group
    }
}

// The _id field is REQUIRED — defines the grouping dimension
// _id can be:

// Single field:
{ $group: { _id: "$status" } }
// Groups by: COMPLETED, PENDING, CANCELLED (one doc per distinct status)

// Multiple fields (compound grouping key):
{ $group: { _id: { region: "$region", year: { $year: "$createdAt" } } } }
// Groups by: {region: "EU", year: 2024}, {region: "US", year: 2024}, etc.

// Expression:
{ $group: { _id: { $dateToString: { format: "%Y-%m", date: "$createdAt" } } } }
// Groups by: "2024-01", "2024-02", etc. (monthly grouping)

// null — global aggregate (all docs in one group):
{ $group: { _id: null, grandTotal: { $sum: "$amount" } } }
// Returns ONE document: { _id: null, grandTotal: 4892341.50 }
```

```javascript
// All accumulator operators with examples:
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    {
        $group: {
            _id: "$region",

            // Counting and summing:
            orderCount:  { $sum: 1 },           // Count documents in group
            totalAmount: { $sum: "$amount" },    // Sum of amount field
            itemCount:   { $sum: { $size: "$items" } },  // Sum of array sizes

            // Statistical:
            avgOrder:    { $avg: "$amount" },
            minOrder:    { $min: "$amount" },
            maxOrder:    { $max: "$amount" },
            stdDev:      { $stdDevPop: "$amount" },  // Population std dev

            // First/last (depends on document order — use with $sort first):
            firstOrder:  { $first: "$createdAt" },  // First document's createdAt
            lastOrder:   { $last: "$createdAt" },   // Last document's createdAt

            // Array accumulators:
            allUserIds:    { $push: "$userId" },     // Array of all userIds (duplicates kept)
            uniqueUserIds: { $addToSet: "$userId" }, // Array of distinct userIds

            // $count accumulator (MongoDB 5.0+):
            docCount:    { $count: {} }              // Equivalent to { $sum: 1 }
        }
    },
    {
        $project: {
            _id: 1,
            orderCount: 1,
            totalAmount: { $round: ["$totalAmount", 2] },
            avgOrder:    { $round: ["$avgOrder", 2] },
            uniqueCustomers: { $size: "$uniqueUserIds" }
        }
    }
])
```

```javascript
// Common $group patterns:

// 1. Count distinct values (cardinality):
db.orders.aggregate([
    { $group: { _id: "$userId" } },
    { $count: "distinctUsers" }
])
// Equivalent to: SELECT COUNT(DISTINCT userId) FROM orders

// 2. Group with conditional accumulation:
db.orders.aggregate([
    {
        $group: {
            _id: "$region",
            completedCount: {
                $sum: { $cond: [{ $eq: ["$status", "COMPLETED"] }, 1, 0] }
            },
            cancelledCount: {
                $sum: { $cond: [{ $eq: ["$status", "CANCELLED"] }, 1, 0] }
            },
            totalCount: { $sum: 1 }
        }
    }
])
// Count by status within each region group — single pass over all documents

// 3. Collect unique tags across all documents:
db.articles.aggregate([
    { $unwind: "$tags" },
    { $group: { _id: null, allTags: { $addToSet: "$tags" } } }
])
// allTags: ["mongodb", "nosql", "database", ...]
```

## Section 4: `$project`

**Q5. What does `$project` do and how is it different from `find()` projection?**
A: `$project` reshapes documents in the pipeline — it can include, exclude, rename, and compute new fields. Unlike `find()` projection which only includes or excludes existing fields, `$project` can compute entirely new fields using expressions, transform values, and restructure the document shape:

```javascript
// $project syntax:
{
    $project: {
        fieldName: 1,         // Include field
        otherField: 0,        // Exclude field (cannot mix 1 and 0 except _id)
        _id: 0,               // Explicitly exclude _id (only field you can exclude alongside includes)
        newName: "$oldName",  // Rename (reference with $)
        computed: <expression> // Compute new field
    }
}

// Example: reshape order document for API response
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    {
        $project: {
            _id: 0,
            orderId: "$_id",                     // Rename _id to orderId
            customerName: "$customer.name",       // Promote nested field
            status: 1,
            totalAmount: "$amount",               // Rename amount

            // Computed fields:
            amountWithTax: { $multiply: ["$amount", 1.08] },  // 8% tax
            isHighValue:   { $gt: ["$amount", 500] },         // Boolean flag
            itemCount:     { $size: "$items" },                // Array length
            year:          { $year: "$createdAt" },            // Date part extraction
            displayDate:   { $dateToString: {
                format: "%Y-%m-%d", date: "$createdAt"
            }},

            // Conditional field:
            priority: {
                $switch: {
                    branches: [
                        { case: { $gt: ["$amount", 1000] }, then: "HIGH" },
                        { case: { $gt: ["$amount", 500] },  then: "MEDIUM" }
                    ],
                    default: "LOW"
                }
            },

            // String operations:
            emailDomain: {
                $arrayElemAt: [
                    { $split: ["$customer.email", "@"] },
                    1
                ]
            }
        }
    }
])
```

```javascript
// $project with arrays:
db.orders.aggregate([
    {
        $project: {
            _id: 1,
            // Slice an array:
            firstThreeItems: { $slice: ["$items", 3] },
            // Get element at index:
            firstItem: { $arrayElemAt: ["$items", 0] },
            lastItem:  { $arrayElemAt: ["$items", -1] },
            // Filter an array to matching elements:
            expensiveItems: {
                $filter: {
                    input: "$items",
                    as: "item",
                    cond: { $gt: ["$$item.price", 100] }
                }
            },
            // Map over array to transform each element:
            itemNames: {
                $map: {
                    input: "$items",
                    as: "item",
                    in: "$$item.name"
                }
            },
            // Reduce array to a single value:
            itemsTotal: {
                $reduce: {
                    input: "$items",
                    initialValue: 0,
                    in: { $add: ["$$value", "$$this.price"] }
                }
            }
        }
    }
])

// $addFields — alternative to $project for adding fields without dropping others:
db.orders.aggregate([
    {
        $addFields: {
            amountWithTax:    { $multiply: ["$amount", 1.08] },
            processingDayOfWeek: { $dayOfWeek: "$createdAt" }
            // All other existing fields are KEPT (unlike $project which drops them)
        }
    }
])
// $addFields: adds new fields, keeps ALL existing fields
// $project: must explicitly include every field you want to keep
// Use $addFields when you only need to ADD to existing documents
// Use $project when you need to reshape or reduce the document
```

## Section 5: `$lookup`

**Q6. How does `$lookup` implement joins in MongoDB — what are the basic and pipeline forms?**
A: `$lookup` performs a left outer join between the current pipeline's documents and another collection. It comes in two forms: the simple equality form (join on field equality) and the pipeline form (join with arbitrary conditions, multiple fields, or additional filtering and transformation of the joined documents):

```javascript
// Form 1: Simple equality join
{
    $lookup: {
        from: "collection_name",   // The collection to join (in same database)
        localField: "field",       // Field in the current pipeline documents
        foreignField: "field",     // Field in the "from" collection
        as: "resultArrayName"      // Output field name (always an array)
    }
}

// Example: add user details to orders
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    {
        $lookup: {
            from: "users",
            localField: "userId",
            foreignField: "_id",
            as: "userDetails"    // Adds array field: [{_id, name, email, ...}]
        }
    },
    {
        $unwind: {
            path: "$userDetails",
            preserveNullAndEmpty: true  // Keep orders with no matching user
        }
    },
    {
        $project: {
            orderId: "$_id",
            amount: 1,
            "userDetails.name": 1,
            "userDetails.email": 1
        }
    }
])

// $lookup always returns an ARRAY in the "as" field:
// - Empty array [] if no matching documents found (left outer join)
// - Array with one element [{...}] if one match
// - Array with multiple elements [{...}, {...}] if many matches
// Must $unwind or use $arrayElemAt to access fields from the joined documents
```

```javascript
// Form 2: Pipeline join (MongoDB 3.6+)
// More powerful: multiple join conditions, filtering, transforming joined docs
{
    $lookup: {
        from: "collection_name",
        let: { localVar: "$localField" },   // Variables from current doc
        pipeline: [
            // Uses $$localVar (double $) to reference variables
            { $match: { $expr: { $eq: ["$foreignField", "$$localVar"] } } },
            { $project: { sensitiveData: 0 } },  // Exclude fields from joined docs
            { $sort: { createdAt: -1 } },
            { $limit: 5 }
        ],
        as: "resultArrayName"
    }
}

// Example: join with multiple conditions + filter + limit
db.orders.aggregate([
    {
        $lookup: {
            from: "products",
            let: {
                orderRegion:   "$region",
                orderCurrency: "$currency"
            },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                { $eq: ["$availableRegion", "$$orderRegion"] },
                                { $eq: ["$currency",        "$$orderCurrency"] },
                                { $eq: ["$isActive",        true] }
                            ]
                        }
                    }
                },
                { $project: { name: 1, price: 1, sku: 1 } },
                { $sort: { price: 1 } },
                { $limit: 10 }
            ],
            as: "availableProducts"
        }
    }
])

// Nested $lookup — join within a joined collection:
db.orders.aggregate([
    {
        $lookup: {
            from: "users",
            localField: "userId",
            foreignField: "_id",
            as: "user"
        }
    },
    { $unwind: "$user" },
    {
        $lookup: {
            from: "companies",                  // Second level join
            localField: "user.companyId",       // Via field from first join
            foreignField: "_id",
            as: "user.company"
        }
    }
])
// Produces: order document with user.company populated inside user
```

```javascript
// Performance considerations for $lookup:

// 1. $lookup does NOT use indexes automatically in all cases
//    The "foreignField" should be indexed:
db.users.createIndex({ _id: 1 });      // Already indexed (PK)
db.products.createIndex({ sku: 1 });   // Index on the join field

// Verify lookup uses index:
db.orders.explain("executionStats").aggregate([
    { $lookup: {
        from: "users",
        localField: "userId",
        foreignField: "_id",    // _id is indexed → lookup uses index
        as: "user"
    }}
])
// Look for "IXSCAN" on the users collection in the explain output

// 2. $match early to reduce documents entering $lookup:
db.orders.aggregate([
    { $match: { status: "COMPLETED", createdAt: { $gte: last30days } } },
    { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } }
])
// If 1M orders but only 10K completed recently: $lookup runs 10K times, not 1M times

// 3. $lookup creates large intermediate documents:
// Order (1KB) × 10K users joined = 10MB intermediate documents
// allowDiskUse: true if this exceeds 100MB

// 4. Concise $lookup (MongoDB 5.0+) — when localField and foreignField are same name:
// Equivalent to join ON orders.userId = users.userId:
db.orders.aggregate([
    {
        $lookup: {
            from: "users",
            localField: "userId",
            foreignField: "userId",
            as: "user"
        }
    }
])
```

## Section 6: `$unwind`

**Q7. What does `$unwind` do — why is it essential for working with arrays, and what are its edge cases?**
A: `$unwind` deconstructs an array field, outputting one document per array element. It is the bridge between array-structured MongoDB documents and operations that need to process individual array elements (like grouping by array element values or filtering within arrays):

```javascript
// Without $unwind — working with the array as a whole:
// Document: { _id: 1, tags: ["mongodb", "nosql", "database"] }
// $group by tag: impossible without $unwind (can't group by individual elements)

// $unwind: creates one document per array element:
// Input:  { _id: 1, name: "Article", tags: ["mongodb", "nosql", "database"] }
// Output:
// { _id: 1, name: "Article", tags: "mongodb" }
// { _id: 1, name: "Article", tags: "nosql" }
// { _id: 1, name: "Article", tags: "database" }
// ↑ Same _id appears 3 times with different tags value

db.articles.aggregate([
    { $unwind: "$tags" },
    {
        $group: {
            _id: "$tags",
            articleCount: { $sum: 1 },
            articles: { $push: "$title" }
        }
    },
    { $sort: { articleCount: -1 } },
    { $limit: 10 }
])
// Top 10 tags by article count
// This is impossible with find() alone — requires array expansion first
```

```javascript
// $unwind options — handling edge cases:
{
    $unwind: {
        path: "$items",              // The array field to unwind
        includeArrayIndex: "itemIdx", // Add field with array index (0, 1, 2...)
        preserveNullAndEmpty: true   // Keep documents where array is null or []
    }
}

// Edge case 1: null or missing array field:
// Document: { _id: 2, name: "Article", tags: null }
// Without preserveNullAndEmpty: document is DROPPED (lost from pipeline)
// With preserveNullAndEmpty: document kept, tags = null in output

// Edge case 2: empty array:
// Document: { _id: 3, name: "Article", tags: [] }
// Without preserveNullAndEmpty: document DROPPED (no elements to unwind)
// With preserveNullAndEmpty: document kept, tags field absent

// Edge case 3: single-element array:
// Document: { _id: 4, name: "Article", tags: ["mongodb"] }
// Output: { _id: 4, name: "Article", tags: "mongodb" }
// ← Produces ONE document (not an array — the single element is unwound)

// includeArrayIndex example:
db.orders.aggregate([
    {
        $unwind: {
            path: "$items",
            includeArrayIndex: "itemPosition"
        }
    },
    {
        $project: {
            orderId: "$_id",
            itemPosition: 1,       // 0, 1, 2... (array index)
            "items.name": 1,
            "items.price": 1
        }
    }
])
// Output includes itemPosition: 0 for first item, 1 for second, etc.
// Useful when position matters (e.g., first item is the "primary" product)
```

```javascript
// $unwind + $group — the "unwind then regroup" pattern:
// Use case: filter an array to keep only matching elements,
//           then rebuild the array

db.orders.aggregate([
    // 1. Unwind the items array:
    { $unwind: "$items" },

    // 2. Filter to keep only items above $50:
    { $match: { "items.price": { $gt: 50 } } },

    // 3. Regroup by order to rebuild the filtered array:
    {
        $group: {
            _id: "$_id",                            // Regroup by original order _id
            orderTotal: { $first: "$totalAmount" }, // Restore scalar fields
            status:     { $first: "$status" },
            filteredItems: { $push: "$items" }      // Rebuild array with only matching items
        }
    }
])
// Result: orders with only their high-value items

// Alternative without $unwind (MongoDB 3.2+) using $filter:
db.orders.aggregate([
    {
        $project: {
            totalAmount: 1,
            status: 1,
            filteredItems: {
                $filter: {
                    input: "$items",
                    as: "item",
                    cond: { $gt: ["$$item.price", 50] }
                }
            }
        }
    }
])
// $filter is cleaner when you just need to filter arrays
// $unwind+$group needed when: aggregating WITHIN items, complex transforms
```

## Section 7: `$sort` and `$limit`

**Q8. How do `$sort` and `$limit` interact with indexes and memory limits in the pipeline?**
A: `$sort` and `$limit` have special optimizer interactions. When `$sort` appears near the beginning of the pipeline, the query optimizer can use an index to provide already-sorted documents, avoiding an in-memory sort. When `$sort` is immediately followed by `$limit`, a further optimization applies — the sort only needs to maintain the top-K elements rather than sorting all documents:

```javascript
// $sort syntax:
{ $sort: { field1: 1, field2: -1, field3: 1 } }
// 1: ascending, -1: descending
// Multiple fields: first sort by field1, ties broken by field2, then field3

// Basic examples:
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $sort: { amount: -1, createdAt: -1 } },  // Highest amount first, then newest
    { $limit: 100 }
])

// Special sort values for text and geospatial:
{ $sort: { score: { $meta: "textScore" } } }    // Sort by text relevance
{ $sort: { distance: { $meta: "geoNearDistance" } } }  // Sort by proximity
```

```javascript
// Index utilization by $sort placement:

// GOOD: $sort at the start (or after $match-only stages) uses index:
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },         // Stage 1: uses index
    { $sort:  { createdAt: -1 } }                // Stage 2: uses index on createdAt
])
// Requires: index on { status: 1, createdAt: -1 } or { createdAt: -1 }
// Plan: IXSCAN provides pre-sorted results → no in-memory sort needed

// BAD: $sort after $group — operates on in-memory grouped results:
db.orders.aggregate([
    { $group: { _id: "$region", total: { $sum: "$amount" } } },
    { $sort:  { total: -1 } }  // Cannot use collection index (sorting computed values)
])
// This is FINE and common — just be aware it's an in-memory sort
// The number of documents here is the number of distinct regions (small)

// Memory limits:
// $sort in memory: limited to 100MB by default
// For large sorts: use allowDiskUse: true
db.orders.aggregate(
    [
        { $sort: { amount: -1 } }  // Sorting 10M documents → exceeds 100MB
    ],
    { allowDiskUse: true }         // Writes temp files for sort
)
// allowDiskUse: dramatically slower (disk I/O) but handles any size
// Better solution: pre-filter to reduce sort input, or sort in application
```

```javascript
// The sort + limit optimization ("Top-K" pattern):
// MongoDB optimizes: $sort followed immediately by $limit
// Instead of sorting ALL documents then taking first K:
// Maintains a priority queue of K elements → only K comparisons per document

db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $sort: { amount: -1 } },    // Would sort all matches...
    { $limit: 10 }                // ...but optimizer: only keeps top 10 during sort
])
// Memory: O(K) not O(N) — regardless of how many match $match
// Equivalent to SQL: SELECT ... ORDER BY amount DESC LIMIT 10

// Anti-pattern: $limit before $sort (different semantics):
db.orders.aggregate([
    { $limit: 10 },               // Takes first 10 documents (arbitrary order)
    { $sort: { amount: -1 } }     // Sorts only those 10
])
// This finds the "largest amount among the first 10 documents" — usually wrong
// Unless you want a random sample sorted

// $skip for pagination (with performance warning):
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $sort:  { createdAt: -1, _id: -1 } },
    { $skip:  9990 },   // Page 1000 of 10-per-page results
    { $limit: 10 }
])
// $skip 9990: must scan and discard 9990 documents before returning 10
// Gets progressively slower with higher page numbers
// Better: cursor-based pagination using $match on the last seen _id/createdAt
```

## Section 8: `$facet`

**Q9. What is `$facet` and when is it the right tool — how does it enable single-pass multi-dimensional analysis?**
A: `$facet` processes incoming documents through multiple independent sub-pipelines simultaneously, producing a single output document containing an array of results for each sub-pipeline. It solves the problem of needing multiple different aggregations over the same filtered dataset without running multiple queries:

```javascript
// Without $facet — three separate queries for a search results page:
// Query 1: paginated results
// Query 2: category counts for facet sidebar
// Query 3: price range summary
// Three round trips to the database, three separate scans

// With $facet — ONE query, ONE scan, three results:
db.products.aggregate([
    // First: filter to the search results (shared by all facets):
    {
        $match: {
            $text: { $search: "wireless headphones" },
            inStock: true
        }
    },

    // $facet: run multiple sub-pipelines on the matched documents simultaneously:
    {
        $facet: {
            // Sub-pipeline 1: paginated product results
            "searchResults": [
                { $sort: { score: { $meta: "textScore" }, popularity: -1 } },
                { $skip: 0 },
                { $limit: 20 },
                {
                    $project: {
                        name: 1, price: 1, brand: 1,
                        rating: 1, imageUrl: 1,
                        score: { $meta: "textScore" }
                    }
                }
            ],

            // Sub-pipeline 2: brand breakdown for sidebar filter
            "brandFacets": [
                { $group: { _id: "$brand", count: { $sum: 1 } } },
                { $sort: { count: -1 } },
                { $limit: 15 }
            ],

            // Sub-pipeline 3: price range distribution
            "priceRanges": [
                {
                    $bucket: {
                        groupBy: "$price",
                        boundaries: [0, 25, 50, 100, 200, 500],
                        default: "500+",
                        output: { count: { $sum: 1 } }
                    }
                }
            ],

            // Sub-pipeline 4: total result count (for pagination UI)
            "totalCount": [
                { $count: "total" }
            ],

            // Sub-pipeline 5: average rating summary
            "ratingSummary": [
                {
                    $group: {
                        _id: null,
                        avgRating:   { $avg: "$rating" },
                        minPrice:    { $min: "$price" },
                        maxPrice:    { $max: "$price" }
                    }
                }
            ]
        }
    }
])
```

```javascript
// $facet output structure:
// {
//   "searchResults": [ {product1}, {product2}, ... (20 products) ],
//   "brandFacets":   [ {_id: "Sony", count: 45}, {_id: "Bose", count: 32}, ... ],
//   "priceRanges":   [ {_id: 0, count: 12}, {_id: 25, count: 34}, ... ],
//   "totalCount":    [ {total: 342} ],          ← Always an array, even for counts
//   "ratingSummary": [ {_id: null, avgRating: 4.2, minPrice: 15, maxPrice: 450} ]
// }

// Accessing totalCount: result[0].totalCount[0]?.total ?? 0

// Important $facet constraints:
// 1. Sub-pipelines SHARE the documents from preceding stages
//    (all sub-pipelines start from the same set of matched documents)
// 2. $facet sub-pipelines are INDEPENDENT (one pipeline's output doesn't affect another)
// 3. $facet sub-pipelines CANNOT use $facet, $out, $merge, or $geoNear
// 4. The input documents to $facet must fit in 100MB
//    (use $match to reduce BEFORE $facet, use allowDiskUse if needed)
// 5. $facet always produces exactly ONE output document containing all sub-pipeline results

// When NOT to use $facet:
// - Sub-pipelines need different filtered datasets (use separate queries)
// - One sub-pipeline processes enormous data (100MB limit per sub-pipeline)
// - Sub-pipelines are independent queries with no shared filter (no benefit)
```

## Section 9: `$bucket` and `$bucketAuto`

**Q10. What is `$bucket` and how does it differ from `$bucketAuto` — when do you use each?**
A: `$bucket` groups documents into user-defined ranges (bins) based on a field value. `$bucketAuto` automatically determines the bucket boundaries to distribute documents as evenly as possible across a specified number of buckets. The choice depends on whether you need meaningful fixed ranges or automatic distribution:

```javascript
// $bucket — manually defined boundaries:
{
    $bucket: {
        groupBy: "$price",         // The field to bucket on (must be sortable)
        boundaries: [0, 25, 50, 100, 200, 500, 1000],
        // Creates buckets:
        // [0, 25)   → products $0 - $24.99
        // [25, 50)  → products $25 - $49.99
        // [50, 100) → products $50 - $99.99
        // [100, 200)
        // [200, 500)
        // [500, 1000)

        default: "1000+",          // Bucket for values outside ALL boundaries
        // Documents with price >= 1000 OR price < 0 go here
        // If no default: documents outside boundaries cause an error

        output: {
            count:    { $sum: 1 },
            products: { $push: "$name" },       // Array of product names in bucket
            avgPrice: { $avg: "$price" },
            minPrice: { $min: "$price" },
            maxPrice: { $max: "$price" }
        }
    }
}

// Example output:
// { "_id": 0,      "count": 12, "avgPrice": 18.5,  "minPrice": 5, "maxPrice": 24 }
// { "_id": 25,     "count": 34, "avgPrice": 37.2,  ... }
// { "_id": 50,     "count": 28, "avgPrice": 74.8,  ... }
// { "_id": 100,    "count": 45, "avgPrice": 148.3, ... }
// { "_id": 200,    "count": 19, "avgPrice": 342.1, ... }
// { "_id": 500,    "count": 8,  "avgPrice": 789.4, ... }
// { "_id": "1000+","count": 3,  "avgPrice": 1499.0,... }
// _id = the lower boundary of the bucket
```

```javascript
// $bucketAuto — automatically determined boundaries:
{
    $bucketAuto: {
        groupBy: "$price",
        buckets: 5,    // How many buckets to create
        // MongoDB will find boundaries that create 5 approximately equal-sized groups
        // Boundaries are determined by the data distribution

        output: {
            count:    { $sum: 1 },
            avgPrice: { $avg: "$price" }
        },

        granularity: "POWERSOF2"
        // Optional: force boundaries to be "round" numbers
        // Options: "R5", "R10", "R20", "R40", "R80", "1-2-5",
        //          "E6", "E12", "E24", "E48", "E96", "E192", "POWERSOF2"
        // POWERSOF2: boundaries at 1, 2, 4, 8, 16, 32, 64, 128, ...
        // 1-2-5: boundaries at 1, 2, 5, 10, 20, 50, 100, ...
        // Use granularity for human-readable price ranges
    }
}

// Example output from $bucketAuto with 5 buckets on [0, 1000] price range:
// { "_id": { "min": 0, "max": 45.99 },    "count": 95,  "avgPrice": 28.3 }
// { "_id": { "min": 46, "max": 124.99 },  "count": 103, "avgPrice": 87.1 }
// { "_id": { "min": 125, "max": 299.99 }, "count": 98,  "avgPrice": 212.4 }
// { "_id": { "min": 300, "max": 599.99 }, "count": 97,  "avgPrice": 445.7 }
// { "_id": { "min": 600, "max": 999.99 }, "count": 107, "avgPrice": 742.1 }
// Each bucket tries to have ~100 documents (500 total / 5 buckets)
// _id is an object with min/max boundaries (not just the lower bound like $bucket)
```

```javascript
// Combining $bucket with $facet for a complete analytics pipeline:
db.products.aggregate([
    { $match: { category: "electronics", inStock: true } },
    {
        $facet: {
            // Price distribution for filtering UI:
            "byPrice": [
                {
                    $bucket: {
                        groupBy: "$price",
                        boundaries: [0, 50, 100, 250, 500, 1000],
                        default: "1000+",
                        output: { count: { $sum: 1 }, avgRating: { $avg: "$rating" } }
                    }
                }
            ],

            // Automatic rating distribution:
            "byRating": [
                {
                    $bucketAuto: {
                        groupBy: "$rating",
                        buckets: 5,
                        output: { count: { $sum: 1 } }
                    }
                }
            ],

            // Category breakdown:
            "bySubcategory": [
                { $group: { _id: "$subcategory", count: { $sum: 1 } } },
                { $sort: { count: -1 } }
            ]
        }
    }
])

// $bucket requirements:
// 1. boundaries: must be an array in ascending order, at least 2 elements
// 2. boundaries: all values must be of the same BSON type
// 3. groupBy field: values must be comparable to boundaries type
// 4. Documents where groupBy field is missing or wrong type:
//    → Go to "default" bucket (if defined) or error (if not defined)
```

## Section 10: Combining Stages — Complete Pipeline Patterns

**Q11. How do you build a complete analytics pipeline combining multiple stages effectively?**
A: Real-world pipelines chain multiple stages in a precise order. The pattern is always: filter first (reduce volume), transform next (reshape and enrich), aggregate last (compute summaries), then present (sort, limit, and shape the final output):

```javascript
// Complete e-commerce analytics pipeline:
// "Monthly revenue by region, with customer lifetime value, for completed orders in 2024"

db.orders.aggregate([
    // === STAGE 1: Reduce volume early with index-friendly $match ===
    {
        $match: {
            status: "COMPLETED",
            createdAt: {
                $gte: ISODate("2024-01-01T00:00:00Z"),
                $lt:  ISODate("2025-01-01T00:00:00Z")
            }
        }
    },
    // Index needed: { status: 1, createdAt: 1 }
    // Reduces: 10M orders → 450K completed orders in 2024

    // === STAGE 2: Join user data ===
    {
        $lookup: {
            from: "users",
            localField: "userId",
            foreignField: "_id",
            as: "user",
            pipeline: [
                { $project: { name: 1, region: 1, tier: 1, _id: 0 } }  // Only needed fields
            ]
        }
    },
    { $unwind: { path: "$user", preserveNullAndEmpty: false } },
    // Drops orders with no matching user (inner join behavior)

    // === STAGE 3: Add computed fields ===
    {
        $addFields: {
            month:    { $dateToString: { format: "%Y-%m", date: "$createdAt" } },
            quarter:  {
                $switch: {
                    branches: [
                        { case: { $in: [{ $month: "$createdAt" }, [1, 2, 3]] },  then: "Q1" },
                        { case: { $in: [{ $month: "$createdAt" }, [4, 5, 6]] },  then: "Q2" },
                        { case: { $in: [{ $month: "$createdAt" }, [7, 8, 9]] },  then: "Q3" },
                        { case: { $in: [{ $month: "$createdAt" }, [10, 11, 12]]}, then: "Q4" }
                    ],
                    default: "Unknown"
                }
            },
            amountUSD: {
                $switch: {
                    branches: [
                        { case: { $eq: ["$currency", "EUR"] }, then: { $multiply: ["$amount", 1.08] } },
                        { case: { $eq: ["$currency", "GBP"] }, then: { $multiply: ["$amount", 1.27] } }
                    ],
                    default: "$amount"   // Already USD
                }
            }
        }
    },

    // === STAGE 4: Group by region and month ===
    {
        $group: {
            _id: {
                region:  "$user.region",
                month:   "$month",
                quarter: "$quarter"
            },
            totalRevenue:   { $sum: "$amountUSD" },
            orderCount:     { $sum: 1 },
            avgOrderValue:  { $avg: "$amountUSD" },
            uniqueCustomers:{ $addToSet: "$userId" },
            premiumRevenue: {
                $sum: {
                    $cond: [{ $eq: ["$user.tier", "premium"] }, "$amountUSD", 0]
                }
            }
        }
    },

    // === STAGE 5: Compute derived group metrics ===
    {
        $addFields: {
            uniqueCustomerCount: { $size: "$uniqueCustomers" },
            premiumPct: {
                $round: [
                    { $multiply: [
                        { $divide: ["$premiumRevenue", { $max: ["$totalRevenue", 0.01] }] },
                        100
                    ]},
                    1
                ]
            }
        }
    },
    { $project: { uniqueCustomers: 0 } },  // Remove the large array we used for computation

    // === STAGE 6: Sort and limit for presentation ===
    { $sort: { "_id.region": 1, "_id.month": 1 } },

    // === STAGE 7: Reshape final output ===
    {
        $project: {
            _id: 0,
            region:              "$_id.region",
            month:               "$_id.month",
            quarter:             "$_id.quarter",
            totalRevenue:        { $round: ["$totalRevenue", 2] },
            orderCount:          1,
            avgOrderValue:       { $round: ["$avgOrderValue", 2] },
            uniqueCustomers:     "$uniqueCustomerCount",
            premiumRevenueShare: { $concat: [{ $toString: "$premiumPct" }, "%"] }
        }
    }
], { allowDiskUse: true, comment: "monthly-revenue-2024" })
```

```javascript
// Search + facets + pagination in one pipeline:
// The pattern used by e-commerce search pages

const searchQuery = "wireless noise cancelling";
const selectedBrand = "Sony";
const page = 2;
const pageSize = 20;

db.products.aggregate([
    // 1. Full-text search + pre-filters:
    {
        $match: {
            $text: { $search: searchQuery },
            inStock: true,
            ...(selectedBrand ? { brand: selectedBrand } : {})
        }
    },

    // 2. Add text relevance score:
    {
        $addFields: {
            searchScore: { $meta: "textScore" }
        }
    },

    // 3. $facet for all sidebar data + results in one pass:
    {
        $facet: {
            // Paginated results:
            "results": [
                { $sort: { searchScore: -1, popularity: -1 } },
                { $skip: (page - 1) * pageSize },
                { $limit: pageSize },
                {
                    $project: {
                        name: 1, price: 1, brand: 1, rating: 1,
                        imageUrl: 1, searchScore: 1
                    }
                }
            ],

            // Total count for pagination:
            "pagination": [
                { $count: "total" }
            ],

            // Brand facets (not filtered by brand — shows all brands for refinement):
            "brandBreakdown": [
                { $group: { _id: "$brand", count: { $sum: 1 } } },
                { $sort: { count: -1 } }
            ],

            // Price distribution:
            "priceHistogram": [
                {
                    $bucketAuto: {
                        groupBy: "$price",
                        buckets: 8,
                        granularity: "1-2-5",
                        output: { count: { $sum: 1 } }
                    }
                }
            ],

            // Average rating:
            "aggregateSummary": [
                {
                    $group: {
                        _id: null,
                        avgRating: { $avg: "$rating" },
                        minPrice:  { $min: "$price" },
                        maxPrice:  { $max: "$price" }
                    }
                }
            ]
        }
    }
])
```

## Section 11: Performance and Optimization

**Q12. How do you diagnose and optimize a slow aggregation pipeline?**
A: Pipeline optimization follows a systematic process: examine the explain plan, identify the slowest stage, and apply targeted fixes. The most common problems are COLLSCAN at the start (no index for `$match`), large document sets entering expensive stages, and memory-spilling sorts:

```javascript
// Step 1: Get the explain plan:
db.orders.explain("executionStats").aggregate([
    { $match: { status: "COMPLETED", region: "EU" } },
    { $group: { _id: "$userId", total: { $sum: "$amount" } } }
])

// What to look for in explain output:
// 1. The first stage: is it IXSCAN or COLLSCAN?
//    "COLLSCAN" → missing index on $match fields → add index
//    "IXSCAN" with high "keysExamined" vs low "docsReturned" → index not selective

// 2. Stage-by-stage document counts:
//    Stage 1 ($match): nReturned: 45000 → Stage 2 ($group): nReturned: 1250
//    If Stage 1 returns most of the collection: $match is not selective
//    → Add more specific conditions, or use a compound index

// 3. "usedDisk": true → $sort or $group spilled to disk
//    → Increase available memory OR filter more aggressively before the stage
//    → break into smaller pipelines if possible

// Step 2: Check index utilization:
db.orders.getIndexes()
// Ensure the compound index covers all $match fields:
// { status: 1, region: 1 } → covers both fields in $match
// vs { status: 1 } only → partial coverage, region filtered in memory

// Create targeted indexes for common aggregation queries:
db.orders.createIndex(
    { status: 1, region: 1, createdAt: -1 },
    { name: "idx_agg_status_region_date" }
)
// Covers: $match on status + region, $sort on createdAt DESC
```

```javascript
// Common optimization patterns:

// Pattern 1: Filter early, join late
// BAD: $lookup on all 1M orders then filter
db.orders.aggregate([
    { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } },
    { $match: { "user.region": "EU", status: "COMPLETED" } }  // Too late!
])

// GOOD: filter first (before expensive $lookup):
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },     // Reduces 1M → 250K docs
    { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } },
    { $unwind: "$user" },
    { $match: { "user.region": "EU" } }      // Further filter after join
])
// Even better: if region is on the order document, put it in the first $match

// Pattern 2: Project to reduce document size before $lookup or $group
// Large documents make $lookup and $group more memory-intensive
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    // Reduce document size BEFORE expensive operations:
    {
        $project: {
            userId: 1,
            amount: 1,
            region: 1,
            createdAt: 1
            // Drop: large text fields, metadata arrays, etc.
        }
    },
    { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } }
])

// Pattern 3: Use $count instead of $group + $project for counting:
// BAD:
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $group: { _id: null, total: { $sum: 1 } } },
    { $project: { _id: 0, total: 1 } }
])

// GOOD — $count is a shorthand that the optimizer can better utilize:
db.orders.aggregate([
    { $match: { status: "COMPLETED" } },
    { $count: "total" }          // Single stage: { total: N }
])

// Pattern 4: Use $merge or $out for results you query repeatedly
db.orders.aggregate([
    { $match: { year: 2024 } },
    { $group: { _id: "$region", total: { $sum: "$amount" } } },
    {
        $merge: {
            into: "regional_revenue_cache",    // Write results to another collection
            on: "_id",                          // Merge key
            whenMatched: "replace",             // Replace existing docs
            whenNotMatched: "insert"            // Insert new docs
        }
    }
])
// regional_revenue_cache is now indexed and queryable — fast subsequent reads
// Schedule this pipeline to run nightly/hourly to keep cache fresh
```

## Section 12: Scenario-Based Questions

**Q13. "Design an aggregation pipeline to generate a user activity dashboard showing: last 30 days activity, top 5 categories purchased, spending trend by week, and whether they qualify for a loyalty upgrade."**
A:

```javascript
const userId = ObjectId("user-id-here");
const thirtyDaysAgo = new Date(Date.now() - 30 * 24 * 60 * 60 * 1000);

db.orders.aggregate([
    // === Filter: this user's completed orders in last 30 days ===
    {
        $match: {
            userId: userId,
            status: "COMPLETED",
            createdAt: { $gte: thirtyDaysAgo }
        }
    },

    // === Enrich: add week number for trend analysis ===
    {
        $addFields: {
            weekNumber: { $isoWeek: "$createdAt" },
            weekYear:   { $isoWeekYear: "$createdAt" },
            weekLabel: {
                $concat: [
                    { $toString: { $isoWeekYear: "$createdAt" } },
                    "-W",
                    { $toString: { $isoWeek: "$createdAt" } }
                ]
            }
        }
    },

    // === $facet: compute all dashboard metrics in one pass ===
    {
        $facet: {

            // Facet 1: overall 30-day summary
            "summary": [
                {
                    $group: {
                        _id: null,
                        totalSpent:   { $sum: "$amount" },
                        orderCount:   { $sum: 1 },
                        avgOrderValue:{ $avg: "$amount" },
                        firstOrder:   { $min: "$createdAt" },
                        lastOrder:    { $max: "$createdAt" }
                    }
                },
                {
                    $project: {
                        _id: 0,
                        totalSpent:    { $round: ["$totalSpent", 2] },
                        orderCount:    1,
                        avgOrderValue: { $round: ["$avgOrderValue", 2] },
                        activeDays: {
                            $dateDiff: {
                                startDate: "$firstOrder",
                                endDate:   "$lastOrder",
                                unit: "day"
                            }
                        },
                        qualifiesForGold: { $gte: ["$totalSpent", 500] },
                        qualifiesForPlat: { $gte: ["$totalSpent", 2000] }
                    }
                }
            ],

            // Facet 2: top 5 categories purchased
            "topCategories": [
                { $unwind: "$items" },
                {
                    $group: {
                        _id: "$items.category",
                        totalSpent:  { $sum: { $multiply: ["$items.price", "$items.qty"] } },
                        itemCount:   { $sum: "$items.qty" }
                    }
                },
                { $sort: { totalSpent: -1 } },
                { $limit: 5 },
                {
                    $project: {
                        _id: 0,
                        category:   "$_id",
                        totalSpent: { $round: ["$totalSpent", 2] },
                        itemCount:  1
                    }
                }
            ],

            // Facet 3: weekly spending trend
            "weeklyTrend": [
                {
                    $group: {
                        _id: "$weekLabel",
                        weekStart: { $min: "$createdAt" },
                        revenue:   { $sum: "$amount" },
                        orders:    { $sum: 1 }
                    }
                },
                { $sort: { "_id": 1 } },  // Chronological order
                {
                    $project: {
                        _id: 0,
                        week:    "$_id",
                        revenue: { $round: ["$revenue", 2] },
                        orders:  1
                    }
                }
            ],

            // Facet 4: recent order activity (last 5 orders)
            "recentOrders": [
                { $sort: { createdAt: -1 } },
                { $limit: 5 },
                {
                    $project: {
                        _id: 1,
                        amount: 1,
                        status: 1,
                        createdAt: 1,
                        itemCount: { $size: "$items" }
                    }
                }
            ]
        }
    },

    // === Reshape output into clean API response ===
    {
        $project: {
            summary:       { $arrayElemAt: ["$summary", 0] },
            topCategories: 1,
            weeklyTrend:   1,
            recentOrders:  1
        }
    }
])
```

**Q14. "You have a `sessions` collection with 500M documents. A pipeline is timing out even with `allowDiskUse: true`. How do you diagnose and fix it?"**
A: A timeout on 500M documents means the pipeline is either scanning too many documents or spilling too much data to disk. The fix is a combination of index strategy, pipeline restructuring, and potentially pre-aggregation:

```javascript
// Step 1: Get the explain plan to find the bottleneck:
db.sessions.explain("executionStats").aggregate(
    [ /* the slow pipeline */ ],
    { allowDiskUse: true }
)

// Look for:
// "nReturned": 500000000 after $match → $match is not filtering
// "totalDocsExamined": >> "totalKeysExamined" → index not covering the query
// "usedDisk": true → memory pressure (but also causes timeout)
// "executionTimeMillis" per stage → which stage is slowest

// Step 2: Ensure $match uses an index:
// If $match on { userId: X, eventType: "purchase", createdAt: > 30daysAgo }:
db.sessions.createIndex(
    { userId: 1, eventType: 1, createdAt: -1 },
    { background: true }   // Build without blocking writes
)
// Check plan after index: IXSCAN with low docsExamined

// Step 3: Restructure pipeline — filter as much as possible before any transformation:
// BAD — unwind before match:
db.sessions.aggregate([
    { $unwind: "$events" },              // 500M docs × avg 10 events = 5 BILLION
    { $match: { "events.type": "purchase" } }
])

// GOOD — filter on the parent document first:
db.sessions.aggregate([
    { $match: { userId: X, "events.type": "purchase", createdAt: { $gte: cutoff } } },
    { $unwind: "$events" },              // Only documents WITH purchase events
    { $match: { "events.type": "purchase" } }  // Filter unneeded events after unwind
])

// Step 4: For very large aggregations, use $out to run incrementally:
// Instead of one massive pipeline that times out:
// Run per day/week and accumulate results:

// Run yesterday's data:
db.sessions.aggregate([
    {
        $match: {
            createdAt: {
                $gte: ISODate("2024-03-14"),
                $lt:  ISODate("2024-03-15")
            }
        }
    },
    { $group: { _id: "$userId", dailyRevenue: { $sum: "$amount" } } },
    {
        $merge: {
            into: "user_revenue_daily",
            on: "_id",
            whenMatched: "replace",
            whenNotMatched: "insert"
        }
    }
], { allowDiskUse: true, maxTimeMS: 300000 })

// Query the pre-aggregated collection instead:
db.user_revenue_daily.aggregate([
    { $match: { date: { $gte: thirtyDaysAgo } } },
    { $group: { _id: "$userId", total: { $sum: "$dailyRevenue" } } },
    { $sort: { total: -1 } },
    { $limit: 100 }
])
// Pre-aggregated collection: ~30 × N_users documents (not 500M)
// Pipeline on pre-aggregated data: fast

// Step 5: Consider time-series collection (MongoDB 5.0+) for IoT/session data:
db.createCollection("sessions_ts", {
    timeseries: {
        timeField:   "createdAt",      // The timestamp field
        metaField:   "metadata",       // Identifier fields (userId, deviceId)
        granularity: "hours"           // Bucket size (seconds, minutes, hours)
    },
    expireAfterSeconds: 7776000        // Auto-delete after 90 days
})
// Time-series collections: optimized storage for time-ordered data
// Automatic bucketing by time reduces storage 50-80%
// Aggregations on timeField use automatic bucketing optimization
```

## Quick Reference Table

| Stage | Purpose | Key options | Performance rule |
|---|---|---|---|
| `$match` | Filter documents | Any query predicate, `$text`, `$expr` | Place FIRST — uses collection indexes; later stages = in-memory filter |
| `$group` | Aggregate by key | `$sum`, `$avg`, `$min`, `$max`, `$push`, `$addToSet`, `$first`, `$last`, `$count` | Expensive for large input; reduce with `$match` first; use `allowDiskUse` |
| `$project` | Reshape documents | Include/exclude, rename, compute expressions, `$filter`, `$map`, `$reduce` | Use `$addFields` when you only need to add without dropping existing fields |
| `$lookup` | Join another collection | Simple equality form or pipeline form with `let`/`pipeline` | Index the `foreignField`; `$match` before `$lookup` to reduce join iterations |
| `$unwind` | Deconstruct array field | `path`, `includeArrayIndex`, `preserveNullAndEmpty` | Use `preserveNullAndEmpty` to keep docs with null/empty arrays |
| `$sort` | Order documents | `1` (asc), `-1` (desc), `$meta: "textScore"` | Before other stages: uses index; after `$group`: in-memory sort (no index) |
| `$limit` | Return first N | Single number argument | Combine with `$sort` immediately before for Top-K optimizer |
| `$skip` | Skip first N | Single number argument | Avoid high `$skip` values for pagination — use cursor-based pagination instead |
| `$facet` | Multiple sub-pipelines on same data | Named sub-pipelines each as arrays | Documents entering `$facet` must fit in 100MB; no `$out`/`$merge` in sub-pipelines |
| `$bucket` | Group into user-defined ranges | `groupBy`, `boundaries`, `default`, `output` | Boundaries must be ascending, same BSON type; `default` required for out-of-range values |
| `$bucketAuto` | Group into auto-determined ranges | `groupBy`, `buckets`, `output`, `granularity` | Distributes evenly; use `granularity` for human-readable boundaries |
| `$count` | Count documents | Single string: output field name | Shorthand for `$group: {_id: null, n: {$sum: 1}}` + `$project`; optimizer-friendly |
| `$addFields` | Add fields without dropping others | Any expression | Prefer over `$project` when you want to keep all existing fields |
| `$out` | Write results to a collection | Collection name (replaces entire collection) | Atomic replace; use `$merge` for upsert behaviour |
| `$merge` | Merge results into a collection | `into`, `on`, `whenMatched`, `whenNotMatched` | Powerful for pre-aggregation caches and incremental updates |

---

**Tip for interviews:** Five things separate strong candidates on MongoDB aggregation: (1) articulating **the stage ordering performance rule** — that `$match` must come first to use collection indexes and reduce document volume before every subsequent stage, that placing `$group` before `$match` forces full-collection processing, and that `$sort` immediately before `$limit` triggers the Top-K optimizer which maintains a K-element priority queue instead of sorting all documents; (2) knowing **`$lookup`'s index requirement and limitations** — that the `foreignField` must be indexed on the joined collection or `$lookup` degrades to a collection scan per pipeline document, that the pipeline form using `let` and `$expr` enables multi-field joins and pre-filtering the joined collection, and that large `$lookup` intermediate results can hit the 100MB memory limit requiring `allowDiskUse: true`; (3) understanding **the `$unwind` + `$group` roundtrip pattern** — that `$unwind` is not just for "flattening arrays" but is the standard way to filter array elements and regroup, and that the alternative `$filter` operator inside `$project` is cleaner when no aggregation on array elements is needed; (4) explaining **`$facet` semantics precisely** — that all sub-pipelines within `$facet` share the same input documents from preceding stages (not separate collection scans), that it produces exactly ONE output document containing all sub-pipeline results as arrays, and that the primary use case is search result pages needing simultaneous results + filters + totals in one database round trip; and (5) being able to design a **pre-aggregation strategy for large collections** — using `$merge` to write daily/hourly aggregates into a summary collection, querying the summary collection for dashboards instead of re-aggregating 500M documents on every request, and understanding that this trades query latency for storage and scheduling complexity.
