## Section 1: How MongoDB Indexes Work Physically

**Q1. How does MongoDB store indexes — what is the physical structure and why does it matter for query planning?**

A: MongoDB uses a B-tree structure for most index types, stored in the WiredTiger storage engine as a separate data structure from the collection's documents. Understanding the physical layout explains every performance characteristic of every index type:

```
MongoDB collection physical layout (WiredTiger):

  Collection file: orders.wt
  ┌────────────────────────────────────────────────────────────────────┐
  │ Document 1: { _id: ObjectId("..."), userId: 42, status: "pending", │
  │              total: 99.99, createdAt: ISODate("2024-01-15") }      │
  │ Document 2: { _id: ObjectId("..."), userId: 1,  status: "shipped", │
  │              total: 149.99, createdAt: ISODate("2024-01-16") }     │
  │ Document 3: { _id: ObjectId("..."), userId: 42, status: "pending", │
  │              total: 29.99, createdAt: ISODate("2024-01-17") }      │
  │ ... (stored in insertion order, no guaranteed sort)                 │
  └────────────────────────────────────────────────────────────────────┘

  Index file: orders.$userId_1.wt  (index on { userId: 1 })
  ┌────────────────────────────────────────────────────────────────────┐
  │  B-tree leaf pages (sorted by userId):                             │
  │  (userId=1,  recordId → doc2_location)                            │
  │  (userId=42, recordId → doc1_location)                            │
  │  (userId=42, recordId → doc3_location)                            │
  └────────────────────────────────────────────────────────────────────┘

Key concepts:
  recordId    — physical location of the document (like PostgreSQL's ctid).
                For WiredTiger: a 64-bit integer identifying the document.
  Index entry — (indexed value, recordId) pair stored in the B-tree.
  Index scan  — traverse B-tree to find matching recordIds.
  Fetch       — use recordId to retrieve the full document from the collection file.
  Covered query — all fields needed are in the index → no fetch needed (like index-only scan).
```

```javascript
// ── Index introspection ───────────────────────────────────────────────────────

// List all indexes on a collection:
db.orders.getIndexes()
// [
//   { v: 2, key: { _id: 1 }, name: '_id_' },   ← always exists
//   { v: 2, key: { userId: 1 }, name: 'userId_1' },
//   { v: 2, key: { status: 1, createdAt: -1 }, name: 'status_1_createdAt_-1' }
// ]

// Index size (in memory and on disk):
db.orders.stats().indexSizes
// {
//   '_id_': 86016,                          ← 84 KB for _id index
//   'userId_1': 163840,                      ← 160 KB for userId index
//   'status_1_createdAt_-1': 229376          ← 224 KB for compound index
// }

// Total index size vs collection size (ratio matters for memory planning):
db.orders.stats({ scale: 1024 * 1024 })
// storageSize: 2048 MB  (documents)
// totalIndexSize: 512 MB (all indexes — should fit in RAM for best performance)

// Validate that indexes are being used — check collection scan vs index usage:
db.orders.aggregate([{ $indexStats: {} }])
// [
//   { name: 'userId_1', accesses: { ops: 48291, since: ISODate("...") } },
//   { name: 'status_1_createdAt_-1', accesses: { ops: 12847, since: ISODate("...") } }
// ]
// ops: 0 after a representative period → index is unused → candidate for removal.

// ── How the query planner chooses an index ────────────────────────────────────
// MongoDB's query planner uses a "trial" system:
// 1. Identifies candidate indexes for the query shape.
// 2. Races candidate plans in parallel (each plan executes for up to 101 results).
// 3. Selects the winning plan based on: fewest keys examined, fewest docs fetched.
// 4. Caches the winning plan for the query shape (invalidated on index changes or 1000 writes).

db.orders.explain("executionStats").find({ userId: 42, status: "pending" })
// Reveals: winning plan, rejected plans, keys examined, docs examined, execution time.
```

## Section 2: Single Field Indexes

**Q2. What are single field indexes — what are all the options and when does each matter?**

A: A single field index is a B-tree on one field of the document. It is the building block for all other index types. The options on a single field index — `unique`, `sparse`, `partialFilterExpression`, `expireAfterSeconds` — cover the most common production requirements:

```javascript
// ── Basic single field index ──────────────────────────────────────────────────
// 1 = ascending sort, -1 = descending sort.
// For single-field indexes, direction is irrelevant for equality queries.
// Direction matters for sort operations on compound indexes.
db.orders.createIndex({ userId: 1 })
// → Creates B-tree sorted by userId ascending.
// → Serves: find by userId, sort by userId, range on userId.
// → Does NOT serve: queries on other fields unless combined.

db.orders.createIndex({ createdAt: -1 })
// → Descending. Serves: sort by createdAt DESC efficiently.
// → A single-field ASC index and DESC index are functionally equivalent
//   (MongoDB can traverse B-trees in either direction).

// ── Unique index ──────────────────────────────────────────────────────────────
db.users.createIndex(
    { email: 1 },
    { unique: true }
)
// → Rejects INSERT/UPDATE if email already exists in any document.
// → On _id: always unique (no need to declare).
// → Null handling: two documents with email: null VIOLATE uniqueness
//   (null is treated as a value — use sparse: true to allow multiple nulls).

// ── Unique + Sparse (allow multiple documents without the field) ───────────────
db.users.createIndex(
    { githubId: 1 },
    { unique: true, sparse: true }
)
// → Indexes only documents where githubId EXISTS (non-null).
// → Documents without githubId are excluded from the index entirely.
// → Multiple documents without githubId: allowed ✓ (they're not in the index).
// → Two documents with githubId: "gh123": rejected ✓.
// → CAVEAT: a query like find({ githubId: { $exists: false } }) cannot use
//   this sparse index (the missing documents aren't in the index).

// ── Partial index (more powerful than sparse) ─────────────────────────────────
// Index only documents matching a filter expression.
db.orders.createIndex(
    { userId: 1, createdAt: -1 },
    {
        partialFilterExpression: {
            status: { $in: ["pending", "processing"] }
        },
        name: "idx_active_orders_by_user"
    }
)
// → Only documents with status "pending" or "processing" are indexed.
// → If 90% of orders are "completed": index is 90% smaller.
// → Query MUST include the partial filter for the planner to use this index:
db.orders.find({ userId: 42, status: "pending" })    // Uses partial index ✓
db.orders.find({ userId: 42 })                        // Does NOT use partial index ✗
//   (planner can't guarantee all userId=42 docs are in the partial index)

// ── Background index builds (pre-MongoDB 4.2) ─────────────────────────────────
// Pre-4.2: foreground build blocked all reads and writes.
db.orders.createIndex({ userId: 1 }, { background: true })  // Deprecated option
// MongoDB 4.2+: ALL index builds are concurrent by default (no background option needed).
// They use a hybrid approach: acquire brief locks only at start and end of build.

// ── Hidden indexes (MongoDB 4.4+) ─────────────────────────────────────────────
// Hide an index from the query planner without dropping it.
// Use to test the impact of removing an index without actually dropping it.
db.orders.hideIndex("userId_1")
// → Query planner ignores this index → queries use COLLSCAN or other indexes.
// → Index still maintained on writes (write overhead persists).
// → Unhide to restore: db.orders.unhideIndex("userId_1")
// → Safe way to validate that an index is truly unused before dropping it.

// ── Index on nested field ─────────────────────────────────────────────────────
db.orders.createIndex({ "shippingAddress.city": 1 })
// Supports: db.orders.find({ "shippingAddress.city": "New York" })
// Dot notation indexes into embedded documents.

// ── Mongoose / NestJS single field index ─────────────────────────────────────
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
import { Document }                     from 'mongoose';

@Schema({ timestamps: true })
export class Order extends Document {
    @Prop({ required: true, index: true })  // Declares { userId: 1 } index
    userId: number;

    @Prop({ required: true, unique: true }) // Declares { orderNumber: 1 } unique index
    orderNumber: string;

    @Prop({ required: true })
    status: string;

    @Prop({ required: true })
    total: number;
}
export const OrderSchema = SchemaFactory.createForClass(Order);

// For partial and sparse indexes, use schema-level index declaration:
OrderSchema.index(
    { userId: 1, createdAt: -1 },
    { partialFilterExpression: { status: { $in: ['pending', 'processing'] } } }
);
```

## Section 3: Compound Indexes

**Q3. What is the ESR rule for compound indexes — how does it differ from SQL's "equality before range"?**

A: MongoDB's ESR rule (Equality, Sort, Range) extends the SQL leftmost-prefix rule by explicitly placing Sort fields between Equality and Range fields. This ordering maximises how many stages of a query's execution use the index:

```
The ESR rule — column ordering for compound indexes:

  Query: db.orders.find({
      status: "pending",          ← Equality (E)
      total: { $gt: 50 }         ← Range    (R)
  }).sort({ createdAt: -1 })     ← Sort     (S)

  WRONG order: { status:1, total:1, createdAt:-1 }   (E, R, S)
    → status (equality) ✓
    → total (range) → B-tree entries no longer contiguous for next field
    → createdAt CANNOT be used for sort (range stop after total)
    → In-memory sort required for createdAt ← costly

  CORRECT order (ESR): { status:1, createdAt:-1, total:1 }   (E, S, R)
    → status (equality) ✓ — all matching entries contiguous
    → createdAt (sort) ✓ — within "pending", entries sorted by createdAt
    → total (range) ✓ — applied as final filter; range is last (acceptable)
    → No in-memory sort: index provides the createdAt order directly ✓

  Why Sort goes before Range:
    After equality columns fix a contiguous block, entries within that block
    are sorted by the next key column. Placing the Sort column next means
    the index provides the desired sort order for free.
    Placing Range next would break contiguity, making the Sort column's
    entries non-contiguous and forcing an in-memory sort.
```

```javascript
// ── ESR in practice ───────────────────────────────────────────────────────────

// Query: all "pending" orders for a tenant, sorted by date, with total > 50
db.orders.find({
    tenantId: "t-123",    // E: equality
    status: "pending",    // E: equality
    total: { $gt: 50 }   // R: range
}).sort({ createdAt: -1 }) // S: sort

// Correct compound index (ESR):
db.orders.createIndex({
    tenantId:  1,   // E — always present, highest cardinality → leftmost
    status:    1,   // E — equality filter
    createdAt: -1,  // S — sort field (after equalities, before range)
    total:     1    // R — range field (last)
})

// Verify with explain:
db.orders.explain("executionStats").find(
    { tenantId: "t-123", status: "pending", total: { $gt: 50 } }
).sort({ createdAt: -1 })
// stage: "IXSCAN"     ← index scan used ✓
// indexBounds: {
//   tenantId: ["t-123", "t-123"],      ← exact equality bound
//   status:   ["pending", "pending"],  ← exact equality bound
//   createdAt: [MaxKey, MinKey],       ← full range (sort scan)
//   total:    [50, Infinity]           ← range filter
// }
// executionStats.needsFetch: false  ← covered query if projected fields are in index ✓
// executionStats.totalDocsExamined: 0  ← never hit the collection ✓

// ── When to put E fields in which order ───────────────────────────────────────
// Among multiple equality fields: put higher-cardinality fields first.
// Higher cardinality → fewer documents match the prefix → faster traversal.
// But: if a field is ALWAYS present in the query, it must be leftmost
// to serve as the leftmost prefix for that index.

// tenantId (100 values) vs status (5 values):
// → tenantId first: each value matches 1/100 of documents → very selective.
// → status first: each value matches 1/5 of documents → less selective.
// → tenantId first is more efficient.

// ── The prefix rule: which queries use a compound index ───────────────────────
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })

// Queries that USE this index (leftmost prefix satisfied):
db.orders.find({ tenantId: "t-123" })                            // prefix: {tenantId}
db.orders.find({ tenantId: "t-123", status: "pending" })         // prefix: {tenantId, status}
db.orders.find({ tenantId: "t-123" }).sort({ createdAt: -1 })    // prefix + sort
db.orders.find({ tenantId: "t-123", status: "pending" }).sort({ createdAt: -1 }) // full ✓

// Queries that do NOT use this index:
db.orders.find({ status: "pending" })                // Missing tenantId (leftmost) ✗
db.orders.find({ status: "pending", createdAt: ... }) // Missing tenantId ✗

// ── Direction matters for sort in compound indexes ────────────────────────────
db.orders.createIndex({ tenantId: 1, createdAt: -1 })

db.orders.find({ tenantId: "t-123" }).sort({ createdAt: -1 }) // ✓ matches index
db.orders.find({ tenantId: "t-123" }).sort({ createdAt:  1 }) // ✓ backward scan
// For compound sort: BOTH columns must have directions that are either
// matching or fully inverted:
db.orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 })
db.orders.find({ tenantId: "t-123" }).sort({ status: 1,  createdAt: -1 }) // ✓ matches
db.orders.find({ tenantId: "t-123" }).sort({ status: -1, createdAt:  1 }) // ✓ inverted
db.orders.find({ tenantId: "t-123" }).sort({ status: 1,  createdAt:  1 }) // ✗ mixed directions → in-memory sort

// ── Covered queries: all fields in the index ──────────────────────────────────
// A covered query never reads the collection — all needed data is in the index.
db.orders.createIndex({ userId: 1, status: 1, total: 1 })

db.orders.find(
    { userId: 42, status: "pending" },
    { _id: 0, userId: 1, status: 1, total: 1 }  // Project only indexed fields
)
// → IXSCAN only, no FETCH stage (totalDocsExamined: 0 in explain) ✓
// IMPORTANT: _id: 0 must be explicitly excluded —
// _id is not in the index, so projecting it forces a FETCH.
```

## Section 4: Multikey Indexes (Arrays)

**Q4. What is a multikey index — how does MongoDB index arrays and what are the restrictions?**

A: A multikey index is automatically created when MongoDB indexes a field that contains an array. For each element in the array, MongoDB creates a separate index entry pointing to the document. This enables queries on array contents but introduces specific restrictions:

```
Multikey index physical structure:

  Document: {
      _id: ObjectId("..."),
      productId: 101,
      tags: ["electronics", "laptop", "sale"]   ← array field
  }

  Index on { tags: 1 }:
  B-tree entries created:
  ("electronics", recordId=doc1)   ← one entry per array element
  ("laptop",      recordId=doc1)   ← all pointing to the SAME document
  ("sale",        recordId=doc1)

  A second document: { tags: ["laptop", "refurbished"] }
  B-tree entries:
  ("laptop",      recordId=doc2)   ← "laptop" now has TWO entries
  ("refurbished", recordId=doc2)

  Query: db.products.find({ tags: "laptop" })
  → B-tree scan finds all entries where tag = "laptop"
  → Returns doc1 AND doc2 (both have "laptop" in their tags array)
```

```javascript
// ── Multikey index creation (automatic) ───────────────────────────────────────
// MongoDB automatically creates a multikey index when the indexed field is an array.
// No special syntax needed:
db.products.createIndex({ tags: 1 })
// If ANY document has tags as an array → multikey index is created.
// MongoDB notes this in the index metadata:
db.products.stats().indexDetails.tags_1.metadata.multikey  // → true

// ── Querying with multikey index ──────────────────────────────────────────────
// Match documents where the array CONTAINS a specific value:
db.products.find({ tags: "laptop" })  // ✓ Uses index

// Match documents where the array contains ALL specified values ($all):
db.products.find({ tags: { $all: ["laptop", "sale"] } })  // ✓ Uses index
// MongoDB uses the index to find "laptop" entries, then filters for "sale".

// Match documents where the array contains elements satisfying a condition:
db.products.find({ prices: { $elemMatch: { $gt: 100, $lt: 500 } } })
// If prices is an array of numbers:
// $elemMatch: one element must satisfy BOTH conditions (>100 AND <500).
// Without $elemMatch: { $gt: 100, $lt: 500 } matches if any element > 100
//   AND any element < 500 (can be different elements — probably wrong).

// ── Indexing array of embedded documents ──────────────────────────────────────
// Document: { variants: [ { sku: "A1", price: 99 }, { sku: "A2", price: 149 } ] }
db.products.createIndex({ "variants.sku": 1 })
// Creates one entry per variant: ("A1", doc1), ("A2", doc1)
db.products.find({ "variants.sku": "A1" })  // ✓ Uses multikey index

// Compound index with array field and scalar field:
db.products.createIndex({ category: 1, "variants.price": 1 })
// category is scalar → one entry per document for category.
// variants.price is array → one entry per variant price per document.
// Combined: (category_value, price_value) entry per variant per document.

// ── The compound multikey restriction ─────────────────────────────────────────
// ONLY ONE array field can be indexed per compound index.
// If two fields are both arrays → ERROR (or the index refuses to apply to such docs).

db.products.createIndex({ tags: 1, relatedIds: 1 })
// → This index is created successfully.
// → BUT: documents where BOTH tags AND relatedIds are arrays
//   CANNOT be inserted (throws a "too many array fields" error).
// → Documents where only ONE of them is an array: fine.

// Example violation:
db.products.insertOne({
    tags: ["laptop", "electronics"],    // array
    relatedIds: [101, 102, 103]         // also array → ERROR if compound index exists
})
// MongoServerError: cannot index parallel arrays [tags] [relatedIds]

// Fix: create separate single-field indexes for each array field:
db.products.createIndex({ tags: 1 })        // For tags queries
db.products.createIndex({ relatedIds: 1 })  // For relatedIds queries
// Now each query can use its own index independently.

// ── Multikey index and covered queries ────────────────────────────────────────
// Covered queries are NOT possible with multikey indexes.
// Reason: the index entry contains the array element, not the full array.
// To reconstruct the full array, the document must be fetched.
db.products.find(
    { tags: "laptop" },
    { _id: 0, tags: 1 }   // Trying to cover...
)
// → Always requires a FETCH stage — covered query is impossible for multikey.

// ── Multikey and sort ─────────────────────────────────────────────────────────
// Sorting by a multikey-indexed field is NOT supported.
db.products.find({ category: "electronics" }).sort({ tags: 1 })
// → Error or in-memory sort — cannot sort by an array field via index.
// Sorting by a scalar field in a compound index that includes an array: fine.
db.products.createIndex({ category: 1, createdAt: -1, tags: 1 })
db.products.find({ category: "electronics" }).sort({ createdAt: -1 }) // ✓

// ── Mongoose schema for multikey index ───────────────────────────────────────
@Schema()
export class Product extends Document {
    @Prop({ type: [String], index: true })   // Multikey index on tags array
    tags: string[];

    @Prop({
        type: [{ sku: String, price: Number }],
    })
    variants: { sku: string; price: number }[];
}
export const ProductSchema = SchemaFactory.createForClass(Product);

// Compound multikey index on embedded array field + scalar field:
ProductSchema.index({ category: 1, 'variants.price': 1 });
```

## Section 5: Text Indexes

**Q5. How do text indexes work in MongoDB — what are the scoring, weighting, and language considerations?**

A: A text index enables full-text search over string content. Unlike a single field index (exact match), a text index tokenises strings, removes stop words, applies stemming, and stores term frequencies for relevance scoring:

```
Text index internals:

  Document: {
      _id: ObjectId("..."),
      title: "Running Shoes for Marathon Training",
      description: "Professional shoes designed for long-distance running"
  }

  Text index on { title: "text", description: "text" }:
  Tokenisation + stemming + stop-word removal:
  title:       "run", "shoe", "marathon", "train"   (stop words: "for" removed)
  description: "profession", "shoe", "design", "long", "distanc", "run"

  B-tree entries (inverted index):
  ("design",    doc1, score: 0.75)
  ("distanc",   doc1, score: 0.75)
  ("long",      doc1, score: 0.75)
  ("marathon",  doc1, score: 1.10)  ← higher score: in title (high weight) + rare
  ("profession",doc1, score: 0.75)
  ("run",       doc1, score: 1.85)  ← appears in both fields
  ("shoe",      doc1, score: 1.85)  ← appears in both fields, title has weight
  ("train",     doc1, score: 1.10)

  Query: db.products.find({ $text: { $search: "running shoes" } })
  → Stemmed: "run", "shoe"
  → Both terms found → combined score: 1.85 + 1.85 = 3.70
  → Higher score = more relevant = sorted first when projecting { score: { $meta: "textScore" } }
```

```javascript
// ── Creating a text index ──────────────────────────────────────────────────────
// Basic text index on one field:
db.articles.createIndex({ content: "text" })

// Text index on multiple fields with weights (default weight = 1):
db.articles.createIndex(
    {
        title:       "text",   // weight = 10 (default 1 → higher means more important)
        summary:     "text",   // weight = 5
        content:     "text",   // weight = 1 (default)
        tags:        "text",   // weight = 3 (tags also indexed as text)
    },
    {
        weights: {
            title:   10,   // Match in title = 10x more relevant than content match
            summary:  5,
            content:  1,
            tags:     3,
        },
        name: "idx_article_text",
        default_language: "english",        // Stemmer and stop words for English
        language_override: "language_field" // Per-document language: { language: "spanish" }
    }
)

// ── ONLY ONE text index per collection (hard limit) ───────────────────────────
// MongoDB allows only one text index per collection.
// It can cover multiple fields (as above), but not two separate text indexes.
// Trying to create a second: MongoServerError: Too many text indexes

// ── Text search queries ────────────────────────────────────────────────────────
// Basic search (any of the terms):
db.articles.find({ $text: { $search: "running shoes" } })
// → Finds documents containing "running" OR "shoes" (stemmed: "run" OR "shoe").

// Exact phrase (quoted):
db.articles.find({ $text: { $search: '"marathon training"' } })
// → Finds documents containing the exact phrase "marathon training".

// Exclude a term (prefix with -):
db.articles.find({ $text: { $search: "shoes -running" } })
// → Finds documents with "shoes" but NOT "running".

// Sort by relevance score:
db.articles.find(
    { $text: { $search: "marathon running" } },
    { score: { $meta: "textScore" }, title: 1, _id: 0 }
).sort({ score: { $meta: "textScore" } })
// → Returns title and textScore, sorted most relevant first.
// Output: [
//   { title: "Marathon Training Guide", score: 4.8 },
//   { title: "Running Tips for Beginners", score: 2.1 }
// ]

// Filter + text search (text must be the only $text operator, but can combine with other filters):
db.articles.find({
    $text: { $search: "marathon" },
    publishedAt: { $gte: new Date("2024-01-01") },  // Combine with regular filter
    status: "published"
})
// → Text index for "marathon" + additional filters on publishedAt and status.

// Language-specific search:
db.articles.find({
    $text: { $search: "corriendo", $language: "spanish" }
})
// → Uses Spanish stemmer: "corriendo" → "correr" (run in Spanish).

// ── Text index limitations ────────────────────────────────────────────────────
// 1. Only one text index per collection.
// 2. Cannot create a compound index with text and other fields in the same key:
//    db.articles.createIndex({ userId: 1, title: "text" })  ← Allowed (compound text)
//    But: { title: "text", content: "text", userId: 1 } → userId must be outside text portion
// 3. Cannot sort by a regular field AND textScore efficiently (needs separate sort).
// 4. Wildcards not supported in $search (use MongoDB Atlas Search for advanced needs).
// 5. $text queries cannot use covered queries (score is computed at query time).
// 6. Prefix matching not supported: "run" finds "run"/"running" (stemmed), not arbitrary prefix.

// ── Compound text index for multi-tenant full-text search ─────────────────────
// Prefix the text fields with tenant equality field:
db.articles.createIndex(
    { tenantId: 1, title: "text", content: "text" },
    { weights: { title: 3, content: 1 } }
)
// Query:
db.articles.find({
    $text: { $search: "marathon" },
    tenantId: "t-123"   // Uses the tenantId prefix of the compound text index
})
// → tenantId narrows the search to one tenant's articles before text scanning.
// This is more efficient than a pure text index (which would scan all tenants).

// ── Atlas Search (alternative to text index for production) ───────────────────
// For production full-text search: MongoDB Atlas Search uses Apache Lucene.
// Benefits over text index:
// • Fuzzy matching, autocomplete, synonyms, faceting, highlighting
// • Better relevance scoring (BM25 instead of term frequency)
// • No one-index-per-collection limit
// • Works with aggregation pipeline via $search stage

// Mongoose text index declaration:
ArticleSchema.index(
    { title: 'text', content: 'text' },
    { weights: { title: 10, content: 1 }, name: 'idx_article_text' }
);
```

## Section 6: Geospatial Indexes

**Q6. What are the two geospatial index types in MongoDB — when do you use `2dsphere` vs `2d`?**

A: MongoDB provides two geospatial index types for different geometric models. `2dsphere` operates on a sphere (the Earth) and uses GeoJSON; `2d` operates on a flat Euclidean plane and uses legacy coordinate pairs. Almost all modern applications use `2dsphere`:

```javascript
// ── 2dsphere index (spherical geometry, modern standard) ──────────────────────
// Supports GeoJSON objects: Point, LineString, Polygon, MultiPolygon, etc.
// Uses spherical calculations (correct for Earth's surface).
// Distances in metres when using GeoJSON.

db.restaurants.createIndex({ location: "2dsphere" })

// Document format (GeoJSON):
db.restaurants.insertOne({
    name: "Burger Palace",
    cuisine: "American",
    location: {
        type: "Point",
        coordinates: [-73.9857, 40.7484]   // [longitude, latitude] — longitude FIRST
        // IMPORTANT: MongoDB GeoJSON is [longitude, latitude], NOT [lat, long].
    },
    rating: 4.5
})

// ── $near: find documents sorted by distance ──────────────────────────────────
db.restaurants.find({
    location: {
        $near: {
            $geometry: {
                type: "Point",
                coordinates: [-73.9855, 40.7580]  // User's location
            },
            $maxDistance: 1000,   // Metres (1 km radius)
            $minDistance: 0       // Minimum distance (optional)
        }
    }
})
// → Returns restaurants within 1km, sorted nearest first.
// → Requires a 2dsphere index on 'location'.
// → CANNOT use $near with $geoWithin in the same query.

// ── $geoWithin: find documents within a polygon ────────────────────────────────
db.restaurants.find({
    location: {
        $geoWithin: {
            $geometry: {
                type: "Polygon",
                coordinates: [[
                    [-74.0059, 40.7128],   // New York City bounding box (simplified)
                    [-73.9442, 40.7128],
                    [-73.9442, 40.7580],
                    [-74.0059, 40.7580],
                    [-74.0059, 40.7128]    // Close the polygon (repeat first point)
                ]]
            }
        }
    }
})
// → Returns all restaurants within the polygon.
// → Does NOT sort by distance (use $near for distance-sorted results).
// → More efficient than $near for "is inside region" queries.

// ── $geoWithin with $centerSphere: circular query (no index needed, but faster with one) ──
db.restaurants.find({
    location: {
        $geoWithin: {
            $centerSphere: [
                [-73.9857, 40.7484],   // [longitude, latitude] of centre
                5 / 3963.2             // Radius in radians (5 miles ÷ Earth radius in miles)
            ]
        }
    }
})

// ── $geoIntersects: find documents whose geometry intersects a shape ───────────
// Useful for: "which delivery zone covers this address?"
db.deliveryZones.createIndex({ zone: "2dsphere" })
db.deliveryZones.insertOne({
    name: "Manhattan Zone A",
    zone: {
        type: "Polygon",
        coordinates: [[/* Manhattan polygon points */]]
    }
})

db.deliveryZones.find({
    zone: {
        $geoIntersects: {
            $geometry: {
                type: "Point",
                coordinates: [-73.9857, 40.7484]   // Customer's address
            }
        }
    }
})
// → Which delivery zone polygons contain this point?

// ── $nearSphere: spherical $near for legacy point format ──────────────────────
// $near with $geometry: uses spherical math (correct for Earth).
// $nearSphere with legacy [lon, lat] format: also spherical.
// Prefer $near with GeoJSON ($geometry) for clarity.

// ── Compound 2dsphere index ───────────────────────────────────────────────────
// Add scalar fields to the geospatial index for filtering before geo operations:
db.restaurants.createIndex({ cuisine: 1, location: "2dsphere" })

db.restaurants.find({
    cuisine: "Italian",     // Filter on cuisine first (index prefix)
    location: {
        $near: {
            $geometry: { type: "Point", coordinates: [-73.9857, 40.7484] },
            $maxDistance: 500
        }
    }
})
// → Cuisine index narrows to Italian restaurants, then geo search within those.
// More efficient than geo-then-filter for queries with selective scalar filters.

// ── 2d index (flat plane, legacy) ─────────────────────────────────────────────
// Use ONLY for: gaming coordinates, floor plans, flat maps, or legacy systems.
// Uses Euclidean distance, NOT spherical.
// Does NOT support GeoJSON.

db.gameObjects.createIndex({ position: "2d" }, { min: -500, max: 500 })  // Map boundary

db.gameObjects.insertOne({
    name: "Treasure Chest",
    position: [125, -87]   // Legacy [x, y] format (NOT GeoJSON)
})

db.gameObjects.find({
    position: {
        $near: [0, 0],          // Find near origin
        $maxDistance: 100       // Flat distance units (not metres)
    }
})

// ── Distance calculation in aggregation ───────────────────────────────────────
// $geoNear aggregation stage: most powerful geospatial query.
// Returns distance in the output document.
db.restaurants.aggregate([
    {
        $geoNear: {
            near: { type: "Point", coordinates: [-73.9857, 40.7484] },
            distanceField: "distanceMetres",   // Adds this field to each output doc
            maxDistance: 2000,                  // 2km
            query: { cuisine: "Italian" },      // Additional filter
            spherical: true                     // Required for 2dsphere
        }
    },
    { $sort:  { distanceMetres: 1 } },
    { $limit: 10 },
    {
        $project: {
            name: 1,
            cuisine: 1,
            distanceMetres: 1,
            distanceKm: { $divide: ["$distanceMetres", 1000] }
        }
    }
])
// → Returns 10 nearest Italian restaurants with their distance in metres and km.
// $geoNear MUST be the first stage in the pipeline.

// ── Mongoose geospatial schema ────────────────────────────────────────────────
@Schema()
export class Restaurant extends Document {
    @Prop({ required: true })
    name: string;

    @Prop({
        type: {
            type: String,
            enum: ['Point'],
            required: true,
        },
        coordinates: {
            type: [Number],   // [longitude, latitude]
            required: true,
        },
    })
    location: { type: string; coordinates: number[] };
}
export const RestaurantSchema = SchemaFactory.createForClass(Restaurant);

// Declare 2dsphere index (must use schema-level, not @Prop index option):
RestaurantSchema.index({ location: '2dsphere' });
```

## Section 7: TTL Indexes

**Q7. How do TTL indexes work — what are the exact mechanics, limitations, and use cases?**

A: A TTL (Time-To-Live) index automatically deletes documents after a specified time. MongoDB runs a background thread (the TTL monitor) that scans the index every 60 seconds and removes expired documents:

```javascript
// ── TTL index: expire after N seconds from a date field ───────────────────────
// The indexed field must be a BSON Date type (or array of Dates).
// expireAfterSeconds: documents are deleted when:
//   current_time > document[dateField] + expireAfterSeconds

db.sessions.createIndex(
    { lastAccessedAt: 1 },
    { expireAfterSeconds: 3600 }   // Delete 1 hour after lastAccessedAt
)

db.sessions.insertOne({
    userId: 42,
    token: "abc123",
    lastAccessedAt: new Date()   // Set to now → expires in 1 hour
})

// ── TTL index: expire at a specific time (expireAfterSeconds: 0) ───────────────
// If expireAfterSeconds: 0, the document is deleted AT the date stored in the field.
// The document specifies its own exact deletion time.
db.scheduledJobs.createIndex(
    { runAt: 1 },
    { expireAfterSeconds: 0 }    // Delete exactly when runAt time is reached
)

db.scheduledJobs.insertOne({
    jobType: "send_email",
    userId: 42,
    runAt: new Date(Date.now() + 24 * 60 * 60 * 1000)   // Expires in 24 hours
})

// ── How the TTL monitor works ─────────────────────────────────────────────────
// The TTLMonitor background thread runs on the PRIMARY only (not replicas).
// It executes every 60 seconds (configurable via ttlMonitorSleepSecs).
// Each run: scans the TTL index, finds expired entries, issues DELETE operations.
// Deletes are replicated to replicas via the oplog (replicas don't run TTLMonitor).

// The 60-second interval means: documents may live up to 60 seconds longer
// than their expiry time. Design for "eventually deleted", not instant deletion.

// Check TTLMonitor status:
db.adminCommand({ serverStatus: 1 }).metrics.ttl
// {
//   deletedDocuments: 48291,   ← Total docs deleted by TTL since server start
//   passes: 1823               ← Number of TTLMonitor passes
// }

// ── TTL index limitations ──────────────────────────────────────────────────────
// 1. The field MUST be a BSON Date (not a string, not a timestamp integer).
//    Non-date fields are ignored by the TTL monitor.
db.sessions.insertOne({ token: "xyz", lastAccessedAt: "2024-01-15T00:00:00Z" })
// ↑ "2024-01-15..." is a STRING, not a Date → TTL monitor ignores this document.
// FIX: new Date("2024-01-15") or ISODate("2024-01-15T00:00:00Z")

// 2. CANNOT create a TTL index on:
//    • The _id field
//    • A compound index (TTL can only be single-field)
//    • Capped collections (they have their own size-based eviction)

// 3. If the TTL field contains an ARRAY of dates: the document expires when
//    the EARLIEST date in the array is past the expiry threshold.
db.events.createIndex({ dates: 1 }, { expireAfterSeconds: 86400 })
db.events.insertOne({ dates: [new Date("2024-01-10"), new Date("2024-02-01")] })
// → Expires 1 day after 2024-01-10 (the earliest date), not 2024-02-01.

// 4. TTL does NOT work on replica sets as primary-on-secondary TTL.
//    Only the current PRIMARY runs the TTL monitor. If a replica is promoted,
//    it starts running TTL within the next 60-second cycle.

// 5. Changing expireAfterSeconds on an existing TTL index:
db.adminCommand({
    collMod: "sessions",
    index: {
        keyPattern: { lastAccessedAt: 1 },
        expireAfterSeconds: 7200    // Change from 3600 to 7200 seconds
    }
})
// → Change takes effect immediately (no need to drop and recreate).

// ── Common TTL patterns ────────────────────────────────────────────────────────

// Pattern 1: Session expiry (sliding window — update lastAccessedAt on each request)
db.sessions.updateOne(
    { token: "abc123" },
    { $set: { lastAccessedAt: new Date() } }   // Reset the TTL timer
)
// → Session lives 3600 seconds from the LAST access, not creation.
// → Like a cookie with a sliding expiration.

// Pattern 2: Fixed expiry (set createdAt, expire after N seconds)
db.otpCodes.createIndex(
    { createdAt: 1 },
    { expireAfterSeconds: 300 }   // OTP codes expire 5 minutes after creation
)
db.otpCodes.insertOne({ userId: 42, code: "123456", createdAt: new Date() })
// → Code is deleted exactly 5 minutes after creation, regardless of use.

// Pattern 3: Scheduled deletion (expireAfterSeconds: 0 + specific date)
db.temporaryLinks.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })
db.temporaryLinks.insertOne({
    url: "https://...",
    token: "share-token",
    expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)  // 7 days from now
})
// → Link is deleted at exactly the stored expiresAt time.

// Pattern 4: Log/audit rotation (keep last N days of data)
db.auditLogs.createIndex(
    { timestamp: 1 },
    { expireAfterSeconds: 90 * 24 * 60 * 60 }  // Keep 90 days of audit logs
)

// ── Mongoose TTL index ────────────────────────────────────────────────────────
@Schema()
export class Session extends Document {
    @Prop({ required: true })
    userId: number;

    @Prop({ required: true })
    token: string;

    // expires: true is Mongoose shorthand for TTL index.
    // The value (3600) is expireAfterSeconds.
    @Prop({ type: Date, default: Date.now, expires: 3600 })
    createdAt: Date;
    // → Creates index: { createdAt: 1 }, { expireAfterSeconds: 3600 }
}
// OR: use SchemaFactory for more control:
SessionSchema.index({ lastAccessedAt: 1 }, { expireAfterSeconds: 3600 });
```

## Section 8: Wildcard and Hashed Indexes

**Q8. What are wildcard indexes and hashed indexes — when are they the right tool?**

A: Wildcard indexes and hashed indexes solve narrow but important problems. Wildcard indexes handle unpredictable field structures; hashed indexes are specifically for sharding:

```javascript
// ── Wildcard indexes (MongoDB 4.2+) ────────────────────────────────────────────
// Index ALL fields in a document (or a subdocument) without knowing them in advance.
// Use case: documents with user-defined or schema-less fields.

// Example: event tracking where each event type has different metadata fields:
// { type: "page_view", metadata: { page: "/home", referrer: "google.com" } }
// { type: "purchase",  metadata: { productId: 101, price: 99.99, currency: "USD" } }
// { type: "search",    metadata: { query: "laptop", filters: ["brand=Dell"] } }

db.events.createIndex({ "metadata.$**": 1 })
// → Indexes ALL fields inside the metadata subdocument.
// → Works for any field, regardless of what it's called.

// Queries that use the wildcard index:
db.events.find({ "metadata.page": "/home" })        // ✓
db.events.find({ "metadata.productId": 101 })       // ✓
db.events.find({ "metadata.query": "laptop" })      // ✓
// → Any field path under metadata is indexed.

// Wildcard index on the entire document:
db.events.createIndex({ "$**": 1 })
// → Indexes EVERY field in every document.
// → Very large index; use "metadata.$**" (scoped) instead when possible.

// Wildcard index with wildcardProjection (include or exclude specific paths):
db.events.createIndex(
    { "$**": 1 },
    {
        wildcardProjection: {
            "metadata.internalField": 0,   // Exclude this field from the index
            "metadata.largeBlob": 0        // Exclude large fields to save space
        }
    }
)

// Wildcard index limitations:
// ✗ Cannot create compound wildcard index (wildcard must be the only key).
// ✗ Cannot use for covered queries (fields are unknown at index creation time).
// ✗ Cannot support sort operations via the index.
// ✗ Does not index: _id field, arrays of arrays.
// ✓ Perfect for: multi-tenant apps with tenant-defined fields, ETL data staging.

// ── Hashed indexes ────────────────────────────────────────────────────────────
// Stores the hash of the indexed field's value, not the value itself.
// PRIMARY USE CASE: shard key for sharded collections.
// Provides uniform distribution across shards even for monotonically increasing values.

db.orders.createIndex({ _id: "hashed" })
// → Used when sharding a collection by _id with uniform distribution.
// sh.shardCollection("myapp.orders", { _id: "hashed" })

// When to use hashed sharding:
// BAD shard key (range-based): { createdAt: 1 }
// → New orders always go to the "most recent time" shard → hotspot.
// GOOD shard key (hashed): { _id: "hashed" }
// → ObjectId hashes are uniformly distributed → balanced shards.
// → BUT: cannot do range queries efficiently on the shard key.

// Hashed index limitations:
// ✗ Does NOT support range queries ($gt, $lt, $between).
// ✗ Does NOT support sort operations.
// ✗ Cannot create compound hashed indexes.
// ✗ Cannot use for covered queries.
// ✓ Only supported operation: exact equality (find by exact _id value).
// ✓ Primary use: shard key definition for uniform distribution.
```

## Section 9: Understanding EXPLAIN()

**Q9. How do you read `explain("executionStats")` output to diagnose index performance?**

A: MongoDB's explain output reveals exactly which index was chosen, how many keys were examined, how many documents were fetched, and where time was spent. Every optimisation decision should start with reading explain output:

```javascript
// ── Running explain ────────────────────────────────────────────────────────────
const plan = db.orders.explain("executionStats").find(
    { tenantId: "t-123", status: "pending", total: { $gt: 50 } }
).sort({ createdAt: -1 }).limit(20)

// ── Reading the winning plan ───────────────────────────────────────────────────
// plan.queryPlanner.winningPlan:
{
    stage: "LIMIT",            // Top level: LIMIT applied
    inputStage: {
        stage: "FETCH",        // Fetch full documents from collection
        // FETCH is present → not a covered query (must read collection)
        filter: {              // Post-fetch filter (applied after index scan)
            total: { $gt: 50 } // ← total was NOT an index condition → applied as filter
        },
        inputStage: {
            stage: "IXSCAN",   // Index scan — the key stage to look for
            keyPattern: { tenantId: 1, status: 1, createdAt: -1 },
            indexName: "tenantId_1_status_1_createdAt_-1",
            isMultiKey: false,
            direction: "forward",
            indexBounds: {
                tenantId:  ["t-123", "t-123"],  // Exact equality ✓
                status:    ["pending", "pending"], // Exact equality ✓
                createdAt: [MaxKey, MinKey]        // Full range scan for sort ✓
            }
        }
    }
}

// What the stages mean:
// COLLSCAN → no index used (full collection scan) — the worst case
// IXSCAN   → index scan — good
// FETCH    → loading full document from collection after index scan
//            present when: projected fields not all in index (not covered)
//            OR: filter fields not in index (applied post-fetch)
// SORT     → in-memory sort (index couldn't provide sort order) — expensive for large result sets
// LIMIT    → LIMIT applied (if before SORT: early termination ✓)
// PROJECTION → field projection

// ── Reading executionStats ─────────────────────────────────────────────────────
// plan.executionStats:
{
    executionSuccess:    true,
    nReturned:           20,            // Documents returned to client
    executionTimeMillis: 3,             // Total query time in ms
    totalKeysExamined:   127,           // Index entries scanned
    totalDocsExamined:   127,           // Collection documents fetched

    // Key ratio: totalKeysExamined / nReturned
    // Ideal: close to 1.0 (examined ≈ returned)
    // Bad:   127 examined / 20 returned = 6.35 → examining 6x too many docs
    // Why: totalCreatedAt is a sort field (full range scan) + total > 50 is post-fetch

    executionStages: {
        stage: "LIMIT",
        nReturned: 20,
        executionTimeMillisEstimate: 1,
        inputStage: {
            stage: "FETCH",
            nReturned: 20,
            totalDocsExamined: 127,     // ← 127 fetched, 20 returned = 107 wasted
            filter: { total: { $gt: 50 } },  // Post-fetch filter
            inputStage: {
                stage: "IXSCAN",
                nReturned: 127,         // Index returned 127 entries (before filter)
                totalKeysExamined: 127,
                indexBounds: { ... }
            }
        }
    }
}

// ── Diagnosing problems from explain output ────────────────────────────────────
// Problem 1: COLLSCAN stage → no index used
//   Fix: create an index that covers the query filter fields.

// Problem 2: totalDocsExamined >> nReturned
//   The filter is applied after fetching documents (post-index filter).
//   Fix: add the filtered field to the compound index so it's applied during IXSCAN.

// Problem 3: SORT stage (in-memory sort)
//   Fix: reorder compound index to put the sort field before range fields (ESR rule).
//   Or: increase allowDiskUse if sort exceeds 100MB memory limit.

// Problem 4: totalKeysExamined >> nReturned (but no SORT stage)
//   Multikey index scanning too many entries, or range is too broad.
//   Fix: add more selective prefix fields to the index.

// Problem 5: FETCH stage present when you expected a covered query
//   Check: is _id being projected? (add _id: 0 to projection)
//   Check: is any projected field missing from the index?

// ── Rejected plans (what the planner considered but didn't choose) ────────────
db.orders.explain("allPlansExecution").find({ ... })
// queryPlanner.rejectedPlans: [...]
// Shows alternative plans the planner evaluated.
// Useful to see if a better index was considered but rejected.

// ── Forcing an index hint (bypass planner for testing) ────────────────────────
db.orders.find({ tenantId: "t-123", status: "pending" })
    .hint({ tenantId: 1, status: 1 })   // Force this specific index
    .explain("executionStats")
// Use to benchmark a specific index vs the planner's choice.
// NEVER use .hint() in production without understanding the full impact.

// ── NestJS Mongoose: running explain ─────────────────────────────────────────
@Injectable()
export class OrderService {
    constructor(
        @InjectModel(Order.name)
        private readonly orderModel: Model<Order>,
    ) {}

    async diagnoseQuery(tenantId: string): Promise<any> {
        return this.orderModel
            .find({ tenantId, status: 'pending' })
            .sort({ createdAt: -1 })
            .limit(20)
            .explain('executionStats');
        // Returns the raw explain output for analysis.
    }
}
```

## Section 10: Index Intersection and Management

**Q10. What is index intersection — when does MongoDB use multiple indexes for one query?**

A: MongoDB can use two or more indexes simultaneously for a single query by intersecting their result sets. This can sometimes substitute for a compound index, but compound indexes are almost always more efficient:

```javascript
// ── Index intersection ─────────────────────────────────────────────────────────
// MongoDB may intersect two single-field indexes if it determines this is
// cheaper than a COLLSCAN (but usually worse than a compound index).

db.orders.createIndex({ status: 1 })
db.orders.createIndex({ userId: 1 })

db.orders.find({ status: "pending", userId: 42 })
// MongoDB might:
// Option A: Use idx_status → get all "pending" order IDs
//           Use idx_userId → get all user=42 order IDs
//           Intersect the two sets → documents matching both
// Option B: Use just idx_userId (more selective) → filter by status in memory
// Option C: Use just idx_status → filter by userId in memory
// Winning plan depends on selectivity statistics.

// EXPLAIN reveals intersection:
{
    stage: "AND_SORTED",   // ← Index intersection stage
    inputStages: [
        { stage: "IXSCAN", indexName: "status_1" },
        { stage: "IXSCAN", indexName: "userId_1" }
    ]
}

// Why a compound index is almost always better than intersection:
// Intersection: scan both indexes → merge → FETCH
// Compound:     scan one index directly → FETCH (or covered query)
// → Compound: one index traversal. Intersection: two index traversals + merge.
// → Compound index is ~2x faster in most cases.
// → Intersection is a fallback when the perfect compound index doesn't exist.

// ── Index management best practices ───────────────────────────────────────────

// Finding unused indexes (check $indexStats after steady-state traffic):
db.orders.aggregate([
    { $indexStats: {} },
    { $match: { "accesses.ops": { $lt: 10 } } },   // Less than 10 uses
    { $project: { name: 1, "accesses.ops": 1, key: 1 } }
])
// → Candidates for removal. Run for at least 1 week (traffic patterns vary).

// Finding slow queries (enable profiler):
db.setProfilingLevel(1, { slowms: 100 })  // Profile queries > 100ms
db.system.profile.find().sort({ ts: -1 }).limit(10)
// → Shows slow queries with their query plans.
// → Look for COLLSCAN or high totalDocsExamined.

// Rebuilding an index (drop + recreate):
db.orders.dropIndex("userId_1")
db.orders.createIndex({ userId: 1 }, { name: "idx_orders_userId" })
// Named indexes are easier to manage than auto-named ones.

// Rolling index build on replica sets (zero downtime):
// 1. Build index on SECONDARY (goes into standby state for index build):
//    rs.secondaries().forEach(s => s.getDB("myapp").orders.createIndex({ userId: 1 }))
// 2. Stepdown primary: rs.stepDown()
// 3. The former primary becomes secondary — build index there too.
// 4. Stepdown again to restore original primary.
// Result: index built without blocking primary writes at any point.
// MongoDB 4.4+: the above is less necessary since builds are non-blocking.
```

## Section 11: NestJS and Mongoose Integration

**Q11. How do you declare all index types in a NestJS Mongoose schema — what are the patterns for complex index configurations?**

A: Mongoose offers three levels of index declaration: field-level (`@Prop`), schema-level (`.index()`), and model-level. Complex indexes — compound, text, geospatial, TTL, partial — always require schema-level or migration-level declarations:

```typescript
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
import { Document, Schema as MongooseSchema } from 'mongoose';

// ── Complete schema with all index types ──────────────────────────────────────
@Schema({
    timestamps: true,   // Auto-adds createdAt and updatedAt Date fields
    collection: 'orders',
})
export class Order extends Document {
    @Prop({ required: true })
    tenantId: string;

    @Prop({ required: true, index: true })  // Single field index
    userId: number;

    @Prop({ required: true })
    status: string;   // Will be part of compound index (declared below)

    @Prop({ required: true })
    total: number;

    @Prop({ type: [String] })
    tags: string[];   // Multikey index declared below

    @Prop({
        type: {
            type: String,
            enum: ['Point'],
        },
        coordinates: { type: [Number] },
    })
    deliveryLocation: { type: string; coordinates: number[] };

    @Prop({ required: true })
    notes: string;   // Text index declared below

    // TTL field — declared with expires in @Prop or schema.index:
    @Prop({ type: Date })
    expiresAt: Date;  // TTL index: expireAfterSeconds: 0 → delete at this time

    createdAt: Date;  // from timestamps: true
    updatedAt: Date;
}

export const OrderSchema = SchemaFactory.createForClass(Order);

// ── Schema-level index declarations ──────────────────────────────────────────

// 1. Compound index (ESR rule: tenantId equity, createdAt sort, total range):
OrderSchema.index(
    { tenantId: 1, status: 1, createdAt: -1, total: 1 },
    { name: 'idx_orders_tenant_status_date_total' }
);

// 2. Partial index (only active orders):
OrderSchema.index(
    { userId: 1, createdAt: -1 },
    {
        partialFilterExpression: { status: { $in: ['pending', 'processing'] } },
        name: 'idx_active_orders_by_user',
    }
);

// 3. Text index (notes field for full-text search):
OrderSchema.index(
    { notes: 'text', tags: 'text' },
    {
        weights: { notes: 1, tags: 3 },
        name: 'idx_orders_text',
        default_language: 'english',
    }
);

// 4. 2dsphere index (geospatial):
OrderSchema.index({ deliveryLocation: '2dsphere' }, { name: 'idx_orders_location' });

// 5. TTL index (auto-delete at expiresAt):
OrderSchema.index(
    { expiresAt: 1 },
    { expireAfterSeconds: 0, name: 'idx_orders_ttl' }
);

// 6. Unique compound index (one active order per user per day):
OrderSchema.index(
    { userId: 1, orderDate: 1 },
    { unique: true, sparse: true, name: 'idx_orders_user_date_unique' }
);

// ── Repository service using indexes correctly ────────────────────────────────
@Injectable()
export class OrderRepository {
    constructor(
        @InjectModel(Order.name)
        private readonly orderModel: Model<Order>,
    ) {}

    // Uses compound index: tenantId (E), status (E), createdAt (S), total (R)
    async findActiveOrdersAboveThreshold(
        tenantId: string,
        minTotal:  number,
        limit:     number,
    ): Promise<Order[]> {
        return this.orderModel
            .find({ tenantId, status: 'pending', total: { $gt: minTotal } })
            .sort({ createdAt: -1 })
            .limit(limit)
            .select({ tenantId: 1, userId: 1, status: 1, total: 1, createdAt: 1, _id: 0 })
            // _id: 0 + all fields in index → covered query (no FETCH stage)
            .lean()  // Return plain JS objects (faster, no Mongoose document overhead)
            .exec();
    }

    // Uses partial index: idx_active_orders_by_user
    // Query MUST include status filter matching the partialFilterExpression:
    async findUserActiveOrders(userId: number): Promise<Order[]> {
        return this.orderModel
            .find({ userId, status: { $in: ['pending', 'processing'] } })
            .sort({ createdAt: -1 })
            .lean()
            .exec();
    }

    // Full-text search: uses text index
    async searchByNotes(searchText: string): Promise<Order[]> {
        return this.orderModel
            .find({ $text: { $search: searchText } })
            .select({ score: { $meta: 'textScore' }, notes: 1, userId: 1 })
            .sort({ score: { $meta: 'textScore' } })
            .limit(20)
            .lean()
            .exec();
    }

    // Geospatial search: uses 2dsphere index
    async findNearbyOrders(
        longitude: number,
        latitude:  number,
        maxDistanceMetres: number,
    ): Promise<Order[]> {
        return this.orderModel
            .find({
                deliveryLocation: {
                    $near: {
                        $geometry: { type: 'Point', coordinates: [longitude, latitude] },
                        $maxDistance: maxDistanceMetres,
                    },
                },
            })
            .limit(50)
            .lean()
            .exec();
    }

    // Multikey search: uses multikey index on tags
    async findByTags(tags: string[]): Promise<Order[]> {
        return this.orderModel
            .find({ tags: { $all: tags } })   // Document must contain ALL specified tags
            .lean()
            .exec();
    }
}
```

## Section 12: Scenario-Based Questions

**Q12. "Queries with `$regex` are extremely slow even though there's an index on the field — what is happening and how do you fix it?"**

A: `$regex` can use an index, but only under specific conditions. The pattern's structure determines whether the regex enables an efficient prefix scan or forces a full index scan:

```javascript
// ── When $regex DOES use the index efficiently ─────────────────────────────────
// Anchored prefix regex: starts with ^ and has no special characters before a literal prefix.
db.users.createIndex({ username: 1 })

db.users.find({ username: /^alice/ })
// ✓ Uses index: the regex is an anchored prefix.
// Index scan from "alice" to "alicf" (next string after "alice" prefix).
// Equivalent to: { username: { $gte: "alice", $lt: "alicf" } }
// EXPLAIN: stage: "IXSCAN", indexBounds: { username: ["alice", "alicf") }

db.users.find({ username: /^alice/i })
// ✗ Case-insensitive prefix: cannot use B-tree efficiently.
// Index stores "Alice", "alice", "ALICE" at different positions.
// Full index scan required.
// FIX: store usernames in lowercase + use /^alice/ (exact case match).
// OR: use a collation index (see below).

// ── When $regex does NOT use the index ────────────────────────────────────────
db.users.find({ username: /alice/ })          // No ^ anchor → full index scan
db.users.find({ username: /alice$/  })        // $ anchor (suffix) → full index scan
db.users.find({ username: /al.ce/  })         // . wildcard → full index scan
db.users.find({ username: /^(alice|bob)/ })   // Alternation → may not use index

// For all these: COLLSCAN or full IXSCAN (all index entries examined).
// High totalKeysExamined / nReturned ratio in explain.

// ── Fix 1: Store indexed values in canonical form ─────────────────────────────
// Problem: case-insensitive search on name
// Instead of: db.users.find({ name: /^john/i })

// Store name in lowercase in a separate field:
db.users.insertOne({
    name: "John Smith",        // Display name
    nameLower: "john smith"    // Indexed, lowercase
})
db.users.createIndex({ nameLower: 1 })
db.users.find({ nameLower: /^john/ })  // Case-sensitive prefix → index-efficient ✓

// ── Fix 2: Collation index for case-insensitive search ────────────────────────
db.users.createIndex(
    { name: 1 },
    { collation: { locale: "en", strength: 2 } }  // strength 2 = case-insensitive
)
// Query must use the same collation:
db.users.find({ name: /^John/ }).collation({ locale: "en", strength: 2 })
// → Case-insensitive prefix scan using the collation index ✓

// ── Fix 3: Use $text search instead of $regex for contains queries ─────────────
// Instead of: db.articles.find({ content: /marathon/i })  (full scan)
// Use:        db.articles.find({ $text: { $search: "marathon" } })  (text index) ✓

// ── Fix 4: Atlas Search for complex pattern matching ──────────────────────────
// For fuzzy, wildcard, and regex on large datasets: use Atlas Search.
// Atlas Search supports efficient wildcard and regex via Lucene.
// db.articles.aggregate([
//     { $search: { wildcard: { path: "username", query: "*alice*", allowAnalyzedField: true } } }
// ])

// ── Diagnosing the regex performance issue ────────────────────────────────────
db.users.explain("executionStats").find({ username: /alice/ })
// BEFORE FIX:
// stage: "IXSCAN" (misleading — index IS used, but scanning ALL entries)
// totalKeysExamined: 1,000,000   ← entire index scanned
// nReturned: 47
// Ratio: 21,277:1 (terrible)

// AFTER FIX (anchored prefix):
db.users.explain("executionStats").find({ username: /^alice/ })
// stage: "IXSCAN"
// totalKeysExamined: 52
// nReturned: 47
// Ratio: 1.1:1 (excellent)
```

**Q13. "Design the complete index strategy for a location-based restaurant search API with filtering, text search, and pagination."**

A: A real-world geo+filter+text search requires layering geospatial, compound, and text indexes with careful thought about query ordering, ESR rule, and the limitations of combining geo with other index types:

```javascript
// ── Schema design ─────────────────────────────────────────────────────────────
db.createCollection("restaurants", {
    validator: {
        $jsonSchema: {
            required: ["name", "cuisine", "location", "rating", "priceLevel", "isOpen"],
            properties: {
                name:       { bsonType: "string" },
                cuisine:    { bsonType: "string" },
                tags:       { bsonType: "array", items: { bsonType: "string" } },
                location:   {
                    bsonType: "object",
                    required: ["type", "coordinates"],
                    properties: {
                        type:        { enum: ["Point"] },
                        coordinates: { bsonType: "array" }
                    }
                },
                rating:     { bsonType: "double", minimum: 0, maximum: 5 },
                priceLevel: { bsonType: "int", minimum: 1, maximum: 4 },
                isOpen:     { bsonType: "bool" },
                expiresAt:  { bsonType: "date" }
            }
        }
    }
})

// ── Query patterns to support ─────────────────────────────────────────────────
// Pattern 1 (60%): Nearby restaurants, filtered by cuisine
//   find({ cuisine, location: $near { maxDistance }, isOpen: true }).sort(distance).limit(20)

// Pattern 2 (20%): Highly-rated restaurants in a city polygon
//   find({ location: $geoWithin { polygon }, rating: $gte, priceLevel: $lte })

// Pattern 3 (15%): Full-text name/description search + location filter
//   find({ $text: "sushi", location: $near ... })

// Pattern 4 (5%):  Admin: all restaurants sorted by rating descending

// ── Index design ──────────────────────────────────────────────────────────────

// Index 1: Primary geo index for Pattern 1 + 2 (compound 2dsphere)
db.restaurants.createIndex(
    { cuisine: 1, location: "2dsphere" },
    { name: "idx_restaurants_cuisine_geo" }
)
// Pattern 1: cuisine (E) + geo $near ✓
// Pattern 2: geo $geoWithin (works, cuisine optional prefix)
// Note: MongoDB requires the 2dsphere field to not have a range bound in compound geo indexes.

// Index 2: Rating + price level filter (for Pattern 2 refinement)
db.restaurants.createIndex(
    { cuisine: 1, rating: -1, priceLevel: 1 },
    { name: "idx_restaurants_cuisine_rating_price" }
)
// Pattern 2: cuisine (E) → rating (S, sort by rating) → priceLevel (R)
// ESR: cuisine=equality, rating=sort(-1 = highest first), priceLevel=range

// Index 3: Text search (for Pattern 3)
db.restaurants.createIndex(
    { cuisine: 1, name: "text", description: "text" },
    {
        weights: { name: 10, description: 1 },
        name: "idx_restaurants_text"
    }
)
// Compound text with cuisine prefix enables per-cuisine text search.

// Index 4: TTL for temporary restaurant listings (e.g., pop-up restaurants)
db.restaurants.createIndex(
    { expiresAt: 1 },
    { expireAfterSeconds: 0, name: "idx_restaurants_ttl", sparse: true }
)
// sparse: true — only documents with expiresAt are indexed.
// Permanent restaurants (no expiresAt) are not in this index → not deleted by TTL.

// Index 5: isOpen partial index (only open restaurants — 70% of documents)
db.restaurants.createIndex(
    { location: "2dsphere" },
    {
        partialFilterExpression: { isOpen: true },
        name: "idx_restaurants_open_geo"
    }
)
// For the common query: find open restaurants near me.
// 30% smaller than a full geo index.

// ── Query implementations ──────────────────────────────────────────────────────

// Pattern 1: Nearby open restaurants by cuisine (uses $geoNear aggregation)
db.restaurants.aggregate([
    {
        $geoNear: {
            near: { type: "Point", coordinates: [longitude, latitude] },
            distanceField: "distanceMetres",
            maxDistance: 5000,
            query: {
                cuisine: "Japanese",
                isOpen:  true
            },
            spherical: true,
            limit: 20   // $geoNear has its own limit (more efficient than $limit after)
        }
    },
    {
        $project: {
            name: 1, cuisine: 1, rating: 1, priceLevel: 1,
            distanceMetres: 1, distanceKm: { $divide: ["$distanceMetres", 1000] }
        }
    }
])

// Pattern 2: Restaurants in a polygon, high-rated, affordable
db.restaurants.find({
    location: {
        $geoWithin: {
            $geometry: {
                type: "Polygon",
                coordinates: [[/* city boundary points */]]
            }
        }
    },
    cuisine:    "Italian",
    rating:     { $gte: 4.0 },
    priceLevel: { $lte: 2 }
}).sort({ rating: -1 }).limit(50)
// Uses: idx_restaurants_cuisine_geo for geo filter
// + idx_restaurants_cuisine_rating_price for rating sort and price filter
// (MongoDB may use index intersection or the planner picks the better one)

// Pattern 3: Text search for "sushi" near a location
db.restaurants.find({
    $text: { $search: "sushi" },
    cuisine: "Japanese",
    location: {
        $near: {
            $geometry: { type: "Point", coordinates: [longitude, latitude] },
            $maxDistance: 2000
        }
    }
})
// IMPORTANT: $text and $near CANNOT be combined in a single query in MongoDB.
// MongoDB error: "text index cannot be used alongside $near"
// WORKAROUND A: Use $geoWithin instead of $near (no distance sort):
db.restaurants.find({
    $text: { $search: "sushi" },
    location: { $geoWithin: { $centerSphere: [[longitude, latitude], 2000/6371000] } }
}).sort({ score: { $meta: "textScore" } })

// WORKAROUND B: Two-step query (application-level):
// Step 1: Text search → get candidate IDs
const textResults = await restaurantModel.find(
    { $text: { $search: 'sushi' } },
    { score: { $meta: 'textScore' } }
).limit(100).lean()

// Step 2: Filter candidates by distance in application:
const nearbyResults = textResults.filter(r => {
    const dist = haversineDistance(r.location.coordinates, [longitude, latitude])
    return dist <= 2000
}).sort((a, b) => b.score - a.score).slice(0, 20)

// WORKAROUND C: Atlas Search (combines text + geo in one query — production recommendation)
db.restaurants.aggregate([
    {
        $search: {
            compound: {
                must: [{ text: { query: "sushi", path: ["name", "description"] } }],
                filter: [{
                    near: {
                        origin: { type: "Point", coordinates: [longitude, latitude] },
                        pivot: 2000,
                        path: "location"
                    }
                }]
            }
        }
    }
])

// ── Index maintenance for this collection ─────────────────────────────────────
// Monitor index usage weekly:
db.restaurants.aggregate([{ $indexStats: {} }])

// Check TTL monitor is deleting expired pop-up restaurants:
db.adminCommand({ serverStatus: 1 }).metrics.ttl.deletedDocuments

// Alert on slow queries:
db.setProfilingLevel(1, { slowms: 200 })
db.system.profile.find({ ns: "myapp.restaurants" }).sort({ ts: -1 }).limit(10)
```

## Quick Reference Tables

### Index Type Selection Guide

| Requirement | Index Type | Key declaration |
|---|---|---|
| Equality / range on one field | Single field | `{ field: 1 }` |
| Multi-field filter + sort | Compound (ESR order) | `{ e1:1, e2:1, s:-1, r:1 }` |
| Array field membership | Multikey (automatic) | `{ arrayField: 1 }` |
| Full-text search | Text | `{ field: "text" }` |
| Near point / within polygon | 2dsphere | `{ field: "2dsphere" }` |
| Flat plane proximity | 2d (legacy) | `{ field: "2d" }` |
| Auto-delete after N seconds | TTL | `{ dateField: 1 }`, `expireAfterSeconds: N` |
| Auto-delete at specific time | TTL | `{ dateField: 1 }`, `expireAfterSeconds: 0` |
| Schema-less / dynamic fields | Wildcard | `{ "prefix.$**": 1 }` |
| Uniform sharding distribution | Hashed | `{ field: "hashed" }` |
| Unique with nulls allowed | Unique + Sparse | `{ field: 1 }`, `unique: true, sparse: true` |
| Partial collection indexing | Partial | `{ field: 1 }`, `partialFilterExpression: {...}` |

### ESR Rule Quick Reference

| Query component | ESR position | Reason |
|---|---|---|
| Equality (`field: value`) | First (E) | Fixes contiguous block in B-tree |
| Sort (`sort({ field: 1 })`) | Second (S) | Provides sort order within equality block |
| Range (`$gt`, `$lt`, `$in` with multiple values) | Last (R) | Range stop only affects subsequent columns |
| `$exists: true` | Treat as range | Does not fix a contiguous block |
| `$in` with one value | Treat as equality | Single value = equality |
| `$in` with multiple values | Treat as range | Multiple values = range scan |

### EXPLAIN Stage Meanings

| Stage | Meaning | Action if unexpected |
|---|---|---|
| `COLLSCAN` | Full collection scan — no index | Create an index on filter fields |
| `IXSCAN` | Index scan ✓ | Check `totalKeysExamined` / `nReturned` ratio |
| `FETCH` | Loading full docs from collection | Add projected fields to index (covered query) |
| `SORT` | In-memory sort | Move sort field before range fields (ESR) |
| `AND_SORTED` | Index intersection | Create a compound index instead |
| `TEXT` | Text index scan | Normal for `$text` queries |
| `GEO_NEAR_2DSPHERE` | Geospatial scan ✓ | Normal for `$near` / `$geoNear` |
| `LIMIT` before `SORT` | Early termination ✓ | Index order matches query sort |
| `LIMIT` after `SORT` | Late termination — all matched sorted first | Fix sort to use index order |

### Index Restrictions Summary

| Index type | Max per collection | Array limitation | Covered query | Sort support |
|---|---|---|---|---|
| Single field | Unlimited | Auto-multikey | ✓ | ✓ |
| Compound | Unlimited | ONE array field max | ✓ | ✓ (if index order matches) |
| Multikey | Unlimited | One array per compound index | ✗ | ✗ on array field |
| Text | **1** | ✗ | ✗ | Via `$meta: "textScore"` only |
| 2dsphere | Unlimited | ✗ (geo field scalar) | ✗ | ✗ |
| TTL | Unlimited (one per field) | ✗ (single field only) | ✗ | ✗ |
| Wildcard | Unlimited | ✗ | ✗ | ✗ |
| Hashed | Unlimited (one per field) | ✗ | ✗ | ✗ |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) knowing the **ESR rule precisely** — Equality fields first, Sort fields second, Range fields last — and being able to explain WHY: equality fixes a contiguous block in the B-tree, placing sort next means the index provides order for free, and placing range last means the range stop only affects itself (no subsequent columns to miss); (2) being exact about **multikey index restrictions** — only ONE array field per compound index, covered queries are impossible for multikey fields, and sorting by an array field via index is not supported; MongoDB automatically makes an index multikey when any document has an array in the indexed field; (3) knowing that **there is exactly one text index per collection** — this is a hard limit, so the text index must cover all text-searchable fields, use weights to tune relevance, and be combined with scalar prefix fields (like `tenantId`) for multi-tenant applications; (4) understanding **TTL mechanics precisely**: the TTL monitor runs every 60 seconds on the PRIMARY only, documents may live up to 60 seconds past their expiry, the indexed field must be a BSON Date (not a string), `expireAfterSeconds: 0` deletes at the exact stored date, and TTL cannot be set on compound indexes; (5) knowing the **`$text` + `$near` incompatibility** — these two operators cannot be combined in a single query, requiring either a `$geoWithin` workaround (loses distance sort), a two-step application-level approach, or MongoDB Atlas Search which supports both natively in one pipeline stage; (6) being able to read **EXPLAIN output** and identify: `COLLSCAN` (missing index), high `totalKeysExamined / nReturned` ratio (wrong column order or too-broad range), `SORT` stage (index doesn't support the sort direction), `FETCH` stage when covered query was expected (projected field missing from index), and `AND_SORTED` (index intersection — usually worse than a compound index); (7) understanding **partial indexes** — they are smaller and faster than full indexes, but the query MUST include the `partialFilterExpression` condition for the planner to choose the partial index; omitting the filter in the query causes the planner to use the full index or a collection scan; and (8) knowing that **geospatial coordinates in GeoJSON are `[longitude, latitude]`** — not latitude-first — which is the opposite of how most humans and mapping APIs express coordinates, and that failing to use the correct order produces silently wrong results (documents appear at the wrong location on the globe).
