# MongoDB Transactions (Multi-Document ACID) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the difference between MongoDB's single-document atomicity and multi-document transactions, and when did multi-document transactions arrive?**
A: MongoDB has always provided atomic operations at the single-document level — a write to one document either fully succeeds or fully fails, regardless of how many fields or embedded arrays are updated. Multi-document ACID transactions (spanning multiple documents and collections) were added in MongoDB 4.0 (2018) for replica sets and extended to sharded clusters in 4.2 (2019):

```
Single-document atomicity (always existed):
  Operation: update a loan document — change status + append to status_history
  db.loans.updateOne(
      { _id: ObjectId("L1") },
      {
          $set:  { status: "approved" },
          $push: { status_history: { status: "approved", at: new Date() } }
      }
  );
  → Atomically: both $set and $push succeed together or neither does
  → No partial state: never "status=approved but history not updated"
  → No transaction needed — document-level atomicity is free and fast

  This is why MongoDB's embedding pattern matters for correctness:
  If you embed related data (status + history), you get atomic writes for free.
  If you reference (status in loans, history in loan_history collection):
  → Two separate writes → no automatic atomicity → need a transaction

Multi-document transactions (MongoDB 4.0+):
  Span: multiple documents, multiple collections, one or more databases
  ACID guarantee: all writes in the transaction succeed or all are rolled back
  Use case: transferring money (debit one account, credit another), saga steps,
            inserting to multiple collections atomically

  const session = client.startSession();
  await session.withTransaction(async () => {
      await db.accounts.updateOne(
          { _id: fromId }, { $inc: { balance: -amount } }, { session }
      );
      await db.accounts.updateOne(
          { _id: toId },   { $inc: { balance: +amount } }, { session }
      );
      // Both succeed or both roll back — atomically
  });

Versioning timeline:
  MongoDB 4.0 (2018): multi-document transactions on replica sets
  MongoDB 4.2 (2019): multi-document transactions on sharded clusters
  MongoDB 5.0+:       distributed transactions with improved performance
  MongoDB 6.0+:       uncommitted reads in transactions (readConcern: "snapshot")

Why transactions are NOT the default approach in MongoDB:
  1. Performance cost: transactions use write conflicts + WiredTiger snapshots
     → higher latency than non-transactional writes
  2. Schema design can often eliminate the need for transactions
     → embed related data → single-document atomic write
  3. Abort and retry: transactions can abort (write conflict) → must retry
  4. Time limit: transactions must complete within 60 seconds (default) or abort
  MongoDB's philosophy: "design the schema to avoid transactions where possible;
  use transactions where correctness requires them"
```

**Q2. What ACID properties does MongoDB guarantee for multi-document transactions?**
A: MongoDB's multi-document transactions are fully ACID compliant when using the correct read/write concerns. Each property has a specific mechanism:

```javascript
// ── Atomicity ─────────────────────────────────────────────────────────────────
// All operations in a transaction commit or all are rolled back
// No partial commit is possible

const session = client.startSession();
try {
    await session.withTransaction(async () => {
        // Operation 1:
        await db.loans.insertOne(
            { _id: ObjectId(), loan_id: "LAN-001", amount: 500000, status: "approved" },
            { session }
        );
        // Operation 2:
        await db.borrowers.updateOne(
            { _id: borrowerId },
            { $inc: { active_loan_count: 1 } },
            { session }
        );
        // If operation 2 throws → operation 1 is also rolled back
        // Borrower's active_loan_count stays unchanged
        // Loan document is NOT in the loans collection
    });
} finally {
    await session.endSession();
}

// ── Consistency ───────────────────────────────────────────────────────────────
// Transaction brings database from one valid state to another
// Application-enforced constraints (e.g. balance ≥ 0) are checked by app code
// Schema validation rules apply within the transaction
// If any operation violates a unique index → entire transaction rolls back

// ── Isolation ─────────────────────────────────────────────────────────────────
// MongoDB transactions use snapshot isolation:
// Each transaction sees a consistent snapshot of the data as of transaction start
// Changes made by concurrent transactions are NOT visible until they commit
// (and even then, only in a subsequent read, not within the current transaction's snapshot)

// readConcern "snapshot" (required for full isolation):
await session.withTransaction(async () => {
    // All reads in this transaction see a consistent snapshot
    const loan = await db.loans.findOne({ _id: loanId }, { session });
    // Even if another transaction modifies this loan between now and the next read:
    const sameLoan = await db.loans.findOne({ _id: loanId }, { session });
    // sameLoan === loan in terms of data (same snapshot)
}, {
    readConcern: { level: "snapshot" },
    writeConcern: { w: "majority" }
});

// ── Durability ────────────────────────────────────────────────────────────────
// Committed transactions survive crashes when writeConcern: { w: "majority" }
// Majority write concern: primary + majority of secondaries have acknowledged the write
// Even if primary crashes immediately after commit, secondaries have the data

// Durability NOT guaranteed when:
//   writeConcern: { w: 1 } → only primary acknowledges → can lose data on primary crash
//   writeConcern: { w: 0 } → fire-and-forget → no durability guarantee

// The correct concerns for full ACID:
const transactionOptions = {
    readConcern:  { level: "snapshot" },  // consistent snapshot isolation
    writeConcern: { w: "majority" },       // durable on majority of nodes
    readPreference: "primary"              // read from primary during transaction
};
```

## Section 2: Sessions and Transaction Lifecycle

**Q3. What is a MongoDB session and why is it required for transactions?**
A: A session is a server-side context that groups related operations. Sessions track causal consistency (operations in a session are causally ordered), enable retryable writes, and are the container for transactions. Every operation inside a transaction must be associated with the same session via the `session` option — operations without the session option are NOT part of the transaction:

```javascript
// Session lifecycle:
const client = new MongoClient(uri);
const session = client.startSession();

try {
    // Session is now active — server allocates resources for it
    // (lsid: logical session ID — 16-byte UUID)
    console.log(session.id);  // { id: Binary(16 bytes) }

    await session.withTransaction(async () => {
        // Every operation MUST pass { session } option:
        await db.loans.insertOne({ ... }, { session });        // ✓ in transaction
        await db.borrowers.updateOne({ ... }, { update }, { session }); // ✓ in transaction

        // MISTAKE: omitting { session } — this write is NOT in the transaction!
        await db.audit_log.insertOne({ ... });  // ✗ executes immediately, NOT rolled back
    });
} finally {
    await session.endSession();
    // Session cleanup: server releases resources, closes transaction context
}

// withTransaction() handles the full lifecycle automatically:
// 1. Calls session.startTransaction(options)
// 2. Runs your async function
// 3. If function returns normally: calls session.commitTransaction()
// 4. If function throws a transient error (write conflict, network): retries automatically
// 5. If function throws a non-transient error: calls session.abortTransaction()
// 6. Re-throws any non-transient errors

// Manual transaction lifecycle (for more control):
await session.startTransaction({
    readConcern:  { level: "snapshot" },
    writeConcern: { w: "majority" }
});

try {
    await db.accounts.updateOne(
        { _id: fromId }, { $inc: { balance: -amount } }, { session }
    );
    await db.accounts.updateOne(
        { _id: toId }, { $inc: { balance: +amount } }, { session }
    );

    await session.commitTransaction();
} catch (err) {
    await session.abortTransaction();
    throw err;
} finally {
    await session.endSession();
}

// Causal consistency within a session (even outside transactions):
// Operations in a session are causally consistent:
// If you write with w:"majority" then read, you will always see your own write
// Even if read goes to a secondary that is slightly behind
// The session tracks an "operation time" and sends it with reads
// Mongod/mongos waits until it has replicated up to that time before serving the read
```

**Q4. What are transient transaction errors and how do you implement correct retry logic?**
A: Transactions can abort for two classes of reasons — transient errors (temporary, worth retrying) and persistent errors (logic/data errors, not worth retrying). Conflating the two and retrying everything causes infinite loops; not retrying transient errors causes unnecessary failures:

```javascript
// Transient error codes (safe to retry the whole transaction):
// TransientTransactionError label: added to errors that are safe to retry
//   - WriteConflict (112): two transactions wrote to the same document
//   - SnapshotUnavailable (246): snapshot too old (transaction ran too long)
//   - NoSuchTransaction (251): transaction expired or was killed
//   - Network errors: connection reset, timeout during the transaction

// UnknownTransactionCommitResult label: commit response uncertain (retry commit only)
//   - Network error during commitTransaction
//   - Server may or may not have committed — retry the commit (not the whole transaction)

// withTransaction() handles BOTH error types automatically:
await session.withTransaction(async () => {
    // ... your operations
});
// withTransaction() retries the entire callback on TransientTransactionError
// withTransaction() retries only commitTransaction on UnknownTransactionCommitResult

// Manual retry logic (if not using withTransaction):
async function runWithRetry<T>(
    session: ClientSession,
    fn: (session: ClientSession) => Promise<T>,
    maxRetries = 3
): Promise<T> {
    for (let attempt = 0; attempt <= maxRetries; attempt++) {
        try {
            await session.startTransaction({
                readConcern:  { level: "snapshot" },
                writeConcern: { w: "majority" }
            });

            const result = await fn(session);
            await session.commitTransaction();
            return result;

        } catch (err: any) {
            await session.abortTransaction();

            // Transient: retry the whole transaction
            if (err.hasErrorLabel('TransientTransactionError') && attempt < maxRetries) {
                const delay = Math.min(100 * 2 ** attempt, 2000);
                await sleep(delay);
                continue;
            }

            // Unknown commit result: retry ONLY the commit (do not re-run operations)
            // withTransaction() handles this — in manual mode, re-call commitTransaction:
            if (err.hasErrorLabel('UnknownTransactionCommitResult')) {
                // The transaction may have committed — check before deciding to retry
                // (checking requires querying with the session's recovery token)
                // Simplest: just throw and let the caller handle idempotency
            }

            // Persistent error: don't retry
            throw err;
        }
    }
    throw new Error(`Transaction failed after ${maxRetries} retries`);
}

// Usage:
const session = client.startSession();
try {
    await runWithRetry(session, async (session) => {
        await db.accounts.updateOne(
            { _id: fromId }, { $inc: { balance: -amount } }, { session }
        );
        await db.accounts.updateOne(
            { _id: toId }, { $inc: { balance: +amount } }, { session }
        );
    });
} finally {
    await session.endSession();
}

// CRITICAL: your transaction callback must be idempotent when using withTransaction()
// withTransaction() may call your callback multiple times on retry
// If your callback has side effects (HTTP calls, emails), those will run N times
// Rule: keep all side effects OUTSIDE the transaction callback
// Execute them only after the transaction commits successfully:
let emailData;
await session.withTransaction(async () => {
    const result = await db.loans.findOneAndUpdate(
        { _id: loanId, status: "approved" },
        { $set: { status: "disbursed", disbursed_at: new Date() } },
        { returnDocument: "after", session }
    );
    emailData = { to: result.value.borrower_email, amount: result.value.amount };
    // Don't send email HERE — transaction may retry
});
// Send email AFTER transaction confirmed:
await emailService.send(emailData);
```

## Section 3: Read and Write Concerns in Transactions

**Q5. What read and write concerns are valid inside transactions and what do they guarantee?**
A: Transaction-level read and write concerns are set when starting the transaction and apply to all operations within it. They cannot be overridden per-operation inside the transaction. The choice of concerns determines the isolation level and durability guarantee:

```javascript
// Valid readConcern levels in transactions:
// "local":    reads from local copy (default outside transactions)
//             In transaction: reads may return data that could be rolled back on crash
//             Lowest latency, least durability
// "majority": reads data acknowledged by majority of replica set
//             Not supported as a transaction readConcern in all MongoDB versions
// "snapshot": reads a consistent snapshot as of transaction start time
//             The most isolated — equivalent to SERIALIZABLE for reads within transaction
//             Required for true repeatable read semantics within a transaction

// Valid writeConcern levels in transactions:
// { w: 0 }:         fire-and-forget (no durability — NEVER use in transactions)
// { w: 1 }:         primary acknowledged (lost if primary crashes before replication)
// { w: "majority" }: majority acknowledged (survives primary crash)
//                   REQUIRED for durable transactions

// Recommended transaction options:
const txnOptions = {
    readConcern:  { level: "snapshot" },   // consistent reads, no stale data
    writeConcern: { w: "majority" },        // durable on commit
    readPreference: "primary"               // reads must go to primary in transactions
};

// readPreference in transactions:
// ONLY "primary" is supported in transactions
// Reading from secondaries in a transaction is NOT allowed
// Reason: secondaries may be behind the primary's snapshot → consistency violation
// This means transactions increase load on the primary

// What "snapshot" readConcern means mechanically:
// Transaction start → WiredTiger assigns a global snapshot timestamp T
// All reads in the transaction see data as of timestamp T
// Concurrent writes that commit AFTER T are invisible to this transaction
// If this transaction tries to write to data that was written after T by another transaction:
//   → Write conflict → transaction aborts with TransientTransactionError

// Read concerns and phantom reads:
// readConcern "snapshot" prevents phantom reads within a transaction:
await session.withTransaction(async () => {
    // First read:
    const count1 = await db.loans.countDocuments(
        { borrower_id: borrowerId, status: "active" },
        { session }
    );
    // → Returns 3

    // Another transaction inserts a new active loan for this borrower and commits

    // Second read (same snapshot):
    const count2 = await db.loans.countDocuments(
        { borrower_id: borrowerId, status: "active" },
        { session }
    );
    // → Still returns 3 (snapshot isolation: new doc invisible to this transaction)
    // This prevents phantom reads — count is consistent within the transaction
}, txnOptions);

// Causally consistent reads between transactions (not within):
// After a transaction commits with w:"majority":
// Subsequent reads in a causally consistent session will see the committed data
// Even if routed to a secondary that hasn't caught up yet
// (the session's operationTime ensures the secondary waits to return data)
```

## Section 4: Performance Characteristics and Limits

**Q6. What are the performance costs of MongoDB transactions and what limits must you know?**
A: Transactions in MongoDB carry measurable overhead compared to single-document operations. Understanding the sources of overhead and the hard limits is essential for designing systems that use transactions correctly:

```
Performance overhead sources:

  1. WiredTiger snapshot management:
     Every transaction holds a snapshot for its duration
     Long-running transactions hold back the oldest snapshot MongoDB can clean up
     → Increases WiredTiger cache pressure
     → Other operations may slow as the cache fills with old versions

  2. Write conflict detection:
     If two transactions write to the same document:
     The second one gets: WriteConflict error (112)
     Must retry → latency doubles on conflict
     High-contention documents → many retries → unpredictable latency

  3. Oplog entries:
     Transaction operations are batched and written to oplog on commit
     Large transactions → large oplog entries → replication lag for secondaries
     Secondaries must apply the entire transaction atomically → replay delay

  4. Lock acquisition:
     MongoDB uses document-level locking (not table-level)
     Within a transaction: locks are held until commit (not released after each op)
     Two transactions accessing the same documents → one blocks

Hard limits (MongoDB default configuration):

  Limit                          │ Default    │ Configuration
  ───────────────────────────────┼────────────┼──────────────────────────────
  Transaction duration           │ 60 seconds │ transactionLifetimeLimitSeconds
  Write operations per txn       │ 1,000      │ Not configurable (hard limit for single commit)
  Total data size per txn        │ 16 MB      │ Not configurable
  Oplog entry size               │ 16 MB      │ Inherited from BSON limit

  If transaction exceeds 60s: automatically aborted by the server
  If >1,000 write ops: must split into multiple transactions
  If oplog entry >16MB: transaction fails (data modified is too large)

// Checking transaction performance:
db.adminCommand({ serverStatus: 1 }).transactions
// Returns:
// {
//   retriedCommits: N,          // how often commits were retried
//   totalCommitted: N,
//   totalAborted: N,
//   totalStarted: N,
//   currentActive: N,
//   currentInactive: N,
//   currentPrepared: N  // for sharded: 2-phase commit prepared count
// }

// High retriedCommits / totalAborted → write conflicts → review schema design
// Many currentActive with growing duration → long-running transactions → investigate

// Measuring transaction latency in application:
async function timedTransaction(fn: () => Promise<void>) {
    const session = client.startSession();
    const start = Date.now();
    try {
        await session.withTransaction(fn, txnOptions);
        console.log(`Transaction committed in ${Date.now() - start}ms`);
    } finally {
        await session.endSession();
    }
}

// Rules for keeping transactions fast:
// 1. Keep transactions SHORT — milliseconds, not seconds
//    Read required data BEFORE starting the transaction if possible
//    (pre-fetch reads outside the transaction, use them inside)
// 2. Minimize the number of documents touched per transaction (< 10 is ideal)
// 3. Avoid user interaction inside a transaction (never wait for user input)
// 4. Avoid network calls inside a transaction (HTTP, external APIs)
// 5. Use appropriate indexes — unindexed operations inside txn are slow AND hold snapshot longer
```

**Q7. What is the write conflict model in MongoDB transactions and how does it differ from PostgreSQL's approach?**
A: MongoDB uses optimistic concurrency control for transactions — two transactions can both read the same document, but when they try to write, only one wins and the other must abort and retry. PostgreSQL at Repeatable Read uses a similar optimistic approach (SSI), but at Read Committed it uses pessimistic locking (the second writer blocks until the first commits):

```javascript
// MongoDB write conflict scenario:
// Document: { _id: "A1", balance: 10000 }

// Transaction 1 (T1):
await session1.withTransaction(async () => {
    const doc = await db.accounts.findOne({ _id: "A1" }, { session: session1 });
    // doc.balance = 10000
    await db.accounts.updateOne(
        { _id: "A1" },
        { $set: { balance: doc.balance - 3000 } },  // → 7000
        { session: session1 }
    );
    // T1 holds write intent lock on A1
});

// Transaction 2 (T2) — concurrent with T1:
await session2.withTransaction(async () => {
    const doc = await db.accounts.findOne({ _id: "A1" }, { session: session2 });
    // doc.balance = 10000 (same snapshot as T1 — neither has committed yet)
    await db.accounts.updateOne(
        { _id: "A1" },
        { $set: { balance: doc.balance - 4000 } },  // → 6000
        { session: session2 }
    );
    // T2 tries to write to A1 — T1 already has write intent lock
    // ERROR: WriteConflict (112) — TransientTransactionError
    // T2 is aborted, must retry
});

// After T1 commits: balance = 7000
// T2 retries: reads balance = 7000, subtracts 4000 → writes 3000
// Final balance: 3000 ✓ (correct: 10000 - 3000 - 4000)

// MongoDB vs PostgreSQL conflict behavior:
//
//                    │ MongoDB (Optimistic)        │ PostgreSQL RR (Optimistic)  │ PostgreSQL RC (Pessimistic)
// ───────────────────┼─────────────────────────────┼─────────────────────────────┼──────────────────────────
// First writer       │ Acquires write lock          │ Writes, holds lock          │ Writes, holds lock
// Second writer      │ Immediate WriteConflict      │ Immediate 40001 error       │ BLOCKS until first commits
// Resolution         │ Abort + retry                │ Abort + retry               │ Second re-reads, continues
// Deadlock possible? │ No (no blocking → no cycle)  │ No (abort, not block)       │ Yes (two blockers deadlock)
// Read-write conflict│ Not tracked (only write-write)│ SSI tracks (write skew)    │ Not tracked at RC

// The important distinction:
// MongoDB: write-write conflict only (not read-write)
//   → Two transactions can both READ the same document without conflict
//   → Write skew IS possible in MongoDB transactions at default settings!
//   → Write skew example:

await session1.withTransaction(async () => {
    const count = await db.loans.countDocuments(
        { borrower_id: "B1", status: "active" },
        { session: session1 }
    );
    // count = 1 (one active loan)
    if (count < 2) {
        await db.loans.insertOne(
            { borrower_id: "B1", status: "active", amount: 50000 },
            { session: session1 }
        );
    }
});

// Concurrent T2 does the same: count = 1, inserts another
// Both commit: B1 now has 2 active loans (violated "max 1 active loan" rule)
// This is write skew — MongoDB does NOT prevent it automatically

// Fix: use findOneAndUpdate with a condition (atomic check-and-write):
await session.withTransaction(async () => {
    const result = await db.borrowers.findOneAndUpdate(
        { _id: "B1", active_loan_count: { $lt: 1 } },  // atomic condition
        { $inc: { active_loan_count: 1 } },
        { session }
    );
    if (!result.value) throw new Error("Max active loan limit reached");
    // Now insert the loan:
    await db.loans.insertOne({ borrower_id: "B1", status: "active", ... }, { session });
});
// The condition on active_loan_count is atomic — prevents write skew
```

## Section 5: Transactions in Sharded Clusters

**Q8. How do transactions work in sharded MongoDB clusters and what additional overhead is involved?**
A: Sharded cluster transactions require a two-phase commit (2PC) protocol coordinated by the mongos router. This adds a "prepare" phase before the actual commit, making sharded transactions more expensive than replica set transactions:

```
Sharded transaction flow (two-phase commit):

  Application → mongos (router)

  Phase 1: Execute operations
    mongos receives all operations in the transaction
    Sends each operation to the appropriate shard(s) based on shard key
    Each shard executes the operation locally and records to its own oplog buffer
    Locks are held on each shard

  Phase 2: Prepare
    mongos sends "prepare" command to ALL participating shards
    Each shard:
      a. Writes a "prepareTransaction" oplog entry
      b. Flushes to durable storage (ensures it can commit or abort durably)
      c. Replies "prepared" to mongos
    If any shard fails to prepare → abort all shards

  Phase 3: Commit
    mongos sends "commitTransaction" to ALL participating shards
    Each shard commits its local transaction
    mongos confirms commit to the application

  Phase 4: Cleanup
    Shards release locks
    Mongos returns success to application

Performance overhead vs replica set transactions:
  Replica set: single commit round trip
  Sharded: prepare + commit = 2 round trips to each shard + coordination
  Latency: typically 2-5× higher than replica set transaction for same operations

  // Setting commitQuorum in sharded transactions:
  // Each shard applies w:"majority" for the prepare and commit phases
  // → At minimum, primary + one secondary of each shard must acknowledge

// Minimizing cross-shard transaction overhead:
// Best case: all operations in a transaction touch documents on ONE shard
//   → mongos still does 2PC, but only with one shard → lower overhead

// Finding which shard a document is on:
db.loans.explain().find({ _id: loanId });
// Shows: winningPlan with shardName → know which shard will be hit

// Designing to minimize cross-shard transactions:
// If loan and its repayments always used together → shard both by loan_id
// → All operations for one loan hit the same shard
// → "Cross-shard" transaction actually becomes single-shard (lower overhead)
db.loans.createIndex({ loan_id: 1 });
sh.shardCollection("mydb.loans", { loan_id: 1 });
sh.shardCollection("mydb.repayments", { loan_id: 1 });
// loan_id="LAN-001" → same chunk on shard1 for both collections
// Transaction updating loan + inserting repayment → single shard → minimal overhead

// Monitoring sharded transaction state:
db.adminCommand({ currentOp: true, $all: true }).inprog.filter(
    op => op.transaction !== undefined
);
// Shows: participating shards, transaction state (Active/Committed/Aborted/Prepared)

// Config server's role in sharded transactions:
// The config server stores the cluster's catalog (shard key ranges, chunk assignments)
// Transactions do NOT go through the config server for data operations
// Config server is only consulted for routing decisions (before the transaction starts)
```

## Section 6: Practical Patterns

**Q9. What is the "transactional outbox" pattern and how does it solve the dual-write problem with MongoDB transactions?**
A: The dual-write problem occurs when you need to atomically write to MongoDB AND publish a message to Kafka/RabbitMQ/SNS. Since you cannot include an external message broker in a MongoDB transaction, you risk a partial failure where the database write succeeds but the message is never sent (or vice versa). The transactional outbox pattern solves this:

```javascript
// The problem:
async function disburseLoan(loanId, amount) {
    // Step 1: Update MongoDB
    await db.loans.updateOne(
        { _id: loanId },
        { $set: { status: "disbursed", disbursed_at: new Date() } }
    );
    // 💥 Server crashes here → loan is "disbursed" in DB but Kafka message never sent
    // → Downstream services (SMS, email, ledger) never know about the disbursement

    // Step 2: Publish to Kafka (outside MongoDB transaction)
    await kafkaProducer.send({ topic: "loan-events", messages: [{ ... }] });
}

// The transactional outbox pattern:
// Instead of sending to Kafka directly, write a message to an "outbox" collection
// in the SAME MongoDB transaction as the business data write.
// A separate "relay" process reads from outbox and publishes to Kafka.

// outbox collection schema:
// {
//   _id: ObjectId,
//   aggregate_id: ObjectId,   // the entity this event is about (loanId)
//   aggregate_type: string,   // "loan"
//   event_type: string,       // "loan_disbursed"
//   payload: object,          // event data
//   created_at: Date,
//   published: boolean,       // has the relay published this?
//   published_at: Date
// }

async function disburseLoan(loanId: ObjectId, amount: Decimal128) {
    const session = client.startSession();
    try {
        await session.withTransaction(async () => {
            // Business data write:
            await db.loans.updateOne(
                { _id: loanId },
                {
                    $set: {
                        status: "disbursed",
                        disbursed_at: new Date(),
                        disbursed_amount: amount
                    }
                },
                { session }
            );

            // Outbox write — SAME transaction:
            await db.outbox.insertOne({
                aggregate_id:   loanId,
                aggregate_type: "loan",
                event_type:     "loan_disbursed",
                payload: {
                    loan_id:      loanId,
                    amount:       amount,
                    disbursed_at: new Date()
                },
                created_at:  new Date(),
                published:   false,
                published_at: null
            }, { session });
            // If ANY operation fails → both roll back → no orphaned outbox messages
        }, txnOptions);
    } finally {
        await session.endSession();
    }
    // After transaction: loan is "disbursed" AND outbox has the message → atomic
}

// Relay process (separate service, reads outbox → publishes to Kafka):
async function relayOutboxMessages() {
    while (true) {
        // Find unpublished messages:
        const messages = await db.outbox.find(
            { published: false },
            { sort: { created_at: 1 }, limit: 100 }
        ).toArray();

        for (const msg of messages) {
            try {
                // Publish to Kafka (at-least-once delivery):
                await kafkaProducer.send({
                    topic: `${msg.aggregate_type}-events`,
                    messages: [{
                        key:   msg.aggregate_id.toString(),
                        value: JSON.stringify(msg.payload)
                    }]
                });

                // Mark as published (single-document update — no transaction needed):
                await db.outbox.updateOne(
                    { _id: msg._id, published: false },  // idempotent check
                    { $set: { published: true, published_at: new Date() } }
                );
            } catch (err) {
                // Kafka publish failed → leave published:false → will retry next cycle
                console.error('Failed to relay message', msg._id, err);
            }
        }

        // Optional: use MongoDB Change Streams instead of polling:
        // Change stream watches the outbox collection for new insertions
        // → near-real-time relay without polling overhead
        await sleep(100);  // poll every 100ms if not using change streams
    }
}

// Using Change Streams for the relay (more efficient than polling):
const changeStream = db.outbox.watch(
    [{ $match: { operationType: "insert", "fullDocument.published": false } }],
    { fullDocument: "updateLookup" }
);

changeStream.on("change", async (event) => {
    const msg = event.fullDocument;
    await kafkaProducer.send({ /* ... */ });
    await db.outbox.updateOne({ _id: msg._id }, { $set: { published: true } });
});
```

**Q10. How do you implement a "check-then-act" pattern safely with MongoDB transactions to prevent race conditions?**

```javascript
// Pattern: read a value, validate it, write based on the result
// Race condition without transaction: two concurrent requests both read,
// both validate, both write → double-spend / over-allocation

// Problem scenario — disbursing a loan only once:
// Without transaction:
async function disburseLoan_WRONG(loanId) {
    const loan = await db.loans.findOne({ _id: loanId });
    if (loan.status !== "approved") throw new Error("Not approved");
    // GAP: another request reads here, also sees "approved"
    await db.loans.updateOne(
        { _id: loanId },
        { $set: { status: "disbursed" } }
    );
    // Both requests disburse → duplicate disbursement
}

// ── Fix 1: findOneAndUpdate with condition (no transaction needed) ──────────
// Atomic: find the document IF it matches the condition AND update in one operation
async function disburseLoan_ATOMIC(loanId: ObjectId, amount: Decimal128) {
    const result = await db.loans.findOneAndUpdate(
        {
            _id: loanId,
            status: "approved"   // condition: only updates if currently approved
        },
        {
            $set: {
                status: "disbursed",
                disbursed_at: new Date(),
                disbursed_amount: amount
            }
        },
        { returnDocument: "after" }
    );

    if (!result.value) {
        throw new ConflictException("Loan is not in approved state or already disbursed");
    }
    return result.value;
}
// Even if two concurrent requests call this: only ONE will find status:"approved"
// The second finds status:"disbursed" → condition fails → no update → throws
// No race condition — findOneAndUpdate is atomic

// ── Fix 2: Transaction for multi-collection check-then-act ──────────────────
// When the check and the write involve different collections:
async function approveLoanWithExposureCheck(
    loanId:     ObjectId,
    borrowerId: ObjectId,
    amount:     number
) {
    const session = client.startSession();
    try {
        await session.withTransaction(async () => {
            // Check current exposure (read — snapshot isolation):
            const borrower = await db.borrowers.findOne(
                { _id: borrowerId },
                { session }
            );

            const currentExposure = borrower.total_active_exposure ?? 0;
            const MAX_EXPOSURE = 1_000_000;

            if (currentExposure + amount > MAX_EXPOSURE) {
                throw new BusinessRuleException(
                    `Exposure limit exceeded: ${currentExposure} + ${amount} > ${MAX_EXPOSURE}`
                );
            }

            // If another concurrent transaction also passed the check and committed
            // BEFORE this transaction started, our snapshot would show the updated
            // exposure → our check would catch it.
            // If they commit AFTER our snapshot but BEFORE our write → write conflict
            // → our transaction aborts → retry → second attempt sees updated exposure → rejects

            // Write: update loan status:
            await db.loans.updateOne(
                { _id: loanId, status: "submitted" },
                { $set: { status: "approved" } },
                { session }
            );

            // Write: update borrower's exposure:
            await db.borrowers.updateOne(
                { _id: borrowerId },
                { $inc: { total_active_exposure: amount } },
                { session }
            );
        }, txnOptions);
    } finally {
        await session.endSession();
    }
}

// ── Fix 3: Optimistic locking with version field ──────────────────────────────
// Alternative to transactions when you want to detect conflicts without locking:
async function updateLoanWithVersion(loanId: ObjectId, update: object, expectedVersion: number) {
    const result = await db.loans.updateOne(
        { _id: loanId, __v: expectedVersion },  // version must match
        {
            ...update,
            $inc: { __v: 1 }                     // increment version
        }
    );

    if (result.matchedCount === 0) {
        throw new ConflictException("Document was modified by another operation (version mismatch)");
    }
}
// Caller reads document, gets __v: 5
// Passes __v: 5 to updateLoanWithVersion
// If another operation modified the doc meanwhile → __v is now 6 → matchedCount: 0 → conflict
// No transaction needed for single-document optimistic locking
```

## Section 7: When NOT to Use Transactions

**Q11. When should you deliberately avoid MongoDB transactions and use alternative patterns instead?**
A: Transactions are powerful but carry overhead. There are well-established patterns in MongoDB that provide correct behavior for many common scenarios without transactions. Knowing when NOT to use a transaction separates a MongoDB expert from someone who applies SQL patterns to MongoDB:

```javascript
// ── Alternative 1: Single-document atomicity replaces the transaction ──────────
// If you embed related data, MongoDB's document-level atomicity is free and fast

// WRONG — using a transaction for what embedding solves:
await session.withTransaction(async () => {
    await db.loans.updateOne({ _id: loanId }, { $set: { status: "approved" } }, { session });
    await db.loan_status_log.insertOne({ loan_id: loanId, status: "approved", at: new Date() }, { session });
});

// CORRECT — embed status history in the loan document:
await db.loans.updateOne(
    { _id: loanId },
    {
        $set:  { status: "approved" },
        $push: { status_history: { status: "approved", at: new Date() } }
    }
);
// Atomic, no transaction, no overhead, simpler code

// ── Alternative 2: findOneAndUpdate for atomic check-and-write ─────────────────
// (shown in Q10) — for single-collection check-then-act patterns

// ── Alternative 3: Idempotent operations with unique indexes ──────────────────
// Instead of a transaction to "ensure only one disbursement":
// Create a unique index on the business key:
db.disbursements.createIndex({ loan_id: 1 }, { unique: true });

// First attempt: succeeds (unique constraint satisfied)
await db.disbursements.insertOne({ loan_id: loanId, amount, disbursed_at: new Date() });

// Second attempt (retry or race condition): fails immediately
// duplicate key error (E11000) → catch and treat as idempotent success
try {
    await db.disbursements.insertOne({ loan_id: loanId, amount, disbursed_at: new Date() });
} catch (err) {
    if (err.code === 11000) {
        // Already disbursed — idempotent, not an error
        return await db.disbursements.findOne({ loan_id: loanId });
    }
    throw err;
}

// ── Alternative 4: Two-phase write for eventual consistency ────────────────────
// For operations that can tolerate a window of inconsistency:
// Write to one collection with a "pending" flag, process, clear the flag

// Example: Transfer funds with two-phase write (no transaction):
// Phase 1: Mark transfer as pending
await db.transfers.insertOne({
    _id: transferId,
    from: fromAccountId,
    to: toAccountId,
    amount,
    status: "pending",
    created_at: new Date()
});

// Phase 2: Apply debit (idempotent: check transfer status first)
await db.accounts.updateOne(
    { _id: fromAccountId, pending_transfer_ids: { $ne: transferId } },
    {
        $inc: { balance: -amount },
        $push: { pending_transfer_ids: transferId }
    }
);

// Phase 3: Apply credit
await db.accounts.updateOne(
    { _id: toAccountId, pending_transfer_ids: { $ne: transferId } },
    {
        $inc: { balance: +amount },
        $push: { pending_transfer_ids: transferId }
    }
);

// Phase 4: Mark transfer complete
await db.transfers.updateOne(
    { _id: transferId },
    { $set: { status: "completed" } }
);
// If any step fails: background process finds "pending" transfers and retries
// Each step is idempotent (the $ne check prevents double-application)

// ── Decision table: transaction vs alternative ─────────────────────────────────
// Scenario                                    │ Use Transaction? │ Alternative
// ────────────────────────────────────────────┼──────────────────┼──────────────────────────
// Status + embedded history update             │ NO               │ Single document atomic write
// "Disburse only once" for one loan           │ NO               │ findOneAndUpdate with condition
// Prevent duplicate insertions                 │ NO               │ Unique index + catch E11000
// Debit one account + credit another           │ YES              │ Two-phase write (if ok eventual)
// Loan approval + exposure check (cross-coll) │ YES              │ -
// Insert loan + publish to Kafka              │ NO               │ Transactional Outbox pattern
// Update N related docs atomically            │ YES (if N < 10)  │ Embed the N docs instead
// Counter increment                            │ NO               │ $inc is atomic per document
```

## Section 8: Scenario-Based Questions

**Q12. "A loan disbursement service debits the company's ledger account and credits the borrower's account. Occasionally, the ledger shows a debit with no corresponding credit. Design the transaction and explain why your approach is correct."**

```javascript
// Root cause of the bug: two separate writes with no atomicity
// Debit succeeds → server crashes → credit never happens → balance discrepancy

// ── Solution 1: Multi-document transaction ────────────────────────────────────
// When both accounts are in the same MongoDB cluster:

async function disburseWithTransaction(
    loanId:       ObjectId,
    ledgerAccId:  ObjectId,
    borrowerAccId: ObjectId,
    amount:       Decimal128
): Promise<void> {
    const session = client.startSession();

    try {
        await session.withTransaction(async () => {
            // Atomic check: loan must be in approved state (not yet disbursed):
            const loan = await db.loans.findOne(
                { _id: loanId, status: "approved" },
                { session }
            );
            if (!loan) throw new BusinessError("Loan not in approved state");

            // Atomic check: sufficient funds in ledger account:
            const ledger = await db.accounts.findOne(
                { _id: ledgerAccId },
                { session }
            );
            const amountNum = parseFloat(amount.toString());
            if (parseFloat(ledger.balance.toString()) < amountNum) {
                throw new BusinessError("Insufficient funds in ledger");
            }

            // Debit ledger:
            const ledgerResult = await db.accounts.updateOne(
                {
                    _id: ledgerAccId,
                    balance: { $gte: amount }   // re-check balance atomically
                },
                { $inc: { balance: -amountNum } },
                { session }
            );
            if (ledgerResult.matchedCount === 0) {
                throw new BusinessError("Insufficient funds or concurrent modification");
            }

            // Credit borrower:
            await db.accounts.updateOne(
                { _id: borrowerAccId },
                { $inc: { balance: amountNum } },
                { session }
            );

            // Update loan status:
            await db.loans.updateOne(
                { _id: loanId, status: "approved" },  // condition prevents double-disbursement
                {
                    $set: {
                        status: "disbursed",
                        disbursed_at: new Date(),
                        disbursed_amount: amount
                    }
                },
                { session }
            );

            // Write disbursement record:
            await db.disbursements.insertOne({
                _id: new ObjectId(),
                loan_id:        loanId,
                ledger_acc_id:  ledgerAccId,
                borrower_acc_id: borrowerAccId,
                amount,
                disbursed_at:   new Date(),
                reference:      `DISB-${loanId.toString().slice(-8).toUpperCase()}`
            }, { session });

        }, {
            readConcern:  { level: "snapshot" },
            writeConcern: { w: "majority" },
            readPreference: "primary"
        });

    } finally {
        await session.endSession();
    }
}

// Why this is correct:
// 1. All 4 operations (debit + credit + loan status + disbursement record) are atomic
// 2. If ANY step fails → all roll back → no debit without credit
// 3. readConcern "snapshot" → consistent view during checks
// 4. writeConcern "majority" → durable even if primary crashes after commit
// 5. Condition on loan status ("approved") → idempotent: cannot disburse twice
// 6. Condition on balance ($gte) → prevents overdraft even with concurrent requests

// ── Solution 2: Transactional Outbox (if ledger is a separate system) ────────
// If borrower account is in an external banking system (not MongoDB):
// Cannot include external system in MongoDB transaction
// Use transactional outbox → write credit instruction to outbox in same txn as debit
// Relay service reads outbox → calls external banking API → marks published

async function disburseWithOutbox(loanId: ObjectId, amount: Decimal128) {
    const session = client.startSession();
    try {
        await session.withTransaction(async () => {
            // Debit internal ledger:
            await db.accounts.updateOne(
                { _id: ledgerAccId },
                { $inc: { balance: -parseFloat(amount.toString()) } },
                { session }
            );
            // Update loan status:
            await db.loans.updateOne(
                { _id: loanId, status: "approved" },
                { $set: { status: "disbursed", disbursed_at: new Date() } },
                { session }
            );
            // Outbox: instruction to credit external account:
            await db.outbox.insertOne({
                event_type:  "credit_borrower_account",
                payload: {
                    loan_id:           loanId.toString(),
                    amount:            amount.toString(),
                    external_bank_ref: loan.borrower_bank_account
                },
                published:   false,
                created_at:  new Date()
            }, { session });
        }, txnOptions);
    } finally {
        await session.endSession();
    }
    // Relay process publishes outbox → calls banking API → marks published
    // If banking API fails: relay retries → at-least-once delivery
    // Banking API must be idempotent (accepts retries with same loan_id)
}
```

**Q13. "Your team is debating whether to use MongoDB transactions for every operation in a financial platform to be safe. What is your position and how do you present the tradeoffs?"**

```javascript
// Position: use transactions SELECTIVELY — only where single-document atomicity
// or alternative patterns are insufficient.

// The cost of blanket transaction use:

// Benchmark comparison (rough numbers, single replica set):
// Single document write (no transaction):  ~0.5ms - 1ms
// Same write inside a transaction:         ~3ms - 8ms   (3-8× overhead)
// Reason: session round trip + snapshot management + write conflict detection

// For 1000 loan status updates/second:
// Without transactions: 1000 × 1ms = 1s total CPU time on DB
// With transactions:    1000 × 5ms = 5s total CPU time on DB
// At high throughput: transactions can saturate the primary unnecessarily

// When transactions are NECESSARY (use them):
const MUST_USE_TRANSACTION = [
    "Transfer funds between two accounts (debit + credit)",
    "Approve loan + update borrower exposure in borrowers collection",
    "Saga steps: compensating actions across multiple collections",
    "Insert order + decrement inventory in separate collections",
    "Multi-collection atomic writes where partial writes cause data corruption"
];

// When transactions are UNNECESSARY (avoid them):
const AVOID_TRANSACTION = [
    // Use single-document atomicity instead:
    "Update loan status + append to embedded status_history",
    "Update any set of fields on a single document",
    // Use findOneAndUpdate instead:
    "Check-then-act on a single document (disburse only once)",
    "Conditional updates with business logic",
    // Use unique indexes instead:
    "Prevent duplicate insertions (unique business key)",
    // Use $inc instead:
    "Increment counters atomically",
    // Use transactional outbox instead:
    "Write to MongoDB + publish to Kafka/queue"
];

// Structured approach to the decision:
function shouldUseTransaction(operation: OperationSpec): boolean {
    // Rule 1: If all writes are to a single document → NO transaction
    if (operation.documentsModified === 1) return false;

    // Rule 2: If the relationship can be embedded → NO transaction
    if (operation.canBeEmbedded) return false;

    // Rule 3: If findOneAndUpdate with condition covers it → NO transaction
    if (operation.isConditionalSingleDocWrite) return false;

    // Rule 4: If unique index + idempotency covers it → NO transaction
    if (operation.canUseUniqueIndex) return false;

    // Rule 5: Multiple documents across collections MUST be consistent → YES transaction
    if (operation.requiresCrossCollectionAtomicity) return true;

    // Rule 6: Involving external systems → NO transaction → use outbox
    if (operation.involvesExternalSystem) return false;  // use outbox instead

    return false;  // default: find the right pattern, not the transaction
}

// The schema design conversation:
// Often the right answer is: "redesign the schema so a transaction isn't needed"
// Example: if you find yourself transacting loan + status_log every operation:
// → Embed status_log in the loan document → no transaction needed
// → Application is simpler, faster, and more correct

// Final position to present to team:
// "Use transactions as the exception, not the default.
//  Design the schema first — embedding related data removes the need for most transactions.
//  Use findOneAndUpdate + conditions for check-then-act.
//  Use unique indexes for deduplication.
//  Reserve transactions for cross-collection writes where partial failure
//  would cause observable data corruption.
//  Profile before and after: a transaction that costs 5× per operation
//  can turn a 10ms API call into a 50ms API call under load."
```

## Quick Reference Table

| Property | MongoDB Transaction Mechanism | Requires |
|---|---|---|
| Atomicity | All ops commit or all roll back | `session` passed to every operation |
| Consistency | Schema validation applies within txn | `$jsonSchema` validators on collections |
| Isolation | Snapshot isolation (as of txn start) | `readConcern: { level: "snapshot" }` |
| Durability | Majority write concern | `writeConcern: { w: "majority" }` |

| Error type | Label | Action |
|---|---|---|
| Write conflict, network interruption | `TransientTransactionError` | Retry entire transaction (withTransaction does this) |
| Commit acknowledgement uncertain | `UnknownTransactionCommitResult` | Retry commit only (not the whole transaction) |
| Business logic error | Neither label | Abort, do not retry |
| Duplicate key (E11000) | Neither label | Abort, handle as idempotent or surface to user |

| Transaction limit | Default | Impact if exceeded |
|---|---|---|
| Duration | 60 seconds | Auto-abort (`transactionLifetimeLimitSeconds`) |
| Write ops per txn | 1,000 | Transaction fails; split into multiple |
| Total data size | 16 MB | Transaction fails; redesign required |
| readPreference | Primary only | Cannot read from secondaries inside txn |

| Scenario | Use Transaction? | Better Alternative |
|---|---|---|
| Status + embedded history | No | Single-document atomic write |
| Disburse only once | No | `findOneAndUpdate` with condition |
| Prevent duplicate record | No | Unique index + catch E11000 |
| DB write + Kafka publish | No | Transactional Outbox Pattern |
| Counter increment | No | `$inc` is atomic per document |
| Debit + credit two accounts | Yes | — |
| Approve loan + update exposure | Yes | — |
| Saga compensation (multi-coll) | Yes | — |

**Tip for interviews:** Five things separate strong candidates on MongoDB transactions: (1) stating clearly that **single-document atomicity is free and covers the majority of MongoDB use cases** — the correct mental model is "design the schema so you don't need a transaction, then add one only when cross-collection atomicity is truly required", not "use transactions for safety everywhere"; (2) knowing the **two error label types and their distinct retry behaviors** — `TransientTransactionError` means retry the entire callback; `UnknownTransactionCommitResult` means retry only the commit (the operations already ran and may have committed); confusing these leads to double-writes or unnecessary failures, and `withTransaction()` handles both automatically which is why it should be preferred over the manual `startTransaction`/`commitTransaction` pattern; (3) explaining **write skew and that MongoDB's snapshot isolation does not prevent it** (Q7) — two transactions can both read a value, both pass a business check, and both write in a way that together violates an invariant, because MongoDB only detects write-write conflicts (not read-write dependencies); the fix is to encode the check atomically in the write condition using `findOneAndUpdate`; (4) knowing the **transactional outbox pattern** (Q9) — for the extremely common case of "write to MongoDB and publish to a message broker", a transaction cannot include the broker, and the correct pattern is to write an outbox document in the same transaction as the business data, then have a relay process publish it; and (5) being able to articulate the **3-8× performance overhead** of transactions and when it matters (Q6, Q13) — a 1ms single-document write becoming a 5ms transactional write is irrelevant at 10 req/s but becomes the bottleneck at 1000 req/s, which is why schema design that avoids transactions is not premature optimization but a genuine architectural decision.
