# MongoDB Sharding: Shard Key Selection, Hashed vs Ranged Sharding, Chunk Migrations
## Interview Q&A (5 YOE Level)

---

## Section 1: Why Sharding Exists

**Q1. What problem does sharding solve — how does it differ from replication, and what does the architecture look like?**

A: Replication copies all data to every node (horizontal read scaling, not write scaling). Sharding partitions data across nodes so each shard holds a distinct subset — enabling horizontal scaling of both reads AND writes beyond what a single machine can handle:

```
Replication (all nodes hold ALL data):

  Write → Primary ──────────────────────────────────────────────────────────────
              │ replicate everything                                             │
              ├──► Replica A (full copy) ── read                               │
              └──► Replica B (full copy) ── read                               │
  Problem: write throughput limited by one primary; data size limited by one server.

Sharding (each shard holds a SUBSET of data):

  ┌─────────────────────────────────────────────────────────────────────────────┐
  │                         Client Application                                  │
  └─────────────────────────────┬───────────────────────────────────────────────┘
                                 │
  ┌──────────────────────────────▼────────────────────────────────────────────┐
  │                      mongos (Query Router)                                 │
  │  Routes queries to the correct shard(s) based on the shard key.           │
  │  Merges results from multiple shards if needed.                            │
  │  Stateless — can run many mongos instances.                                │
  └───────────────┬───────────────────────┬───────────────────────────────────┘
                  │                       │                       │
  ┌───────────────▼──┐        ┌──────────▼──────┐    ┌──────────▼──────────┐
  │  Shard 1         │        │  Shard 2         │    │  Shard 3            │
  │  (replica set)   │        │  (replica set)   │    │  (replica set)      │
  │                  │        │                  │    │                     │
  │  userId: 1-33k   │        │  userId: 33k-67k │    │  userId: 67k-100k   │
  │  Orders for      │        │  Orders for      │    │  Orders for         │
  │  these users     │        │  these users     │    │  these users        │
  │  ≈ 1TB data      │        │  ≈ 1TB data      │    │  ≈ 1TB data         │
  └──────────────────┘        └─────────────────┘    └─────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────────────┐
  │                    Config Servers (replica set, 3 nodes)                    │
  │  Stores cluster metadata: which chunk lives on which shard.                 │
  │  Every mongos reads config server to know routing rules.                    │
  └─────────────────────────────────────────────────────────────────────────────┘

Key properties of a sharded cluster:
  • Total data = sum across all shards (each shard has 1/N of the data).
  • Write throughput = sum across all shard primaries.
  • Read throughput = depends on whether queries are targeted or scatter-gather.
  • Each shard is itself a replica set (HA within the shard).
  • mongos is the only entry point — applications never talk to shards directly.
```

```javascript
// ── When to shard ─────────────────────────────────────────────────────────────
// DON'T shard prematurely. Sharding adds operational complexity.
// Shard when you hit one of these limits on a single replica set:
//
// 1. Storage limit: collection approaches server disk capacity (>1-2 TB per node)
// 2. RAM pressure: working set (frequently accessed data) no longer fits in RAM
// 3. Write bottleneck: primary CPU/disk is saturated despite index optimisation
// 4. Specific compliance need: data must reside in a geographic region (zone sharding)

// Monitoring signals that indicate sharding is needed:
db.serverStatus().connections     // High connection count → mongos can distribute
db.serverStatus().opcounters      // writes/s approaching disk saturation
db.serverStatus().mem.resident    // Working set > available RAM → cache misses
db.serverStatus().wiredTiger.cache["bytes currently in the cache"]

// ── Enabling sharding (mongos shell) ─────────────────────────────────────────
sh.enableSharding("myapp")           // Enable sharding for the database
sh.shardCollection(                   // Shard a specific collection
    "myapp.orders",
    { userId: "hashed" }             // Shard key definition
)
sh.status()                          // Show cluster topology and chunk distribution
```

## Section 2: Shard Key Selection

**Q2. What makes a good shard key — what are the four properties that must be evaluated and how do they interact?**

A: The shard key is the single most consequential architectural decision in a sharded MongoDB deployment. A bad shard key cannot be changed without significant downtime (pre-MongoDB 5.0) and causes hotspots, jumbo chunks, and scatter-gather queries:

```
The four shard key properties:

┌────────────────────────────────────────────────────────────────────────────┐
│ Property 1: CARDINALITY                                                    │
│ Number of distinct values in the shard key.                                │
│ Determines the maximum number of chunks (and thus shards) possible.        │
│                                                                            │
│ LOW cardinality (bad): status = "pending"|"shipped"|"cancelled" (3 values) │
│   → Maximum 3 chunks → maximum 3 shards, regardless of collection size.    │
│   → Adding a 4th shard: impossible to balance (only 3 chunks to split).    │
│                                                                            │
│ HIGH cardinality (good): userId (millions of distinct values)              │
│   → Unlimited chunks, unlimited shards possible.                           │
│   → The collection can grow horizontally without limit.                    │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ Property 2: WRITE DISTRIBUTION                                             │
│ Whether new writes are spread across all shards or concentrated on one.    │
│                                                                            │
│ MONOTONICALLY INCREASING (bad): _id (ObjectId), createdAt, autoincrement  │
│   → All new documents have the highest key value.                          │
│   → All writes go to the shard holding the highest-key chunk.              │
│   → HOTSPOT: one shard gets all writes, others are idle.                   │
│                                                                            │
│ RANDOM DISTRIBUTION (good): hashed shard key, UUID                        │
│   → Writes spread uniformly across all shards.                             │
│   → All shard primaries equally utilized.                                  │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ Property 3: QUERY ISOLATION (targeted vs scatter-gather)                   │
│ Whether a query with the shard key goes to ONE shard or ALL shards.        │
│                                                                            │
│ TARGETED (good): query includes the shard key                              │
│   → mongos routes to exactly one shard → fast, efficient                  │
│   db.orders.find({ userId: 42, ... })  // userId is shard key → one shard  │
│                                                                            │
│ SCATTER-GATHER (bad): query does NOT include the shard key                 │
│   → mongos sends query to ALL shards, merges results → slow, expensive    │
│   db.orders.find({ status: "pending" })  // No shard key → all shards     │
│   → Latency = slowest shard response time.                                 │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ Property 4: FREQUENCY (hotspot within the key space)                      │
│ Whether any shard key value is disproportionately common.                  │
│                                                                            │
│ HIGH FREQUENCY (bad): 80% of documents share key value "userId=1"         │
│   → One chunk (or a few chunks) holds most of the data.                   │
│   → That shard gets most writes AND reads.                                 │
│   → Jumbo chunks form (chunk too large to split, cannot be migrated).      │
│                                                                            │
│ UNIFORM FREQUENCY (good): each userId appears in ~equal proportion         │
│   → Chunks are roughly equal in size → balanced shards.                   │
└────────────────────────────────────────────────────────────────────────────┘
```

```javascript
// ── Evaluating shard key candidates ───────────────────────────────────────────

// Candidate 1: _id (ObjectId)
// Cardinality: ✓ Very high (unique per document)
// Write distribution: ✗ Monotonically increasing → all writes to one shard
// Query isolation: ✓ Most queries include _id
// Frequency: ✓ Each value appears once
// Verdict: POOR for write distribution. Use hashed _id instead.

// Candidate 2: { _id: "hashed" }
// Cardinality: ✓ Very high (hash distributes unique values uniformly)
// Write distribution: ✓ Hash randomises → uniform across shards
// Query isolation: ✓ Equality on _id → targeted
// Frequency: ✓ Uniform (hash distributes evenly)
// Verdict: GOOD for write-heavy collections without range query needs.
// Trade-off: range queries on _id are not efficient (hash breaks ordering).

// Candidate 3: { userId: 1 }
// Cardinality: ✓ High (millions of users)
// Write distribution: ✗ Depends on userId assignment pattern
//   If userId is auto-incrementing: monotonically increasing → hotspot.
//   If userId is UUID/random: uniform → good.
// Query isolation: ✓ Most app queries filter by userId
// Frequency: May have hotspots (power users with millions of documents)
// Verdict: CONDITIONAL — good if userId is random/UUID and queries are user-scoped.

// Candidate 4: { tenantId: 1, userId: 1 }  (compound shard key)
// Cardinality: ✓ tenantId × userId combinations → very high
// Write distribution: ✓ Distributed across tenant+user combinations
// Query isolation: ✓ Queries with tenantId alone use the prefix → semi-targeted
//   (mongos routes to shards holding that tenantId's chunks, not just one chunk)
// Frequency: ✗ Large tenants may have hotspot (many documents per tenantId)
// Verdict: GOOD for multi-tenant SaaS with many tenants.
// Note: tenantId alone is not sufficient (low cardinality); compound key fixes this.

// Candidate 5: { status: 1 }
// Cardinality: ✗ VERY LOW (5 distinct values) → max 5 chunks → max 5 shards
// Write distribution: ✗ All new "pending" orders go to one chunk
// Verdict: NEVER use a low-cardinality field as the sole shard key.

// ── Measuring shard key cardinality ───────────────────────────────────────────
db.orders.aggregate([
    { $group: { _id: "$userId" } },    // Count distinct userId values
    { $count: "distinctValues" }
])
// → { distinctValues: 847293 }  ← High cardinality ✓

// Check frequency distribution (identify power users):
db.orders.aggregate([
    { $group: { _id: "$userId", count: { $sum: 1 } } },
    { $sort: { count: -1 } },
    { $limit: 10 }
])
// → { _id: 1, count: 842391 }  ← User 1 has 842k documents → HOTSPOT risk
// → { _id: 2, count: 1823 }
// → Most users: ~20 orders each
// Verdict: userId alone has frequency hotspot for user 1.
// Fix: compound key { userId: 1, orderId: 1 } or hashed key.
```

**Q3. What is a compound shard key — when does it outperform a single-field shard key?**

A: A compound shard key uses two or more fields as the sharding key. It solves two problems simultaneously: it can increase cardinality beyond what a single field provides, and it can route queries that always include the first field to a subset of shards:

```javascript
// ── When a single field is insufficient ───────────────────────────────────────

// Problem: Single-field shard key on tenantId
// Cardinality: 100 tenants → maximum 100 chunks → maximum 100 shards.
// Frequency: large tenants (enterprise customers) create many documents → hotspot.
// If one tenant has 70% of documents: one shard holds 70% of data.

sh.shardCollection("myapp.events", { tenantId: 1 })
// → Works until you need > 100 shards or a large tenant dominates.

// ── Compound shard key solution ────────────────────────────────────────────────
sh.shardCollection("myapp.events", { tenantId: 1, userId: 1 })
// Cardinality: 100 tenants × 50,000 users = 5,000,000 combinations → very high ✓
// Frequency: large tenants are now split across their users → distributed ✓
// Query isolation:
//   { tenantId: "t-big-corp" } → prefix match → targets tenantId's shards ✓
//   { tenantId: "t-big-corp", userId: 42 } → exact match → one shard ✓
//   { userId: 42 } → missing prefix → SCATTER-GATHER ✗

// ── Compound shard key with hashed second field ────────────────────────────────
// Problem: even with compound key, if userId is sequential (auto-increment),
// writes within a tenant go to one shard.
sh.shardCollection("myapp.events", { tenantId: 1, _id: "hashed" })
// tenantId: groups events by tenant (targeted queries on tenantId work) ✓
// _id hashed: randomises within each tenant's key space ✓
// Write distribution: new events for any tenant spread across shards ✓
// Query: { tenantId, _id } → targeted ✓
// Query: { tenantId } → prefix → semi-targeted (all tenantId's shards) ✓

// ── Understanding prefix targeting ────────────────────────────────────────────
// Compound shard key { tenantId: 1, userId: 1 } creates chunks like:
// Chunk 1: { tenantId: "a", userId: MinKey } → { tenantId: "a", userId: 500 }  → Shard 1
// Chunk 2: { tenantId: "a", userId: 500    } → { tenantId: "b", userId: 100 }  → Shard 2
// Chunk 3: { tenantId: "b", userId: 100    } → { tenantId: "b", userId: 900 }  → Shard 3
// Chunk 4: { tenantId: "b", userId: 900    } → { tenantId: "c", userId: MaxKey }→ Shard 1

// Query: { tenantId: "b" }
// → mongos knows tenantId="b" data is in chunks 2, 3, 4 on shards 1, 2, 3.
// → Sends query to shards 1, 2, 3 only (not all shards if there are 10 shards). ✓
// → Partial scatter-gather: better than full scatter, worse than single-shard.

// ── Checking the current shard key ────────────────────────────────────────────
db.getSiblingDB("config").collections.findOne({ _id: "myapp.orders" })
// {
//   _id: "myapp.orders",
//   key: { userId: 1, _id: 1 },    ← shard key
//   unique: false,
//   lastmodEpoch: ObjectId("..."),
//   ...
// }

// ── Changing the shard key (MongoDB 5.0+) ─────────────────────────────────────
// Before MongoDB 5.0: impossible without resharding (dump, drop, reload).
// MongoDB 5.0+: reshardCollection command (online, no data loss):
db.adminCommand({
    reshardCollection: "myapp.orders",
    key: { userId: 1, createdAt: 1 }    // New shard key
})
// → Redistributes all data with the new key.
// → Takes hours for large collections (writes continue during resharding).
// → MongoDB 6.0: refineCollectionShardKey to ADD fields to the existing key
//   (less disruptive than full resharding):
sh.refineCollectionShardKey(
    "myapp.orders",
    { userId: 1, _id: 1 }              // Add _id to the existing { userId: 1 } key
)
// refineCollectionShardKey: adds a suffix to the existing key without resharding.
// Cannot change or remove the existing prefix.
```

## Section 3: Ranged Sharding

**Q4. How does ranged sharding work — what is the routing mechanism and what makes it susceptible to hotspots?**

A: Ranged sharding partitions the shard key space into contiguous ranges. Each range is assigned to a chunk, and each chunk lives on one shard. Queries that include the shard key can be routed to exactly the shard(s) whose chunk ranges encompass the query values:

```
Ranged sharding — the chunk map:

  Shard key: { userId: 1 }
  userId value space: [ MinKey ─────────────────────────────── MaxKey ]

  Initial state (single chunk, before any data):
  [ MinKey ────────────────────────────────────── MaxKey ] → Shard 1

  After many inserts and chunk splits:
  Chunk 1: [ MinKey ── 10000 )  → Shard 1
  Chunk 2: [ 10000  ── 25000 )  → Shard 2
  Chunk 3: [ 25000  ── 42000 )  → Shard 1
  Chunk 4: [ 42000  ── 67000 )  → Shard 3
  Chunk 5: [ 67000  ── MaxKey ) → Shard 2

  Query: db.orders.find({ userId: 42 })
  mongos: userId=42 falls in Chunk 1 (MinKey-10000) → Shard 1
  → ONE shard receives the query ✓ (targeted query)

  Query: db.orders.find({ userId: { $gte: 20000, $lte: 50000 } })
  mongos: range spans Chunk 2 (10000-25000), Chunk 3 (25000-42000), Chunk 4 (42000-67000)
  → THREE shards receive the query (partial scatter — better than full scatter)
```

```javascript
// ── Ranged sharding setup ─────────────────────────────────────────────────────
sh.shardCollection("myapp.orders", { userId: 1 })
// MongoDB assigns the entire key space to one chunk on one shard.
// Chunks split automatically when they reach 128 MB (configurable).
// The balancer migrates chunks to keep shards equal.

// ── Pre-splitting chunks (avoid initial hotspot) ──────────────────────────────
// Without pre-splitting: ALL writes go to shard 1 (only one chunk).
// Splits happen, balancer moves chunks — but this is reactive and slow.
// Pre-splitting creates chunks before data is loaded:

sh.stopBalancer()  // Stop automatic balancing during pre-split

// Create 12 evenly-spaced chunks across 3 shards:
db.adminCommand({ split: "myapp.orders", middle: { userId: 10000 } })
db.adminCommand({ split: "myapp.orders", middle: { userId: 20000 } })
db.adminCommand({ split: "myapp.orders", middle: { userId: 30000 } })
// ... continue for desired granularity

// Move specific chunks to specific shards:
sh.moveChunk("myapp.orders", { userId: 0 },     "shard001")
sh.moveChunk("myapp.orders", { userId: 10000 }, "shard002")
sh.moveChunk("myapp.orders", { userId: 20000 }, "shard003")

sh.startBalancer()  // Resume automatic balancing

// ── The monotonically increasing key hotspot problem ──────────────────────────
// Shard key: { createdAt: 1 }  (timestamp)
//
// Time →
// Jan 1:  All writes go to the chunk holding the highest createdAt values.
//         That chunk is always on ONE shard (the "right edge" shard).
// Jan 2:  Chunk splits and balancer moves old chunks to other shards.
//         But ALL NEW writes still go to the "right edge" shard.
// Jan 3:  Same pattern — right edge shard is always hot.
//
// Result: Hot shard (high write load) + cold shards (low write load).
// Even with perfect chunk balancing, writes are always concentrated.

// EVIDENCE of monotonic hotspot in explain:
db.orders.explain("executionStats").find({ createdAt: { $gte: new Date() } })
// → shards.shard003 handles ALL recent-data queries.
// sh.status() shows shard003 has the most recent chunk (right edge).

// ── Solutions to the monotonic key hotspot ────────────────────────────────────

// Solution A: Hashed shard key (best for write distribution):
sh.shardCollection("myapp.orders", { _id: "hashed" })
// _id is ObjectId → monotonically increasing → hash randomises it ✓
// Writes distribute uniformly. Range queries on _id lose efficiency.

// Solution B: Compound key with hashed suffix:
sh.shardCollection("myapp.orders", { tenantId: 1, _id: "hashed" })
// Targeted by tenantId. Randomised within each tenant by hashed _id. ✓

// Solution C: Zone sharding with time-based zones:
// Assign a "current" zone to 3 shards and rotate weekly.
// Old data naturally moves to "archive" zones as it ages.
// Complex to manage but preserves range query efficiency on time.

// ── Ranged sharding advantages ────────────────────────────────────────────────
// ✓ Range queries on shard key are efficient (contiguous chunks, few shards hit).
// ✓ Prefix queries on compound shard key are semi-targeted.
// ✓ Natural data locality: documents with similar key values are on the same shard.
//   (Good for time-series: query last 7 days → hits only a few shards.)

// ── Ranged sharding disadvantages ────────────────────────────────────────────
// ✗ Monotonically increasing keys create write hotspots.
// ✗ Uneven data distribution if certain key values are more frequent.
// ✗ Requires pre-splitting for large initial data loads.
```

## Section 4: Hashed Sharding

**Q5. How does hashed sharding work — what does it gain and what does it permanently sacrifice?**

A: Hashed sharding applies a hash function to the shard key value before determining which chunk it belongs to. The hash output is uniformly distributed regardless of the input pattern — solving the monotonic key problem at the cost of range query efficiency:

```
Hashed sharding — how the hash transforms the key space:

  Shard key: { _id: "hashed" }
  Input:  ObjectId("507f1f77bcf86cd799439011")  → hash: -2357346553
  Input:  ObjectId("507f1f77bcf86cd799439012")  → hash:  3891234789
  Input:  ObjectId("507f1f77bcf86cd799439013")  → hash: -1029384756
  Input:  ObjectId("507f1f77bcf86cd799439014")  → hash:  2018374650

  Even though the ObjectIds are sequential (differ by 1),
  their hashes are uniformly distributed across the int64 range:
  [ -9223372036854775808 ─────────────────── 9223372036854775807 ]

  Chunk ranges (on hash values):
  Chunk 1: [ MinKey ─── -3000000000 )  → Shard 1
  Chunk 2: [ -3000000000 ─── 0 )       → Shard 2
  Chunk 3: [ 0 ─── 3000000000 )        → Shard 3
  Chunk 4: [ 3000000000 ─── MaxKey )   → Shard 1

  Insert ObjectId("...011") → hash: -2357346553 → Chunk 1 → Shard 1
  Insert ObjectId("...012") → hash:  3891234789 → Chunk 4 → Shard 1
  Insert ObjectId("...013") → hash: -1029384756 → Chunk 2 → Shard 2
  Insert ObjectId("...014") → hash:  2018374650 → Chunk 3 → Shard 3

  4 sequential inserts → 3 different shards ✓ (uniform distribution)
```

```javascript
// ── Hashed sharding setup ─────────────────────────────────────────────────────
sh.shardCollection("myapp.events", { _id: "hashed" })
// MongoDB automatically:
// 1. Creates 2 chunks per shard (so 6 chunks for 3 shards).
// 2. Distributes those chunks across all shards.
// 3. All chunks are pre-populated with equal hash ranges.
// → No pre-splitting needed — hashed sharding starts balanced immediately. ✓

// Verify initial chunk distribution:
db.getSiblingDB("config").chunks.find(
    { ns: "myapp.events" },
    { shard: 1, min: 1, max: 1 }
).sort({ min: 1 })
// {
//   shard: "shard001", min: { _id: MinKey },           max: { _id: -4611686018427387902 }
//   shard: "shard002", min: { _id: -4611686018427387902}, max: { _id: 0 }
//   shard: "shard003", min: { _id: 0 },                 max: { _id: 4611686018427387902 }
//   shard: "shard001", min: { _id: 4611686018427387902 },max: { _id: MaxKey }
// }
// → 4 chunks distributed across 3 shards from the start.

// ── Hashed sharding advantages ────────────────────────────────────────────────
// ✓ Uniform write distribution — no hotspots even with monotonically increasing keys.
// ✓ Starts balanced — no pre-splitting required.
// ✓ Works well for write-heavy workloads with unpredictable access patterns.
// ✓ Equality queries on the hashed field are still targeted:
db.events.find({ _id: ObjectId("507f1f77bcf86cd799439011") })
// → mongos hashes the _id → finds the shard → ONE shard query ✓

// ── Hashed sharding disadvantages ────────────────────────────────────────────
// ✗ Range queries on the shard key CANNOT be targeted:
db.events.find({ _id: { $gt: ObjectId("507f1f77bcf86cd799439011") } })
// → Hash of range endpoints tells you nothing about which hashes are in between.
// → mongos must query ALL shards (scatter-gather) ✗
// → Performance degrades proportionally with number of shards.

// ✗ Sort on the shard key: scatter-gather + merge-sort across all shards.
db.events.find().sort({ _id: 1 })  // Looks like a sorted scan, is actually scatter-gather.

// ✗ No data locality — documents with similar real values are on different shards.
//   Pattern: "get all events from the last hour" → must query all shards.

// ✗ Compound hashed keys: only the LAST field can be hashed.
sh.shardCollection("myapp.events", { tenantId: 1, _id: "hashed" })
// → tenantId: ranged (prefix queries on tenantId are semi-targeted)
// → _id: hashed (randomises within each tenant)
// → Cannot do: { tenantId: "hashed", _id: 1 } (hashed must be last in compound)

// ── Hashed vs ranged: decision matrix ─────────────────────────────────────────
// Use HASHED when:
//   ✓ Shard key is monotonically increasing (_id, createdAt, auto-increment)
//   ✓ Write throughput is the primary bottleneck
//   ✓ Queries are always by exact shard key value (no range queries on shard key)
//   ✓ Data access pattern is unpredictable/random

// Use RANGED when:
//   ✓ Shard key has good natural distribution (UUID, random hash)
//   ✓ Range queries on the shard key are common and performance-critical
//   ✓ Data locality matters (e.g., all of tenant X's data on one shard)
//   ✓ You need zone sharding (geographic data placement)

// ── Hashed index on non-shard-key field ───────────────────────────────────────
// Hashed indexes (non-sharding) are used for:
// 1. Exact equality queries that need uniform distribution in the index.
// 2. As the shard key for sharding (described above).
// NOT useful for: range queries, covered queries, sort operations.
db.events.createIndex({ userId: "hashed" })  // Standalone hashed index (not shard key)
// → Only useful if userId equality is the sole query pattern.
```

## Section 5: Chunks and the Balancer

**Q6. What is a chunk — how does it get created, split, and moved?**

A: A chunk is the unit of data distribution in MongoDB sharding. It represents a contiguous range of shard key values and always lives entirely on one shard. The balancer moves chunks between shards to keep them balanced:

```
Chunk lifecycle:

  Birth: Every collection starts with one chunk spanning [MinKey, MaxKey].
  
  Growth: Documents are inserted. The chunk accumulates data.
  
  Split: When the chunk reaches chunkSize (default 128 MB), MongoDB splits it:
    [ MinKey ──────── MaxKey ]      becomes:
    [ MinKey ── 5000 ) + [ 5000 ── MaxKey )
    The split point is the median shard key value in the chunk.
    Split is LOCAL — no data moves between shards. Near-instant.
  
  Imbalance: One shard has 8 chunks, another has 2 chunks.
    The balancer detects: imbalance > migrationThreshold (default: 8 for >3 shards)
  
  Migration: Balancer moves a chunk from the busy shard to the less-busy shard.
    Full data copy: the destination shard receives all documents in the chunk.
    Then: the source shard deletes its copy.
    During migration: reads and writes continue (no downtime).
    Catch-up: changes during migration are replicated via change stream.
    Commit: config server updates the chunk→shard mapping atomically.
```

```javascript
// ── Chunk configuration ────────────────────────────────────────────────────────
// Default chunk size: 128 MB (MongoDB 5.0+, was 64 MB in older versions).
// Change chunk size (applies to future splits, not existing chunks):
db.getSiblingDB("config").settings.updateOne(
    { _id: "chunksize" },
    { $set: { value: 64 } },   // 64 MB chunk size
    { upsert: true }
)

// Why change chunk size?
// Smaller chunks: more balanced distribution, more frequent migrations, more overhead.
// Larger chunks: less migration overhead, less balanced, better for large sequential scans.
// Recommendation: leave at 128 MB unless you have a specific reason.

// ── Viewing chunks ─────────────────────────────────────────────────────────────
db.getSiblingDB("config").chunks.find(
    { ns: "myapp.orders" }
).sort({ min: 1 })
// {
//   _id: "myapp.orders-userId_MinKey",
//   ns: "myapp.orders",
//   min: { userId: MinKey },
//   max: { userId: 10000 },
//   shard: "shard001",
//   lastmod: Timestamp(1, 0)
// },
// {
//   min: { userId: 10000 },
//   max: { userId: 25000 },
//   shard: "shard002",
//   ...
// }

// Count chunks per shard:
db.getSiblingDB("config").chunks.aggregate([
    { $match: { ns: "myapp.orders" } },
    { $group: { _id: "$shard", chunks: { $sum: 1 } } },
    { $sort:  { chunks: -1 } }
])
// shard001: 47 chunks   ← slightly more than others (balancer will equalise)
// shard002: 43 chunks
// shard003: 41 chunks

// sh.status() gives a visual overview:
sh.status()
// shards:
//   { _id: "shard001", host: "shard001/host1:27017,host2:27017" }
//   { _id: "shard002", host: "shard002/host3:27017,host4:27017" }

//   myapp.orders    shard key: { "userId" : 1 }

//       shard001   47
//       shard002   43

// ── Manual chunk split ────────────────────────────────────────────────────────
// Force a split at a specific value (useful for pre-splitting before bulk load):
sh.splitAt("myapp.orders", { userId: 50000 })
// Creates split point at userId = 50000.
// If no chunk boundary exists there: creates it.
// Does NOT move data — just splits the chunk in two on the same shard.

sh.splitFind("myapp.orders", { userId: 50000 })
// Splits the chunk that CONTAINS userId=50000 at its median value.
// Useful when you don't know the right split point.

// ── Manual chunk migration ────────────────────────────────────────────────────
// Move a specific chunk to a specific shard:
sh.moveChunk("myapp.orders", { userId: 50000 }, "shard003")
// Moves the chunk containing userId=50000 to shard003.
// Data is copied from current shard to shard003, then deleted from source.
// Takes seconds to minutes depending on chunk size.

// ── The balancer ──────────────────────────────────────────────────────────────
// The balancer runs on the PRIMARY config server.
// It checks chunk distribution every 10 seconds.
// Migration threshold (when imbalance triggers balancing):
//   ≤ 3 shards: migrate when difference > 2 chunks
//   > 3 shards: migrate when difference > 8 chunks
// Each chunk migration moves exactly ONE chunk at a time (per shard pair).
// Multiple migrations can occur in parallel (across different shard pairs).

// Check balancer status:
sh.getBalancerState()          // true/false: is balancer enabled?
sh.isBalancerRunning()         // true/false: is a migration in progress?
sh.getBalancerWindow()         // Scheduled window (if configured)

// Disable balancer (for maintenance or bulk loads):
sh.stopBalancer()
// Wait for any in-progress migrations to complete:
while (sh.isBalancerRunning()) { sleep(1000); print("Waiting..."); }

// Re-enable:
sh.startBalancer()

// Schedule balancer window (run only during off-peak hours):
db.getSiblingDB("config").settings.updateOne(
    { _id: "balancer" },
    { $set: { activeWindow: { start: "01:00", stop: "05:00" } } },
    { upsert: true }
)
// Balancer runs only between 1AM and 5AM. Chunk migrations outside this window stop.
```

## Section 6: Chunk Migrations

**Q7. How does a chunk migration work step by step — what is the performance impact during migration?**

A: A chunk migration is a multi-phase protocol that moves chunk data from a donor shard to a recipient shard without downtime. The protocol is designed so reads and writes can continue throughout, but there is measurable I/O and CPU overhead on both shards:

```
Chunk migration protocol (6 phases):

  Donor shard (source)              Config server             Recipient shard (dest)
  ─────────────────────────────────────────────────────────────────────────────────

  Phase 1: COMMAND
  Balancer sends moveChunk command to donor shard.
  Donor acquires a distributed lock on the chunk (prevents concurrent migrations).

  Phase 2: CLONE
  Donor: "start cloning chunk data to recipient"
  Recipient: reads all documents in the chunk range from donor via internal protocol.
  Donor: continues accepting reads AND writes during clone.
  Duration: depends on chunk size and network speed (seconds to minutes).

  Phase 3: CATCH-UP (replicate changes during clone)
  While clone was running, the donor may have received writes to the chunk.
  Donor: sends the list of changed documents (delete/update/insert) to recipient.
  Recipient: applies these changes to its copy.
  This loop continues until the catch-up backlog is small (configurable threshold).

  Phase 4: WAIT FOR REPLICATION
  Recipient confirms: "I have applied all changes, I'm ready to be the owner."
  Recipient's replica set replicates the data to its own secondaries.

  Phase 5: COMMIT (the critical moment — very brief)
  Config server atomically updates:
    chunk → shard: "shard002" BECOMES "shard003"
  All mongos instances are notified (or learn via cache invalidation on next query).
  From this moment: all routing goes to the new shard.
  Duration: milliseconds.

  Phase 6: CLEANUP
  Donor deletes the documents that were in the migrated chunk.
  Donor releases the distributed lock.

  Timeline:
  ─────────────────────────────────────────────────────────
  Clone (slow, seconds-minutes): reads/writes still on donor
  Catch-up (fast): drain the change log
  Commit (milliseconds): routing switches
  Cleanup (async): donor deletes old data
```

```javascript
// ── Performance impact during migration ───────────────────────────────────────

// Impact on the DONOR shard:
// • Network I/O: sending chunk data to recipient.
// • CPU: serializing and sending documents.
// • Disk I/O: reading chunk data for cloning.
// • Write overhead: tracking changes during clone for catch-up phase.
// Reads and writes still work on donor → no downtime, but latency may increase.

// Impact on the RECIPIENT shard:
// • Network I/O: receiving chunk data.
// • CPU: deserializing and inserting documents.
// • Disk I/O: writing incoming documents.
// Existing queries on recipient continue normally.

// Impact on MONGOS:
// Between Phase 5 (commit) and mongos cache refresh:
// mongos may briefly send a query to the donor (stale routing).
// → Donor redirects with "ChunkMoved" error.
// → mongos retries automatically to the new shard.
// Application sees: a brief spike in query latency (one retry).
// Duration: sub-second for most queries.

// ── Monitoring active migrations ──────────────────────────────────────────────
db.getSiblingDB("config").migrations.find()
// Shows currently-running migrations:
// {
//   _id: "myapp.orders-userId_10000",
//   ns: "myapp.orders",
//   min: { userId: 10000 },
//   max: { userId: 20000 },
//   fromShard: "shard001",
//   toShard:   "shard003",
//   state:     "cloning",       ← current phase
//   stateChangedAt: ISODate("...")
// }

// Migration history (last N migrations):
db.getSiblingDB("config").changelog.find(
    { what: { $in: ["moveChunk.start", "moveChunk.commit", "moveChunk.error"] } }
).sort({ time: -1 }).limit(20)

// Check balancer log for slow migrations:
db.getSiblingDB("config").changelog.find({
    what: "moveChunk.commit",
    "details.duration": { $gt: 30000 }  // Migrations taking > 30 seconds
}).sort({ time: -1 })

// ── Controlling migration bandwidth ───────────────────────────────────────────
// Limit migration throughput to reduce impact on production queries:
db.adminCommand({
    setParameter: 1,
    migrationThrottlingMs: 10   // ms between batch sends (0 = no throttle)
})
// Higher value = slower migration = less impact on production, longer to complete.

// In MongoDB 4.4+: secondary throttling (use secondary for clone reads):
db.getSiblingDB("config").settings.updateOne(
    { _id: "balancer" },
    { $set: { _secondaryThrottle: true } },  // Read from secondary during clone
    { upsert: true }
)
// Reduces load on donor primary during clone phase.

// ── Disabling migrations for bulk loads ───────────────────────────────────────
// When doing a large initial data load:
// 1. Stop balancer (no migrations during load).
// 2. Pre-split chunks to match expected data distribution.
// 3. Load data in parallel to multiple mongos instances.
// 4. After load: re-enable balancer, let it balance over time.
sh.stopBalancer()
// ... bulk load ...
sh.startBalancer()

// ── Migration failures and recovery ───────────────────────────────────────────
// If a migration fails (network partition, shard crash):
// MongoDB uses a two-phase commit on the config server.
// The chunk always belongs to exactly ONE shard (never split between two).
// Config server is the source of truth — no data corruption from failed migrations.
// Failed migrations are retried automatically by the balancer.

// If you see repeated migration failures:
db.getSiblingDB("config").changelog.find({
    what: "moveChunk.error"
}).sort({ time: -1 }).limit(10)
// Common causes: network issues, disk full on recipient, shard primary stepdown.
```

## Section 7: Jumbo Chunks

**Q8. What is a jumbo chunk — how do they form and how do you resolve them?**

A: A jumbo chunk is a chunk that has grown beyond the maximum chunk size but cannot be split because all documents in it share the same shard key value. Since you cannot split within a single shard key value, the chunk cannot be divided further — and since it's oversized, the balancer refuses to migrate it:

```
How a jumbo chunk forms:

  Shard key: { status: 1 }  (LOW CARDINALITY — bad choice)

  Chunk: { status: "pending" } → { status: "shipped" }
         Contains 8 million "pending" documents.
  
  Chunk size: 4.7 GB > 128 MB (max chunk size)
  
  Split attempt: MongoDB tries to split at the median value.
  All documents have status = "pending" → no split point exists!
  The chunk is JUMBO — too large, cannot be split.
  
  Balancer check: Chunk is oversized → needs migration.
  Migration check: Chunk is JUMBO → refuses to migrate.
  Result: Chunk permanently on one shard. Cannot be balanced.
  That shard holds 4.7 GB of a single chunk's data.
  ALL writes to "pending" orders go to that one shard forever.
```

```javascript
// ── Detecting jumbo chunks ────────────────────────────────────────────────────
sh.status({ verbose: true })
// Shows "jumbo" label next to affected chunks:
// chunks:
//   shard001  8
//   shard002  8  [[ too many chunks to print, use verbose if needed ]]
//   shard003  47 jumbo   ← many chunks with 'jumbo' label

// Find jumbo chunks in config:
db.getSiblingDB("config").chunks.find({
    ns: "myapp.orders",
    jumbo: true
})
// { min: { userId: 1 }, max: { userId: 1 }, shard: "shard003", jumbo: true }
// Note: min and max being the same value → only one userId value in this chunk
// → Cannot split → permanently stuck on shard003.

// ── Why the jumbo flag is set ─────────────────────────────────────────────────
// A chunk becomes jumbo when:
// 1. Its size exceeds chunkSize (128 MB default) AND
// 2. MongoDB cannot find a split point (all documents share the same shard key value).
// The balancer then sets the "jumbo: true" flag and refuses to migrate it.

// ── Resolution 1: Clear the jumbo flag (if the chunk CAN now be split) ────────
// This works if new documents were inserted with different shard key values
// since the jumbo flag was set — making a split point now possible.
sh.clearJumboFlag("myapp.orders", { userId: 1 })
// → Removes the jumbo flag.
// → Balancer will try to split and migrate it.
// → If split still fails (all same key): jumbo flag is re-set immediately.

// ── Resolution 2: Manually split the chunk ────────────────────────────────────
// Only works if the chunk contains multiple distinct shard key values:
sh.splitAt("myapp.orders", { userId: 1000 })  // Requires userId=1000 is in the chunk
// After splitting: smaller chunks can be migrated normally.

// ── Resolution 3: Reshard the collection (fix the shard key) ─────────────────
// If the shard key is fundamentally wrong (low cardinality):
// MongoDB 5.0+: reshape with a better key.
db.adminCommand({
    reshardCollection: "myapp.orders",
    key: { userId: 1, _id: 1 }   // Add _id to increase cardinality
})
// → Redistributes ALL data with the new key.
// → Jumbo chunks dissolve (more distinct values = split points exist).
// → Takes hours for large collections but runs online (writes continue).

// ── Resolution 4: Manually move documents out of the jumbo chunk ──────────────
// Last resort if resharding is not possible (old MongoDB version):
// 1. Temporarily set a large chunkSize to allow the balancer to migrate:
db.getSiblingDB("config").settings.updateOne(
    { _id: "chunksize" },
    { $set: { value: 10240 } }  // 10 GB: larger than the jumbo chunk
)
sh.clearJumboFlag("myapp.orders", { userId: 1 })
sh.startBalancer()
// → Balancer migrates the now-"non-jumbo" chunk to another shard.
// 2. After migration: restore chunkSize to 128 MB.

// ── Preventing jumbo chunks ───────────────────────────────────────────────────
// Use a shard key with HIGH CARDINALITY. Low cardinality keys guarantee jumbo chunks.
// Rule: if any shard key value appears in > chunkSize / avg_doc_size documents:
//       that value WILL eventually cause a jumbo chunk.

// Safe cardinality minimum:
// For 128 MB chunks and 1 KB average document size:
// Max documents per shard key value safely = 128 MB / 1 KB = 131,072
// If any value appears more than ~100,000 times: jumbo chunk risk.

// Check document count per shard key value:
db.orders.aggregate([
    { $group: { _id: "$userId", count: { $sum: 1 } } },
    { $match: { count: { $gt: 100000 } } },  // Values with > 100k documents
    { $sort: { count: -1 } }
])
// If any results: those values are at jumbo chunk risk.
```

## Section 8: Targeted vs Scatter-Gather Queries

**Q9. What is the difference between a targeted and scatter-gather query — how does the shard key determine which type runs?**

A: Every query in a sharded cluster is either targeted (goes to one or few shards) or scatter-gather (goes to all shards). The ratio of targeted to scatter-gather queries is the primary determinant of whether sharding improves or degrades query performance:

```
Query routing logic in mongos:

  Rule: If the query filter includes the SHARD KEY (or its prefix for compound keys),
        mongos can identify exactly which shard(s) hold the matching data.
        Otherwise: mongos must broadcast to ALL shards.

  Shard key: { tenantId: 1, userId: 1 }

  Targeted queries (fast):
  ┌────────────────────────────────────────────────────────────────────┐
  │ { tenantId: "t-123", userId: 42 }    → 1 shard   (exact key) ✓  │
  │ { tenantId: "t-123" }                → N shards  (prefix match)  │
  │   (where N = shards holding t-123's chunks — may be 2 of 10)     │
  └────────────────────────────────────────────────────────────────────┘

  Scatter-gather queries (slow):
  ┌────────────────────────────────────────────────────────────────────┐
  │ { userId: 42 }                       → ALL shards ✗              │
  │ { status: "pending" }                → ALL shards ✗              │
  │ { tenantId: { $gt: "t-100" } }       → ALL shards ✗ (range on   │
  │   (range on first key — multiple ranges across all chunks)        │
  └────────────────────────────────────────────────────────────────────┘
```

```javascript
// ── Diagnosing scatter-gather with explain ─────────────────────────────────────
db.orders.explain("executionStats").find({ status: "pending" })
// executionStats.executionStages.shards:
// [
//   { shardName: "shard001", executionStats: { nReturned: 12847, ... } },
//   { shardName: "shard002", executionStats: { nReturned: 14221, ... } },
//   { shardName: "shard003", executionStats: { nReturned: 13108, ... } }
// ]
// All three shards executed the query → SCATTER-GATHER ✗
// Total documents examined: 40,176 (across all shards)

// Targeted query:
db.orders.explain("executionStats").find({ tenantId: "t-123", userId: 42 })
// executionStats.executionStages.shards:
// [
//   { shardName: "shard002", executionStats: { nReturned: 47, ... } }
// ]
// Only ONE shard executed the query → TARGETED ✓

// ── Measuring scatter-gather ratio in production ───────────────────────────────
db.adminCommand({ serverStatus: 1 }).metrics.queryExecutor
// {
//   scanned:        5841293,
//   scannedObjects: 3821847
// }

// Better: use mongos metrics:
db.getSiblingDB("admin").adminCommand({ serverStatus: 1 }).shardingStatistics
// {
//   numHostsTargeted: {
//     oneShard: 48291,   // Targeted queries → one shard
//     allShards: 8472,   // Scatter-gather → all shards ← minimise this
//     manyShard: 3219    // Partial scatter → some shards
//   }
// }
// High allShards / total ratio → shard key is not aligned with query patterns.

// ── The scatter-gather tax ─────────────────────────────────────────────────────
// For N shards:
// Targeted query latency:    same as unsharded (1 shard)
// Scatter-gather latency:    max(all shard latencies) + merge overhead
//                            ≈ 2-5x slower than targeted, growing with N shards.
// Scatter-gather throughput: N × individual query throughput (parallel but expensive)

// Surprising result: adding shards makes scatter-gather queries SLOWER.
// Each new shard adds one more round-trip to every scatter-gather query.
// A query that took 100ms on 1 shard may take 200ms on 10 shards (merge overhead).
// → Sharding only helps if your critical query paths are targeted.

// ── Redesigning to reduce scatter-gather ──────────────────────────────────────
// Problem: shard key is { userId: 1 } but 40% of queries are by tenantId.
//   { tenantId: "t-corp" } → scatter-gather (userId not in filter) ✗

// Solution A: Add tenantId to shard key (compound key):
// Reshard to { tenantId: 1, userId: 1 }
// → { tenantId: "t-corp" } → prefix match → partial scatter ✓

// Solution B: Application-level routing — include shard key in every query:
// Bad:  db.orders.find({ status: "pending" })
// Good: db.orders.find({ tenantId: req.tenantId, status: "pending" })
// → Application always provides the shard key → targeted ✓

// Solution C: Separate unsharded reporting collection:
// Aggregate data into a separate orders_summary collection (not sharded).
// Queries like "all pending orders" run on the summary, not the sharded collection.

// ── $lookup across shards (aggregation) ──────────────────────────────────────
// $lookup with a sharded collection is EXPENSIVE.
// The aggregation must perform scatter-gather on the joined collection.
// In MongoDB 5.0+: $lookup is "shard-aware" for some patterns.
// Best practice: avoid $lookup on sharded collections.
// Alternative: embed related data (denormalise) or use the application to join.
db.orders.aggregate([
    { $match: { tenantId: "t-123" } },
    { $lookup: {
        from:         "products",  // If products is sharded: scatter-gather per lookup
        localField:   "productId",
        foreignField: "_id",
        as:           "product"
    }}
])
// If products is sharded by _id (hashed): each $lookup is a targeted query ✓
// If products is sharded by something else: scatter-gather per document ✗
```

## Section 9: Zone Sharding

**Q10. What is zone sharding — how does it enable geographic data placement and tiered storage?**

A: Zone sharding assigns specific shard key ranges to specific shards (or groups of shards). This enables geographic data residency requirements, tiered storage (hot/warm/cold data), and tenant isolation — all within the same cluster:

```javascript
// ── Geographic zone sharding ───────────────────────────────────────────────────
// Requirement: EU user data must stay in EU shards (GDPR compliance).
//              US user data must stay in US shards.

// Shard key: { region: 1, userId: 1 }

// Step 1: Tag shards with zone labels:
sh.addShardTag("shard001", "US")    // US datacenter shard
sh.addShardTag("shard002", "US")    // US datacenter shard
sh.addShardTag("shard003", "EU")    // EU datacenter shard
sh.addShardTag("shard004", "EU")    // EU datacenter shard

// Step 2: Assign shard key ranges to zones:
sh.addTagRange(
    "myapp.users",
    { region: "US", userId: MinKey },
    { region: "US", userId: MaxKey },
    "US"
)
sh.addTagRange(
    "myapp.users",
    { region: "EU", userId: MinKey },
    { region: "EU", userId: MaxKey },
    "EU"
)
// → All documents where region="US" MUST live on a shard tagged "US".
// → All documents where region="EU" MUST live on a shard tagged "EU".
// → Balancer respects zones: will not move an EU chunk to a US shard.

// Step 3: Insert with the region field:
db.users.insertOne({ region: "EU", userId: 42, name: "Alice" })
// → mongos routes this to an EU shard (shard003 or shard004).
// → Data never leaves EU shards.

// ── Tiered storage with zones ─────────────────────────────────────────────────
// Hot data: recent orders on fast NVMe SSDs.
// Cold data: old orders on slower HDDs (cheaper storage).
// Shard key: { createdAt: 1 }  (ranged, date-based)

sh.addShardTag("nvme-shard001", "hot")
sh.addShardTag("nvme-shard002", "hot")
sh.addShardTag("hdd-shard003",  "cold")
sh.addShardTag("hdd-shard004",  "cold")

// Recent data (last 90 days) → hot shards:
sh.addTagRange(
    "myapp.orders",
    { createdAt: new Date(Date.now() - 90 * 24 * 60 * 60 * 1000) },
    { createdAt: MaxKey },
    "hot"
)
// Old data (before 90 days) → cold shards:
sh.addTagRange(
    "myapp.orders",
    { createdAt: MinKey },
    { createdAt: new Date(Date.now() - 90 * 24 * 60 * 60 * 1000) },
    "cold"
)
// → New orders automatically go to NVMe shards (fast).
// → As data ages past 90 days: zone update moves chunks to HDD shards.
// → Need to update zone ranges periodically (daily/weekly) to slide the window.

// ── Tenant isolation with zones ───────────────────────────────────────────────
// Large enterprise tenant "BigCorp" gets its own dedicated shard:
sh.addShardTag("bigcorp-shard", "bigcorp")
sh.addTagRange(
    "myapp.events",
    { tenantId: "bigcorp", userId: MinKey },
    { tenantId: "bigcorp", userId: MaxKey },
    "bigcorp"
)
// → All BigCorp data lives on its dedicated shard.
// → No resource contention with other tenants.
// → Can provision the BigCorp shard with higher-spec hardware.

// ── Removing a zone ───────────────────────────────────────────────────────────
sh.removeTagRange(
    "myapp.orders",
    { createdAt: MinKey },
    { createdAt: new Date(Date.now() - 90 * 24 * 60 * 60 * 1000) },
    "cold"
)
sh.removeShardTag("hdd-shard003", "cold")
// After removing: balancer redistributes those chunks to any available shard.

// ── Checking zone assignments ──────────────────────────────────────────────────
db.getSiblingDB("config").shards.find({}, { tags: 1 })
// { _id: "shard001", tags: ["US", "hot"] }
// { _id: "shard003", tags: ["EU", "cold"] }

db.getSiblingDB("config").tags.find({ ns: "myapp.orders" })
// { tag: "hot", min: { createdAt: ISODate("2024-10-12") }, max: { createdAt: MaxKey } }
// { tag: "cold", min: { createdAt: MinKey }, max: { createdAt: ISODate("2024-10-12") } }
```

## Section 10: Monitoring and Operations

**Q11. How do you monitor a sharded cluster's health — what metrics indicate problems?**

A: A sharded cluster has more failure modes than a replica set. The config servers, mongos instances, individual shard replica sets, and the balancer all require monitoring:

```javascript
// ── Cluster-wide status ───────────────────────────────────────────────────────
sh.status()           // Chunk distribution, shard list, database list
db.adminCommand({ listShards: 1 })  // All shards and their connection strings

// ── Balancer health ───────────────────────────────────────────────────────────
// Is the balancer running and effective?
sh.getBalancerState()    // true = enabled
sh.isBalancerRunning()   // true = migration in progress right now

// How long since last successful migration?
db.getSiblingDB("config").changelog.findOne(
    { what: "moveChunk.commit" },
    null,
    { sort: { time: -1 } }
).time
// If this was hours ago but chunks are unbalanced → balancer may be stuck.

// Check for balancer errors:
db.getSiblingDB("config").changelog.find(
    { what: "balancer.error" }
).sort({ time: -1 }).limit(10)

// ── Chunk distribution imbalance ─────────────────────────────────────────────
db.getSiblingDB("config").chunks.aggregate([
    { $match: { ns: "myapp.orders" } },
    { $group: { _id: "$shard", count: { $sum: 1 } } },
    { $sort: { count: -1 } }
])
// shard001: 200
// shard002: 198
// shard003: 12   ← severe imbalance: 16x fewer chunks than shard001
// Alert: max_chunks/min_chunks > 2 (for > 3 shards)

// ── Shard-level performance ────────────────────────────────────────────────────
// Connect to each shard and check:
db = connect("shard001-primary/myapp")
db.serverStatus().opcounters   // Writes per second on this shard
db.serverStatus().wiredTiger.cache["bytes currently in the cache"]  // RAM pressure

// Compare write rates across shards (hotspot detection):
// shard001: 8,472 inserts/sec   ← hotspot
// shard002:   847 inserts/sec
// shard003:   912 inserts/sec
// Ratio: 10:1 → severe write hotspot on shard001.

// ── Mongos metrics ────────────────────────────────────────────────────────────
db.adminCommand({ serverStatus: 1 }).shardingStatistics.numHostsTargeted
// { oneShard: 95000, allShards: 48000, manyShard: 5000 }
// Total: 148,000 queries
```

## Section 11: Scenario-Based Questions

**Q12. "Our sharded cluster was fast with 3 shards but got SLOWER after we added a 4th shard — why?"**

A: Adding shards makes scatter-gather queries slower because each new shard adds another round-trip and merge operation. The cluster is probably dominated by scatter-gather queries that don't include the shard key:

```javascript
// ── Diagnosis ─────────────────────────────────────────────────────────────────
// Step 1: Check scatter-gather ratio before and after adding shard 4:
db.adminCommand({ serverStatus: 1 }).shardingStatistics.numHostsTargeted
// { oneShard: 12000, allShards: 88000, manyShard: 0 }
// allShards / total = 88,000 / 100,000 = 88% scatter-gather rate ← catastrophic

// Step 2: Identify which queries are scatter-gather:
db.system.profile.find({
    "command.filter": { $not: { $exists: false } }  // Find queries with filters
}).sort({ ts: -1 }).limit(20)
// → Most slow queries don't include userId (the shard key).

// Step 3: Check query patterns in the application:
// Queries like: db.orders.find({ status: "pending" })  // No shard key
// These hit all N shards. Adding shard 4 → they now hit 4 shards instead of 3.
// 4-way merge is slower than 3-way merge. More shards = more scatter pain.

// ── Root cause: shard key not aligned with query patterns ─────────────────────
// Shard key: { userId: 1 }
// Most common queries:
//   find({ status: "pending" })               → scatter-gather ✗
//   find({ tenantId: "t-corp" })              → scatter-gather ✗
//   find({ createdAt: { $gte: yesterday } })  → scatter-gather ✗
// Only one query is targeted:
//   find({ userId: 42 })                      → targeted ✓ (but this is rare)

// ── Fix: reshard with a better shard key ──────────────────────────────────────
// Option A (MongoDB 5.0+): Reshard to a key that matches query patterns:
db.adminCommand({
    reshardCollection: "myapp.orders",
    key: { tenantId: 1, userId: 1 }   // tenantId is in 90% of queries
})
// After resharding: find({ tenantId: "t-corp" }) → semi-targeted ✓

// Option B: Application-level fix (add shard key to all queries):
// Every query MUST include tenantId (the shard key prefix):

// WRONG (scatter-gather):
const orders = await orderModel.find({ status: 'pending' })

// RIGHT (targeted):
const orders = await orderModel.find({
    tenantId: req.user.tenantId,   // Always include shard key
    status:   'pending'
})

// Option C: Query router middleware (NestJS interceptor):
@Injectable()
export class ShardKeyInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        // Inject tenantId into all database operations for this request:
        const request = context.switchToHttp().getRequest();
        AsyncLocalStorage.run({ tenantId: request.user?.tenantId }, () => next.handle());
        return next.handle();
    }
}

// Repository base class that always injects the shard key:
@Injectable()
export abstract class TenantAwareRepository<T> {
    protected get tenantId(): string {
        return AsyncLocalStorage.getStore()?.tenantId;
    }

    protected get baseFilter() {
        return { tenantId: this.tenantId };  // Always prefix with shard key
    }

    find(filter: FilterQuery<T>): Promise<T[]> {
        return this.model.find({ ...this.baseFilter, ...filter }).lean().exec();
    }
}
```

**Q13. "Design the complete sharding strategy for a multi-tenant event tracking SaaS with 500 tenants, 50M events/day, and a GDPR requirement that EU data stays in EU."**

A: This requires combining zone sharding (geographic placement), a compound shard key (tenant isolation + write distribution), and careful chunk pre-splitting (avoiding the initial hotspot):

```javascript
// ── Requirements analysis ──────────────────────────────────────────────────────
// Scale: 50M events/day ≈ 578 events/second → 3-5 shards needed
// Multi-tenant: 500 tenants → tenantId alone has low cardinality (500 values)
// GDPR: EU tenant data must stay in EU shards
// Query patterns:
//   Pattern A (80%): { tenantId, userId, timestamp: $gte }  → targeted
//   Pattern B (15%): { tenantId, eventType, timestamp: $gte } → semi-targeted
//   Pattern C (5%):  { tenantId } aggregate → semi-targeted

// ── Shard key selection ────────────────────────────────────────────────────────
// Candidate: { tenantId: 1, _id: "hashed" }
//
// Cardinality: 500 tenants × ObjectId_range = very high ✓
// Write distribution: _id hashed within each tenant → uniform ✓
// Monotonic key: _id is ObjectId (increasing) → hash solves it ✓
// Query isolation:
//   { tenantId, userId, ... } → tenantId prefix → semi-targeted ✓
//   { tenantId, eventType, ... } → tenantId prefix → semi-targeted ✓
//   { tenantId } alone → prefix → all tenantId's chunks (semi-targeted) ✓
// GDPR: zone sharding on tenantId prefix → EU tenants stay in EU ✓

sh.shardCollection("myapp.events", { tenantId: 1, _id: "hashed" })

// ── Cluster topology ──────────────────────────────────────────────────────────
// 4 shards: 2 US, 2 EU (each shard is a 3-member replica set)
// 3 config servers (replica set, can span regions)
// 2 mongos per region (stateless routers, can run many)

// US shards:
sh.addShardTag("shard-us-1", "US")   // us-east-1 replica set
sh.addShardTag("shard-us-2", "US")   // us-west-2 replica set

// EU shards:
sh.addShardTag("shard-eu-1", "EU")   // eu-west-1 replica set
sh.addShardTag("shard-eu-2", "EU")   // eu-central-1 replica set

// ── Zone assignment ────────────────────────────────────────────────────────────
// EU tenants (tenant IDs starting with "eu-"):
sh.addTagRange(
    "myapp.events",
    { tenantId: "eu-",    _id: MinKey },
    { tenantId: "eu-zzz", _id: MaxKey },
    "EU"
)
// US tenants (all others):
sh.addTagRange(
    "myapp.events",
    { tenantId: MinKey,   _id: MinKey },
    { tenantId: "eu-",    _id: MaxKey },
    "US"
)
sh.addTagRange(
    "myapp.events",
    { tenantId: "eu-zzz", _id: MinKey },
    { tenantId: MaxKey,   _id: MaxKey },
    "US"
)
// → All documents where tenantId starts with "eu-" → EU shards ✓
// → All other tenants → US shards ✓
// → Balancer enforces zone compliance automatically.

// ── Pre-splitting for bulk load ────────────────────────────────────────────────
sh.stopBalancer()

// Create initial chunks for a sample of tenants:
const tenants = ["eu-corp1", "eu-corp2", "us-startup1", "us-bigcorp", ...]
tenants.forEach(tenantId => {
    // Split into multiple chunks per tenant (for parallelism):
    for (let i = 0; i < 4; i++) {  // 4 chunks per tenant
        db.adminCommand({
            split: "myapp.events",
            middle: { tenantId, _id: ObjectId() }
        })
    }
})

sh.startBalancer()
// Balancer distributes chunks within their zones.

// ── Application layer ──────────────────────────────────────────────────────────
@Injectable()
export class EventRepository {
    constructor(
        @InjectModel(Event.name) private readonly eventModel: Model<Event>,
    ) {}

    // Every query includes tenantId → targeted or semi-targeted:
    async findByUser(tenantId: string, userId: string, since: Date): Promise<Event[]> {
        return this.eventModel
            .find({ tenantId, userId, timestamp: { $gte: since } })
            .sort({ timestamp: -1 })
            .limit(100)
            .lean()
            .exec();
        // Uses index { tenantId, userId, timestamp } on whatever shard holds this tenant.
        // → Semi-targeted (tenantId prefix routes to 1-2 shards) ✓
    }

    async countByType(
        tenantId: string,
        eventType: string,
        from: Date,
        to: Date,
    ): Promise<number> {
        return this.eventModel.countDocuments({
            tenantId,
            eventType,
            timestamp: { $gte: from, $lte: to }
        });
        // → Semi-targeted on tenantId prefix ✓
    }

    // Bulk insert (uses tenantId in every document → routes correctly):
    async insertBatch(events: CreateEventDto[]): Promise<void> {
        // Validate all events have tenantId before inserting:
        if (events.some(e => !e.tenantId)) {
            throw new Error('All events must have a tenantId');
        }
        await this.eventModel.insertMany(events, { ordered: false });
        // ordered: false → continue on individual failures, batch insert is parallel.
    }
}

// ── Index strategy on each shard ──────────────────────────────────────────────
// The shard key { tenantId, _id: hashed } is automatically indexed.
// Add compound indexes for query patterns (created on each shard):
EventSchema.index({ tenantId: 1, userId: 1, timestamp: -1 })      // Pattern A
EventSchema.index({ tenantId: 1, eventType: 1, timestamp: -1 })   // Pattern B
EventSchema.index({ tenantId: 1, timestamp: -1 })                   // Pattern C (aggregation)

// TTL index for data retention (events older than 2 years deleted automatically):
EventSchema.index(
    { timestamp: 1 },
    { expireAfterSeconds: 2 * 365 * 24 * 60 * 60 }  // 2 years
)
// TTL works per-shard (each shard runs its own TTL monitor).
// Chunk migrations are separate from TTL — TTL deletes within each shard independently.
```

## Quick Reference Tables

### Shard Key Property Checklist

| Property | Bad example | Good example | Why it matters |
|---|---|---|---|
| Cardinality | `{ status: 1 }` (5 values) | `{ userId: 1 }` (millions) | Limits max number of shards |
| Write distribution | `{ createdAt: 1 }` (monotonic) | `{ _id: "hashed" }` | Prevents write hotspot |
| Query isolation | Key never in queries | Key in 80%+ of queries | Targeted vs scatter-gather |
| Frequency | `{ userId: 1 }` with power user | `{ userId: 1, _id: 1 }` | Prevents jumbo chunks |

### Hashed vs Ranged Sharding Comparison

| Feature | Ranged sharding | Hashed sharding |
|---|---|---|
| Write distribution | ✗ Hotspot if key is monotonic | ✓ Always uniform |
| Range queries on shard key | ✓ Targeted (contiguous chunks) | ✗ Scatter-gather |
| Initial setup | Needs pre-splitting | Balanced automatically |
| Data locality | ✓ Similar keys on same shard | ✗ Similar keys scattered |
| Zone sharding | ✓ Full support | ⚠ Limited (hash breaks ranges) |
| Best for | Random/UUID keys, range queries, zones | ObjectId, timestamp, auto-increment |

### Chunk Operation Reference

| Operation | Command | Notes |
|---|---|---|
| View all chunks | `db.getSiblingDB("config").chunks.find({ ns: "..." })` | — |
| Manual split at value | `sh.splitAt("db.coll", { key: value })` | No data moves |
| Split at median | `sh.splitFind("db.coll", { key: value })` | Finds chunk containing value |
| Move chunk | `sh.moveChunk("db.coll", { key: value }, "shardName")` | Data moves; brief client retry |
| Clear jumbo flag | `sh.clearJumboFlag("db.coll", { key: value })` | Only if split point now exists |
| Stop balancer | `sh.stopBalancer()` | For maintenance or bulk load |
| Start balancer | `sh.startBalancer()` | Resume automatic balancing |
| Add zone | `sh.addShardTag("shard", "zone")` | Tag the shard |
| Assign zone range | `sh.addTagRange("db.coll", min, max, "zone")` | Bind key range to zone |

### Query Routing Guide

| Query includes... | Routing type | Shards hit |
|---|---|---|
| Exact shard key (all fields) | Targeted | 1 |
| Shard key prefix (compound) | Semi-targeted | K of N (K = shards holding that prefix's chunks) |
| Range on first shard key field (ranged) | Semi-targeted | Shards holding the range |
| Range on first shard key field (hashed) | Scatter-gather | All N |
| Only non-shard key fields | Scatter-gather | All N |
| `$or` spanning multiple shard key values | Scatter-gather | All N |
| `$text` search | Scatter-gather | All N |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being able to explain the **four shard key properties** (cardinality, write distribution, query isolation, frequency) and why each matters — cardinality sets the ceiling on how many shards you can have, write distribution determines whether you have a hotspot, query isolation determines whether queries target one shard or all of them, and frequency determines whether any specific key value causes a jumbo chunk; (2) being precise that **hashed sharding solves the monotonic key problem** by computing a hash before determining which chunk the document belongs to, but permanently sacrifices range query efficiency — the hash of a range is not itself a range, so range queries on a hashed key are always scatter-gather; (3) knowing the **scatter-gather paradox**: adding more shards makes scatter-gather queries SLOWER because each new shard adds another parallel round-trip and merge operation — sharding only improves performance if the critical query paths are targeted, meaning the shard key appears in the WHERE clause; (4) understanding **jumbo chunk formation** precisely — a chunk becomes jumbo when it exceeds `chunkSize` bytes but contains only documents with the same shard key value, making it impossible to split; the only permanent fix is resharding with a higher-cardinality key; (5) knowing the **ESR rule** for compound shard keys (Equality-Sort-Range) mirrors the compound index ordering rule — equality fields first maximize targeted routing, sort fields second provide index sort order, range fields last avoid the range stop problem; (6) understanding that **chunk migration is non-blocking but not free** — during the clone phase, the donor shard experiences extra I/O and CPU, there is a brief period where mongos retries stale-routed queries (one retry per query, sub-second), and the 60-second balancer window means production migrations should be scheduled during low-traffic periods; (7) knowing that **zone sharding is the only built-in mechanism for geographic data residency** — it assigns key ranges to shard groups using `addShardTag` and `addTagRange`, and the balancer enforces zone compliance by refusing to move chunks out of their assigned zones, making it suitable for GDPR and data sovereignty requirements; and (8) understanding that **pre-splitting is essential for large initial data loads** into a new sharded collection — without pre-splitting, all writes go to a single chunk on a single shard until the balancer catches up, creating a transient but severe write hotspot during the load; stopping the balancer, pre-splitting to the expected number of shards, distributing chunks manually, then re-enabling the balancer avoids this.
