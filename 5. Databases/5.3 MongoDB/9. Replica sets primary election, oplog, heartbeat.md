# MongoDB Replica Sets: Primary Election, Oplog, Heartbeat — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a MongoDB replica set and what problems does it solve?**
A: A replica set is a group of MongoDB processes that maintain the same dataset through continuous replication. It solves three distinct operational problems — high availability, data durability, and read scaling — that a standalone MongoDB instance cannot address:

```
Problems a standalone MongoDB instance has:

  Single point of failure:
    Server crashes → application cannot read or write → downtime
    Disk failure → data loss
    No mechanism to recover without manual intervention

  Backup under load:
    Taking a backup blocks or slows the primary
    Backup requires the instance to be mostly idle

  Read throughput ceiling:
    All reads hit one server → CPU and I/O bound by one machine

Replica set solutions:

  High availability (automatic failover):
    Primary goes down → secondaries elect a new primary automatically
    Typical election time: 10-30 seconds
    Application reconnects to new primary → continues with minimal interruption

  Data durability (redundant copies):
    Data written to primary is replicated to N secondaries
    With writeConcern: { w: "majority" }: data survives primary crash
    because majority of nodes have the data before client receives confirmation

  Read scaling (distribute read load):
    Secondaries can serve read queries (with readPreference: secondary)
    Offload reporting, analytics, backup from primary
    Each secondary is a full copy of the dataset

Anatomy of a replica set:
  ┌─────────────────────────────────────────────────────────────┐
  │ Replica Set: rs0                                            │
  │                                                             │
  │  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   │
  │  │   Primary    │   │  Secondary   │   │  Secondary   │   │
  │  │  (reads+     │──▶│  (replays    │   │  (replays    │   │
  │  │   writes)    │   │   oplog)     │──▶│   oplog)     │   │
  │  └──────────────┘   └──────────────┘   └──────────────┘   │
  │        ▲                  │                   │            │
  │        └──────────────────┴── heartbeat ──────┘            │
  └─────────────────────────────────────────────────────────────┘

Minimum viable replica set: 3 members
  Why 3? Election requires a majority (quorum).
  With 2 members: one goes down → remaining one is NOT a majority → no election possible
  With 3 members: one goes down → 2 remaining = majority → election succeeds
  An arbiter (votes but holds no data) can provide the third vote without a full data copy

Special member types:
  Primary:    accepts writes, one at a time per set
  Secondary:  replicates from primary, can serve reads with readPreference:secondary
  Arbiter:    votes in elections, holds no data, uses minimal resources
  Hidden:     secondary that is invisible to clients (backup, analytics — never primary)
  Delayed:    secondary that replicates N hours behind primary (point-in-time recovery)
  Priority 0: secondary that can never become primary (different datacenter)
```

**Q2. What is the replica set oplog and how does it work mechanically?**
A: The oplog (operations log) is a capped collection in the `local` database on every replica set member. The primary records every write operation as an oplog entry; secondaries continuously tail the primary's oplog and replay each entry to maintain an identical copy of the data. It is the replication backbone — without the oplog, secondaries have no way to know what changed:

```javascript
// Oplog location:
// Database: local (not replicated — each member has its own)
// Collection: local.oplog.rs
// Type: capped collection (fixed size, oldest entries overwritten when full)

// Viewing the oplog:
use local
db.oplog.rs.find().sort({ $natural: -1 }).limit(5)
// Returns most recent oplog entries

// Oplog entry structure:
{
    ts:  Timestamp(1705313400, 1),  // wall clock seconds + ordinal within the second
    t:   NumberLong(42),            // term: election term this entry belongs to
    h:   NumberLong(0),             // historical: used to be a hash, now 0
    v:   2,                         // oplog version
    op:  "u",                       // operation type (see below)
    ns:  "mydb.loans",              // namespace: database.collection
    ui:  UUID("..."),               // collection UUID (stable even across renames)
    o2:  { _id: ObjectId("L1") },   // query selector (for updates: identifies the doc)
    o:   { $v: 2, diff: {           // the operation to apply (idempotent form)
        u: { status: "approved" },
        a: { status_history: [{ status: "approved", at: new Date() }] }
    }}
}

// op field values:
// "i" = insert
// "u" = update
// "d" = delete
// "c" = command (createCollection, createIndex, dropCollection, etc.)
// "n" = no-op (heartbeat, used to advance the oplog timestamp)
// "db" = database (deprecated)

// Important oplog properties:

// 1. Idempotent: every oplog entry can be applied multiple times safely
//    The operation is stored in its FINAL form (not the original update operator)
//    Example: { $inc: { counter: 1 } } is stored as the result of applying $inc
//    so re-applying it gives the same result, not incrementing again

// 2. Ordered by Timestamp: ts field monotonically increases
//    Secondaries replay in strict timestamp order
//    No entry can be applied out of order

// 3. Capped: when oplog is full, oldest entries are overwritten (circular buffer)
//    oplog size determines "replication window": how far behind a secondary can fall
//    before it can no longer catch up (must be resynced from scratch)

// Oplog size configuration:
// In mongod.conf:
replication:
    oplogSizeMB: 10240    # 10GB oplog (default: 5% of disk or 990MB, whichever is larger)
// Larger oplog = longer window for secondaries to recover from lag

// Checking oplog window:
db.getReplicationInfo()
// Returns:
// {
//   logSizeMB: 10240,
//   usedMB: 4521,
//   timeDiff: 604800,      // how many seconds of operations the oplog currently holds
//   timeDiffHours: 168,    // 7 days of operations buffered
//   tFirst: "...",         // timestamp of oldest oplog entry
//   tLast: "...",          // timestamp of newest oplog entry
//   now: "..."
// }
// If timeDiffHours < 24: oplog is too small → secondaries that fall behind > 24h
// cannot catch up automatically → must initiate full resync

// Checking secondary oplog lag:
rs.printReplicationInfo()       // on primary: shows oplog window
rs.printSecondaryReplicationInfo() // shows each secondary's lag
// Output per secondary:
// source: secondary-host:27017
//    syncedTo: 2024-01-15 10:30:00 GMT
//    0 secs (0 hrs) behind the primary

// Oplog tailing (how secondaries read):
// Each secondary maintains a cursor on the primary's oplog
// The cursor is a "tailable cursor" — it blocks waiting for new entries rather than closing
// When a new oplog entry is written: cursor returns it → secondary applies it → continues waiting
// This is the continuous replication loop
```

## Section 2: Heartbeat Mechanism

**Q3. How does the heartbeat mechanism work in a replica set and what does it detect?**
A: Every member of a replica set sends a heartbeat ping to every other member every 2 seconds (by default). The heartbeat is a lightweight `isMaster` (or `hello` in MongoDB 5+) command that returns the member's current state, replica set configuration, and replication position. Heartbeats are the mechanism by which members detect failures and trigger elections:

```javascript
// Heartbeat mechanics:
// Interval: heartbeatIntervalMillis = 2000ms (2 seconds, not configurable in production)
// Timeout:  heartbeatTimeoutSecs = 10 seconds
//           If a member doesn't respond within 10s → marked as unreachable

// What a heartbeat checks and returns:
// Each member sends: { hello: 1 } (or { isMaster: 1 } in older versions)
// Response includes:
{
    ismaster: false,          // is this the primary? (legacy field)
    secondary: true,          // is this a secondary?
    hosts: [                  // all known members
        "mongo1:27017",
        "mongo2:27017",
        "mongo3:27017"
    ],
    primary: "mongo1:27017",  // current primary's address
    me: "mongo2:27017",       // this member's address
    setName: "rs0",           // replica set name
    setVersion: 7,            // config version (increments on reconfig)
    electionId: ObjectId("..."),  // current election ID (term)
    lastWrite: {
        opTime: { ts: Timestamp(1705313400, 1), t: NumberLong(42) },
        lastWriteDate: ISODate("2024-01-15T10:30:00Z"),
        majorityOpTime: { ts: Timestamp(1705313398, 5), t: NumberLong(42) }
    },
    operationTime: Timestamp(1705313400, 1),
    ok: 1
}

// What the heartbeat detects:
// 1. Member liveness: did the member respond within heartbeatTimeoutSecs?
//    No response within 10s → member marked DOWN → logged in replica set state

// 2. Primary liveness: secondaries detect primary failure
//    If secondary doesn't receive heartbeat response from primary within electionTimeoutMillis
//    → secondary calls for an election

// 3. Replication lag: lastWrite.opTime shows how current the member is
//    Primary compares its own opTime to each secondary's reported opTime
//    → replication lag in seconds available in rs.status()

// 4. Configuration changes: setVersion in heartbeat response
//    If a member's setVersion doesn't match the majority → reconfig occurred
//    Member updates its local config

// 5. Election state: electionId tracks the current term
//    Stale responses (lower term) indicate a former primary that hasn't stepped down

// Monitoring heartbeat state:
rs.status()
// Returns per-member:
{
    name: "mongo2:27017",
    health: 1,              // 1 = healthy, 0 = unreachable
    state: 2,               // 2 = SECONDARY (see state codes below)
    stateStr: "SECONDARY",
    uptime: 86400,
    optime: {
        ts: Timestamp(1705313399, 3),
        t: NumberLong(42)
    },
    optimeDate: ISODate("2024-01-15T10:29:59Z"),
    lastHeartbeat:      ISODate("2024-01-15T10:30:00Z"),  // last successful heartbeat
    lastHeartbeatRecv:  ISODate("2024-01-15T10:29:58Z"),  // last heartbeat received from this member
    pingMs: 1,              // round-trip time for heartbeat
    lastHeartbeatMessage: "",  // error message if unhealthy
    syncSourceHost: "mongo1:27017",  // where this secondary is replicating from
    syncSourceId: 0
}

// Member state codes:
// 0  = STARTUP       — loading config from disk
// 1  = PRIMARY       — current primary
// 2  = SECONDARY     — replicating from primary
// 3  = RECOVERING    — getting back in sync (initial sync or startup)
// 5  = STARTUP2      — initial sync (copying data)
// 6  = UNKNOWN       — not yet contacted
// 7  = ARBITER       — no data, votes only
// 8  = DOWN          — heartbeat failed
// 9  = ROLLBACK      — undoing writes after stepping down
// 10 = REMOVED       — removed from replica set

// electionTimeoutMillis:
// Time a secondary waits without hearing from the primary before calling an election
// Default: 10000ms (10 seconds)
// Configurable:
rs.reconfig({
    ...rs.conf(),
    settings: {
        electionTimeoutMillis: 10000,   // 10s default
        heartbeatIntervalMillis: 2000,  // 2s heartbeat interval
        heartbeatTimeoutSecs: 10        // 10s heartbeat timeout
    }
})

// Network partition detection:
// Primary crashes → secondaries stop receiving heartbeats → after 10s → call election
// Network partition (primary isolated):
//   Primary: still receives heartbeats from 0 of 2 secondaries
//             → cannot maintain w:"majority" writes → steps down voluntarily
//             → secondaries elect a new primary
//   Application: cannot connect to isolated primary → connects to new primary
```

## Section 3: Primary Election

**Q4. What triggers a primary election and what is the Raft-inspired election algorithm?**
A: MongoDB's election protocol is based on a simplified version of the Raft consensus algorithm. An election is triggered when a secondary determines the primary is unavailable. The election uses a term-based voting system where each member votes for at most one candidate per term:

```
Election triggers:
  1. Primary becomes unreachable (heartbeat timeout after electionTimeoutMillis)
  2. Primary steps down voluntarily (rs.stepDown() command)
  3. Primary detects it cannot reach majority of members → steps down
  4. replicaset reconfig that changes member priorities
  5. Initial startup (no primary exists yet)

Election algorithm (Raft-inspired):

  Step 1: Candidate calls for election
    A secondary that hasn't heard from primary for electionTimeoutMillis:
    → Increments its term number (t: 42 → t: 43)
    → Transitions to CANDIDATE state
    → Sends RequestVote to all other members with:
      { term: 43, candidateId: "mongo2:27017", lastLogIndex: ..., lastLogTerm: ... }

  Step 2: Members decide whether to vote
    Each member votes YES if ALL of the following are true:
    a. The candidate's term is ≥ the voter's current term
    b. The voter has not already voted in this term (each member votes once per term)
    c. The candidate's oplog is at least as up-to-date as the voter's oplog
       (candidate's lastLogTerm > voter's, OR same lastLogTerm AND lastLogIndex ≥ voter's)
    d. The candidate's priority is not lower than the voter's priority

    Votes NO if any condition fails.
    If the voter's term is higher: the candidate's term is stale → no vote, update local term

  Step 3: Candidate wins or loses
    WIN:  candidate receives votes from majority of voting members (including itself)
          → Transitions to PRIMARY state
          → Begins accepting writes
          → Sends heartbeats to all members announcing new primary

    LOSE: another candidate received majority first → election lost
          → Transition back to SECONDARY state
          → Follow the new primary

  Step 4: Old primary rejoins
    Former primary (if it recovers) finds a new primary with higher term
    → Steps down (cannot win election with stale term)
    → Enters ROLLBACK state if it has writes the new primary doesn't
    → Rolls back uncommitted writes to join the new primary's oplog
    → Transitions to SECONDARY state

  Typical election timeline:
  T=0:    Primary crashes / network partition
  T=0-10: Secondaries wait electionTimeoutMillis (10s) without hearing from primary
  T=10:   First secondary calls election (term 43)
  T=10.5: RequestVotes sent to all members
  T=11:   Other secondary responds with vote
  T=11:   Candidate has majority (2 of 3 votes including self)
  T=11:   New primary announced
  T=11-15: Application detects new primary (driver reconnects)
  Total downtime: ~11-15 seconds for typical replica set
```

**Q5. What factors determine which secondary wins an election and how do you control this?**

```javascript
// Factor 1: Priority (most important determinant)
// Higher priority members are preferred as candidates
// Priority 0: cannot be elected primary (ever)
// Priority 1: default — can be elected
// Priority >1: preferred candidate (e.g. priority 10 beats priority 1)

// Configure priorities:
const config = rs.conf();
config.members[0].priority = 10;  // mongo1: strongly preferred primary
config.members[1].priority = 5;   // mongo2: secondary primary (DR site)
config.members[2].priority = 0;   // mongo3: never primary (hidden, analytics)
rs.reconfig(config);

// Factor 2: Oplog freshness
// Candidate must have oplog at least as current as the voters
// If secondary A has opTime T=100 and secondary B has opTime T=95:
// A is preferred (more up-to-date → less rollback risk)
// B will not vote for a candidate with opTime < T=95

// Factor 3: Votes
// Each member has 0 or 1 vote (usually 1)
// Arbiter has 1 vote but no data
// Hidden members have 0 votes (do not participate in elections)
// A member with votes: 0 can still be primary but cannot vote for others

// Factor 4: Connectivity
// The elected primary must be able to reach majority of members
// A member isolated in a minority partition cannot win (cannot get majority votes)

// Forcing a specific member to be primary (controlled failover):
rs.stepDown()   // on current primary: step down for 60s → triggers election
rs.stepDown(60) // step down for 60 seconds

// Or: set all other members' priority to 0, leaving only one eligible:
// (use during maintenance to ensure specific member becomes primary)
const cfg = rs.conf();
cfg.members.forEach((m, i) => {
    m.priority = (m.host === "mongo1:27017") ? 1 : 0;
});
rs.reconfig(cfg);
// mongo1 will win the next election (only eligible candidate)

// Checking current primary and election info:
rs.isMaster()
// {
//   hosts: ["mongo1:27017", "mongo2:27017", "mongo3:27017"],
//   primary: "mongo1:27017",
//   ismaster: true,
//   electionId: ObjectId("7fffffff0000000000000042"),
//   //                               ↑ term: 0x42 = 66
//   setVersion: 7,
//   ok: 1
// }

rs.status().members.find(m => m.stateStr === "PRIMARY")
// {
//   name: "mongo1:27017",
//   state: 1,
//   stateStr: "PRIMARY",
//   electionTime: Timestamp(1705313400, 1),
//   electionDate: ISODate("2024-01-15T10:30:00Z"),
//   configVersion: 7,
//   configTerm: 42
// }

// Arbiter use and limitations:
// An arbiter provides the third vote without storing data
// Saves on storage/RAM for small deployments
// AVOID arbiter in production for important data:
//   - If primary goes down: only 1 secondary remains (no redundancy)
//   - Arbiter cannot serve reads or become primary
//   - With arbiter: losing 1 node of 3 means you might only have 1 data copy
// Better: 3 full data-bearing members (majority = 2, any two can continue)
```

**Q6. What is a rollback and when does it occur in replica set failover?**
A: A rollback occurs when a former primary rejoins after failover and discovers it has writes that are not in the new primary's oplog. These writes were never acknowledged by a majority of members, so they are considered uncommitted and must be undone before the former primary can rejoin as a secondary:

```
When rollback happens:

  Timeline:
  T=0:  Primary (P1) accepts write W1 (w:1 — acknowledged by primary only)
  T=1:  W1 is in P1's oplog but NOT yet replicated to secondaries
  T=2:  P1 crashes (or network partition isolates P1)
  T=12: Secondaries elect P2 as new primary (W1 was never on secondaries)
  T=20: Application writes W2, W3, W4 to new primary P2
  T=60: P1 recovers and tries to rejoin the replica set

  Problem:
  P1's oplog: ... W1 (but NOT W2, W3, W4 — it was isolated)
  P2's oplog: ... W2, W3, W4 (but NOT W1 — it never arrived)
  Divergence: P1 has W1; P2's secondaries have W2/W3/W4

  MongoDB's resolution: rollback
  P1 detects: P2 has a higher election term → P2 is authoritative
  P1 must bring its oplog in sync with P2
  P1 rolls back W1: the write is UNDONE from P1's data files
  P1 saves rolled-back documents to: rollback/<collection>/<timestamp>.bson
  P1 then catches up with P2's oplog (applies W2, W3, W4)
  P1 rejoins as a secondary

Why rollback happens:
  Client used writeConcern: { w: 1 } → only primary acknowledged
  Primary crashed before replicating to majority
  New primary doesn't have the write → must be rolled back on rejoin

How to prevent rollback:
  Use writeConcern: { w: "majority" }
  → Write not acknowledged until majority has it
  → If primary crashes: majority already has the write → new primary has it too
  → No divergence → no rollback needed

// Detecting and handling rollback:
// MongoDB logs rollback events:
// [replication] rollback 1
// [replication] rollback ------ a
// [replication] rollback   { rollback key: ... }
// [replication] rollback ------ b

// Rolled-back data saved to:
// $dbpath/rollback/<dbname>.<collection>/<timestamp>.<ObjectId>.bson
// Use mongorestore to recover if needed:
mongorestore --db mydb --collection loans \
    /var/lib/mongodb/rollback/mydb.loans/2024-01-15T10-30-00.0.bson

// Application-level rollback handling:
// If application used w:1 and there was a rollback:
// The write "succeeded" from the client's perspective but was rolled back
// Application may show data that no longer exists in MongoDB
// → Application must handle eventual consistency or use w:"majority"

// Checking rollback status:
rs.status().members.filter(m => m.stateStr === "ROLLBACK")
// member in ROLLBACK state → actively rolling back → wait for SECONDARY state

// Node.js driver rollback awareness:
// The driver does NOT automatically detect rollback of past writes
// Use change streams with { fullDocumentBeforeChange: "required" } to monitor changes
// For critical financial data: always use w:"majority" to prevent rollback possibility

// Rollback data recovery:
async function checkForRollbackFiles(rollbackPath: string) {
    // Parse the .bson files in rollback directory
    // Each file contains documents that were rolled back
    // Application can decide: discard them or re-apply to new primary
    const files = fs.readdirSync(rollbackPath);
    for (const file of files) {
        if (file.endsWith('.bson')) {
            console.warn(`Rollback detected: ${file} — review and decide whether to re-apply`);
        }
    }
}
```

## Section 4: Replication Mechanics

**Q7. How does an initial sync work when a new secondary joins a replica set?**
A: Initial sync is the process by which a new member (or a recovering member that has fallen too far behind) gets a full copy of the primary's dataset. It involves cloning all data and then catching up with any writes that happened during the clone:

```javascript
// Initial sync steps (MongoDB 4.4+ parallel initial sync):

// Step 1: Choose sync source
// New member picks a sync source (usually the primary, or a secondary with good health)
// Preference: fastest sync source with lowest ping and most current oplog

// Step 2: Clone all collections (parallel in 4.4+)
// Copies every document in every database/collection
// Runs as multiple parallel threads for faster sync
// Records the oplog timestamp at START of clone: T_start

// Step 3: Build indexes
// Builds all indexes on the cloned data
// This is the slowest part for large collections with many indexes

// Step 4: Catch up with oplog
// During clone, primary continued accepting writes
// New secondary applies all oplog entries from T_start to "now"
// If sync takes 2 hours: applies 2 hours of oplog entries

// Step 5: Transition to SECONDARY
// Member transitions: STARTUP → STARTUP2 (syncing) → RECOVERING → SECONDARY
// Once oplog lag is below a threshold → accepts reads → becomes SECONDARY

// Monitoring initial sync progress:
rs.status()
// Member in STARTUP2 state with increasing initialSyncStatus
db.adminCommand({ replSetGetStatus: 1 }).initialSyncStatus
// {
//   failedInitialSyncAttempts: 0,
//   maxFailedInitialSyncAttempts: 10,
//   initialSyncStart: ISODate("2024-01-15T10:00:00Z"),
//   databases: {
//     databasesCloned: 2,
//     databasesToClone: 3,
//     collections: {
//       collectionsCloned: 15,
//       collectionsToClone: 20,
//       documentsCloned: 1500000,
//       approxTotalDataSize: 5000000000,
//       approxTotalBytesCopied: 3000000000
//     }
//   },
//   appliedOps: 150000    // oplog entries applied to catch up
// }

// Initial sync can fail if:
// The sync source's oplog is recycled faster than the clone completes
// → Oplog window is smaller than the time required for initial sync
// → initial sync restarts from scratch
// Fix: larger oplog OR temporarily reduce write load during sync

// Forcing a full resync (when secondary is too far behind):
// On the secondary:
rs.remove("secondary:27017")  // remove from set (on primary)
// Stop mongod on the secondary
// Delete ALL data files: rm -rf /var/lib/mongodb/*
// Start mongod again
// rs.add("secondary:27017")  // add back to set
// → Triggers fresh initial sync

// Or use rsync/file copy from primary (faster for large datasets):
// 1. Lock primary: db.fsyncLock()
// 2. rsync data directory to new secondary
// 3. Unlock primary: db.fsyncUnlock()
// 4. Start secondary with the copied data → will catch up via oplog (much less to replay)

// Initial sync performance settings:
// mongod.conf:
replication:
    initialSyncNumParallelCollections: 4  // parallel collection clones (default: 1 pre-4.4)
    initialSyncOplogBuffer: 100MB         // buffer for oplog during sync
```

**Q8. How does a secondary choose its sync source and what is the sync chain?**
A: Secondaries do not always replicate directly from the primary. In a replica set with geographic distribution or many members, MongoDB implements sync chaining — a secondary can replicate from another secondary, reducing the load on the primary:

```javascript
// Sync source selection algorithm:
// Each secondary independently selects its sync source based on:
// 1. Must have oplog at least as current as the secondary's current position
// 2. Must be within 30 seconds of the primary's optime (not too stale)
// 3. Must have a ping time within 2× the fastest member's ping time
// 4. Prefer members in the same datacenter (lower latency)
// 5. Prefer members that are not the primary (reduce primary load)

// Sync chain example:
// Datacenter A: Primary (mongo1) + Secondary (mongo2)
// Datacenter B: Secondary (mongo3) + Secondary (mongo4)
//
// Without sync chaining: mongo3 and mongo4 both replicate from mongo1 (cross-DC)
// With sync chaining:    mongo3 replicates from mongo1 (cross-DC)
//                        mongo4 replicates from mongo3 (same DC)
// → Primary only sends data to one cross-DC connection
// → Reduces bandwidth usage from primary

// Checking current sync sources:
rs.status().members.map(m => ({
    member:     m.name,
    state:      m.stateStr,
    syncSource: m.syncSourceHost
}))
// [
//   { member: "mongo1:27017", state: "PRIMARY",   syncSource: "" },
//   { member: "mongo2:27017", state: "SECONDARY", syncSource: "mongo1:27017" },
//   { member: "mongo3:27017", state: "SECONDARY", syncSource: "mongo1:27017" },
//   { member: "mongo4:27017", state: "SECONDARY", syncSource: "mongo3:27017" }  ← chaining
// ]

// Disabling sync chaining (force all secondaries to sync from primary):
const cfg = rs.conf();
cfg.settings.chainingAllowed = false;
rs.reconfig(cfg);
// When to disable: if sync chain member goes down → cascading sync source failures
// → secondary falls behind because its chain source is gone
// Tradeoff: more connections to primary vs chain reliability

// Forcing a specific sync source:
// On the secondary (mongosh):
db.adminCommand({ replSetSyncFrom: "mongo1:27017" });
// Useful during maintenance: force a specific sync source temporarily

// Sync lag and its implications:
// replication lag = primary_optime - secondary_optime (in seconds)
// Check: rs.printSecondaryReplicationInfo()
// High lag causes:
// 1. readPreference:secondary returns stale data
// 2. Transactions may not find sufficient snapshot (snapshot too old)
// 3. writeConcern:majority acknowledgement is delayed (primary waits for majority)
// 4. Delayed secondary may have insufficient lag (too short) for point-in-time recovery

// Lag monitoring in application:
const db = client.db("admin");
const status = await db.command({ replSetGetStatus: 1 });
const primary = status.members.find(m => m.state === 1);
const secondaries = status.members.filter(m => m.state === 2);

for (const secondary of secondaries) {
    const lagSeconds = primary.optimeDate - secondary.optimeDate / 1000;
    if (lagSeconds > 30) {
        console.warn(`Secondary ${secondary.name} is ${lagSeconds}s behind primary`);
    }
}
```

## Section 5: Read and Write Concerns with Replica Sets

**Q9. How do readPreference and readConcern interact with replica sets and what are the tradeoffs?**

```javascript
// readPreference: WHERE to send reads (which member)
// readConcern: WHAT data to read (how consistent)
// These are orthogonal settings — choose each independently

// ── readPreference options ─────────────────────────────────────────────────────

// primary (default): all reads go to primary
// → Most consistent (sees latest writes immediately)
// → Primary handles all load
const collection = db.collection("loans", {
    readPreference: "primary"
});

// primaryPreferred: primary if available, secondary otherwise
// → Falls back gracefully during primary failover
// → Reads may be temporarily stale during election
const collection = db.collection("loans", {
    readPreference: "primaryPreferred"
});

// secondary: all reads go to a secondary
// → Offloads primary read load
// → Data may be stale (replication lag)
// → Cannot guarantee seeing your own writes (use sessions for causal consistency)
const collection = db.collection("loans", {
    readPreference: "secondary"
});

// secondaryPreferred: secondary if available, primary if all secondaries are down
// → Good for read-heavy workloads with eventual consistency tolerance
const collection = db.collection("loans", {
    readPreference: "secondaryPreferred"
});

// nearest: member with lowest network latency (primary or secondary)
// → Lowest read latency, may be very stale
// → Use only for data where staleness is completely irrelevant
const collection = db.collection("geo_cache", {
    readPreference: "nearest"
});

// Tag-based readPreference (route reads to specific datacenters or member types):
const collection = db.collection("loans", {
    readPreference: new ReadPreference("secondary", [{ datacenter: "us-east" }])
});
// Requires members to be tagged:
// rs.conf().members[0].tags = { datacenter: "us-east" }

// ── readConcern options ────────────────────────────────────────────────────────

// "local" (default): reads from the member's local state
// → May see data that is rolled back (if w:1 writes occur and primary fails)
// → Fastest: no coordination needed
db.loans.findOne({ _id: loanId }, { readConcern: { level: "local" } });

// "available": like "local" but does not wait for any guarantees
// → Only for sharded clusters, even more relaxed than "local"
// → Rarely used; can return orphaned documents during chunk migrations

// "majority": reads data acknowledged by majority of replica set members
// → Guarantees data will not be rolled back
// → Requires MongoDB to track which data has reached majority
// → Slightly slower than "local" (must check majority watermark)
db.loans.findOne({ _id: loanId }, { readConcern: { level: "majority" } });

// "linearizable": strongest consistency guarantee
// → Reads reflect all successful majority-acknowledged writes that completed before the read
// → Only works with readPreference: "primary"
// → Must issue a read to primary AND wait for confirmation it is still primary
// → Highest latency (involves a majority acknowledgement round trip)
// → Use for: reading data where absolutely no stale read is acceptable
db.loans.findOne({ _id: loanId }, { readConcern: { level: "linearizable" } });

// "snapshot": consistent point-in-time read (for transactions — covered in transactions guide)

// Causal consistency across operations (without full transactions):
// Problem: write to primary → read from secondary → read may be stale
const session = client.startSession({ causalConsistency: true });
try {
    // Write:
    await db.loans.updateOne(
        { _id: loanId }, { $set: { status: "approved" } },
        { session, writeConcern: { w: "majority" } }
    );
    // Read (even on secondary): guaranteed to see the above write
    const loan = await db.loans.findOne(
        { _id: loanId },
        { session, readPreference: "secondary", readConcern: { level: "majority" } }
    );
    // loan.status === "approved" ← guaranteed (causal consistency)
} finally {
    await session.endSession();
}
// Session tracks operationTime + clusterTime
// Secondary receiving the read waits until its optime ≥ the session's operationTime
// → Causally consistent reads from secondaries without full transaction overhead
```

**Q10. What is write concern and how does it interact with replica set durability?**

```javascript
// writeConcern: how many members must acknowledge a write before client receives success

// { w: 0 } — fire and forget:
// Primary doesn't even acknowledge → no guarantees
// Client never knows if write succeeded
// Use only for: metrics, logs where loss is acceptable
await db.metrics.insertOne(event, { writeConcern: { w: 0 } });

// { w: 1 } — primary acknowledged (default):
// Write durably stored on primary's journal
// If primary crashes before replicating: ROLLBACK risk on rejoin
// Client thinks write succeeded, but it may disappear if primary fails
await db.loans.insertOne(loan, { writeConcern: { w: 1 } });

// { w: "majority" } — majority acknowledged:
// Primary + sufficient secondaries have the write before client notified
// Write survives primary crash (majority of members have it)
// New primary MUST have this write (it was on majority → it's in any majority set)
// No rollback risk for majority-acknowledged writes
await db.loans.insertOne(loan, { writeConcern: { w: "majority" } });

// { w: 2 } — specific count:
// Primary + 1 secondary must acknowledge
// More specific than "majority" but less flexible (breaks if you add members)
// Prefer { w: "majority" } over { w: N } for flexibility

// { j: true } — journaled:
// Write must be written to the WiredTiger journal (fsync'd to disk) before ack
// Without j:true: write is in memory (buffer) → server crash loses uncommitted buffer
// With j:true: write survives OS crash on the acknowledging member
// w:"majority" implies j:true on the acknowledging members (usually)
await db.loans.insertOne(loan, { writeConcern: { w: "majority", j: true } });

// { wtimeout: N } — timeout for write concern:
// If majority acknowledgement doesn't happen within N ms → return error
// WITHOUT aborting the write! (write may still propagate eventually)
// Use to prevent indefinite blocking when a secondary is down:
await db.loans.insertOne(loan, {
    writeConcern: { w: "majority", j: true, wtimeout: 5000 }
});
// After 5 seconds with no majority ack: throws WriteConcernError
// But the write may have happened on the primary! (not rolled back)
// Application should check: was the write eventually applied?

// Write concern and elections:
// During election (10-30 seconds): primary is unavailable
// Writes with w:"majority" will block until new primary is elected
// With wtimeout: fail after timeout (must retry)

// Application write concern strategy for a fintech platform:
// Financial data (loans, repayments, accounts): w:"majority", j:true
// → Zero rollback risk, durable on majority before confirmation
// Audit logs: w:1 or w:"majority" (depends on compliance requirements)
// Metrics/analytics: w:0 or w:1 (acceptable to lose)

// Setting default write concern at client level (applies to all operations):
const client = new MongoClient(uri, {
    writeConcern: { w: "majority", j: true }
});

// Or per-collection:
const loans = db.collection("loans", {
    writeConcern: { w: "majority", j: true }
});

// Checking majority acknowledgement in practice:
async function safeInsertLoan(loan: LoanDocument): Promise<void> {
    const result = await db.loans.insertOne(loan, {
        writeConcern: { w: "majority", j: true, wtimeout: 10000 }
    });

    // result.acknowledged is true only if w:"majority" was satisfied
    if (!result.acknowledged) {
        throw new Error("Write not acknowledged by majority");
    }
    // result.insertedId: the ObjectId of the inserted document
}
```

## Section 6: Operational Patterns

**Q11. How do you add, remove, and reconfigure replica set members without downtime?**

```javascript
// Adding a new secondary:
// Step 1: Start the new mongod process with --replSet rs0
// mongod.conf on new member:
// replication:
//   replSetName: "rs0"
// net:
//   bindIp: 0.0.0.0
//   port: 27017

// Step 2: Add to replica set from primary:
rs.add("new-secondary:27017")
// → New member joins as STARTUP2 → begins initial sync
// → Transitions: STARTUP2 → RECOVERING → SECONDARY

// Adding with specific configuration:
rs.add({
    host: "new-secondary:27017",
    priority: 2,
    votes: 1,
    hidden: false,
    tags: { datacenter: "us-west", purpose: "read_replica" }
});

// Adding a hidden member (for backup, analytics):
rs.add({
    host: "analytics-server:27017",
    priority: 0,      // cannot be primary
    hidden: true,     // invisible to clients
    votes: 1          // can vote in elections
});

// Adding a delayed member (point-in-time recovery):
rs.add({
    host: "delayed-secondary:27017",
    priority: 0,
    hidden: true,
    slaveDelay: 3600,  // 1 hour behind primary (seconds)
    votes: 1
});
// Use case: accidental data deletion on primary → delayed secondary still has it
// Recover by promoting the delayed secondary and extracting the data

// Removing a member:
rs.remove("old-secondary:27017")
// → Member removed from config → transitions to REMOVED state
// → Application should update connection strings

// Modifying member configuration (reconfig):
const config = rs.conf();
// Find the member to modify:
const memberIdx = config.members.findIndex(m => m.host === "mongo2:27017");
config.members[memberIdx].priority = 5;
config.members[memberIdx].tags = { purpose: "analytics" };
// Increment the config version (MongoDB does this automatically in rs.reconfig):
rs.reconfig(config);
// reconfig propagates to all members via heartbeat within seconds

// Force reconfig (when majority is unavailable):
rs.reconfig(config, { force: true });
// WARNING: force reconfig can cause data loss if used incorrectly
// Only use when: majority of members are permanently down and cannot recover

// Stepdown and maintenance:
// Step down primary for maintenance:
rs.stepDown(120)  // step down for 120 seconds (will not re-elect itself during this time)
// → Triggers election among secondaries
// → Perform maintenance on the former primary
// → After maintenance: rejoin as secondary automatically

// Planned failover (zero-downtime primary maintenance):
// 1. Ensure secondaries are caught up:
rs.printSecondaryReplicationInfo()  // check lag is < 1s

// 2. Step down primary:
rs.stepDown(300)  // step down for 5 minutes

// 3. Secondaries elect new primary (~10-30s)
// 4. Perform maintenance on old primary (now secondary)
// 5. Old primary automatically rejoins as secondary after stepDown timeout
// 6. Optionally step down the new primary to restore original primary:
//    rs.stepDown() on new primary (if original is preferred)
```

**Q12. How do you monitor replica set health and what are the key alerts to configure?**

```javascript
// Key metrics and commands:

// 1. Overall replica set status:
rs.status()
// Check: all members are SECONDARY or PRIMARY (not DOWN, RECOVERING, UNKNOWN)
// Alert if: any member.health === 0 (unreachable)

// 2. Replication lag per secondary:
rs.printSecondaryReplicationInfo()
// Alert if: lag > 30 seconds for any secondary
// Critical if: lag > oplog window (secondary will need full resync)

// 3. Oplog window remaining:
db.getReplicationInfo()
// Alert if: timeDiffHours < 24 (oplog may be exhausted before secondary recovers)

// 4. Election history:
db.adminCommand({ replSetGetStatus: 1 }).electionCandidateMetrics
// Frequent elections indicate network instability or primary crashes

// 5. Current primary:
db.adminCommand({ hello: 1 }).primary
// Alert if: primary changes more than N times per day

// Programmatic health check in Node.js:
async function checkReplicaSetHealth(client: MongoClient): Promise<HealthReport> {
    const adminDb = client.db("admin");
    const [status, replicationInfo] = await Promise.all([
        adminDb.command({ replSetGetStatus: 1 }),
        adminDb.command({ getReplicationInfo: 1 })
    ]);

    const alerts: string[] = [];

    // Check member health:
    const downMembers = status.members.filter(m => m.health === 0);
    if (downMembers.length > 0) {
        alerts.push(`DOWN members: ${downMembers.map(m => m.name).join(", ")}`);
    }

    // Check replication lag:
    const primary = status.members.find(m => m.state === 1);
    const laggingMembers = status.members
        .filter(m => m.state === 2)
        .filter(m => {
            const lagMs = primary.optimeDate.getTime() - m.optimeDate.getTime();
            return lagMs > 30000;  // > 30 seconds
        });
    if (laggingMembers.length > 0) {
        alerts.push(`Lagging members: ${laggingMembers.map(m => `${m.name}(${m.optimeDate})`).join(", ")}`);
    }

    // Check oplog window:
    if (replicationInfo.timeDiff < 86400) {  // < 24 hours
        alerts.push(`Oplog window critical: ${replicationInfo.timeDiffHours.toFixed(1)} hours remaining`);
    }

    // Check if we have a primary:
    if (!primary) {
        alerts.push("NO PRIMARY ELECTED — replica set is in read-only mode");
    }

    return {
        healthy: alerts.length === 0,
        memberCount: status.members.length,
        primaryName: primary?.name ?? null,
        alerts
    };
}

// Setting up MongoDB Atlas / ops monitoring alerts:
// Key alert conditions for production:
// - Replication lag > 10 seconds (warning), > 60 seconds (critical)
// - No primary for > 30 seconds
// - Oplog window < 24 hours
// - Member state changes (any member goes DOWN or RECOVERING)
// - Election events (more than 2 per hour)
// - Rollback detected (any member enters ROLLBACK state)
```

## Section 7: Scenario-Based Questions

**Q13. "Your primary MongoDB server goes down at 2 AM. Walk through exactly what happens in the replica set and what your on-call engineer needs to do."**

```
Timeline of events (3-member replica set: mongo1=primary, mongo2=secondary, mongo3=secondary):

T=2:00:00 AM — Primary (mongo1) crashes (hardware failure, OOM kill, etc.)

T=2:00:02 AM — mongo2 and mongo3: last heartbeat from mongo1 was successful
T=2:00:04 AM — mongo2 and mongo3: send heartbeat to mongo1 — no response
T=2:00:06 AM — mongo2 and mongo3: second heartbeat timeout — no response
T=2:00:10 AM — electionTimeoutMillis (10s) exceeded — mongo2 or mongo3 calls election

T=2:00:10 AM — mongo2 increments its term (42 → 43) and sends RequestVote to mongo3
T=2:00:10.5 AM — mongo3 receives RequestVote:
    - mongo2's term (43) > mongo3's term (42) ✓
    - mongo2's oplog (T=1:59:55) ≥ mongo3's oplog (T=1:59:50) ✓
    - mongo3 votes YES for mongo2 in term 43

T=2:00:11 AM — mongo2 has 2 votes (self + mongo3) = majority of 3 → wins election
T=2:00:11 AM — mongo2 announces itself PRIMARY (term 43)
T=2:00:11 AM — mongo3 transitions to SECONDARY, begins replicating from mongo2

T=2:00:11 AM — Application drivers:
    - Connections to mongo1: socket error / connection refused
    - Drivers retry with SDAM (Server Discovery and Monitoring)
    - Driver sends hello to remaining members → mongo2 says it's now PRIMARY
    - Driver updates its primary knowledge → reconnects to mongo2

T=2:00:14 AM — Application is fully recovered (connected to new primary mongo2)
Total write downtime: ~14 seconds

What operations were affected:
    - Writes with w:"majority": blocked from 2:00:00-2:00:11, then succeeded on mongo2
    - Writes with w:1: succeeded on mongo1 just before crash — CHECK FOR ROLLBACK RISK
    - Reads with readPreference:primary: failed 2:00:00-2:00:11
    - Reads with readPreference:secondary: unaffected (mongo3 still serving reads)

On-call engineer checklist:

1. VERIFY what happened (do NOT immediately restart mongo1):
   ssh admin@mongo1
   # Check: is mongod running? OOM? Disk full? Hardware failure?
   journalctl -u mongod --since "02:00:00" --until "02:01:00"
   df -h /var/lib/mongodb   # disk space
   dmesg | grep -i "out of memory"

2. CHECK current replica set state:
   # Connect to new primary (mongo2):
   mongosh --host mongo2:27017
   rs.status()
   # Verify: mongo2=PRIMARY, mongo3=SECONDARY, mongo1=DOWN

3. CHECK for rollbacks:
   ls /var/lib/mongodb/rollback/   # on mongo1 (if you can access it)
   # If rollback files exist: review and decide whether to re-apply
   # Check which writes used w:1 around 2:00:00 AM

4. CHECK replication lag on mongo3:
   rs.printSecondaryReplicationInfo()
   # mongo3 should be caught up quickly (only seconds behind)

5. FIX mongo1 (after diagnosing root cause):
   # For OOM: increase memory, reduce mongod cache, add swap
   # For disk: clear space, expand volume
   # For hardware: replace server or use a new instance

6. RESTART mongo1 and let it rejoin:
   systemctl start mongod
   # Watch rs.status() — mongo1 will enter RECOVERING → SECONDARY
   # If mongo1 has divergent writes: will enter ROLLBACK → SECONDARY
   rs.status()  # poll until mongo1 shows SECONDARY

7. DECIDE whether to restore original topology (optional):
   # If mongo1 is preferred primary (higher priority):
   # rs.stepDown() on mongo2 → triggers new election → mongo1 wins (higher priority)
   # If no priority difference: keep mongo2 as primary (it's already running fine)

8. POST-MORTEM:
   # Review: what caused the crash?
   # Review: did any w:1 writes get rolled back? How many? Impact?
   # Action: switch all financial writes to w:"majority" if not already
   # Action: set up alerts for member health, replication lag, elections
```

**Q14. "Your secondary is 6 hours behind the primary. The oplog window is 8 hours. What do you do and what is the risk?"**

```javascript
// Situation assessment:
// Replication lag: 6 hours
// Oplog window: 8 hours
// Time until secondary CAN'T catch up: 8 - 6 = 2 hours remaining

// Risk: if nothing changes:
// Secondary falls more than 8 hours behind → oplog is recycled
// Secondary's last known position no longer exists in the oplog
// Secondary cannot apply changes → enters RECOVERING state
// Must perform a FULL INITIAL SYNC (could take hours/days for large dataset)

// Immediate actions:

// Step 1: Diagnose WHY the secondary is lagging

// Check network bandwidth between primary and secondary:
// ping -s 65000 secondary-host  (large ping to measure bandwidth saturation)
// iperf3 -s on secondary, iperf3 -c secondary-host on primary

// Check if secondary is I/O bound (applying oplog too slowly):
db.adminCommand({ serverStatus: 1 }).metrics.repl.network
// {
//   bytesReceived: 1073741824,   // 1GB received
//   getmores: 50000,             // number of oplog getmore requests
//   ops: { getmores: 50000, readDocumentOps: 5000000 }
// }

// Check oplog apply rate:
db.adminCommand({ serverStatus: 1 }).metrics.repl.apply
// {
//   batches: { num: 1000, totalMillis: 500000 },  // slow batches?
//   ops: 5000000
// }
// If batches.totalMillis / batches.num > 1000ms: secondary is CPU/IO bound

// Check if secondary has long-running queries blocking oplog apply:
db.adminCommand({ currentOp: true, active: true }).inprog.filter(
    op => op.secs_running > 30
)
// Long-running queries prevent oplog application on secondary!
// → Kill the long queries if they are blocking replication

// Step 2: Reduce pressure on the secondary

// If secondary is I/O bound from serving reads:
// → Route reads away from this secondary temporarily:
// Update application readPreference to primaryPreferred or specific secondary tag
// This frees I/O bandwidth for oplog application

// If secondary is CPU bound:
// → Check for expensive oplog operations (large array modifications, many field updates)
// → Primary may be doing large bulk operations → slow on secondary to replay

// Step 3: Buy more time (increase oplog if possible):
// CANNOT increase oplog size without downtime on the secondary
// (oplog resize requires a restart in pre-6.0; MongoDB 6.0+ allows online resize)

// MongoDB 6.0+ online oplog resize:
db.adminCommand({ replSetResizeOplog: 1, size: 20480 })  // Increase to 20GB
// Does NOT affect running processes → no downtime

// Step 4: Monitor progress closely:
// Poll every 5 minutes:
function checkLagTrend() {
    return {
        lag: rs.printSecondaryReplicationInfo(),
        oplogHours: db.getReplicationInfo().timeDiffHours
    };
}
// Is the lag DECREASING? → secondary is catching up → will be fine
// Is the lag INCREASING? → secondary cannot keep up → escalate

// Step 5: If lag is still increasing and oplog window is < 1 hour away:
// Option A: Freeze the secondary (stop it receiving reads) to let it catch up
//   → db.adminCommand({ isMaster: 1 }) on secondary to verify it's actually secondary
//   → Reconfigure readPreference away from this secondary in application

// Option B: Initiate full resync NOW while you still have time:
//   (Better to resync deliberately than have it fail and need emergency resync)
//   On secondary: mongosh
//   db.adminCommand({ resync: 1 })  // pre-4.0 command
//   Or: stop mongod → delete data files → restart → initial sync begins

// Step 6: After secondary catches up, investigate root cause:
// Common causes of severe replication lag:
// a. Network congestion (secondary in another datacenter with limited bandwidth)
//    → Solution: increase bandwidth OR use sync chaining (relay secondary in same DC)
// b. Secondary serves too many read queries → I/O saturated
//    → Solution: move read traffic to a different secondary; add more read replicas
// c. Primary is doing large bulk operations (mass updates, large inserts)
//    → Solution: rate-limit bulk operations; use $sleep between batches
// d. Secondary hardware is underpowered vs primary
//    → Solution: use identical hardware for all replica set members
// e. Oplog application is single-threaded and slow for certain operation types
//    → Solution: MongoDB 4.0+ parallel oplog apply (enabled by default)

// Prevention: oplog size + monitoring:
// Rule of thumb: oplog should hold at least 24 hours of primary writes
// For a busy primary (10GB writes/day): at minimum a 10GB oplog
// Set alert: replication lag > 30 minutes → page on-call
// Set alert: oplog window < 24 hours → investigate disk and oplog size
```

**Tip for interviews:** Five things separate strong candidates on MongoDB replica sets: (1) explaining the **oplog as a capped, idempotent, ordered log** — knowing that entries are stored in their final form (not the original update operator) making them safe to replay multiple times, that the oplog being capped means secondaries that fall behind too far must do a full initial sync, and that the oplog window (time span of entries in the oplog) is the metric to monitor for recovery safety; (2) being precise about **what triggers an election and how the term-based voting works** — a secondary waits `electionTimeoutMillis` (10s default) without a heartbeat from the primary, then increments its term, solicits votes (each member votes once per term for the candidate with the freshest oplog), and wins if it receives votes from a majority; the term increment is what prevents split-brain (a former primary with a stale term cannot win); (3) explaining **rollback — when it happens and how to prevent it** — a former primary that had `w:1` writes that never reached the majority must roll them back when rejoining, because the new primary doesn't have them and is authoritative by virtue of its higher term; the prevention is always using `w:"majority"` for important data so that any surviving majority set includes the write; (4) understanding **the write concern / read preference matrix and their durability implications** — `w:1` is the most common source of surprising data loss in MongoDB deployments, `w:"majority"` is the correct default for any data that matters, and the latency cost (one extra round trip to secondaries) is worth it; and (5) knowing **how to read `rs.status()` diagnostics in a failure scenario** — being able to identify which members are DOWN, calculate replication lag from `optimeDate` differences, estimate whether the secondary can still catch up from the oplog window, and describe the recovery steps including when a full initial sync becomes necessary.
