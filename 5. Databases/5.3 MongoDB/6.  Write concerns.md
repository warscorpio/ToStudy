# Write Concerns: `w:0`, `w:1`, `w:majority` — Durability Tradeoffs: Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a write concern in MongoDB and what fundamental problem does it solve?**

A: A write concern is a MongoDB configuration that specifies how many nodes in a replica set must confirm receipt of a write operation before the driver returns success to the application. It is the primary knob controlling the **durability–latency tradeoff**: more durability requires more acknowledgments, which takes longer.

```
The fundamental problem: asynchronous replication

MongoDB replica set (3 nodes):
  ┌─────────────────────────────────────────────────────────────┐
  │  Primary (P)          Secondary (S1)        Secondary (S2)  │
  │  [Write arrives]       [Replicating...]      [Replicating...]│
  │                          ↑                        ↑          │
  │                  asynchronous, via oplog    asynchronous     │
  └─────────────────────────────────────────────────────────────┘

Without write concerns, the question is: when do we tell the application "success"?
  a) Immediately when the write is buffered (fast, potentially lossy)
  b) After the primary persists it (moderate, safe from primary bugs)
  c) After a majority of nodes persist it (slow, safe from primary failure)
  d) Never — fire and forget (fastest, no durability guarantee at all)

Write concerns answer this question per operation (or per collection, or per client).
```

```javascript
// Write concern is specified wherever you write:
const { MongoClient } = require('mongodb');

// Option 1: Client-level default (applies to all operations)
const client = new MongoClient(uri, {
  writeConcern: { w: 'majority', j: true, wtimeout: 5000 }
});

// Option 2: Collection-level override
const orders = db.collection('orders');

// Option 3: Per-operation override
await orders.insertOne(document, {
  writeConcern: { w: 'majority', j: true }
});

// Option 4: None specified — uses default (w:majority in MongoDB 5.0+ for replica sets)
await orders.insertOne(document);
```

**The three fields in a write concern object:**
```javascript
{
  w: 0 | 1 | 2 | N | 'majority' | 'tagSetName',
  //  ↑ How many nodes must acknowledge
  j: true | false,
  //  ↑ Must the write be flushed to the on-disk journal?
  wtimeout: 5000
  //  ↑ Milliseconds to wait for acknowledgment (not a rollback — see Q12)
}
```

**Q2. How does replication work in a MongoDB replica set and why is it central to understanding write concerns?**

A: A MongoDB replica set is a group of `mongod` instances that maintain the same dataset. One member is the **primary** (accepts all writes); the rest are **secondaries** (replicate from the primary). Understanding how writes flow through this architecture is prerequisite to understanding what each write concern guarantees:

```
Write flow in a 3-member replica set:

Client ──WRITE──> Primary (P)
                     │
                     │ 1. Write applied to in-memory data (WiredTiger cache)
                     │ 2. Written to oplog (capped collection in local.oplog.rs)
                     │ 3. Optionally flushed to journal (controlled by j:true/false)
                     │
                     ├──────────────── async replication ─────────────────────┐
                     │                                                         │
              Secondary (S1)                                          Secondary (S2)
              - Tails primary's oplog                                 - Tails primary's oplog
              - Applies operations in order                           - Applies operations in order
              - Sends acknowledgment to primary when done             - Sends acknowledgment

The oplog:
  - A special capped collection in the 'local' database
  - Records every write operation in an idempotent format
  - Secondaries maintain a "replication lag" — how far behind the primary they are
  - Typical lag: <1ms to seconds depending on network and write volume
  - Lag is the gap between "primary has the data" and "secondary has the data"

Failover:
  - If the primary becomes unreachable, secondaries elect a new primary
  - Writes that were on the old primary but NOT yet replicated are ROLLED BACK
  - This is the core danger that write concerns are designed to address
```

```javascript
// Monitoring replication lag (essential for capacity planning):
// From the primary mongosh:
db.adminCommand({ replSetGetStatus: 1 }).members.map(m => ({
  name:     m.name,
  stateStr: m.stateStr,
  lag:      m.optimeDate ? new Date() - m.optimeDate : null,  // ms behind primary
  health:   m.health,
}));

// Output:
// [
//   { name: 'mongo1:27017', stateStr: 'PRIMARY', lag: 0 },
//   { name: 'mongo2:27017', stateStr: 'SECONDARY', lag: 45 },  ← 45ms behind
//   { name: 'mongo3:27017', stateStr: 'SECONDARY', lag: 62 },
// ]
```

## Section 2: `w:0` — Unacknowledged

**Q3. What does `w:0` mean and when is it appropriate?**

A: `w:0` (unacknowledged) is "fire and forget" — the driver sends the write to MongoDB over the network and immediately returns success without waiting for any acknowledgment from the server. MongoDB may not have received the data at all:

```javascript
// w:0 behavior: driver doesn't wait for any server response
await collection.insertOne(
  { event: 'page_view', userId: '123', timestamp: new Date() },
  { writeConcern: { w: 0 } }
);
// Returns immediately — typically <1ms from application's perspective
// MongoDB may or may not have received this data

// The driver even ignores write errors:
// - Document validation failures: silently ignored
// - Duplicate key violations: silently ignored
// - Network failures: silently ignored
// No error is ever returned with w:0

// What w:0 does NOT protect against:
// ✗ Network failure between driver and MongoDB
// ✗ MongoDB process crash (data in OS socket buffer, never received)
// ✗ Primary crash before persisting the write
// ✗ Replication lag (never replicated — always just one server)
// ✗ Write errors (duplicate keys, validation failures)
```

**When `w:0` is appropriate:**
```javascript
// ✓ High-volume telemetry where occasional loss is acceptable
// ✓ Real-time dashboards that re-aggregate from the source anyway
// ✓ Buffered metrics that are also stored elsewhere (dual-write)
// ✓ Session activity updates ("user last seen at") — approximate is fine
// ✓ Page view counts — approximate count is the goal anyway

// Classic appropriate use case: game analytics
class GameAnalytics {
  async trackEvent(event: AnalyticsEvent): Promise<void> {
    // High volume: 100K events/second
    // Acceptable loss: <0.1% of events
    // Latency requirement: must not slow down game loop
    await this.events.insertOne(event, { writeConcern: { w: 0 } });
    // Returns immediately — game loop never waits for DB
  }
}

// NEVER use w:0 for:
// ✗ User account data, passwords, settings
// ✗ Financial transactions, orders
// ✗ Any data where loss is customer-visible or compliance-relevant
// ✗ Primary keys / IDs your application stores elsewhere
```

**Q4. What are the specific data loss scenarios unique to `w:0`?**

A:

```
Failure scenario 1 — Network packet loss:
  Application: insertOne(..., {w:0}) → driver sends TCP packet
  Network: packet is dropped (load balancer restart, network hiccup)
  MongoDB: never receives the write
  Application: already returned "success" (w:0 means no acknowledgment waited)
  Result: write is permanently lost

Failure scenario 2 — MongoDB process crash:
  Application: insertOne(..., {w:0}) → driver sends write, MongoDB receives it
  MongoDB: write is in OS receive buffer, not yet processed
  MongoDB process: crashes (OOM, SIGKILL)
  Result: write is permanently lost (was in OS buffer, not in MongoDB storage)

Failure scenario 3 — Connection pool recycling / reset:
  Application: insertOne(..., {w:0})
  MongoDB driver: uses a pooled connection that gets reset before write completes
  Result: write may be lost, no error reported

Failure scenario 4 — MongoDB queue full:
  MongoDB: write queue is full (under extreme load)
  MongoDB: drops the write silently
  Application: already returned "success"
  Result: write is permanently lost

Contrast with w:1:
  Each failure above would result in a network error or server error
  returned to the application (because the driver waits for acknowledgment)
  The application knows the write failed and can retry or alert
```

## Section 3: `w:1` — Acknowledged

**Q5. What does `w:1` guarantee and what doesn't it guarantee?**

A: `w:1` means the primary node has acknowledged receiving and applying the write. This prevents the network and process-level failures that `w:0` cannot detect, but it provides no guarantee about replication to secondary nodes:

```javascript
// w:1 guarantees:
// ✓ MongoDB primary received the write
// ✓ Write was applied to the primary's WiredTiger in-memory storage
// ✓ Write was recorded in the primary's oplog
// ✓ Network errors are detected and propagated to the application
// ✓ Document validation errors are detected and returned
// ✓ Duplicate key errors are detected and returned

// w:1 does NOT guarantee:
// ✗ Write has been replicated to any secondary
// ✗ Write has been flushed to disk (unless j:true is also set)
// ✗ Write survives primary failure before replication

await collection.insertOne(orderDocument, { writeConcern: { w: 1 } });
// Returns after primary acknowledges — typically 1-5ms on LAN
// Error is thrown if: duplicate key, validation failure, network error
// No error if: primary crashes after this returns but before replication

// The exact durability of w:1 without j:true:
// WiredTiger has a journal that commits every 100ms by default
// Between journal commits, data is in memory
// If mongod process crashes (SIGKILL, OOM): data in last 100ms may be lost
// If the server machine crashes (power loss): data not in journal is lost
// If the primary fails over: unreplicated data is rolled back
```

**Q6. Why can data written with `w:1` be lost after a primary failover, and what does "rollback" mean?**

A: This is the most important practical limitation of `w:1`. When a primary fails, the remaining nodes elect a new primary. Writes that were only on the old primary — not yet replicated to any secondary — are rolled back when the old primary recovers and rejoins the replica set:

```
Scenario: 3-node replica set, write concern w:1

Timeline:
  t=0:   Order #9999 written to Primary P1 (w:1 returns success to app)
          ↓ oplog entry created on P1
          ↓ replication begins async to S1 and S2

  t=1ms: App receives "write success" for order #9999
          Replication has NOT completed yet (S1 and S2 don't have #9999 yet)

  t=2ms: P1 crashes (power failure, OOM kill, hardware failure)
          Order #9999 exists only in P1's files (which are now inaccessible)

  t=3s:  S1 and S2 detect P1 is gone → election begins → S1 becomes new primary
          S1 does NOT have order #9999 (was replicated 0% at crash time)
          S2 does NOT have order #9999

  t=4s:  App tries to read order #9999 from the new primary S1
          → Not found. The order is "gone."
          The customer was charged but no order exists in the system.

  t=300s: P1 comes back online, discovers it's no longer primary
          P1 "rolls back" its unreplicated writes to match the new primary's state
          P1 writes order #9999 to a rollback file:
          /var/lib/mongodb/rollback/orders.1705312800000.bson
          (A BSON file the DBA can manually examine — not automatically recovered)
          P1 joins as a secondary with order #9999 gone from its oplog

Result: Order #9999 is permanently gone from the live database.
        A manual recovery attempt from the rollback file may restore it,
        but this requires DBA intervention and is not automatic.
```

```javascript
// The rollback file can be manually inspected:
// mongorestore --db myapp --collection orders /var/lib/mongodb/rollback/orders.timestamp.bson
// But the operator must manually review and decide to restore

// Monitoring for rollbacks (indicates w:1 data loss occurred):
db.adminCommand({ replSetGetStatus: 1 }).members.forEach(m => {
  if (m.rollbackId > 0) {
    console.log(`Node ${m.name} has rollback files! Investigate immediately.`);
  }
});
```

## Section 4: `w:majority`

**Q7. What does `w:majority` guarantee and how is "majority" calculated?**

A: `w:majority` means the write must be acknowledged by a **majority** of the replica set's voting members before the driver returns success. A majority is defined as more than half of all voting members:

```
Majority calculation:
  3-member replica set:  majority = floor(3/2) + 1 = 2 nodes
  5-member replica set:  majority = floor(5/2) + 1 = 3 nodes
  7-member replica set:  majority = floor(7/2) + 1 = 4 nodes
  2-member replica set:  majority = 2 nodes (PSA topology is special — see below)

With w:majority in a 3-node replica set:
  Write must be acknowledged by at least 2 of 3 nodes (primary + 1 secondary minimum)

  t=0:   App sends insertOne with w:majority
  t=1ms: Primary P1 applies write, sends async replication to S1 and S2
  t=3ms: S1 replicates the write, sends acknowledgment to P1
  t=3ms: P1 now has acknowledgments from P1 (itself) + S1 = 2 = majority
  t=3ms: Primary returns success to driver
  t=4ms: S2 eventually replicates the write (P1 doesn't need to wait for S2)

Guarantee:
  ✓ Write exists on at least 2 of 3 nodes
  ✓ If P1 fails, either S1 or S2 (both are candidates for the new primary) has the write
  ✓ The new primary was part of the majority that acknowledged → has the write
  ✓ Write cannot be "rolled back" by a standard primary failover
```

```javascript
// w:majority usage:
await collection.insertOne(orderDocument, {
  writeConcern: {
    w: 'majority',  // Most durable standard option
    j: true,        // Also flush to journal (see Q10)
    wtimeout: 5000  // Timeout in ms (see Q12)
  }
});

// What w:majority does NOT guarantee (edge cases):
// ✗ Write survives catastrophic loss of a majority of nodes simultaneously
//   (e.g., 2 of 3 nodes lose power at the same moment — this IS data loss)
// ✗ Write survives a network partition where the minority elects a new primary
//   (requires specific topology failures + configuration that normally shouldn't happen)
// ✓ For standard single-primary-fails scenarios: complete protection

// Comparing w values for a 3-node replica set:
// w:0        → 0 nodes confirmed (fire and forget)
// w:1        → 1 node (primary only)
// w:2        → 2 nodes (primary + 1 secondary) — equivalent to w:majority for 3-node
// w:majority → 2 nodes (floor(3/2)+1 = 2) — same as w:2 here
// w:3        → all 3 nodes must confirm
```

**Q8. How does `w:majority` protect against data loss during primary failover?**

A:

```
w:majority protection proof:

Setup: 3-node replica set {P1, S1, S2}
Write: order #9999 with w:majority

t=0:   Write sent to P1
t=3ms: P1 acknowledges to itself, S1 acknowledges to P1 → 2 = majority → SUCCESS returned
t=3ms: Order #9999 exists on: P1 ✓, S1 ✓, S2 (maybe, still replicating)

t=10ms: P1 crashes

Election: S1 and S2 elect a new primary. Who wins?
  - Both S1 and S2 are candidates
  - The node with the most up-to-date oplog wins the election
  - S1 has order #9999 (was in the majority)
  - S2 may or may not have order #9999

  Case A: S1 wins election
    - S1 has order #9999 → write is preserved ✓

  Case B: S2 wins election
    - S2 may not have order #9999
    - BUT: an election requires a majority of votes (2 of 3)
    - S2 can only win if S1 votes for it
    - S1 only votes for S2 if S2's oplog is at least as up-to-date as S1's
    - If S2's oplog doesn't have order #9999, S1's is more up-to-date
    - S1 will NOT vote for S2 → S2 cannot win the election
    - Therefore: if S1 has order #9999 (guaranteed by w:majority), S1 controls
      the election → either S1 wins, or only a candidate with at least S1's state wins
    → Write is preserved ✓

The invariant: w:majority guarantees that any node that can win an election
has the write, because: (1) the write was on a majority, and (2) a new election
requires a majority of votes, and (3) nodes only vote for candidates
with oplog at least as fresh as their own.

This is the mathematical guarantee behind w:majority.
```

**Q9. What is the latency cost of `w:majority` and how do you measure it?**

A:

```javascript
// Latency composition for w:majority:
// Total latency = primary write time + network RTT to nearest secondary
//               + secondary apply time + network RTT back to primary

// Typical numbers on a well-configured replica set:
// w:0:         <0.1ms  (driver doesn't wait)
// w:1:         1-5ms   (primary write + ACK)
// w:majority:  5-20ms  (primary + secondary round trip)
// w:majority, j:true:  10-50ms (adds disk flush on each node)

// Measuring actual latency with w:majority:
const { performance } = require('perf_hooks');

async function benchmarkWriteConcern(concern) {
  const iterations = 1000;
  const latencies  = [];

  for (let i = 0; i < iterations; i++) {
    const start = performance.now();
    await collection.insertOne(
      { benchmark: true, seq: i, ts: new Date() },
      { writeConcern: concern }
    );
    latencies.push(performance.now() - start);
  }

  latencies.sort((a, b) => a - b);
  return {
    p50:  latencies[Math.floor(iterations * 0.50)].toFixed(2),
    p95:  latencies[Math.floor(iterations * 0.95)].toFixed(2),
    p99:  latencies[Math.floor(iterations * 0.99)].toFixed(2),
    mean: (latencies.reduce((a, b) => a + b) / iterations).toFixed(2),
  };
}

// Typical benchmark results:
console.log(await benchmarkWriteConcern({ w: 0 }));
// { p50: '0.08', p95: '0.15', p99: '0.22', mean: '0.09' }

console.log(await benchmarkWriteConcern({ w: 1 }));
// { p50: '2.1',  p95: '4.8',  p99: '8.2',  mean: '2.3'  }

console.log(await benchmarkWriteConcern({ w: 'majority' }));
// { p50: '8.4',  p95: '18.2', p99: '34.1', mean: '9.1'  }

console.log(await benchmarkWriteConcern({ w: 'majority', j: true }));
// { p50: '14.2', p95: '28.6', p99: '56.3', mean: '15.8' }

// The p99 matters most: outliers reveal replication lag spikes
// A p99 > 100ms suggests the secondary is under load or the network is degraded
```

## Section 5: Journal Write Concern (`j:true`)

**Q10. What is the MongoDB journal and what does `j:true` add to write concern?**

A: The journal is MongoDB's write-ahead log (WAL) — a sequential on-disk log that records every write operation before it's applied to the data files. `j:true` requires a write to be flushed to this on-disk journal before the acknowledgment is sent:

```
WiredTiger write path (j:false — default behavior):

Client write
    ↓
WiredTiger in-memory cache (dirty pages)  ← ACK sent here with j:false, w:1
    ↓ (async, periodically)
WiredTiger checkpoint + journal on disk   ← safe from crash only after this

With j:false:
  If mongod process is killed (SIGKILL) before journal flush:
    Data in memory is lost (up to 100ms of writes — journal commit interval)
  If server OS crashes (power failure):
    Same: memory contents are gone, journal has last 100ms of operations

WiredTiger write path (j:true):

Client write
    ↓
WiredTiger in-memory cache (dirty pages)
    ↓ SYNCHRONOUS fsync to journal file
WiredTiger journal on disk               ← ACK sent here with j:true
    ↓ (async, periodically)
WiredTiger data files

With j:true:
  If mongod process is killed: journal has the write → crash recovery replays it
  If server OS crashes: journal on disk has the write → replayed on restart
  Only data in the journal is guaranteed — the journal IS the durability boundary
```

```javascript
// j:true vs j:false — what each protects against:

// w:1, j:false (MongoDB default before 4.0):
await collection.insertOne(doc, { writeConcern: { w: 1, j: false } });
// Protected from: network failure, MongoDB client errors
// NOT protected from: mongod process crash (data in memory, not yet journaled)
// NOT protected from: primary failover (data not replicated)

// w:1, j:true:
await collection.insertOne(doc, { writeConcern: { w: 1, j: true } });
// Protected from: network failure, MongoDB client errors, mongod process crash
// NOT protected from: primary failover (journaled on primary, not replicated)
// The write is on disk on the primary but primary failure still causes rollback

// w:majority, j:false:
await collection.insertOne(doc, { writeConcern: { w: 'majority', j: false } });
// Protected from: primary failover (write on majority of nodes)
// NOT fully protected from: simultaneous crash of majority nodes (write in their memory)
// In practice: very durable (simultaneous crashes are extremely rare)

// w:majority, j:true (MOST DURABLE standard setting):
await collection.insertOne(doc, { writeConcern: { w: 'majority', j: true } });
// Protected from: primary failover (on majority), individual node crashes (journaled)
// Only vulnerable to: simultaneous disk failure on majority of nodes
// Use for: financial transactions, medical records, any compliance-required data
```

**Q11. What is the full durability matrix and how do you choose the right combination?**

A:

```
DURABILITY MATRIX:

           │ j:false (memory)          │ j:true (disk journal)
───────────┼───────────────────────────┼─────────────────────────────────────
 w:0       │ None — no guarantees      │ Meaningless (w:0 gets no ACK anyway)
           │ Fastest writes            │
───────────┼───────────────────────────┼─────────────────────────────────────
 w:1       │ Protected from:           │ Protected from:
           │  ✓ network errors         │  ✓ network errors
           │  ✓ validation errors      │  ✓ validation errors
           │ NOT from:                 │  ✓ mongod crash (journal survives)
           │  ✗ mongod crash           │ NOT from:
           │  ✗ primary failover       │  ✗ primary failover
           │  ✗ power loss             │  ✗ power loss on primary
           │                           │    (before replication)
───────────┼───────────────────────────┼─────────────────────────────────────
 w:majority│ Protected from:           │ Protected from:
 (STANDARD)│  ✓ network errors         │  ✓ network errors
           │  ✓ primary failover       │  ✓ primary failover
           │ NOT from:                 │  ✓ individual node crashes
           │  ✗ simultaneous in-memory │ NOT from:
           │    loss on majority nodes  │  ✗ simultaneous disk failure on
           │    (extremely rare)        │    majority of nodes (extremely rare)
───────────┼───────────────────────────┼─────────────────────────────────────
 w:all     │ All nodes must ACK        │ Most durable: all nodes + journaled
           │ Performance: worst        │ Not recommended: one offline node
           │ Availability: worst       │ blocks ALL writes permanently
```

```javascript
// Decision guide based on data type:

// Metrics, analytics, logs, caches:
const metricsWriteConcern = { w: 0 };
// Fastest, acceptable loss, high volume

// Application logs, user activity feeds:
const activityWriteConcern = { w: 1 };
// Errors detected; occasional loss on failover acceptable

// User profiles, content, settings:
const contentWriteConcern = { w: 'majority' };
// Survives failover; j:false acceptable if OS crash is tolerable

// Orders, payments, account changes, medical records:
const criticalWriteConcern = { w: 'majority', j: true };
// Maximum durability for single-document writes

// Multi-document financial transactions (MongoDB 4.0+):
const session = client.startSession();
session.startTransaction({
  readConcern:  { level: 'snapshot' },
  writeConcern: { w: 'majority', j: true }
  // w:majority + j:true is REQUIRED for multi-document transactions
  // to prevent partial commits from surviving a failover
});
```

## Section 6: `wtimeout`

**Q12. What does `wtimeout` do and what is the crucial behavior when it fires?**

A: `wtimeout` specifies how long (in milliseconds) the driver will wait for the write concern acknowledgment. When the timeout fires, the driver returns an error to the application — but **the write is NOT rolled back**:

```javascript
await collection.insertOne(orderDocument, {
  writeConcern: {
    w: 'majority',
    j: true,
    wtimeout: 2000   // Wait max 2 seconds for majority ACK
  }
});
// If 2 seconds pass without majority acknowledgment:
// → MongoServerError: Write concern operation timed out
// → wtimeout fires
// → Driver throws error to application

// CRITICAL: what actually happened to the write?
// The primary MAY have already applied the write.
// The secondary may or may not have replicated it.
// The write is NOT automatically rolled back on timeout.
// The application must treat this as "write status unknown."
```

```
The wtimeout ambiguity — why it's dangerous if mishandled:

Scenario:
  1. App sends insertOne(order) with w:majority, wtimeout:2000
  2. Primary applies write immediately (t=1ms)
  3. S1 replication starts
  4. S1 is momentarily slow (GC pause, network jitter)
  5. 2000ms passes without majority ACK
  6. wtimeout fires → driver throws error to application

At this point:
  - The order EXISTS in the primary's oplog
  - The order WILL be replicated to S1 when S1 recovers (in ~50ms)
  - The order WILL survive in the database

If the application treats the timeout as "write failed" and:
  a) Retries the insert → DUPLICATE ORDER (unless idempotent insert)
  b) Shows "order failed" to user → user re-orders → DUPLICATE ORDER
  c) Charges the credit card again → DOUBLE CHARGE

The correct application behavior on wtimeout:
  1. Do NOT assume the write failed
  2. Do NOT retry without checking if the document exists
  3. Re-query to determine if the write succeeded
  4. Use idempotency keys to make retries safe

// Safe retry pattern with wtimeout:
async function durableInsert(
  collection:     Collection,
  document:       Document,
  idempotencyKey: string
): Promise<void> {
  const docWithKey = { ...document, _idempotencyKey: idempotencyKey };

  try {
    await collection.insertOne(docWithKey, {
      writeConcern: { w: 'majority', j: true, wtimeout: 5000 }
    });
  } catch (err) {
    if (err.codeName === 'WriteConcernFailed' || err.message?.includes('timed out')) {
      // Write status UNKNOWN — check if it succeeded before retrying
      const existing = await collection.findOne(
        { _idempotencyKey: idempotencyKey },
        { readConcern: { level: 'majority' } }  // read from majority to see committed data
      );
      if (existing) {
        return;  // Write succeeded despite the timeout error
      }
      // Write truly failed — safe to retry
      throw new Error('Write failed and was not found on retry check');
    }
    throw err;  // Different error — rethrow
  }
}

// wtimeout guidance:
// Set to 10× expected p99 replication latency
// If p99 replication is 20ms: set wtimeout to 200ms
// Never set to 0 (infinite wait — can block indefinitely on replication failure)
// Never set too low (causes false negatives → duplicate writes)
```

## Section 7: Read Concern Interaction

**Q13. How do read concerns interact with write concerns for end-to-end consistency?**

A: Write concerns control durability (will a write survive failure?). Read concerns control visibility (will a read see uncommitted, un-replicated, or rolled-back data?). They work together to define the consistency level of the overall system:

```javascript
// readConcern levels:
// "local"        — reads from local node (primary or secondary); may read data
//                  that will be rolled back if the node was in a stale state
// "available"    — like local but may return orphaned documents (sharded clusters)
// "majority"     — reads only data acknowledged by a majority; won't be rolled back
// "linearizable" — reads reflect all successful majority-acknowledged writes
//                  that completed before the read; strongest consistency guarantee;
//                  only valid on primary; much slower
// "snapshot"     — reads from a consistent snapshot (used in transactions)

// The combinations and what they mean:

// ── PATTERN 1: Eventual Consistency (analytics, cache) ──────────────────────
await collection.insertOne(doc, { writeConcern: { w: 1 } });
await collection.findOne(query, { readConcern: { level: 'local' } });
// Write: primary only (not replicated)
// Read: whatever is on the local node (may be stale on secondaries)
// Risk: reads may not see recent writes; reads may show data that rolls back

// ── PATTERN 2: Standard Application Consistency ──────────────────────────────
await collection.insertOne(doc, { writeConcern: { w: 'majority' } });
await collection.findOne(query, { readConcern: { level: 'majority' } });
// Write: persisted to majority
// Read: only returns majority-acknowledged data (won't show rolled-back data)
// Use for: most CRUD applications, user-facing features

// ── PATTERN 3: Causal Consistency ────────────────────────────────────────────
// Always read your own writes, even when reading from secondaries
const session = client.startSession({ causalConsistency: true });
await collection.insertOne(doc, {
  writeConcern: { w: 'majority' },
  session
});
// Later read in the SAME session — guaranteed to see the above write:
await collection.findOne(query, {
  readConcern: { level: 'majority' },
  session
});
// The session tracks causality tokens — reads from a secondary are guaranteed
// to reflect the write that happened in the same session, even across different nodes

// ── PATTERN 4: Linearizable Read (strongest, slowest) ────────────────────────
await collection.insertOne(doc, { writeConcern: { w: 'majority', j: true } });
await collection.findOne(query, { readConcern: { level: 'linearizable' } });
// Guarantees reading the most recently committed write globally
// Only valid on primary reads; much higher latency
// Use for: leader election, distributed coordination, inventory checks
```

**Q14. What read/write concern combination is required for multi-document transactions?**

A:

```javascript
// MongoDB transactions (4.0+ for replica sets, 4.2+ for sharded clusters)
// require specific concern levels to guarantee atomicity and durability:

const session = client.startSession();

try {
  session.startTransaction({
    // Write concern for the COMMIT of the transaction:
    writeConcern: { w: 'majority', j: true },
    // ↑ REQUIRED: if w:1, a primary failover can cause the commit to be rolled back
    //   even though each individual write within the transaction had no errors

    // Read concern for reads WITHIN the transaction:
    readConcern: { level: 'snapshot' },
    // ↑ All reads within the transaction see a consistent snapshot from the
    //   same point in time — prevents non-repeatable reads and phantom reads
    //   "majority" also works but "snapshot" is more consistent for transactions
  });

  // Operations within the transaction use the transaction's concern settings:
  await ordersCollection.insertOne(
    { userId: 123, total: 99.99, status: 'pending' },
    { session }
  );
  await inventoryCollection.updateOne(
    { productId: 456 },
    { $inc: { stock: -1 } },
    { session }
  );

  // Commit: must be acknowledged by w:majority before success is returned
  await session.commitTransaction();
  // If commitTransaction throws: the transaction was not committed — retry safely

} catch (err) {
  await session.abortTransaction();
  throw err;
} finally {
  await session.endSession();
}

// Why w:majority is REQUIRED for transactions:
// Individual operations within a transaction are not individually committed
// Only the COMMIT is the durability point
// If the primary fails after the commit is applied but before replication:
//   - With w:1: the commit may be rolled back → partial data loss
//   - With w:majority: the commit is on a majority → survives failover
// MongoDB will warn if you use transactions with w:1 or w:0
```

## Section 8: Configuration

**Q15. At what levels can write concerns be configured and what is the MongoDB 5.0 default?**

A: Write concerns can be set at four levels, from most general to most specific. More specific settings override less specific ones:

```javascript
// ── Level 1: Replica Set Default (server-side, lowest priority) ────────────
// rs.getLastErrorDefaults is set in replica set configuration
// Only overrides w:1 if the operation doesn't specify a write concern
// Rarely changed — use client-level instead for application control
db.adminCommand({
  replSetReconfig: {
    ...rs.conf(),
    settings: {
      getLastErrorDefaults: { w: 'majority', j: true }
    }
  }
});

// ── Level 2: Client-Level Default (application-side) ──────────────────────
const client = new MongoClient(uri, {
  writeConcern: { w: 'majority', j: true, wtimeout: 5000 }
  // All operations through this client use this unless overridden
});

// ── Level 3: Collection-Level (per-collection) ────────────────────────────
// Get a collection handle with a specific write concern:
const orders    = db.collection('orders',  { writeConcern: { w: 'majority', j: true } });
const analytics = db.collection('events',  { writeConcern: { w: 0 } });
const sessions  = db.collection('sessions',{ writeConcern: { w: 1 } });
// Different collections have different durability requirements — configure accordingly

// ── Level 4: Per-Operation Override (highest priority) ────────────────────
// Overrides client and collection defaults for this specific call:
await orders.insertOne(urgentOrder, {
  writeConcern: { w: 'majority', j: true, wtimeout: 2000 }
});
await orders.insertOne(lowPriorityOrder, {
  writeConcern: { w: 1 }   // Override for this specific operation
});
```

**What changed in MongoDB 5.0 — a breaking change many teams miss:**
```javascript
// Pre-MongoDB 5.0 default:
// Standalone:    w:1
// Replica sets:  w:1 (!! — only primary acknowledgment by default)

// MongoDB 5.0+ default:
// Standalone:    w:1 (unchanged)
// Replica sets:  w:majority (!! — changed to most durable)

// Impact of the 5.0 change:
// Applications that relied on w:1 performance now get w:majority performance
// Write latency increases (primary + replication round trip)
// Applications may see "Write concern timed out" errors that never occurred before
//   if secondaries are lagging or the wtimeout was set too low

// Check your current effective default:
db.adminCommand({ getDefaultRWConcern: 1 });
// {
//   defaultWriteConcern: { w: 'majority' },  ← 5.0+ default for replica sets
//   defaultReadConcern:  { level: 'local' },
//   ...
// }

// To set a custom default that overrides the MongoDB 5.0 default:
db.adminCommand({
  setDefaultRWConcern: 1,
  defaultWriteConcern: { w: 1 },    // Override back to w:1 if needed
  defaultReadConcern:  { level: 'local' }
});

// URI-level write concern (works for any MongoDB driver):
// mongodb://host:27017/db?w=majority&j=true&wtimeoutMS=5000
```

## Section 9: Advanced Patterns

**Q16. How do you apply different write concerns per collection type within a single application?**

A:

```typescript
// Production NestJS service with per-collection write concern strategy

import { Injectable } from '@nestjs/common';
import { InjectConnection } from '@nestjs/mongoose';
import { Connection, WriteConcern } from 'mongoose';

// Write concern constants — single definition, referenced everywhere:
export const WRITE_CONCERNS = {
  // Financial / compliance: maximum durability
  CRITICAL: new WriteConcern('majority', 5000, true),

  // User data / application state: survives failover, not necessarily journaled
  STANDARD: new WriteConcern('majority', 5000, false),

  // Operational data: primary acknowledgment is sufficient
  RELAXED:  new WriteConcern(1, 2000, false),

  // Telemetry / analytics: best effort
  FIRE_AND_FORGET: new WriteConcern(0),
} as const;

@Injectable()
export class DatabaseService {
  private readonly orders:    Collection;
  private readonly payments:  Collection;
  private readonly events:    Collection;
  private readonly sessions:  Collection;

  constructor(@InjectConnection() private connection: Connection) {
    const db = this.connection.db;

    // Each collection gets the appropriate write concern:
    this.orders   = db.collection('orders',   { writeConcern: WRITE_CONCERNS.CRITICAL });
    this.payments = db.collection('payments', { writeConcern: WRITE_CONCERNS.CRITICAL });
    this.events   = db.collection('events',   { writeConcern: WRITE_CONCERNS.FIRE_AND_FORGET });
    this.sessions = db.collection('sessions', { writeConcern: WRITE_CONCERNS.RELAXED });
  }

  // Critical path: order placement (w:majority, j:true)
  async createOrder(order: CreateOrderDto): Promise<string> {
    const result = await this.orders.insertOne({
      ...order,
      status:    'pending',
      createdAt: new Date(),
    });
    // Uses CRITICAL write concern from collection config
    // Returns only after majority of nodes have the data on disk
    return result.insertedId.toString();
  }

  // High-volume path: event tracking (w:0)
  async trackEvent(event: AnalyticsEvent): Promise<void> {
    await this.events.insertOne(event);
    // Fire and forget — high volume, loss acceptable
  }

  // Selective override for specific operations within a collection:
  async bulkImportHistoricalOrders(orders: Order[]): Promise<void> {
    // Historical import: acceptable to use relaxed concern (data is already durable elsewhere)
    await this.orders.insertMany(orders, {
      writeConcern: WRITE_CONCERNS.RELAXED,  // Override CRITICAL for this bulk operation
      ordered: false,
    });
  }
}
```

**Q17. What are tag-set write concerns and when do you use them for multi-datacenter deployments?**

A:

```javascript
// Tag sets allow write concerns based on node topology (datacenter, rack, region)
// rather than just node count — essential for geographic durability guarantees

// Step 1: Configure replica set with tags
rs.reconfig({
  members: [
    { _id: 0, host: 'mongo-us-east-1:27017', tags: { dc: 'us-east', rack: 'rack1' } },
    { _id: 1, host: 'mongo-us-east-2:27017', tags: { dc: 'us-east', rack: 'rack2' } },
    { _id: 2, host: 'mongo-us-west-1:27017', tags: { dc: 'us-west', rack: 'rack1' } },
    { _id: 3, host: 'mongo-eu-west-1:27017', tags: { dc: 'eu-west', rack: 'rack1' } },
    { _id: 4, host: 'mongo-eu-west-2:27017', tags: { dc: 'eu-west', rack: 'rack2' } },
  ],
  settings: {
    getLastErrorModes: {
      // "multiDC": write must be on at least 2 different data centers
      'multiDC': { dc: 2 },

      // "allDC": write must be on all 3 data centers
      'allDC': { dc: 3 },

      // "twoRack": write must be on at least 2 different racks (within same DC is OK)
      'twoRack': { rack: 2 },

      // "durableUSWest": write must be on at least 1 US West node
      // Useful for compliance: data must exist in specific geographic region
      'durableUSWest': { 'dc': 1 }  // Only target us-west tagged nodes
    }
  }
});

// Step 2: Use tag-based write concern:
await collection.insertOne(customerDocument, {
  writeConcern: {
    w: 'multiDC',   // Custom tag set name
    j: true,
    wtimeout: 10000 // Longer timeout: cross-DC replication is slower
  }
});
// Write succeeds only after it's on at least 2 different data centers
// Survives loss of an entire datacenter

// When to use tag-set write concerns:
// ✓ GDPR compliance: "data must be on EU servers before confirming"
// ✓ Disaster recovery: "must survive loss of us-east entirely"
// ✓ Audit requirements: "financial data must be in two geographic regions"
// ✓ SLA differentiation: "premium customers get multiDC durability, free tier gets w:1"
```

// Fintech application: three categories of data with very different requirements

// ── CATEGORY 1: Financial Transactions — maximum durability ──────────────────
// Requirements: ZERO data loss, GDPR compliance, audit trail, idempotency
// Concern: w:majority, j:true

@Injectable()
export class PaymentService {
  private readonly payments: Collection;

      createdAt: new Date(),

## Quick Reference Table

| Concept | Detail |
|---|---|
| **Write concern** | How many replica set nodes must acknowledge a write before "success" is returned to the application |
| **`w:0`** | Unacknowledged — driver doesn't wait; fastest; no network or validation errors detected; use only for high-volume metrics/analytics |
| **`w:1`** | Primary acknowledged — write applied to primary's memory + oplog; errors detected; unsafe if primary fails before replication |
| **`w:majority`** | Majority of voting nodes must acknowledge — write survives primary failover; slower than w:1 by replication round-trip |
| **`w:N`** | Exactly N nodes must acknowledge — less common; w:2 on a 3-node set = w:majority |
| **`j:true`** | Journal flush required — write persisted to on-disk WAL before ACK; protects against mongod process crash |
| **`j:false`** | Journal flush not required — write in memory; faster; lost on process crash within journal commit interval (~100ms) |
| **`wtimeout`** | Max milliseconds to wait for write concern ACK; on timeout: error returned BUT write is NOT rolled back — status is unknown |
| **wtimeout ambiguity** | Never assume write failed on timeout — re-query to check; use idempotency keys to make safe retries |
| **Majority calculation** | `floor(N/2) + 1` voting members; 3-node: 2; 5-node: 3; 7-node: 4 |
| **Rollback file** | When old primary rejoins, unreplicated writes → `/var/lib/mongodb/rollback/*.bson`; not automatically recovered |
| **MongoDB 5.0 change** | Default write concern for replica sets changed from `w:1` to `w:majority` — significant latency change for existing apps |
| **Oplog** | Capped collection in `local` db; records every write; secondaries tail it; replication lag = how far behind secondaries are |
| **readConcern: "local"** | Returns local node's data; may include data that will be rolled back |
| **readConcern: "majority"** | Returns only data acknowledged by majority; safe from rollback; required for causal consistency |
| **readConcern: "snapshot"** | Consistent point-in-time snapshot; required for multi-document transactions |
| **Causal consistency** | `client.startSession({ causalConsistency: true })` — always read your own writes, even on secondaries; requires `w:majority` + `readConcern:majority` |
| **Transactions** | Require `w:majority, j:true` on commitTransaction — otherwise a primary failover can roll back a committed transaction |
| **Tag-set write concerns** | Write must reach nodes with specific tags (e.g., two different data centers); defined in replica set settings |
| **Per-operation override** | `collection.insertOne(doc, { writeConcern: {...} })` — overrides collection and client defaults |
| **Replication lag** | Check via `db.adminCommand({replSetGetStatus:1})`; high lag = w:majority writes become slow |
| **Recommended: financial data** | `{ w: 'majority', j: true, wtimeout: 10000 }` |
| **Recommended: user data** | `{ w: 'majority', j: false, wtimeout: 5000 }` |
| **Recommended: analytics** | `{ w: 0 }` |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining the **rollback scenario precisely** — why `w:1` writes can disappear after a primary failover, tracing through the sequence (write acknowledged by primary, replication not yet complete, primary crashes, secondaries elect new primary, unreplicated writes are rolled back to rollback files) and why `w:majority` prevents this (any node that can win an election already has the write, because winning requires votes from a majority and nodes only vote for candidates as up-to-date as themselves); (2) the **`wtimeout` ambiguity trap** — a `WriteConcernFailed` timeout error does NOT mean the write didn't happen; the primary may have applied it before the timeout; correctly handling this requires re-querying with `readConcern: majority` to determine the actual state, and using idempotency keys to make retries safe; (3) the **`j:false` vs `j:true` distinction within `w:majority`** — `w:majority, j:false` means the write is in memory on a majority of nodes (survives primary failover but not simultaneous process crashes), while `w:majority, j:true` means the write is flushed to disk on a majority (survives both failover and process crashes); for financial data `j:true` is non-negotiable; (4) the **MongoDB 5.0 default change** from `w:1` to `w:majority` and its operational impact — applications that weren't specifying write concerns explicitly suddenly got higher latency writes after upgrading, and applications with low `wtimeout` values started seeing timeout errors if replication lagged; knowing this change and how to verify current defaults (`db.adminCommand({ getDefaultRWConcern: 1 })`) demonstrates production awareness; and (5) the **transaction write concern requirement** — multi-document transactions must use `w:majority` on `commitTransaction` because the individual operation writes within a transaction are not independently committed; a primary failure after commit but before majority acknowledgment rolls back the entire transaction, so `w:majority` is the only safe option for transactional operations.
