# MongoDB Schema Design: Embedding vs Referencing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the core decision in MongoDB schema design and why does it not exist in relational databases?**
A: In a relational database, schema design has one answer for representing relationships: separate tables joined at query time. MongoDB gives you a genuine choice — embed related data inside one document, or store it in separate collections and reference across them. This choice has no correct universal answer; it depends on access patterns, data size, update frequency, and consistency requirements:

```
Relational databases: one model, one tradeoff
  Users table + Loans table → always separate → always JOIN
  Normalization is the rule: minimize redundancy, maximize consistency
  Query time: JOINs are cheap (hash join, nested loop join, index nested loop)
  Write time: update once in one place → consistent everywhere

MongoDB: two models, different tradeoffs per relationship
  Option A: Embed loan data inside the user document
    { _id: ObjectId, name: "Alice", loans: [{ amount: 50000, status: "active" }] }
  Option B: Reference loan documents from the user
    { _id: ObjectId, name: "Alice" }                    ← users collection
    { _id: ObjectId, user_id: ObjectId, amount: 50000 } ← loans collection

  No JOINs: MongoDB has $lookup (aggregation) but it is more expensive than
             a relational JOIN because it cannot use index-merge algorithms
             and runs as a nested loop lookup per document
  The "join" cost is real → push data together that is read together

The fundamental question:
  "Is this data read together or separately?"
  Read together always → embed (avoid the join cost at read time)
  Read separately, updated independently → reference (avoid the update cost at write time)

Why the choice matters operationally:
  Wrong choice → either:
  A) Unbounded document growth (embed when you should reference)
     → documents exceed 16MB BSON limit → errors
     → working set bloat → memory pressure
     → slow reads (loading 10MB doc to read one field)
  B) Too many round trips (reference when you should embed)
     → N+1 query problem (load 100 users → 100 more queries for their loans)
     → latency multiplied by relationship depth
```

**Q2. What are the three relationship types in MongoDB and what is the starting heuristic for each?**
A: MongoDB schema design distinguishes one-to-one, one-to-many, and many-to-many relationships. Each has a default heuristic — a starting point that applies in the absence of other constraints. The heuristics are starting points, not rules:

```javascript
// ── One-to-One ────────────────────────────────────────────────────────────────
// Heuristic: EMBED (almost always)
// Rationale: if a user always has exactly one address, and you always read
//            the address when you read the user, there is no reason to separate them

// ✓ Embedded one-to-one:
{
    _id: ObjectId("..."),
    name: "Ravi Sharma",
    email: "ravi@example.com",
    kyc_details: {                   // one-to-one: embed
        pan_number: "ABCDE1234F",    // (or store encrypted via CSFLE)
        aadhaar_last4: "5678",
        verified_at: new Date("2024-01-10"),
        verified_by: "KYC_PROVIDER_X"
    },
    address: {                       // one-to-one: embed
        street: "123 MG Road",
        city: "Bengaluru",
        state: "Karnataka",
        pincode: "560001"
    }
}
// Reads: one document fetch → all data present
// Updates: single $set operation on nested fields

// Exception → reference even for one-to-one when:
//   The embedded data is large AND rarely needed (lazy load)
//   The embedded data must be independently accessible (separate API endpoint)
//   The embedded data has different access control (PII in separate collection)

// ── One-to-Many ───────────────────────────────────────────────────────────────
// Heuristic: depends on the "many" side cardinality and growth
//   Few (2-20): EMBED as array
//   Many (20-thousands): REFERENCE from child to parent (child stores parent_id)
//   Massive/unbounded: REFERENCE (never embed unbounded arrays)

// Few → embed:
{
    _id: ObjectId("..."),
    loan_id: "LAN-2024-001",
    status_history: [            // few entries (10-20 max) → embed
        { status: "draft",     changed_at: new Date("2024-01-01") },
        { status: "submitted", changed_at: new Date("2024-01-02") },
        { status: "approved",  changed_at: new Date("2024-01-05") }
    ]
}

// Many → reference (child stores parent FK):
// loans collection: { _id: ObjectId("L1"), borrower_id: ObjectId("B1"), ... }
// repayments collection: { _id: ObjectId("R1"), loan_id: ObjectId("L1"), amount: 5000, ... }
// Query repayments for a loan: db.repayments.find({ loan_id: ObjectId("L1") })

// ── Many-to-Many ──────────────────────────────────────────────────────────────
// Heuristic: depends on which direction is read more frequently
//   Store array of references on the side that is queried (accessed by its _id)
//   Or: store references on both sides if both directions are frequent

// Example: loan officers can handle many loans; loans can have multiple officers
// Option A: embed officer IDs in loan (query "loans for officer" requires index on array):
{ loan_id: "L1", officer_ids: [ObjectId("O1"), ObjectId("O2")] }

// Option B: embed loan IDs in officer (query "officers for loan" requires index on array):
{ officer_id: "O1", loan_ids: [ObjectId("L1"), ObjectId("L2")] }

// Option C: both (denormalized, keeps both directions fast but needs dual-write):
// loans:   { loan_id: "L1", officer_ids: [ObjectId("O1")] }
// officers: { officer_id: "O1", loan_ids: [ObjectId("L1")] }
```

## Section 2: Embedding

**Q3. What are the concrete benefits of embedding and what patterns make embedding the right choice?**
A: Embedding co-locates related data in a single BSON document, meaning a single read returns all related data with no additional queries. The benefits are atomic writes, single-document reads, and simpler application code. The patterns where embedding is clearly correct:

```javascript
// Benefit 1: Atomic writes across related data
// MongoDB guarantees atomicity at the document level (and transaction level for multi-doc)
// Embedded: update loan + status in one atomic operation:
db.loans.updateOne(
    { _id: ObjectId("L1") },
    {
        $set:  { status: "approved" },
        $push: { status_history: { status: "approved", changed_at: new Date() } }
    }
);
// status and status_history are updated atomically — no partial state possible
// Referenced: updating loan status + inserting to status_history collection
//             requires a multi-document transaction (extra overhead, more complex)

// Benefit 2: Single document fetch (no $lookup, no extra round trips)
// Get a loan with all its embedded data:
const loan = await db.loans.findOne({ _id: ObjectId("L1") });
// loan.status_history, loan.documents, loan.addresses all present
// One network round trip, one BSON parse

// Benefit 3: Index on embedded field works normally:
db.loans.createIndex({ "address.pincode": 1 });
db.loans.find({ "address.pincode": "560001" });
// Index is on the outer document — works exactly like any other index

// Patterns that favor embedding:

// Pattern 1: Data with limited cardinality that always changes together
{
    _id: ObjectId("..."),
    loan_id: "LAN-2024-001",
    // EMI schedule: fixed count (tenure_months), always read with the loan:
    emi_schedule: [
        { installment: 1, due_date: new Date("2024-02-01"), amount: Decimal128.fromString("12453.67") },
        { installment: 2, due_date: new Date("2024-03-01"), amount: Decimal128.fromString("12453.67") },
        // ... up to 60 entries for 5-year loan
    ]
    // Access pattern: always load all EMIs when viewing loan details
    // Update pattern: bulk update when foreclosing early → single document update
}

// Pattern 2: Configuration / metadata that belongs exclusively to one parent
{
    _id: ObjectId("..."),
    product_id: "PERSONAL_LOAN_V2",
    name: "Personal Loan",
    // Configuration is owned by product, never shared → embed:
    eligibility_rules: {
        min_age: 21,
        max_age: 65,
        min_income: 25000,
        min_credit_score: 650,
        allowed_employment_types: ["salaried", "self_employed"]
    },
    interest_tiers: [
        { min_score: 750, rate: Decimal128.fromString("10.5") },
        { min_score: 700, rate: Decimal128.fromString("12.0") },
        { min_score: 650, rate: Decimal128.fromString("14.5") }
    ]
}

// Pattern 3: Value objects — data with no independent identity
// A phone number has no meaning outside the context of a user → embed:
{
    _id: ObjectId("..."),
    name: "Priya Mehta",
    phone_numbers: [
        { type: "mobile",  number: "+91-9876543210", verified: true },
        { type: "work",    number: "+91-8012345678", verified: false }
    ]
    // phone_numbers have no _id, no independent queries, no lifecycle outside the user
}

// Pattern 4: Snapshot / denormalized data (preserve historical state)
// When a loan is disbursed, embed a snapshot of the borrower's details at disbursement time
// Even if borrower changes their name later, the disbursement record is accurate:
{
    _id: ObjectId("..."),
    loan_id: "LAN-2024-001",
    disbursement: {
        disbursed_at: new Date("2024-01-15"),
        amount: Decimal128.fromString("500000.00"),
        // Snapshot — NOT a reference — because this state must be preserved:
        borrower_snapshot: {
            name:           "Ravi Sharma",
            pan_number:     "ABCDE1234F",
            address:        "123 MG Road, Bengaluru",
            credit_score:   742,
            monthly_income: 85000
        }
    }
}
```

**Q4. What are the risks of embedding and what are the hard limits that force you to reference?**
A: The most dangerous embedding mistake is embedding an unbounded array — a sub-document array that grows without a cap. This creates documents that grow over time, hit the 16MB BSON limit, cause page splits in the storage engine, and degrade performance as the working set bloats:

```javascript
// ── Hard Limit: 16MB BSON document size ──────────────────────────────────────
// MongoDB enforces a 16MB maximum per document
// An unbounded embedded array will eventually hit this limit

// WRONG — embedding repayments in the loan document:
{
    _id: ObjectId("L1"),
    loan_id: "LAN-2024-001",
    tenure_months: 120,    // 10-year loan → 120 repayments
    repayments: [          // grows to 120 entries → document bloat
        { installment: 1, paid_at: new Date(), amount: Decimal128.fromString("8500") },
        { installment: 2, paid_at: new Date(), amount: Decimal128.fromString("8500") },
        // ... 118 more entries
        // Each entry ~200 bytes → 120 × 200 bytes = 24KB for repayments alone
        // For a platform with 100,000 loans × 24KB = 2.4GB just for repayment arrays
        // Long-tenure loans + rich repayment data → approaching 16MB
    ]
}

// What happens when you approach 16MB:
// → MongoDB throws: BSONObj size: XXXXXX is invalid. Size must be between 0 and 16793600
// → Writes fail → data loss or application errors
// → Cannot fix without splitting the document (requires migration)

// ── Risk: Document growth causes page migrations in WiredTiger ───────────────
// WiredTiger stores documents in 32KB pages
// When a document grows beyond a page (due to $push to array):
//   → Page split: document moved to a new location
//   → Old location becomes a pointer (forwarding address)
//   → Sequential scans now follow forwarding pointers → random I/O
//   → Performance degrades over time as documents grow

// ── Risk: Reading large documents to access small sub-documents ───────────────
// If you embed 1000 status_history entries but only ever display the last 5:
// MongoDB loads the ENTIRE document from disk to serve the query
// Network transfer: full 2MB document → client picks last 5 entries
// Projection helps ($project only returns requested fields) but the server
// still reads the full document from disk into memory first

// WRONG — embed audit trail that grows forever:
{
    _id: ObjectId("..."),
    loan_id: "LAN-2024-001",
    audit_trail: [    // every field change logged here
        { field: "status", old: null, new: "draft",     at: new Date(), by: "system" },
        { field: "status", old: "draft", new: "submitted", at: new Date(), by: "B1" },
        // ... potentially thousands of entries over 10 years
    ]
}

// CORRECT — audit trail as a separate collection (reference by loan_id):
// audit_events collection:
{ _id: ObjectId(), loan_id: ObjectId("L1"), field: "status", old: "draft", new: "submitted", at: new Date() }
// Query: db.audit_events.find({ loan_id: ObjectId("L1") }).sort({ at: -1 }).limit(20)

// ── Risk: Update amplification ────────────────────────────────────────────────
// If borrower data is embedded in EVERY loan document:
{
    _id: ObjectId("L1"),
    borrower: { name: "Ravi Sharma", email: "ravi@old.com", phone: "9999999999" }
}
{
    _id: ObjectId("L2"),
    borrower: { name: "Ravi Sharma", email: "ravi@old.com", phone: "9999999999" }
}
// If Ravi changes his email:
db.loans.updateMany(
    { "borrower.email": "ravi@old.com" },
    { $set: { "borrower.email": "ravi@new.com" } }
);
// Updates EVERY loan document for this borrower → write amplification
// If borrower has 50 loans → 50 write operations instead of 1

// CORRECT for mutable shared data: reference the borrower by ObjectId:
{ _id: ObjectId("L1"), borrower_id: ObjectId("B1"), ... }
{ _id: ObjectId("L2"), borrower_id: ObjectId("B1"), ... }
// Update Ravi's email: one update to borrowers collection → done
```

## Section 3: Referencing

**Q5. What are the two directions of referencing and when does each apply?**
A: A reference is an ObjectId stored in one document pointing to a document in another collection. The reference can be stored on either side of the relationship — the parent (holds child IDs) or the child (holds parent ID). Which side stores the reference determines query patterns and index requirements:

```javascript
// ── Direction 1: Parent stores array of child IDs ─────────────────────────────
// Use when: you frequently query the parent and need to know its children
//           AND the number of children is bounded (not unbounded)

// loans collection (parent):
{
    _id: ObjectId("L1"),
    loan_id: "LAN-2024-001",
    document_ids: [          // bounded array of ObjectIds (max 20 docs)
        ObjectId("D1"),
        ObjectId("D2"),
        ObjectId("D3")
    ]
}
// documents collection (children — independently accessible):
{ _id: ObjectId("D1"), loan_id: ObjectId("L1"), type: "pan_card",  url: "s3://..." }
{ _id: ObjectId("D2"), loan_id: ObjectId("L1"), type: "aadhaar",   url: "s3://..." }

// Querying children given the parent:
const loan = await db.loans.findOne({ _id: ObjectId("L1") });
const docs = await db.documents.find({ _id: { $in: loan.document_ids } }).toArray();
// Two round trips but bounded (no matter how many total documents exist)

// OR with $lookup (single aggregation pipeline):
db.loans.aggregate([
    { $match: { _id: ObjectId("L1") } },
    { $lookup: {
        from: "documents",
        localField: "document_ids",
        foreignField: "_id",
        as: "documents"
    }}
]);

// ── Direction 2: Child stores parent ID ───────────────────────────────────────
// Use when: children can be numerous (unbounded), each child independently queryable
//           AND you frequently query "all children for a parent"

// loans collection (parent — no reference to children):
{ _id: ObjectId("L1"), loan_id: "LAN-2024-001", amount: Decimal128.fromString("500000") }

// repayments collection (children — each stores parent reference):
{ _id: ObjectId("R1"), loan_id: ObjectId("L1"), installment: 1, amount: Decimal128.fromString("8500"), paid_at: new Date() }
{ _id: ObjectId("R2"), loan_id: ObjectId("L1"), installment: 2, amount: Decimal128.fromString("8500"), paid_at: new Date() }
// ... up to 120 repayments, each a separate document

// Index required for efficient child-by-parent query:
db.repayments.createIndex({ loan_id: 1, installment: 1 });
// Query all repayments for a loan:
db.repayments.find({ loan_id: ObjectId("L1") }).sort({ installment: 1 });
// Uses the index → fast regardless of total collection size

// ── Direction 3: Both sides store references (two-way referencing) ─────────────
// Use for many-to-many where BOTH query directions are frequent
// Tradeoff: must maintain consistency across both sides (dual-write)

// Loan officers assigned to loans:
// loan_officers collection:
{
    _id: ObjectId("O1"),
    name: "Sunita Patel",
    loan_ids: [ObjectId("L1"), ObjectId("L2"), ObjectId("L5")]  // her portfolio
}
// loans collection:
{
    _id: ObjectId("L1"),
    officer_ids: [ObjectId("O1"), ObjectId("O2")]  // co-assigned officers
}

// Query "all loans for officer O1": db.loans.find({ _id: { $in: officer.loan_ids } })
// Query "all officers for loan L1": db.loan_officers.find({ _id: { $in: loan.officer_ids } })
// Both directions fast — but assignment requires writing to BOTH documents atomically:
const session = client.startSession();
session.withTransaction(async () => {
    await db.loans.updateOne(
        { _id: loanId },
        { $addToSet: { officer_ids: officerId } },
        { session }
    );
    await db.loan_officers.updateOne(
        { _id: officerId },
        { $addToSet: { loan_ids: loanId } },
        { session }
    );
});
// Multi-document transaction required for consistency
```

**Q6. What is the $lookup aggregation stage and what are its performance characteristics compared to a relational JOIN?**
A: `$lookup` performs a left outer join between collections. It runs as a nested loop — for each document in the left collection, MongoDB searches the right collection for matching documents. This is structurally similar to a nested loop join in relational databases, but without the planner's ability to choose hash joins or merge joins, making it more predictable but also more consistently O(n×m) without indexes:

```javascript
// Basic $lookup syntax:
db.loans.aggregate([
    { $match: { status: "active" } },
    { $lookup: {
        from: "borrowers",          // right collection
        localField: "borrower_id", // field in left (loans)
        foreignField: "_id",        // field in right (borrowers)
        as: "borrower"             // output array field name
    }},
    // $lookup always returns an ARRAY — even for one-to-one:
    // borrower: [{ _id: ObjectId, name: "Ravi", ... }]
    { $unwind: "$borrower" }  // convert array to object for one-to-one
]);

// Pipeline $lookup (MongoDB 3.6+) — join with filtering/transformation:
db.loans.aggregate([
    { $lookup: {
        from: "repayments",
        let: { loan_id: "$_id" },           // pass loan's _id to pipeline
        pipeline: [
            { $match: {
                $expr: { $eq: ["$loan_id", "$$loan_id"] }  // reference let variable
            }},
            { $match: { status: "paid" } },
            { $sort:  { paid_at: -1 } },
            { $limit: 5 }                    // only last 5 repayments
        ],
        as: "recent_repayments"
    }}
]);

// $lookup performance characteristics:

// ✓ Indexed $lookup (correct usage):
// REQUIRED: an index on the foreignField in the right collection
db.borrowers.createIndex({ _id: 1 });  // primary key index (always exists)
db.repayments.createIndex({ loan_id: 1 });  // for loan_id lookups

// With index: each outer document → index seek in right collection → O(log n)
// Without index: each outer document → full scan of right collection → O(n)
// For 1000 loans with 100,000 repayments and no index: 1000 × 100,000 = 100M comparisons

// ✗ Common $lookup anti-pattern — no index on foreignField:
db.loans.aggregate([
    { $lookup: {
        from: "documents",
        localField: "_id",
        foreignField: "loan_id",  // must be indexed! if not: full scan per loan
        as: "documents"
    }}
]);
// If documents has no index on loan_id: O(loans × documents) → devastating

// $lookup vs application-level join:

// Option A: $lookup in aggregation pipeline (server-side join):
const result = await db.loans.aggregate([
    { $match: { status: "active" } },
    { $lookup: { from: "borrowers", localField: "borrower_id", foreignField: "_id", as: "borrower" } }
]).toArray();
// Pros: one round trip to server; server handles all data transfer; indexable
// Cons: memory pressure on server if result set is large; less flexible than app code
//       cannot use connection pool routing (always hits the same mongod/mongos)

// Option B: Application-level join (two queries):
const loans = await db.loans.find({ status: "active" }).toArray();
const borrowerIds = [...new Set(loans.map(l => l.borrower_id.toString()))];
const borrowers = await db.borrowers.find({
    _id: { $in: borrowerIds.map(id => new ObjectId(id)) }
}).toArray();
const borrowerMap = new Map(borrowers.map(b => [b._id.toString(), b]));
const enriched = loans.map(l => ({ ...l, borrower: borrowerMap.get(l.borrower_id.toString()) }));
// Pros: two indexed queries; data fetched in parallel possible;
//       can route reads to replica for borrowers, primary for loans
//       flexible transformation in application code
// Cons: two round trips; more application code; client handles memory

// When to use $lookup vs application-level join:
// $lookup:    simple joins, aggregation pipelines with grouping/facets,
//             admin queries, reporting
// App-level:  high-throughput paths, parallel fetches needed,
//             complex transformation logic, read replica routing
```

## Section 4: The Bucket Pattern and Other Hybrid Approaches

**Q7. What is the Bucket Pattern and when does it solve the embedding vs referencing dilemma?**
A: The Bucket Pattern groups time-series or sequential data into "bucket" documents — each bucket holds a fixed number of events (e.g. 200 sensor readings or 100 transactions). It avoids both the unbounded array problem (too many embedded events → 16MB limit) and the excessive document proliferation problem (one document per event → millions of tiny documents):

```javascript
// Problem: time-series loan events
// Option A (embed all): loan document with thousands of events → 16MB limit
// Option B (reference each): millions of tiny event documents → index overhead, many fetches
// Option C (bucket): groups of N events per document → balanced

// Without bucket pattern (one document per event):
{ _id: ObjectId(), loan_id: ObjectId("L1"), type: "payment_attempt", at: new Date(), amount: 8500 }
{ _id: ObjectId(), loan_id: ObjectId("L1"), type: "payment_success",  at: new Date(), amount: 8500 }
// 10 years × monthly payments = 120 documents per loan
// 100,000 loans → 12,000,000 event documents → large collection, many index entries

// With bucket pattern (N events per bucket document):
{
    _id: ObjectId(),
    loan_id: ObjectId("L1"),
    bucket_start: new Date("2024-01-01"),
    bucket_end:   new Date("2024-03-31"),   // quarterly bucket
    event_count:  6,                         // current number of events in this bucket
    events: [
        { type: "emi_due",       at: new Date("2024-01-01"), amount: Decimal128.fromString("8500") },
        { type: "payment_made",  at: new Date("2024-01-03"), amount: Decimal128.fromString("8500") },
        { type: "emi_due",       at: new Date("2024-02-01"), amount: Decimal128.fromString("8500") },
        { type: "payment_made",  at: new Date("2024-02-04"), amount: Decimal128.fromString("8500") },
        { type: "emi_due",       at: new Date("2024-03-01"), amount: Decimal128.fromString("8500") },
        { type: "payment_made",  at: new Date("2024-03-02"), amount: Decimal128.fromString("8500") }
    ],
    // Pre-aggregated stats (computed on write, avoid re-computation on read):
    stats: {
        total_paid:   Decimal128.fromString("17000"),
        missed_count: 0,
        late_count:   0
    }
}

// Adding a new event to the current bucket:
const BUCKET_SIZE = 200;

async function addLoanEvent(loanId, event) {
    // Try to push to an existing bucket that has space:
    const result = await db.loan_event_buckets.updateOne(
        {
            loan_id: loanId,
            event_count: { $lt: BUCKET_SIZE }   // bucket has room
        },
        {
            $push: { events: event },
            $inc:  { event_count: 1 },
            $set:  { bucket_end: event.at },
            $min:  { bucket_start: event.at }   // in case first event in bucket
        }
    );

    if (result.matchedCount === 0) {
        // No bucket with space → create a new bucket:
        await db.loan_event_buckets.insertOne({
            loan_id:      loanId,
            bucket_start: event.at,
            bucket_end:   event.at,
            event_count:  1,
            events:       [event],
            stats:        { total_paid: Decimal128.fromString("0"), missed_count: 0 }
        });
    }
}

// Querying events in a date range:
db.loan_event_buckets.find({
    loan_id: ObjectId("L1"),
    bucket_end:   { $gte: new Date("2024-01-01") },
    bucket_start: { $lte: new Date("2024-03-31") }
});
// Returns the 1-2 buckets that overlap the date range
// Much fewer documents than one-per-event; much smaller than one-per-loan

// Benefits of bucket pattern:
// → Dramatically fewer documents (100K loans × 12M events → 100K loans × 60K buckets)
// → Pre-aggregated stats avoid re-summing on every read
// → Still supports range queries via bucket_start/bucket_end index
// → Documents never exceed 16MB (BUCKET_SIZE keeps arrays bounded)
// → Write pattern is append-mostly (new events added to current bucket)
```

**Q8. What is the Extended Reference Pattern and when does it solve the N+1 query problem?**
A: The Extended Reference Pattern stores a copy of the most frequently accessed fields from a referenced document alongside the reference ObjectId. It is a controlled, intentional form of denormalization — you choose which fields to duplicate to eliminate the most common $lookup or second query:

```javascript
// Problem: loan list page shows 50 loans with borrower name for each
// Full reference model: 50 loan reads → 50 borrower reads → N+1 problem
// $lookup: one aggregation but full borrower document loaded for each

// Extended reference pattern: embed ONLY the frequently displayed fields:
{
    _id: ObjectId("L1"),
    loan_id: "LAN-2024-001",
    amount: Decimal128.fromString("500000"),
    status: "active",
    // Full reference (for when full borrower is needed):
    borrower_id: ObjectId("B1"),
    // Extended reference (subset of borrower fields for list display):
    borrower_name:  "Ravi Sharma",    // duplicated from borrowers.name
    borrower_email: "ravi@ex.com",    // duplicated from borrowers.email
    // These two fields are enough for the loan list page
    // Full borrower details only needed on loan detail page → separate query
}

// Loan list query — zero extra queries needed:
const loanList = await db.loans.find({ status: "active" })
    .project({ loan_id: 1, amount: 1, status: 1, borrower_name: 1, borrower_email: 1 })
    .sort({ created_at: -1 })
    .limit(50)
    .toArray();
// borrower_name and borrower_email come from the loan document directly
// No join, no $lookup, no N+1

// Loan detail query — fetch the full borrower when needed:
const [loan, borrower] = await Promise.all([
    db.loans.findOne({ _id: ObjectId("L1") }),
    db.borrowers.findOne({ _id: loan.borrower_id })
]);
// Two parallel queries — efficient, and only runs when detail is actually needed

// The update problem for extended references:
// When borrower changes their name → must update all loan documents too
// This is the fundamental tradeoff: read speed vs write complexity

async function updateBorrowerName(borrowerId, newName) {
    // Update the source of truth:
    await db.borrowers.updateOne(
        { _id: borrowerId },
        { $set: { name: newName } }
    );

    // Update all extended references in loans:
    await db.loans.updateMany(
        { borrower_id: borrowerId },
        { $set: { borrower_name: newName } }
    );
    // If borrower has 50 active loans: 50 write operations
    // Acceptable if: name changes are infrequent (they are)
    // Not acceptable if: the field changes constantly
}

// Rule: only extend references with fields that are:
// 1. Read frequently (displayed on every list row or card)
// 2. Updated rarely (name, not last_login timestamp)
// 3. Not the source of critical business logic (not credit score — use reference)

// Choosing which fields to extend:
// ✓ Extend: borrower_name, borrower_phone (display only, rarely changes)
// ✗ Extend: credit_score (changes monthly, drives decisions → always fetch fresh)
// ✗ Extend: account_balance (changes per transaction → stale immediately)
// ✓ Extend: product_name, product_type (loan product rarely changes name)
// ✗ Extend: interest_rate (may be updated → all loans would need re-computation)
```

## Section 5: The Outlier Pattern and Schema Versioning

**Q9. What is the Outlier Pattern and how does it handle the minority of documents that don't fit the common case?**
A: The Outlier Pattern handles the "90/10" situation — where 90% of documents fit a simple embedding model but 10% would exceed limits or degrade performance. Instead of designing the schema for the worst case, design for the common case and add an overflow mechanism for outliers:

```javascript
// Problem: loan officers have on average 50 active loans (fits in array)
// But 5% of officers (senior/regional) manage 500-2000 loans (too many to embed)

// Naive approach: embed loan_ids array
// Problem: 2000 UUIDs × 12 bytes = 24KB just for the array
//          Plus document growth as more loans are assigned
//          Large officers slow down queries that load their document

// Outlier pattern: design for the common case + overflow flag for outliers

// loan_officers collection:
{
    _id: ObjectId("O1"),
    name: "Sunita Patel",
    region: "south",
    // For normal officers: loan_ids embedded (≤ 200 loans fits comfortably):
    loan_ids: [ObjectId("L1"), ObjectId("L2"), /* ... up to 200 */ ],
    loan_count: 47,
    // No overflow flag → this officer is in the normal case
}

{
    _id: ObjectId("O2"),
    name: "Vikram Singh (Regional Head)",
    region: "north",
    loan_ids: [ObjectId("L100"), ObjectId("L101"), /* ... 200 entries */ ],
    loan_count: 1847,
    has_overflow: true   // ← flag: this officer has more loans than fit in the array
}

// Overflow collection (only for outliers):
// officer_loans_overflow collection:
{ _id: ObjectId(), officer_id: ObjectId("O2"), loan_ids: [ObjectId("L301"), ObjectId("L302"), /* ... */] }
{ _id: ObjectId(), officer_id: ObjectId("O2"), loan_ids: [ObjectId("L501"), /* ... */] }
// Paginated overflow documents — each holds the next N loan_ids

// Application logic handling outlier:
async function getOfficerLoans(officerId) {
    const officer = await db.loan_officers.findOne({ _id: officerId });

    if (!officer.has_overflow) {
        // Common case: all loan_ids are in the document
        return db.loans.find({ _id: { $in: officer.loan_ids } }).toArray();
    }

    // Outlier case: load from main document + overflow documents
    const overflowDocs = await db.officer_loans_overflow
        .find({ officer_id: officerId })
        .toArray();

    const allLoanIds = [
        ...officer.loan_ids,
        ...overflowDocs.flatMap(d => d.loan_ids)
    ];
    return db.loans.find({ _id: { $in: allLoanIds } }).toArray();
}

// When to use the Outlier Pattern:
// ✓ Small minority of documents would violate the normal schema design
// ✓ The outlier access pattern is less frequent than the common case
// ✓ You want optimal performance for 90% of queries without penalizing the schema

// Examples:
// → Social network: most users have <1000 followers (embed IDs); celebrities have millions (overflow)
// → Product reviews: most products have <50 reviews (embed summaries); viral products have 10K (overflow)
// → Loan repayment history: most loans <120 months (embed); restructured multi-decade loans (overflow)
```

**Q10. How do you manage schema evolution in MongoDB and what is the Schema Versioning Pattern?**
A: MongoDB's flexible schema is a double-edged sword — you can add fields without migrations, but over time documents in the same collection have different shapes. The Schema Versioning Pattern adds an explicit version field to each document, letting the application handle multiple document shapes without locking the collection for migration:

```javascript
// Problem: loan documents evolve over time
// Version 1 (2022): basic fields
{ _id: ObjectId(), loan_id: "L1", amount: 500000, status: "active" }

// Version 2 (2023): added EMI schedule and borrower snapshot
{
    _id: ObjectId(), loan_id: "L2", amount: 500000, status: "active",
    emi_schedule: [...],
    borrower_snapshot: { name: "...", credit_score: 742 }
}

// Version 3 (2024): restructured to use Decimal128 and added compliance fields
{
    _id: ObjectId(), loan_id: "L3",
    schema_version: 3,    // ← explicit version field
    amount: Decimal128.fromString("500000.00"),   // was number → now Decimal128
    status: "active",
    emi_schedule: [...],
    borrower_snapshot: {...},
    compliance: { fatf_checked: true, checked_at: new Date() }
}

// Schema Versioning Pattern — always include schema_version:
// Repository layer handles multiple versions:
class LoanRepository {
    async findById(id: string): Promise<LoanV3> {
        const doc = await db.loans.findOne({ _id: new ObjectId(id) });
        if (!doc) return null;

        // Upgrade to latest version in memory (lazy migration):
        return this.migrate(doc);
    }

    private migrate(doc: any): LoanV3 {
        const version = doc.schema_version ?? 1;  // no version field = v1

        if (version === 1) {
            // Upgrade v1 → v3: add missing fields with defaults
            doc = {
                ...doc,
                schema_version: 3,
                amount: Decimal128.fromString(doc.amount.toString()),
                emi_schedule: [],
                borrower_snapshot: null,
                compliance: { fatf_checked: false, checked_at: null }
            };
        }

        if (version === 2) {
            // Upgrade v2 → v3: convert amount to Decimal128 + add compliance
            doc = {
                ...doc,
                schema_version: 3,
                amount: Decimal128.fromString(doc.amount.toString()),
                compliance: { fatf_checked: false, checked_at: null }
            };
        }

        return doc as LoanV3;
    }

    async save(loan: LoanV3): Promise<void> {
        // Always save with current schema version:
        await db.loans.replaceOne(
            { _id: loan._id },
            { ...loan, schema_version: 3 },
            { upsert: true }
        );
    }
}

// Background migration (optional — run asynchronously to bring all docs to v3):
async function migrateToV3() {
    const cursor = db.loans.find({
        $or: [
            { schema_version: { $lt: 3 } },
            { schema_version: { $exists: false } }
        ]
    }).batchSize(100);

    for await (const doc of cursor) {
        const migrated = loanRepo.migrate(doc);
        await db.loans.replaceOne({ _id: doc._id }, migrated);
    }
}
// Run in background, collection remains live during migration
// No downtime: application handles both old and new schemas simultaneously
```

## Section 6: Practical Decision Framework

**Q11. How do you systematically decide between embedding and referencing for a new relationship?**
A: A structured set of questions applied to every relationship determines the right model. The questions cover access patterns, cardinality, mutability, and consistency requirements:

```
Decision framework — five questions:

Q1: How often is this data read together?
  Always together  → strong signal to EMBED
  Sometimes together, sometimes separately → leaning toward REFERENCE
  Almost always separately → REFERENCE

Q2: What is the cardinality of the "many" side?
  One (one-to-one)       → EMBED
  Few (2–20)             → EMBED as array
  Many (20–thousands)    → REFERENCE (child holds parent ID)
  Massive / unbounded    → REFERENCE, consider BUCKET pattern for time-series

Q3: Does the "many" side data change frequently?
  Rarely changes (config, address)          → safe to EMBED
  Changes independently and frequently      → REFERENCE (avoid update amplification)
  Changes frequently AND is shared across parents → REFERENCE (single source of truth)

Q4: Is atomicity required across the relationship?
  Yes (status + history must update together) → EMBED (document-level atomicity)
  No (or can use transactions)               → REFERENCE acceptable

Q5: What is the document growth pattern?
  Fixed size (bounded fields)           → EMBED is safe
  Grows over time (event log, comments) → REFERENCE or BUCKET

Applying the framework to common fintech relationships:

  Relationship                          │ Q1    │ Q2      │ Q3       │ Answer
  ──────────────────────────────────────┼───────┼─────────┼──────────┼─────────────
  User → Address                        │ Always│ One     │ Rarely   │ EMBED
  User → KYC Details                    │ Often │ One     │ Rarely   │ EMBED*
  Loan → Status History (last 10)       │ Always│ Few     │ Append   │ EMBED
  Loan → All Events (unbounded)         │ Rarely│ Massive │ Append   │ REFERENCE
  Loan → Borrower Details               │ Often │ One     │ Rarely   │ EXTENDED REF
  Loan → Repayments (120 for 10yr loan) │ Often │ Many    │ Append   │ REFERENCE
  Loan → Documents (max 10)             │ Often │ Few     │ Rarely   │ EMBED or REF**
  Product → Interest Tiers              │ Always│ Few     │ Rarely   │ EMBED
  Officer → Active Loans                │ Often │ 50-2000 │ Changes  │ REF + OUTLIER
  Tenant → All Loans                    │ Never │ Massive │ Append   │ REFERENCE

  * KYC details with PII: REFERENCE to a separate collection if access control differs
  ** Documents: EMBED metadata, REFERENCE actual file storage (GridFS / S3)

Rule of thumb summary:
  EMBED when:    always read together, bounded size, changes together, one-to-one or few
  REFERENCE when: read separately, unbounded or large, changes independently, shared
  EXTENDED REF:  frequent list display needing only 2-3 fields from the referenced doc
  BUCKET:        sequential/time-series data that would otherwise be unbounded array
  OUTLIER:       90% fit normal schema; 10% would break it
```

## Quick Reference Table

| Factor | Favor Embedding | Favor Referencing |
|---|---|---|
| Read frequency together | Always together | Rarely together |
| Cardinality ("many" side) | One or few (≤20) | Many or unbounded |
| Data ownership | Belongs exclusively to parent | Shared across multiple parents |
| Update pattern | Changes together with parent | Changes independently |
| Document size risk | Bounded, small | Large or grows over time |
| Atomicity requirement | Needed across related data | Not needed or transactions acceptable |
| Access control | Same permissions | Different permissions (PII in separate collection) |
| Independent queryability | Never queried alone | Has its own API / query patterns |

| Pattern | Problem it solves | When to use |
|---|---|---|
| Embedding | N+1 reads, join overhead | Data always read together, bounded size |
| Child-references parent | Unbounded one-to-many | Repayments, events, logs |
| Parent-references children | Bounded one-to-many with parent-first access | Documents list, officer's loans (small) |
| Extended Reference | N+1 for list display fields | Loan list showing borrower name without full join |
| Bucket Pattern | Unbounded time-series arrays | Event logs, sensor data, payment history |
| Outlier Pattern | Minority of documents break normal schema | Power users, viral content, large entities |
| Schema Versioning | Evolving schema without migration downtime | Adding fields, restructuring over time |
| Snapshot Embedding | Historical state must be preserved | Disbursement records, invoice snapshots |

---

**Tip for interviews:** Five things separate strong candidates on MongoDB schema design: (1) articulating **the core tradeoff in one sentence** — embed what is read together; reference what is read separately or updated independently — and being able to apply it immediately to any relationship without hesitation; (2) knowing **the 16MB BSON limit and its implications** (Q4) — unbounded embedded arrays will eventually hit this hard limit and cause write failures with no in-place recovery, which is why time-series and audit trails must always reference rather than embed, and why the Bucket Pattern exists to bridge the gap; (3) explaining **the Extended Reference Pattern as a conscious denormalization decision** (Q8) — not "duplicate the field", but "identify the 2-3 fields needed for every list row, embed only those, and accept that they need dual-write when the source changes", with the key insight that you only extend fields that change rarely; (4) being precise about **$lookup performance** (Q6) — $lookup requires an index on the `foreignField` or it degrades to O(n×m), and for high-throughput paths the application-level join (two parallel queries + in-memory merge) is often faster because it can route reads to replicas and avoids server-side memory pressure; and (5) describing **the write-complexity cost of embedding arrays** (Q13) — when you embed `recent_repayments` in the loan document to speed up reads, every payment now requires a transaction across two collections, `$push` with `$slice` to maintain the bounded array, and derived field updates, turning a simple insert into a coordinated multi-document write — the senior candidate can quantify when this tradeoff is worth it and propose the simpler alternative of embedding summary scalars instead of full sub-documents.
