# MongoDB Atlas: Vector Search and Atlas Search (Lucene-based) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Atlas Search and what problem does it solve that MongoDB's standard query engine cannot?**

A: MongoDB's native query engine is built for exact matches, range comparisons, and structured data retrieval. It excels at `{ status: 'pending', userId: 42 }` — precise predicate filtering. What it cannot do well is relevance-ranked full-text search: finding documents where "wireless keyboard" matches a product with description "Bluetooth keyboard without wires, ergonomic design," ranking results by how well they match, handling typos, synonyms, multiple languages, or faceted filtering with result counts.

Atlas Search solves this by embedding Apache Lucene — the same engine behind Elasticsearch and Solr — directly inside MongoDB Atlas. Instead of running a separate search service, Atlas Search indexes your collections into Lucene segments that live alongside your data:

```
Standard MongoDB query engine:
  db.products.find({ name: 'wireless keyboard' })
  → Exact string match only
  → "wireless keyboard" ≠ "Bluetooth keyboard without wires"
  → No relevance ranking — results in insertion order
  → No typo tolerance
  → No synonym expansion
  → No stemming ("keyboards" ≠ "keyboard")

Atlas Search ($search aggregation stage):
  db.products.aggregate([{ $search: { text: { query: 'wireless keyboard', path: 'description' } } }])
  → Full-text matching with tokenisation and stemming
  → Relevance score calculated and returned
  → Fuzzy matching for typos ("keybord" → "keyboard")
  → Synonym support ("wireless" matches "Bluetooth")
  → Autocomplete, facets, highlighting — all in one stage
```

The architectural relationship:

```
┌─────────────────────────────────────────────────────────┐
│                  MongoDB Atlas Cluster                  │
│                                                         │
│  ┌──────────────────────┐  ┌────────────────────────┐  │
│  │  MongoDB Data Store  │  │  Lucene Search Store   │  │
│  │  (BSON documents)    │  │  (inverted indexes,    │  │
│  │                      │  │   BM25 scores,         │  │
│  │  Standard queries    │  │   vector indexes)      │  │
│  │  $match, $sort, etc. │  │                        │  │
│  └──────────┬───────────┘  └────────────┬───────────┘  │
│             │                           │              │
│             └───────────────────────────┘              │
│                          │                             │
│                  Aggregation Pipeline                   │
│               $search + $match + $sort + ...            │
└─────────────────────────────────────────────────────────┘

Sync mechanism:
- MongoDB writes to BSON store (normal writes)
- Atlas Search indexes updates asynchronously into Lucene
- Near real-time: typically < 1-2 seconds lag
- NOT synchronous: a document inserted now may take seconds to be searchable
```

**Q2. How do you create an Atlas Search index — what is the index definition structure?**

A: An Atlas Search index is a JSON definition that tells Lucene how to analyse and index each field in a collection. It is distinct from MongoDB's regular `createIndex()` — Atlas Search indexes are managed through the Atlas UI, Atlas CLI, Atlas Admin API, or Terraform:

```javascript
// Atlas Search index definition structure:
{
    "name":     "products_search_idx",   // Unique name within the collection
    "type":     "search",                // "search" for text, "vectorSearch" for vectors
    "definition": {
        "mappings": {
            "dynamic": false,            // false = only index explicitly mapped fields
                                         // true  = auto-index all fields (convenient, expensive)
            "fields": {
                // Field name → how to analyse and index it
                "name": {
                    "type":     "string",
                    "analyzer": "lucene.standard",  // Tokenise, lowercase, remove stop words
                },
                "description": {
                    "type":     "string",
                    "analyzer": "lucene.english",   // English stemming ("keyboards" → "keyboard")
                    "searchAnalyzer": "lucene.standard",  // Use different analyser at query time
                },
                "sku": {
                    "type":     "string",
                    "analyzer": "lucene.keyword",   // Treat entire value as one token (no splitting)
                    // Good for: product codes, IDs, exact-match fields
                },
                "price": {
                    "type": "number",               // Enables range filters and sorting
                },
                "category": {
                    "type": "string",
                    "analyzer": "lucene.keyword",   // For faceting — exact category name
                },
                "tags": {
                    "type":     "string",
                    "analyzer": "lucene.standard",
                    // Array of strings — each element is indexed independently
                },
                "inStock": {
                    "type": "boolean",              // For filter conditions
                },
                "createdAt": {
                    "type": "date",                 // Enables date range filters and sorting
                },
                "embedding": {
                    "type":         "knnVector",    // For vector search
                    "dimensions":   1536,           // Must match your embedding model's output
                    "similarity":   "cosine",       // cosine | euclidean | dotProduct
                },
                // Nested document field:
                "variants": {
                    "type": "embeddedDocuments",    // Index nested arrays of objects
                    "dynamic": false,
                    "fields": {
                        "color": { "type": "string", "analyzer": "lucene.keyword" },
                        "size":  { "type": "string", "analyzer": "lucene.keyword" },
                        "stock": { "type": "number" },
                    }
                },
                // Autocomplete field (stores n-grams for prefix matching):
                "nameAutocomplete": {
                    "type":            "autocomplete",
                    "analyzer":        "lucene.standard",
                    "tokenization":    "edgeGram",  // edgeGram | rightEdgeGram | nGram | regexCaptureGroup
                    "minGrams":        2,           // Minimum n-gram length
                    "maxGrams":        15,          // Maximum n-gram length
                    "foldDiacritics":  true,        // "café" → "cafe"
                },
            }
        },
        // Custom analyser definitions:
        "analyzers": [
            {
                "name": "myProductAnalyzer",
                "charFilters": [
                    { "type": "htmlStrip" }          // Remove HTML tags before tokenising
                ],
                "tokenizer": {
                    "type": "whitespace"             // Split on whitespace (not punctuation)
                },
                "tokenFilters": [
                    { "type": "lowercase" },
                    { "type": "stop", "tokens": ["the", "a", "an", "and", "or"] },
                    { "type": "snowballStemming", "stemmerName": "english" },
                    { "type": "shingle", "minShingleSize": 2, "maxShingleSize": 3 }
                    // Shingles: "fast wireless keyboard" → also indexes "fast wireless", "wireless keyboard"
                ]
            }
        ],
        // Synonyms:
        "synonyms": [
            {
                "name":     "productSynonyms",
                "source":   { "collection": "synonyms" },
                "analyzer": "lucene.standard"
                // synonyms collection documents:
                // { "mappings": { "type": "equivalent", "synonyms": ["wireless", "bluetooth", "wifi"] } }
                // { "mappings": { "type": "explicit", "input": ["laptop"], "synonyms": ["notebook", "computer"] } }
            }
        ]
    }
}

// Create via Atlas CLI:
// atlas clusters search indexes create --clusterName myCluster --file index.json

// Create via MongoDB driver (Node.js):
// await db.collection('products').createSearchIndex({
//     name: 'products_search_idx',
//     definition: { mappings: { ... } }
// });
```

## Section 2: Atlas Search Queries

**Q3. How do you write an Atlas Search query — what is the `$search` stage and its key operators?**

A: Atlas Search queries are written as a `$search` aggregation stage at the beginning of an aggregation pipeline. The `$search` stage accepts a query object with one or more operators that define what to search for:

```javascript
// ── Basic text search ─────────────────────────────────────────────────────────
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',    // Name of the Atlas Search index
            text: {
                query: 'wireless keyboard',
                path:  'description',         // Field(s) to search
                // path: ['name', 'description']  // Search multiple fields
                fuzzy: {
                    maxEdits:       1,         // Allow 1 typo (Levenshtein distance)
                    prefixLength:   3,         // First 3 chars must match exactly
                    maxExpansions:  50,        // Max variants to consider
                }
            }
        }
    },
    // $meta: 'searchScore' retrieves the relevance score (0-1 range, higher is better):
    {
        $addFields: {
            score: { $meta: 'searchScore' }
        }
    },
    { $sort: { score: -1 } },    // Sort by relevance (usually redundant — $search already ranks)
    { $limit: 20 },
    {
        $project: {
            name:        1,
            description: 1,
            price:       1,
            score:       1,
        }
    }
]);

// ── compound operator: combining multiple conditions ────────────────────────────
// The most important operator — combines must/should/mustNot/filter clauses:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            compound: {
                // must: ALL of these must match (affects score AND filters)
                must: [
                    {
                        text: {
                            query: 'keyboard',
                            path:  ['name', 'description'],
                        }
                    }
                ],
                // should: ANY of these improve the score (optional — boosts ranking)
                should: [
                    {
                        text: {
                            query: 'wireless bluetooth',
                            path:  'description',
                            score: { boost: { value: 2.0 } }  // Double the score contribution
                        }
                    },
                    {
                        text: {
                            query: 'mechanical',
                            path:  'name',
                        }
                    }
                ],
                // mustNot: NONE of these may match
                mustNot: [
                    {
                        text: { query: 'refurbished used', path: 'condition' }
                    }
                ],
                // filter: must match but does NOT affect the relevance score
                // Much more efficient than 'must' for structured predicates:
                filter: [
                    {
                        range: {
                            path: 'price',
                            gte:  50,
                            lte:  300
                        }
                    },
                    {
                        equals: {
                            path:  'inStock',
                            value: true
                        }
                    },
                    {
                        text: {
                            query: 'electronics',
                            path:  'category',
                            score: { constant: { value: 0 } }  // Zero score contribution
                        }
                    }
                ]
            }
        }
    },
    { $limit: 20 },
    { $project: { name: 1, price: 1, score: { $meta: 'searchScore' } } }
]);

// ── Key $search operators ─────────────────────────────────────────────────────
// text: full-text search with tokenisation and stemming
{
    text: { query: 'running shoes', path: 'name' }
}

// range: numeric, date, or string range
{
    range: { path: 'price', gte: 100, lte: 500 }
}
{
    range: { path: 'createdAt', gte: new Date('2024-01-01'), lte: new Date('2024-12-31') }
}

// equals: exact value match (like a $match filter but inside $search)
{
    equals: { path: 'inStock', value: true }
}
{
    equals: { path: 'userId', value: ObjectId('...') }
}

// in: match any value in a list (like $in in standard queries)
{
    in: { path: 'category', value: ['Electronics', 'Computers', 'Accessories'] }
}

// phrase: exact phrase match (word order matters)
{
    phrase: { query: 'wireless mechanical keyboard', path: 'name' }
}

// regex: regular expression match (powerful but slow — use sparingly)
{
    regex: { query: 'KEY.*BOARD', path: 'name', allowAnalyzedField: true }
}

// wildcard: glob-style pattern matching
{
    wildcard: { query: 'key*oard', path: 'name', allowAnalyzedField: true }
}

// exists: field must have a value (not null, not missing)
{
    exists: { path: 'description' }
}

// near: numeric/date proximity (score based on distance from a target value)
{
    near: {
        path:   'price',
        origin: 200,        // Target price
        pivot:  50,         // Score halves every 50 units of distance
    }
}

// geoWithin / geoShape: geographic search
{
    geoWithin: {
        path:   'location',
        circle: { center: { type: 'Point', coordinates: [77.5946, 12.9716] }, radius: 5000 }
    }
}
```

**Q4. How do you implement faceted search with Atlas Search — returning result counts per category?**

A: Faceted search shows counts of results per category/brand/price range, letting users filter progressively. Atlas Search implements this with `$searchMeta` for facet counts and `$search` for paginated results — often run in parallel:

```javascript
// Faceted search: get both results AND facet counts in one aggregation
db.products.aggregate([
    {
        $searchMeta: {
            // $searchMeta returns metadata (facet counts) WITHOUT the actual documents
            // Use $search when you want documents; $searchMeta for counts only
            index: 'products_search_idx',
            facet: {
                operator: {
                    // The base query (same as $search query):
                    compound: {
                        must: [
                            { text: { query: 'keyboard', path: ['name', 'description'] } }
                        ],
                        filter: [
                            { equals: { path: 'isActive', value: true } }
                        ]
                    }
                },
                facets: {
                    // Facet 1: count results per category
                    categoriesFacet: {
                        type:  'string',
                        path:  'category',
                        numBuckets: 10      // Return top 10 categories by count
                    },
                    // Facet 2: count results per price range
                    priceFacet: {
                        type:       'number',
                        path:       'price',
                        boundaries: [0, 50, 100, 200, 500, 1000, Infinity],
                        // Creates buckets: 0-50, 50-100, 100-200, 200-500, 500-1000, 1000+
                        default:    'Other'  // Label for values outside boundaries
                    },
                    // Facet 3: count results per brand
                    brandFacet: {
                        type:  'string',
                        path:  'brand',
                        numBuckets: 20
                    },
                    // Facet 4: date facet
                    dateFacet: {
                        type:       'date',
                        path:       'createdAt',
                        boundaries: [
                            new Date('2024-01-01'),
                            new Date('2024-04-01'),
                            new Date('2024-07-01'),
                            new Date('2024-10-01'),
                            new Date('2025-01-01'),
                        ],
                        default: 'Other'
                    }
                }
            }
        }
    }
]);

// $searchMeta output:
// {
//   "count": { "lowerBound": 1247 },   // Approximate total match count (exact count is expensive)
//   "facet": {
//     "categoriesFacet": {
//       "buckets": [
//         { "_id": "Electronics", "count": 523 },
//         { "_id": "Gaming",      "count": 312 },
//         { "_id": "Office",      "count": 198 },
//         ...
//       ]
//     },
//     "priceFacet": {
//       "buckets": [
//         { "_id": 0,    "count": 45  },   // $0-$50
//         { "_id": 50,   "count": 234 },   // $50-$100
//         { "_id": 100,  "count": 567 },   // $100-$200
//         { "_id": 200,  "count": 312 },   // $200-$500
//         { "_id": 500,  "count": 78  },   // $500-$1000
//         { "_id": 1000, "count": 11  },   // $1000+
//       ]
//     },
//     ...
//   }
// }

// ── Running both search results and facet counts in parallel ───────────────────
// Use $facet to run multiple sub-pipelines in one aggregation:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            compound: {
                must: [{ text: { query: 'keyboard', path: ['name', 'description'] } }],
                filter: [
                    { equals: { path: 'inStock', value: true } },
                    // Apply selected filters (e.g., user clicked "Electronics"):
                    { text: { query: 'Electronics', path: 'category' } }
                ]
            }
        }
    },
    {
        $facet: {
            // Branch 1: paginated search results
            results: [
                { $skip: 0 },
                { $limit: 20 },
                { $project: { name: 1, price: 1, thumbnail: 1, score: { $meta: 'searchScore' } } }
            ],
            // Branch 2: facet counts for the sidebar
            facetCounts: [
                {
                    $searchMeta: {
                        facet: {
                            operator: {
                                // Same query but without the category filter (so all categories show counts)
                                text: { query: 'keyboard', path: ['name', 'description'] }
                            },
                            facets: {
                                categoriesFacet: { type: 'string', path: 'category', numBuckets: 20 },
                                priceFacet: {
                                    type: 'number', path: 'price',
                                    boundaries: [0, 50, 100, 200, 500, 1000]
                                }
                            }
                        }
                    }
                }
            ],
            // Branch 3: total count
            totalCount: [
                { $count: 'total' }
            ]
        }
    }
]);
```

**Q5. How do you implement autocomplete with Atlas Search?**

A: Autocomplete in Atlas Search uses the `autocomplete` field type which stores edge n-grams — prefixes of every token — enabling fast prefix matching as users type:

```javascript
// The autocomplete field type must be defined in the index:
// "nameAutocomplete": {
//     "type":         "autocomplete",
//     "analyzer":     "lucene.standard",
//     "tokenization": "edgeGram",
//     "minGrams":     2,
//     "maxGrams":     15,
// }

// When "Mechanical Keyboard" is indexed with edgeGram:
// Tokens stored: "me", "mec", "mech", "mecha", ..., "mechanical",
//                "ke", "key", "keyb", "keybo", ..., "keyboard"

// Autocomplete query — as user types "mech key":
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            autocomplete: {
                query: 'mech key',
                path:  'nameAutocomplete',   // Must be an 'autocomplete' field
                fuzzy: {
                    maxEdits: 1,             // Tolerate one typo
                }
                // tokenOrder: 'any'         // (default) tokens can appear in any order
                // tokenOrder: 'sequential'  // Tokens must appear in sequence (stricter)
            }
        }
    },
    { $limit: 10 },
    { $project: { name: 1, score: { $meta: 'searchScore' } } }
]);
// Returns: "Mechanical Keyboard", "Mechanical Keypad", ...

// ── Multi-field autocomplete ───────────────────────────────────────────────────
// Autocomplete on both name and brand:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            compound: {
                should: [
                    {
                        autocomplete: {
                            query: userInput,
                            path:  'nameAutocomplete',
                            score: { boost: { value: 3.0 } }  // Name matches score higher
                        }
                    },
                    {
                        autocomplete: {
                            query: userInput,
                            path:  'brandAutocomplete',
                            score: { boost: { value: 1.5 } }
                        }
                    },
                    {
                        autocomplete: {
                            query: userInput,
                            path:  'categoryAutocomplete',
                        }
                    }
                ],
                minimumShouldMatch: 1  // At least one of the should clauses must match
            }
        }
    },
    { $limit: 10 },
    // Return distinct results (de-duplicate if same product matches multiple fields):
    {
        $group: {
            _id:   '$_id',
            name:  { $first: '$name' },
            score: { $first: { $meta: 'searchScore' } }
        }
    },
    { $sort: { score: -1 } },
    { $limit: 10 }
]);

// ── Highlighting matched terms in results ──────────────────────────────────────
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            text: { query: 'wireless keyboard', path: 'description' },
            highlight: {
                path:       'description',  // Field to highlight
                maxCharsToExamine: 500000,  // Characters to examine for highlights
                maxNumPassages:    5,       // Max highlighted snippets per document
            }
        }
    },
    {
        $project: {
            name:        1,
            description: 1,
            highlights:  { $meta: 'searchHighlights' },
            // Returns: [{
            //   "score": 1.456,
            //   "path":  "description",
            //   "texts": [
            //     { "value": "Ergonomic ", "type": "text" },
            //     { "value": "wireless",   "type": "hit"  },   ← matched term
            //     { "value": " ",          "type": "text" },
            //     { "value": "keyboard",   "type": "hit"  },   ← matched term
            //     { "value": " with...",   "type": "text" }
            //   ]
            // }]
        }
    }
]);
```

## Section 3: Vector Search

**Q6. What is vector search and what problem does it solve that Atlas Search cannot?**

A: Atlas Search (Lucene) finds documents containing specific words or their stems and synonyms. It cannot understand meaning — "fast car" and "speedy automobile" are completely different to keyword search. Vector search solves this by representing documents and queries as numerical vectors (embeddings) where semantic similarity is captured by geometric proximity in high-dimensional space:

```
Keyword search (Atlas Search):
  Query: "fast car"
  Matches: documents containing "fast" OR "car" (with BM25 ranking)
  Does NOT match: "speedy automobile", "quick vehicle", "rapid sedan"

Vector search (Atlas Vector Search):
  1. Encode "fast car" as an embedding vector: [0.23, -0.87, 0.45, ..., 0.12] (1536 dims)
  2. Find vectors in the database that are geometrically CLOSE to this vector
  3. Returns: "speedy automobile" (close in vector space), "quick vehicle", etc.
  → Semantic similarity, not keyword overlap

When to use each:
  Atlas Search: keyword search, autocomplete, filtering, facets, exact/fuzzy text matching
  Vector Search: semantic search, "similar items", recommendation, question-answering (RAG)
  Both together: hybrid search (keyword + semantic — the best results in practice)
```

How embeddings work:

```javascript
// Embedding models convert text (or images, audio) to fixed-length float arrays
// The array captures semantic meaning: similar concepts → similar vectors

// Example embedding process for a product description:
// Input:  "Ergonomic wireless mechanical keyboard with RGB lighting"
// Model:  text-embedding-3-small (OpenAI, 1536 dimensions)
// Output: [-0.023, 0.145, -0.891, 0.234, ..., 0.056]  ← 1536 floats

// Similar products produce vectors that are geometrically close:
// "Compact Bluetooth keyboard with backlight" → [-0.018, 0.152, -0.876, ...]
// "Gaming mouse with RGB"                    → [0.567, -0.234, 0.123, ...]
//   ↑ gaming keyboard is close to the query
//              ↑ gaming mouse is far from a keyboard query

// Similarity metrics:
// cosine:     angle between vectors (normalised — doesn't care about magnitude)
//             Best for: text embeddings (most common)
// euclidean:  geometric distance between vector endpoints
//             Best for: absolute magnitude matters (e.g., image features)
// dotProduct: inner product (requires normalised vectors for same result as cosine)
//             Best for: maximum performance (fastest computation)
```

**Q7. How do you set up and query Atlas Vector Search — the complete workflow?**

A: Vector search requires four steps: create a vector index, generate embeddings for your documents, store embeddings in documents, and query with a vector:

```javascript
// ── Step 1: Define the vector search index ────────────────────────────────────
// In Atlas UI: Search → Create Index → Atlas Vector Search
// Index definition:
{
    "name": "products_vector_idx",
    "type": "vectorSearch",
    "fields": [
        {
            "type":       "vector",
            "path":       "embedding",       // Field storing the float array
            "numDimensions": 1536,           // Must match your embedding model
            "similarity": "cosine",          // cosine | euclidean | dotProduct
        },
        // Optional: fields to filter on during vector search
        {
            "type": "filter",
            "path": "category"
        },
        {
            "type": "filter",
            "path": "price"
        },
        {
            "type": "filter",
            "path": "inStock"
        }
    ]
}

// ── Step 2: Generate and store embeddings ─────────────────────────────────────
// Using OpenAI's embedding API (Node.js):
import OpenAI from 'openai';
import { MongoClient } from 'mongodb';

const openai  = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
const client  = new MongoClient(process.env.MONGODB_URI);
const db      = client.db('myapp');
const products = db.collection('products');

async function generateEmbedding(text: string): Promise<number[]> {
    const response = await openai.embeddings.create({
        model: 'text-embedding-3-small',   // 1536 dimensions
        input: text,
    });
    return response.data[0].embedding;
}

// Embed all products (run once, or on write):
async function embedAllProducts(): Promise<void> {
    const cursor = products.find({ embedding: { $exists: false } });

    for await (const product of cursor) {
        // Create a rich text representation to embed:
        const textToEmbed = [
            product.name,
            product.description,
            product.category,
            product.tags?.join(' '),
            `Price: ${product.price}`,
        ].filter(Boolean).join('. ');

        const embedding = await generateEmbedding(textToEmbed);

        await products.updateOne(
            { _id: product._id },
            { $set: { embedding } }
        );

        // Rate limiting: OpenAI limits requests/minute
        await new Promise(resolve => setTimeout(resolve, 100));
    }
}

// Embed new documents on insert (application layer):
async function createProduct(data: ProductInput): Promise<Product> {
    const textToEmbed = `${data.name}. ${data.description}. ${data.category}`;
    const embedding   = await generateEmbedding(textToEmbed);

    const result = await products.insertOne({ ...data, embedding });
    return { ...data, _id: result.insertedId, embedding };
}

// ── Step 3: Query with $vectorSearch ─────────────────────────────────────────
async function semanticSearch(query: string, limit = 10): Promise<Product[]> {
    // Generate embedding for the query (same model as document embeddings):
    const queryEmbedding = await generateEmbedding(query);

    const results = await products.aggregate([
        {
            $vectorSearch: {
                index:         'products_vector_idx',
                path:          'embedding',
                queryVector:   queryEmbedding,    // The query vector
                numCandidates: 150,               // Candidates to consider (≥ limit)
                limit:         limit,             // Final results to return

                // Optional: pre-filter BEFORE vector search (requires filter fields in index):
                filter: {
                    inStock: { $eq: true },
                    price:   { $gte: 50, $lte: 500 },
                    // Note: filter syntax uses standard MongoDB operators
                }

        {
            $project: {
                name:        1,
                description: 1,
                price:       1,

                score: { $meta: 'vectorSearchScore' },
                // Exclude the embedding field (large and not useful to clients):
                embedding: 0,
            }
        }
    ]).toArray();

    return results as Product[];
}
```

**Q8. What is the `numCandidates` parameter and how does the HNSW algorithm work?**

A: `numCandidates` controls the trade-off between search quality and performance in the Hierarchical Navigable Small World (HNSW) approximate nearest neighbour algorithm that Atlas Vector Search uses:

```
Exact nearest neighbour search:
  Compare query vector against EVERY document vector
  → Always finds the true closest vectors
  → O(N × D) time (N documents, D dimensions)
  → Too slow for large collections (1M docs × 1536 dims = ~6 billion operations per query)

HNSW (Approximate Nearest Neighbour):
  A graph-based index where each node (document) connects to its neighbours
  Query traversal navigates the graph to find approximately nearest neighbours
  → Sub-linear time: O(log N × D) — dramatically faster
  → Trade-off: may miss the absolute best matches (approximate, not exact)
  → numCandidates controls how thoroughly the graph is explored

numCandidates parameter:
  Higher value → explores more of the graph → better quality → slower
  Lower value  → explores less              → lower quality → faster
  Rule: numCandidates ≥ 10 × limit (MongoDB's recommendation)
  For limit=10: numCandidates ≥ 100

  numCandidates: 50  → fast, lower recall (some good matches may be missed)
  numCandidates: 150 → balanced (recommended starting point)
  numCandidates: 500 → high quality, slower (for precision-critical use cases)
```

```javascript
// The impact of numCandidates on recall quality:
// For a vector search with limit=10:

// numCandidates: 20 (too low)
// → May miss 2-3 of the true top-10 results
// → Very fast: explores only 20 graph nodes

// numCandidates: 100 (recommended)
// → Typically finds 9-10 of the true top-10 results (90-100% recall)
// → Good balance of speed and quality

// numCandidates: 1000 (high quality)
// → Finds 99%+ of true top-10 results
// → Significantly slower — use only when exact accuracy is critical

// Measuring recall quality:
// No direct metric from MongoDB, but you can test empirically:
// 1. Run exact brute-force search on a small collection: $search over all vectors
// 2. Run vector search with various numCandidates
// 3. Compare result sets: what percentage of exact results appear in ANN results?

// Setting numCandidates based on use case:
const numCandidates = {
    productRecommendation:   limit * 10,  // 10× factor — moderate quality
    similarDocumentSearch:   limit * 15,  // 15× — higher quality
    criticalSemanticSearch:  limit * 50,  // 50× — maximum quality, slower
    realtimeAutocomplete:    limit * 5,   // 5× — minimum quality for speed
};

// The filter interaction with numCandidates:
// When using pre-filter in $vectorSearch:
// numCandidates applies to the POST-FILTER candidate pool
// If your filter removes 99% of documents, consider:
// Option A: Increase numCandidates dramatically to compensate
// Option B: Use post-filter ($match after $vectorSearch) instead of pre-filter
//           Post-filter: ANN finds candidates from ALL documents, then filters
//           Tradeoff: post-filter may return fewer results than 'limit' if many are filtered
db.products.aggregate([
    {
        $vectorSearch: {
            index:         'products_vector_idx',
            path:          'embedding',
            queryVector:   queryEmbedding,
            numCandidates: 1000,   // Large because post-filter will remove many
            limit:         100,    // Oversample because post-filter will reduce this
        }
    },
    // Post-filter (standard $match — runs after vector search):
    { $match: { inStock: true, price: { $gte: 50, $lte: 500 } } },
    { $limit: 10 },   // Final limit after filtering
    { $project: { name: 1, price: 1, score: { $meta: 'vectorSearchScore' } } }
```

## Section 4: Hybrid Search

**Q9. What is hybrid search and how do you implement it by combining `$search` and `$vectorSearch`?**

A: Hybrid search combines keyword search (Atlas Search / BM25) with semantic search (Vector Search) to get the benefits of both: keyword search finds exact term matches reliably; semantic search finds conceptually related content. The challenge is combining two different scoring systems into one ranked result — Reciprocal Rank Fusion (RRF) is the standard technique:

```javascript
// ── Reciprocal Rank Fusion (RRF) ─────────────────────────────────────────────
// RRF combines rankings from multiple retrieval systems:
// RRF_score(d) = Σ 1 / (k + rank_i(d))
// where rank_i(d) is the rank of document d in system i, and k is a constant (default 60)
// A document ranked #1 in any system gets a high score regardless of its score value
// This avoids the problem of incomparable score scales between BM25 and cosine similarity

async function hybridSearch(query: string, limit = 10): Promise<SearchResult[]> {
    const queryEmbedding = await generateEmbedding(query);
    const k              = 60;   // RRF constant (standard value)
    const candidateCount = 100;  // Fetch more than limit to re-rank

    const results = await db.collection('products').aggregate([
        // ── Stage 1: Run $vectorSearch and $search in parallel via $unionWith ──
        {
            $vectorSearch: {
                index:         'products_vector_idx',
                path:          'embedding',
                queryVector:   queryEmbedding,
                numCandidates: candidateCount * 3,
                limit:         candidateCount,
            }
        },
        // Tag vectorSearch results with their rank:
        {
            $group: {
                _id: null,
                vsResults: { $push: { doc: '$$ROOT', vsScore: { $meta: 'vectorSearchScore' } } }
            }
        },
        { $unwind: { path: '$vsResults', includeArrayIndex: 'vsRank' } },
        {
            $project: {
                _id:    '$vsResults.doc._id',
                doc:    '$vsResults.doc',
                vsRank: { $add: ['$vsRank', 1] },  // 1-indexed rank
                vsRRF:  {
                    $divide: [1, { $add: [k, { $add: ['$vsRank', 1] }] }]
                }
            }
        },

        // ── Stage 2: Add keyword search results via $unionWith ─────────────────
        {
            $unionWith: {
                coll:     'products',
                pipeline: [
                    {
                        $search: {
                            index: 'products_search_idx',
                            text:  { query, path: ['name', 'description'] }
                        }
                    },
                    { $limit: candidateCount },
                    {
                        $group: {
                            _id:       null,
                            ksResults: { $push: { doc: '$$ROOT', ksScore: { $meta: 'searchScore' } } }
                        }
                    },
                    { $unwind: { path: '$ksResults', includeArrayIndex: 'ksRank' } },
                    {
                        $project: {
                            _id:    '$ksResults.doc._id',
                            doc:    '$ksResults.doc',
                            ksRank: { $add: ['$ksRank', 1] },
                            ksRRF:  {
                                $divide: [1, { $add: [k, { $add: ['$ksRank', 1] }] }]
                            }
                        }
                    }
                ]
            }
        },

        // ── Stage 3: Merge and combine RRF scores ─────────────────────────────
        {
            $group: {
                _id:   '$_id',
                doc:   { $first: '$doc' },
                vsRRF: { $max: { $ifNull: ['$vsRRF', 0] } },
                ksRRF: { $max: { $ifNull: ['$ksRRF', 0] } },
            }
        },
        {
            $addFields: {
                // Combined RRF score: sum of both systems' contributions
                hybridScore: { $add: ['$vsRRF', '$ksRRF'] }
                // Optional: weight the two systems differently
                // hybridScore: {
                //     $add: [
                //         { $multiply: ['$vsRRF', 0.6] },  // 60% vector
                //         { $multiply: ['$ksRRF', 0.4] },  // 40% keyword
                //     ]
                // }
            }
        },
        { $sort:  { hybridScore: -1 } },
        { $limit: limit },
        {
            $project: {
                name:        '$doc.name',
                description: '$doc.description',
                price:       '$doc.price',
                hybridScore: 1,
                vsRRF:       1,
                ksRRF:       1,
            }
        }
    ]).toArray();

    return results;
}

// ── Simpler hybrid approach: sequential re-ranking ────────────────────────────
// For simpler implementations: run both searches, combine with weighted scoring:
async function simpleHybridSearch(query: string, limit = 10) {
    const [vectorResults, keywordResults] = await Promise.all([
        // Vector search results with rank:
        db.collection('products').aggregate([
            { $vectorSearch: { index: 'products_vector_idx', path: 'embedding',
                               queryVector: await generateEmbedding(query),
                               numCandidates: 100, limit: 50 } },
            { $project: { name: 1, vsScore: { $meta: 'vectorSearchScore' } } }
        ]).toArray(),

        // Keyword search results with rank:
        db.collection('products').aggregate([
            { $search: { index: 'products_search_idx',
                         text: { query, path: ['name', 'description'] } } },
            { $limit: 50 },
            { $project: { name: 1, ksScore: { $meta: 'searchScore' } } }
        ]).toArray(),
    ]);

    // Merge and score using RRF in application code:
    const scores = new Map<string, { doc: any; vsRank?: number; ksRank?: number }>();

    vectorResults.forEach((doc, rank) => {
        const id = doc._id.toString();
        scores.set(id, { doc, vsRank: rank + 1 });
    });

    keywordResults.forEach((doc, rank) => {
        const id  = doc._id.toString();
        const entry = scores.get(id) ?? { doc };
        entry.ksRank = rank + 1;
        scores.set(id, entry);
    });

    return [...scores.values()]
        .map(({ doc, vsRank, ksRank }) => ({
            ...doc,
            hybridScore: (vsRank ? 1 / (60 + vsRank) : 0)
                       + (ksRank ? 1 / (60 + ksRank) : 0),
        }))
        .sort((a, b) => b.hybridScore - a.hybridScore)
        .slice(0, limit);
}
```

## Section 5: Production Patterns

**Q10. How do you implement RAG (Retrieval-Augmented Generation) with Atlas Vector Search and an LLM?**

A: RAG is the dominant pattern for building AI assistants that answer questions using your own data. Atlas Vector Search serves as the retrieval component — finding relevant document chunks — which are then passed to an LLM as context:

```typescript
import OpenAI from 'openai';
import { MongoClient } from 'mongodb';

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
const db     = (new MongoClient(process.env.MONGODB_URI!)).db('knowledge_base');

// ── Step 1: Chunk and embed your documents ────────────────────────────────────
// Documents are split into chunks before embedding (to fit LLM context windows):
async function processDocument(doc: { title: string; content: string; source: string }) {
    const CHUNK_SIZE    = 500;   // characters per chunk (tune for your content)
    const CHUNK_OVERLAP = 100;   // overlap between chunks (context continuity)

    const chunks: string[] = [];
    let start = 0;

    while (start < doc.content.length) {
        chunks.push(doc.content.slice(start, start + CHUNK_SIZE));
        start += CHUNK_SIZE - CHUNK_OVERLAP;
    }

    // Embed all chunks in one API call (batching is more efficient):
    const response = await openai.embeddings.create({
        model: 'text-embedding-3-small',
        input: chunks,
    });

    const chunkDocuments = chunks.map((text, i) => ({
        text,
        embedding:  response.data[i].embedding,
        source:     doc.source,
        title:      doc.title,
        chunkIndex: i,
        totalChunks: chunks.length,
    }));

    await db.collection('knowledge_chunks').insertMany(chunkDocuments);
}

// ── Step 2: RAG query function ────────────────────────────────────────────────
async function ragQuery(userQuestion: string): Promise<string> {
    // 1. Embed the user's question:
    const questionEmbedding = await generateEmbedding(userQuestion);

    // 2. Retrieve relevant chunks via vector search:
    const relevantChunks = await db.collection('knowledge_chunks').aggregate([
        {
            $vectorSearch: {
                index:         'knowledge_vector_idx',
                path:          'embedding',
                queryVector:   questionEmbedding,
                numCandidates: 50,
                limit:         5,    // Top 5 most relevant chunks
            }
        },
        {
            $project: {
                text:   1,
                source: 1,
                title:  1,
                score:  { $meta: 'vectorSearchScore' },
                embedding: 0,    // Don't send 1536 floats to the LLM
            }
        }
    ]).toArray();

    // 3. Build the context for the LLM:
    const context = relevantChunks
        .map(chunk => `Source: ${chunk.title}\n${chunk.text}`)
        .join('\n\n---\n\n');

    // 4. Send to LLM with the context:
    const completion = await openai.chat.completions.create({
        model: 'gpt-4o-mini',
        messages: [
            {
                role:    'system',
                content: `You are a helpful assistant. Answer the user's question using 
                          ONLY the provided context. If the context doesn't contain the 
                          answer, say you don't have that information. 
                          Always cite the source document.`
            },
            {
                role:    'user',
                content: `Context:\n${context}\n\nQuestion: ${userQuestion}`
            }
        ],
        temperature: 0.1,   // Low temperature for factual answers
    });

    const answer = completion.choices[0].message.content ?? '';

    // 5. Optionally: store the query for analytics/fine-tuning:
    await db.collection('queryLogs').insertOne({
        question:  userQuestion,
        chunks:    relevantChunks.map(c => ({ id: c._id, score: c.score })),
        answer,
        timestamp: new Date(),
    });

    return answer;
}

// ── Step 3: Hybrid RAG (better retrieval quality) ────────────────────────────
// Combine vector search + keyword search for retrieval before sending to LLM:
async function hybridRagQuery(question: string): Promise<string> {
    const embedding = await generateEmbedding(question);

    // Vector search for semantic similarity:
    const vectorChunks = await db.collection('knowledge_chunks').aggregate([
        { $vectorSearch: {

        }},
        { $project: { text: 1, source: 1, title: 1, embedding: 0,

        { $search: { index: 'knowledge_search_idx',

        { $project: { text: 1, source: 1, title: 1,

    // Merge with RRF (see Q9) and take top 5:
    const combined = mergeWithRRF(vectorChunks, keywordChunks, 5);
```

**Q11. What are the key performance and cost considerations for Atlas Search and Vector Search in production?**

A: Both features have significant resource implications that must be understood before production deployment:

```javascript
// ── Atlas Search performance considerations ───────────────────────────────────

// 1. Search index sync lag
// Atlas Search indexes are updated ASYNCHRONOUSLY — not synchronously with writes
// Expect 1-5 seconds lag under normal load; up to minutes during heavy indexing
// Impact: a freshly inserted document may not appear in search results immediately
// Design for this: don't assert immediate search visibility after writes in tests

// 2. Search index storage
// Lucene indexes are stored separately from MongoDB data
// Typically 20-50% additional storage beyond the collection size
// Monitor: Atlas UI → Search → Index storage size

// 3. $search must be the FIRST stage in an aggregation pipeline
// The $search stage cannot come after $match, $lookup, etc.
// The ordering of $search + standard stages:
// CORRECT: $search → $match → $sort → $limit → $project
// WRONG:   $match → $search (compile error)
// WRONG:   $search → $group → $search (only one $search per pipeline)

// Use $search filter clauses instead of $match for filtering:
// CORRECT:
{ $search: { compound: { filter: [{ equals: { path: 'inStock', value: true } }],
                         must: [{ text: { query: 'keyboard', path: 'name' } }] } } }
// WRONG (filter before $search not possible):
// { $match: { inStock: true } }, { $search: ... }

// 4. $searchMeta for counts (not $count + $search)
// Counting results after $search is expensive:
// SLOW: { $search: ... }, { $count: 'total' }  ← materialises all results to count
// FAST: { $searchMeta: { facet: { operator: ..., facets: {} } } }
//       ← returns approximate count without materialising results

// ── Atlas Vector Search performance considerations ────────────────────────────

// 1. Embedding generation latency
// The slowest part is usually generating the query embedding:
// text-embedding-3-small: ~50-100ms per request (OpenAI API)
// text-embedding-3-large: ~100-200ms per request
// Local model (llama.cpp): 10-50ms but requires GPU for production use
// Strategy: cache embeddings for common queries

const embeddingCache = new Map<string, number[]>();

async function getCachedEmbedding(text: string): Promise<number[]> {
    const key = text.toLowerCase().trim();
    if (embeddingCache.has(key)) return embeddingCache.get(key)!;

    const embedding = await generateEmbedding(text);
    embeddingCache.set(key, embedding);
    // TTL: LRU cache with max size to prevent unbounded growth
    return embedding;
}

// Each candidate explored adds latency:
// numCandidates: 50  → ~2ms vector search latency
// numCandidates: 150 → ~5ms vector search latency
// numCandidates: 500 → ~15ms vector search latency
// Profile with explain() to find your application's sweet spot

db.products.explain('executionStats').aggregate([

// Consider: text-embedding-3-small (1536 dims) vs ada-002 (1536) vs use your own smaller model
```

## Section 6: Scenario-Based Questions

**Q12. "Design a product search system for an e-commerce platform with 5M products: autocomplete, full-text search, facets, and 'similar products' — choosing between Atlas Search and Vector Search for each."**

A:

```javascript
// ── Architecture decision ─────────────────────────────────────────────────────
// Feature → Technology mapping:
//
// Autocomplete as user types             → Atlas Search (autocomplete field type)
// Full-text search ("wireless keyboard") → Atlas Search (BM25 relevance)
// Facets (category counts, price ranges) → Atlas Search ($searchMeta with facet)
// Filter by price, brand, in-stock       → Atlas Search (compound filter)
// "Similar products" recommendations     → Vector Search (embedding similarity)
// "Customers also viewed" (collab filter) → Vector Search or separate system
// Semantic search ("gift for dad")       → Vector Search or Hybrid

// ── Index design ─────────────────────────────────────────────────────────────

// Atlas Search index definition:
const atlasSearchIndex = {
    name: "products_search",
    definition: {
        mappings: {
            dynamic: false,
            fields: {
                // Autocomplete on name (stores n-grams):
                nameAutocomplete: {
                    type:          "autocomplete",
                    analyzer:      "lucene.standard",
                    tokenization:  "edgeGram",
                    minGrams:      2,
                    maxGrams:      15,
                    foldDiacritics: true,
                },
                // Full-text on name (higher relevance weight):
                name: {
                    type:     "string",
                    analyzer: "lucene.english",
                    // Use 'multi' to index both keyword and text forms:
                    multi: {
                        keyword: { type: "string", analyzer: "lucene.keyword" }
                    }
                },
                description: { type: "string", analyzer: "lucene.english" },
                // For facets: keyword analyser preserves exact values:
                category:    { type: "string", analyzer: "lucene.keyword" },
                brand:       { type: "string", analyzer: "lucene.keyword" },
                // For numeric filters and price facets:
                price:       { type: "number" },
                rating:      { type: "number" },
                inStock:     { type: "boolean" },
                createdAt:   { type: "date" },
            }
        },
        synonyms: [{
            name:     "productSynonyms",
            source:   { collection: "synonyms" },
            analyzer: "lucene.standard"
        }]
    }
};

// Vector search index:
const vectorSearchIndex = {
    name: "products_vector",
    type: "vectorSearch",
    fields: [
        { type: "vector", path: "embedding", numDimensions: 1536, similarity: "cosine" },
        { type: "filter", path: "category" },
        { type: "filter", path: "inStock" },
    ]
};

// ── Complete search endpoint ───────────────────────────────────────────────────
async function searchProducts(params: {
    query?: string;
    page?: number;
    limit?: number;
    filters?: { categories?: string[]; brands?: string[]; minPrice?: number;
                maxPrice?: number; inStock?: boolean };
    sort?: 'relevance' | 'price_asc' | 'price_desc' | 'rating' | 'newest';
    mode?: 'keyword' | 'semantic' | 'hybrid';
}) {
    const { query = '', page = 1, limit = 24, filters = {},
            sort = 'relevance', mode = 'keyword' } = params;

    // Build compound query:
    const filterClauses = [];
    if (filters.categories?.length)
        filterClauses.push({ in: { path: 'category', value: filters.categories } });
    if (filters.brands?.length)
        filterClauses.push({ in: { path: 'brand', value: filters.brands } });
    if (filters.minPrice !== undefined || filters.maxPrice !== undefined)
        filterClauses.push({
            range: { path: 'price', gte: filters.minPrice, lte: filters.maxPrice }
        });
    if (filters.inStock !== undefined)
        filterClauses.push({ equals: { path: 'inStock', value: filters.inStock } });

    // Sort configuration:
    const sortStage = sort === 'relevance'
        ? null  // Let Atlas Search handle relevance ordering
        : { $sort: {
            price_asc:  { price: 1 },
            price_desc: { price: -1 },
            rating:     { rating: -1 },
            newest:     { createdAt: -1 },
          }[sort] };

    if (mode === 'keyword' || !query) {
        return db.collection('products').aggregate([
            {
                $search: {
                    index: 'products_search',
                    compound: {
                        must: query ? [{ text: { query, path: ['name', 'description'],
                                                 synonyms: 'productSynonyms' } }] : [],
                        should: query ? [{ text: { query, path: 'name',
                                                   score: { boost: { value: 2.0 } } } }] : [],
                        filter: filterClauses,
                        minimumShouldMatch: 0,
                    }
                }
            },
            ...(sortStage ? [sortStage] : []),
            { $skip: (page - 1) * limit },
            { $limit: limit },
            { $project: { name: 1, price: 1, brand: 1, thumbnail: 1, rating: 1,
                          score: { $meta: 'searchScore' }, embedding: 0 } }
        ]).toArray();
    }

    if (mode === 'semantic') {
        const queryEmbedding = await generateEmbedding(query);
        return db.collection('products').aggregate([
            { $vectorSearch: {
                index:         'products_vector',
                path:          'embedding',
                queryVector:   queryEmbedding,
                numCandidates: limit * 15,
                limit:         limit,
                filter:        {
                    ...(filters.inStock !== undefined && { inStock: { $eq: filters.inStock } }),
                    ...(filters.categories?.length && { category: { $in: filters.categories } }),
                }
            }},
            { $project: { name: 1, price: 1, brand: 1, thumbnail: 1, rating: 1,
                          score: { $meta: 'vectorSearchScore' }, embedding: 0 } }
        ]).toArray();
    }

    // Hybrid mode (default for best quality):
    return hybridSearch(query, limit);
}

// ── Similar products (pure vector search) ────────────────────────────────────
async function getSimilarProducts(productId: string, limit = 8): Promise<Product[]> {
    // Fetch the product's embedding:
    const product = await db.collection('products').findOne(

        { projection: { embedding: 1, category: 1 } }
    );
    if (!product?.embedding) throw new Error('Product not found or not embedded');

    return db.collection('products').aggregate([
        {
            $vectorSearch: {
                index:         'products_vector',
                path:          'embedding',
                queryVector:   product.embedding,
                numCandidates: 100,
                limit:         limit + 1,  // +1 because the product itself will match
                filter: {
                    // Optionally limit to same category:
                    category: { $eq: product.category }
                }
            }
        },
        // Exclude the product itself from similar results:
        { $match: { _id: { $ne: new ObjectId(productId) } } },
        { $limit: limit },
        { $project: { name: 1, price: 1, thumbnail: 1, rating: 1,
                      similarity: { $meta: 'vectorSearchScore' }, embedding: 0 } }
    ]).toArray() as unknown as Product[];
}
```

**Q13. "Your Atlas Search query returns wrong results — the expected product doesn't appear. How do you debug it?"**

A:

```javascript
// ── Step 1: Verify the document is indexed ────────────────────────────────────
// Check index status (Atlas UI → Search → Index Status → should be READY, not PENDING)
// For newly created indexes: wait for initial sync (may take minutes for large collections)
// For new documents: wait 1-5 seconds for async sync

// Step 2: Check if the document matches by disabling text analysis:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            // Start with 'exists' to confirm the document is indexed at all:
            exists: { path: 'name' }
        }
    },
    { $match: { _id: ObjectId('the-missing-product-id') } },
    { $project: { name: 1 } }
]);
// If this returns the document: it IS indexed, the text query is the problem
// If this returns nothing: the document is NOT indexed (sync issue)

// Step 3: Use the Atlas Search Analyzer Debugger (Atlas UI)
// Search → Analyzers → Analyze Text
// Input: your query term, your field's analyzer
// See exactly what tokens are generated and indexed

// Step 4: Test the analyzer programmatically:
// $search doesn't have a "show tokens" option, but you can test using
// the keywordAnalyzer to find exact field values:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            // Try keyword (exact) search first to isolate text analysis issues:
            text: {
                query:    'EXACT PRODUCT NAME',  // Exact value from the document
                path:     'name',
                // If this returns the product: the issue is in text analysis of your original query
                // If this also returns nothing: mapping problem or document not indexed
            }
        }
    },
    { $limit: 5 }
]);

// Step 5: Check for type mismatches in the index:
// A field indexed as 'string' but queried with 'range' will fail silently
// A field indexed as 'keyword' but queried with 'text' won't do stemming

// Step 6: Verify the field path in the index definition:
// If a nested field: use dot notation in both the index and the query
// Index: "variants.color": { "type": "string" }
// Query: { text: { query: 'red', path: 'variants.color' } }
// Common mistake: indexing 'variants.color' but querying 'variants.colors' (plural)

// Step 7: Score debugging — use explain to see why documents score as they do:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            text: { query: 'keyboard', path: ['name', 'description'] }
        }
    },
    { $limit: 5 },
    {
        $project: {
            name:    1,
            score:   { $meta: 'searchScore' },
            // Note: Atlas Search doesn't expose per-term scoring directly
            // Use Atlas UI Search Tester for detailed score breakdown
        }
    }
]);
// Low score for expected document → stemming issue, missing synonyms, or wrong field weight

// Step 8: Check for synonym configuration issues:
// Test with synonyms disabled to isolate:
db.products.aggregate([
    {
        $search: {
            index: 'products_search_idx',
            text: {
                query: 'keyboard',
                path:  'name',
                // NO synonyms field → tests without synonym expansion
            }
        }
    },
    { $limit: 5 }
]);
// If this works: synonym configuration might be wrong
// If this also fails: the issue is elsewhere

// Step 9: Use the Atlas Search Tester in the UI
// Collections → Search → Query Editor
// Provides: visual query builder, score explanation, synonym expansion preview
// Most effective debugging tool for Atlas Search issues
```

## Quick Reference Table

| Feature | Atlas Search | Atlas Vector Search |
|---|---|---|
| **Underlying technology** | Apache Lucene | HNSW approximate nearest neighbour |
| **Best for** | Keyword matching, autocomplete, facets, full-text relevance | Semantic similarity, recommendations, RAG |
| **Index type** | `"type": "search"` | `"type": "vectorSearch"` |
| **Query stage** | `$search` / `$searchMeta` | `$vectorSearch` |
| **Score metadata** | `{ $meta: 'searchScore' }` | `{ $meta: 'vectorSearchScore' }` |
| **Handles typos** | Yes (fuzzy option) | Yes (by nature of embeddings) |
| **Handles synonyms** | Yes (synonym collection) | Yes (by nature of embeddings) |
| **Facets/counts** | Yes (`$searchMeta` + facet) | No (use $match + $count after) |
| **Filter support** | `compound.filter` clauses | `filter` field in `$vectorSearch` |
| **Must be first stage** | Yes | Yes |
| **Sync latency** | 1-5 seconds | 1-5 seconds |
| **Storage overhead** | ~20-50% of collection size | ~6KB per document (1536 dims) |
| **Key parameter** | `fuzzy.maxEdits` | `numCandidates` |

| $search operator | Use case |
|---|---|
| `text` | Full-text search with tokenisation and stemming |
| `autocomplete` | Prefix/partial word matching as user types |
| `phrase` | Exact word sequence matching |
| `compound` | Combine must/should/mustNot/filter clauses |
| `range` | Numeric, date, or string range filtering |
| `equals` | Exact value match (boolean, number, ObjectId) |
| `in` | Match any value in a list |
| `exists` | Field must be present and non-null |
| `near` | Score by proximity to a numeric/date target |
| `regex` | Regular expression pattern match |
| `geoWithin` | Geographic containment search |

**Tip for interviews:** Six things separate strong candidates on this topic: (1) articulating the **fundamental difference between Atlas Search and Vector Search** — Atlas Search is Lucene-based keyword search (BM25 relevance, tokenisation, stemming, exact/fuzzy matching) while Vector Search is semantic similarity search using numerical embeddings (understanding meaning, not words); knowing when each is appropriate and why hybrid search often beats either alone; (2) knowing that **Atlas Search must be the first stage** in an aggregation pipeline — you cannot do `$match` before `$search`; filtering must happen inside the `$search` stage's `compound.filter` clauses (which don't affect scoring, unlike `must`); (3) understanding **`numCandidates` in vector search** — it's not a quality vs. results trade-off but a quality vs. speed trade-off in the HNSW graph traversal; higher values explore more of the graph for better recall but take longer; the rule of thumb is `numCandidates ≥ 10 × limit`; (4) explaining the **async sync lag** — Atlas Search and Vector Search indexes are updated asynchronously after MongoDB writes, with a 1-5 second typical lag; this means freshly inserted documents aren't immediately searchable, which is a common source of test failures and must be accounted for in application design; (5) knowing the **RRF (Reciprocal Rank Fusion) technique** for hybrid search — the challenge of combining BM25 scores (Atlas Search) with cosine similarity scores (Vector Search) is that they're on incomparable scales; RRF solves this by combining rank positions instead of raw scores, giving `1 / (k + rank)` for each system and summing; and (6) understanding the **RAG pattern** — Vector Search serves as the retrieval layer (finding relevant document chunks by semantic similarity), which are then passed as context to an LLM; the quality of RAG depends on chunking strategy, embedding model choice, `numCandidates` tuning, and whether to use hybrid retrieval.
