## Part 1 — Theory & Interview Q&A

### Section 1: Replica Set Fundamentals

**Q1. What is a MongoDB replica set and why do read preferences exist?**
A: A replica set is MongoDB's high-availability unit — a group of `mongod` instances that maintain the same dataset. One member is elected **primary** (accepts all writes); the rest are **secondaries** (replicate the primary's oplog asynchronously). A third member role, **arbiter**, participates in elections but holds no data.

```
Replica Set Architecture:

  ┌─────────────────────────────────────────────────────────────────┐
  │                      Replica Set                                │
  │                                                                 │
  │  ┌──────────────┐       oplog       ┌──────────────┐           │
  │  │   PRIMARY    │ ─────────────────► │  SECONDARY 1 │           │
  │  │              │                   │  (us-east-1a)│           │
  │  │ All writes   │       oplog       └──────────────┘           │
  │  │ go here      │ ─────────────────► ┌──────────────┐           │
  │  │              │                   │  SECONDARY 2 │           │
  │  └──────────────┘                   │  (us-east-1b)│           │
  │         ▲                           └──────────────┘           │
  │         │                                                       │
  │    Heartbeats                         ┌──────────────┐          │
  │    every 2 sec                        │   ARBITER    │          │
  │         │                             │(vote only,   │          │
  │         └─────────────────────────────│ no data)     │          │
  │                                       └──────────────┘          │
  └─────────────────────────────────────────────────────────────────┘

Why reads from secondaries are possible but non-trivial:
  Writes go to primary only (with optional writeConcern for acknowledgment)
  Oplog replication to secondaries is ASYNCHRONOUS
  → A secondary may be slightly behind the primary (replication lag)
  → Reading from a secondary risks seeing stale data

Read preferences solve the question:
  "Given my consistency requirements and performance goals,
   which replica set member should serve this read?"
```

**Q2. What are all five read preference modes and their fundamental guarantees?**
A: MongoDB defines five read preference modes, each making a different trade-off between consistency, availability, and latency:

```javascript
// The five modes — from strongest consistency to most flexible:

// ── primary (default) ──────────────────────────────────────────────────
// ALL reads go to the primary member
// Guarantees: strongest consistency — you always read the most current data
// Availability: if primary is unavailable (election in progress), reads FAIL
// Use when: financial transactions, inventory counts, any data that must be current

db.collection.find({}).readPref('primary')
// → always routes to PRIMARY regardless of latency

// ── primaryPreferred ──────────────────────────────────────────────────
// Reads go to primary IF available
// Falls back to secondary if primary is unavailable
// Guarantees: strong consistency normally; relaxed during primary absence
// Availability: reads continue during primary failover (via secondaries)

db.collection.find({}).readPref('primaryPreferred')
// → PRIMARY if up, else any available SECONDARY

// ── secondary ────────────────────────────────────────────────────────
// ALL reads go to secondaries (primary NEVER used for reads)
// Guarantees: potentially stale data (replication lag)
// Benefits: offloads read traffic from primary; primary handles writes only
// Use when: analytics, reporting, eventual consistency is acceptable

db.collection.find({}).readPref('secondary')
// → round-robins among available SECONDARIEs; NEVER primary

// ── secondaryPreferred ───────────────────────────────────────────────
// Reads go to secondaries IF any are available
// Falls back to primary only when no secondaries are available
// Guarantees: potentially stale data normally; current data during failover
// Benefit: read scaling without strong availability requirement from secondaries

db.collection.find({}).readPref('secondaryPreferred')
// → any available SECONDARY; falls back to PRIMARY only if no secondaries

// ── nearest ──────────────────────────────────────────────────────────
// Reads go to the member with LOWEST network latency
// Can be primary or secondary — latency is the only criterion
// Guarantees: lowest latency reads; potentially stale if nearest = secondary
// Use when: geographically distributed apps; latency more important than freshness

db.collection.find({}).readPref('nearest')
// → member with lowest round-trip time (within latencyThresholdMS window)
```

```
Comparison table:

  Mode                | Reads To         | Stale Risk | Reads If Primary Down | Latency    |
  --------------------|------------------|------------|----------------------|------------|
  primary             | Primary only     | Never      | No (error)           | Primary's  |
  primaryPreferred    | Primary, then 2° | Possible   | Yes (from 2°)        | Primary's  |
  secondary           | Secondary only   | Yes        | Yes                  | Secondary's|
  secondaryPreferred  | 2°, then Primary | Possible   | Yes (from 1°)        | Secondary's|
  nearest             | Lowest latency   | Possible   | Yes                  | Lowest     |
```

### Section 2: How Read Preference Routing Works

**Q3. How does the MongoDB driver determine which server to route a read to?**
A: The driver maintains a **Server Selection** algorithm that runs continuously, monitoring all replica set members via heartbeats every 10 seconds. For each read operation, the driver executes this selection:

```
Driver server selection algorithm:

Step 1: Topology check
  → Is there a replica set? (vs standalone, sharded cluster)
  → Current topology: RSPrimary, RSSecondary, RSOther, Unknown

Step 2: Apply read preference mode filter
  primary:            eligible = [primary only]
  primaryPreferred:   eligible = [primary]; if empty → [all secondaries]
  secondary:          eligible = [all secondaries]
  secondaryPreferred: eligible = [all secondaries]; if empty → [primary]
  nearest:            eligible = [primary + all secondaries]

Step 3: Apply maxStalenessSeconds filter (if set)
  → Remove servers whose estimated staleness > maxStalenessSeconds
  → Staleness estimate = secondary's last write time vs primary's last write time

Step 4: Apply tag set filter (if tag sets configured)
  → Remove servers that don't match the specified tags
  → If no servers match first tag set: try next tag set in the list

Step 5: Apply latency window filter
  → Find the member with the minimum round-trip time (RTT)
  → All servers within (min_RTT + localThresholdMS) are eligible
  → Default localThresholdMS = 15ms
  → e.g., if fastest server is 5ms: eligible = all servers with RTT ≤ 20ms

Step 6: Random selection from eligible set
  → Randomly select from the servers that passed all filters
  → Random selection provides natural load distribution

Step 7: If no eligible servers: raise ServerSelectionTimeoutError
  → After serverSelectionTimeoutMS (default: 30 seconds)
```

```javascript
// Configuring localThresholdMS (latency window):
const client = new MongoClient(uri, {
  localThresholdMS: 35,  // servers within 35ms of the fastest are eligible
  // default: 15ms — only servers within 15ms of the fastest
  // increase: more candidates → better load balance but higher avg latency
  // decrease: fewer candidates → more consistent latency but less load balance
});

// serverSelectionTimeoutMS: how long to wait for a suitable server
const client = new MongoClient(uri, {
  serverSelectionTimeoutMS: 5000,  // fail after 5s if no suitable server
  // default: 30000ms (30 seconds)
});
```

**Q4. At what granularity can you set read preferences and which takes precedence?**
A: Read preferences can be set at five levels, with more specific scopes overriding broader ones:

```javascript
// ── Level 1: Connection string (broadest scope) ────────────────────────
const uri = 'mongodb://host1:27017,host2:27017,host3:27017/mydb' +
            '?replicaSet=myRS' +
            '&readPreference=secondaryPreferred' +
            '&readPreferenceTags=region:us-east' +
            '&maxStalenessSeconds=120';

// ── Level 2: MongoClient options ──────────────────────────────────────
const client = new MongoClient(uri, {
  readPreference: ReadPreference.SECONDARY_PREFERRED,
  // Applies to all operations unless overridden at a lower level
});

// ── Level 3: Database level ───────────────────────────────────────────
const db = client.db('analytics', {
  readPreference: ReadPreference.SECONDARY,
  // All collections in 'analytics' db read from secondaries
});

// ── Level 4: Collection level ─────────────────────────────────────────
const reportingCollection = db.collection('events', {
  readPreference: new ReadPreference(
    ReadPreference.SECONDARY,
    [{ region: 'us-west' }],  // tag set
    { maxStalenessSeconds: 300 }
  ),
});

// ── Level 5: Per-operation (most specific — highest precedence) ────────
const result = await collection.find({ status: 'active' }, {
  readPreference: ReadPreference.PRIMARY,
  // This specific find uses primary even if collection default is secondary
}).toArray();

// Precedence: per-operation > collection > database > client > connection string

// PyMongo example:
from pymongo import MongoClient, ReadPreference

client = MongoClient(uri)
db = client.get_database('mydb', read_preference=ReadPreference.SECONDARY)
coll = db.get_collection('events')  # inherits SECONDARY from db
result = coll.find_one({'_id': doc_id},
                       read_preference=ReadPreference.PRIMARY)  # overrides to PRIMARY
```

### Section 3: `maxStalenessSeconds` and Data Freshness

**Q5. What is `maxStalenessSeconds` and how does MongoDB estimate staleness?**
A: `maxStalenessSeconds` is a guard on secondary reads — it tells the driver to avoid secondaries that are too far behind the primary. If a secondary's estimated lag exceeds `maxStalenessSeconds`, the driver excludes it from the eligible server pool.

```
Staleness estimation formula:

For a secondary S and primary P:
  estimated_staleness(S) = (S.lastWriteDate_primary - S.lastWriteDate_S)
                           + S.heartbeat_frequency

  Where:
    S.lastWriteDate_primary:  timestamp of the most recent write on the PRIMARY
                              (reported by the secondary in its heartbeat)
    S.lastWriteDate_S:        timestamp of the most recent write the SECONDARY has applied
    S.heartbeat_frequency:    how often the secondary sends heartbeats (default: 10s)

If primary is not monitored (e.g., secondary read preference with no primary connection):
  estimated_staleness(S) = max(lastWriteDate_any_secondary) - S.lastWriteDate_S
                           + S.heartbeat_frequency

Minimum valid maxStalenessSeconds: 90 seconds
  The 90-second minimum prevents scenarios where the staleness window is smaller
  than the heartbeat frequency (10s) × some multiplier, which would make
  the estimate unreliable.
```

```javascript
// Setting maxStalenessSeconds:

// Connection string:
const uri = 'mongodb://host1,host2,host3/?readPreference=secondary&maxStalenessSeconds=120';

// Per operation:
const results = await collection.find({ type: 'report' }, {
  readPreference: new ReadPreference(
    ReadPreference.SECONDARY,
    null,                             // no tag sets
    { maxStalenessSeconds: 120 }      // max 2 minutes stale
  )
}).toArray();

// Per client:
const client = new MongoClient(uri, {
  readPreference: new ReadPreference(
    ReadPreference.SECONDARY_PREFERRED,
    [{ purpose: 'analytics' }],
    { maxStalenessSeconds: 300 }      // analytics can be 5 minutes stale
  )
});

// What happens when ALL secondaries exceed maxStalenessSeconds:
// With secondary:           → no eligible servers → ServerSelectionTimeoutError
// With secondaryPreferred:  → falls back to PRIMARY (ignores staleness for primary)
// With primaryPreferred:    → primary used (primary is never "stale")
// With nearest:             → primary considered (if nearest, within latency window)

// Checking current replication lag in the shell:
rs.printReplicationInfo();
// configured oplog size: 2048 MB
// log length start to end: 86400 secs (24 hrs)
// oplog first event time: Mon Jan 15 2024 00:00:00
// oplog last event time:  Tue Jan 16 2024 00:00:00
// now:                    Tue Jan 16 2024 00:00:05

rs.printSecondaryReplicationInfo();
// source: secondary1:27017
// syncedTo: Tue Jan 16 2024 00:00:03
// 2 secs (0 hrs) behind the primary
// source: secondary2:27017
// syncedTo: Tue Jan 16 2024 00:00:00
// 5 secs (0 hrs) behind the primary
```

### Section 4: Tag Sets

**Q6. What are tag sets and how do you use them to route reads to specific replica set members?**
A: Tag sets allow you to annotate replica set members with custom key-value labels (e.g., `region`, `datacenter`, `purpose`) and then route reads to members matching specific tags. This enables geographic routing, workload isolation, and hardware-tier segregation.

```javascript
// ── Step 1: Configure member tags in replica set configuration ─────────
// In the mongo shell:
cfg = rs.conf();

// Tag primary as us-east datacenter:
cfg.members[0].tags = {
  region:     'us-east',
  datacenter: 'us-east-1a',
  purpose:    'primary'
};

// Tag secondary 1 (same datacenter as primary):
cfg.members[1].tags = {
  region:     'us-east',
  datacenter: 'us-east-1b',
  purpose:    'reporting'
};

// Tag secondary 2 (different region — DR site):
cfg.members[2].tags = {
  region:     'eu-west',
  datacenter: 'eu-west-1a',
  purpose:    'reporting'
};

// Tag secondary 3 (analytics hardware):
cfg.members[3].tags = {
  region:     'us-east',
  datacenter: 'us-east-1c',
  purpose:    'analytics',
  hardware:   'high-mem'
};

rs.reconfig(cfg);

// ── Step 2: Route reads using tag sets ────────────────────────────────
// Read from us-east region only:
const usEastRead = new ReadPreference(
  ReadPreference.SECONDARY,
  [{ region: 'us-east' }]  // tag set: must match region=us-east
);

// Read from analytics hardware:
const analyticsRead = new ReadPreference(
  ReadPreference.SECONDARY,
  [{ purpose: 'analytics', hardware: 'high-mem' }]
);

// Read from reporting nodes with regional fallback (tag set list):
const reportingRead = new ReadPreference(
  ReadPreference.SECONDARY,
  [
    { purpose: 'reporting', region: 'us-east' },  // prefer us-east reporting
    { purpose: 'reporting' },                       // fallback: any reporting node
    {},                                             // final fallback: any secondary
  ]
  // Tag sets tried in order: first matching set wins
  // If no servers match set 1: try set 2
  // If no servers match set 2: try set 3 (empty = any server)
);

// Usage in driver:
const result = await db.collection('reports').find({
  date: { $gte: startDate }
}, {
  readPreference: analyticsRead
}).toArray();

// ── Tag set fallback chains — critical pattern ─────────────────────────
// A tag set list (array of tag sets) provides fallback tiers:
const geoAwareRead = new ReadPreference(
  ReadPreference.NEAREST,
  [
    { region: 'us-east', datacenter: 'us-east-1a' }, // tier 1: same datacenter
    { region: 'us-east' },                            // tier 2: same region
    {},                                               // tier 3: anywhere (global fallback)
  ]
);
// If us-east-1a is down: automatically falls back to any us-east server
// If all us-east is down: falls back to global (nearest available)

// ── Verifying tag configuration ────────────────────────────────────────
rs.conf().members.forEach(m =>
  console.log(m.host, m.priority, m.tags)
);
```

### Section 5: `nearest` Deep Dive

**Q7. How does `nearest` read preference work precisely — what is the latency window and when does it consider primary?**
A: `nearest` selects the server with the **lowest measured round-trip time** (RTT), regardless of whether it is primary or secondary. It uses a sliding window of recent heartbeat measurements to estimate RTT, then applies `localThresholdMS` to create a pool of eligible servers.

```javascript
// nearest algorithm in detail:

// 1. Driver tracks RTT for each server via periodic heartbeats (every 10 seconds)
//    RTT is an exponential moving average:
//    new_RTT = 0.2 * latest_sample + 0.8 * previous_avg
//    (smooths out transient spikes)

// 2. Find the minimum RTT among all eligible servers (primary + all secondaries)
//    e.g.: primary=25ms, secondary1=5ms, secondary2=8ms, secondary3=50ms
//    min_RTT = 5ms (secondary1)

// 3. Eligible pool = all servers with RTT ≤ min_RTT + localThresholdMS
//    default localThresholdMS = 15ms
//    eligible: RTT ≤ 5 + 15 = 20ms
//    → secondary1 (5ms) ✓
//    → secondary2 (8ms) ✓
//    → primary (25ms) ✗  (25 > 20)
//    → secondary3 (50ms) ✗

// 4. Randomly select from eligible pool → secondary1 or secondary2

// Result: nearest doesn't always pick THE single fastest — it picks from a
// window of fast servers. This provides load distribution while still being
// latency-aware.

// Configuring localThresholdMS:
const client = new MongoClient(uri, {
  localThresholdMS: 35,  // wider window → more servers eligible → better distribution
                         // narrower (e.g., 0) → only the single fastest server
});

// nearest + tag sets: tags filter first, THEN latency window within tagged set:
const localDatacenterRead = new ReadPreference(
  ReadPreference.NEAREST,
  [{ datacenter: 'us-east-1a' }]  // only consider us-east-1a servers
  // Then: apply latency window within that datacenter
);

// When nearest routes to primary:
// If primary is in the same datacenter as the app → primary has lowest RTT
// → nearest may consistently pick the primary!
// This is correct behavior but means you can get stale reads from secondaries
// AND primary reads from nearest depending on network topology

// nearest is ideal for:
// ✓ Multi-region deployments where you want local reads
// ✓ Apps that can tolerate stale reads but need low latency
// ✓ Analytics where any replica's data is fine

// nearest is NOT ideal for:
// ✗ Read-your-own-writes requirements (may read from secondary after writing to primary)
// ✗ Monotonic reads (may switch between servers between operations)
// ✗ Any operation requiring the absolute most current data
```

### Section 6: Consistency Models and Causally Consistent Sessions

**Q8. What consistency properties does each read preference mode guarantee or break?**
A: Reading from non-primary members breaks several consistency guarantees that applications often assume implicitly:

```
Consistency properties by read preference:

  Property                  | primary | primaryPreferred | secondary | secondaryPreferred | nearest |
  --------------------------|---------|------------------|-----------|-------------------|---------|
  Read your own writes      |  ✓ Yes  |  ✓ (if primary)  |  ✗ No    |  ✗ (if secondary) | ✗ Maybe |
  Monotonic reads           |  ✓ Yes  |  ✓ (if primary)  |  ✗ No    |  ✗ (if secondary) | ✗ No    |
  Consistent prefix         |  ✓ Yes  |  ✓ (if primary)  |  ✓ Yes   |  ✓ Yes            | ✓ Yes   |
  No stale reads            |  ✓ Yes  |  ✓ (if primary)  |  ✗ No    |  ✗ (if secondary) | ✗ Maybe |
  Reads during failover     |  ✗ No   |  ✓ Yes           |  ✓ Yes   |  ✓ Yes            | ✓ Yes   |

Monotonic reads: once you read a value at time T, you never see an older value
  Problem with secondary: read from secondary1 (5s behind), then secondary2 (10s behind)
  → second read may return data OLDER than the first read (went backward in time!)

Read your own writes: after writing X, your next read returns X (or newer)
  Problem with secondary: write to primary, read from secondary that hasn't replicated yet
  → your own write is invisible to your next read

Consistent prefix: if event B was caused by event A, you see A before B
  Guaranteed by oplog ordering: secondaries apply operations in oplog order
  → you always see a consistent causal prefix (never see B without having seen A)
```

**Q9. What are causally consistent sessions and how do they allow secondary reads with stronger guarantees?**
A: Causally consistent sessions (MongoDB 3.6+) allow applications to read from secondaries without violating read-your-own-writes or monotonic reads. The client tracks **operation time** and **cluster time** and sends them with each operation. Secondaries use these timestamps to wait until they have replicated up to the required point before serving the read.

```javascript
// Without causally consistent sessions — stale read problem:
const session = client.startSession();

await collection.insertOne(
  { userId: 42, balance: 1000 },
  { session }
);
// Write acknowledged on primary at clusterTime T1

// Read with secondary read preference — NO causal consistency:
const result = await collection.findOne(
  { userId: 42 },
  {
    session,
    readPreference: ReadPreference.SECONDARY,
    // No causal consistency → secondary may not have T1 yet → returns null or old value!
  }
);

// ── With causally consistent session ────────────────────────────────────
const causalSession = client.startSession({
  causalConsistency: true   // enable causal consistency for this session
});

await collection.insertOne(
  { userId: 42, balance: 1000 },
  { session: causalSession }
);
// Session records: operationTime = T1 (the time of this write on primary)

// Read from secondary — STILL consistent because of causal session:
const result = await collection.findOne(
  { userId: 42 },
  {
    session: causalSession,
    readPreference: ReadPreference.SECONDARY,
    // Driver sends: afterClusterTime = T1 with the read
    // Secondary: "I must not serve this read until I've replicated up to T1"
    // Secondary waits for its own oplog to reach T1 → returns the document ✓
  }
);
// result = { userId: 42, balance: 1000 }  ← your own write is visible!

// ── How the driver tracks causal state internally ───────────────────────
// Session state:
// {
//   operationTime:  Timestamp(seconds, ordinal),  // last operation's timestamp
//   clusterTime:    { clusterTime: Timestamp, signature: {...} }  // global cluster time
// }
// Every operation updates these timestamps from the server response
// Next operation sends: afterClusterTime = session.operationTime
// Server satisfies "afterClusterTime" by waiting for its oplog to advance past it

// Trade-off of causal consistency on secondaries:
// → May add latency: secondary waits to catch up before serving the read
// → If secondary is severely lagging: your read waits a long time
// → Use maxStalenessSeconds to bound this wait
// → Better to use maxStalenessSeconds + causal consistency together

const causalSession = client.startSession({ causalConsistency: true });
const readOptions = {
  session: causalSession,
  readPreference: new ReadPreference(
    ReadPreference.SECONDARY,
    null,
    { maxStalenessSeconds: 60 }  // if secondary > 60s behind → fall back to primary
  )
};

// ── Causally consistent reads across multiple services ──────────────────
// Pass the operationTime across service boundaries:
// Service A writes, sends operationTime to Service B
// Service B uses it as the afterClusterTime for its read

// Service A (after write):
const writeResult = await collection.insertOne(doc, { session });
const checkpointTime = session.operationTime;  // {t: ..., i: ...} (Timestamp)

// Pass checkpointTime to Service B (via HTTP header, message queue, etc.)

// Service B:
const sessionB = client.startSession({ causalConsistency: true });
sessionB.advanceOperationTime(checkpointTime);  // tell session about A's write
const result = await collection.findOne(filter, {
  session: sessionB,
  readPreference: ReadPreference.SECONDARY
  // Secondary will wait until it has replicated A's write
});
```

### Section 7: Read Preferences in Sharded Clusters

**Q10. How do read preferences behave differently in a sharded cluster vs a replica set?**
A: In a sharded cluster, `mongos` (the query router) manages read preference routing. Each shard is itself a replica set, and read preferences control which member of each shard's replica set serves the read. The `mongos` layer adds another consideration: it always reads from the primary of each shard unless you explicitly specify otherwise.

```javascript
// Sharded cluster topology:
//   Client → mongos → Shard 1 (RS: primary + 2 secondaries)
//                   → Shard 2 (RS: primary + 2 secondaries)
//                   → Shard 3 (RS: primary + 2 secondaries)

// mongos passes read preference to shards:
// With readPreference: secondary
//   → mongos routes to secondary members of EACH shard it queries
//   → if the query touches 3 shards: reads from secondaries of all 3

// Key difference from direct replica set reads:
// ✗ nearest in sharded cluster: "nearest" is per-shard, not across shards
//   → "nearest" in shard 1 = lowest latency within shard 1's replica set
//   → doesn't consider latency across different shards' members

// primary in sharded cluster: default; reads from each shard's primary
// secondary in sharded cluster: reads from a secondary of EACH shard

// Scatter-gather queries and read preferences:
// If a query can't use a shard key → mongos fans out to ALL shards
// readPreference: secondary → reads from secondaries of ALL shards simultaneously
// → This is the primary use case for secondary reads in sharded clusters:
//    fan-out analytics queries distributed across all shard secondaries

// ── Targeted vs broadcast operations ──────────────────────────────────
// Targeted (uses shard key): goes to ONE shard → read preference applies to that shard
// Broadcast (no shard key): goes to ALL shards → read preference applies to each shard

// Best practice for sharded clusters:
// OLTP queries (targeted): primary (default) for consistency
// Analytics queries (broadcast): secondary to avoid loading shard primaries
// Mixed workload: use $readPreference in aggregation pipelines

const analyticsResult = await db.collection('events').aggregate(
  [
    { $match: { date: { $gte: startDate, $lt: endDate } } },
    { $group: { _id: '$category', total: { $sum: '$amount' } } }
  ],
  { readPreference: ReadPreference.SECONDARY }
);
// Each shard returns its secondary's aggregated portion
// mongos merges results from all shard secondaries
```

### Section 8: Scenario / Interview Questions

**Q11. "A team is experiencing high read latency on their primary. They're considering switching to `secondary` read preference for all reads. What risks must they address first?"**
A:

```javascript
// ── Risk 1: Stale reads breaking application logic ──────────────────────
// Scenario: e-commerce checkout
async function reserveInventory(productId, quantity) {
  // Write: decrement stock
  await inventory.updateOne(
    { _id: productId, stock: { $gte: quantity } },
    { $inc: { stock: -quantity } },
    { writeConcern: { w: 'majority' } }
  );

  // Read: verify reservation (currently will switch to secondary)
  const item = await inventory.findOne(
    { _id: productId },
    { readPreference: ReadPreference.SECONDARY }  // NEW
  );
  // DANGER: secondary may not have the write yet
  // item.stock may still show pre-reservation value
  // Appears to have more stock than reality → overselling!
}

// Risk 2: Monotonic read violations
// Session reads report for Jan, then reads for Feb — might see Feb then Jan's data
// depending on which secondary serves each read

// Risk 3: Not all operations support non-primary reads
// - Writes: always go to primary (read preference doesn't affect writes)
// - Transactions: reads within a transaction go to primary by default
//   (distributed transactions across replica sets require primary reads)
// - Count operations on secondary can lag for collection stats

// ── Solutions before switching ──────────────────────────────────────────
// 1. Audit every read: categorize as "must be current" vs "eventually consistent OK"
const safeForSecondary = [
  'analytics queries',
  'historical reports',
  'search/discovery queries',
  'user activity feeds (not real-time)',
];
const mustUsePrimary = [
  'inventory checks at checkout',
  'balance reads before financial transactions',
  'authentication token validation',
  'admin operations',
];

// 2. Use causally consistent sessions for "soft" current reads:
// Operations that need to see their own writes but can tolerate other writes being stale
const session = client.startSession({ causalConsistency: true });
```

## Problem 4 — Monitoring Replication Lag and Automating `maxStalenessSeconds` Alerts

### Problem
Set up replication lag monitoring to alert when secondaries fall behind, and implement automatic degradation that switches to primary reads when lag exceeds thresholds.

```javascript
// ── Replication lag monitoring ─────────────────────────────────────────

async function getReplicationLag(client) {
  const admin = client.db('admin');

  // replSetGetStatus: detailed per-member status
  const rsStatus = await admin.command({ replSetGetStatus: 1 });

  const primary = rsStatus.members.find(m => m.state === 1);  // state 1 = PRIMARY
  if (!primary) return { error: 'No primary found' };

  const primaryLastWrite = primary.optimeDate;  // Date of primary's last oplog entry

  return rsStatus.members
    .filter(m => m.state === 2)  // state 2 = SECONDARY
    .map(member => ({
      host:           member.name,
      stateStr:       member.stateStr,
      lagSeconds:     Math.round((primaryLastWrite - member.optimeDate) / 1000),
      lastHeartbeat:  member.lastHeartbeatMessage,
      health:         member.health,   // 1 = healthy
      pingMs:         member.pingMs,   // round-trip time from primary to this member
    }));
}

// Example output:
// [
//   { host: 'secondary1:27017', lagSeconds: 2,  health: 1, pingMs: 3  },
//   { host: 'secondary2:27017', lagSeconds: 85, health: 1, pingMs: 95 }, // ← HIGH LAG!
// ]

// ── Alert thresholds ───────────────────────────────────────────────────
const LAG_THRESHOLDS = {
  warning:  30,   // warn at 30s lag
  critical: 120,  // critical at 120s lag (2 minutes)
  maxStaleness: 90, // match our maxStalenessSeconds setting
};

async function checkAndAlertReplicationLag(client, alerter) {
  const lagStats = await getReplicationLag(client);

  for (const secondary of lagStats) {
    if (secondary.lagSeconds >= LAG_THRESHOLDS.critical) {
      await alerter.sendAlert({
        severity:  'CRITICAL',
        title:     `Replication lag critical: ${secondary.host}`,
        message:   `Secondary ${secondary.host} is ${secondary.lagSeconds}s behind primary`,
        action:    'Secondary reads may fail (exceeds maxStalenessSeconds). Check disk I/O and network.',
      });
    } else if (secondary.lagSeconds >= LAG_THRESHOLDS.warning) {
      await alerter.sendAlert({
        severity: 'WARNING',
        title:    `Replication lag elevated: ${secondary.host}`,
        message:  `Secondary ${secondary.host} is ${secondary.lagSeconds}s behind primary`,
      });
    }
  }
}

// Run monitoring every 30 seconds:
setInterval(() => checkAndAlertReplicationLag(client, alerter), 30_000);

// ── Adaptive read preference based on lag ─────────────────────────────
// Automatically use primary when secondaries are too stale

class AdaptiveReadRouter {
  constructor(client) {
    this.client       = client;
    this.currentLag   = 0;
    this.forceToMode  = null;  // override when all secondaries are too laggy
    this.lastChecked  = 0;
    this.checkIntervalMs = 10_000;  // re-check lag every 10 seconds
  }

  async updateLagMetrics() {
    const now = Date.now();
    if (now - this.lastChecked < this.checkIntervalMs) return;
    this.lastChecked = now;

    try {
      const lagStats = await getReplicationLag(this.client);
      const minLag   = Math.min(...lagStats.map(s => s.lagSeconds));
      const allStale = lagStats.every(s => s.lagSeconds > LAG_THRESHOLDS.maxStaleness);

      this.currentLag  = minLag;
      this.forceToMode = allStale ? 'primary' : null;
    } catch (err) {
      console.error('Failed to check replication lag:', err);
      // If we can't check: be conservative, use primary
      this.forceToMode = 'primary';
    }
  }

  getAnalyticsReadPreference() {
    // Degraded mode: all secondaries too stale → read from primary
    if (this.forceToMode === 'primary') {
      console.warn('AdaptiveReadRouter: degrading to primary (secondaries too stale)');
      return ReadPreference.PRIMARY;
    }

    // Normal mode: read from secondaries
    return new ReadPreference(
      ReadPreference.SECONDARY_PREFERRED,
      null,
      { maxStalenessSeconds: LAG_THRESHOLDS.maxStaleness }
    );
  }

  async read(collection, filter, options = {}) {
    await this.updateLagMetrics();
    const readPreference = this.getAnalyticsReadPreference();
    return collection.find(filter, { ...options, readPreference }).toArray();
  }
}

// ── Exposing lag metrics via HTTP ──────────────────────────────────────

               : 'healthy';

  res.status(status === 'degraded' ? 503 : 200).json({
    status,
    replicationLag: {
      maxLagSeconds: maxLag,
      members:       lagStats,
    },

  });
});
```

```javascript
      await session.abortTransaction();
      throw new Error('Insufficient funds or account not found');

      { _id: toAccountId },

    throw err;
```

## Quick Reference — Read Preferences Cheat Sheet

```
FIVE MODES:
  primary             → Primary only. Strongest consistency. Fails if primary down.
  primaryPreferred    → Primary if available; secondary if primary down. Fallback availability.
  secondary           → Secondary only. Never primary. Stale reads possible. Read scaling.
  secondaryPreferred  → Secondary if available; primary if all secondaries down. Best availability.
  nearest             → Lowest RTT member (primary or secondary). Best latency. Stale possible.

WHEN TO USE EACH:
  primary:            Financial transactions, inventory at checkout, auth token validation,
                      any "must see latest" operation. Default for good reason.
  primaryPreferred:   Read-heavy OLTP where you want better availability during elections
                      but normally need fresh data. Safe upgrade from primary.
  secondary:          Analytics, reporting, batch jobs, historical queries, search indexing.
                      Deliberately offload primary. Must accept stale data.
  secondaryPreferred: CDN-style reads, user browsing/discovery, social feeds. Maximize
                      secondary usage; primary is a safety net.
  nearest:            Multi-region apps: serve users from local region.
                      Minimize read latency is the primary goal.

TAG SETS:
  Annotate members: cfg.members[N].tags = { region: 'us-east', purpose: 'analytics' }
  Route by tag: new ReadPreference(SECONDARY, [{ purpose: 'analytics' }])
  Fallback chain: [{ region: 'us-east' }, { region: 'us-west' }, {}]
    → empty {} = any server (ultimate fallback)
  Tags try in order: first matching set wins; if no match → next set → ...

maxStalenessSeconds:
  Minimum: 90 seconds (enforced by driver)
  If secondary lag > maxStalenessSeconds → excluded from eligible pool
  If ALL secondaries excluded:
    secondary:          → ServerSelectionTimeoutError
    secondaryPreferred: → falls back to primary
    nearest:            → primary becomes eligible

LATENCY WINDOW (nearest and all modes for selection):
  localThresholdMS (default: 15ms)
  Eligible pool: servers with RTT ≤ min_RTT + localThresholdMS
  Wider window → better load distribution; narrower → more consistent latency
  Random selection from eligible pool (natural load balancing)

CAUSAL CONSISTENCY:
  session = client.startSession({ causalConsistency: true })
  Session tracks operationTime (last write timestamp)
  Secondary reads include afterClusterTime = operationTime
  Secondary WAITS until it has replicated up to that time → reads own writes on secondary
  Use for: post-write reads on secondary without stale data risk
  Cross-service: export session.operationTime; import with session.advanceOperationTime()

TRANSACTIONS:
  Reads within transactions → always PRIMARY (driver enforces)
  readPreference on transaction reads is IGNORED
  readConcern: 'snapshot' in transactions → consistent view of committed data

AGGREGATIONS:
  Pure reads ($match, $group, $sort, $lookup) → safe for secondary
  $out, $merge (write stages) → automatically routed to primary regardless of readPreference
  $lookup → additional reads from other collections use same read preference

SHARDED CLUSTERS:
  mongos passes readPreference to each shard's replica set members
  nearest = nearest within each shard (not across shards)
  Broadcast queries (no shard key): hit ALL shards → secondary reads scale well here
  Targeted queries (shard key): hit ONE shard → secondary reads reduce load on that shard

REPLICATION LAG MONITORING:
  Shell: rs.printSecondaryReplicationInfo() — shows lag per secondary
  Driver: admin.command({ replSetGetStatus: 1 }) → members[].optimeDate
  Lag = primary.optimeDate - secondary.optimeDate
  Alert thresholds: warn at 30s, critical at 90s (matches minimum maxStalenessSeconds)
  High lag causes:
    → Secondary disk I/O overloaded (can't apply oplog fast enough)
    → Network congestion between primary and secondary
    → Long-running operations blocking oplog application

COMMON MISTAKES:
  readPreference: secondary after write without causal session → stale read (read-your-own-writes broken)
  Not setting maxStalenessSeconds with secondary reads → accepts arbitrarily stale data
  Using secondary in a transaction → ignored; reads still go to primary
  Tag set with no matching server → ServerSelectionTimeoutError (no fallback without empty {} set)
  nearest in multi-region without tags → may read from any region (not necessarily local)
  primaryPreferred during election → falls back to secondary briefly (can surprise with stale reads)
  Not monitoring replication lag → maxStalenessSeconds fires unexpectedly under load
```

**Final Tip:** At the 5 YOE level, read preference questions test whether you understand **the replication lag consequence of every non-primary read** and can articulate the exact scenarios where stale reads cause application bugs. The highest-signal answer on `secondary` reads: "When you read from a secondary, you're reading from an asynchronously replicated member — its oplog application is slightly behind the primary. The three consistency properties that break are read-your-own-writes (you wrote to primary but your next read hits a secondary that hasn't replicated it yet), monotonic reads (you read from secondary1 which is 2s behind, then secondary2 which is 5s behind — you went backward in time), and freshness. The solution for the first two is causally consistent sessions, which attach an `afterClusterTime` to secondary reads that forces the secondary to wait until it has replicated your write before serving the read." For `nearest`: "Nearest doesn't always mean secondary — if your app is deployed in the same datacenter as the primary and the primary has lower RTT than the secondaries, `nearest` will consistently route to the primary. This is correct behavior but surprises teams who think `nearest` means secondary. The way to guarantee local-datacenter reads is `nearest` + a tag set filter for the local region, so only in-region servers are candidates regardless of who's primary." For transactions: "Within a multi-document transaction, all reads go to the primary regardless of what read preference you specify — the driver enforces this. The reason is that transactions use a consistent snapshot read concern, and the only server that can guarantee a fully consistent snapshot of the entire transaction's data is the primary where the write lock is held."
