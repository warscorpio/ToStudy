# MongoDB Change Streams — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are change streams, what problem do they solve, and what infrastructure do they require?**
A: Change streams provide a real-time event stream of data changes in MongoDB — inserts, updates, deletes, and replacements — that applications can subscribe to without polling. They solve the fundamental problem of building event-driven systems on top of a database without resorting to application-level workarounds like polling queries or dual-write patterns:

```
The problem change streams solve:

  WITHOUT change streams — polling anti-pattern:
    Application polls every 5 seconds:
    SELECT * FROM orders WHERE updatedAt > lastChecked
    ├── 5-second minimum latency on all events
    ├── Missed events if updatedAt is not reliably set
    ├── Database load from constant queries (even when nothing changed)
    ├── Race conditions: changes between polls can be missed
    └── Cannot detect deletes (deleted rows have no updatedAt)

  WITHOUT change streams — dual-write anti-pattern:
    Application writes to DB AND publishes to Kafka simultaneously:
    await db.orders.insertOne(order);    // Step 1
    await kafka.publish('order', order); // Step 2 — may fail!
    ├── If Step 1 succeeds but Step 2 fails: event is lost
    ├── If application crashes between steps: event is lost
    ├── Requires distributed transaction or outbox pattern
    └── Application owns event publishing (cross-cutting concern)

  WITH change streams — database-driven events:
    ChangeStream subscribes to MongoDB oplog
    ├── Every committed write generates exactly one change event
    ├── Events delivered in commit order (total ordering)
    ├── Sub-millisecond latency from commit to event
    ├── Deletes produce events (with the deleted document's _id)
    ├── Application does NOT need to publish events — DB does it
    └── Resumable: survives connection failures, process restarts
```

```
Infrastructure requirements — change streams are NOT available everywhere:

  Required: Replica Set OR Sharded Cluster
  ├── Replica set: minimum 1-node replica set (even a standalone with rs.initiate())
  │   Change streams read from the oplog (operation log)
  │   Standalone MongoDB: no oplog → no change streams
  └── Sharded cluster: supported on individual shards and the whole cluster
      mongos router coordinates change streams across all shards

  Why replica set is required:
    Change streams are built on the oplog — the replication log that
    replica set members use to sync. The oplog is only created when
    running as a replica set. A standalone MongoDB has no oplog.

  Version requirements:
    MongoDB 3.6+: change streams on collections
    MongoDB 4.0+: change streams on databases (all collections in a db)
    MongoDB 4.0+: change streams on deployments (all databases)
    MongoDB 6.0+: change streams on pre-images (full document before change)

  Development setup (single-node replica set):
    mongod --replSet rs0 --bind_ip localhost
    mongosh: rs.initiate()
    Now change streams work — no need for a real 3-node replica set in dev
```

```javascript
// Minimal change stream example:
const { MongoClient } = require('mongodb');

const client = await MongoClient.connect('mongodb://localhost:27017/?replicaSet=rs0');
const db = client.db('myapp');
const orders = db.collection('orders');

// Open a change stream on the orders collection:

// Listen for change events:

//   "ns": { "db": "myapp", "coll": "orders" },
//   "documentKey": { "_id": ObjectId("...") },
//   "fullDocument": {
//     "_id": ObjectId("..."),
//     "status": "PENDING",
//     "amount": 99.99,
//     "userId": "u-42"
//   }
// }
```

**Q2. How do change streams work internally — what is the oplog and how does the change stream read from it?**
A: Change streams are an abstraction layer on top of MongoDB's oplog (operation log), which is a capped collection that records every write operation in order. Change streams transform the raw oplog entries (which use internal format) into structured, user-friendly change events, with filtering and aggregation pipeline support:

```
Oplog to change stream transformation:

  MongoDB Write Path:
    Client write → WiredTiger storage engine → Oplog (rs.oplog.rs)
                                                    ↓
                                            Change Stream reads oplog
                                                    ↓
                                            Transforms to change event
                                                    ↓
                                            Applies $match filter (if any)
                                                    ↓
                                            Delivers to application

  Oplog entry (raw, internal format):
  {
    "ts": Timestamp(1710000000, 1),  // Operation timestamp
    "op": "i",                        // i=insert, u=update, d=delete, c=command
    "ns": "myapp.orders",             // Namespace
    "o": { "_id": ObjectId("..."),    // The document (for insert)
           "status": "PENDING" }
  }

  Change event (what application sees):
  {
    "_id": { "_data": "826539..." },  // Resume token (opaque string, NOT the doc _id)
    "operationType": "insert",        // Human-readable operation type
    "clusterTime": Timestamp(...),    // Wall clock time
    "ns": { "db": "myapp", "coll": "orders" },
    "documentKey": { "_id": ObjectId("...") },
    "fullDocument": { ... }           // Full document (for insert/replace)
  }

  The change stream infrastructure:
  ├── One internal cursor open on the oplog per watch() call
  ├── Change events cached briefly if consumer is slow
  ├── Resume token in each event = position in oplog
  │   (allows resuming from exactly this point after failure)
  └── Oplog has a size limit (default: 5% of disk or 990MB min)
      Events expire when oplog rotates — must process within the oplog window
```

```javascript
// Watching at different scopes:

// Collection-level (most common — specific collection):
const collectionStream = db.collection('orders').watch();

// Database-level (all collections in a database):
const databaseStream = db.watch();
// Events include which collection changed: event.ns.coll

// Deployment-level (all databases and collections):
const deploymentStream = client.watch();
// Events include which db/collection: event.ns.db, event.ns.coll

// All three support the same pipeline and options
// Collection scope: most efficient (oplog filter reduces noise)
// Deployment scope: highest overhead (every change in entire cluster)
```

```javascript
// Change event structure for each operation type:

// INSERT:
{
    operationType: "insert",
    documentKey: { _id: ObjectId("...") },
    fullDocument: { _id: ObjectId("..."), status: "PENDING", amount: 99.99 }
    // fullDocument is ALWAYS included for inserts
}

// UPDATE (only changed fields by default):
{
    operationType: "update",
    documentKey: { _id: ObjectId("...") },
    updateDescription: {
        updatedFields: { "status": "COMPLETED", "processedAt": ISODate("...") },
        removedFields: ["tempField"],
        truncatedArrays: []   // Arrays that were truncated
    }
    // fullDocument: NOT included by default for updates!
    // Must request fullDocument option to get the full post-update document
}

// REPLACE (replaceOne — entire document replaced):
{
    operationType: "replace",
    documentKey: { _id: ObjectId("...") },
    fullDocument: { _id: ObjectId("..."), /* new complete document */ }
    // fullDocument included: replace sends the full new document
}

// DELETE:
{
    operationType: "delete",
    documentKey: { _id: ObjectId("...") }
    // fullDocument: NOT available — document is already gone
    // Only the _id of the deleted document is available
    // Unless fullDocumentBeforeChange is enabled (pre-image, MongoDB 6.0+)
}
```

## Section 2: Filtering and Pipeline

**Q3. How do you filter change stream events using an aggregation pipeline — what operations are supported?**
A: Change streams accept an optional aggregation pipeline that filters and transforms the event stream before events reach the application. This filtering happens server-side (in the MongoDB process), reducing network traffic and application processing. Only a subset of aggregation stages are supported within a change stream pipeline:

```javascript
// Change stream pipeline syntax:
const pipeline = [
    { $match: { /* filter on change event fields */ } },
    { $project: { /* reshape change events */ } },
    { $addFields: { /* compute new fields */ } }
    // Supported: $match, $project, $addFields, $replaceRoot, $replaceWith
    // NOT supported: $group, $lookup, $bucket, $facet, $geoNear, $out
];

const changeStream = db.collection('orders').watch(pipeline, options);
```

```javascript
// Common filtering patterns:

// 1. Filter by operation type:
const insertOnlyStream = orders.watch([
    { $match: { operationType: "insert" } }
]);
// Receives only new documents — ignores updates and deletes

// 2. Filter by multiple operation types:
const writesStream = orders.watch([
    {
        $match: {
            operationType: { $in: ["insert", "update", "replace"] }
        }
    }
]);

// 3. Filter by specific field changes (updates to specific fields):
const statusChangeStream = orders.watch([
    {
        $match: {
            operationType: "update",
            "updateDescription.updatedFields.status": { $exists: true }
        }
    }
]);
// Only events where the 'status' field was updated

// 4. Filter by field value in inserted/replaced documents:
const highValueStream = orders.watch([
    {
        $match: {
            $or: [
                {
                    operationType: "insert",
                    "fullDocument.amount": { $gte: 1000 }
                },
                {
                    operationType: "replace",
                    "fullDocument.amount": { $gte: 1000 }
                }
            ]
        }
    }
]);
// Only high-value orders — ignores updates (fullDocument not available for updates by default)

// 5. Filter by namespace (useful for database-level streams):
const specificCollectionsStream = db.watch([
    {
        $match: {
            "ns.coll": { $in: ["orders", "payments", "shipments"] }
        }
    }
]);
// Database-level stream: only events from specific collections

// 6. Filter by documentKey (specific document):
const specificDocStream = orders.watch([
    {
        $match: {
            "documentKey._id": ObjectId("specific-id-here")
        }
    }
]);
// Watch a single document — useful for real-time doc collaboration
```

```javascript
// Reshaping change events with $project:
const reshapedStream = orders.watch([
    { $match: { operationType: { $in: ["insert", "update"] } } },
    {
        $project: {
            _id: 0,
            // Flatten the nested structure for easier consumption:
            eventType:  "$operationType",
            orderId:    "$documentKey._id",
            collection: "$ns.coll",
            timestamp:  "$clusterTime",

            // Only include changed fields for updates:
            changedFields: "$updateDescription.updatedFields",

            // Include full document for inserts:
            newOrder: {
                $cond: {
                    if:   { $eq: ["$operationType", "insert"] },
                    then: "$fullDocument",
                    else: "$$REMOVE"  // Omit field entirely
                }
            }
        }
    }
]);

// Output for insert:
// { eventType: "insert", orderId: ObjectId(...), collection: "orders",
//   newOrder: { status: "PENDING", amount: 99.99, ... } }

// Output for update:
// { eventType: "update", orderId: ObjectId(...), collection: "orders",
//   changedFields: { status: "COMPLETED" } }
```

## Section 3: Resume Tokens and Fault Tolerance

**Q4. What is a resume token and how do you use it to build a fault-tolerant change stream consumer?**
A: Every change event contains a `_id` field called the resume token — an opaque value that encodes the event's position in the oplog. By saving the resume token after processing each event, a consumer can reconnect and continue from exactly where it left off, even after a crash or network failure. This is the foundation of exactly-once processing guarantees:

```javascript
// Resume token structure:
// { "_id": { "_data": "826539F8B1000000012B0229296E04" } }
// The _data field is an opaque hex string encoding the oplog position
// Do NOT parse or construct resume tokens — treat as opaque

// Resume token persistence — the key to fault tolerance:
const { MongoClient } = require('mongodb');
const redis = require('ioredis');

async function startFaultTolerantConsumer() {
    const client = await MongoClient.connect(connectionString);
    const db = client.db('myapp');
    const cache = new redis();

    // Load resume token from persistent storage:
    const savedToken = await cache.get('change-stream:orders:resume-token');

    const watchOptions = {
        // Resume from last processed position (null = start from now):
        resumeAfter:       savedToken ? JSON.parse(savedToken) : undefined,
        // Alternative: startAfter — same as resumeAfter for most cases
        // Alternative: startAtOperationTime — resume from a timestamp
    };

    const changeStream = db.collection('orders').watch([], watchOptions);

    changeStream.on('change', async (event) => {
        try {
            // 1. Process the event:
            await processOrderChange(event);

            // 2. Save resume token AFTER successful processing:
            // This is the "at-least-once" checkpoint
            await cache.set(
                'change-stream:orders:resume-token',
                JSON.stringify(event._id)
            );
            // If we crash before saving: we'll reprocess this event on restart
            // (at-least-once delivery — event may be processed more than once)

        } catch (err) {
            console.error('Failed to process change event:', err);
            // Do NOT save the resume token — will retry this event on restart
            // Or: send to dead-letter queue and save token anyway (skip-and-continue)
        }
    });

    // Handle change stream errors:
    changeStream.on('error', async (err) => {
        console.error('Change stream error:', err);
        // The change stream will attempt to reconnect automatically
        // For permanent errors (oplog gap): need to re-establish from scratch
    });

    return changeStream;
}
```

```javascript
// Three resume options and when to use each:

// Option 1: resumeAfter — resume from a specific event token
// Use: normal fault tolerance (crash recovery, reconnection)
const stream = collection.watch([], {
    resumeAfter: lastProcessedToken  // Resumes AFTER this event (exclusive)
});
// The event with this token has already been processed — don't process again
// Next event delivered: the one immediately following this token

// Option 2: startAfter — same semantics as resumeAfter but more explicit
const stream = collection.watch([], {
    startAfter: lastProcessedToken  // Identical to resumeAfter in practice
});

// Option 3: startAtOperationTime — resume from a timestamp
// Use: when you have no resume token but know a wall-clock time
// Use: initial sync — start from a specific point in time
const stream = collection.watch([], {
    startAtOperationTime: new Date("2024-03-15T10:00:00Z")
    // All changes at or after this time
    // Requires MongoDB 4.0+ and the time must be within oplog window
});

// IMPORTANT: what happens when the resume token falls outside the oplog:
// If the process was stopped for a long time (longer than oplog retention window),
// the saved resume token is no longer in the oplog → cannot resume
// Error: "resume point may no longer be in the oplog"
// This is a "broken stream" — must re-establish:
//   1. Take a full snapshot of the current state
//   2. Start a new change stream from NOW (no resumeAfter)
//   3. Apply full snapshot + new events from the stream
// This is the "initial sync" scenario

// Oplog size and retention:
// Default oplog: 5% of disk space or 990MB minimum
// At 1000 writes/sec: oplog fills in hours to days
// Increase oplog for long-running consumers:
// mongod --oplogSize 51200   (50GB oplog)
// Or via replica set config: rs.conf() → update oplogSizeMB
```

```javascript
// Robust reconnection with automatic resume:
// MongoDB Node.js driver handles most reconnection automatically
// The change stream cursor internally manages reconnection using the resume token

class ResilientChangeStreamConsumer {
    constructor(collection, pipeline, options) {
        this.collection = collection;
        this.pipeline = pipeline;
        this.options = options;
        this.resumeToken = null;
        this.running = false;
    }

    async start(handler) {
        this.running = true;
        while (this.running) {
            try {
                await this._consume(handler);
            } catch (err) {
                if (!this.running) break;

                const isResumable = err.code === 40585 || err.hasErrorLabel?.('ResumableChangeStreamError');
                if (!isResumable) {
                    console.error('Non-resumable error:', err);
                    throw err;  // Permanent error — escalate
                }

                console.warn('Resumable error, reconnecting in 1s:', err.message);
                await new Promise(r => setTimeout(r, 1000));
                // Loop: will reopen change stream with this.resumeToken
            }
        }
    }

    async _consume(handler) {
        const opts = {
            ...this.options,
            // If we have a resume token from previous run: use it
            ...(this.resumeToken ? { resumeAfter: this.resumeToken } : {})
        };

        const changeStream = this.collection.watch(this.pipeline, opts);

        try {
            for await (const event of changeStream) {
                await handler(event);
                this.resumeToken = event._id;  // Save latest token in memory
            }
        } finally {
            await changeStream.close();
        }
    }

    async stop() {
        this.running = false;
    }
}

// Usage:
const consumer = new ResilientChangeStreamConsumer(
    db.collection('orders'),
    [{ $match: { operationType: "insert" } }],
    {}
);

await consumer.start(async (event) => {
    await notifyFulfillmentSystem(event.fullDocument);
    await saveResumeToken(event._id);  // Persist for crash recovery
});
```

## Section 4: Full Document Options

**Q5. How do you get the full document on updates and the pre-image on deletes?**
A: By default, update events only contain `updateDescription` (which fields changed and their new values, but not the full document), and delete events only contain the `documentKey` (the `_id` of the deleted document). MongoDB provides options to include the full post-update document and the pre-change document (pre-image):

```javascript
// fullDocument option — get complete document after update:
const stream = orders.watch([], {
    fullDocument: 'updateLookup'
    // Options:
    // 'default':      Include fullDocument for insert and replace; not for update
    // 'updateLookup': Fetch full document from collection after update (extra read)
    // 'whenAvailable': MongoDB 6.0 — include if pre-image available, else null
    // 'required':      MongoDB 6.0 — error if full document not available
});

// With 'updateLookup': update events now include fullDocument:
// {
//   operationType: "update",
//   documentKey: { _id: ObjectId("...") },
//   updateDescription: { updatedFields: { status: "SHIPPED" }, removedFields: [] },
//   fullDocument: {
//     _id: ObjectId("..."),
//     status: "SHIPPED",        // ← current state of the document
//     amount: 99.99,
//     userId: "u-42"
//     // This is a CURRENT LOOKUP — not the state at the moment of update
//     // If document was updated again between the change event and the lookup:
//     // fullDocument may reflect the LATER update, not the one that triggered this event
//   }
// }

// The race condition warning with updateLookup:
// T1: update sets status="SHIPPED"  → change event generated
// T2: update sets status="DELIVERED" (before our stream reads the event)
// T3: our stream reads the event → fetches fullDocument → sees "DELIVERED"
// The event says operationType:"update", updatedFields:{status:"SHIPPED"}
// but fullDocument.status is "DELIVERED" ← stale lookup
// For strict correctness: use updateDescription only, or use pre/post images
```

```javascript
// Pre-images and post-images (MongoDB 6.0+) — exact document at change time:

// Step 1: Enable change stream pre/post images on the collection:
db.createCollection("orders", {
    changeStreamPreAndPostImages: { enabled: true }
});
// Or on an existing collection:
db.runCommand({
    collMod: "orders",
    changeStreamPreAndPostImages: { enabled: true }
});

// When enabled: MongoDB stores a copy of each document before and after each write
// Stored in: config.image_collection (internal collection)
// Retention: configurable (expireAfterSeconds for pre-images)

// Step 2: Request pre/post images in change stream options:
const stream = orders.watch([], {
    fullDocument: 'required',           // Full post-update document (exact state at write time)
    fullDocumentBeforeChange: 'required' // Full pre-update document (exact state before write)
});

// Update event with pre/post images:
// {
//   operationType: "update",
//   documentKey: { _id: ObjectId("...") },
//   updateDescription: { updatedFields: { status: "SHIPPED" } },
//   fullDocumentBeforeChange: {
//     _id: ObjectId("..."),
//     status: "PROCESSING",   // ← exact state BEFORE the update
//     amount: 99.99
//   },
//   fullDocument: {
//     _id: ObjectId("..."),
//     status: "SHIPPED",      // ← exact state AFTER the update (NOT a lookup)
//     amount: 99.99
//   }
// }

// Delete event with pre-image:
// {
//   operationType: "delete",
//   documentKey: { _id: ObjectId("...") },
//   fullDocumentBeforeChange: {
//     _id: ObjectId("..."),
//     status: "CANCELLED",    // ← the document that was deleted
//     amount: 99.99
//   }
//   // fullDocument: not available (deleted)
// }

// Pre-image costs:
// Storage: doubles write amplification (store extra copy of document on each write)
// Extra collection: config.image_collection grows proportionally to write volume
// Must configure retention or it grows unbounded:
db.adminCommand({
    setClusterParameter: {
        changeStreamOptions: {
            preAndPostImages: {
                expireAfterSeconds: 86400  // Keep pre-images for 24 hours
            }
        }
    }
});
```

## Section 5: Event-Driven Architecture Patterns

**Q6. How do you implement the outbox pattern with change streams to guarantee event delivery without dual-write?**
A: The outbox pattern solves the distributed transaction problem: how to atomically write to the database and publish an event, when neither two-phase commit nor distributed transactions are available. With change streams, the database write IS the event source — you only write to the database, and the change stream delivers the event:

```
The dual-write problem and outbox pattern:

  Problem: atomically update order status AND publish to Kafka
  ├── Write to DB, then publish to Kafka: Kafka publish may fail → event lost
  ├── Publish to Kafka, then write to DB: publish may succeed but DB fails → ghost event
  └── Neither is safe without a distributed transaction

  Outbox pattern (with change streams):
  ┌─────────────────────────────────────────────────────┐
  │ Application writes to DB ONLY (one atomic write):   │
  │  - orders collection: { status: "COMPLETED", ... }  │
  │  - outbox collection: { event: "order.completed" }  │
  │  Both in a MongoDB transaction                       │
  └─────────────────────────────────────────────────────┘
                            │
                    Change stream watches
                    outbox collection
                            │
                            ▼
                    ┌───────────────┐
                    │ CDC Relay     │
                    │ reads events  │
                    │ → publishes   │
                    │   to Kafka    │
                    └───────────────┘

  Guarantee: if the order is updated, the outbox event exists.
             Change stream delivers the outbox event exactly once (with resume token).
             Relay publishes to Kafka.
             Event is idempotent (consumer handles at-least-once delivery).
```

```javascript
// Outbox pattern implementation:

// 1. Application writes atomically to orders AND outbox in one transaction:
async function completeOrder(orderId, paymentId) {
    const session = client.startSession();

    try {
        await session.withTransaction(async () => {
            const now = new Date();

            // Update the order:
            await db.collection('orders').updateOne(
                { _id: orderId },
                {
                    $set: {
                        status: 'COMPLETED',
                        completedAt: now,
                        paymentId: paymentId
                    }
                },
                { session }
            );

            // Write to outbox in the SAME transaction:
            await db.collection('outbox').insertOne(
                {
                    _id: new ObjectId(),          // Outbox event ID (for deduplication)
                    aggregateType: 'Order',
                    aggregateId: orderId,
                    eventType: 'order.completed',
                    eventData: {
                        orderId,
                        paymentId,
                        completedAt: now
                    },
                    createdAt: now,
                    published: false              // Mark as unpublished
                },
                { session }
            );
        });
    } finally {
        await session.endSession();
    }
}

// 2. Change stream relay reads outbox and publishes to message broker:
async function startOutboxRelay(kafka, resumeTokenStore) {
    const savedToken = await resumeTokenStore.load('outbox');

    const changeStream = db.collection('outbox').watch(
        [{ $match: { operationType: 'insert' } }],
        { resumeAfter: savedToken, fullDocument: 'required' }
    );

    for await (const event of changeStream) {
        const outboxDoc = event.fullDocument;

        try {
            // Publish to Kafka:
            await kafka.producer.send({
                topic: outboxDoc.aggregateType.toLowerCase(),
                messages: [{
                    key: outboxDoc.aggregateId.toString(),
                    value: JSON.stringify({
                        eventId:    outboxDoc._id.toString(),
                        eventType:  outboxDoc.eventType,
                        data:       outboxDoc.eventData,
                        occurredAt: outboxDoc.createdAt
                    }),
                    headers: {
                        'event-type': outboxDoc.eventType,
                        'idempotency-key': outboxDoc._id.toString()  // For deduplication
                    }
                }]
            });

            // Mark as published (optional — for debugging):
            await db.collection('outbox').updateOne(
                { _id: outboxDoc._id },
                { $set: { published: true, publishedAt: new Date() } }
            );

            // Save resume token AFTER successful publish:
            await resumeTokenStore.save('outbox', event._id);

        } catch (err) {
            // Kafka publish failed — do NOT save resume token
            // Will retry this event on next run (at-least-once delivery)
            console.error('Outbox relay failed:', err);
            throw err;  // Let the outer retry loop handle reconnection
        }
    }
}

// 3. Cleanup old published outbox events (to prevent unbounded growth):
// Run on a schedule:
async function cleanupOutbox() {
    const cutoff = new Date(Date.now() - 7 * 24 * 60 * 60 * 1000); // 7 days old
    const result = await db.collection('outbox').deleteMany({
        published: true,
        publishedAt: { $lt: cutoff }
    });
    console.log(`Deleted ${result.deletedCount} old outbox events`);
}
```

**Q7. How do you implement real-time data synchronisation between MongoDB and other systems (Elasticsearch, Redis, data warehouses) using change streams?**
A: Change streams are the standard mechanism for Change Data Capture (CDC) from MongoDB — keeping downstream systems in sync as the MongoDB data changes. The pattern is an event-driven ETL pipeline that responds to changes rather than running periodic batch jobs:

```javascript
// MongoDB → Elasticsearch sync (real-time search indexing):

class ElasticsearchSync {
    constructor(mongoClient, esClient) {
        this.mongo = mongoClient;
        this.es = esClient;
        this.resumeToken = null;
    }

    async start() {
        const db = this.mongo.db('myapp');

        // Perform initial sync first (if Elasticsearch is empty):
        await this.initialSync(db.collection('products'));

        // Then start streaming changes:
        await this.streamChanges(db.collection('products'));
    }

    async initialSync(collection) {
        // Take a snapshot of the collection:
        console.log('Starting initial sync...');
        const session = this.mongo.startSession();

        // Get a consistent snapshot + the oplog timestamp at that moment:
        const startClusterTime = await this.getClusterTime();

        const cursor = collection.find({}, { session }).batchSize(1000);

        const batch = [];
        for await (const doc of cursor) {
            batch.push({
                index: { _index: 'products', _id: doc._id.toString() }
            });
            batch.push(this.transformForES(doc));

            if (batch.length >= 2000) {  // 1000 documents = 2000 bulk ops
                await this.es.bulk({ body: batch });
                batch.length = 0;
            }
        }
        if (batch.length > 0) {
            await this.es.bulk({ body: batch });
        }

        // Save the timestamp to start change stream from:
        this.syncStartTime = startClusterTime;
        console.log('Initial sync complete');
        await session.endSession();
    }

    async streamChanges(collection) {
        const opts = this.resumeToken
            ? { resumeAfter: this.resumeToken }
            : { startAtOperationTime: this.syncStartTime };

        const changeStream = collection.watch([], {
            ...opts,
            fullDocument: 'updateLookup'
        });

        const buffer = [];
        let flushTimer = null;

        const flush = async () => {
            if (buffer.length === 0) return;
            const toProcess = buffer.splice(0);  // Drain buffer atomically

            const bulkOps = [];
            for (const event of toProcess) {
                if (event.operationType === 'insert' || event.operationType === 'replace' ||
                    event.operationType === 'update') {
                    // Index or update the document:
                    bulkOps.push({ index: { _index: 'products', _id: event.documentKey._id.toString() } });
                    bulkOps.push(this.transformForES(event.fullDocument));
                } else if (event.operationType === 'delete') {
                    // Remove from index:
                    bulkOps.push({ delete: { _index: 'products', _id: event.documentKey._id.toString() } });
                }
            }

            if (bulkOps.length > 0) {
                await this.es.bulk({ body: bulkOps });
            }

            // Save resume token of last processed event:
            const lastEvent = toProcess[toProcess.length - 1];
            this.resumeToken = lastEvent._id;
            await this.saveResumeToken(this.resumeToken);
        };

        for await (const event of changeStream) {
            buffer.push(event);

            // Flush every 500 events or every 100ms (whichever comes first):
            if (buffer.length >= 500) {
                clearTimeout(flushTimer);
                await flush();
            } else if (!flushTimer) {
                flushTimer = setTimeout(async () => {
                    flushTimer = null;
                    await flush();
                }, 100);
            }
        }
    }

    transformForES(doc) {
        // Transform MongoDB document to Elasticsearch document:
        return {
            id: doc._id.toString(),
            name: doc.name,
            description: doc.description,
            price: doc.price,
            category: doc.category,
            tags: doc.tags || [],
            inStock: doc.inStock,
            updatedAt: doc.updatedAt
        };
    }
}
```

**Q8. How do you integrate change streams into a NestJS application — the right patterns for service lifecycle and WebSocket broadcasting?**
A: In NestJS, change streams should be managed as application-lifecycle services that start when the app boots, handle reconnection automatically, and broadcast events to the appropriate downstream systems (WebSockets, queues, other services):

```typescript
// change-stream.service.ts
import { Injectable, OnApplicationBootstrap, OnApplicationShutdown, Logger } from '@nestjs/common';
import { InjectConnection } from '@nestjs/mongoose';
import { Connection, Collection } from 'mongoose';
import { EventEmitter2 } from '@nestjs/event-emitter';

@Injectable()
export class OrderChangeStreamService
    implements OnApplicationBootstrap, OnApplicationShutdown
{
    private readonly logger = new Logger(OrderChangeStreamService.name);
    private changeStream: any;
    private isRunning = false;

    constructor(
        @InjectConnection() private readonly connection: Connection,
        private readonly eventEmitter: EventEmitter2,
        private readonly resumeTokenStore: ResumeTokenStore,
    ) {}

    async onApplicationBootstrap(): Promise<void> {
        // Start change stream when app boots:
        await this.startWatching();
    }

    async onApplicationShutdown(): Promise<void> {
        // Gracefully close when app shuts down:
        this.isRunning = false;
        await this.changeStream?.close();
        this.logger.log('Change stream closed');
    }

    private async startWatching(): Promise<void> {
        this.isRunning = true;
        const collection = this.connection.db.collection('orders');

        while (this.isRunning) {
            try {
                await this.watchCollection(collection);
            } catch (err) {
                if (!this.isRunning) break;
                this.logger.error('Change stream error, reconnecting...', err.message);
                await this.delay(1000);
            }
        }
    }

    private async watchCollection(collection: Collection): Promise<void> {
        const savedToken = await this.resumeTokenStore.load('orders');

        const pipeline = [
            {
                $match: {
                    operationType: { $in: ['insert', 'update', 'delete'] }
                }
            }
        ];

        const options = {
            fullDocument: 'updateLookup' as const,
            ...(savedToken ? { resumeAfter: savedToken } : {})
        };

        this.changeStream = collection.watch(pipeline, options);

        this.logger.log('Change stream started');

        for await (const event of this.changeStream) {
            await this.handleChange(event);
            await this.resumeTokenStore.save('orders', event._id);
        }
    }

    private async handleChange(event: any): Promise<void> {
        switch (event.operationType) {
            case 'insert':
                this.eventEmitter.emit('order.created', {
                    orderId: event.documentKey._id,
                    order: event.fullDocument
                });
                break;

            case 'update':
                const updatedStatus = event.updateDescription?.updatedFields?.status;
                if (updatedStatus) {
                    this.eventEmitter.emit('order.status.changed', {
                        orderId: event.documentKey._id,
                        newStatus: updatedStatus,
                        fullDocument: event.fullDocument
                    });
                }
                break;

            case 'delete':
                this.eventEmitter.emit('order.deleted', {
                    orderId: event.documentKey._id
                });
                break;
        }
    }

    private delay(ms: number): Promise<void> {
        return new Promise(resolve => setTimeout(resolve, ms));
    }
}
```

```typescript
        if (!userId) {
            client.disconnect();
            return;
        }
        if (!this.userSockets.has(userId)) {

        if (userId) {
            const sockets = this.userSockets.get(userId);
            sockets?.delete(client.id);
            if (sockets?.size === 0) {
                this.userSockets.delete(userId);
            }
        }

        this.emitToUser(userId, 'order:created', {
            orderId: payload.orderId,
            status: payload.order.status,
            amount: payload.order.amount
        });
    }

    @OnEvent('order.status.changed')
    handleStatusChange(payload: { orderId: string; newStatus: string; fullDocument: any }) {
```

## Section 7: Advanced Patterns

**Q9. How do you handle high-throughput change streams — batching, backpressure, and parallel processing?**
A: At high write volumes, naively processing each change event synchronously creates a bottleneck. The solution is buffered batch processing with configurable flush intervals, combined with awareness of backpressure to prevent memory exhaustion:

```javascript
// High-throughput change stream processor with batching:
class BatchingChangeStreamProcessor {
    constructor(collection, options = {}) {
        this.collection = collection;
        this.batchSize = options.batchSize ?? 500;
        this.flushIntervalMs = options.flushIntervalMs ?? 100;
        this.maxBufferSize = options.maxBufferSize ?? 5000;
        this.buffer = [];
        this.flushTimer = null;
        this.processing = false;
        this.pauseStream = null;
    }

    async start(batchHandler) {
        const changeStream = this.collection.watch([], {
            resumeAfter: await this.loadResumeToken(),
            fullDocument: 'updateLookup'
        });

        // Schedule periodic flush:
        this.flushTimer = setInterval(
            () => this.flush(batchHandler),
            this.flushIntervalMs
        );

        try {
            for await (const event of changeStream) {
                this.buffer.push(event);

                // Backpressure: if buffer is too large, pause the stream:
                if (this.buffer.length >= this.maxBufferSize) {
                    await this.flush(batchHandler);  // Force flush now
                }

                // Flush on batch size:
                if (this.buffer.length >= this.batchSize) {
                    clearInterval(this.flushTimer);
                    await this.flush(batchHandler);
                    this.flushTimer = setInterval(
                        () => this.flush(batchHandler),
                        this.flushIntervalMs
                    );
                }
            }
        } finally {
            clearInterval(this.flushTimer);
            await this.flush(batchHandler);  // Final flush on shutdown
        }
    }

    async flush(batchHandler) {
        if (this.buffer.length === 0 || this.processing) return;
        this.processing = true;

        const batch = this.buffer.splice(0);  // Atomically drain buffer
        try {
            await batchHandler(batch);

            // Save resume token of last event in batch:
            const lastEvent = batch[batch.length - 1];
            await this.saveResumeToken(lastEvent._id);

        } catch (err) {
            // On failure: prepend batch back to buffer for retry
            this.buffer.unshift(...batch);
            throw err;
        } finally {
            this.processing = false;
        }
    }
}

// Usage with Elasticsearch bulk indexing:

    db.collection('products'),
    { batchSize: 1000, flushIntervalMs: 200 }
);

await processor.start(async (batch) => {
```

**Q10. How do you watch a sharded cluster's change stream — what is different from a replica set?**
A: Change streams on a sharded cluster aggregate events from all shards. The router (`mongos`) coordinates this, presenting a single unified stream to the application. The challenge is that events from different shards may arrive out of wall-clock order, and the resume token must encode position across all shards:

```javascript
// Change stream on a sharded cluster:
// Connect through mongos (not individual shard):
const client = await MongoClient.connect(
    'mongodb://mongos1:27017,mongos2:27017/?replicaSet=configReplSet'
);

// Watch behaves the same API — mongos handles coordination:
const changeStream = client.db('myapp').collection('orders').watch();

// Differences from replica set:

// 1. Global ordering: mongos ensures a consistent global order across shards
//    Events are NOT necessarily in strict time order across shards
//    But they ARE causally consistent (you'll see events in a valid causal order)
//    The clusterTime field is monotonically increasing within each shard
//    but may not be strictly monotonic ACROSS shards

// 2. Resume tokens are shard-aware:
//    A resume token encodes the position across ALL shards
//    Can resume from any mongos — tokens are deployment-scoped

// 3. $match on the shard key gets pushed to individual shards:
const targetShardStream = db.collection('orders').watch([
    { $match: { "fullDocument.region": "EU" } }  // If region is shard key
]);
// This filter is pushed to EU shard only → less cross-shard traffic

// 4. invalidate events on sharded clusters:
// operationType: "invalidate" — emitted when:
//   - The collection is dropped
//   - The database is dropped
//   - The collection is renamed
//   - A shard is added/removed and changes the change stream topology
// After invalidate: the change stream cursor is exhausted — must reopen

changeStream.on('change', (event) => {
    if (event.operationType === 'invalidate') {
        console.warn('Change stream invalidated — need to reopen');
        // The stream is now closed — driver will not reconnect automatically
        // Must: reopen the change stream (possibly from the beginning or a new snapshot)
        changeStream.close().then(() => reopenChangeStream());
    }
});
```

```typescript
        this.startTracking().catch(err =>
            this.logger.error('Tracking service fatal error', err)
        );
    }

    private async startTracking() {
        while (true) {
            try {
                await this.watch();
            } catch (err) {
                this.logger.warn('Reconnecting in 2s...', err.message);
                await new Promise(r => setTimeout(r, 2000));
            }
        }
    }

    private async watch() {
        const savedToken = await this.resumeTokenStore.load('order-tracking');
        const collection = this.connection.db.collection('orders');

        const pipeline = [
            {
                $match: {
                    operationType: { $in: ['insert', 'update'] },
                    $or: [
                        { operationType: 'insert' },
                        { 'updateDescription.updatedFields.status': { $exists: true } },
                        { 'updateDescription.updatedFields.estimatedDelivery': { $exists: true } },
                        { 'updateDescription.updatedFields.trackingNumber': { $exists: true } }
                    ]
                }
            }
        ];

        const stream = collection.watch(pipeline, {
            fullDocument: 'updateLookup',
            ...(savedToken ? { resumeAfter: savedToken } : {})
        });

        for await (const event of stream) {
            await this.handleEvent(event);
            await this.resumeTokenStore.save('order-tracking', event._id);
        }
    }

    private async handleEvent(event: any) {
        const orderId = event.documentKey._id.toString();
        const doc = event.fullDocument;

        if (!doc) return;

        const trackingUpdate = {
            orderId,
            status: doc.status,
            statusLabel: this.getStatusLabel(doc.status),
            estimatedDelivery: doc.estimatedDelivery,
            trackingNumber: doc.trackingNumber,
            lastUpdated: new Date()
        };

        // Broadcast to all clients watching this order:
        await this.gateway.broadcastOrderUpdate(doc.userId, orderId, trackingUpdate);

        this.logger.log(`Order ${orderId} → ${doc.status}`);
    }

    private getStatusLabel(status: string): string {
        const labels: Record<string, string> = {
            'PENDING':    '📋 Order Received',
            'CONFIRMED':  '✅ Order Confirmed',
            'PROCESSING': '📦 Being Prepared',
            'SHIPPED':    '🚚 On the Way',
            'DELIVERED':  '🎉 Delivered',
            'CANCELLED':  '❌ Cancelled'
        };
        return labels[status] ?? status;
    }
}
```

**Q13. "A change stream consumer has been offline for 48 hours and the oplog has rotated. How do you recover without losing events?"**
A: An expired oplog means the resume token is no longer valid. Recovery requires an initial sync (full snapshot) followed by change stream from the snapshot point — the same pattern used when adding a new replica set member:

```javascript
// Recovery procedure when oplog is expired:

class ChangeStreamRecovery {
    constructor(sourceCollection, targetSystem, resumeTokenStore) {
        this.source = sourceCollection;
        this.target = targetSystem;
        this.tokenStore = resumeTokenStore;
    }

    async recover() {
        console.log('Starting recovery: oplog expired, full re-sync needed');

        // Step 1: Delete the invalid resume token:
        await this.tokenStore.delete('my-stream');

        // Step 2: Open a change stream BEFORE taking the snapshot
        //         to capture the exact timestamp:
        //         (This prevents missing changes between snapshot and stream start)
        const preSnapshotStream = this.source.watch([], {
            // No resumeAfter — start from NOW
        });

        // Capture the first "noop" event or wait for the first event
        // to get the current oplog position:
        // Actually, use db command to get cluster time:
        const clusterTimeResult = await this.source.aggregate([
            { $match: { _id: { $exists: false } } }  // Empty match — no results
        ]).toArray();
        // Or: use db.command({ isMaster: 1 }) → operationTime

        const snapshotTime = new Date();

        // Step 3: Close the pre-snapshot stream (we just needed the timestamp):
        await preSnapshotStream.close();

        // Step 4: Take a full snapshot of the current state:
        await this.fullSnapshot();

        // Step 5: Start change stream from the snapshot timestamp:
        const changeStream = this.source.watch([], {
            startAtOperationTime: snapshotTime  // Captures all changes after snapshot
            // This may replay some changes already in snapshot — must handle idempotently
        });

        // Step 6: Process events (idempotently — some may already be in snapshot):
        for await (const event of changeStream) {
            await this.processIdempotent(event);
            await this.tokenStore.save('my-stream', event._id);
        }
    }

    async fullSnapshot() {
        console.log('Taking full snapshot...');
        const cursor = this.source.find({}).batchSize(1000);
        let count = 0;

        for await (const doc of cursor) {
            // Upsert into target system (idempotent):
            await this.target.upsert(doc._id.toString(), doc);
            count++;
            if (count % 10000 === 0) {
                console.log(`Snapshot progress: ${count} documents`);
            }
        }
        console.log(`Snapshot complete: ${count} documents`);
    }

    async processIdempotent(event) {
        // Must be idempotent: snapshot may have already captured this state
        switch (event.operationType) {
            case 'insert':
            case 'replace':
            case 'update':
                // Upsert: safe to apply multiple times
                await this.target.upsert(
                    event.documentKey._id.toString(),
                    event.fullDocument
                );
                break;
            case 'delete':
                // Delete: safe to call multiple times (idempotent)
                await this.target.delete(event.documentKey._id.toString());
                break;
        }
    }
}
```

## Quick Reference Table

| Concept | What it is | Key detail | Common mistake |
|---|---|---|---|
| Change stream | Real-time event stream of MongoDB writes, built on the oplog | Requires replica set (at least single-node with `rs.initiate()`) | Running against standalone MongoDB — no oplog → no change streams |
| Resume token | Opaque cursor position in each change event `_id` field | Persist after each processed event; use `resumeAfter` to recover | Not persisting token — restart reprocesses from beginning (or loses events) |
| `operationType` | Type of change: `insert`, `update`, `replace`, `delete`, `invalidate` | `update` ≠ `replace`: update has `updateDescription`; replace has full `fullDocument` | Treating update and replace identically — replace has no `updateDescription` |
| `fullDocument: 'updateLookup'` | Fetches full document from collection after update events | Has race condition: document may have changed again between event and lookup | Using for strict auditing — stale; use pre/post images instead |
| Pre/post images | Exact document state before AND after each write (MongoDB 6.0+) | Requires `changeStreamPreAndPostImages: { enabled: true }` on collection | Not setting `expireAfterSeconds` — pre-image collection grows unbounded |
| `startAtOperationTime` | Resume from a wall-clock timestamp instead of a token | Must be within the oplog window; used for initial sync recovery | Using timestamps for normal resumption — use resume tokens (more precise) |
| `invalidate` event | Stream emits when collection/database is dropped or renamed | After `invalidate`: stream is exhausted — must reopen | Ignoring `invalidate` events — consumer hangs on a dead stream |
| `$match` in pipeline | Server-side filtering of change events | Applied to the change event structure, not the original documents | Matching on `fullDocument.field` for update events — `fullDocument` not included by default |
| Oplog expiry | Resume tokens older than oplog retention are invalid | Oplog size determines how long tokens remain valid | Pausing consumer for longer than oplog window without increasing oplog size |
| `allowDiskUse` | Not applicable to change streams | Change streams are cursors, not aggregations — this option is not used | Confusing change stream pipeline with aggregation pipeline options |
| Collection vs database vs deployment scope | Collection: one collection; database: all collections; deployment: everything | Narrower scope = less overhead; broader scope = more data | Opening deployment-level stream for per-collection use — unnecessary overhead |
| Idempotent processing | Processing same event twice produces same result | Required for at-least-once delivery; use upsert semantics | Writing non-idempotent handlers — duplicate events on reconnect cause data corruption |

**Tip for interviews:** Five things separate strong candidates on MongoDB change streams: (1) explaining **why a replica set is required** — that change streams are built on the oplog (operation log), which is the internal replication log that only exists in replica set mode, and that even a single-node deployment needs `rs.initiate()` to create the oplog before change streams work; (2) articulating the **resume token checkpoint pattern precisely** — that the token must be saved to durable storage AFTER successful processing (not before), that saving before means an event looks processed but wasn't, and that not saving means every restart reprocesses all events or starts from a new position, and knowing the distinction between `resumeAfter` (start after the token's event, exclusive) vs `startAtOperationTime` (start from a timestamp, used for initial sync recovery); (3) understanding the **fullDocument gap for updates** — that update events do NOT include `fullDocument` by default (only `updateDescription` with changed fields), that `updateLookup` adds a lookup but introduces a race condition where a later update may be reflected, and that pre/post images (MongoDB 6.0+) provide the exact document state at write time without race conditions at the cost of doubled write amplification; (4) being able to design the **outbox pattern** — that writing to an outbox collection in the SAME MongoDB transaction as the business write atomically guarantees the event will exist if the write succeeded, that the change stream on the outbox collection delivers it to the message broker, and that this eliminates the dual-write race condition without requiring a distributed transaction; and (5) knowing **how to handle oplog expiry** — that if the consumer is offline longer than the oplog window, the resume token is invalid ("resume point may no longer be in the oplog"), that recovery requires taking a full collection snapshot before re-establishing the stream from `startAtOperationTime`, and that prevention involves sizing the oplog (`replSetResizeOplog`) to exceed the maximum expected consumer downtime.
