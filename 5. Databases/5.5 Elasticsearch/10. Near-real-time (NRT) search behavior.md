# Near-Real-Time (NRT) Search Behavior (Elasticsearch) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "near-real-time" mean in Elasticsearch and why is it "near" rather than real-time?**
A: Elasticsearch is near-real-time because there is a default latency of up to **1 second** between when a document is indexed and when it becomes visible to search queries. The gap exists because making a document searchable requires creating a new Lucene segment, which involves flushing the in-memory buffer — an operation too expensive to run on every single write. Instead, Elasticsearch batches writes and creates segments on a configurable interval (default: 1 second):

```
Real-time vs Near-Real-Time — the core distinction:

  True real-time system:
    Client writes document at T=0ms
    Client searches for document at T=1ms
    Document appears in results ✓
    Requirement: every write immediately updates the search index
    Cost: a Lucene segment must be created for every single write
          creating a segment involves: sorting terms, building FST, compressing posting lists
          ~1–5ms per document → completely unusable at any meaningful write throughput

  Near-real-time (Elasticsearch default):
    Client writes document at T=0ms       → goes to in-memory buffer + translog
    Client searches at T=200ms            → document NOT visible ✗ (still in buffer)
    Elasticsearch refreshes at T=1000ms   → in-memory buffer → new Lucene segment
    Client searches at T=1001ms           → document IS visible ✓
    Maximum search latency: 1 × refresh_interval (default: 1 second)

Why not refresh on every write?
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ Segment creation cost:                                                  │
  │   Sort all terms in buffer alphabetically (for term dictionary)        │
  │   Build FST (Finite State Transducer) for the term dictionary          │
  │   Compress posting lists (FOR/PFOR encoding)                           │
  │   Write doc values (columnar data for aggregations)                    │
  │   Write norms (field-length factors for BM25 scoring)                  │
  │   Result: typically 1–5ms of CPU work per new segment                  │
  │                                                                         │
  │ At 10,000 writes/second with per-write refresh:                        │
  │   10,000 segment creations/second × 2ms = 20,000ms of CPU/second       │
  │   → 20× more CPU than available → system falls over                    │
  │                                                                         │
  │ With 1-second batching (default):                                       │
  │   1 segment creation/second × 2ms = 2ms of CPU/second                  │
  │   → negligible overhead, 10,000 writes/second easily handled           │
  └─────────────────────────────────────────────────────────────────────────┘

The NRT contract Elasticsearch provides:
  ✓ Any document indexed will be searchable within refresh_interval (default: 1s)
  ✓ The document is durable immediately (translog write) — will survive a crash
  ✗ The document is NOT searchable immediately after the index call returns
  Exception: GET by ID uses a "real-time get" path that bypasses NRT — see Q5
```

**Q2. What is the complete write-to-searchable lifecycle of a document in Elasticsearch?**
A: A document goes through four distinct phases before and after it becomes searchable: write to in-memory buffer and translog, refresh (becomes searchable), flush (persisted to disk), and merge (segments consolidated). Each phase has a different cost, trigger, and effect on search visibility and durability:

```
Complete write lifecycle:

  Phase 0: CLIENT WRITE (T=0)
  ─────────────────────────────────────────────────────────
  PUT /loans/_doc/L001 { "status": "approved", "amount": 50000 }
  ↓
  Primary shard receives the operation
  Two things happen SIMULTANEOUSLY:
    a) Written to TRANSLOG (write-ahead log):
       Sequential append to a file on disk
       fsync per operation by default (index.translog.durability: "request")
       Purpose: durability — if node crashes, translog allows recovery
       NOT for search — translog is NOT searched
    b) Written to IN-MEMORY BUFFER:
       Accumulated in a per-index in-memory structure (Lucene IndexWriter)
       NOT yet a Lucene segment — not searchable
       NOT yet on disk — would be lost in a crash (without the translog)
  Client receives: 200 OK { "result": "created" }
  Document is: DURABLE (translog) but NOT SEARCHABLE

  Phase 1: REFRESH (T + refresh_interval, default T+1s)
  ─────────────────────────────────────────────────────────
  Trigger: automatic (every refresh_interval) OR manual POST /loans/_refresh
  Action:
    In-memory buffer → NEW LUCENE SEGMENT
    The segment is built in memory, then placed in the OS filesystem cache
    Not yet on disk (fsync has NOT happened) — in OS page cache only
    Segment is opened for reading → documents are NOW SEARCHABLE
  Cost: CPU (sort, compress, build FST) — typically 1–10ms depending on buffer size
  After refresh: document IS searchable via search queries
  Durability: still relying on translog (segment is in OS cache, not disk)

  Phase 2: FLUSH (T + 30 minutes, or when translog exceeds 512MB)
  ─────────────────────────────────────────────────────────────────
  Trigger: automatic (translog size threshold or time), OR manual POST /loans/_flush
  Action:
    All segments in OS cache → written to disk (fsync)
    A Lucene commit point is written (records which segments exist)
    Translog is CLEARED (the on-disk segment is now the source of truth)
  After flush: document is searchable AND durable on disk
  Translog recovery: no longer needed for this document (it's now in a flushed segment)

  Phase 3: MERGE (background, automatic)
  ─────────────────────────────────────────────────────────────────
  Trigger: Elasticsearch monitors segment count per shard; merges when too many
  Action:
    N small segments → 1 larger segment
    Deleted documents are physically removed (live docs bit-set applied)
    Old segments deleted after merge completes
  Cost: CPU + disk I/O (can cause write/read latency spikes)
  Effect on searchability: none (documents remain searchable throughout merge)

  Timeline diagram:
  ────────────────────────────────────────────────────────────────────────────
  T=0ms      Write received: translog ✓, in-memory buffer ✓
  T=0ms      Client receives 200 OK
  T=0–999ms  Document: DURABLE (translog) | NOT SEARCHABLE (buffer)
  T=1000ms   Refresh: new segment created in OS cache
  T=1001ms   Document: DURABLE (translog) | SEARCHABLE ✓
  T=30min    Flush: segment fsynced to disk, translog cleared
  T=30min+   Document: DURABLE (disk) | SEARCHABLE ✓
  T=variable Merge: old segments consolidated, deleted docs cleaned up
  ────────────────────────────────────────────────────────────────────────────

Data structures per phase:
  ┌───────────────────┬──────────────────┬────────────────┬────────────────────┐
  │ Phase             │ Location         │ Searchable?    │ Survives crash?    │
  ├───────────────────┼──────────────────┼────────────────┼────────────────────┤
  │ In-memory buffer  │ JVM heap         │ No             │ No (needs translog)│
  │ Translog          │ Disk (fsync'd)   │ No             │ Yes                │
  │ Segment (OS cache)│ OS page cache    │ Yes            │ No (needs translog)│
  │ Segment (flushed) │ Disk (fsync'd)   │ Yes            │ Yes                │
  └───────────────────┴──────────────────┴────────────────┴────────────────────┘
```

## Section 2: The Refresh Mechanism

**Q3. What exactly happens during a refresh and what controls it?**
A: A refresh converts the in-memory write buffer into a searchable Lucene segment. The segment is not necessarily written to disk — it lives in the OS filesystem cache and is made available to Lucene's `IndexReader` by opening a new reader on it. The key insight is that Lucene's `IndexReader` works on any readable file, whether it is flushed to disk or only in OS cache:

```
Refresh internals:

  Lucene's NRT reader model:
    Lucene uses a NearRealTimeReader (NRTManager) pattern internally
    After each refresh:
      Old IndexReader is replaced with a new one that includes the latest segment
      The new reader opens the new segment (even from OS cache) for searching
      In-flight searches using the old reader complete normally (no locking needed)
    Result: search and write are concurrent, lock-free

  What a refresh creates:
    New segment files (in OS cache):
      .tim  — term dictionary (FST of all indexed terms)
      .doc  — posting lists (doc IDs + term frequencies)
      .pos  — positions (for phrase queries)
      .fdx/.fdt — stored field index/data (_source)
      .dvd/.dvm — doc values (for aggregations/sorting)
      .nvm/.nvd — norms (for BM25 length normalization)
    All built from the in-memory buffer contents

  Refresh does NOT:
    ✗ fsync to disk (that's flush)
    ✗ clear the translog (that's flush)
    ✗ affect pending writes (new writes continue to in-memory buffer during refresh)

Controlling refresh_interval:
  Default: "1s"
  Set per-index:
  PUT /loans/_settings
  {
    "index.refresh_interval": "5s"   // refresh every 5 seconds
  }

  Special value: "-1" (disable automatic refresh entirely):
  PUT /loans/_settings
  {
    "index.refresh_interval": "-1"   // no automatic refresh
  }
  // Documents are NEVER automatically searchable
  // Must manually call POST /loans/_refresh to make them visible
  // Use case: bulk indexing where NRT is not required during the load

  Valid values: any positive duration string ("500ms", "2s", "1m")
  Minimum practical value: "100ms" (below this, segment creation overhead dominates)

  Effect of different intervals:
  ┌────────────────────┬──────────────────────┬────────────────────────────────┐
  │ refresh_interval   │ Max search latency   │ Write throughput impact        │
  ├────────────────────┼──────────────────────┼────────────────────────────────┤
  │ "100ms"            │ 100ms                │ High (10 segment creates/sec)  │
  │ "1s" (default)     │ 1 second             │ Low (1 segment create/sec)     │
  │ "10s"              │ 10 seconds           │ Very low                       │
  │ "30s"              │ 30 seconds           │ Minimal                        │
  │ "-1" (disabled)    │ Until manual refresh │ None (zero segment creations)  │
  └────────────────────┴──────────────────────┴────────────────────────────────┘

Manual refresh:
  POST /loans/_refresh         // refresh single index
  POST /loans,orders/_refresh  // refresh multiple indices
  POST /_refresh               // refresh ALL indices (expensive in production)

  When to call manually:
    After bulk indexing completes (when refresh_interval is "-1")
    In integration tests: index test data, refresh, then assert search results
    After a migration/reindex to make newly indexed data immediately available

Checking refresh state and segment count:
  GET /loans/_stats/refresh
  {
    "indices": {
      "loans": {
        "total": {
          "refresh": {
            "total":             3421,     // how many refreshes have occurred
            "total_time_in_millis": 5823,  // total time spent refreshing
            "listeners":         0         // pending refresh listeners (from ?refresh=wait_for)
          }
        }
      }
    }
  }

  GET /loans/_segments
  // Shows all current segments per shard: size, doc count, generation number
  // High segment count (>50 per shard) → merge is falling behind write rate
  // Impacts search: more segments = more places to search = slower queries
```

**Q4. How does the `?refresh` query parameter work and when do you use each option?**
A: Elasticsearch provides three values for the `?refresh` parameter on write requests — `true`, `wait_for`, and `false` (default). They control whether and how the indexing call waits for the document to become searchable before returning to the caller. Each has distinct performance characteristics:

```
?refresh parameter options:

  ?refresh=false (DEFAULT — omitting the parameter entirely)
  ─────────────────────────────────────────────────────────
  Behavior: index the document, return immediately, do NOT trigger a refresh
  Client receives 200 OK immediately after translog write
  Document is searchable after the NEXT scheduled automatic refresh
  Latency: fastest (no refresh cost added to write latency)
  Use: production indexing where 1-second NRT lag is acceptable (most cases)

  PUT /loans/_doc/L001?refresh=false  // or simply omit ?refresh
  { "status": "approved", "amount": 50000 }
  // Returns: 200 OK immediately
  // Search will see L001 within 1 second (next refresh)

  ?refresh=true
  ─────────────────────────────────────────────────────────
  Behavior: index the document AND immediately trigger a FULL SHARD REFRESH
  Returns to client only AFTER the refresh completes
  Document is guaranteed searchable when 200 OK is received
  Latency: write latency + refresh latency (adds 1–10ms typically)
  Cost: one additional refresh per write → DEFEATS the NRT batching optimization

  PUT /loans/_doc/L001?refresh=true
  { "status": "approved", "amount": 50000 }
  // Refresh triggered immediately after this write
  // ALL documents in the shard's in-memory buffer become searchable, not just L001
  // Other concurrent writes also get refreshed as a side effect
  // Returns 200 OK only after the refresh completes

  WARNING — never use ?refresh=true at high write throughput:
  At 1,000 writes/second with ?refresh=true:
    Each write triggers a full shard refresh
    1,000 segment creations/second → system cannot keep up → write latency spikes
    Segments accumulate faster than merges can handle → heap pressure, slow searches
  Use ONLY for: low-volume, interactive use cases where immediate visibility is required
                e.g. user submits a form → you index it → redirect to a page that searches
                e.g. integration tests (index test data, verify it's immediately searchable)

  ?refresh=wait_for
  ─────────────────────────────────────────────────────────
  Behavior: index the document, then WAIT until the document is included in a refresh
            Does NOT trigger a new refresh — waits for the NEXT scheduled refresh
  Returns to client after the NEXT automatic refresh includes this document
  Latency: write latency + time_until_next_refresh (up to refresh_interval, default 1s)
  Cost: holds the client connection open (long-polling style); NO extra refresh created

  PUT /loans/_doc/L001?refresh=wait_for
  { "status": "approved", "amount": 50000 }
  // Submitted at T=0ms
  // Next scheduled refresh at T=700ms (remaining in the 1s cycle)
  // Returns 200 OK at T=700ms (document is now searchable)
  // No extra segment created — waited for the naturally scheduled refresh

  How wait_for works internally:
    The write is registered as a "refresh listener"
    After translog write, the server thread blocks (or async callback)
    When the next refresh completes: listener is notified → response sent
    GET /loans/_stats/refresh → "listeners" count shows pending wait_for requests

  ?refresh=wait_for vs ?refresh=true comparison:
  ┌──────────────────────┬──────────────────────┬──────────────────────────────┐
  │ Property             │ ?refresh=true        │ ?refresh=wait_for            │
  ├──────────────────────┼──────────────────────┼──────────────────────────────┤
  │ Creates new refresh? │ Yes, immediately      │ No, waits for next scheduled │
  │ Client waits?        │ Yes (for the refresh)│ Yes (for the next refresh)   │
  │ Max wait time        │ One refresh duration │ Up to refresh_interval       │
  │ Load on cluster      │ High at scale         │ Low (no extra refreshes)     │
  │ Use at high QPS      │ Never                 │ Acceptable (bounded by interval)│
  └──────────────────────┴──────────────────────┴──────────────────────────────┘

  Practical decision tree:
  ┌── Do you need the doc searchable before the API call returns?
  │     No  → use ?refresh=false (default) — fastest, best for production writes
  │     Yes ─┬─ Write rate is LOW (< 10/sec) and you need immediate visibility?
  │           │     → use ?refresh=true (simplest, acceptable at low volume)
  │           └─ Write rate is MODERATE and you don't want extra segment overhead?
  │                 → use ?refresh=wait_for (waits for natural refresh, no extra cost)

  Applying to bulk API:
  POST /loans/_bulk?refresh=wait_for
  { "index": { "_id": "L001" } }
  { "status": "approved", "amount": 50000 }
  { "index": { "_id": "L002" } }
  { "status": "pending", "amount": 75000 }
  // Both documents are guaranteed searchable when this call returns
  // Only one wait — for the next refresh that includes BOTH documents
```

## Section 3: Real-Time GET vs NRT Search

**Q5. Why does a `GET /loans/_doc/L001` return a document immediately after indexing, but a search query for the same document may not find it?**
A: The `GET` API and the `search` API use fundamentally different read paths. The `GET` API performs a **real-time get** — it checks the translog first, before any segment exists. Since the translog is written before the API call returns, a `GET` by ID always finds the document. The `search` API only reads from Lucene segments, which do not include the document until after a refresh:

```
Two read paths in Elasticsearch:

  Path 1: Real-Time GET (GET /index/_doc/{id})
  ─────────────────────────────────────────────
  Step 1: Determine the shard for this ID
          shard = hash(document_id) % num_primary_shards
  Step 2: Check the in-memory segment buffer AND the translog for this ID
          If found in translog (most recent version): return it immediately
          If found in a refreshed segment: return it
  Step 3: Return the document

  Result: 200 OK with the document, even 0ms after indexing
  No segment needed — the translog IS the real-time data store for GET by ID

  Implementation detail:
    The translog contains the full document (_source, all fields)
    Elasticsearch maintains a translog position index: id → translog offset
    GET by ID: O(1) translog lookup → real-time

  Opt out of real-time GET (read from segment only):
  GET /loans/_doc/L001?realtime=false
  // Will NOT check translog — only reads from segments
  // Document may not be found if not yet refreshed

  Path 2: NRT Search (GET /loans/_search { "query": ... })
  ─────────────────────────────────────────────────────────
  Step 1: The search only reads from LUCENE SEGMENTS
          Segments = inverted index + doc values + stored fields ON DISK OR OS CACHE
          The in-memory buffer and translog are NOT searched
  Step 2: Query runs against all open segments
  Step 3: Return results

  Result: document NOT found until after a refresh creates a segment for it

The mismatch in practice:
  T=0ms:   PUT /loans/_doc/L001 { "status": "approved" }
           → translog written, in-memory buffer written
           → 200 OK returned to client

  T=1ms:   GET /loans/_doc/L001
           → real-time get: checks translog → found → returns document ✓

  T=1ms:   GET /loans/_search { "query": { "term": { "status": "approved" } } }
           → NRT search: checks segments → document not yet in any segment → NOT FOUND ✗

  T=1001ms (after refresh):
           GET /loans/_search { "query": { "term": { "status": "approved" } } }
           → NRT search: new segment exists → FOUND ✓

  Summary:
  ┌──────────────────┬───────────────────────────────┬──────────────────────────┐
  │ Operation        │ Reads from                    │ Sees un-refreshed docs?  │
  ├──────────────────┼───────────────────────────────┼──────────────────────────┤
  │ GET by ID        │ Translog + segments           │ Yes (real-time)          │
  │ MGET (multi-get) │ Translog + segments           │ Yes (real-time)          │
  │ search           │ Segments only                 │ No (NRT — up to 1s lag)  │
  │ search (scroll)  │ Segments only                 │ No                       │
  │ count            │ Segments only                 │ No                       │
  │ exists           │ Segments only                 │ No                       │
  │ GET ?realtime=false│ Segments only               │ No                       │
  └──────────────────┴───────────────────────────────┴──────────────────────────┘

Implication for application design:
  Pattern: index a document, then immediately show it to the user

  // WRONG — will sometimes return 404 or empty results:
  await indexDocument(loan);
  const results = await searchDocuments({ query: { match: { status: "approved" } } });
  // results may not contain the new loan

  // CORRECT option 1 — use GET by ID after indexing:
  await indexDocument(loan);
  const loan = await getById(loanId);  // real-time GET → always finds it
  renderLoanDetail(loan);

  // CORRECT option 2 — use ?refresh=true or ?refresh=wait_for:
  await indexDocument(loan, { refresh: "wait_for" });
  const results = await searchDocuments({ ... });  // now will find the document

  // CORRECT option 3 — design the UI to not immediately search:
  await indexDocument(loan);
  redirect("/loans/${loanId}");  // redirect to detail page using GET by ID, not search
```

## Section 4: Flush and Translog

**Q6. What is the relationship between flush, the translog, and NRT search?**
A: Flush and refresh are independent operations that are often confused. Refresh controls search visibility (in-memory buffer → searchable segment). Flush controls durability (segment → disk + translog cleared). A document can be searchable before it is flushed, and flushed documents were searchable before the flush. The translog bridges the gap between writes and disk persistence:

```
Flush vs Refresh — side-by-side:

  ┌────────────────────┬──────────────────────────┬──────────────────────────────┐
  │ Property           │ Refresh                  │ Flush                        │
  ├────────────────────┼──────────────────────────┼──────────────────────────────┤
  │ Purpose            │ Make docs searchable     │ Persist segments to disk     │
  │ Writes to disk?    │ No (OS cache only)       │ Yes (fsync)                  │
  │ Affects search?    │ Yes (new segment visible)│ No (search continues as-is)  │
  │ Clears translog?   │ No                       │ Yes                          │
  │ Default trigger    │ Every 1 second           │ Every 30min or translog>512MB│
  │ Manual trigger     │ POST /_refresh           │ POST /_flush                 │
  │ Cost               │ CPU (segment build)      │ Disk I/O (fsync)             │
  └────────────────────┴──────────────────────────┴──────────────────────────────┘

Translog role in the lifecycle:
  The translog is a write-ahead log (WAL) — the standard durability pattern:
    Write to log first (cheap, sequential, fsync'd)
    Apply to main data structure second (more expensive, batch-able)

  Translog guarantees: no data loss even if:
    ✓ Node loses power before refresh (segment not yet created)
    ✓ Node loses power before flush (segment in OS cache, not on disk)
    ✓ Node loses power during a merge

  Recovery sequence after crash:
    Elasticsearch starts → opens the last committed Lucene segments (from disk)
    Reads the translog → replays every operation since the last flush
    Re-creates the in-memory state → triggers a refresh → segments available again
    Node joins the cluster

  Recovery time: proportional to translog size
    Small translog (frequent flushes): fast recovery (seconds)
    Large translog: slow recovery (minutes for a 512MB translog)

Translog durability modes:
  index.translog.durability: "request" (default)
    Behavior: every write fsyncs the translog before returning 200 OK
    Durability: zero data loss — no acknowledged write is lost on crash
    Performance: one fsync per write — significant I/O cost at high throughput
    Use: any data where loss is unacceptable

  index.translog.durability: "async"
    Behavior: translog fsynced every sync_interval (default: 5s) in the background
    Durability: up to sync_interval of writes can be lost on sudden power failure
    Performance: no per-write fsync → 3–5× higher write throughput
    Risk: up to 5 seconds of acknowledged writes lost on hard crash (power cut)
    Use: logs, metrics, analytics — where small data loss is acceptable

  PUT /loan_events/_settings
  {
    "index.translog.durability": "async",
    "index.translog.sync_interval": "5s"
  }
  // "async" translog: NRT search behavior is unchanged (still 1-second refresh)
  // Only durability (crash safety) is affected, not search visibility

Flushing on demand:
  POST /loans/_flush
  // Flushes all segments to disk, clears translog
  // When to call manually:
  //   Before taking a snapshot (ensure segments are on disk)
  //   After bulk indexing with async translog (commit to disk)
  //   Before deliberately stopping a node

  POST /loans/_flush?wait_if_ongoing=true
  // Waits if a flush is already in progress (prevents duplicate flushes)

Synced flush (deprecated in 7.6, removed in 8.x):
  Was used to speed up shard recovery by marking all shards with a sync ID
  Replaced by: Elasticsearch automatically performs a flush on shard close (node shutdown)
  In current versions: regular flush handles this correctly

Translog statistics:
  GET /loans/_stats/translog
  {
    "translog": {
      "operations":                  145230,  // total ops in translog
      "size_in_bytes":              52428800,  // translog size (50MB)
      "uncommitted_operations":       1234,   // not yet flushed to disk
      "uncommitted_size_in_bytes":  512000,   // uncommitted translog size
      "earliest_last_modified_age": 120000    // age of oldest unflushed translog entry (ms)
    }
  }
  // If uncommitted_size_in_bytes is near index.translog.flush_threshold_size (512MB default)
  // → auto-flush will trigger soon
```

## Section 5: Shards, Replicas, and NRT

**Q7. When a document is indexed to a primary shard, when does it become searchable on replica shards?**
A: After a write is applied to the primary shard, it is forwarded to all replica shards. Each replica independently refreshes on its own schedule. This means replicas may be 0–2 refresh intervals behind the primary — a document searchable on the primary may not yet be searchable on a replica. Elasticsearch's search routing can land a request on any copy:

```
Primary → Replica write flow:

  Client writes to coordinating node → coordinating node routes to PRIMARY shard
  PRIMARY shard:
    1. Writes to translog + in-memory buffer
    2. Returns 200 OK to CLIENT (if durability satisfied)
    3. Forwards operation to ALL replica shards (in parallel)

  REPLICA shards:
    4. Each replica receives the forwarded operation
    5. Each replica writes to its own translog + in-memory buffer
    6. Replicas refresh independently (not synchronized with primary)
    7. Replicas confirm to primary (primary waits for quorum by default)

  Search routing:
    By default: Elasticsearch can route a search to ANY shard copy (primary or replica)
    Reason: distribute read load across replicas
    Consequence: a document refreshed on the primary may not yet be refreshed on a replica

  Timing scenario:
    T=0ms:    Document written to primary (in-memory buffer)
    T=0ms:    Document forwarded to 2 replica shards
    T=200ms:  Primary's scheduled refresh → document SEARCHABLE on primary
    T=800ms:  Replica shard 1's refresh → document SEARCHABLE on replica 1
    T=1100ms: Replica shard 2's refresh → document SEARCHABLE on replica 2

    Between T=200ms and T=800ms:
    Search routed to primary → finds document ✓
    Search routed to replica 1 → finds document ✗ (not yet refreshed)
    Result: inconsistent search results depending on which shard serves the request

  Is this a real problem in practice?
    For most use cases: No.
    Refresh intervals are 1 second, the window is milliseconds in practice,
    and Elasticsearch randomizes routing across copies on each request.
    For strict read-your-writes consistency: use preference=_primary (forces primary reads)
    or use ?refresh=wait_for (ensures doc is refreshed before the write returns)

Preference parameter — controlling which shard copy serves a search:
  GET /loans/_search?preference=_primary
  // Routes ALL searches to primary shards only
  // Effect: eliminates replica lag for read-your-writes consistency
  // Cost: no read load distribution → primary handles all reads + writes
  // Use: short-term, when strict consistency is required

  GET /loans/_search?preference=_replica
  // Routes to replicas only (reduces primary load)
  // May have slightly more lag than primary

  GET /loans/_search?preference=_local
  // Routes to the local node's shard copy if available
  // Reduces network hops in co-located deployments

  GET /loans/_search?preference=custom_routing_key
  // Sticky routing: same key → always same shard copy
  // Useful: caching — same shard → OS cache warm for this user's queries

wait_for_active_shards — write quorum control:
  PUT /loans/_doc/L001?wait_for_active_shards=all
  // Wait until ALL copies (primary + all replicas) have the operation
  // before returning 200 OK — ensures ALL copies are at least at the
  // translog level (NOT at the searchable/refreshed level)
  // Default: wait_for_active_shards=1 (primary only)

  // Note: this is NOT about search visibility — it's about write durability quorum
  // Even with wait_for_active_shards=all, replicas may not be refreshed yet

Replication and NRT summary:
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │ A document is searchable on a shard only AFTER that shard's refresh runs.   │
  │ Each shard copy (primary + replicas) refreshes on its own schedule.         │
  │ wait_for_active_shards controls WRITE durability quorum, not search lag.    │
  │ ?refresh=wait_for waits for the PRIMARY's refresh (not replicas).           │
  │ For guaranteed read-your-writes: use GET by ID, or ?preference=_primary.    │
  └──────────────────────────────────────────────────────────────────────────────┘
```

## Section 6: Optimizing for Bulk Indexing

**Q8. How do you maximize indexing throughput when NRT search is not needed during a bulk load, and how do you restore NRT behavior after?**
A: The biggest levers for bulk indexing throughput are disabling the automatic refresh and reducing replica count during the load. Refresh is the primary bottleneck because every second a segment is created and opened, consuming CPU and adding to the segment count. With refresh disabled, all writes accumulate in the in-memory buffer until a manual refresh or flush:

```
Bulk indexing optimization pattern:

  Phase 1: Pre-load configuration (BEFORE indexing starts)
  ──────────────────────────────────────────────────────────
  PUT /loans/_settings
  {
    "index.refresh_interval": "-1",            // disable automatic refresh
    "index.number_of_replicas": 0              // disable replicas during load
  }

  Why disable replicas?
    With replicas: every write goes to primary → forwarded to N replicas
    Each replica write = extra disk I/O + network transfer + translog fsync
    At 1M docs/sec: replica forwarding can add 50–200% I/O overhead
    After bulk load: re-enable replicas → Elasticsearch recovers them in bulk (faster)

  Why disable refresh?
    With refresh_interval: "1s" at 100K docs/sec:
      Every second: flush 100K docs from in-memory buffer to a new segment
      100K docs → segment build = 50ms CPU
      After 60 seconds: 60 segments per shard → slow searches, merge pressure
    With refresh_interval: "-1":
      All 6M docs accumulate in the in-memory buffer
      Zero segment creations during load
      One refresh at the end → one segment → optimal for initial loads

  Phase 2: Bulk indexing
  ──────────────────────────────────────────────────────────
  // Use the _bulk API — never send one document at a time:
  POST /loans/_bulk
  { "index": { "_id": "L001" } }
  { "status": "approved", "amount": 50000, "borrower": "Ravi Sharma" }
  { "index": { "_id": "L002" } }
  { "status": "pending",  "amount": 75000, "borrower": "Priya Mehta" }
  // ...more documents

  Optimal bulk request size:
    Too small: overhead per HTTP request dominates
    Too large: memory pressure, GC pauses, timeout risk
    Target: 5–15MB per bulk request, or 1,000–5,000 documents per request
    Tune empirically: measure throughput at 500, 1000, 5000 docs per bulk → pick peak

  Parallel bulk requests:
    One bulk thread per shard (number_of_primary_shards parallel threads)
    More threads than shards: contention with no throughput gain
    POST /loans/_bulk    // thread 1
    POST /loans/_bulk    // thread 2 ... up to num_shards

  Phase 3: Post-load restoration
  ──────────────────────────────────────────────────────────
  // Step 1: trigger a refresh to make all indexed docs searchable:
  POST /loans/_refresh

  // Step 2: optionally force-merge to optimize for read performance:
  POST /loans/_forcemerge?max_num_segments=1
  // Merges all segments into 1 per shard → optimal for read-only or read-heavy indexes
  // WARNING: expensive CPU + I/O operation; do not run on actively-written indexes
  // Wait for completion (can take minutes for large indexes)

  // Step 3: re-enable replicas and restore refresh_interval:
  PUT /loans/_settings
  {
    "index.refresh_interval": "1s",     // restore NRT behavior
    "index.number_of_replicas": 1       // Elasticsearch will now bulk-recover replicas
  }
  // Replica recovery: primary → replica sync runs in background
  // Cluster shows yellow (replicas initializing) → green (replicas ready)

  Expected throughput comparison:
  ┌───────────────────────────────────┬───────────────────────────────────────┐
  │ Configuration                     │ Indexing throughput (approximate)     │
  ├───────────────────────────────────┼───────────────────────────────────────┤
  │ Default settings (refresh 1s, 1r) │ 20,000 docs/sec                       │
  │ refresh=-1, replicas=0            │ 80,000–150,000 docs/sec               │
  │ refresh=-1, replicas=0 + forcemerge│ (post-load) optimal for reads        │
  └───────────────────────────────────┴───────────────────────────────────────┘

Additional bulk indexing settings:
  // Increase indexing buffer size (in-memory buffer before flush):
  PUT /_cluster/settings
  {
    "persistent": {
      "indices.memory.index_buffer_size": "20%"  // default: 10% of heap
    }
  }
  // More buffer → fewer implicit flushes during bulk load → higher throughput

  // Translog for bulk loads (accept risk of up to 5s loss):
  PUT /loans/_settings
  {
    "index.translog.durability": "async",
    "index.translog.sync_interval": "5s"
  }
  // Removes per-write fsync cost → significant improvement at high write rates
  // Restore to "request" after bulk load if strong durability is needed
```

## Section 7: Segments, Merges, and Search Performance

**Q9. How does segment count affect NRT search performance and how do merges interact with ongoing searches?**
A: Every Lucene segment is an independent inverted index. A search query must visit all segments in a shard, merge their results, and return the combined result. More segments = more overhead per query. The NRT write pattern (frequent small refreshes) naturally creates many segments, which is why background merging is essential to maintain search performance:

```
Segment proliferation from NRT writes:

  With refresh_interval: "1s" and 100 writes/second:
    Each refresh: 1 new small segment (100 docs)
    After 10 seconds: 10 segments per shard
    After 1 minute: ~60 segments per shard
    After 1 hour: potentially 3,600 segments per shard (before merging)

  Cost of high segment count:
    Query execution: per-segment overhead × segment_count
    Each segment needs:
      A separate dictionary lookup (FST traversal) per term
      A separate bitset for live docs
      A separate doc values column open
    For 1,000 segments: ~10× more per-query overhead vs 100 segments
    For scoring: merge sort of posting lists from all segments → O(N × segments)

Merge policy — Elasticsearch's automatic segment management:
  Lucene's TieredMergePolicy (default):
    Groups segments into "tiers" by size
    Within a tier: merge N segments into 1 when there are too many
    Default max_merge_at_once: 10 (merge up to 10 segments at a time)
    Default segments_per_tier: 10 (trigger merge when tier has > 10 segments)
    Result: O(log N) total segments for N refreshes → segments grow logarithmically

  Merge visualized:
    After 10 refreshes:
    [1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB]
    → merge → [10MB]                       (1 segment, 10× bigger)

    After 10 more refreshes:
    [10MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB][1MB]
    → merge → [10MB][10MB]                 (2 segments)

    After enough time:
    [10MB][10MB][10MB]...[10MB]
    → merge → [100MB]                      (1 large segment)

  In practice: a healthy shard has ~10–50 segments depending on write rate and merge speed

Merges and ongoing searches — NO disruption:
  Merges happen in the BACKGROUND on merge threads (not search threads)
  During a merge:
    OLD segments: still open → still searched → existing searches continue unaffected
    NEW merged segment: built in a temp file → not yet visible to readers
    After merge completes: new segment opened, old segments closed atomically
    Readers using old segments: complete their search normally
    New readers: use the merged segment → fewer segments to search
  Result: merges are transparent to search — no query interruption, no downtime

Force merge — manual optimization for read-heavy indexes:
  POST /loans/_forcemerge?max_num_segments=1
  // Merges ALL segments per shard down to 1
  // Optimal for: read-only indexes (historical data, completed time periods)
  // Danger: during force merge, significant CPU + I/O
  //         never run on actively-written indexes (merges and writes conflict)
  //         new writes during a force merge → still create new segments → need another merge

  POST /loans/_forcemerge?max_num_segments=5&only_expunge_deletes=true
  // only_expunge_deletes: merge only to reclaim space from deleted documents
  // Does NOT fully consolidate segments (less I/O than full forcemerge)

Checking segment health:
  GET /loans/_segments
  {
    "indices": {
      "loans": {
        "shards": {
          "0": [{
            "num_committed_segments": 15,
            "num_search_segments": 15,
            "segments": {
              "_0": {
                "generation": 0,
                "num_docs":     84321,
                "deleted_docs": 1200,    // space reclaimed at next merge
                "size_in_bytes": 45000000,
                "committed":    true,    // flushed to disk
                "search":       true     // open for search
              }
              // ... more segments
            }
          }]
        }
      }
    }
  }

  Health indicators:
  Segment count > 200 per shard    → merge is falling behind → increase merge threads
  deleted_docs / num_docs > 20%    → space waste → consider forcemerge with expunge_deletes
  num_search_segments > num_committed → refreshes happening faster than flushes (normal, OK)

Merge thread configuration:
  // Default: merge uses floor(sqrt(cpu_count)) threads per node
  // On 8-core machine: floor(sqrt(8)) = 2 merge threads

  PUT /_cluster/settings
  {
    "persistent": {
      "indices.merge.scheduler.max_thread_count": 4  // more threads = faster merges
    }
  }
  // Tradeoff: more merge threads = faster segment consolidation but more I/O competition
  // On SSDs: can increase safely (SSD handles parallel I/O well)
  // On HDDs: keep low (HDDs suffer from parallel seeks)
```

**Q13. "Explain why disabling `refresh_interval` (`-1`) alone does not make data durable, and why setting `translog.durability=async` is a separate concern."**

```javascript
// These two settings control DIFFERENT properties:
//
// refresh_interval: controls SEARCH VISIBILITY (when docs become searchable)
// translog.durability: controls WRITE DURABILITY (whether data survives a crash)
//
// They are orthogonal — changing one does not affect the other:

// Scenario A: refresh_interval=-1, translog.durability=request (default)
PUT /loans/_settings
{
  "index.refresh_interval": "-1",
  "index.translog.durability": "request"  // default
}
// Index a document:
PUT /loans/_doc/L001 { "amount": 50000 }
// → Translog: fsynced immediately (durability=request) → DURABLE ✓
// → In-memory buffer: NOT a segment yet
// → Searchable: NO (refresh disabled)
// If node crashes NOW → data is SAFE (translog on disk) → will be recovered
// After node restarts → translog replayed → doc in memory → refresh needed for search

// Scenario B: refresh_interval=1s, translog.durability=async
PUT /loans/_settings
{
  "index.refresh_interval": "1s",
  "index.translog.durability": "async",
  "index.translog.sync_interval": "5s"
}
// Index a document:
PUT /loans/_doc/L001 { "amount": 50000 }
// → Translog: NOT yet fsynced (async mode, waiting for 5s)
// → In-memory buffer: will become a segment at T+1s
// → Searchable: YES at T+1s (refresh creates a segment)
// If node loses POWER (not graceful shutdown) at T+2s:
//   The segment is in OS cache (not fsynced yet — that's flush, not refresh)
//   The translog is NOT fsynced yet (async, 5s interval)
//   → DATA LOSS: the last 2 seconds of acknowledged writes are GONE

// The two settings control entirely different properties:
// ┌─────────────────────────────────────────────────────────────────────────┐
// │ refresh_interval = "-1"  → documents are NOT searchable (by search API)│
// │                          → documents ARE durable if translog is sync    │
// │                                                                         │
// │ translog.durability = "async" → documents ARE searchable after refresh  │
// │                               → documents are NOT fully durable         │
// └─────────────────────────────────────────────────────────────────────────┘

// For bulk loading where you want BOTH fast AND durable:
PUT /loans/_settings
{
  "index.refresh_interval": "-1",          // not searchable during load (OK)
  "index.translog.durability": "request"   // every write is durable (safe)
}
// Throughput: limited by per-write fsync (translog) — still ~30K-50K docs/sec
// Safety: zero acknowledged write loss on crash

// For bulk loading where speed is paramount and you accept up to 60s of data loss risk:
PUT /loans/_settings
{
  "index.refresh_interval": "-1",
  "index.translog.durability": "async",
  "index.translog.sync_interval": "60s"
}
// Throughput: highest possible (no fsync cost per write)
// Safety: if node crashes, last 60s of writes to this index may be lost
// Acceptable for: data migration where source still exists (can re-index lost docs)
// NOT acceptable for: primary data store, no re-run option
```

## Section 9: Advanced NRT Patterns

**Q14. How does the `index.search.idle.after` setting interact with NRT behavior, and when does Elasticsearch automatically stop refreshing?**
A: Elasticsearch has an optimization where indexes that have received no search requests for a configured idle period pause their automatic refresh. This prevents wasting resources on indexes that nobody is querying — especially useful in multi-tenant setups with many inactive indexes. A search request wakes the index and triggers an immediate refresh:

```
Search idle optimization:

  Default: index.search.idle.after: "30s"
  After 30 seconds with no search requests:
    → Elasticsearch pauses the automatic refresh scheduler for this index
    → Writes still go to translog + in-memory buffer (durability unaffected)
    → No new segments are created
    → Memory is saved (no segment building, no IndexReader churn)

  When a search request arrives on an idle index:
    → Elasticsearch triggers an IMMEDIATE refresh before executing the search
    → This refresh includes all accumulated writes since the index went idle
    → Search sees all current data
    → Automatic refresh scheduling resumes

  Implication for NRT:
    Idle index with 1,000 accumulated writes from the last 5 minutes:
    Search arrives → refresh triggered → ALL 1,000 writes become searchable
    No data is lost — the first search just pays a one-time refresh cost

  Disable idle optimization (always refresh on schedule):
  PUT /loans/_settings
  {
    "index.search.idle.after": "-1"   // never go idle
  }
  // Use for: indexes that are written to continuously but searched infrequently
  // (you want data searchable even when nobody is querying)

  Check idle status:
  GET /loans/_stats
  {
    "indices": {
      "loans": {
        "primaries": {
          "refresh": {
            "total":              1250,
            "external_total":     890,   // externally triggered refreshes (manual or idle wake-up)
            "listeners":          0
          }
        }
      }
    }
  }
  // external_total high relative to total → many idle wake-ups (frequent cold starts)
  // Consider lowering index.search.idle.after for those indexes

Multi-tenant scenario — 1,000 tenant indexes, each lightly used:
  With idle optimization (default):
    Only active indexes consume refresh resources
    10 active indexes: 10 refresh cycles/second → lightweight
    990 idle indexes: 0 refresh cycles/second → saves significant CPU

  Without idle optimization:
    All 1,000 indexes refresh every second → 1,000 segment create operations/second
    Most of them for empty buffers → wasted work
    High background CPU → degrades search latency for active indexes
```

**Q15. What is a "refresh listener" and how does it make `?refresh=wait_for` non-blocking on the server?**
A: Rather than holding a thread blocked while waiting for the next refresh, `?refresh=wait_for` uses an asynchronous listener registered against the index's refresh cycle. This allows the server thread to be released immediately after writing, with a callback invoked when the refresh completes — a classic non-blocking I/O pattern:

```
Refresh listener internals:

  Naive implementation of "wait for refresh" (blocking):
    Write to translog + buffer
    Thread.sleep(time_until_next_refresh)    // thread held idle
    After refresh: send response
    Problem: at 10,000 concurrent wait_for requests → 10,000 blocked threads → OOM

  Elasticsearch's implementation (non-blocking listener):
    Write to translog + buffer
    Register a RefreshListener: { callback: sendResponse, version: currentVersion }
    Release the server thread immediately (back to thread pool)
    When the refresh runs:
      RefreshListener.afterRefresh() is called
      Checks: is the version I'm waiting for now in a segment? YES
      Calls: callback → sendResponse → client receives 200 OK
    Result: zero threads held during the wait period

  The listener registration is per-shard:
    Each shard maintains a list of pending RefreshListeners
    After each refresh: all listeners for that shard are notified
    Thread cost during wait: zero (no thread is blocked)

  Monitoring pending listeners:
  GET /loans/_stats/refresh
  {
    "refresh": {
      "listeners": 247    // 247 requests currently waiting for the next refresh
    }
  }
  // High listener count → many ?refresh=wait_for requests → refresh may be overwhelmed
  // If listeners accumulate: requests are waiting longer than refresh_interval → investigate

  What happens if the shard goes away while waiting?
    Primary shard fails during a wait_for:
    → Listener fires with an error
    → Client receives a connection error / 5xx
    → Client should retry (the write may or may not have been committed)
    → Use idempotent writes (_id specified) to safely retry

  Timeout for wait_for:
    No explicit timeout in the API for wait_for
    Uses the global request timeout if set: ?timeout=30s
    If refresh doesn't happen within timeout: client receives a timeout error
    The document is still indexed (durable in translog) — just wasn't searchable yet
    Re-running the search after the timeout will find the document

  When too many wait_for requests degrade the system:
    Each refresh wakes up ALL pending listeners: O(listeners) overhead at refresh time
    At 10,000 concurrent wait_for requests with 1s refresh:
      Every second: 10,000 listener callbacks fired at once
      Creates a thundering herd → refresh latency spike → listeners wait longer
    Fix: increase refresh_interval slightly (e.g., "2s") to reduce thundering herd frequency
         or avoid wait_for at this scale → redesign to use GET by ID after writes
```

**Tip for interviews:** Five things separate strong candidates on Elasticsearch NRT: (1) explaining precisely **why Elasticsearch is "near" rather than real-time** — making a document searchable requires building a Lucene segment (sort terms, compress posting lists, build FST), which costs 1–5ms of CPU; doing this on every write at high throughput is impossible, so Elasticsearch batches writes in an in-memory buffer and creates one segment per `refresh_interval` (default 1 second); (2) being precise about **the two independent properties of a write** — durability (translog, controlled by `translog.durability`) and search visibility (segments, controlled by `refresh_interval`); a document can be durable but not searchable (in translog, buffer not yet refreshed), or searchable but not fully durable on disk (in OS cache, not yet flushed); these are orthogonal settings and the most common confusion is conflating them; (3) knowing the **two read paths and why GET by ID is real-time** — `GET /{index}/_doc/{id}` checks the translog, making it real-time (the document is always found immediately after a successful write); `_search` only reads Lucene segments (which require a refresh), making it NRT; this asymmetry explains the common "I indexed it but the search doesn't find it" bug; (4) understanding the **three `?refresh` parameter options and their cost model** — `?refresh=false` (default, no overhead, NRT delay), `?refresh=wait_for` (non-blocking listener, waits for next scheduled refresh, no extra segment created — correct for moderate-volume user-triggered writes), and `?refresh=true` (immediately triggers a full shard refresh — catastrophic at scale because it creates one segment per write, exploding segment count and saturating CPU); (5) the **bulk indexing optimization pattern** — disabling `refresh_interval` (`"-1"`) and replicas (`0`) before a bulk load, then restoring them after with a single manual refresh and optional forcemerge — and why each of those three changes helps (no segment churn, no replica forwarding overhead, one final segment per shard respectively).
