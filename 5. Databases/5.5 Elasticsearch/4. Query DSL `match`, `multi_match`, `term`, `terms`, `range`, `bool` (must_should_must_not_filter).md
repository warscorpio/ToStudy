# Elasticsearch Query DSL: `match`, `multi_match`, `term`, `terms`, `range`, `bool` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Query DSL and what is the fundamental distinction between queries that affect relevance scoring and those that do not?**

A: The Elasticsearch Query DSL (Domain Specific Language) is a JSON-based language for expressing search requests. Every search is expressed as a JSON document sent in the request body of a `GET` or `POST` to `_search`. The DSL provides two fundamentally different modes of operation — a distinction that is the single most important concept in Elasticsearch performance:

```
Query context  → Asks "how well does this document match?" → calculates a relevance score (_score)
Filter context → Asks "does this document match?"         → YES or NO, no score calculated

This distinction determines:
  1. Whether a _score is computed (expensive CPU operation)
  2. Whether results can be cached by Elasticsearch's filter cache
```

```json
GET /products/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "match": { "description": "wireless keyboard" }
        }
      ],
      "filter": [
        { "term":  { "inStock": true } },
        { "range": { "price": { "gte": 50, "lte": 300 } } }
      ]
    }
  }
}
```

```
The anatomy of the above:
  "must" (query context):
    match on "description" → Elasticsearch tokenises "wireless keyboard",
    computes TF-IDF / BM25 relevance score for each document.
    Documents with "wireless" and "keyboard" appearing frequently score higher.

  "filter" (filter context):
    term on "inStock" → YES/NO: is inStock exactly true?
    range on "price"  → YES/NO: is price between 50 and 300?
    NO scoring involved for these clauses.
    Results are CACHED by Elasticsearch in a bitset per segment.

Performance implication:
  Filters are dramatically cheaper than queries:
  - No TF-IDF/BM25 calculation
  - Bitset cached after first use → subsequent requests: ~1ms
  - Only documents passing the filter enter the query phase
  - Always put structured conditions (exact values, ranges, booleans) in 'filter', not 'must'
```

The `_score` field:

```json
// Response includes _score for each document:
{
  "hits": {
    "hits": [
      {
        "_index":  "products",
        "_id":     "abc123",
        "_score":  4.782,          ← BM25 relevance score (higher = more relevant)
        "_source": {
          "name":    "Mechanical Wireless Keyboard",
          "description": "Premium wireless keyboard with mechanical switches",
          "price":   199.99,
          "inStock": true
        }
      }
    ]
  }
}
// _score is null for documents in pure filter context (no query context applied)
```

**Q2. How does Elasticsearch analyse text — what is the difference between analysed and non-analysed fields, and why does it matter for which query you choose?**

A: Elasticsearch processes text through an analysis chain before indexing. The analysis chain — tokeniser plus token filters — breaks text into searchable tokens. Whether a field is analysed determines which query types work correctly on it:

```
Field type 'text'    → ANALYSED → use match, match_phrase, multi_match
Field type 'keyword' → NOT analysed → use term, terms, prefix, wildcard
```

```
Input text: "Apple MacBook Pro 16-inch (2023)"

Analysis with 'standard' analyser:
  Tokeniser:    ["Apple", "MacBook", "Pro", "16", "inch", "2023"]
  Lowercase:    ["apple", "macbook", "pro", "16", "inch", "2023"]
  Stored in:    inverted index as those 6 tokens

Mapping:
  "name":        { "type": "text"    }  ← analysed: stored as ["apple","macbook","pro",...]
  "name.keyword":{ "type": "keyword" }  ← raw: stored as "Apple MacBook Pro 16-inch (2023)"
```

```json
// Elasticsearch default mapping for 'name' field:
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "fields": {
          "keyword": {
            "type":        "keyword",
            "ignore_above": 256
          }
        }
      }
    }
  }
}
// name         → analysed text field → use match, match_phrase, multi_match
// name.keyword → raw keyword field   → use term, terms, sort, aggregations
```

The mismatch problem — using the wrong query type on the wrong field type:

```json
// WRONG: term query on an analysed field (almost never what you want)
{
  "query": {
    "term": { "name": "Apple MacBook Pro" }
  }
}
// This looks for the EXACT token "Apple MacBook Pro" in the inverted index.
// But the index stored "apple", "macbook", "pro" as separate lowercase tokens.
// "Apple MacBook Pro" (with capital A, space-delimited) is NOT a token → 0 results.

// CORRECT: match query on an analysed field (analyses the query string first)
{
  "query": {
    "match": { "name": "Apple MacBook Pro" }
  }
}
// Elasticsearch analyses "Apple MacBook Pro" → ["apple", "macbook", "pro"]
// Searches for those tokens → finds the document

// CORRECT: term query on the keyword sub-field (exact, no analysis)
{
  "query": {
    "term": { "name.keyword": "Apple MacBook Pro 16-inch (2023)" }
  }
}
// Exact match against the raw stored value → works correctly
```

## Section 2: Full-Text Queries

**Q3. How does `match` work — what options does it have and when is each appropriate?**

A: `match` is the standard full-text query. It analyses the query string using the same analyser as the target field, then searches for those tokens in the inverted index. Documents containing more of the tokens, and containing them more frequently, score higher:

```json
// Basic match — searches one field:
GET /products/_search
{
  "query": {
    "match": {
      "description": "wireless mechanical keyboard"
    }
  }
}
// Equivalent to: analyse "wireless mechanical keyboard"
//   → ["wireless", "mechanical", "keyboard"]
// Find documents containing these tokens (default operator: OR)
// Score by BM25: documents with all three tokens score highest

// With explicit operator — controls whether ALL or ANY tokens must match:
{
  "query": {
    "match": {
      "description": {
        "query":    "wireless mechanical keyboard",
        "operator": "and"
        // operator: "and" → all three tokens must be present
        // operator: "or"  → (default) at least one token must be present
      }
    }
  }
}

// minimum_should_match — a middle ground between AND and OR:
{
  "query": {
    "match": {
      "description": {
        "query":                "wireless mechanical keyboard fast",
        "minimum_should_match": 3
        // At least 3 of the 4 tokens must match
        // Can also use: "75%" (percentage), "3<75%" (if > 3 tokens, 75% must match)
      }
    }
  }
}

// fuzziness — allow typos (Levenshtein edit distance):
{
  "query": {
    "match": {
      "description": {
        "query":     "keybord",     ← typo: "keybord" instead of "keyboard"
        "fuzziness": "auto"
        // "auto": 0 edits for 1-2 chars, 1 edit for 3-5 chars, 2 edits for 6+ chars
        // "1": exactly 1 character substitution/insertion/deletion allowed
        // "2": exactly 2 edits
      }
    }
  }
}

// boost — weight this field's contribution to the overall score:
{
  "query": {
    "match": {
      "description": {
        "query": "wireless keyboard",
        "boost": 2.0
        // Score contribution from this match is multiplied by 2.0
        // Useful in bool queries to weight some fields more than others
      }
    }
  }
}
```

`match_phrase` — word order and adjacency matter:

```json
// match_phrase: all words must appear in this exact order, adjacent
{
  "query": {
    "match_phrase": {
      "description": "wireless keyboard"
    }
  }
}
// Matches: "ergonomic wireless keyboard with palm rest"  ✓
// Matches: "the wireless keyboard includes a USB dongle" ✓
// No match: "keyboard, wireless type"                    ✗ (wrong order)
// No match: "wireless mechanical keyboard"               ✗ (not adjacent — "mechanical" between)

// slop — allows words to be N positions apart (out of order):
{
  "query": {
    "match_phrase": {
      "description": {
        "query": "wireless keyboard",
        "slop":  1
        // Allow 1 intermediate word: "wireless [X] keyboard" would match
        // slop: 2 → "wireless [X] [Y] keyboard" would match
      }
    }
  }
}
```

**Q4. What is `multi_match` and what are the different `type` options — how do they affect scoring?**

A: `multi_match` runs a `match` query across multiple fields simultaneously. The `type` parameter controls how scores from individual field matches are combined into the final document score:

```json
// Basic multi_match — search the same query across multiple fields:
{
  "query": {
    "multi_match": {
      "query":  "wireless keyboard",
      "fields": ["name", "description", "tags"]
    }
  }
}

// Field boosting with ^ syntax — weight some fields more:
{
  "query": {
    "multi_match": {
      "query":  "wireless keyboard",
      "fields": [
        "name^3",           ← name match is 3× more valuable
        "description^1.5",  ← description match is 1.5× more valuable
        "tags"              ← tags match has default weight (1.0)
      ]
    }
  }
}

// Wildcard field names — match all *_title fields:
{
  "query": {
    "multi_match": {
      "query":  "wireless keyboard",
      "fields": ["*_description", "name*"]
    }
  }
}
```

The `type` parameter — how multi-field scores are combined:

```json
// type: "best_fields" (DEFAULT)
// Score = the score of the BEST single matching field
// Good for: most queries — you care about the strongest match, not the average
// Example: "wireless keyboard" matches name perfectly → name score dominates
{
  "query": {
    "multi_match": {
      "query": "wireless keyboard",
      "fields": ["name", "description"],
      "type":  "best_fields"
      // Also supports: "tie_breaker" to add a fraction of other fields' scores
      // tie_breaker: 0.3 → final score = best_field_score + 0.3 × (other_field_scores)
    }
  }
}

// type: "most_fields"
// Score = sum of ALL field scores
// Good for: when the same concept is described in multiple fields
// Example: "name" and "name.english" (stemmed) both contain the concept
{
  "query": {
    "multi_match": {
      "query": "keyboards",
      "fields": ["name", "name.english"],
      "type":  "most_fields"
      // "keyboards" matches "name" (exact) AND "name.english" (stemmed: "keyboard")
      // most_fields adds both scores → documents with both field matches score higher
    }
  }
}

// type: "cross_fields"
// Treats all fields as one large field, tokens must appear across the combined field space
// Good for: structured data that is split across fields (person first/last name)
{
  "query": {
    "multi_match": {
      "query": "John Smith",
      "fields": ["first_name", "last_name"],
      "type":  "cross_fields"
      // "John" must match in SOME field, "Smith" must match in SOME field
      // Doesn't require both tokens in the same field
      // best_fields would fail: "John Smith" exact phrase not in either field alone
    }
  }
}

// type: "phrase"
// Runs a match_phrase across multiple fields — phrase must appear in at least one field:
{
  "query": {
    "multi_match": {
      "query": "wireless keyboard",
      "fields": ["name", "description"],
      "type":  "phrase",
      "slop":  1
    }
  }
}

// type: "bool_prefix"
// Used for search-as-you-type: full match on all terms except the last, prefix on the last:
{
  "query": {
    "multi_match": {
      "query": "wireless key",     ← user is still typing "key..."
      "fields": ["name", "description"],
      "type":  "bool_prefix"
      // Finds: "wireless keyboard", "wireless keypad", "wireless key organiser"
    }
  }
}
```

## Section 3: Term-Level Queries

**Q5. What are `term` and `terms` queries — when must you use them instead of `match`?**

A: `term` and `terms` are exact-value queries that do not analyse the query string. They operate on the raw token stored in the inverted index. Use them for structured data — IDs, status values, categories, booleans, numbers — not for full-text fields:

```json
// term: exact match on ONE value (no analysis applied to the query value)
GET /orders/_search
{
  "query": {
    "term": {
      "status": {
        "value": "pending"
        // Searches for the EXACT token "pending" in the status field
        // No analysis: "Pending", "PENDING" would NOT match
      }
    }
  }
}

// Shorthand syntax (equivalent):
{
  "query": {
    "term": { "status": "pending" }
  }
}

// term on keyword fields — common patterns:
{
  "query": {
    "term": { "userId": "user-uuid-abc-123" }
    // userId is a keyword field → exact UUID match
  }
}

{
  "query": {
    "term": { "isActive": true }
    // boolean field → exact true/false match
  }
}

{
  "query": {
    "term": { "category.keyword": "Electronics" }
    // 'category' is a text field with a keyword sub-field
    // 'category.keyword' stores the raw unanalysed string
  }
}

// terms: exact match on MULTIPLE values (equivalent to SQL's IN clause)
GET /orders/_search
{
  "query": {
    "terms": {
      "status": ["pending", "processing", "shipped"]
      // Returns documents where status is ANY of these values
    }
  }
}

// terms with boost:
{
  "query": {
    "terms": {
      "category": ["Electronics", "Computers"],
      "boost": 1.5
    }
  }
}

// terms lookup — look up the values from another document (dynamic terms):
// Useful for: "find products in categories the current user follows"
{
  "query": {
    "terms": {
      "category": {
        "index":   "users",
        "id":      "user-123",
        "path":    "followedCategories"
        // Retrieves the followedCategories array from user document "user-123"
        // Then searches for products where category matches any of those values
        // Avoids client-side round-trip: no need to fetch user doc first, then search
      }
    }
  }
}
```

The term-vs-match confusion — the most common Elasticsearch mistake:

```json
// Scenario: a 'status' field that was mapped as 'text' (not 'keyword')
// (common in early Elasticsearch setups without explicit mappings)

// WRONG — term on analysed 'status' text field:
{ "query": { "term": { "status": "Pending" } } }
// "Pending" is NOT a token — the analyser stored "pending" (lowercase)
// Result: 0 documents found (silent failure — no error returned!)

// CORRECT — match on analysed text field:
{ "query": { "match": { "status": "Pending" } } }
// Analyses "Pending" → "pending" → finds the token

// BEST — use keyword field for status (should always be keyword):
// Mapping: { "status": { "type": "keyword" } }
{ "query": { "term": { "status": "Pending" } } }
// Works perfectly: exact match on raw value
// AND benefits from filter cache when used in bool.filter
```

**Q6. How does the `range` query work — what operators does it support and what are its performance characteristics?**

A: `range` queries match documents where a numeric, date, or string field falls within specified bounds. They are efficient when used in filter context (cached) and work across numeric, date, and keyword field types:

```json
// Numeric range:
{
  "query": {
    "range": {
      "price": {
        "gte": 100,    ← greater than or equal (>=)
        "lte": 500     ← less than or equal (<=)
        // gt:  strictly greater than (>)
        // lt:  strictly less than (<)
      }
    }
  }
}

// Date range — multiple date formats supported:
{
  "query": {
    "range": {
      "createdAt": {
        "gte": "2024-01-01",
        "lt":  "2025-01-01",
        "format": "yyyy-MM-dd"
        // Elasticsearch parses the date strings using this format
      }
    }
  }
}

// Date math — relative dates:
{
  "query": {
    "range": {
      "createdAt": {
        "gte": "now-30d/d",    ← 30 days ago, rounded to day boundary
        "lte": "now/d"         ← today, rounded to day boundary
        // Date math syntax:
        // now     = current timestamp
        // +/-Nd   = add/subtract N days
        // +/-Nw   = weeks, +/-Nm = months, +/-Ny = years
        // /d      = round down to day, /M = month, /y = year
        // "now-7d": exactly 7 days ago (NOT rounded)
        // "now-7d/d": 7 days ago rounded to midnight (cacheable — same value all day)
      }
    }
  }
}

// String range — lexicographic ordering:
{
  "query": {
    "range": {
      "name.keyword": {
        "gte": "A",
        "lt":  "M"
        // Matches products whose name starts with A-L
        // Rarely useful — more common for date ranges
      }
    }
  }
}

// boost — score contribution from this range (only in query context, not filter):
{
  "query": {
    "range": {
      "rating": {
        "gte":   4.0,
        "boost": 1.5
        // Documents with rating >= 4.0 get 1.5× score boost
      }
    }
  }
}
```

Performance and caching with `range`:

```json
// WRONG: range in 'must' (query context) → no caching
{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "keyboard" } },
        { "range": { "price": { "gte": 100, "lte": 500 } } }
        // price range in 'must' → calculates score, no cache → slow
      ]
    }
  }
}

// CORRECT: range in 'filter' (filter context) → cached
{
  "query": {
    "bool": {
      "must":   [{ "match": { "description": "keyboard" } }],
      "filter": [{ "range": { "price": { "gte": 100, "lte": 500 } } }]
      // price range in 'filter' → YES/NO, no score → CACHED in bitset
      // First query: builds and caches the bitset → ~5ms
      // Subsequent queries with same range: bitset lookup → <1ms
    }
  }
}

// Date range caching tip: use rounded dates for better cache reuse
// BAD (never cached — 'now' changes every millisecond):
{ "range": { "createdAt": { "gte": "now-30d" } } }

// GOOD (cacheable — value changes once per day):
{ "range": { "createdAt": { "gte": "now-30d/d" } } }
// The /d rounding makes the value constant throughout the day
// → Elasticsearch can cache the bitset for the entire day
```

## Section 4: The Bool Query

**Q7. How does the `bool` query work — what are the four clauses and how do they affect scoring and filtering?**

A: `bool` is the primary compound query — it combines multiple queries using boolean logic. Each of its four clauses has distinct behaviour regarding scoring and document inclusion:

```json
{
  "query": {
    "bool": {
      "must":     [...],      ← MUST match; contributes to _score (query context)
      "filter":   [...],      ← MUST match; does NOT contribute to _score (filter context)
      "should":   [...],      ← SHOULD match; contributes to _score; may be required
      "must_not": [...]       ← MUST NOT match; excluded from results; no _score contribution
    }
  }
}
```

Each clause in depth:

```json
// ── must: required + scoring ──────────────────────────────────────────────────
// Document MUST match ALL must clauses to be included in results.
// Each must clause contributes to the _score.
// Use for: conditions that affect RELEVANCE (text search, fuzzy match).
{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "wireless keyboard" } },
        { "match": { "brand": "Logitech" } }
        // Both must match; scores from both are SUMMED for the final _score
      ]
    }
  }
}

// ── filter: required + no scoring ─────────────────────────────────────────────
// Document MUST match ALL filter clauses to be included in results.
// Filter clauses do NOT contribute to _score (score remains from must/should).
// Filter results are CACHED by Elasticsearch.
// Use for: structured conditions (exact values, ranges, booleans, dates).
{
  "query": {
    "bool": {
      "must":   [{ "match": { "description": "wireless keyboard" } }],
      "filter": [
        { "term":  { "inStock": true } },
        { "range": { "price": { "gte": 50, "lte": 300 } } },
        { "term":  { "category.keyword": "Electronics" } }
        // These three conditions must all be true, but don't affect the score
      ]
    }
  }
}

// ── should: optional + scoring boost ─────────────────────────────────────────
// Documents matching should clauses score HIGHER, but non-matching docs are
// NOT excluded (when used alongside must or filter).
// When used ALONE (no must, no filter): at least one should must match.
{
  "query": {
    "bool": {
      "must":   [{ "match": { "description": "keyboard" } }],
      "should": [
        { "match": { "description": "wireless" } },
        { "match": { "description": "mechanical" } },
        { "term":  { "isFeatured": true } }
        // Documents matching these score HIGHER — but they don't have to match
      ]
    }
  }
}

// minimum_should_match — controls how many should clauses must match:
{
  "query": {
    "bool": {
      "should": [
        { "match": { "name": "wireless" } },
        { "match": { "name": "keyboard" } },
        { "match": { "name": "mechanical" } }
      ],
      "minimum_should_match": 2
      // At least 2 of the 3 should clauses must match
      // Without minimum_should_match AND no must/filter:
      //   → default is 1 (at least one should must match)
      // Without minimum_should_match WITH must or filter:
      //   → default is 0 (should clauses are purely optional boosters)
    }
  }
}

// ── must_not: excluded + no scoring ──────────────────────────────────────────
// Documents matching ANY must_not clause are EXCLUDED from results.
// Must_not runs in filter context: no score contribution, and CAN be cached.
{
  "query": {
    "bool": {
      "must":     [{ "match": { "description": "keyboard" } }],
      "must_not": [
        { "term":  { "status": "discontinued" } },
        { "range": { "price": { "gt": 1000 } } }
        // Exclude discontinued products and anything over $1000
      ]
    }
  }
}
```

**Q8. How do you nest `bool` queries — and why does nesting allow you to build complex query logic?**

A: `bool` queries can be nested arbitrarily — a clause within a `bool` can itself be a `bool`. This composability allows expression of any boolean logic:

```json
// Example: find keyboards that are either:
// A) wireless AND under $200, OR
// B) mechanical AND highly rated

{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "keyboard" } }   ← outer must: must be a keyboard
      ],
      "should": [
        {
          "bool": {
            "must": [                                  ← inner bool for option A
              { "match": { "description": "wireless" } },
              { "range": { "price": { "lte": 200 } } }
            ]
          }
        },
        {
          "bool": {
            "must": [                                  ← inner bool for option B
              { "match": { "description": "mechanical" } },
              { "range": { "rating": { "gte": 4.5 } } }
            ]
          }
        }
      ],
      "minimum_should_match": 1   ← at least one of A or B must match
    }
  }
}

// Nested filter context — filtering on nested sub-documents:
// Data model: each product has an array of variants
// products/_doc/1:
// { "name": "Keyboard", "variants": [
//     { "color": "black", "size": "TKL", "stock": 5 },
//     { "color": "white", "size": "full", "stock": 0 }
//   ]
// }

// WRONG: matches if ANY variant has color=black AND ANY variant has stock > 0
// (might be different variants satisfying each condition)
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "variants.color": "black" } },
        { "range": { "variants.stock": { "gt": 0 } } }
      ]
    }
  }
}

// CORRECT: use nested query to enforce conditions on the SAME variant:
{
  "query": {
    "nested": {
      "path": "variants",
      "query": {
        "bool": {
          "filter": [
            { "term":  { "variants.color": "black" } },
            { "range": { "variants.stock": { "gt": 0 } } }
          ]
        }
      }
    }
  }
}
// Returns only documents where a SINGLE variant is black AND has stock > 0

// The scoring impact of nested bools:
// Outer bool score = sum of all must scores + fraction of should scores
// Inner bool is treated as a single clause → its internal score is one contribution
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "keyboard" } },        // score: 2.5
        {
          "bool": {
            "should": [
              { "match": { "name": "wireless" }  }, // score: 1.8
              { "match": { "name": "mechanical" }}  // score: 1.2
            ]
          }
        }                                           // inner bool score: max(1.8, 1.2) = 1.8
      ]
      // Total: 2.5 + 1.8 = 4.3
    }
  }
}
```

## Section 5: Practical Patterns

**Q9. How do you implement a product search page with filtering, relevance sorting, and facets using the bool query?**

A: A real product search combines full-text queries (for relevance), filter queries (for facets and structured conditions), and aggregations (for facet counts), all in one request:

```json
GET /products/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query":     "wireless keyboard",
            "fields":    ["name^3", "description^1.5", "tags"],
```

**Q10. How do you implement autocomplete and search-as-you-type using the Query DSL?**

A: Autocomplete requires prefix matching on partial tokens as users type. Elasticsearch provides several approaches with different accuracy/performance trade-offs:

```json
// ── Approach 1: match_bool_prefix (simplest, good for most cases) ────────────
// Analyses the input and applies prefix matching only to the LAST token:
GET /products/_search
{
  "query": {
    "match_bool_prefix": {
      "name": "wireless key"
      // Analyses: ["wireless", "key"]
      // Equivalent to:
      // bool: { should: [
      //   { term: { name: "wireless" } },   ← full match on "wireless"
      //   { prefix: { name: "key" } }       ← prefix match on last token
      // ]}
      // Matches: "wireless keyboard", "wireless keypad", "wireless key organiser"
    }
  }
}

// Multi-field version:
{
  "query": {
    "multi_match": {
      "query": "wireless key",
      "type":  "bool_prefix",
      "fields": ["name^3", "description"]
    }
  }
}

// ── Approach 2: search_as_you_type field type (most performant) ──────────────
// Requires special field mapping that pre-indexes n-grams:
// Mapping:
{
  "mappings": {
    "properties": {
      "name": {
        "type": "search_as_you_type"
        // Automatically creates:
        // name           → full text field
        // name._2gram    → 2-word shingles: ["wireless keyboard", "keyboard backlit"]
        // name._3gram    → 3-word shingles
        // name._index_prefix → prefix index for the last token
      }
    }
  }
}

// Query the search_as_you_type field:
{
  "query": {
    "multi_match": {
      "query": "wireless key",
      "type":  "bool_prefix",
      "fields": [
        "name",
        "name._2gram",
        "name._3gram",
        "name._index_prefix"
      ]
    }
  }
}
// Most relevant matches float to the top based on which sub-field matched

// ── Approach 3: completion suggester (fastest for pure autocomplete) ──────────
// Dedicated data structure (FST) optimised for prefix-based suggestion:
// Mapping:
{
  "mappings": {
    "properties": {
      "suggest": {
        "type": "completion",
        "analyzer": "simple"
      }
    }
  }
}

// Index with suggest field:
// PUT /products/_doc/1
// { "name": "Wireless Mechanical Keyboard",
//   "suggest": { "input": ["Wireless Mechanical Keyboard", "keyboard", "mechanical"] } }

// Query:
{
  "suggest": {
    "product_suggest": {
      "prefix": "wire",
      "completion": {
        "field": "suggest",
        "size":  10,
        "fuzzy": { "fuzziness": 1 }
      }
    }
  }
}
// Returns: ["Wireless Mechanical Keyboard", ...] — ultra-fast prefix lookup
// Trade-off: no relevance ranking, only prefix-based, requires special field
```

## Section 6: Scoring and Relevance

**Q11. How does BM25 scoring work in Elasticsearch — what factors affect the `_score` and how do you influence it?**

A: Elasticsearch uses BM25 (Best Match 25) as its default relevance scoring algorithm, replacing the older TF-IDF in Elasticsearch 5+. Understanding the factors lets you influence ranking without adding noisy data:

```
BM25 score for a term in a document:

score(term, doc) = IDF(term) × (TF(term, doc) × (k1 + 1))
                              ─────────────────────────────
                              TF(term, doc) + k1 × (1 - b + b × |doc| / avgDocLen)

Where:
  IDF(term)  = log(1 + (N - n + 0.5) / (n + 0.5))
               N = total documents in index
               n = documents containing the term
               Rare terms (small n) → high IDF → more impact on score

  TF(term, doc) = frequency of term in this document
               More occurrences = higher score, but with diminishing returns
               (unlike raw TF-IDF, BM25 caps the TF contribution)

  k1 = term frequency saturation parameter (default: 1.2)
       Higher = more influence from TF; lower = TF matters less

  b  = length normalisation parameter (default: 0.75)
       1.0 = full normalisation (short docs score higher for same term)
       0.0 = no normalisation (length ignored)

  |doc|     = number of tokens in this document
  avgDocLen = average tokens across all documents
```

Influencing scores with boosts and functions:

```json
// Method 1: boost at query time
{
  "query": {
    "bool": {
      "should": [
        { "match": { "name":        { "query": "keyboard", "boost": 3.0 } } },
        { "match": { "description": { "query": "keyboard", "boost": 1.0 } } }
      ]
    }
  }
}
// Name match is worth 3× more than description match

// Method 2: function_score — modify scores with functions
{
  "query": {
    "function_score": {
      "query": {
        "bool": {
          "must": [{ "match": { "description": "keyboard" } }]
        }
      },
      "functions": [
        {
          "filter": { "term": { "isFeatured": true } },
          "weight": 2.0
          // Featured products: score × 2.0
        },
        {
          "field_value_factor": {
            "field":    "reviewCount",
            "factor":   0.1,
            "modifier": "log1p",
            "missing":  1
            // Boost by log(1 + reviewCount × 0.1)
            // Products with more reviews score higher, but logarithmically
          }
        },
        {
          "gauss": {
            "price": {
              "origin": 150,   ← ideal price
              "scale":  50,    ← score drops by half at 50 away from origin
              "offset": 20,    ← no penalty within ±20 of origin
              "decay":  0.5    ← how fast score decays (0.5 = halves at 'scale')
            }
          }
          // Proximity boost: products near $150 score higher
        }
      ],
      "score_mode": "sum",      ← combine function scores by summing them
      "boost_mode": "multiply"  ← multiply original query score by combined function score
      // score_mode: sum | avg | min | max | multiply | first
      // boost_mode: replace | sum | avg | max | min | multiply
    }
  }
}
```

## Section 7: Scenario-Based Questions

**Q12. "A search for 'apple' is returning iPhone and MacBook results at the top, but none of the apple juice or apple snack products your food store sells. What's wrong and how do you fix it?"**

A:

```json
// Diagnosis: the query is:
GET /products/_search
{
  "query": {
    "match": { "name": "apple" }
  }
}
// Result: MacBook Air, iPhone 15, Apple Watch (all have high IDF for "apple")
// Missing: "Real Fruit Apple Juice", "Organic Apple Slices" (low IDF for "apple" as generic word)

// Root cause 1: missing category filter
// The index contains electronics AND food products in the same index
// No category restriction → electronics ("Apple" brand) match
// Fix: add a filter for the food section the user is browsing:
{
  "query": {
    "bool": {
      "must":   [{ "match": { "name": "apple" } }],
      "filter": [{ "term": { "category.keyword": "Food & Beverages" } }]
    }
  }
}

// Root cause 2: "Apple" (brand) vs "apple" (fruit) - capitalisation issue
// "Apple" (brand) was indexed as "apple" by the standard analyser
// "apple" (fruit) was also indexed as "apple"
// → They look identical to Elasticsearch at the token level

// Fix: use the category filter as the primary disambiguation
// AND boost food-specific terms:
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "apple" } }
      ],
      "should": [
        { "match": { "name": { "query": "juice snack food organic fruit", "boost": 2.0 } } }
      ],
      "filter": [
        { "term": { "category.keyword": "Food & Beverages" } }
      ]
    }
  }
}

// Root cause 3: search context — the query lacks context
// "apple" in a food store is almost always the fruit
// Add contextual synonyms at query time:
{
  "query": {
    "bool": {
      "should": [
        { "match": { "name": "apple" } },
        { "match": { "name": { "query": "apple fruit", "boost": 1.5 } } }
        // Boosts documents that also contain "fruit" alongside "apple"
      ]
    }
  }
}

// Best long-term fix: index-level synonym filter
// In the analyser: "apple => apple, apple_fruit" when category = food
// "apple" (brand) doesn't get the synonym
// Then query "apple_fruit" in food category for better disambiguation
```

**Q13. "Design a query that finds job listings where: the title must contain 'engineer' OR 'developer', the location is either 'remote' OR in ['Bangalore', 'Mumbai'], the salary range overlaps with [80000, 150000], and the company must NOT be in a blocked list."**

A:

```json
GET /jobs/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "bool": {
            "should": [
              { "match": { "title": "engineer"  } },
              { "match": { "title": "developer" } }
            ],
            "minimum_should_match": 1
          }
        }
      ],
      "filter": [
        {
          "bool": {
            "should": [
              { "term":  { "locationType.keyword": "remote" } },
              { "terms": { "city.keyword": ["Bangalore", "Mumbai"] } }
            ],
            "minimum_should_match": 1
          }
        },
        {
          "bool": {
            "must": [
              { "range": { "salaryMin": { "lte": 150000 } } },
              { "range": { "salaryMax": { "gte": 80000  } } }
            ]
          }
        }
      ],
      "must_not": [
        {
          "terms": {
            "companyId.keyword": ["blocked-company-1", "blocked-company-2", "blocked-company-3"]
          }
        }
      ]
    }
  },
  "sort": [
    { "_score":    { "order": "desc" } },
    { "postedAt":  { "order": "desc" } }
  ],
  "size": 20,
  "aggs": {
    "by_city": {
      "terms": { "field": "city.keyword", "size": 10 }
    },
    "salary_stats": {
      "stats": { "field": "salaryMin" }
    }
  }
}

// Explanation of each clause:

// MUST (query context):
//   Inner bool with should: title must contain "engineer" OR "developer"
//   Both match → both contribute to score, higher-matching document scores higher
//   minimum_should_match: 1 → at least one must match (otherwise doc is excluded)

// FILTER (filter context, cached):
//   Inner bool for location: remote OR (Bangalore OR Mumbai)
//     minimum_should_match: 1 → must match at least one of the location conditions
//   Inner bool for salary: overlapping range
//     salaryMin ≤ 150000 AND salaryMax ≥ 80000
//     This is the standard interval overlap check: [jobSalaryMin, jobSalaryMax] ∩ [80000, 150000] ≠ ∅
//     Equivalent to: NOT (jobSalaryMax < 80000 OR jobSalaryMin > 150000)

// MUST_NOT (filter context, cached):
//   Excludes documents where companyId is in the blocked list
//   Note: must_not runs in filter context despite similar semantics to must
//   → It is cached → efficient for a frequently updated blocked list

// Performance notes:
// filter clauses are cached → location and salary filters benefit from caching
// must clause (text search) is NOT cached → runs BM25 on each request
// must_not is cached → blocked company filter is fast
// Sort by _score then postedAt → relevance first, then recency for tied scores
```

## Quick Reference Table

| Query | Field type | Analyses input? | Use for | Scoring |
|---|---|---|---|---|
| `match` | `text` | Yes | Full-text search, one field | Yes (BM25) |
| `match_phrase` | `text` | Yes | Exact phrase, word order | Yes (BM25) |
| `multi_match` | `text` | Yes | Full-text search, multiple fields | Yes (BM25) |
| `match_bool_prefix` | `text` | Yes (prefix on last) | Search-as-you-type | Yes |
| `term` | `keyword`, `number`, `boolean`, `date` | **No** | Exact value match | Filter context: No |
| `terms` | `keyword`, `number`, etc. | **No** | Match any of N values (IN) | Filter context: No |
| `range` | `number`, `date`, `keyword` | **No** | Numeric/date ranges | Filter context: No |
| `bool` | Any | Depends on clauses | Combining queries | Depends on clause |

| Bool clause | Documents | Scoring | Filter cache | Use for |
|---|---|---|---|---|
| `must` | Must match ALL | Yes — contributes | No | Relevance-affecting text queries |
| `filter` | Must match ALL | No — excluded | **Yes** | Structured conditions (values, ranges) |
| `should` | Optional (boosts) | Yes — boosts | No | Optional relevance signals |
| `must_not` | Must match NONE | No — excluded | **Yes** | Exclusion conditions |

| Common mistake | Symptom | Fix |
|---|---|---|
| `term` on `text` field | 0 results for valid data | Use `match` on text; use `term` on `.keyword` sub-field |
| Structured conditions in `must` | No filter caching; slower queries | Move to `filter` clause |
| `match` on `keyword` field | Returns unexpected results or no results | Use `term` on keyword fields |
| Ranges without `/d` rounding in date math | Filter cache invalidated every millisecond | Use `now-30d/d` instead of `now-30d` |
| `terms` with analysed values | Mismatches on case/punctuation | Use `.keyword` sub-field or normalise values |
| No `minimum_should_match` in should-only bool | All documents match (any with any token) | Set `minimum_should_match: 1` or use `must` |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) clearly explaining the **query context vs filter context distinction** — `must` and `should` are query context (BM25 score calculated, no caching), while `filter` and `must_not` are filter context (YES/NO, no score, results cached in bitsets); putting structured conditions like `term`, `terms`, and `range` in `filter` instead of `must` is the single most impactful performance optimisation in Elasticsearch; (2) knowing that **`term` never analyses its input** — it searches for the exact byte sequence in the inverted index; using `term` on an analysed `text` field almost always returns zero results because the stored tokens are lowercase and stemmed while the query value is not; the correct tool is `match` on `text` fields and `term` on `keyword` fields; (3) explaining the **`multi_match` type options** and when each is appropriate — `best_fields` for most searches, `cross_fields` when query tokens are split across different fields (person name), `most_fields` when the same content is indexed multiple ways with different analysers, `bool_prefix` for autocomplete; (4) articulating **how nested `bool` queries express complex boolean logic** — `(A AND B) OR (C AND D)` requires two inner `bool.must` clauses inside an outer `bool.should`; this composability is what makes the Query DSL expressive enough for real search applications; (5) knowing the **salary range overlap pattern** — checking if two intervals overlap uses `salaryMin ≤ userMax AND salaryMax ≥ userMin`; this is a classic interview question about range intersection and comes up directly in job search, availability calendars, and event scheduling; and (6) knowing **when to use `must_not` vs a filter on the complement** — `must_not` is the idiomatic exclusion in Elasticsearch, runs in filter context (cached), and pairs naturally with `must`/`filter`/`should` in the same `bool` query; candidates who write `filter: { term: { status: "not-cancelled" } }` when they mean `must_not: [{ term: { status: "cancelled" } }]` reveal less experience with the DSL.
