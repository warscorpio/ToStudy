# Inverted Index Concept (Elasticsearch) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an inverted index and why is it the foundation of full-text search?**
A: An inverted index is a data structure that maps terms to the documents containing them — the inverse of the natural order (document → words). Instead of asking "what words are in document 5?", an inverted index answers "which documents contain the word 'loan'?" in constant time. It is the reason full-text search can scan millions of documents in milliseconds:

```
The forward index (natural — what databases store):
  Document 1: "personal loan approved borrower Ravi Sharma"
  Document 2: "home loan application submitted borrower Priya"
  Document 3: "personal loan application approved"

  To answer "which documents contain 'loan'?":
    Read doc 1 → scan every word → found
    Read doc 2 → scan every word → found
    Read doc 3 → scan every word → found
    Cost: O(N × avg_document_length) → linear scan → unusable at scale

The inverted index (term → document list):
  ┌──────────────────┬───────────────────────────────────────────────┐
  │ Term             │ Posting List (doc IDs that contain the term)  │
  ├──────────────────┼───────────────────────────────────────────────┤
  │ "approved"       │ [1, 3]                                        │
  │ "application"    │ [2, 3]                                        │
  │ "borrower"       │ [1, 2]                                        │
  │ "home"           │ [2]                                           │
  │ "loan"           │ [1, 2, 3]                                     │
  │ "personal"       │ [1, 3]                                        │
  │ "priya"          │ [2]                                           │
  │ "ravi"           │ [1]                                           │
  │ "sharma"         │ [1]                                           │
  │ "submitted"      │ [2]                                           │
  └──────────────────┴───────────────────────────────────────────────┘

  To answer "which documents contain 'loan'?":
    Hash lookup: "loan" → [1, 2, 3]
    Cost: O(1) lookup + O(results) to return them → effectively instant

  To answer "which documents contain 'personal' AND 'approved'?":
    "personal" → [1, 3]
    "approved" → [1, 3]
    Intersection: [1, 3]
    Cost: O(output_size) — intersection of sorted lists is linear in list size

Why inverted indexes beat B-tree indexes for text:
  B-tree on a text column: can answer "name = 'Ravi'" or "name LIKE 'Rav%'"
  Cannot answer: "name contains 'avi'" → must scan every row
  Cannot rank by relevance: no notion of how many times 'avi' appears
  Cannot handle stemming: 'loan' ≠ 'loans' in a B-tree

  Inverted index:
  ✓ Arbitrary term lookup: "which docs contain 'avi'?" → direct lookup
  ✓ Multi-term AND/OR/NOT: set operations on posting lists
  ✓ Relevance scoring: posting list stores term frequency → TF-IDF, BM25
  ✓ Language-aware: stemming reduces 'loans', 'loaned', 'lending' → 'loan' at index time
```

**Q2. What does Elasticsearch store in the inverted index beyond just document IDs?**
A: A naive inverted index stores only document IDs. Elasticsearch's inverted index is richer — each posting list entry stores additional per-document information that enables relevance scoring, phrase queries, and highlighting. Understanding what is stored explains why relevance scoring works and what the storage cost of full-text indexing is:

```
Full Elasticsearch inverted index entry structure:

  For each term in each field:

  Term: "loan"
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Doc ID │ Term Freq │ Positions      │ Offsets (start, end)             │
  ├────────────────────────────────────────────────────────────────────────┤
  │   1    │     3     │ [2, 8, 14]     │ [(7,11), (45,49), (89,93)]       │
  │   2    │     1     │ [4]            │ [(22,26)]                        │
  │   3    │     2     │ [1, 7]         │ [(0,4), (41,45)]                 │
  └────────────────────────────────────────────────────────────────────────┘

  Components:

  Document ID (doc_id):
    Internal Lucene document number (not the Elasticsearch _id)
    Compact integer — used to look up the document in other data structures
    Monotonically increasing within a segment

  Term Frequency (term_freq):
    How many times this term appears in this document's field
    Used in TF-IDF and BM25 scoring:
      More occurrences → higher relevance score (up to a saturation point in BM25)
    index_options: "freqs" or higher enables this (default for text fields)

  Positions (positions):
    Word position of each occurrence within the field
    Position 0 = first word, position 1 = second word, etc.
    Used for: phrase queries ("personal loan" — must be adjacent positions)
              proximity queries (word_A near word_B)
              slop queries ("loan personal"~1 — within 1 position)
    index_options: "positions" or higher enables this (default for text fields)

  Offsets (start_offset, end_offset):
    Byte offsets of the term in the original string
    start_offset: byte position where term starts in the original text
    end_offset: byte position where term ends
    Used for: highlighting (return the original text with matching terms marked)
    NOT stored by default (requires store_offsets: true or term_vectors)
    Can be reconstructed from positions + postings at highlight time (slower)

  Index options (controls what is stored):
  "docs":      doc IDs only (no freq, no positions, no offsets)
               → can answer: does this doc contain the term? (boolean)
               → cannot: phrase queries, frequency scoring, highlighting
  "freqs":     doc IDs + term frequency
               → can: frequency-based scoring
               → cannot: phrase queries
  "positions": doc IDs + frequency + positions (DEFAULT for text fields)
               → can: phrase queries, proximity, slop
  "offsets":   doc IDs + frequency + positions + character offsets
               → can: fast highlighting without re-analysis
               → cost: ~2× storage of "positions"

Mapping control:
  PUT /loans/_mapping
  {
    "properties": {
      "description": {
        "type": "text",
        "index_options": "positions"  // default: phrase queries work
      },
      "tags": {
        "type": "text",
        "index_options": "docs"  // smaller index: boolean match only
      },
      "notes": {
        "type": "text",
        "index_options": "offsets"  // faster highlighting
      }
    }
  }
```

## Section 2: Analysis Pipeline

**Q3. What is the analysis pipeline and how does text become terms in the inverted index?**
A: Before a text value is indexed, Elasticsearch runs it through an analyzer — a pipeline of three components: character filters, a tokenizer, and token filters. The output of analysis is the list of terms stored in the inverted index. Analysis also runs at query time, ensuring the query terms are transformed identically to the indexed terms:

```
Analysis pipeline:

  Input text: "Personal Loans: Approved for Ravi Sharma (CIBIL: 742)"

  Step 1: Character Filters (zero or more)
    Transform the raw input string BEFORE tokenization
    Examples:
      html_strip:     remove <b>, <p>, etc. HTML tags
      mapping:        replace characters ("&" → "and", "₹" → "INR")
      pattern_replace: regex replacements

    After html_strip + mapping:
    "Personal Loans: Approved for Ravi Sharma INR 742"

  Step 2: Tokenizer (exactly one)
    Split the string into individual tokens
    Examples:
      standard:   split on whitespace + punctuation, lowercase
                  "Personal Loans: Approved for Ravi Sharma INR 742"
                  → ["Personal", "Loans", "Approved", "for", "Ravi", "Sharma", "INR", "742"]
                  (colon, parentheses removed — they are punctuation)

      whitespace: split only on whitespace (keeps punctuation as part of tokens)
                  → ["Personal", "Loans:", "Approved", "for", "Ravi", "Sharma", "(CIBIL:", "742)"]

      keyword:    entire input is one token (no splitting — for exact-match fields)
                  → ["Personal Loans: Approved for Ravi Sharma (CIBIL: 742)"]

      ngram:      generates n-grams from each token (for autocomplete)
                  "loan" → ["l", "lo", "loa", "loan"] (min_gram=1, max_gram=4)

      edge_ngram: generates ngrams from the EDGE (start) only
                  "loan" → ["l", "lo", "loa", "loan"] (for prefix autocomplete)

      pattern:    split on a regex pattern

  Step 3: Token Filters (zero or more, applied in sequence)
    Transform, add, or remove tokens
    Examples:
      lowercase:    "Personal" → "personal", "CIBIL" → "cibil"
      stop:         remove stop words: "for" → removed
      stemmer:      "Loans" → "loan" (English stemming: Porter or Snowball algorithm)
      synonym:      "loan" → ["loan", "credit", "lending"] (expand synonyms)
      ascii_folding: "café" → "cafe" (remove diacritics)
      length:       remove tokens shorter than min_length
      unique:       remove duplicate tokens in the same position

    After lowercase + stop + stemmer:
    ["personal", "loan", "approv", "ravi", "sharma", "inr", "742"]
    (Note: "approved" → "approv" by Porter stemmer)

  Final terms stored in inverted index for this document's field:
  {
    "personal": [doc_id, freq=1, positions=[0]],
    "loan":     [doc_id, freq=1, positions=[1]],
    "approv":   [doc_id, freq=1, positions=[2]],
    "ravi":     [doc_id, freq=1, positions=[3]],
    "sharma":   [doc_id, freq=1, positions=[4]],
    "inr":      [doc_id, freq=1, positions=[5]],
    "742":      [doc_id, freq=1, positions=[6]]
  }

  Query-time analysis (MUST match index-time analysis):
  Query: "Personal Loans"
  Same analyzer → ["personal", "loan"]
  Lookup: personal → [doc_id], loan → [doc_id]
  Result: doc matches both terms ✓

  Mismatch example (always a bug):
  Index with lowercase analyzer → stores "personal"
  Query without lowercase → looks up "Personal" → NOT FOUND
  Fix: use same analyzer at index and query time (Elasticsearch does this automatically
       for match queries — but you must be careful with term queries which bypass analysis)
```

**Q4. What is the difference between `text` and `keyword` fields and what does each store in the inverted index?**
A: This is one of the most important Elasticsearch mapping concepts. `text` fields go through the analysis pipeline and are split into individual terms — enabling full-text search. `keyword` fields are stored as a single unmodified token — enabling exact match, aggregations, and sorting:

```javascript
// text field: analyzed → multiple terms
// keyword field: not analyzed → single token (the entire value)

// Mapping:
PUT /loans/_mapping
{
  "properties": {
    "description": { "type": "text" },           // analyzed
    "status":      { "type": "keyword" },         // not analyzed
    "borrower_name": {                             // both: multi-field
      "type": "text",
      "fields": {
        "keyword": { "type": "keyword" }
      }
    }
  }
}

// What goes into the inverted index:

// text field "description": "Personal Loan Approved"
// After analysis (lowercase + stemming):
// Inverted index: ["personal"] → [doc_id], ["loan"] → [doc_id], ["approv"] → [doc_id]
// Query: match query runs "Personal" through the SAME analyzer → looks up "personal"
// Result: finds doc ✓

// keyword field "status": "under_review"
// Inverted index: ["under_review"] → [doc_id]  ← ENTIRE value as one token
// Query: term query { "status": "under_review" } → looks up "under_review"
// Result: finds doc ✓
// Query: term query { "status": "Under_Review" } → looks up "Under_Review"
// Result: NOT FOUND (keyword is case-sensitive, no normalization)
// Fix for case-insensitive keyword: normalizer (lowercases keyword fields)

// The multi-field pattern (most common production use):
// borrower_name: "Ravi Sharma"
// text version → inverted index: ["ravi", "sharma"]
//   Enables: match query ("ravi"), match_phrase ("ravi sharma")
//   Does NOT support: exact aggregations, sorting (analyzed fields vary by position)
// keyword version → inverted index: ["Ravi Sharma"]
//   Enables: term query (exact match), aggregations (by borrower name), sorting
//   Does NOT support: partial match ("Ravi" doesn't find "Ravi Sharma")

// Query targeting the right sub-field:
GET /loans/_search
{
  "query": {
    "bool": {
      "should": [
        // Full-text search on text version:
        { "match": { "borrower_name": "ravi" } },
        // Exact match on keyword version:
        { "term": { "borrower_name.keyword": "Ravi Sharma" } }
      ]
    }
  },
  "aggs": {
    "top_borrowers": {
      // Aggregation MUST use keyword version (not analyzed):
      "terms": { "field": "borrower_name.keyword", "size": 10 }
    }
  }
}

// Sorting requires keyword or numeric field:
GET /loans/_search
{
  "sort": [
    { "borrower_name.keyword": "asc" },   // ✓ keyword: sorts alphabetically
    { "amount": "asc" }                   // ✓ numeric: sorts numerically
    // { "description": "asc" } ← ERROR: cannot sort on analyzed text field
  ]
}

// Storage implications:
// text field only: smaller index (split into terms, compressed posting lists)
// keyword field only: stores the whole value as one token
// Both (multi-field): ~1.5× storage of either alone
// For low-cardinality keywords (status, category): small overhead
// For high-cardinality keywords (UUIDs, emails): large overhead — consider doc_values only
```

## Section 3: Segments and Lucene Architecture

**Q5. What is a Lucene segment and why does Elasticsearch use an immutable segment-per-write approach?**
A: An Elasticsearch index is backed by a Lucene index, which is composed of one or more segments. Each segment is a fully self-contained, immutable inverted index with its own term dictionary, posting lists, stored fields, and doc values. Immutability is the key design choice — it enables lock-free concurrent reads while writes create new segments, which are then periodically merged:

```
Lucene segment anatomy:

  A segment is a directory of files:
  ┌──────────────────────────────────────────────────────────────────┐
  │ Segment: _0                                                      │
  ├──────────────────────────────────────────────────────────────────┤
  │ .tim  — Term Index: sorted term dictionary (B-tree structure)    │
  │ .tip  — Term Index Prefix: fast pointer into .tim                │
  │ .doc  — Posting Lists (doc IDs + frequencies)                   │
  │ .pos  — Positions (word positions for phrase queries)           │
  │ .pay  — Payloads and offsets (character offsets for highlights) │
  │ .fdx  — Field Index: pointers into stored field data            │
  │ .fdt  — Field Data: stored field values (_source, etc.)         │
  │ .dvd  — Doc Values data (columnar storage for aggregations)     │
  │ .dvm  — Doc Values metadata                                     │
  │ .nvm  — Norms metadata (field length normalization factors)     │
  │ .nvd  — Norms data                                              │
  │ .fnm  — Field Names (mapping of field IDs to names)            │
  │ .si   — Segment info (doc count, doc IDs, version)             │
  │ .liv  — Live docs (bit set: which docs are NOT deleted)         │
  └──────────────────────────────────────────────────────────────────┘

Why immutable segments?

  Problem with mutable indexes (traditional approach):
    Modifying an inverted index requires re-sorting, re-compressing posting lists
    Writers and readers conflict → locks needed → reduced throughput
    B-tree rebalancing causes unpredictable latency spikes

  Immutable segment solution:
    New documents → new segment created
    Updates → old segment marks doc as deleted (flip a bit in .liv)
             + new segment with the new version
    Deletes → mark doc as deleted in .liv (no actual deletion yet)
    Reads → scan all segments, skip deleted docs
    No locks on reads (immutable = thread-safe)
    Write = create small new segment (fast)

  Consequence:
    Many small segments accumulate → merge process needed
    Segment merges: background process merges N small segments into 1 large segment
    During merge: deleted documents are actually removed (true reclamation)
    After merge: old segments deleted, single larger segment replaces them

Document write flow:
  Client sends: PUT /loans/_doc/L001 { "status": "approved", ... }
  ↓
  Shard receives the write
  ↓
  1. Write to in-memory buffer (not yet searchable)
     + Translog (write-ahead log for durability)
  ↓
  2. Refresh (default: every 1 second):
     In-memory buffer → new Lucene segment (now searchable)
     Segment is in OS filesystem cache (not yet on disk)
  ↓
  3. Flush (default: every 30 minutes OR translog size > 512MB):
     Segment written to disk (fsync)
     Translog truncated (data is now durable on disk)
  ↓
  4. Merge (background, automatic):
     Small segments merged into fewer larger segments
     Deleted documents removed during merge

Refresh vs Flush vs Merge:
  Refresh: make new writes searchable (in-memory → segment)
           Default: 1 second → Elasticsearch is "near real-time" (NRT), not real-time
           Manual: POST /loans/_refresh
           Cost: relatively cheap (in-memory operation)

  Flush: persist segments to disk (segment + translog fsync)
         Protects against node failure (data survives restart)
         Manual: POST /loans/_flush
         Cost: disk I/O

  Merge: combine segments (background)
         Reduces segment count → faster searches (fewer segments to scan)
         Cost: CPU + disk I/O (can spike during heavy ingestion)
         Manual: POST /loans/_forcemerge?max_num_segments=1
         (force to single segment — useful for read-only indexes)
```

**Q6. What is the translog and how does it work with segments to provide durability?**
A: The translog (transaction log) is Elasticsearch's write-ahead log — every operation is written to the translog before being acknowledged. If a node crashes before segments are flushed to disk, the translog allows recovery of all operations since the last flush:

```
Durability model:

  Without translog:
    Write arrives → goes to in-memory buffer
    Refresh: in-memory buffer → segment (in OS cache, not on disk)
    Crash before flush: segment lost (only in OS cache) → data loss

  With translog:
    Write arrives
    → Append to translog (durable write, fsync per operation by default)
    → Append to in-memory buffer (fast, not durable)
    Client receives: 200 OK (write is acknowledged)

    Refresh (every 1s): in-memory buffer → searchable segment (OS cache)
    Flush (every 30min): segments written to disk, translog cleared

    Crash after translog write, before flush:
    → Restart: Lucene segments are gone (were in OS cache)
    → Recovery: replay the translog → re-create in-memory operations
    → Segments are rebuilt from translog
    → No data loss

Translog fsync modes:
  index.translog.durability: "request" (default)
    Every write operation: fsync the translog before acknowledging
    → Strongest durability: at most 0 ops lost on crash
    → Cost: one fsync per write operation (significant for high throughput)

  index.translog.durability: "async"
    Translog fsynced every index.translog.sync_interval (default: 5s)
    → Up to 5 seconds of writes can be lost on sudden power failure
    → Benefit: much higher write throughput (no per-operation fsync)
    → Use: when some data loss is acceptable (logs, metrics, non-critical data)

  Configuring async translog for high-throughput ingestion:
  PUT /logs/_settings
  {
    "index.translog.durability": "async",
    "index.translog.sync_interval": "5s"
  }

Translog size and recovery time:
  Large translog → longer recovery time after crash
  Flush threshold: index.translog.flush_threshold_size = 512mb (default)
  When translog exceeds 512MB → automatic flush → translog cleared
  Recovery time ≈ time to replay translog → keep translog size bounded

Checking translog state:
GET /loans/_stats/translog
{
  "_all": {
    "total": {
      "translog": {
        "operations": 145230,    // operations in current translog
        "size_in_bytes": 52428800, // translog size (50MB)
        "uncommitted_operations": 1234,  // not yet flushed to disk
        "uncommitted_size_in_bytes": 512000
      }
    }
  }
}
```

## Section 4: Term Dictionary and Posting Lists

**Q7. How is the term dictionary structured and how does Elasticsearch find terms efficiently?**
A: The term dictionary is a sorted data structure mapping terms to their posting lists. Elasticsearch (via Lucene) uses a Finite State Transducer (FST) — a compact automaton that encodes all terms and their positions on disk with near-minimal memory — stored in the `.tim` file with a prefix-compressed in-memory index:

```
Term dictionary structure:

  Naive approach: hash map of term → posting list offset
    Problem: entire hash map must fit in memory → too large for billions of terms

  Lucene's approach: FST (Finite State Transducer) + prefix compression
    FST: a directed acyclic graph where:
      Each path from start to end state encodes one term
      Shared prefixes share nodes (prefix compression)
      Each end state stores the byte offset into the posting list file (.doc)

  Example FST for terms: ["approv", "application", "loan", "loans", "personal"]:

    Start
    ├── a → p → p → r → o → v → END [offset: 0]  ("approv")
    │           l → i → c → a → t → i → o → n → END [offset: 100]  ("application")
    ├── l → o → a → n → END [offset: 200]  ("loan")
    │              s → END [offset: 280]  ("loans")
    └── p → e → r → s → o → n → a → l → END [offset: 350]  ("personal")

  Memory: FST is ~10 bytes per term (highly compressed)
  1 billion terms: ~10GB FST → fits in heap for large clusters

  Term lookup:
    Query term: "loan"
    FST traversal: l→o→a→n → END [offset: 200]
    Read posting list from .doc at offset 200
    Result: [doc_id_1, doc_id_2, doc_id_3, ...]
    Time: O(term_length) — proportional to the length of the search term

  Prefix search (wildcard like "loan*"):
    FST traversal: l→o→a→n → branch
    Find all END states reachable from this prefix
    Returns: offsets for "loan", "loans", "loaned", "loanee", ...
    Efficient because all terms with same prefix share the same path to the prefix node

  Term statistics stored per term:
    doc_freq: number of documents containing this term
              Used in IDF (inverse document frequency) part of relevance scoring
              Rare term → high IDF → matches are more relevant
    total_term_freq: sum of term_freq across all documents
              Used in some scoring variants

Posting list compression (why Elasticsearch can handle billions of documents):
  Naive posting list: [1, 5, 8, 12, 19, 25, 1000, 1001, 1002]
    Storage: 9 integers × 4 bytes = 36 bytes

  Delta encoding: store differences instead of absolute values
    [1, 4, 3, 4, 7, 6, 975, 1, 1]
    Small numbers → more compressible

  FOR (Frame Of Reference) / PFOR (Patched Frame Of Reference):
    Lucene packs 128 integers at a time
    Finds the minimum number of bits needed for the largest delta in the block
    Encodes all 128 deltas using that bit width
    Result: high compression ratio for dense posting lists

  Typical compression: 2–8 bytes per document ID (vs 4 bytes uncompressed)
  For 1 billion documents: ~2GB compressed vs 4GB uncompressed for a single term
```

**Q8. How does Elasticsearch score documents and what role does the inverted index play in BM25 scoring?**
A: BM25 (Best Match 25) is Elasticsearch's default relevance scoring algorithm, replacing the older TF-IDF in version 5.0. Both algorithms use data stored in the inverted index — term frequency, document frequency, field length — to compute how relevant a document is to a query:

```
BM25 scoring formula:
  score(D, Q) = Σ IDF(t) × (TF(t,D) × (k1 + 1)) / (TF(t,D) + k1 × (1 - b + b × |D|/avgDL))

  Where:
  t        = each term in the query Q
  D        = the document being scored
  TF(t,D)  = term frequency of t in D (from posting list entry)
  |D|      = length of document D in terms (from norms)
  avgDL    = average document length across all documents (computed at index time)
  k1       = term frequency saturation parameter (default 1.2)
             Higher k1: frequency matters more (no saturation)
             Lower k1: diminishing returns from repeated terms
  b        = length normalization (default 0.75)
             b=1: full length normalization (short docs preferred)
             b=0: no length normalization
  IDF(t)   = log(1 + (N - n(t) + 0.5) / (n(t) + 0.5))
             N = total number of documents in the index
             n(t) = number of documents containing term t (doc_freq from posting list)

BM25 vs TF-IDF key difference:
  TF-IDF: TF component grows without bound
    10 occurrences of "loan" → 10× boost vs 1 occurrence
    Problem: document stuffing — repeat terms many times to boost score
  BM25: TF component saturates at k1 (default 1.2)
    Beyond ~3-4 occurrences of "loan": very little additional scoring benefit
    More robust against keyword stuffing

What comes from the inverted index:
  ┌─────────────────────────────────────┬────────────────────────────────────┐
  │ BM25 component                      │ Source in Lucene                   │
  ├─────────────────────────────────────┼────────────────────────────────────┤
  │ TF(t,D): term frequency             │ Posting list entry for (term, doc) │
  │ n(t): docs containing term          │ doc_freq field in term dictionary  │
  │ N: total documents                  │ Segment metadata (doc count)       │
  │ |D|: document length                │ Norms (.nvm, .nvd files)           │
  │ avgDL: average document length      │ Pre-computed at index time          │
  └─────────────────────────────────────┴────────────────────────────────────┘

Norms (field length normalization):
  For each document and each field: stores a compact representation of field length
  Storage: 1 byte per document per field (quantized from actual length)
  Used in BM25's length normalization term
  Disable norms when field length doesn't matter:
  PUT /loans/_mapping
  {
    "properties": {
      "loan_id": {
        "type": "keyword",
        "norms": false   // exact match field: length irrelevant, save space
      },
      "description": {
        "type": "text",
        "norms": true    // default: length normalization applies
      }
    }
  }

Explaining scores (debugging relevance):
GET /loans/_explain/L001
{
  "query": { "match": { "description": "personal loan" } }
}
// Returns:
{
  "explanation": {
    "value": 1.8,
    "description": "sum of:",
    "details": [
      {
        "value": 0.9,
        "description": "weight(description:personal in 0), result of:",
        "details": [
          { "value": 0.6, "description": "idf, computed as log(...)", ... },
          { "value": 1.5, "description": "tf, freq=2.0", ... }
        ]
      },
      {
        "value": 0.9,
        "description": "weight(description:loan in 0), result of:",
        ...
      }
    ]
  }
}
// Shows exactly how score was computed — essential for relevance debugging

Per-field BM25 tuning:
PUT /loans/_mapping
{
  "properties": {
    "title": {
      "type": "text",
      "similarity": "BM25"  // default
    },
    "description": {
      "type": "text",
      "similarity": "custom_bm25"
    }
  }
}

PUT /_settings
{
  "similarity": {
    "custom_bm25": {
      "type": "BM25",
      "k1": 1.5,   // higher: term frequency matters more
      "b": 0.5     // lower: less length normalization
    }
  }
}
```

## Section 5: Doc Values and Stored Fields

**Q9. What are doc values and how do they complement the inverted index for aggregations and sorting?**
A: The inverted index maps terms to documents — it's optimized for the question "which documents contain this term?" Doc values answer the opposite question: "what is the value of field X for document Y?" — stored in columnar format on disk. They power aggregations, sorting, and scripting without loading the entire `_source`:

```
Inverted index vs Doc Values — two complementary structures:

  Inverted index:
    Structure: term → [doc_id, doc_id, doc_id, ...]
    Access pattern: "find all docs where status='approved'"
    Optimized for: search / filtering
    Not suitable for: "give me all status values in this result set" (aggregations)

  Doc Values (forward index — columnar):
    Structure:
      doc_0: status="approved"
      doc_1: status="pending"
      doc_2: status="approved"
      doc_3: status="rejected"
    Access pattern: "for these doc_ids, what is the status value?"
    Optimized for: aggregations, sorting, field retrieval in scripts
    Not suitable for: search (would require full scan)

Physical storage (columnar = contiguous on disk):
  All values for a field are stored together:
  [approved | pending | approved | rejected | approved | ...]
  When aggregating: read ONE column sequentially → cache-friendly, fast
  vs row-based: [doc0_field1 | doc0_field2 | doc0_field3 | doc1_field1 | ...]
  When aggregating field_2: every Nth bytes → poor cache utilization

Doc values are:
  Stored on disk (memory-mapped by the OS)
  NOT in the JVM heap (avoids GC pressure)
  Compressed (for strings: dictionary encoding; for numbers: delta/FOR encoding)
  Available for all non-analyzed fields by default:
    keyword, numeric (long, integer, double), date, boolean, geo
  NOT available for text fields (use fielddata instead — see below)

Mapping control:
  PUT /loans/_mapping
  {
    "properties": {
      "status": {
        "type": "keyword",
        "doc_values": true   // default: enables sorting/aggregation
      },
      "description": {
        "type": "text",
        "doc_values": false  // text fields: no doc values (use fielddata if needed)
      },
      "internal_tag": {
        "type": "keyword",
        "doc_values": false,  // disable doc values: search-only field
        "norms": false         // also disable norms: smallest possible index
      }
    }
  }

Fielddata (alternative for text fields — avoid in production):
  text fields: NOT indexed as doc values (would defeat analysis)
  For aggregations on text: "fielddata": true — loads analyzed terms into JVM heap
  EXPENSIVE: loads entire field into heap → OOM risk → explicitly requires opt-in
  USE CASE: rare analytics on text fields in controlled environments
  BETTER ALTERNATIVE: use .keyword sub-field for aggregations on text

  Example — common mistake:
  GET /loans/_search
  {
    "aggs": {
      "top_descriptions": {
        "terms": { "field": "description" }  // ← ERROR unless fielddata: true
      }
    }
  }
  // Error: "Fielddata is disabled on text fields by default."
  // Fix: aggregate on description.keyword instead
  {
    "aggs": {
      "top_descriptions": {
        "terms": { "field": "description.keyword" }  // ← correct
      }
    }
  }
```

**Q10. What is stored fields (`_source`) and how does it relate to the inverted index?**
A: The `_source` field stores the original JSON document in compressed form alongside the index. It is NOT part of the inverted index — it is a separate stored field used to return the original document in search results. Understanding this separation explains storage costs and how to optimize them:

```
Stored fields vs inverted index:

  When you index: PUT /loans/_doc/L001 { "status": "approved", "amount": 50000 }

  Elasticsearch stores TWO things:

  1. Inverted index entries (for search):
     "approv" → [L001_doc_id, ...]  (from status field, after analysis)
     In doc values: status="approved", amount=50000 (for aggregations)

  2. _source (for retrieval):
     Compressed JSON: { "status": "approved", "amount": 50000 }
     Stored in .fdt files alongside the segment
     Retrieved when you GET /loans/_doc/L001 or search results include _source

  _source is NOT in the inverted index:
  It is NOT used for searching (the inverted index is used for that)
  It IS returned in search results (for display)
  It CAN be used for re-indexing (source of truth for the document)
  It CANNOT be used for aggregations or sorting (doc values are used for that)

Memory and storage implications:

  _source compressed: ~20–40% of raw JSON size
  For 100M loan documents × 1KB average:
    Raw JSON: 100GB
    Compressed _source: ~30GB
  Large _source → slower network transfer, higher storage cost

  Options to reduce _source storage:

  Option 1: Disable _source entirely (aggressive, not recommended):
  PUT /loans/_mapping
  {
    "_source": { "enabled": false }
  }
  // Risk: cannot reindex, cannot use update API, no source in results
  // Only for: purely aggregation-focused indexes where source is never needed

  Option 2: Exclude large fields from _source:
  PUT /logs/_mapping
  {
    "_source": {
      "excludes": ["raw_request_body", "debug_payload"]
    }
  }
  // These fields are still indexed (in inverted index) but not stored in _source
  // Cannot retrieve them in search results but CAN search for them

  Option 3: Synthetic source (Elasticsearch 8.4+):
  PUT /logs/_mapping
  {
    "_source": { "mode": "synthetic" }
  }
  // _source is reconstructed from doc values at query time (not stored)
  // ~40% storage reduction (no stored source) with slight query overhead
  // Limitation: requires all fields to have doc_values, some field types excluded

  Source filtering at query time (best practice for large documents):
  GET /loans/_search
  {
    "_source": ["loan_id", "status", "amount"],  // only return these fields
    "query": { "match": { "description": "personal" } }
  }
  // _source IS stored in full, but only these fields returned in response
  // Reduces network transfer — document is still fully stored on disk
```

## Section 6: Sharding and the Distributed Index

**Q11. How does the inverted index relate to shards and how does a search query cross shard boundaries?**
A: An Elasticsearch index is divided into shards, each of which is a complete Lucene index with its own inverted index, segments, doc values, and stored fields. A search query fans out to all shards simultaneously, each shard scores its documents independently, and the results are merged:

```
Index → Shards → Segments:

  Index "loans" (5 primary shards):
  ┌─────────────────────────────────────────────────────┐
  │ Shard 0: Lucene index                               │
  │   Segment _0: 100,000 docs  ← inverted index        │
  │   Segment _1: 50,000 docs   ← inverted index        │
  │   Segment _2: 75,000 docs   ← inverted index        │
  ├─────────────────────────────────────────────────────┤
  │ Shard 1: Lucene index                               │
  │   Segment _0: 120,000 docs                          │
  │   Segment _1: 80,000 docs                           │
  ├─────────────────────────────────────────────────────┤
  │ ... (shards 2, 3, 4)                                │
  └─────────────────────────────────────────────────────┘

Document routing:
  When indexing: shard = hash(document_id) % num_primary_shards
  Default: consistent hash of _id → determines which shard receives the document
  Custom routing: route all loans for a tenant to the same shard
    PUT /loans/_doc/L001?routing=tenant_123

Search across shards (scatter-gather pattern):

  Step 1: QUERY phase (scatter)
    Coordinating node receives search request
    Broadcasts query to ALL primary (or replica) shards
    Each shard runs the query against its local Lucene index
    Each shard returns its TOP N scoring documents (just doc IDs + scores)
    NOT the full documents yet — just IDs and scores

  Step 2: MERGE phase (gather)
    Coordinating node collects top N results from each shard
    Merges them: global sort by score
    Determines final top K results (e.g. top 10 for page 1)

  Step 3: FETCH phase
    Coordinating node requests ONLY the final top K documents
    Each relevant shard returns the full _source for its documents
    Coordinating node returns merged results to client

  Why two phases (query then fetch)?
    Phase 1 transfers: [doc_id, score] × N per shard × num_shards
    Phase 2 transfers: full _source × K total results
    Without two phases: transfer all _source × N × num_shards → massive waste

BM25 across shards — the IDF problem:
  BM25 uses IDF: IDF(t) = log(1 + (N - n(t) + 0.5) / (n(t) + 0.5))
  N = total docs, n(t) = docs containing term t
  PROBLEM: each shard only knows its LOCAL N and n(t)
  If shard 0 has all the common documents for "loan":
    shard 0 sees: n("loan")=1000, N=10000 → low IDF → low scores for "loan"
    shard 1 sees: n("loan")=1,    N=10000 → high IDF → high score for "loan"
  Result: documents on different shards score differently for the same term
  This creates INCONSISTENT relevance across shards → results appear random

  Solutions:
  Option 1: default — accept the inconsistency (works well enough for large indexes)
    With millions of documents: IDF is similar across shards (law of large numbers)
    Small indexes (< 100K docs): IDF per shard can vary wildly

  Option 2: search_type=dfs_query_then_fetch (Distributed Frequency Search)
    Phase 0: Coordinating node asks ALL shards for their term frequencies
    Combines into global N and n(t) → single global IDF
    Phases 1, 2, 3: proceed with consistent IDF
    Cost: extra round trip → slower (2× query latency) → only for small indexes

  GET /loans/_search?search_type=dfs_query_then_fetch
  {
    "query": { "match": { "description": "personal loan" } }
  }

  Option 3: single shard index (for small indexes where consistency matters)
  PUT /small_catalog
  {
    "settings": { "number_of_shards": 1 }
  }
  // One shard: all documents → single Lucene index → consistent IDF
```

## Section 7: Scenario-Based Questions

**Q12. "A search for 'loan' returns documents where 'loan' appears once, but not documents where 'loans' appears many times. What is causing this and how do you fix it?"**

```javascript
// Diagnosis: stemming is not applied, or query/index analyzers are mismatched

// Test what terms are actually in the inverted index:
GET /loans/_analyze
{
  "analyzer": "standard",  // the default analyzer
  "text": "loans"
}
// Response: [{ "token": "loans", "start_offset": 0, ... }]
// "standard" analyzer: lowercases but does NOT stem
// "loans" is stored as "loans" (not "loan")
// Query "loan" looks up "loan" in the index → finds documents with "loan"
// "loans" is a different term → not found

// Fix 1: Use an analyzer that stems (english analyzer):
PUT /loans/_mapping
{
  "properties": {
    "description": {
      "type": "text",
      "analyzer": "english"  // applies Porter stemmer
    }
  }
}

// Verify:
GET /loans/_analyze
{
  "analyzer": "english",
  "text": "loans approved lending"
}
// Response: ["loan", "approv", "lend"]
// All three stem to their root forms
// Now: "loan", "loans", "loaned", "lending" all → "loan" → match each other

// Fix 2: Synonym expansion (if stemming isn't enough):
// "loan" and "credit" and "financing" should match each other
PUT /loans
{
  "settings": {
    "analysis": {
      "filter": {
        "loan_synonyms": {
          "type": "synonym",
          "synonyms": ["loan, credit, financing, borrowing"]
        }
      },
      "analyzer": {
        "loan_analyzer": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase", "loan_synonyms", "porter_stem"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "description": {
        "type": "text",
        "analyzer": "loan_analyzer"
      }
    }
  }
}

// Verify analyzer behavior:
GET /loans/_analyze
{
  "analyzer": "loan_analyzer",
  "text": "Personal loans for salaried employees"
}
// Tokens: ["person", "loan", "credit", "financ", "borrow", "salari", "employe"]
// "loans" → stemmed to "loan" AND expanded to synonyms

// Fix 3: Search time synonym expansion only (index stays smaller):
// Index-time: store only "loan" (no expansion → smaller index)
// Query-time: expand "loan" to synonyms
PUT /loans
{
  "settings": {
    "analysis": {
      "filter": {
        "search_synonyms": {
          "type": "synonym",
          "synonyms": ["loan, credit, financing"]

      },
      "analyzer": {
        "index_analyzer": {
          "tokenizer": "standard",
          "filter": ["lowercase", "porter_stem"]
        },
        "search_analyzer": {
          "tokenizer": "standard",
          "filter": ["lowercase", "porter_stem", "search_synonyms"]

      }
    }
  },
  "mappings": {
    "properties": {
      "description": {
        "type": "text",
```

**Q14. "Explain why a search for 'approved' returns a document with 'APPROVED' in it, but a term query for 'approved' on a keyword field does not return the same document."**

```javascript
// This demonstrates the critical difference between analyzed (text) and
// non-analyzed (keyword) fields, and between match and term queries.

// Setup:
PUT /loans/_doc/L001
{
  "status_text": "APPROVED",        // text field (analyzed)
  "status_keyword": "APPROVED"      // keyword field (not analyzed)
}

// What's in the inverted index:

// status_text (text field — standard analyzer):
//   Analysis: "APPROVED" → lowercase → "approved"
//   Stored term: "approved"

// status_keyword (keyword field — no analysis):
//   No analysis applied → stored as-is
//   Stored term: "APPROVED"

// Query 1: match query on text field
GET /loans/_search
{
  "query": { "match": { "status_text": "approved" } }
}
// match query ANALYZES the query string: "approved" → lowercase → "approved"
// Looks up "approved" in inverted index for status_text → FOUND ✓
// match query on text field with "APPROVED" also works:
//   query analysis: "APPROVED" → lowercase → "approved" → found ✓

// Query 2: match query on keyword field (unusual but instructive)
GET /loans/_search
{
  "query": { "match": { "status_keyword": "approved" } }
}
// match query on keyword field: keyword fields use "keyword" analyzer
// "keyword" analyzer: no tokenization, no lowercasing, stores as-is
// BUT match query normalizes via the field's search analyzer
// For keyword field: search_analyzer = keyword (identity)
// Query term: "approved" → stored as "approved"
// Inverted index for status_keyword has: "APPROVED"
// "approved" ≠ "APPROVED" → NOT FOUND ✗

// Query 3: term query on keyword field (most common use)
GET /loans/_search
{
  "query": { "term": { "status_keyword": "APPROVED" } }
}
// term query: NO analysis applied to the query term (bypasses analysis entirely)
// Looks up "APPROVED" in inverted index for status_keyword → FOUND ✓
// BUT:
GET /loans/_search
{
  "query": { "term": { "status_keyword": "approved" } }
}
// term query: looks up "approved" → inverted index has "APPROVED" → NOT FOUND ✗

// Query 4: term query on text field (common mistake)
GET /loans/_search
{
  "query": { "term": { "status_text": "APPROVED" } }
}
// term query: NO analysis on query term
// Looks up "APPROVED" in inverted index for status_text
// But the inverted index has "approved" (lowercased by analysis at index time)
// "APPROVED" ≠ "approved" → NOT FOUND ✗
// This is a very common bug: using term query on a text field

// Summary table:
//
// Field type │ Query type │ Query value │ Result  │ Why
// ───────────┼────────────┼─────────────┼─────────┼────────────────────────────────
// text       │ match      │ "approved"  │ FOUND   │ query analyzed → "approved" matches
// text       │ match      │ "APPROVED"  │ FOUND   │ query analyzed → "approved" matches
// text       │ term       │ "approved"  │ FOUND   │ no analysis, index has "approved"
// text       │ term       │ "APPROVED"  │ NOT FOUND│ no analysis, index has "approved"
// keyword    │ term       │ "APPROVED"  │ FOUND   │ no analysis, index has "APPROVED"
// keyword    │ term       │ "approved"  │ NOT FOUND│ no analysis, index has "APPROVED"
// keyword    │ match      │ "APPROVED"  │ FOUND   │ keyword analyzer = identity
// keyword    │ match      │ "approved"  │ NOT FOUND│ case mismatch

// Fix for case-insensitive keyword:
PUT /loans/_mapping
{
  "properties": {
    "status_keyword": {
      "type": "keyword",
      "normalizer": "lowercase_normalizer"  // applies lowercase at index AND query time
    }
  }
}

PUT /loans/_settings
{
  "analysis": {
    "normalizer": {
      "lowercase_normalizer": {
        "type": "custom",
        "filter": ["lowercase"]
      }
    }
  }
}
// Now: "APPROVED" → stored as "approved"
// term query "approved" → finds "APPROVED" documents ✓
// term query "APPROVED" → also finds (normalizer lowercases query too) ✓
```

## Quick Reference Table

| Concept | Description | Used for |
|---|---|---|
| Inverted index | term → [doc_id, freq, positions, offsets] | Full-text search |
| Term dictionary (FST) | Sorted map of terms to posting list offsets | O(term_length) term lookup |
| Posting list | Per-term list of matching documents with metadata | Boolean queries, scoring |
| Doc values | Columnar, on-disk, per-field values | Aggregations, sorting, scripting |
| Stored fields (`_source`) | Compressed original JSON per document | Retrieving full documents |
| Norms | Per-doc, per-field length factor (1 byte) | BM25 length normalization |
| Segment | Immutable Lucene index unit; contains all structures | Unit of write/merge |
| Translog | Write-ahead log for durability | Recovery after crash |
| Analysis pipeline | char filter → tokenizer → token filters | Text → terms at index/query time |

| Field type | Analysis | Inverted index | Doc values | Use for |
|---|---|---|---|---|
| `text` | Yes (stemming, lowercase) | Yes (multiple terms) | No | Full-text search |
| `keyword` | No (stored as-is) | Yes (single token) | Yes | Exact match, aggregations, sort |
| `text` + `.keyword` | Both | Both | Yes (on .keyword) | Full-text + aggregations |
| `long`, `double`, `date` | N/A | Range index | Yes | Numeric range, aggregations |

| Query type | Analyzes query? | Field type | Use for |
|---|---|---|---|
| `match` | Yes | `text` | Standard full-text search |
| `term` | No | `keyword` | Exact match on keyword fields |
| `terms` | No | `keyword` | Multi-value exact match |
| `match_phrase` | Yes | `text` | Adjacent word order matters |
| `range` | No | `date`, numeric | Date/number range filtering |
| `prefix` | No | `keyword` | Starts-with search |
| `wildcard` | No | `keyword` | Pattern matching (slow, avoid on large indexes) |

---

**Tip for interviews:** Five things separate strong candidates on Elasticsearch's inverted index: (1) explaining **the analysis pipeline precisely** — input text goes through character filters → tokenizer → token filters at BOTH index time and query time, and the query must be analyzed with the same analyzer as the index; the most common production bug is using a `term` query (no analysis) against a `text` field (analyzed at index time), which causes case-mismatch misses; (2) knowing **what the posting list stores beyond doc IDs** — term frequency (for BM25 scoring), positions (for phrase queries and proximity), and optionally offsets (for fast highlighting); and knowing the `index_options` setting that controls which of these are stored, since `"docs"` mode drops frequency and positions for a smaller index at the cost of phrase queries; (3) understanding **the segment + translog durability model** — writes go to the translog (durable) and an in-memory buffer (searchable after refresh in 1 second), segments are persisted to disk on flush (every 30 minutes by default), and the translog enables recovery of any operations since the last flush; this also explains why Elasticsearch is "near real-time" (1-second refresh latency) rather than real-time; (4) being precise about **text vs keyword and the three query targets** — `text` fields use `match` queries (analyzed), `keyword` fields use `term` queries (not analyzed), and aggregations/sorting always use `keyword` or numeric doc values; the multi-field pattern (`"type": "text"` with `"fields": {"keyword": {"type": "keyword"}}`) is the production standard for fields that need both full-text search and aggregations; and (5) explaining **the scatter-gather search pattern across shards** and the IDF consistency problem — each shard scores independently using local IDF, which means term frequency statistics differ across shards, producing inconsistent relevance for small indexes; `dfs_query_then_fetch` solves it with a pre-phase that collects global statistics but costs an extra round trip.
