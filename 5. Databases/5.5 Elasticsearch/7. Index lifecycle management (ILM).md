# Elasticsearch Index Lifecycle Management (ILM) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does ILM solve and why is manual index management insufficient at scale?**
A: Elasticsearch indices accumulate data over time. Without lifecycle management, a single index grows indefinitely — degrading search performance, consuming expensive storage, and making retention enforcement a manual operational burden. ILM automates the transition of indices through defined phases based on age, size, or document count:

```
The problem without ILM:

  Time-series data (logs, events, metrics) typical growth:
    Day 1:   logs-2024-01-01 → 5GB
    Day 30:  logs-2024-01-01 → 5GB + logs-2024-01-30 → 5GB (30 indices)
    Year 1:  365 indices, ~1.8TB of data, mixed hot/cold/stale data in same tier

  Without ILM — problems:
  1. Hot data (last 7 days) and cold data (1 year ago) on the same nodes
     → Hot nodes waste resources serving rarely-accessed historical data
     → Cold data wastes SSD space that should serve recent data

  2. Shard count grows indefinitely
     → Each shard has overhead: JVM heap usage (~few KB per shard in cluster state)
     → 10,000 shards: cluster state becomes a bottleneck
     → Default 5 shards/index × 365 days = 1,825 shards per year per data stream

  3. Retention enforcement is manual
     → Engineer must write cron jobs to delete old indices
     → Mistakes: deleting too early (compliance violation) or never deleting (disk full)

  4. No automatic optimization
     → Small indices stay fragmented (many segments)
     → forcemerge must be run manually to optimize read-only historical data

ILM solves this by automating:
  ┌────────────────────────────────────────────────────────────────────────┐
  │ HOT phase:   Active writes + searches. SSD nodes. Regular rollovers.  │
  │              Index rolls over when size > 50GB or age > 1 day          │
  ├────────────────────────────────────────────────────────────────────────┤
  │ WARM phase:  No more writes. Merge to 1 segment. Move to warm nodes.  │
  │              After 7 days in hot                                       │
  ├────────────────────────────────────────────────────────────────────────┤
  │ COLD phase:  Infrequent reads. Move to cold (HDD/object storage).     │
  │              After 30 days in hot                                      │
  ├────────────────────────────────────────────────────────────────────────┤
  │ FROZEN phase: Rare access. Searchable snapshots from object storage.  │
  │               After 90 days in hot                                     │
  ├────────────────────────────────────────────────────────────────────────┤
  │ DELETE phase: Data retention exceeded. Index deleted automatically.   │
  │               After 365 days in hot                                    │
  └────────────────────────────────────────────────────────────────────────┘

ILM timeline example for a loan event log:
  Index created → HOT (writes + searches, SSD, high-replica count)
  After 1 day or 50GB → ROLLOVER → new index becomes active HOT
  After 7 days → WARM (readonly, forcemerge, move to warm nodes)
  After 30 days → COLD (move to cold nodes, reduce replicas)
  After 90 days → FROZEN (searchable snapshots, minimal local disk)
  After 365 days → DELETE (index removed, regulatory retention satisfied)
```

**Q2. What are the five ILM phases and what actions are available in each?**
A: ILM defines five ordered phases. Not all phases are required — you choose which phases apply to your use case. Each phase has a set of allowed actions that can be configured:

```
Phase overview and available actions:

┌─────────┬──────────────────────────────────────────────────────────────────┐
│ HOT     │ The active-write phase. New documents are indexed here.          │
│         │ Most queries hit this phase. Highest resource tier.             │
│ Actions:│                                                                  │
│  rollover      — Create a new index when conditions are met              │
│  set_priority  — Priority for shard recovery (hot=100, warm=50, cold=0) │
│  unfollow      — Convert follower index to regular (CCR teardown)        │
│  shrink        — Reduce primary shard count (must disable writes first)  │
│  forcemerge    — Merge segments (rarely in hot — more often in warm)     │
│  readonly      — Mark index read-only                                     │
│  downsample    — Aggregate time-series to coarser granularity            │
├─────────┼──────────────────────────────────────────────────────────────────┤
│ WARM    │ Index is no longer the write target. Still frequently queried.  │
│         │ Merge to fewer segments, move to cheaper nodes.                 │
│ Actions:│                                                                  │
│  forcemerge    — Merge all segments into 1 (optimizes read performance)  │
│  shrink        — Reduce primary shards to 1 (less overhead)              │
│  allocate      — Move to warm-tier nodes (node attributes)               │
│  readonly      — Mark index read-only (required before forcemerge/shrink)│
│  set_priority  — Lower priority than hot                                  │
│  downsample    — Aggregate time-series data (e.g. per-minute → per-hour) │
│  migrate       — Auto-move to tier based on phase (if tiers configured)  │
├─────────┼──────────────────────────────────────────────────────────────────┤
│ COLD    │ Infrequently accessed. Optimize for storage cost over speed.    │
│ Actions:│                                                                  │
│  allocate      — Move to cold-tier nodes (usually HDD or fewer resources)│
│  set_priority  — Lowest data tier priority                                │
│  freeze        — (deprecated 7.14+) Reduce heap usage                   │
│  searchable_snapshot — Store in object storage, search without restore   │
│  migrate       — Auto-move to cold tier                                   │
│  downsample    — Further aggregation of time-series                      │
├─────────┼──────────────────────────────────────────────────────────────────┤
│ FROZEN  │ Very rare access. Searchable snapshots from S3/GCS/Azure.       │
│         │ Minimal local disk footprint. High query latency acceptable.    │
│ Actions:│                                                                  │
│  searchable_snapshot — Required (that's what makes frozen possible)      │
│  set_priority  — 0 (lowest possible)                                      │
│  allocate      — Optional (defaults to frozen tier)                       │
├─────────┼──────────────────────────────────────────────────────────────────┤
│ DELETE  │ Data retention exceeded. Index is deleted.                      │
│ Actions:│                                                                  │
│  delete        — Delete the index (optional: take snapshot first)        │
│  wait_for_snapshot — Wait for SLM snapshot before deleting               │
└─────────┴──────────────────────────────────────────────────────────────────┘

Phase transition timing:
  Each phase (except HOT and DELETE) has a minimum age:
  The index must be at least this old before ILM attempts the transition

  Timing is relative to the rollover date (if rollover is used) or index creation:
  min_age in WARM: "3d" → 3 days after rollover (not 3 days after hot phase entered)
  min_age in COLD: "30d" → 30 days after rollover

  ILM checks interval (default: 10 minutes):
  indices.lifecycle.poll_interval: "10m"
  ILM does NOT transition immediately when min_age is reached
  It transitions at the NEXT poll after min_age is exceeded
  For time-sensitive transitions: reduce poll_interval (adds cluster overhead)
```

## Section 2: Rollover

**Q3. What is rollover and why is it the most important ILM action?**
A: Rollover is the action that creates a new "active" index when the current one exceeds defined thresholds. It is the foundation of time-series index management — instead of one endlessly growing index, rollover produces a series of bounded indices that can be managed independently through their lifecycle:

```
Without rollover:
  logs → single index, grows forever → eventually 10TB → terrible performance

With rollover:
  logs-000001 → 50GB → ROLLED OVER → enters lifecycle (warm → cold → delete)
  logs-000002 → 50GB → ROLLED OVER → enters lifecycle
  logs-000003 → currently active (writes here)

Rollover conditions (ANY condition met triggers rollover):
  max_age:       time since index creation (or last rollover)
  max_size:      total size of primary shards (not replicas)
  max_docs:      document count (approximate, based on segment metadata)
  max_primary_shard_size: size of the LARGEST primary shard

  Example: rollover when (age > 1 day) OR (primary size > 50GB) OR (docs > 100M)

How rollover works mechanically:

  1. An alias (or data stream) points to the current write index:
     alias "logs" → points to "logs-000001"

  2. ILM checks rollover conditions (every poll_interval):
     logs-000001 age: 26 hours → exceeds max_age: 1d

  3. ILM creates new index:
     "logs-000002" with same mappings and settings as the rollover template

  4. ILM atomically updates the alias:
     "logs" write alias → now points to "logs-000002"
     "logs" read alias → includes BOTH logs-000001 AND logs-000002

  5. logs-000001 is no longer the write target:
     Begins lifecycle (warm phase after 3d, cold after 30d, etc.)

  6. logs-000002 is now active:
     New writes go here, ILM monitors for next rollover

Index naming convention:
  Rollover requires 6-digit suffix: logs-000001, logs-000002, etc.
  The suffix increments on each rollover
  Custom naming via data streams: .ds-logs-2024.01.15-000001
```

**Q4. How do you create an ILM policy and attach it to an index template?**

```javascript
// Step 1: Create the ILM policy
PUT /_ilm/policy/loan_events_policy
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",   // start immediately on index creation
        "actions": {
          "rollover": {
            "max_primary_shard_size": "50gb",
            "max_age": "1d",
            "max_docs": 100000000
          },
          "set_priority": {
            "priority": 100  // highest recovery priority
          }
        }
      },
      "warm": {
        "min_age": "3d",   // 3 days after rollover
        "actions": {
          "set_priority": { "priority": 50 },
          "readonly": {},           // mark read-only before forcemerge
          "forcemerge": {
            "max_num_segments": 1   // merge all segments into 1
          },
          "shrink": {
            "number_of_shards": 1   // reduce from 5 primary shards to 1
          },
          "allocate": {
            "number_of_replicas": 1  // reduce replicas (was 2 in hot)
          }
        }
      },
      "cold": {
        "min_age": "30d",  // 30 days after rollover
        "actions": {
          "set_priority": { "priority": 0 },
          "allocate": {
            "number_of_replicas": 0,  // no replicas in cold (read-only, snapshot backed)
            "require": { "data": "cold" }  // move to cold-tier nodes
          },
          "searchable_snapshot": {
            "snapshot_repository": "s3_repository",
            "force_merge_index": true  // merge before snapshotting
          }
        }
      },
      "frozen": {
        "min_age": "90d",  // 90 days after rollover
        "actions": {
          "searchable_snapshot": {
            "snapshot_repository": "s3_repository"
          }
        }
      },
      "delete": {
        "min_age": "365d", // 365 days after rollover
        "actions": {
          "wait_for_snapshot": {
            "policy": "daily_snapshot_policy"  // ensure snapshot exists before delete
          },
          "delete": {}
        }
      }
    }
  }
}

// Step 2: Create a component template for settings (reusable)
PUT /_component_template/loan_events_settings
{
  "template": {
    "settings": {
      "number_of_shards": 2,
      "number_of_replicas": 1,
      "index.lifecycle.name": "loan_events_policy",  // attach ILM policy
      "index.lifecycle.rollover_alias": "loan_events" // alias ILM uses for rollover
    }
  }
}

// Step 3: Create a component template for mappings (reusable)
PUT /_component_template/loan_events_mappings
{
  "template": {
    "mappings": {
      "properties": {
        "@timestamp":   { "type": "date" },
        "loan_id":      { "type": "keyword" },
        "event_type":   { "type": "keyword" },
        "borrower_id":  { "type": "keyword" },
        "amount":       { "type": "scaled_float", "scaling_factor": 100 },
        "status":       { "type": "keyword" },
        "description":  { "type": "text" },
        "created_at":   { "type": "date" }
      }
    }
  }
}

// Step 4: Create an index template composing the components
PUT /_index_template/loan_events_template
{
  "index_patterns": ["loan_events-*"],  // applies to indices matching this pattern
  "composed_of": ["loan_events_settings", "loan_events_mappings"],
  "priority": 200,  // higher priority than default templates
  "template": {
    "settings": {
      "index.lifecycle.name": "loan_events_policy",
      "index.lifecycle.rollover_alias": "loan_events"
    }
  }
}

// Step 5: Create the initial index and alias
PUT /loan_events-000001
{
  "aliases": {
    "loan_events": {
      "is_write_index": true  // this is the active write index
    }
  }
}
// ILM begins managing loan_events-000001 immediately
// When rollover triggers: loan_events-000002 is created automatically

// Step 6: Write documents via the alias (not the index directly)
POST /loan_events/_doc
{
  "@timestamp": "2024-01-15T10:30:00Z",
  "loan_id": "LAN-2024-001",
  "event_type": "disbursed",
  "amount": 500000
}
// Elasticsearch routes to loan_events-000001 (current write index)
// After rollover: routes to loan_events-000002 automatically
// No application change required — alias handles routing transparently
```

## Section 3: Data Streams

**Q5. What are data streams and how do they simplify ILM compared to managing aliases manually?**
A: Data streams are a higher-level abstraction over time-series indices that automates the alias and rollover machinery. Instead of manually creating aliases, setting `is_write_index`, and managing rollover, a data stream handles all of this internally. Data streams are the recommended approach for any append-only time-series data:

```
Data stream vs manual alias approach:

  Manual alias approach (more control, more complexity):
    You create: loan_events-000001 + alias "loan_events" with is_write_index:true
    ILM creates: loan_events-000002, -000003, etc. on rollover
    You manage: alias definition, write index designation
    Flexible: can have non-time-series data mixed in

  Data stream approach (simpler, more constraints):
    You create: a data stream named "loan_events"
    Elasticsearch creates: .ds-loan_events-2024.01.15-000001 (backing index)
    ILM creates: .ds-loan_events-2024.01.16-000002, etc. on rollover
    You don't manage: aliases, write index flags (automatic)
    Constraint: documents MUST have @timestamp field
    Constraint: only append — no updates/deletes by default
                (updates possible via _update_by_query, deletes via delete_by_query)
    Constraint: index name format is managed by Elasticsearch

Data stream internals:
  A data stream is a named abstraction over one or more backing indices:

  data stream: loan_events
    ├── .ds-loan_events-2024.01.13-000001  (oldest, in COLD phase)
    ├── .ds-loan_events-2024.01.14-000002  (in WARM phase)
    └── .ds-loan_events-2024.01.15-000003  (current HOT write target)

  Searches on "loan_events" fan out to ALL backing indices
  Writes go only to the latest backing index (the write target)
  Rollover: ILM creates new backing index, promotes it to write target

Creating a data stream (requires a matching index template first):

// Step 1: Create the ILM policy (same as before)
PUT /_ilm/policy/logs_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" }
        }
      },
      "warm": { "min_age": "7d", "actions": { "forcemerge": { "max_num_segments": 1 } } },
      "delete": { "min_age": "30d", "actions": { "delete": {} } }
    }
  }
}

// Step 2: Create an index template with data_stream declared
PUT /_index_template/loan_events_template
{
  "index_patterns": ["loan_events"],        // data stream name (not a pattern)
  "data_stream": {},                         // ← this declares it as a data stream template
  "template": {
    "settings": {
      "index.lifecycle.name": "logs_policy",
      "number_of_shards": 2,
      "number_of_replicas": 1
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },    // @timestamp is REQUIRED for data streams
        "loan_id":    { "type": "keyword" },
        "event_type": { "type": "keyword" }
      }
    }
  }
}

// Step 3: Create the data stream (Elasticsearch creates the first backing index)
PUT /_data_stream/loan_events
// Response: { "acknowledged": true }
// Backing index .ds-loan_events-2024.01.15-000001 is created automatically

// Step 4: Index documents (must include @timestamp)
POST /loan_events/_doc
{
  "@timestamp": "2024-01-15T10:30:00Z",
  "loan_id": "LAN-001",
  "event_type": "approved"
}

// Checking data stream status:
GET /_data_stream/loan_events
// Response:
{
  "data_streams": [{
    "name": "loan_events",
    "timestamp_field": { "name": "@timestamp" },
    "indices": [
      {
        "index_name": ".ds-loan_events-2024.01.13-000001",
        "index_uuid": "...",
        "prefer_ilm": true,
        "ilm_policy": "logs_policy",
        "managed_by": "Index Lifecycle Management"
      },
      {
        "index_name": ".ds-loan_events-2024.01.15-000003",
        "index_uuid": "...",
        "prefer_ilm": true
      }
    ],
    "generation": 3,     // how many backing indices have been created
    "status": "GREEN",
    "template": "loan_events_template"
  }]
}

// Rollover a data stream manually (for testing or immediate transition):
POST /loan_events/_rollover

// Searching across all backing indices (transparent):
GET /loan_events/_search
{
  "query": {
    "range": { "@timestamp": { "gte": "now-7d/d" } }
  }
}
// Searches .ds-loan_events-...-000001, -000002, -000003 simultaneously
```

## Section 4: Index Tiers

**Q6. What are data tiers and how do they work with ILM to optimize storage costs?**
A: Data tiers are groups of nodes designated for a specific phase of data lifecycle. Each tier uses different hardware — NVMe SSDs for hot data, HDDs for warm, object storage for frozen. ILM automatically migrates indices between tiers as they progress through phases:

```
Tier architecture:

  Content tier (content):   Indices with no time-series lifecycle (product catalog, users)
                            Mix of SSD and HDD; no automatic migration
  Hot tier (data_hot):      Active writes + recent reads. NVMe SSD.
                            High CPU and memory for indexing throughput
  Warm tier (data_warm):    Read-only, occasional searches. SSD or HDD.
                            Medium CPU; primarily I/O
  Cold tier (data_cold):    Infrequent reads. HDD or similar.
                            Low CPU; high storage density
  Frozen tier (data_frozen): Very rare reads. Searchable snapshots from S3/GCS/Azure.
                              Minimal local disk; data retrieved on demand from object storage

Node tier assignment (elasticsearch.yml):
  # On hot nodes:
  node.roles: [data_hot, master]

  # On warm nodes:
  node.roles: [data_warm]

  # On cold nodes:
  node.roles: [data_cold]

  # On frozen nodes:
  node.roles: [data_frozen]

  # On dedicated master nodes (don't hold data):
  node.roles: [master]

ILM tier migration (migrate action):
  When "migrate" action is included in a phase (default when tiers exist):
    ILM adds index.routing.allocation.include._tier_preference = data_hot
    On WARM transition: changes to data_warm,data_hot (prefers warm, falls back to hot)
    On COLD transition: changes to data_cold,data_warm,data_hot
    On FROZEN transition: changes to data_frozen (searchable snapshots)

  Elasticsearch automatically moves shards to the appropriate tier nodes
  Migration is transparent — no manual shard allocation needed

Cost analysis example:
  Hot tier: NVMe SSD (AWS i3en.2xlarge: $0.63/hr, 7.5TB NVMe)
  Warm tier: EBS HDD (r6g.2xlarge + st1 EBS: $0.20/hr, 7.5TB)
  Cold tier: EBS HDD (m6g.large + sc1 EBS: $0.10/hr, 7.5TB)
  Frozen tier: S3 Standard-IA ($0.0125/GB/month) + frozen node ($0.05/hr)

  For 1TB/day of log ingestion with 90-day retention:
    Without tiers: all 90TB on hot nodes → 12 i3en.2xlarge → ~$5,400/month
    With tiers:
      Hot (7 days): 7TB → 1 i3en.2xlarge → $450/month
      Warm (30 days): 30TB → 4 r6g.2xlarge + EBS → $600/month
      Cold (53 days): 53TB → 7 m6g.large + EBS → $700/month
      Frozen (remaining): S3 at $0.0125/GB → ~$400/month
    Total with tiers: ~$2,150/month (60% cost reduction)

Checking tier allocation:
GET /_cat/shards/loan_events-*?v&h=index,shard,prirep,state,node,tier
// Shows which tier each shard is on

GET /loan_events-000001/_settings?filter_path=*.settings.index.routing
// Shows current tier preference routing
```

## Section 5: Monitoring and Troubleshooting ILM

**Q7. How do you monitor ILM progress and diagnose why an index is stuck in a phase?**
A: ILM runs asynchronously in the background. Indices do not always transition at the exact expected time, and when they get stuck, there is usually a specific actionable error. Knowing the diagnostic commands and common failure modes is essential for production operation:

```javascript
// ── Checking ILM status per index ─────────────────────────────────────────────

GET /loan_events-000001/_ilm/explain
// Response:
{
  "indices": {
    "loan_events-000001": {
      "index": "loan_events-000001",
      "managed": true,
      "policy": "loan_events_policy",
      "lifecycle_date_millis": 1705313400000,  // when ILM clock started (rollover date)
      "age": "5d",                              // age since lifecycle date
      "phase": "warm",
      "phase_time_millis": 1705745400000,       // when warm phase started
      "action": "forcemerge",                   // current action being executed
      "action_time_millis": 1705745500000,
      "step": "check-resource-availability",    // current step within action
      "step_time_millis": 1705745501000,
      "phase_execution": {
        "policy": "loan_events_policy",
        "version": 3,
        "modified_date_in_millis": 1705000000000,
        "phase_definition": { ... }
      }
    }
  }
}

// ── Index stuck — error state ─────────────────────────────────────────────────
GET /loan_events-000001/_ilm/explain
// Response when stuck:
{
  "indices": {
    "loan_events-000001": {
      "managed": true,
      "policy": "loan_events_policy",
      "phase": "warm",
      "action": "shrink",
      "step": "ERROR",                  // ← stuck here
      "step_info": {
        "type": "illegal_state_exception",
        "reason": "index [loan_events-000001] is the write index for alias [loan_events]"
        // Can't shrink a write index — must remove write alias first
      },
      "failed_step": "check-shrink-allocation",
      "failed_step_retry_count": 3      // ILM has retried 3 times
    }
  }
}

// ── All indices with ILM errors ───────────────────────────────────────────────
GET /_ilm/explain?only_errors=true
// Returns only indices in ERROR state — useful for monitoring dashboards

// ── Retry a failed step ───────────────────────────────────────────────────────
// After fixing the root cause: tell ILM to retry
POST /loan_events-000001/_ilm/retry
// ILM re-attempts the failed step

// ── Move an index to a specific step manually ─────────────────────────────────
// For testing or recovering from severe state corruption:
POST /_ilm/move/loan_events-000001
{
  "current_step": {
    "phase": "warm",
    "action": "shrink",
    "name": "ERROR"
  },
  "next_step": {
    "phase": "warm",
    "action": "forcemerge",   // skip shrink, go to next action
    "name": "forcemerge"
  }
}

// ── Common ILM errors and fixes ────────────────────────────────────────────────

// Error 1: "index is the write index for alias"
// Cause: ILM tried to perform forcemerge or shrink but index is still write target
// This should not happen (rollover should have created a new write index)
// Fix: check that rollover happened; if not, manually rollover:
POST /loan_events/_rollover
// Then retry ILM:
POST /loan_events-000001/_ilm/retry

// Error 2: "Cannot shrink index because it has ... primary shards on ... nodes"
// Cause: shrink requires all primary shards to be on ONE node first
// Shrink works by: copy all data to one node → create a new merged index
// If allocation blocked: shrink cannot proceed
// Fix: check allocation explanation:
GET /_cluster/allocation/explain
{
  "index": "loan_events-000001",
  "shard": 0,
  "primary": true
}
// Common cause: not enough disk space on any single warm node to hold all shards

// Error 3: "forcemerge failed because index is not read-only"
// Cause: forcemerge action requires readonly action first in the same phase
// Fix: update the ILM policy to include readonly BEFORE forcemerge:
PUT /_ilm/policy/loan_events_policy
{
  "policy": {
    "phases": {
      "warm": {
        "actions": {
          "readonly": {},          // must come before forcemerge
          "forcemerge": { "max_num_segments": 1 }
        }
      }
    }
  }
}

// Error 4: "snapshot repository not found"
// Cause: searchable_snapshot action references a repo that doesn't exist
// Fix: register the snapshot repository first:
PUT /_snapshot/s3_repository
{
  "type": "s3",
  "settings": {
    "bucket": "my-elasticsearch-snapshots",
    "region": "ap-south-1",
    "base_path": "elasticsearch/snapshots"
  }
}

// ── Monitoring ILM health proactively ─────────────────────────────────────────
// Useful monitoring query for ops dashboards:
GET /_ilm/explain?only_errors=true
// Alert if any index has "step": "ERROR"

// Check ILM poll interval and ensure it's running:
GET /_cluster/settings?include_defaults=true&filter_path=*.indices.lifecycle.poll_interval
// Should be "10m" by default

// Check ILM is not stopped:
GET /_ilm/status

// Other values: "STOPPING" (in transition), "STOPPED" (paused)
// If STOPPED: POST /_ilm/start to resume
```

## Section 6: Advanced ILM Patterns

**Q8. How do you update an existing ILM policy and what happens to indices already being managed?**
A: ILM policy updates apply immediately to all indices using the policy — but with an important nuance: indices already IN a phase do not restart the phase. They apply the new policy at their next step within the current action or at the start of the next phase:

```javascript
// Updating a policy — immediate effect:
PUT /_ilm/policy/loan_events_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_primary_shard_size": "25gb",  // was 50gb — changed to smaller
            "max_age": "12h"                    // was 1d — changed to 12 hours
          }
        }
      },
      "warm": { "min_age": "7d", "actions": { "forcemerge": { "max_num_segments": 1 } } },
      "delete": { "min_age": "90d", "actions": { "delete": {} } }
    }
  }
}

// What happens to existing indices after policy update:
// loan_events-000001 (currently in WARM phase, day 5 of 7-day minimum):
//   Continues in WARM phase until day 7
//   At day 7: transitions to DELETE per the NEW policy (30d was removed, now direct to delete)
//   The new policy is applied at the NEXT PHASE TRANSITION

// loan_events-000003 (currently in HOT phase, age: 8 hours):
//   ILM checks: 8h < new max_age of 12h → no rollover yet
//   At 12h: rollover triggers (new condition)

// Policy version tracking:
GET /_ilm/policy/loan_events_policy
// Response includes:
{
  "loan_events_policy": {
    "version": 4,               // increments with each update
    "modified_date": "2024-01-15T10:30:00.000Z",
    "policy": { ... }
  }
}

// Checking which policy version an index is using:
GET /loan_events-000001/_ilm/explain
// phase_execution.version: 3  ← using older version
// If version is stale: index will update to new version at next step

// Forcefully applying updated policy to an index NOW:
// (Instead of waiting for next step): remove and re-add ILM policy:
PUT /loan_events-000001/_settings
{
  "index.lifecycle.name": null  // detach from ILM
}
PUT /loan_events-000001/_settings
{
  "index.lifecycle.name": "loan_events_policy"  // re-attach (picks up latest version)
}

// Dry-run policy update (preview what would change):
// No native dry-run; use explain API to compare current state with intended:
GET /loan_events-000001/_ilm/explain  // current state
// Compare against new policy manually

// Rolling out policy changes safely:
// 1. Test on a non-production index first
// 2. Change only one phase at a time
// 3. After changing: monitor GET /_ilm/explain?only_errors=true for 1 poll cycle (10min)
// 4. If errors appear: rollback by re-applying the previous policy definition
```

**Q9. How do searchable snapshots work in ILM and what is the tradeoff between frozen and cold tiers?**
A: Searchable snapshots allow an index to be searched directly from object storage (S3, GCS, Azure Blob) without fully restoring it to local disk. ILM uses this in cold and frozen phases to dramatically reduce storage costs while maintaining query capability:

```
Searchable snapshot architecture:

  Traditional snapshot:
    Index → snapshot to S3 → index deleted from nodes → restore → copy back from S3
    Restore time: minutes to hours for large indices
    Cannot search until fully restored

  Searchable snapshot:
    Index → snapshot to S3 → index "mounted" as searchable snapshot
    Local disk: only caches recently accessed data (not the full index)
    Search: reads from S3 cache; on cache miss → fetches from S3 → caches locally
    Query latency: higher than local index (S3 access adds 50-500ms)
    Storage cost: ~$0.023/GB/month (S3) vs ~$0.10+/GB/month (EBS)

Two types of searchable snapshot:
  1. Fully mounted (cold tier):
     - All shard data cached locally on cold-tier nodes
     - Query latency: similar to regular index
     - Storage: full index on both S3 AND cold nodes (during operation)
     - Use: cold data that is occasionally searched and latency matters

  2. Partially mounted (frozen tier):
     - Only recently accessed data cached locally
     - Cache size limited (configurable): xpack.searchable.snapshot.shared_cache.size
     - Cache misses → S3 fetch → higher latency (100ms-2s per miss)
     - Storage: almost no local disk (shared cache only)
     - Use: very rarely accessed data where latency is less important than cost

ILM with searchable snapshots:
  In cold phase:
  "cold": {
    "min_age": "30d",
    "actions": {
      "searchable_snapshot": {
        "snapshot_repository": "s3_repository",
        "force_merge_index": true  // forcemerge before snapshotting (fewer files in S3)
      }
    }
  }
  ILM steps:
    1. Force merge to 1 segment (if force_merge_index: true)
    2. Take snapshot of the index to s3_repository
    3. Delete the original index
    4. Mount the snapshot as a "fully mounted" searchable snapshot
    5. The mounted index replaces the original on cold-tier nodes
    6. Data stream seamlessly includes the mounted index in searches

  In frozen phase:
  "frozen": {
    "min_age": "90d",
    "actions": {
      "searchable_snapshot": {
        "snapshot_repository": "s3_repository"
      }
    }
  }
  ILM steps (if coming from cold):
    1. Unmount the fully-mounted (cold) version
    2. Re-mount as partially-mounted (frozen) version
    3. Local disk usage drops to near zero

Querying frozen indices:
  Frozen indices respond to queries but with higher latency
  Signal to Elasticsearch that you accept the latency:
  GET /loan_events/_search?ignore_throttled=false   // include frozen (default false in 7.x)
  GET /loan_events/_search?ignore_throttled=true    // exclude frozen (for latency-sensitive)
  Elasticsearch 8.x: throttling behavior changed — check documentation for version

  // In query: exclude frozen indices from time-sensitive operations
  GET /loan_events/_search
  {
    "query": {
      "bool": {
        "filter": [
          { "range": { "@timestamp": { "gte": "now-30d" } } }
        ]
      }
    }
  }
  // If ILM/date-math routing is configured: Elasticsearch may skip frozen indices
  // for queries that only cover recent time ranges

S3 repository setup (required for searchable snapshots):
PUT /_snapshot/s3_repository
{
  "type": "s3",
  "settings": {
    "bucket": "my-es-snapshots",
    "region": "ap-south-1",
    "base_path": "snapshots/loan-events",
    "compress": true,              // compress snapshots (~50% size reduction)
    "server_side_encryption": true // encrypt at rest in S3
  }
}
// Verify repository:
POST /_snapshot/s3_repository/_verify
```

**Q10. How do you handle ILM for multi-tenant data where different tenants have different retention requirements?**

```javascript
// Problem: tenant A requires 30-day retention, tenant B requires 365-day retention

// Correct approach: per-tenant ILM policies OR policy-per-retention-tier

// ── Approach 1: Per-tenant data streams + ILM policies ────────────────────────
// Best when: small number of tenants (< 50), very different requirements

// Policy for standard retention (30 days):
PUT /_ilm/policy/standard_30d_policy
{

PUT /_ilm/policy/extended_365d_policy
{
  "policy": {

      "hot":    { "actions": { "rollover": { "max_age": "1d", "max_primary_shard_size": "10gb" } } },

    }
  }
}

// Per-tenant index templates:
PUT /_index_template/tenant_a_template
{
  "index_patterns": ["events-tenant_a-*"],
  "data_stream": {},
  "template": {
    "settings": {
      "index.lifecycle.name": "standard_30d_policy",

}

PUT /_index_template/tenant_b_template
{
  "index_patterns": ["events-tenant_b-*"],
  "data_stream": {},

    "settings": {
      "index.lifecycle.name": "extended_365d_policy",
      "number_of_shards": 2,
      "number_of_replicas": 1
    }
  }
}

// Create data streams per tenant:
PUT /_data_stream/events-tenant_a
PUT /_data_stream/events-tenant_b

// Index with tenant routing:
POST /events-tenant_a/_doc
{
  "@timestamp": "2024-01-15T10:30:00Z",
  "event_type": "loan_approved",
  "loan_id": "LAN-001"
}

// ── Approach 2: Shared index with custom routing + ILM ────────────────────────
// Best when: many tenants (hundreds), similar retention requirements
// Use a single data stream with custom ILM date field:

PUT /_ilm/policy/shared_tenant_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_age": "1d", "max_docs": 5000000 }

      }
    }
  }

POST /events/_delete_by_query
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "tenant_id": "tenant_a" } },
        { "range": { "@timestamp": { "lt": "now-30d/d" } } }
      ]
    }
  }
}
// delete_by_query marks documents as deleted (in .liv files)
// Actual reclamation happens on next segment merge
// Less efficient than DROP index but necessary for per-tenant within shared index

// ── Approach 3: ILM with metadata-driven retention ────────────────────────────
// Dynamic ILM based on tenant metadata (advanced — requires custom orchestration)
// Application determines ILM policy at index creation time:
async function createTenantDataStream(tenantId: string, retentionDays: number): Promise<void> {
    const policyName = `retention_${retentionDays}d`;

    // Create policy if it doesn't exist:
    await esClient.ilm.putLifecycle({
        name: policyName,
        body: {
            policy: {
                phases: {
                    hot: { actions: { rollover: { max_age: '1d' } } },
                    delete: { min_age: `${retentionDays}d`, actions: { delete: {} } }
                }
            }
        }
    });

    // Create index template for this tenant:
    await esClient.indices.putIndexTemplate({
        name: `${tenantId}_template`,
        body: {
            index_patterns: [`events-${tenantId}-*`],
            data_stream: {},
            template: {
                settings: { 'index.lifecycle.name': policyName }
            }
        }
    });

    // Create data stream:
    await esClient.indices.createDataStream({ name: `events-${tenantId}` });
}
```

## Section 8: Scenario-Based Questions

**Q11. "Your Elasticsearch cluster has 50,000 shards and the cluster state is causing master node instability. You have 500 daily log indices each with 5 primary shards and 1 replica = 5,000 shards. How do you use ILM to reduce shard count?"**

```javascript
// Problem: shard overhead
// 500 indices × 5 primary × 2 (primary + replica) = 5,000 shards
// JVM heap for cluster state: ~1KB per shard → ~5MB just for shard metadata
// At 50,000 shards (across all indices): ~50MB of cluster state → master instability

// Root cause: too many primary shards per index + too many small indices

// Solution: ILM with shrink + forcemerge + rollover conditions

// Step 1: Fix new indices — smaller shard count from the start
PUT /_index_template/logs_template
{
  "index_patterns": ["logs-*"],
  "data_stream": {},
  "template": {
    "settings": {
      "number_of_shards": 1,             // was 5; reduce for small daily indices
      "number_of_replicas": 1,
      "index.lifecycle.name": "logs_policy"
    }
  }
}

// Step 2: Fix ILM policy — shrink existing indices when they become warm
PUT /_ilm/policy/logs_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_primary_shard_size": "50gb",  // only roll over when actually large
            "max_age": "1d"
          },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "2d",
        "actions": {
          "set_priority": { "priority": 50 },
          "readonly": {},
          "shrink": {
            "number_of_shards": 1    // 5 primary shards → 1 primary shard
          },
          "forcemerge": {
            "max_num_segments": 1    // all segments → 1 segment
          },
          "allocate": {
            "number_of_replicas": 1  // keep 1 replica (data safety)
          }
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "allocate": {
            "number_of_replicas": 0  // no replicas (snapshot is backup)
          },
          "searchable_snapshot": {
            "snapshot_repository": "s3_repo"
          }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": {
          "wait_for_snapshot": { "policy": "daily_snapshot" },
          "delete": {}
        }
      }
    }
  }
}

// Result after ILM processes all indices:
// Today's index: 1 primary × 2 = 2 shards (was 5 primary × 2 = 10)
// Warm indices (2-30 days): 1 primary × 2 = 2 shards (shrank from 10)
// Cold indices: 1 primary × 1 = 1 shard (0 replicas, mounted snapshot)
// 500 indices:
//   7 hot: 7 × 2 = 14 shards
//   23 warm: 23 × 2 = 46 shards
//   470 cold (searchable snapshots): 470 × 1 = 470 shards
//   Total: 530 shards (was 5,000 → 90% reduction)

// Step 3: Apply shrink to existing warm indices immediately
// (ILM won't retroactively shrink — must apply to existing indices manually or via update_by_query)
// For existing hot indices: update settings to use new ILM policy
POST /_ilm/stop           // pause ILM
PUT /logs-000001/_settings { "index.lifecycle.name": "logs_policy" }
// ... repeat for all existing indices
POST /_ilm/start          // resume ILM

// Monitoring shard count:
GET /_cat/shards?v&h=index,shard,prirep,state,node | wc -l
GET /_cluster/health?filter_path=active_shards,relocating_shards
// Alert if active_shards > 30,000 (adjust threshold based on heap)
```

**Q12. "An ILM-managed index has been stuck in the 'warm' phase for 5 days. The policy says it should delete after 30 days from rollover, but the index is 45 days old. Diagnose and fix."**

```javascript
// Step 1: Check ILM explain output for the stuck index
GET /loan_events-000003/_ilm/explain
// Response (example):
{
  "indices": {
    "loan_events-000003": {
      "managed": true,
      "policy": "loan_events_policy",

      "action": "forcemerge",
      "step": "ERROR",
      "step_info": {
        "type": "elasticsearch_exception",

      "failed_step": "forcemerge",
      "failed_step_retry_count": 12
    }
  }
}

// Diagnosis: index is in RECOVERY state (shard relocation in progress)
// forcemerge cannot run while shards are moving to warm nodes
// ILM retried 12 times over 5 days; retry_count is high

// Step 2: Check why the index is still in RECOVERY
GET /_cat/shards/loan_events-000003?v&h=index,shard,prirep,state,node,unassigned.reason

// index               shard prirep state        node         unassigned.reason
// loan_events-000003  0     p      STARTED      warm-node-1
// loan_events-000003  0     r      UNASSIGNED   -            NODE_LEFT

{
  "index": "loan_events-000003",
  "shard": 0,
  "primary": false
}
// Response: "no nodes to allocate to" — warm tier has only 1 node, replica can't be placed

// Step 4: Fix the allocation issue
// Option A: Add another warm-tier node (long-term fix)
// Option B: Set replicas to 0 temporarily:
PUT /loan_events-000003/_settings
{
  "index.number_of_replicas": 0

// Because ILM transitions happen per-phase, and the index is STUCK in warm phase
// It can't advance to cold/delete while it's in ERROR state

// Step 7: Prevent recurrence
// Add warm tier redundancy OR set replicas: 0 in ILM policy for warm phase:
PUT /_ilm/policy/loan_events_policy
{
  "policy": {
    "phases": {
      "warm": {
        "min_age": "3d",
        "actions": {
          "readonly": {},
          "allocate": {
            "number_of_replicas": 0   // no replicas in warm (snapshot is safety net)

          "forcemerge": { "max_num_segments": 1 }
        }
      }
    }
  }
}

// Additional diagnostic commands:
GET /_ilm/explain?only_errors=true                   // all errors at once
```

## Quick Reference Table

| ILM Phase | Minimum Age | Purpose | Key Actions |
|---|---|---|---|
| Hot | 0ms | Active writes + frequent reads | `rollover`, `set_priority` |
| Warm | Typically 3–7d | Read-only, moderate access | `readonly`, `forcemerge`, `shrink`, `allocate` |
| Cold | Typically 30–60d | Infrequent access | `allocate` (cold nodes), `searchable_snapshot` |
| Frozen | Typically 90–180d | Rare access, object storage | `searchable_snapshot` (partial mount) |
| Delete | Retention limit | Data expired | `wait_for_snapshot`, `delete` |

| Rollover condition | Trigger | Use when |
|---|---|---|
| `max_age` | Time since creation/rollover | Time-series data with predictable size |
| `max_primary_shard_size` | Largest primary shard size | Data size varies; avoid over-sharding |
| `max_docs` | Document count | Even document distribution matters |
| `max_size` | Total primary size (all shards) | Less common; prefer per-shard size |

| Diagnostic command | Use for |
|---|---|
| `GET /<index>/_ilm/explain` | Current ILM state, phase, action, errors |
| `GET /_ilm/explain?only_errors=true` | All indices with ILM errors |
| `POST /<index>/_ilm/retry` | Retry after fixing root cause |
| `POST /_ilm/move/<index>` | Manually advance to a specific step |
| `GET /_ilm/status` | Check if ILM is RUNNING/STOPPED |
| `POST /_ilm/stop` / `POST /_ilm/start` | Pause/resume ILM globally |
| `GET /_cat/shards/<index>?v` | Shard state and node placement |
| `GET /_cluster/allocation/explain` | Why a shard is unassigned |

| Common ILM error | Root cause | Fix |
|---|---|---|
| "index is the write index" | Rollover hasn't happened | Manually `POST /<alias>/_rollover` |
| "forcemerge: index not read-only" | `readonly` missing before `forcemerge` | Add `readonly` action first in policy |
| "Cannot shrink: shards on N nodes" | Shards must be on one node | Check disk space on warm nodes |
| "snapshot repository not found" | Repo not registered | `PUT /_snapshot/<repo>` |
| Stuck in ERROR for days | Any unresolved error | Fix root cause, `POST /_ilm/retry` |
| Age > delete min_age but not deleted | Stuck in earlier phase | Fix the stuck phase, then advance |

---

**Tip for interviews:** Five things separate strong candidates on Elasticsearch ILM: (1) explaining **rollover as the cornerstone of ILM** — rollover creates a new write index when conditions are met, the old index enters the lifecycle, and searches transparently cover all backing indices via the alias or data stream; without rollover, ILM cannot function for time-series data because a single growing index has no natural entry point into the lifecycle; (2) understanding **the timing model precisely** — `min_age` is relative to the rollover date (or index creation if no rollover), ILM polls every 10 minutes by default so transitions do not happen exactly at `min_age`, and an index stuck in an error state in an earlier phase will NOT advance to delete even if the delete `min_age` has passed; (3) knowing **the shrink action requirements** — shrink must run on a non-write index (rollover must have already happened), all primary shards must first be allocated to a single node (ILM handles this automatically), the target shard count must be a divisor of the original count, and the index must be read-only; this is the action most likely to get stuck in production; (4) distinguishing **cold (fully mounted) vs frozen (partially mounted) searchable snapshots** — cold keeps all shard data cached locally so query latency is similar to a regular index, frozen uses a shared cache so most reads hit S3 directly with 100ms–2s latency; the choice is a cost vs latency tradeoff, not a data safety question since both are backed by the same S3 snapshot; and (5) being able to **diagnose a stuck index** — `GET /<index>/_ilm/explain` shows the current phase/action/step and the error message; `POST /<index>/_ilm/retry` retries after the root cause is fixed; and `POST /_ilm/move/<index>` with explicit current/next step can skip a failed action entirely when the correct fix is to bypass rather than repair.
