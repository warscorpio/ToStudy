# Aggregations in Elasticsearch — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are the three families of aggregations in Elasticsearch and how do they differ?**
A: Elasticsearch aggregations are divided into three families: **bucket**, **metric**, and **pipeline**. Understanding which family an aggregation belongs to determines how it can be composed, nested, and what it returns:

```
Three aggregation families:

  1. BUCKET aggregations — partition documents into groups (buckets)
     Each bucket is defined by a criterion; documents that match fall into the bucket
     Bucket aggs return: an array of buckets, each with a doc_count and optional sub-aggs
     Examples: terms, date_histogram, range, filter, nested, histogram

     Analogy: GROUP BY in SQL
     SELECT status, COUNT(*) FROM loans GROUP BY status
     →
     {
       "aggs": { "by_status": { "terms": { "field": "status" } } }
     }

  2. METRIC aggregations — compute numeric values over a set of documents
     Input: a set of documents (or a bucket's documents)
     Output: one number (or a set of numbers for multi-value metrics)
     Examples:
       Single-value: avg, sum, min, max, cardinality, value_count
       Multi-value:  stats (min+max+avg+sum+count), extended_stats, percentiles, top_hits

     Analogy: aggregate functions in SQL: AVG(amount), SUM(amount), COUNT(DISTINCT borrower)

  3. PIPELINE aggregations — compute values from OTHER aggregations' output
     Input: buckets or metrics from a sibling or parent aggregation
     Output: new computed metrics or modified buckets
     Examples: moving_avg, derivative, cumulative_sum, bucket_sort, bucket_selector

     Analogy: window functions or sub-queries in SQL that operate on grouped results

Nesting rules:
  ┌─────────────────────────────────────────────────────────────────────┐
  │ Bucket agg                                                          │
  │   ├─ Can contain sub-bucket aggs (bucket within bucket)            │
  │   ├─ Can contain metric aggs (metric computed per bucket)          │
  │   └─ Can contain pipeline aggs that reference sibling metrics      │
  │                                                                     │
  │ Metric agg                                                          │
  │   └─ Cannot contain sub-aggs (leaf node)                           │
  │                                                                     │
  │ Pipeline agg                                                        │
  │   └─ References other aggs by path; not nested inside them         │
  └─────────────────────────────────────────────────────────────────────┘

How aggregations relate to the query:
  Aggregations run over the set of documents matched by the query.
  A match_all query → aggregations see ALL documents in the index.
  A filtered query → aggregations see only matched documents.
  Special case: "global" agg breaks out of query scope → sees all documents regardless.

  GET /loans/_search
  {
    "size": 0,                          // no hits needed, only agg results
    "query": {
      "term": { "status": "approved" }  // filter to approved loans
    },
    "aggs": {
      "avg_approved_amount": {
        "avg": { "field": "amount" }    // avg only over approved docs
      },
      "all_loans_avg": {
        "global": {},                   // escapes the query filter
        "aggs": {
          "avg_amount": { "avg": { "field": "amount" } }
        }
      }
    }
  }
  // avg_approved_amount: average of approved loans only
  // all_loans_avg.avg_amount: average of ALL loans (global scope)

Data structures used:
  Aggregations almost exclusively use DOC VALUES (columnar, on-disk) — NOT the inverted index
  Doc values for keyword → sorted dictionary + ordinal mapping → perfect for terms agg
  Doc values for numeric fields → delta-compressed column → perfect for avg, sum, min, max
  The inverted index (posting lists) is used for: filtering (which docs to include)
  Doc values are used for: computing values over those docs
```

**Q2. How does Elasticsearch physically execute an aggregation and why does `"size": 0` matter?**
A: Understanding the execution path clarifies why aggregations are fast for some shapes and expensive for others. Elasticsearch separates the search phase (find matching docs) from the aggregation phase (compute over those docs), and doc values are the key data structure powering the computation:

```
Aggregation execution path:

  Step 1: QUERY phase
    Build a bitset (or doc ID set) of all documents matching the query
    This is the scope of the aggregation
    Uses: inverted index → posting list intersection → bitset of matching doc IDs

  Step 2: COLLECT phase (aggregation)
    Walk through the matching doc IDs one by one (or in batches of 128)
    For each doc ID: look up its field value in doc values
    Accumulate into the aggregation's state (running sum, bucket counts, etc.)

    Example: avg aggregation over "amount" field
      Doc ID 1 → doc_values["amount"][1] = 50000
      Doc ID 2 → doc_values["amount"][2] = 75000
      Doc ID 3 → doc_values["amount"][3] = 30000
      Accumulated: sum = 155000, count = 3
      Final: avg = 155000 / 3 = 51666.67

  Step 3: REDUCE phase (coordinating node)
    Each shard returns its partial aggregation result
    Coordinating node merges partial results → final result
    For avg: collect (sum, count) from each shard → global_avg = total_sum / total_count
    For terms: merge bucket lists from each shard → global top-N

Why "size": 0 matters:
  size: 0 → Elasticsearch skips the FETCH phase (no documents returned in "hits")
  size: 10 → Top 10 matching documents are fetched and returned alongside agg results
  Cost of fetch: re-read _source from disk for each result document
  When you only want aggregation results: always set "size": 0

  Without "size": 0:
    GET /loans/_search { "aggs": { ... } }
    → Returns 10 hits (default) + aggregation results
    → 10 extra _source reads from disk: wasted I/O, network, deserialization

  With "size": 0:
    GET /loans/_search { "size": 0, "aggs": { ... } }
    → Returns 0 hits + aggregation results
    → No _source reads: faster, smaller response payload

Request timeout and circuit breakers:
  Aggregations can be memory-intensive (terms agg over high-cardinality field)
  Circuit breakers protect the heap:
    indices.breaker.request.limit: 60% of heap (default)
    If aggregation state exceeds this: request fails with CircuitBreakingException
    → means you need to reduce cardinality, increase shard size limit, or restructure
  Timeout:
    GET /loans/_search?timeout=10s { "size": 0, "aggs": { ... } }
    Returns partial results after 10s with "timed_out": true
```

## Section 2: Terms Aggregation

**Q3. How does the `terms` aggregation work internally and why are its results sometimes approximate?**
A: The `terms` aggregation groups documents by a field's distinct values — like GROUP BY in SQL. Internally it uses global ordinals (an integer dictionary over doc values) to avoid repeated string comparisons. Results are approximate for multi-shard indexes because each shard independently returns its top-N buckets, and globally-important buckets may not rank top-N on every shard:

```
Terms aggregation internals:

  Field: status (keyword, low cardinality: ~5 values)
  Doc values on disk:
    doc_0: "approved"
    doc_1: "pending"
    doc_2: "approved"
    doc_3: "rejected"
    doc_4: "approved"
    doc_5: "pending"

  Step 1: Build global ordinals (done once per segment per field, cached)
    Map distinct values to compact integers:
    0 → "approved"
    1 → "pending"
    2 → "rejected"
    Memory: O(cardinality) — one entry per distinct value

  Step 2: Collect phase
    For each matching doc: look up its ordinal from doc values
    Increment a counter array at that ordinal:
    counters = [0, 0, 0]  // indexed by ordinal

    doc_0: ordinal=0 (approved) → counters[0]++ → [1, 0, 0]
    doc_1: ordinal=1 (pending)  → counters[1]++ → [1, 1, 0]
    doc_2: ordinal=0 (approved) → counters[0]++ → [2, 1, 0]
    doc_3: ordinal=2 (rejected) → counters[2]++ → [2, 1, 1]
    doc_4: ordinal=0 (approved) → counters[0]++ → [3, 1, 1]
    doc_5: ordinal=1 (pending)  → counters[1]++ → [3, 2, 1]

  Step 3: Sort by count, return top "size" results
    Result: approved=3, pending=2, rejected=1

  Step 4: Resolve ordinals → string values
    0→"approved", 1→"pending", 2→"rejected"

Global ordinals vs map execution mode:
  "execution_hint": "global_ordinals"  (default for keyword fields)
    Builds ordinal mapping once, reuses across queries → fast for repeated aggregations
    Best for: low-to-medium cardinality fields (status, category, country)

  "execution_hint": "map"
    Builds a HashMap<String, Long> directly (no ordinal building step)
    Best for: high-cardinality fields, filter context (few docs match query),
              or when the field has very high cardinality and ordinals would be wasteful

Approximation problem — why terms results can be wrong:

  Index: 3 shards, query: top 3 borrowers by loan count
  Actual (global) truth:
    Alice: 100 loans (spread: shard0=60, shard1=25, shard2=15)
    Bob:    90 loans (spread: shard0=10, shard1=50, shard2=30)
    Carol:  80 loans (spread: shard0=80, shard1=0, shard2=0)
    Dave:   70 loans (spread: shard0=5, shard1=35, shard2=30)

  Each shard returns its local top 3 (size=3):
    Shard 0 top 3: Carol=80, Alice=60, Bob=10
    Shard 1 top 3: Bob=50, Dave=35, Alice=25
    Shard 2 top 3: Bob=30, Dave=30, Alice=15

  Coordinating node merges partial counts:
    Alice: 60+25+15 = 100 ✓ (appeared in all 3 shards' top 3)
    Bob:   10+50+30 = 90  ✓ (appeared in all 3)
    Carol: 80+0+0   = 80  ← only shard 0 reported Carol
    Dave:  0+35+30  = 65  ← Carol blocked Dave from shard 0's top 3

  Final top 3: Alice=100, Bob=90, Carol=80
  But CORRECT top 3 should be: Alice=100, Bob=90, Carol=80
  In this case correct — but if size was 2:
    Shard 0 top 2: Carol=80, Alice=60  (Bob dropped from shard 0's top 2)
    Shard 1 top 2: Bob=50, Dave=35
    Shard 2 top 2: Bob=30, Dave=30
    Merged: Carol=80, Alice=60+25+15=100, Bob=50+30=80, Dave=35+30=65
    Wait — Alice still wins but Carol looks like 80 (missing shard1+2 where she had 0)
    Result: Alice=100, Carol=80, Bob=80 — Bob tied/wrong due to incomplete shard data

The fix: shard_size (request more per shard than you need globally):
  "size": 10,          // return top 10 globally
  "shard_size": 100   // but each shard returns its top 100 (to reduce miss probability)
  Default shard_size = max(10, size × 1.5)

  Rule of thumb: shard_size = 3–5× size for high-accuracy requirements
  Tradeoff: larger shard_size → more data transferred from shards → higher memory/latency

Accuracy metrics returned by terms agg:
  "sum_other_doc_count": 4250  // docs NOT in the top buckets (estimate)
  "doc_count_error_upper_bound": 120  // max possible undercount for any bucket
  If doc_count_error_upper_bound = 0 → results are exact
  If > 0 → results are approximate; increase shard_size to reduce error

Full example:
GET /loans/_search
{
  "size": 0,
  "aggs": {
    "by_status": {
      "terms": {
        "field": "status",            // must be keyword or numeric
        "size": 10,                   // top 10 buckets globally
        "shard_size": 50,             // top 50 per shard (more accurate)
        "min_doc_count": 5,           // skip buckets with < 5 docs
        "missing": "unknown",         // bucket name for docs with no status value
        "order": { "_count": "desc" }, // sort by doc count (default)
        "include": ["approved", "pending", "under_review"],  // allowlist
        "show_term_doc_count_error": true  // show per-bucket error in response
      },
      "aggs": {
        "avg_amount": { "avg": { "field": "amount" } }  // metric per bucket
      }
    }
  }
}
```

**Q4. What are global ordinals, when are they built, and how do you control their memory cost?**
A: Global ordinals are a critical optimization for the `terms` aggregation. They map each distinct keyword value to a compact integer, allowing the terms aggregation to use an integer counter array instead of a string hash map. They are built per-segment, cached in the field cache (heap), and rebuilt when the segment changes:

```
Global ordinals lifecycle:

  Per-segment ordinals (always exist for keyword doc values):
    Segment _0 local ordinals:
      0 → "approved"
      1 → "pending"
      2 → "rejected"
    Segment _1 local ordinals:
      0 → "approved"
      1 → "under_review"
      (different segments → different ordinal mappings)

  Global ordinals (built on first use per shard):
    Merge all per-segment ordinals into a single global mapping:
      Global:  0 → "approved", 1 → "pending", 2 → "rejected", 3 → "under_review"
      Segment _0 mapping: local_0→global_0, local_1→global_1, local_2→global_2
      Segment _1 mapping: local_0→global_0, local_1→global_3

    Benefit: aggregation uses a single int[] counter array → cache-friendly, fast
    Cost:    heap memory — typically a few MB for low-cardinality fields
             For 1M distinct values: can be 50–200MB of heap

  When global ordinals are rebuilt:
    Any segment change (new document refresh, segment merge, index refresh)
    → ordinals are invalidated → rebuilt on next use
    → first query after a refresh is slow (ordinal build time)

  Eager global ordinals (pre-build on refresh):
  PUT /loans/_mapping
  {
    "properties": {
      "status": {
        "type": "keyword",
        "eager_global_ordinals": true  // build ordinals at refresh time, not query time
      }
    }
  }
  // Benefit: first query is not slow (ordinals already warm)
  // Cost:    every refresh takes longer (ordinals rebuilt even if no aggregation runs)
  // Use for: fields aggregated on nearly every query (status, category, region)
  // Avoid for: rarely-aggregated high-cardinality fields

Checking global ordinal memory:
GET /loans/_stats/fielddata
{
  "indices": {
    "loans": {
      "total": {
        "fielddata": {
          "memory_size_in_bytes": 8388608,  // 8MB for global ordinals
          "evictions": 0
        }
      }
    }
  }
}

GET /_nodes/stats/indices/fielddata?fields=status,borrower_name
// Shows per-field heap usage for global ordinals
```

## Section 3: Date Histogram Aggregation

**Q5. How does the `date_histogram` aggregation work and what is the difference between `calendar_interval` and `fixed_interval`?**
A: The `date_histogram` aggregation buckets documents into time-based intervals. The critical distinction between `calendar_interval` and `fixed_interval` is whether the interval has a fixed duration in milliseconds or whether it follows calendar semantics (where months and years have varying lengths):

```
date_histogram internals:

  Field: created_at (date, stored as milliseconds since epoch in doc values)
  Interval: "month"
  Elasticsearch computes: floor(doc_timestamp / interval_size_in_ms) → bucket key

  For calendar intervals (month, year, quarter): interval size varies
    January: 31 days = 2,678,400,000ms
    February: 28/29 days = 2,419,200,000ms or 2,505,600,000ms
    Cannot use a single divisor → Elasticsearch uses calendar math (Joda-Time / java.time)

  For fixed intervals (7d, 24h, 30m): interval size is constant
    7d = 7 × 86,400,000ms = exactly 604,800,000ms
    Bucket key = floor(timestamp / 604,800,000) × 604,800,000
    Fast, deterministic, no calendar dependency

calendar_interval — aligns to calendar boundaries:
  Valid values: "minute", "hour", "day", "week", "month", "quarter", "year"
  Also: "1d", "1w", "1M", "1q", "1y" (note: "1M" = one month, "1m" = one minute)
  Behavior:
    "month" → buckets at 2024-01-01, 2024-02-01, 2024-03-01 (not equal durations)
    "week"  → buckets start on Monday (ISO week start)
    "year"  → buckets at 2023-01-01, 2024-01-01, 2025-01-01

  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "loans_per_month": {
        "date_histogram": {
          "field": "created_at",
          "calendar_interval": "month",
          "format": "yyyy-MM",         // how bucket key is displayed
          "time_zone": "Asia/Kolkata"  // shift timestamps before bucketing
        }
      }
    }
  }

fixed_interval — constant-duration buckets:
  Format: "Nd", "Nh", "Nm", "Ns" (N × day/hour/minute/second)
  "30m" = 30 minutes, "2h" = 2 hours, "7d" = 7 days
  Note: "d", "h", "m" are only valid for fixed_interval; "day","hour" for calendar_interval

  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "loans_per_15min": {
        "date_histogram": {
          "field": "created_at",
          "fixed_interval": "15m",
          "offset": "+5m"  // shift bucket start: 00:05, 00:20, 00:35 instead of 00:00, 00:15
        }
      }
    }
  }

When to use which:
  calendar_interval: reporting dashboards, monthly/quarterly business reports
                     where calendar alignment matters (Jan = January, not 30-day chunks)
  fixed_interval:    time-series data, monitoring, log analytics where uniform bucket
                     sizes matter (rate calculations, moving averages)

Time zone handling:
  Default: UTC
  Setting time_zone shifts the reference epoch before bucketing:

  "time_zone": "Asia/Kolkata"  // UTC+5:30
  A document at 2024-01-31T23:30:00 UTC
  → In IST: 2024-02-01T05:00:00 IST → falls in February bucket, not January
  Without time_zone: would be in January bucket (UTC)

  This matters for:
    Daily/weekly/monthly buckets that must align to local business days
    Dashboards showing results to users in different time zones

Extended bounds and min_doc_count:
  Problem: if no loans were disbursed in February, the February bucket simply doesn't appear
  Solution: extended_bounds forces empty buckets to appear

  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly_loans": {
        "date_histogram": {
          "field": "created_at",
          "calendar_interval": "month",
          "min_doc_count": 0,          // include empty buckets (default: 1, skips empty)
          "extended_bounds": {
            "min": "2024-01-01",       // force buckets from this date...
            "max": "2024-12-31"        // ...to this date, even if no docs
          },
          "hard_bounds": {             // EXCLUDE docs outside this range from buckets
            "min": "2024-01-01",
            "max": "2024-12-31"
          }
        }
      }
    }
  }

  extended_bounds: adds empty buckets BETWEEN min and max; docs outside still appear
  hard_bounds: clips the data itself — docs outside range are excluded from any bucket
  min_doc_count: 0 required for extended_bounds to show empty buckets

Sub-aggregations (common pattern — metrics per time bucket):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly": {
        "date_histogram": {
          "field": "created_at",
          "calendar_interval": "month"
        },
        "aggs": {
          "total_disbursed":   { "sum": { "field": "amount" } },
          "avg_loan_size":     { "avg": { "field": "amount" } },
          "unique_borrowers":  { "cardinality": { "field": "borrower_id" } },
          "by_status": {
            "terms": { "field": "status", "size": 5 }
          }
        }
      }
    }
  }
  // Result: per-month buckets, each with total, average, unique borrowers, and status breakdown
```

## Section 4: Metric Aggregations — `avg` and `sum`

**Q6. How do `avg` and `sum` aggregations work internally, and what are the key options for handling missing values and scripts?**
A: `avg` and `sum` are single-value metric aggregations — they return one number. Both operate directly on doc values, which are stored as columnar data on disk and memory-mapped by the OS, making sequential access highly cache-efficient. They are among the cheapest aggregations in Elasticsearch:

```
avg and sum internals:

  sum aggregation: Σ field_value for all matching docs
  avg aggregation: (Σ field_value) / count_of_docs_with_value

  Execution:
    For each matching doc_id (from query bitset):
      Read doc_values["amount"][doc_id]  → numeric value
      Accumulate: running_sum += value, running_count += 1
    Return: sum / count (for avg), or sum (for sum)

  Doc values for numeric fields (long, double, integer):
    Stored as delta-encoded integers on disk (compacted)
    Accessed via memory-mapped file (OS cache, not JVM heap)
    Sequential scan: ~1–2 ns per value (CPU-cache-friendly)
    For 10M matched docs: ~10–20ms just for the numeric scan

  No inverted index needed: aggregations never touch the inverted index
  The query FILTER uses the inverted index (which docs to include)
  The aggregation COMPUTE uses doc values (what values those docs have)

Basic syntax:
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "total_portfolio":   { "sum": { "field": "amount" } },
      "average_loan_size": { "avg": { "field": "amount" } },
      "max_loan":          { "max": { "field": "amount" } },
      "min_loan":          { "min": { "field": "amount" } }
    }
  }

Missing values:
  Docs without the "amount" field → skipped by default (not counted in avg denominator)
  "missing" parameter: treat absent field as if it had this value

  "avg": { "field": "amount", "missing": 0 }
  // docs with no "amount" → treated as 0 → included in avg calculation
  // avg(50000, null, 30000) default  → avg(50000, 30000) = 40000
  // avg(50000, null, 30000) missing:0 → avg(50000, 0, 30000) = 26666

  When to use "missing":
    Guaranteed fair comparison when absence means zero (e.g., "amount not yet set = 0")
    Don't use if absence means "no data" (would skew averages)

Script-based metric (when the field to aggregate doesn't exist directly):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "total_interest_income": {
        "sum": {
          "script": {
            "source": "doc['amount'].value * doc['interest_rate'].value * doc['tenure_years'].value",
            "lang": "painless"
          }
        }
      },
      "effective_yield": {
        "avg": {
          "script": {
            "source": """
              double principal = doc['amount'].value;
              double rate = doc['interest_rate'].value;
              double tenure = doc['tenure_years'].value;
              return (principal * rate * tenure) / principal;
            """,
            "lang": "painless"
          }
        }
      }
    }
  }
  // Scripts use doc values (doc['field'].value) for performance
  // Never use params._source['field'] in agg scripts — reads from stored fields (slow)
  // doc['field'].value → doc values → cache-friendly, fast

Combining with filters (most production use case):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "by_product": {
        "terms": { "field": "product_type", "size": 10 },
        "aggs": {
          "avg_amount":   { "avg": { "field": "amount" } },
          "total_amount": { "sum": { "field": "amount" } },
          "amount_stats": {
            "stats": { "field": "amount" }
            // Returns: min, max, avg, sum, count in a single pass — cheaper than 4 separate aggs
          }
        }
      }
    }
  }

Filter aggregation (compute metric over a filtered sub-set within each bucket):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "high_value_avg": {
        "filter": { "range": { "amount": { "gte": 100000 } } },
        "aggs": {
          "avg_amount": { "avg": { "field": "amount" } }
        }
      },
      "standard_avg": {
        "filter": { "range": { "amount": { "lt": 100000 } } },
        "aggs": {
          "avg_amount": { "avg": { "field": "amount" } }
        }
      }
    }
  }

  Equivalent to SQL:
  SELECT AVG(amount) FILTER (WHERE amount >= 100000) AS high_value_avg,
         AVG(amount) FILTER (WHERE amount < 100000)  AS standard_avg
  FROM loans
```

## Section 5: Cardinality Aggregation

**Q7. How does the `cardinality` aggregation work and why is it approximate?**
A: The `cardinality` aggregation counts the number of distinct values for a field — equivalent to `COUNT(DISTINCT field)` in SQL. Computing an exact distinct count requires tracking every value seen, which takes O(cardinality) memory. Instead, Elasticsearch uses the **HyperLogLog++** algorithm to produce an approximate count with bounded memory and tunable accuracy:

```
Why exact cardinality is expensive:

  Naive approach: maintain a HashSet<value> per shard
    Add every distinct value to the set
    Final count: set.size()
    Memory: O(distinct_values × avg_value_size)

    For 10M distinct borrower IDs (UUIDs, 36 bytes each):
    10,000,000 × 36 = 360MB per shard → unacceptable at scale

  HyperLogLog++ (HLL++) algorithm:
    Input: stream of values
    Hash each value → 64-bit integer
    Observe: position of the LEADING ZERO BIT in the hash
    Intuition: if max leading zeros seen = k, the stream likely has ~2^k distinct values
    Use multiple "registers" (sub-streams) → reduce variance
    Result: ~2% relative error with 8KB of memory per field per shard

    Memory: O(precision) — configurable, bounded
    Error:  ~1–2% relative error at default settings
    Speed:  same speed as sum/avg (one doc values scan)

Cardinality syntax:
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "unique_borrowers": {
        "cardinality": {
          "field": "borrower_id",         // keyword or numeric field
          "precision_threshold": 40000    // see below
        }
      },
      "unique_states": {
        "cardinality": {
          "field": "borrower_state",
          "precision_threshold": 100      // low threshold ok for ~30 states
        }
      }
    }
  }

precision_threshold — the accuracy/memory tradeoff:
  Range: 1 to 40000 (default: 3000)
  Memory per agg instance: precision_threshold × 8 bytes
    precision_threshold=40000 → 40000 × 8 = 320KB per agg per shard
    precision_threshold=3000  → 3000 × 8 = 24KB per agg per shard

  Behavior:
    If true_cardinality ≤ precision_threshold: result is ~100% accurate (no HLL approximation)
    If true_cardinality > precision_threshold: HLL kicks in, ~2% relative error

  Rule: set precision_threshold ≥ expected_max_cardinality × 1.1 for near-exact results
  Examples:
    "status" field: ~5 values → precision_threshold: 10 → exact, cheap
    "state" field: ~30 values → precision_threshold: 50 → exact, cheap
    "borrower_id": ~5M values → precision_threshold: 40000 → approximate (~2% error)
    → Cannot be exact for very high cardinality without prohibitive memory

Precision across shards:
  Each shard independently runs HLL++ → partial HLL sketch
  Coordinating node MERGES the HLL sketches (HLL++ is mergeable)
  No need to transfer all values — only sketches (8KB each) per shard
  Final merge error: same ~2% bound as single-shard

Exact count alternatives (when you need precision):
  Option 1: scripted metric agg with HashSet (exact, but expensive)
    Only for small result sets (<100K distinct values, few matched docs)
  Option 2: pre-compute distinct counts at index time
    Maintain a "unique_borrowers_today" counter in a separate index, updated by pipeline
  Option 3: Rollup or transform:
    Use Data Frame Transforms to materialize distinct counts daily
  Option 4: For truly exact counts on large datasets → use Spark/Flink pre-aggregation

Combining cardinality with date_histogram (time-series distinct counts):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly": {
        "date_histogram": {
          "field": "created_at",
          "calendar_interval": "month"
        },
        "aggs": {
          "unique_borrowers_this_month": {
            "cardinality": {
              "field": "borrower_id",
              "precision_threshold": 10000
            }
          }
        }
      }
    }
  }
  // Caveat: this counts distinct borrowers WITHIN each month
  // It does NOT deduplicate across months (same borrower in Jan + Feb = counted twice, once per month)
  // For cross-period deduplication: use an external system or approximate with HLL union

  Checking if results are reliable:
  // No built-in error_bound field (unlike terms agg)
  // Rule: if true cardinality >> precision_threshold → results undercount
  // Always set precision_threshold based on expected max cardinality, not average
```

## Section 6: Nested Aggregations

**Q8. Why do nested documents require a special `nested` aggregation and how does it differ from a regular aggregation on an object field?**
A: When Elasticsearch stores an array of objects in a document, the values from all objects in the array are flattened into the parent document's fields — losing the relationship between fields within a single object. The `nested` mapping and `nested` aggregation preserve this structure by storing each inner object as a separate hidden Lucene document, and the `nested` aggregation scopes into those hidden documents:

```
The flattening problem (object arrays without nested):

  Document:
  {
    "loan_id": "L001",
    "repayments": [
      { "month": "2024-01", "amount": 5000, "status": "on_time" },
      { "month": "2024-02", "amount": 5000, "status": "late" },
      { "month": "2024-03", "amount": 5000, "status": "on_time" }
    ]
  }

  With type "object" (default), Elasticsearch flattens:
  repayments.month:  ["2024-01", "2024-02", "2024-03"]
  repayments.amount: [5000, 5000, 5000]
  repayments.status: ["on_time", "late", "on_time"]

  The RELATIONSHIP is lost:
  Query: "find loans where a SINGLE repayment has status=late AND amount=5000"
  → Object fields: matches any doc where late exists AND 5000 exists in amount
  → Even if they came from DIFFERENT repayments → FALSE POSITIVE

  Aggregation: "average amount of on_time repayments"
  → Object fields: avg of ALL amounts in docs that HAVE any on_time repayment
  → Cannot isolate: amount for on_time vs late repayments → WRONG RESULT

Nested mapping — separate Lucene documents for inner objects:
  PUT /loans/_mapping
  {
    "properties": {
      "loan_id": { "type": "keyword" },
      "repayments": {
        "type": "nested",  // each element becomes a hidden Lucene document
        "properties": {
          "month":  { "type": "keyword" },
          "amount": { "type": "long" },
          "status": { "type": "keyword" }
        }
      }
    }
  }

  What Elasticsearch stores internally for the above document:
    Hidden doc 1 (nested): repayments.month="2024-01", repayments.amount=5000, repayments.status="on_time"
    Hidden doc 2 (nested): repayments.month="2024-02", repayments.amount=5000, repayments.status="late"
    Hidden doc 3 (nested): repayments.month="2024-03", repayments.amount=5000, repayments.status="on_time"
    Parent doc:            loan_id="L001"  (also links to hidden docs)

  Each hidden doc has its own inverted index entries AND doc values
  Lucene join: parent doc → nested docs via block ordering (nested docs stored just before parent)

The nested aggregation — scope into hidden documents:
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "repayment_analysis": {
        "nested": { "path": "repayments" },  // SCOPE: enter nested documents
        "aggs": {
          "avg_repayment": {
            "avg": { "field": "repayments.amount" }  // operates on NESTED doc values
          },
          "by_status": {
            "terms": { "field": "repayments.status" },
            "aggs": {
              "avg_amount_per_status": {
                "avg": { "field": "repayments.amount" }
              }
            }
          },
          "late_only": {
            "filter": { "term": { "repayments.status": "late" } },
            "aggs": {
              "total_late_amount": { "sum": { "field": "repayments.amount" } }
            }
          }
        }
      }
    }
  }

  Result interpretation:
  "repayment_analysis": {
    "doc_count": 3,          // 3 nested docs (repayments), not 1 parent doc
    "avg_repayment": { "value": 5000 },
    "by_status": {
      "buckets": [
        { "key": "on_time", "doc_count": 2, "avg_amount_per_status": { "value": 5000 } },
        { "key": "late",    "doc_count": 1, "avg_amount_per_status": { "value": 5000 } }
      ]
    },
    "late_only": {
      "doc_count": 1,
      "total_late_amount": { "value": 5000 }
    }
  }

reverse_nested — go back to parent scope:
  "I want to count how many DISTINCT PARENT LOANS have a late repayment"
  From inside a nested agg, reverse_nested exits back to parent scope:

  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "repayments_scope": {
        "nested": { "path": "repayments" },
        "aggs": {
          "late_repayments": {
            "filter": { "term": { "repayments.status": "late" } },
            "aggs": {
              "parent_loans": {
                "reverse_nested": {},  // exit nested scope → back to parent
                "aggs": {
                  "unique_loan_products": {
                    "terms": { "field": "product_type" }  // parent-level field
                  }
                }
              }
            }
          }
        }
      }
    }
  }
  // "parent_loans" doc_count = number of PARENT LOANS with at least 1 late repayment
  // "unique_loan_products" = breakdown of those loans by product type

  Without reverse_nested:
  "parent_loans.doc_count" would count NESTED docs (late repayments), not parent loans
  A loan with 3 late repayments would count as 3, not 1

Nested agg performance considerations:
  Each nested document is a real Lucene document (stored separately)
  Cost: if a loan has 36 repayments → 36 nested docs + 1 parent doc stored
  Index size: roughly proportional to total nested document count
  Query/agg cost: more docs to scan

  Mapping limit:
  index.mapping.nested_fields.limit: 50 (default max nested field types per index)
  index.mapping.nested_objects.limit: 10000 (default max nested objects per document)
  Exceeding: IndexError on ingest — validate cardinality before using nested

  When NOT to use nested:
  If you only need to query parent-level behavior (does any repayment exist) → object is fine
  If inner objects are few and static → nested is fine
  If inner objects are thousands per document → consider a separate index with a join field
```

**Q9. How do you aggregate over a nested field while also filtering on a parent-level field in the same query?**
A: This is a common scenario — for example, "for loans belonging to Branch A, show the breakdown of repayment statuses." The `nested` aggregation is scoped to nested documents, but the parent-level filter applies at the outer query level, which correctly narrows which parent documents (and therefore which nested documents) are included:

```
Filtering parents first, then aggregating nested:

  Scenario: "Among home loans only, what is the distribution of repayment statuses?"

  GET /loans/_search
  {
    "size": 0,
    "query": {
      "term": { "product_type": "home_loan" }   // filter at PARENT level
    },
    "aggs": {
      "repayment_stats": {
        "nested": { "path": "repayments" },      // scope into nested docs
        "aggs": {
          "status_breakdown": {
            "terms": { "field": "repayments.status" }
          }
        }
      }
    }
  }
  // The outer query filters parent docs (home loans only)
  // The nested agg then operates only on the nested docs that belong to those parents
  // This works correctly because nested docs are stored in blocks with their parents

  Filtering WITHIN nested (to narrow which nested docs contribute):
  {
    "size": 0,
    "aggs": {
      "repayments_2024": {
        "nested": { "path": "repayments" },
        "aggs": {
          "only_2024": {
            "filter": {
              "range": { "repayments.month": { "gte": "2024-01", "lte": "2024-12" } }
            },
            "aggs": {
              "status_in_2024": {
                "terms": { "field": "repayments.status" }
              }
            }
          }
        }
      }
    }
  }
  // "filter" inside nested: narrows to nested docs matching the date range
  // parent-level filter: not applied here (all loan types included)

  Combined: filter parents AND filter nested docs:
  {
    "size": 0,
    "query": { "term": { "product_type": "home_loan" } },  // parent filter
    "aggs": {
      "repayments_scope": {
        "nested": { "path": "repayments" },
        "aggs": {
          "q4_only": {
            "filter": {
              "range": { "repayments.month": { "gte": "2024-10", "lte": "2024-12" } }
            },
            "aggs": {
              "status_breakdown": { "terms": { "field": "repayments.status" } },
              "total_collected":   { "sum":  { "field": "repayments.amount" } }
            }
          }
        }
      }
    }
  }
  // Result: for home loans only, in Q4 2024, status distribution and total collected
```

## Section 7: Pipeline Aggregations

**Q10. What are pipeline aggregations and how do `moving_avg`, `cumulative_sum`, and `bucket_sort` work?**
A: Pipeline aggregations operate on the output of other aggregations rather than directly on documents. They are either **parent** (modify the parent multi-bucket aggregation's buckets) or **sibling** (produce a new aggregation at the same level as a sibling). They enable time-series calculations like rolling averages and cumulative totals without post-processing in application code:

```
Pipeline aggregation categories:

  PARENT pipeline aggs (applied to each bucket of the parent agg):
    derivative:       difference between adjacent bucket values (rate of change)
    cumulative_sum:   running total across buckets
    moving_avg:       rolling average over a window of buckets
    moving_fn:        moving window with custom Painless function

  SIBLING pipeline aggs (operate on all buckets of a sibling agg):
    avg_bucket:       average of a metric across all sibling buckets
    max_bucket:       which bucket has the highest metric value
    min_bucket:       which bucket has the lowest metric value
    sum_bucket:       sum of a metric across all sibling buckets
    bucket_sort:      sort the buckets of a sibling agg
    bucket_selector:  filter/remove buckets from a sibling agg

Pipeline path syntax:
  "buckets_path": "monthly>total_disbursed"
  → "monthly" = name of the parent/sibling bucket agg
  → "total_disbursed" = name of the metric inside those buckets
  For nested paths: "monthly>by_status['approved']>avg_amount"

Example: 3-month moving average of loan disbursements:
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly": {
        "date_histogram": {
          "field": "created_at",
          "calendar_interval": "month"
        },
        "aggs": {
          "total_disbursed": { "sum": { "field": "amount" } },
          "moving_3month": {
            "moving_fn": {
              "buckets_path": "total_disbursed",
              "window": 3,
              "script": "MovingFunctions.unweightedAvg(values)"
            }
          },
          "cumulative_total": {
            "cumulative_sum": {
              "buckets_path": "total_disbursed"
            }
          },
          "month_over_month_change": {
            "derivative": {
              "buckets_path": "total_disbursed"
            }
          }
        }
      }
    }
  }
  // moving_3month: avg of current + 2 previous months
  // cumulative_total: running total since the beginning of the time range
  // month_over_month_change: absolute change vs previous month (negative = decline)

  Result for a few months:
  Jan: total=10M, moving_3month=null (not enough prior data), cumulative=10M, change=null
  Feb: total=12M, moving_3month=null (need 3 months), cumulative=22M, change=+2M
  Mar: total=15M, moving_3month=12.33M, cumulative=37M, change=+3M
  Apr: total=11M, moving_3month=12.67M, cumulative=48M, change=-4M

bucket_selector — filter buckets by a metric condition:
  "Show only months where total disbursement > 10M"

  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly": {
        "date_histogram": { "field": "created_at", "calendar_interval": "month" },
        "aggs": {
          "total_disbursed": { "sum": { "field": "amount" } },
          "high_volume_only": {
            "bucket_selector": {
              "buckets_path": { "total": "total_disbursed" },
              "script": "params.total > 10000000"  // only keep if > 10M
            }
          }
        }
      }
    }
  }
  // Months with total < 10M are removed from the response entirely

bucket_sort — sort buckets by a metric (not just by key or count):
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "by_branch": {
        "terms": { "field": "branch_id", "size": 100 },
        "aggs": {
          "total_portfolio": { "sum": { "field": "amount" } },
          "sort_by_portfolio": {
            "bucket_sort": {
              "sort": [
                { "total_portfolio": { "order": "desc" } }
              ],
              "size": 10  // keep only the top 10 after sorting
            }
          }
        }
      }
    }
  }
  // Returns top 10 branches by total portfolio value
  // Different from terms "order": this sorts AFTER the metric is computed
  // More accurate than terms "order" (terms order has the same approximation issue)

sibling aggregation — avg across all buckets:
  GET /loans/_search
  {
    "size": 0,
    "aggs": {
      "monthly": {
        "date_histogram": { "field": "created_at", "calendar_interval": "month" },
        "aggs": {
          "total_disbursed": { "sum": { "field": "amount" } }
        }
      },
      "monthly_average": {
        "avg_bucket": {
          "buckets_path": "monthly>total_disbursed"
        }
      },
      "best_month": {
        "max_bucket": {
          "buckets_path": "monthly>total_disbursed"
        }
      }
    }
  }
  // monthly_average: average monthly disbursement over the entire period
  // best_month: which month had the highest disbursement (key + value)
```

**Q12. "You need a dashboard showing: total loan disbursements per month for the last 12 months, with a 3-month rolling average, sorted so the current month appears last. Empty months should show zero. How do you build this query?"**

```javascript
// Requirements:
// 1. Monthly buckets for last 12 months → date_histogram with calendar_interval
// 2. Empty months show zero → extended_bounds + min_doc_count: 0
// 3. Sum of amounts per month → sub-agg: sum
// 4. 3-month rolling average → pipeline: moving_fn
// 5. Sorted with current month last → date_histogram default is ascending by date ✓

GET /loans/_search
{
  "size": 0,
  "query": {
    "range": {
      "created_at": {
        "gte": "now-12M/M",   // start of 12 months ago (rounded to month)
        "lte": "now/M"        // start of current month (inclusive)
      }
    }
  },
  "aggs": {
    "monthly_disbursements": {
      "date_histogram": {
        "field": "created_at",
        "calendar_interval": "month",
        "format": "yyyy-MM",
        "time_zone": "Asia/Kolkata",
        "min_doc_count": 0,              // show empty months
        "extended_bounds": {
          "min": "now-12M/M",            // force buckets even if no data
          "max": "now/M"
        }
      },
      "aggs": {
        "total_disbursed": {
          "sum": { "field": "amount" }
        },
        "rolling_3m_avg": {
          "moving_fn": {
            "buckets_path": "total_disbursed",
            "window": 3,
            "script": "MovingFunctions.unweightedAvg(values)",
            "gap_policy": "insert_zeros"  // treat empty months as 0 in rolling calc
          }
        }
      }
    }
  }
}

// Result shape:
// [
//   { "key_as_string": "2024-01", "doc_count": 1234, "total_disbursed": { "value": 95000000 }, "rolling_3m_avg": { "value": null } },
//   { "key_as_string": "2024-02", "doc_count": 1456, "total_disbursed": { "value": 112000000 }, "rolling_3m_avg": { "value": null } },
//   { "key_as_string": "2024-03", "doc_count": 1789, "total_disbursed": { "value": 130000000 }, "rolling_3m_avg": { "value": 112333333 } },
//   ...
// ]

// Why rolling_3m_avg is null for first two months:
// moving_fn requires a full window before producing output
// With window=3: first valid value appears at index 2 (the 3rd bucket)
// To include partial window averages, use "shift" parameter or reduce window

// gap_policy options:
// "skip":         exclude empty buckets from the window calculation
// "insert_zeros": treat empty bucket value as 0 (default for sum → correct here)
// "keep_values":  only applies to parent pipeline aggs with existing values

// Performance note:
// The "query" range filter is essential — without it, the agg scans ALL documents
// even though extended_bounds defines the bucket range, the data scan is unrestricted
// Always filter the data range at query level to limit the doc set
```

**Q13. "A `terms` aggregation on `borrower_id` (10 million distinct values) is causing `CircuitBreakingException`. What is happening and how do you fix it?"**

```javascript
// What's happening:
// terms agg on a field with 10M distinct values → needs to:
//   1. Build global ordinals: 10M ordinals × ~8 bytes = ~80MB per shard (heap)
//   2. Build counter array: 10M entries × 8 bytes = ~80MB per shard (heap)
//   3. Sort 10M entries to find top N: O(N log N) time and temp memory
// On a 5-shard index: 5 × 160MB = 800MB just for this agg → heap exhaustion

// Diagnosis:
GET /_nodes/stats/breaker
// Check "request" and "fielddata" breaker: memory_limit vs estimated_size

// Fix 1: Use cardinality instead (if the use case is "how many unique borrowers"):
GET /loans/_search
{
  "size": 0,
  "aggs": {
    "unique_borrowers": {
      "cardinality": {
        "field": "borrower_id",
        "precision_threshold": 40000   // ~320KB per shard — acceptable
      }
    }
  }
}
// cardinality uses HLL++ → bounded memory → no circuit breaker risk

// Fix 2: If you actually need top-N borrowers by loan count, use sampling:
GET /loans/_search
{
  "size": 0,
  "aggs": {
    "sampled": {
      "sampler": {
        "shard_size": 5000   // sample 5000 docs per shard
      },
      "aggs": {
        "top_borrowers": {
          "terms": {
            "field": "borrower_id",
            "size": 10
          }
        }
      }
    }
  }
}
// sampler: limits docs to 5000 per shard → bounded terms agg → no OOM
// Tradeoff: results are approximate (based on sample)

// Fix 3: Restructure as a separate "top borrowers" index (pre-aggregated):
// Use an ingest pipeline or transform to maintain:
//   { "borrower_id": "B001", "loan_count": 23, "total_amount": 1150000, "last_updated": "..." }
// This index has one doc per borrower → cardinality = #borrowers, not #loans
// terms agg on this index is cheap (10M docs but each is already aggregated)

// Fix 4: For analytics on high-cardinality fields → use Elasticsearch rollups
//   or materialize with Data Frame Transforms:
PUT /_transform/borrower_summary
{
  "source": { "index": "loans" },
  "dest":   { "index": "borrower_aggregates" },
  "pivot": {
    "group_by": {
      "borrower_id": { "terms": { "field": "borrower_id" } }
    },
    "aggregations": {
      "loan_count":    { "value_count": { "field": "loan_id" } },
      "total_amount":  { "sum":         { "field": "amount" } },
      "avg_amount":    { "avg":         { "field": "amount" } }
    }
  },
  "sync": {
    "time": { "field": "updated_at", "delay": "60s" }
  }
}
// borrower_aggregates: one doc per borrower, continuously updated
// terms agg on borrower_aggregates → cardinality = #borrowers, not #loans → safe
```

// 200 parent loan documents

// Mapping:

    }

## Section 9: Performance and Memory Internals

**Q15. What controls how much heap aggregations use and how do you diagnose aggregation memory pressure?**

```
Memory sources in aggregations:

  1. Global ordinals (terms agg on keyword fields):
     Heap cost: ~8 bytes × cardinality × number_of_shards
     Low cardinality (status, 5 values): negligible
     High cardinality (borrower_id, 10M values): up to GB

  2. Aggregation state during collection:
     terms agg: counter array sized to cardinality
     cardinality agg: HLL sketch — bounded by precision_threshold
     date_histogram: one bucket per distinct time interval (bounded by data range / interval)
     nested agg: multiplied by nesting depth

  3. Partial results on coordinating node:
     Each shard returns partial results to the coordinating node
     Coordinating node merges in memory
     For terms: each shard returns shard_size buckets × num_shards

Circuit breakers:
  indices.breaker.request.limit: 60% of heap (default)
    Tracks: aggregation state + partial results
    Exceeds limit → CircuitBreakingException: "Data too large"
    Fix: reduce shard_size, reduce size, increase heap, or restructure the agg

  indices.breaker.fielddata.limit: 40% of heap
    Tracks: global ordinals (fielddata cache)
    Exceeds limit → evict older ordinals → rebuild on next query → latency spike
    Fix: enable eager_global_ordinals, increase heap, reduce index cardinality

Diagnosing aggregation performance:
  Step 1: Profile the aggregation
  GET /loans/_search
  {
    "size": 0,
    "profile": true,
    "aggs": { "by_status": { "terms": { "field": "status" } } }
  }
  // "aggregations" section shows time per agg per shard
  // "collectors" section shows total collection time

  Step 2: Check fielddata cache
  GET /_nodes/stats/indices/fielddata
  // memory_size_in_bytes: current heap used by global ordinals
  // evictions: how often ordinals are being rebuilt (high = add heap or add eager_global_ordinals)

  Step 3: Check circuit breaker state
  GET /_nodes/stats/breaker
  // "request": { "tripped": 5 } → 5 circuit breaker trips → aggregation too expensive

Aggregation optimization checklist:
  ✓ Always use "size": 0 when only agg results needed
  ✓ Filter with "query" before aggregating (reduce doc set)
  ✓ Set shard_size only as large as needed for the accuracy required
  ✓ For high-cardinality distinct counts → use cardinality (HLL++) not terms
  ✓ For sorting by sub-metric → use bucket_sort pipeline agg (more accurate than terms "order")
  ✓ For time-series → always filter date range in "query", not just extended_bounds
  ✓ For repeated aggregations on the same field → enable eager_global_ordinals
  ✓ For aggregations on text fields → use .keyword sub-field, never enable fielddata
  ✓ For very high cardinality terms → consider pre-aggregation via Transform or rollup
```

## Quick Reference Tables

| Aggregation | Type | Data structure used | Output | SQL equivalent |
|---|---|---|---|---|
| `terms` | Bucket | Global ordinals (doc values) | Buckets by distinct value | `GROUP BY field` |
| `date_histogram` | Bucket | Doc values (date as ms) | Buckets by time interval | `GROUP BY DATE_TRUNC(field, interval)` |
| `range` | Bucket | Doc values | Buckets by numeric range | `GROUP BY CASE WHEN ...` |
| `filter` | Bucket | Inverted index | Single bucket: matching docs | `WHERE` applied to agg scope |
| `nested` | Bucket | Nested Lucene docs | Switches doc scope to nested | `JOIN` on nested structure |
| `avg` | Metric | Doc values (numeric) | Single number | `AVG(field)` |
| `sum` | Metric | Doc values (numeric) | Single number | `SUM(field)` |
| `min` / `max` | Metric | Doc values (numeric) | Single number | `MIN/MAX(field)` |
| `cardinality` | Metric | Doc values + HLL++ sketch | Approximate distinct count | `COUNT(DISTINCT field)` |
| `stats` | Metric | Doc values (numeric) | min, max, avg, sum, count | Multiple aggregate functions |
| `top_hits` | Metric | Stored fields (`_source`) | Top matching docs per bucket | `ROW_NUMBER() OVER (PARTITION BY ...)` |
| `moving_fn` | Pipeline | Parent bucket metrics | Rolling window metric | Window function |
| `cumulative_sum` | Pipeline | Parent bucket metrics | Running total | `SUM(...) OVER (ORDER BY ...)` |
| `derivative` | Pipeline | Parent bucket metrics | Delta between adjacent buckets | Value − LAG(value) |
| `bucket_sort` | Pipeline | Parent bucket metrics | Sorted / trimmed buckets | `ORDER BY metric LIMIT N` |
| `bucket_selector` | Pipeline | Parent bucket metrics | Filtered buckets | `HAVING metric > threshold` |

| Scenario | Correct aggregation approach |
|---|---|
| Count distinct users | `cardinality` with appropriate `precision_threshold` |
| Top 10 categories by revenue | `terms` (size=10, shard_size=50) + nested `sum` |
| Monthly trend with empty months | `date_histogram` + `min_doc_count: 0` + `extended_bounds` |
| Rolling 7-day average | `date_histogram` (fixed_interval: 1d) + `moving_fn` (window: 7) |
| Aggregate over array of objects | `nested` agg (must use nested mapping) |
| Count parent docs from inside nested | `reverse_nested` inside a `nested` agg |
| Sort buckets by sub-metric | `bucket_sort` pipeline agg |
| Remove low-count buckets | `bucket_selector` pipeline agg |
| Average across all monthly buckets | `avg_bucket` sibling pipeline agg |
| Aggregation on text field | Use `.keyword` sub-field; never enable `fielddata` |
| High-cardinality terms causes OOM | Use `cardinality`, `sampler`, or pre-aggregated Transform |

| terms agg option | Default | Effect |
|---|---|---|
| `size` | 10 | Number of buckets returned globally |
| `shard_size` | max(10, size×1.5) | Buckets requested per shard (accuracy control) |
| `min_doc_count` | 1 | Minimum docs for a bucket to appear |
| `missing` | (absent field not counted) | Bucket name for documents with null field |
| `order` | `{ "_count": "desc" }` | How to sort buckets before returning top-N |
| `include` / `exclude` | (none) | Allowlist / denylist of bucket values |
| `execution_hint` | `global_ordinals` | `map` for high-cardinality + heavy filter context |
| `show_term_doc_count_error` | false | Show per-bucket count error bound in response |

**Tip for interviews:** Five things separate strong candidates on Elasticsearch aggregations: (1) knowing the **three-family taxonomy** — bucket (partition docs), metric (compute values), pipeline (operate on other aggs' output) — and the nesting rules: bucket aggs can have sub-aggs, metric aggs are leaves, pipeline aggs reference siblings or parents by path; (2) explaining the **terms approximation problem precisely** — each shard independently returns its local top-N, so globally-important terms can be undercounted if they don't rank top-N on every shard; the fix is to increase `shard_size` (more results per shard → higher accuracy at higher memory/network cost) and check `doc_count_error_upper_bound` to gauge result trustworthiness; (3) understanding **why nested aggregations report different `doc_count`** — a `nested` agg switches context from parent documents to hidden nested Lucene documents, so `doc_count` inside `nested` counts nested objects, not parent documents; `reverse_nested` is required to count distinct parent documents from within nested scope; (4) being precise about **cardinality's HLL++ tradeoff** — the `precision_threshold` parameter controls the boundary below which results are exact and above which ~2% relative error applies, the memory cost is `precision_threshold × 8 bytes` per shard per agg instance, and results across shards are merged via HLL sketch union (not full value transfer); (5) knowing **the doc values dependency** — virtually all aggregations use doc values (columnar, on-disk, not in JVM heap) rather than the inverted index; the inverted index is only used for the `query` phase to determine which documents to include in the aggregation; this is why aggregating on `text` fields fails by default (text fields have no doc values) and why the fix is always to use a `.keyword` sub-field, not to enable `fielddata` (which loads analyzed terms into heap and is an OOM risk in production).
