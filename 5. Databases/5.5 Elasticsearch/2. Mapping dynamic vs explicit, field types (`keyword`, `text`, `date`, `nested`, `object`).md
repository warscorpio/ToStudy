# Elasticsearch Mapping: Dynamic vs Explicit, Field Types
## Interview Q&A (5 YOE Level)

---

## Section 1: What a Mapping Is

**Q1. What is an Elasticsearch mapping — how does it relate to the inverted index and why does it affect every query?**

A: A mapping is the schema definition for an Elasticsearch index. It describes the fields in each document, their data types, and how each field should be indexed and stored. Every query, aggregation, and sort operation is constrained by decisions made in the mapping:

```
How a document flows through the mapping layer:

  Document indexed:
  {
    "title":    "Running Shoes for Marathon",
    "price":    129.99,
    "tags":     ["sale", "sports"],
    "createdAt":"2024-01-15T10:00:00Z"
  }
                │
                ▼
  Mapping layer (per field):
  ┌──────────────────────────────────────────────────────────────────┐
  │ title:     text     → analyzed → inverted index tokens           │
  │ price:     float    → numeric  → BKD tree (range queries)        │
  │ tags:      keyword  → NOT analyzed → exact-match inverted index  │
  │ createdAt: date     → parsed   → epoch_ms stored as long         │
  └──────────────────────────────────────────────────────────────────┘
                │
                ▼
  Internal data structures per field:

  title field (text → analyzed by standard analyzer):
  Tokens: ["running", "shoes", "for", "marathon"]
  Inverted index:
    "marathon" → [doc_1, doc_47, doc_203]
    "running"  → [doc_1, doc_12, doc_88]
    "shoes"    → [doc_1, doc_19]

  price field (float → BKD tree):
    Supports: range queries ($gt, $lt), aggregations (min/max/avg)
    NOT in inverted index: cannot do full-text search on price.

  tags field (keyword → NOT analyzed):
  Inverted index:
    "sale"   → [doc_1, doc_5, doc_12]
    "sports" → [doc_1, doc_8]
    "SALE"   ← would NOT match "sale" (no lowercasing — exact match only)

  The mapping decision is PERMANENT for an index (cannot change field type).
  Wrong type at creation → must reindex to fix.
```

```json
// ── Get the mapping of an existing index ─────────────────────────────────────
GET /products/_mapping
// {
//   "products": {
//     "mappings": {
//       "properties": {
//         "title":     { "type": "text",    "analyzer": "standard" },
//         "price":     { "type": "float" },
//         "tags":      { "type": "keyword" },
//         "createdAt": { "type": "date" }
//       }
//     }
//   }
// }

// ── Field-level storage options (affect every query decision) ─────────────────
// index: true/false    → whether the field is searchable (added to inverted index)
// doc_values: true/false → columnar storage for aggregations and sorting
// store: true/false    → whether the field value is stored separately from _source
// _source              → the original JSON document (stored by default)

// Common combinations:
// index: true, doc_values: true   → searchable AND aggregatable (default for most types)
// index: true, doc_values: false  → searchable only (text fields default)
// index: false, doc_values: true  → aggregatable only (metrics never searched by text)
// index: false, doc_values: false → field stored in _source only, not searchable
```

## Section 2: Dynamic Mapping

**Q2. How does dynamic mapping work — what are the type inference rules and what can go wrong?**

A: When a document is indexed with a field that has no existing mapping entry, Elasticsearch infers the type from the first value it sees. The inference rules are deterministic but have sharp edges — a single "wrong" first document can permanently mis-type a field for the entire index:

```
Dynamic mapping type inference rules:

  JSON type        → Elasticsearch type (default)
  ─────────────────────────────────────────────────────────────────────
  true / false     → boolean
  number (integer) → long
  number (decimal) → float
  "2024-01-15"     → date  (if matches date_detection patterns)
  "hello world"    → text  (always analyzed) + keyword subfield (default)
  ["a", "b"]       → same type as the element (arrays = multi-value field)
  {"nested": "obj"}→ object (flattened — see Q8)
  null             → no field created (null does not establish a type)

  The "text + keyword" double mapping for strings:
  {
    "title": {
      "type": "text",                    ← full-text search
      "fields": {
        "keyword": {                     ← exact match, aggregations, sort
          "type":         "keyword",
          "ignore_above": 256            ← strings > 256 chars not indexed as keyword
        }
      }
    }
  }
  → Access as: "title" (text search) or "title.keyword" (exact/agg/sort)
```

```json
// ── Three dynamic mapping settings ────────────────────────────────────────────
PUT /my-index
{
  "mappings": {
    "dynamic": "true"
  }
}
// "true" (default): new fields are added to the mapping automatically on first index.
// Fields become searchable and aggregatable immediately.
// Risk: mapping explosion (millions of fields from user-generated data).

PUT /my-index
{
  "mappings": {
    "dynamic": "false"
  }
}
// "false": new fields are SILENTLY IGNORED by the indexer.
// They are stored in _source (you can retrieve them) but NOT searchable or aggregatable.
// No error thrown. Documents index successfully.
// Risk: developers think a field is indexed when it isn't — queries return zero results.
// Use when: schema is fixed and you want to reject unknown fields without errors.

PUT /my-index
{
  "mappings": {
    "dynamic": "strict"
  }
}
// "strict": new fields throw an exception — document is rejected.
// Use for: schema-enforced indices (audit logs, financial data) where unknown fields
// indicate a bug in the application.
// Error: "strict_dynamic_mapping_exception: mapping set to strict, dynamic introduction
//         of [unknown_field] within [_doc] is not allowed"

// ── Dynamic templates: override inference for matched fields ───────────────────
PUT /products
{
  "mappings": {
    "dynamic_templates": [
      {
        "strings_as_keywords": {
          "match_mapping_type": "string",
          "mapping": {
            "type": "keyword"
          }
        }
      }
    ]
  }
}
// ALL string fields → keyword (not text + keyword double-mapping).
// Use when: you know all strings are identifiers or enums (not prose).

PUT /logs
{
  "mappings": {
    "dynamic_templates": [
      {
        "long_as_integer": {
          "match_mapping_type": "long",
          "mapping": { "type": "integer" }
        }
      },
      {
        "metadata_as_keyword": {
          "path_match": "metadata.*",
          "mapping": { "type": "keyword" }
        }
      },
      {
        "no_index_for_large_text": {
          "match": "*_description",
          "mapping": {
            "type":  "text",
            "index": false        // Store but don't index description fields
          }
        }
      }
    ]
  }
}

// ── Mapping explosion: the danger of unlimited dynamic mapping ─────────────────
// Scenario: user-generated event tracking. Each event type has custom attributes.
// Without restriction, each unique attribute becomes a new field in the mapping.
// 1000 event types × 50 attributes = 50,000 fields → cluster instability.

// Mapping explosion causes:
// 1. Master node memory pressure (cluster state stores all mappings in memory).
// 2. Shard memory pressure (each shard loads the mapping on startup).
// 3. Slow query planning (more fields = more analysis).
// 4. Unexpected errors when field limit is hit (default: 1000 fields).

// Default field limit:
PUT /my-index/_settings
{
  "index.mapping.total_fields.limit": 1000  // default; increase with caution
}

// Better solutions for dynamic user data:
// Option A: flattened type (one field, key-value pairs, single keyword mapping)
// Option B: strict mode + schema validation before indexing
// Option C: separate indices per event type
// Option D: runtime fields (query-time field extraction, no mapping cost)
```

## Section 3: Explicit Mapping

**Q3. How do you define explicit mappings — what is the create-vs-update lifecycle and what can never change?**

A: Explicit mappings are defined at index creation or added incrementally. The fundamental constraint is that field types are immutable — you can add new fields but you can never change a field's type once documents exist:

```json
// ── Creating an index with explicit mapping ────────────────────────────────────
PUT /products
{
  "settings": {
    "number_of_shards":   3,
    "number_of_replicas": 1,
    "analysis": {
      "analyzer": {
        "product_analyzer": {
          "type":      "custom",
          "tokenizer": "standard",
          "filter":    ["lowercase", "stop", "kstem"]
        }
      }
    }
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "productId": {
        "type": "keyword"                    // Exact match, aggregations
      },
      "name": {
        "type":     "text",
        "analyzer": "product_analyzer",      // Custom analyzer for search
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }  // For sort/agg
        }
      },
      "description": {
        "type":       "text",
        "analyzer":   "english",             // English stemmer: "running" → "run"
        "index_options": "offsets",          // Store term positions for highlighting
        "term_vector": "with_positions_offsets"
      },
      "price": {
        "type": "scaled_float",
        "scaling_factor": 100               // Stores 129.99 as 12999 (integer precision)
      },
      "tags": {
        "type": "keyword"                   // Array of keywords (multi-value)
      },
      "category": {
        "type": "keyword"
      },
      "inStock": {
        "type": "boolean"
      },
      "createdAt": {
        "type":   "date",
        "format": "strict_date_optional_time||epoch_millis"
      },
      "attributes": {
        "type":    "object",                // Embedded object (flattened)
        "dynamic": false                    // Don't auto-map new attribute fields
      },
      "variants": {
        "type": "nested"                    // Array of objects (NOT flattened)
      },
      "location": {
        "type": "geo_point"                 // Latitude/longitude
      }
    }
  }
}

// ── Adding fields to an existing index (allowed) ──────────────────────────────
PUT /products/_mapping
{
  "properties": {
    "weight": {
      "type": "float"        // New field: fine to add at any time
    },
    "brand": {
      "type": "keyword"
    }
  }
}
// → Adds "weight" and "brand" to the mapping.
// → Existing documents don't have these fields; they are simply absent.
// → New documents can now include these fields.

// ── Changing a field type (NOT ALLOWED) ───────────────────────────────────────
PUT /products/_mapping
{
  "properties": {
    "price": {
      "type": "double"       // Trying to change from scaled_float to double
    }
  }
}
// → ERROR: illegal_argument_exception: mapper [price] of different type,
//   current_type [scaled_float], merged_type [double]

// WHY: Existing Lucene segment files on disk are encoded for scaled_float.
// Changing the type would require rewriting all segment files — i.e., full reindexing.

// ── Correct procedure to change a field type ──────────────────────────────────
// Step 1: Create a new index with the correct mapping.
PUT /products-v2
{ /* new mapping with price as double */ }

// Step 2: Reindex all documents from the old index to the new one:
POST /_reindex
{
  "source": { "index": "products" },
  "dest":   { "index": "products-v2" }
}

// Step 3: Create an alias pointing to the new index:
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products",    "alias": "products-alias" } },
    { "add":    { "index": "products-v2", "alias": "products-alias" } }
  ]
}
// Application uses "products-alias" → zero-downtime mapping change.

// Step 4: Delete the old index after verifying the new one:
DELETE /products
```

## Section 4: The `text` vs `keyword` Distinction

**Q4. What is the fundamental difference between `text` and `keyword` — why is confusing them the most common mapping mistake?**

A: `text` and `keyword` both store strings but use completely different internal representations. `text` is analyzed (tokenized, lowercased, stemmed) enabling full-text search. `keyword` is stored as-is enabling exact match, aggregation, and sorting. Using the wrong type causes queries to silently return no results:

```
text field internals:

  Indexed value: "Running Shoes for Marathon"
  Analyzer: standard (tokenize → lowercase → remove stopwords)
  Tokens stored in inverted index:
    "running" → [this doc]
    "shoes"   → [this doc]
    "marathon" → [this doc]
    (stop words "for" removed)

  Queries that WORK on text:
    match query:      "running shoes"  → matches (tokens "running" + "shoes" found)
    match query:      "RUNNING"        → matches (query is lowercased too)
    match_phrase:     "running shoes"  → matches (adjacent tokens)
    fuzzy:            "runnin"         → matches (edit distance 1)

  Queries that DON'T WORK on text:
    term query:       "Running Shoes"  → NO MATCH (term queries are NOT analyzed;
                                         "Running Shoes" is not in the inverted index,
                                         only "running" and "shoes" separately)
    aggregations:     (on text field)  → ERROR: fielddata is disabled by default
    sort:             (on text field)  → ERROR: cannot sort on analyzed text
    range:            "a" to "z"       → doesn't make semantic sense for text
```

```json
// ── keyword field internals ────────────────────────────────────────────────────
// Indexed value: "Running Shoes for Marathon"
// NOT analyzed: stored exactly as-is in inverted index.
// Inverted index entry: "Running Shoes for Marathon" → [this doc]
// (The whole string is one token — no splitting)

// Queries that WORK on keyword:
// term query:     "Running Shoes for Marathon"  → matches (exact string)
// terms query:    ["sale", "sports"]             → matches if value is in list
// prefix query:   "Running"                     → matches (starts with "Running")
// range:          "A" to "Z"                    → lexicographic range
// aggregations:   terms aggregation on category  → counts per category ✓
// sort:           sorted alphabetically          ✓

// Queries that DON'T WORK on keyword:
// match query:    "running"     → NO MATCH ("Running Shoes for Marathon" ≠ "running")
//                                 (match query IS analyzed, but the stored value is not,
//                                  so "running" ≠ "Running Shoes for Marathon")

// ── The multi-field pattern: both text and keyword ────────────────────────────
// This is the default dynamic mapping for strings:
{
  "name": {
    "type":     "text",
    "analyzer": "standard",
    "fields": {
      "keyword": {
        "type":         "keyword",
        "ignore_above": 256
      }
    }
  }
}
// → name           = analyzed text field (full-text search)
// → name.keyword   = exact keyword field (aggregation, sort, exact match)

// Usage:
GET /products/_search
{
  "query": {
    "match": { "name": "running shoes" }    // Full-text search → uses "name" (text)
  },
  "aggs": {
    "by_name": {
      "terms": { "field": "name.keyword" }  // Aggregation → uses "name.keyword"
    }
  },
  "sort": [
    { "name.keyword": "asc" }              // Sort → uses "name.keyword"
  ]
}

// ── Critical: term query on a text field returns zero results ─────────────────
GET /products/_search
{
  "query": {
    "term": { "name": "Running Shoes" }    // WRONG: returns 0 results even if "Running Shoes" exists
    // Why: term query sends "Running Shoes" to the inverted index without analysis.
    // "Running Shoes" was stored as tokens "running" and "shoes" (separate).
    // The exact string "Running Shoes" is not in the text field's inverted index.
  }
}
// CORRECT for full-text:
GET /products/_search
{
  "query": {
    "match": { "name": "Running Shoes" }   // Analyzed: "running" AND "shoes" → works ✓
  }
}
// CORRECT for exact value:
GET /products/_search
{
  "query": {
    "term": { "name.keyword": "Running Shoes" }  // Exact match on keyword field ✓
  }
}
```

**Q5. How do analyzers work — what are the built-in analyzers and when do you need a custom one?**

A: An analyzer is a pipeline of three components: character filters, a tokenizer, and token filters. It transforms raw text into tokens that are stored in the inverted index. The same analyzer (or a compatible one) runs at both index time and query time — a mismatch between them is one of the most subtle mapping bugs:

```
Analyzer pipeline:

  Input: "  The Quick Brown Fox's Jump! "
         │
         ▼ Character filters (optional pre-processing)
         "  The Quick Brown Fox's Jump  "  ← html_strip, pattern_replace, etc.
         │
         ▼ Tokenizer (split into tokens)
         ["The", "Quick", "Brown", "Fox's", "Jump"]  ← standard tokenizer
         │
         ▼ Token filters (transform each token)
         lowercase:  ["the", "quick", "brown", "fox's", "jump"]
         stop:       ["quick", "brown", "fox's", "jump"]  (removes "the")
         stemmer:    ["quick", "brown", "fox", "jump"]    (fox's → fox)
         │
         Stored in inverted index: "quick", "brown", "fox", "jump"
```

```json
// ── Built-in analyzers ────────────────────────────────────────────────────────

// standard (default for text fields):
// Tokenizer: standard (Unicode-aware word splitting)
// Filters: lowercase + (optionally) stop
// Good for: most European languages
GET /_analyze
{
  "analyzer": "standard",
  "text": "The Quick Brown Fox"
}
// → ["the", "quick", "brown", "fox"]

// english:
// Tokenizer: standard
// Filters: english possessive, lowercase, stop (english), kstem (english stemmer)
// Good for: English prose (search documents, product descriptions)
GET /_analyze
{
  "analyzer": "english",
  "text": "Running faster than foxes"
}
// → ["run", "faster", "fox"]  (running→run, foxes→fox, than removed as stop word)

// keyword:
// Does NOT tokenize — the entire input is one token (same as keyword field type)
// Useful as an analyzer on a text field when you want exact-match behavior

// whitespace:
// Splits on whitespace only (no lowercasing, no punctuation handling)
GET /_analyze
{
  "analyzer": "whitespace",
  "text": "Quick-Brown FOX"
}
// → ["Quick-Brown", "FOX"]   (no lowercasing — "FOX" ≠ "fox" in queries)

// fingerprint:
// Sorts and deduplicates tokens, joins them back → single token
// Use for: duplicate detection (same words, different order)

// ── Custom analyzer ────────────────────────────────────────────────────────────
PUT /blog
{
  "settings": {
    "analysis": {
      "char_filter": {
        "html_strip_filter": {
          "type": "html_strip"             // Remove HTML tags before tokenizing
        }
      },
      "tokenizer": {
        "my_tokenizer": {
          "type":     "standard"
        }
      },
      "filter": {
        "english_stop": {
          "type":       "stop",
          "stopwords":  "_english_"
        },
        "english_stemmer": {
          "type":     "stemmer",
          "language": "english"
        },
        "my_synonym": {
          "type":     "synonym",
          "synonyms": [
            "laptop, notebook, computer",    // All treated as equivalent
            "tv => television"               // tv expands to television (one-way)
          ]
        }
      },
      "analyzer": {
        "blog_content_analyzer": {
          "type":         "custom",
          "char_filter":  ["html_strip_filter"],
          "tokenizer":    "standard",
          "filter":       ["lowercase", "english_stop", "english_stemmer", "my_synonym"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "content": {
        "type":            "text",
        "analyzer":        "blog_content_analyzer",   // Applied at index time
        "search_analyzer": "blog_content_analyzer"    // Applied at query time
        // If search_analyzer differs from analyzer: query tokens ≠ index tokens → misses
      }
    }
  }
}

// ── Testing your analyzer before indexing ─────────────────────────────────────
GET /blog/_analyze
{
  "field": "content",
  "text": "The <b>Quick</b> laptop running fast"
}
// → ["quick", "laptop", "notebook", "computer", "run", "fast"]
// (HTML stripped, lowercased, stopped, stemmed, synonyms expanded)

// ── Index-time vs query-time analyzer mismatch ────────────────────────────────
// SYMPTOM: search for "laptops" finds nothing even though "laptop" is indexed.
// Cause: index analyzer applied stemming (laptop→laptop), but search analyzer
//        was accidentally set to "keyword" (no stemming) → "laptops" sent as-is.
// Fix: ensure same analyzer is used at both index and query time.

// Check what analyzer a field uses at query time:
GET /products/_analyze
{
  "field": "description",           // Uses the field's search_analyzer
  "text": "running shoes"
}
```

## Section 5: The `date` Type

**Q6. How does the `date` field work — what are the format options and what breaks if you get them wrong?**

A: Elasticsearch stores all dates internally as milliseconds since epoch (a `long`). The `format` parameter tells the parser how to read incoming string values. A mismatch between the format and the actual data causes the document to be rejected or the date to be silently stored incorrectly:

```json
// ── Date field with explicit format ───────────────────────────────────────────
PUT /events
{
  "mappings": {
    "properties": {
      "createdAt": {
        "type":   "date",
        "format": "strict_date_optional_time||epoch_millis"
        // || means: try first format, then second format
        // strict_date_optional_time: ISO-8601 with optional time (2024-01-15 or 2024-01-15T10:00:00Z)
        // epoch_millis: Unix timestamp in milliseconds (1705312800000)
      },
      "publishDate": {
        "type":   "date",
        "format": "yyyy-MM-dd"   // Only dates, no time: "2024-01-15"
      },
      "legacyTimestamp": {
        "type":   "date",
        "format": "epoch_second" // Unix timestamp in SECONDS (not millis)
      }
    }
  }
}

// ── Indexing date values ───────────────────────────────────────────────────────
POST /events/_doc
{
  "createdAt": "2024-01-15T10:00:00Z",     // ISO-8601 → parsed ✓
  "createdAt": "2024-01-15T10:00:00.000Z", // ISO-8601 with ms → parsed ✓
  "createdAt": 1705312800000,              // epoch_millis → parsed ✓
  "createdAt": "2024-01-15"               // strict_date_optional_time → parsed ✓
}

POST /events/_doc
{
  "publishDate": "2024-01-15"    // Matches yyyy-MM-dd ✓
  "publishDate": "01/15/2024"   // Does NOT match yyyy-MM-dd → document rejected!
}
// Error: failed to parse date field [01/15/2024] with format [yyyy-MM-dd]

// ── Date queries ──────────────────────────────────────────────────────────────
GET /events/_search
{
  "query": {
    "range": {
      "createdAt": {
        "gte": "2024-01-01",
        "lt":  "2024-02-01",
        "format": "yyyy-MM-dd"   // Optional: specify format for the query value
      }
    }
  }
}

// ── Date math in queries ───────────────────────────────────────────────────────
GET /events/_search
{
  "query": {
    "range": {
      "createdAt": {
        "gte": "now-7d/d",   // 7 days ago, rounded to day
        "lte": "now/d"       // today, rounded to day
      }
    }
  }
}
// Date math:
// now            → current time
// now-1h         → 1 hour ago
// now-7d/d       → 7 days ago, rounded DOWN to the day boundary
// 2024-01-15||+1M/M → 2024-01-15 + 1 month, rounded to month
// Rounding (/d, /M, /y) improves query cache hit rate (fixed boundaries = cacheable)

// ── Date aggregations ─────────────────────────────────────────────────────────
GET /orders/_search
{
  "size": 0,
  "aggs": {
    "sales_over_time": {
      "date_histogram": {
        "field":             "createdAt",
        "calendar_interval": "month",   // 1d, 1w, 1M, 1q, 1y (calendar-aware)
        "format":            "yyyy-MM",
        "time_zone":         "America/New_York"  // Bucket in local time zone
      },
      "aggs": {
        "total_revenue": {
          "sum": { "field": "total" }
        }
      }
    }
  }
}

// ── Common date mistakes ──────────────────────────────────────────────────────
// Mistake 1: storing dates as text strings (prevents range queries):
// WRONG:  "createdAt": { "type": "keyword" } → can only do exact match, no ranges
// RIGHT:  "createdAt": { "type": "date" }    → range queries, date math, histograms

// Mistake 2: inconsistent date formats in source data:
// Some documents: "2024-01-15T10:00:00Z"   (ISO format)
// Other documents: 1705312800000            (epoch_millis)
// Fix: use a combined format: "strict_date_optional_time||epoch_millis"

// Mistake 3: timezone-unaware dates:
// Storing "2024-01-15T10:00:00" (no Z) → Elasticsearch assumes UTC.
// If source data is in local time: date values are wrong by the TZ offset.
// Fix: always store dates in UTC (Z suffix) or use epoch_millis (always UTC).
```

## Section 6: The `object` Type

**Q7. How does the `object` type work — what is field flattening and when does it cause incorrect results?**

A: The `object` type maps embedded JSON objects by flattening their fields into the parent document's namespace. There is no concept of "which object did this field belong to" — this causes a specific class of cross-object matching bugs that is critical to understand:

```
object type — field flattening model:

  Document:
  {
    "name": "Alice",
    "address": {
      "street": "123 Main St",
      "city":   "New York"
    }
  }

  Internal Lucene representation (flattened):
  {
    "name":           "Alice",
    "address.street": "123 Main St",
    "address.city":   "New York"
  }

  Multiple addresses (array of objects):
  {
    "name": "Bob",
    "orders": [
      { "productId": "A1", "status": "shipped" },
      { "productId": "B2", "status": "pending" }
    ]
  }

  Internal Lucene representation (flattened):
  {
    "name":             "Bob",
    "orders.productId": ["A1", "B2"],   // All productIds merged into one field
    "orders.status":    ["shipped", "pending"]  // All statuses merged into one field
  }

  THE BUG: Find orders where productId=A1 AND status=pending
  {
    "query": {
      "bool": {
        "must": [
          { "term": { "orders.productId": "A1" } },
          { "term": { "orders.status": "pending" } }
        ]
      }
    }
  }
  → Matches Bob's document! ✓ (both A1 and pending are in the merged arrays)
  BUT: There is NO order with productId=A1 AND status=pending.
  → A1 is shipped; B2 is pending. The query returns a FALSE POSITIVE.
  This is the cross-object matching problem — object type cannot isolate individual array elements.
```

```json
// ── Object type mapping ────────────────────────────────────────────────────────
PUT /users
{
  "mappings": {
    "properties": {
      "name": { "type": "text" },
      "address": {
        "type": "object",          // Explicit object declaration (implicit by default)
        "properties": {
          "street": { "type": "text" },
          "city":   { "type": "keyword" },
          "zip":    { "type": "keyword" }
        }
      }
    }
  }
}

// Querying nested object fields (dot notation):
GET /users/_search
{
  "query": {
    "term": { "address.city": "New York" }  // Dot notation for object fields
  }
}
// ✓ Works correctly for single-valued objects.
// ✗ Cross-object matching bug only appears with ARRAYS of objects.

// ── When object type is CORRECT ───────────────────────────────────────────────
// Use object type when:
// 1. The field is a single embedded object (not an array of objects):
//    { "user": { "name": "Alice", "email": "alice@example.com" } }
//    → address.name and address.email queries work correctly.

// 2. The "cross-object" bug doesn't matter because you never query
//    two different object fields together in a boolean must clause:
//    Find all orders with status=pending (don't care which productId):
//    → Object type is fine for single-field queries on arrays.

// 3. You need the performance advantage:
//    Object: stored as part of the parent document.
//    Nested: stored as separate hidden documents → slower for queries and indexing.
```

## Section 7: The `nested` Type

**Q8. What is the `nested` type — how does it solve the cross-object matching problem and what does it cost?**

A: The `nested` type stores each element of an array-of-objects as a separate hidden Lucene document. This preserves the relationship between fields within each object. Queries on nested fields must use the `nested` query wrapper, which joins the hidden documents back to their parent:

```
nested type — separate hidden documents model:

  Document with nested type:
  {
    "_id": "order-1",
    "name": "Bob",
    "items": [
      { "productId": "A1", "status": "shipped", "qty": 2 },
      { "productId": "B2", "status": "pending", "qty": 1 }
    ]
  }

  Internal Lucene storage (3 separate documents):

  Hidden doc 1: { "items.productId": "A1", "items.status": "shipped", "items.qty": 2 }
                _routing: "order-1" (co-located with parent on same shard)
  Hidden doc 2: { "items.productId": "B2", "items.status": "pending", "items.qty": 1 }
                _routing: "order-1"
  Parent doc:   { "_id": "order-1", "name": "Bob" }

  Query: items.productId=A1 AND items.status=pending
  Nested query: search hidden doc 1 → productId=A1 ✓ but status=shipped ✗ → NOT matched
                search hidden doc 2 → productId=B2 ✗ → NOT matched
  Result: order-1 is NOT returned. ✓ CORRECT RESULT.
  The query correctly reflects that no item has BOTH productId=A1 AND status=pending.
```

```json
// ── Nested type mapping ────────────────────────────────────────────────────────
PUT /orders
{
  "mappings": {
    "properties": {
      "orderId":   { "type": "keyword" },
      "customerId":{ "type": "keyword" },
      "status":    { "type": "keyword" },
      "items": {
        "type": "nested",                   // Each item = separate hidden document
        "properties": {
          "productId": { "type": "keyword" },
          "name":      { "type": "text", "fields": { "keyword": { "type": "keyword" } } },
          "status":    { "type": "keyword" },
          "quantity":  { "type": "integer" },
          "price":     { "type": "float" }
        }
      }
    }
  }
}

// ── Querying nested fields ─────────────────────────────────────────────────────
// WRONG (object query — cross-object bug):
GET /orders/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "items.productId": "A1" } },
        { "term": { "items.status": "pending" } }  // Bug: cross-object matching
      ]
    }
  }
}

// CORRECT (nested query — joins hidden docs to parent):
GET /orders/_search
{
  "query": {
    "nested": {
      "path": "items",              // The nested field to search within
      "query": {
        "bool": {
          "must": [
            { "term": { "items.productId": "A1" } },
            { "term": { "items.status":    "pending" } }
          ]
        }
      },
      "score_mode": "max"           // How to combine scores from multiple nested docs
      // avg | max | min | sum | none
    }
  }
}
// ✓ Each nested document is evaluated independently → no cross-object matching.

// ── Nested aggregations ────────────────────────────────────────────────────────
GET /orders/_search
{
  "size": 0,
  "aggs": {
    "items_agg": {
      "nested": { "path": "items" },   // Drill into nested documents
      "aggs": {
        "top_products": {
          "terms": {
            "field": "items.productId",
            "size":  10
          },
          "aggs": {
            "total_quantity": {
              "sum": { "field": "items.quantity" }
            },
            "avg_price": {
              "avg": { "field": "items.price" }
            }
          }
        }
      }
    }
  }
}

// ── Reverse nested aggregation (from nested back to parent) ───────────────────
GET /orders/_search
{
  "size": 0,
  "aggs": {
    "items_agg": {
      "nested": { "path": "items" },
      "aggs": {
        "shipped_items": {
          "filter": { "term": { "items.status": "shipped" } },
          "aggs": {
            "order_count": {
              "reverse_nested": {},       // Go back to parent documents
              "aggs": {
                "by_customer": {
                  "terms": { "field": "customerId" }
                }
              }
            }
          }
        }
      }
    }
  }
}
// → Count of unique customers who have at least one shipped item.

// ── Nested type costs ──────────────────────────────────────────────────────────
// 1. Storage: each nested object = hidden Lucene document = extra disk + memory.
//    An order with 50 items = 51 Lucene documents stored (1 parent + 50 nested).
// 2. Indexing speed: each nested document indexed separately (slower than object).
// 3. Query complexity: must always wrap in "nested" query → more verbose.
// 4. Index buffer: nested docs temporarily in index buffer → higher heap usage during indexing.
// 5. Limit: default max nested docs = 10,000 per parent (index.mapping.nested_objects.limit)

// When to use nested vs object:
// nested:  when you need to query TWO DIFFERENT fields of the SAME array element together.
//          (items.productId=A1 AND items.status=pending → must be nested)
// object:  when you only query one field at a time, or the field is not an array.
//          (address.city = "NYC" → object is fine, address is a single object)
```

## Section 8: Numeric and Special Types

**Q9. What are all the numeric field types — when do you choose each and what is `scaled_float`?**

A: Elasticsearch provides eight numeric types covering integers, floating-point, and a special precision type. Choosing the wrong numeric type wastes storage or loses precision; choosing `scaled_float` correctly saves significant disk space for currency and similar fixed-decimal values:

```json
// ── Integer types ─────────────────────────────────────────────────────────────
{
  "age":           { "type": "byte"    },   // -128 to 127 (1 byte)
  "priority":      { "type": "short"   },   // -32768 to 32767 (2 bytes)
  "quantity":      { "type": "integer" },   // -2.1B to 2.1B (4 bytes) ← most common int
  "userId":        { "type": "long"    },   // -9.2 quintillion to 9.2 quintillion (8 bytes)
  "viewCount":     { "type": "unsigned_long" }  // 0 to 18.4 quintillion (8 bytes)
}

// ── Floating-point types ───────────────────────────────────────────────────────
{
  "rating":    { "type": "half_float"   },  // 16-bit float (~3 sig digits) → small metrics
  "score":     { "type": "float"        },  // 32-bit IEEE 754 → general purpose
  "latitude":  { "type": "double"       },  // 64-bit IEEE 754 → high precision (geo, science)
  "price": {
    "type":           "scaled_float",
    "scaling_factor": 100              // Stores as integer: 129.99 → 12999
                                       // Encoding: price × scaling_factor stored as long
                                       // On retrieval: 12999 / 100 = 129.99
  }
}
// scaled_float advantages:
// ✓ Stored as integer internally → smaller on disk (integer compression > float compression).
// ✓ Avoids floating-point precision errors: 1.10 stored as 110, not 1.09999...
// ✓ Aggregations (sum, avg) work on integers → no floating-point accumulation error.
// Use for: prices, percentages, rates — any fixed-decimal value.
// Scaling factor must be chosen to preserve all significant digits:
//   price with 2 decimal places → scaling_factor: 100
//   rate with 4 decimal places  → scaling_factor: 10000

// ── Boolean type ──────────────────────────────────────────────────────────────
{
  "isActive": {
    "type": "boolean"    // Accepts: true/false (JSON), "true"/"false" (string), 1/0 (int)
  }
}
// Useful for: filter queries (isActive: true → bitset filter, very fast).
// doc_values: true (default) → can aggregate and sort on boolean.

// ── IP type ───────────────────────────────────────────────────────────────────
{
  "clientIp": {
    "type": "ip"    // Stores IPv4 and IPv6 as 128-bit integers internally
  }
}
// Supports CIDR range queries:
GET /logs/_search
{
  "query": {
    "term": { "clientIp": "192.168.0.0/24" }   // Matches all IPs in this CIDR range
  }
}

// ── Geo types ─────────────────────────────────────────────────────────────────
{
  "location": {
    "type": "geo_point"   // { "lat": 40.7128, "lon": -74.0060 } or "40.7128,-74.0060"
  },
  "region": {
    "type": "geo_shape"   // GeoJSON polygons, linestrings, etc.
  }
}

// Geo distance query:
GET /restaurants/_search
{
  "query": {
    "geo_distance": {
      "distance": "1km",
      "location": { "lat": 40.7128, "lon": -74.0060 }
    }
  },
  "sort": [
    {
      "_geo_distance": {
        "location": { "lat": 40.7128, "lon": -74.0060 },
        "order":     "asc",
        "unit":      "m"
      }
    }
  ]
}

// ── Keyword type options ───────────────────────────────────────────────────────
{
  "category": {
    "type":           "keyword",
    "ignore_above":   256,        // Strings longer than 256 chars: not indexed (too long)
    "normalizer":     "lowercase", // Apply normalization at index AND query time
    // normalizer vs analyzer: normalizer never tokenizes (whole string remains one token)
    // normalizer lowercases: "NEW YORK" → "new york" → matches "new york" in term query
    "doc_values":     true,        // default: enables aggregation and sort
    "eager_global_ordinals": true  // Pre-build ordinal mapping for fast terms agg on high-cardinality fields
  }
}

// Normalizer definition:
PUT /my-index
{
  "settings": {
    "analysis": {
      "normalizer": {
        "lowercase": {
          "type":   "custom",
          "filter": ["lowercase", "asciifolding"]  // lowercase + convert é→e, ü→u, etc.
        }
      }
    }
  }
}
```

## Section 9: `flattened` and `runtime` Types

**Q10. What are `flattened` and `runtime` field types — what problems do they solve that regular types cannot?**

A: `flattened` is the solution to mapping explosion from dynamic schemas. `runtime` fields enable schema-on-read — you define how to compute a field at query time from existing stored data, without adding it to the mapping or reindexing:

```json
// ── flattened type: one field for all dynamic subfields ────────────────────────
// Problem: user-defined attributes with arbitrary key names.
// Each unique key would become a new field in the mapping → explosion.

// WRONG approach (dynamic mapping on user attributes):
PUT /events
{
  "mappings": {
    "properties": {
      "attributes": {
        "type": "object",   // Each unique attribute key = new field
        "dynamic": true     // → mapping explosion over time
      }
    }
  }
}

// CORRECT: flattened type
PUT /events
{
  "mappings": {
    "properties": {
      "attributes": {
        "type": "flattened"   // All subfields stored under ONE inverted index entry
      }
    }
  }
}

// Indexing:
POST /events/_doc
{
  "attributes": {
    "color":    "red",
    "material": "leather",
    "size":     "XL",
    "sku":      "SHOE-RED-XL"
  }
}

// flattened type: creates ONE inverted index for the entire object.
// All leaf values are stored as keywords (no text analysis).
// Searching:
GET /events/_search
{
  "query": {
    "term": { "attributes.color": "red" }      // ✓ Exact match on leaf value
  }
}
GET /events/_search
{
  "query": {
    "term": { "attributes": "red" }             // ✓ Match on ANY leaf value
  }
}
// Limitations:
// ✗ No range queries on flattened subfields (all stored as keywords)
// ✗ No numeric aggregations (all values are keyword-type)
// ✗ No highlighting
// ✓ Prevents mapping explosion: no matter how many unique attribute keys, still ONE field

// ── runtime fields: schema-on-read ────────────────────────────────────────────
// Define a field that is COMPUTED from stored fields at query time.
// No reindexing needed. No mapping changes needed. Runs a Painless script.
// Slower than indexed fields (computed per query, not pre-indexed).

PUT /orders/_mapping
{
  "runtime": {
    "revenue_with_tax": {
      "type": "double",
      "script": {
        "source": "emit(doc['total'].value * 1.08)"  // 8% tax
      }
    },
    "order_year": {
      "type": "long",
      "script": {
        "source": "emit(doc['createdAt'].value.year)"  // Extract year from date
      }
    },
    "full_name": {
      "type": "keyword",
      "script": {
        "source": "emit(doc['firstName'].value + ' ' + doc['lastName'].value)"
      }
    }
  }
}

// Query on runtime field (computed at query time):
GET /orders/_search
{
  "query": {
    "range": {
      "revenue_with_tax": { "gte": 100, "lt": 200 }  // Computed for each doc
    }
  },
  "fields": ["revenue_with_tax", "order_year"]        // Include in response
}

// Runtime field in agg:
GET /orders/_search
{
  "size": 0,
  "aggs": {
    "by_year": {
      "terms": { "field": "order_year" },
      "aggs": {
        "total_revenue_with_tax": {
          "sum": { "field": "revenue_with_tax" }
        }
      }
    }
  }
}

// Override a mapped field with a runtime field (fix a mapping mistake without reindexing):
PUT /products/_mapping
{
  "runtime": {
    "price": {                                 // Override the mapped "price" field
      "type": "double",
      "script": {
        "source": "emit(doc['price'].value * 1.0)"   // Apply correction factor
      }
    }
  }
}

// ── Performance: runtime vs indexed ──────────────────────────────────────────
// Indexed field: values pre-computed at index time, stored in doc_values.
//   Query: read from BKD tree or doc_values (fast, O(log n) or sequential).
// Runtime field: Painless script executes for EVERY MATCHING DOCUMENT at query time.
//   Query: script runs on each doc's _source → much slower (10-100x for large result sets).
// Use runtime fields for:
// ✓ Fixing mapping mistakes without reindexing (temporary fix during migration)
// ✓ Ad-hoc exploration and debugging
// ✓ Low-volume queries on indices that are expensive to reindex
// Avoid runtime fields for:
// ✗ High-throughput production queries on large datasets
// ✗ Frequently run aggregations (high CPU cost per query)
```

## Section 10: Index Templates

**Q11. How do index templates work — how do you manage mappings across many indices?**

A: Index templates apply mappings, settings, and aliases automatically when a new index is created with a matching name pattern. They are essential for time-series data (daily log indices) and any system that creates indices programmatically:

```json
// ── Component template: reusable mapping block ─────────────────────────────────
PUT /_component_template/base_fields
{
  "template": {
    "mappings": {
      "properties": {
        "createdAt": {
          "type":   "date",
          "format": "strict_date_optional_time||epoch_millis"
        },
        "tenantId": { "type": "keyword" },
        "userId":   { "type": "keyword" }
      }
    }
  }
}

PUT /_component_template/log_settings
{
  "template": {
    "settings": {
      "number_of_shards":   2,
      "number_of_replicas": 1,
      "index.lifecycle.name": "log-policy"   // ILM policy for log rotation
    }
  }
}

// ── Index template: compose component templates ────────────────────────────────
PUT /_index_template/orders-template
{
  "index_patterns": ["orders-*", "order-events-*"],  // Matches index names
  "priority":       100,                              // Higher priority wins on conflict
  "composed_of":    ["base_fields"],                  // Inherit base fields component
  "template": {
    "settings": {
      "number_of_shards":   3,
      "number_of_replicas": 1
    },
    "mappings": {
      "dynamic":    "strict",                         // Reject unknown fields
      "properties": {
        "orderId": { "type": "keyword" },
        "status":  { "type": "keyword" },
        "total": {
          "type":           "scaled_float",
          "scaling_factor": 100
        },
        "items": {
          "type": "nested",
          "properties": {
            "productId": { "type": "keyword" },
            "quantity":  { "type": "integer" },
            "price": {
              "type":           "scaled_float",
              "scaling_factor": 100
            }
          }
        }
      }
    },
    "aliases": {
      "orders": {}   // Every matched index gets this alias
    }
  }
}

// Now any index matching "orders-*" automatically gets this mapping:
PUT /orders-2024-01  // Automatically applies the template ✓

// ── Data streams: managed time-series indices ─────────────────────────────────
// Data streams = alias over multiple backing indices (daily rollover).
// Requires a matching index template with data_stream config.

PUT /_index_template/logs-template
{
  "index_patterns": ["logs-*"],
  "data_stream":    {},                    // Enable data stream support
  "template": {
    "settings": {
      "number_of_shards":   1,
      "number_of_replicas": 1
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },  // Required for data streams
        "level":      { "type": "keyword" },
        "message":    { "type": "text" },
        "service":    { "type": "keyword" }
      }
    }
  }
}

// Create the data stream:
PUT /_data_stream/logs-myapp
// → Creates backing index: .ds-logs-myapp-000001
// → New documents go to the write index.
// → Daily rollover creates .ds-logs-myapp-000002, etc.
// → Old indices automatically move to cold/frozen tiers via ILM.

// ── Simulate template application ─────────────────────────────────────────────
POST /_index_template/orders-template/_simulate_index/orders-2024-02
// Returns: exactly what mapping/settings would be applied to this index name.
// Use before creating the index to verify template composition.

// ── Updating a template (affects future indices only) ─────────────────────────
// Template changes do NOT affect existing indices.
// Existing indices keep their mapping.
// Only new indices matching the pattern get the updated template.
// To update an existing index: must reindex (same as any mapping change).
```

## Section 11: NestJS Integration

**Q12. How do you manage Elasticsearch mappings and queries in a NestJS application — what are the key abstractions?**

A: The `@elastic/elasticsearch` client is the official Node.js client. NestJS integration requires a module wrapper, typed document interfaces, and a service layer that handles both index lifecycle and query construction:

```typescript
import { Injectable, OnModuleInit, Logger }  from '@nestjs/common';
import { ElasticsearchService }               from '@nestjs/elasticsearch';
import {
    MappingProperty,
    SearchRequest,
    QueryDslQueryContainer,
} from '@elastic/elasticsearch/lib/api/types';

// ── Type-safe document interface ──────────────────────────────────────────────
interface ProductDocument {
    productId:   string;
    name:        string;
    description: string;
    price:       number;
    tags:        string[];
    category:    string;
    inStock:     boolean;
    createdAt:   string;   // ISO-8601 date string
    attributes:  Record<string, string>; // Flattened dynamic fields
    variants: Array<{                    // Nested objects
        sku:      string;
        color:    string;
        size:     string;
        quantity: number;
        price:    number;
    }>;
}

// ── Explicit mapping definition (TypeScript) ──────────────────────────────────
const PRODUCT_MAPPING: Record<string, MappingProperty> = {
    productId:   { type: 'keyword' },
    name: {
        type:     'text',
        analyzer: 'standard',
        fields:   { keyword: { type: 'keyword', ignore_above: 256 } },
    },
    description: {
        type:     'text',
        analyzer: 'english',
    },
    price: {
        type:           'scaled_float',
        scaling_factor: 100,
    },
    tags:     { type: 'keyword' },
    category: { type: 'keyword' },
    inStock:  { type: 'boolean' },
    createdAt: {
        type:   'date',
        format: 'strict_date_optional_time||epoch_millis',
    },
    attributes: { type: 'flattened' },   // Prevent mapping explosion
    variants: {
        type: 'nested',
        properties: {
            sku:      { type: 'keyword' },
            color:    { type: 'keyword' },
            size:     { type: 'keyword' },
            quantity: { type: 'integer' },
            price: {
                type:           'scaled_float',
                scaling_factor: 100,
            },
        },
    },
};

// ── Index management service ──────────────────────────────────────────────────
@Injectable()
export class ProductIndexService implements OnModuleInit {
    private readonly logger = new Logger(ProductIndexService.name);
    private readonly INDEX  = 'products';

    constructor(private readonly es: ElasticsearchService) {}

    async onModuleInit(): Promise<void> {
        await this.ensureIndex();
    }

    async ensureIndex(): Promise<void> {
        const exists = await this.es.indices.exists({ index: this.INDEX });
        if (!exists) {
            await this.es.indices.create({
                index: this.INDEX,
                body: {
                    settings: {
                        number_of_shards:   3,
                        number_of_replicas: 1,
                        'index.mapping.total_fields.limit': 200,  // Guard against explosion
                    },
                    mappings: {
                        dynamic:    'strict',       // Reject unknown fields
                        properties: PRODUCT_MAPPING,
                    },
                },
            });
            this.logger.log(`Index "${this.INDEX}" created`);
        }
    }

    // Update mapping when new fields are added (never change existing types):
    async addMappingField(fieldName: string, definition: MappingProperty): Promise<void> {
        await this.es.indices.putMapping({
            index: this.INDEX,
            body:  { properties: { [fieldName]: definition } },
        });
        this.logger.log(`Field "${fieldName}" added to mapping`);
    }
}

// ── Search service with typed queries ─────────────────────────────────────────
@Injectable()
export class ProductSearchService {
    private readonly INDEX = 'products';

    constructor(private readonly es: ElasticsearchService) {}

    async search(params: {
        query?:       string;
        category?:    string;
        minPrice?:    number;
        maxPrice?:    number;
        tags?:        string[];
        inStock?:     boolean;
        variantColor?: string;   // Nested field query
        from?:        number;
        size?:        number;
    }): Promise<{ hits: ProductDocument[]; total: number }> {
        const must: QueryDslQueryContainer[]    = [];
        const filter: QueryDslQueryContainer[]  = [];

        // Full-text search on text fields:
        if (params.query) {
            must.push({
                multi_match: {
                    query:  params.query,
                    fields: ['name^3', 'description', 'tags'],
                    // ^3: boost name matches 3x vs description matches
                    type:   'best_fields',
                    fuzziness: 'AUTO',
                },
            });
        }

        // Keyword exact filter:
        if (params.category) {
            filter.push({ term: { category: params.category } });
        }

        // Boolean filter:
        if (params.inStock !== undefined) {
            filter.push({ term: { inStock: params.inStock } });
        }

        // Range filter on numeric field:
        if (params.minPrice !== undefined || params.maxPrice !== undefined) {
            filter.push({
                range: {
                    price: {
                        ...(params.minPrice !== undefined && { gte: params.minPrice }),
                        ...(params.maxPrice !== undefined && { lte: params.maxPrice }),
                    },
                },
            });
        }

        // Terms filter on keyword array:
        if (params.tags?.length) {
            filter.push({ terms: { tags: params.tags } });
        }

        // Nested query for variant color:
        if (params.variantColor) {
            filter.push({
                nested: {
                    path:  'variants',
                    query: {
                        bool: {
                            must: [
                                { term: { 'variants.color':    params.variantColor } },
                                { range: { 'variants.quantity': { gt: 0 } } },
                            ],
                        },
                    },
                },
            });
        }

        const request: SearchRequest = {
            index: this.INDEX,
            body: {
                from: params.from ?? 0,
                size: params.size ?? 20,
                query: {
                    bool: { must, filter },
                },
                // Aggregations for faceted search:
                aggs: {
                    categories: {
                        terms: { field: 'category', size: 20 },
                    },
                    price_ranges: {
                        range: {
                            field:  'price',
                            ranges: [
                                { to:   50 },
                                { from: 50,  to: 100 },
                                { from: 100, to: 200 },
                                { from: 200 },
                            ],
                        },
                    },
                    available_colors: {
                        nested: { path: 'variants' },
                        aggs: {
                            colors: {
                                terms: { field: 'variants.color', size: 20 },
                            },
                        },
                    },
                },
                highlight: {
                    fields: {
                        name:        { number_of_fragments: 0 },    // Highlight whole field
                        description: { fragment_size: 150, number_of_fragments: 3 },
                    },
                    pre_tags:  ['<em>'],
                    post_tags: ['</em>'],
                },
                sort: params.query
                    ? ['_score']                                   // Relevance sort for text search
                    : [{ 'name.keyword': 'asc' }],                 // Alphabetical for browse
            },
        };

        const response = await this.es.search<ProductDocument>(request);

        return {
            hits:  response.hits.hits.map(hit => ({
                ...hit._source!,
                _highlights: hit.highlight,
            })),
            total: typeof response.hits.total === 'number'
                ? response.hits.total
                : response.hits.total?.value ?? 0,
        };
    }

    // ── Validate mappings don't diverge from code ─────────────────────────────
    async validateMapping(): Promise<{ valid: boolean; issues: string[] }> {
        const response  = await this.es.indices.getMapping({ index: this.INDEX });
        const actual    = response[this.INDEX]?.mappings?.properties ?? {};
        const issues: string[] = [];

        for (const [field, expected] of Object.entries(PRODUCT_MAPPING)) {
            const actualField = actual[field] as MappingProperty | undefined;
            if (!actualField) {
                issues.push(`Field "${field}" missing from index mapping`);
            } else if ((actualField as any).type !== (expected as any).type) {
                issues.push(
                    `Field "${field}" type mismatch: expected ${(expected as any).type}, ` +
                    `got ${(actualField as any).type}`
                );
            }
        }

        return { valid: issues.length === 0, issues };
    }
}
```

## Section 12: Scenario-Based Questions

**Q13. "Search results are missing documents that definitely contain the search term — what could be wrong with the mapping?"**

A: Missing results from a search that should match is almost always a mismatch between the field type, the analyzer used at index time, and the query type used at search time:

```json
// ── Symptom: searching for "Running" finds nothing ─────────────────────────────
GET /products/_search
{
  "query": {
    "term": { "name": "Running" }   // Returns 0 results
  }
}
// Document has: { "name": "Running Shoes for Marathon" }

// ── Diagnosis: use _validate/query ────────────────────────────────────────────
GET /products/_validate/query?explain=true
{
  "query": {
    "term": { "name": "Running" }
  }
}
// Response:
// {
//   "explanations": [{
//     "explanation": "name:Running"  ← Looking for literal "Running" in text index
//   }]
// }
// Problem: "name" is a text field. The analyzer lowercased "Running" to "running"
// at index time. The term query sends "Running" (uppercase) un-analyzed.
// "Running" ≠ "running" in the inverted index → zero results.

// ── Fix A: use match query (analyzed at query time) ───────────────────────────
GET /products/_search
{
  "query": {
    "match": { "name": "Running" }   // Lowercased to "running" before lookup ✓
  }
}

// ── Fix B: use keyword subfield for exact match ────────────────────────────────
GET /products/_search
{
  "query": {
    "term": { "name.keyword": "Running Shoes for Marathon" }   // Exact string ✓
  }
}

// ── Symptom: keyword field not matching despite correct value ──────────────────
GET /products/_search
{
  "query": {
    "term": { "category": "Electronics" }   // Returns 0 results
  }
}
// Document has: { "category": "electronics" }
// Problem: dynamic mapping created category as text (full-text analysis).
// "electronics" was stored as token "electronic" (stemmed).
// "Electronics" sent via term query (un-analyzed) → not found.

// Check what happened:
GET /products/_mapping
// → { "category": { "type": "text", "fields": { "keyword": { "type": "keyword" } } } }
// It IS a text field (dynamic mapping inferred text for the first value).

// Fix: use the keyword subfield:
GET /products/_search
{
  "query": {
    "term": { "category.keyword": "electronics" }  // ✓ Exact match on keyword field
  }
}

// Long-term fix: explicit mapping with category as keyword from the start:
PUT /products/_mapping
// CANNOT change category from text to keyword (immutable).
// → Reindex with correct mapping.

// ── Symptom: nested field query returns parent even when condition fails ────────
GET /orders/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "items.productId": "A1" } },
        { "term": { "items.status":    "pending" } }
      ]
    }
  }
}
// Returns Bob's order (which has A1-shipped and B2-pending) — FALSE POSITIVE.

// Diagnosis: items is mapped as "object", not "nested".
GET /orders/_mapping
// → { "items": { "type": "object" } }  ← wrong mapping

// Fix: reindex with nested mapping:
PUT /orders-v2
{
  "mappings": {
    "properties": {
      "items": {
        "type": "nested",    // ← correct
        "properties": {
          "productId": { "type": "keyword" },
          "status":    { "type": "keyword" }
        }
      }
    }
  }
}
POST /_reindex { "source": { "index": "orders" }, "dest": { "index": "orders-v2" } }

// ── Using _analyze to debug token generation ───────────────────────────────────
GET /products/_analyze
{
  "field": "name",       // Use the field's actual analyzer
  "text": "Running Shoes for Marathon"
}
// → { "tokens": [
//     { "token": "running", "start_offset": 0,  "end_offset": 7  },
//     { "token": "shoes",   "start_offset": 8,  "end_offset": 13 },
//     { "token": "marathon","start_offset": 18, "end_offset": 26 }
//   ]}
// "for" removed (stop word). "Running" → "running" (lowercased).
// Now you know: only "running", "shoes", "marathon" are in the index for this field.
```

## Quick Reference Tables

### Field Type Selection Guide

| Data | Correct type | Common mistake | Why it matters |
|---|---|---|---|
| Prose / descriptions | `text` | `keyword` | Must be analyzed for full-text search |
| IDs, categories, enums | `keyword` | `text` | Aggregations/sort fail on text |
| Both search and agg | `text` + `keyword` subfield | Single type | Use `name` for search, `name.keyword` for agg |
| Prices, rates (decimal) | `scaled_float` | `float` | Avoids floating-point precision errors |
| Large integers | `long` | `integer` | Integer overflows at ±2.1B |
| Timestamps, dates | `date` with format | `keyword` | Range queries and histogram aggs need date type |
| Array of objects (query two fields) | `nested` | `object` | Object causes cross-object false positives |
| Single embedded object | `object` | `nested` | Nested is slower; object is fine for non-arrays |
| Dynamic user attributes | `flattened` | `object` with `dynamic: true` | Mapping explosion from dynamic object |
| Fix-without-reindex | `runtime` | Adding new field | Computed at query time, no reindex needed |

### text vs keyword Decision Matrix

| Operation | `text` field | `keyword` field | `text` + `keyword` subfield |
|---|---|---|---|
| `match` query | ✓ | ✗ (not intended) | ✓ (`field`) |
| `term` query | ✗ (use match) | ✓ | ✓ (`field.keyword`) |
| `terms` agg | ✗ (error) | ✓ | ✓ (`field.keyword`) |
| `sort` | ✗ (error) | ✓ | ✓ (`field.keyword`) |
| Highlighting | ✓ | ✗ | ✓ (`field`) |
| Fuzzy search | ✓ | ✗ | ✓ (`field`) |
| Prefix / wildcard | ✗ (slow) | ✓ | ✓ (`field.keyword`) |
| `range` (alpha) | ✗ | ✓ | ✓ (`field.keyword`) |

### `object` vs `nested` Comparison

| Property | `object` | `nested` |
|---|---|---|
| Storage | Part of parent document | Separate hidden Lucene documents |
| Array isolation | ✗ Cross-object matching bug | ✓ Each element evaluated independently |
| Query syntax | Regular queries (dot notation) | Must wrap in `nested` query |
| Aggregations | Regular aggregations | Must wrap in `nested` agg |
| Indexing speed | Fast | Slower (N extra docs per N array elements) |
| Memory/disk | Low overhead | Higher (extra docs) |
| Max elements | No limit (watch index buffer) | 10,000 default (`nested_objects.limit`) |
| Use when | Single object OR array without cross-field queries | Array of objects with cross-field boolean queries |

### Dynamic Setting Behaviour

| Setting | New field behaviour | Use case |
|---|---|---|
| `"true"` (default) | Auto-mapped, immediately searchable | Exploratory / prototype indices |
| `"false"` | Stored in `_source` only, NOT searchable | Fixed schema, silently ignore extras |
| `"strict"` | Document rejected with error | Auditable schemas, financial data |
| `"runtime"` | Added as runtime field (script-computed) | Exploration without mapping commitment |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise that **`text` fields are analyzed** (tokenized, lowercased, stemmed) and therefore `term` queries on text fields almost always return zero results — `match` is the correct query for text fields and `term` is the correct query for keyword fields; confusing these two is the most common Elasticsearch mapping mistake in production; (2) knowing the **cross-object matching bug with `object` arrays** exactly — when an array of objects is stored as `object` type, Elasticsearch flattens all field values into arrays, losing the correlation between fields within a single array element, causing boolean queries to match across different elements (`productId=A1` from one element AND `status=pending` from a different element return a false positive); `nested` type is the fix; (3) understanding that **field type changes are impossible without reindexing** — the Lucene segment files on disk are encoded for the original type, and the only path to changing a field type is creating a new index with the correct mapping, using `_reindex` to copy data, and switching an alias; (4) knowing the **difference between analyzers and normalizers** — analyzers tokenize (split a string into multiple tokens) while normalizers never tokenize (the entire string remains one token, just transformed with filters like lowercase); normalizers are used on keyword fields when you want case-insensitive exact matching; (5) being precise about the **`dynamic: "false"` trap** — with `false`, documents containing unknown fields are indexed successfully and the unknown fields appear in `_source`, but they are completely invisible to queries and aggregations; developers often assume unknown fields are simply rejected (that's `"strict"`), not silently stored-but-unsearchable; (6) knowing that **`flattened` type prevents mapping explosion** by indexing all leaf values under a single inverted index, treating every leaf value as a keyword — making it correct for arbitrary user-defined attributes or metadata but wrong for anything requiring numeric range queries or text analysis on the values; (7) understanding **runtime fields as schema-on-read** — they are computed by a Painless script at query time for every matching document, making them suitable for fixing mapping mistakes during a migration window or ad-hoc exploration, but significantly slower than indexed fields for production high-throughput queries; and (8) knowing that the **index-time analyzer and search-time analyzer must be compatible** — if you stem "running" to "run" at index time but search with an un-stemmed analyzer, the query "running" is sent as-is to the inverted index where only "run" exists, returning zero results; using `_analyze` on the field directly is the fastest way to debug what tokens are actually stored.
