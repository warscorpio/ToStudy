# Elasticsearch: Scroll API vs `search_after` for Deep Pagination — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is standard `from` + `size` pagination fundamentally broken for deep pages — what is the "deep pagination problem"?**

A: The `from` + `size` pattern is the most natural way to paginate in Elasticsearch — it mirrors `OFFSET` + `LIMIT` in SQL. It works perfectly for the first few pages but becomes prohibitively expensive as `from` grows. Understanding why requires knowing how distributed search actually executes:

```
Standard from + size pagination:
  GET /products/_search
  { "from": 10000, "size": 10, "sort": [{ "createdAt": "desc" }] }

What Elasticsearch actually does:
  1. Sends the query to ALL shards in the index
  2. EACH shard sorts its local documents and returns the top (from + size) results:
     Each shard returns: 10,000 + 10 = 10,010 documents
  3. Coordinating node receives results from all shards:
     5 shards × 10,010 docs = 50,050 documents in memory
  4. Coordinating node merges and re-sorts all 50,050 documents globally
  5. Takes the results at positions 10,000-10,010 from the merged list
  6. Returns 10 documents to the client

Memory and CPU cost:
  from=0,     size=10: 5 shards × 10   docs = 50 docs merged     → fast
  from=1000,  size=10: 5 shards × 1010 docs = 5050 docs merged   → acceptable
  from=10000, size=10: 5 shards × 10010 docs = 50050 docs merged → expensive
  from=100000,size=10: 5 shards × 100010 docs = 500050 docs merged → very expensive
  from=1000000,size=10: Out of memory, or extremely slow
```

The default safety limit:

```json
// Elasticsearch refuses from + size pagination beyond 10,000 by default:
GET /products/_search
{
  "from": 10001,
  "size": 10
}
// Response:
// {
//   "error": {
//     "type": "search_phase_execution_exception",
//     "reason": "Result window is too large, from + size must be less than or equal
//                to: [10000] but was [10011]. See the scroll api or search_after
//                for an efficient way to request many documents."
//   }
// }

// You CAN raise the limit — but you should not:
PUT /products/_settings
{
  "index.max_result_window": 50000
}
// This doesn't fix the problem — it just allows more memory consumption per query
// At 50,000 with 5 shards: 250,000 docs sorted and merged on every page request

// The three alternatives Elasticsearch recommends:
// 1. from + size:  pages 1-10 only (low page numbers, acceptable cost)
// 2. Scroll API:   full document export / sequential processing (stateful, deprecated)
// 3. search_after: efficient deep pagination and live export (stateless, recommended)
```

**Q2. What is the Scroll API — how does it work and what problem was it originally designed to solve?**

A: The Scroll API was designed for bulk document export — processing every document in an index sequentially, like a database cursor. Instead of computing the global sort on every page, it takes a snapshot of the index state and returns batches from that snapshot:

```
Scroll API flow:

  Step 1: Initialize the scroll — create a snapshot + get first batch
    POST /products/_search?scroll=5m
    { "size": 1000, "query": { "match_all": {} }, "sort": ["_doc"] }

  Elasticsearch:
    → Freezes a view of the index (not a true copy — uses segment-level isolation)
    → Executes the query against that frozen view
    → Returns first batch of 1000 documents + a scroll_id
    → Keeps the scroll context open for 5 minutes

  Step 2: Fetch subsequent batches using the scroll_id
    POST /_search/scroll
    { "scroll": "5m", "scroll_id": "DXF1ZXJ5QW5kRmV0Y2gBAAAAAAAA..." }

  Elasticsearch:
    → Uses the same scroll context (frozen view)
    → Returns the NEXT 1000 documents (no re-sorting)
    → Returns a new scroll_id for the next batch
    → Resets the 5-minute TTL

  Step 3: Repeat until hits.hits is empty
    → hits.hits: [] means you've reached the end

  Step 4: Clean up (important — scroll contexts consume heap memory)
    DELETE /_search/scroll
    { "scroll_id": "DXF1ZXJ5QW5kRmV0Y2gBAAAAAAAA..." }
```

```javascript
// Node.js implementation of Scroll API:
const { Client } = require('@elastic/elasticsearch');
const client = new Client({ node: process.env.ELASTICSEARCH_URL });

async function scrollAllDocuments(indexName: string, query: object): Promise<void> {
    // Step 1: Initialize scroll
    let response = await client.search({
        index:  indexName,
        scroll: '5m',          // Keep scroll context alive for 5 minutes
        size:   1000,          // Documents per batch
        body: {
            query,
            sort: ['_doc'],    // _doc sort = natural index order (fastest for export)
            // No _score needed for full export → saves CPU
        },
    });

    let scrollId = response._scroll_id;
    let totalProcessed = 0;

    while (response.hits.hits.length > 0) {
        // Process this batch:
        await processBatch(response.hits.hits);
        totalProcessed += response.hits.hits.length;
        console.log(`Processed ${totalProcessed} documents`);

        // Fetch next batch:
        response = await client.scroll({
            scroll_id: scrollId,
            scroll:    '5m',   // Reset the TTL with each scroll call
        });

        scrollId = response._scroll_id;  // scroll_id may change between calls
    }

    // Clean up the scroll context:
    await client.clearScroll({ scroll_id: scrollId });
    console.log(`Export complete: ${totalProcessed} total documents`);
}

// Usage:
await scrollAllDocuments('products', { match_all: {} });
```

Why Scroll API has significant problems:

```
Problems with the Scroll API:
  1. Stateful — server maintains scroll context in heap memory per client
     Thousands of concurrent scrolls = OOM pressure on coordinating nodes

  2. Point-in-time snapshot — sees a frozen view of the index
     Documents added/updated after scroll initialisation are INVISIBLE
     Fine for export; terrible for pagination of live data

  3. No jumping to a specific page — must iterate sequentially
     Cannot: "go to page 500" → must scroll through pages 1-499 first

  4. Deprecated for pagination use case since Elasticsearch 7.10
     Elasticsearch documentation now says:
     "Do not use the scroll API for real-time requests.
     Use search_after instead."

  5. TTL management — if scroll context expires before you fetch the next batch:
     The scroll_id becomes invalid → no graceful resumption possible

  6. Scroll IDs rotate — the returned scroll_id may change between scroll calls
     Must always use the most recently returned scroll_id
```

## Section 2: `search_after`

**Q3. How does `search_after` work — what is the mechanism that makes it efficient?**

A: `search_after` is stateless deep pagination using a cursor based on the sort values of the last document seen. Instead of asking for "documents starting at offset 10,000", it asks for "documents that come AFTER this specific sort key" — a question each shard can answer locally without coordinating huge sorted lists:

```
search_after mechanism:

  Instead of: "Give me documents 10,000-10,010"
  It asks:    "Give me the next 10 documents after sort_key=[2024-01-15T10:30:00Z, 'prod-9999']"

  Each shard:
    - Has its own locally sorted inverted index
    - Can efficiently find "next documents after this sort key" via a range scan
    - Returns ONLY the next 'size' documents (no over-fetching)
    - Cost per page: O(log N) to find the position + O(size) to read results

  Coordinating node:
    - Receives small batches from each shard (just 'size' docs each)
    - Merges and returns final 'size' results
    - No matter how deep the page: always efficient
```

```json
// Page 1 — no search_after needed:
GET /products/_search
{
  "size": 10,
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_id": { "order": "asc" } }
    // _id as tiebreaker: REQUIRED for deterministic pagination
    // Without a unique tiebreaker, documents with identical sort values
    // may appear on multiple pages or be skipped entirely
  ],
  "query": { "match": { "description": "keyboard" } }
}

// Response — note the sort values on the last document:
// {
//   "hits": {
//     "hits": [
//       { "_id": "prod-1", "sort": ["2024-01-15T10:30:00.000Z", "prod-1"] },
//       { "_id": "prod-2", "sort": ["2024-01-15T10:25:00.000Z", "prod-2"] },
//       ...
//       { "_id": "prod-10", "sort": ["2024-01-15T09:00:00.000Z", "prod-10"] }
//                                     ↑ capture this sort value for next page
//     ]
//   }
// }

// Page 2 — use search_after with the last document's sort values:
GET /products/_search
{
  "size": 10,
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_id": { "order": "asc" } }
  ],
  "query": { "match": { "description": "keyboard" } },
  "search_after": ["2024-01-15T09:00:00.000Z", "prod-10"]
  // "Give me the next 10 documents that come AFTER this sort position"
  // Must contain EXACTLY the same values as the sort values of the last document
  // in the previous response
}

// Page 3 — use sort values from the last document of page 2:
{
  "search_after": ["2024-01-14T22:00:00.000Z", "prod-20"]
}

// And so on — no server state maintained between requests
```

Why the tiebreaker is mandatory:

```json
// Without a tiebreaker:
// Page 1 documents 1-10: all have createdAt = "2024-01-15T10:30:00Z" (same timestamp)
// Page 2 search_after: ["2024-01-15T10:30:00Z"]
// Elasticsearch finds all documents where createdAt > "2024-01-15T10:30:00Z"
// → Returns 0 documents (all matching docs have EQUAL timestamp, not greater)
// → Pagination is stuck / broken

// With _id as tiebreaker:
// sort: [{ "createdAt": "desc" }, { "_id": "asc" }]
// Page 1: last doc = { createdAt: "2024-01-15T10:30:00Z", _id: "prod-5" }
// Page 2 search_after: ["2024-01-15T10:30:00Z", "prod-5"]
// Elasticsearch: find docs where (createdAt > "2024-01-15T10:30:00Z")
//                             OR (createdAt = "2024-01-15T10:30:00Z" AND _id > "prod-5")
// → Correctly returns the next batch even with duplicate timestamps

// _id is guaranteed unique → perfect tiebreaker
// Can also use a database sequence number or other unique field
```

**Q4. What is a Point-in-Time (PIT) and why is it required for correct `search_after` behaviour when the index is being modified?**

A: `search_after` without a PIT has a subtle consistency problem: if documents are added or deleted between page fetches, the underlying index changes and the sort order shifts — causing documents to be skipped or duplicated across pages. A PIT (Point-in-Time) freezes the index state, giving consistent pagination across all pages of a single session:

```
Problem without PIT:

  Page 1 fetch (index state A): returns docs [1, 2, 3, ..., 10]
  [Between page 1 and page 2: document "prod-5" is deleted, "prod-11" is inserted]
  Page 2 fetch (index state B — changed!):
    → "prod-11" was inserted BEFORE prod-10 in sort order → appears on page 1's range
       → prod-11 is SKIPPED (never returned on any page)
    → "prod-5" was deleted → the sort order of remaining documents shifted
       → Some document from page 1's range is now returned again on page 2 (DUPLICATE)

  Result: missing documents and duplicates across pages

Solution: Point-in-Time (PIT)

  1. Open a PIT: Elasticsearch records which Lucene segments exist RIGHT NOW
  2. All search_after pages use the SAME PIT → consistent view of the index
  3. Changes to the index after the PIT is opened are INVISIBLE to this session
  4. The PIT is lightweight: it pins the relevant Lucene segments (doesn't copy data)
```

```javascript
// Complete search_after + PIT workflow:
const { Client } = require('@elastic/elasticsearch');
const client = new Client({ node: process.env.ELASTICSEARCH_URL });

async function paginateWithSearchAfter(
    indexName: string,
    query: object,
    pageSize: number = 100,
): Promise<AsyncGenerator<any[]>> {

    // Step 1: Open a Point-in-Time
    const pitResponse = await client.openPointInTime({
        index:     indexName,
        keep_alive: '5m',   // Keep PIT alive for 5 minutes
    });
    const pitId = pitResponse.id;

    async function* pages(): AsyncGenerator<any[]> {
        let searchAfter: any[] | undefined = undefined;

        try {
            while (true) {
                // Step 2: Execute search with PIT and search_after
                const response = await client.search({
                    body: {
                        size:  pageSize,
                        query,
                        pit: {
                            id:         pitId,
                            keep_alive: '5m',    // Reset PIT TTL on each request
                        },
                        sort: [
                            { createdAt: { order: 'desc' } },
                            { _shard_doc: 'asc' },
                            // _shard_doc: the recommended tiebreaker when using PIT
                            // (replaces _id — more efficient with PIT)
                            // _shard_doc = internal doc ID, unique within a shard+segment
                        ],
                        ...(searchAfter && { search_after: searchAfter }),
                        // Note: when using PIT, do NOT specify 'index' in the query
                        // The PIT already knows the index
                        track_total_hits: false,  // Skip total count for performance
                    },
                });

                const hits = response.hits.hits;

                if (hits.length === 0) {
                    break;  // No more results
                }

                // Update search_after for the next page:
                searchAfter = hits[hits.length - 1].sort;

                // Yield this page to the caller:
                yield hits.map(hit => hit._source);
            }
        } finally {
            // Step 3: Always close the PIT (releases pinned Lucene segments)
            await client.closePointInTime({ id: pitId });
        }
    }

    return pages();
}

// Usage:
const pageGenerator = await paginateWithSearchAfter('products', {
    bool: {
        filter: [{ term: { category: 'Electronics' } }]
    }
}, 500);

for await (const page of pageGenerator) {
    await processBatch(page);
    console.log(`Processed batch of ${page.length} documents`);
}
```

The PIT and `search_after` sort field interaction:

```json
// When using PIT, sort on '_shard_doc' instead of '_id' for the tiebreaker:
// '_shard_doc' is an internal Lucene document ID that is:
//   - Unique within a shard (not globally unique like _id)
//   - Sequential and monotonically increasing within a segment
//   - Faster to sort on than _id (which requires a global ID lookup)
//   - ONLY meaningful within a PIT context (values change on index updates)

// Correct PIT + search_after sort:
{
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_shard_doc": { "order": "asc" } }   ← PIT-specific tiebreaker
  ]
}

// Without PIT, use _id as tiebreaker:
{
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_id": { "order": "asc" } }          ← stable tiebreaker without PIT
  ]
}
```

## Section 3: Detailed Comparison

**Q5. What are the specific trade-offs between Scroll API and `search_after` + PIT — when is each appropriate?**

A:

```
FEATURE COMPARISON:

Feature                    │ Scroll API           │ search_after + PIT
───────────────────────────┼──────────────────────┼──────────────────────────────
Server state               │ Heavy (scroll context│ Light (PIT only pins segments)
                           │ keeps sorted results)│
Memory per session         │ High (full sorted    │ Low (just segment references)
                           │ result set cached)   │
Concurrent sessions        │ Problematic at scale │ Efficient at any scale
Can skip to arbitrary page │ No (sequential only) │ No (sequential only)
Index consistency          │ Yes (snapshot)       │ Yes (with PIT), No (without)
Works with live data       │ Stale (snapshot)     │ Live (within PIT window)
Works without PIT          │ Yes                  │ Yes (but risk of skips/dupes)
Can resume after TTL expiry│ No (context lost)    │ Yes (store search_after cursor)
Elasticsearch version      │ 2.0+                 │ search_after: 5.0+, PIT: 7.10+
Status                     │ Deprecated for       │ Recommended (current best
                           │ pagination           │ practice)
Sorting requirement        │ None needed          │ Requires consistent sort order
Performance per page       │ Fast (pre-sorted)    │ Fast (O(log N) per shard)
Deep pagination cost       │ O(1) per page after  │ O(log N) per page always
                           │ initial scan         │ (same regardless of depth)
Cleanup required           │ Yes (clearScroll)    │ Yes (closePointInTime)
Client complexity          │ Medium               │ Medium-High
```

```
USE CASE MAPPING:

Use Scroll API for:
  ✓ Legacy Elasticsearch (< 7.10) where PIT is unavailable
  ✓ One-time bulk export that will complete before the scroll TTL expires
  ✓ Pipeline processing where you need to consume ALL documents exactly once
    and index modifications during processing are acceptable to miss
  ✗ Real-time user-facing pagination (deprecated/wrong tool)
  ✗ Long-running processes that might exceed the scroll TTL

Use search_after + PIT for:
  ✓ User-facing pagination on live data (e-commerce, search results)
  ✓ Bulk export with consistent index view (Elasticsearch 7.10+)
  ✓ Any scenario where you might pause and resume pagination
  ✓ High-concurrency environments (multiple users paginating simultaneously)
  ✓ Long-running exports (can re-open PIT if it expires, or use longer keep_alive)
  ✗ Elasticsearch versions before 7.10 (fall back to Scroll or from+size)
  ✗ When you need to jump to page N directly (neither Scroll nor search_after allows this)
```

**Q6. How do you handle errors, timeouts, and resumption in production implementations of both patterns?**

A: Production systems must handle the case where pagination is interrupted — the scroll context or PIT expires, the client crashes, or the process needs to be restarted:

```typescript
// ── Robust Scroll API with error handling ──────────────────────────────────────
async function scrollWithRecovery(
    indexName: string,
    query: object,
    onBatch: (hits: any[]) => Promise<void>,
    checkpointFile: string,
): Promise<void> {
    const SCROLL_TTL  = '5m';
    const BATCH_SIZE  = 1000;

    let scrollId: string | undefined;
    let totalProcessed = 0;

    // Read checkpoint if resuming:
    // NOTE: Scroll cannot truly resume — the scroll_id from a previous run
    // will be invalid. But we can record how many docs were processed and
    // skip them on restart (using from+size for initial batches, then scroll).
    // For true resumption: use search_after instead.

    try {
        // Initialize scroll:
        let response = await client.search({
            index:  indexName,
            scroll: SCROLL_TTL,
            size:   BATCH_SIZE,
            body:   { query, sort: ['_doc'] },
        });

        scrollId = response._scroll_id;

        while (response.hits.hits.length > 0) {
            await onBatch(response.hits.hits);
            totalProcessed += response.hits.hits.length;

            // Extend TTL and fetch next batch:
            try {
                response = await client.scroll({
                    scroll_id: scrollId,
                    scroll:    SCROLL_TTL,
                });
                scrollId = response._scroll_id;
            } catch (err: any) {
                if (err.message?.includes('No search context found')) {
                    // Scroll context expired — cannot resume
                    throw new Error(
                        `Scroll context expired after ${totalProcessed} documents. ` +
                        `Restart the job. Consider using search_after for resumable export.`
                    );
                }
                throw err;
            }
        }

    } finally {
        if (scrollId) {
            await client.clearScroll({ scroll_id: scrollId }).catch(err =>
                console.warn('Failed to clear scroll context:', err.message)
            );
        }
    }
}

// ── Robust search_after + PIT with checkpoint and resumption ───────────────────
interface PaginationCheckpoint {
    pitId:       string;
    searchAfter: any[] | null;
    processed:   number;
    createdAt:   string;
}

async function resumablePaginateWithPIT(
    indexName: string,
    query: object,
    onBatch: (hits: any[]) => Promise<void>,
    checkpointStore: CheckpointStore,  // Redis, DB, or file
): Promise<void> {
    const PAGE_SIZE    = 500;
    const PIT_TTL      = '10m';   // Longer TTL for resumable export
    const SORT_FIELD   = 'createdAt';

    // Try to load an existing checkpoint:
    let checkpoint = await checkpointStore.load() as PaginationCheckpoint | null;

    let pitId: string;
    let searchAfter: any[] | null = null;
    let totalProcessed = 0;

    if (checkpoint) {
        // Check if the saved PIT is still valid:
        try {
            // Test the PIT by making a dummy search:
            await client.search({
                body: {
                    size: 0,
                    pit:  { id: checkpoint.pitId, keep_alive: PIT_TTL },
                },
            });
            // PIT is still valid — resume from checkpoint:
            pitId        = checkpoint.pitId;
            searchAfter  = checkpoint.searchAfter;
            totalProcessed = checkpoint.processed;
            console.log(`Resuming from checkpoint: ${totalProcessed} already processed`);
        } catch {
            // PIT expired — start fresh
            console.log('Checkpoint PIT expired — starting fresh');
            checkpoint = null;
        }
    }

    if (!checkpoint) {
        // Open a new PIT:
        const pitResponse = await client.openPointInTime({
            index:      indexName,
            keep_alive: PIT_TTL,
        });
        pitId = pitResponse.id;

        // Save initial checkpoint:
        await checkpointStore.save({
            pitId,
            searchAfter: null,
            processed:   0,
            createdAt:   new Date().toISOString(),
        });
    }

    try {
        while (true) {
            const response = await client.search({
                body: {
                    size:  PAGE_SIZE,
                    query,
                    pit:   { id: pitId, keep_alive: PIT_TTL },
                    sort:  [
                        { [SORT_FIELD]: { order: 'asc' } },
                        { _shard_doc: 'asc' },
                    ],
                    ...(searchAfter && { search_after: searchAfter }),
                    track_total_hits: false,
                },
            });

            // Update PIT ID (it may change after each request):
            pitId = response.pit_id!;

            const hits = response.hits.hits;
            if (hits.length === 0) break;

            // Process the batch:
            await onBatch(hits.map(h => h._source));
            totalProcessed += hits.length;

            // Update the cursor:
            searchAfter = hits[hits.length - 1].sort;

            // Save checkpoint after EVERY batch (enables resumption):
            await checkpointStore.save({
                pitId,
                searchAfter,
                processed: totalProcessed,
                createdAt: new Date().toISOString(),
            });

            console.log(`Processed ${totalProcessed} documents`);
        }

        console.log(`Export complete: ${totalProcessed} total documents`);
        await checkpointStore.clear();

    } finally {
        // Always close the PIT:
        await client.closePointInTime({ id: pitId }).catch(err =>
            console.warn('Failed to close PIT:', err.message)
        );
    }
}
```

## Section 4: User-Facing Pagination

**Q7. How do you implement user-facing pagination with `search_after` — storing and returning cursors?**

A: User-facing pagination differs from export: users can jump backwards, share links to pages, and sessions can be long. The cursor (search_after value) must be serialised and returned to the client:

```typescript
import { createHash } from 'crypto';

interface PaginatedResponse<T> {
    items:       T[];
    total:       number;
    nextCursor:  string | null;
    prevCursor:  string | null;
    hasMore:     boolean;
}

interface CursorPayload {
    searchAfter: any[];
    pitId:       string;
    query:       string;  // Hash of the query — to detect query changes between pages
    direction:   'forward' | 'backward';
}

class ElasticsearchPaginator {
    private readonly PAGE_SIZE = 20;
    private readonly PIT_TTL   = '5m';

    // Encode cursor: base64(JSON(CursorPayload))
    private encodeCursor(payload: CursorPayload): string {
        return Buffer.from(JSON.stringify(payload)).toString('base64url');
    }

    private decodeCursor(cursor: string): CursorPayload {
        return JSON.parse(Buffer.from(cursor, 'base64url').toString('utf8'));
    }

    private queryHash(query: object): string {
        return createHash('md5').update(JSON.stringify(query)).digest('hex');
    }

    async search(params: {
        query:  object;
        cursor: string | null;
        size?:  number;
    }): Promise<PaginatedResponse<any>> {
        const size       = params.size ?? this.PAGE_SIZE;
        const queryHash  = this.queryHash(params.query);
        let pitId: string;
        let searchAfter: any[] | null = null;

        if (params.cursor) {
            // Decode the cursor from the client:
            const cursor = this.decodeCursor(params.cursor);

            // Validate the cursor belongs to the same query:
            if (cursor.query !== queryHash) {
                // Query changed — start fresh (cursor is invalid for new query)
                throw new Error('Cursor is invalid for the current query');
            }

            pitId       = cursor.pitId;
            searchAfter = cursor.searchAfter;
        } else {
            // First page: open a new PIT
            const pitResponse = await client.openPointInTime({
                index:      'products',
                keep_alive: this.PIT_TTL,
            });
            pitId = pitResponse.id;
        }

        // Fetch size+1 documents to know if there's a next page:
        const response = await client.search({
            body: {
                size: size + 1,  // Fetch one extra to detect hasMore
                query: params.query,
                pit:   { id: pitId, keep_alive: this.PIT_TTL },
                sort: [
                    { createdAt:  { order: 'desc' } },
                    { _shard_doc: { order: 'asc'  } },
                ],
                ...(searchAfter && { search_after: searchAfter }),
                track_total_hits: false,
            },
        });

        // Update PIT ID (may change):
        pitId = response.pit_id!;

        const hits    = response.hits.hits;
        const hasMore = hits.length > size;
        const items   = hasMore ? hits.slice(0, size) : hits;

        // Build the next cursor:
        let nextCursor: string | null = null;
        if (hasMore) {
            nextCursor = this.encodeCursor({
                searchAfter: items[items.length - 1].sort,
                pitId,
                query:       queryHash,
                direction:   'forward',
            });
        } else {
            // No more pages — close the PIT
            await client.closePointInTime({ id: pitId }).catch(console.error);
        }

        return {
            items:      items.map(h => h._source),
            total:      -1,   // Don't count total (expensive) for cursor-based pagination
            nextCursor,
            prevCursor: null,  // search_after only supports forward pagination
            hasMore,
        };
    }
}

// API endpoint:
app.get('/api/products', async (req, res) => {
    const paginator = new ElasticsearchPaginator();

    const query = {
        bool: {
            must:   [{ match: { description: req.query.q as string ?? '' } }],
            filter: [{ term: { isActive: true } }],
        }
    };

    const result = await paginator.search({
        query,
        cursor: req.query.cursor as string ?? null,
    });

    res.json(result);
    // Response:
    // {
    //   "items": [...],
    //   "hasMore": true,
    //   "nextCursor": "eyJzZWFyY2hBZnRlciI6...",   ← opaque cursor, send with next request
    //   "prevCursor": null
    // }
});

// GET /api/products?q=keyboard              ← first page (no cursor)
// GET /api/products?q=keyboard&cursor=eyJ...  ← next page (use returned nextCursor)
```

**Q8. What are the limitations of `search_after` — what can it NOT do that developers often expect?**

A:

```typescript
// ── Limitation 1: Cannot jump to an arbitrary page ───────────────────────────
// User wants to go to page 50 directly:
// With from+size: { from: 490, size: 10 }  ← works (but expensive)
// With search_after: Must paginate through pages 1-49 sequentially first
// → No solution: deep jumping is fundamentally incompatible with the approach
//
// Mitigation: limit how many pages users can access
// "We found 5,000 results. Showing pages 1-100." — beyond 100, prompt users to refine

// ── Limitation 2: Cannot paginate backwards ───────────────────────────────────
// User is on page 5 and clicks "Previous":
// search_after has no built-in backwards pagination
//
// Option A: Reverse the sort order AND reverse the results (complex):
async function prevPage(lastFirstItemSortValues: any[]): Promise<any[]> {
    const response = await client.search({
        body: {
            size: 10,
            sort: [
                { createdAt: { order: 'asc' } },   // REVERSED sort
                { _shard_doc: { order: 'desc' } },  // REVERSED tiebreaker
            ],
            search_after: lastFirstItemSortValues,  // Sort values of first item of current page
            pit: { id: pitId, keep_alive: '5m' },
        },
    });
    // Reverse the returned results (because we reversed the sort):
    return response.hits.hits.reverse().map(h => h._source);
}
// Very complex to implement correctly; requires storing both first and last item sort values

// Option B: Store visited pages in a stack (common practical solution):
// Client maintains: [sortValuesPage1End, sortValuesPage2End, ..., sortValuesCurrentEnd]
// "Previous" pops the stack and re-fetches from the previous search_after
// This requires the client to maintain cursor history

// Option C: Accept forward-only navigation (most common production decision)
// Many search UIs (Google, Amazon, LinkedIn) don't truly support "previous" with deep pagination
// They use infinite scroll (forward only) or show "Next" but not "Previous" beyond nearby pages

// ── Limitation 3: search_after cursor is tightly coupled to sort order ────────
// If the sort changes between pages (different sort field), the cursor is invalid:
// Page 1: sort by price
// User changes to: sort by rating
// search_after from page 1 (price-based) is meaningless for price-based cursor
// → Must start pagination over when sort changes
// → Include sort definition in the cursor → detect changes → restart if changed

// ── Limitation 4: Total hit count is expensive with search_after ──────────────
// Users often want "Showing page 5 of 47 pages" display
// track_total_hits: true → Elasticsearch counts ALL matching docs → expensive
// track_total_hits: false → Elasticsearch returns an approximate count
//
// Practical solution:
const response = await client.search({
    body: {
        query,
        track_total_hits: 1000,  // Exact count up to 1000, "10000+" beyond
        size: 20,
    }
});
// response.hits.total: { value: 1000, relation: "gte" }
// → Display: "More than 1,000 results" when relation is "gte"

// ── Limitation 5: PIT memory consumption at scale ────────────────────────────
// Each PIT pins some Lucene segment readers in memory
// 10,000 concurrent users with open PITs = significant heap pressure
// Mitigation:
//   - Short PIT TTL (1-2 minutes for interactive search)
//   - Close PITs immediately when pagination is complete
//   - Monitor: GET /_cat/pit_stats?v
//   - Alert on: too many open PITs (custom threshold)
```

## Section 5: Complete Comparison and Decision Framework

**Q9. How do you choose between `from+size`, Scroll API, and `search_after` + PIT — and when might you combine approaches?**

A:

```
DECISION FRAMEWORK:

Question 1: How many pages does the user need?
  ≤ 10 pages (≤ 100-200 results total)    → from + size (simple, sufficient)
  > 10 pages, user-facing                 → search_after + PIT
  ALL documents (export/migration)         → search_after + PIT (ES 7.10+) or Scroll

Question 2: Does the user need to jump to arbitrary pages?
  Yes → from + size only (accept the performance cost, limit max page)
  No  → search_after + PIT (much more efficient)

Question 3: Is this a live system with concurrent index updates?
  Yes → search_after + PIT (consistent view across pages)
  No  → Any approach works

Question 4: What Elasticsearch version?
  < 7.10 → PIT not available → from+size (shallow) or Scroll (deep export)
  ≥ 7.10 → search_after + PIT (recommended for all deep pagination)

Question 5: Do you need to resume if the process is interrupted?
  Yes → search_after + PIT + checkpoint storage
  No  → Any approach works for its context

COMBINING APPROACHES:
  Common pattern: from+size for pages 1-3, search_after+PIT for pages 4+
  - Users rarely go beyond page 3 in search results
  - Pages 1-3 with from+size: simple implementation, fast
  - Pages 4+ with search_after: correct deep pagination
  - At the "page 3 → page 4" transition: switch to cursor-based
  - Implementation: track the sort values of page 1-3 items without PIT,
    open PIT at page 4 boundary using search_after from last item of page 3
```

The memory and performance numbers side by side:

```javascript
// Concrete cost comparison for page 1000, size 10, 5 shards, 1M documents per shard:

// from + size:
// Each shard sorts and returns: from + size = 10,000 + 10 = 10,010 documents
// 5 shards × 10,010 = 50,050 documents merged on coordinating node
// Memory: ~50,050 × avg_doc_size (e.g., 1KB = ~50MB per request)
// Time: O(N log N) where N = from + size

// Scroll API (after initialisation):
// Scroll context holds sorted results; fetching next batch is O(size) from cursor
// But: initialisation cost same as from+size for the initial scan
// Memory per scroll context: held on coordinating node heap (per-scroll-context)

// search_after + PIT:
// Each shard: binary search to find sort position → O(log N)
// Returns exactly 'size' documents
// 5 shards × 10 documents = 50 documents merged on coordinating node
// Memory: ~50 × avg_doc_size = trivial
// Time: O(log N per shard) regardless of how deep the page is

// Benchmark (approximate, varies by hardware and document size):
// Page depth:      from+size    │   Scroll   │  search_after
// ─────────────────────────────┼────────────┼───────────────
// Page 10  (100 docs offset):  │  2ms       │   2ms         │  2ms
// Page 100 (1000 offset):      │  10ms      │   2ms         │  2ms
// Page 1000 (10k offset):      │  80ms      │   2ms         │  2ms
// Page 10000 (100k offset):    │  ERROR*    │   5ms         │  3ms
// * Rejected by max_result_window=10000 default
```

## Section 6: Scenario-Based Questions

**Q10. "Your e-commerce platform has a product export job that runs nightly — exporting 2 million products to S3 for analytics. It currently uses the Scroll API but occasionally fails when the scroll context expires. Redesign it."**

A:

```typescript
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';
import { createWriteStream } from 'fs';

// Problems with the current Scroll approach:
// 1. Scroll context expires if the export takes longer than scroll_keep_alive
// 2. On failure: must restart from the beginning (no resumption)
// 3. Memory on coordinating node: holds sorted list of 2M document references

// Redesigned approach: search_after + PIT + checkpointing

interface ExportCheckpoint {
    pitId:       string | null;
    searchAfter: any[] | null;
    exported:    number;
    startedAt:   string;
}

class ResumableProductExporter {
    private readonly BATCH_SIZE    = 2000;
    private readonly PIT_KEEP_ALIVE = '15m';  // Generous TTL for a slow export
    private readonly CHECKPOINT_KEY = 'nightly_export_checkpoint';

    constructor(
        private readonly esClient: any,
        private readonly s3Client: S3Client,
        private readonly redis: any,
    ) {}

    async run(): Promise<void> {
        console.log('Starting nightly product export');
        const startTime = Date.now();

        // Load or create checkpoint:
        let checkpoint = await this.loadCheckpoint();
        let pitId:       string;
        let searchAfter: any[] | null;
        let exported:    number;

        if (checkpoint?.pitId) {
            // Try to resume from checkpoint:
            const isValid = await this.isPITValid(checkpoint.pitId);

            if (isValid) {
                console.log(`Resuming export: ${checkpoint.exported} already exported`);
                pitId       = checkpoint.pitId;
                searchAfter = checkpoint.searchAfter;
                exported    = checkpoint.exported;
            } else {
                console.log('Previous PIT expired — restarting export');
                checkpoint = null;
            }
        }

        if (!checkpoint) {
            // Start fresh:
            const pitResponse = await this.esClient.openPointInTime({
                index:      'products',
                keep_alive: this.PIT_KEEP_ALIVE,
            });
            pitId       = pitResponse.id;
            searchAfter = null;
            exported    = 0;

            await this.saveCheckpoint({ pitId, searchAfter, exported,
                                        startedAt: new Date().toISOString() });
        }

        // Collect all batches into a stream to S3:
        const s3Key    = `exports/products-${new Date().toISOString().split('T')[0]}.ndjson`;
        const chunks: string[] = [];

        try {
            while (true) {
                const response = await this.esClient.search({
                    body: {
                        size:  this.BATCH_SIZE,
                        query: {
                            bool: {
                                filter: [{ term: { isActive: true } }]
                            }
                        },
                        pit: {
                            id:         pitId,
                            keep_alive: this.PIT_KEEP_ALIVE,  // Extend TTL every call
                        },
                        sort: [
                            { _shard_doc: 'asc' },  // Natural order — fastest for export
                        ],
                        _source: ['id', 'name', 'price', 'category', 'sku', 'updatedAt'],
                        track_total_hits: false,
                        ...(searchAfter && { search_after: searchAfter }),
                    },
                });

                // PIT ID may change — update it:
                pitId = response.pit_id;

                const hits = response.hits.hits;
                if (hits.length === 0) break;

                // Serialise batch as NDJSON:
                const batchNDJSON = hits
                    .map(h => JSON.stringify(h._source))
                    .join('\n') + '\n';

                chunks.push(batchNDJSON);
                exported    += hits.length;
                searchAfter  = hits[hits.length - 1].sort;

                // Checkpoint after every batch:
                await this.saveCheckpoint({ pitId, searchAfter, exported,
                                            startedAt: checkpoint?.startedAt ?? new Date().toISOString() });

                if (exported % 100_000 === 0) {
                    console.log(`Exported ${exported.toLocaleString()} products`);
                }
            }

            // Upload to S3:
            await this.s3Client.send(new PutObjectCommand({
                Bucket: 'my-analytics-bucket',
                Key:    s3Key,
                Body:   chunks.join(''),
                ContentType: 'application/x-ndjson',
            }));

            const duration = ((Date.now() - startTime) / 1000).toFixed(1);
            console.log(`Export complete: ${exported.toLocaleString()} products in ${duration}s → s3://${s3Key}`);

            // Clear checkpoint on success:
            await this.clearCheckpoint();

        } catch (err) {
            console.error('Export failed — checkpoint saved for resumption:', err);
            throw err;
        } finally {
            // Always close PIT:
            await this.esClient.closePointInTime({ id: pitId }).catch(console.error);
        }
    }

    private async isPITValid(pitId: string): Promise<boolean> {
        try {
            await this.esClient.search({
                body: { size: 0, pit: { id: pitId, keep_alive: '1m' } },
            });
            return true;
        } catch {
            return false;
        }
    }

    private async loadCheckpoint(): Promise<ExportCheckpoint | null> {
        const data = await this.redis.get(this.CHECKPOINT_KEY);
        return data ? JSON.parse(data) : null;
    }

    private async saveCheckpoint(checkpoint: ExportCheckpoint): Promise<void> {
        await this.redis.set(
            this.CHECKPOINT_KEY,
            JSON.stringify(checkpoint),
            'EX',
            86400,  // Expire checkpoint after 24h (next nightly run starts fresh)
        );
    }

    private async clearCheckpoint(): Promise<void> {
        await this.redis.del(this.CHECKPOINT_KEY);
    }
}
```

**Q11. "Users report that our infinite scroll sometimes shows duplicate products when scrolling. The API uses `search_after`. What could cause this and how do you fix it?"**

A:

```typescript
// ── Root cause 1: Missing or non-unique tiebreaker ────────────────────────────
// Sort only on non-unique field (e.g., createdAt):
{
  "sort": [{ "createdAt": "desc" }]
  // If 50 products have the same createdAt timestamp:
  // page 1 returns products 1-20 of those 50 (which 20? non-deterministic)
  // page 2 search_after: ["2024-01-15T10:30:00Z"]
  // Elasticsearch returns docs where createdAt < "2024-01-15T10:30:00Z"
  // → The remaining 30 products with EQUAL timestamps are SKIPPED
  // → AND some from the first batch may repeat if the sort is non-deterministic
}

// Fix: always add a unique tiebreaker:
{
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_id": { "order": "asc" } }         // Unique tiebreaker
  ]
}
// With PIT, use _shard_doc instead of _id (more efficient):
{
  "sort": [
    { "createdAt": { "order": "desc" } },
    { "_shard_doc": { "order": "asc" } }
  ]
}

// ── Root cause 2: No PIT, index modified between pages ────────────────────────
// Products deleted or re-indexed between page fetches shift the sort order
// Products can appear twice or be skipped

// Fix: use a PIT
const response = await client.search({
    body: {
        query,
        pit:  { id: pitId, keep_alive: '5m' },
        sort: [
            { createdAt: { order: 'desc' } },
            { _shard_doc: { order: 'asc'  } },
        ],
        search_after: searchAfter,
    }
});
// Index changes after the PIT was opened are invisible → consistent pagination

// ── Root cause 3: PIT ID not updated between pages ────────────────────────────
// The PIT ID returned in the response body MAY change between requests
// Using the old PIT ID causes inconsistency

// Bug:
const pitId = response.pit_id;  // ← captured once, never updated
// Later pages use the same pitId even if Elasticsearch returned a new one

// Fix: always update pitId from the response:
let pitId = (await client.openPointInTime({ index: 'products', keep_alive: '5m' })).id;

while (true) {
    const response = await client.search({
        body: {
            pit: { id: pitId, keep_alive: '5m' },
            sort, search_after,
        }
    });

    pitId = response.pit_id;  // ← ALWAYS update the PIT ID from response
    // ...
}

// ── Root cause 4: Passing wrong search_after values ───────────────────────────
// search_after must contain sort values in the SAME ORDER as the sort array
// If sort has 2 fields, search_after must have exactly 2 values

// Bug:
const lastDoc = hits[hits.length - 1];
search_after = [lastDoc._source.createdAt];  // Missing tiebreaker value!

// Fix:
search_after = lastDoc.sort;  // Use .sort directly — contains all sort field values
// The .sort array in each hit contains the sort values in order
// This is the correct and safe way to extract the cursor
```

## Quick Reference Table

| Aspect | `from` + `size` | Scroll API | `search_after` + PIT |
|---|---|---|---|
| **Page depth** | ≤ 10,000 docs (default) | Unlimited | Unlimited |
| **Memory cost** | O(from × shards) | O(1) per batch after init | O(size × shards) always |
| **Server state** | None | Scroll context (heavy) | PIT (lightweight) |
| **Index consistency** | No | Yes (snapshot) | Yes (with PIT) |
| **Arbitrary page jump** | ✓ Yes | ✗ No | ✗ No |
| **Backwards pagination** | ✓ Yes | ✗ No | ✗ Complex |
| **Resume on failure** | ✓ Yes (just re-request) | ✗ No (context lost) | ✓ Yes (store cursor) |
| **Live data** | Slightly stale | Stale (snapshot) | Fresh (within PIT window) |
| **Status** | Fine for shallow pages | Deprecated for pagination | ✓ Recommended |
| **Elasticsearch version** | Any | 2.0+ | `search_after`: 5.0+, PIT: 7.10+ |
| **Cleanup required** | No | ✓ `clearScroll` | ✓ `closePointInTime` |
| **Tiebreaker required** | No | No | ✓ **Yes** (critical) |

| Failure mode | Cause | Fix |
|---|---|---|
| Duplicate results | Non-unique sort field | Add `_id` or `_shard_doc` as tiebreaker |
| Skipped results | No PIT, index modified | Open PIT and use its ID with all pages |
| Stale results | Old PIT ID reused | Always update `pitId = response.pit_id` |
| `search_after` ignored | Wrong number of values | Use `hits[last].sort` directly (not `_source` fields) |
| PIT expired | Long pause between pages | Use longer `keep_alive`; implement checkpoint/resume |
| Scroll context expired | Long processing between batches | Switch to `search_after` + PIT for resumable export |
| `max_result_window` error | `from + size > 10,000` | Switch to `search_after`; don't raise the limit |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) explaining **why `from+size` is O(from × shards)** — each shard must sort and return `from + size` documents regardless of which page is requested; the coordinating node must merge all of those results globally; doubling the page depth doubles the work on every shard and doubles the merge cost; this is why it's "broken" for deep pagination even though it works fine for pages 1-10; (2) articulating **why `search_after` needs a unique tiebreaker** — without it, documents with identical values in the sort field create non-deterministic ordering that causes skips and duplicates; `_id` is the universal safe choice, `_shard_doc` is the efficient choice when using a PIT; (3) explaining the **subtle difference between Scroll and search_after + PIT consistency** — Scroll takes a snapshot of the index at initialisation time and is frozen (new writes are invisible), while search_after + PIT provides a consistent view but within a living index that can still have the PIT window change if documents are updated; both are more consistent than search_after without a PIT; (4) knowing that **the PIT ID can change between requests** and must always be updated from `response.pit_id` — using the original PIT ID after it has changed causes inconsistency and is one of the most common implementation bugs; (5) explaining **the resumability advantage of search_after** — because the cursor (search_after value) is a sort key that lives in the index, a failed export can be restarted from the last checkpoint; Scroll cannot be resumed because the scroll context lives on the server and expires; this makes search_after strictly better for long-running export jobs; and (6) knowing **when the Scroll API is still appropriate** — for Elasticsearch versions before 7.10 where PIT is unavailable, the Scroll API remains the only option for full index traversal; candidates who categorically say "never use Scroll" without mentioning the version constraint reveal a gap in practical knowledge.
