# Relevance Scoring: TF-IDF vs BM25 (Elasticsearch) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is relevance scoring in a search engine and why is it the hard part of search?**

A: Relevance scoring is the process of assigning a numeric score to each document that matches a query, ranking the results so the most useful documents appear first. It is the hard part of search because "most useful" is inherently subjective — the same document that answers one user's question may be irrelevant to another user asking the same words.

```
The information retrieval problem:

User query: "python"
Documents:
  A: "Python is a snake found in Africa..."              (5 mentions of python)
  B: "Python programming tutorial for beginners..."      (3 mentions of python)
  C: "Comparing Java, Python, and Go performance..."     (1 mention of python)

User intent: python programming language
Ideal ranking: B > C > A

But a naive word-counting algorithm ranks: A > B > C (by term frequency)

Relevance scoring tries to bridge the gap between what the user typed
and what they actually meant, using statistical signals from the corpus.
```

**The three signals that drive classical relevance scoring:**
```
1. Term Frequency (TF):
   How often does the query term appear in this document?
   More occurrences → document is more "about" this term
   (subject to diminishing returns — the 100th occurrence matters less than the 1st)

2. Inverse Document Frequency (IDF):
   How rare is this term across ALL documents?
   "python" in 10% of documents → less informative (many docs are about it)
   "multiprocessing" in 0.01% of documents → highly specific → more informative
   Rare terms are more discriminative → should count more toward the score

3. Field Length Normalization:
   A 5-word document where every word is "python" is less authoritative than
   a 500-word document about Python with equal term frequency.
   Normalization adjusts for document length.

TF-IDF combines (1) and (2). BM25 combines (1), (2), and (3) more effectively.
```

**Q2. What is the conceptual difference between TF-IDF and BM25, before looking at formulas?**

A: Both algorithms use the same three signals (TF, IDF, field length), but differ in how they apply them:

```
TF-IDF (classic, developed 1970s-1980s):
  - Multiplies TF × IDF
  - TF grows linearly (or as sqrt) — the more occurrences, the higher the score
  - No natural ceiling on TF contribution
  - Length normalization is a simple divisor (not tunable)
  - Problem: a document with a term 100 times scores proportionally more than one
    with it 10 times, even though the marginal value of the 100th occurrence is
    nearly zero for a user who wants to know if the document is "about" that term

BM25 (Best Matching 25, developed 1994 by Robertson & Sparck Jones):
  - Uses a more sophisticated TF formula with built-in saturation
  - TF contribution approaches an asymptotic ceiling (k1 + 1) as TF → ∞
  - Length normalization is parameterized (tunable via b)
  - Better IDF formula that handles edge cases
  - Default scorer in Elasticsearch 5.0+ (replaced classic TF-IDF)

The intuition behind BM25's name:
  The "BM" stands for "Best Match" — developed as part of the Okapi research project.
  "25" is literally the 25th iteration of the formula that the researchers found
  worked best empirically across test collections. Not a mathematical constant.
```

## Section 2: TF-IDF in Depth

**Q3. What is the mathematical formula for TF-IDF as Lucene (Elasticsearch's foundation) implemented it?**

A: Lucene's classic similarity used a modified TF-IDF rather than the textbook formula, with square root dampening on TF and a shifted IDF:

```
Classic Lucene TF-IDF score for document D matching query Q:

score(D, Q) = Σ (for each term t in Q):
              queryNorm(Q) × coord(Q, D) × (
                tf(t in D) × idf(t)² × t.getBoost() × norm(t, D)
              )

Breaking down each component:

─── tf(t in D) ──────────────────────────────────────────────────────────────────
  tf = sqrt(termFrequency)
  If "python" appears 4 times in document D: tf = sqrt(4) = 2.0
  If "python" appears 16 times: tf = sqrt(16) = 4.0

  The sqrt dampens the effect of repeated terms, but still grows without bound.
  (BM25 fixes this with a proper asymptote.)

─── idf(t) ──────────────────────────────────────────────────────────────────────
  idf = log((numDocs + 1) / (docFreq + 1)) + 1
  Where: numDocs = total documents in index
         docFreq = documents containing this term

  If "python" appears in 1000 of 10000 docs:
  idf = log((10000+1)/(1000+1)) + 1 = log(10.0) + 1 ≈ 3.3

  If "the" appears in 9999 of 10000 docs:
  idf = log((10000+1)/(9999+1)) + 1 = log(1.0002) + 1 ≈ 1.0

  Score uses idf² in the formula — highly discriminative terms get quadratic boost.

─── norm(t, D) ────────────────────────────────────────────────────────────────
  norm = 1 / sqrt(numTerms in D)
  A 4-word document: norm = 1/sqrt(4) = 0.5
  A 100-word document: norm = 1/sqrt(100) = 0.1

  This is stored per-field as a 1-byte value (lossy compression).

─── coord(Q, D) ────────────────────────────────────────────────────────────────
  (Removed in ES 6.0 / Lucene 7.0)
  Was: fraction of query terms found in document
  Query "red python snake": coord = 3/3 if all found, 2/3 if only 2 found

─── queryNorm(Q) ────────────────────────────────────────────────────────────────
  Normalization factor across all query terms (constant for a given query)
  Makes scores from different queries comparable — rarely matters in practice

Example:
  Query: "python tutorial"
  Document D: "Python tutorial for beginners" (4 words, both terms present)
  numDocs = 100, docFreq("python") = 10, docFreq("tutorial") = 5

  tf("python", D)   = sqrt(1) = 1.0
  idf("python")     = log(101/11) + 1 = log(9.18) + 1 ≈ 3.22
  tf("tutorial", D) = sqrt(1) = 1.0
  idf("tutorial")   = log(101/6) + 1  = log(16.8) + 1 ≈ 3.82
  norm(D)           = 1/sqrt(4) = 0.5

  raw_score ≈ (1.0 × 3.22² × 0.5) + (1.0 × 3.82² × 0.5) ≈ 5.18 + 7.29 = 12.47
```

**Q4. What are the specific problems with TF-IDF that motivated BM25?**

A:

```
Problem 1 — Term Frequency Saturation (the most critical flaw):

  In TF-IDF: score grows with each additional occurrence of a term.
  Even with sqrt dampening, a document mentioning "python" 100 times
  scores significantly more than one mentioning it 10 times.

  But does a user asking about "python" care whether a document says it
  100 vs 10 times? After ~5-10 occurrences, additional mentions provide
  very little additional evidence that the document is "about" python.

  TF-IDF doesn't model this diminishing return — it keeps scoring higher.
  BM25 saturates: the 10th mention contributes much less than the 1st.

  Consequence: spam documents stuffed with keywords score artificially high.

─────────────────────────────────────────────────────────────────────────────────

Problem 2 — Length Normalization is not tunable:

  TF-IDF normalizes by 1/sqrt(numTerms) — hard-coded formula.
  For different types of content, you want different normalization:

  Short field (title, SKU): you DO want length normalization
    "Python Book" (2 words, 1 mention) should be relevant despite being short

  Long field (legal document): you DON'T want as much normalization
    A 10,000-word authoritative python reference should score well even
    though its per-word TF is low

  There's no way to tune TF-IDF's normalization. BM25 has a parameter (b).

─────────────────────────────────────────────────────────────────────────────────

Problem 3 — IDF edge cases:

  Classic IDF = log(N / df) breaks when df = N (all docs contain the term)
  → log(N/N) = log(1) = 0 → term contributes nothing
  → Adding 1 inside log and +1 outside are hacks to handle this

  BM25's IDF formula handles these edge cases more gracefully.

─────────────────────────────────────────────────────────────────────────────────

Visualizing the saturation problem:

  Term frequency →    1      2      5     10     50    100
  TF-IDF (sqrt TF):   1.0   1.41   2.24  3.16  7.07  10.0   ← keeps growing
  BM25 (k1=1.2):      1.0   1.54   2.33  2.73  3.07   3.19  ← asymptotes at ~3.33
```

## Section 3: BM25 in Depth

**Q5. What is the BM25 formula and how does each component work?**

A:

```
BM25 score for document D matching query Q:

score(D, Q) = Σ (for each term qi in Q):
              IDF(qi) × (TF(qi,D) × (k1 + 1)) / (TF(qi,D) + k1 × (1 - b + b × |D|/avgdl))

Where:
  TF(qi, D)  = frequency of term qi in document D
  k1         = term saturation parameter (Elasticsearch default: 1.2)
  b          = length normalization parameter (Elasticsearch default: 0.75)
  |D|        = number of terms in document D (field length)
  avgdl      = average field length across all documents in the index

  IDF(qi) = log((N - n(qi) + 0.5) / (n(qi) + 0.5) + 1)
  Where:
    N      = total number of documents
    n(qi)  = number of documents containing term qi

Breaking down the TF component:

  Numerator:   TF × (k1 + 1)
  Denominator: TF + k1 × (1 - b + b × |D|/avgdl)

  As TF → ∞:
  score → (TF × (k1+1)) / (TF + k1 × ...) → (k1+1) / 1 = k1 + 1
  ↑ This is the ASYMPTOTE — score can never exceed k1 + 1 for TF alone
  With k1=1.2: maximum TF contribution is 2.2

  Length normalization factor: (1 - b + b × |D|/avgdl)
  - When b=0: factor = 1.0 → no normalization
  - When b=1: factor = |D|/avgdl → full normalization by relative length
  - When |D|=avgdl: factor = 1.0 → no adjustment (document is exactly average length)
  - When |D| > avgdl: factor > 1 → TF is penalized (denominator grows)
  - When |D| < avgdl: factor < 1 → TF is rewarded (denominator shrinks)
```

```python
# Python implementation of BM25 for a single term:
import math

def bm25_term_score(
    tf:     int,     # Term frequency in this document
    n:      int,     # Documents containing this term
    N:      int,     # Total documents in index
    dl:     int,     # This document's length (terms)
    avgdl:  float,   # Average document length in index
    k1:     float = 1.2,
    b:      float = 0.75
) -> float:
    # IDF (Elasticsearch's BM25 variant, adds 1 to avoid negative IDF):
    idf = math.log((N - n + 0.5) / (n + 0.5) + 1)

    # Length-normalized TF:
    tf_normalized = tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))

    return idf * tf_normalized

# Example: "python tutorial" in a 50-document index
# Document: "Learn Python Tutorial" (3 words)
# Corpus average: 100 words per document
score = (
  bm25_term_score(tf=1, n=10, N=50, dl=3, avgdl=100, k1=1.2, b=0.75) +  # "python"
  bm25_term_score(tf=1, n=5,  N=50, dl=3, avgdl=100, k1=1.2, b=0.75)    # "tutorial"
)
print(f"Score: {score:.4f}")

# Demonstrating saturation with different TF values:
for tf in [1, 2, 5, 10, 50, 100]:
    score = bm25_term_score(tf=tf, n=10, N=50, dl=100, avgdl=100)
    print(f"TF={tf:3d}: score={score:.4f}")
# TF=  1: score=0.5764
# TF=  2: score=0.8262  (↑ large gain)
# TF=  5: score=1.1117  (↑ still growing)
# TF= 10: score=1.2609  (↑ slowing significantly)
# TF= 50: score=1.3951  (↑ barely changed from TF=10)
# TF=100: score=1.4082  (↑ negligible gain from TF=50)
# Max possible ≈ 1.419 (= IDF × (k1+1))
```

**Q6. What does the `k1` parameter control and how do you tune it?**

A:

```
k1 controls the degree of term frequency saturation — how quickly the TF
contribution reaches its ceiling and how high that ceiling is.

Mathematical effect:
  k1 = 0:   TF is completely ignored — binary (term present/absent only)
             score = IDF × 1  for any document containing the term
  k1 = 1.2: (default) — moderate saturation. TF contributes meaningfully
             up to ~3-5 occurrences, then diminishes rapidly
  k1 = 2.0: Higher ceiling. More benefit from higher TF.
             Better when you want to reward documents that deeply cover a topic
  k1 → ∞:  TF contribution grows without bound (approaches classic TF-IDF behavior)

Visualization (ceiling = k1 + 1, IDF factored out):
  k1=0.0:  ceiling=1.0  [|                    ]  (binary — doesn't matter how many)
  k1=1.2:  ceiling=2.2  [||||||||||||         ]  (most gain in first 3-4 mentions)
  k1=2.0:  ceiling=3.0  [||||||||||||||       ]  (rewarding more mentions)
  k1=5.0:  ceiling=6.0  [||||||||||||||||||||]   (high reward for density)
```

```bash
# Tuning k1 for different use cases:

# Use case 1: Short text matching (titles, product names, tags)
# You want exact matches to win; frequency doesn't mean much in 5-word titles
# → Lower k1 (0.5-1.0): one mention is enough
PUT /products/_settings
{
  "similarity": {

      "type": "BM25",
      "k1": 0.5,     # Near-binary: one mention is nearly as good as three
      "b": 0.3       # Less length normalization (titles are all short)
    }
  }
}

# Use case 2: Long document search (research papers, legal docs)
# Frequency matters — a paper that discusses "neural networks" 50 times
# is more authoritative than one that mentions it twice
# → Higher k1 (1.5-2.0): reward topic depth
PUT /papers/_settings
{
  "similarity": {
    "body_similarity": {
      "type": "BM25",
      "k1": 1.8,     # More reward for topic density
      "b": 0.8       # Strong length normalization for fair comparison
    }
  }
}

# Use case 3: FAQ / short Q&A
# Short answers where one precise mention beats ten vague mentions
# → k1 close to 0 (0.3-0.8)
```

**Q7. What does the `b` parameter control and what happens at extreme values?**

A:

```
b controls the degree of field length normalization — how much a document's
length relative to the average affects its score.

b = 0.0:  No length normalization
          A 3-word document with 1 "python" mention = a 3000-word document with 1 "python"
          Use for: fields where length is irrelevant (date, category, ID)

b = 0.75: Default — moderate normalization
          Short documents with same TF get a bonus vs long documents
          Because a short focused document is assumed more relevant per word

b = 1.0:  Full normalization — completely relative to average length
          Score is purely proportional to TF/length (term density)
          A 3-word document with 1 "python" = 30-word with 10 "python"
          Use for: when absolute term density is the right measure

Mathematical interpretation:
  length_factor = (1 - b + b × |D|/avgdl)

  b=0.0: factor = 1.0 always               (length ignored)
  b=0.75 and |D| = avgdl: factor = 1.0     (average length — no adjustment)
  b=0.75 and |D| = 2×avgdl: factor = 1.75  (penalized — document is too long)
  b=0.75 and |D| = 0.5×avgdl: factor = 0.625 (rewarded — short and relevant)
```

```bash
# Practical example: e-commerce product search
# Product names are short (3-5 words), descriptions are long (50-200 words)
# We want BOTH to be comparable — shouldn't be dominated by description length

PUT /products
{

    "similarity": {

      # A 2-word name and a 5-word name should be equally treated

      "desc_sim": { "type": "BM25", "k1": 1.2, "b": 0.75 }
      # b=0.75 for description: long detailed descriptions should be normalized
    }
  },
  "mappings": {
    "properties": {
      "name":        { "type": "text", "similarity": "name_sim" },
      "description": { "type": "text", "similarity": "desc_sim" }
    }
  }
}
```

**Q8. How does BM25's IDF formula differ from classical TF-IDF's IDF, and why does it matter?**

A:

```
Classical TF-IDF IDF:
  idf = log(N / df)                     (textbook Salton formula)
  idf = log(N / (df + 1)) + 1           (Lucene's smoothed variant)
  Where N = total docs, df = docs containing term

BM25 IDF:
  idf = log((N - df + 0.5) / (df + 0.5) + 1)    (Robertson-Sparck Jones)

Key differences and why they matter:

─── Negative IDF prevention ──────────────────────────────────────────────────
  Classic: when df = N (term in every doc), log(1) = 0 → zero contribution
           when df > N/e (~37%), idf < 1 → penalizes the document!

  BM25: adding 1 outside the log ensures IDF is always positive
        Even if term appears in every document: log(0.5/N + 0.5 + 1) > 0

─── Edge case: stop words in corpus ──────────────────────────────────────────
  Suppose "the" appears in 99.9% of documents in a corpus with 10,000 docs
  Classic: idf = log(10000 / 9990 + 1) + 1 ≈ 1.001 (nearly zero contribution)
  BM25:    idf = log((10000-9990+0.5)/(9990+0.5)+1) = log(10.5/9990.5+1) ≈ 0.001

  Both are low, but BM25's formula handles the boundary more smoothly

─── Impact on search quality ─────────────────────────────────────────────────
  In practice, the IDF formula difference is less impactful than the TF saturation.
  The major practical improvements of BM25 come from the TF saturation and the
  parameterized length normalization.

  But BM25's IDF is numerically more stable and handles extreme cases gracefully.
```

## Section 4: Practical Differences

**Q9. Demonstrate the TF saturation difference with a concrete example.**

A:

```
Scenario: Query = "neural networks"
Index of 10,000 AI research papers

Document A: "Introduction to Machine Learning"
  - Mentions "neural networks" 1 time in 200-word abstract

Document B: Marketing blog post about AI trends
  - Mentions "neural networks" 20 times in 500-word post

Ideal result: Document A should rank higher (authoritative, focused abstract)
              Document B is keyword-stuffed marketing content

TF-IDF scoring (simplified, ignoring IDF and normalization for clarity):
  TF-IDF (A): sqrt(1) = 1.0
  TF-IDF (B): sqrt(20) × (200/500 normalization...) ≈ 4.47 × 0.632 ≈ 2.82
  Winner:  B  ← Wrong! Keyword stuffing wins.

BM25 scoring (k1=1.2, b=0.75):
  avgdl = 300 (words)
  BM25 (A): TF=1, dl=200:  (1 × 2.2) / (1 + 1.2 × (0.25 + 0.75×200/300)) = 2.2/1.7 = 1.29
  BM25 (B): TF=20, dl=500: (20 × 2.2) / (20 + 1.2 × (0.25 + 0.75×500/300)) = 44/22.8 = 1.93
  Winner:  B  ← Still wins, but the gap is 1.93/1.29 = 1.5× (vs TF-IDF's 2.82×)

  With appropriate b=0.8 (more aggressive length normalization):
  BM25 (A): dl=200 (short → lower length factor → higher score)
  BM25 (B): dl=500 (long → higher length factor → lower score)
  After normalization: A ≈ 1.41, B ≈ 1.67 — gap further reduced

  And with other query signals (phrase matching, field boost for title):
  A's title "Introduction to Machine Learning" containing relevant terms
  would get a further boost, tipping it above B.

The key lesson:
  BM25 doesn't ELIMINATE keyword stuffing advantage, but REDUCES it significantly.
  Combined with field boosting (title > body) and other signals, it works well.
```

**Q10. How do the length normalization approaches compare between TF-IDF and BM25?**

A:

```
TF-IDF length normalization:
  norm = 1 / sqrt(numTermsInField)
  This is stored per document as a single byte (lossy precision)
  Cannot be tuned without modifying source code

  Consequence: a 4-word field gets norm=0.5, a 100-word field gets norm=0.1
  The ratio is sqrt(100/4) = 5 — meaning the 100-word doc needs 5× more occurrences
  of a term to achieve the same score as the 4-word doc

BM25 length normalization:
  The b parameter makes this tunable:
  - b=0: no normalization (length doesn't matter)
  - b=1: relative normalization by average length
  - b=0.75: default — between the extremes

Comparing the raw normalization factors (avgdl=100, query term appears once):
  doc_length   TF-IDF norm   BM25(b=0.75)factor   BM25(b=0)factor
  ─────────────────────────────────────────────────────────────────
  10           0.316         0.625                 1.0
  50           0.141         0.813                 1.0
  100 (avg)    0.100         1.000                 1.0   (reference point)
  200          0.071         1.375                 1.0
  500          0.045         2.125                 1.0
  1000         0.032         3.250                 1.0

  TF-IDF: sqrt(10/1000) = 3.16× advantage for 10-word vs 1000-word doc
  BM25(b=0.75): 3.25/0.625 = 5.2× advantage for 10-word vs 1000-word doc
  
  Wait — BM25 actually normalizes MORE aggressively than TF-IDF!
  This is because BM25's factor goes into the denominator, amplifying it
  for very long documents more than TF-IDF's sqrt does.
  
  The b parameter lets you dial this: b=0 completely disables it,
  b=0.5 gives gentle normalization, b=1.0 gives full relative normalization.
```

## Section 5: Elasticsearch Implementation

**Q11. How do you configure BM25 parameters in Elasticsearch at the index and field level?**

A:

```bash
# BM25 is the default since Elasticsearch 5.0 — usually no configuration needed
# Elasticsearch uses: k1=1.2, b=0.75 by default

# ── Custom similarity at index level ─────────────────────────────────────────
PUT /search_index
{
  "settings": {
    "similarity": {
      "product_name_bm25": {
        "type": "BM25",
        "k1": 0.8,     # Lower k1: near-binary matching for short product names
        "b":  0.3      # Lower b: product names are all short, don't over-normalize
      },
      "body_bm25": {
        "type": "BM25",
        "k1": 1.5,     # Higher k1: reward topic depth in long documents
        "b":  0.8      # Higher b: normalize long documents aggressively
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type":       "text",
        "similarity": "product_name_bm25"    # Apply custom BM25 to this field
      },
      "description": {
        "type":       "text",
        "similarity": "body_bm25"
      },
      "category": {
        "type":       "keyword"              # No similarity — exact match only
      }
    }
  }
}

# ── Classic TF-IDF (for comparison or legacy compatibility) ───────────────────
PUT /legacy_index
{
  "settings": {
    "similarity": {
      "classic_tfidf": {
        "type": "classic"    # Lucene's classic TF-IDF (deprecated but available)
      }
    }
  }
}

# ── Disable field norms (saves memory, disables length normalization) ─────────
PUT /compact_index
{
  "mappings": {
    "properties": {
      "tags": {
        "type":  "text",
        "norms": false    # Don't store field length — saves ~1 byte per doc per field
                          # Appropriate when length normalization doesn't make sense
                          # (e.g., tags are always short — length is meaningless)
      }
    }
  }
}

# ── Verify the similarity being used ─────────────────────────────────────────
GET /search_index/_mapping
# Check the "similarity" field in each property
```

**Q13. What is the `norms` setting and when do you disable it?**

A:

```bash
# "norms" stores per-document field length information for length normalization.
# Each field, for each document, stores a 1-byte approximation of field length.

# Memory cost: 1 byte per document per text field
# 100M documents × 10 text fields = ~1GB of RAM just for norms
# This is loaded into memory on node startup and stays there

# When to KEEP norms (default: true):
# - Length normalization is meaningful for this field
# - Body text, descriptions, articles — longer ≠ more relevant (normalize it)

# When to DISABLE norms (norms: false):
# - Length normalization makes no sense for this field
# - Tags: "python backend" vs "python" — number of tags shouldn't matter
# - Category names: "Electronics" vs "Electronic Devices" — same category
# - ID fields, codes, short enumerable values
# - Memory is very tight and the field is indexed on many documents

PUT /products/_mapping
{
  "properties": {
    "tags": {
      "type":  "text",
      "norms": false,    # Don't penalize documents with more tags
      "index_options": "freqs"   # Still track term frequency but not positions
    },
    "category_path": {
      "type":  "text",
      "norms": false,
      "index_options": "docs"    # Only track which docs contain term (no freq)
    }
  }
}

# index_options controls what's stored in the inverted index:
# "docs":     Only doc IDs (can't compute TF, can't do phrase queries)
# "freqs":    Doc IDs + term frequency (can compute TF but not positions)
# "positions": + positions (enables phrase queries and proximity scoring)
# "offsets":  + start/end character positions (for highlighting)
# Default: "positions" for text fields (enables phrase queries)
# Memory cost: docs < freqs < positions < offsets
```

**Q14. How does field boosting work in Elasticsearch and how does it interact with BM25?**

```bash
# Field boost: multiply the BM25 score for that field by the boost factor
```

**Q15. What are the `multi_match` query types and how do they aggregate BM25 scores across fields?**

```bash
# A document with "python" in title AND description is better than one

# Use when: terms are distributed across fields
```

## Section 7: Customizing Relevance

**Q16. What is the `function_score` query and what customization options does it provide?**

A: `function_score` wraps any query and modifies its BM25 score using custom functions. It is the primary tool for injecting business signals into relevance:

```bash
# Structure:
{
  "query": {
    "function_score": {
      "query": { /* your base query */ },
      "functions": [ /* one or more scoring functions */ ],
      "score_mode": "sum",      # How to combine function scores: sum|avg|max|min|multiply|first
      "boost_mode": "multiply"  # How combined function score modifies query score: multiply|replace|sum|avg|max|min
    }
  }
}

# ── field_value_factor: use a numeric field as a multiplier ──────────────────
{
  "query": {
    "function_score": {
      "query": { "match": { "description": "python tutorial" } },
      "functions": [
        {
          "field_value_factor": {
            "field":    "popularity_score",   # A numeric field in your documents
            "modifier": "log1p",              # Apply log(1 + x) to avoid extreme values
            "factor":   0.5,                  # Scale the field value before applying modifier
            "missing":  1                     # Default if field is missing
          }
        }
      ],
      "boost_mode": "multiply"   # Final score = BM25_score × popularity_factor
    }
  }
}

# modifier options: none, log, log1p, log2p, ln, ln1p, ln2p, square, sqrt, reciprocal
# log1p is common: safe for values starting at 0, diminishing returns on large values

# ── weight: multiply score by a constant ─────────────────────────────────────
{
  "functions": [
    {
      "filter": { "term": { "is_featured": true } },
      "weight": 2.0   # Featured items get 2× score boost
    },
    {
      "filter": { "term": { "in_stock": true } },
      "weight": 1.5   # In-stock items get 1.5× boost
    }
  ],
  "score_mode": "multiply"   # Combine function results: 2.0 × 1.5 = 3× for featured+in-stock
}

# ── random_score: deterministic random boost (for result diversity) ──────────
{
  "functions": [
    {
      "random_score": { "seed": "today", "field": "_seq_no" }
      # Same seed+field = same random score for each document
      # Changes daily with "today" as seed
      # Prevents the same results appearing in the same order every time
    }
  ]
}
```

**Q17. How do decay functions score by distance from an ideal value?**

A:

```bash
# Decay functions reward documents whose field values are close to an "origin"
# and penalize documents whose values are far from it.
# Shape of the decay: gauss (bell curve), exp (exponential), linear

# ── Date decay: reward recent documents ──────────────────────────────────────
{
  "query": {
    "function_score": {
      "query": { "match": { "content": "python" } },
      "functions": [
        {
          "gauss": {
            "published_at": {
              "origin": "now",       # Ideal value: published today
              "scale":  "30d",       # At 30 days old, score is 0.5× (half-life)
              "offset": "7d",        # Within 7 days: no decay (full score)
              "decay":  0.5          # Score at scale distance from origin (default 0.5)
            }
          }
        }
      ],
      "boost_mode": "multiply"
    }
  }
}
# A post from today: decay_score = 1.0  → final = BM25 × 1.0
# A post from 30 days ago: decay_score = 0.5 → final = BM25 × 0.5
# A post from 90 days ago: decay_score ≈ 0.125 → significantly penalized

# ── Geo distance decay: reward documents near the user ───────────────────────
{
  "functions": [
    {
      "gauss": {
        "location": {
          "origin": { "lat": 40.7128, "lon": -74.0060 },  # New York City
          "scale":  "2km",     # At 2km away, score drops to 0.5
          "offset": "500m",    # Within 500m: no decay
          "decay":  0.5
        }
      }
    }
  ]
}

# ── Price proximity: reward items near the target price ───────────────────────
{
  "functions": [
    {
      "linear": {              # Linear decay instead of gaussian
        "price": {
          "origin": 50,        # Target price: $50
          "scale":  20,        # At $30 or $70 away, score = 0.5
          "offset": 5,         # Within $5 of target: no decay
          "decay":  0.5
        }
      }
    }
  ]
}

# Three decay shapes:
# gauss:  bell curve — gentle near origin, steeper further out (most natural)
# exp:    exponential — constant percentage drop per unit of distance
# linear: straight line to zero — hard cutoff at (scale × 1/decay) distance
```

## Quick Reference Table

| Concept | TF-IDF | BM25 |
|---|---|---|
| **Default in ES** | Legacy (pre-5.0) | Default since ES 5.0 |
| **TF formula** | `sqrt(freq)` (Lucene) | `freq × (k1+1) / (freq + k1 × length_factor)` |
| **TF saturation** | Grows without bound | Asymptotes at `k1 + 1` |
| **IDF formula** | `log((N+1)/(df+1)) + 1` | `log((N−n+0.5)/(n+0.5) + 1)` |
| **Length norm** | `1/sqrt(numTerms)` (hardcoded) | Parameterized via `b` (0=off, 1=full) |
| **Tunable params** | None | `k1` (saturation), `b` (length norm) |
| **Coord factor** | Yes (removed ES 6.0) | No |
| **k1 default** | N/A | 1.2 |
| **b default** | N/A | 0.75 |
| **k1 effect** | N/A | Higher = more reward for repeat terms; 0 = binary |
| **b effect** | N/A | Higher = more length normalization; 0 = no normalization |
| **Keyword stuffing** | More vulnerable | Resistant (saturation) |
| **Configure in ES** | `"type": "classic"` | `"type": "BM25"` in similarity setting |
| **`norms: false`** | Disables length norm | Disables length norm (b param irrelevant) |
| **Explain API** | Shows tf, idf, norm | Shows tf, idf, k1, b, dl, avgdl |
| **`function_score`** | Wraps any query | Wraps any query |
| **`field_value_factor`** | Business signal injection | Business signal injection |
| **Decay functions** | Date/geo/numeric decay | Date/geo/numeric decay |
| **multi_match types** | best_fields, most_fields, cross_fields, phrase | Same |
| **Field boost syntax** | `"field^2.0"` | `"field^2.0"` |
| **Short field recommendation** | N/A | Lower k1 (0.5-1.0), lower b (0.1-0.3) |
| **Long field recommendation** | N/A | Default k1 (1.2-1.5), higher b (0.75-0.85) |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining the **TF saturation problem precisely** — in TF-IDF, a document mentioning a term 100 times scores proportionally higher than one mentioning it 10 times (sqrt dampening helps but doesn't cap it), whereas BM25's TF contribution asymptotically approaches `k1 + 1` as TF grows; this means in BM25, the 50th mention contributes negligibly compared to the 1st, which models how humans actually assess relevance; (2) knowing what **k1 and b actually do** from first principles — k1 controls the height of the TF saturation ceiling (k1=0 is binary, k1=1.2 is standard, higher values reward topic depth) and b controls the degree of length normalization (b=0 ignores length, b=1 normalizes fully by relative length, b=0.75 is the default balance), and being able to say "for short product names I'd use low b because all names are similar length, so normalization just hurts exact matches"; (3) being able to **use the Explain API** — knowing that `GET /index/_explain/id { "query": {...} }` returns the full score breakdown showing individual TF, IDF, k1, b, dl, and avgdl values, which is the only way to debug why a document scored unexpectedly; (4) distinguishing the **three layers of scoring customization** — BM25 similarity settings (index-time, apply per-field), query-time field boosting (multiply a field's score by a constant), and `function_score` queries (inject numeric signals like popularity, recency, geo-distance into the score formula) — knowing when to use each and that they compose multiplicatively; and (5) the **`norms: false` tradeoff** — norms stores ~1 byte per document per text field (100M documents × 10 fields = ~1GB in memory) for length normalization; disabling it saves memory but means all documents are treated as the same length; appropriate for tag fields and other short enumerable values where length normalization makes no semantic sense.
