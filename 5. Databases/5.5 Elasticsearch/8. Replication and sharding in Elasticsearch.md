# Replication and Sharding in Elasticsearch
## Interview Q&A (5 YOE Level)

---

## Section 1: The Architecture

**Q1. What is the physical relationship between an Elasticsearch index, a shard, and a Lucene index — why does this matter for every performance decision?**

A: An Elasticsearch index is a logical namespace. Shards are the physical units of storage and parallelism. Each shard is a complete, self-contained Lucene index. This three-layer relationship determines how data is distributed, searched, and recovered:

```
Elasticsearch logical → physical mapping:

  ES Index "products" (logical)
  ┌──────────────────────────────────────────────────────────────────┐
  │  Primary Shard 0          Primary Shard 1          Primary Shard 2│
  │  ┌──────────────────┐     ┌──────────────────┐    ┌─────────────┐│
  │  │ Lucene Index 0   │     │ Lucene Index 1   │    │Lucene Index │││
  │  │                  │     │                  │    │     2       │││
  │  │ Segments:        │     │ Segments:        │    │             │││
  │  │  seg_0.si        │     │  seg_0.si        │    │             │││
  │  │  seg_1.si        │     │  seg_2.si        │    │             │││
  │  │  ...             │     │  ...             │    │             │││
  │  │                  │     │                  │    │             │││
  │  │ Inverted Index   │     │ Inverted Index   │    │ Inverted    │││
  │  │ Doc Values       │     │ Doc Values       │    │ Index ...   │││
  │  │ Stored Fields    │     │ Stored Fields    │    │             │││
  │  └──────────────────┘     └──────────────────┘    └─────────────┘││
  └──────────────────────────────────────────────────────────────────┘

  Physical node placement (cluster with 3 nodes, 1 replica):
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │   Node 1     │  │   Node 2     │  │   Node 3     │
  │  [P0] [R2]   │  │  [P1] [R0]   │  │  [P2] [R1]   │
  └──────────────┘  └──────────────┘  └──────────────┘
  P = Primary, R = Replica
  No node holds both P and R for the same shard (guaranteed by Elasticsearch).

  Why this matters:
  1. A search query fans out to ALL primary shards (or replicas).
     More shards → more parallelism → but also more coordination overhead.
  2. Each shard is a full Lucene index: heap memory per shard ≈ 50MB minimum.
     100 shards × 50MB = 5GB heap just for shard overhead (independent of data).
  3. Segment merges happen within a shard (not across shards).
     Merge pressure is per-shard, not per-index.
  4. Primary shard count is FIXED at index creation.
     Replicas can be changed at any time; primaries cannot (must reindex or split/shrink).
```

```json
// ── Viewing the physical shard layout ─────────────────────────────────────────
GET /_cat/shards/products?v&h=index,shard,prirep,state,docs,store,node
// index    shard prirep state   docs   store  node
// products 0     p      STARTED 184291 142.3mb node-1
// products 0     r      STARTED 184291 142.3mb node-2
// products 1     p      STARTED 183847 141.9mb node-2
// products 1     r      STARTED 183847 141.9mb node-3
// products 2     p      STARTED 183471 141.7mb node-3
// products 2     r      STARTED 183471 141.7mb node-1
// prirep: p=primary, r=replica
// Each primary and its replica have identical doc counts (fully in sync).

// ── A shard IS a Lucene index ─────────────────────────────────────────────────
GET /_nodes/stats/indices?filter_path=nodes.*.indices.segments
// Shows per-node segment statistics: segment count, memory, doc values, etc.
// High segment count per shard → force merge opportunity.

GET /products/_stats?level=shards
// Detailed per-shard statistics: docs, store size, indexing rate, query rate.
```

**Q2. What is the cluster topology — what roles do master, data, and coordinating nodes play?**

A: Each Elasticsearch node can take on one or more roles. In production, separating roles prevents resource contention between the cluster's control plane (master) and data plane (data nodes):

```
Node roles and their responsibilities:

  MASTER-ELIGIBLE NODES (at least 3 in production):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Elected master (1 at a time):                                    │
  │   • Maintains cluster state: index mappings, shard assignments   │
  │   • Decides shard allocation (which shard lives on which node)   │
  │   • Processes cluster-level changes (create/delete index)        │
  │   • Does NOT handle data reads or writes directly                │
  │                                                                  │
  │ Cluster state is replicated to ALL nodes (read-only copies).     │
  │ Master publishes state changes via a publish/ack protocol.       │
  └──────────────────────────────────────────────────────────────────┘

  DATA NODES:
  ┌──────────────────────────────────────────────────────────────────┐
  │   • Store shards (primary and replica)                           │
  │   • Execute searches and aggregations on their local shards      │
  │   • Handle indexing (write) requests for their primary shards    │
  │   • CPU, RAM, and disk intensive — the "worker" nodes            │
  └──────────────────────────────────────────────────────────────────┘

  COORDINATING-ONLY NODES (no roles assigned):
  ┌──────────────────────────────────────────────────────────────────┐
  │   • Receive client requests                                      │
  │   • Fan out searches to all relevant shards                      │
  │   • Collect and merge results from all shards                    │
  │   • CPU intensive (merging large result sets)                    │
  │   • Do not store data; do not participate in cluster state       │
  └──────────────────────────────────────────────────────────────────┘

  INGEST NODES:
    • Run ingest pipelines (field extraction, enrichment) before indexing.
    • Pipeline: grok patterns, JSON parsing, GeoIP lookup, script transforms.

  TYPICAL PRODUCTION TOPOLOGY:
    3 dedicated master-eligible nodes (small: 4-8 GB heap)
    N data nodes              (large: 32-64 GB heap, fast NVMe)
    2+ coordinating nodes     (medium: 16-32 GB heap, CPU-optimised)
    1-2 ingest nodes          (medium, optional)
```

```json
// ── Node configuration (elasticsearch.yml) ────────────────────────────────────
// Dedicated master:
// node.roles: [master]

// Dedicated data:
// node.roles: [data, data_content, data_hot, data_warm, data_cold]

// Coordinating only:
// node.roles: []   (no roles = pure coordinator)

// ── Viewing node roles in a running cluster ───────────────────────────────────
GET /_cat/nodes?v&h=name,ip,heap.percent,ram.percent,cpu,role
// name    ip         heap.percent  ram.percent  cpu  role
// node-1  10.0.0.1   45            72           12   mr      (master + data)
// node-2  10.0.0.2   48            74           15   mr
// node-3  10.0.0.3   52            76           18   mr
// node-4  10.0.0.4   78            88           35   d       (data only)
// node-5  10.0.0.5   82            90           42   d
// node-6  10.0.0.6   15            30           8    -       (coordinating)
// role: m=master-eligible, d=data, i=ingest, r=remote_cluster_client

GET /_cluster/state/master_node
// Returns the current elected master node ID.

GET /_cluster/health
// Returns: cluster_name, status (green/yellow/red), active_shards, etc.
```

## Section 2: Sharding

**Q3. How does Elasticsearch route a document to a shard — what is the routing formula and when do you override it?**

A: Every document lands on exactly one primary shard, determined by a hash of its routing value. The formula is deterministic — the same key always maps to the same shard, which is how reads find documents without searching all shards:

```
Default routing formula:

  shard = hash(_routing) % number_of_primary_shards

  Default _routing = document _id (if not specified)

  Example: document _id = "order-42"
    hash("order-42") = 1234567890 (some large number)
    1234567890 % 3   = 0          (for a 3-shard index)
    → Document lives on primary shard 0

  This is why PRIMARY SHARD COUNT IS IMMUTABLE:
  If you change from 3 to 4 shards:
    1234567890 % 4 = 2 (different shard!)
  Existing documents would be on shard 0 but the formula now points to shard 2.
  The document would be "lost" (not found by the routing formula).
  → Must reindex to rebuild the shard-document mapping.
```

```json
// ── Checking which shard a document routes to ─────────────────────────────────
GET /products/_search_shards?routing=order-42
// {
//   "nodes": { "node-1": { ... } },
//   "shards": [[
//     { "index": "products", "shard": 0, "primary": true,  "node": "node-1" },
//     { "index": "products", "shard": 0, "primary": false, "node": "node-2" }
//   ]]
// }
// → order-42 routes to shard 0, which has its primary on node-1.

// ── Custom routing: forcing documents to specific shards ──────────────────────
// Use case: multi-tenant — all documents for tenant T on the same shard.
// Benefit: a query for tenant T's data only hits ONE shard (not all).

// Index with custom routing:
PUT /events/_doc/event-1?routing=tenant-abc
{
  "tenantId": "tenant-abc",
  "event":    "page_view"
}

// Search with custom routing:
GET /events/_search?routing=tenant-abc
{
  "query": {
    "term": { "tenantId": "tenant-abc" }
  }
}
// → Query goes to exactly ONE shard (the one that holds tenant-abc's documents).
// → No fan-out to other shards → 3x faster for N shards.

// Enforce routing (reject documents without routing key):
PUT /events
{
  "mappings": {
    "_routing": {
      "required": true      // Document indexed without routing= → 400 error
    }
  }
}

// ── Routing with aliases ───────────────────────────────────────────────────────
PUT /events/_alias/events-tenant-abc
{
  "routing":       "tenant-abc",    // All ops through this alias use routing=tenant-abc
  "filter": {
    "term": { "tenantId": "tenant-abc" }
  }
}
// Application queries "events-tenant-abc" alias:
// → Auto-routes to tenant-abc's shard AND filters to tenant-abc's documents.
// → Perfect multi-tenant isolation without application-level routing management.

// ── Custom routing caveats ────────────────────────────────────────────────────
// 1. Hotspot risk: if one tenant has far more data than others,
//    their shard becomes a hotspot (more data + more queries).
//    Mitigate: use a composite routing key (e.g., tenantId + date bucket).

// 2. Uneven distribution: custom routing can create very unbalanced shards.
//    Monitor: GET /_cat/shards?v and check the "store" column for balance.

// 3. Routing value must be consistent: if you index with routing=X,
//    you MUST query with routing=X or the document won't be found.
//    Missing routing on GET/DELETE: document not found (searched wrong shard).

// ── num_routing_shards: enabling future splits ─────────────────────────────────
PUT /products
{
  "settings": {
    "number_of_shards":      3,
    "number_of_routing_shards": 12
    // Internal routing uses 12 virtual shards.
    // Can split from 3 → 6 → 12 without full reindex.
    // External behavior: still 3 physical shards.
    // Requires the factor to be a multiple: 12/3=4, 12/6=2, 12/12=1 ✓
  }
}
```

**Q4. How do you choose the right number of primary shards — what are the costs of too few and too many?**

A: Shard count is the most consequential index setting. Too few shards create bottlenecks on large indices; too many shards create overhead that degrades performance even on small indices. The right number depends on the expected data volume, query patterns, and heap budget:

```
Shard sizing economics:

  TOO FEW SHARDS (under-sharding):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Single shard holds 500 GB:                                       │
  │ • One node processes ALL queries for this index (no parallelism) │
  │ • Segment merges are large and slow (blocking indexing)          │
  │ • Recovery time: massive (must re-replicate 500 GB)              │
  │ • Cannot be split without downtime (must reindex)                │
  └──────────────────────────────────────────────────────────────────┘

  TOO MANY SHARDS (over-sharding):
  ┌──────────────────────────────────────────────────────────────────┐
  │ 1000 shards × 50 MB heap overhead = 50 GB heap consumed by       │
  │ shard metadata alone (before any actual data!).                  │
  │                                                                  │
  │ Each query fans out to 1000 shards:                              │
  │ • 1000 threads spawned per search                                │
  │ • 1000 results merged by the coordinating node                   │
  │ • Network overhead: 1000 round-trips of results                  │
  │ • Queue depth: 1000 concurrent shard-level searches              │
  │                                                                  │
  │ The cluster state (managed by master) grows proportionally:      │
  │ master heap pressure, slower state updates.                      │
  └──────────────────────────────────────────────────────────────────┘

  SWEET SPOT:
  • 10–50 GB per shard (Elastic's recommendation for most workloads)
  • 20–40 GB for search-heavy workloads (more shards → more parallelism)
  • Up to 50 GB for write-heavy / log workloads
  • Maximum: 200 GB per shard (segments become unwieldy)
  • Maximum active shards per node: 1000 (Elasticsearch 7.x default limit)
```

```json
// ── Shard sizing calculation ──────────────────────────────────────────────────
// Expected index size: 600 GB
// Target shard size: 30 GB
// Primary shards needed: 600 / 30 = 20
// BUT: plan for data growth. If data doubles in 1 year: 1200 GB / 30 = 40 shards.
// Choose: 30 primary shards (covers 6 months of growth, plan to rollover).

// Data: 100 million documents × 500 bytes avg = 50 GB raw
// With compression (~3x): 17 GB stored
// With doc_values and inverted index overhead (~2x): 34 GB total
// Target 30 GB per shard → 2 primary shards (but headroom: 3 is safer).

// ── Per-shard heap estimation ──────────────────────────────────────────────────
GET /_nodes/stats/indices/segments?human
// Look for: segments.memory (per node)
// Estimate: fielddata + filter cache + segment metadata ≈ 50 MB minimum per shard
// Rule of thumb: JVM heap / 50 MB = max shards safely on that node
// 32 GB heap → 640 shards maximum (including all replicas)

// ── Setting shard count at creation ───────────────────────────────────────────
PUT /products
{
  "settings": {
    "number_of_shards":   5,      // IMMUTABLE after creation (unless split/shrink)
    "number_of_replicas": 1       // Can change at any time
  }
}

// ── Checking shard sizes ───────────────────────────────────────────────────────
GET /_cat/shards/products?v&s=store:desc&h=index,shard,prirep,store,docs
// Sorted by shard size descending. Alert if any shard > 50 GB.

GET /_cat/indices?v&h=index,pri,rep,docs.count,store.size,pri.store.size
// pri.store.size = total size of primary shards
// Divide by pri to get average primary shard size.

// ── Shard count guidelines summary ────────────────────────────────────────────
// Type                Recommended shard size   Shards per node limit
// Time-series logs    20-50 GB                 <100 active hot shards per node
// Search indices      10-30 GB                 <50 shards per node
// Small dev indices   use default 1            N/A
// Large write-heavy   30-50 GB                 balance write throughput
```

## Section 3: Replication

**Q5. How does Elasticsearch write a document — what is the primary/replica write model?**

A: Elasticsearch uses a primary-based replication model. Every write goes to the primary shard first, which validates, indexes, and then forwards the operation to all in-sync replica shards in parallel. The response is not sent to the client until all in-sync replicas have confirmed:

```
Write path for a single document:

  Client
    │
    ▼ POST /products/_doc/1
  Coordinating Node (any node receiving the request)
    │ Routes to: hash("1") % 3 = 0 → Primary Shard 0 on Node-1
    │
    ▼
  Node-1 (Primary Shard 0)
    ├─ Validate document against mapping (strict/dynamic)
    ├─ Write to in-memory buffer (IndexWriter buffer)
    ├─ Write to translog (durability — survives crash before segment flush)
    ├─ Forward operation to replica shards IN PARALLEL:
    │     ├──► Node-2 (Replica Shard 0): write to buffer + translog
    │     └──► (additional replicas if number_of_replicas > 1)
    │
    ├─ Wait for all IN-SYNC replicas to acknowledge
    │   (default: wait_for_active_shards = 1 = only primary)
    │
    └──► Client: 200 OK { "_id": "1", "result": "created" }

  Key concepts:
  IN-SYNC replica set: replicas that have acknowledged all operations.
    Replicas fall OUT of sync if: network partition, slow I/O, node restart.
    Master removes out-of-sync replicas from the set.
    An out-of-sync replica must resync from the primary before being readded.

  TRANSLOG: write-ahead log per shard.
    Survives crashes (written to disk with fsync by default every 5s or per-request).
    On startup: translog is replayed to recover operations not yet in segments.
    Flushed (converted to Lucene segments) periodically or when it gets large.
```

```json
// ── Write consistency: wait_for_active_shards ──────────────────────────────────
// Controls how many shard copies must be active before a write proceeds.
// Default: "1" (only the primary must be active).
// "all": all primary + all replicas must acknowledge (strongest consistency).
// "2": primary + 1 replica must acknowledge.

POST /products/_doc/1?wait_for_active_shards=2
{
  "name": "Laptop",
  "price": 999.99
}
// → Waits until primary AND at least 1 replica have confirmed write.
// → If only primary is up (replica down): request BLOCKS or times out.

// Global default for all indices:
PUT /products/_settings
{
  "index.write.wait_for_active_shards": "1"  // Default — writes proceed with primary only
}

// ── Refresh and visibility ─────────────────────────────────────────────────────
// Documents are not searchable immediately after indexing.
// Lucene writes to an in-memory buffer. Documents become searchable only after:
// 1. A refresh: flushes the buffer to a new Lucene segment (default: every 1 second).
// 2. Or: an explicit refresh request.

// After indexing, wait for refresh before querying (testing/low-latency scenarios):
POST /products/_doc/1?refresh=true
{ "name": "Laptop" }
// refresh=true: forces immediate refresh (makes document searchable NOW).
// Expensive: creates a new segment on every write. Avoid in production.

POST /products/_doc/1?refresh=wait_for
{ "name": "Laptop" }
// Waits for the next scheduled refresh (up to index.refresh_interval = 1s).
// Less expensive: doesn't force a new refresh; just waits for the next one.

// ── Optimising write throughput ───────────────────────────────────────────────
// For bulk indexing: increase refresh interval to reduce segment churn.
PUT /products/_settings
{
  "index.refresh_interval": "30s"    // Refresh every 30s instead of 1s
}
// → Fewer segments created → fewer merges → higher indexing throughput.
// → Downside: documents not searchable for up to 30s after indexing.

// Disable replicas during bulk load (add after):
PUT /products/_settings
{
  "index.number_of_replicas": 0      // No replica overhead during initial load
}
// After bulk load:
PUT /products/_settings
{
  "index.number_of_replicas": 1,
  "index.refresh_interval":   "1s"   // Restore defaults
}

// ── Translog configuration ────────────────────────────────────────────────────
// Default: sync translog to disk every 5 seconds (durability window: up to 5s of writes)
PUT /products/_settings
{
  "index.translog.sync_interval": "5s",       // Default: 5s
  "index.translog.durability":    "async"     // async = every sync_interval
                                              // request = fsync on every write (slowest, safest)
}
// "request" durability: survives crashes with zero data loss, but ~2-5ms extra latency per write.
// "async" durability: may lose up to sync_interval seconds of data on node crash.
```

**Q6. How does Elasticsearch handle sequence numbers and primary terms — what do they prevent?**

A: Sequence numbers and primary terms are the foundation of Elasticsearch's optimistic concurrency control and exactly-once delivery guarantees. They replaced the older `_version` system and enable precise conflict detection:

```
Sequence numbers and primary terms:

  PRIMARY TERM:
  • An integer that increments every time a new primary is elected.
  • Used to distinguish "old primary" commands from "new primary" commands.
  • Prevents a network-partitioned (zombie) primary from overwriting new data.
  • Stored in cluster state: { "index": "products", "shard": 0, "primary_term": 3 }

  SEQUENCE NUMBER:
  • A per-shard monotonically increasing integer.
  • Every operation (index, update, delete) gets the next sequence number.
  • Primary assigns sequence numbers and forwards them to replicas.
  • Replicas apply operations in sequence number order.
  • Used for: replay detection, primary/replica resync, optimistic concurrency.

  Example: what happens if a zombie primary tries to write after failover:
  t=0:  Primary P0 (primary_term=2) owns shard 0.
  t=1:  P0 is partitioned. New primary elected: P1 (primary_term=3).
  t=2:  Client writes to P1 (seq_no=100, primary_term=3).
  t=3:  P0 comes back online. It tries to forward old operations (seq_no=99, primary_term=2).
  t=3:  Replicas reject P0's operations: primary_term=2 < current primary_term=3.
        P0's writes are discarded. No data corruption. ✓
```

```json
// ── Optimistic concurrency control with sequence numbers ──────────────────────
// Read the current _seq_no and _primary_term:
GET /products/_doc/1
// {
//   "_index":        "products",
//   "_id":           "1",
//   "_version":      3,
//   "_seq_no":       47,         ← Last sequence number for this document
//   "_primary_term": 2,          ← Primary term when last written
//   "_source": { "name": "Laptop", "price": 999.99 }
// }

// Update with optimistic lock (fails if another write happened between read and write):
PUT /products/_doc/1?if_seq_no=47&if_primary_term=2
{
  "name": "Gaming Laptop",
  "price": 1299.99
}
// → Succeeds ONLY IF the document's current _seq_no=47 AND _primary_term=2.
// → If another writer changed it first (seq_no is now 48):
//   ERROR: VersionConflictEngineException: version conflict, required seqno [47]
//          but found [48]

// ── Retry on conflict (for update operations) ─────────────────────────────────
POST /products/_update/1?retry_on_conflict=3
{
  "script": {
    "source": "ctx._source.price += params.increase",
    "params": { "increase": 100 }
  }
}
// retry_on_conflict=3: retry up to 3 times if a version conflict occurs.
// Elasticsearch re-reads the document and re-applies the script each retry.
// Use for: atomic increments, counter updates, append-to-array operations.

// ── Checking shard-level sequence number state ─────────────────────────────────
GET /products/_stats?filter_path=indices.products.shards
// Shows per-shard: seq_no.global_checkpoint (lowest seq_no all in-sync replicas have)
//                  seq_no.local_checkpoint  (highest seq_no this shard has processed)
// global_checkpoint: the "safe" point — all data up to here is replicated.
// Replicas with local_checkpoint < global_checkpoint are behind.

// ── The global checkpoint and safe recovery ────────────────────────────────────
// If a replica falls behind and then reconnects:
// It only needs to resync operations AFTER its local_checkpoint.
// With sequence numbers: efficient partial resync (not full copy).
// Without sequence numbers (pre-6.0): full shard copy needed on reconnect.
```

## Section 4: The Read Path

**Q7. How does a search request execute across shards — what is the two-phase scatter-gather process?**

A: Every search in Elasticsearch is a two-phase operation: a scatter phase distributes the query to all relevant shards, and a gather phase merges results at the coordinating node. Understanding this determines how to design queries for performance:

```
Two-phase search execution:

  PHASE 1: QUERY (scatter — parallel)
  ┌──────────────────────────────────────────────────────────────────┐
  │ Coordinating node sends query to ALL shards (or routing subset): │
  │                                                                  │
  │   Shard 0: executes query locally → returns [doc_ids + scores]  │
  │   Shard 1: executes query locally → returns [doc_ids + scores]  │
  │   Shard 2: executes query locally → returns [doc_ids + scores]  │
  │                                                                  │
  │ Each shard returns: top K doc_ids with their scores             │
  │ (K = from + size, to allow final merging)                       │
  │ Shard does NOT return document content in Phase 1.              │
  └──────────────────────────────────────────────────────────────────┘
                     │ merge
  PHASE 2: FETCH (gather — targeted)
  ┌──────────────────────────────────────────────────────────────────┐
  │ Coordinating node:                                               │
  │   1. Merges scores from all shards → selects global top K       │
  │   2. Fetches full document content ONLY for the final top K     │
  │      (targeted requests to specific shards by doc_id)           │
  │   3. Returns merged, scored, paginated results to client        │
  └──────────────────────────────────────────────────────────────────┘

  Deep pagination problem:
  GET /products/_search  { "from": 10000, "size": 10 }
  Phase 1: Each of 5 shards must return top 10,010 doc_ids
  → 5 × 10,010 = 50,050 doc_ids collected and sorted at coordinator
  → Only 10 used. 50,040 fetched and discarded.
  → Memory spike at coordinator. O(from × shards) cost.
  → Use search_after or scroll for deep pagination instead.
```

```json
// ── Read preference: primary vs replica ────────────────────────────────────────
// By default: reads are round-robined across primary and replica shards.
// Each has identical data → load balanced across all copies.

GET /products/_search?preference=_local
// _local: prefer shard copies on the same node as the coordinating node.
// Reduces network hops for frequently-searched clusters on same hardware.

GET /products/_search?preference=_primary
// _primary: always read from primary shards (strong consistency).
// Use when replica lag is unacceptable (just-indexed documents must be visible).

GET /products/_search?preference=custom-value
// Custom string: all searches with the same preference value hit the same shard.
// Use for: consistent pagination (same shard order across pages).

// ── Adaptive replica selection (ARS) ─────────────────────────────────────────
// Elasticsearch tracks response time of each shard copy.
// Coordinator sends queries to the FASTEST available shard copy (primary or replica).
// Enabled by default in 7.x+:
GET /_cluster/settings?filter_path=**.use_adaptive_replica_selection
// → { "cluster.routing.use_adaptive_replica_selection": "true" }

// ── search_after: efficient deep pagination ────────────────────────────────────
// Uses the sort values of the last returned document as the cursor.
// No O(from) overhead — constant performance regardless of page depth.

// Page 1:
GET /products/_search
{
  "size": 10,
  "sort": [
    { "price": "asc" },
    { "_id":   "asc" }      // Tie-breaker: must be unique to prevent duplicate pages
  ]
}
// Response includes: "sort": [99.99, "product-42"] for the last result.

// Page 2 (using sort values as cursor):
GET /products/_search
{
  "size": 10,
  "sort": [
    { "price": "asc" },
    { "_id":   "asc" }
  ],
  "search_after": [99.99, "product-42"]   // Resume from last result's sort values
}
// → Efficient: each shard scans only forward from the cursor.

// ── Point-in-time (PIT) for consistent pagination ─────────────────────────────
// Problem with search_after alone: new documents or deletes change pagination.
// PIT freezes a consistent view of the index for the duration of pagination.

POST /products/_pit?keep_alive=5m
// → { "id": "abc123xyz..." }  // PIT ID

// Use PIT with search_after for consistent pages:
GET /_search
{
  "size": 10,
  "pit": {
    "id": "abc123xyz...",
    "keep_alive": "5m"
  },
  "sort": [{ "_doc": "asc" }],   // Sort by internal doc order (fastest)
  "search_after": [47]
}

// Close PIT when done (releases resources):
DELETE /_pit
{ "id": "abc123xyz..." }
```

## Section 5: Replica Management

**Q8. When should you increase vs decrease replica count — what are the exact trade-offs?**

A: Replicas serve two purposes: high availability (HA) and read throughput. Increasing replicas improves both. Decreasing replicas saves storage and indexing overhead. The trade-off is quantifiable:

```
Replica count economics:

  0 replicas:
  ┌──────────────────────────────────────────────────────────────────┐
  │ HA:          None. Shard is unrecoverable if the node dies.      │
  │ Read scale:  None. Only primary serves reads.                    │
  │ Write speed: Fastest (no forwarding to replicas).                │
  │ Storage:     Minimum (1× data).                                  │
  │ Use when:    Batch indexing (add replicas after), dev/test.      │
  └──────────────────────────────────────────────────────────────────┘

  1 replica (most common):
  ┌──────────────────────────────────────────────────────────────────┐
  │ HA:          Survives 1 node failure per shard.                  │
  │ Read scale:  2× read throughput (primary + replica serve reads). │
  │ Write speed: Primary writes + 1 replica forward per shard.       │
  │ Storage:     2× data.                                            │
  │ Use when:    Standard production workload.                       │
  └──────────────────────────────────────────────────────────────────┘

  2 replicas:
  ┌──────────────────────────────────────────────────────────────────┐
  │ HA:          Survives 2 node failures per shard.                 │
  │ Read scale:  3× read throughput.                                 │
  │ Write speed: Primary + 2 replica forwards.                       │
  │ Storage:     3× data.                                            │
  │ Use when:    Read-heavy search (product catalogue, autocomplete). │
  │              Cross-zone HA (zone A: primary, B: replica1, C: replica2). │
  └──────────────────────────────────────────────────────────────────┘
```

```json
// ── Changing replica count at runtime ─────────────────────────────────────────
PUT /products/_settings
{
  "index.number_of_replicas": 2
}
// → Takes effect immediately. Elasticsearch starts copying shards.
// → No downtime. No reindexing required.
// → Cluster goes YELLOW during copy (replicas are INITIALIZING, not yet active).
// → Returns GREEN when all replicas are fully synced.

// ── Cluster health and shard states ───────────────────────────────────────────
GET /_cluster/health/products
// {
//   "status": "yellow",          ← One or more replicas unassigned
//   "active_shards": 3,          ← Primary shards active
//   "relocating_shards": 0,
//   "initializing_shards": 3,    ← Replicas being copied (not yet searchable)
//   "unassigned_shards": 0,
//   "active_shards_percent_as_number": 50.0
// }
// green: all primary AND replica shards are active.
// yellow: all primary shards active, but some replicas unassigned/initializing.
//   → Data is safe (primaries serve reads). HA may be reduced.
// red: one or more PRIMARY shards are unassigned.
//   → Queries for documents on that shard return partial results or errors.
//   → DATA LOSS RISK if shard is not recovered.

// ── Forcing replicas to specific nodes (zone awareness) ───────────────────────
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.awareness.attributes": "zone",
    "cluster.routing.allocation.awareness.force.zone.values": "zone-a,zone-b,zone-c"
  }
}
// Requires nodes to be tagged:
// elasticsearch.yml: node.attr.zone: zone-a

// Effect: primary and replica of the SAME shard are placed in DIFFERENT zones.
// Cluster survives a full zone outage (lost zone had only primaries or only replicas).
// With force values: if zone-b is lost, ES does NOT move zone-b's primaries to zone-a
// (which would put 2 copies on zone-a, leaving zone-c empty).
// Instead: promotes zone-c replicas to primary → balanced across remaining zones.

// ── Exclude nodes from receiving new shards ───────────────────────────────────
// Graceful node decommission (move all shards off before shutdown):
PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.allocation.exclude._name": "node-4"
  }
}
// → All shards on node-4 are relocated to other nodes.
// → Wait until node-4 has zero shards: GET /_cat/shards?node=node-4
// → Then shut down node-4 safely.
// Reset after:
PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.allocation.exclude._name": null
  }
}
```

## Section 6: Split, Shrink, and Clone

**Q9. How do you change primary shard count after index creation — when do you use split vs shrink vs reindex?**

A: Primary shard count is immutable at creation, but Elasticsearch provides three mechanisms to change it — each with different requirements, guarantees, and use cases:

```
Three shard count change operations:

  SPLIT: N primary shards → M primary shards (M must be a multiple of N)
  ┌──────────────────────────────────────────────────────────────────┐
  │ 3 shards → 6 shards (each shard splits into 2)                  │
  │ Requirement: set number_of_routing_shards at creation            │
  │ Data: each original shard's documents are split across the       │
  │       new shards. Some routing keys move to new shards.          │
  │ Downtime: zero. Reads continue during split.                     │
  │ Speed: fast (hard links until merge; no full data copy).         │
  │ Use when: index grew beyond expected size; need more parallelism. │
  └──────────────────────────────────────────────────────────────────┘

  SHRINK: N primary shards → M primary shards (N must be a multiple of M)
  ┌──────────────────────────────────────────────────────────────────┐
  │ 6 shards → 3 shards (pairs of shards merge)                     │
  │ Requirement: ALL primary shards must be on the SAME node.        │
  │ (Relocate all primaries to one node before shrinking.)           │
  │ Data: merged. Source shards hard-linked into target index.       │
  │ Downtime: zero. Reads continue during shrink.                    │
  │ Use when: index is small but has too many shards (over-sharded). │
  └──────────────────────────────────────────────────────────────────┘

  REINDEX: complete data copy with any shard count
  ┌──────────────────────────────────────────────────────────────────┐
  │ 3 shards → 7 shards (arbitrary count change)                    │
  │ Requirement: create new index with correct mapping.              │
  │ Data: full copy (slow — reads all source documents, re-indexes). │
  │ Downtime: near-zero with alias switchover.                       │
  │ Use when: changing both shard count AND mapping simultaneously.  │
  │ Slowest option: proportional to data size.                       │
  └──────────────────────────────────────────────────────────────────┘
```

```json
// ── Split operation ────────────────────────────────────────────────────────────
// Step 1: Make source index read-only (required for split):
PUT /products/_settings
{
  "index.blocks.write": true    // No new documents during split
}

// Step 2: Execute split (3 → 6 shards):
POST /products/_split/products-v2
{
  "settings": {
    "index.number_of_shards": 6,
    "index.number_of_replicas": 1
  }
}
// → Creates products-v2 with 6 primary shards.
// → Uses hard links initially (fast). Data fills in during background merge.
// → Monitor: GET /_cat/recovery/products-v2?v

// Step 3: After split completes, remove the write block on the source
//         (or keep it read-only as a historical index):
PUT /products/_settings { "index.blocks.write": null }

// Step 4: Switch alias to new index:
POST /_aliases {
  "actions": [
    { "remove": { "index": "products",    "alias": "products-alias" } },
    { "add":    { "index": "products-v2", "alias": "products-alias" } }
  ]
}

// ── Shrink operation ───────────────────────────────────────────────────────────
// Step 1: Move ALL primary shards to one specific node:
PUT /products/_settings
{
  "index.routing.allocation.require._name": "node-1",
  "index.blocks.write": true
}
// Wait until all primaries are on node-1:
GET /_cat/shards/products?v&h=shard,prirep,node

// Step 2: Execute shrink (6 → 2 shards):
POST /products/_shrink/products-shrunk
{
  "settings": {
    "index.number_of_shards":   2,
    "index.number_of_replicas": 1,
    "index.routing.allocation.require._name": null    // Allow shard to move again
  }
}

// ── Clone operation (exact copy with same shard count) ─────────────────────────
// Useful for: creating a test index from production data.
PUT /products/_settings { "index.blocks.write": true }

POST /products/_clone/products-clone
{
  "settings": {
    "index.number_of_replicas": 0    // No replicas for the clone (test use)
  }
}
PUT /products/_settings { "index.blocks.write": null }

// ── Reindex with new shard count ──────────────────────────────────────────────
PUT /products-7shards
{
  "settings": {
    "number_of_shards": 7   // Any number — not constrained by multiples
  }
}

POST /_reindex
{
  "source": {
    "index": "products",
    "slice": {            // Parallel reindex with multiple workers
      "id":  0,
      "max": 4            // 4 parallel slices
    }
  },
  "dest": { "index": "products-7shards" }
}
// Throttle to avoid overwhelming the cluster:
POST /_reindex?requests_per_second=500   // 500 docs/s max
```

## Section 7: Index Lifecycle Management (ILM)

**Q10. How does ILM manage shards and replicas across the hot-warm-cold-frozen architecture?**

A: ILM automates index transitions through phases based on age, size, or document count. Each phase has different shard and replica configurations matching the data's access pattern — hot data on fast NVMe, cold data on slow HDD, frozen data on object storage:

```
Hot-Warm-Cold-Frozen data tiers:

  HOT tier (data_hot nodes: NVMe SSDs, high CPU):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Current active write index                                       │
  │ number_of_shards:   1 (one write target)                        │
  │ number_of_replicas: 1 (HA for writes)                           │
  │ Rollover: when index is 7 days old OR 50 GB OR 100M docs        │
  │ Query: all searches include hot indices (freshest data)          │
  └──────────────────────────────────────────────────────────────────┘
                          │ rollover
                          ▼ (becomes read-only after rollover)
  WARM tier (data_warm nodes: HDDs, lower CPU):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Read-only indices (no more writes)                               │
  │ Force merge: reduce to 1 segment per shard (maximum compression)│
  │ Shrink: reduce to fewer shards (not all are needed for reads)   │
  │ number_of_replicas: 1 (still need HA)                           │
  │ Age: 7 days to 30 days                                           │
  └──────────────────────────────────────────────────────────────────┘
                          │ age
                          ▼
  COLD tier (data_cold nodes: cheap HDDs or object storage):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Read-only, infrequently queried                                  │
  │ number_of_replicas: 0 (save storage — data is recoverable)      │
  │ Snapshot stored: backup on S3/GCS before entering cold          │
  │ Queries include cold tier: slower response acceptable            │
  │ Age: 30 days to 90 days                                          │
  └──────────────────────────────────────────────────────────────────┘
                          │ age
                          ▼
  FROZEN tier (searchable snapshots — data in object storage):
  ┌──────────────────────────────────────────────────────────────────┐
  │ Data stored on S3/GCS, NOT on local disks                        │
  │ Queried via searchable snapshot (data fetched on-demand)         │
  │ Very slow queries (S3 latency per segment read)                  │
  │ Near-zero local disk cost                                         │
  │ Age: 90+ days                                                    │
  └──────────────────────────────────────────────────────────────────┘
```

```json

PUT /_ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_age":            "7d",
            "max_primary_shard_size": "50gb",
            "max_docs":           100000000
          },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "7d",
        "actions": {
          "set_priority":  { "priority": 50 },
          "readonly":      {},               // Make index read-only
          "shrink":        { "number_of_shards": 1 },  // Reduce to 1 shard
          "forcemerge":    { "max_num_segments": 1 },  // Single segment per shard
          "allocate": {
            "require": { "data": "warm" }    // Move to warm-tier nodes
          }
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "set_priority": { "priority": 0 },
          "allocate": {
            "number_of_replicas": 0,         // Remove replicas
            "require": { "data": "cold" }    // Move to cold-tier nodes
          }
        }
      },
      "frozen": {
        "min_age": "90d",
        "actions": {
          "searchable_snapshot": {
            "snapshot_repository": "my-s3-repo"  // Move to S3
          }
        }
      },
      "delete": {
        "min_age": "365d",
        "actions": {
          "delete": {}                        // Delete after 1 year
        }
      }
    }
  }
}

// ── Checking ILM status for an index ─────────────────────────────────────────
GET /logs-myapp-2024.01.15/_ilm/explain
// {
//   "indices": {
//     "logs-myapp-2024.01.15": {

//       "managed":         true,

//       "lifecycle_date":  "2024-01-15T00:00:00Z",
//       "phase":           "warm",
//       "action":          "forcemerge",

//       "phase_time":      "2024-01-22T00:00:00Z",

//     }
//   }

// ── Rollover: creating new write indices automatically ────────────────────────
// Rollover creates a new index when the old one meets conditions.
// Requires: an alias with is_write_index:true pointing to the current write target.

PUT /logs-myapp-000001

      "is_write_index": true
    }
  }
}

// Rollover check (called by ILM or manually):

// Searches on logs-myapp alias: hit BOTH 000001 and 000002.
```

## Section 8: Cross-Cluster Replication

**Q11. What is Cross-Cluster Replication (CCR) — how does it differ from regular replica shards?**

A: Regular replicas live in the same cluster as the primary and are synchronously updated. CCR replicates indices across physically separate clusters — primarily for geo-distribution, disaster recovery, or reporting workloads that should not impact production:

```
CCR topology:

  Leader Cluster (production, US-East)       Follower Cluster (DR, EU-West)
  ┌──────────────────────────────┐           ┌──────────────────────────────┐
  │  Index: products (leader)    │           │  Index: products (follower)   │
  │  Shards: [P0] [P1] [P2]     │──async────►│  Shards: [F0] [F1] [F2]    │
  │  Writes: allowed ✓           │           │  Writes: blocked (read-only) │
  │  Reads:  normal             │           │  Reads:  from local cluster  │
  └──────────────────────────────┘           └──────────────────────────────┘
  
  Replication mechanism:
  Follower continuously polls leader for new translog operations.
  Not real-time (some lag, typically seconds).
  Follower applies operations in sequence number order.
  Follower is ALWAYS behind the leader (asynchronous).
  
  Use cases:
  1. Disaster recovery (follower in different region promotes to leader on failover).
  2. Local reads for geographically distributed users.
  3. Analytics workloads isolated from production (queries don't impact leader).
  4. Federation: merge data from multiple clusters for cross-cluster search.
```

```json
// ── Setting up CCR ────────────────────────────────────────────────────────────
// On follower cluster: configure remote cluster connection:
PUT /_cluster/settings
{
  "persistent": {
    "cluster.remote.leader-cluster.seeds": ["10.0.0.1:9300", "10.0.0.2:9300"]
  }
}

// Create a follower index that replicates from the leader:
PUT /products/_ccr/follow
{
  "remote_cluster":  "leader-cluster",
  "leader_index":    "products",
  "settings": {
    "index.number_of_replicas": 1     // Replicas on the FOLLOWER cluster
  }
}

// Monitor replication lag:
GET /products/_ccr/stats
// {
//   "follower_aliases": ["products"],
//   "shard_stats": [{
//     "leader_global_checkpoint":   1000000,
//     "follower_global_checkpoint": 999850,  ← 150 ops behind
//     "bytes_read":                 148291849,
//     "operations_read":            999850,
//     "time_since_last_read_millis": 325      ← replication lag in ms
//   }]
// }

// Pause replication (for maintenance):
POST /products/_ccr/pause_follow

// Resume:
POST /products/_ccr/resume_follow

// Promote follower to a regular index (leader failover):
POST /products/_ccr/unfollow
// After: follower becomes a writable, standalone index.

// ── Auto-follow patterns: automatically replicate new indices ─────────────────
PUT /_ccr/auto_follow/logs-pattern
{
  "remote_cluster":          "leader-cluster",
  "leader_index_patterns":   ["logs-*"],      // Auto-follow any index matching this
  "follow_index_pattern":    "{{leader_index}}",
  "settings": {
    "index.number_of_replicas": 0   // No replicas for auto-followed log indices
  }
}
// Any new "logs-*" index on the leader: automatically created as follower index.
```

## Section 9: Monitoring Cluster Health

**Q12. What metrics and APIs reveal the health of sharding and replication — how do you diagnose a degraded cluster?**

A: A degraded cluster shows as yellow or red status. Diagnosing the root cause requires distinguishing between: unassigned replicas (yellow — safe), unassigned primaries (red — data risk), and allocation failures (misconfiguration or resource exhaustion):

```json
// ── Complete health diagnostic workflow ────────────────────────────────────────

// Step 1: Overall cluster state:
GET /_cluster/health
// cluster_state: green | yellow | red
// active_primary_shards: must equal expected count
// unassigned_shards: 0 for green, >0 for yellow/red

// Step 2: Which shards are unassigned and why:
GET /_cat/shards?v&h=index,shard,prirep,state,node,reason
// state: STARTED | INITIALIZING | RELOCATING | UNASSIGNED
// reason: NODE_LEFT | ALLOCATION_FAILED | INDEX_CREATED | etc.

// Step 3: WHY a shard is unassigned (allocation explanation):
GET /_cluster/allocation/explain
// Without body: explains the FIRST unassigned shard it finds.
// With body:
GET /_cluster/allocation/explain
{
  "index":   "products",
  "shard":   0,
  "primary": false    // false = explain a replica
}
// Response:
// {
//   "index": "products",
//   "shard": 0,
//   "primary": false,
//   "current_state": "unassigned",
//   "unassigned_info": {
//     "reason": "NODE_LEFT",
//     "last_allocation_status": "no_attempt"
//   },
//   "can_allocate": "no",
//   "allocate_explanation": "cannot allocate because allocation is not permitted to any of the nodes",
//   "node_allocation_decisions": [
//     {
//       "node_name": "node-1",
//       "deciders": [{
//         "decider":     "same_shard",
//         "decision":    "NO",
//         "explanation": "a copy of this shard is already allocated to this node"
//         // Can't put replica on node-1 because primary is already there.
//       }]
//     }
//   ]
// }

// Step 4: Common causes and fixes:
// "same_shard" decision NO → Not enough nodes for this replica count.
//   Fix: add more nodes OR reduce replica count.
//   PUT /products/_settings { "index.number_of_replicas": 0 }

// "disk watermark" → Node is nearly full.
GET /_cat/allocation?v&h=shards,disk.used,disk.avail,disk.percent,node
// disk.percent > 85%: WARNING watermark (no new shard allocation to this node)
// disk.percent > 90%: HIGH watermark (relocate shards OFF this node)
// disk.percent > 95%: FLOOD_STAGE (index made read-only)
// Fix: free disk space or add nodes.

// ── Disk watermark configuration ──────────────────────────────────────────────
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.disk.watermark.low":        "85%",
    "cluster.routing.allocation.disk.watermark.high":       "90%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "95%"
  }
}

// ── Shard rebalancing settings ─────────────────────────────────────────────────
GET /_cluster/settings?flat_settings=true&include_defaults=true
// cluster.routing.rebalance.enable: all | primaries | replicas | none
// none: disable all shard movements (during maintenance).
// primaries: only move primary shards.

PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.rebalance.enable": "none"   // Freeze shard movement
  }
}
// After maintenance:
PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.rebalance.enable": null      // Restore default (all)
  }
}

// ── Recovery speed tuning ──────────────────────────────────────────────────────
// Shard recovery (copying data to a new replica) uses network I/O.
// Default is deliberately throttled to not overwhelm the cluster.
PUT /_cluster/settings
{
  "transient": {
    "indices.recovery.max_bytes_per_sec": "500mb"   // Increase during recovery (default: 40mb)
  }
}
// After recovery completes: reset to default or reduce to avoid impacting queries.
```

## Section 10: Scenario-Based Questions

**Q13. "The cluster turned red — one primary shard is unassigned after a node failure — what do you do?"**

A: A red cluster with an unassigned primary means some documents are potentially inaccessible. The response depends on whether the data is recoverable from another copy or the node needs to be brought back:

```json
// ── Step 1: Assess the situation ──────────────────────────────────────────────
GET /_cluster/health
// cluster_state: red  ← critical
// active_primary_shards: 2 (of 3 expected)
// unassigned_shards: 1 (or 2 including its replica)

GET /_cat/shards/products?v&h=shard,prirep,state,node
// products  0  p  STARTED     node-1
// products  0  r  STARTED     node-2
// products  1  p  STARTED     node-2
// products  1  r  STARTED     node-1
// products  2  p  UNASSIGNED  ←── primary missing! (node-3 died)
// products  2  r  UNASSIGNED  ←── replica also missing (was on node-3 too?!)

// Step 2: Was there a replica of shard 2 on another node?
GET /_cluster/allocation/explain
{
  "index":   "products",
  "shard":   2,
  "primary": true
}
// Response reveals: no copy of this shard exists on any live node.
// (Both primary and replica were on node-3 — CRITICAL misconfiguration:
//  replica should NEVER be on the same node as its primary.
//  Elasticsearch prevents this normally, but if node-3 held the only remaining copy...)

// This should NOT happen with proper configuration.
// If it does happen: the data on shard 2 is LOST.

// ── Step 3a: If node-3 can be restarted ───────────────────────────────────────
```

**Q14. "Design the complete sharding and replication strategy for a multi-tenant SaaS platform with 200 tenants, 50M documents/day ingestion, and sub-100ms p99 search latency."**

A: The design requires balancing write throughput (shard count × nodes), search speed (replica count × coordinating nodes), and operational simplicity (ILM, rollover, tier allocation):

```
Cluster sizing:

  Write throughput:
    50M docs/day = 578 docs/sec sustained
    Peak: 3× = 1734 docs/sec (assume bursty traffic)
    Per data node capacity: ~5000 simple docs/sec (with 1 replica)
    Data nodes needed for writes: 1734 / 5000 × (1 + 1 replica overhead) ≈ 2 nodes
    Add headroom: 6 hot data nodes (NVMe, 32 GB heap each)

  Storage per day:
    50M × 500 bytes avg = 25 GB raw
    With Lucene overhead (~2x): 50 GB/day
    Hot tier (7 days): 350 GB
    Warm tier (30 days): 1.5 TB
    Cold tier (90 days): 4.5 TB
    Total: ~6.4 TB active data (excluding frozen)

  Search SLA: p99 < 100ms
    Query fan-out to 5 shards with 1 replica = 5 shard-level searches
    Each shard search target: < 20ms (leaves 80ms for network + merge)
    6 hot nodes × 2 shard copies per node = 12 concurrent search capacity
    Add 3 coordinating nodes (16 GB heap, high CPU for result merging)
```

### Shard Configuration Summary

| Decision | Immutable? | Formula / Rule | When to revisit |
|---|---|---|---|
| Primary shard count | Yes (after creation) | target_size / 30 GB per shard | Reindex or split when data exceeds capacity |
| Replica count | No (change anytime) | ≥1 for HA; add for read throughput | Increase under read load; decrease during bulk ingest |
| Shard size | N/A (emerges from data) | Target: 10–50 GB | Alert if any shard > 50 GB |
| Total shards per node | Limit: 1000 | (primaries + replicas) / node count | Alert if > 500 shards/node |
| Heap per shard | ~50 MB minimum | heap / 50 MB = max shards | Monitor JVM heap % |

### Cluster Health States

| State | Condition | Severity | Data risk |
|---|---|---|---|
| `green` | All primary AND replica shards active | ✓ Normal | None |
| `yellow` | All primaries active; some replicas unassigned | ⚠ Degraded | None (primaries intact) |
| `red` | One or more PRIMARY shards unassigned | 🔴 Critical | Yes — documents on missing shard inaccessible |

### Write Path Durability Settings

| Setting | Value | Behaviour | Use when |
|---|---|---|---|
| `wait_for_active_shards` | `1` (default) | Wait for primary only | Max write throughput |
| `wait_for_active_shards` | `2` | Wait for primary + 1 replica | Balance durability/speed |
| `wait_for_active_shards` | `all` | Wait for all copies | Max durability (slowest) |
| `translog.durability` | `async` | fsync every `sync_interval` | High throughput, small data-loss risk |
| `translog.durability` | `request` | fsync on every write | Zero data loss on node crash |
| `refresh_interval` | `1s` (default) | Docs searchable within 1s | Normal search use cases |
| `refresh_interval` | `30s` | 30s before searchable | Bulk ingest optimisation |
| `refresh_interval` | `-1` | No automatic refresh | Maximum bulk throughput |

### ILM Tier Comparison

| Tier | Node type | Typical hardware | Replicas | Write? | Query speed |
|---|---|---|---|---|---|
| Hot | `data_hot` | NVMe SSD, high CPU | 1 | ✓ Active write | Fast (<10ms) |
| Warm | `data_warm` | SSD or fast HDD | 1 | ✗ Read-only | Medium (20–50ms) |
| Cold | `data_cold` | Cheap HDD | 0 | ✗ Read-only | Slow (50–200ms) |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise that **a shard IS a Lucene index** — with its own inverted index, doc values, stored fields, and segment files — and that each shard carries approximately 50 MB of JVM heap overhead independent of data, which is why over-sharding (too many tiny shards) degrades performance even on small indices; (2) knowing that **primary shard count is immutable at creation** and the only mechanisms to change it are: split (multiply by a factor, requires `number_of_routing_shards` to be set at creation), shrink (divide by a factor, requires all primaries on one node), or full reindex (arbitrary count, slowest, most flexible); (3) understanding the **two-phase search execution** — Phase 1 (query) fans out to all shards, each returning only doc_ids and scores for the top K results; Phase 2 (fetch) retrieves full document content only for the final top K winners — and knowing that `from+size` deep pagination causes Phase 1 to return `from+size` results from every shard (`search_after` with PIT is the correct alternative); (4) knowing the **primary-based replication write model** exactly: the primary validates, writes, forwards to all in-sync replicas in parallel, waits for acknowledgement from all in-sync replicas, then responds to the client — and that `wait_for_active_shards` controls how many copies must acknowledge before the response is sent; (5) understanding **sequence numbers and primary terms** — primary term increments on every new primary election (prevents zombie primaries from writing stale data), and sequence numbers provide per-shard monotonically increasing operation identifiers that enable efficient resync (only operations after the local checkpoint need to be replayed, not a full shard copy); (6) knowing that **replica shards serve reads by default** and Elasticsearch uses adaptive replica selection to route reads to the fastest available copy, so adding replicas increases read throughput proportionally but also increases the write amplification (each write must be forwarded to all in-sync replicas); (7) understanding **ILM's hot-warm-cold-frozen architecture** — hot (NVMe, active writes, 1 replica), warm (read-only after rollover, force-merged to 1 segment, shrunk), cold (no replicas, cheap storage), frozen (searchable snapshots on S3, near-zero local disk cost) — and the role of `forcemerge` in reducing segment count for read-only warm indices; and (8) knowing that **custom routing** (`?routing=tenantId`) can eliminate fan-out entirely for multi-tenant queries, sending them to exactly one shard, but requires enforcing the routing key at both index and query time (`_routing: { required: true }` in the mapping), and that using the same routing key for all tenants defeats sharding by concentrating all data on one shard.
