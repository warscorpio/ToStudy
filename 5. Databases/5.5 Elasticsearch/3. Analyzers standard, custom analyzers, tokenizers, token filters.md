## Section 1: Fundamentals

**Q1. What is an analyzer in Elasticsearch, and why does the analysis pipeline exist?**
A: An analyzer is a pipeline that transforms raw text into a sequence of tokens (terms) that are stored in the inverted index and used for full-text search. Without analysis, searching for "Running shoes" would not match documents containing "run" or "SHOES" — analysis normalises text into searchable units. Every piece of full-text data in Elasticsearch passes through an analyzer twice: once at index time (converting the document field value into tokens) and once at query time (converting the search query into tokens to look up in the index):

```
The analysis pipeline — three components in sequence:

  Input text: "The Quick Brown Fox's Jumps! Over the lazy dogs."
       │
       ▼
  ┌─────────────────────────────────────────────┐
  │ 1. CHARACTER FILTERS (0 or more)            │
  │    Pre-process the raw text string          │
  │    Before tokenization                      │
  │    Examples: strip HTML, replace &→and      │
  │    Output: modified character stream        │
  │    "The Quick Brown Fox's Jumps! Over..."   │
  └──────────────────┬──────────────────────────┘
                     │
                     ▼
  ┌─────────────────────────────────────────────┐
  │ 2. TOKENIZER (exactly 1, required)          │
  │    Split character stream into tokens       │
  │    Defines the unit of search               │
  │    Output: ["The","Quick","Brown","Fox's",  │
  │             "Jumps","Over","the","lazy",    │
  │             "dogs"]                         │
  └──────────────────┬──────────────────────────┘
                     │
                     ▼
  ┌─────────────────────────────────────────────┐
  │ 3. TOKEN FILTERS (0 or more)                │
  │    Transform individual tokens              │
  │    Add, remove, or modify tokens            │
  │    lowercase: ["the","quick","brown","fox's"│
  │                "jumps","over","the","lazy", │
  │                "dogs"]                      │
  │    stop words: ["quick","brown","fox's",    │
  │                 "jumps","lazy","dogs"]      │
  │    stemmer:    ["quick","brown","fox",      │
  │                 "jump","lazi","dog"]        │
  └──────────────────┬──────────────────────────┘
                     │
                     ▼
  Inverted index tokens: quick, brown, fox, jump, lazi, dog
```

```
Why analysis matters — query matching:

  Without analysis:
    Document field:     "Running Shoes for Athletes"
    Index tokens:       "Running Shoes for Athletes"  ← one token or exact string
    Query: "running"    → NO MATCH (case mismatch, not an exact string)
    Query: "shoes"      → NO MATCH
    Query: "RUNNING SHOES" → NO MATCH

  With standard analysis (lowercase + stop words + word splitting):
    Document field:     "Running Shoes for Athletes"
    Index tokens:       ["running", "shoes", "athletes"]
    Query: "running"    → MATCH ("running" → "running")
    Query: "SHOES"      → MATCH ("SHOES" → "shoes" → match "shoes")
    Query: "shoe"       → NO MATCH (stemming not in standard analyzer)

  With English analyzer (lowercase + stop words + English stemmer):
    Index tokens:       ["run", "shoe", "athlet"]
    Query: "runs"       → MATCH ("runs" → "run" → match "run")
    Query: "running"    → MATCH ("running" → "run" → match "run")
    Query: "athlete"    → MATCH ("athlete" → "athlet" → match "athlet")
    Query: "athletic"   → MATCH ("athletic" → "athlet" → match "athlet")
```

**Q2. What is the inverted index and how does analysis feed into it?**
A: The inverted index is the core data structure that makes full-text search efficient. Instead of scanning every document for a search term, Elasticsearch maintains a mapping from each unique token to the list of documents containing that token. Analysis determines what goes into this index:

```
Inverted index construction from three documents:

  Doc 1: "Elasticsearch is a search engine"
  Doc 2: "Search engines use inverted indexes"
  Doc 3: "The search is fast"

  After standard analysis (lowercase, tokenize, remove stop words "is", "a", "the"):
  Doc 1 tokens: [elasticsearch, search, engine]
  Doc 2 tokens: [search, engines, use, inverted, indexes]
  Doc 3 tokens: [search, fast]

  Inverted index:
  ┌──────────────┬─────────────────────────────────────────┐
  │ Token        │ Document list (postings)                 │
  ├──────────────┼─────────────────────────────────────────┤
  │ elasticsearch│ [Doc1(pos:0)]                            │
  │ search       │ [Doc1(pos:1), Doc2(pos:0), Doc3(pos:1)] │
  │ engine       │ [Doc1(pos:2)]                            │
  │ engines      │ [Doc2(pos:1)]                            │← not matched by "engine"!
  │ use          │ [Doc2(pos:2)]                            │
  │ inverted     │ [Doc2(pos:3)]                            │
  │ indexes      │ [Doc2(pos:4)]                            │
  │ fast         │ [Doc3(pos:2)]                            │
  └──────────────┴─────────────────────────────────────────┘

  Query: "search"
    Lookup "search" → [Doc1, Doc2, Doc3] ← instant, no scanning

  Query: "search engine"   (match_query)
    Lookup "search" → [Doc1, Doc2, Doc3]
    Lookup "engine" → [Doc1]
    Intersection of both terms → [Doc1]
    OR semantics → [Doc1, Doc2, Doc3] (ranked by how many terms match)

  Problem visible: "engine" and "engines" are different tokens
  ← stemming solves this (both → "engin")
  ← This is why analyzer choice is critical at INDEX DESIGN TIME
     (changing an analyzer requires reindexing)
```

## Section 2: Built-in Analyzers

**Q3. What are the built-in analyzers in Elasticsearch — when do you use each?**
A: Elasticsearch ships with several pre-built analyzers covering common use cases. Understanding their differences prevents the mistake of using the wrong analyzer for a use case:

```bash
# 1. STANDARD ANALYZER (default for text fields)
POST /_analyze
{
    "analyzer": "standard",
    "text": "The 2 QUICK Brown-Foxes jumped over the lazy dog's bone."
}
# Tokens: [the, 2, quick, brown, foxes, jumped, over, the, lazy, dog's, bone]
# Components: Unicode Text Segmentation tokenizer + lowercase filter + stop words (disabled by default)
# - Splits on whitespace AND punctuation
# - Lowercases all tokens
# - Does NOT stem: "foxes" ≠ "fox", "jumped" ≠ "jump"
# - Preserves numbers: "2" is a token
# - Handles apostrophes: "dog's" becomes "dog's" (not split)
# Use: General English text, product names, descriptions when exact-ish matching is wanted

# 2. ENGLISH ANALYZER
POST /_analyze
{
    "analyzer": "english",
    "text": "The 2 QUICK Brown-Foxes jumped over the lazy dog's bone."
}
# Tokens: [2, quick, brown, fox, jump, lazi, dog, bone]
# Components: standard tokenizer + lowercase + stop words (English) + possessive stemmer + Porter stemmer
# - Removes stop words: "the", "over" removed
# - Stems: "foxes"→"fox", "jumped"→"jump", "lazy"→"lazi", "dog's"→"dog"
# - Aggressive stemming: "lazi" is not a word but matches "lazy", "lazier", "laziest"
# Use: English language search where linguistic stemming improves recall

# 3. SIMPLE ANALYZER
POST /_analyze
{
    "analyzer": "simple",
    "text": "The 2 QUICK Brown-Foxes jumped."
}
# Tokens: [the, quick, brown, foxes, jumped]
# Components: lowercase tokenizer (splits on non-letter characters, lowercases)
# - Splits on ALL non-letter characters (numbers too!)
# - "2" is DISCARDED (not a letter)
# - Hyphen in "Brown-Foxes" splits into two tokens: "brown", "foxes"
# Use: When you want letter-only tokens and numbers are meaningless

# 4. WHITESPACE ANALYZER
POST /_analyze
{
    "analyzer": "whitespace",
    "text": "The 2 QUICK Brown-Foxes jumped."
}
# Tokens: [The, 2, QUICK, Brown-Foxes, jumped.]
# - Splits ONLY on whitespace
# - Does NOT lowercase
# - Keeps punctuation attached: "jumped." has the period
# Use: log tokens, codes where case and punctuation matter

# 5. STOP ANALYZER
POST /_analyze
{
    "analyzer": "stop",
    "text": "The 2 QUICK Brown-Foxes jumped over the lazy dog."
}
# Tokens: [quick, brown, foxes, jumped, lazy, dog]
# Components: lowercase tokenizer + stop word filter
# - Like simple but also removes stop words
# Use: Rarely — usually English or custom analyzer is better

# 6. KEYWORD ANALYZER
POST /_analyze
{
    "analyzer": "keyword",
    "text": "The 2 QUICK Brown-Foxes jumped."
}
# Tokens: ["The 2 QUICK Brown-Foxes jumped."]
# - Treats the ENTIRE input as a SINGLE token
# - No transformation whatsoever
# Use: Exact-match fields (email, product codes, tags, status fields)
#      For fields that should be sorted or aggregated
#      (But for these: use keyword field type, not analyzer explicitly)

# 7. FINGERPRINT ANALYZER
POST /_analyze
{
    "analyzer": "fingerprint",
    "text": "John, JAMES, John Smith, JAMES"
}
# Tokens: ["james john smith"]
# - Lowercases, removes stop words, sorts tokens, deduplicates, joins with space
# - Produces a canonical "fingerprint" of the text
# Use: Duplicate detection, clustering similar records
```

```bash
# Language analyzers — beyond English:
# Available: arabic, armenian, basque, bengali, brazilian, bulgarian,
#            catalan, cjk, czech, danish, dutch, english, estonian,
#            finnish, french, galician, german, greek, hindi, hungarian,
#            indonesian, irish, italian, latvian, lithuanian, norwegian,
#            persian, portuguese, romanian, russian, sorani, spanish,
#            swedish, turkish, thai

POST /_analyze
{
    "analyzer": "german",
    "text": "Ich bin ein Berliner"
}
# Tokens: [ich, berliner]
# German-specific: removes "bin", "ein" as stop words
# German stemmer handles compound words and declensions

POST /_analyze
{
    "analyzer": "cjk",
    "text": "東京は大きな都市です"
}
# CJK (Chinese/Japanese/Korean): bigram tokenizer
# Tokens: [東京, 京は, は大, 大き, きな, な都, 都市, 市で, です]
# Creates overlapping 2-character tokens (bigrams)
```

## Section 3: Tokenizers

**Q4. What are the key tokenizers and when does each apply?**
A: The tokenizer is the heart of the analysis pipeline — it defines how text is split into tokens. Choosing the wrong tokenizer is the most fundamental analysis mistake because it determines what can and cannot be matched:

```bash
# 1. STANDARD TOKENIZER (default)
# Unicode Text Segmentation algorithm — splits on whitespace and punctuation
POST /_analyze
{
    "tokenizer": "standard",
    "text": "John's quick.brown@foxes.com test_code 192.168.1.1"
}
# Tokens: [John's, quick.brown, foxes.com, test_code, 192.168.1.1]
# - Keeps "John's" together (apostrophe in middle)
# - Keeps email-like "quick.brown@foxes.com" somewhat together
# - Keeps "192.168.1.1" together (IP address)
# Use: General text, documents, most English content

# 2. WHITESPACE TOKENIZER
POST /_analyze
{
    "tokenizer": "whitespace",
    "text": "foo bar  baz  (hello) world"
}
# Tokens: [foo, bar, baz, (hello), world]
# - Splits ONLY on whitespace characters
# - Preserves all punctuation attached to words
# Use: When tokens are space-separated and punctuation is meaningful

# 3. KEYWORD TOKENIZER
POST /_analyze
{
    "tokenizer": "keyword",
    "text": "New York City"
}
# Tokens: ["New York City"]   ← one single token, the whole input
# Use: Fields where the entire value is a single token (but usually just use keyword field type)

# 4. LETTER TOKENIZER
POST /_analyze
{
    "tokenizer": "letter",
    "text": "test-code_123 hello world"
}
# Tokens: [test, code, hello, world]
# - Splits on any non-letter character (removes numbers too)
# Use: Very rarely — simple analyzer covers this with lowercasing

# 5. LOWERCASE TOKENIZER
POST /_analyze
{
    "tokenizer": "lowercase",
    "text": "The Quick BROWN FOX"
}
# Tokens: [the, quick, brown, fox]
# - Like letter tokenizer but also lowercases
# Use: Slightly more efficient than letter + lowercase filter

# 6. UAX URL EMAIL TOKENIZER
POST /_analyze
{
    "tokenizer": "uax_url_email",
    "text": "Email me at user@example.com or visit https://example.com/path"
}
# Tokens: [Email, me, at, user@example.com, or, visit, https://example.com/path]
# - Like standard but PRESERVES URLs and email addresses as single tokens
# Use: Documents containing URLs or email addresses that should be searchable as-is

# 7. PATTERN TOKENIZER
# Use a regex to define the DELIMITER (what to split on):
PUT /test_index
{
    "settings": {
        "analysis": {
            "tokenizer": {
                "comma_tokenizer": {
                    "type": "pattern",
                    "pattern": ","          // Split on comma
                }
            }
        }
    }
}
POST /test_index/_analyze
{
    "tokenizer": "comma_tokenizer",
    "text": "red,blue,green,yellow"
}
# Tokens: [red, blue, green, yellow]
# Use: CSV data, pipe-delimited values, structured text with clear delimiters

# 8. EDGE NGRAM TOKENIZER
# Creates tokens from the beginning of words — essential for autocomplete:
PUT /autocomplete_index
{
    "settings": {
        "analysis": {
            "tokenizer": {
                "edge_ngram_tokenizer": {
                    "type": "edge_ngram",
                    "min_gram": 2,
                    "max_gram": 15,
                    "token_chars": ["letter", "digit"]
                }
            }
        }
    }
}
POST /autocomplete_index/_analyze
{
    "tokenizer": "edge_ngram_tokenizer",
    "text": "elasticsearch"
}
# Tokens: [el, ela, elas, elast, elasti, elastic, elastics, elasticsearch]
# → Typing "ela" matches "elasticsearch" because "ela" is an edge ngram of it
# Use: Search-as-you-type, autocomplete, prefix matching

# 9. NGRAM TOKENIZER
# Creates ALL ngrams (not just from edge):
POST /_analyze
{
    "tokenizer": {
        "type": "ngram",
        "min_gram": 3,
        "max_gram": 4
    },
    "text": "hello"
}
# Tokens: [hel, hell, ell, ello, llo]
# ← 3-grams and 4-grams of every position
# Use: Fuzzy substring matching, languages without word boundaries (CJK)

# 10. PATH HIERARCHY TOKENIZER
POST /_analyze
{
    "tokenizer": "path_hierarchy",
    "text": "/usr/local/bin/elasticsearch"
}
# Tokens: [/usr, /usr/local, /usr/local/bin, /usr/local/bin/elasticsearch]
# Use: File paths, category hierarchies, URL structures
# Enables: "show me everything under /usr/local"
```

## Section 4: Token Filters

**Q5. What are the most important token filters and what transformation does each apply?**
A: Token filters receive the stream of tokens from the tokenizer and can add, remove, or modify tokens. They are applied in order, so the sequence matters — lowercasing before stemming is correct; stemming before lowercasing produces different results:

```bash
# 1. LOWERCASE FILTER (most commonly used)
POST /_analyze
{
    "tokenizer": "standard",
    "filter": ["lowercase"],
    "text": "The QUICK Brown FOX"
}
# Input tokens:  [The, QUICK, Brown, FOX]
# Output tokens: [the, quick, brown, fox]
# Always apply: without lowercase, "Fox" and "fox" don't match

# 2. STOP FILTER (remove common words)
POST /_analyze
{
    "tokenizer": "standard",
    "filter": ["lowercase", "stop"],
    "text": "the quick brown fox is a very fast animal"
}
# Input:  [the, quick, brown, fox, is, a, very, fast, animal]
# Output: [quick, brown, fox, very, fast, animal]
# "the", "is", "a" removed as English stop words
# Default stop list: english stop words
# Custom stop list: specify your own

# 3. STEMMER FILTER
POST /_analyze
{
    "tokenizer": "standard",
    "filter": [
        "lowercase",
        { "type": "stemmer", "language": "english" }
    ],
    "text": "running runners ran quickly eating eats"
}
# Output: [run, runner, ran, quickli, eat, eat]
# Porter stemmer: algorithmic reduction to root form
# "running"→"run", "quickly"→"quickli", "eating"→"eat", "eats"→"eat"
# Note: "ran" does NOT stem to "run" (irregular verb — use snowball or keyword_marker)

# 4. SYNONYM FILTER
# Define synonyms so "car" matches "automobile" and "vehicle":
PUT /products_index
{
    "settings": {
        "analysis": {
            "filter": {
                "synonym_filter": {
                    "type": "synonym",
                    "synonyms": [
                        "car, automobile, vehicle",     // All three are equivalent
                        "US, United States, America",   // Equivalent terms
                        "elasticsearch => es, elastic"  // One-way: es expands to elastic
                    ]
                }
            }
        }
    }
}
# Synonym expansion at index time vs query time — a critical decision:
# Index time: "car" indexed as ["car", "automobile", "vehicle"]
#   → Query for any term finds the document
#   → Pros: simpler query-time logic
#   → Cons: larger index, cannot change synonyms without reindexing
# Query time: "car" in query expands to ["car", "automobile", "vehicle"]
#   → Pros: change synonyms without reindexing (update settings only)
#   → Cons: must use search_analyzer different from index_analyzer

# 5. ASCII FOLDING FILTER
POST /_analyze
{
    "tokenizer": "standard",
    "filter": ["lowercase", "asciifolding"],
    "text": "café résumé naïve Ångström"
}
# Output: [cafe, resume, naive, angstrom]
# Converts accented characters to their ASCII equivalents
# Use: European language content where users search without accents

# 6. KEYWORD MARKER FILTER
# Prevent specific words from being stemmed:
PUT /test_index
{
    "settings": {
        "analysis": {
            "filter": {
                "protected_words": {
                    "type": "keyword_marker",
                    "keywords": ["elasticsearch", "kibana", "logstash"]
                }
            }
        }
    }
}
# Apply BEFORE the stemmer: marks these words so stemmer skips them
# "elasticsearch" would otherwise stem to "elasticsearch" (fine) or worse

# 7. EDGE NGRAM FILTER (vs edge ngram tokenizer)
# Apply edge ngrams AFTER tokenization (to individual tokens):
POST /_analyze
{
    "tokenizer": "standard",
    "filter": [
        "lowercase",
        {
            "type": "edge_ngram",
            "min_gram": 2,
            "max_gram": 10
        }
    ],
    "text": "quick brown"
}
# Input tokens:  [quick, brown]
# Output tokens: [qu, qui, quic, quick, br, bro, brow, brown]
# Unlike edge_ngram TOKENIZER (which generates from the beginning of the whole text),
# edge_ngram FILTER generates from the start of EACH token
# Use: Autocomplete on individual words (vs whole phrases)

# 8. SHINGLE FILTER (word ngrams)
POST /_analyze
{
    "tokenizer": "standard",
    "filter": [
        "lowercase",
        {
            "type": "shingle",
            "min_shingle_size": 2,
            "max_shingle_size": 3
        }
    ],
    "text": "new york city"
}
# Output: [new, new york, new york city, york, york city, city]
# Creates multi-word tokens alongside single words
# Use: Phrase detection, "New York" should match as a unit

# 9. UNIQUE FILTER
POST /_analyze
{
    "tokenizer": "standard",
    "filter": ["lowercase", "unique"],
    "text": "the cat sat on the mat and the cat"
}
# Input:  [the, cat, sat, on, the, mat, and, the, cat]
# Output: [the, cat, sat, on, mat, and]
# Removes duplicate tokens (keeps first occurrence)
# Use: Reduce index size, prevent inflated term frequency scores

# 10. TRUNCATE FILTER
POST /_analyze
{
    "tokenizer": "standard",
    "filter": [
        "lowercase",
        { "type": "truncate", "length": 8 }
    ],
    "text": "superlongword hello"
}
# Output: [superlongword → "superlongword" becomes "superlonw" ...wait
# Actually: tokens are truncated to max 8 chars
# "superlongword" → "superlon"
# "hello" → "hello" (already < 8)
# Use: Limit index size for very long tokens (URLs, codes)

# 11. WORD DELIMITER GRAPH FILTER (powerful, complex)
POST /_analyze
{
    "tokenizer": "keyword",
    "filter": ["word_delimiter_graph"],
    "text": "Wi-Fi SuperUser PowerShell1.0 test_code"
}
# Output: [Wi, Fi, Wi-Fi, Super, User, SuperUser, Power, Shell, 1.0, PowerShell, 1.0, test, code]
# Splits on: case changes (SuperUser→Super+User), hyphens, underscores
# Also generates: the concatenated form (SuperUser) alongside the parts
# Use: Product names, technical terms, code identifiers, camelCase
```

## Section 5: Character Filters

**Q6. What are character filters and when do you need them?**
A: Character filters pre-process the raw text string before it reaches the tokenizer. They are less commonly needed than token filters but essential for specific data types — HTML content, custom symbol handling, or pattern replacement:

```bash
# 1. HTML STRIP CHARACTER FILTER
POST /_analyze
{
    "char_filter": ["html_strip"],
    "tokenizer": "standard",
    "text": "<p>Hello <b>World</b>! <a href='#'>Click here</a></p>"
}
# After char filter: "Hello World!  Click here "
# After tokenizer:   [Hello, World, Click, here]
# HTML tags removed, text content preserved
# HTML entities decoded: &amp; → &, &lt; → <, &nbsp; → space

# 2. MAPPING CHARACTER FILTER
# Replace specific character sequences before tokenization:
PUT /custom_index
{
    "settings": {
        "analysis": {
            "char_filter": {
                "symbol_replacer": {
                    "type": "mapping",
                    "mappings": [
                        "& => and",
                        "@ => at",
                        "# => number ",
                        "٣ => 3"      // Arabic-Indic digit
                    ]
                }
            }
        }
    }
}
POST /custom_index/_analyze
{
    "char_filter": ["symbol_replacer"],
    "tokenizer": "standard",
    "text": "R&B music @ $5 #trending"
}
# After char filter: "R and B music at $5 number trending"
# After tokenizer:   [R, and, B, music, at, 5, number, trending]
# Use: Symbol normalization, special character handling, unicode normalization

# 3. PATTERN REPLACE CHARACTER FILTER
PUT /pattern_index
{
    "settings": {
        "analysis": {
            "char_filter": {
                "camel_case_splitter": {
                    "type": "pattern_replace",
                    "pattern": "(?<=[a-z])(?=[A-Z])",  // Between lower and upper
                    "replacement": " "
                },
                "remove_special": {
                    "type": "pattern_replace",
                    "pattern": "[^\\w\\s]",  // Not word char or space
                    "replacement": ""
                }
            }
        }
    }
}
POST /pattern_index/_analyze
{
    "char_filter": ["camel_case_splitter"],
    "tokenizer": "standard",
    "text": "getUserById createOrderItem"
}
# After char filter: "get User By Id create Order Item"
# After tokenizer:   [get, User, By, Id, create, Order, Item]
# Use: Code search, camelCase method names, technical identifiers
```

## Section 6: Custom Analyzers

**Q7. How do you define a custom analyzer in an index mapping, and what are the gotchas?**
A: Custom analyzers are defined in the index settings (not the mapping) and then referenced in the mapping. The settings contain the component definitions; the mapping contains where to apply them. This separation means components can be reused across multiple fields:

```bash
# Complete custom analyzer definition:
PUT /products
{
    "settings": {
        "analysis": {
            # Step 1: Define custom CHARACTER FILTERS:
            "char_filter": {
                "html_clean": {
                    "type": "html_strip"
                },
                "ampersand_replace": {
                    "type": "mapping",
                    "mappings": ["& => and"]
                }
            },

            # Step 2: Define custom TOKENIZERS:
            "tokenizer": {
                "product_tokenizer": {
                    "type": "standard",
                    "max_token_length": 50   # Ignore very long tokens
                }
            },

            # Step 3: Define custom TOKEN FILTERS:
            "filter": {
                "english_stop": {
                    "type": "stop",
                    "stopwords": "_english_"   # Built-in English stop list
                },
                "product_synonyms": {
                    "type": "synonym",
                    "synonyms_path": "analysis/synonyms.txt",  # External file
                    "updateable": true   # Can update without reindexing (query time only)
                },
                "edge_ngram_filter": {
                    "type": "edge_ngram",
                    "min_gram": 2,
                    "max_gram": 20
                },
                "english_stemmer": {
                    "type": "stemmer",
                    "language": "english"
                },
                "english_possessive": {
                    "type": "stemmer",
                    "language": "possessive_english"
                }
            },

            # Step 4: Assemble into ANALYZERS:
            "analyzer": {
                # Search analyzer — used at query time:
                "product_search_analyzer": {
                    "type": "custom",
                    "char_filter": ["html_clean", "ampersand_replace"],
                    "tokenizer": "product_tokenizer",
                    "filter": [
                        "english_possessive",   # "product's" → "product"
                        "lowercase",            # Must come early
                        "english_stop",         # Remove stop words
                        "english_stemmer"       # Stem words
                    ]
                },

                # Index analyzer for autocomplete — generates edge ngrams:
                "autocomplete_index_analyzer": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": [
                        "lowercase",
                        "edge_ngram_filter"  # "elas" matches "elasticsearch"
                    ]
                },

                # Search analyzer for autocomplete — does NOT generate edge ngrams:
                "autocomplete_search_analyzer": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": ["lowercase"]
                    # Do NOT apply edge_ngram at query time
                    # Query "elas" should match exactly "elas" in the index
                    # The index has "el", "ela", "elas"... so "elas" hits
                }
            }
        }
    },

    # Step 5: Reference analyzers in mappings:
    "mappings": {
        "properties": {
            "name": {
                "type": "text",
                "analyzer": "product_search_analyzer",
                # search_analyzer defaults to analyzer if not specified
                # Use same for both unless autocomplete or synonyms:
                "fields": {
                    "autocomplete": {
                        "type": "text",
                        "analyzer": "autocomplete_index_analyzer",
                        "search_analyzer": "autocomplete_search_analyzer"
                        # CRITICAL: different analyzers for index vs search
                        # Index: generates edge ngrams from "elasticsearch"
                        # Search: tokenizes "elas" normally
                        # Match: "elas" (search token) hits "elas" (index token)
                    },
                    "keyword": {
                        "type": "keyword"  # For exact match, sorting, aggs
                    }
                }
            },
            "description": {
                "type": "text",
                "analyzer": "product_search_analyzer"
            },
            "sku": {
                "type": "keyword"  # Exact match only — no analysis
            }
        }
    }
}
```

```bash
# Critical gotcha: index analyzer vs search analyzer mismatch for autocomplete

# WRONG: same analyzer for both (edge ngrams at query time):
# Index "elasticsearch" → tokens: [el, ela, elas, elast, ..., elasticsearch]
# Query "elastic" → tokens: [el, ela, elas, elast, elasti, elastic]
# Match: "el" (query) hits "el" (index) AND "ela" hits "ela", etc.
# Problem: "a" would match EVERYTHING because "a" is an edge ngram of almost any word!
# Short queries produce massive result sets (all docs with any word starting with "a")

# CORRECT: edge ngram only at INDEX time, normal analysis at QUERY time:
# Index "elasticsearch" → tokens: [el, ela, elas, elast, ..., elasticsearch]
# Query "elastic" → tokens: [elastic]  ← just the whole word
# Match: "elastic" hits "elastic" in the index ngrams
# Query "elas" → tokens: [elas]
# Match: "elas" hits "elas" in the index ngrams
# MUCH more precise

# Verify the difference with the Analyze API:
POST /products/_analyze
{
    "analyzer": "autocomplete_index_analyzer",
    "text": "elasticsearch kibana"
}
# Shows: many short tokens from edge ngrams

POST /products/_analyze
{
    "analyzer": "autocomplete_search_analyzer",
    "text": "ela"
}
# Shows: ["ela"] ← just this one token, which matches in the ngram index
```

## Section 7: Advanced Patterns

**Q8. How do you implement multi-field analysis — using the same data for both full-text search and exact matching?**
A: A single field value often needs to be used in multiple ways: full-text search (analyzed), exact matching or aggregation (keyword), and autocomplete (edge ngrams). Elasticsearch's `fields` parameter supports all of these from one source field:

```bash
PUT /articles
{
    "settings": {
        "analysis": {
            "analyzer": {
                "autocomplete_idx": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": ["lowercase", {
                        "type": "edge_ngram",
                        "min_gram": 1,
                        "max_gram": 20
                    }]
                }
            }
        }
    },
    "mappings": {
        "properties": {
            "title": {
                # Primary field: full-text search with English analysis
                "type": "text",
                "analyzer": "english",   # Stems: "running" → "run"

                "fields": {
                    # Sub-field 1: exact match and aggregations
                    "keyword": {
                        "type": "keyword",
                        "ignore_above": 256   # Ignore values longer than 256 chars
                    },

                    # Sub-field 2: autocomplete (prefix search)
                    "autocomplete": {
                        "type": "text",
                        "analyzer": "autocomplete_idx",
                        "search_analyzer": "standard"  # Must NOT use edge ngram at search
                    },

                    # Sub-field 3: unstemmed for exact phrase match
                    "standard": {
                        "type": "text",
                        "analyzer": "standard"  # No stemming: "running" stays "running"
                    }
                }
            }
        }
    }
}

# Query routing: use the right sub-field for each query type:

# Full-text search (stemmed): uses title (primary field)
GET /articles/_search
{
    "query": {
        "match": {
            "title": "running shoes"
            # "running"→"run", finds docs with "run", "runner", "runs", "running"
        }
    }
}

# Autocomplete (prefix):
GET /articles/_search
{
    "query": {
        "match": {
            "title.autocomplete": "run sho"
            # "run" and "sho" match edge ngrams: ["r","ru","run"] and ["s","sh","sho"...]
        }
    }
}

# Exact match (for filters, aggregations):
GET /articles/_search
{
    "query": {
        "term": {
            "title.keyword": "Running Shoes for Athletes"
            # Exact string match — case sensitive
        }
    },
    "aggs": {
        "top_titles": {
            "terms": {
                "field": "title.keyword"  # Aggregation requires keyword type
            }
        }
    }
}

# Phrase match (unstemmed — "running shoes" as exact phrase):
GET /articles/_search
{
    "query": {
        "match_phrase": {
            "title.standard": "running shoes"
            # "running" and "shoes" as adjacent tokens, no stemming
        }
    }
}
```

```bash
# The multi-field pattern for a product catalogue:
# Requirements:
# 1. Full-text search: "wireless headphones" finds "wireless Bluetooth headphones"
# 2. Autocomplete: typing "wire" suggests "Wireless Headphones Sony"
# 3. Filter by exact category: category = "Electronics > Audio"
# 4. Sort by name alphabetically
# 5. Facet/aggregate by brand

PUT /products
{
    "mappings": {
        "properties": {
            "name": {
                "type": "text",
                "analyzer": "english",
                "fields": {
                    "keyword": { "type": "keyword" },          # Sort, exact filter
                    "autocomplete": {
                        "type": "text",
                        "analyzer": "autocomplete_idx",
                        "search_analyzer": "standard"
                    }
                }
            },
            "category": {
                "type": "keyword",                             # Always exact match
                "fields": {
                    "text": { "type": "text" }                # If users search in category names
                }
            },
            "brand": {
                "type": "keyword",                             # Aggregation + filter
                "fields": {
                    "text": { "type": "text", "analyzer": "english" }
                }
            },
            "description": {
                "type": "text",
                "analyzer": "english"
            },
            "price": { "type": "float" },
            "in_stock": { "type": "boolean" }
        }
    }
}
```

**Q9. How do you implement synonym search — and why should synonyms usually be applied at query time rather than index time?**
A: Synonyms expand a search term to include semantically equivalent alternatives. The placement of synonym expansion (index time vs query time) has significant operational implications for index maintainability:

```bash
# Index-time synonyms — expanded when document is indexed:
PUT /products_idx_synonyms
{
    "settings": {
        "analysis": {
            "filter": {
                "idx_synonyms": {
                    "type": "synonym",
                    "synonyms": [
                        "laptop, notebook, portable computer",
                        "tv, television, telly",
                        "phone, mobile, smartphone, cell"
                    ]
                }
            },
            "analyzer": {
                "with_synonyms": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": ["lowercase", "idx_synonyms"]
                }
            }
        }
    },
    "mappings": {
        "properties": {
            "name": {
                "type": "text",
                "analyzer": "with_synonyms"
            }
        }
    }
}

# What index-time synonyms do:
# Document "MacBook Laptop 2024":
# Tokens: [macbook, laptop, notebook, portable, computer, 2024]
# "laptop" expands to all synonyms AND keeps "laptop"
# Larger index: each synonym expands the posting list

# Problem: to add a new synonym:
# Must reindex ALL documents (can take hours/days for large indices)
# Cannot update synonyms without downtime or complex alias swap

# Query-time synonyms — expanded when query is processed:
PUT /products_qtime_synonyms
{
    "settings": {
        "analysis": {
            "filter": {
                "search_synonyms": {
                    "type": "synonym_graph",      # Use synonym_graph for query time
                    "synonyms": [
                        "laptop, notebook, portable computer",
                        "tv, television"
                    ],
                    "updateable": true             # Can update via reload API
                }
            },
            "analyzer": {
                "index_analyzer": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": ["lowercase"]        # NO synonyms at index time
                },
                "search_analyzer": {
                    "type": "custom",
                    "tokenizer": "standard",
                    "filter": ["lowercase", "search_synonyms"]  # Synonyms only at search
                }
            }
        }
    },
    "mappings": {
        "properties": {
            "name": {
                "type": "text",
                "analyzer": "index_analyzer",
                "search_analyzer": "search_analyzer"  # Different analyzer for queries
            }
        }
    }
}

# Query-time synonym expansion:
# User searches "laptop"
# search_analyzer expands to: [laptop, notebook, portable, computer]
# Multi-term query searches for ALL expanded terms
# Finds documents with "laptop" OR "notebook" OR "portable computer"

# Update synonyms WITHOUT reindexing (updateable: true):
POST /products_qtime_synonyms/_reload_search_analyzers
# Reloads all updateable token filters from their file/inline definition
# Takes effect immediately — no reindexing needed
# (Update the synonyms file first, then reload)

# synonym vs synonym_graph:
# synonym: processes tokens sequentially (works for single-token synonyms)
# synonym_graph: handles multi-word synonyms correctly ("portable computer" as 2 tokens)
# ALWAYS use synonym_graph for query-time; synonym for index-time
```

## Section 9: Operations and Debugging

**Q13. How do you change an analyzer on an existing index — what is the reindexing process?**
A: Once an index has documents, you cannot change the analyzer for existing fields — the indexed tokens are already in the inverted index with the old analysis. The process requires creating a new index with the updated settings and reindexing all documents:

```bash
# The safe zero-downtime analyzer change process:

# Step 1: Create new index with updated settings:
PUT /products_v2
{
    "settings": {
        "analysis": { /* new analyzer configuration */ }
    },
    "mappings": {
        "properties": {
            "name": {
                "type": "text",
                "analyzer": "new_analyzer"  # Changed from old analyzer
            }
        }
    }
}

# Step 2: Reindex from old to new:
POST /_reindex
{
    "source": {
        "index": "products_v1",
        "size": 1000               # Batch size
    },
    "dest": {
        "index": "products_v2",
        "op_type": "create"        # Skip existing docs (for incremental reindex)
    }
}
# For large indices: can take hours. Run as async task:
POST /_reindex?wait_for_completion=false
{
    "source": { "index": "products_v1" },
    "dest": { "index": "products_v2" }
}
# Returns: { "task": "oTUltX4IQMOUUVeiohTt8A:12345" }

# Monitor progress:
GET /_tasks/oTUltX4IQMOUUVeiohTt8A:12345

# Step 3: Verify document count matches:
GET /products_v1/_count   # Should match:
GET /products_v2/_count

# Step 4: Verify analysis quality on sample queries:
GET /products_v2/_search
{
    "query": { "match": { "name": "wireless headphones" } },
    "size": 5
}
# Compare results to products_v1 — new analyzer should give better results

# Step 5: Switch alias from old to new index atomically:
POST /_aliases
{
    "actions": [
        { "remove": { "index": "products_v1", "alias": "products" } },
        { "add":    { "index": "products_v2", "alias": "products" } }
    ]
}
# Atomic: reads switch from v1 to v2 with no downtime
# Application uses "products" alias — unaffected by underlying index change

# Step 6: Keep v1 for rollback:
# If v2 has problems: swap alias back to v1
POST /_aliases
{
    "actions": [
        { "remove": { "index": "products_v2", "alias": "products" } },
        { "add":    { "index": "products_v1", "alias": "products" } }
    ]
}
# After confidence in v2: DELETE /products_v1

# What you CAN change without reindexing:
# - search_analyzer (only affects query time, not stored index)
# - Adding a new field (new field gets analyzed correctly)
# - Updating updateable synonym filters (then reload_search_analyzers)
# - Changing the analyzer for new fields not yet indexed

# What requires reindexing:
```

## Quick Reference Table

| Component | What it does | Applied before tokenizer? | Key examples |
|---|---|---|---|
| Character filter | Pre-processes raw text string | Yes — before tokenization | `html_strip`, `mapping` (& → and), `pattern_replace` |
| Tokenizer | Splits text into token stream (required, exactly one) | N/A — is the split step | `standard`, `whitespace`, `keyword`, `edge_ngram`, `pattern`, `uax_url_email` |
| Token filter | Transforms individual tokens (0 or more, in order) | No — after tokenization | `lowercase`, `stop`, `stemmer`, `synonym_graph`, `asciifolding`, `edge_ngram` |
| `standard` analyzer | Splits on whitespace/punctuation, lowercases | – | Default for `text` fields; no stemming |
| `english` analyzer | Splits + lowercase + stop words + Porter stemmer | – | Good for English text; "running" → "run" |
| `keyword` analyzer | No transformation — whole input = one token | – | Use `keyword` field type instead for most cases |
| `edge_ngram` tokenizer | Generates prefix tokens from each word | – | Use for autocomplete; index-time only (NOT at search time) |
| `synonym_graph` filter | Expands tokens to include synonyms | – | Use at query time with `updateable: true` to avoid reindexing |
| `asciifolding` filter | Converts accented chars to ASCII | – | "café" → "cafe"; add `preserve_original: true` to keep both |
| `stemmer` filter | Reduces words to root form (algorithmic) | – | `language: english` for Porter; "running" → "run", "dogs" → "dog" |
| `stop` filter | Removes common words (the, is, a, an) | – | Use `_english_` for built-in English stop list |
| `word_delimiter_graph` | Splits on case change, hyphens, underscores | – | "SuperUser" → ["Super", "User", "SuperUser"]; for technical terms |
| `fields` in mapping | Multiple analyzers for one source field | – | `name` (text/english), `name.keyword` (keyword), `name.autocomplete` (edge ngram) |
| Analyze API | Test any analyzer/tokenizer/filter combination | – | Always use before committing to an analyzer; debug mismatches |
| Reindexing | Required to change index-time analyzer | – | Create new index → `_reindex` → swap alias → delete old index |
| `search_analyzer` | Override analyzer used at query time | – | Required for autocomplete (no edge ngram at query time) and synonym_graph |

**Tip for interviews:** Five things separate strong candidates on Elasticsearch analyzers: (1) explaining the **three-component pipeline precisely** — character filter (pre-processes raw text), tokenizer (splits into tokens, exactly one required), and token filter (transforms tokens, zero or more applied in sequence order) — and knowing that the order of token filters matters: lowercase before stemmer is required because stemmers typically expect lowercase input, and asciifolding before stemming handles accented characters; (2) articulating the **autocomplete edge ngram trap** — that edge ngram must be applied at INDEX time only (as the `analyzer` setting), not at QUERY time (the `search_analyzer` must use standard tokenization), because applying edge ngrams at query time means a user typing "a" generates edge ngrams including the single character "a" which matches almost every document (catastrophically broad results), while at query time you want to lookup the exact typed prefix against the precomputed edge ngram tokens in the index; (3) knowing **the synonym placement decision** — that index-time synonyms expand the inverted index (larger storage, faster queries, requires reindexing to update) while query-time synonyms with `synonym_graph` and `updateable: true` can be reloaded via `_reload_search_analyzers` without reindexing (the operational winner for most production systems), and that `synonym_graph` must be used at query time for multi-word synonyms because `synonym` (non-graph) doesn't correctly handle multi-token expansions in a query context; (4) understanding **why reindexing is required for index-time analyzer changes** — that the inverted index already stores tokens from the old analyzer and there is no way to re-analyze existing stored documents in-place, requiring the create-new-index → `_reindex` → atomic alias swap pattern, and knowing what does NOT require reindexing (changes to `search_analyzer`, adding new fields, updating `updateable` synonym filters with `_reload_search_analyzers`); and (5) being able to design the **multi-field pattern** — `"name"` field with `analyzer: english` for full-text search, `"name.keyword"` with `type: keyword` for sorting/aggregations/exact filters, and `"name.autocomplete"` with edge ngram index analyzer and standard search analyzer for prefix search — and explaining that all three derive from the same source value without data duplication in the document.
