# PostgreSQL Slow Query Log Analysis — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the slow query log and why is it the starting point for database performance work?**

A: The slow query log is a mechanism that records SQL statements exceeding a configurable execution time threshold into a log file (or the system log). It is the starting point for performance work because it identifies exactly which queries are consuming disproportionate time — without guessing, without reading application code, and without instrumenting anything:

```
Performance investigation hierarchy:

1. Slow query log       ← identifies WHICH queries are slow
2. EXPLAIN ANALYZE      ← reveals WHY a specific query is slow
3. pg_stat_statements   ← aggregates across many executions (total impact)
4. Index analysis       ← determines whether an index would help
5. Schema / query rewrite ← fixes the root cause
```

Without the slow query log, you're guessing. With it, you have a ranked list of exactly which queries to look at first.

PostgreSQL has two complementary mechanisms:

```
auto_explain + log_min_duration_statement:
  → Logs individual slow queries with their query text and (optionally) their plan
  → Good for: finding the first occurrence of a slow query, debugging episodic slowness

pg_stat_statements:
  → Aggregates statistics across ALL executions of every query pattern
  → Good for: finding queries that are fast individually but collectively expensive
  → Example: a query taking 5ms each, called 1 million times/day = 83 minutes of DB CPU
    → would NOT appear in the slow query log (below threshold)
    → WOULD appear at the top of pg_stat_statements by total_exec_time
```

**Q2. How do you configure PostgreSQL to capture slow queries — what are the essential parameters?**

A: Slow query logging is controlled by parameters in `postgresql.conf` (or `ALTER SYSTEM` for live changes without restart):

```ini
# ── Core slow query logging ───────────────────────────────────────────────────

# Threshold in milliseconds — queries taking longer than this are logged
# 0      = log ALL queries (very verbose — development only)
# -1     = disable slow query logging entirely (default)
# 250    = log queries over 250ms (good starting point for busy systems)
# 1000   = log queries over 1 second (conservative — only obvious problems)
log_min_duration_statement = 250

# What to include in the log line:
log_line_prefix = '%t [%p]: user=%u,db=%d,app=%a,client=%h '
# %t = timestamp
# %p = process ID (useful for correlating entries)
# %u = username
# %d = database name
# %a = application name (set by client: SET application_name = 'api-server')
# %h = client host/IP

# Log actual parameter values (not $1, $2 placeholders):
log_min_duration_statement = 250

# Also log queries that are waiting for locks:
log_lock_waits = on
deadlock_timeout = 1s   # Log lock waits longer than 1 second

# Log checkpoint activity (I/O pressure indicator):
log_checkpoints = on

# Log connections/disconnections (useful for connection pool debugging):
log_connections = on
log_disconnections = on

# Where logs go:
log_destination = 'stderr'           # Standard error (systemd/Docker captures this)
logging_collector = on               # Write to files instead of stderr
log_directory = 'pg_log'            # Relative to data directory
log_filename = 'postgresql-%Y-%m-%d.log'  # Daily rotation
log_rotation_age = 1d               # New file daily
log_rotation_size = 100MB           # Also rotate if file exceeds 100MB
log_truncate_on_rotation = off      # Append to existing rotated file
```

Applying changes without a full restart:

```sql
-- Parameters that can be changed with a reload (no restart needed):
-- log_min_duration_statement, log_line_prefix, log_lock_waits, log_checkpoints

-- Apply the reload:
SELECT pg_reload_conf();
-- OR from the shell:
-- pg_ctl reload
-- OR via systemd:
-- systemctl reload postgresql

-- Verify the change took effect:
SHOW log_min_duration_statement;
-- log_min_duration_statement
-- ──────────────────────────
--  250ms

-- Parameters that REQUIRE a restart:
-- logging_collector, log_destination, log_directory, log_filename
-- (These affect where logs go, not what gets logged)

-- Temporarily lower the threshold for a specific session (debugging):
SET log_min_duration_statement = 0;  -- Log everything in this session
-- Your queries here
RESET log_min_duration_statement;

-- Temporarily lower for a specific database:
ALTER DATABASE myapp SET log_min_duration_statement = 100;

-- Temporarily lower for a specific user:
ALTER ROLE analytics_user SET log_min_duration_statement = 500;
```

## Section 2: Reading the Log

**Q3. What does a slow query log entry look like — what does each field tell you?**

A: A log entry contains several fields that together tell you what ran, how long it took, and in what context. Reading them correctly is the core diagnostic skill:

```
2024-01-15 10:32:47.234 IST [28491]: user=app,db=production,app=api-server,client=10.0.1.23
    LOG:  duration: 3427.891 ms  statement: SELECT o.id, o.total, u.email, u.name,
        p.name AS product_name, p.sku
        FROM orders o
        JOIN users u ON u.id = o.user_id
        JOIN order_items oi ON oi.order_id = o.id
        JOIN products p ON p.id = oi.product_id
        WHERE o.status = 'pending'
          AND o.created_at > '2024-01-08 00:00:00'
        ORDER BY o.created_at DESC;
```

Dissecting the entry:

```
2024-01-15 10:32:47.234 IST
└── Timestamp: when the query FINISHED (not when it started)
    To find start time: subtract duration from timestamp
    Start time = 10:32:47.234 - 3427.891ms ≈ 10:32:43.806

[28491]
└── PostgreSQL backend process ID
    Use to correlate with other log entries in the same connection
    Find current activity: SELECT pid, query FROM pg_stat_activity WHERE pid = 28491

user=app,db=production,app=api-server,client=10.0.1.23
└── Context fields (from log_line_prefix):
    user=app          → which database role executed the query
    db=production     → which database
    app=api-server    → application_name set by the client
                        Tells you which service/component sent the query
    client=10.0.1.23  → IP of the application server
                        Useful for multi-service architectures

LOG:  duration: 3427.891 ms
└── How long the query took to EXECUTE (does not include parse/plan time separately)
    3427.891ms = 3.4 seconds — significantly over any reasonable threshold

statement: SELECT o.id, ...
└── The actual SQL text
    With log_min_duration_statement: full text is always included
    With log_statement = 'all': includes queries below threshold too
    Bound parameters are shown as literals when log_parameter_sanitize is off
```

Bind parameters — the difference between parameterised and literal queries:

```
# Query sent as parameterised (prepared statement):
2024-01-15 10:32:47 [28491]: LOG:  duration: 3427.891 ms
    statement: SELECT * FROM orders WHERE user_id = $1 AND status = $2

# Without seeing actual values, you can't test the query — need parameters too:
# Add to postgresql.conf:
log_parameter_max_length = 1024   # Include up to 1024 chars of each parameter value

# Now the log shows:
2024-01-15 10:32:47 [28491]: LOG:  duration: 3427.891 ms
    execute <unnamed>: SELECT * FROM orders WHERE user_id = $1 AND status = $2
    parameters: $1 = '42', $2 = 'pending'

# With parameters, you can copy-paste and run EXPLAIN ANALYZE directly
```

**Q4. How do you read a log file with many entries — what patterns do you look for?**

A: Raw log files from busy production systems can have thousands of entries per day. The analysis workflow moves from raw log → aggregation → prioritisation → root cause:

```bash
# ── Initial triage: what's in the log? ────────────────────────────────────────

# Count slow query entries in a log file:
grep "LOG:  duration:" postgresql-2024-01-15.log | wc -l
# 4,827 slow queries in one day — significant problem

# Show the top 10 slowest individual queries:
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | grep -oP 'duration: \K[0-9.]+' \
    | sort -n -r \
    | head -20
# 45234.123
# 38912.456
# 31234.789
# 28945.012
# ...
# Top query took 45 seconds — severe problem

# Find all queries over 10 seconds:
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | awk -F'duration: ' '{print $2}' \
    | awk '{if ($1+0 > 10000) print $0}' \
    | wc -l
# 23 queries over 10 seconds

# ── Extract the actual query text for the worst entries ───────────────────────

# Show duration + first 120 chars of query for top offenders:
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | sort -t: -k3 -n -r \
    | head -20 \
    | awk '{print substr($0,1,200)}'

# ── Time distribution: when are slow queries happening? ───────────────────────
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | grep -oP '^\d{4}-\d{2}-\d{2} \K\d{2}' \
    | sort | uniq -c | sort -k2 -n
#   12 08     ← slow queries during hour 08
#   89 09     ← spike at 09:00 (morning batch job?)
#  234 10     ← peak at 10:00 (business hours)
#  198 11
#   15 23     ← late night maintenance?

# ── Application context: which service is causing this? ───────────────────────
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | grep -oP 'app=\K[^ ,]+' \
    | sort | uniq -c | sort -nr
# 3421 api-server         ← most slow queries from api-server
#  892 background-worker  ← second most
#  289 analytics          ← analytics service
#  225 admin-panel

# ── Per-user breakdown: which role? ───────────────────────────────────────────
grep "LOG:  duration:" postgresql-2024-01-15.log \
    | grep -oP 'user=\K[^ ,]+' \
    | sort | uniq -c | sort -nr
# 4102 app_user       ← production application user
#  725 analytics_user ← analytics queries
```

## Section 3: `pg_stat_statements`

**Q5. What is `pg_stat_statements` and why is it essential alongside the slow query log?**

A: `pg_stat_statements` is a PostgreSQL extension that tracks aggregate statistics for every distinct query pattern executed. While the slow query log captures individual slow executions, `pg_stat_statements` shows the cumulative cost of a query across all executions — revealing queries that are fast individually but devastating collectively:

```sql
-- Enable the extension (requires postgresql.conf change + restart):
-- shared_preload_libraries = 'pg_stat_statements'
-- pg_stat_statements.track = all         -- track all SQL including nested
-- pg_stat_statements.max = 10000         -- max distinct query fingerprints to track
-- pg_stat_statements.track_utility = on  -- track VACUUM, CREATE INDEX, etc.

-- Then:
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- The view (PostgreSQL 14+ column names):
SELECT
    query,
    calls,
    total_exec_time,
    mean_exec_time,
    stddev_exec_time,
    min_exec_time,
    max_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    shared_blks_written,
    temp_blks_read,
    temp_blks_written,
    blk_read_time,
    blk_write_time
FROM pg_stat_statements
LIMIT 5;
```

The two most important queries for initial analysis:

```sql
-- Query 1: Top queries by TOTAL time (worst aggregate impact)
-- These are the queries you should fix first:
SELECT
    LEFT(query, 100)                               AS query_snippet,
    calls,
    ROUND(total_exec_time::numeric, 2)             AS total_ms,
    ROUND(mean_exec_time::numeric, 2)              AS mean_ms,
    ROUND(stddev_exec_time::numeric, 2)            AS stddev_ms,
    ROUND(total_exec_time / SUM(total_exec_time)
        OVER () * 100, 2)                          AS pct_of_total,
    rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- Example output:
-- query_snippet                                       │ calls  │ total_ms  │ mean_ms │ pct_of_total
-- ────────────────────────────────────────────────────┼────────┼───────────┼─────────┼─────────────
-- SELECT o.id, o.total FROM orders WHERE status=$1   │ 482001 │ 3241567.4 │ 6.72    │ 38.2
-- UPDATE sessions SET last_seen=$1 WHERE id=$2        │ 920345 │ 1842034.1 │ 2.00    │ 21.7
-- SELECT * FROM products WHERE category_id=$1 LIMIT…  │ 234521 │  934201.5 │ 3.98    │ 11.0
--
-- The first query takes 6.72ms average — below any slow query threshold
-- But called 482k times → 3.2 SECONDS of cumulative DB time in the stats window
-- This would NEVER appear in the slow query log

-- Query 2: Top queries by MEAN time (worst individual performance)
-- These are the queries causing the worst user-facing latency:
SELECT
    LEFT(query, 100)                               AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2)              AS mean_ms,
    ROUND(max_exec_time::numeric, 2)               AS max_ms,
    ROUND(stddev_exec_time::numeric, 2)            AS stddev_ms,
    ROUND(total_exec_time::numeric, 2)             AS total_ms
FROM pg_stat_statements
WHERE calls > 10                      -- Ignore one-off queries
ORDER BY mean_exec_time DESC
LIMIT 20;

-- Query 3: High variance queries — inconsistent performance (indexing or locking issue)
SELECT
    LEFT(query, 80)                                AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2)              AS mean_ms,
    ROUND(stddev_exec_time::numeric, 2)            AS stddev_ms,
    ROUND(stddev_exec_time / NULLIF(mean_exec_time, 0), 2) AS cv,  -- Coefficient of variation
    ROUND(max_exec_time::numeric, 2)               AS max_ms
FROM pg_stat_statements
WHERE calls > 100
ORDER BY (stddev_exec_time / NULLIF(mean_exec_time, 0)) DESC
LIMIT 20;
-- High CV (> 2.0) means sometimes fast, sometimes very slow
-- Common cause: lock contention, cache misses, or data-dependent query plans

-- Query 4: I/O-heavy queries (reading many blocks from disk)
SELECT
    LEFT(query, 80)                                AS query_snippet,
    calls,
    ROUND(mean_exec_time::numeric, 2)              AS mean_ms,
    shared_blks_read                               AS disk_blocks_read,
    shared_blks_hit                                AS cache_hits,
    ROUND(shared_blks_read::numeric /
        NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 2)
                                                   AS cache_miss_pct,
    temp_blks_read + temp_blks_written             AS temp_io
FROM pg_stat_statements
WHERE shared_blks_read > 0
ORDER BY shared_blks_read DESC
LIMIT 20;
-- High cache_miss_pct → query is reading from disk, not cache
-- High temp_io → sorts/hash joins spilling to disk → increase work_mem

-- Reset statistics (do this at the start of a monitoring window):
SELECT pg_stat_statements_reset();
-- Or reset for one query:
SELECT pg_stat_statements_reset(userid, dbid, queryid)
FROM pg_stat_statements
WHERE query LIKE '%orders%status%'
LIMIT 1;
```

**Q6. How do you correlate `pg_stat_statements` data with the slow query log — what's the combined workflow?**

A: The two tools answer complementary questions. The workflow uses both:

```sql
-- Step 1: pg_stat_statements → identify the query patterns with highest impact
SELECT
    queryid,
    LEFT(query, 120) AS query_snippet,
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    ROUND(mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;

-- Output:
-- queryid             │ query_snippet                                          │ calls  │ total_ms   │ mean_ms
-- ────────────────────┼────────────────────────────────────────────────────────┼────────┼────────────┼────────
-- 3289472819374629384 │ SELECT o.id, o.total, u.email FROM orders o JOIN u... │ 482001 │ 3241567.40 │ 6.72

-- Step 2: Search the slow query log for actual examples of this query
-- (The slow query log shows parameter values; pg_stat_statements shows the pattern)
grep "orders.*JOIN.*users" postgresql-2024-01-15.log \
    | grep "duration: [0-9]\{3,\}" \
    | head -5
# Finds log entries of this query when it WAS slow (outliers)

-- Step 3: Extract a representative example with real parameter values
# From the log:
# duration: 3427.891 ms  statement: SELECT o.id, o.total, u.email
#   FROM orders o JOIN users u ON u.id = o.user_id
#   WHERE o.status = 'pending' AND o.created_at > '2024-01-08 00:00:00'
#   ORDER BY o.created_at DESC;

-- Step 4: Run EXPLAIN ANALYZE with the actual parameters
EXPLAIN (ANALYZE, BUFFERS)
    SELECT o.id, o.total, u.email
    FROM orders o JOIN users u ON u.id = o.user_id
    WHERE o.status = 'pending' AND o.created_at > '2024-01-08 00:00:00'
    ORDER BY o.created_at DESC;

-- Step 5: Identify the bottleneck (seq scan, bad estimates, sort spill, etc.)
-- Step 6: Implement fix (create index, rewrite query, increase work_mem)
-- Step 7: Compare pg_stat_statements before and after:
--   Reset stats → run workload → check new mean_exec_time
--   Confirm improvement is reflected in aggregate data, not just one test

-- Correlating by queryid (PostgreSQL 14+):
-- pg_stat_statements.queryid is consistent within a session
-- Useful when log_line_prefix includes %Q (query ID in log entries)
-- log_line_prefix = '%t [%p]: [%Q] user=%u,db=%d '
-- Then grep the slow log for a specific queryid:
# grep "\[3289472819374629384\]" postgresql-2024-01-15.log | head -3
```

## Section 4: `auto_explain`

**Q7. What is `auto_explain` and how do you use it to capture query plans automatically for slow queries?**

A: `auto_explain` is a PostgreSQL module that automatically logs the execution plan for queries exceeding a threshold. Instead of manually running `EXPLAIN ANALYZE` after the fact, `auto_explain` captures the plan at the time the slow query actually ran — including any runtime conditions (hot cache, cold cache, parallel workers) that may not be reproducible:

```ini
# postgresql.conf — load at startup (requires restart):
shared_preload_libraries = 'pg_stat_statements,auto_explain'

# auto_explain parameters (can be changed with ALTER SYSTEM + pg_reload_conf()):
auto_explain.log_min_duration = 500    # Log plans for queries over 500ms
auto_explain.log_analyze = on          # Include actual row counts and times (like EXPLAIN ANALYZE)
auto_explain.log_buffers = on          # Include buffer usage (shared hit/read)
auto_explain.log_timing = on           # Include per-node timing (set off if overhead is concern)
auto_explain.log_triggers = off        # Include trigger execution stats
auto_explain.log_verbose = off         # Include verbose output (very detailed)
auto_explain.log_format = text         # 'text' or 'json' (json easier to parse programmatically)
auto_explain.log_nested_statements = on # Also log plans for queries inside functions/procedures
auto_explain.sample_rate = 1.0         # Sample rate 0.0-1.0 (1.0 = log all qualifying queries)
                                        # Use 0.1 to log only 10% of slow queries (reduce volume)
```

What the log looks like with `auto_explain`:

```
2024-01-15 10:32:47.234 IST [28491]: user=app,db=production,app=api-server,client=10.0.1.23
    LOG:  duration: 3427.891 ms  plan:

                ORDER BY o.created_at DESC

          (actual time=3421.234..3427.456 rows=97234 loops=1)

-- Diagnosis from the auto_explain output:
-- 1. Sort spilled to disk (external merge, 12MB) → increase work_mem
-- 2. Seq Scan on orders filtering 200k rows to find 97k → composite index on (status, created_at)
-- 3. Seq Scan on users (150k rows) for Hash Join → index might help if this join is selective
```

Enabling `auto_explain` without a restart (session or database level):

```sql
-- Enable for the current session only (no restart needed):
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 0;   -- Log every query in this session
SET auto_explain.log_analyze = on;

-- Test:
SELECT pg_sleep(0.1);
-- Now check the log — should show the plan for the sleep

-- Enable for a specific database without restart:
ALTER DATABASE production SET auto_explain.log_min_duration = 1000;
-- Requires a new connection to take effect for existing sessions
-- Useful for temporary debugging without touching postgresql.conf
```

## Section 5: Tooling for Log Analysis

**Q8. What are `pgBadger` and other tools that automate slow query log analysis?**

A: Manual log analysis with `grep` and `awk` works for targeted investigation, but automated tools aggregate, rank, and visualise the log data at scale:

```bash
# ── pgBadger: the standard PostgreSQL log analyser ────────────────────────────
# Produces HTML reports with: slowest queries, most frequent queries,
# lock waits, connection statistics, error breakdown

# Installation:
# apt install pgbadger  (Debian/Ubuntu)
# brew install pgbadger  (macOS)
# cpan pgBadger         (from CPAN)
# OR: https://github.com/darold/pgbadger

# Basic usage — analyse a log file:
pgbadger postgresql-2024-01-15.log -o report.html
# Opens a comprehensive HTML report in your browser

# Most useful options:
pgbadger \
    --format stderr \                 # Log format (stderr, syslog, csv, jsonlog)
    --prefix '%t [%p]: user=%u,db=%d,app=%a,client=%h ' \  # Must match log_line_prefix
    --outfile report.html \           # Output file
    --top 30 \                        # Show top 30 queries in each category
    --sample 3 \                      # Include 3 example queries for each pattern
    --quiet \                         # Suppress progress output
    postgresql-2024-01-15.log

# Analyse multiple log files (e.g., a week of logs):
pgbadger \
    --outfile weekly-report.html \
    postgresql-2024-01-1{0,1,2,3,4,5,6}.log

# Incremental mode for large log files (process in chunks):
pgbadger --incremental --outdir /var/www/pgbadger/ postgresql-2024-01-15.log

# pgBadger report sections relevant to slow queries:
# - "Slowest individual queries" → worst single executions
# - "Time consuming queries" → highest total time across all executions
# - "Most frequent queries" → called most often (potential for N+1)
# - "Queries that waited the most" → lock contention
```

## Section 6: Acting on What You Find

**Q9. How do you systematically act on slow query log findings — the full diagnostic-to-fix workflow?**

A: Finding a slow query is only the start. The workflow from log entry to fix follows a consistent path:

```sql
-- ── STEP 1: Extract the query with real parameters ────────────────────────────
-- From the log:
-- duration: 4823.123 ms  statement:
--   SELECT u.id, u.email, COUNT(o.id) AS order_count
--   FROM users u
--   LEFT JOIN orders o ON o.user_id = u.id
--   WHERE u.plan = 'enterprise' AND u.created_at > '2024-01-01'
--   GROUP BY u.id, u.email
--   ORDER BY order_count DESC
--   LIMIT 50;

-- ── STEP 2: Run EXPLAIN ANALYZE with those exact parameters ───────────────────
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
    SELECT u.id, u.email, COUNT(o.id) AS order_count
    FROM users u
    LEFT JOIN orders o ON o.user_id = u.id
    WHERE u.plan = 'enterprise' AND u.created_at > '2024-01-01'
    GROUP BY u.id, u.email
    ORDER BY order_count DESC
    LIMIT 50;

-- ── STEP 3: Identify the bottleneck ───────────────────────────────────────────
-- Checklist to go through the plan output:
-- □ Is there a Seq Scan on a large table?
--     → Check "Rows Removed by Filter" — is it discarding most rows?
--     → If yes: create index on the filter column(s)
-- □ Are estimated rows wildly different from actual rows?
--     → Run: ANALYZE <tablename>; then re-check
-- □ Is Sort spilling to disk? ("external merge  Disk: NkB")
--     → Increase work_mem for the session or globally
-- □ Is Hash batching? ("Batches: N > 1")
--     → Increase work_mem
-- □ Is there a Nested Loop with loops=large_number on the inner scan?
--     → The inner scan cost × loops = real cost
--     → Add index on the inner table's join column
-- □ Is there a Filter after Index Scan (not Index Cond)?
--     → The non-indexed column is filtering heap rows after fetch
--     → Add it to a composite index
-- □ Are there many "shared read" buffers (disk reads)?
--     → I/O-bound — index to reduce rows, increase shared_buffers, or add RAM

-- ── STEP 4: Formulate and test the fix ────────────────────────────────────────

-- Hypothesis from STEP 3:
-- Seq Scan on users: filtering enterprise plan users from created_at > 2024-01-01
-- No index on (plan, created_at)

-- Create index (use CONCURRENTLY to avoid locking the table):
CREATE INDEX CONCURRENTLY users_plan_created_idx
    ON users(plan, created_at)
    WHERE plan = 'enterprise';  -- Partial index if you only ever filter enterprise

-- Verify the index would be used:
EXPLAIN
    SELECT u.id, u.email
    FROM users u
    WHERE u.plan = 'enterprise' AND u.created_at > '2024-01-01';
-- Should now show: Index Scan using users_plan_created_idx on users

-- ── STEP 5: Measure the improvement ──────────────────────────────────────────
-- Before (from log): duration: 4823.123 ms
-- After (from EXPLAIN ANALYZE): actual time=0.034..89.234 ms
-- Improvement: 54× faster

-- ── STEP 6: Monitor in production ────────────────────────────────────────────
-- Reset pg_stat_statements for a clean baseline:
SELECT pg_stat_statements_reset();

-- Wait 24 hours, then check if the query's mean_exec_time improved:
SELECT
    LEFT(query, 80)               AS query,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS mean_ms,
    ROUND(total_exec_time::numeric, 2) AS total_ms
FROM pg_stat_statements
WHERE query LIKE '%users%enterprise%'
ORDER BY total_exec_time DESC;

-- ── STEP 7: Confirm the index is actually being used ─────────────────────────
SELECT
    indexrelname,
    idx_scan        AS times_used,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'users' AND indexrelname = 'users_plan_created_idx';
-- idx_scan should be increasing over time
```

**Q10. What are the common patterns you find in slow query logs — and what is the fix for each?**

A: Across production systems, the same patterns appear repeatedly. Recognising them from the log output accelerates diagnosis:

```sql
-- ── Pattern 1: The Missing Index ──────────────────────────────────────────────
-- Log evidence:
-- duration: 2340.123 ms  statement:
--   SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

-- EXPLAIN shows:
-- Seq Scan on orders  (cost=0.00..9250.00 rows=3 width=96)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 199997  ← reading 200k rows to find 3

-- Fix:
CREATE INDEX CONCURRENTLY orders_user_id_created_idx
    ON orders(user_id, created_at DESC);

-- ── Pattern 2: The N+1 Query ──────────────────────────────────────────────────
-- Log evidence (multiple rapid entries, all < threshold individually):
-- 10:32:47 duration: 2.1 ms  statement: SELECT * FROM products WHERE id = 1
-- 10:32:47 duration: 1.8 ms  statement: SELECT * FROM products WHERE id = 2
-- 10:32:47 duration: 2.3 ms  statement: SELECT * FROM products WHERE id = 3
-- ... (repeated 500 times in 2 seconds, same app process)
-- Individually fast, but 500 × 2ms = 1 second of overhead per request

-- Detection in pg_stat_statements:
SELECT LEFT(query, 80), calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
WHERE query LIKE 'SELECT%products%WHERE id%'
ORDER BY calls DESC;
-- calls: 2,400,000 in one day — N+1 pattern

-- Fix: Rewrite application to use WHERE id IN ($1, $2, $3, ...)
-- Or: use JOIN instead of per-row lookup
-- In an ORM (TypeORM): use eager loading / relations
-- In Prisma: use include: { products: true }

-- ── Pattern 3: Lock Contention ─────────────────────────────────────────────────
-- Log evidence (log_lock_waits = on):
-- duration: 8923.456 ms  statement: UPDATE orders SET status='shipped' WHERE id = $1
-- LOG:  process 28491 acquired ShareLock on transaction 7823456 after 8900.234 ms
-- LOG:  process 28491 still waiting for ShareLock on transaction 7823456 after 1000.000 ms
--         DETAIL:  Process holding the lock: 29234.
--         HINT:  See server log for query description of process 29234.

-- The UPDATE waited 8.9 seconds for a lock — another process held it

-- Investigation:
SELECT pid, state, wait_event_type, wait_event, query_start, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_start;
-- Shows currently blocked/blocking queries

-- Fix options:
-- - Reduce transaction duration (commit faster)
-- - Break large batch updates into smaller chunks
-- - Use SELECT ... FOR UPDATE SKIP LOCKED for queue processing
-- - Reorder operations to reduce lock window

-- ── Pattern 4: The Unparameterised Query ─────────────────────────────────────
-- Log evidence (query plan cache thrashing):
-- duration: 45.2 ms  statement: SELECT * FROM users WHERE id = 12345
-- duration: 43.8 ms  statement: SELECT * FROM users WHERE id = 12346
-- duration: 44.1 ms  statement: SELECT * FROM users WHERE id = 12347
-- (Each query is a literal, not a parameterised $1)

-- Each distinct literal is a separate query in pg_stat_statements
-- No plan caching → planning overhead on every execution
-- AND: pg_stat_statements fills with 100k unique entries → degrades performance

-- Fix: use parameterised queries in the application
-- Node.js: client.query('SELECT * FROM users WHERE id = $1', [userId])
-- Not:     client.query(`SELECT * FROM users WHERE id = ${userId}`)

-- ── Pattern 5: Sorting Without an Index ───────────────────────────────────────
-- Log evidence:
-- duration: 6234.123 ms  statement:
--   SELECT * FROM audit_log ORDER BY created_at DESC LIMIT 100;

-- auto_explain shows:
-- Sort  (cost=…)  Sort Method: external merge  Disk: 45320kB  ← 45MB sort to disk
--   ->  Seq Scan on audit_log (5,000,000 rows)

-- Fix:
CREATE INDEX CONCURRENTLY audit_log_created_at_idx ON audit_log(created_at DESC);
-- Now: Index Scan Backward → zero sort cost, no disk spill

-- ── Pattern 6: Stale Statistics ──────────────────────────────────────────────
-- Log evidence:
-- duration: 12345.678 ms  statement:
--   SELECT * FROM events WHERE type = 'click' AND user_id = $1;

-- auto_explain shows:
-- Nested Loop (cost=… rows=2)  (actual rows=45234)  ← estimated 2, got 45k!
--   (planner chose nested loop because it thought 2 rows would match)
--   (with 45k matches, hash join would be 100x faster)

-- Fix:
ANALYZE events;
-- Then re-check EXPLAIN — planner should now choose hash join or bitmap scan

-- ── Pattern 7: DISTINCT on Large Result Sets ──────────────────────────────────
-- Log evidence:
-- duration: 8923.456 ms  statement:
--   SELECT DISTINCT user_id FROM events WHERE created_at > '2024-01-01';

-- EXPLAIN shows:
-- HashAggregate  (Batches: 8  Memory Usage: 4096kB)  ← hash agg spilled 8x to disk
--   ->  Seq Scan on events (50,000,000 rows)

-- Fix options:
-- 1. Index on user_id with created_at filter:
CREATE INDEX events_user_created_idx ON events(user_id, created_at);
-- Allows Index Only Scan returning distinct user_ids efficiently

-- 2. Rewrite with EXISTS (if checking existence is the real goal):
SELECT id FROM users WHERE EXISTS (
    SELECT 1 FROM events
    WHERE events.user_id = users.id AND events.created_at > '2024-01-01'
);

-- 3. Materialised view if this query runs frequently
```

## Section 7: Production Considerations

**Q11. What is the performance overhead of enabling slow query logging and `pg_stat_statements` in production?**

A: Both have overhead, but it is manageable with the right configuration:

```sql
-- ── log_min_duration_statement overhead ───────────────────────────────────────
-- Measuring the duration of every query: negligible (uses existing timer)
-- Writing to the log: only for queries exceeding the threshold
--
-- At 250ms threshold on a busy system:
-- If 0.1% of queries are slow → log volume is tiny → negligible overhead
-- If all queries are "slow" (threshold=0) → log write per query → 1-5% overhead
--
-- The log writing itself is buffered by the logging collector process
-- It does NOT block the query execution path

-- Impact by threshold:
-- log_min_duration_statement = -1   → 0% overhead (disabled)
-- log_min_duration_statement = 1000 → negligible (only very slow queries)
-- log_min_duration_statement = 250  → negligible to low (few queries at 250ms)
-- log_min_duration_statement = 0    → 2-5% overhead (every query logged)

-- ── pg_stat_statements overhead ────────────────────────────────────────────────
-- pg_stat_statements intercepts every query execution
-- Overhead: 1-5% on typical workloads (stated in PostgreSQL documentation)
-- Cause: query normalisation (replace literals with $1), hash computation, stat update

-- Reducing pg_stat_statements overhead:
-- pg_stat_statements.max = 1000     (default 5000 — fewer entries = less memory pressure)
-- pg_stat_statements.track = top    (only top-level queries, not nested)
-- pg_stat_statements.track_utility = off (don't track VACUUM, ANALYZE, etc.)

-- ── auto_explain overhead ─────────────────────────────────────────────────────
-- auto_explain.log_analyze = on adds EXPLAIN ANALYZE overhead to every slow query
-- EXPLAIN ANALYZE itself adds ~0-10% overhead to query execution
-- But: only affects queries already exceeding the threshold
-- At 500ms threshold: slow queries pay the auto_explain overhead
--                     fast queries are unaffected
--
-- auto_explain.sample_rate = 0.1 → only 10% of slow queries get the EXPLAIN ANALYZE
-- Use this on extremely high-volume systems where even slow query auto_explain is heavy

-- ── Monitoring overhead in practice ───────────────────────────────────────────
-- Recommended production configuration for a busy OLTP system:
-- log_min_duration_statement = 500    ← 500ms threshold
-- auto_explain.log_min_duration = 2000 ← Only log plans for very slow queries
-- auto_explain.log_analyze = on
-- auto_explain.sample_rate = 0.5      ← 50% sampling of slow queries
-- pg_stat_statements.track = top
-- pg_stat_statements.max = 5000

-- ── Disk space for logs ────────────────────────────────────────────────────────
-- A log entry for a slow query: ~200-1000 bytes
-- With auto_explain (plan included): 500-5000 bytes per entry
-- At 1000 slow queries/day with auto_explain:
--   1000 × 3000 bytes average = 3 MB/day
-- At 100,000 slow queries/day:
--   100,000 × 3000 bytes = 300 MB/day
-- Ensure log rotation is configured:
log_rotation_age = 1d
log_rotation_size = 500MB
```

**Q12. "Users report the application was slow between 14:00 and 15:00 yesterday. How do you investigate using the slow query log?"**

```bash
# ── Step 1: Extract the relevant time window from the log ─────────────────────
# PostgreSQL log format: 2024-01-15 14:00:00.123 IST [pid]:
grep "2024-01-15 1[45]:" postgresql-2024-01-15.log \
    | grep "LOG:  duration:" \
    > slow_queries_14_15h.txt

wc -l slow_queries_14_15h.txt
# 2,847 slow queries between 14:00 and 15:00
# Normal baseline: ~50/hour — this is 57x above normal

# ── Step 2: Distribution within the window ────────────────────────────────────
grep "2024-01-15 1[45]:" postgresql-2024-01-15.log \
    | grep "LOG:  duration:" \
    | grep -oP '^\d{4}-\d{2}-\d{2} \d{2}:\K\d{2}' \
    | sort | uniq -c
#   12 00     ← 14:00 — normal
#   18 01
#  234 04     ← 14:04 — spike starts!
#  489 05
#  512 06
#  498 07
#  423 08
#  312 09
#  156 10
#   23 11     ← returning to normal by 14:11
#   15 12
# Spike lasted ~7 minutes (14:04-14:11)

# ── Step 3: What queries were slow during the spike? ──────────────────────────
grep "2024-01-15 14:0[4-9]:" postgresql-2024-01-15.log \
    | grep "LOG:  duration:" \
    > spike_queries.txt

# Summarise by query pattern (strip literals):
grep "statement:" spike_queries.txt \
    | sed 's/= [0-9]*/= N/g; s/= '"'"'[^'"'"']*'"'"'/= '"'"'?'"'"'/g' \
    | sort | uniq -c | sort -nr | head -10
# 1823  SELECT * FROM products WHERE category_id = N AND status = '?'
#  456  UPDATE inventory SET quantity = N WHERE product_id = N
#   78  SELECT * FROM orders WHERE user_id = N ORDER BY created_at DESC

# Most slow queries are: SELECT products WHERE category_id = N AND status = ?

# ── Step 4: What triggered it? Check for a deployment or batch job ────────────
grep "2024-01-15 14:0[0-4]:" postgresql-2024-01-15.log \
    | grep -E "CREATE INDEX|DROP INDEX|VACUUM|checkpoint|autovacuum"
# 2024-01-15 14:04:12 [1234]: LOG:  automatic vacuum of table "production.public.products"
# 2024-01-15 14:04:12 [1234]: LOG:  automatic analyze of table "production.public.products"
# AUTOVACUUM ran at 14:04 — correlates perfectly with the spike

# autovacuum on a large table holds brief locks and causes I/O pressure
# This can slow queries that normally use the table

# ── Step 5: pg_stat_statements for quantification ────────────────────────────
```

```sql
-- Check if the product query appears as unusually slow in pg_stat_statements:
SELECT
    LEFT(query, 80) AS query,
    calls,
    ROUND(mean_exec_time::numeric, 2)   AS mean_ms,
    ROUND(max_exec_time::numeric, 2)    AS max_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms
FROM pg_stat_statements
WHERE query LIKE '%products%category_id%status%'
ORDER BY max_exec_time DESC;
-- High stddev_ms and high max_exec_time confirms bursty slow performance

-- ── Step 6: Prevention ─────────────────────────────────────────────────────────
-- autovacuum_vacuum_cost_delay: throttle autovacuum I/O to reduce impact
ALTER TABLE products SET (
    autovacuum_vacuum_cost_delay = 10,   -- 10ms delay between cost units (default 2ms)
    autovacuum_vacuum_cost_limit = 400   -- Total cost per delay unit
);
-- This makes autovacuum slower but reduces its impact on concurrent queries
```

**Q13. "pg_stat_statements shows a query with mean=3ms and 2 million calls per day. The slow query log has zero entries for it. Should you optimise it?"**

A:

```sql
-- The query appears in pg_stat_statements:
-- SELECT u.id, u.name FROM users WHERE email = $1
-- calls:           2,000,000/day
-- mean_exec_time:  3.2ms
-- total_exec_time: 6,400,000ms = 6,400 seconds = 106 minutes/day
-- threshold:       log_min_duration_statement = 250ms (so it never logs)

-- STEP 1: Calculate the business impact
-- 3.2ms × 2,000,000 = 106 minutes of database CPU per day
-- If this is a lookup by email (authentication), it runs on every login check
-- This is almost certainly worth optimising

-- STEP 2: EXPLAIN ANALYZE the query
EXPLAIN (ANALYZE, BUFFERS)
    SELECT id, name FROM users WHERE email = 'alice@example.com';

-- Scenario A — already using an index (fast path):
--  Index Scan using users_email_idx on users (cost=0.43..8.45 rows=1 width=48)
--                                            (actual time=0.021..0.023 rows=1 loops=1)
--    Index Cond: ((email)::text = 'alice@example.com'::text)
--    Buffers: shared hit=3
-- If mean is 3.2ms but EXPLAIN ANALYZE shows 0.023ms:
-- The 3.2ms includes network latency + connection overhead + planning time
-- The actual query is already optimal — reduce connection overhead instead
-- (connection pooling with PgBouncer, reducing round-trips)

-- Scenario B — seq scan on large table:
--  Seq Scan on users (cost=0.00..4567.00 rows=1 width=48)
--                    (actual time=3.123..3.189 rows=1 loops=1)
--    Filter: ((email)::text = 'alice@example.com'::text)
--    Rows Removed by Filter: 149999
-- Now 3.2ms = genuine query time → index on email needed

-- STEP 3: The rule for optimising sub-threshold queries
-- Total_exec_time × (improvement_factor - 1) = time saved
-- If we cut 3.2ms → 0.05ms (64× faster):
-- Saved: (3.2 - 0.05) / 1000 × 2,000,000 = 6,300 seconds/day = 105 minutes

-- YES, optimise if total_exec_time > ~1 hour/day
-- The slow query log threshold is NOT the right filter for cumulative impact

-- STEP 4: For high-frequency queries, also check cache efficiency:
SELECT
    shared_blks_hit,
    shared_blks_read,
    ROUND(shared_blks_hit::numeric / NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 2)
        AS cache_hit_pct
FROM pg_stat_statements
WHERE query LIKE 'SELECT%users%email%';
-- cache_hit_pct = 99.8% → mostly cached → problem is not I/O
-- cache_hit_pct = 60%   → reading from disk frequently → more RAM or better index

-- STEP 5: Index-only scan opportunity
-- If only selecting id and name, and email is the filter:
CREATE INDEX users_email_covering ON users(email) INCLUDE (id, name);
-- Now: Index Only Scan → Heap Fetches: 0 → saves the heap fetch per call
-- At 2M calls/day, saving even 0.5ms per call = 1000 seconds/day saved
```

## Quick Reference Table

| Tool | What it shows | Best for |
|---|---|---|
| `log_min_duration_statement` | Individual slow query text + duration | First occurrence of a slow query, episodic problems |
| `auto_explain` | Query plan at execution time for slow queries | Understanding WHY a specific execution was slow |
| `pg_stat_statements` | Aggregate stats across all executions | Finding high-impact queries, cumulative cost |
| `pgBadger` | HTML report from log file | Management reporting, pattern discovery at scale |
| `pg_stat_activity` | Currently executing queries | Real-time diagnosis of ongoing slowness |
| `pg_stat_user_indexes` | Index usage counts | Confirming an index is used; finding unused indexes |

| Log pattern | Diagnosis | Fix |
|---|---|---|
| `Rows Removed by Filter: N` (large N, Seq Scan) | Missing index | `CREATE INDEX CONCURRENTLY` on filter column |
| `Sort Method: external merge  Disk: NkB` | Sort spilling to disk | Increase `work_mem`; add sorted index |
| `Batches: N` (N > 1) on Hash node | Hash join/aggregate spilling to disk | Increase `work_mem` |
| Many rapid identical queries (N+1 pattern) | ORM not batching queries | Rewrite to use `IN` / `JOIN`; fix ORM eager loading |
| `still waiting for ShareLock` | Lock contention | Reduce transaction duration; use `SKIP LOCKED` |
| High `stddev_exec_time` in pg_stat_statements | Inconsistent — lock contention or cache misses | Investigate concurrent activity; check index health |
| Estimated rows ≪ Actual rows in auto_explain | Stale statistics | `ANALYZE <table>` |
| `Heap Fetches: N` on Index Only Scan | Visibility map not set | `VACUUM <table>` |
| Same literal values (not `$1`, `$2`) | Unparameterised queries | Fix application to use bind parameters |

| pg_stat_statements query | Purpose |
|---|---|
| `ORDER BY total_exec_time DESC` | Highest aggregate impact (fix these first) |
| `ORDER BY mean_exec_time DESC WHERE calls > 10` | Worst individual latency |
| `ORDER BY calls DESC` | Highest frequency (N+1 detector) |
| `ORDER BY stddev/mean DESC` | Most inconsistent (lock/cache suspects) |
| `ORDER BY shared_blks_read DESC` | Most I/O intensive |
| `WHERE temp_blks_read + temp_blks_written > 0` | Queries spilling to disk |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **`pg_stat_statements` and the slow query log are complementary, not redundant** — the slow query log finds individual slow executions, while `pg_stat_statements` reveals the cumulative cost of queries that are fast individually but devastating at scale; a query called 2 million times per day at 3ms each accumulates 100 minutes of DB CPU time but never appears in a 250ms slow query log; (2) understanding **`auto_explain` captures the plan AT EXECUTION TIME** — running `EXPLAIN ANALYZE` after the fact may not reproduce the exact conditions (cache state, table statistics, concurrent load) that made a query slow, while `auto_explain` logged the actual plan with real timing during the actual slow execution; (3) knowing the **critical difference between `total_exec_time` and `mean_exec_time` in pg_stat_statements** — sorting by `mean_exec_time` finds the worst individual queries, but sorting by `total_exec_time` finds the queries costing the most aggregate DB time, which is the right prioritisation criterion for optimisation work; (4) articulating **why the slow query log alone is insufficient for N+1 detection** — individual N+1 queries are fast (1-5ms each), so they fall below any reasonable threshold; detecting them requires either `pg_stat_statements` ordered by `calls` or log analysis showing many identical queries in rapid succession from the same process; (5) knowing that **`log_parameter_max_length`** (or `log_min_duration_statement` with `%q` in `log_line_prefix`) is needed to see actual parameter values in the log — without this, you see `WHERE user_id = $1` but not the actual value, making it impossible to reproduce the query for `EXPLAIN ANALYZE`; and (6) understanding **the performance cost trade-offs** — `log_min_duration_statement` at a reasonable threshold (250-500ms) adds negligible overhead since log writing only occurs for already-slow queries; `pg_stat_statements` adds 1-5% overhead universally and should be enabled in all production environments; `auto_explain` with `log_analyze = on` adds EXPLAIN ANALYZE overhead only to queries already exceeding the threshold, which is acceptable.
