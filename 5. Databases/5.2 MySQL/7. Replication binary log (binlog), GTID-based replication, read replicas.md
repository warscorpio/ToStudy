## Interview Q&A (5 YOE Level)

## Section 1: Why Replication Exists

**Q1. What problems does database replication solve — what are the fundamental guarantees it provides and the trade-offs it introduces?**

A: Replication copies data from one database server to one or more others. It solves three distinct problems — high availability, read scalability, and geographical distribution — but each solution introduces its own consistency trade-off:

```
Replication topology (MySQL primary–replica):

  ┌──────────────────────────────────────────────────────────────────┐
  │                     PRIMARY (source)                             │
  │  Writes: INSERT, UPDATE, DELETE, DDL                             │
  │  Reads:  all reads (strong consistency)                          │
  │  binlog: records every change in order                           │
  └──────────────────┬───────────────────────────────────────────────┘
                     │  binlog stream
          ┌──────────┼──────────┐
          │          │          │
  ┌───────▼──┐  ┌────▼─────┐  ┌▼──────────┐
  │ Replica 1│  │ Replica 2│  │ Replica 3 │
  │ (same    │  │ (same    │  │ (different│
  │  region) │  │  region) │  │  region)  │
  │ Reads ✓  │  │ Reads ✓  │  │ Reads ✓   │
  │ Failover │  │ Analytics│  │ Low-latency│
  │ candidate│  │ queries  │  │ for EU    │
  └──────────┘  └──────────┘  └──────────┘

Three problems replication solves:

  1. High Availability (HA):
     Primary fails → promote a replica → application reconnects.
     RTO (Recovery Time Objective): seconds to minutes.
     RPO (Recovery Point Objective): depends on sync mode (see Q9).

  2. Read Scalability:
     Route SELECT queries to replicas → primary handles only writes.
     10 replicas → ~10x read throughput (within consistency constraints).
     Trade-off: replicas may lag behind primary → reads may be stale.

  3. Geographical Distribution:
     Replica in EU region → EU users read locally (low latency).
     Writes still go to primary (single authoritative source).
     Trade-off: cross-region replication lag can be 50-200ms.

Core trade-off (CAP theorem in practice):
  Strong consistency + High availability requires synchronous replication
  → writes blocked until ALL replicas confirm → high write latency.
  High availability + Partition tolerance (typical default)
  → asynchronous replication → replicas may lag → eventual consistency.
```

```sql
-- ── Verifying replication status on MySQL primary ─────────────────────────────
SHOW MASTER STATUS;
-- File:              mysql-binlog.000042   ← current binlog file
-- Position:          194732841             ← byte offset within that file
-- Binlog_Do_DB:                           ← databases included (empty = all)
-- Binlog_Ignore_DB:                       ← databases excluded
-- Executed_Gtid_Set: a1b2c3d4-...:1-9821  ← if GTID mode enabled

-- On replica:
SHOW REPLICA STATUS\G   -- MySQL 8.0+ (was SHOW SLAVE STATUS in older versions)
-- Replica_IO_Running: Yes         ← I/O thread: downloading binlog from primary ✓
-- Replica_SQL_Running: Yes        ← SQL thread: applying events from relay log ✓
-- Seconds_Behind_Source: 0        ← Replication lag in seconds (0 = caught up)
-- Source_Log_File: mysql-binlog.000042
-- Read_Source_Log_Pos: 194732841  ← How far I/O thread has read
-- Relay_Log_File: relay-bin.000018
-- Relay_Log_Pos: 4               ← How far SQL thread has applied
-- Last_Error:                     ← Empty = no current error ✓
```

## Section 2: The Binary Log (binlog)

**Q2. What is the binary log — what does it record and how is it structured?**

A: The binary log is MySQL's ordered, durable record of every change made to the database. It is the replication source of truth — replicas stream it and re-apply it. It also enables point-in-time recovery (PITR):

```
Binlog physical structure:

  mysql-binlog.000001  (first file — rotated when size limit or FLUSH LOGS)
  mysql-binlog.000002
  mysql-binlog.000042  (current file)

  Each binlog file:
  ┌──────────────────────────────────────────────────────┐
  │ File header (magic number + format description event) │
  ├──────────────────────────────────────────────────────┤
  │ Event 1: Format Description Event (FDE)               │
  │   timestamp, server_id, binlog_version                │
  ├──────────────────────────────────────────────────────┤
  │ Event 2: GTID event (if GTID mode)                    │
  │   server_uuid:transaction_id                          │
  ├──────────────────────────────────────────────────────┤
  │ Event 3: Query event (BEGIN)                          │
  ├──────────────────────────────────────────────────────┤
  │ Event 4: Table Map event (identifies the table)       │
  │   db: myapp, table: orders, column types              │
  ├──────────────────────────────────────────────────────┤
  │ Event 5: Write Rows event (ROW format INSERT)         │
  │   before_image: NULL (insert has no before)           │
  │   after_image: {id:42, user_id:1, total:99.99, ...}  │
  ├──────────────────────────────────────────────────────┤
  │ Event 6: Xid event (COMMIT, transaction ID)           │
  └──────────────────────────────────────────────────────┘
```

```sql
-- ── Inspecting binlog contents ────────────────────────────────────────────────
-- List binlog files:
SHOW BINARY LOGS;
-- Log_name              │ File_size │ Encrypted
-- ──────────────────────┼───────────┼──────────
-- mysql-binlog.000040   │ 1073741895│ No
-- mysql-binlog.000041   │ 1073741903│ No
-- mysql-binlog.000042   │  194732841│ No        ← current

-- Read binlog events:
SHOW BINLOG EVENTS IN 'mysql-binlog.000042' LIMIT 20;
-- Log_name            │ Pos │ Event_type    │ End_log_pos │ Info
-- ────────────────────┼─────┼───────────────┼─────────────┼──────────────────
-- mysql-binlog.000042 │   4 │ Format_desc   │         126 │ Server ver: 8.0.33
-- mysql-binlog.000042 │ 126 │ Previous_gtids│         197 │ a1b2...:1-9820
-- mysql-binlog.000042 │ 197 │ Gtid          │         276 │ SET @@SESSION.GTID_NEXT= 'a1b2...:9821'
-- mysql-binlog.000042 │ 276 │ Query         │         352 │ BEGIN
-- mysql-binlog.000042 │ 352 │ Table_map     │         421 │ table_id: 89 (myapp.orders)
-- mysql-binlog.000042 │ 421 │ Write_rows    │         509 │ table_id: 89 flags: STMT_END_F
-- mysql-binlog.000042 │ 509 │ Xid           │         540 │ COMMIT /* xid=1234 */

-- Command-line tool (more readable output):
-- mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-binlog.000042

-- ── Binlog configuration ──────────────────────────────────────────────────────
-- In my.cnf (must be set on the primary):
-- [mysqld]
-- log_bin = mysql-binlog            -- Enable binlog, set base filename
-- binlog_format = ROW               -- STATEMENT | ROW | MIXED (see Q3)
-- server_id = 1                     -- Unique ID (required for replication)
-- binlog_expire_logs_seconds = 604800  -- Keep binlogs for 7 days (MySQL 8.0)
-- max_binlog_size = 1G              -- Rotate when file reaches this size
-- sync_binlog = 1                   -- Flush to disk after every transaction (durability)
-- innodb_flush_log_at_trx_commit = 1 -- InnoDB redo log flush (pairs with sync_binlog)

-- ── sync_binlog and durability ────────────────────────────────────────────────
-- sync_binlog = 0: OS decides when to flush. Fast, but binlog can be lost on crash.
-- sync_binlog = 1: Flush after EVERY transaction. Slowest, safest. Recommended for primary.
-- sync_binlog = N: Flush after N transactions. Balance between speed and durability.

-- With sync_binlog=1 AND innodb_flush_log_at_trx_commit=1:
-- → Transactions are durable: committed data survives any crash.
-- → This is the "gold standard" configuration for a primary.
-- → Trade-off: each write requires a disk sync (~1-5ms on spinning disk, <1ms on SSD).
```

**Q3. What are the three binlog formats — what are the exact trade-offs between `STATEMENT`, `ROW`, and `MIXED`?**

A: The binlog format controls what information is recorded for each change. The choice profoundly affects replication correctness, binlog size, and the ability to use point-in-time recovery:

```sql
-- ── STATEMENT format ──────────────────────────────────────────────────────────
-- Records the EXACT SQL statement that was executed.
-- Replicas re-execute the same SQL.

SET binlog_format = STATEMENT;
UPDATE orders SET updated_at = NOW() WHERE user_id = 42;

-- Binlog contains:
-- Query: UPDATE orders SET updated_at = NOW() WHERE user_id = 42

-- On replica: re-executes this exact SQL.
-- Problem: NOW() on the replica returns a DIFFERENT time than on the primary.
-- Result: updated_at differs between primary and replica → DATA DIVERGENCE.

-- Other non-deterministic functions that break STATEMENT replication:
-- UUID(), RAND(), USER(), FOUND_ROWS(), LOAD_FILE(), sysdate()
-- Any function that returns different values at different times or on different hosts.

-- When STATEMENT is safe:
-- ✓ Pure deterministic SQL: UPDATE orders SET status = 'shipped' WHERE id = ?
-- ✓ Simple INSERTs and DELETEs without non-deterministic functions
-- ✓ DDL statements (always replicated as statements regardless of format)

-- Advantages of STATEMENT:
-- ✓ Compact binlog: stores SQL text, not row data. One UPDATE affecting 1M rows
--   is one binlog event vs 1M row events in ROW format.
-- ✓ Human-readable: easy to inspect with mysqlbinlog
-- ✗ Non-deterministic functions cause data divergence
-- ✗ Some statements are explicitly "unsafe" (MySQL warns/errors)

-- ── ROW format (recommended default) ──────────────────────────────────────────
-- Records the BEFORE and AFTER image of each modified row.
-- Replicas apply the exact row changes — no SQL re-execution.

SET binlog_format = ROW;
UPDATE orders SET updated_at = NOW() WHERE user_id = 42;

-- Binlog contains (for each of the 47 rows matching user_id=42):
-- Table_map: myapp.orders
-- Update_rows:
--   before: {id:101, user_id:42, updated_at: 2024-01-15 09:00:00}
--   after:  {id:101, user_id:42, updated_at: 2024-01-15 10:30:45}  ← exact value
--   before: {id:203, user_id:42, updated_at: 2024-01-14 08:15:00}
--   after:  {id:203, user_id:42, updated_at: 2024-01-15 10:30:45}
--   ... (one entry per row)

-- Advantages of ROW:
-- ✓ Deterministic: exact row values replicated, no function re-evaluation
-- ✓ Correct for all SQL patterns (triggers, stored procedures, non-deterministic functions)
-- ✓ Enables row-based conflict detection in multi-primary topologies
-- ✓ Required for most CDC (Change Data Capture) tools: Debezium, Maxwell, etc.
-- ✗ Binlog is much larger: 1M-row UPDATE = 1M row events
-- ✗ Difficult to read with mysqlbinlog without --verbose flag
-- ✗ More I/O on both primary (writing) and replica (reading and applying)

-- ── MIXED format ──────────────────────────────────────────────────────────────
-- Uses STATEMENT by default; automatically switches to ROW for unsafe statements.
SET binlog_format = MIXED;
-- Safe statements → STATEMENT format (compact)
-- Unsafe statements → ROW format (correct)

-- MySQL detects "unsafe" patterns and switches automatically:
-- • Non-deterministic functions (UUID, NOW, RAND, USER...)
-- • Statements with LIMIT (ordering may differ between servers)
-- • INSERT INTO ... SELECT from tables with AUTO_INCREMENT
-- • User-defined functions (UDFs)
-- • Stored procedures that contain any unsafe statement

-- Trade-off vs pure ROW:
-- ✓ Smaller binlog for safe statements
-- ✗ Harder to predict which format is used in which transaction
-- ✗ CDC tools may not handle MIXED format well (prefer ROW for CDC)

-- ── binlog_row_image: controlling ROW format verbosity ───────────────────────
-- Controls which columns appear in the before/after row image:
-- binlog_row_image = FULL (default):
--   Records ALL columns in before and after image.
--   Safe, but large. Required for most CDC tools.
-- binlog_row_image = MINIMAL:
--   Before image: only the columns needed to identify the row (PK + changed cols).
--   After image: only the columns that changed.
--   Smaller binlog. May break some CDC tools.
-- binlog_row_image = NOBLOB:
--   Like FULL but excludes BLOB/TEXT columns if they didn't change.
--   Good middle ground for tables with large BLOB columns.

-- ── Checking current binlog format ────────────────────────────────────────────
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';
SHOW VARIABLES LIKE 'sync_binlog';
```

## Section 3: How Replication Works Physically

**Q4. Walk through the complete replication mechanism — what are the I/O thread, SQL thread, and relay log?**

A: MySQL replication is a three-step pipeline. Each step has its own thread and its own failure mode. Understanding the pipeline explains why replica lag has two independent components:

```
Complete replication pipeline:

  PRIMARY server                        REPLICA server
  ┌─────────────────────────┐           ┌──────────────────────────────────────┐
  │  Client writes          │           │                                      │
  │  BEGIN                  │           │  ┌──────────┐      ┌─────────────┐  │
  │  INSERT INTO orders ... │           │  │ I/O      │      │ SQL Thread  │  │
  │  COMMIT                 │           │  │ Thread   │      │             │  │
  │         │               │           │  │          │      │             │  │
  │  ┌──────▼─────────────┐ │           │  │ Connects │      │ Reads relay │  │
  │  │    binlog writer   │ │  binlog   │  │ to       │      │ log and     │  │
  │  │                    │─┼──events──►│  │ primary  │      │ applies     │  │
  │  │ mysql-binlog.000042│ │           │  │ I/O      │      │ each event  │  │
  │  └────────────────────┘ │           │  │          │  ┌───│ to replica  │  │
  │                         │           │  │ Writes   │  │   │ database    │  │
  │  ┌──────────────────┐   │           │  │ events   │  │   │             │  │
  │  │   Binlog dump    │   │           │  │ to relay │  │   │ Executes    │  │
  │  │   thread (one    │◄──┼───────────┤  │ log      │  │   │ transactions│  │
  │  │   per replica)   │   │           │  └──────────┘  │   │ in order    │  │
  │  └──────────────────┘   │           │       │        │   └─────────────┘  │
  └─────────────────────────┘           │       ▼        │                    │
                                        │  ┌─────────────▼─────────┐         │
                                        │  │  Relay Log              │         │
                                        │  │  relay-bin.000018       │         │
                                        │  │  (local copy of primary │         │
                                        │  │   binlog events)        │         │
                                        │  └─────────────────────────┘         │
                                        └──────────────────────────────────────┘

Step 1: I/O Thread (on replica)
  • Connects to primary using a replication user (REPLICATION SLAVE privilege).
  • Requests binlog events starting from a specific file+position (or GTID).
  • Primary's binlog dump thread sends events as they are committed.
  • I/O thread writes events to the relay log (local file on replica disk).
  • If primary is unavailable: I/O thread retries with exponential backoff.

Step 2: Relay Log (on replica disk)
  • Buffer between I/O thread (network speed) and SQL thread (apply speed).
  • If the SQL thread is slow: relay log grows (disk usage concern).
  • If I/O thread falls behind: Seconds_Behind_Source increases from network lag.
  • relay-log-space-limit: cap relay log total size (pause I/O thread if exceeded).

Step 3: SQL Thread (on replica)
  • Reads events from relay log.
  • Applies each event to the replica's database in the exact order received.
  • Single-threaded by default → bottleneck for high-write primaries.
  • Multi-threaded replica (MTR): parallel apply across schemas or transactions.
```

```sql
-- ── Setting up replication (MySQL 8.0+, GTID mode) ────────────────────────────

-- On PRIMARY:
-- 1. Create replication user:
CREATE USER 'replicator'@'%'
    IDENTIFIED WITH caching_sha2_password BY 'strong-password';
GRANT REPLICATION SLAVE ON *.* TO 'replicator'@'%';
FLUSH PRIVILEGES;

-- 2. Take a consistent backup (for initial data load):
-- mysqldump --single-transaction --master-data=2 --all-databases > dump.sql
-- OR: clone plugin (MySQL 8.0.17+):
-- INSTALL PLUGIN clone SONAME 'mysql_clone.so';

-- On REPLICA:
-- 1. Restore the backup.
-- 2. Configure replication source:
CHANGE REPLICATION SOURCE TO               -- MySQL 8.0.23+ syntax
    SOURCE_HOST     = 'primary-host',
    SOURCE_PORT     = 3306,
    SOURCE_USER     = 'replicator',
    SOURCE_PASSWORD = 'strong-password',
    SOURCE_AUTO_POSITION = 1,              -- Use GTID (not file+position)
    GET_SOURCE_PUBLIC_KEY = 1,             -- For caching_sha2_password
    SOURCE_CONNECTION_AUTO_FAILOVER = 1;  -- Auto-failover (MySQL 8.0.22+)

-- 3. Start replication:
START REPLICA;

-- 4. Monitor:
SHOW REPLICA STATUS\G

-- ── Multi-threaded replication (MTR) ─────────────────────────────────────────
-- Single SQL thread is a common bottleneck on write-heavy primaries.
-- Enable parallel apply:

-- In my.cnf on replica:
-- replica_parallel_workers = 8         -- Number of parallel apply workers
-- replica_parallel_type = LOGICAL_CLOCK -- Apply non-conflicting transactions in parallel
--                                        -- LOGICAL_CLOCK = based on binlog group commit
--                                        -- DATABASE = parallel per schema (simpler, less parallel)
-- replica_preserve_commit_order = ON    -- Maintain commit order on replica (required for
--                                          consistent reads, slight throughput cost)

-- LOGICAL_CLOCK parallelism:
-- If two transactions on the primary committed in the same binlog "group commit",
-- they touched different rows → safe to apply in parallel on the replica.
-- This is determined by the last_committed and sequence_number fields in each GTID event.

-- ── Monitoring the replication threads ────────────────────────────────────────
-- Show all replication threads:
SELECT
    id,
    user,
    host,
    db,
    command,
    state,
    LEFT(info, 100) AS query
FROM   information_schema.processlist
WHERE  command IN ('Binlog Dump GTID', 'Slave_IO', 'Slave_SQL',
                   'Replica_IO', 'Replica_SQL')
ORDER  BY command;
```

## Section 4: GTID-Based Replication

**Q5. What is a GTID — how does GTID replication differ fundamentally from file-position-based replication?**

A: A Global Transaction Identifier (GTID) is a unique, globally stable identifier assigned to every committed transaction. It makes the replication position independent of file names and byte offsets, which eliminates an entire class of failover complexity:

```
File-position-based replication (old model):

  Primary binlog state:
    File:     mysql-binlog.000042
    Position: 194732841

  Replica tracks:
    Read from: mysql-binlog.000042 at position 194732841

  Failover problem:
    Primary crashes at position 194732841.
    New primary (was Replica A) has:
      File:     mysql-binlog.000001  ← completely different filename!
      Position: 847392              ← completely different position!
    You CANNOT tell Replica B to switch to the new primary because
    the new primary's binlog file and position have no mapping to the old primary's.
    Manual intervention required: calculate offset, risk skipping or duplicating events.

GTID-based replication (modern model):

  Every committed transaction gets a GTID:
    Format: server_uuid:transaction_number
    Example: a1b2c3d4-e5f6-7890-abcd-ef1234567890:9821

  Primary GTID state (executed_gtid_set):
    a1b2c3d4-...:1-9821   ← "I have applied GTIDs 1 through 9821 from server a1b2..."

  Replica tracks:
    Retrieved_Gtid_Set:  a1b2c3d4-...:1-9821  ← received from primary
    Executed_Gtid_Set:   a1b2c3d4-...:1-9821  ← applied to replica DB

  Failover with GTID:
    Primary (a1b2c3d4) crashes after GTID :9821.
    Replica A (b3c4d5e6) is promoted as new primary.
    Replica A has applied GTIDs: a1b2c3d4-...:1-9821 (same as old primary).
    Replica B knows it has applied: a1b2c3d4-...:1-9818 (3 GTIDs behind).
    Replica B tells new primary: "give me everything after 1-9818"
    → New primary sends GTIDs :9819, :9820, :9821 → Replica B catches up.
    → No file/position calculation. GTID handles it automatically. ✓
```

```sql
-- ── GTID configuration (my.cnf) ───────────────────────────────────────────────
-- [mysqld]
-- gtid_mode = ON                    -- Enable GTID mode (OFF → ON_PERMISSIVE → ON)
-- enforce_gtid_consistency = ON     -- Reject statements incompatible with GTIDs
-- log_bin = mysql-binlog            -- binlog required for GTIDs
-- server_id = 1                     -- Unique per server in the topology

-- ── Enabling GTID on a running system (online, no downtime in MySQL 8.0) ──────
-- Step 1: Enable permissive mode (accepts both GTID and non-GTID transactions):
SET @@GLOBAL.ENFORCE_GTID_CONSISTENCY = WARN;      -- Log warnings
SET @@GLOBAL.ENFORCE_GTID_CONSISTENCY = ON;         -- Reject unsafe statements
SET @@GLOBAL.GTID_MODE = OFF_PERMISSIVE;            -- Old tx: no GTID, new tx: optional
-- Step 2: Wait for all replicas to apply all non-GTID transactions.
SET @@GLOBAL.GTID_MODE = ON_PERMISSIVE;             -- New tx: always GTID
-- Step 3: Confirm no non-GTID transactions in flight:
SHOW VARIABLES LIKE 'ONGOING_ANONYMOUS_TRANSACTION_COUNT';
-- → 0: safe to proceed
SET @@GLOBAL.GTID_MODE = ON;                        -- Full GTID mode

-- ── GTID-related variables and functions ──────────────────────────────────────
-- The GTID set the primary has executed:
SELECT @@GLOBAL.GTID_EXECUTED;
-- → a1b2c3d4-e5f6-7890-abcd-ef1234567890:1-9821

-- The GTID set purged from binlog (too old to be on disk):
SELECT @@GLOBAL.GTID_PURGED;
-- → a1b2c3d4-...:1-4500   (GTIDs 1-4500 are gone, purged from disk)

-- Check if a replica has caught up:
-- On replica:
SELECT GTID_SUBSET(
    'a1b2c3d4-...:1-9821',   -- GTIDs on primary
    @@GLOBAL.GTID_EXECUTED   -- GTIDs on this replica
);
-- → 1 (TRUE): replica has applied all primary GTIDs ✓
-- → 0 (FALSE): replica is behind

-- Wait for replica to catch up to a specific GTID (application-level use):
SELECT WAIT_FOR_EXECUTED_GTID_SET('a1b2c3d4-...:9821', 5.0);
-- → Returns 0 if GTID 9821 is applied within 5 seconds
-- → Returns 1 if timeout exceeded
-- Use case: after a write on primary, ensure a read on a specific replica sees it.

-- ── Statements incompatible with GTID (enforce_gtid_consistency blocks these) ──
-- CREATE TABLE ... SELECT ...:  creates a table and inserts from a query in one statement.
--   Problem: this is TWO operations (DDL + DML) which cannot be a single atomic GTID.
--   Fix: split into CREATE TABLE + INSERT INTO ... SELECT ...

-- CREATE/DROP TEMPORARY TABLE inside a transaction:
--   Temporary table DDL is not replicated; creates non-determinism.
--   Fix: use regular tables or move temp table creation outside transactions.

-- UPDATE/INSERT on transactional + non-transactional tables in one transaction:
--   Non-transactional tables (MyISAM) commit immediately; cannot be rolled back.
--   Fix: use InnoDB for all tables; avoid mixing storage engines.

-- ── GTID and point-in-time recovery ────────────────────────────────────────────
-- Restore from backup, then apply binlog events from a specific GTID forward:
-- mysqlbinlog --include-gtids="a1b2c3d4-...:9000-9821" mysql-binlog.* | mysql

-- Skip a specific GTID (e.g., a transaction that caused an error on replica):
SET GTID_NEXT = 'a1b2c3d4-...:9821';
BEGIN; COMMIT;   -- Empty transaction "consumes" this GTID without doing anything
SET GTID_NEXT = 'AUTOMATIC';
START REPLICA;
-- This effectively tells MySQL: "I acknowledge GTID 9821 — skip it."
-- USE WITH EXTREME CAUTION: skipping transactions causes data divergence.
```

**Q6. What is a GTID set — how are GTIDs represented, merged, and used for replication state?**

A: A GTID set is a compact notation for a collection of GTIDs from multiple servers. It is the complete replication state — more information-dense than a single file+position pair:

```sql
-- ── GTID set notation ─────────────────────────────────────────────────────────
-- Single server, contiguous range:
a1b2c3d4-e5f6-7890-abcd-ef1234567890:1-9821

-- Single server, non-contiguous (e.g., after a skipped transaction):
a1b2c3d4-...:1-9820:9822-10000   -- GTID 9821 was skipped

-- Multiple servers (e.g., after failover or multi-primary):
a1b2c3d4-...:1-9821,             -- Original primary's transactions
b3c4d5e6-...:1-45                -- New primary's own transactions after promotion

-- ── GTID functions ────────────────────────────────────────────────────────────
-- GTID_SUBSET(subset, superset): is every GTID in 'subset' also in 'superset'?
SELECT GTID_SUBSET('a1b2...:1-100', 'a1b2...:1-200');
-- → 1 (TRUE): 1-100 is a subset of 1-200 ✓

-- GTID_UNION(set1, set2): combine two GTID sets:
SELECT GTID_UNION('a1b2...:1-50', 'a1b2...:51-100');
-- → 'a1b2...:1-100'

-- GTID_SUBTRACT(set1, set2): GTIDs in set1 but not in set2 (what's missing):
SELECT GTID_SUBTRACT('a1b2...:1-100', 'a1b2...:1-90');
-- → 'a1b2...:91-100'  (replica is missing these 10 GTIDs)

-- ── Monitoring GTID lag ────────────────────────────────────────────────────────
-- How many transactions is this replica behind?
SELECT
    GTID_SUBTRACT(
        (SELECT @@GLOBAL.GTID_EXECUTED FROM primary_server),   -- primary's GTIDs
        @@GLOBAL.GTID_EXECUTED                                  -- replica's GTIDs
    ) AS missing_gtids;

-- In practice, connect to both servers from your monitoring system:

-- lag_count = count_gtids_in_set(missing)
-- alert if lag_count > 1000  (threshold depends on write rate)

-- ── GTID and mysqldump for replica initialization ──────────────────────────────
-- mysqldump with GTID-consistent backup:
-- mysqldump \
--   --single-transaction \
--   --source-data=2 \          -- Includes CHANGE SOURCE TO ... GTID position
--   --set-gtid-purged=ON \     -- Includes SET @@GLOBAL.GTID_PURGED = '...'
--   --all-databases > dump.sql

-- dump.sql will contain:
-- SET @@GLOBAL.GTID_PURGED='a1b2c3d4-...:1-9821';
-- This tells the new replica: "you have all GTIDs up to 9821 from the backup;
-- start replication from GTID 9822 onwards."

-- ── Multi-primary (Group Replication) GTID semantics ──────────────────────────
-- MySQL Group Replication uses a GROUP_REPLICATION_GROUP_NAME UUID as the
-- GTID source for all group transactions:
-- 00000000-0000-0000-0000-000000000000:1-N  (the group UUID)
-- Individual server UUIDs are used for local (view change) transactions.
-- This allows any node in the group to write while GTIDs remain unique cluster-wide.
```

## Section 5: Read Replicas

**Q7. What consistency guarantees do read replicas provide — how do you handle replica lag in application code?**

A: Read replicas provide eventual consistency — reads may see a state that is slightly behind the primary. For most reads this is acceptable; for reads that must immediately see a recent write, explicit strategies are required:

```
Replica lag and its consequences:

  Time →    0ms      50ms     100ms    150ms
  Primary:  INSERT order #42  COMMIT
  Replica:  [not yet applied] [applying] order #42 visible

  Application reads replica at 60ms:
    SELECT * FROM orders WHERE id = 42  → EMPTY (not yet applied)
    User sees: "Order not found" — but they just created it!
    This is the read-after-write inconsistency problem.

  Causes of replica lag:
  1. Network latency (primary → replica binlog transfer)
  2. SQL thread single-threaded apply (fixed by multi-threaded replication)
  3. Long-running transactions on primary (replica must apply in order)
  4. Large batch operations on primary (one giant transaction)
  5. Heavy read load on replica (SQL thread competes with SELECT queries)
  6. Disk I/O bottleneck on replica (slower than primary)
```

```sql
-- ── Measuring replica lag ──────────────────────────────────────────────────────
-- Method 1: Seconds_Behind_Source (approximate, has caveats):
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: 12   ← This replica is 12 seconds behind the primary
-- Caveat: this measures the timestamp difference between the current event
-- being applied and when it was committed on the primary.
-- It can be 0 even when replica is behind (e.g., when no new events are arriving).

-- Method 2: Heartbeat-based lag (more accurate):
-- The pt-heartbeat tool (Percona Toolkit) inserts a timestamp row every second
-- and measures how long ago the replica last applied it:
-- pt-heartbeat --master-server-id=1 --update --daemonize  (on primary)
-- pt-heartbeat --master-server-id=1 --monitor              (on replica)
-- → Reports: 0.5s lag  (accurate to milliseconds)

-- Method 3: GTID-based lag measurement (most accurate):
-- Compare primary's GTID_EXECUTED with replica's GTID_EXECUTED.
-- Count the number of missing GTIDs (transactions, not seconds).
SELECT
    GTID_SUBTRACT(
        source_gtid_executed,        -- from primary: SELECT @@GLOBAL.GTID_EXECUTED
        @@GLOBAL.GTID_EXECUTED       -- replica's current GTIDs
    ) AS lag_gtids;

-- ── Application strategies for replica lag ────────────────────────────────────

-- Strategy 1: Read-after-write consistency — always read primary after writing
-- The simplest strategy. Only works if the primary can handle the read load.

@Injectable()
export class OrderService {
    constructor(
        private readonly primaryDataSource:  DataSource,  // → primary
        private readonly replicaDataSource:  DataSource,  // → replica
    ) {}

    async createOrder(dto: CreateOrderDto): Promise<Order> {
        // Write goes to primary:
        const order = await this.primaryDataSource
            .getRepository(Order)
            .save(dto);

        // Read-after-write: also read from primary (guaranteed to see the write):
        return this.primaryDataSource
            .getRepository(Order)
            .findOneOrFail({ where: { id: order.id } });
    }

    async listOrders(userId: number): Promise<Order[]> {
        // Non-critical list read → replica (may be slightly stale, acceptable):
        return this.replicaDataSource
            .getRepository(Order)
            .find({ where: { userId }, order: { createdAt: 'DESC' } });
    }
}

-- Strategy 2: GTID-based wait — wait for replica to catch up to a specific point
-- After a write, store the GTID of that write and use it to ensure the replica
-- is up to date before reading.

async createOrderAndReadFromReplica(dto: CreateOrderDto): Promise<Order> {
    // Write to primary and get the GTID:
    const order = await this.primaryDataSource.transaction(async (manager) => {
        return manager.save(Order, dto);
    });

    // Get the GTID of this transaction from the primary:
    const [{ gtid }] = await this.primaryDataSource.query(
        'SELECT @@GLOBAL.GTID_EXECUTED AS gtid'
    );

    // Tell the replica to wait until it has applied this GTID:
    const [{ result }] = await this.replicaDataSource.query(
        'SELECT WAIT_FOR_EXECUTED_GTID_SET(?, 5) AS result',
        [gtid]
    );
    // result = 0: replica caught up ✓
    // result = 1: timeout after 5 seconds → fall back to primary read

    if (result === 1) {
        // Replica too far behind — read from primary:
        return this.primaryDataSource
            .getRepository(Order)
            .findOneOrFail({ where: { id: order.id } });
    }

    // Replica caught up — safe to read from replica:
    return this.replicaDataSource
        .getRepository(Order)
        .findOneOrFail({ where: { id: order.id } });
}

-- Strategy 3: Session tracking / sticky reads
-- After a write, route all subsequent reads in that user session to primary
-- for a fixed time window (e.g., 2 seconds).

@Injectable()
export class RouteDecisionService {
    private primaryUntil = new Map<string, number>(); // userId → timestamp

    stickToPrimary(userId: string, durationMs = 2000): void {
        this.primaryUntil.set(userId, Date.now() + durationMs);
    }

    shouldUsePrimary(userId: string): boolean {
        const expiry = this.primaryUntil.get(userId);
        if (!expiry) return false;
        if (Date.now() > expiry) {
            this.primaryUntil.delete(userId);
            return false;
        }
        return true;
    }

    getDataSource(userId: string): DataSource {
        return this.shouldUsePrimary(userId)
            ? this.primaryDataSource
            : this.replicaDataSource;
    }
}

-- Strategy 4: Replica version check header
-- Client sends the version (GTID or timestamp) they last wrote with.
-- Server checks if the replica is current before responding.
-- Used by ProxySQL and some MySQL connectors (session track GTID).
```

**Q8. What queries belong on a replica — which must always go to the primary?**

A: The routing decision is based on consistency requirements, transaction semantics, and the nature of the operation. Getting this wrong either overloads the primary or returns stale data:

```sql
-- ── ALWAYS route to PRIMARY ────────────────────────────────────────────────────

-- 1. All writes (DML and DDL):
INSERT INTO orders ...;
UPDATE orders SET status = 'shipped' WHERE id = ?;
DELETE FROM sessions WHERE expires_at < NOW();
CREATE INDEX ...; ALTER TABLE ...;

-- 2. Reads inside a write transaction:
BEGIN;
SELECT balance FROM accounts WHERE id = ? FOR UPDATE;  -- Must see the latest value
UPDATE accounts SET balance = balance - 100 WHERE id = ?;
COMMIT;
-- The FOR UPDATE explicitly requires primary; any read inside a write transaction
-- must use the same connection as the write.

-- 3. Read-after-write (when no GTID wait strategy is in place):
-- User just created a record — they expect to see it immediately.
-- Route their next GET request to primary.

-- 4. Admin and monitoring queries:
SHOW PROCESSLIST;
SELECT * FROM information_schema.INNODB_TRX;
SELECT @@GLOBAL.GTID_EXECUTED;
-- These should never go to a replica.

-- 5. Queries requiring up-to-the-millisecond accuracy:
-- Financial balances, inventory counts, seat availability.
-- Even 1 second of lag can cause double-booking or overselling.

-- ── SAFE to route to REPLICA ──────────────────────────────────────────────────

-- 1. Reporting and analytics queries (tolerate minutes of lag):
SELECT
    DATE(created_at)   AS date,
    status,
    SUM(total)         AS revenue,
    COUNT(*)           AS order_count
FROM   orders
WHERE  created_at > NOW() - INTERVAL 30 DAY
GROUP  BY DATE(created_at), status
ORDER  BY date DESC;
-- If this is 30 seconds behind, the report is still useful.
-- And it won't block primary writes during its long runtime.

-- 2. Background job reads that don't need the latest data:
SELECT id FROM users WHERE last_login_at < NOW() - INTERVAL 90 DAY;
-- A list of inactive users for a cleanup job — a few seconds of lag is irrelevant.

-- 3. Search and autocomplete:
SELECT name, id FROM products WHERE name LIKE ? LIMIT 10;
-- 1-2 seconds of lag in search results is imperceptible to users.

-- 4. Public/anonymous content:
SELECT title, content, published_at FROM posts
WHERE  published_at < NOW()
ORDER  BY published_at DESC LIMIT 20;
-- Blog posts visible to everyone — slight staleness is fine.

-- 5. Aggregates used for display (not business logic):
SELECT COUNT(*) FROM orders WHERE status = 'pending';
-- Dashboard widget — approximate count is sufficient.

-- ── Gray area: route to replica with awareness of lag ─────────────────────────

-- User profile reads after the user just updated their profile:
SELECT * FROM users WHERE id = ?;
-- If the user just updated their email, routing to replica may show old email.
-- Solution: use session stickiness (route to primary for 2s after any write).

-- Inventory reads before checkout:
SELECT stock FROM products WHERE id = ?;
-- If slightly stale, the final INSERT into orders (which goes to primary)
-- will catch the actual constraint violation. The replica read is an optimistic
-- pre-check, not the final enforcement.
```

## Section 6: Semi-Synchronous Replication

**Q9. What is semi-synchronous replication — how does it change the durability guarantees and performance trade-offs?**

A: Standard MySQL replication is fully asynchronous — the primary commits and responds to the client before any replica has received the data. Semi-synchronous replication requires at least one replica to acknowledge receipt before the primary responds:

```
Three replication durability levels:

  Asynchronous (default):
  Client → PRIMARY commit → Client receives "OK"
                ↓ (some time later)
  PRIMARY → Replica (no acknowledgement required)
  Risk: Primary crashes after commit, before replica receives the event
        → Data loss: committed transaction is gone forever.
  Benefit: Zero write latency penalty.

  Semi-synchronous (rpl_semi_sync):
  Client → PRIMARY commit → PRIMARY waits for ≥1 replica ACK → Client receives "OK"
                                    ↓ (simultaneous)
                             PRIMARY → Replica → relay log written → ACK sent
  Risk: NO data loss if at least 1 replica acknowledged.
        If replica crashes: falls back to async (configurable timeout).
  Benefit: At-most-once data loss. ~2-5ms additional write latency.

  Fully synchronous (MySQL Group Replication with quorum):
  Client → PRIMARY → ALL replicas commit → Client receives "OK"
  Risk: None (quorum commit = data safe on majority of nodes).
  Benefit: Zero data loss (strong consistency).
  Cost: Write latency = max(all replica commit times). High latency.
```

```sql
-- ── Configuring semi-synchronous replication (MySQL 8.0+) ─────────────────────
-- On PRIMARY (my.cnf):
-- plugin_load_add = 'rpl_semi_sync_source=semisync_source.so'
-- rpl_semi_sync_source_enabled = ON
-- rpl_semi_sync_source_wait_for_replica_count = 1   -- Wait for 1 replica ACK
-- rpl_semi_sync_source_timeout = 1000               -- Fall back to async after 1000ms

-- On REPLICA (my.cnf):
-- plugin_load_add = 'rpl_semi_sync_replica=semisync_replica.so'
-- rpl_semi_sync_replica_enabled = ON

-- Runtime enable:
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = ON;
SET GLOBAL rpl_semi_sync_source_wait_for_replica_count = 1;
SET GLOBAL rpl_semi_sync_source_timeout = 1000;  -- ms

-- ── Monitoring semi-sync state ─────────────────────────────────────────────────
SHOW STATUS LIKE 'Rpl_semi_sync%';
-- Rpl_semi_sync_source_clients:             1      ← replicas in semi-sync mode
-- Rpl_semi_sync_source_net_avg_wait_time:   1823   ← avg μs waiting for ACK
-- Rpl_semi_sync_source_no_tx:               0      ← txns that got NO ACK (async fallback)
-- Rpl_semi_sync_source_yes_tx:              9821   ← txns that got ACK (semi-sync)
-- Rpl_semi_sync_source_status:              ON     ← currently in semi-sync mode

-- Rpl_semi_sync_source_no_tx > 0:
-- Transactions that fell back to async (replica was too slow or unavailable).
-- These transactions have NO guarantee of reaching any replica before primary crash.
-- Alert on this metric if zero data loss is a requirement.

-- ── AFTER_SYNC vs AFTER_COMMIT ─────────────────────────────────────────────────
-- rpl_semi_sync_source_wait_point = AFTER_SYNC (default, MySQL 5.7.2+):
--   PRIMARY writes to binlog → sends to replica → waits for ACK
--   → THEN commits to InnoDB → responds to client.
--   The transaction is in primary's binlog BEFORE InnoDB commit.
--   If primary crashes after replica ACKs but before InnoDB commit:
--   Primary loses the transaction; replica has it.
--   On promotion: replica has a transaction the dead primary never committed.
--   Fix: failover tools (Orchestrator, MySQL Router) handle this.

-- rpl_semi_sync_source_wait_point = AFTER_COMMIT (older behavior):
--   PRIMARY commits to InnoDB → sends to replica → waits for ACK → responds to client.
--   Phantom read problem: between InnoDB commit and replica ACK, OTHER sessions on
--   primary can see the committed data, but the replica hasn't received it yet.
--   AFTER_SYNC avoids this phantom; AFTER_SYNC is strongly preferred.

-- ── When to use semi-synchronous ──────────────────────────────────────────────
-- Use semi-sync when:
--   • You need zero data loss on primary failure (financial, healthcare)
--   • Write latency of 1-5ms is acceptable
--   • You have a geographically close replica (cross-region = 50-200ms latency)

-- Use async when:
--   • Write performance is critical
--   • Some data loss on failure is acceptable (analytics, logging)
--   • Replica is geographically distant (semi-sync latency would be prohibitive)
```

## Section 7: PostgreSQL Replication Comparison

**Q10. How does PostgreSQL replication differ from MySQL binlog replication — what is WAL-based streaming replication?**

A: PostgreSQL uses its Write-Ahead Log (WAL) as the replication source instead of a binlog. The fundamental mechanism is similar but the implementation details differ in important ways — particularly around logical vs physical replication:

```
MySQL vs PostgreSQL replication comparison:

  MySQL (binlog):                        PostgreSQL (WAL):
  ┌────────────────────────────┐         ┌────────────────────────────┐
  │ binlog (logical changes)   │         │ WAL (physical changes)     │
  │   INSERT/UPDATE/DELETE     │         │   page-level byte changes  │
  │   ROW or STATEMENT format  │         │   always physical          │
  │   separate from redo log   │         │   IS the crash-recovery log│
  └────────────────────────────┘         └────────────────────────────┘
  Replica receives SQL or row images     Replica receives page patches
  Replica re-executes or applies rows    Replica applies page changes

  PostgreSQL Physical (Streaming) Replication:
  • Replica receives raw WAL bytes — identical to crash recovery.
  • Replica is a byte-for-byte copy of the primary.
  • Replica is in recovery mode (standby) — READ ONLY.
  • Cannot have different indexes, schema, or data from primary.
  • Very fast: one WAL stream, no SQL parsing.
  • Hot standby: replica accepts read-only queries while in recovery.

  PostgreSQL Logical Replication (pg_logical / built-in since PG 10):
  • Replica receives logical changes (row-level changes decoded from WAL).
  • Replica can have different indexes, table structure, data types.
  • Can replicate specific tables (not entire database).
  • Supports cross-version replication (PG 14 primary → PG 16 replica).
  • Used for: zero-downtime upgrades, selective replication, ETL.
```

```sql
-- ── PostgreSQL streaming replication setup ────────────────────────────────────

-- postgresql.conf (primary):
-- wal_level = replica               -- Minimum for replication (logical for logical replication)
-- max_wal_senders = 10              -- Max concurrent replica connections
-- wal_keep_size = 1GB               -- Keep 1GB of WAL for lagging replicas
-- synchronous_standby_names = ''    -- '' = async; 'replica1' = sync with that replica
-- archive_mode = on                 -- Enable WAL archiving (for PITR + pg_basebackup)
-- archive_command = 'cp %p /mnt/wal-archive/%f'  -- Archive WAL files

-- pg_hba.conf (primary):
-- host replication replicator 10.0.0.0/24 scram-sha-256

-- On primary: create replication user:
CREATE USER replicator REPLICATION LOGIN PASSWORD 'strong-password';

-- On replica: take a base backup and start streaming:
-- pg_basebackup \
--   -h primary-host \
--   -U replicator \
--   -D /var/lib/postgresql/data \
--   -P -Xs -R   (-R writes recovery.conf / postgresql.auto.conf for standby)
-- The -R flag creates:
-- primary_conninfo = 'host=primary-host user=replicator'
-- in postgresql.auto.conf, enabling streaming automatically on replica start.

-- ── Monitoring PostgreSQL replication ─────────────────────────────────────────
-- On primary: view replication lag per replica:
SELECT
    application_name,
    client_addr,
    state,                     -- streaming | catchup | backup | startup
    sent_lsn,                  -- WAL position sent to this replica
    write_lsn,                 -- WAL written to replica disk
    flush_lsn,                 -- WAL flushed to replica disk (durable)
    replay_lsn,                -- WAL applied to replica's database
    write_lag,                 -- Time between primary commit and replica write
    flush_lag,                 -- Time between primary commit and replica flush
    replay_lag,                -- Time between primary commit and replica apply
    sync_state                 -- async | sync | potential | quorum
FROM   pg_stat_replication;

-- replay_lag is the equivalent of MySQL's Seconds_Behind_Source.
-- flush_lag = 0: replica has durably flushed → safe for failover (no data loss).

-- Replica's own view of its lag:
SELECT
    now() - pg_last_xact_replay_timestamp() AS replication_lag;
-- → interval '00:00:02.3'  (2.3 seconds behind primary)

-- ── PostgreSQL synchronous replication ────────────────────────────────────────
-- postgresql.conf (primary):
-- synchronous_standby_names = 'FIRST 1 (replica1, replica2)'
-- Meaning: wait for at least 1 of (replica1, replica2) to flush WAL before committing.
-- FIRST 1: the first one to respond is sufficient.
-- ANY 1: same as FIRST 1 for 1 replica.
-- FIRST 2 (r1, r2, r3): wait for 2 of the 3 listed replicas (quorum).

-- synchronous_commit settings (per transaction or globally):
SET synchronous_commit = remote_write;   -- Wait for replica to write (not flush)
SET synchronous_commit = remote_apply;   -- Wait for replica to APPLY (readable on replica)
SET synchronous_commit = on;            -- Wait for primary flush only (default)
SET synchronous_commit = off;           -- Async (risk losing ~wal_writer_delay of txns)
-- remote_apply is the strongest: after commit, data is immediately readable
-- on synchronous replicas. Strongest consistency guarantee.

-- ── PostgreSQL logical replication ────────────────────────────────────────────
-- Primary: create a publication (what to replicate):
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
-- OR: all tables:
CREATE PUBLICATION pub_all FOR ALL TABLES;

-- Replica: create a subscription (connect to publication):
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=primary-host dbname=myapp user=replicator password=secret'
    PUBLICATION pub_orders;
-- → Starts replicating orders and order_items to this replica.
-- → The replica can have additional tables, indexes, or even different schemas.
-- → Supports cross-version replication.
```

## Section 8: Failover and High Availability

**Q11. How do you promote a replica to primary — what role does GTID play in failover?**

A: Failover is the most dangerous operational event in a replicated system. GTID makes the mechanics safer, but the process still requires careful coordination to avoid data loss, split-brain, and topology inconsistency:

```
Failover process (MySQL GTID-based):

  BEFORE:
    Primary (a1b2...) executed GTIDs 1-9821
    Replica A (c3d4...)  applied GTIDs 1-9820  ← most advanced
    Replica B (e5f6...)  applied GTIDs 1-9818
    Replica C (g7h8...)  applied GTIDs 1-9815  ← furthest behind

  Event: Primary crashes at GTID 9821.

  Step 1: Identify the most advanced replica.
    Replica A applied GTIDs 1-9820 → has the most data → promote this one.
    Orchestrator/MHA identifies this automatically from SHOW REPLICA STATUS.

  Step 2: Apply missing GTIDs from relay logs (if available).
    Replica A may have received GTID 9821 in its relay log even before applying it.
    Apply remaining relay log entries to get to 9821.

  Step 3: Promote Replica A to primary.
    STOP REPLICA;        -- Stop applying relay log (it's now the primary)
    RESET REPLICA ALL;   -- Clear replica configuration (it's now a source)
    -- Replica A is now a primary. Its UUID is c3d4...

  Step 4: Point other replicas at the new primary.
    On Replica B and C:
    STOP REPLICA;
    CHANGE REPLICATION SOURCE TO
        SOURCE_HOST = 'replica-a-host',
        SOURCE_AUTO_POSITION = 1;   -- GTID: automatically finds the right position
    START REPLICA;
    -- B is missing GTIDs 9821-9820 from old primary? No — it's looking for
    -- c3d4...:1-N (new primary's own transactions going forward).
    -- Old primary's GTIDs (a1b2...) are tracked separately.
    -- GTID_AUTO_POSITION handles the merge correctly. ✓

  Step 5: Update application to point to new primary.
    DNS failover, ProxySQL routing update, or Virtual IP (VIP) reassignment.

  AFTER:
    New primary: Replica A (c3d4...) — accepted GTIDs a1b2...:1-9820 from old primary
    Replica B: applied a1b2...:1-9818, now replicating from new primary
    Replica C: applied a1b2...:1-9815, now replicating from new primary
    Missing: a1b2...:9821 (last transaction from old primary before crash)
    → If sync_binlog=1 and rpl_semi_sync were used: this may be safe to skip.
    → If async replication: GTID 9821 is permanently lost (data loss event).
```

## Section 9: Replication Filtering and Specific Use Cases

**Q12. How does replication filtering work — what are the use cases and dangers of partial replication?**

A: Replication filters allow selective replication of specific databases, tables, or events. They are essential for certain architectures but introduce correctness risks if misconfigured:

```sql
-- ── Server-level filters (my.cnf on PRIMARY) ──────────────────────────────────
-- binlog_do_db: only log changes to these databases in the binlog.
-- binlog_ignore_db: exclude these databases from the binlog.

-- DANGER with binlog_do_db:
-- MySQL evaluates binlog_do_db based on the CURRENT DEFAULT DATABASE,
-- not the table's actual database.
-- Example: binlog_do_db = myapp

USE myapp;
INSERT INTO myapp.orders (user_id) VALUES (1);  -- Logged ✓ (default DB = myapp)

USE information_schema;
INSERT INTO myapp.orders (user_id) VALUES (2);  -- NOT LOGGED ✗ (default DB ≠ myapp)
-- This is a well-known gotcha. The fully-qualified table name doesn't matter.
-- Use replicate_* filters on the REPLICA side instead — they check the actual table.

-- ── Replica-side filters (my.cnf on REPLICA) ─────────────────────────────────
-- These are evaluated by the SQL thread AFTER receiving ALL binlog events.
-- They filter what gets applied to the replica's database.

-- replicate_do_db: apply changes only from these databases:
-- replicate_do_db = myapp

-- replicate_ignore_db: ignore changes from these databases:
-- replicate_ignore_db = test, temp_db

-- replicate_do_table: apply changes only to these specific tables:
-- replicate_do_table = myapp.orders, myapp.users

-- replicate_ignore_table: exclude specific tables:
-- replicate_ignore_table = myapp.sessions, myapp.temp_cache

-- replicate_wild_do_table: wildcard patterns:
-- replicate_wild_do_table = myapp.%   -- All tables in myapp

-- replicate_wild_ignore_table:
-- replicate_wild_ignore_table = myapp.cache_%  -- Exclude cache tables

-- ── Use cases for replication filtering ───────────────────────────────────────

-- 1. Dedicated reporting replica (only replicate reporting tables):
-- replicate_do_table = myapp.orders, myapp.users, myapp.products
-- Replica has only the tables needed for reports → smaller footprint.
-- Risk: joins that reference un-replicated tables fail on the replica.

-- 2. Excluding high-write low-value tables from replication:
-- replicate_ignore_table = myapp.sessions, myapp.rate_limit_counters
-- These tables are written millions of times per day but don't need replication.
-- Reduces replication load significantly.
-- Risk: replica's session table is empty — don't route session reads there.

-- 3. Multi-tenant database-per-tenant with selective replication:
-- Replicate only tenant_42's database to their dedicated analytics instance:
-- replicate_do_db = tenant_42
-- replicate_do_db = tenant_43

-- ── Dynamic filter changes (MySQL 8.0) ────────────────────────────────────────
-- Change filters without restarting replica:
STOP REPLICA SQL_THREAD;
CHANGE REPLICATION FILTER
    REPLICATE_DO_TABLE = (myapp.orders, myapp.users),
    REPLICATE_IGNORE_TABLE = (myapp.sessions);
START REPLICA SQL_THREAD;

-- View current filters:
SELECT * FROM performance_schema.replication_applier_filters;
```

## Section 10: Application Layer Patterns

**Q13. How do you implement read/write splitting in a NestJS application — what abstractions prevent scattered routing logic?**

A: Read/write splitting without a clean abstraction leads to `if (isWrite) usePrimary else useReplica` scattered throughout every service. The correct approach centralises routing behind a single DataSource interface:

```typescript
import { Injectable, Scope }               from '@nestjs/common';
import { DataSource, EntityManager }        from 'typeorm';
import { REQUEST }                          from '@nestjs/core';
import { Request }                          from 'express';

// ── DataSource module: two named connections ───────────────────────────────────
@Module({
    imports: [
        TypeOrmModule.forRootAsync({
            name: 'primary',
            useFactory: (config: ConfigService): TypeOrmModuleOptions => ({
                type:     'mysql',
                host:     config.getOrThrow('MYSQL_PRIMARY_HOST'),
                port:     config.get<number>('MYSQL_PRIMARY_PORT', 3306),
                username: config.getOrThrow('MYSQL_USER'),
                password: config.getOrThrow('MYSQL_PASSWORD'),
                database: config.getOrThrow('MYSQL_DATABASE'),
                entities: ['dist/**/*.entity.js'],
                extra: {
                    connectionLimit:   20,
                    connectTimeout:     5_000,
                    decimalNumbers:     true,   // Return DECIMAL as number, not string
                },
            }),
            inject: [ConfigService],
        }),
        TypeOrmModule.forRootAsync({
            name: 'replica',
            useFactory: (config: ConfigService): TypeOrmModuleOptions => ({
                type:     'mysql',
                host:     config.getOrThrow('MYSQL_REPLICA_HOST'),
                port:     config.get<number>('MYSQL_REPLICA_PORT', 3306),
                username: config.getOrThrow('MYSQL_READONLY_USER'),
                password: config.getOrThrow('MYSQL_READONLY_PASSWORD'),
                database: config.getOrThrow('MYSQL_DATABASE'),
                entities: ['dist/**/*.entity.js'],
                extra: { connectionLimit: 40 },  // More connections for reads
            }),
            inject: [ConfigService],
        }),
    ],
})
export class DatabaseModule {}

// ── Smart DataSource router ───────────────────────────────────────────────────
@Injectable()
export class DataSourceRouter {
    constructor(
        @InjectDataSource('primary') private readonly primary: DataSource,
        @InjectDataSource('replica')  private readonly replica:  DataSource,
    ) {}

    // The main API: choose based on write flag or explicit override
    forRead(): DataSource  { return this.replica;  }
    forWrite(): DataSource { return this.primary; }

    // Ensure read-after-write consistency using GTID wait:
    async forReadAfterWrite(primaryGtid: string, timeoutSec = 3): Promise<DataSource> {
        try {
            const [{ result }] = await this.replica.query(
                `SELECT WAIT_FOR_EXECUTED_GTID_SET(?, ?) AS result`,
                [primaryGtid, timeoutSec],
            );
            return result === 0 ? this.replica : this.primary;
        } catch {
            return this.primary; // Fall back to primary on any error
        }
    }

    // Get primary's current GTID after a write (call immediately after commit):
    async getCurrentGtid(): Promise<string> {
        const [{ gtid }] = await this.primary.query(
            'SELECT @@GLOBAL.GTID_EXECUTED AS gtid'
        );
        return gtid as string;
    }
}

// ── Base repository with routing ──────────────────────────────────────────────
@Injectable()
export abstract class RoutedRepository<T> {
    constructor(
        protected readonly router: DataSourceRouter,
        protected readonly entity: EntityTarget<T>,
    ) {}

    protected get readRepo()  { return this.router.forRead().getRepository(this.entity);  }
    protected get writeRepo() { return this.router.forWrite().getRepository(this.entity); }

    protected transaction<R>(work: (manager: EntityManager) => Promise<R>): Promise<R> {
        return this.router.forWrite().transaction(work);
    }
}

// ── Order repository using the base ──────────────────────────────────────────
@Injectable()
export class OrderRepository extends RoutedRepository<Order> {
    constructor(router: DataSourceRouter) {
        super(router, Order);
    }

    // Read: goes to replica automatically
    findByUser(userId: number): Promise<Order[]> {
        return this.readRepo.find({
            where:  { userId },
            order:  { createdAt: 'DESC' },
            take:   50,
        });
    }

    // Write: goes to primary automatically
    async create(dto: CreateOrderDto): Promise<{ order: Order; gtid: string }> {
        const order = await this.writeRepo.save(dto);
        const gtid  = await this.router.getCurrentGtid();
        return { order, gtid };
    }

    // Read-after-write: waits for replica to catch up
    async findAfterCreate(id: number, gtid: string): Promise<Order> {
        const ds = await this.router.forReadAfterWrite(gtid);
        return ds.getRepository(Order).findOneOrFail({ where: { id } });
    }
}

// ── Service using the repository ─────────────────────────────────────────────
@Injectable()
export class OrderService {
    constructor(private readonly orderRepo: OrderRepository) {}

    async createOrder(dto: CreateOrderDto): Promise<Order> {
        const { order, gtid } = await this.orderRepo.create(dto);
        // Immediately after create: wait for replica to catch up, then read from replica:
        return this.orderRepo.findAfterCreate(order.id, gtid);
    }

    async getUserOrders(userId: number): Promise<Order[]> {
        // Stale-read-OK: replica is fine:
        return this.orderRepo.findByUser(userId);
    }
}

// ── Monitoring replication lag from NestJS ────────────────────────────────────
@Injectable()
export class ReplicationMonitorService {
    private readonly logger = new Logger(ReplicationMonitorService.name);

    constructor(
        @InjectDataSource('primary') private readonly primary: DataSource,
        @InjectDataSource('replica')  private readonly replica:  DataSource,
    ) {}

    @Cron('*/30 * * * * *')  // Every 30 seconds
    async checkReplicationLag(): Promise<void> {
        try {
            const [primary] = await this.primary.query(
                'SELECT @@GLOBAL.GTID_EXECUTED AS gtid'
            );
            const [replica] = await this.replica.query(
                'SELECT @@GLOBAL.GTID_EXECUTED AS gtid'
            );
            const [{ missing }] = await this.replica.query(
                `SELECT GTID_SUBTRACT(?, ?) AS missing`,
                [primary.gtid, replica.gtid],
            );

            // Count missing GTIDs (approximate lag in transactions):
            const lagTransactions = missing
                ? missing.split(',').length  // Rough count
                : 0;

            this.logger.log(`Replication lag: ~${lagTransactions} transactions`);

            if (lagTransactions > 1000) {
                this.logger.warn(`HIGH REPLICATION LAG: ${lagTransactions} transactions behind`);
                // Trigger alert (PagerDuty, Slack, etc.)
            }
        } catch (err) {
            this.logger.error('Failed to check replication lag', err);
        }
    }
}
```

## Section 11: Scenario-Based Questions

**Q14. "Replication suddenly stopped — the SQL thread reports an error. Walk through the complete diagnosis and recovery."**

A: A stopped SQL thread is the most common replication emergency. The approach depends on whether the error is a data conflict, a schema mismatch, or a corrupt event:

```sql
-- ── Step 1: Identify the error ────────────────────────────────────────────────
SHOW REPLICA STATUS\G

-- Replica_SQL_Running: No          ← SQL thread stopped
-- Last_SQL_Error: Could not execute Write_rows event on table myapp.orders;
--   Duplicate entry '42' for key 'orders.PRIMARY'
-- Last_SQL_Errno: 1062
-- Relay_Source_Log_File: mysql-binlog.000042
-- Exec_Source_Log_Pos:   194732841
-- Retrieved_Gtid_Set:    a1b2...:1-9821
-- Executed_Gtid_Set:     a1b2...:1-9819  ← stopped at 9819

-- ── Step 2: Understand the error ─────────────────────────────────────────────
-- Error 1062: Duplicate key entry.
-- Replica already has a row with id=42 in orders.
-- Primary sent an INSERT for id=42, but replica already has it.
-- Possible causes:
-- a) Someone inserted directly into the replica (violating read-only principle)
-- b) A previous failover left the replica with data the new primary doesn't know about
-- c) Application accidentally wrote directly to the replica's port

-- ── Step 3: Investigate the conflicting row ───────────────────────────────────
-- On REPLICA: check the conflicting row:
SELECT * FROM orders WHERE id = 42;
-- Check if this row is legitimate or should not be here.

-- On PRIMARY: check the same row:
SELECT * FROM orders WHERE id = 42;
-- Compare. If primary has it → replica has a duplicate. If primary doesn't → replica has a ghost.

-- ── Step 4: Resolution options ────────────────────────────────────────────────

-- Option A: Skip the conflicting event (GTID mode — CAREFUL: causes data divergence)
-- Only do this if you understand what data is being skipped:
STOP REPLICA;
SET GTID_NEXT = 'a1b2c3d4-...:9820';  -- The failed GTID
BEGIN; COMMIT;                          -- Empty transaction to "consume" the GTID
SET GTID_NEXT = 'AUTOMATIC';
START REPLICA;
-- → Replica skips GTID 9820 and continues from 9821.
-- → The INSERT that caused the error is never applied to the replica.
-- → Replica now has different data from primary for row 42.

-- Option B: Fix the data and retry (preferred when data must match):
-- On REPLICA: delete the conflicting row (or update it to match what primary expects):
SET SESSION sql_log_bin = 0;   -- Don't log this fix to replica's own binlog
DELETE FROM orders WHERE id = 42;
SET SESSION sql_log_bin = 1;

START REPLICA;
-- → The INSERT from the primary is now applied successfully (no conflict).
-- → Replica catches up.

-- Option C: Rebuild the replica from a fresh backup (safest for diverged replica):
STOP REPLICA;
RESET REPLICA ALL;
-- Re-take a backup from primary and reinitialize the replica.
-- Used when the replica has significant data divergence or unknown cause.

-- ── Step 5: Prevent recurrence ────────────────────────────────────────────────
-- Make replica read-only (prevents accidental direct writes):
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;   -- Blocks even SUPER users (MySQL 5.7.8+)

-- In my.cnf:
-- read_only = ON
-- super_read_only = ON

-- ── Step 6: Validate data consistency ─────────────────────────────────────────
-- pt-table-checksum (Percona Toolkit): finds rows that differ between primary and replica:
-- pt-table-checksum \
--   --host=primary-host \
--   --replicate=myapp.checksums \
--   --databases=myapp

-- On replica, check results:
SELECT db, tbl, chunk, master_cnt, this_cnt, master_crc, this_crc
FROM   myapp.checksums
WHERE  master_crc <> this_crc OR master_cnt <> this_cnt;
-- Rows returned = tables with data divergence.

-- pt-table-sync: fix diverged tables (use with extreme caution on production):
-- pt-table-sync --execute --sync-to-master replica-host
```

**Q15. "Design the complete replication architecture for a high-traffic, globally distributed SaaS application with zero RPO requirement."**

A: Zero RPO (no data loss on failure) requires synchronous replication for at least one replica. The global distribution adds latency constraints that force a layered architecture:

```
Architecture: zero RPO primary region, eventual consistency across regions

  ┌─────────────────────────────────────────────────────────────────────┐
  │                     US-EAST REGION (primary)                        │
  │                                                                      │
  │  ┌─────────────┐    semi-sync     ┌──────────────────────────────┐  │
  │  │   PRIMARY   │──────────────────►│  HA REPLICA (us-east-2b)   │  │
  │  │ (us-east-2a)│   (<2ms, same    │  hot standby, zero data loss │  │
  │  │             │    AZ group)     │  auto-promote on failure     │  │
  │  └─────┬───────┘                  └──────────────────────────────┘  │
  │        │ async                                                        │
  │        │ replication     ┌──────────────────────────────────────┐    │
  │        └────────────────►│  READ REPLICAS (us-east-2c, 2d)     │    │
  │                          │  multiple instances for read scale   │    │
  │                          └──────────────────────────────────────┘    │
  └──────────────────────────────────────────────────────────────────────┘
           │ async replication (50-200ms latency)
  ┌────────┼────────────────────────────────────────────────────────────┐
  │        ▼              EU-WEST REGION (read replica region)          │
  │  ┌─────────────────────────────────────────────────────────────────┐│
  │  │  EU READ REPLICAS (eu-west-1a, 1b)                             ││
  │  │  Serve EU user reads locally (low latency)                     ││
  │  │  Writes still go to US primary (write amplification trade-off) ││
  │  └─────────────────────────────────────────────────────────────────┘│
  └─────────────────────────────────────────────────────────────────────┘

Design decisions and their rationale:

1. Semi-synchronous replication to HA replica (same availability zone group):
   • RPO = 0: HA replica has ACKed every committed transaction before client sees OK.
   • RTO ≈ 30s: Orchestrator detects failure in 5s, promotes in 25s.
   • Same-AZ group: network latency < 2ms → semi-sync overhead < 2ms per write.
   • If HA replica is unavailable: falls back to async with alert.

2. Async replication to read replicas (same region):
   • Read scale without write latency penalty.
   • Replica lag target: < 500ms (monitored via pt-heartbeat).
   • ProxySQL routes SELECTs to replicas, routes writes to primary.

3. Async replication to EU region:
   • Cross-region latency: 80-120ms.
   • EU reads served locally: EU users see ~5ms read latency vs ~110ms to US.
   • EU writes still go to US primary: ~110ms additional write latency for EU.
   • Trade-off: EU writes are slow. If EU write volume is high, consider:
     a. Multi-primary (Group Replication): both US and EU can write.
        Cost: conflict detection overhead, more complex schema design.
     b. Geographic sharding: EU users' data lives on EU primary.
        Cost: cross-shard queries, complex routing.
```

## Quick Reference Tables

### Binlog Format Comparison

| Feature | STATEMENT | ROW | MIXED |
|---|---|---|---|
| Records | SQL text | Row before/after images | Statement OR row (auto) |
| Non-deterministic functions | ✗ Divergence | ✓ Safe | ✓ Auto-switches to ROW |
| Binlog size | Small (1 event per statement) | Large (1 event per row) | Middle |
| Human readable | ✓ Easy | ✗ Needs `--verbose` | Depends |
| CDC tool support | Limited | ✓ Required | ✗ Difficult |
| DDL replication | As statement | As statement | As statement |
| Stored procedures | ✗ Unsafe | ✓ Safe | ✓ Auto-safe |
| Recommended for | Legacy; read-heavy | **Production default** | Legacy with unsafe stmts |

### Replication Mode Comparison (MySQL vs PostgreSQL)

| Feature | MySQL Binlog | MySQL GTID | PG Streaming (Physical) | PG Logical |
|---|---|---|---|---|
| Position tracking | File + offset | GTID set | LSN (Log Sequence Number) | LSN + publication |
| Failover complexity | High (manual offset calc) | Low (auto-position) | Low (LSN-based) | Medium |
| Cross-version | ✗ Same version only | ✗ Same version | ✗ Same version | ✓ Cross-version |
| Selective tables | Via filter (risky) | Via filter | ✗ All or nothing | ✓ Per-table |
| Replica schema diff | ✗ Must match | ✗ Must match | ✗ Must match | ✓ Can differ |
| Zero data loss mode | Semi-sync | Semi-sync | synchronous_commit=remote_apply | synchronous_commit=remote_apply |
| Built-in HA | Group Replication | Group Replication | Patroni / repmgr (external) | Patroni + logical |

### Replica Lag Strategies

| Strategy | How it works | Best for | Downside |
|---|---|---|---|
| Always read primary | All reads → primary | Critical consistency | Defeats purpose of replicas |
| Read-after-write via sticky session | After write, route reads to primary for N seconds | User-facing write then read | Simple; still uses primary for writes |
| GTID wait (`WAIT_FOR_EXECUTED_GTID_SET`) | Wait for replica to apply specific GTID before reading | Precise read-after-write from replica | Adds latency; timeout fallback needed |
| Accept staleness | Route all reads to replica unconditionally | Reports, analytics, search | Stale reads; not for write-critical data |
| ProxySQL session tracking | ProxySQL tracks write GTID, routes to caught-up replica | Transparent to application | Requires ProxySQL 2.0+ |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise about **ROW format vs STATEMENT format** — ROW records before/after row images and is always deterministic; STATEMENT re-executes SQL and breaks with `NOW()`, `UUID()`, `RAND()`, and any non-deterministic function; ROW format is the correct default for production and is required for CDC tools like Debezium; (2) understanding the **I/O thread → relay log → SQL thread pipeline** and knowing that replication lag has two independent components: network lag (I/O thread falls behind) and apply lag (SQL thread falls behind), and that multi-threaded replication with `replica_parallel_workers` and `LOGICAL_CLOCK` parallelism fixes the second bottleneck; (3) explaining **GTID vs file-position replication** precisely — GTID assigns a globally unique identifier to every committed transaction, making the replication position portable across server crashes and promotions, eliminating the "calculate the offset on the new primary" problem that makes file-position failover error-prone; (4) knowing the **range stop rule for GTID sets**: `GTID_SUBTRACT(primary_gtids, replica_gtids)` gives you exactly which transactions the replica is missing, and `WAIT_FOR_EXECUTED_GTID_SET()` lets an application block until a replica has applied a specific transaction — the mechanism for consistent read-after-write from a replica; (5) understanding **semi-synchronous replication's durability guarantee** — with `AFTER_SYNC` mode, the primary writes to its binlog and waits for at least one replica to acknowledge receipt before responding to the client, meaning no committed transaction is lost even if the primary crashes immediately after the ACK; but the fallback to async when no replica ACKs within the timeout is a silent durability downgrade that must be monitored; (6) knowing that **`read_only = ON` and `super_read_only = ON` are mandatory on replicas** — any direct write to a replica breaks replication (duplicate key errors, data divergence) and is the most common cause of the SQL thread stopping with error 1062; (7) understanding **replication filtering pitfalls** — `binlog_do_db` is evaluated based on the current default database, not the actual table schema, so cross-database queries (using `USE different_db; INSERT INTO filtered_db.table ...`) are silently not logged; replica-side `replicate_do_table` is safer because it checks the actual table name regardless of the current default database; and (8) knowing the **PostgreSQL equivalents** — WAL is both the crash-recovery log and the replication stream (binlog is separate in MySQL); `pg_stat_replication.replay_lag` is the PostgreSQL equivalent of `Seconds_Behind_Source`; `synchronous_commit = remote_apply` is the equivalent of MySQL semi-sync with `AFTER_COMMIT`; and logical replication enables cross-version migration and selective table replication that physical streaming replication cannot do.
