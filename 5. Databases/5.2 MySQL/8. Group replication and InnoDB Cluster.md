## Section 1: Fundamentals

**Q1. What is MySQL Group Replication, what problem does it solve over traditional replication, and what does it guarantee?**
A: Traditional MySQL replication (source-replica) is asynchronous by default — the source commits and returns success to the client before confirming that the replica has received or applied the change. If the source fails immediately after committing, transactions not yet shipped to the replica are lost. Group Replication replaces this model with a distributed consensus protocol that ensures all members of the group agree on the order and outcome of every transaction before it is committed:

```
Traditional Asynchronous Replication — the durability gap:

  Client
    │
    ▼
  Source ──COMMIT──► returns 200 OK to client
    │
    │ (async, may lag seconds or minutes)
    ▼
  Replica

  Failure scenario:
  1. Source commits txn T1
  2. Source crashes before sending binlog event to replica
  3. Replica promotes to new source
  4. T1 is LOST — replica never received it
  5. Client was told "success" — data is gone

Traditional Semi-Synchronous Replication — partial improvement:
  Source waits for ACK from at least 1 replica before committing
  Eliminates data loss on single failure BUT:
  - Only 1 replica must ACK (not a quorum)
  - No automatic failover — manual intervention needed
  - The "1 ACK" replica may not be the one that becomes primary

Group Replication — what it guarantees:
  ┌────────────────────────────────────────────────────────────────┐
  │ Distributed consensus: transaction is committed ONLY when a    │
  │ majority (quorum) of members have certified and agreed on it   │
  │                                                                │
  │ Guarantees:                                                    │
  │  1. No data loss on failure (all committed txns are on        │
  │     majority of nodes)                                         │
  │  2. Automatic primary election (Paxos-based)                  │
  │  3. Conflict detection (write-write conflicts resolved)        │
  │  4. Consistent reads (all members have same committed data)    │
  └────────────────────────────────────────────────────────────────┘
```

```
Group Replication architecture:

  ┌───────────┐     ┌───────────┐     ┌───────────┐
  │  Member 1  │     │  Member 2  │     │  Member 3  │
  │ (Primary)  │────▶│(Secondary)│────▶│(Secondary)│
  │            │◀────│           │◀────│           │
  └─────┬──────┘     └─────┬─────┘     └─────┬─────┘
        │                  │                  │
        └──────────────────┼──────────────────┘
                    Group Communication
                    (Paxos protocol — GCS)
                    Certify → Agree → Apply

  Write path (Single-Primary mode):
  1. Client writes to PRIMARY only
  2. PRIMARY receives transaction
  3. Before commit: broadcasts txn to GROUP via Group Communication System (GCS)
  4. ALL members certify: does this txn conflict with any concurrent txn?
  5. If quorum certifies OK → all members commit in same global order
  6. PRIMARY returns success to client
  7. Secondaries apply the certified transaction in order

  Read path:
  - Reads from PRIMARY: always consistent (just committed)
  - Reads from SECONDARY: eventually consistent (slight replication lag)
```

**Q2. What is the Paxos-based consensus protocol that underpins Group Replication — how does XCom (Group Communication System) work?**
A: Group Replication uses a modified Paxos implementation called XCom (eXtended Communication system) as its Group Communication System (GCS). XCom provides the total ordering guarantee: all members agree on the same global sequence of transactions before any member commits:

```
Paxos consensus — simplified three-phase protocol:

  Goal: all nodes agree on a single value (in GR: the next transaction to apply)

  Phase 1: Prepare
    Proposer (Primary): "I propose txn T1. Will you accept proposals from me?"
    Acceptors (all members): "Yes, I haven't seen a higher-numbered proposal"

  Phase 2: Accept
    Proposer: "Accept value T1 with sequence number N"
    Acceptors: "Accepted"

  Phase 3: Learn
    Once QUORUM (majority) of acceptors accept → value is DECIDED
    All members learn the decided value → commit in the agreed order

  Quorum requirement:
    3-member group: quorum = 2 (majority of 3)
    5-member group: quorum = 3 (majority of 5)
    7-member group: quorum = 4 (majority of 7)
    Maximum group size: 9 members (MySQL Group Replication limit)

  Why quorum prevents split-brain:
    If network partitions into [Member1] and [Member2, Member3]:
    [Member1] alone: 1 vote, quorum=2 → cannot commit → stops accepting writes
    [Member2, Member3]: 2 votes, quorum=2 → has quorum → continues
    No two partitions can both have quorum → only one side commits
    Data consistency preserved even under network partition
```

```
XCom transaction certification — conflict detection:

  The certification process runs BEFORE commit:

  Transaction T1 (on Primary):
    Writes to: rows with PKs (t=orders, pk=42) and (t=users, pk=7)
    Writeset: {orders:42, users:7}

  Transaction T2 (concurrent, on same Primary in Single-Primary mode,
                  or on different Primary in Multi-Primary mode):
    Writes to: rows with PKs (t=orders, pk=42) and (t=products, pk=15)
    Writeset: {orders:42, products:15}

  Conflict detection:
    T1 writeset ∩ T2 writeset = {orders:42} → CONFLICT!
    The transaction that arrived LATER in the global order: ROLLBACK
    Earlier transaction: COMMIT

  No conflict example:
    T3 writeset: {customers:99, payments:55}
    T4 writeset: {customers:100, orders:43}
    T3 ∩ T4 = {} → no conflict → BOTH commit concurrently

  This is OPTIMISTIC CONCURRENCY CONTROL:
    Transactions run speculatively, checked for conflicts at commit time
    Works well when conflicts are rare (most OLTP workloads)
    Works poorly when many transactions touch the same rows (hotspot pattern)
```

```sql
-- Checking Group Replication status:
SELECT * FROM performance_schema.replication_group_members;
-- +---------------------------+--------------------------------------+-----------+-------------+--------------+-------------+
-- | CHANNEL_NAME              | MEMBER_ID                            | MEMBER_HOST| MEMBER_PORT | MEMBER_STATE | MEMBER_ROLE |
-- +---------------------------+--------------------------------------+-----------+-------------+--------------+-------------+
-- | group_replication_applier | aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa | mysql1    |        3306 | ONLINE       | PRIMARY     |
-- | group_replication_applier | bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb | mysql2    |        3306 | ONLINE       | SECONDARY   |
```

## Section 2: Modes of Operation

**Q3. What is Single-Primary mode vs Multi-Primary mode — when do you choose each, and what are the risks of Multi-Primary?**
A: Group Replication supports two topology modes. Single-Primary is the default and recommended mode for almost all workloads. Multi-Primary allows writes to any member simultaneously but introduces significant complexity and constraints:

```
Single-Primary mode (default, recommended):

  Architecture:
    One member is elected PRIMARY → accepts writes
    All other members are SECONDARY → read-only
    Automatic primary election on failure

  Write flow:
    Client → PRIMARY → certify → all members commit → PRIMARY returns OK
    Secondaries: apply certified transactions in global order

  Benefits:
  ✓ Simple: all writes go to one place (no routing complexity for writes)
  ✓ No write-write conflicts (only one writer)
  ✓ Full SQL support — no restrictions on transaction types
  ✓ Predictable behaviour under failure

  Limitations:
  ✗ Write throughput limited to single node capacity
  ✗ Read scalability via secondaries (reads may lag)
  ✗ Failover requires client reconnect to new primary

Multi-Primary mode:

  Architecture:
    ALL members accept writes simultaneously
    Every write: certified against concurrent writes on other members

  Write flow:
    Client → ANY MEMBER → broadcast to group → certify → all commit
    If conflict detected: one transaction rolled back (application must retry)

  Benefits:
  ✓ Write throughput scales across multiple nodes
  ✓ Geographic distribution (write to nearest node)

  Risks and restrictions:
  ✗ Conflicts: concurrent writes to same row → one rolled back (app must retry)
  ✗ Restrictions on DDL: serialised (one at a time across group)
  ✗ SERIALIZABLE isolation level: not supported (uses lower isolation)
  ✗ Foreign key cascade: not fully supported (can cause conflicts)
  ✗ SELECT ... FOR UPDATE across different primaries: may deadlock
  ✗ Complex: application must handle rollbacks and retries
  ✗ AUTO_INCREMENT gaps: each member has different auto_increment_offset
     to avoid PK conflicts (group_replication_auto_increment_increment)
```

```sql
-- Checking and switching modes:

-- Check current mode:
SELECT @@group_replication_single_primary_mode;
-- 1 = Single-Primary, 0 = Multi-Primary

-- Switch to Multi-Primary (requires group restart):
-- Stop group replication on all members:
STOP GROUP_REPLICATION;

-- Set multi-primary mode on all members:
SET GLOBAL group_replication_single_primary_mode=OFF;
SET GLOBAL group_replication_enforce_update_everywhere_checks=ON;
-- enforce_update_everywhere_checks: enables additional conflict detection
-- for FK cascades and serializable transactions in multi-primary mode

-- Restart group replication (bootstrap on first node):
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;

-- Other nodes join:
START GROUP_REPLICATION;

-- Online switch (MySQL 8.0 — no restart needed):
SELECT group_replication_switch_to_multi_primary_mode();
SELECT group_replication_switch_to_single_primary_mode();
-- These functions coordinate the mode change across the group atomically
```

```sql
-- Multi-Primary conflict detection in action:

-- Member 1 and Member 2 both execute concurrently:
-- Member 1: UPDATE accounts SET balance = 500 WHERE id = 42;
-- Member 2: UPDATE accounts SET balance = 600 WHERE id = 42;
-- Both write to: {accounts:42}

-- Group receives both and must order them:
-- If Member 1's write arrives first in GCS total order:
--   Member 1's write: COMMIT
--   Member 2's write: ROLLBACK (conflict with already-committed T1)

-- Application on Member 2 sees:
-- ERROR 1213 (40001): Deadlock found when trying to get lock;
-- try restarting transaction
-- Application MUST retry the transaction

-- Detect conflict frequency:
SELECT COUNT_TRANSACTIONS_IN_QUEUE,
       COUNT_TRANSACTIONS_CHECKED,
       COUNT_CONFLICTS_DETECTED,
       COUNT_TRANSACTIONS_ROWS_VALIDATING,
       TRANSACTIONS_COMMITTED_ALL_MEMBERS
FROM performance_schema.replication_group_member_stats
WHERE MEMBER_ID = @@server_uuid;
-- COUNT_CONFLICTS_DETECTED: how many transactions were rolled back due to conflicts
-- If this is non-zero in a multi-primary setup: application needs retry logic
-- If this is high: consider switching to single-primary
```

## Section 3: InnoDB Cluster

**Q4. What is MySQL InnoDB Cluster — how does it relate to Group Replication, MySQL Router, and MySQL Shell?**
A: InnoDB Cluster is MySQL's high-availability solution that packages three components — Group Replication (data layer), MySQL Router (connection routing), and MySQL Shell (management interface) — into a unified, manageable system. Group Replication handles data; Router handles transparent failover for applications; Shell provides the management API:

```
InnoDB Cluster architecture:

  ┌─────────────────────────────────────────────────────────────┐
  │                     Application Layer                        │
  │   App Server 1      App Server 2      App Server 3          │
  └─────────┬───────────────┬─────────────────┬────────────────┘
            │               │                 │
            └───────────────┴─────────────────┘
                            │
                     ┌──────▼──────┐
                     │   MySQL     │    Automatically routes:
                     │   Router    │    - Writes → PRIMARY
                     │  (x2, HA)   │    - Reads → PRIMARY or SECONDARY
                     └──────┬──────┘    Monitors cluster health
                            │          Re-routes on failover (< 1s)
            ┌───────────────┼───────────────┐
            │               │               │
     ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐
     │  MySQL 1    │ │  MySQL 2    │ │  MySQL 3    │
     │ (PRIMARY)   │ │ (SECONDARY) │ │ (SECONDARY) │
     │             │ │             │ │             │
     └─────────────┘ └─────────────┘ └─────────────┘
           ↕               ↕               ↕
     ┌─────────────────────────────────────────────┐
     │         Group Replication (GCS/Paxos)        │
     │    Consensus, certification, global order    │
     └─────────────────────────────────────────────┘

  Component responsibilities:
  ┌─────────────────┬──────────────────────────────────────────┐
  │ Group           │ Data consistency, consensus, automatic    │
  │ Replication     │ primary election, conflict detection      │
  ├─────────────────┼──────────────────────────────────────────┤
  │ MySQL Router    │ Application-transparent failover,         │
  │                 │ read/write splitting, connection pooling  │
  ├─────────────────┼──────────────────────────────────────────┤
  │ MySQL Shell     │ Cluster management API (JS/Python/SQL),  │
  │                 │ deployment, monitoring, administration    │
  └─────────────────┴──────────────────────────────────────────┘
```

**Q5. What does MySQL Router do — how does it provide transparent failover and read/write splitting?**
A: MySQL Router is a lightweight proxy that sits between the application and the cluster. It maintains a real-time map of which member is the primary and which are secondaries, rerouting connections automatically when the topology changes. Applications connect to the Router's ports — they never need to know individual member addresses:

```
MySQL Router port model:

  Router exposes multiple ports, each with different routing policies:

  Port 6446: Read/Write — routes to PRIMARY only
    ├── App sends a write: always goes to current primary
    └── If primary fails: Router detects new primary, reconnects
        (connection briefly drops, application must handle reconnect)

  Port 6447: Read-Only — routes to SECONDARY members (round-robin or random)
    ├── App sends reads: distributed across available secondaries
    └── If a secondary fails: Router stops routing to it, continues with others

  Port 6448: Read/Write (X Protocol — for MySQL Shell and newer drivers)
  Port 6449: Read-Only  (X Protocol)

  Application connection string:
    BEFORE InnoDB Cluster: mysql://app:pass@mysql1:3306/mydb
    AFTER  InnoDB Cluster: mysql://app:pass@router-host:6446/mydb
    ← Application talks to Router, not directly to cluster members
```

```
Router failover mechanism:

  Normal state: PRIMARY = mysql1
  Router: routes port 6446 → mysql1:3306

  Failure event: mysql1 crashes
  ├── Group Replication detects: mysql1 UNREACHABLE
  ├── Remaining members (mysql2, mysql3) have quorum → elect new primary
  ├── Election: mysql2 elected PRIMARY (deterministic based on weight + UUID)
  ├── Router detects topology change (polls metadata every 0.5s by default)
  └── Router: routes port 6446 → mysql2:3306

  Application perspective:
  - Existing connections to port 6446: broken at failover (mysql1 died)
  - Application connection pool: retries → gets mysql2 via Router
  - Time from failure to new connections working: 1-5 seconds typically
  - No application reconfiguration needed (still connecting to Router)

  Router checks cluster topology via:
  1. mysql_innodb_cluster_metadata schema (stored on cluster members)
  2. GCS messaging (Router is notified of topology changes)
  Router keeps this map updated continuously
```

```bash
# MySQL Router setup and bootstrap:

# Bootstrap Router from an existing InnoDB Cluster:
mysqlrouter --bootstrap root@mysql1:3306 --directory /etc/mysqlrouter/myCluster

# What --bootstrap does:
# 1. Connects to mysql1 to read cluster topology
# 2. Creates router account in MySQL (mysql_router_<hash>@<host>)
# 3. Writes mysqlrouter.conf with:
#    - Cluster member addresses
#    - Port assignments (6446, 6447, 6448, 6449)
#    - Routing policies (round-robin, first-available)
#    - Metadata cache configuration

# Generated mysqlrouter.conf (key sections):
# [routing:bootstrap_rw]
# bind_address = 0.0.0.0
# bind_port = 6446
# destinations = metadata-cache://myCluster/?role=PRIMARY
# routing_strategy = first-available  ← always goes to primary
# protocol = classic

# [routing:bootstrap_ro]
# bind_port = 6447
# destinations = metadata-cache://myCluster/?role=SECONDARY
# routing_strategy = round-robin-with-fallback  ← distributes across secondaries
# ← fallback to primary if no secondaries available
# protocol = classic

# Start Router:
mysqlrouter &
# Or as systemd service: systemctl start mysqlrouter

# Verify Router is routing correctly:
mysql -h router-host -P 6446 -e "SELECT @@hostname, @@read_only;"
# @@hostname: mysql1 (primary)
# @@read_only: 0

mysql -h router-host -P 6447 -e "SELECT @@hostname, @@read_only;"
# @@hostname: mysql2 or mysql3 (secondary)
# @@read_only: 1
```

## Section 4: Deployment and Configuration

**Q6. What are the prerequisites and configuration requirements for Group Replication?**
A: Group Replication has strict requirements that go beyond standard MySQL replication setup. Missing any of these causes either startup failures or silent data integrity problems:

```sql
-- Required MySQL configuration (my.cnf / my.ini):

[mysqld]
# Server identity — MUST be unique per member:
server_id = 1                          -- Different on every member (1, 2, 3...)
gtid_mode = ON                         -- Global Transaction Identifiers required
enforce_gtid_consistency = ON          -- Enforces GTID-safe statement restrictions

# Binary logging — required for GR:
log_bin = mysql-bin                    -- Enable binary logging
binlog_format = ROW                    -- Row-based replication (not STATEMENT or MIXED)
                                       -- Required: statement mode cannot certify conflicts
log_slave_updates = ON                 -- Secondaries also log applied transactions
                                       -- Required for chain replication and recovery

# InnoDB requirements:
default_storage_engine = InnoDB        -- Must use InnoDB (only engine GR supports)
innodb_flush_log_at_trx_commit = 1    -- Full ACID durability (1 = safest)
sync_binlog = 1                        -- Flush binlog to disk on every commit

# Group Replication plugin:
plugin_load_add = 'group_replication.so'  -- Load the GR plugin at startup

# Group identity — SAME on all members:
group_replication_group_name = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee'
# Must be a valid UUID, same for all members in the same group

# Communication addresses:
group_replication_local_address = 'mysql1:33061'
# This member's address for GCS (Group Communication System)
# Port 33061 is the group communication port (not the MySQL client port 3306)

group_replication_group_seeds = 'mysql1:33061,mysql2:33061,mysql3:33061'
# All members' GCS addresses — used for initial contact when joining

# Network and timeouts:
group_replication_member_weight = 50   -- Higher weight = preferred for primary election
                                       -- Range: 0-100 (default 50)
                                       -- The member with highest weight becomes primary
```

```sql
-- Per-member differences (only server_id and local_address differ):

-- mysql1/my.cnf:
-- server_id = 1
-- group_replication_local_address = 'mysql1:33061'

-- mysql2/my.cnf:
-- server_id = 2
-- group_replication_local_address = 'mysql2:33061'

-- mysql3/my.cnf:
-- server_id = 3
-- group_replication_local_address = 'mysql3:33061'

-- All other GR settings: identical across members

-- Verify configuration is compatible for Group Replication:
-- MySQL Shell does this automatically, but manually:
SELECT * FROM performance_schema.replication_group_configuration_version;
-- Also check:
SHOW VARIABLES LIKE 'gtid_mode';            -- Must be ON
SHOW VARIABLES LIKE 'binlog_format';        -- Must be ROW
SHOW VARIABLES LIKE 'log_bin';              -- Must be ON
SHOW VARIABLES LIKE 'enforce_gtid_consistency'; -- Must be ON
```

```sql
-- Starting Group Replication manually:

-- On the FIRST member (bootstrap — creates the group):
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION
    USER='replication_user'
    , PASSWORD='repl_password'
    , DEFAULT_AUTH='caching_sha2_password';
SET GLOBAL group_replication_bootstrap_group=OFF;
-- bootstrap_group=ON: this member doesn't wait for others — it creates the group
-- CRITICAL: set back to OFF immediately after start
-- If left ON: starting GR again creates a SECOND group (split-brain!)

-- On subsequent members (join existing group):
START GROUP_REPLICATION
    USER='replication_user'
    , PASSWORD='repl_password'
    , DEFAULT_AUTH='caching_sha2_password';
-- No bootstrap_group — member contacts group_replication_group_seeds to join

-- Create the replication user (on primary, before starting GR):
SET SQL_LOG_BIN=0;  -- Don't replicate this user creation via GR
CREATE USER 'replication_user'@'%' IDENTIFIED BY 'repl_password';
GRANT REPLICATION SLAVE ON *.* TO 'replication_user'@'%';
GRANT CONNECTION_ADMIN ON *.* TO 'replication_user'@'%';
SET SQL_LOG_BIN=1;
```

**Q7. How does a new member join an existing Group Replication group — what is clone-based recovery?**
A: When a new member joins a group, it must catch up to the current state of the group's data before it can participate. For small lag (few transactions missing), Group Replication uses distributed recovery via binlog. For large lag (member was offline for a long time), MySQL 8.0 provides clone-based recovery that copies a complete data snapshot:

```
Member join process — two recovery methods:

  New member contacts group_replication_group_seeds
  → Joins the group membership (RECOVERING state)
  → Needs to catch up on all committed transactions it missed

  Method 1: Distributed Recovery (binlog-based)
    New member selects a donor (existing online member)
    New member fetches missing transactions from donor's binlog
    Applies them in order (RECOVERING state, read-only)
    When caught up: transitions to ONLINE

  Suitable when:
  ✓ New member has been offline for a short time
  ✓ Missing only a few thousand transactions
  ✓ Donor's binlog retention covers the gap

  Not suitable when:
  ✗ New member is completely fresh (no data at all)
  ✗ Gap is so large donor's binlog was purged
  ✗ Binlog-based catchup would take hours

  Method 2: Clone Plugin Recovery (MySQL 8.0+)
    New member uses MySQL Clone plugin to copy ENTIRE dataset from donor
    Clone: online, hot snapshot — consistent copy while donor serves traffic
    After clone: gap between clone timestamp and now filled via binlog
    Then: transitions to ONLINE

  Suitable when:
  ✓ New member is fresh (no data)
  ✓ Large amount of data to catch up on
  ✓ Faster to copy everything than replay binlogs

  Group Replication auto-selects the method:
  If gap can be filled by binlog → binlog recovery
  If binlog gap too large → automatically triggers clone
```

```sql
-- Installing and enabling clone for new member joins:

-- On all members (donor and recipient):
INSTALL PLUGIN clone SONAME 'mysql_clone.so';
-- Or in my.cnf: plugin_load_add = 'clone.so'

-- Grant clone privilege (for the replication user):
GRANT BACKUP_ADMIN ON *.* TO 'replication_user'@'%';
-- BACKUP_ADMIN: required to be a clone donor

-- Configure clone to be used automatically by GR recovery:
SET GLOBAL group_replication_clone_threshold = 1;
-- Threshold in transactions: if new member is more than 1 transaction behind
-- and donor's binlog covers the gap, use binlog
-- If gap > threshold transactions AND binlog covers: use binlog
-- If binlog is purged: always use clone

-- More practical threshold:
SET GLOBAL group_replication_clone_threshold = 1000000;
-- If behind by more than 1M transactions: use clone
-- If behind by less: use binlog recovery

-- Monitor recovery progress on the joining member:
SELECT * FROM performance_schema.replication_group_member_stats
WHERE MEMBER_ID = @@server_uuid;

-- Monitor clone progress (if clone is happening):
SELECT STATE, BEGIN_TIME, END_TIME, ERROR_NO, BINLOG_FILE, BINLOG_POSITION
FROM performance_schema.clone_status;
-- STATE: Not Started → In Progress → Completed
-- BINLOG_POSITION: where binlog recovery picks up after clone
```

## Section 5: Failure Handling and Failover

**Q8. What happens when the primary fails — how does Group Replication elect a new primary, and what is the application impact?**
A: When the primary crashes or becomes unreachable, the remaining members detect the failure through the GCS heartbeat mechanism and run a primary election algorithm. The entire process — from failure detection to new primary being active — typically takes 5-15 seconds depending on configuration:

```
Failure detection and primary election timeline:

  T+0s:   Primary (mysql1) crashes
  T+1s:   GCS heartbeat timeout: mysql2 and mysql3 cannot contact mysql1
           Both mark mysql1 as UNREACHABLE
           (group_replication_member_expel_timeout: default 0s → expelled immediately)
  T+2s:   Group reaches consensus: mysql1 expelled from group
           mysql1's MEMBER_STATE → UNREACHABLE in replication_group_members
  T+2s:   Primary election algorithm runs on remaining members:
           Candidate evaluation order:
           1. Highest group_replication_member_weight (tie → lowest UUID wins)
           2. Must be ONLINE (not RECOVERING)
           3. Must have same MySQL version as group minimum version
           mysql2: weight=50, UUID=bbbb...
           mysql3: weight=50, UUID=cccc...
           → mysql2 wins (lower UUID as tiebreaker)
  T+3s:   mysql2 transitions to PRIMARY
           mysql3 remains SECONDARY
           mysql2's super_read_only: OFF (primary accepts writes)
           mysql3's super_read_only: ON (secondary rejects writes)
  T+3s:   Cluster metadata updated: mysql2 = PRIMARY
  T+3s:   MySQL Router detects topology change (next metadata poll)
  T+4s:   Router updates routing: port 6446 → mysql2:3306
  T+4s:   Application's new connections route to mysql2

  Impact on in-flight transactions at T+0:
  ├── Transactions that reached quorum (certified by majority):
  │     Applied on mysql2 and mysql3 (were already committed on majority)
  │     No data loss
  └── Transactions that did NOT reach quorum (in progress on mysql1 only):
        Lost — mysql1 crashed before certification
        Client received no response or connection error → application retries
```

**Q9. What is the flow control mechanism in Group Replication — why does secondary lag cause primary slowdown?**
A: Group Replication's flow control prevents secondaries from falling too far behind the primary. If a secondary's transaction application queue grows beyond a threshold, the group slows down the primary's certification throughput to give secondaries time to catch up:

```
Flow control mechanism:

  Normal operation:
  Primary: commits 10,000 TPS (transactions per second)
  Secondary applies: 10,000 TPS → queue stays near 0

  Secondary falls behind (e.g., due to complex transaction applying):
  Primary: still commits 10,000 TPS
  Secondary applies: 8,000 TPS → queue grows at 2,000 TPS
  After 5 seconds: secondary has 10,000 txns in applier queue

  Flow control triggers:
  When queue > group_replication_flow_control_applier_threshold (default: 25000):
    Group sends FLOW_CONTROL_THROTTLE message
    Primary: slows down certification approvals
    Effectively: reduces write throughput on primary to let secondaries catch up

  Impact: a slow secondary slows the ENTIRE GROUP's write throughput
  This is the most common performance complaint with Group Replication
```

```sql
-- Monitoring flow control:

-- COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE: how many txns waiting to apply

-- Flow control settings:
SHOW VARIABLES LIKE 'group_replication_flow_control%';
-- group_replication_flow_control_mode:        QUOTA (default) | DISABLED
-- group_replication_flow_control_applier_threshold: 25000 (transactions)
-- group_replication_flow_control_certifier_threshold: 25000

-- Only disable if: secondaries are read-only replicas with SLA-acceptable lag
```

## Section 6: Performance and Tuning

**Q10. What are the performance characteristics of Group Replication — what workloads is it well-suited for and where does it struggle?**
A: Group Replication's certification overhead adds latency to every write transaction. Understanding this overhead and its workload implications is essential for capacity planning and knowing when GR is appropriate:

```
Group Replication write latency profile:

  Standard MySQL write (no replication):
    Client → MySQL → write to InnoDB → COMMIT
    Latency: 1-5ms (local disk I/O)

  Group Replication write (3-member single-primary):
    Client → PRIMARY → transaction → broadcast writesets to GCS
                      ↑             ↓
                      COMMIT ← Certification complete (quorum received)
    GCS round trip: 1-5ms (LAN), 50-200ms (WAN/cross-region)
    Latency: local_commit + network_round_trip_to_quorum
    LAN (same datacenter): 2-10ms total write latency
    WAN (cross-region): 51-205ms total write latency

  This latency overhead affects:
  ✗ High-frequency single-row updates (point-of-sale, counter increments)
  ✗ Interactive UI writes expecting <5ms response
  ✗ Cross-region deployments where RTT is 50ms+

  Workloads where GR overhead is negligible:
  ✓ Batch inserts (latency per batch, not per row)
  ✓ Writes that are already slow (complex business logic >100ms)
  ✓ Same-datacenter LAN deployment
  ✓ Read-heavy workloads (writes are rare relative to reads)
```

```sql
-- Identifying Group Replication performance bottlenecks:

-- 1. High certification latency:
SELECT LAST_CONFLICT_FREE_TRANSACTION,
       COUNT_TRANSACTIONS_IN_QUEUE,
       COUNT_TRANSACTIONS_CHECKED
FROM performance_schema.replication_group_member_stats;
-- If COUNT_TRANSACTIONS_IN_QUEUE is consistently high on the primary:
-- Certification is backed up — reduce write rate or optimize writesets

-- 2. Large writesets (transactions touching many rows):
-- GR writesets grow with number of rows modified in a transaction
-- Large writeset = more data to broadcast = higher certification time
-- Check average transaction size:
SELECT AVG(COUNT_TRANSACTIONS_ROWS_VALIDATING)
FROM performance_schema.replication_group_member_stats;
-- High value: transactions modify many rows → split into smaller batches

-- 3. Hotspot conflicts (same rows updated frequently):
SELECT COUNT_CONFLICTS_DETECTED
FROM performance_schema.replication_group_member_stats;
-- Any conflicts in single-primary = unexpected (only primary writes)
-- In multi-primary: monitor for high conflict rate → reduce concurrent writes to same rows

-- 4. Secondary lag causing flow control:
SELECT MEMBER_ID,
       COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE
FROM performance_schema.replication_group_member_stats;
-- If any secondary has a growing queue: investigate applier thread count,
-- disk I/O on secondary, complex triggers that slow apply
```

```sql
-- Optimizing writes for Group Replication:

-- 1. Keep transactions small (fewer rows per transaction):
-- BAD: one transaction modifying 1M rows
START TRANSACTION;
UPDATE orders SET status = 'ARCHIVED' WHERE created_at < '2020-01-01';
-- Updates 5M rows → 5M-row writeset → huge broadcast → slow certification
COMMIT;

-- GOOD: batch into smaller transactions:
SET @batch_size = 1000;
REPEAT
    START TRANSACTION;
    UPDATE orders SET status = 'ARCHIVED'
    WHERE created_at < '2020-01-01'
      AND status != 'ARCHIVED'
    LIMIT 1000;
    COMMIT;
UNTIL ROW_COUNT() = 0 END REPEAT;
-- Each transaction: 1000-row writeset → fast certification

-- 2. Avoid cross-row hotspots (counter pattern):
-- BAD in multi-primary: global counter updated by every transaction
-- Every transaction conflicts with every other → near-100% conflict rate
-- Solution: use separate counter-sharding approach or move to single-primary
-- Or: use INSERT into a counter table + periodic aggregate (append-only)

-- 3. For large read queries: use secondaries via Router port 6447:
-- Offload analytical queries from primary
-- Reduces primary CPU and I/O → more headroom for write certification
```

## Section 7: Monitoring and Operations

**Q11. How do you monitor a running InnoDB Cluster — what metrics matter and how do you respond to them?**
A: Monitoring Group Replication requires tracking three categories: group membership health (is the cluster intact?), replication lag (are secondaries keeping up?), and conflict/error rates (is data consistency maintained?):

```sql
-- Dashboard query: overall cluster health
SELECT
    m.MEMBER_ID,
    m.MEMBER_HOST,
    m.MEMBER_PORT,
    m.MEMBER_STATE,
    m.MEMBER_ROLE,
    s.COUNT_TRANSACTIONS_IN_QUEUE AS certifier_queue,
    s.COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE AS applier_queue,
    s.COUNT_CONFLICTS_DETECTED AS conflicts,
    s.COUNT_TRANSACTIONS_CHECKED AS certified_total
FROM performance_schema.replication_group_members m
JOIN performance_schema.replication_group_member_stats s
    ON m.MEMBER_ID = s.MEMBER_ID
ORDER BY m.MEMBER_ROLE DESC;  -- PRIMARY first

-- Ideal output:
-- MEMBER_STATE: all ONLINE
-- certifier_queue: 0 or very low (< 100)
-- applier_queue: 0 or very low on all members
-- conflicts: 0 (single-primary) or very low (multi-primary)

-- Alert conditions:
-- Any MEMBER_STATE = UNREACHABLE or ERROR: immediate alert
-- certifier_queue > 1000: certification backing up → write throttle incoming
-- applier_queue > 10000 on any member: secondary falling behind → flow control
-- conflicts > 0 in single-primary: shouldn't happen → investigate application
```

```sql
-- Monitoring secondary lag specifically:
```

```python
# 2. Add new members
```

## Section 8: Advanced Topics

**Q13. How do you implement read/write splitting with InnoDB Cluster — what consistency guarantees do reads from secondaries provide?**
A: MySQL Router handles routing, but the application must understand what consistency level it will get when reading from a secondary. Secondaries apply transactions asynchronously — they may be seconds behind the primary, causing stale reads:

```
Read consistency models in InnoDB Cluster:

  1. Reads from PRIMARY (port 6446):
     Always consistent — just committed transactions are immediately visible
     Suitable for: reads that MUST see the latest write (e.g., "read what I just wrote")
     Cost: all reads go to one node → less scalability

  2. Reads from SECONDARY (port 6447):
     Eventually consistent — may lag behind primary by milliseconds to seconds
     Suitable for: reports, analytics, non-time-critical reads
     Benefit: distributed across multiple nodes → better read scalability

  3. Causal consistency (AFTER_SYNC / AFTER_COMMIT):
     Wait until secondary has applied at least up to a specific GTID
     The write returns a "sync point" (GTID) to the client
     The read waits until the secondary reaches that GTID
     Suitable for: "read your own writes" from secondary
     Cost: read latency includes secondary catchup time
```

```sql
-- Implementing "read your own writes" from secondary:

-- Write on primary (port 6446):
START TRANSACTION;
INSERT INTO notifications (user_id, message) VALUES (42, 'Order shipped!');
COMMIT;

-- Get the GTID of the just-committed transaction:
SELECT @@GLOBAL.GTID_EXECUTED AS gtid_executed;
-- Returns: 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa:1-1000'
-- The "1-1000" includes our just-committed transaction as txn 1000

-- Now read from secondary (port 6447) — but wait until it has our txn:
SET SESSION group_replication_consistency = 'AFTER_SYNC';
-- AFTER_SYNC: this session's reads wait until the secondary has applied
-- the transaction at the GTID seen at this session's start

-- Or use WAIT_FOR_EXECUTED_GTID_SET:
SELECT WAIT_FOR_EXECUTED_GTID_SET('aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa:1-1000', 5);
-- 0 = success (secondary has applied up to txn 1000 within 5 seconds)
-- 1 = timeout (secondary didn't catch up within 5 seconds)
-- Then safe to read:
SELECT * FROM notifications WHERE user_id = 42;
-- Guaranteed to see our just-inserted notification

-- MySQL 8.0 consistency levels for reads (per session or global):
SET SESSION group_replication_consistency = 'EVENTUAL';
-- EVENTUAL (default): reads are served immediately (may be stale)

SET SESSION group_replication_consistency = 'BEFORE';
-- BEFORE: read waits until this member has applied all transactions
-- committed before this read started (consistent snapshot)

SET SESSION group_replication_consistency = 'AFTER';
-- AFTER: a write waits until committed transaction applied on ALL online members
-- Most expensive: write latency includes all members applying the transaction

SET SESSION group_replication_consistency = 'BEFORE_AND_AFTER';
-- Combines BEFORE (read) and AFTER (write): strong consistency everywhere
-- Highest latency: use only when absolutely necessary
```

```sql
-- Application-level read/write splitting:

-- Connection pool with two pools:
-- Write pool: connects to router:6446 (primary)
-- Read pool:  connects to router:6447 (secondaries)

-- Node.js example (pseudocode):
-- const writePool = mysql.createPool({ host: 'router', port: 6446 });
-- const readPool  = mysql.createPool({ host: 'router', port: 6447 });

-- Use write pool for mutations:

-- Use read pool for queries:
-- const orders = await readPool.query('SELECT * FROM orders WHERE user_id = ?', [userId]);

-- For "read your own write" pattern: use writePool for the subsequent read

-- MySQL Router read/write splitting (MySQL Router 8.0.24+):

-- INSERT/UPDATE/DELETE → primary
-- No application changes needed (Router inspects query type)

-- [routing:rwsplit]

-- destinations = metadata-cache://myCluster/?role=PRIMARY_AND_SECONDARY
-- routing_strategy = round-robin-with-fallback
-- access_mode = auto   ← Router automatically splits read/write
```

**Q15. "A newly added member is stuck in RECOVERING state for over an hour. What are the causes and how do you fix each?"**
A: A member stuck in RECOVERING is actively trying to catch up with the group but something is preventing completion. The cause determines the fix:

```sql
-- Step 1: Check what recovery method is in use:
-- On the joining member:
SELECT * FROM performance_schema.replication_connection_status
WHERE CHANNEL_NAME = 'group_replication_recovery';
-- SERVICE_STATE: ON = recovery connection active, OFF = not connected

-- Check if clone is in progress:
SELECT STATE, BEGIN_TIME, BYTES_COPIED, BINLOG_FILE, BINLOG_POSITION
FROM performance_schema.clone_status;
-- If STATE = 'In Progress': clone is running (may take hours for large datasets)
-- BYTES_COPIED: track progress — is it advancing?
-- If BYTES_COPIED is not advancing for 10+ minutes: clone is stuck

-- Step 2: Check for errors:
SHOW REPLICA STATUS FOR CHANNEL 'group_replication_recovery'\G
-- Seconds_Behind_Source: how far behind the donor
-- Last_IO_Error: connection error to donor
-- Last_SQL_Error: error applying a transaction

-- Step 3: Identify the root cause:

-- Cause A: Donor's binlog was purged (gap too large for binlog recovery)
-- Symptom: Last_IO_Error = "Got fatal error 1236 from source: 'The slave is
--           connecting using CHANGE MASTER TO MASTER_AUTO_POSITION = 1,
--           but the master has purged binary logs containing GTIDs that the slave requires.'"
-- Fix: Configure clone plugin and set threshold to trigger clone:
SET GLOBAL group_replication_clone_threshold = 1;
STOP GROUP_REPLICATION;
START GROUP_REPLICATION USER='replication_user' PASSWORD='repl_password';
-- Clone now triggered automatically
```

```sql
-- Cause B: Clone is running but extremely slow (large dataset)
-- Symptoms: clone_status shows 'In Progress', BYTES_COPIED advancing slowly
-- Check: is clone donor being throttled?
SELECT * FROM performance_schema.clone_status;
-- If BYTES_COPIED is advancing: just wait — may take hours for 500GB+

-- Accelerate by choosing a faster donor:
STOP GROUP_REPLICATION;
-- Set preferred donor IP:
SET GLOBAL group_replication_recovery_endpoints = 'mysql2:3306';
-- mysql2 may have faster network/disk to the joining member
START GROUP_REPLICATION USER='replication_user' PASSWORD='repl_password';

-- Cause C: Authentication failure connecting to donor:
-- Last_IO_Error: "Access denied for user 'replication_user'@'...' (using password: YES)"
-- Fix: Create replication user on donor (may have been missed):
-- On the donor:
CREATE USER 'replication_user'@'<joining_member_ip>' IDENTIFIED BY 'repl_password';
GRANT REPLICATION SLAVE ON *.* TO 'replication_user'@'<joining_member_ip>';
GRANT BACKUP_ADMIN ON *.* TO 'replication_user'@'<joining_member_ip>';
FLUSH PRIVILEGES;

-- Cause D: Transaction on joining member not compatible (errant transactions):
-- Joining member has transactions that don't exist in the group
-- (e.g., someone accidentally wrote to it while it was standalone)
-- Symptom: RECOVERING but error in performance_schema.replication_applier_status_by_worker
-- 1032: Can't find record — divergent data
-- Fix: Reset the joining member entirely:
STOP GROUP_REPLICATION;
RESET MASTER;      -- Clears all local GTIDs
RESET REPLICA ALL; -- Clears replication configuration
-- Re-bootstrap from a full donor clone (data must be reloaded)

-- After fixing the cause: restart recovery:
STOP GROUP_REPLICATION;
START GROUP_REPLICATION USER='replication_user' PASSWORD='repl_password';
-- Monitor: should transition RECOVERING → ONLINE within minutes (or hours if large clone)
```

**Tip for interviews:** Five things separate strong candidates on Group Replication and InnoDB Cluster: (1) explaining **how Paxos consensus prevents data loss** — that Group Replication requires a quorum (majority) to certify every transaction before the primary commits, meaning a committed transaction is always on at least (N/2+1) nodes, so even if half the cluster fails simultaneously, no committed transaction is lost (unlike async replication where committed-on-primary but not-yet-replicated transactions disappear on primary failure); (2) being able to articulate **the three-component architecture** — that InnoDB Cluster is Group Replication (consensus) + MySQL Router (routing) + MySQL Shell (management), and specifically that MySQL Router is what makes failover transparent to applications by absorbing the primary address change (applications connect to Router's stable port, not directly to members), with sub-5-second re-routing after failure; (3) knowing **the quorum math and its operational implications** — that a 3-member cluster needs 2 for quorum, so tolerates 1 failure; a 5-member cluster needs 3, tolerating 2 failures; and that losing quorum means the remaining members go read-only (cannot commit), requiring either `forceQuorumUsingPartitionOf` or rebuilding the cluster, with the warning that force-quorum risks split-brain if the "dead" members are actually just partitioned; (4) understanding **why flow control exists and when it becomes a problem** — that Group Replication throttles primary write throughput when any secondary's applier queue exceeds `group_replication_flow_control_applier_threshold`, meaning a slow secondary (due to disk I/O, complex triggers, or under-resourced hardware) can visibly reduce write throughput on the primary, and that the fix is increasing parallel applier threads (`replica_parallel_workers`) on secondaries before increasing the threshold; and (5) knowing **the single-primary vs multi-primary tradeoffs precisely** — not just that multi-primary allows all nodes to write, but specifically that it restricts SERIALIZABLE isolation, foreign key cascades, and requires applications to handle `ER_TRANSACTION_ROLLBACK_DUE_TO_SERIALIZATION` (error 1213) rollbacks with retry logic, making it appropriate only for truly independent write streams (geographic sharding by region) rather than general-purpose high-throughput writes where the conflict rate would eliminate any throughput benefit.
