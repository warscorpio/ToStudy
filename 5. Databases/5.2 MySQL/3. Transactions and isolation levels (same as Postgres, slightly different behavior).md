## Section 1: Fundamentals

**Q1. How does MySQL's transaction architecture differ from PostgreSQL's at the engine level?**
A: MySQL separates the storage engine from the query layer — transactions are a storage engine concern, not a server concern. InnoDB is the only production storage engine that supports transactions. MyISAM (legacy) has no transactions at all. This architecture means the isolation level behavior, locking model, and MVCC implementation are InnoDB-specific, not MySQL-wide:

```
MySQL architecture (layered):
  ┌─────────────────────────────────────────────────┐
  │  MySQL Server Layer                              │
  │  - SQL parsing, query optimization, result sets  │
  │  - No transaction awareness                      │
  ├─────────────────────────────────────────────────┤
  │  InnoDB Storage Engine                           │
  │  - Transaction management (BEGIN/COMMIT/ROLLBACK)│
  │  - MVCC (Multi-Version Concurrency Control)      │
  │  - Row-level locking                             │
  │  - Redo log (WAL equivalent)                     │
  │  - Undo log (MVCC version store)                 │
  ├─────────────────────────────────────────────────┤
  │  MyISAM Storage Engine (legacy, avoid)           │
  │  - No transactions                               │
  │  - Table-level locking only                      │
  │  - No MVCC                                       │
  └─────────────────────────────────────────────────┘

PostgreSQL architecture (unified):
  ┌─────────────────────────────────────────────────┐
  │  PostgreSQL (single, unified engine)             │
  │  - Transactions, MVCC, locking all at one level  │
  │  - No pluggable storage engine concept           │
  │  - WAL is the single source of truth             │
  └─────────────────────────────────────────────────┘

Key structural differences:
  InnoDB MVCC: uses UNDO LOG (separate rollback segment)
               old row versions stored in undo log pages (not inline in heap)
               undo log is a separate physical structure from the row data
  PostgreSQL:  uses HEAP TUPLE versioning (old versions in-place in heap files)
               old versions visible as dead tuples until VACUUM reclaims them

  InnoDB locking: gap locks + next-key locks (integral to phantom prevention)
  PostgreSQL:     MVCC snapshot (no gap locks needed at REPEATABLE READ)

  InnoDB default: REPEATABLE READ
  PostgreSQL default: READ COMMITTED

  InnoDB autocommit: ON by default (each statement is its own transaction)
  PostgreSQL:        explicit transactions only (BEGIN required)
```

**Q2. What is InnoDB's MVCC implementation and how does it differ from PostgreSQL's?**
A: InnoDB stores the current row in the clustered index (the heap) and old versions in a separate undo log. A read view determines which undo log version is visible. PostgreSQL stores all versions in the heap and uses dead tuple cleanup via VACUUM. The behavioral difference is significant for long-running transactions:

```
InnoDB MVCC mechanics:

  Current row (in clustered index / primary key B-tree):
  ┌──────────────────────────────────────────────────────┐
  │ id │ balance │ DB_TRX_ID │ DB_ROLL_PTR              │
  │ A1 │   900   │  txid 210 │ → undo log entry #847    │
  └──────────────────────────────────────────────────────┘
  DB_TRX_ID:  transaction ID that last modified this row
  DB_ROLL_PTR: pointer into undo log where old version lives

  Undo log (old versions, stored separately):
  ┌────────────────────────────────────────────────────┐
  │ entry #847: { id: A1, balance: 1000, trx: 150 }   │ ← version before txid 210 updated it
  │             → #512: { id: A1, balance: 1200, ... } │ ← version before txid 150
  └────────────────────────────────────────────────────┘
  Version chain: current row → undo entry → older undo entry → ...

  Read view (snapshot):
    Created at: transaction START (REPEATABLE READ) or statement start (READ COMMITTED)
    Contains: low_limit_id (no txid this high or higher is visible)
              up_limit_id (all txids lower than this are visible)
              trx_ids[] (list of active txids at snapshot time — not visible)
    To read a row: walk the version chain until finding a version
                   whose DB_TRX_ID is visible to this read view

PostgreSQL MVCC comparison:
  Old versions: stored as dead tuples IN THE HEAP alongside live tuples
  Cleanup: VACUUM reclaims dead tuples (periodic, asynchronous)
  Bloat risk: long-running transactions prevent VACUUM → table bloat

InnoDB MVCC comparison:
  Old versions: stored IN UNDO LOG (separate from heap)
  Cleanup: undo log entries purged by purge thread (when no read view needs them)
  Bloat risk: long-running transactions hold back undo log purge → undo log grows
              history list length (HLL) metric tracks undo log backlog:
              SHOW ENGINE INNODB STATUS\G  → look for "History list length"
              HLL > 100,000 → long-running transaction holding back purge → investigate

-- Checking for long-running transactions (cause of undo log bloat):
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_seconds,
    trx_rows_locked,
    trx_rows_modified,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started ASC;
-- Transactions running for > 60s are candidates for investigation/kill
```

**Q3. What is MySQL's default isolation level and why is it different from PostgreSQL's default?**
A: MySQL InnoDB defaults to REPEATABLE READ; PostgreSQL defaults to READ COMMITTED. This is a historically significant difference — MySQL chose REPEATABLE READ as the default because its original binary log format (statement-based replication) required it to prevent replication inconsistencies. PostgreSQL chose READ COMMITTED because it provides better concurrency for typical OLTP workloads:

```sql
-- Checking and setting isolation level in MySQL:

-- Check current session isolation level:
SELECT @@transaction_isolation;          -- MySQL 5.7.20+
SELECT @@tx_isolation;                   -- MySQL 5.7 legacy name (deprecated)
-- Returns: 'REPEATABLE-READ' (default)

-- Check global default:
SELECT @@global.transaction_isolation;

-- Set for current session:
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- Set for next transaction only (one-shot):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- Must be set before BEGIN (applies to next transaction, then reverts to session default)

-- Set globally (affects new connections, not existing ones):
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Persist across restarts (my.cnf / my.ini):
[mysqld]
transaction_isolation = READ-COMMITTED   -- note hyphen, not underscore

-- Why REPEATABLE READ was MySQL's historical default:
-- MySQL's original binary log format = STATEMENT-BASED replication
-- Statement-based replication: logs the SQL statement, not the rows changed
-- Under READ COMMITTED:
--   Primary: UPDATE accounts SET balance=balance*2 WHERE status='active'
--   Between execution on primary and replica: another transaction changes status
--   Replica executes same statement → different rows match → different result
-- REPEATABLE READ + statement-based binlog: consistent snapshot during statement
--   → same rows match on primary and replica → consistent replication
-- Modern binlog format (ROW-BASED, default since MySQL 5.7.7) logs changed rows
--   → READ COMMITTED is safe with row-based binlog
--   → Many production deployments switch to READ COMMITTED + row-based binlog

-- Check binlog format:
SHOW VARIABLES LIKE 'binlog_format';
-- 'ROW' = safe to use READ COMMITTED
-- 'STATEMENT' or 'MIXED' = keep REPEATABLE READ or change binlog format first
```

## Section 2: Read Uncommitted and Read Committed

**Q4. How does READ UNCOMMITTED behave in MySQL InnoDB and when would you use it?**
A: READ UNCOMMITTED in MySQL, like in PostgreSQL, allows dirty reads — reading uncommitted changes from other transactions. Unlike PostgreSQL (which silently upgrades READ UNCOMMITTED to READ COMMITTED via MVCC), MySQL InnoDB actually implements dirty reads at this level:

```sql
-- MySQL actually allows dirty reads at READ UNCOMMITTED (PostgreSQL does not):

-- Session A:
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
UPDATE accounts SET balance = 0 WHERE id = 'A1';
-- NOT committed yet

-- Session B (READ UNCOMMITTED):
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 0  ← DIRTY READ — Session A has not committed!

-- Session A:
ROLLBACK;
-- balance reverts to original (say 50000)

-- Session B re-reads:
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 50000  ← the dirty read value (0) never existed

-- Why MySQL can do dirty reads but PostgreSQL cannot:
-- PostgreSQL: MVCC always presents committed versions → dirty reads structurally impossible
-- MySQL InnoDB: at READ UNCOMMITTED, bypasses MVCC read view entirely
--               reads the current row directly without checking DB_TRX_ID visibility
--               → sees whatever is in the clustered index regardless of commit state

-- Legitimate uses in MySQL:
-- 1. Approximate COUNT(*) on large tables (avoid MVCC overhead):
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT COUNT(*) FROM large_table;
-- Avoids building a read view — faster for huge tables, acceptable for estimates

-- 2. Monitoring queries that need current state, not snapshot:
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT * FROM job_queue WHERE status = 'processing';
-- Shows current processing state including uncommitted changes

-- 3. Schema inspection (INFORMATION_SCHEMA queries):
-- MySQL internally uses READ UNCOMMITTED for some INFORMATION_SCHEMA reads

-- NEVER use for:
-- Financial calculations, eligibility checks, decisions with real-world consequences
```

**Q5. How does READ COMMITTED differ between MySQL and PostgreSQL in its snapshot model?**
A: Both databases take a new snapshot per statement at READ COMMITTED, but the underlying mechanism is different — PostgreSQL uses a transaction ID watermark; MySQL builds a new read view for each statement from the current active transaction list. The observable behavior is largely the same, but there is one important MySQL-specific difference: the locking behavior:

```sql
-- Snapshot model comparison at READ COMMITTED:

-- Both PostgreSQL and MySQL:
--   Snapshot taken at: start of each SQL statement (not the transaction)
--   Effect: each statement sees all commits that completed before THAT statement started
--   Non-repeatable reads: allowed (re-reading same row in same transaction can show different value)
--   Phantom reads: allowed

-- MySQL-specific READ COMMITTED behavior:

-- 1. Gap locks are RELEASED at READ COMMITTED (key MySQL difference):
--    At REPEATABLE READ: InnoDB uses gap locks to prevent phantoms
--    At READ COMMITTED: InnoDB does NOT use gap locks → higher concurrency for INSERTs
--    Consequence: phantom reads are possible (and allowed) at READ COMMITTED

-- Session A (READ COMMITTED):
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT * FROM loans WHERE amount > 100000;
-- Returns: { L3: 150000, L7: 200000 }

-- Session B:
INSERT INTO loans (id, amount) VALUES ('L11', 175000);
COMMIT;

-- Session A (same transaction):
SELECT * FROM loans WHERE amount > 100000;
-- Returns: { L3: 150000, L7: 200000, L11: 175000 }  ← PHANTOM (new row appeared)
-- This is expected at READ COMMITTED — phantom reads are allowed

-- 2. Semi-consistent read (MySQL InnoDB unique feature at READ COMMITTED):
--    When an UPDATE hits a locked row, MySQL may re-read the latest committed version
--    to check if the WHERE clause still matches before deciding to wait for the lock:

-- Session A:
BEGIN;
UPDATE loans SET status='approved' WHERE amount > 100000 AND status='pending';
-- Locks rows where amount > 100000 AND status='pending'

-- Session B (READ COMMITTED):
BEGIN;
UPDATE loans SET status='rejected' WHERE amount > 50000 AND status='pending';
-- Session B's WHERE clause overlaps — some rows might be locked by A
-- InnoDB semi-consistent read: checks the LATEST COMMITTED version of locked rows
-- If the latest committed version does NOT match Session B's WHERE clause:
--   → Session B skips that row (doesn't wait for lock)
-- If the latest committed version MATCHES Session B's WHERE clause:
--   → Session B waits for Session A's lock

-- This is a performance optimization unique to MySQL at READ COMMITTED
-- PostgreSQL does not have semi-consistent reads

-- Setting READ COMMITTED for a production application (with ROW-based binlog):
-- my.cnf:
[mysqld]
transaction_isolation = READ-COMMITTED
binlog_format = ROW       -- required for safe replication with READ COMMITTED

-- Application code (Node.js with mysql2):
const connection = await pool.getConnection();
await connection.query('SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED');
await connection.beginTransaction();
try {
    const [rows] = await connection.query(
        'SELECT balance FROM accounts WHERE id = ? FOR UPDATE', [accountId]
    );
    // ...
    await connection.commit();
} catch (err) {
    await connection.rollback();
    throw err;
} finally {
    connection.release();
}
```

## Section 3: Repeatable Read

**Q6. How does MySQL InnoDB implement REPEATABLE READ and what makes it different from the SQL standard's definition?**
A: MySQL InnoDB's REPEATABLE READ uses a consistent read view taken at the first read in the transaction. This is structurally similar to PostgreSQL's REPEATABLE READ. However, MySQL InnoDB also adds gap locks and next-key locks to prevent phantom reads — making its REPEATABLE READ implementation prevent phantoms for locked reads, but allowing phantoms for plain SELECT (consistent reads):

```sql
-- MySQL REPEATABLE READ: snapshot taken at first READ in transaction
-- (PostgreSQL: snapshot taken at first statement, which is also a read)

-- Session A (REPEATABLE READ, MySQL default):
BEGIN;
SELECT balance FROM accounts WHERE id = 'A1';
-- Snapshot created HERE → balance = 1000

-- Session B:
UPDATE accounts SET balance = 500 WHERE id = 'A1';
COMMIT;

-- Session A (same transaction, same snapshot):
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 1000 ← non-repeatable read prevented by read view

COMMIT;

-- The PHANTOM READ nuance in MySQL REPEATABLE READ:

-- CONSISTENT READ (plain SELECT) — uses read view — NO phantoms:
BEGIN;
SELECT * FROM loans WHERE amount > 100000;
-- Returns: { L3, L7 }   snapshot created here

-- (Session B inserts L11 with amount=175000 and commits)

SELECT * FROM loans WHERE amount > 100000;
-- Returns: { L3, L7 }   ← SAME snapshot → phantom prevented for consistent reads

-- LOCKING READ (SELECT ... FOR UPDATE / FOR SHARE) — uses current data + gap locks:
BEGIN;
SELECT * FROM loans WHERE amount > 100000 FOR UPDATE;
-- Returns: { L3, L7 }   AND acquires next-key locks on this range

-- (Session B tries to INSERT L11 with amount=175000)
-- Session B BLOCKS (gap lock prevents insert in the amount > 100000 range)

-- Session A re-reads:
SELECT * FROM loans WHERE amount > 100000 FOR UPDATE;
-- Returns: { L3, L7 }   ← Session B is still blocked → no phantom possible

COMMIT;
-- Session B unblocks, inserts L11

-- KEY INSIGHT: MySQL REPEATABLE READ prevents phantoms differently for:
--   Consistent read (plain SELECT): snapshot prevents phantoms → MVCC-based
--   Locking read (FOR UPDATE/SHARE): gap locks prevent phantoms → lock-based

-- PostgreSQL REPEATABLE READ:
--   Consistent read: snapshot prevents phantoms (same as MySQL)
--   Locking read: snapshot still applies → phantom prevention is purely MVCC-based
--   → PostgreSQL does NOT use gap locks even at REPEATABLE READ
```

**Q7. What are gap locks and next-key locks in MySQL InnoDB and why does PostgreSQL not need them?**
A: InnoDB uses gap locks to prevent phantom inserts in a range that a transaction has read. A next-key lock is the combination of a record lock on a row plus a gap lock on the interval before it. PostgreSQL avoids these entirely because its snapshot mechanism naturally prevents phantoms without any locking on reads:

```sql
-- Gap lock: locks the SPACE BETWEEN index entries (no actual row)
-- Prevents INSERT into the locked gap by other transactions
-- Does NOT block reads (other transactions can still SELECT the gap)
-- Held at: REPEATABLE READ and SERIALIZABLE

-- Index entries for amount column: 50000 ... 100000 ... 150000 ... 200000

-- When Session A does:
SELECT * FROM loans WHERE amount BETWEEN 100000 AND 200000 FOR UPDATE;
-- InnoDB acquires:
--   Record lock on 100000 (the row itself)
--   Gap lock on (50000, 100000) ← gap before 100000
--   Record lock on 150000
--   Gap lock on (100000, 150000) ← gap between 100000 and 150000
--   Record lock on 200000
--   Gap lock on (150000, 200000) ← gap between 150000 and 200000
--   Gap lock on (200000, +∞)    ← gap after last entry in range

-- Next-key lock = record lock + gap lock on the preceding gap:
--   Next-key lock on 150000 = record lock(150000) + gap lock(100000, 150000)

-- Effect: Session B cannot INSERT a row with amount = 175000
--   175000 falls in gap (150000, 200000) → blocked by gap lock

-- Session B:
INSERT INTO loans (id, amount) VALUES ('L11', 175000);
-- BLOCKS until Session A commits or rolls back

-- Gap lock on EQUALITY condition:
SELECT * FROM loans WHERE id = 'L1' FOR UPDATE;
-- If id='L1' EXISTS: record lock only (no gap lock needed — exact row locked)
-- If id='L1' DOES NOT EXIST: gap lock on the gap where 'L1' would be
--   → prevents INSERT of 'L1' by another transaction

-- GAP LOCK DEADLOCKS (MySQL-specific gotcha):
-- Two transactions both try to insert the same key:
-- Session A: INSERT INTO loans (id) VALUES ('L99') → acquires gap lock, waits for row insert
-- Session B: INSERT INTO loans (id) VALUES ('L99') → acquires same gap lock, waits for row insert
-- DEADLOCK: both hold gap locks, both waiting for the INSERT to complete
-- Error: ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

-- Disabling gap locks (READ COMMITTED eliminates them):
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- At READ COMMITTED: InnoDB does NOT acquire gap locks
-- Result: phantoms are allowed (by definition) AND INSERT throughput improves
-- This is often the right tradeoff for high-concurrency OLTP

-- Why PostgreSQL doesn't need gap locks:
-- PostgreSQL's snapshot at REPEATABLE READ covers the entire table state at snapshot time
-- Any row inserted AFTER the snapshot is invisible to the transaction → phantom impossible
-- No gap needs to be locked because MVCC snapshot is the barrier
-- PostgreSQL readers NEVER block writers (even at REPEATABLE READ)

-- Checking locks held in MySQL:
SELECT
    engine_lock_id,
    engine_transaction_id,
    thread_id,
    object_schema,
    object_name,
    index_name,
    lock_type,        -- 'RECORD' or 'TABLE'
    lock_mode,        -- 'X', 'S', 'X,GAP', 'S,GAP', 'X,REC_NOT_GAP', 'X,INSERT_INTENTION'
    lock_status,      -- 'GRANTED' or 'WAITING'
    lock_data         -- key value or 'supremum pseudo-record' for gap after last entry
FROM performance_schema.data_locks;
-- lock_mode='X,GAP': exclusive gap lock (no row, just the space)
-- lock_mode='X,REC_NOT_GAP': record lock without gap lock (at READ COMMITTED)
-- lock_mode='X,INSERT_INTENTION': intention to insert — compatible with gap locks
--   but blocked if a gap lock exists covering the insertion point
```

**Q8. What is the "consistent read after DML" anomaly unique to MySQL REPEATABLE READ?**
A: MySQL InnoDB has a subtle behavior where a transaction can see its OWN uncommitted writes but uses the snapshot for other transactions' data. This leads to a specific anomaly: after a transaction modifies data, a subsequent SELECT in the same transaction sees the modification — even if the snapshot predates the change — because InnoDB mixes snapshot reads with current-version reads for rows the current transaction has modified:

```sql
-- The self-modification visibility rule:
-- A transaction always sees its own uncommitted changes in subsequent reads
-- This is expected (SELECT should see what you just wrote)
-- BUT combined with the snapshot, it creates a subtle inconsistency:

-- Session A (REPEATABLE READ):
BEGIN;
SELECT COUNT(*) FROM loans WHERE status = 'active';
-- Returns: 5   (snapshot created: sees 5 active loans)

UPDATE loans SET status = 'active' WHERE status = 'pending' AND amount > 200000;
-- Updates 3 rows: they were 'pending' → now 'active'

SELECT COUNT(*) FROM loans WHERE status = 'active';
-- Returns: 8   ← sees its OWN update (3 more active loans)
-- BUT the snapshot still applies for OTHER transactions' changes

-- This is correct and expected — you see your own changes
-- The anomaly arises in more complex scenarios:

-- Session A (REPEATABLE READ):
BEGIN;
SELECT * FROM loans WHERE id = 'L1';
-- Returns: { id: L1, status: 'pending' }   snapshot created

-- Session B:
UPDATE loans SET status = 'approved' WHERE id = 'L1';
COMMIT;

-- Session A:
UPDATE loans SET amount = 60000 WHERE id = 'L1' AND status = 'pending';
-- InnoDB: checks CURRENT version of L1 (not snapshot!) for the WHERE clause of UPDATE
-- Current version: status = 'approved' (Session B's committed change)
-- WHERE status = 'pending' → does NOT match → 0 rows updated

-- Session A then reads:
SELECT * FROM loans WHERE id = 'L1';
-- Returns: { id: L1, status: 'pending' }   ← snapshot still shows 'pending'!
-- But the UPDATE just saw 'approved' → inconsistency between SELECT and UPDATE

-- This happens because:
-- SELECT uses snapshot (consistent read) → sees old 'pending'
-- UPDATE/DELETE uses CURRENT data + locks → sees committed 'approved'
-- If UPDATE succeeds: subsequent SELECT shows the new value (own change visible)
-- If UPDATE fails (0 rows): SELECT still shows snapshot value ('pending')

-- This is a known MySQL behavior and not a bug — it's documented
-- It can cause application confusion: "I checked the status was 'pending' but my update affected 0 rows"

-- Solution: use SELECT ... FOR UPDATE to lock the row before updating:
BEGIN;
SELECT * FROM loans WHERE id = 'L1' FOR UPDATE;
-- FOR UPDATE reads CURRENT version (not snapshot) + acquires lock
-- Returns: { id: L1, status: 'approved' }   ← current version
-- Now application sees the correct current state before deciding to update
UPDATE loans SET amount = 60000 WHERE id = 'L1' AND status = 'pending';
-- Now the application knows status='approved' → can handle accordingly
COMMIT;
```

## Section 4: Serializable

**Q9. How does MySQL InnoDB implement SERIALIZABLE isolation and how does it differ from PostgreSQL's SSI?**
A: MySQL InnoDB implements SERIALIZABLE using strict two-phase locking (2PL) — every read acquires a shared lock, every write acquires an exclusive lock, and all locks are held until commit. This is the traditional approach. PostgreSQL uses SSI (Serializable Snapshot Isolation) — an optimistic approach with dependency tracking. The performance characteristics are dramatically different:

```sql
-- MySQL SERIALIZABLE: 2PL (Two-Phase Locking)
-- Every SELECT automatically becomes SELECT ... FOR SHARE
-- Reads BLOCK writers; writers BLOCK readers

-- Session A (SERIALIZABLE):
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
SELECT * FROM loans WHERE status = 'active';
-- InnoDB acquires SHARED lock on ALL matching rows + gap locks on the range
-- Equivalent to: SELECT * FROM loans WHERE status = 'active' FOR SHARE

-- Session B:
BEGIN;
UPDATE loans SET amount = 60000 WHERE id = 'L1';
-- L1 has status='active' → it is LOCKED by Session A's shared lock
-- Session B BLOCKS waiting for Session A to release the shared lock

-- Session A commits → Session B unblocks → update succeeds

-- Write skew prevention (doctor on-call example):
-- Session A (SERIALIZABLE):
BEGIN;
SELECT COUNT(*) FROM oncall;  -- returns 2 → acquires shared lock + next-key locks on ALL rows
DELETE FROM oncall WHERE doctor = 'Alice';  -- tries to acquire exclusive lock
-- Can proceed (shared → exclusive upgrade on Alice's row)
COMMIT;

-- Session B (SERIALIZABLE):
BEGIN;
SELECT COUNT(*) FROM oncall;  -- BLOCKS on shared lock (Session A holds shared locks)
-- Waits until Session A commits
-- After Session A commits: count = 1 → knows only 1 doctor remains → cannot delete
-- Returns 1 → application logic: "only one doctor left, cannot remove"
-- Write skew prevented by blocking

-- PostgreSQL SERIALIZABLE (SSI): optimistic approach
-- Reads do NOT block writes → both transactions proceed concurrently
-- SSI tracks read/write dependencies → aborts if a dangerous cycle is detected
-- One transaction gets ERROR 40001 → must retry
-- No blocking, but requires retry logic

-- Performance comparison:
--
--              │ MySQL SERIALIZABLE      │ PostgreSQL SERIALIZABLE
-- ─────────────┼─────────────────────────┼───────────────────────────
-- Reader blocks │ YES (shared lock)       │ NO (MVCC snapshot)
-- Writer blocks │ YES (waiting for reader)│ NO (writes proceed)
-- Conflict res  │ Blocking (wait)         │ Abort + retry (optimistic)
-- Throughput    │ Low (high contention)   │ Higher (but retry overhead)
-- Deadlock risk │ High                   │ Lower (no blocking reads)

-- MySQL SERIALIZABLE in practice:
-- Very rarely used directly — the read-locking causes severe contention
-- Alternative: use SELECT ... FOR SHARE explicitly at REPEATABLE READ
-- This gives the same safety for specific queries without blanket locking

-- Checking lock waits and deadlocks:
SHOW ENGINE INNODB STATUS\G
-- Look for: "LATEST DETECTED DEADLOCK" and "TRANSACTIONS" sections
-- Or use:
SELECT * FROM performance_schema.data_lock_waits\G
```

## Section 5: Key Behavioral Differences from PostgreSQL

**Q10. What are the most important behavioral differences between MySQL and PostgreSQL isolation levels that a developer switching databases must know?**
A: There are six critical behavioral differences that cause real bugs when developers assume PostgreSQL behavior in MySQL or vice versa:

```sql
-- ── Difference 1: Default isolation level ────────────────────────────────────
-- PostgreSQL: READ COMMITTED (more concurrent, non-repeatable reads allowed)
-- MySQL:      REPEATABLE READ (more conservative, snapshot held for transaction)

-- Impact: code written for MySQL that relies on a stable snapshot across statements
-- will break silently if moved to PostgreSQL (READ COMMITTED takes new snapshot per statement)

-- PostgreSQL — non-repeatable read is normal:
BEGIN;
SELECT balance FROM accounts WHERE id='A1';  -- 1000
-- (another session updates balance to 500 and commits)
SELECT balance FROM accounts WHERE id='A1';  -- 500 ← different! new snapshot per statement
COMMIT;

-- MySQL default (REPEATABLE READ) — no non-repeatable read:
BEGIN;
SELECT balance FROM accounts WHERE id='A1';  -- 1000
-- (another session updates balance to 500 and commits)
SELECT balance FROM accounts WHERE id='A1';  -- 1000 ← same! snapshot held
COMMIT;

-- ── Difference 2: Gap locks (MySQL only) ─────────────────────────────────────
-- PostgreSQL: no gap locks at any isolation level (MVCC handles phantoms)
-- MySQL:      gap locks at REPEATABLE READ and SERIALIZABLE

-- Impact: MySQL deadlocks caused by gap lock conflicts are impossible in PostgreSQL
-- MySQL-specific deadlock pattern:
-- T1: INSERT INTO t VALUES (5);  -- gap lock on (4, 6)
-- T2: INSERT INTO t VALUES (5);  -- gap lock on (4, 6) → DEADLOCK
-- PostgreSQL: no gap locks → no such deadlock pattern

-- ── Difference 3: Phantom reads at REPEATABLE READ ────────────────────────────
-- PostgreSQL: phantoms prevented for ALL reads (consistent + locking)
-- MySQL:      phantoms prevented for consistent reads (plain SELECT)
--             but NOT for locking reads (FOR UPDATE) without gap locks

-- MySQL REPEATABLE READ — phantom with FOR UPDATE if gap locks release:
BEGIN;
SELECT * FROM loans WHERE amount > 100000 FOR UPDATE;
-- Returns: { L3, L7 }
-- Gap locks held: (100000, +∞)

-- Another session inserts L11 (175000) BUT ALSO at a gap lock boundary...
-- In some edge cases (supremum record, purged history), MySQL may miss a phantom
-- PostgreSQL: snapshot at REPEATABLE READ is a clean barrier → no phantom ever

-- ── Difference 4: Autocommit behavior ────────────────────────────────────────
-- PostgreSQL: no autocommit (must use BEGIN/COMMIT; single statements NOT auto-committed)
-- MySQL:      autocommit = ON by default (each statement is its own transaction)

-- MySQL autocommit:
SET autocommit = 1;  -- default
UPDATE accounts SET balance = 500 WHERE id = 'A1';
-- This is implicitly: BEGIN; UPDATE ...; COMMIT;
-- No explicit BEGIN needed
-- No way to rollback (already committed)

-- MySQL disable autocommit:
SET autocommit = 0;
UPDATE accounts SET balance = 500 WHERE id = 'A1';
-- Now uncommitted — must COMMIT or ROLLBACK explicitly

-- PostgreSQL: autocommit is always "on" at the protocol level but each statement
-- that is not inside a BEGIN/COMMIT is its own implicit transaction
-- Behavior is similar but the mental model differs

-- ── Difference 5: SAVEPOINT behavior ─────────────────────────────────────────
-- Both support SAVEPOINTs but MySQL resets the autocommit context after ROLLBACK TO SAVEPOINT

-- MySQL:
BEGIN;
INSERT INTO loans VALUES ('L1', 50000);
SAVEPOINT sp1;
INSERT INTO loans VALUES ('L2', 60000);
ROLLBACK TO SAVEPOINT sp1;  -- undoes L2 insert, L1 still exists
-- Transaction is STILL active (not committed)
COMMIT;  -- commits L1 only

-- PostgreSQL: identical behavior — SAVEPOINTs work the same way

-- ── Difference 6: Error handling and rollback behavior ───────────────────────
-- PostgreSQL: ANY error inside a transaction aborts the ENTIRE transaction
--             Subsequent statements until ROLLBACK get: "ERROR: current transaction is aborted"
-- MySQL:      errors do NOT automatically abort the transaction
--             You can continue executing statements after an error

-- PostgreSQL:
BEGIN;
INSERT INTO accounts VALUES ('A1', 1000);
INSERT INTO accounts VALUES ('A1', 2000);  -- duplicate key ERROR
-- Transaction is now ABORTED
SELECT 1;  -- ERROR: current transaction is aborted, commands ignored until end of transaction block
ROLLBACK;  -- must rollback

-- MySQL:
BEGIN;
INSERT INTO accounts VALUES ('A1', 1000);
INSERT INTO accounts VALUES ('A1', 2000);  -- duplicate key ERROR (statement fails)
-- Transaction is STILL ACTIVE (not aborted!)
SELECT balance FROM accounts WHERE id='A1';  -- Works fine! Returns 1000
COMMIT;  -- commits the first INSERT (A1 with balance 1000)

-- This means MySQL applications MUST check for errors per statement
-- and decide whether to continue or rollback
-- PostgreSQL applications can rely on error = abort (simpler error handling)

-- Node.js implication:
// PostgreSQL: one try/catch around the whole transaction is sufficient
// MySQL: must check rowsAffected or catch errors per statement to avoid partial commits
```

**Q11. How does locking behavior differ between MySQL and PostgreSQL for `SELECT FOR UPDATE` and what are the MySQL-specific lock modes?**

```sql
-- PostgreSQL FOR UPDATE lock modes:
--   FOR UPDATE: exclusive row lock (blocks all other FOR UPDATE and FOR SHARE)
--   FOR SHARE:  shared row lock (blocks FOR UPDATE, allows other FOR SHARE)
--   FOR NO KEY UPDATE: weaker exclusive (allows FOR SHARE on non-key columns)
--   FOR KEY SHARE: weakest shared (only blocks FOR UPDATE, not FOR NO KEY UPDATE)
--   NOWAIT: fail immediately if lock unavailable
--   SKIP LOCKED: skip locked rows (ideal for queues)

-- MySQL InnoDB FOR UPDATE lock modes:
--   FOR UPDATE: exclusive next-key lock (record + gap)
--   FOR SHARE:  shared next-key lock (MySQL 8.0+; LOCK IN SHARE MODE in older versions)
--   NOWAIT:     fail immediately (MySQL 8.0+)
--   SKIP LOCKED: skip locked rows (MySQL 8.0+)

-- MySQL LOCK IN SHARE MODE (pre-8.0 equivalent of FOR SHARE):
SELECT * FROM loans WHERE id = 'L1' LOCK IN SHARE MODE;
-- MySQL 8.0+:
SELECT * FROM loans WHERE id = 'L1' FOR SHARE;

-- MySQL-specific: OF table syntax for locking specific tables in a join:
SELECT l.*, a.balance
FROM loans l
JOIN accounts a ON l.account_id = a.id
WHERE l.id = 'L1'
FOR UPDATE OF l;         -- MySQL 8.0+: lock only loans table, not accounts
-- PostgreSQL equivalent: FOR UPDATE OF l (identical syntax)

-- Locking non-existent rows (important difference):
-- PostgreSQL FOR UPDATE on non-existent row: no lock taken (nothing to lock)
-- MySQL FOR UPDATE on non-existent row: gap lock on the position where the row would be
--   → prevents another transaction from inserting that row

-- Example:
-- Session A:
SELECT * FROM loans WHERE id = 'L99' FOR UPDATE;
-- PostgreSQL: returns 0 rows, no lock
-- MySQL: returns 0 rows, BUT acquires gap lock around 'L99' position

-- Session B:
INSERT INTO loans (id, amount) VALUES ('L99', 50000);
-- PostgreSQL: succeeds immediately (no lock from Session A)
-- MySQL: BLOCKS (gap lock prevents insert)

-- This makes MySQL more consistent for "check and insert" patterns:
-- MySQL gap lock ensures if you checked that L99 doesn't exist, nobody can insert it
-- PostgreSQL: you'd need SERIALIZABLE or a unique constraint + handle the conflict

-- SKIP LOCKED for job queues (both databases):
-- MySQL:
SELECT id, payload FROM job_queue
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- PostgreSQL (identical):
SELECT id, payload FROM job_queue
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- Both implementations: skip rows locked by other workers → no blocking
-- Each worker atomically claims a different job
```

## Section 6: Practical Configuration and Patterns

**Q12. How do you implement safe financial transactions in MySQL that avoid the common race conditions?**

```sql
-- Pattern 1: Lost update prevention with FOR UPDATE (both MySQL and PostgreSQL):

-- The race condition:
-- T1: SELECT balance FROM accounts WHERE id='A1' → 10000
-- T2: SELECT balance FROM accounts WHERE id='A1' → 10000
-- T1: UPDATE accounts SET balance=7000 WHERE id='A1'  (10000 - 3000)
-- T2: UPDATE accounts SET balance=6000 WHERE id='A1'  (10000 - 4000)
-- Result: 6000 (T1's deduction of 3000 is lost)

-- Fix: SELECT FOR UPDATE:
BEGIN;
SELECT balance FROM accounts WHERE id='A1' FOR UPDATE;
-- Acquires exclusive lock on A1
-- T2 trying the same: BLOCKS here until T1 commits
UPDATE accounts SET balance = balance - 3000 WHERE id='A1';
COMMIT;
-- T2 unblocks: re-reads balance (now 7000), deducts 4000 → 3000 ✓

-- Pattern 2: Atomic UPDATE (no separate SELECT, MySQL and PostgreSQL):
UPDATE accounts SET balance = balance - 3000
WHERE id = 'A1' AND balance >= 3000;  -- overdraft protection in WHERE clause
-- If 0 rows affected: insufficient funds (balance < 3000)
-- Row-level write lock serializes concurrent updates automatically
-- No need to raise isolation level

-- Pattern 3: Optimistic locking with version column (MySQL):
-- MySQL doesn't have PostgreSQL's 40001 serialization error at REPEATABLE READ
-- Optimistic locking must be implemented at application level:

ALTER TABLE accounts ADD COLUMN version INT DEFAULT 0;

-- Read with version:
SELECT balance, version FROM accounts WHERE id='A1';
-- Returns: balance=10000, version=5

-- Update with version check:
UPDATE accounts SET balance=7000, version=6
WHERE id='A1' AND version=5;
-- If 0 rows affected: concurrent update detected (version changed) → retry

-- Node.js:
async function debitWithOptimisticLock(accountId: string, amount: number) {
    for (let attempt = 0; attempt < 3; attempt++) {
        const [rows] = await pool.query(
            'SELECT balance, version FROM accounts WHERE id = ?', [accountId]
        );
        const { balance, version } = rows[0];
        if (balance < amount) throw new Error('Insufficient funds');

        const [result] = await pool.query(
            'UPDATE accounts SET balance = ?, version = ? WHERE id = ? AND version = ?',
            [balance - amount, version + 1, accountId, version]
        );
        if (result.affectedRows === 1) return;  // success
        // affectedRows = 0: version changed → retry
        await sleep(50 * 2 ** attempt);
    }
    throw new Error('Could not acquire optimistic lock after 3 attempts');
}

-- Pattern 4: INSERT ... ON DUPLICATE KEY UPDATE (MySQL-specific, no PostgreSQL equivalent):
-- MySQL's UPSERT — atomic check-insert-or-update:
INSERT INTO loan_counters (borrower_id, loan_count)
VALUES ('B1', 1)
ON DUPLICATE KEY UPDATE loan_count = loan_count + 1;
-- If borrower_id exists: increments count (atomic)
-- If not exists: inserts with count=1
-- Prevents race condition between CHECK and INSERT

-- PostgreSQL equivalent: INSERT ... ON CONFLICT DO UPDATE (UPSERT):
INSERT INTO loan_counters (borrower_id, loan_count)
VALUES ('B1', 1)
ON CONFLICT (borrower_id) DO UPDATE SET loan_count = loan_counters.loan_count + 1;
```

**Q13. How do you diagnose and resolve deadlocks in MySQL InnoDB?**

```sql
-- Deadlock detection:
-- InnoDB has a background deadlock detector that runs continuously
-- When detected: InnoDB picks the transaction with fewer rows modified → rolls it back
-- Error returned to that transaction: ERROR 1213 (40001): Deadlock found

-- Getting deadlock details:
SHOW ENGINE INNODB STATUS\G
-- Look for: "LATEST DETECTED DEADLOCK" section
-- Shows: which transactions were involved, which locks were held, which were waiting

-- Performance Schema deadlock history (MySQL 8.0+):
-- Enable events_statements_history_long for full query capture
UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES'
WHERE NAME = 'events_statements_history_long';

-- Recent deadlock information:
SELECT * FROM performance_schema.events_statements_history_long
WHERE MYSQL_ERRNO = 1213
ORDER BY TIMER_START DESC LIMIT 10;

-- Common MySQL deadlock patterns:

-- Pattern 1: Lock order inconsistency (same as PostgreSQL):
-- T1: UPDATE accounts WHERE id=1, then UPDATE accounts WHERE id=2
-- T2: UPDATE accounts WHERE id=2, then UPDATE accounts WHERE id=1
-- → deadlock
-- Fix: always update rows in consistent order (e.g., ascending id)

-- Pattern 2: Gap lock + insert deadlock (MySQL-specific):
-- At REPEATABLE READ with gap locks:
-- T1: SELECT * FROM loans WHERE id='L99' FOR UPDATE
--     (L99 doesn't exist → gap lock acquired on (L98, L100))
-- T2: SELECT * FROM loans WHERE id='L99' FOR UPDATE
--     (L99 doesn't exist → tries to acquire same gap lock → WAITS)
-- T1: INSERT INTO loans (id) VALUES ('L99')
--     (INSERT INTENTION lock → compatible with gap lock → but now T2 holds gap lock)
-- → deadlock
-- Fix: use READ COMMITTED (removes gap locks) or rethink the select-then-insert pattern

-- Pattern 3: Foreign key deadlock (MySQL-specific):
-- InnoDB acquires shared lock on PARENT row when child row is inserted/updated
-- If parent is being modified concurrently → shared lock conflicts with exclusive lock
-- Fix: lock parent rows explicitly before child operations

-- Application-level deadlock handling (Node.js with mysql2):
async function executeWithDeadlockRetry<T>(
    fn: (conn: Connection) => Promise<T>,
    maxRetries = 3,
): Promise<T> {
    const conn = await pool.getConnection();
    for (let attempt = 0; attempt <= maxRetries; attempt++) {
        try {
            await conn.beginTransaction();
            const result = await fn(conn);
            await conn.commit();
            return result;
        } catch (err: any) {
            await conn.rollback();
            const isDeadlock = err.code === 'ER_LOCK_DEADLOCK';    // 1213
            const isLockTimeout = err.code === 'ER_LOCK_WAIT_TIMEOUT'; // 1205
            if ((isDeadlock || isLockTimeout) && attempt < maxRetries) {
                const delay = Math.min(50 * 2 ** attempt + Math.random() * 50, 1000);
                await sleep(delay);
                continue;
            }
            throw err;
        } finally {
            if (attempt === maxRetries || /* success */ true) conn.release();
        }
    }
}
```

## Section 7: Scenario-Based Questions

**Q14. "Your MySQL application processes concurrent loan disbursements. Two concurrent requests both pass the 'loan not yet disbursed' check and both disburse the same loan. Which anomaly is this, and how do you fix it specifically for MySQL?"**

```sql
-- Diagnosis: Lost update / check-then-act race under default REPEATABLE READ
-- Both transactions read disbursed_at=NULL from their snapshots
-- Both pass the check, both execute the disbursement

-- The broken flow (REPEATABLE READ default):
-- T1: SELECT disbursed_at FROM loans WHERE id='L1' → NULL  (snapshot created)
-- T2: SELECT disbursed_at FROM loans WHERE id='L1' → NULL  (own snapshot, also NULL)
-- T1: UPDATE loans SET disbursed_at=NOW() WHERE id='L1' → success
-- T1: COMMIT
-- T2: UPDATE loans SET disbursed_at=NOW() WHERE id='L1' → success (overwrites T1!)
-- T2: COMMIT
-- Result: double disbursement

-- Fix 1: SELECT FOR UPDATE (lock then check):
BEGIN;
SELECT disbursed_at FROM loans WHERE id='L1' FOR UPDATE;
-- FOR UPDATE reads CURRENT version (not snapshot) + acquires exclusive lock
-- T2 trying the same: BLOCKS here

-- T1 proceeds:
-- disbursed_at = NULL → proceed with disbursement
UPDATE loans SET disbursed_at = NOW() WHERE id='L1';
INSERT INTO disbursements (loan_id, amount) VALUES ('L1', 50000);
COMMIT;

-- T2 unblocks: re-reads CURRENT version → disbursed_at = (T1's timestamp)
-- disbursed_at IS NOT NULL → abort, return "already disbursed"
ROLLBACK;

-- Fix 2: Conditional UPDATE (atomic, no need for SELECT first):
UPDATE loans
   SET disbursed_at = NOW()
 WHERE id = 'L1'
   AND disbursed_at IS NULL;         -- only if not yet disbursed
-- affectedRows = 1: this transaction won the race → proceed with INSERT
-- affectedRows = 0: another transaction already disbursed → abort

-- Node.js implementation:
async function disburseLoan(loanId: string, amount: number) {
    const conn = await pool.getConnection();
    try {
        await conn.beginTransaction();

        const [result] = await conn.query(
            'UPDATE loans SET disbursed_at = NOW() WHERE id = ? AND disbursed_at IS NULL',
            [loanId]
        );

        if ((result as ResultSetHeader).affectedRows === 0) {
            await conn.rollback();
            throw new ConflictException('Loan already disbursed');
        }

        await conn.query(
            'INSERT INTO disbursements (loan_id, amount, disbursed_at) VALUES (?, ?, NOW())',
            [loanId, amount]
        );

        await conn.commit();
    } catch (err) {
        await conn.rollback();
        throw err;
    } finally {
        conn.release();
    }
}

-- Fix 3: UNIQUE constraint (database-level idempotency, same as PostgreSQL):
ALTER TABLE disbursements ADD UNIQUE KEY uq_loan_disbursement (loan_id);
-- Second INSERT fails with ER_DUP_ENTRY (1062) → catch and treat as idempotent
```

**Q15. "A MySQL team is experiencing mysterious data inconsistencies in a report that joins three tables. The report runs under the default isolation level and takes 30 seconds. Different runs of the same report show different totals. Diagnose and fix."**

```sql
-- Diagnosis: Read skew under default REPEATABLE READ
-- Wait — MySQL REPEATABLE READ should prevent this via snapshot!
-- But the snapshot is taken at the FIRST READ of the transaction
-- If the report runs without an explicit BEGIN, each statement auto-commits
-- → autocommit = ON (MySQL default) → each JOIN is its own transaction
-- → each statement sees a different snapshot
-- → READ SKEW across the three table reads

-- Check autocommit:
SELECT @@autocommit;  -- returns 1 (ON) → each statement auto-commits!

-- The broken pattern (autocommit ON, no BEGIN):
-- Statement 1: SELECT SUM(amount) FROM disbursements WHERE date='2024-01'
--   → own transaction, snapshot at time T1
-- (concurrent update changes repayments between T1 and T2)
-- Statement 2: SELECT SUM(amount) FROM repayments WHERE date='2024-01'
--   → OWN transaction, snapshot at time T2
-- Statement 3: SELECT balance FROM loan_summary WHERE month='2024-01'
--   → OWN transaction, snapshot at time T3
-- All three statements see different database states → totals inconsistent

-- Fix: wrap in explicit transaction (forces single snapshot):
SET autocommit = 0;
-- Or: use explicit BEGIN

BEGIN;
-- Now all three queries use the SAME snapshot (taken at first read):
SELECT SUM(amount) AS disbursements
FROM disbursements WHERE MONTH(disbursed_at) = 1 AND YEAR(disbursed_at) = 2024;

SELECT SUM(amount) AS repayments
FROM repayments WHERE MONTH(paid_at) = 1 AND YEAR(paid_at) = 2024;

SELECT SUM(outstanding_balance) AS outstanding
FROM loan_accounts;
COMMIT;
-- All three queries see the same consistent database state

-- Node.js with mysql2 — consistent multi-query report:
async function generateMonthlyReport(year: number, month: number) {
    const conn = await pool.getConnection();
    try {
        await conn.beginTransaction();
        // All queries below share the same REPEATABLE READ snapshot:

        const [[{ disbursements }]] = await conn.query<RowDataPacket[]>(
            'SELECT SUM(amount) AS disbursements FROM disbursements WHERE YEAR(disbursed_at)=? AND MONTH(disbursed_at)=?',
            [year, month]
        );
        const [[{ repayments }]] = await conn.query<RowDataPacket[]>(
            'SELECT SUM(amount) AS repayments FROM repayments WHERE YEAR(paid_at)=? AND MONTH(paid_at)=?',
            [year, month]
        );
        const [[{ outstanding }]] = await conn.query<RowDataPacket[]>(
            'SELECT SUM(outstanding_balance) AS outstanding FROM loan_accounts'
        );

        await conn.commit();
        return { disbursements, repayments, outstanding };
    } catch (err) {
        await conn.rollback();
        throw err;
    } finally {
        conn.release();
    }
}

-- Additional fix: use READ ONLY transaction hint (MySQL 5.6+):
START TRANSACTION READ ONLY;
-- Hint: this transaction will not write → InnoDB can optimize (skip undo log checks)
-- Does NOT change isolation level — still REPEATABLE READ with consistent snapshot
```

**Q16. "You're migrating a Node.js application from PostgreSQL to MySQL. The app uses REPEATABLE READ on PostgreSQL for financial calculations. What specific behaviors must you audit and potentially change in the application code?"**

```sql
-- Audit checklist for PostgreSQL → MySQL migration at REPEATABLE READ:

-- ── Check 1: Serialization error handling (40001) ─────────────────────────────
-- PostgreSQL REPEATABLE READ: throws 40001 on write-write conflict
-- MySQL REPEATABLE READ: does NOT throw 40001 on write-write conflict
--   Instead: the second UPDATE blocks and waits (using lock wait timeout)
--   → The second UPDATE proceeds after first commits (no retry needed for 40001)
--   → BUT: lock_wait_timeout exceeded → throws ER_LOCK_WAIT_TIMEOUT (1205)

-- PostgreSQL code that retries on 40001:
try {
    await executeTransaction();
} catch (err) {
    if (err.code === '40001') await retry();  // serialization failure
}

-- MySQL equivalent: retry on 1205 (lock wait timeout), not 40001
try {
    await executeTransaction();
} catch (err) {
    if (err.errno === 1205) await retry();   // ER_LOCK_WAIT_TIMEOUT
    if (err.errno === 1213) await retry();   // ER_LOCK_DEADLOCK
}

-- ── Check 2: Error handling within transactions ───────────────────────────────
-- PostgreSQL: any error aborts the ENTIRE transaction
-- MySQL: errors fail the STATEMENT but not the transaction

-- PostgreSQL code (safe assumption: error = abort):
try {
    await client.query('INSERT INTO loans VALUES (...)');
    await client.query('INSERT INTO accounts VALUES (...)');  // if this fails → all rolled back
    await client.query('COMMIT');
} catch (err) {
    await client.query('ROLLBACK');
}

-- MySQL: must check each statement OR set explicit error handling:
-- Option A: check affectedRows after each statement
-- Option B: use STRICT SQL mode to make MySQL abort on error (like PostgreSQL):
SET sql_mode = 'STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
-- With STRICT mode: MySQL behavior is closer to PostgreSQL (error → transaction abort)

-- Check current sql_mode:
SELECT @@sql_mode;
-- Ensure STRICT_TRANS_TABLES is included

-- ── Check 3: Autocommit assumption ───────────────────────────────────────────
-- PostgreSQL: no autocommit (every statement needs explicit transaction or runs alone)
-- MySQL: autocommit=ON by default

-- If PostgreSQL code assumes statements without BEGIN are NOT committed:
-- This assumption holds in MySQL with autocommit=OFF
-- Or: always wrap in explicit BEGIN/COMMIT in application code

-- ── Check 4: Phantom read behavior ───────────────────────────────────────────
-- PostgreSQL REPEATABLE READ: phantoms impossible (MVCC snapshot covers everything)
-- MySQL REPEATABLE READ: phantoms prevented for consistent reads
--                        but edge cases exist with locking reads

-- Code that relies on "no phantom ever at REPEATABLE READ":
-- If the code does plain SELECT (not FOR UPDATE) → safe in MySQL too
-- If the code does SELECT ... FOR UPDATE and then re-reads → test carefully in MySQL

-- ── Check 5: FOR UPDATE locking behavior difference ───────────────────────────
-- PostgreSQL FOR UPDATE on non-existent row: no lock (nothing to lock)
-- MySQL FOR UPDATE on non-existent row: gap lock (prevents concurrent insert)

-- Code that uses SELECT FOR UPDATE to "reserve a spot":
SELECT * FROM slots WHERE id='S1' FOR UPDATE;
-- If slot doesn't exist:
-- PostgreSQL: 0 rows, no lock → concurrent INSERT of S1 is possible
-- MySQL: 0 rows, gap lock → concurrent INSERT of S1 is blocked

-- ── Check 6: FOR UPDATE visibility (most critical for financial code) ──────────
-- PostgreSQL FOR UPDATE: reads current committed version (bypasses snapshot)

-- SELECT (no FOR UPDATE): PostgreSQL uses per-statement snapshot (READ COMMITTED)
```

**Tip for interviews:** Five things separate strong candidates on MySQL vs PostgreSQL isolation: (1) knowing that **MySQL defaults to REPEATABLE READ while PostgreSQL defaults to READ COMMITTED** (Q3) — and the historical reason (statement-based binary log replication required snapshot stability), and that switching MySQL to READ COMMITTED is safe with row-based binlog (`binlog_format=ROW`); (2) explaining **gap locks and next-key locks as MySQL-specific mechanisms** (Q7) — PostgreSQL prevents phantoms purely via MVCC snapshot and has zero gap locks even at REPEATABLE READ, while MySQL uses gap locks at REPEATABLE READ to prevent phantom inserts into locked ranges — this causes MySQL-specific deadlock patterns (two inserts competing for the same gap) that are impossible in PostgreSQL; (3) knowing the **consistent-read vs locking-read phantom distinction in MySQL** (Q6) — plain `SELECT` uses the transaction's snapshot (phantoms prevented), but the edge cases around locking reads and gap lock coverage mean MySQL's phantom prevention is mechanistically different from PostgreSQL's clean snapshot barrier; (4) understanding the **MySQL statement-error-does-not-abort-transaction behavior** (Q10) — in PostgreSQL, any error inside a transaction aborts the whole transaction and subsequent statements fail until `ROLLBACK`; in MySQL without `STRICT_TRANS_TABLES` mode, a statement error fails only that statement and the transaction continues — this is the most common source of partial-commit bugs when migrating from PostgreSQL; and (5) being precise about **FOR UPDATE visibility semantics in MySQL** (Q8) — at REPEATABLE READ, plain `SELECT` uses the transaction's snapshot but `SELECT FOR UPDATE` reads the current committed version, which can create an apparent inconsistency where a SELECT shows one value and a subsequent UPDATE finds zero rows because the current version doesn't match the snapshot-visible value.
