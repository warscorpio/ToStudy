### Section 1: `FULLTEXT` Index Fundamentals

**Q1. What is a `FULLTEXT` index and how does it differ from a `LIKE` search or a regular B+ Tree index?**
A: A `FULLTEXT` index enables full-text search — finding documents that contain specific words or phrases, with relevance ranking. It is fundamentally different from both `LIKE` and regular B+ Tree indexes:

```sql
-- ── LIKE search — pattern matching ────────────────────────────────────
SELECT * FROM articles WHERE body LIKE '%database performance%';
-- Problems:
-- 1. Cannot use any index — full table scan every time (O(n) per row)
-- 2. '%word%' prefix wildcard: index unusable even if index exists
-- 3. No relevance: "database" in a 10,000-word document = "database" in title
-- 4. No word boundary awareness: '%base%' matches 'database', 'database', 'codebase'
-- 5. No synonym, stemming, or stop-word handling
-- Performance on 10M rows: 30-120 seconds

-- ── B+ Tree index on text — only prefix searches ───────────────────────
CREATE INDEX idx_title ON articles (title(100));  -- prefix index
SELECT * FROM articles WHERE title = 'MySQL Internals';   -- ✓ uses index (equality)
SELECT * FROM articles WHERE title LIKE 'MySQL%';         -- ✓ uses index (prefix)
SELECT * FROM articles WHERE title LIKE '%MySQL%';        -- ✗ full scan (non-prefix)
-- Completely inadequate for "find documents containing the word MySQL"

-- ── FULLTEXT index — inverted index for word-based search ─────────────
CREATE FULLTEXT INDEX ft_body ON articles (body);

SELECT *, MATCH(body) AGAINST ('database performance') AS relevance
FROM articles
WHERE MATCH(body) AGAINST ('database performance');
-- 1. Uses the inverted index: O(log N) to find matching document IDs
-- 2. Returns relevance score: articles mentioning both words score higher
-- 3. Understands word boundaries: exact word 'base' ≠ 'database'
-- 4. Filters stop words ('the', 'a', 'in') automatically
-- 5. Minimum word length: words shorter than innodb_ft_min_token_size (3) ignored
-- Performance on 10M rows: < 100ms
```

```
FULLTEXT index internal structure — inverted index:

Conceptually, for a table with 3 articles:
  Article 1: "MySQL database performance tuning"
  Article 2: "database indexing strategies"
  Article 3: "MySQL performance benchmarks"

Inverted index (stored in InnoDB auxiliary tables):
  Word        → [doc_id, position, weight, ...]
  'mysql'     → [1, 0], [3, 0]     ← appears in docs 1 and 3
  'database'  → [1, 1], [2, 0]     ← appears in docs 1 and 2
  'performance'→ [1, 2], [3, 1]    ← appears in docs 1 and 3
  'tuning'    → [1, 3]
  'indexing'  → [2, 1]
  ...

Query: MATCH(body) AGAINST('database performance')
  → Look up 'database': docs {1, 2}
  → Look up 'performance': docs {1, 3}
  → Union: docs {1, 2, 3}; doc 1 matches BOTH words → highest relevance
  → Score = f(term frequency, inverse document frequency, field length)
    (TF-IDF variant)

InnoDB FULLTEXT auxiliary tables (created per indexed column):
  FTS_<id>_BEING_DELETED        → docs being deleted
  FTS_<id>_BEING_DELETED_CACHE  → cache of docs being deleted
  FTS_<id>_CONFIG               → index configuration
  FTS_<id>_DELETED              → deleted doc IDs
  FTS_<id>_DELETED_CACHE        → cached deleted IDs
  FTS_<id>_DOC_ID               → maps row ID ↔ FTS_DOC_ID
  FTS_<id>_INDEX_1..6           → the actual inverted index (sharded across 6 tables)
```

**Q2. What are the three `FULLTEXT` search modes and when should each be used?**
A: MySQL's `MATCH ... AGAINST` supports three modes with very different behaviors:

```sql
-- ── Mode 1: Natural Language (default) ────────────────────────────────
-- Treats the search string as a natural language phrase
-- Returns rows scored by relevance (TF-IDF)
-- No special operator support

SELECT title, MATCH(title, body) AGAINST ('mysql index optimization') AS score
FROM articles
WHERE MATCH(title, body) AGAINST ('mysql index optimization')
ORDER BY score DESC;
-- 'mysql', 'index', 'optimization' treated as independent keywords
-- Documents containing all three words rank highest
-- Stop words ('the', 'a', 'in', 'is') automatically ignored
-- Words appearing in >50% of rows are ignored (too common to be discriminating)
-- Relevance = 0 for documents that don't match → WHERE clause filters them

-- Limitation: no AND/OR/NOT logic; no phrase search; >50% suppression

-- ── Mode 2: Boolean Mode ───────────────────────────────────────────────
-- Supports operators for precise control
-- No automatic >50% suppression (rare words still scored)
-- Relevance scores are less precise than natural language mode

SELECT title, MATCH(title, body) AGAINST ('+mysql +index -slow' IN BOOLEAN MODE) AS score
FROM articles
WHERE MATCH(title, body) AGAINST ('+mysql +index -slow' IN BOOLEAN MODE);

-- Boolean mode operators:
-- +word     MUST include: document must contain this word to match
-- -word     MUST NOT include: exclude documents containing this word
-- word      OPTIONAL: contributes to score if present but not required
-- "phrase"  Exact phrase: must contain this exact sequence of words
-- word*     Prefix: matches 'index', 'indexes', 'indexing', 'indexed'
-- ~word     Negation contribution: document containing this word gets LOWER score
-- >word     Increase relevance contribution of this word
-- <word     Decrease relevance contribution of this word
-- (expr)    Grouping: (+mysql +(>performance <optimization))

-- Examples:
AGAINST('+mysql +"query cache"'           IN BOOLEAN MODE)  -- mysql AND exact phrase "query cache"
AGAINST('+performance -slow'              IN BOOLEAN MODE)  -- performance but NOT slow
AGAINST('index*'                          IN BOOLEAN MODE)  -- prefix: indexes, indexing, etc.
AGAINST('+mysql +(index|query|optimize)'  IN BOOLEAN MODE)  -- mysql AND (index OR query OR optimize)
AGAINST('+replication ~slave'             IN BOOLEAN MODE)  -- replication, lower score if 'slave'
AGAINST('>speed <memory optimization'     IN BOOLEAN MODE)  -- boost speed, demote memory

-- ── Mode 3: Query Expansion (two-pass search) ─────────────────────────
-- Phase 1: Natural language search
-- Phase 2: Take words from the top-ranked results → expand the search
-- Finds semantically related documents (implicit synonym expansion)

SELECT title
FROM articles
WHERE MATCH(title, body) AGAINST ('database' WITH QUERY EXPANSION);
-- First pass: finds documents about 'database'
-- These documents also contain: 'MySQL', 'table', 'query', 'index', 'row'
-- Second pass: search for all those words combined
-- Result: much broader set including MySQL-specific articles
-- even if they don't explicitly say 'database'

-- Use when: user entered a very short query; want discovery-style search
-- Caution: can return noisy results; test carefully

-- Blind query expansion:
AGAINST ('database' WITH QUERY EXPANSION)
-- = same as query expansion (MySQL also supports WITH QUERY EXPANSION as alias)
```

**Q3. How do you create a `FULLTEXT` index and what are its constraints?**
A:

```sql
-- ── Creating FULLTEXT indexes ──────────────────────────────────────────

-- At table creation:
CREATE TABLE articles (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  title       VARCHAR(200) NOT NULL,
  body        TEXT         NOT NULL,
  category    VARCHAR(50),
  published   TINYINT(1)   NOT NULL DEFAULT 1,
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  FULLTEXT INDEX ft_title        (title),            -- single-column
  FULLTEXT INDEX ft_title_body   (title, body),      -- multi-column (searches both as one)
  FULLTEXT INDEX ft_ngram_body   (body) WITH PARSER ngram  -- ngram parser (CJK languages)
);

-- Adding to existing table:
ALTER TABLE articles ADD FULLTEXT INDEX ft_body (body);
CREATE FULLTEXT INDEX ft_body ON articles (body);  -- equivalent

-- ── Constraints ────────────────────────────────────────────────────────
-- Only on:        CHAR, VARCHAR, TEXT (and their variants)
-- Engines:        InnoDB (MySQL 5.6+), MyISAM
-- Column types:   NOT applicable to: INT, DATE, DECIMAL, JSON, BLOB (must use TEXT)
-- Multiple cols:  Multi-column FULLTEXT is treated as ONE virtual concatenated field
--                 MATCH must name ALL columns in the SAME index; can't mix
-- Max index len:  Each indexed word max 84 characters (longer words truncated)

-- ── Minimum word length ────────────────────────────────────────────────
-- InnoDB:  innodb_ft_min_token_size = 3  (words < 3 chars ignored)
-- MyISAM:  ft_min_word_len = 4
SHOW VARIABLES LIKE 'innodb_ft_min_token_size';
-- Changing requires: SET GLOBAL innodb_ft_min_token_size = 2;
-- Then: rebuild ALL fulltext indexes:
ALTER TABLE articles DROP INDEX ft_body, ADD FULLTEXT INDEX ft_body (body);
-- Or: OPTIMIZE TABLE articles; (for MyISAM)

-- ── Stop words ────────────────────────────────────────────────────────
-- Default InnoDB stop word list: 36 common English words
-- ('a', 'as', 'be', 'but', 'by', 'do', 'for', 'i', 'in', 'it', 'me', 'my',
--  'no', 'not', 'of', 'on', 'or', 'so', 'the', 'to', 'up', 'us', 'was', 'who')
-- Custom stop words:
SET GLOBAL innodb_ft_server_stopword_table = 'mydb/my_stopwords';
CREATE TABLE my_stopwords (value VARCHAR(30)) ENGINE=InnoDB;
INSERT INTO my_stopwords VALUES ('php'), ('java'), ('net');  -- domain-specific stop words
-- Then rebuild indexes

-- Disable stop words entirely (for very short documents or precise boolean mode):
SET GLOBAL innodb_ft_enable_stopword = 0;

-- ── The >50% rule (natural language mode only) ────────────────────────
-- If a word appears in more than 50% of rows, it's ignored in natural language mode
-- Example: searching 'mysql' in a MySQL tutorial database where all 10K articles mention 'mysql'
-- → 'mysql' treated as not discriminating → no results!
-- Fix: use BOOLEAN MODE (no >50% suppression):
WHERE MATCH(body) AGAINST('+mysql' IN BOOLEAN MODE);
```

**Q4. How does `FULLTEXT` relevance scoring work and how do you use it effectively?**
A: The relevance score is a floating-point number derived from TF-IDF (Term Frequency × Inverse Document Frequency), weighted by field position and length. Higher scores indicate better matches.

```sql
-- Relevance scoring demonstration:
CREATE TABLE articles (
  id INT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(200),
  body TEXT,
  FULLTEXT INDEX ft_all (title, body)
);

INSERT INTO articles (title, body) VALUES
  ('MySQL Performance', 'MySQL is a popular database. Performance tuning is important.'),
  ('Database Fundamentals', 'Databases store data. MySQL is one example of a database system.'),
  ('Advanced MySQL', 'MySQL MySQL MySQL MySQL MySQL - very keyword heavy'),
  ('PostgreSQL Guide', 'PostgreSQL is another database system with different features.');

SELECT
  id, title,
  MATCH(title, body) AGAINST ('mysql database') AS relevance
FROM articles
WHERE MATCH(title, body) AGAINST ('mysql database')
ORDER BY relevance DESC;

-- Typical output:
-- | id | title                 | relevance |
-- |----|----------------------|-----------|
-- |  1 | MySQL Performance    |  1.842    | ← 'mysql' in title (higher weight) + body
-- |  3 | Advanced MySQL       |  1.231    | ← 'mysql' appears many times (TF high) but may be penalized
-- |  2 | Database Fundamentals|  0.987    | ← 'database' twice + 'mysql' once
-- (PostgreSQL article: no 'mysql' → relevance=0 → excluded by WHERE clause)

-- Key TF-IDF factors:
-- TF (Term Frequency): how often the word appears in this document
--   → 'mysql' in article 3 (5 times) scores higher than in article 1 (1 time)
-- IDF (Inverse Doc Frequency): how rare the word is across all documents
--   → 'mysql' appears in 3/4 docs → lower IDF than 'performance' (1/4 docs)
-- Field position: words in title weighted higher than words in body
-- Document length normalization: shorter docs with same TF score higher

-- ── Practical relevance boosting ──────────────────────────────────────
-- Multi-column FULLTEXT: weight title matches higher by querying separately:
SELECT
  id, title,
  MATCH(title) AGAINST ('mysql performance' IN BOOLEAN MODE) * 10  -- title weight
  + MATCH(body) AGAINST ('mysql performance' IN BOOLEAN MODE)      -- body weight
  AS custom_relevance
FROM articles
WHERE MATCH(title, body) AGAINST ('mysql performance')  -- use combined index for filtering
ORDER BY custom_relevance DESC;
-- Requires separate indexes on title and body for this pattern

-- ── Displaying relevance in results ───────────────────────────────────
-- Relevance must appear in both WHERE and SELECT — can be computed twice (optimizer usually deduplicates)
-- Use subquery to compute once:
SELECT * FROM (
  SELECT
    id, title, body,
    MATCH(title, body) AGAINST ('mysql index') AS relevance
  FROM articles
) ranked
WHERE relevance > 0
ORDER BY relevance DESC
LIMIT 10;

-- Minimum score threshold:
SELECT id, title, MATCH(title, body) AGAINST ('mysql') AS score
FROM articles
HAVING score > 0.5    -- only show results with meaningful relevance
ORDER BY score DESC;
```

**Q5. What is the `ngram` full-text parser and when do you need it?**
A: The default `FULLTEXT` parser tokenizes words by whitespace and punctuation — it is word-based and designed for Latin-script languages. Asian languages (Chinese, Japanese, Korean) don't use spaces between words, so every character (or pair of characters) must be indexed individually. The `ngram` parser solves this by generating fixed-size character n-grams from the text.

```sql
-- Default parser (word-based): fails for CJK
-- "数据库性能" ("database performance" in Chinese) has NO spaces
-- Default parser indexes the entire string as one token: '数据库性能'
-- Searching for '数据库' (database) → finds nothing (not a token)

-- ngram parser: indexes every n consecutive characters
-- With ngram_token_size=2 (default):
-- '数据库性能' → tokens: '数据', '据库', '库性', '性能'
-- Searching for '数据库' → decomposes to '数据', '据库'
-- → matches the document! ✓

-- Create table with ngram parser:
CREATE TABLE chinese_articles (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(200),
  body  TEXT,
  FULLTEXT INDEX ft_ngram_title (title) WITH PARSER ngram,
  FULLTEXT INDEX ft_ngram_body  (body)  WITH PARSER ngram
);

-- ngram_token_size (default: 2) — set in my.cnf:
-- [mysqld]
-- ngram_token_size=2
-- Requires server restart; affects all ngram indexes

-- Searching with ngram:
SELECT title
FROM chinese_articles
WHERE MATCH(title) AGAINST ('数据库' IN BOOLEAN MODE);
-- Decomposes '数据库' into ngrams '数据', '据库'
-- Boolean mode: documents containing both ngrams rank highest

-- ngram also works for Latin text (searches for substrings):
-- ngram_token_size=2 on 'hello' → 'he', 'el', 'll', 'lo'
-- Can search for word fragments: AGAINST('ell') → finds 'hello', 'yellow', etc.
-- Useful for product SKUs, serial numbers, partial word search

-- ngram minimum token size:
-- innodb_ft_min_token_size is IGNORED for ngram parser
-- ngram_token_size governs instead
-- Ensure ngram_token_size ≤ length of shortest query term
```

### Section 2: `JSON` Type Fundamentals

**Q6. What is MySQL's `JSON` data type and how is it stored internally?**
A: MySQL's `JSON` column type (introduced in MySQL 5.7.8) stores JSON documents in a **binary format** optimized for efficient retrieval — not as plain text. This binary format allows MySQL to access specific paths within the document without fully parsing the entire string.

```sql
-- Creating a table with JSON columns:
CREATE TABLE products (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  name        VARCHAR(100) NOT NULL,
  attributes  JSON,           -- can be NULL unless NOT NULL specified
  metadata    JSON NOT NULL DEFAULT (JSON_OBJECT()),
  PRIMARY KEY (id)
);

-- JSON column characteristics:
-- 1. AUTO-VALIDATION: invalid JSON is rejected at insert time
INSERT INTO products (name, attributes) VALUES ('Widget', '{"color": "red", "size": 5}');  -- ✓
INSERT INTO products (name, attributes) VALUES ('Widget', '{invalid json}');  -- ✗ Error 3140

-- 2. NORMALIZED binary storage (not raw string):
-- InnoDB stores JSON in an internal binary format:
--   - Object keys are sorted and deduplicated
--   - Numeric values stored as binary (not string digits)
--   - Direct path access without full parse
--   - {"b": 2, "a": 1} stored as {"a": 1, "b": 2} (keys sorted)

-- 3. SIZE LIMIT:
-- Max JSON document size = max_allowed_packet (default: 64MB in MySQL 8.0)
-- Practical limit: keep documents well under 1MB for performance

-- 4. NULL vs JSON null:
INSERT INTO products (name, attributes) VALUES ('Test', NULL);       -- SQL NULL (no value)
INSERT INTO products (name, attributes) VALUES ('Test', 'null');     -- JSON null (a JSON value)
INSERT INTO products (name, attributes) VALUES ('Test', JSON_OBJECT()); -- empty JSON object {}

-- Check what's stored:
SELECT name, attributes, JSON_TYPE(attributes)
FROM products;
-- | name  | attributes | JSON_TYPE(attributes) |
-- |-------|------------|-----------------------|
-- | Test  | NULL       | NULL                  | ← SQL NULL
-- | Test  | null       | NULL                  | ← JSON null (also NULL in JSON_TYPE)
-- | Test  | {}         | OBJECT                | ← empty object

-- 5. Partial update optimization (MySQL 8.0+):
-- JSON_SET, JSON_REPLACE, JSON_REMOVE on binary JSON:
-- InnoDB can update ONLY the changed path in the document (not rewrite the entire column)
-- Requires: value being replaced is same size or smaller
-- Reduces I/O and undo log overhead significantly for small changes to large documents
-- Enable with: binlog_format = ROW + binlog_row_image = FULL (MySQL default)
```

**Q7. What are the JSON path expression operators and how do they work?**
A: JSON path expressions navigate within a JSON document. Every path starts with `$` (the root document), then uses operators to traverse objects and arrays.

```sql
-- Sample document:
SET @doc = '{
  "name": "Alice",
  "age": 30,
  "address": {
    "city": "New York",
    "zip": "10001"
  },
  "tags": ["mysql", "databases", "performance"],
  "scores": [
    {"subject": "math", "grade": 95},
    {"subject": "science", "grade": 88}
  ],
  "metadata": {
    "created": "2024-01-15",
    "source": "api"
  }
}';

-- ── Path operators ─────────────────────────────────────────────────────

-- $ — root
SELECT JSON_EXTRACT(@doc, '$');              -- returns the whole document

-- .key — object key access
SELECT JSON_EXTRACT(@doc, '$.name');        -- "Alice"
SELECT JSON_EXTRACT(@doc, '$.address.city'); -- "New York"

-- [N] — array index (0-based)
SELECT JSON_EXTRACT(@doc, '$.tags[0]');     -- "mysql"
SELECT JSON_EXTRACT(@doc, '$.tags[2]');     -- "performance"
SELECT JSON_EXTRACT(@doc, '$.tags[-1]');    -- MySQL 8.0.17+: last element "performance"
SELECT JSON_EXTRACT(@doc, '$.scores[0].grade'); -- 95

-- [*] — all array elements (wildcard)
SELECT JSON_EXTRACT(@doc, '$.tags[*]');     -- ["mysql", "databases", "performance"]
SELECT JSON_EXTRACT(@doc, '$.scores[*].grade'); -- [95, 88]

-- .* — all object values (wildcard)
SELECT JSON_EXTRACT(@doc, '$.address.*');   -- ["New York", "10001"]
SELECT JSON_EXTRACT(@doc, '$.*');           -- all top-level values as array

-- [M to N] — array range (MySQL 8.0+)
SELECT JSON_EXTRACT(@doc, '$.tags[0 to 1]'); -- ["mysql", "databases"]
SELECT JSON_EXTRACT(@doc, '$.scores[last]'); -- last array element (MySQL 8.0+)

-- ** — recursive descent (searches all levels)
SELECT JSON_EXTRACT(@doc, '$**.grade');     -- [95, 88] — finds 'grade' anywhere in tree

-- ── The -> and ->> operators (shorthand) ─────────────────────────────
-- -> is an alias for JSON_EXTRACT (returns JSON-quoted string)
-- ->> is an alias for JSON_UNQUOTE(JSON_EXTRACT) (returns unquoted string)

SELECT attributes->'$.color'  FROM products;  -- returns: "red"  (with quotes)
SELECT attributes->>'$.color' FROM products;  -- returns: red    (without quotes)

-- -> returns a JSON string with quotes:
SELECT JSON_EXTRACT('{"name": "Alice"}', '$.name');  -- "Alice" (quoted)
-- ->> removes the JSON string quotes:
SELECT '{"name": "Alice"}' ->> '$.name';             -- Alice  (unquoted, usable as VARCHAR)

-- This matters for:
WHERE attributes->>'$.color' = 'red'   -- ✓ string comparison (unquoted)
WHERE attributes->'$.color'  = 'red'   -- ✗ comparing JSON string "red" to VARCHAR 'red'
WHERE attributes->'$.color'  = '"red"' -- ✓ but ugly

-- JSON_VALUE (MySQL 8.0) — extract with type casting:
SELECT JSON_VALUE(@doc, '$.age' RETURNING UNSIGNED)           -- 30 (numeric)
SELECT JSON_VALUE(@doc, '$.address.zip' RETURNING CHAR(10))   -- '10001' (string)
SELECT JSON_VALUE(@doc, '$.missing' DEFAULT 0 ON EMPTY)       -- 0 (not found → default)
SELECT JSON_VALUE(@doc, '$.age' RETURNING UNSIGNED ERROR ON ERROR) -- strict: error if type mismatch
```

### Section 3: JSON Modification Functions

**Q8. What are `JSON_SET`, `JSON_INSERT`, and `JSON_REPLACE` and how do they differ?**
A: All three modify a JSON document but have different semantics for existing vs non-existing paths:

```sql
-- Test document:
SET @doc = '{"name": "Alice", "age": 30, "city": "NYC"}';

-- ── JSON_SET: insert OR update (upsert) ───────────────────────────────
-- If path exists   → REPLACE the value
-- If path missing  → INSERT the value
SELECT JSON_SET(@doc, '$.age', 31);                    -- updates age: {"name":"Alice","age":31,"city":"NYC"}
SELECT JSON_SET(@doc, '$.email', 'alice@test.com');   -- inserts email (didn't exist): adds email field
SELECT JSON_SET(@doc,                                  -- multiple operations at once:
  '$.age', 31,
  '$.email', 'alice@test.com',
  '$.city', 'LA'
);

-- ── JSON_INSERT: insert only (no overwrite) ────────────────────────────
-- If path exists   → IGNORE (keep existing value)
-- If path missing  → INSERT the value
SELECT JSON_INSERT(@doc, '$.age', 99);                 -- age exists → ignored: age still 30
SELECT JSON_INSERT(@doc, '$.phone', '+1-555-1234');    -- phone missing → inserted

-- Use case: setting default values without overwriting user-provided values:
UPDATE users
SET preferences = JSON_INSERT(
  COALESCE(preferences, '{}'),  -- start with existing or empty object
  '$.theme', 'light',           -- only sets if not already set by user
  '$.language', 'en'
)
WHERE preferences IS NULL OR JSON_EXTRACT(preferences, '$.theme') IS NULL;

-- ── JSON_REPLACE: replace only (no insert) ────────────────────────────
-- If path exists   → REPLACE the value
-- If path missing  → IGNORE (don't insert)
SELECT JSON_REPLACE(@doc, '$.age', 31);                -- age exists → updated: 31
SELECT JSON_REPLACE(@doc, '$.missing', 'value');       -- missing → ignored: doc unchanged

-- Use case: updating only fields that exist (safe update):
UPDATE orders
SET line_items = JSON_REPLACE(
  line_items,
  CONCAT('$.items[', @item_index, '].status'), 'shipped'
  -- only updates if items[N].status exists; won't add ghost fields
);

-- ── JSON_REMOVE: delete a path ─────────────────────────────────────────
SELECT JSON_REMOVE(@doc, '$.city');                    -- {"name":"Alice","age":30}
SELECT JSON_REMOVE(@doc, '$.name', '$.city');          -- remove multiple: {"age":30}

-- Remove array element:
SET @arr = '[1, 2, 3, 4, 5]';
SELECT JSON_REMOVE(@arr, '$[2]');   -- [1, 2, 4, 5]  (index 2 = value 3)
SELECT JSON_REMOVE(@arr, '$[0]', '$[0]');  -- CAUTION: removes index 0 twice
-- After first removal: [2,3,4,5]; second removal of index 0: [3,4,5]
-- Removals applied left to right; indices shift!

-- ── JSON_MERGE_PATCH vs JSON_MERGE_PRESERVE ────────────────────────────
-- JSON_MERGE_PATCH (RFC 7396): last value wins for duplicate keys
SELECT JSON_MERGE_PATCH(
  '{"a": 1, "b": {"x": 1, "y": 2}}',
  '{"b": {"x": 99, "z": 3}, "c": 4}'
);
-- Result: {"a": 1, "b": {"x": 99, "z": 3}, "c": 4}
-- b.y is GONE (patch replaces b entirely)  ← RFC 7396 behavior
-- Use: applying partial updates where missing = "remove this key"

-- JSON_MERGE_PRESERVE (MySQL 5.7.22+): keeps both values for duplicate keys
SELECT JSON_MERGE_PRESERVE(
  '{"a": 1, "tags": ["mysql"]}',
  '{"a": 2, "tags": ["database"]}'
);
-- Result: {"a": [1, 2], "tags": ["mysql", "database"]}
-- Duplicate values become arrays
-- Use: accumulating/aggregating JSON data
```

### Section 4: JSON Querying Functions

**Q9. How do you search within JSON documents using `JSON_CONTAINS`, `JSON_CONTAINS_PATH`, and `JSON_SEARCH`?**
A:

```sql
-- Sample table:
CREATE TABLE products (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  name       VARCHAR(100),
  attributes JSON
);
INSERT INTO products (name, attributes) VALUES
  ('Laptop', '{"color": "silver", "ram": 16, "storage": [256, 512], "tags": ["portable", "business"]}'),
  ('Phone',  '{"color": "black",  "ram": 8,  "storage": [128],      "tags": ["mobile", "portable"]}'),
  ('Tablet', '{"color": "silver", "ram": 4,  "storage": [64, 128],  "tags": ["portable", "consumer"]}');

-- ── JSON_CONTAINS: check if a value exists ────────────────────────────
-- JSON_CONTAINS(target, candidate [, path])
-- Returns 1 if candidate is contained in target (at the optional path)

-- Check if a specific value exists anywhere:
SELECT name FROM products
WHERE JSON_CONTAINS(attributes, '"portable"', '$.tags');
-- Returns: Laptop, Phone, Tablet (all have "portable" in tags array)
-- NOTE: candidate must be a VALID JSON value (strings must be quoted: '"portable"' not 'portable')

-- Check if a specific key-value pair exists:
SELECT name FROM products
WHERE JSON_CONTAINS(attributes, '{"color": "silver"}');
-- Returns: Laptop, Tablet
-- Checks if the object {"color":"silver"} is contained in attributes

-- Check for a specific array element:
SELECT name FROM products
WHERE JSON_CONTAINS(attributes->'$.storage', '512');
-- Returns: Laptop (has 512 in storage array)

-- ── JSON_CONTAINS_PATH: check if a path exists ─────────────────────────
-- JSON_CONTAINS_PATH(doc, 'one'|'all', path[, path...])
-- 'one': returns 1 if at least ONE of the paths exists
-- 'all': returns 1 if ALL of the paths exist

-- Check if a path exists:
SELECT name FROM products
WHERE JSON_CONTAINS_PATH(attributes, 'one', '$.color');
-- All rows match (all have $.color)

-- Check if ALL paths exist:
SELECT name FROM products
WHERE JSON_CONTAINS_PATH(attributes, 'all', '$.color', '$.ram', '$.storage');
-- All rows match

-- Check for optional nested path:
SELECT name FROM products
WHERE JSON_CONTAINS_PATH(attributes, 'one', '$.discount.percentage');
-- Returns: nothing (no products have $.discount.percentage)

-- ── JSON_SEARCH: find the PATH where a value exists ────────────────────
-- JSON_SEARCH(doc, 'one'|'all', search_string [, escape_char [, path]])
-- Returns the PATH(s) where the search string is found (not the value itself!)
-- Supports LIKE-style wildcards: % and _

-- Find WHERE 'portable' exists:
SELECT name, JSON_SEARCH(attributes, 'one', 'portable') AS found_at
FROM products;
-- | name   | found_at      |
-- |--------|---------------|
-- | Laptop | "$.tags[0]"   | ← 'portable' is at tags[0] in Laptop
-- | Phone  | "$.tags[1]"   | ← 'portable' is at tags[1] in Phone
-- | Tablet | "$.tags[0]"   | ← 'portable' is at tags[0] in Tablet

-- Find ALL paths where a pattern exists:
SELECT name, JSON_SEARCH(attributes, 'all', 'port%') AS found_at
FROM products WHERE name = 'Laptop';
-- Returns: ["$.tags[0]"] (only 'portable' starts with 'port')

-- Search within specific path:
SELECT name, JSON_SEARCH(attributes, 'all', 'black', NULL, '$.color') AS color_path
FROM products;
-- | name  | color_path  |
-- |-------|-------------|
-- | Phone | "$.color"   |

-- ── JSON_KEYS: get all object keys ─────────────────────────────────────
SELECT JSON_KEYS(attributes) FROM products WHERE id = 1;
-- ["color", "ram", "storage", "tags"]

SELECT JSON_KEYS(attributes, '$.') FROM products WHERE id = 1;
-- same (path = root)

-- ── JSON_LENGTH and JSON_DEPTH ─────────────────────────────────────────
SELECT
  name,
  JSON_LENGTH(attributes)           AS top_level_count,  -- number of top-level key/elements
  JSON_LENGTH(attributes->'$.tags') AS tags_count,        -- number of tags
  JSON_DEPTH(attributes)            AS nesting_depth       -- max nesting level
FROM products;
-- | name   | top_level | tags | depth |
-- |--------|-----------|------|-------|
-- | Laptop |     4     |  2   |   3   |
-- | Phone  |     4     |  2   |   3   |
-- | Tablet |     4     |  2   |   3   |
```

**Q10. How do you aggregate JSON data with `JSON_ARRAYAGG` and `JSON_OBJECTAGG`?**
A:

```sql
-- ── JSON_ARRAYAGG: aggregate values into a JSON array ──────────────────
SELECT
  category,
  JSON_ARRAYAGG(name)             AS product_names,
  JSON_ARRAYAGG(price ORDER BY price) AS sorted_prices  -- MySQL 8.0
FROM products
GROUP BY category;
-- | category    | product_names            | sorted_prices |
-- |-------------|--------------------------|---------------|
-- | Electronics | ["Laptop", "Phone"]      | [299, 899]    |
-- | Accessories | ["Case", "Cable"]        | [9.99, 19.99] |

-- Build a JSON array of objects:
SELECT
  category,
  JSON_ARRAYAGG(
    JSON_OBJECT('id', id, 'name', name, 'price', price)
    ORDER BY price DESC
  ) AS products
FROM products
GROUP BY category;
-- | category    | products                                                          |
-- |-------------|-------------------------------------------------------------------|
-- | Electronics | [{"id":1,"name":"Laptop","price":899},{"id":2,"name":"Phone",...}]|

-- ── JSON_OBJECTAGG: aggregate key-value pairs into a JSON object ────────
SELECT
  user_id,
  JSON_OBJECTAGG(preference_key, preference_value) AS preferences
FROM user_preferences
GROUP BY user_id;
-- | user_id | preferences                                     |
-- |---------|--------------------------------------------------|
-- |    42   | {"theme": "dark", "language": "en", "tz": "UTC"}|

-- ── Unnesting JSON arrays for aggregation ──────────────────────────────
-- JSON_TABLE (MySQL 8.0): relational view of JSON data
SELECT p.name, jt.tag
FROM products p,
JSON_TABLE(
  p.attributes->'$.tags',
  '$[*]'
  COLUMNS (tag VARCHAR(50) PATH '$')

-- |--------|------------|
-- | Laptop | portable   |
-- | Laptop | business   |
-- | Phone  | mobile     |
-- | Phone  | portable   |

-- Count products per tag (unnesting + aggregation):
SELECT jt.tag, COUNT(*) AS product_count
FROM products p,
JSON_TABLE(
  p.attributes->'$.tags',
  '$[*]'
  COLUMNS (tag VARCHAR(50) PATH '$')
) AS jt
GROUP BY jt.tag
ORDER BY product_count DESC;
```

### Section 5: Indexing JSON Columns

**Q11. Why can't you create a regular index on a JSON column and what are the alternatives?**
A: MySQL cannot create a B+ Tree index directly on a JSON column because JSON values have no fixed size or consistent comparison semantics — the same path might hold a string in one row and a number in another. Three solutions exist for indexing JSON data:

```sql
-- ❌ Direct JSON column index — not allowed:
CREATE INDEX idx_json ON products (attributes);
-- Error: BLOB/TEXT column 'attributes' used in key specification without a key length

-- ── Solution 1: Generated Column + Index (MySQL 5.7+) ──────────────────
-- A generated column extracts a specific path; the index is on the generated column

ALTER TABLE products
  ADD COLUMN attr_color VARCHAR(50)
    GENERATED ALWAYS AS (attributes->>'$.color') STORED,
    -- STORED: value computed and stored on disk (takes space, faster reads)
    -- VIRTUAL: computed on the fly (no space, but can still be indexed in MySQL 8.0)
  ADD INDEX idx_color (attr_color);

-- Now this uses the index:
SELECT name FROM products WHERE attr_color = 'silver';
-- EXPLAIN: type=ref, key=idx_color ✓

-- Or with VIRTUAL (MySQL 8.0+):
ALTER TABLE products
  ADD COLUMN attr_ram INT UNSIGNED
    GENERATED ALWAYS AS (attributes->>'$.ram' + 0) VIRTUAL,
  ADD INDEX idx_ram (attr_ram);

SELECT name FROM products WHERE attr_ram >= 16;  -- uses idx_ram

-- ── Solution 2: Functional Index (MySQL 8.0.13+) ──────────────────────
-- Creates an implicit generated column + index in one statement
-- No visible column added to the table

CREATE INDEX idx_color_func ON products
  ((attributes->>'$.color'));  -- double parentheses required for expressions

-- Usage:
SELECT name FROM products WHERE attributes->>'$.color' = 'silver';
-- EXPLAIN: uses idx_color_func ✓ (MySQL recognizes the expression matches the index)

-- Functional index on numeric JSON value:
CREATE INDEX idx_ram_func ON products
  ((CAST(attributes->>'$.ram' AS UNSIGNED)));

SELECT name FROM products WHERE CAST(attributes->>'$.ram' AS UNSIGNED) >= 16;
-- Must use the same expression in WHERE to match the functional index

-- ── Solution 3: Multi-Valued Index (MySQL 8.0.17+) ─────────────────────
-- Indexes multiple values from a JSON array in one index
-- Essential for searching within JSON arrays without JSON_TABLE

-- Create multi-valued index on the tags array:
CREATE INDEX idx_tags ON products
  ((CAST(attributes->'$.tags' AS CHAR(50) ARRAY)));
--                                          ↑ ARRAY keyword = multi-valued index

-- Usage: MEMBER OF operator (designed for multi-valued indexes):
SELECT name FROM products
WHERE 'portable' MEMBER OF (attributes->'$.tags');
-- EXPLAIN: uses idx_tags ✓ (much faster than JSON_CONTAINS for large tables)

-- Also works with JSON_CONTAINS:
SELECT name FROM products
WHERE JSON_CONTAINS(attributes->'$.tags', '"portable"');
-- MySQL 8.0.17+ can use the multi-valued index for JSON_CONTAINS too

-- JSON_OVERLAPS (MySQL 8.0.17+):
SELECT name FROM products
WHERE JSON_OVERLAPS(attributes->'$.tags', '["portable", "business"]');
-- Returns rows where tags array has ANY element in common with the given array
-- EXPLAIN: can use multi-valued index

-- Multi-valued index limitations:
-- Only on JSON arrays of scalar values (no arrays of objects)
-- NULL values in the array are not indexed
-- Max index entry length applies (innodb_large_prefix)
-- Can't be part of a composite index with other columns
-- Can't be a PRIMARY KEY or UNIQUE key

-- Checking generated column / functional index usage:
EXPLAIN SELECT name FROM products WHERE (attributes->>'$.color') = 'silver' \G
-- key: idx_color_func
-- Extra: Using index condition ✓
```

### Section 6: Scenario / Interview Questions

**Q12. "When should you use a JSON column vs a normalized relational schema?"**
A:

```sql
-- ── Use JSON when ────────────────────────────────────────────────────

-- 1. Truly schema-less / variable attributes per entity:
-- An e-commerce platform sells electronics, clothing, books — completely different attributes:
-- Electronics: voltage, wattage, frequency_response, connectivity
-- Clothing:    size, material, color, fit, wash_instructions
-- Books:       isbn, author, publisher, pages, edition
-- Normalized: 50+ attribute tables or one massive EAV table (terrible)
-- JSON: one 'attributes' column per product category — clean and flexible

-- 2. Storing configuration / preferences with unpredictable keys:
-- User settings: each user might have different keys in their preferences
-- App configs: feature flags, A/B test assignments, plugin settings
-- These grow without schema changes → JSON wins

-- 3. Caching or storing API responses:
CREATE TABLE api_cache (
  cache_key  VARCHAR(255) PRIMARY KEY,
  response   JSON NOT NULL,
  expires_at DATETIME NOT NULL,
  INDEX idx_expires (expires_at)
);
-- Store third-party API responses as-is; no need to normalize transient cache data

-- 4. Hierarchical data with variable depth:
-- File system paths, comment threads, org chart subtrees
-- JSON naturally represents trees

-- 5. The data is consumed as a unit (always read/written together):
-- If you always SELECT * and never filter/aggregate on sub-fields → JSON is fine

-- ── Use normalized tables when ────────────────────────────────────────

-- 1. You need to filter, sort, or aggregate on the data:
-- WHERE attributes->>'$.price' > 100  → no index → full table scan at scale
-- (can work with functional indexes, but adds complexity)

-- 2. Data integrity and foreign keys matter:
-- JSON has no referential integrity: attributes->>'$.category_id' can reference
-- a non-existent category with no FK constraint

-- 3. You query individual fields frequently:
SELECT AVG(attributes->>'$.ram' + 0) FROM products WHERE ...;
-- Aggregating over JSON paths is slow without generated column indexes
-- A normalized 'ram INT' column + index is cleaner and faster

-- 4. The schema is stable and well-understood:
-- Products with known attributes, orders with known structure → normalize!
-- JSON flexibility isn't needed and adds hidden costs

-- Anti-pattern: using JSON as a "flexible" escape hatch when you actually need normalization
CREATE TABLE users (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  data  JSON  -- BAD: stuffing name, email, created_at, role into JSON
);
-- Every query needs JSON path extraction → slow, verbose, un-indexed
-- Just use proper columns!

-- The hybrid approach (best of both worlds):
CREATE TABLE products (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(100) NOT NULL,     -- always queried → normalized
  price       DECIMAL(10,2) NOT NULL,    -- always queried → normalized
  category_id INT NOT NULL,              -- FK, always filtered → normalized
  attributes  JSON,                      -- variable per category → JSON
  INDEX idx_price (price),
  INDEX idx_category (category_id)
  -- Functional indexes on attributes if specific paths are queried:
  -- INDEX idx_color ((attributes->>'$.color'))
);
```

**Q13. "A FULLTEXT search query is returning no results even though you're sure the words exist in the table. What are all the causes?"**
A:

```sql
-- ── Cause 1: >50% rule in NATURAL LANGUAGE MODE ────────────────────────
SELECT COUNT(*) FROM articles;                    -- 100 total rows
SELECT COUNT(*) FROM articles
WHERE MATCH(body) AGAINST ('tutorial');           -- 0 results

-- Check how many rows contain the word:
SELECT COUNT(*) FROM articles WHERE body LIKE '%tutorial%';  -- 90 rows!
-- 90/100 = 90% > 50% threshold → MySQL ignores this word in natural language mode

-- Fix: use BOOLEAN MODE (no >50% rule):
WHERE MATCH(body) AGAINST('+tutorial' IN BOOLEAN MODE);  -- returns results ✓

-- ── Cause 2: Word shorter than minimum token size ─────────────────────
SHOW VARIABLES LIKE 'innodb_ft_min_token_size';
-- Value: 3  (words < 3 chars ignored)

-- Searching for 'db' (2 chars) → silently returns no results
WHERE MATCH(body) AGAINST('db');    -- 'db' is 2 chars → filtered out → 0 results

-- Fix: reduce minimum token size (requires rebuild):
-- my.cnf: innodb_ft_min_token_size = 2
-- Then rebuild: ALTER TABLE articles DROP INDEX ft_body, ADD FULLTEXT INDEX ft_body(body);

-- Fix alternative: search for longer form: AGAINST('database' IN BOOLEAN MODE)

-- ── Cause 3: Word is a stop word ──────────────────────────────────────
SHOW VARIABLES LIKE 'innodb_ft_server_stopword_table';
SHOW VARIABLES LIKE 'innodb_ft_enable_stopword';

-- Default stop words include: 'in', 'it', 'is', 'a', 'the', 'be', 'to', 'or'
-- Searching for 'the database' → 'the' is a stop word → only 'database' searched
-- Searching for 'or' alone → stop word → no results

-- Check if word is a stop word:
SELECT * FROM information_schema.innodb_ft_default_stopword
WHERE value = 'your_word';

-- Fix: remove stop word from the list or disable stop words:
SET GLOBAL innodb_ft_enable_stopword = 0;
-- Rebuild index after changing

-- ── Cause 4: FULLTEXT index doesn't include the searched column ────────
-- You indexed 'title' but searched 'body':
CREATE FULLTEXT INDEX ft_title ON articles(title);  -- only title
WHERE MATCH(body) AGAINST('mysql');  -- ← Error or no index used

-- Fix: create the index on the column you're searching:
CREATE FULLTEXT INDEX ft_body ON articles(body);

-- Or search the right column:
WHERE MATCH(title) AGAINST('mysql');

-- ── Cause 5: Multi-column index — searching wrong column combination ───
CREATE FULLTEXT INDEX ft_all ON articles(title, body);

-- Must use BOTH columns in MATCH (or create separate index):
WHERE MATCH(title) AGAINST('mysql');        -- ✗ Error: ft_all is on (title,body) together
WHERE MATCH(title, body) AGAINST('mysql');  -- ✓ matches ft_all

-- Fix: either use the right column list in MATCH or create separate indexes

-- ── Cause 6: Index not built / index cache not flushed ─────────────────
-- InnoDB FULLTEXT indexes have a cache that's flushed to disk periodically
-- Freshly inserted rows may not appear immediately in searches

-- Force flush:
SET GLOBAL innodb_ft_aux_table = 'mydb/articles';  -- point to the table
SELECT * FROM information_schema.innodb_ft_index_cache;  -- see cached (not yet flushed) entries
-- Flush:
SET GLOBAL innodb_optimize_fulltext_only = 1;
OPTIMIZE TABLE articles;  -- flushes FULLTEXT cache to disk
SET GLOBAL innodb_optimize_fulltext_only = 0;

-- ── Cause 7: stopword is domain-specific ──────────────────────────────
-- "MySQL" might be on a custom stopword list for a general tech database
-- "php" on a PHP tutorial site (appears in 90%+ of articles → >50% rule)
-- Check and adjust the stopword table or switch to boolean mode
```

## Problem 2 — Replacing EAV with JSON: Product Attributes

### Problem
A legacy system uses an EAV (Entity-Attribute-Value) table for product attributes. It has 30M rows in the `product_attributes` table and requires 5-way joins to reconstruct a product. Migrate to JSON with proper indexing.

```sql
-- ── Legacy EAV Schema (the problem) ────────────────────────────────────
CREATE TABLE products_old (
  id   INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  sku  VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE product_attributes (
  product_id INT NOT NULL,
  attr_name  VARCHAR(50) NOT NULL,
  attr_value VARCHAR(500),
  PRIMARY KEY (product_id, attr_name),
  INDEX idx_attr_name_value (attr_name, attr_value(100))
);

-- Querying is a nightmare (5-way join for 5 attributes):
SELECT
  p.id, p.name, p.sku,
  color.attr_value AS color,
  size.attr_value  AS size,
  weight.attr_value AS weight,
  brand.attr_value AS brand,
  material.attr_value AS material
FROM products_old p
LEFT JOIN product_attributes color    ON p.id = color.product_id    AND color.attr_name    = 'color'
LEFT JOIN product_attributes size     ON p.id = size.product_id     AND size.attr_name     = 'size'
LEFT JOIN product_attributes weight   ON p.id = weight.product_id   AND weight.attr_name   = 'weight'
LEFT JOIN product_attributes brand    ON p.id = brand.product_id    AND brand.attr_name    = 'brand'
LEFT JOIN product_attributes material ON p.id = material.product_id AND material.attr_name = 'material'
WHERE p.sku = 'LAPTOP-PRO-001';
-- 5 index lookups + 5 join operations for ONE product!

-- ── New JSON Schema ────────────────────────────────────────────────────
CREATE TABLE products_new (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  name        VARCHAR(100) NOT NULL,
  sku         VARCHAR(50)  NOT NULL,
  category    VARCHAR(50)  NOT NULL,
  -- Core fields that are ALWAYS queried: normalized (not JSON)
  price       DECIMAL(10, 2) NOT NULL,
  brand       VARCHAR(100),
  -- Variable attributes: JSON
  attributes  JSON,
  PRIMARY KEY (id),
  UNIQUE KEY uq_sku (sku),
  INDEX idx_brand (brand),
  INDEX idx_category_price (category, price),
  -- Functional indexes for commonly-filtered JSON paths:
  INDEX idx_color    ((attributes->>'$.color')),
  INDEX idx_material ((attributes->>'$.material'))
);

-- ── Migration: EAV → JSON ─────────────────────────────────────────────
-- Step 1: Aggregate EAV rows per product into JSON object
INSERT INTO products_new (name, sku, category, price, brand, attributes)
SELECT
  p.name,
  p.sku,
  COALESCE(MAX(CASE WHEN pa.attr_name = 'category' THEN pa.attr_value END), 'uncategorized'),
  COALESCE(MAX(CASE WHEN pa.attr_name = 'price' THEN pa.attr_value + 0 END), 0),
  MAX(CASE WHEN pa.attr_name = 'brand' THEN pa.attr_value END),
  JSON_OBJECTAGG(
    pa.attr_name,
    pa.attr_value
  )  AS attributes
FROM products_old p
LEFT JOIN product_attributes pa ON p.id = pa.product_id
GROUP BY p.id, p.name, p.sku;
-- JSON_OBJECTAGG aggregates ALL attribute name→value pairs into one JSON object per product

-- Verify:
SELECT id, name, JSON_PRETTY(attributes) FROM products_new LIMIT 1 \G
-- attributes: {
--   "color": "silver",
--   "size": "15 inch",
--   "weight": "1.8 kg",
--   "material": "aluminum",
--   "brand": "TechCorp",
--   ...
-- }

-- ── New query: single table, no joins ─────────────────────────────────
-- Old: 5-way join query (30+ lines SQL)
-- New:
SELECT id, name, sku, attributes->>'$.color' AS color, attributes->>'$.size' AS size
FROM products_new
WHERE sku = 'LAPTOP-PRO-001';
-- Result: one row, one index seek on uq_sku — massively simpler

-- ── Filtering on JSON attributes ──────────────────────────────────────
-- Find silver laptops under $1000:
SELECT id, name, price, attributes->>'$.color' AS color
FROM products_new
WHERE category = 'Laptops'
  AND price < 1000
  AND attributes->>'$.color' = 'silver';
-- Uses: idx_category_price (category+price filter) + idx_color (color filter)
-- EXPLAIN: possible_keys includes idx_color, idx_category_price

-- Find products by material (uses functional index):
SELECT id, name FROM products_new
WHERE attributes->>'$.material' = 'aluminum';
-- EXPLAIN: key=idx_material, type=ref ✓

-- Find products with any of multiple colors (multi-value JSON):
-- For products with multiple colors: attributes.colors = ["silver", "black", "gold"]
CREATE INDEX idx_colors_mv ON products_new
  ((CAST(attributes->'$.colors' AS CHAR(30) ARRAY)));

SELECT id, name FROM products_new
WHERE 'silver' MEMBER OF (attributes->'$.colors');
-- Uses multi-valued index ✓
```

## Problem 3 — JSON Document Store: User Preferences and Dynamic Configs

### Problem
Build a user preferences system where users can set arbitrary key-value configurations, the system stores defaults, and preferences can be merged. Handle partial updates efficiently.

```sql
-- ── Schema: preferences hierarchy ─────────────────────────────────────
CREATE TABLE preferences (
  user_id    INT UNSIGNED NOT NULL,
  scope      ENUM('global', 'app', 'feature') NOT NULL DEFAULT 'app',
  app_id     VARCHAR(50),
  prefs      JSON NOT NULL DEFAULT (JSON_OBJECT()),
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, scope, app_id),
  -- Functional index for theme (frequently queried):
  INDEX idx_theme ((prefs->>'$.theme'))
);

-- ── Setting and updating preferences ──────────────────────────────────

-- Set initial preferences (insert or fully replace):
INSERT INTO preferences (user_id, scope, app_id, prefs)
VALUES (42, 'app', 'dashboard', '{
  "theme": "dark",
  "language": "en",
  "notifications": {"email": true, "push": false},
  "layout": "grid"
}')
ON DUPLICATE KEY UPDATE
  prefs      = VALUES(prefs),
  updated_at = NOW();

-- Update single field (partial update — efficient binary JSON update in MySQL 8.0):
UPDATE preferences
SET prefs = JSON_SET(prefs, '$.theme', 'light')
WHERE user_id = 42 AND scope = 'app' AND app_id = 'dashboard';
-- InnoDB can partially update the binary JSON (same-size replacement → no full rewrite)

-- Update nested field:
UPDATE preferences
SET prefs = JSON_SET(prefs, '$.notifications.push', true)
WHERE user_id = 42 AND scope = 'app' AND app_id = 'dashboard';

-- Toggle a boolean:
UPDATE preferences
SET prefs = JSON_SET(
  prefs,
  '$.notifications.email',
  NOT (prefs->>'$.notifications.email' = 'true')
)
WHERE user_id = 42 AND scope = 'app' AND app_id = 'dashboard';

-- ── Merging defaults with user preferences ─────────────────────────────
-- System defaults + user overrides (user wins on conflicts):
SELECT
  42 AS user_id,
  JSON_MERGE_PATCH(
    -- Layer 1: system-wide defaults (base)
    '{
      "theme": "light",

      (SELECT prefs FROM preferences
       WHERE user_id = 42 AND scope = 'app' AND app_id = 'dashboard'),

SELECT user_id FROM preferences
WHERE scope = 'app' AND app_id = 'dashboard'
```

## Problem 4 — Multi-Valued JSON Index for Tag-Based Search

### Problem
A `posts` table stores tags as a JSON array. Build efficient filtering by tags, including multi-tag AND/OR queries, and tag frequency analysis.

```sql
-- ── Schema with multi-valued index ────────────────────────────────────
CREATE TABLE posts (
  id         INT UNSIGNED NOT NULL AUTO_INCREMENT,
  title      VARCHAR(300) NOT NULL,
  body       MEDIUMTEXT,
  author_id  INT UNSIGNED NOT NULL,
  tags       JSON,         -- ["mysql", "performance", "indexing"]
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  FULLTEXT INDEX ft_title_body (title, body),
  -- Multi-valued index on the tags array:
  INDEX idx_tags ((CAST(tags AS CHAR(50) ARRAY)))
);

-- Sample data:
INSERT INTO posts (title, tags) VALUES
('MySQL Indexing Guide',   '["mysql", "indexing", "performance", "database"]'),
('Query Optimization',     '["mysql", "performance", "query", "optimization"]'),
('PostgreSQL vs MySQL',    '["mysql", "postgresql", "database", "comparison"]'),
('Redis Caching Patterns', '["redis", "caching", "performance", "nosql"]');

-- ── Single-tag filter (uses multi-valued index) ────────────────────────
-- Find all posts tagged 'mysql':
SELECT id, title FROM posts
WHERE 'mysql' MEMBER OF (tags);
EXPLAIN SELECT id, title FROM posts WHERE 'mysql' MEMBER OF (tags) \G
-- key: idx_tags, type: ref — index used! ✓

-- ── AND filter: posts with ALL specified tags ──────────────────────────
-- Find posts tagged BOTH 'mysql' AND 'performance':
SELECT id, title FROM posts
WHERE 'mysql'       MEMBER OF (tags)
  AND 'performance' MEMBER OF (tags);
-- Both conditions use idx_tags (intersection of index lookups)

-- Alternative with JSON_CONTAINS (also uses idx_tags in MySQL 8.0.17+):
SELECT id, title FROM posts
WHERE JSON_CONTAINS(tags, '["mysql", "performance"]');
-- JSON_CONTAINS with array: doc must contain ALL elements

-- ── OR filter: posts with ANY of specified tags ────────────────────────
-- Find posts tagged 'mysql' OR 'postgresql':
SELECT id, title FROM posts
WHERE JSON_OVERLAPS(tags, '["mysql", "postgresql"]');
-- JSON_OVERLAPS: returns true if any element in common
-- EXPLAIN: can use idx_tags for this

-- Alternative with OR:
SELECT id, title FROM posts
WHERE 'mysql'      MEMBER OF (tags)
   OR 'postgresql' MEMBER OF (tags);
-- MySQL uses union of index ranges from idx_tags

-- ── Tag frequency analysis ─────────────────────────────────────────────
-- How many posts have each tag?
SELECT jt.tag, COUNT(*) AS post_count
FROM posts,
JSON_TABLE(
  posts.tags,
  '$[*]' COLUMNS (tag VARCHAR(50) PATH '$')
) AS jt
GROUP BY jt.tag
ORDER BY post_count DESC;
-- | tag          | post_count |
-- |--------------|------------|
-- | mysql        |     3      |
-- | performance  |     3      |
-- | database     |     2      |
-- | indexing     |     1      |
-- | optimization |     1      |

-- ── Tag co-occurrence analysis ─────────────────────────────────────────
-- Which tags appear together most often?
WITH post_tags AS (
  SELECT p.id, jt.tag
  FROM posts p,
  JSON_TABLE(p.tags, '$[*]' COLUMNS (tag VARCHAR(50) PATH '$')) jt
)
SELECT
  a.tag AS tag1,
  b.tag AS tag2,
  COUNT(*) AS cooccurrence
FROM post_tags a
JOIN post_tags b ON a.id = b.id AND a.tag < b.tag  -- avoid (A,B) and (B,A) duplicates
GROUP BY a.tag, b.tag
ORDER BY cooccurrence DESC
LIMIT 10;
-- | tag1        | tag2         | cooccurrence |
-- |-------------|--------------|--------------|
-- | mysql       | performance  |      2       |
-- | mysql       | database     |      2       |
-- | database    | performance  |      1       |

-- ── Updating the tags array ───────────────────────────────────────────
-- Add a tag (if not already present):
UPDATE posts
SET tags = JSON_ARRAY_APPEND(tags, '$', 'tutorial')
WHERE id = 1
  AND NOT ('tutorial' MEMBER OF (tags));  -- prevent duplicates

-- Remove a specific tag:
-- First, find the index, then remove it (no direct JSON_ARRAY_REMOVE by value in MySQL)
-- Use JSON_TABLE to find the position, then JSON_REMOVE:
UPDATE posts p
JOIN (
  SELECT p.id, jt.idx
  FROM posts p,
  JSON_TABLE(p.tags, '$[*]' COLUMNS (idx FOR ORDINALITY, val VARCHAR(50) PATH '$')) jt
  WHERE jt.val = 'tutorial' AND p.id = 1
) tag_pos ON p.id = tag_pos.id
SET p.tags = JSON_REMOVE(p.tags, CONCAT('$[', tag_pos.idx - 1, ']'));
-- idx is 1-based (ORDINALITY), JSON path is 0-based → subtract 1

-- Or: application-side remove (simpler):
-- Read tags array, remove element in app code, SET tags = JSON_ARRAY(remaining...)
```

## Problem 5 — Combining `FULLTEXT` and `JSON` for a Product Search Engine

### Problem
Build a product search that combines full-text search on `name`/`description` with JSON attribute filtering, relevance ranking, and faceted search counts — all in a single efficient query.

```sql
-- ── Schema ─────────────────────────────────────────────────────────────
CREATE TABLE catalog (
  id            INT UNSIGNED NOT NULL AUTO_INCREMENT,
  name          VARCHAR(200) NOT NULL,
  description   TEXT,
  brand         VARCHAR(100) NOT NULL,
  price         DECIMAL(10, 2) NOT NULL,
  category      VARCHAR(50) NOT NULL,
  in_stock      TINYINT(1) NOT NULL DEFAULT 1,
  attributes    JSON,
  tags          JSON,
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  -- Full-text search:
  FULLTEXT INDEX ft_search (name, description),
  -- Regular index for filtering:
  INDEX idx_brand_price (brand, price),
  INDEX idx_category_price (category, price),
  INDEX idx_in_stock (in_stock),
  -- Functional indexes for JSON attribute filters:
  INDEX idx_color    ((attributes->>'$.color')),
  INDEX idx_size     ((attributes->>'$.size')),
  -- Multi-valued index for tags:
  INDEX idx_tags     ((CAST(tags AS CHAR(50) ARRAY)))
);

-- ── Full search query with all filters ────────────────────────────────
-- User search: 'wireless headphones' with filters: brand=Sony, price=$50-$300, color=black, tag=noise-cancelling

SELECT
  c.id,
  c.name,
  c.brand,
  c.price,
  c.attributes->>'$.color' AS color,
  c.attributes->>'$.connectivity' AS connectivity,
  -- Relevance score:
  MATCH(c.name, c.description) AGAINST ('wireless headphones' IN BOOLEAN MODE) AS relevance,
  -- Boosted score: name match is 3×, add recency decay:
  (
    MATCH(c.name, c.description) AGAINST ('+wireless +headphones' IN BOOLEAN MODE) * 3
    + MATCH(c.name, c.description) AGAINST ('"wireless headphones"' IN BOOLEAN MODE) * 5  -- exact phrase boost
    + (1 / (1 + DATEDIFF(NOW(), c.created_at) / 30))  -- recency: newer = higher score
  ) AS custom_score
FROM catalog c
WHERE
  -- Full-text filter (uses FULLTEXT index):
  MATCH(c.name, c.description) AGAINST ('+wireless +headphones' IN BOOLEAN MODE)
  -- Regular column filters:
  AND c.in_stock = 1
  AND c.price BETWEEN 50 AND 300
  AND c.brand = 'Sony'
  -- JSON attribute filters (uses functional indexes):
  AND c.attributes->>'$.color' = 'black'
  -- Multi-valued tag filter (uses multi-valued index):
  AND 'noise-cancelling' MEMBER OF (c.tags)
ORDER BY custom_score DESC
LIMIT 20 OFFSET 0;

-- ── Faceted search counts (facets) ────────────────────────────────────
-- Return: how many results exist per facet value (for sidebar filters)
-- This is the hardest part — must count WITHIN the search results

-- Step 1: Get matching product IDs from the full-text + required filters:
WITH search_results AS (
  SELECT id, price, brand, attributes->>'$.color' AS color, tags
  FROM catalog
  WHERE MATCH(name, description) AGAINST ('+wireless +headphones' IN BOOLEAN MODE)
    AND in_stock = 1
    AND price BETWEEN 50 AND 300
    -- NOTE: do NOT apply brand/color/tag filters here — we need all results for facet counts
),
-- Step 2: Brand facet counts (from ALL results, not filtered by brand):
brand_counts AS (
  SELECT
    c.brand,
    COUNT(*) AS count
  FROM catalog c
  JOIN search_results sr ON c.id = sr.id
  GROUP BY c.brand
),
-- Step 3: Color facet counts:
color_counts AS (
  SELECT
    c.attributes->>'$.color' AS color,
    COUNT(*) AS count
  FROM catalog c
  JOIN search_results sr ON c.id = sr.id
  GROUP BY c.attributes->>'$.color'
),
-- Step 4: Tag facet counts (unnest JSON arrays):
tag_counts AS (
  SELECT
    jt.tag,
    COUNT(*) AS count
  FROM catalog c
  JOIN search_results sr ON c.id = sr.id,
  JSON_TABLE(c.tags, '$[*]' COLUMNS (tag VARCHAR(50) PATH '$')) jt
  GROUP BY jt.tag
  ORDER BY count DESC
  LIMIT 20  -- top 20 tags only
)
-- Return facets as JSON (simpler to return as one resultset):
SELECT JSON_OBJECT(
  'brands', (SELECT JSON_ARRAYAGG(JSON_OBJECT('value', brand, 'count', count)) FROM brand_counts),
  'colors', (SELECT JSON_ARRAYAGG(JSON_OBJECT('value', color, 'count', count)) FROM color_counts),
  'tags',   (SELECT JSON_ARRAYAGG(JSON_OBJECT('value', tag, 'count', count)) FROM tag_counts)
) AS facets;

-- Returns a single JSON object with all facet counts:
-- {
--   "brands": [{"value": "Sony", "count": 45}, {"value": "Bose", "count": 32}, ...],
--   "colors": [{"value": "black", "count": 52}, {"value": "white", "count": 28}, ...],
--   "tags":   [{"value": "wireless", "count": 89}, {"value": "noise-cancelling", "count": 41}, ...]
-- }
```

## Quick Reference — `FULLTEXT` and `JSON` Cheat Sheet

```
FULLTEXT INDEX:
  Only on: CHAR, VARCHAR, TEXT columns; InnoDB + MyISAM
  Create: CREATE FULLTEXT INDEX name ON t(col1, col2) [WITH PARSER ngram]
  Search: WHERE MATCH(col1, col2) AGAINST (query [mode])
  Match columns must EXACTLY match the indexed column list

SEARCH MODES:
  Natural Language (default):  relevance scoring; >50% word rule; no operators
  Boolean Mode:                operators; no >50% rule; +required -excluded "phrase" word* ~demote
  Query Expansion:             2-pass; expands query with words from top results

BOOLEAN OPERATORS:
  +word    → must include
  -word    → must exclude
  "phrase" → exact phrase match
  word*    → prefix wildcard (index* → indexes, indexing)
  ~word    → lowers score if present
  >word    → boost word's contribution to score
  <word    → demote word's contribution to score
  (expr)   → grouping

GOTCHAS:
  >50% rule: words in >50% of rows ignored in NATURAL LANGUAGE MODE → use BOOLEAN MODE
  innodb_ft_min_token_size=3: words <3 chars ignored → reduce for short terms
  Stop words: 'a','the','in','or' etc ignored → check innodb_ft_default_stopword
  Multi-col index: MATCH must list same columns as the index, in same order
  Relevance in WHERE and SELECT: MySQL usually deduplicates the computation
  ngram parser: use for CJK; controlled by ngram_token_size (not ft_min_token_size)

JSON TYPE:
  Auto-validates on insert → invalid JSON rejected
  Binary storage format → direct path access without full parse
  Keys sorted alphabetically on storage
  Max size = max_allowed_packet
  Partial update possible in MySQL 8.0 (same-size path replacement)

PATH EXPRESSIONS:
  $           → root document
  $.key       → object key
  $[N]        → array index (0-based)
  $[last]     → last array element (MySQL 8.0)
  $[*]        → all array elements
  $.*         → all object values
  $**.key     → recursive search for key at any depth

KEY EXTRACTION FUNCTIONS:
  JSON_EXTRACT(doc, path) = doc->path     → returns JSON (quoted strings)
  JSON_UNQUOTE(JSON_EXTRACT(d,p)) = ->>   → returns unquoted string
  JSON_VALUE(doc, path RETURNING type)    → MySQL 8.0; typed extraction with defaults

MODIFICATION FUNCTIONS:
  JSON_SET(doc, path, val)     → insert OR replace (upsert)
  JSON_INSERT(doc, path, val)  → insert only (ignore if exists)
  JSON_REPLACE(doc, path, val) → replace only (ignore if missing)
  JSON_REMOVE(doc, path)       → delete path
  JSON_MERGE_PATCH(a, b)       → RFC 7396: b wins; b's null removes key from a
  JSON_MERGE_PRESERVE(a, b)    → duplicates become arrays

SEARCH FUNCTIONS:
  JSON_CONTAINS(target, candidate[, path])     → does target contain candidate?
  JSON_CONTAINS_PATH(doc, 'one'|'all', paths)  → does path exist?
  JSON_SEARCH(doc, 'one'|'all', pattern)       → returns PATH where value found
  X MEMBER OF (json_array)                     → is X an element of the array? (MySQL 8.0)
  JSON_OVERLAPS(a, b)                          → any elements in common? (MySQL 8.0)

INDEXING JSON:
  Direct index: NOT ALLOWED on JSON column
  Generated column: ADD COLUMN x VARCHAR AS (doc->>'$.key') STORED; ADD INDEX(x)
  Functional index: ADD INDEX ((doc->>'$.key')) — implicit generated column (MySQL 8.0)
  Multi-valued:     ADD INDEX ((CAST(doc->'$.array' AS CHAR(N) ARRAY))) — for arrays (MySQL 8.0.17)
  Use MEMBER OF with multi-valued index for array element search
  Must use EXACT same expression in WHERE as in the functional index

AGGREGATION:
  JSON_ARRAYAGG(expr [ORDER BY])   → aggregate values into JSON array
  JSON_OBJECTAGG(key_expr, val)    → aggregate key-value pairs into JSON object
  JSON_TABLE(doc, path COLUMNS())  → relational view of JSON (unnesting arrays)

COMMON BUGS:
  FULLTEXT >50% rule    → switch to BOOLEAN MODE with + prefix
  Short words ignored   → reduce innodb_ft_min_token_size, rebuild index
  Stop word not found   → it's in the stop word list; use BOOLEAN MODE or remove stop word
  JSON type comparison  → ->> gives unquoted string; -> gives JSON-quoted string
  JSON false vs SQL FALSE → JSON_EXTRACT returns JSON false; use = false (lowercase) or = 0
  Missing path returns  → JSON_EXTRACT returns NULL for missing path; use COALESCE or DEFAULT
  Functional index miss → expression in WHERE must exactly match index definition
  MEMBER OF type mismatch → 'word' MEMBER OF (json_array): ensure types match (all strings or all ints)
```

**Final Tip:** At the 5 YOE level, MySQL FULLTEXT and JSON questions test whether you understand the **constraints and failure modes**, not just the happy-path API. The highest-signal answer on FULLTEXT: "The >50% suppression rule is the most common production 'bug' I've seen — a search for 'tutorial' on a tutorials website returns zero results because every article contains that word. The fix is always Boolean mode with the `+` prefix, which has no suppression rule. The second most common issue is the `innodb_ft_min_token_size=3` default silently ignoring words like 'id', 'db', 'go', 'vm' — you discover this when users can't find anything by searching short technical terms." For JSON indexing: "You can't index a JSON column directly — you have to extract a specific path and index that. In MySQL 8.0 you can do this cleanly with a functional index: `ADD INDEX ((attributes->>'$.color'))` creates an implicit generated column and indexes it. The catch is that the WHERE clause must use the exact same expression — `WHERE attributes->>'$.color' = 'black'` — not `WHERE JSON_EXTRACT(attributes, '$.color') = '"black"'`, even though they're semantically equivalent. For JSON arrays, the multi-valued index with `MEMBER OF` is the right tool — `JSON_CONTAINS` was the workaround before MySQL 8.0.17 and is notably slower without the multi-valued index."
