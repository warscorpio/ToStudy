# Deadlock Detection and Prevention — Interview Q&A (5 YOE Level)

## Section 1: Fundamentals

**Q1. What is a deadlock and what are the four Coffman conditions that define one?**

A: A deadlock is a situation where two or more transactions are each waiting for a lock held by another transaction in the group, forming a circular dependency — none can proceed and none will voluntarily release their locks.

The four **Coffman conditions** (1971) must ALL hold simultaneously for a deadlock to exist. Preventing any single condition prevents deadlocks entirely:

```
Condition 1 — Mutual Exclusion:
  At least one resource is held in non-sharable mode.
  Only one transaction can hold the lock at a time.
  Database example: an exclusive row lock on the accounts row for id=1.

Condition 2 — Hold and Wait:
  A transaction holds at least one resource while waiting to acquire additional resources.
  Database example: T1 holds the lock on account A and waits for the lock on account B.

Condition 3 — No Preemption:
  Locks cannot be forcibly taken from a transaction — only voluntarily released on commit/rollback.
  Database example: the database cannot steal T1's lock on account A to give to T2.
  (Deadlock detection DOES preempt — but only by aborting the transaction, not stealing its lock.)

Condition 4 — Circular Wait:
  A cycle exists: T1 waits for T2, T2 waits for T3, ..., Tn waits for T1.
  Database example:
    T1 holds lock(A), waits for lock(B)
    T2 holds lock(B), waits for lock(A)
    → Cycle: T1 → T2 → T1
```

```sql
-- Classic bank transfer deadlock (illustrates all four conditions):

-- T1 (transfer $100 from Alice to Bob):
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE name = 'Alice';  -- locks Alice's row
-- T1 now holds: lock(Alice), waits for: lock(Bob)

-- T2 (concurrent transfer $50 from Bob to Alice):
BEGIN;
UPDATE accounts SET balance = balance - 50  WHERE name = 'Bob';    -- locks Bob's row
-- T2 now holds: lock(Bob), waits for: lock(Alice)

-- T2 tries to update Alice:
UPDATE accounts SET balance = balance + 50  WHERE name = 'Alice';  -- BLOCKS — T1 holds Alice
-- T2 holds lock(Bob), waiting for lock(Alice)

-- T1 tries to update Bob:
UPDATE accounts SET balance = balance + 100 WHERE name = 'Bob';    -- BLOCKS — T2 holds Bob
-- T1 holds lock(Alice), waiting for lock(Bob)

-- DEADLOCK: T1 → T2 → T1
-- Neither transaction can proceed. Neither will release its lock.
-- The database must intervene.
```

**Q2. How does a deadlock differ from a livelock and from lock starvation?**

A: All three are concurrency failures but with distinct mechanisms and symptoms:

```
DEADLOCK — circular wait, all involved processes are blocked:
  T1 waits for T2. T2 waits for T1.
  Neither makes any progress. Both are blocked.
  CPU usage: near zero (all waiting).
  Resolution: database detects and aborts one victim.
  Symptom: transaction aborted with "deadlock detected" error.

LIVELOCK — active processes that don't make progress:
  T1 detects T2 is waiting, backs off out of courtesy.
  T2 detects T1 backed off, advances — then T1 retries.
  T2 detects T1 is now waiting, backs off.
  Both keep aborting and retrying but never complete.
  CPU usage: high (both actively retrying).
  Resolution: randomized backoff breaks the symmetry.
  Symptom: high retry rate, low throughput, no deadlock errors.
  Database world example: both transactions retry instantly after deadlock,
  re-acquiring locks in the same order, deadlocking again immediately.

STARVATION — one process never gets the resource it needs:
  Many transactions constantly hold the lock T_hungry needs.
  T_hungry waits indefinitely — not blocked by a cycle, just always behind others.
  The waited-for transactions DO make progress (no cycle).
  Resolution: priority queuing, aging (increase priority over time).
  Symptom: one transaction (or query type) has enormously higher latency than others.
  Database world example: a long-running report query always waits behind
  OLTP writes that constantly arrive — query eventually times out.
```

```
Quick identification:
  "No transaction makes progress" → deadlock (cycle) or livelock (symmetrical retry)
  "One transaction never gets the lock" → starvation
  "Transactions abort and immediately deadlock again" → livelock from instant retry
  "CPU is high but no work is done" → livelock
  "CPU is low, transactions just sit" → deadlock
```

## Section 2: Database Deadlocks

**Q3. What are the most common deadlock patterns in relational databases?**

A: Most database deadlocks follow one of three patterns:

```sql
-- ── Pattern 1: Different Lock Order (most common) ────────────────────────────
-- Two transactions acquire the same locks in different order.

-- T1: locks rows in order A → B
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- acquires lock(1)
SELECT * FROM accounts WHERE id = 2 FOR UPDATE;   -- wants lock(2)... BLOCKS if T2 holds it

-- T2: locks rows in order B → A (opposite order!)
BEGIN;
SELECT * FROM accounts WHERE id = 2 FOR UPDATE;   -- acquires lock(2)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- wants lock(1)... BLOCKS if T1 holds it

-- Deadlock: T1 holds(1) waits(2), T2 holds(2) waits(1)

-- ── Pattern 2: Escalating Lock (read then write) ──────────────────────────────
-- Transaction reads a row (shared lock), then tries to upgrade to write (exclusive lock)
-- when another transaction has also read the same row.

-- T1:
BEGIN;
SELECT * FROM inventory WHERE product_id = 42;      -- acquires shared lock
-- ... computation ...
UPDATE inventory SET stock = stock - 1 WHERE product_id = 42;  -- wants exclusive lock

-- T2 (concurrent):
BEGIN;
SELECT * FROM inventory WHERE product_id = 42;      -- also acquires shared lock (compatible)
-- ... computation ...
UPDATE inventory SET stock = stock - 1 WHERE product_id = 42;  -- wants exclusive lock

-- Neither can upgrade: each holds a shared lock that blocks the other's upgrade
-- PostgreSQL: ERRCODE 40P01 deadlock detected
-- Solution: use SELECT FOR UPDATE from the start (get exclusive lock immediately)

-- ── Pattern 3: InnoDB Gap Lock / Delete-Then-Insert ───────────────────────────
-- Covered in Q4 — unique to MySQL InnoDB's phantom-read prevention

-- ── Pattern 4: Foreign Key Lock Escalation ────────────────────────────────────
-- InnoDB acquires shared locks on parent rows when child rows are modified.

-- T1:
BEGIN;
UPDATE orders SET status = 'shipped' WHERE id = 1;
-- InnoDB acquires: exclusive lock on orders row 1
-- InnoDB acquires: shared lock on users row (the FK parent) to validate FK

-- T2 (concurrent):
BEGIN;
DELETE FROM users WHERE id = 123;
-- Wants: exclusive lock on users row 123
-- BLOCKED by T1's shared lock on users row 123

-- T1 then tries another update that needs users row 123:
UPDATE orders SET user_id = 123 WHERE id = 2;
-- Wants: shared lock on users row 123
-- BLOCKED by T2's waiting exclusive lock (wait queue ordering)

-- DEADLOCK: T1 (via FK) ↔ T2 (direct delete)
-- Prevention: avoid deleting parent rows while child transactions are in progress;
-- use ON DELETE CASCADE or process deletions first
```

**Q4. How do InnoDB's gap locks and next-key locks cause deadlocks that wouldn't exist with exact-row locks?**

A: InnoDB uses **next-key locks** (a combination of record lock + gap lock) at REPEATABLE READ isolation level to prevent phantom reads. These locks protect ranges of the index, not just specific rows — and multiple transactions can acquire compatible gap locks on the same range simultaneously, creating a deadlock when both then try to insert into that range:

```sql
-- Table: orders (user_id INT, total DECIMAL)
-- Existing rows: user_id = 3, user_id = 7 (no rows with user_id 4, 5, or 6)

-- T1: "Delete any existing order for user 5, then insert a new one"
BEGIN;
DELETE FROM orders WHERE user_id = 5;
-- user_id=5 doesn't exist, but InnoDB must prevent a phantom read.
-- InnoDB acquires: GAP LOCK on (3, 7) — the gap between existing rows 3 and 7.
-- Gap locks from different transactions ARE COMPATIBLE (multiple can coexist).
-- T1's gap lock doesn't block T2 from also getting a gap lock on (3, 7).

-- T2: same operation, concurrent
BEGIN;
DELETE FROM orders WHERE user_id = 5;
-- T2 also acquires: GAP LOCK on (3, 7) — compatible with T1's gap lock. SUCCESS.

-- T1 now tries to INSERT:
INSERT INTO orders (user_id, total) VALUES (5, 100.00);
-- INSERT must acquire an INSERT INTENTION LOCK on gap (3, 7).
-- INSERT intention locks are INCOMPATIBLE with gap locks held by other transactions.
-- T2 holds a gap lock on (3, 7) → T1's INSERT BLOCKS.

-- T2 now tries to INSERT:
INSERT INTO orders (user_id, total) VALUES (5, 200.00);
-- T2 also needs INSERT INTENTION LOCK on gap (3, 7).
-- T1 holds a gap lock on (3, 7) → T2's INSERT BLOCKS.

-- DEADLOCK:
-- T1 holds gap(3,7), waits for T2's gap(3,7) to release so it can INSERT
-- T2 holds gap(3,7), waits for T1's gap(3,7) to release so it can INSERT
-- Neither gap lock will be released until the transaction commits
-- Neither transaction can commit until its INSERT succeeds

-- This deadlock involves NO overlapping rows — both want to insert user_id=5
-- but neither actually holds a row lock on user_id=5 yet.

-- Prevention options:
-- 1. Use READ COMMITTED isolation level (no gap locks)
--    SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 2. Ensure the row exists before the "delete then insert" pattern:
--    Use INSERT ... ON DUPLICATE KEY UPDATE (single statement, no gap lock race)
INSERT INTO orders (user_id, total) VALUES (5, 100.00)
ON DUPLICATE KEY UPDATE total = VALUES(total);

-- 3. Serialize the upsert with an explicit lock:
SELECT id FROM orders WHERE user_id = 5 FOR UPDATE;
-- Gets exclusive record lock or gap lock exclusively — T2 would wait, not deadlock
```

## Section 3: Deadlock Detection

**Q5. What is a wait-for graph and how do databases use it to detect deadlocks?**

A: A wait-for graph is a directed graph where:
- **Nodes** represent transactions (or processes)
- **Directed edges** `T1 → T2` mean "T1 is waiting for a lock currently held by T2"

A deadlock exists if and only if the wait-for graph contains a **cycle**:

```
Example wait-for graph for the bank transfer deadlock:

  T1 ---holds---> lock(Alice)
  T2 ---holds---> lock(Bob)
  T1 ---waits---> lock(Bob)    [held by T2]  →  T1 → T2
  T2 ---waits---> lock(Alice)  [held by T1]  →  T2 → T1

Wait-for graph:
  T1 ──────────────> T2
   ↑                  │
   └──────────────────┘
  Cycle detected → DEADLOCK

Three-way deadlock:
  T1 waits for lock held by T2  →  T1 → T2
  T2 waits for lock held by T3  →  T2 → T3
  T3 waits for lock held by T1  →  T3 → T1

  T1 → T2 → T3 → T1  (cycle of length 3)

Detection algorithm (DFS for cycles):
  1. Start DFS from any node
  2. Mark nodes as "in current path" during DFS
  3. If we reach a node already "in current path" → cycle found → deadlock
  4. Time complexity: O(V + E) where V=transactions, E=lock-wait pairs
```

```sql
-- Viewing the wait-for graph in PostgreSQL:
SELECT
  waiting.pid                     AS waiting_pid,
  waiting.query                   AS waiting_query,
  blocking.pid                    AS blocking_pid,
  blocking.query                  AS blocking_query,
  waiting_locks.relation::regclass AS locked_table
FROM pg_stat_activity waiting
JOIN pg_locks waiting_locks
  ON waiting_locks.pid = waiting.pid
  AND NOT waiting_locks.granted
JOIN pg_locks blocking_locks
  ON blocking_locks.locktype  = waiting_locks.locktype
  AND blocking_locks.relation = waiting_locks.relation
  AND blocking_locks.granted
JOIN pg_stat_activity blocking
  ON blocking.pid = blocking_locks.pid;

-- InnoDB wait-for graph (current lock waits):
SELECT
  r.trx_id               AS waiting_txn,
  r.trx_mysql_thread_id  AS waiting_thread,
  r.trx_query            AS waiting_query,
  b.trx_id               AS blocking_txn,
  b.trx_mysql_thread_id  AS blocking_thread,
  b.trx_query            AS blocking_query
FROM information_schema.INNODB_TRX r
JOIN information_schema.INNODB_TRX b
  ON r.trx_wait_started IS NOT NULL
ORDER BY r.trx_wait_started;
```

**Q6. How does PostgreSQL detect deadlocks and choose which transaction to kill?**

A: PostgreSQL uses a **timeout-triggered** detection approach — it does not continuously maintain a wait-for graph. Instead, when a lock wait has persisted for longer than `deadlock_timeout` (default: 1 second), PostgreSQL runs a full cycle detection scan:

```sql
-- Configuration:
SHOW deadlock_timeout;        -- '1s' by default
SHOW lock_timeout;            -- '0' by default (no limit on lock wait)
SHOW log_lock_waits;          -- 'off' by default

-- Recommended production settings:
deadlock_timeout   = 1s       -- detect deadlocks after 1s of waiting
lock_timeout       = 30s      -- hard limit on any single lock wait
log_lock_waits     = on       -- log slow lock acquisitions (> deadlock_timeout)
log_min_duration_statement = 1000  -- also log slow queries

-- What PostgreSQL does on detecting a deadlock:
-- 1. Runs DFS cycle detection on the full wait-for graph
-- 2. Finds a cycle
-- 3. Selects a victim — the process that is "most recent" or "easiest to abort"
--    (heuristic: PostgreSQL aborts the transaction that initiated the LAST lock request
--    in the cycle, which is the transaction that triggered the detection)
-- 4. Sends the victim an internal signal to abort
-- 5. The victim's transaction rolls back completely (all changes undone)
-- 6. PostgreSQL raises: ERROR 40P01: deadlock detected

-- The error includes the cycle description:
-- ERROR:  deadlock detected
-- DETAIL: Process 12345 waits for ShareLock on transaction 7890;
--         blocked by process 67890.
--         Process 67890 waits for ShareLock on transaction 4567;
--         blocked by process 12345.
-- HINT:   See server log for query details.

-- The surviving transaction(s) proceed normally after the victim is aborted.
-- Application must catch error code 40P01 and retry the aborted transaction.
```

**Q7. How does InnoDB detect deadlocks and how does it choose the victim?**

A: InnoDB takes an **immediate detection** approach — it runs cycle detection synchronously whenever a transaction tries to acquire a lock and must wait. If the new wait would create a cycle, InnoDB aborts one of the transactions immediately rather than waiting for a timeout:

```sql
-- InnoDB deadlock detection:
-- When T1 requests a lock held by T2:
-- InnoDB builds/updates the wait-for graph immediately
-- Runs DFS to check if T1 → T2 creates a cycle
-- If cycle found → immediately choose victim and abort it
-- Typical latency: microseconds (no 1-second wait like PostgreSQL)

-- Victim selection heuristic:
-- InnoDB chooses the transaction with FEWER MODIFIED ROWS to roll back
-- (minimizes wasted work — the "lighter" transaction is aborted)
-- If equal: the transaction that requested the lock LAST is aborted

-- Configuration:
innodb_deadlock_detect = ON    -- default; turn OFF for very high-contention tables
                                -- where deadlock detection itself becomes a bottleneck
                                -- (graph traversal under thousands of concurrent transactions)
                                -- When OFF: rely on innodb_lock_wait_timeout instead

innodb_lock_wait_timeout = 50  -- seconds to wait before timeout (default 50)
                                -- Used as fallback when deadlock_detect is OFF
                                -- or when the cycle involves very long lock chains

-- Error codes:
-- MySQL: ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
-- SQLSTATE: 40001 (same as PostgreSQL's 40P01 — serialization failure family)

-- When innodb_deadlock_detect = OFF and timeout fires:
-- ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
-- SQLSTATE: HY000 — note: this is NOT the same as 40001 deadlock error!
-- Must handle both error codes in application retry logic when using InnoDB without detect

-- Log ALL deadlocks (not just the most recent one):
innodb_print_all_deadlocks = ON   -- writes each deadlock to the MySQL error log
                                   -- essential for production debugging
                                   -- default OFF (only the last deadlock visible in SHOW INNODB STATUS)
```

## Section 4: Prevention Strategies

**Q8. How does consistent lock ordering prevent deadlocks, and how do you implement it?**

A: Lock ordering eliminates the **Circular Wait** Coffman condition. If every transaction always acquires locks in the same global order, no cycle can form in the wait-for graph:

```
Without ordering:                    With consistent ordering (ascending ID):
T1: lock(1) then lock(2)             T1: lock(1) then lock(2)
T2: lock(2) then lock(1)             T2: lock(1) then lock(2)
                                           ↑ same order
T1 → T2 → T1  (cycle → deadlock)    T2 waits for T1 to release lock(1)
                                      No cycle → no deadlock
```

```sql
-- WRONG: application acquires locks in parameter order
-- transfer(from_account, to_account) → different callers pass args in different order
-- transfer(1, 2) locks: 1 then 2
-- transfer(2, 1) locks: 2 then 1  → DEADLOCK

-- CORRECT: always sort by account ID before locking
-- transfer(from_account, to_account):
--   accounts_to_lock = sort([from_account, to_account]) by id ascending
--   lock accounts_to_lock[0] first, then accounts_to_lock[1]

-- SQL implementation (PostgreSQL):
CREATE OR REPLACE FUNCTION transfer(
  from_id  BIGINT,
  to_id    BIGINT,
  amount   NUMERIC
) RETURNS VOID AS $$
DECLARE
  first_id  BIGINT := LEAST(from_id, to_id);       -- always lock smaller ID first
  second_id BIGINT := GREATEST(from_id, to_id);    -- then larger ID
BEGIN
  -- Lock in consistent order regardless of which is source and which is destination:
  PERFORM id FROM accounts WHERE id = first_id  FOR UPDATE;
  PERFORM id FROM accounts WHERE id = second_id FOR UPDATE;

  UPDATE accounts SET balance = balance - amount WHERE id = from_id;
  UPDATE accounts SET balance = balance + amount WHERE id = to_id;
END;
$$ LANGUAGE plpgsql;

-- Now both transfer(1,2) and transfer(2,1) lock in order [1, 2]
-- One transaction waits for the other — no cycle possible

-- For locking multiple rows in order:
SELECT id FROM accounts
WHERE id = ANY(ARRAY[1, 5, 3, 2])
ORDER BY id         -- ← critical: ORDER BY ensures consistent lock acquisition order
FOR UPDATE;
-- Regardless of which IDs are passed, locks are acquired in ID order: 1, 2, 3, 5
```

```typescript
// Application-level consistent ordering:
async function transfer(
  fromAccountId: number,
  toAccountId:   number,
  amount:        number,
  trx:           Transaction
): Promise<void> {
  // Sort IDs to ensure consistent lock acquisition order:
  const [firstId, secondId] = [fromAccountId, toAccountId].sort((a, b) => a - b);

  // Lock in sorted order:
  await trx.raw(`SELECT id FROM accounts WHERE id = ? FOR UPDATE`, [firstId]);
  await trx.raw(`SELECT id FROM accounts WHERE id = ? FOR UPDATE`, [secondId]);

  await trx.raw(`UPDATE accounts SET balance = balance - ? WHERE id = ?`, [amount, fromAccountId]);
  await trx.raw(`UPDATE accounts SET balance = balance + ? WHERE id = ?`, [amount, toAccountId]);
}
```

**Q9. How does minimizing transaction scope reduce deadlock probability?**

A: Short transactions hold fewer locks for less time, reducing the window during which another transaction can acquire conflicting locks:

```sql
-- LONG transaction scope — high deadlock risk:
BEGIN;
  -- 1. Read product data:
  SELECT * FROM products WHERE id = 42 FOR UPDATE;   -- holds lock for entire transaction

  -- 2. Expensive computation outside DB (HTTP API call, PDF generation):
  -- ← 2 seconds pass while locks are held

  -- 3. Read user data:
  SELECT * FROM users WHERE id = 100 FOR UPDATE;    -- holds more locks

  -- 4. Write order:
  INSERT INTO orders (...) VALUES (...);

  -- 5. More external API calls:
  -- ← another 1 second

  -- 6. Update inventory:
  UPDATE inventory SET stock = stock - 1 WHERE product_id = 42;
COMMIT;

-- Total lock hold time: ~3-4 seconds
-- Other transactions trying to access product 42 or user 100 wait the full duration
-- High probability of deadlock with any concurrent order for the same product/user

-- SHORT transaction scope — low deadlock risk:
-- Step 1: Gather data WITHOUT locks
SELECT stock FROM inventory WHERE product_id = 42;
SELECT credit_limit FROM users WHERE id = 100;

-- Step 2: Do computation OUTSIDE the transaction
-- (validate, compute prices, call external APIs)

-- Step 3: Short atomic transaction — lock only what you need to write
BEGIN;
  SELECT stock FROM inventory WHERE product_id = 42 FOR UPDATE;  -- lock only here
  -- Immediate check and write — no external calls while locked:
  IF stock >= 1 THEN
    UPDATE inventory SET stock = stock - 1 WHERE product_id = 42;
    INSERT INTO orders (product_id, user_id, ...) VALUES (42, 100, ...);
  END IF;
COMMIT;
-- Total lock hold time: <10ms
-- Probability of deadlock: dramatically reduced
```

**Q10. What is the role of isolation levels in deadlock frequency?**

A: Higher isolation levels require more locks to provide their guarantees, increasing contention and deadlock probability. Choosing the right isolation level for your workload is a meaningful deadlock prevention lever:

```sql
-- READ UNCOMMITTED (MySQL only, not PostgreSQL):
-- No locks for reads. No phantom protection.
-- Deadlock frequency: lowest possible for reads.
-- NEVER use: reads see uncommitted "dirty" data.

-- READ COMMITTED:
-- No shared locks held for reads (MVCC reads committed data without locks).
-- No gap locks in MySQL InnoDB (only record locks for writes).
-- Deadlock frequency: low.
-- Good for: OLTP with high write throughput.
-- Trade-off: non-repeatable reads (two identical SELECTs can return different values).
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- REPEATABLE READ (MySQL InnoDB default, PostgreSQL default):
-- No shared locks for reads (MVCC), but gap locks for write operations.
-- InnoDB adds gap locks to prevent phantoms → more deadlock surface.
-- Deadlock frequency: medium.
-- Required for: certain replication modes (MySQL statement-based replication).

-- SERIALIZABLE:
-- Full predicate locking — reads acquire shared locks that block concurrent writes.
-- Even plain SELECTs can cause deadlocks.
-- Deadlock frequency: highest.
-- PostgreSQL SSI aborts conflicting transactions even without a traditional cycle.
-- Use when: strict correctness is non-negotiable (financial ledgers, inventory control).

-- Practical recommendation:
-- Default: REPEATABLE READ (provides consistency for most apps)
-- High-write OLTP: READ COMMITTED (eliminates gap lock deadlocks)
-- Financial / critical data: SERIALIZABLE (with retry logic for serialization failures)

-- In MySQL InnoDB: READ COMMITTED eliminates almost all gap lock deadlocks:
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- Gap locks are not used → the DELETE-then-INSERT deadlock pattern (Q4) disappears
-- Record locks still exist — but only for rows that actually exist

-- In PostgreSQL: READ COMMITTED eliminates some but not all deadlocks:
-- MVCC prevents most read-write deadlocks but writer-writer deadlocks remain
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

**Q11. What is SELECT FOR UPDATE SKIP LOCKED and when does it prevent deadlocks?**

A: `SELECT FOR UPDATE SKIP LOCKED` acquires locks on matching rows BUT skips (ignores) any rows that are already locked by another transaction — instead of waiting. This pattern is essential for job queues and work distribution where any available item is acceptable:

```sql
-- Job queue pattern WITHOUT SKIP LOCKED — causes deadlocks/contention:
-- T1: SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE;
--     → picks job_id=1, locks it
-- T2: SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE;
--     → also picks job_id=1 (same query, same result), BLOCKS waiting for T1's lock

-- If T2 queries without FOR UPDATE first, then updates:
-- T2: SELECT id FROM jobs WHERE status='pending' LIMIT 1;  → returns job_id=1
-- T2: UPDATE jobs SET status='processing' WHERE id=1;      → BLOCKS (T1 has it)
-- T1: UPDATE jobs SET status='processing' WHERE id=1; COMMIT;
-- T2: Unblocks, updates an already-processing job → duplicate work

-- WITH SKIP LOCKED — no contention, no deadlocks:
BEGIN;
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY priority DESC, created_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;    -- ← locks the first available unlocked job

-- If job_id=1 is locked by T1, T2 automatically skips it and picks job_id=2
-- No waiting. No deadlock. Each worker gets a different job.

UPDATE jobs SET status = 'processing', worker_id = $1, started_at = NOW()
WHERE id = $returned_id;
COMMIT;

-- Full job queue implementation:
-- Worker process loop:
LOOP:
  BEGIN;
  SELECT id, payload FROM jobs WHERE status='pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED;
  IF no_rows_returned: sleep(1s); CONTINUE;
  UPDATE jobs SET status='processing' WHERE id=returned_id;
  COMMIT;

  result = process(payload);

  BEGIN;
  UPDATE jobs SET status = (CASE WHEN result.ok THEN 'done' ELSE 'failed' END),
                 result = result.data,
                 finished_at = NOW()
  WHERE id = returned_id;
  COMMIT;
  GOTO LOOP;

-- Properties of SKIP LOCKED:
-- ✓ No lock waits → no deadlocks between workers
-- ✓ Perfect for worker pool patterns
-- ✗ No fairness guarantee (some jobs may be skipped if a slow worker holds their lock)
-- ✗ Not suitable when you NEED a specific row (use regular FOR UPDATE in that case)
```

## Section 5: Optimistic Locking

**Q12. What is optimistic locking and how does it avoid the deadlock problem entirely?**

A: Optimistic locking assumes conflicts are rare — it doesn't acquire any database locks during reads. Instead, it detects conflicts at write time by checking whether the data changed since it was read:

```sql
-- Schema: version column incremented on every update
ALTER TABLE accounts ADD COLUMN version INT NOT NULL DEFAULT 0;

-- Optimistic locking read-modify-write cycle:

-- Step 1: Read (no lock acquired)
SELECT id, balance, version FROM accounts WHERE id = 1;
-- Returns: id=1, balance=1000, version=5

-- Step 2: Compute new value (application logic)
-- new_balance = 1000 - 100 = 900

-- Step 3: Write with version check (the optimistic check)
UPDATE accounts
SET balance = 900,
    version = version + 1    -- increment version to invalidate other readers
WHERE id = 1
  AND version = 5;           -- ← ONLY updates if nobody else changed it since our read

-- rows_affected = 1 → SUCCESS: we were the only writer for this version
-- rows_affected = 0 → CONFLICT: someone else updated between our read and write
--                     → RETRY: re-read the new version, recompute, retry the write

-- Why no deadlocks:
-- No SELECT FOR UPDATE → no exclusive lock during the read phase
-- The UPDATE itself takes an exclusive lock momentarily (milliseconds)
-- No circular wait: transactions don't hold locks while waiting for other locks
-- At worst: retry overhead (not a deadlock)
```

```typescript
// TypeORM optimistic locking with @VersionColumn:
@Entity()
export class Account {
  @PrimaryGeneratedColumn()
  id: number;

  @Column('decimal', { precision: 15, scale: 2 })
  balance: number;

  @VersionColumn()          // TypeORM auto-increments this on every save
  version: number;
}

// TypeORM handles the version check automatically:
async function debit(accountId: number, amount: number): Promise<void> {
  const account = await accountRepo.findOneOrFail({ where: { id: accountId } });
  account.balance -= amount;
  // TypeORM adds: WHERE id=? AND version=? to the UPDATE
  // Throws OptimisticLockVersionMismatchError if version changed
  await accountRepo.save(account);
}

// For manual optimistic locking (raw SQL via TypeORM):
async function debitWithRetry(accountId: number, amount: number): Promise<void> {
  const maxRetries = 3;
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const account = await db.query(
      'SELECT id, balance, version FROM accounts WHERE id = ?', [accountId]
    );
    const newBalance = account.balance - amount;
    if (newBalance < 0) throw new Error('Insufficient funds');

    const result = await db.query(
      'UPDATE accounts SET balance = ?, version = version + 1 WHERE id = ? AND version = ?',
      [newBalance, accountId, account.version]
    );

    if (result.affectedRows === 1) return;   // SUCCESS

    if (attempt === maxRetries - 1) throw new Error('Too many conflicts — please retry');
    await sleep(Math.random() * 50);   // Brief random backoff before retry
  }
}
```

**Optimistic vs Pessimistic locking — when to use each:**
```
Optimistic locking:
  ✓ Low contention (conflicts are rare)
  ✓ Long read-compute-write cycles (holding locks during computation is too expensive)
  ✓ Distributed systems (no shared lock manager)
  ✓ REST APIs where a "read then write" spans two HTTP requests
  ✗ High contention (frequent conflicts → excessive retries → livelock risk)
  ✗ Multi-row operations requiring atomicity across many rows

Pessimistic locking (SELECT FOR UPDATE):
  ✓ High contention (conflicts are frequent — better to wait than retry)
  ✓ Short transactions (lock is held briefly)
  ✓ Multi-row operations (lock everything needed upfront)
  ✗ Long-running operations that hold locks across user interactions
  ✗ Distributed reads where a lock manager is unavailable
```

## Section 6: Deadlock Retry Logic

**Q13. How do you implement correct retry logic for deadlocked transactions?**

A: The critical rule: **retry the entire transaction from the beginning**, not just the failed statement. A deadlock victim has its entire transaction rolled back — any intermediate work is gone:

```typescript
// Deadlock error codes to detect:
const DEADLOCK_ERROR_CODES = new Set([
  '40P01',  // PostgreSQL: deadlock detected
  '40001',  // MySQL/PostgreSQL: serialization failure (Serializable level)
]);

const LOCK_TIMEOUT_CODES = new Set([
  '55P03',  // PostgreSQL: lock not available (lock_timeout)
  '1205',   // MySQL: lock wait timeout exceeded
]);

function isRetryableError(err: Error & { code?: string }): boolean {
  return DEADLOCK_ERROR_CODES.has(err.code ?? '') ||
         LOCK_TIMEOUT_CODES.has(err.code ?? '') ||
         err.code === '1213';  // MySQL deadlock (numeric code)
}

async function withDeadlockRetry<T>(
  operation: () => Promise<T>,
  options: {
    maxRetries?:    number;    // default 3
    baseDelayMs?:   number;    // default 50ms
    maxDelayMs?:    number;    // default 2000ms
    onRetry?:       (attempt: number, err: Error) => void;
  } = {}
): Promise<T> {
  const {
    maxRetries  = 3,
    baseDelayMs = 50,
    maxDelayMs  = 2000,
    onRetry,
  } = options;

  let lastError: Error;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await operation();   // operation() must include BEGIN and COMMIT
    } catch (err) {
      lastError = err as Error;

      if (!isRetryableError(lastError) || attempt === maxRetries) {
        throw lastError;          // Non-retryable or too many retries
      }

      onRetry?.(attempt + 1, lastError);

      // Exponential backoff with full jitter:
      const delay = Math.min(
        maxDelayMs,
        baseDelayMs * Math.pow(2, attempt) * (0.5 + Math.random() * 0.5)
      );
      await new Promise(resolve => setTimeout(resolve, delay));
      // Jitter is critical: if all conflicting transactions retry at the same time,
      // they deadlock again immediately (livelock)
    }
  }

  throw lastError!;
}

// Usage in NestJS service:
@Injectable()
export class TransferService {
  constructor(
    private readonly dataSource: DataSource,
    private readonly logger: Logger,
  ) {}

  async transfer(fromId: number, toId: number, amount: number): Promise<void> {
    await withDeadlockRetry(
      () => this.executeTransfer(fromId, toId, amount),
      {
        maxRetries: 3,
        onRetry: (attempt, err) => {
          this.logger.warn(
            `Transfer deadlock (attempt ${attempt}/3): ${err.message}`,
            { fromId, toId, amount }
          );
        },
      }
    );
  }

  private async executeTransfer(fromId: number, toId: number, amount: number): Promise<void> {
    // The ENTIRE transaction is inside the retried function:
    await this.dataSource.transaction(async (manager) => {
      // Consistent lock ordering: always lock smaller ID first
      const [first, second] = [fromId, toId].sort((a, b) => a - b);
      await manager.query('SELECT id FROM accounts WHERE id = ? FOR UPDATE', [first]);
      await manager.query('SELECT id FROM accounts WHERE id = ? FOR UPDATE', [second]);

      const [from] = await manager.query('SELECT balance FROM accounts WHERE id = ?', [fromId]);
      if (from.balance < amount) throw new Error('Insufficient funds');

      await manager.query('UPDATE accounts SET balance = balance - ? WHERE id = ?', [amount, fromId]);
      await manager.query('UPDATE accounts SET balance = balance + ? WHERE id = ?', [amount, toId]);
    });
    // If a deadlock occurs anywhere inside transaction(), it propagates here
    // withDeadlockRetry catches it, waits, and re-calls executeTransfer from scratch
  }
}
```

**Q15. How do you diagnose and monitor deadlocks in PostgreSQL?**

A:

```sql
-- ── Enable deadlock logging ────────────────────────────────────────────────────
-- postgresql.conf:
log_lock_waits = on                  -- Log when a lock wait exceeds deadlock_timeout
deadlock_timeout = 1s                -- How long before deadlock check runs (and logging)
log_min_duration_statement = 1000   -- Also log slow queries (ms)

-- When a deadlock occurs, PostgreSQL logs to stderr/pg_log:
-- 2024-01-15 10:23:45 UTC [12345] ERROR:  deadlock detected
-- 2024-01-15 10:23:45 UTC [12345] DETAIL: Process 12345 waits for ShareLock
--   on transaction 54321; blocked by process 67890.
--   Process 67890 waits for ShareLock on transaction 54321;
--   blocked by process 12345.
-- 2024-01-15 10:23:45 UTC [12345] HINT:  See server log for query details.
-- 2024-01-15 10:23:45 UTC [12345] CONTEXT: while updating tuple (0,1)
--   in relation "accounts"

-- ── View current lock waits ────────────────────────────────────────────────────
SELECT
  COALESCE(blocked_locks.relation::regclass::text, '') AS locked_table,
  blocked_activity.pid                                  AS blocked_pid,
  blocked_activity.query                                AS blocked_query,
  blocking_locks.pid                                    AS blocking_pid,
  blocking_activity.query                               AS blocking_query,
  now() - blocked_activity.query_start                  AS wait_duration
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity
  ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
  ON blocking_locks.locktype    = blocked_locks.locktype
  AND blocking_locks.relation   = blocked_locks.relation
  AND blocking_locks.granted    = true
  AND blocking_locks.pid       != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity
  ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted
ORDER BY wait_duration DESC;

-- ── Detect likely deadlock candidates (before they deadlock) ──────────────────
-- Transactions waiting for locks that are also waiting:
WITH lock_info AS (
  SELECT
    l.pid,
    l.granted,
    l.locktype,
    l.relation,
    l.transactionid,
    a.query,
    a.xact_start
  FROM pg_locks l
  JOIN pg_stat_activity a USING (pid)
)
SELECT
  w.pid AS waiting_pid, w.query AS waiting_query,
  h.pid AS holding_pid, h.query AS holding_query
FROM lock_info w
JOIN lock_info h
  ON h.transactionid = w.transactionid
  AND h.granted = true
  AND w.granted = false
  AND h.pid != w.pid;
```

**Q16. What are PostgreSQL advisory locks and when do they resolve deadlock scenarios?**

A: Advisory locks are explicit, application-controlled locks that are NOT tied to a specific table row or schema object. The application assigns an arbitrary integer key and calls lock functions:

```sql
-- Advisory lock types:
-- pg_advisory_lock(key)         — session-level: held until released or session ends
-- pg_advisory_xact_lock(key)    — transaction-level: released automatically on commit/rollback
-- pg_advisory_lock_shared(key)  — shared (multiple readers) version
-- pg_try_advisory_xact_lock(key) — non-blocking: returns false if can't acquire immediately

-- ── Use case 1: serialize operations on a logical entity (no row to lock) ─────
-- Prevent two workers from processing the same user's data concurrently,
-- even when reading from different tables:

BEGIN;
-- Acquire advisory lock using the user_id as the key:
SELECT pg_advisory_xact_lock($1);   -- $1 = user_id (e.g., 1234)

-- Now safe to process user 1234's data across multiple tables:
-- (No other transaction can hold this advisory lock for user 1234 simultaneously)
SELECT * FROM users WHERE id = $1;
SELECT * FROM orders WHERE user_id = $1;
SELECT * FROM subscriptions WHERE user_id = $1;
-- ... complex computation ...
UPDATE users SET processed_at = NOW() WHERE id = $1;
COMMIT;  -- advisory lock released automatically

-- ── Use case 2: prevent deadlocks by ordering advisory lock acquisition ───────
-- If you can't enforce lock ordering at the row level (e.g., application code
-- from multiple services), use advisory locks with consistent key ordering:

-- Service A: transfer from account 1 to account 2
-- Always acquire advisory locks in ascending order:
PERFORM pg_advisory_xact_lock(LEAST(1, 2));
PERFORM pg_advisory_xact_lock(GREATEST(1, 2));
-- Now do the actual UPDATE (row-level lock is brief, consistent order is enforced)

-- ── Use case 3: global mutex for distributed operations ───────────────────────
-- Only one instance at a time can run scheduled maintenance:
-- Returns false if already locked (non-blocking try):
DO $$
BEGIN
  IF NOT pg_try_advisory_xact_lock(99999) THEN
    RAISE NOTICE 'Maintenance already running — skipping';
    RETURN;
  END IF;
  -- ... do maintenance work ...
END;
$$;

-- Advisory locks are NOT held across connection pool recycling:
-- Use pg_advisory_xact_lock for transaction-level (auto-released on commit/rollback)
-- Use pg_advisory_lock for session-level (explicit pg_advisory_unlock needed)
-- Always prefer pg_advisory_xact_lock in application code to avoid lock leaks
```

## Section 8: Advanced Patterns

**Q17. How do distributed deadlocks occur across microservices, and why are they harder to detect?**

A: Distributed deadlocks occur when multiple services each hold resources that the other needs, but no single service or database can see the complete wait-for graph:

```
Distributed deadlock scenario:
  Service A holds: lock on Order #123 in orders-db
  Service B holds: lock on Payment #456 in payments-db

  Service A calls Service B: "update payment #456 for order #123"
  → Service B waits for lock on Payment #456 (held by itself? no...)

  Actually the deadlock pattern:
  Service A: holds(order-lock), calls ServiceB.reserveInventory() → waiting for ServiceB
  Service B: holds(inventory-lock), calls ServiceA.confirmOrder() → waiting for ServiceA
  
  Neither database sees the full picture:
    orders-db: sees a transaction waiting for... nothing (it's waiting for an HTTP response)
    inventory-db: sees a transaction waiting for... nothing (waiting for HTTP response)
  
  No database deadlock detector can find this cycle — it spans HTTP calls, not DB locks.
```

```
Detection and prevention for distributed deadlocks:

1. TIMEOUTS (most practical):
   Every service call has a deadline.
   If Service A waits more than 30 seconds for Service B, abort.
   Service B similarly times out.
   One of them will time out first → breaks the deadlock.
   
   Implementation: HTTP client timeout + distributed tracing to identify the timeout cause.

2. SAGA PATTERN (eliminate distributed locking):
   Instead of distributed locking, use compensating transactions.
   Each step is independently committed; failures trigger compensating actions.
   
   Order saga:
   Step 1: Reserve inventory (commit) → if later steps fail: RELEASE inventory
   Step 2: Charge payment (commit)   → if later steps fail: REFUND payment
   Step 3: Create order (commit)     → if this fails: compensate steps 1 and 2
   
   No distributed lock held across steps → no distributed deadlock possible.

3. AVOID CIRCULAR DEPENDENCIES:
   Service A should never call Service B while Service B can call Service A.
   Enforce unidirectional call graphs (DAG — Directed Acyclic Graph).
   If bidirectional calls are needed: use events/queues instead of direct calls.

4. SINGLE SERVICE OWNS EACH RESOURCE:
   Each resource is owned by exactly one service.
   Only the owning service locks and modifies it.
   Other services request changes through the owner → no distributed lock competition.
```

**Q20. "Design a complete deadlock-resistant payment processing system."**

A:

```typescript
// ── Architecture: deadlock resistance at every layer ─────────────────────────

// Layer 1: Database schema — optimized for minimal lock contention
/*
CREATE TABLE accounts (
  id         BIGINT PRIMARY KEY,         -- sequential IDs → consistent ordering
  user_id    BIGINT NOT NULL,
  balance    DECIMAL(15,2) NOT NULL DEFAULT 0,
  version    INT NOT NULL DEFAULT 0,     -- optimistic locking version
  updated_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE transfers (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  from_account  BIGINT NOT NULL,
  to_account    BIGINT NOT NULL,
  amount        DECIMAL(15,2) NOT NULL,
  status        ENUM('pending','completed','failed') DEFAULT 'pending',
  idempotency_key VARCHAR(64) UNIQUE NOT NULL,  -- prevents duplicate processing
  created_at    TIMESTAMP DEFAULT NOW()
);
*/

// Layer 2: Transaction with consistent lock ordering + short scope
@Injectable()
export class PaymentService {
  constructor(
    private dataSource: DataSource,
    private readonly logger: Logger,
  ) {}

  async processTransfer(dto: TransferDto): Promise<TransferResult> {
    // Idempotency: prevent duplicate transfers
    const existing = await this.dataSource
      .getRepository(Transfer)
      .findOne({ where: { idempotencyKey: dto.idempotencyKey } });

    if (existing) {
      return { transferId: existing.id, status: existing.status };
    }

    return withDeadlockRetry(
      () => this.executeTransfer(dto),
      {
        maxRetries: 5,
        baseDelayMs: 20,
        onRetry: (attempt, err) =>
          this.logger.warn(`Transfer retry ${attempt}`, { dto, error: err.message }),
      }
    );
  }

  private async executeTransfer(dto: TransferDto): Promise<TransferResult> {
    return this.dataSource.transaction('READ COMMITTED', async (trx) => {
      // Consistent lock order: always lock smaller account ID first
      const lockOrder = [dto.fromAccountId, dto.toAccountId].sort((a, b) => a - b);

      // Acquire locks in sorted order — one SELECT with ORDER BY
      const accounts = await trx
        .getRepository(Account)
        .createQueryBuilder('a')
        .where('a.id IN (:...ids)', { ids: lockOrder })
        .orderBy('a.id', 'ASC')        // ← consistent ordering
        .setLock('pessimistic_write')
        .getMany();

      const from = accounts.find(a => a.id === dto.fromAccountId);
      const to   = accounts.find(a => a.id === dto.toAccountId);
      if (!from || !to) throw new AccountNotFoundException();
      if (from.balance < dto.amount) throw new InsufficientFundsException();

      // Write (locks already held, this is fast):
      from.balance -= dto.amount;
      to.balance   += dto.amount;
      await trx.save([from, to]);

      const transfer = trx.getRepository(Transfer).create({
        fromAccount:    dto.fromAccountId,
        toAccount:      dto.toAccountId,
        amount:         dto.amount,
        status:         'completed',
        idempotencyKey: dto.idempotencyKey,
      });
      await trx.save(transfer);

      return { transferId: transfer.id, status: 'completed' };
    });
  }
}

      SELECT
        COUNT(*)                     AS waiting_locks,
        MAX(TIMESTAMPDIFF(SECOND, trx_wait_started, NOW())) AS max_wait_seconds
      FROM information_schema.INNODB_TRX
      WHERE trx_wait_started IS NOT NULL
    `);

    if (result.max_wait_seconds > 10) {
      this.metrics.gauge('db.lock_wait.max_seconds', result.max_wait_seconds);
      if (result.max_wait_seconds > 30) {
        this.alerts.fire('DEADLOCK_RISK', {
          waitingLocks: result.waiting_locks,
          maxWaitSeconds: result.max_wait_seconds,
        });
      }
    }
  }
}
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **Coffman conditions** | Mutual exclusion + Hold & Wait + No preemption + Circular wait — ALL four must hold for a deadlock |
| **Breaking Circular Wait** | Lock ordering: always acquire locks in the same global order (e.g., ascending ID) — the most effective prevention |
| **Breaking Hold & Wait** | Acquire all needed locks at once in one statement: `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE` |
| **PostgreSQL detection** | Triggered after `deadlock_timeout` (default 1s) — runs DFS cycle detection on wait-for graph |
| **PostgreSQL error code** | `40P01` (deadlock detected), `40001` (serialization failure at Serializable level) |
| **InnoDB detection** | Immediate — runs DFS on every lock wait; `innodb_deadlock_detect=ON` by default |
| **InnoDB error codes** | `1213` / SQLSTATE `40001` (deadlock), `1205` / SQLSTATE `HY000` (lock timeout — different!) |
| **Victim selection** | Both DBs choose the transaction with fewer modified rows (least work to roll back) |
| **Wait-for graph** | Directed graph: `T1 → T2` means T1 waits for T2's lock; a cycle = deadlock |
| **Retry rule** | ALWAYS retry the ENTIRE transaction — partial retries are wrong (victim is fully rolled back) |
| **Exponential backoff with jitter** | Prevents livelock: `delay = min(maxDelay, base * 2^attempt * (0.5 + random()*0.5))` |
| **Gap locks (InnoDB)** | Acquired at REPEATABLE READ for range/missing-row queries; compatible between transactions but block INSERT INTENTION |
| **Delete-then-insert deadlock** | Two transactions both DELETE missing row (get compatible gap locks), then both INSERT → deadlock on INSERT INTENTION |
| **Prevention: READ COMMITTED** | Eliminates gap locks in MySQL InnoDB — removes the delete-then-insert deadlock class |
| **Optimistic locking** | `UPDATE ... WHERE version = N` — no locks during read; detects conflict at write time; application retries |
| **Pessimistic locking** | `SELECT ... FOR UPDATE` — holds exclusive lock from read through write; prevents conflicts at cost of contention |
| **SKIP LOCKED** | `SELECT ... FOR UPDATE SKIP LOCKED` — skips locked rows instead of waiting; ideal for job queues |
| **Advisory locks** | `pg_advisory_xact_lock(key)` — application-level locks independent of table rows; auto-released on commit |
| **`innodb_print_all_deadlocks`** | `ON` — logs every deadlock to MySQL error log; essential for production debugging |
| **`SHOW ENGINE INNODB STATUS`** | Shows the most recent deadlock: which transactions, which locks held, which waited for, which rolled back |
| **Distributed deadlocks** | Span multiple services/DBs; no single detector can see the full cycle; prevent with timeouts + Saga pattern |
| **Short transactions** | Reduce deadlock probability by minimizing lock hold duration — do computation BEFORE opening the transaction |
| **Isolation level impact** | SERIALIZABLE > REPEATABLE READ > READ COMMITTED in terms of deadlock frequency |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) naming and explaining all four **Coffman conditions** with database examples, and knowing that preventing ANY ONE of them prevents deadlocks — most solutions target Circular Wait (consistent lock ordering) or Hold & Wait (acquire all locks at once); (2) the **consistent lock ordering** pattern with precise SQL implementation — `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE` acquires all locks in a single statement in a consistent order, eliminating deadlocks between transactions that need the same set of rows; (3) knowing the **retry must cover the entire transaction** — a deadlock victim has its ENTIRE transaction rolled back, so retrying only the failed statement leaves the transaction in an unknown state; always wrap the full `BEGIN/COMMIT` block in the retry loop; (4) the **InnoDB gap lock deadlock pattern** — two concurrent "delete-then-insert" operations on the same missing key acquire compatible gap locks simultaneously, then both deadlock when trying to get INSERT INTENTION locks; this is prevented by `READ COMMITTED` isolation (which eliminates gap locks), by `INSERT ... ON DUPLICATE KEY UPDATE`, or by pre-acquiring an exclusive lock with `SELECT FOR UPDATE`; and (5) the **exponential backoff with jitter** for retry logic — without jitter, two deadlocked transactions retry simultaneously, acquire locks in the same order, deadlock again immediately, and spin indefinitely (livelock); the random component breaks the symmetry and allows one to proceed before the other.
