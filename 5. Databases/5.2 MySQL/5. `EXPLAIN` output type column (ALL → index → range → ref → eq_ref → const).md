# MySQL `EXPLAIN` Output: Access Types — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is `EXPLAIN` in MySQL, and what does it tell you that you cannot learn from query timing alone?**
A: `EXPLAIN` instructs MySQL's query optimizer to reveal the execution plan it chose for a query — without actually running the query. Timing tells you a query is slow; `EXPLAIN` tells you *why* and *where* the slowness originates:

```sql
-- Basic EXPLAIN:
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

-- Output columns:
-- id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra
--  1 | SIMPLE      | orders| NULL       | ALL  | NULL          | NULL| NULL    | NULL| 89432| 10.00   | Using where

-- What each column reveals:
-- id:            Query block number (subqueries get higher numbers)
-- select_type:   SIMPLE, PRIMARY, SUBQUERY, DERIVED, UNION...
-- table:         Which table this row is about
-- partitions:    Which partition(s) accessed (if table is partitioned)
-- type:          THE MOST IMPORTANT COLUMN — the access method used
-- possible_keys: Indexes MySQL considered using
-- key:           The index MySQL actually chose (NULL = no index)
-- key_len:       How many bytes of the index key were used
-- ref:           What was compared to the index key (const, column name...)
-- rows:          Estimated rows MySQL expects to examine
-- filtered:      Estimated % of rows remaining after table filter
-- Extra:         Additional information (Using where, Using index, filesort...)
```

```sql
-- EXPLAIN ANALYZE (MySQL 8.0.18+) — runs the query AND shows actual timings:
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;

-- Output (tree format):
-- -> Filter: (orders.user_id = 42)  (cost=9032.45 rows=8943) (actual time=0.045..18.2 rows=312 loops=1)
--     -> Table scan on orders  (cost=9032.45 rows=89432) (actual time=0.038..15.1 rows=89432 loops=1)

-- "rows=89432" (estimate) vs "rows=89432" (actual) — wide gap = stale statistics
-- "actual time=0.038..15.1" — 15ms just to scan the table
-- "loops=1" — this node executed once (in a nested loop join: loops > 1)

-- EXPLAIN FORMAT=JSON — machine-readable, more detail:
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 42;
-- Contains: cost_info, used_columns, attached_condition, rows_examined_per_scan
-- Useful for programmatic analysis and tooling

-- EXPLAIN FORMAT=TREE — readable tree structure (MySQL 8.0+):
EXPLAIN FORMAT=TREE SELECT u.name, COUNT(o.id)
FROM users u JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
-- -> Aggregate: count(o.id)
--     -> Nested loop inner join  (cost=...)
--         -> Index scan on u using PRIMARY
--         -> Index lookup on o using orders_user_id (user_id=u.id)
```

```sql
-- What EXPLAIN reveals that timing cannot:

-- 1. Whether an index is being used at all:
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2024-03-15';
-- type: ALL, key: NULL → index on created_at is IGNORED due to function wrapping
-- Timing: "1.8 seconds" — you know it's slow, but not WHY

-- 2. Whether a join uses the right index:
EXPLAIN SELECT * FROM orders o JOIN users u ON u.id = o.user_id WHERE u.region = 'EU';
-- Shows: which table is the outer loop, which index drives the join
-- "rows=50000" on the inner join table → nested loop will execute 50K times

-- 3. Whether a sort requires a filesort (in memory or on disk):
EXPLAIN SELECT * FROM orders ORDER BY total DESC LIMIT 10;
-- Extra: "Using filesort" → no index to satisfy ORDER BY → explicit sort step
-- vs "Using index" → sort avoidance

-- 4. Estimated rows — the planner's accuracy:
-- estimated rows=5, actual rows=500,000 → optimizer chose wrong plan
-- Fix: ANALYZE TABLE orders; to refresh statistics
```

**Q2. What is the `type` column and why is it the single most important field in `EXPLAIN` output?**
A: The `type` column (also called the "join type" or "access type") describes *how* MySQL accesses rows in the table for this step of the query. It is an ordered quality indicator from worst to best — reading it tells you immediately whether a query has a fundamental performance problem:

```
Access type hierarchy — worst to best:

  ALL       ← Full table scan — reads every row, no index
  index     ← Full index scan — reads entire index, no heap filter
  range     ← Index range scan — reads a contiguous range of index entries
  ref       ← Index lookup by non-unique key — multiple rows may match
  eq_ref    ← Index lookup by unique key — at most one row per lookup
  const     ← Single row matched at parse time — treated as a constant
  system    ← Table has exactly one row — specialisation of const

  NULL      ← No table access needed (e.g. SELECT 1+1, or covered by index)

Qualitative meaning:
  ALL, index        → Problem: reads too much data; likely needs an index
  range             → Acceptable: bounded scan; can be optimised further
  ref, eq_ref       → Good: index lookup; check rows count
  const, system     → Optimal: single-row lookup; cannot be improved

The type column answers: "Is this query using indexes effectively?"
Everything else in EXPLAIN helps explain why or how much it matters.
```

```sql
-- Seeing all types in one EXPLAIN (multi-table join):
EXPLAIN
SELECT o.id, o.total, u.name, p.name AS product
FROM orders o                                    -- type: ALL (no index used here)
JOIN users u ON u.id = o.user_id                -- type: eq_ref (u.id is PK)
JOIN order_items oi ON oi.order_id = o.id       -- type: ref (non-unique FK index)
JOIN products p ON p.id = oi.product_id         -- type: eq_ref (p.id is PK)
WHERE o.created_at > '2024-01-01'               -- no index on created_at → ALL
LIMIT 100;

-- Fix the ALL: add index on (created_at) → type becomes range
-- Each row in EXPLAIN corresponds to one table in the join
-- Rows are shown in join execution order (outer loop first)
```

## Section 2: `ALL` — Full Table Scan

**Q3. When does MySQL choose `ALL`, what does it cost, and how do you diagnose the root cause?**
A: `type: ALL` means MySQL reads every row in the table. For small tables it is harmless; for large tables it is the most common cause of catastrophic query performance:

```sql
-- ALL appears when:
-- 1. No index exists for the WHERE condition
-- 2. An index exists but MySQL chooses not to use it (low selectivity, wrong type)
-- 3. Function wraps the indexed column (index cannot be used)
-- 4. The query has no WHERE clause

-- Case 1: No index — most common:
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
-- type: ALL, key: NULL, possible_keys: NULL
-- rows: 2,847,000 (full table)

-- Diagnosis: check what indexes exist:
SHOW INDEX FROM orders;
-- No index on status → add one:
CREATE INDEX idx_status ON orders (status);
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
-- type: ref, key: idx_status, rows: 284,000 (10% of table)
-- But: 10% selectivity might still be slow — consider composite index
```

```sql
-- Case 2: Index exists but MySQL ignores it (low selectivity):
-- status column has 3 values: PENDING(5%), COMPLETED(90%), CANCELLED(5%)

CREATE INDEX idx_status ON orders (status);
EXPLAIN SELECT * FROM orders WHERE status = 'COMPLETED';
-- type: ALL, key: NULL, possible_keys: idx_status
-- MySQL estimated: returning 90% of table via index → full scan is cheaper
-- possible_keys shows the index EXISTS but key shows it was REJECTED

-- Why MySQL chose ALL over the index:
-- Index scan: ~2.5M index entries → 2.5M random heap reads (for SELECT *)
-- Full scan: 2.5M sequential reads
-- Random I/O is expensive: sequential page read ≈ 4× faster than random
-- Returning 90% of rows: full scan wins

-- Fix: only query low-selectivity columns in combination with high-selectivity ones:
EXPLAIN SELECT * FROM orders WHERE status = 'COMPLETED' AND user_id = 42;
-- type: ref, key: idx_user_id (or composite index) — user_id is selective
-- status filtered afterward

-- Or force index use (testing only — usually wrong in production):
SELECT * FROM orders FORCE INDEX (idx_status) WHERE status = 'COMPLETED';
-- Usually worse than letting optimizer decide
```

```sql
-- Case 3: Function on indexed column — the invisible index killer:
-- Index exists on created_at:
CREATE INDEX idx_created ON orders (created_at);

-- BAD — function wraps indexed column:
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- type: ALL, key: NULL (index bypassed by YEAR() function)
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2024-03-15';
-- type: ALL, key: NULL (DATE() function prevents index use)
EXPLAIN SELECT * FROM orders WHERE created_at + INTERVAL 1 DAY > NOW();
-- type: ALL, key: NULL (arithmetic on indexed column)

-- GOOD — rewrite to preserve the indexed column:
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
-- type: range, key: idx_created ← index used

EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-03-15' AND created_at < '2024-03-16';
-- type: range, key: idx_created ← equivalent to DATE(created_at) = '2024-03-15'

-- Other function patterns that break index usage:
-- WHERE LOWER(email) = 'alice@example.com'        → use collation or generated column
-- WHERE SUBSTRING(phone, 1, 3) = '555'            → index on full phone column useless
-- WHERE ABS(score - 100) < 10                     → rewrite as score BETWEEN 90 AND 110
-- WHERE CAST(user_id AS CHAR) = '42'              → type mismatch (implicit cast)
```

```sql
-- Case 4: Implicit type conversion — a subtle ALL trigger:
-- Column: user_id INT (indexed)
-- Query:
EXPLAIN SELECT * FROM orders WHERE user_id = '42';
-- type: ref, key: idx_user_id ← MySQL converts '42' to INT implicitly: works

-- But with string column:
-- Column: session_token VARCHAR(64) (indexed)
EXPLAIN SELECT * FROM sessions WHERE session_token = 123;
-- type: ALL — MySQL must cast session_token to INT for each row
-- Cannot use index (index is on VARCHAR, comparison is on INT)
-- Fix: use string literal: WHERE session_token = '123abc...'

-- Measure actual rows examined vs returned (efficiency ratio):
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
-- rows=2847000, filtered=100.00 → examining 2.8M rows to return ~2.8M rows
-- ratio: 1:1 (bad — full scan)

-- Good ratio after index:
-- rows=142350, filtered=100.00 → examining only matching rows
-- For a filter, look for filtered close to 100% (planner knows how many match)
```

## Section 3: `index` — Full Index Scan

**Q4. What is `type: index` and how does it differ from `ALL` — is it always better?**
A: `type: index` means MySQL scans the entire index tree from left to right, rather than the heap table. It is better than `ALL` only when the index is much smaller than the table, or when the query can be satisfied entirely from the index (a covering index scan):

```sql
-- index appears in two scenarios:

-- Scenario 1: Query satisfied entirely from the index (covering index scan)
-- Table: orders (id, user_id, status, total, created_at, notes, ...)
CREATE INDEX idx_status ON orders (status);

EXPLAIN SELECT status FROM orders ORDER BY status;
-- type: index, key: idx_status, Extra: Using index
-- "Using index" in Extra = covering index scan (no heap access)
-- Reading the index in order satisfies both the ORDER BY and the SELECT status
-- The index is much smaller than the heap → faster than ALL even though full scan

-- Scenario 2: ORDER BY on an indexed column that MySQL reads in index order
EXPLAIN SELECT id, status FROM orders ORDER BY status;
-- type: index, key: idx_status, Extra: Using index
-- id is the primary key → included in secondary index (InnoDB clustered key)
-- Returns all rows, sorted by status, reading index pages in order

-- When index is NOT better than ALL:
-- Scenario: return all rows but sorted order doesn't matter
EXPLAIN SELECT * FROM orders;
-- type: ALL (if no ORDER BY using index)
-- EXPLAIN SELECT * FROM orders ORDER BY status;
-- type: index, key: idx_status, Extra: NULL (NOT "Using index")
-- Here: reading index page for key+PK, then fetching heap page for * columns
-- = random I/O for every row → may be slower than sequential table scan
```

```sql
-- Distinguishing good index scan from bad index scan:
-- The "Extra" column is the key differentiator:

-- GOOD: Extra = "Using index" (covering scan — no heap access):
EXPLAIN SELECT user_id, status FROM orders WHERE 1=1;
-- type: index, key: idx_user_id_status, Extra: Using index
-- All needed columns (user_id, status) are in the index
-- Fast: only reads index pages (much smaller than heap)

-- LESS GOOD: Extra = NULL or "Using where" (index scan + heap access):
EXPLAIN SELECT * FROM orders ORDER BY status;
-- type: index, key: idx_status, Extra: NULL (or "Using where" if filtered)
-- For each index entry: fetches full row from heap
-- If table is large: this can be slower than ALL (random vs sequential I/O)

-- The diagnosis: check if "Using index" appears in Extra:
-- "Using index" present → covering scan → index scan is efficient
-- "Using index" absent  → index scan + heap fetch → may be suboptimal
-- If not covering: consider adding INCLUDE columns to make it covering
-- MySQL 8.0: CREATE INDEX idx ON orders (status) INCLUDE (user_id, total);
-- Or: redesign query to only SELECT columns in the index
```

```sql
-- When MySQL chooses index over ALL for covering queries:
-- Table: users (id INT PK, email VARCHAR, name VARCHAR, created_at DATETIME)
-- Needs: COUNT(*) of all users

EXPLAIN SELECT COUNT(*) FROM users;
-- MySQL 8.0:
-- type: index, key: PRIMARY, Extra: Using index
-- InnoDB: secondary index is smaller than heap
-- If a secondary index exists: MySQL may prefer it over PRIMARY for COUNT(*)
-- because secondary index pages fit better in buffer pool

-- Compare sizes:
SHOW TABLE STATUS LIKE 'users'\G
-- Data_length: 524288000 (500MB heap)
-- Index_length: 41943040  (40MB index)
-- Reading 40MB index vs 500MB heap for COUNT(*): index wins

-- Force index to verify:
EXPLAIN SELECT COUNT(*) FROM users USE INDEX (idx_email);
-- type: index, key: idx_email, Extra: Using index
-- idx_email is a covering index for COUNT(*) (just needs to count rows)
```

## Section 4: `range` — Index Range Scan

**Q5. What operators produce `type: range`, and what is the performance profile of a range scan?**
A: `type: range` means MySQL uses an index to locate rows within a bounded contiguous range of key values. It is significantly better than ALL or index-full-scan because only a portion of the index and heap is read. The operators that produce it are: `BETWEEN`, `>`, `<`, `>=`, `<=`, `=` on a non-unique key when combined with range operators, `IN(...)` for non-unique values, and `LIKE 'prefix%'`:

```sql
-- Operators that produce range:

-- BETWEEN:
EXPLAIN SELECT * FROM orders WHERE total BETWEEN 100 AND 500;
-- type: range, key: idx_total

-- > / >= / < / <=:
EXPLAIN SELECT * FROM orders WHERE created_at >= '2024-01-01';
-- type: range, key: idx_created_at

-- IN on non-primary/non-unique key:
EXPLAIN SELECT * FROM orders WHERE status IN ('PENDING', 'PROCESSING');
-- type: range, key: idx_status
-- MySQL treats IN as a set of range intervals internally

-- LIKE with prefix (left-anchored):
EXPLAIN SELECT * FROM users WHERE name LIKE 'Ali%';
-- type: range, key: idx_name
-- Index sorted lexicographically → can scan 'Ali...' through 'Alj...'

-- LIKE with leading wildcard — NOT a range:
EXPLAIN SELECT * FROM users WHERE name LIKE '%Ali%';
-- type: ALL — leading wildcard cannot use B-tree index
-- Fix: use FULLTEXT index for substring search
```

```sql
-- Performance profile of range scans:

-- Key metrics to evaluate a range scan:
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01';
-- type: range
-- key: idx_created_at
-- rows: 125000      ← estimated rows in the range (important!)
-- key_len: 8        ← 8 bytes (DATETIME uses 8 bytes in index)
-- filtered: 100.00  ← all range rows pass the filter (no additional filter)

-- The "rows" estimate is critical for range scans:
-- rows=100: tiny range → fast
-- rows=500000: large range → potentially slow despite using index
-- At some threshold: full scan is cheaper (MySQL calculates this)

-- When range degrades to ALL:
CREATE INDEX idx_created ON orders (created_at);
EXPLAIN SELECT * FROM orders WHERE created_at > '2020-01-01';
-- If 95% of rows match: MySQL may choose ALL over range
-- type: ALL — selectivity too low for range scan to be beneficial

-- Verify with EXPLAIN ANALYZE to see actual vs estimated:
EXPLAIN ANALYZE SELECT * FROM orders WHERE created_at > '2024-03-01';
-- actual rows=12500, estimated rows=13200 → good estimate
-- vs: actual rows=12500, estimated rows=1200 → poor estimate → check statistics
```

```sql
-- Composite index and range — the critical column order rule:

-- Index: (user_id, status, created_at)
CREATE INDEX idx_composite ON orders (user_id, status, created_at);

-- Range on the LAST column — all prefix columns used with equality:
EXPLAIN SELECT * FROM orders
WHERE user_id = 42 AND status = 'PENDING' AND created_at > '2024-01-01';
-- type: range, key: idx_composite, key_len: full composite length
-- Optimal: equality on user_id and status, then range on created_at

-- Range on a MIDDLE column — columns after the range column are NOT usable:
EXPLAIN SELECT * FROM orders
WHERE user_id = 42 AND created_at > '2024-01-01' AND status = 'PENDING';
-- type: range, key: idx_composite, key_len: shorter (only user_id + created_at used)
-- status equality cannot be used because created_at range comes first in the index
-- The range "breaks" the composite key usage for subsequent columns
-- Fix: reorder index to put the range column last: (user_id, status, created_at)

-- key_len reveals how much of the composite index is used:
-- (user_id INT=4, status VARCHAR(20)=22, created_at DATETIME=8)
-- key_len=4:  only user_id used
-- key_len=26: user_id + status used
-- key_len=34: all three columns used
-- Short key_len on a composite index = columns after the range are wasted
```

```sql
-- range vs ref — why range is "worse" even with the same index:

-- ref: index lookup at a specific value (equality, non-unique):
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type: ref, key: idx_user_id
-- MySQL uses the index to jump directly to user_id=42 entries

-- range: index scan over an interval:
EXPLAIN SELECT * FROM orders WHERE user_id BETWEEN 40 AND 50;
-- type: range, key: idx_user_id
-- MySQL scans from user_id=40 to user_id=50 continuously

-- Why ref is considered better than range:
-- ref: point lookup → exact seek position in B-tree → minimal I/O
-- range: must scan from start of range to end → more index pages read
-- But: if ref matches many rows and range matches few, range can be faster
-- The "type" is a heuristic guide, not an absolute performance guarantee
-- Always check the "rows" column alongside type
```

## Section 5: `ref` — Non-Unique Index Lookup

**Q6. What conditions produce `type: ref`, and how does the `ref` column reveal what the index is compared to?**
A: `type: ref` is the result of an equality condition on a non-unique (or not fully-unique) index. MySQL uses the index to find the exact subtree of matching rows, then fetches each one. It is substantially better than range because there is no scanning — just a direct tree traversal to the matching key value:

```sql
-- ref appears when:
-- 1. Equality on a non-unique index column
-- 2. Equality on a prefix of a composite unique index (not the full key)
-- 3. JOIN on a non-unique foreign key index

-- Case 1: Equality on non-unique index:
CREATE INDEX idx_user_id ON orders (user_id);  -- user_id is not unique (one user, many orders)

EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type: ref
-- key: idx_user_id
-- ref: const          ← the constant value 42 was used as the lookup key
-- rows: 127           ← estimated rows matching user_id=42

-- The "ref" column (not the "type" column) shows WHAT was compared to the index:
-- ref: const           → compared to a constant value (literal in query)
-- ref: db.table.column → compared to a column from another table in the join
-- ref: func            → compared to the result of a function

-- Case 2: JOIN on foreign key — the most common ref scenario:
EXPLAIN
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 42;
-- Row for users:  type: const (u.id=42 is unique → const, not ref)
-- Row for orders: type: ref, ref: db.users.id
--                 ← ref column shows: index compared to users.id column
```

```sql
-- Multi-column index and ref:
CREATE INDEX idx_user_status ON orders (user_id, status);

-- Equality on full composite (non-unique combination):
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND status = 'PENDING';
-- type: ref
-- key: idx_user_status
-- key_len: length of both columns (user_id INT + status VARCHAR)
-- ref: const,const   ← both columns compared to constants

-- Equality on prefix only (user_id but not status):
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type: ref
-- key: idx_user_status (index starts with user_id → usable as prefix)
-- key_len: 4 (only user_id portion of the composite key)
-- ref: const

-- Equality on middle column only — index NOT used:
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
-- type: ALL (or index if covering)
-- Cannot use idx_user_status — must start from the leftmost column
-- Fix: separate index on status, or reorder composite index
```

```sql
-- ref in JOIN queries — reading the ref column to understand join execution:
EXPLAIN
SELECT u.name, o.id, p.name AS product
FROM users u
JOIN orders o ON o.user_id = u.id        -- o.user_id has non-unique index
JOIN order_items oi ON oi.order_id = o.id -- oi.order_id has non-unique index
JOIN products p ON p.id = oi.product_id   -- p.id is PRIMARY KEY (unique)
WHERE u.region = 'EU';

-- Expected plan (reading EXPLAIN output row by row):
-- id | table | type   | key           | ref               | rows
--  1 | u     | ref    | idx_region    | const             | 15000  ← EU users
--  1 | o     | ref    | idx_user_id   | mydb.u.id         | 12     ← per-user orders
--  1 | oi    | ref    | idx_order_id  | mydb.o.id         | 3      ← per-order items
--  1 | p     | eq_ref | PRIMARY       | mydb.oi.product_id| 1      ← unique product

-- Reading the ref column:
-- u: ref=const → u.region compared to the string constant 'EU'
-- o: ref=mydb.u.id → o.user_id compared to u.id (from outer table)
-- oi: ref=mydb.o.id → oi.order_id compared to o.id (from outer table)
-- p: ref=mydb.oi.product_id → p.id compared to oi.product_id (unique → eq_ref)

-- rows in context of JOIN (multiply down the tree):
-- 15000 users × 12 orders × 3 items × 1 product = 540,000 total row lookups
-- Each non-1 "rows" estimate in a ref is a concern — check if indexes are selective enough
```

```sql
-- Diagnosing ref with high row counts:
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type: ref, rows: 458000
-- One user has 458K orders? Possible for a high-volume account.
-- OR: statistics are wrong (stale) and optimizer overestimates
-- ANALYZE TABLE orders; ← refresh statistics

-- Check actual vs estimated:
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
-- actual rows=1250, estimated rows=458000 → severe overestimate
-- Fix: ANALYZE TABLE; or increase innodb_stats_persistent_sample_pages

-- Selectivity check:
SELECT COUNT(*) FROM orders WHERE user_id = 42;           -- 1250
SELECT COUNT(*) FROM orders;                              -- 2847000
SELECT 1250/2847000.0;                                    -- 0.044% (good selectivity)
-- index is being used correctly; the rows estimate was just stale
```

## Section 6: `eq_ref` — Unique Index Lookup

**Q7. What produces `type: eq_ref`, why is it the best possible access type for a JOIN, and what distinguishes it from `const`?**
A: `type: eq_ref` is the best access type possible for a join — it means MySQL finds exactly one matching row per outer row by using a PRIMARY KEY or UNIQUE index lookup. Each lookup is guaranteed to return at most one row, making it optimal:

```sql
-- eq_ref appears when:
-- 1. JOIN uses the PRIMARY KEY or a UNIQUE index for the inner table lookup
-- 2. ALL columns of the unique index are covered by the equality condition
-- 3. The lookup value comes from the outer table (not a constant)

-- The canonical eq_ref pattern — joining to a dimension table:
EXPLAIN
SELECT o.id, u.name, u.email
FROM orders o
JOIN users u ON u.id = o.user_id;  -- u.id is PRIMARY KEY

-- type: eq_ref for users table
-- key: PRIMARY
-- ref: mydb.o.user_id  ← each orders row looks up EXACTLY ONE user by PK
-- rows: 1              ← always 1 for eq_ref

-- Why rows=1 makes eq_ref so efficient:
-- Nested loop join with eq_ref inner:
-- For each order (outer): one B-tree lookup into users → exactly 1 row
-- No scanning, no range traversal — pure point lookup
-- Cost: O(outer_rows × log(inner_table_size))
-- For ref (non-unique): O(outer_rows × matching_rows × log(inner_size))
```

```sql
-- eq_ref requires the FULL unique/primary key:

-- Table: order_items with composite PRIMARY KEY (order_id, product_id):
CREATE TABLE order_items (
    order_id   INT NOT NULL,
    product_id INT NOT NULL,
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

-- JOIN using FULL composite PK → eq_ref:
EXPLAIN
SELECT oi.quantity, p.name
FROM orders o
JOIN order_items oi ON oi.order_id = o.id AND oi.product_id = o.main_product_id
JOIN products p ON p.id = oi.product_id;
-- oi: type=eq_ref (both order_id AND product_id provided → full PK)
-- p:  type=eq_ref (p.id is PK → single row)

-- JOIN using only PARTIAL composite PK → ref (not eq_ref):
EXPLAIN
SELECT oi.quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.id;  -- Only order_id provided
-- oi: type=ref (only first part of PK → multiple product rows per order)
-- rows: 3 (average items per order, not 1)
-- Not eq_ref because the full unique key is not satisfied
```

```sql
-- eq_ref vs const — the critical distinction:

-- const: the unique lookup value is a CONSTANT (known at parse time)
-- eq_ref: the unique lookup value comes from ANOTHER TABLE (the outer join row)

-- const scenario — outer query constant value:
EXPLAIN SELECT * FROM users WHERE id = 42;
-- type: const (id=42 is known before execution starts)
-- MySQL substitutes this row as a "constant" in the plan
-- Any reference to users.column in the rest of the query uses the known value

-- eq_ref scenario — join column from outer table:
EXPLAIN
SELECT u.name FROM orders o JOIN users u ON u.id = o.user_id;
-- users: type=eq_ref (u.id=o.user_id — value from orders, not known at parse time)
-- For each order row, a new unique lookup into users is needed

-- The const optimization — MySQL substitutes the constant row:
EXPLAIN
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 42;
-- users: type=const (u.id=42 → found single row at planning time)
-- orders: type=ref (o.user_id=42 → non-unique lookup for this user's orders)
-- MySQL knows u.name at plan time → no join needed for users at execution
-- This is why const is "better" than eq_ref: zero execution cost
```

```sql
-- When eq_ref disappears and becomes ref — a common regression:

-- Before: unique index on (order_id, product_id):
-- JOIN oi ON oi.order_id = o.id AND oi.product_id = 5 → eq_ref

-- After someone adds a nullable column to the PK relationship:
-- If the join condition involves a nullable column, MySQL uses ref instead of eq_ref
-- Nullable unique index: MySQL allows multiple NULL values (NULLs are not equal)
-- So: WHERE nullable_unique_col = value → ref (NULLs need special handling)

-- Fix: declare JOIN columns as NOT NULL where semantically appropriate
-- Or: use partial index with WHERE col IS NOT NULL

-- eq_ref in a self-join:
EXPLAIN
SELECT e.name, m.name AS manager_name
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;  -- m.id is PK
-- m: type=eq_ref (even in a self-join on PK)
-- rows: 1 (always — each employee has at most one manager)
```

## Section 7: `const` and `system` — Optimal Access

**Q8. What is `type: const` and what does MySQL do differently with a const table than any other access type?**
A: `type: const` is the optimal access type for a single-row lookup. It occurs when MySQL can prove at parse time that exactly one row will match — via a PRIMARY KEY or UNIQUE index lookup against a constant value. MySQL executes the lookup before the main execution phase and substitutes the result as a compile-time constant throughout the rest of the plan:

```sql
-- const appears when:
-- 1. WHERE primary_key = constant_value
-- 2. WHERE unique_key = constant_value (for a non-nullable unique column)
-- 3. All columns of a composite PK/UNIQUE are matched to constants

-- Scenario 1: Primary key equality:
EXPLAIN SELECT * FROM users WHERE id = 42;
-- type: const
-- key: PRIMARY
-- ref: const
-- rows: 1

-- Scenario 2: Unique key equality:
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
-- Requires: UNIQUE INDEX on email (or PRIMARY KEY)
-- type: const
-- key: idx_email_unique
-- rows: 1

-- Scenario 3: Composite PK with all columns:
EXPLAIN SELECT * FROM order_items WHERE order_id = 100 AND product_id = 5;
-- PRIMARY KEY (order_id, product_id)
-- type: const (BOTH columns of composite PK provided)

-- Scenario 4: Composite PK with only one column:
EXPLAIN SELECT * FROM order_items WHERE order_id = 100;
-- type: ref (only FIRST column of composite PK → not unique → multiple rows possible)
```

```sql
-- What MySQL does with a const table — the "constant substitution" optimization:

-- Query with const table:
EXPLAIN
SELECT u.name, COUNT(o.id) AS order_count, SUM(o.total) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 42
GROUP BY u.id;

-- EXPLAIN output:
-- id | table | type  | key     | rows | Extra
--  1 | u     | const | PRIMARY | 1    | ← const: fetched at planning time
--  1 | o     | ref   | idx_uid | 312  | ← only orders table scanned at runtime

-- What happens:
-- At optimization time: SELECT * FROM users WHERE id=42 → fetches row immediately
-- u.name, u.email, etc. are NOW KNOWN CONSTANTS
-- Execution plan for orders: already knows user_id=42 → simple index scan
-- GROUP BY u.id: removed (constant value, grouping is trivial)

-- The GROUP BY removal is a key benefit:
-- Without const: GROUP BY u.id would require sorting or hashing
-- With const: u.id is a constant → GROUP BY eliminated → faster

-- COUNT(*) on const: MySQL knows there's exactly 1 group → no grouping needed
-- Very efficient: single pass through orders table with ref access
```

```sql
-- const vs ref with PRIMARY KEY — why UNIQUE matters:

-- Unique nullable column:
CREATE TABLE sessions (
    token VARCHAR(64) NOT NULL,
    user_id INT,
    UNIQUE KEY (token)
);

EXPLAIN SELECT * FROM sessions WHERE token = 'abc123';
-- type: const (token is UNIQUE and NOT NULL → guaranteed 1 row)

-- Non-unique index:
CREATE INDEX idx_user_id ON sessions (user_id);
EXPLAIN SELECT * FROM sessions WHERE user_id = 42;
-- type: ref (user_id not unique → multiple sessions per user)

-- Effect of NULLable on unique index:
CREATE TABLE preferences (
    user_id INT,
    category VARCHAR(50),
    UNIQUE KEY (user_id, category)
);
EXPLAIN SELECT * FROM preferences WHERE user_id = 42 AND category = 'theme';
-- type: const (full unique key, both NOT NULL)
-- If category were NULL:
-- EXPLAIN SELECT * FROM preferences WHERE user_id = 42 AND category IS NULL;
-- type: ref (NULL is never equal to NULL → not truly unique from MySQL's perspective)
```

```sql
-- system — the specialisation of const for single-row tables:
-- system: table has exactly ONE physical row (or is empty)
-- Extremely rare in real applications
-- More common with system tables or temporary tables with 1 row

CREATE TABLE config (
    key_name VARCHAR(50) PRIMARY KEY,
    value    TEXT
);
INSERT INTO config VALUES ('app_version', '2.0.0');

EXPLAIN SELECT * FROM config WHERE key_name = 'app_version';
-- type: const (table has data, single PK lookup)
-- If table had exactly 1 row total:
-- type: system (MySQL detects single-row table → hardcodes the value)

-- In practice: system appears in EXPLAIN subqueries and derived tables:
EXPLAIN SELECT * FROM (SELECT MAX(id) AS max_id FROM orders) AS derived;
-- derived: type=system (aggregate returns exactly 1 row)

-- The system/const distinction is academic in practice:
-- Both represent "MySQL knows the value before execution starts"
-- Neither requires repeated disk access during the main query execution
```

## Section 8: `key_len` and `ref` in Depth

**Q9. How do you use `key_len` to diagnose which parts of a composite index are actually being used?**
A: `key_len` reports the number of bytes MySQL used from the index key. For composite indexes, this reveals exactly how many columns are being used — a shorter-than-expected `key_len` is diagnostic evidence that the composite index is only partially utilised:

```sql
-- Understanding key_len values for common data types:

-- Fixed-length types:
-- TINYINT:   1 byte     + 1 if nullable
-- SMALLINT:  2 bytes    + 1 if nullable
-- INT:       4 bytes    + 1 if nullable
-- BIGINT:    8 bytes    + 1 if nullable
-- FLOAT:     4 bytes    + 1 if nullable
-- DOUBLE:    8 bytes    + 1 if nullable
-- DATE:      3 bytes    + 1 if nullable
-- DATETIME:  8 bytes    + 1 if nullable (MySQL 5.6+)
-- TIMESTAMP: 4 bytes    + 1 if nullable

-- Variable-length types (with utf8mb4 charset):
-- CHAR(N):   N × 4 bytes           + 1 if nullable
-- VARCHAR(N): N × 4 bytes + 2      + 1 if nullable (2 bytes for length prefix)
-- Example: VARCHAR(50) utf8mb4 = 50 × 4 + 2 = 202 bytes (NOT NULL)
--                                           = 203 bytes (NULL)

-- Composite index key_len calculation:
CREATE TABLE orders (
    id         INT NOT NULL AUTO_INCREMENT,
    user_id    INT NOT NULL,          -- 4 bytes (NOT NULL)
    status     VARCHAR(20) NOT NULL,  -- 20 × 4 + 2 = 82 bytes (NOT NULL, utf8mb4)
    created_at DATETIME NOT NULL,     -- 8 bytes (NOT NULL)
    PRIMARY KEY (id),
    INDEX idx_composite (user_id, status, created_at)
);
-- Index total: 4 + 82 + 8 = 94 bytes

-- Query using only user_id:
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- key_len: 4   ← only user_id (4 bytes) used

-- Query using user_id + status:
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND status = 'PENDING';
-- key_len: 86  ← user_id (4) + status (82) = 86

-- Query using all three:
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND status = 'PENDING'
  AND created_at > '2024-01-01';
-- key_len: 94  ← all three columns (4 + 82 + 8 = 94)
-- type: range (range on created_at — the last column)
```

```sql
-- Using key_len to diagnose partial index use:

-- Index: (user_id INT, status VARCHAR(20), amount DECIMAL(10,2))
-- Expected: WHERE user_id=42 AND status='PENDING' AND amount > 100 uses all 3 columns
EXPLAIN SELECT * FROM orders
WHERE user_id = 42 AND status = 'PENDING' AND amount > 100;

-- If key_len = 86 (user_id + status only, not amount):
-- Something prevented amount from being used in the index
-- Possible cause: amount column in index is nullable
-- Check: SHOW CREATE TABLE orders → if amount allows NULL: +1 byte,
--         and range on nullable third column may not be used

-- If key_len = 4 (only user_id):
-- The query didn't match the index prefix correctly
-- Maybe status comparison uses a different character set
-- Or: status has an implicit type conversion

-- Practical audit: for each composite index, know the expected key_len
-- When actual key_len < expected: investigate why

-- NULL bytes add 1 to key_len:
CREATE INDEX idx_nullable ON orders (user_id, deleted_at);
-- user_id INT NOT NULL:  4 bytes
-- deleted_at DATETIME:   8 bytes + 1 NULL byte = 9 bytes
-- Total expected: 4 + 9 = 13 bytes

EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND deleted_at IS NULL;
-- key_len: 13 ← both columns used (NULL byte included in deleted_at)
-- type: ref

EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND deleted_at = '2024-01-01';
-- key_len: 13 ← same
-- type: ref
```

## Section 9: The `Extra` Column

**Q10. What are the most important `Extra` values and what do they reveal about query performance?**
A: The `Extra` column provides additional context that the `type` column alone cannot express. Several `Extra` values indicate serious performance problems; others indicate optimizations being applied:

```sql
-- Critical Extra values to watch for:

-- "Using filesort" — explicit sort step required:
EXPLAIN SELECT * FROM orders ORDER BY total DESC;
-- Extra: Using filesort (no index to satisfy ORDER BY)
-- MySQL must collect all matching rows, then sort them
-- Sort happens in memory (sort_buffer_size) or spills to disk
-- Fix: CREATE INDEX ON orders (total) or add total to existing composite index

-- "Using temporary" — temporary table created:
EXPLAIN SELECT status, COUNT(*) FROM orders GROUP BY status;
-- With no index on status: Extra: Using temporary; Using filesort
-- MySQL builds a temp table to hold intermediate GROUP BY results
-- Then sorts temp table to produce ordered output
-- Fix: CREATE INDEX ON orders (status) → may eliminate temp table

-- "Using filesort" + "Using temporary" together — worst combination:
-- GROUP BY a non-indexed column with ORDER BY a different column
-- Fix: index on GROUP BY column; separate index or composite for ORDER BY

-- "Using index" — covering index (no heap access):
EXPLAIN SELECT user_id, status FROM orders WHERE user_id = 42;
-- Extra: Using index (if both user_id and status are in the index)
-- Best possible: data returned directly from index pages
-- No heap access → dramatically fewer I/O operations

-- "Using index condition" — Index Condition Pushdown (ICP):
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND status LIKE 'P%';
-- Extra: Using index condition
-- MySQL pushes the status LIKE 'P%' condition into the index scan
-- Filters rows at the index level before fetching from heap
-- Better than fetching all user_id=42 rows then filtering status
-- Available for range, ref, ref_or_null, eq_ref access types
```

```sql
-- More Extra values:

-- "Using where" — filter applied after reading row:
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND notes LIKE '%urgent%';
-- Extra: Using where
-- user_id=42: handled by index (key: idx_user_id)
-- notes LIKE '%urgent%': applied as a post-fetch filter (no index for notes)
-- Rows fetched by index, then filtered by the WHERE clause

-- "Using where; Using index" — covering index with additional filter:
EXPLAIN SELECT user_id, status FROM orders WHERE user_id = 42 AND status = 'PENDING';
-- Extra: Using where; Using index
-- Both columns in index (covering), but extra filter applied within index scan
-- Still efficient: no heap access, filter in index

-- "Using join buffer (Block Nested Loop)" — no index for join:
EXPLAIN
SELECT * FROM orders o JOIN users u ON u.region = o.ship_region;
-- Extra for users: Using join buffer (Block Nested Loop)
-- No index on u.region or o.ship_region → MySQL buffers rows in join_buffer_size
-- Worst join type — fix by adding an index on the join column

-- "Impossible WHERE" — optimizer determined no rows can match:
EXPLAIN SELECT * FROM orders WHERE 1=0;
-- Extra: Impossible WHERE
-- MySQL skips execution entirely — returns empty set immediately
-- Also appears for provably impossible conditions:
-- WHERE id = 5 AND id = 6 (can't be both 5 and 6)

-- "Select tables optimized away" — aggregate on indexed column, no scan needed:
EXPLAIN SELECT MAX(id) FROM orders;
-- Extra: Select tables optimized away
-- InnoDB: MAX(id) on the PRIMARY KEY → read the rightmost B-tree leaf
-- One I/O operation regardless of table size → O(log N) not O(N)

-- "Not exists" — LEFT JOIN optimization:
EXPLAIN
SELECT u.id FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;  -- Users with no orders
-- Extra: Not exists
-- MySQL short-circuits: as soon as one matching order is found, the row is excluded
-- Equivalent to anti-join optimisation
```

## Section 10: Advanced Scenarios

**Q11. How do you read a multi-table EXPLAIN — interpreting join order and the interaction between access types?**
A: In a multi-table query, EXPLAIN shows one row per table in the order MySQL will join them. Reading the output correctly requires understanding that each row's `rows` estimate compounds with the previous rows' estimates:

```sql
-- Multi-table EXPLAIN walkthrough:
EXPLAIN
SELECT
    u.name,
    COUNT(o.id) AS order_count,
    SUM(oi.unit_price * oi.quantity) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN order_items oi ON oi.order_id = o.id
WHERE u.region = 'EU'
  AND o.status = 'COMPLETED'
  AND o.created_at >= '2024-01-01'
GROUP BY u.id, u.name;
```

```
EXPLAIN output:
id | select_type | table | type  | key                     | ref              | rows   | filtered | Extra
 1 | SIMPLE      | u     | ref   | idx_region              | const            | 15000  | 100.00   |
 1 | SIMPLE      | o     | ref   | idx_user_created_status | mydb.u.id        | 8      | 25.00    | Using index condition
 1 | SIMPLE      | oi    | ref   | idx_order_id            | mydb.o.id        | 4      | 100.00   |

Reading this plan:

Step 1: users table (outer loop)
  type=ref: index on region, equality lookup
  rows=15000: estimated 15K EU users
  filtered=100.00: all 15K pass (region='EU' is the only filter on users)
  → 15,000 users will drive the join

Step 2: orders table (middle loop, driven by users)
  type=ref: index on (user_id, created_at, status) — leading column user_id matches
  ref=mydb.u.id: each orders lookup uses u.id from the outer loop
  rows=8: estimated 8 orders per user
  filtered=25.00: only 25% of those 8 pass the status/date filters (= 2 per user)
  Extra: Using index condition (ICP: status and created_at filtered at index level)
  → 15,000 × 8 × 0.25 = 30,000 order rows examined, ~30,000 pass to next step

Step 3: order_items (inner loop, driven by orders)
  type=ref: index on order_id
  ref=mydb.o.id: each items lookup uses o.id from orders row
  rows=4: estimated 4 items per order
  filtered=100.00: all items pass
  → 30,000 orders × 4 items = 120,000 total row lookups in order_items

Total work estimate: 15,000 + 30,000 + 120,000 = 165,000 row lookups
Compare to worst case (ALL + ALL + ALL): 500K × 2M × 10M = catastrophic
```

```sql
-- Diagnosing bad join order in the plan:
-- MySQL joins tables in the order shown in EXPLAIN
-- If a large table appears first (ALL with many rows), that's the outer loop
-- Each inner table is accessed once per outer row → large outer = expensive

-- Bad: large table first, small table second
-- id | table  | type | rows
--  1 | orders | ALL  | 2847000  ← outer loop: 2.8M iterations
--  1 | users  | ref  | 1        ← inner: ref for each of 2.8M orders

-- Better: small table first, large table as inner
-- id | table  | type  | rows
--  1 | users  | const | 1        ← const: one user
--  1 | orders | ref   | 312      ← inner: 312 orders for that user

-- Force join order (use carefully — only if optimizer is wrong):
SELECT STRAIGHT_JOIN u.name, o.total
FROM users u STRAIGHT_JOIN orders o ON o.user_id = u.id
WHERE u.id = 42;
-- STRAIGHT_JOIN forces left-to-right join order as written
-- verify with EXPLAIN before using in production
```

**Q12. How do you fix the most common EXPLAIN red flags — a practical guide from `ALL` to optimised?**
A: Most slow queries fall into a handful of recognisable EXPLAIN patterns. Each pattern has a standard diagnosis and fix:

```sql
-- RED FLAG 1: type=ALL with high rows and no key
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING' AND user_id = 42;
-- type: ALL, key: NULL, rows: 2847000

-- Diagnosis: no index covers (user_id, status) combination
-- Fix: add composite index with high-selectivity column first:
CREATE INDEX idx_user_status ON orders (user_id, status);
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING' AND user_id = 42;
-- type: ref, key: idx_user_status, rows: 12
```

```sql
-- RED FLAG 2: type=ALL despite index existing (function on column)
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- type: ALL, key: NULL, possible_keys: idx_created_at
-- (index exists but function prevents use)

-- Fix: rewrite without function on the indexed column:
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
-- type: range, key: idx_created_at, rows: 125000
```

```sql
-- RED FLAG 3: Extra="Using filesort" on a high-rows query
EXPLAIN SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
-- type: ref, key: idx_user_id, rows: 312, Extra: Using filesort
-- Index on user_id found the rows, but filesort needed for ORDER BY

-- Fix: composite index covering both filter and sort:
CREATE INDEX idx_user_created ON orders (user_id, created_at DESC);
EXPLAIN SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
-- type: ref, key: idx_user_created, rows: 10, Extra: Using index condition
-- Rows drops from 312 to 10 — LIMIT exploits index order
```

```sql
-- RED FLAG 4: Extra="Using temporary; Using filesort" in GROUP BY
EXPLAIN SELECT user_id, COUNT(*) FROM orders
WHERE status = 'COMPLETED' GROUP BY user_id ORDER BY COUNT(*) DESC;
-- type: ALL, Extra: Using temporary; Using filesort

-- Fix step 1: index on status (for the filter):
CREATE INDEX idx_status ON orders (status);
-- Fix step 2: index on (status, user_id) for GROUP BY efficiency:
CREATE INDEX idx_status_user ON orders (status, user_id);
EXPLAIN SELECT user_id, COUNT(*) FROM orders
WHERE status = 'COMPLETED' GROUP BY user_id ORDER BY COUNT(*) DESC;
-- type: range/ref, rows much lower
-- "Using temporary" may remain for ORDER BY COUNT(*) (no index for runtime counts)
-- Focus: eliminate the ALL first, then tune further
```

```sql
-- RED FLAG 5: ref with rows=50000+ in a JOIN inner table
EXPLAIN
SELECT u.name, COUNT(e.id)
FROM users u JOIN events e ON e.user_id = u.id
GROUP BY u.id;
-- events: type=ref, rows=58000 ← 58K events per user lookup

-- Diagnosis: either one user legitimately has 58K events,
-- or statistics are stale, or the index is not selective enough

-- Check actual:
EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = (SELECT id FROM users LIMIT 1);
-- actual rows=150, estimated rows=58000 → statistics stale
-- Fix: ANALYZE TABLE events;
-- Or: if real user has 58K events → this is expected, consider:
--     covering index to avoid heap fetch
--     summary table for frequent aggregations

-- RED FLAG 6: key_len much shorter than composite index total
-- Index: (user_id INT, status VARCHAR(20), amount DECIMAL) expected key_len=90
EXPLAIN SELECT * FROM orders WHERE user_id = 42 AND amount > 100;
-- key: idx_user_status_amount, key_len: 4 (only user_id!)
-- status is skipped → the column between user_id and amount in the index

-- Fix: reorder the query to use the index prefix correctly:
-- If common queries are: user_id + amount (skipping status):
-- Create a separate index: (user_id, amount)
-- Or rewrite: WHERE user_id=42 AND status IS NOT NULL AND amount > 100
-- (forces status usage if it's NOT NULL for all rows)
```

## Quick Reference Table

| type | Condition | rows typical | Index used | Performance |
|---|---|---|---|---|
| `ALL` | No index, or index rejected by optimizer | Full table | No | Worst — scan every row |
| `index` | Full index scan (covering or for ORDER BY) | Full index | Yes (index pages) | Bad unless covering (`Using index` in Extra) |
| `range` | `BETWEEN`, `>`, `<`, `IN`, `LIKE 'x%'` | Fraction of table | Yes | Acceptable — bounded scan |
| `ref` | Equality on non-unique index | Multiple rows | Yes | Good — direct index subtree lookup |
| `eq_ref` | Equality on PRIMARY KEY or UNIQUE (join inner table) | Always 1 | Yes (PK/UNIQUE) | Excellent — single row per lookup |
| `const` | Equality on PK/UNIQUE against a constant | Always 1 | Yes (PK/UNIQUE) | Optimal — row fetched at parse time |
| `system` | Table has exactly 1 row | Always 1 | N/A | Optimal — specialisation of const |

| `Extra` value | Meaning | Action required |
|---|---|---|
| `Using filesort` | No index to satisfy ORDER BY — explicit sort | Add index covering the ORDER BY columns |
| `Using temporary` | Temp table for GROUP BY or DISTINCT | Add index on GROUP BY column |
| `Using index` | Covering index — no heap access | Excellent — no action needed |
| `Using index condition` | Index Condition Pushdown — filter at index level | Good — ICP is working |
| `Using where` | Post-fetch filter (some work after index) | Check if filter column can be added to index |
| `Using join buffer (BNL)` | No index for join condition | Add index on join column |
| `Impossible WHERE` | Optimizer proved no rows can match | Check query logic; returns 0 rows |
| `Select tables optimized away` | Aggregate resolved from index alone | Optimal — no action needed |
| `Not exists` | Anti-join optimisation for `LEFT JOIN ... IS NULL` | Good — optimisation applied |

| `key_len` pattern | Diagnosis | Fix |
|---|---|---|
| 0 (key is NULL) | No index used at all | Check type=ALL — add or fix index |
| Shorter than expected composite | Only prefix of composite index used | Rewrite query, reorder composite columns, or add range column last |
| Includes NULL byte (+1) | Index column is nullable | Declare NOT NULL if semantically correct |
| Full length of composite | Entire composite index used | Optimal for this index |

---

**Tip for interviews:** Five things separate strong candidates on MySQL `EXPLAIN` output: (1) knowing **the ordered quality hierarchy** — that `ALL` and `index` represent problems (reading the whole table or whole index), `range` is acceptable, `ref` and `eq_ref` are good, and `const`/`system` are optimal — and being able to immediately name `ALL` with `key=NULL` as the critical red flag requiring a missing index; (2) explaining **the exact distinction between `eq_ref` and `ref`** — that `eq_ref` requires the full PRIMARY KEY or full UNIQUE index matched with equality and the lookup value comes from the outer table (guaranteeing rows=1), while `ref` is a non-unique index or partial unique index match (multiple rows possible), and that `const` is `eq_ref` where the value is a constant known at parse time rather than a runtime column from another table; (3) using **`key_len` to diagnose partial composite index usage** — that each data type contributes a known number of bytes to `key_len`, that a shorter-than-full-composite `key_len` means columns after the first range predicate are being wasted, and that reordering the composite index to put equality columns before range columns recovers the full index length; (4) reading **the `Extra` column as the second tier of diagnosis** — that `Using filesort` means the ORDER BY cannot be satisfied by the index and requires a sort step (fix: create or extend an index to cover the ORDER BY), that `Using temporary` combined with `Using filesort` is the worst combination (GROUP BY + ORDER BY with no index), and that `Using index` is the positive signal of a covering index where no heap access is needed; and (5) being able to **calculate estimated total work from a multi-table EXPLAIN** — multiplying the `rows` values down the join tree (accounting for `filtered` percentage) to understand the total row lookups, recognising that a large `rows` value on the inner table of a nested loop join is multiplicatively expensive, and knowing that the outer table should almost always be the smallest/most-filtered table in the plan.
