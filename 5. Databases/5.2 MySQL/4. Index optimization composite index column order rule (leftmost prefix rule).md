# Index Optimisation: Composite Index Column Order — The Leftmost Prefix Rule
## Interview Q&A (5 YOE Level)

---

## Section 1: Why Column Order Matters Physically

**Q1. How does a B-tree composite index physically store its keys — why does column order determine usability?**

A: A composite index is a single B-tree sorted lexicographically by all key columns in declaration order. Understanding the physical sort order is the only way to reason correctly about which queries can use an index and which cannot:

```
Composite index on (status, created_at, user_id):

  B-tree leaf pages (sorted lexicographically — status first, then created_at, then user_id):

  ┌────────────────────────────────────────────────────────────────────────┐
  │ Leaf page 1                                                            │
  │  ('cancelled', 2024-01-01, 201) → ctid (4,1)                         │
  │  ('cancelled', 2024-01-02, 107) → ctid (4,2)                         │
  │  ('cancelled', 2024-01-03, 301) → ctid (4,3)                         │
  │  ('cancelled', 2024-01-15, 89)  → ctid (7,1)                         │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Leaf page 2                                                            │
  │  ('pending',   2024-01-01, 42)  → ctid (0,1)                         │
  │  ('pending',   2024-01-01, 199) → ctid (0,2)                         │
  │  ('pending',   2024-01-02, 42)  → ctid (1,3)   ← same user, next day │
  │  ('pending',   2024-01-14, 88)  → ctid (3,2)                         │
  ├────────────────────────────────────────────────────────────────────────┤
  │ Leaf page 3                                                            │
  │  ('shipped',   2024-01-01, 55)  → ctid (2,1)                         │
  │  ('shipped',   2024-01-08, 199) → ctid (5,1)                         │
  │  ('shipped',   2024-01-22, 42)  → ctid (9,3)                         │
  └────────────────────────────────────────────────────────────────────────┘

The critical insight: the B-tree is sorted by status FIRST.
  • All 'cancelled' entries come before all 'pending' entries.
  • Within 'pending', entries are sorted by created_at.
  • Within (pending, 2024-01-01), entries are sorted by user_id.

What the planner CAN do (contiguous ranges exist in the index):
  WHERE status = 'pending'                   → contiguous block ✓
  WHERE status = 'pending' AND created_at = '2024-01-01' → contiguous sub-block ✓
  WHERE status = 'pending' AND created_at > '2024-01-01' → contiguous range ✓

What the planner CANNOT do efficiently (no contiguous range):
  WHERE created_at = '2024-01-01'           → scattered: Jan 1 entries exist
                                              under cancelled, pending, shipped, ...
                                              Not contiguous → index is useless here.
  WHERE user_id = 42                        → scattered across every status and date.
```

```sql
-- ── Proving the physical sort with a real table ───────────────────────────────
CREATE TABLE orders (
    id         BIGSERIAL PRIMARY KEY,
    status     TEXT NOT NULL,
    created_at DATE NOT NULL,
    user_id    BIGINT NOT NULL,
    total      NUMERIC(10,2)
);

CREATE INDEX idx_orders_s_c_u ON orders(status, created_at, user_id);

-- The index physically stores entries in this order:
-- (cancelled, 2024-01-01, 89), (cancelled, 2024-01-01, 201), ...
-- (pending,   2024-01-01, 42), (pending,   2024-01-01, 199), ...
-- (shipped,   2024-01-01, 55), ...

-- When the planner uses the index for WHERE status = 'pending':
-- It jumps to the first ('pending', ...) entry in the B-tree (O(log n))
-- and scans forward until it hits the first ('shipped', ...) entry.
-- This is a contiguous range scan — extremely efficient.

-- When the planner tries WHERE created_at = '2024-01-01':
-- Entries for 2024-01-01 are NOT contiguous — they appear at:
--   ('cancelled', 2024-01-01, ...)
--   ('pending',   2024-01-01, ...)
--   ('shipped',   2024-01-01, ...)
-- The planner would have to scan the entire index, checking each entry.
-- A seq scan on the table is cheaper — that's what the planner chooses.

-- ── The formal rule stated precisely ──────────────────────────────────────────
-- For an index on (col_A, col_B, col_C):
-- The index is useful only when the WHERE clause includes col_A,
-- or includes (col_A AND col_B), or includes (col_A AND col_B AND col_C).
-- Any other combination (col_B alone, col_C alone, col_B AND col_C) cannot
-- traverse the B-tree efficiently — a seq scan is chosen instead.
-- This is the leftmost prefix rule.
```

**Q2. Walk through every valid and invalid query pattern for a three-column index — what the planner does in each case.**

A: The leftmost prefix rule has exact, testable consequences for every possible filter combination. Each pattern either forms a contiguous range in the B-tree or does not:

```sql
CREATE INDEX idx ON orders(status, created_at, user_id);

-- ── PATTERN 1: Leftmost column only — uses index ─────────────────────────────
EXPLAIN SELECT * FROM orders WHERE status = 'pending';
-- Index Scan using idx on orders
--   Index Cond: (status = 'pending')
-- B-tree: jump to first 'pending' entry, scan forward to 'shipped'. ✓
-- Can use the index. How much of the index: only the status dimension.

-- ── PATTERN 2: First two columns — uses index ─────────────────────────────────
EXPLAIN SELECT * FROM orders WHERE status = 'pending' AND created_at = '2024-01-01';
-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at = '2024-01-01'))
-- B-tree: jump to ('pending', '2024-01-01'), scan to ('pending', '2024-01-02'). ✓

-- ── PATTERN 3: All three columns — uses index ──────────────────────────────────
EXPLAIN SELECT * FROM orders
WHERE status = 'pending' AND created_at = '2024-01-01' AND user_id = 42;
-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at = '2024-01-01')
--               AND (user_id = 42))
-- B-tree: jumps to exact entry. Often only 1-2 index pages read. ✓

-- ── PATTERN 4: Range on second column after equality on first — uses index ─────
EXPLAIN SELECT * FROM orders
WHERE status = 'pending' AND created_at > '2024-01-01';
-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at > '2024-01-01'))
-- B-tree: jump to ('pending', '2024-01-01'), scan forward. ✓
-- Third column (user_id) CANNOT be used further — see Pattern 5.

-- ── PATTERN 5: Range on second, equality on third — third column is useless ────
EXPLAIN SELECT * FROM orders
WHERE status = 'pending' AND created_at > '2024-01-01' AND user_id = 42;
-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at > '2024-01-01'))
--   Filter: (user_id = 42)   ← user_id applied AFTER index traversal as a recheck
-- Reason: after a range on created_at, the user_id entries are no longer
-- sorted contiguously. Index can only narrow to (pending, >2024-01-01),
-- then user_id = 42 must be checked row by row within that range.
-- user_id contributes NOTHING to the B-tree traversal here.

-- ── PATTERN 6: Second column only — does NOT use index ────────────────────────
EXPLAIN SELECT * FROM orders WHERE created_at = '2024-01-01';
-- Seq Scan on orders
--   Filter: (created_at = '2024-01-01')
-- created_at entries are scattered by status prefix. Index not useful. ✗

-- ── PATTERN 7: Third column only — does NOT use index ─────────────────────────
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan on orders
--   Filter: (user_id = 42)
-- user_id entries are scattered across all (status, created_at) combinations. ✗

-- ── PATTERN 8: Second and third column, skipping first — does NOT use index ───
EXPLAIN SELECT * FROM orders WHERE created_at = '2024-01-01' AND user_id = 42;
-- Seq Scan on orders
--   Filter: ((created_at = '2024-01-01') AND (user_id = 42))
-- Without status in the filter, no leftmost prefix → index useless. ✗

-- ── PATTERN 9: OR on first column — uses index via BitmapOr ──────────────────
EXPLAIN SELECT * FROM orders WHERE status IN ('pending', 'processing');
-- Bitmap Heap Scan on orders
--   → BitmapOr
--       Bitmap Index Scan: Index Cond: (status = 'pending')
--       Bitmap Index Scan: Index Cond: (status = 'processing')
-- PostgreSQL runs two index scans and ORs the bitmaps. ✓
-- Equivalent: each value in IN(...) forms its own leftmost prefix scan.

-- ── PATTERN 10: ORDER BY matching the index — no Sort node ───────────────────
EXPLAIN SELECT * FROM orders
WHERE status = 'pending'
ORDER BY created_at ASC, user_id ASC;
-- Index Scan using idx on orders
--   Index Cond: (status = 'pending')
-- No Sort node — index already provides (status, created_at, user_id) order. ✓
-- PostgreSQL reads leaf pages sequentially: sorted by created_at then user_id ✓

EXPLAIN SELECT * FROM orders
WHERE status = 'pending'
ORDER BY user_id ASC;   -- user_id is not the next key column after status
-- Index Scan using idx + Sort   ← Sort node added
-- user_id is not sorted within 'pending' entries alone
-- (it's sorted within (status, created_at) pairs, not within status alone).
```

## Section 2: Equality vs Range — The Range Stop Rule

**Q3. Why does a range predicate on a column stop the index from using subsequent columns — what is the "range stop" rule?**

A: Once the B-tree scan encounters a range condition on a column, the entries beyond that column are no longer guaranteed to be contiguous in the index. This is not a planner limitation — it is a physical consequence of how the B-tree is sorted:

```
Visualising why range stops subsequent column usage:

Index on (status, created_at, user_id):

  Physical order in the index leaf pages:

  ('pending', 2024-01-01, 42)   ← user_id=42 appears on Jan 1
  ('pending', 2024-01-01, 199)
  ('pending', 2024-01-02, 5)    ← user_id=5 appears on Jan 2
  ('pending', 2024-01-02, 42)   ← user_id=42 ALSO appears on Jan 2
  ('pending', 2024-01-03, 42)   ← user_id=42 ALSO appears on Jan 3
  ('pending', 2024-01-03, 88)

  Query: WHERE status = 'pending' AND created_at > '2024-01-01' AND user_id = 42

  After the range on created_at (> 2024-01-01):
    The matching range is: ('pending', 2024-01-02, *) onwards
    Within this range, user_id=42 appears at positions 4 and 5.
    But so does user_id=5 (position 3), user_id=88 (position 6), etc.
    user_id is NOT contiguous within the (pending, > 2024-01-01) range.
    → The index cannot skip to user_id=42; it must scan all entries in the range.
    → user_id=42 is applied as a recheck filter, not an index condition.

  Contrast with WHERE status = 'pending' AND created_at = '2024-01-01' AND user_id = 42:
    The equality on created_at FIXES Jan 1. Within Jan 1, user_id IS sorted:
    ('pending', 2024-01-01, 42)  ← contiguous within (pending, Jan 1)
    ('pending', 2024-01-01, 199)
    → Index jumps directly to (pending, Jan-1, 42). user_id IS an index condition.
```

```sql
-- ── Confirming range stop in EXPLAIN output ────────────────────────────────────
-- Equality on all three: third column is an index condition
EXPLAIN (ANALYZE)
SELECT * FROM orders
WHERE status = 'pending' AND created_at = '2024-01-01' AND user_id = 42;

-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at = '2024-01-01')
--                AND (user_id = 42))           ← ALL THREE are Index Cond
--   actual rows=1  (jumps directly to one entry)

-- Range on second: third column becomes a Filter
EXPLAIN (ANALYZE)
SELECT * FROM orders
WHERE status = 'pending' AND created_at > '2024-01-01' AND user_id = 42;

-- Index Scan using idx on orders
--   Index Cond: ((status = 'pending') AND (created_at > '2024-01-01'))
--   Filter: (user_id = 42)                     ← user_id is NOT Index Cond
--   Rows Removed by Filter: 8432               ← 8432 rows scanned, most discarded
--   actual rows=47

-- Rows Removed by Filter is the cost of range stop:
-- The index narrowed to ~8479 rows; 8432 were discarded after the index scan.
-- user_id=42 contributed nothing to the B-tree traversal.

-- ── The equality exhaustion principle ─────────────────────────────────────────
-- Equality on a column "exhausts" that dimension of the sort:
-- All matching entries are guaranteed to be contiguous, so the next
-- column's sort order is fully intact for the planner to use.

-- Range on a column "opens up" that dimension:
-- Multiple values satisfy the range, and within each value, the next
-- column is sorted — but ACROSS values, the next column is interleaved.

-- Rule: put all equality-filter columns BEFORE any range-filter column.
-- This maximises how deeply the planner can use the index for traversal.

-- ── Practical example of column reordering to fix range stop ──────────────────
-- Query: WHERE user_id = 42 AND created_at > '2024-01-01'

-- BAD index — range stop hits immediately after user_id (second column):
CREATE INDEX idx_bad ON orders(user_id, created_at);
-- Wait — this is actually FINE for this query pattern!
-- user_id = 42 (equality, first column) → then range on created_at.
-- Equality on user_id exhausts the user_id dimension.
-- created_at range is the LAST condition — no subsequent columns to miss.

-- The problem arises with THREE columns:
-- Query: WHERE user_id = 42 AND created_at > '2024-01-01' AND status = 'pending'

-- BAD index for this query:
CREATE INDEX idx_bad2 ON orders(user_id, created_at, status);
-- user_id = 42 (equality) ✓ → created_at > Jan-1 (RANGE — stops here) → status MISSED
-- status is a recheck filter.

-- GOOD index for this query (equality columns before range):
CREATE INDEX idx_good ON orders(user_id, status, created_at);
-- user_id = 42 (equality) ✓ → status = 'pending' (equality) ✓ → created_at > Jan-1 (range, last)
-- All three columns contribute to the B-tree traversal.
-- No wasted recheck filters.
```

## Section 3: Cardinality and Column Ordering

**Q4. How does column cardinality affect the ordering decision — is "high cardinality first" always correct?**

A: Cardinality (number of distinct values) influences index selectivity but does NOT override the leftmost prefix rule. The correct order is determined first by query pattern (equality before range), and only then by cardinality within the equality columns:

```sql
-- ── The "high cardinality first" rule — when it applies ───────────────────────
-- For equality-only columns with no range columns:
-- Higher cardinality first → better selectivity → fewer rows to scan per lookup.

-- Table: 1,000,000 orders
-- status: 5 distinct values (cardinality = 5) → each value matches ~200,000 rows
-- user_id: 50,000 distinct values (cardinality = 50,000) → each value matches ~20 rows

-- Query: WHERE status = 'pending' AND user_id = 42
-- (Both equality — no range columns to worry about.)

-- Index A: (status, user_id)
--   B-tree jumps to ('pending', 42) → finds ~20 rows. ✓
-- Index B: (user_id, status)
--   B-tree jumps to (42, 'pending') → finds ~20 rows. ✓
-- SAME result — row count is identical regardless of equality column order.
-- High cardinality first (user_id) only matters when:
--   1. The index is used WITHOUT the other column:
--      WHERE user_id = 42 → index B (user_id first) works, index A (status first) does not.
--   2. You only have ONE index and need it to serve both single-column and dual-column queries.

-- ── When cardinality ordering matters: single-column prefix queries ────────────
-- If you also run: WHERE status = 'pending' (without user_id)
--   Index A (status, user_id): works for this query ✓
--   Index B (user_id, status): does NOT work for this query ✗
-- If you also run: WHERE user_id = 42 (without status)
--   Index A (status, user_id): does NOT work ✗
--   Index B (user_id, status): works ✓

-- Decision framework:
--   1. Which single-column queries need to use this index? Put those columns first.
--   2. Among equality columns with no single-column needs, put higher cardinality first.
--   3. Put range-filter columns AFTER all equality-filter columns.
--   4. Use INCLUDE for projection-only columns.

-- ── Cardinality vs query pattern: a concrete conflict ─────────────────────────
-- Table: events (1M rows)
-- tenant_id:  cardinality = 100 (low — 10,000 rows per tenant)
-- event_type: cardinality = 20  (lower — 50,000 rows per type)
-- user_id:    cardinality = 10,000 (high — 100 rows per user)
-- created_at: range column

-- Query pattern:
-- WHERE tenant_id = ? AND event_type = ? AND user_id = ? AND created_at > ?

-- "High cardinality first" rule suggests: (user_id, tenant_id, event_type, created_at)
-- BUT: queries always filter on ALL four columns together. Order within equality
-- columns doesn't affect row count. So cardinality is irrelevant here.

-- The REAL consideration: which column is sometimes omitted from the WHERE clause?
-- If tenant_id is ALWAYS present: put it first (enables single-column prefix use)
-- If user_id is sometimes omitted: don't put it before tenant_id
--   (otherwise WHERE tenant_id = ? AND event_type = ? won't use the index)

-- ── Demonstrating selectivity interaction ─────────────────────────────────────
-- Measure per-column selectivity with statistics:
SELECT
    attname,
    n_distinct,
    CASE
        WHEN n_distinct > 0 THEN ROUND(100.0 / n_distinct, 2)
        ELSE ROUND(100.0 * ABS(n_distinct), 2)  -- Negative = fraction of total rows
    END AS approx_pct_per_value
FROM   pg_stats
WHERE  tablename = 'orders'
AND    attname IN ('status', 'created_at', 'user_id', 'tenant_id')
ORDER  BY approx_pct_per_value;

-- attname    │ n_distinct │ approx_pct_per_value
-- ───────────┼────────────┼─────────────────────
-- user_id    │  50000     │ 0.002%   ← most selective
-- created_at │  -0.9      │ 0.11%    ← high cardinality date
-- tenant_id  │  100       │ 1.0%
-- status     │  5         │ 20.0%    ← least selective

-- High-selectivity (high-cardinality) columns in WHERE clauses help the index
-- return fewer rows per lookup. But only if the leftmost prefix rule is satisfied.
```

**Q5. How should you order columns when queries have different filter combinations — the multi-query design problem?**

A: A single composite index must serve multiple query patterns simultaneously. The design becomes a constraint-satisfaction problem: find the column order that maximises the number of query patterns that get efficient index traversal:

```sql
-- ── Setup: four query patterns against the same table ─────────────────────────
-- Table: audit_logs (10M rows)
-- Columns: tenant_id, user_id, action, severity, occurred_at

-- Pattern A (60% of traffic): WHERE tenant_id = ? ORDER BY occurred_at DESC
-- Pattern B (25% of traffic): WHERE tenant_id = ? AND user_id = ?
-- Pattern C (10% of traffic): WHERE tenant_id = ? AND action = ? AND occurred_at > ?
-- Pattern D (5% of traffic):  WHERE tenant_id = ? AND severity = 'critical'

-- ── Analysis ──────────────────────────────────────────────────────────────────
-- tenant_id appears in ALL four patterns → MUST be the leftmost column.
-- After tenant_id:
--   Pattern A needs: nothing more for filtering, but ORDER BY occurred_at
--   Pattern B needs: user_id (equality)
--   Pattern C needs: action (equality) then occurred_at (range)
--   Pattern D needs: severity (equality)

-- No single index can perfectly serve all four patterns.
-- Option 1: Multiple indexes (one per pattern):
CREATE INDEX idx_a ON audit_logs(tenant_id, occurred_at DESC);
CREATE INDEX idx_b ON audit_logs(tenant_id, user_id);
CREATE INDEX idx_c ON audit_logs(tenant_id, action, occurred_at);
CREATE INDEX idx_d ON audit_logs(tenant_id, severity) WHERE severity = 'critical';
-- → Best query performance. Cost: 4 indexes = write amplification on every INSERT.

-- Option 2: One composite index that covers the most important patterns:
CREATE INDEX idx_primary ON audit_logs(tenant_id, user_id, action, occurred_at)
    INCLUDE (severity);
-- Coverage analysis:
--   Pattern A: tenant_id ✓ (prefix), occurred_at in INCLUDE → no extra heap fetch
--              BUT: no ORDER BY support without Sort node (occurred_at is 4th key)
--   Pattern B: tenant_id + user_id ✓ (first two columns, both equality)
--   Pattern C: tenant_id + action ✗ (action is 3rd column, user_id must come first)
--              → becomes Filter on action, not Index Cond
--   Pattern D: tenant_id + severity ✗ (severity in INCLUDE, not key) → Filter

-- Option 3: Two indexes covering all patterns efficiently:
-- Index 1: Serves patterns A and D (tenant + time, tenant + severity):
CREATE INDEX idx_tenant_time ON audit_logs(tenant_id, severity, occurred_at DESC)
    INCLUDE (user_id, action);
-- Pattern A: tenant_id ✓, occurred_at order (3rd key, but severity may be filtered or ignored)
-- Pattern D: tenant_id + severity ✓

-- Index 2: Serves patterns B and C:
CREATE INDEX idx_tenant_user_action ON audit_logs(tenant_id, user_id, action, occurred_at)
    INCLUDE (severity);
-- Pattern B: tenant_id + user_id ✓
-- Pattern C: tenant_id + action ✗ (user_id is between them)
-- → Still need to reconsider.

-- ── The correct multi-pattern solution ────────────────────────────────────────
-- Identify the "anchor column" (always present): tenant_id
-- Group patterns by their secondary filter:
--   user_id group:  B (tenant + user_id)
--   action group:   C (tenant + action + occurred_at range)
--   time group:     A (tenant + occurred_at ORDER BY)
--   severity group: D (tenant + severity = 'critical' — partial index!)

-- Final design:
CREATE INDEX idx_al_user ON audit_logs(tenant_id, user_id, occurred_at DESC)
    INCLUDE (action, severity);
-- Serves B + A (via tenant_id + occurred_at time ordering for A)

CREATE INDEX idx_al_action ON audit_logs(tenant_id, action, occurred_at DESC)
    INCLUDE (user_id, severity);
-- Serves C perfectly: tenant_id (eq) + action (eq) + occurred_at (range)

CREATE INDEX idx_al_critical ON audit_logs(tenant_id, occurred_at DESC)
    WHERE severity = 'critical';
-- Serves D: partial index — only 5% of rows, very small index.
-- Also serves A (without severity filter) if the main index is larger.

-- ── Measuring trade-offs with EXPLAIN on each pattern ─────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, action, occurred_at FROM audit_logs
WHERE  tenant_id = 1 AND user_id = 42
ORDER  BY occurred_at DESC LIMIT 20;
-- → Index Only Scan using idx_al_user  Heap Fetches: 0  ✓

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, action, occurred_at FROM audit_logs
WHERE  tenant_id = 1 AND action = 'login' AND occurred_at > NOW() - INTERVAL '7 days';
-- → Index Scan using idx_al_action  ✓
```

## Section 4: ORDER BY and the Index

**Q6. How does the index sort order interact with `ORDER BY` — when does the planner avoid a Sort node?**

A: The B-tree provides its entries in sorted order. If the query's `ORDER BY` matches the index's sort sequence exactly — including direction — the planner can read the index in order and skip the Sort node entirely. Mismatches always add a Sort node:

```sql
-- ── Index: (tenant_id ASC, occurred_at DESC, user_id ASC) ────────────────────
CREATE INDEX idx_tenant_time_user
    ON audit_logs(tenant_id ASC, occurred_at DESC, user_id ASC);

-- ── ORDER BY that MATCHES the index — no Sort node ───────────────────────────
EXPLAIN SELECT tenant_id, occurred_at, user_id
FROM   audit_logs
WHERE  tenant_id = 1
ORDER  BY occurred_at DESC, user_id ASC;
-- Index Only Scan Backward... No, actually:
-- Index Only Scan using idx_tenant_time_user
--   Index Cond: (tenant_id = 1)
-- (No Sort node — index provides (occurred_at DESC, user_id ASC) order
--  within the tenant_id = 1 range) ✓

-- ── ORDER BY that is OPPOSITE to index — planner reads backward ───────────────
EXPLAIN SELECT tenant_id, occurred_at, user_id
FROM   audit_logs
WHERE  tenant_id = 1
ORDER  BY occurred_at ASC, user_id DESC;
-- Index Only Scan Backward using idx_tenant_time_user
--   (reading the B-tree in reverse — still no Sort node)
-- PostgreSQL can scan any B-tree in either direction, so the exact opposite
-- of the index sort order is also served without a Sort node.

-- ── Mixed direction ORDER BY — REQUIRES Sort node ─────────────────────────────
EXPLAIN SELECT tenant_id, occurred_at, user_id
FROM   audit_logs
WHERE  tenant_id = 1
ORDER  BY occurred_at DESC, user_id DESC;   -- user_id direction differs from index
-- Index Scan using idx_tenant_time_user + Sort   ← Sort node added
-- The index has (occurred_at DESC, user_id ASC).
-- The query wants (occurred_at DESC, user_id DESC).
-- PostgreSQL cannot simply reverse: reversing would give (occurred_at ASC, user_id DESC)
-- which is also wrong. A sort is unavoidable.

-- This is the only case where specifying sort direction in the index matters:
CREATE INDEX idx_a ON orders(created_at DESC, user_id DESC);  -- serves DESC, DESC
CREATE INDEX idx_b ON orders(created_at ASC,  user_id ASC);   -- serves ASC, ASC (and DESC, DESC via backward scan)
-- A single ASC index serves both ASC and DESC (via backward scan).
-- You only need explicit DESC direction when mixing: (col_A ASC, col_B DESC).

-- ── ORDER BY column not in index — always adds Sort ──────────────────────────
EXPLAIN SELECT tenant_id, occurred_at, total
FROM   orders
WHERE  user_id = 42
ORDER  BY total DESC;   -- total is not in the index
-- Index Scan using idx_orders_user_id + Sort
-- Index handles the WHERE, Sort handles the ORDER BY. No way to avoid it.

-- ── LIMIT interaction: index order eliminates Sort AND enables early stop ──────
EXPLAIN SELECT * FROM audit_logs
WHERE  tenant_id = 1
ORDER  BY occurred_at DESC
LIMIT  10;
-- Index Scan using idx_tenant_time_user
--   Index Cond: (tenant_id = 1)
--   Limit: 10 rows
-- (No Sort — index provides order. With LIMIT 10: stops after 10 index entries.
--  Even if 1M rows match tenant_id = 1, only 10 index pages are read.) ✓

-- The performance difference:
-- Without index supporting ORDER BY:
--   Fetch ALL matching rows → sort all of them → return 10.
--   For 1M matching rows: sort 1M rows just to return 10.
-- With index supporting ORDER BY:
--   Read 10 index entries in order → return immediately.
--   Constant time regardless of matching row count.
```

## Section 5: Common Mistakes and Anti-Patterns

**Q7. What are the most common column ordering mistakes — patterns that look correct but aren't?**

A: Index design mistakes follow recurring patterns. Each represents a misunderstanding of the leftmost prefix rule applied to a specific query shape:

```sql
-- ── MISTAKE 1: Range column before equality columns ────────────────────────────
-- Query: WHERE created_at > '2024-01-01' AND status = 'pending' AND user_id = 42
CREATE INDEX idx_mistake_1 ON orders(created_at, status, user_id);
-- PROBLEM: created_at is a range column first. After the range on created_at,
-- status and user_id cannot be used as index conditions.
EXPLAIN SELECT * FROM orders
WHERE created_at > '2024-01-01' AND status = 'pending' AND user_id = 42;
-- Index Scan: Index Cond: (created_at > '2024-01-01')
--             Filter: ((status = 'pending') AND (user_id = 42))
--             Rows Removed by Filter: 89,234  ← wasted work

-- CORRECT: equality columns before range columns:
CREATE INDEX idx_fix_1 ON orders(status, user_id, created_at);
-- Index Scan: Index Cond: ((status = 'pending') AND (user_id = 42)
--                         AND (created_at > '2024-01-01'))  ✓

-- ── MISTAKE 2: Low-cardinality boolean/enum first without a reason ─────────────
-- Table: tasks (5M rows), is_deleted BOOLEAN (cardinality = 2)
-- Query: WHERE is_deleted = FALSE AND user_id = ? AND due_date > ?
CREATE INDEX idx_mistake_2 ON tasks(is_deleted, user_id, due_date);
-- is_deleted = FALSE matches ~95% of rows. The index prefix is barely selective.
-- Jumping to is_deleted = FALSE lands on 4.75M entries — still a massive scan.
EXPLAIN SELECT * FROM tasks WHERE is_deleted = FALSE AND user_id = 42;
-- Index Scan: Index Cond: ((is_deleted = FALSE) AND (user_id = 42))
-- Works but: planner must scan all (FALSE, 42) entries → if user 42 has many tasks,
-- this is fine. But the is_deleted prefix provides almost no selectivity benefit.

-- CORRECT A: put higher-cardinality equality column first:
CREATE INDEX idx_fix_2a ON tasks(user_id, due_date) WHERE is_deleted = FALSE;
-- Partial index: excludes the 5% deleted rows → smaller, more selective index.
-- WHERE user_id = ? AND is_deleted = FALSE → Index Scan  ✓ (partial predicate matches)

-- CORRECT B: if you also need to query deleted tasks:
CREATE INDEX idx_fix_2b ON tasks(user_id, is_deleted, due_date);
-- user_id (high cardinality, equality) first → is_deleted (equality) → due_date (range)

-- ── MISTAKE 3: Indexing the join column on the wrong side ─────────────────────
-- Query joining orders (large) to users (small):
-- SELECT * FROM orders o JOIN users u ON u.id = o.user_id WHERE u.name ILIKE 'Alice%'
-- Common mistake: index on users.name (the filter side)
CREATE INDEX idx_users_name ON users(name);  -- Useful for the WHERE filter
-- But the join condition o.user_id = u.id requires:
-- For each user matching the name filter, find their orders.
-- Without index on orders.user_id: seq scan of orders for EACH matching user.
CREATE INDEX idx_orders_user_id ON orders(user_id);  -- The join key on the FK side
-- Both indexes needed — the FK child side is the one most often missed.

-- ── MISTAKE 4: Redundant prefix column ────────────────────────────────────────
-- Existing index: idx_a on orders(user_id)
CREATE INDEX idx_mistake_4 ON orders(user_id, created_at);
-- idx_a on (user_id) is now REDUNDANT — idx_mistake_4 serves all queries
-- that idx_a served (leftmost prefix = user_id). Delete idx_a.
-- Having both wastes write overhead and memory.

-- Find redundant indexes:
SELECT
    pg_size_pretty(pg_relation_size(i.indexrelid)) AS index_size,
    ix.indkey::TEXT AS key_columns,
    i.indexrelname
FROM   pg_stat_user_indexes i
JOIN   pg_index ix ON ix.indexrelid = i.indexrelid
WHERE  i.relname = 'orders'
ORDER  BY ix.indkey;
-- Look for indexes where one index's key columns are a prefix of another's.

-- ── MISTAKE 5: Ignoring implicit sort from PK ─────────────────────────────────
-- Creating an index that duplicates the PK order:
-- Table has: id BIGSERIAL PRIMARY KEY (B-tree index on id already exists)
CREATE INDEX idx_mistake_5 ON orders(user_id, id);
-- If your query is: WHERE user_id = 42 ORDER BY id ASC
-- This index is correct. But if you only need to find rows by user_id,
-- adding id to the index for "ordering" without a specific ORDER BY id query
-- is just wasting space.

-- ── MISTAKE 6: BETWEEN as two ranges ─────────────────────────────────────────
-- BETWEEN is treated as two range conditions: col >= low AND col <= high.
-- It is a range condition — columns after it are not used as index conditions.
CREATE INDEX idx_mistake_6 ON orders(status, amount, created_at);
-- Query: WHERE status = 'pending' AND amount BETWEEN 100 AND 500 AND created_at > ?
-- Index Cond: ((status = 'pending') AND (amount >= 100) AND (amount <= 500))
-- Filter: (created_at > ...)   ← created_at is a Filter, not Index Cond
-- The BETWEEN on amount is a range → stops the index from using created_at.

-- CORRECT: equality columns before BETWEEN/range:
CREATE INDEX idx_fix_6 ON orders(status, created_at, amount);
-- Only works if created_at is equality-filtered elsewhere.
-- If created_at is also a range: put the more selective range first and accept the stop.

-- ── MISTAKE 7: Column in SELECT but not INCLUDE causes heap fetch ──────────────
-- Trying to use an index-only scan but forgetting a projected column:
CREATE INDEX idx_mistake_7 ON orders(user_id, status);
-- INCLUDE (total) is missing.
SELECT user_id, status, total FROM orders WHERE user_id = 42;
-- → Index Scan (NOT Index Only Scan) — total forces heap fetch.
-- Fix:
CREATE INDEX idx_fix_7 ON orders(user_id, status) INCLUDE (total);
-- → Index Only Scan  Heap Fetches: 0  ✓
```

**Q8. What is a "skip scan" and does PostgreSQL support it?**

A: A skip scan (also called a loose index scan) allows the planner to use an index without the leftmost prefix by scanning for each distinct value of the missing leading column. PostgreSQL does not natively support skip scans, but there are workarounds for specific patterns:

```sql
-- ── What a skip scan would do (conceptually) ──────────────────────────────────
-- Index: (status, user_id)
-- Query: WHERE user_id = 42   ← no 'status' filter

-- A skip scan would:
-- 1. Find the first distinct status value: 'cancelled'
-- 2. Scan the ('cancelled', 42) entries → return matching rows
-- 3. Find the next distinct status: 'pending'
-- 4. Scan ('pending', 42) entries → return matching rows
-- 5. Repeat for all distinct status values.
-- Total: cardinality(status) × O(log n) lookups instead of a full index scan.
-- Works efficiently when cardinality of the leading column is LOW.

-- ── PostgreSQL's position: no native skip scan (as of PostgreSQL 16) ──────────
-- PostgreSQL does NOT implement skip scans.
-- MySQL/InnoDB does support loose index scans in specific GROUP BY queries.
-- The PostgreSQL planner cannot use the (status, user_id) index for:
-- WHERE user_id = 42 (without status).
-- Result: always falls back to seq scan or a separate index on user_id.

-- ── Workaround A: separate index on the missing prefix column ─────────────────
CREATE INDEX idx_orders_user_id ON orders(user_id);
-- Serves WHERE user_id = 42 directly. No skip scan needed.
-- Extra index cost: write amplification on every INSERT/UPDATE.

-- ── Workaround B: LATERAL join to simulate skip scan ─────────────────────────
-- Only viable when the leading column has VERY LOW cardinality.
-- Works by explicitly enumerating the distinct leading column values:

SELECT DISTINCT status FROM orders;  -- Returns: 'cancelled', 'pending', 'shipped'

-- Skip-scan simulation:
SELECT o.*
FROM   (SELECT UNNEST(ARRAY['cancelled','pending','shipped','processing','delivered'])
        AS status) AS s,
       LATERAL (
           SELECT * FROM orders
           WHERE  status = s.status
           AND    user_id = 42
           LIMIT  1000
       ) AS o;
-- For each of the 5 status values, uses index (status, user_id) → finds user_id=42.
-- Total: 5 index lookups instead of one full scan.
-- Limitation: must hardcode or dynamically fetch the distinct status values.

-- ── Workaround C: add a selective partial index per leading value ──────────────
-- If one leading value dominates the query pattern:
CREATE INDEX idx_pending_user ON orders(user_id) WHERE status = 'pending';
-- WHERE user_id = 42 AND status = 'pending' → uses this partial index ✓
-- Very small index (only pending orders). Fast. No skip scan needed.

-- ── When to just add a separate index ────────────────────────────────────────
-- If WHERE user_id = 42 (without status filter) runs frequently:
-- Just add a separate index on (user_id) or (user_id, ...).
-- The maintenance cost is lower than the complexity of skip scan workarounds.
-- Use pg_stat_user_indexes to verify the existing (status, user_id) index
-- is actually being used before adding more indexes:
SELECT indexrelname, idx_scan, idx_tup_read
FROM   pg_stat_user_indexes
WHERE  relname = 'orders';
-- idx_scan = 0 → index never used → remove it.
```

## Section 6: EXPLAIN Analysis for Index Order Decisions

**Q9. How do you read `EXPLAIN` output to diagnose whether column order is optimal — what signals indicate a misorder?**

A: `EXPLAIN (ANALYZE, BUFFERS)` reveals exactly how the planner uses (or fails to use) the index for each column. The key signals are in the distinction between `Index Cond` and `Filter`, and in the `Rows Removed by Filter` count:

```sql
-- ── The diagnostic template ────────────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, user_id, status, total
FROM   orders
WHERE  status = 'pending'
AND    created_at > '2024-01-01'
AND    user_id = 42;

-- ── Reading the output: good column order ─────────────────────────────────────
-- When index is (status, user_id, created_at) — equality before range:

-- Index Scan using idx_s_u_c on orders
--   (cost=0.56..24.78 rows=19 width=32)
--   (actual time=0.041..0.312 rows=18 loops=1)
--
-- ① Index Cond: ((status = 'pending')          ← Index condition on col 1
--                AND (user_id = 42)             ← Index condition on col 2
--                AND (created_at > '2024-01-01')) ← Index condition on col 3 (range, last)
--
-- ② Filter: (none)                              ← No post-scan filter
-- ③ Rows Removed by Filter: 0                  ← Zero wasted row reads
-- ④ Buffers: shared hit=4                       ← Only 4 index/heap pages

-- INTERPRETATION: All three WHERE columns are Index Cond.
-- The B-tree traversal used all three columns.
-- Zero rows discarded after the index scan. Optimal.

-- ── Reading the output: bad column order ──────────────────────────────────────
-- When index is (created_at, status, user_id) — range column first:

-- Index Scan using idx_c_s_u on orders
--   (cost=0.56..9842.33 rows=18 width=32)
--   (actual time=0.039..891.234 rows=18 loops=1)
--
-- ① Index Cond: (created_at > '2024-01-01')   ← Only the range column used in index
-- ② Filter: ((status = 'pending')              ← POST-SCAN filter (not index cond)
--             AND (user_id = 42))              ← POST-SCAN filter
-- ③ Rows Removed by Filter: 342,891           ← 342K rows read and discarded
-- ④ Buffers: shared hit=892 read=4831         ← Thousands of pages read

-- INTERPRETATION: Only created_at contributes to B-tree traversal.
-- status and user_id are rechecked row-by-row after the index scan.
-- 342,891 rows fetched from heap only to be discarded. Severe misorder.
-- Fix: reorder to (status, user_id, created_at).

-- ── The key signals in EXPLAIN output ─────────────────────────────────────────
-- "Index Cond" for a column → column used in B-tree traversal ✓ (good)
-- "Filter" for a column     → column NOT used in B-tree traversal ✗ (bad if count is high)
-- "Rows Removed by Filter: N" where N is large → index scan returning too many rows ✗
-- "Buffers: read=N" where N is large → too many pages read from disk ✗

-- ── Distinguishing Filter from a bad index vs. low selectivity ────────────────
-- Filter is sometimes acceptable — when the filtered column has low cardinality
-- and few rows are discarded:
-- Filter: (status = 'pending')    Rows Removed by Filter: 3
-- → Only 3 rows discarded → Filter is cheap → column order may be fine.

-- But:
-- Filter: (status = 'pending')    Rows Removed by Filter: 89,234
-- → 89K rows discarded → column order is wrong (or index is missing).

-- ── Automated diagnosis query ─────────────────────────────────────────────────
-- Find queries with high filter removal rates (index misorder symptoms):
SELECT
    query,
    calls,
    ROUND(total_exec_time::NUMERIC / calls, 2) AS avg_ms,
    rows / NULLIF(calls, 0)                    AS avg_rows_returned
FROM   pg_stat_statements
WHERE  query ILIKE '%orders%'
AND    total_exec_time / NULLIF(calls, 0) > 100  -- Slow queries (>100ms avg)
ORDER  BY total_exec_time DESC
LIMIT  20;
-- Identify slow queries, then run EXPLAIN on each to check for Filter vs Index Cond.

-- ── Using auto_explain to capture plans automatically ─────────────────────────
-- In postgresql.conf:
-- shared_preload_libraries = 'auto_explain'
-- auto_explain.log_min_duration = 100   -- Log plans for queries > 100ms
-- auto_explain.log_analyze = true
-- auto_explain.log_buffers = true
-- auto_explain.log_triggers = true
-- → All slow query plans automatically appear in PostgreSQL log.
-- → Review "Filter" nodes for "Rows Removed by Filter" counts.
```

## Section 7: TypeORM Index Declaration

**Q10. How do you declare correctly ordered composite indexes in TypeORM — and how do you verify them?**

A: TypeORM generates indexes from entity decorators, but the column ordering in the decorator directly maps to the index column order in PostgreSQL. The framework offers no guidance on ordering — that is entirely the developer's responsibility:

```typescript
import {
    Entity, PrimaryGeneratedColumn, Column,
    Index, CreateDateColumn, ManyToOne, JoinColumn,
} from 'typeorm';

// ── Composite index via @Index on the entity class ────────────────────────────
@Entity('orders')

// Index 1: serves WHERE status = ? AND user_id = ? (and their prefixes)
// Equality columns in order: status then user_id.
// No range column → this index also serves WHERE status = ? alone.
@Index('idx_orders_status_user', ['status', 'userId'])

// Index 2: serves WHERE userId = ? ORDER BY createdAt DESC LIMIT N
// Equality first (userId), then range/sort column (createdAt).
// CORRECT ORDER — equality before the temporal range.
@Index('idx_orders_user_date', ['userId', 'createdAt'])

// Index 3: serves WHERE tenantId = ? AND status = ? AND createdAt > ?
// tenantId (equality, always present), status (equality), createdAt (range — last).
// CORRECT: all equalities before the range.
@Index('idx_orders_tenant_status_date', ['tenantId', 'status', 'createdAt'])

export class Order {
    @PrimaryGeneratedColumn()
    id: number;

    @Column({ name: 'tenant_id' })
    tenantId: number;

    @Column({ name: 'user_id' })
    userId: number;

    @Column()
    status: string;   // 'pending' | 'shipped' | 'cancelled' | ...

    @Column('decimal', { precision: 10, scale: 2 })
    total: number;

    @CreateDateColumn({ name: 'created_at' })
    createdAt: Date;

    @Column({ name: 'notes', nullable: true })
    notes: string;    // Not indexed — never queried directly
}

// ── INCLUDE columns via migration (TypeORM decorators don't support INCLUDE) ────
// TypeORM's @Index does not support the INCLUDE clause.
// Must use a raw migration query:
import { MigrationInterface, QueryRunner } from 'typeorm';

export class AddCoveringIndexOrders1700000001000 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<void> {
        // Drop the TypeORM-generated index first (if it exists without INCLUDE):
        await queryRunner.query(`
            DROP INDEX CONCURRENTLY IF EXISTS idx_orders_user_date
        `);

        // Recreate with INCLUDE for index-only scan support:
        await queryRunner.query(`
            CREATE INDEX CONCURRENTLY idx_orders_user_date
            ON orders(user_id ASC, created_at DESC)
            INCLUDE (status, total)
        `);
        -- Column order analysis:
        -- user_id: equality filter → leftmost ✓
        -- created_at: range filter / ORDER BY → second (after equality) ✓
        -- status, total: INCLUDE → available for index-only scans ✓
    }

    public async down(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`
            DROP INDEX CONCURRENTLY IF EXISTS idx_orders_user_date
        `);
        // TypeORM will recreate the basic version on next sync if @Index is present.
    }
}

// ── Service: writing queries that respect the index order ─────────────────────
@Injectable()
export class OrderService {
    constructor(
        @InjectRepository(Order)
        private readonly repo: Repository<Order>,
        private readonly dataSource: DataSource,
    ) {}

    // ✓ Uses idx_orders_tenant_status_date fully:
    //   WHERE tenantId = ? AND status = ? AND createdAt > ?   (all Index Cond)
    async getPendingOrdersSince(tenantId: number, since: Date): Promise<Order[]> {
        return this.repo
            .createQueryBuilder('o')
            .select(['o.id', 'o.userId', 'o.status', 'o.total'])  // Matches INCLUDE
            .where('o.tenantId = :tenantId', { tenantId })          // Leftmost: equity ✓
            .andWhere('o.status = :status', { status: 'pending' }) // Second: equality ✓
            .andWhere('o.createdAt > :since', { since })           // Third: range ✓
            .orderBy('o.createdAt', 'DESC')
            .getMany();
    }

    // ✗ Skips leftmost prefix — creates a Filter, not Index Cond on tenantId:
    async getOrdersByStatusWrong(status: string): Promise<Order[]> {
        return this.repo.find({
            where: { status },  // Missing tenantId — no leftmost prefix for multi-tenant index
        });
        // Planner: seq scan or uses a different index (if one on status exists)
    }

    // ── Verifying index usage in development ─────────────────────────────────
    async diagnoseQuery(tenantId: number, status: string, since: Date): Promise<void> {
        const [result] = await this.dataSource.query(`
            EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
            SELECT id, user_id, status, total
            FROM   orders
            WHERE  tenant_id  = $1
            AND    status     = $2
            AND    created_at > $3
            ORDER  BY created_at DESC
        `, [tenantId, status, since]);

        const plan = result['QUERY PLAN'][0]['Plan'];

        console.log('Node Type:            ', plan['Node Type']);
        // Target: 'Index Only Scan' or 'Index Scan'

        console.log('Index Cond:           ', plan['Index Cond']);
        // Target: includes all three WHERE columns

        console.log('Filter:               ', plan['Filter'] ?? '(none)');
        // Target: '(none)' — any Filter here = column order problem

        console.log('Rows Removed by Filter:', plan['Rows Removed by Filter'] ?? 0);
        // Target: 0 — non-zero = the filter is discarding rows (bad)

        console.log('Heap Fetches:         ', plan['Heap Fetches'] ?? 'N/A');
        // Target: 0 — non-zero = INCLUDE columns missing or VM not current

        console.log('Buffers shared read:  ', plan['Shared Read Blocks'] ?? 0);
        // Target: low — many disk reads = large scan or missing index
    }
}
```

## Section 8: Advanced Patterns

**Q11. How do expression indexes interact with the leftmost prefix rule?**

A: An expression index uses a computed value as a key column. The leftmost prefix rule applies identically — the expression must appear in the query's WHERE or ORDER BY in exactly the same form used in the index definition:

```sql
-- ── Expression as a key column ────────────────────────────────────────────────
-- Query pattern: WHERE LOWER(email) = ? AND tenant_id = ?
-- (case-insensitive email lookup, always combined with tenant_id)

-- WRONG column order (expression is second):
CREATE INDEX idx_wrong_expr ON users(tenant_id, LOWER(email));
-- For WHERE tenant_id = ? AND LOWER(email) = ?:
--   tenant_id = ? ✓ (leftmost), LOWER(email) = ? ✓ (second, equality after equality)
-- Actually this is fine for the two-column query pattern.
-- BUT for WHERE LOWER(email) = ? alone (without tenant_id):
--   Cannot use this index — no leftmost prefix.

-- CORRECT order if LOWER(email) is the primary lookup key:
CREATE INDEX idx_correct_expr ON users(LOWER(email), tenant_id);
-- Serves: WHERE LOWER(email) = ?                          ✓ (leftmost prefix)
-- Serves: WHERE LOWER(email) = ? AND tenant_id = ?        ✓ (both columns)
-- Does NOT serve: WHERE tenant_id = ? alone               ✗

-- ── The expression must match EXACTLY ────────────────────────────────────────
CREATE INDEX idx_lower_email ON users(LOWER(email));

-- Uses the index (expression matches):
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';  ✓

-- Does NOT use the index (different expression form):
SELECT * FROM users WHERE email = 'alice@example.com';  ✗ (no LOWER())
SELECT * FROM users WHERE LOWER(email) LIKE 'alice%';   ✗ (LIKE, not =)
SELECT * FROM users WHERE email ILIKE 'alice@example.com';  ✗ (ILIKE, not LOWER() =)

-- ILIKE can use the index IF the index uses the citext extension or a specific
-- operator class, but not a plain LOWER() expression index.

-- ── Composite expression index with the leftmost rule ─────────────────────────
-- Query: WHERE DATE_TRUNC('month', created_at) = '2024-01-01' AND user_id = 42
CREATE INDEX idx_month_user
    ON orders(DATE_TRUNC('month', created_at), user_id);

EXPLAIN SELECT * FROM orders
WHERE DATE_TRUNC('month', created_at) = '2024-01-01'::TIMESTAMPTZ
AND   user_id = 42;
-- Index Scan using idx_month_user
--   Index Cond: ((date_trunc('month'::text, created_at) = '2024-01-01')
--                AND (user_id = 42))  ✓

-- The expression in the WHERE must match the index expression character-for-character
-- (PostgreSQL normalises some variations, but exact match is safest).

-- ── NULLS FIRST / NULLS LAST and the leftmost rule ────────────────────────────
-- NULL ordering affects how the index handles nullable columns.
-- Default: ASC = NULLS LAST, DESC = NULLS FIRST.
-- If queries use ORDER BY col NULLS FIRST on an ASC column:
CREATE INDEX idx_nulls ON orders(completed_at ASC NULLS FIRST, user_id);
-- ORDER BY completed_at ASC NULLS FIRST → matches index → no Sort node ✓
-- ORDER BY completed_at ASC NULLS LAST  → does NOT match → Sort node added

-- ── GIN / GiST indexes and the leftmost rule ──────────────────────────────────
-- GIN and GiST indexes do not support composite (multi-column) B-tree style indexing.
-- They are single-column (or use their own internal structure for multi-column).
-- The leftmost prefix rule applies ONLY to B-tree (and hash) indexes.
-- For JSONB, full-text, or geometric data: use GIN/GiST, not composite B-tree.
```

**Q12. How do you use `pg_stat_user_indexes` and `pg_stats` to audit and refine composite index column order?**

A: The combination of usage statistics and column statistics provides an evidence-based approach to index design. Usage tells you which indexes are being used; column statistics tell you how selective each column is:

```sql
-- ── Full index audit query ────────────────────────────────────────────────────
SELECT
    i.indexrelname                                         AS index_name,
    t.relname                                              AS table_name,
    pg_size_pretty(pg_relation_size(i.indexrelid))        AS index_size,
    i.idx_scan                                            AS scans,
    i.idx_tup_read                                        AS tuples_read,
    i.idx_tup_fetch                                       AS tuples_fetched,
    ROUND(i.idx_tup_fetch::NUMERIC
          / NULLIF(i.idx_tup_read, 0) * 100, 1)           AS fetch_ratio_pct,
    pg_get_indexdef(i.indexrelid)                         AS definition
FROM   pg_stat_user_indexes  i
JOIN   pg_class              t ON t.oid = i.relid
WHERE  t.relname = 'orders'
ORDER  BY i.idx_scan DESC;

-- fetch_ratio_pct: what % of index-read tuples were actually fetched from heap.
-- Low fetch_ratio (e.g., 0.1%) = index is returning many rows that are then discarded
--   = column order may be wrong (range before equality) or selectivity is poor.
-- High fetch_ratio (e.g., 95%+) = index is accurately targeting needed rows.

-- Unused indexes (idx_scan = 0 after a representative period):
SELECT
    indexrelname AS index_name,
    relname      AS table_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS wasted_size
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0
AND    relname NOT LIKE 'pg_%'
ORDER  BY pg_relation_size(indexrelid) DESC;
-- → Candidates for removal (verify over weeks, not hours — traffic patterns vary).

-- ── Column selectivity analysis: deciding cardinality ordering ────────────────
SELECT
    attname                        AS column_name,
    n_distinct,
    correlation,
    CASE
        WHEN n_distinct > 0 THEN n_distinct
        ELSE ROUND(ABS(n_distinct) * (SELECT reltuples FROM pg_class WHERE relname = 'orders'))
    END                            AS estimated_distinct_values,
    array_length(most_common_vals::text::text[], 1)  AS num_common_vals_tracked,
    most_common_freqs[1]           AS most_common_value_frequency
FROM   pg_stats
WHERE  tablename = 'orders'
AND    attname   IN ('status', 'user_id', 'tenant_id', 'created_at', 'total')
ORDER  BY estimated_distinct_values DESC;

-- Use this to answer:
-- 1. Which columns have high cardinality? (candidates for non-leftmost placement
--    ONLY when they are always equality-filtered)
-- 2. Which columns have low cardinality? (consider partial index instead of
--    full index with low-cardinality leading column)
-- 3. correlation near 1.0: column is physically ordered similarly to heap.
--    An index scan on this column is sequential-ish → cheaper than indicated by
--    random_page_cost alone.

-- ── Slow query report combining pg_stat_statements and EXPLAIN ────────────────
-- Identify the top-5 slowest queries touching 'orders':
SELECT
    LEFT(query, 120)          AS query_snippet,
    calls,
    ROUND(mean_exec_time, 1)  AS avg_ms,
    ROUND(total_exec_time / 1000, 1) AS total_sec,
    rows / NULLIF(calls, 0)   AS avg_rows
FROM   pg_stat_statements
WHERE  query ILIKE '%orders%'
AND    mean_exec_time > 10   -- Only queries averaging > 10ms
ORDER  BY total_exec_time DESC
LIMIT  5;

-- For each slow query: run EXPLAIN (ANALYZE, BUFFERS) manually.
-- Look for:
--   "Filter" instead of "Index Cond" → column order wrong
--   "Seq Scan" → index missing entirely
--   "Rows Removed by Filter: N" where N is high → selectivity problem
--   "Heap Fetches: N" where N is high → INCLUDE columns missing or VACUUM needed
--   "Sort" → ORDER BY not matched by index order

-- ── After index redesign: measuring improvement ───────────────────────────────
SELECT pg_stat_reset();  -- Reset statistics (do this at the start of a benchmark period)
-- ... run workload for 1-2 hours ...

-- Compare before/after:
SELECT
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM   pg_stat_user_indexes
WHERE  relname = 'orders'
ORDER  BY idx_scan DESC;
-- New index should show high idx_scan and high fetch_ratio.
-- Old redundant index should show idx_scan = 0 → safe to drop.
```

## Section 9: Scenario-Based Questions

**Q13. "This query is slow even though there's an index on all the columns — what is wrong?"**

```sql
CREATE INDEX idx_orders_all ON orders(created_at, status, user_id, tenant_id);

-- Slow query:
SELECT id, user_id, total
FROM   orders
WHERE  tenant_id = 5
AND    status    = 'pending'
AND    created_at > '2024-01-01';
```

A: The index column order violates every rule simultaneously — a range column is first, and the equality columns that should lead are buried after it:

```sql
-- ── Step 1: Run EXPLAIN to confirm the diagnosis ──────────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id, total
FROM   orders
WHERE  tenant_id  = 5
AND    status     = 'pending'
AND    created_at > '2024-01-01';

-- Index Scan using idx_orders_all on orders
--   Index Cond: (created_at > '2024-01-01')         ← ONLY the range column used
--   Filter: ((tenant_id = 5) AND (status = 'pending'))  ← Both equalities are Filters!
--   Rows Removed by Filter: 2,891,432               ← Nearly 3M rows discarded
--   Buffers: shared hit=892 read=31,847

-- ── Step 2: Understand why this happens ───────────────────────────────────────
-- Index physical order: (created_at, status, user_id, tenant_id)
-- created_at is FIRST. A range on it (> 2024-01-01) is the only Index Cond.
-- Everything after a range is interleaved — status and tenant_id are scattered
-- within the matching date range.
-- The planner scans all 3M rows with created_at > Jan-1, then discards
-- those that don't match tenant_id=5 and status='pending'.

-- ── Step 3: Identify the correct order ────────────────────────────────────────
-- Rule: equality columns BEFORE range columns.
-- Query filters:
--   tenant_id = 5     → equality → goes FIRST or SECOND
--   status = 'pending' → equality → goes FIRST or SECOND
--   created_at > '2024-01-01' → range → goes LAST

-- Which equality column first? Consider:
-- a) Which is more selective? tenant_id (many tenants) vs status (5 values).
-- b) Which is always present in queries? If all queries filter by tenant_id: put it first.
-- c) Does either column have single-column queries? Create separate index if so.

-- Assuming tenant_id is always present (multi-tenant app):
CREATE INDEX idx_orders_fixed
    ON orders(tenant_id, status, created_at)
    INCLUDE (id, user_id, total);
-- Column order: tenant_id (equality, leftmost), status (equality, second),
--               created_at (range, last — correct position).
-- INCLUDE: id, user_id, total → projected columns → index-only scan possible.

-- ── Step 4: Verify the fix ────────────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id, total
FROM   orders
WHERE  tenant_id  = 5
AND    status     = 'pending'
AND    created_at > '2024-01-01';

-- Index Only Scan using idx_orders_fixed on orders
--   Index Cond: ((tenant_id = 5) AND (status = 'pending')
--                AND (created_at > '2024-01-01'))      ← ALL THREE are Index Cond ✓
--   Filter: (none)                                     ← No post-scan filter ✓
--   Rows Removed by Filter: 0
--   Heap Fetches: 0                                    ← Index-only scan ✓
--   Buffers: shared hit=12                             ← 12 pages vs 32,739 pages ✓
-- Execution Time: 0.41 ms  (was 4,231 ms — ~10,000x improvement)

-- ── Step 5: Drop the broken index ────────────────────────────────────────────
DROP INDEX CONCURRENTLY idx_orders_all;
-- idx_orders_all is now redundant and harmful (write overhead, wrong order).
```

**Q14. "Design the complete index strategy for a multi-tenant analytics API with five query patterns — justify every column position."**

A: Working through five distinct patterns against the same table demonstrates how to balance the leftmost prefix rule across competing query shapes:

```sql
-- ── Table and query patterns ──────────────────────────────────────────────────
CREATE TABLE events (
    id          BIGSERIAL    PRIMARY KEY,
    tenant_id   BIGINT       NOT NULL,   -- Always present in WHERE (multi-tenant)
    user_id     BIGINT       NOT NULL,   -- Present in ~70% of queries
    event_type  TEXT         NOT NULL,   -- 20 distinct values (medium cardinality)
    severity    TEXT         NOT NULL,   -- 4 distinct values: info/warn/error/critical
    occurred_at TIMESTAMPTZ  NOT NULL,   -- Always used as range or ORDER BY
    metadata    JSONB,                   -- Never filtered; sometimes projected
    session_id  UUID
);

-- Pattern 1 (40%): Tenant dashboard — all events for a tenant, recent first
-- SELECT id, user_id, event_type, severity, occurred_at
-- FROM events
-- WHERE tenant_id = ? AND occurred_at > NOW() - INTERVAL '7 days'
-- ORDER BY occurred_at DESC LIMIT 100

-- Pattern 2 (25%): User activity log
-- SELECT id, event_type, severity, occurred_at
-- FROM events
-- WHERE tenant_id = ? AND user_id = ? AND occurred_at > ?
-- ORDER BY occurred_at DESC LIMIT 50

-- Pattern 3 (20%): Error monitoring — errors and criticals
-- SELECT id, user_id, event_type, occurred_at
-- FROM events
-- WHERE tenant_id = ? AND severity IN ('error', 'critical') AND occurred_at > ?
-- ORDER BY occurred_at DESC LIMIT 200

-- Pattern 4 (10%): Event type breakdown
-- SELECT id, user_id, severity, occurred_at
-- FROM events
-- WHERE tenant_id = ? AND event_type = ? AND occurred_at BETWEEN ? AND ?
-- ORDER BY occurred_at DESC

-- Pattern 5 (5%): Session replay
-- SELECT id, event_type, severity, occurred_at, metadata
-- FROM events
-- WHERE tenant_id = ? AND session_id = ?
-- ORDER BY occurred_at ASC

-- ── Analysis and index design ─────────────────────────────────────────────────

-- tenant_id: in ALL patterns → always leftmost column ✓

-- Index 1: Serves patterns 1 and 2 (time-range queries)
-- Pattern 1: tenant_id (eq) → occurred_at (range) → OK (user_id not needed for P1)
-- Pattern 2: tenant_id (eq) → user_id (eq) → occurred_at (range) → all Index Cond
-- Decision: tenant_id (eq, always first), user_id (eq, often present),
--           occurred_at (range, always last)
-- Pattern 1 can use this index via prefix (tenant_id, occurred_at range)
-- but user_id is between them... problem?
-- Actually: tenant_id (eq) → user_id (eq or skipped via separate index) → occurred_at (range)
-- Pattern 1 doesn't filter on user_id — it can use (tenant_id, occurred_at) prefix
-- IF we put occurred_at second. But then Pattern 2 can't use user_id as Index Cond.
-- Solution: two indexes, one per pattern group.

CREATE INDEX CONCURRENTLY idx_events_tenant_time
    ON events(tenant_id, occurred_at DESC)
    INCLUDE (id, user_id, event_type, severity);
-- Pattern 1: tenant_id (eq) ✓ → occurred_at (range+order) ✓
-- No Filter for any P1 column.
-- Index-only scan: all projected columns in INCLUDE.

CREATE INDEX CONCURRENTLY idx_events_tenant_user_time
    ON events(tenant_id, user_id, occurred_at DESC)
    INCLUDE (id, event_type, severity);
-- Pattern 2: tenant_id (eq) ✓ → user_id (eq) ✓ → occurred_at (range+order) ✓
-- All three WHERE columns are Index Cond.
-- Index-only scan possible (id, event_type, severity in INCLUDE).

-- Index 2: Serves pattern 3 (severity filter)
-- tenant_id (eq) → severity (equality, IN clause) → occurred_at (range)
-- IN ('error', 'critical') = two equality scans, BitmapOr, then occurred_at range
CREATE INDEX CONCURRENTLY idx_events_tenant_severity_time
    ON events(tenant_id, severity, occurred_at DESC)
    INCLUDE (id, user_id, event_type);
-- Pattern 3: tenant_id (eq) ✓ → severity IN (...) ✓ → occurred_at (range) ✓
-- Partial index alternative (even smaller — only errors and criticals):
CREATE INDEX CONCURRENTLY idx_events_errors
    ON events(tenant_id, occurred_at DESC)
    INCLUDE (id, user_id, event_type, severity)
    WHERE severity IN ('error', 'critical');
-- 5x smaller than full index. Query must include WHERE severity IN ('error','critical')
-- for the planner to use this partial index.

-- Index 3: Serves pattern 4 (event_type filter with BETWEEN range)
-- tenant_id (eq) → event_type (eq) → occurred_at (range, BETWEEN = two bounds)
CREATE INDEX CONCURRENTLY idx_events_tenant_type_time
    ON events(tenant_id, event_type, occurred_at DESC)
    INCLUDE (id, user_id, severity);
-- Pattern 4: tenant_id (eq) ✓ → event_type (eq) ✓ → occurred_at BETWEEN ✓
-- BETWEEN is a range → occurred_at is last (correct).

-- Index 4: Serves pattern 5 (session_id lookup)
-- tenant_id (eq) → session_id (eq, UUID — high cardinality)
-- metadata not indexed (JSONB, use GIN separately if needed for JSON filtering)
CREATE INDEX CONCURRENTLY idx_events_tenant_session
    ON events(tenant_id, session_id, occurred_at ASC)
    INCLUDE (id, event_type, severity);
-- Pattern 5: tenant_id (eq) ✓ → session_id (eq) ✓ → occurred_at (ORDER BY ASC) ✓
-- occurred_at ASC matches ORDER BY ASC → no Sort node.

-- ── Verification: run EXPLAIN for each pattern ────────────────────────────────
-- Pattern 1:
EXPLAIN SELECT id, user_id, event_type, severity, occurred_at
FROM events WHERE tenant_id = 1 AND occurred_at > NOW() - INTERVAL '7 days'
ORDER BY occurred_at DESC LIMIT 100;
-- → Index Only Scan using idx_events_tenant_time  Heap Fetches: 0  ✓

-- Pattern 2:
EXPLAIN SELECT id, event_type, severity, occurred_at
FROM events WHERE tenant_id = 1 AND user_id = 42 AND occurred_at > NOW() - INTERVAL '30 days'
ORDER BY occurred_at DESC LIMIT 50;
-- → Index Only Scan using idx_events_tenant_user_time  Heap Fetches: 0  ✓

-- Pattern 3:
EXPLAIN SELECT id, user_id, event_type, occurred_at
FROM events WHERE tenant_id = 1 AND severity IN ('error','critical') AND occurred_at > NOW() - INTERVAL '1 day'
ORDER BY occurred_at DESC LIMIT 200;
-- → Index Only Scan using idx_events_errors (partial)  ✓

-- Pattern 4:
EXPLAIN SELECT id, user_id, severity, occurred_at
FROM events WHERE tenant_id = 1 AND event_type = 'login'
AND occurred_at BETWEEN '2024-01-01' AND '2024-01-31' ORDER BY occurred_at DESC;
-- → Index Only Scan using idx_events_tenant_type_time  Heap Fetches: 0  ✓

-- Pattern 5:
EXPLAIN SELECT id, event_type, severity, occurred_at, metadata
FROM events WHERE tenant_id = 1 AND session_id = 'uuid-here' ORDER BY occurred_at ASC;
-- → Index Scan using idx_events_tenant_session  ✓
-- (metadata is not in any index → heap fetch needed — acceptable for 5% traffic)
```

## Quick Reference Tables

### Leftmost Prefix Rule: Query Pattern → Index Usability

For index `(A, B, C)`:

| WHERE clause | Columns used as Index Cond | Remaining columns | Verdict |
|---|---|---|---|
| `A = ?` | A | B, C unused | ✓ Uses index (partial) |
| `A = ? AND B = ?` | A, B | C unused | ✓ Uses index |
| `A = ? AND B = ? AND C = ?` | A, B, C | — | ✓ Full index use |
| `A = ? AND B > ?` | A, B | C: Filter | ✓ Partial — range stops C |
| `A = ? AND B > ? AND C = ?` | A, B | C: Filter only | ✓/⚠ C wasted after range |
| `A > ?` | A | B, C: Filter | ✓ Partial — range stops B, C |
| `B = ?` | (none) | A missing | ✗ No leftmost prefix |
| `B = ? AND C = ?` | (none) | A missing | ✗ No leftmost prefix |
| `A = ? AND C = ?` | A | B missing, C: Filter | ⚠ B gap — C not used in B-tree |

### Column Ordering Decision Framework

| Situation | Correct position |
|---|---|
| Column present in ALL query patterns | Leftmost |
| Equality-filtered column | Before any range-filtered column |
| Range-filtered column | After all equality columns; last among key columns |
| Projection-only column (never in WHERE/ORDER BY) | Use `INCLUDE`, not key |
| High-cardinality among equality columns | First among equality columns (for selectivity) |
| Low-cardinality column needed alone sometimes | Consider partial index instead |
| ORDER BY column (no range filter above it) | After equality columns in same direction |
| Expression column | Must appear in WHERE in identical expression form |

### Common Mistakes and Their Fixes

| Mistake | Symptom in EXPLAIN | Fix |
|---|---|---|
| Range column before equality columns | Equality columns show as `Filter`, high `Rows Removed` | Reorder: equality → range |
| Missing leftmost column in query | Planner uses seq scan | Add missing column to WHERE, or create separate index |
| High-cardinality column buried after range | Column appears as `Filter` | Move to before the range column |
| Projection column missing from INCLUDE | `Index Scan` instead of `Index Only Scan` | Add to `INCLUDE` clause |
| Redundant prefix index | Unused index wastes write overhead | Drop the shorter prefix index |
| Mixed ORDER BY direction | `Sort` node added | Create index with matching ASC/DESC mix |
| Expression mismatch | Index not chosen for expression queries | Use exact same expression in WHERE as in index |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) explaining the **physical reason for the rule** — the B-tree is sorted lexicographically, so entries for a non-leading column are only contiguous within a fixed value of every column to its left; skipping a column leaves its entries scattered throughout the index; (2) being precise about the **range stop rule** — an equality condition on a column "exhausts" that dimension and leaves the next column's sort intact, but a range condition opens up that dimension and interleaves subsequent columns, making them unreachable as B-tree traversal conditions; (3) knowing that **cardinality ordering applies only within equality columns** and is irrelevant compared to the equality-before-range rule — placing a low-cardinality equality column after a range column is a far worse mistake than placing it last among equality columns; (4) reading `EXPLAIN` output precisely — specifically the distinction between `Index Cond` (column used in B-tree traversal) and `Filter` (column checked row-by-row after the index scan), and knowing that `Rows Removed by Filter` is the quantitative measure of how much damage a misordered column is causing; (5) knowing that **PostgreSQL does not support skip scans** (unlike MySQL) — if a leading column is missing from the WHERE clause, a new index must be created or the query rewritten; (6) understanding that `INCLUDE` columns are **not subject to the leftmost prefix rule at all** — they are payload stored only in leaf pages, available for index-only scans but useless for B-tree traversal or ORDER BY; (7) understanding the **interaction with ORDER BY** — the index eliminates a Sort node only when the ORDER BY sequence exactly matches the index's key column sequence and direction (or its exact reverse), and that LIMIT queries especially benefit because the planner can stop reading after finding the first N matching rows in index order; and (8) knowing that **multiple indexes are often better than one large composite index** for serving multiple query patterns — write amplification from N indexes is predictable and manageable, while a single misdesigned composite index serves no query well and wastes the same write overhead.
