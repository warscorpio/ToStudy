# MySQL Partitioning — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is MySQL partitioning and how does it differ architecturally from PostgreSQL partitioning?**
A: MySQL partitioning is a server-layer feature — the MySQL server routes rows to partitions before the storage engine sees them. This means partitioning is technically storage-engine-agnostic at the routing level, though InnoDB is the only engine worth using in production. PostgreSQL partitioning is implemented via table inheritance with explicit child tables. The two differ in important structural ways:

```
MySQL partitioning architecture:

  SQL Layer (MySQL Server):
    → Parses partition expression (e.g. YEAR(created_at))
    → Evaluates expression for each row on INSERT/UPDATE
    → Routes row to the correct partition number
    → On SELECT: evaluates WHERE clause → prunes partitions

  Storage Engine Layer (InnoDB):
    → Each partition is a separate InnoDB tablespace (.ibd file)
    → Each partition has its own B-tree indexes
    → Transactions span across partitions transparently

  Physical files (with innodb_file_per_table=ON, default):
    transactions.frm          ← table definition (MySQL 5.x; .sdi in 8.0)
    transactions#P#p2024_01.ibd   ← January 2024 partition data + indexes
    transactions#P#p2024_02.ibd   ← February 2024 partition data + indexes
    ...

PostgreSQL partitioning comparison:
  PG: child tables are fully independent PostgreSQL tables with separate OIDs
  PG: parent table is a routing shell with zero storage
  PG: each child can have different indexes, tablespaces, storage parameters
  MySQL: partitions share the same table definition — no per-partition DDL

Key structural differences:
  ┌──────────────────────────────┬───────────────────────┬──────────────────────┐
  │ Feature                      │ MySQL                 │ PostgreSQL           │
  ├──────────────────────────────┼───────────────────────┼──────────────────────┤
  │ Partition expression         │ Must evaluate to INT  │ Any data type        │
  │ NULL handling                │ Goes to partition p0  │ Goes to DEFAULT      │
  │ Subpartitioning              │ Supported (RANGE+HASH)│ Supported (any combo)│
  │ Per-partition indexes        │ Not supported         │ Supported            │
  │ ATTACH/DETACH without lock   │ Not supported (ALTER) │ DETACH CONCURRENTLY  │
  │ Global unique constraint     │ Partition key required│ Partition key required│
  │ INFORMATION_SCHEMA           │ PARTITIONS table      │ pg_inherits           │
  │ Maximum partitions           │ 8192 per table        │ No hard limit         │
  └──────────────────────────────┴───────────────────────┴──────────────────────┘
```

**Q2. What is the fundamental constraint on MySQL partition expressions and why does it matter?**
A: MySQL requires all partition expressions to evaluate to an integer (or NULL). Unlike PostgreSQL which can partition on any data type directly, MySQL forces you to extract or convert values to integers for the partition key. This has significant implications for how you partition on dates, strings, and composite values:

```sql
-- MySQL partition expression must return INTEGER:

-- ✓ Valid: integer column directly
PARTITION BY RANGE (id)

-- ✓ Valid: function that returns integer
PARTITION BY RANGE (YEAR(created_at))
PARTITION BY RANGE (TO_DAYS(created_at))
PARTITION BY HASH (MONTH(created_at))

-- ✗ Invalid: DATE/DATETIME directly
PARTITION BY RANGE (created_at)  -- ERROR: Field 'created_at' is of a not allowed type

-- ✗ Invalid: VARCHAR directly
PARTITION BY LIST (status)       -- ERROR: Field 'status' is of a not allowed type

-- The workaround for date ranges — use TO_DAYS() or UNIX_TIMESTAMP():
PARTITION BY RANGE (TO_DAYS(created_at))
    PARTITION p2024_01 VALUES LESS THAN (TO_DAYS('2024-02-01')),
    PARTITION p2024_02 VALUES LESS THAN (TO_DAYS('2024-03-01'));
-- TO_DAYS() converts a date to the number of days since year 0
-- TO_DAYS('2024-01-01') = 739251, TO_DAYS('2024-02-01') = 739282

-- Cleaner: RANGE COLUMNS (MySQL 5.5+) — bypasses the integer requirement:
PARTITION BY RANGE COLUMNS (created_at)
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01'),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01');
-- RANGE COLUMNS accepts DATE, DATETIME, VARCHAR, INT — no integer conversion needed
-- Also supports multi-column partition keys (unlike RANGE on a single expression)

-- Similarly: LIST COLUMNS for non-integer list values:
PARTITION BY LIST COLUMNS (status)
    PARTITION p_active   VALUES IN ('active'),
    PARTITION p_pending  VALUES IN ('pending', 'under_review'),
    PARTITION p_closed   VALUES IN ('approved', 'rejected', 'disbursed');
-- Avoids the VARCHAR restriction of plain LIST partitioning

-- The COLUMNS variants (RANGE COLUMNS, LIST COLUMNS) are almost always
-- preferable to RANGE and LIST in modern MySQL development:
-- → accept natural types (DATE, VARCHAR)
-- → no MAXVALUE keyword needed for dates (use actual date string)
-- → multi-column support
```

**Q3. What is partition pruning in MySQL and what conditions enable or disable it?**
A: Partition pruning is the optimizer's ability to skip partitions that cannot contain rows matching the WHERE clause. It is the primary performance benefit of partitioning — turning a full-table scan into a targeted single-partition scan. MySQL evaluates the partition expression against the WHERE clause at query planning time:

```sql
-- Setup:
CREATE TABLE loan_events (
    id         BIGINT UNSIGNED AUTO_INCREMENT,
    loan_id    VARCHAR(36) NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    created_at DATETIME    NOT NULL,
    payload    JSON,
    PRIMARY KEY (id, created_at)   -- partition key must be in PK
) PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01'),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01'),
    PARTITION p2024_03 VALUES LESS THAN ('2024-04-01'),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)
);

-- ✓ Pruning works — constant value in WHERE:
EXPLAIN SELECT * FROM loan_events WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
-- partitions: p2024_01    ← only January partition scanned

EXPLAIN SELECT * FROM loan_events WHERE created_at = '2024-01-15 10:30:00';
-- partitions: p2024_01

EXPLAIN SELECT * FROM loan_events WHERE created_at BETWEEN '2024-01-01' AND '2024-02-28';
-- partitions: p2024_01,p2024_02    ← two partitions

-- ✓ Pruning works — IN list:
EXPLAIN SELECT * FROM loan_events
WHERE created_at IN ('2024-01-15', '2024-03-20');
-- partitions: p2024_01,p2024_03

-- ✗ Pruning FAILS — function on partition key:
EXPLAIN SELECT * FROM loan_events WHERE YEAR(created_at) = 2024;
-- partitions: ALL    ← MySQL cannot prune — expression wraps the column
-- Fix: WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

-- ✗ Pruning FAILS — non-deterministic function:
EXPLAIN SELECT * FROM loan_events WHERE created_at > NOW() - INTERVAL 30 DAY;
-- partitions: ALL    ← NOW() evaluated at runtime, not plan time
-- Fix: compute the date in application code and use a literal:
-- WHERE created_at > '2024-06-15'  (computed by application before sending query)

-- ✗ Pruning FAILS — OR across partition keys:
EXPLAIN SELECT * FROM loan_events
WHERE created_at < '2024-01-01' OR loan_id = 'L12345';
-- partitions: ALL    ← loan_id is not partition key, OR prevents pruning

-- Verifying pruning with EXPLAIN:
EXPLAIN SELECT count(*) FROM loan_events
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'\G
-- Look for: partitions: p2024_01
-- If partitions: ALL → pruning failed → fix the WHERE clause

-- EXPLAIN PARTITIONS (older syntax, same as EXPLAIN with partitions column):
EXPLAIN PARTITIONS SELECT * FROM loan_events WHERE created_at >= '2024-01-01'\G
```

## Section 2: RANGE and RANGE COLUMNS Partitioning

**Q4. How do you implement RANGE COLUMNS partitioning for a time-series table and manage the partition lifecycle?**
A: RANGE COLUMNS is the preferred approach for time-series data in MySQL — it accepts DATE and DATETIME directly without TO_DAYS() conversion, supports natural date string bounds, and handles multi-column partition keys. Lifecycle management (creating future partitions, dropping old ones) must be done manually or via automation since MySQL has no equivalent of pg_partman:

```sql
-- Production-ready time-series table with RANGE COLUMNS:
CREATE TABLE transactions (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id   VARCHAR(36)    NOT NULL,
    loan_id     VARCHAR(36)    NOT NULL,
    amount      DECIMAL(15,2)  NOT NULL,
    status      VARCHAR(20)    NOT NULL,
    created_at  DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at),   -- created_at required in PK (partition key rule)
    INDEX idx_tenant_created (tenant_id, created_at),
    INDEX idx_loan (loan_id)
) ENGINE=InnoDB
  PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01 00:00:00'),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01 00:00:00'),
    PARTITION p2024_03 VALUES LESS THAN ('2024-04-01 00:00:00'),
    PARTITION p2024_04 VALUES LESS THAN ('2024-05-01 00:00:00'),
    PARTITION p2024_05 VALUES LESS THAN ('2024-06-01 00:00:00'),
    PARTITION p2024_06 VALUES LESS THAN ('2024-07-01 00:00:00'),
    PARTITION p2024_07 VALUES LESS THAN ('2024-08-01 00:00:00'),
    PARTITION p2024_08 VALUES LESS THAN ('2024-09-01 00:00:00'),
    PARTITION p2024_09 VALUES LESS THAN ('2024-10-01 00:00:00'),
    PARTITION p2024_10 VALUES LESS THAN ('2024-11-01 00:00:00'),
    PARTITION p2024_11 VALUES LESS THAN ('2024-12-01 00:00:00'),
    PARTITION p2024_12 VALUES LESS THAN ('2025-01-01 00:00:00'),
    PARTITION p_future  VALUES LESS THAN (MAXVALUE)    -- catch-all for future data
);

-- ── Adding a new partition (before data arrives) ─────────────────────────────
-- Cannot add a partition at the end when MAXVALUE exists — must REORGANIZE:
ALTER TABLE transactions REORGANIZE PARTITION p_future INTO (
    PARTITION p2025_01 VALUES LESS THAN ('2025-02-01 00:00:00'),
    PARTITION p_future  VALUES LESS THAN (MAXVALUE)
);
-- REORGANIZE splits p_future into a named January 2025 partition + new p_future
-- InnoDB moves zero rows (p_future was empty) → instant if no data in p_future
-- If p_future has data: MySQL must redistribute it → can be slow → do before data arrives

-- Without MAXVALUE — cleaner lifecycle management:
-- Use explicit partitions only, add new ones at the end:
ALTER TABLE transactions ADD PARTITION (
    PARTITION p2025_01 VALUES LESS THAN ('2025-02-01 00:00:00')
);
-- Simple ADD PARTITION works when there is no MAXVALUE catch-all
-- Tradeoff: INSERTs with created_at beyond all defined partitions → ERROR
-- Must create partitions proactively before data arrives

-- Automation (stored procedure called by an Event Scheduler):
DELIMITER //
CREATE PROCEDURE add_next_month_partition()
BEGIN
    DECLARE next_month_start DATETIME;
    DECLARE next_month_end   DATETIME;
    DECLARE partition_name   VARCHAR(20);

    SET next_month_start = DATE_FORMAT(NOW() + INTERVAL 1 MONTH, '%Y-%m-01');
    SET next_month_end   = DATE_FORMAT(NOW() + INTERVAL 2 MONTH, '%Y-%m-01');
    SET partition_name   = CONCAT('p', DATE_FORMAT(NOW() + INTERVAL 1 MONTH, '%Y_%m'));

    -- Check if partition already exists:
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.PARTITIONS
        WHERE TABLE_SCHEMA = DATABASE()
          AND TABLE_NAME = 'transactions'
          AND PARTITION_NAME = partition_name
    ) THEN
        SET @sql = CONCAT(
            'ALTER TABLE transactions REORGANIZE PARTITION p_future INTO (',
            'PARTITION ', partition_name, ' VALUES LESS THAN (''', next_month_end, '''),',
            'PARTITION p_future VALUES LESS THAN (MAXVALUE)',
            ')'
        );
        PREPARE stmt FROM @sql;
        EXECUTE stmt;
        DEALLOCATE PREPARE stmt;
    END IF;
END //
DELIMITER ;

-- Schedule via MySQL Event Scheduler:
CREATE EVENT evt_add_partition
    ON SCHEDULE EVERY 1 MONTH
    STARTS '2024-12-01 00:00:00'
    DO CALL add_next_month_partition();

-- ── Dropping old partitions (archival) ───────────────────────────────────────
-- Dropping a partition in MySQL: instant, no DELETE scan, no VACUUM
ALTER TABLE transactions DROP PARTITION p2022_01;
-- Removes the .ibd file for p2022_01 — all data in that partition is gone
-- Much faster than: DELETE FROM transactions WHERE created_at < '2022-02-01'

-- Archiving before dropping (export to CSV):
SELECT * FROM transactions PARTITION (p2022_01)
INTO OUTFILE '/var/lib/mysql-files/transactions_2022_01.csv'
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n';
-- Then: ALTER TABLE transactions DROP PARTITION p2022_01;

-- Exchanging partition with a standalone table (for archival without locking):
CREATE TABLE transactions_archive_2022_01 LIKE transactions;
-- Remove partitioning from the archive table:
ALTER TABLE transactions_archive_2022_01 REMOVE PARTITIONING;
-- Exchange: swaps the data between partition and standalone table (fast, minimal lock):
ALTER TABLE transactions EXCHANGE PARTITION p2022_01
    WITH TABLE transactions_archive_2022_01;
-- Now p2022_01 is empty; transactions_archive_2022_01 has the data
-- Can DROP PARTITION p2022_01 (empty, instant)
-- Can move transactions_archive_2022_01 to cold storage or another server
ALTER TABLE transactions DROP PARTITION p2022_01;
```

**Q5. What is the RANGE partitioning (non-COLUMNS) and when does it still apply?**

```sql
-- RANGE (integer expression) — older form, still used when:
-- 1. Partitioning on integer IDs (AUTO_INCREMENT primary keys)
-- 2. Legacy codebases on MySQL 5.1 (RANGE COLUMNS was added in 5.5)
-- 3. When a specific integer expression is natural (YEAR(), MONTH())

-- RANGE on AUTO_INCREMENT ID (horizontal sharding by ID range):
CREATE TABLE loan_applications (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    borrower_id VARCHAR(36)    NOT NULL,
    amount      DECIMAL(15,2)  NOT NULL,
    status      VARCHAR(20)    NOT NULL,
    created_at  DATETIME       NOT NULL,
    PRIMARY KEY (id)   -- id alone can be PK for RANGE on id
) ENGINE=InnoDB
  PARTITION BY RANGE (id) (
    PARTITION p0 VALUES LESS THAN (1000000),
    PARTITION p1 VALUES LESS THAN (2000000),
    PARTITION p2 VALUES LESS THAN (3000000),
    PARTITION p_max VALUES LESS THAN MAXVALUE
);
-- Use case: older rows (low IDs) queried less often → move them to slower storage
-- New rows always go to p_max → hot data in the latest partition

-- RANGE on YEAR(date) — common for yearly archival:
CREATE TABLE audit_logs (
    id         BIGINT UNSIGNED AUTO_INCREMENT,
    entity_id  VARCHAR(36) NOT NULL,
    action     VARCHAR(50) NOT NULL,
    created_at DATE NOT NULL,
    PRIMARY KEY (id, created_at)
) ENGINE=InnoDB
  PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2021 VALUES LESS THAN (2022),
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
-- Simple: one partition per year, easy to understand
-- Coarse: cannot drop a single month — only entire year
-- Pruning: WHERE YEAR(created_at) = 2024 → FAILS (function wraps column)
-- Fix:     WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01' → prunes p2024

-- RANGE on TO_DAYS() — monthly granularity without RANGE COLUMNS:
CREATE TABLE events (
    id         BIGINT UNSIGNED AUTO_INCREMENT,
    event_date DATE NOT NULL,
    data       VARCHAR(255),
    PRIMARY KEY (id, event_date)
) ENGINE=InnoDB
  PARTITION BY RANGE (TO_DAYS(event_date)) (
    PARTITION p2024_01 VALUES LESS THAN (TO_DAYS('2024-02-01')),
    PARTITION p2024_02 VALUES LESS THAN (TO_DAYS('2024-03-01')),
    PARTITION p_future  VALUES LESS THAN MAXVALUE
);
-- TO_DAYS('2024-02-01') = 739282 (evaluated at CREATE TABLE time, stored as constant)
-- Pruning: WHERE event_date >= '2024-01-01' AND event_date < '2024-02-01' → works
-- Why prefer RANGE COLUMNS instead:
--   RANGE COLUMNS ('2024-02-01') is more readable than RANGE (TO_DAYS(...))
--   RANGE COLUMNS handles DATETIME (not just DATE)
--   RANGE COLUMNS does not require function evaluation
```

## Section 3: LIST and LIST COLUMNS Partitioning

**Q6. How does LIST COLUMNS partitioning work in MySQL and what are its production use cases?**
A: LIST COLUMNS partitioning assigns rows to partitions based on exact value membership in a defined list. It is the right choice when the partition key is categorical and discrete — region, status, tenant tier, country code. Unlike PostgreSQL's LIST partitioning, MySQL requires every possible value to be explicitly assigned to a partition or handled via a DEFAULT partition (MySQL 8.0+):

```sql
-- LIST COLUMNS partitioning by region:
CREATE TABLE loan_applications (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id   VARCHAR(36)    NOT NULL,
    region      VARCHAR(20)    NOT NULL,
    borrower_id VARCHAR(36)    NOT NULL,
    amount      DECIMAL(15,2)  NOT NULL,
    status      VARCHAR(20)    NOT NULL DEFAULT 'draft',
    created_at  DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, region)   -- region in PK (partition key requirement)
) ENGINE=InnoDB
  PARTITION BY LIST COLUMNS (region) (
    PARTITION p_north   VALUES IN ('north', 'north_east', 'north_west'),
    PARTITION p_south   VALUES IN ('south', 'south_east', 'south_west'),
    PARTITION p_central VALUES IN ('central', 'west'),
    PARTITION p_other   VALUES IN ('unknown', 'overseas')
);

-- No DEFAULT in MySQL 5.x: INSERT with unlisted region → ERROR
-- MySQL 8.0+: can add a DEFAULT partition:
-- PARTITION p_default DEFAULT  ← catches any value not in other lists

-- Query with partition pruning:
EXPLAIN SELECT * FROM loan_applications WHERE region = 'north'\G
-- partitions: p_north

EXPLAIN SELECT * FROM loan_applications WHERE region IN ('north', 'south')\G
-- partitions: p_north,p_south

-- Multi-value LIST COLUMNS (composite key):
CREATE TABLE events (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    country     CHAR(2)  NOT NULL,
    event_type  VARCHAR(30) NOT NULL,
    created_at  DATETIME NOT NULL,
    PRIMARY KEY (id, country, event_type)
) ENGINE=InnoDB
  PARTITION BY LIST COLUMNS (country, event_type) (
    PARTITION p_in_loan   VALUES IN (('IN', 'LOAN_CREATED'), ('IN', 'LOAN_APPROVED')),
    PARTITION p_in_kyc    VALUES IN (('IN', 'KYC_SUBMITTED'), ('IN', 'KYC_APPROVED')),
    PARTITION p_us_loan   VALUES IN (('US', 'LOAN_CREATED'), ('US', 'LOAN_APPROVED')),
    PARTITION p_other     VALUES IN (('IN', 'OTHER'), ('US', 'OTHER'))
);
-- Each partition maps to a specific (country, event_type) combination
-- Very granular — typically only useful when both columns always appear in WHERE

-- Adding a new value to a LIST partition (if an existing partition covers it):
ALTER TABLE loan_applications REORGANIZE PARTITION p_other INTO (
    PARTITION p_other   VALUES IN ('unknown', 'overseas'),
    PARTITION p_digital VALUES IN ('digital', 'fintech')
);
-- REORGANIZE moves any existing rows in p_other that match the new values
-- to p_digital (usually none if 'digital' is a new value)

-- LIST COLUMNS for status partitioning:
CREATE TABLE loan_lifecycle (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    loan_id     VARCHAR(36)    NOT NULL,
    status      VARCHAR(20)    NOT NULL,
    updated_at  DATETIME       NOT NULL,
    PRIMARY KEY (id, status)
) ENGINE=InnoDB
  PARTITION BY LIST COLUMNS (status) (
    PARTITION p_active  VALUES IN ('draft', 'submitted', 'under_review', 'approved'),
    PARTITION p_funded  VALUES IN ('disbursed', 'repaying'),
    PARTITION p_closed  VALUES IN ('fully_repaid', 'rejected', 'cancelled', 'written_off')
);
-- p_active: hot, frequently queried, needs fast index scans
-- p_closed: cold, infrequently queried, candidate for slower tablespace
-- Pruning: WHERE status = 'approved' → p_active only
```

## Section 4: HASH and KEY Partitioning

**Q7. What is the difference between HASH and KEY partitioning in MySQL, and when does each apply?**
A: MySQL has two hash-based partitioning variants. HASH uses a user-defined expression (must evaluate to integer); KEY uses MySQL's internal hashing function (works on any column type including VARCHAR and DATE). KEY is generally preferred because it avoids the integer-expression constraint and is computed by MySQL's own algorithm:

```sql
-- HASH partitioning (user-defined integer expression):
CREATE TABLE audit_logs (
    id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    entity_id BIGINT UNSIGNED NOT NULL,
    action    VARCHAR(50)    NOT NULL,
    logged_at DATETIME       NOT NULL,
    PRIMARY KEY (id, entity_id)
) ENGINE=InnoDB
  PARTITION BY HASH (entity_id)
  PARTITIONS 8;
-- Routes row to: partition = entity_id % 8
-- entity_id=1 → partition 1
-- entity_id=9 → partition 1 (same bucket)
-- entity_id=8 → partition 0

-- HASH with an expression:
PARTITION BY HASH (YEAR(logged_at))
PARTITIONS 4;
-- Routes: YEAR(logged_at) % 4
-- 2024 % 4 = 0, 2023 % 4 = 3, 2022 % 4 = 2, 2021 % 4 = 1
-- Distribution is uneven if years are not evenly distributed

-- KEY partitioning (MySQL internal hash function):
CREATE TABLE user_sessions (
    session_id VARCHAR(64)  NOT NULL,
    user_id    VARCHAR(36)  NOT NULL,
    data       JSON,
    expires_at DATETIME     NOT NULL,
    PRIMARY KEY (session_id)
) ENGINE=InnoDB
  PARTITION BY KEY (session_id)
  PARTITIONS 16;
-- MySQL hashes session_id (VARCHAR — impossible with plain HASH)
-- Internal MD5-like hash → uniform distribution
-- No integer conversion needed

-- KEY with no explicit column (uses PRIMARY KEY):
PARTITION BY KEY()
PARTITIONS 8;
-- Uses the PRIMARY KEY column(s) automatically
-- Equivalent to PARTITION BY KEY (pk_column) PARTITIONS 8

-- HASH vs KEY comparison:
-- ┌──────────────────────────────┬───────────────────┬───────────────────────┐
-- │ Property                     │ HASH              │ KEY                   │
-- ├──────────────────────────────┼───────────────────┼───────────────────────┤
-- │ Expression type              │ Integer only      │ Any type              │
-- │ User-defined expression      │ Yes               │ No (MySQL handles it) │
-- │ Distribution                 │ Depends on expr   │ Uniform (internal hash│
-- │ Pruning support              │ Equality only     │ Equality only         │
-- │ Use with VARCHAR/UUID        │ No (need cast)    │ Yes (native)          │
-- │ LINEAR variant               │ LINEAR HASH       │ LINEAR KEY            │
-- └──────────────────────────────┴───────────────────┴───────────────────────┘

-- LINEAR HASH / LINEAR KEY (faster partition management, less uniform distribution):
PARTITION BY LINEAR HASH (entity_id) PARTITIONS 8;
PARTITION BY LINEAR KEY  (user_id)   PARTITIONS 16;
-- LINEAR uses powers-of-2 algorithm:
--   Adding/dropping partitions is faster (only some rows need to move)
--   Tradeoff: less uniform distribution than standard HASH/KEY
-- Use LINEAR when: partition count changes frequently (adding partitions)

-- Hash pruning — equality only:
EXPLAIN SELECT * FROM audit_logs WHERE entity_id = 42\G
-- partitions: p2  (42 % 8 = 2 → only p2 scanned)

EXPLAIN SELECT * FROM audit_logs WHERE entity_id > 40\G
-- partitions: ALL  (range on hash key → no pruning possible)
-- Hash partitioning does NOT help range queries
```

**Q8. What is the repartitioning problem with HASH/KEY partitioning in MySQL and how do you mitigate it?**

```sql
-- The repartitioning problem:
-- Changing partition count (e.g. 4 → 8) requires rebuilding the entire table
-- All rows must be rehashed and redistributed
-- For a 500GB table: can take hours, requires significant I/O

-- MySQL repartitioning: ALTER TABLE ... PARTITION BY HASH (...) PARTITIONS 8;
-- This is a full table rebuild (not instant)
-- MySQL 5.6+: online DDL can perform this without a full table lock
--   but still requires the full data copy operation

-- Adding partitions to HASH:
ALTER TABLE audit_logs ADD PARTITION PARTITIONS 4;
-- Adds 4 more partitions (total: 8+4=12)
-- MySQL must redistribute some rows from existing partitions to new ones
-- For standard HASH: many rows move (proportion: 4/12 of data)
-- For LINEAR HASH: fewer rows move (only those that fall in new buckets)

-- Coalescing partitions (reducing count):
ALTER TABLE audit_logs COALESCE PARTITION 4;
-- Reduces by 4 partitions (12 → 8)
-- Some rows from removed partitions moved to remaining ones
-- LINEAR HASH: fewer rows to move

-- Mitigation strategies:

-- 1. Choose partition count generously upfront:
-- If you expect 8-16 concurrent writers, start with 16
-- Empty partitions cost almost nothing (tiny .ibd file)
-- Much better than repartitioning later

-- 2. Use powers of 2 for easier scaling:
PARTITION BY LINEAR HASH (entity_id) PARTITIONS 8;
-- Adding 8 more → 16 total → LINEAR HASH minimizes redistribution

-- 3. Sub-partitioning for incremental scaling:
-- Start with 4 HASH partitions
-- When volume grows: add HASH sub-partitioning to each partition
-- Avoids full table rebuild of the top-level partitions

-- 4. Application-level sharding as alternative:
-- For extreme scale: shard at application layer (separate tables/schemas per shard)
-- More operational complexity but no repartitioning problem

-- Checking partition distribution (are partitions even?):
SELECT
    partition_name,
    table_rows,
    avg_row_length,
    data_length / 1024 / 1024 AS data_mb
FROM information_schema.PARTITIONS
WHERE table_schema = 'mydb'
  AND table_name = 'audit_logs'
ORDER BY partition_name;
-- Large variance in table_rows → uneven distribution → consider different hash expression
```

## Section 5: Subpartitioning

**Q9. How does MySQL subpartitioning work and what combinations are supported?**
A: MySQL supports subpartitioning (composite partitioning) where each partition of a RANGE or LIST table is further divided by HASH or KEY. This allows double pruning — first on the range/list, then on the hash — and improves write parallelism within each time slice or category:

```sql
-- Subpartitioning: RANGE COLUMNS + KEY
-- Each month's data is split into 4 KEY sub-partitions by tenant_id
-- → pruning by date + hash distribution by tenant_id

CREATE TABLE transactions (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id   VARCHAR(36)    NOT NULL,
    amount      DECIMAL(15,2)  NOT NULL,
    created_at  DATETIME       NOT NULL,
    PRIMARY KEY (id, tenant_id, created_at)  -- all partition keys in PK
) ENGINE=InnoDB
  PARTITION BY RANGE COLUMNS (created_at)
  SUBPARTITION BY KEY (tenant_id)
  SUBPARTITIONS 4
  (
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01'),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01'),
    PARTITION p2024_03 VALUES LESS THAN ('2024-04-01'),
    PARTITION p_future  VALUES LESS THAN (MAXVALUE)
  );

-- Physical files created:
-- transactions#P#p2024_01#SP#p2024_01sp0.ibd  ← Jan, key bucket 0
-- transactions#P#p2024_01#SP#p2024_01sp1.ibd  ← Jan, key bucket 1
-- transactions#P#p2024_01#SP#p2024_01sp2.ibd  ← Jan, key bucket 2
-- transactions#P#p2024_01#SP#p2024_01sp3.ibd  ← Jan, key bucket 3
-- transactions#P#p2024_02#SP#p2024_02sp0.ibd  ← Feb, key bucket 0
-- ... (4 partitions × 4 subpartitions = 16 total .ibd files)

-- Query pruning with subpartitioning:
EXPLAIN SELECT * FROM transactions
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'
  AND tenant_id = 'T1'\G
-- partitions: p2024_01_p2024_01sp2  (only Jan partition, only T1's hash bucket)
-- → 1 of 16 partitions scanned

-- Subpartitioning rules:
-- ✓ RANGE + HASH subpartitions
-- ✓ RANGE + KEY subpartitions
-- ✓ LIST + HASH subpartitions
-- ✓ LIST + KEY subpartitions
-- ✗ HASH + anything (HASH cannot be the top-level for subpartitioning)
-- ✗ KEY + anything

-- Named subpartitions (for per-subpartition options like tablespace):
PARTITION BY RANGE COLUMNS (created_at)
SUBPARTITION BY HASH (TO_DAYS(created_at))
(
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01') (
        SUBPARTITION p2024_01_a,
        SUBPARTITION p2024_01_b,
        SUBPARTITION p2024_01_c,
        SUBPARTITION p2024_01_d
    ),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01') (
        SUBPARTITION p2024_02_a,
        SUBPARTITION p2024_02_b,
        SUBPARTITION p2024_02_c,
        SUBPARTITION p2024_02_d
    )
);

-- Total partition count consideration:
-- 12 months × 8 subpartitions = 96 .ibd files
-- Each open .ibd file: ~8KB of OS file descriptor + InnoDB buffer pool header
-- max_connections × 96 partitions × file_open_cache → watch open file limits
-- Stay below 1024 total partitions in most production deployments
```

## Section 6: Constraints and Limitations

**Q10. What are the most impactful MySQL partitioning constraints that differ from PostgreSQL?**
A: MySQL's partitioning has several hard constraints that PostgreSQL does not have. Knowing these prevents painful surprises when designing partitioned schemas. The most critical are the primary key constraint, the lack of foreign keys on partitioned tables, and the NULL routing behavior:

```sql
-- ── Constraint 1: Partition key MUST be in PRIMARY KEY and UNIQUE indexes ──────

-- This FAILS:
CREATE TABLE loans (
    id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,  -- PK doesn't include created_at
    loan_id    VARCHAR(36) NOT NULL,
    created_at DATETIME NOT NULL
) PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01')
);
-- ERROR 1503: A PRIMARY KEY must include all columns in the table's
-- partitioning function (prefixed columns are not considered).

-- This WORKS:
CREATE TABLE loans (
    id         BIGINT UNSIGNED AUTO_INCREMENT,
    loan_id    VARCHAR(36) NOT NULL,
    created_at DATETIME    NOT NULL,
    PRIMARY KEY (id, created_at)   -- created_at included in PK
) PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01'),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)
);

-- Same rule applies to UNIQUE constraints:
-- If you have UNIQUE (loan_id), must change to UNIQUE (loan_id, created_at)
-- This means the UNIQUE constraint no longer prevents duplicates across partitions
-- for the same loan_id in different time periods (loan_id='L1' could exist in p2024 and p2025)

-- Workaround for global uniqueness:
-- Option A: Include created_at in the unique index (weakens uniqueness semantics)
-- Option B: Use a separate lookup table (non-partitioned) for global unique keys:
CREATE TABLE loan_id_registry (
    loan_id    VARCHAR(36) PRIMARY KEY,   -- globally unique, non-partitioned
    created_at DATETIME NOT NULL,
    INDEX (created_at)
);
-- Application inserts into loan_id_registry first (to enforce uniqueness),
-- then inserts into the partitioned loans table

-- ── Constraint 2: No FOREIGN KEY support on partitioned tables ─────────────────
-- Neither referencing (FK pointing TO a partitioned table)
-- nor referenced (FK on a partitioned table pointing somewhere) is supported

-- This FAILS:
CREATE TABLE loan_events (
    id      BIGINT UNSIGNED AUTO_INCREMENT,
    loan_id VARCHAR(36) NOT NULL,
    -- ...
    PRIMARY KEY (id, loan_id),
    FOREIGN KEY (loan_id) REFERENCES loans(loan_id)  -- ERROR on partitioned loans table
) PARTITION BY RANGE COLUMNS (created_at) (...);

-- ERROR 1506: Foreign keys are not yet supported in conjunction with partitioning

-- Workaround: enforce referential integrity at application level
-- Or: use a non-partitioned reference table + partitioned data table
-- Or: switch to CHECK constraints + application-layer validation

-- ── Constraint 3: NULL values go to the FIRST partition (RANGE/LIST) ───────────
-- PostgreSQL: NULLs go to the DEFAULT partition
-- MySQL: NULLs treated as:
--   RANGE: NULL < any value → goes to the first (lowest) partition
--   LIST: NULL goes to a partition that explicitly lists NULL in VALUES IN (NULL)
--         If no partition lists NULL → ERROR
--   HASH/KEY: NULL hashes to partition 0

-- Example:
CREATE TABLE events (
    id      BIGINT UNSIGNED AUTO_INCREMENT,
    event_date DATE,    -- nullable!
    PRIMARY KEY (id, event_date)   -- NULL in primary key: bad practice
) PARTITION BY RANGE (TO_DAYS(event_date)) (
    PARTITION p_null_and_old VALUES LESS THAN (TO_DAYS('2020-01-01')),  -- NULL goes here!
    PARTITION p2020 VALUES LESS THAN (TO_DAYS('2021-01-01')),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
-- INSERT with event_date=NULL → goes to p_null_and_old (NULL < all)
-- This is confusing and error-prone — avoid nullable partition keys

-- ── Constraint 4: Partition expression must be deterministic ───────────────────
-- Cannot use: NOW(), RAND(), CURRENT_DATE, USER(), non-deterministic UDFs
-- Can use: deterministic functions (YEAR(), MONTH(), TO_DAYS(), ABS(), etc.)
-- Cannot use: subqueries in partition expression

-- ── Constraint 5: ALTER TABLE locks the table (no CONCURRENTLY option) ──────────
-- PostgreSQL: ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY (minimal lock)
-- MySQL: Most partition maintenance operations lock the table:
--   ADD PARTITION: typically fast if MAXVALUE reorganize is avoided
--   DROP PARTITION: instant (removes .ibd file) — no table lock in MySQL 5.6+
--   REORGANIZE PARTITION: table copy → long lock for large partitions
--   TRUNCATE PARTITION: fast (like DROP+recreate), row-level locks
-- Use pt-online-schema-change or gh-ost for zero-downtime schema changes

-- Checking partition metadata:
SELECT
    PARTITION_NAME,
    PARTITION_METHOD,
    PARTITION_EXPRESSION,
    PARTITION_DESCRIPTION,
    TABLE_ROWS,
    DATA_LENGTH / 1024 / 1024 AS data_mb,
    INDEX_LENGTH / 1024 / 1024 AS index_mb
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = 'mydb'
  AND TABLE_NAME = 'transactions'
ORDER BY PARTITION_ORDINAL_POSITION;
```

## Section 7: Indexes on Partitioned Tables

**Q11. How do indexes work on MySQL partitioned tables and what limitations exist compared to PostgreSQL?**
A: MySQL only supports local indexes on partitioned tables — each partition has its own copy of every index. There are no global indexes spanning all partitions. This means non-partition-key lookups must search every partition's index. PostgreSQL has the same limitation for declarative partitioning but the implications are worth knowing precisely for MySQL:

```sql
-- All indexes in MySQL partitioned tables are LOCAL (per-partition):
CREATE TABLE loan_events (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    loan_id     VARCHAR(36)    NOT NULL,
    event_type  VARCHAR(50)    NOT NULL,
    created_at  DATETIME       NOT NULL,
    PRIMARY KEY (id, created_at),
    INDEX idx_loan_id (loan_id),            -- local: one index per partition
    INDEX idx_event_type (event_type)       -- local: one index per partition
) PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2024_01 VALUES LESS THAN ('2024-02-01'),
    PARTITION p2024_02 VALUES LESS THAN ('2024-03-01'),
    PARTITION p_future  VALUES LESS THAN (MAXVALUE)
);

-- Query on partition key + indexed column (fast):
EXPLAIN SELECT * FROM loan_events
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'
  AND loan_id = 'L12345'\G
-- partitions: p2024_01        ← pruned to one partition
-- type: ref                   ← uses idx_loan_id within p2024_01 only
-- rows: ~10                   ← examines small number of rows

-- Query on non-partition-key (searches all partitions):
EXPLAIN SELECT * FROM loan_events WHERE loan_id = 'L12345'\G
-- partitions: p2024_01,p2024_02,p_future   ← ALL partitions searched
-- type: ref                                 ← uses idx_loan_id in EACH partition
-- rows: ~10 × N_partitions                 ← multiplied by partition count

-- The performance implication:
-- 24 monthly partitions: loan_id lookup = 24 index scans merged
-- Each scan is fast (index is small per partition) but 24 scans vs 1 global scan
-- For a loan with 5 events in one month: 24 × 5 = 120 index entries examined vs 5
-- For SMALL result sets: multiple small index scans often still faster than one
--   large global index scan on a huge table (better cache utilization)
-- For LARGE result sets across many partitions: can be slower

-- Workaround for frequent non-partition-key lookups:

-- Option 1: Add the non-partition-key to a composite index with a narrow range:
-- Query pattern: find all events for a loan in last 3 months
-- WHERE loan_id='L1' AND created_at >= NOW() - INTERVAL 3 MONTH
-- Add index: (loan_id, created_at)
-- Prunes to last 3 months' partitions (3 scans) + loan_id index within each
CREATE INDEX idx_loan_created ON loan_events (loan_id, created_at);

-- Option 2: Separate lookup table (non-partitioned) for loan_id → partition mapping:
CREATE TABLE loan_event_index (
    loan_id    VARCHAR(36) NOT NULL,
    event_id   BIGINT UNSIGNED NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (loan_id, created_at, event_id)  -- non-partitioned, global
);
-- On INSERT to loan_events: also INSERT to loan_event_index
-- Loan history query: SELECT created_at FROM loan_event_index WHERE loan_id='L1'
--   → then SELECT * FROM loan_events WHERE id=? AND created_at=? (partition-pruned)

-- Option 3: Application-level date range requirement:
-- Enforce that all queries include a created_at range → partition pruning always works
-- WHERE loan_id='L1' AND created_at >= '2024-01-01' (application always adds this)

-- Checking index usage per partition:
-- MySQL does not expose per-partition index stats directly in standard tables
-- Use EXPLAIN to check type and key columns for partition-key queries
-- Use pt-query-digest to find slow queries hitting all partitions
```

## Section 8: Operational Concerns

**Q12. How do you perform partition maintenance operations safely in production MySQL?**

```sql
-- ── TRUNCATE PARTITION (fast row removal without dropping the partition): ──────
-- Removes all rows from a partition instantly (like TRUNCATE TABLE but scoped)
-- Much faster than DELETE WHERE (no row-by-row delete + undo log)
ALTER TABLE transactions TRUNCATE PARTITION p2022_01;
-- Partition p2022_01 still exists (empty) — ready for new data if the range is reused
-- This is faster than DROP + ADD PARTITION if you plan to reuse the partition

-- ── REBUILD PARTITION (defragment, like OPTIMIZE TABLE per partition): ──────────
ALTER TABLE transactions REBUILD PARTITION p2024_01;
-- Rebuilds the .ibd file for p2024_01 — removes fragmentation, reclaims space
-- Can run during low-traffic windows
-- MySQL 5.7+: InnoDB can do this online with --online=true (pt-online-schema-change)

-- ── ANALYZE PARTITION (update statistics): ───────────────────────────────────
ALTER TABLE transactions ANALYZE PARTITION p2024_01;
-- Updates InnoDB statistics for p2024_01 → better query plans
-- ANALYZE ALL PARTITIONS:
ALTER TABLE transactions ANALYZE PARTITION ALL;

-- ── OPTIMIZE PARTITION (combines ANALYZE + REBUILD): ──────────────────────────
ALTER TABLE transactions OPTIMIZE PARTITION p2024_01;
-- Equivalent to REBUILD + ANALYZE — reclaims space and updates stats

-- ── EXCHANGE PARTITION (production archival, minimal lock): ────────────────────
-- Create archive table with same schema but NO partitioning:
CREATE TABLE transactions_archive_2022_01 LIKE transactions;
ALTER TABLE transactions_archive_2022_01 REMOVE PARTITIONING;

-- Exchange: swaps data between partition and archive table (fast, brief lock):
ALTER TABLE transactions EXCHANGE PARTITION p2022_01
    WITH TABLE transactions_archive_2022_01;
-- After: p2022_01 is empty; transactions_archive_2022_01 has the 2022 January data

-- Verify exchange:
SELECT COUNT(*) FROM transactions PARTITION (p2022_01);       -- 0
SELECT COUNT(*) FROM transactions_archive_2022_01;           -- N (original row count)

-- Drop the now-empty partition:
ALTER TABLE transactions DROP PARTITION p2022_01;

-- Move archive to cold storage (separate server or tablespace):
-- Or: export to CSV, then DROP TABLE

-- ── REMOVE PARTITIONING (convert back to regular table): ──────────────────────
ALTER TABLE transactions REMOVE PARTITIONING;
-- Merges all partitions into a single non-partitioned InnoDB table
-- Full table rebuild — can take a long time on large tables
-- Use pt-online-schema-change for zero-downtime version

-- ── Monitoring partition health: ──────────────────────────────────────────────

-- Row distribution across partitions:
SELECT
    PARTITION_NAME,
    TABLE_ROWS,
    ROUND(DATA_LENGTH / 1024 / 1024, 2)  AS data_mb,
    ROUND(INDEX_LENGTH / 1024 / 1024, 2) AS index_mb,
    CREATE_TIME,
    UPDATE_TIME
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = 'production'
  AND TABLE_NAME   = 'transactions'
ORDER BY PARTITION_ORDINAL_POSITION;

-- Find queries hitting all partitions (missing pruning):
-- Enable slow query log + long_query_time=0 temporarily
-- Or use performance_schema:
SELECT
    digest_text,
    count_star,
    avg_timer_wait / 1000000000 AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
WHERE digest_text LIKE '%transactions%'
  AND avg_timer_wait > 1000000000  -- > 1 second
ORDER BY avg_timer_wait DESC
LIMIT 20;
-- Run EXPLAIN on slow queries → check partitions column → fix WHERE clauses
```

## Section 9: Scenario-Based Questions

**Q13. "A MySQL `loan_events` table has grown to 800M rows over 3 years. Historical queries for last 30 days are fast, but cross-year analytics take 5 minutes. Implement partitioning with zero downtime."**

```sql
-- Strategy: create a new partitioned table, migrate data in batches, swap tables

-- Step 1: Create the new partitioned table:
CREATE TABLE loan_events_partitioned (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    loan_id     VARCHAR(36)    NOT NULL,
    event_type  VARCHAR(50)    NOT NULL,
    created_at  DATETIME       NOT NULL,
    payload     JSON,
    PRIMARY KEY (id, created_at),
    INDEX idx_loan_created (loan_id, created_at),
    INDEX idx_event_type   (event_type, created_at)
) ENGINE=InnoDB
  PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2021_h1  VALUES LESS THAN ('2021-07-01'),
    PARTITION p2021_h2  VALUES LESS THAN ('2022-01-01'),
    PARTITION p2022_q1  VALUES LESS THAN ('2022-04-01'),
    PARTITION p2022_q2  VALUES LESS THAN ('2022-07-01'),
    PARTITION p2022_q3  VALUES LESS THAN ('2022-10-01'),
    PARTITION p2022_q4  VALUES LESS THAN ('2023-01-01'),
    PARTITION p2023_01  VALUES LESS THAN ('2023-02-01'),
    -- ... monthly for recent years
    PARTITION p2024_01  VALUES LESS THAN ('2024-02-01'),
    PARTITION p2024_02  VALUES LESS THAN ('2024-03-01'),
    PARTITION p_future   VALUES LESS THAN (MAXVALUE)
);
-- Older data: quarterly partitions (coarser, less management overhead)
-- Recent data: monthly partitions (finer, faster pruning for recent queries)

-- Step 2: Migrate data in batches (background, production still writing to old table):
-- Use pt-archive or a custom script:
INSERT INTO loan_events_partitioned
SELECT * FROM loan_events
WHERE id BETWEEN 1 AND 10000000;    -- first 10M rows

INSERT INTO loan_events_partitioned
SELECT * FROM loan_events
WHERE id BETWEEN 10000001 AND 20000000;
-- Repeat, advancing the range
-- Run at low-traffic hours; throttle with SLEEP(0.1) between batches

-- Step 3: Set up dual-write trigger during migration:
DELIMITER //
CREATE TRIGGER sync_loan_events_insert
AFTER INSERT ON loan_events
FOR EACH ROW
BEGIN
    INSERT INTO loan_events_partitioned
    VALUES (NEW.id, NEW.loan_id, NEW.event_type, NEW.created_at, NEW.payload)
    ON DUPLICATE KEY UPDATE
        loan_id = NEW.loan_id;   -- no-op if already migrated
END //
DELIMITER ;

-- Step 4: Verify row counts match:
SELECT COUNT(*) FROM loan_events;                -- original
SELECT COUNT(*) FROM loan_events_partitioned;   -- should match after full migration

-- Step 5: Atomic table swap (brief application pause — seconds):
-- Application: enable maintenance mode (stop writes)
-- Or: use RENAME TABLE (atomic in MySQL):
RENAME TABLE
    loan_events TO loan_events_old,
    loan_events_partitioned TO loan_events;
-- Both renames happen atomically — no window where the table is missing
-- Drop the sync trigger (now on loan_events_old, which is being retired):
DROP TRIGGER sync_loan_events_insert;

-- Step 6: Verify queries and query plans:
EXPLAIN SELECT * FROM loan_events
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'\G
-- partitions: p2024_01  ← only January scanned

-- Step 7: Monitor then drop old table:
-- After 1-2 weeks of confirmed correct operation:
DROP TABLE loan_events_old;
```

**Q14. "Your team wants to use MySQL partitioning for multi-tenant isolation with 200 enterprise tenants. Design the schema and partition strategy."**

```sql
-- Analysis:
-- 200 enterprise tenants → 200 LIST partitions (upper limit but manageable)
-- Each tenant: 1M-10M rows → significant per-tenant volume
-- Queries: always filtered by tenant_id (SaaS pattern)
-- Compliance: tenant data must be deletable instantly (GDPR right to erasure)

-- Design: LIST COLUMNS by tenant_id

CREATE TABLE loan_applications (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id   VARCHAR(36)    NOT NULL,
    borrower_id VARCHAR(36)    NOT NULL,
    amount      DECIMAL(15,2)  NOT NULL,
    status      VARCHAR(20)    NOT NULL,
    loan_type   VARCHAR(30)    NOT NULL,
    created_at  DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, tenant_id),
    INDEX idx_tenant_status_created (tenant_id, status, created_at),
    INDEX idx_tenant_borrower       (tenant_id, borrower_id),
    INDEX idx_created               (created_at)
) ENGINE=InnoDB
  PARTITION BY LIST COLUMNS (tenant_id) (
    PARTITION p_tenant_t001 VALUES IN ('tenant-uuid-001'),
    PARTITION p_tenant_t002 VALUES IN ('tenant-uuid-002'),
    -- ... one per tenant
    PARTITION p_tenant_t200 VALUES IN ('tenant-uuid-200'),
    PARTITION p_new_tenants DEFAULT   -- MySQL 8.0+: catch new tenants
);

-- Query pruning for all tenant queries:
EXPLAIN SELECT * FROM loan_applications
WHERE tenant_id = 'tenant-uuid-001'
  AND status = 'pending'\G
-- partitions: p_tenant_t001   ← only this tenant's partition
-- type: ref                   ← uses idx_tenant_status_created

-- GDPR right to erasure: instant tenant data deletion:
ALTER TABLE loan_applications DROP PARTITION p_tenant_t099;
-- Removes all data for tenant-uuid-099 instantly (no DELETE scan, no VACUUM)
-- Returns the storage to the OS immediately

-- Adding a new enterprise tenant from the shared pool:
-- 1. Create data for new tenant in p_new_tenants (DEFAULT catches them)
-- 2. When tenant grows: assign dedicated partition
ALTER TABLE loan_applications REORGANIZE PARTITION p_new_tenants INTO (
    PARTITION p_tenant_t201 VALUES IN ('tenant-uuid-201'),
    PARTITION p_new_tenants DEFAULT
);
-- MySQL scans p_new_tenants and moves tenant-uuid-201's rows to the new partition

-- Limitations to communicate:
-- 1. No FK to/from partitioned table → enforce relationships in application
-- 2. UNIQUE constraints must include tenant_id
--    (business uniqueness like "one active loan per borrower" must include tenant_id)
-- 3. 200 partitions × all indexes → many open .ibd files
--    Set: open_files_limit and innodb_open_files to accommodate
--    SHOW VARIABLES LIKE 'open_files_limit';  -- should be > 200 × 3 (indexes)

-- For smaller tenants (1000s of SMB tenants):
-- Do NOT use per-tenant partitions → too many partitions
-- Use: tenant_id column + index + Row-level security at application layer
-- Partitioning by tenant only works when tenant count is bounded and manageable
```

**Q15. "A MySQL partitioned table's ALTER TABLE to add a partition is blocking production writes for 30 seconds. How do you fix this?"**

```sql
-- Root cause analysis:
-- ALTER TABLE transactions REORGANIZE PARTITION p_future INTO (...)
-- REORGANIZE requires:
--   - MDL (Metadata Lock) on the table → blocks all DML during the lock acquisition
--   - Data redistribution if p_future has rows

-- Why REORGANIZE blocks:
-- MySQL must rebuild the affected partitions
-- For ADD PARTITION (without MAXVALUE): instant — new empty .ibd created
-- For REORGANIZE (splitting p_future): must move rows from p_future to new partition
--   If p_future is empty: near-instant
--   If p_future has data: full data copy → minutes or longer

-- Fix 1: Create partitions BEFORE data arrives (proactive creation):
-- If p_future is always empty at the time of REORGANIZE → instant operation
-- Schedule partition creation 1 month in advance:
-- (same stored procedure from Q4 — called monthly via Event Scheduler)
-- When REORGANIZE runs on empty p_future: creates new partition + new empty p_future
-- ~milliseconds, not 30 seconds

-- Fix 2: Use ADD PARTITION instead of REORGANIZE (when no MAXVALUE catch-all):
-- Remove MAXVALUE partition:
ALTER TABLE transactions DROP PARTITION p_future;
-- Then simply ADD PARTITION at the end:
ALTER TABLE transactions ADD PARTITION (
    PARTITION p2025_01 VALUES LESS THAN ('2025-02-01 00:00:00')
);
-- ADD PARTITION on an existing table (no MAXVALUE): instant — just adds empty .ibd
-- Tradeoff: any INSERT with created_at beyond all defined partitions → ERROR
-- Must proactively create partitions before they are needed

-- Fix 3: pt-online-schema-change for ALTER that cannot be done online:
pt-online-schema-change \
    --alter "REORGANIZE PARTITION p_future INTO (
        PARTITION p2025_01 VALUES LESS THAN ('2025-02-01'),
        PARTITION p_future VALUES LESS THAN (MAXVALUE)
    )" \
    --host=primary \
    --database=mydb \
    --table=transactions \
    --execute
-- pt-osc creates a shadow table, copies data, syncs with triggers, swaps names
-- Zero write downtime (trigger-based sync during the swap)
-- Slower overall but does not block production

-- Fix 4: gh-ost (GitHub's online schema change tool):
gh-ost \
    --alter="REORGANIZE PARTITION p_future INTO (...)" \
    --host=replica \
    --database=mydb \
    --table=transactions \
    --execute
-- gh-ost uses binlog streaming instead of triggers → less write overhead than pt-osc
-- More complex to set up but preferred for high-write tables

-- Fix 5: Check MDL wait timeout (prevent long blocking):
SET SESSION lock_wait_timeout = 5;    -- wait at most 5s for MDL → fail fast
SET SESSION innodb_lock_wait_timeout = 5;
-- If ALTER cannot acquire lock within 5s → ERROR, not silent 30s block
-- Better to fail fast and retry at a lower-traffic moment

-- Prevention: monitor p_future row count:
SELECT TABLE_ROWS FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA='mydb' AND TABLE_NAME='transactions' AND PARTITION_NAME='p_future';
-- Alert if TABLE_ROWS > 0 (data is leaking into p_future before new partition is created)
-- This is a signal that partition creation automation has failed
```

## Quick Reference Table

| Partition type | Expression type | Pruning supports | Best for | Cannot do |
|---|---|---|---|---|
| RANGE (int expr) | Integer only | `<`, `>`, `BETWEEN` | Integer IDs, YEAR() expressions | DATE/VARCHAR directly |
| RANGE COLUMNS | Any (DATE, VARCHAR, INT) | `<`, `>`, `BETWEEN`, multi-column | Time-series (preferred over RANGE) | Non-deterministic functions |
| LIST (int expr) | Integer only | `=`, `IN (...)` | Integer category codes | VARCHAR categories |
| LIST COLUMNS | Any (VARCHAR, DATE, INT) | `=`, `IN (...)`, multi-column | Region, status, tenant (preferred) | High-cardinality values |
| HASH (int expr) | Integer expression | `=` only | Integer IDs, even distribution | Range queries, VARCHAR |
| KEY (any column) | Any (internal hash) | `=` only | UUID, VARCHAR keys, even distribution | Range queries, repartitioning |
| LINEAR HASH/KEY | Any (power-of-2 hash) | `=` only | Frequent partition count changes | Uniform distribution |

| Operation | MySQL | Notes |
|---|---|---|
| Add partition (no MAXVALUE) | `ALTER TABLE ... ADD PARTITION (...)` | Instant — new empty .ibd |
| Add partition (with MAXVALUE) | `ALTER TABLE ... REORGANIZE PARTITION p_future INTO (...)` | Fast if p_future empty; slow if not |
| Drop partition | `ALTER TABLE ... DROP PARTITION pname` | Instant — removes .ibd file |
| Truncate partition | `ALTER TABLE ... TRUNCATE PARTITION pname` | Fast — empties without dropping |
| Swap partition for archival | `ALTER TABLE ... EXCHANGE PARTITION pname WITH TABLE archive` | Brief lock, very fast |
| Archive data | `EXCHANGE` then `DROP PARTITION` | Zero-downtime archival pattern |
| Remove partitioning | `ALTER TABLE ... REMOVE PARTITIONING` | Full table rebuild — use pt-osc |
| Change partition count (HASH) | `ALTER TABLE ... PARTITIONS N` | Full rebuild — plan upfront |

| MySQL vs PostgreSQL | MySQL | PostgreSQL |
|---|---|---|
| Partition expression | Must return integer (except COLUMNS variants) | Any data type |
| NULL routing | First partition (RANGE/LIST) | DEFAULT partition |
| Foreign keys | Not supported on partitioned tables | Supported (v12+, with restrictions) |
| Per-partition indexes | Not supported | Supported |
| Global unique constraint | Partition key must be in unique index | Partition key must be in unique index |
| Default isolation level | REPEATABLE READ | READ COMMITTED |
| Detach without lock | Not supported | `DETACH CONCURRENTLY` (v14+) |
| Maximum partitions | 8192 | No hard limit |

**Tip for interviews:** Five things separate strong candidates on MySQL partitioning: (1) knowing that **MySQL partition expressions must return integers, and that RANGE COLUMNS / LIST COLUMNS bypass this restriction** (Q2) — and being able to say why RANGE COLUMNS is almost always preferable to RANGE with TO_DAYS() because it accepts DATE/DATETIME natively, is more readable, and supports multi-column keys; (2) knowing the **partition key must appear in every UNIQUE index and PRIMARY KEY** (Q10) — this is the most common mistake when designing partitioned schemas in MySQL, and the consequence is that business-level uniqueness constraints (e.g. one loan per borrower) must include the partition key, weakening their enforcement to within-partition scope; (3) explaining **partition pruning failure conditions precisely** (Q3) — wrapping the partition key in a function (e.g. `YEAR(created_at)`) defeats pruning even when the underlying column would prune correctly, and the fix is to rewrite the WHERE clause as a range comparison on the raw column; (4) knowing that **MySQL has no global indexes on partitioned tables** (Q11) — every non-partition-key lookup searches all partitions' local indexes, and the mitigation strategies (composite index including partition key, secondary lookup table, application-enforced date range requirement) demonstrate production awareness; and (5) understanding the **REORGANIZE PARTITION vs ADD PARTITION distinction for lifecycle management** (Q15) — REORGANIZE is needed when a MAXVALUE catch-all partition exists and must be split, is fast only when the catch-all is empty, and the correct production pattern is proactive partition creation before data arrives so the REORGANIZE always touches an empty partition.
