### Section 1: Why Distributed Locks Exist

**Q1. What problem does a distributed lock solve and when do you actually need one?**
A: A distributed lock ensures that across multiple processes, servers, or containers, **at most one holder executes a critical section at a time**. It is the distributed equivalent of a mutex — but far harder to implement correctly because networks partition, clocks drift, processes pause, and nodes crash without clean notification.

```
Single-process concurrency:
  Thread A ──┐
             ├── mutex.lock() → critical section → mutex.unlock()
  Thread B ──┘
  OS guarantees: threads share memory; lock state is authoritative

Distributed concurrency (the hard version):
  Server A (us-east-1) ──┐
                          ├── ??? → critical section → release
  Server B (eu-west-1) ──┘
  Problem: no shared memory; network may delay/drop messages;
           Server A may pause (GC) for 30s without any signal to Server B;
           clocks on A and B may drift by hundreds of milliseconds

When you need a distributed lock:
  ✓ Exactly one server should process a given job (cron deduplication)
  ✓ Preventing double-charge in payment processing
  ✓ Ensuring exactly one replica runs a migration at startup
  ✓ Resource allocation (assigning a unique slot/seat to a user)
  ✓ Leader election (simplified: "who owns this task right now?")

When you DON'T need a distributed lock (better alternatives exist):
  ✗ Just need idempotency → use idempotency keys in your DB instead
  ✗ Preventing duplicate DB writes → use unique constraints (DB handles it)
  ✗ Rate limiting → use Redis counters (INCR) or token bucket
  ✗ Leader election for long-running processes → use etcd leases or ZooKeeper
  ✗ Sequencing writes → use optimistic locking (version/etag in DB)
```

**Q2. What is the single-node Redis lock pattern, why is `SETNX` + `EXPIRE` wrong, and what is the correct implementation?**
A: The correct single-node Redis lock requires **one atomic command**: `SET key token NX PX ttl`. Using two separate commands (`SETNX` then `EXPIRE`) creates a race condition where the process can crash between the two — leaving a lock with no expiry (deadlock forever).

```python
import uuid, time, redis

r = redis.Redis(decode_responses=True)

# ── WRONG: two commands, not atomic ───────────────────────────────────
def acquire_lock_wrong(resource: str, ttl_ms: int) -> str | None:
    lock_id = str(uuid.uuid4())
    acquired = r.setnx(f"lock:{resource}", lock_id)   # set only if not exists
    if acquired:
        r.expire(f"lock:{resource}", ttl_ms // 1000)  # ← RACE: crash here = no expiry!
        return lock_id
    return None
# If the process dies between SETNX and EXPIRE:
# → lock key exists with NO expiry → locked forever until manual deletion

# ── CORRECT: single atomic command ────────────────────────────────────
def acquire_lock(resource: str, ttl_ms: int) -> str | None:
    lock_id = str(uuid.uuid4())   # unique token to identify THIS lock holder
    key     = f"lock:{resource}"

    # SET key value NX PX ttl
    # NX:  only set if key does Not eXist (atomic check-and-set)
    # PX:  expiry in milliseconds (auto-expire prevents deadlock on crash)
    acquired = r.set(key, lock_id, nx=True, px=ttl_ms)
    return lock_id if acquired else None
# Atomic: either both set AND expiry happen, or neither

# ── CORRECT release: must verify ownership before deleting ────────────
RELEASE_SCRIPT = """
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
"""
# Lua script is atomic — no other command can run between GET and DEL
# This prevents releasing another holder's lock (e.g., after our lock expired
# and someone else acquired it, we must not delete their lock)

def release_lock(resource: str, lock_id: str) -> bool:
    key    = f"lock:{resource}"
    result = r.eval(RELEASE_SCRIPT, 1, key, lock_id)
    return result == 1
# Returns True if we successfully released OUR lock
# Returns False if lock had already expired or was held by someone else

# ── Full usage pattern ────────────────────────────────────────────────
def with_lock(resource: str, ttl_ms: int, fn: callable):
    lock_id = acquire_lock(resource, ttl_ms)
    if lock_id is None:
        raise LockNotAcquiredError(f"Could not acquire lock on {resource}")
    try:
        return fn()
    finally:
        release_lock(resource, lock_id)

# Why the unique token matters:
# Scenario without token (just SET lock:payment 1 NX PX 5000):
# T=0:   Server A acquires lock (lock:payment = 1, expires T=5s)
# T=4.9: Server A starts payment processing
# T=5.0: Lock expires! (A paused due to GC)
# T=5.1: Server B acquires the lock (lock:payment = 1)
# T=5.2: Server A finishes, does DEL lock:payment → deletes B's lock!
# T=5.3: Server C acquires the lock → now A AND C both think they hold it

# With unique token:
# T=5.2: Server A runs RELEASE_SCRIPT: GET lock:payment → returns B's token, not A's
#        → script returns 0 → A knows it lost the lock → A aborts the operation
```

### Section 2: The Redlock Algorithm

**Q3. What is the Redlock algorithm and why does single-node Redis locking fail?**
A: Single-node Redis locking has one fundamental weakness: **the Redis node itself is a single point of failure**. If the Redis master crashes after granting a lock but before the lock key is replicated to the replica, and the replica is promoted to master, the new master has no record of the lock — another client can acquire it. **Two clients simultaneously hold the same lock**.

```
Single-node failure scenario:
  T=0: Client A acquires lock on Redis master (SET lock:pay token-A NX PX 30000)
  T=1: Redis master crashes — lock:pay has NOT been replicated to replica
  T=2: Replica is promoted to master (empty — no lock key)
  T=3: Client B acquires lock on new master (SET lock:pay token-B NX PX 30000)
  T=4: Both Client A and Client B believe they hold the lock!
       → double processing, data corruption

Redlock solution:
  Run N independent Redis instances (typically N=5, no replication between them)
  Acquire lock on MAJORITY (≥ N/2+1) of instances
  A lock is only "held" if acquired on a majority → no single node failure can cause
  both sides to independently reach a majority
```

The Redlock algorithm (as specified by Salvatore Sanfilippo, Redis creator):

```
Given N Redis instances (recommended: N=5, all independent):

1. Record the start time T1 in milliseconds

2. Try to acquire the lock on ALL N instances sequentially:
   - Use same key name and same unique random token on every instance
   - Use a short timeout per instance (much less than lock TTL)
     e.g., for 10s lock TTL → 5-50ms timeout per instance
   - If instance doesn't respond within timeout: immediately move to next

3. After attempting all N instances, record current time T2

4. Compute elapsed = T2 - T1

5. The lock is considered ACQUIRED only if:
   a. At least N/2+1 instances (majority) responded with success, AND
   b. elapsed < lock TTL (there's still meaningful validity time remaining)
   actual_validity_time = lock TTL - elapsed - clock_drift_factor

6. If the lock was acquired:
   → Use the lock for actual_validity_time duration only
   → Do NOT use it for the full TTL (subtract acquisition time)

7. If the lock was NOT acquired (< majority or timed out):
   → Release the lock on ALL instances (including ones that said "acquired")
   → Wait a random delay before retrying (prevent thundering herd)
   → Retry or fail

Algorithm properties:
  Safety:     At most one client holds the lock at any time (with quorum)
  Liveness:   Eventually acquires if the majority of instances are available
  Fault tolerance: Survives failure of ⌊N/2⌋ instances (e.g., 2 of 5)
```

**Q4. Walk through the Redlock algorithm with a concrete 5-node example, showing what happens when two nodes fail.**
A:

```
Setup: 5 Redis instances: R1, R2, R3, R4, R5
Lock TTL: 10,000ms (10 seconds)
Per-instance timeout: 50ms
Clock drift safety factor: 200ms (estimated max drift)

Client A attempts to acquire:
  T=0ms:   Try R1 → acquired (reply in 2ms)
  T=2ms:   Try R2 → acquired (reply in 3ms)
  T=5ms:   Try R3 → timeout (R3 is down, wait 50ms)
  T=55ms:  Try R4 → acquired (reply in 4ms)
  T=59ms:  Try R5 → acquired (reply in 3ms)
  T=62ms:  Total elapsed = 62ms

Results:
  Successes: R1, R2, R4, R5 = 4 of 5 (majority: ≥3) ✓
  Elapsed: 62ms < 10,000ms ✓
  actual_validity = 10,000 - 62 - 200 = 9,738ms

  Lock ACQUIRED. Client A may use it for 9,738ms.

Client B attempts simultaneously (slight delay):
  T=1ms:   Try R1 → FAILED (R1 already has Client A's lock)
  T=3ms:   Try R2 → FAILED
  T=6ms:   Try R3 → timeout (R3 is down)
  T=56ms:  Try R4 → FAILED
  T=60ms:  Try R5 → FAILED

Results:
  Successes: 0 of 5 (minority) ✗
  Lock NOT ACQUIRED.
  Client B releases any partial locks (none in this case) and retries after random delay.

Why 2 failures is the limit for N=5:
  With 2 failures: 3 nodes available, need 3 (majority) → barely possible
  With 3 failures: 2 nodes available, need 3 (majority) → impossible
  Formula: can tolerate ⌊N/2⌋ failures
  N=3: tolerates 1 failure; N=5: tolerates 2; N=7: tolerates 3

Why N must be ODD:
  Even N=4: majority = 3; tolerate 1 failure (2 failures → 2 nodes = can't reach 3)
            N=4 tolerates same failures as N=3 but costs more instances
  Odd N=5:  majority = 3; tolerates 2 failures — better than N=4 at same cost (in terms of
            failure tolerance: N=5 > N=4 > N=3 in practice)

What "independent" means for N instances:
  → Different physical machines (not VMs on same host)
  → Different power supplies (different racks)
  → Different network paths (different switches)
  → No replication between them (replication creates shared fate)
  → Ideally in different data centers or availability zones
```

**Q5. What is the correct per-instance acquisition timeout in Redlock and why?**
A: The per-instance timeout must be **much smaller than the lock TTL** — the default suggestion is a small fraction (e.g., 5–10% of TTL). If the timeout is too large, acquiring the lock takes too long relative to its validity time.

```python
# Relationship between TTL, timeout, and validity:

lock_ttl_ms      = 10_000  # 10 seconds total lock validity
per_instance_timeout_ms = 50  # 5ms is good for local network; 50ms for WAN

# Worst case acquisition time (all N instances either respond or timeout):
# N instances × per_instance_timeout = 5 × 50ms = 250ms
# Actual validity = 10,000 - 250 - clock_drift = ~9,700ms

# If per_instance_timeout is too large (e.g., 2000ms):
# Worst case = 5 × 2000ms = 10,000ms
# Actual validity = 10,000 - 10,000 - clock_drift = NEGATIVE → can't acquire

# Clock drift factor (why subtract it):
# Real machines have NTP-corrected clocks but still drift between corrections
# Redis can't freeze time during XADD — the key's TTL is based on server clock
# Typical NTP correction: ±100ms; conservative safety margin: 200-300ms
# clock_drift = max_drift * N_instances + redis_command_processing_overhead

CLOCK_DRIFT_FACTOR = 0.01   # 1% of TTL as clock drift allowance
DRIFT_CONSTANT_MS  = 2      # 2ms constant for Redis command overhead

def actual_validity(ttl_ms: int, elapsed_ms: int) -> int:
    drift = int(ttl_ms * CLOCK_DRIFT_FACTOR) + DRIFT_CONSTANT_MS
    return ttl_ms - elapsed_ms - drift
# If validity ≤ 0: lock NOT considered acquired even if majority succeeded
```

### Section 3: The Redlock Controversy

**Q6. What is Martin Kleppmann's critique of Redlock and is he correct?**
A: In 2016, Martin Kleppmann published "How to do distributed locking" arguing that Redlock is **unsafe for correctness-critical systems** due to two scenarios that the algorithm cannot prevent: GC pauses and clock jumps. His argument is important and partially correct — but applies to a specific class of use cases.

```
Kleppmann's Scenario 1 — GC pause:

  T=0:   Client A acquires Redlock (5 of 5 nodes) → lock valid for 10s
  T=1:   Client A's JVM triggers a Stop-The-World GC pause
  T=11:  GC finishes. Client A resumes. 10 SECONDS have passed.
         Client A's lock has EXPIRED on all Redis nodes.
  T=11:  Client B acquires the same Redlock (5 of 5 nodes)
  T=11:  Client A is still running, has NOT checked if its lock expired
         Client A accesses the shared resource simultaneously with Client B
         → DATA CORRUPTION

Kleppmann's Scenario 2 — Clock jump:

  Redlock step 3: check if elapsed < TTL
  This relies on the local monotonic clock for timing.

  But the Redis server's TTL is based on ITS clock.
  If Redis server R2's clock jumps forward by 5 seconds (due to NTP correction):
  → R2's locks expire 5 seconds early
  → The lock "held" by Client A may have already expired on R2
  → Client B can now acquire R2's slot
  → With 3 of 5 nodes acquired (original 3: R1, R3, R4 minus R2 due to expiry)
     Client B can claim majority...

Antirez's (Redis creator's) response:
  "Redlock is designed to provide mutual exclusion in environments where
   it's fine to have brief windows of non-mutual exclusion during extreme
   system events (GC pauses, clock jumps, node failures)."
  He argues:
  → GC pauses of 10+ seconds are application-level bugs (fix your JVM tuning)
  → Clock jumps are infrastructure-level bugs (fix your NTP configuration)
  → Redlock is still correct for "efficiency" locks (preventing duplicate work)
    but NOT for "correctness" locks (preventing data corruption absolutely)

The practical verdict:
  Redlock provides PROBABILISTIC safety, not MATHEMATICAL safety.
  Use Redlock for:
    ✓ Preventing duplicate job processing (double-processing is costly but recoverable)
    ✓ Rate limiting (bounded by clock drift, not critical)
    ✓ Cache stampede prevention (lock expires → fallback → not catastrophic)
    ✓ Resource allocation where brief conflicts are detectable and recoverable

  Do NOT use Redlock (without fencing tokens) for:
    ✗ Financial transactions where double-processing = double-charge (unrecoverable)
    ✗ Database schema migrations (idempotency is hard to guarantee)
    ✗ File system operations that must be atomic across services
```

**Q7. What is a fencing token and how does it address the GC-pause problem that Redlock cannot?**
A: A fencing token is a **monotonically increasing number** issued with the lock. Every operation performed under the lock sends the fencing token to the resource being protected. The resource rejects any operation with a token **older than the last seen token** — even if the lock-holder believes it still holds the lock.

```
Fencing token sequence diagram:

  Lock Service (etcd/ZooKeeper/DB)
       ↑ issues token=33 to Client A
       ↑ issues token=34 to Client B (after A's lease expired)

  Client A ─── acquires lock ─→ gets token=33
  Client A ─── GC pause (15s) ────────────────────────────────────────
  Client B ─── acquires lock (A's expired) ─→ gets token=34
  Client B ─── writes to storage with token=34 ─→ Storage: max_token=34, ✓ accepted
  Client A ─── resumes ─→ writes to storage with token=33
             Storage: 33 < 34 (max_token) → ✗ REJECTED
             Client A gets an error → aborts the operation
             Data integrity preserved!

Without fencing tokens (Redlock only):
  Client A ─── GC pause (15s) ──────────────────────
  Client A's lock expires, Client B acquires it
  Client A ─── resumes, doesn't know lock expired ─→ writes to storage → ✓ ACCEPTED
  Client B ─── also writes to storage → ✓ ACCEPTED
  Both writes committed → corruption!

Why Redlock can't provide fencing tokens:
  Fencing tokens require a monotonically increasing counter.
  Redis can provide this (INCR is atomic) but Redlock doesn't define this.
  Even if you add INCR to the Redlock implementation:
  → The counter must come from a SINGLE authoritative source
  → But Redlock deliberately avoids a single source (that's the whole point)
  → Two Redis nodes could independently issue the same counter value

Where fencing tokens come from:
  ZooKeeper:  zxid (ZooKeeper Transaction ID) — monotonic across all writes
  etcd:       revision (Raft log index) — monotonic across cluster
  PostgreSQL: sequence + advisory lock — monotonic per database
  These systems have true consensus and provide real monotonic tokens.

Implementation:
  # Storage side: reject stale writes
  def write_with_fence(data: dict, token: int) -> bool:
      current_max = db.get("max_lock_token")
      if token < current_max:
          raise StaleOperationError(f"Token {token} rejected; max seen = {current_max}")
      db.set("max_lock_token", token)
      db.write(data)
      return True

  # Correct answer: if you need fencing tokens, use etcd or ZooKeeper, not Redis
```

**Q8. When is Redlock the right tool and when should you use etcd or ZooKeeper instead?**
A:

```
Decision framework:

  Question 1: Does BRIEF mutual exclusion failure cause UNRECOVERABLE harm?
    YES → etcd or ZooKeeper (true consensus, fencing tokens, monotonic guarantees)
    NO  → Redlock may be sufficient (brief overlap is detectable/recoverable)

  Question 2: Is the protected operation IDEMPOTENT?
    YES → Redlock is much safer (GC pause → duplicate = same result = safe)
    NO  → Need fencing tokens (strong consistency required)

  Question 3: What are your infrastructure constraints?
    Already have Redis → Redlock (simple, no new infra)
    Already have etcd/Consul (Kubernetes) → use their lease mechanisms
    Need correctness > convenience → ZooKeeper or etcd with Raft

  Use Redlock for:                    Use etcd/ZooKeeper for:
  ──────────────────────────────────  ──────────────────────────────────────
  Cron job deduplication              Financial transaction serialization
  Cache stampede prevention           Database schema migration locks
  Email/SMS send-once (idempotent)    Leader election (long-lived processes)
  Job queue deduplication             Distributed coordination with history
  Feature rollout gates               Correctness-critical resource allocation
  Rate limiting (approximate OK)      Any operation needing fencing tokens

etcd vs ZooKeeper:
  etcd:       Raft consensus; HTTP/gRPC API; cloud-native; Kubernetes default
              Lease mechanism (like distributed lock with TTL)
              Revision number = fencing token
  ZooKeeper:  ZAB consensus; Java; mature; sequential znodes = fencing tokens
              Ephemeral znodes: auto-deleted when client session ends (crash-safe)
              More complex to operate; common in Kafka, HBase ecosystems
```

### Section 4: Implementing Redlock

**Q9. What does a production-quality Redlock implementation look like and what edge cases must it handle?**
A:

```python
import uuid, time, redis, logging
from contextlib import contextmanager
from dataclasses import dataclass

log = logging.getLogger(__name__)

@dataclass
class LockAcquisitionResult:
    acquired:        bool
    lock_id:         str
    validity_ms:     int           # actual remaining validity time
    succeeded_nodes: list[int]     # indices of nodes where lock was set
    elapsed_ms:      int

class RedlockManager:
    # Redlock constants (per algorithm specification):
    CLOCK_DRIFT_FACTOR = 0.01      # 1% of TTL as safety margin
    DRIFT_CONSTANT_MS  = 2         # 2ms constant overhead per acquire
    RETRY_DELAY_BASE   = 200       # ms base delay between retries
    RETRY_DELAY_JITTER = 100       # ms random jitter (reduces thundering herd)

    def __init__(self, nodes: list[dict], quorum: int | None = None):
        """
        nodes: list of Redis connection kwargs, e.g.:
          [{'host': 'redis1', 'port': 6379},
           {'host': 'redis2', 'port': 6379},
           {'host': 'redis3', 'port': 6379}]
        quorum: minimum nodes to acquire (default: majority = N//2 + 1)
        """
        self.clients = [redis.Redis(**node, decode_responses=True,
                                    socket_timeout=0.05,     # 50ms timeout per node
                                    socket_connect_timeout=0.05)
                        for node in nodes]
        self.N       = len(nodes)
        self.quorum  = quorum or (self.N // 2 + 1)

        if self.N < 3:
            raise ValueError("Redlock requires at least 3 Redis nodes")
        if self.N % 2 == 0:
            log.warning("Even number of Redis nodes reduces fault tolerance; use odd N")

    # Lua script for atomic check-and-delete (safe release):
    RELEASE_SCRIPT = """
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
    """

    def _try_acquire_on_node(
        self, client: redis.Redis, key: str, lock_id: str, ttl_ms: int
    ) -> bool:
        try:
            return client.set(key, lock_id, nx=True, px=ttl_ms) is not None
        except redis.RedisError as e:
            log.warning(f"Failed to acquire lock on node: {e}")
            return False   # treat node error as "not acquired" on this node

    def _try_release_on_node(
        self, client: redis.Redis, key: str, lock_id: str
    ) -> bool:
        try:
            result = client.eval(self.RELEASE_SCRIPT, 1, key, lock_id)
            return result == 1
        except redis.RedisError as e:
            log.warning(f"Failed to release lock on node: {e}")
            return False

    def _drift(self, ttl_ms: int) -> int:
        return int(ttl_ms * self.CLOCK_DRIFT_FACTOR) + self.DRIFT_CONSTANT_MS

    def acquire(
        self,
        resource:     str,
        ttl_ms:       int,
        retry_count:  int = 3,
        retry_delay_ms: int | None = None,
    ) -> LockAcquisitionResult:
        key     = f"redlock:{resource}"
        lock_id = str(uuid.uuid4())

        for attempt in range(retry_count):
            if attempt > 0:
                # Wait before retry with jitter to prevent thundering herd:
                import random
                delay = (retry_delay_ms or self.RETRY_DELAY_BASE) + \
                        random.randint(0, self.RETRY_DELAY_JITTER)
                time.sleep(delay / 1000)

            start_ms = int(time.monotonic() * 1000)  # monotonic clock (not wall clock)

            # Step 2: Try to acquire on ALL nodes:
            succeeded_nodes = []
            for i, client in enumerate(self.clients):
                if self._try_acquire_on_node(client, key, lock_id, ttl_ms):
                    succeeded_nodes.append(i)

            # Step 3 & 4: Check quorum and remaining validity:
            elapsed_ms = int(time.monotonic() * 1000) - start_ms
            validity   = ttl_ms - elapsed_ms - self._drift(ttl_ms)

            if len(succeeded_nodes) >= self.quorum and validity > 0:
                log.debug(
                    f"Redlock acquired: resource={resource}, "
                    f"quorum={len(succeeded_nodes)}/{self.N}, "
                    f"validity={validity}ms, attempt={attempt+1}"
                )
                return LockAcquisitionResult(
                    acquired=True, lock_id=lock_id,
                    validity_ms=validity, succeeded_nodes=succeeded_nodes,
                    elapsed_ms=elapsed_ms
                )

            # Step 7: Failed — release on ALL nodes (even ones that didn't respond):
            log.warning(
                f"Redlock not acquired: resource={resource}, "
                f"quorum={len(succeeded_nodes)}/{self.N} (need {self.quorum}), "
                f"validity={validity}ms, attempt={attempt+1}/{retry_count}"
            )
            self._release_all(key, lock_id)

        return LockAcquisitionResult(
            acquired=False, lock_id=lock_id,
            validity_ms=0, succeeded_nodes=[],
            elapsed_ms=0
        )

    def _release_all(self, key: str, lock_id: str) -> None:
        # Release in parallel would be better; sequential for simplicity here:
        for i, client in enumerate(self.clients):
            released = self._try_release_on_node(client, key, lock_id)
            log.debug(f"Released lock on node {i}: {released}")

    def release(self, resource: str, lock_id: str) -> int:
        key      = f"redlock:{resource}"
        released = sum(
            1 for client in self.clients
            if self._try_release_on_node(client, key, lock_id)
        )
        log.debug(f"Released Redlock on {released}/{self.N} nodes")
        return released

    @contextmanager
    def lock(
        self,
        resource:       str,
        ttl_ms:         int,
        retry_count:    int = 3,
        retry_delay_ms: int | None = None,
    ):
        """Context manager for automatic release."""
        result = self.acquire(resource, ttl_ms, retry_count, retry_delay_ms)
        if not result.acquired:
            raise LockNotAcquiredError(
                f"Could not acquire Redlock on '{resource}' after {retry_count} attempts"
            )
        try:
            yield result    # caller receives LockAcquisitionResult (has validity_ms, lock_id)
        finally:
            self.release(resource, result.lock_id)

class LockNotAcquiredError(Exception):
    pass

# ── Usage ──────────────────────────────────────────────────────────────
redlock = RedlockManager(nodes=[
    {"host": "redis1.internal", "port": 6379},
    {"host": "redis2.internal", "port": 6379},
    {"host": "redis3.internal", "port": 6379},
    {"host": "redis4.internal", "port": 6379},
    {"host": "redis5.internal", "port": 6379},
])

# Context manager (recommended):
try:
    with redlock.lock("payment:order:ORD-001", ttl_ms=10_000) as lock_info:
        # Critical section — at most one process runs this globally
        process_payment("ORD-001")
        # Check remaining validity before long operations:
        if lock_info.validity_ms < 2000:
            raise LockExpiredWarning("Lock about to expire; aborting to be safe")
except LockNotAcquiredError:
    # Another process already holds the lock
    return {"error": "Payment is being processed by another request"}
```

### Section 5: Lock Extension and Watchdog Pattern

**Q10. What is the watchdog pattern and when is lock extension necessary?**
A: If a critical section might take longer than the lock TTL, the process risks its lock expiring mid-operation. The **watchdog** (also called lock renewal or lease extension) is a background thread that periodically extends the lock TTL while the main thread is still processing.

```python
import threading

class WatchdogLock:
    """
    A Redlock that automatically extends itself via a background watchdog thread.
    Used when the critical section duration is unpredictable.
    """

    def __init__(
        self,
        redlock_manager: RedlockManager,
        resource:        str,
        ttl_ms:          int,
        renewal_interval_ms: int | None = None,
    ):
        self.manager   = redlock_manager
        self.resource  = resource
        self.ttl_ms    = ttl_ms
        # Renew at 2/3 of TTL: TTL=10s → renew at ~6.7s
        self.renewal_ms = renewal_interval_ms or int(ttl_ms * 2 / 3)
        self.lock_id:    str | None = None
        self._stop_event = threading.Event()
        self._watchdog:  threading.Thread | None = None

    def acquire(self) -> bool:
        result = self.manager.acquire(self.resource, self.ttl_ms)
        if not result.acquired:
            return False

        self.lock_id = result.lock_id
        self._start_watchdog()
        return True

    def _start_watchdog(self) -> None:
        self._stop_event.clear()
        self._watchdog = threading.Thread(
            target=self._watchdog_loop, daemon=True,
            name=f"watchdog:{self.resource}"
        )
        self._watchdog.start()

    def _watchdog_loop(self) -> None:
        while not self._stop_event.wait(timeout=self.renewal_ms / 1000):
            success = self._extend_lock()
            if not success:
                log.error(
                    f"Watchdog failed to extend lock on '{self.resource}'. "
                    f"Lock may have expired — critical section may be unsafe!"
                )
                # Can't forcibly stop the main thread from here
                # Best practice: main thread periodically checks a "lock_valid" flag
                break

    def _extend_lock(self) -> bool:
        # Extend on all nodes that have our lock:
        key            = f"redlock:{self.resource}"
        lock_id        = self.lock_id
        extended_count = 0
        EXTEND_SCRIPT  = """
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("PEXPIRE", KEYS[1], ARGV[2])
        else
            return 0
        end
        """
        for client in self.manager.clients:
            try:
                result = client.eval(EXTEND_SCRIPT, 1, key, lock_id, self.ttl_ms)
                if result == 1:
                    extended_count += 1
            except redis.RedisError:
                pass

        success = extended_count >= self.manager.quorum
        log.debug(
            f"Lock extension: {extended_count}/{self.manager.N} nodes, "
            f"quorum={success}"
        )
        return success

    def release(self) -> None:
        self._stop_event.set()
        if self._watchdog:
            self._watchdog.join(timeout=1.0)
        if self.lock_id:
            self.manager.release(self.resource, self.lock_id)
            self.lock_id = None

    def __enter__(self):
        if not self.acquire():
            raise LockNotAcquiredError(f"Could not acquire lock on '{self.resource}'")
        return self

    def __exit__(self, *args):
        self.release()

# Usage — long-running critical section:
with WatchdogLock(redlock, "migration:users-table", ttl_ms=10_000) as wl:
    # This may take 30+ seconds, but the watchdog renews the lock every ~6.7s
    run_large_database_migration()
    # Lock stays valid indefinitely as long as this process is alive and
    # the watchdog can reach majority of Redis nodes

# Watchdog tradeoffs:
# ✓ Prevents lock expiry during slow operations
# ✗ If watchdog thread dies silently: lock expires unexpectedly
# ✗ If network partition isolates this node: watchdog fails → lock expires
#   → another node may acquire → both run the critical section!
# ✗ Makes the "crash = lock released" safety property weaker
#    (lock only releases when watchdog stops renewing, not immediately on crash)
# Best practice: only use watchdog when the critical section is genuinely long;
#                prefer a TTL slightly longer than expected operation time + use short operations
```

### Section 6: Scenario / Interview Questions

**Q11. "An interviewer asks: a developer on your team implemented Redlock using 5 Redis nodes, but the 5 nodes are 5 replicas of the same Redis master. What's wrong?"**
A:

```
The answer: this completely defeats the purpose of Redlock.

Redlock assumes N INDEPENDENT Redis instances with NO shared state.
Using replicas of the same master means:

  1. All 5 nodes share the same data (they're replicas, not independent)
  2. If the MASTER has the lock data → all 5 replicas eventually have it
  3. If the MASTER crashes → all 5 replicas lose the data simultaneously
  4. The "majority quorum" from Redlock is meaningless:
     Acquiring on 3 of 5 replicas = acquiring on 3 copies of the same data
     Not 3 independent decisions — 3 copies of 1 decision

The failure scenario is WORSE than single-node:
  Master crashes → all replicas lose lock state simultaneously
  A new master is elected → no lock records
  Client B acquires the lock → B and A both hold it
  This is identical to the single-node failure Redlock was designed to prevent!

Additionally: replica lag means a replica might not have the lock key
  Master accepts SET lock:payment tokenA NX PX 10000
  Replica replication lag: 5ms later the replica has the key
  If Redlock reads from replicas during that 5ms: it sees "no lock" → false majority
  Result: two clients both believe they acquired the lock on "different nodes"
  (Actually the same data center/master, just lagging replicas)

What they should have done:
  5 SEPARATE Redis instances on SEPARATE physical machines
  No replication connection between them
  Each instance is fully independent
  Only then does "majority quorum" provide the intended safety guarantee
```

**Q12. "What happens if a client holds a Redlock and then has a 45-second GC pause? Walk through the exact sequence of events."**
A:

```
Initial state:
  Client A holds Redlock on resource "payment:ORD-001" with TTL=30s
  5 Redis nodes: R1-R5, all have lock:payment:ORD-001 = token-A

Timeline:
  T=0s:   Client A acquires Redlock (TTL=30s)
           R1: lock:payment:ORD-001 = token-A (expires T=30)
           R2-R5: same

  T=2s:   Client A begins processing payment for ORD-001

  T=5s:   Client A's JVM triggers a Stop-The-World GC pause
           (GC is running; Client A's code is 100% suspended)
           NO heartbeats, NO network activity, NO clock progression in app
           The Redlock TTL countdown continues on Redis servers

  T=30s:  ALL Redis nodes: lock:payment:ORD-001 EXPIRES automatically
           The key is gone from all 5 Redis nodes

  T=31s:  Client B tries to acquire Redlock on payment:ORD-001
           R1: SET lock:payment:ORD-001 token-B NX PX 30000 → acquired ✓
           R2-R5: same
           Quorum: 5 of 5 ✓ → Client B holds the Redlock

  T=35s:  Client B begins processing payment for ORD-001

  T=50s:  Client A's GC pause ends (45 seconds elapsed)
           Client A's code resumes
           Client A DOES NOT CHECK if its lock expired
           (Checking elapsed time requires the developer to explicitly code this)
           Client A continues: "I have the lock, let me finish the payment"

  T=50s-T=60s: BOTH Client A and Client B are processing payment for ORD-001
               → Double charge → data corruption → unhappy customer

How Redlock-aware code SHOULD handle this:
  Option 1: Check elapsed time before each operation
    if time.monotonic() - lock_acquired_at > ttl_seconds:
        raise LockExpiredError("Lock expired during GC pause; aborting")

  Option 2: Use fencing tokens with the storage system
    storage.write(data, fencing_token=34)  # storage rejects if token < max_seen

  Option 3: Use idempotent operations
    if not payment_already_processed(ORD-001):  # idempotency check IN the operation
        process_payment(ORD-001)
    # Even if both A and B execute this: only one actually processes due to DB unique constraint

Correct takeaway:
  Redlock does NOT prevent A from continuing after a GC pause.
  Redlock does NOT prevent B from acquiring after A's lock expires.
  Redlock only prevents B from acquiring while A's lock is VALID.
  The responsibility to detect "my lock expired" is on the application code.
```

## Problem 1 — Cron Job Deduplication Across Kubernetes Pods

### Problem
A Node.js application runs in Kubernetes with 8 replicas. A cron job fires every minute on all 8 pods simultaneously — but only one should execute the actual job logic (sending a daily digest email). Implement deduplication using Redlock.

```javascript
// ── Without Redlock (broken): all 8 pods run the job ──────────────────
// cron.js (wrong):
cron.schedule('0 8 * * *', async () => {

  retryCount:    0,      // 0 = don't retry; cron runs every minute, no point waiting
  retryDelay:    200,    // ms between retries (ignored when retryCount=0)
  retryJitter:   100,    // ms of random jitter

});

// The cron job with leader election:
cron.schedule('0 8 * * *', async () => {

  let lock;
  try {

    console.log(`[${process.env.POD_NAME}] Acquired cron lock for ${jobBucket}`);

    console.log(`[${process.env.POD_NAME}] Daily digest complete`);

// The "loser" pod should immediately skip and do nothing.

// ── Monitoring: who is running the cron? ─────────────────────────────
// The winning pod logs "Acquired cron lock" — visible in pod logs
// All other pods log "Skipping" — normal operation
```

## Problem 2 — Payment Processing: The Double-Charge Problem

### Problem
A payment service may receive the same payment request multiple times (retries from the client, load balancer retries). Implement defense-in-depth: Redlock + database idempotency key + fencing-token-style protection.

```python
import uuid, time, redis, hashlib
from contextlib import contextmanager

redlock = RedlockManager(nodes=[
    {"host": "redis1.internal", "port": 6379},
    {"host": "redis2.internal", "port": 6379},
    {"host": "redis3.internal", "port": 6379},
])

class PaymentService:
    """
    Defense-in-depth against double-charge:
    Layer 1: Redlock — prevents concurrent processing of same payment
    Layer 2: Database unique constraint on idempotency_key — catches races Redlock misses
    Layer 3: Amount verification — catches edge cases in both layers
    """

    def process_payment(
        self,
        order_id:         str,
        amount_cents:     int,
        idempotency_key:  str,
        payment_method:   dict,
    ) -> dict:

        # ── Layer 2 check (fast path, no lock): already processed? ────────
        existing = db.payments.find_by_idempotency_key(idempotency_key)
        if existing:
            log.info(f"Payment {idempotency_key} already processed, returning cached result")
            return existing.to_response()

        # ── Layer 1: Redlock — prevent concurrent processing ──────────────
        lock_resource = f"payment:order:{order_id}"
        result        = redlock.acquire(lock_resource, ttl_ms=30_000, retry_count=3)

        if not result.acquired:
            raise PaymentConflictError(
                f"Payment for order {order_id} is being processed. "
                f"Please wait a moment and try again."
            )

        lock_acquired_at = time.monotonic()

        try:
            # ── Layer 2 (inside lock): double-check after acquiring lock ──
            existing = db.payments.find_by_idempotency_key(idempotency_key)
            if existing:
                log.info(f"Payment already completed (found after lock acquisition)")
                return existing.to_response()

            # ── Safety check: is the lock still valid? (GC pause detection) ─
            elapsed = (time.monotonic() - lock_acquired_at) * 1000
            remaining_validity = result.validity_ms - elapsed
            if remaining_validity < 5_000:
                raise LockExpiredWarning(
                    f"Lock validity too low ({remaining_validity:.0f}ms). "
                    f"Aborting to prevent potential double-charge."
                )

            # ── Charge the card via payment gateway ───────────────────────
            charge_result = stripe.charge(
                amount=amount_cents,
                currency="usd",
                source=payment_method["token"],
                idempotency_key=idempotency_key,  # Stripe also has idempotency!
                metadata={"order_id": order_id},
            )

            # ── Check validity AGAIN after the network call (could have taken seconds) ─
            elapsed = (time.monotonic() - lock_acquired_at) * 1000
            remaining_validity = result.validity_ms - elapsed
            if remaining_validity < 0:
                # Lock expired during the Stripe call!
                # Another process MAY be running. Check if our charge actually succeeded:
                if charge_result.status == "succeeded":
                    # We charged successfully but can't safely proceed with DB write
                    # The charge is already committed at Stripe — must record it
                    # This is a critical situation: log urgently and attempt DB write anyway
                    log.critical(
                        f"Lock expired AFTER charge succeeded! "
                        f"charge_id={charge_result.id}, order={order_id}. "
                        f"Recording charge despite expired lock."
                    )
                    # Proceed — the database unique constraint on idempotency_key
                    # will prevent a duplicate record if another process also tries:
                else:
                    raise LockExpiredError(
                        f"Lock expired during charge attempt. "
                        f"Charge did not succeed; safe to retry."
                    )

            # ── Layer 3: record in DB (unique constraint prevents duplicates) ─
            try:
                payment_record = db.payments.create({
                    "idempotency_key":  idempotency_key,  # ← UNIQUE constraint!
                    "order_id":         order_id,
                    "amount_cents":     amount_cents,
                    "stripe_charge_id": charge_result.id,
                    "status":           "succeeded",
                    "processed_at":     time.time(),
                })
            except db.UniqueConstraintError:
                # Another process also succeeded (race condition despite the lock)
                # The Stripe idempotency_key prevents double-charging at the gateway
                # The DB unique constraint prevents duplicate records
                # Both layers caught the race — this payment was already recorded
                existing = db.payments.find_by_idempotency_key(idempotency_key)
                log.warning(
                    f"Race condition caught by DB unique constraint. "
                    f"Payment {idempotency_key} already in DB."
                )
                return existing.to_response()

            return payment_record.to_response()

        finally:
            redlock.release(lock_resource, result.lock_id)

# ── Why three layers? ─────────────────────────────────────────────────
# Layer 1 (Redlock): prevents most concurrent processing; fast rejection
# Layer 2 (DB idempotency check): catches Redlock failures (GC pause, clock jump)
# Layer 3 (DB unique constraint): final safety net; works even if code has bugs
# Stripe idempotency: catches double-charges if we call Stripe twice somehow

# The key insight: NO SINGLE MECHANISM IS SUFFICIENT
# Each layer covers different failure modes the others miss
```

## Problem 4 — Rate-Limited Lock Acquisition with Backoff

### Problem
Multiple services compete for a shared external API rate limit (e.g., 10 API calls per second). Implement a distributed token bucket using Redlock that fairly distributes access across services.

```python
import time, math
from typing import Generator

class DistributedTokenBucket:
    """
    Token bucket rate limiter using Redlock for distributed coordination.
    Rate: `rate` tokens per second, burst capacity `capacity`.
    """

    # Lua script: atomic token consumption + replenishment
    # Returns [tokens_remaining, granted]
    # granted = 1 if the request was allowed; 0 if rate-limited
    CONSUME_SCRIPT = """
    local key        = KEYS[1]
    local capacity   = tonumber(ARGV[1])
    local rate       = tonumber(ARGV[2])   -- tokens per second
    local now        = tonumber(ARGV[3])   -- current timestamp (ms)
    local requested  = tonumber(ARGV[4])   -- tokens to consume

    local data       = redis.call("HMGET", key, "tokens", "last_refill")
    local tokens     = tonumber(data[1])
    local last_refill = tonumber(data[2])

    -- Initialize on first use:
    if tokens == nil then
        tokens     = capacity
        last_refill = now
    end

    -- Refill based on time elapsed:
    local elapsed_ms  = now - last_refill
    local new_tokens  = math.min(capacity, tokens + (elapsed_ms * rate / 1000))

    -- Try to consume:
    local granted = 0
    if new_tokens >= requested then
        new_tokens = new_tokens - requested
        granted    = 1
    end

    -- Save state with TTL:
    redis.call("HMSET", key, "tokens", new_tokens, "last_refill", now)
    redis.call("PEXPIRE", key, 60000)   -- auto-expire after 60s of inactivity

    return {math.floor(new_tokens * 100) / 100, granted}
    """

    def __init__(
        self,
        redlock:  RedlockManager,
        name:     str,
        rate:     float,    # tokens per second
        capacity: int,      # max burst capacity
    ):
        self.redlock  = redlock
        self.key      = f"tokenbucket:{name}"
        self.rate     = rate
        self.capacity = capacity
        # Use single Redis node for the bucket state (simpler; use same redlock nodes):
        self.r = redlock.clients[0]   # token state is on one node (bucket is soft state)

    def try_consume(self, tokens: int = 1) -> tuple[bool, float]:
        """
        Try to consume `tokens` from the bucket.
        Returns: (granted: bool, remaining: float)
        """
        now_ms = int(time.monotonic() * 1000)
        result = self.r.eval(
            self.CONSUME_SCRIPT, 1, self.key,
            self.capacity, self.rate, now_ms, tokens
        )
        remaining = float(result[0])
        granted   = result[1] == 1
        return granted, remaining

    @contextmanager
    def acquire_tokens(self, tokens: int = 1, max_wait_ms: int = 5000) -> Generator:
        """
        Acquire tokens, waiting up to max_wait_ms with exponential backoff.
        Raises RateLimitExceeded if tokens can't be acquired in time.
        """
        deadline  = time.monotonic() + max_wait_ms / 1000
        wait_ms   = 50   # initial retry delay

        while time.monotonic() < deadline:
            granted, remaining = self.try_consume(tokens)
            if granted:
                yield remaining   # caller proceeds
                return

            # Not granted: calculate wait time for next available token
            wait_for_s = tokens / self.rate   # time to accumulate `tokens` tokens
            wait_ms    = min(int(wait_for_s * 1000), max_wait_ms // 4, wait_ms * 2)
            log.debug(f"Rate limited, waiting {wait_ms}ms (remaining: {remaining:.2f})")

            if time.monotonic() + wait_ms / 1000 > deadline:
                break
            time.sleep(wait_ms / 1000)

        raise RateLimitExceeded(
            f"Could not acquire {tokens} tokens from '{self.key}' "
            f"within {max_wait_ms}ms"
        )

class RateLimitExceeded(Exception):
    pass
```

## Quick Reference — Distributed Locking Cheat Sheet

```
SINGLE-NODE REDIS LOCK:
  Acquire: SET key token NX PX ttl_ms
    NX: only set if Not eXist (atomic compare-and-set)
    PX: millisecond TTL (auto-expire prevents deadlock on crash)
    token: unique UUID — identifies this specific lock holder
  Release: Lua script (atomic GET + compare + DEL)
    if GET(key) == my_token: DEL(key)  else: return 0
    NEVER just DEL(key) — may delete another holder's lock
  Weakness: Redis master crash → replica promoted → lock state lost → two holders

REDLOCK ALGORITHM (N independent instances, typically N=5):
  1. Record start time T1 (monotonic clock)
  2. Try SET key token NX PX ttl on ALL N nodes sequentially
     Use short per-node timeout (e.g., 50ms) → don't wait for slow/down nodes
  3. Record end time T2; elapsed = T2 - T1
  4. ACQUIRED if: successes ≥ N/2+1 (majority) AND elapsed < ttl
     actual_validity = ttl - elapsed - clock_drift_factor
  5. If not acquired: release on ALL nodes (including failed ones) → retry with jitter
  6. Release: Lua GET+DEL on all N nodes

KEY NUMBERS:
  N=3: quorum=2, tolerates 1 failure
  N=5: quorum=3, tolerates 2 failures (RECOMMENDED)
  N=7: quorum=4, tolerates 3 failures
  per-node timeout: 5-10% of TTL (e.g., 50ms for 10s TTL)
  clock_drift_factor: 1% of TTL + 2ms constant
  retry delay: 200ms base + 0-100ms random jitter (prevents thundering herd)

SETNX + EXPIRE IS WRONG (two commands, not atomic):
  Process crash between SETNX and EXPIRE = lock with no expiry = deadlock forever
  Always use: SET key token NX PX ttl (single atomic command)

REDLOCK LIMITATIONS (Kleppmann's critique):
  GC pause: client A paused 15s → lock expires → B acquires → A resumes → both hold lock
  Clock jump: NTP correction causes premature TTL expiry → two holders
  Redlock cannot prevent: client continuing after lock expiry (no way to stop it)
  Redlock CAN prevent: two clients BOTH acquiring a fresh lock simultaneously (quorum safety)

FENCING TOKENS (the correct solution for correctness-critical systems):
  Lock service issues monotonically increasing token with each lock grant
  Resource rejects writes with token ≤ last seen token
  Redlock cannot provide real fencing tokens (needs single authority for monotonicity)
  etcd revisions / ZooKeeper zxid / DB sequences = real fencing tokens

WHEN TO USE WHAT:
  Redis single-node lock: simple apps, single Redis instance, consistency not critical
  Redlock:                distributed, "efficiency" locks, duplicate work prevention,
                          cron deduplication, idempotent operations
  etcd/ZooKeeper:         correctness-critical, leader election, fencing tokens required,
                          financial transactions, schema migrations

WATCHDOG PATTERN (for long-running critical sections):
  Background thread extends lock TTL every 2/3 of TTL period
  Stops extending when main thread finishes (releases lock)
  Risk: if watchdog dies silently → lock expires unexpectedly
  Best practice: validate lock validity at checkpoints in long operations

COMMON BUGS:
  SETNX then EXPIRE (not atomic)           → use SET NX PX instead
  Using replicas as "N independent nodes"  → defeats Redlock; all share state
  Not using unique token per lock holder   → deletes other holder's lock on release
  retryCount > 0 for cron job deduplication → queued failures run at wrong time
  No validity time check after acquiring  → lock may have expired during slow operations
  Releasing without token check           → may release another holder's lock
  Even N of nodes (N=4 same fault tolerance as N=3, costs more)
  TTL too short relative to operation duration → lock expires during operation
  Single per-node timeout too large        → acquisition takes longer than TTL
  Not releasing on acquire failure        → partial locks accumulate, exhaust resources

LIBRARIES:
  Python: redlock-py, pottery (Redis), redis-py (manual)
  Node.js: redlock (npm), ioredis/redlock
  Java: Redisson (built-in Redlock support)
  Go: redsync
  All implement the 5-step algorithm; verify they handle: partial acquire cleanup,
  validity time check, unique token per acquire, monotonic clock for elapsed time
```

**Final Tip:** At the 5 YOE level, Redlock questions test whether you understand both **how the algorithm works** and **its fundamental limitations** — and can articulate when it is and isn't the right tool. The highest-signal answer on why SETNX+EXPIRE is wrong: "They're two separate commands — not atomic. If the process crashes after SETNX succeeds but before EXPIRE runs, the key exists with no TTL: the lock is held forever. `SET key token NX PX ttl` is the single atomic command that solves this — it either sets the key with the TTL or it doesn't — no intermediate state possible." On Kleppmann's critique: "Kleppmann's argument is correct but applies only to correctness-critical operations. A 30-second JVM GC pause can cause the lock to expire while the client still thinks it holds it, allowing a second client to acquire it — both then run the critical section. Redlock cannot prevent this. The solution for correctness-critical systems is fencing tokens from etcd or ZooKeeper: the storage system rejects writes from a client with a stale (lower) token even if that client genuinely believes it holds the lock. For 'efficiency' locks like cron deduplication — where duplicate work is costly but recoverable — Redlock is perfectly adequate and much simpler to operate." On why replicas of the same master break Redlock: "Redlock's safety comes from the quorum — to hold the lock, you must acquire it on `N/2+1` independent nodes. 'Independent' means they don't share state. If you use replicas of the same master, they share state: when the master crashes, all replicas simultaneously lose the lock key. There's no quorum protection — one failure (the master) defeats all 5 nodes at once. The N instances must be on separate physical machines with no replication between them."
