# Caching Patterns: Cache-Aside, Write-Through, Write-Behind, Read-Through — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does caching solve — and what are the fundamental trade-offs every caching pattern must balance?**

A: Caching exists because the primary datastore (a relational database, document store, or external API) cannot serve reads fast enough, cheaply enough, or at high enough concurrency for the application's requirements. A cache sits between the application and the datastore, absorbing reads for data that doesn't change on every request:

```
Without cache:
  Every request → DB query → 10-50ms latency per query
  100 concurrent users → 100 concurrent DB queries
  DB becomes the bottleneck at scale

With cache:
  First request → DB query → store result in cache
  Subsequent requests → cache hit → 0.1-1ms latency
  100 concurrent users → 1-5 DB queries (only on cache misses)
  DB is protected; response time improves by 10-100×
```

Every caching pattern is a different answer to three fundamental questions:

```
Question 1: WHO populates the cache?
  Application code populates it (cache-aside, write-through, write-behind)
  OR a caching library/infrastructure layer populates it (read-through)

Question 2: WHEN does a write go to the DB?
  Immediately on every write (write-through)
  OR asynchronously/eventually (write-behind)
  OR only on explicit cache miss reads (cache-aside — cache is not written on writes)

Question 3: WHAT consistency guarantee does each pattern provide?
  Strong consistency (write-through: cache and DB always agree)
  Eventual consistency (write-behind: DB lags behind cache)
  Potential staleness (cache-aside: cache may be stale between invalidation and repopulation)
```

The core trade-off triangle:

```
                    Consistency
                        ▲
                        │
              write-through
                        │
          ─────────────┼─────────────
         │             │             │
         │      cache-beside         │
    Performance ◄──────────────► Simplicity
         │                          │
    write-behind                read-through
         │                          │
         └──────────────────────────┘

No pattern wins on all three — the right choice depends on your workload:
  High read-to-write ratio + tolerate stale data:  cache-aside
  Need strong consistency + can absorb write latency: write-through
  Need maximum write throughput + tolerate lag:     write-behind
  Want to hide caching complexity from callers:     read-through
```

**Q2. What are the four main caching patterns — and which layer owns the cache in each?**

A: The patterns differ in which component (application, cache library, or cache infrastructure) is responsible for each operation:

```
Pattern         | Read path                    | Write path                  | Cache owner
────────────────┼──────────────────────────────┼─────────────────────────────┼─────────────
Cache-Aside     | App: check cache → DB on miss | App: write DB, invalidate   | Application
Read-Through    | Library: check cache → DB     | App: write DB, invalidate   | Cache library
Write-Through   | App or library: check cache   | Library: write cache → DB   | Cache library
Write-Behind    | App or library: check cache   | Library: write cache →      | Cache library
                |                              |   async DB (deferred)       |

In practice, cache-aside is implemented in application code.
Read-through, write-through, and write-behind are typically provided by a
caching framework (AWS ElastiCache DAX, NCache, Ehcache, Spring Cache, etc.)
that sits transparently between your code and the DB.
```

## Section 2: Cache-Aside (Lazy Loading)

**Q3. How does the cache-aside pattern work — what are the exact read and write flows?**

A: Cache-aside (also called lazy loading) is the most common caching pattern and the default assumption when people say "add Redis caching." The application is entirely responsible for managing the cache — it checks the cache first, falls back to the database on a miss, and populates the cache itself:

```typescript
import { Redis } from 'ioredis';
import { Pool } from 'pg';

const redis = new Redis(process.env.REDIS_URL);
const db    = new Pool({ connectionString: process.env.DATABASE_URL });

// ── READ PATH (cache-aside) ────────────────────────────────────────────────────
// Step 1: Check the cache
// Step 2: On miss → query the database
// Step 3: Store result in cache
// Step 4: Return result

async function getProduct(productId: string): Promise<Product | null> {
    const cacheKey = `product:${productId}`;

    // Step 1: Check cache
    const cached = await redis.get(cacheKey);
    if (cached !== null) {
        return JSON.parse(cached);   // Cache HIT → return immediately
    }

    // Step 2: Cache MISS → query database
    const result = await db.query(
        'SELECT * FROM products WHERE id = $1',
        [productId]
    );
    const product = result.rows[0] ?? null;

    // Step 3: Store in cache (only if we found something)
    if (product !== null) {
        await redis.set(cacheKey, JSON.stringify(product), 'EX', 3600);
        // EX 3600 = expire in 1 hour
        // This TTL is the backstop: even if we forget to invalidate,
        // the data will eventually be fresh (at the cost of serving stale for ≤ 1 hour)
    }

    // Step 4: Return
    return product;
}

// ── WRITE PATH (cache-aside) ───────────────────────────────────────────────────
// Cache-aside does NOT write to the cache on updates.
// It INVALIDATES (deletes) the cache entry — forcing the next read to re-populate it.

async function updateProduct(productId: string, data: UpdateProductInput): Promise<Product> {
    // Step 1: Write to the database (source of truth first)
    const result = await db.query(
        'UPDATE products SET name=$1, price=$2, updated_at=NOW() WHERE id=$3 RETURNING *',
        [data.name, data.price, productId]
    );
    const updated = result.rows[0];

    // Step 2: Invalidate the cache (not update — delete)
    await redis.del(`product:${productId}`);
    // Next read will go to DB (miss) and repopulate the cache with fresh data

    return updated;
}

// ── Why invalidate instead of update? ─────────────────────────────────────────
// Updating the cache on write seems faster, but creates a race condition:
//
// Thread A: reads product from DB → gets old value
// Thread B: writes new product to DB → invalidates cache
// Thread A: writes OLD product to cache → cache has stale data!
//
// Solution: delete the cache entry on write.
// The next read triggers a fresh DB query and populates the cache correctly.
// This approach is safe under concurrent access.
//
// Exception: you CAN update the cache if:
// - The write is transactional (using Redis MULTI/EXEC or Lua scripts)
// - You know no other writer is concurrent
// But for simplicity, delete is the safe default.
```

Cache-aside in a service layer (TypeScript with dependency injection):

```typescript
@Injectable()
export class ProductService {
    private readonly CACHE_TTL = 3600;  // 1 hour

    constructor(
        private readonly redis: Redis,
        private readonly productRepo: ProductRepository,
    ) {}

    async findById(id: string): Promise<Product | null> {
        const key    = `product:${id}`;
        const cached = await this.redis.get(key);

        if (cached) {
            return JSON.parse(cached) as Product;
        }

        const product = await this.productRepo.findById(id);

        if (product) {
            await this.redis.setex(key, this.CACHE_TTL, JSON.stringify(product));
        }

        return product;
    }

    async update(id: string, dto: UpdateProductDto): Promise<Product> {
        const product = await this.productRepo.update(id, dto);
        await this.redis.del(`product:${id}`);
        return product;
    }

    async delete(id: string): Promise<void> {
        await this.productRepo.delete(id);
        await this.redis.del(`product:${id}`);
    }

    // Bulk invalidation when category changes affect multiple products:
    async updateCategory(categoryId: string, dto: UpdateCategoryDto): Promise<void> {
        await this.categoryRepo.update(categoryId, dto);

        // Invalidate all products in this category:
        // Option A: scan for keys matching pattern (SCAN, not KEYS — never use KEYS in production)
        const pattern = `product:category:${categoryId}:*`;
        let cursor = '0';
        do {
            const [nextCursor, keys] = await this.redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
            cursor = nextCursor;
            if (keys.length > 0) {
                await this.redis.del(...keys);
            }
        } while (cursor !== '0');

        // Option B: store a version/generation counter (more scalable):
        await this.redis.incr(`category:${categoryId}:version`);
        // Cache key includes the version: `product:${id}:v${version}`
        // When version changes, all old keys are automatically stale (and expire via TTL)
    }
}
```

**Q4. What are the advantages and failure modes of cache-aside — the thundering herd and stale data problems?**

A: Cache-aside is simple and resilient but has two well-known failure modes that require explicit mitigation in production:

```typescript
// ── Failure Mode 1: Thundering Herd (cache stampede) ─────────────────────────
// Scenario: A popular item's cache entry expires. Simultaneously, 500 requests
// arrive for that item. All 500 see a cache miss, all 500 query the database.
// Result: 500 concurrent DB queries for the same row — DB overload.

// Detection:
// redis-cli INFO stats → keyspace_misses spikes
// DB monitoring → sudden burst of identical queries

// ── Fix 1: Mutex lock (per-key locking) ─────────────────────────────────────
async function getProductWithMutex(productId: string): Promise<Product | null> {
    const cacheKey = `product:${productId}`;
    const lockKey  = `lock:product:${productId}`;

    // Check cache first:
    const cached = await redis.get(cacheKey);
    if (cached) return JSON.parse(cached);

    // Try to acquire the lock (SET NX EX = set if not exists, with expiry):
    const lockAcquired = await redis.set(lockKey, '1', 'NX', 'EX', 10);
    // Returns 'OK' if lock acquired, null if another process holds it

    if (lockAcquired === 'OK') {
        try {
            // Double-check after acquiring lock (another process may have populated):
            const cachedAgain = await redis.get(cacheKey);
            if (cachedAgain) return JSON.parse(cachedAgain);

            // We have the lock — we're the only one querying the DB:
            const product = await db.query('SELECT * FROM products WHERE id = $1', [productId]);
            const result  = product.rows[0] ?? null;

            if (result) {
                await redis.setex(cacheKey, 3600, JSON.stringify(result));
            }
            return result;
        } finally {
            await redis.del(lockKey);  // Always release the lock
        }
    } else {
        // Another process is querying the DB — wait and retry:
        await new Promise(resolve => setTimeout(resolve, 50));
        return getProductWithMutex(productId);  // Retry (now the cache should be populated)
    }
}

// ── Fix 2: Probabilistic early expiration ────────────────────────────────────
// Instead of waiting for expiry, proactively refresh slightly before it expires.
// Uses the "XFetch" algorithm: the closer to expiry, the higher the probability of refresh.
async function getProductWithEarlyExpiry(productId: string): Promise<Product | null> {
    const cacheKey = `product:${productId}`;
    const beta     = 1.0;  // Higher = more aggressive early refresh

    const [value, ttl] = await Promise.all([
        redis.get(cacheKey),
        redis.ttl(cacheKey),
    ]);

    if (value !== null) {
        const data = JSON.parse(value) as { product: Product; delta: number; expiry: number };
        // XFetch: refresh if random < delta/ttl * log(uniform_random)
        const shouldRefresh = -data.delta * beta * Math.log(Math.random()) > ttl;

        if (!shouldRefresh) {
            return data.product;  // Cache is still fresh enough
        }
        // Fall through to refresh
    }

    // Query DB and store with timing metadata:
    const start   = Date.now();
    const result  = await db.query('SELECT * FROM products WHERE id = $1', [productId]);
    const delta   = (Date.now() - start) / 1000;  // Seconds to compute the value
    const product = result.rows[0] ?? null;

    if (product) {
        const expiry = Math.floor(Date.now() / 1000) + 3600;
        await redis.setex(cacheKey, 3600, JSON.stringify({ product, delta, expiry }));
    }

    return product;
}

// ── Failure Mode 2: Stale data ────────────────────────────────────────────────
// The cache holds old data because:
// A) The TTL hasn't expired yet, but the DB was updated
// B) The invalidation on write failed (Redis was temporarily unavailable)
// C) Multiple services update the DB but only some invalidate the cache

// ── Fix for stale data: write-invalidate with retry ──────────────────────────
async function updateProductSafely(id: string, data: UpdateProductInput): Promise<Product> {
    const product = await db.query(
        'UPDATE products SET ... WHERE id = $1 RETURNING *', [id]
    );

    // Retry cache invalidation with exponential backoff:
    const MAX_RETRIES = 3;
    for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
        try {
            await redis.del(`product:${id}`);
            break;  // Success
        } catch (err) {
            if (attempt === MAX_RETRIES) {
                // Log and alert but don't fail the write
                logger.error({ err, productId: id }, 'Cache invalidation failed after retries');
                // The TTL will eventually clean up the stale entry
            }
            await new Promise(resolve => setTimeout(resolve, 100 * Math.pow(2, attempt)));
        }
    }

    return product.rows[0];
}
```

## Section 3: Write-Through

**Q5. How does the write-through pattern work — what makes it different from cache-aside on writes?**

A: Write-through keeps the cache and database permanently synchronised by writing to both on every update, in the same operation. Unlike cache-aside (which deletes the cache on write), write-through immediately stores the new value in both layers:

```typescript
// ── WRITE PATH (write-through) ────────────────────────────────────────────────
// Step 1: Write to CACHE first
// Step 2: Write to DATABASE (synchronously, in the same operation)
// Step 3: Return success only when BOTH writes succeed

async function updateProductWriteThrough(id: string, data: UpdateProductInput): Promise<Product> {
    // Build the updated product object:
    const product = {
        id,
        name:      data.name,
        price:     data.price,
        updatedAt: new Date().toISOString(),
    };

    // Write BOTH simultaneously (or sequentially, depending on implementation):
    // Option A: Write cache first, then DB
    await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
    await db.query(
        'UPDATE products SET name=$1, price=$2, updated_at=NOW() WHERE id=$3',
        [data.name, data.price, id]
    );

    // Option B: Write DB first, then cache (safer — DB is the source of truth)
    const result = await db.query(
        'UPDATE products SET name=$1, price=$2, updated_at=NOW() WHERE id=$3 RETURNING *',
        [data.name, data.price, id]
    );
    const saved = result.rows[0];
    await redis.setex(`product:${id}`, 3600, JSON.stringify(saved));

    return saved;
}

// ── READ PATH (write-through) ─────────────────────────────────────────────────
// Same as cache-aside: check cache, fall back to DB on miss
// (Reads are unchanged — the guarantee is about writes)
async function getProductWriteThrough(id: string): Promise<Product | null> {
    const cached = await redis.get(`product:${id}`);
    if (cached) return JSON.parse(cached);

    const result = await db.query('SELECT * FROM products WHERE id = $1', [id]);
    const product = result.rows[0] ?? null;

    // On read miss: populate the cache (same as cache-aside)
    if (product) {
        await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
    }

    return product;
}
```

Write-through in a framework (Spring Cache style, conceptual TypeScript):

```typescript
// Write-through is often implemented transparently by caching frameworks.
// The application code looks clean — the framework handles dual writes.

// Pseudocode for a write-through decorator:
function WriteThrough(cacheKey: (id: string) => string, ttl: number) {
    return function(target: any, methodName: string, descriptor: PropertyDescriptor) {
        const originalMethod = descriptor.value;

        descriptor.value = async function(id: string, data: any) {
            // Execute the original DB write:
            const result = await originalMethod.call(this, id, data);

            // Automatically update the cache with the DB result:
            await redis.setex(cacheKey(id), ttl, JSON.stringify(result));

            return result;
        };
    };
}

class ProductService {
    @WriteThrough(id => `product:${id}`, 3600)
    async update(id: string, data: UpdateProductInput): Promise<Product> {
        // This method only writes to DB — the decorator handles the cache
        return this.productRepo.update(id, data);
    }
}
```

The write-through transaction problem — what happens if one write fails:

```typescript
// Critical failure scenario:
// Cache write succeeds → DB write fails → Cache has data DB doesn't

async function updateProductAtomically(id: string, data: UpdateProductInput): Promise<Product> {
    // Option 1: DB first (safer — DB is source of truth)
    const result = await db.query(
        'UPDATE products SET name=$1, price=$2 WHERE id=$3 RETURNING *',
        [data.name, data.price, id]
    );
    const saved = result.rows[0];

    // If cache write fails: stale data in cache → TTL will eventually clean it
    // (Same problem as cache-aside, but cache-aside has DELETE which is safer)
    try {
        await redis.setex(`product:${id}`, 3600, JSON.stringify(saved));
    } catch (err) {
        // Cache write failed — log but don't fail the response
        // The cache entry will remain stale until TTL expires
        logger.warn({ err, id }, 'Write-through cache update failed');
    }

    return saved;

    // Option 2: Atomic write using a Lua script or Redis transaction
    // Guarantees: both happen or neither (for the cache side)
    // But: cannot atomically span cache + DB (different systems)
    // True atomicity across cache + DB requires distributed transactions (very complex)
}
```

**Q6. What are the advantages and disadvantages of write-through — when does it outperform cache-aside?**

A: Write-through solves cache-aside's primary weakness (stale data after writes) but introduces its own costs:

```
ADVANTAGES of write-through over cache-aside:

1. No stale reads after writes
   After updateProduct() returns, any subsequent read gets fresh data from cache
   (no window where the cache is stale)

2. Cache is always populated for written data
   After writing product X, the next read of product X is guaranteed to be a cache hit
   (cache-aside would be a miss until the first read after a write)

3. Better for write-heavy workloads with frequent subsequent reads
   E-commerce: update product price → immediately read it for order confirmation
   With write-through: read is a cache hit (fast)
   With cache-aside: read is a cache miss → DB query (slower)

DISADVANTAGES of write-through:

1. Higher write latency (synchronous dual write)
   Every write must write to both cache AND DB
   Total write time ≈ cache_write_time + db_write_time
   (vs cache-aside: write_time ≈ db_write_time + del_time, where del is faster than set)

2. Cache pollution with data that is never read
   Write-through populates the cache with every written value
   If you write 10,000 products but only read 100 of them:
   → 9,900 cache slots wasted on data nobody reads
   → Eviction kicks out other useful data to make room
   → Net negative for cache efficiency

3. The "cold start" problem
   On a new deployment with an empty cache:
   Read-heavy patterns still need to warm the cache via reads
   Write-through only helps for data written AFTER the cache is in place

4. Write failures are more complex
   If cache write succeeds and DB write fails (or vice versa):
   → Cache and DB are inconsistent
   → Write-through doesn't solve the consistency problem perfectly without transactions

WHEN write-through beats cache-aside:
  - High read/write ratio FOR THE SAME DATA (write then immediately read)
  - Low write volume (write latency overhead is acceptable)
  - Data that is always read after being written (user settings, shopping cart)

WHEN cache-aside beats write-through:
  - Write-heavy workloads where most writes are never subsequently read from cache
  - You need lower write latency
  - The cache is large and cache pollution is a concern
```

## Section 4: Write-Behind (Write-Back)

**Q7. How does write-behind work — what is the full flow and what makes it fundamentally different?**

A: Write-behind (also called write-back) decouples writes from database persistence entirely. Writes go to the cache immediately and to the database asynchronously — the application gets a fast write acknowledgement, but the database is only updated later by a background process:

```typescript
import { EventEmitter } from 'events';

// ── Write-behind architecture ─────────────────────────────────────────────────
//
// Write request → [Cache] → Acknowledge to client
//                    ↓ (async, background)
//                  [DB Writer Process] → [Database]
//
// The "write buffer" is a queue of pending DB writes.
// Common implementations: Redis list, Kafka topic, or in-memory queue

class WriteBehindCache {
    private readonly writeQueue = 'write_queue:products';

    // ── WRITE PATH (write-behind) ─────────────────────────────────────────────
    // Step 1: Write to cache immediately
    // Step 2: Enqueue a "dirty write" record (don't write to DB yet)
    // Step 3: Return success to the client (DB write hasn't happened yet!)
    async updateProduct(id: string, data: UpdateProductInput): Promise<Product> {
        const product = {
            id,
            name:      data.name,
            price:     data.price,
            updatedAt: new Date().toISOString(),
            _dirty:    true,   // Mark as not yet persisted to DB
        };

        // Write to cache immediately (fast):
        await redis.setex(`product:${id}`, 3600, JSON.stringify(product));

        // Enqueue the write for later DB persistence:
        const writeRecord = JSON.stringify({
            operation: 'update',
            id,
            data,
            timestamp: Date.now(),
        });
        await redis.lpush(this.writeQueue, writeRecord);

        // Return immediately — DB not yet updated
        return product;
    }

    // ── BACKGROUND DB WRITER ───────────────────────────────────────────────────
    // This process runs continuously, draining the write queue and persisting to DB
    async startBackgroundWriter(): Promise<void> {
        console.log('Write-behind worker started');

        while (true) {
            try {
                // BRPOP: blocking pop from the right end of the list
                // Waits up to 5 seconds for a new item before checking again
                const item = await redis.brpop(this.writeQueue, 5);

                if (!item) continue;  // Timeout — queue was empty, loop again

                const [, writeRecordStr] = item;
                const writeRecord = JSON.parse(writeRecordStr);

                await this.persistToDatabase(writeRecord);

            } catch (err) {
                logger.error({ err }, 'Write-behind worker error');
                // Don't crash the worker — log and continue
                await new Promise(resolve => setTimeout(resolve, 1000));
            }
        }
    }

    private async persistToDatabase(record: WriteRecord): Promise<void> {
        const MAX_RETRIES = 5;

        for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
            try {
                await db.query(
                    'UPDATE products SET name=$1, price=$2, updated_at=$3 WHERE id=$4',
                    [record.data.name, record.data.price, record.data.updatedAt, record.id]
                );

                // Mark the cache entry as no longer dirty:
                const cached = await redis.get(`product:${record.id}`);
                if (cached) {
                    const product = JSON.parse(cached);
                    delete product._dirty;
                    await redis.setex(`product:${record.id}`, 3600, JSON.stringify(product));
                }

                return;  // Success

            } catch (err) {
                if (attempt === MAX_RETRIES) {
                    logger.error({ err, record }, 'Write-behind: failed to persist after max retries');
                    // Dead letter queue: save failed records for manual review
                    await redis.lpush('dead_letter:products', JSON.stringify({ record, err: err.message }));
                    return;
                }
                const delay = 1000 * Math.pow(2, attempt);  // Exponential backoff
                await new Promise(resolve => setTimeout(resolve, delay));
            }
        }
    }

    // ── READ PATH (write-behind) ───────────────────────────────────────────────
    // Reads always check the cache first — the cache has the MOST UP-TO-DATE data
    // (more up-to-date than the DB, since writes go to cache first)
    async getProduct(id: string): Promise<Product | null> {
        const cached = await redis.get(`product:${id}`);
        if (cached) {
            const product = JSON.parse(cached);
            delete product._dirty;  // Don't expose internal marker to clients
            return product;
        }

        // On cache miss: read from DB (the async writes should have caught up by now)
        const result  = await db.query('SELECT * FROM products WHERE id = $1', [id]);
        const product = result.rows[0] ?? null;

        if (product) {
            await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
        }

        return product;
    }
}
```

Batching writes in write-behind (the real performance win):

```typescript
class BatchWriteBehindCache {
    private readonly BATCH_SIZE    = 100;
    private readonly BATCH_WINDOW  = 500;  // ms — collect writes for 500ms then flush

    async startBatchWriter(): Promise<void> {
        while (true) {
            // Collect up to BATCH_SIZE items within BATCH_WINDOW milliseconds:
            const batch: WriteRecord[] = [];
            const deadline = Date.now() + this.BATCH_WINDOW;

            while (batch.length < this.BATCH_SIZE && Date.now() < deadline) {
                const timeRemaining = Math.max(0, deadline - Date.now()) / 1000;
                const item = await redis.brpop(this.writeQueue, timeRemaining);
                if (item) batch.push(JSON.parse(item[1]));
                else break;  // Queue empty
            }

            if (batch.length === 0) continue;

            // Single batch DB write — MUCH more efficient than one query per item:
            await this.batchPersist(batch);
        }
    }

    private async batchPersist(records: WriteRecord[]): Promise<void> {
        // Deduplicate: if the same product was written 5 times,
        // only keep the most recent write (avoid unnecessary DB writes):
        const deduplicated = new Map<string, WriteRecord>();
        for (const record of records) {
            const existing = deduplicated.get(record.id);
            if (!existing || record.timestamp > existing.timestamp) {
                deduplicated.set(record.id, record);
            }
        }

        // Batch UPDATE (PostgreSQL-specific):
        const uniqueRecords = [...deduplicated.values()];
        const values = uniqueRecords.flatMap((r, i) => [
            r.id, r.data.name, r.data.price,
        ]);
        const placeholders = uniqueRecords.map((_, i) =>
            `($${i * 3 + 1}, $${i * 3 + 2}, $${i * 3 + 3})`
        ).join(', ');

        await db.query(`
            INSERT INTO products (id, name, price)
            VALUES ${placeholders}
            ON CONFLICT (id) DO UPDATE
            SET name = EXCLUDED.name, price = EXCLUDED.price, updated_at = NOW()
        `, values);

        logger.info({ count: uniqueRecords.length }, 'Batch write-behind persisted');
    }
}
```

**Q8. What are the critical risks of write-behind and how do you mitigate them?**

A: Write-behind trades consistency for performance, and that trade has concrete failure scenarios that must be designed around:

```typescript
// ── Risk 1: Data loss on cache/queue failure ──────────────────────────────────
// If the write queue (Redis) crashes before the background writer drains it,
// all pending writes are LOST — they exist in cache but will never reach the DB.

// Mitigation A: use Redis with AOF persistence (append-only file):
// redis.conf:
// appendonly yes
// appendfsync everysec   ← flush AOF to disk every second (max 1s of data loss)
// appendfsync always     ← flush on every write (no data loss, but ~50% slower writes)

// Mitigation B: use a durable queue (Kafka, SQS) instead of a Redis list:
// SQS: messages are replicated and retained for up to 14 days
// Kafka: topic with replication factor 3 → survives node failures

// Mitigation C: write to a WAL (write-ahead log) in the DB AND cache:
// The DB WAL records the intent to write even before the data is in the table
// Requires tight integration between cache and DB subsystem

// ── Risk 2: Dirty reads from other services ───────────────────────────────────
// Service A: writes product price update to cache (write-behind)
// Service B: directly queries DB to get the product price → gets OLD price
// (because the DB hasn't been updated yet)
// → Service B makes a decision based on stale data

// Mitigation: all services MUST use the cache, never bypass it
// Or: use write-through instead if other services read the DB directly

// ── Risk 3: Ordering violations ──────────────────────────────────────────────
// Write 1 at t=0: price → $100
// Write 2 at t=1: price → $200
// DB writer processes Write 2 before Write 1 (queue processing order not guaranteed):
// DB ends up with: price → $100 (WRONG — earlier write wins)

// Mitigation: include a version/timestamp in each write record
// DB writer uses optimistic locking or conditional update:
await db.query(`
    UPDATE products
    SET price = $1, updated_at = $2
    WHERE id = $3 AND updated_at < $2   ← Only update if record is older
`, [newPrice, timestamp, productId]);
// If updated_at >= timestamp: the write is dropped (a newer write already landed)

// ── Risk 4: Cache eviction of dirty data ─────────────────────────────────────
// If a "dirty" (not yet persisted) cache entry is evicted by Redis:
// → The write is LOST if it's still in the queue
// → But the queue entry references data that's no longer in cache

// Mitigation: set TTL on dirty entries much longer than the write-behind window:
// If writes are flushed every 500ms, set dirty key TTL to at least 1 hour
// The queue will be drained long before the TTL expires

// Mitigation B: store the full write data in the queue (not just a reference):
await redis.lpush(this.writeQueue, JSON.stringify({
    operation: 'update',
    id:        record.id,
    data:      record.data,  // ← Full data, not a reference to the cache key
    timestamp: Date.now(),
}));
// Even if the cache entry is evicted, the queue has everything needed to write to DB

// ── When write-behind is appropriate ─────────────────────────────────────────
// ✓ Write-heavy workloads: IoT telemetry, real-time analytics, game state
// ✓ Writes that can be batched: 1000 individual → 1 batch INSERT (100× faster)
// ✓ Best-effort data: analytics, counters, non-critical state
// ✓ Data that is written frequently but read infrequently from DB directly

// ✗ Financial transactions: must be in DB immediately for ACID guarantees
// ✗ Data read by external systems bypassing cache: other services see stale DB
// ✗ Low-tolerance for data loss: any queue/cache failure = permanent data loss
```

## Section 5: Read-Through

**Q9. How does read-through differ from cache-aside — what is the transparency it provides?**

A: Read-through looks identical to cache-aside from the caller's perspective — both check cache first and fall back to the DB on a miss. The difference is architectural: in cache-aside, the application code explicitly checks the cache; in read-through, a caching layer sits between the application and the data source and handles the check transparently:

```typescript
// ── CACHE-ASIDE: application manages the cache explicitly ─────────────────────
async function getProduct_CacheAside(id: string): Promise<Product | null> {
    // Application code is aware of and responsible for the cache:
    const cached = await redis.get(`product:${id}`);
    if (cached) return JSON.parse(cached);

    const product = await db.findProduct(id);
    if (product) await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
    return product;
}

// ── READ-THROUGH: application only knows about the "datastore" ────────────────
// The caching layer (CacheManager below) intercepts the call transparently:
async function getProduct_ReadThrough(id: string): Promise<Product | null> {
    // Application code calls the cache layer as if it were the DB:
    return cacheManager.get(`product:${id}`, () => db.findProduct(id), 3600);
    // The cacheManager handles: check cache → call loader on miss → store → return
    // Application doesn't know or care whether it got the data from cache or DB
}

// ── Read-through CacheManager implementation ──────────────────────────────────
class CacheManager {
    constructor(private readonly redis: Redis) {}

    async get<T>(
        key:     string,
        loader:  () => Promise<T | null>,   // Called on cache miss to fetch from source
        ttl:     number,                    // Seconds
    ): Promise<T | null> {
        // Check cache:
        const cached = await this.redis.get(key);
        if (cached !== null) {
            return JSON.parse(cached) as T;
        }

        // Cache miss → call the loader (the "real" data source):
        const value = await loader();

        // Populate cache:
        if (value !== null) {
            await this.redis.setex(key, ttl, JSON.stringify(value));
        }

        return value;
    }

    async invalidate(key: string): Promise<void> {
        await this.redis.del(key);
    }

    async invalidatePattern(pattern: string): Promise<void> {
        let cursor = '0';
        do {
            const [next, keys] = await this.redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
            cursor = next;
            if (keys.length > 0) await this.redis.del(...keys);
        } while (cursor !== '0');
    }
}

// ── NestJS / dependency injection integration ─────────────────────────────────
@Injectable()
export class ProductService {
    constructor(
        private readonly cacheManager: CacheManager,
        private readonly productRepo: ProductRepository,
    ) {}

    // Clean service code — no explicit cache management:
    async findById(id: string): Promise<Product | null> {
        return this.cacheManager.get(
            `product:${id}`,
            () => this.productRepo.findById(id),
            3600,
        );
    }

    async findByCategory(categoryId: string): Promise<Product[]> {
        return this.cacheManager.get(
            `products:category:${categoryId}`,
            () => this.productRepo.findByCategory(categoryId),
            1800,
        ) ?? [];
    }

    async update(id: string, dto: UpdateProductDto): Promise<Product> {
        const product = await this.productRepo.update(id, dto);
        // Still need explicit invalidation on writes:
        await this.cacheManager.invalidate(`product:${id}`);
        await this.cacheManager.invalidatePattern(`products:category:${product.categoryId}:*`);
        return product;
    }
}
```

Read-through with a framework (conceptual decorator approach):

```typescript
// Many frameworks implement read-through as a decorator or annotation:

// NestJS with cache-manager:
import { CacheInterceptor } from '@nestjs/cache-manager';

@Controller('products')
@UseInterceptors(CacheInterceptor)  // Read-through: auto-caches responses
export class ProductController {
    @Get(':id')
    @CacheTTL(3600)
    async getProduct(@Param('id') id: string): Promise<Product> {
        return this.productService.findById(id);
        // First request: not cached → handler runs → response cached
        // Subsequent requests: cached → handler doesn't run → cached response returned
    }
}

// The framework-provided read-through handles:
// - Cache key generation (based on URL/params by default)
// - Cache lookup and population
// - TTL management
// Application code is completely unaware of caching
```

**Q10. What is negative caching — and why is it essential for read-through and cache-aside?**

A: Negative caching stores a "null" or "not found" result in the cache when a key lookup returns nothing. Without it, repeated lookups for non-existent keys always miss the cache and hit the database — a common attack vector (cache penetration) and a source of unnecessary DB load:

```typescript
// ── The problem without negative caching ──────────────────────────────────────
async function getProduct_NegativeBug(id: string): Promise<Product | null> {
    const cached = await redis.get(`product:${id}`);
    if (cached) return JSON.parse(cached);

    const product = await db.findProduct(id);  // ← Always called for non-existent IDs

    if (product) {  // ← Only caches if found, never if null
        await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
    }

    return null;
}
// Attacker sends: GET /products/fake1, /products/fake2, ..., /products/fake1000000
// Each request: cache miss → DB query → null → nothing cached → repeat forever
// DB drowns in queries for non-existent products (cache penetration attack)

// ── Fix: negative caching ─────────────────────────────────────────────────────
const NEGATIVE_CACHE_SENTINEL = 'null_sentinel';   // A value that means "not found"
const NEGATIVE_CACHE_TTL      = 300;               // 5 minutes (shorter than positive TTL)

async function getProduct_WithNegativeCache(id: string): Promise<Product | null> {
    const cached = await redis.get(`product:${id}`);

    if (cached !== null) {
        // Check if this is a "not found" sentinel:
        if (cached === NEGATIVE_CACHE_SENTINEL) {
            return null;  // Cache hit for non-existent item
        }
        return JSON.parse(cached);  // Cache hit for existing item
    }

    const product = await db.findProduct(id);

    if (product) {
        // Cache the found product with standard TTL:
        await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
    } else {
        // Cache the "not found" result with SHORT TTL:
        // Short TTL: if the product is created soon, we don't serve stale "null" for long
        await redis.setex(`product:${id}`, NEGATIVE_CACHE_TTL, NEGATIVE_CACHE_SENTINEL);
    }

    return product ?? null;
}

// ── Alternative: use a Bloom filter to skip cache for definitely-non-existent keys ──
// For very large ID spaces, a Bloom filter (probabilistic data structure) tells you
// with certainty if something does NOT exist, without querying the DB:
import { BloomFilter } from 'bloomfilter';

class ProductCache {
    // Bloom filter initialised with all existing product IDs:
    private bloomFilter = new BloomFilter(10_000_000, 4);  // 10M items, 4 hash functions

    constructor() {
        // Populate on startup:
        this.seedBloomFilter();
    }

    private async seedBloomFilter(): Promise<void> {
        const ids = await db.query('SELECT id FROM products');
        for (const row of ids.rows) {
            this.bloomFilter.add(row.id);
        }
    }

    async getProduct(id: string): Promise<Product | null> {
        // Quick check: does this ID DEFINITELY not exist?
        if (!this.bloomFilter.test(id)) {
            return null;  // Bloom filter says: definitely not in DB → don't even query
        }

        // ID might exist → proceed with cache/DB check
        const cached = await redis.get(`product:${id}`);
        if (cached) return JSON.parse(cached);

        const product = await db.findProduct(id);
        if (product) {
            await redis.setex(`product:${id}`, 3600, JSON.stringify(product));
        }
        return product ?? null;
    }
}
// Bloom filter false positive rate: 0.1-1% → occasionally queries DB for non-existent IDs
// Bloom filter false negative rate: 0% → never misses a real ID
```

## Section 6: Choosing and Combining Patterns

**Q11. How do you combine multiple caching patterns in a real application — and how do the patterns interact?**

A: Production systems rarely use a single caching pattern in isolation. The common architecture combines cache-aside for reads (or read-through for transparency) with write-through or write-behind for writes, selected per-entity based on consistency requirements:

```typescript
// ── Entity-by-entity pattern selection ────────────────────────────────────────

// User profiles: write-through (consistency critical — display on every page)
// Product catalogue: cache-aside (high read volume, infrequent writes)
// Session data: write-through or noeviction (must not be silently lost)
// Analytics events: write-behind (high volume, DB persistence can lag)
// Configuration: cache-aside with long TTL (changes rarely, reads are critical)

class ApplicationCache {
    // USER PROFILES — write-through (strong consistency)
    async getUserProfile(userId: string): Promise<UserProfile | null> {
        const cached = await redis.get(`user:profile:${userId}`);
        if (cached) return JSON.parse(cached);

        const profile = await db.findUserProfile(userId);
        if (profile) await redis.setex(`user:profile:${userId}`, 3600, JSON.stringify(profile));
        return profile;
    }

    async updateUserProfile(userId: string, data: UpdateProfileInput): Promise<UserProfile> {
        // Write-through: update DB AND cache together
        const profile = await db.updateUserProfile(userId, data);
        await redis.setex(`user:profile:${userId}`, 3600, JSON.stringify(profile));
        return profile;
    }

    // PRODUCT CATALOGUE — cache-aside (high read volume, writes are infrequent)
    async getProduct(productId: string): Promise<Product | null> {
        const cached = await redis.get(`product:${productId}`);
        if (cached) return JSON.parse(cached);

        const product = await db.findProduct(productId);
        if (product) await redis.setex(`product:${productId}`, 7200, JSON.stringify(product));
        return product;
    }

    async updateProduct(productId: string, data: UpdateProductInput): Promise<Product> {
        // Cache-aside: update DB, then invalidate (not update) cache
        const product = await db.updateProduct(productId, data);
        await redis.del(`product:${productId}`);     // Invalidate
        await redis.del(`products:category:${product.categoryId}`);  // Invalidate list too
        return product;
    }

    // ANALYTICS EVENTS — write-behind (high throughput, eventual consistency OK)
    async recordEvent(event: AnalyticsEvent): Promise<void> {
        // Write to cache immediately (for real-time dashboards):
        await redis.lpush(`events:${event.userId}`, JSON.stringify(event));
        await redis.expire(`events:${event.userId}`, 3600);

        // Enqueue for async DB write (batched):
        await redis.lpush('analytics_write_queue', JSON.stringify(event));
        // Background worker flushes this queue to DB every 5 seconds in batches
    }
}

// ── Cache hierarchy: L1 (in-process) → L2 (Redis) → L3 (DB) ──────────────────
// For ultra-high-frequency reads, add an in-process memory cache as L1:
class MultiLevelCache {
    private l1Cache = new Map<string, { value: unknown; expiresAt: number }>();
    private readonly L1_TTL_MS = 5000;  // 5 seconds in-process cache

    async get<T>(key: string, loader: () => Promise<T | null>, redisTtl: number): Promise<T | null> {
        // L1: in-process memory (fastest, no network)
        const l1Entry = this.l1Cache.get(key);
        if (l1Entry && l1Entry.expiresAt > Date.now()) {
            return l1Entry.value as T;
        }

        // L2: Redis (fast, shared across processes)
        const cached = await redis.get(key);
        if (cached !== null) {
            const value = JSON.parse(cached) as T;
            // Populate L1 from L2:
            this.l1Cache.set(key, { value, expiresAt: Date.now() + this.L1_TTL_MS });
            return value;
        }

        // L3: Database (slow, source of truth)
        const value = await loader();
        if (value !== null) {
            // Populate both L1 and L2:
            this.l1Cache.set(key, { value, expiresAt: Date.now() + this.L1_TTL_MS });
            await redis.setex(key, redisTtl, JSON.stringify(value));
        }

        return value;
    }

    invalidate(key: string): void {
        // Must invalidate both layers:
        this.l1Cache.delete(key);
        redis.del(key).catch(err => logger.error({ err, key }, 'L2 invalidation failed'));
    }
}
```

## Section 7: Scenario-Based Questions

**Q12. "Your cache hit rate is 95% but users are still seeing stale product prices after updates. The update code calls `redis.del(key)` correctly. What's wrong?"**

A:

```typescript
// ── Diagnosis checklist ───────────────────────────────────────────────────────

// Problem 1: Multiple cache key formats (most common cause)
// The update deletes `product:123` but the GET populates `product:id:123`
async function update(id: string) {
    await db.updateProduct(id);
    await redis.del(`product:${id}`);            // Deletes this key
}

async function get(id: string) {
    const cached = await redis.get(`product:id:${id}`);  // Different key format!
    if (cached) return JSON.parse(cached);
    // ... populates `product:id:${id}` but update deletes `product:${id}`
}
// Fix: centralise key generation in one function:
const cacheKey = (id: string) => `product:${id}`;

// Problem 2: Multiple cache entries for the same data
// List/search results contain the product but aren't invalidated:
async function update(id: string, data: UpdateProductInput) {
    const product = await db.updateProduct(id, data);
    await redis.del(`product:${id}`);            // Single item: invalidated ✓
    // BUT: forgot to invalidate:
    // `products:category:${product.categoryId}` ← list contains stale product
    // `products:search:*`                        ← search cache contains stale product
    // `homepage:featured`                        ← homepage cache has the product
    return product;
}
// Fix: systematically track ALL cache keys that include this product
// Use cache tagging or per-entity invalidation lists (see below)

// Problem 3: Race condition — read between delete and repopulation
// t=0: Update runs → writes to DB → calls redis.del(`product:${id}`)
// t=1: Request A: GET → cache miss → queries DB → gets fresh data → SET cache
// t=2: Another stale-cache issue from a different code path overwrites with old data
// Fix: always SET from the DB result, never from application memory

// Problem 4: Multiple deployment instances, inconsistent code
// Old instance: caches key as `prod:${id}`
// New instance: reads/invalidates key as `product:${id}`
// During rolling deployment: old cache key is never invalidated
// Fix: key versioning — include a version in all cache keys
const KEY_VERSION = 'v2';
const cacheKey = (id: string) => `product:${KEY_VERSION}:${id}`;
// Rolling deploy: old `product:v1:${id}` keys are ignored, new `v2` keys are fresh

// Problem 5: Cache invalidation failed silently
async function update(id: string) {
    await db.updateProduct(id);
    try {
        await redis.del(`product:${id}`);
    } catch (err) {
        // Swallowed the error — redis.del failed but nothing alerted
        logger.error(err);  // Logged but not monitored
    }
}
// Fix: monitor cache invalidation failures as alerts, not just logs

// ── Cache tagging for systematic invalidation ─────────────────────────────────
class TaggedCache {
    async set(key: string, value: unknown, ttl: number, tags: string[]): Promise<void> {
        await redis.setex(key, ttl, JSON.stringify(value));

        // Register this key under each tag:
        for (const tag of tags) {
            await redis.sadd(`tag:${tag}`, key);
            await redis.expire(`tag:${tag}`, ttl + 60);  // Tag set expires slightly after entries
        }
    }

    async invalidateByTag(tag: string): Promise<void> {
        const keys = await redis.smembers(`tag:${tag}`);
        if (keys.length > 0) {
            await redis.del(...keys);
        }
        await redis.del(`tag:${tag}`);
    }
}

// Usage:
const taggedCache = new TaggedCache();

// Cache a product under multiple tags:
await taggedCache.set(
    `product:${id}`,
    product,
    3600,
    [`product:${id}`, `category:${product.categoryId}`, 'products']
);

// When a product updates: invalidate everything tagged with it
await taggedCache.invalidateByTag(`product:${id}`);
// Automatically clears: the product entry, category lists, any composite cache entries
```

**Q13. "Design the caching strategy for an e-commerce platform's product catalogue — you need: product detail pages (high read, infrequent write), inventory stock levels (frequent reads AND writes), and order history (write-heavy, infrequent reads)."**

A:

```typescript
// ── Product Detail Pages: Cache-Aside + Long TTL ───────────────────────────────
// Characteristics: 10,000 reads per product per day, updated rarely (price changes ~weekly)
// Strategy: cache-aside, 4-hour TTL, write-invalidation on update

class ProductDetailCache {
    private readonly TTL = 4 * 3600;  // 4 hours

    async get(productId: string): Promise<ProductDetail | null> {
        const key    = `product:detail:v3:${productId}`;
        const cached = await redis.get(key);
        if (cached) return JSON.parse(cached);

        const product = await db.getProductWithDetails(productId);
        // Cache everything needed for the detail page in one entry:
        // (product + related products + spec sheet + reviews summary)
        // Avoids multiple cache lookups per page render

        if (product) {
            await redis.setex(key, this.TTL, JSON.stringify(product));
        } else {
            // Negative cache: product doesn't exist
            await redis.setex(key, 300, 'null_sentinel');
        }

        return product;
    }

    async invalidate(productId: string): Promise<void> {
        await redis.del(`product:detail:v3:${productId}`);
        // Also invalidate category listing pages that showed this product:
        await redis.del(`product:list:category:${product.categoryId}`);
    }
}

// ── Inventory Stock Levels: Write-Through + Short TTL ─────────────────────────
// Characteristics: Read on every product page load; written on every purchase/restock
// Strategy: write-through (cache always reflects current stock), short TTL (5 min)
// Critical: overselling is a serious problem → strong consistency is essential

class InventoryCache {
    private readonly TTL = 300;  // 5 minutes

    async getStock(productId: string): Promise<number> {
        const key    = `inventory:stock:${productId}`;
        const cached = await redis.get(key);
        if (cached !== null) return parseInt(cached, 10);

        const stock = await db.getStockLevel(productId);
        await redis.setex(key, this.TTL, stock.toString());
        return stock;
    }

    // Write-through: update DB AND cache atomically (as much as possible)
    async reserveStock(productId: string, quantity: number): Promise<boolean> {
        // Use DB transaction for the authoritative check and decrement:
        const result = await db.transaction(async (tx) => {
            const stock = await tx.query(
                'SELECT quantity FROM inventory WHERE product_id = $1 FOR UPDATE',
                [productId]
            );
            if (stock.rows[0].quantity < quantity) return false;

            await tx.query(
                'UPDATE inventory SET quantity = quantity - $1 WHERE product_id = $2',
                [quantity, productId]
            );
            return true;
        });

        if (result) {
            // Write-through: reflect the DB state in cache immediately
            const newStock = await db.getStockLevel(productId);
            await redis.setex(`inventory:stock:${productId}`, this.TTL, newStock.toString());
        }

        return result;
    }

    // Real-time stock updates via Redis atomic decrement (with DB sync):
    async atomicDecrement(productId: string, quantity: number): Promise<number> {
        const key = `inventory:stock:${productId}`;

        // Ensure cache is warm before decrement:
        const warm = await redis.exists(key);
        if (!warm) {
            const stock = await db.getStockLevel(productId);
            await redis.setex(key, this.TTL, stock.toString());
        }

        // Atomic decrement in Redis (prevents race conditions):
        const newValue = await redis.decrby(key, quantity);

        if (newValue < 0) {
            // Rolled past zero → restore and reject
            await redis.incrby(key, quantity);
            return -1;  // Indicate insufficient stock
        }

        // Async DB sync (write-behind for the counter, but with DB as final authority):
        setImmediate(() => {
            db.query(
                'UPDATE inventory SET quantity = $1 WHERE product_id = $2 AND quantity > $1',
                [newValue, productId]
            ).catch(err => logger.error({ err }, 'Inventory sync failed'));
        });

        return newValue;
    }
}

// ── Order History: Write-Behind + No Caching for Reads ────────────────────────
// Characteristics: Written on every order (high volume); read rarely (order history page)
// Strategy: write-behind for DB persistence; no Redis caching for reads
// (Order history pages are low-traffic; no benefit to caching them)

class OrderService {
    async createOrder(orderData: CreateOrderInput): Promise<Order> {
        // Write to cache FIRST (for real-time order tracking):
        const order = {
            id:         generateId(),
            ...orderData,
            status:     'pending',
            createdAt:  new Date().toISOString(),
        };

        await redis.setex(`order:${order.id}`, 86400, JSON.stringify(order));
        // User can immediately see their order status via the cache

        // Enqueue DB write (write-behind):
        await redis.lpush('order_write_queue', JSON.stringify(order));

        return order;
    }

    // Order status (read from cache — real-time):
    async getOrderStatus(orderId: string): Promise<string | null> {
        const cached = await redis.get(`order:${orderId}`);
        if (cached) return JSON.parse(cached).status;
        return null;
    }

    // Order HISTORY page (skip cache — read from DB, infrequent):
    async getOrderHistory(userId: string, page: number): Promise<Order[]> {
        // No cache here: rare read, large result set, not worth the cache space
        return db.getOrdersByUser(userId, page);
    }
}

// ── Summary of pattern selection ───────────────────────────────────────────────
//
// Product Details:  Cache-Aside   — infrequent writes, very high read volume
// Inventory Stock:  Write-Through — frequent reads AND writes, consistency critical
// Order Status:     Write-Behind  — very high write volume, reads from cache
// Order History:    No Cache      — infrequent reads, large result sets
```

## Quick Reference Table

| Pattern | Read flow | Write flow | Consistency | Write latency | Cache pollution | Best for |
|---|---|---|---|---|---|---|
| **Cache-Aside** | App: cache → DB on miss → cache | App: write DB → delete cache | Eventual (stale window) | Low (just DB + delete) | Low (only misses populate) | High read-to-write ratio; general purpose |
| **Read-Through** | Library: cache → DB on miss → cache | App: write DB → delete cache | Eventual | Low | Low | Same as cache-aside but cleaner code |
| **Write-Through** | App/lib: cache → DB on miss | Library: write cache → write DB | Strong (cache ≈ DB) | Higher (cache + DB) | High (all writes cached) | Write then read same data; consistency critical |
| **Write-Behind** | App/lib: cache → DB on miss | Library: write cache → async DB | Eventual (DB lags) | Very low (cache only) | Low | High write throughput; eventual consistency OK |

| Pattern | Risk | Mitigation |
|---|---|---|
| Cache-Aside | Thundering herd on expiry | Mutex lock or probabilistic early expiration |
| Cache-Aside | Stale data if invalidation fails | Short TTL as backstop; retry invalidation |
| Cache-Aside | Cache penetration (non-existent keys) | Negative caching; Bloom filter |
| Write-Through | Cache pollution (write-never-read data) | Targeted use (only for data that IS read after write) |
| Write-Through | Write amplification (every write touches both) | Accept the cost; monitor write latency |
| Write-Behind | Data loss if queue/cache fails | Durable queue (Kafka/SQS); Redis AOF persistence |
| Write-Behind | Dirty reads from DB (other services see stale) | All readers must go through the cache |
| Write-Behind | Out-of-order writes land wrong value in DB | Timestamp-based conditional updates in DB |
| Read-Through | Still requires explicit write invalidation | Combine with a cache manager that handles invalidation |

**Tip for interviews:** Six things separate strong candidates on this topic: (1) explaining **why cache-aside invalidates (DEL) instead of updating (SET) on writes** — if the application writes old data to the cache after a concurrent writer has already written newer data, the cache ends up with a stale value that won't expire until the TTL; DELETE is safe because the next read always fetches from the authoritative DB; UPDATE is only safe if writes are serialised or transactional across both systems; (2) articulating the **thundering herd problem** specifically — it's not just "many requests hit the DB at once" but precisely that all concurrent readers see a cache miss for the same key simultaneously (e.g., after a popular key's TTL expires), producing N identical DB queries that the cache was supposed to prevent; the mutex lock and probabilistic early expiration are the two standard solutions; (3) knowing that **write-behind is the only pattern with real data loss risk** — a cache failure or queue failure before the background writer drains it means writes are permanently lost; the mitigation is a durable queue (Kafka, SQS) rather than an in-memory or Redis list; (4) explaining **cache penetration** and negative caching — attackers or bugs that query non-existent keys bypass the cache on every request; storing a sentinel value for "not found" (with a short TTL) prevents the DB from being hit repeatedly for the same missing key; (5) knowing **when to combine patterns** — a single application typically uses cache-aside for product catalogues (high reads, rare writes), write-through for session data (must be consistent), and write-behind for analytics events (high write volume, eventual consistency acceptable); the choice is per-entity, not per-application; and (6) explaining the **read-through vs cache-aside distinction** — functionally identical for the caller, but read-through moves caching responsibility from application code to a caching framework layer; cache-aside is explicit (application code knows about Redis), read-through is transparent (application code only knows about the caching layer's interface); the trade-off is between control and simplicity.
