### Section 1: String

**Q1. What is the Redis String type and what makes it more powerful than its name implies?**
A: A Redis String is a binary-safe sequence of bytes — it can hold text, serialized JSON, raw binary data, integers, or floating-point numbers. Despite being called a "string," it is the most general-purpose Redis type and underpins several higher-level patterns.

```
Maximum size: 512 MB per key
Internal encoding (automatic, based on value):
  int:      when the value is an integer fitting in a long (e.g., "42")
  embstr:   strings ≤ 44 bytes (single memory allocation)
  raw:      strings > 44 bytes (two allocations: the SDS struct + the buffer)
```

```bash
# ── Core commands ────────────────────────────────────────────────────
SET    key value [EX seconds] [PX milliseconds] [NX|XX] [GET] [KEEPTTL]
GET    key
MGET   key [key ...]         # atomic multi-get (one round trip)
MSET   key value [key value ...] # atomic multi-set
GETSET key value             # set + return old value (atomically)
GETDEL key                   # get + delete (atomically) — Redis 6.2+
APPEND key value             # append to existing string value

# Numeric operations (atomic — no race conditions):
INCR    key                  # increment integer by 1 (creates key at 0 if missing)
INCRBY  key increment        # increment by N
INCRBYFLOAT key increment    # increment float
DECR    key
DECRBY  key decrement

# Expiry variants:
SETEX   key seconds value    # SET + EXPIRE atomically (legacy)
PSETEX  key milliseconds value
SET key value EX 3600        # modern equivalent (preferred)
```

```python
import json, redis

r = redis.Redis()

def get_product(product_id: str) -> dict:
    cache_key = f"product:{product_id}"
    cached    = r.get(cache_key)

    if cached:
        return json.loads(cached)  # cache hit → 0 database I/O

    product = db.products.find_one({"_id": product_id})  # cache miss → DB query
    r.setex(
        cache_key,
        3600,              # TTL: 1 hour
        json.dumps(product)
    )
    return product

# Batch fetch with MGET — one round trip for many items:
def get_products(ids: list[str]) -> list[dict | None]:
    keys    = [f"product:{pid}" for pid in ids]
    cached  = r.mget(*keys)   # single round trip → list of bytes | None

    results = []
    missing_ids = []
    for pid, val in zip(ids, cached):
        if val:
            results.append(json.loads(val))
        else:
            results.append(None)   # placeholder
            missing_ids.append(pid)

    # Fetch and cache only the missing ones:
    if missing_ids:
        from_db = db.products.find({"_id": {"$in": missing_ids}})
        pipe    = r.pipeline()
        for product in from_db:
            pipe.setex(f"product:{product['_id']}", 3600, json.dumps(product))
        pipe.execute()

    return results
```

```python
import uuid

def acquire_lock(resource: str, ttl_ms: int = 5000) -> str | None:
    lock_id = str(uuid.uuid4())   # unique token to identify this lock holder
    # SET NX PX: set only if NOT EXISTS, with millisecond expiry
    # Atomic: prevents two callers from both seeing "key doesn't exist"
    acquired = r.set(
        f"lock:{resource}",
        lock_id,
        px=ttl_ms,    # auto-expire: prevents deadlock if process crashes
        nx=True       # NX: only set if key does not already exist
    )
    return lock_id if acquired else None

def release_lock(resource: str, lock_id: str) -> bool:
    # MUST verify we own the lock before releasing
    # Use a Lua script for atomic check-and-delete:
    script = """
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
    """
    result = r.eval(script, 1, f"lock:{resource}", lock_id)
    return result == 1

# Usage:
lock_id = acquire_lock("payment:user:42", ttl_ms=3000)
if lock_id:
    try:
        process_payment(user_id=42)
    finally:
        release_lock("payment:user:42", lock_id)
else:
    raise LockNotAcquiredError("Another process is processing payment for user 42")
```

### Section 2: List

**Q2. What is the Redis List and what access patterns does it enable that other data structures can't?**
A: A Redis List is a doubly-linked list of strings. It supports O(1) push and pop from either end and O(n) random access. The linked-list structure makes it optimal for queue and stack patterns, and the blocking commands (`BLPOP`, `BRPOP`) enable efficient work distribution without polling.

```bash
# Push / pop from both ends:
LPUSH key value [value ...]   # push to LEFT (head)
RPUSH key value [value ...]   # push to RIGHT (tail)
LPOP  key [count]             # pop from LEFT
RPOP  key [count]             # pop from RIGHT

# Blocking pop — waits up to timeout for an element:
BLPOP  key [key ...] timeout  # blocks if list empty; 0 = wait forever
BRPOP  key [key ...] timeout

# Range / trim:
LRANGE key start stop         # 0-based; -1 = last element; O(n)
LTRIM  key start stop         # keep only elements in range; O(n)
LLEN   key                    # O(1)
LINDEX key index              # O(n) — avoid for large lists
LINSERT key BEFORE|AFTER pivot value
```

**Use case 1 — Task queue (producer-consumer):**
```python
# Producer: web request handler
def enqueue_email(to: str, subject: str, body: str) -> None:
    task = json.dumps({"to": to, "subject": subject, "body": body, "ts": time.time()})
    r.rpush("queue:emails", task)   # RPUSH to tail (FIFO with BLPOP from head)

# Consumer: background worker process
def email_worker() -> None:
    print("Email worker started, waiting for jobs...")
    while True:
        # BLPOP blocks for up to 5 seconds if queue is empty
        # Returns: [b'queue:emails', b'{"to":...}'] or None
        result = r.blpop("queue:emails", timeout=5)
        if result is None:
            continue   # timeout — loop and check again

        _, raw_task = result
        task = json.loads(raw_task)
        try:
            send_email(task["to"], task["subject"], task["body"])
        except Exception as e:
            # Reliability concern: if worker crashes mid-processing, task is lost
            # For reliability: use BRPOPLPUSH to move to a "processing" list first
            r.rpush("queue:emails:failed", raw_task)

# Reliable queue with LMOVE (Redis 6.2+) / BRPOPLPUSH (legacy):
def reliable_email_worker() -> None:
    while True:
        # Atomically move from "pending" to "processing":
        raw_task = r.lmove(
            "queue:emails",
            "queue:emails:processing",
            src="LEFT", dst="RIGHT"
        )
        if raw_task is None:
            time.sleep(0.1)
            continue

        task = json.loads(raw_task)
        try:
            send_email(task["to"], task["subject"], task["body"])
            r.lrem("queue:emails:processing", 1, raw_task)  # remove from processing
        except Exception:
            # Move back to failed; processing list still holds it until resolved
            r.rpush("queue:emails:failed", raw_task)
            r.lrem("queue:emails:processing", 1, raw_task)
```

### Section 3: Hash

**Q3. What is the Redis Hash and when does it outperform storing serialized JSON in a String?**
A: A Redis Hash is a map of field-value pairs, similar to a Python dict or JavaScript object. It enables partial reads and partial updates — you can read a single field or update one field without loading and re-serializing the entire object. It also enables atomic field-level increments.

```bash
HSET    key field value [field value ...]   # set one or more fields (Redis 4.0+)
HGET    key field
HMGET   key field [field ...]               # multi-field get (one round trip)
HGETALL key                                 # all fields and values
HDEL    key field [field ...]
HEXISTS key field
HLEN    key
HKEYS   key                                 # all field names
HVALS   key                                 # all values
HINCRBY     key field increment             # atomic increment on integer field
HINCRBYFLOAT key field increment
HSCAN       key cursor [MATCH pattern] [COUNT count]  # iterate (large hashes)
```

**Use case 1 — User profile / object storage:**
```python
# Store user as Hash — fields readable independently:
def create_user(user_id: str, data: dict) -> None:
    r.hset(f"user:{user_id}", mapping={
        "name":       data["name"],
        "email":      data["email"],
        "plan":       data["plan"],       # "free" | "pro" | "enterprise"
        "credits":    str(data.get("credits", 0)),
        "created_at": str(int(time.time())),
        "login_count": "0",
    })
    r.expire(f"user:{user_id}", 86400 * 30)   # 30-day cache

# Partial read — get only what you need (no JSON deserialization overhead):
def get_user_plan(user_id: str) -> str:
    return r.hget(f"user:{user_id}", "plan").decode()   # reads ONE field only

# Partial update — no read-modify-write cycle:
def upgrade_user(user_id: str, new_plan: str) -> None:
    r.hset(f"user:{user_id}", "plan", new_plan)         # updates ONE field only

# Atomic increment on a specific field:
def consume_credit(user_id: str) -> int:
    remaining = r.hincrby(f"user:{user_id}", "credits", -1)
    if remaining < 0:
        r.hincrby(f"user:{user_id}", "credits", 1)      # rollback
        raise InsufficientCreditsError()
    return remaining

# Batch read with HMGET — single round trip for multiple fields:
def get_user_display_info(user_id: str) -> dict:
    name, plan, credits = r.hmget(f"user:{user_id}", "name", "plan", "credits")
    return {
        "name":    name.decode() if name else None,
        "plan":    plan.decode() if plan else None,
        "credits": int(credits) if credits else 0,
    }

# String approach (comparison — worse for partial access):
# r.setex(f"user:{user_id}", 86400*30, json.dumps(user_data))
# Upgrading plan: GET → json.loads → modify → json.dumps → SET
# Three Redis operations vs ONE HSET for partial update
```

**Use case 3 — Rate limiting with per-endpoint counters:**
```python
def check_rate_limit(user_id: str, window_key: str, limits: dict) -> bool:
    # Hash: one key per user per time window; fields = endpoints
    hash_key = f"ratelimit:{user_id}:{window_key}"

    pipe = r.pipeline()
    for endpoint in limits:
        pipe.hincrby(hash_key, endpoint, 0)   # get current count
    pipe.expire(hash_key, 60)
    results = pipe.execute()

    for endpoint, current in zip(limits.keys(), results[:-1]):
        if current >= limits[endpoint]:
            return False  # over limit

    return True
```

### Section 4: Set

**Q4. What is the Redis Set and what social-graph and analytics operations become trivial with it?**
A: A Redis Set is an unordered collection of unique strings. Uniqueness is enforced automatically — adding a duplicate is a no-op. Sets support O(1) membership testing and O(n) set algebra operations (union, intersection, difference) that enable powerful social graph queries.

```bash
SADD        key member [member ...]   # add members; returns count added
SREM        key member [member ...]   # remove members
SISMEMBER   key member                # is member in set? O(1)
SMISMEMBER  key member [member ...]   # multi-membership check (Redis 6.2+)
SMEMBERS    key                       # all members (avoid on large sets)
SCARD       key                       # cardinality (count) O(1)
SRANDMEMBER key [count]               # random member(s) without removing
SPOP        key [count]               # remove and return random member(s)

# Set algebra:
SUNION      key [key ...]             # union of all sets
SINTER      key [key ...]             # intersection
SDIFF       key [key ...]             # members in first set not in others
SUNIONSTORE destination key [key ...] # union → store in destination
SINTERSTORE destination key [key ...]
SDIFFSTORE  destination key [key ...]
```

**Use case 1 — Social graph (followers/following):**
```python
def follow(follower_id: str, followed_id: str) -> None:
    r.sadd(f"following:{follower_id}", followed_id)
    r.sadd(f"followers:{followed_id}", follower_id)

def unfollow(follower_id: str, followed_id: str) -> None:
    r.srem(f"following:{follower_id}", followed_id)
    r.srem(f"followers:{followed_id}", follower_id)

def is_following(follower_id: str, followed_id: str) -> bool:
    return r.sismember(f"following:{follower_id}", followed_id)

def get_follow_counts(user_id: str) -> dict:
    return {
        "followers": r.scard(f"followers:{user_id}"),
        "following": r.scard(f"following:{user_id}"),
    }

# Mutual friends ("people you both follow"):
def mutual_friends(user_a: str, user_b: str) -> set:
    return r.sinter(f"following:{user_a}", f"following:{user_b}")

# "People you might know" (friends of friends, not already following):
def suggested_follows(user_id: str) -> set:
    # Who does user_id follow?
    already_following = r.smembers(f"following:{user_id}")
    # Collect everyone those people follow:
    pipe = r.pipeline()
    for uid in already_following:
        pipe.smembers(f"following:{uid.decode()}")
    sets_of_friends = pipe.execute()  # list of sets

    # Union all friends-of-friends:
    all_fof = set()
    for s in sets_of_friends:
        all_fof.update(s)

    # Remove: already following + self:
    return all_fof - already_following - {user_id.encode()}

# Or use SUNIONSTORE for large graphs (avoids pulling all data to application):
def suggested_follows_server_side(user_id: str) -> list:
    following_keys = [f"following:{uid.decode()}"
                      for uid in r.smembers(f"following:{user_id}")]
    if not following_keys:
        return []
    tmp_key = f"tmp:fof:{user_id}"
    r.sunionstore(tmp_key, *following_keys)    # union computed server-side
    r.sdiffstore(tmp_key, tmp_key,             # remove already-following + self
                 f"following:{user_id}", f"self:{user_id}")
    suggestions = r.smembers(tmp_key)
    r.delete(tmp_key)
    return suggestions
```

### Section 5: Sorted Set

**Q5. What is the Redis Sorted Set and what makes it the most versatile Redis data structure?**
A: A Sorted Set (ZSet) is a collection of unique members, each with an associated floating-point **score**. Members are always ordered by score (ascending). It combines the uniqueness of a Set with the ordering of a sorted list, enabling O(log N) rank queries, range queries by score, and sliding-window time operations. The score can represent anything numeric: rank, timestamp, priority, distance, relevance.

```bash
ZADD    key [NX|XX] [GT|LT] [CH] [INCR] score member [score member ...]
ZSCORE  key member              # get member's score; O(1)
ZRANK   key member              # 0-based rank (ascending); O(log N)
ZREVRANK key member             # rank in descending order
ZRANGE  key start stop [BYSCORE|BYLEX] [REV] [LIMIT offset count] [WITHSCORES]
ZRANGEBYSCORE key min max [WITHSCORES] [LIMIT offset count]   # by score range
ZREVRANGEBYSCORE key max min ...  # descending score range
ZRANGEBYLEX key min max [LIMIT offset count]  # lexicographic range (equal scores)
ZREM    key member [member ...]
ZINCRBY key increment member     # atomic score increment
ZCARD   key                      # total count; O(1)
ZCOUNT  key min max              # count members with score in [min, max]
ZPOPMIN key [count]              # remove + return lowest-score members
ZPOPMAX key [count]              # remove + return highest-score members
ZUNIONSTORE destination numkeys key [key ...] [WEIGHTS ...] [AGGREGATE SUM|MIN|MAX]
ZINTERSTORE destination numkeys key [key ...] ...
ZDIFFSTORE destination numkeys key [key ...]
```

**Use case 1 — Leaderboard:**
```python
# Add / update scores:
def update_score(leaderboard: str, user_id: str, score: float) -> None:
    r.zadd(leaderboard, {user_id: score})
    # ZSets are always sorted — no manual ordering needed

def increment_score(leaderboard: str, user_id: str, points: float) -> float:
    return r.zincrby(leaderboard, points, user_id)   # atomic; returns new score

# Top-N players:
def get_top_n(leaderboard: str, n: int = 10) -> list[dict]:
    # ZREVRANGE: highest scores first (descending)
    top = r.zrevrange(leaderboard, 0, n - 1, withscores=True)
    return [
        {"rank": i + 1, "user_id": uid.decode(), "score": score}
        for i, (uid, score) in enumerate(top)
    ]

# A specific user's rank:
def get_user_rank(leaderboard: str, user_id: str) -> dict:
    rank  = r.zrevrank(leaderboard, user_id)   # 0-based; None if not found
    score = r.zscore(leaderboard, user_id)
    return {
        "rank":  (rank + 1) if rank is not None else None,  # 1-based
        "score": score,
    }

# Players around a given user ("neighborhood" in leaderboard):
def get_nearby_players(leaderboard: str, user_id: str, radius: int = 5) -> list[dict]:
    rank = r.zrevrank(leaderboard, user_id)
    if rank is None:
        return []
    start = max(0, rank - radius)
    stop  = rank + radius
    nearby = r.zrevrange(leaderboard, start, stop, withscores=True)
    return [
        {
            "rank":    start + i + 1,
            "user_id": uid.decode(),
            "score":   score,
            "is_self": uid.decode() == user_id
        }
        for i, (uid, score) in enumerate(nearby)
    ]

# Score range query (players between 1000 and 2000 points):
def players_in_score_range(leaderboard: str, min_score: float, max_score: float) -> list:
    return r.zrangebyscore(leaderboard, min_score, max_score, withscores=True)
```

**Use case 2 — Sliding window rate limiter:**
```python
def is_rate_limited(user_id: str, limit: int, window_seconds: int) -> bool:
    key  = f"rate:{user_id}"
    now  = time.time()
    pipe = r.pipeline()

    # Remove timestamps outside the sliding window:
    pipe.zremrangebyscore(key, 0, now - window_seconds)
    # Add current request timestamp (score=timestamp, member=unique per request):
    pipe.zadd(key, {f"{now}:{uuid.uuid4()}": now})
    # Count requests in the window:
    pipe.zcard(key)
    # Expire the key (cleanup):
    pipe.expire(key, window_seconds + 1)

    _, _, count, _ = pipe.execute()

    return count > limit   # True = rate limited

# vs Fixed window rate limiter (String INCR approach):
def is_rate_limited_fixed(user_id: str, limit: int) -> bool:
    key     = f"rate:fixed:{user_id}:{int(time.time() // 60)}"  # per-minute bucket
    current = r.incr(key)
    if current == 1:
        r.expire(key, 60)   # first request in window → set expiry
    return current > limit

# Sliding window (ZSet): accurate; memory = O(requests in window) per user
# Fixed window (String): approximate (burst at window boundary); memory = O(1) per user
```

**Use case 3 — Priority queue:**
```python
def enqueue_job(queue: str, job: dict, priority: int) -> None:
    # Lower score = higher priority (1 is highest priority, 100 is lowest)
    r.zadd(queue, {json.dumps(job): priority})

def dequeue_job(queue: str) -> dict | None:
    # ZPOPMIN atomically removes and returns the lowest-scoring (highest-priority) element
    result = r.zpopmin(queue)  # [(member, score)]
    if not result:
        return None
    raw_job, priority = result[0]
    return json.loads(raw_job)

def peek_job(queue: str) -> dict | None:
    result = r.zrange(queue, 0, 0, withscores=True)  # lowest score, don't remove
    if not result:
        return None
    raw_job, priority = result[0]
    return {"job": json.loads(raw_job), "priority": priority}
```

```python
    now = time.time()

def get_events_in_range(stream_key: str, start_ts: float, end_ts: float) -> list[dict]:
    raw = r.zrangebyscore(stream_key, start_ts, end_ts)
    return [json.loads(item) for item in raw]

def cleanup_old_events(stream_key: str, max_age_seconds: int) -> int:
    cutoff = time.time() - max_age_seconds
    return r.zremrangebyscore(stream_key, 0, cutoff)   # returns count removed
```

### Section 6: Bitmap

**Q6. What is a Redis Bitmap and what makes it dramatically more memory-efficient than Sets for boolean tracking?**
A: A Redis Bitmap is not a separate data type — it is the String type accessed via bit-level operations. A bit at position `N` represents a boolean flag for the entity with ID `N`. Because each entity uses exactly 1 bit, tracking 1 million users requires only 128 KB of memory, versus ~50 MB in a Set (storing user ID strings).

```bash
SETBIT  key offset value         # set bit at position `offset` to 0 or 1
GETBIT  key offset               # get bit at position `offset`
BITCOUNT key [start end [BYTE|BIT]]  # count 1-bits (in byte range or bit range)
BITPOS  key bit [start [end [BYTE|BIT]]] # position of first 0 or 1 bit
BITOP   operation destkey key [key ...]  # AND, OR, XOR, NOT across bitmaps
```

**Use case 1 — Daily active users (DAU) tracking:**
```python
def mark_user_active(user_id: int, date: str) -> None:
    # Bit at position user_id = 1 means user was active on this date
    r.setbit(f"active:{date}", user_id, 1)
    # Memory: 10M users → 10M bits = 1.25 MB per day (vs 40-80 MB with Set)

def was_user_active(user_id: int, date: str) -> bool:
    return r.getbit(f"active:{date}", user_id) == 1

def count_dau(date: str) -> int:
    return r.bitcount(f"active:{date}")   # O(N/8): counts all 1-bits

# Users active on BOTH Monday and Tuesday (AND = retention):
def users_active_both_days(date1: str, date2: str) -> int:
    dest = f"tmp:active:both:{date1}:{date2}"
    r.bitop("AND", dest, f"active:{date1}", f"active:{date2}")
    count = r.bitcount(dest)
    r.delete(dest)
    return count

# Weekly active users (OR of 7 daily bitmaps):
def count_wau(dates: list[str]) -> int:

    dest = "tmp:active:week"
    r.bitop("OR", dest, *keys)   # union of 7 days
    count = r.bitcount(dest)
    r.delete(dest)
    return count
```

### Section 7: HyperLogLog

**Q7. What is HyperLogLog and when should you use it instead of a Set for cardinality counting?**
A: HyperLogLog (HLL) is a probabilistic data structure for **estimating** the number of unique elements. It uses at most 12 KB of memory regardless of the number of elements counted, versus memory proportional to the set size for an exact Set. The trade-off: approximately ±0.81% error rate.

```bash
PFADD   key element [element ...]    # add elements; returns 1 if HLL changed
PFCOUNT key [key ...]                # estimate cardinality
PFMERGE destkey sourcekey [sourcekey ...]  # merge multiple HLLs into one
```

**Use case 1 — Unique visitors at massive scale:**
```python
def track_visit(page: str, user_id: str, date: str) -> None:
    r.pfadd(f"hll:visitors:{page}:{date}", user_id)
    r.expire(f"hll:visitors:{page}:{date}", 86400 * 90)  # keep 90 days

def estimate_unique_visitors(page: str, date: str) -> int:
    return r.pfcount(f"hll:visitors:{page}:{date}")
    # 10M unique visitors → ~12 KB memory (vs ~400 MB for a Set with string IDs)
    # Error: ±0.81% → "about 10,000,000" ± 81,000

# Count unique visitors across multiple pages (OR across pages):
def estimate_unique_visitors_across_pages(pages: list[str], date: str) -> int:
    keys = [f"hll:visitors:{page}:{date}" for page in pages]
    return r.pfcount(*keys)   # PFCOUNT on multiple keys = union estimate

# Merge HLLs for weekly report (don't re-add all raw events):
def merge_weekly_hll(page: str, week_dates: list[str]) -> None:
    src_keys  = [f"hll:visitors:{page}:{d}" for d in week_dates]
    dest_key  = f"hll:visitors:{page}:week:{week_dates[0]}"
    r.pfmerge(dest_key, *src_keys)
    r.expire(dest_key, 86400 * 365)   # keep weekly rollups for a year

# When to use HLL vs Set:
# HLL:    counting unique users across millions of events (DAU, MAU, page views)
#         you need an estimate; exact count not required
#         memory budget is tight; storing all IDs is impractical
# Set:    you need the exact set of members (e.g., to look up who they are)
#         you need exact count; ±0.81% error is unacceptable
#         you'll perform operations like SINTER (HLL can only count, not retrieve)
```

### Section 8: Stream

**Q8. What is the Redis Stream and how does it differ from List-based queues and Pub/Sub?**
A: A Stream is an append-only log data structure (introduced in Redis 5.0). Unlike Lists, Streams retain messages after consumption. Unlike Pub/Sub, Streams are persistent and support consumer groups — multiple consumers can process a stream, with each message delivered to exactly one consumer in a group, with delivery tracking and acknowledgment.

```bash
XADD    key [MAXLEN [~] count] * field value [field value ...]
XREAD   [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]
XREADGROUP GROUP group consumer [COUNT count] [BLOCK ms] [NOACK] STREAMS key > [id ...]
XACK    key group id [id ...]     # acknowledge processed message
XLEN    key
XRANGE  key start end [COUNT count]
XREVRANGE key end start [COUNT count]
XINFO   STREAM key | GROUPS key | CONSUMERS key group
XPENDING key group [[IDLE min-idle-time] start end count [consumer]]
XCLAIM  key group consumer min-idle-time id [id ...]  # reassign stalled messages
XTRIM   key MAXLEN [~] count | MINID [~] threshold
```

**Use case 1 — Event log with consumer groups (reliable messaging):**
```python
# Producer: publish events
def publish_order_event(order_id: str, event_type: str, data: dict) -> str:
    stream_key = "stream:orders"
    message_id = r.xadd(stream_key, {
        "order_id":   order_id,
        "event_type": event_type,
        "data":       json.dumps(data),
        "timestamp":  str(time.time()),
    }, maxlen=100_000)  # cap at 100K messages (approximate trim)
    return message_id.decode()

# Setup consumer groups once:
def setup_consumer_groups() -> None:
    try:
        r.xgroup_create("stream:orders", "email-service",  id="0")
        r.xgroup_create("stream:orders", "inventory-service", id="0")
        r.xgroup_create("stream:orders", "analytics-service", id="0")
    except redis.exceptions.ResponseError as e:
        if "BUSYGROUP" not in str(e):
            raise   # group already exists → OK; other errors → re-raise

# Consumer: read and process (exactly-once delivery per group):
def order_email_consumer(consumer_name: str) -> None:
    group    = "email-service"
    stream   = "stream:orders"

    while True:
        # ">" means: give me messages not yet delivered to any consumer in this group
        messages = r.xreadgroup(
            group, consumer_name,
            {stream: ">"},
            count=10,
            block=5000   # block up to 5 seconds if no messages
        )

        if not messages:
            continue

        for _, message_list in messages:
            for msg_id, fields in message_list:
                try:
                    process_order_email(fields)
                    r.xack(stream, group, msg_id)   # acknowledge = remove from PEL
                except Exception as e:
                    log.error(f"Failed to process {msg_id}: {e}")
                    # Message stays in PEL (Pending Entries List)
                    # Will be retried / claimed by another consumer

# Dead-letter handling (reclaim stalled messages):
def recover_stalled_messages(consumer_name: str) -> None:
    group  = "email-service"
    stream = "stream:orders"
    # Find messages pending > 60 seconds (maybe the original consumer crashed):
    pending = r.xpending_range(stream, group, min="-", max="+", count=10,
                                idle=60_000)  # idle for 60+ seconds
    for msg in pending:
        r.xclaim(stream, group, consumer_name, min_idle_time=60_000, message_ids=[msg["message_id"]])
```

**Comparison — List vs Stream vs Pub/Sub:**
```
                    List        Stream          Pub/Sub
Message history:    No          Yes (persisted) No
Multiple consumers: Manual      Consumer groups  All subscribers (broadcast)
Acknowledgment:     No          Yes (XACK/PEL)  No
Consumer groups:    No          Yes             No
Blocking reads:     BLPOP       XREAD BLOCK     SUBSCRIBE (always blocking)
Persistence:        RDB/AOF     RDB/AOF         None (fire and forget)
Back-pressure:      Manual      MAXLEN          None
Replay from start:  No          Yes (XRANGE)    No

Use List when:        Simple FIFO; no ack needed; OK to lose if worker crashes
Use Stream when:      Reliable delivery; multiple independent consumers; replay needed
Use Pub/Sub when:     Real-time broadcast; no persistence; chat, live dashboards
```

### Section 9: Geospatial

**Q9. What is Redis Geospatial and how does it enable location-based queries?**
A: Redis Geospatial commands store latitude/longitude coordinates and enable queries like "find all members within N km of a point" or "distance between two stored locations." Internally, geospatial data is stored in a Sorted Set — the score is a Geohash-derived 52-bit integer, so all Sorted Set commands apply.

```bash
GEOADD      key longitude latitude member [...]
GEODIST     key member1 member2 [M|KM|FT|MI]
GEOPOS      key member [member ...]
GEOSEARCH   key FROMLONLAT lon lat | FROMMEMBER member
            BYRADIUS radius M|KM|FT|MI | BYBOX width height M|KM|FT|MI
            [ASC|DESC] [COUNT count [ANY]] [WITHCOORD] [WITHDIST] [WITHHASH]
GEOSEARCHSTORE destination key ...   # store results in a Sorted Set
GEOHASH     key member [member ...]  # returns geohash string
```

```python
def add_store(store_id: str, lon: float, lat: float, name: str) -> None:
```

### Section 10: Scenario / Interview Questions

**Q10. "An interviewer asks: why would you use a Sorted Set for rate limiting instead of a String counter?"**
A:

```
String INCR rate limiting (fixed window):
  Key: "rate:user:42:2024010914"  (window = per-hour bucket)
  Value: integer count of requests
  Algorithm:
    INCR the key; if first request, EXPIRE 3600
    If count > limit: reject

  Problem — boundary burst:
    Limit: 100 requests/hour
    User sends 100 requests at 11:59 → all pass (bucket for hour 11)
    Window resets at 12:00
    User sends 100 requests at 12:01 → all pass (bucket for hour 12)
    Result: 200 requests in 2 minutes (2× the intended limit!)

Sorted Set rate limiting (sliding window):
  Key: "rate:user:42"
  Members: unique request IDs
  Scores: Unix timestamps

  Algorithm (per request):
    1. ZREMRANGEBYSCORE (remove requests outside the window)
    2. ZADD current timestamp
    3. ZCARD → count requests in window
    4. If count > limit: reject
    5. EXPIRE key

  Benefit: truly sliding window — never allows 2× burst
  Cost: O(log N + M) per request (N = requests in window, M = expired to remove)
        Memory = O(requests in window) per user
        More complex implementation

When to use which:
  String INCR: limits don't require precision; high throughput needed; simpler is better
  Sorted Set:  precise rate limiting required; billing use cases; security-sensitive APIs
```

**Q11. "When would you use a HyperLogLog instead of a Sorted Set for a leaderboard-style unique count?"**
A:

```python
# Scenario: count unique users who viewed each product page
# Products: 10 million; Users: 100 million

# HyperLogLog approach:
# Memory: 10M products × 12 KB/HLL = 120 GB (!! too much if all in RAM simultaneously)
# BUT: if only active products are in RAM (10K products active at once):
#       10K × 12 KB = 120 MB — very manageable
# HLL gives you: count of unique viewers per product
# HLL does NOT give you: list of who viewed (can't retrieve members)

# Sorted Set approach (exact, with scores as view counts):
# zadd product:viewers:1234 {user_id: timestamp}
# Can check SISMEMBER: has user X viewed product Y?
# Can get ZCARD: exact unique viewer count
# Memory: 1000 viewers × ~70 bytes = 70 KB per product
# 10K active products × 70 KB = 700 MB (feasible)
# 10M products × 70 KB = 700 GB (not feasible for all in RAM)

# Decision framework:
# Need the exact set of viewers?          → Set/Sorted Set (HLL can't retrieve members)
# Need to check "has user X seen this?"   → Set/Sorted Set (HLL is write-only for members)
# Just need the count?                    → HLL is sufficient
# >100M unique elements to count?         → HLL almost mandatory (Set would be GBs)
# Error tolerance: ±1%?                   → HLL OK; ±0%? → Set required

# HyperLogLog is the right answer for:
# - Daily/monthly unique user counts (DAU/MAU)
# - Unique search query counting
# - A/B test participant counting (how many users saw each variant)
# - Unique IP counts for security monitoring
```

## Problem 1 — Session Management: Comparing String vs Hash Approaches

### Problem
An authentication service stores sessions with 8 fields (user ID, role, permissions, IP, user agent, created_at, last_activity, device). Implement session storage, evaluate both String (JSON) and Hash approaches, and show when each is correct.

```python
import json, time, uuid, redis
from typing import Optional

r = redis.Redis(decode_responses=True)

# ── Approach A: String (JSON) ──────────────────────────────────────────
class StringSessionStore:
    TTL = 3600  # 1 hour

    def create(self, user_id: str, metadata: dict) -> str:
        session_id = str(uuid.uuid4())
        session    = {
            "user_id":       user_id,
            "role":          metadata["role"],
            "permissions":   metadata["permissions"],   # list of strings
            "ip":            metadata["ip"],
            "user_agent":    metadata["user_agent"],
            "created_at":    time.time(),
            "last_activity": time.time(),
            "device":        metadata["device"],
        }
        r.setex(f"session:{session_id}", self.TTL, json.dumps(session))
        return session_id

    def get(self, session_id: str) -> Optional[dict]:
        raw = r.get(f"session:{session_id}")
        return json.loads(raw) if raw else None

    def touch(self, session_id: str) -> None:
        # Refresh TTL + update last_activity: must GET → modify → SET
        raw = r.get(f"session:{session_id}")
        if raw:
            session = json.loads(raw)
            session["last_activity"] = time.time()
            r.setex(f"session:{session_id}", self.TTL, json.dumps(session))
        # Drawback: 2 round trips + serialize/deserialize entire object on EVERY request

    def get_role(self, session_id: str) -> Optional[str]:
        session = self.get(session_id)
        return session["role"] if session else None
        # Drawback: fetch ALL fields to read ONE field (permissions list could be large)

# ── Approach B: Hash ─────────────────────────────────────────────────────
class HashSessionStore:
    TTL = 3600

    def create(self, user_id: str, metadata: dict) -> str:
        session_id = str(uuid.uuid4())
        r.hset(f"session:{session_id}", mapping={
            "user_id":       user_id,
            "role":          metadata["role"],
            "permissions":   json.dumps(metadata["permissions"]),  # JSON-encode list fields
            "ip":            metadata["ip"],
            "user_agent":    metadata["user_agent"],
            "created_at":    str(time.time()),
            "last_activity": str(time.time()),
            "device":        metadata["device"],
        })
        r.expire(f"session:{session_id}", self.TTL)
        return session_id

    def get(self, session_id: str) -> Optional[dict]:
        data = r.hgetall(f"session:{session_id}")
        if not data:
            return None
        data["permissions"] = json.loads(data["permissions"])
        data["created_at"]  = float(data["created_at"])
        data["last_activity"] = float(data["last_activity"])
        return data

    def touch(self, session_id: str) -> None:
        # Update ONE field without fetching everything:
        r.hset(f"session:{session_id}", "last_activity", str(time.time()))
        r.expire(f"session:{session_id}", self.TTL)
        # 2 commands, but no GET + deserialize + reserialize overhead

    def get_role(self, session_id: str) -> Optional[str]:
        return r.hget(f"session:{session_id}", "role")   # reads ONE field only

    def update_ip(self, session_id: str, new_ip: str) -> None:
        r.hset(f"session:{session_id}", "ip", new_ip)   # partial update, O(1)

    def get_auth_fields(self, session_id: str) -> tuple:
        # Read only the 2 fields needed for authorization check:
        return r.hmget(f"session:{session_id}", "user_id", "role", "permissions")
        # HMGET reads only 3 out of 8 fields — bandwidth + CPU efficient

# ── When String wins over Hash ────────────────────────────────────────
# - You always read ALL fields at once (no partial reads ever needed)
# - The serialized value has nested structures (deep nesting → Hash fields get awkward)
# - You use APPEND, string length checks (STRLEN)
# - The data is consumed by a non-Redis system as opaque bytes

# ── When Hash wins over String ─────────────────────────────────────────
# - You frequently update individual fields (touch/last_activity on every request)
# - You sometimes read only a subset of fields (role check: HGET vs full GET+parse)
# - You need atomic increments on numeric fields (HINCRBY on credits, counters)
# - The structure has well-defined flat fields (no deep nesting)

# ── Performance comparison on touch() at 10K req/s ────────────────────
# String approach: GET (read 400 bytes) + json.loads + set last_activity + json.dumps + SET
#   Network: 400 bytes in + 400 bytes out per request = 800 bytes × 10K = 8 MB/s
#   CPU:     json.loads + json.dumps × 10K/s = significant Python overhead

# Hash approach: HSET last_activity + EXPIRE
#   Network: ~50 bytes in + ~30 bytes out per request = 80 bytes × 10K = 0.8 MB/s
#   CPU:     minimal (no deserialization)
#   10× less network, near-zero CPU for the touch() operation
```

## Problem 2 — Real-Time Leaderboard with Rank Neighbors and Score History

### Problem
Build a game leaderboard supporting: updating scores, getting top 10, getting a player's rank with neighbors, tracking score history, and serving weekly/monthly sub-leaderboards.

```python
import time, json, redis
from datetime import datetime

r = redis.Redis(decode_responses=True)

class LeaderboardService:
    def __init__(self, game: str):
        self.game = game

    def _board_key(self, period: str) -> str:
        if period == "all_time":
            return f"lb:{self.game}:all"
        elif period == "weekly":
            week = datetime.utcnow().isocalendar()[1]
            year = datetime.utcnow().year
            return f"lb:{self.game}:week:{year}:{week}"
        elif period == "monthly":
            month = datetime.utcnow().strftime("%Y%m")
            return f"lb:{self.game}:month:{month}"
        raise ValueError(f"Unknown period: {period}")

    def record_score(self, player_id: str, score: float) -> dict:
        pipe = r.pipeline()

        # Update all-time, weekly, and monthly boards in one pipeline:
        for period in ("all_time", "weekly", "monthly"):
            key = self._board_key(period)
            # ZADD with GT: only update if new score is GREATER than existing
            pipe.zadd(key, {player_id: score}, gt=True)

        # Weekly and monthly boards expire after their period ends:
        pipe.expire(self._board_key("weekly"),  86400 * 8)   # 8 days
        pipe.expire(self._board_key("monthly"), 86400 * 35)  # 35 days

        # Store score history for this player:
        history_key = f"lb:{self.game}:history:{player_id}"
        pipe.zadd(history_key, {str(time.time()): score})  # score=score, member=timestamp
        # Note: inverted! member=timestamp, score=score for time-ordered history
        # Actually let's use score=timestamp and encode score in member:
        pipe.zadd(history_key, {json.dumps({"score": score, "ts": time.time()}): time.time()})
        pipe.zremrangebyrank(history_key, 0, -51)  # keep last 50 entries
        pipe.expire(history_key, 86400 * 90)

        results = pipe.execute()

        # Return updated rank info:
        return self.get_player_rank(player_id, "all_time")

    def get_top_n(self, n: int = 10, period: str = "all_time") -> list[dict]:
        key     = self._board_key(period)
        entries = r.zrevrange(key, 0, n - 1, withscores=True)
        return [
            {
                "rank":      i + 1,
                "player_id": player_id,
                "score":     score,
            }
            for i, (player_id, score) in enumerate(entries)
        ]

    def get_player_rank(self, player_id: str, period: str = "all_time") -> dict | None:
        key   = self._board_key(period)
        rank  = r.zrevrank(key, player_id)     # 0-based descending rank
        score = r.zscore(key, player_id)
        if rank is None:
            return None
        return {
            "player_id": player_id,
            "rank":      rank + 1,             # 1-based
            "score":     score,
            "total":     r.zcard(key),
            "percentile": round((1 - rank / r.zcard(key)) * 100, 1)
        }

    def get_rank_with_neighbors(
        self, player_id: str, radius: int = 3, period: str = "all_time"
    ) -> dict:
        key  = self._board_key(period)
        rank = r.zrevrank(key, player_id)
        if rank is None:
            return {"player_id": player_id, "ranked": False}

        start   = max(0, rank - radius)
        stop    = rank + radius
        entries = r.zrevrange(key, start, stop, withscores=True)

        return {
            "player_id":  player_id,
            "rank":       rank + 1,
            "score":      r.zscore(key, player_id),
            "neighbors":  [
                {
                    "rank":      start + i + 1,
                    "player_id": pid,
                    "score":     score,
                    "is_self":   pid == player_id,
                }
                for i, (pid, score) in enumerate(entries)
            ]
        }

    def get_players_in_score_range(
        self, min_score: float, max_score: float, period: str = "all_time"
    ) -> list[dict]:
        key     = self._board_key(period)
        entries = r.zrangebyscore(key, min_score, max_score, withscores=True)
        return [
            {"player_id": pid, "score": score}
            for pid, score in reversed(entries)  # highest score first
        ]

    def get_score_history(self, player_id: str) -> list[dict]:
        key = f"lb:{self.game}:history:{player_id}"
        raw = r.zrange(key, 0, -1, withscores=True)
        return [
            {**json.loads(member), "timestamp": score}
            for member, score in raw
        ]

    def combine_boards(self, period_a: str, period_b: str, dest_key: str) -> int:
        # Combined leaderboard: player's max score from two periods
        r.zunionstore(
            dest_key,
            {self._board_key(period_a): 1, self._board_key(period_b): 1},
            aggregate="MAX"  # use the higher of the two scores
        )
        return r.zcard(dest_key)

# Usage:
lb = LeaderboardService("battle_royale")
lb.record_score("player_42",  9800)
lb.record_score("player_17", 12400)
lb.record_score("player_99",  7200)

print(lb.get_top_n(5))
# [{'rank': 1, 'player_id': 'player_17', 'score': 12400.0}, ...]

print(lb.get_rank_with_neighbors("player_42", radius=2))
# {'player_id': 'player_42', 'rank': 2, 'neighbors': [
```

## Problem 3 — Pub/Sub vs Streams vs List: Choosing the Right Queue

### Problem
A notification service needs to send messages to users. Three team members propose different Redis patterns. Evaluate each and implement the correct one for the use case.

```python
# Use case: "Send in-app notifications when orders are shipped.
# Multiple notification types: push, email, SMS.
# Messages must not be lost if a consumer crashes.
# Some notifications are sent to multiple services independently."

# ── Option A: Pub/Sub (wrong for this use case) ────────────────────────
# Proposed: PUBLISH order:shipped {data}; consumers SUBSCRIBE order:shipped

def publisher_pubsub(order: dict) -> None:
    r.publish("notifications:order_shipped", json.dumps(order))
    # ✗ WRONG: if push-service is down when message published → message LOST
    # ✗ WRONG: no acknowledgment → no way to know if message was processed
    # ✗ WRONG: if push-service restarts → misses all messages published while down
    # ✓ RIGHT if: live chat, real-time dashboard updates, short-lived signals

# ── Option B: List (adequate but limited) ────────────────────────────────
# Proposed: LPUSH queue:push_notifications {data}; BRPOP in consumers

def publisher_list(order: dict) -> None:
    payload = json.dumps(order)
    r.rpush("queue:push_notifications",  payload)
    r.rpush("queue:email_notifications", payload)   # separate queue per consumer type
    r.rpush("queue:sms_notifications",   payload)   # push to 3 separate lists!

# Problems:
# ✗ Each service has its own queue → publisher must know about all consumers
# ✗ Adding a 4th service requires changing the publisher
# ✗ No replayability: once consumed, message is gone
# ✗ No visibility into what's been processed / pending
# ✓ Acceptable for single-consumer queues with simple requirements

# ── Option C: Streams (correct for this use case) ─────────────────────
# One stream, multiple independent consumer groups

class NotificationPublisher:
    STREAM = "stream:notifications"

    def publish_order_shipped(self, order_id: str, order: dict) -> str:
        msg_id = r.xadd(
            self.STREAM,
            {
                "event_type": "order.shipped",
                "order_id":   order_id,
                "user_id":    order["user_id"],
                "tracking":   order.get("tracking_number", ""),
                "carrier":    order.get("carrier", ""),
                "payload":    json.dumps(order),
            },
            maxlen=500_000,  # cap stream at 500K messages (approximate)
        )
        return msg_id.decode()

class NotificationConsumer:
    STREAM = "stream:notifications"

    def __init__(self, service_name: str, consumer_id: str):
        self.group    = f"{service_name}-group"
        self.consumer = consumer_id
        self._setup_group()

    def _setup_group(self) -> None:
        try:
            # id="0": start from the very beginning of the stream
            # (new groups can specify "$" to only get new messages)
            r.xgroup_create(self.STREAM, self.group, id="0", mkstream=True)
        except redis.exceptions.ResponseError as e:
            if "BUSYGROUP" not in str(e):
                raise

    def process_messages(self, handler: callable, batch_size: int = 10) -> None:
        while True:
            # ">" = only messages not yet delivered to any consumer in this group:
            messages = r.xreadgroup(
                self.group, self.consumer,
                {self.STREAM: ">"},
                count=batch_size,
                block=5000
            )

            if not messages:
                self._reclaim_stalled()   # check for crashed consumers
                continue

            for _, msg_list in messages:
                for msg_id, fields in msg_list:
                    try:
                        handler(fields)
                        r.xack(self.STREAM, self.group, msg_id)
                    except Exception as e:
                        # Don't ACK → stays in PEL → will be reclaimed
                        log.error(f"Failed to process {msg_id}: {e}")

    def _reclaim_stalled(self) -> None:
        # Reclaim messages pending > 5 minutes (worker probably crashed):
        stalled = r.xpending_range(
            self.STREAM, self.group,
            min="-", max="+",
            count=20,
            idle=300_000  # 5 minutes idle
        )
        if stalled:
            ids = [msg["message_id"] for msg in stalled]
            r.xclaim(self.STREAM, self.group, self.consumer,
                     min_idle_time=300_000, message_ids=ids)

# Three independent services consume the SAME stream:
push_consumer  = NotificationConsumer("push-service",  "push-worker-1")
email_consumer = NotificationConsumer("email-service", "email-worker-1")
sms_consumer   = NotificationConsumer("sms-service",   "sms-worker-1")

# Adding a 4th service requires NO changes to the publisher:
# analytics_consumer = NotificationConsumer("analytics", "analytics-worker-1")

# Publisher doesn't change:
pub = NotificationPublisher()
pub.publish_order_shipped("ORD-001", {"user_id": "42", "carrier": "UPS"})

# Stream allows replay: if sms-service was down, it can catch up from msg_id="0"
# List would have lost those messages; Pub/Sub never stores them
```

## Problem 4 — Combining Data Structures: Trending Topics

### Problem
Build a "trending now" feature: topics trend based on mentions in the last hour. The system must update in real time, decay old mentions, and provide the top 10 trending topics efficiently.

```python
import time, math, redis
from collections import defaultdict

r = redis.Redis(decode_responses=True)

class TrendingTopics:
    """
    Architecture:
      1. Sorted Set "trending:scores" → topic: decay-weighted score (for top-N query)
      2. Per-minute count Sets → track raw mention counts per minute for decay
      3. String counters → total all-time mentions per topic
    """

    DECAY_FACTOR     = 0.98     # score × 0.98 per minute old (exponential decay)
    WINDOW_MINUTES   = 60       # consider last 60 minutes
    TOP_N            = 10

    def record_mention(self, topic: str) -> None:
        now_minute = int(time.time() // 60)

        pipe = r.pipeline()

        # 1. Increment per-minute count for this topic:
        minute_key = f"trending:raw:{now_minute}"
        pipe.hincrby(minute_key, topic, 1)
        pipe.expire(minute_key, 3600 + 120)   # keep 60 min + 2 min buffer

        # 2. Recompute this topic's decayed score and update ZSet:
        # We do this lazily in get_trending() rather than on every mention
        # to avoid recomputing decay for all 60 minutes on each record

        # 3. Add to a set of "active topics" to bound the computation in get_trending():
        pipe.sadd("trending:active_topics", topic)
        pipe.expire("trending:active_topics", 3600)

        # 4. Increment all-time counter (String):
        pipe.incr(f"trending:total:{topic}")

        pipe.execute()

    def _compute_score(self, topic: str) -> float:
        """Compute decay-weighted score across the last 60 minutes."""
        now_minute = int(time.time() // 60)
        total_score = 0.0

        # Batch fetch all minute buckets for this topic:
        pipe = r.pipeline()
        for delta in range(self.WINDOW_MINUTES):
            minute = now_minute - delta
            pipe.hget(f"trending:raw:{minute}", topic)
        counts = pipe.execute()

        for delta, count in enumerate(counts):
            if count:
                # Older minutes have lower weight: 0.98^delta
                weight = self.DECAY_FACTOR ** delta
                total_score += int(count) * weight

        return total_score

    def recompute_trending(self) -> None:
        """Recompute scores for all active topics. Call periodically (e.g., every minute)."""
        active_topics = r.smembers("trending:active_topics")
        if not active_topics:
            return

        pipe = r.pipeline()
        for topic in active_topics:
            score = self._compute_score(topic)
            if score > 0.01:    # prune topics that have effectively decayed to 0
                pipe.zadd("trending:scores", {topic: score})
            else:
                pipe.zrem("trending:scores", topic)
                pipe.srem("trending:active_topics", topic)

        # Keep only top 1000 in the sorted set (prune the long tail):
        pipe.zremrangebyrank("trending:scores", 0, -(1001))
        pipe.expire("trending:scores", 3600)
        pipe.execute()

    def get_trending(self, n: int = 10) -> list[dict]:
        """Get top N trending topics with scores."""
        results = r.zrevrange("trending:scores", 0, n - 1, withscores=True)
        return [
            {
                "topic": topic,
                "score": round(score, 2),
                "rank":  i + 1,
                "all_time_mentions": int(r.get(f"trending:total:{topic}") or 0),
            }
            for i, (topic, score) in enumerate(results)
        ]

    def get_topic_momentum(self, topic: str) -> dict:
        """Is this topic trending up or down? Compare last 10 min vs prev 10 min."""
        now_minute = int(time.time() // 60)

        pipe = r.pipeline()
        for delta in range(20):
            pipe.hget(f"trending:raw:{now_minute - delta}", topic)
        counts = pipe.execute()

        recent   = sum(int(c or 0) for c in counts[:10])   # last 10 min
        previous = sum(int(c or 0) for c in counts[10:])   # prior 10 min

        if previous == 0:
            momentum = "new" if recent > 0 else "inactive"
        elif recent > previous * 1.2:
            momentum = "rising"
        elif recent < previous * 0.8:
            momentum = "falling"
        else:
            momentum = "stable"

        return {
            "topic":       topic,
            "recent_10m":  recent,
            "previous_10m": previous,
            "momentum":    momentum,
            "change_pct":  round((recent - previous) / max(previous, 1) * 100, 1),
        }

# Usage:
trending = TrendingTopics()

# Simulate mentions (typically called from application layer on content creation):
for topic in ["python", "redis", "python", "ai", "python", "redis", "kubernetes"]:
    trending.record_mention(topic)

# Run periodically (cron / scheduler every 60s):
trending.recompute_trending()

# Query:
print(trending.get_trending(5))
# [{'topic': 'python', 'score': 3.0, 'rank': 1, 'all_time_mentions': 3},
#  {'topic': 'redis', 'score': 2.0, 'rank': 2, 'all_time_mentions': 2}, ...]

print(trending.get_topic_momentum("python"))
# {'topic': 'python', 'recent_10m': 3, 'previous_10m': 0, 'momentum': 'new', ...}
```

## Quick Reference — Redis Data Structures Cheat Sheet

```
STRING:
  Internal: int / embstr (≤44B) / raw (>44B)
  Key commands: GET/SET/MGET/MSET, INCR/INCRBY, SET NX PX (atomic lock)
  Use for:  JSON cache, HTML fragments, counters (page views, API calls),
            distributed locks (SET NX PX + Lua release), idempotency keys,
            rate limiting (INCR fixed-window), feature flags (single bit)
  Avoid when: need partial field updates (use Hash); need ordering (use ZSet)

LIST:
  Internal: listpack (small) → quicklist (large, doubly-linked list of ziplists)
  Key commands: LPUSH/RPUSH/LPOP/RPOP, BLPOP/BRPOP (blocking!), LRANGE, LTRIM
  Use for:  Task queues (RPUSH + BLPOP = FIFO), stacks (LPUSH + LPOP = LIFO),
            recent-N capped feed (LPUSH + LTRIM), activity history
  Avoid when: need unique members (use Set); need ordering by value (use ZSet)
  Reliable queue: LMOVE (atomic move pending → processing list)

HASH:
  Internal: listpack (≤128 fields, ≤64B values) → hashtable (larger)
  Key commands: HSET/HGET/HMGET/HGETALL, HINCRBY, HDEL, HLEN
  Use for:  Object/entity storage (user profiles, product data), shopping carts
            (field=product_id, value=quantity), session data, per-field counters
  Beats String when: partial reads or updates needed; numeric field increments
  Avoid when: deeply nested structures (flat fields only); need sorted access

SET:
  Internal: listpack (≤128 members, ≤64B each) → hashtable (larger)
  Key commands: SADD/SREM/SISMEMBER, SCARD, SMEMBERS, SUNION/SINTER/SDIFF
  Use for:  Unique visitor tracking, tags/labels, social graph (followers/following),
            deduplication, blacklists/whitelists, "mutual friends" (SINTER),
            "people you may know" (SDIFF of SUNION of following sets)
  Avoid when: need scores/ordering (use ZSet); >10M members in one set (use HLL for counting)

SORTED SET:
  Internal: listpack (≤128 members, ≤64B each) → skiplist + hashtable (larger)
  Key commands: ZADD (with NX/XX/GT/LT/INCR), ZRANGE/ZREVRANGE, ZRANK/ZREVRANK,
                ZSCORE, ZINCRBY, ZPOPMIN/ZPOPMAX, ZRANGEBYSCORE, ZCOUNT
  Use for:  Leaderboards (score=points), sliding-window rate limiter (score=timestamp),
            priority queues (score=priority), time-series event log (score=timestamp),
            trending topics (score=decay-weighted count), geo search (internally ZSet)
  The most versatile Redis type: anything needing ordered + scored + unique members

BITMAP:
  Internal: String with bit-level operations
  Key commands: SETBIT/GETBIT, BITCOUNT, BITOP (AND/OR/XOR/NOT), BITPOS
  Use for:  Daily active users per day (bit N = user N active today),
            feature flags at scale (bit N = user N has feature),
            presence tracking, attendance, boolean analytics
  Memory: 10M users = 1.25 MB (vs ~50 MB for Set of string user IDs)
  Avoid when: user IDs are not compact integers or are >500M (bitmap too large)

HYPERLOGLOG:
  Internal: 12 KB max; probabilistic data structure
  Key commands: PFADD, PFCOUNT, PFMERGE
  Use for:  Counting unique visitors (DAU/MAU), unique search queries,
            A/B test participant counting — any large-scale cardinality estimate
  Trade-off: ±0.81% error; cannot retrieve members; write-only for individuals
  Avoid when: exact count required; need to check membership; <10K elements (use Set)

STREAM:
  Internal: radix tree of listpacks
  Key commands: XADD, XREAD, XREADGROUP, XACK, XPENDING, XCLAIM, XTRIM
  Use for:  Reliable message queues with consumer groups (exactly-once delivery),
            event sourcing, IoT sensor ingestion, activity logs, audit trails
  vs List:  Stream retains history; List deletes on pop; Stream has consumer groups
  vs Pub/Sub: Stream persists messages; Pub/Sub is fire-and-forget
  Use Pub/Sub for: real-time broadcasts where history/reliability don't matter

GEOSPATIAL:
  Internal: Sorted Set (Geohash as score)
  Key commands: GEOADD, GEODIST, GEOSEARCH, GEOPOS, GEOHASH
  Use for:  Nearest store/driver/restaurant, delivery radius, proximity alerts

COMMON PATTERNS:
  Distributed lock:    SET key token NX PX ttl + Lua script for safe release
  Cache-aside:         GET → miss → DB → SET EX → return
  Rate limiting:       Fixed window: INCR + EXPIRE | Sliding: ZADD + ZREMRANGEBYSCORE
  Leaderboard:         ZADD + ZREVRANGE + ZREVRANK + ZINCRBY
  Session:             HSET (partial updates) vs SET (always full read)
  Queue:               RPUSH + BLPOP (simple) | Stream (reliable/multi-consumer)
  DAU tracking:        Bitmap (compact) | HLL (estimates only) | Set (exact+queryable)
  Social graph:        SADD (follow) + SINTER (mutual) + SDIFF (suggestions)
  Recent N items:      LPUSH + LTRIM (capped list)
  Pub/Sub vs Stream:   Pub/Sub = broadcast, no history | Stream = persistent, ack, groups

MEMORY USAGE ESTIMATES:
  String "hello":    ~52 bytes
  Hash 10 fields:    ~200 bytes
  List 1000 items:   ~40 KB
  Set 1000 members:  ~40 KB
  ZSet 1000 members: ~80 KB (member + score)
  HyperLogLog:       max 12 KB (regardless of elements counted)
  Bitmap 10M users:  1.25 MB

ENCODING THRESHOLDS (defaults, configurable via redis.conf):
  Hash:    listpack → hashtable at: 128 fields OR any field/value > 64 bytes
  List:    listpack → quicklist at: 128 elements OR any element > 64 bytes
  Set:     listpack → hashtable at: 128 members OR any member > 64 bytes
           intset → hashtable: when any member is not an integer
  ZSet:    listpack → skiplist at: 128 members OR any member > 64 bytes
  Listpack uses less memory but O(n) lookups; hashtable/skiplist use more memory but O(1)/O(log n)
```

**Final Tip:** At the 5 YOE level, Redis data structure questions test whether you can **match the access pattern to the data structure** — not just list what each type does. The highest-signal answer on Hash vs String for object storage: "I use Hash when I need partial reads or updates — if I'm touching `last_activity` on every request and the object has 50 fields, a Hash lets me `HSET key last_activity $now` in one command without fetching and re-serializing the entire object. With String + JSON, that's GET → json.loads → modify → json.dumps → SET: three operations, full serialize/deserialize cycle, 10× the network bandwidth. I use String when I always read all fields at once and never need field-level atomicity." For Sorted Set vs other types for rate limiting: "The sliding window rate limiter with a Sorted Set (score = timestamp) is more accurate than the String INCR fixed-window approach because it eliminates the boundary burst problem. With fixed windows, a user can make N requests at second 59 of one window and N more at second 1 of the next window — 2N requests in 2 seconds against an N/minute limit. The sliding window tracks actual timestamps and counts only requests within the last 60 seconds regardless of window boundaries. The trade-off is O(log N) per request vs O(1), and memory proportional to requests-in-window vs O(1) per user." For choosing between Stream, List, and Pub/Sub: "List is for simple single-consumer queues where losing a message if the worker crashes is acceptable — it's the simplest but the least reliable. Stream with consumer groups gives you durability, acknowledgment, and multiple independent consumers from the same message without the publisher knowing who the consumers are. Pub/Sub is fire-and-forget broadcast — if no subscriber is connected when the message is published, it's lost, so it's only appropriate for live real-time signals like chat or dashboard updates where history genuinely doesn't matter."
