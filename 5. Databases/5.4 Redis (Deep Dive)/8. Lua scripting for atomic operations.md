# Lua Scripting for Atomic Operations in Redis — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does Redis support Lua scripting and what problem does it solve that `MULTI/EXEC` cannot?**

A: Redis is single-threaded. Every command executes atomically in isolation, but **sequences** of commands are not atomic — another client can interleave between them. `MULTI/EXEC` handles this for fixed command sequences, but it cannot express server-side conditional logic. Lua scripting solves this:

```
The race condition that MULTI/EXEC cannot prevent:

Client A: GET stock:product:42  → "5"
Client B: GET stock:product:42  → "5"  (reads before A decrements)
Client A: DECR stock:product:42 → "4"
Client B: DECR stock:product:42 → "3"  (both sold the same "last" unit)
Stock is now 3 but 2 units were sold — oversold by 1

MULTI/EXEC attempt — still fails:
Client A:
  WATCH stock:product:42
  MULTI
  GET stock:product:42   ← QUEUED (not executed yet!)
  ...decide here? can't — haven't read the value yet
  DECR stock:product:42
  EXEC

Problem: MULTI/EXEC queues commands without executing them.
You cannot read a value and branch based on it inside a MULTI/EXEC block.
WATCH enables optimistic locking (retry on conflict) but NOT conditional logic.
```

```lua
-- Lua solution: atomic check-then-decrement (runs without interruption)
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then
  return redis.error_reply('INSUFFICIENT_STOCK')
end
redis.call('DECRBY', KEYS[1], ARGV[1])
return stock - tonumber(ARGV[1])
-- This entire script executes atomically — no other client can run between lines
```

**What each mechanism solves:**

| Problem | Pipeline | MULTI/EXEC | Lua Script |
|---|---|---|---|
| Reduce round trips | ✓ | ✓ | ✓ |
| Atomic sequence | ✗ | ✓ | ✓ |
| Server-side conditionals | ✗ | ✗ | ✓ |
| Read-then-write atomically | ✗ | ✗ (WATCH workaround) | ✓ |
| Complex business logic | ✗ | ✗ | ✓ |
| No network overhead | ✓ | ✗ (RTT per EXEC) | ✓ |

**Q2. What is the atomicity guarantee of a Lua script in Redis?**

A: While a Lua script executes, Redis **suspends all other client commands**. No other command can be processed until the script completes. This is true atomicity — not optimistic locking — because Redis is single-threaded and the script monopolizes the event loop:

```
Redis event loop during Lua execution:

Normal (no script):
t=0ms: Client A: SET key1 "hello"    → processed
t=1ms: Client B: INCR counter        → processed
t=2ms: Client A: GET key1            → processed

During Lua script (Client A runs EVAL):
t=0ms: Client A: EVAL "script" ...   → starts executing
t=0ms:   [script]: GET stock         → 100
t=0ms:   [script]: DECRBY stock 1    → 99
t=0ms:   [script]: HSET orders id X  → OK
t=0ms: Client A: EVAL returns 99
t=1ms: Client B: INCR counter        → NOW processed (was queued, never interrupted)
t=2ms: Client C: GET stock           → 99 (sees completed script result)

The guarantee:
✓ The script sees a consistent snapshot — no other client modifies data mid-script
✓ All writes in the script appear atomically to other clients (all or nothing on crash)
✓ Scripts are replicated as a unit in replication and AOF
✗ Not a transaction in the ACID sense — no ROLLBACK if script logic errors midway
   (commands that already ran are committed; you must write idempotent logic)
```

```bash
# The single-threaded guarantee in action:
# EVEN if your script takes 50ms, Client B's command is not processed until it finishes
# This is why you must keep scripts SHORT — long scripts block ALL other clients

# Safety valve:
redis-cli CONFIG SET lua-time-limit 5000   # Default: 5000ms
# After 5 seconds, Redis logs a warning and starts accepting only:
# - SCRIPT KILL (if script has made NO writes)
# - SHUTDOWN NOSAVE (if script has made writes — accept data loss)
# There is NO way to gracefully abort a writing Lua script mid-execution
```

## Section 2: EVAL Command

**Q3. What is the syntax of `EVAL` and why are `KEYS` and `ARGV` separate arrays?**

A: `EVAL` is the command to execute a Lua script:

```bash
EVAL script numkeys key [key ...] arg [arg ...]
#    ↑      ↑        ↑              ↑
#    Lua    How many  Key names      Additional
#    code   of the    (KEYS[1..N])   arguments
#           next args               (ARGV[1..M])
#           are keys
```

```bash
# Example: sliding window rate limiter
EVAL "
  local count = redis.call('INCR', KEYS[1])
  if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
  end
  return count
" 1 ratelimit:user:1001 60
# numkeys=1, KEYS[1]="ratelimit:user:1001", ARGV[1]="60"

# KEYS and ARGV are 1-indexed (Lua convention, not 0-indexed like most languages):
-- KEYS[1] = "ratelimit:user:1001"
-- KEYS[2] = second key (if any)
-- ARGV[1] = "60"
-- ARGV[2] = second arg (if any)

# Multiple keys and args:
EVAL script 2 key1 key2 arg1 arg2 arg3
# numkeys=2
# KEYS = { [1]="key1", [2]="key2" }
# ARGV = { [1]="arg1", [2]="arg2", [3]="arg3" }
```

**Why keys and args are separate:**
```bash
# The separation exists for Redis Cluster compatibility.
# In Redis Cluster, keys must hash to the same slot.
# The cluster proxy MUST know which keys a script accesses to route it correctly.
# If keys were embedded in the script string, the cluster couldn't parse them.

# CORRECT: keys declared in KEYS array
EVAL "return redis.call('GET', KEYS[1])" 1 mykey
# Cluster can extract: "this script accesses 'mykey' → route to that shard"

# WRONG: keys hardcoded in script (works on single Redis, breaks on Cluster):
EVAL "return redis.call('GET', 'mykey')" 0
# Cluster doesn't know this script accesses 'mykey' → routing error

# Cluster constraint: all KEYS must hash to the same slot
# Use hash tags to force keys to the same slot:
EVAL "
  redis.call('SET', KEYS[1], ARGV[1])
  redis.call('SET', KEYS[2], ARGV[2])
  return 1
" 2 {user:1001}:session {user:1001}:profile "sess_data" "prof_data"
# {} part is the hash tag — both keys hash based on "user:1001" → same slot
```

**Q4. How do data types convert between Redis and Lua?**

A: Redis and Lua have different type systems. Redis uses a protocol (RESP) with specific reply types; Lua uses dynamic typing. Conversions happen automatically but have surprising edge cases:

```lua
-- Redis → Lua type conversions:
-- Redis integer reply    → Lua number
-- Redis bulk string      → Lua string
-- Redis multi-bulk reply → Lua table (array, 1-indexed)
-- Redis status reply     → Lua table { ok = "STATUS_MESSAGE" }
-- Redis error reply      → Lua table { err = "error message" }
-- Redis nil bulk reply   → Lua false (NOT nil! This is surprising)
-- Redis nil multi-bulk   → Lua false

-- Demonstration:
local val = redis.call('GET', 'nonexistent_key')
-- val is FALSE (not nil) when the key doesn't exist!
if val == false then
  -- key doesn't exist
end
if not val then
  -- also works: 'not false' is true, 'not nil' is also true
end
```

```lua
-- Lua → Redis type conversions:
-- Lua number (integer)   → Redis integer reply
-- Lua string             → Redis bulk string
-- Lua table (array)      → Redis multi-bulk reply
-- Lua table { ok = ... } → Redis status reply
-- Lua table { err = ... }→ Redis error reply
-- Lua false or nil       → Redis nil bulk reply
-- Lua true               → Redis integer 1

-- THE CRITICAL FLOAT TRAP:
-- Lua numbers that look like floats are TRUNCATED to integers when returned
local result = 3.14
return result   -- Returns 3 to Redis client, NOT 3.14!

-- To return a float, return it as a string:
return tostring(3.14)   -- Returns "3.14" as a bulk string

-- Safe type checking pattern:
local count = redis.call('INCR', KEYS[1])
-- count is a Lua number (integer), not a string
-- Always use tonumber() when receiving numeric values from redis.call()
-- because GET returns a STRING even if the stored value is a number:
local balance = tonumber(redis.call('GET', KEYS[1])) or 0
-- tonumber(nil) would fail — 'or 0' provides a safe default
```

```bash
# Seeing conversions in action from redis-cli:
EVAL "return redis.call('GET', 'existing_string_key')" 0
# → "the string value"  (bulk string)

EVAL "return redis.call('INCR', 'counter')" 0
# → (integer) 42

EVAL "return redis.call('GET', 'nonexistent')" 0
# → (nil)   (Lua false → Redis nil)

EVAL "return {1, 'two', 3}" 0
# → 1) (integer) 1
#   2) "two"
#   3) (integer) 3

EVAL "return {ok='PONG'}" 0
# → PONG  (status reply)

EVAL "return {err='ERR something went wrong'}" 0
# → (error) ERR something went wrong
```

## Section 3: Error Handling

**Q5. What is the difference between `redis.call()` and `redis.pcall()`?**

A: Both execute a Redis command from within Lua. The difference is how they handle command errors:

```lua
-- redis.call(): propagates errors (like throwing an exception)
-- If the command returns a Redis error, the ENTIRE script aborts immediately
-- The error is returned to the caller as a Redis error reply

-- redis.pcall(): catches errors (like try-catch)
-- If the command returns a Redis error, returns a Lua table { err = "message" }
-- Script continues executing

-- ── redis.call() — fail fast ──────────────────────────────────────────────────
local result = redis.call('HSET', KEYS[1], 'field', 'value')
-- If KEYS[1] is the wrong type (e.g., a String, not a Hash):
-- → Script immediately aborts with error:
--   WRONGTYPE Operation against a key holding the wrong kind of value

-- ── redis.pcall() — defensive ──────────────────────────────────────────────────
local result = redis.pcall('HSET', KEYS[1], 'field', 'value')
if result.err then
  -- Handle gracefully:
  redis.log(redis.LOG_WARNING, 'HSET failed: ' .. result.err)
  return redis.error_reply('OPERATION_FAILED: ' .. result.err)
end
-- Script continues here if HSET succeeded

-- ── When to use which ─────────────────────────────────────────────────────────
-- redis.call():  When errors are unexpected programming bugs
--                When you want fail-fast behavior
--                Most commands in most scripts — simpler code

-- redis.pcall(): When you need to handle expected errors gracefully
--                When you want to inspect the error and return custom messages
--                When you're doing conditional operations that might fail

-- ── Example: atomic upsert with error context ─────────────────────────────────
local function safe_get(key)
  local result = redis.pcall('GET', key)
  if result.err then
    return nil, result.err
  end
  return result, nil
end

local value, err = safe_get(KEYS[1])
if err then
  return redis.error_reply('GET_FAILED: ' .. err)
end
-- value is either the string value or Lua false (key doesn't exist)
```

**Q6. How do you construct and return custom errors and status replies from Lua scripts?**

A:

```lua
-- ── Custom error replies ───────────────────────────────────────────────────────
-- These propagate to the Redis client as error replies (prefixed with -)

return redis.error_reply('ERR not enough stock')
-- Client receives: (error) ERR not enough stock

-- With conventional error prefix (Redis convention: TYPE MESSAGE):
return redis.error_reply('INSUFFICIENT_STOCK Only 3 units available, requested 5')
-- Client receives: (error) INSUFFICIENT_STOCK Only 3 units available, requested 5

-- ── Custom status replies ──────────────────────────────────────────────────────
-- These propagate as simple status replies (prefixed with +)
return redis.status_reply('OK')
-- Client receives: OK

return redis.status_reply('QUEUED')
-- Client receives: QUEUED

-- ── Equivalent table syntax (returns same results): ──────────────────────────
return { err = 'ERR not enough stock' }     -- same as redis.error_reply(...)
return { ok  = 'QUEUED' }                   -- same as redis.status_reply(...)

-- ── Practical error handling in Node.js (receiving Lua errors): ─────────────
const result = await redis.eval(script, 1, 'stock:product:42', '5');
// If script returns redis.error_reply:
// → ReplyError: INSUFFICIENT_STOCK Only 3 units available

// Catching in application code:
try {
  const remaining = await redis.eval(reserveScript, 1, stockKey, requested);
  return { success: true, remaining: Number(remaining) };
} catch (err) {
  if (err.message.startsWith('INSUFFICIENT_STOCK')) {
    return { success: false, reason: 'out_of_stock' };
  }
  throw err;  // Unexpected error — rethrow
}
```

## Section 4: EVALSHA and Script Management

**Q7. What is `EVALSHA` and why should you use it in production instead of `EVAL`?**

A: Every `EVAL` call sends the full script body over the network. For scripts called thousands of times per second, transmitting even a 200-byte script adds unnecessary bandwidth and parsing overhead. `EVALSHA` sends only the SHA1 hash (40 characters):

```bash
# Step 1: Load script into Redis cache (once per deployment or startup):
SCRIPT LOAD "
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock == nil or stock < tonumber(ARGV[1]) then
    return redis.error_reply('INSUFFICIENT_STOCK')
  end
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return stock - tonumber(ARGV[1])
"
# → "b8059ff43d9cf6ab6d25b5651c69c20028bfee86"  (SHA1 hash)

# Step 2: Call by hash (40 chars instead of full script body):
EVALSHA b8059ff43d9cf6ab6d25b5651c69c20028bfee86 1 stock:product:42 3
# → (integer) 97   (remaining stock)

# Verify a script exists in the cache:
SCRIPT EXISTS b8059ff43d9cf6ab6d25b5651c69c20028bfee86
# → 1  (exists)
SCRIPT EXISTS deadbeefdeadbeefdeadbeef0000000000000000
# → 0  (doesn't exist)

# Clear all cached scripts (e.g., after a memory crunch):
SCRIPT FLUSH          # Synchronous flush
SCRIPT FLUSH ASYNC    # Async flush (Redis 6.2+, non-blocking)

# Script cache is NOT persisted:
# - Cleared on Redis restart
# - Cleared on SCRIPT FLUSH
# - NOT cleared on BGSAVE or AOF replay
# → Must reload scripts on every Redis restart
```

```typescript
// Production pattern: script registry with automatic reload
class RedisScriptRegistry {
  private scripts: Map<string, { body: string; sha?: string }> = new Map();

  constructor(private redis: Redis) {}

  register(name: string, body: string): void {
    this.scripts.set(name, { body, sha: undefined });
  }

  async load(): Promise<void> {
    for (const [name, script] of this.scripts.entries()) {
      script.sha = await this.redis.script('load', script.body) as string;
      console.log(`Loaded script '${name}': ${script.sha}`);
    }
  }

  async run(name: string, numkeys: number, ...keysAndArgs: string[]): Promise<unknown> {
    const script = this.scripts.get(name);
    if (!script) throw new Error(`Unknown script: ${name}`);

    try {
      // Fast path: use SHA (40 chars instead of full script)
      return await this.redis.evalsha(script.sha!, numkeys, ...keysAndArgs);
    } catch (err) {
      // If SHA not found (Redis restarted, SCRIPT FLUSH called):
      if (err.message.includes('NOSCRIPT')) {
        // Reload the script and retry with EVAL:
        script.sha = await this.redis.script('load', script.body) as string;
        return await this.redis.evalsha(script.sha, numkeys, ...keysAndArgs);
      }
      throw err;
    }
  }
}

// Usage:
const registry = new RedisScriptRegistry(redis);

registry.register('reserve_stock', `
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if not stock or stock < tonumber(ARGV[1]) then
    return redis.error_reply('INSUFFICIENT_STOCK')
  end
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return stock - tonumber(ARGV[1])
`);

await registry.load();  // Call once at startup

const remaining = await registry.run('reserve_stock', 1, 'stock:product:42', '3');
```

**Q8. What are Redis Functions (Redis 7.0+) and how do they improve on `EVALSHA`?**

A: Redis Functions replace the `EVAL`/`EVALSHA` script cache with a proper library model. Functions are **persistent** (survive restarts, included in RDB dumps), **named** (not by SHA1), and **organized** into libraries:

```bash
# ── Loading a Function Library ────────────────────────────────────────────────
FUNCTION LOAD "#!lua name=inventory_lib\n
  local function reserve(keys, args)
    local stock_key = keys[1]
    local requested = tonumber(args[1])
    local order_id  = args[2]

    local stock = tonumber(redis.call('GET', stock_key))
    if not stock or stock < requested then
      return redis.error_reply('INSUFFICIENT_STOCK')
    end
    redis.call('DECRBY', stock_key, requested)
    redis.call('HSET', 'reservations', order_id, requested)
    return stock - requested
  end

  local function release(keys, args)
    local stock_key = keys[1]
    local order_id  = args[1]

    local reserved = tonumber(redis.call('HGET', 'reservations', order_id))
    if not reserved then return 0 end
    redis.call('INCRBY', stock_key, reserved)
    redis.call('HDEL', 'reservations', order_id)
    return reserved
  end

  redis.register_function('reserve', reserve)
  redis.register_function('release', release)
"

# Replace an existing library:
FUNCTION LOAD REPLACE "#!lua name=inventory_lib\n ..."

# ── Calling a Function ─────────────────────────────────────────────────────────
FCALL reserve 1 stock:product:42 3 order-9999
# → (integer) 97

FCALL release 1 stock:product:42 order-9999
# → (integer) 3

# ── Managing Libraries ─────────────────────────────────────────────────────────
FUNCTION LIST                      # List all libraries
FUNCTION LIST LIBRARYNAME invent*  # Filter by name prefix
FUNCTION DUMP                      # Binary dump (for migration)
FUNCTION RESTORE <dump>            # Restore from dump
FUNCTION DELETE inventory_lib      # Delete a library
FUNCTION STATS                     # Current execution stats (running function, etc.)

# ── What Functions add over EVALSHA ────────────────────────────────────────────
# Feature              EVALSHA          Functions
# ─────────────────────────────────────────────────────────────────────────────
# Persistence          NO (cache only)  YES (in RDB/AOF)
# Survive restart      NO               YES (no reload needed)
# Naming               SHA1 hash only   Human-readable name
# Organization         Individual       Grouped into libraries
# Replication          YES              YES
# Deployment           Manual reload    Atomic library replace
# Discovery            SCRIPT EXISTS    FUNCTION LIST
```

## Section 5: MULTI/EXEC vs Lua vs Pipeline

**Q9. When do you use MULTI/EXEC vs Lua scripting vs pipelining?**

A:

```
DECISION FRAMEWORK:

Question 1: Do you need atomicity at all?
  NO → Use Pipeline (reduces round trips, no atomicity)
  YES → Continue to Question 2

Question 2: Does the logic depend on values read from Redis?
  (i.e., "read X, then decide what to write based on X")
  NO → Use MULTI/EXEC
  YES → Use Lua scripting

Question 3 (for MULTI/EXEC): Can conflicts be handled by retrying?
  YES → Use WATCH + MULTI/EXEC (optimistic locking)
  NO (conflicts are rare + cost of retry is high) → Use Lua scripting
```

```typescript
// ── Pipeline: multiple commands, no atomicity, one round trip ────────────────
const pipeline = redis.pipeline();
pipeline.set('key1', 'value1');
pipeline.incr('counter');
pipeline.expire('key1', 3600);
const results = await pipeline.exec();
// All 3 commands sent in one TCP packet → one round trip
// But another client CAN interrupt between commands
// Results: [[null, 'OK'], [null, 5], [null, 1]]

// ── MULTI/EXEC: atomic sequence, no conditionals ──────────────────────────────
// Good for: "atomically increment two counters"
await redis.multi()
  .incr('total_orders')
  .incr('orders:today')
  .exec();
// Atomic: either both increment or neither does (no conditional logic needed)

// WATCH + MULTI/EXEC: optimistic locking
async function addUniqueItem(setKey: string, item: string): Promise<boolean> {
  while (true) {
    await redis.watch(setKey);
    const isMember = await redis.sismember(setKey, item);
    if (isMember) {
      await redis.unwatch();
      return false;  // Already exists
    }
    const result = await redis.multi().sadd(setKey, item).exec();
    if (result !== null) return true;  // Success
    // result === null means WATCH detected a change → retry
    // Good when conflicts are rare; bad under high contention (many retries)
  }
}

// ── Lua scripting: atomic + conditional ──────────────────────────────────────
// Good for: "check balance, then debit if sufficient"
const debitScript = `
  local balance = tonumber(redis.call('GET', KEYS[1]))
  if not balance or balance < tonumber(ARGV[1]) then
    return 0
  end
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return 1
`;
const success = await redis.eval(debitScript, 1, 'balance:user:1001', '100');
// Atomic check-and-debit — no retry needed, no race condition

// ── Summary ───────────────────────────────────────────────────────────────────
// Pipeline:       Fastest, non-atomic, pure throughput optimization
// MULTI/EXEC:     Simple atomicity, no conditionals, fixed command set
// WATCH+MULTI:    Optimistic locking, retries on conflict, read-then-write
// Lua:            Full power, atomic conditionals, server-side logic, blocking
```

## Section 6: Common Atomic Patterns

**Q10. How do you implement a correct distributed lock release in Lua?**

A: The naive `DEL lock:resource` is unsafe — it may delete a lock held by a different client. The atomic check-and-delete pattern requires Lua:

```lua
-- THE PROBLEM without Lua:
-- Client A: acquires lock, stores UUID "abc123" as value
-- Client A: starts processing (takes 35 seconds)
-- Lock expires at 30 seconds (TTL ran out)
-- Client B: acquires the same lock, stores UUID "xyz789"
-- Client A: finishes, runs: DEL lock:resource
--           ← WRONG: just deleted B's lock, not its own!
-- Client C: acquires the same lock — now A and B and C all think they have the lock

-- CORRECT: check-and-delete (Lua ensures no race between check and delete)
-- lua/release_lock.lua:
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
-- KEYS[1]: lock key name
-- ARGV[1]: the unique token this client stored when it acquired the lock

-- Acquiring the lock (SET NX EX — already atomic without Lua):
-- SET lock:resource <unique_token> NX EX <timeout_seconds>
-- NX = set only if Not eXists (atomic acquisition)
-- EX = expire in N seconds (automatic release on crash)
```

```typescript
class DistributedLock {
  private readonly RELEASE_SCRIPT = `
    if redis.call('GET', KEYS[1]) == ARGV[1] then
      return redis.call('DEL', KEYS[1])
    else
      return 0
    end
  `;

  constructor(private redis: Redis) {}

  async acquire(
    resource:    string,
    ttlSeconds:  number = 30
  ): Promise<string | null> {
    const token = crypto.randomUUID();   // Unique per lock acquisition
    const key   = `lock:${resource}`;

    // Atomic: SET key token NX EX ttl
    // Returns 'OK' if acquired, null if already locked
    const result = await this.redis.set(key, token, 'NX', 'EX', ttlSeconds);
    return result === 'OK' ? token : null;
  }

  async release(resource: string, token: string): Promise<boolean> {
    const key    = `lock:${resource}`;
    const result = await this.redis.eval(
      this.RELEASE_SCRIPT,
      1,       // numkeys
      key,     // KEYS[1]
      token    // ARGV[1]
    ) as number;
    return result === 1;   // 1 = successfully deleted our lock, 0 = not our lock
  }

  async withLock<T>(
    resource:   string,
    ttlSeconds: number,
    fn:         () => Promise<T>
  ): Promise<T> {
    const token = await this.acquire(resource, ttlSeconds);
    if (!token) throw new LockUnavailableError(`Cannot acquire lock: ${resource}`);

    try {
      return await fn();
    } finally {
      await this.release(resource, token);
    }
  }
}

// Usage:
const lock = new DistributedLock(redis);
await lock.withLock('payment:order-9999', 30, async () => {
  // Critical section — only one instance runs this at a time
  await processPayment('order-9999');
});
```

**Q11. How do you implement a sliding window rate limiter atomically in Lua?**

A:

```lua
-- Sliding window rate limiter using Sorted Set
-- KEYS[1]: rate limit key (e.g., "ratelimit:user:1001")
-- ARGV[1]: current timestamp in milliseconds
-- ARGV[2]: window duration in milliseconds
-- ARGV[3]: max requests per window

local key           = KEYS[1]
local now           = tonumber(ARGV[1])
local window_ms     = tonumber(ARGV[2])
local limit         = tonumber(ARGV[3])
local window_start  = now - window_ms

-- 1. Remove expired entries (outside the window)
redis.call('ZREMRANGEBYSCORE', key, 0, window_start)

-- 2. Count current requests in window
local count = redis.call('ZCARD', key)

if count < limit then
  -- 3. Add current request (score=timestamp, member=unique per request)
  --    Using now + random suffix to handle multiple requests at same millisecond
  redis.call('ZADD', key, now, now .. '-' .. math.random(1, 1000000))

  -- 4. Set expiry to slightly longer than window (cleanup)
  redis.call('PEXPIRE', key, window_ms + 1000)

  -- Return: [allowed=1, count=N, limit=L, remaining=L-N-1]
  return {1, count + 1, limit, limit - count - 1}
else
  -- Rate limited: find when the oldest request expires (when they can retry)
  local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
  local retry_after_ms = window_ms - (now - tonumber(oldest[2]))

  -- Return: [allowed=0, count=N, limit=L, retry_after_ms=T]
  return {0, count, limit, retry_after_ms}
end
```

**Q12. How do you implement a token bucket rate limiter in Lua?**

A: The token bucket allows controlled bursting — a bucket fills at a constant rate and each request consumes a token:

```lua
-- Token bucket rate limiter
-- KEYS[1]:  bucket key (e.g., "bucket:user:1001")
-- ARGV[1]:  current timestamp (seconds, float for precision)
-- ARGV[2]:  bucket capacity (max tokens)
-- ARGV[3]:  refill rate (tokens per second)
-- ARGV[4]:  tokens requested (usually 1)

local key          = KEYS[1]
local now          = tonumber(ARGV[1])
local capacity     = tonumber(ARGV[2])
local refill_rate  = tonumber(ARGV[3])
local requested    = tonumber(ARGV[4])

-- Load current state (tokens remaining, last refill time):
local data        = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens      = tonumber(data[1])
local last_refill = tonumber(data[2])

-- First request: initialize bucket at full capacity
if tokens == nil then
  tokens      = capacity
  last_refill = now
end

-- Refill tokens based on elapsed time:
local elapsed    = math.max(0, now - last_refill)   -- clamp to prevent negative elapsed
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

-- Try to consume tokens:
if new_tokens >= requested then
  -- Allow: consume tokens
  local remaining = new_tokens - requested
  redis.call('HMSET', key,
    'tokens',      remaining,
    'last_refill', now
  )
  -- Expire after enough time to fill from 0 to capacity:
  local ttl = math.ceil(capacity / refill_rate) + 10
  redis.call('EXPIRE', key, ttl)
  return {1, math.floor(remaining)}   -- {allowed, tokens_remaining}
else
  -- Deny: update refill time but don't go below 0
  redis.call('HMSET', key,
    'tokens',      new_tokens,
    'last_refill', now
  )
  redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 10)
  -- Return when they can retry: time to accumulate 'requested' tokens
  local wait_time = math.ceil((requested - new_tokens) / refill_rate)
  return {0, math.floor(new_tokens), wait_time}
end

-- Behavior: capacity=100, refill_rate=10/s
-- At t=0: bucket has 100 tokens
-- Send 100 requests: bucket at 0
-- At t=0.1s: +1 token → bucket has 1 (1 more request allowed)
-- At t=10s: +100 tokens → bucket full again
-- Burst of 100 requests allowed; then 10/s sustained
```

**Q13. How do you implement atomic compare-and-swap (CAS) in Lua?**

A:

```lua
-- Atomic Compare-And-Swap:
-- "Set key to new_value only if it currently equals expected_value"
-- Returns 1 on success, 0 if value didn't match (concurrent modification)

local current = redis.call('GET', KEYS[1])

-- Handle nil (key doesn't exist):
if ARGV[1] == '' and current == false then
  -- Special case: expected "empty/nil", and key doesn't exist → match
  redis.call('SET', KEYS[1], ARGV[2])
  return 1
end

if current ~= ARGV[1] then
  -- Value changed since we last read — CAS failure
  return 0
end

-- Values match — perform the swap
if ARGV[2] == '' then
  -- Empty new value means DELETE
  redis.call('DEL', KEYS[1])
else
  redis.call('SET', KEYS[1], ARGV[2])
end
return 1
```

**Q14. How do you implement atomic inventory reservation with expiry cleanup?**

A:

```lua
-- Inventory reservation: atomically check stock, reserve it, and record the reservation
-- KEYS[1]: stock key        (e.g., "stock:product:42")
-- KEYS[2]: reservations key (e.g., "reservations:product:42")
-- ARGV[1]: quantity requested
-- ARGV[2]: reservation ID (order ID or cart ID)
-- ARGV[3]: reservation TTL in seconds (e.g., 900 = 15 minutes)

local stock_key      = KEYS[1]
local reserv_key     = KEYS[2]
local qty            = tonumber(ARGV[1])
local reservation_id = ARGV[2]
local ttl            = tonumber(ARGV[3])

-- Check for duplicate reservation (idempotency):
local existing = redis.call('HGET', reserv_key, reservation_id)
if existing then
  -- Already reserved by this order — return success with existing qty
  return {1, tonumber(existing), tonumber(redis.call('GET', stock_key))}
end

-- Check available stock:
local stock = tonumber(redis.call('GET', stock_key))
if not stock then
  return redis.error_reply('PRODUCT_NOT_FOUND')
end
if stock < qty then
  return redis.error_reply('INSUFFICIENT_STOCK:' .. tostring(stock) .. ':' .. tostring(qty))
end

-- Reserve: decrement stock, record reservation with expiry:
redis.call('DECRBY', stock_key, qty)
redis.call('HSET', reserv_key, reservation_id, qty)
redis.call('EXPIRE', reserv_key, ttl)

-- Return: {success=1, reserved_qty, remaining_stock}
return {1, qty, stock - qty}
```

## Section 7: Performance and Limits

**Q15. What happens when a Lua script runs too long and how do you prevent it?**

A:

```bash
# lua-time-limit: maximum script execution time (default: 5000ms = 5 seconds)
redis-cli CONFIG GET lua-time-limit
# → 5000

redis-cli CONFIG SET lua-time-limit 1000  # Reduce to 1 second for safety

# What happens when the limit is exceeded:
# 1. Script continues running (the limit is not a hard kill)
# 2. Redis starts logging: CRITICAL: A Lua script has been running for too long...
# 3. Redis STARTS ACCEPTING only these commands while script runs:
#    - SCRIPT KILL   (if script has NOT written anything)
#    - SHUTDOWN NOSAVE
# 4. All other clients: receive "BUSY Redis is busy running a script"

# If the script has NOT made any writes:
SCRIPT KILL
# → OK (script is terminated, transaction rolled back)

# If the script HAS made writes (cannot safely kill mid-write):
# SCRIPT KILL returns: (error) UNKILLABLE Script already executed write commands
# The only option is to let it finish or: SHUTDOWN NOSAVE (lose unsaved data!)

# Prevention strategies:
# 1. Never iterate over unbounded data in Lua:
for _, key in ipairs(redis.call('KEYS', '*')) do   -- NEVER do this
  redis.call('DEL', key)   -- Could take forever on production DB
end

# 2. Add iteration limits:
local count = 0
local max_iterations = 1000
while count < max_iterations do
  -- ... process one item ...
  count = count + 1
end

# 3. Process in batches instead of one giant script:
-- Bad: one script processes 1 million items
-- Good: many scripts each process 1000 items (call from application in a loop)

# 4. Set lua-time-limit conservatively:
# If your longest legitimate script takes 100ms: set limit to 500ms
# This gives headroom for slow moments while catching true runaway scripts
```

**Q16. What are the performance tradeoffs of Lua scripts vs pure Redis commands?**

A:

```
Performance profile of Lua scripts:

BENEFITS:
  ✓ Eliminates multiple round trips (N commands → 1 EVAL round trip)
  ✓ Avoids client-server-client-server zigzag for conditional logic
  ✓ EVALSHA + pre-loaded scripts: only 40-char SHA sent vs full script body

COSTS:
  ✓ Script startup overhead: ~10-50 microseconds to initialize Lua VM per EVAL
  ✗ Blocks ALL other clients for the duration of the script
  ✗ Cannot use Lua for I/O operations (no HTTP calls, file reads, etc.)
  ✗ Debugging is harder than pure Redis commands

Typical latency comparison (single Redis server, LAN):
  2 separate GET+SET:    ~0.5ms (1 round trip per command × 2)
  Pipeline GET+SET:      ~0.3ms (both commands in 1 round trip)
  Lua script GET+SET:    ~0.1ms (1 round trip, server-side execution of both)

When Lua wins significantly:
  - Read-modify-write patterns (at least 2 round trips → 1)
  - Conditional logic (WATCH+MULTI+EXEC overhead avoided)
  - Complex atomic operations

When Lua is unnecessary overhead:
  - Single command: just call the command directly
  - Fixed set of commands without conditionals: use MULTI/EXEC or Pipeline
  - One-time administrative operations

Rule of thumb: use Lua when you need atomicity + conditionality, not just atomicity.
```

## Section 9: Scenario-Based Questions

**Q18. "What is wrong with these Lua scripts and what are the consequences?"**

```lua
-- Script A:
local keys = redis.call('KEYS', '*')
for _, key in ipairs(keys) do
  if redis.call('TTL', key) == -1 then
    redis.call('EXPIRE', key, 3600)
  end
end
return #keys
```

```lua
-- Script B:
local user_id = ARGV[1]  -- "user:1001"
local result = redis.call('GET', 'sessions:' .. user_id)
return result
```

```lua
-- Script C:
local count = redis.call('INCR', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[1])
return count
```

A: Three distinct problems:

**Script A — `KEYS *` causes catastrophic blocking:**
```lua
-- Problem 1: KEYS * scans every key in the database
-- On a production Redis with 10 million keys: takes seconds
-- During this scan: ALL other clients are blocked (Lua atomicity guarantee)
-- This is the #1 cause of Redis production outages from Lua scripts

-- Problem 2: Iterating 10 million keys in Lua is extremely slow
-- Each redis.call() within the loop has overhead

-- Problem 3: No bound on execution time → will exceed lua-time-limit

-- Fix: Use SCAN instead, and do it iteratively from the application (not in Lua):
-- SCAN 0 MATCH * COUNT 1000 → process batch → SCAN cursor → repeat
-- Never use KEYS in production; never call KEYS from Lua

-- Fix for the task: use a background job with SCAN, not a Lua script
```

**Script B — hardcoded key prefix violates Cluster compatibility:**
```lua
-- Problem: 'sessions:' .. user_id hardcodes the key prefix in the script
-- In Redis Cluster: the cluster cannot parse which key is accessed
-- The key 'sessions:user:1001' is NOT in the KEYS array
-- → Cluster routes the script to a random shard → might not be where the key lives

-- Consequence: in single-instance Redis: works fine
--              in Redis Cluster: random failures (MOVED errors)

-- Fix: pass the key as KEYS[1]
local result = redis.call('GET', KEYS[1])
return result
-- Caller: EVAL script 1 "sessions:user:1001"
```

**Script C — race condition between INCR and EXPIRE:**
```lua
-- Problem: INCR and EXPIRE are two separate commands
-- In Lua they're atomic (no other client interrupts), BUT:
-- If the script crashes or is killed between INCR and EXPIRE (extremely rare),
-- the counter exists without TTL (leaks)

-- More importantly: the Expire is called EVERY time, resetting the TTL on every request
-- For a rate limiter, this means the window keeps sliding with each request
-- A client who sends 1 request per second never expires → bypasses rate limiting

-- Fix: set EXPIRE only on the first increment (count == 1):
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return count
-- This correctly starts the window on the first request, not on every request
```

**Q19. "Implement an atomic session token rotation — read the old token, generate a new one, and swap them, all without any window where both or neither are valid."**

A:

```lua
-- Session token rotation:
-- KEYS[1]: session key holding the current token
-- ARGV[1]: new token (generated by the application before calling)
-- ARGV[2]: session TTL in seconds

-- The race condition WITHOUT atomicity:
-- Step 1: GET current_token
-- [race: another client invalidates the token here]
-- Step 2: SET key new_token
-- Step 3: DELETE old_token
-- Window: between step 1 and 2, the old token is still valid but we already "rotated"

-- Atomic rotation ensures:
-- 1. We return the old token (for invalidation or comparison)
-- 2. The new token is set in the same atomic operation
-- 3. Zero window where both or neither are valid

local session_key = KEYS[1]
local new_token   = ARGV[1]
local ttl         = tonumber(ARGV[2])

-- Get and immediately replace the current token:
local old_token = redis.call('GET', session_key)

-- Whether the session exists or not, set the new token:
redis.call('SET', session_key, new_token, 'EX', ttl)

-- Return the old token so the caller knows what to invalidate:
if old_token == false then
  return redis.status_reply('NEW_SESSION')
end
return old_token
```

```typescript
class SessionManager {
  private readonly ROTATION_SCRIPT = `
    local old_token = redis.call('GET', KEYS[1])
    redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[2])
    if old_token == false then
      return redis.status_reply('NEW_SESSION')
    end
    return old_token
  `;

  private readonly VALIDATE_SCRIPT = `
    -- Atomic token validation + TTL extension
    local current = redis.call('GET', KEYS[1])
    if current == false then
      return redis.error_reply('SESSION_NOT_FOUND')
    end
    if current ~= ARGV[1] then
      return redis.error_reply('TOKEN_MISMATCH')
    end
    -- Valid: extend the session
    redis.call('EXPIRE', KEYS[1], ARGV[2])
    return current
  `;

  async createSession(userId: string, ttlSeconds: number): Promise<string> {
    const token      = crypto.randomUUID();
    const sessionKey = `session:${userId}`;

    const result = await redis.eval(
      this.ROTATION_SCRIPT, 1,
      sessionKey, token, ttlSeconds.toString()
    );
    // result is 'NEW_SESSION' (status) or old token (string)
    return token;
  }

  async rotateToken(userId: string, currentToken: string, ttlSeconds: number): Promise<{
    newToken: string;
    invalidatedToken: string;
  }> {
    const sessionKey = `session:${userId}`;
    const newToken   = crypto.randomUUID();

    // First validate the current token (optional: include in rotation script):
    const oldToken = await redis.eval(
      this.ROTATION_SCRIPT, 1,
      sessionKey, newToken, ttlSeconds.toString()
    ) as string;

    if (oldToken === 'NEW_SESSION') {
      throw new SessionNotFoundError(userId);
    }
    if (oldToken !== currentToken) {
      // The token changed between the request arriving and now — possible replay attack
      throw new TokenMismatchError('Token was already rotated by another request');
    }

    return { newToken, invalidatedToken: oldToken };
  }

  async validate(userId: string, token: string, ttlSeconds: number): Promise<boolean> {
    const sessionKey = `session:${userId}`;

    try {
      await redis.eval(
        this.VALIDATE_SCRIPT, 1,
        sessionKey, token, ttlSeconds.toString()
      );
      return true;
    } catch (err) {
      return false;  // SESSION_NOT_FOUND or TOKEN_MISMATCH
    }
  }
}
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **`EVAL` syntax** | `EVAL script numkeys key [key ...] arg [arg ...]` — KEYS and ARGV are 1-indexed |
| **Atomicity guarantee** | Script monopolizes Redis event loop — NO other commands execute during script |
| **Not a transaction** | No ROLLBACK — commands executed before an error are committed; write idempotent logic |
| **`redis.call()`** | Raises error immediately on Redis error — whole script aborts |
| **`redis.pcall()`** | Returns `{ err = "message" }` on error — script can inspect and continue |
| **`redis.error_reply(msg)`** | Return a Redis error reply to caller — `(error) msg` |
| **`redis.status_reply(msg)`** | Return a Redis status reply — `+msg` |
| **Float return trap** | Lua floats are truncated to int when returned — use `tostring(float)` to return decimals |
| **Nil as false** | Redis nil bulk reply → Lua `false` (not `nil`) — check `if val == false` or `if not val` |
| **`EVALSHA`** | Send 40-char SHA1 instead of full script body — load once with `SCRIPT LOAD` |
| **Script cache** | NOT persistent — cleared on restart; use EVALSHA with NOSCRIPT error retry |
| **Redis Functions (7.0+)** | `FUNCTION LOAD` / `FCALL` — persistent, named, organized into libraries |
| **KEYS array requirement** | All accessed keys must be in KEYS array for Cluster compatibility — never hardcode key names |
| **Hash tags** | `{user:1001}:session` and `{user:1001}:profile` hash to same slot → usable in same script |
| **`lua-time-limit`** | Default 5000ms — after this, only SCRIPT KILL or SHUTDOWN NOSAVE accepted |
| **`SCRIPT KILL`** | Terminates a running script ONLY if it has not made any writes |
| **`KEYS *` in Lua** | NEVER — scans entire keyspace, blocks all clients for seconds; use SCAN from application |
| **`MULTI/EXEC` vs Lua** | MULTI/EXEC: no conditionals, fixed command set; Lua: full conditionals, server-side logic |
| **WATCH + MULTI** | Optimistic locking — good for low-contention; Lua is better for high-contention CAS |
| **redis.log()** | `redis.log(redis.LOG_WARNING, msg)` — writes to Redis server log file |
| **`--eval` flag** | `redis-cli --eval script.lua key1 key2 , arg1 arg2` — test scripts from CLI |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining **why Lua is needed beyond `MULTI/EXEC`** precisely — `MULTI/EXEC` queues commands for atomic execution but cannot branch based on values read from Redis; a `GET` inside `MULTI` returns `QUEUED`, not the value; Lua runs server-side with real variables and conditionals, enabling the read-then-conditionally-write pattern that is the core use case; (2) the **`KEYS *` anti-pattern in Lua** — calling `redis.call('KEYS', '*')` inside a Lua script scans the entire keyspace while blocking ALL other clients (Lua atomicity), turning a bad command into a catastrophic one; the correct approach is SCAN from the application in a loop, never KEYS from Lua; (3) **the distributed lock release pattern** and why the naive `DEL lock:key` is wrong — if the lock's TTL expired between the application's work completing and the `DEL` executing, another client may have acquired the lock, and `DEL` would delete their lock; the atomic Lua pattern `if GET(key) == my_token then DEL(key)` ensures we only delete our own lock; (4) the **`EVALSHA` + NOSCRIPT retry pattern** — pre-loading scripts with `SCRIPT LOAD` returns a SHA1 used in subsequent `EVALSHA` calls (40 chars vs full script body), but the script cache is volatile and cleared on restart; production code must catch `NOSCRIPT` errors and reload via `EVAL`/`SCRIPT LOAD` then retry; and (5) knowing that **Lua `false` is not `nil`** — Redis nil replies (missing keys) become Lua `false` not Lua `nil`, so checking `if result == nil then` is WRONG; the correct check is `if result == false then` or `if not result then`; this is one of the most common Lua scripting bugs.
