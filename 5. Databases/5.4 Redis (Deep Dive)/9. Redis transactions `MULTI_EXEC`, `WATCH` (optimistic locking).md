# Redis Transactions: `MULTI/EXEC`, `WATCH` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a Redis transaction and how does it differ fundamentally from a database transaction?**
A: A Redis transaction is a block of commands queued and executed atomically in a single pass. The word "transaction" is intentionally limited here — Redis transactions provide atomicity and isolation but deliberately do NOT provide rollback on command errors. Understanding what Redis transactions are and are not prevents a class of subtle bugs that arise from applying SQL transaction semantics to Redis:

```
What Redis MULTI/EXEC provides:

  Atomicity (partial):
    All queued commands execute as a single uninterrupted unit
    No other client's commands can interleave between MULTI and EXEC
    The server processes the entire queue in one shot — no interleaving
    BUT: if a command inside the transaction fails (runtime error):
         the other commands still execute — there is NO rollback

  Isolation:
    From other clients' perspective: the transaction is invisible until EXEC
    No partial state is visible to other clients during the queued phase
    All effects become visible atomically on EXEC

What Redis MULTI/EXEC does NOT provide:

  Rollback:
    SQL: BEGIN → error → ROLLBACK → all changes undone
    Redis: MULTI → EXEC → one command fails → other commands committed
    "Errors happening inside a transaction do not stop it" — Redis docs

  Serializability:
    Redis is single-threaded: transactions execute serially
    BUT: between MULTI and EXEC (the queuing phase), other clients run freely
    The "read then conditionally write" pattern requires WATCH (see Q5)

  Cross-key consistency checks:
    Redis cannot enforce: "only commit if loan.balance ≥ withdrawal_amount"
    Conditions are evaluated in application code BEFORE MULTI
    By the time EXEC runs, the condition may no longer hold (race condition)
    WATCH solves this specific problem (see Q5)

Database comparison:
  ┌──────────────────────┬─────────────────────────┬────────────────────────┐
  │ Property             │ SQL Transaction          │ Redis MULTI/EXEC       │
  ├──────────────────────┼─────────────────────────┼────────────────────────┤
  │ Atomicity            │ Yes (all or nothing)     │ Partial (no rollback)  │
  │ Consistency          │ Yes (constraints)        │ No (no constraints)    │
  │ Isolation            │ Yes (concurrent txns)    │ Yes (single-threaded)  │
  │ Durability           │ Yes (WAL)                │ Depends on persistence │
  │ Rollback on error    │ Yes                      │ No                     │
  │ Read-then-write safe │ Yes (locking/SSI)        │ No (need WATCH)        │
  │ Nested transactions  │ Yes (SAVEPOINT)          │ No                     │
  └──────────────────────┴─────────────────────────┴────────────────────────┘

Why Redis made this choice:
  Redis is designed for high throughput (100K+ ops/second)
  Rollback requires storing "undo" state → memory and CPU overhead
  Redis's view: programming errors (wrong type) should be caught in testing
                not via rollback in production
  The most common Redis use cases (caching, counting, queuing) don't need rollback
  For rollback semantics: use a relational database
```

**Q2. What is Redis's single-threaded execution model and why does it make MULTI/EXEC safe from interleaving?**
A: Redis processes commands from all clients on a single thread. This means only one command executes at any moment. MULTI/EXEC exploits this: the entire queued command block is executed without yielding back to the event loop, making interleaving from other clients impossible during EXEC:

```
Redis event loop (simplified):

  Single thread:
    while (true) {
        event = epoll_wait(fd_set);   // wait for any client activity
        for each (readable client in event) {
            command = parseCommand(client.buffer);
            if (client.inTransaction) {
                queueCommand(client.txQueue, command);  // MULTI state: queue it
                sendQueued(client);                     // reply: QUEUED
            } else {
                result = executeCommand(command);       // normal: execute now
                sendReply(client, result);
            }
        }
        // EXEC processing:
        for each (client with pending EXEC) {
            for each (command in client.txQueue) {
                executeCommand(command);  // runs all queued commands
            }
            sendBulkReply(client, results);
        }
    }

Why no interleaving during EXEC:
  The EXEC loop runs ALL queued commands WITHOUT yielding to epoll_wait
  No other client's commands can run between queue[0] and queue[N]
  Redis's single thread is the guarantee — not locks or snapshots

Proof of atomicity (client A and client B race):

  Without MULTI/EXEC (not atomic):
    Time → Client A            Time → Client B
    GET counter  → 10           -
    -                           GET counter → 10    ← reads same value
    SET counter 11              -
    -                           SET counter 11      ← overwrites A's write!
    Final: 11 instead of 12 (lost update)

  With MULTI/EXEC (atomic):
    Client A:        Client B:
    MULTI            (waits)
    GET counter      (waits)
    SET counter 11   (waits)
    EXEC → executes all 3 at once, no other commands run between them
    (Client B runs after EXEC completes)
    Final: correct sequence

  Note: GET inside a transaction returns a queued command result, NOT a value
  MULTI/EXEC is for WRITE atomicity — reads inside a transaction don't return live values
  You cannot use "read the value, then conditionally write" inside MULTI alone
  → That requires WATCH (see Q5)
```

## Section 2: MULTI/EXEC Mechanics

**Q3. What is the complete MULTI/EXEC lifecycle and what responses does each phase return?**

```
MULTI/EXEC lifecycle (four phases):

Phase 1: MULTI — enter transaction mode
  Client sends: MULTI
  Server responds: +OK
  Server state: client.inTransaction = true, client.txQueue = []

Phase 2: Queuing — accumulate commands
  Client sends any write command (SET, INCR, HSET, LPUSH, etc.)
  Server does NOT execute it
  Server responds: +QUEUED  ← this is the only valid response during queuing
  Server state: command appended to txQueue

  Two types of errors during queuing:
    a. Syntax errors (command doesn't exist, wrong arg count):
       Server responds: -ERR  ← error, NOT QUEUED
       Transaction is DISCARDED automatically on EXEC (entire txn aborted)
       This is the ONE case Redis discards the whole transaction

    b. Wrong-type errors (LPUSH on a string key):
       Server responds: +QUEUED  ← command is queued despite being wrong
       Error only surfaces at EXEC time (not pre-flight checked)
       Transaction still executes other commands (no rollback)

Phase 3: EXEC — execute all queued commands
  Client sends: EXEC
  Server executes every command in queue, in order, without interruption
  Server responds: array of results, one per queued command

  Response format:
  1) (reply for command 1)
  2) (error for command 2, if it failed at runtime)
  3) (reply for command 3)
  ...
  Bulk reply: client receives all results at once

Phase 4: Optional DISCARD — abandon queued commands
  Client sends: DISCARD
  Server discards txQueue, exits transaction mode
  Server responds: +OK
  Use: when application logic decides mid-queuing that the transaction shouldn't run

Complete example in Redis CLI:
  > MULTI
  OK
  > SET loan:L1:status "approved"
  QUEUED
  > HINCRBY loan:L1:stats approvals 1
  QUEUED
  > ZADD leaderboard 750 "borrower:B1"
  QUEUED
  > EXEC
  1) OK                    ← result of SET
  2) (integer) 5           ← result of HINCRBY (new value: 5)
  3) (integer) 1           ← result of ZADD (1 new member added)

Error within EXEC (wrong type — not a syntax error):
  > MULTI
  OK
  > SET mykey "hello"
  QUEUED
  > LPUSH mykey item       ← mykey is a string, not a list
  QUEUED
  > INCR counter
  QUEUED
  > EXEC
  1) OK                    ← SET succeeded
  2) (error) WRONGTYPE...  ← LPUSH failed (type mismatch)
  3) (integer) 1           ← INCR succeeded  ← NOT rolled back!
  // mykey = "hello" (set), counter = 1 (incremented) — LPUSH error was isolated
```

**Q4. How do you use MULTI/EXEC in Node.js and what does the pipeline API look like?**

```javascript
import { createClient } from 'redis';

const client = await createClient({ url: 'redis://localhost:6379' }).connect();

// ── Basic MULTI/EXEC with Node.js redis client ────────────────────────────────

// Method 1: client.multi() — returns a transaction object
// Commands are queued locally, sent in one batch on exec()
const multi = client.multi();

multi.set('loan:L1:status', 'approved');
multi.hIncrBy('loan:L1:stats', 'approvals', 1);
multi.zAdd('leaderboard', { score: 750, value: 'borrower:B1' });

const results = await multi.exec();
// results: ['OK', 5, 1]
// If any command fails: results[i] is an Error instance, not thrown

// Handling per-command errors:
const multi2 = client.multi();
multi2.set('mykey', 'hello');
multi2.lPush('mykey', 'item');  // will fail: mykey is a string
multi2.incr('counter');

const results2 = await multi2.exec();
// results2: ['OK', Error('WRONGTYPE...'), 1]
// Other commands run — no rollback
// Application must check each result:
results2.forEach((result, i) => {
    if (result instanceof Error) {
        console.error(`Command ${i} failed:`, result.message);
    }
});

// Method 2: execAsPipeline() (not a transaction — no atomicity)
// Sends commands in a batch for network efficiency but without MULTI/EXEC
// Use when atomicity is NOT needed (reduces round trips)
const pipeline = client.multi();  // same API, different execution mode
// Note: in node-redis v4, multi() always sends MULTI/EXEC
// Pipelining without MULTI uses .pipeline() in some older drivers

// ── DISCARD example ───────────────────────────────────────────────────────────
const multi3 = client.multi();
multi3.set('loan:L2:status', 'processing');
multi3.hSet('loan:L2', 'officer_id', 'O1');

// Application decides: cancel this transaction
await multi3.discard();
// Commands never executed, no state changed

// ── Transaction inside a retry loop (pattern for WATCH) ──────────────────────
// See Q6 for WATCH + retry pattern

// ── NestJS / Service layer pattern ───────────────────────────────────────────
@Injectable()
export class LoanStatusService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async approveAndUpdateStats(loanId: string, borrowerId: string, score: number): Promise<void> {
        const multi = this.redis.multi();

        multi.set(`loan:${loanId}:status`, 'approved');
        multi.hIncrBy(`stats:loans`, 'total_approved', 1);
        multi.hSet(`loan:${loanId}:meta`, {
            approved_at: Date.now().toString(),
            officer: 'SYSTEM'
        });
        multi.zAdd('approved_loans_by_score', { score, value: `loan:${loanId}` });

        const results = await multi.exec();

        // Check for errors (unlikely for these command types, but defensive):
        const errors = results.filter(r => r instanceof Error);
        if (errors.length > 0) {
            throw new InternalServerErrorException(
                `Transaction partially failed: ${errors.map(e => (e as Error).message).join(', ')}`
            );
        }
    }
}
```

## Section 3: WATCH — Optimistic Locking

**Q5. What problem does WATCH solve that MULTI/EXEC alone cannot, and how does it work?**
A: MULTI/EXEC ensures commands execute without interleaving, but it cannot handle the read-then-write pattern: you cannot read a value, make a decision, and write based on that decision — because the value may change between your read and your EXEC. WATCH provides optimistic locking: watch a key, and if ANY other client modifies it before your EXEC, the entire transaction is aborted:

```
The read-then-write race condition (without WATCH):

  Goal: increment a loan's amount only if it's below 500,000

  Client A:                    Client B:
  GET loan:L1:amount → 480000  -
  -                            SET loan:L1:amount 490000  ← B modifies it
  (amount < 500000: proceed)
  MULTI
  SET loan:L1:amount 530000    ← A sets to 480000 + 50000 based on STALE read
  EXEC
  Final: 530000 — WRONG! Correct should be: reject (490000 + 50000 = 540000 > 500000)
  A made a decision on a value that was already stale

WATCH solves this with optimistic locking:

  Client A:
  WATCH loan:L1:amount         ← register: "tell me if this changes"
  GET loan:L1:amount → 480000  ← read the watched key
  (480000 < 500000: conditionally proceed)
  MULTI
  SET loan:L1:amount 530000
  EXEC → returns nil           ← ABORTED because B modified loan:L1:amount after WATCH!

  Client B (between WATCH and EXEC):
  SET loan:L1:amount 490000    ← modifies the watched key

  WATCH mechanism:
    WATCH registers the key in Redis's "watched keys" table for this client
    Redis tracks the current version of the key at WATCH time
    If ANY client (including this one) modifies the key before EXEC:
      → EXEC returns nil (empty reply) instead of an array of results
      → Transaction is aborted — NO commands executed
      → Client should retry (re-read, re-evaluate, re-queue)

  What "modify" means for WATCH:
    Any write command: SET, DEL, INCR, HSET, LPUSH, EXPIRE, etc.
    Even if the VALUE doesn't change: SET key same_value still triggers abort
    Expiration of a watched key (TTL expiry) also triggers abort

  WATCH is reset by:
    EXEC (whether succeeded or aborted): WATCH is cleared
    DISCARD: WATCH is cleared
    UNWATCH: explicitly unwatch all keys
    Connection close: WATCH is cleared

  WATCH + MULTI/EXEC = compare-and-swap (CAS):
    WATCH key         ← checkpoint: "I've seen this value"
    GET key           ← read the current value
    < application logic >
    MULTI
    SET key new_value ← write based on what we read
    EXEC              ← succeeds ONLY IF key wasn't modified since WATCH
```

**Q6. How do you implement the WATCH/MULTI/EXEC retry loop correctly?**
A: Because a WATCH abort means "the value changed — try again", the correct pattern wraps the entire operation in a retry loop. The loop re-reads the value and re-evaluates the condition on each attempt:

```javascript
import { createClient, WatchError } from 'redis';

const client = await createClient({ url: 'redis://localhost:6379' }).connect();

// ── Pattern 1: Manual WATCH/MULTI/EXEC retry loop ────────────────────────────

async function incrementIfBelow(key: string, limit: number, increment: number): Promise<boolean> {
    const MAX_RETRIES = 10;

    for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
        // Step 1: WATCH the key (must happen BEFORE reading)
        await client.watch(key);

        // Step 2: Read the current value
        const currentValue = await client.get(key);
        const current = parseInt(currentValue ?? '0', 10);

        // Step 3: Application logic (check condition)
        if (current + increment > limit) {
            // Condition fails: no need to write
            await client.unwatch();  // release the watch
            return false;            // signal: limit would be exceeded
        }

        // Step 4: Queue and execute transaction
        const multi = client.multi();
        multi.set(key, (current + increment).toString());
        // Add any other atomically-needed commands here

        try {
            const results = await multi.exec();
            // exec() returns null if WATCH detected a change (WatchError in some drivers)
            if (results === null) {
                // Transaction was aborted — retry
                continue;
            }
            return true;  // success
        } catch (err) {
            if (err instanceof WatchError) {
                // In some driver versions: WatchError thrown instead of null return
                continue;  // retry
            }
            throw err;  // unexpected error: rethrow
        }
    }

    throw new Error(`Could not complete transaction after ${MAX_RETRIES} attempts`);
}

// ── Pattern 2: client.executeIsolated() — cleaner WATCH pattern ──────────────
// node-redis v4 provides executeIsolated() which gives a dedicated connection
// for WATCH/MULTI/EXEC to avoid contaminating the shared connection pool

async function transferBalance(fromKey: string, toKey: string, amount: number): Promise<boolean> {
    return client.executeIsolated(async (isolatedClient) => {
        const MAX_RETRIES = 5;

        for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
            // Watch both keys — abort if EITHER changes:
            await isolatedClient.watch([fromKey, toKey]);

            const [fromBalance, toBalance] = await Promise.all([
                isolatedClient.get(fromKey),
                isolatedClient.get(toKey)
            ]);

            const from = parseFloat(fromBalance ?? '0');
            const to   = parseFloat(toBalance ?? '0');

            if (from < amount) {
                await isolatedClient.unwatch();
                return false;  // insufficient balance
            }

            const multi = isolatedClient.multi();
            multi.set(fromKey, (from - amount).toFixed(2));
            multi.set(toKey,   (to + amount).toFixed(2));

            const results = await multi.exec();

            if (results === null) {
                // Watched key changed — retry
                const delay = Math.min(10 * 2 ** attempt, 100);  // exponential backoff
                await sleep(delay);
                continue;
            }

            return true;  // transfer succeeded
        }

        return false;  // too many retries (high contention)
    });
}

// ── Pattern 3: ioredis watchMulti helper ─────────────────────────────────────
// ioredis provides a cleaner API for WATCH:
import Redis from 'ioredis';
const ioredis = new Redis();

async function conditionalUpdate(key: string, expectedValue: string, newValue: string): Promise<boolean> {
    let attempts = 0;
    while (attempts < 5) {
        attempts++;
        let result: string[] | null;

        try {
            result = await ioredis
                .multi()
                .watch(key)
                .set(key, newValue)
                .exec();
        } catch (err) {
            continue;  // retry on error
        }
        // ioredis: null result means WATCH abort
        if (result !== null) return true;
    }
    return false;
}

// ── Pattern 4: Lua scripts as an alternative to WATCH ────────────────────────
// Lua scripts execute atomically in Redis WITHOUT needing WATCH
// For complex conditions: Lua is often simpler and more efficient than WATCH retry loop

const transferLua = `
local fromBalance = tonumber(redis.call('GET', KEYS[1]))
local toBalance   = tonumber(redis.call('GET', KEYS[2]))
local amount      = tonumber(ARGV[1])

if fromBalance == nil then
    return redis.error_reply('ERR source key does not exist')
end
if fromBalance < amount then
    return redis.error_reply('ERR insufficient balance')
end

redis.call('SET', KEYS[1], tostring(fromBalance - amount))
redis.call('SET', KEYS[2], tostring((toBalance or 0) + amount))
return 'OK'
`;

// Load script (returns SHA):
const sha = await client.scriptLoad(transferLua);

// Execute:
try {
    await client.evalSha(sha, {
        keys: ['account:A1:balance', 'account:A2:balance'],
        arguments: ['5000']
    });
    console.log('Transfer successful');
} catch (err) {
    if (err.message.includes('insufficient balance')) {
        console.log('Transfer rejected: insufficient funds');
    }
}
// Lua executes atomically — no WATCH needed, no retry loop needed
// But: Lua is synchronous (blocks Redis during execution) — keep scripts short
```

**Q7. What are the subtle failure modes of WATCH that catch developers off-guard?**

```javascript
// ── Failure mode 1: Reading WITHOUT WATCH first ────────────────────────────────
// WRONG — reading before WATCH means the value can change before WATCH registers:
const value = await client.get('counter');   // read BEFORE WATCH
await client.watch('counter');               // watch AFTER read
// Between GET and WATCH: another client modified counter → we don't know!
// The WATCH only detects changes AFTER it was set
// The pre-WATCH read is stale

// CORRECT — WATCH before read:
await client.watch('counter');               // watch FIRST
const value = await client.get('counter');   // read AFTER WATCH
// Now: if counter changes between WATCH and EXEC → EXEC returns null → retry

// ── Failure mode 2: Watching the wrong key ────────────────────────────────────
// WRONG — watching a key that isn't the one you're basing logic on:
await client.watch('session:user123');       // watching sessions
const balance = await client.get('account:A1:balance');  // reading balance
const multi = client.multi();
multi.set('account:A1:balance', (parseFloat(balance) - 100).toString());
await multi.exec();
// The balance can change between read and EXEC — session WATCH doesn't protect it!

// CORRECT — watch exactly the keys you read and write based on:
await client.watch('account:A1:balance');    // watch what you're reading
const balance = await client.get('account:A1:balance');
const multi = client.multi();
multi.set('account:A1:balance', (parseFloat(balance) - 100).toString());
await multi.exec();

// ── Failure mode 3: Not retrying on null result ───────────────────────────────
// WRONG — treating null as success:
await client.watch('counter');
const val = await client.get('counter');
const multi = client.multi();
multi.incr('counter');
const result = await multi.exec();
// result is null if WATCH aborted — but this code doesn't check!
// Silently does nothing → counter not incremented → application proceeds as if it was

// CORRECT — check for null and retry:
let result = null;
while (result === null) {
    await client.watch('counter');
    const val = await client.get('counter');
    const multi = client.multi();
    multi.set('counter', (parseInt(val ?? '0') + 1).toString());
    result = await multi.exec();
}

// ── Failure mode 4: WATCH in connection pool environment ──────────────────────
// WRONG — using a pooled connection for WATCH:
// Connection pools share connections across requests
// If connection is returned to pool between WATCH and EXEC:
//   Another request reuses the same connection → executes unrelated commands
//   EXEC runs in the context of those unrelated commands → undefined behavior

// CORRECT — use a dedicated connection for WATCH/MULTI/EXEC:
// node-redis: client.executeIsolated()
// ioredis: use a fresh connection or ioredis.duplicate()
const dedicated = client.duplicate();
await dedicated.connect();
try {
    await dedicated.watch('counter');
    const val = await dedicated.get('counter');
    const multi = dedicated.multi();
    multi.incr('counter');
    await multi.exec();
} finally {
    await dedicated.disconnect();
}

// ── Failure mode 5: TTL expiry triggering abort ───────────────────────────────
// If a watched key expires between WATCH and EXEC:
// The key "changed" (from existing to non-existent) → EXEC aborts
// This can cause infinite retry loops if the key expires faster than retries complete

await client.watch('rate:limit:user123');   // key has TTL of 1 second
await sleep(1100);                          // key expires during application logic
const multi = client.multi();
multi.incr('rate:limit:user123');
const result = await multi.exec();
// result = null → retry → key still doesn't exist → watch sees no key → hmm
// A non-existent key: WATCH triggers on creation (nil → value change)

// Solution: use Lua script for rate limiting (no WATCH needed):
const rateLimitLua = `
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local ttl = tonumber(ARGV[2])
local current = tonumber(redis.call('GET', key)) or 0
if current >= limit then
    return 0
end
redis.call('INCR', key)
if current == 0 then
    redis.call('EXPIRE', key, ttl)
end
return 1
`;

// ── Failure mode 6: High contention → infinite retries ────────────────────────
// Under high concurrency on the same key: every client retries but only one wins per attempt
// N concurrent clients: O(N²) total attempts in the worst case
// Solution for hot keys: use INCR (atomic, no WATCH needed) or Lua scripts
// WATCH is designed for LOW-contention scenarios
```

## Section 4: Practical Patterns

**Q8. What are the correct use cases for MULTI/EXEC (without WATCH) and what can you accomplish with simple batched atomicity?**

```javascript
// MULTI/EXEC without WATCH: use when you don't need to read-then-write
// The commands are write-only or the writes don't depend on current values

// ── Pattern 1: Atomic multi-key update (status change + stats) ───────────────
async function markLoanDisbursed(loanId: string, borrowerId: string, amount: number): Promise<void> {
    const now = Date.now();
    const multi = client.multi();

    // All writes — no reads needed inside the transaction:
    multi.hSet(`loan:${loanId}`, {
        status: 'disbursed',
        disbursed_at: now.toString(),
        disbursed_amount: amount.toString()
    });
    multi.sAdd('loans:disbursed', loanId);            // add to disbursed set
    multi.sRem('loans:active', loanId);               // remove from active set
    multi.hIncrByFloat('stats:disbursements:today',
        'total_amount', amount);                       // increment daily total
    multi.hIncrBy('stats:disbursements:today',
        'count', 1);                                   // increment count
    multi.zAdd('disbursements:recent',
        { score: now, value: loanId });               // add to recent sorted set
    multi.expire(`loan:${loanId}:processing_lock`, 0); // delete the lock

    await multi.exec();
    // All 7 operations execute atomically
    // No other client can see a partial state (e.g. loan in BOTH active and disbursed sets)
}

// ── Pattern 2: Cache warm-up (atomic SET multiple keys) ──────────────────────
async function cacheUserProfile(userId: string, profile: UserProfile): Promise<void> {
    const key = `user:${userId}`;
    const multi = client.multi();

    multi.hSet(key, {
        name:       profile.name,
        email:      profile.email,
        credit_score: profile.creditScore.toString(),
        kyc_status: profile.kycStatus
    });
    multi.expire(key, 3600);   // 1 hour TTL — atomically with the hSet

    await multi.exec();
    // Without MULTI: hSet succeeds but expire might fail → key lives forever
    // With MULTI: both happen atomically → no "zombie" keys without TTL
}

// ── Pattern 3: Pub/Sub + state update atomically ─────────────────────────────
async function approveAndNotify(loanId: string): Promise<void> {
    const multi = client.multi();

    multi.hSet(`loan:${loanId}`, 'status', 'approved');
    multi.lPush('notifications:queue', JSON.stringify({
        type: 'LOAN_APPROVED',
        loan_id: loanId,
        timestamp: Date.now()
    }));
    multi.publish('loan:events', JSON.stringify({ event: 'approved', loanId }));

    await multi.exec();
    // State update + notification queue push + pub/sub happen atomically
    // No scenario where loan is marked approved but notification is missing
}

// ── Pattern 4: Batch delete with MULTI ───────────────────────────────────────
async function clearUserSession(sessionId: string, userId: string): Promise<void> {
    const multi = client.multi();

    multi.del(`session:${sessionId}`);
    multi.sRem(`user:${userId}:sessions`, sessionId);
    multi.hIncrBy(`stats:sessions`, 'total_cleared', 1);

    await multi.exec();
    // Session removed from both its own key AND user's session set — atomically
}

// ── Pattern 5: Sorted set + hash update (leaderboard + metadata) ─────────────
async function recordLoanScore(borrowerId: string, score: number, loanId: string): Promise<void> {
    const multi = client.multi();

    // Update leaderboard score:
    multi.zAdd('credit:leaderboard', { score, value: borrowerId });
    // Update borrower's latest score metadata:
    multi.hSet(`borrower:${borrowerId}:meta`, {
        latest_score: score.toString(),
        last_evaluated: Date.now().toString(),
        last_loan_id: loanId
    });
    // Trim leaderboard to top 1000:
    multi.zRemRangeByRank('credit:leaderboard', 0, -1001);

    await multi.exec();
    // Leaderboard and metadata always consistent — no partial update
}
```

**Q9. When should you use WATCH vs Lua scripts vs Redis Streams for different concurrency patterns?**
A: WATCH, Lua scripts, and Redis Streams each solve different concurrency problems. Choosing the wrong tool leads to either correctness bugs (not using WATCH when needed) or performance problems (using WATCH when Lua would be simpler):

```javascript
// Decision matrix:
//
//                          │ WATCH/MULTI/EXEC       │ Lua Script             │ Streams / List
// ─────────────────────────┼────────────────────────┼────────────────────────┼─────────────────
// Read-then-write          │ YES (core use case)     │ YES (simpler)          │ NO
// Conditional write        │ YES                     │ YES (simpler)          │ NO
// Multiple key atomicity   │ YES                     │ YES                    │ NO
// High contention          │ NO (retry overhead)     │ YES (one shot)         │ YES (queue)
// Complex server-side logic│ AWKWARD (client-side)   │ YES (Lua is expressive)│ NO
// Blocking (BLPOP etc.)    │ NO (can't queue these)  │ NO                     │ YES
// Fan-out / pub-sub        │ PARTIAL (MULTI only)    │ NO (can publish)       │ YES
// At-least-once processing │ NO                      │ NO                     │ YES (ACK model)

// ── Use WATCH when: ─────────────────────────────────────────────────────────
// - Low contention (retries are rare)
// - Client-side logic is complex (hard to express in Lua)
// - You need to read multiple keys and write based on combinations

// Transfer with complex business logic (client-side):
async function complexTransfer(fromId: string, toId: string, amount: number): Promise<string> {
    return client.executeIsolated(async (c) => {
        for (let i = 0; i < 5; i++) {
            await c.watch([`account:${fromId}`, `account:${toId}`, `limits:${fromId}`]);

            const [fromBal, toBal, dailyLimit, dailyUsed] = await Promise.all([
                c.get(`account:${fromId}`),
                c.get(`account:${toId}`),
                c.get(`limits:${fromId}:daily`),
                c.get(`limits:${fromId}:used_today`)
            ]);

            const from  = parseFloat(fromBal ?? '0');
            const to    = parseFloat(toBal ?? '0');
            const limit = parseFloat(dailyLimit ?? '100000');
            const used  = parseFloat(dailyUsed ?? '0');

            // Complex client-side checks (hard to express in Lua):
            if (from < amount) throw new Error('Insufficient balance');
            if (used + amount > limit) throw new Error('Daily limit exceeded');
            if (amount > from * 0.9) throw new Error('Cannot transfer >90% of balance');

            const transactionId = `TXN-${Date.now()}-${Math.random().toString(36).slice(2)}`;
            const multi = c.multi();
            multi.set(`account:${fromId}`, (from - amount).toFixed(2));
            multi.set(`account:${toId}`,   (to + amount).toFixed(2));
            multi.incrByFloat(`limits:${fromId}:used_today`, amount);
            multi.set(`txn:${transactionId}`, JSON.stringify({ fromId, toId, amount, at: Date.now() }));

            const results = await multi.exec();
            if (results !== null) return transactionId;
        }
        throw new Error('Transfer failed: too many concurrent modifications');
    });
}

// ── Use Lua when: ───────────────────────────────────────────────────────────
// - Logic is simple enough to express in Lua
// - High contention (no retry needed — Lua executes atomically, once)
// - Performance matters (one round trip vs multiple for WATCH retry loop)

// Rate limiting (high contention — many clients updating same counter):
const RATE_LIMIT_LUA = `
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- Sliding window using sorted set:
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)

if count >= limit then
    return {0, limit - count}  -- blocked, remaining = 0
end

redis.call('ZADD', key, now, now .. math.random())
redis.call('EXPIRE', key, window / 1000 + 1)
return {1, limit - count - 1}  -- allowed, remaining count
`;

async function checkRateLimit(userId: string, limit: number, windowMs: number): Promise<boolean> {
    const result = await client.eval(RATE_LIMIT_LUA, {
        keys: [`rate:${userId}`],
        arguments: [limit.toString(), windowMs.toString(), Date.now().toString()]
    }) as [number, number];
    return result[0] === 1;  // 1 = allowed, 0 = blocked
}
// Lua: executes atomically, no contention, no WATCH needed, one round trip

// ── Use Streams when: ────────────────────────────────────────────────────────
// - Work queue with at-least-once processing guarantee
// - Multiple consumers competing for items
// - Need acknowledgement / dead-letter handling

// Job queue with acknowledgement:
async function enqueueJob(jobData: object): Promise<string> {
    // XADD: add to stream (returns stream entry ID)
    return client.xAdd('jobs:queue', '*', {
        data: JSON.stringify(jobData),
        enqueued_at: Date.now().toString()
    });
}

async function processJobs(consumerId: string): Promise<void> {
    while (true) {
        // XREADGROUP: claim jobs from consumer group
        const entries = await client.xReadGroup(
            'workers',        // consumer group
            consumerId,       // this worker's ID
            [{ key: 'jobs:queue', id: '>' }],  // '>' = new messages only
            { COUNT: 1, BLOCK: 2000 }          // block 2s if no messages
        );

        if (!entries || entries.length === 0) continue;

        for (const { id, message } of entries[0].messages) {
            try {
                await processJob(JSON.parse(message.data));
                // Acknowledge: remove from pending list
                await client.xAck('jobs:queue', 'workers', id);
            } catch (err) {
                // Leave in pending — will be reclaimed after timeout
                console.error(`Job ${id} failed:`, err);
            }
        }
    }
}
```

## Section 5: WATCH Contention and Performance

**Q10. How does contention affect WATCH performance and what are the limits of the optimistic locking approach?**

```javascript
// Contention analysis for WATCH:

// Low contention scenario (99% success rate):
// - 10 clients updating DIFFERENT keys
// - Retry rate ≈ 0 (keys don't conflict)
// - WATCH overhead: minimal (one extra command per transaction)
// - WATCH is the right tool

// Medium contention scenario (50% success rate):
// - 10 clients competing for ONE shared counter
// - Each client retries on average twice before success
// - Total round trips: 2× what you'd need with Lua
// - Acceptable for non-hot-path operations

// High contention scenario (10% success rate):
// - 1000 clients competing for the same key (flash sale, rate limit)
// - Expected retries per client: 10 attempts × 1000 clients = 10,000 total WATCH/MULTI/EXEC sets
// - Many clients never complete (livelock risk)
// - WATCH is the WRONG tool here

// Livelock with WATCH under extreme contention:
// Client A watches key → B modifies → A retries
// Client B watches key → A modifies → B retries
// Client A watches key → B modifies → A retries
// ... infinite cycle
// Real-world: exponential backoff with jitter breaks livelock in practice
//             but throughput is severely degraded

// Measuring contention:
// Add instrumentation to your retry loop:
async function watchedOperation(key: string): Promise<boolean> {
    let retries = 0;
    let result: unknown[] | null = null;

    while (result === null) {
        retries++;
        await client.watch(key);
        const val = await client.get(key);

        const multi = client.multi();
        multi.incr(key);
        result = await multi.exec();

        if (retries > 3) {
            // Log high contention for monitoring:
            console.warn(`WATCH contention on ${key}: attempt ${retries}`);
        }
    }

    metrics.histogram('redis.watch.retries', retries, { key });
    return true;
}

// Performance comparison (1000 concurrent clients, same key):
//
//             │ WATCH + retry │ Lua script │ INCR (atomic) │ Queue (Streams)
// ────────────┼───────────────┼────────────┼───────────────┼────────────────
// Throughput  │ ~10K ops/s    │ ~100K ops/s│ ~1M ops/s     │ ~50K msgs/s
// Correctness │ ✓             │ ✓          │ ✓ (for incr)  │ ✓
// Complexity  │ Medium        │ Low-medium  │ Low           │ High
// Retries     │ Many (10+)    │ None       │ None          │ None
//
// For a hot counter: use INCR (not WATCH)
// For conditional increment: use Lua (not WATCH)
// For complex cross-key logic with low contention: use WATCH

// Reducing contention with sharding:
// Instead of one key for a counter: shard it across N keys
// Total counter = SUM of N shards
// Each client picks a random shard → reduces contention by N×:

const COUNTER_SHARDS = 16;

async function shardedIncrement(counterName: string): Promise<void> {
    const shard = Math.floor(Math.random() * COUNTER_SHARDS);
    await client.incr(`counter:${counterName}:shard:${shard}`);
}

async function shardedTotal(counterName: string): Promise<number> {
    const keys = Array.from({ length: COUNTER_SHARDS },
        (_, i) => `counter:${counterName}:shard:${i}`
    );
    const values = await client.mGet(keys);
    return values.reduce((sum, v) => sum + parseInt(v ?? '0', 10), 0);
}
// INCR on separate shards: zero contention per shard (INCR is inherently atomic)
// Sum: slightly stale (reads N keys non-atomically) but accurate enough for counters
```

## Section 6: Scenario-Based Questions

**Q11. "You're building a seat reservation system using Redis. Users claim seats from a limited pool. Two users must not get the same seat. Design the solution using the correct Redis primitives."**

```javascript
// Requirements:
// - N seats available (e.g. 100 for a webinar)
// - Each seat can only be assigned to one user
// - Concurrent requests must not double-assign
// - Show the seat number to the user immediately

// ── Approach 1: SPOP (simplest, most correct) ──────────────────────────────
// Use a Redis SET containing all available seat numbers
// SPOP atomically removes and returns a random element — inherently race-safe

async function initializeSeats(eventId: string, totalSeats: number): Promise<void> {
    const seats = Array.from({ length: totalSeats }, (_, i) => (i + 1).toString());
    await client.sAdd(`seats:available:${eventId}`, seats);
}

async function claimSeat(eventId: string, userId: string): Promise<number | null> {
    // SPOP: atomically removes a random member and returns it
    // No WATCH needed — SPOP is inherently atomic (no read-then-write)
    const seat = await client.sPop(`seats:available:${eventId}`);

    if (seat === null) {
        return null;  // no seats available
    }

    // Record the assignment:
    await client.set(`seat:${eventId}:${seat}`, userId);
    await client.sAdd(`seats:claimed:${userId}:${eventId}`, seat);

    return parseInt(seat, 10);
}

// SPOP: one round trip, zero contention, atomic
// Redis ensures only one client gets each seat number

// ── Approach 2: WATCH for specific seat selection ────────────────────────────
// If users must pick a specific seat (not random):

async function claimSpecificSeat(
    eventId: string,
    userId: string,
    seatNumber: number
): Promise<boolean> {
    const seatKey = `seat:${eventId}:${seatNumber}`;

    return client.executeIsolated(async (c) => {
        for (let attempt = 0; attempt < 5; attempt++) {
            await c.watch(seatKey);

            const currentOwner = await c.get(seatKey);
            if (currentOwner !== null) {
                await c.unwatch();
                return false;  // seat already taken
            }

            const multi = c.multi();
            multi.set(seatKey, userId);   // claim the seat
            multi.sRem(`seats:available:${eventId}`, seatNumber.toString());

            const results = await multi.exec();
            if (results !== null) return true;  // claimed successfully
            // null: another client grabbed the seat → retry will see it's taken
        }
        return false;  // too many concurrent attempts for this seat
    });
}

// ── Approach 3: Lua script (best for high-contention seat claiming) ───────────
const CLAIM_SEAT_LUA = `
local seatKey    = KEYS[1]     -- seat:eventId:seatNumber
local availKey   = KEYS[2]     -- seats:available:eventId
local seat       = ARGV[1]     -- seat number (string)
local userId     = ARGV[2]     -- user ID

-- Check if seat is available:
local owner = redis.call('GET', seatKey)
if owner ~= false then
    return redis.error_reply('ERR seat already claimed by ' .. owner)
end

-- Check if seat is in the available set:
local inSet = redis.call('SISMEMBER', availKey, seat)
if inSet == 0 then
    return redis.error_reply('ERR seat not available')
end

-- Claim the seat:
redis.call('SET', seatKey, userId)
redis.call('SREM', availKey, seat)

return 'OK'
`;

const claimSeatSha = await client.scriptLoad(CLAIM_SEAT_LUA);

async function claimSeatLua(eventId: string, userId: string, seatNumber: number): Promise<boolean> {
    try {
        await client.evalSha(claimSeatSha, {
            keys: [
                `seat:${eventId}:${seatNumber}`,
                `seats:available:${eventId}`
            ],
            arguments: [seatNumber.toString(), userId]
        });
        return true;
    } catch (err) {
        if (err.message.includes('ERR seat already claimed') ||
            err.message.includes('ERR seat not available')) {
            return false;
        }
        throw err;
    }
}

// ── Comparison for this use case:
// SPOP (random seat):      best — atomic, one round trip, zero contention
// WATCH (specific seat):   acceptable — low contention per seat (each seat chosen rarely)
// Lua (specific seat):     best for specific seat — atomic, one round trip, no retry
```

**Q12. "Your application uses Redis WATCH to implement a transfer between two accounts. Under load testing, you're seeing 30% of transactions fail with 'too many retries'. Diagnose and fix."**

```javascript
// Diagnosis: high contention on account keys
// 30% failure rate → many clients competing for the same accounts
// Likely: a small number of "hot" accounts being updated very frequently

// Step 1: Instrument the current code to confirm:
async function transferWithMetrics(fromId: string, toId: string, amount: number) {
    let attempts = 0;
    return client.executeIsolated(async (c) => {
        while (attempts < 10) {
            attempts++;

            await c.watch([`account:${fromId}:balance`, `account:${toId}:balance`]);
            const [fromBal, toBal] = await Promise.all([
                c.get(`account:${fromId}:balance`),
                c.get(`account:${toId}:balance`)
            ]);

            const from = parseFloat(fromBal ?? '0');
            if (from < amount) throw new Error('Insufficient balance');

            const multi = c.multi();
            multi.set(`account:${fromId}:balance`, (from - amount).toFixed(2));
            multi.set(`account:${toId}:balance`, (parseFloat(toBal ?? '0') + amount).toFixed(2));

            const results = await multi.exec();
            if (results !== null) {
                metrics.histogram('transfer.attempts', attempts);
                return true;
            }
            // Add jitter to reduce thundering herd:
            await sleep(Math.random() * 10 * attempts);
        }
        metrics.increment('transfer.failed');
        throw new Error('Transfer failed: high contention');
    });
}

// Step 2: After instrumentation, confirm:
// - Most failures are on a few "hot" accounts (company escrow, payment gateway accounts)
// - p99 attempts: 8-9 → confirms contention

// Step 3: Fix — replace WATCH with Lua for atomic conditional debit:
const TRANSFER_LUA = `
local fromKey   = KEYS[1]
local toKey     = KEYS[2]
local amount    = tonumber(ARGV[1])
local txnId     = ARGV[2]

local fromBal = tonumber(redis.call('GET', fromKey))
local toBal   = tonumber(redis.call('GET', toKey)) or 0

if fromBal == nil then
    return redis.error_reply('ERR source account not found')
end
if fromBal < amount then
    return redis.error_reply('ERR insufficient balance: ' .. fromBal .. ' < ' .. amount)
end

redis.call('SET', fromKey, tostring(fromBal - amount))
redis.call('SET', toKey,   tostring(toBal + amount))
redis.call('LPUSH', 'txn:log', txnId .. ':' .. fromKey .. ':' .. toKey .. ':' .. amount)

return {fromBal - amount, toBal + amount}
`;

const transferSha = await client.scriptLoad(TRANSFER_LUA);

async function transferLua(fromId: string, toId: string, amount: number): Promise<[number, number]> {
    const txnId = `TXN-${Date.now()}-${Math.random().toString(36).slice(2)}`;
    try {
        const result = await client.evalSha(transferSha, {
            keys: [
                `account:${fromId}:balance`,
                `account:${toId}:balance`
            ],
            arguments: [amount.toString(), txnId]
        });
        return result as [number, number];  // [new from balance, new to balance]
    } catch (err) {
        if (err.message.includes('insufficient balance')) {
            throw new InsufficientFundsError(err.message);
        }
        throw err;
    }
}

// Result after fix:
// - No retries (Lua executes atomically, one shot)
// - Throughput: ~100K transfers/second (vs ~10K with WATCH retries)
// - Zero failures from contention
// - Identical correctness guarantees (Lua is atomic in Redis)

// When to keep WATCH despite contention:
// - Client-side logic is too complex for Lua (external API calls, complex validation)
// - Low contention in production (load test was artificially concentrated)
// - Contention is on DIFFERENT keys per request (hash by user → natural sharding)
```

## Quick Reference Table

| Feature | `MULTI/EXEC` | `WATCH` + `MULTI/EXEC` | Lua Script |
|---|---|---|---|
| Atomicity | Yes (no interleaving) | Yes (aborts if watched key changes) | Yes (single execution) |
| Rollback on error | No | No (abort = no execution) | Optional (return error) |
| Read-then-write safe | No | Yes | Yes |
| Retry required | No | Yes (on nil result) | No |
| Round trips | 2 (MULTI + EXEC) | 3+ (WATCH + GET + MULTI + EXEC) | 1 (EVAL) |
| High contention | Fine | Degrades (many retries) | Best (no retries) |
| Complex logic | Client-side only | Client-side only | Server-side (Lua) |
| Best for | Batched writes | Low-contention CAS | High-contention CAS |

| Error type | When it occurs | Effect on transaction |
|---|---|---|
| Syntax/unknown command (queuing phase) | Command doesn't exist, wrong arg count | Whole transaction discarded on EXEC |
| Runtime error (EXEC phase) | Wrong type, out-of-range | Only that command fails; others execute |
| WATCH abort | Watched key modified before EXEC | EXEC returns null; no commands run |
| Connection drop | Between MULTI and EXEC | Transaction discarded (server cleans up) |

| Pattern | Tool | Why |
|---|---|---|
| Batch write (no read) | `MULTI/EXEC` | Simple, atomic batch |
| Atomic increment | `INCR`/`INCRBY` | Built-in atomicity, no WATCH needed |
| Conditional write (low contention) | `WATCH` + `MULTI/EXEC` | CAS with retry |
| Conditional write (high contention) | Lua script | No retry, one round trip |
| Random item from pool | `SPOP` | Inherently atomic pop |
| Rate limiting | Lua (sliding window) | Atomic check + increment in one step |
| Work queue | Redis Streams | At-least-once with ACK |
| Balance transfer | Lua | Atomic check + debit + credit |

**Tip for interviews:** Five things separate strong candidates on Redis transactions: (1) being precise that **MULTI/EXEC does not provide rollback** — a runtime error inside the transaction (wrong type, etc.) fails only that command and the others still execute; the only case where the whole transaction is discarded is a syntax error during the queuing phase; candidates who say "Redis transactions are ACID" without this caveat miss the critical difference from SQL; (2) explaining **why WATCH must come BEFORE the read** (Q7 failure mode 1) — WATCH registers a checkpoint at the moment it is called; any read that happens before WATCH is unprotected, and a modification between that read and the WATCH will not be detected; the correct sequence is always WATCH → GET → application logic → MULTI → commands → EXEC; (3) knowing that **WATCH requires a dedicated connection** in connection pool environments — pooled connections are shared across requests, so another request may issue commands on the same connection between your WATCH and EXEC, which either contaminates your transaction state or triggers a spurious abort; `executeIsolated()` in node-redis solves this by giving a fresh connection; (4) articulating **when to use Lua instead of WATCH** — for high-contention operations (rate limiting, balance transfers with many concurrent requests), WATCH creates a retry storm where each retry generates more load; Lua executes atomically in a single server-side operation with no retry needed; the threshold is roughly: if contention causes >10% retry rate in production, switch to Lua; and (5) knowing **SPOP as the correct primitive for pool/seat/inventory claiming** — `SPOP` atomically removes and returns a random member from a set, which is exactly the semantics you need for "give me an available resource"; this is simpler than WATCH/MULTI/EXEC and correct by construction, and candidates who reach for WATCH first for this pattern are solving a simpler problem than they think.
