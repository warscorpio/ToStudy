# Redis Pub/Sub: Channels, Patterns, and Limitations — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Redis Pub/Sub, how does it work at the protocol level, and what problem does it solve?**
A: Redis Pub/Sub is a message broadcasting mechanism built directly into the Redis server. Publishers send messages to named channels; subscribers receive all messages published to channels they have subscribed to. The delivery is immediate and fire-and-forget — Redis holds no state about messages, requiring no storage or queuing infrastructure beyond the in-memory routing table of active subscriptions:

```
Pub/Sub model — message routing in Redis:

  Publisher                Redis Server               Subscribers
     │                         │                          │
     │  PUBLISH news "Brexit"  │                          │
     ├────────────────────────►│                          │
     │                         │  Routing table lookup:   │
     │                         │  channel "news" →        │
     │                         │  [client-A, client-B]    │
     │                         │                          │
     │                         │─── "news", "Brexit" ────►│ client-A
     │                         │─── "news", "Brexit" ────►│ client-B
     │                         │                          │
     │  (3) returned to pub    │  No storage              │
     │  ← integer: 2 listeners │  No queue                │
     │                         │  No persistence          │

  What Redis does:
    1. Receives PUBLISH command
    2. Looks up the channel name in an internal hash table
    3. For each subscribed client: writes the message to their output buffer
    4. Returns the number of subscribers who received the message to the publisher
    5. Discards the message — no storage of any kind

  What Redis does NOT do:
    ✗ Buffer messages for offline subscribers
    ✗ Track which subscribers received which messages
    ✗ Retry failed deliveries
    ✗ Persist any messages to disk
    ✗ Guarantee delivery to any subscriber
```

```
The problem Pub/Sub solves — fan-out without N individual writes:

  WITHOUT Pub/Sub:
    Notification system for 10,000 connected users:
    for each user in connected_users:
        write_to_user_socket(user.socket, notification)
    ← Application must track all connections and write to each individually
    ← Single application process handles all 10K writes
    ← Doesn't scale across multiple application servers

  WITH Pub/Sub:
    app_server_1, app_server_2, app_server_3 each SUBSCRIBE to "notifications"
    When event occurs: PUBLISH notifications "{ type: 'alert', msg: '...' }"
    ← Redis fans out to ALL subscribed app servers in one operation
    ← Each app server broadcasts to its connected WebSocket clients
    ← Scales: add more app servers, all automatically receive the message
    ← Redis handles the fan-out routing centrally
```

```bash
# Redis Pub/Sub protocol — raw commands:

# Subscriber (in one terminal):
SUBSCRIBE news sports weather
# Redis responds with confirmation for each subscription:
# 1) "subscribe"
# 2) "news"
# 3) (integer) 1     ← now subscribed to 1 channel
# 1) "subscribe"
# 2) "sports"
# 3) (integer) 2     ← now subscribed to 2 channels
# 1) "subscribe"
# 2) "weather"
# 3) (integer) 3

# Publisher (in another terminal):
PUBLISH news "Breaking: major earthquake in Pacific"
# Redis returns: (integer) 2  ← number of subscribers who received this

PUBLISH sports "World Cup final: 2-1"
# Redis returns: (integer) 1

PUBLISH cricket "Test match update"
# Redis returns: (integer) 0  ← nobody subscribed to "cricket" — message lost
```

```bash
# The subscriber client receives messages in this format:
# 1) "message"     ← message type
# 2) "news"        ← channel name
# 3) "Breaking: major earthquake in Pacific"  ← message body

# Subscriber state — a subscribed client CANNOT run other commands:
SUBSCRIBE news
# Client is now in "subscribe mode" — connection exclusively for Pub/Sub
# Only allowed commands in subscribe mode:
# SUBSCRIBE, UNSUBSCRIBE, PSUBSCRIBE, PUNSUBSCRIBE, PING, RESET, QUIT
# All other commands return error: "ERR Command not allowed inside a subscription context"
# This means: need SEPARATE connections for publishing and subscribing
```

**Q2. What are the subscription state implications — why do subscribed connections become exclusively dedicated?**
A: When a Redis client issues `SUBSCRIBE`, the connection transitions into a special subscription state. The TCP connection is held open in a listening mode where the client receives pushed messages from the server. This fundamental design choice means the connection cannot be reused for regular Redis operations:

```
Connection state machine:

  Normal connection:           Subscribed connection:
  ┌─────────────────┐          ┌──────────────────────────────┐
  │ GET key         │          │ SUBSCRIBE channel            │
  │ SET key value   │          │ ← enters subscription mode   │
  │ HSET hash f v   │          │                              │
  │ ZADD zset s m   │          │ Only allowed:                │
  │ PUBLISH ch msg  │          │   SUBSCRIBE ch [ch ...]      │
  │ ... any command │          │   UNSUBSCRIBE [ch ...]       │
  └─────────────────┘          │   PSUBSCRIBE pat [pat ...]   │
                                │   PUNSUBSCRIBE [pat ...]     │
                                │   PING [message]             │
                                │   RESET                      │
                                │   QUIT                       │
                                │                              │
                                │ Cannot use: GET, SET, LPUSH, │
                                │   ZADD, HSET, EXEC, ...      │
                                └──────────────────────────────┘

  Implication for connection pools:
    Standard pattern: one connection for pub/sub listening
                      separate connection for all other Redis operations
    A connection pool of 10 connections for general use
    + 1 dedicated long-lived connection for subscribing
    Never put the subscribe connection back in the pool
```

```javascript
// Correct connection separation in Node.js (ioredis):
const Redis = require('ioredis');

// Connection 1: General purpose (GET, SET, ZADD, etc.):
const redis = new Redis({ host: 'localhost', port: 6379 });

// Connection 2: Pub/Sub subscriber (exclusively for subscriptions):
const subscriber = new Redis({ host: 'localhost', port: 6379 });
// This connection will be in subscribe mode — cannot run normal commands

// Connection 3: Publisher (can be the general connection, or a dedicated one):
// Publishing uses normal commands — the general 'redis' connection can publish
// Or use a dedicated publisher connection for clarity

// Subscribe:
await subscriber.subscribe('notifications', 'orders');
subscriber.on('message', (channel, message) => {
    // This fires every time a message arrives on subscribed channels
    console.log(`Channel: ${channel}, Message: ${message}`);
});

// Publish (using general connection — NOT the subscriber connection):
await redis.publish('notifications', JSON.stringify({
    type: 'alert',
    userId: 'u-42',
    message: 'Your order has shipped'
}));

// Wrong — trying to GET from subscriber connection:
// await subscriber.get('some-key');  // ERROR: not allowed in subscribe mode
```

## Section 2: Channels

**Q3. How do channels work in Redis Pub/Sub — what is the data structure and what are the naming conventions?**
A: A channel in Redis Pub/Sub is simply a string — Redis maintains an internal hash table mapping channel names to lists of subscribed client connections. Channels are created implicitly when a client subscribes and disappear when the last subscriber unsubscribes. There is no configuration, creation, or management required for channels:

```
Channel internals — Redis data structure:

  Redis maintains (in memory):
  pubsub_channels: {
    "news":          [client-A, client-B, client-C],
    "orders":        [client-D],
    "notifications": [client-A, client-D, client-E, client-F],
    "chat:room:42":  [client-G, client-H]
  }

  Memory cost:
    Each subscription: ~100-200 bytes (pointer in the list per channel per client)
    10,000 subscribers × 5 channels each = 50,000 subscriptions
    Memory: ~50,000 × 150 bytes = ~7.5MB
    Redis Pub/Sub is memory-efficient for the routing table

  Channel lifecycle:
    SUBSCRIBE "news" by first client:  {"news": [client-A]} created
    SUBSCRIBE "news" by second client: {"news": [client-A, client-B]}
    UNSUBSCRIBE "news" by client-A:    {"news": [client-B]}
    UNSUBSCRIBE "news" by client-B:    "news" key removed (channel ceases to exist)
```

```javascript
// Channel naming conventions — no enforcement, but strong conventions:

// Hierarchical naming with colons (most common — follows Redis key convention):
// "chat:room:42"         — chat messages in room 42
// "user:notifications:u-42"  — notifications for user u-42
// "orders:status:SHIPPED"    — order status change events
// "inventory:product:p-123"  — inventory updates for product p-123

// Flat naming for simple cases:
// "news"
// "sports"
// "global-alerts"

// Event-type naming:
// "event.order.created"
// "event.payment.processed"
// "event.user.registered"

// Service-prefixed naming (microservices):
// "order-service.events"
// "payment-service.events"
// "inventory-service.low-stock"

// Subscribing to multiple channels at once:
await subscriber.subscribe(
    'notifications:u-42',    // User-specific
    'notifications:global',  // Broadcast to all
    'chat:room:42'           // Room-specific
);

// Subscribing returns the total subscription count:
subscriber.on('message', (channel, message) => {
    const parsed = JSON.parse(message);

    // Route based on channel:
    switch (channel) {
        case 'notifications:u-42':
            handlePersonalNotification(parsed);
            break;
        case 'notifications:global':
            handleGlobalBroadcast(parsed);
            break;
        case 'chat:room:42':
            handleChatMessage(parsed);
            break;
    }
});

// Introspection — who is subscribed to what:
// PUBSUB CHANNELS — list all active channels:
await redis.pubsub('CHANNELS');                    // All channels
await redis.pubsub('CHANNELS', 'chat:*');          // Channels matching pattern
// Returns: ["chat:room:1", "chat:room:42", "chat:room:99"]

// PUBSUB NUMSUB — subscriber count per channel:
await redis.pubsub('NUMSUB', 'news', 'sports', 'weather');
// Returns: ["news", 3, "sports", 1, "weather", 0]

// PUBSUB NUMPAT — count of active pattern subscriptions:
await redis.pubsub('NUMPAT');
// Returns: 4 (4 PSUBSCRIBE patterns active)
```

```javascript
// Publishing with channel targeting:

// Targeted (specific user):
await redis.publish(`user:${userId}:notifications`,
    JSON.stringify({ type: 'order_shipped', orderId })
);

// Broadcast (all users):
await redis.publish('broadcast:all',
    JSON.stringify({ type: 'maintenance_window', start: '2024-03-15T02:00:00Z' })
);

// Room-scoped (chat):
await redis.publish(`chat:${roomId}`,
    JSON.stringify({ author: username, text: message, ts: Date.now() })
);

// Return value of PUBLISH:
const recipientCount = await redis.publish('news', 'Breaking news!');
// recipientCount: integer — how many clients received this message
// 0 = nobody listening (message lost — no subscribers at this moment)
// This is a critical limitation: the publisher has no way to ensure delivery
```

## Section 3: Pattern Subscriptions

**Q4. What are pattern subscriptions (`PSUBSCRIBE`) and how do glob patterns work in Redis?**
A: Pattern subscriptions allow a client to subscribe to all channels whose names match a glob-style pattern, rather than subscribing to individual channels by exact name. This enables dynamic channel subscription without knowing channel names in advance:

```bash
# Pattern subscription syntax:
PSUBSCRIBE pattern [pattern ...]

# Glob patterns supported:
# *   matches any sequence of characters (including empty)
# ?   matches exactly one character
# [abc] matches any character in the set (a, b, or c)
# [a-z] matches any character in the range

# Examples:
PSUBSCRIBE "news.*"
# Matches: "news.breaking", "news.sports", "news.weather"
# Doesn't match: "news", "sport.news", "old-news"

PSUBSCRIBE "chat:room:*"
# Matches: "chat:room:1", "chat:room:42", "chat:room:abc"
# Doesn't match: "chat:room:", "chat:user:5"

PSUBSCRIBE "user:*:notifications"
# Matches: "user:u-42:notifications", "user:admin:notifications"
# Doesn't match: "user:notifications", "user:u-42:alerts"

PSUBSCRIBE "orders:*"
# Matches: "orders:created", "orders:shipped", "orders:COMPLETED"
PSUBSCRIBE "h?llo"
# Matches: "hello", "hallo", "hxllo"
# Doesn't match: "hllo", "heello"

PSUBSCRIBE "h[ae]llo"
# Matches: "hello", "hallo"
# Doesn't match: "hillo"
```

```javascript
// Pattern subscription in Node.js (ioredis):
const subscriber = new Redis();

// Subscribe to a pattern:
await subscriber.psubscribe('chat:room:*');
await subscriber.psubscribe('user:*:notifications');
await subscriber.psubscribe('orders:*');

// Pattern messages come through 'pmessage' event (NOT 'message'):
subscriber.on('pmessage', (pattern, channel, message) => {
    // pattern: the glob pattern that matched
    // channel: the ACTUAL channel the message was published to
    // message: the message content
    console.log(`Pattern: ${pattern}`);
    console.log(`Actual channel: ${channel}`);
    console.log(`Message: ${message}`);
});

// Example: publisher sends to "chat:room:42"
// subscriber's pmessage fires with:
// pattern:  "chat:room:*"
// channel:  "chat:room:42"   ← actual channel used
// message:  "Hello everyone!"

// Key difference: pmessage vs message events:
// SUBSCRIBE → fires 'message' event
// PSUBSCRIBE → fires 'pmessage' event (with pattern parameter)
// A client can use BOTH:
subscriber.on('message', (channel, message) => {
    // From exact channel subscriptions (SUBSCRIBE)
});
subscriber.on('pmessage', (pattern, channel, message) => {
    // From pattern subscriptions (PSUBSCRIBE)
});
```

```javascript
// Practical pattern subscription use cases:

// 1. Chat rooms — subscribe to all rooms at once:
await subscriber.psubscribe('chat:room:*');
// One subscription handles all chat rooms
// When new room is created: no re-subscription needed

// 2. User-specific channels — gateway subscribes to all users:
// WebSocket gateway: subscribe to all user notification channels:
await subscriber.psubscribe('user:*:notifications');
// Receive notifications for ALL users through one pattern
// Route to appropriate WebSocket connection based on actual channel:
subscriber.on('pmessage', (pattern, channel, message) => {
    // Extract userId from channel name:
    const userId = channel.split(':')[1];  // "user:u-42:notifications" → "u-42"
    const ws = userWebSocketMap.get(userId);
    if (ws?.readyState === WebSocket.OPEN) {
        ws.send(message);
    }
});

// 3. Event type routing — subscribe to a category of events:
await subscriber.psubscribe('event.order.*');
// Receives: event.order.created, event.order.shipped, event.order.cancelled

// 4. Keyspace notifications — subscribe to Redis key events (special pattern):
// Must enable keyspace notifications first:
// redis.config('SET', 'notify-keyspace-events', 'KEA')
// K = keyspace events, E = keyevent events, A = all commands

await subscriber.psubscribe('__keyevent@0__:expired');
// Fires when any key in database 0 expires
// Pattern: "__keyevent@{dbindex}__:{event}"
// Useful for: TTL-based event triggers without polling

subscriber.on('pmessage', (pattern, channel, message) => {
    // message = the key that expired
    console.log(`Key expired: ${message}`);
    // Can trigger cleanup, cache invalidation, or business logic
});
```

```javascript
// Pattern performance considerations:
// Every PUBLISH must check ALL active patterns for a match
// Pattern matching is O(N × M) where:
//   N = number of pattern subscriptions (PSUBSCRIBE count)
//   M = length of the channel name being published to

// PUBSUB NUMPAT: check how many active patterns exist:
const patternCount = await redis.pubsub('NUMPAT');
// If patternCount is in the thousands: PUBLISH operations slow down
// Redis must check every pattern against every publish

// Rule: prefer exact channel SUBSCRIBE over PSUBSCRIBE when channel names are known
// PSUBSCRIBE: for dynamic discovery of channels where names are not known at subscribe time
// SUBSCRIBE:  when you know exactly which channels to watch

// Bad: using patterns when exact names are known:
// subscriber.psubscribe('chat:room:42')  ← use SUBSCRIBE instead
// subscriber.psubscribe('news')          ← use SUBSCRIBE instead

// Good: using patterns for genuinely dynamic cases:
// subscriber.psubscribe('user:*:notifications')  ← don't know all user IDs
// subscriber.psubscribe('__keyevent@0__:expired') ← all expirations
```

## Section 4: Core Limitations

**Q5. What is the "no persistence" limitation — what exactly is lost and in what failure scenarios?**
A: Redis Pub/Sub has no persistence whatsoever. Messages are routed to currently-connected subscribers and immediately discarded. This is not a configuration option — it is fundamental to the design. Understanding exactly what this means and when it matters is critical for choosing Pub/Sub vs alternatives:

```
Persistence gap — what exactly gets lost:

  Scenario 1: Subscriber is down during publish
    T=0: subscriber-A subscribed to "orders"
    T=1: subscriber-A crashes (or disconnects)
    T=2: PUBLISH orders "order-123 shipped"
         Redis routing table: no subscribers for "orders"
         PUBLISH returns 0 (zero recipients)
         Message: permanently lost
    T=3: subscriber-A restarts and reconnects
         Subscribes to "orders" again
         Does NOT receive the message from T=2
         No way to know message was missed

  Scenario 2: Subscriber connected but slow (slow consumer)
    T=0: subscriber-B subscribed to "orders"
    T=1: 1,000 messages published in 1 second
         subscriber-B can only process 100/sec
    T=2: Redis output buffer for subscriber-B fills up
    T=3: Redis disconnects subscriber-B (client-output-buffer-limit exceeded)
         subscriber-B misses all messages during disconnect + reconnect
         "fast subscriber required" — there is no backpressure or buffering

  Scenario 3: Redis itself fails
    T=0: publisher sends 100 messages
    T=1: Redis crashes
    T=2: Redis restarts (even with AOF/RDB enabled)
         Pub/Sub messages are NOT written to the persistence files
         (AOF records commands — PUBLISH is recorded, but on restart:
          no subscribers to deliver to, so all messages are effectively lost)

  Scenario 4: Network partition between publisher and Redis
    T=0: publisher sends message
    T=1: network packet lost before reaching Redis
         message never delivered to any subscriber
         publisher received no error (TCP connection may still look alive)
```

```javascript
// Observing message loss — the "publish returns 0" pattern:
const recipientCount = await redis.publish('orders', 'order shipped');
// recipientCount === 0 → nobody received this message
// No error, no exception, no retry — message is simply gone

// This is especially dangerous in gap scenarios:
// Between subscriber disconnect and reconnect:
//   Gap duration: 50ms (auto-reconnect)
//   Messages published during 50ms gap: all lost
//   No notification to the publisher or consumer that messages were missed
//   Consumer resumes as if no gap occurred

// Detecting if you missed messages (NOT built into Redis):
// Must be implemented in application code:
// Option 1: sequence numbers in messages
await redis.publish('orders', JSON.stringify({
    seq: sequenceNumber++,    // Publisher maintains incrementing sequence
    event: 'shipped',
    orderId: 'order-123'
}));

// Consumer detects gaps:
let lastSeq = 0;
subscriber.on('message', (channel, message) => {
    const { seq, event, orderId } = JSON.parse(message);
    if (seq !== lastSeq + 1) {
        console.warn(`SEQUENCE GAP: expected ${lastSeq + 1}, got ${seq}`);
        // Recovery: fetch missed data from primary storage (database)
    }
    lastSeq = seq;
    processEvent(event, orderId);
});
```

**Q6. What are the other core limitations of Redis Pub/Sub beyond persistence — no consumer groups, no message history, and no delivery guarantees?**
A: Beyond persistence, Pub/Sub has several interconnected limitations that collectively constrain it to use cases where message loss is acceptable. Understanding all of them together determines whether Pub/Sub is the right tool:

```
Complete limitations inventory:

  1. NO PERSISTENCE (covered in Q5)
     Messages not stored — unavailable after delivery

  2. NO MESSAGE HISTORY
     Cannot replay past messages
     New subscriber: receives only messages published AFTER subscription
     Cannot ask "what messages did I miss?"

  3. NO CONSUMER GROUPS / COMPETING CONSUMERS
     Every subscriber receives EVERY message (broadcast semantics)
     Cannot partition work: "only one of my 5 workers should process this"
     Cannot have N workers sharing a queue (each gets all messages)
     All Redis Pub/Sub is broadcast — no unicast or load-balancing

  4. NO ACKNOWLEDGEMENT / DELIVERY GUARANTEE
     Publisher gets a count: how many received it right now
     No ACK from subscriber confirming processing
     "Fire and forget" — no way to know if processing succeeded
     Cannot retry on consumer failure

  5. NO BACKPRESSURE
     Slow consumer → buffer fills → Redis disconnects the subscriber
     No flow control: publisher rate not throttled by consumer capacity
     Fast publisher + slow consumer = guaranteed message loss

  6. NO FILTERING AT CONSUMER LEVEL
     All messages on a channel delivered to all subscribers
     Cannot say "client-A wants only order events where amount > $100"
     Must filter in application code (still receives all messages)

  7. NO ORDERING GUARANTEE ACROSS CHANNELS
     Within ONE channel: messages received in publish order (FIFO)
     ACROSS channels: no ordering guarantee
     If you PUBLISH to channel-A then channel-B: subscriber may see B before A

  8. AT-MOST-ONCE DELIVERY (not at-least-once or exactly-once)
     Message either delivered once or not delivered at all
     No retry, no duplicate, no backlog
```

```javascript
// The consumer group limitation in practice:
// Scenario: 5 worker processes, each subscribed to "jobs" channel
// When job is published: ALL 5 workers receive it
// All 5 try to process the same job → duplicates, race conditions, wasted work

// This is why Redis Streams (XADD/XREAD) exist — they have consumer groups:
// Only one worker in a consumer group processes each message

// Workaround for competing consumers with Pub/Sub:
// Use Pub/Sub for NOTIFICATION, then race on a Redis lock or list:
subscriber.on('message', async (channel, message) => {
    const { jobId } = JSON.parse(message);

    // Try to acquire a lock on this job:
    const acquired = await redis.set(
        `job:lock:${jobId}`,
        workerId,
        'NX',       // Only set if not exists
        'EX', 30    // 30 second TTL
    );

    if (!acquired) return;  // Another worker got it first
    // Only one worker will proceed:
    await processJob(jobId);
    await redis.del(`job:lock:${jobId}`);
});
// This workaround: still sends message to all workers, uses extra Redis round-trips
// Better: use Redis Streams from the start if competing consumers are needed
```

```javascript
// The slow consumer disconnection:
// Redis config: client-output-buffer-limit
// Default for pubsub clients:
// client-output-buffer-limit pubsub 32mb 8mb 60
// ← 32MB hard limit: disconnect immediately if output buffer exceeds 32MB
// ← 8MB soft limit: if buffer exceeds 8MB for 60 continuous seconds → disconnect

// When subscriber is disconnected due to buffer overflow:
// subscriber receives a disconnect event — no indication of how many messages were lost
subscriber.on('close', () => {
    console.warn('Disconnected — may have missed messages');
    // Cannot determine how many messages were missed
});

// Mitigation: keep subscribers fast (don't do slow async work in the message handler):
// BAD — slow processing blocks the message handler:
subscriber.on('message', async (channel, message) => {
    await db.query('INSERT INTO events ...');  // Slow DB write in message handler
    await externalApiCall(message);            // Slow HTTP request
    // If these are slow: buffer fills, disconnection, message loss
});

// GOOD — hand off to a queue immediately:
const eventQueue = new AsyncQueue();
subscriber.on('message', (channel, message) => {
    eventQueue.push({ channel, message });  // Non-blocking, returns immediately
});
// Background worker drains the queue asynchronously:
eventQueue.process(async ({ channel, message }) => {
    await db.query('INSERT INTO events ...');  // Slow work done here
});
```

## Section 5: Redis Pub/Sub vs Redis Streams

**Q7. When should you choose Redis Pub/Sub over Redis Streams, and what does Streams provide that Pub/Sub cannot?**
A: Redis Streams (added in Redis 5.0) is the evolved message queue with persistence, consumer groups, and message history. Pub/Sub and Streams solve different problems — the choice depends on whether you need "broadcast now" or "reliable delivery with history":

```
Decision framework:

  Redis Pub/Sub — choose when:
  ✓ Real-time broadcast (all connected listeners must receive NOW)
  ✓ Message loss is acceptable (e.g., live metrics, presence updates)
  ✓ No need for consumer groups (all subscribers should see all messages)
  ✓ Simplest possible infrastructure
  ✓ Chat systems where offline users miss messages (expected behaviour)
  ✓ Cache invalidation signals (ok to miss — next read just fetches fresh data)
  ✓ Live dashboard updates (stale dashboard is acceptable briefly)
  ✓ WebSocket broadcast through multiple app servers

  Redis Streams — choose when:
  ✓ Messages must not be lost (orders, payments, user actions)
  ✓ Consumer groups needed (competing consumers, load balancing)
  ✓ Replay required (new consumer starts from beginning of history)
  ✓ Processing acknowledgement required (mark message as processed)
  ✓ Backpressure required (consumer pace controls delivery)
  ✓ Multiple independent consumer groups on the same data
  ✓ Ordered event log (audit trail, event sourcing)
```

```javascript
// Redis Streams — what Pub/Sub cannot do:

// XADD: persistent append to a stream:
await redis.xadd('orders:events', '*',    // '*' = auto-generate ID
    'event', 'order.created',
    'orderId', 'ord-123',
    'amount', '99.99',
    'userId', 'u-42'
);
// Message stored in Redis (optionally with MAXLEN to cap the stream)
// Survives: consumer disconnect, Redis restart (if RDB/AOF enabled)

// XGROUP: consumer groups — competing consumers:
await redis.xgroup('CREATE', 'orders:events', 'fulfillment-workers', '$', 'MKSTREAM');
// fulfillment-workers group: only one worker processes each message

// XREADGROUP: claim a message for processing:
const messages = await redis.xreadgroup(
    'GROUP', 'fulfillment-workers', 'worker-1',
    'COUNT', 10,
    'BLOCK', 2000,
    'STREAMS', 'orders:events', '>'
);
// Only worker-1 gets these messages (not worker-2, worker-3...)
// Other workers get different messages from the stream

// XACK: acknowledge successful processing:
await redis.xack('orders:events', 'fulfillment-workers', messageId);
// Message is marked as processed — removed from Pending Entries List (PEL)
// If worker-1 crashes before XACK: message stays in PEL
// Another worker can claim it via XPENDING + XCLAIM (redelivery)

// XREAD: replay from the beginning (new consumer group):
await redis.xread('COUNT', 100, 'STREAMS', 'orders:events', '0');
// '0' = start from the very first message in the stream
// New consumer group can process historical messages — impossible with Pub/Sub
```

```
Comparison table:
```

## Section 6: NestJS Integration

**Q8. How do you implement Redis Pub/Sub in a NestJS application for WebSocket broadcasting across multiple server instances?**
A: In NestJS, the most common Pub/Sub use case is scaling WebSocket gateways across multiple server instances. When a user connected to `server-1` should receive a message triggered by an action on `server-2`, the servers use Redis Pub/Sub to broadcast between themselves:

```typescript
// redis-pubsub.service.ts
import { Injectable, OnModuleInit, OnModuleDestroy, Logger } from '@nestjs/common';
import { InjectRedis } from '@nestjs-modules/ioredis';
import Redis from 'ioredis';
import { EventEmitter2 } from '@nestjs/event-emitter';

@Injectable()
export class RedisPubSubService implements OnModuleInit, OnModuleDestroy {
    private readonly logger = new Logger(RedisPubSubService.name);
    private subscriber: Redis;     // Dedicated subscriber connection
    private publisher: Redis;      // Publisher (can share with main Redis)

    constructor(
        @InjectRedis() private readonly redis: Redis,
        private readonly eventEmitter: EventEmitter2
    ) {}

    async onModuleInit(): Promise<void> {
        // Create dedicated subscriber connection:
        this.subscriber = this.redis.duplicate();
        this.publisher = this.redis;  // Reuse main connection for publishing

        // Subscribe to channels:
        await this.subscriber.subscribe(
            'notifications:broadcast',
            'chat:messages',
            'system:alerts'
        );

        // Subscribe to pattern for user-specific channels:
        await this.subscriber.psubscribe('user:*:notifications');

        // Handle exact channel messages:
        this.subscriber.on('message', (channel: string, message: string) => {
            this.handleMessage(channel, message);
        });

        // Handle pattern messages:
        this.subscriber.on('pmessage', (pattern: string, channel: string, message: string) => {
            this.handlePatternMessage(pattern, channel, message);
        });

        this.logger.log('Redis Pub/Sub initialized');
    }

    async onModuleDestroy(): Promise<void> {
        await this.subscriber.unsubscribe();
        await this.subscriber.punsubscribe();
        await this.subscriber.quit();
    }

    private handleMessage(channel: string, rawMessage: string): void {
        try {
            const message = JSON.parse(rawMessage);

            // Emit as internal NestJS event for other services to handle:
            this.eventEmitter.emit(`pubsub.${channel}`, message);
        } catch (err) {
            this.logger.error(`Failed to parse message on ${channel}:`, err.message);
        }
    }

    private handlePatternMessage(
        pattern: string,
        channel: string,
        rawMessage: string
    ): void {
        try {
            const message = JSON.parse(rawMessage);
            // Extract userId from "user:u-42:notifications" → "u-42":
            if (pattern === 'user:*:notifications') {
                const parts = channel.split(':');
                const userId = parts[1];
                this.eventEmitter.emit('pubsub.user.notification', { userId, ...message });
            }
        } catch (err) {
            this.logger.error(`Pattern message parse error:`, err.message);
        }
    }

    async publish(channel: string, message: object): Promise<number> {
        const serialized = JSON.stringify(message);
        const recipientCount = await this.publisher.publish(channel, serialized);

        if (recipientCount === 0) {
            this.logger.warn(`Message published to ${channel} with 0 recipients`);
        }
        return recipientCount;
    }

    async publishToUser(userId: string, message: object): Promise<void> {
        await this.publish(`user:${userId}:notifications`, message);
    }

    async broadcast(message: object): Promise<void> {
        await this.publish('notifications:broadcast', message);
    }
}
```

## Section 7: Patterns and Use Cases

**Q9. What are the canonical Pub/Sub patterns in production systems — where is it the right tool despite its limitations?**
A: Understanding the correct use cases for Pub/Sub (where its limitations are acceptable) is as important as knowing its limitations. The key is workloads where messages are valuable only while live, delivery is "nice to have," and the data exists durably elsewhere:

```javascript
// Pattern 1: Cache invalidation broadcast
// When cached data changes: notify all app servers to clear their local caches
// Message loss: acceptable — stale cache is tolerable briefly
// All servers must receive: YES (broadcast semantics — perfect for Pub/Sub)

class CacheInvalidationService {
    constructor(redis, localCache) {
        this.redis = redis;
        this.localCache = localCache;
        this.subscriber = redis.duplicate();
    }

    async start() {
        await this.subscriber.subscribe('cache:invalidate');
        this.subscriber.on('message', (channel, message) => {
            const { keys, pattern } = JSON.parse(message);
            if (keys) {
                keys.forEach(key => this.localCache.delete(key));
            }
            if (pattern) {
                this.localCache.deletePattern(pattern);
            }
        });
    }

    async invalidate(keys) {
        // Update the primary store first:
        await Promise.all(keys.map(k => this.redis.del(k)));

        // Broadcast invalidation to all app servers:
        await this.redis.publish('cache:invalidate', JSON.stringify({ keys }));
        // If some servers miss this: their cache goes stale temporarily
        // Next read: cache miss → fetch from DB → correct data
        // Acceptable because the data is correct in the DB
    }
}
```

```javascript
// Pattern 2: Presence system (who is online)
// Message loss: acceptable — online status is eventually consistent
// High frequency: users send heartbeats every 30s — missing one is fine

class PresenceService {

        await this.redis.publish(`presence:${userId}`,

        // Other users just don't get the real-time update — TTL expiry catches it
    }
}
```

## Section 8: Reliability Workarounds

**Q10. How do you build at-least-once delivery on top of Pub/Sub — and when should you just use Streams instead?**
A: Several patterns attempt to add reliability to Pub/Sub, but they all add complexity that approaches the complexity of using Redis Streams directly. Understanding these patterns helps evaluate when the workaround cost exceeds the cost of switching tools:

```javascript
// Workaround 1: Pub/Sub notification + database fetch
// The most common and practical pattern for critical data

// Publisher:
async function publishOrderEvent(orderId, eventType) {
    // 1. Write event to durable storage FIRST:
    const eventId = await db.events.insert({
        type: eventType,
        orderId,
        status: 'PENDING',
        createdAt: new Date()
    });

    // 2. Publish a NOTIFICATION (not the data itself):
    await redis.publish('order:events',
        JSON.stringify({
            eventId,        // Just the ID
            eventType,
            orderId
        })
    );
    // If Pub/Sub message lost: subscriber fetches pending events from DB on startup
}

// Subscriber:
subscriber.on('message', async (channel, raw) => {
    const { eventId } = JSON.parse(raw);

    // Fetch from DB (idempotent, handles gaps):
    const event = await db.events.findById(eventId);
    if (event?.status === 'PENDING') {
        await processEvent(event);
        await db.events.update(eventId, { status: 'COMPLETED' });
    }
});

// On startup: process any missed events:
async function recoverMissedEvents() {
    const pending = await db.events.findAll({ status: 'PENDING' });
    for (const event of pending) {
        await processEvent(event);
        await db.events.update(event.id, { status: 'COMPLETED' });
    }
}

// Assessment: this pattern works but requires a database.
// If you already have a database and need this complexity:
// just use outbox + polling, or switch to Redis Streams
```

```javascript
// Workaround 2: Last-value cache with Pub/Sub
// Store the latest state in a Redis key; Pub/Sub notifies of change
// Subscriber reads from the key (not from the message itself)

// Publisher:
async function updateOrderStatus(orderId, status) {
    // Store current state in Redis key (durable via RDB/AOF):
    await redis.set(`order:${orderId}:status`, status);

    // Notify subscribers that this order changed:
    await redis.publish('order:status:changed', orderId);
}

// Subscriber:
subscriber.on('message', async (channel, orderId) => {
    // Read current state from the key (not from message):
    const status = await redis.get(`order:${orderId}:status`);
    if (status) {
        await updateUI(orderId, status);
    }
});

// If Pub/Sub message lost:
// - Subscriber misses the notification
// - Redis key still has the correct current state
// - Next time subscriber checks (or next notification): correct value

// On startup: check all watched orders for current state:
async function syncInitialState(watchedOrderIds) {
    const statuses = await redis.mget(
        ...watchedOrderIds.map(id => `order:${id}:status`)
    );
    // Apply current states to UI — no gap from Pub/Sub miss
}
```

```javascript
// When to give up on workarounds and use Redis Streams:

// Signal 1: Your workaround requires a database anyway
// → Just use Redis Streams instead (more integrated)

// Signal 2: You need message ordering across multiple event types
// → Pub/Sub channels have independent ordering; Streams have total order

// Signal 3: You need N independent consumer groups
// Pub/Sub: all N groups receive all messages (broadcast)
// Streams: each consumer group independently processes all messages

// Signal 4: You need replay for new consumers
// → Streams provide this natively; Pub/Sub workaround is complex

// Direct comparison for an order processing system:

// Pub/Sub approach (with workarounds):
// PUBLISH "order:events" {"eventId": 123}    ← notification
// DB: store event, mark pending
// Subscriber: fetch from DB, process, mark complete
// Recovery: scan DB for pending events on startup
// → 3+ Redis operations + 2+ DB operations per message

// Redis Streams approach (clean):
// XADD "order:events" "*" eventType "created" orderId "ord-123"
// XREADGROUP GROUP workers worker-1 STREAMS "order:events" >
// XACK "order:events" workers messageId
// → 3 Redis operations total, no external DB needed
// → Persistence, ordering, consumer groups, replay — built in
```

## Section 9: Scenario-Based Questions

**Q11. "You're building a notification system for a SaaS app with 50,000 concurrent users across 10 app servers. Design the Pub/Sub architecture."**
A:

```javascript
// Architecture decision:
// - 50K concurrent users → WebSocket connections distributed across 10 servers
// - Each server ~5K connections
// - When user on server-1 triggers event for user on server-7: needs Redis Pub/Sub

// Channel design:
// Per-user channels: "user:{userId}:notifications"
// Broadcast channel: "notifications:all"
// Per-tenant channels: "tenant:{tenantId}:notifications" (for SaaS)

// Server-side architecture:
class NotificationArchitecture {
    constructor() {
        // Each app server has:
        this.redis = new Redis(redisConfig);          // General purpose
        this.subscriber = this.redis.duplicate();     // Subscriber connection
        this.userSockets = new Map();                 // Local socket registry
    }

    async initialize() {
        // Subscribe to global broadcast channel:
        await this.subscriber.subscribe('notifications:all');

        // Subscribe to pattern for user-specific channels:
        // NOTE: with 50K users, each having their own channel would mean
        // the subscriber pattern "user:*:notifications" matches all of them
        // → One pattern subscription covers all users on this server
        await this.subscriber.psubscribe('user:*:notifications');

        // For tenant channels:
        await this.subscriber.psubscribe('tenant:*:notifications');

        this.subscriber.on('message', (channel, message) => {
            this.handleBroadcast(message);
        });

        this.subscriber.on('pmessage', (pattern, channel, message) => {
            this.routeToSocket(pattern, channel, message);
        });
    }

    registerSocket(userId, socket) {
        this.userSockets.set(userId, socket);
    }

    unregisterSocket(userId) {
        this.userSockets.delete(userId);
    }

    routeToSocket(pattern, channel, message) {
        if (pattern === 'user:*:notifications') {
            const userId = channel.split(':')[1];
            const socket = this.userSockets.get(userId);
            if (socket?.connected) {
                socket.emit('notification', JSON.parse(message));
            }
            // If user not on this server: another server handles it
        } else if (pattern === 'tenant:*:notifications') {
            const tenantId = channel.split(':')[1];
            // Broadcast to all users of this tenant on THIS server:
            for (const [userId, socket] of this.userSockets) {
                if (socket.data.tenantId === tenantId && socket.connected) {
                    socket.emit('notification', JSON.parse(message));
                }
            }
        }
    }

    handleBroadcast(message) {
        // Broadcast to ALL sockets on this server:
        for (const [userId, socket] of this.userSockets) {
            if (socket.connected) {
                socket.emit('broadcast', JSON.parse(message));
            }
        }
    }
}

// Notification trigger (from any server):
class NotificationTrigger {
    constructor(redis) {
        this.redis = redis;
    }

    async notifyUser(userId, notification) {
        const recipients = await this.redis.publish(
            `user:${userId}:notifications`,
            JSON.stringify(notification)
        );
        if (recipients === 0) {
            // User not connected to any server right now
            // Store for later retrieval:
            await this.redis.lpush(
                `user:${userId}:pending`,
                JSON.stringify({ ...notification, ts: Date.now() })
            );
            await this.redis.expire(`user:${userId}:pending`, 86400); // 24h TTL
        }
    }

    // When user connects: deliver pending notifications:
    async deliverPending(userId, socket) {
        const pending = await this.redis.lrange(`user:${userId}:pending`, 0, -1);
        if (pending.length > 0) {
            pending.reverse().forEach(msg => socket.emit('notification', JSON.parse(msg)));
            await this.redis.del(`user:${userId}:pending`);
        }
    }
}

// Scaling considerations:
// 50K users × 1 pattern sub each = handled by "user:*:notifications" pattern
// Pattern matching cost: each PUBLISH checks all patterns
// With few patterns (3-5) and 50K PUBLISH/sec: acceptable
// With thousands of patterns: consider moving to exact channel subscriptions
// or switching to Socket.IO Redis adapter which handles this transparently
```

**Q12. "Explain why Redis Pub/Sub is appropriate for cache invalidation but NOT appropriate for order processing — use concrete failure scenarios."**
A:

```javascript
// SCENARIO A: Cache invalidation with Pub/Sub — message loss is acceptable

// System: product catalogue cached in 10 app servers' in-memory LRU caches
// Product price changes: $99.99 → $89.99

async function updateProductPrice(productId, newPrice) {
    // Step 1: Update primary database (durable):
    await db.products.update(productId, { price: newPrice });

    // Step 2: Update Redis cache key (durable):
    await redis.set(`product:${productId}`, JSON.stringify({ price: newPrice, ...}), 'EX', 3600);

    // Step 3: Publish invalidation notification:
    await redis.publish('cache:invalidate', JSON.stringify({ key: `product:${productId}` }));
}

// Failure scenario: server-3 misses the Pub/Sub message
// server-3 app: still has cached price $99.99
// User on server-3 sees: $99.99 for 1 more hour (until cache TTL expires)
// Next user request: cache miss → fetch from DB → sees $89.99
// Cost of failure: user temporarily sees old price
// Impact: low (cosmetic, self-healing, no data corruption)
// Pub/Sub is CORRECT here: eventual consistency is acceptable

// SCENARIO B: Order processing with Pub/Sub — message loss is catastrophic

// System: order created → Pub/Sub → fulfillment worker processes order
async function createOrder(userId, items) {
    const order = await db.orders.insert({
        userId, items, status: 'PENDING', createdAt: new Date()
    });

    // Publish to trigger fulfillment:
    await redis.publish('orders:new', JSON.stringify({
        orderId: order.id,
        userId,
        items
    }));

    return order;
}

// Failure scenario 1: fulfillment worker disconnected at the moment of publish
// Worker goes offline at T=10:00:00.000
// Order created at T=10:00:00.001
// PUBLISH returns 0 (no subscribers)
// Worker reconnects at T=10:00:00.100
// Worker never receives this order
// Customer paid, order exists in DB, but fulfillment never happens
// Customer waits forever for shipping notification
// Impact: HIGH (unfulfilled paid order — revenue damage, customer complaint)

// Failure scenario 2: network hiccup during busy period
// 1000 orders created per second
// Worker connection drops for 50ms (TCP reconnect)
// 50 orders published during reconnect gap: all lost
// 50 customers with unfulfilled orders
// No way for the worker to know it missed them
// No error logged — Pub/Sub silently dropped them

// Failure scenario 3: slow fulfillment worker
// Worker processes one order in 500ms
// Orders arriving at 10/second
// Worker buffer fills → Redis disconnects worker
// Orders published during reconnect: all lost

// THE FIX: Redis Streams for order processing
async function createOrderWithStreams(userId, items) {
    const order = await db.orders.insert({
        userId, items, status: 'PENDING'
    });

    // XADD persists to Redis stream (survives worker disconnect):
    await redis.xadd('orders:stream', '*',
        'orderId', order.id,
        'userId', userId,
        'items', JSON.stringify(items)
    );

    return order;
}

// Fulfillment worker (with Redis Streams):
async function fulfillmentWorker() {
    while (true) {
        // XREADGROUP: claims messages, no message lost on worker disconnect:
        const messages = await redis.xreadgroup(
            'GROUP', 'fulfillment', 'worker-1',
            'COUNT', 10,
            'BLOCK', 2000,
            'STREAMS', 'orders:stream', '>'
        );

        for (const [stream, events] of messages ?? []) {
            for (const [id, fields] of events) {
                try {
                    await processOrder(fields);
                    await redis.xack('orders:stream', 'fulfillment', id);
                    // XACK: message removed from Pending Entries List
                    // If worker crashes before XACK: message redelivered to another worker
                } catch (err) {
                    // Message stays in PEL, can be redelivered via XCLAIM
                    console.error('Processing failed, will retry:', err);
                }
            }
        }
    }
}
```

## Quick Reference Table

| Concept | What it is | Key behaviour | Common mistake |
|---|---|---|---|
| `SUBSCRIBE channel` | Client subscribes to exact channel name | Connection enters subscribe-only mode — no other commands | Using the subscriber connection to run regular Redis commands |
| `PUBLISH channel msg` | Send message to all subscribers of channel | Returns integer: number of recipients (0 = nobody got it) | Assuming non-zero return means message was processed |
| `PSUBSCRIBE pattern` | Subscribe to all channels matching glob pattern | Fires `pmessage` event (not `message`); pattern must match full channel name | Mixing up `message` and `pmessage` event handlers |
| `UNSUBSCRIBE` | Leave one or more exact channels | When last subscriber leaves: channel ceases to exist | Forgetting to unsubscribe on service shutdown (connection stays in subscribe mode) |
| `PUNSUBSCRIBE` | Leave one or more patterns | After unsubscribing all: connection exits subscribe mode | |
| No persistence | Messages not stored anywhere | If no subscriber present at publish time: message permanently lost | Using Pub/Sub for critical events (orders, payments) without a durability layer |
| At-most-once delivery | Message delivered 0 or 1 times | No retry, no ACK, no backlog | Expecting Pub/Sub to guarantee delivery — use Redis Streams for that |
| Subscriber connection | Dedicated connection required | Cannot run normal commands while subscribed | Sharing subscriber connection with normal Redis operations |
| Slow consumer disconnect | `client-output-buffer-limit pubsub 32mb 8mb 60` | Redis disconnects slow subscribers (buffer full) | Doing slow async work inside the message handler |
| `PUBSUB CHANNELS [pattern]` | List all active channels | Only shows channels with at least one subscriber | Checking channels to verify a message was received — use NUMSUB instead |
| `PUBSUB NUMSUB channel...` | Count subscribers per channel | Returns channel name + count pairs | |
| `PUBSUB NUMPAT` | Count active pattern subscriptions | Performance indicator: many patterns = slow PUBLISH | |
| Fan-out semantics | Every subscriber gets every message | Cannot do load-balanced "one of N workers processes this" | Using Pub/Sub for work queues — use Redis Lists or Streams for competing consumers |
| Keyspace notifications | Built-in pattern for Redis key events | Requires `notify-keyspace-events` config; listens via `PSUBSCRIBE __keyevent@N__:event` | Forgetting to set the config — events never fire |
| Redis Streams vs Pub/Sub | Streams: persistent, consumer groups, replay; Pub/Sub: broadcast now, ephemeral | Use Streams for reliability; use Pub/Sub for real-time broadcast where loss is ok | Using Pub/Sub for everything — the limitations only matter when you need guarantees |

**Tip for interviews:** Five things separate strong candidates on Redis Pub/Sub: (1) explaining **exactly what "no persistence" means operationally** — not just "messages are lost" but specifically that there are three distinct loss scenarios: subscriber offline at publish time (message never delivered), slow consumer buffer overflow (Redis disconnects the subscriber mid-stream), and Redis itself restarting (messages in flight are gone even with AOF enabled because Pub/Sub messages are never written to the persistence files), and being able to name the `client-output-buffer-limit pubsub 32mb 8mb 60` config that controls slow consumer disconnection; (2) knowing the **dedicated connection requirement precisely** — that `SUBSCRIBE` transitions a connection into subscribe-only mode where only `SUBSCRIBE`, `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE`, `PING`, `RESET`, and `QUIT` are allowed, and therefore publishing and subscribing require separate Redis connections (never share a subscriber connection with a connection pool for normal operations); (3) distinguishing **`message` from `pmessage` events** — that `SUBSCRIBE` triggers `message` events with two parameters (channel, message), while `PSUBSCRIBE` triggers `pmessage` events with three parameters (pattern, channel, message), where pattern is the glob that matched and channel is the actual channel name that was published to; (4) articulating **the appropriate use cases for Pub/Sub vs Redis Streams** — that Pub/Sub is correct for cache invalidation broadcast, WebSocket fan-out across server instances, live metrics, and presence updates (all of which tolerate message loss because the data exists durably elsewhere), while Streams are required for order processing, payment events, or any work queue where every message must be processed exactly once with acknowledgement; and (5) knowing **the Socket.IO Redis adapter pattern** — that scaling WebSocket gateways across multiple servers is the canonical Pub/Sub use case, where the adapter transparently uses `PUBLISH`/`PSUBSCRIBE` to bridge `socket.to(room).emit()` calls across server instances so that a message from a user on server-1 reaches a user on server-7 without the application code knowing about the multi-server topology.
