# Redis Sentinel: High Availability Monitoring — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Redis Sentinel, what problem does it solve, and how does it differ from Redis Cluster?**
A: Redis Sentinel is a separate daemon process that monitors a Redis primary-replica topology and provides automatic failover when the primary becomes unavailable. It solves the single point of failure problem in a standalone Redis setup: without Sentinel, if the primary crashes, a human must manually promote a replica — and the application must be reconfigured to point to it. Sentinel automates this entire process:

```
Without Sentinel — manual failover:

  ┌──────────┐       ┌──────────┐       ┌──────────┐
  │  Client  │──────►│ Primary  │──────►│ Replica  │
  └──────────┘       └──────────┘       └──────────┘
                           ↕
                       crashes
                           ↓
  1. Human notices primary is down (minutes to hours)
  2. Human connects to replica, runs: REPLICAOF NO ONE
  3. Human updates application config with new primary address
  4. Human restarts application (or updates config dynamically)
  5. Human provisions a new replica
  Total downtime: minutes to hours, proportional to human response speed

With Sentinel — automatic failover:

  ┌──────────┐    ┌──────────────────────────────────────────────┐
  │  Client  │───►│          Sentinel Topology                   │
  └──────────┘    │  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
     │ asks:      │  │Sentinel 1│  │Sentinel 2│  │Sentinel 3│  │
     │ "who is    │  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
     │  primary?" │       │              │              │         │
     └────────────┼───────┴──────────────┴──────────────┘        │
                  │              monitor                           │
                  │  ┌──────────┐                ┌──────────┐    │
                  │  │ Primary  │────replication─►│ Replica  │    │
                  │  │(becomes  │                │(promoted │    │
                  │  │ replica) │                │to primary│    │
                  │  └──────────┘                └──────────┘    │
                  └──────────────────────────────────────────────┘
  1. Sentinel nodes detect primary is down (seconds via PING/heartbeat)
  2. Sentinels reach quorum agreement (vote on failure)
  3. Leader Sentinel promotes a replica to primary (REPLICAOF NO ONE)
  4. Other replicas reconfigured to follow new primary
  5. Client queries Sentinel to discover new primary address
  Total downtime: 10-30 seconds (configurable)
```

```
Sentinel vs Redis Cluster — critical distinction:

  Redis Sentinel:
    Purpose:    High availability for a SINGLE dataset
    Data:       One primary holds all data (replicas are hot standbys)
    Scaling:    Vertical only — you cannot shard data across nodes
    Failover:   Automatic primary promotion
    Use when:   Dataset fits on one server; need HA without data sharding
    Complexity: Moderate (Sentinels + primary + replicas)

  Redis Cluster:
    Purpose:    Horizontal scaling AND high availability
    Data:       Sharded across 16384 hash slots on multiple primaries
    Scaling:    Horizontal — add shards to increase capacity
    Failover:   Built-in (Cluster handles its own failover without Sentinels)
    Use when:   Dataset exceeds single server capacity; need sharding
    Complexity: Higher (multiple primaries + replicas, slot management)

  Key: Sentinel does NOT shard data. If your dataset is 500GB and
  your server has 128GB RAM, Sentinel cannot help — use Cluster.
  Sentinel solves: "what if my Redis server goes down?"
  Cluster solves:  "how do I store more data than fits on one server?"
```

**Q2. What are Sentinel's four core responsibilities — monitoring, notification, automatic failover, and configuration provider?**
A: Sentinel is designed around four distinct roles that collectively deliver high availability. Understanding each role explains why Sentinel requires multiple instances and why clients must talk to Sentinel before connecting to Redis:

```
The four responsibilities:

1. MONITORING
   Sentinel continuously checks that Redis primary and replica
   instances are working correctly.
   Method: sends PING command every sentinel-down-after-milliseconds
   (default 30 seconds) to each monitored Redis instance
   If no response within the timeout: marks instance as Subjectively Down (SDOWN)
   SDOWN + quorum agreement: marks as Objectively Down (ODOWN) → triggers failover

2. NOTIFICATION
   Sentinel can notify administrators and other programs via:
   - Pub/Sub channels (Sentinel publishes events to its own Pub/Sub)
   - Configurable scripts executed on events
   Events: +sdown, -sdown, +odown, +slave-reconf-done, +failover-end, etc.
   Applications can subscribe to Sentinel's Pub/Sub to react to topology changes

3. AUTOMATIC FAILOVER
   When primary is ODOWN (objective down — quorum agrees it's failed):
   - Elect a leader Sentinel to coordinate failover
   - Select the best replica to promote (based on priority, replication offset, ID)
   - Send REPLICAOF NO ONE to the chosen replica
   - Reconfigure other replicas to follow the new primary
   - Update Sentinel configuration with new primary address
   - Notify clients via Pub/Sub that primary address changed

4. CONFIGURATION PROVIDER
   Clients do NOT connect directly to Redis primary address
   Clients connect to Sentinel and ask: "what is the current primary?"
   Sentinel returns: the current primary's host:port
   Client then connects to that primary
   On failover: client must reconnect to Sentinel to discover new primary
   This is why Sentinel's address is stable — Redis primary address changes
```

```bash
# Sentinel as configuration provider — the client connection pattern:

# Step 1: Client connects to ANY Sentinel node and asks for primary:
redis-cli -h sentinel-1 -p 26379
SENTINEL get-master-addr-by-name mymaster
# Returns: 1) "redis-primary" 2) "6379"

# Step 2: Client connects to the returned address:
redis-cli -h redis-primary -p 6379
SET key value

# After failover — primary has changed:
SENTINEL get-master-addr-by-name mymaster
# Returns: 1) "redis-replica-1" 2) "6379"  ← new primary!

# Client must reconnect to Sentinel on connection errors to rediscover
# In production: Redis client libraries handle this automatically
# (ioredis, redis-py, Jedis all have native Sentinel support)
```

## Section 2: Architecture and Quorum

**Q3. How does Sentinel's quorum and leader election work — what is SDOWN vs ODOWN?**
A: Sentinel uses a two-phase failure detection system to prevent false positives from triggering unnecessary failovers. A single Sentinel declaring a primary down (SDOWN) is not enough — a majority must agree (ODOWN) before failover begins. This protects against network partitions and individual Sentinel failures:

```
SDOWN vs ODOWN — the two-phase failure detection:

  SDOWN (Subjectively Down):
    One Sentinel's LOCAL opinion that an instance is unreachable
    Trigger: no response to PING within down-after-milliseconds
    This is a LOCAL assessment — no coordination with other Sentinels
    A single network hiccup between THIS Sentinel and Redis can cause SDOWN
    Action: none — just a flag on this Sentinel's local state

  ODOWN (Objectively Down):
    QUORUM number of Sentinels agree the primary is unreachable
    Trigger: Sentinel that detected SDOWN asks others: "do you also see it as down?"
    Others respond with their own assessment
    If >= quorum Sentinels confirm SDOWN: state promoted to ODOWN
    Action: failover process begins

  Why two phases?
    Network partition scenario:
    Sentinel-1 loses connection to primary (SDOWN for Sentinel-1)
    Sentinel-2 and Sentinel-3 can still reach primary (no SDOWN for them)
    Sentinel-1 asks: "anyone else see it down?"
    Sentinel-2, Sentinel-3 respond: "no, we can reach it"
    Quorum (2 of 3) NOT reached → no ODOWN → no failover
    Result: correct — primary is NOT actually down, just Sentinel-1's link is broken

    True failure scenario:
    Primary crashes
    All 3 Sentinels detect SDOWN (no PING response)
    Sentinel-1 asks others: "down for you too?"
    All 3 confirm: quorum (3 >= 2) → ODOWN → failover triggered
    Result: correct — primary IS actually down
```

```
Leader election — which Sentinel coordinates the failover:

  When ODOWN is declared: Sentinels must elect ONE leader to perform failover
  (Avoid multiple Sentinels simultaneously trying to promote different replicas)

  Election algorithm (Raft-based):
  1. Sentinel that detected ODOWN first: sends SENTINEL is-master-down-by-addr
     with its own runid to request votes from other Sentinels
  2. Each Sentinel can vote for only ONE candidate per epoch (term)
  3. First Sentinel to receive votes from quorum of Sentinels: elected leader
  4. Leader Sentinel performs the failover (promotes replica, reconfigures others)
  5. Epoch number increments: prevents stale leaders from interfering

  Quorum vs majority:
    quorum: minimum Sentinels needed to declare ODOWN (configurable)
    majority: minimum Sentinels needed to elect a leader (floor(N/2)+1)
    These are SEPARATE thresholds:
    3 Sentinels: quorum can be 2, majority is always 2
    5 Sentinels: quorum can be 3, majority is always 3
    Recommendation: set quorum = majority for simplicity
```

```bash
# Observing SDOWN/ODOWN transitions via Sentinel Pub/Sub:
redis-cli -h sentinel-1 -p 26379
SUBSCRIBE __sentinel__:hello   # Internal Sentinel gossip channel

# Or listen to Sentinel events:
PSUBSCRIBE *   # All Sentinel events

# Event types published by Sentinel:
# +sdown          ← instance entered SDOWN
# -sdown          ← instance exited SDOWN (came back up)
# +odown          ← instance entered ODOWN (quorum reached)
# -odown          ← instance exited ODOWN
# +failover-state-select-slave   ← selecting which replica to promote
# +selected-slave ← chosen replica identified
# +promoted-slave ← replica has been promoted to primary
# +failover-end   ← failover completed successfully
# +slave-reconf-sent   ← REPLICAOF sent to replica
# +slave-reconf-inprog ← replica is reconfiguring
# +slave-reconf-done   ← replica finished reconfiguring

# Human-readable Sentinel event log (redis-sentinel.log):
# 12345:X 15 Mar 2024 10:00:01.234 # +sdown master mymaster 127.0.0.1 6379
# 12345:X 15 Mar 2024 10:00:01.890 # +odown master mymaster 127.0.0.1 6379 #quorum 2/2
# 12345:X 15 Mar 2024 10:00:01.892 # +failover-state-select-slave master mymaster
# 12345:X 15 Mar 2024 10:00:01.950 # +selected-slave slave 127.0.0.1:6380 127.0.0.1 6380
# 12345:X 15 Mar 2024 10:00:02.100 # +promoted-slave slave 127.0.0.1:6380 127.0.0.1 6380
# 12345:X 15 Mar 2024 10:00:02.350 # +failover-end master mymaster 127.0.0.1 6380
```

**Q4. What is the minimum viable Sentinel deployment, and why are odd numbers required?**
A: The minimum viable Sentinel deployment is three Sentinel instances with quorum set to 2. Fewer Sentinels cannot provide split-brain protection; non-odd counts can leave the system unable to elect a leader. Understanding the math behind these requirements prevents common deployment mistakes:

```
Why 3 Sentinels minimum:

  1 Sentinel:
    ODOWN requires quorum=1 (only one Sentinel exists)
    Network hiccup between Sentinel and primary: triggers failover
    Sentinel itself crashes: no monitoring at all
    No election possible (no peers to vote)
    Verdict: NOT HA — single point of failure

  2 Sentinels:
    Quorum would need to be 2 (both must agree)
    One Sentinel crashes: cannot reach quorum → failover never triggers
    Quorum = 1: any one Sentinel can trigger failover → split-brain possible
    Majority for leader election: 2 (floor(2/2)+1 = 2)
    If Sentinel-2 crashes: Sentinel-1 cannot get 2 votes → no leader
    Verdict: either insecure (quorum=1) or cannot failover (quorum=2)

  3 Sentinels (recommended minimum):
    Quorum = 2: requires 2 of 3 Sentinels to agree on ODOWN
    Can tolerate 1 Sentinel failure: 2 remain, can reach quorum=2
    Can elect a leader: majority = floor(3/2)+1 = 2 votes needed
    If 1 Sentinel crashes: 2 remain → can still failover
    Verdict: correct HA with 1 Sentinel failure tolerance

  5 Sentinels:
    Can tolerate 2 Sentinel failures
    Quorum = 3 (majority), leader election needs 3 votes
    More robust for geographically distributed deployments
    Verdict: use for multi-datacenter deployments

  Why odd numbers:
    Even numbers can deadlock during leader election:
    4 Sentinels split 2-2: neither candidate gets majority (3 needed)
    → No leader → no failover → stuck
    Odd numbers: one candidate always gets (N+1)/2 votes
    Always use: 3, 5, 7 Sentinels (never 2, 4, 6)
```

```
Sentinel placement for fault tolerance — geographic distribution:

  Single datacenter (basic HA):
  ┌────────────────────────────────────────┐
  │  Datacenter A                          │
  │  ┌──────────┐ ┌──────────┐            │
  │  │ Redis    │ │ Redis    │            │
  │  │ Primary  │ │ Replica  │            │
  │  └──────────┘ └──────────┘            │
  │  ┌──────────┐ ┌──────────┐ ┌────────┐│
  │  │Sentinel 1│ │Sentinel 2│ │Sent. 3 ││
  │  └──────────┘ └──────────┘ └────────┘│
  └────────────────────────────────────────┘
  Problem: datacenter failure = total outage

  Multi-datacenter (proper HA):
  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐
  │  DC-A          │  │  DC-B          │  │  DC-C          │
  │  Redis Primary │  │  Redis Replica │  │  (no Redis)    │
  │  Sentinel 1    │  │  Sentinel 2    │  │  Sentinel 3    │
  └────────────────┘  └────────────────┘  └────────────────┘
  DC-A fails:
    DC-B + DC-C have 2 Sentinels → quorum=2 → can failover
    DC-B Replica promoted to Primary
    DC-A comes back: becomes Replica (old primary demoted)
  DC-C is "tie-breaker" DC — just a Sentinel, no Redis
```

## Section 3: Configuration

**Q5. How do you configure Redis Sentinel — what does `sentinel.conf` contain and what do the critical parameters mean?**
A: Sentinel runs as a separate process with its own configuration file. Most parameters have sensible defaults, but several are critical for correctness and must be understood to tune for your specific environment:

```bash
# /etc/redis/sentinel.conf — complete production configuration with explanations

# Sentinel listens on port 26379 (convention — not enforced):
port 26379
bind 0.0.0.0           # Accept connections from any interface
# bind 127.0.0.1       # Localhost only — use if Sentinels are on same machine

# Daemonize (run in background):
daemonize yes
logfile /var/log/redis/sentinel.log
pidfile /var/run/redis/sentinel.pid

# Working directory (where sentinel writes config updates):
dir /var/lib/redis-sentinel

# ══════════════════════════════════════════════════
# THE CORE CONFIGURATION — one per monitored primary
# ══════════════════════════════════════════════════

# sentinel monitor <master-name> <ip> <port> <quorum>
sentinel monitor mymaster 192.168.1.10 6379 2
#                 ↑            ↑         ↑    ↑
#            logical name    primary   port  quorum
#            (used by app    address         (min Sentinels to agree on failure)
#            to look up)

# Authentication — if Redis requires AUTH:
sentinel auth-pass mymaster your-redis-password
# Must be set if Redis primary/replicas use requirepass
# Sentinel uses this password to connect to Redis instances

# sentinel down-after-milliseconds <master-name> <ms>
sentinel down-after-milliseconds mymaster 30000
# How long (ms) a Redis instance must be unreachable before SDOWN is declared
# Default: 30000 (30 seconds)
# Lower: faster detection, more false positives on busy networks
# Higher: fewer false positives, slower failover
# Production recommendation: 10000-30000ms

# sentinel failover-timeout <master-name> <ms>
sentinel failover-timeout mymaster 180000
# Maximum time (ms) allowed for a failover attempt
# If failover takes longer: it's aborted and retried
# Default: 3 minutes (180000ms)
# Should be > (down-after-milliseconds × 2)

# sentinel parallel-syncs <master-name> <count>
sentinel parallel-syncs mymaster 1
# How many replicas can sync from new primary simultaneously after failover
# 1: replicas sync one at a time (other replicas remain readable during sync)
# N: N replicas sync in parallel (faster catchup, but N replicas temporarily unavailable)
# Production recommendation: 1 for most deployments

# TLS configuration (Redis 6.0+):
# sentinel tls-port 26380
# sentinel tls-cert-file /etc/redis/sentinel.crt
# sentinel tls-key-file /etc/redis/sentinel.key
# sentinel tls-ca-cert-file /etc/redis/ca.crt
```

```bash
# Additional Sentinel configuration for production:

# Notification script — called on events:
sentinel notification-script mymaster /opt/redis/notify.sh
# Script called with: event-type event-description
# Example: on failover, send Slack alert

# Client reconfiguration script — called when clients need to be notified:
sentinel client-reconfig-script mymaster /opt/redis/reconfig.sh
# Called with: master-name role state from-ip from-port to-ip to-port
# Use to update load balancers, DNS, etc. when primary changes

# Announce address (important for NAT/Docker environments):
sentinel announce-ip 10.0.1.50    # External IP this Sentinel announces to peers
sentinel announce-port 26379      # External port
# Without this: Sentinel announces its internal IP which peers may not reach
# In Docker: announce the container's external IP/port

# TLS for Sentinel-to-Redis connections:
# sentinel tls-replication yes
# sentinel tls-auth-clients no   # Don't require TLS from Redis clients

# Resolved configuration after Sentinel discovers replicas:
# (Sentinel auto-appends these when it discovers topology — do not edit manually)
# sentinel known-replica mymaster 192.168.1.11 6379
# sentinel known-replica mymaster 192.168.1.12 6379
# sentinel known-sentinel mymaster 192.168.1.21 26379 <sentinel-runid>
# sentinel known-sentinel mymaster 192.168.1.22 26379 <sentinel-runid>
# sentinel current-epoch 3
```

```bash
# Redis primary configuration for Sentinel compatibility:
# /etc/redis/redis.conf (primary):

bind 0.0.0.0
protected-mode no          # Allow connections from Sentinels
requirepass your-password
masterauth your-password   # Password to use when replicating (same as requirepass)

# Replica configuration:
# /etc/redis/redis.conf (replica):
replicaof 192.168.1.10 6379    # Point to primary
requirepass your-password
masterauth your-password        # Must match primary's requirepass

# Priority for replica promotion (lower = preferred):
replica-priority 100           # Default: 100
# Set lower on "better" replicas to make them preferred for promotion:
# replica-priority 50   ← this replica promoted first if primary fails
# replica-priority 200  ← this replica promoted last (e.g., cross-region replica)
# replica-priority 0    ← NEVER promote this replica (use for async offload replicas)

# Minimum replicas for primary to accept writes:
min-replicas-to-write 1        # Refuse writes if no replicas connected
min-replicas-max-lag 10        # Refuse writes if all replicas lag > 10 seconds
# These prevent split-brain: if primary loses all replicas (network partition)
# it stops accepting writes, preventing data from being committed only to the
# isolated primary that will be demoted
```

## Section 4: Failover Process

**Q6. Walk through the complete failover sequence — what happens from primary crash to clients connecting to the new primary?**
A: A failover involves coordination between multiple Sentinel instances, the remaining Redis replicas, and ultimately the client applications. The sequence has eight distinct phases:

```
Complete failover timeline:

  T+0s:   Primary Redis crashes (hardware failure, OOM, network issue)

  T+0s to T+30s: DETECTION PHASE
    Sentinels send PING to primary every second
    No response received within down-after-milliseconds (30s)
    Each Sentinel independently marks primary as SDOWN
    (All 3 Sentinels will reach SDOWN at roughly the same time)

  T+30s: AGREEMENT PHASE
    Sentinel-1 (first to reach SDOWN) asks Sentinel-2 and Sentinel-3:
    SENTINEL is-master-down-by-addr <primary-ip> <primary-port> <epoch> <sentinel-runid>
    Sentinel-2 and Sentinel-3 confirm: "yes, we also see it as down"
    2 confirmations >= quorum (2) → ODOWN declared

  T+30s: LEADER ELECTION PHASE
    Sentinel-1 requests votes from Sentinel-2 and Sentinel-3 to be leader
    Sentinel-2 and Sentinel-3 vote for Sentinel-1 (first to ask wins votes)
    Sentinel-1 elected as leader (has majority votes: 3 including its own)

  T+30.1s: REPLICA SELECTION PHASE (by Leader Sentinel-1)
    Evaluate available replicas — score each:
    1. Exclude replicas with high replication lag (> 10 seconds behind)
    2. Sort by replica-priority (lower = preferred)
    3. Tie-break: most up-to-date replication offset (has most data)
    4. Final tie-break: lexicographically smallest run ID
    Best replica selected: Replica-1 (priority=100, offset=9999)

  T+30.2s: PROMOTION PHASE
    Leader Sentinel sends to Replica-1:
    REPLICAOF NO ONE
    Replica-1 stops replicating, becomes new primary
    Replica-1 now accepts write commands

  T+30.3s: RECONFIGURATION PHASE
    Leader Sentinel sends to Replica-2:
    REPLICAOF <Replica-1-ip> <Replica-1-port>
    Replica-2 starts replicating from new primary (Replica-1)
    Sentinel updates its own config: mymaster → Replica-1's address

  T+30.5s: CLIENT NOTIFICATION PHASE
    Sentinel publishes to __sentinel__:hello channel:
    +switch-master mymaster <old-ip> 6379 <new-ip> 6379
    Applications subscribed to Sentinel events receive this
    Sentinel now responds to:
    SENTINEL get-master-addr-by-name mymaster
    with: Replica-1's address (the new primary)

  T+31s: CLIENT RECONNECTION PHASE
    Client libraries detect connection failure to old primary
    Clients query Sentinel: get-master-addr-by-name mymaster
    Clients receive new primary address (Replica-1)
    Clients reconnect to new primary
    Normal operation resumes

  T+??: OLD PRIMARY RECOVERY
    Old primary comes back online
    Sentinel detects it and sends: REPLICAOF <new-primary-ip> <port>
    Old primary demoted to replica — follows the new primary
    Data from old primary (if any committed during isolation) is DISCARDED
    Old primary syncs from new primary (partial or full resync)

  Total failover time: ~30-35 seconds (with default 30s down-after-milliseconds)
  Downtime window: from T+0 (crash) to T+31 (clients reconnect)
  To reduce downtime: lower down-after-milliseconds (e.g., 5000ms = 5s)
```

```bash
# Manually observing failover:

# Force a failover for testing (without crashing anything):
redis-cli -h sentinel-1 -p 26379
SENTINEL failover mymaster
# Triggers a controlled failover even though primary is healthy
# Useful for planned maintenance: promotes a replica, no downtime for reads

# Check current primary after failover:
SENTINEL get-master-addr-by-name mymaster
# 1) "192.168.1.11"   ← new primary (was replica)
# 2) "6379"

# Check all replicas and their status:
SENTINEL replicas mymaster
# Returns info for each replica:
# name, ip, port, runid, flags, lag, offset, priority, etc.

# Check Sentinel's view of all Sentinels:
SENTINEL sentinels mymaster
# Returns info for each peer Sentinel

# Reset Sentinel state (after topology changes):
SENTINEL reset mymaster
# Clears Sentinel's accumulated state about the named master
# Use after major topology changes (e.g., replacing all replicas)
```

**Q7. How does Sentinel handle split-brain — what happens when the old primary comes back after failover?**
A: Split-brain occurs when both the old primary and the new primary are accepting writes simultaneously, creating diverging datasets. Sentinel prevents this through the `min-replicas-to-write` configuration on the old primary and through the reconnection protocol:

```
Split-brain scenario and prevention:

  Network partition scenario (most dangerous):
  ┌──────────────────────────────────────────────────────────┐
  │ T=0: Network splits into two partitions                   │
  │                                                          │
  │ Partition A:          │  Partition B:                    │
  │  Primary (healthy)    │   Replica-1                      │
  │  App Server-1         │   Replica-2                      │
  │  Sentinel-1           │   Sentinel-2                     │
  │                       │   Sentinel-3                     │
  │                       │   App Server-2                   │
  └──────────────────────────────────────────────────────────┘

  Without protection:
  Partition B: Sentinel-2 + Sentinel-3 → quorum (2) → ODOWN → failover
              Replica-1 promoted to primary
              App Server-2 writes to Replica-1 (new primary in Partition B)
  Partition A: Primary is still running, App Server-1 writes to old primary
              SPLIT BRAIN: two primaries accepting different writes

  When partition heals:
  Old primary forced to replicate from new primary
  Old primary's writes DISCARDED (those that didn't reach new primary)
  App Server-1's writes are LOST

  Prevention via min-replicas-to-write:

  # In primary's redis.conf:
  min-replicas-to-write 1
  min-replicas-max-lag 10

  In Partition A:
  Primary loses connection to both replicas (they're in Partition B)
  Primary's connected replica count drops to 0
  min-replicas-to-write=1: "must have at least 1 connected replica to accept writes"
  Primary stops accepting writes → returns error to App Server-1
  App Server-1 gets write errors → knows something is wrong → stops writing
  When partition heals: no lost data (App Server-1's writes were rejected)
```

```bash
# What happens to old primary data when it rejoins:

# Old primary comes back after failover:
# Sentinel sends: REPLICAOF <new-primary-ip> <new-primary-port>
# Old primary stops being a primary, starts replicating from new primary

# PARTIAL RESYNC (if old primary's replication backlog overlaps):
# New primary's replication_id matches old primary's secondary_replication_id
# Only the missing commands need to be sent (not full resync)
# Fast recovery

# FULL RESYNC (if old primary was partitioned too long):
# Old primary's offset is too far behind (backlog was cleared)
# BGSAVE on new primary, send full RDB to old primary
# Old primary discards ALL its data, loads RDB from new primary
# Any writes made to old primary during partition: PERMANENTLY LOST

# Check if a resync is happening:
redis-cli -h old-primary -p 6379 INFO replication
# master_link_status: down    ← still syncing
# master_link_status: up      ← sync complete
# master_last_io_seconds_ago: 0  ← actively replicating

# Monitor resync progress:
redis-cli -h new-primary -p 6379 INFO replication
# connected_slaves: 1
# slave0: ip=192.168.1.10,port=6379,state=sync,offset=99999,lag=0
```

## Section 5: Client Integration

**Q8. How do client libraries connect through Sentinel — what is the correct connection pattern in Node.js?**
A: Clients should never hardcode the Redis primary address when using Sentinel. Instead, they connect to one or more Sentinel addresses, query for the current primary, then connect to Redis. Client libraries like ioredis abstract this entirely, handling automatic reconnection, failover detection, and primary rediscovery:

```javascript
// ioredis — native Sentinel support:
const Redis = require('ioredis');

// WRONG: hardcoding Redis primary address (breaks on failover):
const redis = new Redis({ host: 'redis-primary', port: 6379 });
// After failover: redis-primary is now a replica → writes fail

// CORRECT: Sentinel-aware client:
const redis = new Redis({
    sentinels: [
        { host: 'sentinel-1', port: 26379 },
        { host: 'sentinel-2', port: 26379 },
        { host: 'sentinel-3', port: 26379 }
    ],
    name: 'mymaster',          // Must match sentinel.conf master-name
    password: 'redis-password', // Redis AUTH password (not Sentinel password)
    sentinelPassword: 'sentinel-password',  // If Sentinels have requirepass
    role: 'master',            // 'master' (writes) or 'slave' (reads)

    // Connection retry on failover:
    retryStrategy: (times) => {
        if (times > 10) return null;  // Give up after 10 retries
        return Math.min(times * 200, 2000);  // Exponential backoff, max 2s
    },

    // Failover detection sensitivity:
    sentinelRetryStrategy: (times) => Math.min(times * 200, 5000),
    enableOfflineQueue: true,  // Buffer commands during failover (default: true)
    maxRetriesPerRequest: 3,   // Retry each command up to 3 times
});

// ioredis handles:
// 1. Connects to first available Sentinel
// 2. Sends: SENTINEL get-master-addr-by-name mymaster
// 3. Connects to returned primary address
// 4. If primary fails: receives error, reconnects to Sentinel
// 5. Gets new primary address, reconnects
// Application code: identical to standalone Redis

// Read from replica (for read scaling):
const replicaClient = new Redis({
    sentinels: [
        { host: 'sentinel-1', port: 26379 },
        { host: 'sentinel-2', port: 26379 },
        { host: 'sentinel-3', port: 26379 }
    ],
    name: 'mymaster',
    password: 'redis-password',
    role: 'slave',             // Connect to a replica for reads
    preferredSlaves: [         // Prefer specific replicas (optional):
        { ip: '192.168.1.11', port: '6379', prio: 1 },
        { ip: '192.168.1.12', port: '6379', prio: 2 }
    ]
});
```

## Section 7: Advanced Topics

**Q10. How do you perform a planned failover (maintenance), and what is the risk of data loss during unplanned failover?**
A: Planned failovers (for maintenance) can be done with zero data loss because the operation is controlled. Unplanned failovers carry a risk of data loss proportional to how much replication lag exists at the moment of failure:

```bash
# Planned failover — for primary maintenance (zero data loss):
# Goal: promote a replica without downtime or data loss

# Step 1: Check replica lag before proceeding:
redis-cli -h redis-primary -p 6379 INFO replication
# slave0: ip=192.168.1.11,port=6379,state=online,offset=999999,lag=0
# lag=0: fully caught up → safe to failover now

# Step 2: Trigger Sentinel failover:
redis-cli -h sentinel-1 -p 26379 SENTINEL failover mymaster
# Sentinel immediately:
# 1. Picks the best replica
# 2. Waits for it to fully sync (offset matches primary)
# 3. Sends REPLICAOF NO ONE (promotes replica)
# 4. Old primary becomes replica
# No writes are lost because: failover only completes when replica is 100% synced

# Step 3: Verify new primary:
redis-cli -h sentinel-1 -p 26379 SENTINEL get-master-addr-by-name mymaster
# 1) "192.168.1.11"   ← new primary (previously Replica-1)

# Step 4: Perform maintenance on old primary (now a replica):
# redis-cli -h 192.168.1.10 -p 6379 SHUTDOWN SAVE
# (upgrade, replace hardware, etc.)

# Step 5: Bring old primary back as a replica:
# redis-server /etc/redis/redis.conf
# It will automatically join as a replica via Sentinel's REPLICAOF command
```

```
Data loss risk during unplanned failover:

  Maximum data loss = replication lag at the moment of primary crash

  Example:
  Primary repl offset: 100000 bytes generated
  Replica repl offset: 99950 bytes applied
  Replication lag: 50 bytes (50 bytes not yet sent to replica)

  Primary crashes: those 50 bytes are lost
  Replica promoted: starts from offset 99950
  Clients reconnect: resume writing from 99950
  The 50 bytes are permanently gone

  Minimizing data loss:

  1. Keep replicas as caught up as possible:
     - Use fast network between primary and replicas
     - Monitor replication lag (should be < 1 second)
     - Tune: repl-backlog-size (larger = more buffer for temporary disconnects)

  2. Use min-replicas-to-write to prevent extreme lag:
     min-replicas-to-write 1      ← primary refuses writes if no connected replicas
     min-replicas-max-lag 10      ← primary refuses writes if all replicas lag > 10s
     # In the worst case: application gets write errors for ~10s before failover
     # But: reduces maximum data loss to ~10 seconds of writes

  3. Synchronous replication (WAIT command):
     WAIT 1 1000    ← wait for 1 replica to acknowledge, timeout 1000ms
     SET important-key important-value
     WAIT 1 1000    ← blocks until 1 replica has this write, or timeout
     # Converts one write from async to sync — used for critical data only
     # Has latency cost: must wait for replica ACK before returning

  4. Accept some data loss (most realistic position):
     For cache, sessions, rate limiters: losing a few seconds of data is fine
     For financial transactions: use a relational database with synchronous replication
     Redis Sentinel is not a zero-data-loss solution — it's a best-effort HA solution
```

**Q11. What are the networking requirements for Sentinel — what must be reachable from where?**
A: Sentinel requires a specific connectivity matrix between all components. In cloud or containerized environments, firewall rules and NAT configuration are the most common source of Sentinel failures:

```
Required network connectivity matrix:

  Every Sentinel must reach:
  ├── Every Redis instance (primary and replicas) on port 6379
  │   (To send PING, INFO, and replication commands)
  ├── Every other Sentinel on port 26379
  │   (To exchange gossip, vote in elections, coordinate failover)
  └── Client applications need NOT connect to all Sentinels
      (Just need to reach at least 1 working Sentinel)

  Every Redis primary must reach:
  └── Every replica on their replication port (6379 by default)

  Every Redis replica must reach:
  └── The primary for replication

  Visualization:

  ┌───────────────────────────────────────────────────────────────┐
  │                    Required connections                       │
  │                                                               │
  │  Sentinel-1 ←→ Sentinel-2 ←→ Sentinel-3 (port 26379)         │
  │       ↕              ↕              ↕                         │
  │       └──────────────┼──────────────┘                        │
  │                      ↕ (all Sentinels to all Redis)           │
  │  Primary ←→ Replica-1 ←→ Replica-2 (port 6379)               │
  │  (replication: Primary → Replicas)                            │
  │                                                               │
  │  App Server → Sentinel-1 OR Sentinel-2 OR Sentinel-3 (26379)  │
  │  App Server → Primary (6379) — after discovery                │
  └───────────────────────────────────────────────────────────────┘
```

## Section 8: Scenario-Based Questions

**Q12. "Your Sentinel cluster is not failing over even though the primary is clearly down. Walk through how you diagnose this."**
A:

```bash
# Step 1: Verify Sentinel processes are running:
systemctl status redis-sentinel    # or: ps aux | grep redis-sentinel
# If not running: start them first

# Step 2: Check if Sentinels can reach the primary:
redis-cli -h sentinel-1 -p 26379 SENTINEL master mymaster | grep -E "flags|last-ok-ping"
# flags: s_down,master  ← Sentinel-1 sees it as SDOWN
# last-ok-ping-reply: 45000  ← 45 seconds since last successful ping

redis-cli -h sentinel-2 -p 26379 SENTINEL master mymaster | grep flags
# flags: master  ← Sentinel-2 does NOT see it as SDOWN!
# Root cause: Sentinel-2 can still reach the primary (partial network failure)

# Sentinel-1 has SDOWN, Sentinel-2 does not → quorum (2) not reached
# ODOWN never declared → no failover triggered

# Step 3: Verify Sentinels can reach each other:
redis-cli -h sentinel-1 -p 26379 SENTINEL sentinels mymaster
# For each peer Sentinel, check:
# flags: sentinel            ← healthy
# flags: sentinel,s_down     ← THIS Sentinel cannot reach that peer!
# If any Sentinel appears disconnected: inter-Sentinel connectivity broken

# Step 4: Check quorum configuration:
redis-cli -h sentinel-1 -p 26379 SENTINEL master mymaster | grep quorum
# quorum: 3   ← Oops! Requires 3/3 Sentinels to agree, but only 2 are reachable
# Fix: lower quorum if you have 3 Sentinels: should be 2

redis-cli -h sentinel-1 -p 26379 SENTINEL set mymaster quorum 2
redis-cli -h sentinel-2 -p 26379 SENTINEL set mymaster quorum 2
redis-cli -h sentinel-3 -p 26379 SENTINEL set mymaster quorum 2

# Step 5: Check Sentinel log for specific errors:
tail -100 /var/log/redis/sentinel.log
# Common entries:
# +sdown master mymaster  → SDOWN detected (good)
# -sdown master mymaster  → Sentinel keeps flip-flopping (flapping)
#   → down-after-milliseconds too low, or network is flaky
# Could not connect to sentinel ...  → inter-Sentinel communication issue

# Step 6: If quorum was met but failover didn't start:
# Check epoch and leader election:
redis-cli -h sentinel-1 -p 26379 INFO sentinel
# sentinel_masters: 1
# master0:name=mymaster,status=odown,...
# status=odown means ODOWN was reached but leader election may have failed

# Check if any Sentinel won the election:
# Look for this in logs:
# +elected-leader master mymaster   → leader was elected
# No +elected-leader in logs        → election failed (Sentinels can't communicate)

# Emergency manual failover if everything is stuck:
redis-cli -h sentinel-1 -p 26379 SENTINEL failover mymaster
# This forces a failover from this Sentinel regardless of election
# Use only when automatic failover is completely stuck
```

**Q13. "Design a Redis Sentinel deployment for a 3-region active-passive web application."**
A:

```
Architecture for 3-region active-passive deployment:

  Region US-EAST (PRIMARY):     Region EU-WEST (SECONDARY):   Region AP-SOUTHEAST (OBSERVER):
  ┌──────────────────────┐      ┌──────────────────────┐      ┌──────────────────────┐
  │  Redis PRIMARY       │─────►│  Redis Replica-EU    │      │                      │
  │  (accepts writes)    │      │  (read-only)         │      │                      │
  │                      │─────►│                      │      │                      │
  │  Redis Replica-US    │      │                      │      │                      │
  │  (local standby)     │      │                      │      │                      │
  │                      │      │                      │      │                      │
  │  Sentinel-US-1       │      │  Sentinel-EU-1       │      │  Sentinel-AP-1       │
  │  Sentinel-US-2       │      │  Sentinel-EU-2       │      │                      │
  └──────────────────────┘      └──────────────────────┘      └──────────────────────┘

  Quorum: 3 (out of 5 Sentinels)
  Scenario: US-EAST goes down completely

  Surviving Sentinels: EU-1, EU-2, AP-1 (3 Sentinels = quorum of 3)
  Failover: Replica-EU promoted to primary
  Application in EU-WEST: now writes to EU primary (was already reading there)
  Application in AP-SOUTHEAST: must redirect writes to EU primary (WAN latency)
```

```bash
# sentinel.conf for US-EAST Sentinel instances:
port 26379
sentinel monitor mymaster 10.0.1.10 6379 3
sentinel auth-pass mymaster your-password
sentinel down-after-milliseconds mymaster 30000
sentinel failover-timeout mymaster 180000
sentinel parallel-syncs mymaster 1

# Key design decisions:

# 1. Quorum = 3 (out of 5 Sentinels):
#    Tolerates: 2 Sentinel failures or 1 whole region going down
#    EU-WEST + AP-SOUTHEAST = 3 Sentinels → can still failover

# 2. down-after-milliseconds = 30000 (30 seconds):
#    Cross-region network can have spikes → 30s prevents false positives
#    Within same region: 5-10s is acceptable

# 3. replica-priority configuration in redis.conf:
#    Replica-US (local standby): replica-priority 50   ← PREFERRED for failover
#    Replica-EU (cross-region):  replica-priority 100  ← less preferred
#    If US-EAST fails: Replica-US might also be down → Replica-EU promoted
#    If only primary fails: Replica-US (still in US-EAST) promoted (lower priority)

# 4. Cross-region replication latency:
#    Replica-EU will always lag behind primary (50-100ms WAN RTT)
#    This means up to 100ms of data may be lost in a failover
#    Accept this OR use WAIT 1 1000 for critical writes

# Application configuration — must handle multi-region Sentinel:
```

## Quick Reference Table

| Concept | What it is | Key detail | Common mistake |
|---|---|---|---|
| Sentinel process | Separate daemon (not Redis) running on port 26379 | Monitors Redis topology, provides automatic failover and service discovery | Running Sentinel on same server as the Redis it monitors — server failure takes both |
| SDOWN | Subjectively Down — one Sentinel's local assessment | Single Sentinel cannot reach the instance within `down-after-milliseconds` | Confusing SDOWN (local view) with ODOWN (quorum agreement) — only ODOWN triggers failover |
| ODOWN | Objectively Down — quorum of Sentinels agree | Requires `quorum` number of Sentinels to confirm SDOWN before failover begins | Setting quorum too high — if quorum > surviving Sentinels, failover never triggers |
| Quorum | Minimum Sentinels required to agree on ODOWN | Should be majority of Sentinel count; separate from leader election majority | Setting quorum = 1 — one Sentinel's network hiccup triggers failover |
| `down-after-milliseconds` | PING timeout before SDOWN is declared | Default: 30,000ms; lower = faster detection, more false positives | Too low on high-latency networks — constant false failovers |
| `failover-timeout` | Maximum time allowed for failover attempt | Default: 180,000ms; if exceeded, failover aborts and retries | Too short — partial failovers that abort mid-way leave cluster in inconsistent state |
| `parallel-syncs` | Replicas that sync from new primary simultaneously | 1 = sequential (other replicas stay readable); N = parallel (faster but N replicas unavailable) | Setting high parallel-syncs — all replicas unavailable for reads during post-failover sync |
| `SENTINEL get-master-addr-by-name` | Client command to discover current primary | Returns host:port of current primary; must be called by clients on reconnect | Hardcoding Redis primary address in application — breaks after first failover |
| `min-replicas-to-write` | Primary refuses writes if fewer than N replicas connected | Prevents split-brain: isolated primary stops accepting writes | Leaving at 0 — primary accepts writes even when partitioned, causes data loss |
| `replica-priority 0` | Mark a replica as never eligible for promotion | Use for cross-region async replicas, analytics replicas, or backup-only replicas | Not setting priority 0 on replicas that should never be primary — they may be promoted |
| Sentinel Pub/Sub | Sentinels publish events to `__sentinel__:hello` and event channels | `+failover-end`, `+switch-master`, `+sdown`, etc. — subscribe to react to topology changes | Polling Sentinel for status instead of subscribing — misses events, adds latency |
| `SENTINEL failover` | Trigger a controlled failover without a crash | Zero data loss — waits for full sync before promoting; used for planned maintenance | Using `SHUTDOWN` on primary for maintenance instead — triggers unplanned failover |
| Dedicated Sentinel connection | Pub/Sub subscriber connection specifically for Sentinel | Like Redis Pub/Sub, Sentinel streams messages — use a dedicated connection | Mixing regular commands with Sentinel Pub/Sub on one connection |
| `announce-ip` / `announce-port` | Override what IP/port Sentinel advertises to peers | Required in Docker/NAT environments where internal IPs aren't routable between nodes | Forgetting `announce-ip` in Docker — Sentinels tell peers their internal container IP |

**Tip for interviews:** Five things separate strong candidates on Redis Sentinel: (1) explaining **SDOWN vs ODOWN precisely** — that SDOWN is a single Sentinel's local assessment (no failover triggered), that ODOWN requires at least `quorum` Sentinels to independently confirm the primary is unreachable, and that this two-phase detection prevents false positives from single-node network issues while requiring the quorum to be less than or equal to the number of surviving Sentinels for failover to work; (2) knowing **why 3 Sentinels is the minimum** — that 1 Sentinel is a single point of failure, that 2 Sentinels either can't reach quorum (if one fails) or have split-vote in leader election, and that 3 gives you both quorum=2 safety and majority=2 leader election with tolerance for 1 Sentinel failure, and that the general rule is always use odd numbers; (3) articulating **the data loss window during unplanned failover** — that the maximum data lost equals the replication lag at the moment of primary failure (bytes of writes shipped to primary but not yet received by any replica), that `min-replicas-to-write 1` with `min-replicas-max-lag 10` limits this to at most 10 seconds of writes by making the primary stop accepting writes when replicas lag too much, and that this trades brief write unavailability for reduced data loss; (4) knowing **the client discovery pattern** — that applications must connect to Sentinel addresses (not Redis addresses), call `SENTINEL get-master-addr-by-name` to discover the current primary, connect to that address, and repeat the discovery on connection failure, and that this is why Sentinel addresses are stable configuration while the Redis primary address changes during failover; and (5) being able to explain **why failover doesn't trigger** when diagnosing — the two most common causes being quorum not reached (check if Sentinels can communicate with each other and with Redis), and `down-after-milliseconds` set too low causing SDOWN to flip-flop before quorum can be gathered, with the Sentinel log (`+sdown` followed immediately by `-sdown` events) as the diagnostic evidence.
