## Section 1: Fundamentals

**Q1. How does Redis organize its type system and what are internal encodings?**

A: Redis exposes nine user-facing data types, but each type uses one of several **internal encodings** depending on the data's size and content. Redis switches encoding automatically when thresholds are crossed — the interface stays the same, but the memory layout and performance characteristics change:

```
User-facing type    Internal encodings (smallest to largest)
─────────────────────────────────────────────────────────────────────────────
String              int → embstr → raw
List                listpack → quicklist
Set                 intset → listpack → hashtable
Sorted Set          listpack → skiplist + hashtable
Hash                listpack → hashtable
HyperLogLog         sparse → dense (internal sub-types)
Stream              radix tree of listpacks
Bitmap              (operations on String type)
Geospatial          (operations on Sorted Set type)

# Inspect the actual internal encoding of a key:
OBJECT ENCODING mykey
# → "embstr"  (String ≤44 bytes)
# → "listpack" (small Hash/List/Set/ZSet)
# → "quicklist" (larger List)
# → "skiplist"  (larger Sorted Set)
# → "hashtable" (larger Hash or Set)
# → "intset"    (Set containing only integers)
```

**Why internal encodings matter:**
```
listpack vs hashtable for a Hash with 5 fields vs 200 fields:

5 fields (listpack):
  Memory: ~200 bytes total (compact linear scan)
  HGET: O(N) linear scan — fast because N is small and data fits in CPU cache
  Perfect for: user profile with a few fields

200 fields (hashtable):
  Memory: ~6KB (separate allocations, pointer overhead)
  HGET: O(1) hash lookup — necessary because linear scan over 200 would be slow
  Perfect for: product catalog with many attributes

The thresholds (configurable in redis.conf):
  hash-max-listpack-entries  128   # Switch Hash to hashtable above this
  hash-max-listpack-value     64   # bytes — switch if any field/value exceeds this
  list-max-listpack-size     128   # entries per listpack node in quicklist
  zset-max-listpack-entries  128   # Switch Sorted Set to skiplist above this
  zset-max-listpack-value     64   # bytes
  set-max-intset-entries     512   # integers — switch Set to hashtable above this
  set-max-listpack-entries   128   # Redis 7.0+: listpack stage for Set
```

**Q2. What is a Redis String and what makes it more than a simple cache value?**

A: A String is Redis's most versatile type — it stores any binary-safe sequence of bytes up to 512 MB. Beyond simple key-value caching, Strings support atomic numeric operations, conditional writes, and time-to-live semantics that enable complex patterns in a single round trip:

```bash
# ── Basic get/set ─────────────────────────────────────────────────────────────
SET user:session:abc123 '{"userId":"1","role":"admin"}' EX 3600
GET user:session:abc123

# ── Atomic options on SET ─────────────────────────────────────────────────────
SET lock:order:999 "worker-1" NX EX 30
# NX: Only set if the key does NOT exist (atomically)
# XX: Only set if the key DOES exist
# EX: Expire in seconds
# PX: Expire in milliseconds
# EXAT: Expire at Unix timestamp (seconds)
# GET: Return old value before overwriting (Redis 6.2+)

SET lock:order:999 "worker-2" NX EX 30
# → nil (worker-1 holds the lock)
# This is the foundation of simple distributed locking

# ── Atomic counter operations ──────────────────────────────────────────────────
INCR  page:views:/home          # Atomic increment by 1
INCRBY page:views:/home 10      # Atomic increment by N
DECR  inventory:product:42
DECRBY inventory:product:42 5   # Decrement by N
INCRBYFLOAT temperature:sensor1 0.5  # Float increment (stored as string internally)
# All atomic: safe under concurrent access without locks

# ── Multi-key operations (single round trip) ──────────────────────────────────
MSET user:1:name "Alice" user:1:email "alice@example.com" user:2:name "Bob"
MGET user:1:name user:1:email user:2:name
# → ["Alice", "alice@example.com", "Bob"]

# ── Append and length ─────────────────────────────────────────────────────────
APPEND log:today "2024-01-15T10:00:00 GET /api/users\n"
STRLEN log:today    # → length in bytes

# ── Get with expiry extension (Redis 6.2+) ────────────────────────────────────
GETEX user:session:abc123 EX 3600    # Get + reset TTL (touch pattern)
GETEX user:session:abc123 PERSIST    # Get + remove TTL

# ── Internal encoding observation ─────────────────────────────────────────────
SET counter 42
OBJECT ENCODING counter           # → "int" (stored as integer, not string)

SET short_str "hello"
OBJECT ENCODING short_str         # → "embstr" (≤44 bytes: single allocation)

SET long_str "this string is longer than 44 bytes total..."
OBJECT ENCODING long_str          # → "raw" (>44 bytes: two allocations)
```

## Section 2: List

**Q3. How does a Redis List work internally and what are its primary use cases?**

A: A Redis List is an ordered sequence of string elements, optimized for push/pop operations at both ends. Internally it uses a **quicklist** — a doubly-linked list of **listpack** nodes (compact arrays):

```bash
# ── Pushing elements ──────────────────────────────────────────────────────────
LPUSH queue:emails msg1 msg2 msg3     # Left push: msg3 is now HEAD
RPUSH queue:emails msg4               # Right push: msg4 is now TAIL
# After above: [msg3, msg2, msg1, msg4]

# ── Popping elements ─────────────────────────────────────────────────────────
LPOP queue:emails       # → "msg3" (removes from left)
RPOP queue:emails       # → "msg4" (removes from right)
LPOP queue:emails 3     # Redis 6.2+: pop N elements at once → ["msg2", "msg1"]

# ── Non-destructive reads ──────────────────────────────────────────────────────
LRANGE messages:user:1  0 -1    # All elements (0=first, -1=last)
LRANGE messages:user:1  0  9    # First 10 elements
LRANGE messages:user:1 -5 -1   # Last 5 elements
LINDEX messages:user:1  0       # Element at index 0 (O(N))
LLEN   messages:user:1          # Length

# ── List as a FIFO queue (task queue) ──────────────────────────────────────────
# Producer:
RPUSH jobs:email '{"to":"alice@example.com","subject":"Welcome"}'
# Consumer:
LPOP  jobs:email                # First in, first out

# ── List as a LIFO stack ──────────────────────────────────────────────────────
# Push:  LPUSH stack item
# Pop:   LPOP  stack

# ── Trim to bounded length (sliding window log) ───────────────────────────────
LPUSH recent:actions:user:1 "viewed product 42"
LTRIM recent:actions:user:1 0 99    # Keep only the 100 most recent actions
# Call LTRIM after every LPUSH to maintain a capped list

# ── Atomic move between lists (reliable queue pattern) ────────────────────────
LMOVE queue:jobs queue:jobs:in-progress LEFT LEFT
# Atomically pop from left of source, push to left of destination
# If worker crashes: item stays in jobs:in-progress for reprocessing

# ── Time complexity summary ───────────────────────────────────────────────────
# LPUSH / RPUSH / LPOP / RPOP: O(1)
# LINDEX by index: O(N) — avoid on large lists
# LRANGE: O(S+N) where S is start offset
# LLEN: O(1)
```

**Q4. What are BLPOP and BRPOP and when do you use blocking pops?**

A: `BLPOP` and `BRPOP` are the blocking variants of `LPOP`/`RPOP`. If the list is empty, the client blocks (waits) until an element is pushed or the timeout expires — instead of polling in a loop:

```bash
# Non-blocking poll (inefficient):
# while True:
#   item = LPOP queue:jobs
#   if item: process(item)
#   else: sleep(0.1)  # Wastes 100ms and hammers Redis with empty polls

# Blocking pop (efficient — no polling):
BLPOP queue:jobs 30    # Block for up to 30 seconds waiting for a job
# Returns when:
#   a) An element is pushed to queue:jobs → [key, value] returned
#   b) Timeout expires → nil returned
# 0 timeout: block indefinitely

# Multiple queues with priority (check queue:urgent before queue:normal):
BLPOP queue:urgent queue:normal 30
# Redis checks queue:urgent first, then queue:normal
# Returns from the FIRST non-empty key found

# Reliable consumer pattern:
BRPOPLPUSH queue:jobs queue:jobs:processing 30
# Deprecated in Redis 6.2 — use BLMOVE instead:
BLMOVE queue:jobs queue:jobs:processing LEFT LEFT 30
# Atomically: pop from queue:jobs, push to queue:jobs:processing
# Worker periodically checks queue:jobs:processing for stale items

# LMPOP (Redis 7.0+): pop from first non-empty list in a list of keys
LMPOP 3 queue:high queue:medium queue:low LEFT COUNT 10
# → pops up to 10 items from the first non-empty queue
```

## Section 3: Set

**Q5. What is a Redis Set and what operations make it powerful for social graph problems?**

A: A Redis Set is an unordered collection of unique strings. Its constant-time membership testing and set-algebra operations (union, intersection, difference) make it ideal for problems involving relationships between entities:

```bash
# ── Basic operations ──────────────────────────────────────────────────────────
SADD   tags:post:1 "redis" "database" "nosql"    # Add members (returns count added)
SREM   tags:post:1 "nosql"                        # Remove member
SCARD  tags:post:1                                # Cardinality (count): → 2
SISMEMBER tags:post:1 "redis"                     # Membership test: → 1 (true)
SMISMEMBER tags:post:1 "redis" "mysql" "nosql"   # Bulk membership: → [1, 0, 0]
SMEMBERS tags:post:1                              # All members (unordered)

# ── Social graph: following/followers ────────────────────────────────────────
SADD following:alice  "bob" "carol" "dave"
SADD following:bob    "alice" "carol" "eve"
SADD followers:alice  "bob"
SADD followers:bob    "alice" "carol"

# Mutual followers (both follow each other):
SINTER following:alice following:bob
# → {"carol"}  (both alice and bob follow carol)

# People alice follows but bob doesn't (unique to alice's feed):
SDIFF following:alice following:bob
# → {"dave"}

# Everyone either follows:
SUNION following:alice following:bob
# → {"carol", "dave", "eve", "alice", "bob"}

# "People you may know" — people bob follows who also follow alice:
SINTER following:bob followers:alice
# → {"carol"} (carol follows alice and bob follows carol)

# ── Store results in a new key (for subsequent operations) ─────────────────
SINTERSTORE result:mutual:alice:bob following:alice following:bob
EXPIRE result:mutual:alice:bob 60   # Cache the expensive result briefly

# ── Random sampling ───────────────────────────────────────────────────────────
SRANDMEMBER tags:post:1 3      # 3 random members (no removal, can repeat if N < 0)
SPOP tags:post:1 2             # Remove AND return 2 random members

# Time complexity:
# SADD, SREM, SISMEMBER: O(1) average
# SCARD: O(1)
# SMEMBERS, SUNION, SINTER, SDIFF: O(N) — avoid SMEMBERS on large sets
# SINTERSTORE: O(N*M) where N=smallest set, M=number of sets
```

## Section 4: Sorted Set

**Q6. What is a Redis Sorted Set, what internal data structure enables its range operations, and what is the skip list?**

A: A Sorted Set is a collection where every member is associated with a floating-point **score**. Members are unique but scores can repeat. Members are always stored in score order, enabling efficient range queries by score or by rank:

```bash
# ── Adding and inspecting elements ────────────────────────────────────────────
ZADD leaderboard 1500.0 "player:alice"
ZADD leaderboard 2300.0 "player:bob"
ZADD leaderboard  900.0 "player:carol"
ZADD leaderboard 2300.0 "player:dave"    # Same score as bob — lexicographic order for ties

# Flags on ZADD:
# NX: Only add if member does NOT exist
# XX: Only update if member DOES exist
# GT: Only update if new score is GREATER than current
# LT: Only update if new score is LESS than current
# CH: Return number of elements changed (added + updated) instead of just added

ZADD leaderboard GT 2500.0 "player:alice"  # Update only if 2500 > 1500 ✓

ZSCORE   leaderboard "player:alice"   # → "2500"
ZRANK    leaderboard "player:carol"   # → 0 (0-indexed, ascending: carol has lowest score)
ZREVRANK leaderboard "player:alice"   # → 0 (0-indexed, descending: alice has highest)
ZINCRBY  leaderboard 100 "player:carol"   # Atomic increment: carol's score → 1000

# ── Range queries (the core power of Sorted Sets) ─────────────────────────────
# By rank (position):
ZRANGE leaderboard 0 -1                     # All: ascending score order
ZRANGE leaderboard 0 -1 WITHSCORES          # With scores
ZRANGE leaderboard 0  9 REV WITHSCORES      # Top 10: descending order (Redis 6.2+)

# By score:
ZRANGE leaderboard 1000 2000 BYSCORE            # Members with score 1000–2000
ZRANGE leaderboard "(1000" 2000 BYSCORE         # Exclusive lower bound
ZRANGE leaderboard 2000 1000 BYSCORE REV        # Descending by score
ZRANGEBYSCORE leaderboard 1000 2000 LIMIT 0 10  # Pre-6.2 syntax (still works)

# ZCARD: count of members O(1)
ZCARD leaderboard    # → 4
# ZCOUNT: count in score range O(log N)
ZCOUNT leaderboard 1000 3000   # → count of members with score [1000, 3000]
```

**The skip list — why range operations are O(log N):**
```
A skip list is a probabilistic data structure with multiple levels of linked lists.
Lower levels contain all elements; higher levels contain express lanes that skip ahead:

Level 3: carol ─────────────────────────────── alice
Level 2: carol ──────────── bob ─────────────── alice
Level 1: carol ─── dave ─── bob ─── [others] ─── alice   (all elements, sorted by score)

Searching for rank of "alice":
  Start at Level 3: carol → alice in 1 jump
  Used express lane to skip 3 elements — O(log N) total jumps

Without skip list (linked list): O(N) sequential scan from carol to alice
With skip list: O(log N) — jumps to the right neighborhood, then scans

Redis's internal Sorted Set representation for large sets:
  - Skip list for score-ordered range operations: ZRANGE, ZRANGEBYSCORE
  - Hash table for O(1) member-to-score lookup: ZSCORE, ZINCRBY
  - Both structures maintained in sync — writes update both
  - Memory cost: ~2x a plain sorted structure, but enables both O(1) lookup and O(log N) ranges
```

**Q7. How do you implement a leaderboard and a sliding window rate limiter with Sorted Sets?**

A:

```bash
# ── LEADERBOARD ──────────────────────────────────────────────────────────────

# Update score (add points from game round):
ZADD leaderboard:week:2024-W3 INCR 350 "player:alice"
# INCR flag: increment existing score instead of replacing

# Top 10 players with scores:
ZRANGE leaderboard:week:2024-W3 0 9 REV WITHSCORES
# → [("player:bob", 2300), ("player:alice", 2500), ...]

# A specific player's rank (1-indexed for display):
ZREVRANK leaderboard:week:2024-W3 "player:carol"
# → 2 (0-indexed) → display as rank 3

# Players within 100 points of a given score (nearby leaderboard):
ZSCORE leaderboard:week:2024-W3 "player:alice"   # → 2500
ZRANGEBYSCORE leaderboard:week:2024-W3 2400 2600 WITHSCORES

# Weekly reset: copy to historical, reset current
RENAME leaderboard:week:2024-W3 leaderboard:archive:2024-W3
EXPIRE leaderboard:archive:2024-W3 2592000   # Keep 30 days

# ── SLIDING WINDOW RATE LIMITER ───────────────────────────────────────────────
# Allow 100 requests per 60 seconds per user, sliding window

function isRateLimited(userId, limit=100, windowMs=60000):
  key = "ratelimit:" + userId
  now = currentTimeMilliseconds()
  windowStart = now - windowMs

  pipeline:
    ZREMRANGEBYSCORE key 0 windowStart    # Remove requests outside window
    ZADD key now (now + random_suffix)    # Add current request (score=timestamp)
    ZCARD key                              # Count requests in window
    EXPIRE key 60                          # Clean up idle keys

  count = results[2]
  return count > limit

# Explanation:
# Score = timestamp in ms
# ZREMRANGEBYSCORE removes entries older than the window
# ZCARD counts remaining (recent) entries
# All operations in a pipeline = single round trip + atomic via Lua:

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window_start = now - tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', key, 0, window_start)
redis.call('ZADD', key, now, now .. '-' .. math.random())
local count = redis.call('ZCARD', key)
redis.call('EXPIRE', key, math.ceil(tonumber(ARGV[2]) / 1000) + 1)
return count

# Why Sorted Set beats simple counter for rate limiting:
# Counter approach (INCR + EXPIRE): fixed window — can allow 2× burst at window boundary
# At :59s: 100 requests (window 1). At :01s: 100 more requests (window 2). 200 in 2s.
# Sorted Set sliding window: truly rolling — always exactly 60s lookback, no burst spike
```

## Section 5: Hash

**Q8. What is a Redis Hash and how does it compare to storing each field as a separate String key?**

A: A Hash is a collection of field-value pairs stored under a single Redis key — a map within a key. For small hashes, it uses a compact listpack encoding that is dramatically more memory-efficient than separate String keys:

```bash
# ── Basic operations ──────────────────────────────────────────────────────────
HSET   user:1000 name "Alice" email "alice@example.com" role "admin" score 1500
HGET   user:1000 name                    # → "Alice"
HMGET  user:1000 name email              # → ["Alice", "alice@example.com"]
HDEL   user:1000 score                   # Remove a field
HEXISTS user:1000 role                   # → 1 (field exists)
HLEN   user:1000                         # → 3 (number of fields)

HGETALL user:1000
# → ["name", "Alice", "email", "alice@example.com", "role", "admin"]
# Flat list: field, value, field, value...

HKEYS user:1000   # → ["name", "email", "role"]
HVALS user:1000   # → ["Alice", "alice@example.com", "admin"]

# ── Atomic numeric operations on fields ───────────────────────────────────────
HINCRBY    user:1000 login_count 1        # Increment integer field
HINCRBYFLOAT user:1000 average_rating 0.2 # Increment float field

# ── Memory comparison: Hash vs individual Strings ──────────────────────────────
# Scenario: 1 million users, 5 fields each

# Approach A: Individual String keys (5M keys):
# user:1000:name   → "Alice"
# user:1000:email  → "alice@example.com"
# ... 5 keys per user
# Memory per key: ~70 bytes overhead (key, expiry, pointer)
# Total: 5M × 70B = 350MB OVERHEAD ALONE before even storing values
# Plus each key-value pair: ~50B average value = 250MB
# TOTAL: ~600MB for 1M users

# Approach B: Hash per user (1M keys, each a small hash):
# user:1000 → {name: Alice, email: alice@example.com, role: admin}
# When hash has ≤128 fields AND all values ≤64 bytes → LISTPACK ENCODING
# Listpack: ~35 bytes base + ~25 bytes per field-value pair
# Per user: 35 + 5×25 = 160 bytes
# Total: 1M × 160B = 160MB
# SAVING: ~75% less memory vs individual String keys

# ── Scanning large hashes without blocking ────────────────────────────────────
HSCAN user:1000 0 MATCH "score*" COUNT 10
# Returns: [next_cursor, [field, value, field, value, ...]]
# cursor=0 means scan complete

# ── Per-field TTL (Redis 7.4+) ────────────────────────────────────────────────
HEXPIRE user:1000 3600 FIELDS 2 temp_token reset_code
# Set TTL on individual hash fields (new in Redis 7.4)
```

## Section 6: HyperLogLog

**Q9. What is HyperLogLog, what does it trade for its efficiency, and when is it appropriate?**

A: HyperLogLog is a probabilistic algorithm for estimating the **cardinality** (number of distinct elements) of a set. It uses a fixed ~12 KB of memory regardless of how many unique elements have been added — at the cost of a ~0.81% standard error:

```bash
# ── Basic operations ──────────────────────────────────────────────────────────
PFADD visitors:2024-01-15 "user:1001" "user:1002" "user:1003"
# → 1 (internal representation changed — new distinct elements added)

PFADD visitors:2024-01-15 "user:1001"   # Duplicate
# → 0 (internal representation unchanged — user:1001 already counted)

PFCOUNT visitors:2024-01-15
# → 3 (approximately — within 0.81% error)

# Multi-key count (union cardinality):
PFADD visitors:2024-01-14 "user:1002" "user:1004" "user:1005"
PFCOUNT visitors:2024-01-14 visitors:2024-01-15
# → approximately 5 (union: 1001, 1002, 1003, 1004, 1005)

# Merge multiple HyperLogLogs into one:
PFMERGE visitors:week:2024-W3 visitors:2024-01-14 visitors:2024-01-15
PFCOUNT visitors:week:2024-W3   # Weekly unique visitor estimate

# ── Memory efficiency at scale ─────────────────────────────────────────────────
# Tracking 100 million unique visitors using a Set:
# SET: 100M strings × ~50 bytes each = ~5 GB per day
# HyperLogLog: exactly 12 KB regardless of cardinality
# Cost: ≤0.81% error — "1,000,000 vs 1,008,100" — acceptable for analytics

# ── What HyperLogLog CANNOT do ─────────────────────────────────────────────────
# ✗ Retrieve individual elements (probabilistic, not stored)
# ✗ Remove elements (add-only structure)
# ✗ Provide exact counts (inherent error)
# ✗ Check if a specific element was added (use Bloom filter for that)

# ── When to use HyperLogLog ────────────────────────────────────────────────────
# ✓ Daily/weekly/monthly unique visitors (analytics)
# ✓ Unique IP addresses that hit an endpoint (rate limiting tier)
# ✓ Distinct search queries processed
# ✓ Unique users in an A/B test (approximate cohort sizing)
# ✓ Any cardinality question where 1% error is acceptable and memory matters

# ── Alternatives for different requirements ───────────────────────────────────
# Exact count, small set: Redis Set (SCARD)
# Exact count, large set: Sorted Set with member-as-score trick or external DB
# Membership test (is X in set?): Bloom filter (Redis Bloom module)
# Cardinality + membership: Cuckoo filter (Redis Bloom module)
```

## Section 7: Streams

**Q10. What is a Redis Stream and how does it differ structurally from a List used as a queue?**

A: A Stream is a persistent, append-only log — the Redis equivalent of Kafka topics or an event sourcing log. Unlike a List (where elements are destroyed on pop), Stream entries remain after being read. Multiple consumer groups can independently process the same entries:

```bash
# ── Adding entries (XADD) ─────────────────────────────────────────────────────
XADD events:orders * \
  orderId "order-9999" \
  userId "user-1001" \
  total "99.99" \
  status "placed"
# * = auto-generate ID: <millisecondsTimestamp>-<sequenceNumber>
# → "1705312800000-0"  (15-digit ms timestamp + sequence for same-ms entries)

# Manual ID (must be monotonically increasing):
XADD events:orders 1705312800001-0 orderId "order-10000" total "49.99"

# Capped stream (keep last N entries or entries within time window):
XADD events:orders MAXLEN ~ 10000 * orderId "order-10001" total "29.99"
# ~ = approximate trimming (more efficient; Redis rounds to listpack boundaries)

# ── Reading entries ────────────────────────────────────────────────────────────
XLEN events:orders    # → number of entries

XRANGE events:orders - +           # All entries (oldest first)
XRANGE events:orders - + COUNT 10  # First 10 entries
XRANGE events:orders 1705312800000-0 +   # From specific ID onwards

XREVRANGE events:orders + - COUNT 5     # Latest 5 entries

# Read new entries since last seen (non-blocking):
XREAD COUNT 10 STREAMS events:orders 1705312799999-0
# Returns entries with ID > 1705312799999-0

# Blocking read — wait for new entries:
XREAD BLOCK 5000 COUNT 1 STREAMS events:orders $
# $ = "new entries since I started listening" (like TAIL -F)
# 5000 = block for 5 seconds max

# ── List vs Stream comparison ──────────────────────────────────────────────────
# Feature                  List            Stream
# ─────────────────────────────────────────────────────────────────────────────
# After read (pop)         Entry deleted   Entry persists
# Multiple consumers       Compete for each item  Can have independent groups
# Message ordering         FIFO            Append-only log with IDs
# Replay past messages     ✗ (destructive)  ✓ (XRANGE from past ID)
# Consumer acknowledgment  ✗               ✓ (XACK)
# Pending/unacked messages ✗               ✓ (PEL - Pending Entry List)
# Memory bound             LTRIM manually  MAXLEN or MINID
# Blocking wait            BLPOP           XREAD BLOCK 0 ... $ or consumer group
```

**Q11. What are consumer groups in Redis Streams and how do they enable at-least-once delivery?**

A: A consumer group is a subscription model where multiple workers can cooperate to process a stream in parallel, with each entry delivered to exactly one consumer at a time — and a built-in mechanism to recover from consumer failures:

```bash
# ── Creating a consumer group ─────────────────────────────────────────────────
XGROUP CREATE events:orders group:order-processor $ MKSTREAM
# $ = start from the latest entry (don't reprocess historical entries)
# 0 = start from the beginning of the stream (process all historical entries)
# MKSTREAM: create the stream if it doesn't exist

# ── Consuming messages in a group ─────────────────────────────────────────────
# Worker 1 reads up to 10 unprocessed messages:
XREADGROUP GROUP group:order-processor consumer:worker-1 COUNT 10 STREAMS events:orders >
# > = "give me undelivered messages" (the special pending ID)
# Returns entries, marks them as "pending" for consumer:worker-1

# Worker 2 reads independently:
XREADGROUP GROUP group:order-processor consumer:worker-2 COUNT 10 STREAMS events:orders >
# Gets DIFFERENT entries than worker-1 (fan-out within the group)

# ── Acknowledging processed messages ──────────────────────────────────────────
XACK events:orders group:order-processor 1705312800000-0 1705312800001-0
# Removes from PEL (Pending Entry List) — "I successfully processed these"

# ── Inspecting pending messages ───────────────────────────────────────────────
XPENDING events:orders group:order-processor - + 10
# Shows: [entry-id, consumer-name, elapsed-ms-since-delivery, delivery-count]
# delivery-count > 1 means this was retried (consumer failed or was slow)

# ── Claiming abandoned messages (consumer crashed) ─────────────────────────────
XAUTOCLAIM events:orders group:order-processor consumer:worker-3 60000 0-0
# 60000ms = min idle time before claiming
# Claims ALL messages idle > 60 seconds, assigns to worker-3
# Previous: XCLAIM (manual, one-by-one) — XAUTOCLAIM is more efficient

# ── Full at-least-once delivery lifecycle ─────────────────────────────────────
# 1. Worker reads message (entry enters PEL, delivery-count=1)
# 2a. Worker processes successfully → XACK → removed from PEL ✓
# 2b. Worker crashes → message stays in PEL, idle time grows
# 3. Another worker: XAUTOCLAIM → claims the idle message, delivery-count=2
# 4. If delivery-count exceeds threshold → move to dead letter stream

async function processWithConsumerGroup(workerId: string): Promise<void> {
  const MAX_DELIVERY_COUNT = 3;

  while (true) {
    // Read new messages
    const entries = await redis.xreadgroup(
      'GROUP', 'group:order-processor', `worker:${workerId}`,
      'COUNT', '10', 'BLOCK', '2000',
      'STREAMS', 'events:orders', '>'
    );

    if (!entries) continue;  // Timeout, no new messages

    for (const [streamKey, messages] of entries) {
      for (const [id, fields] of messages) {
        try {
          await processOrder(parseFields(fields));
          await redis.xack('events:orders', 'group:order-processor', id);
        } catch (err) {
          // Don't ACK → stays in PEL → will be reclaimed by XAUTOCLAIM
          logger.error(`Failed to process ${id}`, err);
        }
      }
    }

    // Periodically check for and reclaim abandoned messages:
    const [, claimed] = await redis.xautoclaim(
      'events:orders', 'group:order-processor', `worker:${workerId}`,
      '30000', '0-0', 'COUNT', '10'
    );
    // Process claimed messages too...
  }
}
```

## Section 8: Bitmaps

**Q12. What are Redis Bitmaps and how do they achieve extreme memory efficiency?**

A: Bitmaps are not a separate Redis type — they are **bit-level operations on String values**. Each bit in a String can be independently set or cleared, creating an array of boolean flags indexed by offset. The memory efficiency comes from packing 8 boolean values into a single byte:

```bash
# ── Basic bit operations ──────────────────────────────────────────────────────
SETBIT user:active:2024-01-15 1001 1   # Mark user 1001 as active on Jan 15
SETBIT user:active:2024-01-15 1002 1   # Mark user 1002
SETBIT user:active:2024-01-15 5000 1   # Mark user 5000
GETBIT user:active:2024-01-15 1001     # → 1 (was active)
GETBIT user:active:2024-01-15 9999     # → 0 (was not active)

# Count all active users on a specific day:
BITCOUNT user:active:2024-01-15        # → 3

# Count active users in a specific user ID range (byte range for large bitmaps):
BITCOUNT user:active:2024-01-15 0 999  # Users 0-7999 (byte 0 to byte 999)

# Find the FIRST active user (first 1 bit):
BITPOS user:active:2024-01-15 1        # → 1001
# Find first INACTIVE user:
BITPOS user:active:2024-01-15 0        # → 0 (first user not marked)

# ── Set operations across days (BITOP) ────────────────────────────────────────
# Users active on BOTH Jan 15 AND Jan 16 (retained users):
BITOP AND retained:jan15-16 user:active:2024-01-15 user:active:2024-01-16
BITCOUNT retained:jan15-16    # → count of users active on both days

# Users active on Jan 15 OR Jan 16 (total unique active users):
BITOP OR total:jan15-16 user:active:2024-01-15 user:active:2024-01-16
BITCOUNT total:jan15-16

# Users active Jan 15 but NOT Jan 16 (churned users):
BITOP NOT active:jan16:inverted user:active:2024-01-16
BITOP AND churned:jan15-16 user:active:2024-01-15 active:jan16:inverted
BITCOUNT churned:jan15-16

# ── Memory efficiency calculation ─────────────────────────────────────────────
# Tracking 10 million users' daily activity:
# Set approach: 10M strings per day × ~50 bytes = 500MB per day
# Bitmap: offset = user_id → 10,000,000 bits = 1,250,000 bytes = 1.25MB per day
# Savings: 99.75% less memory

# Even sparse bitmaps: if only 1000 of 10M users are active,
# the bitmap is still 1.25MB (allocates up to the highest offset)
# HyperLogLog would use ~12KB but can't do AND/OR/NOT operations

# ── BITFIELD: sub-byte integer fields ────────────────────────────────────────
# Store multiple small integers in a single bitmap:
BITFIELD user:stats:1001 \
  SET u8 0   5   \    # 8-bit unsigned at offset 0: login count = 5
  SET u8 8   3   \    # 8-bit unsigned at offset 8: purchase count = 3
  SET u16 16 1500     # 16-bit unsigned at offset 16: points = 1500

BITFIELD user:stats:1001 INCRBY u16 16 50   # Atomic increment points by 50
BITFIELD user:stats:1001 GET u8 0            # → 5 (login count)
# Packs user stats in 4 bytes (32 bits) instead of 3 separate String keys
```

**Q13. How do you implement a comprehensive daily active user (DAU) tracking system with Bitmaps?**

A:

```typescript
// Production DAU tracking with Bitmaps + cohort analysis

class UserActivityTracker {
  constructor(private redis: Redis) {}

  // Track a user activity (O(1), sub-millisecond)
  async trackActivity(userId: number, date: string): Promise<void> {
    await this.redis.setbit(`dau:${date}`, userId, 1);
    // date format: "2024-01-15"
    // userId is the bit offset — must be a non-negative integer
    // If userId is a UUID: use a separate integer→UUID mapping
  }

  // Count DAU for a specific day (O(N/8) — fast even for millions)
  async getDailyActiveUsers(date: string): Promise<number> {
    return this.redis.bitcount(`dau:${date}`);
  }

  // Check if a specific user was active on a day (O(1))
  async wasActiveOn(userId: number, date: string): Promise<boolean> {
    const bit = await this.redis.getbit(`dau:${date}`, userId);
    return bit === 1;
  }

  // Weekly active users (union of 7 days):
  async getWeeklyActiveUsers(dates: string[]): Promise<number> {
    const destKey = `wau:${dates[0]}_${dates[dates.length-1]}`;
    await this.redis.bitop('OR', destKey, ...dates.map(d => `dau:${d}`));
    await this.redis.expire(destKey, 86400);  // Cache 24h
    return this.redis.bitcount(destKey);
  }

  // Day-over-day retention (users active on both days):
  async getRetainedUsers(day1: string, day2: string): Promise<number> {
    const destKey = `retained:${day1}:${day2}`;
    await this.redis.bitop('AND', destKey, `dau:${day1}`, `dau:${day2}`);
    await this.redis.expire(destKey, 3600);
    return this.redis.bitcount(destKey);
  }

  // New users today (active today but NOT active yesterday):
  async getNewActiveUsers(today: string, yesterday: string): Promise<number> {
    const invertedYesterday = `dau:${yesterday}:inverted`;
    const newUsersKey = `new-active:${today}`;

    const pipeline = this.redis.pipeline();
    pipeline.bitop('NOT', invertedYesterday, `dau:${yesterday}`);
    pipeline.bitop('AND', newUsersKey, `dau:${today}`, invertedYesterday);
    pipeline.bitcount(newUsersKey);
    pipeline.expire(newUsersKey, 3600);
    pipeline.expire(invertedYesterday, 3600);
    const results = await pipeline.exec();

    return results[2][1] as number;  // bitcount result
  }
}

// Bitmap keys by day: expire after 90 days
// Storage: 10M users = 1.25MB per day × 90 days = 112.5MB total
// vs Set of strings: 500MB per day × 90 days = 45GB
```

## Section 9: Geospatial

**Q14. How does Redis store geospatial data internally and what operations does it support?**

A: Redis geospatial data is stored as a **Sorted Set** where the score is a **52-bit geohash** derived from the longitude and latitude. This allows range queries over geographic proximity using the existing skip list structure, with approximately 0.6m precision:

```bash
# ── Adding locations ──────────────────────────────────────────────────────────
GEOADD stores:nyc \
  -74.0060 40.7128 "store:manhattan-1" \
  -73.9857 40.7484 "store:midtown-2"   \
  -74.0442 40.6892 "store:brooklyn-1"

# Arguments: longitude, latitude, member
# Returns: count of new members added

# ── Query position ────────────────────────────────────────────────────────────
GEOPOS stores:nyc "store:manhattan-1"
# → [[-74.0060, 40.7128]]  (returns with slight floating-point rounding)

# ── Compute distance ─────────────────────────────────────────────────────────
GEODIST stores:nyc "store:manhattan-1" "store:midtown-2" km
# → "4.2873" (distance in km)
# Units: m (meters), km, mi (miles), ft (feet)

# ── Get geohash (shareable compact location code) ────────────────────────────
GEOHASH stores:nyc "store:manhattan-1"
# → ["dr5regw3pp6"]  (11-char base32 geohash for ~2.4m precision)

# ── Search by radius or bounding box (GEOSEARCH — Redis 6.2+) ─────────────────
# Find all stores within 5km of a point:
GEOSEARCH stores:nyc \
  FROMLONLAT -74.0060 40.7128 \
  BYRADIUS 5 km \
  ASC \
  COUNT 10 \
  WITHCOORD \
  WITHDIST

# → [
#     ["store:manhattan-1", "0.0000", [-74.0060, 40.7128]],
#     ["store:midtown-2",   "4.2873", [-73.9857, 40.7484]],
#   ]

# Find all stores within a bounding box:
GEOSEARCH stores:nyc \
  FROMLONLAT -74.0060 40.7128 \
  BYBOX 20 20 km \
  ASC \
  COUNT 10

# Search from an existing member (not a coordinate):
GEOSEARCH stores:nyc \
  FROMMEMBER "store:manhattan-1" \
  BYRADIUS 5 km \
  ASC

# ── Store results in another key ───────────────────────────────────────────────
GEOSEARCHSTORE nearby:stores:user:1001 \
  stores:nyc \
  FROMLONLAT -74.0060 40.7128 \
  BYRADIUS 5 km \
  ASC COUNT 10 STOREDIST
# STOREDIST: stored key uses distance as score instead of geohash
# Allows: ZRANGE nearby:stores:user:1001 0 -1 WITHSCORES → closest to furthest

# ── Why it's a Sorted Set under the hood ──────────────────────────────────────
# GEOADD is internally a ZADD with a geohash score
ZADD stores:nyc 1791769574948687 "store:manhattan-1"  # What GEOADD actually does
OBJECT ENCODING stores:nyc   # → "ziplist" or "skiplist" (it's a Sorted Set!)

# This means: ZRANGE, ZCARD, ZREM, ZINCRBY all work on geospatial keys
ZCARD stores:nyc    # Count of locations
ZREM stores:nyc "store:closed"   # Remove a location

# Limitations:
# - Coordinates are approximate (±0.6m)
# - No 3D support (altitude ignored)
# - No polygon search (only circle/box)
# - Max ±85.05112878° latitude (Mercator projection limit)
```

```bash
set-max-listpack-value      64

# Lower zset-max-listpack-entries from 128 to 32 if:
# - You have millions of small sorted sets (e.g., per-user data)
```

## Section 11: Choosing the Right Structure

**Q16. How do you choose between Redis data structures for a given use case?**

A:

```
DECISION MATRIX:

Question: "Do I need to..."
────────────────────────────────────────────────────────────────────────────────

Store a single value (string, number, serialized JSON)?
  → String: SET/GET, INCR for counters, SETNX for distributed locks

Cache a complex object with individually updatable fields?
  → Hash (HSET/HGET) if fields are accessed individually
  → String (SET with JSON.stringify) if always read/written as a whole

Maintain an ordered, sequenced list?
  → List: LPUSH/RPUSH/LPOP/RPOP
  → Use case: queue (RPUSH + LPOP), stack (LPUSH + LPOP), activity feed (LPUSH + LTRIM)

Maintain a collection of UNIQUE items?
  → Set: SADD/SISMEMBER
  → Use case: tags, unique visitor IPs, social graph (followers)
  → Need set algebra (AND/OR/NOT)? Set over HyperLogLog

Need to count DISTINCT items approximately?
  → HyperLogLog: PFADD/PFCOUNT
  → Use case: unique visitors, distinct queries, A/B test participants
  → Not needed if exact count required (use Set) or membership test (use Bloom filter)

Maintain an ordered collection with scores/priorities?
  → Sorted Set: ZADD/ZRANGE/ZRANGEBYSCORE
  → Use case: leaderboard, rate limiter, priority queue, autocomplete prefix search

Process a stream of events with multiple consumers?
  → Stream: XADD/XREADGROUP
  → Use case: event sourcing, audit log, real-time pipeline
  → vs List: Stream persists after reading, supports consumer groups, has IDs

Track boolean states per entity ID across millions of entities?
  → Bitmap: SETBIT/GETBIT/BITCOUNT
  → Use case: DAU tracking, feature flag rollout (which users have it on)

Store location and query by proximity?
  → Geospatial: GEOADD/GEOSEARCH
  → Use case: nearby stores, driver locations, delivery zones

────────────────────────────────────────────────────────────────────────────────
TIME COMPLEXITY SUMMARY:
Operation type              Best structure    Complexity
─────────────────────────────────────────────────────────────────────────────
Key-value lookup            String            O(1)
Membership test             Set               O(1)
Range query by rank         Sorted Set        O(log N + M) where M=results
Range query by score        Sorted Set        O(log N + M)
Approximate cardinality     HyperLogLog       O(1)
Arbitrary boolean per ID    Bitmap            O(1) per bit
Proximity search            Geospatial        O(N+log M)
Multi-consumer event bus    Stream            O(log N) XADD, O(M) XREADGROUP
Pop from head/tail          List              O(1)
Set algebra (AND/OR/NOT)    Set               O(N*M) for intersection
```

```typescript
class GamingLeaderboard {
  constructor(private redis: Redis) {}

  // ── Score updates (Sorted Set core) ──────────────────────────────────────
  async addScore(playerId: string, points: number, gameId: string): Promise<void> {
    const pipeline = this.redis.pipeline();

    // Global leaderboard (all-time):
    pipeline.zincrby('leaderboard:global', points, playerId);

    // Season leaderboard (reset monthly):
    const season = this.getCurrentSeason();  // e.g., "2024-01"
    pipeline.zincrby(`leaderboard:season:${season}`, points, playerId);

    // Game-specific leaderboard:
    pipeline.zincrby(`leaderboard:game:${gameId}`, points, playerId);

    // Score history (Sorted Set with timestamp as score):
    const eventId = `${Date.now()}-${Math.random().toString(36).slice(2)}`;
    pipeline.zadd(`history:player:${playerId}`, Date.now(), `${points}:${gameId}:${eventId}`);
    pipeline.zremrangebyrank(`history:player:${playerId}`, 0, -101);  // Keep last 100

    await pipeline.exec();
  }

  // ── Global rank (O(log N)) ────────────────────────────────────────────────
  async getGlobalRank(playerId: string): Promise<{ rank: number; score: number }> {
    const [rank, score] = await Promise.all([
      this.redis.zrevrank('leaderboard:global', playerId),
      this.redis.zscore('leaderboard:global', playerId),
    ]);
    return {
      rank:  (rank ?? -1) + 1,  // Convert 0-indexed to 1-indexed, -1 if not found
      score: parseFloat(score ?? '0'),
    };
  }

  // ── Top N players (O(log N + N)) ──────────────────────────────────────────
  async getTopPlayers(n: number): Promise<Array<{ playerId: string; score: number; rank: number }>> {
    const results = await this.redis.zrange(
      'leaderboard:global', 0, n - 1,
      'REV', 'WITHSCORES'
    );
    // results: ['player:alice', '2500', 'player:bob', '2300', ...]
    const players = [];
    for (let i = 0; i < results.length; i += 2) {
      players.push({
        playerId: results[i],
        score:    parseFloat(results[i + 1]),
        rank:     i / 2 + 1,
      });
    }
    return players;
  }

  // ── Friends leaderboard — the clever part ─────────────────────────────────
  async getFriendsLeaderboard(playerId: string): Promise<FriendsRank[]> {
    // Friends stored in a Set:
    const friends = await this.redis.smembers(`friends:${playerId}`);
    const toRank  = [...friends, playerId];

    // Get scores for all friends at once:
    const scores = await this.redis.zmscore('leaderboard:global', ...toRank);

    // Sort by score in-memory (small set — friends are typically <500):
    return toRank
      .map((id, i) => ({ playerId: id, score: parseFloat(scores[i] ?? '0') }))
      .sort((a, b) => b.score - a.score)
      .map((p, i) => ({ ...p, rank: i + 1 }));
  }

  // ── Players near a specific rank (context leaderboard) ────────────────────
  async getPlayersAroundRank(playerId: string, range: number = 5): Promise<PlayerContext[]> {
    const rank = await this.redis.zrevrank('leaderboard:global', playerId);
    if (rank === null) return [];

    const start = Math.max(0, rank - range);
    const end   = rank + range;

    const results = await this.redis.zrange(
      'leaderboard:global', start, end,
      'REV', 'WITHSCORES'
    );

    return this.parseZrangeResults(results, start + 1);
  }

  // ── Pagination (for leaderboard page with 50 players) ────────────────────
  async getLeaderboardPage(page: number, pageSize: number = 50): Promise<PageResult> {
    const start = (page - 1) * pageSize;
    const end   = start + pageSize - 1;

    const [results, total] = await Promise.all([
      this.redis.zrange('leaderboard:global', start, end, 'REV', 'WITHSCORES'),
      this.redis.zcard('leaderboard:global'),
    ]);

    return {
      players:    this.parseZrangeResults(results, start + 1),
      total,
      totalPages: Math.ceil(total / pageSize),
      page,
    };
  }
}
```

**Q18. "Design a multi-layer Redis Streams event pipeline with consumer groups, dead letters, and monitoring."**

A:

```typescript
// Architecture:
// Publishers → events:raw stream
//   Consumer Group A (order-service): processes orders
//   Consumer Group B (analytics-service): processes analytics
//   Dead letter stream: events:dead-letter (for failed processing)

class EventPipeline {
  private readonly RAW_STREAM       = 'events:raw';
  private readonly DEAD_LETTER      = 'events:dead-letter';
  private readonly MAX_DELIVERIES   = 3;
  private readonly CLAIM_IDLE_MS    = 30_000;   // 30 seconds

  constructor(
    private redis:      Redis,
    private group:      string,
    private consumerId: string,
  ) {}

  // ── Publishing (O(log N)) ─────────────────────────────────────────────────
  async publish(eventType: string, payload: object): Promise<string> {
    const id = await this.redis.xadd(
      this.RAW_STREAM, 'MAXLEN', '~', '100000', '*',  // cap at ~100K entries
      'type',      eventType,
      'payload',   JSON.stringify(payload),
      'timestamp', Date.now().toString(),
      'traceId',   generateTraceId(),
    );
    return id;  // e.g., "1705312800000-0"
  }

  // ── Consuming with at-least-once delivery ─────────────────────────────────
  async consume(handler: (event: StreamEvent) => Promise<void>): Promise<void> {
    // Create consumer group if not exists:
    await this.redis.xgroup('CREATE', this.RAW_STREAM, this.group, '$', 'MKSTREAM')
      .catch(e => { if (!e.message.includes('BUSYGROUP')) throw e; });

    while (true) {
      try {
        // 1. Read new messages:
        const entries = await this.redis.xreadgroup(
          'GROUP', this.group, this.consumerId,
          'COUNT', '10', 'BLOCK', '2000',
          'STREAMS', this.RAW_STREAM, '>'
        ) as StreamReadGroupResult;

        if (entries) {
          for (const entry of entries[0][1]) {
            await this.processEntry(entry, handler);
          }
        }

        // 2. Reclaim idle messages from crashed consumers:
        await this.reclaimIdleMessages(handler);

      } catch (err) {
        logger.error('Consumer loop error', { group: this.group, consumerId: this.consumerId, err });
        await sleep(1000);
      }
    }
  }

  private async processEntry(
    [id, rawFields]: [string, string[]],
    handler: (event: StreamEvent) => Promise<void>
  ): Promise<void> {
    const fields = parseStreamFields(rawFields);
    const event: StreamEvent = {
      id,
      type:      fields.type,
      payload:   JSON.parse(fields.payload),
      timestamp: parseInt(fields.timestamp),
      traceId:   fields.traceId,
    };

    try {
      await handler(event);
      await this.redis.xack(this.RAW_STREAM, this.group, id);
      logger.debug('Processed', { id, type: event.type });

    } catch (err) {
      // Check delivery count — if exceeded, send to dead letter:
      const [,pending] = await this.redis.xpending(
        this.RAW_STREAM, this.group, id, id, 1
      ) as XPendingResult;

      const deliveryCount = pending?.[0]?.[3] ?? 1;

      if (deliveryCount >= this.MAX_DELIVERIES) {
        await this.sendToDeadLetter(id, event, err as Error);
        await this.redis.xack(this.RAW_STREAM, this.group, id);  // Remove from PEL
        logger.error('Sent to dead letter', { id, deliveryCount, err });
      } else {
        logger.warn('Processing failed, will retry', { id, deliveryCount, err });
        // Don't ACK — stays in PEL, will be reclaimed
      }
    }
  }

  private async reclaimIdleMessages(
    handler: (event: StreamEvent) => Promise<void>
  ): Promise<void> {
    const [nextId, entries] = await this.redis.xautoclaim(
      this.RAW_STREAM, this.group, this.consumerId,
      this.CLAIM_IDLE_MS, '0-0', 'COUNT', '10'
    ) as XAutoclaimResult;

    for (const entry of entries) {
      await this.processEntry(entry, handler);
    }
  }

  private async sendToDeadLetter(
    originalId: string,
    event:      StreamEvent,
    err:        Error
  ): Promise<void> {
    await this.redis.xadd(
      this.DEAD_LETTER, 'MAXLEN', '~', '10000', '*',
      'originalId',    originalId,
      'group',         this.group,
      'type',          event.type,
      'payload',       JSON.stringify(event.payload),
      'error',         err.message,
      'failedAt',      Date.now().toString(),
    );
  }

  // ── Monitoring ────────────────────────────────────────────────────────────
  async getMetrics(): Promise<StreamMetrics> {
    const [streamLen, pendingSummary] = await Promise.all([
      this.redis.xlen(this.RAW_STREAM),
      this.redis.xpending(this.RAW_STREAM, this.group) as Promise<XPendingSummary>,
    ]);

    return {
      streamLength:       streamLen,
      pendingCount:       pendingSummary[0],    // Total pending in this group
      oldestPendingMs:    pendingSummary[1] ? Date.now() - parseInt(pendingSummary[1]) : 0,
      deadLetterLength:   await this.redis.xlen(this.DEAD_LETTER),
      lagBehindLatest:    streamLen - (pendingSummary[2] || 0),
    };
  }
}
```

| **Sorted Set** | listpack → skiplist+hashtable | ZADD, ZRANGE, ZRANGEBYSCORE, ZINCRBY, ZREVRANK | O(log N) write/lookup, O(log N+M) range | Leaderboard, rate limiter, priority queue, autocomplete |
| **Hash** | listpack → hashtable | HSET, HGET, HMGET, HINCRBY, HGETALL | O(1) per field (hashtable), O(N) scan | User profile, object storage, per-field counters |
| **HyperLogLog** | sparse → dense | PFADD, PFCOUNT, PFMERGE | O(1) | Unique visitor count, cardinality estimation (~0.81% error) |
| **Stream** | radix tree of listpacks | XADD, XREADGROUP, XACK, XAUTOCLAIM, XPENDING | O(log N) add, O(M) read | Event sourcing, audit log, multi-consumer queue |
| **Bitmap** | (String operations) | SETBIT, GETBIT, BITCOUNT, BITOP, BITPOS | O(1) per bit, O(N/8) BITCOUNT | DAU tracking, feature flags, boolean arrays |
| **Geospatial** | (Sorted Set operations) | GEOADD, GEOSEARCH, GEODIST, GEOPOS | O(log N+M) search | Nearby stores, driver location, delivery zones |
| `w:majority` protects | Primary failover | Replication to majority before ACK | Higher latency | Financial data, user records |
| **Blocking ops** | List, Sorted Set, Stream | BLPOP, BZPOPMIN, XREAD BLOCK | O(1) when triggered | Worker queues (no polling) |
| **Atomic multi-op** | All types | MULTI/EXEC, Lua scripts, Pipeline | Varies | Avoiding race conditions |
| **Memory encoding** | Configurable thresholds | OBJECT ENCODING, MEMORY USAGE | — | Tune when millions of small keys |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing that **Bitmaps and Geospatial are not separate Redis types** — Bitmaps are bit-level operations on Strings, and Geospatial is Sorted Set with geohash scores; being able to run `ZADD myGeoKey <geohash> "location"` and `OBJECT ENCODING myGeoKey` and see `ziplist`/`skiplist` proves this; (2) the **internal encoding system** — every Redis type switches between compact (listpack/intset) and performant (hashtable/skiplist) encoding based on configurable thresholds; a Hash with 5 fields is a listpack with O(N) HGET but faster due to CPU cache locality, while a 200-field Hash uses a hashtable with O(1) HGET; tuning these thresholds can save 50%+ memory for millions of small objects; (3) the **HyperLogLog vs Set tradeoff** precisely — HyperLogLog uses ≤12KB regardless of cardinality with ~0.81% standard error, while a Set is exact but uses memory proportional to unique elements; knowing that you CANNOT retrieve individual elements or remove them from HyperLogLog (it's one-way), and that Bloom filters are the right choice when you need membership testing; (4) **Redis Streams consumer groups** vs a List queue — the critical difference is that Streams entries persist after reading (enabling replay, audit, and multiple independent consumer groups), while List items are destroyed on `LPOP`; the Pending Entry List (PEL) + `XAUTOCLAIM` combination enables at-least-once delivery when consumers crash, which a List cannot provide; and (5) the **sliding window rate limiter with Sorted Set** pattern precisely — `ZADD key <now_ms> <unique_request_id>`, `ZREMRANGEBYSCORE key 0 <window_start>`, `ZCARD key` — all in a Lua script for atomicity — which solves the "double spend at window boundary" problem that a simple INCR+EXPIRE counter has; being able to explain why the fixed-window counter allows 2× burst at the boundary while the Sorted Set approach is truly sliding.
