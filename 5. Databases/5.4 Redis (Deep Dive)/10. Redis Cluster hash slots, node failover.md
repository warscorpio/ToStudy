## Interview Q&A (5 YOE Level)

## Section 1: Why Redis Cluster Exists

**Q1. What problem does Redis Cluster solve — how does it differ from Sentinel and standalone Redis?**

A: Redis Cluster solves horizontal data partitioning. Sentinel solves high availability for a single dataset. Standalone Redis is one server with one dataset. The three are not alternatives but layers — Cluster provides both partitioning AND HA built in:

```
Three Redis deployment models:

  ┌─────────────────────────────────────────────────────────────────────┐
  │  Standalone Redis                                                    │
  │  ONE master. All data on one server.                                │
  │  Limit: single server RAM, single server throughput.                │
  │  HA: none (manual recovery on failure).                             │
  └─────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────┐
  │  Redis + Sentinel                                                    │
  │  ONE master + N replicas + M Sentinel processes.                    │
  │  Sentinel monitors master, promotes a replica on failure.           │
  │  Limit: still ONE dataset — all data on every node.                 │
  │  Scale: reads to replicas, but writes only to one master.           │
  │  HA: yes (Sentinel promotes replica if master fails).               │
  └─────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────┐
  │  Redis Cluster                                                       │
  │  N shards, each a master + optional replicas.                       │
  │  Data PARTITIONED across shards (each shard holds 1/N of data).    │
  │  Limit: multi-key operations restricted to same slot.               │
  │  Scale: writes AND reads distributed across all masters.            │
  │  HA: yes (built-in, no Sentinel needed — replicas auto-promote).   │
  └─────────────────────────────────────────────────────────────────────┘

  Minimum Redis Cluster: 3 masters + 3 replicas (6 nodes total).
  Why 3 masters minimum? Quorum for failover voting requires > N/2 masters.
  With 2 masters: if 1 fails, the remaining 1 cannot form a majority → cluster stops.
  With 3 masters: if 1 fails, 2 remain → majority quorum → failover proceeds.
```

```
Redis Cluster topology (6-node example):

  ┌───────────────────────────────────────────────────────────────────┐
  │  Master 1 (M1)              Master 2 (M2)              Master 3   │
  │  Slots 0-5460               Slots 5461-10922           (M3)       │
  │  node-1:6379                node-2:6379                Slots      │
  │       │                          │                     10923-16383 │
  │       │ replicates               │ replicates          node-3:6379 │
  │       ▼                          ▼                          │      │
  │  Replica 1 (R1)             Replica 2 (R2)             Replica 3  │
  │  node-4:6379                node-5:6379                (R3)       │
  │                                                         node-6:6379│
  └───────────────────────────────────────────────────────────────────┘

  Cluster bus: every node connects to every other node on port+10000
  (data port 6379 → cluster bus port 16379)
  Used for: gossip, failure detection, failover voting, slot migration.
  Client connections go to the DATA PORT (6379), not the cluster bus.
```

## Section 2: Hash Slots

**Q2. What are hash slots — how does a key map to a slot and then to a node?**

A: Redis Cluster divides the key space into exactly 16384 hash slots. Every key belongs to exactly one slot. Every master owns a contiguous or non-contiguous subset of slots. The two-level mapping (key → slot → node) is what makes resharding possible without full data movement:

```
Two-level mapping:

  Key ──[CRC16 → mod 16384]──► Slot ──[cluster metadata]──► Node

  Level 1: Key → Slot (deterministic, computed by CLIENT and SERVER identically)
  Level 2: Slot → Node (stored in cluster metadata, changes only during resharding)

  Why 16384 slots (not 65536 or 1048576)?
  Each node broadcasts which slots it owns in gossip heartbeat messages.
  The slot bitmap is 16384 bits = 2 KB per message.
  65536 slots: 8 KB heartbeat — too large for frequent gossip.
  16384 slots: enough granularity for ~1000 nodes (16 slots/node average).
  In practice: clusters rarely exceed 1000 nodes; 16384 is a pragmatic choice.
```

```redis
-- ── CRC16 hash slot formula ───────────────────────────────────────────────────
-- slot = CRC16(key) mod 16384
-- CRC16: CCITT variant (XMODEM), 16-bit output.
-- The result is always in [0, 16383].

-- Compute slot for a key (Redis command):
CLUSTER KEYSLOT mykey
-- → 14687  (this key belongs to slot 14687)

CLUSTER KEYSLOT user:42
-- → 5679

CLUSTER KEYSLOT order:123:items
-- → 11298

-- ── Which node owns slot 14687? ────────────────────────────────────────────────
CLUSTER NODES
-- <id> <ip:port@cport> <flags> <master> <ping-sent> <pong-recv> <epoch> <link-state> <slots>
-- a1b2c3 10.0.0.1:6379@16379 master - 0 1705312800000 1 connected 0-5460
-- d4e5f6 10.0.0.2:6379@16379 master - 0 1705312800000 2 connected 5461-10922
-- g7h8i9 10.0.0.3:6379@16379 master - 0 1705312800000 3 connected 10923-16383
-- ...

-- Slot 14687 is in range 10923-16383 → node g7h8i9 (10.0.0.3:6379).

CLUSTER SLOTS
-- Returns slot ranges with their owning nodes (deprecated, use CLUSTER SHARDS):
-- [[0, 5460, ["10.0.0.1", 6379, "a1b2c3..."], ["10.0.0.4", 6379, "j1k2l3..."]],
--  [5461, 10922, ["10.0.0.2", 6379, "d4e5f6..."], ...],
--  [10923, 16383, ["10.0.0.3", 6379, "g7h8i9..."], ...]]
-- Format: [slot_start, slot_end, [master_ip, master_port, master_id], [replica_ip, ...]]

CLUSTER SHARDS   -- Redis 7.0+ (replaces CLUSTER SLOTS)
-- Richer format including replica info, health state, and slot ranges.

-- ── Full cluster status ────────────────────────────────────────────────────────
CLUSTER INFO
-- cluster_enabled:1                   ← clustering is active
-- cluster_state:ok                    ← all slots covered, quorum healthy
-- cluster_slots_assigned:16384        ← all 16384 slots have an owner
-- cluster_slots_ok:16384              ← all assigned slots are reachable
-- cluster_slots_pfail:0               ← no slots in PFAIL state
-- cluster_slots_fail:0                ← no slots in FAIL state (would block writes)
-- cluster_known_nodes:6               ← 6 nodes known to this node
-- cluster_size:3                      ← 3 master nodes
-- cluster_current_epoch:7             ← config epoch (increments on topology changes)
-- cluster_my_epoch:3                  ← this node's epoch
-- cluster_stats_messages_sent:18492   ← gossip messages sent
-- cluster_stats_messages_received:18291

-- cluster_state: ok | fail
-- ok: all slots assigned and reachable → cluster serves requests.
-- fail: some slots have no master → cluster STOPS accepting writes to those slots.
--       Reads MAY still work if replica is accessible (depends on client config).
```

**Q3. How does hash tag work — why is it essential for multi-key operations?**

A: A hash tag overrides the key-used-for-hashing. Only the content between the first `{` and `}` pair is hashed. This forces multiple keys to the same slot, enabling cross-key operations that would otherwise fail across slots:

```
Hash tag mechanics:

  Without hash tag:
    CLUSTER KEYSLOT user:42:profile   → slot 4821  (different nodes)
    CLUSTER KEYSLOT user:42:orders    → slot 12094
    CLUSTER KEYSLOT user:42:sessions  → slot 9301
    → MGET user:42:profile user:42:orders user:42:sessions → CROSSSLOT error

  With hash tag {user:42}:
    CLUSTER KEYSLOT {user:42}:profile  → hash only "user:42" → slot 4096
    CLUSTER KEYSLOT {user:42}:orders   → hash only "user:42" → slot 4096
    CLUSTER KEYSLOT {user:42}:sessions → hash only "user:42" → slot 4096
    → All three keys on the SAME node → MGET works ✓

  Hash tag rules:
    1. Find the first '{' in the key.
    2. Find the first '}' after that '{'.
    3. If both found and the substring between them is non-empty: hash ONLY that substring.
    4. Otherwise (no '{', no '}', or empty '{}'): hash the entire key.

  Examples:
    key: "user:{42}:profile"    → hashes "42"
    key: "{user:42}:profile"    → hashes "user:42"
    key: "user:{}:profile"      → empty tag → hashes full key "user:{}:profile"
    key: "user:{42"             → no closing '}' → hashes full key
    key: "{42}:profile:{99}"    → first tag wins → hashes "42"
    key: "{}user:42"            → empty first tag → hashes full key
```

```redis
-- ── Verifying hash tags ────────────────────────────────────────────────────────
CLUSTER KEYSLOT {user:42}:profile
-- → 4096
CLUSTER KEYSLOT {user:42}:orders
-- → 4096   ← same slot ✓
CLUSTER KEYSLOT {user:42}:sessions
-- → 4096   ← same slot ✓

-- Multi-key operations now work:
MGET {user:42}:profile {user:42}:orders {user:42}:sessions
-- ✓ All on the same node → single round-trip

MSET {user:42}:profile "..." {user:42}:orders "..." {user:42}:sessions "..."
-- ✓ Atomic multi-set across these keys

-- ── Transactions (MULTI/EXEC) require same-slot keys ──────────────────────────
MULTI
GET {user:42}:profile
SET {user:42}:last_seen "2024-01-15"
EXEC
-- ✓ Both keys in slot 4096 → transaction valid

MULTI
GET {user:42}:profile
GET user:99:profile    -- Different slot! No hash tag matches user:42.
EXEC
-- EXECABORT: keys in request don't hash to the same slot.

-- ── Lua scripts and hash tags ─────────────────────────────────────────────────
-- Lua scripts in Redis Cluster: all keys accessed by the script must be in
-- the same slot. Keys must be declared as KEYS array (not computed inside script).
EVAL "return redis.call('GET', KEYS[1])" 1 {user:42}:profile
-- ✓ Key declared in KEYS[1]

-- WRONG: accessing a key computed inside the script:
EVAL "return redis.call('GET', 'user:42:profile')" 0
-- This works on standalone but in Cluster: the node receiving the command
-- may not own that key → unpredictable results or errors.

-- ── Pipelines and hash tags ────────────────────────────────────────────────────
-- Clients like ioredis automatically pipeline commands to the correct nodes.
-- Multi-key commands in a pipeline that span different slots:
-- → Client splits them into per-node batches → multiple round-trips.
-- With hash tags: → single batch to one node → one round-trip.

-- ── Common hash tag patterns ──────────────────────────────────────────────────
-- Pattern 1: User-scoped data (all user data co-located):
--   {user:42}:profile, {user:42}:settings, {user:42}:notifications
-- Pattern 2: Order-scoped data:
--   {order:123}:items, {order:123}:payment, {order:123}:shipment
-- Pattern 3: Tenant-scoped data:
--   {tenant:abc}:users, {tenant:abc}:settings, {tenant:abc}:billing
-- Pattern 4: Session data with related keys:
--   {session:xyz}:data, {session:xyz}:metadata, {session:xyz}:activity

-- ── Anti-pattern: over-using the same hash tag ────────────────────────────────
-- WRONG: using a common prefix for unrelated data:
SET {app}:user:42 "..."
SET {app}:order:123 "..."
SET {app}:product:101 "..."
-- All keys hash to the slot for "app" → ALL data on ONE node → defeats sharding.
-- Use specific, data-scoped tags, not application-wide tags.
```

## Section 3: Request Routing

**Q4. How does a client route requests to the correct node — what are `MOVED` and `ASK` redirects?**

A: Redis Cluster clients must route each command to the node that owns the key's slot. When they get it wrong, the server returns a redirect. `MOVED` means the slot permanently lives elsewhere. `ASK` means the slot is temporarily being migrated:

```
Client routing strategy:

  Naive approach (wrong): send all commands to any node.
  → Every command returns MOVED redirects → very slow.

  Smart client approach: maintain a local slot→node map.
  On startup: CLUSTER SLOTS or CLUSTER SHARDS → build the map.
  On each command: compute CRC16(key) mod 16384 → look up node → connect directly.
  On MOVED: update the map and retry → correct for future commands too.
```

```redis
-- ── MOVED redirect: permanent slot relocation ─────────────────────────────────
-- Client connects to node A (owns slots 0-5460).
-- Client sends: GET user:42:profile  (slot 4821 → owned by node A → fine)
-- Client sends: GET product:101      (slot 14687 → owned by node C, NOT node A)
-- Node A responds:
-- (error) MOVED 14687 10.0.0.3:6379
--         ↑ error type   ↑ correct slot   ↑ correct node for that slot

-- Client should:
-- 1. Update local cache: slot 14687 → 10.0.0.3:6379
-- 2. Retry the command directly against 10.0.0.3:6379.
-- 3. From now on: route all slot-14687 requests to 10.0.0.3:6379 (no more MOVED).

-- MOVED means: the slot assignment is PERMANENTLY at this other node.
-- The client's cached slot map was stale. MOVED is the correction signal.

-- ── ASK redirect: slot is being migrated ─────────────────────────────────────
-- During CLUSTER SETSLOT migration (resharding in progress):
-- Slot 7000 is being moved from Node A to Node B.
-- Some keys from slot 7000 already migrated to Node B.
-- Other keys from slot 7000 still on Node A.

-- Client sends GET to Node A for a key in slot 7000:
-- If the key is still on Node A: → returns the value normally.
-- If the key has already migrated to Node B: → Node A responds:
-- (error) ASK 7000 10.0.0.2:6379

-- Client should:
-- 1. Connect to Node B (10.0.0.2:6379).
-- 2. Send ASKING (mandatory before the command during ASK migration).
-- 3. Send the original command.
-- 4. DO NOT update the slot→node cache (migration is temporary).
--    Once migration completes, a MOVED will permanently update the map.

-- Why ASKING is required:
-- During migration, Node B is not yet the "owner" of slot 7000.
-- Normally, Node B would reject a command for slot 7000 (not its slot).
-- ASKING tells Node B: "I know you don't own this slot yet, but check your
-- local import buffer for this specific key."
-- Without ASKING: Node B returns MOVED 7000 (back to Node A) → infinite loop.

-- ── Redirect frequency in a healthy cluster ────────────────────────────────────
-- Smart clients (ioredis, redis-py cluster, Jedis): MOVED redirects are rare.
-- The client slot map is refreshed on each MOVED → correct for future commands.
-- In steady state (no resharding): MOVED redirects should be near zero.
-- During resharding: ASK redirects spike → normal, resolves when migration done.

-- Monitor redirects:
CLUSTER INFO | grep -E "redirected|moved|ask"
-- (Not directly in CLUSTER INFO, but in keyspace stats)

INFO commandstats | grep -E "moved|ask"
-- cmdstat_asked:calls=42,usec=1230  ← ASK redirects issued (during resharding)
```

## Section 4: The Gossip Protocol

**Q5. How do cluster nodes discover each other and detect failures — what is the gossip protocol?**

A: Redis Cluster uses a gossip protocol for topology discovery and failure detection. Every node periodically sends heartbeat messages to a random subset of other nodes. These messages contain the sender's view of the entire cluster — which nodes are healthy, which are failing, and which slots each node owns:

```
Gossip protocol structure:

  Every 100ms (cluster-node-timeout / 10, minimum 1s):
  Each node selects a random sample of OTHER nodes and sends PING.

  PING message contains:
  ┌──────────────────────────────────────────────────────────────────┐
  │ Sender info: node ID, IP:port, slot bitmap, epoch               │
  │ Gossip info (3 random nodes from sender's view):                 │
  │   - Node ID, IP:port, flags (master/replica/pfail/fail)         │
  │   - Last ping sent, last pong received, epoch                   │
  └──────────────────────────────────────────────────────────────────┘

  Recipients respond with PONG (same structure, from recipient's view).
  Recipients also MEET nodes they haven't seen before (cluster expansion).

  Each node maintains a table of all known nodes:
    node_id → { ip, port, flags, slots, last_pong, epoch }

  Why gossip (not a central coordinator)?
  - No single point of failure (no coordinator to fail).
  - Scales to 1000 nodes without bottleneck.
  - Eventual consistency: all nodes converge on the same view within seconds.
  - Self-healing: stale information is overwritten by fresher gossip.
```

```redis
-- ── Cluster node flags ────────────────────────────────────────────────────────
CLUSTER NODES
-- Each node entry includes flags (comma-separated):
-- master    → this node is a master
-- slave     → this node is a replica (Redis 7.0+: "replica" in some outputs)
-- myself    → this is the node you're connected to
-- fail?     → node has been PFAIL (possibly failed) — waiting for confirmation
-- fail      → node has been FAIL (majority agree it's down) → failover started
-- handshake → node just joined, handshake in progress
-- noaddr    → IP/port unknown for this node
-- noflags   → no flags (all good)

-- Example output:
-- a1b2c3 10.0.0.1:6379@16379 myself,master - 0 0 1 connected 0-5460
-- d4e5f6 10.0.0.2:6379@16379 master - 0 1705312800003 2 connected 5461-10922
-- g7h8i9 10.0.0.3:6379@16379 master,fail - 0 1705312800000 3 disconnected 10923-16383
--                                   ↑ FAIL flag: this node is confirmed failed

-- ── Failure detection timing ──────────────────────────────────────────────────
-- cluster-node-timeout: configurable (default 15000ms = 15 seconds).
-- This is the MOST IMPORTANT cluster tuning parameter.

-- Failure detection timeline:
--
-- t=0:    Node M3 crashes (power loss, OOM kill, etc.)
-- t=0:    Other nodes continue sending PING to M3.
-- t=0:    M3 doesn't respond.
-- t=15s:  cluster-node-timeout expires.
--         The first node to notice marks M3 as PFAIL (possibly failed).
--         PFAIL is a local opinion — not yet cluster-wide agreement.
-- t=15s+: Gossip spreads PFAIL opinion to other nodes via PING/PONG messages.
-- t=?:    Majority of masters (>N/2) agree M3 is PFAIL → M3 is FAIL.
--         FAIL propagation: immediate broadcast (not gradual gossip).
--         ALL nodes receive FAIL(M3) within milliseconds.
-- t=?:    M3's replicas see FAIL(M3) → start failover election.
-- t=~30s: Total time from crash to new master elected (2× cluster-node-timeout typical).

-- Tuning cluster-node-timeout:
-- Lower (e.g., 5000ms): faster failover, more sensitive to network hiccups.
-- Higher (e.g., 30000ms): fewer false positives, slower failover.
-- Recommendation: 5000-15000ms for LAN; 15000-30000ms for WAN/cloud.

CONFIG GET cluster-node-timeout
-- → cluster-node-timeout 15000

CONFIG SET cluster-node-timeout 5000  -- Faster failover (5s timeout)
```

## Section 5: Node Failover

**Q6. Walk through the complete failover process — from failure detection to a new master serving requests.**

A: Redis Cluster failover is a Raft-like distributed election. When a master is confirmed failed, its replicas race to become the new master by requesting votes from other masters. The first replica to collect a majority wins:

```
Detailed failover timeline:

  CLUSTER: 3 masters (M1, M2, M3), 3 replicas (R1→M1, R2→M2, R3→M3)

  t=0:     M3 crashes.
  t=0-15s: M1 and M2 send PING to M3. No response. Internal clock ticking.
  t=15s:   cluster-node-timeout expires for M1 and M2.
           Both flag M3 as PFAIL in their local view.
  t=15s+:  Next gossip cycle: M1 and M2 include M3=PFAIL in their PING messages.
           M1 gossips to R3: "M3 is PFAIL."
           M2 gossips to R3: "M3 is PFAIL."
  t=~16s:  R3 receives PFAIL reports from majority of masters (M1 and M2).
           R3 promotes M3 from PFAIL → FAIL.
           R3 broadcasts FAIL(M3) message to ALL cluster nodes immediately.
           (FAIL propagation is immediate broadcast, not gossip.)
  t=~16s:  All nodes receive FAIL(M3). Cluster state for slots 10923-16383: ERROR.
           Writes to those slots are rejected until failover completes.

  ── ELECTION PHASE ────────────────────────────────────────────────────────────

  t=~16s:  R3 starts failover election countdown.
           Delay before requesting votes:
           500ms + random(0-500ms) + rank × 1000ms
           rank = position of R3 among M3's replicas by replication offset
           (replica with most data = rank 0 = fastest to start election)

  t=~16.5s: R3 (rank=0, most up-to-date) sends FAILOVER_AUTH_REQUEST to all masters:
            "I want to become the new master for slots 10923-16383.
             My config epoch is 7. My replication offset is 492847."

  t=~16.5s: M1 and M2 evaluate the request:
            - Is M3 really failed? YES (FAIL flag is set)
            - Is R3 a replica of M3? YES
            - Has M1/M2 already voted in this epoch? NO
            - Is R3's config epoch valid? YES
            → Both M1 and M2 respond FAILOVER_AUTH_ACK to R3.

  t=~16.5s: R3 receives 2 votes out of 2 eligible voters (M1, M2).
            2 > 2/2 = 1 (majority) → ELECTION WON.

  t=~16.5s: R3 promotes itself to MASTER:
            - Sets itself as master (clears replica-of).
            - Increments config epoch to 8 (must be > all other epochs).
            - Claims ownership of slots 10923-16383.
            - Broadcasts PONG to all nodes announcing new topology.

  t=~17s:  All nodes receive R3's PONG → update their slot maps.
            New topology:
              M1 owns slots 0-5460    (unchanged)
              M2 owns slots 5461-10922 (unchanged)
              R3 (now M3-new) owns slots 10923-16383 (promoted)

  t=~17s:  Smart clients receive MOVED redirect or poll cluster state:
            → Update slot→node maps → route to R3 (now master).
            Clients that were blocked during failover: now unblocked.

  Total downtime for slot range 10923-16383:
    cluster-node-timeout + election time ≈ 15s + 1s = ~16s.
    During this window: writes to those slots fail (reads may work via remaining replicas).
```

```redis
-- ── Monitoring failover progress ──────────────────────────────────────────────
-- On any surviving node, watch the cluster state:
CLUSTER INFO
-- cluster_state:ok              ← cluster recovered after failover
-- cluster_slots_ok:16384        ← all slots covered again

CLUSTER NODES
-- ...
-- g7h8i9 10.0.0.3:6379@16379 master,fail - 0 1705312800000 3 disconnected 10923-16383
--                                   ↑ old M3: still shows as failed
-- r3node 10.0.0.6:6379@16379 master - g7h8i9 0 1705312800200 8 connected 10923-16383
--                                   ↑ R3 promoted: now master, epoch=8

-- The "fail" flag on old M3 persists until:
-- A. The old M3 restarts and rejoins as a replica of the new master.
-- B. An admin removes it with CLUSTER FORGET.

-- ── What happens to the old M3 when it comes back online ─────────────────────
-- Old M3 restarts. It still thinks it owns slots 10923-16383 (stale config epoch 3).
-- Old M3 broadcasts PONG with epoch=3.
-- Other nodes have epoch=8 → they ignore Old M3's slot claims.
-- Old M3 receives PINGs from other nodes with epoch=8.
-- Old M3 detects: its epoch < cluster epoch. Another node claims its slots.
-- Old M3 demotes itself to REPLICA automatically.
-- Old M3 starts replicating from R3 (new master for those slots).
-- No manual intervention required for the old master to rejoin as a replica. ✓

-- ── Forcing a manual failover ─────────────────────────────────────────────────
-- Graceful planned maintenance: no data loss guaranteed.
-- Execute on the REPLICA that should become the new master:
CLUSTER FAILOVER
-- Process:
-- 1. Replica tells its master: "stop accepting writes" (master enters pause state).
-- 2. Replica catches up: replication offset matches master's.
-- 3. Replica wins election (guaranteed: master cooperates, no timeout needed).
-- 4. Old master demotes to replica.
-- Zero data loss. Zero client errors (master pauses briefly, then traffic resumes on replica).
-- Downtime: only the replication catch-up time (usually <100ms).

CLUSTER FAILOVER TAKEOVER
-- Forceful failover: skip the election, promote unconditionally.
-- Use ONLY when master is unreachable AND you are certain no quorum exists.
-- Risk: if the old master is still running (network partition): SPLIT BRAIN.
-- Both old master and the takeover node both think they own the same slots.
-- Clients with stale routing may write to the old master → LOST WRITES.
-- Use takeover only as a last resort.

CLUSTER FAILOVER FORCE
-- Like TAKEOVER but allows the replica to be behind (may lose some data).
-- Use when the master is confirmed dead and you need to restore service immediately.
```

**Q7. What is split-brain in Redis Cluster — how does the cluster prevent it and what happens when prevention fails?**

A: Split-brain occurs when two nodes both believe they are the master for the same slot range simultaneously. Redis Cluster's config epoch system prevents this in most cases, but network partitions can still cause brief split-brain windows:

```
Split-brain scenario:

  Cluster: M1(slots 0-5460), M2(slots 5461-10922), M3(slots 10923-16383)
  Replicas: R1→M1, R2→M2, R3→M3

  Network partition: M3 is isolated. M3 can still serve clients in its network partition.
  The other partition: M1, M2, R1, R2, R3 (majority side).

  majority side:
  t=15s: M1 and M2 flag M3 as PFAIL → FAIL.
  t=16s: R3 wins election → becomes new master for slots 10923-16383.
         Epoch: 8 (higher than M3's epoch 3).
  t=16s: Writes to slots 10923-16383 go to R3 in the majority partition.

  minority side (M3's partition):
  t=15s: M3 is still running! Clients in this partition still write to M3.
         M3 doesn't know it's failed — it has no quorum to detect its own failure.
  t=16s: M3 continues accepting writes. SPLIT BRAIN: both M3 and R3 accept writes.

  Mitigation: cluster-require-full-coverage and min-replicas-to-write:
  cluster-require-full-coverage no  ← default: serve partial slot coverage
  cluster-require-full-coverage yes ← stop ALL writes if any slot is uncovered

  min-replicas-to-write: M3 stops accepting writes after N seconds without replicas:
  cluster-replica-validity-factor 10 (default)
  If M3 has 0 reachable replicas for >15s × 10 = 150s: M3 stops writes.
  This limits the split-brain window to ~150s (tunable).

  Resolution when partition heals:
  Old M3 comes back online → sees R3 has epoch=8 > M3's epoch=3.
  M3 demotes itself to replica of R3 → applies R3's data.
  ANY WRITES made to M3 during the partition ARE LOST (overwritten by R3's data).
```

```redis
-- ── Configuring split-brain protection ────────────────────────────────────────
CONFIG GET cluster-require-full-coverage
-- → cluster-require-full-coverage yes
-- yes: if ANY slot is unassigned (no master), cluster stops ALL writes (safest).
-- no:  cluster continues serving the slots that DO have a master.
-- Recommendation: yes for critical data; no for higher availability.

CONFIG GET cluster-migration-barrier
-- → cluster-migration-barrier 1
-- Minimum number of replicas a master must have before the cluster
-- will "steal" one of its replicas to cover a master that has no replicas.
-- Default 1: a master keeps its replicas unless it has > 1.

-- ── Detecting split-brain in monitoring ────────────────────────────────────────
-- On each node, check if it sees itself as master for its slots:
CLUSTER INFO | grep cluster_my_epoch
-- cluster_my_epoch:8   ← must match the epoch of the current master for these slots.

-- If two nodes claim the same slots with the same epoch: split brain.
-- Should never happen with correct epoch management (higher epoch wins).
-- Check all nodes:
redis-cli -h node1 CLUSTER NODES | grep 10923-16383
redis-cli -h node3 CLUSTER NODES | grep 10923-16383
-- Both should show the SAME master for those slots.

-- ── Minimum replicas to prevent single-node writes ────────────────────────────
CONFIG GET min-replicas-to-write
-- → min-replicas-to-write 0
-- Default: 0 (writes accepted even with zero replicas — may lose data on crash).
-- Recommended for HA: 1 (master requires at least 1 replica to accept writes).
CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10  -- Replica must be within 10 seconds of lag
-- If the replica is more than 10s behind: master treats it as unavailable.
-- If 0 replicas are within the lag limit: master stops accepting writes (noeviction-like).
```

## Section 6: Cluster Operations

**Q8. How do you add and remove nodes, and how does resharding work?**

A: Resharding moves slot ownership between nodes while the cluster continues serving traffic. Slots migrate one by one — each migration moves keys in that slot from the source node to the destination node:

```redis
-- ── Adding a new master node ──────────────────────────────────────────────────
-- Start the new node in cluster mode:
-- redis-server --cluster-enabled yes --cluster-config-file nodes-7.conf --port 6385

-- Add it to the cluster:
redis-cli --cluster add-node 10.0.0.7:6385 10.0.0.1:6379
-- → New node joins the cluster with NO slots assigned.
-- → It knows all other nodes (via CLUSTER MEET and gossip).
-- → It holds NO data yet.

-- Reshard slots to the new node:
redis-cli --cluster reshard 10.0.0.1:6379
-- Interactive prompt:
-- How many slots do you want to move? 1365       ← 16384 / 4 nodes (adding 4th)
-- What is the receiving node ID? <new-node-id>
-- Source (all/specific node IDs): all           ← take proportionally from all masters
-- → Starts migration: moves 1365 slots to the new node.

-- ── Adding a replica to an existing master ────────────────────────────────────
redis-cli --cluster add-node 10.0.0.8:6386 10.0.0.1:6379 --cluster-slave \
    --cluster-master-id <master-node-id>
-- → New node starts as a replica of the specified master.
-- → Begins replication (full SYNC then incremental).

-- ── Removing a node ───────────────────────────────────────────────────────────
-- Step 1: Move all slots off the node being removed (if it's a master):
redis-cli --cluster reshard 10.0.0.1:6379
-- Source: <node-to-remove-id>
-- Destination: (distribute to remaining nodes)

-- Step 2: Remove the now-empty node:
redis-cli --cluster del-node 10.0.0.1:6379 <node-id>
-- → Sends CLUSTER FORGET to all other nodes.
-- → Node shuts down (if using --cluster-yes flag).

-- ── Manual resharding step by step ───────────────────────────────────────────
-- Move slot 7000 from Node A to Node B:

-- 1. Tell destination (Node B) it will IMPORT slot 7000:
redis-cli -h node-b CLUSTER SETSLOT 7000 IMPORTING <node-a-id>

-- 2. Tell source (Node A) it will MIGRATE slot 7000:
redis-cli -h node-a CLUSTER SETSLOT 7000 MIGRATING <node-b-id>

-- 3. Move keys in slot 7000 from A to B (repeat until no keys remain):
redis-cli -h node-a CLUSTER GETKEYSINSLOT 7000 100
-- Returns up to 100 key names in slot 7000 on node A.
-- For each batch of keys:
redis-cli -h node-a MIGRATE node-b 6379 "" 0 5000 KEYS key1 key2 key3 ...
-- MIGRATE atomically moves keys: serializes on A, sends to B, deletes from A.
-- "" means "multiple keys" mode (KEYS flag).
-- 0 = destination DB, 5000 = timeout ms.

-- 4. After all keys moved: confirm slot ownership:
redis-cli -h node-a CLUSTER SETSLOT 7000 NODE <node-b-id>
redis-cli -h node-b CLUSTER SETSLOT 7000 NODE <node-b-id>
-- Both nodes agree: slot 7000 is now owned by Node B.
-- Gossip propagates this to all other nodes within seconds.

-- ── During migration: client behaviour ────────────────────────────────────────
-- Keys still on Node A: → client hits A → served normally ✓
-- Keys already migrated to Node B: → client hits A → ASK 7000 node-b
--   → client sends ASKING to B → B serves the key ✓
-- After migration complete: → MOVED 7000 node-b permanently

-- ── Cluster fix: repairing inconsistent state ─────────────────────────────────
redis-cli --cluster fix 10.0.0.1:6379
-- Checks all nodes for:
-- - Open slots (IMPORTING/MIGRATING not resolved after migration failure)
-- - Slot coverage gaps
-- - Epoch conflicts
-- Attempts to repair automatically.

redis-cli --cluster check 10.0.0.1:6379
-- Read-only health check: reports issues without fixing them.
```

## Section 7: Cluster Limitations

**Q9. What operations are restricted or impossible in Redis Cluster — how do you work around each?**

A: Redis Cluster's partitioned architecture imposes hard constraints on operations that involve multiple keys. Understanding these limitations is essential before migrating from standalone Redis:

```redis
-- ── Restriction 1: Multi-key commands must target the same slot ───────────────
-- Commands that operate on multiple keys in a single call:
MGET key1 key2 key3          -- All keys must be in the same slot
MSET key1 v1 key2 v2         -- All keys must be in the same slot
SMOVE src dst member         -- src and dst must be in the same slot
SUNION key1 key2 key3        -- All keys must be in the same slot
SINTERSTORE dest key1 key2   -- All keys must be in the same slot
ZUNIONSTORE dest key1 key2   -- All keys must be in the same slot
RPOPLPUSH src dst            -- src and dst must be in the same slot
LMOVE src dst LEFT RIGHT     -- src and dst must be in the same slot

-- Without hash tags → CROSSSLOT error:
MGET user:42 user:99
-- (error) CROSSSLOT Keys in request don't hash to the same slot

-- With hash tags → same slot:
MGET {user}:42 {user}:99   -- BAD IDEA: all users on one slot (hotspot)
MGET {user:42} {user:42}:recent  -- Better: group by entity, not type

-- Workaround without hash tags: application-level multi-get:
const results = await Promise.all([
    redis.get('user:42'),
    redis.get('user:99')
]);
-- Two separate commands → two network round-trips but no cluster error.
-- ioredis cluster client batches these by shard → parallel, not sequential.

-- ── Restriction 2: Transactions (MULTI/EXEC) ──────────────────────────────────
MULTI
GET user:42
SET user:42:last_seen "now"
EXEC
-- ✓ Only if BOTH keys are in the same slot.

MULTI
GET user:42       -- slot 4821
SET product:101 "v"  -- slot 14687 → different slot!
EXEC
-- (error) EXECABORT Transaction discarded because of previous errors.
-- Cluster rejects the transaction before EXEC (at MULTI time).

-- Workaround: use Lua scripts for atomic multi-key operations on same slot:
EVAL "
    local v1 = redis.call('GET', KEYS[1])
    redis.call('SET', KEYS[2], KEYS[3])
    return v1
" 2 {user:42}:profile {user:42}:last_seen "2024-01-15"
-- Both KEYS must be in the same slot (enforced by the cluster routing).

-- ── Restriction 3: Lua scripts must declare all keys ─────────────────────────
-- All keys accessed in a Lua script must be declared in KEYS[].
-- The cluster validates that all declared keys are in the same slot.
-- Keys computed inside the script (not in KEYS[]) bypass this check → danger.

-- SAFE:
EVAL "return redis.call('GET', KEYS[1])" 1 {user:42}:profile
-- UNSAFE (cluster may route to wrong node):
EVAL "return redis.call('GET', 'user:42:profile')" 0
-- → The node executing the script may not own slot 4821.

-- ── Restriction 4: Database number ───────────────────────────────────────────
SELECT 1   -- In cluster: only DB 0 is allowed.
-- (error) ERR SELECT is not allowed in cluster mode

-- Workaround: use key prefixes to namespace:
SET db1:user:42 "..."  -- Simulates a separate database

-- ── Restriction 5: Pub/Sub scoping ───────────────────────────────────────────
-- PUBLISH goes to the SPECIFIC node it's sent to.
-- SUBSCRIBE on a different node: does NOT receive messages published to node A.
-- In cluster: pub/sub does NOT propagate across nodes by default.

SUBSCRIBE channel   -- Only receives messages from the node you're connected to.
PUBLISH channel msg -- Goes to THIS node's subscribers only.

-- Workaround A: always PUBLISH and SUBSCRIBE to the same node.
--   Compute: slot = CRC16("channel") mod 16384 → connect to that node's master.
-- Workaround B: use Redis Cluster's cluster_broadcast (PUBSUB SHARDCHANNELS):
--   Redis 7.0: SSUBSCRIBE / SPUBLISH → shard-aware pub/sub.
--   Messages published with SPUBLISH go to all nodes that have subscribers.
-- Workaround C: use a dedicated pub/sub Redis instance (not in cluster).

-- ── Restriction 6: SCAN across all keys ──────────────────────────────────────
SCAN 0 MATCH "user:*" COUNT 100
-- SCAN on a cluster node: scans ONLY THAT NODE'S keys.
-- Keys on other nodes: NOT included.

-- Full cluster scan (must scan all nodes):
redis-cli --cluster call 10.0.0.1:6379 SCAN 0 COUNT 100
-- Calls SCAN on every node and aggregates results (not atomic — keys may move).

-- ioredis cluster scan (TypeScript):
async function* clusterScan(redis: Cluster, pattern: string): AsyncGenerator<string> {
    const nodes = redis.nodes('master');
    for (const node of nodes) {
        let cursor = '0';
        do {
            const [nextCursor, keys] = await node.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
            cursor = nextCursor;
            yield* keys;
        } while (cursor !== '0');
    }
}

-- ── Restriction 7: KEYS command ───────────────────────────────────────────────
KEYS "user:*"
-- Returns only keys on the node you're connected to. Not a cluster-wide KEYS.
-- Still dangerous in production (blocks the event loop). Use SCAN instead.
```

## Section 8: NestJS and ioredis Integration

**Q10. How do you configure a Redis Cluster client in NestJS — what are the critical settings for correct cluster behaviour?**

A: ioredis has built-in Redis Cluster support. The client maintains a slot→node map, handles MOVED redirects automatically, and distributes commands to the correct nodes. The configuration choices determine performance, resilience, and correctness:

```typescript
import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import Redis, { Cluster, ClusterOptions }             from 'ioredis';

// ── ioredis Cluster client configuration ──────────────────────────────────────
@Injectable()
export class RedisClusterService implements OnModuleInit, OnModuleDestroy {
    private cluster: Cluster;

    async onModuleInit(): Promise<void> {
        this.cluster = new Redis.Cluster(
            // Startup nodes: only need ONE reachable node to bootstrap.
            // ioredis discovers all other nodes via CLUSTER NODES automatically.
            [
                { host: '10.0.0.1', port: 6379 },
                { host: '10.0.0.2', port: 6379 },  // Fallback if first is down
                { host: '10.0.0.3', port: 6379 },  // Multiple for resilience
            ],
            {
                // ── Slot refresh ──────────────────────────────────────────────
                slotsRefreshTimeout: 2000,  // Refresh slot map on MOVED in <2s
                slotsRefreshInterval: 0,    // 0 = refresh only on MOVED/error (not polling)
                // Non-zero: periodic background refresh (useful if cluster topology
                // changes without triggering MOVED — e.g., replica promotion).

                // ── Redirection handling ──────────────────────────────────────
                maxRedirections: 16,   // Max MOVED/ASK redirections before giving up
                retryDelayOnMoved:  0, // Immediately retry after slot map refresh
                retryDelayOnFailover: 100,  // ms delay after detecting failover in progress

                // ── Cluster-level options ─────────────────────────────────────
                clusterRetryStrategy: (times: number) => {
                    // Called when connection to ALL startup nodes fails.
                    if (times > 10) return null; // Give up after 10 attempts
                    return Math.min(100 * Math.pow(2, times), 3000); // Exponential backoff
                },

                // ── Node-level options (applied to each shard connection) ─────
                redisOptions: {
                    password:   process.env.REDIS_PASSWORD,
                    tls:        process.env.NODE_ENV === 'production' ? {} : undefined,
                    // Per-node socket options:
                    connectTimeout:    10_000, // 10s to establish connection
                    commandTimeout:     5_000, // 5s for each command to complete
                    keepAlive:          30_000, // TCP keepalive to detect dead connections
                    // Reconnect strategy per node:
                    reconnectOnError: (err) => {
                        const targetErrors = ['READONLY', 'LOADING'];
                        return targetErrors.some(e => err.message.includes(e));
                        // READONLY: client wrote to a replica → reconnect to master
                        // LOADING: node is loading from RDB → retry
                    },
                    lazyConnect:   true, // Connect on first command, not at startup
                    enableOfflineQueue: true, // Queue commands while reconnecting
                    maxRetriesPerRequest: 3,
                },

                // ── Read from replicas ────────────────────────────────────────
                scaleReads: 'slave', // slave | all | master (default: master)
                // master: all reads to masters (strongly consistent)
                // slave:  all reads to replicas (slightly stale, less master load)
                // all:    round-robin across masters + replicas
                // Note: reading from replicas may return stale data (eventual consistency)
                // Use 'slave' only for workloads that tolerate stale reads.
            } satisfies ClusterOptions,
        );

        this.cluster.on('error',     (err) => console.error('Cluster error:', err));
        this.cluster.on('node error',(err, addr) => console.error(`Node ${addr} error:`, err));
        this.cluster.on('+node',     (node) => console.log('Node added:', node.options.host));
        this.cluster.on('-node',     (node) => console.log('Node removed:', node.options.host));
        this.cluster.on('reconnecting', () => console.log('Cluster reconnecting...'));
    }

    async onModuleDestroy(): Promise<void> {
        await this.cluster.quit();
    }

    // ── Accessing the cluster client ──────────────────────────────────────────
    getCluster(): Cluster { return this.cluster; }
}

// ── Service usage with hash tags ──────────────────────────────────────────────
@Injectable()
export class UserCacheService {
    constructor(private readonly redisSvc: RedisClusterService) {}

    private get client(): Cluster { return this.redisSvc.getCluster(); }

    async setUserData(userId: number, data: UserData): Promise<void> {
        // Use hash tags to co-locate all user-related keys:
        const pipeline = this.client.pipeline();
        pipeline.hset(`{user:${userId}}:profile`, {
            name:      data.name,
            email:     data.email,
            updatedAt: Date.now().toString(),
        });
        pipeline.expire(`{user:${userId}}:profile`, 3600);
        pipeline.set(`{user:${userId}}:last_seen`, Date.now().toString(), 'EX', 86400);
        await pipeline.exec();
        // All keys in slot for "user:{userId}" → same node → single pipeline ✓
    }

    async getUserProfile(userId: number): Promise<UserProfile | null> {
        // HGETALL on a cluster: works on any key (single key, no slot restriction)
        const data = await this.client.hgetall(`{user:${userId}}:profile`);
        if (!data || Object.keys(data).length === 0) return null;
        return data as UserProfile;
    }

    async mgetUserProfiles(userIds: number[]): Promise<(UserProfile | null)[]> {
        // Multi-key operation: keys from DIFFERENT users → DIFFERENT slots.
        // Must use parallel single-GETs, not MGET:
        const results = await Promise.all(
            userIds.map(id => this.client.hgetall(`{user:${id}}:profile`))
        );
        // ioredis Cluster client automatically routes each GET to the correct node.
        // Multiple requests to different nodes run in PARALLEL (pipelining per node).
        return results.map(r => (r && Object.keys(r).length > 0) ? r as UserProfile : null);
    }

    // ── Scan across all master nodes ──────────────────────────────────────────
    async deleteKeysByPattern(pattern: string): Promise<number> {
        const masters = this.client.nodes('master');
        let deleted = 0;

        await Promise.all(masters.map(async (node) => {
            let cursor = '0';
            do {
                const [nextCursor, keys] = await node.scan(
                    cursor, 'MATCH', pattern, 'COUNT', 100
                );
                cursor = nextCursor;
                if (keys.length > 0) {
                    // Each node's pipeline handles only its own keys (no cross-slot issue):
                    const pipeline = node.pipeline();
                    keys.forEach(key => pipeline.del(key));
                    const results = await pipeline.exec();
                    deleted += results?.filter(([, v]) => v === 1).length ?? 0;
                }
            } while (cursor !== '0');
        }));

        return deleted;
    }
}

// ── Lua script on a cluster (all keys must be in same slot) ───────────────────
@Injectable()
export class AtomicOperationsService {
    constructor(private readonly redisSvc: RedisClusterService) {}

    // Rate limiting with Lua: atomic INCR + EXPIRE (single slot guaranteed by key)
    async checkRateLimit(userId: number, limit: number): Promise<boolean> {
        const key = `rate:{${userId}}`;  // Hash tag: {userId} ensures consistent slot
        const lua = `
            local count = redis.call('INCR', KEYS[1])
            if count == 1 then
                redis.call('EXPIRE', KEYS[1], 60)
            end
            return count <= tonumber(ARGV[1])
        `;
        const allowed = await this.redisSvc.getCluster().eval(
            lua, 1, key, limit
        ) as number;
        return Boolean(allowed);
    }
}
```

## Section 10: Scenario-Based Questions

**Q12. "After a network partition, two master nodes are claiming ownership of the same slots — how did this happen and how do you fix it?"**

A: This is a split-brain scenario caused by a network partition that prevented quorum-based failover from completing cleanly. The config epoch system should prevent permanent split-brain, but the detection and recovery require understanding the epoch resolution rules:

```redis
-- ── Diagnosis ─────────────────────────────────────────────────────────────────
-- Run CLUSTER NODES on several nodes and compare:
redis-cli -h node1 CLUSTER NODES | sort
redis-cli -h node2 CLUSTER NODES | sort
redis-cli -h node3 CLUSTER NODES | sort

-- Split-brain signature:
-- From node1's perspective:
-- a1b2c3 10.0.0.1:6379 myself,master - 0 0 1 connected 10923-16383  epoch=3
-- g7h8i9 10.0.0.3:6379 slave - a1b2c3 0 0 8 connected 10923-16383   epoch=8

-- From node3's perspective:
-- g7h8i9 10.0.0.3:6379 myself,master - 0 0 8 connected 10923-16383  epoch=8
-- a1b2c3 10.0.0.1:6379 master,fail   - 0 0 1 connected 10923-16383  epoch=3

-- Analysis:
-- Node3 (g7h8i9) won a legitimate election (epoch=8 > epoch=3).
-- Node1 (a1b2c3) is still running with epoch=3 (it was partitioned during failover).
-- Node1 thinks it's still master; node3 thinks it's master. SPLIT BRAIN.

-- ── Resolution ────────────────────────────────────────────────────────────────
-- In practice: when the partition heals, Redis automatically resolves this.
-- Node1 receives gossip from node3 (epoch=8 > node1's epoch=3).
-- Node1 updates its config: "g7h8i9 is master for these slots with epoch=8".
-- Node1 demotes itself to replica of g7h8i9 automatically.
-- Node1 connects to g7h8i9 and starts replication.
-- Any writes made to node1 during the partition are LOST (overwritten).

-- If automatic resolution didn't happen (rare — manual fix):
-- Force node1 to demote by sending it a CLUSTER RESET:
redis-cli -h node1 CLUSTER RESET SOFT
-- SOFT RESET: clears all slot assignments; node stays in cluster but without slots.
-- Hard reset (CLUSTER RESET HARD): removes all cluster info; node leaves cluster.
-- Then rejoin node1 as a replica of g7h8i9:
redis-cli -h node1 CLUSTER REPLICATE <g7h8i9-node-id>

-- ── Preventing future split-brain ─────────────────────────────────────────────
-- 1. Set min-replicas-to-write to stop writes when isolated:
CONFIG SET min-replicas-to-write 1        -- Require 1 replica acknowledgement
CONFIG SET min-replicas-max-lag 10        -- Replica must be within 10 seconds

-- 2. Set cluster-node-timeout appropriately for the network:
CONFIG SET cluster-node-timeout 5000      -- 5s for stable LAN

-- 3. Monitor replication lag:
INFO replication
-- role:master
-- connected_slaves:1
-- slave0:ip=10.0.0.6,port=6379,state=online,offset=492847,lag=0
-- master_repl_offset:492847
-- ← lag=0: replica is fully caught up ✓

-- ── Write loss estimation from split-brain ────────────────────────────────────
-- After healing: compare node1 and node3's replication offsets at split time.
-- node1's last offset: 492847 (written before partition)
-- node3's offset when elected: 492512 (slightly behind node1 at election time)
-- Difference: 492847 - 492512 = 335 bytes of AOF = ~few dozen small commands
-- These writes to node1 during the partition are lost.
-- With min-replicas-to-write=1: node1 would have stopped accepting writes
-- when it lost contact with its replica → ZERO data loss instead.
```

**Q13. "Design a Redis Cluster strategy for a high-traffic NestJS API serving 50,000 requests/second with session management, rate limiting, and a product cache."**

A: The design must balance slot colocation (for multi-key operations), key distribution (for even load), and cluster sizing (for the write throughput target):

```
Cluster sizing calculation:

  Target: 50,000 req/s
  Assumption: each request hits Redis 3 times on average (session read, rate check, cache read)
  Redis ops/s required: 150,000 ops/s
  Single Redis master: ~100,000-200,000 simple ops/s (hardware dependent)
  Safe target per master: ~80,000 ops/s (leave headroom)
  Masters needed: 150,000 / 80,000 = 1.875 → 3 masters minimum (round up + 1 for resilience)

  Final topology: 3 masters + 3 replicas = 6 nodes
  Each master owns: 16384 / 3 ≈ 5461 slots
  Replicas: 1 per master (tolerate one node failure per shard)
```

```typescript
// ── Key namespace design ───────────────────────────────────────────────────────
// All key prefixes with their TTL, slot strategy, and eviction priority:

// SESSION KEYS (sliding TTL, critical):
// {session:<uuid>}:data      → HASH, EX 3600 (1hr), EXPIRE XX to slide
// {session:<uuid>}:activity  → STRING, EX 86400 (24hr)
// Hash tag: {session:<uuid>} → session keys co-located for HGETALL + last_seen multi-op

// RATE LIMIT KEYS (fixed TTL, lossy OK):
// rate:{userId}:global     → STRING (counter), EX 60
// rate:{userId}:api        → STRING (counter), EX 3600
// Hash tag: rate:{userId} → allows MGET for multiple rate windows

// PRODUCT CACHE (medium TTL, evictable):
// product:{productId}       → HASH, EX 300 (5 min)
// {product:{productId}}:variants → HASH, EX 300 (co-located with main product)
// Note: No hash tag on product key alone — products are accessed individually.

// FEATURE FLAGS (persistent, never evict):
// feature:{flagName}         → STRING, no TTL
// Note: No hash tag — feature flags are accessed individually.

// ── Cluster configuration ──────────────────────────────────────────────────────
export const clusterConfig: ClusterOptions = {
    slotsRefreshTimeout: 2000,
    slotsRefreshInterval: 60_000,  // Refresh every minute (catch topology changes)
    maxRedirections: 16,
    retryDelayOnFailover: 100,

    redisOptions: {
        password:         process.env.REDIS_PASSWORD,
        tls:              { rejectUnauthorized: true },
        connectTimeout:   5_000,
        commandTimeout:   3_000,   // Fail fast — 3s is already slow for a cache
        maxRetriesPerRequest: 2,
        enableOfflineQueue: false,  // REJECT commands during reconnect (don't queue up)
        // Why disable offline queue: if Redis is down for 10s, 500k queued commands
        // would flood Redis when it comes back → cascading failure.
        // Better: fail fast → caller uses DB fallback.
    },

    scaleReads: 'slave',  // Session reads are eventually consistent (1-2ms lag OK)
    // Exception: rate limiting MUST read from master (replica lag could allow over-limit).
    // Handle in application: rate limiter uses a separate master-only client.
};

// ── Request lifecycle example ──────────────────────────────────────────────────
@Injectable()
export class RequestHandler {
    constructor(
        private readonly session:   SessionService,
        private readonly rateLimit: RateLimiterService,
        private readonly cache:     ProductCacheService,
    ) {}

    async handleProductRequest(
        sessionToken: string,
        productId:    string,
        userId:       number,
    ): Promise<Product> {
        // 1. Session validation (read from replica: scaleReads=slave):
        const session = await this.session.get(sessionToken);
        if (!session) throw new UnauthorizedException();

        // 2. Rate limiting (MUST use master connection for accuracy):
        const { allowed } = await this.rateLimit.checkLimit(userId, 100);
        if (!allowed) throw new TooManyRequestsException();

        // 3. Product cache (read from replica OK: stale by max 300s):
        const product = await this.cache.get(productId);

        // 4. Session touch (slide TTL: writes always go to master):
        await this.session.touch(sessionToken);

        return product;
    }
}

// ── Cluster health monitoring in NestJS ───────────────────────────────────────
@Injectable()
export class ClusterHealthService implements OnModuleInit {
    private readonly logger = new Logger(ClusterHealthService.name);

    constructor(private readonly redisSvc: RedisClusterService) {}

    onModuleInit(): void {
        // Monitor failover events:
        this.redisSvc.getCluster().on('+node', (node) => {
            this.logger.log(`Node JOINED cluster: ${node.options.host}:${node.options.port}`);
        });
        this.redisSvc.getCluster().on('-node', (node) => {
            this.logger.warn(`Node LEFT cluster: ${node.options.host}:${node.options.port}`);
        });
        this.redisSvc.getCluster().on('node error', (err, key) => {
            this.logger.error(`Node error [${key}]: ${err.message}`);
        });
    }

    async getClusterStatus(): Promise<ClusterStatus> {
        const nodes  = this.redisSvc.getCluster().nodes('master');
        const checks = await Promise.allSettled(
            nodes.map(async (node) => {
                const info  = await node.cluster('INFO') as string;
                const parse = (field: string) =>
                    parseInt(info.split('\r\n').find(l => l.startsWith(field))
                                  ?.split(':')[1] ?? '0');
                return {
                    host:        node.options.host,
                    state:       info.includes('cluster_state:ok') ? 'ok' : 'fail',
                    slotsCovered: parse('cluster_slots_ok:'),
                    slotsOk:     parse('cluster_slots_assigned:'),
                    nodesFail:   parse('cluster_slots_fail:'),
                };
            })
        );

        return {
            nodes: checks.map((r, i) =>
                r.status === 'fulfilled' ? r.value : { host: nodes[i].options.host, state: 'unreachable' }
            ),
            allOk: checks.every(r => r.status === 'fulfilled' && (r.value as any).state === 'ok'),
        };
    }
}
```

## Quick Reference Tables

### Hash Slot Distribution

| Nodes | Slots per node | Max keys/slot (1KB docs, 128MB chunk) |
|---|---|---|
| 3 | 5461 | ~131,072 |
| 6 | 2730 | ~131,072 |
| 10 | 1638 | ~131,072 |
| 100 | 163 | ~131,072 |
| 1000 | 16 | ~131,072 (minimum granularity) |

### Failover Timing

| Phase | Duration | Notes |
|---|---|---|
| Crash to PFAIL | `cluster-node-timeout` (default 15s) | First node notices no response |
| PFAIL to FAIL | Gossip spread (~1-2s) | Majority of masters agree |
| FAIL broadcast | ~100ms | Immediate broadcast (not gossip) |
| Election delay | 500ms + random(0-500ms) + rank × 1s | Weighted by replication offset |
| Election voting | ~100ms | Masters reply with ACK/NACK |
| Promotion + gossip | ~1s | New master broadcasts PONG |
| **Total** | **~17-30s** | With default 15s timeout |
| Manual (`CLUSTER FAILOVER`) | <500ms | Graceful, no data loss |

### MOVED vs ASK Redirect

| Property | MOVED | ASK |
|---|---|---|
| Meaning | Slot permanently at another node | Slot currently being migrated |
| Client action | Update slot map + retry | Send ASKING + retry (don't update map) |
| Frequency | Only on stale slot map | During resharding only |
| Cache update | Yes — update slot→node permanently | No — temporary state |
| Issued by | Any node for any slot it doesn't own | Source node for migrating keys |

### Multi-Key Operation Behaviour

| Operation | Standalone | Cluster (no tag) | Cluster (with hash tag) |
|---|---|---|---|
| `MGET key1 key2` | ✓ | ✗ CROSSSLOT | ✓ (same slot) |
| `MSET k1 v1 k2 v2` | ✓ | ✗ CROSSSLOT | ✓ (same slot) |
| `MULTI/EXEC` | ✓ | ✗ (cross-slot) | ✓ (same slot) |
| `EVAL` (multi-key) | ✓ | ✗ (routing) | ✓ (declare in KEYS[]) |
| `SUNIONSTORE` | ✓ | ✗ CROSSSLOT | ✓ (same slot) |
| `SCAN` (all keys) | ✓ | ✗ (per-node only) | ✗ (must scan each node) |
| `PUBLISH/SUBSCRIBE` | ✓ | ✗ (per-node) | Use SSUBSCRIBE (v7.0+) |
| `SELECT db` | ✓ | ✗ CLUSTERDOWN | N/A (DB 0 only) |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise that **Redis Cluster uses exactly 16384 hash slots** — not configurable — and explaining the reason: the slot bitmap in gossip heartbeats is 2 KB at 16384 slots, which is a pragmatic balance between granularity (enough for ~1000 nodes) and message size overhead; (2) knowing the **CRC16 hash tag rule exactly** — the content between the FIRST `{` and the FIRST `}` after it is hashed (not the whole key), the tag must be non-empty to activate, and the first tag wins if multiple appear — and being able to explain why it exists: without hash tags, any multi-key operation across different entities is a CROSSSLOT error since each key independently maps to its own slot; (3) understanding the **MOVED vs ASK distinction precisely**: MOVED means the slot permanently lives elsewhere and the client should update its cached slot map, while ASK means a specific key has already migrated during an in-progress resharding and the client must send ASKING before the command on the new node but must NOT update the permanent slot map; (4) knowing the **failover process step by step**: PFAIL is a local opinion by one node that a peer hasn't responded within `cluster-node-timeout`; FAIL is when a majority of masters agree on PFAIL (making it cluster-wide); a replica then wins an election by receiving `>N/2` votes from the remaining masters, where the replica with the highest replication offset gets the shortest election delay; (5) understanding **split-brain in cluster**: when a partition heals, the config epoch resolves it automatically — the node with the higher epoch (the one that was elected after the partition) wins, and the lower-epoch node demotes itself to replica; writes made to the lower-epoch node during the partition are permanently lost, which is why `min-replicas-to-write=1` limits the damage window; (6) knowing that **SCAN in a cluster returns only the keys on the node you're connected to** — a cluster-wide key scan must iterate every master node separately using `redis.nodes('master')`, and that keys may move between calls making the result non-atomic; (7) knowing the **pub/sub limitation**: PUBLISH sends to subscribers of only that specific node; in Redis 7.0+, `SSUBSCRIBE`/`SPUBLISH` (shard pub/sub) propagates to all nodes that have subscribers for the channel, solving the cross-node pub/sub problem without a separate dedicated pub/sub instance; and (8) knowing that **ioredis handles MOVED redirects automatically** by refreshing the slot map and retrying, that `scaleReads: 'slave'` distributes reads to replicas for throughput but introduces eventual consistency, and that `enableOfflineQueue: false` is the correct setting for cache use cases to fail fast and fall back to the database rather than queuing thousands of commands during a Redis outage.
