# Redis Expiration Strategies: TTL, EXPIRE, PERSIST, Passive vs Active Eviction
## Interview Q&A (5 YOE Level)

---

## Section 1: How Redis Stores Expiration

**Q1. How does Redis physically store expiration data alongside keys — what is the internal data structure?**

A: Redis maintains a separate hash table alongside the main key-value store. Each entry in this expiration dictionary maps a key name to an absolute Unix timestamp in milliseconds. This architecture has precise consequences for expiration accuracy, memory use, and replication behaviour:

```
Redis memory layout (simplified):

  Main dictionary (key → value):
  ┌────────────────────────────────────────────────────────────────┐
  │ "session:abc123" → { userId: 42, role: "admin", ... }  (hash) │
  │ "rate:user:42"   → "87"                                (string)│
  │ "product:101"    → { name: "Laptop", price: 999 }      (hash) │
  │ "leaderboard"    → [(alice,100),(bob,90),...]           (zset) │
  └────────────────────────────────────────────────────────────────┘

  Expiry dictionary (key → absolute expiry timestamp in ms):
  ┌────────────────────────────────────────────────────────────────┐
  │ "session:abc123" → 1705312800000   (2024-01-15 10:00:00 UTC)  │
  │ "rate:user:42"   → 1705312860000   (expires in 60s from now)  │
  │                                                                │
  │ "product:101"    → (not present = no expiry, persistent)       │
  │ "leaderboard"    → (not present = persistent)                  │
  └────────────────────────────────────────────────────────────────┘

Key observations:
  1. Expiry is stored as ABSOLUTE Unix timestamp in milliseconds (not "seconds from now").
     EXPIRE key 60  →  stores: current_time_ms + 60_000
     After server restart: the absolute timestamp is still valid (Redis saves it to RDB/AOF).

  2. Keys without an expiry entry are PERSISTENT — they live forever unless DEL'd.

  3. The expiry dictionary consumes ~8 bytes per key that has a TTL
     (the timestamp value) plus dictionary overhead.
     For 1M keys with TTLs: ~10-15 MB of additional memory for the expiry table.

  4. Expiry is per-key, NOT per-value. You cannot set TTL on a specific hash field
     or a specific list element — only on the top-level key.
```

```redis
-- Inspecting the expiry dictionary directly:
DEBUG OBJECT session:abc123
-- Value at: 0x7f... refcount:1 encoding:ziplist serializedlength:42
-- lru_seconds_idle:3 type:hash

-- Check internal key encoding and expiry:
OBJECT ENCODING session:abc123     -- ziplist, hashtable, quicklist, etc.
OBJECT IDLETIME session:abc123     -- Seconds since last access (for LRU)
OBJECT FREQ session:abc123         -- Access frequency (for LFU)

-- The expiry timestamp stored internally:
PTTL session:abc123      -- Returns remaining TTL in milliseconds
-- → 59847  (key expires in ~59.8 seconds)

-- Show all keys with TTLs (EXPENSIVE in production — use SCAN):
-- KEYS * then TTL on each (never do this in production)
-- Instead: use SCAN with TYPE and TTL checks in application code.
```

**Q2. What is the full family of expiration commands — what are the exact semantics of each?**

A: Redis provides six expiration-setting commands and two inspection commands. The differences between them — seconds vs milliseconds, relative vs absolute, conditions — matter for precision and for avoiding race conditions:

```redis
-- ── Setting expiration (relative — seconds from NOW) ─────────────────────────
EXPIRE key seconds
-- Sets expiry to: current_time + seconds.
-- Returns 1 if timeout was set, 0 if key does not exist.
-- Any previously set TTL is OVERWRITTEN.
EXPIRE session:abc123 3600          -- Expires in 1 hour
-- → (integer) 1

-- ── Setting expiration (relative — milliseconds from NOW) ─────────────────────
PEXPIRE key milliseconds
-- Higher precision than EXPIRE. Internally stored as ms anyway.
-- Use when you need sub-second TTLs (e.g., 500ms rate limit windows).
PEXPIRE otp:42 300000              -- Expires in 5 minutes (300,000 ms)
-- → (integer) 1

-- ── Setting expiration (absolute — Unix timestamp in SECONDS) ─────────────────
EXPIREAT key unix-timestamp
-- Expires AT a specific wall-clock time.
-- Useful when expiry should coincide with a known event (end of day, end of contest).
EXPIREAT contest:leaderboard 1706745600  -- Expires at 2024-02-01 00:00:00 UTC
-- → (integer) 1

-- ── Setting expiration (absolute — Unix timestamp in MILLISECONDS) ─────────────
PEXPIREAT key unix-timestamp-ms
-- Millisecond-precision absolute expiry.
PEXPIREAT token:xyz 1705312800000  -- Expires at exact ms timestamp
-- → (integer) 1

-- ── Redis 7.0+: EXPIRE with conditions (NX, XX, GT, LT) ─────────────────────
EXPIRE key seconds NX
-- Set TTL ONLY IF the key has NO existing TTL (persistent key).
-- Use: ensure a persistent key gets a TTL without overwriting an existing one.
EXPIRE session:abc123 3600 NX
-- → (integer) 1 if set, 0 if key already had a TTL (no change made).

EXPIRE key seconds XX
-- Set TTL ONLY IF the key ALREADY has a TTL.
-- Use: renew/slide a TTL for existing volatile keys; ignore persistent keys.
EXPIRE session:abc123 3600 XX
-- → (integer) 1 if renewed, 0 if key was persistent (no change).

EXPIRE key seconds GT
-- Set TTL ONLY IF the new TTL is GREATER than the current TTL.
-- Use: extend a TTL; never shorten it.
EXPIRE lock:resource 30 GT
-- → (integer) 1 if new TTL > current TTL (extended), 0 if current is already longer.

EXPIRE key seconds LT
-- Set TTL ONLY IF the new TTL is LESS than the current TTL.
-- Use: shorten a TTL; never extend it.
-- Rare but useful for deadline-based expiry (deadline moves closer, never further).

-- ── Inspecting TTL ────────────────────────────────────────────────────────────
TTL key
-- Returns remaining TTL in SECONDS.
-- → positive integer: remaining seconds
-- → -1: key exists but has NO TTL (persistent)
-- → -2: key does NOT EXIST
TTL session:abc123    -- → 3547  (about 59 minutes left)
TTL product:101       -- → -1   (persistent, no TTL)
TTL nonexistent       -- → -2   (key not found)

PTTL key
-- Returns remaining TTL in MILLISECONDS (higher precision).
PTTL session:abc123   -- → 3547382  (3547.382 seconds)

-- ── Removing expiration (making a key persistent) ─────────────────────────────
PERSIST key
-- Removes the TTL from a key → key becomes persistent.
-- Returns 1 if TTL was removed, 0 if key had no TTL or doesn't exist.
PERSIST session:abc123
-- → (integer) 1
TTL session:abc123
-- → -1  (now persistent — will never expire on its own)

-- ── Atomic set + expire (avoiding a race condition) ───────────────────────────
-- WRONG (two commands = race condition if crash between them):
SET session:abc123 "data"
EXPIRE session:abc123 3600    -- If server crashes here: session lives forever!

-- CORRECT (SET with EX option — atomic):
SET session:abc123 "data" EX 3600       -- Set value AND expiry atomically
SET session:abc123 "data" PX 300000     -- Set with millisecond TTL
SET session:abc123 "data" EXAT 1706745600    -- Set with absolute Unix timestamp
SET session:abc123 "data" PXAT 1706745600000 -- Set with absolute ms timestamp

-- The SET command's NX and XX options combine with expiry:
SET session:abc123 "data" EX 3600 NX
-- Set value + TTL only if key does NOT exist.
-- Use: atomic "create session if not exists".

SET lock:resource "owner-id" EX 30 NX
-- Distributed lock: acquire only if not already held, with 30s auto-release.
-- → (nil) if lock is already held (NX condition failed)
-- → "OK" if lock acquired
```

## Section 2: Passive Eviction (Lazy Expiration)

**Q3. What is passive eviction — how does it work, what are its limitations, and when does it fire?**

A: Passive eviction (also called lazy expiration) is Redis's first line of expiry enforcement. When a client accesses a key, Redis checks the expiry dictionary for that key before returning any value. If the key is expired, Redis deletes it at that moment and returns a "key not found" response:

```
Passive eviction timeline:

  t=0s:   SET session:abc123 "data" EX 60   → key stored, expiry = t+60
  t=61s:  Key is expired (absolute time has passed).
          BUT Redis has NOT deleted it yet.
          Redis does NOT scan for expired keys continuously.
          The key still exists in memory — consuming RAM.

  t=62s:  Client sends: GET session:abc123
          Redis checks expiry dictionary:
            "session:abc123" → timestamp 60s ago → EXPIRED
          Redis atomically:
            1. Deletes the key from main dictionary.
            2. Removes it from the expiry dictionary.
            3. Returns (nil) to the client.
          The key is now gone.

  t=63s:  Another client sends: GET session:abc123
          → (nil) immediately (key doesn't exist anymore).

  If NO client ever accesses the key after t=60s:
          The key lives in memory indefinitely until active expiration finds it.
```

```redis
-- ── Observing passive expiration ─────────────────────────────────────────────
SET test:passive "value" EX 5
-- Wait 10 seconds...
-- Key is now expired but possibly not yet deleted.

DEBUG SLEEP 0.001  -- Force a brief pause (for demonstration only)
EXISTS test:passive
-- → 0  (EXISTS checks the expiry dictionary — expired key returns 0)
-- Behind the scenes: EXISTS triggered passive deletion.

-- ── Commands that trigger passive expiration ──────────────────────────────────
-- Any command that accesses a key by name checks expiry first:
GET key        -- If expired: delete + return nil
SET key value  -- Does NOT check expiry (overwrites without caring about old TTL)
EXISTS key     -- If expired: delete + return 0
HGET key field -- If key expired: delete + return nil
LRANGE key     -- If expired: delete + return empty array
TTL key        -- If expired: delete + return -2
TYPE key       -- If expired: delete + return "none"
RENAME key dst -- If source expired: returns error

-- Commands that do NOT trigger passive expiration:
-- No command accesses a key without also checking its expiry.
-- All key-accessing commands check expiry before any other operation.

-- ── Passive expiration and replication ────────────────────────────────────────
-- On a PRIMARY:
-- Passive expiration fires → Redis sends a DEL command to all REPLICAS.
-- The DEL is written to the AOF log and sent via the replication stream.
-- Replicas NEVER expire keys on their own from client access.
-- They only expire when they receive a DEL from the primary's passive eviction.

-- On a REPLICA:
-- Client sends GET expired_key to replica directly.
-- Replica checks expiry: key is expired.
-- BUT: replica cannot independently delete the key (must wait for primary's DEL).
-- Replica returns (nil) to the client.
-- Replica does NOT delete the key yet (it will when primary sends DEL).
-- This means: between when the key expires and when the primary sends DEL,
-- reading from a replica returns (nil) but the key still consumes memory.

-- ── The fundamental limitation of passive eviction ───────────────────────────
-- Passive eviction only fires when a key is accessed.
-- Keys that are SET with a TTL and NEVER accessed again after expiry:
--   → Stay in memory consuming RAM until active eviction finds them.
--   → In extreme cases: all memory filled with "zombie" expired keys.
-- This is why active eviction exists — to clean up unaccessed expired keys.
```

## Section 3: Active Eviction

**Q4. How does Redis's active expiration cycle work — what is the algorithm and how does it affect CPU and key expiry accuracy?**

A: Active eviction is a background process that periodically samples the expiry dictionary and deletes expired keys regardless of client access. It runs as a timed job in Redis's event loop and is designed to balance CPU usage against expiry accuracy:

```
Active expiration algorithm (runs every 100ms by default):

  Each cycle:
  ┌──────────────────────────────────────────────────────────────────┐
  │  1. Sample 20 random keys from the EXPIRY dictionary             │
  │     (only keys WITH a TTL — keys without TTL are not sampled).   │
  │                                                                  │
  │  2. Delete all sampled keys that are expired.                    │
  │     Count how many were expired: call this "expired_count".      │
  │                                                                  │
  │  3. Check: expired_count / 20 > 25% ?                           │
  │     (More than 5 of the 20 sampled keys were expired)            │
  │                                                                  │
  │  4. YES (high expiry rate): run another cycle IMMEDIATELY.       │
  │     Repeat until: expired_count / sample_size ≤ 25%             │
  │     OR: 25ms time limit exceeded (don't monopolize the thread).  │
  │                                                                  │
  │  5. NO (low expiry rate): wait for next scheduled cycle (100ms). │
  └──────────────────────────────────────────────────────────────────┘

Why this algorithm?
  The 25% threshold adaptive loop prevents Redis from falling behind when
  a large number of keys expire simultaneously (e.g., after a bulk EXPIRE at t=0).
  Without the adaptive loop: Redis would sample 20 keys every 100ms even if
  10,000 keys expired per second → memory fills up with expired keys.
  With the adaptive loop: Redis keeps cycling until the expired ratio drops.

  The 25ms time limit prevents active expiration from blocking client queries
  for more than ~25ms. Redis is single-threaded: a long expiry loop would
  delay all client commands.
```

```redis
-- ── Configuring active expiration ─────────────────────────────────────────────
-- In redis.conf:
-- hz 10             -- Run background tasks (including active expiration) 10 times/second
--                      Default: 10 (range: 1-500)
--                      Higher hz: more frequent expiry checks, faster TTL accuracy.
--                      Lower hz: less CPU usage, slower expiry.
-- dynamic-hz yes    -- Automatically increase hz when more clients are connected.
--                      Redis scales hz up to 500 when under heavy load.

-- Checking current hz:
CONFIG GET hz           -- → hz 10
CONFIG GET dynamic-hz   -- → dynamic-hz yes

-- Change hz at runtime (no restart needed):
CONFIG SET hz 20        -- Check expiry 20 times/second (more accurate, more CPU)

-- ── The statistical guarantee ─────────────────────────────────────────────────
-- Active expiration provides a STATISTICAL guarantee, not an absolute one.
-- At steady state (after the adaptive loop stabilises):
-- At most 25% of volatile keys may be expired-but-not-yet-deleted at any moment.
--
-- Example:
-- 1,000,000 keys with TTLs expire over 1 minute.
-- Worst case: up to 250,000 expired keys linger in memory at any instant.
-- With 100ms cycles sampling 20 keys: this backlog drains in a few seconds.
-- But there is always a brief window between expiry and deletion.
--
-- For applications that need EXACT expiry enforcement (not probabilistic):
-- Active + passive together provide adequate accuracy for most use cases.
-- For millisecond-precision expiry: client-side timestamps + validation.

-- ── Monitoring active expiration ──────────────────────────────────────────────
INFO stats | grep expired
-- expired_keys:48291       -- Total keys expired by active + passive eviction (since start)

INFO keyspace
-- db0:keys=982847,expires=741293,avg_ttl=3847291
--     ↑ total keys  ↑ keys with TTL  ↑ average ms remaining

-- High expires/keys ratio (>50%): many volatile keys → active expiry is busy.
-- If expired_keys is growing slowly despite many key expirations:
--   → hz is too low → increase hz or investigate CPU bottleneck.

-- ── Active expiration and the event loop ──────────────────────────────────────
-- Redis is single-threaded (for command processing).
-- Active expiration runs between processing client commands.
-- If active expiration runs for 25ms: ALL client commands wait 25ms.
-- Visible as: periodic latency spikes of ~25ms in command response times.
-- Monitor with:
LATENCY HISTORY event  -- Recent latency events
LATENCY LATEST         -- Latest latency for all event types
-- → "expire-cycle" events: duration of each active expiration cycle.
-- Duration > 25ms: active expiration is saturated → increase hz or reduce volatile keys.

-- ── Active expiration in Redis Cluster ────────────────────────────────────────
-- Each shard (master node) runs its own active expiration independently.
-- No coordination between shards for expiration.
-- Expired keys are deleted locally + DEL replicated to shard's replicas.
-- No cluster-wide expiry event or notification.
```

## Section 4: Memory Eviction Policies

**Q5. What are Redis's eight eviction policies — what does each do when `maxmemory` is reached?**

A: When Redis reaches its `maxmemory` limit, it must decide what to evict to make room for new writes. The eight eviction policies cover the spectrum from "never evict" to "evict the globally least useful key":

```
Redis memory management hierarchy:

  maxmemory limit reached
          │
          ▼
  Eviction policy runs (SELECT which key to evict)
          │
  ┌───────┴─────────────────────────────────────────────────────────┐
  │                Eight eviction policies                          │
  │                                                                 │
  │ POOL A: volatile-* (operates only on keys WITH a TTL)          │
  │   volatile-lru    → evict least-recently-used among TTL keys   │
  │   volatile-lfu    → evict least-frequently-used among TTL keys │
  │   volatile-random → evict a random TTL key                     │
  │   volatile-ttl    → evict the TTL key closest to expiry        │
  │                                                                 │
  │ POOL B: allkeys-* (operates on ALL keys, with or without TTL)  │
  │   allkeys-lru     → evict least-recently-used key (global)     │
  │   allkeys-lfu     → evict least-frequently-used key (global)   │
  │   allkeys-random  → evict any random key                       │
  │                                                                 │
  │ POOL C: safety valve                                            │
  │   noeviction      → reject writes with OOM error (safe, strict)│
  └─────────────────────────────────────────────────────────────────┘
```

```redis
-- ── Configuring eviction ──────────────────────────────────────────────────────
-- redis.conf:
-- maxmemory 4gb                        -- Memory limit (0 = no limit, not recommended)
-- maxmemory-policy allkeys-lru         -- Eviction policy
-- maxmemory-samples 10                 -- LRU/LFU approximation sample size

-- Runtime change (no restart):
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru
CONFIG SET maxmemory-samples 10

-- ── noeviction (the "safe" default in some configurations) ───────────────────
-- When maxmemory is reached: REJECT all write commands with an error.
-- Read commands (GET, HGET, etc.) still work.
-- Error returned: OOM command not allowed when used memory > 'maxmemory'

CONFIG SET maxmemory-policy noeviction
SET newkey "value"
-- (error) OOM command not allowed when used memory > 'maxmemory'.

-- Use noeviction when:
-- • Redis is a database (not a cache): data loss is unacceptable.
-- • The application can handle OOM errors gracefully (retry, alert).
-- • You want explicit control over what gets deleted (application manages TTLs).

-- ── volatile-lru: evict least recently used (only TTL keys) ──────────────────
CONFIG SET maxmemory-policy volatile-lru
-- When full: find the TTL key that was accessed least recently → delete it.
-- If no TTL keys exist: behaves like noeviction (cannot evict persistent keys).
-- Use when: mixing cached data (with TTL) and persistent data (without TTL).
-- Persistent keys are NEVER evicted — they are protected.

-- ── allkeys-lru: evict least recently used (any key) ─────────────────────────
CONFIG SET maxmemory-policy allkeys-lru
-- When full: find ANY key (TTL or persistent) accessed least recently → delete it.
-- This is the most common production setting for a pure cache.
-- Use when: Redis is used exclusively as a cache (no persistent data).
-- ALL keys are candidates for eviction → evict the coldest ones first.

-- ── volatile-lfu: evict least frequently used (only TTL keys) ─────────────────
CONFIG SET maxmemory-policy volatile-lfu
-- When full: find the TTL key with the lowest access frequency → delete it.
-- LFU tracks HOW MANY TIMES a key has been accessed, not just when.
-- A key accessed once 1 second ago has lower LFU score than a key
-- accessed 1000 times over the past hour (even if it hasn't been used recently).
-- Use when: access patterns are stable and popular keys should never be evicted
--   even if they haven't been touched recently.

-- ── allkeys-lfu: evict least frequently used (any key) ───────────────────────
CONFIG SET maxmemory-policy allkeys-lfu
-- When full: find ANY key with the lowest access frequency → delete it.
-- Best for: caches with a stable "hot" working set that must be preserved
--   even if individual hot keys aren't accessed for minutes at a time
--   (e.g., product catalogue — popular items are always popular).

-- ── volatile-random: evict a random TTL key ───────────────────────────────────
CONFIG SET maxmemory-policy volatile-random
-- When full: pick a random key that has a TTL → delete it.
-- No intelligence about access patterns — purely random among volatile keys.
-- Use when: all cached data has roughly equal value and access frequency.
--   Avoids LRU overhead (clock updates on every access).

-- ── allkeys-random: evict any random key ─────────────────────────────────────
CONFIG SET maxmemory-policy allkeys-random
-- When full: pick any random key → delete it.
-- Use rarely. Only sensible when data access is uniformly random
--   (all keys equally likely to be needed next).

-- ── volatile-ttl: evict the TTL key closest to expiry ─────────────────────────
CONFIG SET maxmemory-policy volatile-ttl
-- When full: among TTL keys, pick the one with the SMALLEST remaining TTL.
-- Logic: a key expiring in 1 second has less value than one expiring in 1 hour.
-- Use when: TTL directly represents value/freshness
--   (shorter TTL = less valuable = safe to evict first).
-- Anti-pattern: if TTL and value are unrelated, this evicts wrong keys.

-- ── Monitoring eviction ────────────────────────────────────────────────────────
INFO stats | grep evicted
-- evicted_keys:8472   -- Total keys evicted since server started

INFO memory
-- maxmemory:4294967296        -- Configured limit (4 GB)
-- used_memory:4290000000      -- Currently used (~99% full)
-- mem_fragmentation_ratio:1.2 -- Memory fragmentation (>1.5 is high)

-- Alert thresholds:
-- evicted_keys growing rapidly: eviction is actively removing data.
-- used_memory > 90% of maxmemory: approaching eviction threshold.
-- mem_fragmentation_ratio > 1.5: Redis is wasting memory internally → consider MEMORY PURGE
```

## Section 5: LRU vs LFU — The Approximation Algorithm

**Q6. How does Redis approximate LRU and LFU without maintaining exact access logs — what is the "pool" algorithm?**

A: Exact LRU requires a doubly-linked list of all keys sorted by last access time — O(N) memory and O(1) update per access. Redis uses an approximation that is O(1) memory overhead per key and configurable accuracy:

```
True LRU (why Redis doesn't use it):
  Doubly-linked list: MRU ← K7 ↔ K3 ↔ K1 ↔ K9 ↔ K2 → LRU
  On access of K3: move K3 to head → O(1) pointer update
  On eviction: remove K2 (tail) → O(1)
  Memory: one prev + one next pointer per key = 16 bytes × 1M keys = 16 MB overhead.
  Redis chose: approximate LRU to avoid this overhead.

Redis LRU approximation (the "pool" algorithm, Redis 3.0+):
  Each key stores ONE value: lru_clock (24-bit Unix timestamp in seconds).
  On any access: lru_clock for that key is updated to current time.
  Memory overhead: 3 bytes per key (encoded in the redisObject header).

  Eviction selection:
  1. Sample N random keys (N = maxmemory-samples, default 10).
  2. Add them to an eviction candidate pool (size: 16 entries, sorted by lru_clock).
  3. Evict the key with the OLDEST lru_clock in the pool.
  4. On next eviction: re-use the pool (survivors from last round stay in pool).
     New samples are added only if they are older than the oldest current pool entry.
  Result: pool gradually fills with increasingly older keys → good LRU approximation.
```

```redis
-- ── LRU clock resolution and wrap-around ──────────────────────────────────────
-- lru_clock uses 24 bits at 1-second resolution.
-- Maximum representable time: 2^24 seconds ≈ 194 days.
-- The clock wraps around every 194 days.
-- Redis handles wrap-around: keys idle for > 194 days have incorrect lru_clock.
-- In practice: any key idle for >194 days is a strong LRU candidate anyway.

-- Check a key's LRU idle time:
OBJECT IDLETIME session:abc123
-- → 847  (seconds since last access — computed from lru_clock difference)

-- Sample size impact:
CONFIG SET maxmemory-samples 5    -- Faster, less accurate (good for low memory pressure)
CONFIG SET maxmemory-samples 10   -- Default: good balance
CONFIG SET maxmemory-samples 20   -- Slower, approaches true LRU accuracy

-- ── LFU (Least Frequently Used) counter ──────────────────────────────────────
-- Redis 4.0+ LFU uses an 8-bit counter in the redisObject header.
-- NOT a simple access count (would overflow quickly for popular keys).
-- Uses Morris Counter (probabilistic decrement): logarithmic, not linear.
-- Formula: counter is incremented with probability 1 / (counter × lfu_log_factor + 1)
-- Result: counter grows proportionally to log(access_count).
-- At lfu_log_factor=10 (default):
--   counter=5:   ~10 accesses
--   counter=10:  ~100 accesses
--   counter=20:  ~10,000 accesses
--   counter=30:  ~1,000,000 accesses (max ~255 for 8 bits)

-- LFU counter decay (avoids old popular keys never being evicted):
-- Every lfu_decay_time minutes of idle time: counter is decremented by 1.
-- Default: lfu_decay_time=1 (counter decremented every 1 minute of idleness).
-- After 10 minutes of no access: counter drops by 10 → key becomes eviction candidate.

CONFIG GET lfu-log-factor   -- → lfu-log-factor 10
CONFIG GET lfu-decay-time   -- → lfu-decay-time 1

CONFIG SET lfu-log-factor 20   -- Higher: counter grows more slowly → better for
                                --   workloads where very popular keys need protection
CONFIG SET lfu-decay-time 5    -- Higher: counter decays more slowly → stale
                                --   popular keys survive longer after going cold

-- Check a key's LFU frequency counter:
OBJECT FREQ product:101
-- → 142  (LFU counter value — higher = more frequently used = less likely to evict)

-- ── Choosing between LRU and LFU ──────────────────────────────────────────────
-- LRU (allkeys-lru / volatile-lru):
-- ✓ Best when: recency predicts future access.
--   "If I accessed it recently, I'll probably access it again soon."
-- ✓ Temporal locality: web sessions, real-time feeds, recent query results.
-- ✗ Fails for: scan-resistant workloads. A one-time sequential scan evicts hot keys.
--   Example: one-off report query reads 1M keys → all hot keys evicted.

-- LFU (allkeys-lfu / volatile-lfu):
-- ✓ Best when: frequency predicts future access.
--   "Popular items today will be popular tomorrow."
-- ✓ Temporal frequency: product catalogues, user profiles, shared configurations.
-- ✓ Scan-resistant: one scan doesn't bump all scanned keys to MRU.
-- ✗ Fails for: bursty new keys. A new popular key starts with counter=0
--   and may be evicted before its frequency is established.
-- → Warm-up needed: LFU takes time to learn the access pattern.
```

## Section 6: Expiration in Replication and Persistence

**Q7. How does key expiration interact with replication, persistence (RDB/AOF), and Redis Cluster?**

A: Key expiration is not re-evaluated on replicas or on restore — the absolute timestamp stored at write time remains valid. Understanding how expiry propagates through replication and survives restarts prevents subtle consistency bugs:

```
Expiry and replication — the DEL propagation model:

  PRIMARY                          REPLICA
  ───────                          ───────
  t=0:  SET key "v" EX 60          receives: SET key "v" EX 60
        stores: expiry=t+60         stores: expiry=t+60 (same absolute time)

  t=61: client accesses key         (no client access)
        passive eviction fires       key is expired but Redis hasn't deleted it
        → DELETE key                 waits for primary's DEL command
        → sends DEL key to replica

        OR:
        active eviction cycle
        samples key → it's expired
        → DELETE key
        → sends DEL key to replica   receives DEL → deletes key

  REPLICA READS during t=61 window (before primary sends DEL):
    GET key on replica:
    → Replica checks expiry: expired!
    → Returns (nil) to client (correct behavior)
    → Does NOT delete the key (only primary initiates deletes)
    → Key stays in replica memory until primary's DEL arrives
```

```redis
-- ── Replica expiry: WAIT for replication sync ──────────────────────────────────
-- Pattern: set a key with TTL, immediately read from a replica.
-- Risk: DEL hasn't replicated yet; replica still has the key.
-- But: replica will return (nil) because it checks the expiry timestamp.
-- The key is logically deleted on the replica; it just physically remains.
-- Memory leak risk: expired keys on replicas occupy RAM until DEL arrives.

-- Monitoring expired key replication lag:
-- On replica:
INFO stats | grep expired_stale
-- expired_stale_perc: 0.14    -- % of lookups where key was expired but not yet DEL'd
-- High expired_stale_perc → primary is slow to propagate DELs (high replication lag)

-- ── RDB persistence and expiry ────────────────────────────────────────────────
-- When RDB snapshot is taken: ONLY non-expired keys are saved.
-- Expired keys are NOT written to the RDB file (they're already logically gone).
-- On RESTORE from RDB: expiry timestamps are restored as-is.
-- Keys that expired during the backup-to-restore window: immediately deleted on load.

-- Check: after restoring an RDB from 1 hour ago:
-- A key with EX 7200 at backup time still has ~3600 seconds remaining.
-- A key with EX 1800 at backup time is already expired → deleted on load.
-- This is correct — absolute timestamps survive persistence correctly.

-- ── AOF persistence and expiry ────────────────────────────────────────────────
-- AOF logs every write command including EXPIRE/PEXPIRE.
-- On RESTORE from AOF: commands are replayed in order.
-- EXPIRE commands with relative times:
--   EXPIRE key 3600  → replayed LATER → key gets 3600s TTL from NOW, not from original time.
--   This could extend the lifetime of keys beyond their original intent!
-- EXPIREAT / PEXPIREAT commands: use absolute timestamps → correctly replayed.
-- Recommendation: prefer EXPIREAT / SET ... EXAT for AOF-safe expiry.

-- AOF rewrite removes expired keys:
-- During BGREWRITEAOF: Redis reconstructs the AOF without expired key commands.
-- Result: compact AOF without SET+EXPIRE for already-expired keys.

-- ── Redis Cluster and expiry ──────────────────────────────────────────────────
-- Each slot's master handles expiry for its own keys.
-- No cross-node expiry coordination needed (keys are partitioned, not replicated cross-shard).
-- Keyspace notifications in Cluster: subscribe to each node individually.
-- There is no cluster-wide "key expired" channel.

-- ── WAIT command: ensure expiry DEL reaches replicas ─────────────────────────
-- After deleting or letting a key expire on primary:
-- Ensure the DEL has replicated before reading from a replica:
WAIT 1 100
-- → Blocks until at least 1 replica has acknowledged the latest primary operations,
--   or 100ms timeout.
-- → Returns number of replicas that acknowledged.
-- Use for: strongly-consistent reads after writes/expirations.
```

## Section 7: Keyspace Notifications

**Q8. What are keyspace notifications — how do you subscribe to key expiration events?**

A: Keyspace notifications allow clients to subscribe to events that happen to keys — including expiration events. This enables reactive patterns: invalidate application caches, trigger cleanup jobs, or audit key lifecycles without polling:

```redis
-- ── Enabling keyspace notifications ───────────────────────────────────────────
-- Disabled by default (notifications have CPU overhead).
-- Enable in redis.conf or at runtime:
CONFIG SET notify-keyspace-events "KEA"
-- K: Keyspace events (events published to __keyspace@<db>__ channel)
-- E: Keyevent events (events published to __keyevent@<db>__ channel)
-- A: All events (shorthand for g$lzxetd)
-- g: Generic commands (DEL, EXPIRE, RENAME, ...)
-- $: String commands (SET, GETSET, ...)
-- l: List commands
-- z: Sorted set commands
-- x: Expired events (when a key expires — the one we care about)
-- e: Evicted events (when a key is evicted by maxmemory policy)
-- t: Stream commands
-- d: Module key type events

-- For just expiry and eviction events:
CONFIG SET notify-keyspace-events "Kxe"
-- K: Keyspace events
-- x: Expired key events
-- e: Evicted key events

-- ── Two notification channels ─────────────────────────────────────────────────
-- Channel 1: __keyspace@<db>__:<keyname>  → tells WHAT HAPPENED to this key
-- Channel 2: __keyevent@<db>__:<event>    → tells WHICH KEY experienced this event

-- Example: key "session:abc123" expires in db 0:
-- Keyspace event:  PUBLISH __keyspace@0__:session:abc123 "expired"
-- Keyevent event:  PUBLISH __keyevent@0__:expired "session:abc123"

-- Subscribe to ALL expired key events in db 0 (keyevent channel):
PSUBSCRIBE __keyevent@0__:expired
-- → Receives a message whenever ANY key expires.
-- Message format: { channel: "__keyevent@0__:expired", message: "session:abc123" }
-- The message contains the KEY NAME, not the value (value is already gone).

-- Subscribe to events on a specific key:
PSUBSCRIBE __keyspace@0__:session:abc123
-- → Receives events: "set", "expire", "del", "expired", "evicted"
-- → Monitors the full lifecycle of one specific key.

-- ── Critical limitation of expiry notifications ────────────────────────────────
-- The "expired" notification fires WHEN THE KEY IS DELETED, not when it expires.
-- A key expires at t=60s but active eviction doesn't delete it until t=60.8s.
-- The notification fires at t=60.8s (when deletion occurs), not t=60s.
-- For millisecond-precision expiry triggers: use client-side timers instead.

-- Another critical limitation:
-- If the Redis primary goes down before sending the notification:
-- The notification is LOST. Notifications are not persisted.
-- If a replica is promoted: it will eventually delete the key via active expiry,
-- but the notification for the ORIGINAL expiry may not fire.
-- Keyspace notifications are "best effort", not guaranteed.

-- ── NestJS: subscribing to expiry events ─────────────────────────────────────
import { Injectable, OnModuleInit, Logger } from '@nestjs/common';
import Redis from 'ioredis';
import { InjectRedis } from '@liaoliaots/nestjs-redis';

@Injectable()
export class KeyExpiryListener implements OnModuleInit {
    private readonly logger = new Logger(KeyExpiryListener.name);
    private subscriber: Redis;

    constructor(@InjectRedis() private readonly redis: Redis) {}

    async onModuleInit(): Promise<void> {
        // Enable keyspace notifications (if not set in redis.conf):
        await this.redis.config('SET', 'notify-keyspace-events', 'Kx');

        // Create a DEDICATED subscriber client (subscribe mode blocks other commands):
        this.subscriber = this.redis.duplicate();

        await this.subscriber.psubscribe('__keyevent@0__:expired');

        this.subscriber.on('pmessage', (_pattern, channel, expiredKey) => {
            this.logger.log(`Key expired: ${expiredKey}`);
            this.handleKeyExpiry(expiredKey);
        });
    }

    private handleKeyExpiry(key: string): void {
        if (key.startsWith('session:')) {
            const sessionId = key.replace('session:', '');
            this.sessionCleanupService.onSessionExpired(sessionId);
        }
        if (key.startsWith('lock:')) {
            const lockKey = key.replace('lock:', '');
            this.lockMonitor.onLockExpired(lockKey);
        }
    }
}
```

## Section 8: Application Patterns

**Q9. What are the canonical Redis expiration patterns — how do you implement session management, rate limiting, OTP codes, and caching with correct TTL semantics?**

A: Each expiration pattern has a specific combination of commands that must be used atomically to avoid race conditions between the write and the TTL assignment:

```typescript
import { Injectable }    from '@nestjs/common';
import { InjectRedis }   from '@liaoliaots/nestjs-redis';
import Redis             from 'ioredis';

// ── Pattern 1: Session management (sliding expiration) ────────────────────────
// Session should expire N seconds after the LAST request, not after creation.
// Every request resets the TTL (sliding window).

@Injectable()
export class SessionService {
    private readonly SESSION_TTL = 3600; // 1 hour inactivity timeout

    constructor(@InjectRedis() private readonly redis: Redis) {}

    async createSession(userId: number, data: Record<string, string>): Promise<string> {
        const sessionId = crypto.randomUUID();
        const key = `session:${sessionId}`;

        // HSET + EXPIRE in one pipeline (not atomic, but fast):
        const pipeline = this.redis.pipeline();
        pipeline.hset(key, { userId: String(userId), ...data, createdAt: Date.now().toString() });
        pipeline.expire(key, this.SESSION_TTL);
        await pipeline.exec();

        return sessionId;
    }

    async getSession(sessionId: string): Promise<Record<string, string> | null> {
        const key = `session:${sessionId}`;

        // GETDEL-like pattern: get + reset TTL atomically via Lua
        // Simple version (two commands — race condition if concurrent expire):
        const [data, _] = await this.redis
            .pipeline()
            .hgetall(key)
            .expire(key, this.SESSION_TTL)  // Slide the TTL on every access
            .exec() as [[null, Record<string, string>], [null, number]];

        // If the hash is empty: key doesn't exist (expired or never set)
        if (!data[1] || Object.keys(data[1]).length === 0) return null;
        return data[1];
    }

    async destroySession(sessionId: string): Promise<void> {
        await this.redis.del(`session:${sessionId}`);
    }

    // Sliding window with EXPIRE XX (only slide if key exists, don't resurrect):
    async touchSession(sessionId: string): Promise<boolean> {
        const key = `session:${sessionId}`;
        const result = await this.redis.expire(key, this.SESSION_TTL, 'XX');
        return result === 1; // false = session didn't exist (already expired)
    }
}

// ── Pattern 2: Fixed-window rate limiting ─────────────────────────────────────
// Each window starts fresh. Key expires at the end of the window.
// Simple: one key per user per window, with TTL = window duration.

@Injectable()
export class RateLimiterService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    // Returns: { allowed: boolean, remaining: number, resetInSeconds: number }
    async checkLimit(userId: number, limitPerMinute: number): Promise<RateLimitResult> {
        const windowKey = `rate:${userId}:${Math.floor(Date.now() / 60000)}`; // 1-min window
        // Key changes every minute → new window, old key expires in 1 min

        const lua = `
            local key     = KEYS[1]
            local limit   = tonumber(ARGV[1])
            local window  = tonumber(ARGV[2])
            local current = redis.call('INCR', key)
            if current == 1 then
                redis.call('EXPIRE', key, window)
            end
            return {current, redis.call('TTL', key)}
        `;
        // Lua script: INCR + EXPIRE in one atomic operation.
        // If INCR creates the key (result=1): set EXPIRE.
        // Subsequent INCRs: key already has TTL, don't reset it.

        const [current, ttl] = await this.redis.eval(lua, 1, windowKey, limitPerMinute, 60) as [number, number];

        return {
            allowed:         current <= limitPerMinute,
            remaining:       Math.max(0, limitPerMinute - current),
            resetInSeconds:  ttl,
        };
    }
}

// ── Pattern 3: Sliding window rate limiting (more accurate) ───────────────────
// Uses a sorted set where member=request_timestamp, score=timestamp.
// Count requests in the last N seconds by removing old entries.

async checkSlidingWindow(userId: number, limitPerMinute: number): Promise<boolean> {
    const key   = `rate:sliding:${userId}`;
    const now   = Date.now();
    const window = 60_000; // 1 minute in ms

    const lua = `
        local key     = KEYS[1]
        local now     = tonumber(ARGV[1])
        local window  = tonumber(ARGV[2])
        local limit   = tonumber(ARGV[3])
        local cutoff  = now - window
        redis.call('ZREMRANGEBYSCORE', key, 0, cutoff)    -- Remove old requests
        local count = redis.call('ZCARD', key)             -- Count requests in window
        if count < limit then
            redis.call('ZADD', key, now, now)              -- Add this request
            redis.call('PEXPIRE', key, window)             -- Reset key TTL
            return 1   -- Allowed
        end
        return 0   -- Rate limited
    `;

    const allowed = await this.redis.eval(lua, 1, key, now, window, limitPerMinute) as number;
    return allowed === 1;
}

// ── Pattern 4: OTP / verification code ────────────────────────────────────────
// One-time code, expires after 5 minutes, can only be used once.

@Injectable()
export class OtpService {
    private readonly OTP_TTL = 300; // 5 minutes

    constructor(@InjectRedis() private readonly redis: Redis) {}

    async generateOtp(userId: number): Promise<string> {
        const otp = Math.floor(100000 + Math.random() * 900000).toString(); // 6 digits
        const key = `otp:${userId}`;

        // SET with EX — atomic set + TTL. NX ensures only one OTP at a time:
        await this.redis.set(key, otp, 'EX', this.OTP_TTL);
        // Without NX: allows generating a new OTP before the old one expires.
        // With NX: one OTP at a time (prevents spam).
        // Trade-off: NX blocks re-send until old OTP expires.

        return otp;
    }

    async verifyOtp(userId: number, code: string): Promise<boolean> {
        const key = `otp:${userId}`;

        // Atomic get-and-delete: verify + consume in one step.
        // Prevents replay attacks (code cannot be used twice).
        const lua = `
            local stored = redis.call('GET', KEYS[1])
            if stored == ARGV[1] then
                redis.call('DEL', KEYS[1])
                return 1
            end
            return 0
        `;

        const result = await this.redis.eval(lua, 1, key, code) as number;
        return result === 1;
    }
}

// ── Pattern 5: Cache-aside with TTL ──────────────────────────────────────────
// Read from Redis; on miss, load from DB and cache with TTL.
// TTL determines how stale the cache can be.

@Injectable()
export class ProductCacheService {
    private readonly CACHE_TTL = 300;     // 5 minutes for most products
    private readonly HOT_CACHE_TTL = 60;  // 1 minute for pricing (volatile)

    constructor(
        @InjectRedis()   private readonly redis:          Redis,
        private readonly productRepository: ProductRepository,
    ) {}

    async getProduct(productId: string): Promise<Product> {
        const cacheKey = `product:${productId}`;

        // Try cache first:
        const cached = await this.redis.get(cacheKey);
        if (cached) return JSON.parse(cached);

        // Cache miss: load from DB:
        const product = await this.productRepository.findById(productId);
        if (!product) throw new NotFoundException();

        // Store in cache with TTL:
        await this.redis.set(cacheKey, JSON.stringify(product), 'EX', this.CACHE_TTL);

        return product;
    }

    async invalidateProduct(productId: string): Promise<void> {
        // Explicit invalidation on update (don't wait for TTL):
        await this.redis.del(`product:${productId}`);
    }

    // Stale-while-revalidate: return stale data, refresh in background.
    async getProductSWR(productId: string): Promise<Product> {
        const cacheKey      = `product:${productId}`;
        const lockKey       = `product:refresh:${productId}`;
        const STALE_TTL     = 600;  // Cache entry lives up to 10 minutes
        const FRESH_TTL     = 300;  // Data is "fresh" for 5 minutes

        const [cachedJson, remainingTtl] = await this.redis
            .pipeline()
            .get(cacheKey)
            .ttl(cacheKey)
            .exec() as [[null, string | null], [null, number]];

        if (cachedJson[1]) {
            const cached = JSON.parse(cachedJson[1]);
            // If TTL < STALE_TTL - FRESH_TTL: data is stale → refresh in background
            if (remainingTtl[1] < (STALE_TTL - FRESH_TTL)) {
                // Non-blocking refresh: acquire lock to prevent stampede
                const locked = await this.redis.set(lockKey, '1', 'EX', 10, 'NX');
                if (locked === 'OK') {
                    // Background refresh (fire-and-forget):
                    this.productRepository.findById(productId).then(async (fresh) => {
                        if (fresh) {
                            await this.redis.set(cacheKey, JSON.stringify(fresh), 'EX', STALE_TTL);
                        }
                        await this.redis.del(lockKey);
                    }).catch(console.error);
                }
            }
            return cached; // Return stale data immediately (SWR pattern)
        }

        // Full cache miss: synchronous load
        const product = await this.productRepository.findById(productId);
        await this.redis.set(cacheKey, JSON.stringify(product), 'EX', STALE_TTL);
        return product;
    }
}

// ── Pattern 6: Distributed lock with auto-release TTL ─────────────────────────
// Critical: the lock MUST auto-release if the holder crashes.
// SET NX EX provides atomic lock acquisition + TTL in one command.

@Injectable()
export class DistributedLockService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async withLock<T>(
        resource:   string,
        ttlSeconds: number,
        work:       () => Promise<T>,
    ): Promise<T> {
        const lockKey = `lock:${resource}`;
        const ownerId = crypto.randomUUID(); // Unique per lock holder

        // Atomic acquire: SET NX EX
        const acquired = await this.redis.set(lockKey, ownerId, 'EX', ttlSeconds, 'NX');
        if (acquired !== 'OK') {
            throw new ConflictException(`Resource ${resource} is locked`);
        }

        try {
            return await work();
        } finally {
            // Release ONLY if we still own the lock (prevent releasing another holder's lock):
            const lua = `
                if redis.call('GET', KEYS[1]) == ARGV[1] then
                    return redis.call('DEL', KEYS[1])
                else
                    return 0
                end
            `;
            await this.redis.eval(lua, 1, lockKey, ownerId);
        }
    }
}
```

## Section 9: Advanced TTL Patterns

**Q10. How do you implement TTL extension, TTL inheritance, and handling of the cache stampede problem?**

A: Several subtle problems arise at scale with TTL-based caching — thundering herds when popular keys expire simultaneously, the difficulty of atomically reading and extending a TTL, and the propagation of TTLs through derived keys:

```typescript
// ── Cache stampede / thundering herd prevention ────────────────────────────────
// Problem: 1000 concurrent requests for the same expired key.
// Without protection: all 1000 go to the database simultaneously.

@Injectable()
export class StampedeProtectedCache {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    // ── Solution A: Probabilistic early expiration (XFetch algorithm) ─────────
    // Randomly trigger a cache refresh BEFORE the key expires.
    // Higher probability of early refresh as TTL decreases.
    async getWithEarlyExpiry<T>(
        key:     string,
        loader:  () => Promise<T>,
        ttl:     number,
        beta  =  1.0,  // Higher beta = more aggressive early refresh
    ): Promise<T> {
        const deltaKey = `${key}:delta`; // Stores how long the last fetch took

        const [cached, ttlMs, delta] = await this.redis
            .pipeline()
            .get(key)
            .pttl(key)
            .get(deltaKey)
            .exec() as [[null, string|null], [null, number], [null, string|null]];

        if (cached[1] !== null) {
            const computeDeltaMs = parseFloat(delta[1] ?? '0') || 100;
            const remainingMs    = ttlMs[1];
            // XFetch formula: should_refresh = random() < beta × delta × log(1/random())
            // Simplified: refresh if remaining TTL is less than beta × delta × random factor
            const shouldRefreshEarly = remainingMs > 0 &&
                -computeDeltaMs * beta * Math.log(Math.random()) > remainingMs;

            if (!shouldRefreshEarly) return JSON.parse(cached[1]);
        }

        // Fetch fresh data (this instance is the refresher):
        const start  = Date.now();
        const fresh  = await loader();
        const elapsed = Date.now() - start;

        await this.redis
            .pipeline()
            .set(key,      JSON.stringify(fresh),     'EX', ttl)
            .set(deltaKey, elapsed.toString(),         'EX', ttl)
            .exec();

        return fresh;
    }

    // ── Solution B: Request coalescing (mutex per cache key) ───────────────────
    // Only ONE request fetches from DB on cache miss; others wait for it.
    private readonly inflight = new Map<string, Promise<any>>();

    async getCoalesced<T>(key: string, loader: () => Promise<T>, ttl: number): Promise<T> {
        // Check cache first:
        const cached = await this.redis.get(key);
        if (cached) return JSON.parse(cached);

        // Already loading: join the existing promise instead of spawning a new DB call:
        if (this.inflight.has(key)) {
            return this.inflight.get(key)!;
        }

        // First miss: load and cache:
        const fetchPromise = loader().then(async (data) => {
            await this.redis.set(key, JSON.stringify(data), 'EX', ttl);
            this.inflight.delete(key);
            return data;
        }).catch((err) => {
            this.inflight.delete(key);
            throw err;
        });

        this.inflight.set(key, fetchPromise);
        return fetchPromise;
    }
}

// ── TTL inheritance: child keys expire with parent ────────────────────────────
// Redis has no built-in parent-child key relationship.
// Simulate it: store child keys' names in the parent, expire them manually.

@Injectable()
export class GroupedExpiryService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async setWithGroup(
        groupKey:   string,
        memberKey:  string,
        value:      string,
        groupTtl:   number,
    ): Promise<void> {
        const pipeline = this.redis.pipeline();
        // Store the value with the same TTL as the group:
        pipeline.set(memberKey, value, 'EX', groupTtl);
        // Track member in the group's set:
        pipeline.sadd(groupKey, memberKey);
        pipeline.expire(groupKey, groupTtl);
        await pipeline.exec();
    }

    async expireGroup(groupKey: string): Promise<void> {
        const members = await this.redis.smembers(groupKey);
        if (members.length === 0) return;

        const pipeline = this.redis.pipeline();
        members.forEach(member => pipeline.del(member));
        pipeline.del(groupKey);
        await pipeline.exec();
    }
}

// ── Atomic read + extend pattern (GET + EXPIRE atomically) ────────────────────
// Non-atomic: GET then EXPIRE → race condition if key expires between them.
// Atomic via Lua:

@Injectable()
export class AtomicSessionService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async getAndSlide(sessionId: string, ttlSeconds: number): Promise<string | null> {
        const lua = `
            local value = redis.call('GET', KEYS[1])
            if value then
                redis.call('EXPIRE', KEYS[1], ARGV[1])
                return value
            end
            return nil
        `;
        const result = await this.redis.eval(
            lua, 1, `session:${sessionId}`, ttlSeconds
        ) as string | null;
        return result;
    }
}
```

## Section 11: Scenario-Based Questions

**Q12. "Redis memory is growing unboundedly even though we set TTLs on all cache keys — what is happening?"**

A: This is the most common Redis memory leak pattern. Several mechanisms can bypass or extend TTL beyond the intended value:

```redis
-- ── Diagnosis ─────────────────────────────────────────────────────────────────
-- Step 1: Check if keys actually have TTLs set:
INFO keyspace
-- db0:keys=2847293,expires=12847
-- Only 12,847 of 2.8 million keys have TTLs! 99.5% are persistent. ← Root cause

-- Step 2: Find which key types are persistent:
redis-cli --scan --pattern "*" | shuf -n 1000 | while read key; do
    ttl=$(redis-cli TTL "$key")
    type=$(redis-cli TYPE "$key")
    if [ "$ttl" -eq -1 ]; then echo "$type $key"; fi
done | awk '{print $1}' | sort | uniq -c | sort -rn
-- → 892 hash      (session hashes without TTL)
-- → 43 string     (some string keys without TTL)

-- Step 3: Check if PERSIST is accidentally called:
-- Grep application code for: redis.persist(), PERSIST command in Lua scripts

-- Step 4: Check SET command usage:
-- SET key value      → CLEARS the existing TTL! (no EX option = persistent)
-- SET key value EX N → Correctly sets value + TTL atomically

-- ── Common causes of TTL bypass ────────────────────────────────────────────────

-- Cause 1: Using SET without EX to update a value (strips existing TTL):
-- WRONG:
SET session:abc123 "data" EX 3600    -- Creates key with TTL
-- ... later ...
SET session:abc123 "updated_data"    -- Updates but STRIPS the TTL! Key is now persistent.

-- CORRECT: use KEEPTTL option (Redis 6.0+):
SET session:abc123 "updated_data" KEEPTTL   -- Updates value, preserves existing TTL

-- OR: use HSET for hash updates (HSET doesn't touch the key's TTL):
HSET session:abc123 field "updated_value"   -- TTL preserved ✓

-- Cause 2: PERSIST called accidentally (e.g., in error handling):
-- Code pattern: trying to recover an expired key by removing its TTL
-- → makes the key permanent instead of letting it expire

-- Cause 3: Keys created without TTL in a code path that was supposed to set one:
-- Example: cache warming job creates keys but forgets to EXPIRE them.
-- All 2M warmed keys are now persistent.
-- FIX: add a TTL to every warming operation.

-- Cause 4: maxmemory-policy = noeviction + no TTLs = memory fills up:
-- noeviction: never evict → memory just grows.
-- Without TTLs: keys never self-expire.
-- FIX A: set TTLs on all cache keys.
-- FIX B: change policy to allkeys-lru if Redis is a pure cache.

-- ── Batch fix: add TTL to all persistent keys ─────────────────────────────────
redis-cli --scan --pattern "cache:*" | while read key; do
    ttl=$(redis-cli TTL "$key")
    if [ "$ttl" -eq -1 ]; then
        redis-cli EXPIRE "$key" 3600  -- Add 1 hour TTL to each persistent cache key
    fi
done
-- WARNING: This is slow for millions of keys. Use SCAN + pipeline in production.

-- TypeScript batch fix:
async function fixMissingTtls(redis: Redis, pattern: string, ttl: number): Promise<void> {
    let cursor = '0';
    let fixed  = 0;
    do {
        const [nextCursor, keys] = await redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
        cursor = nextCursor;

        if (keys.length === 0) continue;
        const pipeline = redis.pipeline();
        keys.forEach(key => pipeline.expire(key, ttl, 'NX')); // NX: only if no TTL
        await pipeline.exec();
        fixed += keys.length;
    } while (cursor !== '0');
    console.log(`Fixed TTLs for ${fixed} keys`);
}
```

**Q13. "Design the complete Redis expiration strategy for a NestJS API with sessions, rate limiting, feature flags, and a product cache."**

A: A complete production strategy layers different TTL patterns based on data volatility, consistency requirements, and eviction priority:

```typescript
// ── Memory budget and eviction policy ─────────────────────────────────────────
// Redis config:
// maxmemory 8gb
// maxmemory-policy volatile-lfu    ← LFU for cached data; never evict persistent keys
//                                     (feature flags and locks have no TTL — never evicted)
// hz 20                             ← Check expiry 20x/second (more accurate TTL)
// notify-keyspace-events Kx         ← Expiry notifications for session cleanup

// Key taxonomy (ALL keys explicitly categorised):
//
// PERSISTENT (no TTL) — not evicted:
//   feature:*      Feature flags (business critical, change rarely)
//   config:*       Runtime configuration
//
// SHORT TTL (volatile-lfu priority eviction):
//   lock:*         30s  — Distributed locks (auto-release on crash)
//   otp:*          300s — One-time passwords (5 minutes)
//   rate:*         60s  — Rate limit windows (1 minute)
//
// MEDIUM TTL:
//   session:*      3600s — User sessions (1 hour, sliding)
//   token:*        900s  — API tokens (15 minutes, fixed)
//
// LONG TTL (high eviction priority if memory needed):
//   product:*      300s  — Product data (5 minutes, cache-aside)
//   user:*         600s  — User profiles (10 minutes)
//   search:*       60s   — Search results (1 minute)

@Module({
    imports: [
        RedisModule.forRootAsync({
            useFactory: (config: ConfigService) => ({
                config: {
                    host:     config.getOrThrow('REDIS_HOST'),
                    port:     config.get<number>('REDIS_PORT', 6379),
                    password: config.get('REDIS_PASSWORD'),
                    db:       0,
                    // Connection pool:
                    maxRetriesPerRequest: 3,
                    retryStrategy: (times) => Math.min(times * 50, 2000),
                    // Keyspace notifications for session cleanup:
                    // Enabled via CONFIG SET at app startup (see onModuleInit).
                },
            }),
            inject: [ConfigService],
        }),
    ],
})
export class CacheModule implements OnModuleInit {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async onModuleInit(): Promise<void> {
        // Enable keyspace notifications (idempotent):
        await this.redis.config('SET', 'notify-keyspace-events', 'Kx');
        this.redis.config('SET', 'hz', '20');
    }
}

// ── Feature flags: persistent, never expire ───────────────────────────────────
@Injectable()
export class FeatureFlagService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async isEnabled(flag: string, userId?: string): Promise<boolean> {
        const key = `feature:${flag}`;
        // No TTL — feature flags changed explicitly via admin API, not by expiry.
        if (userId) {
            // User-level override (also persistent):
            const userOverride = await this.redis.hget(`feature:overrides:${userId}`, flag);
            if (userOverride !== null) return userOverride === '1';
        }
        const value = await this.redis.get(key);
        return value === '1';
    }

    async setFlag(flag: string, enabled: boolean): Promise<void> {
        // PERSIST key intentionally — feature flags don't expire.
        await this.redis.set(`feature:${flag}`, enabled ? '1' : '0');
        // No EXPIRE — persistent by design.
    }
}

// ── Session: sliding TTL with keyspace notification cleanup ───────────────────
@Injectable()
export class SessionService {
    private readonly SESSION_TTL = 3600;

    async get(sessionId: string): Promise<SessionData | null> {
        const lua = `
            local v = redis.call('HGETALL', KEYS[1])
            if #v == 0 then return nil end
            redis.call('EXPIRE', KEYS[1], ARGV[1])
            return v
        `;
        const result = await this.redis.eval(lua, 1, `session:${sessionId}`, this.SESSION_TTL);
        if (!result) return null;
        // Convert flat array [k1, v1, k2, v2, ...] to object:
        const flat = result as string[];
        return Object.fromEntries(
            Array.from({ length: flat.length / 2 }, (_, i) => [flat[i*2], flat[i*2+1]])
        ) as SessionData;
    }
}

// ── Product cache: LFU-aware TTL with stampede protection ─────────────────────
@Injectable()
export class ProductCacheService {
    // Hot products get longer TTLs so LFU keeps them in memory longer:
    private readonly HOT_TTL  = 1800;  // 30 minutes for hot items
    private readonly COLD_TTL =  120;  // 2 minutes for rarely accessed items

    async get(productId: string): Promise<Product> {
        const key = `product:${productId}`;

        // Get value AND its access frequency:
        const [cached, freq] = await this.redis
            .pipeline()
            .get(key)
            .object('FREQ', key)
            .exec() as [[null, string|null], [null, number|null]];

        if (cached[1]) return JSON.parse(cached[1]);

        // Cache miss: load from DB:
        const product = await this.productRepo.findById(productId);

        // Adaptive TTL: more frequent access → longer TTL:
        const accessFreq = freq[1] ?? 0;
        const ttl = accessFreq > 50 ? this.HOT_TTL : this.COLD_TTL;

        await this.redis.set(key, JSON.stringify(product), 'EX', ttl);
        return product;
    }
}
```

### Expiration Command Reference

| Command | Precision | Absolute/Relative | Condition support | Returns |
|---|---|---|---|---|
| `EXPIRE key s` | Seconds | Relative | NX, XX, GT, LT (v7.0+) | 1=set, 0=not set |
| `PEXPIRE key ms` | Milliseconds | Relative | NX, XX, GT, LT (v7.0+) | 1=set, 0=not set |
| `EXPIREAT key ts` | Seconds | Absolute | NX, XX, GT, LT (v7.0+) | 1=set, 0=not set |
| `PEXPIREAT key ms-ts` | Milliseconds | Absolute | NX, XX, GT, LT (v7.0+) | 1=set, 0=not set |
| `TTL key` | Seconds | — | — | secs, -1=persist, -2=missing |
| `PTTL key` | Milliseconds | — | — | ms, -1=persist, -2=missing |
| `PERSIST key` | — | — | — | 1=removed, 0=no TTL or missing |
| `SET key val EX s` | Seconds | Relative | NX, XX | OK or nil |
| `SET key val EXAT ts` | Seconds | Absolute | NX, XX | OK or nil |
| `SET key val KEEPTTL` | Preserved | — | NX, XX | OK or nil |

### Eviction Policy Decision Guide

| Scenario | Recommended policy | Reason |
|---|---|---|
| Pure cache (all keys can be evicted) | `allkeys-lru` or `allkeys-lfu` | Any key is expendable |
| Mixed: cache (TTL) + persistent data | `volatile-lru` or `volatile-lfu` | Only evict TTL keys |
| Access pattern is recency-based | `allkeys-lru` / `volatile-lru` | Recent = probably needed again |
| Popular items stay popular | `allkeys-lfu` / `volatile-lfu` | Frequency > recency |
| Redis is a database (no data loss) | `noeviction` | Reject writes instead of data loss |
| TTL = value proxy (shorter = less valuable) | `volatile-ttl` | Evict soonest-expiring first |
| Uniform access, no pattern | `allkeys-random` | No intelligence needed |

### Active vs Passive Eviction Comparison

| Property | Passive (lazy) | Active (background) |
|---|---|---|
| When it fires | On key access | Every 1/hz seconds (default: 100ms) |
| Keys cleaned | Only accessed expired keys | Random sample of ALL volatile keys |
| Guaranteed? | No — unaccessed keys may linger | Probabilistic — ≤25% may linger |
| CPU cost | Per-access check (~0μs) | Periodic cycle (up to 25ms) |
| Memory reclaimed | Immediate on access | Eventually (within seconds) |
| Replication | Primary sends DEL to replicas | Primary sends DEL to replicas |
| Replica behaviour | Returns nil; waits for primary DEL | Does not run (replica-only passive) |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) knowing that **Redis stores expiry as an absolute Unix timestamp in milliseconds** — not "seconds from now" — which means the expiry survives server restarts correctly when RDB/AOF is used, but `EXPIRE` (relative) in AOF replay gives the wrong TTL while `EXPIREAT` (absolute) is safe; (2) being precise that **passive eviction fires on key access** and deletes the key at that moment, while **active eviction is a probabilistic background cycle** that samples 20 random volatile keys every `1/hz` seconds and loops aggressively when more than 25% of samples are expired — both are needed because passive alone would allow unlimited memory growth from unaccessed expired keys; (3) understanding the **replica eviction model**: replicas check the expiry dictionary and return `nil` for expired keys but do NOT delete them independently — they wait for the primary to send a DEL command from its own passive or active eviction, which means expired keys temporarily consume memory on replicas and keyspace notifications only fire from the primary; (4) knowing the **eight eviction policies precisely** and when each is appropriate — the `volatile-*` family only evicts TTL keys (persistent keys are protected), the `allkeys-*` family evicts any key (used for pure caches), `volatile-ttl` treats shorter remaining TTL as lower value, and `noeviction` rejects writes with an OOM error rather than deleting data; (5) understanding **LRU vs LFU**: LRU (approximate, 24-bit lru_clock per key, pool algorithm) evicts the least recently used key, making it optimal for recency-based access patterns; LFU (Morris counter with logarithmic growth and time-based decay) evicts the least frequently used key, making it optimal for stable popularity distributions and resistant to one-time scans that would flush LRU's hot keys; (6) knowing that **SET without EX silently strips an existing TTL**, making a cached key permanent — the correct command to update a value while preserving its TTL is `SET key value KEEPTTL` (Redis 6.0+) or `HSET` for hash fields; (7) understanding the **keyspace notification limitations**: the "expired" notification fires when the key is physically deleted (not when its timestamp passes), notifications are best-effort (lost on failover), you must subscribe to each Redis Cluster node separately (no cluster-wide expiry channel), and a dedicated subscriber client is always required (subscribe mode blocks all other commands on that connection); and (8) knowing the **atomic patterns for TTL-sensitive operations**: `SET key value EX N NX` for atomic create-with-TTL-if-not-exists, Lua scripts for atomic get-and-delete (OTP verification), and pipeline for multi-command operations where partial failure is acceptable but two separate TCP round-trips are not.
