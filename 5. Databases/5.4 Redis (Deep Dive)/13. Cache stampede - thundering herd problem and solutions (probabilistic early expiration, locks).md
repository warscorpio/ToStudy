# Cache Stampede / Thundering Herd Problem and Solutions — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a cache stampede and what causes it?**

A: A cache stampede (also called a "dog pile" effect) occurs when a popular cached key expires and many concurrent requests reach the cache simultaneously, all find a miss, and all simultaneously query the backend data source. The backend — which was protected by the cache — suddenly receives the full traffic load at once:

```
Normal operation (cache hit):
  1000 req/s ──► Cache ──► [HIT] ──► Response
                  ↑
             (Backend sees 0 req/s)

Cache miss (key expired):
  1000 req/s ──► Cache ──► [MISS] ──► 1000 req/s ──► Database
                                          ↑
                                    (Database sees 1000 simultaneous queries
                                     instead of 0 — catastrophic overload)
```

**The anatomy of a stampede:**

```
Timeline:
  t=0s:  Key "leaderboard:global" set with TTL=3600s
  t=3600s: TTL expires — key no longer in cache

  t=3600.000s: Request 1 → GET leaderboard:global → MISS
  t=3600.001s: Request 2 → GET leaderboard:global → MISS
  t=3600.002s: Request 3 → GET leaderboard:global → MISS
  ...
  t=3600.100s: Requests 1-1000 all hitting the database simultaneously
               (All arrived in the 100ms before any could finish and repopulate cache)

  t=3601.500s: Request 1 finishes → sets cache (1500ms DB query)
  t=3601.501s: Requests 2-1000 also set cache (redundant work, DB already overwhelmed)

  Database during this window:
    - 1000 complex queries running simultaneously
    - Connection pool exhausted
    - Query queue fills up
    - Response times increase → more timeouts → more retries → amplification
    - Potential complete database outage
```

**Root causes:**
```
1. Time-based expiration: Most common trigger — a single TTL causing simultaneous misses
2. Cache flush / FLUSHDB: Deployment clears the entire cache → all keys miss at once
3. Cold start: New cache instance with empty data — every key misses
4. Vertical scaling event: New cache node joining (resharding moves keys)
5. Memory pressure eviction: LRU/LFU evicts popular keys under memory pressure
6. Correlated TTLs: Many keys set at the same time → expire at the same time
```

**Q2. How does "thundering herd" relate to cache stampede, and what is the broader pattern?**

A: "Thundering herd" is an older term from operating systems describing any situation where many processes/threads simultaneously wake up competing for a single resource, causing contention and wasted work. Cache stampede is one specific instance:

```
Thundering herd in different contexts:

1. OS: accept() with multiple processes
   - Linux pre-3.9: many processes in listen socket's accept queue all wake up
     when ONE connection arrives
   - All but one get EAGAIN, waste CPU context-switching
   - Fixed by: SO_REUSEPORT (delivers to only ONE listener) in Linux 3.9+

2. Thread pool / worker pool:
   - Task completes a batch job, notifies ALL waiting workers with broadcast
   - All workers wake up, fight for the lock, one wins, 99 go back to sleep
   - Fix: signal (wake one) vs broadcast (wake all)

3. Connection pool:
   - Database connection limit reached; 500 app threads waiting
   - One connection released → all 500 threads try to acquire it
   - Fix: queue-based pool with fair scheduler

4. Cache stampede (our focus):
   - Popular cache key expires → all waiting requests miss simultaneously
   - All hit the backing store at once
   - Fix: locking, probabilistic early expiry, background refresh

5. Load balancer leader election:
   - All nodes detect leader failure simultaneously
   - All nodes try to become leader at the same time
   - Fix: randomized election timeouts (Raft protocol)

Common thread across all thundering herd scenarios:
  1. A shared resource becomes unavailable
  2. Many waiting processes detect this simultaneously
  3. All attempt to acquire/reconstruct the resource simultaneously
  4. Only one can succeed; the rest waste effort or cause harm
  Solutions: Serialization (lock), Jitter (spread timing), Optimistic probability
```

## Section 2: The Problem in Depth

**Q3. What are the cascading failure modes of a cache stampede?**

A:

```
Cascade chain — how one expired key can cause a full outage:

Phase 1: Cache miss storm (t=0 to t+2s)
  - 5000 requests/second; cache hit rate drops from 99% to 0%
  - All 5000 req/s hit the database
  - Database normally handles 100 req/s (cache protected it)
  - Database query queue fills up → queries take 10x longer

Phase 2: Timeout amplification (t+2s to t+10s)
  - Slow database responses → application layer timeouts (30s default)
  - Client retries → 5000 req/s × 3 retries = 15,000 req/s to database
  - Connection pool: 200 connections × 30s = 200 connections held for 30s
  - New requests cannot get connections → application errors

Phase 3: Resource exhaustion (t+10s to t+30s)
  - Application server memory: 15K concurrent requests × 2MB per request = 30GB
  - JVM / Node.js heap exhausted → OOM errors → process restarts
  - Restarted processes have cold caches → amplify the stampede further
  - Health checks fail → load balancer removes instances → fewer servers = more load per server

Phase 4: Complete outage (t+30s onward)
  - Database connections exhausted → all queries fail
  - Application returns 500 errors to all users
  - Monitoring alerts firing → on-call engineer paged at 3 AM

Metrics to watch during a stampede:
  - Cache hit rate: sudden drop (99% → 0%)
  - Database query rate: sudden spike
  - Database connection count: approaching max_connections
  - Application p99 latency: sudden spike (10ms → 10,000ms)
  - Application error rate: sudden spike
  - Kubernetes pod restarts (OOM): increasing
```

**Q4. When are applications most vulnerable to cache stampedes?**

A:

```
High-vulnerability scenarios:

1. Single hot key with many concurrent readers:
   - A viral post, a trending product, a live sports score
   - 50,000 req/s hitting one key → all 50K miss simultaneously at expiry
   - The hotter the key, the worse the stampede

2. Deployment or cache flush events:
   - Rolling deployment: new pods start with empty caches
   - All pods restart simultaneously → all caches empty → all requests miss
   - Scheduled FLUSHDB for cache invalidation → equivalent to mass TTL expiry

3. Coordinated TTL expiry:
   - Batch job runs at midnight, populates 10,000 keys with TTL=86400
   - The NEXT midnight: all 10,000 keys expire simultaneously
   - 10,000 different keys all miss at once

4. After a cache maintenance window:
   - Cache server upgraded / replaced
   - Application reconnects → empty cache → stampede

5. Seasonal traffic spikes:
   - Black Friday: 100x normal traffic
   - Cache was sized for normal traffic
   - Under load: LRU evictions → suddenly hot keys evicted under high traffic
   - Worst case: highest traffic → highest stampede risk

Identifying at-risk keys in production:
```

```typescript
// Track which keys cause the most backend calls on cache miss:
class InstrumentedCache {
  private missCounters = new Map<string, number>();

  async get<T>(key: string, fetchFn: () => Promise<T>, ttl: number): Promise<T> {
    const cached = await redis.get(key);
    if (cached) return JSON.parse(cached);

    // Record the miss:
    this.missCounters.set(key, (this.missCounters.get(key) ?? 0) + 1);

    const value = await fetchFn();
    await redis.setex(key, ttl, JSON.stringify(value));
    return value;
  }

  getHotMissKeys(threshold = 100): string[] {
    return [...this.missCounters.entries()]
      .filter(([, count]) => count > threshold)
      .sort(([, a], [, b]) => b - a)
      .map(([key]) => key);
    // These keys are stampede candidates → prioritize protection
  }
}
```

## Section 3: Solution — Locking

**Q5. How does a distributed lock prevent a cache stampede?**

A: A lock ensures only one process recomputes the cache value when a miss occurs. All other processes that miss the cache acquire the same lock — and block until the winner has repopulated the cache:

```typescript
// Naive locking (works but blocks waiting requests):
async function getWithLock<T>(
  key:     string,
  fetchFn: () => Promise<T>,
  ttl:     number
): Promise<T> {
  // Try to get from cache first:
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const lockKey   = `lock:${key}`;
  const lockToken = crypto.randomUUID();
  const lockTTL   = 30;  // seconds — prevent lock holder from holding forever

  // Try to acquire the lock (NX = only set if Not eXists):
  const acquired = await redis.set(lockKey, lockToken, 'NX', 'EX', lockTTL);

  if (acquired === 'OK') {
    // This process WON the lock — we compute the value:
    try {
      const value = await fetchFn();
      await redis.setex(key, ttl, JSON.stringify(value));
      return value;
    } finally {
      // Release lock (only if we still own it — Lua script for atomicity):
      await releaseLock(lockKey, lockToken);
    }
  } else {
    // Another process holds the lock — wait and poll:
    const result = await waitForCache(key, 30_000);  // max 30s wait
    if (result !== null) return result;
    // If still not available after timeout, throw or fallback:
    throw new CacheComputationTimeout(`Cache not populated within 30s for key: ${key}`);
  }
}

async function waitForCache<T>(key: string, maxWaitMs: number): Promise<T | null> {
  const start = Date.now();
  while (Date.now() - start < maxWaitMs) {
    await sleep(50);  // Poll every 50ms
    const value = await redis.get(key);
    if (value) return JSON.parse(value);
  }
  return null;
}

// Lua script for atomic lock release (see Lua scripting doc):
async function releaseLock(lockKey: string, token: string): Promise<void> {
  await redis.eval(
    `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end`,
    1, lockKey, token
  );
}
```

**Q6. What is the "stale-while-recomputing" pattern and why is it critical for user experience?**

A: The naive lock approach makes ALL waiting requests block — potentially for 5-30 seconds — while the winning process recomputes the value. The stale-while-recomputing pattern serves the previous (slightly outdated) value to all waiters immediately, blocking zero requests:

```typescript
// Key insight: store the stale value separately with a longer TTL
// So when the primary key expires, we can still serve the old data

interface CacheEntry<T> {
  value:     T;
  computedAt: number;  // Unix timestamp ms
}

async function getWithLockAndStale<T>(
  key:           string,
  fetchFn:       () => Promise<T>,
  ttl:           number,    // seconds — "fresh" TTL
  staleTtl:      number = ttl * 2   // stale copy lives 2× longer
): Promise<{ value: T; stale: boolean }> {
  const staleKey  = `stale:${key}`;
  const lockKey   = `lock:${key}`;
  const lockToken = crypto.randomUUID();

  // Check fresh cache first:
  const fresh = await redis.get(key);
  if (fresh) return { value: JSON.parse(fresh), stale: false };

  // Fresh key expired — try to acquire lock for recompute:
  const acquired = await redis.set(lockKey, lockToken, 'NX', 'EX', 30);

  if (acquired === 'OK') {
    // Won the lock — check one more time (double-check: another process may have
    // just finished computing and set the key right before we got the lock):
    const doubleCheck = await redis.get(key);
    if (doubleCheck) {
      await releaseLock(lockKey, lockToken);
      return { value: JSON.parse(doubleCheck), stale: false };
    }

    // We really need to compute:
    try {
      const value = await fetchFn();
      // Store fresh AND stale versions:
      await redis.pipeline()
        .setex(key,      ttl,      JSON.stringify(value))
        .setex(staleKey, staleTtl, JSON.stringify(value))  // Keep longer as backup
        .exec();
      return { value, stale: false };
    } finally {
      await releaseLock(lockKey, lockToken);
    }

  } else {
    // Lost the lock — serve stale if available (no blocking!):
    const stale = await redis.get(staleKey);
    if (stale) {
      // Return stale data immediately — user doesn't wait
      return { value: JSON.parse(stale), stale: true };
    }

    // No stale data (truly cold cache) — must wait for the lock holder:
    const result = await waitForCache<T>(key, 15_000);
    if (result) return { value: result, stale: false };

    throw new CacheTimeoutError(`Could not get value for ${key}`);
  }
}

// Middleware usage — transparently handles stale marking:
app.get('/api/leaderboard', async (req, res) => {
  const { value, stale } = await getWithLockAndStale(
    'leaderboard:global',
    () => computeLeaderboard(),
    300    // fresh TTL: 5 minutes
  );

  if (stale) {
    res.setHeader('X-Cache-Status', 'STALE');  // Visible in DevTools for debugging
  }
  res.json(value);
});
```

**Q7. What are the failure modes of lock-based stampede prevention?**

A:

```
Failure 1: Lock holder crashes before populating cache
  - Process A wins lock, starts computing
  - Process A crashes (OOM, SIGKILL, unhandled exception)
  - Lock has a TTL (e.g., 30s) → lock auto-expires after 30s
  - For 30 seconds: all requesters either wait or get stale data
  - After 30s: next requester wins lock and recomputes
  - Risk: long computation + lock TTL too short → lock expires while computing
           → two processes computing simultaneously → redundant work (not stampede)

Failure 2: Lock TTL shorter than computation time
  - Computation takes 45s but lockTTL=30s
  - At 30s: lock expires while process A is still computing
  - Process B sees no lock → acquires lock → also starts computing
  - Both A and B finish → both write to cache → wasted work (but not catastrophic)
  - Fix: set lock TTL to (expected_compute_time × 3) OR extend the lock periodically

Failure 3: All stale copies expired (truly cold cache):
  - Application restarts, cold start, new deployment
  - No fresh data AND no stale data
  - All requests waiting on the lock holder to compute
  - Effectively: one process computes, all others block — this is acceptable
  - Mitigation: cache warming at startup (see Q17)

Failure 4: Noisy waiters under extreme load:
  - 10,000 req/s hitting the same key
  - One process computes (30s), 9,999 × 30s of threads waiting
  - Memory exhaustion from 10,000 blocked threads/coroutines

  Fix: Add a waiting limit — if more than N requests are waiting, return error:
```

```typescript
class StampedeLock {
  private waiting = new Map<string, number>();  // key → count of waiters
  private readonly MAX_WAITERS = 50;

  async get<T>(key: string, fetchFn: () => Promise<T>, ttl: number): Promise<T> {
    const cached = await redis.get(key);
    if (cached) return JSON.parse(cached);

    const currentWaiters = this.waiting.get(key) ?? 0;
    if (currentWaiters >= this.MAX_WAITERS) {
      // Too many waiters — fail fast (circuit breaker pattern):
      throw new TooManyWaitersError(`Stampede protection: ${key} has ${currentWaiters} waiters`);
    }

    this.waiting.set(key, currentWaiters + 1);
    try {
      return await this.computeWithLock(key, fetchFn, ttl);
    } finally {
      const count = this.waiting.get(key) ?? 1;
      if (count <= 1) this.waiting.delete(key);
      else this.waiting.set(key, count - 1);
    }
  }
}
```

## Section 4: Probabilistic Early Expiration (XFetch)

**Q8. What is the XFetch algorithm and how does probabilistic early expiration work?**

A: XFetch (from the paper "Optimal Probabilistic Cache Stampede Prevention" by Vattani, Chierichetti, and Lowenstein, 2015) solves stampede without locking. Each cache reader independently decides — with increasing probability as expiry approaches — to recompute the value early. Because the decision is probabilistic and independent per client, recomputes are spread over time rather than concentrated at the exact expiry moment:

```
The XFetch decision formula:
  Recompute early if:
    current_time − β × δ × log(rand()) > expiry_time

Where:
  current_time: Unix timestamp (now)
  expiry_time:  Unix timestamp when the cached value expires
  δ (delta):    Time to recompute the value (seconds) — stored alongside the value
  β (beta):     Tuning parameter (default: 1.0)
  rand():       Uniform random number in (0, 1) — each caller independently draws one

Simplify: let remaining_ttl = expiry_time − current_time
  The formula is equivalent to:
    −β × δ × log(rand()) > remaining_ttl
  Since −log(U) where U~Uniform(0,1) is Exponential(1):
    β × δ × Exponential(1) > remaining_ttl

Probability of recomputing at a given remaining TTL:
  P(recompute | remaining_ttl = t) = e^(−t / (β × δ))

Examples with β=1, δ=2s (recompute takes 2 seconds):
  t = 20s remaining → P = e^(−20/2) = e^(−10) ≈ 0.0045%  (very unlikely)
  t = 10s remaining → P = e^(−10/2) = e^(−5)  ≈ 0.67%    (rare)
  t = 4s  remaining → P = e^(−4/2)  = e^(−2)  ≈ 13.5%    (sometimes)
  t = 2s  remaining → P = e^(−2/2)  = e^(−1)  ≈ 36.8%    (often)
  t = 0s  remaining → P = e^(0)     = 1        = 100%     (always — expired)
```

```typescript
// XFetch implementation:
interface XFetchEntry<T> {
  value:      T;
  delta:      number;   // Milliseconds it took to compute (measured at set time)
  expiry:     number;   // Unix timestamp ms when this entry expires
}

class XFetchCache {
  constructor(
    private redis: Redis,
    private beta: number = 1.0
  ) {}

  async get<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    ttlMs:   number              // Desired TTL in milliseconds
  ): Promise<T> {
    const raw = await redis.get(key);

    if (raw !== null) {
      const entry: XFetchEntry<T> = JSON.parse(raw);
      const now           = Date.now();
      const remainingMs   = entry.expiry - now;

      // XFetch decision: should we recompute early?
      // -beta * delta * Math.log(Math.random()) generates an exponential RV
      const earlyRecompute =
        remainingMs <= 0 ||   // Already expired
        (-this.beta * entry.delta * Math.log(Math.random())) > remainingMs;

      if (!earlyRecompute) {
        return entry.value;   // Cache hit — serve existing value
      }

      // Early recompute path — trigger ASYNC (non-blocking):
      // Serve the current (slightly-stale) value immediately,
      // refresh in background:
      this.recomputeAsync(key, fetchFn, ttlMs, entry.delta).catch(err =>
        logger.error('XFetch background recompute failed', { key, err })
      );
      return entry.value;   // Return current value without waiting for refresh
    }

    // True cache miss (no value at all) — must compute synchronously:
    return this.recomputeSync(key, fetchFn, ttlMs);
  }

  private async recomputeSync<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    ttlMs:   number
  ): Promise<T> {
    const start = Date.now();
    const value = await fetchFn();
    const delta = Date.now() - start;   // Measure actual compute time

    await this.store(key, value, delta, ttlMs);
    return value;
  }

  private async recomputeAsync<T>(
    key:       string,
    fetchFn:   () => Promise<T>,
    ttlMs:     number,
    prevDelta: number
  ): Promise<void> {
    const start = Date.now();
    const value = await fetchFn();
    const delta = Date.now() - start;   // Update delta with latest measurement

    await this.store(key, value, delta, ttlMs);
  }

  private async store<T>(
    key:   string,
    value: T,
    delta: number,
    ttlMs: number
  ): Promise<void> {
    const entry: XFetchEntry<T> = {
      value,
      delta,                        // Store compute time for future XFetch decisions
      expiry: Date.now() + ttlMs,   // Store absolute expiry (not relative TTL)
    };
    await redis.set(key, JSON.stringify(entry), 'PX', ttlMs);
    // PX = expire in milliseconds
  }
}

// Usage:
const cache = new XFetchCache(redis, 1.0);

app.get('/api/leaderboard', async (req, res) => {
  const leaderboard = await cache.get(
    'leaderboard:global',
    () => db.query('SELECT ... FROM scores ORDER BY score DESC LIMIT 100'),
    300_000  // 5 minute TTL
  );
  res.json(leaderboard);
});
```

**Q9. How do you tune XFetch's `beta` and `delta` parameters?**

A:

```
β (beta) — controls how aggressively early recompute is triggered:
  β = 1.0:  Default. Recomputes proportionally to compute time.
  β > 1.0:  More aggressive — starts recomputing earlier.
             Use when: stampede would be catastrophic, backend can handle extra load.
  β < 1.0:  Less aggressive — starts recomputing later.
             Use when: compute is expensive, want to minimize redundant work.
  β = 0:    Never early recompute (equivalent to no XFetch).

δ (delta) — the measured time to recompute the value (auto-measured):
  Stored alongside the cached value (measured on the last recompute).
  Key insight: delta is SELF-CALIBRATING — the system learns the actual compute time.
  Under load (slow DB): delta grows → XFetch starts recomputing earlier (self-adapting!)
  Under light load (fast DB): delta shrinks → XFetch starts later (less wasted work)
```

```typescript
// Scenario analysis — choosing beta:

// Scenario 1: High-traffic endpoint, DB can handle some extra load

// With beta=1: at t=59.8s remaining (~compute_time before expiry)
//   P ≈ 36.8% — reasonable early recompute rate
// With beta=2: at t=59.6s remaining (2×compute_time before expiry)
//   P ≈ 36.8% — starts earlier, more redundant computes, better stampede protection

// Scenario 2: Very expensive computation, stampede not catastrophic
// key='monthly:report', ttl=3600s, compute=30,000ms (30 seconds)
// With beta=0.5: at t=15s remaining
//   P ≈ 36.8% — waits until 15s before expiry (less redundant work)

// Practical guidance:
const BETA_PRESETS = {
  'critical':    2.0,   // Mission-critical: aggressively early, accept redundant work
  'default':     1.0,   // Standard: balanced protection
  'expensive':   0.5,   // Costly recompute: conservative early trigger
  'cheap':       1.5,   // Fast recompute: slightly aggressive (overhead is low)
};

// Monitoring XFetch effectiveness:
class MonitoredXFetchCache extends XFetchCache {
  private earlyRecomputeCount = 0;
  private coldMissCount = 0;
  private hitCount = 0;

  getMetrics() {
    const total = this.hitCount + this.earlyRecomputeCount + this.coldMissCount;
    return {
      hitRate:           this.hitCount / total,
      earlyRecomputeRate: this.earlyRecomputeCount / total,   // Should be low
      coldMissRate:      this.coldMissCount / total,           // Should be near 0

}
```

**Q10. What are the advantages of XFetch over lock-based approaches and when does each excel?**

A:

```
XFetch advantages:
  ✓ No locks — no deadlock risk, no lock timeout complexity
  ✓ Never blocks any request — all requests get a value immediately
  ✓ Self-calibrating — delta adapts to actual compute time
  ✓ Stateless — no coordination between processes needed
  ✓ Works across distributed systems without shared lock state
  ✓ Mathematically proven optimal (the paper shows it minimizes stampede risk)
  ✓ Gradually distributes recompute load (not a binary all-or-nothing)

XFetch disadvantages:
  ✗ Requires storing delta alongside the cached value (slightly larger payload)
  ✗ Multiple processes may simultaneously early-recompute (controlled redundancy)
  ✗ Doesn't work without an initial value (cold start still needs synchronous compute)
  ✗ More complex to implement and reason about than a simple lock

Lock-based advantages:
  ✓ Exactly ONE recompute at a time (no redundant work)
  ✓ Simpler to reason about correctness
  ✓ Works for resources where even two simultaneous computes is unacceptable
    (e.g., sending an email — you don't want two processes each sending it)

Lock-based disadvantages:
  ✗ Blocking: all waiters hold connections while waiting
  ✗ Single point of failure: lock holder crash = 30-second wait for everyone
  ✗ Polling overhead on waiters
  ✗ Complex lock release (need Lua script to avoid releasing someone else's lock)

Decision matrix:
  Computation has side effects (email, payment): Use lock — exactly-once matters
  High concurrency (10K+ req/s): Use XFetch — lock bottlenecks at scale
  Can serve stale immediately: Use XFetch + background refresh
  Cold start problem is the main concern: Use cache warming (see Q17)
  Mix of both: XFetch for hot keys, lock for idempotent-critical operations
```

## Section 5: Background Refresh and Logical TTL

**Q11. What is the logical TTL (soft expiration) pattern?**

A: Instead of relying on Redis's hard TTL to trigger cache invalidation, store a "soft expiry" timestamp inside the cached value. The Redis key has a much longer TTL (the stale window), but the application checks the soft expiry and triggers a background refresh if crossed — all while serving the existing (slightly stale) value immediately:

```typescript
interface SoftExpiryEntry<T> {
  value:        T;
  softExpiry:   number;   // Unix ms — when to trigger background refresh
  // Hard TTL (Redis EX) is set to softExpiry + staleWindowMs
}

class SoftExpiryCache {
  constructor(
    private redis:         Redis,
    private staleWindowMs: number = 60_000   // How long after softExpiry to keep stale data
  ) {}

  async set<T>(key: string, value: T, freshTtlMs: number): Promise<void> {
    const entry: SoftExpiryEntry<T> = {
      value,
      softExpiry: Date.now() + freshTtlMs,
    };
    // Hard TTL = softExpiry + staleWindow (keep stale data available for staleWindowMs extra)
    const hardTtlMs = freshTtlMs + this.staleWindowMs;
    await redis.set(key, JSON.stringify(entry), 'PX', hardTtlMs);
  }

  async get<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    ttlMs:   number
  ): Promise<T> {
    const raw = await redis.get(key);

    if (raw === null) {
      // Hard TTL expired (stale window is over) or truly cold cache:
      const value = await fetchFn();
      await this.set(key, value, ttlMs);
      return value;
    }

    const entry: SoftExpiryEntry<T> = JSON.parse(raw);

    if (Date.now() > entry.softExpiry) {
      // SOFT expiry crossed — serve stale immediately, refresh in background:
      this.refreshInBackground(key, fetchFn, ttlMs).catch(err =>
        logger.error('Background refresh failed', { key, err })
      );
      return entry.value;   // Serve stale — no waiting!
    }

    return entry.value;     // Still fresh — serve immediately
  }

  private async refreshInBackground<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    ttlMs:   number
  ): Promise<void> {
    // Prevent multiple concurrent background refreshes for the same key:
    const lockKey = `refresh-lock:${key}`;
    const acquired = await redis.set(lockKey, '1', 'NX', 'PX', ttlMs);
    if (!acquired) return;  // Another process is already refreshing

    try {
      const value = await fetchFn();
      await this.set(key, value, ttlMs);
    } finally {
      await redis.del(lockKey);
    }
  }
}

// Why this is better than hard TTL:
// Hard TTL: key disappears → everyone misses → stampede
// Soft TTL: key always present (until staleWindow ends) → nobody misses
//           background refresh replaces value before hard TTL expires
//           even if refresh fails: stale data still served (degraded not failed)
```

**Q12. What is "stale-while-revalidate" and how does it map to the HTTP Cache-Control header?**

A:

```bash
# HTTP Cache-Control: stale-while-revalidate (RFC 5861)
Cache-Control: max-age=300, stale-while-revalidate=60

# What it means:
# - Fresh for 300 seconds (5 minutes): serve from cache directly
# - Stale for 60 more seconds (5-6 minute range): serve stale + trigger async revalidation
# - After 360 seconds: hard miss, must wait for revalidation before responding

# This is exactly the "soft TTL" pattern applied to HTTP:
# soft_expiry = 300s, stale_window = 60s, hard_expiry = 360s

# In Nginx (proxy_cache_revalidate):
proxy_cache_revalidate on;
proxy_cache_use_stale updating;    # Serve stale while background revalidation runs
```

```typescript
// NestJS interceptor implementing stale-while-revalidate:
@Injectable()
export class StaleWhileRevalidateInterceptor implements NestInterceptor {
  constructor(
    private redis: Redis,
    private ttlMs: number,
    private staleMs: number
  ) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const req  = context.switchToHttp().getRequest<Request>();
    const res  = context.switchToHttp().getResponse<Response>();
    const key  = `swr:${req.method}:${req.url}`;

    return from(this.handleSWR(key, next, res));
  }

  private async handleSWR(
    key:  string,
    next: CallHandler,
    res:  Response
  ): Promise<unknown> {
    const raw = await redis.get(key);

    if (raw) {
      const { value, softExpiry } = JSON.parse(raw);

      if (Date.now() > softExpiry) {
        // Stale — serve immediately and revalidate asynchronously:
        res.setHeader('X-Cache', 'STALE');
        // Fire background refresh (don't await):
        next.handle().pipe(take(1)).subscribe(freshValue => {
          this.store(key, freshValue);
        });
        return value;
      }

      res.setHeader('X-Cache', 'HIT');
      return value;
    }

    // Cache miss — compute synchronously:
    const value = await lastValueFrom(next.handle().pipe(take(1)));
    res.setHeader('X-Cache', 'MISS');
    await this.store(key, value);
    return value;
  }

  private async store(key: string, value: unknown): Promise<void> {
    const entry = { value, softExpiry: Date.now() + this.ttlMs };
    await redis.set(key, JSON.stringify(entry), 'PX', this.ttlMs + this.staleMs);
  }
}
```

## Section 6: In-Process Request Coalescing

**Q13. What is request coalescing and how does it reduce backend load within a single process?**

A: Request coalescing (also called request deduplication or promise coalescing) prevents multiple concurrent requests within the same process from independently querying the backend for the same data. All concurrent requests for the same key share a single in-flight Promise:

```typescript
class CoalescingCache {
  // Map from cache key → in-flight Promise
  // Multiple callers waiting for the same key all receive the SAME Promise:
  private inFlight = new Map<string, Promise<unknown>>();

  async get<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    ttlMs:   number
  ): Promise<T> {
    // Check distributed cache first:
    const cached = await redis.get(key);
    if (cached) return JSON.parse(cached);

    // Check in-flight registry — is another request already computing this?
    const existing = this.inFlight.get(key) as Promise<T> | undefined;
    if (existing) {
      // Return the SAME promise — no new backend request!
      // When the first request finishes, all waiting requests get the result:
      return existing;
    }

    // Start a new computation and register it:
    const promise = fetchFn()
      .then(async value => {
        await redis.set(key, JSON.stringify(value), 'PX', ttlMs);
        return value;
      })
      .finally(() => {
        // Clean up registry when done (success or failure):
        this.inFlight.delete(key);
      });

    this.inFlight.set(key, promise as Promise<unknown>);
    return promise;
  }
}

// What happens with 1000 concurrent requests for 'leaderboard:global':
// Request 1:   Cache miss → starts fetchFn → Promise P1 → stored in inFlight
// Request 2:   Cache miss → sees P1 in inFlight → returns P1 (waits on existing)
// Request 3:   Cache miss → sees P1 in inFlight → returns P1 (waits on existing)
// ...
// Request 1000: Cache miss → sees P1 in inFlight → returns P1 (waits on existing)
// fetchFn() finishes → P1 resolves → All 1000 requests get the value simultaneously
// Database received: 1 query (not 1000)

// IMPORTANT LIMITATION: works only within a SINGLE PROCESS
// Request from Pod A and Request from Pod B both hit the database separately
// (they have separate inFlight maps — no shared memory)
// Combine with distributed lock for cross-process protection
```

**Q14. What is the DataLoader pattern and when does it apply to stampede prevention?**

A: DataLoader (originally from Facebook/GraphQL) batches and deduplicates data loading requests within a single event loop tick — turning N individual queries into one batch query:

```typescript
import DataLoader from 'dataloader';

// DataLoader creates a "batch function" that receives ALL keys requested
// within a single tick of the event loop:
const userLoader = new DataLoader<number, User>(async (userIds: readonly number[]) => {
  // Called once with ALL userIds requested this tick:
  const users = await db.query(
    `SELECT * FROM users WHERE id = ANY($1)`,
    [[...userIds]]
  );

  // DataLoader requires results in the SAME ORDER as the input keys:
  return userIds.map(id => users.find(u => u.id === id) ?? new Error(`User ${id} not found`));
});

// Usage — 100 concurrent GraphQL resolvers each request different users:
async function resolveUser(userId: number): Promise<User> {
  return userLoader.load(userId);   // Batched! Not individual queries
}

// What happens with 100 concurrent requests for users 1-100:
// Tick 1: resolveUser(1), resolveUser(2), ..., resolveUser(100) all called
// DataLoader waits for the tick to end, collects all keys: [1, 2, ..., 100]
// Fires ONE batch query: SELECT * FROM users WHERE id = ANY([1..100])
// All 100 promises resolve with their respective user

// DataLoader also caches within the request lifetime:
userLoader.load(1);   // Database hit
userLoader.load(1);   // Cache hit (same DataLoader instance, same request)

// Combining DataLoader with Redis for cross-request caching:
class CachedDataLoader<K, V> {
  private loader: DataLoader<K, V>;

  constructor(
    private redis:   Redis,
    private keyFn:   (key: K) => string,
    private batchFn: (keys: K[]) => Promise<(V | Error)[]>,
    private ttlMs:   number
  ) {
    this.loader = new DataLoader<K, V>(async (keys) => {
      const cacheKeys = keys.map(this.keyFn);
      const cached    = await redis.mget(...cacheKeys);

      const missing: { key: K; idx: number }[] = [];
      cached.forEach((val, i) => {
        if (!val) missing.push({ key: keys[i], idx: i });
      });

      if (missing.length > 0) {
        const fetched = await this.batchFn(missing.map(m => m.key));
        const pipeline = redis.pipeline();
        fetched.forEach((val, i) => {
          if (!(val instanceof Error)) {
            pipeline.set(cacheKeys[missing[i].idx], JSON.stringify(val), 'PX', this.ttlMs);
            cached[missing[i].idx] = JSON.stringify(val);
          }
        });
        await pipeline.exec();
      }

      return cached.map(v => v ? JSON.parse(v) : new Error('Not found'));
    }, { cache: false });   // Disable DataLoader's in-memory cache (Redis handles it)
  }
}
```

## Section 7: TTL Jitter

**Q15. How does TTL jitter prevent coordinated cache expiration stampedes?**

A: Jitter adds randomness to TTL values so that keys set at the same time don't all expire at the same time. Instead of a cliff-edge expiry event, expirations are spread across a window:

```typescript
// Without jitter — synchronized batch expiry:
async function cacheProduct(productId: string, data: Product): Promise<void> {
  await redis.setex(`product:${productId}`, 3600, JSON.stringify(data));
  // If 10,000 products are cached at midnight with TTL=3600s:
  // At 1:00 AM the NEXT DAY: all 10,000 expire simultaneously → stampede
}

// With jitter — desynchronized expiry:
function jitteredTtl(baseTtl: number, jitterFraction: number = 0.2): number {
  // Add ±jitterFraction of baseTtl as random jitter
  const jitter = baseTtl * jitterFraction;
  return Math.floor(baseTtl + (Math.random() * 2 - 1) * jitter);
  // baseTtl=3600, jitter=0.2: TTL is randomly between 2880s and 4320s
}

async function cacheWithJitter(key: string, data: unknown, baseTtl: number): Promise<void> {
  const ttl = jitteredTtl(baseTtl);
  await redis.setex(key, ttl, JSON.stringify(data));
}

// Effect of jitter on a batch of 10,000 products cached at midnight:
// Without jitter: all 10,000 expire at exactly 1:00 AM
// With 20% jitter (TTL: 2880-4320s): expirations spread from 12:48 AM to 2:12 AM
// → Instead of 10,000 misses in 1 second: ~111 misses per minute (86x reduction in burst)

// Larger jitter for higher protection:
const JITTER_PRESETS = {
  light:    0.1,   // ±10%: minimal spread, still coordinated
  moderate: 0.2,   // ±20%: good general purpose
  heavy:    0.5,   // ±50%: highly desynchronized, keys expire spread over TTL/2 window
};

// For cache-aside pattern with jitter:
async function getOrSet<T>(
  key:     string,
  fetchFn: () => Promise<T>,
  baseTtl: number,
  jitter:  number = 0.2
): Promise<T> {
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const value = await fetchFn();
  const ttl   = jitteredTtl(baseTtl, jitter);
  await redis.setex(key, ttl, JSON.stringify(value));
  return value;
}
```

**Q16. When is jitter insufficient and what specific problem does it not solve?**

A:

```
Jitter SOLVES: Coordinated batch expiration stampede
  - Scenario: batch job populates N keys with the same TTL → they expire together
  - Jitter spreads the expirations → no synchronized miss cliff
  - ✓ Effective

Jitter DOES NOT SOLVE: Hot single-key stampede
  - Scenario: ONE extremely popular key expires
  - Jitter doesn't help because there's only ONE key to jitter
  - If the single key 'leaderboard:global' expires at t=3600, jitter might shift it to
    t=3500 or t=3700 — but when it DOES expire, all 50K concurrent users still miss at once
  - ✗ Not effective — need XFetch or locking for this case

Summary of what each solution addresses:

Problem type                    | Jitter | Lock | XFetch | Soft-TTL | Coalescing
─────────────────────────────────────────────────────────────────────────────────
Single hot key expiry           | ✗      | ✓    | ✓      | ✓        | ✓ (in-process)
Many keys expiring together     | ✓      | ✗    | ✗      | ✓        | ✗
Cache flush / cold start        | ✗      | ✗    | ✗      | ✗        | ✓ (partial)
Redundant backend calls         | ✗      | ✓    | Partial | ✓       | ✓

Use jitter in combination with other strategies:
  - Jitter prevents batch coordination issues
  - XFetch or Lock prevents hot-key stampede
  - Together: comprehensive protection
```

## Section 8: Cache Warming

**Q17. How does cache warming prevent cold-start stampedes?**

A: Cache warming proactively populates the cache before it's needed — either before deployment or before a TTL expires — so the cache is never empty from the first user's perspective:

```typescript
class CacheWarmer {
  // Strategy 1: Proactive pre-expiry refresh (scheduled)
  async warmBeforeExpiry(
    key:          string,
    fetchFn:      () => Promise<unknown>,
    ttlSeconds:   number,
    refreshAtPct: number = 0.8   // Refresh when 80% of TTL has elapsed
  ): Promise<void> {
    // Check remaining TTL:
    const remainingTtl = await redis.ttl(key);

    if (remainingTtl < 0) {
      // Key doesn't exist (−2) or has no TTL (−1):
      await this.populate(key, fetchFn, ttlSeconds);
      return;
    }

    const elapsedPct = 1 - (remainingTtl / ttlSeconds);
    if (elapsedPct >= refreshAtPct) {
      // 80%+ of TTL elapsed → refresh proactively:
      await this.populate(key, fetchFn, ttlSeconds);
      logger.info(`Proactively refreshed ${key} (${Math.round(elapsedPct * 100)}% elapsed)`);
    }
  }

  // Strategy 2: On-startup warm-up (deployment pattern)
  async warmOnStartup(hotKeys: Array<{ key: string; fetch: () => Promise<unknown>; ttl: number }>): Promise<void> {
    const pipeline = redis.pipeline();

    // Check which keys are missing:
    hotKeys.forEach(({ key }) => pipeline.exists(key));
    const existence = await pipeline.exec();

    const missing = hotKeys.filter((_, i) => existence[i][1] === 0);
    logger.info(`Warming ${missing.length}/${hotKeys.length} cold keys on startup`);

    // Populate missing keys (with concurrency limit to avoid overwhelming the DB):
    const concurrency = 5;
    const chunks = chunk(missing, concurrency);

    for (const batch of chunks) {
      await Promise.all(
        batch.map(({ key, fetch, ttl }) => this.populate(key, fetch, ttl))
      );
    }

    logger.info('Cache warm-up complete');
  }

  // Strategy 3: "Copy-on-write" deployment warm-up
  async warmNewDeployment(
    oldRedisUrl: string,    // Old deployment's Redis
    newRedisUrl: string,    // New deployment's Redis (empty)
    keysToWarm:  string[]
  ): Promise<void> {
    const oldRedis = createRedisClient(oldRedisUrl);
    const newRedis = createRedisClient(newRedisUrl);

    // Copy warm data from old deployment's cache:
    for (const key of keysToWarm) {
      const [value, ttl] = await Promise.all([
        oldRedis.get(key),
        oldRedis.ttl(key),
      ]);
      if (value && ttl > 0) {
        await newRedis.setex(key, ttl, value);
      }
    }

    await oldRedis.quit();
    await newRedis.quit();
    logger.info(`Pre-warmed ${keysToWarm.length} keys for new deployment`);
  }

  private async populate(key: string, fetchFn: () => Promise<unknown>, ttl: number): Promise<void> {
    const lockKey = `warm-lock:${key}`;
    const acquired = await redis.set(lockKey, '1', 'NX', 'EX', 30);
    if (!acquired) return;  // Another process is already warming this key

    try {
      const value = await fetchFn();
      await redis.setex(key, jitteredTtl(ttl, 0.1), JSON.stringify(value));
    } finally {
      await redis.del(lockKey);
    }
  }
}
```

## Section 9: Choosing the Right Solution

**Q18. How do you choose between stampede prevention strategies and when do you combine them?**

A:

```
Decision framework:

Step 1: What kind of stampede?
  └─ Many keys expiring together (batch, deployment, flush)?
       └─ Add TTL jitter to all cache writes
  └─ Single hot key occasionally expires?
       └─ Continue to Step 2

Step 2: Can you serve slightly stale data?
  └─ YES (most cases):
       └─ Use Soft TTL + background refresh (best user experience — never waits)
       └─ Alternatively: XFetch (mathematically optimal, self-calibrating)
  └─ NO (real-time data, financial precision required):
       └─ Continue to Step 3

Step 3: Is consistency (exactly-one recompute) critical?
  └─ YES (side effects like email, payment, non-idempotent write):
       └─ Use distributed lock + blocking wait with stale fallback
  └─ NO (idempotent recompute):
       └─ Use XFetch (allows occasional parallel recomputes, fine for pure reads)

Step 4: What is the traffic pattern?
  └─ Mostly within single process (monolith, low traffic):
       └─ In-process coalescing (DataLoader / Promise registry) — simplest
  └─ Multi-instance / microservices:
       └─ Distributed lock or XFetch (need Redis coordination)
  └─ Very high concurrency (10K+ req/s per key):
       └─ XFetch (lock becomes a bottleneck) or Soft TTL

Combined strategy for production:

class ProductionCacheService {
  async get<T>(key: string, fetchFn: () => Promise<T>, options: CacheOptions): Promise<T> {
    // Layer 1: In-process coalescing (free — saves intra-process redundancy)
    const coalescingKey = key;
    const inFlight = this.inFlightMap.get(coalescingKey);
    if (inFlight) return inFlight as Promise<T>;

    const computation = this.getOrRefresh(key, fetchFn, options);
    this.inFlightMap.set(coalescingKey, computation as Promise<unknown>);
    computation.finally(() => this.inFlightMap.delete(coalescingKey));
    return computation;
  }

  private async getOrRefresh<T>(
    key:     string,
    fetchFn: () => Promise<T>,
    options: CacheOptions
  ): Promise<T> {
    // Layer 2: Distributed cache read with soft TTL
    const raw = await redis.get(key);
    if (raw) {
      const entry = JSON.parse(raw) as SoftExpiryEntry<T>;

      // Layer 3: XFetch probabilistic early recompute
      const shouldRecompute = this.xfetchShouldRecompute(entry);
      if (shouldRecompute) {
        // Background refresh — serve current value immediately:
        this.backgroundRefresh(key, fetchFn, options).catch(logger.error);
      }
      return entry.value;
    }

    // True miss — synchronous compute (rare if warming is in place):
    return this.compute(key, fetchFn, options);
  }
}
```

**Q20. "Implement a complete stampede-resistant cache for a high-traffic leaderboard endpoint."**

A:

```typescript
// The leaderboard scenario:
// - 50,000 req/s hitting /api/leaderboard/global
// - Leaderboard computed from DB: takes 2000ms (complex aggregation)
// - Can serve up to 10s stale (scoreboard updates every 10s anyway)
// - 10 application pods

class LeaderboardCache {
  private readonly KEY     = 'leaderboard:global';
  private readonly TTL_MS  = 30_000;   // 30s fresh TTL
  private readonly STALE_MS = 60_000;  // 60s additional stale window = 90s hard TTL
  private readonly BETA    = 1.5;      // Aggressive XFetch for high traffic
  private inFlight: Promise<Leaderboard> | null = null;  // In-process coalescing

  async get(): Promise<{ data: Leaderboard; stale: boolean }> {
    // Layer 1: In-process coalescing — all reqs in this pod share one Promise
    if (this.inFlight) {
      const data = await this.inFlight;
      return { data, stale: false };
    }

    const promise = this.fetchFromCacheOrCompute();
    this.inFlight = promise.then(r => r.data);
    setTimeout(() => { this.inFlight = null; }, 100);  // Clear after 100ms tick
    return promise;
  }

  private async fetchFromCacheOrCompute(): Promise<{ data: Leaderboard; stale: boolean }> {
    const raw = await redis.get(this.KEY);

    if (raw) {
      const entry: SoftExpiryEntry<Leaderboard> = JSON.parse(raw);
      const now           = Date.now();
      const remainingMs   = entry.softExpiry - now;

      // XFetch: should we probabilistically recompute early?
      const xfetchDecision =
        remainingMs <= 0 ||
        (-this.BETA * entry.delta * Math.log(Math.random())) > remainingMs;

      if (xfetchDecision && remainingMs > 0) {
        // Still has data — trigger background refresh:
        this.backgroundRefresh(entry.delta).catch(err =>
          logger.error('Leaderboard background refresh failed', { err })
        );
        return { data: entry.value, stale: remainingMs <= 0 };
      }

      if (remainingMs > 0) {
        return { data: entry.value, stale: false };   // Truly fresh
      }

      // Soft expiry passed — serve stale + refresh:
      this.backgroundRefresh(entry.delta).catch(logger.error);
      return { data: entry.value, stale: true };      // Serve stale immediately
    }

    // True cache miss (cold start) — compute synchronously:
    const start = Date.now();
    const data  = await this.computeLeaderboard();
    const delta = Date.now() - start;

    await this.store(data, delta);
    return { data, stale: false };
  }

  private async backgroundRefresh(prevDelta: number): Promise<void> {
    // Prevent multiple pods from simultaneously refreshing:
    const lockKey   = `lock:refresh:${this.KEY}`;
    const lockToken = crypto.randomUUID();
    const acquired  = await redis.set(lockKey, lockToken, 'NX', 'PX', this.TTL_MS);

    if (!acquired) return;   // Another pod is refreshing

    try {
      const start = Date.now();
      const data  = await this.computeLeaderboard();
      const delta = Date.now() - start;

      await this.store(data, delta);
      logger.info('Leaderboard refreshed', { delta, prevDelta });
    } finally {
      await releaseLock(lockKey, lockToken);
    }
  }

  private async store(data: Leaderboard, delta: number): Promise<void> {
    const entry: SoftExpiryEntry<Leaderboard> = {
      value:      data,
      softExpiry: Date.now() + this.TTL_MS,
      delta,                   // Measured compute time for XFetch calibration
    };
    const hardTtlMs = this.TTL_MS + this.STALE_MS;   // 90s total
    // Jitter: ±10% to prevent coordinated expiry
    const jitteredMs = hardTtlMs * (0.9 + Math.random() * 0.2);

    await redis.set(this.KEY, JSON.stringify(entry), 'PX', Math.floor(jitteredMs));
  }

  private async computeLeaderboard(): Promise<Leaderboard> {
    return db.query(`
      SELECT user_id, username, SUM(points) AS score,
             RANK() OVER (ORDER BY SUM(points) DESC) AS rank
      FROM scores
      WHERE created_at > NOW() - INTERVAL '30 days'
      GROUP BY user_id, username
      ORDER BY score DESC
      LIMIT 100
    `);
  }
}

// Result: 50,000 req/s hit the leaderboard endpoint
// - Layer 1 (in-process coalescing): 10 pods × 1 compute = max 10 concurrent DB queries
//   instead of 50,000
// - Layer 2 (XFetch): recomputes spread over time before expiry — no cliff-edge
// - Layer 3 (soft TTL): stale data always available — no blocking waits
// - Layer 4 (jitter): prevents pods from all refreshing at the exact same second
// - Layer 5 (background lock): prevents simultaneous cross-pod redundant refreshes
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **Cache stampede** | Many concurrent requests miss the cache simultaneously → backend overwhelmed |
| **Thundering herd** | Broader pattern: many processes compete for a single resource simultaneously |
| **Root triggers** | TTL expiry of hot key; cache flush; cold start; deployment; LRU eviction under load |
| **Cascade risk** | Miss storm → DB overload → slow responses → client retries → amplification → outage |
| **Locking** | One process recomputes; others wait or get stale — prevents redundant backend calls |
| **Lock failure mode** | Lock holder crash → all waiters blocked until lock TTL; lock TTL < compute time → two recomputes |
| **Stale-while-recomputing** | Serve previous (stale) value to waiters while winner recomputes — zero blocking |
| **XFetch (probabilistic)** | Each reader independently decides to early-recompute with P = e^(−t/(β×δ)); no locks |
| **XFetch formula** | `earlyRecompute = −β × δ × log(random()) > remaining_ttl` |
| **delta (δ)** | Measured recompute time — self-calibrates from previous computation; stored in cache entry |
| **beta (β)** | Tuning: 1.0=default, >1=aggressive early recompute, <1=conservative |
| **Soft TTL (logical TTL)** | Store soft expiry inside value; hard Redis TTL = soft + stale window; serve stale + background refresh |
| **Stale-while-revalidate** | HTTP Cache-Control equivalent of soft TTL; serve stale, async revalidate |
| **In-process coalescing** | Single process: share one Promise per key — N concurrent requests → 1 backend call |
| **DataLoader** | Batch + deduplicate requests within one event loop tick — N queries → 1 batch query |
| **TTL jitter** | `ttl = baseTtl * (1 + random() * ±jitterFraction)` — prevents coordinated batch expiry |
| **Jitter limitation** | Fixes multi-key coordinated expiry; does NOT fix single-hot-key stampede |
| **Cache warming** | Proactively populate cache before deployment or before TTL expires |
| **Init container warming** | K8s: run warmer before traffic is routed to new pods (readinessProbe gate) |
| **Double-check locking** | After acquiring lock, re-check cache before computing (another process may have just finished) |
| **Background refresh lock** | Only one pod/process performs background refresh — Redis SET NX prevents duplicates |
| **When to use XFetch** | High concurrency, idempotent recompute, can tolerate rare parallel recomputes |
| **When to use lock** | Side effects (exactly-one required); moderate concurrency; simple implementation preferred |
| **When to use soft TTL** | Always — combines with any strategy; zero latency for users (always serves immediately) |
| **Combined strategy** | Jitter + Soft TTL + XFetch + In-process coalescing = comprehensive protection |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) drawing the **failure cascade precisely** — cache miss → backend overwhelm → slow responses → client retries → amplification → connection pool exhaustion → OOM → pod restarts → colder cache → worse stampede; naming this cascade shows production experience rather than textbook knowledge; (2) the **XFetch formula** `−β × δ × log(random()) > remaining_ttl` and being able to explain what each term does — delta is the measured recompute time (stored in the cached value and self-calibrating), beta controls aggressiveness, and the negative log of a uniform random variable generates an exponential distribution that produces the right probability curve (near-zero early, ~37% at one delta before expiry, 100% at expiry); (3) the **critical difference between TTL jitter and XFetch** — jitter prevents multiple different keys from expiring at the same time (coordinated batch expiry), but does nothing for a single hot key expiring with thousands of concurrent readers; XFetch solves the single-hot-key case while jitter solves the coordinated batch case; production systems need both; (4) the **soft TTL pattern** as a baseline — storing the soft expiry timestamp inside the cached value alongside the data, setting the Redis TTL longer than the soft expiry, and serving stale data during background refresh means users never wait at all; this combines with any other strategy and should arguably be used everywhere; and (5) **in-process coalescing as the first layer** — a single Node.js pod handling 5,000 req/s for the same leaderboard key should share one in-flight Promise across all concurrent requests in that process, turning 5,000 simultaneous DB calls into 1 before even involving Redis locks or XFetch.
