# Redis Eviction Policies — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is memory eviction in Redis and why does it exist — what happens when Redis runs out of memory?**

A: Redis stores all data in RAM. When the amount of data written to Redis exceeds the configured `maxmemory` limit, Redis must decide what to do: refuse new writes, or make room by deleting existing keys. The eviction policy (`maxmemory-policy`) determines which strategy Redis uses when it hits that ceiling:

```
Without eviction (noeviction — the default):
  Client writes data...
  Redis heap: [───────────────────────── 99% full ─────────────────────────]
  Next write arrives...
  Redis returns: OOM command not allowed when used memory > 'maxmemory'.

With eviction (e.g., allkeys-lru):
  Client writes data...
  Redis heap: [───────────────────────── 99% full ─────────────────────────]
  Next write arrives...
  Redis: selects and deletes a key using the LRU policy
  Redis heap: [──────────────────────── 95% full ─────────────────────────]
  Write succeeds.
```

The memory ceiling and what triggers eviction:

```bash
# Set the maximum memory Redis can use:
redis-cli CONFIG SET maxmemory 2gb

# Or in redis.conf:
# maxmemory 2gb

# Redis checks memory usage on every write command.
# When used_memory >= maxmemory AND a write command arrives:
# → Redis runs the eviction cycle
# → Attempts to free enough memory to complete the write
# → If it can't free enough (e.g., noeviction policy): OOM error

# Check current memory state:
redis-cli INFO memory
# used_memory: 2147483648       ← bytes currently used
# used_memory_human: 2.00G
# maxmemory: 2147483648
# maxmemory_human: 2.00G
# maxmemory_policy: allkeys-lru
# mem_fragmentation_ratio: 1.23  ← < 1.0 means Redis is using swap (bad)
#
# Check eviction stats:
redis-cli INFO stats | grep evicted_keys
# evicted_keys: 14892            ← total keys evicted since server start
```

What happens internally when eviction runs:

```
Redis eviction cycle (simplified):
  1. A SET/LPUSH/ZADD/etc. command arrives
  2. Redis checks: used_memory >= maxmemory?
     → No: execute the command normally
     → Yes: enter eviction loop
  3. Eviction loop:
     a. Select an eviction candidate based on maxmemory-policy
     b. Delete the candidate
     c. Check: used_memory < maxmemory?
        → Yes: execute the pending command
        → No:  repeat from (a)
     d. If can't free enough memory (noeviction or no volatile keys):
        → Return OOM error to the client
  4. Execute the pending write command
```

**Q2. What are all the eviction policies Redis supports — what is the complete taxonomy?**

A: Redis 7.x supports eight eviction policies, organised along two dimensions: which keys are eligible for eviction, and how the eviction candidate is selected:

```
Dimension 1 — Key eligibility:
  allkeys-*   → Any key in the database can be evicted
  volatile-*  → Only keys with a TTL (EXPIRE set) can be evicted
  noeviction  → No keys are evicted; OOM error is returned instead

Dimension 2 — Selection algorithm:
  -lru        → Least Recently Used (last access time)
  -lfu        → Least Frequently Used (access frequency counter)
  -random     → Random selection (no ordering)
  -ttl        → Smallest TTL (soonest to expire anyway)
```

The complete list:

```bash
# The 8 policies:
noeviction         # Default. Refuse writes when full. No keys removed.
allkeys-lru        # Remove any key, least recently used first.
volatile-lru       # Remove TTL-bearing keys, least recently used first.
allkeys-lfu        # Remove any key, least frequently used first.
volatile-lfu       # Remove TTL-bearing keys, least frequently used first.
allkeys-random     # Remove any key, chosen at random.
volatile-random    # Remove TTL-bearing keys, chosen at random.
volatile-ttl       # Remove TTL-bearing key with the smallest remaining TTL first.

# Set the policy:
redis-cli CONFIG SET maxmemory-policy allkeys-lru

# Or in redis.conf:
# maxmemory-policy allkeys-lru

# Verify:
redis-cli CONFIG GET maxmemory-policy
# 1) "maxmemory-policy"
# 2) "allkeys-lru"
```

A mental model for choosing between them:

```
Are ALL your keys cache-able (none is authoritative source of truth)?
  → allkeys-lru or allkeys-lfu

Do only SOME keys have TTL, and others are permanent?
  → volatile-lru or volatile-lfu (protects permanent keys from eviction)

Is cache hit rate more important than eviction precision?
  → allkeys-lru (widely tested, good general performance)

Do you have hot keys that are accessed frequently but not recently?
  → allkeys-lfu (better for skewed/Zipfian access patterns)

Do you need precise control via explicit TTLs?
  → volatile-ttl

Is Redis used as a primary datastore (not just cache)?
  → noeviction (never silently delete data)
```

## Section 2: LRU Policies

**Q3. How does Redis implement LRU — why is it approximate rather than exact?**

A: A true LRU cache requires a doubly-linked list ordered by last-access time and a hash map for O(1) lookup. Every access moves the accessed node to the head of the list. This is O(1) per operation but requires storing a pointer to the list node with every key — adding 16 bytes of overhead per key and requiring pointer updates on every read, which adds write pressure to the memory allocator.

Redis implements a **sampled approximation of LRU** to avoid this overhead:

```
True LRU:
  Access order maintained in a linked list: [newest] → [old] → [oldest]
  Evict: always removes from the tail (O(1))
  Cost: 16 bytes per key for list pointers + pointer update on every read

Redis approximate LRU:
  Each key stores: lru_clock (24-bit timestamp, seconds resolution)
  Updated on every access: SET, GET, INCR, etc.
  On eviction: sample N random keys, evict the one with the oldest lru_clock
  Cost: 4 bytes per key for the clock field (already part of the redisObject)
```

```bash
# The sample size is configurable:
redis-cli CONFIG SET maxmemory-samples 5   # Default: sample 5 random keys
redis-cli CONFIG SET maxmemory-samples 10  # Better approximation, more CPU
redis-cli CONFIG SET maxmemory-samples 50  # Near-perfect LRU, much more CPU

# Trade-off:
# samples=5:  Fast eviction, some inaccuracy (occasionally evicts a recently used key)
# samples=10: Good approximation (Redis docs say comparable to true LRU)
# samples=50: Near-perfect, but eviction cycle scans 50 keys each time

# Visualising the approximation:
# True LRU guarantees: evicts the single globally-oldest key
# Redis LRU guarantees: evicts the oldest among a random sample
# In practice with samples=10: the selected key is rarely more than 10th-oldest overall
# For cache use cases: this approximation is effectively indistinguishable from true LRU
```

The `lru_clock` field and its wraparound:

```c
// Inside every Redis key object (redisObject):
// lru_clock: 24 bits, counting seconds, updates every LRU_CLOCK_RESOLUTION (1000ms)
// Max value: 2^24 = 16,777,216 seconds ≈ 194 days
// After 194 days: wraps around to 0

// Redis accounts for wraparound when comparing timestamps:
// if (lruClock(key) > server.lruclock):
//     age = server.lruclock + (MAX_LRU - lruClock(key))
// else:
//     age = server.lruclock - lruClock(key)

// Check a key's idle time:
redis-cli OBJECT IDLETIME mykey
# Returns seconds since the key was last accessed
# Useful for debugging which keys are cold
```

**Q4. What is `allkeys-lru` vs `volatile-lru` — when does the distinction matter?**

A: The `allkeys-` prefix means Redis can evict ANY key in the database. The `volatile-` prefix means Redis can only evict keys that have an expiration time set. This distinction is critical when you mix two classes of data in Redis:

```bash
# Scenario: Redis used as both a session store AND a rate-limit counter
# Sessions: ALWAYS have a TTL (they should expire)
# Rate limit counters: NO TTL (they're permanent reference data)

# Set up mixed data:
SET session:user:123 "userData" EX 3600     # Has TTL → volatile-* eligible
SET session:user:456 "userData" EX 7200     # Has TTL → volatile-* eligible
SET ratelimit:counter:1 100                  # NO TTL  → only allkeys-* eligible
SET ratelimit:counter:2 50                   # NO TTL  → only allkeys-* eligible

# With volatile-lru:
# When Redis runs out of memory, it only considers session:* keys for eviction
# (because they have TTLs)
# ratelimit:counter:* keys are NEVER evicted regardless of memory pressure
# → Your rate limit counters are protected

# With allkeys-lru:
# When Redis runs out of memory, it considers ALL keys
# A ratelimit:counter key might be evicted if it was accessed less recently
# → Rate limit counters could be silently deleted → broken rate limiting

# When volatile-lru fails:
# If ALL keys without TTLs are needed AND volatile keys are exhausted:
# Redis falls back to noeviction behaviour for volatile-lru/volatile-lfu/volatile-random/volatile-ttl
# i.e., if there are no volatile keys to evict, Redis returns OOM error

# Demonstration:
redis-cli CONFIG SET maxmemory 1mb
redis-cli CONFIG SET maxmemory-policy volatile-lru

# Fill Redis with only non-expiring keys:
for i in $(seq 1 10000); do
    redis-cli SET "permanent:$i" "value_that_fills_memory_$i"
done
# Eventually: (error) OOM command not allowed when used memory > 'maxmemory'.
# volatile-lru had nothing to evict (no volatile keys exist)

# Fix: either use allkeys-lru, or ensure all cache keys have TTLs
```

Using `volatile-lru` correctly — the two-tier pattern:

```bash
# Tier 1: Permanent data (no TTL) — NEVER evicted with volatile-lru
SET config:featureFlags '{"darkMode": true}' # No EXPIRE
SET reference:countryCodes '{"IN": "India", "US": "United States"}' # No EXPIRE

# Tier 2: Cache data (with TTL) — eligible for eviction with volatile-lru
SET cache:user:profile:123 '{"name": "Alice"}' EX 3600   # Can be evicted
SET cache:product:details:456 '{"price": 99.99}' EX 1800  # Can be evicted

# With volatile-lru: permanent keys are safe, cache keys are evicted by LRU order
# This is the intended use case for volatile-lru
```

## Section 3: LFU Policies

**Q5. What is LFU and how does Redis implement it — how is it different from LRU?**

A: LRU evicts keys that haven't been accessed *recently*. LFU evicts keys that haven't been accessed *frequently*. The distinction matters when access patterns are skewed: a key accessed 10,000 times over the past month but not in the last hour looks "old" to LRU and might be evicted — but LFU recognises it as hot and protects it.

Redis implements LFU using a logarithmic counter (the Morris counter), stored in the same 24-bit field used by LRU:

```
LRU field (24 bits): seconds-resolution timestamp of last access
  → Reused for LFU as:
LFU field (24 bits):
  - High 16 bits: last decrement time (minutes resolution)
  - Low  8 bits:  frequency counter (0-255, logarithmic)

The 8-bit logarithmic counter:
  Value 0:   accessed 0-1 times
  Value 1:   accessed ~2 times
  Value 5:   accessed ~14 times
  Value 10:  accessed ~57 times
  Value 100: accessed ~3 million times
  Value 255: accessed ~billions of times
  → Logarithmic growth: each increment requires more accesses than the last
  → Counter saturation at 255 is by design (very hot keys stay at 255)
```

```bash
# LFU configuration parameters:
redis-cli CONFIG SET lfu-log-factor 10
# Default: 10. Controls how quickly the counter saturates.
# Lower value  = counter reaches 255 with fewer accesses (faster saturation)
# Higher value = more accesses needed to reach high counts (slower saturation)
# At lfu-log-factor=10: counter reaches 255 after ~1 million accesses
# At lfu-log-factor=1:  counter reaches 255 after ~100 accesses

redis-cli CONFIG SET lfu-decay-time 1
# Default: 1. Minutes before the counter is halved (decay).
# 0 = no decay (counter only grows, never decays — dangerous)
# 1 = counter halves every 1 minute of non-access
# This prevents old-but-once-popular keys from blocking eviction forever

# How the frequency counter decays:
# A key accessed 1000 times per second for one hour:
# → Counter reaches 255 (saturated)
# After 1 minute without access:
# → Counter = 255 / 2 = 127  (halved by decay)
# After another minute:
# → Counter = 127 / 2 = 63
# → Eventually becomes evictable

# Check a key's frequency counter:
redis-cli OBJECT FREQ mykey
# Returns: 42   ← the current LFU counter value
# (Only works when maxmemory-policy is allkeys-lfu or volatile-lfu)
```

LRU vs LFU — when each outperforms:

```
Scenario: Product catalogue cache
  Hot products (top 100): accessed 10,000 times/hour
  Long-tail products (99,900 others): accessed 1 time/day

  With allkeys-lru:
    A hot product accessed 5 minutes ago may be "less recent" than
    a long-tail product accessed 4 minutes ago → hot product evicted
    → Causes cache churn: hot product re-fetched from DB frequently

  With allkeys-lfu:
    Hot products have high frequency counters → protected from eviction
    Long-tail products have low counters → evicted first
    → Cache stays efficient even with bursty access to long-tail items

Scenario: Time-series sensor data
  Each data point accessed exactly once when received
  Older data never re-accessed

  With allkeys-lfu:
    All keys have frequency counter = 1 → random eviction among them
    → No benefit over allkeys-random

  With allkeys-lru:
    Oldest data has largest idle time → evicted first
    → Natural FIFO ordering aligns with time-series access patterns

Decision guide:
  Zipfian access distribution (few hot, many cold keys) → allkeys-lfu
  Time-series / sequential access                       → allkeys-lru
  Uniform random access                                 → allkeys-random (lowest overhead)
  Unknown / mixed                                       → allkeys-lru (safe default)
```

## Section 4: Other Policies

**Q6. When would you use `allkeys-random` or `volatile-random` — and is `volatile-ttl` ever the right choice?**

A: Random eviction seems naïve, but it has legitimate uses. `volatile-ttl` is a specific tool for a specific pattern:

```bash
# ── allkeys-random / volatile-random ─────────────────────────────────────────
# When to use:
# 1. You know your cache has uniform access distribution
#    (all keys accessed equally often → LRU/LFU give no advantage over random)
# 2. You want minimal eviction overhead
#    (random selection requires no sorting, tracking, or counter updates)
# 3. Memory-constrained environments where you can't afford LRU/LFU metadata

# The real cost of random vs LRU:
# allkeys-random: O(1) eviction selection (just call rand())
# allkeys-lru:    O(N_samples) comparison of lru_clock fields
# For maxmemory-samples=5: LRU scans 5 keys → still very cheap
# Practical difference: negligible for most workloads

# When NOT to use random:
# Any workload with hot/cold key distribution → random evicts hot keys
# (bad cache hit rate compared to LRU/LFU)

# ── volatile-ttl ─────────────────────────────────────────────────────────────
# volatile-ttl selects volatile keys and evicts the one with the SMALLEST remaining TTL
# (the one that would expire soonest anyway)
#
# Use case: You want eviction to mimic natural expiration
# Example: user sessions with varying TTLs

SET session:user:A "data" EX 60    # Expires in 60s  ← evicted first with volatile-ttl
SET session:user:B "data" EX 3600  # Expires in 1h
SET session:user:C "data" EX 86400 # Expires in 24h  ← protected from eviction longest

# With volatile-ttl: when memory is full, session:user:A is evicted first
# (it would expire soon anyway → least loss of utility)

# This is different from volatile-lru:
# volatile-lru evicts whichever volatile key was accessed least recently
# volatile-ttl evicts whichever volatile key expires soonest

# When volatile-ttl shines:
# You set TTLs to reflect business priority:
# Critical session: EX 86400 (long TTL = high priority = protected longer)
# Temporary token:  EX 300   (short TTL = low priority = evicted first)
# The TTL acts as an implicit priority queue for eviction

# Sampled approximation: volatile-ttl also uses sampling
# Like LRU: samples N volatile keys, evicts the one with smallest TTL
# maxmemory-samples applies here too
```

**Q7. What is `noeviction` and when is it the correct choice — despite seeming like a failure mode?**

A: `noeviction` is the default and is often the right choice when Redis is used as a primary datastore rather than a cache. The OOM error on writes is a deliberate signal that your memory capacity needs to increase, not that data should be silently deleted:

```bash
# noeviction behaviour:
redis-cli CONFIG SET maxmemory-policy noeviction

# When maxmemory is reached, write commands return an error:
# SET → (error) OOM command not allowed when used memory > 'maxmemory'
# LPUSH → (error) OOM command not allowed when used memory > 'maxmemory'
# INCR  → (error) OOM command not allowed when used memory > 'maxmemory'

# Read commands still work:
# GET → returns the value (or nil)
# HGET → returns the field value
# LRANGE → returns the list elements

# When noeviction is the right choice:

# 1. Redis as a primary datastore (not a cache)
# Queues, pub/sub, session store for authoritative sessions
# Losing data is NOT acceptable → refuse writes rather than silently delete

# 2. Redis used for rate limiting
SET ratelimit:user:123 0            # Counter for API rate limiting
# If rate limit key is evicted → user gets unlimited API access → security issue
# noeviction → OOM error → you know you need more memory → fix the root cause

# 3. Redis as a job queue (RPUSH/LPOP patterns)
# If a job entry is evicted → task is silently lost → production bug
# noeviction → error → job isn't accepted → client retries → no data loss

# 4. Financial or audit data
# Any data where silent deletion is worse than write failure

# The correct response to OOM with noeviction:
# a. Alert: your Redis memory is full
# b. Investigate: which keys are largest? (use redis-cli --bigkeys or SCAN + DEBUG OBJECT)
# c. Fix: increase maxmemory, add a replica + cluster, prune old data, or compress values

# Monitoring for OOM errors with noeviction:
redis-cli INFO stats | grep rejected_connections
# rejected_connections: 0
# (noeviction doesn't reject connections, but your client will see OOM errors on writes)

# Better: monitor in your application:
# try {
//   await redis.set(key, value);
// } catch (err) {
//   if (err.message.includes('OOM')) {
//     metrics.increment('redis.oom_errors');
//     // Alert ops team, fail gracefully
//   }
// }
```

## Section 5: Interaction with TTL and Key Design

**Q8. How does setting TTLs interact with eviction policies — and what is the "expiration before eviction" ordering?**

A: Redis has two independent mechanisms for removing keys: TTL expiration and eviction. They operate at different times and for different reasons. Understanding their interaction prevents common bugs:

```bash
# Mechanism 1: TTL expiration (lazy + active)
# LAZY: when a key is accessed and found to be expired → deleted then
# ACTIVE: Redis periodically scans 20 random volatile keys → deletes expired ones
#         (runs 10 times per second: CONFIG GET hz → "hz" "10")
# Purpose: recover memory from naturally expired keys
# Independent of maxmemory

# Mechanism 2: Eviction (triggered by memory pressure)
# Runs only when: used_memory >= maxmemory AND a write command arrives
# Selects victim based on maxmemory-policy
# Purpose: make room for new writes
# Only runs when maxmemory is set

# The ordering when memory is full AND keys have TTLs:
# 1. A write command arrives
# 2. Redis checks used_memory >= maxmemory
# 3. If yes: runs eviction cycle (maxmemory-policy determines victim)
# 4. Victim is deleted (eviction)
# 5. Separately: the TTL expiration cycle also runs (async)
# → Expired keys are removed by expiration, not eviction
# → evicted_keys counter counts only policy-based evictions, not expirations

# Common confusion: EXPIRE doesn't "protect" a key from eviction
# With volatile-lru: EXPIRE makes a key ELIGIBLE for eviction (not protected)
# With allkeys-lru: EXPIRE has no effect on eviction eligibility

# Check expiration stats:
redis-cli INFO stats | grep expired_keys
# expired_keys: 45823   ← keys removed because their TTL elapsed
redis-cli INFO stats | grep evicted_keys
# evicted_keys: 891     ← keys removed due to memory pressure

# The TTL expiration cycle:
# Redis runs a background job every 1/hz seconds (default: every 100ms)
# Each cycle: picks 20 random volatile keys, deletes expired ones
# If > 25% of the 20 sampled keys were expired: repeat immediately
# This keeps expired key count low without full table scans
```

Best practices for TTL + eviction policy combinations:

```bash
# Pattern 1: Pure cache (all keys are cache entries)
# Use allkeys-lru or allkeys-lfu
# Set TTLs on all keys as a safety net for stale data
# TTLs ensure eventual cleanup; eviction handles memory pressure
redis-cli CONFIG SET maxmemory-policy allkeys-lru
SET cache:product:123 '{"name":"Keyboard"}' EX 3600  # 1h TTL

# Pattern 2: Mixed store (some permanent, some cache)
# Use volatile-lru or volatile-lfu
# Only cache keys get TTLs (they're eviction eligible)
# Permanent keys get no TTL (they're eviction immune)
redis-cli CONFIG SET maxmemory-policy volatile-lru
SET config:appSettings '{"theme":"dark"}'              # No TTL → never evicted
SET cache:user:profile:42 '{"name":"Alice"}' EX 1800   # TTL → can be evicted

# Pattern 3: Priority-based eviction
# Use volatile-ttl
# Set TTLs proportional to value (longer TTL = higher priority)
redis-cli CONFIG SET maxmemory-policy volatile-ttl
SET session:premium_user:1 "data" EX 86400   # High priority (24h TTL)
SET session:free_user:2    "data" EX 1800    # Lower priority (30min TTL)
# When memory is full: free_user sessions are evicted before premium_user sessions

# Anti-pattern: volatile-* with no keys having TTLs
# If NO keys have TTLs and you use volatile-lru:
# → Redis cannot evict anything (no volatile keys)
# → Falls back to noeviction behaviour
# → OOM errors even though you think you have an eviction policy
redis-cli CONFIG SET maxmemory-policy volatile-lru
SET key1 "value1"  # No TTL
SET key2 "value2"  # No TTL
# (fill memory...)
SET key3 "value3"  # → OOM error (nothing to evict!)
```

## Section 6: Monitoring and Tuning

**Q9. How do you monitor eviction behaviour in production and tune the policy?**

A: Eviction activity is visible through Redis's INFO output and keyspace statistics. The goal is understanding whether eviction is hurting your cache hit rate and whether the chosen policy is selecting victims appropriately:

```bash
# ── Key metrics to monitor ────────────────────────────────────────────────────

redis-cli INFO stats | grep -E 'evicted_keys|expired_keys|keyspace_hits|keyspace_misses'
# evicted_keys:1892      ← total evictions since start (counter never resets)
# expired_keys:45823     ← total TTL expirations since start
# keyspace_hits:892341   ← total successful key lookups
# keyspace_misses:12453  ← total failed key lookups (key missing or expired)

# Cache hit rate:
# hit_rate = keyspace_hits / (keyspace_hits + keyspace_misses)
# hit_rate = 892341 / (892341 + 12453) = 98.6%
# Good hit rate: > 95% for a cache
# Poor hit rate: < 90% (too much eviction, wrong policy, or insufficient memory)

# Is eviction happening too fast?
# High evicted_keys growing quickly = memory too small OR TTLs too long

redis-cli INFO memory | grep -E 'used_memory|maxmemory|mem_fragmentation'
# used_memory: 1073741824    (1GB used)
# maxmemory:   1073741824    (1GB limit → at capacity!)
# mem_fragmentation_ratio: 1.08   (1.0 = no fragmentation, < 1.0 = using swap → bad)

# Fragmentation: Redis allocates memory in chunks (jemalloc).
# Ratio > 1.5: significant fragmentation → memory is being wasted
# Ratio < 1.0: RSS < used_memory → Redis is using swap → serious performance issue
# Fix high fragmentation:
redis-cli CONFIG SET activedefrag yes          # Active defragmentation (Redis 4.0+)
redis-cli CONFIG SET active-defrag-enabled yes  # Alternative name depending on version

# ── Finding what's consuming memory ───────────────────────────────────────────

# Big key scanner (scans all keys, reports largest by type):
redis-cli --bigkeys
# Scanning the entire keyspace to find biggest keys as well as
# average sizes per key type.  You can use -i 0.1 to sleep 0.1 sec per 100 SCAN commands.
# -------- summary -------
# Biggest string found 'cache:product:bigProduct' has 1048576 bytes  ← 1MB string
# Biggest list   found 'queue:jobs'               has 50342 elements
# Biggest zset   found 'leaderboard:global'        has 1000000 members

# Sample random keys for analysis:
redis-cli OBJECT ENCODING mykey     # ziplist, listpack, hashtable, skiplist, etc.
redis-cli OBJECT IDLETIME mykey     # seconds since last access (LRU mode)
redis-cli OBJECT FREQ mykey         # access frequency counter (LFU mode)
redis-cli OBJECT REFCOUNT mykey     # reference count (usually 1)
redis-cli DEBUG OBJECT mykey        # serializedlength: estimated serialized size

# Memory usage per key:
redis-cli MEMORY USAGE mykey
# (integer) 8432  ← 8.4KB for this key including metadata and value

# ── Tuning the policy ─────────────────────────────────────────────────────────

# Test different policies without downtime (takes effect immediately):
redis-cli CONFIG SET maxmemory-policy allkeys-lfu

# Monitor hit rate before and after change:
# Collect baseline for 10 minutes with allkeys-lru
# Switch to allkeys-lfu
# Collect hit rate for 10 minutes
# Compare: which gives better hit rate for your workload?

# Tune sample size for better LRU/LFU accuracy:
redis-cli CONFIG SET maxmemory-samples 10  # Default 5, max ~20 is practical

# Tune LFU parameters:
redis-cli CONFIG SET lfu-log-factor 10    # Default: 10
redis-cli CONFIG SET lfu-decay-time 1     # Default: 1 minute

# Save tuning changes permanently:
redis-cli CONFIG REWRITE   # Writes current CONFIG to redis.conf file
```

## Section 7: Advanced Patterns

**Q10. How do eviction policies interact with Redis Cluster — does each node evict independently?**

A: In Redis Cluster, each node manages its own subset of keyspace (hash slots 0-16383 distributed across nodes). Eviction is entirely local — each node applies `maxmemory-policy` independently for its own memory:

```bash
# Redis Cluster and eviction:
# Node 1 (slots 0-5460):   maxmemory=2gb, used=1.9gb → may be evicting
# Node 2 (slots 5461-10921): maxmemory=2gb, used=0.5gb → no eviction needed
# Node 3 (slots 10922-16383): maxmemory=2gb, used=2.0gb → definitely evicting

# Each node's eviction is independent — there is no cross-node eviction coordination
# A key hashed to Node 3 may be evicted while an equivalent slot on Node 1 has free space

# Cluster-aware monitoring:
for node in node1:6379 node2:6379 node3:6379; do
    echo "=== $node ==="
    redis-cli -h ${node%:*} -p ${node#*:} INFO memory | grep -E 'used_memory|maxmemory'
    redis-cli -h ${node%:*} -p ${node#*:} INFO stats | grep evicted_keys
done

# Setting maxmemory for all nodes consistently:
# Cluster config: each redis.conf should have the same maxmemory value
# If nodes have different maxmemory: some nodes fill up faster → uneven eviction

# Cluster-specific eviction gotcha:
# With allkeys-lru: a hot key on a loaded node (Node 3) may be evicted
# while the same "equivalent" key on Node 1 would not be
# (because Node 1 has free memory and doesn't need to evict)
# This can cause cache stampedes on Node 3 specifically

# Mitigation: even distribution of hot keys across nodes
# Ensure hash tags don't overly concentrate hot keys on one node:
# Bad:  {user}:profile:1, {user}:profile:2, {user}:profile:3 → all on same node (same hash tag)
# Good: user:profile:1, user:profile:2, user:profile:3 → distributed by hash of full key
```

**Q11. How do you implement key protection against eviction for specific critical keys?**

A: There is no built-in "never evict this key" flag in Redis (unlike Memcached). You implement protection through policy selection and TTL absence:

```bash
# Method 1: Use volatile-* policies — critical keys get no TTL
redis-cli CONFIG SET maxmemory-policy volatile-lru

# Critical keys: no EXPIRE
SET system:config '{"maintenanceMode": false}'   # No TTL → never evicted
SET auth:publicKey 'rsa-public-key-data'          # No TTL → never evicted

# Cache keys: with EXPIRE
SET cache:product:123 '{"name":"Keyboard"}' EX 3600  # Has TTL → evictable

# Method 2: Separate Redis instances for different key classes
# Instance 1: noeviction, small maxmemory
#   → Only stores critical config, session data, rate limits
#   → OOM error signals "add more memory" rather than silent data loss

# Instance 2: allkeys-lru, large maxmemory
#   → Stores cache data
#   → Eviction is acceptable

# This is the cleanest separation: two Redis instances, each with different roles

# Method 3: Application-level refresh before eviction
# Keep critical keys alive by refreshing them periodically:
async function keepAlive(redis, key, intervalMs = 60000) {
    setInterval(async () => {
        const value = await redis.get(key);
        if (value === null) {
            // Key was evicted — restore it
            await restoreFromPrimaryDatastore(key);
        }
    }, intervalMs);
}

# Method 4: Monitor for eviction of specific key patterns
redis-cli CONFIG SET notify-keyspace-events 'Eg'  # Enable eviction events
# 'E' = Keyevent events, published on key operations
# 'g' = Generic commands (DEL, EXPIRE, RENAME, ...)
# 'e' = Eviction events specifically

# In Node.js, subscribe to eviction events:
const sub = redis.duplicate();
await sub.subscribe('__keyevent@0__:evicted', (message) => {
    console.warn(`Key evicted: ${message}`);
    if (message.startsWith('critical:')) {
        alertOpsTeam(`CRITICAL: Redis evicted ${message}`);
        restoreKey(message);
    }
});

redis-cli CONFIG SET notify-keyspace-events 'Kg'  # 'K' = Keyspace events (alternative)
```

**Q13. "You're building a rate limiter with Redis. Which eviction policy do you use and why — and what happens if Redis evicts a rate limit counter?"**

A:

```bash
# ── The problem with eviction for rate limiters ───────────────────────────────
# Rate limiter stores: INCR ratelimit:user:123 EX 60
# If this key is evicted: the counter resets to 0
# → The user gets a fresh 60-second window immediately
# → They can make unlimited requests by triggering eviction

# ── Option 1: noeviction (most conservative) ─────────────────────────────────
redis-cli CONFIG SET maxmemory-policy noeviction

# Rate limit keys:
SET  ratelimit:user:123 0 EX 60   # Sliding window counter
INCR ratelimit:user:123            # Increment on each request

# With noeviction: if memory fills up, new INCR/SET commands fail
# → New requests can't be rate-limited → but they also can't start new sessions
# → System fails closed (safe for security purposes)
# → OOM alert fires → ops team adds memory

# ── Option 2: volatile-lru with rate limit keys having NO TTL ─────────────────
# But wait: rate limit keys SHOULD have TTLs (they should reset after the window)
# So volatile-lru doesn't protect them

# ── Option 3: Separate Redis instance for rate limiting ───────────────────────
# Best practice for production:
# Redis instance 1: noeviction, small maxmemory (e.g., 512MB)
#   → Only rate limit counters and critical state
#   → OOM error = alert + fail open or closed based on business decision

# Redis instance 2: allkeys-lru, large maxmemory (e.g., 8GB)
#   → Cache data (product details, user profiles, etc.)
#   → Eviction is acceptable → data reloaded from DB on miss

# Application code:
const rateLimitRedis = createClient({ url: process.env.RATE_LIMIT_REDIS_URL });
const cacheRedis     = createClient({ url: process.env.CACHE_REDIS_URL });

// Rate limit check (uses dedicated Redis with noeviction):
async function checkRateLimit(userId: string): Promise<boolean> {
    const key     = `ratelimit:user:${userId}`;
    const current = await rateLimitRedis.incr(key);

    if (current === 1) {
        await rateLimitRedis.expire(key, 60); // Set window on first increment
    }

    return current <= 100; // Allow 100 requests per 60 seconds
}

// Cache lookup (uses cache Redis with allkeys-lru):
async function getProduct(productId: string): Promise<Product | null> {
    const cached = await cacheRedis.get(`product:${productId}`);
    if (cached) return JSON.parse(cached);

    const product = await db.findProduct(productId);
    if (product) {
        await cacheRedis.set(`product:${productId}`, JSON.stringify(product), { EX: 3600 });
    }
    return product;
}

# ── Defensive rate limiting: fail open vs fail closed on eviction ─────────────
async function checkRateLimitWithFallback(userId: string): Promise<boolean> {
    try {
        return await checkRateLimit(userId);
    } catch (err) {
        if (err.message.includes('OOM')) {
            // Redis is full — decision: allow or deny?
            // Fail OPEN:  return true  (allow request — user experience priority)
            // Fail CLOSED: return false (deny request — security priority)
            metrics.increment('ratelimit.redis_oom_fallback');
            return true; // Fail open: don't block users due to infrastructure issues
        }
        throw err; // Other errors: propagate
    }
}
```

## Quick Reference Table

| Policy | Eligible keys | Selection method | Use when |
|---|---|---|---|
| `noeviction` | None (no eviction) | N/A — returns OOM error | Redis is a primary datastore; data loss is unacceptable |
| `allkeys-lru` | All keys | Least recently used (approximate) | Pure cache; all keys are replaceable; most common choice |
| `volatile-lru` | Keys with TTL only | Least recently used | Mixed store: some permanent keys + cache keys with TTLs |
| `allkeys-lfu` | All keys | Least frequently used | Skewed/Zipfian access; hot keys must be protected |
| `volatile-lfu` | Keys with TTL only | Least frequently used | Mixed store + Zipfian access pattern |
| `allkeys-random` | All keys | Random | Uniform access distribution; minimal overhead needed |
| `volatile-random` | Keys with TTL only | Random | Mixed store + uniform cache access |
| `volatile-ttl` | Keys with TTL only | Smallest remaining TTL | TTL encodes business priority; soonest-to-expire evicted first |

| Metric | Command | What it tells you |
|---|---|---|
| Cache hit rate | `INFO stats` → `keyspace_hits / (hits + misses)` | < 90% → eviction too aggressive or wrong policy |
| Eviction count | `INFO stats` → `evicted_keys` | Growing fast → memory too small |
| Memory usage | `INFO memory` → `used_memory / maxmemory` | > 95% → near-eviction threshold |
| Fragmentation | `INFO memory` → `mem_fragmentation_ratio` | > 1.5 → enable `activedefrag`; < 1.0 → using swap |
| Key idle time | `OBJECT IDLETIME key` | Seconds since last access (LRU mode) |
| Key frequency | `OBJECT FREQ key` | LFU counter value (LFU mode) |
| Memory per key | `MEMORY USAGE key` | Bytes used by one key |

| Anti-pattern | Problem | Fix |
|---|---|---|
| `volatile-*` with no keys having TTLs | Falls back to noeviction → OOM errors | Ensure cache keys have TTLs, or switch to `allkeys-*` |
| `allkeys-lru` for rate limit counters | Rate limit counter can be silently evicted | Use separate Redis instance with `noeviction` for rate limiting |
| Very large keys in cache (MB+) | One large key causes many small hot keys to be evicted | Enforce size limit on cached values; store large objects in object storage |
| Same maxmemory-policy for cache + primary data | Primary data (no TTL) is vulnerable to eviction | Use `volatile-*` or separate Redis instances by data class |
| `maxmemory-samples` = 1 | LRU/LFU selection is nearly random | Keep default (5) or increase to 10 for better approximation |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **Redis LRU is approximate, not exact** — Redis samples `maxmemory-samples` (default 5) random keys and evicts the least recently used among that sample, rather than maintaining a true global LRU order; this avoids the O(N) overhead of maintaining a sorted linked list but occasionally evicts keys that aren't the globally oldest; (2) explaining the **`volatile-*` fallback behaviour** — when `volatile-lru` or any `volatile-*` policy is active but NO keys have TTLs, Redis cannot evict anything and falls back to `noeviction` behaviour, returning OOM errors; this is a common production bug where developers set `volatile-lru` but forget to set TTLs on their cache keys; (3) articulating **when LFU beats LRU** — for Zipfian access distributions (few hot keys, many cold keys), LRU may evict a popular key that wasn't accessed in the last hour while LFU keeps it (high frequency counter); LRU is better for time-series or sequential access where recency correctly predicts future access; (4) knowing that **eviction and TTL expiration are independent mechanisms** — `evicted_keys` counts policy-based evictions while `expired_keys` counts natural TTL expirations; they serve different purposes and run on different triggers (eviction: write commands when `used_memory >= maxmemory`; expiration: lazy on access + periodic active scanning); (5) the **architectural answer to protecting critical data** — there is no per-key "never evict" flag; the correct solution is either using `volatile-*` policies (critical keys have no TTL, cache keys do) or separate Redis instances with different `maxmemory-policy` settings; and (6) understanding **`noeviction` is often the correct choice** for non-cache Redis deployments — rate limiters, job queues, session stores, and primary datastores should use `noeviction` so that an OOM error surfaces as a visible signal requiring infrastructure action rather than silent data loss.
