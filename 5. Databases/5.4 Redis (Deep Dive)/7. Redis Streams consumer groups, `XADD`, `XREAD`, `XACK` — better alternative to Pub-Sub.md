### Section 1: Stream Fundamentals

**Q1. What is a Redis Stream and what problem does it solve that Lists and Pub/Sub cannot?**
A: A Redis Stream is an **append-only log data structure** — every entry is written to the end and stays there until explicitly trimmed or deleted. It gives Redis the semantics of a distributed log (like Apache Kafka), but inside a single Redis instance.

```
The gap between List and Kafka that Streams fill:

  List (before Streams):
    ✓ Simple queue: RPUSH + BLPOP
    ✗ Message is GONE after being popped — no replay
    ✗ Only one consumer can pop a message (single-consumer)
    ✗ No acknowledgment: crash mid-processing → message lost
    ✗ No visibility into what's pending/being processed

  Pub/Sub (before Streams):
    ✓ Fan-out: one message → many subscribers simultaneously
    ✗ Fire-and-forget: subscriber offline → message lost, permanently
    ✗ No persistence: Redis restart → all buffered messages gone
    ✗ No consumer groups: ALL subscribers receive ALL messages (broadcast)
    ✗ No acknowledgment, no delivery tracking

  Stream (solution):
    ✓ Messages persist until explicitly trimmed (replay possible)
    ✓ Consumer groups: message delivered to ONE consumer per group
    ✓ Acknowledgment: XACK marks a message as fully processed
    ✓ Pending Entries List (PEL): tracks in-flight messages; crash-safe
    ✓ Multiple independent groups: each sees every message independently
    ✓ Non-destructive reads: consumers read without removing messages
    ✓ Back-pressure: MAXLEN caps stream size

  Stream vs Kafka:
    Redis Stream: simpler ops, all in RAM, single-node, low latency (<1ms)
    Kafka:        disk-based, partitioned, multi-broker, very high throughput
    Use Stream when: latency critical, existing Redis infra, <100K msg/s
    Use Kafka when: millions of msg/s, long retention (days/weeks), compliance logging
```

**Q2. What is the internal structure of a Redis Stream and how are entry IDs formatted?**
A: Internally a Stream is a **radix tree** of **listpack** nodes. Each listpack (a compact sequential encoding) holds a batch of entries. This structure gives O(1) append and O(log N) lookup by ID.

```bash
# Stream entry ID format: <millisecondsTime>-<sequenceNumber>
# e.g.: 1704067200000-0
#        ↑                ↑
#        Unix ms timestamp  sequence (for multiple entries same ms)

# XADD with auto-generated ID (* = let Redis generate):
XADD mystream * event "user_signup" user_id "42" email "alice@example.com"
# → "1704067200123-0"  (Redis sets timestamp + sequence)

# XADD with partial ID (provide ms, Redis fills sequence):
XADD mystream 1704067200000-* event "click"
# → "1704067200000-0" first call
# → "1704067200000-1" second call same millisecond

# XADD with fully explicit ID (must be > all existing IDs):
XADD mystream 1704067200000-5 event "manual"
# → "1704067200000-5"

# Special IDs:
# 0 or 0-0:  beginning of stream (XRANGE, XREAD)
# $:         "current last ID" at the time of the command (XREAD for new messages only)
# >:         "next undelivered" within consumer group context (XREADGROUP)
# -:         smallest possible ID (XRANGE start)
# +:         largest possible ID (XRANGE end)

# XLEN: O(1) count of entries
XLEN mystream
# → 1

# ID ordering guarantees:
# 1. Auto-generated IDs are always monotonically increasing
# 2. Redis rejects XADD if explicit ID ≤ last entry's ID
# 3. IDs survive Redis restarts (millisecond precision preserved)
# 4. Cross-second ordering: 1704067200999-0 < 1704067201000-0
```

### Section 2: `XADD` — Writing to a Stream

**Q3. What are all of `XADD`'s options and when do you use each?**
A:

```bash
XADD key
  [NOMKSTREAM]           # don't create stream if it doesn't exist
  [MAXLEN|MINID [=|~] threshold [LIMIT count]]  # trim while adding
  *|id                   # auto-generate ID (*) or specify explicit ID
  field value [field value ...]  # one or more field-value pairs

# ── NOMKSTREAM ────────────────────────────────────────────────────────
# Useful when producers should only write to pre-existing streams:
XADD orders NOMKSTREAM * event "placed" order_id "ORD-001"
# → returns nil if 'orders' stream doesn't exist (no implicit creation)
# → prevents typo-caused phantom streams (e.g., "ordrrs" silently created)

# ── MAXLEN trimming ──────────────────────────────────────────────────
# Keep at most N entries; trim oldest entries during XADD (no separate cron needed):

# Exact trim (= or no modifier): trim precisely to N entries; expensive
XADD mystream MAXLEN = 1000 * event "click"
# Stream will have EXACTLY 1000 entries after this XADD

# Approximate trim (~): trim when "significantly over" threshold; much faster
XADD mystream MAXLEN ~ 1000 * event "click"
# Stream may have slightly MORE than 1000 entries (up to ~1000 + listpack overhead)
# Efficient: only trims full listpack nodes (no need to split nodes)
# Use ~ in production — exact trim is O(n) per trimmed entry, ~ is amortized O(1)

# ── MINID trimming ───────────────────────────────────────────────────
# Trim entries OLDER than a specific ID (time-based retention):
XADD mystream MINID ~ 1704067200000-0 * event "click"
# Removes all entries with ID < 1704067200000-0 (entries older than that timestamp)
# Useful for sliding time-window retention (e.g., keep only last 24h of events)

# Time-based retention example:
import time, redis
r = redis.Redis(decode_responses=True)

def add_event(stream: str, event: dict, keep_hours: int = 24) -> str:
    cutoff_ms = int((time.time() - keep_hours * 3600) * 1000)
    return r.xadd(
        stream,
        event,
        minid=f"{cutoff_ms}-0",  # trim entries older than keep_hours
        approximate=True         # ~ flag: efficient approximate trim
    )
```

```python
# Pipeline multiple XADD for batch publish (one round trip):
pipe = r.pipeline()
events = [
    {"user_id": "1", "action": "click", "page": "/home"},
    {"user_id": "2", "action": "view",  "page": "/product"},
    {"user_id": "3", "action": "buy",   "page": "/checkout"},
]
for event in events:
    pipe.xadd("stream:pageviews", event, maxlen=100_000, approximate=True)

ids = pipe.execute()  # list of generated IDs
```

### Section 3: `XREAD` — Reading Without Consumer Groups

**Q4. What is `XREAD` and when do you use it instead of `XREADGROUP`?**
A: `XREAD` is for **consumers that don't use consumer groups** — they read the stream independently, tracking their own position. There is no shared state, no acknowledgment, and no delivery tracking. Every `XREAD` caller receives the same messages. This mirrors a "broadcast log" pattern: every reader is an independent observer.

```bash
XREAD
  [COUNT count]              # max entries per stream to return
  [BLOCK milliseconds]       # 0 = block indefinitely; omit for non-blocking
  STREAMS key [key ...]      # one or more streams
         id  [id  ...]       # last-seen ID per stream ($ = only new)

# ── Non-blocking: read from beginning ────────────────────────────────
XREAD COUNT 10 STREAMS mystream 0
# Returns up to 10 entries starting from ID 0 (the very beginning)
# Response: [[b'mystream', [(b'id1', {...}), (b'id2', {...}), ...]]]

# ── Non-blocking: read new entries (from current position) ────────────
# App tracks last_id in memory or persistent storage:
last_id = "0"
while True:
    results = r.xread({"mystream": last_id}, count=100)
    if results:
        for stream_name, messages in results:
            for msg_id, fields in messages:
                process(fields)
                last_id = msg_id   # advance position
    else:
        time.sleep(0.1)           # no new messages; poll

# ── Blocking: efficient alternative to polling ────────────────────────
last_id = "0"
while True:
    results = r.xread({"mystream": last_id}, count=100, block=5000)
    # block=5000: wait up to 5 seconds for new messages
    # block=0:    wait indefinitely (never times out)
    if results:
        for stream_name, messages in results:
            for msg_id, fields in messages:
                process(fields)
                last_id = msg_id

# ── The $ special ID: only messages published AFTER the XREAD call ───
results = r.xread({"mystream": "$"}, block=0)
# "$" = "the ID of the last entry at the time this XREAD was called"
# Useful for: live tail of a stream (like `tail -f` for logs)
# WARNING: if multiple messages arrive between two XREAD calls, you miss those
#          between your last processed ID and $
# CORRECT: use 0 initially, then track last_id explicitly (never use $ after the first call)

# ── Reading from multiple streams simultaneously ─────────────────────
results = r.xread({"stream:orders": last_order_id, "stream:events": last_event_id},
                  count=50, block=1000)
# Blocks until EITHER stream has new data
# Returns messages from ALL streams that had data
```

**When `XREAD` (no groups) vs `XREADGROUP`:**
```
XREAD (no consumer group):
  → Each caller independently tracks its own position
  → All callers see ALL messages (broadcast to independent observers)
  → No delivery tracking, no acknowledgment, no crash recovery
  → Use for: monitoring/logging service that tails the stream;
             materialized views that replay the log from position;
             any "read all messages" independent observer

XREADGROUP (consumer group):
  → Shared state: group tracks last-delivered-id
  → Each message delivered to EXACTLY ONE consumer in the group
  → PEL tracks in-flight messages; XACK removes from PEL
  → Crash recovery: pending messages can be reclaimed by other consumers
  → Use for: reliable task queues, microservice event consumers,
             any "process each message exactly once" pattern
```

### Section 4: Consumer Groups

**Q5. What is a consumer group and how does it partition stream delivery?**
A: A consumer group is a named **shared cursor** into a stream. All consumers that join the same group cooperate: the group tracks which messages have been delivered, and ensures each new message goes to exactly **one** consumer within the group. Multiple groups on the same stream are fully independent — each group sees all messages, but within each group, messages are partitioned across consumers.

```bash
# Create a consumer group:
XGROUP CREATE stream_key group_name start_id [MKSTREAM] [ENTRIESREAD count]

XGROUP CREATE stream:orders email-service $ MKSTREAM
#                           ↑             ↑  ↑
#                           group name    |  create stream if missing
#                                         $ = only process NEW messages (ignore history)

XGROUP CREATE stream:orders inventory-service 0
#                                              0 = process ALL messages from beginning

# start_id options:
# 0 or 0-0: start from very beginning of stream
# $:        start from messages added AFTER this XGROUP CREATE call
# specific_id: start from entries after that specific ID

# Consumer group internal state (per group):
# last_delivered_id: the ID of the most recently delivered message
# pending_entries_list (PEL): messages delivered but not yet ACKed
# consumers: named consumers within the group and their PEL subsets
```

```python
# Setting up multiple independent consumer groups on one stream:
def setup_stream_groups(stream: str) -> None:
    groups = [
        ("email-service",     "$"),  # only new orders
        ("inventory-service", "$"),  # only new orders
        ("analytics-service", "0"),  # replay from beginning (catch up)
        ("fraud-detector",    "$"),  # only new orders
    ]
    for group_name, start_id in groups:
        try:
            r.xgroup_create(stream, group_name, id=start_id, mkstream=True)
            print(f"Created group: {group_name}")
        except redis.exceptions.ResponseError as e:
            if "BUSYGROUP" in str(e):
                print(f"Group already exists: {group_name}")
            else:
                raise

# Multiple groups receiving the same message:
#
# Stream: stream:orders
#   Entry 1704067200000-0: {order_id: "ORD-001", amount: 99.99}
#
# email-service group:     delivers ORD-001 to email-worker-1 → sent, XACK
# inventory-service group: delivers ORD-001 to inv-worker-1  → decremented, XACK
# analytics-service group: delivers ORD-001 to analytics-1  → recorded, XACK
# fraud-detector group:    delivers ORD-001 to fraud-1       → scored, XACK
#
# Each group independently ACKs its own delivery
# The stream entry itself is not deleted — all groups must process it
# (Entry only deleted by XDEL or XTRIM)
```

**Q6. What is `XREADGROUP` and how does it differ from `XREAD`?**
A: `XREADGROUP` reads on behalf of a named consumer within a named group. The `>` special ID delivers **new, undelivered** messages and adds them to the group's Pending Entries List (PEL). Specifying a numeric ID instead re-delivers **already-pending** messages for that consumer (retry pattern after restart).

```bash
XREADGROUP GROUP group consumer
  [COUNT count]
  [BLOCK milliseconds]
  [NOACK]
  STREAMS key [key ...]
          id  [id  ...]     # ">" for new; specific ID for re-read pending

# ── Normal operation: get new messages ───────────────────────────────
XREADGROUP GROUP email-service email-worker-1 COUNT 10 BLOCK 5000 STREAMS stream:orders >
# ">" = give me messages not yet delivered to ANY consumer in email-service group
# Side effect: message added to PEL for email-worker-1
# Response same structure as XREAD

# ── After worker restart: re-read own pending messages ────────────────
XREADGROUP GROUP email-service email-worker-1 COUNT 100 STREAMS stream:orders 0
# "0" = give me MY pending messages (from my PEL) that I haven't ACKed yet
# Used on startup: re-process anything that was in-flight when I crashed
# These messages are NOT re-added to PEL (already there)

# ── NOACK flag: skip the PEL (fire-and-forget with groups) ────────────
XREADGROUP GROUP analytics-service analytics-1 COUNT 100 NOACK STREAMS stream:orders >
# NOACK: messages are NOT added to PEL
# Useful when: losing a message is acceptable (analytics can re-process later);
#              want consumer group routing without delivery guarantees
# Tradeoff: NOACK is faster (no PEL write) but not crash-safe
```

### Section 5: `XACK` and the Pending Entries List

**Q7. What is the Pending Entries List (PEL) and what exactly does `XACK` do?**
A: The Pending Entries List (PEL) is per-group, per-consumer metadata tracking every message that has been **delivered but not yet acknowledged**. It represents "messages currently in flight" — delivered to a consumer but not yet confirmed as processed. `XACK` removes an entry from the PEL, signaling that processing is complete.

```
PEL structure (per consumer group):

  Group "email-service" PEL:
  ┌─────────────────────────────────────────────────────────────────┐
  │  Message ID          │ Consumer       │ Delivery Time │ Count  │
  │──────────────────────│────────────────│───────────────│────────│
  │  1704067200000-0     │ email-worker-1 │ 1704067200100 │   1    │
  │  1704067200001-0     │ email-worker-1 │ 1704067200105 │   1    │
  │  1704067200002-0     │ email-worker-2 │ 1704067200110 │   1    │
  │  1704067200003-0     │ email-worker-1 │ 1704067199000 │   3    │  ← 3 delivery attempts!
  └─────────────────────────────────────────────────────────────────┘
  Count = 3 means this message was delivered 3 times (crash/retry scenario)
  It's been with email-worker-1 for 200+ seconds without ACK (stalled!)

  After XACK stream:orders email-service 1704067200000-0:
  → Entry removed from PEL
  → Message is "done" for the email-service group
  → Memory for this PEL entry freed
  → Stream entry itself STILL EXISTS (other groups haven't processed it yet)
```

```bash
# XACK syntax:
XACK key group id [id ...]
# Returns: integer count of successfully ACKed messages

# Single ACK:
XACK stream:orders email-service "1704067200000-0"

# Batch ACK (much more efficient than one XACK per message):
XACK stream:orders email-service "1704067200000-0" "1704067200001-0" "1704067200002-0"
# Returns: 3 (number of entries removed from PEL)

# XPENDING: inspect what's in the PEL
XPENDING stream:orders email-service - + 10
# Returns: list of pending entries with delivery count and idle time (ms since delivery)
# Response:
# [
#   ['1704067200003-0', 'email-worker-1', 200500, 3],
#   #  ↑ message ID      ↑ consumer       ↑ idle ms  ↑ delivery count
# ]

XPENDING stream:orders email-service IDLE 60000 - + 10
# Only return entries idle > 60 seconds (stalled messages)
```

```python
# Complete reliable consumer loop with proper XACK:
def reliable_consumer(stream: str, group: str, consumer: str,
                       handler: callable, batch_size: int = 10) -> None:
    # Step 1: On startup, process any messages this consumer had in-flight
    process_pending_messages(stream, group, consumer, handler)

    # Step 2: Main loop — get new messages
    while True:
        results = r.xreadgroup(
            group, consumer,
            {stream: ">"},
            count=batch_size,
            block=5000
        )

        if not results:
            # No new messages — check for stalled messages from other consumers
            reclaim_stalled_messages(stream, group, consumer, handler)
            continue

        for _, message_list in results:
            process_messages(stream, group, message_list, handler)

def process_messages(stream, group, message_list, handler) -> None:
    ack_ids = []
    for msg_id, fields in message_list:
        try:
            handler(fields)
            ack_ids.append(msg_id)
        except Exception as e:
            log.error(f"Processing failed for {msg_id}: {e}")
            # Don't add to ack_ids → stays in PEL → will be reclaimed

    # Batch ACK all successful messages in one command:
    if ack_ids:
        r.xack(stream, group, *ack_ids)

def process_pending_messages(stream, group, consumer, handler) -> None:
    # Re-read my own pending messages after restart:
    while True:
        results = r.xreadgroup(group, consumer, {stream: "0"}, count=100)
        if not results or not results[0][1]:
            break  # no more pending messages for this consumer
        _, message_list = results[0]
        process_messages(stream, group, message_list, handler)
```

### Section 6: Crash Recovery with `XCLAIM` and `XAUTOCLAIM`

**Q8. How do you handle messages from consumers that have crashed and what is `XCLAIM`?**
A: When a consumer crashes mid-processing, its pending messages remain in the PEL indefinitely. `XCLAIM` transfers ownership of pending messages to a different (healthy) consumer, enabling crash recovery without losing messages. `XAUTOCLAIM` (Redis 6.2+) automates the scan-and-transfer in one command.

```bash
# XCLAIM: manually transfer specific pending messages to a new consumer
XCLAIM key group new_consumer min-idle-time id [id ...]
  [TIME ms-unix-time]   # override last-delivery time (for testing)
  [RETRYCOUNT count]    # override delivery count
  [FORCE]               # claim even if not in PEL (creates PEL entry)
  [JUSTID]              # return only IDs, not full messages

# Example: claim messages idle > 30 seconds from any consumer:
XCLAIM stream:orders email-service email-worker-2 30000 "1704067200003-0"
# → Transfers 1704067200003-0 from email-worker-1 to email-worker-2
# → Increments delivery count (was 3, now 4)
# → Resets idle time (last delivery = now)
# → email-worker-2 receives the full message to retry

# XAUTOCLAIM (Redis 6.2+): scan PEL for stalled messages + claim in one command
XAUTOCLAIM stream:orders email-service email-worker-2 30000 0-0 COUNT 10
#                                                     ↑        ↑     ↑
#                                              min-idle(ms)  start  max entries
# Returns: [next_start_id, [[id, fields], ...], [deleted_ids]]
# next_start_id: use as start in next XAUTOCLAIM call to paginate through PEL
# deleted_ids: entries that were in PEL but no longer in stream (already deleted)
```

```python
def reclaim_stalled_messages(
    stream: str, group: str, consumer: str, handler: callable,
    idle_ms: int = 30_000,     # claim messages idle > 30 seconds
    max_retries: int = 5
) -> None:
    start = "0-0"

    while True:
        # XAUTOCLAIM: find and claim stalled messages in one command
        next_id, messages, deleted = r.xautoclaim(
            stream, group, consumer,
            min_idle_time=idle_ms,
            start_id=start,
            count=10
        )

        for msg_id, fields in messages:
            # Check delivery count — send to dead letter if too many retries:
            pending_info = r.xpending_range(stream, group, min=msg_id, max=msg_id, count=1)
            if pending_info and pending_info[0]["times_delivered"] >= max_retries:
                send_to_dead_letter(stream, group, msg_id, fields)
                r.xack(stream, group, msg_id)
                continue

            try:
                handler(fields)
                r.xack(stream, group, msg_id)
            except Exception as e:
                log.error(f"Retry failed for {msg_id}: {e}")
                # Stays in PEL; delivery count incremented; will be reclaimed again

        if next_id == "0-0":
            break   # scanned through entire PEL; no more stalled messages
        start = next_id  # continue from where we left off

def send_to_dead_letter(stream: str, group: str, msg_id: str, fields: dict) -> None:
    # Write to a dead letter stream for manual investigation:
    r.xadd(
        f"{stream}:dead-letter",
        {
            "original_stream":   stream,
            "original_group":    group,
            "original_msg_id":   msg_id,
            "original_fields":   json.dumps(fields),
            "failed_at":         str(time.time()),
        },
        maxlen=10_000,
        approximate=True
    )
    log.warning(f"Message {msg_id} sent to dead letter after max retries")
```

### Section 7: Stream Inspection and Maintenance

**Q9. What commands help you monitor and maintain a stream in production?**
A:

```bash
# ── XLEN: total entries in stream ────────────────────────────────────
XLEN stream:orders
# → 845231

# ── XRANGE: read entries by ID range ─────────────────────────────────
XRANGE stream:orders - +                    # all entries (AVOID on large streams!)
XRANGE stream:orders - + COUNT 10           # first 10 entries
XRANGE stream:orders 1704067200000-0 + COUNT 100  # from specific ID onward
XRANGE stream:orders (1704067200000-0 +     # exclusive start (Redis 6.2+)

# ── XREVRANGE: newest entries first ──────────────────────────────────
XREVRANGE stream:orders + - COUNT 10        # last 10 entries (most recent first)

# ── XINFO STREAM: overall stream metadata ────────────────────────────
XINFO STREAM stream:orders
# Returns: length, radix-tree-keys, radix-tree-nodes, last-generated-id,
#          max-deleted-entry-id, entries-added, recorded-first-entry-id,
#          first-entry (oldest entry), last-entry (newest entry)

XINFO STREAM stream:orders FULL COUNT 2
# FULL: includes all consumer group details + first N PEL entries per consumer

# ── XINFO GROUPS: consumer group status ──────────────────────────────
XINFO GROUPS stream:orders
# Returns per group:
#   name:              "email-service"
#   consumers:         3               (active consumers)
#   pending:           12              (messages in PEL not yet ACKed)
#   last-delivered-id: "1704067200100-0"
#   entries-read:      845219
#   lag:               12              (entries-added - entries-read = unprocessed)

# ── XINFO CONSUMERS: per-consumer detail ─────────────────────────────
XINFO CONSUMERS stream:orders email-service
# Returns per consumer:
#   name:              "email-worker-1"
#   pending:           5
#   idle:              234             (ms since last interaction)
#   inactive:          234             (same, Redis 7.2+)

# ── XTRIM: explicit trimming (separate from XADD) ─────────────────────
XTRIM stream:orders MAXLEN ~ 100000     # trim to ~100K entries
XTRIM stream:orders MINID ~ 1704067200000-0  # trim entries older than ID

# ── XDEL: remove specific entries ────────────────────────────────────
XDEL stream:orders "1704067200000-0"
# Marks entry as deleted (tombstone); memory freed when listpack node emptied
# XLEN decrements; PEL entries for this ID become "orphaned"
# Use for: removing sensitive data (GDPR right-to-erasure); NOT for normal queue management

# ── XGROUP SETID: rewind a consumer group ────────────────────────────
XGROUP SETID stream:orders email-service 0   # rewind to beginning (replay all)
XGROUP SETID stream:orders email-service $   # skip to current (drop backlog)
XGROUP SETID stream:orders email-service "1704067200000-0"  # specific position

# ── XGROUP DELCONSUMER: remove a consumer and its PEL ────────────────
XGROUP DELCONSUMER stream:orders email-service email-worker-3
# Returns: number of pending messages that consumer had (now orphaned in group PEL)
# Orphaned messages reassignable via XCLAIM/XAUTOCLAIM

# ── XGROUP DESTROY: delete entire consumer group ─────────────────────
XGROUP DESTROY stream:orders old-service
# Removes group + all its PEL entries; does NOT affect stream entries
```

### Section 8: Streams vs Pub/Sub — The Complete Comparison

**Q10. When should you definitively choose Streams over Pub/Sub and vice versa?**
A:

```
┌────────────────────────────┬──────────────────────────┬──────────────────────────┐
│ Concern                    │ Pub/Sub                  │ Stream                   │
├────────────────────────────┼──────────────────────────┼──────────────────────────┤
│ Message persistence        │ None (fire-and-forget)   │ Persists until trimmed   │
│ Subscriber offline?        │ Messages lost forever    │ Messages wait in stream  │
│ Redis restart?             │ All buffered msgs lost   │ Stream survives (RDB/AOF)│
│ Message delivery           │ Best-effort broadcast    │ At-least-once (with ACK) │
│ Multiple consumers         │ All get every message    │ Group: one gets each msg │
│ Independent consumers      │ All subscribe separately │ Separate consumer groups │
│ Acknowledgment             │ None                     │ XACK removes from PEL   │
│ Crash recovery             │ None                     │ XCLAIM stalled messages  │
│ Replay / rewind            │ Impossible               │ XGROUP SETID 0 + replay  │
│ Back-pressure              │ None                     │ MAXLEN caps stream size  │
│ Pending message visibility │ None                     │ XPENDING shows in-flight │
│ Consumer lag monitoring    │ None                     │ XINFO GROUPS shows lag   │
│ Throughput                 │ Very high (no metadata)  │ High (metadata overhead) │
│ Complexity                 │ Simple                   │ More complex             │
├────────────────────────────┼──────────────────────────┼──────────────────────────┤
│ Use when                   │ Live chat notifications  │ Order processing pipeline│
│                            │ Real-time dashboard push │ Email/SMS delivery queue │
│                            │ "Live or nothing" signals│ Event-driven microservices│
│                            │ Game state broadcasting  │ Audit logs               │
│                            │ Short-lived pub/sub      │ IoT sensor ingestion     │
└────────────────────────────┴──────────────────────────┴──────────────────────────┘

Key insight: Pub/Sub is a BROADCAST mechanism; Stream is a LOG + QUEUE mechanism.
  Pub/Sub asks: "who is listening RIGHT NOW?"
  Stream asks:  "what needs to be processed, and has it been processed yet?"
```

**Q11. "What happens if no consumer calls XACK — does the stream grow forever?"**
A:

```
Scenario: stream receives 1M messages but consumers never XACK

The stream itself:
  Messages stored in the stream data structure
  Stream grows until trimmed by MAXLEN or MINID
  XTRIM or XDEL can remove entries regardless of PEL status
  → Stream memory controlled independently of ACK status

The PEL (Pending Entries List):
  Every XREADGROUP with ">" adds entry to PEL
  Without XACK: PEL grows unboundedly (one entry per unacknowledged message)
  PEL contains: msg_id + consumer name + delivery timestamp + delivery count
  Each PEL entry: ~70-80 bytes
  1 million unACKed messages × 70 bytes = 70 MB of PEL memory — significant!

What goes wrong:
  1. Memory: PEL accumulates → OOM if unchecked
  2. XCLAIM/XAUTOCLAIM: must scan the entire PEL to find stalled messages
     → PEL has 1M entries → XAUTOCLAIM is slow to scan
  3. XINFO GROUPS "lag" metric becomes inaccurate (lag ≠ unprocessed if ACK skipped)

Solutions:
  1. Always XACK after processing (non-negotiable for consumer groups)
  2. Set MAXLEN on XADD to cap stream size (prevents stream memory growth)
  3. Monitor PEL size: XPENDING stream group - + COUNT 1 → first check total pending
  4. Use NOACK in XREADGROUP if delivery guarantee is not needed (analytics)
  5. XAUTOCLAIM with TTL-based cleanup: if message idle > max_retries_window → dead-letter + XACK

Production check:
  XINFO GROUPS stream:orders | grep pending
  → If "pending" > 10000 and growing: something is wrong with ACK logic
```

**Q12. "How would you implement exactly-once delivery using Redis Streams?"**
A: Redis Streams guarantees **at-least-once delivery** — a message may be delivered multiple times (after crash + reclaim). True exactly-once requires an **idempotent consumer**:

```python
# True exactly-once = at-least-once + idempotent consumer

# Method 1: idempotency key in Redis (best for short-lived operations)
def idempotent_handler(fields: dict) -> None:
    msg_id    = fields.get("_msg_id", "unknown")   # pass msg_id in fields
    idem_key  = f"processed:{msg_id}"

    # Atomic check-and-set: if key exists → already processed → skip
    was_set = r.set(idem_key, "1", nx=True, ex=86400)  # SET NX EX 24h
    if not was_set:
        log.info(f"Message {msg_id} already processed, skipping")
        return   # idempotent skip — but still XACK (message WAS processed)

    # Process:
    send_email(fields["to"], fields["subject"], fields["body"])
    # On crash here: next delivery will find idem_key set → skip send, still ACK

# Method 2: database idempotency (transactional guarantee)
def db_idempotent_handler(fields: dict, msg_id: str) -> None:
    try:
        with db.transaction():
            # Unique constraint on stream_message_id prevents duplicate processing:
            db.execute(
                "INSERT INTO processed_messages (stream_msg_id, processed_at) VALUES (?, ?)"
                "ON CONFLICT (stream_msg_id) DO NOTHING",
                [msg_id, datetime.utcnow()]
            )
            # Only proceed if the INSERT succeeded (not a duplicate):
            rows_affected = db.last_row_count()
            if rows_affected == 0:
                return  # already processed

            # Do the actual work inside the same transaction:
            do_database_work(fields)
    except Exception:
        raise  # don't ACK; let it be retried

# Method 3: XADD with explicit ID (idempotent producer)
# If producer crashes after XADD but before getting confirmation:
# Re-send with the SAME explicit ID → Redis rejects duplicate (ID must be > last)
# Limitation: only works if producer knows what ID it generated
# Better: generate ID client-side, use as XADD id argument

def idempotent_xadd(stream: str, event: dict, event_id: str) -> None:
    # Use event_id as the Redis stream ID:
    # This requires event_id to be a valid Redis Stream ID format (ms-seq)
    # OR store event_id as a field and rely on consumer idempotency
    r.xadd(stream, {"event_id": event_id, **event})
    # Consumer checks: if event_id already in processed set → skip
```

**Q13. "Your stream has 1 million pending messages and consumers are not making progress. How do you diagnose and recover?"**
A:

```bash
# Step 1: Assess the situation
XINFO GROUPS stream:orders
# Output: pending: 1000000, lag: 1000000, consumers: 0
# → All consumers are down! PEL has grown to 1M entries.

XINFO CONSUMERS stream:orders email-service
# Output: empty list (no consumers currently connected)

# Step 2: Check stream health
XLEN stream:orders             # total stream length
XINFO STREAM stream:orders     # first/last entry, memory info

# Step 3: Check what's in the PEL
XPENDING stream:orders email-service - + 5  # sample 5 pending entries
# Shows: message IDs, consumer names, idle time (probably hours!), delivery count

# Step 4: Recovery options

# Option A: Restart consumers (they'll reclaim their own pending via "0" read)
# Start the email-service consumers → they XREADGROUP with "0" → re-process own PEL

# Option B: If consumers are permanently gone, reclaim all pending to a new consumer:
XGROUP DELCONSUMER stream:orders email-service dead-worker-1
# Returns: 500000 (orphaned messages now in group PEL, unclaimed)
# Then XAUTOCLAIM to new consumer:
XAUTOCLAIM stream:orders email-service new-worker-1 0 0-0 COUNT 1000
# Repeat until all claimed

# Option C: If backlog is too old / invalid — skip it:
XGROUP SETID stream:orders email-service $
# → Group's last-delivered-id jumps to current end of stream
# → 1M pending messages are "orphaned" in PEL (won't be delivered as "new")
# → WARNING: PEL still holds those 1M entries! Must clean up:
# Use XAUTOCLAIM to claim-and-discard them, or XGROUP DELCONSUMER for each consumer

# Option D: Drain PEL without reprocessing (acknowledge everything):
# Read all pending with "0" + XACK without processing:
while True:
    results = r.xreadgroup("email-service", "cleanup-worker",
                            {"stream:orders": "0"}, count=1000)
    if not results or not results[0][1]:
        break
    ids = [msg_id for msg_id, _ in results[0][1]]
    r.xack("stream:orders", "email-service", *ids)
    print(f"Discarded {len(ids)} stale messages")
```

from typing import Callable

r   = redis.Redis(decode_responses=True)
log = logging.getLogger(__name__)

STREAM = "stream:orders"

            maxlen=500_000,
            approximate=True,
        )

# ── Base consumer class ────────────────────────────────────────────────

class StreamConsumer:
    def __init__(
        self,
        stream:      str,
        group:       str,
        consumer_id: str,
        handler:     Callable[[dict], None],
        batch_size:  int = 10,
        block_ms:    int = 5_000,
        max_retries: int = 5,
        stale_ms:    int = 30_000,
    ):
        self.stream      = stream
        self.group       = group
        self.consumer    = consumer_id
        self.handler     = handler
        self.batch_size  = batch_size
        self.block_ms    = block_ms
        self.max_retries = max_retries
        self.stale_ms    = stale_ms
        self._setup_group()

    def _setup_group(self) -> None:
        try:
            r.xgroup_create(self.stream, self.group, id="$", mkstream=True)
            log.info(f"Created consumer group '{self.group}'")
        except redis.exceptions.ResponseError as e:
            if "BUSYGROUP" not in str(e):
                raise

    def run(self) -> None:
        log.info(f"Consumer {self.consumer} starting in group {self.group}")
        # Phase 1: recover any messages this consumer had pending before restart
        self._process_own_pending()
        # Phase 2: main loop
        while True:
            self._try_claim_stalled()
            self._consume_new()

    def _process_own_pending(self) -> None:
        log.info("Checking for own pending messages...")
        while True:
            results = r.xreadgroup(
                self.group, self.consumer,
                {self.stream: "0"},   # "0" = my pending messages
                count=self.batch_size
            )
            if not results or not results[0][1]:
                break
            _, msgs = results[0]
            log.info(f"Re-processing {len(msgs)} pending messages from previous session")
            self._handle_batch(msgs)

    def _consume_new(self) -> None:
        results = r.xreadgroup(
            self.group, self.consumer,
            {self.stream: ">"},       # ">" = new, undelivered messages
            count=self.batch_size,
            block=self.block_ms
        )
        if results:
            _, msgs = results[0]
            self._handle_batch(msgs)

    def _handle_batch(self, msgs: list) -> None:
        ack_ids = []
        for msg_id, fields in msgs:
            if self._process_one(msg_id, fields):
                ack_ids.append(msg_id)

        if ack_ids:
            r.xack(self.stream, self.group, *ack_ids)
            log.debug(f"ACKed {len(ack_ids)} messages")

    def _process_one(self, msg_id: str, fields: dict) -> bool:
        try:
            self.handler(fields)
            return True
        except Exception as e:
            log.error(f"Handler failed for {msg_id}: {e}")
            return False   # stays in PEL; will be retried via stale claim

    def _try_claim_stalled(self) -> None:
        start = "0-0"
        claimed_count = 0
        while True:
            next_id, msgs, deleted = r.xautoclaim(
                self.stream, self.group, self.consumer,
                min_idle_time=self.stale_ms,
                start_id=start,
                count=20
            )
            if msgs:
                # Check retry count before processing:
                filtered = self._filter_dead_letters(msgs)
                if filtered:
                    self._handle_batch(filtered)
                    claimed_count += len(filtered)

            if next_id == "0-0":
                break
            start = next_id

        if claimed_count:
            log.info(f"Reclaimed {claimed_count} stalled messages")

    def _filter_dead_letters(self, msgs: list) -> list:
        valid = []
        dead_ids = []
        for msg_id, fields in msgs:
            pending = r.xpending_range(
                self.stream, self.group, min=msg_id, max=msg_id, count=1
            )
            if pending and pending[0]["times_delivered"] >= self.max_retries:
                self._send_to_dead_letter(msg_id, fields)
                dead_ids.append(msg_id)
            else:
                valid.append((msg_id, fields))

        if dead_ids:
            r.xack(self.stream, self.group, *dead_ids)

        return valid

    def _send_to_dead_letter(self, msg_id: str, fields: dict) -> None:
        r.xadd(
            f"{self.stream}:dead-letter:{self.group}",
            {
                "original_id":     msg_id,
                "original_fields": json.dumps(fields),
                "group":           self.group,
                "consumer":        self.consumer,
                "failed_at":       str(time.time()),
            },
            maxlen=10_000,
            approximate=True
        )
        log.warning(f"Dead-lettered {msg_id} after {self.max_retries} attempts")

# ── Service handlers ───────────────────────────────────────────────────

def inventory_handler(fields: dict) -> None:
    if fields.get("event_type") != "order.placed":
        return   # skip non-relevant events

    order_id = fields["order_id"]

## Problem 2 — Event Sourcing with Stream Replay

### Problem
Build an account balance system using Redis Streams as the event store. The balance is derived entirely from the event log — not stored directly. Support balance queries, event replay, and point-in-time balance reconstruction.

```python
from decimal import Decimal

ACCOUNT_STREAM_PREFIX = "eventsource:account"

class AccountEventStore:
    def append_event(self, account_id: str, event_type: str, amount: Decimal,
                     metadata: dict | None = None) -> str:
        stream = f"{ACCOUNT_STREAM_PREFIX}:{account_id}"
        msg_id = r.xadd(stream, {
            "event_type": event_type,        # "deposit" | "withdrawal" | "fee" | "interest"
            "amount":     str(amount),
            "currency":   "USD",
            "metadata":   json.dumps(metadata or {}),
            "created_at": str(time.time()),
        })
        # Invalidate cached balance:
        r.delete(f"balance:cache:{account_id}")
        return msg_id

    def deposit(self, account_id: str, amount: Decimal, note: str = "") -> str:
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        return self.append_event(account_id, "deposit", amount, {"note": note})

    def withdraw(self, account_id: str, amount: Decimal, note: str = "") -> str:
        if amount <= 0:
            raise ValueError("Withdrawal amount must be positive")
        # Check balance before writing (read-then-write, not atomic — acceptable here):
        current = self.get_balance(account_id)
        if current < amount:
            raise ValueError(f"Insufficient funds: balance={current}, requested={amount}")
        return self.append_event(account_id, "withdrawal", amount, {"note": note})

    def get_balance(self, account_id: str, at_time: float | None = None) -> Decimal:
        # Check cache first (only for current balance, not historical):
        if at_time is None:
            cached = r.get(f"balance:cache:{account_id}")
            if cached:
                return Decimal(cached)

        balance = self._replay(account_id, at_time)

        if at_time is None:
            r.setex(f"balance:cache:{account_id}", 60, str(balance))

        return balance

    def _replay(self, account_id: str, until_time: float | None = None) -> Decimal:
        stream  = f"{ACCOUNT_STREAM_PREFIX}:{account_id}"
        balance = Decimal("0")
        start   = "0"

        while True:
            # Read in batches to avoid loading entire stream into memory:
            entries = r.xrange(stream, start, "+", count=500)
            if not entries:
                break

            for msg_id, fields in entries:
                # Stop replay at point-in-time if specified:
                if until_time is not None:
                    entry_ts = float(fields.get("created_at", 0))
                    if entry_ts > until_time:
                        return balance

                amount     = Decimal(fields["amount"])
                event_type = fields["event_type"]

                if event_type in ("deposit", "interest"):
                    balance += amount
                elif event_type in ("withdrawal", "fee"):
                    balance -= amount
                # else: unknown event type → log and skip

            # Advance start to one past the last entry:
            last_id = entries[-1][0]
            # Convert "1704067200000-0" to "1704067200000-1":
            ms, seq = last_id.split("-")
            start   = f"{ms}-{int(seq) + 1}"

            if len(entries) < 500:
                break   # got fewer than batch_size → we've read everything

        return balance

    def get_transaction_history(
        self, account_id: str, start_time: float | None = None, limit: int = 50
    ) -> list[dict]:
        stream   = f"{ACCOUNT_STREAM_PREFIX}:{account_id}"
        start_id = f"{int(start_time * 1000)}-0" if start_time else "0"

        entries = r.xrevrange(stream, "+", start_id, count=limit)
        return [
            {
                "id":         msg_id,
                "type":       fields["event_type"],
                "amount":     Decimal(fields["amount"]),
                "timestamp":  float(fields.get("created_at", 0)),
                "metadata":   json.loads(fields.get("metadata", "{}")),
            }
            for msg_id, fields in entries
        ]

    def get_balance_at(self, account_id: str, timestamp: float) -> Decimal:
        return self._replay(account_id, until_time=timestamp)

    def get_running_balance(self, account_id: str) -> list[dict]:
        """Return all events with running balance at each point."""
        stream  = f"{ACCOUNT_STREAM_PREFIX}:{account_id}"
        balance = Decimal("0")
        result  = []

        for msg_id, fields in r.xrange(stream, "-", "+"):
            amount     = Decimal(fields["amount"])
            event_type = fields["event_type"]
            if event_type in ("deposit", "interest"):
                balance += amount
            elif event_type in ("withdrawal", "fee"):
                balance -= amount

            result.append({
                "id":              msg_id,
                "type":            event_type,
                "amount":          amount,
                "running_balance": balance,
                "timestamp":       float(fields.get("created_at", 0)),
            })

        return result

# Usage:
store = AccountEventStore()
store.deposit("acct-001",  Decimal("1000.00"), note="Initial deposit")
store.deposit("acct-001",  Decimal("500.00"),  note="Paycheck")
store.withdraw("acct-001", Decimal("200.00"),  note="Rent")

print(store.get_balance("acct-001"))           # → Decimal('1300.00')
print(store.get_balance_at("acct-001", time.time() - 3600))  # balance 1 hour ago

# Auditing: rebuild balance from scratch at any point
history = store.get_running_balance("acct-001")
for entry in history:
    print(f"{entry['type']:12} {entry['amount']:>10} → balance: {entry['running_balance']}")
# deposit       1000.00 → balance: 1000.00
# deposit        500.00 → balance: 1500.00
# withdrawal     200.00 → balance: 1300.00
```

AUDIT_STREAM = "audit:admin_actions"

                "ip_address":  ip_address,
                "result":      result,
                "timestamp":   str(time.time()),
            },
            # Retention: trim entries older than 90 days:
            minid=f"{cutoff_ms}-0",
            approximate=True,
        )
        # Secondary indexes for efficient filtering (using Sorted Sets):
        self._update_indexes(admin_id, msg_id, resource)
        return msg_id

    def _update_indexes(self, admin_id: str, msg_id: str, resource: str) -> None:
        now = time.time()
        pipe = r.pipeline()
        # Index by admin_id: ZSet with score=timestamp for time-range queries per admin:
        pipe.zadd(f"audit:idx:admin:{admin_id}", {msg_id: now})
        pipe.expire(f"audit:idx:admin:{admin_id}", 86400 * self.RETENTION_DAYS)
        # Index by resource type:
        pipe.zadd(f"audit:idx:resource:{resource}", {msg_id: now})
        pipe.expire(f"audit:idx:resource:{resource}", 86400 * self.RETENTION_DAYS)
        # Trim indexes to same retention window:
        cutoff = now - self.RETENTION_DAYS * 86400
        pipe.zremrangebyscore(f"audit:idx:admin:{admin_id}", 0, cutoff)
        pipe.zremrangebyscore(f"audit:idx:resource:{resource}", 0, cutoff)
        pipe.execute()

    def query_by_admin(
        self,
        admin_id: str,
        start_time: float | None = None,
        end_time:   float | None = None,
        limit: int = 100,
    ) -> list[dict]:
        index_key = f"audit:idx:admin:{admin_id}"
        min_score = start_time if start_time else "-inf"
        max_score = end_time   if end_time   else "+inf"

        # Get message IDs from the ZSet index:
        msg_ids = r.zrangebyscore(
            index_key, min_score, max_score,
            start=0, num=limit
        )
        if not msg_ids:
            return []

        return self._fetch_by_ids(msg_ids)

    def _fetch_by_ids(self, msg_ids: list[str]) -> list[dict]:
        pipe = r.pipeline()
        for msg_id in msg_ids:
            ms, seq = msg_id.split("-")
            pipe.xrange(AUDIT_STREAM, msg_id, msg_id, count=1)
        results = pipe.execute()

        entries = []
        for batch in results:
            for msg_id, fields in batch:
                entries.append({
                    "id":          msg_id,
                    "admin_id":    fields["admin_id"],
                    "action":      fields["action"],
                    "resource":    fields["resource"],
                    "resource_id": fields["resource_id"],
                    "details":     json.loads(fields["details"]),
                    "ip_address":  fields["ip_address"],
                    "result":      fields["result"],
                    "timestamp":   float(fields["timestamp"]),
                })
        return entries

    def query_time_range(
        self, start_time: float, end_time: float, limit: int = 1000
    ) -> list[dict]:
        # Stream supports direct time-range queries via ID format:
        start_id = f"{int(start_time * 1000)}-0"
        end_id   = f"{int(end_time * 1000)}-{2**32 - 1}"  # max sequence for end ms

        entries = r.xrange(AUDIT_STREAM, start_id, end_id, count=limit)
        return [
            {
                "id":          msg_id,
                **{k: json.loads(v) if k == "details" else v
                   for k, v in fields.items()},
                "timestamp":   float(fields.get("timestamp", 0)),
            }
            for msg_id, fields in entries
        ]

    def export_for_compliance(self, output_file: str) -> int:
        """Export entire audit log to a file for compliance reporting."""
        count = 0
        start = "0"

        with open(output_file, "w") as f:
            while True:
                batch = r.xrange(AUDIT_STREAM, start, "+", count=1000)
                if not batch:
                    break

                for msg_id, fields in batch:
                    record = {"_id": msg_id, **fields, "details": json.loads(fields["details"])}
                    f.write(json.dumps(record) + "\n")
                    count += 1

                last_id = batch[-1][0]
                ms, seq = last_id.split("-")
                start   = f"{ms}-{int(seq) + 1}"

                if len(batch) < 1000:
                    break

        return count

            "total_entries":     info["length"],
            "first_entry_id":    info.get("first-entry", [None, None])[0],
            "last_entry_id":     info.get("last-entry",  [None, None])[0],

        try:
            groups = r.xinfo_groups(self.stream)
        except redis.exceptions.ResponseError:
            return []

        health = []
        for g in groups:
            consumers = []
            try:
                consumers_raw = r.xinfo_consumers(self.stream, g["name"])
                consumers = [
                    {
                        "name":        c["name"],
                        "pending":     c["pending"],
                        "idle_ms":     c["idle"],
                        "stalled":     c["idle"] > 30_000 and c["pending"] > 0,
                    }
                    for c in consumers_raw
                ]
            except Exception:
                pass

            # Count stalled messages (idle > 30s):
            stalled_count = 0
            try:
                stalled = r.xpending_range(
                    self.stream, g["name"],
                    min="-", max="+", count=100,
                    idle=30_000
                )
                stalled_count = len(stalled)
            except Exception:
                pass

            lag = g.get("lag", 0)
            health.append({
                "group":              g["name"],
                "pending_total":      g["pending"],
                "lag":                lag,

                "last_delivered_id":  g["last-delivered-id"],
                "consumers":          consumers,
                "stalled_messages":   stalled_count,
                "consumer_count":     g["consumers"],
            })

        cutoff_ms  = int((time.time() - sample_seconds) * 1000)

        # XLEN gives total; count entries after cutoff to estimate recent rate:
        recent_entries = 0
        try:
            batch = r.xrange(self.stream, cutoff_id, "+", count=10_000)
            recent_entries = len(batch)

            pass

            "entries_last_60s":    recent_entries,
            "estimated_per_second": round(recent_entries / sample_seconds, 2),

                        "dead_letter_count": dl_count,

            pass

## Quick Reference — Redis Streams Cheat Sheet

```
CORE COMMANDS:
  XADD   key [NOMKSTREAM] [MAXLEN|MINID [~] N] *|id field value [...]
         → append entry; * = auto-ID; ~ = approximate trim (use in prod!)
  XREAD  [COUNT n] [BLOCK ms] STREAMS key id
         → read entries independently; 0 = from start; $ = new only
  XREADGROUP GROUP g consumer [COUNT n] [BLOCK ms] [NOACK] STREAMS key >|id
         → read as group member; > = new; 0 = own pending; id = specific
  XACK   key group id [id ...]
         → acknowledge; removes from PEL; must call after successful processing
  XLEN   key                       → O(1) entry count
  XRANGE key start end [COUNT n]   → iterate forward (-=oldest, +=newest)
  XREVRANGE key end start [COUNT n] → iterate backward
  XTRIM  key MAXLEN|MINID [~] threshold → explicit trim (vs XADD MAXLEN)
  XDEL   key id [id ...]           → remove specific entries (tombstone)

CONSUMER GROUP COMMANDS:
  XGROUP CREATE  key group id [MKSTREAM] → create group; id=0 replay; id=$ new only
  XGROUP SETID   key group id            → rewind/skip (0=replay; $=drop backlog)
  XGROUP DESTROY key group              → delete group + its PEL
  XGROUP DELCONSUMER key group consumer → remove consumer + its pending (careful!)
  XPENDING key group [IDLE ms] - + count [consumer] → inspect in-flight messages
  XCLAIM     key group consumer min-idle-ms id [...]  → manually reassign pending
  XAUTOCLAIM key group consumer min-idle-ms start-id [COUNT n]  → auto scan+claim (6.2+)

INSPECTION:
  XINFO STREAM   key           → stream metadata, first/last entry
  XINFO GROUPS   key           → per-group: pending, lag, last-delivered-id
  XINFO CONSUMERS key group    → per-consumer: pending, idle time

ENTRY ID FORMAT:
  <milliseconds>-<sequence>    e.g.: 1704067200000-0
  *: auto-generate (always use in production)
  $: "current last ID" at time of command (XREAD for tailing; XGROUP CREATE to skip history)
  >: "next undelivered" (XREADGROUP only; triggers PEL tracking)
  0 or 0-0: beginning of stream
  -: minimum possible ID (XRANGE start)
  +: maximum possible ID (XRANGE end)

TRIMMING (choose ~ approximate in production):
  MAXLEN = 1000:  keep EXACTLY 1000 entries (expensive; splits listpack nodes)
  MAXLEN ~ 1000:  keep approximately 1000 (fast; only trims full nodes)
  MINID  ~ X:     trim entries with ID < X (time-based retention via timestamp in ID)

DELIVERY GUARANTEES:
  at-least-once:  XREADGROUP + XACK → message stays in PEL until ACKed
  exactly-once:   at-least-once + idempotent consumer (check/set idempotency key before processing)
  at-most-once:   XREADGROUP NOACK → no PEL tracking; crash = lost message

CRASH RECOVERY PATTERN:
  On startup:     XREADGROUP ... STREAMS key 0   → re-read own pending (not yet ACKed)
  Stalled msgs:   XAUTOCLAIM ... min-idle-time   → claim messages idle > threshold
  Dead letters:   track delivery count; after max_retries → XADD dead-letter stream + XACK

COMPARISON:
  vs List:       Stream keeps history; List deletes on pop; Stream has PEL + groups
  vs Pub/Sub:    Stream persists; Pub/Sub fire-and-forget; Stream has ACK + groups
  vs Kafka:      Kafka: disk-based, partitioned, millions/sec; Stream: RAM, simpler ops
  Use Stream:    reliable task queue, event sourcing, microservice messaging, audit log
  Use Pub/Sub:   live chat, real-time dashboard push, "live or nothing" signals only

COMMON BUGS:
  Forgetting XACK          → PEL grows unboundedly → OOM eventually
  Using $ start for replay → new services miss historical messages (use 0 instead)
  Not recovering pending   → on restart, skip re-reading own PEL → messages silently dropped
  No XCLAIM/XAUTOCLAIM     → stalled messages (from crashed workers) never retried
  MAXLEN without ~          → expensive exact trim on every XADD → use ~ always
  No dead-letter handling  → poison pill messages loop forever (incr delivery count forever)
  XDEL without XACK        → PEL entry becomes orphaned (references deleted entry)
  Single consumer per group → no parallelism; add more consumers to same group for scaling
  BLOCK 0 in prod          → blocks the connection forever if stream is empty at exactly that moment;
                             use a reasonable timeout (e.g., BLOCK 5000) and loop
```

**Final Tip:** At the 5 YOE level, Redis Streams questions test whether you understand the **PEL as the source of truth for in-flight work** and can explain the complete lifecycle of a message from `XADD` to `XACK`. The highest-signal answer on why Streams beat Pub/Sub for task queues: "Pub/Sub has no persistence — if the subscriber is down for even one second, those messages are gone forever. Streams store every message until explicitly trimmed, so a consumer that's offline for an hour comes back and processes everything it missed via its consumer group position. The consumer group's `last-delivered-id` is the key: it advances only as messages are delivered, and the PEL tracks which delivered messages haven't been acknowledged yet. If the worker crashes, those PEL entries stay there until another worker claims them via `XAUTOCLAIM`. This gives you at-least-once delivery, which you then make exactly-once by storing a processed flag in Redis before doing the side effect." For the `>` vs `0` distinction: "The `>` special ID in `XREADGROUP` means 'give me messages that haven't been delivered to any consumer in this group yet' — it's the normal operational mode. Passing `0` instead means 're-give me my own pending messages that I got but haven't ACKed' — this is what you call on startup to re-process anything that was in-flight when the process crashed. If you always use `>` and never handle `0` on startup, you silently drop every message that was mid-processing at crash time."
