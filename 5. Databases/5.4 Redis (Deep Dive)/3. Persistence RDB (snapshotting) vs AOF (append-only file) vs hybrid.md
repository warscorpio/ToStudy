# Redis Persistence: RDB, AOF, and Hybrid — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does Redis need persistence and what is the fundamental challenge it faces?**
A: Redis is an in-memory data store — all data lives in RAM for microsecond access times. Without persistence, a Redis restart (planned or due to crash) loses all data. Persistence writes data to disk so it can be recovered after a restart. The fundamental challenge is that writing to disk is orders of magnitude slower than memory operations, and doing it naively would block the event loop and destroy Redis's single-threaded performance:

```
The core tension:

  Redis's value proposition:
    All data in RAM → sub-millisecond reads and writes
    Single-threaded event loop → no lock contention
    Throughput: 100,000–1,000,000 ops/second

  Disk persistence requirements:
    Sequential disk write: ~100MB/s (SSD) → 10ms for 1GB
    fsync (durable flush): 1–10ms per call
    Writing 10GB dataset: ~100 seconds of blocking I/O

  If persistence blocks the event loop:
    All client requests pause while data is written to disk
    A 10GB RDB save takes ~100s → application appears frozen for 100s
    Unacceptable for any production workload

Redis's solution: fork-based persistence
  Redis uses fork() to create a child process
  The child handles all disk I/O
  The parent (Redis server) continues serving requests
  The OS uses copy-on-write (CoW) semantics:
    Child shares the parent's memory pages initially (no copy needed)
    When parent modifies a page: OS copies that page for the child
    Child always sees the original (pre-fork) snapshot of memory
  Cost: not disk I/O blocking the event loop, but fork() itself + CoW copies

What each persistence mode covers:
  No persistence: fastest, but data is ephemeral (cache-only use case)
  RDB (snapshotting): periodic full dumps — good throughput, risk of data loss
  AOF (Append-Only File): every write logged — low data loss risk, larger files
  Hybrid (RDB+AOF): combines both — recommended for most production use cases
```

**Q2. What is copy-on-write (CoW) and why is it critical to understanding Redis persistence performance?**
A: Copy-on-write is a Linux kernel optimization that makes `fork()` nearly instantaneous regardless of dataset size. When Redis forks a child process, the kernel does not immediately copy all memory — instead it marks all memory pages as shared and read-only. A copy is made only when either process modifies a page. This makes the fork fast but creates a write amplification cost:

```
Copy-on-write mechanics:

  Before fork:
    Parent process: [Page A: loan data] [Page B: user data] [Page C: session data]
    All pages in RAM, writable

  Immediately after fork():
    Parent: [Page A] [Page B] [Page C]  ← all marked read-only (shared)
    Child:  [Page A] [Page B] [Page C]  ← same physical pages (no copy!)
    Fork time: milliseconds (just copies the page table, not the pages)

  Parent receives a write (e.g. UPDATE loan status):
    OS triggers: copy Page A to a new physical location
    Parent modifies new copy of Page A
    Child still reads original Page A (snapshot from fork time)
    Physical RAM: now has two copies of Page A

  Child writes RDB/AOF to disk:
    Child reads its pages (original pre-fork snapshots)
    Writes them sequentially to disk
    No interference with parent's operations

Memory overhead during persistence:
  Best case (no writes during save): child uses ~0 extra memory (all pages shared)
  Worst case (high write rate during save): parent modifies all pages → 2× memory usage
  Practical case: 10–30% extra memory during save for typical workloads

  This is why Redis recommends:
  maxmemory should be 50–60% of physical RAM
  to leave room for CoW overhead during saves

CoW and latency:
  fork() itself: proportional to page table size (number of pages) NOT data size
    1GB dataset: fork in ~10ms
    10GB dataset: fork in ~100ms
    During fork: Redis is BLOCKED (single-threaded, cannot serve requests)
    This fork latency is the "fork tax" — visible as a latency spike in metrics

  After fork: Redis runs normally; child runs concurrently on separate CPU core

  Latency spikes during fork (observable with LATENCY HISTORY):
  redis-cli LATENCY HISTORY fork
  # Timestamps and duration of fork() calls
  # > 200ms fork time → dataset too large or THP (Transparent Huge Pages) enabled
  # Fix THP: echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

## Section 2: RDB (Snapshotting)

**Q3. How does RDB persistence work and what is the binary format it produces?**
A: RDB (Redis Database) persistence creates a point-in-time snapshot of the entire dataset as a compact binary file. Redis forks a child process to write the snapshot; the child serializes all key-value pairs into the RDB format and atomically renames the file when complete. The primary purpose is fast restarts and compact backups:

```
RDB file structure (binary format):

  ┌─────────────────────────────────────────────────────────────┐
  │ Magic string: "REDIS" (5 bytes)                             │
  │ RDB version:  "0011" (4 bytes, current version 11)         │
  ├─────────────────────────────────────────────────────────────┤
  │ Auxiliary fields (metadata):                                │
  │   redis-ver:  "7.2.3"                                      │
  │   redis-bits: 64                                           │
  │   ctime:      Unix timestamp of creation                   │
  │   used-mem:   memory used at save time                     │
  ├─────────────────────────────────────────────────────────────┤
  │ Per-database sections:                                      │
  │   SELECT db_number (0xFF opcode + varint)                  │
  │   DB size info: key count + expiry count                   │
  │   Per key-value pair:                                      │
  │     [optional: expiry timestamp]                           │
  │     [type byte: string=0, list=10, set=2, zset=3, hash=4] │
  │     [key: length-prefixed string]                          │
  │     [value: type-specific encoding]                        │
  ├─────────────────────────────────────────────────────────────┤
  │ EOF marker (0xFF)                                           │
  │ CRC64 checksum (8 bytes)                                   │
  └─────────────────────────────────────────────────────────────┘

Compact encoding examples:
  Integer strings: "12345" stored as integer (3 bytes instead of 7)
  Small lists/sets/hashes/zsets: listpack encoding (dense format, no pointers)
  Large collections: linked list / skip list / hashtable encoding

RDB file operations:
  Write: temporary file → complete write → atomic rename (no corruption on crash)
  Read (on startup): load entire file into memory sequentially
    Load speed: ~0.5–2GB/second from SSD
    10GB RDB: 5–20 seconds to load on startup

Triggering RDB saves:

  1. Automatic (save directives in redis.conf):
  save 3600 1      # save if ≥1 key changed in last 3600s (1 hour)
  save 300 100     # save if ≥100 keys changed in last 300s (5 min)
  save 60 10000    # save if ≥10000 keys changed in last 60s (1 min)
  # Multiple conditions: save when ANY condition is met
  # Default Redis config includes all three above

  2. Manual (blocks or forks):
  BGSAVE        # background save (forks child, returns immediately)
  SAVE          # foreground save (BLOCKS Redis until complete) — never use in production

  3. Shutdown:
  SHUTDOWN SAVE   # save on clean shutdown (if RDB enabled)

  4. Replication:
  # When a replica connects: primary creates RDB and sends to replica
  # This is an automatic BGSAVE triggered by replica sync

Checking RDB status:
  redis-cli LASTSAVE           # Unix timestamp of last successful RDB save
  redis-cli BGSAVE             # Trigger background save
  redis-cli INFO persistence
  # rdb_last_save_time: 1705313400
  # rdb_changes_since_last_save: 15234  ← writes since last save (potential loss on crash)
  # rdb_bgsave_in_progress: 0
  # rdb_last_bgsave_status: ok
  # rdb_last_bgsave_time_sec: 12       ← last save took 12 seconds
```

**Q4. What are the RDB persistence tradeoffs — specifically the data loss window and the fork cost?**

```
RDB data loss window:

  Scenario with save 60 10000 (save every minute if 10K changes):
  T=0:    RDB save completed (all data on disk)
  T=1s:   Application writes loan disbursement record
  T=2s:   Application writes repayment record
  ...
  T=59s:  9999 more writes have occurred
  T=60s:  RDB save triggers (10000 change threshold met)
  T=61s:  Server crashes BEFORE the 60s save completes (save was in progress)

  Data at T=61s:
    On disk (last successful RDB): state at T=0
    In memory (lost): everything from T=1s to T=61s
    Data loss: up to 60+ seconds of writes = potentially thousands of operations

  The RDB data loss window equals the interval between successful saves.
  For save 60 10000: worst case loss = ~60 seconds + save duration

  Financial implications:
    Loan disbursement at T=1s: in memory, NOT on disk → lost on crash
    Application "succeeded" (client received OK) → customer expects disbursement
    Database shows no record → data inconsistency

  Acceptable use cases for this level of loss:
  ✓ Cache layers (Redis as L2 cache — source of truth is elsewhere)
  ✓ Session storage (sessions can be re-authenticated)
  ✓ Rate limiting counters (slight inaccuracy after crash is acceptable)
  ✓ Leaderboards / ephemeral rankings

  Not acceptable for:
  ✗ Financial transactions (disbursements, payments, transfers)
  ✗ Inventory counts (overselling is a business problem)
  ✗ Deduplication keys (re-processing after crash causes duplicates)
  ✗ Any data where the application has confirmed success to the user

RDB fork cost:

  fork() latency (Redis is BLOCKED during fork):
  Dataset size │ Approximate fork time │ Impact
  ─────────────┼──────────────────────┼──────────────────────────────────
  1 GB         │ 10–20 ms             │ Barely noticeable
  5 GB         │ 50–100 ms            │ Occasional latency spike
  10 GB        │ 100–200 ms           │ P99 latency spikes visible
  50 GB        │ 500ms–1s             │ Serious latency problem
  100 GB       │ 1–2 seconds          │ Application timeouts

  The fork latency is from copying the page table, not the data.
  Transparent Huge Pages (THP) dramatically worsen this:
    Normal 4KB pages: 1GB = 262,144 pages → small page table
    THP 2MB pages:    1GB = 512 pages → large per-page metadata
    With THP: fork for 10GB can take 2–5s → Redis stalls
    ALWAYS disable THP for Redis: echo never > /sys/kernel/mm/transparent_hugepage/enabled

  Post-fork CoW overhead:
    During RDB save: parent writes cause page copies
    High write throughput during save → higher memory usage, more CPU
    Rule: allow extra 20–30% memory headroom for CoW during saves
    If Redis OOM-kills during save: maxmemory is too close to physical RAM

  Disabling RDB completely (cache-only Redis):
  # redis.conf:
  save ""          # disable all automatic saves
  # Or: comment out all save lines
  # Also set: appendonly no (if not using AOF)
```

## Section 3: AOF (Append-Only File)

**Q5. How does AOF persistence work and what does it write?**
A: AOF (Append-Only File) records every write command executed by Redis in the order received. On restart, Redis replays the AOF file command by command to reconstruct the dataset. Unlike RDB which is a full snapshot, AOF is an incremental log of operations — providing much finer granularity of durability at the cost of larger files and slower restarts:

```
AOF format:

  Every write command is serialized in RESP (Redis Serialization Protocol) format
  and appended to the AOF file:

  Example: SET loan:L1 "{status:approved}" EX 3600
  AOF entry:
  *5\r\n           ← 5 arguments
  $3\r\n           ← argument 1 length: 3 bytes
  SET\r\n          ← argument 1: "SET"
  $9\r\n           ← argument 2 length: 9 bytes
  loan:L1\r\n      ← argument 2: key
  $17\r\n          ← argument 3 length: 17 bytes
  {status:approved}\r\n  ← argument 3: value
  $2\r\n           ← argument 4 length: 2 bytes
  EX\r\n           ← argument 4: "EX"
  $4\r\n           ← argument 5 length: 4 bytes
  3600\r\n         ← argument 5: TTL

  Commands recorded: SET, GET (no), INCR, HSET, LPUSH, ZADD, DEL, EXPIRE, etc.
  Commands NOT recorded: read-only commands (GET, HGET, LRANGE, etc.)
  → AOF records ONLY write operations

  On startup: Redis reads AOF file line by line, re-executes each command
  Final state: identical to the state when the AOF was last written

AOF append flow (single-threaded write path):

  Client command received
       ↓
  Command executed in memory (in-memory state updated immediately)
       ↓
  Command appended to AOF write buffer (in-memory, not yet on disk)
       ↓
  Response sent to client (client receives OK)
       ↓
  Background thread: flushes AOF buffer to disk (fsync policy determines when)

  Critical: client receives success BEFORE the fsync
  Whether the data is durable depends on the fsync policy (Q6)

AOF file growth:
  Every write adds to the AOF file → file grows without bound
  Without rewriting: SET key 1, SET key 2, ..., SET key 1000
    AOF has 1000 entries for one key
  After AOF rewrite: AOF has 1 entry (the final state)

AOF rewrite (compaction):

  BGREWRITEAOF command:
    Forks a child process
    Child scans current in-memory state (not the old AOF file)
    Writes a NEW AOF containing only the minimum commands to recreate current state
    Parent buffers new writes to an AOF rewrite buffer during the child's work
    When child finishes: parent appends rewrite buffer to new AOF, atomically replaces old

  Automatic rewrite triggers (redis.conf):
  auto-aof-rewrite-percentage 100   # rewrite when AOF is 100% larger than baseline
  auto-aof-rewrite-min-size 64mb    # don't rewrite if AOF < 64MB

  Example automatic rewrite sequence:
    AOF baseline (after last rewrite): 100MB
    AOF grows to 200MB (100% increase) → BGREWRITEAOF triggered
    New AOF (after rewrite): 80MB (compacted)
    New baseline: 80MB → next rewrite at 160MB

  Rewrite performance:
    Forks a child → same CoW concerns as RDB
    For 10GB dataset: rewrite fork ~100ms, write ~30s
    During rewrite: parent continues serving requests (no blocking)

Checking AOF status:
  redis-cli INFO persistence
  # aof_enabled: 1
  # aof_rewrite_in_progress: 0
  # aof_rewrite_scheduled: 0
  # aof_last_rewrite_time_sec: 28
  # aof_current_size: 134217728     ← current AOF file size (128MB)
  # aof_base_size: 67108864         ← size after last rewrite (64MB)
  # aof_pending_rewrite: 0
  # aof_buffer_length: 0            ← bytes in write buffer (not yet flushed)
  # aof_rewrite_buffer_length: 0    ← bytes buffered during rewrite
  # aof_last_bgrewrite_status: ok
  # aof_last_write_status: ok
```

**Q6. What are the three AOF fsync policies and what durability do they each provide?**
A: The fsync policy is the most important AOF configuration decision — it determines exactly when AOF data is flushed to the operating system's durable storage. There are three modes, each trading off durability vs performance:

```
fsync policies (appendfsync in redis.conf):

┌──────────────┬──────────────────────────────┬──────────────┬───────────────────┐
│ Policy       │ When fsync() is called        │ Data loss    │ Performance       │
│              │                               │ on crash     │ impact            │
├──────────────┼──────────────────────────────┼──────────────┼───────────────────┤
│ always       │ After EVERY write command     │ ≤ 1 command  │ High (1 fsync/op) │
│ everysec     │ Once per second (background)  │ ≤ 1 second   │ Good (default)    │
│ no           │ Never (OS decides, ~30s)      │ ≤ 30 seconds │ Best (no fsync)   │
└──────────────┴──────────────────────────────┴──────────────┴───────────────────┘

appendfsync always:
  redis.conf: appendfsync always

  Mechanism:
    Each write command → append to AOF → fsync() → client receives OK
    fsync() is a synchronous call that blocks until OS confirms data is on disk
    Using a background thread to avoid blocking the event loop
    But throughput is limited by disk fsync speed (~100-1000 fsyncs/second on SSD)

  Durability: strongest possible — at most 1 command can be lost on crash
    If Redis crashes: last write was fsynced → data is intact
    If OS crashes: last fsynced write is safe (prior to fsync in progress = lost)

  Performance: significant throughput reduction
    SSD: ~10,000–50,000 writes/second max (limited by fsync rate)
    vs Redis without persistence: 100,000–1,000,000 writes/second
    For high-throughput applications: 10× throughput reduction

  Use for:
  ✓ Financial transactions where every command must be durable
  ✓ Counters / IDs that must not be re-issued after crash
  ✗ High-throughput write paths (cache updates, metrics)

appendfsync everysec (DEFAULT):
  redis.conf: appendfsync everysec

  Mechanism:
    Write commands → append to AOF buffer (in-memory, fast)
    Background thread: fsync() called once per second
    Client receives OK immediately after memory write (not after fsync)

  Durability: lose at most 1 second of writes on crash
    If Redis crashes at 14:00:00.999: data written since 13:59:59.999 may be lost
    The "1 second" is not exact — it's time since LAST fsync, not wall time
    High write throughput: 1 second of data = thousands to millions of commands

  Performance: excellent
    Throughput: effectively same as no-persistence (write to buffer is fast)
    Background fsync: runs on a different thread, minimal impact on event loop
    Latency: occasional 1–2ms spike when fsync blocks the buffer swap

  Use for: most production workloads
  ✓ Session storage, rate limiting, queues
  ✓ Application-level data where 1 second of loss is acceptable
  ✓ Primary Redis with replica (replica provides additional durability)
  ✗ Financial data requiring zero loss

appendfsync no:
  redis.conf: appendfsync no

  Mechanism:
    Redis never calls fsync() — writes to OS buffer only
    OS decides when to flush (typically every 30 seconds, up to as long as dirty page timeout)
    Data in OS buffer is lost if OS or server crashes (power failure, kernel panic)

  Durability: lose up to 30+ seconds of writes on crash (OS-dependent)

  Performance: best possible (no fsync overhead at all)

  Use for:
  ✓ AOF as a compaction mechanism only (with everysec being primary)
  ✓ Testing and development
  ✓ When durability is irrelevant (ephemeral data)
  ✗ Any production data you care about

# redis.conf AOF configuration:
appendonly yes             # enable AOF
appendfilename "redis.aof" # AOF filename (in dir specified by 'dir')
appendfsync everysec       # fsync policy
no-appendfsync-on-rewrite yes   # disable fsync during BGREWRITEAOF
                                # prevents fsync from blocking during rewrite
                                # slight data loss risk during rewrite (worth it)
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-use-rdb-preamble yes   # hybrid format (RDB snapshot + AOF delta) — see Q9
```

**Q7. What is AOF rewriting and what happens to the AOF during a crash mid-rewrite?**

```
AOF rewrite crash safety:

  Normal AOF corruption scenario (without rewrite):
    AOF write in progress: "SET key value\r\n"
    Power failure mid-write: "SET key va" → file has truncated entry
    On restart: Redis reads "SET key va" → RESP parse error
    Without handling: Redis refuses to start (corrupt AOF)

  Redis's truncation handling:
    aof-load-truncated yes (default):
      On startup: if AOF has a truncated last entry → log warning → continue loading
      The truncated entry is silently ignored
      All prior entries are replayed correctly
      Scenario: at most 1 command (the truncated one) is lost
    aof-load-truncated no:
      On startup: corrupt AOF → Redis refuses to start → manual intervention needed
      More strict: forces you to inspect/repair the AOF manually
      Use: when you need to ensure no data is silently lost

  Repairing a corrupt AOF manually:
  redis-check-aof --fix redis.aof
  # Scans AOF for the first corrupt entry
  # Truncates the file at that point (discards the corrupt entry and everything after)
  # Use with caution: may discard valid data after the first corrupt entry

  AOF rewrite crash safety:
    During BGREWRITEAOF:
      Child writes to a TEMP file (not the current AOF)
      Parent continues writing to CURRENT AOF
      Parent also buffers new writes to an in-memory rewrite buffer
      If child crashes mid-rewrite: temp file is discarded → no impact
        Current AOF is still intact → restart uses current AOF
      If parent crashes mid-rewrite: current AOF is intact → use current AOF
      Only after child COMPLETES:
        Parent appends rewrite buffer to temp file
        Atomic rename: temp file → new AOF (replaces old)
      The rename is atomic at OS level → no state where both old and new are partial

  Multi-part AOF (Redis 7.0+):
    Before 7.0: single monolithic AOF file
    Redis 7.0+: AOF split into multiple files
      base.rdb: RDB snapshot as the base
      incr.aof: incremental AOF delta since the base
      manifest: tracks which files are current
    Benefits: faster rewrites (base doesn't need rewriting)
               cleaner separation of base state and incremental changes
```

## Section 4: Hybrid Persistence (RDB + AOF)

**Q8. What is the hybrid persistence mode and why is it the recommended production configuration?**
A: Hybrid persistence enables both RDB and AOF simultaneously. Redis uses the AOF for durability (at-most-1-second loss with `everysec`) and maintains RDB snapshots for fast restarts and backups. On restart, Redis prefers the AOF over the RDB because the AOF is more up-to-date. This combination gives you the best of both modes:

```
Why not just use one mode:

  RDB only:
  ✓ Fast restart (binary load, no command replay)
  ✓ Compact file (compressed binary, good for backups)
  ✗ Data loss window = time between saves (60s to hours)
  ✗ Fork cost on every save interval
  Use: caches, development, or when loss is acceptable

  AOF only:
  ✓ Lowest data loss (everysec = ≤1s loss)
  ✓ Human-readable/replayable log
  ✗ Slow restart for large datasets (replays every command ever issued)
    10GB dataset: millions of commands → minutes of startup time
  ✗ Large files (every SET of the same key is a separate entry until rewrite)
  ✗ BGREWRITEAOF is still expensive (fork, CoW overhead)
  Use: when durability is paramount and slow restarts are acceptable

  Hybrid (RDB + AOF):
  ✓ Fast restart: load RDB first (binary), then replay only recent AOF delta
  ✓ Good durability: AOF with everysec = ≤1s loss
  ✓ Compact backups: RDB snapshots can be used for point-in-time recovery
  ✓ Smaller AOF: BGREWRITEAOF uses RDB format as base (see Q9)
  Use: most production Redis deployments

Restart behavior with both enabled:

  Redis startup logic:
  1. Check if AOF is enabled (appendonly yes)
  2. If yes: load AOF (and ignore RDB — AOF is more authoritative)
     Load base RDB snapshot (if hybrid format)
     Replay incremental AOF commands
  3. If no (RDB only): load RDB file

  Critical: if both exist, AOF takes precedence
  Accidental AOF disabling: if you disable AOF and restart with only RDB:
    Redis loads the (older) RDB snapshot → loses data written since last RDB save
    Always be deliberate about which mode is active

Configuration for hybrid:
  # redis.conf:
  # RDB:
  save 3600 1
  save 300 100
  save 60 10000
  dbfilename dump.rdb

  # AOF:
  appendonly yes
  appendfilename "appendonly.aof"
  appendfsync everysec
  no-appendfsync-on-rewrite yes
  auto-aof-rewrite-percentage 100
  auto-aof-rewrite-min-size 64mb

  # Hybrid AOF format (RDB preamble — see Q9):
  aof-use-rdb-preamble yes

  dir /var/lib/redis

Recovery scenarios:

  Scenario 1: Redis crashes (signal kill, OOM)
    AOF is intact up to last fsync (everysec → ≤1s loss)
    RDB may be hours old (last BGSAVE)
    Restart: Redis loads AOF (more recent) → recovers all but ≤1s of data

  Scenario 2: Disk corruption corrupts AOF
    Fallback: use the most recent RDB snapshot (from automated backups)
    Run redis-check-aof --fix on the corrupted AOF
    Or: restore from RDB + manually replay any critical operations

  Scenario 3: Full server loss (no disk)
    Restore from off-site RDB backup
    Re-apply any commands from application logs since the backup
    (Application should be designed to handle this via idempotent operations)
```

**Q9. What is the RDB-preamble AOF format (aof-use-rdb-preamble) and how does it accelerate restarts?**
A: The RDB-preamble format (introduced in Redis 4.0, enabled by default since 7.0) stores an RDB snapshot at the beginning of the AOF file during rewrite, followed by AOF commands for the delta. This eliminates the slow command-by-command replay for most of the data and dramatically speeds up restart for large datasets:

```
Standard AOF file structure (aof-use-rdb-preamble no):
  ┌──────────────────────────────────────────────────────────┐
  │ SET loan:L1 "..." EX 3600                                │
  │ SET loan:L2 "..." EX 3600                                │
  │ HSET user:U1 name "Ravi" email "ravi@example.com"       │
  │ SET loan:L1 "updated..."                                  │
  │ ... (millions of commands for 10GB dataset)              │
  │ SET counter:daily 47823                                  │
  │ [... recent commands ...]                                │
  └──────────────────────────────────────────────────────────┘
  Restart: Redis replays every single command in order
  Restart time for 10GB: 5–20 minutes (millions of SET/HSET/etc. commands)

RDB-preamble AOF file structure (aof-use-rdb-preamble yes):
  ┌──────────────────────────────────────────────────────────┐
  │ REDIS0011...  ← RDB binary snapshot (10GB → 3GB compressed) │
  │ [RDB data for all keys at rewrite time]                  │
  ├──────────────────────────────────────────────────────────┤
  │ SET loan:L3 "..."         ← AOF commands SINCE rewrite   │
  │ INCR counter:hourly       ← only the incremental delta   │
  │ [... recent commands ...]                                │
  └──────────────────────────────────────────────────────────┘
  Restart:
    Load RDB preamble (binary, fast: ~1–5 seconds for 10GB)
    Replay only AOF delta (small: seconds of recent commands)
  Restart time: 5–30 seconds for 10GB (vs 5–20 minutes without preamble)

How the RDB preamble is created:
  When BGREWRITEAOF runs:
    Child forks
    Child writes current in-memory state as RDB binary to new AOF file
    Parent buffers new commands to rewrite buffer (in memory)
    Child finishes RDB write → begins writing rewrite buffer as AOF commands
    Rename temp file → new AOF file
    Future writes: appended as standard AOF commands (RESP format)
    Result: base is RDB + incremental is AOF

  When is the RDB preamble updated?
    Only on BGREWRITEAOF (automatic or manual)
    Between rewrites: delta grows as AOF commands
    At next rewrite: new RDB preamble captures all current state

Checking AOF format:
  redis-cli DEBUG SLEEP 0  # wake up Redis if paused
  redis-cli DEBUG SET-ACTIVE-EXPIRE 0

  # Inspect the AOF file manually:
  head -c 5 /var/lib/redis/appendonly.aof
  # "REDIS" → RDB preamble format (starts with RDB magic)
  # "*2\r\n" → Pure AOF format (starts with RESP array)

  # redis-check-aof works on both formats:
  redis-check-aof /var/lib/redis/appendonly.aof
  # AOF analyzed: size=xxx, ok_up_to=xxx, diff=xxx

Performance comparison (10GB dataset):
  Mode               │ Write throughput │ Restart time │ Data loss risk
  ───────────────────┼──────────────────┼──────────────┼─────────────────
  No persistence     │ 100% (baseline)  │ 0s (empty)   │ 100% on crash
  RDB only (1min)    │ ~99%             │ 5–20s        │ ≤ 60s of writes
  AOF (everysec)     │ ~95%             │ 5–20 min     │ ≤ 1s of writes
  AOF (always)       │ ~10–30%          │ 5–20 min     │ ≤ 1 command
  Hybrid (recommended)│ ~95%            │ 10–40s       │ ≤ 1s of writes
```

## Section 5: Redis Sentinel and Persistence

**Q10. How does persistence interact with Redis Sentinel for high availability?**
A: Redis Sentinel provides automated failover for Redis. Persistence mode affects how quickly a replica can replace a failed primary and what data loss occurs during failover. Understanding this interaction is essential for production HA design:

```
Redis Sentinel + Persistence interaction:

  Without persistence (cache only):
    Primary crashes → Sentinel promotes a replica
    New primary has all data that was replicated before crash
    Replication is asynchronous: data written to primary but not yet replicated = LOST
    After promotion: new primary is missing recent writes
    Typical loss: last N milliseconds of writes (replication lag)

  With AOF (everysec) on primary AND replicas:
    Primary crashes → Sentinel promotes a replica
    Replica's AOF has data up to ≤1 second before the crash
    Note: replica AOF is separate from primary AOF
          Redis replication sends commands to replica → replica writes to its own AOF
    Data loss: at most 1s of AOF lag + replication lag between primary and replica

  Replica AOF configuration (important):
    Each replica should have appendonly yes in its config
    This ensures replica survives its OWN crash independently
    Without replica AOF: replica crashes → restarts empty → full resync from primary

  min-replicas-to-write and min-replicas-max-lag:
    redis.conf on primary:
    min-replicas-to-write 1         # primary refuses writes if fewer than 1 replica is up-to-date
    min-replicas-max-lag 10         # "up-to-date" = replica lag ≤ 10 seconds

    Effect: if all replicas fall behind by > 10s → primary stops accepting writes
    → Prevents primary from accepting writes that replicas will never see
    → Trades availability for consistency (primary goes read-only)
    → Data loss in crash scenario is bounded by the lag threshold (10s)

  The failover data loss window:
    With min-replicas-max-lag 10:
    Worst case loss on crash: 10s of writes (replica was 10s behind)
    With everysec AOF: ≤1s lost on new primary after promotion
    Without min-replicas-max-lag: loss can be unbounded (replica could be minutes behind)

  Persistence for fast replica resync:
    When a replica reconnects after a gap:
    If gap ≤ repl-backlog-size: partial resync (only missed commands sent)
    If gap > repl-backlog-size: full resync needed
      Full resync: primary does BGSAVE → sends RDB to replica → replica loads RDB
      With AOF-only (no RDB): full resync is slower (primary must create temporary RDB)
      With hybrid: primary already has RDB ready → faster full resync

  # Production Sentinel + persistence configuration:
  # Primary redis.conf:
  appendonly yes
  appendfsync everysec
  no-appendfsync-on-rewrite yes
  save 3600 1
  save 300 100
  save 60 10000
  min-replicas-to-write 1
  min-replicas-max-lag 10
  repl-backlog-size 256mb   # large backlog reduces full resync frequency

  # Replica redis.conf:
  appendonly yes             # replica has its own AOF
  appendfsync everysec
  replica-read-only yes
  # Note: save "" is sometimes used on replicas (no RDB on replica, rely on primary's RDB)
  # But best practice: enable both on all members for independent recovery
```

## Section 6: Operational Practices

**Q11. How do you take backups of Redis and what is the correct procedure to avoid serving corrupt data?**

```bash
# ── RDB backup ────────────────────────────────────────────────────────────────

# Trigger a background save and wait for completion:
redis-cli BGSAVE
# Returns: "Background saving started"
# Wait for completion:
redis-cli --no-auth-warning -a $REDIS_PASSWORD \
    DEBUG SLEEP 0  # wake up if blocked
watch -n 1 "redis-cli INFO persistence | grep rdb_bgsave_in_progress"
# When rdb_bgsave_in_progress:0 → save is complete

# Check save was successful:
redis-cli INFO persistence | grep rdb_last_bgsave_status
# rdb_last_bgsave_status:ok  ← success
# rdb_last_bgsave_status:err ← failure (check logs)

# Copy the RDB file (after save completes):
cp /var/lib/redis/dump.rdb /backup/redis/dump-$(date +%Y%m%d-%H%M%S).rdb
# Never copy the RDB while a save is in progress — file may be partially written
# The BGSAVE writes to a temp file → atomic rename on completion → copy after rename

# Automated backup script:
#!/bin/bash
BACKUP_DIR="/backup/redis"
REDIS_DATA="/var/lib/redis/dump.rdb"

# Trigger save:
redis-cli BGSAVE > /dev/null

# Wait for save to complete (poll every second):
while [ "$(redis-cli INFO persistence | grep rdb_bgsave_in_progress | cut -d: -f2 | tr -d '\r')" = "1" ]; do
    sleep 1
done

# Verify success:
STATUS=$(redis-cli INFO persistence | grep rdb_last_bgsave_status | cut -d: -f2 | tr -d '\r')
if [ "$STATUS" != "ok" ]; then
    echo "ERROR: RDB save failed"
    exit 1
fi

# Copy with timestamp:
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
cp "$REDIS_DATA" "$BACKUP_DIR/dump-$TIMESTAMP.rdb"
echo "Backup completed: dump-$TIMESTAMP.rdb"

# ── AOF backup ────────────────────────────────────────────────────────────────
# Copying AOF while Redis is running is safe (append-only, no in-place modifications)
# But: copy may capture a mid-write state for the current command

# Safer: pause AOF writes during copy (brief, milliseconds):
redis-cli BGREWRITEAOF  # wait for rewrite to complete first
# Then copy:
cp /var/lib/redis/appendonly.aof /backup/redis/aof-$(date +%Y%m%d-%H%M%S).aof

# ── Restoring from backup ─────────────────────────────────────────────────────
# Stop Redis:
systemctl stop redis

# Replace data file(s):
cp /backup/redis/dump-20240115-103000.rdb /var/lib/redis/dump.rdb
# Ensure correct permissions:
chown redis:redis /var/lib/redis/dump.rdb

# If restoring RDB but AOF is enabled:
# The AOF will take precedence on startup!
# Option A: temporarily disable AOF in config, start, re-enable
# Option B: delete the AOF file (Redis will load RDB, then create fresh AOF):
rm /var/lib/redis/appendonly.aof

# Start Redis:
systemctl start redis

# Verify data loaded correctly:
redis-cli DBSIZE         # number of keys
redis-cli INFO keyspace  # keys per database
redis-cli DEBUG SLEEP 0  # confirm Redis is responsive

# ── Verifying RDB integrity ───────────────────────────────────────────────────
redis-check-rdb /backup/redis/dump-20240115-103000.rdb
# Scans the RDB file for corruption
# Output: ok (file is valid) or error description

# ── Off-site backup strategy ─────────────────────────────────────────────────
# Automate to S3/GCS:
aws s3 cp /backup/redis/dump-$(date +%Y%m%d-%H%M%S).rdb \
    s3://my-bucket/redis-backups/ \
    --storage-class STANDARD_IA  # infrequent access for cost savings

# Retention: keep daily RDBs for 7 days, weekly for 4 weeks, monthly for 12 months
# Test restores monthly: verify backup actually contains the expected data
```

**Q12. What is the correct persistence configuration for different Redis use cases?**

```yaml
# ── Use case 1: Pure cache (no persistence) ─────────────────────────────────
# Redis as L2 cache — source of truth is the primary database
# Data can be rebuilt from DB on cache miss after Redis restart

# redis.conf:
save ""                   # disable all RDB saves
appendonly no             # disable AOF
maxmemory 8gb             # set memory limit
maxmemory-policy allkeys-lru  # evict LRU keys when memory full

# Startup: empty cache (cold start — DB will warm it up)
# Data loss: 100% on restart (intentional — cache is rebuilt automatically)

# ── Use case 2: Session store (moderate durability) ──────────────────────────
# User sessions — loss of sessions = users must re-authenticate
# Acceptable: lose up to 1 second of sessions on crash

# redis.conf:
appendonly yes
appendfsync everysec
no-appendfsync-on-rewrite yes
save 900 1               # RDB backup for fast restart
save 300 10
aof-use-rdb-preamble yes
maxmemory-policy volatile-lru  # evict keys with TTLs first (sessions have TTL)

# Data loss: ≤ 1 second of sessions (users may need to re-login)
# Restart: fast (hybrid format)

# ── Use case 3: Job queue (high durability) ──────────────────────────────────
# Redis as a Sidekiq / BullMQ / Celery queue backend
# Job loss = missed processing = business impact

# redis.conf:
appendonly yes
appendfsync everysec        # or "always" for critical jobs
no-appendfsync-on-rewrite yes
save 60 10000              # frequent RDB for fast resync
save 300 100
save 3600 1
aof-use-rdb-preamble yes
min-replicas-to-write 1    # require at least 1 replica before accepting writes
min-replicas-max-lag 10

# On replica:
appendonly yes
appendfsync everysec

# Data loss: ≤ 1 second + replication lag (bounded by min-replicas-max-lag)

# ── Use case 4: Leaderboard / analytics counters ─────────────────────────────
# Sorted sets for leaderboards — slight inaccuracy after crash is acceptable
# Counters can be recomputed from source events if needed

# redis.conf:
appendonly yes
appendfsync everysec
save 300 100
save 60 10000
aof-use-rdb-preamble yes
# No min-replicas-to-write: availability > consistency for leaderboards

# ── Use case 5: Rate limiting (no persistence needed) ────────────────────────
# Redis rate limit counters (e.g. INCR + EXPIRE for sliding window)
# After crash: rate limits reset — acceptable (brief window of excess requests)

# redis.conf:
save ""
appendonly no
# Rate limits are short-lived (TTL = 1 minute typically)
# Even with persistence, the 1s AOF loss means counters may be off by 1s

# ── Use case 6: Financial / critical data ─────────────────────────────────────
# Balances, transaction deduplication keys, idempotency tokens
# Zero tolerance for data loss

# redis.conf:
appendonly yes
appendfsync always          # every command fsynced — accept throughput hit
no-appendfsync-on-rewrite no # don't skip fsync during rewrite
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 128mb
save 60 1000               # frequent RDB
aof-use-rdb-preamble yes
min-replicas-to-write 1
min-replicas-max-lag 5     # tight lag bound

# On all replicas:
appendonly yes
appendfsync always

# Data loss: at most 1 command (the one being fsynced at crash time)
# Throughput: reduced (fsync per command) — acceptable for financial use cases
# where correctness > throughput
```

## Section 7: Scenario-Based Questions

**Q13. "Your Redis instance crashed and on restart, it comes up with data that's 45 minutes old. You have both RDB and AOF enabled. What happened and how do you prevent this in the future?"**

```bash
# Diagnosis: Redis loaded the RDB instead of the AOF

# Why this happens:
# 1. AOF file corruption:
#    If AOF file is corrupted → Redis falls back to RDB (if aof-load-truncated no)
#    Or → Redis refuses to start (if aof-load-truncated yes but file is unreadable)
#
# 2. AOF was accidentally disabled:
#    Config change (appendonly no) → Redis loaded RDB on restart
#    Check: redis-cli CONFIG GET appendonly
#
# 3. AOF file was deleted or not found:
#    Check: ls -la /var/lib/redis/
#
# 4. Wrong data directory:
#    Redis is reading from a different 'dir' than where AOF was written
#    Check: redis-cli CONFIG GET dir

# Investigation steps:
# 1. Check current persistence config:
redis-cli INFO persistence
# aof_enabled: 0  ← AOF is DISABLED → that's why RDB was loaded

redis-cli CONFIG GET appendonly
# appendonly: no  ← confirmed

# 2. Check what config file Redis is using:
redis-cli INFO server | grep config_file
# config_file:/etc/redis/redis.conf

# 3. Look at the config file for appendonly setting:
grep -n "appendonly" /etc/redis/redis.conf
# appendonly no  ← was disabled, possibly by accident or a config deployment

# 4. Check AOF file status:
ls -la /var/lib/redis/
# appendonly.aof: present, modified 45 minutes ago (last write before crash)
# dump.rdb: present, modified 45 minutes ago (last RDB save before crash)

# The 45-minute old data is from the RDB because:
# → AOF was disabled (or the file was missing/corrupt)
# → Redis fell back to the last RDB snapshot (45 minutes old)

# Recovery steps:
# 1. Stop Redis:
systemctl stop redis

# 2. Enable AOF in config:
sed -i 's/^appendonly no/appendonly yes/' /etc/redis/redis.conf

# 3. Verify AOF file is present and intact:
redis-check-aof /var/lib/redis/appendonly.aof
# If ok: proceed
# If corrupted: redis-check-aof --fix /var/lib/redis/appendonly.aof

# 4. Start Redis (will load AOF, which is more recent than the RDB):
systemctl start redis

# 5. Verify data is back to the correct state:
redis-cli DBSIZE
redis-cli INFO persistence | grep aof_enabled  # should be: 1

# Prevention:
# 1. Use configuration management (Ansible, Terraform) to ensure appendonly yes
#    is always set → config drift detection

# 2. Monitor aof_enabled in alerting:
redis-cli INFO persistence | grep aof_enabled
# Alert if: aof_enabled=0 in production

# 3. Add startup check in Redis init script:
# Before starting Redis: verify appendonly yes is in the config
grep -q "appendonly yes" /etc/redis/redis.conf || \
    { echo "ERROR: AOF not enabled in Redis config"; exit 1; }

# 4. Test recovery procedures quarterly:
# Spin up a Redis instance from the latest RDB backup
# Verify the data matches expectations
# Practice the "corrupt AOF recovery" procedure in a staging environment
```

**Q14. "You need Redis to be both fast AND durable for a loan disbursement deduplication key store. Keys are checked before disbursement (SET if not exists), and duplicates must never be processed. Design the persistence configuration."**

```bash
# Requirements:
# - Deduplication: SET loan:disbursement:{loan_id} "1" NX EX 86400
# - If this key exists: loan was already disbursed → reject
# - After Redis crash: keys must still exist (loss = duplicate disbursement = financial disaster)
# - Performance: must handle 1000 disbursements/second peak

# Design decisions:

# 1. Persistence mode: AOF with appendfsync always
#    Rationale: each SET NX must be fsynced before returning success to application
#    If Redis crashes after returning OK but before fsync: key is gone → duplicate risk
#    appendfsync always: every command fsynced → key is durable on OK response

# 2. High availability: Redis Sentinel or Redis Cluster
#    Primary + 2 replicas for automatic failover
#    min-replicas-to-write 1 + min-replicas-max-lag 5
#    Ensures write propagates to at least one replica before acceptance

# 3. Throughput calculation:
#    appendfsync always: limited by SSD fsync speed
#    NVMe SSD: ~100,000–200,000 IOPS → 100,000–200,000 fsyncs/second
#    Actual Redis with always: ~10,000–50,000 write ops/second (overhead reduces it)
#    1000 disbursements/second: well within capacity ✓

# redis.conf for primary:
appendonly yes
appendfsync always              # every SET NX is fsynced immediately
no-appendfsync-on-rewrite no   # don't skip fsync even during rewrite (strict)
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-use-rdb-preamble yes        # fast restart with hybrid format

save 300 100                    # RDB backup (for point-in-time recovery)
save 3600 1

min-replicas-to-write 1
min-replicas-max-lag 5

# Redis Sentinel config (sentinel.conf):
sentinel monitor dedup-redis primary-host 6379 2
sentinel down-after-milliseconds dedup-redis 5000
sentinel failover-timeout dedup-redis 60000
sentinel parallel-syncs dedup-redis 1

# Application code (Node.js):
import { createClient } from 'redis';

const redis = createClient({
    socket: { host: 'sentinel-host', port: 26379 },
    // Use Sentinel for automatic failover:
    sentinels: [
        { host: 'sentinel1', port: 26379 },
        { host: 'sentinel2', port: 26379 },
        { host: 'sentinel3', port: 26379 }
    ],
    name: 'dedup-redis'
});

async function disburseLoan(loanId: string, amount: number): Promise<void> {
    const deduplicationKey = `loan:disbursement:${loanId}`;
    const TTL_SECONDS = 86400;  // 24 hours

    // Atomic check-and-set (NX = only if not exists):
    const result = await redis.set(
        deduplicationKey,
        JSON.stringify({ amount, initiated_at: new Date().toISOString() }),
        { NX: true, EX: TTL_SECONDS }

    // Proceed with actual disbursement:
    try {

        await redis.del(deduplicationKey);
        throw bankingError;
    }
}
```

**Tip for interviews:** Five things separate strong candidates on Redis persistence: (1) explaining **copy-on-write precisely** (Q2) — fork() is near-instant (copies the page table, not the data), the child sees a frozen snapshot of memory at fork time, and CoW pages are only copied when the parent modifies them, which means a high write rate during a save causes memory usage to spike toward 2× the dataset size; this is why `maxmemory` should be set to 50-60% of physical RAM; (2) being precise about **the data loss window for each mode** — RDB loss equals the time since the last successful save (configurable but at best 60 seconds with `save 60 10000`); AOF everysec loses at most 1 second; AOF always loses at most 1 command; and knowing that with hybrid, Redis prefers the AOF on startup because it is more recent than the RDB; (3) explaining the **fork latency spike** as distinct from the I/O blocking concern — the I/O is handled by the child (no event loop block), but fork() itself blocks Redis for tens to hundreds of milliseconds proportional to dataset size, which shows up as a P99 latency spike, and Transparent Huge Pages dramatically worsen it; (4) knowing that **`aof-use-rdb-preamble yes` solves the AOF slow restart problem** (Q9) — without it, a 10GB dataset may require replaying millions of commands taking 5-20 minutes; with it, the RDB base is loaded in seconds and only the incremental AOF delta is replayed; and (5) being able to justify **`appendfsync always` specifically for deduplication and idempotency keys** (Q14) — if Redis returns OK for a SET NX but crashes before the fsync, the key is gone, the next request sees no key, and a duplicate operation proceeds; `appendfsync everysec` is insufficient for this case because the 1-second window is exactly when a well-timed crash causes the failure.
