## Section 1: Fundamentals

**Q1. What is a database index, why does it exist, and what does it cost?**
A: An index is a separate data structure maintained alongside a table that allows PostgreSQL to locate rows matching a condition without scanning every row in the table. It trades write overhead and storage for faster reads:

```
Without an index — sequential scan (Seq Scan):

  SELECT * FROM orders WHERE user_id = 'u-42';

  PostgreSQL reads every page of the orders table in sequence:
  Page 1: [ row1(u-1), row2(u-7), row3(u-42) ← match, row4(u-2) ]
  Page 2: [ row5(u-9), row6(u-42) ← match,  row7(u-3), row8(u-1) ]
  ...
  Page N: [ ... ]

  Cost: O(N) — reads every row regardless of matches
  For 10 million rows: ~10M row evaluations
  For 0.001% selectivity (100 matches): still reads all 10M rows

With a B-tree index on user_id:

  Index structure (sorted by user_id):
  ... → [u-41: page 892] → [u-42: pages 3, 17, 891] → [u-43: page 7] → ...

  PostgreSQL traverses the B-tree in O(log N) steps:
  Root → branch → leaf → heap page
  For 10M rows: ~23 comparisons to find u-42's entries
  Then fetches only the matching pages from the heap
```

```
Index costs — what you pay:

  Storage:
    B-tree on a TEXT column: ~30-50% of the column's data size
    A 10GB table might have 3-5GB of indexes
    More indexes = larger backups, more RAM needed for index pages

  Write overhead (INSERT / UPDATE / DELETE):
    Every data change must also update all affected indexes
    INSERT into a table with 5 indexes: 6 writes (1 heap + 5 index updates)
    Bulk loading: DROP indexes, load data, rebuild — much faster

  Vacuum overhead:
    Dead index entries (from UPDATEs/DELETEs) must be cleaned
    Index bloat: pages with many dead entries waste space and slow scans
    autovacuum handles this, but large tables may need tuning

  Query planning overhead:
    More indexes = more options for the planner to evaluate
    Usually negligible, but 20+ indexes on one table can slow planning

  The break-even point:
    Index worth using when: (rows scanned with index) < (rows without) × random_page_cost / seq_page_cost
    Defaults: random_page_cost=4, seq_page_cost=1
    Rule: index beneficial when selectivity < ~25% (fetches <25% of table)
    Below 5% selectivity: index almost always faster than seq scan
    Above 25%: seq scan may be faster (sequential I/O vs random I/O)
```

**Q2. How does PostgreSQL's query planner decide whether to use an index?**
A: The planner is a cost-based optimizer. It estimates the cost of each possible execution plan — including seq scan, index scan, index-only scan, and bitmap scan — and chooses the cheapest:

```sql
-- EXPLAIN shows the planner's chosen plan and cost estimates:
EXPLAIN SELECT * FROM orders WHERE user_id = 'u-42';

-- Output:
-- Index Scan using orders_user_id_idx on orders  (cost=0.43..8.45 rows=3 width=120)
--   Index Cond: (user_id = 'u-42'::uuid)
--
-- cost=0.43..8.45: startup_cost..total_cost (in arbitrary planner units)
-- rows=3: estimated matching rows (from statistics)
-- width=120: average row width in bytes

-- EXPLAIN ANALYZE — actually runs the query, shows real timings:
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 'u-42';
-- Buffers: shared hit=4 read=2  ← cache hits vs disk reads
-- Actual time=0.023..0.031 ms  ← real execution time
-- Actual rows=3               ← real rows returned
```

```sql
-- The four index access methods:

-- 1. Index Scan — fetch heap rows one at a time via index:
--    Fast for low selectivity (<1% of rows)
--    Each index entry → random heap page read (expensive for many rows)

-- 2. Bitmap Index Scan + Bitmap Heap Scan — batch fetch:
--    Build a bitmap of matching heap pages, then fetch in page order
--    Better than index scan for moderate selectivity (1-15%)
--    Can combine multiple indexes with AND/OR (BitmapAnd, BitmapOr)

-- 3. Index Only Scan — no heap access needed:
--    All required columns are IN the index (INCLUDE or part of key)
--    Fastest possible index access — avoids heap reads entirely
--    Requires visibility map to be current (autovacuum must run)

-- 4. Sequential Scan — reads heap pages in order:
--    Best for high selectivity (>25%) or very small tables
--    Sequential I/O is much faster than random I/O

-- Statistics that drive planner decisions:
SELECT
    attname,
    n_distinct,         -- Estimated distinct values (-1 = all unique)
    correlation,        -- Physical order correlation with logical order
    most_common_vals,   -- Most frequent values
    most_common_freqs   -- Frequency of most common values
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

-- Update statistics manually (normally autovacuum does this):
ANALYZE orders;
-- Or with higher sampling for better estimates on large tables:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;  -- default: 100
ANALYZE orders;
```

```sql
-- Why the planner might IGNORE an index (and what to do):

-- 1. Low selectivity — index not worth it:
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
-- Seq Scan: if 40% of orders are PENDING, seq scan is faster
-- Fix: nothing — planner is correct. Consider partial index if needed.

-- 2. Stale statistics — planner has wrong row count estimate:
-- If ANALYZE hasn't run recently, estimates may be wildly off
-- Fix: ANALYZE the table, or increase default_statistics_target

-- 3. Table too small — seq scan is always faster for tiny tables:
-- A table with 50 rows fits in 1-2 pages — index adds overhead
-- Fix: nothing — correct behaviour

-- 4. random_page_cost too high relative to actual hardware:
-- Default: random_page_cost=4 assumes spinning disk
-- On SSD: set random_page_cost=1.1 to make index scans more attractive
ALTER SYSTEM SET random_page_cost = 1.1;  -- For SSD storage
SELECT pg_reload_conf();

-- 5. Force index use for testing (not for production):
SET enable_seqscan = off;   -- Forces planner to use indexes even when suboptimal
-- Never use in production — only for diagnosing planner decisions
```

## Section 2: B-tree Index

**Q3. How does a B-tree index work internally, and what operations does it support?**
A: B-tree (Balanced Tree) is PostgreSQL's default index type. It stores index entries in a balanced tree of fixed-size pages, sorted by the indexed value. All leaf nodes are at the same depth, and sibling leaves are linked for range scans:

```
B-tree structure (for an index on orders.created_at):

                    [Root page]
                   /            \
        [Branch page]          [Branch page]
        2024-01-01              2024-07-01
       /           \           /           \
  [Leaf]       [Leaf]      [Leaf]       [Leaf]
  Jan 1-15    Jan 16-31   Jul 1-15    Jul 16-31
  ↓               ↓           ↓           ↓
  heap TIDs   heap TIDs   heap TIDs   heap TIDs

  Leaf pages are doubly linked: ←[Jan1-15]↔[Jan16-31]↔...→
  Range scan: find start leaf → follow links without revisiting tree

  Properties:
  - Depth: O(log N) — 1M rows → ~5 levels deep
  - Lookup: O(log N) comparisons
  - Range scan: O(log N) to find start + O(K) to scan K matching entries
  - Always balanced: no degradation over time (unlike a BST)
  - Fill factor: pages kept ~70% full to allow insertions without page splits
```

```sql
-- B-tree supports these operators:
-- =, <, >, <=, >=, BETWEEN, IN, IS NULL, IS NOT NULL
-- LIKE 'prefix%' (left-anchored only — NOT LIKE '%suffix')
-- Sorting (ORDER BY) — can satisfy sort without separate sort step
-- Uniqueness enforcement (UNIQUE constraint uses a B-tree internally)

-- Create B-tree indexes (default — no need to specify USING btree):
CREATE INDEX ON orders (created_at);
CREATE INDEX ON orders (user_id, status);          -- Composite
CREATE UNIQUE INDEX ON users (email);              -- Unique
CREATE INDEX ON orders (created_at DESC NULLS LAST); -- Specific sort order

-- B-tree with INCLUDE — index-only scan without adding to sort key:
CREATE INDEX ON orders (user_id) INCLUDE (total, status);
-- user_id is the lookup key; total and status are stored but not part of key
-- Index scan on user_id can return total and status without hitting heap

-- Partial index — only index rows matching a condition:
CREATE INDEX ON orders (created_at)
WHERE status = 'PENDING';
-- Index is smaller (only PENDING orders)
-- Index is only used when query includes WHERE status = 'PENDING'
CREATE INDEX ON orders (user_id)
WHERE deleted_at IS NULL;
-- Only index non-deleted rows — soft-delete pattern
```

```sql
-- Composite index column order matters:

-- Index: (user_id, status, created_at)
CREATE INDEX ON orders (user_id, status, created_at);

-- USES index (leading column present):
SELECT * FROM orders WHERE user_id = 'u-42';
SELECT * FROM orders WHERE user_id = 'u-42' AND status = 'PENDING';
SELECT * FROM orders WHERE user_id = 'u-42' AND status = 'PENDING' AND created_at > '2024-01-01';
SELECT * FROM orders WHERE user_id = 'u-42' AND created_at > '2024-01-01';
-- ↑ Uses index on user_id only, then filters on created_at (skips status)

-- Does NOT use index (leading column missing):
SELECT * FROM orders WHERE status = 'PENDING';          -- No user_id
SELECT * FROM orders WHERE created_at > '2024-01-01';  -- No user_id

-- Rule: the index is useful for any prefix of its columns
-- Column order: most selective first OR most commonly queried prefix first
-- For equality + range: put equality columns first, range column last
-- Bad:  (created_at, user_id) — range on created_at blocks use of user_id
-- Good: (user_id, created_at) — equality on user_id, then range on created_at

-- Index on expression:
CREATE INDEX ON users (lower(email));
-- Supports: WHERE lower(email) = 'user@example.com'
-- Does NOT support: WHERE email = 'User@Example.com' (different expression)
```

```sql
-- Diagnosing B-tree index health:

-- Index size and bloat:
SELECT
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan AS times_used,
    idx_tup_read AS tuples_read,
    idx_tup_fetch AS tuples_fetched
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

-- Find unused indexes (candidates for removal):
SELECT
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan AS scans_since_stats_reset
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND NOT indisprimary   -- Not the primary key
  AND NOT indisunique    -- Not a unique constraint
ORDER BY pg_relation_size(indexrelid) DESC;
-- Run AFTER a full traffic cycle (restart resets stats)
-- Unused indexes: DELETE or DROP them — they add write cost with no read benefit

-- Rebuild bloated index without locking:
REINDEX INDEX CONCURRENTLY orders_user_id_idx;
-- Builds a new index in background, swaps atomically — no table lock
```

## Section 3: Hash Index

**Q4. What is a Hash index, when does it outperform B-tree, and what are its limitations?**
A: A Hash index stores a hash of the indexed value and a pointer to the heap row. Lookup is O(1) for exact equality — faster than B-tree's O(log N) for that specific case. But it cannot support anything other than equality:

```
Hash index structure:

  Index entry: hash(value) → heap TID

  Lookup: WHERE id = 'abc-123'
    1. Compute hash('abc-123') → bucket 7842
    2. Scan bucket 7842 for matching entries → heap TID
    3. Fetch heap row

  O(1) lookup — no tree traversal needed
  For UUID primary keys: hash may beat B-tree for pure equality lookups

  B-tree lookup: O(log N) — typically 3-5 page reads for 1M+ rows
  Hash lookup:   O(1)     — typically 1-2 page reads regardless of table size

  The difference is small in practice for most workloads.
  Hash is primarily useful when:
    - Table is very large (millions of rows)
    - Workload is almost exclusively equality lookups
    - Range queries and sorting are never needed on this column
```

```sql
-- Create a hash index:
CREATE INDEX ON sessions USING HASH (session_token);

-- Hash index ONLY supports: =
-- The following use the hash index:
SELECT * FROM sessions WHERE session_token = 'abc123def456';

-- The following do NOT use the hash index:
SELECT * FROM sessions WHERE session_token > 'abc';   -- No range support
SELECT * FROM sessions WHERE session_token LIKE 'abc%'; -- No prefix support
SELECT * FROM sessions ORDER BY session_token;          -- No sort support

-- When hash index makes sense:
-- Token lookup tables (session tokens, API keys, cache keys)
-- The column is a long string (UUID, SHA-256 hash) where the hash
-- is much smaller than the key itself, saving index space

-- Hash index properties:
-- Cannot be used for UNIQUE constraints
-- Cannot enforce uniqueness (B-tree required for unique indexes)
-- Cannot be used for multicolumn indexes
-- WAL-logged (durable) since PostgreSQL 10 — prior versions: not crash-safe
-- Smaller than B-tree for long key values (stores hash, not the value)

-- In practice: B-tree on UUID is already fast enough for most workloads.
-- Hash indexes are a micro-optimisation — profile before switching.
```

## Section 4: GIN Index

**Q5. What is a GIN index and how does it handle composite values like JSONB, arrays, and full-text search?**
A: GIN (Generalized Inverted Index) is designed for columns whose values contain multiple "elements" — a JSONB document contains many keys, an array contains many items, a text document contains many words. A regular B-tree can only index the whole value; GIN creates an entry per element, pointing back to rows that contain it:

```
GIN index structure — inverted index:

  Traditional B-tree on a column:
    value → row pointer
    'PENDING' → [row5, row12, row891]

  GIN on a JSONB column (orders.metadata):
    element → row pointers
    'status'      → [row1, row2, row3, ...]   ← rows containing key "status"
    'express'     → [row2, row7, row91, ...]   ← rows containing value "express"
    'user_id'     → [row1, row3, row5, ...]
    'shipping'    → [row4, row8, row12, ...]

  GIN on a tsvector column (products.search_vector):
    lexeme → row pointers + positions
    'quick'   → {row1: [3,15], row4: [1]}   ← row1 has "quick" at positions 3 and 15
    'brown'   → {row1: [4], row7: [2]}
    'fox'     → {row1: [5], row3: [7,12]}

  Query: WHERE search_vector @@ to_tsquery('quick & fox')
    Intersect posting lists for 'quick' and 'fox' → rows containing both
```

```sql
-- GIN for JSONB:
CREATE TABLE products (
    id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name     TEXT NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'
);

-- GIN index on the entire JSONB column:
CREATE INDEX ON products USING GIN (metadata);

-- Supports jsonb operators:
-- @> (contains): does the jsonb contain this sub-document?
SELECT * FROM products
WHERE metadata @> '{"category": "electronics", "in_stock": true}';

-- ? (key exists):
SELECT * FROM products WHERE metadata ? 'discount_pct';

-- ?| (any key exists):
SELECT * FROM products WHERE metadata ?| ARRAY['discount_pct', 'promo_code'];

-- ?& (all keys exist):
SELECT * FROM products WHERE metadata ?& ARRAY['category', 'brand', 'sku'];

-- @? (jsonpath match):
SELECT * FROM products WHERE metadata @? '$.variants[*].color ? (@ == "red")';

-- Does NOT support with standard GIN:
-- metadata->>'price' > '100'    ← use jsonb_path_ops or expression index
-- metadata->'price' = '99.99'  ← equality on extracted value

-- jsonb_path_ops — faster GIN for @> queries, smaller index:
CREATE INDEX ON products USING GIN (metadata jsonb_path_ops);
-- Only supports @> and @? operators
-- Smaller and faster than default GIN for @> heavy workloads
-- Cannot use ? or ?| operators with jsonb_path_ops

-- Partial GIN — only index specific category:
CREATE INDEX ON products USING GIN (metadata)
WHERE metadata ? 'variants';  -- Only products with variants key
```

```sql
-- GIN for arrays:
CREATE TABLE posts (
    id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    body TEXT,
    tags TEXT[] NOT NULL DEFAULT '{}'
);

CREATE INDEX ON posts USING GIN (tags);

-- Supports array operators:
-- @> (contains all): tags contains ALL of these
SELECT * FROM posts WHERE tags @> ARRAY['postgresql', 'performance'];

-- <@ (contained by): tags is a subset of these
SELECT * FROM posts WHERE tags <@ ARRAY['sql', 'postgresql', 'database'];

-- && (overlap): tags shares at least one element
SELECT * FROM posts WHERE tags && ARRAY['postgresql', 'mysql'];

-- = (array equality): requires B-tree, NOT GIN
```

```sql
-- GIN for full-text search:
CREATE TABLE articles (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title          TEXT NOT NULL,
    body           TEXT NOT NULL,
    search_vector  TSVECTOR
                   GENERATED ALWAYS AS (
                       setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
                       setweight(to_tsvector('english', coalesce(body,  '')), 'B')
                   ) STORED
    -- title words weighted A (highest), body words weighted B
);

CREATE INDEX ON articles USING GIN (search_vector);

-- Full-text search queries:
-- to_tsquery: strict — requires valid tsquery syntax
SELECT id, title,
       ts_rank(search_vector, query) AS rank
FROM articles,
     to_tsquery('english', 'postgresql & (index | performance)') query
WHERE search_vector @@ query
ORDER BY rank DESC
LIMIT 10;

-- websearch_to_tsquery: accepts natural language (safer for user input):
SELECT id, title
FROM articles
WHERE search_vector @@ websearch_to_tsquery('english', 'postgresql index performance');
-- Handles: "postgresql index" (phrase), -noise (exclude), OR

-- plainto_tsquery: treats all words as AND:
SELECT * FROM articles
WHERE search_vector @@ plainto_tsquery('english', 'postgresql performance');
-- Equivalent to: 'postgresql' & 'performance'

-- Index on expression (if not using generated column):
CREATE INDEX ON articles USING GIN (
    to_tsvector('english', title || ' ' || body)
);
-- Query MUST use the same expression:
WHERE to_tsvector('english', title || ' ' || body) @@ query
-- If expression doesn't match: index not used
```

```sql
-- GIN performance characteristics:

-- Build time: SLOW — GIN indexes all elements, creating many entries
-- Update time: SLOW for individual updates — many index entries change
--   GIN uses a "pending list" to batch updates:
--   New entries go to a pending list first (fast write)
--   Periodic vacuum merges pending list into main index (slower but amortised)

-- gin_pending_list_limit (default: 4MB):
-- Controls how much pending list accumulates before auto-cleanup
-- Higher value: better write performance, slower reads when list is large
ALTER TABLE articles SET (autovacuum_vacuum_cost_delay = 2); -- Tune vacuum

-- fastupdate parameter:
CREATE INDEX ON articles USING GIN (search_vector) WITH (fastupdate = on);
-- on (default): batch writes via pending list — fast writes, occasional slow reads
-- off: immediately merge — slow writes, consistently fast reads
-- Use fastupdate=off for read-heavy, infrequently-updated data

-- GIN is generally much larger than B-tree:
-- A TEXT[] column with average 10 tags: GIN index ~10x column size
-- Plan for extra storage accordingly
```

**Q6. How do you implement full-text search with GIN — what is the difference between `tsvector`, `tsquery`, and ranking?**
A: Full-text search in PostgreSQL operates on `tsvector` (a processed, normalized document) and `tsquery` (a search query with boolean operators). The `@@` operator tests if a document matches a query:

```sql
-- tsvector: preprocessed searchable document
SELECT to_tsvector('english', 'The quick brown foxes jumped over lazy dogs');
-- 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2
-- Stopwords removed: 'the', 'over'
-- Stemmed: 'foxes'→'fox', 'jumped'→'jump', 'lazy'→'lazi'
-- Position numbers preserved for phrase search

-- tsquery: a boolean search expression
SELECT to_tsquery('english', 'quick & fox');        -- AND
SELECT to_tsquery('english', 'quick | fox');        -- OR
SELECT to_tsquery('english', '!quick');             -- NOT
SELECT to_tsquery('english', 'quick <-> fox');      -- FOLLOWED BY (phrase)
SELECT to_tsquery('english', 'quick <2> fox');      -- quick within 2 words of fox
SELECT to_tsquery('english', 'quic:*');             -- Prefix match (quic*)

-- Match test:
SELECT to_tsvector('english', 'The quick brown fox') @@
       to_tsquery('english', 'quick & fox');
-- Returns: true

-- Highlighting matching terms:
SELECT ts_headline(
    'english',
    'The quick brown fox jumped over the lazy dog',
    to_tsquery('english', 'quick & fox'),
    'StartSel=<b>, StopSel=</b>, MaxWords=20'
);
-- Returns: 'The <b>quick</b> brown <b>fox</b> jumped over the lazy dog'
```

```sql
-- Ranking results — how relevant is the match?

-- ts_rank: based on term frequency (TF):
SELECT
    id,
    title,
    ts_rank(search_vector, query) AS rank
FROM articles,
     to_tsquery('english', 'postgresql') query
WHERE search_vector @@ query
ORDER BY rank DESC;

-- ts_rank_cd: cover density — prefers matches close together:
SELECT ts_rank_cd(search_vector, query, 32) AS rank  -- 32 = normalize by doc length
FROM articles,
     websearch_to_tsquery('english', 'index performance') query
WHERE search_vector @@ query
ORDER BY rank DESC;

-- Normalization options (bitmask):
-- 0  (default): no normalization
-- 1:  divide by 1 + logarithm of document length
-- 2:  divide by document length
-- 4:  divide by mean harmonic distance between extents
-- 8:  divide by number of unique words
-- 16: divide by 1 + logarithm of number of unique words
-- 32: divide by rank (self-normalization)

-- Weight-aware ranking (A=1.0, B=0.4, C=0.2, D=0.1 defaults):
-- Matches in title (weight A) count more than body (weight B)
SELECT ts_rank(
    search_vector,
    query,
    0  -- normalization
) AS rank
FROM articles,
     to_tsquery('english', 'postgresql') query
WHERE search_vector @@ query
ORDER BY rank DESC;
-- setweight() during tsvector creation (Q5) feeds into this ranking
```

```sql
-- Production full-text search setup:

-- Multi-language support:
CREATE TABLE documents (
    id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    language TEXT NOT NULL DEFAULT 'english',
    content  TEXT NOT NULL,
    -- Store language with the document for correct stemming:
    search_vector TSVECTOR GENERATED ALWAYS AS (
        to_tsvector(language::regconfig, content)
    ) STORED
);

-- Trigger-based approach (alternative to generated column):
-- Use when tsvector combines multiple columns with different weights:
CREATE OR REPLACE FUNCTION update_search_vector()
RETURNS TRIGGER AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', coalesce(NEW.title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(NEW.subtitle, '')), 'B') ||
        setweight(to_tsvector('english', coalesce(NEW.body, '')), 'C') ||
        setweight(to_tsvector('english', coalesce(array_to_string(NEW.tags, ' '), '')), 'B');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trig_update_search_vector
BEFORE INSERT OR UPDATE ON articles
FOR EACH ROW EXECUTE FUNCTION update_search_vector();

-- Combining FTS with other filters:
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM articles,
     websearch_to_tsquery('english', 'postgresql performance') query
WHERE search_vector @@ query
  AND category = 'database'
  AND published_at > NOW() - INTERVAL '1 year'
ORDER BY rank DESC
LIMIT 20;
-- GIN handles the @@ operator; other filters applied after
-- For high-selectivity category/date filters, partial index may help
```

## Section 5: GiST Index

**Q7. What is a GiST index and what types of data does it handle that B-tree cannot?**
A: GiST (Generalized Search Tree) is a framework for building index types over arbitrary data. Where B-tree requires a strict total ordering (`<`, `=`, `>`), GiST only requires that you can define "does this index entry overlap with this search predicate?" — making it suitable for geometric shapes, ranges, network addresses, and custom types:

```
GiST — a tree where nodes can represent arbitrary predicates:

  B-tree node: "all values in this subtree are between X and Y"
  GiST node:  "all values in this subtree are CONSISTENT with predicate P"
               P can mean: overlaps, contains, is within distance N, etc.

  GiST supports pluggable operator classes:
    point_ops:     spatial containment, distance, overlap
    range_type_ops: range overlap, containment, adjacency
    tsvector_ops:  full-text search (alternative to GIN for tsvector)
    inet_ops:      IP network containment
    ltree_ops:     hierarchical label tree paths
```

```sql
-- GiST for geometric/spatial types:
CREATE TABLE venues (
    id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name     TEXT NOT NULL,
    location POINT NOT NULL,  -- (longitude, latitude)
    area     POLYGON
);

CREATE INDEX ON venues USING GIST (location);
CREATE INDEX ON venues USING GIST (area);

-- Nearest-neighbour search (KNN — K Nearest Neighbours):
SELECT name,
       location <-> POINT(-73.9857, 40.7484) AS distance_degrees
FROM venues
ORDER BY location <-> POINT(-73.9857, 40.7484)  -- Times Square
LIMIT 10;
-- GiST index makes ORDER BY distance + LIMIT efficient (index-ordered scan)
-- Without GiST: would compute distance for every row, then sort

-- Containment / overlap:
SELECT * FROM venues WHERE area @> POINT(-73.98, 40.75);  -- Point inside polygon
SELECT * FROM venues WHERE area && BOX('(-74,40),(-73,41)'); -- Polygon overlaps box

-- PostGIS (extension for real geographic queries):
-- CREATE INDEX ON venues USING GIST (geom);  -- PostGIS geometry column
-- SELECT * FROM venues
-- WHERE ST_DWithin(geom, ST_MakePoint(-73.99, 40.75)::geography, 1000);
-- ← Within 1000 meters, using geography type for accurate earth-surface distance
```

```sql
-- GiST for range types — schedule, time slot, version range:
CREATE TABLE subscriptions (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL,
    plan        TEXT NOT NULL,
    active_period DATERANGE NOT NULL,  -- [start_date, end_date)
    EXCLUDE USING GIST (user_id WITH =, active_period WITH &&)
    -- A user cannot have two overlapping subscription periods
    -- && = overlap operator; WITH = means same user_id
);

CREATE INDEX ON subscriptions USING GIST (active_period);

-- Range operators with GiST:
-- @>  contains: does the range contain this value/range?
SELECT * FROM subscriptions
WHERE active_period @> CURRENT_DATE;   -- Currently active subscriptions

-- &&  overlaps: does the range overlap?
SELECT * FROM subscriptions
WHERE active_period && DATERANGE('2024-01-01', '2024-12-31');

-- <<  strictly left of (range ends before X starts)
-- >>  strictly right of
-- -|- adjacent (ranges touch but don't overlap)
SELECT * FROM subscriptions
WHERE active_period -|- DATERANGE('2024-06-01', '2024-12-31');
-- Find subscriptions that ended just when this period started

-- Timestamp ranges for booking systems:
CREATE TABLE bookings (
    id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    room_id  UUID NOT NULL,
    period   TSTZRANGE NOT NULL,
    EXCLUDE USING GIST (room_id WITH =, period WITH &&)
    -- No double-booking: same room_id AND overlapping period is forbidden
);
```

```sql
-- GiST vs GIN for tsvector (full-text search):
-- Both can index tsvector, but GIN is almost always preferred for FTS:

CREATE INDEX ON articles USING GIST (search_vector);   -- Possible but slower searches
CREATE INDEX ON articles USING GIN  (search_vector);   -- Preferred for FTS

-- GiST tsvector:
--   Faster to build and update than GIN
--   More compact than GIN
--   Slower search queries (lossy — may return false positives, needs heap recheck)

-- GIN tsvector:
--   Slower to build, larger index
--   Faster search queries (exact — no false positives)
--   Better for read-heavy workloads

-- Use GiST for tsvector only when:
--   Write performance is more critical than query performance
--   The column is updated very frequently
--   Index size is a concern

-- GiST for IP addresses and network ranges:
CREATE TABLE access_rules (
    id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    network INET NOT NULL,
    action  TEXT NOT NULL
);
CREATE INDEX ON access_rules USING GIST (network inet_ops);

SELECT action FROM access_rules
WHERE network >>= '192.168.1.42';  -- Find the most specific network containing this IP
-- >>= : contains or equals (find all networks containing the given IP)
```

**Q8. How do you use GiST for the exclusion constraint pattern?**
A: GiST's ability to index arbitrary overlap predicates makes it uniquely suited for exclusion constraints — "no two rows can have overlapping values" — which no other index type supports:

```sql
-- Exclusion constraints — preventing overlap at the database level:

-- Room booking — no double booking:
CREATE TABLE room_bookings (
    id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    room_id   UUID NOT NULL,
    guest_id  UUID NOT NULL,
    period    TSTZRANGE NOT NULL,
    CONSTRAINT no_double_booking
        EXCLUDE USING GIST (
            room_id WITH =,      -- Same room
            period  WITH &&      -- Overlapping time
        )
    -- Reject: same room_id AND overlapping period
    -- Allow:  different room_id (= returns false) OR non-overlapping period (&& returns false)
);

-- Test:
INSERT INTO room_bookings (room_id, guest_id, period)
VALUES ('room-1', 'guest-a', '[2024-06-01, 2024-06-05)');  -- OK

INSERT INTO room_bookings (room_id, guest_id, period)
VALUES ('room-1', 'guest-b', '[2024-06-03, 2024-06-08)');
-- ERROR: conflicting key value violates exclusion constraint "no_double_booking"
-- DETAIL: Key (room_id, period)=(..., ["2024-06-03","2024-06-08")) conflicts with
--         existing key (room_id, period)=(..., ["2024-06-01","2024-06-05")).

INSERT INTO room_bookings (room_id, guest_id, period)
VALUES ('room-2', 'guest-b', '[2024-06-03, 2024-06-08)');  -- OK — different room

-- The EXCLUDE constraint creates the GiST index automatically.
-- The GiST index is used to check for conflicts during INSERT/UPDATE.

-- Multi-column exclusion — conference scheduling:
CREATE TABLE conference_slots (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    speaker_id   UUID NOT NULL,
    room_id      UUID NOT NULL,
    time_period  TSTZRANGE NOT NULL,
    CONSTRAINT no_speaker_overlap
        EXCLUDE USING GIST (speaker_id WITH =, time_period WITH &&),
    CONSTRAINT no_room_overlap
        EXCLUDE USING GIST (room_id WITH =, time_period WITH &&)
    -- Speaker can't be in two places at once
    -- Room can't host two talks at once
);

-- btree_gist extension — include non-geometric types in GiST exclusion:
-- By default, WITH = only works with geometric/range types in GiST.
-- The btree_gist extension adds support for scalar types (UUID, TEXT, INT):
CREATE EXTENSION btree_gist;

-- Now UUID can be used with WITH = in GiST exclusion constraints:
CREATE TABLE employee_shifts (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    employee_id  UUID NOT NULL,    -- Scalar — needs btree_gist
    shift_period TSTZRANGE NOT NULL,
    CONSTRAINT no_shift_overlap
        EXCLUDE USING GIST (employee_id WITH =, shift_period WITH &&)
);
-- Without btree_gist: ERROR: data type uuid has no default operator class for
--                            access method "gist"
```

## Section 6: BRIN Index

**Q9. What is a BRIN index and when does it massively outperform a B-tree?**
A: BRIN (Block Range INdex) stores the minimum and maximum value of an indexed column for each range of physical heap pages (a "block range," typically 128 pages). It is extraordinarily small and cheap to maintain, but only works when the data is physically correlated with the index column — meaning rows with similar values are stored near each other on disk:

```
BRIN structure — summary of block ranges:

  Table heap (each block range = 128 pages × 8KB = 1MB of data):

  Block range 0 (pages 0-127):
    rows inserted Jan 2024 → min: 2024-01-01, max: 2024-01-31

  Block range 1 (pages 128-255):
    rows inserted Feb 2024 → min: 2024-02-01, max: 2024-02-29

  Block range 2 (pages 256-383):
    rows inserted Mar 2024 → min: 2024-03-01, max: 2024-03-31

  BRIN index: just 3 entries (vs B-tree: millions of entries)

  Query: WHERE created_at BETWEEN '2024-02-10' AND '2024-02-20'
    Block range 0: max=Jan 31 < Feb 10 → SKIP (no possible matches)
    Block range 1: min=Feb 1, max=Feb 29 → SCAN (range overlaps)
    Block range 2: min=Mar 1 > Feb 20 → SKIP (no possible matches)
    Result: only block range 1 scanned — 1/3 of the table
```

```sql
-- BRIN index creation and usage:
CREATE INDEX ON events USING BRIN (occurred_at);
-- Default pages_per_range: 128 (tune based on data volume and query range)

CREATE INDEX ON events USING BRIN (occurred_at) WITH (pages_per_range = 32);
-- Smaller ranges: more precise exclusion, larger index (but still tiny vs B-tree)
-- Larger ranges: coarser exclusion, smaller index, fewer maintenance updates

-- BRIN size comparison:
-- Table: 100GB of time-series events, 500M rows
-- B-tree on created_at: ~15GB index
-- BRIN on created_at:   ~150KB index (100,000x smaller!)

-- BRIN works by eliminating block ranges that cannot contain matching rows:
SELECT * FROM events
WHERE occurred_at BETWEEN '2024-03-01' AND '2024-03-31';
-- BRIN: skip all block ranges where max < '2024-03-01' OR min > '2024-03-31'
-- Result: only March block ranges are scanned

-- BRIN supports: =, <, >, <=, >=, BETWEEN, IS NULL, IS NOT NULL
-- (same as B-tree for range queries — but only efficient if data is correlated)
```

```sql
-- When BRIN is appropriate — the correlation requirement:

-- Check physical correlation:
SELECT correlation
FROM pg_stats
WHERE tablename = 'events' AND attname = 'occurred_at';
-- correlation = 1.0:  perfectly correlated — BRIN is optimal
-- correlation = 0.0:  no correlation — BRIN provides zero benefit
-- correlation = 0.8+: good correlation — BRIN is effective

-- HIGH correlation (BRIN ideal):
--   append-only tables: log tables, event streams, audit trails
--   created_at / inserted_at on tables where rows are never updated
--   sensor readings inserted in chronological order
--   auto-increment IDs (SERIAL, BIGSERIAL, sequences)

-- LOW correlation (BRIN useless, use B-tree):
--   user_id on orders (orders spread across the table randomly)
--   status field (PENDING/SHIPPED mixed throughout)
--   email addresses (inserted in any order)

-- Partition + BRIN — the best of both worlds for time-series:
-- Partition table by month (PostgreSQL table partitioning)
-- BRIN index on each partition's created_at
-- Query: partition pruning eliminates months, BRIN eliminates blocks within month
CREATE TABLE events_2024_03 PARTITION OF events
FOR VALUES FROM ('2024-03-01') TO ('2024-04-01');
CREATE INDEX ON events_2024_03 USING BRIN (occurred_at);
```

```sql
-- BRIN maintenance:

-- BRIN index is NOT automatically updated when rows are inserted
-- (Unlike B-tree which updates immediately)
-- New rows are NOT in the BRIN index until explicitly summarized:

-- Auto-summarization (enabled by default since PostgreSQL 10):
-- As new rows are inserted, PostgreSQL auto-summarizes new block ranges
-- Controlled by: autovacuum_vacuum_scale_factor and autovacuum settings

-- Manual summarization:
SELECT brin_summarize_new_values('events_occurred_at_idx');
-- Summarizes any block ranges not yet in the index

SELECT brin_summarize_range('events_occurred_at_idx', 0, 127);
-- Summarize specific block range (for targeted maintenance)

-- Rebuild BRIN after a large bulk load:
SELECT brin_summarize_new_values('events_occurred_at_idx');
-- Or rebuild entirely:
REINDEX INDEX events_occurred_at_idx;

-- Check if BRIN is being used:
EXPLAIN SELECT * FROM events WHERE occurred_at > NOW() - INTERVAL '1 day';
-- Should show: Bitmap Heap Scan + Bitmap Index Scan using BRIN index
-- NOT showing index: data not correlated, or range too wide (entire table scanned anyway)
```

## Section 7: Choosing the Right Index

**Q10. How do you decide which index type to use — what is the decision framework?**
A: Index selection follows the data type and operator pattern of the queries you need to optimise. Start with the access pattern, match it to the operator class, then consider size and maintenance tradeoffs:

```
Index selection decision tree:

  What is the column type and query pattern?
  │
  ├── Scalar value (text, int, uuid, date, timestamp, enum)
  │   ├── Equality + range + sort + LIKE 'prefix%'  → B-TREE (default)
  │   ├── Equality only + very large table           → HASH (micro-optimisation)
  │   └── Append-only, high physical correlation     → BRIN (time-series / logs)
  │
  ├── Composite value (contains multiple elements)
  │   ├── JSONB / hstore                             → GIN (metadata queries)
  │   ├── Arrays (TEXT[], INT[], UUID[])             → GIN (array operators)
  │   └── tsvector (full-text search documents)      → GIN (FTS queries)
  │
  └── Non-scalar / spatial / overlap
      ├── Geometric types (POINT, POLYGON, CIRCLE)   → GiST (spatial queries)
      ├── Range types (DATERANGE, TSTZRANGE, INT4RANGE)→ GiST (range overlap)
      ├── Network addresses (INET, CIDR)             → GiST (network containment)
      ├── Nearest-neighbour / KNN queries            → GiST (ORDER BY distance)
      ├── Exclusion constraints (no overlap)         → GiST (+ btree_gist)
      └── Hierarchical labels (ltree)                → GiST or GIN
```

```sql
-- Side-by-side comparison for the same use case:

-- Use case: find articles about PostgreSQL performance

-- Option A: LIKE search on TEXT (no special index)
CREATE INDEX ON articles (title);  -- B-tree
SELECT * FROM articles WHERE title LIKE '%postgresql%';
-- B-tree CANNOT use the index for '%postgresql%' (leading wildcard)
-- Result: seq scan — slow on large tables

-- Option B: Full-text search (GIN)
CREATE INDEX ON articles USING GIN (search_vector);
SELECT * FROM articles WHERE search_vector @@ to_tsquery('postgresql');
-- GIN index → fast, language-aware, stemmed ('postgresql' finds 'PostgreSQL')

-- Option C: pg_trgm trigram index (GIN or GiST) — LIKE with leading wildcard
CREATE EXTENSION pg_trgm;
CREATE INDEX ON articles USING GIN (title gin_trgm_ops);
SELECT * FROM articles WHERE title ILIKE '%postgresql%';
-- GIN trigram index supports LIKE '%pattern%' and ILIKE
-- Different from FTS: no stemming, no ranking, just substring match

-- When to use trigram vs FTS:
-- pg_trgm: substring matching ('postgresql' finds 'my-postgresql-talk')
--          good for: autocomplete, typo-tolerant search, LIKE queries
-- FTS:     word-level matching with stemming and ranking
--          good for: document search, blog search, product search
```

```sql
-- Common index patterns in production:

-- 1. Soft delete — partial index skips deleted rows:
CREATE INDEX ON users (email) WHERE deleted_at IS NULL;
-- All queries include WHERE deleted_at IS NULL → small, fast index

-- 2. Covering index — avoid heap access for common queries:
CREATE INDEX ON orders (user_id) INCLUDE (status, total, created_at);
-- SELECT status, total FROM orders WHERE user_id = 'u-42'
-- → Index-Only Scan: returns data from index without touching heap

-- 3. Composite + partial — most specific first:
CREATE INDEX ON orders (status, created_at)
WHERE status IN ('PENDING', 'PROCESSING');
-- Only active statuses indexed — much smaller than full index

-- 4. Expression index for case-insensitive lookup:
CREATE INDEX ON users (lower(email));
-- SELECT * FROM users WHERE lower(email) = lower('User@Example.com');
-- ← Must use lower() in query to use this index

-- 5. Multi-index bitmap scan — combine multiple partial indexes:
-- PostgreSQL can combine multiple indexes with BitmapAnd/BitmapOr:
SELECT * FROM orders WHERE user_id = 'u-42' OR status = 'URGENT';
-- Can combine: index on user_id + index on status via BitmapOr

-- 6. BRIN + partitioning for time-series:
CREATE TABLE metrics (
    time    TIMESTAMPTZ NOT NULL,
    device  UUID NOT NULL,
    value   FLOAT8 NOT NULL
) PARTITION BY RANGE (time);
-- Monthly partitions + BRIN per partition → tiny indexes, fast range scans
```

## Section 8: Index Maintenance and Operations

**Q11. How do you build and manage indexes in production without downtime?**
A: Standard `CREATE INDEX` takes a full table lock that blocks writes. `CREATE INDEX CONCURRENTLY` builds the index in background without blocking, at the cost of taking longer and being more complex to manage:

```sql
-- Standard CREATE INDEX — blocks writes:
CREATE INDEX ON orders (created_at);
-- ACCESS SHARE lock on table — blocks INSERT, UPDATE, DELETE
-- Duration: proportional to table size (minutes to hours for large tables)
-- Acceptable for: development, initial schema setup, maintenance windows

-- CONCURRENTLY — no write locks:
CREATE INDEX CONCURRENTLY ON orders (created_at);
-- Two table scans: first to build index, second to catch concurrent changes
-- Takes 2-3x longer than standard CREATE INDEX
-- Does NOT block reads or writes during build
-- Cannot be run inside a transaction (requires its own implicit transaction)
-- If it fails: leaves an INVALID index — must drop and retry:

-- Check for invalid indexes:
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
  AND NOT EXISTS (
      SELECT 1 FROM pg_class c
      JOIN pg_index i ON i.indexrelid = c.oid
      WHERE c.relname = indexname
        AND i.indisvalid
  );
-- Drop and retry if invalid:
DROP INDEX CONCURRENTLY orders_created_at_idx;
CREATE INDEX CONCURRENTLY ON orders (created_at);
```

```sql
-- Zero-downtime index operations:

-- 1. Replace an index (e.g., adding a column to an existing index):
-- Old: (user_id) — new: (user_id, created_at)
CREATE INDEX CONCURRENTLY new_orders_idx ON orders (user_id, created_at);
-- Both indexes exist and are maintained during transition
DROP INDEX CONCURRENTLY old_orders_user_id_idx;
-- Zero downtime: queries use whichever index the planner prefers

-- 2. Rebuild a bloated index:
REINDEX INDEX CONCURRENTLY orders_created_at_idx;
-- New index built alongside old, swapped atomically
-- PostgreSQL 12+ for CONCURRENTLY option on REINDEX

-- 3. Change index fill factor (for tables with many updates):
CREATE INDEX orders_status_idx ON orders (status) WITH (fillfactor = 70);
-- 70% full on build — leaves 30% space for updates (avoids page splits)
-- Useful for hot indexes on frequently-updated columns

-- 4. Monitor index build progress:
SELECT
    phase,
    blocks_done,
    blocks_total,
    round(100.0 * blocks_done / nullif(blocks_total, 0), 1) AS pct_done,
    tuples_done,
    tuples_total
FROM pg_stat_progress_create_index
WHERE relid = 'orders'::regclass;
```

```sql
-- Index bloat — when indexes grow larger than necessary:

-- Bloat occurs because:
-- B-tree: deleted/updated entries marked dead, not immediately reclaimed
-- GIN: pending list accumulates, main tree has dead entries

-- Estimate index bloat:
SELECT
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    pg_size_pretty(
        pg_relation_size(indexrelid) - pg_relation_size(indexrelid) * 0.7
    ) AS estimated_bloat   -- Very rough estimate
FROM pg_stat_user_indexes
WHERE relname = 'orders';

-- For precise bloat: use pgstattuple extension:
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstatindex('orders_created_at_idx');
-- Returns: avg_leaf_density (should be >70%), leaf_fragmentation, etc.

-- Fix bloat:
REINDEX INDEX CONCURRENTLY orders_created_at_idx;
-- Or for the whole table:
REINDEX TABLE CONCURRENTLY orders;

-- Autovacuum settings for high-traffic indexes:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- Vacuum when 1% of rows are dead (default: 20%)
    autovacuum_analyze_scale_factor = 0.005 -- Analyze when 0.5% of rows change
);
-- Frequent autovacuum → less bloat accumulation
```

## Section 9: Scenario-Based Questions

**Q12. "A query that filters on a JSONB column is doing a sequential scan despite having a GIN index. Walk through your diagnosis."**
A: GIN indexes on JSONB only support specific operators. Using the wrong operator, or querying on an extracted value rather than using a containment operator, silently bypasses the index:

```sql
-- The table and index:
CREATE TABLE products (
    id       UUID PRIMARY KEY,
    metadata JSONB
);
CREATE INDEX ON products USING GIN (metadata);  -- Standard GIN

-- Diagnose: run EXPLAIN to confirm seq scan:
EXPLAIN SELECT * FROM products WHERE metadata->>'price' > '100';
-- Seq Scan on products (cost=0.00..45231.00 rows=...)
-- Filter: ((metadata->>'price') > '100')
-- The ->> operator extracts a TEXT value — GIN cannot index this

-- Root cause analysis — which operators GIN supports:
-- ✓ metadata @> '{"status": "active"}'        -- containment → GIN used
-- ✓ metadata ? 'discount'                     -- key exists → GIN used
-- ✓ metadata ?| ARRAY['a', 'b']               -- any key → GIN used
-- ✗ metadata->>'price' > '100'                -- extracted value comparison → NO GIN
-- ✗ metadata->>'name' LIKE '%widget%'         -- extracted text search → NO GIN
-- ✗ (metadata->'price')::numeric > 100        -- cast comparison → NO GIN

-- Fix 1: rewrite query to use @> (if equality):
SELECT * FROM products WHERE metadata @> '{"status": "active"}';  -- Uses GIN

-- Fix 2: expression index for extracted value comparisons:
CREATE INDEX ON products ((metadata->>'price'));    -- B-tree on extracted text
SELECT * FROM products WHERE metadata->>'price' > '100';   -- Uses expression index
-- But text comparison of numbers: '9' > '100' is true (lexicographic!)

-- Correct: cast to numeric in expression index:
CREATE INDEX ON products ((( metadata->>'price')::numeric));
SELECT * FROM products WHERE (metadata->>'price')::numeric > 100;

-- Fix 3: jsonb_path_ops for @> and @? only (faster, smaller):
DROP INDEX products_metadata_idx;
CREATE INDEX ON products USING GIN (metadata jsonb_path_ops);
-- Now only @> and @? work; ? and ?| do NOT work with jsonb_path_ops

-- Fix 4: restructure data — move frequently-queried JSONB fields to columns:
ALTER TABLE products ADD COLUMN price NUMERIC GENERATED ALWAYS AS
    ((metadata->>'price')::numeric) STORED;
CREATE INDEX ON products (price);
-- Fastest option: regular B-tree on a real column with proper type
```

**Q13. "Your time-series table has 2 billion rows. A B-tree on `timestamp` is 200GB and inserts are slow. Design the optimal indexing strategy."**
A: A 200GB B-tree on a time-series table is the classic sign that BRIN with table partitioning is the right architecture — the B-tree is massive because it indexes every row, while BRIN only needs one entry per block range:

```sql
-- Step 1: measure current correlation to confirm BRIN viability:
SELECT correlation FROM pg_stats
WHERE tablename = 'metrics' AND attname = 'recorded_at';
-- If > 0.9: BRIN will work well (data is physically ordered by time)
-- Append-only time-series almost always has correlation ≈ 1.0

-- Step 2: partition by time range (monthly or daily depending on volume):
CREATE TABLE metrics (
    recorded_at  TIMESTAMPTZ NOT NULL,
    device_id    UUID NOT NULL,
    metric_name  TEXT NOT NULL,
    value        FLOAT8 NOT NULL
) PARTITION BY RANGE (recorded_at);

-- Create monthly partitions:
CREATE TABLE metrics_2024_01 PARTITION OF metrics
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE metrics_2024_02 PARTITION OF metrics
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- (Automate partition creation with pg_partman extension)

-- Step 3: BRIN index on each partition (or the parent):
CREATE INDEX ON metrics USING BRIN (recorded_at) WITH (pages_per_range = 32);
-- Index size on parent: ~1MB (vs 200GB B-tree)
-- PostgreSQL automatically creates BRIN on each partition

-- Step 4: B-tree indexes for non-time queries (device_id lookups):
CREATE INDEX ON metrics (device_id, recorded_at);
-- Or per-partition for smaller indexes:
CREATE INDEX ON metrics_2024_01 (device_id);
-- device_id queries scoped to a partition (after partition pruning by recorded_at)

-- Step 5: drop the old B-tree:
DROP INDEX metrics_recorded_at_btree_idx;   -- After confirming BRIN works

-- Result:
-- Before: 200GB B-tree, slow inserts (index maintenance per row)
-- After:  ~1MB BRIN, fast inserts (BRIN updated per block range, not per row)
--         partition pruning eliminates months from queries
--         query: WHERE recorded_at > NOW() - INTERVAL '7 days'
--         → only last partition(s) scanned, BRIN eliminates most blocks

-- Step 6: query pattern for the partitioned table:
EXPLAIN SELECT avg(value)
FROM metrics
WHERE recorded_at > NOW() - INTERVAL '7 days'
  AND device_id = 'device-42'
  AND metric_name = 'cpu_usage';
-- Partition Pruning: eliminates all but current month partition
-- Bitmap Index Scan: BRIN eliminates block ranges outside the 7-day window
-- Filter: device_id and metric_name applied on remaining rows
-- Much faster: ~50MB scanned vs 200GB previously

-- For time-series workloads: also consider TimescaleDB extension
-- (hypertables with automatic partitioning and compression)
```

**Q14. "Users report that search on a 50M row product catalogue is slow even though you have a GIN index. How do you diagnose and fix it?"**
A: GIN index search can be slow for several reasons: the search term is too common (low selectivity), fastupdate pending list is large, or the query is combining FTS with unindexed filters in an inefficient order:

```sql
-- Step 1: confirm the GIN index is actually being used:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name, ts_rank(search_vector, query) AS rank
FROM products,
     websearch_to_tsquery('english', 'laptop') query
WHERE search_vector @@ query
ORDER BY rank DESC
LIMIT 20;

-- Check the output:
-- If Seq Scan: GIN not used — recheck query matches index expression
-- If Bitmap Index Scan → Bitmap Heap Scan: GIN used, check timing breakdown

-- Step 2: check if the search term is too common:
SELECT ts_stat('SELECT search_vector FROM products')
AS (word TEXT, ndoc INT, nentry INT)
ORDER BY ndoc DESC
LIMIT 10;
-- If 'laptop' appears in 40% of 50M rows: 20M results → slow even with GIN
-- GIN finds all matching rows but there are too many to rank and return quickly
```

```sql
-- Step 3: check GIN pending list size (fastupdate accumulation):
SELECT pg_size_pretty(pg_relation_size('products_search_vector_idx'));
-- If larger than expected: pending list may be large

-- Force pending list flush:
VACUUM products;   -- Merges pending list into main GIN index

-- Or disable fastupdate for stable read-heavy catalogue:
ALTER INDEX products_search_vector_idx SET (fastupdate = off);
-- New entries go directly to main index (slower writes, consistent reads)
```

```sql
-- Step 4: fix slow combined queries (FTS + category filter):
-- Slow: GIN finds millions of 'laptop' matches, then filters by category
EXPLAIN SELECT id, name
FROM products
WHERE search_vector @@ websearch_to_tsquery('electronics')
  AND category = 'laptops'  -- Applied AFTER GIN returns millions of rows
ORDER BY ts_rank(search_vector, websearch_to_tsquery('electronics')) DESC
LIMIT 20;

-- Fix A: partial GIN index per category:
CREATE INDEX ON products USING GIN (search_vector)
WHERE category = 'laptops';
-- Query must include WHERE category = 'laptops' to use this index
-- Smaller index → faster search within category

-- Fix B: combined filter pushdown with index on category:
CREATE INDEX ON products (category);
-- Planner may choose: filter by category first (if highly selective),
-- then apply FTS filter on smaller result set

-- Fix C: pre-filter with a fast index, then FTS:
-- Use CTE to narrow candidates before full FTS:
WITH candidates AS (
    SELECT id
    FROM products
    WHERE category = 'laptops'
      AND price BETWEEN 500 AND 2000     -- B-tree indexes used
      AND in_stock = true
)
SELECT p.id, p.name, ts_rank(p.search_vector, query) AS rank
FROM candidates c
JOIN products p ON p.id = c.id,
     websearch_to_tsquery('english', 'gaming laptop') query
WHERE p.search_vector @@ query
ORDER BY rank DESC
LIMIT 20;
-- If category + price reduces candidates to 10,000 rows:
-- FTS on 10,000 rows is fast even without a GIN on that subset
```

```sql
-- Step 5: if search is still too slow — pg_trgm similarity for autocomplete:
CREATE EXTENSION pg_trgm;
CREATE INDEX ON products USING GIN (name gin_trgm_ops);

-- Fast autocomplete / fuzzy search:
SELECT name, similarity(name, 'lapt') AS sim
FROM products
WHERE name % 'lapt'            -- % = similarity threshold (default 0.3)
ORDER BY sim DESC
LIMIT 10;
-- GIN trigram index handles LIKE '%lapt%', ILIKE, and similarity queries
-- Complements FTS: trigram for autocomplete, FTS for full document search
```

| B-tree | Scalar: INT, TEXT, UUID, DATE, ENUM | `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `LIKE 'x%'`, `IS NULL`, `ORDER BY` | Medium | Low | Default choice for almost everything; equality, range, sort, uniqueness |
| Hash | Scalar: UUID, TEXT, large keys | `=` only | Small (stores hash not value) | Low | Equality-only on very large tables where B-tree depth matters; rare |
| GIN | JSONB, arrays, tsvector | `@>`, `<@`, `&&`, `?`, `?|`, `?&`, `@@`, `@?` | Large | High (pending list amortises) | Composite values: JSONB metadata, tag arrays, full-text search |
| GiST | Geometry, ranges, INET, tsvector | `&&`, `@>`, `<@`, `<->`, `>>`, `<<`, `-|-` | Medium | Medium | Spatial queries, range overlap, exclusion constraints, KNN, IP containment |
| BRIN | Append-only scalar with physical correlation | `=`, `<`, `>`, `<=`, `>=`, `BETWEEN` | Tiny | Very low | Time-series / log tables with correlation ≈ 1.0; billions of rows |
| GIN (pg_trgm) | TEXT with trigrams | `LIKE '%x%'`, `ILIKE`, `%` (similarity) | Large | High | Substring search, autocomplete, fuzzy matching, LIKE with leading wildcard |
| GiST (btree_gist) | Scalar + range in exclusion constraint | All GiST ops + B-tree ops | Medium | Medium | Exclusion constraints mixing scalar equality (UUID, INT) with range overlap |

**Tip for interviews:** Five things separate strong candidates on PostgreSQL index types: (1) explaining **why B-tree is the default** and what its internal structure buys you — that it's a balanced tree of sorted pages with linked leaf nodes, which is why it supports range scans, sorts, and LIKE prefix matching in one structure, and that the planner's cost model compares random I/O (index scan) vs sequential I/O (seq scan), which is why `random_page_cost = 1.1` on SSDs dramatically changes which indexes get used; (2) understanding **GIN's inverted index model** — that it maps each element (JSONB key, array item, lexeme) to a posting list of row IDs, which is why `@>` (containment) is supported but `->>` extraction + comparison is not, and knowing that the fix for extraction queries is an expression index on the extracted, cast value; (3) knowing **when BRIN is transformative** — that it stores only min/max per block range and is therefore 100,000x smaller than a B-tree for correlated time-series data, checking `pg_stats.correlation` to confirm viability, and that partitioning + BRIN is the standard architecture for billion-row time-series tables; (4) being able to explain **GiST's role for range overlap and exclusion constraints** — that no other index type supports the `&&` overlap operator used in `EXCLUDE USING GIST (room_id WITH =, period WITH &&)`, and that `btree_gist` is required to use scalar types like UUID in GiST exclusion constraints; and (5) knowing the **operational difference between `CREATE INDEX` and `CREATE INDEX CONCURRENTLY`** — that the standard form takes a lock that blocks writes (acceptable in dev, dangerous in production), that `CONCURRENTLY` does two passes with no write locks but leaves an `INVALID` index on failure that must be dropped and retried, and that `REINDEX INDEX CONCURRENTLY` (PostgreSQL 12+) is the equivalent for rebuilding bloated indexes without downtime.
