# PostgreSQL Partitioning: Range, List, Hash — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is table partitioning and what problem does it solve that indexes alone cannot?**
A: Partitioning divides a single logical table into multiple physical storage units (partitions) based on a column's value. Each partition is a real PostgreSQL table with its own heap files, indexes, and statistics. The parent table is a routing shell with no data of its own:

```
The problem indexes alone cannot solve:

  Table: transactions, 500M rows, growing 2M rows/day
  Query: SELECT * FROM transactions WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'

  With a B-tree index on created_at:
    Index scan → fetches ~60M rows from January → random I/O across entire table
    VACUUM must scan all 500M rows to reclaim dead tuples
    Table statistics cover all 500M rows → planner estimates less accurate
    Deleting old data (WHERE created_at < '2022-01-01'): DELETE scans + vacuums millions

  With monthly range partitioning:
    Parent: transactions (no data)
    Child:  transactions_2024_01 (January data only, ~60M rows)
    Child:  transactions_2024_02 (February data only)
    ...
    Child:  transactions_2021_12 (old data, candidate for dropping)

    Query hits ONLY transactions_2024_01 → sequential scan of 60M vs random I/O on 500M
    VACUUM runs per partition → fast, targeted
    Statistics per partition → accurate planner estimates
    Archive old data: DROP TABLE transactions_2021_12 → instant (no DELETE, no VACUUM)

What partitioning solves that indexes cannot:
  1. Partition pruning: planner eliminates entire partitions from the query plan
     → fewer blocks read than even an index scan on a cold, large table
  2. Bulk data management: DROP/DETACH a partition = instant archival (no row-by-row DELETE)
  3. Parallel maintenance: VACUUM, ANALYZE, REINDEX run per partition independently
  4. Data locality: hot recent data in one partition → fits in shared_buffers
  5. Index size: index on each partition is fraction of a global index → fits in memory

What partitioning does NOT replace:
  - Indexes within partitions (still needed for non-partition-key lookups)
  - Query optimization (poor queries are still poor on partitions)
  - Connection pooling or caching
```

**Q2. How does PostgreSQL implement declarative partitioning and what are the roles of parent and child tables?**
A: PostgreSQL declarative partitioning (introduced in v10, matured in v11-v14) uses inheritance with routing rules. The parent table defines the schema and partition strategy; child tables hold the actual data:

```sql
-- Parent table: schema definition only, zero rows stored here
CREATE TABLE transactions (
    id          UUID        NOT NULL DEFAULT gen_random_uuid(),
    tenant_id   UUID        NOT NULL,
    amount      NUMERIC(15,2) NOT NULL,
    status      TEXT        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);    -- partition strategy declared here

-- Child partitions: real tables with actual storage
CREATE TABLE transactions_2024_01
    PARTITION OF transactions
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');  -- [inclusive, exclusive)

CREATE TABLE transactions_2024_02
    PARTITION OF transactions
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- What happens on INSERT:
INSERT INTO transactions (tenant_id, amount, status, created_at)
VALUES ('T1', 50000, 'completed', '2024-01-15 10:30:00');
-- PostgreSQL routes to transactions_2024_01 automatically
-- The row physically lives in transactions_2024_01's heap file

-- What happens on SELECT:
SELECT * FROM transactions WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
-- PostgreSQL planner applies partition pruning:
-- Checks each partition's range against WHERE clause
-- Eliminates transactions_2024_02 (range doesn't overlap)
-- Queries ONLY transactions_2024_01
-- → Seq Scan on transactions_2024_01 (not the parent)

-- Querying a specific partition directly (bypasses routing overhead):
SELECT * FROM transactions_2024_01 WHERE tenant_id = 'T1';

-- Viewing partition structure:
SELECT
    parent.relname AS parent,
    child.relname  AS partition,
    pg_get_expr(child.relpartbound, child.oid) AS bounds
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
WHERE parent.relname = 'transactions';

-- Key structural facts:
-- 1. PRIMARY KEY and UNIQUE constraints must include the partition key
--    (enforced per partition, not globally across partitions)
-- 2. Foreign keys FROM a partitioned table work normally
--    Foreign keys TO a partitioned table require partition key in the FK columns (v12+)
-- 3. Indexes created on the parent are automatically created on each partition
-- 4. Each partition can have its own tablespace (archive partitions on cheap storage)
-- 5. DEFAULT partition catches rows that match no other partition bound
```

**Q3. What is partition pruning and how does the planner decide which partitions to scan?**
A: Partition pruning is the process by which the query planner eliminates partitions that cannot contain rows matching the WHERE clause. It happens at plan time (static pruning) and at execution time (dynamic pruning):

```sql
-- Setup: transactions partitioned by RANGE (created_at), monthly partitions

-- Static pruning (at plan time — constant values in WHERE):
EXPLAIN SELECT * FROM transactions
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';

-- Plan:
-- Seq Scan on transactions_2024_01
-- (other partitions pruned at plan time — never appear in plan)

-- Dynamic pruning (at execution time — parameterized or runtime values):
EXPLAIN SELECT * FROM transactions
WHERE created_at >= $1 AND created_at < $2;
-- Plan:
-- Append
--   -> Seq Scan on transactions_2024_01
--      Filter: (created_at >= $1 AND created_at < $2)
--   -> Seq Scan on transactions_2024_02
--      Filter: ...
-- (all partitions appear in plan — runtime values unknown at plan time)
-- But at EXECUTION time: only matching partitions are actually scanned

-- enable_partition_pruning (on by default):
SET enable_partition_pruning = on;   -- dynamic pruning enabled
-- EXPLAIN ANALYZE shows "Subplans Removed: N" — N partitions pruned at runtime

-- Conditions that enable pruning:
-- ✓ Simple comparison: WHERE created_at >= '2024-01-01'
-- ✓ Equality:          WHERE status = 'active'   (list partitioning)
-- ✓ IN list:           WHERE month IN (1, 2, 3)   (list partitioning)
-- ✓ BETWEEN:           WHERE created_at BETWEEN '2024-01-01' AND '2024-03-31'

-- Conditions that PREVENT pruning:
-- ✗ Function on partition key: WHERE date_trunc('month', created_at) = '2024-01-01'
--   Fix: WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'
-- ✗ Non-immutable function:   WHERE created_at > NOW() - INTERVAL '30 days'
--   → NOW() is not immutable → planner cannot prune at plan time
--   → runtime pruning still works for this case
-- ✗ OR across partition keys: WHERE created_at < '2024-01-01' OR status = 'cancelled'
--   → OR prevents clean range inference → no pruning on the OR branch
-- ✗ Implicit cast mismatch:   partition key is TIMESTAMPTZ, filter uses DATE
--   Fix: explicit cast or use consistent types

-- Verifying pruning worked:
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM transactions
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31';
-- Look for: "Partitions selected: 1" or only one child table in the plan
-- If multiple children appear AND are all scanned: pruning not working → check WHERE clause
```

## Section 2: Range Partitioning

**Q4. How does range partitioning work and what are its bounds semantics?**
A: Range partitioning assigns each row to the partition whose range contains the partition key value. Ranges are defined as `[FROM, TO)` — FROM is inclusive, TO is exclusive. Ranges must not overlap and must cover the expected data (or use a DEFAULT partition):

```sql
-- Partition bounds: [FROM inclusive, TO exclusive)
CREATE TABLE loan_repayments (
    id             UUID         NOT NULL DEFAULT gen_random_uuid(),
    loan_id        UUID         NOT NULL,
    amount         NUMERIC(15,2) NOT NULL,
    due_date       DATE         NOT NULL,
    paid_at        TIMESTAMPTZ,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Monthly partitions for 2024:
CREATE TABLE loan_repayments_2024_01 PARTITION OF loan_repayments
    FOR VALUES FROM ('2024-01-01 00:00:00+00') TO ('2024-02-01 00:00:00+00');

CREATE TABLE loan_repayments_2024_02 PARTITION OF loan_repayments
    FOR VALUES FROM ('2024-02-01 00:00:00+00') TO ('2024-03-01 00:00:00+00');

-- Bounds for December (year boundary):
CREATE TABLE loan_repayments_2024_12 PARTITION OF loan_repayments
    FOR VALUES FROM ('2024-12-01 00:00:00+00') TO ('2025-01-01 00:00:00+00');

-- DEFAULT partition (catches rows not in any defined range):
CREATE TABLE loan_repayments_future PARTITION OF loan_repayments
    DEFAULT;
-- Without DEFAULT: INSERT with created_at outside all ranges → ERROR
-- With DEFAULT: INSERT goes to loan_repayments_future → no error

-- MINVALUE / MAXVALUE for open-ended ranges:
CREATE TABLE loan_repayments_archive PARTITION OF loan_repayments
    FOR VALUES FROM (MINVALUE) TO ('2023-01-01 00:00:00+00');
-- Catches all rows before 2023

-- Multi-column range partitioning:
CREATE TABLE events (
    tenant_id  UUID NOT NULL,
    event_time TIMESTAMPTZ NOT NULL,
    payload    JSONB
) PARTITION BY RANGE (tenant_id, event_time);
-- Range evaluated as composite: (tenant_id, event_time) as a tuple
-- FROM ('T1', '2024-01-01') TO ('T1', '2024-02-01')
-- Less common — usually better to partition by time only and use tenant_id as a filter

-- What happens if no partition matches and no DEFAULT:
INSERT INTO loan_repayments (loan_id, amount, due_date, created_at)
VALUES ('L1', 5000, '2025-01-15', '2025-01-15');
-- ERROR: no partition of relation "loan_repayments" found for row
-- → must create 2025 partition before inserting 2025 data

-- Automating partition creation (pg_partman extension):
-- pg_partman handles automatic creation of future partitions and
-- detachment of old ones on a schedule
-- Installation: CREATE EXTENSION pg_partman;
-- Setup: SELECT partman.create_parent('public.loan_repayments', 'created_at', 'native', 'monthly');
-- Maintenance: SELECT partman.run_maintenance();  -- call via cron
```

**Q5. What are the common range partitioning strategies and how do you choose partition size?**

```sql
-- Partition size choices and their tradeoffs:

-- Too small (daily partitions on a table with 2M rows/day):
CREATE TABLE txns_2024_01_01 PARTITION OF transactions
    FOR VALUES FROM ('2024-01-01') TO ('2024-01-02');
-- Problems:
-- 365 partitions per year → planner must evaluate all bounds → plan time overhead
-- Each partition's index is tiny → sequential scan faster than index scan on tiny tables
-- Schema management nightmare (automatic partition creation essential)
-- Many files → OS-level file descriptor pressure

-- Too large (yearly partitions on a table with 2M rows/day):
CREATE TABLE txns_2024 PARTITION OF transactions
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
-- Problems:
-- 730M rows per partition → hardly better than no partitioning
-- Dropping old data: must wait for entire year to pass before dropping
-- Large indexes don't fit in memory → same as unpartitioned

-- Right size — monthly for most time-series OLTP tables:
-- 2M rows/day × 30 days = 60M rows per partition
-- Index on partition fits in memory (UUID index ~1.5GB for 60M rows — still large)
-- Annual archival: drop one year = drop 12 files → instant

-- Weekly for very high volume (10M+ rows/day):
-- 10M × 7 = 70M rows per partition — manageable

-- Quarterly for lower volume historical tables:
-- 100K rows/day × 90 days = 9M rows per partition — easy

-- Partition size decision framework:
-- Target: 10M–100M rows per partition for OLTP
-- Check: does the partition's index fit in shared_buffers? (aim: yes for hot partitions)
-- Check: how often do you need to drop old data? (partition granularity = minimum drop unit)
-- Check: how many total partitions? (rule of thumb: < 1000 partitions per parent table)

-- Indexes on range-partitioned tables:
-- Global index (on parent): one index entry per row, spans all partitions
-- Local index (on parent using CREATE INDEX): creates one index per partition
-- PostgreSQL only supports local indexes (one per partition) for declarative partitioning

CREATE INDEX ON loan_repayments (loan_id);
-- Creates: idx_loan_repayments_2024_01_loan_id
--          idx_loan_repayments_2024_02_loan_id
--          ... (one per partition)
-- Each is a fraction of a global index → fits in memory individually
-- Query with partition pruning + index: scans only matching partition's index

-- Querying across partitions:
SELECT * FROM loan_repayments WHERE loan_id = 'L1';
-- No partition pruning possible (loan_id not the partition key)
-- Scans EVERY partition's index → potentially slow if many partitions
-- This is why the partition key should match your most common query filter
```

**Q6. How do you manage partition lifecycle — creating future partitions and archiving old ones?**

```sql
-- The partition lifecycle problem:
-- Range partitions must exist BEFORE data arrives
-- If no partition exists for a date and no DEFAULT: INSERT fails
-- Old partitions must be archived/dropped on a schedule

-- ── Creating partitions proactively ──────────────────────────────────────────

-- Manual (for small partition counts):
-- Run monthly via cron or migration script:
CREATE TABLE transactions_2025_01 PARTITION OF transactions
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

-- PostgreSQL function to create next month's partition:
CREATE OR REPLACE FUNCTION create_next_month_partition()
RETURNS void AS $$
DECLARE
    next_month_start  DATE := date_trunc('month', NOW() + INTERVAL '1 month');
    next_month_end    DATE := date_trunc('month', NOW() + INTERVAL '2 months');
    partition_name    TEXT := 'transactions_' || to_char(next_month_start, 'YYYY_MM');
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_class c
        JOIN pg_inherits i ON c.oid = i.inhrelid
        JOIN pg_class p ON p.oid = i.inhparent
        WHERE p.relname = 'transactions' AND c.relname = partition_name
    ) THEN
        EXECUTE format(
            'CREATE TABLE %I PARTITION OF transactions
             FOR VALUES FROM (%L) TO (%L)',
            partition_name,
            next_month_start,
            next_month_end
        );
        RAISE NOTICE 'Created partition: %', partition_name;
    END IF;
END;
$$ LANGUAGE plpgsql;

-- Schedule via pg_cron:
SELECT cron.schedule('create_partitions', '0 0 1 * *', 'SELECT create_next_month_partition()');

-- ── Archiving and dropping old partitions ─────────────────────────────────────

-- Option 1: DROP (immediate, no recovery)
DROP TABLE transactions_2022_01;
-- Instant — removes the partition file from disk
-- No VACUUM needed, no DELETE scan
-- Cannot be undone (unless you have a backup)

-- Option 2: DETACH then archive (safe, recoverable)
-- Detach removes the partition from routing without dropping data:
ALTER TABLE transactions DETACH PARTITION transactions_2022_01;
-- transactions_2022_01 is now a standalone regular table
-- Queries on transactions no longer touch it
-- The data still exists — can query it directly, export it, or move it

-- Then optionally move to cold storage / separate database, then drop:
\COPY transactions_2022_01 TO '/archive/transactions_2022_01.csv' CSV HEADER;
DROP TABLE transactions_2022_01;

-- Option 3: DETACH CONCURRENTLY (PostgreSQL 14+ — no lock on parent)
-- Standard DETACH takes ShareUpdateExclusiveLock on parent (blocks some operations)
-- DETACH CONCURRENTLY takes a weaker lock — suitable for production:
ALTER TABLE transactions DETACH PARTITION transactions_2022_01 CONCURRENTLY;

-- Option 4: Attach existing table as partition (for loading historical data)
-- Useful when migrating a legacy table into a partitioned schema:
CREATE TABLE transactions_2021_legacy (LIKE transactions INCLUDING ALL);
-- Load data into transactions_2021_legacy (COPY, INSERT, etc.)
-- Then attach:
ALTER TABLE transactions ATTACH PARTITION transactions_2021_legacy
    FOR VALUES FROM ('2021-01-01') TO ('2022-01-01');
-- PostgreSQL validates that all rows satisfy the partition constraint
-- Use CHECK constraint to skip validation scan (if you already know the data is valid):
ALTER TABLE transactions_2021_legacy
    ADD CONSTRAINT check_2021 CHECK (created_at >= '2021-01-01' AND created_at < '2022-01-01')
    NOT VALID;
ALTER TABLE transactions ATTACH PARTITION transactions_2021_legacy
    FOR VALUES FROM ('2021-01-01') TO ('2022-01-01');
-- With NOT VALID constraint: ATTACH skips the full table scan → instant
```

## Section 3: List Partitioning

**Q7. How does list partitioning work and when is it the right choice over range?**
A: List partitioning assigns rows to partitions based on membership in an explicit list of values. It is appropriate when the partition key is a discrete categorical column — region, status, tenant tier, country code — rather than a continuous value like a timestamp:

```sql
-- List partitioning: each partition owns a specific set of discrete values
CREATE TABLE loan_applications (
    id          UUID   NOT NULL DEFAULT gen_random_uuid(),
    tenant_id   UUID   NOT NULL,
    region      TEXT   NOT NULL,   -- 'north', 'south', 'east', 'west', 'central'
    status      TEXT   NOT NULL,
    amount      NUMERIC(15,2),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY LIST (region);

-- Each partition owns specific values:
CREATE TABLE loan_applications_north   PARTITION OF loan_applications
    FOR VALUES IN ('north');

CREATE TABLE loan_applications_south   PARTITION OF loan_applications
    FOR VALUES IN ('south');

-- Multiple values in one partition (grouping regions):
CREATE TABLE loan_applications_east_central PARTITION OF loan_applications
    FOR VALUES IN ('east', 'central');

CREATE TABLE loan_applications_west    PARTITION OF loan_applications
    FOR VALUES IN ('west');

-- DEFAULT catches any region not listed above:
CREATE TABLE loan_applications_other   PARTITION OF loan_applications DEFAULT;

-- Query with partition pruning:
SELECT * FROM loan_applications WHERE region = 'north';
-- Planner: checks partition lists → only loan_applications_north matches
-- Seq Scan on loan_applications_north (all others pruned)

SELECT * FROM loan_applications WHERE region IN ('east', 'central');
-- Planner: checks partition lists → loan_applications_east_central matches
-- Seq Scan on loan_applications_east_central

SELECT * FROM loan_applications WHERE region = 'north' OR region = 'south';
-- Planner: checks both → two partitions scanned (north + south)
-- Append → Seq Scan on loan_applications_north + Seq Scan on loan_applications_south

-- When list partitioning is appropriate:
-- ✓ Finite, stable set of discrete values (regions, countries, status codes)
-- ✓ Queries almost always filter on this column
-- ✓ Data volume roughly balanced across partitions
-- ✓ Operational isolation: different teams/compliance zones per region

-- When list partitioning is NOT appropriate:
-- ✗ High cardinality (thousands of distinct values → thousands of partitions)
-- ✗ Values change frequently (restructuring partitions requires migration)
-- ✗ Queries rarely filter on this column (pruning never triggers)
-- ✗ Very uneven distribution (one value has 90% of rows)
```

**Q8. How do you use list partitioning for multi-tenant isolation and what are the tradeoffs?**
A: List partitioning by `tenant_id` is a common multi-tenant strategy — each tenant's data lives in its own partition, providing physical isolation, independent vacuum cycles, and the ability to drop a tenant's data instantly. The tradeoff is scalability: you need one partition per tenant:

```sql
-- Multi-tenant partitioning by tenant_id:
CREATE TABLE events (
    id         UUID NOT NULL DEFAULT gen_random_uuid(),
    tenant_id  UUID NOT NULL,
    event_type TEXT NOT NULL,
    payload    JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY LIST (tenant_id);

-- One partition per tenant:
CREATE TABLE events_tenant_t001 PARTITION OF events
    FOR VALUES IN ('00000000-0000-0000-0000-000000000001');

CREATE TABLE events_tenant_t002 PARTITION OF events
    FOR VALUES IN ('00000000-0000-0000-0000-000000000002');

-- DEFAULT for tenants not yet assigned their own partition:
CREATE TABLE events_shared PARTITION OF events DEFAULT;

-- Benefits:
-- 1. Pruning: WHERE tenant_id='T1' scans only that tenant's partition
-- 2. VACUUM per tenant: large tenant doesn't delay other tenants' vacuum
-- 3. Instant offboarding: DROP TABLE events_tenant_t001 → all data gone, no DELETE scan
-- 4. Per-tenant tablespace: move large tenant to faster storage
-- 5. Per-tenant indexes: create extra indexes only for power-user tenants

-- Moving a growing tenant from shared to dedicated partition:
-- Step 1: Create new dedicated partition
CREATE TABLE events_tenant_t099 (LIKE events INCLUDING ALL);

-- Step 2: Copy data
INSERT INTO events_tenant_t099 SELECT * FROM events_shared WHERE tenant_id = 'T99';

-- Step 3: Add constraint (needed for ATTACH without validation scan)
ALTER TABLE events_tenant_t099
    ADD CONSTRAINT check_tenant CHECK (tenant_id = 'T99') NOT VALID;

-- Step 4: Delete from shared (or do it after ATTACH)
DELETE FROM events_shared WHERE tenant_id = 'T99';

-- Step 5: Attach dedicated partition
ALTER TABLE events ATTACH PARTITION events_tenant_t099
    FOR VALUES IN ('T99');

-- Tradeoffs of per-tenant partitioning:
-- ✗ Scalability: 1000 tenants = 1000 partitions
--   → planner overhead for queries without tenant_id filter
--   → each partition has its own indexes → many small indexes in buffer cache
-- ✗ Small tenants waste partition overhead (dedicated files for tiny data)
-- ✗ Schema changes: ALTER TABLE propagates to all child partitions (slow for thousands)

-- When per-tenant partitioning is appropriate:
-- Large tenants (>1M rows each), limited count (<100-200 tenants)
-- Strict data isolation requirements (compliance, GDPR right-to-erasure)
-- Variable SLA: premium tenants get faster storage, shared tenants share

-- Alternative for thousands of small tenants:
-- Row-level tenant_id column + index + RLS (Row Level Security)
-- No partitioning — simpler, scales to any number of tenants
-- RLS enforces tenant isolation at query level:
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON events
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

## Section 4: Hash Partitioning

**Q9. How does hash partitioning work and what problem does it solve that range and list cannot?**
A: Hash partitioning computes a hash of the partition key value modulo the number of partitions and assigns the row accordingly. It distributes rows evenly across partitions even when values have no natural ordering and no finite enumerable set — which makes it the only option for uniformly distributing write load:

```sql
-- Hash partitioning: rows distributed by hash(key) % modulus
CREATE TABLE audit_logs (
    id         UUID NOT NULL DEFAULT gen_random_uuid(),
    entity_id  UUID NOT NULL,
    action     TEXT NOT NULL,
    payload    JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY HASH (entity_id);

-- N partitions: specify modulus (total) and remainder (this partition's bucket)
CREATE TABLE audit_logs_p0 PARTITION OF audit_logs
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);   -- hash(entity_id) % 4 = 0

CREATE TABLE audit_logs_p1 PARTITION OF audit_logs
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);   -- hash(entity_id) % 4 = 1

CREATE TABLE audit_logs_p2 PARTITION OF audit_logs
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);

CREATE TABLE audit_logs_p3 PARTITION OF audit_logs
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);

-- All remainders 0..N-1 must be covered (no DEFAULT possible for hash partitioning)

-- How routing works:
INSERT INTO audit_logs (entity_id, action) VALUES ('abc-123', 'UPDATE');
-- PostgreSQL computes: hashvalue = hash('abc-123') % 4
-- hashvalue = 2 → row goes to audit_logs_p2

-- Every entity_id always goes to the same partition:
-- hash('abc-123') % 4 = 2 → always audit_logs_p2
-- All rows for entity 'abc-123' are co-located in one partition

-- Query with hash partitioning:
SELECT * FROM audit_logs WHERE entity_id = 'abc-123';
-- Planner: computes hash('abc-123') % 4 = 2 → prunes to audit_logs_p2
-- Index Scan or Seq Scan on audit_logs_p2 only ← partition pruning works for equality!

SELECT * FROM audit_logs WHERE action = 'DELETE';
-- action is NOT the partition key → NO pruning → all 4 partitions scanned
-- Hash partitioning only prunes on equality of the partition key

-- What hash partitioning solves:
-- UUID primary keys, user IDs, entity IDs — no natural range, infinite cardinality
-- Write-heavy tables: 4 partitions = 4 independent heap files = parallel writes
-- Even distribution: hash function ensures ~equal rows per partition (no hotspots)
-- Lock contention reduction: INSERTs to different partitions don't contend

-- What hash partitioning does NOT solve:
-- Range queries: WHERE created_at > '2024-01-01' → all partitions scanned (no pruning)
-- Archiving: no concept of "old" vs "new" data → cannot drop a partition to archive
-- Data locality: related entity's rows in same partition, but no time-based locality
```

**Q10. How do you choose the number of hash partitions and what is the cost of repartitioning?**

```sql
-- Choosing the number of partitions:

-- Too few (2 partitions):
-- Each partition still very large → limited parallelism benefit
-- Uneven hash distribution is more likely with few buckets

-- Too many (128 partitions):
-- Planner must evaluate 128 bounds even after pruning
-- Each partition's index is tiny → sequential scan beats index scan for small partitions
-- Many open file descriptors (one per partition per connection)
-- max_locks_per_transaction may need tuning (default 64 — limits how many partitions
-- a single transaction can touch without hitting lock table limit)

-- Rule of thumb:
-- 4–16 partitions for write parallelism on write-heavy tables
-- 8–32 partitions for large lookup tables (billions of rows)
-- Stay below 100 unless using pg_partman and automatic management

-- Target: each partition has 50M–500M rows (performance sweet spot)

-- Parallelism alignment:
-- max_worker_processes: number of parallel workers available
-- Setting partitions = max_parallel_workers_per_gather (default 2) aligns
-- partition scan parallelism with available workers

-- The repartitioning problem (CRITICAL interview point):
-- Hash partitioning cannot be rescaled without rewriting all data.
-- Changing from MODULUS 4 to MODULUS 8 requires:
--   1. Create new parent table with PARTITION BY HASH and MODULUS 8
--   2. Create 8 new child partitions
--   3. INSERT INTO new_table SELECT * FROM old_table  ← full table rewrite
--   4. Swap table names, update application
-- This is an expensive operation on a live system (hours/days for billions of rows)

-- Contrast with range partitioning:
-- Adding a new month's partition to a range table: instantaneous (CREATE TABLE)
-- Data naturally flows into new partition going forward

-- Mitigation strategy — pre-plan for growth:
-- If you think you'll need 8 partitions in 2 years, create 8 now
-- Extra empty partitions cost nothing (no storage for empty tables)
-- Better than repartitioning later

-- Alternatively: use power-of-2 moduli to allow sub-partitioning:
-- Start with MODULUS 4
-- When growth demands more, create sub-partitions for each parent:
CREATE TABLE audit_logs_p0 PARTITION OF audit_logs
    FOR VALUES WITH (MODULUS 4, REMAINDER 0)
    PARTITION BY HASH (entity_id);

CREATE TABLE audit_logs_p0_sub0 PARTITION OF audit_logs_p0
    FOR VALUES WITH (MODULUS 2, REMAINDER 0);
CREATE TABLE audit_logs_p0_sub1 PARTITION OF audit_logs_p0
    FOR VALUES WITH (MODULUS 2, REMAINDER 1);
-- Result: 8 effective buckets without rewriting existing data in p1, p2, p3
```

## Section 5: Combining Partitioning Strategies

**Q11. What is sub-partitioning and when does it make sense?**
A: Sub-partitioning (composite partitioning) applies a second partitioning strategy to each child partition. The canonical use case is partitioning by time first (range), then by tenant or region (list or hash) within each time slice:

```sql
-- Sub-partitioning: RANGE by time → LIST by region
CREATE TABLE transactions (
    id         UUID NOT NULL DEFAULT gen_random_uuid(),
    region     TEXT NOT NULL,
    amount     NUMERIC(15,2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Q1 2024 partition, sub-partitioned by region:
CREATE TABLE transactions_2024_q1 PARTITION OF transactions
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01')
    PARTITION BY LIST (region);

CREATE TABLE transactions_2024_q1_north PARTITION OF transactions_2024_q1
    FOR VALUES IN ('north');
CREATE TABLE transactions_2024_q1_south PARTITION OF transactions_2024_q1
    FOR VALUES IN ('south');
CREATE TABLE transactions_2024_q1_other PARTITION OF transactions_2024_q1
    DEFAULT;

-- Query benefit: double pruning
SELECT * FROM transactions
WHERE created_at BETWEEN '2024-01-01' AND '2024-03-31'
  AND region = 'north';
-- Prune by range: only transactions_2024_q1 (Q1 2024)
-- Prune by list:  only transactions_2024_q1_north (north region)
-- → reads ONE sub-partition out of potentially many

-- When sub-partitioning is appropriate:
-- ✓ Two independent high-cardinality filter dimensions (time AND region/tenant)
-- ✓ Both dimensions appear in most queries
-- ✓ Total leaf partition count stays manageable (< 1000)
-- 4 quarters × 5 regions = 20 leaf partitions — manageable
-- 12 months × 50 states = 600 leaf partitions — borderline
-- 365 days × 1000 tenants = 365,000 leaf partitions — too many

-- When sub-partitioning is NOT appropriate:
-- ✗ Only one dimension commonly filtered (second level adds overhead without benefit)
-- ✗ Total leaf count becomes unmanageable
-- ✗ Uneven distribution between sub-partitions (one region has 90% of rows)

-- Alternative: partition by range, use composite index for the second dimension:
CREATE INDEX ON transactions (region, created_at) WHERE region = 'north';
-- Often simpler than sub-partitioning for moderate data sizes
```

**Q12. How do you handle the common pattern of partitioning by time with secondary lookup by entity ID?**

```sql
-- Common pattern: time-series data queried by time range OR by entity ID
-- Table: loan_events — append-only audit trail for all loan state changes

CREATE TABLE loan_events (
    id          UUID        NOT NULL DEFAULT gen_random_uuid(),
    loan_id     UUID        NOT NULL,
    event_type  TEXT        NOT NULL,
    payload     JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

CREATE TABLE loan_events_2024_01 PARTITION OF loan_events
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
-- ... more monthly partitions

-- Query 1: time-range scan (benefits from partitioning):
SELECT * FROM loan_events
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31';
-- Partition pruning → only January partition scanned ✓

-- Query 2: loan history (does NOT benefit from partitioning):
SELECT * FROM loan_events
WHERE loan_id = 'L12345'
ORDER BY created_at ASC;
-- loan_id is not the partition key → ALL partitions scanned
-- Each partition has its own index on loan_id → scans all partition indexes
-- For 24 monthly partitions: 24 index scans → bitmap merge → expensive for old loans

-- Solutions for the entity-lookup problem:

-- Solution 1: Index on (loan_id, created_at) on each partition
CREATE INDEX ON loan_events (loan_id, created_at ASC);
-- Applies to all current and future partitions
-- Query 2 scans all partition indexes (unavoidable without partition pruning)
-- But each partition's index is small → each scan fast → sum still acceptable
-- Acceptable when: entities don't span too many partitions (recent loans only need recent partition)

-- Solution 2: Partial index on loan_id for recent partitions only
-- Recent loans are almost always in the current month's partition:
CREATE INDEX ON loan_events_2024_01 (loan_id, created_at ASC);
-- For current month's partition — full compound index
-- For old partitions: no index on loan_id (loan histories rarely queried for 2022 loans)

-- Solution 3: Secondary lookup table (separate non-partitioned index)
CREATE TABLE loan_event_index (
    loan_id     UUID        NOT NULL,
    event_id    UUID        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (loan_id, created_at, event_id)
);
-- On INSERT to loan_events: also INSERT to loan_event_index
-- Loan history query: first lookup event IDs from loan_event_index,
--                     then fetch from loan_events by (id, created_at)
-- This is the "secondary index" pattern for partitioned tables

-- Solution 4: Include loan_id in partition key (composite range)
-- If loans are always queried within known time ranges, restrict application queries:
-- "Always include a time range filter when looking up loan events"
-- WHERE loan_id = 'L1' AND created_at >= '2024-01-01'
-- Prunes to January partition + indexes within it — fast
-- Requires application-level discipline (enforce with query timeout / query analysis)
```

## Section 6: Operational Concerns

**Q13. How do indexes, constraints, and primary keys work on partitioned tables?**

```sql
-- Index behavior on partitioned tables:

-- Creating index on parent → creates matching index on all existing AND future partitions:
CREATE INDEX ON loan_repayments (loan_id);
-- Creates: loan_repayments_2024_01_loan_id_idx
--          loan_repayments_2024_02_loan_id_idx
--          ... (one per partition, automatically)

-- Creating index on parent CONCURRENTLY (non-blocking):
CREATE INDEX CONCURRENTLY ON loan_repayments (loan_id);
-- Builds each partition's index concurrently
-- No table lock on parent — safe for production

-- Checking all partition indexes:
SELECT
    i.relname AS index_name,
    t.relname AS partition_name,
    pg_size_pretty(pg_relation_size(i.oid)) AS index_size
FROM pg_index ix
JOIN pg_class i ON i.oid = ix.indexrelid
JOIN pg_class t ON t.oid = ix.indrelid
WHERE t.relname LIKE 'loan_repayments_%'
ORDER BY t.relname, i.relname;

-- PRIMARY KEY on partitioned table (must include partition key):
-- PostgreSQL requires the partition key to be part of the PK
-- (uniqueness can only be enforced per-partition, not globally across partitions)

-- WRONG: partition key (created_at) not in PK
CREATE TABLE transactions (
    id         UUID PRIMARY KEY,          -- ERROR if created_at is partition key
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- CORRECT: include partition key in PK
CREATE TABLE transactions (
    id         UUID        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (id, created_at)          -- partition key included
) PARTITION BY RANGE (created_at);

-- Why this limitation exists:
-- Uniqueness is enforced per-partition (local index, not global)
-- Two rows with the same id in different partitions would not conflict
-- PostgreSQL cannot check across all partitions for uniqueness (no global index)

-- Workaround: gen_random_uuid() guarantees uniqueness probabilistically
-- UUIDs are unique globally without a cross-partition constraint check
-- For business keys (email, reference_code), a UNIQUE constraint across partitions
-- is not supported natively — use a separate non-partitioned lookup table

-- FOREIGN KEY constraints:
-- FK FROM partitioned table: works normally
-- FK TO partitioned table: supported in PostgreSQL 12+ but partition key must be in FK

-- Triggers on partitioned tables (PostgreSQL 13+):
-- BEFORE/AFTER triggers on parent propagate to all partitions
CREATE TRIGGER audit_trigger AFTER INSERT OR UPDATE ON loan_repayments
    FOR EACH ROW EXECUTE FUNCTION audit_log_function();
-- Fires on all partitions automatically
```

**Q14. How does VACUUM and ANALYZE behave differently on partitioned tables and why does it matter?**

```sql
-- Autovacuum on partitioned tables: runs per partition independently

-- Why this is beneficial:
-- Non-partitioned table (500M rows):
--   Autovacuum: scans all 500M rows → takes hours → table statistics stale during scan
--   Dead tuples: accumulate across entire table → large memory footprint for vacuum

-- Partitioned table (same 500M rows, 12 monthly partitions):
--   Autovacuum: scans each partition independently (~42M rows each)
--   Recent partition (active writes): vacuumed frequently (many dead tuples)
--   Old partitions (no writes): rarely need vacuum (no dead tuples accumulate)
--   → vacuum is targeted, fast, less disruptive

-- Checking autovacuum per partition:
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    last_autoanalyze,
    autovacuum_count
FROM pg_stat_user_tables
WHERE relname LIKE 'loan_repayments_%'
ORDER BY n_dead_tup DESC;

-- Manual VACUUM on specific partition (without touching others):
VACUUM ANALYZE loan_repayments_2024_01;

-- Running VACUUM on parent cascades to all partitions:
VACUUM ANALYZE loan_repayments;
-- Equivalent to: VACUUM each child in sequence

-- ANALYZE per partition — why statistics are more accurate:
-- Non-partitioned 500M row table: ANALYZE samples ~30,000 rows
--   from 500M → 0.006% sample → poor estimates for non-uniform distributions
-- Partitioned table: ANALYZE samples 30,000 rows from each partition
--   → much higher effective sample rate per partition → better planner estimates
--   → planner knows January has 62M rows at avg $5,000 and July has 58M at avg $8,000
--   → distinct histograms per partition → accurate selectivity estimates

-- Statistics inheritance: parent table has aggregate statistics
--   (NOT the per-partition histograms — those live on child tables)
-- Planner uses child statistics when it knows which partitions to access

-- Bloat and old partitions:
-- A detached-but-not-dropped partition still needs VACUUM
-- After dropping: no ongoing maintenance needed (file is gone)
-- This is why DETACH + DROP is preferred over DELETE + VACUUM for archival

-- pg_partman autovacuum configuration per partition:
-- pg_partman can set different autovacuum thresholds per partition:
-- Recent (hot) partitions: lower threshold → vacuum more frequently
-- Old (cold) partitions: higher threshold (or disable autovacuum) → save resources
ALTER TABLE transactions_2022_01
    SET (autovacuum_enabled = false);  -- frozen old partition, no writes, no need
```

## Section 7: Scenario-Based Questions

**Q15. "Your `loan_events` table has grown to 2 billion rows over 4 years. Queries for the last 30 days are fast, but monthly reports spanning a full year take 40 minutes. How do you partition this table with zero downtime?"**

```sql
-- Strategy: range partition by created_at (monthly), migrate data with zero downtime

-- Phase 1: Create new partitioned table alongside old table
CREATE TABLE loan_events_partitioned (
    id          UUID        NOT NULL,
    loan_id     UUID        NOT NULL,
    event_type  TEXT        NOT NULL,
    payload     JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (id, created_at)           -- partition key in PK
) PARTITION BY RANGE (created_at);

-- Create partitions for all 4 years of data:
DO $$
DECLARE
    start_date DATE := '2020-01-01';
    end_date   DATE := '2025-01-01';
    current    DATE := start_date;
BEGIN
    WHILE current < end_date LOOP
        EXECUTE format(
            'CREATE TABLE loan_events_%s PARTITION OF loan_events_partitioned
             FOR VALUES FROM (%L) TO (%L)',
            to_char(current, 'YYYY_MM'),
            current,
            current + INTERVAL '1 month'
        );
        current := current + INTERVAL '1 month';
    END LOOP;
END $$;

-- Create same indexes on partitioned table:
CREATE INDEX ON loan_events_partitioned (loan_id, created_at);

-- Phase 2: Backfill historical data in batches (run over days/weeks)
-- Process old data by month to avoid locking and memory pressure:
INSERT INTO loan_events_partitioned
SELECT * FROM loan_events
WHERE created_at >= '2020-01-01' AND created_at < '2020-02-01';
-- Repeat for each month (automate with a script or pg_background)

-- Phase 3: Dual-write during cutover (application writes to BOTH tables)
-- Or: use a trigger on the old table to replicate to the new one

CREATE OR REPLACE FUNCTION replicate_to_partitioned()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO loan_events_partitioned VALUES (NEW.*);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sync_to_partitioned
    AFTER INSERT ON loan_events
    FOR EACH ROW EXECUTE FUNCTION replicate_to_partitioned();

-- Phase 4: Finish backfill for any gap between historical load and trigger creation
INSERT INTO loan_events_partitioned
SELECT * FROM loan_events le
WHERE le.created_at > (SELECT MAX(created_at) FROM loan_events_partitioned)
  AND NOT EXISTS (SELECT 1 FROM loan_events_partitioned lep WHERE lep.id = le.id);

-- Phase 5: Atomic swap (brief maintenance window — seconds, not hours)
BEGIN;
ALTER TABLE loan_events RENAME TO loan_events_old;
ALTER TABLE loan_events_partitioned RENAME TO loan_events;
-- Drop the trigger (now writing to new partitioned table directly):
DROP TRIGGER sync_to_partitioned ON loan_events_old;
COMMIT;

-- Phase 6: Drop old table after validation (days/weeks later, after confirming)
DROP TABLE loan_events_old;

-- Result: same table name, now partitioned
-- Year query: scans 12 partitions × 167M rows each (sequentially per partition)
-- vs before:  scanned 2B rows randomly → 40 min → now ~3 min
-- Recent 30-day query: scans 1-2 partitions only → same fast as before
```

**Q16. "You're designing a multi-tenant analytics table for a fintech platform with 50 enterprise tenants and 5,000 SMB tenants. Each enterprise tenant generates 10M rows/month; each SMB tenant generates 10K rows/month. Which partitioning strategy do you use?"**

```sql
-- Analysis:
-- 50 enterprise tenants × 10M rows/month = 500M rows/month
-- 5,000 SMB tenants × 10K rows/month = 50M rows/month
-- Total: ~550M rows/month
-- Enterprise = 91% of data volume; SMB = 9%

-- Option 1: RANGE by time (monthly)
-- 12 monthly partitions/year — manageable
-- All 5,050 tenants in each monthly partition
-- Tenant queries: WHERE tenant_id='T1' AND created_at >= '2024-01-01' → good pruning
-- But: large enterprise tenant's data mixed with SMBs in same partition
--      VACUUM on a partition affects all tenants → large tenants slow vacuum for all

-- Option 2: LIST by tenant_id
-- 5,050 partitions → too many (planner overhead, file descriptor limits)
-- Impractical for 5,000 SMB tenants

-- Option 3: Hybrid — RANGE by time, sub-partitioned by tenant tier
CREATE TABLE analytics_events (
    id          UUID        NOT NULL,
    tenant_id   UUID        NOT NULL,
    tenant_tier TEXT        NOT NULL,  -- 'enterprise', 'smb'
    event_type  TEXT        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (id, created_at, tenant_tier)
) PARTITION BY RANGE (created_at);

CREATE TABLE analytics_events_2024_01 PARTITION OF analytics_events
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01')
    PARTITION BY LIST (tenant_tier);

CREATE TABLE analytics_events_2024_01_enterprise PARTITION OF analytics_events_2024_01
    FOR VALUES IN ('enterprise');
CREATE TABLE analytics_events_2024_01_smb PARTITION OF analytics_events_2024_01
    FOR VALUES IN ('smb');

-- Benefits:
-- Enterprise data physically separate from SMB → VACUUM runs don't interfere
-- Enterprise queries: prune by month + prune by 'enterprise' → smaller scan
-- SMB queries: prune by month + prune by 'smb' → smaller scan
-- Index sizes: enterprise partition's index is large but contained
--              SMB partition's index is ~10× smaller (less data)

-- Query analysis:
SELECT * FROM analytics_events
WHERE tenant_id = 'ENTERPRISE_01' AND created_at >= '2024-01-01';
-- Prune: only 2024_01 range → only _enterprise sub-partition
-- Index scan on (tenant_id, created_at) within enterprise partition ✓

-- Option 4: Hash partitioning for write distribution (if write throughput is the bottleneck)
-- PARTITION BY HASH (tenant_id) with 16 partitions
-- Evenly distributes writes across 16 heap files → parallel write workers
-- Tradeoff: no time-based archival, queries for one enterprise tenant hit all 16 partitions

-- Recommended final design for this scenario:
-- Range by created_at (monthly) + sub-partition enterprise tier by hash (4 buckets)
-- Enterprise tier gets hash sub-partitioning for write parallelism
-- SMB tier stays as a single sub-partition (low volume)
CREATE TABLE analytics_events_2024_01_enterprise PARTITION OF analytics_events_2024_01
    FOR VALUES IN ('enterprise')
    PARTITION BY HASH (tenant_id);

CREATE TABLE analytics_events_2024_01_ent_p0 PARTITION OF analytics_events_2024_01_enterprise
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- ... p1, p2, p3

-- This gives:
-- Time-based archival: drop monthly partitions annually
-- Enterprise isolation: separate physical files from SMB
-- Write parallelism: 4 hash buckets for enterprise writes
-- Total leaf partitions: 12 months × (4 enterprise hash + 1 SMB) = 60 — manageable
```

**Q17. "A hash-partitioned table with 4 partitions is running out of capacity. Each partition is 500GB. You need to double the partition count to 8. Walk through the strategy."**

```sql
-- Problem: MODULUS 4 cannot be changed to MODULUS 8 in-place
-- All data must be rehashed — some rows that were in p0 belong in new p4, p5, etc.

-- Zero-downtime strategy using sub-partitioning:

-- Step 1: Convert existing hash partitions to sub-partitioned parents
-- Each existing partition becomes a parent of 2 sub-partitions
-- hash(key) % 8 = 0 maps to: hash(key) % 4 = 0 AND hash(key) % 2 = 0
-- hash(key) % 8 = 4 maps to: hash(key) % 4 = 0 AND hash(key) % 2 = 1

ALTER TABLE audit_logs_p0 PARTITION BY HASH (entity_id);

-- Step 2: Create 2 sub-partitions for each existing partition
CREATE TABLE audit_logs_p0_sub0 PARTITION OF audit_logs_p0
    FOR VALUES WITH (MODULUS 2, REMAINDER 0);
CREATE TABLE audit_logs_p0_sub1 PARTITION OF audit_logs_p0
    FOR VALUES WITH (MODULUS 2, REMAINDER 1);

-- When you ATTACH the first sub-partition:
-- PostgreSQL moves data from p0 into sub-partitions automatically
-- Existing rows are redistributed within p0 only (not cross-partition)
-- p1, p2, p3 are unchanged during this operation

-- Repeat for p1, p2, p3:
ALTER TABLE audit_logs_p1 PARTITION BY HASH (entity_id);
CREATE TABLE audit_logs_p1_sub0 PARTITION OF audit_logs_p1 FOR VALUES WITH (MODULUS 2, REMAINDER 0);
CREATE TABLE audit_logs_p1_sub1 PARTITION OF audit_logs_p1 FOR VALUES WITH (MODULUS 2, REMAINDER 1);

-- Result: 4 parent partitions, each with 2 sub-partitions = 8 effective buckets
-- Queries: pruned to parent partition first, then sub-partition → effectively 8-way split
-- No full table rewrite required

-- Alternative (if sub-partitioning is not desired): full migration approach
-- Step 1: Create new table with MODULUS 8
CREATE TABLE audit_logs_new (LIKE audit_logs INCLUDING ALL)
    PARTITION BY HASH (entity_id);

FOR i IN 0..7 LOOP
    EXECUTE format(
        'CREATE TABLE audit_logs_new_p%s PARTITION OF audit_logs_new
         FOR VALUES WITH (MODULUS 8, REMAINDER %s)', i, i
    );
END LOOP;

-- Step 2: Backfill in batches with throttling (avoid overwhelming I/O):
-- Use pagination or ctid range to process in chunks:
INSERT INTO audit_logs_new
SELECT * FROM audit_logs
WHERE ctid >= '(0,1)' AND ctid < '(100000,1)';
-- Repeat for all ctid ranges

-- Step 3: Logical replication or trigger to capture new writes during backfill

-- Step 4: Cutover (atomic rename, brief lock)
BEGIN;
ALTER TABLE audit_logs RENAME TO audit_logs_old;
ALTER TABLE audit_logs_new RENAME TO audit_logs;
COMMIT;

-- Step 5: Drop old table after validation
DROP TABLE audit_logs_old;

-- Lesson: choose initial partition count generously
-- If you expect 8 eventually, start with 8
-- Empty partitions cost nothing
```

## Quick Reference Table

| Strategy | Partition key type | Pruning works on | Best for | Cannot do |
|---|---|---|---|---|
| Range | Continuous (timestamp, integer, date) | `<`, `>`, `BETWEEN`, `=` | Time-series, sequential IDs, archival | Discrete categories, even distribution |
| List | Discrete (text, enum, UUID set) | `=`, `IN (...)` | Regions, tenants, status groups, compliance isolation | Continuous values, high cardinality (>200 values) |
| Hash | Any (UUID, text, integer) | `=` only | Write distribution, UUID keys, high-cardinality with no natural order | Range queries, time-based archival, repartitioning |

| Operation | Range | List | Hash |
|---|---|---|---|
| Add new partition | `CREATE TABLE ... FOR VALUES FROM ... TO ...` | `CREATE TABLE ... FOR VALUES IN (...)` | Cannot add — must repartition |
| Drop old data | `DROP TABLE partition` (instant) | `DROP TABLE partition` (instant) | Not applicable (no temporal ordering) |
| Partition pruning | Any comparison on key | Equality / IN on key | Equality on key only |
| Even distribution | Not guaranteed (time hotspots) | Depends on cardinality of values | Guaranteed by hash function |
| Sub-partitioning | Combine with LIST or HASH | Combine with RANGE or HASH | Combine with HASH (power-of-2 expansion) |

| Decision guide | Use this |
|---|---|
| Data grows over time, archive by age | Range (monthly or quarterly) |
| Fixed set of categories, each queried independently | List |
| UUID or high-cardinality key, write throughput focus | Hash |
| Time-series with secondary tenant dimension | Range + List sub-partition |
| Massive table, writes spread across many entities | Hash (choose count generously) |
| Need to drop old data without DELETE | Range (drop partition = instant) |
| Multi-tenant, < 200 large tenants | List (one partition per tenant) |
| Multi-tenant, thousands of small tenants | Row-level RLS, not partitioning |

**Tip for interviews:** Five things separate strong candidates on PostgreSQL partitioning: (1) explaining **what partitioning solves that indexes cannot** (Q1) — the key insight is partition pruning eliminates entire physical files from I/O, while an index still causes random heap access across the full file; and that archiving with `DROP TABLE partition` is instant vs `DELETE` + `VACUUM` which takes hours on a billion-row table; (2) knowing **partition pruning conditions precisely** (Q3) — pruning works on direct comparisons against the partition key, but is blocked by functions on the key (`date_trunc()`), non-immutable functions (`NOW()` at plan time), and implicit casts — and knowing to use `WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'` instead of `date_trunc('month', created_at) = '2024-01-01'`; (3) understanding **why the PRIMARY KEY must include the partition key** (Q13) — PostgreSQL enforces uniqueness per-partition with local indexes (no global index exists), so without the partition key in the PK, two rows with the same business key in different partitions would not conflict, violating uniqueness silently; (4) knowing **hash partitioning's repartitioning problem** (Q10, Q17) — changing `MODULUS 4` to `MODULUS 8` requires a full table rewrite (not just adding partitions), which is why you should choose the partition count generously upfront or use sub-partitioning as an incremental expansion strategy; and (5) explaining **the entity-lookup problem for range-partitioned tables** (Q12) — when the partition key is `created_at` but queries also filter by `loan_id`, all partitions must be scanned (no pruning), and the solutions (secondary lookup table, application-enforced time range, partial indexes on recent partitions) demonstrate you understand that partitioning optimizes for one access pattern and may worsen others.
