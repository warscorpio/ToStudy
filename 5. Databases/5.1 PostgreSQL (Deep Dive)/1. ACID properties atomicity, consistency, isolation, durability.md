# ACID Properties in PostgreSQL — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are ACID properties and why do they exist — what problem does each solve?**
A: ACID is a set of guarantees that a database transaction must satisfy to be considered reliable. Each property addresses a specific failure mode that arises when multiple operations must succeed or fail as a unit, or when multiple clients access the database concurrently:

```
Without ACID — what can go wrong:

  Scenario: Transfer $100 from Account A to Account B
  Step 1: Deduct $100 from A  (A: $500 → $400)
  Step 2: Add    $100 to B    (B: $200 → $300)

  Failure modes without ACID:
  ┌──────────────────────────────────────────────────────────────┐
  │ Power failure after Step 1, before Step 2:                   │
  │   A lost $100, B never received it — money vanished          │
  │   → Atomicity prevents this                                  │
  │                                                              │
  │ Balance constraint: A must not go below $0                   │
  │   Step 1 succeeds even if A only has $50                     │
  │   → Consistency prevents this                                │
  │                                                              │
  │ Concurrent reader sees A=$400 but B=$200 (mid-transfer):     │
  │   Balance sheet shows $100 less than it should               │
  │   → Isolation prevents this                                  │
  │                                                              │
  │ Transaction committed, then disk fails:                      │
  │   Committed data is lost on restart                          │
  │   → Durability prevents this                                 │
  └──────────────────────────────────────────────────────────────┘
```

```
The four properties:

  ATOMICITY   — All operations in a transaction succeed, or none do.
                "All or nothing." Partial success is impossible.
                Implemented by: rollback log (undo log / WAL)

  CONSISTENCY — A transaction brings the database from one valid state
                to another valid state. All constraints, rules, and
                invariants hold before and after.
                Implemented by: constraint checking (FK, UNIQUE, CHECK),
                triggers, application-level validation

  ISOLATION   — Concurrent transactions execute as if they were serial.
                One transaction cannot see the intermediate state of another.
                Implemented by: MVCC (Multi-Version Concurrency Control),
                locks, isolation levels

  DURABILITY  — Once a transaction is committed, it stays committed.
                Even if the server crashes immediately after COMMIT,
                the data is not lost.
                Implemented by: Write-Ahead Log (WAL), fsync, replication
```

**Q2. What is a transaction in PostgreSQL — how do you start, commit, and roll back one?**
A: A transaction is a sequence of SQL operations executed as a single logical unit. In PostgreSQL, every statement is implicitly wrapped in a transaction if not explicitly started — but implicit single-statement transactions are committed immediately:

```sql
-- Explicit transaction:
BEGIN;                          -- or START TRANSACTION;

  UPDATE accounts
  SET balance = balance - 100
  WHERE id = 'account-a';

  UPDATE accounts
  SET balance = balance + 100
  WHERE id = 'account-b';

COMMIT;                         -- Both updates committed atomically

-- OR:
ROLLBACK;                       -- Both updates undone — neither persisted
```

```sql
-- Savepoints — partial rollback within a transaction:
BEGIN;

  INSERT INTO orders (user_id, total) VALUES ('u1', 99.99)
  RETURNING id;                 -- order_id = 42

  SAVEPOINT after_order;        -- Named checkpoint

  INSERT INTO order_items (order_id, product_id, quantity)
  VALUES (42, 'prod-1', 2);

  -- Something went wrong with the item:
  ROLLBACK TO SAVEPOINT after_order;
  -- order row still exists, item insert undone

  -- Try again with corrected data:
  INSERT INTO order_items (order_id, product_id, quantity)
  VALUES (42, 'prod-2', 1);

  RELEASE SAVEPOINT after_order;  -- Optional: releases the savepoint slot

COMMIT;
-- Result: order row + corrected item row committed
```

```sql
-- Transaction status — PostgreSQL tracks state:
BEGIN;
  SELECT 1/0;    -- Division by zero — error
  -- Transaction is now in an ERROR state (aborted)
  -- ALL subsequent statements fail until rollback:
  SELECT * FROM orders;
  -- ERROR: current transaction is aborted, commands ignored until ROLLBACK

ROLLBACK;        -- Required to clear the error state

-- Checking transaction state in application code (node-postgres):
-- client.query() throws on error — wrapping in try/catch is essential:

async function transfer(from: string, to: string, amount: number): Promise<void> {
    await client.query('BEGIN');
    try {
        await client.query(
            'UPDATE accounts SET balance = balance - $1 WHERE id = $2',
            [amount, from]
        );
        await client.query(
            'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
            [amount, to]
        );
        await client.query('COMMIT');
    } catch (err) {
        await client.query('ROLLBACK');
        throw err;
    }
}
```

## Section 2: Atomicity

**Q3. How does PostgreSQL implement atomicity — what is the Write-Ahead Log (WAL)?**
A: Atomicity requires that either all operations in a transaction are applied or none are. PostgreSQL implements this through the Write-Ahead Log: every change is recorded in the log *before* it is applied to the actual data pages. On crash recovery, PostgreSQL replays the WAL to restore committed transactions and discards any uncommitted changes:

```
WAL (Write-Ahead Log) — the implementation of atomicity and durability:

  Without WAL (naive approach):
    UPDATE accounts SET balance = 400 WHERE id = 'a';
    → Write new value directly to disk page
    → Crash during write: page is half-written, corrupted
    → Database unreadable

  With WAL:
    UPDATE accounts SET balance = 400 WHERE id = 'a';
    → Step 1: Write log record to WAL file on disk
              { txn: 42, op: UPDATE, table: accounts, pk: 'a',
                old: {balance: 500}, new: {balance: 400} }
    → Step 2: Mark change in memory (shared buffer pool)
    → Step 3: Eventually write dirty page to disk (checkpoint)
    → Crash between Step 1 and Step 3: WAL exists on disk
    → On restart: PostgreSQL reads WAL, replays committed transactions,
                  discards uncommitted ones
    → Data is correct regardless of when the crash occurred
```

```sql
-- Observing WAL in PostgreSQL:

-- Current WAL write position:
SELECT pg_current_wal_lsn();
-- Returns: 0/3A8F9D0  (Log Sequence Number)

-- WAL files on disk:
-- $PGDATA/pg_wal/  ← directory containing WAL segment files
-- Each segment: 16MB by default (wal_segment_size)

-- WAL level configuration (affects what's logged):
SHOW wal_level;
-- minimal: just enough for crash recovery
-- replica: includes data for streaming replication
-- logical: includes data for logical decoding (CDC, logical replication)

-- Force a WAL flush (for durability testing):
SELECT pg_switch_wal();   -- Archives current WAL segment
```

```
WAL and atomicity — the rollback path:

  BEGIN;
    UPDATE accounts SET balance = 400 WHERE id = 'a';  -- WAL record written
    UPDATE accounts SET balance = 300 WHERE id = 'b';  -- WAL record written
  ROLLBACK;

  PostgreSQL does NOT need to "undo" disk writes because:
  1. The actual data page may still be in memory (shared buffers)
  2. The WAL records are marked as part of an aborted transaction
  3. On crash recovery: aborted transaction WAL records are ignored
  4. If data page was already written to disk:
     → PostgreSQL uses the "old" values in the WAL record to restore it
     → This is the "undo" operation — WAL stores before-images

  Shared buffer pool:
    RAM buffer between PostgreSQL and disk.
    Dirty pages (modified, not yet on disk) live here.
    Changes are visible to other connections reading from the buffer pool.
    Checkpoint process periodically flushes dirty pages to disk.
    WAL ensures any crash between writes is recoverable.
```

**Q4. What guarantees does atomicity provide at the application level — and what are its limits?**
A: Atomicity guarantees that a logical unit of work either fully succeeds or leaves no trace. But "atomic" in the database sense has precise boundaries that application code must respect:

```sql
-- Atomicity boundary 1: within a transaction, all or nothing
BEGIN;
  INSERT INTO orders (id, user_id, total) VALUES (1, 'u1', 99.99);
  INSERT INTO order_items (order_id, product_id) VALUES (1, 'prod-1');
  -- If second INSERT fails (e.g. FK violation), both are rolled back
COMMIT;
-- Guarantee: you never see an order without its items (if both succeed together)

-- Atomicity boundary 2: single statement is always atomic
UPDATE orders SET status = 'SHIPPED'
WHERE user_id = 'u1';
-- If this updates 500 rows and crashes after 300:
-- On recovery: 0 rows updated (the statement is treated as one unit)
-- You never see 300 shipped + 200 not shipped from a single UPDATE

-- Atomicity limit 1: cross-database operations
-- PostgreSQL cannot atomically span two separate database connections
-- If you update Postgres AND send an email AND write to Redis,
-- only the Postgres part is atomic.
-- Email sent → Postgres ROLLBACK → email already gone, cannot undo

-- Atomicity limit 2: external side effects
-- Calling pg_notify() inside a transaction:
BEGIN;
  INSERT INTO orders ...;
  PERFORM pg_notify('order_created', '{"id": 1}');
ROLLBACK;
-- The INSERT is rolled back, but pg_notify was already sent
-- Listeners received an event for a non-existent order
-- Solution: send notifications AFTER commit, check existence in listener
```

```typescript
// Application-level atomicity pattern — outbox table:
// Problem: atomically record an event AND publish it
// Solution: write the event to the DB in the same transaction,
//           a background process reads and publishes it

async function createOrder(data: CreateOrderData): Promise<Order> {
    const client = await pool.connect();
    try {
        await client.query('BEGIN');

        // 1. Write the order:
        const { rows: [order] } = await client.query(
            'INSERT INTO orders (user_id, total) VALUES ($1, $2) RETURNING *',
            [data.userId, data.total]
        );

        // 2. Write the event to the outbox — same transaction:
        await client.query(
            `INSERT INTO outbox_events (aggregate_id, event_type, payload)
             VALUES ($1, 'order.created', $2)`,
            [order.id, JSON.stringify(order)]
        );

        await client.query('COMMIT');
        // Both order and event row committed atomically
        // Background process (CDC or polling) reads outbox → publishes to Kafka/SQS
        // If publish fails: event stays in outbox → retry
        // Guaranteed: no order without an event, no event without an order

        return order;
    } catch (err) {
        await client.query('ROLLBACK');
        throw err;
    } finally {
        client.release();
    }
}
```

## Section 3: Consistency

**Q5. What does consistency mean in PostgreSQL — how are constraints enforced?**
A: Consistency means a transaction can only bring the database from one valid state to another valid state. "Valid" is defined by the constraints and rules declared in the schema. PostgreSQL enforces consistency through several mechanisms:

```sql
-- Constraint types in PostgreSQL:

-- 1. NOT NULL — column must have a value:
CREATE TABLE orders (
    id         UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    user_id    UUID NOT NULL,           -- Cannot insert NULL user_id
    total      NUMERIC(10,2) NOT NULL
                CONSTRAINT positive_total CHECK (total > 0),
    status     TEXT NOT NULL DEFAULT 'PENDING'
);

-- 2. UNIQUE — no duplicate values (or combinations):
CREATE TABLE users (
    id      UUID PRIMARY KEY,
    email   TEXT NOT NULL UNIQUE,       -- Per-column unique
    username TEXT NOT NULL
);
-- Multi-column unique:
CREATE UNIQUE INDEX ON order_items (order_id, product_id);
-- Same product cannot appear twice in one order

-- 3. PRIMARY KEY — unique + not null (implicit B-tree index):
-- Every table should have one. UUID vs SERIAL: UUIDs are distributed-safe.

-- 4. FOREIGN KEY — referential integrity:
CREATE TABLE order_items (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id    UUID NOT NULL REFERENCES orders(id)
                  ON DELETE CASCADE    -- Delete items when order deleted
                  ON UPDATE CASCADE,   -- Update items when order id changes
    product_id  UUID NOT NULL REFERENCES products(id)
                  ON DELETE RESTRICT,  -- Cannot delete product with existing items
    quantity    INT NOT NULL CHECK (quantity > 0)
);

-- 5. CHECK — arbitrary boolean condition:
CREATE TABLE products (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name         TEXT NOT NULL,
    price        NUMERIC(10,2) NOT NULL,
    discount_pct NUMERIC(5,2) DEFAULT 0,
    CONSTRAINT valid_price CHECK (price > 0),
    CONSTRAINT valid_discount CHECK (discount_pct BETWEEN 0 AND 100),
    CONSTRAINT discount_less_than_price CHECK (price * (1 - discount_pct/100) > 0)
);

-- 6. EXCLUSION — no overlapping ranges (calendar/booking systems):
CREATE TABLE room_bookings (
    room_id   UUID NOT NULL,
    period    TSTZRANGE NOT NULL,
    EXCLUDE USING GIST (room_id WITH =, period WITH &&)
    -- Cannot book the same room for overlapping time ranges
    -- && = overlap operator for ranges
);
```

```sql
-- Deferred constraints — checked at COMMIT, not at statement execution:
-- Useful when temporarily violating a constraint within a transaction

-- Example: swap two values that must be unique
-- Both rows have unique position values (1 and 2). To swap:
-- Standard: UPDATE position=2 WHERE id=A → violates UNIQUE (B already has 2)

CREATE TABLE ranked_items (
    id       UUID PRIMARY KEY,
    position INT NOT NULL,
    CONSTRAINT unique_position UNIQUE (position) DEFERRABLE INITIALLY DEFERRED
    --                                                       ↑ Checked at COMMIT, not each statement
);

BEGIN;
  -- These would violate UNIQUE if checked immediately:
  UPDATE ranked_items SET position = 2 WHERE id = 'item-a';  -- Both now 2
  UPDATE ranked_items SET position = 1 WHERE id = 'item-b';  -- Both now unique
COMMIT;  -- Constraint checked here — passes (positions are 1 and 2)

-- INITIALLY IMMEDIATE (default): checked after each statement
-- INITIALLY DEFERRED: checked at COMMIT
-- Can override per-transaction:
BEGIN;
  SET CONSTRAINTS unique_position DEFERRED;
  -- ... operations ...
COMMIT;
```

```sql
-- Consistency is the responsibility of BOTH the database AND the application:

-- Database enforces structural consistency (what's declarable in SQL):
ALTER TABLE accounts ADD CONSTRAINT non_negative_balance
    CHECK (balance >= 0);

-- Application enforces business consistency (what's too complex for SQL):
-- "A premium order requires at least $100 total"
-- "An order cannot be cancelled after it has shipped"
-- These live in service-layer code, not SQL constraints

-- The distinction matters: if business rule is only in the app,
-- direct DB access (psql, migrations, scripts) can violate it.
-- Critical rules should be in the DB; complex rules can be in the app.
```

**Q6. How do you implement application-level consistency with advisory locks?**
A: Some consistency requirements cannot be expressed as SQL constraints because they depend on application logic or require coordination across multiple tables. PostgreSQL's advisory locks let you implement these:

```sql
-- Advisory locks — application-defined locks, not tied to rows/tables:
-- Use case: "only one process should run the daily report generation"

-- Session-level advisory lock (held until released or session ends):
SELECT pg_try_advisory_lock(12345);   -- 12345 = application-defined lock key
-- Returns: true (acquired) or false (already held by another session)

-- Transaction-level advisory lock (released on COMMIT/ROLLBACK):
SELECT pg_try_advisory_xact_lock(12345);
-- Automatically released at end of transaction — no manual release needed
```

```typescript
// Preventing duplicate processing with advisory locks:
// Problem: multiple workers might pick up the same job

async function processUserReward(userId: string): Promise<void> {
    const client = await pool.connect();
    try {
        await client.query('BEGIN');

        // Hash the userId to a bigint lock key:
        const lockKey = hashToInt64(userId);

        const { rows } = await client.query(
            'SELECT pg_try_advisory_xact_lock($1)',
            [lockKey]
        );
        const acquired = rows[0].pg_try_advisory_xact_lock;

        if (!acquired) {
            // Another process is handling this user — skip
            await client.query('ROLLBACK');
            return;
        }

        // Locked — safe to process without race condition:
        const reward = await calculateReward(client, userId);
        await client.query(
            'INSERT INTO rewards (user_id, amount) VALUES ($1, $2)',
            [userId, reward]
        );

        await client.query('COMMIT');
        // Lock released automatically at COMMIT
    } catch (err) {
        await client.query('ROLLBACK');
        throw err;
    } finally {
        client.release();
    }
}

function hashToInt64(str: string): bigint {
    // Simple hash — in practice use a proper hash function:
    let hash = 0n;
    for (let i = 0; i < str.length; i++) {
        hash = (hash * 31n + BigInt(str.charCodeAt(i))) & 0x7FFFFFFFFFFFFFFFn;
    }
    return hash;
}
```

```sql
-- SELECT FOR UPDATE — row-level locking for read-modify-write:
-- Problem: check balance, then deduct — race condition between check and deduct

-- WRONG (race condition):
-- Connection A: SELECT balance FROM accounts WHERE id = 'a'  → 500
-- Connection B: SELECT balance FROM accounts WHERE id = 'a'  → 500
-- Connection A: UPDATE accounts SET balance = 400 WHERE id = 'a'
-- Connection B: UPDATE accounts SET balance = 400 WHERE id = 'a'  -- both deducted!

-- CORRECT:
BEGIN;
  SELECT balance FROM accounts
  WHERE id = 'account-a'
  FOR UPDATE;          -- Locks the row: other transactions block on this row
  -- balance = 500

  -- Safe to use the value — no other transaction can modify this row:
  UPDATE accounts SET balance = 400 WHERE id = 'account-a';
COMMIT;                -- Lock released

-- FOR UPDATE NOWAIT — fail immediately instead of blocking:
SELECT * FROM accounts WHERE id = 'a' FOR UPDATE NOWAIT;
-- Throws: ERROR: could not obtain lock on row in relation "accounts"

-- FOR UPDATE SKIP LOCKED — skip rows held by others (queue pattern):
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- If another worker holds a row lock, skip it and take the next available
-- Implements a concurrent work queue without blocking
```

## Section 4: Isolation

**Q7. What is MVCC and how does PostgreSQL use it to implement isolation?**
A: Multi-Version Concurrency Control (MVCC) is PostgreSQL's primary isolation mechanism. Instead of locking rows when they are read, PostgreSQL keeps multiple versions of each row and shows each transaction the version that was current when the transaction started:

```
MVCC — keeping multiple row versions:

  Row in heap storage:
  ┌──────────────────────────────────────────────────────────┐
  │ xmin │ xmax │ data                                       │
  │  101 │    0 │ { id: 'a', balance: 500 }   ← current     │
  └──────────────────────────────────────────────────────────┘

  xmin: transaction ID that CREATED this row version
  xmax: transaction ID that DELETED/UPDATED this row version (0 = still alive)

  When txn 102 updates balance to 400:
  ┌──────────────────────────────────────────────────────────┐
  │ xmin │ xmax │ data                                       │
  │  101 │  102 │ { id: 'a', balance: 500 }   ← old version │
  │  102 │    0 │ { id: 'a', balance: 400 }   ← new version │
  └──────────────────────────────────────────────────────────┘

  Txn 103 (started before 102 committed):
    Sees xmin=101 (active when 103 started), xmax=102 (102 not committed yet)
    → Reads balance: 500  ← the old version

  Txn 104 (started after 102 committed):
    Sees xmin=102 (committed), xmax=0 (alive)
    → Reads balance: 400  ← the new version

  Result: readers never block writers, writers never block readers
          Each transaction sees a consistent snapshot of the database
```

```sql
-- Observing MVCC in action:

-- Transaction ID of current transaction:
SELECT txid_current();         -- e.g. 7823

-- Snapshot: which transactions are "visible" to us:
SELECT txid_current_snapshot();
-- Returns: 7820:7824:7821
-- Format: xmin:xmax:xip_list
-- xmin=7820: all txns < 7820 are committed (visible)
-- xmax=7824: all txns >= 7824 are not yet started (invisible)
-- xip_list=7821: in-progress transactions (invisible even though < xmax)

-- See actual xmin/xmax on rows (requires casting):
SELECT id, balance, xmin, xmax
FROM accounts
WHERE id = 'account-a';
-- xmin and xmax are system columns visible with explicit SELECT
```

```sql
-- MVCC and VACUUM — cleaning up dead rows:
-- Old row versions accumulate (the 500-balance row above stays until VACUUM)
-- VACUUM identifies rows where xmax is a committed transaction (row is "dead")
-- and marks their space as reusable

-- Manual vacuum:
VACUUM accounts;              -- Removes dead rows, does not lock table
VACUUM FULL accounts;         -- Rewrites table, reclaims disk space, LOCKS table

-- Autovacuum — PostgreSQL's background cleaner:
-- Triggered when ~20% of rows in a table are dead
-- Critical for performance: without vacuum, table bloat grows and
-- transaction ID wraparound (after 2^31 transactions) corrupts data

-- Transaction ID wraparound — the VACUUM emergency:
-- PostgreSQL uses 32-bit transaction IDs (cycles every ~2 billion txns)
-- If VACUUM doesn't run and IDs wrap: old rows appear "in the future"
-- PostgreSQL enters read-only safety mode to prevent data loss
-- Monitor: SELECT age(datfrozenxid) FROM pg_database WHERE datname = current_database();
-- If age > 1.5 billion: URGENT — run VACUUM FREEZE
```

**Q8. What are the isolation levels in PostgreSQL, and what anomalies does each prevent?**
A: SQL defines four isolation levels. Each prevents a different class of concurrency anomaly. PostgreSQL implements all four, though its implementation (via MVCC) is stronger than the SQL standard requires at some levels:

```
The anomalies:

  Dirty read:     Reading uncommitted data from another transaction.
                  Txn A updates row → Txn B reads it → Txn A rolls back
                  B acted on data that never existed.

  Non-repeatable read: Reading the same row twice gets different values.
                  Txn A reads row (x=1) → Txn B updates to x=2, commits
                  → Txn A reads row again (x=2). Same query, different result.

  Phantom read:   A query returns different rows when repeated.
                  Txn A: SELECT WHERE status='pending' → 5 rows
                  Txn B: INSERT a new pending row, commits
                  Txn A: SELECT WHERE status='pending' → 6 rows (phantom appeared)

  Serialization anomaly: Result not achievable by any serial ordering.
                  (See Q9 for write skew example)
```

```sql
-- The four isolation levels:

-- READ UNCOMMITTED (weakest):
-- SQL standard: allows dirty reads.
-- PostgreSQL: treats as READ COMMITTED (dirty reads never happen with MVCC).
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- READ COMMITTED (default in PostgreSQL):
-- Prevents: dirty reads
-- Allows:   non-repeatable reads, phantom reads
-- Each STATEMENT gets a fresh snapshot of committed data.
-- Different statements in the same transaction can see different data.
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- REPEATABLE READ:
-- Prevents: dirty reads, non-repeatable reads
-- Allows:   phantom reads (in SQL standard; PostgreSQL also prevents phantoms here)
-- The transaction gets a snapshot at the START of the transaction.
-- Same query always returns same data within the transaction.
-- PostgreSQL also prevents phantom reads at this level (stronger than standard).
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- SERIALIZABLE (strongest):
-- Prevents: all anomalies including serialization anomalies (write skew)
-- Transactions execute as if they ran one at a time in some serial order.
-- PostgreSQL uses Serializable Snapshot Isolation (SSI) — predicate locking.
-- Some transactions may be aborted and need retry (serialization failures).
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

```sql
-- Demonstrating non-repeatable read under READ COMMITTED:

-- Session A:
BEGIN;  -- READ COMMITTED (default)
SELECT balance FROM accounts WHERE id = 'a';  -- Returns 500

-- Session B (runs concurrently):
BEGIN;
UPDATE accounts SET balance = 400 WHERE id = 'a';
COMMIT;

-- Session A (continues):
SELECT balance FROM accounts WHERE id = 'a';  -- Returns 400! (different result)
-- Under READ COMMITTED: each statement sees committed data at statement start
-- The second SELECT sees B's committed update
COMMIT;

-- Under REPEATABLE READ: second SELECT would still return 500
-- The snapshot was taken at transaction start — B's commit is invisible
```

```sql
-- READ COMMITTED and the TOCTOU (Time-Of-Check-Time-Of-Use) problem:

-- Inventory reservation:
BEGIN;  -- READ COMMITTED
SELECT quantity FROM inventory WHERE product_id = 'p1';
-- Returns: 5

-- (Another transaction reserves 5 items and commits here)

-- Still in our transaction:
UPDATE inventory
SET quantity = quantity - 3
WHERE product_id = 'p1'
  AND quantity >= 3;   -- Check-then-update

-- quantity is now 5 - 3 = 2? Or 0 - 3 = -2?
-- The UPDATE sees the LATEST committed data (not our earlier SELECT)
-- If the other transaction took 4, quantity is now 1
-- quantity >= 3 check sees 1 — update affects 0 rows (safe)
-- But our SELECT told us 5 was available — we may have told the user "in stock"

-- Fix: use SELECT FOR UPDATE or REPEATABLE READ + retry on conflict
```

**Q9. What is write skew and how does SERIALIZABLE isolation prevent it?**
A: Write skew is a serialization anomaly where two concurrent transactions each read overlapping data, make decisions based on what they read, and write to *different* rows — yet the combined outcome is impossible under any serial execution. It's invisible to all isolation levels below SERIALIZABLE:

```
Write skew — the on-call scheduling problem:

  Invariant: "At least one doctor must be on call at all times."
  Current state: Alice = on_call, Bob = on_call

  Txn A (Alice requesting leave):
    SELECT COUNT(*) FROM doctors WHERE on_call = true  → 2 (Alice and Bob both on)
    -- "There's another doctor on call, safe for me to take leave"
    UPDATE doctors SET on_call = false WHERE name = 'Alice'

  Txn B (Bob requesting leave, concurrent with A):
    SELECT COUNT(*) FROM doctors WHERE on_call = true  → 2 (both still on, A not committed)
    -- "There's another doctor on call, safe for me to take leave"
    UPDATE doctors SET on_call = false WHERE name = 'Bob'

  Both commit. Result: 0 doctors on call. Invariant violated.

  Why this is NOT a dirty read, non-repeatable read, or phantom:
    A reads a count (no single row changed under A during its execution)
    B reads a count (same)
    Each writes a DIFFERENT row than the other read
    Neither transaction's read set was modified — yet the outcome is wrong
```

```sql
-- Demonstrating write skew prevention with SERIALIZABLE:

CREATE TABLE doctors (
    name    TEXT PRIMARY KEY,
    on_call BOOLEAN NOT NULL
);
INSERT INTO doctors VALUES ('Alice', true), ('Bob', true);

-- Session A:
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- 2

-- Session B (concurrent):
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- 2
UPDATE doctors SET on_call = false WHERE name = 'Bob';
COMMIT;  -- Bob's leave approved

-- Session A (continues):
UPDATE doctors SET on_call = false WHERE name = 'Alice';
COMMIT;
-- ERROR: could not serialize access due to concurrent update
-- ERROR CODE: 40001 (serialization_failure)
-- PostgreSQL detected that no serial ordering of these transactions
-- produces the committed result — one must be aborted and retried

-- Application must catch 40001 and retry the transaction:
```

```typescript
// Handling serialization failures with automatic retry:
async function withSerializable<T>(
    pool: Pool,
    fn: (client: PoolClient) => Promise<T>,
    maxRetries = 5
): Promise<T> {
    for (let attempt = 0; attempt < maxRetries; attempt++) {
        const client = await pool.connect();
        try {
            await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
            const result = await fn(client);
            await client.query('COMMIT');
            return result;
        } catch (err: any) {
            await client.query('ROLLBACK');

            // Serialization failure — retry:
            if (err.code === '40001' && attempt < maxRetries - 1) {
                // Optional: exponential backoff with jitter:
                const delay = Math.min(100 * 2 ** attempt + Math.random() * 50, 2000);
                await new Promise(resolve => setTimeout(resolve, delay));
                continue;
            }
            throw err;
        } finally {
            client.release();
        }
    }
    throw new Error(`Transaction failed after ${maxRetries} attempts`);
}

// Usage:
const result = await withSerializable(pool, async (client) => {
    const { rows } = await client.query(
        'SELECT COUNT(*)::int AS count FROM doctors WHERE on_call = true'
    );
    if (rows[0].count < 2) {
        throw new Error('Cannot take leave: insufficient on-call coverage');
    }
    await client.query(
        'UPDATE doctors SET on_call = false WHERE name = $1',
        ['Alice']
    );
    return { approved: true };
});
```

```sql
-- When to use each isolation level in practice:

-- READ COMMITTED (default) — use for:
--   Most OLTP workloads: reads, simple updates, inserts
--   When conflicts are rare and the cost of retry > cost of occasional anomaly
--   Reports that can tolerate slightly stale data

-- REPEATABLE READ — use for:
--   Analytical queries that run long and must see a consistent snapshot
--   Batch jobs that SELECT then UPDATE based on the SELECT result
--   Generating reports from multiple tables (consistent view across joins)

-- SERIALIZABLE — use for:
--   Financial transactions (balance transfers, ledger entries)
--   Inventory reservation with hard limits
--   Any invariant that spans multiple rows or tables
--   Scheduling/booking systems (on-call, room booking)
--   Accept: some transactions abort and retry — this is correct behaviour

-- Rule of thumb:
--   Default to READ COMMITTED. Upgrade to SERIALIZABLE for invariants that
--   span multiple reads within one transaction. REPEATABLE READ for long readers.
```

## Section 5: Durability

**Q10. How does PostgreSQL guarantee durability — what happens between COMMIT and the data being safe?**
A: Durability means a committed transaction survives any subsequent failure — process crash, OS crash, power loss. PostgreSQL guarantees this through a combination of WAL, `fsync`, and optionally replication:

```
The COMMIT path — what happens when you COMMIT:

  1. Transaction generates WAL records for all changes
  2. WAL records written to WAL buffer (in shared memory)
  3. WAL buffer flushed to WAL files on disk (fsync)
     ← This is the durability point: data is on disk
  4. COMMIT SUCCESS returned to client
  5. (Later) Actual data pages flushed to disk at checkpoint

  If crash happens:
    After step 3: WAL on disk → replay on restart → durable ✓
    Before step 3: WAL not on disk → changes lost → rolled back on restart ✓
    (Neither case corrupts the database)

  Step 3 is the expensive one — fsync() forces OS buffer to hardware
  synchronous_commit = on (default): client waits for step 3
  synchronous_commit = off: client gets response after step 2 (faster, less durable)
```

```sql
-- Durability configuration options:

SHOW synchronous_commit;
-- on (default): wait for WAL flush to disk before confirming COMMIT
-- local: wait for local WAL flush (ignore replication lag)
-- remote_write: wait for standby to receive WAL (not necessarily flush)
-- remote_apply: wait for standby to apply WAL (strongest)
-- off: return COMMIT before WAL flush — up to ~synchronous_commit_delay ms data loss risk

-- Asynchronous commit tradeoff:
-- synchronous_commit = off: 2-3x throughput improvement for write-heavy workloads
-- Cost: up to synchronous_commit_delay (200ms default) of committed data could be lost
-- Use for: non-critical writes (analytics events, logs, session data)
-- Never use for: financial transactions, anything where data loss is unacceptable

-- Per-transaction override:
BEGIN;
  SET LOCAL synchronous_commit = off;   -- Only affects this transaction
  INSERT INTO analytics_events ...;
COMMIT;                                  -- Returns before WAL flush
```

```sql
-- Checkpoints — flushing dirty pages to disk:
-- WAL ensures durability, but data pages in shared_buffers must also reach disk
-- Checkpoint: PostgreSQL writes all dirty pages to disk and records WAL position
-- After a checkpoint, WAL before the checkpoint position is no longer needed for recovery

SHOW checkpoint_completion_target;  -- 0.9 (default): spread checkpoint I/O over 90% of interval
SHOW checkpoint_timeout;            -- 5min (default): checkpoint at least every 5 minutes
SHOW max_wal_size;                  -- 1GB (default): force checkpoint when WAL grows this large

-- After a crash and restart, PostgreSQL:
-- 1. Finds the last checkpoint record in WAL
-- 2. Replays WAL from that point forward
-- 3. Any committed transactions in WAL are applied
-- 4. Any uncommitted transactions are ignored
-- Recovery time ∝ WAL size since last checkpoint
-- Frequent checkpoints → faster recovery, more I/O during normal operation

-- Forced checkpoint (for benchmarking or maintenance):
CHECKPOINT;
```

```sql
-- Replication — extending durability across machines:

-- Streaming replication (physical):
-- Primary sends WAL stream to standby(s) in real time
-- Standby replays WAL → exact copy of primary

-- Synchronous replication — strongest durability:
-- Primary waits for standby to confirm WAL received/applied before confirming COMMIT
ALTER SYSTEM SET synchronous_standby_names = 'standby1';
-- COMMIT only returns after standby1 has received WAL (remote_write)
-- or applied it (remote_apply depending on synchronous_commit setting)
-- Cost: COMMIT latency includes network RTT to standby
-- Benefit: zero data loss even if primary fails immediately after COMMIT

-- Asynchronous replication (default):
-- Primary does not wait for standbys
-- Lag: standby may be seconds behind primary
-- If primary fails: committed transactions not yet replicated are lost
-- Benefit: no latency penalty for writes

-- Check replication lag:
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    (sent_lsn - replay_lsn) AS replication_lag_bytes
FROM pg_stat_replication;
```

```
WAL as a multi-purpose foundation:

                     │
         ┌───────────┼───────────────────┐
         ▼           ▼                   ▼
```

## Section 6: Practical Patterns

**Q12. How do you implement optimistic locking vs pessimistic locking, and when do you choose each?**
A: Locking strategy is a consistency mechanism that prevents lost updates — two concurrent transactions overwriting each other's changes. The choice is between blocking (pessimistic) and detecting-and-retrying (optimistic):

```sql
-- Pessimistic locking — block competitors at read time:
-- Use when: conflicts are frequent, transactions are short, blocking is acceptable

BEGIN;
  -- Lock the row immediately — other transactions block on this row:
  SELECT id, balance, version
  FROM accounts
  WHERE id = 'account-a'
  FOR UPDATE;               -- Row is locked until COMMIT/ROLLBACK

  -- No concurrent modification possible — safe to read-modify-write:
  UPDATE accounts
  SET balance = balance - 100
  WHERE id = 'account-a';

COMMIT;                     -- Lock released

-- FOR SHARE — allows concurrent reads but blocks writes:
SELECT * FROM products WHERE id = 'p1' FOR SHARE;
-- Other reads allowed, writes blocked
-- Use for: "I'm reading this to validate a FK, don't delete it"
```

```sql
-- Optimistic locking — detect conflicts at write time:
-- Use when: conflicts are rare, reads outnumber writes, blocking is expensive

-- Add a version column to the table:
ALTER TABLE accounts ADD COLUMN version INT NOT NULL DEFAULT 1;

-- Read the version:
SELECT id, balance, version FROM accounts WHERE id = 'account-a';
-- Returns: { id: 'account-a', balance: 500, version: 7 }

-- Update only if version hasn't changed:
UPDATE accounts
SET balance = 400,
    version = version + 1
WHERE id = 'account-a'
  AND version = 7;          -- ← Optimistic lock check

-- Check rows affected:
-- rowsAffected = 1: no one changed the row between our read and write ✓
-- rowsAffected = 0: someone else modified it — our update was rejected, retry
```

```typescript
// Optimistic locking in application code:
async function debitAccount(accountId: string, amount: number): Promise<boolean> {
    const maxRetries = 3;

    for (let attempt = 0; attempt < maxRetries; attempt++) {
        const client = await pool.connect();
        try {
            // Read current state:
            const { rows } = await client.query(
                'SELECT balance, version FROM accounts WHERE id = $1',
                [accountId]
            );
            const { balance, version } = rows[0];

            if (balance < amount) {
                throw new Error('Insufficient funds');
            }

            // Attempt update with version check:
            const result = await client.query(
                `UPDATE accounts
                 SET balance = balance - $1, version = version + 1
                 WHERE id = $2 AND version = $3`,
                [amount, accountId, version]
            );

            if (result.rowCount === 1) {
                return true;   // Success — our version matched
            }

            // Version mismatch — concurrent modification detected:
            // Retry the whole read-modify-write cycle:
            if (attempt === maxRetries - 1) {
                throw new Error('Optimistic lock failed after max retries');
            }
            // Small backoff before retry:
            await new Promise(r => setTimeout(r, 10 * (attempt + 1)));

        } finally {
            client.release();
        }
    }
    return false;
}
```

```
Pessimistic vs Optimistic — decision guide:

  Pessimistic (FOR UPDATE):
  ✓ High contention: many transactions competing for same rows
  ✓ Long transactions where retry cost is prohibitive
  ✓ Financial operations where retrying is complex
  ✗ Risk: deadlocks if multiple locks acquired in different orders
  ✗ Risk: lock contention degrades throughput under high load

  Optimistic (version column):
  ✓ Low contention: most transactions succeed without conflict
  ✓ High read-to-write ratio: reads don't block anything
  ✓ Short operations where retry is cheap
  ✗ Risk: starvation if contention is high (constant retry loops)
  ✗ Requires retry logic in application code
  ✗ Does not protect against write skew (only lost updates)
```

**Q13. How do deadlocks occur and how does PostgreSQL handle them?**
A: A deadlock occurs when two transactions each hold a lock that the other needs, creating a circular wait. PostgreSQL detects deadlocks automatically and aborts one transaction to break the cycle:

```sql
-- Classic deadlock:

-- Session A:                          -- Session B:
BEGIN;                                  BEGIN;
UPDATE accounts                         UPDATE accounts
SET balance = balance - 100             SET balance = balance + 50
WHERE id = 'account-a';   -- Locks A    WHERE id = 'account-b';  -- Locks B

-- (both proceed to the next statement)

UPDATE accounts                         UPDATE accounts
SET balance = balance + 100             SET balance = balance - 50
WHERE id = 'account-b';   -- BLOCKS!    WHERE id = 'account-a';  -- BLOCKS!
-- Waiting for B's lock on account-b   -- Waiting for A's lock on account-a
-- A waits for B, B waits for A → DEADLOCK

-- PostgreSQL detects the cycle (after deadlock_timeout, default 1s):
-- ERROR: deadlock detected
-- DETAIL: Process 12345 waits for ShareLock on transaction 67890;
--         blocked by process 54321.
--         Process 54321 waits for ShareLock on transaction 12345;
--         blocked by process 12345.
-- HINT: See server log for query details.
-- One session gets the error, the other proceeds.
```

```sql
-- Preventing deadlocks — the canonical solution:
-- Always acquire locks in a CONSISTENT ORDER across all transactions

-- BAD: Transaction A locks account-a then account-b
--      Transaction B locks account-b then account-a → potential deadlock

-- GOOD: Both transactions lock in alphabetical / ID order:
BEGIN;
  -- Always lock the lower ID first:
  SELECT * FROM accounts
  WHERE id IN ('account-a', 'account-b')
  ORDER BY id                  -- Deterministic order
  FOR UPDATE;                  -- Locks both in consistent order
  -- Now safe to proceed without deadlock risk
  UPDATE accounts SET balance = balance - 100 WHERE id = 'account-a';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'account-b';
COMMIT;
```

```typescript
// Application-level deadlock handling:
async function transfer(fromId: string, toId: string, amount: number): Promise<void> {
    const client = await pool.connect();
    try {
        await client.query('BEGIN');

        // Lock both accounts in consistent order (prevents deadlock):
        const [first, second] = [fromId, toId].sort();
        await client.query(
            'SELECT id FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE',
            [[first, second]]
        );

        // Now safely update:
        await client.query(
            'UPDATE accounts SET balance = balance - $1 WHERE id = $2',
            [amount, fromId]
        );
        await client.query(
            'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
            [amount, toId]
        );

        await client.query('COMMIT');
    } catch (err: any) {
        await client.query('ROLLBACK');

        // Deadlock detected — retry:
        if (err.code === '40P01') {
            await new Promise(r => setTimeout(r, Math.random() * 100));
            return transfer(fromId, toId, amount);   // Retry once
        }
        throw err;
    } finally {
        client.release();
    }
}
```

## Section 7: Advanced Topics

**Q14. How does PostgreSQL handle long-running transactions and what are the operational risks?**
A: Long-running transactions hold locks, prevent VACUUM from reclaiming space, and can cause significant operational problems at scale. They are the most common source of production database incidents:

```sql
-- Find long-running transactions:
SELECT
    pid,
    now() - pg_stat_activity.xact_start AS duration,
    query,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND (now() - xact_start) > interval '5 minutes'
ORDER BY duration DESC;

-- Find locks held by long-running transactions:
SELECT
    blocked_locks.pid       AS blocked_pid,
    blocked_activity.query  AS blocked_query,
    blocking_locks.pid      AS blocking_pid,
    blocking_activity.query AS blocking_query,
    now() - blocking_activity.xact_start AS blocking_duration
FROM pg_catalog.pg_locks AS blocked_locks
JOIN pg_catalog.pg_stat_activity AS blocked_activity
    ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks AS blocking_locks
    ON  blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity AS blocking_activity
    ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

```sql
-- Kill a blocking query (emergency):
SELECT pg_cancel_backend(pid);    -- Sends SIGINT — query cancelled, transaction intact
SELECT pg_terminate_backend(pid); -- Sends SIGTERM — connection terminated, transaction rolled back

-- Operational risks of long transactions:

-- Risk 1: Table bloat from VACUUM blocked
-- VACUUM cannot reclaim rows that might be visible to open transactions.
-- xmin of the oldest open transaction is the "horizon" for VACUUM.
-- A 2-hour-old transaction prevents VACUUM from cleaning 2 hours of dead rows.
-- Result: tables grow on disk, queries slow down (more pages to scan).

-- Risk 2: Replication slot lag (for logical replication)
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;
-- A transaction holding an old snapshot prevents WAL from being archived.
-- WAL accumulates, disk fills, primary panics.

-- Risk 3: Lock contention
-- Schema migrations (ALTER TABLE) require ACCESS EXCLUSIVE lock.
-- They block behind any open transactions — and block ALL new queries too.
-- 1 stuck 30-second transaction + migration attempt = database outage

-- Prevention:
-- Set idle_in_transaction_session_timeout:
ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
SELECT pg_reload_conf();
-- Automatically terminates sessions idle in a transaction for >30s
-- Prevents forgotten BEGIN; with no COMMIT
```

```sql
-- Statement timeout — prevent runaway queries:
SET statement_timeout = '10s';   -- Per-session
-- Or per-transaction:
BEGIN;
  SET LOCAL statement_timeout = '5s';
  SELECT ... expensive query ...
  -- Automatically cancelled if takes >5s
COMMIT;

-- Or globally:
ALTER SYSTEM SET statement_timeout = '30s';
-- Applies to all connections — tune to your worst-case acceptable query time
```

**Q15. How do ACID properties interact with connection pooling (PgBouncer) and ORMs like Prisma or TypeORM?**
A: Connection pooling changes the relationship between application connections and database connections. This has important implications for transactions and ACID guarantees:

```
Connection pooling modes:

  Session mode: one application connection = one database connection
    Transactions work normally — all ACID properties preserved
    Disadvantage: scales poorly (each idle app connection holds a DB connection)

  Transaction mode: application connection borrows a DB connection
    per TRANSACTION, returns it to pool after COMMIT/ROLLBACK
    Advantage: 1000 app connections can share 20 DB connections
    Disadvantage: session-level state is LOST between transactions:
      - SET LOCAL variable → lost (only persisted in session)
      - Prepared statements → not available across pool connections
      - Advisory locks (session-level) → lost
      - LISTEN/NOTIFY → broken
      - Temporary tables → lost

  Statement mode: one DB connection per statement (rarely used)
    Transactions are BROKEN — each statement may use a different connection
    Never use for transactional workloads
```

```typescript
// PgBouncer transaction mode — what breaks:

// BROKEN with transaction pooling:
// SET is session-level — next transaction may get a different connection
await client.query("SET search_path TO tenant_123, public");  // Lost after COMMIT
await client.query("SELECT * FROM orders");  // Different connection — wrong schema!

// FIX: use SET LOCAL (transaction-scoped) inside explicit transactions:
await client.query('BEGIN');
await client.query("SET LOCAL search_path TO tenant_123, public");  // Only this txn
await client.query("SELECT * FROM orders");  // Correct schema
await client.query('COMMIT');

// BROKEN: session-level advisory locks:
await client.query("SELECT pg_advisory_lock(42)");  // Acquired on connection X
// ... connection returned to pool ...
await client.query("SELECT pg_advisory_unlock(42)"); // Different connection Y — no-op!

// FIX: use transaction-level advisory locks:
BEGIN;
  SELECT pg_advisory_xact_lock(42);  -- Released on COMMIT/ROLLBACK
  -- ... critical section ...
COMMIT;
```

```typescript
// TypeORM transactions — how the ORM manages ACID:
import { DataSource, EntityManager } from 'typeorm';

// Method 1: managed transaction (recommended):
await dataSource.transaction(async (manager: EntityManager) => {
    // All operations through `manager` use the same DB connection and transaction
    const order = await manager.save(Order, { userId: 'u1', total: 99.99 });
    await manager.save(OrderItem, { orderId: order.id, productId: 'p1', quantity: 2 });
    // If either throws, TypeORM calls ROLLBACK automatically

// Method 2: manual (when you need savepoints or isolation level control):

    await queryRunner.manager.save(Order, { ... });
    await queryRunner.commitTransaction();
} catch (err) {
    await queryRunner.rollbackTransaction();
    throw err;
} finally {
    await queryRunner.release();
}

// Prisma transactions:
// Method 1: $transaction array (interactive transaction):
await prisma.$transaction([
    prisma.order.create({ data: { userId: 'u1', total: 99.99 } }),
    prisma.inventory.update({ where: { id: 'p1' }, data: { quantity: { decrement: 1 } } }),
]);

// Method 2: interactive transaction (callback — for read-then-write patterns):
await prisma.$transaction(async (tx) => {
    const inventory = await tx.inventory.findUnique({ where: { id: 'p1' } });
    if (inventory.quantity < 1) throw new Error('Out of stock');
    return tx.order.create({ data: { userId: 'u1', total: 99.99 } });
}, {
    isolationLevel: Prisma.TransactionIsolationLevel.Serializable,
    maxWait: 5000,   // Max time to wait for a connection from pool
    timeout: 10000,  // Max transaction duration
});
```

**Q16. "A financial audit reveals $200 went missing in overnight batch processing. Walk through how you'd diagnose a consistency violation."**
A: Missing money in a financial system typically means an update succeeded on one side of a transfer but not the other — an atomicity failure or a race condition that violated consistency:

```sql
-- Step 1: Check if transactions completed atomically
-- Look for the specific time window in WAL / application logs:

-- Find incomplete transfers (debit without credit):
SELECT
    t1.id AS debit_id,
    t1.account_id AS from_account,
    t1.amount,
    t1.created_at,
    t2.id AS credit_id
FROM transactions t1
LEFT JOIN transactions t2
    ON  t2.transfer_reference = t1.transfer_reference
    AND t2.type = 'credit'
WHERE t1.type = 'debit'
  AND t1.created_at BETWEEN '2024-03-15 00:00:00' AND '2024-03-15 06:00:00'
  AND t2.id IS NULL;   -- Debit exists, no matching credit
-- If rows returned: atomicity failure — BEGIN/COMMIT not wrapping both sides
```

```sql
-- Step 2: Check for double-debits (non-repeatable read or race condition):
SELECT account_id, COUNT(*) AS debit_count, SUM(amount) AS total_debited
FROM transactions
WHERE type = 'debit'
  AND transfer_reference = ANY(SELECT transfer_reference FROM transfers WHERE batch_id = 'batch-2024-0315')
GROUP BY account_id
HAVING COUNT(*) > 1;
-- If rows: same account debited multiple times for the same transfer
-- Cause: missing idempotency check, optimistic lock not enforced
```

```sql
-- Step 3: Verify running balance adds up:
SELECT
    account_id,
    SUM(CASE WHEN type = 'credit' THEN amount ELSE -amount END) AS calculated_balance,
    (SELECT balance FROM accounts WHERE id = account_id) AS stored_balance,
    SUM(CASE WHEN type = 'credit' THEN amount ELSE -amount END)
        - (SELECT balance FROM accounts WHERE id = account_id) AS discrepancy
FROM transactions
GROUP BY account_id
HAVING ABS(
    SUM(CASE WHEN type = 'credit' THEN amount ELSE -amount END)
    - (SELECT balance FROM accounts WHERE id = account_id)
) > 0.001;
-- Accounts where sum of transactions doesn't match stored balance
-- Cause: balance updated without recording the transaction, or vice versa
```

**Q17. "Your application has intermittent 'could not serialize access' errors under load. How do you reduce them without dropping to a lower isolation level?"**
A: Serialization failures under load mean transactions are genuinely conflicting — the right response is to reduce transaction scope, retry efficiently, and redesign hot paths, not to weaken isolation:

```sql
-- Step 1: Measure how often serialization failures happen:
SELECT
    count(*) FILTER (WHERE conflicts > 0) AS transactions_with_conflict,
    sum(conflicts) AS total_conflicts,
    sum(deadlocks) AS deadlocks
FROM pg_stat_database
WHERE datname = current_database();

-- Per-table conflict stats (PostgreSQL 14+):
SELECT
    relname,
    seq_scan,
    idx_scan,
    n_tup_upd,
    n_tup_ins
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC
LIMIT 10;
-- Hot tables (high n_tup_upd) are the serialization conflict source
```

```typescript
// Step 2: Reduce transaction scope — hold locks for the shortest possible time:

// BAD: Slow operation inside transaction (HTTP call inside BEGIN...COMMIT):
await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
const externalData = await fetch('https://api.partner.com/pricing');  // Network call!
// Transaction is open for the duration of the HTTP call — holding locks
await client.query('UPDATE products SET price = $1', [externalData.price]);
await client.query('COMMIT');

// GOOD: Fetch outside transaction, use inside:
const externalData = await fetch('https://api.partner.com/pricing');
await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
await client.query('UPDATE products SET price = $1', [externalData.price]);
await client.query('COMMIT');
// Transaction is open for <1ms — minimal conflict window
```

```typescript
// Step 3: Efficient retry with exponential backoff and jitter:
async function withRetry<T>(
    fn: () => Promise<T>,
    options = { maxAttempts: 5, baseDelayMs: 50 }
): Promise<T> {
    for (let attempt = 1; attempt <= options.maxAttempts; attempt++) {
        try {
            return await fn();
        } catch (err: any) {
            const isRetryable = err.code === '40001'  // Serialization failure
                             || err.code === '40P01'; // Deadlock

            if (!isRetryable || attempt === options.maxAttempts) throw err;

            // Jittered exponential backoff:
            const delay = Math.min(
                options.baseDelayMs * 2 ** (attempt - 1) + Math.random() * options.baseDelayMs,
                2000  // Cap at 2 seconds
            );
            await new Promise(r => setTimeout(r, delay));
        }
    }
    throw new Error('Unreachable');
}
```

```sql
-- Step 4: Redesign hot-path updates to reduce conflict surface:

-- BAD: Global counter (every transaction touches the same row):
UPDATE stats SET order_count = order_count + 1;  -- Serializes all order creation!

-- GOOD: Counter table with sharding (reduce contention):
-- Insert into one of N shards randomly:
INSERT INTO order_count_shards (shard_id, count)
VALUES ((RANDOM() * 100)::INT, 1)
ON CONFLICT (shard_id)
DO UPDATE SET count = order_count_shards.count + 1;

-- Read: sum all shards:
SELECT SUM(count) FROM order_count_shards;

-- BETTER for analytics: use pg_stat_user_tables or a separate analytics store
-- Don't run serializable transactions for counters at all

-- Step 5: Use SKIP LOCKED for queue-like workloads to avoid serialization:
-- Instead of SERIALIZABLE + detecting who gets the job:
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY priority DESC, created_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;    -- READ COMMITTED is sufficient for this pattern
UPDATE jobs SET status = 'processing' WHERE id = $1;
-- SKIP LOCKED prevents any serialization conflict — each worker gets a different job
```

## Quick Reference Table

| Property | What it guarantees | PostgreSQL mechanism | Common failure mode |
|---|---|---|---|
| Atomicity | All operations in a transaction succeed or none do | WAL (undo via before-images), ROLLBACK | BEGIN without COMMIT/ROLLBACK in error paths; external side effects (emails, API calls) outside the transaction |
| Consistency | Transaction brings DB from one valid state to another | Constraints (PK, FK, UNIQUE, CHECK), triggers, deferred constraints | Business rules only in app code — direct DB access bypasses them; forgetting FK constraints on join tables |
| Isolation | Concurrent transactions don't see each other's intermediate state | MVCC (row versions with xmin/xmax), isolation levels, locking | Using READ COMMITTED for read-modify-write patterns (TOCTOU race); forgetting to handle `40001` serialization failure retries |
| Durability | Committed data survives crashes | WAL fsync, checkpoints, `synchronous_commit`, replication | `synchronous_commit = off` on financial data; no replication (single point of failure); PITR not configured |
| MVCC | Readers don't block writers; each txn sees a consistent snapshot | Row versions with xmin/xmax; VACUUM cleans dead rows | Long-running transactions blocking VACUUM → table bloat; idle-in-transaction sessions holding VACUUM horizon |
| READ COMMITTED | Prevents dirty reads only; each statement gets a fresh snapshot | Default isolation level; each statement re-evaluates visibility | Using it for `SELECT count → UPDATE` patterns — count may be stale by the time UPDATE runs |
| REPEATABLE READ | Snapshot at transaction start; same query always returns same data | Snapshot taken at `BEGIN`; PostgreSQL also prevents phantoms here | Serialization anomalies (write skew) still possible — needs SERIALIZABLE for those |
| SERIALIZABLE | All anomalies prevented including write skew | SSI (Serializable Snapshot Isolation) with predicate locking | Not handling `40001` errors — application crashes instead of retrying; not reducing transaction scope first |
| `SELECT FOR UPDATE` | Exclusive row lock — blocks other updates until COMMIT | Row-level lock in lock manager | Acquiring locks in inconsistent order across transactions → deadlock (`40P01`) |
| Deadlock (`40P01`) | Circular lock wait — PostgreSQL aborts one transaction | deadlock_timeout detection, cycle detection in lock graph | Not retrying on `40P01`; not acquiring locks in consistent ID order |
| `idle_in_transaction` | Sessions with open transactions doing nothing hold VACUUM horizon | `idle_in_transaction_session_timeout` setting | Forgetting to set timeout — long-running idle transactions cause table bloat and block schema migrations |
| Outbox pattern | Atomically record event + publish it | Write event to outbox table in same transaction; background process publishes | Sending Kafka/SQS messages inside the transaction — message sent even if transaction rolls back |

---

**Tip for interviews:** Five things separate strong candidates on ACID in PostgreSQL: (1) explaining **MVCC and why readers don't block writers** — that PostgreSQL keeps multiple row versions (xmin/xmax) and each transaction sees the version that was current when its snapshot was taken, and knowing that VACUUM's job is to clean up dead row versions that no active transaction can see anymore — and that long transactions blocking VACUUM is the most common production consequence of MVCC; (2) distinguishing **the isolation levels by the specific anomaly each prevents** — being able to describe a concrete write skew scenario (the on-call doctor example), explain why it passes REPEATABLE READ's checks (neither transaction's read rows were modified), and know that SERIALIZABLE with SSI catches it via predicate locking, plus know to handle `40001` with retry; (3) knowing the **WAL's dual role** — it provides both atomicity (undo via before-images if crash before commit) and durability (redo via after-images on crash recovery), and that `synchronous_commit = on` means the client doesn't get a COMMIT response until the WAL is on disk — not until the data page is on disk (that's the checkpoint); (4) being able to articulate **the operational risk of long transactions** — that they pin the VACUUM horizon preventing dead row cleanup causing table bloat, hold locks that block DDL (ALTER TABLE) causing cascading query timeouts, and that `idle_in_transaction_session_timeout` is the operational safeguard — not being able to name this timeout is a tell that someone hasn't operated PostgreSQL in production; and (5) understanding **connection pooling's interaction with transactions** — that PgBouncer in transaction mode is incompatible with session-level advisory locks, `SET` (not `SET LOCAL`), and prepared statements, and that the fix for multi-tenant schema switching (`SET search_path`) inside a pool is `SET LOCAL` inside an explicit transaction, not a session-level SET before the transaction starts.
