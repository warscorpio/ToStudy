# Concurrency Anomalies: Dirty Read, Non-Repeatable Read, Phantom Read — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why do concurrency anomalies exist and what is the core tradeoff databases make?**
A: Concurrency anomalies exist because databases allow multiple transactions to execute simultaneously for throughput, but simultaneous access to shared data produces outcomes that would be impossible if transactions ran one at a time. The database must choose how much isolation to enforce — more isolation means fewer anomalies but more blocking and lower throughput:

```
The root problem:

  Serial execution (one at a time):
    T1 runs completely → T2 runs completely
    Zero anomalies — T2 always sees T1's fully committed result
    Throughput: 1 transaction at a time → terrible for high-load systems

  Concurrent execution (overlapping):
    T1: READ balance → ... → WRITE balance
    T2:                READ balance → ... → WRITE balance
    Overlapping reads and writes produce anomalies if not controlled

  The tradeoff:
    Full isolation (Serializable) → equivalent to serial execution
                                  → maximum correctness, minimum throughput
    No isolation (Read Uncommitted) → maximum concurrency
                                    → maximum throughput, maximum anomalies

  Three classic read anomalies (SQL standard):
    Dirty Read          — reading uncommitted data from another transaction
    Non-Repeatable Read — re-reading a row and finding it changed
    Phantom Read        — re-running a range query and finding new/missing rows

  One write anomaly (beyond the classic three):
    Write Skew         — two transactions each make consistent writes
                         that together violate an invariant
                         (covered in isolation levels — mentioned here for completeness)

Why the anomalies matter in practice:
  A financial platform making a credit decision reads account balance,
  runs eligibility logic, then writes an approval. If the balance it read
  was uncommitted, or changed between reads, the credit decision is based
  on data that doesn't reflect reality → financial loss or regulatory breach.
```

**Q2. What is a transaction and what properties must it guarantee for anomalies to be preventable?**
A: A transaction is a unit of work that satisfies ACID properties. Anomalies are breakdowns specifically in the Isolation property — understanding all four ACID properties clarifies what isolation is and is not responsible for:

```
ACID:

  Atomicity:   All operations in a transaction succeed or all are rolled back.
               Partial writes never persist.
               → Prevents corruption from crashes mid-transaction.

  Consistency: A transaction moves the database from one valid state to another.
               Application-defined constraints (CHECK, FK, UNIQUE) are enforced.
               → Prevents invalid data at the row/table level.

  Isolation:   Concurrent transactions appear to execute as if they ran serially.
               One transaction's in-progress state is invisible to others
               (to the degree the isolation level permits).
               → Prevents the three read anomalies (and write skew at Serializable).

  Durability:  Committed data survives crashes (written to WAL / redo log).
               → Prevents data loss after commit.

Isolation levels are a dial on "I" in ACID:
  Read Uncommitted  — weakest isolation, allows all three read anomalies
  Read Committed    — prevents dirty reads only
  Repeatable Read   — prevents dirty reads + non-repeatable reads (+ phantoms in PostgreSQL)
  Serializable      — prevents all anomalies including write skew

The anomalies in this guide (dirty read, non-repeatable read, phantom read)
are all violations of the Isolation property — not Atomicity, Consistency, or Durability.
```

**Q3. How do databases physically implement isolation — what mechanisms underlie anomaly prevention?**
A: Two fundamentally different approaches: lock-based concurrency control (2PL) and snapshot-based concurrency control (MVCC). Most production databases (PostgreSQL, MySQL InnoDB, Oracle) use MVCC:

```
Approach 1: Two-Phase Locking (2PL) — lock-based
  Read operation  → acquire shared lock (S lock) on rows read
  Write operation → acquire exclusive lock (X lock) on rows written
  S + S: compatible (multiple readers allowed)
  S + X: incompatible (writer blocks until reader releases)
  X + X: incompatible (writers serialize)

  Phase 1 (growing): acquire locks as needed
  Phase 2 (shrinking): release locks after commit/rollback

  Anomaly prevention:
    Dirty read prevented:     S lock on read blocks X lock from uncommitted writer
    Non-repeatable read:      S lock held until commit → writer can't modify
    Phantom read:             Range/predicate lock on the query range
  Drawback: readers block writers, writers block readers → contention

Approach 2: MVCC (Multi-Version Concurrency Control) — snapshot-based
  Each row has multiple versions stamped with transaction IDs:
    xmin: transaction that created this version
    xmax: transaction that deleted/updated this version (0 = current)

  A transaction's snapshot determines which versions it sees:
    "I can see row versions created by transactions that committed before I started"

  Example:
    Row: { id: 1, balance: 1000 }  ← created by txid 100
    T200 updates balance to 900:
      Old version: xmin=100, xmax=200, balance=1000  ← visible to snapshots < T200
      New version: xmin=200, xmax=0,   balance=900   ← visible to snapshots ≥ T200

  Anomaly prevention:
    Dirty read prevented:     snapshot only includes committed transactions
                              T200's new version invisible until T200 commits
    Non-repeatable read:      snapshot is stable — same version visible on re-read
    Phantom read:             snapshot covers the entire table state at snapshot time
  Advantage: readers never block writers, writers never block readers

PostgreSQL: pure MVCC — no read locks at any isolation level
MySQL InnoDB: MVCC for reads + gap locks for phantom prevention
SQL Server: lock-based by default, MVCC optional (snapshot isolation)
Oracle: MVCC always
```

## Section 2: Dirty Read

**Q4. What is a dirty read and why is it the most severe of the three anomalies?**
A: A dirty read occurs when transaction A reads data written by transaction B before B commits. If B then rolls back, A has operated on data that never officially existed. It is the most severe anomaly because the data read was never real — it is literally phantom data:

```
Definition: Reading uncommitted (in-progress) changes from another transaction.

Timeline:
  T1: BEGIN
  T1: UPDATE accounts SET balance = 0 WHERE id = 'A1'  ← not yet committed
  T2: SELECT balance FROM accounts WHERE id = 'A1'      ← reads 0  (dirty read!)
  T2: decides "balance is 0, reject loan application"
  T1: ROLLBACK  ← balance reverts to original value (say 50000)
  T2: has made a decision based on data that never existed

Why it is the worst anomaly:
  Non-repeatable read: you read data that was committed, then it was changed
  Phantom read:        you missed committed rows that appeared
  Dirty read:          you read data that was NEVER committed → never real
                       All decisions based on it are built on a fiction

Concrete example — loan disbursement:
  T1 (loan processor):   BEGIN
                         UPDATE loans SET disbursed_at = NOW(),
                                         disbursed_amount = 50000
                           WHERE id = 'L1'
                         -- Something fails — payment gateway error

  T2 (audit service):    SELECT disbursed_amount FROM loans WHERE id = 'L1'
                         -- Reads 50000 (dirty!)
                         -- Audit records disbursement of ₹50,000 to regulators

  T1:                    ROLLBACK  -- disbursement actually never happened

  Consequence: regulator has a false record of a disbursement that never occurred.

Database support:
  PostgreSQL:  READ UNCOMMITTED silently becomes READ COMMITTED — dirty reads
               are IMPOSSIBLE in PostgreSQL regardless of isolation level.
  MySQL:       READ UNCOMMITTED allows dirty reads.
  SQL Server:  READ UNCOMMITTED (or WITH(NOLOCK) hint) allows dirty reads.
  Oracle:      Never allows dirty reads (MVCC always on).

Dirty read is allowed at: READ UNCOMMITTED
Dirty read is prevented at: READ COMMITTED and above
```

**Q5. How does a database prevent dirty reads mechanically, and what is the cost of that prevention?**

```
Prevention via MVCC (PostgreSQL, MySQL InnoDB, Oracle):

  Uncommitted writes create new row versions with xmax = 0 (current writer's txid)
  The snapshot rule: a row version is visible only if xmin is from a COMMITTED transaction
  An uncommitted version's xmin transaction is still in progress → not in snapshot → invisible

  T1 writes { xmin=200, xmax=0, balance=0 } — T1 not yet committed
  T2's snapshot: "include only transactions that committed before I started"
  T2 starts after T1's BEGIN but before T1's COMMIT:
    T2 checks xmin=200 → is txid 200 committed? NO → version invisible to T2
    T2 falls back to previous version { xmin=100, xmax=200, balance=50000 }
    Is txid 100 committed? YES → visible
    Is xmax=200 committed? NO → this deletion not yet real → row still exists
  T2 reads balance=50000 (the pre-update value) ← no dirty read

  Cost: near zero for MVCC
    Row versions already exist for MVCC (needed for ROLLBACK anyway)
    No extra locking required
    This is why PostgreSQL does not distinguish READ UNCOMMITTED from READ COMMITTED —
    MVCC makes dirty reads impossible without any performance cost

Prevention via locking (2PL):
  T1 takes exclusive lock (X lock) on the row when writing
  T2 must take shared lock (S lock) to read the row
  S + X are incompatible → T2 BLOCKS until T1 commits or rolls back
  After T1 commits: X lock released → T2 acquires S lock → reads committed value
  After T1 rolls back: X lock released → T2 reads original value

  Cost: reads block on uncommitted writes → contention at high concurrency
        This is the overhead that MVCC eliminates

-- Demonstrating dirty read in MySQL (one of the few places you can actually trigger it):
-- Session A:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
UPDATE accounts SET balance = 0 WHERE id = 'A1';
-- Do NOT commit yet

-- Session B:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns 0 — dirty read of Session A's uncommitted write

-- Session A:
ROLLBACK;

-- Session B re-reads:
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns original value — the 0 it read earlier never existed
```

**Q6. When would an engineer deliberately use READ UNCOMMITTED despite the dirty read risk?**
A: There are narrow legitimate use cases where dirty reads are acceptable — where approximate data is better than blocking, and decisions made on it are inconsequential if the data rolls back:

```
Legitimate uses of READ UNCOMMITTED:

1. Approximate COUNT / SUM for dashboard estimates:
   "How many loan applications are pending?" for a dashboard widget
   → Exact count doesn't matter; blocking on every write is unacceptable
   → A dirty count of 1204 vs the real count of 1200 is fine for display

   SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
   SELECT COUNT(*) FROM loan_applications WHERE status = 'pending';
   -- Fast, non-blocking; slightly imprecise but acceptable for a dashboard

2. Data warehouse bulk export (append-only tables):
   Exporting from a log table where rows are only ever inserted, never updated
   → Dirty read of an uncommitted INSERT: worst case, we export a row that rolls back
   → Row is simply absent from the rolled-back state — minor gap, not a corruption

3. Progress monitoring of a long-running batch:
   A batch process updates a progress counter in a row
   → Reading the uncommitted progress gives a real-time view of completion
   → If the batch rolls back, the progress resets — acceptable

What you should NEVER use READ UNCOMMITTED for:
  ✗ Financial calculations (balance, exposure, P&L)
  ✗ Eligibility checks (credit limits, KYC status)
  ✗ Deduplication logic ("has this been processed?")
  ✗ Any decision that has real-world consequences

SQL Server WITH(NOLOCK) — common misuse:
  WITH(NOLOCK) is READ UNCOMMITTED for a single table in a query
  Widely misused as a "performance optimization" in SQL Server codebases
  Risks: dirty reads, non-repeatable reads, and can even return DUPLICATE rows
         or skip rows entirely (due to page splits during read)
  Correct use: only for genuinely approximate, inconsequential reads
```

## Section 3: Non-Repeatable Read

**Q7. What is a non-repeatable read and in what application patterns does it cause real bugs?**
A: A non-repeatable read occurs when transaction A reads a row, transaction B updates and commits that row, and transaction A reads the same row again within the same transaction and gets a different value. The same read, run twice, gives different results:

```
Definition: Within a single transaction, the same row is read twice and
            returns different values because another transaction modified
            and committed it between the two reads.

Timeline:
  T1: BEGIN
  T1: SELECT balance FROM accounts WHERE id='A1'  → 10000
                    ↕ T2 executes and commits
  T2: BEGIN
  T2: UPDATE accounts SET balance = 3000 WHERE id='A1'
  T2: COMMIT
                    ↕ T2 is done
  T1: SELECT balance FROM accounts WHERE id='A1'  → 3000  ← different!
  T1: COMMIT

  T1 read 10000, then read 3000 from the same row in the same transaction.
  Any logic in T1 that relied on the first read is now inconsistent with the second.

Patterns where this causes bugs:

Pattern 1 — Check then act (the classic):
  T1: SELECT status FROM loans WHERE id='L1'   → 'pending'
  T1: if status == 'pending': ... (other processing)
  -- (T2 updates status to 'approved' and commits)
  T1: SELECT status FROM loans WHERE id='L1'   → 'approved'  ← inconsistency
  T1: INSERT INTO audit_log(loan_id, old_status, new_status)
        VALUES ('L1', 'pending', 'approved')
  -- But T1's first read said 'pending' — audit logic is based on stale state

Pattern 2 — Two-phase validation:
  T1: SELECT balance FROM accounts WHERE id='A1'  → 10000
  T1: SELECT loan_amount FROM loans WHERE id='L1' → 8000
  -- (T2 debits account: balance now 1500)
  T1: if balance >= loan_amount: disburse()
  T1: SELECT balance FROM accounts WHERE id='A1'  → 1500  ← now fails the check!
  -- Validation result changed mid-transaction

Pattern 3 — Report aggregation:
  T1: SELECT SUM(balance) FROM accounts WHERE branch='Delhi'   → 5000000
  -- (T2 transfers funds: Delhi account debited, Mumbai account credited)
  T1: SELECT COUNT(*) FROM accounts WHERE branch='Delhi' AND balance > 0 → 98
  -- These two numbers now reflect different points in time → inconsistent report

Pattern 4 — Optimistic locking version check:
  T1: SELECT version FROM records WHERE id='R1'  → 5
  T1: ... long processing ...
  -- (T2 updates record, version is now 6)
  T1: UPDATE records SET data='...', version=6
        WHERE id='R1' AND version=5  → 0 rows updated
  -- Optimistic lock detected the change — but T1 wasted all that processing time
  -- (This is actually correct behaviour — the point is the re-read gave a different version)
```

**Q8. How do MVCC and locking each prevent non-repeatable reads, and what is the implementation difference?**

```
Prevention via MVCC (Repeatable Read isolation):

  At transaction start: snapshot is taken recording which transactions have committed
  All reads in the transaction use this SAME snapshot — frozen in time
  Even after T2 commits a new version, T1's snapshot excludes T2's txid
  → T1 always sees the same version of the row no matter how many times it reads it

  Example:
    T1 starts: snapshot = {committed txids: 1..199}
    T1 reads account A1: version with xmin=150 (committed, in snapshot) → balance=10000
    T2 (txid=210) updates A1, commits
    T1 re-reads A1: new version has xmin=210 → 210 not in snapshot → invisible
                    T1 still sees xmin=150 version → balance=10000  ← repeatable!

  Cost: snapshot is cheap (just record the txid watermark at transaction start)
        No additional locks taken for reads

Prevention via 2PL locking (Repeatable Read with shared locks):

  T1 reads a row → acquires S (shared) lock and HOLDS it until commit
  T2 tries to update that row → needs X lock → incompatible with T1's S lock → BLOCKS
  T1 commits → releases S lock → T2 unblocks and can update

  This guarantees T1's re-read returns the same value (row cannot change while T1 holds S lock)
  Cost: S locks held for the full transaction duration → writers block on all rows T1 has read
        High-read, high-write workloads suffer significant contention

Key difference:
  MVCC: T2 does NOT block — it writes its new version, commits freely
        T1 simply doesn't see T2's version (snapshot excludes it)
        Readers never block writers, writers never block readers

  2PL:  T2 BLOCKS until T1 commits — real contention, real latency
        Readers block writers on shared locks

PostgreSQL uses MVCC — setting REPEATABLE READ has zero reader-writer contention.
MySQL InnoDB uses MVCC for the re-read prevention but still uses gap locks for phantoms.

-- Demonstrating non-repeatable read in PostgreSQL at READ COMMITTED:
-- Session A:
BEGIN;  -- default: READ COMMITTED
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 10000

-- Session B:
BEGIN;
UPDATE accounts SET balance = 3000 WHERE id = 'A1';
COMMIT;

-- Session A (still in same transaction):
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 3000  ← non-repeatable read (READ COMMITTED takes new snapshot per statement)
ROLLBACK;

-- Preventing it — switch to REPEATABLE READ:
-- Session A:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 10000

-- Session B: UPDATE accounts SET balance = 3000 WHERE id = 'A1'; COMMIT;

-- Session A (same transaction, same snapshot):
SELECT balance FROM accounts WHERE id = 'A1';
-- Returns: 10000  ← snapshot frozen, non-repeatable read prevented
COMMIT;
```

**Q9. What is the "read skew" variant of non-repeatable read and how does it differ from a simple re-read?**
A: Read skew is a non-repeatable read across multiple tables or rows — you read a consistent set of related values, then a committed transaction changes some of them, and a second read of the set shows an inconsistent combination that never existed as a real database state:

```
Simple non-repeatable read: same row, read twice, different values
Read skew: related rows across tables, read in two phases, inconsistent combination

Example — bank transfer between accounts:
  Invariant: account A1 + account A2 must always sum to 100 (conservation of money)
  Initial state: A1=70, A2=30 (sum=100)

  T1 (auditor):                         T2 (transfer):
  BEGIN                                 BEGIN
  SELECT balance FROM accounts          UPDATE accounts SET balance=20 WHERE id='A1'
    WHERE id='A1'  → 70                 UPDATE accounts SET balance=80 WHERE id='A2'
                                        COMMIT
  SELECT balance FROM accounts
    WHERE id='A2'  → 80  ← T2 committed
  COMMIT

  T1 observed: A1=70, A2=80 → sum=150
  This combination (A1=70, A2=80) NEVER EXISTED as a real database state.
  T1 read A1 from the pre-transfer state and A2 from the post-transfer state.

Why it is worse than simple non-repeatable read:
  Simple: you notice balance changed, you know data moved — just re-run
  Read skew: you see a COMBINATION that was never real
             Your report shows ₹1.5 crore when only ₹1 crore exists
             An audit finding based on this is fundamentally wrong

Prevention:
  Repeatable Read / Serializable: single snapshot covers ALL reads
  Both A1 and A2 are read from the same snapshot → always consistent combination

  Under Repeatable Read:
    T1's snapshot is taken before T2's commit
    T1 reads A1=70 from snapshot ✓
    T1 reads A2=30 from same snapshot ✓  (not the post-transfer 80)
    T1 sees sum=100 ← correct, consistent

-- Read skew is the reason financial reporting requires at minimum Repeatable Read —
-- a single snapshot guarantees all reads within the transaction are from the same
-- moment in time, preventing inconsistent cross-table combinations.

-- TypeScript — wrapping a multi-table report in Repeatable Read:
async function generateBalanceReport(db: Pool): Promise<BalanceReport> {
    const client = await db.connect();
    try {
        await client.query('BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY');

        // All three queries see exactly the same database state:
        const accounts = await client.query(
            'SELECT id, balance FROM accounts WHERE active = true'
        );
        const pendingDebits = await client.query(
            'SELECT account_id, SUM(amount) AS total FROM pending_txns GROUP BY account_id'
        );
        const frozenAmounts = await client.query(
            'SELECT account_id, amount FROM frozen_funds'
        );

        await client.query('COMMIT');

        // Cross-table arithmetic is consistent — all from same snapshot:
        return buildReport(accounts.rows, pendingDebits.rows, frozenAmounts.rows);
    } finally {
        client.release();
    }
}
```

## Section 4: Phantom Read

**Q10. What is a phantom read and how does it differ structurally from a non-repeatable read?**
A: A phantom read occurs when transaction A executes a range query, transaction B inserts or deletes rows matching that range and commits, and transaction A re-executes the same range query and gets a different set of rows. The difference from non-repeatable read is about rows vs values — phantoms are about the set of rows that match a condition changing, not about a known row's value changing:

```
Non-repeatable read: a row you already KNOW ABOUT changes its values
Phantom read:        the SET OF ROWS matching your query changes
                     (new rows appear or existing rows disappear from the result set)

The "phantom" metaphor: new rows appear in or vanish from a query result
like phantoms — they weren't there before, but now they are (or vice versa)

Timeline:
  T1: BEGIN
  T1: SELECT * FROM loans WHERE amount > 100000  → { L3: 150000, L7: 200000 }

                    ↕ T2 executes and commits
  T2: BEGIN
  T2: INSERT INTO loans (id, amount) VALUES ('L11', 175000)
  T2: COMMIT

  T1: SELECT * FROM loans WHERE amount > 100000  → { L3: 150000, L7: 200000, L11: 175000 }
  T1: COMMIT

  L11 is a "phantom row" — it appeared in T1's second range query even though
  T1 never knew about it in the first query.

Non-repeatable read analogy:
  T1: SELECT amount FROM loans WHERE id='L3'  → 150000
  T2: UPDATE loans SET amount = 90000 WHERE id='L3'; COMMIT;
  T1: SELECT amount FROM loans WHERE id='L3'  → 90000  ← SAME row, DIFFERENT value

Phantom read — the new row was not in T1's first result:
  T1 does not re-read L11 specifically — L11 didn't exist in T1's first query.
  L11 is a NEW row that entered T1's search range.

Why this distinction matters for locking:
  Non-repeatable read: lock the rows you READ → writer can't change them
  Phantom read:        you cannot lock rows that DON'T EXIST YET
                       You need to lock the RANGE or PREDICATE, not specific rows
                       → This is why phantom prevention requires different mechanisms
                          (MVCC snapshot or predicate/gap locks)
```

**Q11. What are the three mechanisms databases use to prevent phantom reads, and how does each work?**

```
Mechanism 1: MVCC Snapshot (PostgreSQL Repeatable Read and above)

  Snapshot covers the ENTIRE table state at the moment it was taken.
  Any rows inserted after the snapshot's transaction ID boundary are invisible:

  T1 snapshot: committed transactions up to txid 199
  T2 (txid=210) inserts L11 and commits
  T1 re-runs range query: scans all rows with amount > 100000
    L3:  xmin=150 → in snapshot → visible
    L7:  xmin=180 → in snapshot → visible
    L11: xmin=210 → NOT in snapshot → invisible (phantom prevented!)
  T1 sees same 2 rows both times ← no phantom

  Cost: zero additional locking — snapshot naturally covers new rows
  This is why PostgreSQL's REPEATABLE READ prevents phantoms (stronger than SQL standard)

Mechanism 2: Gap Locks (MySQL InnoDB at REPEATABLE READ)

  Rows are stored in a B-tree index ordered by the indexed column.
  A gap lock locks the "gap" between existing index entries:

  Index entries for amount > 100000:
    ...(gap before L3)...[L3: 150000]...(gap)...[L7: 200000]...(gap after L7)...

  When T1 reads amount > 100000, InnoDB acquires:
    Gap lock on (100000, L3): no inserts in this range allowed
    Gap lock on (L3, L7):     no inserts in this range allowed
    Gap lock on (L7, +∞):     no inserts in this range allowed

  T2 tries INSERT INTO loans (amount) VALUES (175000):
    175000 falls in gap (L3, L7) → blocked by T1's gap lock → T2 waits
  T1 commits → gap lock released → T2 can now insert
  T1's re-read (before commit) sees the same rows ← no phantom

  Cost: real blocking — T2 is suspended until T1 commits
        Reduces concurrency for inserts in locked ranges

Mechanism 3: Predicate Locks / SIREAD Locks (PostgreSQL Serializable / SSI)

  Tracks what PREDICATES (not just rows) each transaction has read.
  Any insert that would satisfy a previously-read predicate creates a conflict:

  T1 reads: SELECT * FROM loans WHERE amount > 100000
  → PostgreSQL records: T1 has read "all loans where amount > 100000"

  T2 inserts: INSERT INTO loans (amount) VALUES (175000)
  → PostgreSQL checks: does this new row satisfy any recorded predicate?
  → 175000 > 100000 → YES → conflict with T1 → T2 gets rw-dependency with T1

  If a dangerous dependency cycle is detected: one transaction is aborted (40001)
  If no cycle: both can commit (the insert doesn't actually cause a serialization anomaly)

  This is more precise than gap locks — only aborts when there is a true anomaly,
  not just any insert in the range.

Summary:
  MVCC snapshot:    prevents phantoms by hiding post-snapshot rows (no blocking)
  Gap locks:        prevents phantoms by blocking inserts in read ranges (blocking)
  Predicate locks:  prevents phantoms + write skew by tracking read predicates (optimistic)
```

**Q12. What is the "predicate non-repeatable read" variant of phantom read and how does it apply to DELETE?**
A: A phantom read is usually illustrated with INSERT but also applies to DELETE — rows disappear from a range query between reads, which is the symmetric case. Collectively these are predicate-level anomalies — the matching set of rows changes:

```
Phantom INSERT (standard example — rows appear):
  T1: SELECT COUNT(*) FROM loans WHERE borrower='B1'  → 3
  T2: INSERT INTO loans(borrower, amount) VALUES('B1', 50000); COMMIT;
  T1: SELECT COUNT(*) FROM loans WHERE borrower='B1'  → 4  ← phantom appeared

Phantom DELETE (rows disappear):
  T1: SELECT * FROM available_slots WHERE date='2024-02-15'  → 5 slots
  T2: DELETE FROM available_slots WHERE id='S3' AND date='2024-02-15'; COMMIT;
  T1: SELECT * FROM available_slots WHERE date='2024-02-15'  → 4 slots  ← one vanished

  T1 was planning to offer slot S3 to a user — it no longer exists.
  If T1 tries to book S3: foreign key / existence check fails at booking time.

Phantom UPDATE that changes set membership:
  This is the most subtle form — a row moves INTO or OUT OF a range due to UPDATE:

  T1: SELECT * FROM loans WHERE status='pending'  → { L1, L2, L3 }
  T2: UPDATE loans SET status='approved' WHERE id='L4'; COMMIT;
  T1: SELECT * FROM loans WHERE status='pending'  → { L1, L2, L3 }
  -- L4 was never in T1's result (it wasn't pending before), so no phantom here.

  But consider:
  T2: UPDATE loans SET status='pending' WHERE id='L5'; COMMIT;
  -- L5 was 'draft', now becomes 'pending'
  T1: SELECT * FROM loans WHERE status='pending'  → { L1, L2, L3, L5 }  ← L5 is phantom!

  An UPDATE that changes a row's predicate membership is effectively:
    DELETE old version (removed from result set)
    INSERT new version (added to result set)
  MVCC handles this correctly: T1's snapshot has the pre-update version of L5
  which has status='draft' → L5 does not appear in T1's 'pending' query ← correct

-- Practical consequence of phantom DELETE in a booking system:
-- Session A (book a slot):
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT id FROM available_slots WHERE event_id='E1' AND status='open'
  LIMIT 1;                                    -- Returns S3

-- Session B (admin cancels slot):
DELETE FROM available_slots WHERE id='S3'; COMMIT;

-- Session A:
INSERT INTO bookings(slot_id, user_id) VALUES('S3', 'U7');
-- FOREIGN KEY VIOLATION: slot S3 no longer exists
-- Without isolation, this is a runtime error instead of a graceful conflict message

-- Fix: SELECT FOR UPDATE on the slot before booking
BEGIN;
SELECT id FROM available_slots
  WHERE event_id='E1' AND status='open'
  LIMIT 1
  FOR UPDATE;              -- locks S3 immediately
-- If S3 was deleted: 0 rows returned → handle gracefully
-- If S3 exists: locked → Session B's DELETE blocks until we commit
INSERT INTO bookings(slot_id, user_id) VALUES('S3', 'U7');
COMMIT;
```

## Section 5: Comparing the Three Anomalies

**Q13. What is a precise side-by-side comparison of the three anomalies and the minimum fix for each?**

```
                   │ Dirty Read            │ Non-Repeatable Read    │ Phantom Read
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Definition         │ Read uncommitted data  │ Same row read twice,   │ Range query run twice,
                   │ from another txn       │ value changed between  │ different row set
                   │                       │ reads (due to commit)  │ (insert/delete committed)
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Unit of anomaly    │ Uncommitted write      │ Committed update to    │ Committed insert or
                   │                       │ a known row            │ delete matching predicate
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
What changes       │ Data that will be      │ A row's column value   │ The COUNT / SET of rows
                   │ rolled back            │                        │ matching a WHERE clause
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Requires re-read?  │ No — single read is    │ Yes — re-read same row │ Yes — re-run same range
                   │ already wrong          │                        │ query
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Prevented by       │ READ COMMITTED         │ REPEATABLE READ        │ REPEATABLE READ (PG)
                   │                       │                        │ SERIALIZABLE (standard)
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Mechanism          │ MVCC: only committed   │ MVCC: per-txn snapshot │ MVCC: snapshot covers
                   │ versions visible       │ freezes row versions   │ entire table state
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
PostgreSQL         │ Impossible at any      │ Prevented at           │ Prevented at
                   │ isolation level        │ REPEATABLE READ+       │ REPEATABLE READ+
                   │ (MVCC always on)       │                        │ (stronger than standard)
───────────────────┼───────────────────────┼────────────────────────┼────────────────────────
Severity           │ Highest — based on     │ Medium — read data     │ Medium — query result
                   │ data that never existed│ that no longer applies │ set changed

Application-level mitigation when isolation level cannot be raised:

  Dirty read (READ UNCOMMITTED → READ COMMITTED):
    → Always use at least READ COMMITTED (default in PostgreSQL, MySQL)
    → Never use WITH(NOLOCK) in SQL Server for decision-making queries

  Non-repeatable read (READ COMMITTED → REPEATABLE READ):
    → SELECT ... FOR UPDATE on rows that must not change mid-transaction
    → Optimistic locking: version column checked at UPDATE time
    → Atomic UPDATE: fold read+write into one statement (UPDATE ... WHERE balance >= amount)

  Phantom read (READ COMMITTED / REPEATABLE READ → SERIALIZABLE or explicit locks):
    → Use REPEATABLE READ in PostgreSQL (MVCC prevents phantoms natively)
    → Use SELECT ... FOR UPDATE on the range with NOWAIT or SKIP LOCKED
    → Move business logic to a constraint: UNIQUE, CHECK, or partial index
    → Use Serializable for invariants spanning multiple rows
```

**Q14. How do you identify which anomaly is affecting your application in production?**
A: Each anomaly has a distinct symptom pattern. Matching the symptom to the anomaly guides the minimal fix:

```
Diagnostic questions:

Q: "Is the wrong value based on data that was later rolled back?"
   YES → Dirty Read
   Check: are you using READ UNCOMMITTED or WITH(NOLOCK)?
   Fix: use READ COMMITTED minimum

Q: "Did the application read the same row twice and get different values
    within the same logical operation?"
   YES → Non-Repeatable Read
   Check: multiple SELECT statements on same row across a transaction boundary
   Fix: REPEATABLE READ, FOR UPDATE, or optimistic locking version check

Q: "Did a COUNT, SUM, or result SET change size unexpectedly between two
    range queries in the same operation?"
   YES → Phantom Read
   Check: range queries (WHERE x > N, WHERE status='X') run multiple times
   Fix: REPEATABLE READ (PostgreSQL), SERIALIZABLE, or explicit range lock

Code-level signals for each:

  Dirty read signals:
    - Using READ UNCOMMITTED explicitly
    - SQL Server WITH(NOLOCK) hints on write-heavy tables
    - Symptoms: values that "shouldn't be possible" appear briefly, then vanish
                audit trail shows values that don't correspond to any committed state

  Non-repeatable read signals:
    - Transaction does a SELECT, calls a service, then does another SELECT of same data
    - Long transactions (seconds to minutes) where intervening commits are likely
    - Symptoms: validation passes but write fails; report numbers are slightly off;
                "I checked before inserting and it was fine!" type bugs

  Phantom read signals:
    - Counting rows to enforce a limit ("max 3 loans per borrower")
    - Selecting available items then booking one
    - Symptoms: COUNT was N, but constraint was violated; "impossible" duplicates;
                limit exceeded despite check

-- Logging strategy to identify the anomaly (add to debug instrumentation):
async function tracedQuery(
    client: PoolClient,
    sql: string,
    params: unknown[],
    label: string,
) {
    const result = await client.query(sql, params);
    console.log(`[${label}] rows=${result.rowCount} snapshot=${await getSnapshotInfo(client)}`);
    return result;
}

async function getSnapshotInfo(client: PoolClient) {
    const { rows } = await client.query(
        'SELECT txid_current(), pg_current_snapshot()'
    );
    return rows[0];
}

// If two calls to tracedQuery on the same table/query return different snapshot info
// under READ COMMITTED → confirms non-repeatable read / phantom opportunity
```

## Section 6: Advanced Patterns

**Q15. How do you prevent all three anomalies in a single read-modify-write pattern without changing the isolation level?**
A: Read-modify-write (check a value, compute new value, write back) is the most common pattern that suffers from all three anomalies. A set of SQL-level techniques eliminates them at READ COMMITTED by making the read and write atomic:

```sql
-- Scenario: loan exposure check — borrower must not exceed ₹500,000 total
-- Pattern 1: NAIVE (suffers dirty read, non-repeatable read, phantom) ─────────
BEGIN;
-- Read current exposure (phantom: new loans may be inserted concurrently)
SELECT SUM(amount) FROM loans WHERE borrower_id = $1 AND status = 'active';
-- Application checks: if sum + new_amount <= 500000 proceed
-- (non-repeatable: sum may change before we write)
INSERT INTO loans (borrower_id, amount, status) VALUES ($1, $2, 'active');
COMMIT;

-- Pattern 2: SELECT FOR UPDATE (prevents non-repeatable read, not phantom) ────
-- Does not help for aggregate phantom — you can't lock rows that don't exist yet
BEGIN;
SELECT SUM(amount) FROM loans WHERE borrower_id = $1 AND status = 'active'
  FOR UPDATE;                    -- locks existing active loans for this borrower
-- Prevents other writers from changing these rows
-- BUT: does not prevent INSERT of new loans by another transaction (phantom)
INSERT INTO loans (borrower_id, amount, status) VALUES ($1, $2, 'active');
COMMIT;

-- Pattern 3: Advisory lock (application-level mutex per borrower) ─────────────
-- Locks at the borrower level — prevents concurrent exposure checks for same borrower
BEGIN;
SELECT pg_advisory_xact_lock(hashtext($1));  -- lock keyed on borrower_id (released at COMMIT)
-- Now no other transaction can hold this lock for the same borrower_id
SELECT SUM(amount) FROM loans WHERE borrower_id = $1 AND status = 'active';
-- safe from phantom: concurrent insert for this borrower blocks on advisory lock
INSERT INTO loans (borrower_id, amount, status) VALUES ($1, $2, 'active');
COMMIT;

-- Pattern 4: CTE with conditional insert (atomic check-and-insert) ─────────────
-- The check and insert are one statement — no gap between read and write
WITH exposure AS (
    SELECT SUM(amount) AS total
      FROM loans
     WHERE borrower_id = $1 AND status = 'active'
),
new_loan AS (
    INSERT INTO loans (borrower_id, amount, status)
    SELECT $1, $2, 'active'
      FROM exposure
     WHERE total + $2 <= 500000         -- condition: only insert if within limit
    RETURNING id
)
SELECT id FROM new_loan;

-- If 0 rows returned: exposure limit exceeded → no insert happened
-- If 1 row returned: insert succeeded atomically
-- PostgreSQL evaluates the CTE in one execution — no concurrent insert can
-- slip between the SELECT in exposure and the INSERT in new_loan

-- Pattern 5: CHECK constraint + DEFERRED trigger (declarative invariant) ───────
-- Move the invariant into the database schema — enforced regardless of application code

-- Create a summary table maintained by triggers:
CREATE TABLE borrower_exposure (
    borrower_id UUID PRIMARY KEY,
    total_active_amount NUMERIC(15,2) DEFAULT 0
);

CREATE OR REPLACE FUNCTION update_exposure() RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO borrower_exposure (borrower_id, total_active_amount)
          VALUES (NEW.borrower_id, NEW.amount)
          ON CONFLICT (borrower_id) DO UPDATE
             SET total_active_amount = borrower_exposure.total_active_amount + NEW.amount;
    END IF;
    -- Handle UPDATE and DELETE cases...
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_exposure
  AFTER INSERT OR UPDATE OR DELETE ON loans
  FOR EACH ROW EXECUTE FUNCTION update_exposure();

ALTER TABLE borrower_exposure
  ADD CONSTRAINT chk_exposure_limit
  CHECK (total_active_amount <= 500000);

-- Now any INSERT that would exceed the limit fails with a CHECK violation
-- regardless of isolation level or application logic
```

**Q16. How does each anomaly manifest differently in an ORM (TypeORM / Prisma) vs raw SQL, and what ORM-specific pitfalls exist?**

```typescript
// ── Non-repeatable read in TypeORM (common ORM pitfall) ──────────────────────

// Pitfall: entity manager caches entities within the same transaction unit of work
// First findOne and second findOne may return the SAME JavaScript object
// (from L1 cache), hiding the non-repeatable read at the application level
// but the underlying SQL still has the anomaly

// This is DANGEROUS — the ORM masks the symptom but not the bug:
await AppDataSource.transaction(async (manager) => {
    const loan1 = await manager.findOneBy(Loan, { id: 'L1' });
    // (another transaction updates loan L1 and commits)
    const loan2 = await manager.findOneBy(Loan, { id: 'L1' });
    // TypeORM may return the SAME in-memory object for both calls
    // loan1 === loan2 (same reference) — no re-read at all in some configurations
    // You think you're safe; you're not — concurrent DB state is inconsistent
});

// Fix: use queryRunner with explicit isolation level
const queryRunner = AppDataSource.createQueryRunner();
await queryRunner.connect();
await queryRunner.startTransaction('REPEATABLE READ');
try {
    const loan1 = await queryRunner.manager.findOneBy(Loan, { id: 'L1' });
    const loan2 = await queryRunner.manager.findOneBy(Loan, { id: 'L1' });
    // Now uses actual REPEATABLE READ snapshot — loan1 values === loan2 values
    await queryRunner.commitTransaction();
} catch (err) {
    await queryRunner.rollbackTransaction();
    throw err;
} finally {
    await queryRunner.release();
}

// ── Phantom read in Prisma (aggregate queries across transaction) ─────────────

// Pitfall: Prisma's $transaction does not automatically set isolation level
// Each operation in the array gets its own statement-level snapshot (READ COMMITTED)

// WRONG — phantom-prone:
await prisma.$transaction([
    prisma.loan.count({ where: { borrowerId: 'B1', status: 'active' } }),
    prisma.loan.create({ data: { borrowerId: 'B1', amount: 50000, status: 'active' } }),
]);
// The count and the create are separate statements — another transaction
// could insert between them

// RIGHT — explicit isolation level:
await prisma.$transaction(
    async (tx) => {
        const count = await tx.loan.count({
            where: { borrowerId: 'B1', status: 'active' },
        });
        if (count >= 3) throw new Error('Max loans exceeded');
        return tx.loan.create({
            data: { borrowerId: 'B1', amount: 50000, status: 'active' },
        });
    },
    { isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead },
);

// ── Dirty read via raw query in Knex ─────────────────────────────────────────
// Knex does not expose READ UNCOMMITTED directly but raw query can:
await knex.raw('SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED');
// Subsequent queries in the connection will allow dirty reads
// This is almost always a mistake — document explicitly if intentional

// CORRECT: rely on default (READ COMMITTED) or bump up:
await knex.transaction(async (trx) => {
    await trx.raw('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ');
    const { rows } = await trx.raw(
        'SELECT SUM(amount) AS total FROM loans WHERE borrower_id = ?',
        [borrowerId],
    );
    // ... rest of logic
});
```

## Section 7: Scenario-Based Questions

**Q17. "Your CIBIL credit check service reads applicant data, calls an external CIBIL API (takes 2–3 seconds), then writes a credit decision. You're seeing decisions made on stale data. Which anomaly is this and how do you fix it?"**

```typescript
// Diagnosis: the 2–3 second external API call creates a window for concurrent
// transactions to modify applicant data between the read and the write.
// This is a NON-REPEATABLE READ — same row read implicitly at decision time
// may differ from what was read before the API call.

// The broken flow:
async function processCreditCheck(applicantId: string) {
    // Read 1: applicant data at time T
    const applicant = await db.query(
        'SELECT income, existing_loans, status FROM applicants WHERE id = $1',
        [applicantId]
    );

    // External API call: 2-3 seconds pass
    // During this time: another transaction updates existing_loans += 1 and commits
    const cibilScore = await cibilApi.check(applicant.rows[0]);

    // Decision based on STALE data (existing_loans was 2, now it's 3)
    // cibilScore was computed for the old state
    await db.query(
        'INSERT INTO credit_decisions(applicant_id, score, decision) VALUES($1, $2, $3)',
        [applicantId, cibilScore, cibilScore > 700 ? 'approved' : 'rejected']
    );
}
// Bug: decision is based on income/loans from 3 seconds ago — state changed mid-flow

// Fix 1: re-read and validate after API call (optimistic, low contention):
async function processCreditCheck(applicantId: string) {
    const before = await db.query(
        'SELECT income, existing_loans, status, updated_at FROM applicants WHERE id = $1',
        [applicantId]
    );

    const cibilScore = await cibilApi.check(before.rows[0]);

    // Re-read and compare version/timestamp:
    const after = await db.query(
        'SELECT updated_at FROM applicants WHERE id = $1', [applicantId]
    );
    if (after.rows[0].updated_at.getTime() !== before.rows[0].updated_at.getTime()) {
        throw new ConflictException('Applicant data changed during credit check — retry');
    }

    await db.query(
        'INSERT INTO credit_decisions(applicant_id, score, decision) VALUES($1, $2, $3)',
        [applicantId, cibilScore, cibilScore > 700 ? 'approved' : 'rejected']
    );
}

// Fix 2: move external call OUTSIDE the transaction (best practice):
// Do not hold a DB transaction open while calling an external API
async function processCreditCheck(applicantId: string) {
    // Short transaction 1: read snapshot
    const applicant = await db.query(
        'SELECT income, existing_loans, status, version FROM applicants WHERE id = $1',
        [applicantId]
    );
    const snapshot = applicant.rows[0];

    // External call with NO transaction open:
    const cibilScore = await cibilApi.check(snapshot);

    // Short transaction 2: write decision, verify nothing changed
    const result = await db.query(`
        INSERT INTO credit_decisions(applicant_id, score, decision)
        SELECT $1, $2, $3
          FROM applicants
         WHERE id = $1 AND version = $4   -- only insert if version unchanged
        RETURNING id
    `, [applicantId, cibilScore, cibilScore > 700 ? 'approved' : 'rejected', snapshot.version]);

    if (result.rowCount === 0) {
        throw new ConflictException('Applicant data changed — retry credit check');
    }
}
```

**Q18. "A loan limit check passes for two concurrent applications from the same borrower and both get approved, violating a 'max one active loan per borrower' rule. Which anomaly is this and what are the three ways to fix it?"**

```sql
-- Diagnosis: PHANTOM READ
-- T1 checks: SELECT COUNT(*) FROM loans WHERE borrower_id='B1' AND status='active' → 0
-- T2 checks: SELECT COUNT(*) FROM loans WHERE borrower_id='B1' AND status='active' → 0
-- T1 inserts loan (passes check)
-- T2 inserts loan (passes check — phantom: T2 didn't see T1's insert yet)
-- Both commit → 2 active loans → violation

-- Fix 1: UNIQUE partial index (database enforces the invariant) ───────────────
-- The strongest fix — makes the invariant impossible to violate regardless of
-- isolation level, application bugs, or concurrent transactions:

CREATE UNIQUE INDEX uq_one_active_loan_per_borrower
    ON loans (borrower_id)
    WHERE status = 'active';

-- Now the second INSERT fails with:
-- ERROR: duplicate key value violates unique constraint "uq_one_active_loan_per_borrower"
-- Application catches UniqueViolation (SQLSTATE 23505) and returns "loan already active"

-- Fix 2: Advisory lock (application-level serialization per borrower) ─────────
BEGIN;
SELECT pg_advisory_xact_lock(('x' || md5('loan_check_' || $1))::bit(64)::bigint);
-- Both concurrent transactions try to acquire lock keyed on borrower_id
-- Second transaction BLOCKS here until first commits
SELECT COUNT(*) FROM loans WHERE borrower_id = $1 AND status = 'active';
-- Now safe: count reflects committed state including first transaction's insert
INSERT INTO loans (borrower_id, amount, status) VALUES ($1, $2, 'active');
COMMIT;
-- Lock released

-- Fix 3: Serializable isolation (SSI detects the rw-dependency) ───────────────
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM loans WHERE borrower_id = $1 AND status = 'active';
-- PostgreSQL records predicate: "T1 read count of active loans for borrower B1"
INSERT INTO loans (borrower_id, amount, status) VALUES ($1, $2, 'active');
COMMIT;

-- When T2 also inserts for borrower B1:
-- SSI detects: T1 and T2 both read the count (which each other's insert changes)
-- → rw-dependency cycle → one transaction aborts with 40001
-- Application retries → sees count=1 → rejects second loan

-- Ranking the fixes:
-- 1. Unique partial index   → BEST: zero application code, enforced at DB level,
--                                   works regardless of isolation or app bugs
-- 2. Advisory lock          → GOOD: explicit, understandable, no isolation level change
--                                   but application must always use the lock pattern
-- 3. Serializable           → GOOD for complex invariants not expressible as constraints
--                             but requires retry logic and has higher overhead

-- TypeScript — implementing Fix 1 (catching the unique violation):
async function applyForLoan(borrowerId: string, amount: number): Promise<Loan> {
    try {
        return await prisma.loan.create({
            data: { borrowerId, amount, status: 'active' },
        });
    } catch (err) {
        if (err.code === '23505') {  // unique_violation SQLSTATE
            throw new ConflictException(
                'A loan is already active for this borrower'
            );
        }
        throw err;
    }
}
```

**Q19. "A financial report runs three queries — total disbursements, total repayments, and net outstanding — and the net outstanding doesn't match disbursements minus repayments. What is this anomaly and how do you fix it?"**

```typescript
// Diagnosis: READ SKEW (variant of non-repeatable read across tables)
// Three queries run at three different statement-level snapshots (READ COMMITTED)
// A transfer or repayment committed between queries causes inconsistency:
//
// Query 1 (snapshot at T=10:00:00): disbursements = 5,000,000
// (Repayment posted between queries)
// Query 2 (snapshot at T=10:00:01): repayments = 1,500,000  ← includes new repayment
// Query 3 (snapshot at T=10:00:01): outstanding = 3,700,000 ← also includes new repayment
//
// Disbursements - Repayments = 5,000,000 - 1,500,000 = 3,500,000
// But outstanding = 3,700,000 ← doesn't match
// Query 2 and 3 saw the repayment; Query 1 didn't → three queries from three moments

// Broken implementation:
async function generateFinancialReport(date: Date) {
    // Each query takes its own snapshot — READ COMMITTED default:
    const { rows: [{ total }] } = await db.query(
        'SELECT SUM(amount) AS total FROM disbursements WHERE date <= $1', [date]
    );
    const { rows: [{ repaid }] } = await db.query(
        'SELECT SUM(amount) AS repaid FROM repayments WHERE date <= $1', [date]
    );
    const { rows: [{ outstanding }] } = await db.query(
        'SELECT SUM(outstanding_balance) AS outstanding FROM loan_accounts', []
    );

    return { total, repaid, outstanding, check: total - repaid };
    // check !== outstanding under concurrent writes
}

// Fix: single transaction with REPEATABLE READ ─────────────────────────────────
async function generateFinancialReport(date: Date) {
    const client = await pool.connect();
    try {
        await client.query(
            'BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY'
        );
        // Single snapshot taken here — all three queries see the same state:

        const { rows: [{ total }] } = await client.query(
            'SELECT SUM(amount) AS total FROM disbursements WHERE date <= $1', [date]
        );
        const { rows: [{ repaid }] } = await client.query(
            'SELECT SUM(amount) AS repaid FROM repayments WHERE date <= $1', [date]
        );
        const { rows: [{ outstanding }] } = await client.query(
            'SELECT SUM(outstanding_balance) AS outstanding FROM loan_accounts'
        );

        await client.query('COMMIT');

        // Now guaranteed: total - repaid === outstanding (all from same snapshot)
        return { total, repaid, outstanding };
    } catch (err) {
        await client.query('ROLLBACK');
        throw err;
    } finally {
        client.release();
    }
}

// For long-running reports that risk serialization errors — use DEFERRABLE:
await client.query(
    'BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE'
);
// Waits briefly at start until a guaranteed-safe snapshot is available
// Then runs with zero risk of 40001 abort for the entire report duration
// Ideal for month-end / quarter-end financial reports that take minutes
```

## Quick Reference Table

| Anomaly | Trigger | Unit | Prevented by | PostgreSQL minimum |
|---|---|---|---|---|
| Dirty Read | Read uncommitted write | Single row, uncommitted | READ COMMITTED | Impossible (MVCC always on) |
| Non-Repeatable Read | Re-read row after commit | Single row value | REPEATABLE READ | REPEATABLE READ |
| Phantom Read | Re-run range query after insert/delete | Set of rows | SERIALIZABLE (standard) / REPEATABLE READ (PostgreSQL) | REPEATABLE READ |
| Read Skew | Read related rows across tables at different snapshots | Multiple rows/tables | REPEATABLE READ | REPEATABLE READ |
| Write Skew | Two txns each consistent, together invalid | Cross-row invariant | SERIALIZABLE | SERIALIZABLE |

| Fix technique | Prevents | Isolation level required | Notes |
|---|---|---|---|
| READ COMMITTED (default) | Dirty reads | READ COMMITTED | Default in PostgreSQL and MySQL |
| REPEATABLE READ | Dirty + non-repeatable + phantom (PostgreSQL) | REPEATABLE READ | Must retry on 40001 |
| SERIALIZABLE | All anomalies including write skew | SERIALIZABLE | SSI in PostgreSQL — optimistic, must retry |
| `SELECT FOR UPDATE` | Lost update, non-repeatable read | READ COMMITTED+ | Explicit row lock; does not prevent phantom |
| `SELECT FOR UPDATE SKIP LOCKED` | Phantom in queue patterns | READ COMMITTED | Each worker gets different rows |
| Atomic UPDATE (`SET x = x - n WHERE x >= n`) | Lost update | READ COMMITTED | No separate read needed |
| Unique/partial index | Phantom insert (specific invariants) | READ COMMITTED | Best: enforced at DB level regardless of app |
| `pg_advisory_xact_lock` | All anomalies for a specific key | READ COMMITTED | Application-level mutex; must be used consistently |
| CTE check-and-insert | Lost update + phantom | READ COMMITTED | Check and write in one atomic statement |

---

**Tip for interviews:** Five things separate strong candidates on concurrency anomalies: (1) being precise about **what changes in each anomaly** — dirty read is about uncommitted data, non-repeatable read is about a committed change to a known row's value, phantom read is about the count or set of matching rows changing — candidates who conflate them signal shallow understanding; (2) knowing that **PostgreSQL prevents dirty reads at all isolation levels** including READ UNCOMMITTED because MVCC makes uncommitted versions invisible by design, and that requesting READ UNCOMMITTED in PostgreSQL silently upgrades to READ COMMITTED; (3) explaining **why phantoms require a different prevention mechanism than non-repeatable reads** (Q11) — you can lock specific rows to prevent their values changing, but you cannot lock rows that don't exist yet, so phantom prevention requires MVCC snapshot coverage of the whole table or range/predicate locks; (4) identifying **read skew as a cross-table variant of non-repeatable read** (Q9) — a common senior-level trap question where a report shows numbers that don't add up despite each query returning correct data individually, because each query used a different statement-level snapshot under READ COMMITTED; and (5) knowing the **CTE check-and-insert pattern** (Q15) — folding a SELECT check and an INSERT into a single CTE eliminates the gap between read and write without changing isolation level, and is the most practical production fix for phantom-driven duplicate insertion bugs.
