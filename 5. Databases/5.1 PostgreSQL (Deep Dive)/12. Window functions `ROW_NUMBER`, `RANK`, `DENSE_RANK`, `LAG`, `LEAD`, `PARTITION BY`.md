## Part 1 — Theory & Interview Q&A

### Section 1: Window Function Fundamentals

**Q1. What is a window function and how does it fundamentally differ from an aggregate function?**
A: A window function performs a calculation across a set of rows that are related to the current row — its **window** — and returns a value **for every row**, preserving the full result set. An aggregate function collapses many rows into one summary row.

```sql
-- Sample data: sales table
-- | id | rep     | region | amount | month  |
-- |----|---------|--------|--------|--------|
-- |  1 | Alice   | North  |  5000  | Jan    |
-- |  2 | Bob     | North  |  3000  | Jan    |
-- |  3 | Carol   | South  |  7000  | Jan    |
-- |  4 | Alice   | North  |  6000  | Feb    |
-- |  5 | Bob     | North  |  4000  | Feb    |
-- |  6 | Carol   | South  |  8000  | Feb    |

-- Aggregate function — collapses rows, loses detail:
SELECT region, SUM(amount) AS total
FROM   sales
GROUP BY region;
-- | region | total |
-- |--------|-------|
-- | North  | 18000 |   ← 4 rows collapsed to 1
-- | South  | 15000 |   ← 2 rows collapsed to 1

-- Window function — computes across rows but keeps every row:
SELECT
  id, rep, region, amount,
  SUM(amount) OVER (PARTITION BY region) AS region_total
FROM sales;
-- | id | rep   | region | amount | region_total |
-- |----|-------|--------|--------|--------------|
-- |  1 | Alice | North  |  5000  |    18000     | ← row kept, total added
-- |  2 | Bob   | North  |  3000  |    18000     | ← row kept, same total
-- |  4 | Alice | North  |  6000  |    18000     | ← row kept, same total
-- |  5 | Bob   | North  |  4000  |    18000     | ← row kept, same total
-- |  3 | Carol | South  |  7000  |    15000     | ← different partition
-- |  6 | Carol | South  |  8000  |    15000     |

-- Key insight: window function = calculation without GROUP BY collapse
-- You get the aggregate value AND the individual row detail simultaneously
```

**Q2. What is the `OVER()` clause and what are its three components?**
A: The `OVER()` clause is what transforms a regular function into a window function. It defines the **window** — which rows the function can see when computing its result for each row. It has three optional components:

```sql
function_name() OVER (
  PARTITION BY col1, col2    -- 1. divide rows into groups (partitions)
  ORDER BY     col3 DESC     -- 2. define row order within each partition
  ROWS BETWEEN               -- 3. frame: which rows in the partition to include
    UNBOUNDED PRECEDING
    AND CURRENT ROW
)

-- Component 1: PARTITION BY
-- Divides the result set into independent groups (like GROUP BY but without collapsing)
-- The window function resets and recalculates for each partition
-- Omitting PARTITION BY → the entire result set is one partition

-- Component 2: ORDER BY (within OVER)
-- Defines the logical order of rows within each partition
-- Required for: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, running totals
-- Optional for: pure aggregates like SUM() OVER (PARTITION BY ...)

-- Component 3: Frame Specification
-- Defines which rows within the ordered partition are included in the calculation
-- Only meaningful when ORDER BY is present
-- Default frame when ORDER BY present: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
-- Default frame when ORDER BY absent: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
```

**Q3. What is the window frame and what do `ROWS` vs `RANGE` mean?**
A: The **frame** is a subset of rows within a partition. It specifies which rows are included in the calculation for each row. The frame moves with each row — for row 5, the frame might be rows 3–5; for row 6, it shifts to rows 4–6.

```sql
-- ROWS frame: physical row positions (exact row count)
-- RANGE frame: logical range of values (rows with same ORDER BY value)

-- Frame boundary keywords:
-- UNBOUNDED PRECEDING  → first row of the partition
-- N PRECEDING          → N rows before the current row
-- CURRENT ROW          → the current row itself
-- N FOLLOWING          → N rows after the current row
-- UNBOUNDED FOLLOWING  → last row of the partition

-- Running total (cumulative sum) — most common frame use:
SELECT
  month, amount,
  SUM(amount) OVER (
    ORDER BY month
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    --   ↑ every row from start to current row
  ) AS running_total
FROM monthly_sales;
-- | month | amount | running_total |
-- |-------|--------|---------------|
-- | Jan   |  5000  |     5000      |
-- | Feb   |  3000  |     8000      |  ← 5000 + 3000
-- | Mar   |  7000  |    15000      |  ← 5000 + 3000 + 7000

-- Moving average (3-month rolling window):
SELECT
  month, amount,
  AVG(amount) OVER (
    ORDER BY month
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    --           ↑ 2 rows back + current = 3-row window
  ) AS moving_avg_3mo
FROM monthly_sales;
-- | month | amount | moving_avg_3mo |
-- |-------|--------|----------------|
-- | Jan   |  5000  |  5000.00       |  ← only 1 row available
-- | Feb   |  3000  |  4000.00       |  ← (5000+3000)/2
-- | Mar   |  7000  |  5000.00       |  ← (5000+3000+7000)/3
-- | Apr   |  6000  |  5333.33       |  ← (3000+7000+6000)/3

-- ROWS vs RANGE — the critical difference:
-- ROWS counts physical rows; RANGE matches rows by ORDER BY value

-- With ties in ORDER BY (two rows both have month='Jan'):
-- ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
--   → includes exactly the rows up to (and including) the physical current row

-- RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
--   → includes all rows whose ORDER BY value ≤ current row's value
--   → ties are ALL included (even rows "after" current in physical order)

-- Practical impact:
SELECT
  rep, amount,
  SUM(amount) OVER (ORDER BY amount ROWS  BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_sum,
  SUM(amount) OVER (ORDER BY amount RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS range_sum
FROM sales;
-- | rep   | amount | rows_sum | range_sum |
-- |-------|--------|----------|-----------|
-- | Bob   |  3000  |  3000   |  3000     |
-- | Bob   |  4000  |  7000   |  7000     |
-- | Alice |  5000  | 12000   | 12000     |
-- | Alice |  6000  | 18000   | 18000     |
-- | Carol |  7000  | 25000   | 25000     |
-- | Carol |  8000  | 33000   | 33000     |
-- (no ties in this dataset — ROWS and RANGE produce the same result)

-- With ties (amount = 5000 for two rows):
-- ROWS:  each row's running_sum is computed independently (physical position)
-- RANGE: both rows with amount=5000 get the same running_sum (both treated as "at same position")
-- RANGE is the DEFAULT when ORDER BY is present — be aware of tie behavior
```

### Section 2: Ranking Functions

**Q4. What are `ROW_NUMBER`, `RANK`, and `DENSE_RANK` and how do they differ when there are ties?**
A: All three assign a number to each row within a partition based on an ORDER BY, but they handle ties differently:

```sql
-- Sample: employee salaries with ties
-- | name    | dept  | salary |
-- |---------|-------|--------|
-- | Alice   | Eng   |  90000 |
-- | Bob     | Eng   |  75000 |
-- | Carol   | Eng   |  75000 |  ← tie with Bob
-- | Dave    | Eng   |  60000 |
-- | Eve     | Sales |  80000 |
-- | Frank   | Sales |  70000 |
-- | Grace   | Sales |  70000 |  ← tie with Frank

SELECT
  name, dept, salary,
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS row_num,
  RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS dense_rnk
FROM employees;

-- | name  | dept  | salary | row_num | rnk | dense_rnk |
-- |-------|-------|--------|---------|-----|-----------|
-- | Alice | Eng   |  90000 |    1    |  1  |     1     |
-- | Bob   | Eng   |  75000 |    2    |  2  |     2     |  ← tie
-- | Carol | Eng   |  75000 |    3    |  2  |     2     |  ← tie: same rank
-- | Dave  | Eng   |  60000 |    4    |  4  |     3     |  ← after tie
-- | Eve   | Sales |  80000 |    1    |  1  |     1     |
-- | Frank | Sales |  70000 |    2    |  2  |     2     |  ← tie
-- | Grace | Sales |  70000 |    3    |  2  |     2     |  ← tie: same rank
--                                                 ↑no 3: gap after tie

-- ROW_NUMBER():
--   Always unique. Ties broken arbitrarily (or by adding more ORDER BY cols).
--   Bob and Carol both get 75000 but one gets 2, one gets 3 — deterministic
--   only if ORDER BY is fully deterministic (no ties).
--   Use when: deduplication, pagination, exactly-N-per-group.

-- RANK():
--   Ties get the SAME rank. Next rank SKIPS by the number of tied rows.
--   Bob=2, Carol=2 → Dave gets 4 (skips 3). There IS no rank 3.
--   Use when: competition-style ranking ("tied for 2nd place").

-- DENSE_RANK():
--   Ties get the SAME rank. Next rank does NOT skip.
--   Bob=2, Carol=2 → Dave gets 3. No gaps in the sequence.
--   Use when: ranking where gaps are confusing (product popularity tiers).

-- Memory device:
--   RANK:       "Olympic podium" — two silvers, no bronze
--   DENSE_RANK: "Billboard chart" — two #2 songs, next is #3 (not #4)
--   ROW_NUMBER: "Queue position" — always unique, first come first served
```

**Q5. What is `NTILE` and when would you use it over other ranking functions?**
A: `NTILE(n)` distributes rows into exactly `n` buckets (tiles) as evenly as possible and returns the bucket number. Use it for percentile analysis, creating equal-sized groups, or A/B test assignment.

```sql
-- Divide employees into 4 salary quartiles:
SELECT
  name, salary,
  NTILE(4) OVER (ORDER BY salary DESC) AS salary_quartile
FROM employees;
-- | name  | salary | salary_quartile |
-- |-------|--------|-----------------|
-- | Alice |  90000 |       1         | ← top 25% (Q1 = highest)
-- | Eve   |  80000 |       1         |
-- | Bob   |  75000 |       2         |
-- | Carol |  75000 |       2         |
-- | Frank |  70000 |       3         |
-- | Grace |  70000 |       3         |
-- | Dave  |  60000 |       4         | ← bottom 25%

-- When rows don't divide evenly:
-- NTILE distributes remainders to the first buckets
-- 7 rows into 4 tiles: bucket 1 = 2 rows, buckets 2-4 = ~1-2 rows
-- (ceil(7/4) = 2 for first 7 MOD 4 = 3 buckets, then 1 row each)

-- Practical uses:
-- 1. Percentile labels for dashboards:
SELECT
  customer_id, total_spend,
  CASE NTILE(100) OVER (ORDER BY total_spend)
    WHEN 100 THEN 'Top 1%'
    ELSE NTILE(100) OVER (ORDER BY total_spend) || 'th percentile'
  END AS percentile_label
FROM customer_stats;

-- 2. Assigning users to A/B test buckets:
SELECT
  user_id,
  NTILE(2) OVER (ORDER BY RANDOM()) AS ab_group
  -- ab_group = 1 → control, ab_group = 2 → treatment
FROM users
WHERE experiment_enrolled = true;

-- 3. Commission tiers:
SELECT
  rep, total_sales,
  CASE NTILE(3) OVER (ORDER BY total_sales DESC)
    WHEN 1 THEN 'Gold'
    WHEN 2 THEN 'Silver'
    WHEN 3 THEN 'Bronze'
  END AS commission_tier
FROM sales_reps;
```

**Q6. What are `PERCENT_RANK` and `CUME_DIST` and how are they calculated?**
A: Both return a value between 0 and 1 expressing the row's relative position within its partition:

```sql
-- PERCENT_RANK: (rank - 1) / (total rows in partition - 1)
-- → always 0 for the first row, 1 for the last
-- → how many rows are STRICTLY BELOW this row (as a proportion)

-- CUME_DIST: rank / total rows in partition
-- → never 0 (always ≥ 1/N), 1 for the last row
-- → what fraction of rows are ≤ this row's value (cumulative distribution)

SELECT
  name, salary,
  ROUND(PERCENT_RANK() OVER (ORDER BY salary), 3) AS pct_rank,
  ROUND(CUME_DIST()   OVER (ORDER BY salary), 3) AS cum_dist
FROM employees;
-- | name  | salary | pct_rank | cum_dist |
-- |-------|--------|----------|----------|
-- | Dave  |  60000 |  0.000   |  0.143   | ← lowest: pct_rank=0, cum_dist=1/7
-- | Frank |  70000 |  0.167   |  0.429   | ← tied
-- | Grace |  70000 |  0.167   |  0.429   | ← same cum_dist for ties
-- | Bob   |  75000 |  0.500   |  0.571   |
-- | Carol |  75000 |  0.500   |  0.571   |
-- | Eve   |  80000 |  0.667   |  0.714   |
-- | Alice |  90000 |  1.000   |  1.000   | ← highest: both = 1.0

-- Use case: find employees earning more than 75% of their department:
SELECT name, dept, salary
FROM (
  SELECT
    name, dept, salary,
    CUME_DIST() OVER (PARTITION BY dept ORDER BY salary) AS cd
  FROM employees
) ranked
WHERE cd >= 0.75;
```

### Section 3: Value Functions — `LAG` and `LEAD`

**Q7. What are `LAG` and `LEAD` and what are all their arguments?**
A: `LAG` and `LEAD` are **navigation functions** that access the value of a column from another row within the same partition — without a self-join. `LAG` looks backward (previous rows); `LEAD` looks forward (subsequent rows).

```sql
-- Full syntax:
LAG (expression [, offset [, default]]) OVER (partition_and_order)
LEAD(expression [, offset [, default]]) OVER (partition_and_order)

-- expression:  the column or expression whose value to retrieve
-- offset:      how many rows back (LAG) or forward (LEAD) — default 1
-- default:     value to return when the offset goes out of partition bounds — default NULL

-- Basic example: month-over-month comparison
-- | month      | revenue |
-- |------------|---------|
-- | 2024-01    |  50000  |
-- | 2024-02    |  62000  |
-- | 2024-03    |  58000  |
-- | 2024-04    |  71000  |

SELECT
  month,
  revenue,
  LAG(revenue)          OVER (ORDER BY month)    AS prev_month_rev,
  LAG(revenue, 1, 0)    OVER (ORDER BY month)    AS prev_month_rev_default0,
  LAG(revenue, 3)       OVER (ORDER BY month)    AS rev_3mo_ago,
  LEAD(revenue)         OVER (ORDER BY month)    AS next_month_rev,
  LEAD(revenue, 2)      OVER (ORDER BY month)    AS rev_2mo_ahead
FROM monthly_revenue
ORDER BY month;

-- | month   | revenue | prev_month | prev_0 | rev_3mo | next_month | 2mo_ahead |
-- |---------|---------|------------|--------|---------|------------|-----------|
-- | 2024-01 |  50000  |   NULL     |   0    |  NULL   |   62000    |   58000   |
-- | 2024-02 |  62000  |  50000     | 50000  |  NULL   |   58000    |   71000   |
-- | 2024-03 |  58000  |  62000     | 62000  |  NULL   |   71000    |   NULL    |
-- | 2024-04 |  71000  |  58000     | 58000  | 50000   |   NULL     |   NULL    |

-- Month-over-month change (absolute and percentage):
SELECT
  month,
  revenue,
  revenue - LAG(revenue) OVER (ORDER BY month)  AS mom_change,
  ROUND(
    (revenue - LAG(revenue) OVER (ORDER BY month))
    / LAG(revenue) OVER (ORDER BY month) * 100,
    2
  )                                              AS mom_pct_change
FROM monthly_revenue
ORDER BY month;
-- | month   | revenue | mom_change | mom_pct_change |
-- |---------|---------|------------|----------------|
-- | 2024-01 |  50000  |    NULL    |      NULL      |
-- | 2024-02 |  62000  |   12000    |      24.00     |
-- | 2024-03 |  58000  |   -4000    |      -6.45     |
-- | 2024-04 |  71000  |   13000    |      22.41     |
```

**Q8. How does `PARTITION BY` interact with `LAG` and `LEAD` — what happens at partition boundaries?**
A: `LAG` and `LEAD` never cross partition boundaries. The offset "wraps around" only within the same partition — at the partition boundary, the default value is returned instead. This is crucial for correct period-over-period comparisons across groups.

```sql
-- Without PARTITION BY (wrong for multi-region comparison):
SELECT
  region, month, revenue,
  LAG(revenue) OVER (ORDER BY region, month) AS prev_revenue
FROM regional_revenue;
-- | region | month   | revenue | prev_revenue |
-- |--------|---------|---------|--------------|
-- | North  | 2024-01 |  50000  |    NULL      |
-- | North  | 2024-02 |  62000  |   50000      |
-- | South  | 2024-01 |  70000  |   62000      |  ← WRONG: prev is North Feb!
-- | South  | 2024-02 |  80000  |   70000      |

-- With PARTITION BY region (correct — resets at region boundary):
SELECT
  region, month, revenue,
  LAG(revenue) OVER (PARTITION BY region ORDER BY month) AS prev_revenue
FROM regional_revenue;
-- | region | month   | revenue | prev_revenue |
-- |--------|---------|---------|--------------|
-- | North  | 2024-01 |  50000  |    NULL      |  ← partition boundary
-- | North  | 2024-02 |  62000  |   50000      |  ✓ previous North month
-- | South  | 2024-01 |  70000  |    NULL      |  ← NEW partition: resets to NULL
-- | South  | 2024-02 |  80000  |   70000      |  ✓ previous South month

-- Year-over-year comparison (LAG by 12 months within region):
SELECT
  region, month, revenue,
  LAG(revenue, 12) OVER (
    PARTITION BY region
    ORDER BY month
  ) AS revenue_same_month_prev_year,
  ROUND(
    (revenue - LAG(revenue, 12) OVER (PARTITION BY region ORDER BY month))
    / LAG(revenue, 12) OVER (PARTITION BY region ORDER BY month) * 100,
    1
  ) AS yoy_pct
FROM regional_revenue;
```

### Section 4: Other Value Functions

**Q9. What are `FIRST_VALUE`, `LAST_VALUE`, and `NTH_VALUE` and what frame gotcha must you know?**
A: These functions return the first, last, or Nth value in the window frame. `LAST_VALUE` has a critical frame trap that catches most developers off guard.

```sql
-- FIRST_VALUE: always returns the first value in the ordered window
SELECT
  name, dept, salary,
  FIRST_VALUE(name) OVER (
    PARTITION BY dept
    ORDER BY salary DESC
  ) AS highest_earner_in_dept
FROM employees;
-- Returns the name of the highest-paid person in each dept for every row

-- LAST_VALUE gotcha — the default frame is:
-- RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
-- So "last value" is actually the CURRENT ROW's value (not the last in partition!)

-- ❌ This does NOT return the lowest salary in the dept:
SELECT
  name, dept, salary,
  LAST_VALUE(salary) OVER (
    PARTITION BY dept
    ORDER BY salary DESC
    -- default frame: UNBOUNDED PRECEDING TO CURRENT ROW
    -- → "last" row in frame is always the current row
    -- → returns the CURRENT row's salary (useless!)
  ) AS wrong_last_salary
FROM employees;

-- ✓ Correct: extend frame to end of partition:
SELECT
  name, dept, salary,
  LAST_VALUE(salary) OVER (
    PARTITION BY dept
    ORDER BY salary DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    --                                   ↑ extend to end of partition
  ) AS lowest_salary_in_dept   -- now truly the last (lowest) salary
FROM employees;

-- NTH_VALUE: get the Nth row's value (1-indexed):
SELECT
  name, dept, salary,
  NTH_VALUE(salary, 2) OVER (
    PARTITION BY dept
    ORDER BY salary DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS second_highest_salary
FROM employees;
-- Returns the second-highest salary in each dept for every row in that dept
-- NULL for depts with only one employee
```

### Section 5: `PARTITION BY` Deep Dive

**Q10. What exactly does `PARTITION BY` do and how does it interact with `GROUP BY`?**
A: `PARTITION BY` divides the result set into partitions **before** the window function runs. It is conceptually like `GROUP BY` for the window calculation, but critically: it does not collapse rows. The full result set is still returned — each partition is an independent window.

```sql
-- PARTITION BY — window calculation per group, all rows preserved:
SELECT
  dept, name, salary,
  AVG(salary)   OVER (PARTITION BY dept) AS dept_avg,
  MAX(salary)   OVER (PARTITION BY dept) AS dept_max,
  COUNT(*)      OVER (PARTITION BY dept) AS dept_headcount,
  salary - AVG(salary) OVER (PARTITION BY dept) AS above_below_avg
FROM employees;
-- | dept  | name  | salary | dept_avg | dept_max | headcount | above_below |
-- |-------|-------|--------|----------|----------|-----------|-------------|
-- | Eng   | Alice |  90000 |  75000   |  90000   |     4     |   +15000    |
-- | Eng   | Bob   |  75000 |  75000   |  90000   |     4     |       0     |
-- | Eng   | Carol |  75000 |  75000   |  90000   |     4     |       0     |
-- | Eng   | Dave  |  60000 |  75000   |  90000   |     4     |   -15000    |
-- | Sales | Eve   |  80000 |  73333   |  80000   |     3     |    +6667    |
-- | Sales | Frank |  70000 |  73333   |  80000   |     3     |    -3333    |
-- | Sales | Grace |  70000 |  73333   |  80000   |     3     |    -3333    |

-- Combining GROUP BY and window functions:
-- GROUP BY happens first → then window functions apply to the grouped result:
SELECT
  dept,
  SUM(salary)  AS total_salary,
  AVG(salary)  AS dept_avg,
  -- Window function on the grouped result — each dept row sees ALL depts:
  SUM(SUM(salary)) OVER ()     AS company_total,
  ROUND(
    SUM(salary) / SUM(SUM(salary)) OVER () * 100,
    1
  )                            AS pct_of_company_payroll
FROM employees
GROUP BY dept;
-- | dept  | total_salary | dept_avg | company_total | pct_payroll |
-- |-------|--------------|----------|---------------|-------------|
-- | Eng   |    300000    |  75000   |    510000     |    58.8%    |
-- | Sales |    220000    |  73333   |    510000     |    41.2%    |
-- SUM(SUM(salary)) OVER () — nested aggregate as window function
-- inner SUM: per-dept total (from GROUP BY)
-- outer SUM OVER(): sum of all dept totals = company total

-- Multiple PARTITION BY columns:
SELECT
  dept, job_level, name, salary,
  AVG(salary) OVER (PARTITION BY dept, job_level) AS level_avg_in_dept,
  RANK()      OVER (PARTITION BY dept, job_level ORDER BY salary DESC) AS rank_in_level
FROM employees;
-- Partitions by (dept, job_level) combinations:
-- Eng/Senior: its own window
-- Eng/Junior: its own window
-- Sales/Senior: its own window
```

**Q11. How does omitting `PARTITION BY` affect window function behavior?**
A: Without `PARTITION BY`, the entire result set (or the set filtered by `WHERE`) is treated as one single partition. Every row in the result sees the same window — every other row. This is correct for company-wide rankings or running totals, but wrong if you want per-group calculations.

```sql
-- Without PARTITION BY: all rows are one partition
SELECT
  name, dept, salary,
  RANK() OVER (ORDER BY salary DESC) AS company_rank  -- rank across entire company
FROM employees;
-- | name  | dept  | salary | company_rank |
-- |-------|-------|--------|--------------|
-- | Alice | Eng   |  90000 |      1       |
-- | Eve   | Sales |  80000 |      2       |
-- | Bob   | Eng   |  75000 |      3       |
-- | Carol | Eng   |  75000 |      3       |
-- | Frank | Sales |  70000 |      5       |
-- | Grace | Sales |  70000 |      5       |
-- | Dave  | Eng   |  60000 |      7       |

-- With PARTITION BY dept: rank within each department separately
SELECT
  name, dept, salary,
  RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS dept_rank
FROM employees;
-- | name  | dept  | salary | dept_rank |
-- |-------|-------|--------|-----------|
-- | Alice | Eng   |  90000 |     1     |  ← rank 1 in Eng
-- | Eve   | Sales |  80000 |     1     |  ← rank 1 in Sales (separate ranking)
-- Ranks restart at 1 for each partition

-- Running total — company-wide (no partition):
SELECT
  month, revenue,
  SUM(revenue) OVER (ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
    AS cumulative_revenue
FROM monthly_revenue;

-- Running total — per region (with partition):
SELECT
  region, month, revenue,
  SUM(revenue) OVER (
    PARTITION BY region
    ORDER BY month
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS cumulative_revenue_per_region
FROM monthly_revenue;
```

### Section 6: Performance and Execution

**Q12. How does the SQL engine execute window functions and what are the performance implications?**
A: Window functions execute in a specific phase of query processing — after `WHERE`, `JOIN`, and `GROUP BY`, but before `HAVING`, `ORDER BY`, and `LIMIT`. This positioning has important consequences:

```sql
-- Query execution order (conceptual):
-- 1. FROM / JOIN        → build the full joined result set
-- 2. WHERE              → filter rows
-- 3. GROUP BY           → aggregate (if present)
-- 4. HAVING             → filter aggregated groups
-- 5. [Window functions computed here — on the result of steps 1-4]
-- 6. SELECT             → project columns (window functions resolved here)
-- 7. DISTINCT
-- 8. ORDER BY
-- 9. LIMIT / OFFSET

-- Consequence 1: window functions CAN'T be used in WHERE or HAVING directly
-- ❌ This fails — window function not yet computed when WHERE runs:
SELECT name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
FROM employees
WHERE rn = 1;   -- ERROR: column "rn" does not exist (window not computed yet)

-- ✓ Must wrap in a subquery or CTE:
WITH ranked AS (
  SELECT name, dept, salary,
         ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT name, dept, salary
FROM ranked
WHERE rn = 1;   -- filter AFTER window function is computed

-- Consequence 2: multiple window functions on same OVER() spec
-- DB optimizer may reuse the same sort pass for identical OVER() specs:
SELECT
  name, salary,
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn,
  RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS drk
  -- Same OVER() clause → one sort pass for all three ✓
FROM employees;

-- vs. different OVER() specs → multiple sort passes:
SELECT
  name, salary,
  RANK() OVER (PARTITION BY dept   ORDER BY salary DESC) AS dept_rank,
  RANK() OVER (PARTITION BY region ORDER BY salary DESC) AS region_rank
  -- Different PARTITION BY → two separate sort + window operations
FROM employees;

-- Consequence 3: PARTITION BY on high-cardinality columns is expensive
-- Each partition = a segment that must be sorted independently
-- Low-cardinality PARTITION BY (dept = 5 values): efficient
-- High-cardinality PARTITION BY (user_id = 10M values): very expensive
-- → consider pre-aggregating or indexing on partition columns

-- Indexes that help window functions:
-- CREATE INDEX idx_emp_dept_salary ON employees (dept, salary DESC);
-- → covers PARTITION BY dept ORDER BY salary DESC
-- → can use index scan instead of sort
```

**Q13. How do you use multiple window specifications efficiently — the `WINDOW` clause?**
A: The `WINDOW` clause (supported by PostgreSQL, MySQL 8+, SQL Server 2022+) lets you name a window specification and reuse it, avoiding repetition and helping the optimizer reuse sort passes.

```sql
-- Without WINDOW clause — repetitive and potentially multiple sort passes:
SELECT
  name, dept, salary,
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn,
  RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS drk,
  FIRST_VALUE(name) OVER (PARTITION BY dept ORDER BY salary DESC) AS top_earner,
  LAG(salary)  OVER (PARTITION BY dept ORDER BY salary DESC) AS prev_salary
FROM employees;

-- With WINDOW clause — DRY and optimizer-friendly:
SELECT
  name, dept, salary,
  ROW_NUMBER()      OVER w AS rn,
  RANK()            OVER w AS rnk,
  DENSE_RANK()      OVER w AS drk,
  FIRST_VALUE(name) OVER w AS top_earner,
  LAG(salary)       OVER w AS prev_salary
FROM employees
WINDOW w AS (PARTITION BY dept ORDER BY salary DESC);
-- One named window → optimizer sorts once, runs all functions on that sort

-- Multiple named windows:
SELECT
  name, dept, region, salary,
  RANK() OVER dept_window   AS dept_rank,
  RANK() OVER region_window AS region_rank,
  SUM(salary) OVER dept_window AS dept_total   -- reuse same window for aggregate
FROM employees
WINDOW
  dept_window   AS (PARTITION BY dept   ORDER BY salary DESC),
  region_window AS (PARTITION BY region ORDER BY salary DESC);

-- Extending a named window (PostgreSQL):
SELECT
  name, dept, salary,
  SUM(salary) OVER w                                   AS dept_total,
  SUM(salary) OVER (w ORDER BY salary)                 AS running_dept_total,
  AVG(salary) OVER (w ORDER BY salary ROWS 2 PRECEDING) AS moving_3mo_avg
FROM employees
WINDOW w AS (PARTITION BY dept);
-- w defines the partition; each usage adds its own ORDER BY / frame
```

**Q14. "Explain the difference between `ROW_NUMBER()` and `RANK()` with a concrete business example where each is the correct choice."**
A:

```sql
-- Scenario: e-commerce product reviews

-- Table: reviews (product_id, reviewer_id, rating, helpful_votes, created_at)

-- ── Where ROW_NUMBER is correct: deduplication ───────────────────────
-- Business requirement: "show only the most recent review per reviewer per product"
-- Each reviewer should appear exactly once — ties must be broken

WITH deduped AS (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY product_id, reviewer_id
      ORDER BY created_at DESC    -- most recent first
    ) AS rn
  FROM reviews
)
SELECT product_id, reviewer_id, rating, created_at
FROM   deduped
WHERE  rn = 1;
-- ROW_NUMBER correct here: if a reviewer left 2 reviews on the same day,
-- we want exactly one (arbitrary tie-break is acceptable)
-- RANK would return multiple rows for tied timestamps (wrong — duplicates remain)

-- ── Where RANK is correct: competition-style podium ──────────────────
-- Business requirement: "show the top 3 most helpful reviewers per product.
--                        If two reviewers tie, both should appear on the podium."

WITH ranked AS (
  SELECT product_id, reviewer_id, SUM(helpful_votes) AS total_helpful,
    RANK() OVER (
      PARTITION BY product_id
      ORDER BY SUM(helpful_votes) DESC
    ) AS rnk
  FROM reviews
  GROUP BY product_id, reviewer_id
)
SELECT product_id, reviewer_id, total_helpful, rnk
FROM   ranked
WHERE  rnk <= 3;
-- RANK correct: 2 reviewers with 50 helpful votes each → BOTH get rank 1
-- Both appear in the result (which may have >3 rows — that's correct business behavior)
-- ROW_NUMBER would arbitrarily exclude one of the tied reviewers (wrong — unfair)

-- ── Where DENSE_RANK is correct: popularity tiers ────────────────────
-- Business requirement: "assign tier badges 1-5 to products by sales rank.
--                        No tier should be skipped — badge levels must be contiguous."

WITH tier_ranked AS (
  SELECT product_id, total_sales,
    DENSE_RANK() OVER (ORDER BY total_sales DESC) AS sales_rank
  FROM product_sales
)
SELECT
  product_id,
  CASE
    WHEN sales_rank = 1 THEN 'Bestseller'
    WHEN sales_rank = 2 THEN 'Top Pick'
    WHEN sales_rank = 3 THEN 'Popular'
    ELSE 'Standard'
  END AS badge
FROM tier_ranked;
-- DENSE_RANK: if products A and B both have 1000 sales (rank 2),
-- the next product gets rank 3 (not 4) → 'Popular' badge exists
-- RANK: next product would get rank 4 → 'Popular' badge (rank 3) never assigned (gap!)
```

**Q15. "How would you write a query to detect gaps in a sequence or find missing values using window functions?"**
A:

```sql
-- Problem: find gaps in order IDs (some orders were deleted)
-- orders table: order_id (should be 1,2,3... but some are missing)

-- Method 1: LAG to find where next_id != current_id + 1
WITH ordered AS (
  SELECT
    order_id,
    LEAD(order_id) OVER (ORDER BY order_id) AS next_id
  FROM orders
)
SELECT
  order_id + 1 AS gap_start,
  next_id  - 1 AS gap_end,
  next_id - order_id - 1 AS missing_count
FROM ordered
WHERE next_id - order_id > 1;
-- If order_ids are: 1, 2, 5, 6, 10
-- | gap_start | gap_end | missing_count |
-- |-----------|---------|---------------|
-- |     3     |    4    |       2       |  ← IDs 3,4 missing
-- |     7     |    9    |       3       |  ← IDs 7,8,9 missing

-- Method 2: islands and gaps (more complex — group consecutive sequences)
-- Find runs of consecutive order_ids:
WITH numbered AS (
  SELECT
    order_id,
    order_id - ROW_NUMBER() OVER (ORDER BY order_id) AS island_id
    -- For consecutive IDs: order_id - row_number is constant
    -- Gap → island_id changes
    -- 1-1=0, 2-2=0, 5-3=2, 6-4=2, 10-5=5
  FROM orders
)
SELECT
  MIN(order_id) AS island_start,
  MAX(order_id) AS island_end,
  COUNT(*)       AS island_size
FROM numbered
GROUP BY island_id
ORDER BY island_start;
-- | island_start | island_end | island_size |
-- |--------------|------------|-------------|
-- |      1       |     2      |      2      |  ← first consecutive run
-- |      5       |     6      |      2      |  ← second run
-- |     10       |    10      |      1      |  ← third run (single)
```

## Problem 1 — Top-N Per Group (The Classic Window Function Interview Problem)

### Problem
Given a `products` table with columns `category`, `product_name`, `price`, and `units_sold`, return the **top 3 best-selling products in each category**. Ties in `units_sold` should both appear (ties count as the same rank), but only show up to rank 3.

```sql
-- Sample data:
-- | category | product_name  | price | units_sold |
-- |----------|---------------|-------|------------|
-- | Books    | SQL Mastery   |  49   |    1200    |
-- | Books    | Python Guide  |  39   |    1200    |  ← tie with SQL Mastery
-- | Books    | JS Handbook   |  29   |     900    |
-- | Books    | CSS Tricks    |  19   |     600    |
-- | Books    | HTML Basics   |   9   |     400    |
-- | Tech     | Laptop Pro    | 999   |     500    |
-- | Tech     | Phone Max     | 799   |     450    |
-- | Tech     | Tablet Air    | 599   |     300    |
-- | Tech     | Earbuds       |  99   |     300    |  ← tie with Tablet Air

-- ❌ Naive attempt — can't filter on window function in WHERE:
SELECT category, product_name, units_sold,
  DENSE_RANK() OVER (PARTITION BY category ORDER BY units_sold DESC) AS dr
FROM products
WHERE dr <= 3;  -- ERROR: column "dr" doesn't exist at WHERE evaluation time

-- ❌ ROW_NUMBER instead of RANK — silently excludes tied products:
SELECT category, product_name, units_sold, rn
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY category ORDER BY units_sold DESC) AS rn
  FROM products
) r
WHERE rn <= 3;
-- Books: SQL Mastery(1), Python Guide(2), JS Handbook(3)  ← one tie winner chosen arbitrarily
-- Tech:  Laptop(1), Phone(2), Tablet(3) OR Earbuds(3) ← arbitrarily picks one of the tied pair
-- Wrong: either SQL Mastery or Python Guide silently excluded depending on physical row order
```

### Correct Solution

```sql
-- ✓ DENSE_RANK in CTE, filter after:
WITH ranked_products AS (
  SELECT
    category,
    product_name,
    price,
    units_sold,
    DENSE_RANK() OVER (
      PARTITION BY category
      ORDER BY units_sold DESC
    ) AS sales_rank
  FROM products
)
SELECT
  category,
  sales_rank,
  product_name,
  price,
  units_sold
FROM ranked_products
WHERE sales_rank <= 3
ORDER BY category, sales_rank, product_name;

-- | category | rank | product_name  | price | units_sold |
-- |----------|------|---------------|-------|------------|
-- | Books    |  1   | Python Guide  |  39   |    1200    | ← tied at rank 1
-- | Books    |  1   | SQL Mastery   |  49   |    1200    | ← tied at rank 1
-- | Books    |  2   | JS Handbook   |  29   |     900    | ← rank 2 (no gap after tie)
-- | Books    |  3   | CSS Tricks    |  19   |     600    | ← rank 3
-- | Tech     |  1   | Laptop Pro    | 999   |     500    |
-- | Tech     |  2   | Phone Max     | 799   |     450    |
-- | Tech     |  3   | Earbuds       |  99   |     300    | ← tied at rank 3
-- | Tech     |  3   | Tablet Air    | 599   |     300    | ← tied at rank 3 — both appear
-- Result: 8 rows (>= 3 per category because of ties) — correct business behavior

-- ✓ Alternative: RANK instead of DENSE_RANK
-- Difference: if Books had TWO rank-1 products, the next would be rank 3 (not rank 2)
-- DENSE_RANK: 1,1,2,3 → with <= 3 filter: 4 products shown (ranks 1,1,2,3)
-- RANK:       1,1,3,4 → with <= 3 filter: 3 products shown (ranks 1,1,3 — rank 4 excluded)
-- Which is correct depends on business rule:
--   "top 3 ranks" (no gaps) → DENSE_RANK
--   "top 3 positions even with gaps" → RANK

-- ✓ Variant: top N with secondary sort for tie-breaking:
WITH ranked AS (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY category
      ORDER BY units_sold DESC, price DESC  -- secondary sort breaks ties deterministically
    ) AS rn
  FROM products
)
SELECT * FROM ranked WHERE rn <= 3;
-- Now exactly 3 per category, tie broken by higher price
-- Use when business rule is "exactly 3, break ties by price"
```

### Why Each Ranking Function Gives Different Results

```
For Books category: SQL Mastery (1200), Python Guide (1200), JS Handbook (900), CSS Tricks (600)

ROW_NUMBER() with <= 3 filter:
  SQL Mastery=1, Python Guide=2, JS Handbook=3, CSS Tricks=4
  Shows: SQL Mastery, Python Guide, JS Handbook (exactly 3)
  Misses: Python Guide and SQL Mastery are tied — one arbitrarily excluded

RANK() with <= 3 filter:
  SQL Mastery=1, Python Guide=1, JS Handbook=3, CSS Tricks=4
  Shows: SQL Mastery, Python Guide, JS Handbook (3 rows because rank 2 skipped)
  Rank 2 never exists — next after tie at 1 is 3

DENSE_RANK() with <= 3 filter:
  SQL Mastery=1, Python Guide=1, JS Handbook=2, CSS Tricks=3
  Shows: SQL Mastery, Python Guide, JS Handbook, CSS Tricks (4 rows)
  Shows ALL of rank 3 — includes CSS Tricks because ties compress the numbering
```

## Problem 2 — Running Totals, Moving Averages, and Period Comparison

### Problem
A `daily_orders` table has columns `order_date`, `revenue`, `region`. Calculate:
1. Running total revenue per region
2. 7-day moving average per region
3. Week-over-week revenue change
4. Revenue as a percentage of monthly total

```sql
-- Setup: daily_orders (order_date DATE, region TEXT, revenue NUMERIC)

-- ── Part 1: Running total per region ──────────────────────────────────
SELECT
  order_date,
  region,
  revenue,
  SUM(revenue) OVER (
    PARTITION BY region
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total
FROM daily_orders
ORDER BY region, order_date;

-- ── Part 2: 7-day moving average per region ───────────────────────────
SELECT
  order_date,
  region,
  revenue,
  ROUND(
    AVG(revenue) OVER (
      PARTITION BY region
      ORDER BY order_date
      ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
      -- 6 preceding + current = 7 rows (7-day window)
      -- First 6 days: averages fewer rows (window doesn't have 7 yet)
    ),
    2
  ) AS moving_avg_7d,
  COUNT(*) OVER (
    PARTITION BY region
    ORDER BY order_date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS days_in_window  -- shows how many actual days used (< 7 for first few)
FROM daily_orders
ORDER BY region, order_date;

-- ── Part 3: Week-over-week revenue change ─────────────────────────────
-- First aggregate to weekly, then compute WoW change:
WITH weekly_revenue AS (
  SELECT
    DATE_TRUNC('week', order_date) AS week_start,
    region,
    SUM(revenue) AS weekly_rev
  FROM daily_orders
  GROUP BY DATE_TRUNC('week', order_date), region
),
wow_comparison AS (
  SELECT
    week_start,
    region,
    weekly_rev,
    LAG(weekly_rev) OVER (
      PARTITION BY region
      ORDER BY week_start
    ) AS prev_week_rev,
    LAG(weekly_rev, 4) OVER (   -- 4 weeks ago = same week last month
      PARTITION BY region
      ORDER BY week_start
    ) AS same_week_prev_month
  FROM weekly_revenue
)
SELECT
  week_start,
  region,
  weekly_rev,
  prev_week_rev,
  weekly_rev - prev_week_rev AS wow_change,
  ROUND(
    (weekly_rev - prev_week_rev)::NUMERIC / NULLIF(prev_week_rev, 0) * 100,
    1
  ) AS wow_pct_change,
  -- 4-week rolling average for trend smoothing:
  ROUND(
    AVG(weekly_rev) OVER (
      PARTITION BY region
      ORDER BY week_start
      ROWS BETWEEN 3 PRECEDING AND CURRENT ROW
    ),
    0
  ) AS rolling_4wk_avg
FROM wow_comparison
ORDER BY region, week_start;

-- ── Part 4: Revenue as percentage of monthly total ─────────────────────
WITH daily_with_monthly AS (
  SELECT
    order_date,
    region,
    revenue,
    -- Monthly total per region (PARTITION BY region AND month):
    SUM(revenue) OVER (
      PARTITION BY region, DATE_TRUNC('month', order_date)
    ) AS monthly_regional_total,
    -- Monthly total across ALL regions:
    SUM(revenue) OVER (
      PARTITION BY DATE_TRUNC('month', order_date)
    ) AS monthly_total
  FROM daily_orders
)
SELECT
  order_date,
  region,
  revenue,
  monthly_regional_total,
  ROUND(revenue / monthly_regional_total * 100, 2) AS pct_of_region_month,
  ROUND(revenue / monthly_total * 100, 2)          AS pct_of_all_regions_month
FROM daily_with_monthly
ORDER BY order_date, region;
```

## Problem 3 — Deduplication and Slowly Changing Dimensions

### Problem
A `customer_events` table logs every time a customer record changes, creating duplicates with different timestamps. Also, a `product_prices` table has historical price changes. Use window functions to get the current state and build a type-2 SCD (slowly changing dimension).

```sql
-- customer_events: customer_id, event_time, email, status, address
-- Multiple rows per customer — only the latest matters

-- ── Deduplication: keep only the most recent record per customer ───────
WITH deduped AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY event_time DESC   -- most recent first → rn=1 is the latest
    ) AS rn
  FROM customer_events
)
SELECT
  customer_id, event_time, email, status, address
FROM deduped
WHERE rn = 1;

-- ── Finding first AND latest event per customer in one pass ───────────
SELECT DISTINCT
  customer_id,
  FIRST_VALUE(event_time) OVER w AS first_seen,
  LAST_VALUE(event_time)  OVER w_full AS last_seen,
  FIRST_VALUE(email)      OVER w AS original_email,
  LAST_VALUE(email)       OVER w_full AS current_email,
  COUNT(*) OVER (PARTITION BY customer_id) AS total_events
FROM customer_events
WINDOW
  w      AS (PARTITION BY customer_id ORDER BY event_time
              ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING),
  w_full AS (PARTITION BY customer_id ORDER BY event_time
              ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);
-- Note: LAST_VALUE requires UNBOUNDED FOLLOWING to reach the last row

-- ── SCD Type 2: build valid_from/valid_to date ranges ─────────────────
-- product_prices: product_id, price, effective_date
-- Each row = price change on that date
-- Build: product_id, price, valid_from, valid_to (NULL = current)

WITH price_history AS (
  SELECT
    product_id,
    price,
    effective_date AS valid_from,
    LEAD(effective_date) OVER (
      PARTITION BY product_id
      ORDER BY effective_date
    ) AS valid_to   -- next effective_date = when this price expires
  FROM product_prices
)
SELECT
  product_id,
  price,
  valid_from,
  COALESCE(valid_to - INTERVAL '1 day', '9999-12-31') AS valid_to,
  -- valid_to IS NULL → current price (use 9999-12-31 or leave as NULL)
  valid_to IS NULL AS is_current_price
FROM price_history
ORDER BY product_id, valid_from;

-- | product_id | price | valid_from | valid_to   | is_current |
-- |------------|-------|------------|------------|------------|
-- | P001       | 9.99  | 2024-01-01 | 2024-02-28 | false      |
-- | P001       | 12.99 | 2024-03-01 | 2024-05-31 | false      |
-- | P001       | 11.99 | 2024-06-01 | 9999-12-31 | true       |

-- Query: what was P001's price on 2024-04-15?
SELECT price
FROM price_history_scd
WHERE product_id = 'P001'
  AND '2024-04-15' BETWEEN valid_from AND valid_to;
-- → 12.99 ✓
```

## Problem 4 — Session Analysis and Gap Detection

### Problem
A `page_views` table logs user activity with `user_id`, `page`, `viewed_at`. Define a **session** as activity within 30 minutes of the previous action. Assign session IDs and compute session-level metrics.

```sql
-- page_views: user_id TEXT, page TEXT, viewed_at TIMESTAMP

-- ── Step 1: detect session boundaries ─────────────────────────────────
-- A new session starts when gap from previous view > 30 minutes
WITH time_gaps AS (
  SELECT
    user_id,
    page,
    viewed_at,
    LAG(viewed_at) OVER (
      PARTITION BY user_id
      ORDER BY viewed_at
    ) AS prev_view_at,
    -- Is this the start of a new session?
    CASE
      WHEN LAG(viewed_at) OVER (PARTITION BY user_id ORDER BY viewed_at) IS NULL
        THEN 1  -- first event for this user → new session
      WHEN viewed_at - LAG(viewed_at) OVER (PARTITION BY user_id ORDER BY viewed_at)
           > INTERVAL '30 minutes'
        THEN 1  -- gap > 30 min → new session
      ELSE 0    -- same session continues
    END AS is_new_session
  FROM page_views
),
-- ── Step 2: assign session IDs using cumulative sum of session starts ──
session_assigned AS (
  SELECT
    user_id,
    page,
    viewed_at,
    is_new_session,
    -- Running count of session starts = session number for this user:
    SUM(is_new_session) OVER (
      PARTITION BY user_id
      ORDER BY viewed_at
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS session_num,
    -- Global unique session ID:
    user_id || '-' || LPAD(
      SUM(is_new_session) OVER (
        PARTITION BY user_id
        ORDER BY viewed_at
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
      )::TEXT, 4, '0'
    ) AS session_id
  FROM time_gaps
),
-- ── Step 3: compute session-level metrics ─────────────────────────────
session_metrics AS (
  SELECT
    user_id,
    session_id,
    session_num,
    page,
    viewed_at,
    -- Session start time: first view in the session
    FIRST_VALUE(viewed_at) OVER (
      PARTITION BY user_id, session_num
      ORDER BY viewed_at
      ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS session_start,
    -- Session end time: last view in the session
    LAST_VALUE(viewed_at) OVER (
      PARTITION BY user_id, session_num
      ORDER BY viewed_at
      ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS session_end,
    -- Pages in this session:
    COUNT(*) OVER (
      PARTITION BY user_id, session_num
    ) AS pages_in_session,
    -- Position within session (1 = landing page):
    ROW_NUMBER() OVER (
      PARTITION BY user_id, session_num
      ORDER BY viewed_at
    ) AS page_position,
    -- Next page the user visited:
    LEAD(page) OVER (
      PARTITION BY user_id, session_num
      ORDER BY viewed_at
    ) AS next_page
  FROM session_assigned
)
-- ── Step 4: final result with session summary ──────────────────────────
SELECT
  user_id,
  session_id,
  page,
  viewed_at,
  page_position,
  session_start,
  session_end,
  EXTRACT(EPOCH FROM (session_end - session_start)) / 60 AS session_duration_min,
  pages_in_session,
  -- Is this the entry page?
  page_position = 1 AS is_entry_page,
  -- Is this the exit page (no next page within session)?
  next_page IS NULL AS is_exit_page,
  next_page
FROM session_metrics
ORDER BY user_id, viewed_at;

-- ── Session summary (one row per session): ─────────────────────────────
SELECT DISTINCT
  user_id,
  session_id,
  session_start,
  session_end,
  ROUND(EXTRACT(EPOCH FROM (session_end - session_start)) / 60.0, 2) AS duration_min,
  pages_in_session,
  FIRST_VALUE(page) OVER (
    PARTITION BY user_id, session_id
    ORDER BY viewed_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS landing_page,
  LAST_VALUE(page) OVER (
    PARTITION BY user_id, session_id
    ORDER BY viewed_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS exit_page
FROM session_metrics;
```

## Problem 5 — Cohort Retention Analysis

### Problem
Given a `signups` table (`user_id`, `signup_date`) and `logins` table (`user_id`, `login_date`), calculate week-by-week cohort retention — what percentage of users who signed up in a given week are still active in subsequent weeks.

```sql
-- ── Step 1: assign cohort week to each user ────────────────────────────
WITH user_cohorts AS (
  SELECT
    user_id,
    DATE_TRUNC('week', signup_date) AS cohort_week
  FROM signups
),
-- ── Step 2: get all login weeks per user ───────────────────────────────
user_activity AS (
  SELECT DISTINCT
    user_id,
    DATE_TRUNC('week', login_date) AS activity_week
  FROM logins
),
-- ── Step 3: join cohorts with activity ────────────────────────────────
cohort_activity AS (
  SELECT
    c.cohort_week,
    a.activity_week,
    -- Week number since signup (0 = signup week, 1 = first week after, etc.):
    CAST(
      (a.activity_week - c.cohort_week) / 7 AS INT
    ) AS weeks_since_signup,
    COUNT(DISTINCT c.user_id) AS active_users
  FROM user_cohorts c
  JOIN user_activity a USING (user_id)
  GROUP BY c.cohort_week, a.activity_week
),
-- ── Step 4: get cohort sizes (week 0 = total signed up) ───────────────
cohort_sizes AS (
  SELECT
    cohort_week,
    COUNT(*) AS cohort_size
  FROM user_cohorts
  GROUP BY cohort_week
),
-- ── Step 5: calculate retention percentages ────────────────────────────
retention AS (
  SELECT
    ca.cohort_week,
    ca.weeks_since_signup,
    ca.active_users,
    cs.cohort_size,
    ROUND(ca.active_users::NUMERIC / cs.cohort_size * 100, 1) AS retention_pct,
    -- Retention relative to previous week (week-over-week within cohort):
    LAG(ca.active_users) OVER (
      PARTITION BY ca.cohort_week
      ORDER BY ca.weeks_since_signup
    ) AS prev_week_active,
    ROUND(
      (ca.active_users - LAG(ca.active_users) OVER (
        PARTITION BY ca.cohort_week ORDER BY ca.weeks_since_signup
      ))::NUMERIC
      / NULLIF(LAG(ca.active_users) OVER (
        PARTITION BY ca.cohort_week ORDER BY ca.weeks_since_signup
      ), 0) * 100,
      1
    ) AS churn_rate_pct
  FROM cohort_activity ca
  JOIN cohort_sizes cs USING (cohort_week)
)
-- ── Final retention table ──────────────────────────────────────────────
SELECT
  cohort_week,
  cohort_size,
  weeks_since_signup,
  active_users,
  retention_pct,
  churn_rate_pct
FROM retention
WHERE weeks_since_signup BETWEEN 0 AND 12   -- show first 12 weeks
ORDER BY cohort_week, weeks_since_signup;

-- | cohort_week | cohort_size | week | active | retention% | churn% |
-- |-------------|-------------|------|--------|------------|--------|
-- | 2024-01-01  |    1000     |  0   |  1000  |   100.0    |  NULL  |
-- | 2024-01-01  |    1000     |  1   |   720  |    72.0    | -28.0  |
-- | 2024-01-01  |    1000     |  2   |   550  |    55.0    | -23.6  |
-- | 2024-01-01  |    1000     |  4   |   420  |    42.0    | -10.5  |
-- | 2024-01-08  |    1200     |  0   |  1200  |   100.0    |  NULL  |
-- | 2024-01-08  |    1200     |  1   |   900  |    75.0    | -25.0  |
-- ...

-- ── Pivot to classic cohort table format (PostgreSQL crosstab / conditional agg):
SELECT
  cohort_week,
  cohort_size,
  MAX(CASE WHEN weeks_since_signup = 0 THEN retention_pct END)  AS "Week 0",
  MAX(CASE WHEN weeks_since_signup = 1 THEN retention_pct END)  AS "Week 1",
  MAX(CASE WHEN weeks_since_signup = 2 THEN retention_pct END)  AS "Week 2",
  MAX(CASE WHEN weeks_since_signup = 4 THEN retention_pct END)  AS "Week 4",
  MAX(CASE WHEN weeks_since_signup = 8 THEN retention_pct END)  AS "Week 8",
  MAX(CASE WHEN weeks_since_signup = 12 THEN retention_pct END) AS "Week 12"
FROM retention
GROUP BY cohort_week, cohort_size
ORDER BY cohort_week;
-- | cohort_week | size | Week 0 | Week 1 | Week 2 | Week 4 | Week 8 | Week 12 |
-- |-------------|------|--------|--------|--------|--------|--------|---------|
-- | 2024-01-01  | 1000 | 100.0  |  72.0  |  55.0  |  42.0  |  30.0  |  22.0   |
-- | 2024-01-08  | 1200 | 100.0  |  75.0  |  58.0  |  45.0  |  NULL  |  NULL   |
-- (NULL = future weeks not yet observable)
```

## Quick Reference — Window Functions Cheat Sheet

```
SYNTAX:
  function() OVER (
    [PARTITION BY col1, col2]   → divide into independent groups
    [ORDER BY col3 ASC/DESC]    → row order within partition
    [frame_clause]              → which rows to include
  )

  frame_clause:
    ROWS  BETWEEN start AND end    → physical row count
    RANGE BETWEEN start AND end    → rows with same ORDER BY value (default)
    GROUPS BETWEEN ...             → groups of rows with same value

  frame bounds:
    UNBOUNDED PRECEDING  → first row of partition
    N PRECEDING          → N rows before current
    CURRENT ROW          → current row (default end for ORDER BY present)
    N FOLLOWING          → N rows after current
    UNBOUNDED FOLLOWING  → last row of partition

RANKING FUNCTIONS (require ORDER BY, ignore frame):
  ROW_NUMBER()   → 1,2,3,4 — always unique, ties broken arbitrarily
  RANK()         → 1,1,3,4 — ties same rank, gaps after tie
  DENSE_RANK()   → 1,1,2,3 — ties same rank, NO gaps
  NTILE(n)       → 1..n    — divides into n equal buckets
  PERCENT_RANK() → 0.0..1.0 — (rank-1)/(rows-1) — 0 for first
  CUME_DIST()    → 0..1.0  — rows≤current/total — never 0

VALUE FUNCTIONS:
  LAG(expr, n, default)        → value from n rows BEFORE current (within partition)
  LEAD(expr, n, default)       → value from n rows AFTER current (within partition)
  FIRST_VALUE(expr)            → first value in window frame
  LAST_VALUE(expr)             → last value in frame (BEWARE: default frame = CURRENT ROW)
  NTH_VALUE(expr, n)           → nth value in frame (1-indexed)

  LAST_VALUE gotcha: always add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  or RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

AGGREGATE AS WINDOW:
  SUM(col)   OVER (...)  → running/partition total
  AVG(col)   OVER (...)  → running/partition average or moving average
  COUNT(*)   OVER (...)  → running/partition count
  MIN/MAX    OVER (...)  → running/partition min/max

EXECUTION ORDER (window functions run AFTER WHERE, GROUP BY, HAVING):
  FROM → WHERE → GROUP BY → HAVING → [window functions] → SELECT → ORDER BY → LIMIT
  → Cannot filter on window function alias in WHERE/HAVING
  → Must wrap in subquery or CTE to filter on window result

DEFAULT FRAMES:
  With ORDER BY:    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  Without ORDER BY: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

KEY PATTERNS:
  Top-N per group:        ROW_NUMBER/DENSE_RANK in CTE, WHERE rn <= N
  Deduplication:          ROW_NUMBER in CTE, WHERE rn = 1
  Running total:          SUM() OVER (PARTITION BY x ORDER BY date ROWS UNBOUNDED PRECEDING TO CURRENT)
  Moving average (7d):    AVG() OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
  MoM/YoY change:         LAG(col, 1)/LAG(col, 12) OVER (PARTITION BY region ORDER BY month)
  Session assignment:     SUM(is_new_session) OVER (PARTITION BY user ORDER BY time)
  Gaps in sequence:       LEAD(id) OVER (ORDER BY id) - id > 1
  SCD Type 2 dates:       LEAD(effective_date) OVER (PARTITION BY id ORDER BY date) AS valid_to
  Cohort retention:       COUNT DISTINCT with PARTITION BY cohort_week
  Percentile labels:      NTILE(100) OVER (ORDER BY metric)

COMMON BUGS:
  Filtering on window alias in WHERE    → wrap in CTE or subquery
  LAST_VALUE returning current row      → add ROWS UNBOUNDED PRECEDING TO UNBOUNDED FOLLOWING
  LAG crossing partition boundary       → add PARTITION BY to prevent cross-group leakage
  RANGE vs ROWS tie behavior            → RANGE includes all tied rows (default); ROWS is physical
  NULL in LAG/LEAD                      → provide default arg: LAG(col, 1, 0)
  RANK skipping numbers                 → expected: use DENSE_RANK for contiguous numbering
  Window on GROUP BY result             → use SUM(SUM(col)) OVER () for correct nesting
  Multiple OVER() with same spec        → use WINDOW clause to define once, reuse everywhere
  High-cardinality PARTITION BY         → expensive; add composite index on (partition, order) cols
```

**Final Tip:** At the 5 YOE level, window function questions test whether you can reason about **when the window resets, what the frame includes, and which function to choose given tie semantics**. The highest-signal answer on `ROW_NUMBER` vs `RANK` vs `DENSE_RANK`: "I ask the business question first. If the requirement is 'show exactly one row per group — deduplicate or paginate' then `ROW_NUMBER` is correct because ties must be broken to get exactly N rows. If it's 'all tied entries should share a rank — no one gets unfairly excluded' then `RANK` or `DENSE_RANK`, and the choice between those depends on whether the gap after a tie is confusing: a leaderboard usually wants `RANK` because 'two silvers, no bronze' is meaningful; a category-tier system usually wants `DENSE_RANK` because skipping tier 2 when two products tie for it is confusing to users." For `LAST_VALUE`: "The most common window function production bug I've seen is `LAST_VALUE` returning the current row instead of the last row in the partition. It happens because the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — so the 'last' row in the frame is always the current row. The fix is always explicit: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`." For `LAG`/`LEAD` and partitions: "Without `PARTITION BY`, `LAG` happily crosses group boundaries — the first row of `South` region sees the last row of `North` as its previous row. Always ask: should the lag reset at group boundaries? If yes, `PARTITION BY` is mandatory."
