# Composite Indexes, Partial Indexes, Covering Indexes (`INCLUDE`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. How does a B-tree index work in PostgreSQL and what problem does it solve?**
A: A B-tree (Balanced Tree) index is a separate on-disk data structure that maps column values to physical row locations (ctid — block number + tuple offset). Without an index, every query must scan every row of the table (sequential scan). The index lets PostgreSQL navigate directly to matching rows in O(log n) time:

```
Table: loans (1,000,000 rows)
Query: SELECT * FROM loans WHERE id = 'L12345'

Without index (Sequential Scan):
  Read block 1 → check every row → no match
  Read block 2 → check every row → no match
  ...
  Read block 8192 → found!
  Cost: O(n) — reads every row

With B-tree index on (id):
  Read root node → compare 'L12345' with pivot keys → go right subtree
  Read internal node → compare → go left subtree
  Read leaf node → find 'L12345' → ctid = (4021, 7)
  Read heap block 4021, tuple 7 → done
  Cost: O(log n) — reads ~3-4 nodes for 1M rows

B-tree structure:
                     [L50000 | L80000]           ← root node
                    /         |         \
          [L20000|L35000]  [L65000]  [L90000|L95000]  ← internal nodes
          /    |    \          |
  [L1..L19] [L20..L34] [L35..L49]  [L50..L64]        ← leaf nodes
      ↓           ↓          ↓
   ctid list   ctid list   ctid list                  ← heap pointers

Leaf nodes are doubly linked → range scans traverse leaves without going back to root:
  WHERE id BETWEEN 'L10000' AND 'L20000':
    Navigate to leaf containing L10000 → scan right through linked leaves → stop at L20000

Index entry size:
  Each leaf entry: key value(s) + ctid (6 bytes) + visibility info
  A (uuid) index entry: 16 bytes key + 6 bytes ctid = ~22 bytes per row
  1M rows: index ~22MB vs table potentially GBs → index fits in memory, table does not
```

**Q2. What is the access pattern a B-tree index supports and what queries cannot use it?**
A: A B-tree index supports equality, range, prefix, and ORDER BY operations on its leading columns. Understanding what it cannot do is as important as knowing what it can:

```sql
-- Index: CREATE INDEX ON loans (status, created_at, amount);

-- ✓ Supported patterns:

-- Equality on leading column:
WHERE status = 'pending'

-- Equality + range on next column:
WHERE status = 'pending' AND created_at > '2024-01-01'

-- Equality on all columns:
WHERE status = 'pending' AND created_at = '2024-01-15' AND amount = 50000

-- ORDER BY aligned with index (avoids sort step):
WHERE status = 'pending' ORDER BY created_at ASC

-- Range on leading column (uses index, less efficiently):
WHERE status IN ('pending', 'approved')

-- ✗ Patterns the index cannot support efficiently:

-- Skipping the leading column:
WHERE created_at > '2024-01-01'
-- Index on (status, created_at) → status is leading → skipping it means
-- PostgreSQL cannot navigate the B-tree (status varies across all entries)
-- Result: sequential scan (or index scan with full index scan — still O(n))

-- Function on indexed column (index stores raw value, not f(value)):
WHERE LOWER(borrower_name) = 'alice'
-- Fix: CREATE INDEX ON loans (LOWER(borrower_name))  ← expression index

-- Negation:
WHERE status != 'rejected'
-- B-tree cannot represent "everything except X" efficiently
-- Fix: partial index on the positive case if selectivity is high

-- LIKE with leading wildcard:
WHERE reference_code LIKE '%ABC%'
-- B-tree is ordered by prefix — trailing wildcards work, leading do not
-- Fix: pg_trgm extension + GIN index for arbitrary substring search

-- NULL comparisons on non-partial index:
WHERE column IS NULL
-- B-tree DOES index NULLs (unlike some databases) → IS NULL is supported
-- But if NULLs are rare, a partial index WHERE column IS NOT NULL is smaller/faster
```

## Section 2: Composite Indexes

**Q3. What is a composite index and what is the column ordering rule?**
A: A composite (multi-column) index is a B-tree built on two or more columns concatenated as a single key. The index is sorted first by the first column, then by the second within equal first-column values, and so on. Column order determines which queries the index can accelerate:

```sql
-- Creating composite indexes:
CREATE INDEX idx_loans_status_created ON loans (status, created_at);
CREATE INDEX idx_loans_tenant_status_created ON loans (tenant_id, status, created_at);

-- The sort order analogy — think of a phone book:
-- Phone book sorted by (last_name, first_name):
--   You CAN look up: all 'Sharma' entries (leading column)
--   You CAN look up: 'Sharma, Ravi' specifically (both columns)
--   You CANNOT efficiently look up: all 'Ravi' entries without scanning every page
--     (first_name is not the leading sort key)

-- Composite index on (status, created_at):
-- Stored order:
--   ('active',   2024-01-01)  → ctid A
--   ('active',   2024-01-15)  → ctid B
--   ('active',   2024-03-01)  → ctid C
--   ('pending',  2024-01-05)  → ctid D
--   ('pending',  2024-02-10)  → ctid E
--   ('rejected', 2023-12-01)  → ctid F

-- Query analysis:
EXPLAIN SELECT * FROM loans WHERE status = 'active' AND created_at > '2024-01-01';
-- Index Scan on idx_loans_status_created
-- Index Cond: ((status = 'active') AND (created_at > '2024-01-01'))
-- ✓ Both columns used — navigates to 'active' entries, then applies date range

EXPLAIN SELECT * FROM loans WHERE status = 'active';
-- Index Scan on idx_loans_status_created
-- ✓ Leading column used — navigates to 'active' block, scans all entries

EXPLAIN SELECT * FROM loans WHERE created_at > '2024-01-01';
-- Seq Scan on loans  (index NOT used)
-- ✗ Leading column (status) not in WHERE — index cannot help
-- PostgreSQL would have to scan all ('active', *), ('pending', *), ('rejected', *)
-- entries anyway — equivalent to a full index scan → planner chooses seq scan

-- Column ordering rule — most selective or most common filter first:
-- Common pattern: (tenant_id, status, created_at)
-- Query 1: WHERE tenant_id='T1'                        → uses leading column ✓
-- Query 2: WHERE tenant_id='T1' AND status='pending'   → uses two columns ✓
-- Query 3: WHERE tenant_id='T1' AND status='pending'   → uses all three ✓
--             AND created_at > '2024-01-01'
-- Query 4: WHERE status='pending'                      → does NOT use index ✗
--   → if Query 4 is also common, create a separate index on (status) or (status, created_at)
```

**Q4. What is the "leading column rule" in detail, and when can PostgreSQL use a composite index without the leading column?**
A: PostgreSQL can only efficiently use a composite index when the query constrains the leading column(s). However, there is one exception: the index skip scan (bitmap index scan on multiple ranges) can sometimes avoid the constraint, though it is less efficient:

```sql
-- Index: CREATE INDEX ON loans (status, created_at, borrower_id);

-- Case 1: Leading column present (optimal):
WHERE status = 'active'                          -- uses index, navigates directly
WHERE status = 'active' AND created_at > '2024' -- uses index on both columns
WHERE status IN ('active', 'pending')            -- bitmap scan: two ranges merged

-- Case 2: Leading column absent (index skipped by planner):
WHERE created_at > '2024-01-01'                 -- seq scan (status not constrained)
WHERE borrower_id = 'B1'                        -- seq scan (first two columns missing)

-- Case 3: Gap in the middle (partial use):
WHERE status = 'active' AND borrower_id = 'B1'
-- PostgreSQL uses the index for status='active' but cannot apply borrower_id
-- via the index (created_at is in between, not constrained)
-- Index used for: status = 'active'
-- Filter applied as: borrower_id = 'B1' (checked row by row after index scan)
-- Still faster than seq scan if status='active' is selective enough

-- EXPLAIN output showing partial use:
EXPLAIN ANALYZE
SELECT * FROM loans WHERE status = 'active' AND borrower_id = 'B1';
-- Index Scan using idx_loans_status_created_borrower on loans
-- Index Cond: (status = 'active')
-- Filter: (borrower_id = 'B1')     ← applied after index, not via index
-- Rows Removed by Filter: 4821     ← still had to check 4821 rows post-index

-- Solution: reorder or add an index that covers the actual query pattern:
CREATE INDEX ON loans (status, borrower_id);  -- if this query is frequent
CREATE INDEX ON loans (borrower_id, status);  -- if borrower_id is more selective

-- When to create a separate index vs adding to composite:
-- Rule: if a query omits the leading column, it needs its own index.
-- Adding borrower_id to the end of (status, created_at, borrower_id)
-- does NOT help queries that filter on (status, borrower_id) without created_at range.
-- Those queries need either: (status, borrower_id) or (borrower_id, status)

-- Index selectivity:
-- High selectivity (many distinct values): user_id, loan_id, email → good leading column
-- Low selectivity (few distinct values): status ('active'|'pending'|'rejected'),
--   boolean flags, gender → poor leading column alone (returns many rows)
--   BUT can be a good second column after a high-selectivity first column
```

**Q5. How does column ordering in a composite index interact with ORDER BY and what is an index-only sort?**
A: PostgreSQL can satisfy an ORDER BY clause using the index's natural sort order — avoiding a separate sort step entirely. This requires the ORDER BY columns to be a prefix of the index columns and the sort direction to match:

```sql
-- Index: CREATE INDEX ON loans (tenant_id, status, created_at DESC);

-- Query 1 — ORDER BY aligns with index (no sort step):
SELECT * FROM loans
WHERE tenant_id = 'T1' AND status = 'active'
ORDER BY created_at DESC;
-- Index Scan Backward on idx (or forward, depending on direction)
-- No Sort node in EXPLAIN → index provides pre-sorted output

-- Query 2 — ORDER BY direction mismatch (index scan backward):
SELECT * FROM loans
WHERE tenant_id = 'T1' AND status = 'active'
ORDER BY created_at ASC;
-- PostgreSQL can scan the index backward → still no Sort node
-- B-tree leaves are doubly linked → traversal in either direction is O(1) per step

-- Query 3 — ORDER BY on non-trailing column (sort required):
SELECT * FROM loans
WHERE tenant_id = 'T1'
ORDER BY status ASC, created_at DESC;
-- Index can be used for the tenant_id filter
-- But (status, created_at) are interleaved in index by tenant_id → sort still needed
-- Unless: query does not filter by status → index order (tenant_id, status, created_at DESC)
--          naturally produces (status ASC, created_at DESC) within each tenant_id group

-- Practical example — paginated loan list:
-- Index: CREATE INDEX ON loans (tenant_id, created_at DESC);
SELECT id, amount, status FROM loans
WHERE tenant_id = 'T1'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
-- Index Scan on idx (tenant_id, created_at DESC)
-- Reads exactly 20 leaf entries → returns → done
-- No sort, no table scan of non-matching rows
-- This is why the index column order must match your ORDER BY for pagination

-- NULLS ordering:
-- Index: CREATE INDEX ON loans (due_date ASC NULLS LAST);
-- Matches: ORDER BY due_date ASC NULLS LAST
-- Mismatches: ORDER BY due_date ASC NULLS FIRST (default in PostgreSQL for ASC)
-- Create index with same NULLS ordering as your query to avoid sort step

-- ASC/DESC per column in composite index:
CREATE INDEX ON loans (status ASC, created_at DESC);
-- Satisfies: ORDER BY status ASC, created_at DESC   → no sort
-- Does NOT satisfy: ORDER BY status ASC, created_at ASC  → needs sort (or index scan backward won't help mixed directions)
-- Mixed ASC/DESC in one composite index is the solution for mixed-direction sorts
```

**Q6. How do you choose between one composite index and multiple single-column indexes?**
A: The planner can combine multiple single-column indexes via bitmap scans, but a well-designed composite index is almost always faster for queries that filter on multiple columns together:

```sql
-- Scenario: common query filters
-- Query A: WHERE tenant_id = 'T1' AND status = 'active'    (very frequent)
-- Query B: WHERE tenant_id = 'T1'                           (frequent)
-- Query C: WHERE status = 'active'                          (occasional)
-- Query D: WHERE tenant_id = 'T1' AND created_at > '2024'  (occasional)

-- Option 1: Two single-column indexes
CREATE INDEX idx_tenant ON loans (tenant_id);
CREATE INDEX idx_status ON loans (status);

-- For Query A: planner may use bitmap AND:
-- Bitmap Index Scan on idx_tenant → bitmap of tenant_id='T1' rows
-- Bitmap Index Scan on idx_status → bitmap of status='active' rows
-- BitmapAnd → intersection
-- Heap Bitmap Scan → fetch matching rows
-- Cost: two index scans + bitmap intersection + heap fetch (potentially random I/O)

-- Option 2: One composite index
CREATE INDEX idx_tenant_status ON loans (tenant_id, status);

-- For Query A:
-- Index Scan on idx_tenant_status  (tenant_id='T1', status='active')
-- Navigates directly to matching entries → single sorted traversal
-- Cost: one index scan + heap fetch

-- Composite wins for Query A: single navigation vs bitmap intersection
-- But idx_tenant_status does NOT help Query C (WHERE status='active')
-- → still need idx_status for Query C if it's important

-- Decision framework:
-- 1. Identify the most frequent query patterns (from pg_stat_statements)
-- 2. For each group of columns always queried together: composite index in selectivity order
-- 3. For columns queried independently: separate indexes
-- 4. Avoid over-indexing: every index costs write overhead + storage + planner time

-- Write overhead — why you cannot just index everything:
-- INSERT into a table with 5 indexes: must write 6 data structures (heap + 5 indexes)
-- UPDATE on indexed column: delete old index entry, insert new index entry (in each affected index)
-- A write-heavy table (millions of inserts/day) with 10 indexes: significant throughput loss

-- pg_stat_user_indexes — find unused indexes and remove them:
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,           -- number of times this index was used
    idx_tup_read,       -- tuples read via this index
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan ASC;
-- idx_scan = 0 after weeks of production traffic → index is unused → candidate for removal
```

## Section 3: Partial Indexes

**Q7. What is a partial index and what problem does it solve that a full index cannot?**
A: A partial index is built with a WHERE clause — it indexes only the rows that satisfy the predicate. For tables where a small fraction of rows are "active" or "interesting", a partial index is dramatically smaller and faster than a full index on the same column:

```sql
-- Problem: loan_applications table has 10,000,000 rows
-- 9,800,000 rows have status = 'processed' (historical, rarely queried)
--   200,000 rows have status = 'pending'   (active, queried constantly)

-- Full index on status:
CREATE INDEX idx_loans_status ON loan_applications (status);
-- Size: indexes all 10M rows → large index
-- For WHERE status='pending': must navigate to 'pending' entries among 10M entries
-- Selectivity: 200,000 / 10,000,000 = 2% — decent but index is bloated with history

-- Partial index on pending only:
CREATE INDEX idx_loans_pending ON loan_applications (created_at)
WHERE status = 'pending';
-- Size: indexes only 200,000 rows → ~98% smaller
-- Fits entirely in memory (shared_buffers) vs full index that may not
-- For WHERE status='pending': entire index IS the pending set → ultra-fast
-- For WHERE status='processed': cannot use this index → but those queries are rare anyway

-- Query must include the index predicate (or a stronger condition):
-- ✓ Uses partial index:
SELECT * FROM loan_applications WHERE status = 'pending' AND created_at > '2024-01-01';
SELECT * FROM loan_applications WHERE status = 'pending';

-- ✗ Does NOT use partial index:
SELECT * FROM loan_applications WHERE created_at > '2024-01-01';
-- Predicate status='pending' not in WHERE → planner cannot use the partial index

-- Unique partial index — enforce uniqueness only for active records:
CREATE UNIQUE INDEX uq_active_loan_per_borrower
    ON loans (borrower_id)
    WHERE status = 'active';
-- Only one active loan per borrower allowed
-- Closed loans don't violate this: multiple (borrower_id, status='closed') rows fine

-- More examples of partial index predicates:
-- Index only soft-deleted records (for deletion audit queries):
CREATE INDEX ON records (deleted_at DESC) WHERE deleted_at IS NOT NULL;

-- Index only unverified emails (for verification reminder jobs):
CREATE INDEX ON users (created_at) WHERE email_verified = false;

-- Index only large transactions (for fraud detection queries):
CREATE INDEX ON transactions (amount DESC, created_at) WHERE amount > 100000;

-- Index only null values (find records missing required data):
CREATE INDEX ON kyc_documents (borrower_id) WHERE pan_number IS NULL;
```

**Q8. How does a partial index interact with query planning — when will PostgreSQL use it vs ignore it?**
A: PostgreSQL uses a partial index only when the query's WHERE clause logically implies the index predicate. The planner checks this through constraint implication — the query condition must be equal to or stronger than the index predicate:

```sql
-- Index: CREATE INDEX ON loans (created_at) WHERE status = 'pending';

-- ✓ Condition implies predicate — index used:
WHERE status = 'pending'                         -- exact match
WHERE status = 'pending' AND created_at > '2024' -- stronger (adds more conditions)
WHERE status = 'pending' AND borrower_id = 'B1'  -- stronger (additional constraint)

-- ✗ Condition does not imply predicate — index NOT used:
WHERE status = 'active'                          -- different value → different subset
WHERE status IN ('pending', 'active')            -- superset of index predicate
WHERE created_at > '2024'                        -- predicate not in WHERE at all

-- Subtle case — parameterized queries:
-- Application code:
await db.query('SELECT * FROM loans WHERE status = $1 AND created_at > $2', ['pending', date]);

-- PostgreSQL's generic plan: WHERE status = $1 → planner does not know $1='pending' at plan time
-- May not use the partial index for the generic plan
-- Force the planner to see the constant by using a literal or enabling plan caching:
await db.query('SELECT * FROM loans WHERE status = $1 AND created_at > $2',
               ['pending', date], { text: true }); // pg driver option

-- Or restructure the query to use literal:
await db.query(`SELECT * FROM loans WHERE status = 'pending' AND created_at > $1`, [date]);
-- Now planner sees literal 'pending' → can use partial index

-- Checking if partial index is used:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM loans WHERE status = 'pending' AND created_at > '2024-01-01';
-- Look for: "Index Scan using idx_loans_pending on loans"
-- NOT: "Seq Scan" or "Index Scan using idx_loans_status (full index)"

-- Partial index on expression:
CREATE INDEX ON users (LOWER(email)) WHERE active = true;
-- Enables: WHERE LOWER(email) = 'user@example.com' AND active = true
-- Only indexes active users' emails — smaller, avoids deactivated accounts

-- Partial index for NULL values (rare use — index a "missing data" set):
CREATE INDEX ON applications (submitted_at) WHERE reviewed_at IS NULL;
-- Query: find all applications not yet reviewed, ordered by submission date:
SELECT * FROM applications
WHERE reviewed_at IS NULL
ORDER BY submitted_at
LIMIT 100;
-- Partial index is exactly this set, already sorted by submitted_at → fast pagination
```

**Q9. What are the maintenance and storage tradeoffs of partial indexes versus full indexes?**

```sql
-- Storage comparison (real numbers):
-- Table: loan_applications, 10M rows, 200K pending

-- Full index on (status, created_at):
-- ~10M entries × (8 bytes status + 8 bytes created_at + 6 bytes ctid) ≈ 220 MB

-- Partial index on (created_at) WHERE status='pending':
-- ~200K entries × (8 bytes created_at + 6 bytes ctid) ≈ 2.8 MB
-- → 98.7% smaller → fits in shared_buffers → dramatically faster

-- Write overhead comparison:
-- INSERT a new pending loan:
--   Full index: must insert into full 220MB index (may cause page splits)
--   Partial index: must insert into 2.8MB index (almost always in memory)
-- UPDATE status from pending to processed:
--   Full index: update entry in full index (key change: remove old, add new)
--   Partial index: DELETE from partial index (row no longer matches WHERE)
--   → one operation vs two for full index on status changes

-- Vacuum and bloat:
-- Full index: MVCC dead tuples accumulate across all 10M rows
-- Partial index: dead tuples only from the 200K pending rows → vacuum faster

-- When partial indexes are NOT the right choice:
-- 1. The "interesting" subset is large (>20-30% of table):
--    Partial index nearly same size as full — storage savings minimal
--    But write overhead increases (must check predicate on every write)

-- 2. The subset is very dynamic (rows frequently enter and leave the predicate):
--    Every status change → insert into or delete from partial index
--    High churn on the indexed column negates write efficiency benefits

-- 3. Multiple queries with different predicates:
--    Separate partial indexes for each: WHERE status='pending', WHERE status='active'
--    → multiple small indexes vs one full index → combined may exceed full index size
--    → consider: one composite full index + one partial for hottest subset

-- Monitoring partial index health:
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename = 'loan_applications'
ORDER BY pg_relation_size(indexrelid) DESC;
```

## Section 4: Covering Indexes (`INCLUDE`)

**Q10. What is a covering index and what is the difference between a key column and an `INCLUDE` column?**
A: A covering index is one that contains all columns a query needs — so PostgreSQL can answer the query entirely from the index without touching the heap (the main table). The `INCLUDE` clause (PostgreSQL 11+) adds extra columns to the leaf nodes of the index without making them part of the sort key:

```
B-tree structure with INCLUDE:

  CREATE INDEX ON loans (status, created_at) INCLUDE (amount, borrower_id);

  Internal nodes (for navigation only):
    Contains: status, created_at (key columns)
    Does NOT contain: amount, borrower_id

  Leaf nodes (for data retrieval):
    Contains: status, created_at, amount, borrower_id, ctid
    ← amount and borrower_id stored here, not in internal nodes

Key column (part of sort key):
  - Used for navigation through the B-tree
  - Determines which queries can use the index
  - Stored in ALL nodes (internal + leaf)
  - Can be used in WHERE, JOIN, ORDER BY

INCLUDE column (non-key, leaf-only):
  - NOT used for navigation
  - Stored ONLY in leaf nodes
  - Cannot be used in WHERE or ORDER BY to leverage the index
  - Purpose: avoid heap access by having the value already in the leaf

Why INCLUDE instead of just adding another key column?
  CREATE INDEX ON loans (status, created_at, amount, borrower_id);
  vs
  CREATE INDEX ON loans (status, created_at) INCLUDE (amount, borrower_id);

  Difference:
    Key version: amount and borrower_id in internal nodes → larger internal nodes
                 → fewer keys per page → taller tree → more I/O for navigation
    INCLUDE version: amount and borrower_id only in leaf nodes → internal nodes stay slim
                     → more keys per internal node page → shorter tree → faster navigation
                     → leaf nodes are larger (same data), but navigation is faster

  Additionally:
    Key version: WHERE amount > 50000 CAN use the index for navigation
    INCLUDE version: WHERE amount > 50000 CANNOT use the index for navigation
                     (amount not a key → no B-tree ordering on it)
    → choose INCLUDE when you only need the value fetched, not filtered/sorted
```

**Q11. What is an index-only scan and how does `INCLUDE` enable it?**
A: An index-only scan is when PostgreSQL reads all required data from the index leaf nodes without accessing the heap at all. This is typically 5–10× faster for read-heavy queries because the index is smaller, sorted, and more likely to be in memory:

```sql
-- Setup:
CREATE TABLE loans (
    id          UUID PRIMARY KEY,
    status      TEXT,
    created_at  TIMESTAMPTZ,
    amount      NUMERIC(15,2),
    borrower_id UUID,
    -- ... 20 more columns
);

-- Query: dashboard summary — only needs status, created_at, amount
SELECT status, created_at, amount
FROM loans
WHERE status = 'active'
ORDER BY created_at DESC
LIMIT 50;

-- Without covering index (Index Scan + Heap Fetch):
CREATE INDEX idx_status_created ON loans (status, created_at DESC);

EXPLAIN ANALYZE SELECT status, created_at, amount FROM loans
WHERE status = 'active' ORDER BY created_at DESC LIMIT 50;
-- Index Scan using idx_status_created on loans
--   Index Cond: (status = 'active')
-- → "amount" NOT in index → must fetch heap for every row
-- Heap Fetches: 50
-- Even though we only need 3 columns, must read full heap rows (potentially wide rows)

-- With covering index (Index-Only Scan):
CREATE INDEX idx_status_created_covering ON loans (status, created_at DESC)
INCLUDE (amount);

EXPLAIN ANALYZE SELECT status, created_at, amount FROM loans
WHERE status = 'active' ORDER BY created_at DESC LIMIT 50;
-- Index Only Scan using idx_status_created_covering on loans
--   Index Cond: (status = 'active')
-- Heap Fetches: 0      ← never touched the heap!
-- All required columns (status, created_at, amount) found in index leaf nodes

-- The visibility map caveat:
-- Index-only scan requires the page to be marked "all-visible" in the visibility map
-- PostgreSQL needs to verify tuple visibility (MVCC) even for index-only scans
-- If the page is not all-visible: must check heap for visibility → "Heap Fetches > 0"
-- VACUUM sets all-visible bits → run VACUUM on write-heavy tables for index-only scan benefit

-- Checking heap fetches in production:
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, created_at, amount FROM loans
WHERE status = 'active' ORDER BY created_at DESC LIMIT 50;
-- Look for:
--   "Index Only Scan" → good, might be using INCLUDE columns
--   "Heap Fetches: 0" → perfect, fully index-only
--   "Heap Fetches: N" → some pages not all-visible, VACUUM needed

-- Columns that are good candidates for INCLUDE:
-- 1. Frequently SELECTed alongside the filter columns
-- 2. NOT used in WHERE / ORDER BY (those belong as key columns)
-- 3. Wide enough that avoiding heap access is meaningful (UUIDs, TEXT, JSONB snippets)
-- 4. Not frequently updated (updates to INCLUDE columns still require index maintenance)
```

**Q12. How does `INCLUDE` interact with unique constraints and primary keys?**
A: `INCLUDE` columns can be added to unique indexes and primary keys to create covering constraints — the uniqueness is still on the key columns, but the leaf nodes store additional data:

```sql
-- Standard unique index (only key columns):
CREATE UNIQUE INDEX uq_loans_reference ON loans (reference_code);
-- Enforces: no two rows with the same reference_code
-- But queries need: SELECT id, status FROM loans WHERE reference_code = 'REF-12345'
-- → must access heap for id and status

-- Unique index with INCLUDE (covering unique constraint):
CREATE UNIQUE INDEX uq_loans_reference_covering ON loans (reference_code)
INCLUDE (id, status, amount);
-- Still enforces: no duplicate reference_code
-- But now: SELECT id, status, amount FROM loans WHERE reference_code = 'REF-12345'
-- → Index Only Scan → no heap access

-- Primary key with INCLUDE (PostgreSQL 11+):
-- Cannot add INCLUDE to PRIMARY KEY directly in CREATE TABLE syntax
-- Workaround: create a unique index with INCLUDE, then use it as a constraint

-- For lookup-by-PK patterns where you also need a few extra columns:
CREATE UNIQUE INDEX pk_loans_covering ON loans (id) INCLUDE (status, amount, borrower_id);

-- Typical API pattern: GET /loans/:id → return id, status, amount, borrower_id
-- With pk_loans_covering: Index Only Scan → 0 heap fetches → extremely fast

-- Foreign key enforcement with INCLUDE:
-- PostgreSQL checks FK references using the referenced table's index
-- If you INCLUDE the FK columns in an index on the referencing side, queries
-- that JOIN on FK can become index-only:

CREATE INDEX ON disbursements (loan_id) INCLUDE (amount, disbursed_at);
-- Query: SELECT d.amount, d.disbursed_at FROM disbursements d WHERE d.loan_id = 'L1'
-- Index Only Scan → 0 heap fetches
```

## Section 5: Combining All Three

**Q13. How do you combine composite, partial, and covering index features into a single index?**
A: All three features compose freely — a single index can be composite (multiple key columns), partial (WHERE clause), and covering (INCLUDE columns). The combination targets a specific query pattern precisely:

```sql
-- Target query: active loan dashboard for a specific tenant
SELECT id, amount, borrower_id
FROM loans
WHERE tenant_id = 'T1'
  AND status = 'active'
  AND created_at > NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 100;

-- Naive approach: full index on all filter columns
CREATE INDEX idx_naive ON loans (tenant_id, status, created_at DESC);
-- Problem: indexes ALL rows (including processed/rejected from 5 years ago)
--          doesn't include id, amount, borrower_id → heap access required

-- Optimized: composite + partial + covering
CREATE INDEX idx_active_loans_dashboard
    ON loans (tenant_id, created_at DESC)                  -- composite key: tenant + date
    INCLUDE (id, amount, borrower_id)                      -- covering: avoid heap access
    WHERE status = 'active';                               -- partial: only active rows

-- Analysis of each component:
-- Composite (tenant_id, created_at DESC):
--   Navigates to exact tenant, then reads most-recent-first → no sort step
-- Partial (WHERE status='active'):
--   Excludes historical processed/rejected rows → 95% smaller index
--   Index fits in memory → hot cache hits
-- INCLUDE (id, amount, borrower_id):
--   All SELECT columns in leaf nodes → Index Only Scan, 0 heap fetches

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, borrower_id
FROM loans
WHERE tenant_id = 'T1'
  AND status = 'active'
  AND created_at > NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 100;
-- Index Only Scan using idx_active_loans_dashboard on loans
-- Index Cond: ((tenant_id = 'T1') AND (created_at > (now() - '30 days'::interval)))
-- Filter: none (status='active' is the partial index predicate — already filtered)
-- Heap Fetches: 0
-- Rows Removed by Filter: 0
-- Actual rows: 100   Actual total time: 0.8ms

-- vs no index: Seq Scan → ~850ms for 2M row table
-- vs composite only: Index Scan + heap fetch → ~12ms
-- vs composite + partial: Index Scan + heap fetch → ~4ms
-- vs all three combined: Index Only Scan → ~0.8ms

-- Cost of this optimized index:
-- Storage: only active loans × (tenant_id + created_at + id + amount + borrower_id)
--          ~50K rows × 60 bytes ≈ 3MB (vs 400MB for naive full composite covering index)
-- Write cost: every INSERT of active loan → written to index
--             every status change from active → deleted from index
--             updates to amount/borrower_id → index leaf updated (INCLUDE maintenance)
```

**Q14. How do you design indexes for a multi-tenant SaaS application with compound filtering patterns?**

```sql
-- Schema: multi-tenant lending platform
CREATE TABLE loan_applications (
    id              UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    borrower_id     UUID NOT NULL,
    status          TEXT NOT NULL,  -- 'draft','submitted','under_review','approved','rejected'
    loan_type       TEXT NOT NULL,  -- 'personal','home','business','education'
    amount          NUMERIC(15,2),
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW(),
    assigned_to     UUID,           -- loan officer
    credit_score    INTEGER,
    CONSTRAINT fk_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id)
);

-- Identify query patterns from the application:
-- Q1 (very frequent): tenant dashboard — list recent applications for a tenant
--   WHERE tenant_id=$1 ORDER BY created_at DESC LIMIT 20
-- Q2 (frequent): agent queue — pending applications assigned to an agent
--   WHERE tenant_id=$1 AND assigned_to=$2 AND status='submitted'
-- Q3 (frequent): status filter — applications by type and status for a tenant
--   WHERE tenant_id=$1 AND loan_type=$2 AND status=$3 ORDER BY created_at DESC
-- Q4 (occasional): credit score analysis — applications above a credit score threshold
--   WHERE tenant_id=$1 AND credit_score > $2 AND status='approved'
-- Q5 (rare): borrower history — all applications for a borrower across tenant
--   WHERE borrower_id=$1 ORDER BY created_at DESC

-- Index design:

-- Q1: composite covering index
CREATE INDEX idx_tenant_dashboard
    ON loan_applications (tenant_id, created_at DESC)
    INCLUDE (id, status, loan_type, amount);
-- Handles Q1: tenant_id filter + created_at sort + all needed columns in leaf

-- Q2: composite partial covering index
CREATE INDEX idx_agent_queue
    ON loan_applications (tenant_id, assigned_to, created_at DESC)
    INCLUDE (id, borrower_id, loan_type, amount)
    WHERE status = 'submitted';
-- Partial: only submitted applications → small, hot index
-- Covers Q2 query completely: Index Only Scan

-- Q3: composite covering index (different key order — loan_type before status)
CREATE INDEX idx_tenant_type_status
    ON loan_applications (tenant_id, loan_type, status, created_at DESC)
    INCLUDE (id, amount, assigned_to);
-- Handles Q3: all three filters as key + sort + covering

-- Q4: composite partial (approved only, credit_score as key)
CREATE INDEX idx_credit_approved
    ON loan_applications (tenant_id, credit_score DESC)
    INCLUDE (id, amount, borrower_id)
    WHERE status = 'approved';
-- Partial: only approved (minority) → small index
-- Key: (tenant_id, credit_score DESC) → WHERE credit_score > N uses range on key

-- Q5: separate index on borrower_id (cross-tenant lookup)
CREATE INDEX idx_borrower_history
    ON loan_applications (borrower_id, created_at DESC)
    INCLUDE (id, tenant_id, status, loan_type);
-- No partial: borrower history spans all statuses
-- Covering: avoids heap for the typical borrower profile page

-- Verify with pg_stat_statements (after production traffic):
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time
FROM pg_stat_statements
WHERE query LIKE '%loan_applications%'
ORDER BY total_exec_time DESC
LIMIT 10;
-- Identify slow queries that are still doing heap fetches or seq scans
-- → add INCLUDE columns or adjust key order
```

## Section 6: Observability and Maintenance

**Q15. How do you verify that an index is being used correctly and identify index bloat?**

```sql
-- ── Verifying index usage ─────────────────────────────────────────────────────

-- 1. EXPLAIN ANALYZE — see the actual execution plan:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, amount FROM loans
WHERE tenant_id = 'T1' AND status = 'active'
ORDER BY created_at DESC LIMIT 50;

-- Key things to look for:
-- "Index Only Scan" → best case, no heap access
-- "Index Scan"      → using index but hitting heap for some columns
-- "Bitmap Heap Scan" + "Bitmap Index Scan" → many rows, batching heap access
-- "Seq Scan"        → index not used (check why)
-- "Heap Fetches: 0" → truly index-only (visibility map fully set)
-- "Heap Fetches: N" → some pages need heap check (VACUUM needed)
-- "Rows Removed by Filter: N" → filter applied after index (index not tight enough)

-- 2. pg_stat_user_indexes — usage statistics:
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan AS times_used,
    idx_tup_read AS index_tuples_read,
    idx_tup_fetch AS heap_tuples_fetched,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'loans'
ORDER BY idx_scan DESC;

-- idx_scan = 0: index never used → drop it
-- idx_tup_fetch / idx_tup_read ratio ≈ 1.0: index is tight, fetching only matched rows
-- idx_tup_fetch / idx_tup_read ratio << 1: index scan returns many rows filtered later
--   → index not selective enough for the query pattern
--   → consider adding filter columns to the index or using a partial index

-- 3. pg_statio_user_indexes — buffer cache efficiency:
SELECT
    relname,
    indexrelname,
    idx_blks_read  AS disk_reads,
    idx_blks_hit   AS cache_hits,
    round(100.0 * idx_blks_hit / NULLIF(idx_blks_read + idx_blks_hit, 0), 2)
        AS cache_hit_pct
FROM pg_statio_user_indexes
WHERE relname = 'loans'
ORDER BY idx_blks_read DESC;
-- cache_hit_pct < 90%: index not fitting in shared_buffers → bloated or undersized

-- ── Index bloat detection ─────────────────────────────────────────────────────

-- Dead tuples in the index (from UPDATEs and DELETEs):
SELECT
    relname AS table_name,
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,
    -- Estimate bloat ratio (approximate):
    round(100.0 * (1 - pg_stat_get_live_tuples(indexrelid)::float
          / NULLIF(pg_stat_get_tuples_inserted(indexrelid), 0)), 2) AS bloat_estimate_pct
FROM pg_stat_user_indexes
WHERE relname = 'loans';

-- Rebuilding bloated indexes without locking (PostgreSQL 12+):
REINDEX INDEX CONCURRENTLY idx_active_loans_dashboard;
-- Builds new index in background → swaps → no table lock
-- Old index remains available during build → zero downtime

-- ── Finding missing indexes ───────────────────────────────────────────────────

-- Queries doing sequential scans on large tables:
SELECT
    schemaname,
    relname,
    seq_scan,          -- sequential scans
    seq_tup_read,      -- tuples read via seq scan
    idx_scan,          -- index scans
    n_live_tup         -- approximate row count
FROM pg_stat_user_tables
WHERE seq_scan > 0
  AND n_live_tup > 10000
ORDER BY seq_tup_read DESC;
-- High seq_tup_read on large tables → missing or unused indexes on common query columns

-- Combine with pg_stat_statements to find the specific slow queries:
SELECT
    query,
    calls,
    round(mean_exec_time::numeric, 2) AS avg_ms,
    round(total_exec_time::numeric, 2) AS total_ms
FROM pg_stat_statements
WHERE mean_exec_time > 100   -- queries averaging > 100ms
ORDER BY total_exec_time DESC;
-- Run EXPLAIN on these queries to determine what index would help
```

## Section 7: Scenario-Based Questions

**Q16. "A query fetching loan officer's pending queue takes 800ms on a 5M row table. The query is: `SELECT id, borrower_name, amount, created_at FROM loan_applications WHERE assigned_to = $1 AND status = 'pending' ORDER BY created_at ASC LIMIT 20`. Design the optimal index."**

```sql
-- Step 1: Analyse the query
-- Filter: assigned_to = $1  (equality, varies per officer)
-- Filter: status = 'pending'  (equality, low cardinality — maybe 5% of rows)
-- Order:  created_at ASC     (needs sort or index-ordered output)
-- Select: id, borrower_name, amount, created_at (must avoid heap if possible)
-- Limit:  20 (only first 20 rows needed)

-- Step 2: Estimate row distribution
-- 5M total rows
-- ~250K assigned to various officers
-- ~250K with status='pending' (~5%)
-- Maybe ~1K are (assigned_to='officer_X' AND status='pending') per officer
-- These 1K rows need to be returned in created_at order, first 20 returned

-- Step 3: Index design options

-- Option A: composite only
CREATE INDEX ON loan_applications (assigned_to, status, created_at ASC);
-- Navigates to assigned_to='officer_X', status='pending', scans in created_at order
-- But: SELECT needs id, borrower_name, amount → heap fetch for each of 20 rows
-- And: indexes all statuses, not just pending

-- Option B: partial composite (no INCLUDE yet)
CREATE INDEX ON loan_applications (assigned_to, created_at ASC)
WHERE status = 'pending';
-- Smaller: only 5% of rows (pending only)
-- For LIMIT 20: reads first 20 leaf entries for assigned_to='officer_X'
-- Still: heap fetch for id, borrower_name, amount

-- Option C: partial composite covering ← OPTIMAL
CREATE INDEX idx_officer_pending_queue
    ON loan_applications (assigned_to, created_at ASC)
    INCLUDE (id, borrower_name, amount)
    WHERE status = 'pending';

-- Why this is optimal:
-- Partial (status='pending'): ~5% of rows → index is 20× smaller than full
-- Key (assigned_to, created_at ASC): navigates to officer, reads in date order
-- INCLUDE (id, borrower_name, amount): all SELECT columns in leaf nodes
-- LIMIT 20: reads exactly 20 leaf nodes → stops → never reads heap

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, borrower_name, amount, created_at
FROM loan_applications
WHERE assigned_to = 'OA-123' AND status = 'pending'
ORDER BY created_at ASC LIMIT 20;
-- Index Only Scan using idx_officer_pending_queue
-- Index Cond: (assigned_to = 'OA-123')
-- Heap Fetches: 0
-- Actual rows: 20   Actual time: 0.3ms  ← from 800ms

-- Step 4: Verify the index predicate is usable with parameterized queries
-- Using status = 'pending' as a literal in the query ensures the planner
-- can match it to the partial index predicate:
await db.query(`
    SELECT id, borrower_name, amount, created_at
    FROM loan_applications
    WHERE assigned_to = $1 AND status = 'pending'
    ORDER BY created_at ASC LIMIT 20
`, [officerId]);
-- status = 'pending' is a literal → planner uses partial index ✓
```

**Q17. "Your `pg_stat_user_indexes` shows an index with `idx_scan = 0` after 3 months in production. How do you safely decide whether to drop it?"**

```sql
-- An index with zero scans wastes storage and slows every write.
-- But dropping the wrong index can kill query performance. Systematic approach:

-- Step 1: Gather context before deciding
SELECT
    indexname,
    indexdef,                                              -- see what columns it covers
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan,
    pg_stat_get_last_autoanalyze_time(relid) AS last_analyze
FROM pg_stat_user_indexes
JOIN pg_stat_user_tables USING (relid)
WHERE indexrelname = 'idx_to_evaluate';

-- Step 2: Check when statistics were last reset (idx_scan = 0 may just mean reset recently)
SELECT stats_reset FROM pg_stat_bgwriter;
-- If stats_reset was 2 days ago: 0 scans is not meaningful
-- If stats_reset was 90+ days ago: 0 scans is strong evidence of unused index

-- Step 3: Check what the index covers — is it a unique constraint?
SELECT conname, contype FROM pg_constraint
WHERE conindid = (SELECT oid FROM pg_class WHERE relname = 'idx_to_evaluate');
-- contype = 'u' (unique) or 'p' (primary key): DO NOT DROP — constraint enforcement
-- contype = NULL: purely for query performance → safe to consider dropping

-- Step 4: Search application code and query logs for the columns
-- Check pg_stat_statements for queries that reference the indexed columns:
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
WHERE query ~* 'loan_applications'  -- table name
  AND query ~* 'column_in_index';   -- column(s) the index covers
-- If no matching queries: column is never used in WHERE → index is truly unused

-- Step 5: Check for batch jobs or cron jobs that may run infrequently
-- A quarterly report may run idx_scan=4 per year — would show 0 after 3 months
-- Check job schedules before dropping

-- Step 6: Safe removal — use a temporary rename first
-- Instead of dropping immediately, rename to signal "candidate for removal":
ALTER INDEX idx_old_unused RENAME TO idx_old_unused_DROP_CANDIDATE;
-- Monitor for 2 more weeks — if no errors and no query complaints:
DROP INDEX CONCURRENTLY idx_old_unused_DROP_CANDIDATE;
-- CONCURRENTLY: drops without locking the table (takes longer but safe for production)

-- Step 7: If unsure — use pg_hint_plan or SET enable_indexscan=off to test
-- Temporarily disable the index for a test query and see if it slows down:
SET enable_indexscan = off;
EXPLAIN ANALYZE <the query you think this index serves>;
SET enable_indexscan = on;
-- If plan changes significantly and gets much slower: index WAS being used somehow
-- (perhaps by a different code path than you expected)
```

**Q18. "A daily cron job queries all overdue loans: `SELECT id, borrower_id, due_date, amount FROM loans WHERE due_date < NOW() AND status = 'active'`. The table has 8M rows and the query takes 45 seconds. Design the solution."**

```sql
-- Analysis:
-- 8M total rows
-- status='active': probably 10-15% (long-term platform)
-- due_date < NOW(): unknown — depends on how many active loans are overdue
-- If platform is healthy: maybe 2-5% are overdue → highly selective combined filter
-- If platform has problems: maybe 30-40% overdue → less selective

-- Step 1: Check current situation
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, borrower_id, due_date, amount
FROM loans
WHERE due_date < NOW() AND status = 'active';
-- If Seq Scan: no useful index exists
-- If Index Scan with high "Rows Removed by Filter": index on one column, not both

-- Step 2: Design the index

-- Option A: partial index on active loans (if active is minority)
CREATE INDEX idx_active_overdue
    ON loans (due_date ASC)
    INCLUDE (id, borrower_id, amount)
    WHERE status = 'active';

-- Why:
-- Partial (status='active'): maybe 800K rows out of 8M → 10× smaller
-- Key (due_date ASC): WHERE due_date < NOW() is a range scan on leading key
--   PostgreSQL navigates to the start of the index, scans forward until due_date >= NOW()
-- INCLUDE (id, borrower_id, amount): all SELECT columns → Index Only Scan

-- Query compatibility with partial index:
SELECT id, borrower_id, due_date, amount
FROM loans
WHERE due_date < NOW()
  AND status = 'active';  -- literal 'active' → matches partial index predicate
-- Index Only Scan → reads only overdue active loans → no heap access

-- Option B: if active loans are majority (bad case), use composite without partial
CREATE INDEX idx_status_duedate_covering
    ON loans (status, due_date ASC)
    INCLUDE (id, borrower_id, amount);
-- Key: (status, due_date) → WHERE status='active' AND due_date < NOW()
-- INCLUDE: covers SELECT columns

-- Step 3: Check VACUUM status (for Index Only Scan to work)
SELECT
    relname,
    last_vacuum,
    last_autovacuum,
    n_dead_tup,
    n_live_tup
FROM pg_stat_user_tables
WHERE relname = 'loans';
-- If last_autovacuum was long ago and n_dead_tup is high:
VACUUM ANALYZE loans;  -- sets visibility map → enables Index Only Scan (Heap Fetches: 0)

-- Step 4: Validate
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, borrower_id, due_date, amount
FROM loans
WHERE due_date < NOW() AND status = 'active';
-- Expected: Index Only Scan → Heap Fetches: 0 → ~200ms instead of 45s

-- Step 5: Additional optimization — if the cron job can tolerate slight staleness
-- Run under REPEATABLE READ so the snapshot is consistent for the whole export:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT id, borrower_id, due_date, amount
FROM loans
WHERE due_date < NOW() AND status = 'active'
ORDER BY due_date ASC;  -- process oldest overdue first
COMMIT;
-- READ ONLY hint allows PostgreSQL to skip certain lock acquisitions
```

## Quick Reference Table

| Index type | Syntax | Best for | Storage vs full index |
|---|---|---|---|
| Composite | `(col_a, col_b, col_c)` | Queries filtering multiple columns together | Same as full if all rows indexed |
| Partial | `(col) WHERE predicate` | Queries always filtering a minority subset | Proportional to matching rows |
| Covering (INCLUDE) | `(col_a) INCLUDE (col_b, col_c)` | Avoid heap access for frequent SELECT columns | Larger leaf nodes; same internal nodes |
| Partial + Covering | `(col_a) INCLUDE (col_b) WHERE pred` | Hot minority of rows, index-only reads | Smallest possible for targeted pattern |
| Expression | `(LOWER(col))` | Case-insensitive or transformed filter | Same as standard, stores expression result |

| Decision | Guideline |
|---|---|
| Leading column order | Most common equality filter first; range filter last; high cardinality before low |
| Key vs INCLUDE | Key: used in WHERE / ORDER BY. INCLUDE: only SELECTed, never filtered |
| Partial predicate | Use when subset queried is < 20-30% of table and predicate is always present |
| When to drop an index | idx_scan = 0 after 90+ days, no unique constraint, not a FK support index |
| When to REINDEX | High bloat (frequent updates on indexed columns), Heap Fetches unexpectedly high |
| VACUUM importance | Run VACUUM ANALYZE before expecting Index Only Scans; sets visibility map |
| Composite vs multiple single | Composite wins for always-together filters; separate for independent filters |

---

**Tip for interviews:** Five things separate strong candidates on PostgreSQL indexes: (1) stating the **leading column rule precisely** (Q3, Q4) — a composite index on `(a, b, c)` can serve queries on `(a)`, `(a, b)`, `(a, b, c)` but not `(b)`, `(b, c)`, or `(a, c)` with a gap; and knowing the corollary that a query filtering on a non-leading column needs its own separate index; (2) explaining **why INCLUDE columns are in leaf nodes only** (Q10) — they don't affect B-tree navigation (internal nodes stay slim) but allow Index Only Scans by putting the SELECT columns in the leaf without enlarging the sort key; (3) knowing that **Index Only Scans require the visibility map to be set** (Q11) — without VACUUM, PostgreSQL still has to check the heap for MVCC visibility even if all columns are in the index, so `Heap Fetches > 0` after adding an INCLUDE index is a VACUUM problem, not an index problem; (4) being precise about **when a partial index predicate is matched** (Q8) — the query's WHERE clause must logically imply the index predicate, parameterized queries with `$1` may not match at plan time, and `status = 'pending'` as a literal in the query is required to trigger the partial index; and (5) combining all three into a **composite partial covering index** with a concrete example (Q13, Q16) — showing you understand that `(key_columns) INCLUDE (select_columns) WHERE predicate` is the way to target a specific hot query pattern with the smallest possible index that answers it entirely from the index leaves.
