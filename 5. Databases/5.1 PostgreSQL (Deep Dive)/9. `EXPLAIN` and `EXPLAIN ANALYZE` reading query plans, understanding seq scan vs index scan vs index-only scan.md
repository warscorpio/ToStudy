# PostgreSQL `EXPLAIN` and `EXPLAIN ANALYZE`: Reading Query Plans — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a query plan and why does PostgreSQL generate one before executing every query?**

A: Before executing any SQL statement, PostgreSQL's query planner (also called the optimizer) produces an execution plan — a tree of operations describing exactly how it will retrieve and process the data. The planner generates multiple candidate plans and picks the one with the lowest estimated cost. Understanding this plan is the foundation of query optimization.

```sql
-- Without EXPLAIN: query executes, you see only the result
SELECT * FROM orders WHERE user_id = 42;

-- With EXPLAIN: shows the plan WITHOUT executing the query
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

--                              QUERY PLAN
-- ─────────────────────────────────────────────────────────────────────────────
--  Index Scan using orders_user_id_idx on orders  (cost=0.43..8.45 rows=3 width=96)
--    Index Cond: (user_id = 42)
-- (2 rows)

-- With EXPLAIN ANALYZE: executes the query AND shows actual runtime statistics
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;

--  Index Scan using orders_user_id_idx on orders
--    (cost=0.43..8.45 rows=3 width=96)
--    (actual time=0.042..0.051 rows=3 loops=1)
--  Planning Time: 0.112 ms
--  Execution Time: 0.078 ms
```

The planner's job — choosing between alternative plans:

```
For: SELECT * FROM orders WHERE user_id = 42 AND status = 'pending'

Candidate plans the planner evaluates:
  Plan A: Sequential scan → filter user_id=42 AND status='pending'
  Plan B: Index scan on orders_user_id_idx → filter status='pending'
  Plan C: Index scan on orders_status_idx → filter user_id=42
  Plan D: Bitmap scan combining both indexes
  Plan E: Index scan on composite (user_id, status) index (if it exists)

Planner picks the plan with lowest estimated total cost.
Cost = estimated disk I/O pages × random_page_cost
     + estimated CPU operations × cpu_tuple_cost
     + estimated index lookups × cpu_index_tuple_cost
```

Why the planner can be wrong — statistics:

```sql
-- The planner uses statistics collected by ANALYZE (run automatically by autovacuum)
-- Statistics live in pg_statistic and are viewable via pg_stats

SELECT attname, n_distinct, correlation, most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

-- n_distinct:     estimated number of distinct values (-1 = all distinct, -0.5 = 50% distinct)
-- correlation:    physical vs logical order correlation (1.0 = perfectly sorted = cheap seq scan)
-- most_common_vals:  ['pending','shipped','delivered','cancelled']
-- most_common_freqs: [0.45, 0.30, 0.20, 0.05]

-- If statistics are stale (table changed dramatically since last ANALYZE),
-- the planner uses wrong estimates → chooses a bad plan
-- Fix: run ANALYZE orders; or VACUUM ANALYZE orders;
```

**Q2. What is the difference between `EXPLAIN` and `EXPLAIN ANALYZE` — when do you use each?**

A: The distinction is critical: `EXPLAIN` estimates, `EXPLAIN ANALYZE` measures. Each serves a different diagnostic purpose:

```sql
-- EXPLAIN: planning only — no query execution
-- Use when:
--   - Query is destructive (DELETE, UPDATE) and you don't want side effects
--   - Query takes too long to run even once in prod
--   - You want to check if an index will be used without paying execution cost
--   - Comparing plan choices by tweaking configuration parameters

EXPLAIN DELETE FROM sessions WHERE expires_at < NOW();
--  Delete on sessions  (cost=0.00..2847.33 rows=0 width=0)
--    ->  Seq Scan on sessions  (cost=0.00..2847.33 rows=47823 width=6)
--          Filter: (expires_at < now())
-- Safe — no rows deleted

-- EXPLAIN ANALYZE: executes the query AND collects runtime stats
-- Use when:
--   - Diagnosing why a query is slow in production
--   - Checking whether estimated rows match actual rows (plan quality)
--   - Identifying which node in a complex plan is the bottleneck
--   - Verifying that a new index is actually being used

EXPLAIN ANALYZE SELECT count(*) FROM orders WHERE status = 'pending';
--  Aggregate  (cost=5832.10..5832.11 rows=1 width=8)
--             (actual time=42.310..42.311 rows=1 loops=1)
--    ->  Seq Scan on orders  (cost=0.00..5589.00 rows=97240 width=0)
--                            (actual time=0.025..38.104 rows=97240 loops=1)
--          Filter: ((status)::text = 'pending'::text)
--          Rows Removed by Filter: 102760
--  Planning Time: 0.182 ms
--  Execution Time: 42.381 ms

-- WARNING: EXPLAIN ANALYZE on DML runs the DML for real!
-- Wrap in a transaction and roll back to safely analyze DML:
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'processing' WHERE status = 'pending';
ROLLBACK;
-- Now the UPDATE ran (for timing purposes) but changes are rolled back
```

The full set of `EXPLAIN` options:

```sql
-- EXPLAIN (FORMAT JSON) — machine-readable, better for programmatic parsing
EXPLAIN (FORMAT JSON) SELECT * FROM orders WHERE user_id = 42;

-- EXPLAIN (ANALYZE, BUFFERS) — adds I/O statistics (most useful for diagnosis)
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
--  Index Scan using orders_user_id_idx on orders
--    (cost=0.43..8.45 rows=3 width=96)
--    (actual time=0.042..0.051 rows=3 loops=1)
--    Buffers: shared hit=4
--             ^^^^^^^^^^^^^^^^^
--             'shared hit=4' means 4 pages read from shared_buffers (RAM cache)
--             'shared read=4' would mean read from disk (much slower)
--             'shared written=1' means dirty pages written out

-- EXPLAIN (ANALYZE, BUFFERS, VERBOSE) — adds column-level details, schema names
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
    SELECT u.email, COUNT(o.id)
    FROM users u
    LEFT JOIN orders o ON o.user_id = u.id
    GROUP BY u.email;

-- EXPLAIN (ANALYZE, TIMING OFF) — disables per-node timing (faster for tight loops)
-- Timing has overhead; use TIMING OFF when loops=many_thousands and timing is skewing results

-- Most useful combination for real diagnosis:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) <your slow query>;
```

## Section 2: Reading the Query Plan

**Q3. How do you read the structure of an EXPLAIN output — what do the nodes, costs, and indentation mean?**

A: A query plan is a tree of nodes. Each node is one operation. Indentation shows the parent-child relationship — a child node feeds data to its parent. Execution flows bottom-up: leaf nodes run first, root node last:

```sql
EXPLAIN ANALYZE
    SELECT u.email, COUNT(o.id) as order_count
    FROM users u
    JOIN orders o ON o.user_id = u.id
    WHERE u.created_at > '2024-01-01'
    GROUP BY u.email
    ORDER BY order_count DESC
    LIMIT 10;
```

```
Limit  (cost=15234.56..15234.58 rows=10 width=40)
       (actual time=156.234..156.237 rows=10 loops=1)
  ->  Sort  (cost=15234.56..15236.06 rows=600 width=40)
            (actual time=156.232..156.233 rows=10 loops=1)
        Sort Key: (count(o.id)) DESC
        Sort Method: top-N heapsort  Memory: 25kB
        ->  HashAggregate  (cost=15198.00..15204.00 rows=600 width=40)
                           (actual time=155.876..156.134 rows=847 loops=1)
              Group Key: u.email
              Batches: 1  Memory Usage: 233kB
              ->  Hash Join  (cost=2847.50..14448.00 rows=150000 width=32)
                             (actual time=28.456..140.234 rows=148293 loops=1)
                    Hash Cond: (o.user_id = u.id)
                    ->  Seq Scan on orders o  (cost=0.00..9250.00 rows=200000 width=16)
                                             (actual time=0.012..52.341 rows=200000 loops=1)
                    ->  Hash  (cost=2660.00..2660.00 rows=15000 width=24)
                              (actual time=27.876..27.876 rows=15432 loops=1)
                              Buckets: 16384  Batches: 1  Memory Usage: 897kB
                          ->  Seq Scan on users u  (cost=0.00..2660.00 rows=15000 width=24)
                                                   (actual time=0.010..22.432 rows=15432 loops=1)
                                Filter: (created_at > '2024-01-01'::date)
                                Rows Removed by Filter: 4568
Planning Time: 1.234 ms
Execution Time: 156.450 ms
```

Anatomy of each node line:

```
Seq Scan on orders o  (cost=0.00..9250.00 rows=200000 width=16)
                      (actual time=0.012..52.341 rows=200000 loops=1)
│                     │    │        │       │       │    │       │
│                     │    │        │       │       │    │       └── how many times this node ran
│                     │    │        │       │       │    └── actual rows returned
│                     │    │        │       │       └── actual end time (ms since query start)
│                     │    │        │       └── actual start time (ms since query start)
│                     │    │        └── estimated rows to return
│                     │    └── estimated total cost (to return all rows)
│                     └── estimated startup cost (before first row returned)
└── node type and target
```

Cost units — understanding the scale:

```sql
-- Cost is in arbitrary units, NOT milliseconds
-- Default cost parameters:
-- seq_page_cost     = 1.0  (reading a page sequentially)
-- random_page_cost  = 4.0  (random page read — much more expensive)
-- cpu_tuple_cost    = 0.01 (processing one row in CPU)
-- cpu_index_tuple_cost = 0.005 (processing one index entry)
-- cpu_operator_cost = 0.0025 (one operator evaluation)

-- A cost of 9250.00 on a seq scan means:
-- ~9250 / 1.0 = 9250 sequential page reads (if the table is large)
-- OR: many CPU operations on many rows

-- Costs are CUMULATIVE: child costs are included in parent costs
-- Limit's cost=15234.56 includes all costs below it in the tree

-- Key diagnostic: compare estimated vs actual rows
-- Large divergence = stale statistics = bad plan choices
-- Here: HashAggregate estimated 600 rows, got 847 → acceptable
-- But if it estimated 600 and got 150,000 → serious statistics problem
```

The `loops` counter and what it means:

```sql
-- loops=1: this node ran once (typical for outer table scans)
-- loops=N: this node ran N times (typically for inner sides of nested loops)

-- When a node has loops=N, the actual time shown is PER LOOP (not total):
-- actual time=0.042..0.051 rows=3 loops=5000
-- Total actual time = 0.051ms × 5000 = 255ms  ← the REAL cost
-- Total rows returned = 3 × 5000 = 15000

-- This is a critical reading mistake: forgetting to multiply by loops
-- A tiny-looking node with loops=100000 can be the query's bottleneck
```

**Q4. What are the most important numbers to look at when diagnosing a slow query plan?**

A: With a complex plan, you need a triage strategy — not every number matters equally. Check these in order:

```sql
EXPLAIN (ANALYZE, BUFFERS)
    SELECT o.id, o.total, u.email
    FROM orders o
    JOIN users u ON u.id = o.user_id
    WHERE o.status = 'pending'
    ORDER BY o.created_at DESC
    LIMIT 20;

--  Limit  (cost=0.86..218.54 rows=20 width=52)
--         (actual time=0.089..1.243 rows=20 loops=1)
--    ->  Nested Loop  (cost=0.86..1059834.23 rows=97240 width=52)
--                     (actual time=0.088..1.238 rows=20 loops=1)
--          ->  Index Scan Backward using orders_created_at_idx on orders o
--                (cost=0.43..75432.10 rows=97240 width=36)
--                (actual time=0.045..0.068 rows=20 loops=1)
--                  Filter: ((status)::text = 'pending'::text)
--                  Rows Removed by Filter: 0
--          ->  Index Scan using users_pkey on users u
--                (cost=0.43..0.99 rows=1 width=24)
--                (actual time=0.058..0.058 rows=1 loops=20)
--                  Index Cond: (id = o.user_id)
--                  Buffers: shared hit=60
--  Planning Time: 0.445 ms
--  Execution Time: 1.289 ms
```

Triage checklist in priority order:

```
1. Total Execution Time (bottom of output)
   → "Execution Time: 1.289 ms" — is this acceptable?
   → If fast: stop here. If slow: continue investigating.

2. Estimated vs Actual Rows — the most important diagnostic
   → Large divergence = planner chose wrong plan
   → Rule of thumb: if actual_rows > estimated_rows × 10 → statistics problem

   In the plan above:
   orders seq scan: estimated 97240, actual 20 — seems wrong!
   BUT: actual=20 because Limit stopped the scan after 20 rows
   The Nested Loop only fetched 20 outer rows (LIMIT propagated)
   This is correct behaviour — not a statistics problem here

3. Find the most time-consuming node
   → Look for the node where (actual_end_time × loops) is highest
   → Or sort by (actual_end_time - actual_start_time) × loops

4. Buffers: shared read vs shared hit
   → shared hit=60: pages found in RAM cache (fast)
   → shared read=60: pages read from disk (slow, potential I/O bottleneck)
   → High read count with slow query → add more RAM or optimize to avoid large scans

5. "Rows Removed by Filter" on a scan
   → "Rows Removed by Filter: 50000" on a Seq Scan
   → means 50000 rows were read and discarded → index could help

6. Sort Method: disk vs memory
   → "Sort Method: external merge  Disk: 4520kB" → sort spilled to disk → slow
   → "Sort Method: quicksort  Memory: 25kB" → in-memory → fast
   → Fix: increase work_mem, or add an index that provides pre-sorted output

7. Hash Batches > 1
   → "Batches: 4  Memory Usage: 4096kB" → hash join spilled to disk
   → Fix: increase work_mem
```

## Section 3: Scan Types

**Q5. What is a Sequential Scan — when does PostgreSQL choose it and when is it a problem?**

A: A sequential scan (Seq Scan) reads every page of a table from beginning to end, examining each row against the filter condition. It is the simplest access method and sometimes the correct choice:

```sql
-- A seq scan:
EXPLAIN SELECT * FROM orders WHERE status = 'pending';

--  Seq Scan on orders  (cost=0.00..5589.00 rows=97240 width=96)
--    Filter: ((status)::text = 'pending'::text)

-- Physical execution:
-- 1. Read first page (8KB) of orders table from disk (or cache)
-- 2. Examine each row on that page: does status = 'pending'?
-- 3. Return matching rows
-- 4. Read next page, repeat until end of table
```

When a seq scan is the CORRECT choice:

```sql
-- Case 1: High selectivity — most rows match anyway
-- If 90% of orders have status='pending', scanning all and returning 90% is efficient
-- An index would add overhead for nearly no benefit

-- Case 2: Small table — fits in a few pages
-- A table with 100 rows: seq scan reads 1 page → faster than index overhead
-- PostgreSQL's threshold: roughly, if the scan reads < ~5% of table pages via random I/O,
-- it prefers the index; otherwise seq scan

-- Case 3: Table is freshly loaded and ordered — high correlation
SELECT correlation FROM pg_stats WHERE tablename='orders' AND attname='created_at';
-- correlation: 0.99 → rows physically stored in created_at order
-- Sequential scan on ordered data is extremely cache-friendly → fast

-- Forcing a seq scan to test alternatives:
SET enable_indexscan = off;
SET enable_bitmapscan = off;
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- Now planner must use seq scan — useful for comparison
RESET enable_indexscan;
RESET enable_bitmapscan;
```

When a seq scan is a PROBLEM:

```sql
-- Seq Scan on a large table filtering a small fraction of rows:
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
--  Seq Scan on orders  (cost=0.00..5589.00 rows=3 width=96)
--                      (actual time=12.340..156.789 rows=3 loops=1)
--    Filter: (user_id = 42)
--    Rows Removed by Filter: 199997   ← Read 200,000 rows to find 3

-- "Rows Removed by Filter: 199997" with actual rows=3 is the red flag
-- Fix: create an index on user_id

CREATE INDEX orders_user_id_idx ON orders(user_id);
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
--  Index Scan using orders_user_id_idx on orders  (cost=0.43..8.45 rows=3 width=96)
--                                                 (actual time=0.042..0.051 rows=3 loops=1)
-- 156ms → 0.051ms

-- Common reasons the planner chooses seq scan despite a relevant index:
-- 1. Estimated selectivity is too low (statistics think many rows match)
--    Fix: ANALYZE the table
-- 2. random_page_cost is set too high (not reflecting SSD reality)
--    For SSDs: SET random_page_cost = 1.1; (close to seq_page_cost)
-- 3. The index is bloated / not being used (pg_stat_user_indexes.idx_scan = 0)
-- 4. Table is small enough that seq scan is genuinely faster
-- 5. Implicit type cast prevents index use (see Q9)
```

**Q6. What is an Index Scan — how does it work and what does its plan output tell you?**

A: An index scan uses a B-tree (or other index type) to find the exact pages and row locations that satisfy the condition, then fetches those specific rows from the heap (the actual table storage). It trades sequential I/O for precision:

```sql
EXPLAIN (ANALYZE, BUFFERS)
    SELECT id, email, created_at
    FROM users
    WHERE email = 'alice@example.com';

--  Index Scan using users_email_key on users
--    (cost=0.43..8.45 rows=1 width=48)
--    (actual time=0.054..0.056 rows=1 loops=1)
--    Index Cond: ((email)::text = 'alice@example.com'::text)
--    Buffers: shared hit=3
```

How an index scan works at the page level:

```
B-tree for users(email):
                  [m...]
                /         \
          [a...h]          [n...z]
          /     \          /     \
     [a...c]  [d...h]  [n...q]  [r...z]
        ...      ...      ...      ...
     [alice@...]  ← leaf node: (email value, heap pointer → page 847, offset 23)

Index scan steps:
1. Traverse B-tree: 3 pages read (root → branch → leaf)
2. Get heap pointer: (page=847, offset=23)
3. Fetch page 847 from heap, extract row at offset 23
4. Return row

Total I/O: 4 pages (3 index + 1 heap) — much less than a full seq scan
```

When index scans become expensive — the heap fetch problem:

```sql
-- If many rows match, random heap fetches add up:
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 5;
-- user_id=5 has 50,000 orders (pathological case)

--  Index Scan using orders_user_id_idx on orders
--    (cost=0.43..98234.56 rows=50000 width=96)
--    (actual time=0.032..2456.789 rows=50000 loops=1)
--    Index Cond: (user_id = 5)
--    Buffers: shared hit=234 read=49823
-- shared read=49823 → 49823 random page reads from disk → very slow

-- For high-cardinality results, a bitmap scan is better (see Q7)
-- The planner usually makes this choice automatically

-- Index Scan Backward — for ORDER BY DESC:
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
--  Limit  (cost=0.43..1.89 rows=10 width=96)
--    ->  Index Scan Backward using orders_created_at_idx on orders
--          (cost=0.43..29240.43 rows=200000 width=96)
-- "Backward" = traverses the B-tree right-to-left for DESC order
-- Zero sort cost — the index already provides the order
```

Reading Index Cond vs Filter — a critical distinction:

```sql
EXPLAIN ANALYZE
    SELECT * FROM orders
    WHERE user_id = 42 AND status = 'pending';

-- If only user_id is indexed:
--  Index Scan using orders_user_id_idx on orders
--    (cost=0.43..15.67 rows=1 width=96)
--    (actual time=0.034..0.123 rows=12 loops=1)
--    Index Cond: (user_id = 42)          ← evaluated IN the index (fast)
--    Filter: ((status)::text = 'pending') ← evaluated on heap rows (after fetch)
--    Rows Removed by Filter: 88          ← 88 rows fetched from heap then discarded

-- "Index Cond" = condition pushed into the index traversal
--   → Only matching index entries are visited
-- "Filter" = condition applied to rows AFTER they're fetched from the heap
--   → Still requires fetching those rows

-- Fix: composite index (user_id, status) — moves status into Index Cond
CREATE INDEX orders_user_id_status_idx ON orders(user_id, status);
-- Now both conditions are evaluated in the index → fewer heap fetches
```

**Q7. What is a Bitmap Index Scan — when does PostgreSQL use it and how does it differ from an Index Scan?**

A: A Bitmap Index Scan is a two-phase process: first it scans the index to build an in-memory bitmap of which heap pages contain matching rows, then it fetches those pages in sequential (page number) order. This converts random I/O into sequential I/O for medium-selectivity queries:

```sql
EXPLAIN (ANALYZE, BUFFERS)
    SELECT * FROM orders
    WHERE user_id BETWEEN 100 AND 200;

--  Bitmap Heap Scan on orders
--    (cost=234.56..5678.90 rows=8940 width=96)
--    (actual time=3.456..45.678 rows=8834 loops=1)
--    Recheck Cond: ((user_id >= 100) AND (user_id <= 200))
--    Heap Blocks: exact=3421
--    Buffers: shared hit=234 read=3234
--    ->  Bitmap Index Scan on orders_user_id_idx
--          (cost=0.00..232.33 rows=8940 width=0)
--          (actual time=2.876..2.876 rows=8834 loops=1)
--          Index Cond: ((user_id >= 100) AND (user_id <= 200))
```

The two phases explained:

```
Phase 1 — Bitmap Index Scan:
  Scans the index for all entries where user_id BETWEEN 100 AND 200.
  Builds a bitmap: each bit represents one heap PAGE (not row).
  Bit=1 means "this page contains at least one matching row."
  Result: a compact in-memory structure of which pages to visit.

Phase 2 — Bitmap Heap Scan:
  Reads each marked page IN PAGE-NUMBER ORDER (sequential I/O).
  Rechecks the condition on each row within those pages.
  Returns matching rows.

  "Recheck Cond" appears because:
  - If the bitmap is very large (exceeds work_mem),
    it switches to "lossy" mode: bits represent pages, not individual rows.
  - In lossy mode, every row on a marked page must be rechecked.
  - "Heap Blocks: exact=3421" means no lossy mode here (all blocks are exact).
  - "Heap Blocks: lossy=500" would mean lossy mode for those 500 blocks.
```

BitmapAnd and BitmapOr — combining multiple indexes:

```sql
EXPLAIN
    SELECT * FROM orders
    WHERE user_id = 42 OR status = 'pending';

--  Bitmap Heap Scan on orders
--    (cost=1456.78..8934.56 rows=99234 width=96)
--    Recheck Cond: ((user_id = 42) OR ((status)::text = 'pending'::text))
--    ->  BitmapOr  (cost=1456.78..1456.78 rows=99244 width=0)
--          ->  Bitmap Index Scan on orders_user_id_idx
--                (cost=0.00..4.57 rows=4 width=0)
--                Index Cond: (user_id = 42)
--          ->  Bitmap Index Scan on orders_status_idx
--                (cost=0.00..1452.00 rows=99240 width=0)
--                Index Cond: ((status)::text = 'pending'::text)

-- BitmapOr: combine bitmaps with OR logic — all pages from either bitmap
-- BitmapAnd: combine bitmaps with AND logic — only pages in BOTH bitmaps (smaller result)

-- This is how PostgreSQL can use multiple indexes for one query —
-- a capability the planner uses when no single composite index covers all conditions
```

**Q8. What is an Index-Only Scan — what makes it possible and when is it the fastest option?**

A: An index-only scan returns data directly from the index without accessing the heap (the table) at all. It is the fastest scan type for queries where all required columns are stored in the index — no heap fetches means pure sequential I/O on the index pages:

```sql
-- Covering index: all SELECT columns are in the index
CREATE INDEX orders_covering_idx
    ON orders(user_id, status, created_at)
    INCLUDE (total, id);  -- INCLUDE: stored in leaf nodes, not part of the sort key

EXPLAIN (ANALYZE, BUFFERS)
    SELECT id, total, status, created_at
    FROM orders
    WHERE user_id = 42
    ORDER BY created_at DESC;

--  Index Only Scan Backward using orders_covering_idx on orders
--    (cost=0.43..12.56 rows=4 width=48)
--    (actual time=0.028..0.035 rows=4 loops=1)
--    Index Cond: (user_id = 42)
--    Heap Fetches: 0                    ← KEY INDICATOR: zero heap access
--    Buffers: shared hit=3
```

What makes an index-only scan possible:

```
Requirements for Index Only Scan:
1. All columns in SELECT list must be in the index (key columns OR INCLUDE columns)
2. All WHERE conditions must be satisfiable from the index alone
3. The visibility map must show the page is "all-visible"
   (all rows on that page are visible to all transactions)
   → If visibility map bit is not set, PostgreSQL must check the heap for visibility
   → This is why "Heap Fetches: 123" appears even on an Index Only Scan

-- Heap Fetches in Index Only Scan:
-- Heap Fetches: 0   → pure index-only (ideal)
-- Heap Fetches: 500 → 500 heap pages checked for visibility
--   (table not yet VACUUMed after recent writes — visibility map not current)
-- Fix: VACUUM orders; → sets visibility map bits → Heap Fetches drops to 0
```

Designing for index-only scans:

```sql
-- B-tree index stores ALL key columns — these are always available for index-only scans
-- INCLUDE clause adds non-key columns to leaf pages only (not for filtering, but for coverage)

-- Example: query that benefits from covering index
-- Frequent query:
SELECT user_id, status, created_at FROM orders
WHERE user_id BETWEEN 100 AND 200;

-- Without covering index: Index Scan + heap fetch for each row (width=full row)
-- With covering index on (user_id, status, created_at): Index Only Scan

-- The INCLUDE clause (PostgreSQL 11+):
-- Good for columns you SELECT but don't filter/sort on:
CREATE INDEX orders_status_include ON orders(status)
    INCLUDE (id, total, created_at);
-- Now: WHERE status = 'pending' → Index Only Scan returning id, total, created_at
-- The included columns don't bloat the internal B-tree nodes — only leaf pages

-- Check whether an index is being used for index-only scans in production:
SELECT
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch   -- If idx_tup_fetch = 0, index is used only for scanning, not heap fetches
FROM pg_stat_user_indexes
WHERE relname = 'orders';
```

## Section 4: Join Strategies

**Q9. What are the three join strategies — Nested Loop, Hash Join, Merge Join — and when does the planner choose each?**

A: For every JOIN in a query, the planner picks one of three algorithms. The choice depends on the sizes of the tables, available indexes, sort order, and memory:

```sql
-- ── Nested Loop Join ───────────────────────────────────────────────────────────
-- Algorithm: for each row in the outer table, scan the inner table for matches
-- Best when: outer table is small AND inner table has an index on the join key

EXPLAIN
    SELECT o.id, u.email
    FROM orders o
    JOIN users u ON u.id = o.user_id
    WHERE o.id = 'order-uuid-123';

--  Nested Loop  (cost=0.87..16.92 rows=1 width=52)
--    ->  Index Scan using orders_pkey on orders o
--          (cost=0.43..8.45 rows=1 width=36)
--          Index Cond: (id = 'order-uuid-123'::uuid)
--    ->  Index Scan using users_pkey on users u
--          (cost=0.43..8.45 rows=1 width=24)
--          Index Cond: (id = o.user_id)
-- loops=1 on inner: only 1 outer row → only 1 inner lookup
-- Ideal scenario for Nested Loop

-- When Nested Loop is bad:
-- Large outer table × no index on inner → O(N×M) complexity → very slow
-- You'll see: loops=50000 on the inner scan → pay inner scan cost 50000 times

-- ── Hash Join ──────────────────────────────────────────────────────────────────
-- Algorithm: hash the smaller table into a hash table in memory,
--            then scan the larger table and probe the hash for each row
-- Best when: neither table is tiny, no useful index on join key,
--            both tables fit in work_mem (memory-based hash)

EXPLAIN
    SELECT u.email, COUNT(o.id)
    FROM users u
    JOIN orders o ON o.user_id = u.id
    GROUP BY u.email;

--  HashAggregate  (...)
--    ->  Hash Join  (cost=2847.50..14448.00 rows=150000 width=32)
--          Hash Cond: (o.user_id = u.id)
--          ->  Seq Scan on orders o  (...)
--          ->  Hash  (cost=2660.00..2660.00 rows=15000 width=24)
--                Buckets: 16384  Batches: 1  Memory Usage: 897kB
--              ->  Seq Scan on users u  (...)
-- "Batches: 1" → hash table fits in work_mem (fast)
-- "Batches: 4" → hash table spilled to disk (slow) → increase work_mem

-- ── Merge Join ─────────────────────────────────────────────────────────────────
-- Algorithm: both inputs must be sorted on the join key;
--            merge them like merge sort — advance through both simultaneously
-- Best when: both inputs are already sorted (from index scan or prior sort)
--            AND the join produces many rows

EXPLAIN
    SELECT o.id, u.email
    FROM orders o
    JOIN users u ON u.id = o.user_id
    ORDER BY u.id;

--  Merge Join  (cost=0.86..45678.90 rows=200000 width=52)
--    Merge Cond: (u.id = o.user_id)
--    ->  Index Scan using users_pkey on users u  (sorted by id)
--    ->  Index Scan using orders_user_id_idx on orders o  (sorted by user_id)
-- Both inputs sorted by the join key → merge join with zero sort cost

-- Sort comparison:
-- Nested Loop: O(N log M) with index, O(N×M) without
-- Hash Join:   O(N+M) build + O(N+M) probe = O(N+M) — scales well for large tables
-- Merge Join:  O(N log N + M log M) sort + O(N+M) merge — excellent if pre-sorted
```

## Section 5: Common Diagnoses and Fixes

**Q10. How do you identify and fix bad row estimates — the most common cause of poor query plans?**

A: When the planner's estimated rows diverge dramatically from actual rows, it makes wrong plan choices. The fix is usually refreshing statistics:

```sql
-- Identifying bad estimates:
EXPLAIN ANALYZE
    SELECT * FROM orders
    WHERE status = 'pending'
    AND created_at > NOW() - INTERVAL '7 days';

--  Seq Scan on orders  (cost=0.00..5589.00 rows=12 width=96)   ← estimated: 12 rows
--                      (actual time=0.023..134.456 rows=18947 loops=1)  ← actual: 18,947 rows
--    Filter: ((status='pending') AND (created_at > (now() - '7 days'::interval)))
--    Rows Removed by Filter: 181053

-- Estimated 12 rows, got 18,947 — 1578× off!
-- Planner chose seq scan thinking result was tiny
-- With correct estimate, it might choose a bitmap scan or composite index

-- Why estimates are wrong:

-- Cause 1: Stale statistics
ANALYZE orders;  -- Refresh statistics for this table
-- autovacuum does this automatically but may lag behind heavy write workloads

-- Cause 2: Table statistics target too low
-- Default: 100 samples per column (statistics_target = 100)
-- For highly skewed distributions, increase it:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;
-- Now pg_stats has more histogram buckets for 'status' → better estimates

-- Cause 3: Correlated multi-column predicates
-- The planner assumes independence: P(status='pending' AND created_at > '7 days')
--   = P(status='pending') × P(created_at > '7 days')
-- But if 'pending' orders are always recent, this independence assumption is wrong
-- Fix: Extended Statistics (PostgreSQL 10+)
CREATE STATISTICS orders_status_created_stat (dependencies)
    ON status, created_at FROM orders;
ANALYZE orders;
-- Now planner knows status and created_at are correlated → better estimate

-- Cause 4: Function in WHERE clause
WHERE DATE_TRUNC('day', created_at) = '2024-01-15'
-- Planner cannot use histogram of created_at for a function result
-- Fix: rewrite to range:
WHERE created_at >= '2024-01-15' AND created_at < '2024-01-16'
-- Now planner can use created_at histogram directly

-- Checking pg_stats for a column:
SELECT
    n_distinct,
    correlation,
    most_common_vals::text,
    most_common_freqs::text,
    histogram_bounds::text
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
```

**Q11. What prevents indexes from being used — the most common index-defeating patterns?**

A: Even with the perfect index, certain query patterns prevent the planner from using it. These are called "index-defeating" patterns and are extremely common in real codebases:

```sql
-- ── Pattern 1: Implicit type cast ─────────────────────────────────────────────
-- Column is integer, but you pass a string literal

-- Table: users.id is INTEGER, indexed
SELECT * FROM users WHERE id = '42';
--  Seq Scan on users  (cost=...)
--    Filter: ((id)::text = '42'::text)
-- PostgreSQL casts id to text to compare with '42' → index on integer id is useless
-- Fix: pass the correct type
SELECT * FROM users WHERE id = 42;  -- integer literal
-- OR cast the parameter: WHERE id = '42'::integer

-- ── Pattern 2: Function on the indexed column ─────────────────────────────────
-- Index is on email, but a function is applied to it

SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
--  Seq Scan on users  (cost=...)
--    Filter: (lower((email)::text) = 'alice@example.com')
-- B-tree index on email cannot satisfy LOWER(email) predicate

-- Fix A: function-based index
CREATE INDEX users_email_lower_idx ON users(LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- Now uses the function index

-- Fix B: store data normalised (always lowercase) — simpler long-term
-- Fix C: case-insensitive collation (PostgreSQL 12+ with ICU)

-- Other common examples:
WHERE EXTRACT(YEAR FROM created_at) = 2024
-- → Can't use index on created_at
-- Fix: WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

WHERE TO_CHAR(created_at, 'YYYY-MM') = '2024-01'
-- Fix: same range rewrite

WHERE LENGTH(description) > 100
-- No index can help here — full expression index needed

-- ── Pattern 3: LIKE with leading wildcard ─────────────────────────────────────
SELECT * FROM users WHERE email LIKE '%@gmail.com';
-- B-tree traversal requires knowing the prefix → leading wildcard defeats it
-- Fix: use a trigram index for arbitrary substring search
CREATE EXTENSION pg_trgm;
CREATE INDEX users_email_trgm_idx ON users USING GIN (email gin_trgm_ops);
SELECT * FROM users WHERE email LIKE '%@gmail.com';  -- Now uses GIN index
SELECT * FROM users WHERE email ILIKE '%gmail%';    -- Also works with GIN + trgm

-- Trailing wildcard is fine with a standard B-tree:
SELECT * FROM users WHERE email LIKE 'alice%';  -- Uses B-tree index on email

-- ── Pattern 4: OR across different columns ────────────────────────────────────
-- Index on user_id exists, but:
SELECT * FROM orders WHERE user_id = 42 OR status = 'pending';
-- Planner may seq scan because one side (status) has no index → bitmap scan or seq scan
-- Fix: add index on status → planner can do BitmapOr combining both indexes

-- ── Pattern 5: NOT IN / != / NOT LIKE ────────────────────────────────────────
SELECT * FROM orders WHERE status != 'cancelled';
-- Often a seq scan even with index on status
-- Reason: if 95% of rows match, index doesn't help — seq scan is cheaper
-- This is usually the correct planner choice

-- ── Pattern 6: Wrong column order in composite index ─────────────────────────
CREATE INDEX orders_status_user_idx ON orders(status, user_id);

-- This uses the index (leading column matches):
WHERE status = 'pending' AND user_id = 42  -- ✓ uses index

-- This does NOT use the index efficiently (skips leading column):
WHERE user_id = 42  -- ✗ cannot use (status, user_id) without status condition
-- PostgreSQL 9.0+ can "skip scan" in some cases but it's not reliable

-- Fix: create a separate index on (user_id) OR use (user_id, status) order

-- ── Pattern 7: NULL handling ──────────────────────────────────────────────────
SELECT * FROM orders WHERE completed_at IS NULL;
-- B-tree indexes DO include NULL values (unlike some other databases)
-- This IS an index-able condition in PostgreSQL — no special handling needed
-- Exception: partial indexes can exclude NULLs
CREATE INDEX orders_pending_idx ON orders(id) WHERE completed_at IS NULL;
-- This partial index only covers pending (uncompleted) orders → smaller, faster
```

**Q12. How do you use `EXPLAIN ANALYZE` to diagnose a specific slow query — a worked diagnostic example?**

A: Systematic diagnosis from output to fix:

```sql
-- Slow query reported in production (taking 8+ seconds):
EXPLAIN (ANALYZE, BUFFERS)
    SELECT
        u.id, u.email,
        COUNT(o.id)        AS order_count,
        SUM(o.total)       AS lifetime_value,
        MAX(o.created_at)  AS last_order_at
    FROM users u
    LEFT JOIN orders o ON o.user_id = u.id
    WHERE u.created_at > '2023-01-01'
      AND u.is_active = true
    GROUP BY u.id, u.email
    ORDER BY lifetime_value DESC NULLS LAST
    LIMIT 50;
```

```
--  Limit  (cost=84532.10..84532.22 rows=50 width=64)
--         (actual time=8234.123..8234.136 rows=50 loops=1)          ← 8.2 seconds total
--    ->  Sort  (cost=84532.10..84784.60 rows=101000 width=64)
--              (actual time=8234.121..8234.129 rows=50 loops=1)
--          Sort Key: (sum(o.total)) DESC NULLS LAST
--          Sort Method: external merge  Disk: 12480kB               ← RED FLAG: sort spilled to disk
--          ->  HashAggregate  (cost=78432.00..79442.00 rows=101000 width=64)
--                             (actual time=8100.234..8201.456 rows=87432 loops=1)
--                Group Key: u.id, u.email
--                Batches: 4  Memory Usage: 4096kB                  ← RED FLAG: hash spilled to disk
--                ->  Hash Left Join  (cost=4532.00..67932.00 rows=1950000 width=40)
--                                   (actual time=45.234..6543.210 rows=1950000 loops=1)
--                      Hash Cond: (o.user_id = u.id)
--                      ->  Seq Scan on orders o  (cost=0.00..9250.00 rows=200000 width=24)
--                                               (actual time=0.012..52.341 rows=200000 loops=1)
--                          Buffers: shared hit=1250 read=2834      ← 2834 disk reads for orders
--                      ->  Hash  (cost=4407.00..4407.00 rows=10000 width=24)
--                                (actual time=44.876..44.876 rows=101234 loops=1)
--                            Buckets: 131072  Batches: 1  Memory Usage: 6432kB
--                            ->  Seq Scan on users u  (cost=0.00..4407.00 rows=10000 width=24)
--                                                     (actual time=0.010..38.234 rows=101234 loops=1)
--                                  Filter: ((is_active = true) AND (created_at > '2023-01-01'))
--                                  Rows Removed by Filter: 3898   ← filter removes 3898 rows
--                                  Buffers: shared hit=2047
--  Planning Time: 2.456 ms
--  Execution Time: 8234.345 ms
```

Reading the diagnosis:

```
Finding 1: Sort spilled to disk (Sort Method: external merge  Disk: 12480kB)
  → work_mem is too low for this query's sort
  → Fix: SET work_mem = '64MB'; (session level) or tune postgresql.conf

Finding 2: HashAggregate spilled to disk (Batches: 4)
  → Aggregation hash table too large for work_mem
  → Same fix: increase work_mem

Finding 3: users seq scan with estimated 10,000 rows but actual 101,234 rows
  → Statistics are stale — planner underestimated users by 10×
  → Caused planner to choose wrong hash bucket count
  → Fix: ANALYZE users;

Finding 4: Seq Scan on orders with 2,834 disk reads
  → Large orders table being fully scanned
  → There's a LEFT JOIN — not all 200,000 order rows are needed
  → An index on orders.user_id would let a nested loop join fetch only relevant orders
  → But: with 101,234 users, a nested loop doing 101,234 index lookups might still be slow
  → Better: let planner decide after fixing statistics

Fixes to apply in order:
1. ANALYZE users;  -- Fix statistics → planner gets better estimates
2. ANALYZE orders;
3. SET work_mem = '64MB'; -- Or permanent config change
4. CREATE INDEX IF NOT EXISTS orders_user_id_idx ON orders(user_id); -- If missing
5. Re-run EXPLAIN ANALYZE and check if sort and hash no longer spill to disk
```

After fixes:

```sql
ANALYZE users;
ANALYZE orders;
SET work_mem = '64MB';

EXPLAIN (ANALYZE, BUFFERS) <same query>;

--  Limit  (cost=12345.67..12345.79 rows=50 width=64)
--         (actual time=234.123..234.136 rows=50 loops=1)            ← 234ms vs 8.2s
--    ->  Sort  (cost=12345.67..12600.17 rows=101000 width=64)
--              (actual time=234.121..234.129 rows=50 loops=1)
--          Sort Method: top-N heapsort  Memory: 29kB                ← in-memory, tiny
--          ->  HashAggregate  (cost=8432.00..9442.00 rows=101000 width=64)
--                             (actual time=198.234..221.456 rows=101234 loops=1)
--                Group Key: u.id, u.email
--                Batches: 1  Memory Usage: 14336kB                 ← in-memory now
```

## Section 6: Scenario-Based Questions

**Q13. "A query was fast for months and suddenly became slow after a data spike. You have no query change. What do you check first?"**

A:

```sql
-- Step 1: Confirm the slow query's current plan:
EXPLAIN (ANALYZE, BUFFERS) <the slow query>;
-- Look for: unexpected seq scans on large tables, bad row estimates

-- Step 2: Check statistics freshness:
SELECT
    schemaname, relname, last_analyze, last_autoanalyze,
    n_live_tup, n_dead_tup, n_mod_since_analyze
FROM pg_stat_user_tables
WHERE relname IN ('orders', 'users');  -- Tables involved in the query

-- n_mod_since_analyze: rows modified since last ANALYZE
-- If this is large relative to n_live_tup: statistics are stale
-- Rule of thumb: autovacuum triggers ANALYZE when n_mod_since_analyze > 20% of n_live_tup

-- Step 3: Check pg_stats for the filtered columns:
SELECT
    attname,
    n_distinct,
    most_common_vals::text,
    most_common_freqs::text
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
-- If the data spike changed the distribution (new status values, different proportions)
-- but statistics weren't re-analyzed: planner uses outdated frequencies

-- Step 4: Manual fix:
ANALYZE orders;
-- Then re-run the slow query — often this alone fixes it

-- Step 5: If ANALYZE doesn't help — check for index bloat:
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

-- An index with idx_scan=0 is being maintained but never used → waste
-- An index much larger than expected → bloated → REINDEX to rebuild

-- Step 6: Check for lock issues (if query is stalled, not just slow):
SELECT pid, state, wait_event_type, wait_event, query_start, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_start;
-- 'Lock' in wait_event_type → query is blocked waiting for a lock
```

**Q14. "How do you confirm that a new index you created is actually being used and helping?"**

A:

```sql
-- Step 1: Verify the index exists and is valid:
SELECT indexname, indexdef, indisvalid, indisready
FROM pg_indexes
JOIN pg_index ON pg_indexes.indexname::regclass = pg_index.indexrelid
WHERE tablename = 'orders';
-- indisvalid = false → index build failed or is being built
-- indisready = false → index not yet ready to use

-- Step 2: Check the plan before and after:
-- Before creating the index (or disable with enable_indexscan=off):
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
-- After:
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
-- Compare: seq scan → index scan, and execution time improvement

-- Step 3: Monitor index usage in production via pg_stat_user_indexes:
SELECT
    indexrelname,
    idx_scan        AS times_used,
    idx_tup_read    AS index_entries_examined,
    idx_tup_fetch   AS heap_rows_fetched
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan DESC;
-- idx_scan: increments each time the index is used in a query
-- An idx_scan that grows over time = index is being used
-- idx_scan = 0 after 24 hours in production = index is never used → drop it

-- Step 4: Check for slow queries that SHOULD use the index:
-- pg_stat_statements (requires pg_stat_statements extension):
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time
FROM pg_stat_statements
WHERE query LIKE '%orders%'
  AND query LIKE '%user_id%'
ORDER BY mean_exec_time DESC
LIMIT 10;
-- If mean_exec_time is still high after index creation:
-- → The query may not be using the new index (check EXPLAIN again)
-- → Or the index isn't selective enough for the typical query

-- Step 5: Confirm index-only scan (best case) by checking heap fetches:
EXPLAIN (ANALYZE, BUFFERS)
    SELECT user_id, status, created_at FROM orders WHERE user_id = 42;
--  Index Only Scan using orders_covering_idx on orders
--    Heap Fetches: 0   ← perfect: zero heap I/O
-- vs
--    Heap Fetches: 200 ← needs VACUUM to set visibility map bits

VACUUM orders;  -- Sets visibility map → reduces Heap Fetches
```

## Quick Reference Table

| Scan type | When PostgreSQL uses it | Best for | Heap access |
|---|---|---|---|
| **Seq Scan** | No useful index; table small; high selectivity (>~20% rows match) | Full table reads, small tables | All pages, sequential |
| **Index Scan** | Index on filter column; low selectivity; ordered result needed | Point lookups, small result sets | Random access per matching row |
| **Bitmap Index Scan** | Medium selectivity; multiple indexes to combine; large result set | Range scans, OR conditions, multi-index queries | Sequential (sorted by page number) |
| **Index Only Scan** | All SELECT columns in index; visibility map set | Covering index queries | None (zero heap access) |

| Plan indicator | What it means | Fix |
|---|---|---|
| `Seq Scan` + `Rows Removed by Filter: N` | Reading entire table, discarding N rows | Create index on filter column |
| `Filter` (vs `Index Cond`) | Condition evaluated after heap fetch | Add column to index or use composite index |
| `Sort Method: external merge Disk: NkB` | Sort spilled to disk | Increase `work_mem`; add sorted index |
| `Batches: N` (N > 1) on Hash node | Hash table spilled to disk | Increase `work_mem` |
| `Heap Fetches: N` on Index Only Scan | Visibility map not set | Run `VACUUM` on the table |
| `loops=N` on inner node | Inner plan runs N times | Check if outer table is large; consider hash join |
| Estimated rows ≪ Actual rows | Stale statistics | Run `ANALYZE`; increase `statistics_target` |
| `Recheck Cond` + `Heap Blocks: lossy` | Bitmap went lossy (exceeded `work_mem`) | Increase `work_mem` |
| `BitmapAnd` / `BitmapOr` | Combining multiple index scans | Consider composite index to avoid bitmap overhead |

| Common index-defeating pattern | Example | Fix |
|---|---|---|
| Function on indexed column | `WHERE LOWER(email) = 'x'` | Function-based index or normalise data |
| Implicit type cast | `WHERE id = '42'` (id is integer) | Use correct literal type: `WHERE id = 42` |
| Leading wildcard LIKE | `WHERE name LIKE '%smith'` | GIN trigram index |
| OR across unindexed column | `WHERE a=1 OR b=2` (only a indexed) | Index on b; or use UNION ALL |
| Wrong composite index column order | `(status, user_id)` used with `WHERE user_id=?` | Create index in query order `(user_id, status)` |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **`EXPLAIN ANALYZE` actually executes the query** — it is never safe to run on a `DELETE` or `UPDATE` without wrapping it in a `BEGIN`/`ROLLBACK` transaction, and confusing `EXPLAIN` (plan only, no execution) with `EXPLAIN ANALYZE` (plan + actual execution) is a common and dangerous mistake; (2) understanding **null propagation from the `loops` counter** — when a node shows `(actual time=0.05..0.07 rows=3 loops=5000)`, the total cost is `0.07 × 5000 = 350ms`, not `0.07ms`; candidates who ignore `loops` will misidentify the bottleneck in any query with nested loops; (3) articulating the **difference between `Index Cond` and `Filter`** in an index scan — `Index Cond` is evaluated inside the index traversal (only matching index entries are visited), while `Filter` is evaluated on heap rows after they've been fetched (wasted I/O if many rows are removed); a large `Rows Removed by Filter` on an index scan means the index is not selective enough or a composite index would help; (4) knowing **why an index-only scan shows `Heap Fetches > 0`** — it's not because the index doesn't cover the columns, it's because the visibility map hasn't been set for some pages (the table hasn't been VACUUMed recently enough), and the fix is `VACUUM`, not changing the index; (5) explaining **when a seq scan is the correct choice** — when selectivity is high (many rows match), when the table is small, or when `correlation` near 1.0 makes sequential I/O very cache-friendly; good candidates don't blindly say "seq scan = bad", they explain the cost model that makes it sometimes optimal; and (6) knowing that **stale statistics cause bad row estimates which cause wrong plan choices** — when you see estimated rows wildly different from actual rows, the immediate fix is `ANALYZE <tablename>`, and for correlated multi-column predicates you can use extended statistics (`CREATE STATISTICS`) to give the planner correlation information it doesn't have by default.
