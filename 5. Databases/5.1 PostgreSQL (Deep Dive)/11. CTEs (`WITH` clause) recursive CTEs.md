# CTEs (`WITH` Clause): Recursive CTEs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a CTE, what problem does it solve, and what is its scope?**

A: A CTE (Common Table Expression) is a named, temporary result set defined within a `WITH` clause that exists for the duration of a single SQL statement. It is evaluated once and can be referenced by name anywhere in the query that follows the `WITH` clause.

```sql
-- Without CTE — nested subquery: hard to read, repeated logic is harder to maintain
SELECT
  dep.name AS department,
  emp_stats.avg_salary,
  emp_stats.headcount
FROM departments dep
JOIN (
  SELECT
    department_id,
    ROUND(AVG(salary), 2) AS avg_salary,
    COUNT(*) AS headcount
  FROM employees
  WHERE status = 'active'
  GROUP BY department_id
) AS emp_stats ON dep.id = emp_stats.department_id
WHERE emp_stats.headcount > 5;

-- With CTE — named, readable, reusable within the same statement:
WITH active_emp_stats AS (
  SELECT
    department_id,
    ROUND(AVG(salary), 2) AS avg_salary,
    COUNT(*) AS headcount
  FROM employees
  WHERE status = 'active'
  GROUP BY department_id
)
SELECT
  dep.name AS department,
  s.avg_salary,
  s.headcount
FROM departments dep
JOIN active_emp_stats s ON dep.id = s.department_id
WHERE s.headcount > 5;
```

**Scope rules:**
```sql
-- A CTE is visible only within the query it belongs to.
-- It cannot be referenced outside its statement.

WITH high_value_orders AS (
  SELECT * FROM orders WHERE total > 1000
)
SELECT * FROM high_value_orders;   -- OK — within the same statement

SELECT * FROM high_value_orders;   -- ERROR: relation "high_value_orders" does not exist
```

**Q2. How do you chain multiple CTEs and what visibility rules apply between them?**

A: Multiple CTEs are separated by commas after the single `WITH` keyword. Each CTE can reference any CTE defined before it — CTEs are evaluated in dependency order, not necessarily declaration order:

```sql
WITH
  -- CTE 1: base data
  active_users AS (
    SELECT id, name, email, created_at
    FROM users
    WHERE status = 'active'
  ),

  -- CTE 2: references CTE 1
  user_order_counts AS (
    SELECT
      u.id,
      u.name,
      COUNT(o.id) AS order_count,
      SUM(o.total) AS lifetime_value
    FROM active_users u                     -- references active_users
    LEFT JOIN orders o ON o.user_id = u.id
    GROUP BY u.id, u.name
  ),

  -- CTE 3: references both CTE 1 and CTE 2
  high_value_users AS (
    SELECT
      u.email,
      oc.order_count,
      oc.lifetime_value
    FROM active_users u                     -- references CTE 1
    JOIN user_order_counts oc ON oc.id = u.id  -- references CTE 2
    WHERE oc.lifetime_value > 5000
  )

-- Main query: references any CTE defined above
SELECT * FROM high_value_users ORDER BY lifetime_value DESC;
```

**Column naming in CTEs:**
```sql
-- Option 1: name columns in the SELECT list
WITH stats AS (
  SELECT department_id, AVG(salary) AS avg_sal, COUNT(*) AS cnt
  FROM employees GROUP BY department_id
)
SELECT * FROM stats;

-- Option 2: name columns in the CTE header (less common, same effect)
WITH stats(department_id, avg_sal, cnt) AS (
  SELECT department_id, AVG(salary), COUNT(*)
  FROM employees GROUP BY department_id
)
SELECT * FROM stats;
```

## Section 2: CTE vs Subquery vs Temporary Table

**Q3. When should you use a CTE vs an inline subquery vs a temporary table?**

A:

```sql
-- ── Inline subquery ──────────────────────────────────────────────────────────
-- Use when: the logic is used exactly once and is short enough to read inline
SELECT u.name, o.total
FROM users u
JOIN (SELECT user_id, SUM(total) AS total FROM orders GROUP BY user_id) o
  ON o.user_id = u.id;

-- Downsides:
-- - Cannot be reused in the same query
-- - Deep nesting becomes unreadable quickly
-- - Some databases can't name it without a CTE

-- ── CTE ──────────────────────────────────────────────────────────────────────
-- Use when:
-- - Logic is complex enough to name and explain
-- - The same derived result is referenced more than once in the query
-- - Building a recursive query (requires WITH RECURSIVE)
-- - Readability and maintainability matter

WITH order_totals AS (
  SELECT user_id, SUM(total) AS total FROM orders GROUP BY user_id
)
SELECT u.name, ot.total
FROM users u
JOIN order_totals ot ON ot.user_id = u.id
WHERE ot.total > (SELECT AVG(total) FROM order_totals);  -- ← second reference to the CTE

-- Downsides:
-- - May be materialized (evaluated fully before main query runs) — can be slower
--   if the main query's WHERE clause would have reduced the data significantly
-- - Scope is limited to the single statement

-- ── Temporary table ───────────────────────────────────────────────────────────
-- Use when:
-- - The result is large AND referenced multiple times ACROSS statements
-- - You need to add an index to the intermediate result for further queries
-- - The computation is expensive and you want to cache it for the session

CREATE TEMP TABLE heavy_stats AS
  SELECT department_id, AVG(salary) AS avg_sal
  FROM employees
  GROUP BY department_id;

CREATE INDEX ON heavy_stats (department_id);  -- CTE cannot have its own index

SELECT d.name, hs.avg_sal
FROM departments d
JOIN heavy_stats hs ON hs.department_id = d.id;

SELECT e.name, hs.avg_sal
FROM employees e
JOIN heavy_stats hs ON hs.department_id = e.department_id;
-- Same intermediate result used in two separate queries

DROP TABLE heavy_stats;  -- Or let it drop at end of session

-- Decision matrix:
-- Single reference, simple: inline subquery
-- Multi-reference or complex, same statement: CTE
-- Multi-statement, large result, needs index: temp table
```

**Q4. What is CTE materialization and how did PostgreSQL 12 change the default behavior?**

A: Materialization means the CTE is evaluated **once in full** and its result stored in memory before the main query uses it. This prevents the query planner from pushing predicates (WHERE clauses) from the outer query into the CTE — a behavior called the "optimization fence."

**Pre-PostgreSQL 12 (always materialized):**
```sql
-- PostgreSQL 11 and earlier: ALL CTEs are materialized
WITH expensive_cte AS (
  SELECT * FROM very_large_table    -- Returns 10 million rows
)
SELECT * FROM expensive_cte WHERE id = 42;

-- What happens:
-- 1. CTE evaluated fully: 10M rows computed and stored in memory
-- 2. WHERE id=42 applied to the stored result
-- 3. Returns 1 row — but 10M rows were materialized needlessly

-- This is the "optimization fence": the planner CANNOT push "WHERE id=42"
-- into the CTE to let it use an index on very_large_table
```

**PostgreSQL 12+ (inline by default):**
```sql
-- PostgreSQL 12+: CTEs are NOT materialized by default unless:
-- 1. The CTE is RECURSIVE
-- 2. The CTE contains a side-effecting operation (INSERT/UPDATE/DELETE)
-- 3. The CTE is referenced MORE THAN ONCE (materialized to avoid computing twice)

WITH expensive_cte AS (
  SELECT * FROM very_large_table    -- 10 million rows
)
SELECT * FROM expensive_cte WHERE id = 42;

-- PG12+ behavior: CTE is inlined (treated like a subquery)
-- Planner pushes WHERE id=42 INTO the CTE → index scan on very_large_table
-- Result: reads 1 row instead of 10M

-- EXPLICIT CONTROL over materialization:
-- Force materialization (pre-PG12 behavior, optimization fence):
WITH expensive_cte AS MATERIALIZED (
  SELECT * FROM very_large_table
)
SELECT * FROM expensive_cte WHERE id = 42;

-- Prevent materialization (force inline even when PG12 would choose to materialize):
WITH stats AS NOT MATERIALIZED (
  SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id
)
SELECT * FROM users u JOIN stats s ON s.user_id = u.id WHERE s.cnt > 10;
```

**When MATERIALIZED is deliberately useful:**
```sql
-- Use MATERIALIZED to guarantee a CTE runs only once when its output is
-- non-deterministic (e.g., contains RANDOM() or NOW()) and you need
-- the same values throughout the query:
WITH snapshot AS MATERIALIZED (
  SELECT id, NOW() AS recorded_at, RANDOM() AS rand_score
  FROM candidates
)
-- Both references use the SAME recorded_at and rand_score values:
INSERT INTO audit_log SELECT id, recorded_at, 'snapshot' FROM snapshot;
SELECT * FROM snapshot WHERE rand_score > 0.5;
-- Without MATERIALIZED: each reference might re-evaluate NOW() and RANDOM()

-- Also useful as an optimization fence to force early filtering:
WITH pre_filtered AS MATERIALIZED (
  SELECT * FROM events
  WHERE user_id = 123
    AND created_at > NOW() - INTERVAL '7 days'
)
-- Complex downstream query that might otherwise scan the full table:
SELECT
  e1.id,
  COUNT(e2.id) FILTER (WHERE e2.type = 'click') AS clicks
FROM pre_filtered e1
LEFT JOIN pre_filtered e2 ON e2.session_id = e1.session_id
GROUP BY e1.id;
-- MATERIALIZED ensures events is filtered once (7-day window)
-- rather than having the complex self-join push confusing predicates in
```

## Section 3: Recursive CTEs — Structure and Execution

**Q5. What is a recursive CTE and what is its mandatory structure?**

A: A recursive CTE references itself in its own definition. It requires the `RECURSIVE` keyword on the `WITH` clause and must have exactly two parts joined by `UNION ALL` (or `UNION`):

```sql
WITH RECURSIVE cte_name AS (

  -- ── ANCHOR MEMBER ────────────────────────────────────────────────────────
  -- Non-recursive base case. Evaluated ONCE to produce the initial result set.
  -- Does NOT reference cte_name.
  SELECT initial_values

  UNION ALL    -- UNION ALL (allows duplicates, faster) or UNION (deduplicates)

  -- ── RECURSIVE MEMBER ─────────────────────────────────────────────────────
  -- References cte_name — this is what makes it recursive.
  -- Evaluated repeatedly until it produces zero rows.
  -- Can only reference cte_name on the LEFT side of a JOIN (not a subquery).
  SELECT next_values
  FROM cte_name          -- ← self-reference
  JOIN other_tables ...
  WHERE termination_condition

)
SELECT * FROM cte_name;
```

**Constraints on the recursive member:**
```sql
-- ALLOWED in recursive member:
SELECT, FROM, WHERE, JOIN, GROUP BY, HAVING, LIMIT in outer query
Reference to cte_name on the left side of a join

-- NOT ALLOWED in recursive member:
-- Aggregate functions: COUNT, SUM, AVG (cannot aggregate over the recursive term)
-- Window functions: ROW_NUMBER(), RANK()
-- DISTINCT / DISTINCT ON
-- Subqueries that reference cte_name
-- LEFT JOIN where cte_name is on the right side

-- WRONG — aggregate in recursive member:
WITH RECURSIVE bad AS (
  SELECT 1 AS n
  UNION ALL
  SELECT COUNT(*) FROM bad    -- ERROR: aggregate functions not allowed
)

-- WRONG — self-reference on right side of LEFT JOIN:
WITH RECURSIVE bad AS (
  SELECT id FROM nodes WHERE parent IS NULL
  UNION ALL
  SELECT n.id FROM nodes n LEFT JOIN bad b ON b.id = n.parent  -- ERROR: bad on right side
)
```

**Q6. How does PostgreSQL execute a recursive CTE step by step?**

A: PostgreSQL uses a working-table algorithm — it maintains a "working table" that is replaced at each iteration by the new rows generated by the recursive member:

```sql
-- Example: generate integers 1 through 5
WITH RECURSIVE counter AS (
  SELECT 1 AS n          -- anchor
  UNION ALL
  SELECT n + 1           -- recursive member
  FROM counter
  WHERE n < 5            -- termination
)
SELECT n FROM counter;
```

```
Execution trace:
─────────────────────────────────────────────────────────────────────────────

Iteration 0 — evaluate anchor:
  Working table W0 = { (n=1) }
  Result so far  = { (n=1) }

Iteration 1 — evaluate recursive member using W0:
  SELECT n + 1 FROM W0 WHERE n < 5
  → {(n=2)}  (1 < 5, so 2 is generated)
  Working table W1 = { (n=2) }
  Result so far  = { (n=1), (n=2) }

Iteration 2 — evaluate recursive member using W1:
  SELECT n + 1 FROM W1 WHERE n < 5
  → {(n=3)}
  Working table W2 = { (n=3) }
  Result so far  = { (n=1), (n=2), (n=3) }

Iteration 3: W3 = { (n=4) }, result grows
Iteration 4: W4 = { (n=5) }, result grows

Iteration 5 — evaluate recursive member using W4:
  SELECT n + 1 FROM W4 WHERE n < 5
  → WHERE 5 < 5 is FALSE → no rows generated
  Working table W5 = {} (empty)

TERMINATION: working table is empty → recursion stops.

Final result: { 1, 2, 3, 4, 5 }

Key properties of the algorithm:
- Each iteration only sees the rows from the PREVIOUS iteration (not all accumulated rows)
- This is why it terminates: each step produces a subset based on the "frontier"
- UNION ALL: each step's output is appended to the result
- UNION:     each step's output is deduplicated against ALL prior results
             (much slower — requires comparing against the entire accumulated set)
```

**Q7. What are the ways to prevent infinite recursion in a recursive CTE?**

A: Without a termination condition, a recursive CTE runs until it exhausts memory or hits a system limit. There are three main strategies:

```sql
-- Strategy 1: WHERE clause in the recursive member (most common)
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name, 1 AS depth
  FROM categories WHERE parent_id IS NULL

  UNION ALL

  SELECT c.id, c.parent_id, c.name, t.depth + 1
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
  WHERE t.depth < 10    -- ← stop at depth 10 to prevent runaway on malformed data
)
SELECT * FROM tree;

-- Strategy 2: Cycle detection via a visited array
-- (covered in Q9 — essential for graph data with potential cycles)

-- Strategy 3: Rely on the data structure being a proper tree (no cycles)
-- For adjacency lists without cycles (org chart, filesystem):
-- The recursion naturally terminates when it reaches leaf nodes (no children)
-- WHERE c.parent_id = t.id will return 0 rows at leaves → stops

-- PostgreSQL's built-in safety valve:
-- No single recursive CTE may use more than work_mem memory for its working table
-- (default 4MB — increase with SET work_mem = '256MB' for large hierarchies)

-- The max_recursion_depth GUC does NOT exist in PostgreSQL (unlike MySQL's @@cte_max_recursion_depth)
-- PostgreSQL relies on the above strategies + memory limits

-- What infinite recursion looks like (DO NOT RUN IN PRODUCTION):
WITH RECURSIVE infinite AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM infinite    -- no termination
)
SELECT * FROM infinite LIMIT 10;
-- LIMIT in the OUTER query DOES stop execution in PostgreSQL
-- but only after the working table has filled memory
-- for truly safe recursion, always add WHERE in the recursive member
```

## Section 4: Common Recursive Patterns

**Q8. How do you traverse a tree hierarchy with a recursive CTE?**

A: Tree hierarchies (org charts, category trees, bill of materials, file systems) are the most common use case for recursive CTEs. The pattern: anchor on the root(s), join children at each step:

```sql
-- Schema: adjacency list (each row knows its parent)
CREATE TABLE employees (
  id         INT PRIMARY KEY,
  name       TEXT NOT NULL,
  title      TEXT,
  manager_id INT REFERENCES employees(id)  -- NULL for the CEO
);

-- ── Find the full management chain BELOW a given manager ─────────────────────
WITH RECURSIVE org_tree AS (
  -- Anchor: start from the target manager (Sarah, id=3)
  SELECT
    id,
    name,
    title,
    manager_id,
    0         AS depth,
    name::TEXT AS path    -- track the path from root to leaf
  FROM employees
  WHERE id = 3

  UNION ALL

  -- Recursive: everyone who reports to someone already in the tree
  SELECT
    e.id,
    e.name,
    e.title,
    e.manager_id,
    ot.depth + 1,
    ot.path || ' → ' || e.name
  FROM employees e
  JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT
  id,
  REPEAT('  ', depth) || name AS indented_name,    -- visual indent by depth
  title,
  depth,
  path
FROM org_tree
ORDER BY path;    -- sorts into tree traversal order

-- Result:
-- id | indented_name          | title    | depth | path
-- ---+------------------------+----------+-------+---------------------------
--  3 | Sarah                  | VP Eng   |     0 | Sarah
--  7 |   Alice                | Manager  |     1 | Sarah → Alice
-- 12 |     Charlie            | Engineer |     2 | Sarah → Alice → Charlie
-- 13 |     Diana              | Engineer |     2 | Sarah → Alice → Diana
--  8 |   Bob                  | Manager  |     1 | Sarah → Bob
-- 15 |     Eve                | Engineer |     2 | Sarah → Bob → Eve

-- ── Find all ANCESTORS of a given employee (bottom-up traversal) ──────────────
WITH RECURSIVE ancestors AS (
  -- Anchor: start from the target employee
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE id = 15  -- Eve

  UNION ALL

  -- Recursive: find the manager of each person already in the result
  SELECT e.id, e.name, e.manager_id, a.depth + 1
  FROM employees e
  JOIN ancestors a ON e.id = a.manager_id   -- ← REVERSED JOIN: find parent, not children
)
SELECT id, name, depth AS levels_above_eve
FROM ancestors
ORDER BY depth;
-- 15 | Eve    | 0
--  8 | Bob    | 1
--  3 | Sarah  | 2
--  1 | CEO    | 3

-- ── Flatten a category tree for breadcrumbs ───────────────────────────────────
WITH RECURSIVE breadcrumb AS (
  SELECT id, name, parent_id, name::TEXT AS full_path
  FROM categories WHERE id = 42    -- target category

  UNION ALL

  SELECT c.id, c.name, c.parent_id, c.name || ' > ' || b.full_path
  FROM categories c
  JOIN breadcrumb b ON c.id = b.parent_id
)
SELECT full_path
FROM breadcrumb
WHERE parent_id IS NULL    -- root node has the complete path built up
LIMIT 1;
-- Electronics > Computers > Laptops > Gaming Laptops
```

**Q9. How do you traverse a graph and detect cycles in a recursive CTE?**

A: Unlike trees, graphs can have cycles (A→B→C→A). Without cycle detection, the recursion runs forever. The standard approach: maintain an array of visited nodes:

```sql
-- Schema: directed graph (A→B means A links to B)
CREATE TABLE links (
  from_page TEXT,
  to_page   TEXT
);

-- ── Find all pages reachable from 'Home', with cycle detection ────────────────
WITH RECURSIVE reachable AS (
  -- Anchor: start at Home, visited = [Home]
  SELECT
    to_page                         AS current_page,
    ARRAY['Home', to_page]          AS visited,    -- track the path taken
    false                           AS is_cycle,
    1                               AS hops
  FROM links
  WHERE from_page = 'Home'

  UNION ALL

  SELECT
    l.to_page,
    r.visited || l.to_page,         -- append newly visited page to path
    l.to_page = ANY(r.visited),     -- is the next page already in our path? = cycle
    r.hops + 1
  FROM links l
  JOIN reachable r ON l.from_page = r.current_page
  WHERE NOT r.is_cycle              -- stop expanding once a cycle is detected
    AND r.hops < 20                 -- safety: limit depth even without cycles
)
SELECT DISTINCT
  current_page,
  hops,
  visited AS path,
  is_cycle
FROM reachable
ORDER BY hops, current_page;

-- ── Find all SHORTEST PATHS between two nodes ─────────────────────────────────
WITH RECURSIVE paths AS (
  SELECT
    'A'         AS current_node,
    ARRAY['A']  AS path,
    0           AS distance
  WHERE 'A' != 'D'   -- anchor: starting node (only if not already at target)

  UNION ALL

  SELECT
    e.to_node,
    p.path || e.to_node,
    p.distance + 1
  FROM edges e
  JOIN paths p ON e.from_node = p.current_node
  WHERE e.to_node != ALL(p.path)      -- avoid cycles: don't revisit nodes in current path
    AND p.distance < (                -- stop once we find first path to target
      SELECT MIN(distance) FROM paths WHERE current_node = 'D'
    )
)
SELECT path, distance
FROM paths
WHERE current_node = 'D'
ORDER BY distance
LIMIT 5;    -- top 5 shortest paths
```

**Q10. How do you control traversal order — breadth-first vs depth-first?**

A: PostgreSQL's working-table algorithm processes all rows in the current working table before moving to the next iteration, which resembles BFS. But the actual output order within a level is not guaranteed. To impose a specific order:

```sql
-- ── Breadth-First Search (BFS) — level by level ───────────────────────────────
-- Natural for finding shortest paths, "closest" related items

WITH RECURSIVE bfs AS (
  SELECT id, name, parent_id,
         0 AS level,
         ARRAY[id] AS path    -- use for ordering
  FROM nodes WHERE parent_id IS NULL

  UNION ALL

  SELECT n.id, n.name, n.parent_id,
         b.level + 1,
         b.path || n.id
  FROM nodes n
  JOIN bfs b ON n.parent_id = b.id
)
SELECT id, name, level
FROM bfs
ORDER BY level, id;     -- ← ORDER BY level gives BFS output
-- Level 0: root
-- Level 1: all children of root
-- Level 2: all grandchildren
-- ...

-- ── Depth-First Search (DFS) — follow one branch to the end ──────────────────
-- Natural for building paths, hierarchical exports

WITH RECURSIVE dfs AS (
  SELECT id, name, parent_id,
         0 AS depth,
         ARRAY[id]::INT[] AS sort_path   -- lexicographic sort gives DFS order
  FROM nodes WHERE parent_id IS NULL

  UNION ALL

  SELECT n.id, n.name, n.parent_id,
         d.depth + 1,
         d.sort_path || n.id
  FROM nodes n
  JOIN dfs d ON n.parent_id = d.id
)
SELECT id, name, depth,
       REPEAT('  ', depth) || name AS indented
FROM dfs
ORDER BY sort_path;     -- ← ORDER BY the path array gives DFS output
-- Root
--   Child A
--     Grandchild A1
--     Grandchild A2
--   Child B
--     Grandchild B1
```

## Section 5: PostgreSQL 14+ CYCLE and SEARCH Clauses

**Q11. What are the `CYCLE` and `SEARCH` clauses introduced in PostgreSQL 14?**

A: PostgreSQL 14 added SQL-standard clauses that implement cycle detection and traversal-order control without requiring manual array tracking:

```sql
-- ── CYCLE clause — automatic cycle detection ──────────────────────────────────
-- Without CYCLE: manual ARRAY tracking as shown in Q9
-- With CYCLE: PostgreSQL handles it automatically

WITH RECURSIVE org AS (
  SELECT id, name, manager_id
  FROM employees
  WHERE id = 1

  UNION ALL

  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN org ON org.id = e.manager_id
)
CYCLE id                    -- ← detect cycles on the 'id' column
SET is_cycle                -- ← boolean column added: true when cycle detected
USING path                  -- ← array column added: records the cycle path

SELECT id, name, is_cycle, path
FROM org
WHERE NOT is_cycle;         -- ← filter out the cycle rows

-- The CYCLE clause is equivalent to manually writing:
-- visited = ARRAY[id], is_cycle = id = ANY(visited)
-- but is cleaner and SQL-standard

-- Multi-column cycle detection (cycle detected when ALL columns repeat):
WITH RECURSIVE paths AS (...)
CYCLE from_node, to_node    -- detect when this PAIR of columns repeats
SET is_cycle
USING path_array;

-- ── SEARCH clause — declarative traversal order ───────────────────────────────
-- Instead of ORDER BY sort_path, declare the order in the CTE itself

-- Breadth-first:
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id FROM nodes WHERE parent_id IS NULL
  UNION ALL
  SELECT n.id, n.name, n.parent_id FROM nodes n JOIN tree ON n.parent_id = tree.id
)
SEARCH BREADTH FIRST BY id SET order_col    -- ← adds 'order_col' column

SELECT id, name FROM tree ORDER BY order_col;    -- BFS order
-- 'order_col' is an auto-generated ordering column (array type internally)

-- Depth-first:
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id FROM nodes WHERE parent_id IS NULL
  UNION ALL
  SELECT n.id, n.name, n.parent_id FROM nodes n JOIN tree ON n.parent_id = tree.id
)
SEARCH DEPTH FIRST BY id SET order_col

SELECT id, name FROM tree ORDER BY order_col;    -- DFS order

-- SEARCH and CYCLE together:
WITH RECURSIVE org AS (
  SELECT id, name, manager_id FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id FROM employees e JOIN org ON org.id = e.manager_id
)
SEARCH DEPTH FIRST BY id SET traversal_order
CYCLE id SET is_cycle USING cycle_path

SELECT id, name FROM org
WHERE NOT is_cycle
ORDER BY traversal_order;
```

## Section 6: DML with CTEs

**Q12. How do you use CTEs with INSERT, UPDATE, and DELETE?**

A: PostgreSQL allows data-modifying statements inside CTEs. These are called "data-modifying CTEs" — they execute once and the modified rows are available via `RETURNING` for subsequent CTEs or the main query:

```sql
-- ── INSERT with RETURNING ─────────────────────────────────────────────────────
WITH inserted_users AS (
  INSERT INTO users (name, email, created_at)
  VALUES
    ('Alice', 'alice@example.com', NOW()),
    ('Bob',   'bob@example.com',   NOW())
  RETURNING id, name, email
)
-- Use the inserted rows immediately:
INSERT INTO user_audit (user_id, action, timestamp)
SELECT id, 'CREATED', NOW()
FROM inserted_users;

-- ── UPDATE with RETURNING ─────────────────────────────────────────────────────
WITH price_updates AS (
  UPDATE products
  SET
    price      = price * 1.10,
    updated_at = NOW()
  WHERE category = 'electronics'
  RETURNING id, name, price AS new_price, (price / 1.10) AS old_price
)
-- Log the changes:
INSERT INTO price_history (product_id, old_price, new_price, changed_at)
SELECT id, old_price, new_price, NOW()
FROM price_updates;

-- ── DELETE with RETURNING — soft-delete or archive pattern ───────────────────
WITH deleted_orders AS (
  DELETE FROM orders
  WHERE
    status = 'cancelled'
    AND created_at < NOW() - INTERVAL '90 days'
  RETURNING *
)
-- Archive before deleting:
INSERT INTO orders_archive
SELECT *, NOW() AS archived_at
FROM deleted_orders;

-- Verify what was archived:
SELECT COUNT(*) AS archived_count FROM deleted_orders;
-- Note: SELECT from a data-modifying CTE sees the rows affected by that CTE
```

**Q13. What is the "upsert and fan-out" CTE pattern?**

A: A powerful pattern where a single CTE performs a write (INSERT/UPDATE/DELETE) and the result fans out to update multiple related tables atomically:

```sql
-- Pattern: move an order from pending to processed, update inventory, log the action
-- All in a single atomic statement (one transaction, no race conditions)

WITH
  -- Step 1: Update the order status and capture what changed
  processed_order AS (
    UPDATE orders
    SET status = 'processed', processed_at = NOW()
    WHERE id = $1 AND status = 'pending'
    RETURNING id, user_id, total, items
  ),

  -- Step 2: Decrement inventory for each item in the order
  -- (runs AFTER processed_order, uses its result)
  inventory_update AS (
    UPDATE inventory i
    SET quantity = i.quantity - oi.quantity
    FROM order_items oi
    JOIN processed_order po ON oi.order_id = po.id
    WHERE i.product_id = oi.product_id
    RETURNING i.product_id, i.quantity AS remaining
  ),

  -- Step 3: Insert an audit log entry
  audit_entry AS (
    INSERT INTO order_audit (order_id, action, performed_at, metadata)
    SELECT
      id,
      'PROCESSED',
      NOW(),
      jsonb_build_object('total', total, 'user_id', user_id)
    FROM processed_order
    RETURNING order_id
  )

-- Final SELECT: return a summary of what happened
SELECT
  po.id              AS order_id,
  po.total,
  COUNT(iu.product_id) AS items_updated,
  ae.order_id IS NOT NULL AS audit_logged
FROM processed_order po
LEFT JOIN inventory_update iu ON true
LEFT JOIN audit_entry ae ON ae.order_id = po.id
GROUP BY po.id, po.total, ae.order_id;

-- Key properties of data-modifying CTEs:
-- 1. All data-modifying CTEs in one statement execute in the SAME snapshot
--    (they see the same pre-statement state of the database)
-- 2. Changes from one CTE ARE visible to subsequent CTEs
-- 3. The entire statement is atomic — if any CTE fails, all changes roll back
-- 4. Execution order: determined by dependencies (which CTE references which)
```

**Important isolation note:**
```sql
-- Data-modifying CTEs within the same statement see a snapshot of the DB
-- as it existed BEFORE the statement started.
-- Two CTEs in the same statement that both DELETE from the same table
-- will NOT see each other's deletions:

WITH
  del_a AS (DELETE FROM items WHERE id = 1 RETURNING id),
  del_b AS (DELETE FROM items WHERE id = 1 RETURNING id)  -- same row!
SELECT * FROM del_a, del_b;
-- del_a and del_b both see the row (pre-statement snapshot)
-- Result: both delete the same row — but only one physically deletes it
-- The actual row is deleted once; both CTEs "claim" to have deleted it
-- This is a known PostgreSQL behavior — avoid deleting same rows from multiple CTEs
```

## Section 7: Performance Considerations

**Q14. How does CTE materialization affect query performance, and when is the optimization fence harmful vs helpful?**

A:

```sql
-- ── Harmful optimization fence (pre-PG12 or explicit MATERIALIZED) ───────────

-- Scenario: find the top-spending user in a specific country
WITH user_totals AS (          -- Returns 10 million rows
  SELECT user_id, country, SUM(amount) AS total
  FROM transactions
  GROUP BY user_id, country
)
SELECT user_id, total
FROM user_totals
WHERE country = 'US'
ORDER BY total DESC
LIMIT 1;

-- Pre-PG12: full GROUP BY over 10M transactions, then filter by country
-- EXPLAIN shows: Seq Scan (10M rows) → Sort → Limit
-- PG12+ inline: filter country='US' is pushed into the CTE
-- → GROUP BY only runs over US transactions → much faster

-- ── Helpful optimization fence ────────────────────────────────────────────────

-- Scenario: CTE with random sampling — you want the SAME random rows referenced twice
WITH random_sample AS MATERIALIZED (
  SELECT * FROM products ORDER BY RANDOM() LIMIT 100
)
SELECT p.id, p.name, r.similar_product_id
FROM random_sample p
JOIN recommendations r ON r.product_id = p.id
WHERE r.similar_product_id IN (SELECT id FROM random_sample);
-- Both references to random_sample use the SAME 100 rows
-- Without MATERIALIZED: might generate two different random samples

-- ── Self-referencing CTE (must be materialized or inlined carefully) ──────────

-- CTE used twice: PG12+ auto-materializes to avoid double execution
WITH expensive_query AS (
  SELECT user_id, complex_json_processing(data) AS result
  FROM raw_events
  WHERE ts > NOW() - INTERVAL '1 day'
)
SELECT r.user_id, r.result
FROM expensive_query r
WHERE r.user_id IN (SELECT user_id FROM expensive_query WHERE result->>'type' = 'premium');
-- PG12+: auto-materializes since expensive_query is referenced twice
-- Manual override: add AS NOT MATERIALIZED if the double scan is actually cheaper
-- (happens when the result set is tiny and each filtered reference can use an index)
```

**Q15. How do you identify and fix slow recursive CTEs?**

A:

```sql
-- ── Diagnosing recursive CTE performance ─────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, c.name FROM categories c JOIN tree ON c.parent_id = tree.id
)
SELECT * FROM tree;

-- Key things to look for in EXPLAIN:
-- "WorkTable Scan" — each iteration scans the working table (unavoidable)
-- High "loops" count → many iterations → deep hierarchy or many rows per level
-- Sequential scans on the base table → missing index on parent_id

-- Common fix 1: ensure the JOIN column is indexed
CREATE INDEX ON categories(parent_id);    -- Critical for tree traversal performance
-- Without this: each recursive step scans the full table looking for children

-- Common fix 2: limit depth when only top-N levels are needed
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, c.parent_id, t.depth + 1
  FROM categories c JOIN tree t ON c.parent_id = t.id
  WHERE t.depth < 3    -- only get top 3 levels, not the entire tree
)
SELECT * FROM tree;

-- Common fix 3: for large hierarchies, consider a closure table or ltree extension
-- ltree: stores materialized paths (e.g., 'Root.Electronics.Laptops')
-- Allows querying descendants with: SELECT * FROM categories WHERE path <@ 'Electronics'
-- Much faster than recursive CTE for very deep or wide trees

-- Benchmark: closure table vs recursive CTE for common operations:
-- Find all descendants:
--   Recursive CTE:   O(depth × width × log N per join)
--   Closure table:   O(1) index lookup
-- Find all ancestors:
--   Recursive CTE:   O(depth × log N)
--   Closure table:   O(1) index lookup
-- Insert new node:
--   Recursive CTE:   O(1) (just insert the row)
--   Closure table:   O(depth) — must insert all ancestor-descendant pairs

-- Choose closure table when: hierarchy is deep, read-heavy, rarely restructured
-- Choose recursive CTE when: hierarchy is shallow, write-heavy, simple structure
```

## Section 8: Sequences and Advanced Patterns

**Q16. How do you generate date series, Fibonacci sequences, and other computed sequences with recursive CTEs?**

A:

```sql
-- ── Integer series (prefer generate_series in PostgreSQL) ─────────────────────
WITH RECURSIVE series AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM series WHERE n < 100
)
SELECT n FROM series;
-- PostgreSQL shortcut: SELECT generate_series(1, 100);
-- Use recursive CTE only when the series logic is complex

-- ── Date series (filling gaps in time-series data) ────────────────────────────
-- Find days with no orders and fill them with 0:
WITH RECURSIVE date_range AS (
  SELECT '2024-01-01'::DATE AS d
  UNION ALL
  SELECT d + 1 FROM date_range WHERE d < '2024-01-31'
),
daily_orders AS (
  SELECT DATE(created_at) AS order_date, COUNT(*) AS orders
  FROM orders
  WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'
  GROUP BY DATE(created_at)
)
SELECT
  dr.d AS date,
  COALESCE(do.orders, 0) AS orders
FROM date_range dr
LEFT JOIN daily_orders do ON do.order_date = dr.d
ORDER BY dr.d;
-- Ensures every day appears even if no orders were placed

-- ── Fibonacci sequence ────────────────────────────────────────────────────────
WITH RECURSIVE fib AS (
  SELECT 0::BIGINT AS a, 1::BIGINT AS b, 1 AS n
  UNION ALL
  SELECT b, a + b, n + 1
  FROM fib
  WHERE n < 20
)
SELECT n, a AS fib_value FROM fib;
-- n=1→0, n=2→1, n=3→1, n=4→2, n=5→3, ...

-- ── Running totals / cumulative sums ─────────────────────────────────────────
-- (Better done with window functions, but shows recursive pattern)
WITH RECURSIVE running AS (
  SELECT id, amount,
         amount AS running_total,
         ROW_NUMBER() OVER (ORDER BY id) AS rn
  FROM transactions
  WHERE rn = 1

  UNION ALL

  SELECT t.id, t.amount,
         r.running_total + t.amount,
         r.rn + 1
  FROM transactions t
  JOIN running r ON r.rn + 1 = (
    SELECT ROW_NUMBER() OVER (ORDER BY id)
    FROM transactions WHERE id = t.id
  )
)
-- Note: window functions can't be used in recursive members,
-- so this requires creative join logic — window function is usually better:
SELECT id, SUM(amount) OVER (ORDER BY id ROWS UNBOUNDED PRECEDING) FROM transactions;
```

**Q17. How do you use a CTE to implement a bill of materials explosion (parts hierarchy)?**

A:

```sql
-- Bill of materials: a product contains components which themselves contain sub-components
CREATE TABLE bom (
  parent_part_id TEXT,
  child_part_id  TEXT,
  quantity       NUMERIC,    -- how many of the child are needed per parent
  PRIMARY KEY (parent_part_id, child_part_id)
);

-- "Explode" the BOM: find ALL materials needed to build 'BIKE-001', including sub-assemblies
WITH RECURSIVE bom_explosion AS (
  -- Anchor: direct components of BIKE-001, quantity = 1 unit of the bike
  SELECT
    parent_part_id,
    child_part_id,
    quantity            AS direct_qty,
    quantity            AS total_qty,   -- cumulative quantity through the hierarchy
    1                   AS level,
    ARRAY[parent_part_id, child_part_id] AS path
  FROM bom
  WHERE parent_part_id = 'BIKE-001'

  UNION ALL

  -- Recursive: sub-components of each component, multiplied by their parent's quantity
  SELECT
    b.parent_part_id,
    b.child_part_id,
    b.quantity                          AS direct_qty,
    b.quantity * be.total_qty           AS total_qty,  -- ← quantity accumulation
    be.level + 1,
    be.path || b.child_part_id
  FROM bom b
  JOIN bom_explosion be ON b.parent_part_id = be.child_part_id
  WHERE b.child_part_id != ALL(be.path)   -- cycle detection: skip if part already in path
)
SELECT
  child_part_id,
  SUM(total_qty)  AS total_quantity_needed,  -- aggregate across paths
  MIN(level)      AS shallowest_level
FROM bom_explosion
GROUP BY child_part_id
ORDER BY shallowest_level, child_part_id;

-- The quantity multiplication (b.quantity * be.total_qty) is the key to BOM explosions:
-- BIKE-001 needs 2 × WHEEL-ASSY
-- WHEEL-ASSY needs 32 × SPOKE
-- Therefore BIKE-001 needs 2 × 32 = 64 SPOKE total
```

## Section 9: Scenario-Based Questions

**Q18. "What is wrong with this recursive CTE and what will happen when it runs?"**

```sql
WITH RECURSIVE hierarchy AS (
  SELECT id, name, manager_id FROM employees
  UNION ALL
  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN hierarchy h ON e.manager_id = h.id
)
SELECT * FROM hierarchy WHERE id = 5;
```

A: Three problems:

**Problem 1 — The anchor has no base case:**
```sql
-- The anchor is:
SELECT id, name, manager_id FROM employees
-- This returns ALL employees — not just the root(s).
-- The anchor should be the starting point (e.g., WHERE manager_id IS NULL for roots,
-- or WHERE id = specific_root for a subtree).

-- With all employees as the anchor, the recursive member then finds everyone
-- who manages anyone already in the result — which starts as everyone.
-- This creates an enormous, likely infinite working table.
```

**Problem 2 — No termination condition:**
```sql
-- The recursive member:
SELECT e.id, e.name, e.manager_id
FROM employees e
JOIN hierarchy h ON e.manager_id = h.id
-- No WHERE clause to limit depth.
-- Combined with Problem 1, this will recursively expand indefinitely.
```

**Problem 3 — Outer WHERE applied too late:**
```sql
WHERE id = 5
-- This filter applies to the FINAL result, not during recursion.
-- Even if the recursion eventually terminates, all employees are traversed
-- before filtering to id=5. The filter cannot push into the recursive CTE
-- (PostgreSQL does not currently optimize this).
-- Result: massive computation to find one row.
```

**Corrected version:**
```sql
-- Find all direct and indirect reports of employee 5:
WITH RECURSIVE hierarchy AS (
  -- Anchor: ONLY employee 5 (the starting node)
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE id = 5

  UNION ALL

  -- Recursive: find direct reports of everyone already in the tree
  SELECT e.id, e.name, e.manager_id, h.depth + 1
  FROM employees e
  JOIN hierarchy h ON e.manager_id = h.id
  WHERE h.depth < 10    -- safety termination
)
SELECT * FROM hierarchy ORDER BY depth, name;

-- OR to find employee 5 AND all their ancestors (management chain above them):
WITH RECURSIVE hierarchy AS (
  SELECT id, name, manager_id FROM employees WHERE id = 5
  UNION ALL
  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN hierarchy h ON e.id = h.manager_id    -- ← reversed: find the manager of each person
)
SELECT * FROM hierarchy;
```

**Q19. "Write a recursive CTE that finds all connected components in an undirected graph."**

A: In an undirected graph each edge (A,B) appears twice — once as A→B and once as B→A. Finding connected components means grouping nodes where every node can reach every other node in the group:

```sql
-- Schema: undirected edges stored as pairs
CREATE TABLE edges (node_a TEXT, node_b TEXT);
INSERT INTO edges VALUES
  ('A', 'B'), ('B', 'A'),
  ('B', 'C'), ('C', 'B'),
  ('D', 'E'), ('E', 'D'),
  ('F', 'F');  -- isolated node

-- Strategy:
-- 1. For each node, find its entire reachable component
-- 2. Use the lexicographically smallest reachable node as the "component ID"
-- 3. All nodes with the same component ID are in the same component

WITH RECURSIVE
  -- All unique nodes in the graph:
  all_nodes AS (
    SELECT node_a AS node FROM edges
    UNION
    SELECT node_b AS node FROM edges
  ),

  -- For each node, do a BFS to find all reachable nodes:
  reachability AS (
    -- Anchor: each node can reach itself
    SELECT
      node         AS source,      -- the node we started from
      node         AS reachable,   -- the node currently being explored
      ARRAY[node]  AS visited
    FROM all_nodes

    UNION ALL

    SELECT
      r.source,
      e.node_b,
      r.visited || e.node_b
    FROM reachability r
    JOIN edges e ON e.node_a = r.reachable
    WHERE e.node_b != ALL(r.visited)    -- cycle detection
  ),

  -- For each node, find the smallest node in its reachable set (component ID):
  components AS (
    SELECT source AS node, MIN(reachable) AS component_id
    FROM reachability
    GROUP BY source
  )

SELECT
  component_id,
  ARRAY_AGG(node ORDER BY node) AS nodes_in_component,
  COUNT(*)                       AS component_size
FROM components
GROUP BY component_id
ORDER BY component_id;

-- Result:
-- component_id | nodes_in_component | component_size
-- -------------+--------------------+----------------
--      A       | {A, B, C}          | 3
--      D       | {D, E}             | 2
--      F       | {F}                | 1
```

**Q20. "Design a recursive CTE for a real-world permission system where roles inherit from other roles."**

A:

```sql
-- Schema: roles can inherit permissions from other roles
CREATE TABLE roles (id INT PRIMARY KEY, name TEXT);
CREATE TABLE role_inheritance (child_role_id INT, parent_role_id INT);
CREATE TABLE role_permissions (role_id INT, permission TEXT);

-- Find ALL permissions of a user (direct role + all inherited permissions):
WITH RECURSIVE
  -- Step 1: get the user's directly assigned roles
  user_roles AS (
    SELECT role_id FROM user_role_assignments WHERE user_id = $1
  ),

  -- Step 2: expand each role to include all parent roles (transitively)
  all_applicable_roles AS (
    -- Anchor: directly assigned roles
    SELECT role_id, ARRAY[role_id] AS path
    FROM user_roles

    UNION ALL

    -- Recursive: parent roles of roles already in the set
    SELECT ri.parent_role_id, aar.path || ri.parent_role_id
    FROM role_inheritance ri
    JOIN all_applicable_roles aar ON ri.child_role_id = aar.role_id
    WHERE ri.parent_role_id != ALL(aar.path)    -- prevent cycles in role hierarchy
  ),

  -- Step 3: collect all unique permissions from all applicable roles
  effective_permissions AS (
    SELECT DISTINCT rp.permission, r.name AS granted_by_role
    FROM all_applicable_roles aar
    JOIN roles r ON r.id = aar.role_id
    JOIN role_permissions rp ON rp.role_id = aar.role_id
  )

SELECT
  permission,
  ARRAY_AGG(granted_by_role ORDER BY granted_by_role) AS granted_by
FROM effective_permissions
GROUP BY permission
ORDER BY permission;

-- Example output for a user with role 'Editor' (inherits from 'Viewer'):
-- permission      | granted_by
-- ----------------+---------------------------
-- content.create  | {Editor}
-- content.delete  | {Editor}
-- content.read    | {Editor, Viewer}
-- content.update  | {Editor}
-- profile.view    | {Viewer}
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **CTE syntax** | `WITH name AS (SELECT ...) SELECT ... FROM name` — single-statement scope |
| **Multiple CTEs** | Separated by commas; later CTEs can reference earlier ones |
| **Column naming** | Name in SELECT list OR in `WITH name(col1, col2) AS (...)` header |
| **Materialization (pre-PG12)** | Always materialized — full CTE evaluated before outer query; optimization fence |
| **Materialization (PG12+)** | Inlined by default (unless recursive, volatile, side-effecting, or referenced 2+ times) |
| **`AS MATERIALIZED`** | Force full evaluation before outer query — ensures single evaluation for non-deterministic CTEs |
| **`AS NOT MATERIALIZED`** | Force inlining — allows planner to push predicates into the CTE |
| **`WITH RECURSIVE`** | Enables self-referencing CTEs; keyword on `WITH`, not on individual CTE name |
| **Anchor member** | Non-recursive first part; evaluated once; produces the initial working table |
| **Recursive member** | References the CTE; evaluated repeatedly until empty result; joins against previous iteration only |
| **`UNION ALL` vs `UNION`** | `UNION ALL` is faster (no deduplication); `UNION` deduplicates against ALL accumulated rows |
| **Termination** | Recursion stops when the recursive member produces 0 rows; always include a WHERE or depth limit |
| **Depth tracking** | Add `depth + 1` column to anchor/recursive; use `WHERE depth < N` to cap traversal |
| **Cycle detection** | `ARRAY[start_node]` in anchor; `visited || new_node` in recursive; `WHERE new_node != ALL(visited)` |
| **`CYCLE` clause (PG14+)** | `CYCLE col SET is_cycle USING path` — automatic cycle detection without manual arrays |
| **`SEARCH BREADTH FIRST`** | PG14+ — adds ordering column for BFS; use with `ORDER BY order_col` |
| **`SEARCH DEPTH FIRST`** | PG14+ — adds ordering column for DFS; use with `ORDER BY order_col` |
| **Data-modifying CTEs** | `INSERT/UPDATE/DELETE ... RETURNING` inside a CTE; all run against same pre-statement snapshot |
| **Atomicity of DML CTEs** | All data-modifying CTEs in one statement are atomic; failure rolls back all changes |
| **BFS order** | `ORDER BY depth` or `SEARCH BREADTH FIRST BY col` — processes each level before going deeper |
| **DFS order** | `ORDER BY path_array` or `SEARCH DEPTH FIRST BY col` — follows one branch to leaf before backtracking |
| **`work_mem`** | Controls memory available for the recursive working table; increase for large hierarchies: `SET work_mem = '256MB'` |
| **Index on join column** | `CREATE INDEX ON table(parent_id)` — essential for recursive CTE performance; each iteration joins on this |
| **Restrictions** | Recursive member cannot use: aggregate functions, window functions, DISTINCT, GROUP BY |
| **vs temp table** | Temp table: spans multiple statements, can be indexed; CTE: single statement, no index |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining the **materialization behavior change in PostgreSQL 12** precisely — before PG12 CTEs were always materialized (an "optimization fence" preventing predicate pushdown), while PG12+ inlines them by default so the planner can push WHERE clauses in; knowing when to explicitly use `AS MATERIALIZED` (non-deterministic expressions like `RANDOM()` referenced twice, or to force early filtering) vs `AS NOT MATERIALIZED` shows production awareness; (2) the **working-table algorithm** for recursive CTE execution — each iteration only sees rows from the previous iteration (not all accumulated rows), which is why the recursion terminates: leaf nodes produce zero rows from the recursive member, emptying the working table; being able to trace through a 3-level tree iteration by iteration distinguishes mechanical understanding from pattern-matching; (3) **mandatory cycle detection** for graph data — any table that allows many-to-many relationships (not a strict tree) can have cycles, and a recursive CTE without cycle detection will run forever; the `visited || new_node WHERE new_node != ALL(visited)` pattern, and the cleaner PG14 `CYCLE` clause, are the two approaches to know; (4) the **`UNION ALL` vs `UNION` tradeoff** in the recursive member — `UNION` deduplicates against the entire accumulated result set at every iteration (extremely expensive for large hierarchies), while `UNION ALL` is almost always correct with explicit cycle detection via the visited-array pattern; and (5) **data-modifying CTEs** — being able to write a single atomic statement that INSERTs, UPDATEs multiple tables, and returns a result using chained CTEs with `RETURNING` clauses, and knowing that all DML CTEs in one statement execute against the same pre-statement snapshot (so two CTEs deleting the same row both "see" it but only one physically deletes it).
