# PostgreSQL Vacuum and Autovacuum: Why Dead Tuples Matter — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a dead tuple and why does PostgreSQL create them instead of updating rows in place?**
A: A dead tuple is a row version that is no longer visible to any transaction but still occupies space on the heap page. PostgreSQL creates dead tuples as a direct consequence of its MVCC (Multi-Version Concurrency Control) architecture — the same mechanism that allows readers to never block writers:

```
MVCC and dead tuples — why they are inevitable:

  Table: accounts (one row: id=1, balance=500)

  Initial state:
  ┌─────────────────────────────────────────────┐
  │ Page 0                                      │
  │ [xmin=100, xmax=0, id=1, balance=500] ← live│
  └─────────────────────────────────────────────┘
  xmin=100: created by transaction 100
  xmax=0:   not yet deleted/updated

  Transaction 200 runs: UPDATE accounts SET balance=400 WHERE id=1;

  PostgreSQL does NOT modify the existing row in place.
  Instead:
  1. Marks old row as "deleted by txn 200": xmax=200
  2. Inserts a NEW row version with the new value

  ┌─────────────────────────────────────────────┐
  │ Page 0                                      │
  │ [xmin=100, xmax=200, id=1, balance=500] DEAD│ ← old version
  │ [xmin=200, xmax=0,   id=1, balance=400] LIVE│ ← new version
  └─────────────────────────────────────────────┘

  Why NOT update in place?
    If txn 200 updates in place and another txn (201) started before 200
    committed, txn 201 would see balance=400 — the new, uncommitted value.
    That is a dirty read — MVCC prevents this by keeping the old version alive.
    Txn 201 sees xmax=200 (not yet committed from its snapshot's perspective)
    and reads the old row: balance=500. Correct isolation, zero locking.

  After txn 200 commits:
    Old row: [xmin=100, xmax=200] — dead for any txn that started after 200
    New row: [xmin=200, xmax=0]   — live
    Old row is now a dead tuple: occupies space, invisible to all new readers
```

```sql
-- Observing dead tuples:
SELECT
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1)
        AS dead_pct,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'accounts'
ORDER BY n_dead_tup DESC;

-- After many UPDATEs with no VACUUM:
-- n_live_tup: 1,000,000
-- n_dead_tup: 4,000,000   ← 4 updates per row on average
-- dead_pct:   80.0%        ← 80% of table space is wasted

-- See actual xmin/xmax on rows:
SELECT id, balance, xmin, xmax
FROM accounts
WHERE id = 1;
-- xmin: transaction that created this version
-- xmax: transaction that deleted/updated this version (0 = still live)
```

```sql
-- DELETE also creates dead tuples (not just UPDATE):
DELETE FROM accounts WHERE id = 1;
-- Row is NOT physically removed. Instead:
-- [xmin=100, xmax=201, id=1, balance=500]  ← xmax=201 marks it as deleted
-- The row sits on the page until VACUUM reclaims it.

-- INSERT followed by ROLLBACK also creates a dead tuple:
BEGIN;
  INSERT INTO accounts (id, balance) VALUES (99, 1000);
  -- Row inserted with xmin = current_txn, xmax = 0
ROLLBACK;
-- After rollback: the row's xmin points to an aborted transaction
-- Row is invisible (xmin is aborted) but still occupies space → dead tuple
-- VACUUM reclaims these too
```

**Q2. Why do dead tuples matter — what are the concrete performance consequences of bloat?**
A: Dead tuples cause table and index bloat. Bloat degrades performance in ways that compound over time and can be catastrophic at scale:

```
Performance consequences of dead tuple accumulation:

  1. Increased table size → more pages to read for sequential scans:
     Table: 1M live rows + 4M dead rows = 5M row-sized slots
     Page size: 8KB, avg row: 200 bytes → ~40 rows per page
     Pages to scan: 5M / 40 = 125,000 pages
     With clean table: 1M / 40 = 25,000 pages
     Sequential scan cost: 5× slower (reads 5× more data)

  2. Index bloat — indexes point to dead rows:
     B-tree index entry: (key value) → (heap page, offset)
     Dead tuples: index entries still exist pointing to dead rows
     Index scan: traverses index → fetches heap page → row is dead → skip
     Result: wasted I/O for every dead index entry visited

  3. Shared buffer cache pollution:
     8GB shared_buffers, 80% bloated table: cache fills with dead tuple pages
     Live data must compete with dead data for cache space
     Effective cache hit rate drops → more disk reads

  4. Visibility map not updated:
     Visibility map: tracks which pages contain ONLY live tuples
     Index-Only Scans require a clean visibility map (no heap fetch needed)
     Bloated pages: not in visibility map → Index-Only Scan falls back to heap
     → Index-Only Scan becomes Index Scan (more expensive)

  5. Transaction ID wraparound risk (the most severe consequence):
     PostgreSQL transaction IDs are 32-bit unsigned integers (cycles at ~2.1B)
     Tables with old, unvacuumed rows block txid advancement
     If horizon reaches wraparound: old rows appear "in the future" → data loss
     PostgreSQL enters read-only emergency mode to prevent corruption
```

```sql
-- Measuring bloat impact:
-- Check if Index-Only Scans are being degraded by bloat:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE user_id = 'u-42';
-- Index Only Scan (good):
--   Heap Fetches: 0    ← no heap access (visibility map clean)
-- vs degraded:
--   Heap Fetches: 450  ← heap fetches needed (visibility map stale due to bloat)

-- Measure table bloat with pgstattuple (extension):
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT
    table_len,
    tuple_count,
    tuple_len,
    dead_tuple_count,
    dead_tuple_len,
    round(dead_tuple_len::numeric / nullif(table_len, 0) * 100, 1) AS dead_pct,
    free_space
FROM pgstattuple('orders');
-- table_len:        500MB (total table size on disk)
-- dead_tuple_count: 2,000,000
-- dead_tuple_len:   200MB  (40% of table is dead)
-- free_space:       50MB   (previously vacuumed but not yet reused)

-- Index bloat:
SELECT * FROM pgstatindex('orders_user_id_idx');
-- avg_leaf_density: 45.3%   (pages only 45% full → lots of wasted space)
-- leaf_fragmentation: 62.1% (high fragmentation → random I/O for range scans)
-- Healthy index: avg_leaf_density > 70%, fragmentation < 30%
```

## Section 2: How VACUUM Works

**Q3. What exactly does VACUUM do — step by step?**
A: VACUUM is PostgreSQL's dead tuple reclamation process. It does not shrink the table on disk (that requires VACUUM FULL), but it marks dead space as reusable and performs several critical maintenance tasks:

```
VACUUM execution — what happens inside:

  Phase 1: Heap scan — identify dead tuples
    Reads every heap page in the table
    For each row: checks xmin/xmax against the oldest active transaction
      xmax is committed AND xmax < oldest_active_txn → row is dead to everyone
      Collects TIDs (tuple IDs) of dead rows into a list

  Phase 2: Index vacuuming — remove dead index entries
    For each index on the table:
      Scans index entries pointing to the dead TIDs collected in Phase 1
      Removes those index entries
      (This is the most expensive phase for heavily-indexed tables)

  Phase 3: Heap vacuuming — reclaim page space
    Returns to heap pages containing dead tuples
    Marks dead slots as free space (adds to Free Space Map)
    Updates visibility map: if ALL tuples on a page are now live and committed
      marks the page as "all-visible" in the visibility map
      → enables Index-Only Scans on this page (no heap fetch needed)

  Phase 4: Truncate (optional)
    If trailing pages (at the end of the file) are entirely empty:
      Truncates the file to return disk space to the OS
      Requires a brief ACCESS EXCLUSIVE lock
      Only happens if many trailing pages are empty

  What VACUUM does NOT do:
    Does NOT lock the table for reads or writes (runs concurrently)
    Does NOT return reclaimed space to the OS (except trailing truncation)
    Does NOT compact rows within pages (pages have gaps after reclamation)
    Does NOT rebuild indexes (REINDEX required for that)
```

```sql
-- Monitoring VACUUM progress in real time:
SELECT
    phase,
    heap_blks_scanned,
    heap_blks_total,
    round(100.0 * heap_blks_scanned / nullif(heap_blks_total, 0), 1) AS heap_pct,
    index_vacuum_count,
    num_dead_tuples,
    num_index_tuples
FROM pg_stat_progress_vacuum
WHERE relid = 'orders'::regclass;
-- phase: 'scanning heap' → 'vacuuming indexes' → 'vacuuming heap' → 'truncating'
-- Shows real-time progress: useful for large table vacuums

-- What VACUUM actually did (after completion):
SELECT
    relname,
    vacuum_count,
    autovacuum_count,
    last_vacuum,
    last_autovacuum,
    n_tup_del AS rows_deleted_since_last_analyze,
    n_dead_tup AS current_dead_tuples
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

```sql
-- VACUUM options — tuning what it does:

-- Basic VACUUM (reclaim dead tuples, update visibility map):
VACUUM orders;

-- VACUUM ANALYZE (vacuum + update statistics in one pass):
VACUUM ANALYZE orders;
-- More efficient than running VACUUM then ANALYZE separately
-- Statistics update helps planner make better decisions after large data changes

-- VACUUM VERBOSE (show what it did):
VACUUM VERBOSE orders;
-- Output:
-- INFO:  vacuuming "public.orders"
-- INFO:  scanned index "orders_pkey" to remove 2 row versions
-- INFO:  scanned index "orders_user_id_idx" to remove 2 row versions
-- INFO:  "orders": removed 250000 row versions in 8750 pages
-- INFO:  "orders": found 250000 removable, 3750000 nonremovable row versions
--        in 125000 out of 125000 pages
-- INFO:  index "orders_pkey": pages: 8192 in total, 0 newly deleted, ...
-- DETAIL: CPU: user: 2.15 s, system: 0.12 s, elapsed: 5.83 s

-- VACUUM FULL — rewrites the entire table:
VACUUM FULL orders;
-- Takes ACCESS EXCLUSIVE lock — blocks ALL reads and writes
-- Rewrites table to a new file, compacting all pages
-- Returns disk space to the OS
-- Rebuilds all indexes from scratch
-- Use only during maintenance windows
-- Alternative for online compaction: pg_repack extension
```

**Q4. What is the Free Space Map (FSM) and the Visibility Map (VM) — how do they interact with VACUUM?**
A: The FSM and VM are per-table auxiliary data structures that VACUUM maintains. The FSM enables efficient INSERT placement; the VM enables Index-Only Scans and controls which pages need VACUUM attention:

```
Free Space Map (FSM):
  One entry per heap page: how many bytes of free space on that page
  Updated by VACUUM when dead tuples are reclaimed
  Used by INSERT/UPDATE: find a page with enough space for the new row
  Without FSM: INSERT always goes to the end of the file → table grows forever
  File: base/<dboid>/<tableoid>_fsm (created automatically when needed)

  Before VACUUM:
    Page 0: [live][dead][dead][live][dead] → 0 bytes free (dead slots not yet reclaimed)
    Page 1: [live][live][dead][dead][dead] → 0 bytes free
  After VACUUM:
    Page 0: [live][FREE][FREE][live][FREE] → 3 × avg_row_size bytes free
    Page 1: [live][live][FREE][FREE][FREE] → 3 × avg_row_size bytes free
  FSM updated: page 0 has N bytes free, page 1 has M bytes free
  Next INSERT: FSM consulted → row placed in existing page → no extension needed

Visibility Map (VM):
  Two bits per heap page:
    Bit 1 (all-visible):   ALL tuples on this page are visible to ALL transactions
    Bit 2 (all-frozen):    ALL tuples on this page are frozen (safe from txid wraparound)
  File: base/<dboid>/<tableoid>_vm

  Impact of all-visible bit:
    Index-Only Scan on a column: planner fetches value from index
    Normally: must check heap to verify row is visible (dead? in progress?)
    If page is all-visible: skip heap check entirely → true Index-Only Scan
    If page NOT all-visible: heap fetch required → degrades to Index Scan

  VACUUM sets all-visible when:
    Every tuple on the page has xmax = 0 (not deleted) or xmax is committed
    AND xmax < oldest_active_transaction (visible to everyone)
```

```sql
-- Checking visibility map coverage:
SELECT
    heap_blks_read,
    heap_blks_hit,
    idx_blks_read,
    idx_blks_hit,
    toast_blks_read,
    tidx_blks_read
FROM pg_statio_user_tables WHERE relname = 'orders';

-- More targeted: what fraction of pages are all-visible?
SELECT
    relname,
    pg_size_pretty(pg_relation_size(oid)) AS heap_size,
    pg_size_pretty(pg_relation_size(oid, 'vm')) AS vm_size
FROM pg_class
WHERE relname = 'orders';

-- Count all-visible pages vs total pages:
CREATE EXTENSION pg_visibility;  -- Extension for visibility map inspection

SELECT
    all_visible,        -- count of all-visible pages
    all_frozen,         -- count of all-frozen pages
    pd_all_visible      -- number where pd_all_visible flag is set in page header
FROM pg_visibility_summary('orders');
-- If all_visible is much less than total pages:
-- Many pages are not all-visible → Index-Only Scans degrading to heap fetches
-- Run VACUUM to set the all-visible bit on clean pages
```

## Section 3: Autovacuum

**Q5. How does autovacuum work — what triggers it and how does it decide which tables to process?**
A: Autovacuum is a background process (actually a launcher that spawns worker processes) that automatically runs VACUUM and ANALYZE based on configurable thresholds. It monitors `pg_stat_user_tables` to decide when a table needs attention:

```
Autovacuum trigger formula:

  VACUUM triggered when:
    n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup

  Defaults:
    autovacuum_vacuum_threshold     = 50    (minimum dead tuples before considering vacuum)
    autovacuum_vacuum_scale_factor  = 0.20  (20% of live tuples)

  Example: orders table with 1,000,000 live rows
    Trigger at: 50 + 0.20 × 1,000,000 = 200,050 dead tuples
    If 200,051 rows are deleted/updated without VACUUM → autovacuum triggers

  ANALYZE triggered when:
    rows_changed > autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × n_live_tup

  Defaults:
    autovacuum_analyze_threshold    = 50
    autovacuum_analyze_scale_factor = 0.10  (10% of live tuples)

  Example: orders with 1,000,000 rows
    ANALYZE trigger: 50 + 0.10 × 1,000,000 = 100,050 rows changed
```

```sql
-- Checking current autovacuum settings:
SHOW autovacuum;                          -- on/off
SHOW autovacuum_max_workers;              -- 3 (default: up to 3 concurrent workers)
SHOW autovacuum_vacuum_threshold;         -- 50
SHOW autovacuum_vacuum_scale_factor;      -- 0.2
SHOW autovacuum_analyze_threshold;        -- 50
SHOW autovacuum_analyze_scale_factor;     -- 0.1
SHOW autovacuum_vacuum_cost_delay;        -- 2ms (throttling between I/O operations)
SHOW autovacuum_vacuum_cost_limit;        -- 200 (cost units before sleeping)

-- See which tables autovacuum is currently processing:
SELECT
    pid,
    datname,
    relid::regclass AS table_name,
    phase,
    heap_blks_scanned,
    heap_blks_total,
    num_dead_tuples
FROM pg_stat_progress_vacuum
JOIN pg_stat_activity USING (pid)
WHERE backend_type = 'autovacuum worker';

-- See autovacuum history per table:
SELECT
    schemaname,
    relname,
    last_autovacuum,
    autovacuum_count,
    last_autoanalyze,
    autoanalyze_count,
    n_dead_tup,
    n_live_tup,
    n_mod_since_analyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
-- Tables with high n_dead_tup that haven't been autovacuumed recently:
-- autovacuum is falling behind — needs tuning
```

```sql
-- How autovacuum is throttled — the cost-based delay:

-- Autovacuum reads/writes pages, consuming I/O bandwidth.
-- Without throttling, it would compete aggressively with user queries.
-- Cost-based throttling: autovacuum accumulates a "cost" for each I/O operation.
-- When the cost limit is reached, autovacuum sleeps for autovacuum_vacuum_cost_delay.

-- Cost model:
--   vacuum_cost_page_hit   = 1   (page found in shared_buffers — cheap)
--   vacuum_cost_page_miss  = 10  (page read from disk — moderate)
--   vacuum_cost_page_dirty = 20  (page modified and written — expensive)

-- Default: autovacuum_vacuum_cost_limit = 200
-- After accumulating 200 cost units, sleep 2ms (autovacuum_vacuum_cost_delay)
-- Rate: 200 units / (2ms sleep) → throughput depends on page hits vs misses

-- Example throughput:
-- If all pages are in cache (cost_page_hit=1): 200 pages per 2ms → 100,000 pages/sec
-- If all pages from disk (cost_page_miss=10): 20 pages per 2ms → 10,000 pages/sec
-- For a 100GB table (12.8M pages): 1280 seconds = ~21 minutes from disk
-- This is intentionally slow to avoid overwhelming the I/O subsystem

-- The throttling is why autovacuum can fall behind on busy tables:
-- Heavy INSERT/UPDATE/DELETE produces dead tuples faster than throttled autovacuum cleans
```

**Q6. How do you tune autovacuum for high-traffic tables — what parameters matter most?**
A: Default autovacuum settings work for moderate workloads but consistently fall behind on large, frequently-updated tables. The two axes of tuning are aggressiveness (how often it triggers) and throughput (how fast it runs when triggered):

```sql
-- Problem: 500M row orders table with 100K updates/minute
-- Default trigger: 50 + 0.20 × 500,000,000 = 100,000,050 dead tuples
-- At 100K updates/minute: ~1000 minutes (16+ hours) before first autovacuum triggers
-- By then: 100M dead tuples, severe bloat

-- Fix: per-table autovacuum settings (preferred over global changes):
ALTER TABLE orders SET (
    -- Trigger much sooner on large tables:
    autovacuum_vacuum_scale_factor  = 0.01,   -- 1% instead of 20% (5M dead = trigger)
    autovacuum_analyze_scale_factor = 0.005,  -- 0.5% for ANALYZE

    -- Increase throughput (reduce throttling):
    autovacuum_vacuum_cost_delay    = 2,      -- 2ms (already default)
    autovacuum_vacuum_cost_limit    = 800,    -- 4× default: process 4× more pages per sleep

    -- For critical tables — eliminate throttling entirely:
    -- autovacuum_vacuum_cost_delay = 0,      -- No sleep (aggressive — impacts I/O)

    -- Reduce minimum threshold (for tables that are always small but active):
    autovacuum_vacuum_threshold     = 100,    -- Lower baseline for small tables
    autovacuum_analyze_threshold    = 50
);

-- Check what a specific table's effective settings are:
SELECT
    relname,
    reloptions  -- Shows per-table settings
FROM pg_class
WHERE relname = 'orders';
```

```sql
-- Global autovacuum settings — affect all tables (change with care):
-- In postgresql.conf or via ALTER SYSTEM:

-- Allow more concurrent autovacuum workers (default: 3):
ALTER SYSTEM SET autovacuum_max_workers = 6;
-- Useful when: multiple tables need simultaneous vacuuming
-- Cost: each worker uses CPU and I/O

-- Increase overall autovacuum aggressiveness:
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = 0.05;  -- 5% (was 20%)
ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 400;     -- 2× throughput

-- For SSD storage (random I/O is cheap — less throttling needed):
ALTER SYSTEM SET autovacuum_vacuum_cost_delay = 0;       -- No delay
ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 2000;    -- 10× default throughput

-- Apply global changes:
SELECT pg_reload_conf();

-- For per-table changes — immediate effect:
-- No reload needed; applied at next autovacuum cycle
```

```sql
-- Autovacuum and INSERT-only tables:
-- Before PostgreSQL 13: autovacuum only triggered on UPDATE/DELETE (dead tuples)
-- INSERT-only tables never triggered autovacuum → visibility map never updated
-- → Index-Only Scans always fell back to heap (no all-visible pages)

-- PostgreSQL 13+: INSERT-triggered autovacuum:
SHOW autovacuum_vacuum_insert_threshold;    -- 1000 (default)
SHOW autovacuum_vacuum_insert_scale_factor; -- 0.2  (default)
-- VACUUM triggers when:
--   inserts_since_last_vacuum > 1000 + 0.2 × n_live_tup
-- For append-only tables (logs, events, audit): tune these down:
ALTER TABLE audit_log SET (
    autovacuum_vacuum_insert_scale_factor = 0.05,  -- 5% inserts triggers vacuum
    autovacuum_vacuum_insert_threshold    = 100
);
-- Ensures visibility map is kept current → Index-Only Scans work efficiently
```

## Section 4: Transaction ID Wraparound

**Q7. What is transaction ID wraparound and why is it the most catastrophic consequence of neglecting VACUUM?**
A: PostgreSQL uses 32-bit transaction IDs (XIDs) to track which transactions created and modified which rows. These IDs are sequential and eventually wrap around to zero. Without VACUUM "freezing" old rows, this wraparound causes PostgreSQL to mistake old rows for future rows — making them invisible — which is effectively data loss:

```
Transaction ID wraparound — the ticking clock:

  PostgreSQL XID space: 0 to 4,294,967,295 (~4.3 billion)
  But: XIDs use modular arithmetic treating the space as circular.
  Each XID can "see" 2^31 (≈2.1 billion) past XIDs and 2^31 future XIDs.

  Current XID: 2,000,000,000

  A row created by XID 1 (xmin=1):
  Is XID 1 "in the past"? 2,000,000,000 - 1 = 1,999,999,999 < 2^31 → YES → visible ✓

  After 2.1 billion more transactions, current XID = 4,100,000,000:
  Wraparound: 4,100,000,000 mod 4,294,967,296 = a small number (e.g., 100,000)

  Now: is XID 1 "in the past"?
  Using modular arithmetic: XID 1 appears to be 2^31 - 1 transactions IN THE FUTURE
  → Row with xmin=1 is now INVISIBLE (appears to belong to a future transaction)
  → Data disappears without deletion!

  PostgreSQL's protection mechanisms:
  1. VACUUM FREEZE: replaces old XIDs with a special "frozen" marker
     Frozen tuples are visible to ALL transactions — no XID comparison needed
  2. autovacuum_freeze_max_age (default: 200,000,000):
     Force VACUUM FREEZE before any table reaches 200M XIDs old
  3. Emergency read-only mode:
     If any table reaches (2^31 - 1) XIDs old: PostgreSQL refuses all writes
     Error: "database is not accepting commands to avoid wraparound data loss"
     Solution: immediate VACUUM FREEZE — potentially hours-long on large tables
```

```sql
-- Monitoring transaction ID age — the most important VACUUM metric:

-- Age of the oldest XID in the database:
SELECT
    datname,
    age(datfrozenxid) AS db_age,
    2147483647 - age(datfrozenxid) AS xids_until_wraparound
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
-- db_age > 1,500,000,000: URGENT — schedule VACUUM FREEZE
-- db_age > 1,800,000,000: CRITICAL — wraparound imminent
-- db_age > 2,100,000,000: EMERGENCY — PostgreSQL will enter read-only mode

-- Age per table (find the oldest table):
SELECT
    schemaname,
    relname,
    age(relfrozenxid) AS table_age,
    pg_size_pretty(pg_total_relation_size(oid)) AS table_size,
    2147483647 - age(relfrozenxid) AS xids_remaining
FROM pg_class
JOIN pg_namespace ON pg_namespace.oid = pg_class.relnamespace
WHERE relkind = 'r'
  AND schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY age(relfrozenxid) DESC
LIMIT 20;
-- The table with the highest age is the wraparound risk
-- Its relfrozenxid must be updated by VACUUM FREEZE before reaching ~2.1B
```

```sql
-- VACUUM FREEZE — the wraparound prevention mechanism:
-- Replaces actual XIDs with a special "frozen" marker in old rows
-- Frozen rows are visible to all transactions, no XID comparison needed

-- PostgreSQL automatically freezes old rows during normal VACUUM when:
--   xmin < current_xid - vacuum_freeze_min_age (default: 50,000,000)
--   The row's XID is "old enough" to be safe to freeze

-- Force freeze of all rows in a table (resets relfrozenxid):
VACUUM FREEZE orders;
-- This is slow: must visit every page to freeze old rows
-- Do during low-traffic windows for large tables

-- Autovacuum triggers aggressive freeze when:
--   age(relfrozenxid) > autovacuum_freeze_max_age (default: 200,000,000)
-- This is a forced VACUUM FREEZE regardless of dead tuple count
-- Can cause unexpected I/O spikes on databases that haven't been tuned

-- Tune freeze thresholds to spread the work:
ALTER SYSTEM SET vacuum_freeze_min_age = 10000000;    -- Freeze sooner (was 50M)
ALTER SYSTEM SET autovacuum_freeze_max_age = 100000000; -- Force vacuum sooner (was 200M)
-- More frequent but smaller freeze operations vs less frequent but larger ones

-- After manual VACUUM FREEZE, check the age dropped:
SELECT relname, age(relfrozenxid) AS new_age
FROM pg_class WHERE relname = 'orders';
-- Should be much lower than before the VACUUM FREEZE
```

## Section 5: VACUUM FULL and Alternatives

**Q8. When should you use `VACUUM FULL` vs alternatives like `pg_repack` — what are the tradeoffs?**
A: `VACUUM FULL` is the nuclear option — it eliminates bloat completely but at the cost of an exclusive lock that blocks all reads and writes for the duration. For production systems, alternatives exist that achieve similar results online:

```
VACUUM vs VACUUM FULL:

  VACUUM (regular):
    Lock level: no lock (runs concurrently with reads AND writes)
    What it does: marks dead space as reusable within pages
    Disk space: NOT returned to OS (reused for future inserts)
    Page compaction: NO — pages have gaps from reclaimed tuples
    Index rebuild: NO — index entries just removed, not compacted
    Speed: fast for the amount of work done (throttled by default)
    Use when: routine maintenance, autovacuum equivalent

  VACUUM FULL:
    Lock level: ACCESS EXCLUSIVE — blocks ALL reads and writes
    What it does: rewrites entire table to a new heap file
    Disk space: returned to OS — table shrinks to minimum size
    Page compaction: YES — all live rows packed into minimum pages
    Index rebuild: YES — all indexes rebuilt from scratch (clean and compact)
    Speed: slow — reads entire table, writes entirely new copy
    Duration: proportional to table size (minutes to hours for large tables)
    Use when: massive one-time bloat removal, maintenance window available
    Risk: during the lock: application is completely unavailable for this table
```

```sql
-- When VACUUM FULL is appropriate:
-- 1. After bulk DELETE that removed >50% of rows (table is permanently smaller)
-- 2. After a migration that rewrote all rows
-- 3. One-time cleanup of a historically neglected database
-- 4. The table is small enough that the lock duration is tolerable (<1 minute)
-- 5. During a scheduled maintenance window where downtime is acceptable

-- VACUUM FULL execution:
VACUUM FULL orders;
-- Builds a new heap file alongside the old one
-- Requires ~2× the current table size in free disk space during operation
-- After completion: old file deleted, new compact file becomes the table
-- All indexes also rebuilt

-- Monitor VACUUM FULL progress:
SELECT
    phase,
    heap_blks_scanned,
    heap_blks_total,
    round(100.0 * heap_blks_scanned / nullif(heap_blks_total, 0), 1) AS pct_done
FROM pg_stat_progress_vacuum WHERE relid = 'orders'::regclass;
-- Note: phase for VACUUM FULL shows different phases than regular VACUUM
```

```sql
-- pg_repack — online alternative to VACUUM FULL:
-- npm install... kidding: CREATE EXTENSION pg_repack; (after OS package install)
-- pg_repack rewrites the table concurrently without an exclusive lock:

-- Installation:
-- apt-get install postgresql-16-repack (or your version)
-- In psql: CREATE EXTENSION pg_repack;

-- Usage:
-- pg_repack -h localhost -U postgres -d mydb -t orders
-- Or for an index:
-- pg_repack -h localhost -U postgres -d mydb --index orders_user_id_idx

-- How pg_repack works:
-- 1. Creates a new table with same structure
-- 2. Copies all rows to new table (no lock yet)
-- 3. Creates a trigger on original table to capture concurrent changes
-- 4. Replays captured changes to new table (catches up)
-- 5. Brief EXCLUSIVE lock to swap new table in place (milliseconds)
-- 6. Drops old table

-- Tradeoffs vs VACUUM FULL:
-- pg_repack: no significant downtime, requires extra disk space (2× table size)
--            takes longer overall (concurrent copy is slower)
--            requires the pg_repack extension
-- VACUUM FULL: complete downtime during lock, same disk space requirement
--              may be faster in absolute time if you have a maintenance window

-- Other online alternatives:
-- CLUSTER orders USING orders_created_at_idx;
--   Rewrites table in index order (physical clustering) + takes ACCESS EXCLUSIVE
--   Better than VACUUM FULL for sequential scan performance afterward
--   Same lock downside — not truly online
```

## Section 6: Operational Monitoring

**Q9. How do you detect that autovacuum is falling behind — what metrics matter and what do you do?**
A: Autovacuum falling behind is one of the most common and insidious production PostgreSQL problems. It manifests as gradually worsening query performance, growing table sizes, and eventually system instability. Detection requires monitoring the right metrics before symptoms become severe:

```sql
-- Dashboard query: autovacuum health across all tables
SELECT
    schemaname || '.' || relname AS table_name,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_live_tup,
    n_dead_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1)
        AS dead_pct,
    n_mod_since_analyze,
    last_autovacuum::date AS last_vacuum,
    last_autoanalyze::date AS last_analyze,
    age(relfrozenxid) AS xid_age,
    -- How many dead tuples until autovacuum would trigger?
    greatest(0,
        (current_setting('autovacuum_vacuum_threshold')::int +
         current_setting('autovacuum_vacuum_scale_factor')::float * n_live_tup)
        - n_dead_tup
    ) AS dead_tups_until_trigger
FROM pg_stat_user_tables
JOIN pg_class ON pg_class.oid = pg_stat_user_tables.relid
ORDER BY n_dead_tup DESC
LIMIT 20;

-- Red flags to alert on:
-- dead_pct > 20%: significant bloat accumulating
-- xid_age > 500,000,000: approaching risky territory
-- last_vacuum > 1 day ago for high-traffic tables: autovacuum too slow
-- dead_tups_until_trigger < 0: autovacuum is triggered but still behind
```

```sql
-- Check if autovacuum is currently running and what it's doing:
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY duration DESC;

-- Check autovacuum cancellations (autovacuum killed by user queries):
SELECT
    relname,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
WHERE last_autovacuum < NOW() - INTERVAL '1 hour'
  AND n_dead_tup > 100000
ORDER BY n_dead_tup DESC;
-- These tables have many dead tuples but haven't been vacuumed recently
-- Could mean: autovacuum being killed by lock_timeout or statement_timeout

-- Find autovacuum lock conflicts:
SELECT
    blocked_activity.pid AS blocked_pid,
    blocking_activity.pid AS blocking_pid,
    blocked_activity.backend_type,
    blocking_activity.query AS blocking_query,
    now() - blocked_activity.query_start AS blocked_duration
FROM pg_stat_activity AS blocked_activity
JOIN pg_locks AS blocked_locks ON blocked_activity.pid = blocked_locks.pid
JOIN pg_locks AS blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND NOT blocked_locks.granted
    AND blocking_locks.granted
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_stat_activity AS blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE blocked_activity.backend_type = 'autovacuum worker';
-- If autovacuum is constantly being blocked by long-running queries:
-- Consider: lock_timeout for autovacuum, or fix the long-running queries
```

```sql
-- Common autovacuum problems and solutions:

-- Problem 1: autovacuum_max_workers all busy but more tables need vacuum
SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'autovacuum worker';
-- If = autovacuum_max_workers: workers exhausted
-- Fix: increase autovacuum_max_workers (check CPU and I/O capacity first)
ALTER SYSTEM SET autovacuum_max_workers = 6;
SELECT pg_reload_conf();

-- Problem 2: one table consuming all autovacuum capacity
-- A huge table takes hours to vacuum → other tables starved
-- Fix: run manual VACUUM on the large table, let autovacuum handle others:
VACUUM (VERBOSE, ANALYZE) orders;  -- Manual, non-throttled
-- Or: set aggressive per-table settings for critical small tables
ALTER TABLE hot_small_table SET (autovacuum_vacuum_cost_limit = 2000);

-- Problem 3: autovacuum repeatedly cancelled by lock_timeout
-- Long transactions hold locks → autovacuum waits → lock_timeout kills autovacuum
-- Fix: autovacuum is exempt from lock_timeout by default (PostgreSQL 12+)
-- But check: lock_timeout on autovacuum specifically:
SHOW lock_timeout;  -- Session-level; autovacuum uses its own timeout
-- autovacuum.lock_timeout defaults to 0 (no timeout) in PostgreSQL 12+
-- Earlier versions: set autovacuum_lock_timeout explicitly

-- Problem 4: table never vacuumed because always "active" (long transactions)
-- The VACUUM horizon (oldest active transaction) blocks cleanup of dead tuples
-- that are still potentially visible to old transactions
-- Fix: find and kill old transactions:
SELECT pid, now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE xact_start < NOW() - INTERVAL '1 hour'
ORDER BY xact_start;
-- Terminate: SELECT pg_terminate_backend(pid);
-- Prevent recurrence: SET idle_in_transaction_session_timeout = '10min';
```

**Q10. How do you set up proactive VACUUM monitoring and alerting?**
A: The right approach is to monitor the leading indicators — XID age, dead tuple percentage, and autovacuum lag — before they become symptoms:

```sql
-- Query to export as a monitoring metric (run every 5 minutes):
SELECT
    -- Wraparound risk:
    max(age(datfrozenxid)) AS max_db_xid_age,
    (SELECT max(age(relfrozenxid))
     FROM pg_class
     WHERE relkind = 'r') AS max_table_xid_age,

    -- Bloat accumulation:
    (SELECT count(*) FROM pg_stat_user_tables
     WHERE n_dead_tup::float / nullif(n_live_tup + n_dead_tup, 0) > 0.2)
        AS tables_with_20pct_bloat,

    -- Autovacuum lag:
    (SELECT count(*) FROM pg_stat_user_tables
     WHERE n_dead_tup > 100000
       AND last_autovacuum < NOW() - INTERVAL '1 hour')
        AS overdue_vacuums

FROM pg_database WHERE datname = current_database();
```

```
Alert thresholds (Prometheus / Grafana / Datadog):

  max_db_xid_age:
    Warning:  > 500,000,000 (25% of wraparound limit)
    Critical: > 1,500,000,000 (75% of limit — schedule VACUUM FREEZE immediately)
    Emergency:> 1,800,000,000 (90% — VACUUM FREEZE now, alert on-call)

  max_table_xid_age:
    Warning:  > 200,000,000 (autovacuum will force freeze soon — expect I/O spike)
    Critical: > 800,000,000

  dead_tuple_percentage (per table):
    Warning:  > 10% on any table
    Critical: > 30% on any table over 1GB

  time_since_last_autovacuum (on high-traffic tables):
    Warning:  > 30 minutes for tables with > 1M rows
    Critical: > 2 hours
```

```sql
-- Emergency response: manual VACUUM for critical situations:

-- When wraparound is imminent (xid_age approaching 1.5B+):
-- Stop autovacuum from taking resources for other tables:
ALTER TABLE noncritical_table SET (autovacuum_enabled = false);

-- Run VACUUM FREEZE aggressively on the oldest tables:
-- First: find them
SELECT relname, age(relfrozenxid)
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 5;

-- Then: freeze them (set maintenance_work_mem high for speed):
SET maintenance_work_mem = '2GB';
VACUUM FREEZE VERBOSE critical_table;
-- maintenance_work_mem: controls how many dead TIDs fit in memory per vacuum pass
-- Larger value → fewer passes needed → faster vacuum on tables with many dead tuples
-- Default: 64MB (too small for large tables)

-- After emergency: re-enable autovacuum on non-critical tables:
ALTER TABLE noncritical_table SET (autovacuum_enabled = true);

-- Check progress:
SELECT relname, age(relfrozenxid) AS age_before, now() AS checked_at
FROM pg_class WHERE relname IN ('critical_table');
-- Run again after VACUUM FREEZE completes to confirm age dropped
```

## Section 7: Advanced Topics

**Q11. How does VACUUM interact with replication — what is a replication slot and why is it dangerous for VACUUM?**
A: Replication slots prevent WAL segments from being recycled until the subscriber has consumed them. But they also prevent VACUUM from advancing the `xmin` horizon — dead tuples cannot be cleaned if a replication slot holds an old transaction snapshot:

```sql
-- Replication slots and the VACUUM horizon:

-- Each replication slot records the oldest XID that the subscriber might need
-- VACUUM cannot remove dead tuples created after that XID
-- If the subscriber falls far behind: VACUUM is blocked from cleaning
-- → Dead tuples accumulate → bloat grows → performance degrades

-- Check replication slot lag:
SELECT
    slot_name,
    slot_type,
    database,
    active,
    active_pid,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_lag,
    catalog_xmin,
    age(catalog_xmin) AS catalog_xmin_age,
    xmin,
    age(xmin) AS xmin_age
FROM pg_replication_slots;

-- Danger signals:
-- catalog_xmin_age > 100,000,000: logical replication slot very old
-- wal_lag > 10GB: subscriber far behind, WAL accumulating on primary
-- If active = false: slot is inactive (subscriber disconnected)
--   → Slot is still preventing WAL recycling AND VACUUM advancement
--   → This will cause disk to fill and wraparound risk

-- Solution for inactive slots (subscriber is gone permanently):
DROP REPLICATION SLOT slot_name;
-- WARNING: this permanently breaks the replication connection
-- Subscriber will need to resync from scratch

-- Set a limit on replication lag to auto-drop problematic slots:
ALTER SYSTEM SET max_slot_wal_keep_size = '10GB';
-- If WAL kept for a slot exceeds 10GB: slot is automatically invalidated
-- Prevents disk exhaustion from runaway slots (PostgreSQL 13+)

-- For logical replication subscribers falling behind:
-- Check lag on subscriber side:
-- SELECT * FROM pg_stat_subscription;
-- If lag growing: subscriber may be overloaded, or network issue
-- Fix: increase subscriber worker count or publication batching
```

```sql
-- The catalog_xmin problem — logical replication and vacuuming system catalogs:
-- Logical replication slots track catalog_xmin: oldest XID reading the catalog
-- pg_catalog tables (pg_class, pg_attribute, etc.) accumulate dead tuples
-- but autovacuum cannot clean them if catalog_xmin is held old

-- Check catalog bloat:
SELECT
    relname,
    n_dead_tup,
    n_live_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct
FROM pg_stat_all_tables
WHERE schemaname = 'pg_catalog'
  AND n_dead_tup > 100
ORDER BY n_dead_tup DESC;
-- pg_attribute and pg_class are the most commonly bloated catalog tables
-- High bloat here slows down query planning (planner reads catalog frequently)

-- Fix: if catalog_xmin is held old by a lagging logical slot,
-- the only solutions are:
-- 1. Let the subscriber catch up
-- 2. Drop the slot and resync the subscriber
-- 3. Increase wal_receiver_timeout to give subscriber more time before disconnect
```

**Q12. How does `maintenance_work_mem` affect VACUUM performance?**
A: VACUUM uses memory to collect the TIDs (tuple identifiers) of dead rows before removing their index entries. If the dead tuple list exceeds `maintenance_work_mem`, VACUUM must make multiple passes over the indexes — dramatically increasing the time for heavily-indexed tables:

```
VACUUM memory and multi-pass behaviour:

  Dead tuples collected in heap scan Phase 1:
    Each dead TID: 6 bytes (page number + offset)
    maintenance_work_mem: 64MB default → 64MB / 6 bytes = ~11M TIDs per pass

  If table has 50M dead tuples and maintenance_work_mem = 64MB:
    Pass 1: collect 11M dead TIDs → vacuum ALL indexes for these 11M
    Pass 2: collect 11M dead TIDs → vacuum ALL indexes again
    Pass 3: collect 11M dead TIDs → vacuum ALL indexes again
    Pass 4: collect 11M dead TIDs → vacuum ALL indexes again
    Pass 5: collect 6M dead TIDs  → vacuum ALL indexes once more
    Total: 5 complete index scans instead of 1

  For a table with 10 indexes:
    maintenance_work_mem = 64MB:   5 passes × 10 indexes = 50 index scans
    maintenance_work_mem = 1GB:    1 pass  × 10 indexes = 10 index scans
    1GB version: 5× faster for this table

  Memory cost: maintenance_work_mem is per-VACUUM-worker, not shared
  With autovacuum_max_workers = 6: up to 6 × maintenance_work_mem in use
  At 1GB × 6 workers = 6GB RAM reserved for autovacuum
  Balance against shared_buffers and work_mem needs
```

```sql
-- Setting maintenance_work_mem for a manual VACUUM session:
SET maintenance_work_mem = '1GB';
VACUUM (VERBOSE, ANALYZE) orders;
-- Only affects this session — does not change autovacuum's memory

-- Changing maintenance_work_mem for autovacuum:
ALTER SYSTEM SET autovacuum_work_mem = 256MB;  -- Separate from maintenance_work_mem
SELECT pg_reload_conf();
-- autovacuum_work_mem: -1 = use maintenance_work_mem (default)
-- Setting it explicitly: autovacuum workers use this much, manual VACUUM uses maintenance_work_mem

-- Monitoring multi-pass vacuum:
VACUUM VERBOSE (ANALYZE) orders;
-- In verbose output, look for:
-- "scanned index ... to remove ... row versions" appearing multiple times
-- Multiple scans = multi-pass = maintenance_work_mem too small

-- For a specific bloated table — one-off with high memory:
SET maintenance_work_mem = '2GB';  -- Temporary for this session
VACUUM FREEZE VERBOSE orders;
RESET maintenance_work_mem;        -- Reset to default after
```

## Section 8: Scenario-Based Questions

**Q13. "Your production database has been running for 2 years with default settings. Table sizes have ballooned. Queries that used to take 50ms now take 2 seconds. Design a recovery plan."**
A: A neglected database with 2 years of default settings almost certainly has bloated tables, bloated indexes, stale statistics, and possibly a high XID age. The recovery is a sequence of increasingly aggressive interventions:

```sql
-- Step 1: Assess the damage

-- What's the XID age? (Most urgent risk):
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database ORDER BY age(datfrozenxid) DESC;

-- Which tables are most bloated?
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(oid)) AS total_size,
    n_dead_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
    age(relfrozenxid) AS xid_age
FROM pg_stat_user_tables
JOIN pg_class ON pg_class.oid = relid
ORDER BY pg_total_relation_size(oid) DESC
LIMIT 20;

-- Are statistics stale? (Compare estimate vs actual):
EXPLAIN (ANALYZE) SELECT count(*) FROM orders WHERE status = 'PENDING';
-- Large gap between rows= estimate and actual rows= → run ANALYZE

-- Are Index-Only Scans working?
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id FROM orders WHERE user_id = 'u-42';
-- "Heap Fetches: 50000" → visibility map not current → VACUUM needed
```

```sql
-- Step 2: Emergency fixes (immediate, during business hours)

-- Update statistics first (fast, no lock):
ANALYZE;  -- Analyzes all tables (or specify critical ones)
-- This alone may improve query plans within minutes

-- Set maintenance_work_mem high for the session:
SET maintenance_work_mem = '2GB';

-- Vacuum the 5 most critical (largest/most bloated) tables manually:
VACUUM (VERBOSE, ANALYZE) orders;
VACUUM (VERBOSE, ANALYZE) order_items;
VACUUM (VERBOSE, ANALYZE) users;
VACUUM (VERBOSE, ANALYZE) products;
VACUUM (VERBOSE, ANALYZE) events;
-- Regular VACUUM: no lock, runs concurrently — safe during business hours
-- Each may take minutes to hours depending on table size and dead tuple count

-- If XID age is > 1 billion — also freeze the oldest tables:
VACUUM FREEZE orders;  -- More thorough than regular VACUUM
```

```sql
-- Step 3: Fix autovacuum settings (prevent recurrence)

-- Increase aggressiveness for large tables:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_analyze_scale_factor = 0.005,
    autovacuum_vacuum_cost_limit = 800
);
ALTER TABLE order_items SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_cost_limit = 800
);

-- Increase global capacity:
ALTER SYSTEM SET autovacuum_max_workers = 6;
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = 0.05;  -- 5% (was 20%)
ALTER SYSTEM SET maintenance_work_mem = '256MB';  -- For autovacuum workers
ALTER SYSTEM SET autovacuum_work_mem = '256MB';
SELECT pg_reload_conf();

-- Prevent idle transactions from holding VACUUM horizon:
ALTER SYSTEM SET idle_in_transaction_session_timeout = '10min';
SELECT pg_reload_conf();
```

```sql
-- Step 4: VACUUM FULL for worst offenders (requires maintenance window)

-- Schedule a maintenance window for the tables with > 50% bloat:
-- During window (application offline or read-only):
SET maintenance_work_mem = '4GB';

VACUUM FULL VERBOSE orders;
VACUUM FULL VERBOSE order_items;
-- Monitor: SELECT phase, heap_blks_scanned, heap_blks_total
```

**Q14. "Autovacuum is running but a specific table keeps accumulating dead tuples faster than VACUUM can process. How do you diagnose why and what do you do?"**
A: When autovacuum is running but a table keeps bloating, there are three root causes: autovacuum is being cancelled, it's too throttled to keep up with the write rate, or an old transaction is preventing cleanup:

```sql
-- Diagnosis Step 1: Is autovacuum actually running on this table?
SELECT pid, query, state, backend_type, query_start
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
  AND query LIKE '%my_hot_table%';
-- If no rows: autovacuum is not currently running on this table
-- Check: is another worker consuming all autovacuum capacity?
SELECT count(*), backend_type FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker' GROUP BY backend_type;
-- If count = autovacuum_max_workers: workers exhausted on other tables

-- Diagnosis Step 2: Is autovacuum being cancelled?
-- Check PostgreSQL log for cancellation messages:
-- grep "autovacuum: canceling" /var/log/postgresql/postgresql.log
-- Message: "autovacuum: canceling vacuum of table "public.my_hot_table"
--           due to conflict with recovery"
-- (This happens on hot standby replicas — autovacuum cancelled to avoid
--  conflicting with replica queries)

-- Diagnosis Step 3: Is an old transaction blocking the VACUUM horizon?
SELECT
    pid,
    usename,
    application_name,
    now() - xact_start AS txn_duration,
    backend_xid,
    backend_xmin,
    state,
    query
FROM pg_stat_activity
WHERE (backend_xmin IS NOT NULL OR backend_xid IS NOT NULL)
  AND state != 'idle'
ORDER BY txn_duration DESC NULLS LAST;
-- If a transaction has been open for hours:
-- Its backend_xmin prevents VACUUM from cleaning tuples created after it started
-- Even if autovacuum runs, it cannot remove "recently" dead tuples
-- Fix: terminate the old transaction (with care):
-- SELECT pg_terminate_backend(pid) WHERE pid = <long_running_pid>;

-- Diagnosis Step 4: Is the write rate just too high?
-- Calculate write rate vs autovacuum cleanup rate:
SELECT
    relname,
    n_tup_upd + n_tup_del AS writes_since_reset,
    autovacuum_count,
    last_autovacuum,
    n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'my_hot_table';
-- If writes_since_reset >> n_live_tup × autovacuum_vacuum_scale_factor:
-- The write rate genuinely exceeds autovacuum capacity at current settings
```

```sql
-- Solutions:

-- Solution 1: Reduce autovacuum throttling for this specific table:
ALTER TABLE my_hot_table SET (
    autovacuum_vacuum_cost_delay  = 0,      -- Remove sleep between I/O operations
    autovacuum_vacuum_cost_limit  = 2000,   -- 10× default throughput
    autovacuum_vacuum_scale_factor = 0.01   -- Trigger earlier (1% dead tuples)
);

-- Solution 2: Run manual VACUUM alongside autovacuum (additive):
-- Manual VACUUM does not conflict with autovacuum — they run concurrently
-- But: they split the dead tuple work
SET maintenance_work_mem = '1GB';  -- Give manual vacuum more memory
VACUUM (PARALLEL 4) my_hot_table;  -- PostgreSQL 13+: parallel vacuum workers
-- PARALLEL N: use up to N workers for index vacuuming (parallel index scans)
-- Dramatically faster for tables with many indexes

-- Solution 3: Partition the table to distribute vacuum load:
-- A 1-billion row table vacuum takes hours
-- 12 monthly partitions of ~83M rows each:
--   Autovacuum processes each partition independently
--   Smaller partitions = faster per-partition vacuum = less bloat per partition
--   Write-heavy current month gets frequent vacuum, old months rarely need it

-- Solution 4: Application-level dead tuple reduction:
-- Consider HOT (Heap-Only Tuple) updates:
-- HOT update: when UPDATE changes only non-indexed columns on the same page
--   PostgreSQL chains old and new tuple versions on the same page
--   No index update needed (index still points to old tuple, follows chain)
--   Dead tuple reclaimed without index scan (cheaper vacuum)
-- Enable HOT: use lower fillfactor on tables with many updates:
ALTER TABLE my_hot_table SET (fillfactor = 70);
-- 30% page slack: more room for HOT updates within the same page
-- VACUUM FULL or CLUSTER needed to apply fillfactor to existing pages
-- Rebuild: VACUUM FULL my_hot_table;  (or pg_repack for online)
```

## Quick Reference Table

| Concept | What it is | Why it matters | Key metric |
|---|---|---|---|
| Dead tuple | A row version no longer visible to any transaction, still occupying heap space | Causes table/index bloat, degrades seq scan, pollutes buffer cache, blocks index-only scans | `n_dead_tup` in `pg_stat_user_tables` |
| VACUUM | Background reclamation of dead tuple space; marks space as reusable; updates FSM and visibility map | Prevents bloat, enables index-only scans, advances freeze horizon | `last_autovacuum`, `vacuum_count` |
| VACUUM FULL | Rewrites entire table to remove bloat; returns disk to OS | Eliminates bloat completely; requires ACCESS EXCLUSIVE lock blocking all traffic | Duration ∝ table size; plan maintenance window |
| Autovacuum | Background daemon that runs VACUUM/ANALYZE automatically based on thresholds | Prevents manual VACUUM requirement; keeps tables healthy without operator intervention | Workers running: `pg_stat_activity WHERE backend_type = 'autovacuum worker'` |
| Autovacuum trigger | `n_dead_tup > threshold + scale_factor × n_live_tup` | Default 20% scale factor means large tables wait too long | `autovacuum_vacuum_scale_factor` per-table override |
| Cost-based throttling | Autovacuum sleeps `vacuum_cost_delay` after accumulating `vacuum_cost_limit` cost units | Prevents autovacuum from overwhelming I/O but causes it to fall behind on write-heavy tables | `autovacuum_vacuum_cost_limit`, `autovacuum_vacuum_cost_delay` |
| Visibility Map | Per-table bitmap: which pages contain only live, committed tuples | Index-Only Scans require all-visible pages; stale visibility map forces heap fetches | `Heap Fetches: N` in `EXPLAIN ANALYZE` — should be 0 |
| Free Space Map | Per-table: amount of free space per page after VACUUM | Enables INSERT to reuse reclaimed space instead of extending the file | `pg_relation_size(oid, 'fsm')` |
| XID wraparound | 32-bit transaction IDs cycle at ~2.1B; un-frozen old rows become invisible | Most catastrophic consequence of neglected VACUUM; causes data loss and PostgreSQL emergency mode | `age(relfrozenxid)` — alert > 500M, critical > 1.5B |
| VACUUM FREEZE | Replaces actual XIDs with frozen marker; frozen rows visible to all transactions | Resets the wraparound clock; must happen before tables reach ~2.1B XID age | `vacuum_freeze_min_age`, `autovacuum_freeze_max_age` |
| `maintenance_work_mem` | Memory for VACUUM's dead TID list per pass | Too small → multi-pass index scans → very slow vacuum on indexed tables | Set `2GB` for manual VACUUM of large tables; `autovacuum_work_mem` for autovacuum |
| Replication slot lag | Slot records oldest XID subscriber needs; prevents VACUUM from cleaning older tuples | Inactive or lagging slots cause bloat to accumulate despite VACUUM running | `age(xmin)` in `pg_replication_slots`; `pg_wal_lsn_diff()` for WAL lag |
| HOT update | UPDATE that changes only non-indexed columns on same page; no index update needed | Cheaper than regular UPDATE; reduces index bloat; lower vacuum cost | Increase via `fillfactor < 100` on frequently-updated tables |

**Tip for interviews:** Five things separate strong candidates on PostgreSQL VACUUM: (1) explaining **why dead tuples are structurally inevitable** — that MVCC requires keeping old row versions alive so that transactions with older snapshots can still see them, and that the xmin/xmax system means every UPDATE creates a new row version and marks the old one deleted, making dead tuple accumulation the fundamental cost of MVCC's no-reader-locks guarantee; (2) knowing **the three-layer consequence of bloat** — that dead tuples waste space causing seq scans to read more pages, that index entries pointing to dead rows waste I/O during index scans, and most critically that un-vacuumed pages don't get their all-visible bit set in the visibility map, which forces Index-Only Scans to make heap fetches and effectively degrades them to Index Scans — and that `Heap Fetches: N` in `EXPLAIN ANALYZE` is the diagnostic signature of this degradation; (3) being able to explain **XID wraparound from first principles** — that PostgreSQL uses 32-bit modular arithmetic for transaction visibility, that the safe window is only 2^31 (~2.1B) XIDs behind the current XID, that un-frozen rows from before that window appear to be "in the future" and become invisible (data loss), and that VACUUM FREEZE replaces actual XIDs with a special frozen marker that is always visible to all transactions; (4) knowing **the default autovacuum trigger formula** and why it fails for large tables — that `threshold + 0.2 × n_live_tup` means a 500M row table needs 100M dead tuples before autovacuum triggers, which at 100K updates/minute takes 1000 minutes, and that the fix is per-table `autovacuum_vacuum_scale_factor = 0.01` to trigger at 1% instead of 20%; and (5) understanding **why `maintenance_work_mem` matters for VACUUM speed** — that VACUUM collects dead TIDs in memory and removes index entries for all of them in one pass, but if there are more dead TIDs than fit in `maintenance_work_mem`, it must make multiple passes over all indexes (each pass = a full index scan per index), so a table with 50M dead tuples and `maintenance_work_mem = 64MB` (holds ~11M TIDs) requires 5 complete passes over all indexes, while 1GB of memory does it in one pass.
