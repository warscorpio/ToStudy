# PostgreSQL Transaction Isolation Levels — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a transaction isolation level and why does it exist?**
A: A transaction isolation level defines how and when changes made by one transaction become visible to other concurrent transactions. It exists because allowing transactions to see each other's in-progress work freely causes data anomalies — but preventing it entirely requires locking that kills throughput. Isolation levels are a tunable tradeoff between correctness and concurrency:

```
The fundamental tension:
  High isolation  → fewer anomalies → more locking → lower throughput
  Low isolation   → more anomalies → less locking → higher throughput

Why this matters in practice:
  A lending platform processes 500 concurrent loan applications.
  Each application reads account balance, then writes a debit.
  Without isolation: two transactions both read balance=10000,
                     both decide "sufficient funds", both debit 8000
                     → balance goes to -6000.
  With isolation:    one transaction wins; the other re-reads the
                     updated balance and correctly fails the check.

SQL standard defines four levels (lowest to highest isolation):
  1. Read Uncommitted  — see other transactions' uncommitted changes
  2. Read Committed    — see only committed changes (snapshot per statement)
  3. Repeatable Read   — snapshot at transaction start, no phantom rows
  4. Serializable      — full serializability (as if transactions ran one at a time)

PostgreSQL specifics:
  - PostgreSQL does NOT implement Read Uncommitted as a separate level.
    Requesting it silently upgrades to Read Committed.
  - PostgreSQL uses MVCC (Multi-Version Concurrency Control) — readers
    never block writers, writers never block readers. Isolation is achieved
    via snapshots, not read locks.
  - Default isolation level: Read Committed.
```

**Q2. What is MVCC and how does PostgreSQL use it to implement isolation without read locks?**
A: Multi-Version Concurrency Control maintains multiple versions of each row, each stamped with the transaction IDs that created and deleted it. A transaction's snapshot determines which row versions are visible to it — no read lock needed:

```
Row version structure (simplified):
  Each heap tuple has system columns:
    xmin  — transaction ID that inserted this row version
    xmax  — transaction ID that deleted/updated this row (0 if current)
    ctid  — physical location of this tuple

  Example: row with id=1, balance=1000
  ┌─────────┬─────────┬───────────────────────────┐
  │  xmin   │  xmax   │  data                     │
  ├─────────┼─────────┼───────────────────────────┤
  │  txid 5 │    0    │  { id:1, balance: 1000 }  │ ← current version
  └─────────┴─────────┴───────────────────────────┘

  Transaction 10 updates balance to 900:
  ┌─────────┬─────────┬───────────────────────────┐
  │  xmin   │  xmax   │  data                     │
  ├─────────┼─────────┼───────────────────────────┤
  │  txid 5 │  txid10 │  { id:1, balance: 1000 }  │ ← old version (visible to snapshots < txid10)
  │  txid10 │    0    │  { id:1, balance:  900 }  │ ← new version (visible to snapshots ≥ txid10)
  └─────────┴─────────┴───────────────────────────┘

Snapshot = set of transaction IDs visible to the current transaction.
  "Visible" means: xmin committed AND xmin is in my snapshot AND (xmax = 0 OR xmax not committed OR xmax not in my snapshot)

How this enables concurrency:
  - Reader (SELECT) takes no locks — it just reads the version its snapshot says is current
  - Writer (UPDATE/DELETE) takes a row-level write lock — but only blocks other writers, not readers
  - Reader and writer can proceed simultaneously on the same row

MVCC cleanup:
  Old row versions are not removed immediately — VACUUM reclaims them later.
  This is why long-running transactions are harmful: they hold back the snapshot
  horizon, preventing VACUUM from cleaning dead tuples → table bloat.
```

**Q3. What are the four read phenomena the SQL standard defines, and which isolation level prevents each?**
A: The SQL standard defines four data anomalies that arise from concurrent transactions. Each isolation level is defined by which anomalies it prevents:

```
Anomaly 1: Dirty Read
  Definition: Transaction A reads data written by Transaction B before B commits.
              If B rolls back, A has read data that never existed.
  Example:
    T1: UPDATE accounts SET balance = 0 WHERE id = 1;   -- not yet committed
    T2: SELECT balance FROM accounts WHERE id = 1;       -- sees 0 (dirty!)
    T1: ROLLBACK;                                        -- balance was never 0
    T2 made a decision based on a phantom value.

Anomaly 2: Non-Repeatable Read
  Definition: Transaction A reads a row, Transaction B updates and commits it,
              Transaction A re-reads the same row and gets a different value.
  Example:
    T1: SELECT balance FROM accounts WHERE id = 1;  -- reads 1000
    T2: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
    T1: SELECT balance FROM accounts WHERE id = 1;  -- reads 500 (different!)
    T1's two reads of the same row produced different results.

Anomaly 3: Phantom Read
  Definition: Transaction A runs a range query, Transaction B inserts/deletes
              rows matching that range and commits, Transaction A re-runs the
              same range query and gets a different set of rows.
  Example:
    T1: SELECT * FROM loans WHERE amount > 100000;  -- returns 5 rows
    T2: INSERT INTO loans (amount) VALUES (150000); COMMIT;
    T1: SELECT * FROM loans WHERE amount > 100000;  -- returns 6 rows (phantom!)
    The new row "appeared" between T1's two reads.

Anomaly 4: Serialization Anomaly (Write Skew)
  Definition: The combined result of two concurrent transactions produces an
              outcome that could not result from any serial execution.
  Example (on-call doctor problem):
    Rule: at least one doctor must be on call.
    T1: SELECT count(*) FROM oncall; -- sees 2
    T2: SELECT count(*) FROM oncall; -- sees 2
    T1: DELETE FROM oncall WHERE doctor = 'Alice'; -- COMMIT
    T2: DELETE FROM oncall WHERE doctor = 'Bob';   -- COMMIT
    Result: 0 doctors on call — violates the constraint.
    Neither transaction alone would have caused this.

Prevention table:
                        │ Dirty  │ Non-Rep│ Phantom│ Serializ│
  ──────────────────────┼────────┼────────┼────────┼─────────┤
  Read Uncommitted      │  No    │  No    │  No    │  No     │
  Read Committed        │  Yes   │  No    │  No    │  No     │
  Repeatable Read       │  Yes   │  Yes   │  Yes*  │  No     │
  Serializable          │  Yes   │  Yes   │  Yes   │  Yes    │

  * PostgreSQL's Repeatable Read prevents phantom reads via snapshot isolation
    (stronger than the SQL standard requires at this level).
    The standard only guarantees phantom-free at Serializable.
```

## Section 2: Read Committed

**Q4. How does Read Committed work in PostgreSQL and what is its snapshot model?**
A: Read Committed is PostgreSQL's default. It takes a new snapshot at the start of each statement — not the transaction. Every SQL statement sees all commits that happened before that statement began:

```sql
-- Snapshot model: per-statement (not per-transaction)

-- Session A:
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- Snapshot taken HERE (start of statement) → sees all commits up to this moment
-- Returns: 1000

-- (Session B runs and commits: UPDATE accounts SET balance = 900 WHERE id = 1)

SELECT balance FROM accounts WHERE id = 1;
-- NEW snapshot taken HERE → sees Session B's commit
-- Returns: 900  ← different from first read (non-repeatable read)

COMMIT;

-- Practical implication — UPDATE sees committed rows even mid-transaction:
BEGIN;
-- Check if loan is eligible:
SELECT status FROM loans WHERE id = 'L1';  -- snapshot 1: sees 'pending'

-- (Another session approves the loan: UPDATE loans SET status='approved' WHERE id='L1'; COMMIT)

-- Update based on our check:
UPDATE loans SET disbursed_at = NOW() WHERE id = 'L1' AND status = 'pending';
-- UPDATE takes its OWN snapshot → sees 'approved' → 0 rows updated
-- The WHERE status='pending' correctly rejects the now-approved loan
-- This is the "lost update" problem if not handled with SELECT ... FOR UPDATE

COMMIT;

-- Why Read Committed is the default:
-- Most OLTP workloads tolerate non-repeatable reads in practice
-- Per-statement snapshots mean minimal blocking (only write-write conflicts)
-- Suitable for: simple CRUD, most web application operations, reporting queries
--               where data is allowed to be slightly stale
```

**Q5. What is the lost update problem under Read Committed and how do you prevent it?**
A: A lost update happens when two transactions read the same value, compute a new value based on it, and write back — the second write silently overwrites the first:

```sql
-- Lost update scenario (Read Committed, default):
-- Both sessions deduct from the same account simultaneously.

-- Session A:                               -- Session B:
BEGIN;                                      BEGIN;
SELECT balance FROM accounts WHERE id=1;    SELECT balance FROM accounts WHERE id=1;
-- Returns: 10000                           -- Returns: 10000

-- A computes: 10000 - 3000 = 7000
UPDATE accounts                             -- B computes: 10000 - 4000 = 6000
  SET balance = 7000
  WHERE id = 1;
COMMIT;
                                            UPDATE accounts
                                              SET balance = 6000
                                              WHERE id = 1;
                                            COMMIT;
-- Final balance: 6000  ← A's deduction of 3000 is lost!
-- Should be: 10000 - 3000 - 4000 = 3000

-- ── Fix 1: SELECT ... FOR UPDATE (pessimistic locking) ──────────────────────
-- Acquires a row-level write lock on SELECT — second transaction blocks
-- until first commits or rolls back:

-- Session A:                               -- Session B:
BEGIN;                                      BEGIN;
SELECT balance FROM accounts               SELECT balance FROM accounts
  WHERE id = 1                               WHERE id = 1
  FOR UPDATE;  -- acquires lock             FOR UPDATE;  -- BLOCKS here
-- Returns: 10000

UPDATE accounts SET balance = 7000
  WHERE id = 1;
COMMIT;
-- Lock released                           -- Unblocks, re-reads: balance = 7000
                                           UPDATE accounts SET balance = 7000 - 4000 = 3000
                                             WHERE id = 1;
                                           COMMIT;
-- Final balance: 3000 ✓

-- ── Fix 2: Atomic UPDATE (no separate SELECT needed) ─────────────────────────
-- The database applies the arithmetic — no read-modify-write cycle in application code:

UPDATE accounts
  SET balance = balance - 3000
  WHERE id = 1 AND balance >= 3000;  -- condition prevents overdraft

-- PostgreSQL evaluates balance atomically under a row lock
-- Concurrent updates serialize correctly

-- ── Fix 3: Optimistic concurrency (version column) ───────────────────────────
-- No locks — detect conflicts at write time using a version number:

ALTER TABLE accounts ADD COLUMN version INTEGER DEFAULT 0;

-- Session A reads: { balance: 10000, version: 5 }
-- Session B reads: { balance: 10000, version: 5 }

-- A updates:
UPDATE accounts SET balance = 7000, version = 6
  WHERE id = 1 AND version = 5;  -- condition: version must still be 5
-- 1 row updated → success

-- B tries:
UPDATE accounts SET balance = 6000, version = 6
  WHERE id = 1 AND version = 5;  -- version is now 6 → 0 rows updated!
-- Application detects 0 rows → retry or return conflict error
```

## Section 3: Repeatable Read

**Q6. How does Repeatable Read work in PostgreSQL and how does its snapshot model differ from Read Committed?**
A: Repeatable Read takes a single snapshot at the start of the transaction — not per statement. Every read within the transaction sees the database as it was at that moment, regardless of commits happening concurrently:

```sql
-- Snapshot model: per-transaction (one snapshot for the whole transaction)

-- Session A (Repeatable Read):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM accounts WHERE id = 1;
-- Snapshot taken HERE (start of first statement) → 1000

-- (Session B: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT)

SELECT balance FROM accounts WHERE id = 1;
-- Uses SAME snapshot → still sees 1000 (no non-repeatable read!)

SELECT SUM(balance) FROM accounts;
-- Same snapshot → consistent aggregate (Session B's change invisible)

COMMIT;

-- PostgreSQL's Repeatable Read also prevents phantom reads:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT COUNT(*) FROM loans WHERE amount > 100000;  -- returns 5

-- (Session B: INSERT INTO loans(amount) VALUES(150000); COMMIT)

SELECT COUNT(*) FROM loans WHERE amount > 100000;  -- still returns 5 (no phantom!)
-- The new row is invisible to our snapshot

COMMIT;

-- Note: the SQL standard does NOT require Repeatable Read to prevent phantoms —
-- PostgreSQL's snapshot isolation is stronger than the standard mandates at this level.
-- This is because MVCC snapshot naturally covers both non-repeatable reads and phantoms.

-- When to use Repeatable Read:
-- 1. Reports / analytics that read multiple tables and need a consistent view:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(l.amount) FROM loans l JOIN accounts a ON l.account_id = a.id;
SELECT COUNT(*)       FROM loans WHERE status = 'disbursed';
-- Both queries see exactly the same state of the database → consistent report
COMMIT;

-- 2. Read-modify-write cycles that need stable reads:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM loan_applications WHERE status = 'pending' FOR UPDATE;
-- Process each, knowing no other rows changed status during our transaction
COMMIT;
```

**Q7. What is the serialization error under Repeatable Read and how do you handle it?**
A: When two Repeatable Read (or Serializable) transactions try to update the same row that both have snapshot-read, PostgreSQL detects the conflict and aborts one of them with error code `40001` (`serialization_failure`). The application must retry:

```sql
-- Conflict scenario under Repeatable Read:

-- Session A:                                  -- Session B:
BEGIN TRANSACTION ISOLATION LEVEL              BEGIN TRANSACTION ISOLATION LEVEL
  REPEATABLE READ;                               REPEATABLE READ;

SELECT balance FROM accounts WHERE id=1;
-- Snapshot: balance=1000

                                               SELECT balance FROM accounts WHERE id=1;
                                               -- Snapshot: balance=1000

UPDATE accounts SET balance=700 WHERE id=1;
-- Succeeds (first writer wins)

COMMIT;
                                               UPDATE accounts SET balance=600 WHERE id=1;
                                               -- ERROR: could not serialize access due to
                                               -- concurrent update
                                               -- SQLSTATE: 40001

-- Session B must ROLLBACK and retry the entire transaction:
                                               ROLLBACK;
                                               -- Retry: BEGIN → SELECT → sees 700 → UPDATE

-- Application-level retry loop (Node.js / TypeScript):
async function withRetry<T>(
    fn: () => Promise<T>,
    maxRetries = 3,
): Promise<T> {
    for (let attempt = 0; attempt <= maxRetries; attempt++) {
        try {
            return await fn();
        } catch (err) {
            const isSerializationError =
                err.code === '40001' ||  // serialization_failure
                err.code === '40P01';    // deadlock_detected

            if (isSerializationError && attempt < maxRetries) {
                // Exponential backoff with jitter:
                const delay = Math.min(100 * 2 ** attempt + Math.random() * 50, 2000);
                await new Promise(resolve => setTimeout(resolve, delay));
                continue;
            }
            throw err;
        }
    }
}

// Usage:
await withRetry(async () => {
    await db.transaction(async (trx) => {
        await trx.raw('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ');
        const { rows } = await trx.raw(
            'SELECT balance FROM accounts WHERE id = $1', [accountId]
        );
        const newBalance = rows[0].balance - amount;
        if (newBalance < 0) throw new Error('Insufficient funds');
        await trx.raw(
            'UPDATE accounts SET balance = $1 WHERE id = $2', [newBalance, accountId]
        );
    });
});
```

## Section 4: Serializable

**Q8. How does Serializable isolation work in PostgreSQL and what is SSI (Serializable Snapshot Isolation)?**
A: PostgreSQL's Serializable level uses SSI — Serializable Snapshot Isolation — introduced in PostgreSQL 9.1. Unlike traditional Serializable implementations that use heavy locking, SSI uses optimistic concurrency with conflict detection. It tracks dependencies between transactions and aborts one when it detects a cycle that would make the outcome non-serializable:

```
SSI theory — detecting dangerous patterns:

Traditional Serializable: lock everything that's read → extreme contention
SSI: let transactions proceed optimistically, track read/write dependencies,
     abort if a dependency cycle would produce a non-serializable outcome

Dependency types SSI tracks:
  rw-dependency: T1 reads a version that T2 then writes (T1 "read before" T2 "wrote")
  wr-dependency: T1 writes a version that T2 then reads (T1 "wrote before" T2 "read")
  ww-dependency: T1 and T2 both write the same row

A serialization anomaly requires a cycle of rw-dependencies:
  T1 → (rw) → T2 → (rw) → T1  ← dangerous cycle: abort one

Predicate locking (SIREAD locks):
  PostgreSQL tracks what each transaction has READ (not just written):
  - Row-level: specific row read
  - Page-level: group of rows read (when too many row locks)
  - Relation-level: full table scan
  These are not blocking locks — they're phantom-detection bookmarks.

When SSI detects a dangerous rw-dependency cycle:
  → Picks the "pivot" transaction and aborts it with:
    ERROR: could not serialize access due to read/write dependencies among transactions
    SQLSTATE: 40001

Performance characteristics:
  - Reads take no additional locks (still MVCC snapshots)
  - Small overhead from tracking SIREAD locks
  - Throughput close to Repeatable Read for non-conflicting workloads
  - Much better than traditional 2PL Serializable
  - Overhead grows with conflict rate — high-conflict workloads may need architecture rethink
```

```sql
-- Serializable in practice — write skew prevention:

-- Scenario: doctor on-call system (classic write skew example)
-- Rule: at least one doctor must remain on call

CREATE TABLE oncall (doctor TEXT PRIMARY KEY);
INSERT INTO oncall VALUES ('Alice'), ('Bob');

-- Session A (Serializable):                 -- Session B (Serializable):
BEGIN TRANSACTION ISOLATION LEVEL            BEGIN TRANSACTION ISOLATION LEVEL
  SERIALIZABLE;                                SERIALIZABLE;

SELECT COUNT(*) FROM oncall;                 SELECT COUNT(*) FROM oncall;
-- Returns: 2                                -- Returns: 2

DELETE FROM oncall WHERE doctor='Alice';     DELETE FROM oncall WHERE doctor='Bob';
COMMIT;
                                             COMMIT;
                                             -- ERROR: could not serialize access
                                             -- due to read/write dependencies
                                             -- ROLLBACK and retry

-- Under Read Committed or Repeatable Read:
-- Both would commit → 0 doctors on call (constraint violation, data corruption)

-- Under Serializable:
-- SSI detects the rw-dependency cycle → aborts one transaction
-- Result: exactly one delete succeeds → 1 doctor on call ✓

-- Setting Serializable:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- or:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- must be first statement in transaction
-- or change default for session:
SET default_transaction_isolation = 'serializable';
-- or change default for a specific role:
ALTER ROLE myapp SET default_transaction_isolation = 'serializable';
```

**Q9. What is the difference between Repeatable Read and Serializable in PostgreSQL for write-skew scenarios?**
A: Repeatable Read prevents anomalies caused by reading stale data (non-repeatable reads, phantoms) but does NOT prevent write skew — where two transactions each read a consistent snapshot and make writes that together violate an invariant. Only Serializable catches this:

```sql
-- Write skew comparison — same scenario, different isolation levels:

-- Invariant: total loan exposure for a borrower must not exceed 500000

-- ── Under Repeatable Read (write skew NOT prevented) ─────────────────────────
-- Session A:                               -- Session B:
BEGIN TRANSACTION ISOLATION LEVEL           BEGIN TRANSACTION ISOLATION LEVEL
  REPEATABLE READ;                            REPEATABLE READ;

SELECT SUM(amount) FROM loans               SELECT SUM(amount) FROM loans
  WHERE borrower_id = 'B1';                   WHERE borrower_id = 'B1';
-- Returns: 400000                          -- Returns: 400000

-- A checks: 400000 + 150000 = 550000 > 500000? No: 400000 + 50000 = 450000 ≤ 500000
INSERT INTO loans(borrower_id, amount)
  VALUES('B1', 50000);

COMMIT;
                                            -- B checks: 400000 + 100000 = 500000 ≤ 500000
                                            INSERT INTO loans(borrower_id, amount)
                                              VALUES('B1', 100000);
                                            COMMIT;
-- Both commit!
-- Total: 400000 + 50000 + 100000 = 550000 ← exceeds limit!
-- Each transaction read a consistent snapshot but together they violated the invariant.

-- ── Under Serializable (write skew IS prevented) ─────────────────────────────
-- Session A:                               -- Session B:
BEGIN TRANSACTION ISOLATION LEVEL           BEGIN TRANSACTION ISOLATION LEVEL
  SERIALIZABLE;                               SERIALIZABLE;

SELECT SUM(amount) FROM loans               SELECT SUM(amount) FROM loans
  WHERE borrower_id = 'B1';                   WHERE borrower_id = 'B1';
-- Returns: 400000                          -- Returns: 400000

INSERT INTO loans(borrower_id, amount)
  VALUES('B1', 50000);
COMMIT;
                                            INSERT INTO loans(borrower_id, amount)
                                              VALUES('B1', 100000);
                                            -- ERROR: could not serialize access
                                            -- due to read/write dependencies

-- SSI detected: B read the SUM that A then changed → rw-dependency cycle → abort B
-- Application retries B → reads SUM=450000 → 450000+100000=550000 > 500000 → rejects ✓

-- When Repeatable Read is sufficient vs when you need Serializable:
--
-- Repeatable Read sufficient:
--   - Read-only transactions (reports, analytics)
--   - Writes that don't depend on aggregates or sets read in the same transaction
--   - Lost update prevention via SELECT FOR UPDATE (explicit locking)
--
-- Serializable required:
--   - Transactions that read an aggregate/set AND write based on that read
--   - Any invariant that spans multiple rows (exposure limits, capacity checks)
--   - When you can't use explicit locks (e.g. the predicate is complex)
--   - Financial systems where correctness trumps throughput
```

## Section 5: Locking Interactions

**Q10. How do `SELECT FOR UPDATE`, `SELECT FOR SHARE`, and `NOWAIT` / `SKIP LOCKED` interact with isolation levels?**
A: Explicit locking (`FOR UPDATE`, `FOR SHARE`) adds row-level write or read locks on top of MVCC. They work within any isolation level but their semantics interact with the snapshot in important ways:

```sql
-- SELECT FOR UPDATE: acquires exclusive row lock
--   - Blocks other FOR UPDATE and FOR SHARE on same rows
--   - Does NOT block plain SELECT (MVCC handles that)
--   - Lock held until transaction commits or rolls back
--   - Under Read Committed: re-reads the row after acquiring lock (sees latest committed data)
--   - Under Repeatable Read: re-reads the row; if changed since snapshot → serialization error

-- SELECT FOR SHARE: acquires shared row lock
--   - Blocks FOR UPDATE but not other FOR SHARE or plain SELECT
--   - Use when you want to prevent deletion/update but allow other readers to share the lock

-- Basic pattern — prevent concurrent updates:
BEGIN;
SELECT * FROM loan_applications
  WHERE id = 'LA1'
  FOR UPDATE;
-- Row is now locked — concurrent FOR UPDATE on same row will block
UPDATE loan_applications SET status = 'approved' WHERE id = 'LA1';
COMMIT;

-- NOWAIT — fail immediately instead of blocking:
BEGIN;
SELECT * FROM loan_applications
  WHERE id = 'LA1'
  FOR UPDATE NOWAIT;
-- If lock unavailable: ERROR: could not obtain lock on row in relation "loan_applications"
-- Application can catch this and tell the user "record is in use"
-- Better UX than blocking indefinitely

-- SKIP LOCKED — skip rows that are locked (job queue pattern):
-- Perfect for work queues: multiple workers compete for pending jobs
-- without stepping on each other

CREATE TABLE job_queue (
    id SERIAL PRIMARY KEY,
    payload JSONB,
    status TEXT DEFAULT 'pending'
);

-- Worker process — atomically claim a job:
BEGIN;
SELECT id, payload
  FROM job_queue
  WHERE status = 'pending'
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED;
-- Skips any rows already locked by another worker
-- Returns the next available unlocked row (or 0 rows if all claimed)

UPDATE job_queue SET status = 'processing' WHERE id = :claimed_id;
COMMIT;
-- Each worker gets a different job — no duplicate processing

-- FOR UPDATE with table join — lock only specific table:
SELECT l.*, a.balance
  FROM loans l
  JOIN accounts a ON l.account_id = a.id
  FOR UPDATE OF a;    -- lock only accounts rows, not loans rows
  -- FOR UPDATE OF loans, a;  -- lock both

-- Isolation level interaction with FOR UPDATE:
-- Read Committed + FOR UPDATE:
--   PostgreSQL re-reads the row AFTER acquiring the lock
--   If the row changed since the SELECT, the new values are used
--   → you see the latest committed state of the locked row

-- Repeatable Read + FOR UPDATE:
--   If the row was modified by another committed transaction since the snapshot:
--   ERROR: could not serialize access due to concurrent update (40001)
--   → must retry the whole transaction
```

**Q11. What is a deadlock in PostgreSQL and how does it differ from a lock wait timeout?**
A: A deadlock occurs when two transactions each hold a lock the other needs — neither can proceed. PostgreSQL detects deadlocks automatically and aborts one transaction. A lock wait is simply blocking until the lock becomes available:

```sql
-- Deadlock example:
-- Session A:                               -- Session B:
BEGIN;                                      BEGIN;
UPDATE accounts SET balance=700             UPDATE accounts SET balance=600
  WHERE id = 1;  -- locks row 1              WHERE id = 2;  -- locks row 2

UPDATE accounts SET balance=400             UPDATE accounts SET balance=300
  WHERE id = 2;  -- BLOCKS (B has lock)      WHERE id = 1;  -- BLOCKS (A has lock)

-- PostgreSQL deadlock detector (runs every deadlock_timeout ms, default 1s):
-- Detects cycle: A waits for B, B waits for A
-- Chooses one to abort (typically the transaction that committed fewer tuples):
-- ERROR:  deadlock detected
-- DETAIL: Process 12345 waits for ShareLock on transaction 67890; blocked by process 54321.
--         Process 54321 waits for ShareLock on transaction 12345; blocked by process 12345.
-- HINT:   See server log for query details.
-- SQLSTATE: 40P01

-- Prevention: always acquire locks in a consistent order:
-- Always update lower id first → no circular dependency:
BEGIN;
UPDATE accounts SET balance=700 WHERE id = 1;  -- consistent: low id first
UPDATE accounts SET balance=400 WHERE id = 2;  -- consistent: then high id
COMMIT;

-- Lock wait vs deadlock:
--   Lock wait: T1 holds lock, T2 waits → T2 eventually gets it when T1 commits
--   Deadlock: T1 waits for T2, T2 waits for T1 → neither can proceed → abort one

-- Relevant PostgreSQL settings:
-- deadlock_timeout (default 1s):
--   How long to wait before running deadlock detection algorithm.
--   NOT the time before aborting — just when to check.
--   Lower values detect deadlocks faster but increase overhead.

-- lock_timeout (default 0 = wait forever):
--   Maximum time to wait for a lock before erroring.
--   SET lock_timeout = '5s';
--   ERROR: canceling statement due to lock timeout (SQLSTATE: 55P03)

-- statement_timeout (default 0 = no limit):
--   Maximum time for any single statement.
--   SET statement_timeout = '30s';
--   Aborts the statement (not the transaction) if exceeded.

-- idle_in_transaction_session_timeout (default 0 = no limit):
--   Aborts sessions that hold open transactions but haven't run a query.
--   Critical for preventing long-lived idle transactions from blocking VACUUM:
--   SET idle_in_transaction_session_timeout = '60s';
```

## Section 6: Practical Configuration

**Q12. How do you set the isolation level in PostgreSQL at different scopes?**

```sql
-- ── Per-transaction (most common): ───────────────────────────────────────────
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Must be the first statement after BEGIN, before any reads/writes
SELECT ...;
COMMIT;

-- Or equivalently (shorthand):
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT ...;
COMMIT;

-- Read-only hint (optimizer can skip certain locks for read-only transactions):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;

-- Deferrable (only meaningful for Serializable READ ONLY):
-- Waits at start until a snapshot can be taken that is guaranteed serializable
-- → no abort risk during the transaction; good for long-running reports
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;

-- ── Per-session: ─────────────────────────────────────────────────────────────
SET SESSION default_transaction_isolation = 'repeatable read';
-- Affects all subsequent transactions in this connection
-- Resets when connection is closed (if using connection pool, set per-query)

-- ── Per-role (persists across connections): ───────────────────────────────────
ALTER ROLE reporting_user SET default_transaction_isolation = 'repeatable read';
ALTER ROLE app_user SET default_transaction_isolation = 'read committed';

-- ── Per-database: ─────────────────────────────────────────────────────────────
ALTER DATABASE mydb SET default_transaction_isolation = 'serializable';

-- ── In application code (Node.js with pg / Knex / TypeORM): ──────────────────

// Raw pg:
await client.query('BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ');
await client.query('SELECT ...');
await client.query('COMMIT');

// Knex:
await knex.transaction(async (trx) => {
    await trx.raw('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ');
    await trx('accounts').where('id', accountId).select('balance');
});

// TypeORM:
await dataSource.transaction(
    'REPEATABLE READ',  // TypeORM accepts isolation level as first arg
    async (manager) => {
        return manager.findOne(Account, { where: { id: accountId } });
    }
);

// Prisma (as of v5):
await prisma.$transaction(
    async (tx) => {
        return tx.account.findUnique({ where: { id: accountId } });
    },
    { isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead }
);
```

**Q13. What are the performance implications of each isolation level and how do you monitor contention?**

```sql
-- Performance characteristics:

-- Read Committed (default):
--   Lock held:    row write lock only (released after each statement? No — after COMMIT)
--   Blocking:     writer blocks other writers on same row; readers never block
--   Throughput:   highest
--   Retry rate:   very low (only on UPDATE of row updated concurrently mid-transaction)
--   Use for:      most OLTP workloads

-- Repeatable Read:
--   Lock held:    same as Read Committed for writes; snapshot held for reads
--   Blocking:     same write-write conflicts; serialization errors instead of blocking
--   Throughput:   slightly lower due to conflict detection overhead
--   Retry rate:   low-moderate (concurrent writes to same rows cause 40001)
--   Use for:      financial calculations, reports needing consistent view

-- Serializable (SSI):
--   Lock held:    SIREAD locks tracked in addition to write locks
--   Blocking:     SSI aborts instead of blocking (optimistic)
--   Throughput:   10-30% lower than Read Committed (SIREAD lock tracking overhead)
--   Retry rate:   depends on conflict rate — can be high under heavy write contention
--   Use for:      correctness-critical workflows, complex invariants across rows

-- Monitoring lock contention:

-- Active locks and waiters:
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    query,
    now() - query_start AS query_duration
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- Lock dependency graph (who is blocking whom):
SELECT
    blocked.pid          AS blocked_pid,
    blocked.query        AS blocked_query,
    blocking.pid         AS blocking_pid,
    blocking.query       AS blocking_query
FROM pg_stat_activity AS blocked
JOIN pg_stat_activity AS blocking
    ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- Long-running transactions (hold back VACUUM horizon):
SELECT
    pid,
    now() - pg_stat_activity.xact_start AS transaction_duration,
    query,
    state
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND now() - xact_start > interval '5 minutes'
ORDER BY transaction_duration DESC;

-- Serialization failure rate (track in application metrics):
-- Catch SQLSTATE 40001 and 40P01, increment counter, alert if retry rate > 5%
```

## Section 7: Scenario-Based Questions

**Q14. "Your loan disbursement service occasionally double-disburses. Two concurrent API calls for the same loan both pass the 'not yet disbursed' check and both write a disbursement record. How do you fix it with the right isolation level and locking strategy?"**

```sql
-- Root cause: classic check-then-act race condition under Read Committed
-- Both transactions see disbursed_at IS NULL, both proceed

-- Bad (racy) pattern:
BEGIN;
SELECT disbursed_at FROM loans WHERE id = 'L1';
-- Both see: disbursed_at = NULL

-- Application code: if disbursed_at is null, proceed
INSERT INTO disbursements (loan_id, amount, disbursed_at)
  VALUES ('L1', 50000, NOW());
UPDATE loans SET disbursed_at = NOW() WHERE id = 'L1';
COMMIT;
-- Both transactions complete → two disbursements ← BUG

-- ── Fix 1: SELECT FOR UPDATE (recommended for this pattern) ──────────────────
BEGIN;
SELECT id, disbursed_at FROM loans
  WHERE id = 'L1'
  FOR UPDATE;
-- Second caller BLOCKS here until first commits

-- After first caller commits, second caller unblocks and re-reads:
-- disbursed_at is now set → second caller exits without disbursing
IF disbursed_at IS NOT NULL THEN
    ROLLBACK;
    RETURN 'already disbursed';
END IF;

INSERT INTO disbursements (loan_id, amount, disbursed_at)
  VALUES ('L1', 50000, NOW());
UPDATE loans SET disbursed_at = NOW() WHERE id = 'L1';
COMMIT;

-- ── Fix 2: Unique constraint (database-level idempotency) ────────────────────
-- Add a unique constraint that physically prevents double disbursement:
ALTER TABLE disbursements ADD CONSTRAINT uq_loan_disbursement UNIQUE (loan_id);
-- Second INSERT fails with unique violation (SQLSTATE 23505)
-- Application catches this and treats it as idempotent success

-- ── Fix 3: Conditional UPDATE (atomic check-and-set) ─────────────────────────
-- Attempt to atomically claim the loan for disbursement:
WITH claim AS (
    UPDATE loans
       SET disbursed_at = NOW()
     WHERE id = 'L1'
       AND disbursed_at IS NULL   -- only updates if not yet disbursed
    RETURNING id, amount
)
INSERT INTO disbursements (loan_id, amount, disbursed_at)
  SELECT id, amount, NOW() FROM claim;

-- If 0 rows returned from claim → loan already disbursed → INSERT inserts nothing
-- Exactly one concurrent UPDATE can win the race (write-write serialization)
-- No explicit transaction isolation level change needed — works under Read Committed

-- Application code (Node.js):
const result = await db.query(`
    WITH claim AS (
        UPDATE loans
           SET disbursed_at = NOW()
         WHERE id = $1 AND disbursed_at IS NULL
        RETURNING id, amount
    )
    INSERT INTO disbursements (loan_id, amount, disbursed_at)
      SELECT id, amount, NOW() FROM claim
    RETURNING loan_id
`, [loanId]);

if (result.rowCount === 0) {
    throw new ConflictException('Loan already disbursed');
}
```

**Q15. "A nightly report query runs at midnight and takes 20 minutes. During that time, application writes cause the report to show inconsistent numbers — some tables show pre-midnight state, some post-midnight. How do you fix this?"**

```sql
-- Root cause: report runs under Read Committed (default)
-- Each SELECT in the report takes a new snapshot
-- Writes between statements make different tables visible at different points in time

-- Symptom:
-- SELECT SUM(amount) FROM loans WHERE created_at < midnight;     → snapshot at 00:01
-- SELECT SUM(balance) FROM accounts WHERE updated_at < midnight; → snapshot at 00:15
-- The two numbers are from different moments — cross-table inconsistency

-- ── Fix 1: Repeatable Read for the report connection ─────────────────────────
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
-- Single snapshot taken now — ALL queries in this transaction see the same state
-- Application writes during the 20 minutes are invisible to this transaction

SELECT SUM(amount) FROM loans;         -- snapshot at 00:00:00
-- (app writes 100 new loans during report)
SELECT SUM(balance) FROM accounts;     -- still snapshot at 00:00:00 ← consistent!

COMMIT;

-- ── Fix 2: SERIALIZABLE READ ONLY DEFERRABLE (for zero-abort risk) ───────────
-- DEFERRABLE waits at BEGIN until it can guarantee a safe serializable snapshot
-- Then runs with no risk of serialization errors during the transaction
-- Ideal for long-running read-only reports:

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
-- PostgreSQL waits here until a safe snapshot is available (usually milliseconds)
-- Then the 20-minute report runs with zero chance of 40001 abort

SELECT SUM(amount) FROM loans;
SELECT SUM(balance) FROM accounts;
-- Perfect consistency, no retries needed

COMMIT;

-- ── Fix 3: Materialized snapshot (export to a reporting table) ────────────────
-- Decouples report from live tables entirely — best for very heavy reports

BEGIN;
CREATE TEMP TABLE report_snapshot AS
    SELECT l.id, l.amount, a.balance
    FROM loans l JOIN accounts a ON l.account_id = a.id;
COMMIT;

-- Run all report queries against report_snapshot
-- Live tables can be modified freely during the report
DROP TABLE report_snapshot;

-- ── Fix 4: Logical replication to a read replica ─────────────────────────────
-- Run reports against a replica with slight replication lag
-- Replica has its own MVCC state — reports are isolated from primary writes
-- Latency: typically < 1s on healthy replication
-- Note: replica still uses Read Committed by default — set Repeatable Read on replica too
```

**Q16. "You're building a seat reservation system for loan officer appointments. Two users must not be able to book the same slot. What isolation level and locking approach do you use?"**

```sql
-- Requirement: exactly one booking per slot — idempotent, no double-booking

CREATE TABLE appointment_slots (
    id          SERIAL PRIMARY KEY,
    slot_time   TIMESTAMPTZ NOT NULL,
    officer_id  UUID NOT NULL,
    booked_by   UUID,                    -- NULL if available
    booked_at   TIMESTAMPTZ,
    UNIQUE (slot_time, officer_id)       -- one slot per officer per time
);

-- ── Approach 1: SELECT FOR UPDATE SKIP LOCKED (optimistic queue) ─────────────
-- Best for high-concurrency slot grabbing:

BEGIN;
SELECT id FROM appointment_slots
  WHERE slot_time = $1
    AND officer_id = $2
    AND booked_by IS NULL
  FOR UPDATE SKIP LOCKED
  LIMIT 1;

-- If 0 rows: slot is taken → return "slot unavailable" immediately
-- If 1 row:  we have the lock → proceed with booking

UPDATE appointment_slots
   SET booked_by = $3,
       booked_at = NOW()
 WHERE id = :slot_id;

COMMIT;

-- SKIP LOCKED means concurrent requests for the same slot immediately see
-- "0 rows" if the slot is locked → no waiting, instant "unavailable" response
-- Much better UX than blocking until the first booker commits

-- ── Approach 2: Conditional UPDATE (atomic, no two-phase select) ─────────────
-- Simpler — no explicit locking, leverages write-write serialization:

WITH booking AS (
    UPDATE appointment_slots
       SET booked_by = $3,
           booked_at = NOW()
     WHERE slot_time = $1
       AND officer_id = $2
       AND booked_by IS NULL       -- only if still available
    RETURNING id
)
SELECT id FROM booking;

-- If 0 rows: slot was already booked (race condition handled by DB)
-- If 1 row: booked successfully
-- Concurrent UPDATEs to the same row serialize automatically (write-write lock)

-- ── Approach 3: INSERT with UNIQUE constraint (if modelling differently) ───────
-- Model bookings as a separate table — UNIQUE constraint prevents duplicates:

CREATE TABLE bookings (
    slot_id     INTEGER REFERENCES appointment_slots(id),
    user_id     UUID NOT NULL,
    booked_at   TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (slot_id)     -- only one booking per slot
);

INSERT INTO bookings (slot_id, user_id)
  VALUES ($1, $2)
  ON CONFLICT (slot_id) DO NOTHING
  RETURNING slot_id;

-- If 0 rows returned: slot already booked (another INSERT won the race)
-- If 1 row returned: booked successfully
-- The UNIQUE constraint enforces the invariant at the database level
-- No isolation level change needed — works under Read Committed
```

**Q17. "A financial audit requires that account balance reports be perfectly consistent with transaction logs for the same time period. How do you implement this in PostgreSQL?"**

```sql
-- Requirement: balance report and transaction log must reflect exactly the same
-- moment in time — no writes between the two queries can affect either

-- ── Solution: pg_export_snapshot() + SET TRANSACTION SNAPSHOT ────────────────
-- Export a snapshot from one transaction and import it in another
-- Both transactions see exactly the same database state

-- Transaction 1 (snapshot exporter):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT pg_export_snapshot();
-- Returns: '00000003-0000001B-1'  ← snapshot identifier

-- Share this identifier with Transaction 2 (via application coordination)
-- Transaction 1 must stay open while Transaction 2 imports the snapshot

-- Transaction 2 (snapshot importer):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION SNAPSHOT '00000003-0000001B-1';
-- Now T2 sees exactly the same state as T1's snapshot

SELECT SUM(balance) FROM accounts;         -- consistent with T1's view
SELECT SUM(amount) FROM transactions
  WHERE created_at BETWEEN $start AND $end; -- same snapshot

COMMIT;

-- Transaction 1 can commit after T2 has imported the snapshot:
COMMIT;

-- ── Practical implementation (two parallel report queries): ──────────────────

// Node.js application:
async function consistentAuditReport(startDate: Date, endDate: Date) {
    const snapshotClient = await pool.connect();
    const reportClient = await pool.connect();

    try {
        // Export snapshot:
        await snapshotClient.query(
            'BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ'
        );
        const { rows } = await snapshotClient.query('SELECT pg_export_snapshot()');
        const snapshotId = rows[0].pg_export_snapshot;

        // Import snapshot in report client:
        await reportClient.query(
            'BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ'
        );
        await reportClient.query(
            `SET TRANSACTION SNAPSHOT '${snapshotId}'`
        );

        // Both queries now see the identical state:
        const [balances, transactions] = await Promise.all([
            reportClient.query('SELECT id, balance FROM accounts'),
            reportClient.query(
                'SELECT * FROM transactions WHERE created_at BETWEEN $1 AND $2',
                [startDate, endDate]
            ),
        ]);

        await reportClient.query('COMMIT');
        await snapshotClient.query('COMMIT');  // release snapshot

        return { balances: balances.rows, transactions: transactions.rows };
    } finally {
        snapshotClient.release();
        reportClient.release();
    }
}
```

**Q18. "You're seeing high deadlock rates (40P01 errors) in your loan processing service. How do you diagnose the cause and fix it?"**

```sql
-- Step 1: Log deadlocks to identify the queries involved:
-- In postgresql.conf:
-- log_min_messages = ERROR          (log at least errors)
-- deadlock_timeout = 500ms          (detect faster during diagnosis)
-- log_lock_waits = on               (log waits exceeding deadlock_timeout)

-- Step 2: Query pg_stat_activity during the incident:
SELECT pid, query, state, wait_event, now() - xact_start AS txn_age
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY txn_age DESC;

-- Step 3: Identify lock ordering issue from logs
-- Typical deadlock log excerpt:
-- DETAIL:  Process 1234 waits for ShareLock on transaction 5678;
--          blocked by process 9012.
--          Process 9012 waits for ShareLock on transaction 1234;
--          blocked by process 1234.
-- HINT:    See server log for query details.
-- CONTEXT: while updating tuple in relation "loans"
--          while updating tuple in relation "accounts"

-- This tells us: one transaction locks loans then accounts
--               another locks accounts then loans → deadlock

-- Step 4: Fix — enforce consistent lock acquisition order in application code:

// BEFORE (deadlock-prone):
async function processLoanApplication(loanId: string, accountId: string) {
    // Worker A processes loan L1 → account A1
    // Worker B processes loan L2 → account A1 → loan L1  ← circular
    await db.transaction(async (trx) => {
        await trx('loans').where({ id: loanId }).forUpdate();
        await trx('accounts').where({ id: accountId }).forUpdate();
        // ... process
    });
}

// AFTER (deadlock-safe — always lock in consistent order):
async function processLoanApplication(loanId: string, accountId: string) {
    // Sort resource IDs before locking — always acquire in ascending UUID order
    const resources = [
        { table: 'loans', id: loanId },
        { table: 'accounts', id: accountId },
    ].sort((a, b) => a.id.localeCompare(b.id));

    await db.transaction(async (trx) => {
        for (const resource of resources) {
            await trx(resource.table)
                .where({ id: resource.id })
                .forUpdate();
        }
        // All code paths acquire locks in the same order → no circular dependency
    });
}

-- Step 5: Reduce lock scope with SKIP LOCKED for queue processing:
-- If multiple workers process from the same queue table,
-- SKIP LOCKED eliminates contention entirely (each worker gets different rows)

-- Step 6: Shorten transactions — the longer a transaction holds locks,
-- the higher the chance of a deadlock:
-- Move non-DB work (HTTP calls, file IO) OUTSIDE the transaction
-- Do validation before BEGIN, not inside
```

## Quick Reference Table

| Isolation Level | Snapshot Model | Dirty Read | Non-Repeatable Read | Phantom Read | Write Skew |
|---|---|---|---|---|---|
| Read Uncommitted | Per statement (= Read Committed in PG) | Possible* | Possible | Possible | Possible |
| Read Committed | Per statement | Prevented | Possible | Possible | Possible |
| Repeatable Read | Per transaction | Prevented | Prevented | Prevented† | Possible |
| Serializable | Per transaction + SSI | Prevented | Prevented | Prevented | Prevented |

*PostgreSQL silently upgrades Read Uncommitted to Read Committed — dirty reads never occur.
†PostgreSQL's MVCC snapshot prevents phantoms at Repeatable Read (stronger than SQL standard requires).

| Tool | Purpose | When to use |
|---|---|---|
| `FOR UPDATE` | Exclusive row lock | Prevent lost update, check-then-act patterns |
| `FOR SHARE` | Shared row lock | Prevent deletion while others hold shared interest |
| `NOWAIT` | Fail immediately if lock unavailable | Prefer error over waiting (UI responsiveness) |
| `SKIP LOCKED` | Skip locked rows | Worker queues — each worker claims different rows |
| `REPEATABLE READ` | Consistent transaction snapshot | Reports spanning multiple queries, consistent reads |
| `SERIALIZABLE` | Full SSI, write-skew prevention | Complex invariants across rows, financial correctness |
| `DEFERRABLE` | Delay snapshot until guaranteed safe | Long-running read-only reports, zero abort risk |
| `pg_export_snapshot()` | Share snapshot between connections | Parallel queries that must see identical state |
| Retry on `40001`/`40P01` | Handle serialization and deadlock errors | Any code using RR or Serializable |

---

**Tip for interviews:** Five things separate strong candidates on PostgreSQL isolation levels: (1) knowing that **PostgreSQL's Repeatable Read prevents phantom reads** via MVCC snapshot isolation (Q3, Q6) — the SQL standard only requires phantom prevention at Serializable, but PostgreSQL's snapshot naturally covers it, so you can say "PostgreSQL's RR is stronger than the standard at that level"; (2) understanding **write skew precisely** (Q9) — dirty reads and non-repeatable reads are well-known, but write skew (two transactions each read a consistent snapshot and together violate an invariant) is the subtler anomaly that only Serializable prevents, and being able to give a concrete example (on-call doctors, exposure limits) demonstrates real depth; (3) knowing **SSI vs traditional 2PL Serializable** (Q8) — PostgreSQL uses optimistic concurrency with SIREAD lock tracking rather than blocking read locks, which is why Serializable in PostgreSQL has much better throughput than in databases using strict 2PL; (4) being precise about **FOR UPDATE's interaction with isolation levels** (Q10) — under Read Committed, FOR UPDATE re-reads the locked row after acquiring the lock (you see the latest committed state, not your snapshot); under Repeatable Read, if the row changed since your snapshot, you get a 40001 serialization error rather than the updated data; and (5) knowing the **40001 retry pattern is mandatory** (Q7) — Repeatable Read and Serializable are not drop-in replacements for Read Committed; any code using them must implement retry logic with exponential backoff because serialization failures are a normal, expected outcome of optimistic concurrency control, not exceptional errors.
