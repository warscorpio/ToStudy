# Index-Only Scans vs Heap Scans — Interview Q&A (5 YOE Level)

---

## Section 1: Physical Storage Fundamentals

**Q1. How does PostgreSQL physically store data — what are the heap and index structures?**

A: Every table in PostgreSQL is stored as a **heap** — a collection of 8 KB pages in no particular order. Indexes are separate files with their own page structure that point back into the heap. Understanding this physical layout is the foundation for every scan-type decision the query planner makes:

```
Physical layout on disk:

  TABLE: orders (the heap)
  ┌────────────────────────────────────────────────────────────┐
  │ Page 0 (8 KB)                                              │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │ Page header │ ItemId[0] │ ItemId[1] │ ItemId[2] │... │  │
  │  ├──────────────────────────────────────────────────────┤  │
  │  │ Tuple 2 (row)    │ Tuple 1 (row)    │ Tuple 0 (row) │  │
  │  └──────────────────────────────────────────────────────┘  │
  │  Each tuple: xmin | xmax | cols...                         │
  ├────────────────────────────────────────────────────────────┤
  │ Page 1 (8 KB)   ...                                        │
  ├────────────────────────────────────────────────────────────┤
  │ Page N (8 KB)   ...                                        │
  └────────────────────────────────────────────────────────────┘

  INDEX: idx_orders_user_id  (B-tree, separate file)
  ┌────────────────────────────────────────────────────────────┐
  │ Root page                                                  │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │ key: 101 → page 3  │ key: 250 → page 7  │ ...       │  │
  │  └──────────────────────────────────────────────────────┘  │
  │        │                        │                          │
  │  Leaf pages (sorted by user_id):                           │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │ (user_id=42, ctid=(page=0, offset=1))                │  │ ← ctid = heap location
  │  │ (user_id=42, ctid=(page=4, offset=7))                │  │
  │  │ (user_id=43, ctid=(page=0, offset=2))                │  │
  │  └──────────────────────────────────────────────────────┘  │
  └────────────────────────────────────────────────────────────┘

Key vocabulary:
  ctid    — physical location of a heap tuple: (page_number, offset_within_page)
  TID     — Tuple Identifier — same as ctid
  heap    — the table file itself (unsorted, append-mostly)
  heap fetch — going from an index entry (ctid) to the actual heap page to read the row
```

```sql
-- You can see ctids directly:
SELECT ctid, id, user_id, status
FROM   orders
LIMIT  5;

--  ctid   │  id  │ user_id │ status
-- ────────┼──────┼─────────┼─────────
-- (0,1)   │    1 │      42 │ pending
-- (0,2)   │    2 │      43 │ shipped
-- (1,1)   │    3 │      42 │ pending   ← same user, different heap page

-- The index stores (user_id=42, ctid=(0,1)) and (user_id=42, ctid=(1,1)).
-- To answer: SELECT * FROM orders WHERE user_id = 42
-- the planner must visit heap page 0 and heap page 1 — two heap fetches.

-- Heap pages are 8 KB each:
SHOW block_size;  -- → 8192

-- Total heap pages for a table:
SELECT relpages, reltuples
FROM   pg_class
WHERE  relname = 'orders';
```

**Q2. What is a sequential scan (seq scan), and when does the planner choose it over an index?**

A: A sequential scan reads every page of the heap from beginning to end, visiting every row. It requires no index and has no per-row overhead for pointer lookups — but it reads every page regardless of whether the rows match the filter:

```sql
-- Sequential scan anatomy:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE status = 'shipped';

-- Seq Scan on orders  (cost=0.00..18432.00 rows=62000 width=87)
--                     (actual time=0.042..312.451 rows=61843 loops=1)
--   Filter: ((status)::text = 'shipped')
--   Rows Removed by Filter: 438157
--   Buffers: shared hit=4233 read=3982
-- Planning Time: 0.142 ms
-- Execution Time: 341.287 ms

-- Breaking down the cost estimate:
-- cost=0.00         → startup cost (first row): nothing to set up for seq scan
-- cost=18432.00     → total cost (all rows)
--   = pages * seq_page_cost + rows * cpu_tuple_cost + rows * cpu_operator_cost
--   = 8215 * 1.0   + 500000 * 0.01 + 500000 * 0.0025
-- Buffers: shared hit=4233  → pages found in shared_buffers (RAM cache)
--          read=3982        → pages read from disk (slower)

-- ── When the planner CHOOSES seq scan over index scan ────────────────────────
--
-- 1. Low selectivity: the filter matches most rows
--    If status = 'shipped' matches 60% of rows, touching the index
--    then fetching 60% of heap pages costs MORE than reading heap pages once.
--
-- 2. Small table: fits in a few pages
--    A 3-page table is faster to scan fully than to navigate a B-tree.
--
-- 3. No usable index exists for the filter
--
-- 4. Random I/O cost vs sequential I/O cost
--    seq_page_cost = 1.0  (default)
--    random_page_cost = 4.0  (default — random reads cost 4x more)
--    Index scan = many random heap fetches → expensive at scale.
--    Seq scan = one sequential pass → predictable, cache-friendly.
--
-- The break-even point is roughly:
--   index scan wins when selectivity < seq_page_cost / random_page_cost
--   i.e., when < ~25% of rows match (with default cost settings).
--   On SSDs: random_page_cost ≈ 1.1 → break-even is ~90%, index nearly always wins.

-- ── Forcing a seq scan for testing (never in production) ─────────────────────
SET enable_seqscan = OFF;
EXPLAIN SELECT * FROM orders WHERE status = 'shipped';
-- Forces the planner to use an index even when it wouldn't choose to.
-- Useful for benchmarking what the index path would cost.
SET enable_seqscan = ON; -- Always reset
```

## Section 2: Index Scans and Heap Fetches

**Q3. How does a standard index scan work — what is a heap fetch and why does it have a cost?**

A: A standard index scan uses the B-tree to find matching `ctid` values, then fetches each matching row from the heap. The index traversal is cheap; the heap fetch is where the cost accumulates:

```sql
-- Standard index scan:
CREATE INDEX idx_orders_user_id ON orders(user_id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id, status, total
FROM   orders
WHERE  user_id = 42;

-- Index Scan using idx_orders_user_id on orders
--   (cost=0.56..892.34 rows=847 width=38)
--   (actual time=0.043..8.341 rows=843 loops=1)
--   Index Cond: (user_id = 42)
--   Buffers: shared hit=12 read=831
-- Execution Time: 8.721 ms

-- What happens step by step:
-- 1. Traverse B-tree from root to leaf for user_id = 42
--    → finds leaf entries: [(42, ctid=(0,1)), (42, ctid=(4,7)), (42, ctid=(9,3)), ...]
-- 2. For EACH ctid, fetch the heap page to read the full row:
--    → Visit heap page 0 (offset 1)  → read id, user_id, status, total
--    → Visit heap page 4 (offset 7)  → read id, user_id, status, total
--    → Visit heap page 9 (offset 3)  → read id, user_id, status, total
--    ...843 heap fetches total

-- Why heap fetches are expensive:
-- • Each ctid may point to a DIFFERENT heap page (random access pattern)
-- • 843 rows spread across many pages → many random disk reads
-- • random_page_cost = 4.0 by default → 4x penalty vs sequential reads
-- • On spinning disks: random reads are dramatically slower (seek time)
-- • On SSDs: still slower than sequential, but gap is smaller

-- ── Bitmap Index Scan: batching heap fetches ──────────────────────────────────
-- When an index scan would require too many random heap fetches, the planner
-- uses a Bitmap Index Scan instead — it scans the entire index first,
-- builds a bitmap of matching heap page numbers, then reads those pages
-- sequentially (in page order, not ctid order).

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id BETWEEN 100 AND 200;

-- Bitmap Heap Scan on orders
--   (cost=245.33..8901.22 rows=9823 width=87)
--   (actual time=3.421..89.234 rows=9812 loops=1)
--   Recheck Cond: ((user_id >= 100) AND (user_id <= 200))
--   Heap Blocks: exact=4821
--   Buffers: shared hit=1023 read=4044
--   →  Bitmap Index Scan on idx_orders_user_id
--        (cost=0.00..242.88 rows=9823 width=0)
--        (actual time=2.891..2.891 rows=9812 loops=1)
--        Index Cond: ((user_id >= 100) AND (user_id <= 200))

-- Bitmap scan phases:
-- Phase 1 (Bitmap Index Scan): scan the index → build an in-memory bitmap
--   bit per heap page: 1 = "has at least one matching row"
-- Phase 2 (Bitmap Heap Scan): visit marked pages IN ORDER (sequential-ish)
--   → "Recheck Cond" because bitmap is lossy at high page counts:
--     when too many pages match, the bitmap tracks pages not individual rows,
--     so each row on the page must be re-evaluated against the filter.

-- Summary of scan types and when they appear:
-- Seq Scan:          low selectivity, no index, small table
-- Index Scan:        high selectivity (few rows), low page count in result
-- Bitmap Index Scan: medium selectivity, many rows but want sorted page access
-- Index Only Scan:   all needed columns are in the index (next section)
```

## Section 3: Index-Only Scans

**Q4. What is an index-only scan and what exact conditions must be met for the planner to use one?**

A: An index-only scan answers the query entirely from the index pages — it never touches the heap. This is possible only when (a) every column the query needs is stored in the index, and (b) the visibility map confirms the rows are visible without checking heap tuple headers:

```sql
-- ── What makes an index-only scan possible ────────────────────────────────────

-- Condition 1: The index covers all projected columns
-- Query needs: user_id, total → index must store both.

CREATE INDEX idx_orders_user_total ON orders(user_id, total);

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total
FROM   orders
WHERE  user_id = 42;

-- Index Only Scan using idx_orders_user_total on orders
--   (cost=0.56..28.91 rows=843 width=12)
--   (actual time=0.031..1.247 rows=843 loops=1)
--   Index Cond: (user_id = 42)
--   Heap Fetches: 0          ← NO heap pages read
--   Buffers: shared hit=9
-- Execution Time: 1.318 ms   ← vs 8.721 ms for index scan above

-- • "Heap Fetches: 0" is the definitive marker of a true index-only scan.
-- • All 843 rows returned from index pages alone — no heap I/O.

-- ── Condition 2: Visibility Map (the part most candidates miss) ───────────────
-- PostgreSQL cannot read MVCC visibility from the index entry alone.
-- The heap tuple header contains xmin/xmax (which transactions created/deleted it).
-- Without the heap, the planner cannot confirm a row is visible to the current tx.
--
-- Solution: the Visibility Map (VM) — one bit per heap page.
-- Bit = 1 ("all-visible"): ALL tuples on this page are visible to ALL transactions.
--   → Index-only scan can return rows from this page without a heap fetch.
-- Bit = 0 ("not all-visible"): some tuples may be dead or in-progress.
--   → Must fetch the heap page to check visibility → "Heap Fetches: N" goes up.

-- Observing heap fetches due to visibility:
-- After a large batch of UPDATEs (before VACUUM runs):
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;

-- Index Only Scan using idx_orders_user_total on orders
--   Heap Fetches: 312        ← 312 heap page fetches due to VM bits being 0
--   Buffers: shared hit=9 read=298

-- After VACUUM sets the VM bits:
VACUUM orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;

-- Index Only Scan using idx_orders_user_total on orders
--   Heap Fetches: 0          ← VM bits are now 1 → no heap fetches needed
--   Buffers: shared hit=9

-- ── Querying the visibility map ──────────────────────────────────────────────
-- pg_visibility extension shows VM state per page:
CREATE EXTENSION IF NOT EXISTS pg_visibility;

SELECT blkno, all_visible, all_frozen
FROM   pg_visibility('orders')
LIMIT  10;

--  blkno │ all_visible │ all_frozen
-- ───────┼─────────────┼────────────
--      0 │ t           │ t          ← page 0: all-visible, safe for index-only scan
--      1 │ f           │ f          ← page 1: NOT all-visible, heap fetch needed
--      2 │ t           │ f
--      3 │ f           │ f

SELECT COUNT(*) FROM pg_visibility('orders') WHERE NOT all_visible;
-- → How many pages are "dirty" (need heap fetch for index-only scans)
-- High count = VACUUM hasn't run recently = index-only scans are degrading.

-- ── Condition 3: The index type must support index-only scans ─────────────────
-- B-tree:  ✓ Supports index-only scans
-- Hash:    ✓ Supports (PostgreSQL 13+)
-- GiST:    ✗ / ✓ (depends on operator class — most do NOT support it)
-- GIN:     ✗ Does NOT support index-only scans
-- BRIN:    ✗ Does NOT support index-only scans
-- SP-GiST: ✗ / ✓ (depends on operator class)
```

**Q5. Walk through every column requirement for an index-only scan — what happens when the `SELECT` list contains a column not in the index?**

A: The index-only scan degrades to a standard index scan the moment the query needs any column the index does not store. The planner makes this decision at plan time — it either uses the index-only path or falls back to heap fetches for every matched row:

```sql
-- ── Setup ─────────────────────────────────────────────────────────────────────
CREATE INDEX idx_orders_user_total ON orders(user_id, total);
-- Index stores: user_id (key), total (key), ctid (implicit)

-- ── Test 1: All projected columns in index → index-only scan ─────────────────
EXPLAIN SELECT user_id, total
FROM orders WHERE user_id = 42;
-- → Index Only Scan    Heap Fetches: 0  ✓

-- ── Test 2: Add a column NOT in index → falls back to index scan ──────────────
EXPLAIN SELECT user_id, total, status   -- status is NOT in the index
FROM orders WHERE user_id = 42;
-- → Index Scan (NOT index-only)
--   For every matched row: fetch heap page to read 'status'.

-- ── Test 3: SELECT * always causes heap fetch ─────────────────────────────────
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- → Index Scan (or Bitmap Index Scan for large results)
-- SELECT * requests all columns; heap always needed.

-- ── Test 4: WHERE-only column (not projected) — still index-only ──────────────
EXPLAIN SELECT total            -- total is in index
FROM orders WHERE user_id = 42; -- user_id is in index
-- → Index Only Scan  ✓
-- The filter column (user_id) doesn't need to be projected, only readable from index.

-- ── Test 5: ORDER BY using index column — no extra sort ──────────────────────
EXPLAIN SELECT user_id, total
FROM orders WHERE user_id = 42
ORDER BY total DESC;
-- → Index Only Scan (Backward)  ← uses index order, no sort node needed ✓

-- ── Test 6: Aggregate functions — can use index-only ─────────────────────────
EXPLAIN SELECT COUNT(*), SUM(total), AVG(total)
FROM orders WHERE user_id = 42;
-- → Index Only Scan (total is in index)
-- COUNT(*), SUM, AVG can be computed from index data alone.

-- ── Test 7: JOIN — index-only on one side is still valuable ──────────────────
EXPLAIN
SELECT o.user_id, o.total, u.name
FROM   orders o
JOIN   users  u ON u.id = o.user_id
WHERE  o.user_id = 42;
-- → Index Only Scan on orders (user_id, total are in index)
-- → Index Scan or Seq Scan on users (need u.name from heap)
-- The index-only scan on orders still avoids heap fetches for the orders side.

-- ── Diagnostic: checking if Heap Fetches is unexpectedly high ─────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;
--                                    ↑ All columns in index

-- If you see:
--   Index Only Scan ... Heap Fetches: 8341
-- It means: the index qualifies for an index-only scan structurally,
-- but the visibility map bits are 0 on many pages → heap fetches for visibility.
-- Fix: run VACUUM to set all-visible bits.

-- vs. if you see:
--   Index Scan ...   (no "Only")
-- It means: the planner chose NOT to use the index-only path at all —
-- likely because a projected column is missing from the index.
```

## Section 4: Covering Indexes

**Q6. What is a covering index and what is the `INCLUDE` clause — how does it differ from adding a column to the key?**

A: A covering index is any index that stores enough columns to answer a query without heap access. The `INCLUDE` clause (PostgreSQL 11+) adds columns to the index leaf pages without making them part of the sort key — a crucial distinction for correctness and efficiency:

```sql
-- ── Without INCLUDE: all columns are key columns ─────────────────────────────
CREATE INDEX idx_orders_user_status_total
    ON orders(user_id, status, total);
-- B-tree sorted by: (user_id, status, total) — all three affect ordering.
-- Can use index-only scan for queries projecting any subset of these three.
-- Can filter on user_id, (user_id, status), or (user_id, status, total) efficiently.
-- CANNOT efficiently filter on status alone (not a leftmost prefix — see Q10).

-- ── With INCLUDE: key + non-key (payload) columns ────────────────────────────
CREATE INDEX idx_orders_user_id_inc
    ON orders(user_id)
    INCLUDE (status, total, created_at);

-- B-tree sorted by: user_id only.
-- Leaf pages store: (user_id, status, total, created_at, ctid)
-- NON-key columns (status, total, created_at):
--   ✓ Available for index-only scans (no heap fetch for projection)
--   ✗ Cannot be used in the WHERE clause to narrow the B-tree traversal
--   ✗ Cannot be used for ORDER BY or range scans
--   ✗ Not stored in internal B-tree pages (only leaf pages) → smaller index

-- ── Practical difference: when INCLUDE is better than key ────────────────────

-- Scenario: frequently run query:
SELECT user_id, status, total
FROM   orders
WHERE  user_id = 42;

-- Option A: (user_id, status, total) as all key columns
CREATE INDEX idx_a ON orders(user_id, status, total);
-- Works for index-only scan. BUT:
-- If you also run: WHERE user_id = 42 AND status = 'pending'
-- the index sorts by status within user_id — efficient range on (user_id, status).
-- status as a key is good when you filter on it.

-- Option B: (user_id) INCLUDE (status, total)
CREATE INDEX idx_b ON orders(user_id) INCLUDE (status, total);
-- Works for index-only scan. AND:
-- Internal B-tree nodes are smaller (only user_id) → more keys per page → better fanout.
-- Use this when status/total are ONLY projected, never filtered or sorted.

-- ── INCLUDE for unique indexes — the canonical use case ──────────────────────
-- A unique index enforces uniqueness on the key columns only.
-- INCLUDE lets you add extra columns without expanding the uniqueness constraint:

CREATE UNIQUE INDEX idx_users_email_inc
    ON users(email)
    INCLUDE (id, name, created_at);
-- Unique on: email only.
-- Covers queries like: SELECT id, name FROM users WHERE email = 'alice@example.com'
-- → Index Only Scan, no heap fetch, AND the unique constraint is correct.

-- Without INCLUDE:
CREATE UNIQUE INDEX idx_users_email_wrong
    ON users(email, id, name, created_at);
-- Now uniqueness is on (email, id, name, created_at) — WRONG.
-- Two rows with same email but different id would NOT violate this constraint.

-- ── Size comparison ────────────────────────────────────────────────────────────
SELECT
    indexrelid::regclass           AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    indkey                         AS key_columns,
    pg_get_indexdef(indexrelid)    AS definition
FROM   pg_index
WHERE  indrelid = 'orders'::regclass
ORDER  BY pg_relation_size(indexrelid) DESC;

-- (user_id, status, total) as keys:         ~145 MB  (all three in every B-tree node)
-- (user_id) INCLUDE (status, total):        ~112 MB  (only user_id in internal nodes)
-- Smaller internal nodes → better cache utilisation → faster traversal.
```

**Q7. How do you create covering indexes in TypeORM — and how do you verify they are being used?**

A: TypeORM exposes covering indexes through the `@Index` decorator with `INCLUDE`, through `QueryBuilder`, and through raw migration SQL. The verification step — reading `EXPLAIN ANALYZE` output — is as important as the index creation:

```typescript
import {
    Entity, PrimaryGeneratedColumn, Column,
    Index, CreateDateColumn,
} from 'typeorm';

// ── INCLUDE via entity decorator (TypeORM 0.3+) ───────────────────────────────
@Entity('orders')
@Index('idx_orders_user_id_inc', ['userId'], {
    // include is passed through synchronize/migration generation:
    // TypeORM 0.3.x exposes this via the include option:
    include: ['status', 'total', 'createdAt'],  // Non-key columns
})
@Index('idx_orders_status_created', ['status', 'createdAt']) // Regular multi-col
export class Order {
    @PrimaryGeneratedColumn()
    id: number;

    @Column()
    userId: number;

    @Column()
    status: string;

    @Column('decimal', { precision: 10, scale: 2 })
    total: number;

    @CreateDateColumn()
    createdAt: Date;

    @Column({ nullable: true })
    notes: string;   // Not indexed — if projected, triggers heap fetch
}

// ── Creating covering index via QueryRunner in a migration ────────────────────
import { MigrationInterface, QueryRunner } from 'typeorm';

export class AddCoveringIndexOrders1700000000000 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<void> {
        // Standard covering index with INCLUDE:
        await queryRunner.query(`
            CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user_id_inc
            ON orders(user_id)
            INCLUDE (status, total, created_at)
        `);
        // CONCURRENTLY: does not block writes during build.
        // IF NOT EXISTS: idempotent — safe to re-run.

        // Covering index for a report query:
        await queryRunner.query(`
            CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_status_date_inc
            ON orders(status, created_at)
            INCLUDE (user_id, total)
        `);
        // Supports: WHERE status = 'pending' ORDER BY created_at
        //   + projects user_id and total without heap fetch.
    }

    public async down(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`DROP INDEX CONCURRENTLY IF EXISTS idx_orders_user_id_inc`);
        await queryRunner.query(`DROP INDEX CONCURRENTLY IF EXISTS idx_orders_status_date_inc`);
    }
}

// ── Service: writing queries that enable index-only scans ─────────────────────
@Injectable()
export class OrderService {
    constructor(
        @InjectRepository(Order)
        private readonly orderRepo: Repository<Order>,
        private readonly dataSource: DataSource,
    ) {}

    // ✓ Index-only scan possible: only user_id, status, total projected
    async getUserOrderSummary(userId: number): Promise<{ status: string; total: number }[]> {
        return this.orderRepo
            .createQueryBuilder('o')
            .select(['o.status', 'o.total'])  // Both in INCLUDE columns
            .where('o.userId = :userId', { userId })
            .getMany();
        // Generates: SELECT status, total FROM orders WHERE user_id = ?
        // → Index Only Scan using idx_orders_user_id_inc  Heap Fetches: 0
    }

    // ✗ Heap fetch required: 'notes' is not in any index
    async getUserOrderDetails(userId: number): Promise<Order[]> {
        return this.orderRepo
            .createQueryBuilder('o')
            .select(['o.status', 'o.total', 'o.notes']) // notes not in index
            .where('o.userId = :userId', { userId })
            .getMany();
        // → Index Scan (with heap fetches for notes column)
    }

    // ── Verifying index usage in development ──────────────────────────────────
    async explainQuery(userId: number): Promise<void> {
        const [explainResult] = await this.dataSource.query(`
            EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
            SELECT status, total
            FROM   orders
            WHERE  user_id = $1
        `, [userId]);

        const plan = explainResult['QUERY PLAN'][0]['Plan'];
        console.log('Node type:  ', plan['Node Type']);      // 'Index Only Scan'
        console.log('Heap Fetches:', plan['Heap Fetches']);   // 0 = perfect
        console.log('Index Name:  ', plan['Index Name']);
        console.log('Actual Rows: ', plan['Actual Rows']);
        console.log('Actual Time: ', plan['Actual Total Time']);
    }
}
```

## Section 5: The Visibility Map and VACUUM

**Q8. How does the visibility map work — why does `VACUUM` directly affect index-only scan performance?**

A: The visibility map is the bridge between the index-only scan path and MVCC correctness. Without it, every index-only scan would need a heap fetch to confirm row visibility — defeating the purpose. `VACUUM` is what keeps the visibility map current:

```sql
-- ── The visibility map: one bit per heap page ─────────────────────────────────
-- Two bits per page (stored in a separate fork of the table file):
-- Bit 0 — all_visible: all tuples on this page are visible to all transactions.
-- Bit 1 — all_frozen:  all tuples are frozen (xmin set to FrozenTransactionId).
--                      Frozen tuples are always visible — VACUUM doesn't need to check them.

-- Why a page becomes NOT all-visible:
-- 1. Any INSERT onto the page (new tuple — visible only to some transactions)
-- 2. Any UPDATE touching the page (old version may still be live for some readers)
-- 3. Any DELETE on the page (deleted tuple may still be visible to active readers)
-- 4. HOT update on the page (see Q12)

-- When does a page become all-visible again?
-- VACUUM scans each page, checks that all live tuples are visible to all
-- active transactions, then sets the all_visible bit.
-- autovacuum does this automatically — but there is a lag.

-- ── Measuring the visibility map impact ──────────────────────────────────────
-- Before any writes (clean table):
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_vacuum,
       last_autovacuum
FROM   pg_stat_user_tables
WHERE  relname = 'orders';

-- Simulate a burst of updates (dirtying the visibility map):
UPDATE orders SET total = total * 1.01 WHERE user_id BETWEEN 1 AND 100;
-- → ~thousands of pages dirtied (old versions created, VM bits cleared)

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;
-- Index Only Scan ... Heap Fetches: 843   ← all pages dirty → heap fetch every row

-- Run VACUUM:
VACUUM (VERBOSE) orders;
-- INFO:  vacuuming "public.orders"
-- INFO:  scanned index "idx_orders_user_id_inc" to remove 12341 row versions
-- INFO:  "orders": removed 12341 dead row versions in 1823 pages
-- INFO:  "orders": found 12341 removable, 487659 nonremovable row versions
-- INFO:  all_visible bits set: 8215 pages   ← VM bits restored

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;
-- Index Only Scan ... Heap Fetches: 0     ← VM bits restored → pure index-only ✓

-- ── autovacuum tuning for index-only scan performance ─────────────────────────
-- Default autovacuum triggers too late for high-write tables.
-- Reduce the trigger threshold for tables with index-only scan queries:

ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor    = 0.01,  -- Trigger after 1% of rows changed (default 20%)
    autovacuum_vacuum_threshold       = 1000,  -- Or after 1000 row changes (default 50)
    autovacuum_analyze_scale_factor   = 0.005, -- Also analyze more frequently
    autovacuum_vacuum_cost_delay      = 2      -- ms — faster vacuum (default 2ms)
);
-- More frequent vacuuming → more pages all-visible → index-only scans stay fast.

-- ── Monitoring visibility map health for a table ─────────────────────────────
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- n_dead_tup > 10% → autovacuum is behind → index-only scans degrade.

-- ── The two-bitmap structure (all_visible vs all_frozen) ─────────────────────
-- all_frozen pages are a superset of all_visible:
-- If all_frozen = TRUE → all_visible is implicitly TRUE.
-- Frozen tuples can be skipped entirely by VACUUM in future runs.
-- Aggressive VACUUM (FREEZE) sets all_frozen bits:
VACUUM FREEZE orders;
-- → Freezes old enough tuples, sets all_frozen bits → VACUUM runs faster in future.
```

## Section 6: Partial and Expression Indexes

**Q9. How do partial indexes enable index-only scans on subsets of data — and when are they better than full indexes?**

A: A partial index covers only the rows that match a `WHERE` predicate. It is smaller, faster to scan, and can enable index-only scans on a targeted subset while leaving the rest of the table without index overhead:

```sql
-- ── Scenario: 95% of orders are 'completed', 5% are 'pending' ────────────────
-- Queries almost always look at pending orders:
-- SELECT user_id, total FROM orders WHERE status = 'pending' AND user_id = 42;
-- Full index on (status, user_id): includes 95% completed orders — wasteful.

-- ── Partial index: index only pending orders ──────────────────────────────────
CREATE INDEX idx_orders_pending_user
    ON orders(user_id)
    INCLUDE (total)
    WHERE status = 'pending';   -- Partial index predicate

-- ── What the planner sees ─────────────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total
FROM   orders
WHERE  status  = 'pending'   -- Matches the partial index predicate
AND    user_id = 42;

-- Index Only Scan using idx_orders_pending_user on orders
--   (cost=0.29..4.87 rows=23 width=12)
--   (actual time=0.018..0.312 rows=22 loops=1)
--   Index Cond: (user_id = 42)
--   Filter: (status = 'pending')   ← predicate checked against index, not heap
--   Heap Fetches: 0
-- ✓ Only 5% of rows in the index → index is 95% smaller → fits in cache more easily.

-- ── Partial index vs full index size ─────────────────────────────────────────
-- Full index on (user_id) INCLUDE (total): indexes all 500,000 rows → ~145 MB
-- Partial index (WHERE status = 'pending'): indexes 25,000 rows → ~7 MB
-- → 20x smaller, 20x more likely to fit in shared_buffers.

-- ── Query must include the partial index predicate (exact match required) ─────
-- This query CANNOT use the partial index:
SELECT user_id, total FROM orders WHERE user_id = 42;
-- → Missing "status = 'pending'" → planner cannot guarantee the partial index
--   covers the needed rows → falls back to full index or seq scan.

-- ── Partial index for soft deletes ────────────────────────────────────────────
-- Most queries never look at deleted rows — exclude them from the index:
CREATE INDEX idx_orders_active
    ON orders(user_id, created_at)
    INCLUDE (status, total)
    WHERE deleted_at IS NULL;   -- Partial: only non-deleted rows

SELECT user_id, created_at, status, total
FROM   orders
WHERE  deleted_at IS NULL
AND    user_id = 42
ORDER  BY created_at DESC;
-- → Index Only Scan using idx_orders_active
--   The WHERE deleted_at IS NULL in the query matches the partial index predicate.

-- ── Partial unique index ───────────────────────────────────────────────────────
-- Unique email per active user (soft-delete scenario):
CREATE UNIQUE INDEX idx_users_active_email
    ON users(email)
    WHERE deleted_at IS NULL;
-- Allows multiple rows with the same email if all but one are soft-deleted.
-- Enforces uniqueness only among active users.

-- ── Expression (functional) index — index-only scan on computed values ─────────
-- Query: find orders where EXTRACT(YEAR FROM created_at) = 2024
-- Without an index on the expression, this is always a seq scan:
CREATE INDEX idx_orders_year ON orders(EXTRACT(YEAR FROM created_at));
-- Now the planner can use this index — but NOT for index-only scans:
-- The index stores the computed value, but the heap must be fetched for
-- any projected column not in the index.

-- To enable index-only scans on expressions:
CREATE INDEX idx_orders_year_inc
    ON orders(EXTRACT(YEAR FROM created_at))
    INCLUDE (user_id, total, status);

EXPLAIN
SELECT user_id, total, status
FROM   orders
WHERE  EXTRACT(YEAR FROM created_at) = 2024;
-- → Index Only Scan using idx_orders_year_inc   Heap Fetches: 0  ✓
```

## Section 7: Multi-Column Indexes and Column Order

**Q10. How does column order in a multi-column index affect index-only scans — what is the leftmost prefix rule?**

A: The B-tree structure means a multi-column index can only be efficiently traversed when the filter or sort starts from the leftmost key column. This rule determines not just whether an index is used, but whether an index-ONLY scan is achievable:

```sql
-- ── Index: (user_id, status, created_at) INCLUDE (total) ─────────────────────
CREATE INDEX idx_orders_composite
    ON orders(user_id, status, created_at)
    INCLUDE (total);

-- The B-tree is sorted by user_id first, then status within user_id,
-- then created_at within status. Think of it as nested sort:
--   user_id=1, status='pending',  created_at=2024-01-01
--   user_id=1, status='pending',  created_at=2024-01-15
--   user_id=1, status='shipped',  created_at=2024-01-02
--   user_id=2, status='pending',  created_at=2024-01-03
--   user_id=2, status='shipped',  created_at=2024-01-10

-- ── Queries that CAN use this index efficiently ───────────────────────────────

-- Leftmost prefix only:
SELECT user_id, status, created_at, total
FROM   orders WHERE user_id = 1;
-- → Index Only Scan ✓ (user_id is leftmost)

-- Two leftmost prefixes:
SELECT user_id, status, created_at, total
FROM   orders WHERE user_id = 1 AND status = 'pending';
-- → Index Only Scan ✓ (equality on first two columns)

-- All three key columns:
SELECT user_id, status, created_at, total
FROM   orders WHERE user_id = 1 AND status = 'pending' AND created_at > '2024-01-01';
-- → Index Only Scan ✓ (range on the last key column is fine)

-- Range on leftmost, equality impossible after range in B-tree:
SELECT user_id, status, created_at, total
FROM   orders WHERE user_id BETWEEN 1 AND 10;
-- → Bitmap Index Scan or Index Scan (range on first column → less efficient)

-- ── Queries that CANNOT use this index efficiently ────────────────────────────

-- Skip the leftmost prefix — filter on status without user_id:
SELECT user_id, status, created_at, total
FROM   orders WHERE status = 'pending';
-- → Seq Scan or separate index on status needed.
-- The B-tree is sorted by user_id first; 'pending' rows are scattered throughout.

-- Skip a middle column — filter on user_id and created_at, skip status:
SELECT user_id, status, created_at, total
FROM   orders WHERE user_id = 1 AND created_at > '2024-01-01';
-- → Index Scan using the index (user_id prefix helps), but the planner
--   cannot use created_at to skip B-tree pages because status is in between.
--   Filter on created_at is applied AFTER the index lookup, not during.
-- → Still beneficial (filters on user_id), but created_at is a "recheck filter".

-- ── Choosing column order: equality vs range vs cardinality ──────────────────
-- Rule: put equality-filter columns BEFORE range-filter columns.
-- Reason: equality exhausts the sort key (all matching rows are contiguous),
--         but a range on the first column makes subsequent columns unsorted.

-- BAD order for this query pattern: WHERE status = 'pending' AND created_at > '2024'
CREATE INDEX idx_bad ON orders(created_at, status);
-- → Range on created_at first → status entries are scattered → can't use status in B-tree.

-- GOOD order:
CREATE INDEX idx_good ON orders(status, created_at);
-- → Equality on status → all 'pending' rows contiguous → range on created_at within them.

-- ── Index for ORDER BY — avoid a sort node ───────────────────────────────────
-- If WHERE column order matches ORDER BY column order → planner skips Sort node.
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);

EXPLAIN
SELECT user_id, created_at, total
FROM   orders
WHERE  user_id = 42
ORDER  BY created_at DESC;
-- → Index Only Scan (Backward)  ← using index order, no Sort node ✓

EXPLAIN
SELECT user_id, created_at, total
FROM   orders
WHERE  user_id = 42
ORDER  BY created_at ASC;   -- Opposite direction from index
-- → Index Only Scan (Forward) or Index Scan — planner may scan index forward
--   or add a Sort node depending on cost.
-- → If you need both ASC and DESC, create an ASC index;
--   PostgreSQL can scan B-trees in both directions efficiently.
```

## Section 8: Reading EXPLAIN Output

**Q11. How do you read `EXPLAIN (ANALYZE, BUFFERS)` output to diagnose scan type performance — what are the key numbers?**

A: `EXPLAIN ANALYZE` is the primary diagnostic tool. Every query optimisation decision should start and end with reading actual plan output, not guessing:

```sql
-- ── Full annotated EXPLAIN output ─────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT user_id, status, total
FROM   orders
WHERE  user_id = 42
ORDER  BY created_at DESC
LIMIT  20;

-- Index Only Scan Backward using idx_orders_user_id_inc on orders
-- ──────────────────────────────────────────────────────────────────────────────
--   (cost=0.56..47.22 rows=20 width=24)       ← ESTIMATED cost and rows
--   (actual time=0.031..0.214 rows=20 loops=1) ← ACTUAL time and rows
--
-- ① Node Type: "Index Only Scan Backward"
--    "Only" → no heap fetch (good)
--    "Backward" → index scanned in reverse (ORDER BY DESC without extra Sort)
--
-- ② cost=0.56..47.22
--    0.56   = startup cost (time to return FIRST row) — B-tree traversal
--    47.22  = total cost (time to return ALL rows in this node)
--    These are in arbitrary "cost units" (not milliseconds).
--    Compare to seq scan cost to understand planner's choice.
--
-- ③ rows=20 width=24
--    rows=20  → planner estimates 20 rows returned
--    width=24 → average bytes per row (user_id=4, status=8, total=8, overhead=4)
--
-- ④ actual time=0.031..0.214
--    0.031 ms = time to first row (startup)
--    0.214 ms = time to last row (total for this node)
--
-- ⑤ loops=1 → this node executed once (would be >1 in nested loop joins)
--    actual time is PER LOOP — multiply by loops for total contribution.
--
-- ⑥ Index Cond: (user_id = 42)
--    Condition evaluated against the index — no heap needed for this filter.
--
-- ⑦ Heap Fetches: 0
--    THE KEY METRIC for index-only scan quality.
--    0   = perfect — all rows from index pages, VM bits all set.
--    > 0 = VM bits not set — VACUUM needed or recently written pages.
--
-- ⑧ Buffers: shared hit=7 read=0
--    shared hit = pages found in shared_buffers (RAM cache)
--    read       = pages read from disk (each = ~1 random I/O)
--    dirtied    = pages dirtied during this query (normally 0 for reads)
--    written    = pages written to disk (normally 0 for reads)
--    Goal: maximise hit, minimise read.

-- ── Spotting a plan regression ────────────────────────────────────────────────
-- Before optimisation:
-- Seq Scan on orders
--   (cost=0.00..18432.00 rows=843 width=24)
--   (actual time=0.039..312.451 rows=843 loops=1)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 499157
--   Buffers: shared hit=1832 read=6383

-- After adding covering index + VACUUM:
-- Index Only Scan using idx_orders_user_id_inc on orders
--   (cost=0.56..47.22 rows=843 width=24)
--   (actual time=0.031..0.981 rows=843 loops=1)
--   Index Cond: (user_id = 42)
--   Heap Fetches: 0
--   Buffers: shared hit=7 read=0

-- Improvement:
--   Execution time: 312 ms → 0.98 ms  (320x faster)
--   Buffer hits:    8215 pages → 7 pages
--   Disk reads:     6383 → 0

-- ── Identifying estimate vs actual row count mismatch ─────────────────────────
-- If estimated rows << actual rows: statistics are stale → run ANALYZE.
-- Large mismatch leads to bad plan choices.

-- Seq Scan on orders
--   (cost=0.00..8432.00 rows=50 width=87)    ← estimates 50 rows
--   (actual time=0.039..412.231 rows=94832 loops=1)  ← actually 94,832 rows
-- → Planner chose seq scan thinking there were 50 rows.
-- → Fix: ANALYZE orders; to refresh statistics.
-- → Or increase statistics target: ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;

-- ── Key EXPLAIN nodes and what they mean ─────────────────────────────────────
-- Seq Scan:           Full table read. rows_removed_by_filter → wasteful if high.
-- Index Scan:         B-tree + heap fetch per row. Efficient for < ~5% selectivity.
-- Index Only Scan:    B-tree only (if heap_fetches=0). Best case.
-- Bitmap Index Scan:  B-tree → bitmap → sequential heap pages. Medium selectivity.
-- Bitmap Heap Scan:   Second phase of bitmap scan. "Recheck Cond" = lossy bitmap.
-- Sort:               In-memory or on-disk sort. Present when index can't provide order.
-- Hash Join:          Join using hash table. Common for large joins.
-- Nested Loop:        Join by iterating outer rows and probing inner. Good for small outer.
-- Materialize:        Saves inner plan to memory/disk for re-use in nested loop.
```

## Section 9: Statistics and Planner Decisions

**Q12. How do table statistics affect scan type selection — what is `ANALYZE` and when do you need to tune `statistics` targets?**

A: The planner's cost estimates depend entirely on statistics collected by `ANALYZE`. Stale or low-resolution statistics cause the planner to choose the wrong scan type — typically picking a seq scan when an index-only scan would be far faster:

```sql
-- ── What ANALYZE collects ─────────────────────────────────────────────────────
-- For each column, ANALYZE stores in pg_statistic:
--   most_common_vals   — the N most frequent values
--   most_common_freqs  — frequency of each MCV
--   histogram_bounds   — bucket boundaries for range estimates
--   n_distinct         — number of distinct values (negative = fraction of total)
--   correlation        — how sorted the column is vs heap order (1=perfectly sorted)

-- View column statistics:
SELECT
    attname,
    n_distinct,
    correlation,
    most_common_vals::text,
    most_common_freqs::text
FROM   pg_stats
WHERE  tablename = 'orders'
AND    attname   IN ('user_id', 'status', 'total');

-- attname  │ n_distinct │ correlation │ most_common_vals         │ most_common_freqs
-- ─────────┼────────────┼─────────────┼──────────────────────────┼──────────────────
-- user_id  │  -0.5      │   0.02      │                          │
-- status   │  4         │   0.31      │ {completed,pending,...}  │ {0.62,0.21,...}
-- total    │  -0.8      │   0.01      │                          │

-- n_distinct = -0.5 → ~50% of rows have a distinct user_id (computed as fraction)
-- correlation = 0.02 → user_id is nearly random vs heap order
--   Low correlation → index scan causes many random heap fetches → planner prefers seq scan
--   High correlation → index scan accesses heap mostly sequentially → planner prefers index scan

-- ── statistics target: controlling histogram resolution ───────────────────────
-- Default statistics target = 100 (100 histogram buckets, 100 MCVs).
-- For columns with high cardinality or skewed distributions, increase it:

ALTER TABLE orders ALTER COLUMN user_id    SET STATISTICS 500;
ALTER TABLE orders ALTER COLUMN created_at SET STATISTICS 500;
ANALYZE orders;  -- Re-collect with higher resolution

-- Verify the improvement:
SELECT tablename, attname, n_distinct, avg_width
FROM   pg_stats
WHERE  tablename = 'orders';

-- ── Correlation and index scan choice ─────────────────────────────────────────
-- correlation = 1.0  → column values are stored in the same order as the heap.
--                       An index scan reads heap pages sequentially → cheap.
--                       Planner prefers index scan even at moderate selectivity.
-- correlation = 0.0  → values are in random heap order.
--                       Index scan = random page accesses → expensive.
--                       Planner needs high selectivity to prefer index scan.

-- Clustering the table improves correlation:
CLUSTER orders USING idx_orders_user_id_inc;
-- → Rewrites the heap in index order → user_id correlation becomes ~1.0.
-- → Index scans become sequential-ish → much cheaper.
-- → CLUSTER is a one-time operation; heap becomes unsorted again after writes.
-- → For ongoing benefit, use pg_partman or BRIN indexes for time-series data.

-- ── When the planner chooses seq scan despite a good index ────────────────────
-- 1. Table is small (fits in 1-3 pages): seq scan is faster than B-tree traversal.
-- 2. Low selectivity: filter matches > ~25% of rows (default settings).
-- 3. Low correlation: random heap access makes index scan costly.
-- 4. Stale statistics: planner thinks there are fewer rows than there are.
-- 5. random_page_cost is too high vs actual disk speed (SSD vs HDD).

-- Tuning random_page_cost for SSDs (major impact on index-only scan preference):
-- In postgresql.conf:
--   random_page_cost = 1.1   -- SSD (default 4.0 assumes spinning disk)
--   seq_page_cost    = 1.0
-- With random_page_cost = 1.1, index scans win at much lower selectivity.
-- At random_page_cost = 1.0, index scan is almost always chosen over seq scan.

-- ── Extended statistics for correlated columns ────────────────────────────────
-- If two columns are correlated (e.g. city and zip_code, or status and resolved_at),
-- the planner assumes independence and underestimates row counts.

CREATE STATISTICS stat_orders_status_user (dependencies)
    ON status, user_id
    FROM orders;
ANALYZE orders;
-- → Planner now understands correlation between status and user_id.
-- → Row estimates are more accurate → better scan type selection.
```

## Section 10: HOT Updates

**Q13. What is a HOT update and how does it affect index-only scan performance?**

A: Heap Only Tuple (HOT) is PostgreSQL's optimisation for updating non-indexed columns. When a row is updated and none of the changed columns are part of any index, PostgreSQL can create the new tuple version on the same heap page without creating a new index entry — keeping the index small and the visibility map healthier:

```sql
-- ── What happens on a normal UPDATE ──────────────────────────────────────────
-- UPDATE orders SET status = 'shipped' WHERE id = 1;
-- If 'status' is indexed:
--   1. New heap tuple created (possibly on a different page)
--   2. New index entry added pointing to new tuple's ctid
--   3. Old index entry marked dead (but still occupies space)
--   4. VACUUM later removes dead index entries
--   5. VM bit for old page cleared → index-only scans degrade

-- ── HOT update (non-indexed column changed) ────────────────────────────────────
-- UPDATE orders SET notes = 'Expedited' WHERE id = 1;
-- If 'notes' is NOT indexed:
--   1. New heap tuple created ON THE SAME PAGE as the old one
--   2. Old tuple's t_ctid points to new tuple (heap chain)
--   3. NO new index entry created — the old index entry still valid
--   4. Index sees old ctid → follows HOT chain on heap page → finds new version
--   5. VM bit MAY remain set if the page stays all-visible
-- Result: index stays small, visibility map stays cleaner.

-- ── Checking HOT update rate ──────────────────────────────────────────────────
SELECT
    relname,
    n_tup_upd    AS total_updates,
    n_tup_hot_upd AS hot_updates,
    ROUND(100.0 * n_tup_hot_upd / NULLIF(n_tup_upd, 0), 1) AS hot_pct
FROM   pg_stat_user_tables
WHERE  relname = 'orders';

--  relname │ total_updates │ hot_updates │ hot_pct
-- ─────────┼───────────────┼─────────────┼─────────
--  orders  │    1,234,567  │    987,234  │    79.9

-- 80% HOT rate is good. Low HOT rate means:
-- 1. Many updates touch indexed columns → more index bloat → slower index scans.
-- 2. Check if over-indexed: every index on a column prevents HOT updates.
-- 3. Consider removing indexes that are never used (pg_stat_user_indexes).

-- ── HOT and fill factor ────────────────────────────────────────────────────────
-- HOT updates require free space on the SAME page as the old tuple.
-- If the page is full (default fillfactor=100), HOT is impossible → normal update.

-- For frequently-updated tables: lower the fillfactor to reserve space for HOT:
ALTER TABLE orders SET (fillfactor = 70);
-- → Each page is only 70% full initially.
-- → 30% reserved for HOT updates on the same page.
-- → More HOT updates → index stays smaller → index-only scans stay faster.
-- Trade-off: table takes ~43% more disk space (100/70).

-- Same for indexes:
CREATE INDEX idx_orders_user_id_inc ON orders(user_id)
    INCLUDE (status, total)
    WITH (fillfactor = 80);
-- → Index pages 80% full → room for split-less inserts on adjacent pages.

-- ── Finding over-indexed tables hurting HOT rate ──────────────────────────────
-- Indexes that are never used but still prevent HOT updates:
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,         -- Number of times this index was used for a scan
    idx_tup_read,     -- Tuples read via this index
    idx_tup_fetch     -- Tuples fetched from heap via this index
FROM   pg_stat_user_indexes
WHERE  tablename = 'orders'
ORDER  BY idx_scan ASC;

-- Indexes with idx_scan = 0 (or very low):
-- → Never used → consuming space, preventing HOT updates, degrading write throughput.
-- → Candidates for removal (verify with pg_stat_reset() after a representative period).
```

## Section 11: Scenario-Based Questions

**Q14. "Our queries were fast for months, then slowed down suddenly — EXPLAIN now shows heap fetches spiking to thousands."**

A: This is the classic autovacuum lag pattern. The visibility map has gone stale after a write burst, and the index-only scan is now doing heap fetches for nearly every row:

```sql
-- ── Step 1: Confirm the symptom ───────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;

-- Index Only Scan using idx_orders_user_id_inc on orders
--   Heap Fetches: 8341   ← sudden spike from 0
--   Buffers: shared hit=9 read=8291   ← thousands of disk reads
-- Execution time: 2341 ms → was 1.2 ms

-- ── Step 2: Check visibility map health ──────────────────────────────────────
SELECT COUNT(*) AS dirty_pages
FROM   pg_visibility('orders')
WHERE  NOT all_visible;
-- → 8215 dirty pages  (95% of total pages)
-- Confirms: almost the entire table's VM bits are cleared.

-- ── Step 3: Check autovacuum state ───────────────────────────────────────────
SELECT
    last_autovacuum,
    n_dead_tup,
    n_live_tup,
    autovacuum_count,
    last_vacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- last_autovacuum: 2024-01-15 03:00:00  ← ran 6 hours ago
-- n_dead_tup:      2,341,892            ← millions of dead tuples

-- What happened: a batch job ran UPDATE orders SET ... for millions of rows.
-- Autovacuum was triggered but ran slowly (default cost_delay).
-- Result: millions of dead tuples, VM bits cleared everywhere.

-- ── Step 4: Immediate fix — manual VACUUM ────────────────────────────────────
VACUUM (VERBOSE, ANALYZE) orders;
-- VERBOSE shows progress. ANALYZE refreshes statistics while it runs.
-- After: n_dead_tup ≈ 0, all_visible bits restored.

-- Re-check:
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total FROM orders WHERE user_id = 42;
-- Index Only Scan ... Heap Fetches: 0  ← restored ✓
-- Execution time: 1.3 ms               ← back to normal ✓

-- ── Step 5: Prevent recurrence — tune autovacuum for this table ───────────────
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor    = 0.005,  -- Trigger after 0.5% changes (was 20%)
    autovacuum_vacuum_threshold       = 500,    -- Or after 500 rows (was 50 — too low)
    autovacuum_vacuum_cost_delay      = 2,      -- Run faster (ms between cost sleeps)
    autovacuum_vacuum_cost_limit      = 800     -- More work per cost period (was 200)
);

-- ── Step 6: For batch jobs — VACUUM in the job itself ─────────────────────────
-- Run VACUUM after large batch updates instead of waiting for autovacuum:
-- In the NestJS batch job:
async function runBatchUpdate(dataSource: DataSource): Promise<void> {
    await dataSource.query(`
        UPDATE orders
        SET    status = 'archived'
        WHERE  created_at < NOW() - INTERVAL '2 years'
    `);
    // Immediately vacuum to restore VM bits:
    await dataSource.query(`VACUUM (ANALYZE) orders`);
    // Note: VACUUM cannot run inside a transaction — run it after COMMIT.
}
```

**Q15. "Design the index strategy for a high-traffic e-commerce order listing API — support filtering by user, status, and date range, with index-only scans."**

A: This requires mapping every query pattern to a covering index, accounting for column order rules, visibility map maintenance, and partial indexes for common status filters:

```sql
-- ── Query patterns to support ─────────────────────────────────────────────────
-- Pattern 1: User's order list (most common — 80% of traffic)
--   SELECT id, status, total, created_at
--   FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20

-- Pattern 2: User's pending orders
--   SELECT id, status, total, created_at
--   FROM orders WHERE user_id = ? AND status = 'pending'

-- Pattern 3: Admin date range report
--   SELECT user_id, status, SUM(total)
--   FROM orders WHERE created_at BETWEEN ? AND ? GROUP BY user_id, status

-- Pattern 4: Status queue (worker picks up pending orders)
--   SELECT id, user_id, total FROM orders WHERE status = 'pending'
--   ORDER BY created_at ASC LIMIT 50 FOR UPDATE SKIP LOCKED

-- ── Index 1: User's order list (Pattern 1 + 2) ────────────────────────────────
CREATE INDEX CONCURRENTLY idx_orders_user_date
    ON orders(user_id, created_at DESC)
    INCLUDE (id, status, total);
-- Column order: user_id (equality) → created_at DESC (order)
-- INCLUDE: id, status, total → all projected columns covered
-- Supports Pattern 1: WHERE user_id = ? ORDER BY created_at DESC → Index Only Scan
-- Supports Pattern 2: WHERE user_id = ? AND status = 'pending'
--   → planner uses idx_orders_user_date (user_id prefix) + filter on status
--   → Heap Fetches: 0 if status is in INCLUDE ✓

-- ── Index 2: Partial index for pending orders only (Pattern 2 + 4) ────────────
CREATE INDEX CONCURRENTLY idx_orders_pending_queue
    ON orders(created_at ASC)
    INCLUDE (id, user_id, total)
    WHERE status = 'pending';
-- Partial: only ~5% of orders (pending ones) → 20x smaller than full index.
-- Supports Pattern 4 exactly: WHERE status = 'pending' ORDER BY created_at ASC
--   → Index Only Scan using idx_orders_pending_queue  Heap Fetches: 0 ✓
-- Also used for FOR UPDATE SKIP LOCKED job queue.

-- ── Index 3: Date range report (Pattern 3) ───────────────────────────────────
CREATE INDEX CONCURRENTLY idx_orders_created_status
    ON orders(created_at, status)
    INCLUDE (user_id, total);
-- Column order: created_at first (range filter) → status within date range
-- INCLUDE: user_id, total → GROUP BY and SUM can be done from index
-- Supports Pattern 3: WHERE created_at BETWEEN ? AND ? GROUP BY user_id, status
--   → Index Only Scan → no heap fetch for the aggregation ✓
-- Note: SUM(total) computed from INCLUDE column → no heap access.

-- ── Verification: all patterns use index-only scans ───────────────────────────

-- Pattern 1:
EXPLAIN SELECT id, status, total, created_at
FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
-- → Index Only Scan Backward using idx_orders_user_date  Heap Fetches: 0 ✓

-- Pattern 2:
EXPLAIN SELECT id, status, total, created_at
FROM orders WHERE user_id = 42 AND status = 'pending';
-- → Index Only Scan using idx_orders_user_date
--   Index Cond: (user_id = 42)
--   Filter: (status = 'pending')
--   Heap Fetches: 0 ✓

-- Pattern 3:
EXPLAIN SELECT user_id, status, SUM(total)
FROM orders WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'
GROUP BY user_id, status;
-- → Index Only Scan using idx_orders_created_status  Heap Fetches: 0 ✓

-- Pattern 4:
EXPLAIN SELECT id, user_id, total
FROM orders WHERE status = 'pending'
ORDER BY created_at ASC LIMIT 50;
-- → Index Only Scan using idx_orders_pending_queue  Heap Fetches: 0 ✓

-- ── TypeORM entity with all indexes ───────────────────────────────────────────
@Entity('orders')
@Index('idx_orders_user_date',       ['userId', 'createdAt'], { /* DESC handled in migration */ })
@Index('idx_orders_created_status',  ['createdAt', 'status'])
export class Order {
    @PrimaryGeneratedColumn() id: number;
    @Column() userId: number;
    @Column() status: string;
    @Column('decimal', { precision: 10, scale: 2 }) total: number;
    @CreateDateColumn() createdAt: Date;
    @Column({ nullable: true }) notes: string; // Not indexed — never projected alone
}

-- ── autovacuum tuning for the high-write orders table ─────────────────────────
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.005,
    autovacuum_vacuum_threshold     = 1000,
    autovacuum_analyze_scale_factor = 0.002,
    fillfactor                      = 80     -- Reserve 20% for HOT updates
);

-- ── Index maintenance monitoring queries ─────────────────────────────────────
-- Weekly check: are index-only scans still working?
SELECT
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM   pg_stat_user_indexes
WHERE  tablename = 'orders'
ORDER  BY idx_scan DESC;

-- Heap fetch ratio for index-only scans (low ratio = healthy):
WITH stats AS (
    SELECT
        schemaname,
        relname,
        heap_blks_read,
        heap_blks_hit,
        idx_blks_read,
        idx_blks_hit
    FROM pg_statio_user_tables
    WHERE relname = 'orders'
)
SELECT
    relname,
    heap_blks_read AS heap_disk_reads,
    idx_blks_read  AS index_disk_reads,
    ROUND(100.0 * heap_blks_read / NULLIF(heap_blks_read + idx_blks_read, 0), 1)
        AS heap_read_pct
FROM stats;
-- heap_read_pct close to 0%: mostly reading from index → index-only scans working.
-- heap_read_pct high: heap reads dominate → VM bits dirty, index misses, or missing INCLUDE.
```

## Quick Reference Tables

### Scan Type Comparison

| Scan type | Reads index? | Reads heap? | When chosen | Key indicator in EXPLAIN |
|---|---|---|---|---|
| Seq Scan | No | Yes — all pages | Low selectivity, small table, no index | `Seq Scan`, `Rows Removed by Filter` |
| Index Scan | Yes | Yes — matched rows | High selectivity, high correlation | `Index Scan`, heap fetches implicit |
| Bitmap Index Scan | Yes (full range) | Yes — by page order | Medium selectivity, multi-index | `Bitmap Index Scan` + `Bitmap Heap Scan` |
| Index Only Scan | Yes | No (if VM bits set) | All columns in index, VM current | `Index Only Scan`, `Heap Fetches: 0` |

### Index-Only Scan Checklist

| Requirement | How to verify | Fix if failing |
|---|---|---|
| All projected columns in index | `EXPLAIN` shows `Index Only Scan` | Add `INCLUDE (col)` or add to key |
| Visibility map bits set | `Heap Fetches: 0` in EXPLAIN | Run `VACUUM (ANALYZE) tablename` |
| Index type supports it | B-tree = ✓, GIN = ✗ | Switch to B-tree for covering queries |
| Statistics are fresh | Estimated ≈ actual rows in EXPLAIN | Run `ANALYZE tablename` |
| Selectivity is high enough | Planner picks Index Only Scan | Tune `random_page_cost` or use partial index |

### Column Order Rules for Multi-Column Indexes

| Query pattern | Correct column order | Reason |
|---|---|---|
| `WHERE a = ? AND b = ?` | `(a, b)` | Either order works — both equality |
| `WHERE a = ? ORDER BY b` | `(a, b)` | Equality first, then sorted column |
| `WHERE a = ? AND b > ?` | `(a, b)` | Equality before range |
| `WHERE a > ? AND b = ?` | `(b, a)` | Equality (b) before range (a) |
| `WHERE a = ? AND b = ? ORDER BY c` | `(a, b, c)` | Equalities then sort |
| `WHERE a IN (?,?) ORDER BY b` | `(a, b)` | IN treated as equality in B-tree |

### EXPLAIN Key Fields

| Field | What it tells you | Healthy value |
|---|---|---|
| `Heap Fetches: N` | Heap pages read during index-only scan | 0 (after VACUUM) |
| `Rows Removed by Filter` | Rows read but discarded | Low — high means wrong index or low selectivity |
| `Buffers: shared read=N` | Pages read from disk (not cache) | Low — high means insufficient `shared_buffers` |
| `actual rows` vs `rows` | Estimate accuracy | Close — mismatch means stale statistics |
| `loops=N` | Times this node ran (nested loops) | Multiply time by loops for total |
| `actual time=X..Y` | Start time..total time (ms) | Per loop — multiply by loops |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise that an index-only scan has **two independent requirements** — all projected columns must be in the index AND the visibility map bits must be set — and knowing that `Heap Fetches: N` in EXPLAIN is the single metric that reveals whether the visibility map condition is met, not just whether the plan is labelled "Index Only Scan"; (2) knowing that **`VACUUM` is what sets all-visible bits** in the visibility map, and that any `UPDATE` or `DELETE` clears those bits — meaning a write-heavy table will see `Heap Fetches` climb over time between vacuum runs, and autovacuum must be tuned aggressively for tables relied upon for index-only scan performance; (3) understanding the **`INCLUDE` clause vs adding a column as a key** — INCLUDE columns are stored only in leaf pages (smaller internal nodes, better cache efficiency) and cannot be used for filtering or sorting, while key columns are in every B-tree node and can be used in WHERE, ORDER BY, and range filters; (4) knowing the **leftmost prefix rule** — a composite index on `(a, b, c)` supports filters on `a`, `(a, b)`, and `(a, b, c)` efficiently, but NOT on `b` or `c` alone; putting equality-filter columns before range-filter columns is the most important ordering decision; (5) knowing that **`random_page_cost`** is the lever that determines how aggressively the planner favours index scans over sequential scans — defaulting to `4.0` for spinning disks, it should be set to `1.1`–`1.5` for SSDs, dramatically changing the break-even point at which an index scan is chosen; (6) understanding **HOT updates** — when an UPDATE touches only non-indexed columns and the new tuple fits on the same heap page, no new index entry is created, the visibility map is disturbed less, and the index stays compact; over-indexing prevents HOT updates and increases write amplification; (7) being able to **read EXPLAIN output** with confidence — specifically: "Index Only Scan" vs "Index Scan" vs "Bitmap Index Scan", what `Heap Fetches`, `Buffers: shared read`, `Rows Removed by Filter`, and `loops` mean, and how to spot estimate vs actual row count mismatches that signal stale statistics; and (8) knowing that **partial indexes** can enable index-only scans on a targeted subset of rows at a fraction of the size of a full index — the canonical pattern is `WHERE status = 'pending'` for a queue table where 95% of rows are completed, making the index 20x smaller and more likely to fit in `shared_buffers`.
