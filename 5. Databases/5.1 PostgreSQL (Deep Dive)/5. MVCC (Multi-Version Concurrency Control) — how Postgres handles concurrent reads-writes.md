# MVCC (Multi-Version Concurrency Control) — How Postgres Handles Concurrent Reads/Writes: Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is MVCC, what problem does it solve, and what is PostgreSQL's core guarantee?**

A: MVCC (Multi-Version Concurrency Control) is a concurrency model where each write creates a new **version** of a row rather than modifying the row in place. Readers and writers operate on different versions simultaneously — no reader needs to wait for a writer to finish, and no writer needs to wait for a reader to finish.

**The problem without MVCC — naive locking:**
```
Without MVCC (naive reader-writer lock model):
────────────────────────────────────────────────────────────
T1 (write): BEGIN UPDATE accounts SET balance=900 WHERE id=1
            ← holds write lock on row
T2 (read):  BEGIN SELECT balance FROM accounts WHERE id=1
            ← BLOCKED — waiting for T1's write lock to release

T1 commits → releases lock → T2 finally runs

Effect: reads and writes are serialized — no true concurrency
```

**With MVCC:**
```
T1 (write): BEGIN UPDATE accounts SET balance=900 WHERE id=1
            ← creates NEW row version (xmin=T1.xid)
            ← marks OLD row version as deleted by T1 (xmax=T1.xid)

T2 (read):  BEGIN SELECT balance FROM accounts WHERE id=1
            ← reads the OLD row version (T1 hasn't committed yet)
            ← sees balance=1000 (pre-update value)
            ← NOT BLOCKED — reads a consistent past version

T1 commits
T3 (read):  SELECT balance FROM accounts WHERE id=1
            ← sees balance=900 (T1 committed — new version is visible)
```

PostgreSQL's core MVCC guarantee: **readers never block writers, writers never block readers.** The only contention is writer-vs-writer on the same row.

**Q2. What are `xmin`, `xmax`, and `ctid` — PostgreSQL's hidden system columns?**

A: Every row in every PostgreSQL table has hidden system columns that implement MVCC visibility. They are not shown by `SELECT *` but can be accessed explicitly:

```sql
-- Reveal system columns:
SELECT xmin, xmax, ctid, id, name, balance
FROM accounts
WHERE id = 1;

--  xmin | xmax |  ctid  | id |  name   | balance
-- ------+------+--------+----+---------+---------
--   487 |    0 | (0,3)  |  1 | Alice   |  1000
```

**`xmin` — birth transaction:**
The transaction ID (xid) that **created** this row version. A row is visible only if `xmin` committed and that commit is in the reader's visible range. Every INSERT and every UPDATE's new version sets `xmin` to the inserting/updating transaction's xid.

**`xmax` — death transaction:**
The transaction ID that **deleted or superseded** this row version. `0` (or special `InvalidTransactionId`) means the row is not deleted. A row is considered dead when `xmax` is set to a committed transaction's xid. UPDATE sets `xmax` on the old version; DELETE sets `xmax` on the current version.

**`ctid` — physical address:**
The current physical location of the row: `(page_number, item_offset_within_page)`. `(0,3)` means page 0, third slot. `ctid` changes every time a row is updated because the new version is written at a new location. This is how HOT (Heap Only Tuple) chains work — the old version's `ctid` redirects to the new version on the same page.

```sql
-- System columns reveal the full MVCC state:
-- Before any updates:
SELECT xmin, xmax, ctid FROM accounts WHERE id = 1;
-- xmin=487, xmax=0, ctid=(0,3)

-- After UPDATE (in the same transaction, before commit):
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
SELECT xmin, xmax, ctid FROM accounts WHERE id = 1;
-- xmin=501 (current txn), xmax=0, ctid=(0,7)    ← new version

-- The OLD version still exists at (0,3):
-- xmin=487, xmax=501, ctid=(0,3)  ← dead once txn 501 commits
```

## Section 2: Transaction IDs and Snapshots

**Q3. What are transaction IDs and how does PostgreSQL assign them?**

A: A transaction ID (xid) is a 32-bit unsigned integer counter that PostgreSQL increments for every transaction that modifies data. Transaction IDs form the backbone of MVCC visibility — the relationship between an xid and a snapshot's "in-the-past" threshold determines whether a row version is visible.

```sql
-- See the current transaction's xid:
SELECT txid_current();   -- e.g., 7842301

-- See xid without starting a new one (read-only):
SELECT txid_current_if_assigned();  -- NULL for read-only transactions

-- See your current snapshot:
SELECT txid_current_snapshot();
-- 7842289:7842302:7842295,7842301
-- ↑ xmin      ↑ xmax    ↑ xip (in-progress xids)
```

**Critical distinction — when xids are assigned:**
- **Read-only transactions** (no INSERT/UPDATE/DELETE) never receive a permanent xid. They get a "virtual transaction id" (vxid) for lock management only. This is why read-only queries don't accelerate xid exhaustion.
- **Write transactions** receive a permanent xid at their first DML statement (not at `BEGIN`).

```sql
BEGIN;
-- No xid assigned yet:
SELECT txid_current_if_assigned();  -- NULL

-- Now assign an xid:
UPDATE accounts SET balance = 900 WHERE id = 1;
SELECT txid_current_if_assigned();  -- 7842305 (now assigned)
COMMIT;
```

**Transaction ID storage in `pg_xact` (formerly `pg_clog`):**
PostgreSQL maintains a commit log — a bitmap on disk — recording whether each xid committed, rolled back, is in-progress, or sub-transaction committed. When checking visibility, PostgreSQL looks up this bitmap to determine the commit status of `xmin` and `xmax`.

**Q4. What is a "snapshot" in PostgreSQL MVCC and what does it contain?**

A: A snapshot is a point-in-time view of which transactions were active (uncommitted) when the snapshot was taken. It is used to determine which row versions are visible to the transaction that holds the snapshot.

```
Snapshot structure:
{
  xmin:  7842289   — all xids < xmin are definitely in the past (committed or rolled back)
  xmax:  7842302   — all xids >= xmax haven't started yet (definitely invisible)
  xip:   [7842295, 7842301]   — active (uncommitted) transactions between xmin and xmax
}
```

**Visibility determination using the snapshot:**

| xid condition | Meaning | Visible? |
|---|---|---|
| `xid < snapshot.xmin` | Committed before snapshot | Always visible |
| `xid >= snapshot.xmax` | Started after snapshot | Always invisible |
| `xmin ≤ xid < xmax AND xid NOT IN xip` | Committed between xmin and xmax | Visible |
| `xmin ≤ xid < xmax AND xid IN xip` | Was active at snapshot time | Invisible (may not commit) |
| xid is our own transaction | Our own write | Visible to us |

```sql
-- Demonstration: two concurrent transactions with different snapshots

-- Session 1:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT txid_current_snapshot();
-- 7842289:7842292:7842291
-- Interpretation: 7842291 is active, everything < 7842289 is committed

-- Session 2 (runs concurrently):
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;  -- xid = 7842291
COMMIT;

-- Session 1 (still running):
SELECT balance FROM accounts WHERE id = 1;
-- Returns 1000, NOT 500 — 7842291 was in xip (active at snapshot time)
-- Even though 7842291 committed AFTER Session 1 started, it was in-progress
-- when Session 1's snapshot was taken → Session 1 uses the old row version
```

## Section 3: Isolation Levels

**Q5. How do PostgreSQL's isolation levels differ in terms of snapshot timing?**

A: The isolation level controls **when** the snapshot is taken — at the start of the transaction or at the start of each statement. This determines how much change the transaction sees during its lifetime:

```sql
-- READ COMMITTED (PostgreSQL default)
-- ─────────────────────────────────────────────────────────────────────────────
-- Snapshot taken at the start of EACH STATEMENT.
-- Each new SELECT sees all commits that happened before that SELECT started.

BEGIN;  -- No snapshot yet
SELECT balance FROM accounts WHERE id = 1;   -- Snapshot A: sees commits up to now
-- Some other transaction commits a change here
SELECT balance FROM accounts WHERE id = 1;   -- Snapshot B: sees the new commit too!
-- Two identical SELECTs can return different values within the same transaction
COMMIT;

-- REPEATABLE READ
-- ─────────────────────────────────────────────────────────────────────────────
-- Snapshot taken at the start of the FIRST STATEMENT of the transaction.
-- All subsequent statements use the same snapshot.

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- Snapshot taken HERE, returns 1000
-- Other transaction commits balance=500
SELECT balance FROM accounts WHERE id = 1;   -- SAME snapshot: still returns 1000
-- Guaranteed consistent view for the entire transaction
COMMIT;

-- SERIALIZABLE
-- ─────────────────────────────────────────────────────────────────────────────
-- Same snapshot behavior as REPEATABLE READ for reading,
-- but adds SSI (Serializable Snapshot Isolation) tracking for write conflicts.
-- Transactions are aborted if they would produce a non-serializable history.

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;  -- May fail with "ERROR: could not serialize access due to concurrent update"
--                                                ↑ must retry the whole transaction

-- Note: PostgreSQL has no READ UNCOMMITTED isolation level in practice.
-- SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED is accepted but treated as READ COMMITTED.
-- MVCC makes dirty reads mechanically impossible — there's no way to read uncommitted versions.
```

**Q6. What concurrency anomalies exist, which isolation levels prevent them, and how?**

A: The SQL standard defines four anomalies. PostgreSQL's MVCC prevents most of them automatically and its Serializable level prevents all of them:

**Dirty read** — reading uncommitted data from another transaction:
```
T1: UPDATE accounts SET balance=0 WHERE id=1   (not committed)
T2: SELECT balance FROM accounts WHERE id=1    → sees 0  (dirty read)
T1: ROLLBACK → the 0 was a lie
```
```
PostgreSQL prevention: mechanically impossible under MVCC.
Row versions with xmin of an uncommitted transaction are never visible to other
transactions — the xip list in the snapshot ensures this.
Prevented at: ALL levels (including Read Committed)
```

**Non-repeatable read** — two reads of the same row return different values:
```
T1: SELECT balance FROM accounts WHERE id=1  → 1000
T2: UPDATE accounts SET balance=500 WHERE id=1; COMMIT
T1: SELECT balance FROM accounts WHERE id=1  → 500 (different value!)
```
```
PostgreSQL prevention at Read Committed: NOT prevented — each statement re-snapshots.
PostgreSQL prevention at Repeatable Read: PREVENTED — snapshot is fixed at first statement.
```

**Phantom read** — a re-execution of a range query returns new rows inserted by another transaction:
```
T1: SELECT * FROM accounts WHERE balance > 0   → 5 rows
T2: INSERT INTO accounts (id, balance) VALUES (6, 100); COMMIT
T1: SELECT * FROM accounts WHERE balance > 0   → 6 rows (phantom!)
```
```
PostgreSQL prevention: PREVENTED at Repeatable Read and above.
(Note: SQL standard only requires Serializable to prevent phantoms, but
PostgreSQL's snapshot-based approach prevents them at Repeatable Read too —
new rows inserted after the snapshot are invisible because their xmin is >= xmax.)
```

**Write skew** — two transactions each read overlapping data and write non-overlapping data, together violating a constraint:
```
Constraint: total balance across all accounts must stay positive
T1: SELECT SUM(balance) FROM accounts → 100; UPDATE accounts SET balance=0 WHERE id=1
T2: SELECT SUM(balance) FROM accounts → 100; UPDATE accounts SET balance=0 WHERE id=2
Both commit → sum = 0 → violated the constraint (each saw 100, each wrote 0, sum is now 0)
```
```
Not prevented by Read Committed or Repeatable Read — neither transaction wrote
to a row the other wrote to, so there's no write-write conflict to detect.
Prevented at: SERIALIZABLE only (via SSI cycle detection)
```

**Lost update** — a classic race condition where one update overwrites another:
```
T1: SELECT balance FROM accounts WHERE id=1  → 100
T2: SELECT balance FROM accounts WHERE id=1  → 100
T1: UPDATE accounts SET balance = 100 + 50 WHERE id=1  → 150; COMMIT
T2: UPDATE accounts SET balance = 100 + 30 WHERE id=1  → 130; COMMIT
Result: 130 — T1's +50 is lost
```
```
Prevention in PostgreSQL:
- SELECT FOR UPDATE: locks the row; T2 blocks until T1 commits, then re-reads 150
- At Repeatable Read: T2's UPDATE detects that the row changed since its snapshot
  → "ERROR: could not serialize access due to concurrent update" → T2 must retry
- Use atomic UPDATE instead: UPDATE SET balance = balance + 30 WHERE id=1
  → the addition happens inside a single statement — no read-modify-write race
```

## Section 4: DML Operations Under MVCC

**Q7. What happens physically to row versions when you run UPDATE, DELETE, and INSERT?**

A: Each DML operation creates or modifies row versions in the heap — the actual data storage — while leaving old versions intact until VACUUM reclaims them:

```sql
-- Initial state:
-- Table heap (page 0):
-- Slot 1: xmin=100, xmax=0,   name='Alice', balance=1000  ← live row
--         ctid=(0,1)

-- ── INSERT ──────────────────────────────────────────────────────────────────
-- Transaction xid=200:
INSERT INTO accounts (id, name, balance) VALUES (2, 'Bob', 500);

-- Heap after:
-- Slot 1: xmin=100, xmax=0,   name='Alice', balance=1000  ← unchanged
-- Slot 2: xmin=200, xmax=0,   name='Bob',   balance=500   ← new row, invisible until 200 commits

-- ── UPDATE ──────────────────────────────────────────────────────────────────
-- Transaction xid=201:
UPDATE accounts SET balance = 900 WHERE id = 1;

-- Postgres does NOT overwrite Slot 1. It:
-- 1. Marks Slot 1 as "deleted" by 201:
--    Slot 1: xmin=100, xmax=201, name='Alice', balance=1000  ← old version, "dead" after 201 commits
-- 2. Writes a new row version at Slot 3:
--    Slot 3: xmin=201, xmax=0,   name='Alice', balance=900   ← new version

-- Concurrent readers still see Slot 1 (if 201 is in their xip)
-- Readers after 201 commits see Slot 3

-- ── DELETE ──────────────────────────────────────────────────────────────────
-- Transaction xid=202:
DELETE FROM accounts WHERE id = 2;

-- Postgres does NOT remove Slot 2. It:
-- Sets xmax on Slot 2:
-- Slot 2: xmin=200, xmax=202, name='Bob', balance=500  ← "dead" after 202 commits

-- No new row version is created for DELETE.
-- The heap still holds the row until VACUUM removes it.

-- ── ROLLBACK of xid=201 ──────────────────────────────────────────────────────
ROLLBACK;  -- Transaction 201 rolls back

-- Postgres marks 201 as aborted in pg_xact.
-- Slot 1: xmin=100, xmax=201 — but 201 is aborted, so xmax is invalid
--         → Row is STILL LIVE (abort of xmax = row not actually deleted)
-- Slot 3: xmin=201, xmax=0   — but 201 is aborted, so xmin is invalid
--         → Row is DEAD (never became visible; will be cleaned by VACUUM)
```

**Q8. What is a HOT (Heap Only Tuple) update and why does PostgreSQL prefer it?**

A: A regular UPDATE writes a new row version AND adds a new entry to every index covering the table. For a table with 5 indexes, updating one non-indexed column creates 5 new index entries — significant write amplification.

HOT (Heap Only Tuple) eliminates index updates when an update doesn't touch any indexed columns and there's space on the same heap page:

```
Regular UPDATE (updates name — an indexed column):
  Old version:  heap slot (0,1), name='Alice'
  New version:  heap slot (0,3), name='Alicia'
  Index update: every index that covers name gets a new entry pointing to (0,3)
  ─────────────────────────────────────────────────────────────────────────────
  Writes: 1 heap (new version) + N index updates

HOT UPDATE (updates balance — not indexed, same page has space):
  Old version:  heap slot (0,1), balance=1000
                   └─ ctid updated to point forward to (0,2)  ← "HOT chain redirect"
  New version:  heap slot (0,2), balance=900
  Index:        NOT updated — indexes still point to (0,1), which chains to (0,2)
  ─────────────────────────────────────────────────────────────────────────────
  Writes: 1 heap (new version) + 0 index updates

When a query uses the index to find the row:
  Index → (0,1) → [follow HOT chain] → (0,2) → return balance=900
```

**HOT update preconditions** (both must be true):
```sql
-- 1. No indexed column is changed (PostgreSQL checks this per-column)
UPDATE accounts SET balance = 900 WHERE id = 1;
-- OK for HOT if 'balance' is not indexed, 'id' is not changed

UPDATE accounts SET name = 'Alicia' WHERE id = 1;
-- NOT HOT if 'name' is indexed — requires index entry update

-- 2. There is free space on the SAME heap page as the old version
-- fillfactor setting controls how much space is left for HOT:
CREATE TABLE accounts (...) WITH (fillfactor = 70);
-- 30% of each page is left free for future HOT updates
-- Higher fillfactor = less free space = fewer HOT opportunities but less wasted space
```

**Q9. How does `SELECT FOR UPDATE` interact with MVCC, and when does it block?**

A: `SELECT FOR UPDATE` (and `SELECT FOR SHARE`) step outside pure MVCC and acquire actual row-level locks. The reason: MVCC alone cannot prevent lost updates in a read-then-write pattern.

```sql
-- Pattern that requires SELECT FOR UPDATE:
BEGIN;
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;
-- PostgreSQL:
-- 1. Finds the visible row version using MVCC (snapshot visibility)
-- 2. Checks if the row is currently locked by another transaction
-- 3. If locked: WAITS for the lock to release (blocking)
-- 4. Once acquired: re-checks the row's current version (in case it changed while waiting)
-- 5. Returns the row AND holds an exclusive lock until COMMIT/ROLLBACK

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- Lock released here

-- What happens when two sessions race:
-- T1: SELECT balance FROM accounts WHERE id=1 FOR UPDATE → gets lock, sees 1000
-- T2: SELECT balance FROM accounts WHERE id=1 FOR UPDATE → BLOCKS (T1 holds lock)
-- T1: UPDATE ... SET balance = 900; COMMIT → releases lock
-- T2: Unblocks, re-reads the ROW (not its cached 1000 value!) → sees 900
-- T2: UPDATE ... SET balance = 800; COMMIT
-- Correct: no lost update (serial execution: 1000 → 900 → 800)

-- Without FOR UPDATE:
-- T1: SELECT balance → 1000
-- T2: SELECT balance → 1000 (both read at same time via MVCC)
-- T1: UPDATE SET balance = 900; COMMIT
-- T2: UPDATE SET balance = 1000 + (-200) = 800... wait, T2 read 1000
--     T2: UPDATE SET balance = 900; COMMIT  ← T1's -100 is lost
```

**`SKIP LOCKED` — non-blocking alternative:**
```sql
-- Job queue pattern: pick a job nobody else is working on
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Skips rows locked by other transactions instead of waiting
-- Perfect for worker pools where any job is acceptable
```

## Section 5: Dead Tuples and VACUUM

**Q10. What are dead tuples, why do they accumulate, and what prevents their immediate removal?**

A: A dead tuple is a row version whose `xmax` has committed — meaning the row was deleted or updated — and which is therefore no longer visible to any future transaction. However, PostgreSQL cannot immediately remove a dead tuple because it might still be **visible to currently active transactions** whose snapshots predate the deletion:

```
Timeline:
  xid=500 commits: UPDATE accounts SET balance=900 WHERE id=1
                   → Old version (xmax=500) is now "dead"
                   → New version (xmin=500) is live

  But: Transaction xid=490 started before 500 and is STILL RUNNING.
       Its snapshot sees 500 as "in the past" (xip was empty when it started).
       Wait, let me redo:

  Let's say at the time of 490's snapshot:
    xmin=485, xmax=491, xip=[]
  So 490's snapshot sees all xids < 491 as committed/rolled back.
  xid=500 hasn't happened yet from 490's perspective.

  490's snapshot sees: xmax=500 is NOT YET committed (500 > 491 = 490's xmax)
  → 490 still needs the OLD row version (xmin=485, xmax=500 → xmax invisible to 490)
  → The old version must NOT be removed

  VACUUM cannot remove the old version until:
  - xid=490 commits or rolls back AND
  - No other active transaction has a snapshot that predates xid=500's commit

The "xmin horizon":
  The oldest snapshot's xmin value is the horizon.
  VACUUM can only remove dead tuples with xmax < the xmin horizon.
  Any dead tuple from a transaction newer than the horizon must be preserved.
```

```sql
-- See how much dead tuple bloat exists:
SELECT
  schemaname,
  relname,
  n_live_tup,
  n_dead_tup,
  round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
  last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

-- A table with 1M live rows and 500K dead rows is 33% bloated
-- Each dead tuple wastes ~50–500 bytes of heap space (size of the row)
-- This reduces cache efficiency and forces sequential scans over more pages
```

**Q11. What does VACUUM do and how does it differ from VACUUM FULL?**

A: VACUUM reclaims space occupied by dead tuples so PostgreSQL can reuse it for new rows. It does NOT return space to the operating system — it merely marks pages as available for future inserts within the same table.

```sql
-- Regular VACUUM:
VACUUM accounts;
-- Scans the table for dead tuples
-- Marks their space as reusable (sets page visibility map bits)
-- Does NOT lock the table for reads/writes — concurrent access is allowed
-- Does NOT shrink the file on disk — frees pages for PostgreSQL reuse only
-- Updates pg_class.reltuples (approximate row count)
-- Updates visibility map (used by index-only scans)
-- Freezes old tuples if they approach wraparound age

VACUUM VERBOSE accounts;
-- Same as above but prints progress:
-- INFO:  vacuuming "public.accounts"
-- INFO:  scanned index "accounts_pkey" to remove 15000 row versions
-- INFO:  "accounts": removed 15000 row versions in 120 pages
-- INFO:  "accounts": found 15000 removable, 50000 nonremovable row versions

-- VACUUM FULL:
VACUUM FULL accounts;
-- Acquires an EXCLUSIVE LOCK on the table (all reads/writes blocked!)
-- Rewrites the entire table into a new file, compacting live rows together
-- DOES return space to the OS (file shrinks)
-- Much slower — avoid in production during peak hours
-- Use when a table has extreme bloat (>50% dead) and you can afford the downtime
-- After VACUUM FULL, REINDEX may be needed to compact indexes too

-- ANALYZE:
ANALYZE accounts;
-- Samples the table to update query planner statistics (pg_statistic)
-- Not related to dead tuple cleanup but often run together: VACUUM ANALYZE

-- VACUUM ANALYZE (common combination):
VACUUM ANALYZE accounts;
```

**autovacuum:**
```sql
-- PostgreSQL runs autovacuum automatically based on thresholds:
-- autovacuum triggers when:
--   n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup
-- Defaults: threshold=50, scale_factor=0.2 (20% dead → trigger)

-- Per-table tuning for high-write tables:
ALTER TABLE accounts SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- Trigger at 1% dead (not 20%)
  autovacuum_vacuum_threshold    = 100    -- Minimum 100 dead tuples to trigger
);

-- Monitor autovacuum activity:
SELECT relname, last_autovacuum, last_autoanalyze, autovacuum_count
FROM pg_stat_user_tables
WHERE last_autovacuum > NOW() - INTERVAL '1 hour'
ORDER BY last_autovacuum DESC;
```

**Q12. How do long-running transactions prevent VACUUM and cause table bloat?**

A: VACUUM can only remove dead tuples that are older than the oldest active snapshot's xmin — called the "relfrozenxid horizon" or "xmin horizon." A single long-running transaction freezes this horizon and prevents cleanup of ALL dead tuples created since that transaction started:

```
Timeline:
  t=0h:  Transaction A starts (xid=1000). Snapshot taken.
         A's snapshot xmin ≈ 998 (approximation)

  t=0h:  Your app is running normally:
         1000 UPDATEs per minute → 1000 dead tuples/min

  t=3h:  Transaction A is still running (idle in transaction, forgotten!)
         180,000 dead tuples have accumulated
         VACUUM runs but can only clean tuples where xmax < 998
         → The 180,000 new dead tuples (xmax ≥ 1000) CANNOT be cleaned

  t=6h:  360,000 dead tuples. Table has doubled in size on disk.
         Queries scan 2× more pages. Cache hit rate drops. Query times increase.

  t=6h:  Transaction A finally ends (or killed by idle_in_transaction_session_timeout)
         VACUUM can now clean all 360,000 dead tuples

  t=6h+: Table size shrinks... but only internally (pages marked free).
         File on disk remains large until VACUUM FULL or pg_repack.
```

```sql
-- Monitor long-running transactions — the most important production MVCC query:
SELECT
  pid,
  usename,
  application_name,
  state,
  now() - xact_start    AS transaction_age,
  now() - query_start   AS query_age,
  left(query, 80)       AS current_query
FROM pg_stat_activity
WHERE state != 'idle'
  AND xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 20;

-- Kill a transaction that's causing problems:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE xact_start < now() - INTERVAL '1 hour'
  AND state = 'idle in transaction';

-- Prevent idle-in-transaction from hanging indefinitely:
-- postgresql.conf:
idle_in_transaction_session_timeout = '5min'
-- Any transaction idle in transaction for 5 min is automatically terminated
-- This is the single most impactful config for preventing bloat in OLTP apps

-- Check the current xmin horizon (what VACUUM can see):
SELECT
  backend_xmin,
  pg_xact_commit_timestamp(backend_xmin) AS xmin_started,
  now() - pg_xact_commit_timestamp(backend_xmin) AS xmin_age
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY backend_xmin
LIMIT 5;
```

## Section 6: Transaction ID Wraparound

**Q13. What is transaction ID wraparound and why is it potentially catastrophic?**

A: PostgreSQL's transaction ID counter is a 32-bit integer — it can hold approximately 4 billion values (2³²). PostgreSQL uses modular arithmetic: a transaction "in the past" is one whose xid is within 2³¹ (about 2.1 billion) steps behind the current xid. A transaction "in the future" is one more than 2³¹ steps ahead.

**The wraparound danger:**
```
Current xid: 2,100,000,000
Row with xmin=1 (very old committed row)

Normal view: xid=1 is 2,100,000,000 steps in the past → visible ✓

xid counter reaches: 4,200,000,000
Now: xid=1 is exactly 2,100,000,000 steps in the past → still visible ✓

xid counter wraps around to: 1 (modular arithmetic: 4,294,967,296 → 0 → 1)
New current xid: 3
Now from the new current xid=3's perspective:
  xid=1 is 2 steps in the past → visible ✓

But as the new counter approaches 2,100,000,000 again:
Current xid: 2,100,000,001
  xid=1 is 2,100,000,000 steps in the FUTURE (across the wraparound boundary)
  → xid=1 is treated as an uncommitted or invisible future transaction
  → EVERY row with xmin=1 (very old rows) becomes invisible
  → The database cannot see its own data — catastrophic data loss
```

```sql
-- PostgreSQL actually shuts down before this happens:
-- WARNING at age > 10 million from autovacuum_freeze_max_age
-- ERROR: database is not accepting commands to avoid wraparound

-- Monitor wraparound risk:
SELECT
  datname,
  age(datfrozenxid)          AS database_age,
  2147483647 - age(datfrozenxid) AS transactions_until_wraparound
FROM pg_database
ORDER BY age(datfrozenxid) DESC;

-- Per-table risk:
SELECT
  relname,
  age(relfrozenxid)          AS table_age,
  2147483647 - age(relfrozenxid) AS transactions_until_wraparound
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 10;

-- Rule of thumb: if age > 1.5 billion → investigate immediately
--               if age > 2.0 billion → EMERGENCY
```

**Q14. How does VACUUM FREEZE protect against transaction ID wraparound?**

A: VACUUM FREEZE replaces the actual transaction ID in `xmin` with a special constant called `FrozenTransactionId` (value 2). A frozen row is always visible to all transactions — no xid comparison is needed. This permanently removes the row from wraparound risk:

```sql
-- Before freeze: row has actual xmin
-- xmin=500, xmax=0 → visible if 500 is in your visible past range

-- After VACUUM FREEZE:
-- xmin=2 (FrozenTransactionId), xmax=0 → ALWAYS visible, regardless of current xid
-- The row is "detached" from the xid counter — it can never become invisible

-- Freeze thresholds (postgresql.conf):
vacuum_freeze_min_age      = 50000000   -- Don't freeze rows younger than 50M transactions
vacuum_freeze_table_age    = 150000000  -- Force full-table freeze scan at this age
autovacuum_freeze_max_age  = 200000000  -- autovacuum triggers BEFORE this age

-- Sequence:
-- age < 50M:    Row too new to freeze (might need its xmin for visibility logic)
-- 50M < age < 150M: Row eligible to freeze if VACUUM scans that page anyway
-- age > 150M:   Force a full-table scan to freeze everything
-- age > 200M:   autovacuum urgently triggers even on tables below normal vacuum threshold
-- age > 2.1B:   PostgreSQL refuses new connections to protect data integrity

-- Manual freeze (useful before expected high-volume periods):
VACUUM FREEZE accounts;

-- After freeze, check frozen status:
SELECT relfrozenxid, age(relfrozenxid) FROM pg_class WHERE relname = 'accounts';
-- relfrozenxid=7842305 means all rows with xmin <= 7842305 are frozen
-- age tells you how many transactions ago the last freeze happened

-- pg_visibility extension — check per-page freeze status:
SELECT * FROM pg_visibility('accounts') WHERE all_frozen = false LIMIT 10;
-- Pages where not all rows are frozen (candidates for freeze vacuum)
```

## Section 7: Serializable Snapshot Isolation

**Q15. How does PostgreSQL's Serializable isolation level work beyond snapshot isolation?**

A: Snapshot isolation (what Repeatable Read provides) prevents most anomalies but not write skew. Write skew happens when two transactions read overlapping data and write non-overlapping data such that their combined effect is impossible in any serial execution.

PostgreSQL implements SSI (Serializable Snapshot Isolation) using **predicate locks** — locks on the data you READ, not just the data you write. SSI detects cycles in the "dependency graph" between concurrent transactions:

```sql
-- Classic write skew scenario (doctors on-call):
-- Constraint: at least one doctor must be on call at all times
-- Table: doctors(name, on_call BOOLEAN)
-- Current state: Alice=true, Bob=true

-- T1 (Alice going off call):
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- reads: 2 doctors on call
-- T1 decides: safe to go off call (2 > 1)

-- T2 (Bob going off call), concurrent with T1:
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- reads: 2 doctors on call
-- T2 decides: safe to go off call (2 > 1)

-- T1 writes:
UPDATE doctors SET on_call = false WHERE name = 'Alice';
COMMIT;  -- succeeds

-- T2 writes:
UPDATE doctors SET on_call = false WHERE name = 'Bob';
COMMIT;
-- ERROR:  could not serialize access due to concurrent update
-- DETAIL: Process 1234 updated a row.
-- SQLSTATE: 40001  ← serialization failure

-- T2 must RETRY the entire transaction.
-- On retry, T2 reads COUNT(*) → 1 (Alice is now off call) → decides NOT to go off call.
-- Constraint preserved.
```

**How SSI detects the cycle:**
```
SSI tracks three types of dependencies between concurrent transactions:
  rw-dependency (T1 reads what T2 later wrote): T1 → T2
  ww-dependency (T2 overwrites what T1 wrote): T1 → T2

A serialization anomaly exists when a cycle forms:
  T1 --rw--> T2 --rw--> T1   (T1 read T2's write target; T2 read T1's write target)

In the doctors example:
  T1 reads on_call (the SET T2 writes to) → T1 -rw→ T2
  T2 reads on_call (the SET T1 writes to) → T2 -rw→ T1
  Cycle detected → one transaction aborted (T2 in this case)

PostgreSQL tracks these dependencies via "siread locks" (SIRead locks):
  - Taken on index pages or heap pages when you read them under Serializable
  - Compared against write locks taken by concurrent transactions
  - When a dangerous cycle is detected, the later-committing transaction is aborted
```

```sql
-- Application must handle serialization failures:
async function transferDoctorCall(name: string): Promise<void> {
  for (let attempt = 0; attempt < 3; attempt++) {
    try {
      await db.transaction('SERIALIZABLE', async (trx) => {
        const count = await trx.raw(
          'SELECT COUNT(*) FROM doctors WHERE on_call = true'
        );
        if (count.rows[0].count <= 1) {
          throw new Error('Cannot go off call — only doctor on call');
        }
        await trx.raw(
          'UPDATE doctors SET on_call = false WHERE name = ?', [name]
        );
      });
      return;  // Success
    } catch (err) {
      if (err.code === '40001' && attempt < 2) {
        // Serialization failure — retry
        await sleep(Math.random() * 100);  // Random backoff
        continue;
      }
      throw err;  // Non-retryable error or too many retries
    }
  }
}
```

## Section 8: Production Monitoring

**Q16. How do you monitor MVCC health in production PostgreSQL?**

A:

```sql
-- ── 1. Dead tuple bloat (most common MVCC issue) ─────────────────────────────
SELECT
  schemaname || '.' || relname                     AS table,
  pg_size_pretty(pg_total_relation_size(relid))    AS total_size,
  n_live_tup,
  n_dead_tup,
  round(n_dead_tup::numeric /
    NULLIF(n_live_tup + n_dead_tup, 0) * 100, 1)  AS dead_pct,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;

-- ── 2. Long-running transactions (the primary bloat cause) ───────────────────
SELECT
  pid,
  usename,
  application_name,
  state,
  now() - xact_start   AS txn_age,
  wait_event_type,
  wait_event,
  left(query, 100)     AS query_preview
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND state != 'idle'
ORDER BY xact_start
LIMIT 20;

-- ── 3. Wraparound risk (run this in a monitoring script daily) ────────────────
SELECT
  datname,
  age(datfrozenxid)                             AS age,
  ROUND(age(datfrozenxid)::numeric / 2147483647 * 100, 1) AS pct_to_wraparound
FROM pg_database
ORDER BY age DESC;
-- Alert when pct_to_wraparound > 50%
-- EMERGENCY when pct_to_wraparound > 80%

SELECT
  relname,
  age(relfrozenxid)                             AS age,
  pg_size_pretty(pg_relation_size(oid))         AS table_size
FROM pg_class
WHERE relkind = 'r'
  AND age(relfrozenxid) > 100000000   -- Tables > 100M transactions old
ORDER BY age DESC;

-- ── 4. Active locks (concurrent write contention) ────────────────────────────
SELECT
  COALESCE(relation::regclass::text, 'N/A') AS table,
  locktype,
  mode,
  granted,
  pid,
  now() - a.xact_start                     AS lock_age,
  left(a.query, 80)                         AS query
FROM pg_locks l
LEFT JOIN pg_stat_activity a ON a.pid = l.pid
WHERE NOT granted                           -- Show blocked locks
ORDER BY lock_age DESC;

-- Find the blocking session:
SELECT
  blocked.pid                             AS blocked_pid,
  blocking.pid                            AS blocking_pid,
  left(blocked_activity.query, 80)        AS blocked_query,
  left(blocking_activity.query, 80)       AS blocking_query,
  now() - blocked_activity.xact_start    AS blocked_age
FROM pg_locks AS blocked
JOIN pg_locks AS blocking
  ON blocking.transactionid = blocked.transactionid
  AND blocking.pid != blocked.pid
  AND NOT blocked.granted
JOIN pg_stat_activity AS blocked_activity  ON blocked_activity.pid  = blocked.pid
JOIN pg_stat_activity AS blocking_activity ON blocking_activity.pid = blocking.pid;

-- ── 5. autovacuum effectiveness ────────────────────────────────────────────────
SELECT
  relname,
  autovacuum_count,
  autoanalyze_count,
  last_autovacuum,
  last_autoanalyze,
  n_dead_tup,
  n_mod_since_analyze
FROM pg_stat_user_tables
WHERE last_autovacuum < now() - INTERVAL '24 hours'
  AND n_dead_tup > 1000
ORDER BY n_dead_tup DESC;
-- Tables with many dead tuples and no recent autovacuum may need manual VACUUM
-- or adjusted per-table autovacuum thresholds
```

## Section 9: Scenario-Based Questions

**Q17. "Trace the exact xmin/xmax changes through a concurrent read-write scenario."**

```sql
-- Setup:
CREATE TABLE balances (id INT PRIMARY KEY, amount NUMERIC);
INSERT INTO balances VALUES (1, 1000);  -- Committed by xid=500

-- Initial heap state:
-- Slot (0,1): xmin=500, xmax=0, id=1, amount=1000

-- Now two concurrent sessions:

-- Session A (xid=600):
BEGIN;
UPDATE balances SET amount = 900 WHERE id = 1;
-- BEFORE COMMIT:
```

A: Tracing each step:

```
Step 1: Session A (xid=600) starts UPDATE
─────────────────────────────────────────
PostgreSQL:
  a) Finds current visible version of row id=1:
     Slot (0,1): xmin=500, xmax=0 → xmin=500 is committed, xmax=0 → VISIBLE
  b) Creates a new row version:
     Slot (0,2): xmin=600, xmax=0, id=1, amount=900   ← new version (invisible to others; 600 not committed)
  c) Updates old version's xmax:
     Slot (0,1): xmin=500, xmax=600, id=1, amount=1000  ← marked "deleted" by 600

Heap state now:
  (0,1): xmin=500, xmax=600, amount=1000   ← old version
  (0,2): xmin=600, xmax=0,   amount=900    ← new version (600 not yet committed)

Step 2: Session B starts a SELECT (Read Committed)
─────────────────────────────────────────────────────
Session B snapshot: xmin=598, xmax=601, xip=[600]
(xid=600 is in xip — Session A is active)

Session B evaluates Slot (0,1):
  xmin=500 < xmin_snapshot=598 → xmin is in the past → xmin is visible
  xmax=600 is in xip → xmax is active (not committed) → xmax is NOT a completed deletion
  → Row is LIVE from B's perspective → B reads amount=1000

Session B evaluates Slot (0,2):
  xmin=600 is in xip → xmin is active → NOT visible (we don't see uncommitted writes)
  → Row is invisible

B sees: amount=1000  ← reads the old version, not blocked

Step 3: Session A commits (xid=600 now in pg_xact as COMMITTED)
────────────────────────────────────────────────────────────────
pg_xact[600] = COMMITTED

Step 4: Session B issues another SELECT (Read Committed — new snapshot)
──────────────────────────────────────────────────────────────────────
Session B takes NEW snapshot: xmin=598, xmax=601, xip=[]  ← 600 is NO LONGER in xip

Session B evaluates Slot (0,1):
  xmin=500 → visible
  xmax=600 → is xid=600 committed? YES (pg_xact) and 600 < xmax=601 and 600 NOT in xip
  → xmax is a completed deletion → row IS DEAD → SKIP

Session B evaluates Slot (0,2):
  xmin=600 < xmax=601 and NOT in xip and pg_xact[600]=COMMITTED → VISIBLE
  xmax=0 → not deleted
  → Row is LIVE

B sees: amount=900  ← now sees Session A's committed write

Under REPEATABLE READ: Session B would use the SAME snapshot from Step 2
  → B would ALWAYS see amount=1000 (600 in xip in original snapshot)
  → Even after A commits, B's snapshot still has 600 in xip → old version visible
  → B never sees the update within this transaction

Step 5: VACUUM eventually runs
───────────────────────────────
After ALL active snapshots that started before A's commit are gone:
  Slot (0,1): xmax=600, committed → DEAD, safe to remove
  VACUUM removes Slot (0,1): heap space reclaimed for future rows
  Slot (0,2) remains as the live version

Final heap state:
  (0,2): xmin=600, xmax=0, id=1, amount=900   ← only the live version remains
```

**Q18. "Why did this production query suddenly start taking 10 seconds when it used to take 10ms?"**

```sql
-- Query (runs fine normally, suddenly slow):
SELECT * FROM events WHERE user_id = 123 ORDER BY created_at DESC LIMIT 10;
-- Normally: 10ms (index scan)
-- Suddenly: 10 seconds (sequential scan)

EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 123 ORDER BY created_at DESC LIMIT 10;
-- Seq Scan on events (cost=0.00..892341.00 rows=1000000)  ← FULL TABLE SCAN!
-- Filter: (user_id = 123)
-- Rows Removed by Filter: 4999990
```

A: The planner switched from an index scan to a sequential scan — the most common cause after a long-running transaction causes massive table bloat:

```
Diagnosis step-by-step:

1. Check for long-running transactions:
   SELECT pid, now()-xact_start AS age, query FROM pg_stat_activity
   WHERE state != 'idle' AND xact_start IS NOT NULL ORDER BY xact_start;
   ─────────────────────────────────────────────────────
   Result: pid=5432 has been running for 9 HOURS (idle in transaction)

2. Check dead tuple accumulation:
   SELECT relname, n_live_tup, n_dead_tup, pg_size_pretty(pg_total_relation_size('events'))
   FROM pg_stat_user_tables WHERE relname = 'events';
   ─────────────────────────────────────────────────────
   n_live_tup:  500,000 (half million real rows)
   n_dead_tup:  4,500,000 (nine times as many dead rows!)
   size:        2.4 GB (expected ~200 MB)

3. Root cause chain:
   - events table has 1000 UPDATEs/min (status changes on events)
   - Each UPDATE creates a dead tuple
   - Over 9 hours: 9×60×1000 = 540,000 dead tuples added
   - Long-running transaction (pid=5432) prevents VACUUM from cleaning any of them
   - Table grew from 200MB to 2.4GB (mostly dead tuples)
   - Table statistics still say 500,000 rows
   - But the table file is now 2.4GB
   - Planner estimates: seq scan (read 2.4GB) vs index scan (500K rows × jump to heap)
   - At this bloat ratio, planner incorrectly prefers seq scan

4. Immediate fixes:
   -- Kill the blocking transaction:
   SELECT pg_terminate_backend(5432);

   -- Run VACUUM to clean dead tuples:
   VACUUM ANALYZE events;

   -- Verify:
   SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables WHERE relname='events';
   -- n_dead_tup should drop dramatically

   -- Query returns to 10ms:
   EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 123 ORDER BY created_at DESC LIMIT 10;
   -- Index Scan using idx_events_user_created on events  ← back to index scan

5. Permanent fix:
   -- Prevent idle-in-transaction sessions:
   ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
   SELECT pg_reload_conf();

   -- Tune autovacuum for this high-write table:
   ALTER TABLE events SET (
     autovacuum_vacuum_scale_factor  = 0.01,   -- Trigger at 1% dead (not 20%)
     autovacuum_vacuum_cost_delay    = 2,       -- Faster vacuum (less IO throttling)
     autovacuum_vacuum_cost_limit    = 400      -- More vacuum work per cycle
   );
```

**Q19. "Explain what happens when two transactions concurrently UPDATE the same row."**

A: The outcome depends on isolation level and commit order. This is the "first updater wins" rule:

```
Concurrent UPDATE scenario:
  Row: id=1, balance=1000, xmin=100, xmax=0

T1 (xid=200): UPDATE balances SET balance=900 WHERE id=1
T2 (xid=201): UPDATE balances SET balance=850 WHERE id=1

Both start simultaneously.

Case A: T1 commits before T2 tries to UPDATE:
─────────────────────────────────────────────
T1: Creates new version (xmin=200, balance=900), marks old xmax=200
T1: COMMITS

T2 tries to UPDATE:
  Under READ COMMITTED:
    T2 finds the current version (xmin=200, balance=900) — T1 committed, so T2 sees it
    T2 waits for T1's row lock... T1 already committed, no lock to wait for
    T2 re-evaluates WHERE id=1 on the NEW version → still matches
    T2 creates newer version (xmin=201, balance=850), marks T1's version xmax=201
    T2 COMMITS
    Result: balance=850 (T2's update applied on T1's committed value — correct)

  Under REPEATABLE READ:
    T2's snapshot was taken before T1 committed (T1 was in T2's xip)
    T2 tries to UPDATE: PostgreSQL detects that the row was updated by a committed
    transaction (T1) that is NOT visible in T2's snapshot
    → ERROR: could not serialize access due to concurrent update
    T2 must ROLLBACK and RETRY the entire transaction
    On retry: T2's new snapshot sees T1's committed version → applies correctly

Case B: T1 and T2 BOTH try to UPDATE before either commits:
──────────────────────────────────────────────────────────────
T1: Finds row, creates new version (xmin=200), marks old xmax=200, holds row lock
T2: Tries to UPDATE the same row (where id=1)
    → Row is currently locked by T1 (xmax=200 is in-progress)
    → T2 BLOCKS — waits for T1's lock to release

T1 COMMITS:
  T2 unblocks.
  T2 re-evaluates:
    Under READ COMMITTED: T2 sees T1's new version (balance=900), applies UPDATE → balance=850
    Under REPEATABLE READ: T2's snapshot predates T1's commit → SERIALIZATION ERROR → ROLLBACK

T1 ROLLS BACK:
  T2 unblocks.
  T2 re-evaluates:
    The original row version (xmin=100, xmax=200, xmax=200 now ABORTED) → still live!
    T2 applies UPDATE on the original version → balance=850
    T2 COMMITS: Result: balance=850 (T1's partial work discarded; T2 succeeded)
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **MVCC core guarantee** | Readers never block writers; writers never block readers — only writer-vs-writer on the same row contends |
| **`xmin`** | Transaction ID that created this row version — set on INSERT and UPDATE (new version) |
| **`xmax`** | Transaction ID that deleted this row version — set on DELETE and UPDATE (old version); 0 = not deleted |
| **`ctid`** | Physical location `(page, slot)` — changes on every UPDATE; used to follow HOT chains |
| **Snapshot** | `{xmin, xmax, xip}` — xids < xmin are in the past; xids >= xmax are in the future; xip = active |
| **Visibility rule** | Row visible if: xmin committed AND in past, AND (xmax=0 OR xmax not committed OR xmax in future) |
| **Read Committed** | New snapshot per statement — two identical SELECTs in one txn can return different values |
| **Repeatable Read** | Snapshot fixed at first statement — consistent view for entire transaction; prevents phantoms too |
| **Serializable (SSI)** | Same as Repeatable Read + predicate locks + cycle detection — prevents write skew; may abort transactions |
| **Dirty read** | Prevented at ALL levels by MVCC — uncommitted xmin values are never visible to other transactions |
| **Write skew** | Only prevented by Serializable — two transactions read overlapping data, write non-overlapping data |
| **UPDATE mechanics** | Creates new row version (xmin=txid), marks old version with xmax=txid — old version not overwritten |
| **DELETE mechanics** | Sets xmax on current version — no new version created; physical row remains until VACUUM |
| **HOT update** | New version on same page + no indexed column changed → index NOT updated; saves write amplification |
| **Dead tuple** | Row version where xmax is committed — no longer visible to any future snapshot |
| **VACUUM** | Reclaims dead tuple space (marks pages free); does NOT shrink file on disk |
| **VACUUM FULL** | Rewrites table file, returns space to OS; requires EXCLUSIVE lock — avoid in production peak hours |
| **xmin horizon** | Oldest snapshot's xmin across all active transactions — VACUUM cannot clean dead tuples newer than this |
| **`idle_in_transaction_session_timeout`** | Most important MVCC config — kills transactions idle in BEGIN state; prevents bloat accumulation |
| **Transaction ID wraparound** | 32-bit xid counter; at ~2.1B past xids, old rows appear "in the future" and become invisible |
| **FrozenTransactionId** | Special xmin value 2 — row is always visible; set by VACUUM FREEZE to protect against wraparound |
| **`autovacuum_freeze_max_age`** | Default 200M — autovacuum urgently runs freeze scan before table age exceeds this |
| **Serialization failure (40001)** | Application must catch this SQLSTATE and retry the entire transaction from the beginning |
| **`SELECT FOR UPDATE`** | Acquires row-level exclusive lock — readers under MVCC are not blocked but other writers wait |
| **`SKIP LOCKED`** | `SELECT FOR UPDATE SKIP LOCKED` — skips locked rows instead of blocking; ideal for job queues |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining **why MVCC means "readers never block writers" with precision** — not just reciting the slogan but tracing through `xmin`/`xmax` to show that a reader sees the old row version with `xmax=in-progress-txn` (where the xmax txid is in the reader's `xip` list) while the writer creates a new version; being able to draw the "two slots on the heap" picture for a concurrent UPDATE distinguishes mechanical understanding from surface knowledge; (2) the **snapshot structure** — knowing that a snapshot is `{xmin, xmax, xip}` and being able to determine visibility from first principles: xids < xmin are always in the past, xids >= xmax are always invisible, and xids in xip were active (uncommitted) at snapshot time; (3) **why long-running transactions cause table bloat** — connecting the xmin horizon to VACUUM's inability to clean dead tuples: a transaction that started 6 hours ago holds the xmin horizon at its start time, which prevents all 6 hours of dead tuples from being cleaned, causing the table to grow until the transaction ends; knowing that `idle_in_transaction_session_timeout` is the fix; (4) the **transaction ID wraparound** as PostgreSQL's most catastrophic failure mode — a 32-bit counter that, if allowed to lap itself, makes ancient rows appear to be "in the future" and invisible; that VACUUM FREEZE replaces real xid values with `FrozenTransactionId` (value 2) to permanently mark rows as always-visible; and that monitoring `age(relfrozenxid)` against the 2-billion threshold is a mandatory production health check; and (5) the **HOT update optimization** — why updates to non-indexed columns on pages with free space avoid index updates entirely, and why setting `fillfactor=70` on high-update tables deliberately leaves 30% of each page empty to enable HOT chains, trading space for dramatically reduced write amplification.
