# Connection Pooling: PgBouncer — Session vs Transaction vs Statement Mode
## Interview Q&A (5 YOE Level)

---

## Section 1: Why Connection Pooling Exists

**Q1. What is the cost of a PostgreSQL connection — why does connection pooling matter at scale?**

A: Every PostgreSQL connection is a heavyweight operating-system resource. Understanding the exact cost of each connection explains why pooling is not optional at scale — it is architectural necessity:

```
PostgreSQL connection lifecycle (without pooling):

  Application server             PostgreSQL server
  ┌─────────────────┐            ┌─────────────────────────────────────────┐
  │  Request comes  │──TCP SYN──►│                                         │
  │  in             │◄──TCP SYN──│  Fork a new OS process (~5 MB RAM)      │
  │                 │──────────►│  Authenticate (SSL handshake if TLS)     │
  │                 │◄──────────│  Load pg_hba.conf rules                  │
  │                 │           │  Allocate shared memory segment           │
  │                 │           │  Load session parameters                 │
  │  Runs query     │──SQL─────►│                                         │
  │                 │◄──result──│  Execute                                 │
  │  Request ends   │──FIN─────►│                                         │
  │                 │           │  Destroy process (~2-5 ms cleanup)       │
  └─────────────────┘            └─────────────────────────────────────────┘

Per-connection costs:
  • RAM:         5–10 MB per backend process (shared_buffers excluded)
  • CPU:         fork() system call + authentication = 1–5 ms per new connection
  • File desc:   ~10 file descriptors per backend
  • Semaphores:  for lock management
  • WAL writer:  coordination overhead scales with connection count
```

```sql
-- ── Measuring connection overhead ─────────────────────────────────────────────
-- Current connections and their memory:
SELECT
    COUNT(*)                              AS total_connections,
    COUNT(*) FILTER (WHERE state = 'active') AS active,
    COUNT(*) FILTER (WHERE state = 'idle')   AS idle,
    COUNT(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_tx
FROM   pg_stat_activity
WHERE  datname = current_database();

-- Memory used by backend processes (Linux):
SELECT
    pid,
    usename,
    application_name,
    state,
    ROUND(rss / 1024.0, 1) AS rss_mb  -- Resident set size in MB
FROM   pg_stat_activity
JOIN   (
    SELECT pid,
           CAST(split_part(pg_read_file('/proc/' || pid || '/status', 0, 4096),
           E'\nVmRSS:\t', 2) AS TEXT) AS rss
    FROM pg_stat_activity WHERE pid <> pg_backend_pid()
) mem USING (pid)
WHERE  datname = current_database();
-- Typical result: each backend uses 5–12 MB RSS.

-- max_connections (hard limit — PostgreSQL refuses connections above this):
SHOW max_connections;  -- Default: 100

-- At 500 connections, PostgreSQL uses:
-- 500 × 8 MB = 4 GB RAM just for backend processes
-- Plus contention on internal shared memory structures (proc arrays, lock tables)
-- Performance degrades noticeably above ~200 active connections.

-- ── What happens without pooling: the "connection storm" ─────────────────────
-- Application with 50 servers × 20 threads = 1,000 concurrent connections.
-- PostgreSQL default max_connections = 100.
-- Result:
--   • Connections beyond 100: FATAL: sorry, too many clients already
--   • Under peak load: all 100 slots busy → queuing at TCP level
--   • Spiky traffic: connection setup latency adds 2–5 ms per request
--   • Idle connections: hold RAM, wake up periodically → wasted resources

-- ── Connection pooling: the solution ─────────────────────────────────────────
-- PgBouncer sits between the application and PostgreSQL:
--
--  App server 1 ──┐
--  App server 2 ──┤   ┌─────────────┐   (small pool)   ┌──────────────┐
--  App server 3 ──┼──►│  PgBouncer  │──────10 conns────►│  PostgreSQL  │
--  App server 4 ──┤   └─────────────┘                   └──────────────┘
--  App server 5 ──┘
--
-- 500 app connections → PgBouncer → 10 PostgreSQL connections.
-- PgBouncer queues and multiplexes: app sees instant response, PG sees steady load.
```

**Q2. What is PgBouncer and how does it work architecturally?**

A: PgBouncer is a lightweight, single-process connection pooler. It speaks the PostgreSQL wire protocol on both sides — the application thinks it is talking to PostgreSQL; PostgreSQL thinks PgBouncer is a client. The multiplexing happens entirely in PgBouncer's event loop:

```
PgBouncer internal architecture:

  ┌──────────────────────────────────────────────────────────────────┐
  │                        PgBouncer process                         │
  │                                                                  │
  │  Client connections (from apps):                                 │
  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ... (thousands)  │
  │  │ C1   │ │ C2   │ │ C3   │ │ C4   │ │ C5   │                  │
  │  └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘                  │
  │     │        │        │        │        │                        │
  │  ┌──▼────────▼────────▼────────▼────────▼─────────────────┐     │
  │  │              libevent event loop (single thread)        │     │
  │  │  Routes: client request → available server connection   │     │
  │  │  Queues: if no server connection free → wait            │     │
  │  └──┬────────┬────────┬────────┬──────────────────────────┘     │
  │     │        │        │        │                                  │
  │  ┌──▼───┐ ┌──▼───┐ ┌──▼───┐ ┌──▼───┐                           │
  │  │ S1   │ │ S2   │ │ S3   │ │ S4   │  (few: 5-50 server conns) │
  │  └──────┘ └──────┘ └──────┘ └──────┘                           │
  │  Server connections (to PostgreSQL):                             │
  └──────────────────────────────────────────────────────────────────┘

Key architectural properties:
  • Single process, single thread — uses async I/O (libevent/epoll).
  • Very low memory: ~2 KB per client connection vs 8 MB per PostgreSQL backend.
  • No SQL parsing — operates at protocol level (reads packet headers, routes bytes).
  • Per-database, per-user pools — each (dbname, user) pair has its own pool.
  • Server connections are REAL PostgreSQL connections — full auth, real backends.
```

```ini
# ── pgbouncer.ini: core configuration ─────────────────────────────────────────
[databases]
# Format: alias = connection string to PostgreSQL
myapp = host=postgres-primary port=5432 dbname=myapp_production

# Read replica for read-only queries:
myapp_replica = host=postgres-replica port=5432 dbname=myapp_production

[pgbouncer]
# Network:
listen_addr   = *                  # Listen on all interfaces
listen_port   = 6432               # Default PgBouncer port (not 5432)
unix_socket_dir = /var/run/pgbouncer  # Unix socket (faster than TCP for local)

# Pool mode — THE most important setting (see Q3-Q5):
pool_mode = transaction            # session | transaction | statement

# Pool sizes:
default_pool_size = 20             # Max server connections per (db, user) pair
min_pool_size     = 5              # Keep at least N server connections open
max_client_conn   = 1000           # Max simultaneous client connections to PgBouncer
reserve_pool_size = 5              # Extra connections for when pool is exhausted
reserve_pool_timeout = 3           # Seconds to wait before using reserve pool

# Connection lifecycle:
server_idle_timeout    = 600       # Close idle server connections after 600s
client_idle_timeout    = 0         # 0 = never close idle client connections
server_lifetime        = 3600      # Recycle server connections after 1 hour
server_connect_timeout = 15        # Timeout for new server connection

# Authentication:
auth_type = scram-sha-256          # Match PostgreSQL auth method
auth_file = /etc/pgbouncer/userlist.txt  # "username" "password-hash" pairs
# OR use auth_query to delegate to PostgreSQL:
auth_query = SELECT usename, passwd FROM pg_shadow WHERE usename = $1

# TLS:
server_tls_sslmode = require       # Always TLS to PostgreSQL
client_tls_sslmode = allow         # Allow TLS from clients

# Logging:
log_connections = 1                # Log connect/disconnect
log_disconnections = 1
stats_period = 60                  # Log pool stats every 60s
```

## Section 2: The Three Pool Modes

**Q3. What is session mode — when is it appropriate and what are its limitations?**

A: Session mode assigns one PostgreSQL backend connection to each client connection for the entire life of the client session. The client and server connection are 1:1 — PgBouncer provides connection limiting and reconnection, but not true multiplexing:

```
Session mode — connection assignment:

  Client C1 connects  → assigned Server S1 for the ENTIRE session
  Client C2 connects  → assigned Server S2 for the ENTIRE session
  Client C3 connects  → assigned Server S3 for the ENTIRE session
  Client C4 connects  → WAITS if all server connections are busy

  C1 runs a query:     C1 uses S1 (S2, S3 are idle — held by C2, C3)
  C1 idles for 10s:    S1 is HELD even though C1 is doing nothing
  C1 disconnects:      S1 is returned to the pool for the next client
```

```sql
-- ── What session mode preserves ──────────────────────────────────────────────
-- ALL PostgreSQL session-level features work without restriction:

-- 1. Prepared statements (PREPARE / EXECUTE):
PREPARE stmt_get_user AS SELECT * FROM users WHERE id = $1;
EXECUTE stmt_get_user(42);   -- Works — same server connection throughout session

-- 2. Session-level advisory locks:
SELECT pg_advisory_lock(12345);   -- Held for the session duration ✓

-- 3. Temporary tables:
CREATE TEMP TABLE session_data (id INT, value TEXT);
INSERT INTO session_data VALUES (1, 'hello');
SELECT * FROM session_data;  -- ✓ Temp table lives for the session

-- 4. SET / RESET (session-level parameter changes):
SET search_path = tenant_1, public;
SET work_mem = '256MB';       -- ✓ Persists for the session

-- 5. LISTEN / NOTIFY:
LISTEN channel_name;          -- ✓ Receives notifications on this connection

-- 6. Cursors (DECLARE / FETCH):
BEGIN;
DECLARE my_cursor CURSOR FOR SELECT * FROM orders ORDER BY id;
FETCH 100 FROM my_cursor;     -- ✓ Cursor persists between fetches

-- 7. WITH HOLD cursors (survive COMMIT):
DECLARE my_cursor CURSOR WITH HOLD FOR SELECT * FROM products;
COMMIT;
FETCH 10 FROM my_cursor;      -- ✓ Works — connection not reassigned

-- ── When session mode is the right choice ────────────────────────────────────
-- 1. Applications that use session-level features heavily:
--    • Long-lived cursors with WITH HOLD
--    • Session-level advisory locks for leader election
--    • SET search_path per tenant (multi-tenant row isolation)
--    • LISTEN/NOTIFY for real-time features

-- 2. You need connection LIMITING but not multiplexing:
--    max_client_conn = 500, default_pool_size = 100
--    → Caps PostgreSQL at 100 connections even if 500 clients connect.
--    → But each of the 100 active clients holds a server connection.

-- 3. Migrating a legacy application to use a pooler with minimal code changes.

-- ── Session mode limitations ──────────────────────────────────────────────────
-- Pool utilisation is low: a client sitting idle holds a server connection.
-- For 100 server connections and 500 clients:
--   Only 100 clients can be active simultaneously — 400 queue or get an error.
--   An idle connected client (waiting for user input) blocks other clients.
-- No true multiplexing — session mode is just connection limiting + lifecycle management.

-- ── Example: TypeORM with PgBouncer in session mode ──────────────────────────
// DataSource configuration — session mode is the easiest to configure:
const dataSource = new DataSource({
    type:     'postgres',
    host:     'pgbouncer',       // Connect to PgBouncer, not PostgreSQL directly
    port:     6432,
    database: 'myapp',
    username: 'appuser',
    password: 'secret',
    // Session mode: no special configuration needed.
    // All TypeORM features work out of the box.
    extra: {
        max: 50,    // TypeORM pool size = max clients to PgBouncer
        // Each TypeORM connection will hold a PgBouncer session.
    },
});
```

**Q4. What is transaction mode — why is it the most efficient mode and what does it break?**

A: Transaction mode assigns a server connection only for the duration of a transaction. The moment a transaction commits or rolls back, the server connection returns to the pool. This is the mode that delivers true multiplexing — 1,000 clients sharing 20 server connections:

```
Transaction mode — connection assignment:

  C1 begins transaction → assigned S1
  C1 executes queries   → using S1
  C1 commits            → S1 RETURNED to pool
                           (S1 immediately available for C2, C3, C4, ...)

  C2 begins transaction → assigned S1 (same server conn, different client)
  C2 executes queries
  C2 commits            → S1 returned

  Between transactions: C1 holds NO server connection.
  PgBouncer multiplexes: 1000 clients share 20 server connections.
```

```sql
-- ── Why transaction mode dramatically outperforms session mode ────────────────
-- Typical web request: 2-5 ms of DB work, 50-200 ms of total request time.
-- In session mode: server connection held for 50-200 ms (90% of time: idle).
-- In transaction mode: server connection held for 2-5 ms.
-- → Same 20 server connections serve 10-40x more client transactions per second.

-- ── What WORKS in transaction mode (no change needed) ─────────────────────────
-- Multi-statement transactions:
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = 100 WHERE id = 1;
COMMIT;
-- → All three statements use the same server connection (within one transaction).
-- → Transaction pooling guarantees connection continuity within a BEGIN/COMMIT block.

-- Plain queries (autocommit):
SELECT * FROM users WHERE id = 42;
-- → Gets a server connection, runs query, releases connection.
-- → No BEGIN needed — PostgreSQL wraps single statements in implicit transactions.

-- READ COMMITTED queries: ✓
-- REPEATABLE READ transactions: ✓ (held for duration of explicit transaction)
-- SERIALIZABLE transactions: ✓
-- INSERT, UPDATE, DELETE: ✓
-- Explicit transactions with any number of statements: ✓

-- ── What BREAKS in transaction mode ───────────────────────────────────────────

-- 1. Session-level prepared statements (PREPARE / EXECUTE)
--    PREPARE creates a named statement on the server connection.
--    In transaction mode, the next query may use a DIFFERENT server connection.
--    → The prepared statement doesn't exist on the new connection.
PREPARE get_user (BIGINT) AS SELECT * FROM users WHERE id = $1;
-- After COMMIT: server connection released.
EXECUTE get_user(42);
-- ERROR: prepared statement "get_user" does not exist
-- (PgBouncer gave this client a different server connection)

-- FIX A: Use protocol-level prepared statements (not SQL-level PREPARE):
-- Most drivers (node-postgres, psycopg3) use the extended query protocol.
-- PgBouncer in transaction mode intercepts these and maintains a per-client
-- prepared statement cache on each server connection transparently.
-- Set: prepared_statement_cache_queries = 100  (in pgbouncer.ini)

-- FIX B: Disable prepared statements in the driver:
// TypeORM:
extra: { statement_cache_size: 0 }   // node-postgres: disable statement caching
// OR configure PgBouncer:
// prepare_threshold = 0   (in pgbouncer.ini) — disables protocol-level prep

-- 2. Session-level advisory locks
SELECT pg_advisory_lock(12345);   -- Acquires on server connection S1
COMMIT;                           -- S1 released back to pool
-- ... time passes, PgBouncer assigns S2 for next transaction ...
SELECT pg_advisory_unlock(12345); -- Tries to release on S2 — WRONG connection!
-- → Returns FALSE: lock was held on S1, which another client may now be using.
-- → Lock leaks until S1's session ends.

-- FIX: Use TRANSACTION-LEVEL advisory locks:
BEGIN;
SELECT pg_advisory_xact_lock(12345);  -- Held only until COMMIT/ROLLBACK ✓
-- ... do work ...
COMMIT;  -- Lock released automatically — safe in transaction mode

-- 3. Temporary tables
CREATE TEMP TABLE session_cache (key TEXT, value TEXT);
COMMIT;  -- Connection released, temp table lives on server connection S1
-- ... PgBouncer gives S2 for next transaction ...
SELECT * FROM session_cache;  -- ERROR: relation "session_cache" does not exist
-- (S2 doesn't have the temp table that was created on S1)

-- FIX: Don't use temp tables in transaction mode.
-- Alternative: use CTEs, subqueries, or application-level caching.
-- Alternative: use actual tables with a session_id column + cleanup job.

-- 4. SET (session-level parameter changes)
SET search_path = tenant_1, public;  -- Changes search_path on server connection S1
COMMIT;  -- S1 released
-- Next query may land on S2 with default search_path → wrong schema!
SET work_mem = '256MB';  -- Wasted — may not apply to queries run after next tx
SET LOCAL work_mem = '256MB';  -- SET LOCAL is safe: reverts at transaction end

-- FIX A: Use SET LOCAL for transaction-scoped settings:
BEGIN;
SET LOCAL search_path = tenant_1, public;  -- Reverts at COMMIT/ROLLBACK ✓
-- ... tenant-specific queries ...
COMMIT;

-- FIX B: Configure via connection string parameters (applied at server_reset_query):
# In pgbouncer.ini:
server_reset_query = RESET ALL;  -- Resets all SET params when connection returned
# This makes SET safe IF you re-apply it at the start of every transaction.

-- FIX C: Use schema-qualified names in queries:
SELECT * FROM tenant_1.users WHERE id = 42;  -- No reliance on search_path

-- 5. LISTEN / NOTIFY
LISTEN order_updates;  -- Subscribes on S1
-- S1 released after next COMMIT.
-- Notifications sent to S1 are lost (another client now using S1).
-- FIX: Use a DEDICATED connection (not through PgBouncer) for LISTEN/NOTIFY.
-- Or use session mode for the specific connection that needs LISTEN.

-- 6. Cursors (DECLARE / FETCH without WITH HOLD)
BEGIN;
DECLARE my_cursor CURSOR FOR SELECT * FROM large_table ORDER BY id;
FETCH 100 FROM my_cursor;
COMMIT;  -- Cursor destroyed (transaction ended)
-- ... PgBouncer gives different server connection ...
FETCH 100 FROM my_cursor;  -- ERROR: cursor does not exist

-- FIX: Fetch all data in a single transaction, or use LIMIT/OFFSET pagination.
-- WITH HOLD cursors: survive COMMIT at the session level → don't use in tx mode.

-- 7. Two-phase commit (PREPARE TRANSACTION)
PREPARE TRANSACTION 'my-distributed-tx';  -- Requires a stable server connection
-- Transaction mode may reassign the connection → 2PC state becomes inaccessible.
-- FIX: Use session mode for distributed transactions, or avoid 2PC.
```

**Q5. What is statement mode — when would you ever use it?**

A: Statement mode is the most aggressive form of multiplexing: the server connection is returned to the pool after every single SQL statement, even within an explicit transaction. This makes explicit transactions fundamentally broken — it is essentially unusable for general application workloads:

```sql
-- ── Statement mode behaviour ──────────────────────────────────────────────────
-- Every statement — even inside a BEGIN/COMMIT block — may land on a
-- different server connection. PostgreSQL has no way to maintain transaction
-- state across different backend processes.

BEGIN;              -- Statement 1 → uses server S1, then S1 is released
UPDATE ...;         -- Statement 2 → uses server S2 (may be different!)
COMMIT;             -- Statement 3 → uses server S3 (commits a DIFFERENT transaction!)
-- The UPDATE on S2 was auto-committed when S2 was released.
-- The COMMIT on S3 commits whatever transaction (possibly nothing) is on S3.
-- Result: transaction atomicity is COMPLETELY BROKEN in statement mode.

-- ── What breaks in statement mode ────────────────────────────────────────────
-- Everything that transaction mode breaks, PLUS:
-- • Explicit transactions (BEGIN/COMMIT) — DO NOT USE
-- • Any session-level state whatsoever
-- • Transaction isolation levels are meaningless
-- • Any query that spans multiple round-trips

-- ── What still works in statement mode ───────────────────────────────────────
-- Only single-statement workloads with no session dependency:
SELECT 1;                          -- ✓
SELECT * FROM products LIMIT 10;   -- ✓ (autocommit, single statement)
INSERT INTO logs VALUES (...);     -- ✓ (single statement, autocommit)

-- ── The one real-world use case: simple query routing ─────────────────────────
-- A read-only analytics tier with:
--   • No transactions (all single-statement reads)
--   • No session state (no SET, no PREPARE, no TEMP tables)
--   • Maximum server connection reuse across thousands of concurrent readers
--   • Stateless reporting queries that are purely SELECT

-- Example: a real-time analytics dashboard that fires one SELECT per widget.
-- Each SELECT is independent. Statement mode gives maximum throughput.

-- ── Why statement mode is almost never used ───────────────────────────────────
-- Transaction mode already provides excellent multiplexing for typical web apps.
-- The marginal gain of statement mode (fractionally faster connection recycling)
-- is not worth the inability to use transactions.
-- Statement mode is the default in PgBouncer docs but NOT the recommendation.

-- ── Summary of mode restrictions ──────────────────────────────────────────────
-- Feature                    Session mode   Transaction mode   Statement mode
-- ─────────────────────────────────────────────────────────────────────────────
-- Explicit transactions       ✓              ✓                  ✗
-- SQL PREPARE/EXECUTE         ✓              ✗ (use protocol)   ✗
-- Protocol prepared stmts     ✓              ✓ (with cache)     ✗
-- Session advisory locks      ✓              ✗ (use xact lock)  ✗
-- Transaction advisory locks  ✓              ✓                  ✗
-- Temporary tables            ✓              ✗                  ✗
-- SET (session-level)         ✓              ✗ (use SET LOCAL)  ✗
-- SET LOCAL (tx-level)        ✓              ✓                  ✗
-- LISTEN / NOTIFY             ✓              ✗ (dedicate conn)  ✗
-- Cursors (no WITH HOLD)      ✓              ✓ (within tx)      ✗
-- Cursors (WITH HOLD)         ✓              ✗                  ✗
-- PREPARE TRANSACTION (2PC)   ✓              ✗                  ✗
-- LOAD (load shared lib)      ✓              ✗                  ✗
```

## Section 3: Transaction Mode Deep Dive

**Q6. How does PgBouncer handle prepared statements in transaction mode — what is `prepare_threshold`?**

A: The PostgreSQL wire protocol has two ways to prepare statements: SQL-level (`PREPARE` / `EXECUTE`) and protocol-level (the extended query protocol's `Parse`/`Bind`/`Execute` messages). PgBouncer in transaction mode only handles the protocol-level variant, with a per-client cache:

```
Two types of prepared statements:

SQL-level (PREPARE):
  Client sends:  PREPARE get_user AS SELECT * FROM users WHERE id = $1
  PostgreSQL stores: named statement "get_user" on that server connection
  Problem: only exists on that specific server connection → breaks in tx mode

Protocol-level (extended query protocol):
  Client sends:  Parse (query text + statement name)
                 Bind (parameter values)
                 Execute
  PgBouncer intercepts Parse and maintains a per-client map:
    client C1: { "get_user" → query_text }
  When C1's "get_user" lands on server S1 (first time):
    PgBouncer sends Parse to S1, caches that S1 now knows "get_user"
  When C1's "get_user" lands on server S2 (server changed):
    PgBouncer notices S2 doesn't have "get_user" yet
    Sends Parse to S2 first, then Bind/Execute
  → Transparent re-preparation on new server connections ✓
```

```ini
# pgbouncer.ini: prepared statement configuration

# prepare_threshold (default: 0 in older versions, now varies):
# 0 = disable protocol-level prepared statements entirely (safest, slowest)
# N = prepare a statement on the server after it has been seen N times
#     (amortises the Parse overhead)
# Recommended for transaction mode: 0 or a small number (5-10)
prepare_threshold = 0

# prepared_statement_cache_queries:
# How many prepared statements to cache per server connection.
# Higher = more memory, fewer re-preparations.
prepared_statement_cache_queries = 0   # 0 = no caching (safe but slower)
# OR:
prepared_statement_cache_queries = 100  # Cache up to 100 prepared statements per connection

# server_reset_query:
# SQL run when a server connection is returned to the pool.
# DISCARD ALL resets ALL server state (search_path, work_mem, temp tables, cursors, etc.)
server_reset_query = DISCARD ALL
# For transaction mode, DISCARD ALL is called between transactions automatically.
# This is what makes SET (session-level) not persist across transactions.

# server_reset_query_always:
# If true: run reset query even after a transaction (not just session-level events).
# Default false for transaction mode (reset query is already called between transactions).
server_reset_query_always = 0
```

```typescript
// ── TypeORM configuration for transaction mode ─────────────────────────────────
// The most critical setting: disable TypeORM's statement caching.
// TypeORM uses node-postgres (pg) under the hood, which uses protocol-level
// prepared statements. With PgBouncer in transaction mode, this can cause issues
// unless PgBouncer's prepared statement cache is enabled.

const dataSource = new DataSource({
    type:     'postgres',
    host:     'pgbouncer-host',
    port:     6432,
    database: 'myapp',
    username: 'appuser',
    password: 'secret',

    extra: {
        // Option A: Disable prepared statements entirely (simplest, slightly slower):
        statement_cache_size: 0,
        // This tells node-postgres to NOT use protocol-level prepared statements.
        // Every query goes through the simple query protocol.
        // No prepared statement caching in PgBouncer needed.

        // Option B: Enable PgBouncer prepared statement cache (faster, more complex):
        // Leave statement_cache_size at default (node-postgres caches prepared statements).
        // Configure pgbouncer.ini:
        //   prepared_statement_cache_queries = 100
        //   prepare_threshold = 0
        // PgBouncer handles re-preparation transparently.

        // Connection pool settings:
        max:             20,   // Match PgBouncer's default_pool_size
        idleTimeoutMillis: 10000,
        connectionTimeoutMillis: 5000,
    },

    // Ensure migrations don't use prepared statements during schema changes:
    migrationsRun: false,
});

// ── Detecting prepared statement errors in production ─────────────────────────
// Symptom: "prepared statement 'xyz' does not exist"
// Cause: TypeORM cached prepared statement name, PgBouncer switched server connections.
// Fix: set statement_cache_size: 0 in the DataSource extra config.

// ── Testing if your app works in transaction mode ─────────────────────────────
// Quick test: connect to PgBouncer port, run:
SHOW pool_mode;  -- Should return "transaction"

-- Then run your most complex query flows and check for:
-- • "prepared statement does not exist" → disable statement caching
-- • "relation does not exist" (temp table) → refactor to avoid temp tables
-- • Unexpected search_path → use SET LOCAL or schema-qualified names
-- • Advisory lock leaks → switch to pg_advisory_xact_lock
```

**Q7. How does `server_reset_query` work and what state does it clean between clients in transaction mode?**

A: When PgBouncer returns a server connection to the pool (after a client's transaction ends), it runs `server_reset_query` to erase any residual state left by the previous client. This is the mechanism that makes connection sharing safe:

```sql
-- ── Default server_reset_query: DISCARD ALL ────────────────────────────────────
-- DISCARD ALL is equivalent to:
RESET ALL;              -- Resets all SET parameters to their config-file defaults
DEALLOCATE ALL;         -- Removes all prepared statements (SQL-level PREPARE)
CLOSE ALL;              -- Closes all open cursors
UNLISTEN *;             -- Cancels all LISTEN subscriptions
SELECT pg_advisory_unlock_all();  -- Releases all advisory locks
DISCARD SEQUENCES;      -- Resets sequence state
DISCARD TEMP;           -- Drops all temporary tables

-- After DISCARD ALL, the server connection is in the same state as a fresh connection.
-- The next client gets a clean slate regardless of what the previous client did.

-- ── What DISCARD ALL does NOT reset ──────────────────────────────────────────
-- • The current database (cannot change it after connection without reconnecting)
-- • The current user/role (cannot change it without reconnecting)
-- • In-flight transactions: PgBouncer never recycles a connection mid-transaction
-- • Application_name: some apps set this for monitoring — reset with RESET ALL

-- ── Performance cost of server_reset_query ────────────────────────────────────
-- DISCARD ALL takes ~0.1 ms per connection recycle.
-- At 10,000 transactions/second with 20 server connections:
-- Each server connection is recycled up to 500 times/second.
-- 500 × 0.1 ms = 50 ms/second of reset overhead per server connection.
-- This is usually acceptable, but for extreme throughput:

-- Lighter alternatives:
server_reset_query = RESET search_path; DEALLOCATE ALL;
-- Only reset what your application actually changes.

-- Or: rely on SET LOCAL (reverts automatically) and avoid DISCARD ALL:
server_reset_query =   -- Empty string: no reset query
# Risk: residual state from buggy clients leaks to the next client.
# Only safe if your application is well-disciplined about session state.

-- ── Verifying reset behaviour ─────────────────────────────────────────────────
-- Connect to PgBouncer, run in transaction mode:
BEGIN;
SET LOCAL work_mem = '512MB';
SHOW work_mem;  -- → 512MB (within transaction)
COMMIT;         -- SET LOCAL reverts at COMMIT

-- In another transaction (same client):
SHOW work_mem;  -- → 4MB (default) ← SET LOCAL correctly reverted ✓

-- Verify temp table cleanup:
BEGIN;
CREATE TEMP TABLE t (x INT);
INSERT INTO t VALUES (1);
COMMIT;  -- PgBouncer recycles server connection, runs DISCARD ALL

-- Next transaction (may be different server connection):
SELECT * FROM t;  -- ERROR: relation "t" does not exist ← correctly cleaned ✓
```

## Section 4: Configuration and Tuning

**Q8. How do you size the connection pool — what formulas and signals guide `default_pool_size` and `max_client_conn`?**

A: Pool sizing is one of the most consequential configuration decisions. Too small: clients queue and experience latency spikes. Too large: PostgreSQL is overwhelmed and performance degrades for everyone:

```
Pool sizing model:

  Variables:
    C  = number of application server instances
    T  = threads (or async workers) per instance
    P  = fraction of time each thread is in a DB transaction
    W  = target PostgreSQL server connections (= default_pool_size)

  Desired: W server connections can service C×T client connections

  In transaction mode:
    W = C × T × P   (Little's Law applied to the connection pool)

  Example:
    5 app servers × 20 threads = 100 client connections
    Each thread: 10ms DB time out of 100ms request time → P = 0.1
    W = 100 × 0.1 = 10 server connections needed
    Set default_pool_size = 15 (add 50% headroom)

  PostgreSQL guideline:
    Optimal server connections ≈ (CPU cores × 2) + effective_io_concurrency
    For a 16-core server: 16 × 2 + 8 = 40 connections
    Beyond ~100 active connections: PostgreSQL scheduler contention outweighs parallelism.
```

```ini
# ── Sizing parameters ─────────────────────────────────────────────────────────

[pgbouncer]
# default_pool_size: server connections per (database, user) pair.
# Rule of thumb: 10–25 for OLTP web apps on typical hardware.
# Start with: (PostgreSQL_max_connections - system_connections) / number_of_pools
default_pool_size = 20

# max_client_conn: maximum total client connections to PgBouncer.
# Should be >> default_pool_size (that's the point of pooling).
# Limit: OS file descriptor limit (ulimit -n), PgBouncer typically handles 10k+.
max_client_conn = 2000

# reserve_pool_size: extra server connections for burst traffic.
# Borrowed from when the pool is exhausted. Use sparingly.
reserve_pool_size = 5
reserve_pool_timeout = 3  # Seconds before using reserve pool

# max_db_connections: global cap on server connections to one database.
# Prevents one database from consuming all connections when multiple databases share PgBouncer.
max_db_connections = 50

# ── Timeout configuration ─────────────────────────────────────────────────────
# query_timeout: max time for a single query (0 = disabled).
# If exceeded: client disconnected, server connection killed.
query_timeout = 30   # seconds — protect against runaway queries

# query_wait_timeout: max time a client waits for a server connection from the pool.
# If pool is full and a client waits longer than this: "no more connections allowed"
query_wait_timeout = 10  # seconds

# client_idle_timeout: disconnect clients idle for this long.
# Prevents ghost connections from holding pool slots.
client_idle_timeout = 300  # 5 minutes

# server_idle_timeout: close server connections idle longer than this.
# Prevents server-side "too many connections" from idle pool members.
server_idle_timeout = 600  # 10 minutes

# server_lifetime: maximum age of a server connection (recycle proactively).
# Useful for rotating connections after configuration changes.
server_lifetime = 3600  # 1 hour

# ── Signals that the pool is too small ───────────────────────────────────────
-- In SHOW POOLS output:
-- cl_waiting > 0 for sustained periods → pool too small (clients queuing)
-- sv_idle = 0 and cl_waiting > 0 → all server connections busy → increase pool

-- In application logs:
-- "connection timeout expired" from the driver → query_wait_timeout exceeded
-- P99 latency spike with no corresponding query time increase → pool wait time

-- ── Signals that the pool is too large ───────────────────────────────────────
-- PostgreSQL pg_stat_activity shows many 'active' queries running slowly
-- PostgreSQL lock contention increases (more connections = more lock waiters)
-- PostgreSQL context switching overhead (visible in CPU usage per query)
-- pg_stat_activity shows total connections near max_connections → approaching limit

-- ── Per-database pool override ────────────────────────────────────────────────
[databases]
# Override pool size for a specific database:
reporting_db = host=postgres port=5432 dbname=reporting pool_size=5
# Analytics database: fewer connections, longer timeouts.
analytics    = host=postgres port=5432 dbname=analytics pool_size=10 pool_mode=session
# Use session mode for analytics (long-running queries, cursors).
```

**Q9. How do you monitor PgBouncer — what do `SHOW POOLS`, `SHOW CLIENTS`, and `SHOW SERVERS` reveal?**

A: PgBouncer exposes its internal state through a virtual `pgbouncer` database. Connecting to it with `psql` and running `SHOW` commands is the primary operational monitoring interface:

```sql
-- ── Connect to PgBouncer admin interface ──────────────────────────────────────
-- psql -h pgbouncer-host -p 6432 -U pgbouncer_admin pgbouncer
-- The user must be in admin_users or stats_users in pgbouncer.ini.

-- ── SHOW POOLS: the most important view ───────────────────────────────────────
SHOW POOLS;

-- database │ user    │ cl_active │ cl_waiting │ cl_cancel_req │
-- ─────────┼─────────┼───────────┼────────────┼───────────────┤
-- myapp    │ appuser │    18     │     2      │      0        │
--
-- sv_active │ sv_idle │ sv_used │ sv_tested │ sv_login │ maxwait │ pool_mode
-- ──────────┼─────────┼─────────┼───────────┼──────────┼─────────┼──────────
--    18     │    2    │   0     │     0     │    0     │    4    │ transaction

-- Column meanings:
-- cl_active:    Clients currently executing a query or in a transaction.
-- cl_waiting:   Clients waiting for a server connection from the pool.
--               ← CRITICAL METRIC: should be 0 or near 0 in steady state.
--               Sustained cl_waiting > 0 means the pool is too small.
-- sv_active:    Server connections currently assigned to a client.
-- sv_idle:      Server connections in the pool, ready for use.
--               ← If sv_idle = 0 AND cl_waiting > 0: pool exhausted.
-- sv_used:      Server connections that have been used but not reset yet.
-- sv_login:     Server connections currently being established.
-- maxwait:      Seconds the oldest waiting client has been waiting.
--               ← If maxwait > 1-2 seconds: clients are experiencing latency.
-- pool_mode:    Confirms transaction/session/statement mode for this pool.

-- ── SHOW CLIENTS: individual client connection state ─────────────────────────
SHOW CLIENTS;

-- type │ user    │ database │ state   │ addr        │ port │ ...│ wait │ query
-- ─────┼─────────┼──────────┼─────────┼─────────────┼──────┼────┼──────┼──────
-- C    │ appuser │ myapp    │ active  │ 10.0.0.5   │ 5823 │ ...│  0   │ SELECT ...
-- C    │ appuser │ myapp    │ waiting │ 10.0.0.6   │ 5824 │ ...│  3   │ BEGIN

-- state = 'waiting': client is waiting for a pool server connection.
-- wait: seconds this client has been waiting.

-- ── SHOW SERVERS: individual server connection state ─────────────────────────
SHOW SERVERS;

-- type │ user    │ database │ state  │ addr        │ port │ ...│ age │ query
-- ─────┼─────────┼──────────┼────────┼─────────────┼──────┼────┼─────┼──────
-- S    │ appuser │ myapp    │ active │ 10.0.0.10  │ 5432 │ ...│ 3h  │ SELECT ...
-- S    │ appuser │ myapp    │ idle   │ 10.0.0.10  │ 5432 │ ...│ 3h  │

-- state = 'idle':   Waiting in the pool for a client.
-- state = 'active': Currently serving a client.
-- state = 'used':   Just returned from a client, running server_reset_query.
-- age: age of the server connection (compare to server_lifetime).

-- ── SHOW STATS: per-database request throughput ───────────────────────────────
SHOW STATS;

-- database │ total_xact_count │ total_query_count │ total_received │
-- ─────────┼──────────────────┼───────────────────┼────────────────┤
-- myapp    │    12,847,231    │    48,291,847     │  128,491 MB    │
--
-- total_wait_time │ avg_xact_time │ avg_query_time
-- ────────────────┼───────────────┼────────────────
--      3,291 ms   │      2.3 ms  │      0.6 ms

-- avg_wait_time: time clients spend waiting for a pool connection.
--   Should be < 1ms for well-sized pools. > 5ms: pool is undersized.
-- avg_query_time: time to execute queries. Spike here = database performance issue.
-- avg_xact_time:  time per transaction. Long transactions hold server connections.

-- ── SHOW CONFIG: current PgBouncer configuration ─────────────────────────────
SHOW CONFIG;
-- Shows all current pgbouncer.ini settings.
-- Can reload without restart: RELOAD; (in pgbouncer admin console)

-- ── Operational commands ──────────────────────────────────────────────────────
RELOAD;             -- Reload pgbouncer.ini without dropping connections
PAUSE myapp;        -- Stop sending new queries to myapp (for maintenance)
RESUME myapp;       -- Resume after PAUSE
KILL myapp;         -- Immediately drop all connections to myapp
SUSPEND;            -- Flush all buffers and wait (for safe backup of PgBouncer state)
RESUME;             -- Resume after SUSPEND
SHUTDOWN;           -- Graceful shutdown

-- ── Prometheus monitoring integration ─────────────────────────────────────────
-- pgbouncer_exporter (open source) exposes SHOW POOLS / SHOW STATS as metrics:
-- pgbouncer_pool_cl_waiting{database="myapp"}   → Alert if > 0 for > 30s
-- pgbouncer_pool_sv_idle{database="myapp"}      → Alert if = 0 (pool exhausted)
-- pgbouncer_pool_maxwait_seconds{database="myapp"} → Alert if > 5s
-- pgbouncer_stats_avg_wait_seconds              → P95 pool wait time
```

## Section 5: NestJS and TypeORM Integration

**Q10. How do you configure TypeORM for PgBouncer in transaction mode — what must change at the ORM level?**

A: Connecting TypeORM to PgBouncer in transaction mode requires tuning the node-postgres driver settings, disabling incompatible features, and handling the edge cases that transaction mode introduces:

```typescript
import { DataSource, DataSourceOptions } from 'typeorm';
import { ConfigService }                 from '@nestjs/config';

// ── Full TypeORM DataSource configuration for PgBouncer transaction mode ───────
export function createDataSourceOptions(config: ConfigService): DataSourceOptions {
    const isProd = config.get('NODE_ENV') === 'production';

    return {
        type:     'postgres',

        // Connect to PgBouncer, NOT PostgreSQL directly:
        host:     config.get('PGBOUNCER_HOST', 'localhost'),
        port:     config.get<number>('PGBOUNCER_PORT', 6432),
        database: config.get('DB_NAME'),
        username: config.get('DB_USER'),
        password: config.get('DB_PASSWORD'),

        ssl: isProd ? { rejectUnauthorized: true, ca: config.get('DB_SSL_CA') } : false,

        // TypeORM connection pool (connections TO PgBouncer, not to PostgreSQL):
        // Keep this small — PgBouncer handles the real multiplexing.
        // Too many TypeORM connections → more PgBouncer client slots used.
        extra: {
            // node-postgres pool settings:
            max:                    20,     // Max connections from this app instance to PgBouncer
            min:                    2,      // Keep at least 2 connections warm
            idleTimeoutMillis:      10_000, // Close idle connections after 10s
            connectionTimeoutMillis: 5_000, // Fail if cannot connect within 5s

            // ── CRITICAL for transaction mode: disable prepared statement caching ──
            // node-postgres by default sends 'Parse' protocol messages for prepared statements.
            // PgBouncer in transaction mode may route these to different server connections.
            // safest option: disable prepared statements at driver level:
            statement_cache_size: 0,
            // This makes node-postgres use the simple query protocol instead of extended.
            // Trade-off: slightly slower (no query plan caching), but 100% safe.

            // OR: let PgBouncer cache them (more complex, requires PgBouncer config):
            // statement_cache_size: 0,  // Keep at 0 — PgBouncer handles caching

            // Application name (visible in pg_stat_activity):
            application_name: `${config.get('APP_NAME')}-${process.env.HOSTNAME}`,
        },

        // TypeORM-level settings:
        logging:          isProd ? ['error', 'warn'] : ['query', 'error'],
        maxQueryExecutionTime: 10_000,  // Log queries taking > 10s

        // Migrations: run directly against PostgreSQL (bypass PgBouncer):
        // Migrations may use features incompatible with transaction mode
        // (CONCURRENTLY, DDL in transactions, etc.)
        migrations: ['src/migrations/*.ts'],
        migrationsRun: false,  // Run migrations separately, not on startup
    };
}

// ── Service layer: patterns safe with transaction mode ─────────────────────────
@Injectable()
export class OrderService {
    constructor(
        @InjectRepository(Order)
        private readonly orderRepo: Repository<Order>,
        private readonly dataSource: DataSource,
    ) {}

    // ✓ SAFE: Standard transaction — all statements on same server connection
    async createOrder(userId: number, items: CreateOrderItemDto[]): Promise<Order> {
        return this.dataSource.transaction(async (manager) => {
            // All queries in this callback use the SAME server connection.
            // PgBouncer guarantees connection continuity within a BEGIN/COMMIT block.
            const order = await manager.save(Order, { userId, total: 0 });

            const orderItems = items.map(item =>
                manager.create(OrderItem, { ...item, orderId: order.id })
            );
            await manager.save(OrderItem, orderItems);

            const total = items.reduce((s, i) => s + i.unitPrice * i.quantity, 0);
            await manager.update(Order, order.id, { total });

            return manager.findOneOrFail(Order, { where: { id: order.id } });
        });
    }

    // ✓ SAFE: SET LOCAL within a transaction (reverts at COMMIT)
    async getOrdersForTenant(tenantId: number): Promise<Order[]> {
        return this.dataSource.transaction(async (manager) => {
            // SET LOCAL: scoped to this transaction — safe in transaction mode
            await manager.query(`SET LOCAL search_path = tenant_${tenantId}, public`);
            return manager.find(Order, { where: { tenantId } });
            // At COMMIT: search_path reverts, server connection returned to pool
        });
    }

    // ✗ UNSAFE: Session-level advisory lock (replace with transaction-level)
    // BAD:
    async unsafeLock(resourceId: number): Promise<void> {
        await this.dataSource.query(`SELECT pg_advisory_lock(${resourceId})`);
        // Lock held on server connection S1.
        // Next query may use S2 — lock is lost/leaked.
    }

    // ✓ SAFE: Transaction-level advisory lock
    async safeWithLock<T>(resourceId: number, work: () => Promise<T>): Promise<T> {
        return this.dataSource.transaction(async (manager) => {
            await manager.query('SELECT pg_advisory_xact_lock($1)', [resourceId]);
            // Lock held for duration of transaction only → released at COMMIT ✓
            return work();
        });
    }

    // ✗ UNSAFE: Temp table without wrapping in a single transaction
    async unsafeTempTable(): Promise<void> {
        await this.dataSource.query('CREATE TEMP TABLE t (x INT)');
        // Server connection returned after this statement (transaction mode).
        await this.dataSource.query('SELECT * FROM t');
        // May be on a different server connection → "relation t does not exist"
    }

    // ✓ SAFE: Temp table within a single transaction
    async safeTempTable(): Promise<void> {
        await this.dataSource.transaction(async (manager) => {
            await manager.query('CREATE TEMP TABLE t (x INT)');
            await manager.query('INSERT INTO t VALUES (1), (2)');
            const rows = await manager.query('SELECT * FROM t');
            // All on same server connection within the transaction ✓
            return rows;
        });
    }
}
```

## Section 6: Advanced Patterns

**Q11. How do you run multiple PgBouncer instances — what are the patterns for high availability and read/write splitting?**

A: A single PgBouncer process is a single point of failure and a throughput bottleneck. Production deployments use multiple instances with a load balancer, or dedicated instances per application pod:

```
Production PgBouncer topology options:

Option A: Sidecar PgBouncer (Kubernetes)
  ┌──────────────────────────────┐
  │ Pod                          │
  │  ┌─────────┐  ┌───────────┐ │      ┌──────────────────┐
  │  │  App    │──►│PgBouncer  │─┼─────►│   PostgreSQL      │
  │  │container│  │ (sidecar) │ │      │   (Primary)       │
  │  └─────────┘  └───────────┘ │      └──────────────────┘
  └──────────────────────────────┘
  • One PgBouncer per pod — eliminates network hop between app and pooler.
  • Each PgBouncer manages its own pool of PostgreSQL connections.
  • Total PostgreSQL connections = pods × default_pool_size.
  • Failure of one pod takes its PgBouncer with it — no global SPOF.
  • Simple: no shared state between PgBouncer instances.

Option B: Centralised PgBouncer with load balancer
  ┌──────────┐    ┌──────────────┐    ┌──────────────┐
  │ App 1    │──►│              │──►│ PgBouncer A  │──┐
  │ App 2    │──►│  HAProxy /   │──►│ PgBouncer B  │──┼──► PostgreSQL
  │ App 3    │──►│  Keepalived  │──►│ PgBouncer C  │──┘
  └──────────┘    └──────────────┘    └──────────────┘
  • Multiple PgBouncer instances behind a load balancer.
  • HAProxy health checks PgBouncer instances (port probe or SHOW CONFIG).
  • Each PgBouncer has its own server connection pool → total = N × pool_size.
  • Keepalived provides VIP (virtual IP) failover.

Option C: Read/Write split topology
                              ┌── PgBouncer Write ──► PostgreSQL Primary
  App ──► HAProxy ──────────►┤
                              └── PgBouncer Read  ──► PostgreSQL Replica(s)
  • Write queries → PgBouncer pointing at primary.
  • Read queries → PgBouncer pointing at replicas.
  • Application must explicitly route queries (different DataSource configs).
  • HAProxy can split on connection destination port: 6432=write, 6433=read.
```

```ini
# ── PgBouncer for read replica (read-only pool) ────────────────────────────────
[databases]
# Write pool (primary):
myapp_write = host=postgres-primary port=5432 dbname=myapp

# Read pool (replica — note: same database name alias):
myapp_read  = host=postgres-replica port=5432 dbname=myapp

[pgbouncer]
listen_port = 6433   # Different port for read pool
pool_mode   = transaction
default_pool_size = 30  # Replicas can handle more connections (read-only)
```


## Section 7: Scenario-Based Questions

**Q12. "After migrating to PgBouncer, we're seeing intermittent errors: 'prepared statement X does not exist'. What is happening and how do you fix it?"**

A: This is the most common PgBouncer transaction mode misconfiguration. The driver is sending protocol-level prepared statement names, PgBouncer switches server connections between statements, and the named statement doesn't exist on the new server connection:

```
Timeline of the bug:

  Client C1 connects to PgBouncer in transaction mode.
  
  Request 1:
    C1 → PgBouncer: Parse("stmt_1", "SELECT * FROM users WHERE id = $1")
    PgBouncer → Server S1: Parse("stmt_1", "SELECT * FROM users WHERE id = $1")
    S1 stores named statement "stmt_1"
    C1 → PgBouncer: Bind("stmt_1", [42]) → Execute → Sync
    PgBouncer → S1: Bind/Execute/Sync (finds "stmt_1" ✓)
    Transaction commits → S1 returned to pool.

  Request 2 (milliseconds later):
    C1 → PgBouncer: Bind("stmt_1", [99])
    PgBouncer assigns S2 (S1 is busy serving C2)
    PgBouncer → S2: Bind("stmt_1", [99])
    S2: ERROR: prepared statement "stmt_1" does not exist
    PgBouncer → C1: ERROR: prepared statement "stmt_1" does not exist ← client sees this
```

```typescript
// ── Diagnosis ─────────────────────────────────────────────────────────────────
// 1. Confirm pool mode:
//    psql -h pgbouncer-host -p 6432 -U admin pgbouncer
//    SHOW POOLS;  → pool_mode = transaction ✓

// 2. Check driver version and settings:
//    node-postgres (pg): uses prepared statements by default
//    TypeORM:            wraps node-postgres

// ── Fix A: Disable prepared statements at driver level (recommended) ──────────

// [databases]
```

**Q13. "We're seeing 'ERROR: no more connections allowed' from PgBouncer under peak load — walk through the complete diagnosis and fix."**

A: `no more connections allowed` means the PgBouncer pool is exhausted — all `default_pool_size` server connections are in use and `max_client_conn` or `query_wait_timeout` has been reached. The fix depends on which bottleneck is actually binding:

```sql
-- ── Step 1: Identify the bottleneck ───────────────────────────────────────────
-- Connect to PgBouncer admin:
SHOW POOLS;

-- Scenario A: cl_waiting > 0, sv_idle = 0
-- ┌──────────┬──────────┬───────────┬────────────┬──────────┬─────────┬─────────┐
-- │ database │ user     │ cl_active │ cl_waiting │ sv_active│ sv_idle │ maxwait │
-- ├──────────┼──────────┼───────────┼────────────┼──────────┼─────────┼─────────┤
-- │ myapp    │ appuser  │    20     │    47      │    20    │    0    │   12s   │
-- Pool is exhausted: 20 server connections all busy, 47 clients waiting.
-- Fix: increase default_pool_size (if PostgreSQL can handle more connections).

-- Scenario B: cl_active < pool_size, but connections are idle in transaction
SHOW CLIENTS;
-- Many clients with state = 'active' but executing slow queries.
-- OR: clients state = 'idle' but inside a transaction (connection held, not in pool).

-- Step 2: Check if PostgreSQL can handle more connections:
SELECT COUNT(*) FROM pg_stat_activity;  -- Current connections
SHOW max_connections;                    -- Maximum allowed
-- If current ≈ max_connections: PostgreSQL is the bottleneck.
--   Cannot increase default_pool_size without also increasing max_connections.

-- Step 3: Find long-running transactions holding server connections:
SELECT
    pid,
    usename,
    state,
    now() - xact_start    AS tx_duration,
    now() - query_start   AS query_duration,
    LEFT(query, 100)      AS current_query
FROM   pg_stat_activity
WHERE  datname = 'myapp'
AND    state   != 'idle'
ORDER  BY tx_duration DESC NULLS LAST;

-- Long transactions hold server connections for their entire duration.
-- A 30-second transaction holds a server connection for 30 seconds.
-- During that time, 19 other clients share the remaining 19 connections.

-- Step 4: Determine if the issue is pool size or query performance:
SHOW STATS;
-- avg_query_time: if this is high, queries are slow → fix queries, not pool size.
-- avg_wait_time:  if this is high, pool is too small → increase pool size.

-- ── Fixes based on diagnosis ──────────────────────────────────────────────────

-- Fix 1: Increase pool size (if PostgreSQL can handle it):
-- In pgbouncer.ini:
default_pool_size = 30   -- Increase from 20
-- On PostgreSQL:
ALTER SYSTEM SET max_connections = 200;  -- Increase from 100
SELECT pg_reload_conf();
-- CAUTION: increasing max_connections requires PostgreSQL restart on older versions.

-- Fix 2: Set query_wait_timeout to fail fast (better UX than hanging):
query_wait_timeout = 5   -- Fail after 5s instead of hanging indefinitely
-- Client sees: "ERROR: query_wait_timeout expired" → application can retry or return 503.

-- Fix 3: Reduce transaction duration to free connections faster:
-- Find and fix N+1 query patterns that keep transactions open.
-- Move non-DB work outside transactions.
-- Use savepoints instead of nested long transactions.

-- Fix 4: Add idle_in_transaction_session_timeout on PostgreSQL:
ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
SELECT pg_reload_conf();
-- Auto-kills connections that are in a transaction but idle for > 30s.
-- Frees up server connections held by crashed clients or forgotten transactions.

-- Fix 5: Scale PgBouncer horizontally (if single PgBouncer is bottleneck):
-- Add a second PgBouncer instance behind HAProxy.
-- total_pool_size doubles; PostgreSQL sees the same total connections.

-- ── Monitoring to prevent recurrence ──────────────────────────────────────────
-- Alert: pgbouncer_pool_cl_waiting > 5 for > 60 seconds
-- Alert: pgbouncer_pool_maxwait_seconds > 3
-- Alert: pgbouncer_pool_sv_idle == 0 for > 30 seconds
-- Dashboard: plot cl_active, cl_waiting, sv_active, sv_idle over time.
```

```typescript
        super();
    }

        try {
            // Verify PgBouncer is reachable AND PostgreSQL connection works:
            await this.dataSource.query('SELECT 1');

            // Check PgBouncer pool health (connect to admin port):
            const poolStats = await this.getPgBouncerStats();
            const isExhausted = poolStats.cl_waiting > 10;

                sv_idle:     poolStats.sv_idle,
                sv_active:   poolStats.sv_active,

            host:     process.env.PGBOUNCER_HOST,
            port:     6432,

                FROM   pgbouncer.pools
                WHERE  database = 'myapp'
            `);
            return rows[0] ?? {};
        } finally {
            await adminPool.end();
        }
    }
```

| True multiplexing | No (1:1 mapping) | **Yes** | **Yes (extreme)** |
| Explicit transactions | ✓ | ✓ | ✗ |
| SQL PREPARE/EXECUTE | ✓ | ✗ | ✗ |
| Protocol prepared stmts | ✓ | ✓ (with cache) | ✗ |
| Session advisory locks | ✓ | ✗ | ✗ |
| Xact advisory locks | ✓ | ✓ | ✗ |
| Temporary tables | ✓ | ✗ | ✗ |
| `SET` (session level) | ✓ | ✗ | ✗ |
| `SET LOCAL` (tx level) | ✓ | ✓ | ✗ |
| LISTEN / NOTIFY | ✓ | ✗ | ✗ |
| Cursors (no WITH HOLD) | ✓ | ✓ (within tx) | ✗ |
| Cursors (WITH HOLD) | ✓ | ✗ | ✗ |
| PREPARE TRANSACTION | ✓ | ✗ | ✗ |
| Typical use case | Legacy apps, analytics | **Most web apps** | Single-statement read workloads |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) being precise that **transaction mode is the correct default for most web applications** — session mode provides connection limiting but not true multiplexing; the 1,000 clients sharing 20 server connections stat only holds in transaction mode; (2) knowing the exact list of **what breaks in transaction mode** and the fix for each: SQL-level PREPARE (switch to `statement_cache_size: 0`), session advisory locks (switch to `pg_advisory_xact_lock`), temp tables (refactor to CTEs or application state), session-level SET (switch to SET LOCAL), and LISTEN/NOTIFY (use a dedicated direct connection bypassing PgBouncer); (3) understanding that **`server_reset_query = DISCARD ALL`** is what makes transaction mode safe — it resets ALL session state when a server connection is returned to the pool, and knowing what `DISCARD ALL` actually resets (RESET ALL, DEALLOCATE ALL, CLOSE ALL, UNLISTEN *, advisory locks, temp tables); (4) knowing the **two types of prepared statements** — SQL-level (`PREPARE`/`EXECUTE`, breaks in transaction mode) vs protocol-level (the extended query protocol's Parse/Bind/Execute, which PgBouncer can handle with a per-client cache in transaction mode) — confusing these two is the source of the most common PgBouncer migration bug; (5) being able to **read `SHOW POOLS` output** and diagnose: `cl_waiting > 0` means pool is exhausted (increase `default_pool_size`), `sv_idle = 0` confirms exhaustion, `maxwait > 5s` means clients are experiencing pool-induced latency, and knowing the fix for each; (6) understanding the **pool sizing formula**: server connections needed ≈ (clients × fraction of time in a DB transaction), and that PostgreSQL performance degrades above ~100–200 active connections regardless of how many PgBouncer allocates; (7) knowing that **migrations must bypass PgBouncer** and connect directly to PostgreSQL — `CREATE INDEX CONCURRENTLY` cannot run inside a transaction, DDL needs stable connections, and PgBouncer's transaction mode is incompatible with several migration patterns; and (8) knowing that **LISTEN/NOTIFY requires a dedicated connection** that bypasses PgBouncer entirely — LISTEN subscribes a server connection to a channel, but in transaction mode that server connection is returned to the pool and given to another client after each transaction, making it impossible to receive notifications reliably.
