# Foreign Keys, Cascades, Deferrable Constraints — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does a foreign key constraint actually do at the PostgreSQL engine level — how is it enforced?**

A: A foreign key (FK) is a referential integrity constraint that guarantees every value in a child column exists as a primary key (or unique key) value in the parent table. PostgreSQL enforces this using internally managed triggers — not application code, not middleware, not the ORM:

```
Referential integrity model:

  Parent table: users             Child table: orders
  ┌──────────────────────────┐    ┌─────────────────────────────────────────┐
  │ id (PK) │ name           │    │ id (PK) │ user_id (FK → users.id) │ ... │
  ├─────────┼────────────────┤    ├─────────┼─────────────────────────┼─────┤
  │    1    │ Alice          │◄───│    10   │          1              │ ... │
  │    2    │ Bob            │◄───│    11   │          2              │ ... │
  │    3    │ Carol          │    │    12   │          1              │ ... │
  └─────────┴────────────────┘    └─────────┴─────────────────────────┴─────┘

  Constraint guarantees:
  • Every orders.user_id value (1, 2, 1) exists in users.id ✓
  • INSERT INTO orders (user_id) VALUES (99) → ERROR: user 99 does not exist
  • DELETE FROM users WHERE id = 1 → ERROR: orders still reference user 1
    (unless a cascade action is defined)
```

```sql
-- ── How PostgreSQL enforces FK constraints: internal triggers ──────────────────
-- PostgreSQL creates FOUR system triggers per FK constraint:
--   RI_ConstraintTrigger_c_NNNN  (INSERT on child):
--     Checks that the new child row's FK value exists in the parent.
--   RI_ConstraintTrigger_c_NNNN  (UPDATE on child):
--     Checks the new FK value if the FK column is updated.
--   RI_ConstraintTrigger_a_NNNN  (DELETE on parent):
--     Checks for referencing rows in the child; acts per ON DELETE rule.
--   RI_ConstraintTrigger_a_NNNN  (UPDATE on parent):
--     Checks for referencing rows if the PK column is updated; acts per ON UPDATE rule.

-- Observe these triggers:
SELECT tgname, tgtype, tgfoid::regproc
FROM   pg_trigger
WHERE  tgrelid = 'orders'::regclass
AND    tgname LIKE 'RI_%';

-- ── Basic FK declaration ──────────────────────────────────────────────────────
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE orders (
    id         BIGSERIAL PRIMARY KEY,
    user_id    BIGINT NOT NULL
               REFERENCES users(id),        -- Inline FK: references users.id (PK)
    total      NUMERIC(10,2) NOT NULL,
    status     TEXT NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- ── Table-level FK syntax (required for composite FKs and named constraints) ──
CREATE TABLE order_items (
    id         BIGSERIAL PRIMARY KEY,
    order_id   BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity   INT    NOT NULL CHECK (quantity > 0),
    price      NUMERIC(10,2) NOT NULL,

    -- Named constraint: critical for clear error messages and ALTER TABLE DROP
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id)
        REFERENCES orders(id)
        ON DELETE CASCADE,

    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id)
        REFERENCES products(id)
        ON DELETE RESTRICT
);

-- ── What the FK references — must be PK or UNIQUE ─────────────────────────────
-- Default: REFERENCES users(id) → references the PRIMARY KEY of users.
-- Can reference any UNIQUE constraint — not just the PK:
CREATE TABLE tenants (
    id       BIGSERIAL PRIMARY KEY,
    slug     TEXT NOT NULL UNIQUE    -- Can be referenced as an FK target
);

CREATE TABLE projects (
    id          BIGSERIAL PRIMARY KEY,
    tenant_slug TEXT NOT NULL REFERENCES tenants(slug)  -- References UNIQUE column
);

-- ── Checking FK constraint metadata ───────────────────────────────────────────
SELECT
    tc.constraint_name,
    tc.table_name          AS child_table,
    kcu.column_name        AS child_column,
    ccu.table_name         AS parent_table,
    ccu.column_name        AS parent_column,
    rc.delete_rule,
    rc.update_rule,
    rc.is_deferrable,
    rc.initially_deferred
FROM   information_schema.table_constraints    AS tc
JOIN   information_schema.key_column_usage     AS kcu USING (constraint_name, table_schema)
JOIN   information_schema.constraint_column_usage AS ccu USING (constraint_name, table_schema)
JOIN   information_schema.referential_constraints AS rc USING (constraint_name, table_schema)
WHERE  tc.constraint_type = 'FOREIGN KEY'
AND    tc.table_schema     = 'public'
ORDER  BY tc.table_name, tc.constraint_name;
```

**Q2. What locking does a foreign key constraint acquire — and why does this matter for concurrent applications?**

A: FK enforcement acquires row-level locks on the parent table to prevent phantom inserts and deletes during constraint checking. These implicit locks are the most common hidden source of lock contention in high-traffic applications:

```sql
-- ── FK check on INSERT into child: acquires FOR KEY SHARE on parent ────────────
-- When you INSERT a row into orders (user_id = 42):
--   1. PostgreSQL checks that user 42 exists in users.
--   2. To prevent user 42 from being deleted concurrently (between the check
--      and the commit), PostgreSQL acquires FOR KEY SHARE on the users row.
--   3. FOR KEY SHARE conflicts with FOR UPDATE and FOR NO KEY UPDATE
--      (anything that would delete or change the PK).
--   4. The lock is held until the child transaction commits.

-- Consequence: if another transaction is trying to DELETE FROM users WHERE id = 42
-- (which acquires FOR UPDATE on user 42), it will BLOCK until the INSERT into
-- orders commits — even though both are short transactions.

-- ── Observing FK locks ────────────────────────────────────────────────────────
-- Session A (child insert, doesn't commit):
BEGIN;
INSERT INTO orders (user_id, total) VALUES (42, 99.99);
-- (hold, do not commit yet)

-- Session B (concurrently viewing lock state):
SELECT
    pid,
    relation::regclass,
    mode,
    granted,
    page, tuple
FROM   pg_locks
WHERE  locktype = 'tuple'
AND    relation = 'users'::regclass;

-- pid │ relation │ mode          │ granted │ page │ tuple
-- ────┼──────────┼───────────────┼─────────┼──────┼──────
-- 123 │ users    │ KeyShareLock  │ t       │  0   │  42   ← FOR KEY SHARE on user row

-- Session C:
BEGIN;
DELETE FROM users WHERE id = 42;
-- → BLOCKS: DELETE needs FOR NO KEY UPDATE/FOR UPDATE, conflicts with KeyShareLock.
-- Session C unblocks only when Session A commits or rolls back.

-- ── The solution: missing indexes on FK columns ───────────────────────────────
-- When you DELETE FROM users WHERE id = 42, PostgreSQL must check if any orders
-- reference user 42. Without an index on orders.user_id, this is a seq scan on
-- orders — holding the lock for the entire scan duration.
-- With an index: the check is near-instant.

-- PostgreSQL does NOT automatically create an index on FK columns (unlike some databases).
-- ALWAYS create an index on every FK column in the child table:

CREATE INDEX idx_orders_user_id       ON orders(user_id);
CREATE INDEX idx_order_items_order_id  ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);

-- ── Finding FK columns missing indexes (critical maintenance query) ────────────
SELECT
    tc.table_name    AS child_table,
    kcu.column_name  AS fk_column,
    tc.constraint_name,
    'MISSING INDEX'  AS action_needed
FROM   information_schema.table_constraints    AS tc
JOIN   information_schema.key_column_usage     AS kcu
       USING (constraint_name, table_schema)
WHERE  tc.constraint_type = 'FOREIGN KEY'
AND    tc.table_schema     = 'public'
AND    NOT EXISTS (
    SELECT 1
    FROM   pg_index       AS ix
    JOIN   pg_attribute   AS a ON a.attrelid = ix.indrelid
                               AND a.attnum   = ANY(ix.indkey)
    WHERE  ix.indrelid = (tc.table_name)::regclass
    AND    a.attname   = kcu.column_name
);
-- → Any row returned = an FK without an index = potential lock contention + slow deletes.
```

## Section 2: Cascade Actions

**Q3. What are the five `ON DELETE` actions — what does each do and when do you choose each?**

A: The `ON DELETE` action specifies what PostgreSQL does to child rows when the referenced parent row is deleted. Each is a fundamentally different business rule encoded at the database level:

```sql
-- ── ON DELETE NO ACTION (default) ─────────────────────────────────────────────
-- "Do nothing about child rows — but FAIL if any exist at constraint check time."
-- The key distinction: NO ACTION defers the check to end of statement (or
-- end of transaction for DEFERRABLE constraints). It does NOT cascade anything.
-- Practically identical to RESTRICT in non-deferrable constraints.

CREATE TABLE orders (
    user_id BIGINT REFERENCES users(id) ON DELETE NO ACTION
);
DELETE FROM users WHERE id = 1;
-- ERROR: update or delete on table "users" violates foreign key constraint
--        "orders_user_id_fkey" on table "orders"
-- DETAIL: Key (id)=(1) is still referenced from table "orders".

-- ── ON DELETE RESTRICT ─────────────────────────────────────────────────────────
-- "Fail IMMEDIATELY if any child rows exist — no deferral even for DEFERRABLE FKs."
-- NO ACTION vs RESTRICT: RESTRICT fires at row-level (before statement completes).
-- NO ACTION fires at statement-level (after all rows in the statement are processed).
-- For non-deferrable constraints: identical behaviour.
-- For deferrable constraints: RESTRICT still fires immediately regardless of deferral.

CREATE TABLE order_items (
    product_id BIGINT REFERENCES products(id) ON DELETE RESTRICT
);
-- Even inside a transaction that defers constraint checking,
-- ON DELETE RESTRICT fires immediately when the DELETE runs.

-- ── ON DELETE CASCADE ─────────────────────────────────────────────────────────
-- "Delete all child rows automatically when the parent is deleted."
-- Use when child rows are OWNED BY the parent — they have no meaning without it.

CREATE TABLE orders (
    id      BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id) ON DELETE CASCADE
);
CREATE TABLE order_items (
    id       BIGSERIAL PRIMARY KEY,
    order_id BIGINT REFERENCES orders(id) ON DELETE CASCADE
);

DELETE FROM users WHERE id = 1;
-- → Deletes all orders for user 1 (via orders FK cascade).
-- → For each deleted order, deletes all order_items (via order_items FK cascade).
-- → THREE tables affected by ONE DELETE statement. Cascades chain.

-- DANGER: Cascades silently delete data. If you accidentally delete a parent,
-- all descendants are gone — no prompt, no error, no recovery without a backup.
-- Mitigations:
--   1. Audit triggers on parent tables.
--   2. Soft deletes (deleted_at column) instead of hard deletes.
--   3. Application-level explicit delete with confirmation.

-- ── ON DELETE SET NULL ────────────────────────────────────────────────────────
-- "Set the FK column to NULL when the parent is deleted."
-- Use when the child row can exist without a parent, but the reference should be cleared.
-- The FK column MUST be nullable.

CREATE TABLE posts (
    id         BIGSERIAL PRIMARY KEY,
    author_id  BIGINT REFERENCES users(id) ON DELETE SET NULL,  -- nullable
    title      TEXT NOT NULL,
    content    TEXT
);

DELETE FROM users WHERE id = 1;
-- → posts.author_id is set to NULL for all posts by user 1.
-- → Posts still exist; author is anonymous.
-- Use case: soft content moderation (delete the user, keep their content).

-- ── ON DELETE SET DEFAULT ─────────────────────────────────────────────────────
-- "Set the FK column to its DEFAULT value when the parent is deleted."
-- Rarely used in practice. The default must itself be a valid FK value
-- (must exist in the parent table), or also NULL (then same as SET NULL).

CREATE TABLE tasks (
    id          BIGSERIAL PRIMARY KEY,
    assigned_to BIGINT DEFAULT 1 REFERENCES users(id) ON DELETE SET DEFAULT
    -- If the assigned user is deleted, reassign to user 1 (the admin).
);
-- Caveat: if user 1 (the default) is also deleted, the constraint fires and fails.

-- ── Decision guide ─────────────────────────────────────────────────────────────
-- Parent:users ──→ Child:orders
--   Orders owned by user (meaningless without user) → ON DELETE CASCADE
-- Parent:users ──→ Child:posts (authored content)
--   Posts exist independently → ON DELETE SET NULL (author_id nullable)
-- Parent:products ──→ Child:order_items
--   Cannot delete a product if it's in an active order → ON DELETE RESTRICT
-- Parent:categories ──→ Child:products
--   Cannot delete a category with products → ON DELETE RESTRICT (or NO ACTION)
-- Parent:users ──→ Child:audit_logs
--   Logs must be kept even if user deleted → ON DELETE SET NULL (user_id nullable)
--   OR: no FK at all (denormalise user info into the log row)
```

**Q4. What does `ON UPDATE CASCADE` do — and when should you avoid it?**

A: `ON UPDATE CASCADE` propagates changes to a parent's referenced column (usually the PK) to all matching FK values in child rows. It is rarely needed when PKs are surrogate keys (integers, UUIDs) but becomes essential when using natural keys that change:

```sql
-- ── ON UPDATE CASCADE: propagating PK changes ─────────────────────────────────
-- Scenario: using a natural key (slug) as the referenced column

CREATE TABLE categories (
    slug  TEXT PRIMARY KEY,    -- Natural key — can change
    name  TEXT NOT NULL
);

CREATE TABLE products (
    id            BIGSERIAL PRIMARY KEY,
    category_slug TEXT REFERENCES categories(slug)
                  ON UPDATE CASCADE    -- propagate slug changes
                  ON DELETE RESTRICT   -- don't delete if products exist
);

INSERT INTO categories VALUES ('electronics', 'Electronics');
INSERT INTO products (category_slug) VALUES ('electronics');

-- Rename the category slug:
UPDATE categories SET slug = 'tech-gadgets' WHERE slug = 'electronics';
-- → ON UPDATE CASCADE fires:
--   UPDATE products SET category_slug = 'tech-gadgets'
--   WHERE  category_slug = 'electronics'
-- → All products automatically updated. No orphan rows.

-- ── Why ON UPDATE CASCADE is rarely needed with surrogate keys ────────────────
-- If your PK is BIGSERIAL or UUID, it never changes.
-- ON UPDATE CASCADE on a BIGSERIAL PK column: technically works, never fires.
-- Only needed for natural keys (slugs, codes, email-as-PK patterns).

-- ── ON UPDATE SET NULL and ON UPDATE SET DEFAULT ───────────────────────────────
-- Same semantics as ON DELETE variants, but triggered by parent UPDATE.
-- Extremely rare — ON UPDATE CASCADE covers the common case.

-- ── Full reference: all 5 actions for both events ─────────────────────────────
CREATE TABLE example (
    parent_id BIGINT REFERENCES parents(id)
        ON DELETE  NO ACTION      -- Default: fail at end of statement
        ON UPDATE  CASCADE        -- Propagate PK changes
);

-- Valid combinations for ON DELETE / ON UPDATE:
-- NO ACTION   — fail at end-of-statement (or deferred if DEFERRABLE)
-- RESTRICT    — fail immediately at row level (ignores deferral)
-- CASCADE     — delete/update matching child rows
-- SET NULL    — set FK column to NULL (column must be nullable)
-- SET DEFAULT — set FK column to DEFAULT value
```

**Q5. How do cascades chain — and what are the dangers of deep cascade trees?**

A: Cascades chain recursively: deleting a parent triggers deletion of its children, which triggers deletion of their children, and so on. PostgreSQL handles this correctly but the implications for locking, performance, and accidental data loss are significant:

```sql
-- ── Deep cascade chain example ────────────────────────────────────────────────
CREATE TABLE tenants (id BIGSERIAL PRIMARY KEY, name TEXT);
CREATE TABLE users   (id BIGSERIAL PRIMARY KEY, tenant_id BIGINT REFERENCES tenants(id) ON DELETE CASCADE);
CREATE TABLE orders  (id BIGSERIAL PRIMARY KEY, user_id   BIGINT REFERENCES users(id)   ON DELETE CASCADE);
CREATE TABLE items   (id BIGSERIAL PRIMARY KEY, order_id  BIGINT REFERENCES orders(id)  ON DELETE CASCADE);
CREATE TABLE refunds (id BIGSERIAL PRIMARY KEY, item_id   BIGINT REFERENCES items(id)   ON DELETE CASCADE);

DELETE FROM tenants WHERE id = 1;
-- PostgreSQL executes (in this order):
-- 1. DELETE FROM refunds WHERE item_id  IN (SELECT id FROM items WHERE order_id IN ...)
-- 2. DELETE FROM items   WHERE order_id IN (SELECT id FROM orders WHERE user_id IN ...)
-- 3. DELETE FROM orders  WHERE user_id  IN (SELECT id FROM users WHERE tenant_id = 1)
-- 4. DELETE FROM users   WHERE tenant_id = 1
-- 5. DELETE FROM tenants WHERE id = 1
-- All in ONE transaction — all or nothing.

-- ── Dangers ────────────────────────────────────────────────────────────────────
-- 1. Silent bulk deletion: one DELETE removes millions of rows across 5 tables.
--    No warning, no confirmation, no "are you sure?".

-- 2. Long-running transaction + lock accumulation:
--    Each cascade step acquires ROW EXCLUSIVE locks on the affected tables.
--    If any step is slow (no FK index, large table), the entire chain blocks.
--    Other transactions wanting locks on any of these tables queue up.

-- 3. Trigger interactions:
--    If any cascaded table has row-level triggers (audit, soft-delete),
--    they fire for EACH cascaded row — potentially thousands of trigger executions.
--    TRUNCATE does not fire row-level triggers; cascaded DELETE does.

-- 4. Circular cascade detection:
--    PostgreSQL detects and prevents infinite loops:
--    A → B → A  would cause: ERROR: infinite recursion detected in rules
--    Self-referential cascades are handled specially (see Q9).

-- ── Mitigating cascade risks ──────────────────────────────────────────────────
-- Option A: Soft deletes — add deleted_at TIMESTAMPTZ instead of hard delete.
--   No cascade, no data loss, full audit trail.
--   Application filters WHERE deleted_at IS NULL.

-- Option B: Audit trigger before cascade fires:
CREATE OR REPLACE FUNCTION log_before_delete()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO deletion_audit (table_name, row_id, deleted_at, deleted_by)
    VALUES (TG_TABLE_NAME, OLD.id, NOW(), current_setting('app.current_user_id', TRUE));
    RETURN OLD;
END;
$$;

CREATE TRIGGER audit_orders_delete
    BEFORE DELETE ON orders
    FOR EACH ROW EXECUTE FUNCTION log_before_delete();
-- Fires for every order deleted via cascade — maintains an audit trail.

-- Option C: Explicit application-managed deletion with checks:
-- Instead of FK cascade, remove the FK and handle deletion order in the application.
-- Gives full control: check counts, log, notify, then delete leaf tables first.

-- ── Checking existing cascade chains in a schema ──────────────────────────────
WITH RECURSIVE fk_tree AS (
    SELECT
        tc.table_name         AS child,
        ccu.table_name        AS parent,
        rc.delete_rule,
        1                     AS depth
    FROM   information_schema.table_constraints       tc
    JOIN   information_schema.constraint_column_usage ccu USING (constraint_name, table_schema)
    JOIN   information_schema.referential_constraints rc  USING (constraint_name, table_schema)
    WHERE  tc.constraint_type = 'FOREIGN KEY'
    AND    rc.delete_rule     = 'CASCADE'

    UNION ALL

    SELECT
        tc.table_name,
        ccu.table_name,
        rc.delete_rule,
        ft.depth + 1
    FROM   information_schema.table_constraints       tc
    JOIN   information_schema.constraint_column_usage ccu USING (constraint_name, table_schema)
    JOIN   information_schema.referential_constraints rc  USING (constraint_name, table_schema)
    JOIN   fk_tree ft ON tc.table_name = ft.child
    WHERE  tc.constraint_type = 'FOREIGN KEY'
    AND    rc.delete_rule     = 'CASCADE'
    AND    ft.depth < 10  -- Prevent runaway recursion
)
SELECT DISTINCT parent, child, depth
FROM   fk_tree
ORDER  BY depth, parent;
-- Shows every cascade chain in your schema — depth > 3 warrants careful review.
```

## Section 3: Deferrable Constraints

**Q6. What does `DEFERRABLE` mean — what is the difference between `INITIALLY IMMEDIATE` and `INITIALLY DEFERRED`?**

A: By default, every FK constraint is checked at the end of each statement (immediately). `DEFERRABLE` moves that check to the end of the transaction, allowing intermediate states that would otherwise violate the constraint. This is essential for certain data mutation patterns:

```sql
-- ── Non-deferrable (default): constraint checked after EACH statement ──────────
CREATE TABLE nodes (
    id        BIGSERIAL PRIMARY KEY,
    parent_id BIGINT REFERENCES nodes(id)  -- Non-deferrable (default)
);
-- Try to insert a node that references a parent that doesn't exist yet:
INSERT INTO nodes (id, parent_id) VALUES (2, 1);  -- parent 1 doesn't exist yet
-- ERROR: insert or update on table "nodes" violates foreign key constraint
-- There is no way to insert two mutually-referencing rows — one must always exist first.

-- ── DEFERRABLE INITIALLY IMMEDIATE ────────────────────────────────────────────
-- Constraint CAN be deferred, but defaults to checking after each statement.
-- You opt in to deferral per-transaction using SET CONSTRAINTS.
CREATE TABLE nodes (
    id        BIGSERIAL PRIMARY KEY,
    parent_id BIGINT REFERENCES nodes(id)
              DEFERRABLE INITIALLY IMMEDIATE  -- Can defer, defaults to immediate
);

-- Default behaviour (no deferral) — same as non-deferrable:
INSERT INTO nodes (id, parent_id) VALUES (2, 1);
-- ERROR: still fails — IMMEDIATE mode checks after each statement.

-- Opted-in deferral — within a transaction:
BEGIN;
SET CONSTRAINTS ALL DEFERRED;  -- Switch all deferrable constraints to DEFERRED
-- Or target a specific constraint:
-- SET CONSTRAINTS fk_nodes_parent DEFERRED;

INSERT INTO nodes (id, parent_id) VALUES (1, 2);  -- parent 2 doesn't exist yet
INSERT INTO nodes (id, parent_id) VALUES (2, 1);  -- parent 1 doesn't exist yet
COMMIT;  -- BOTH FK checks run here — both now satisfy each other ✓

-- ── DEFERRABLE INITIALLY DEFERRED ─────────────────────────────────────────────
-- Constraint is ALWAYS deferred until COMMIT, unless explicitly made immediate.
-- Automatically deferral — no SET CONSTRAINTS needed.
CREATE TABLE nodes (
    id        BIGSERIAL PRIMARY KEY,
    parent_id BIGINT REFERENCES nodes(id)
              DEFERRABLE INITIALLY DEFERRED   -- Always deferred by default
);

BEGIN;
INSERT INTO nodes (id, parent_id) VALUES (1, 2);  -- No error — check deferred
INSERT INTO nodes (id, parent_id) VALUES (2, 1);  -- No error — check deferred
COMMIT;  -- Both constraints checked here — both valid ✓

-- Making it immediate within a transaction (override):
BEGIN;
SET CONSTRAINTS fk_nodes_parent IMMEDIATE;  -- Override to immediate for this tx
INSERT INTO nodes (id, parent_id) VALUES (1, 2);
-- ERROR: parent 2 doesn't exist — immediate check fires after this statement.
ROLLBACK;

-- ── Summary table ─────────────────────────────────────────────────────────────
-- Mode                            When is FK checked?
-- ─────────────────────────────────────────────────────────────────────────────
-- NOT DEFERRABLE (default)        After each statement, always
-- DEFERRABLE INITIALLY IMMEDIATE  After each statement (unless SET CONSTRAINTS DEFERRED)
-- DEFERRABLE INITIALLY DEFERRED   At COMMIT (unless SET CONSTRAINTS IMMEDIATE)
```

**Q7. What are the real-world use cases for deferrable constraints — walk through a concrete scenario for each?**

A: There are four canonical scenarios where deferrable constraints are not just convenient but required for correctness:

```sql
-- ── Use Case 1: Circular references (mutual parent-child) ─────────────────────
-- Departments have a manager (a user); users belong to a department.
-- Neither can be inserted first if both FKs are non-deferrable.

CREATE TABLE departments (
    id         BIGSERIAL PRIMARY KEY,
    name       TEXT NOT NULL,
    manager_id BIGINT REFERENCES employees(id) DEFERRABLE INITIALLY DEFERRED
);

CREATE TABLE employees (
    id            BIGSERIAL PRIMARY KEY,
    name          TEXT NOT NULL,
    department_id BIGINT REFERENCES departments(id) DEFERRABLE INITIALLY DEFERRED
);

BEGIN;
INSERT INTO departments (id, name, manager_id) VALUES (1, 'Engineering', 101);
-- → No error: manager_id = 101 check deferred.
INSERT INTO employees (id, name, department_id) VALUES (101, 'Alice', 1);
-- → No error: department_id = 1 exists now; employee 101 check deferred.
COMMIT;
-- Both checks fire: department 1 exists ✓, employee 101 exists ✓

-- ── Use Case 2: Reordering items with a unique ordering column ─────────────────
-- Items in a playlist have a UNIQUE position (1, 2, 3, ...).
-- Moving item from position 2 to position 1 requires:
--   UPDATE items SET position = 1 WHERE id = B;  -- Fails: position 1 already taken
--   UPDATE items SET position = 2 WHERE id = A;  -- Fails: position 2 already taken
-- Both updates violate uniqueness immediately. Need deferral.

CREATE TABLE playlist_items (
    id          BIGSERIAL PRIMARY KEY,
    playlist_id BIGINT NOT NULL,
    position    INT    NOT NULL,
    track_id    BIGINT NOT NULL,
    CONSTRAINT  uq_playlist_position UNIQUE (playlist_id, position)
                DEFERRABLE INITIALLY DEFERRED  -- Unique constraints can also be deferred
);

BEGIN;
SET CONSTRAINTS uq_playlist_position DEFERRED;
UPDATE playlist_items SET position = 3 WHERE id = A;  -- Temporary value
UPDATE playlist_items SET position = 1 WHERE id = B;
UPDATE playlist_items SET position = 2 WHERE id = A;
COMMIT;  -- Uniqueness checked here — all positions unique ✓

-- Alternative without deferral: use a temporary "impossible" value:
BEGIN;
UPDATE playlist_items SET position = -1  WHERE id = A;  -- Temp: no conflict
UPDATE playlist_items SET position =  1  WHERE id = B;
UPDATE playlist_items SET position =  2  WHERE id = A;
COMMIT;
-- Works but is a hack — deferral is cleaner.

-- ── Use Case 3: Bulk data loading / migration ─────────────────────────────────
-- Loading a large dataset where parent and child rows arrive in arbitrary order.
-- Non-deferrable: must sort rows, load parents first, then children.
-- Deferrable: load in any order, let DB sort it out at commit.

BEGIN;
SET CONSTRAINTS ALL DEFERRED;

COPY order_items (id, order_id, product_id, quantity, price)
FROM '/tmp/items.csv' CSV HEADER;
-- Some items may reference orders not yet inserted — deferred, no error.

COPY orders (id, user_id, total, status)
FROM '/tmp/orders.csv' CSV HEADER;
-- Orders may reference users not yet inserted — deferred, no error.

COPY users (id, email, name)
FROM '/tmp/users.csv' CSV HEADER;

COMMIT;
-- ALL FK checks fire: if any reference is invalid, the entire load rolls back ✓
-- No need to sort the CSV files or use multiple passes.

-- ── Use Case 4: UPSERT / replace patterns ─────────────────────────────────────
-- Replacing a parent row's PK value (rare but needed for natural keys):

ALTER TABLE categories ADD CONSTRAINT uq_categories_id UNIQUE (id)
    DEFERRABLE INITIALLY DEFERRED;

BEGIN;
-- Reassign all products to a new category ID:
UPDATE products SET category_id = 999 WHERE category_id = 1;
-- → Deferred: new category 999 doesn't exist yet — OK.
UPDATE categories SET id = 999 WHERE id = 1;
-- → Deferred: old category 1 still referenced... temporarily.
COMMIT;
-- FK checks fire: all products now point to category 999 which exists ✓
```

**Q8. How do you use `SET CONSTRAINTS` to control deferral at the transaction level — and what constraints can be deferred?**

A: `SET CONSTRAINTS` is the per-transaction override mechanism. Only `DEFERRABLE` constraints respond to it — `NOT DEFERRABLE` constraints are always immediate and ignore `SET CONSTRAINTS`:

```sql
-- ── SET CONSTRAINTS syntax ────────────────────────────────────────────────────

-- Defer ALL deferrable constraints in this transaction:
SET CONSTRAINTS ALL DEFERRED;

-- Defer a specific named constraint:
SET CONSTRAINTS fk_orders_user_id DEFERRED;

-- Defer multiple named constraints:
SET CONSTRAINTS fk_orders_user_id, fk_items_order_id DEFERRED;

-- Make a INITIALLY DEFERRED constraint check immediately (override):
SET CONSTRAINTS fk_nodes_parent IMMEDIATE;
-- → Any violation is checked NOW for all rows modified so far in the transaction.

-- ── What can be deferred ──────────────────────────────────────────────────────
-- FK constraints:     DEFERRABLE applies ✓
-- UNIQUE constraints: DEFERRABLE applies ✓ (see Use Case 2 above)
-- PRIMARY KEY:        DEFERRABLE applies ✓ (rarely useful)
-- CHECK constraints:  NOT deferrable in PostgreSQL (always immediate)
-- NOT NULL:           NOT deferrable (column-level constraint, always immediate)
-- EXCLUDE:            DEFERRABLE applies ✓

-- ── Verifying deferral state for a transaction ────────────────────────────────
-- There is no direct way to query the current deferral state in pg_catalog.
-- Use pg_constraint to check if a constraint is deferrable:
SELECT
    conname,
    contype,           -- f=foreign key, u=unique, p=primary key
    condeferrable,     -- TRUE if DEFERRABLE was declared
    condeferred        -- TRUE if INITIALLY DEFERRED
FROM   pg_constraint
WHERE  conrelid = 'orders'::regclass;

-- ── Deferrable constraints in TypeORM ────────────────────────────────────────
-- TypeORM does not natively generate DEFERRABLE in @JoinColumn decorators.
-- Must use raw migration SQL:
await queryRunner.query(`
    ALTER TABLE orders
        ADD CONSTRAINT fk_orders_user_id
        FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE NO ACTION
        DEFERRABLE INITIALLY DEFERRED
`);

-- To use SET CONSTRAINTS in a TypeORM transaction:
await dataSource.transaction(async (manager) => {
    await manager.query('SET CONSTRAINTS ALL DEFERRED');
    // Now safe to insert in any order within this transaction
    await manager.save(Node, { id: 1, parentId: 2 });
    await manager.save(Node, { id: 2, parentId: 1 });
    // FK checks run at COMMIT
});
```

## Section 4: Performance Implications

**Q9. What are all the performance implications of foreign keys — indexes, lock contention, and write amplification?**

A: Foreign keys impose overhead on every DML operation that touches the constrained columns. Understanding each source of overhead is essential for designing high-throughput schemas:

```sql
-- ── 1. Missing FK index: catastrophic DELETE/UPDATE performance ────────────────
-- Scenario: DELETE FROM users WHERE id = 42.
-- PostgreSQL must check: does any orders row reference user 42?
-- Without index on orders.user_id:
--   → Sequential scan of orders (500k rows) to check for references
--   → During this scan, a RowShareLock is held on orders
--   → Other operations on orders block for the scan duration

EXPLAIN ANALYZE
SELECT 1 FROM orders WHERE user_id = 42 LIMIT 1;
-- WITHOUT INDEX:
-- Seq Scan on orders  (cost=0.00..18432.00 ...) (actual time=312.4 ms ...)
-- WITH INDEX:
-- Index Scan using idx_orders_user_id on orders  (actual time=0.08 ms ...)

-- Rule: create an index on EVERY foreign key column in child tables.
-- Exception: if the child table is tiny (<1000 rows) — seq scan is fast enough.

-- ── 2. Write amplification from cascades ──────────────────────────────────────
-- ON DELETE CASCADE causes additional DELETE statements.
-- Each cascaded DELETE is a full write operation with its own:
--   • Index updates (for each index on the child table)
--   • WAL records
--   • Lock acquisitions
--   • Trigger firings (if any triggers exist on child)

-- Measure cascade impact:
EXPLAIN ANALYZE DELETE FROM users WHERE id = 1;
-- Planning Time: ...
-- Trigger for constraint fk_orders_user_id: time=... calls=1
-- Trigger for constraint fk_items_order_id: time=... calls=1
-- Execution Time: 2341.432 ms  ← includes cascade time

-- ── 3. FK check on every INSERT into child ─────────────────────────────────────
-- Every INSERT into orders must verify user_id exists in users.
-- Cost: one index lookup on users.id per INSERT row.
-- With a PK index on users.id: ~0.1 ms per insert (negligible).
-- Without a PK (unusual but possible for heap-only tables): seq scan → catastrophic.

-- ── 4. Bulk insert with FK verification: use DISABLE TRIGGER ──────────────────
-- For trusted bulk data loads where FK validity is guaranteed externally:
BEGIN;
-- Disable FK trigger checks for this session (SUPERUSER only):
ALTER TABLE order_items DISABLE TRIGGER ALL;

COPY order_items FROM '/tmp/items.csv' CSV HEADER;

ALTER TABLE order_items ENABLE TRIGGER ALL;
COMMIT;
-- Risk: if any row violates the FK, the constraint is now broken silently.
-- Safer: use SET CONSTRAINTS ALL DEFERRED instead (validates at COMMIT).

-- ── 5. Partitioned tables and foreign keys ─────────────────────────────────────
-- PostgreSQL does not support FK constraints pointing TO a partitioned table
-- (as of PostgreSQL 16 — this restriction may be lifted in future versions).
-- Workaround: reference the parent partition, or handle referential integrity
-- at the application level for partitioned parent tables.

-- FK FROM a partitioned table TO a regular table: supported ✓
-- FK FROM a regular table TO a partitioned table: NOT supported ✗

-- ── 6. FK and connection pooling (PgBouncer transaction mode) ─────────────────
-- DEFERRABLE INITIALLY DEFERRED + SET CONSTRAINTS requires the entire
-- transaction to run on the same database connection.
-- PgBouncer in transaction mode assigns connections per-transaction — safe ✓.
-- PgBouncer in statement mode: SET CONSTRAINTS is lost between statements — UNSAFE ✗.
-- Always use transaction or session mode when using deferrable constraints.
```

## Section 5: Self-Referential and Composite Foreign Keys

**Q10. How do self-referential foreign keys work — what are the patterns for hierarchical data?**

A: A self-referential FK references the same table it is in. This is the standard model for tree-structured data: categories, org charts, threaded comments, file systems. It requires special consideration for inserts, deletes, and queries:

```sql
-- ── Adjacency list model (most common self-referential pattern) ───────────────
CREATE TABLE categories (
    id        BIGSERIAL PRIMARY KEY,
    parent_id BIGINT REFERENCES categories(id)
              ON DELETE RESTRICT       -- Prevent deleting a category with sub-categories
              DEFERRABLE INITIALLY DEFERRED,  -- Allow bulk inserts in any order
    name      TEXT NOT NULL,
    slug      TEXT NOT NULL UNIQUE,
    depth     INT  NOT NULL DEFAULT 0  -- Denormalised for fast depth queries
);

-- Insert root category (no parent):
INSERT INTO categories (name, slug) VALUES ('Electronics', 'electronics');

-- Insert child category:
INSERT INTO categories (name, slug, parent_id, depth)
VALUES ('Laptops', 'laptops', 1, 1);  -- parent 1 must exist → FK check

-- ── Recursive delete (leaf-first ordering) ───────────────────────────────────
-- ON DELETE RESTRICT prevents deleting a parent with children.
-- Must delete leaf-first:
WITH RECURSIVE subtree AS (
    SELECT id FROM categories WHERE id = 1  -- Root to delete
    UNION ALL
    SELECT c.id FROM categories c
    JOIN subtree s ON c.parent_id = s.id    -- All descendants
)
DELETE FROM categories
WHERE id IN (SELECT id FROM subtree)
ORDER BY depth DESC;  -- Delete deepest first (leaves before parents)

-- ── Circular reference prevention ────────────────────────────────────────────
-- PostgreSQL does NOT prevent cycles in self-referential FKs automatically.
-- A → B → C → A is a valid FK chain (each references a valid parent).
-- Prevent cycles in application code or with a trigger:

CREATE OR REPLACE FUNCTION prevent_category_cycle()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
DECLARE
    ancestor_id BIGINT;
BEGIN
    IF NEW.parent_id IS NULL THEN RETURN NEW; END IF;

    WITH RECURSIVE ancestors AS (
        SELECT id, parent_id FROM categories WHERE id = NEW.parent_id
        UNION ALL
        SELECT c.id, c.parent_id FROM categories c
        JOIN ancestors a ON a.parent_id = c.id
    )
    SELECT id INTO ancestor_id
    FROM   ancestors
    WHERE  id = NEW.id;

    IF FOUND THEN
        RAISE EXCEPTION 'Circular reference detected: category % would be its own ancestor', NEW.id;
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_prevent_category_cycle
    BEFORE INSERT OR UPDATE ON categories
    FOR EACH ROW EXECUTE FUNCTION prevent_category_cycle();

-- ── Querying hierarchies with recursive CTEs ──────────────────────────────────
-- All descendants of category 1:
WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 0 AS depth,
           ARRAY[id] AS path    -- Track path for cycle detection in queries
    FROM   categories WHERE id = 1

    UNION ALL

    SELECT c.id, c.name, c.parent_id, t.depth + 1,
           t.path || c.id
    FROM   categories c
    JOIN   tree t ON c.parent_id = t.id
    WHERE  NOT c.id = ANY(t.path)  -- Prevent infinite loop if cycle exists
)
SELECT id, name, depth,
       repeat('  ', depth) || name AS indented_name
FROM   tree
ORDER  BY path;

-- ── Self-referential in TypeORM ───────────────────────────────────────────────
@Entity()
export class Category {
    @PrimaryGeneratedColumn()
    id: number;

    @Column({ nullable: true })
    parentId: number | null;

    @ManyToOne(() => Category, cat => cat.children, { nullable: true })
    @JoinColumn({ name: 'parent_id' })
    parent: Category | null;

    @OneToMany(() => Category, cat => cat.parent)
    children: Category[];

    @Column()
    name: string;

    @Column({ unique: true })
    slug: string;
}
// TypeORM generates: REFERENCES categories(id) — self-referential ✓
// Does NOT generate DEFERRABLE — add via migration if needed for bulk inserts.
```

**Q11. How do composite foreign keys work — and when are they necessary?**

A: A composite FK references a composite unique key (or composite PK) in the parent. The number and types of columns must match exactly. They are necessary when the parent table's identity requires multiple columns — often in multi-tenant or time-versioned schemas:

```sql
-- ── Composite PK referenced by composite FK ───────────────────────────────────
-- Multi-tenant schema: every entity scoped to a tenant.
-- The PK is (tenant_id, id) — globally unique per tenant.

CREATE TABLE tenants (
    id   BIGSERIAL PRIMARY KEY,
    slug TEXT NOT NULL UNIQUE
);

CREATE TABLE products (
    tenant_id  BIGINT NOT NULL REFERENCES tenants(id),
    id         BIGSERIAL NOT NULL,
    name       TEXT NOT NULL,
    price      NUMERIC(10,2),
    PRIMARY KEY (tenant_id, id)   -- Composite PK
);

CREATE TABLE orders (
    tenant_id  BIGINT NOT NULL REFERENCES tenants(id),
    id         BIGSERIAL NOT NULL,
    user_id    BIGINT NOT NULL,
    PRIMARY KEY (tenant_id, id)
);

CREATE TABLE order_items (
    tenant_id  BIGINT NOT NULL,
    id         BIGSERIAL NOT NULL,
    order_id   BIGINT NOT NULL,
    product_id BIGINT NOT NULL,

    PRIMARY KEY (tenant_id, id),

    -- Composite FK: references (tenant_id, id) in orders
    CONSTRAINT fk_items_order
        FOREIGN KEY (tenant_id, order_id)
        REFERENCES orders(tenant_id, id)
        ON DELETE CASCADE,

    -- Composite FK: references (tenant_id, id) in products
    CONSTRAINT fk_items_product
        FOREIGN KEY (tenant_id, product_id)
        REFERENCES products(tenant_id, id)
        ON DELETE RESTRICT
);
-- This guarantees: an order item can only reference an order and product
-- belonging to the SAME tenant. Cross-tenant references are impossible at DB level.

-- ── Index on composite FK ─────────────────────────────────────────────────────
-- Index must cover ALL FK columns in the same order:
CREATE INDEX idx_items_order   ON order_items(tenant_id, order_id);
CREATE INDEX idx_items_product ON order_items(tenant_id, product_id);
-- NOT sufficient: CREATE INDEX ON order_items(order_id) — missing tenant_id.

-- ── Composite FK in TypeORM ───────────────────────────────────────────────────
@Entity()
@Index(['tenantId', 'orderId'])  -- Must index all FK columns
export class OrderItem {
    @PrimaryGeneratedColumn()
    id: number;

    @Column()
    tenantId: number;

    @Column()
    orderId: number;

    @Column()
    productId: number;

    @ManyToOne(() => Order)
    @JoinColumn([
        { name: 'tenant_id', referencedColumnName: 'tenantId' },
        { name: 'order_id',  referencedColumnName: 'id'       },
    ])
    order: Order;

    @ManyToOne(() => Product)
    @JoinColumn([
        { name: 'tenant_id',  referencedColumnName: 'tenantId' },
        { name: 'product_id', referencedColumnName: 'id'       },
    ])
    product: Product;
}
```

## Section 6: TypeORM Implementation

**Q12. How do you model all FK relationship types in TypeORM — and what are the common pitfalls?**

A: TypeORM's `@ManyToOne`, `@OneToMany`, `@OneToOne`, and `@ManyToMany` decorators generate FK constraints. The pitfalls are in the defaults TypeORM chooses for cascade, `onDelete`, and `nullable`:

```typescript
import {
    Entity, PrimaryGeneratedColumn, Column,
    ManyToOne, OneToMany, OneToOne, ManyToMany,
    JoinColumn, JoinTable, CreateDateColumn,
    Index,
} from 'typeorm';

// ── Many-to-One (most common: child has FK to parent) ─────────────────────────
@Entity()
export class Order {
    @PrimaryGeneratedColumn()
    id: number;

    // @ManyToOne generates: user_id BIGINT NOT NULL REFERENCES users(id)
    // Default onDelete: 'NO ACTION' — no cascade
    // nullable: false → NOT NULL (correct for required relationships)
    @ManyToOne(() => User, user => user.orders, {
        nullable: false,       // NOT NULL FK column (default: true = nullable)
        onDelete: 'CASCADE',   // SQL-level: ON DELETE CASCADE
        // Note: this is DIFFERENT from TypeORM-level cascade (see below)
    })
    @JoinColumn({ name: 'user_id' })  // Explicit column name (otherwise TypeORM guesses)
    @Index()                          // ALWAYS add index to FK column
    user: User;

    @Column({ name: 'user_id' })
    userId: number;  // Expose FK column directly for queries without JOIN
}

@Entity()
export class User {
    @PrimaryGeneratedColumn()
    id: number;

    @OneToMany(() => Order, order => order.user)
    // OneToMany does NOT generate any FK — the FK is on the child (Order.userId)
    // cascade: true here means TypeORM will save/remove orders when saving the User
    // This is APPLICATION-LEVEL cascade (TypeORM), NOT SQL-level ON DELETE CASCADE.
    orders: Order[];
}

// ── CRITICAL: TypeORM cascade vs SQL ON DELETE CASCADE ────────────────────────
// TypeORM { cascade: true } on @OneToMany:
//   → When you call userRepo.save(user) and user.orders has new orders,
//     TypeORM also saves those orders in a separate SQL statement.
//   → Does NOT generate ON DELETE CASCADE in SQL.
//   → If you delete a user via SQL: DELETE FROM users WHERE id = 1
//     TypeORM cascade does NOT fire — orphan orders remain.

// SQL onDelete: 'CASCADE' on @ManyToOne:
//   → Generates: REFERENCES users(id) ON DELETE CASCADE in SQL.
//   → Fires at the DATABASE level for ALL deletes (SQL, TypeORM, triggers).
//   → TypeORM cascade option has no effect on SQL-level deletes.

// Best practice: use SQL-level onDelete for data integrity,
// TypeORM cascade for convenience in application code (saves, removes).

// ── One-to-One ────────────────────────────────────────────────────────────────
@Entity()
export class UserProfile {
    @PrimaryGeneratedColumn()
    id: number;

    // FK is on UserProfile, not on User.
    @OneToOne(() => User, { onDelete: 'CASCADE' })
    @JoinColumn({ name: 'user_id' })  // JoinColumn MUST be on the FK-owning side
    @Index({ unique: true })           // FK + UNIQUE → one profile per user
    user: User;

    @Column({ name: 'user_id', unique: true })
    userId: number;

    @Column({ nullable: true })
    bio: string;
}

// ── Many-to-Many (generates a join table with two FKs) ────────────────────────
@Entity()
export class Product {
    @PrimaryGeneratedColumn()
    id: number;

    @ManyToMany(() => Tag, tag => tag.products, {
        cascade: ['insert', 'update'],  // TypeORM-level: auto-save tags
    })
    @JoinTable({
        name: 'product_tags',           // Explicit join table name
        joinColumn:        { name: 'product_id', referencedColumnName: 'id' },
        inverseJoinColumn: { name: 'tag_id',     referencedColumnName: 'id' },
    })
    tags: Tag[];
}

// TypeORM generates product_tags:
-- CREATE TABLE product_tags (
--     product_id BIGINT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
--     tag_id     BIGINT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
--     PRIMARY KEY (product_id, tag_id)
-- );
-- Note: TypeORM always adds ON DELETE CASCADE on join table FKs (not configurable).

// ── Common pitfalls ───────────────────────────────────────────────────────────

// Pitfall 1: Missing @Index() on FK columns
// TypeORM does NOT auto-create indexes on FK columns.
// You must add @Index() explicitly or create them in migrations.
@Column({ name: 'user_id' })
@Index()  // ← Must be explicit
userId: number;

// Pitfall 2: Nullable FK when NOT NULL is intended
@ManyToOne(() => User)  // Default nullable: true → allows orphan rows
user: User;
// Fix:
@ManyToOne(() => User, user => user.orders, { nullable: false })
user: User;

// Pitfall 3: Forgetting to expose the FK column ID
// Without userId column, you must JOIN to get user_id:
// BAD:  const userId = (await order.user).id   ← lazy loads user just for the ID
// GOOD: order.userId                            ← available without JOIN
@Column({ name: 'user_id' })
userId: number;  // Explicit FK column accessor

// Pitfall 4: TypeORM cascade removing unintended data
@OneToMany(() => Order, o => o.user, { cascade: ['remove'] })
orders: Order[];
// If cascade: ['remove'] is set AND you call userRepo.remove(user):
// TypeORM executes DELETE for each order individually (N+1 deletes).
// For bulk removal: use SQL-level ON DELETE CASCADE instead.

// ── Adding deferrable constraints via migration ────────────────────────────────
export class MakeFkDeferrable1700000000001 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<void> {
        // TypeORM cannot generate DEFERRABLE — must use raw SQL:
        await queryRunner.query(`
            ALTER TABLE nodes
                DROP CONSTRAINT IF EXISTS fk_nodes_parent,
                ADD  CONSTRAINT fk_nodes_parent
                     FOREIGN KEY (parent_id)
                     REFERENCES nodes(id)
                     ON DELETE RESTRICT
                     DEFERRABLE INITIALLY DEFERRED
        `);
    }

    public async down(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`
            ALTER TABLE nodes
                DROP CONSTRAINT IF EXISTS fk_nodes_parent,
                ADD  CONSTRAINT fk_nodes_parent
                     FOREIGN KEY (parent_id)
                     REFERENCES nodes(id)
                     ON DELETE RESTRICT
        `);
    }
}
```

## Section 7: Managing FK Constraints

**Q13. How do you add, validate, and drop FK constraints on large live tables without downtime?**

A: Adding a FK to an existing table with millions of rows requires a full scan to validate existing data. Doing this naively takes an `ACCESS EXCLUSIVE` lock for the entire scan duration — potentially minutes of downtime:

```sql
-- ── WRONG: blocking FK addition on a large table ──────────────────────────────
ALTER TABLE orders ADD CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id) REFERENCES users(id);
-- → ACCESS EXCLUSIVE lock on orders (blocks ALL reads and writes)
-- → Full table scan to validate existing data
-- → On 50M rows: potentially minutes of complete table unavailability.

-- ── CORRECT: two-phase non-blocking FK addition ───────────────────────────────

-- Phase 1: Add the constraint WITHOUT validating existing rows (near-instant lock):
ALTER TABLE orders ADD CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id) REFERENCES users(id)
    NOT VALID;
-- → Brief ACCESS EXCLUSIVE (metadata only — no row scanning).
-- → New INSERTs and UPDATEs are immediately checked.
-- → Existing rows are NOT validated yet — the constraint is "not valid".
-- → Table is available again in milliseconds.

-- Phase 2: Validate existing rows (SHARE UPDATE EXCLUSIVE — non-blocking):
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_user;
-- → Acquires SHARE UPDATE EXCLUSIVE (allows concurrent reads AND writes).
-- → Scans existing rows to verify all user_id values exist in users.
-- → Can run during normal business hours on a live table.
-- → If any violation is found: ERROR — the constraint remains NOT VALID.

-- ── Checking constraint validity ──────────────────────────────────────────────
SELECT conname, convalidated
FROM   pg_constraint
WHERE  conrelid = 'orders'::regclass
AND    contype  = 'f';

-- conname           │ convalidated
-- ──────────────────┼──────────────
-- fk_orders_user    │ f   ← NOT YET VALIDATED (queries cannot assume it's enforced)
-- After VALIDATE:
-- fk_orders_user    │ t   ← VALID (planner can use FK for query optimisation)

-- ── IMPORTANT: NOT VALID FK is still enforced for NEW rows ────────────────────
-- Between Phase 1 and Phase 2, the constraint state is:
-- • New INSERTs:  FK is checked ✓
-- • New UPDATEs:  FK column changes are checked ✓
-- • Existing rows: NOT checked — may contain violations
-- This is safe for new-code deployments where existing data is trusted.

-- ── Dropping a FK constraint ──────────────────────────────────────────────────
-- Also requires ACCESS EXCLUSIVE briefly, but no row scanning:
ALTER TABLE orders DROP CONSTRAINT fk_orders_user;
-- → Near-instant. Only removes the constraint metadata.

-- On large live tables: set lock_timeout to avoid queue blockage:
SET lock_timeout = '3s';
ALTER TABLE orders DROP CONSTRAINT fk_orders_user;
-- If the lock cannot be acquired in 3s: ERROR (retry during lower traffic).

-- ── In a TypeORM migration (non-blocking pattern) ─────────────────────────────
export class AddFkNonBlocking1700000000002 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<void> {
        // Step 1: ensure FK index exists (create it CONCURRENTLY first):
        await queryRunner.query(`
            CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user_id
            ON orders(user_id)
        `);

        // Step 2: add FK with NOT VALID (near-instant):
        await queryRunner.query(`
            ALTER TABLE orders
            ADD CONSTRAINT fk_orders_user_id
            FOREIGN KEY (user_id)
            REFERENCES users(id)
            ON DELETE NO ACTION
            NOT VALID
        `);

        // Step 3: validate (non-blocking, but may take a while):
        await queryRunner.query(`
            ALTER TABLE orders
            VALIDATE CONSTRAINT fk_orders_user_id
        `);
        // Note: VALIDATE cannot run inside an explicit transaction in TypeORM migrations.
        // TypeORM migrations run in transactions by default — split into two migrations
        // if the validate step needs to run outside a transaction.
    }

    public async down(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`
            ALTER TABLE orders DROP CONSTRAINT IF EXISTS fk_orders_user_id
        `);
        await queryRunner.query(`
            DROP INDEX CONCURRENTLY IF EXISTS idx_orders_user_id
        `);
    }
}
```

## Section 8: Scenario-Based Questions

**Q14. "We're getting FK violation errors on INSERT but the parent row definitely exists — what could cause this?"**

A: This is one of the most confusing FK bugs. The parent row visually exists but the FK check fails — always a transaction isolation or timing issue:

```sql
-- ── Cause 1: Parent row created in a transaction that hasn't committed ─────────
-- Session A (not yet committed):
BEGIN;
INSERT INTO users (id, email) VALUES (42, 'alice@example.com');
-- (DO NOT COMMIT YET)

-- Session B:
INSERT INTO orders (user_id, total) VALUES (42, 99.99);
-- ERROR: insert or update on table "orders" violates foreign key constraint
-- DETAIL: Key (user_id)=(42) is not present in table "users".
--
-- Why: Session B runs at READ COMMITTED isolation (default).
-- User 42 was inserted by Session A but not yet committed.
-- READ COMMITTED can only see committed data → user 42 is invisible to Session B.
-- FK check fails even though the row "exists" (in an uncommitted transaction).
--
-- Fix: Commit Session A before Session B inserts the child row.
-- In application code: ensure parent is created and committed before creating children.

-- ── Cause 2: Race condition in application code ───────────────────────────────
-- Application checks user exists with one connection, then inserts order with another.
-- Another process deletes the user between the check and the insert.

-- BROKEN pattern:
const user = await userRepo.findOne({ where: { id: userId } }); // check
if (!user) throw new NotFoundException();
const order = await orderRepo.save({ userId, total });           // insert
// Between these two calls: user could be deleted → FK violation on insert.

-- CORRECT pattern A: Let the FK do the work (no application-level check needed):
try {
    const order = await orderRepo.save({ userId, total });
} catch (err) {
    if (err.code === '23503') {  // PostgreSQL FK violation error code
        throw new NotFoundException(`User ${userId} not found`);
    }
    throw err;
}

-- CORRECT pattern B: Wrap in a transaction (prevents the deletion between check and insert):
await dataSource.transaction(async (manager) => {
    const user = await manager.findOne(User, {
        where: { id: userId },
        lock: { mode: 'pessimistic_read' },  // FOR SHARE — prevents concurrent DELETE
    });
    if (!user) throw new NotFoundException();
    await manager.save(Order, { userId, total });
});

-- ── Cause 3: Deferred constraint checked at wrong point ───────────────────────
-- With DEFERRABLE INITIALLY DEFERRED, the FK error is thrown at COMMIT, not INSERT.
-- Application catches the error at COMMIT and misattributes it.
-- Reading the DETAIL in the error reveals the actual constraint violated:
-- ERROR: insert or update on table "orders" violates foreign key constraint "fk_orders_user"
-- DETAIL: Key (user_id)=(999) is not present in table "users".
-- Check error.detail in the application for the specific key value.

-- ── Cause 4: Wrong schema or connection ───────────────────────────────────────
-- The FK references users in schema 'public', but the insert is going to
-- orders in schema 'tenant_xyz'. The FK check looks in the wrong users table.
-- Fix: set search_path correctly, or use schema-qualified references.

-- ── Handling FK errors in TypeORM service ────────────────────────────────────
import { Injectable } from '@nestjs/common';
import { QueryFailedError } from 'typeorm';

@Injectable()
export class OrderService {
    async createOrder(userId: number, total: number): Promise<Order> {
        try {
            return await this.orderRepo.save({ userId, total });
        } catch (err) {
            if (err instanceof QueryFailedError) {
                const pgErr = err.driverError;
                switch (pgErr.code) {
                    case '23503':  // foreign_key_violation
                        // Parse pgErr.detail for constraint name and key value:
                        // 'Key (user_id)=(42) is not present in table "users".'
                        throw new NotFoundException(
                            `Referenced entity not found: ${pgErr.detail}`
                        );
                    case '23505':  // unique_violation
                        throw new ConflictException(`Duplicate entry: ${pgErr.detail}`);
                    case '23514':  // check_violation
                        throw new BadRequestException(`Constraint failed: ${pgErr.constraint}`);
                }
            }
            throw err;
        }
    }
}

-- ── PostgreSQL FK violation error codes ────────────────────────────────────────
-- 23000  integrity_constraint_violation (parent class)
-- 23001  restrict_violation
-- 23502  not_null_violation
-- 23503  foreign_key_violation   ← FK check failed
-- 23505  unique_violation
-- 23514  check_violation
-- 23P01  exclusion_violation
```

**Q15. "Design the complete FK and cascade strategy for a multi-tenant SaaS order management schema — all constraints, indexes, and deferral requirements."**

A: A production multi-tenant schema requires careful layering of FK constraints, cascade rules, indexes, and deferrable constraints for bulk operations:

```sql
-- ── Complete schema ───────────────────────────────────────────────────────────

CREATE TABLE tenants (
    id         BIGSERIAL    PRIMARY KEY,
    slug       TEXT         NOT NULL UNIQUE,
    name       TEXT         NOT NULL,
    plan       TEXT         NOT NULL DEFAULT 'free',
    created_at TIMESTAMPTZ  DEFAULT NOW(),
    deleted_at TIMESTAMPTZ             -- Soft delete (avoid CASCADE hell)
);

CREATE TABLE users (
    id          BIGSERIAL    PRIMARY KEY,
    tenant_id   BIGINT       NOT NULL REFERENCES tenants(id) ON DELETE RESTRICT,
    email       TEXT         NOT NULL,
    name        TEXT         NOT NULL,
    role        TEXT         NOT NULL DEFAULT 'member',
    created_at  TIMESTAMPTZ  DEFAULT NOW(),
    deleted_at  TIMESTAMPTZ,
    UNIQUE (tenant_id, email)          -- Unique email per tenant
);
CREATE INDEX idx_users_tenant_id ON users(tenant_id);

CREATE TABLE products (
    tenant_id   BIGINT         NOT NULL,
    id          BIGSERIAL      NOT NULL,
    name        TEXT           NOT NULL,
    sku         TEXT           NOT NULL,
    price       NUMERIC(10,2)  NOT NULL CHECK (price >= 0),
    stock       INT            NOT NULL DEFAULT 0 CHECK (stock >= 0),
    deleted_at  TIMESTAMPTZ,
    PRIMARY KEY (tenant_id, id),
    UNIQUE (tenant_id, sku),
    CONSTRAINT fk_products_tenant
        FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE RESTRICT
);
CREATE INDEX idx_products_tenant ON products(tenant_id);

CREATE TABLE orders (
    tenant_id   BIGINT         NOT NULL,
    id          BIGSERIAL      NOT NULL,
    user_id     BIGINT         NOT NULL,
    status      TEXT           NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','confirmed','shipped','delivered','cancelled')),
    total       NUMERIC(10,2)  NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ    DEFAULT NOW(),
    PRIMARY KEY (tenant_id, id),
    CONSTRAINT fk_orders_tenant
        FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE RESTRICT,
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE RESTRICT     -- Don't delete user if they have orders
        DEFERRABLE INITIALLY IMMEDIATE  -- Can defer for bulk import
);
CREATE INDEX idx_orders_tenant    ON orders(tenant_id);
CREATE INDEX idx_orders_user      ON orders(user_id);
CREATE INDEX idx_orders_status    ON orders(tenant_id, status);

CREATE TABLE order_items (
    tenant_id   BIGINT         NOT NULL,
    id          BIGSERIAL      NOT NULL,
    order_id    BIGINT         NOT NULL,
    product_id  BIGINT         NOT NULL,
    quantity    INT            NOT NULL CHECK (quantity > 0),
    unit_price  NUMERIC(10,2)  NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (tenant_id, id),
    CONSTRAINT fk_items_order
        FOREIGN KEY (tenant_id, order_id)    -- Composite FK: ensures same-tenant
        REFERENCES orders(tenant_id, id)
        ON DELETE CASCADE                    -- Items owned by order
        DEFERRABLE INITIALLY DEFERRED,       -- For bulk order creation
    CONSTRAINT fk_items_product
        FOREIGN KEY (tenant_id, product_id)  -- Composite FK: ensures same-tenant
        REFERENCES products(tenant_id, id)
        ON DELETE RESTRICT                   -- Cannot delete product in an order
);
CREATE INDEX idx_items_order   ON order_items(tenant_id, order_id);
CREATE INDEX idx_items_product ON order_items(tenant_id, product_id);

CREATE TABLE shipments (
    id          BIGSERIAL    PRIMARY KEY,
    tenant_id   BIGINT       NOT NULL,
    order_id    BIGINT       NOT NULL,
    tracking    TEXT,
    shipped_at  TIMESTAMPTZ,
    CONSTRAINT fk_shipments_order
        FOREIGN KEY (tenant_id, order_id)
        REFERENCES orders(tenant_id, id)
        ON DELETE CASCADE                -- Shipments owned by order
);
CREATE INDEX idx_shipments_order ON shipments(tenant_id, order_id);

-- ── Rationale for each cascade choice ────────────────────────────────────────
-- tenants → users:      RESTRICT   (don't cascade-delete thousands of users)
-- tenants → products:   RESTRICT   (audit trail; soft-delete tenants instead)
-- users   → orders:     RESTRICT   (preserve order history when user is deleted)
-- orders  → items:      CASCADE    (items have no meaning without an order)
-- orders  → shipments:  CASCADE    (shipments have no meaning without an order)
-- items   → products:   RESTRICT   (cannot delete a product that's been ordered)

-- ── Bulk order creation using deferrable constraints ──────────────────────────
-- Create an order with 100 items atomically, FK checked at COMMIT:
async function createOrderWithItems(
    tenantId:  number,
    userId:    number,
    items:     Array<{ productId: number; quantity: number; unitPrice: number }>,
    dataSource: DataSource,
): Promise<void> {
    await dataSource.transaction(async (manager) => {
        // fk_items_order is DEFERRABLE INITIALLY DEFERRED —
        // we can insert items before the order total is finalised.
        await manager.query('SET CONSTRAINTS fk_items_order DEFERRED');

        const [order] = await manager.query(`
            INSERT INTO orders (tenant_id, user_id, total)
            VALUES ($1, $2, 0)
            RETURNING id
        `, [tenantId, userId]);

        const orderId = order.id;
        const total   = items.reduce((sum, i) => sum + i.unitPrice * i.quantity, 0);

        // Insert all items in one statement:
        const values  = items.map((item, i) => `($1, $${i*3+2}, $${i*3+3}, $${i*3+4})`).join(',');
        const params  = [orderId, ...items.flatMap(i => [i.productId, i.quantity, i.unitPrice])];
        await manager.query(`
            INSERT INTO order_items (order_id, product_id, quantity, unit_price)
            VALUES ${values}
        `, [tenantId, ...params]);

        await manager.query(`
            UPDATE orders SET total = $1 WHERE id = $2 AND tenant_id = $3
        `, [total, orderId, tenantId]);
        // COMMIT: fk_items_order checked → all items reference the real order ✓
    });
}

-- ── Observing all constraints in the final schema ─────────────────────────────
SELECT
    tc.table_name,
    tc.constraint_name,
    tc.constraint_type,
    ccu.table_name  AS references,
    rc.delete_rule,
    rc.is_deferrable,
    rc.initially_deferred
FROM   information_schema.table_constraints    tc
JOIN   information_schema.key_column_usage     kcu USING (constraint_name, table_schema)
JOIN   information_schema.constraint_column_usage ccu USING (constraint_name, table_schema)
JOIN   information_schema.referential_constraints rc  USING (constraint_name, table_schema)
WHERE  tc.constraint_type = 'FOREIGN KEY'
AND    tc.table_schema    = 'public'
ORDER  BY tc.table_name;
```

## Quick Reference Tables

### `ON DELETE` / `ON UPDATE` Actions

| Action | Child row when parent deleted/updated | Child FK must be nullable? | When to use |
|---|---|---|---|
| `NO ACTION` (default) | Error at end of statement | No | Default — explicit intent to block |
| `RESTRICT` | Error immediately at row level | No | When deferral must not apply |
| `CASCADE` | Deleted / updated to match | No | Child owned by parent; no meaning without it |
| `SET NULL` | FK column set to `NULL` | **Yes** | Child exists independently; reference cleared |
| `SET DEFAULT` | FK column set to default | Default must be valid FK value | Reassign to a fallback parent |

### Deferrable Constraint Modes

| Mode | When checked | `SET CONSTRAINTS` effect | Use case |
|---|---|---|---|
| `NOT DEFERRABLE` (default) | After each statement | No effect | Standard constraints |
| `DEFERRABLE INITIALLY IMMEDIATE` | After each statement | Can be deferred per-tx | Opt-in deferral when needed |
| `DEFERRABLE INITIALLY DEFERRED` | At `COMMIT` | Can be made immediate per-tx | Circular refs, bulk loads, reordering |

### PostgreSQL FK Error Codes

| Code | Name | Cause |
|---|---|---|
| `23503` | `foreign_key_violation` | FK value not found in parent (INSERT/UPDATE child or DELETE parent) |
| `23505` | `unique_violation` | Duplicate value in unique/PK constraint |
| `23502` | `not_null_violation` | NULL in NOT NULL column |
| `23514` | `check_violation` | CHECK constraint failed |
| `23P01` | `exclusion_violation` | EXCLUDE constraint failed |

### FK Checklist for Production Schemas

| Item | Check | Fix |
|---|---|---|
| Index on every FK column | `pg_stat_user_indexes` shows `idx_scan > 0` | `CREATE INDEX CONCURRENTLY` |
| Constraint naming | All FKs named explicitly | `ADD CONSTRAINT fk_... FOREIGN KEY ...` |
| NOT NULL on required FKs | `nullable: false` in TypeORM | `COLUMN NOT NULL` in DDL |
| Large-table FK addition | Use `NOT VALID` + `VALIDATE` separately | Two-phase migration |
| Cascade depth > 3 | Review for accidental bulk delete risk | Consider soft deletes |
| Deferrable for circular refs | `DEFERRABLE INITIALLY DEFERRED` | Raw SQL in migration |
| `random_page_cost` for FK checks | Tuned for SSD if applicable | `SET random_page_cost = 1.1` |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) knowing that **FK constraints are enforced by internally managed triggers** — four system triggers per constraint — and that these triggers fire on every INSERT, UPDATE, and DELETE touching the constrained columns, making FK enforcement invisible overhead that accumulates at scale; (2) being precise about the **implicit `FOR KEY SHARE` lock** that every child-table INSERT acquires on the referenced parent row — this is the most common hidden source of lock contention in high-write applications, and it persists until the child's transaction commits; (3) knowing that **PostgreSQL does NOT automatically create indexes on FK columns** in child tables — a missing index on an FK column means every parent DELETE requires a full sequential scan of the child table, which at scale causes both catastrophic performance and long lock hold times; (4) being exact about the difference between **`NO ACTION` and `RESTRICT`** — both reject FK violations, but `NO ACTION` defers its check to the end of the statement (allowing within-statement tricks like triggers that fix violations), while `RESTRICT` fires immediately at the row level and ignores deferral even for deferrable constraints; (5) understanding the **`NOT VALID` + `VALIDATE CONSTRAINT` two-phase pattern** for adding FKs to large live tables — `NOT VALID` acquires a brief `ACCESS EXCLUSIVE` but does no row scanning, then `VALIDATE CONSTRAINT` uses `SHARE UPDATE EXCLUSIVE` (non-blocking) to check existing rows; skipping this pattern risks minutes of table unavailability; (6) knowing that **`DEFERRABLE INITIALLY DEFERRED` is the solution for circular references** (department has a manager who is an employee, employees belong to a department) and for reordering items with unique position columns — without deferral, these patterns require workarounds like temporary NULL values or artificial gap values; (7) understanding that **TypeORM's `cascade: true` on `@OneToMany` is application-level cascade** (TypeORM saves related entities in separate SQL statements) which is completely different from SQL-level `ON DELETE CASCADE` (the database deletes child rows automatically) — confusing these two is a common source of data integrity bugs; and (8) knowing that **composite FK columns must ALL be covered by a single composite index** — a separate index on each column individually does not satisfy the FK check for composite keys, and the index column order must match the FK column declaration order.
