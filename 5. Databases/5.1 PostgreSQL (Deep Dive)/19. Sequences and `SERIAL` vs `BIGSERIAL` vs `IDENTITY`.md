# PostgreSQL Sequences: `SERIAL` vs `BIGSERIAL` vs `IDENTITY` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a sequence in PostgreSQL and how does it work at the storage level?**

A: A sequence is a special single-row table that generates monotonically increasing (or decreasing) integer values. It is an independent database object — not tied to any column or table — that maintains its own state and provides the `nextval()`, `currval()`, and `setval()` functions for interacting with it:

```sql
-- Create a standalone sequence:
CREATE SEQUENCE order_id_seq
    START WITH 1
    INCREMENT BY 1
    MINVALUE 1
    MAXVALUE 9223372036854775807   -- default: max BIGINT
    NO CYCLE                       -- error when exhausted (CYCLE restarts from MINVALUE)
    CACHE 1;                       -- how many values to pre-allocate per session

-- The sequence is a real object in the catalog:
SELECT * FROM pg_class WHERE relname = 'order_id_seq' AND relkind = 'S';
-- relkind = 'S' → sequence

-- Inspect its current state:
SELECT * FROM order_id_seq;
--  last_value | log_cnt | is_called
-- ────────────┼─────────┼──────────
--           1 │      32 │ f
-- last_value: the value last returned (or start value if never called)
-- is_called:  false = nextval() will return last_value itself on first call
--             true  = nextval() will increment first, then return

-- Interact with the sequence:
SELECT nextval('order_id_seq');  -- Returns 1 (first call), increments internal state
SELECT nextval('order_id_seq');  -- Returns 2
SELECT currval('order_id_seq');  -- Returns 2 (last value returned in THIS session)
SELECT lastval();                -- Returns 2 (last value from ANY sequence in this session)

-- Jump to a specific value (e.g., after bulk data import):
SELECT setval('order_id_seq', 1000);          -- Next nextval() returns 1001
SELECT setval('order_id_seq', 1000, false);   -- Next nextval() returns 1000
--                                      ↑ is_called = false → returns this value itself

-- Use the sequence in an INSERT:
INSERT INTO orders (id, user_id, total)
VALUES (nextval('order_id_seq'), 42, 99.99);
```

How sequences maintain state across crashes — the critical property:

```sql
-- Sequences are NOT transactional for their counter.
-- This is intentional and fundamental to their design.

BEGIN;
SELECT nextval('order_id_seq');  -- Returns 3
ROLLBACK;
-- The sequence value is NOT rolled back — it stays at 3
-- Next call: nextval() returns 4

-- Why non-transactional?
-- If sequences were transactional, concurrent sessions would block each other
-- waiting for sequences in a serialised queue.
-- Non-transactional = multiple sessions can call nextval() concurrently
-- without any locking. The trade-off: gaps are normal and expected.

-- Consequence: sequence values can have GAPS
-- Gaps occur when:
-- 1. A transaction uses a sequence value then rolls back
-- 2. CACHE > 1 (pre-allocated values are lost on session termination)
-- 3. Server crash while cached values were in memory

-- Sequence state survives server restarts (written to storage, not WAL for every increment)
-- PostgreSQL flushes the sequence state to disk every log_cnt increments
-- (visible in pg_class.relfilenode — the sequence file is 24 bytes)
```

**Q2. What is `SERIAL` and what does it actually create under the hood?**

A: `SERIAL` is not a true data type — it is a PostgreSQL-specific shorthand notation (a "macro") that expands into three separate SQL statements when the `CREATE TABLE` runs. Understanding what it creates is essential for managing sequences independently:

```sql
-- When you write this:
CREATE TABLE orders (
    id    SERIAL PRIMARY KEY,
    total NUMERIC(10, 2)
);

-- PostgreSQL internally executes these three things:

-- 1. Creates a sequence named <table>_<column>_seq:
CREATE SEQUENCE orders_id_seq
    START WITH 1
    INCREMENT BY 1
    NO MINVALUE
    NO MAXVALUE
    CACHE 1;

-- 2. Creates the column as INTEGER with a default that calls nextval():
-- id INTEGER NOT NULL DEFAULT nextval('orders_id_seq')
-- (SERIAL does NOT automatically add PRIMARY KEY — you must add it explicitly)
-- (In the example above, PRIMARY KEY is explicit — SERIAL only adds the default)

-- 3. Transfers ownership of the sequence to the column:
ALTER SEQUENCE orders_id_seq OWNED BY orders.id;
-- OWNED BY means: drop the sequence when the table (or column) is dropped

-- Verify what was created:
\d orders
-- Column │  Type   │ Nullable │            Default
-- ───────┼─────────┼──────────┼───────────────────────────────────────
-- id     │ integer │ not null │ nextval('orders_id_seq'::regclass)
-- total  │ numeric │          │

-- Inspect the sequence:
\d orders_id_seq
-- Type: integer          ← SERIAL creates an integer-typed sequence (max ~2.1 billion)
-- Start: 1
-- Minimum: 1
-- Maximum: 2147483647    ← INT max (2^31 - 1)
-- Increment: 1
-- Cycles?: no
-- Cache: 1
-- Owned by: orders.id   ← owned by the column

-- The sequence is a separate object — you can manipulate it independently:
SELECT setval('orders_id_seq', 5000);  -- Jump the counter
ALTER SEQUENCE orders_id_seq INCREMENT BY 10;  -- Change step size
```

The four SERIAL pseudo-types and their underlying integer sizes:

```sql
-- SMALLSERIAL → SMALLINT (2 bytes, -32768 to 32767)
-- SERIAL      → INTEGER  (4 bytes, -2,147,483,648 to 2,147,483,647)
-- BIGSERIAL   → BIGINT   (8 bytes, -9,223,372,036,854,775,808 to 9,223,372,036,854,775,807)

-- Practical range for auto-increment (starting from 1, positive only):
-- SMALLSERIAL: max ~32,767 rows         → almost never use for IDs
-- SERIAL:      max ~2.1 billion rows    → sufficient for many applications
-- BIGSERIAL:   max ~9.2 quintillion rows → essentially inexhaustible

-- Check how full a SERIAL column is:
SELECT
    last_value,
    2147483647 AS max_value,
    round(last_value::numeric / 2147483647 * 100, 2) AS pct_used
FROM orders_id_seq;

-- Exhausting a SERIAL column:
-- When nextval() exceeds 2147483647 on a SERIAL column:
-- ERROR:  integer out of range
-- The INSERT fails even though the sequence could continue generating values
-- (the sequence itself is not exhausted — the COLUMN type is)
-- Fix: ALTER TABLE orders ALTER COLUMN id TYPE BIGINT;
--      (sequence continues from where it left off)
```

## Section 2: SERIAL vs BIGSERIAL

**Q3. When should you use `SERIAL` vs `BIGSERIAL` — and is there a scenario where `SERIAL` overflows in practice?**

A: The choice is a capacity planning decision. While 2.1 billion rows seems enormous, several real-world patterns can exhaust a `SERIAL` faster than expected:

```sql
-- Case 1: High-volume event or audit tables
-- An application logging 1,000 events per second:
-- 1,000 × 60 × 60 × 24 × 365 = 31,536,000,000 per year
-- SERIAL exhausted in: 2,147,483,647 / 31,536,000,000 ≈ 68 days

-- Case 2: Soft deletes accumulate sequence gaps
-- App inserts 10M rows per day, deletes 9.9M, net growth is 100k/day
-- But the SEQUENCE increments for every insert, not just retained rows
-- After 215 days: sequence exhausted, table has only ~21M live rows

-- Case 3: Rollbacks and CACHE > 1 waste values
-- With CACHE = 100 and 1000 application server instances:
-- At startup, each server pre-allocates 100 values → 100,000 values "used"
-- After deployment: these cached values are gone (not rolled back to the sequence)

-- Case 4: Multi-tenant SaaS with shared ID space
-- Sequences are per-table but IDs are used in URLs shared across tenants
-- Competitor intelligence: tenant B can guess tenant A's order count from IDs

-- DECISION FRAMEWORK:
-- Use SERIAL when:
--   - Table will never exceed ~500 million rows in its lifetime
--   - Storage efficiency matters (4 bytes vs 8 bytes per row)
--   - Legacy schema compatibility (joins with existing INTEGER foreign keys)

-- Use BIGSERIAL when:
--   - High-volume tables (events, logs, messages, audit trails)
--   - You're unsure about future scale — defaulting to BIGSERIAL costs very little
--   - The table stores time-series data that grows indefinitely

-- The cost of BIGSERIAL vs SERIAL:
-- 4 extra bytes per row × 100 million rows = 400 MB extra storage
-- On a 1TB table this is 0.04% overhead — usually irrelevant

-- Best practice (2024): always use BIGSERIAL or IDENTITY BIGINT
-- Storage is cheap; schema migrations to fix overflow are expensive

-- Example of a dangerous SERIAL usage:
CREATE TABLE events (
    id         SERIAL PRIMARY KEY,    -- DANGEROUS for event tables
    user_id    INTEGER,
    event_type VARCHAR(50),
    payload    JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
-- A busy SaaS application with 100k users generating 100 events/day:
-- 100,000 × 100 × 365 = 3,650,000,000 events/year → overflow in 7 months

-- Safe version:
CREATE TABLE events (
    id         BIGSERIAL PRIMARY KEY,  -- 9.2 quintillion rows -- effectively unlimited
    user_id    INTEGER,
    event_type VARCHAR(50),
    payload    JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Q4. What are the operational problems with `SERIAL` that make `IDENTITY` columns preferred?**

A: `SERIAL` has several rough edges that cause real operational problems. These motivated the introduction of `IDENTITY` columns in PostgreSQL 10:

```sql
-- Problem 1: The sequence is NOT truly bound to the column
-- SERIAL creates a sequence and sets a DEFAULT, but the DEFAULT can be bypassed:

CREATE TABLE users (id SERIAL PRIMARY KEY, email TEXT);

-- User can INSERT an explicit value, bypassing the sequence:
INSERT INTO users (id, email) VALUES (1, 'alice@example.com');  -- Works fine
INSERT INTO users (id, email) VALUES (1, 'bob@example.com');    -- Fails: duplicate
-- But now the sequence still starts at 1:
INSERT INTO users (email) VALUES ('carol@example.com');  -- Gets id=1 → DUPLICATE KEY ERROR

-- The sequence has no idea you manually inserted id=1
-- Fix: manually advance the sequence after bulk loading explicit values
SELECT setval('users_id_seq', (SELECT MAX(id) FROM users));

-- Problem 2: SERIAL is non-standard SQL — not portable
-- Works only in PostgreSQL (and a few PostgreSQL-compatible forks)
-- IDENTITY (SQL:2003 standard) is supported by PostgreSQL, Oracle, DB2, SQL Server, MariaDB 10.3+

-- Problem 3: The DEFAULT can be overridden by ORM column definitions
-- Some ORMs (older Hibernate, certain NestJS/TypeORM configs) set the DEFAULT
-- on INSERT to a value fetched from the sequence outside the INSERT statement:
-- SELECT nextval('users_id_seq');  -- Gets value N in Java
-- INSERT INTO users (id, email) VALUES (N, 'alice@example.com');
-- This bypasses the server-side DEFAULT entirely — harmless but unidiomatic

-- Problem 4: Column ownership and DROP semantics are surprising
-- OWNED BY means the sequence is dropped when the column is dropped:
ALTER TABLE users DROP COLUMN id;
-- This ALSO drops the sequence orders_id_seq — without a separate warning

-- But if you rename the table, the sequence name doesn't change:
ALTER TABLE users RENAME TO customers;
-- Sequence is still named: users_id_seq  ← confusing after rename

-- Problem 5: pg_dump and schema migrations are messy
-- pg_dump renders SERIAL as:
-- id integer NOT NULL,
-- ...
-- CREATE SEQUENCE users_id_seq ...
-- ALTER SEQUENCE users_id_seq OWNED BY users.id;
-- ALTER TABLE ONLY users ALTER COLUMN id SET DEFAULT nextval('users_id_seq'::regclass);
-- Four separate statements for what should be one concept

-- IDENTITY avoids all of these (see Q5)
```

## Section 3: IDENTITY Columns

**Q5. What is an `IDENTITY` column — how does it differ from `SERIAL` and what is its syntax?**

A: `IDENTITY` columns (SQL:2003 standard, PostgreSQL 10+) are the modern replacement for `SERIAL`. They are semantically a true column property rather than a sequence + default shorthand. The key functional difference is that `IDENTITY` columns can be configured to reject explicit value insertion entirely:

```sql
-- IDENTITY column syntax:
CREATE TABLE orders (
    id    INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    total NUMERIC(10, 2)
);

-- OR: GENERATED BY DEFAULT (more permissive — allows explicit INSERT)
CREATE TABLE orders (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    total NUMERIC(10, 2)
);

-- With sequence options inline:
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY (
        START WITH 1000
        INCREMENT BY 1
        CACHE 10
    ) PRIMARY KEY,
    total NUMERIC(10, 2)
);
```

`GENERATED ALWAYS` vs `GENERATED BY DEFAULT` — the critical distinction:

```sql
-- GENERATED ALWAYS: rejects explicit values entirely
CREATE TABLE orders_always (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    total NUMERIC(10, 2)
);

INSERT INTO orders_always (total) VALUES (99.99);           -- OK: id generated automatically
INSERT INTO orders_always (id, total) VALUES (5, 99.99);    -- ERROR:
-- ERROR:  cannot insert a non-DEFAULT value into column "id"
-- DETAIL: Column "id" is an identity column defined as GENERATED ALWAYS.
-- HINT:   Use OVERRIDING SYSTEM VALUE to override.

-- The only way to insert an explicit value with GENERATED ALWAYS:
INSERT INTO orders_always (id, total)
    OVERRIDING SYSTEM VALUE
    VALUES (5, 99.99);   -- Allowed, but use only for data migrations/fixes

-- GENERATED BY DEFAULT: allows explicit values (more like SERIAL behaviour)
CREATE TABLE orders_default (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    total NUMERIC(10, 2)
);

INSERT INTO orders_default (total) VALUES (99.99);          -- OK: id auto-generated
INSERT INTO orders_default (id, total) VALUES (5, 99.99);  -- OK: explicit value accepted
-- GENERATED BY DEFAULT is needed for:
-- - Data migrations (inserting rows with specific IDs from another system)
-- - ORMs that fetch the sequence value and pass it explicitly

-- GENERATED ALWAYS is preferred when:
-- - You want to prevent accidental explicit ID insertion
-- - IDs are purely internal (not meaningful business values)
-- - You want the strictest constraint for correctness

-- Using OVERRIDING USER VALUE with GENERATED BY DEFAULT:
-- (less common — not needed since explicit values are allowed)
INSERT INTO orders_default (id, total)
    OVERRIDING USER VALUE
    VALUES (5, 99.99);
-- OVERRIDING USER VALUE ignores the provided id and uses the generated value instead
-- Essentially the opposite of OVERRIDING SYSTEM VALUE
```

How `IDENTITY` avoids `SERIAL`'s problems:

```sql
-- Problem 1 solved: GENERATED ALWAYS prevents bypassing the sequence
INSERT INTO orders (total) VALUES (99.99);       -- Must use this form
-- No way to accidentally get sequence/value conflicts

-- Problem 2 solved: IDENTITY is standard SQL
-- Same syntax in Oracle, DB2, MariaDB 10.3+, SQL Server (with minor variations)

-- Problem 3 solved: ORMs can't set a custom DEFAULT
-- IDENTITY is a column attribute, not a DEFAULT expression
-- ORMs should use INSERT ... RETURNING id to get the generated value

-- Problem 4 solved: DROP TABLE drops the sequence without confusion
-- The sequence is owned by the identity column and cleaned up automatically
-- Renaming the table also renames nothing separately — the identity is part of the column

-- Problem 5 solved: pg_dump renders IDENTITY cleanly:
-- id bigint NOT NULL GENERATED ALWAYS AS IDENTITY
-- One line, standard SQL

-- Inspect an IDENTITY column:
\d orders
-- Column │  Type  │ Nullable │              Default
-- ───────┼────────┼──────────┼────────────────────────────────────────────────
-- id     │ bigint │ not null │ generated always as identity
-- total  │ numeric│          │

-- The underlying sequence (still created, but managed by PostgreSQL):
SELECT pg_get_serial_sequence('orders', 'id');
-- Returns: public.orders_id_seq
-- You can still manipulate it directly if needed:
SELECT setval(pg_get_serial_sequence('orders', 'id'), 10000);
-- But prefer ALTER TABLE instead (keeps everything in one place):
ALTER TABLE orders ALTER COLUMN id RESTART WITH 10000;
ALTER TABLE orders ALTER COLUMN id SET INCREMENT BY 5;
```

**Q6. How do you alter an `IDENTITY` column — changing sequence options, restarting, and converting from `SERIAL`?**

A: `IDENTITY` columns are managed through `ALTER TABLE` rather than `ALTER SEQUENCE`, keeping the operation at the logical level:

```sql
-- Restart the sequence (e.g., after truncating a table):
ALTER TABLE orders ALTER COLUMN id RESTART WITH 1;
-- Equivalent of: SELECT setval('orders_id_seq', 0, false);
-- But cleaner — no need to know the sequence name

-- Restart and reset all sequence options:
ALTER TABLE orders ALTER COLUMN id RESTART;
-- Resets to the START value defined when the column was created

-- Change sequence options:
ALTER TABLE orders ALTER COLUMN id SET INCREMENT BY 10;
ALTER TABLE orders ALTER COLUMN id SET START WITH 1000;
ALTER TABLE orders ALTER COLUMN id SET MINVALUE 1;
ALTER TABLE orders ALTER COLUMN id SET MAXVALUE 999999999;
ALTER TABLE orders ALTER COLUMN id SET CACHE 50;
ALTER TABLE orders ALTER COLUMN id SET CYCLE;    -- Restart from MINVALUE when exhausted
ALTER TABLE orders ALTER COLUMN id SET NO CYCLE; -- Error when exhausted (default)

-- Change GENERATED ALWAYS ↔ GENERATED BY DEFAULT:
ALTER TABLE orders ALTER COLUMN id SET GENERATED ALWAYS;
ALTER TABLE orders ALTER COLUMN id SET GENERATED BY DEFAULT;

-- Convert a SERIAL column to IDENTITY (common migration task):
-- Step 1: Drop the existing DEFAULT (which called nextval())
ALTER TABLE orders ALTER COLUMN id DROP DEFAULT;

-- Step 2: Drop the old sequence (after removing OWNED BY)
ALTER SEQUENCE orders_id_seq OWNED BY NONE;
DROP SEQUENCE orders_id_seq;

-- Step 3: Add IDENTITY with the current state preserved:
ALTER TABLE orders ALTER COLUMN id
    ADD GENERATED ALWAYS AS IDENTITY (
        START WITH 1
        RESTART WITH <current_max + 1>  -- Preserve existing IDs
    );
-- Replace <current_max + 1> with:
-- (SELECT MAX(id) + 1 FROM orders)

-- Practical migration with dynamic value:
DO $$
DECLARE
    next_id BIGINT;
BEGIN
    SELECT COALESCE(MAX(id), 0) + 1 INTO next_id FROM orders;

    ALTER TABLE orders ALTER COLUMN id DROP DEFAULT;
    ALTER SEQUENCE orders_id_seq OWNED BY NONE;
    DROP SEQUENCE orders_id_seq;
    ALTER TABLE orders ALTER COLUMN id
        ADD GENERATED ALWAYS AS IDENTITY (START WITH 1 RESTART WITH 1);
    -- Then restart to the actual next value:
    EXECUTE format('ALTER TABLE orders ALTER COLUMN id RESTART WITH %s', next_id);
END $$;

-- Verify:
\d orders
-- id │ bigint │ not null │ generated always as identity
```

## Section 4: Sequences in Depth

**Q7. What is the `CACHE` parameter and how does it affect performance and gap behaviour?**

A: The `CACHE` parameter determines how many sequence values each database session pre-allocates from the shared sequence object into its private memory. Higher cache values dramatically reduce contention on the sequence object but increase gap size:

```sql
-- Default: CACHE 1 — no pre-allocation, every nextval() hits the sequence object
CREATE SEQUENCE order_seq CACHE 1;

-- With CACHE 1:
-- Session A: nextval() → acquires lock on sequence → reads 1 → releases lock
-- Session B: nextval() → acquires lock on sequence → reads 2 → releases lock
-- Session C: nextval() → acquires lock on sequence → reads 3 → releases lock
-- Lock contention is real overhead at high concurrency

-- With CACHE 100:
CREATE SEQUENCE order_seq CACHE 100;
-- Session A: first nextval() → acquires lock once → pre-allocates 1..100 → releases lock
--            subsequent calls use cached values 1,2,3,...,100 without any lock
-- Session B: first nextval() → acquires lock once → pre-allocates 101..200 → releases lock
--            uses 101,102,...,200

-- Performance impact (approximate on a busy sequence):
-- CACHE 1:   ~10,000-50,000 nextval() calls/second (limited by lock overhead)
-- CACHE 100: ~1,000,000+ nextval() calls/second (mostly in-memory)

-- Gap implications with CACHE > 1:
-- If Session B pre-allocates 101..200 and then:
--   - Session B crashes / rolls back / server restarts
--   - Values 101..200 are LOST — they'll never be used
--   - The next session gets 201..300
-- This is expected behaviour, not a bug

-- Example: after server restart with CACHE 1000
-- Before restart: last used value was 547
-- After restart: sequence resumes from 1548 (PostgreSQL rounds up to next cache boundary)
-- Gap of ~1000 values — normal with high CACHE setting

-- When to use high CACHE values:
-- - Applications generating millions of IDs per day
-- - Multiple application server instances competing for sequence values
-- - Performance-critical bulk insert operations

-- When CACHE 1 is appropriate:
-- - Low-volume tables (< 1000 inserts/day)
-- - When gaps are completely unacceptable for audit/compliance (though they're unavoidable even with CACHE 1 due to rollbacks)
-- - Development environments where predictable IDs matter

-- Checking CACHE value for an existing sequence:
SELECT seqcache FROM pg_sequences WHERE sequencename = 'order_seq';
-- OR:
SELECT cache_size FROM pg_sequence WHERE seqrelid = 'order_seq'::regclass;
```

**Q8. How do sequences behave in concurrent environments — what guarantees does PostgreSQL provide?**

A: PostgreSQL sequences provide exactly one guarantee: every call to `nextval()` returns a unique value not returned to any other caller in the same or any other session. Everything else — ordering, consecutiveness, gap-freedom — is explicitly NOT guaranteed:

```sql
-- The one guarantee: uniqueness
-- These three sessions can all call nextval() simultaneously:
-- Session A: gets 1
-- Session B: gets 2
-- Session C: gets 3
-- No two sessions get the same value (enforced by a lightweight lock on the sequence)

-- What is NOT guaranteed:

-- 1. Ordering relative to COMMIT time
-- Session A: nextval()=1 (at 10:00:00), INSERT, slow processing, COMMIT at 10:00:10
-- Session B: nextval()=2 (at 10:00:01), INSERT, COMMIT at 10:00:02
-- In the table: row with id=2 was committed BEFORE row with id=1
-- You cannot sort by id and get chronological order reliably
-- Use a TIMESTAMPTZ column for true ordering

-- 2. Consecutive values (gaps are expected)
-- The following all cause gaps:
--   Rolled-back transactions
--   CACHE > 1 (wasted cached values on session end)
--   Server restarts with CACHE > 1
--   setval() jumps

-- 3. Absence of reuse
-- Once a value is issued by nextval(), it is never reissued
-- (unless you call setval() to manually go back — a dangerous operation)

-- 4. All values being used
-- With CACHE 100 and 10 sessions: sessions get blocks 1-100, 101-200, ..., 901-1000
-- But sessions use values in the order they insert — interleaved
-- Rows in the table will NOT have sequential IDs

-- Demonstration of non-sequential inserts with concurrent sessions:
-- Session A: nextval() = 1, INSERT (pending), slow computation...
-- Session B: nextval() = 2, INSERT (pending), COMMIT → row id=2 visible
-- Session A: COMMIT → row id=1 visible
-- SELECT * FROM orders ORDER BY id gives: 1, 2 (correct order)
-- SELECT * FROM orders ORDER BY created_at gives: 2, 1 (commit order)

-- The practical implication for APIs:
-- If you expose numeric IDs in URLs: /orders/1, /orders/2, ...
-- Competitors can probe consecutive IDs to enumerate your data
-- And: an id of 5000 doesn't mean "this is the 5000th order" (gaps exist)
-- Alternative: UUIDs, or opaque external IDs alongside internal sequence IDs

-- Checking for gaps (for audit purposes):
SELECT
    id,
    LEAD(id) OVER (ORDER BY id) AS next_id,
    LEAD(id) OVER (ORDER BY id) - id - 1 AS gap_size
FROM orders
WHERE LEAD(id) OVER (ORDER BY id) IS NOT NULL
    AND LEAD(id) OVER (ORDER BY id) - id > 1;
-- Shows all gaps: which id is followed by a gap, and how large

-- For compliance: if you MUST have gap-free audit numbers, use a separate
-- sequential counter managed within a transaction (much slower):
CREATE TABLE audit_numbers (
    next_number BIGINT NOT NULL DEFAULT 1
);
INSERT INTO audit_numbers VALUES (1);

-- In the same transaction as the audit event:
BEGIN;
UPDATE audit_numbers SET next_number = next_number + 1
RETURNING next_number - 1 AS audit_number;
-- This is serialised (UPDATE lock) — only one transaction at a time
-- True gap-free sequence but a global bottleneck
COMMIT;
```

## Section 5: UUID as an Alternative

**Q9. When should you choose `UUID` instead of a sequence-based primary key — and what are the trade-offs?**

A: UUIDs (Universally Unique Identifiers) are 128-bit values that can be generated without coordination, making them ideal for distributed systems. The trade-offs versus sequences are real and must be understood:

```sql
-- UUID primary key options in PostgreSQL:

-- Option A: gen_random_uuid() — random UUID v4 (PostgreSQL 13+ built-in)
CREATE TABLE orders (
    id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    total NUMERIC(10, 2)
);

-- Option B: uuid-ossp extension — various UUID versions
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE TABLE orders (
    id    UUID PRIMARY KEY DEFAULT uuid_generate_v4(),  -- random v4
    total NUMERIC(10, 2)
);

-- Option C: UUID v7 (time-ordered, available in PostgreSQL 17 or via extension)
-- UUID v7 is sequentially generated with a timestamp prefix:
-- 018f1b2c-3d4e-7000-8000-000000000001  ← first part is timestamp
-- This preserves the B-tree locality benefits of sequential IDs

-- ── SEQUENCE advantages over UUID ──────────────────────────────────────────────
-- 1. Storage: 4 bytes (INT) or 8 bytes (BIGINT) vs 16 bytes (UUID)
--    On a 100M row table with 5 indexes referencing the PK:
--    INT:  100M × 4B × 6 = 2.4 GB in PK + FK storage
--    UUID: 100M × 16B × 6 = 9.6 GB — 4× larger

-- 2. B-tree index performance: sequential IDs append to the rightmost leaf
--    → minimal page splits, predictable write pattern, better cache usage
--    Random UUIDs write to random leaf pages → frequent page splits → index bloat

-- 3. Human readability: order/12345 vs order/018f1b2c-3d4e-7000-8000-...
--    Easier for support, debugging, log analysis

-- 4. Join performance: INTEGER joins use simpler comparisons (4-byte integer equality)
--    UUID joins require 16-byte comparison — still fast, but slightly more CPU

-- ── UUID advantages over SEQUENCE ──────────────────────────────────────────────
-- 1. No central coordination needed
--    Application can generate UUIDs locally without a DB round-trip
--    Critical for: distributed systems, mobile offline-first apps, microservices

-- 2. No information leakage
--    Sequential IDs reveal: total record count, creation order, business volume
--    UUIDs are opaque — a competitor can't infer your order volume from URLs

-- 3. Merge-friendly
--    When combining data from multiple databases or shards:
--    Sequential IDs collide; UUIDs don't (with overwhelming probability)

-- 4. Pre-generation for INSERT batches
--    Generate 1000 UUIDs locally, use them in batch inserts
--    No need to round-trip for each ID or use currval() afterward

-- ── UUID v7: best of both worlds ────────────────────────────────────────────────
-- UUID v7 format (draft RFC):
-- [ 48-bit Unix timestamp in ms ][ 12-bit sequence ][ 62-bit random ]
-- 018f1b2c-3d4e-7xxx-xxxx-xxxxxxxxxxxx
-- ↑ Monotonically increasing (for the same millisecond, sequence increments)
-- → B-tree appends to rightmost leaf (like sequential integers)
-- → No coordination needed (like random UUIDs)
-- → Globally unique (like UUIDs)

-- PostgreSQL 17 adds UUIDv7 support; earlier versions use an extension:
-- https://github.com/fboulnois/pg_uuidv7
CREATE EXTENSION IF NOT EXISTS pg_uuidv7;
CREATE TABLE orders (
    id    UUID PRIMARY KEY DEFAULT uuid_generate_v7(),
    total NUMERIC(10, 2)
);

-- RECOMMENDATION matrix:
-- Single PostgreSQL instance, internal IDs only    → BIGINT GENERATED ALWAYS AS IDENTITY
-- Distributed system, microservices, mobile        → UUID v7 (or v4 if v7 unavailable)
-- Need human-readable short IDs in URLs            → BIGINT IDENTITY + slug/hash for external
-- Merging data from multiple sources/databases     → UUID
-- Maximum write performance on high-volume tables  → UUID v7 or BIGINT IDENTITY with CACHE
```

## Section 6: Practical Patterns

**Q10. How do you handle sequence resets after bulk data loads — the most common operational gotcha?**

A: After loading data with explicit IDs (from a backup, migration, or seed script), the sequence doesn't know about those IDs and will start from 1 — causing primary key violations on the next INSERT:

```sql
-- Scenario: bulk load from another system
TRUNCATE TABLE orders RESTART IDENTITY;  -- Resets sequence to 1

INSERT INTO orders (id, user_id, total) VALUES
    (1000, 1, 99.99),
    (1001, 2, 49.99),
    (2500, 3, 199.99);  -- Imported data with existing IDs

-- Now try a normal insert:
INSERT INTO orders (user_id, total) VALUES (4, 29.99);
-- ERROR: duplicate key value violates unique constraint "orders_pkey"
-- DETAIL: Key (id)=(1) already exists.
-- Sequence returned 1, but id=1 doesn't exist... wait...
-- Actually: sequence starts at 1, so it returned 1, but that ID is not in the table.
-- It returns 2, 3, 4... and eventually hits 1000 or 1001:
-- ERROR at id=1000: duplicate key value

-- Fix: advance the sequence past the highest existing ID:

-- Method 1: explicit setval (for SERIAL):
SELECT setval('orders_id_seq', (SELECT MAX(id) FROM orders));
-- setval with two args: is_called=true → NEXT nextval() returns MAX(id)+1

-- Method 2: setval with is_called=false (if you want NEXT call to return MAX(id) itself):
SELECT setval('orders_id_seq', (SELECT MAX(id) FROM orders), false);
-- Rarely what you want — use method 1

-- Method 3: ALTER TABLE for IDENTITY columns:
ALTER TABLE orders ALTER COLUMN id RESTART WITH (SELECT MAX(id) + 1 FROM orders);
-- Sadly: this doesn't accept a subquery directly — use DO block:
DO $$
DECLARE next_val BIGINT;
BEGIN
    SELECT COALESCE(MAX(id), 0) + 1 INTO next_val FROM orders;
    EXECUTE format('ALTER TABLE orders ALTER COLUMN id RESTART WITH %s', next_val);
END $$;

-- Method 4: TRUNCATE RESTART IDENTITY — only if you want to reset to 1:
TRUNCATE TABLE orders RESTART IDENTITY;
-- Resets sequence AND deletes all rows — use only when appropriate

-- Method 5: pg_get_serial_sequence — works for both SERIAL and IDENTITY:
SELECT setval(
    pg_get_serial_sequence('orders', 'id'),
    COALESCE(MAX(id), 0)
)
FROM orders;
-- pg_get_serial_sequence() returns the sequence name regardless of SERIAL vs IDENTITY

-- The safe post-load script pattern:
-- Always run this after any bulk data load with explicit IDs:
DO $$
DECLARE
    tbl TEXT := 'orders';
    col TEXT := 'id';
    seq TEXT;
    max_val BIGINT;
BEGIN
    seq := pg_get_serial_sequence(tbl, col);
    EXECUTE format('SELECT COALESCE(MAX(%I), 0) FROM %I', col, tbl) INTO max_val;
    PERFORM setval(seq, max_val);
    RAISE NOTICE 'Sequence % reset to %', seq, max_val;
END $$;
```

**Q11. How do `RETURNING` and sequences interact — how do you retrieve the generated ID after an INSERT?**

A: The `RETURNING` clause is the idiomatic PostgreSQL way to retrieve auto-generated values after an INSERT. It is superior to `lastval()` / `currval()` for correctness in concurrent applications:

```sql
-- ── RETURNING clause — best approach ──────────────────────────────────────────
INSERT INTO orders (user_id, total)
VALUES (42, 99.99)
RETURNING id;
--   id
-- ────
-- 1001

-- Return multiple generated/computed columns:
INSERT INTO orders (user_id, total)
VALUES (42, 99.99)
RETURNING id, created_at, total * 1.18 AS total_with_tax;
--   id  │         created_at         │ total_with_tax
-- ──────┼────────────────────────────┼────────────────
--  1001 │ 2024-01-15 10:30:00+05:30  │      117.9882

-- Batch insert with RETURNING — gets all generated IDs:
INSERT INTO orders (user_id, total)
VALUES (1, 50.00), (2, 75.00), (3, 100.00)
RETURNING id, user_id;
--  id   │ user_id
-- ──────┼─────────
--  1001 │       1
--  1002 │       2
--  1003 │       3
-- All three IDs returned in insertion order

-- ── currval() — session-scoped, error-prone ────────────────────────────────────
INSERT INTO orders (user_id, total) VALUES (42, 99.99);
SELECT currval('orders_id_seq');  -- Returns the ID just generated
-- Problem: if two inserts happened in the same session (e.g., via triggers),
-- currval() returns the LAST sequence value used in the session
-- not necessarily the one from YOUR insert

-- ── lastval() — even more dangerous ───────────────────────────────────────────
INSERT INTO orders (user_id, total) VALUES (42, 99.99);
SELECT lastval();
-- Returns the last value from ANY sequence used in the current session
-- If a trigger on orders also inserted into audit_log (which has its own sequence),
-- lastval() returns the audit_log sequence value, NOT the orders id

-- ── ORM patterns for RETURNING ────────────────────────────────────────────────

-- TypeORM (NestJS):
-- TypeORM uses RETURNING internally for IDENTITY/SERIAL columns
// @Entity()
// export class Order {
//     @PrimaryGeneratedColumn()  // maps to SERIAL or IDENTITY
//     id: number;
// }
// const order = await orderRepo.save({ userId: 42, total: 99.99 });
// order.id  // populated by TypeORM via RETURNING or lastval()

-- Prisma:
// const order = await prisma.order.create({
//     data: { userId: 42, total: 99.99 }
// });
// order.id  // Prisma uses RETURNING clause automatically

-- Raw SQL with node-postgres (pg):
// const result = await client.query(
//     'INSERT INTO orders (user_id, total) VALUES ($1, $2) RETURNING id',
//     [42, 99.99]
// );
// const orderId = result.rows[0].id;

-- ── INSERT INTO ... SELECT ... RETURNING ───────────────────────────────────────
-- Get IDs for a bulk insert derived from a query:
INSERT INTO order_archives (user_id, total, original_id)
SELECT user_id, total, id FROM orders WHERE created_at < '2023-01-01'
RETURNING id AS archive_id, original_id;
-- Returns the newly created archive_id alongside the original order id
-- for building the cross-reference mapping
```

## Section 7: Scenario-Based Questions

**Q12. "Your SERIAL primary key is approaching its maximum value (2.1 billion) in production. How do you fix it with zero downtime?"**

A:

```sql
-- Diagnosis: check current sequence state
SELECT
    last_value,
    2147483647 AS max_serial_value,
    round(last_value::numeric / 2147483647 * 100, 4) AS pct_used
FROM orders_id_seq;
--  last_value │ max_serial_value │ pct_used
-- ────────────┼──────────────────┼──────────
--  2000000000 │       2147483647 │   93.1%   ← critical

-- Column type check:
SELECT column_name, data_type, column_default
FROM information_schema.columns
WHERE table_name = 'orders' AND column_name = 'id';
-- id │ integer │ nextval('orders_id_seq'::regclass)  ← integer = SERIAL

-- PLAN: Expand the column type from INTEGER to BIGINT
-- (This is safe because BIGINT is a superset of INTEGER)

-- Step 1: Alter the COLUMN type (the sequence already generates BIGINT values)
-- In PostgreSQL, ALTER COLUMN TYPE on a primary key requires a brief lock
-- but the actual type cast INTEGER → BIGINT is instant (no table rewrite needed):
ALTER TABLE orders ALTER COLUMN id TYPE BIGINT;
-- This acquires an ACCESS EXCLUSIVE lock momentarily for the DDL,
-- but since INTEGER fits in BIGINT with no conversion, it's near-instant
-- (In PostgreSQL, integer widening to bigint does NOT require a table rewrite
-- on some versions — verify with your PostgreSQL version)

-- Step 2: Fix foreign key columns in referencing tables:
-- Find all foreign keys pointing to orders.id:
SELECT
    tc.table_name,
    kcu.column_name,
    ccu.table_name AS foreign_table,
    ccu.column_name AS foreign_column
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage ccu ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY' AND ccu.table_name = 'orders';

-- For each referencing column (e.g., order_items.order_id INTEGER):
ALTER TABLE order_items ALTER COLUMN order_id TYPE BIGINT;
-- Repeat for all FK tables

-- Step 3: Verify the sequence range is now sufficient:
\d orders_id_seq
-- Maximum: 9223372036854775807  ← BIGINT max — the sequence was ALWAYS bigint range
-- The sequence itself was not the problem — the COLUMN was INTEGER

-- Alternative: Convert to IDENTITY while we're at it:
-- Step 3 (continued): Upgrade to IDENTITY for future cleanliness:
ALTER TABLE orders ALTER COLUMN id DROP DEFAULT;
ALTER SEQUENCE orders_id_seq OWNED BY NONE;
DROP SEQUENCE orders_id_seq;
ALTER TABLE orders ALTER COLUMN id
    ADD GENERATED ALWAYS AS IDENTITY (
        START WITH 1
        RESTART WITH 2000000001  -- Continue from current position
    );

-- Zero downtime considerations:
-- ALTER COLUMN TYPE on integer→bigint: acquires brief ACCESS EXCLUSIVE lock
-- For a truly zero-downtime migration on a very busy table:
-- 1. Add a new BIGINT column: ALTER TABLE orders ADD COLUMN id_new BIGINT;
-- 2. Backfill: UPDATE orders SET id_new = id; (in batches)
-- 3. Create indexes on id_new
-- 4. In a brief maintenance window: swap id_new → id (rename columns)
-- This is complex — for most applications the direct ALTER is fast enough
```

**Q13. "You're designing a distributed payment system where order IDs are generated by multiple services before hitting the database. Which ID strategy do you choose?"**

A:

```sql
-- Requirements:
-- 1. Multiple services generate IDs (cannot coordinate with a central DB)
-- 2. IDs must be globally unique across all services/shards
-- 3. Good database insert performance (B-tree locality)
-- 4. Time-sortable (useful for debugging and pagination)
-- 5. Not guessable (don't expose business volume)

-- ANALYSIS of options:

-- OPTION A: BIGINT IDENTITY — REJECTED
-- Requires coordination: services must hit the DB to get an ID
-- In a distributed payment system, the DB is often on the other side of a network call
-- High-latency ID generation; single point of failure for ID generation

-- OPTION B: Random UUID v4 — PARTIALLY ACCEPTED
-- Pros: No coordination, globally unique, not guessable
-- Cons: Random writes to B-tree → frequent page splits → up to 30% write overhead
--       at scale (hundreds of millions of rows); poor cache performance

-- OPTION C: UUID v7 — BEST CHOICE
-- Pros: Time-ordered (B-tree locality), no coordination, globally unique, not guessable
-- Cons: Requires PostgreSQL 17 or extension; slightly more complex to generate in app

-- OPTION D: Snowflake ID / ULID — GOOD ALTERNATIVE
-- A 64-bit integer structured as: [timestamp_ms][datacenter][machine][sequence]
-- Sortable, no coordination needed if machine IDs are pre-assigned
-- Libraries available for Node.js, Java, Python, Go

-- CHOSEN ARCHITECTURE: UUID v7

-- Database schema:
CREATE TABLE payments (
    id           UUID PRIMARY KEY DEFAULT uuid_generate_v7(),
    order_id     UUID NOT NULL REFERENCES orders(id),
    amount       NUMERIC(15, 4) NOT NULL,
    currency     CHAR(3) NOT NULL,
    status       TEXT NOT NULL DEFAULT 'pending',
    idempotency_key TEXT UNIQUE,  -- Prevent duplicate payments
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processed_at TIMESTAMPTZ
);

-- Services generate IDs before INSERT:
-- Node.js (using uuidv7 npm package):
-- import { uuidv7 } from 'uuidv7';
-- const paymentId = uuidv7();  // '018f1b2c-3d4e-7000-8000-000000000001'
-- await db.query('INSERT INTO payments (id, ...) VALUES ($1, ...)', [paymentId, ...]);

-- Idempotency via the idempotency_key:
-- Payment service receives: { idempotencyKey: 'user_123_order_456_attempt_1', amount: 99.99 }
INSERT INTO payments (id, order_id, amount, currency, idempotency_key)
VALUES (uuid_generate_v7(), $1, $2, $3, $4)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING id, status;
-- If a duplicate payment request arrives: ON CONFLICT returns the original row
-- Prevents double charging even if the service retries

-- B-tree performance comparison:
-- Random UUIDs: each insert hits a random leaf page → cache miss → page split
-- Sequential INT: inserts hit only the rightmost leaf → hot page → always in cache
-- UUID v7: same as sequential INT (timestamp prefix keeps inserts ordered)

-- Index size comparison after 100M rows:
-- BIGINT PK index:     ~2.2 GB
-- Random UUID PK index: ~3.5 GB (larger due to key size + fragmentation)
-- UUID v7 PK index:    ~3.5 GB (same key size as UUID, but less fragmentation)

-- Additional recommendation: keep a human-friendly reference number
ALTER TABLE payments ADD COLUMN reference_number TEXT GENERATED ALWAYS AS (
    'PAY-' || UPPER(SUBSTRING(id::text, 1, 8))
) STORED;
-- Gives: PAY-018F1B2C for customer support and receipts
-- While UUID v7 is used internally for DB joins and API routing
```

## Quick Reference Table

| Feature | `SERIAL` | `BIGSERIAL` | `GENERATED ALWAYS AS IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY` |
|---|---|---|---|---|
| **SQL standard** | PostgreSQL only | PostgreSQL only | SQL:2003 ✓ | SQL:2003 ✓ |
| **Underlying type** | `INTEGER` (4 bytes) | `BIGINT` (8 bytes) | Any integer type | Any integer type |
| **Max value** | ~2.1 billion | ~9.2 quintillion | Depends on type | Depends on type |
| **Explicit INSERT** | Allowed (bypasses seq) | Allowed (bypasses seq) | Rejected (use OVERRIDING) | Allowed |
| **Sequence name** | `<table>_<col>_seq` | `<table>_<col>_seq` | `<table>_<col>_seq` | `<table>_<col>_seq` |
| **pg_dump output** | Multi-statement (messy) | Multi-statement (messy) | Single `GENERATED` clause | Single `GENERATED` clause |
| **Alter sequence** | `ALTER SEQUENCE` | `ALTER SEQUENCE` | `ALTER TABLE … ALTER COLUMN` | `ALTER TABLE … ALTER COLUMN` |
| **Restart** | `SELECT setval(...)` | `SELECT setval(...)` | `ALTER TABLE … RESTART` | `ALTER TABLE … RESTART` |
| **Recommended** | Legacy only | Legacy only | ✓ Preferred | When ORMs need explicit values |

| Scenario | Recommended ID type |
|---|---|
| New single-DB application | `BIGINT GENERATED ALWAYS AS IDENTITY` |
| Existing code using SERIAL | Keep SERIAL; migrate to IDENTITY on next opportunity |
| Table may exceed 2.1B rows | `BIGINT` — never use `INTEGER`/`SERIAL` |
| Distributed system, services generate IDs | UUID v7 (or ULID) |
| Need human-readable short IDs | `BIGINT IDENTITY` + computed reference column |
| Merging data from multiple sources | UUID (any version) |
| Lookup tables with < 32K rows | `SMALLINT` (not SMALLSERIAL — use IDENTITY) |

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **`SERIAL` is syntactic sugar**, not a real data type — it expands into a `CREATE SEQUENCE`, a column `DEFAULT nextval(...)`, and an `OWNED BY` clause; this matters when you need to manipulate the sequence independently or understand why `pg_dump` produces multi-statement output; (2) understanding the **`GENERATED ALWAYS` vs `GENERATED BY DEFAULT` distinction** — `GENERATED ALWAYS` rejects explicit value inserts (protecting sequence integrity) while `GENERATED BY DEFAULT` allows them; most new schemas should use `GENERATED ALWAYS` since ORMs should use `RETURNING` to get generated IDs, not pre-fetch them; (3) explaining **why sequences have gaps** and that gaps are not a bug — rolled-back transactions, `CACHE > 1` pre-allocation, and server restarts all cause gaps; the sequence guarantees uniqueness and monotonicity, not consecutiveness; candidates who claim "sequences should never have gaps" reveal a fundamental misunderstanding; (4) knowing the **SERIAL integer overflow problem** — `SERIAL` maps to `INTEGER` with a max of ~2.1 billion; high-volume event or audit tables can exhaust this in months, not years; the fix is `ALTER TABLE ... ALTER COLUMN id TYPE BIGINT` and the mitigation is always using `BIGSERIAL` or `BIGINT IDENTITY` for new tables; (5) being able to explain the **post-bulk-load sequence reset pattern** — after inserting rows with explicit IDs from a migration or seed script, the sequence doesn't know about them and will start at 1; the fix is `SELECT setval(pg_get_serial_sequence('table', 'col'), (SELECT MAX(id) FROM table))`, and forgetting this causes a cascade of primary key violations; and (6) knowing when to choose **UUID over sequences** — for distributed systems where multiple services need to generate IDs before hitting the database, random sequential IDs require DB coordination; UUID v7 (time-ordered) gives the B-tree locality benefits of sequential integers combined with the coordination-free generation of UUIDs.
